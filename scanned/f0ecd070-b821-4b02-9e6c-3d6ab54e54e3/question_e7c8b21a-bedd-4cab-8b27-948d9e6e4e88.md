Shipit::MergeRequest::StatusChecker#success? (subclass of `Status::Group`) determines merge-readiness purely from `head.statuses_and_check_runs`, which is populated identically whether the underlying `Status` came from the victim's own CI or from a forged cross-repo webhook via `StatusHandler#process`. Attacker action: attacker discovers the sha of the current head of a real pending merge-queued PR on `victim/prod` (visible via GitHub's public API on that PR) and pushes an identical commit to their own repo `attacker/evil`, then fires the status webhook. Preconditions: `merge_queue_enabled?` true on victim stack; attacker never has write access to `victim/prod`. Call sequence: identical to the previous chain but emphasizing the attacker never needed to interact with `victim/prod` at all - only read its public sha and control their own repo's webhook. Binding: `session[:user_id]`/API identity is irrelevant here because there is no authenticated actor in the write path at all - the binding that must hold is repository-of-webhook-secret == repository-of-mutated-MergeRequest, and it is absent. Scoped impact: Critical, zero-interaction cross-tenant merge forgery requiring only public read access to the victim's PR sha. Proof idea: minitest constructing two `shipit_commits` fixtures with identical shas in different stacks, POST the status webhook only against the attacker's stack context, assert the victim's `MergeRequest#all_status_checks_passed?` becomes true.
