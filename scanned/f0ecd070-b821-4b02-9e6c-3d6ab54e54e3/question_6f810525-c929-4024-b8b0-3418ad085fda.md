Shipit::Stack#next_expected_commit_to_deploy / UndeployedCommit#expected_to_be_deployed? gate the 'green means go' UI indicator using `deployable?` computed from the same unscoped Status writes. Attacker action: attacker forges `success` on a victim's mid-queue commit (not the newest), preconditions being `maximum_commits_per_deploy` set and multiple undeployed commits queued behind a real failing commit. Call sequence: `StatusHandler#process` mutates commit X's status -> `Stack#next_expected_commit_to_deploy` recomputes `commits_to_deploy.find(&:deployable?)` -> a commit becomes the 'expected to deploy' target ahead of the actually-passing commits, changing which commit `ContinuousDeliveryJob` deploys next. Binding: the repository whose CI produced the signal must equal the repository whose deploy ordering (`next_expected_commit_to_deploy`) is altered - it does not. Scoped impact: Critical, attacker selects which specific victim commit gets shipped by continuous delivery by forging status on it via an unrelated repository's webhook. Proof idea: minitest with three undeployed victim commits, none deployable, then posting the cross-repo forged status for the middle one, asserting `stack.next_commit_to_deploy` now returns that specific commit.
