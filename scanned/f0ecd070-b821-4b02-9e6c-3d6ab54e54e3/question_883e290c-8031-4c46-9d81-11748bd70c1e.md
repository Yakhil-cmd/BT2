Shipit::Commit.where(sha: params.sha) in StatusHandler#process performs no `.reachable` or `.limit` scoping and matches literally every `Commit` row across all `Stack`s sharing that sha, including commits belonging to archived or locked stacks. Attacker action: attacker forges a `success` status for a sha that matches a commit in a victim stack currently `locked?` for an unrelated safety reason (e.g. an incident freeze). Preconditions: victim stack `lock_reason` present. Call sequence: `create_status_from_github!` still executes and updates the `Status` row (locking doesn't prevent this) -> `Commit#deployable?`'s `!locked?` check refers to the *commit's* lock flag, not the *stack's* - so if only the stack (not the commit) is locked, `Stack#deployable?`'s own `!locked?` still blocks deploys, but `Commit#deployable?` on the commit will read true, corrupting any UI/API code path (e.g. `require_ci` on `Api::DeploysController#create` with `force: true`) that checks `commit.deployable?` without re-checking `stack.locked?`. Preconditions continued: operator or automation calls deploy with `force: true` believing the commit is CI-green. Binding: `commit.deployable?` truthiness must equal the actual CI state of the *victim's own* CI provider for that repository - it does not, since it was set by an attacker's unrelated repository. Scoped impact: Critical, forged deployability signal survives even when the stack is under an incident lock, misleading force-deploy decisions. Proof idea: minitest locking a victim stack, posting the cross-repo status webhook, asserting `commit.deployable?` is true while `stack.locked?` remains true, then exercising `Api::DeploysController#create` with `force: true`.
