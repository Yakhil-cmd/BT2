Shipit::UndeployedCommit#deploy_disallowed? is `!deployable? || !stack.deployable?`, feeding the stack page's per-commit 'Deploy' button gating shown to operators. Attacker action: attacker forges a cross-repo `success` status (as in the primary scenario) on a victim commit that an operator is about to review on the Stacks UI, making `deploy_disallowed?` return false when the real CI never passed. Preconditions: operator has the stack page open or is about to call the deploy API; victim commit previously showed `deploy_state == 'failure'`. Call sequence: `StatusHandler#process` -> `create_status_from_github!` -> `Commit#deployable?` flips -> `UndeployedCommit#deploy_disallowed?` flips to false -> operator (or an automated CD pipeline) calls `Api::DeploysController#create` with `require_ci: true`, which only checks `commit.deployable?` and passes. Binding: the repository whose CI produced the underlying signal (none, in this case attacker's SHA collision) must equal the repository whose deploy-gating flag (`deployable?`) is being trusted by `Api::DeploysController#create`'s `require_ci` check - it does not. Scoped impact: Critical, forged cross-repo CI state defeats the `require_ci` safety check on the deploy API, enabling deployment of an unverified commit. Proof idea: minitest posting the cross-repo status webhook then calling `Api::DeploysController#create` with `require_ci: true`, asserting response `:accepted` instead of the expected `:unprocessable_entity`.
