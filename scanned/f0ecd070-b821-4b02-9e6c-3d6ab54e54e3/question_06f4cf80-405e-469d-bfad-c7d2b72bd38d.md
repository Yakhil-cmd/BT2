Shipit::ProcessMergeRequestsJob#perform calls `merge_request.reject_unless_mergeable!` before checking `all_status_checks_passed?`; `reject_unless_mergeable!` only inspects `merge_conflict?`, `any_status_checks_missing?`, `any_status_checks_failed?`, and `stale?` - none of which validate that the underlying `Status` rows originated from the correct repository's CI. Attacker action: attacker opens PR #N on `victim/prod`, then before CI reports, posts a status webhook signed by `attacker/evil` claiming `state: success` for PR #N's head sha (shared via a crafted identical commit). Preconditions: PR #N's head commit has no real status yet (`any_status_checks_missing?` would normally be true and reject with `ci_missing`). Call sequence: forged `success` status is written to the shared commit row before `reject_unless_mergeable!` runs -> `any_status_checks_missing?` returns false -> PR is not rejected -> `all_status_checks_passed?` returns true -> `merge!` executes `stack.github_api.merge_pull_request`. Binding: the repository whose webhook_secret authenticated the status (attacker's) must equal the repository of the PR being merged (victim's) - it does not. Scoped impact: Critical, unauthorized merge of a pull request into the victim's default branch via GitHub API call using the app's own `GITHUB_TOKEN`, triggered purely by a forged webhook against an unrelated repository. Proof idea: minitest asserting `Shipit.github.api.expects(:merge_pull_request)` is called after seeding the cross-repo status webhook and running `ProcessMergeRequestsJob.perform_now(stack)` on a PR with no legitimate CI status.
