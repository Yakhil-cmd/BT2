Shipit::Commit#refresh_statuses! and RefreshStatusesJob both eventually call `create_status_from_github!`, but the vulnerable ingress is StatusHandler#process's direct GitHub-sourced webhook path with zero `stack`/`repository` predicate. Attacker action: attacker's repository is entirely unknown to Shipit (`Repository.from_github_repo_name('attacker/evil')` returns nil), so `Handler#stacks` would return `Stack.none`, yet `StatusHandler#process` never calls `stacks` at all - it queries `Commit` directly. Preconditions: attacker's org still has *a* `webhook_secret` configured in `Shipit.github_apps`/`Shipit.github(organization:)` config (any onboarded org, not necessarily one hosting the target repo). Call sequence: `verify_signature` succeeds because `repository_owner` resolves to any known org, even one with no relationship to the target commit's stack -> `StatusHandler.call` -> `Commit.where(sha:)` -> commits across every stack of every repository sharing that sha are mutated. Binding: the set of stacks reachable via `repository_name` (empty for unknown repo) must equal the set of commits actually mutated by `StatusHandler#process` (unrestricted `Commit.where(sha:)`) - it does not, proving the handler ignores repository identity entirely, not merely misresolves it. Scoped impact: Critical, database-wide cross-tenant writes independent of whether the sending repository is registered in Shipit at all. Proof idea: minitest stubbing `Repository.from_github_repo_name` to return nil (simulating an unknown attacker repo) while still asserting `commit.statuses.count` increases for a real victim commit sharing the sha.
