Target: `Shipit::Api::CCMenuController#stack` (overriding `Shipit::Api::BaseController#stack`). Attacker action: an unprivileged internet user holds an `ApiClient` token scoped with `stack_id` set to stack A (e.g. obtained via a leaked/legitimate CCMenu URL for stack A) and sends `GET /api/stacks/:stack_id/cc.xml?token=<tokenA>` with `stack_id` set to stack B's param instead of A's. Preconditions: `ApiClient` A exists with `stack_id: A.id` and `permissions: ['read:stack']`; stack B exists and is owned by a different repository/tenant. Call sequence: `authenticate_api_client` calls `ApiClient.authenticate(params[:token])` which succeeds and sets `@current_api_client` to client A; `#show` calls `stack`, which is overridden in `CCMenuController` to call `Stack.from_param!(params[:stack_id])` directly instead of going through `Shipit::Api::BaseController#stacks` (which would have scoped by `current_api_client.stack_id`). Binding that breaks: the stack an API request touches ∈ the stacks `current_api_client.stack_id` authorises -- here stack B ∉ {A}. Scoped impact: Critical, unauthenticated-scope read of stack B's deploy/build status belonging to another tenant, bypassing the token's intended single-stack scope. Proof idea: minitest controller test creating two stacks in different repos, an `ApiClient` scoped to stack A via `stack_id:`, and asserting `get :show, params: { stack_id: stackB.to_param, token: clientA.authentication_token }` returns stack B's data instead of a 404/403.
