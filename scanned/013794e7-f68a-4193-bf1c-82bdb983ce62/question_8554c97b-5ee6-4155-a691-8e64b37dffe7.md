Target: Shipit::Commit#refresh_statuses! / RefreshStatusesJob interplay with forged StatusHandler writes creating a race where victim's own legitimate GitHub poll is overwritten. Attacker action: immediately after victim's legitimate CI posts a 'pending' or 'failure' status through GitHub's real webhook (or Shipit's periodic RefreshStatusesJob), attacker POSTs a cross-org forged 'success' status for the same sha/context before or after, using Status ordering (`has_many :statuses, -> { order(created_at: :desc) }`) and `created_at` supplied directly from the untrusted payload (accepts :created_at, String) to force their forged row to sort as most recent. Preconditions: attacker controls the created_at string in the payload (StatusHandler.params `accepts :created_at, String`), no server-side clamping to Time.now observed. Call sequence: create_status_from_github! -> statuses.replicate_from_github!(stack_id, github_status) persists created_at verbatim; Commit#status ultimately orders by created_at desc, so a forged, artificially-future created_at from attacker's payload can outrank the genuine CI result regardless of real arrival order. Binding: created_at ordering used to determine Commit#status == arrival order of authenticated-for-this-repo events -- fails because an untrusted, foreign-org-authenticated created_at string can be set to any value. Scoped impact: Critical, an attacker can guarantee their forged cross-repo status wins the ordering race against victim's genuine CI signal indefinitely by supplying a future timestamp. Proof idea: test creating a real 'failure' status with created_at: Time.now, then use StatusHandler.call with an attacker-signed payload with created_at: 10.years.from_now and state: 'success', asserting commit.status.state becomes 'success'.
