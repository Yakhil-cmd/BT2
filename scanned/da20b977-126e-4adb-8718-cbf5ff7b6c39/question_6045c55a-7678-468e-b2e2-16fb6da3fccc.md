In lib/shipit/github_app.rb, GitHubApp#initialize memoizes `@webhook_secret = @config[:webhook_secret].presence` per organization instance, and Shipit.github(organization:) memoizes GitHubApp instances in `@github[organization]`. Attacker action: send two POSTs to /webhooks in sequence: first with repository_owner = 'org-with-secret-later-removed' while its config still has a webhook_secret (fails without correct HMAC), then -- exploiting operational reality that Shipit.github is a process-lifetime memoized singleton -- determine if a runtime config reload (e.g. secrets rotated without process restart) leaves the OLD webhook_secret cached in `@github[organization]`, meaning a signature valid under a previously-rotated-out secret is still accepted. Preconditions: operator rotates webhook_secret in the secrets store without restarting the Shipit process (a supported operational scenario per docs/setup.md's guidance to update `secret_key_base`/config live). Call sequence: Shipit.github(organization: org) returns the memoized GitHubApp built with the pre-rotation secret; verify_webhook_signature validates against stale key material. Binding: the webhook_secret used to verify the current request must equal the currently-configured (post-rotation) webhook_secret for that org, not a memoized stale one. Impact: High, authentication bypass window after secret rotation (an attacker who obtained an old leaked secret retains forge capability) -- note this requires an already-leaked secret so classify precisely as High, not Critical, and only demonstrable via memoization semantics, not a live leak. Proof idea: unit test constructing Shipit.github(organization: 'x') to memoize a GitHubApp, then mutating Shipit.secrets.github[:x][:webhook_secret] and asserting Shipit.github(organization: 'x').send(:webhook_secret) still returns the old value.
