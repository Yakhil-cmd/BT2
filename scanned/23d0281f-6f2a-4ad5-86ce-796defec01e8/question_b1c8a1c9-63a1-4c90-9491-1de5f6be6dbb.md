Target: Shipit::RollbackCommands#env and Shipit::Command#unbundled_env. Attacker action: an unprivileged contributor opens a PR against a repository with Review Stacks enabled and includes a `shipit.yml` on their own branch defining a `rollback.variables` entry named `GITHUB_TOKEN` (or `GIT_ASKPASS`, or `PATH`) with an attacker-chosen default. Preconditions: `Repository#review_stacks_enabled` is true and provisioning behavior is `allow_all`; the fork branch becomes `ReviewStack#branch` via `ReviewStackAdapter#stack_attributes`. Call sequence: `TaskCommands#env` builds `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` where `@task.env` was filtered only by `EnvironmentVariables#permit` against the KEYS defined in the attacker's own `deploy_spec.rollback_variables`, then `RollbackCommands#env` adds `ROLLBACK=1` and the merged hash is passed unmodified into `Command#unbundled_env` (`BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)`) right before `PTY.spawn`. Binding that breaks: the set of KEYS reaching `PTY.spawn` from `@task.env` must equal a host-controlled allowlist of variable NAMES, but it instead equals whatever keys the attacker's own `shipit.yml` declares. Scoped impact: Critical — RCE on the deploy host via `GITHUB_TOKEN`/`GIT_ASKPASS`/`PATH` clobbering in the spawned process environment for the repository being deployed. Proof idea: a minitest asserting that `Shipit::Commands.for(rollback).env['GITHUB_TOKEN']` differs from `Shipit.github(organization: stack.repository.owner).token` once a rollback variable named `GITHUB_TOKEN` is declared in the deploy spec and supplied by the triggering request.
