Target: `Status::STATES` enum and `Commit#state` (`delegate :state, to: :status`) as consumed by `Commit#revert_of?`/deploy safety UI, but concretely `Commit#blocked?`'s dependency on `stack.commits.reachable.newer_than(...).older_than(...).any?(&:blocking?)`. Attacker action: send two crafted status webhooks signed for their own repo: one marking a shared-sha earlier commit `error` (making it blocking) and, moments later after achieving some other goal, `success` (removing the block), all without ever holding credentials to the victim org. Precondition: victim stack uses `blocking_statuses`. Call sequence: both calls funnel through `StatusHandler#process` -> `Commit.where(sha:)` -> `create_status_from_github!`, each silently mutating the victim commit's CI status with no ownership check. Binding: the repository verified by `webhook_secret` on each of the two requests must equal the repository of the blocking commit's stack; neither request satisfies this. Scoped impact: Critical, an attacker can arbitrarily toggle a victim's deploy-blocking state on demand at any time, at will, from their own repository. Proof idea: minitest test posting two attacker-signed webhooks in sequence (error then success) for the same shared sha and asserting `commit.reload.blocking?` toggles accordingly for the victim's commit.
