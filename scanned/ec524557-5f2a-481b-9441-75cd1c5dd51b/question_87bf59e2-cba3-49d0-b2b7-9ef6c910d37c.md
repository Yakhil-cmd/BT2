In app/models/shipit/user.rb, `User.find_or_create_author_from_github_commit` matches `github_commit.commit.message` against `/^Merge-Requested-By: ([\w\-.]+)$/` and, if it matches, calls `find_or_create_by_login!(match_info[1])` which performs `Shipit.github.api.user(login)` and creates a `User` row -- entirely driven by an attacker-authored commit message with no check that the named login authorized this merge or that the commit was verified as belonging to a trusted actor. Attacker action: attacker pushes/merges a commit into a repository they control with a commit message body containing `Merge-Requested-By: victim-admin-login`, then triggers the `push`/`status` webhook flow that calls `Commit.from_github`. Precondition: `victim-admin-login` is a real GitHub login (public info); repository tracked by Shipit. Call sequence: webhook (`push`) -> `GithubSyncJob`/`Commit.from_github` -> `User.find_or_create_author_from_github_commit` -> `find_or_create_by_login!('victim-admin-login')` -> commit's `author` attributed to `victim-admin-login`'s `User` record. Binding: the GitHub identity that actually authored/approved the merge == the `author` on the `Commit` row; the commit-message-derived login can diverge from the real committer with nothing reconciling them. Scoped impact (Critical): attribution/authorization forgery -- a `Commit` (and downstream deploy) appears authored by an arbitrary GitHub user (e.g. a Shipit-authorized team member), which can be used to make an attacker's code appear pre-approved or bypass author-based deploy/merge policies. Proof idea: minitest test in test/models/commits_test.rb style asserting `Commit.create_from_github!` sets `commit.author.login == 'victim-admin-login'` purely from an attacker-controlled commit message, while the real Octokit `commit.author`/`commit.committer` (or the webhook sender) differs.
