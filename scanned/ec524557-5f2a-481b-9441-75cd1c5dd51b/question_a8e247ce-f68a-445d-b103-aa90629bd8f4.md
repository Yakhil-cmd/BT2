app/controllers/shipit/api/base_controller.rb `#identify_user` sets `current_user` from the `X-Shipit-User` request header (`User.where('lower(login) = ?', ...)`) with no cryptographic binding to the `ApiClient` that authenticated via `authenticate_api_client`/Basic auth token. Attacker action: an attacker who holds no ApiClient token cannot exploit this alone, but this is exploitable in combination with any endpoint that trusts `X-Shipit-User` -- e.g. app/controllers/shipit/api/rollbacks_controller.rb `#create` uses `current_user` as `deploy.trigger_rollback(current_user, ...)`; a caller who has ANY valid ApiClient token (even one scoped to `deploy:stack` only, not tied to any particular human) can set `X-Shipit-User: <any-login>` to attribute the rollback/deploy to an arbitrary Shipit `User` row. Precondition: at least one broadly-scoped ApiClient exists (host misconfiguration is out of scope, but the binding itself is never enforced by this engine regardless of configuration). Call sequence: `Api::BaseController#authenticate_api_client` verifies the `ApiClient` token only -> `#identify_user` trusts the header alone -> `RollbacksController#create` calls `deploy.trigger_rollback(current_user, ...)`. Binding: `current_api_client`'s bound identity (its `creator`) == `current_user` derived from `X-Shipit-User`; never checked. Scoped impact (High/Critical borderline -> classify Critical since it authorizes a deploy/rollback under a forged identity): unauthorized deploy/rollback attributed to an arbitrary user bypasses author-based audit trail and any per-user restriction. Proof idea: minitest test using `ApiHelper#authenticate!` with a generic client, setting `request.headers['X-Shipit-User']` to a different user's login than the ApiClient's `creator`, and asserting the resulting `Rollback#user` equals the impersonated login with no error.
