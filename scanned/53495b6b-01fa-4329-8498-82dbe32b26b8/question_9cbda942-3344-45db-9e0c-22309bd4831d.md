Target: Shipit::WebhooksController#repository_owner and #event (app/controllers/shipit/webhooks_controller.rb). Attacker action: POST /webhooks with header `X-Github-Event: push` but a JSON body shaped like a `membership` event (containing `organization.login` and `team`/`member` keys but no `repository` key), for an org configured without webhook_secret (chained with question 1) or for any org if a handler is registered generically. Preconditions: `Shipit::Webhooks::DEFAULT_HANDLERS['push']` present. Call sequence: `event` reads only the header, `repository_owner` falls back to `params.dig('organization','login')` when `repository` is absent, `verify_signature` picks the app for that org, then `Shipit::Webhooks.for_event('push')` handlers are invoked with a body they never validated matches a push shape (params access on missing keys). Binding that breaks: the handler invoked for event X == a body actually produced by GitHub for event X; the controller trusts the client-supplied header/body pairing completely. Impact: Critical if a handler's loose param access (`params.dig(...)`, no `requires` clause enforced before use) lets a mismatched body drive an unintended write (e.g. GithubSyncJob enqueued with attacker-chosen `after` sha for an existing stack) though the header claims a different semantic event than the body layout implies. Proof idea: minitest posting a push-shaped header with a membership-shaped body against a repo/org with a real webhook_secret disabled in test config, asserting whichever side-effect executes doesn't validate the mismatch.
