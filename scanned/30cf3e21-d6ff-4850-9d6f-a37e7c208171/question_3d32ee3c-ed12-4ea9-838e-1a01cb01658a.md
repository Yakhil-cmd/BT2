Target: `Shipit::Webhooks::Handlers::Handler#repository_name` versus `WebhooksController#repository_owner`. Attacker action: attacker crafts a webhook JSON body where `repository.owner.login` (used for signature-org selection) is a legitimate org they control, but `repository.full_name`'s prefix differs from `repository.owner.login` (GitHub normally guarantees these match, but nothing in this engine enforces it independently) — e.g. `repository.full_name = 'other-org/other-repo'` while `repository.owner.login = 'attacker-org'`. Preconditions: attacker controls the raw JSON body and can compute a valid HMAC with their own `webhook_secret`. Call sequence: `verify_signature` passes because it only checks `repository_owner` (`repository.owner.login`); `Handler#repository_name` then uses the independently-read `repository.full_name` to resolve `stacks`/`Repository`. Binding: `repository.owner.login` (verified) must equal the owner prefix of `repository.full_name` (used to mutate); the engine reads these as two separate JSON paths and never asserts equality. Impact: Critical — this is the exact missing binding described in the target file's scope: a signed-but-mismatched payload lets an attacker's own org's secret authorize writes against any repository named in `full_name`. Proof: minitest POSTing such a crafted, correctly-signed body and asserting whether `PushHandler`/other handlers act on the mismatched `full_name` repository — this should fail today, proving the gap.
