Target: `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` / `pull_request_has_provisioning_label?`. Attacker action: attacker opens a PR and, before the repository owner reviews it, adds a self-chosen label whose name happens to collide with `repository.provisioning_label_name`, or renames their own label to match it exactly (labels on one's own PR in a public repo are attacker-controllable). Preconditions: `provisioning_behavior_allow_with_label?`. Call sequence: `provision?` reads `pull_request_label_names` straight from the unauthenticated payload with no check that the label was applied by a maintainer versus the PR author, then calls `ReviewStackAdapter#find_or_create!`, provisioning a `ReviewStack` that will later execute `shipit.yml` from the attacker's fork. Binding: the actor who applied the provisioning label must hold write access equivalent to `Shipit.github_teams`/maintainer status; today the label name alone gates provisioning with no actor check. Impact: Critical — unauthorized deploy trigger: fork-authored `shipit.yml` gets provisioned/executed without any authenticated maintainer approval. Proof: minitest webhook `opened` event where PR author's own labels include the provisioning label name, asserting `ReviewStack` gets created despite `sender.login` having no `Shipit.github_teams` membership.
