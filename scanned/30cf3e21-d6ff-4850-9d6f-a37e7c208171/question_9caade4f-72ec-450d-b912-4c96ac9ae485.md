Target: `Shipit::User.find_or_create_author_from_github_commit` and `MergeRequest::MERGE_REQUEST_FIELD` regex. Attacker action: attacker pushes a commit (or opens a PR whose head commit) with a commit message body containing a forged `Merge-Requested-By: <victim-login>` line (or whatever `MERGE_REQUEST_FIELD` is), where `<victim-login>` is an existing GitHub/Shipit user. Preconditions: this commit becomes a `github_commit` processed via `Commit` creation path (e.g. sync during `sync_github` or task run). Call sequence: `find_or_create_author_from_github_commit` regex-matches the attacker-authored commit message and calls `find_or_create_by_login!(match_info[1])`, attributing authorship of the commit row to `victim-login` instead of the actual GitHub commit author. Binding: the `author_id` written on the `Commit` row must equal the GitHub identity that authored the commit per GitHub's own commit `author`/`committer` fields, not a self-declared string inside the attacker-controlled commit message. Impact: Critical — cross-identity write: an attacker can attribute their own malicious commit's authorship to any other user, corrupting `Commit#author_id`/audit trail used elsewhere for `deployable?`/approval logic. Proof: minitest calling `User.find_or_create_author_from_github_commit` with a stubbed `github_commit` whose message contains a forged merge-request field for a different existing user, asserting the returned `User` differs from `github_commit.author`.
