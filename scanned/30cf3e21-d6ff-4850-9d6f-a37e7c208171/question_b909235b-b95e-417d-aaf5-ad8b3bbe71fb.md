Target: `Shipit::Api::BaseController#identify_user`. Attacker action: attacker sends any authenticated API request (using their own valid `ApiClient` basic-auth credentials, which they are assumed NOT to have per attacker model — however consider the case where `Shipit.disable_api_authentication` is left true, or where `X-Shipit-User` header is attacker-settable on an otherwise-authenticated request) with header `X-Shipit-User: <victim-login>`. Preconditions: none beyond passing `authenticate_api_client`. Call sequence: `current_user` -> `identify_user` -> `User.where('lower(login) = ?', user_login.downcase).first` — trusts the client-supplied header entirely to set `current_user` for the request, used later for `deployable?`/task-triggering authorization logic. Binding: `current_user` must equal the GitHub identity that authenticated the credentials presented (`current_api_client`), not an arbitrary self-reported header value. Impact: Critical — identity-binding violation: any API caller can impersonate an arbitrary existing user for authorization decisions keyed off `current_user` (e.g. deploy/lock attribution), an authentication-bypass on the identity layer. Proof: minitest ActionDispatch integration test sending a request with `X-Shipit-User` set to a different user's login than the one implied by the `ApiClient`, asserting `current_user.login` equals the header value with no cross-check against the API client's own identity.
