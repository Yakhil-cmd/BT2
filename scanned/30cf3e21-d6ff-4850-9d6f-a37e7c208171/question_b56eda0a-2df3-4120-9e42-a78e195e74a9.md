Target: `Shipit::Hook.emit`/`Hook.deliver` and `Shipit::Hook#deliver!`. Attacker action: attacker triggers any webhook event that legitimately reaches `Hook.emit(event, stack, payload)` for a stack they can influence (e.g. via a `pull_request` event on their own fork), causing `Hook.deliver!` to build a `DeliverySpec` and POST `payload` (which may include `secret:` — the OUTBOUND hook's own `Hook#secret` attribute) to `delivery_url`. Preconditions: a global or stack-scoped `Hook` exists with an operator-configured `delivery_url`. Call sequence: `deliver!` passes `secret:` into `DeliverHookJob.perform_later`, which signs via `DeliverySigner`; if `payload` itself (built from attacker-influenced webhook fields via `coerce_payload`) is ever reflected back to the attacker (e.g. included in a response or a hook target the attacker controls as `delivery_url` if hook `delivery_url` were ever attacker-settable), it could leak internal fields. Preconditions for exploit: none of the fields in `payload` are actually the `secret` itself since it's passed as a keyword separate from serialized payload — Impact assessed as Critical only if `serialize_payload` ever includes `secret`; verify it does not. Binding: `secret` used to sign a delivery must never appear inside `serialize_payload(payload)` sent to `delivery_url`. Impact: Critical if broken — credential exfiltration of the hook signing secret to an external `delivery_url`. Proof: minitest calling `Hook#deliver!`/`serialize_payload` and asserting the JSON/query body sent never contains the `secret` value.
