Target: Shipit::TaskCommands#steps / Shipit::Task#definition. Attacker action: attacker's shipit.yml on their PR branch defines a custom task under 'tasks:' whose name collides with a task name normally provided by a trusted default (e.g. discover_task_definitions), overriding its `steps` array to run attacker-authored shell commands, then relies on an operator triggering that task by its familiar name without inspecting the diff. Preconditions: DeploySpec#task_definitions merges `discover_task_definitions.merge(config('tasks') || {})`, giving explicit config('tasks') entries precedence; the task is triggered from the checked-out attacker branch's shipit.yml (working_directory) rather than a pinned/reviewed spec. Call sequence: TasksController#create -> Stack#trigger_task(definition_id, user, env:) -> find_task_definition -> DeploySpec#find_task_definition merges attacker config over discovered default -> Task#definition.steps returns attacker-authored commands -> TaskCommands#perform -> Command#start. Binding: the `steps` array executed for a named task must equal the steps an authorized reviewer approved for that task name, not whatever is currently checked out on an unreviewed branch at task.working_directory -- no version pinning/approval gate exists between shipit.yml content and execution. Impact: Critical, RCE: an operator's routine trigger of a familiar task name executes attacker-substituted shell steps because task definitions are read live from the deployed/checked-out ref rather than a reviewed baseline. Proof: minitest test defining a 'restart' task override in a fixture shipit.yml with malicious steps, calling Stack#trigger_task('restart', authorized_user), asserting TaskCommands#perform builds Command objects from the attacker's steps rather than any previously approved definition.
