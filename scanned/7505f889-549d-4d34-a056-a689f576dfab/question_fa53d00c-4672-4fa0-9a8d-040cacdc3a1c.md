Given two `Shipit::Commit` rows in two unrelated `Shipit::Stack`s sharing the same `sha` (e.g. both created from the empty git tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which any attacker can produce in a repo they own with `git commit-tree`), does a single 'status' webhook from the attacker's own repository update BOTH commits? Attacker action: push an empty-tree commit to their fork, then have their own CI POST `state: success` for that sha to /webhooks with their own repository info. Preconditions: any other stack in the Shipit instance also contains a commit with that same well-known empty-tree sha (common for initial/orphan commits). Call sequence: `StatusHandler#process` -> `Commit.where(sha: params.sha).each`. Binding: the set of `Commit` rows mutated by one verified payload must equal `{commits belonging to the repository named in that payload}`, not `{all commits in the DB with matching sha}`. Scoped impact: Critical, one webhook mutates N tenants' CI state simultaneously. Proof idea: minitest creating two commits with identical sha across two stack fixtures, posting one status webhook, asserting both `statuses` associations grew.
