Target: Shipit::UndeployedCommit#deploy_disallowed? (app/models/shipit/undeployed_commit.rb, `!deployable? || !stack.deployable?`) as read by the dashboard/API after a forged status. Attacker action: emit a status webhook for a colliding sha with `state: success` from a repo they control. Preconditions: victim commit was previously blocked/pending and appears in `UndeployedCommit` listing for its stack. Call sequence: StatusHandler#process -> create_status_from_github! -> Commit#deployable? flips true -> UndeployedCommit#deploy_disallowed? flips false, exposing a 'ready to deploy' state to any authenticated (even low-privilege) operator viewing the victim's stack UI who then manually deploys. Binding: commit.stack.repository.full_name == the repository named in the payload that produced the Status. Scoped impact: Critical - an attacker manufactures a false-green light that leads an operator of an unrelated repository to trigger an unauthorized deploy. Proof idea: minitest test creating an UndeployedCommit for stack A, posting a status webhook whose repository.full_name is stack B's repo but sha matches stack A's commit, and asserting `deploy_disallowed?` becomes false on stack A.
