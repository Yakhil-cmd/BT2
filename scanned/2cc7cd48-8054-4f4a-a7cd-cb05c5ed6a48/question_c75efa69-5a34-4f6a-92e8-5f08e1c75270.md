Target: `Webhooks::Handlers::StatusHandler#process`. Attacker action: forge/POST a `status` event whose verified `repository_owner` is an org the attacker legitimately controls, but whose body `sha` matches a commit sha belonging to a stack under a completely different, victim repository (sha collision is not required - `StatusHandler` looks up `Commit.where(sha: params.sha)` globally, not scoped to the verified repository). Preconditions: victim repository has a tracked commit with a known sha (e.g. visible via a public GitHub page or task output); attacker controls their own org's webhook secret. Call sequence: `verify_signature` passes for attacker's org; `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository/org filter at all. Binding: organization that authenticated the payload == organization owning the commit whose status is mutated; here the handler never checks it. Impact: Critical, cross-repository write - attacker can set arbitrary CI status (state, description, target_url) on any known commit sha across ANY tenant's stack, potentially flipping `deployable_status` and enabling `schedule_merges` on a victim's commit as shown in `Commit#add_status`. Proof: create commits under two different fixture stacks with same/known sha, POST `status` webhook verified for org A naming that sha, assert the commit under org B's stack received the forged status.
