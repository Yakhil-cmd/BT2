Target: `Shipit::GitHubApp#verify_webhook_signature`. Attacker action: send POST /webhooks with `X-Hub-Signature: sha256=<anything>` (GitHub's newer default header actually uses `X-Hub-Signature-256`, but this code only reads `X-Hub-Signature`); regardless, craft `X-Hub-Signature` value as `sha256=deadbeef` for an org that DOES have a `webhook_secret` configured. Preconditions: target org has webhook_secret configured. Call sequence: `verify_webhook_signature` does `algorithm, signature = signature.split('=', 2)` then `return false unless algorithm == 'sha1'`. Binding: the algorithm/format check itself doesn't grant bypass here (returns false correctly for non-sha1) - this question instead targets whether an attacker who forces `algorithm` to literally be the string 'sha1' but supplies a signature computed over a DIFFERENT byte-exact body than `request.raw_post` (e.g. exploiting any place raw_post might be re-encoded/mutated before comparison) can still pass `secure_compare`. Preconditions/call sequence: confirm `verify_signature` passes `request.raw_post` (not re-serialized JSON) to both the signature function and to `JSON.parse` in `#create` - if these ever diverge (e.g. due to Rack middleware buffering or encoding transforms) the HMAC could verify bytes different from what handlers act on. Binding: bytes verified by HMAC == bytes parsed and dispatched to handlers. Impact: Critical if divergence exists (verification/execution mismatch), otherwise a negative-control test. Proof: integration test asserting `request.raw_post` observed inside `verify_signature` and inside `#create` are the identical string for a given POST body with unicode/whitespace variations.
