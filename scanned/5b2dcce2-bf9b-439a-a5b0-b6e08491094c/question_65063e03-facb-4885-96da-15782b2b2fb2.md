Attacker action: attacker forges any status for a shared sha to flip commit.stack.ignore_ci off/on for the FIRST matching commit found by Commit.where(sha:), even for a stack whose operators deliberately never configured a CI hook (relying on ignore_ci: true by default until first real status arrives). Preconditions: victim stack currently has ignore_ci: true (no CI configured) and a Commit whose sha the attacker reproduces. Binding: the stack whose CI-enforcement mode is switched on == the stack whose real CI system emitted the payload, which fails since the payload's real origin is the attacker's own unrelated repo. Impact: Critical, cross-repository stack configuration mutation - attacker can force a victim stack to start enforcing CI it never configured, potentially blocking (denial-adjacent but here framed as unauthorized state mutation) or, combined with a second forged success status, unlocking deploys that were previously always-allowed under ignore_ci. Proof idea: minitest test asserting stack.ignore_ci flips from true to false on stack B purely from a status webhook verified under stack A's org's secret.
