Target: Shipit::Api::BaseController#authenticate_api_client and Shipit::Api::CCMenuController#authenticate_api_client. Attacker action: an unprivileged internet user first triggers a Shipit operator to visit /ccmenu/*stack_id (Shipit::CCMenuUrlController#fetch) for a stack the operator can see, capturing the returned ccmenu_url whose token param is client.authentication_token for a freshly created ApiClient scoped read:stack to that single stack; the attacker then replays that token as ?token= against GET /api/stacks/*stack_id/ccmenu for a DIFFERENT stack_id than the one it was minted for. Preconditions: Shipit.disable_api_authentication is false; the ApiClient created by CCMenuUrlController#client has stack_id set to the original stack. Call sequence: CCMenuController#authenticate_api_client -> ApiClient.authenticate(params[:token]) sets @current_api_client, then CCMenuController#stack overrides BaseController#stack to call Stack.from_param!(params[:stack_id]) directly, bypassing BaseController#stacks' current_api_client.stack_id scoping. Binding that breaks: stack accessed via CCMenuController#stack ∈ Stack.where(id: current_api_client.stack_id) is never enforced because #stack is overridden to skip #stacks entirely. Scoped impact: Critical, unauthorized read of another stack's deploy/task state (last_deployed commit, activity) using a token scoped to a different stack. Proof idea: minitest controller test authenticating CCMenuController with a stack-scoped ApiClient token for stack A, requesting show with stack_id of stack B, and asserting the response leaks stack B data instead of 403/404.
