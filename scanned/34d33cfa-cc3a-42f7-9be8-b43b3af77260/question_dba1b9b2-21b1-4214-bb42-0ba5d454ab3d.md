Target: Shipit::WebhooksController#create and Shipit::Webhooks::Handlers::Handler#repository_name across ALL handlers (push, status, check_suite, membership, pull_request/*). Attacker action: send a single POST /webhooks whose event maps to multiple registered handlers or whose repository_owner (used for verification) differs from repository.full_name's owner segment for every handler type in one batch, e.g. owner login='org-a' but full_name='org-b/repo'. Preconditions: both org-a and org-b are configured GitHub Apps in Shipit's secrets.github, org-a's webhook_secret is known/controlled by attacker (their own org), org-b hosts the real target stack/repository. Call sequence: verify_signature only ever inspects repository_owner (org-a) for HMAC verification; #create hands the SAME raw JSON to Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }, and every handler independently re-derives its target from payload.dig('repository','full_name') = org-b/repo, never re-checking that org-b's webhook_secret was involved. Binding broken: for every handler, org verifying (org-a) != org owning the target (org-b), demonstrating the vulnerability is systemic to Handler#repository_name, not particular to one handler. Impact: Critical - generalized cross-tenant forgery: a single crafted payload signed by one tenant's secret can write to any other tenant's stacks, commits, or teams depending on event type. Proof idea: minitest test parametrized over event types (push, status, check_suite), each signed with org-a's stubbed secret but naming org-b's repository, asserting the corresponding side effect (job enqueue, status write, check-run schedule) occurs against org-b's records.
