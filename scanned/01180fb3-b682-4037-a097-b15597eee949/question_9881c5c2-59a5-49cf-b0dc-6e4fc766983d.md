In `Shipit::Stack#trigger_task` (app/models/shipit/stack.rb:139-151), `user.id` (the acting `current_user`) is stored on the `Task`, but the `env` hash merged in comes from `TaskDefinition#variables_with_defaults`, whose `default` values are sourced from the same fork-controlled `shipit.yml` used to define the task in the first place (via `discover_task_definitions`/`config('tasks')` in DeploySpec). Attacker action: PR author defines a custom task in their branch's `shipit.yml` with a variable default that is a crafted git-ref-like or flag-like string later used verbatim in a `steps` command. Precondition: a maintainer, believing they are running a benign custom task listed in the Tasks UI, triggers it against the review branch. Call sequence: TasksController#create -> Stack#trigger_task -> TaskDefinition#variables_with_defaults -> Task#env -> Command#start via task execution -> PTY.spawn. Binding that breaks: EXECUTION TRUST -- every default env VALUE reaching `Command#start` must originate from a spec an authorized user approved, but the spec (`shipit.yml`) itself is fork-authored and never reviewed/approved before its `tasks` defaults are trusted and executed. Impact: Critical, remote code execution on the deploy host driven entirely by a fork-authored `shipit.yml` default value, with the only 'authorized' actor being a maintainer who approved running *a* task, not the specific fork-controlled default value inside it. Proof idea: minitest test loading a `DeploySpec` from a fixture `shipit.yml` with an attacker-chosen task variable default containing a git flag-injection string, calling `Stack#trigger_task`, and asserting the resulting `Task#env`/command args carry that value unsanitized into `Command#start`'s argv.
