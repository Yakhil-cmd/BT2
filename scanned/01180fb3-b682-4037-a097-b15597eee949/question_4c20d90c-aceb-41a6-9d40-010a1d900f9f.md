In `Shipit::WebhooksController#repository_owner` (app/controllers/shipit/webhooks_controller.rb:59-62), the organization used to select the `webhook_secret` for HMAC verification is `params.dig('repository','owner','login') || params.dig('organization','login')`, read directly from the unverified JSON body before `verify_signature` runs. Attacker action: a GitHub-originated `membership` event for organization `victim-org` is delivered, but the attacker cannot control GitHub's payload structure for a real event -- however, a maintainer-triggered custom webhook proxy or replay tool re-posting a modified body could set `repository.owner.login` to an org with a different (attacker-known) secret while `organization.login` still names `victim-org`. Precondition: at least two GitHub orgs configured in Shipit, one of which the attacker administers and thus knows its `webhook_secret`. Call sequence: WebhooksController#verify_signature picks org via `repository_owner` (repository.owner.login) -> `MembershipHandler#find_or_create_team!` uses `params.organization.login` (a different field) at app/models/shipit/webhooks/handlers/membership_handler.rb:38-42. Binding that breaks: the org whose secret authenticated the HMAC must equal the org named in `params.organization.login` that the handler writes into `Team#organization`, but the controller and handler read two different JSON fields. Impact: Critical, a payload authenticated with one organization's webhook_secret can write/mutate a Team record scoped to a different organization. Proof idea: minitest controller test posting a membership payload where `repository.owner.login` (attacker's own org, secret known) diverges from `organization.login` (victim org), asserting the request passes signature verification yet the created/updated `Team#organization` equals the victim org.
