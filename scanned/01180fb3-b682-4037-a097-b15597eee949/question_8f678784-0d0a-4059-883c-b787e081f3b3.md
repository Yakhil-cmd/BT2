In `Shipit::Command#unbundled_env` (lib/shipit/command.rb:103-105), the environment hash spawned via `PTY.spawn` is `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` with `@env` sourced from `StackCommands#env`/`Commands#base_env` (lib/shipit/commands.rb:37-50), which includes `GITHUB_TOKEN` and, for tasks, from `Task#env`/`TaskDefinition#filter_envs` derived from `shipit.yml` variables. Attacker action: a fork-authored `shipit.yml` on a PR branch declares a task `variables` entry named `GITHUB_TOKEN` or `GIT_ASKPASS` (allowed since `EnvironmentVariables#permit` (lib/shipit/environment_variables.rb:13-18) only checks that submitted keys are a subset of `variable_definitions`, itself sourced from the same untrusted `shipit.yml`). Precondition: the task/definition is executed against the PR's branch with review-stack execution of that branch's `shipit.yml`. Call sequence: TaskDefinition#filter_envs -> EnvironmentVariables#permit -> Commands#git -> Command#unbundled_env -> PTY.spawn. Binding that breaks: the set of KEYS ending up in `unbundled_env` must be restricted to an engine-defined allowlist excluding `GITHUB_TOKEN`/`GIT_ASKPASS`, but `variable_definitions` (the allowlist) is itself read from the same untrusted `shipit.yml` the attacker authored, so the allowlist can name any key including the secret-carrying ones. Impact: Critical, exfiltration of `GITHUB_TOKEN` by having the spawned git process print or leak the overridden/observed environment value into task output. Proof idea: minitest test defining a `DeploySpec`/`TaskDefinition` whose `variables` includes `GITHUB_TOKEN`, submitting `env: {'GITHUB_TOKEN' => 'attacker-marker'}` through `EnvironmentVariables#permit`, and asserting the value flows unmodified into `Command#unbundled_env` and would overwrite/expose the real token key.
