In `Shipit::User.find_or_create_committer_from_github_commit` (app/models/shipit/user.rb:30-32), the committer identity is taken from `github_commit.committer` or `github_commit.commit.committer`, both of which for push-event webhook payloads are populated from the raw, client-supplied git commit trailer object (name/email), not from a GitHub-authenticated identity, unless GitHub has matched the email to a verified account. Attacker action: push a commit to a fork/PR branch with `git commit --committer-email` set to an email string that is not a verified GitHub account, so `id` is absent. Precondition: repository tracked by a Stack with `sync_github` enabled. Call sequence: PushHandler -> GithubSyncJob -> Commit.from_github -> find_or_create_committer_from_github_commit -> find_or_create_from_github -> create_from_github. Binding that breaks: `User#github_id` should equal a GitHub-verified account id before a `User` row is created, but `create_from_github` is reached whenever `find_from_github` returns nil, writing a new row keyed on attacker-supplied name/email with no github_id verification gate. Impact: Critical, an authorization-adjacent row (`Shipit::User`) is created from unauthenticated free-text git metadata with no authenticated actor confirming it. Proof idea: minitest test with a stubbed github_commit whose committer has `id: nil`, asserting `User.create_from_github` persists a row and that no downstream code ever revokes or reconciles it against a real GitHub account.
