Target: `EnvironmentVariables#interpolate` double-substitution risk when `@env` values themselves contain `$WORD` tokens. Attacker action: PR's `shipit.yml` sets a `deploy.variables` default or supplies deploy-time `env` value like `FOO=$GITHUB_TOKEN` (a literal dollar-word as the *value*, not command), then a later step references `$FOO`. Preconditions: `FOO` is in `deploy_variables` so `EnvironmentVariables#permit` allows it; the step text is `echo $FOO`. Call sequence: `Command#interpolated_arguments` -> `EnvironmentVariables#interpolate('echo $FOO')` matches `$FOO`, replaces with `Shellwords.escape(@env.fetch('FOO'))` == `Shellwords.escape('$GITHUB_TOKEN')`, which escapes the literal string `$GITHUB_TOKEN` as one token (it does NOT re-expand it, since `interpolate` runs once via a single `gsub` pass over the original argument, not recursively over the substituted value). Binding: every interpolated value is escaped exactly once and never re-scanned for `$WORD`, so the substituted `$GITHUB_TOKEN` text remains an inert escaped string in the shell rather than expanding to Shipit's real token. Confirm this holds so that FOO=$GITHUB_TOKEN is NOT a path to leak the real secret. Scoped impact: none if the binding holds (negative test) — but if `gsub`'s block return value were ever re-scanned, it would leak `ENV['GITHUB_TOKEN']`. Proof idea: minitest asserting `Command.new('echo $FOO', env: {'FOO' => '$GITHUB_TOKEN'}).interpolated_arguments == ["echo $GITHUB_TOKEN"]` verbatim (single escape, no second-pass expansion) even when `ENV['GITHUB_TOKEN']` is stubbed to a real-looking secret.
