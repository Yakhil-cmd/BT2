Target: Shipit::Webhooks::Handlers::Handler#stacks and #repository_name used implicitly by handlers extending Handler (e.g., CheckSuiteHandler, MembershipHandler) — cross-check whether any subclass resolves stacks via payload.dig('repository','full_name') without verifying that name against the app/org whose webhook_secret verified the request. Preconditions: a Shipit deployment configured with multiple GitHub Apps/orgs sharing one Shipit host per README's multi-tenant mounting. Call sequence: WebhooksController resolves the App by trying each configured webhook_secret against the raw body signature (app identification is by secret match, not by repository field) -> Handler#stacks -> Repository.from_github_repo_name(repository_name) where repository_name is read straight from the unsigned-content-but-signature-covered body's 'repository.full_name' -- if two configured Apps' secrets could both validly sign a body naming a repository belonging to the other App's org (e.g., an app installed on repos across both orgs, or a shared secret misconfiguration), stacks would resolve to the wrong org's data. Binding: the organization whose webhook_secret verified the body == the organization owning the repository named in that same body -- Handler itself performs no such cross-check; it trusts repository.full_name unconditionally once ANY configured secret verifies the signature. Impact: Critical, cross-org data mutation if a single Shipit instance has multiple GitHub Apps and any app's secret can verify a payload naming a repository under a different app/org. Proof idea: minitest configuring two apps with distinct webhook_secrets in test secrets, signing a payload naming org B's repository with org A's secret in a test double-app setup, and asserting the request is rejected rather than resolving Repository.from_github_repo_name for org B.
