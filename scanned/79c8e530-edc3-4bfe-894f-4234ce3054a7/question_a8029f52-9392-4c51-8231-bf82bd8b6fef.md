Target: Shipit::Webhooks::Handlers::StatusHandler#process. Attacker action: attacker who owns a fork repository (any repo they own) configures a GitHub App/webhook on their own repo pointing at the shared Shipit host, and sends a validly-signed 'status' event for their own app installation but with sha equal to a commit sha that happens to exist in a different, victim organization's repository/stack (git commit shas are content-addressed and can coincide only for identical trees, but can also be deliberately copied by forking and cherry-picking a victim's exact commit). Preconditions: the Shipit instance verifies the webhook signature per-app (per README multi-org mounting) but StatusHandler#process does `Commit.where(sha: params.sha).each` with no repository/app scoping at all. Call sequence: WebhooksController resolves app by matching webhook_secret against the signature (identifying only which App's secret verified, not which repo) -> StatusHandler.call(params) -> Commit.where(sha: params.sha) -> iterates ALL commits across ALL stacks/repositories sharing that sha -> commit.create_status_from_github!(params) mutates each. Binding: the organization/repository whose webhook_secret verified this payload == the organization/repository owning every Commit row mutated by this handler -- StatusHandler never checks this equality since it queries Commit by sha alone with no repository scope. Impact: Critical, a payload signed for/about one repository can write CI status onto a Commit row belonging to a different repository/tenant whenever the sha happens to be shared (e.g., a forked/cherry-picked commit, or two repos with a common ancestor commit prior to divergence), corrupting merge/deploy CI-gating decisions (`required_statuses`) for the victim stack. Proof idea: minitest creating two Commit rows with the identical sha in two different Stacks/Repositories, POSTing a valid status payload signed for repo A's app, and asserting only repo A's Commit received create_status_from_github! (the bug: both do).
