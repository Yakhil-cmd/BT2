Target: `Shipit::Webhooks::Handlers::Handler#stacks` used by `PushHandler`, `CheckSuiteHandler`. Attacker action: POST /webhooks `push` event where `repository.full_name` matches a repository that is mirrored/registered under multiple `Repository` rows (e.g., a renamed org still resolvable to an old full_name pointing at a different current owner) — signature valid for the CURRENT owner org, but the `Repository` row's stacks belong to stacks configured against a different actual GitHub org due to a stale `full_name`. Preconditions: a `Repository` row exists with `full_name` no longer matching the org that currently controls that GitHub login (organization rename scenario, but from webhook payload perspective, still just string matching). Call sequence: `stacks` = `Repository.from_github_repo_name(repository_name)&.stacks`. Binding: organization currently authenticated by `webhook_secret` == organization actually controlling the `full_name` string stored in Shipit's `Repository` row. Impact: Critical — since Shipit trusts the body's `full_name` for both verification-adjacent lookups (via `repository_owner`) and the final stack match, an attacker who registers/renames a GitHub org to briefly match a stale `full_name` could push updates to someone else's stack. Proof idea: integration test simulating this by manually setting a `Repository.full_name` and sending a validly-signed payload from a DIFFERENT verified org login but with matching `full_name` string, assert stack mutated despite org mismatch.
