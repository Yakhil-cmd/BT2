Target: `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` combined with `Team#organization=`. Attacker action: POST /webhooks `membership` event validly signed for attacker's own installed org 'attacker-org', body names `team.id` equal to an EXISTING victim `Team.github_id`, and `organization.login`='attacker-org'. Preconditions: existing `Team` row with `github_id=X` and `organization='victim-org'`. Call sequence: `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end` — the block only runs on CREATE, so if team exists it's found as-is; but if the numeric id collided freshly (team not yet existing) the newly created team's `organization` field gets set from attacker-controlled `params.organization.login`. Binding: `Team#organization` recorded == organization actually verified by the webhook_secret that produced this payload — for the create-path this holds, but the question probes whether member additions to a FOUND existing team (`team.add_member(member)`) re-validate that the verifying org matches the found team's stored `organization`. It does not: `process` never compares `team.organization` to `repository_owner`/verifying org. Impact: Critical escalation into `Shipit.github_teams` — attacker guesses/observes a victim team's numeric `github_id` (e.g., from public GitHub team API or org page) and, from their own validly-signed webhook, adds an arbitrary `User` (created via `User.find_or_create_by_login!(params.member.login)`, itself attacker-controlled string) as a member of that team regardless of which org it belongs to. Proof idea: minitest with a `Team` fixture (`github_id: 555, organization: 'victim-org'`), POST membership webhook signed for 'attacker-org' with `team.id: 555`, `action:'added'`, assert `team.members` gains the attacker-specified login.
