Target: `Shipit::User.find_or_create_by_login!` block `user.github_user = Shipit.github.api.user(login)` executed with the default/first configured GitHub client rather than an org-scoped one. Attacker action: in a multi-org Shipit deployment (`config/secrets.yml` with per-org `github:` blocks), attacker sends a `membership` webhook for org A naming a `member.login` that only exists on GitHub Enterprise org B's instance, or exploits `Shipit.github.api` defaulting to a single global client that cannot distinguish tenants. Preconditions: multiple `github_teams`/orgs configured per README's multi-org example. Call sequence: `find_or_create_by_login!` calls `Shipit.github.api.user(login)` without passing `organization:`, so the login is resolved against whichever org happens to be `Shipit.github`'s default, potentially fetching/associating the wrong tenant's account data into the `User` row later linked via `Membership` to org A's team. Binding broken: the organization whose webhook triggered user creation == the organization whose GitHub API client resolved that user's identity data. Scoped impact: Critical, cross-tenant identity data written into a `User` row and linked via `Membership` to the wrong organization's team. Proof idea: minitest with two configured orgs, stubbing `Shipit.github.api.user` vs `Shipit.github(organization: 'org-b').api.user` to return different profiles, and asserting `find_or_create_by_login!` invoked from org A's webhook never fetches org B's profile data.
