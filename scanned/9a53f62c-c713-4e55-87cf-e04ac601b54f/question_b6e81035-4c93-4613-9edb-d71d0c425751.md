[register-for-bond roll-sbtc net transfer] Can an unprivileged attacker roll over from an existing sBTC bond (`old-sbtc = get-staker-custodied-sbtc(tx-sender)`) into a new bond with a smaller `new-sbtc` via `register-for-bond`'s `roll-sbtc(tx-sender, old-sbtc, new-sbtc)`, such that the net refund transferred out exceeds `old-sbtc - new-sbtc` because `roll-sbtc`'s internal transfer direction/amount doesn't match the `protocol-bond-memberships.amount-sats` actually recorded for the old bond (e.g., stale `old-sbtc` read before a concurrent `unstake-sbtc` in the same block already reduced custody)? Preconditions: attacker has an active sBTC bond membership and issues `unstake-sbtc` and `register-for-bond` in the same block/transaction sequence they control the ordering of. Call sequence: `unstake-sbtc` reduces `amount-sats` and `total-sbtc-staked` and pays out sats -> same-block `register-for-bond` reads `get-staker-custodied-sbtc` (post-unstake) as `old-sbtc` -> `roll-sbtc` -> refund. Equality (LOCK CONSERVATION): sBTC refunded via `roll-sbtc` == `old-sbtc` (the staker's actual custodied balance at call time) minus `new-sbtc`, with no double refund of sats already paid out by `unstake-sbtc`. Impact: Critical, if `old-sbtc` is stale/higher than actual custody, the refund pays sBTC not actually held by the contract for this staker (unbacked payout / theft from the reserve). Proof idea: Rust/Clarity integration test ordering `unstake-sbtc` then `register-for-bond` in the same block and asserting the sbtc-token balance delta equals exactly the remaining custodied sats, not the pre-unstake amount.
