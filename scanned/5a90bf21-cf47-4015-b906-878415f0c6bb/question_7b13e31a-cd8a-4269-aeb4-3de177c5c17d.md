[Function: deposit / vault.deposit] Attacker A calls deposit(amount=CAP-SUPPLY - current-assets, min-out, recipient=A) on a vault (e.g. v0-vault-stx.clar / v0-4-market.clar-linked vault) as soon as headroom to CAP-SUPPLY opens, filling `(var-get assets)` up to `(var-get cap-supply)`. Victim B is an ordinary supplier who submits deposit(amount=X, min-out, recipient=B) in the same block, after A's tx. B holds no prior position; B's tx aborts on `(asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)`. Sequence: Block N: A's deposit lands first, sets assets = CAP-SUPPLY; Block N: B's deposit reverts. Invariant broken: ORDERING NEUTRALITY - the outcome of B's deposit depends on whether A transacted first in the same block. B loses: the ability to deposit and earn yield for as long as A (or any repeat of this pattern) keeps assets pinned at CAP-SUPPLY. Impact: temporary freezing of funds (High). Proof idea: two-account Clarinet test - run B's deposit alone in a fresh block and assert success; then in a new block have A deposit to the cap first, then B deposit the same amount, and assert B's call now returns err ERR-SUPPLY-CAP-EXCEEDED.
