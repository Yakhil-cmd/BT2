Target: `Shipit::Repository.stacks` combined with `Shipit::Commit.where(sha:)`. Attacker action: attacker targets a single GitHub repository that Shipit tracks with *multiple* Shipit stacks (e.g., one per deploy branch/environment: `staging`, `production`), pushes a commit to a throwaway branch producing a sha that also exists (via cherry-pick/rebase) on the `production` branch's stack, and fires the `status` webhook from the throwaway branch's context. Preconditions: `Repository has_many :stacks`; both stacks' `Commit` rows share the sha. Call sequence: `StatusHandler#process`'s unscoped `Commit.where(sha:)` updates the `production` stack's commit even though the webhook's authenticating context is the throwaway branch. Binding: the stack targeted by a status write == the stack whose branch the webhook event actually concerns; broken even *within a single repository* since `StatusHandler` has no per-stack/per-branch filter. Impact: Critical, unauthorized deploy trigger on the `production` stack from a status event that only concerns a non-production branch. Proof idea: two stacks under one `Repository`, shared-sha commits, POST one status webhook, assert both stacks' commits/`deployable?` change.
