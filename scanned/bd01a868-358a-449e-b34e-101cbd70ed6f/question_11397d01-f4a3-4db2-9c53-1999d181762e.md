Target: `Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!`. Attacker action: POST /webhooks membership event with `team: {id: <known github_id>, name: 'x', slug: 'x', url: 'x'}` where that `github_id` already backs a `Shipit::Team` row referenced by `Shipit.github_teams`. Preconditions: attacker knows or guesses the numeric GitHub team id (team ids are visible via public GitHub UI/API for many orgs). Call sequence: `Team.find_or_create_by!(github_id: params.team.id)` finds the existing row (the block only runs on creation, so `organization` is not overwritten), then `process` calls `team.add_member(User.find_or_create_by_login!(params.member.login))`. Binding: a `Membership` row for a team in `Shipit.github_teams` == a membership GitHub actually reports for that team - broken since `find_or_create_by!` keys only on `github_id`, never re-validating `params.organization.login` against the stored `team.organization`. Impact: Critical, escalation into `Shipit.github_teams` authorization for any attacker who can produce a verified-looking membership event (see verification gap questions) naming a pre-existing team id. Proof idea: minitest asserting `Team.find_or_create_by!` does not compare `params.organization.login` to the existing `team.organization` before allowing `add_member`.
