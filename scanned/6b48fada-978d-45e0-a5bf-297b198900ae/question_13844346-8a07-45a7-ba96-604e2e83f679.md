[Function: deposit] Attacker A calls (deposit u9999999999999 u0 A) on v0-vault-stx.clar in block N, filling the `assets` data-var to within 1 unit of `cap-supply` (CAP-STX-SUPPLY = u10000000000000, set via set-cap-supply). Victim B, an ordinary supplier who prepared a same-block (deposit u5000000000000 u0 B) to earn yield before an anticipated rate change, has their call fail with ERR-SUPPLY-CAP-EXCEEDED because `(<= (+ current-assets amount) CAP-SUPPLY)` fails against the now-saturated `assets` var. B cannot deposit at all in this block and must wait for A to `redeem` or for accrual to somehow free room, which A controls. This violates ORDERING NEUTRALITY: B's transaction outcome depends on whether A transacted first in the same block. Impact: temporary freezing of funds (B's capital sits idle earning nothing while intended). Proof: two-account Clarinet simnet test, deploy vault-stx, mint wstx to A and B, submit A's deposit then B's deposit in same block via mineBlock, assert B's tx returns ERR-SUPPLY-CAP-EXCEEDED while an isolated run of B's deposit alone succeeds.
