`WebhooksController#repository_owner` falls back to `params.dig('organization', 'login')` when `repository.owner.login` is absent, meaning the value used to pick which org's `webhook_secret` verifies the HMAC is attacker-suppliable independent of which repository the `pull_request` handler eventually resolves via `params.repository.full_name`. Can an attacker send a 'reopened' pull_request payload that OMITS `repository.owner.login` but includes a top-level `organization.login` pointing at an org they control (with its own valid `webhook_secret`), while `repository.full_name` still names a victim org's tracked repository, thereby making `verify_signature` validate against the attacker's own secret while `ReopenedHandler#repository` resolves the victim repo? Binding: organization whose webhook_secret authenticated the payload == organization named in `params.repository.full_name` that the handler mutates. Impact: Critical, cross-tenant repository/stack mutation via HMAC-org/payload-org mismatch. Proof: controller test posting a payload with `organization.login` = attacker org (valid signature) and `repository.full_name` = 'victim-org/repo', asserting the victim's `Shipit::Repository`'s stacks are unarchived.
