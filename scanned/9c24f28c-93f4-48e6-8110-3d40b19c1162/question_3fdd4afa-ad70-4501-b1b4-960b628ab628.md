`Shipit::Api::BaseController#identify_user` sets `current_user` from `request.headers['X-Shipit-User']` looked up by `User.where('lower(login) = ?', user_login.downcase).first`, entirely independent of `authenticate_api_client`/the actual `ApiClient` that authenticated the request. Can an attacker holding no session but able to reach any endpoint where `Shipit.disable_api_authentication` is enabled (a documented configuration path) or otherwise satisfying `authenticate_api_client`, set an arbitrary `X-Shipit-User` header naming a privileged login to make `current_user` resolve to that user, and have actions (e.g. `LocksController#create` calling `stack.lock(params.reason, current_user)`) recorded as performed by that victim login? Binding: the identity that authenticated this HTTP request (`current_api_client`) == the identity recorded via `current_user` for the mutation performed. Impact: Critical, an attacker's request being recorded/attributed as an authorized user's action with no session or OAuth token for that user. Proof: integration test sending a request with `X-Shipit-User: victim` header and asserting the resulting `Task`/`Lock` record's actor is `victim` although no `ApiClient` or session belongs to `victim`.
