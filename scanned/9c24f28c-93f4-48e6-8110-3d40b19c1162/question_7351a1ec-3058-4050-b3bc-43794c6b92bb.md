`Shipit::User.find_or_create_author_from_github_commit` parses `github_commit.commit.message` for `/^Merge-Requested-By: ([\w\-.]+)$/` and, if matched, calls `find_or_create_by_login!(match_info[1])`, attributing authorship of a `Commit` to an arbitrary GitHub login string embedded in a commit message. Can an attacker push a commit (or open/reopen a PR whose head commit) containing a crafted `Merge-Requested-By: <victim-login>` trailer so that `Commit#author` becomes a `Shipit::User` for a login the attacker does not control, and can this misattributed authorship later be relied upon by any authorization-adjacent check that reads `commit.author`? Binding: the GitHub identity that actually authored/pushed the commit == the `User` recorded as `Commit#author`. Impact: Critical, cross-identity attribution allowing an attacker to make deploy history/audit trails (and any code trusting `Commit#author`) point at a victim login with no authentication by that victim. Proof: minitest calling `Commit.from_github` with a stubbed GitHub commit resource whose message contains `Merge-Requested-By: victim-login` and asserting the created `Commit#author.login == 'victim-login'` even though the actual webhook sender was the attacker.
