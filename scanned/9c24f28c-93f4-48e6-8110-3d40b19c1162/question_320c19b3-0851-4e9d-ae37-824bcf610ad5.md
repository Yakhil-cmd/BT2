Since `Handler#repository_name` and `WebhooksController#repository_owner` are computed independently from the same `payload`/`params` hash but via different dig paths (`repository.full_name` vs `repository.owner.login`/`organization.login`), and `check_suite` payloads from GitHub always include a nested `repository` object, verify: does `Repository.from_github_repo_name(repository_name).owner` always equal `repository_owner` for every possible well-formed but attacker-crafted check_suite JSON body accepted by `verify_signature`? Attacker action: construct and POST a check_suite payload where `organization.login` is present (triggering the `repository_owner` fallback branch) but differs from `repository.owner.login`, signed using the secret for whichever org GitHub's real webhook delivery would use -- reachable if Shipit is dual-homed for an org that owns repos transferred from another org, leaving a stale `organization.login` in cached/replayed payloads. Precondition: attacker can replay/craft an X-Hub-Signature valid for the CURRENT owner of a repository that was recently transferred, using an old cached secret is out of scope (dead end), but a live org administering repos in two `organization` contexts is in scope. Binding: `repository_owner` (used for HMAC secret selection, preferring `repository.owner.login` else falling back to `organization.login`) == the owner actually used by `Repository.from_github_repo_name` to scope stacks. Impact: Critical if the two diverge for any org's legitimately signed payload, since it collapses the tenant boundary this handler depends on. Proof: minitest test posting a signed check_suite body where `repository.owner.login` and `organization.login` differ, one matching the signing org and one matching a different Repository row, asserting which repository's stacks get mutated.
