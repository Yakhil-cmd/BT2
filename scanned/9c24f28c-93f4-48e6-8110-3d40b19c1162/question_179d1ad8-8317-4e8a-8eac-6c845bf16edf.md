Commit#schedule_refresh_check_runs! (app/models/shipit/commit.rb) is invoked both from CheckSuiteHandler#process and from Commit's own `after_commit` callback on create -- meaning a check_suite webhook can force re-evaluation of ANY commit's checks whose sha+branch match, independent of whether that commit's Stack currently has `active_task?` (used elsewhere to gate deploys). Attacker action: for a repository they own, open a PR, get a check_suite event queued, then repeatedly POST forged (but validly self-signed) check_suite payloads referencing an OLDER `head_sha` still present in `stack.commits` while a deploy Task is mid-flight for a NEWER commit on the same branch. Precondition: Stack has `continuous_deployment?` enabled and an active_task. Call sequence: CheckSuiteHandler#process -> Commit#schedule_refresh_check_runs! -> RefreshCheckRunsJob -> Commit#refresh_check_runs! -> create_or_update_check_run_from_github! -> Commit#add_status -> `stack.schedule_merges if new_status.pending? || new_status.success?` -> ContinuousDeliveryJob.perform_later(stack). Binding: the commit whose CI state legitimately advanced to success == the commit that `stack.schedule_merges`/ContinuousDeliveryJob treats as the newest deployable commit. Impact: Critical, unauthorized deploy trigger -- an attacker can use a self-owned repository's legitimately-signed but semantically stale check_suite event to force ContinuousDeliveryJob to re-evaluate and potentially ship an older or different commit than CI last approved. Proof: minitest test with two commits on one stack, faking check_runs responses via Mocha stub on stack.github_api, and asserting ContinuousDeliveryJob.perform_later's target commit matches only the commit whose real check_suite the GitHub API would report.
