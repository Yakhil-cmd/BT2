`Shipit::Commands#base_env` and `Shipit::Command#unbundled_env` place `GITHUB_TOKEN` and (if `Shipit.use_git_askpass?`) `GIT_ASKPASS` into the process environment with no key allowlist, while `DeploySpec::FileSystem#machine_env` is deep-merged from the `machine.environment` section of the `shipit.yml` checked out at the untrusted commit that a ReviewStack (created by ReopenedHandler via ReviewStackAdapter) deploys. Can an attacker who opens/reopens a PR from a fork and controls that fork's `shipit.yml` set `machine.environment.GIT_ASKPASS` or `PATH` to an attacker-controlled script path, so that `TaskCommands#env` (`super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)`) overrides those keys before `Command#start` calls `PTY.spawn`? Binding: the set of environment KEYS an authorized reviewer approved for the deploy spec == the set of keys actually present in `Command#unbundled_env`. Impact: Critical, RCE on the deploy host by substituting `GIT_ASKPASS`/`PATH` to run attacker code with the app's `GITHUB_TOKEN` available. Proof: unit test building `TaskCommands#env` with a stubbed `DeploySpec::FileSystem#machine_env` returning `{'GIT_ASKPASS' => '/tmp/evil'}` sourced from an untrusted branch and asserting the value flows unfiltered into `Command#unbundled_env`.
