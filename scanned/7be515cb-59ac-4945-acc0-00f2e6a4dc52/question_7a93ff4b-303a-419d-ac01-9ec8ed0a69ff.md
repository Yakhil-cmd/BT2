[stake-update / locking_error_to_vm_error] Can an unprivileged attacker craft (via a malicious `signer-manager-trait`) a `stake-update` response whose `(ok ...)` tuple omits `amount-ustx`, causing `parse_pox_stake_result` to return `LockingError::PoxMalformedResponse`, which `locking_error_to_vm_error` maps to `VmInternalError::Expect` — does this abort just the transaction (leaving the pre-existing lock's `amount_locked()` unchanged) or can it be triggered post-mutation of `staker-info`/`staker-signer-cycle-memberships` map state such that Clarity state is updated but the Rust lock is not, breaking the identity STX locked == contract-validated amount-ustx? Preconditions: attacker's own `stake-update` call, prior active stake. Call sequence: `stake-update` mutates `staker-info` then returns tuple -> `handle_stake_lockup_update_pox_v5` -> malformed parse -> `locking_error_to_vm_error` -> transaction abort. Equality: `staker-info.amount-ustx` (Clarity map) == `STXBalance.amount_locked()` (Rust) after the transaction concludes, whether committed or reverted. Impact: Critical if the abort does not roll back the Clarity map mutation, permanently desynchronizing committed amount from actual lock (double-counting / unbacked state).
