Target: `PreStxOp::parse_from_tx` output derivation (stack_stx.rs:72-144) used identically as the `sender` for StackStxOp/DelegateStxOp/TransferStxOp/VoteForAggregateKeyOp. Attacker action: construct a PreStxOp whose first Bitcoin output address is NOT a standard hash-mode-coercible address (e.g., a Taproot / non-P2PKH/P2SH output) so that `try_into_stacks_address()` fails during PreStxOp's own construction is impossible (PreStxOp requires success via `.ok_or_else(InvalidInput)`), but craft it to *just barely* pass by using a legacy address type whose `coerce_hash_mode` differs from the actual spending key's natural hash mode, causing the derived `StacksAddress` to correspond to a *different* principal than the one that will ultimately sign the second-output spend authorizing the StackStxOp. Preconditions: attacker fully controls both outputs' scripts of the PreStxOp transaction (self-crafted), so this is really testing whether output[0]'s *address encoding* is required to match output[1]'s *spending key* at all — currently the code never cross-validates them. Call sequence: `PreStxOp::parse_from_tx` sets `output` = StacksAddress from output[0] only, with zero requirement that output[1]'s spender is the same key. `StackStxOp::from_tx` receives this `sender` blindly. Equality that breaks: IDENTITY — the STX locked by the applied StackStxOp must equal STX owned by the address whose Bitcoin *input* (spending key) authorized the chained ops; here the identity is entirely output[0]'s address field, decoupled from any actual signature proving output[0]'s owner authorized the subsequent stack. Impact: Critical — this is the core of the identified target scope: any attacker who can construct a PreStxOp where output[0] names victim V (any public P2PKH/P2SH address, no private key needed to *name* an address as an output) and then spends output[1] with their own key can mint a StackStxOp that locks V's real Stacks STX balance without V's consent. Proof idea: Rust integration test: build a PreStxOp with output[0] = victim's well-known StacksAddress-mapped BTC address, output[1] spendable by attacker's key; submit the PreStx then a StackStxOp spending output[1]; assert the resulting `StackStxOp.sender == victim`, then run it through `process_stacking_ops` and assert the victim's on-chain STX gets locked with zero signature check from the victim, demonstrating `sender` authorization is purely a naming/output-order artifact, not a proof of Bitcoin-key-to-Stacks-key custody.
