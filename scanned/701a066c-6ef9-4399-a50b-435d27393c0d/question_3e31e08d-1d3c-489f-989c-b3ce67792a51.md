`Api::CCMenuController#authenticate_api_client` (lines 33-36) reads the token exclusively from `params[:token]` (the query string) instead of the `Authorization` header used by `Api::BaseController`. Attacker action: capture a CCMenu URL shared in a public build badge or CI dashboard (URLs are commonly embedded in HTML `<img>`/iframe tags or logged by proxies) and replay `params[:token]` against a different `stack_id`. Preconditions: any previously-issued CCMenu token. Call sequence: `authenticate_api_client` calls `ApiClient.authenticate(params[:token])`; on success `@current_api_client` is set, `super` is skipped, and `require_permission :read, :stack` only checks `current_api_client.check_permissions!(:read, :stack)`, never the requested `stack_id`. Binding: the permission checked (`read:stack`, unscoped) == the permission the action needs (`read:stack` on this specific stack). Impact: Critical, unauthorized read of arbitrary stack build status once any single CCMenu token leaks via a URL (query strings are commonly logged/cached, unlike Authorization headers). Proof idea: minitest requesting `/ccmenu.xml?token=<leaked>` for a stack the token was never scoped to and asserting `response.status == 200`.
