In EditedHandler (app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb), pull_request.title/body edits are attacker-fully-controlled text on their own PR, and the handler resolves its target Repository from params.repository.full_name in the same payload. Attacker action: POST /webhooks X-Github-Event=pull_request action=edited with repository.full_name naming a repository OTHER than the one the attacker's real PR belongs to but still owned by the same verifying organization (e.g., attacker's real PR is on OrgA/repo-x but crafts full_name = 'OrgA/repo-y', a sibling repo under the same org whose webhook_secret verified the request). Preconditions: OrgA owns both repo-x and repo-y, only repo-x has an actual PR from the attacker; repo-y has an existing ReviewStack. Call sequence: verify_signature passes for OrgA (correct secret, since both repos share the org's app) -> EditedHandler#process -> repository resolved to repo-y via params.repository.full_name -> any title/body-driven mutation applied to repo-y's stack despite the real GitHub event originating from repo-x. Binding: params.repository.full_name == the repository that actually emitted this GitHub event; WEBHOOK_PROVENANCE only checks the owning organization, never the specific repository, so same-org cross-repository forgery remains possible. Scoped impact: Critical, cross-repository write within the same organization - attacker with write-nothing access to repo-x can forge edits attributed to repo-y solely because both share one webhook_secret. Proof idea: minitest signing a payload with repo-x's real HMAC secret (org-level) but repository.full_name set to repo-y, asserting whether EditedHandler mutates repo-y's records, demonstrating the org-level (not repo-level) trust boundary.
