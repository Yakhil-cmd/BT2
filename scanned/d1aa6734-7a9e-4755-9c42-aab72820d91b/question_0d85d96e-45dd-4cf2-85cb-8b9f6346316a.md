Target: GithubAuthenticationController#callback / User#requires_fresh_login? interaction with force_github_authentication (Authentication concern). Attacker action: attacker forces a victim through a stale/rotated OAuth callback (e.g. by replaying an old omniauth.auth env with a legacy-format token) so session[:user_id] gets set even though requires_fresh_login? would later flag the token; before force_github_authentication's fresh-login reset_session executes on the next request, the attacker races a request using the still-valid old session to perform an action. Preconditions: window between session[:user_id] assignment in callback and the next request's requires_fresh_login? check in force_github_authentication. Call sequence: callback sets session[:user_id]/session[:authenticated] without reset_session -> attacker-supplied concurrent request hits a deploy-triggering action before force_github_authentication's reset_session fires. Binding: the session bound at callback time == the session validated as fresh at the moment of the privileged action; a race breaks this equality. Impact: Critical, unauthorized deploy/rollback triggered using a session that should have been invalidated. Proof idea: test simulating two sequential requests where the second manually invokes the deploy action between callback and force_github_authentication's reset_session, asserting the action still succeeds.
