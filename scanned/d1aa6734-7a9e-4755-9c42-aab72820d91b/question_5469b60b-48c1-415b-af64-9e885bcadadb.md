Target: Shipit::User.find_or_create_from_github vs User.find_or_create_by_login!. Attacker action: attacker who can influence a login string reaching find_or_create_by_login! (e.g. via MergeRequest field parsing in User.find_or_create_author_from_github_commit) supplies a login of an account that later authenticates via OAuth with a different github_id, and session[:user_id] set at callback time (keyed by github_id via find_or_create_from_github) resolves to a User row created/keyed differently by login elsewhere. Preconditions: two distinct User rows can exist for what should be one GitHub identity: one created by github_id lookup, one created by login lookup. Call sequence: commit ingestion path calls find_or_create_by_login!(login) creating/matching a User row by login; OAuth callback later calls find_or_create_from_github(github_user) matching by github_id; if login is reused/changed on GitHub, the two paths can bind session[:user_id] to a User row that is not the same account that completed this OAuth exchange. Binding: the User row session[:user_id] names == the GitHub account (github_id) that completed this OAuth exchange in this session; broken when login-keyed and id-keyed User rows diverge. Impact: Critical, an identity resolves to a User row other than the authenticating GitHub account, enabling actions (deploys) misattributed to the wrong account. Proof idea: unit test creating a User via find_or_create_by_login!('alice') then authenticating via find_or_create_from_github with github_id belonging to a renamed 'alice' and asserting only one canonical row is returned/bound.
