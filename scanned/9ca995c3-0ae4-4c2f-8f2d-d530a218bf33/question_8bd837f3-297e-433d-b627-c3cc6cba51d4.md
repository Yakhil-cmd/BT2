Since `GithubAuthenticationController` is `ActionController::Base` with no `protect_from_forgery` and `callback` is routed for both `post :callback` and `get :callback` (config/routes.rb), can an attacker force a victim's browser to GET `/github/auth/github/callback` cross-site with attacker-controlled `omniauth.auth` unavailable, but instead force completion of an attacker-initiated OAuth flow bound to the victim's browser session (CSRF on the OAuth callback / login CSRF)? Precondition: attacker starts OAuth flow with GitHub as themselves, obtains a valid `code`, embeds the callback URL (with attacker's own auth code) as an `<img>`/redirect in a page the victim visits while having an active but unauthenticated Shipit session. Call sequence: victim's browser executes the forged GET to `/github/auth/github/callback`, `omniauth.auth` resolves to attacker's own GitHub identity (via the strategy processing the injected code), `session[:user_id] = sign_in_github(auth)` binds victim's browser session to the attacker's `User` row. Binding: the GitHub identity that completed the OAuth exchange == the identity intended by the victim's browser owner; here it breaks because the browser is victim's but the identity is attacker's, then the attacker uses the shared client machine/browser to access the now-authenticated victim's session as themselves. Impact: High, forced OAuth completion / login CSRF (session[:user_id] bound without correlation to a nonce). Proof: functional test posting a fabricated `omniauth.auth` to `callback` on a controller with no CSRF token and asserting the session is set without any state/nonce check.
