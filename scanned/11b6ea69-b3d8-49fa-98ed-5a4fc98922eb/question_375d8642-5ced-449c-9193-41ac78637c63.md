[Target: Commands#base_env + Shipit.github] `Commands#base_env` calls `Shipit.github` with no `organization:` kwarg, defaulting to `github_default_organization`, to fetch `github.token` for `GITHUB_TOKEN`. In a multi-org config (per docs/setup.md 'Using Multiple GitHub Applications'), `Shipit.github` (no args) uses `secrets.github.keys.first` unless that key is a `TOP_LEVEL_GH_KEYS` member. Binding: the `GITHUB_TOKEN` injected into a stack's/task's `Command#unbundled_env` == the token belonging to the GitHub App installed for the ORGANIZATION THAT OWNS THAT STACK's repository, not merely the first-configured org. Attacker action: as an unprivileged user, open a PR / trigger a deploy on a stack belonging to Org-B in a multi-org install where Org-A is configured first; if `Commands#github` resolves to Org-A's app for a stack under Org-B, Org-A's `GITHUB_TOKEN` leaks into a git/checkout `Command` operating against Org-B's `git_path`/`repo_name`. Impact: Critical, credential exfiltration/cross-tenant token exposure — Org-A's `GITHUB_TOKEN` embedded in `unbundled_env` passed to `PTY.spawn`, potentially echoed in git error output or usable via `GIT_ASKPASS`. Proof: test with two orgs configured, a stack whose `Repository#owner` is Org-B, asserting `TaskCommands#env['GITHUB_TOKEN']` equals `Shipit.github(organization: 'org-b').token`, not `Shipit.github.token` (default org).]
