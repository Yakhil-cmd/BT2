Target: Shipit::User#authorized? memoization `@authorized ||= ...`. Attacker action: after a forged Membership grants authorized? == true for an already-loaded current_user instance within a single request/session lifetime, attacker sends a follow-up 'removed' membership event that legitimately or illegitimately revokes the Membership mid-session. Preconditions: current_user object is memoized per-request via `@current_user ||= find_current_user`, and `@authorized` is memoized per-instance. Call sequence: within one long-lived request (e.g. streaming task output), authorized? is computed once and cached, so a revocation event during the request does not retroactively deny access for that request. Binding: current_user.authorized? evaluated at request start == the true authorization state for the entire duration of that request; memoization can only ever grant a request that was valid at start, never widen scope beyond what was true then, so this is expected behavior, not a vulnerability, UNLESS @authorized survives across requests via some shared/cached User object (e.g. a class-level cache), which this code does not show. Scoped impact: none confirmed in this file; negative finding retained for completeness. Proof idea: minitest test confirming a new User.find_by(id:) per request always recomputes @authorized fresh, i.e. no cross-request leakage of a stale true value.
