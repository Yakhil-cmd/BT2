Target: Shipit::Team.github_team=(github_team) invoked inside find_or_create_team!'s creation block. Attacker action: since the assignment block only runs on first creation, an attacker who wins the race to be first to deliver a membership webhook for a not-yet-existing github_id can set team.slug, team.name, and team.api_url arbitrarily while binding organization to whatever they supply, then later any legitimate operator's config referencing Shipit.github_teams by handle (organization/slug) may resolve inconsistently. Preconditions: Shipit.github_teams config lists a handle like 'shopify/developers' but the corresponding Team row has not yet been created via find_or_create_by_handle (e.g. fresh install before rake teams:fetch runs). Call sequence: attacker's forged webhook creates the Team row first, seeding organization/slug/github_id from attacker-controlled payload; when the operator's config later resolves 'shopify/developers' via Team.find_or_create_by_handle, it may find_by(organization:, slug:) match the attacker-seeded row if slug/organization strings coincide, adopting the attacker's github_id as canonical. Binding: the Team record backing a Shipit.github_teams handle must be the one whose github_id was fetched from Shipit.github(organization:).api.org_teams, not one seeded by an unauthenticated webhook. Impact: Critical - attacker plants a shadow Team object that later becomes the operator's authorization anchor, letting the attacker retain membership. Proof idea: minitest test creating a Team via a crafted MembershipHandler payload before calling Team.find_or_create_by_handle('shopify/developers'), then asserting find_by returns the attacker-seeded row rather than one whose github_id was fetched from a stubbed org_teams API call.
