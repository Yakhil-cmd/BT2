Target: `Shipit::Commit#create_status_from_github!` called from `Commit#refresh_statuses!` versus from `StatusHandler#process` (comparing trusted vs untrusted call sites). Attacker action: attacker confirms that the *same* method used for the polling job `RefreshStatusesJob` (which is scoped, since `refresh_statuses!` fetches `stack.github_api.statuses(github_repo_name, sha, ...)` using the *stack's own* authenticated API client for the *correct* repo) is reused unscoped by the webhook path, so the vulnerability is specific to the untrusted webhook ingress, not the method itself. Preconditions: none. Call sequence: contrast `refresh_statuses!`'s `github_repo_name`-scoped Octokit call with `StatusHandler#process`'s cross-repo `Commit.where(sha:)`. Binding: `create_status_from_github!` is only ever invoked with data already scoped to `commit.stack`'s repository == true for `refresh_statuses!`, false for `StatusHandler#process`. Impact: Critical, precisely localizes the fix boundary (the webhook ingress, not the persistence method) which is required for correct remediation and regression testing. Proof idea: minitest exercising `refresh_statuses!` with a Faraday/WebMock stub scoped to the correct repo API, contrasted with a `StatusHandler` test showing the unscoped write, both targeting the same `create_status_from_github!` method.
