Target: Shipit::ReviewStack#env and Shipit::Command#interpolate_environment_variables. Attacker action: add a label named 'foo' to a PR while the repository's shipit.yml deploy step contains a token like '$FOO' (a legitimate operator-authored reference to a task variable named FOO). Preconditions: repository.review_stacks_enabled=true; deploy_spec.deploy_steps contains a command referencing $FOO expecting it to come from an operator-approved VariableDefinition. Call sequence: capture_labels persists 'foo' -> ReviewStack#env produces {'FOO'=>'true'} -> TaskCommands#env merges @stack.env before deploy_spec.machine_env/@task.env, so if no VariableDefinition named FOO with a default is set later in the chain, the label's 'true' value survives -> Command#interpolate_environment_variables/EnvironmentVariables#interpolate substitutes '$FOO' in the deploy step's argument with Shellwords.escape(env.fetch('FOO')) = 'true' -> Command#start executes the resulting command line via PTY.spawn. Binding: the value substituted for $FOO in the executed command line == the value an operator declared via VariableDefinition('FOO').default; here it is instead the label-injected 'true' because ReviewStack#env's label hash was never passed through EnvironmentVariables#permit. Scoped impact: Critical - an unprivileged PR label can silently redefine an operator-intended deploy variable referenced by name in the deploy script, altering the exact arguments Command#start passes to PTY.spawn. Proof idea: minitest building a Command with args '$FOO' and env from Shipit::TaskCommands.new(task).env (with stack.pull_request.labels=['foo'] and no VariableDefinition FOO declared), asserting command.interpolated_arguments == ['true'] instead of any operator-controlled default.
