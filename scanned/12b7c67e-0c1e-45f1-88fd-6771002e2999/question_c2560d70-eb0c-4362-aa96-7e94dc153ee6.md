Target: Shipit::Webhooks::Handlers::Handler#stacks / #repository_name versus Shipit::Webhooks::Handlers::StatusHandler#process. Attacker action: POST /webhooks event: status with any well-formed payload. Preconditions: none beyond a matching sha existing somewhere in the commits table. Call sequence: unlike Shipit::Webhooks::Handlers::PullRequest::OpenedHandler, ClosedHandler, LabeledHandler and ReopenedHandler, all of which resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record, StatusHandler#process never calls `stacks` or `repository_name` at all. Binding: every other webhook Handler enforces repository == Repository.from_github_repo_name(payload['repository']['full_name']) before mutating state, but StatusHandler does not, so 'repository scoped' never holds true for this handler. Scoped impact: Critical - StatusHandler is the single handler in the engine that performs a cross-repository write by construction. Proof idea: minitest comparing StatusHandler.new(payload).process's row-level side effects against OpenedHandler.new(payload).process for a payload naming an unrelated/unknown repository, asserting OpenedHandler no-ops (Repository.from_github_repo_name returns nil -> NullRepository) while StatusHandler still writes a Status.
