Target: `StacksChainState::make_reward_set` epoch-dependent sort key (`k.reward_address.bytes()` vs `k.reward_address.to_burnchain_repr()`) in boot/mod.rs. Attacker action: submit two `stake` calls whose `reward-address` tuples serialize identically under `to_burnchain_repr()` but differently under `bytes()` (or vice versa), exploiting an epoch-boundary reward-set computation that could combine entries that should be treated as distinct addresses (or fail to combine ones that should be), so `slots_taken = stacked_amt/threshold` is computed over a different aggregate than intended. Preconditions: reward-set computation straddles the Epoch21 boundary check (`epoch_id < StacksEpochId::Epoch21`) with crafted `PoxAddress` variants. Call sequence: `stake` with address variant A -> `stake` with address variant B (same effective payout target, different serialization) -> `make_reward_set` sorts/aggregates by the epoch-selected key -> combination loop may merge or fail to merge A and B. Equality that breaks: reward slots and signing weight assigned to the merged/unmerged group != the STX any single reward-address owner actually locked. Impact: Critical if merging lets an attacker capture reward slots representing STX they don't own; High if it only causes bookkeeping to double count within eligible aggregate. Proof idea: unit test constructing `RawRewardSetEntry`s with `PoxAddress` values chosen to collide under one serialization but not the other, run through `make_reward_set` at each epoch, and assert combined `stacked_amt` for the merged address equals the sum only when they are genuinely the same on-chain address.
