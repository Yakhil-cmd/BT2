[Target: Shipit::User#authorized? memoization ivar @authorized] Attacker who is added to a team via a forged membership webhook mid-session (while an operator process already memoized `@authorized ||= ...` to false for that same User instance in a long-lived worker/console) checks whether authorized? ever refreshes. Binding: authorized? computed at call time must equal the CURRENT Membership state, not a cached true/false from before the forged webhook landed. Impact: Critical if stale-false blocks detection, but more importantly if a stale-TRUE persists after a legitimate 'removed' webhook is later forged to hide the trail, the attacker keeps access despite a Membership deletion. Proof: test calling user.authorized? (memoizing false), creating a Membership row for a Shipit.github_teams team_id directly, then calling authorized? again on the SAME in-memory instance and asserting it does not re-check (documents the ivar-cache staleness) vs a freshly loaded User instance which does reflect the new row.
