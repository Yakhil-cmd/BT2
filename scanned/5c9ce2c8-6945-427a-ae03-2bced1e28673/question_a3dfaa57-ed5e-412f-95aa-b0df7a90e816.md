If an attacker cannot easily reproduce a full sha collision, can they instead achieve the same cross-repository write by pushing a commit to their own fork whose *first parent* chain happens to include a commit object identical to one used historically by ANY tracked victim stack (e.g., a widely-reused base commit such as an initial license/README commit shared across many bootstrapped repositories with identical timestamps/authors), then letting their CI emit success for that shared ancestor sha, and does that ancestor commit being present in the victim's stack (even if not HEAD) let `stack.schedule_merges`/hooks fire for the victim stack regardless of the ancestor's position in history? Preconditions: shared ancestor commit exists as a `Commit` row in the victim stack (common when repos are forked/templated). Call sequence: `StatusHandler#process` -> matches the shared ancestor `Commit` row in the victim stack -> `add_status` -> hooks/`schedule_merges` fire for that stack. Binding: same repository-equality binding as above, now shown to be exploitable even via non-HEAD, ancestor commits. Scoped impact: Critical, broadens the attack surface to any shared/templated commit history, not just handcrafted collisions. Proof idea: seed two stacks whose commit fixtures share an ancestor sha (as templated repos would), forge a status for that sha from one stack's repo, assert the other stack's `schedule_merges`/hooks fire.
