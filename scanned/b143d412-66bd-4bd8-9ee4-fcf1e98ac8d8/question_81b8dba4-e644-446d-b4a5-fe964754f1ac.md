`force_github_authentication` in `app/controllers/concerns/shipit/authentication.rb` calls `reset_session` only on the `requires_fresh_login?` branch, but the `GithubAuthenticationController#callback` that actually assigns a fresh `session[:user_id]` never calls `reset_session` beforehand. Can an attacker who obtained a Shipit session cookie prior to any login (e.g. by visiting the public `root_path` which sets a session cookie via Rails' session middleware) have a victim complete GitHub OAuth in that same pre-existing session, and then use the *original*, attacker-known session id (unrotated) after the victim's browser is redirected via `return_url`, to access the victim's `current_user` on subsequent requests through the shared cookie? Binding: the session identifier valid before `callback` runs == the session identifier valid after `callback` sets `session[:user_id]` (must be false/rotated for the binding to hold safely). Impact: Critical, session fixation granting the attacker full impersonation of the victim's authenticated `User`, including any stack the victim can deploy or repository they can add. Proof idea: minitest `ActionDispatch::IntegrationTest` capturing the `_session_id` cookie before `get :callback` and asserting it differs after `callback` completes.
