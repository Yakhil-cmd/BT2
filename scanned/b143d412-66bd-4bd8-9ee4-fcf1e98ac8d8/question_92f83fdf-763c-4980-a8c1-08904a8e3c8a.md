`GithubAuthenticationController#logout` calls `reset_session` and redirects to `root_path`, but `callback` on a *re-login* (e.g. a currently `session[:authenticated] = true` browser hitting `/github/auth/github` again for a different GitHub account, such as switching org accounts) never resets the session before overwriting `session[:user_id]`. Can an attacker with local access to a shared/kiosk browser session (already logged in as User A) trigger a fresh OmniAuth callback that leaves stale non-`user_id` session keys (e.g. any per-user cached state some other controller writes into `session`) bleeding from User A into the freshly bound User B session, such that a value keyed to User A persists and is read under `current_user` == User B? Binding: every session key present after `callback` completes for GitHub identity B == a key legitimately set for identity B, none carried over from identity A. Impact: Critical, cross-identity data/authorization leakage inside one browser session. Proof idea: minitest setting an arbitrary extra `session[:some_flag]` under one login, then invoking `callback` with a different `auth.extra.raw_info.id`, asserting stale keys do not survive tied to the new `current_user`.
