`User.find_or_create_by_login!(login)` (used by `PullRequest#github_pull_request=` for `self.user =` and `self.assignees =`, and by `MembershipHandler#process` for team membership) performs `find_or_create_by!(login:) { |user| user.github_user = Shipit.github.api.user(login) }`. Can an attacker open a pull request whose GitHub account's `login` string exactly matches, case-sensitively or via GitHub's case-insensitive login uniqueness quirks, an existing Shipit `User`'s `login` column that belongs to a *different* `github_id` (e.g. a renamed/deleted-then-recreated GitHub account reusing an old login string) such that the attacker's PR is silently attributed via `find_or_create_by!(login:)` to the pre-existing `User` row, letting the attacker's pull request inherit that `User`'s standing (e.g. being counted as `assignees` on a stack they can influence)? Binding: the `User` row returned by `find_or_create_by_login!(login)` for a given PR payload == the `User` row whose `github_id` matches the actual GitHub account that owns that PR right now. Impact: Critical, cross-account attribution allowing an unprivileged PR author to impersonate an existing `User`'s identity within Shipit's data model. Proof idea: minitest creating a `Shipit::User` fixture with `login: 'alice'` and a stale `github_id`, then calling `User.find_or_create_by_login!('alice')` and asserting no `Octokit` re-verification of `github_id` occurs, silently reusing the row.
