Target: Shipit::CCMenuUrlController#fetch, Shipit::CCMenuUrlController#client. Attacker action: an authenticated low-privilege Shipit user (or an attacker who tricks an operator into visiting a crafted link) issues GET /ccmenu/:stack_id for a stack_id they should not have CCMenu access to; the controller unconditionally creates (or reuses) an ApiClient named 'CCMenu Client' scoped with permissions read:stack and hands back a URL embedding client.authentication_token. Preconditions: ShipitController-level authentication only requires a session (no per-stack authorization check exists in this controller besides Stack.from_param!). Call sequence: #fetch -> #client -> ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client') (no stack: attribute set) -> #stack -> Stack.from_param! -> uri built with token=client.authentication_token, which authenticates against Api::CCMenuController for ANY stack because the created ApiClient has stack_id nil (unscoped). Binding: the stack an API request touches ∈ the stacks current_api_client.stack_id authorises — since the minted client's stack_id is nil, `stacks` returns Stack.all, so the binding is vacuously broken for every stack, not just the requested one. Impact: Critical, a single CCMenu URL fetched for one stack grants read access to every stack in the installation via the same unscoped token. Proof idea: minitest test calling CCMenuUrlController#fetch for stack A, extracting the token, then using it against Api::CCMenuController#show for stack B and asserting it should be :forbidden but returns :ok, and asserting ApiClient.last.stack_id.nil?.
