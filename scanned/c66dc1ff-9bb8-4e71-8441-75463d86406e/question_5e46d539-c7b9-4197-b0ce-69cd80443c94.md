Target: Shipit::EnvironmentVariables#permit (lib/shipit/environment_variables.rb) and DeploySpec#deploy_variables. Attacker action: opens a PR that edits `shipit.yml`'s `deploy.variables` to declare a `name` that collides with an internal key later merged by `TaskCommands#env`/`DeployCommands#env` (e.g. `name: GIT_ASKPASS` or `name: TASK_ID`). Preconditions: an operator triggers a deploy through the UI/API supplying `env` for that declared variable. Call sequence: `Stack#build_deploy` -> `filter_deploy_envs(env)` -> `EnvironmentVariables#permit` allows the key solely because `variable_definitions.map(&:name)` contains it, never checking the value -> `Deploy#env` stored -> `DeployCommands#env` does `super.merge(@stack.env).merge(hardcoded keys).merge(deploy_spec.machine_env).merge(@task.env)`, where `@task.env` (attacker-declared name) is merged LAST. Binding: a key permitted by `EnvironmentVariables#permit` because its NAME matches a `VariableDefinition` == a key whose VALUE cannot override `GIT_ASKPASS`/`GITHUB_TOKEN` set earlier in the merge chain. Scoped impact: Critical, RCE/credential substitution on the deploy host if the attacker-declared variable name is merged after and overrides `GIT_ASKPASS` (the git credential helper script path), letting the attacker redirect git's askpass to an arbitrary script. Proof idea: minitest declare `deploy.variables: [{name: 'GIT_ASKPASS'}]`, submit deploy with `env: {'GIT_ASKPASS' => '/tmp/evil'}`, and assert `DeployCommands#env['GIT_ASKPASS']` still equals the Shipit-controlled snippet path, not `/tmp/evil`.
