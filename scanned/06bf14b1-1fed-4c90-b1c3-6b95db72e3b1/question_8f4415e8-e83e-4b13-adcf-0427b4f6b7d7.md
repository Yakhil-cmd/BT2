CheckSuiteHandler#process iterates `stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)` where `head_sha` is an attacker-suppliable 40-hex string from the webhook body. Attacker action: POST a check_suite payload (signed with attacker's own org's webhook_secret for their own repo) where `head_sha` matches, by chance or by intentionally computing a colliding short value, the `sha` of a Commit belonging to a DIFFERENT Stack under the same Repository (e.g., a stack tracking a protected branch) if such a commit's sha happens to be reachable across stacks sharing one repository. Precondition: Repository has multiple Stacks (e.g., staging and production) sharing overlapping commit history. Call sequence: `stacks.where(branch: head_branch)` is not filtered by sha ownership boundary beyond `stack.commits`, so if head_branch collides with a second stack's branch name, the wrong stack's identical-sha commit gets `schedule_refresh_check_runs!`. Binding: the Stack whose branch was verified as the payload's target == the only Stack whose Commit#sha is scheduled for refresh. Impact: Critical -- RefreshCheckRunsJob for a stack not represented by the actual CI check_suite, potentially flipping Commit#status via Commit#add_status and calling `stack.schedule_merges` (ContinuousDeliveryJob), causing an unauthorized deploy of code the attacker did not target. Proof: minitest test seeding two stacks in one repository with a shared branch name and a shared commit sha, asserting RefreshCheckRunsJob.perform_later receives commit_id only for the intended stack.
