Target: Shipit::Commit.from_github and Shipit::User.find_or_create_author_from_github_commit. Attacker action: open a pull request from a fork with a commit whose author email/login is crafted to match an existing privileged Shipit::User record (e.g. a maintainer's public commit email), or a commit.author that is nil/spoofable in the API response consumed by Commit.from_github. Preconditions: push_handler or refresh path calls Commit.from_github(commit) using data ultimately sourced from an authenticated push/status/PR webhook whose payload embeds attacker-controlled commit metadata. Call sequence: Commit.from_github -> User.find_or_create_author_from_github_commit(commit) -> record.author = <matched User> -> Commit#lock/author fields persisted. Binding: IDENTITY BINDING - the User bound as commit.author must equal the GitHub identity that authenticated the request, not an attacker-supplied email/login string in the commit payload. Scoped impact: Critical, an attacker forges attribution of a commit to a privileged Shipit::User, which can affect authorization checks that key off merge_request.merge_requested_by or lock_author. Proof idea: minitest test feeding a fabricated commit object with a maintainer's email as author to Commit.from_github and asserting the resulting Commit#author is not silently bound to that User without the maintainer having authenticated the request.
