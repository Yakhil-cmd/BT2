Shipit::Stack#base_path (used to compute the on-disk deploy directory passed as `chdir:` to every Command in TaskCommands/StackCommands) is derived from repository owner/name and possibly `environment`, all of which for a `push`/`pull_request` webhook-created Stack originate from `repository.full_name`/`repository.owner.login` in the unsigned-until-verified JSON body. Can an attacker who owns a real GitHub org (and thus a real, valid webhook_secret for their own org) send a `repository.name`/`owner.login` value containing path traversal sequences (e.g. `../../etc`) that, once verified for THEIR org, gets persisted as a Stack/Repository record whose `base_path` escapes the intended deploys root directory used for `FileUtils.mkdir_p(@chdir)` in Command#start? Binding: `Stack#base_path`, and thus the `chdir` argument to every subsequent `PTY.spawn`, is confined to Shipit's configured deploys root for every possible repository owner/name string accepted from a webhook body. Scoped impact: Critical, filesystem write/traversal outside the deploys sandbox on the deploy host, potentially enabling code execution via planted files elsewhere on disk. Proof: POST a validly-signed webhook for an attacker-owned org whose repository.name contains '../', assert Repository/Stack creation succeeds, then assert whether Stack#base_path/chdir resolves inside or outside the expected deploys root.
