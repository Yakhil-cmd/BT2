Target: Shipit::Commit#state (delegated to :status, i.e. Status::Group aggregation) after a forged cross-repo Status insertion competes with the victim's genuine statuses for the same commit and context. Attacker action: forge a status with the SAME `context` string the victim's real CI uses (a guessable default like 'continuous-integration/travis-ci' or 'ci/circle') and state: success, racing against a real pending/failure status from the victim's actual CI provider for that context. Preconditions: victim commit already has a real Status row with that context in 'failure' or 'pending' state. Call sequence: StatusHandler#process -> new Status row created with the forged context/state on the victim's commit -> Commit#status (Status::Group) resolves per-context to the latest by created_at; attacker can set `created_at` in the payload to any timestamp, allowing them to appear as the most recent report for that context. Binding: the most-recent Status for a given context on a commit == the most recent report from the CI system the victim actually configured for that context; fails, since `created_at` is attacker-supplied and unauthenticated per repository. Impact (Critical, unauthorized deploy/merge because a forged, attacker-timestamped status displaces a real failing one): shows the exploit works even against actively-monitored commits, not just idle ones. Proof idea: minitest creating a real failing Status with a past created_at, then a forged cross-org Status with the same context, state success, and created_at in the future, asserting commit.reload.state == 'success'.
