Target: `Shipit::ApiClient.authenticate` / `Shipit::ApiClient.message_verifier`. Attacker action: send `token` values that are valid decimal strings (e.g., `'1'`, `'2'`, ...) signed with a verifier over `Shipit.api_clients_secret`, exploiting the fact the payload is simply `id.to_i` with no client-specific nonce or expiry. Preconditions: attacker has captured one valid signed token for their own low-privilege `ApiClient` (e.g. their own CCMenu token). Call sequence: `authenticate` calls `message_verifier.verify(token).to_i` then `find_by(id: ...)`; because there's no scope/expiry/audience binding in the signed payload beyond the raw id, the token is a bare capability for that id forever. Binding: the token issued for `ApiClient#id == N` is valid, and used, only for the `stack_id` associated with `N`'s row at issuance time — this binding breaks if the `ApiClient` row's `stack_id` is later changed by an update endpoint (`Api::StacksController` has no client-scope update, but if any other engine code path re-associates an `ApiClient`, the old token silently gains the new scope). Scoped impact (Critical): a previously-issued token retroactively grants access to whatever stack its underlying `ApiClient#stack_id` gets reassigned to, without re-authentication. Whose stack: the stack that the reassigned `ApiClient` now points at. Proof idea: model test updating an existing `ApiClient`'s `stack_id` and asserting an already-issued `authentication_token` (generated before the change) still verifies and now scopes to the new stack.
