Target: Shipit::Api::BaseController#identify_user and #current_user. Attacker action: sends any authenticated API request (using a legitimately-scoped, low-permission ApiClient token, e.g. one only holding read:stack) with header X-Shipit-User: <victim_login> where victim_login is an existing privileged User's GitHub login. Preconditions: a User row with that login exists; attacker knows or guesses any valid login (e.g. a well-known maintainer). Call sequence: #current_user memoizes identify_user, which does User.where('lower(login) = ?', user_login.downcase).first with no authentication of the header's authenticity, then any controller action that records the actor via current_user (e.g. Api::TasksController, Api::MergeRequestsController) persists that record with the impersonated user as author. Binding: current_user == the GitHub identity that authenticated this request; this breaks because current_user is derived from an unauthenticated request header, not from a verified identity. Impact: Critical — cross-identity attribution/impersonation lets an unprivileged token holder attribute a mutating record (merge request, task, comment) to an arbitrary victim user. Proof idea: integration test with a scoped ApiClient token, POST to an endpoint using current_user with X-Shipit-User set to another fixture user's login, assert the created record's author/user_id equals the victim, not the actual token holder.
