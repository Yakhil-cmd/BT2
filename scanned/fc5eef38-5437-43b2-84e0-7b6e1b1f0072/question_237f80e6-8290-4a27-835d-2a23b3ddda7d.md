`ReopenedHandler`'s `params` DSL (`explicit-parameters`) requires `pull_request.head.sha`/`ref` as `String` but places no constraint preventing `head.sha` from being an arbitrary attacker-chosen 40-hex-like string unrelated to any commit that actually exists in the repository (no format/length validation, no GitHub API round-trip to confirm the SHA is real before being persisted via `stack.build_pull_request.update!(github_pull_request: params.pull_request)` inside `ReviewStackAdapter#create!`). Can an attacker set `pull_request.head.sha` to a SHA that resolves (via later `GithubSyncJob`/`Commit.from_github`) to a DIFFERENT, unrelated commit already present in Shipit's database for another branch/PR, causing `PullRequest#github_pull_request_head_sha` and the eventual deploy commit resolution to diverge from what was actually approved? Binding: the head commit SHA a maintainer reviewed on GitHub == the head SHA `Shipit::PullRequest` stores and later deploys. Impact: Critical, deploy of a commit that was never associated with the reviewed PR head, i.e. unauthorized ship of attacker-controlled code under a benign-looking PR record. Proof: minitest creating a ReviewStack via a reopened payload with a forged head.sha, and asserting the stored `PullRequest` record differs from `params.pull_request.head.sha`'s actual GitHub-side ref with nothing in the engine reconciling the two.
