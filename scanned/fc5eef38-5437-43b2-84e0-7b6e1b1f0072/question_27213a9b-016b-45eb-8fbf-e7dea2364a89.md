`Shipit::Command#start` builds `interpolated_arguments` via `EnvironmentVariables.with(env).interpolate(argument)` for each argument, and `Stack#env` includes `'GITHUB_REPO_OWNER' => repository.owner` / `'GITHUB_REPO_NAME' => repository.name`, both ultimately sourced (at Repository-creation time) from `params.repository.full_name` in the original webhook payload processed by handlers like `ReopenedHandler`. If a deploy script declared in shipit.yml interpolates `$GITHUB_REPO_OWNER`/`$GITHUB_REPO_NAME` into a command argument, and `Repository#owner`/`#name` were ever set from a payload for a differently-cased or Unicode-confusable full_name than the one actually authenticated, can the interpolated argument diverge from the org whose secret authenticated the write, producing a shell/path argument that targets the wrong org's resources? Binding: `repository.owner`/`repository.name` recorded on the `Repository` row == the `repository.full_name` segments present in the specific payload whose HMAC verified against that org's secret. Impact: Critical, environment-variable interpolation of stale/mismatched repository identity into a command argument passed to `PTY.spawn`. Proof: unit test creating a Repository from one payload's full_name, then processing a `ReopenedHandler` payload with a differently-cased full_name for the 'same' `Repository.from_github_repo_name` lookup, asserting `Stack#env['GITHUB_REPO_OWNER']` reflects unreconciled data.
