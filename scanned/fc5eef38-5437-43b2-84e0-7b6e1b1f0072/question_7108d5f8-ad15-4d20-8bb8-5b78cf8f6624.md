`Api::BaseController#stacks` scopes stacks via `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` calls `stacks.from_param!(params[:stack_id])`. Any endpoint under this base (reachable from an attacker holding no `ApiClient` token but where `Shipit.disable_api_authentication` is set, a documented configuration) would fall back to `UnlimitedApiClient.new`. Given `ReopenedHandler`'s webhook path never touches `ApiClient` at all, can an attacker chain the review-stack creation from a forged/misrouted webhook (per the earlier org-confusion findings) with a subsequent `UnlimitedApiClient`-scoped API call to read/mutate the newly created cross-org stack, with no equality check anywhere binding the `ApiClient#stack_id` (if scoped) to the repository whose webhook secret actually authenticated the original write? Binding: the stack an `ApiClient` is authorized for (`stack_id`) == the stack a webhook-created row actually belongs to. Impact: Critical, stack-scope confusion allowing an attacker to read/deploy a stack outside an `ApiClient`'s authorized `stack_id` once cross-org creation has occurred. Proof: integration test creating a cross-org stack via a crafted webhook, then issuing an API request scoped to an unrelated stack_id and asserting the API cannot distinguish stack provenance.
