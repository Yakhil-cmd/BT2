`Command#unbundled_env` computes `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` where `@env` for a deploy `Task` is `TaskCommands#env`, which merges `deploy_spec.machine_env` (from the untrusted checked-out `shipit.yml`) AFTER `Shipit.env`/stack env but BEFORE `@task.env`. Since `machine_env` keys are unrestricted strings from YAML, can an attacker's `shipit.yml` declare a key literally named `GITHUB_TOKEN` or `GIT_ASKPASS` to overwrite the value Shipit itself computed in `StackCommands#env`/`Commands#base_env`, and is there any point in the merge chain that re-asserts those two specific keys came from `Shipit.github(organization:).token` rather than the deploy spec? Binding: the value of `env['GITHUB_TOKEN']` set by `Shipit::Commands#base_env` == the value of `GITHUB_TOKEN` present in the environment reaching `PTY.spawn`. Impact: Critical, an attacker's shipit.yml silently swapping the deploy host's real GitHub App token for an attacker-controlled string used by subsequent git/GITHUB_TOKEN-dependent steps, or vice versa, exfiltrating the real token if it is echoed. Proof: unit test asserting `TaskCommands#env['GITHUB_TOKEN']` after `deploy_spec.machine_env` returns `{'GITHUB_TOKEN' => 'attacker'}`, showing no reconciliation restores the App-issued token.
