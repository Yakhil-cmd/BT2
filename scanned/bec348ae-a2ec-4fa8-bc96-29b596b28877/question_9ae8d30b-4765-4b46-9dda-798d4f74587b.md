Target: Shipit::User.find_or_create_from_github vs Shipit::User.find_or_create_by_login!. Attacker action: attacker who owns a fork opens a PR whose merge-request commit message contains `Merge-Requested-By: <victim-login>` (consumed by `find_or_create_author_from_github_commit`), and separately the same attacker completes a real OAuth login as themselves. Preconditions: a `Shipit::User` row already exists for `<victim-login>` created via `find_or_create_by_login!` (keyed on `login`) distinct from a row later created for the same human via `find_or_create_from_github` (keyed on `github_id`). Call sequence: webhook handler calls `find_or_create_by_login!('victim-login')`, creating/reusing a `User` row keyed purely on the login string; later, OAuth callback's `sign_in_github` calls `find_or_create_from_github(auth.extra.raw_info)` keyed on `github_id`, potentially creating a second, different `User` row for the same GitHub account if `github_id` isn't populated yet on the login-keyed row. Binding: the `User` row `session[:user_id]` names after OAuth == the `User` row identified by `login` from commit-message attribution for the same real GitHub account. Impact: Critical, an authenticated session's `current_user` can resolve to a `User` record that does not correspond 1:1 with attribution records used for authorization/audit (`authorized?`, team membership), letting an attacker's session inherit/collide with team-derived authorization state built for a different row. Proof idea: model test creating a `User` via `find_or_create_by_login!('someone')` then calling `find_or_create_from_github(raw_info_with_github_id_for_someone)` and asserting whether it returns the same `id` or creates a second row.
