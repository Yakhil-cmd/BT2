`Shipit::TaskDefinition#render_title` (app/models/shipit/task_definition.rb) executes `@title % env.symbolize_keys` where `@title` comes verbatim from `config['title']` in the repository's `shipit.yml`. Attacker action: PR contributor sets `tasks.restart.title: "%<SECRET_KEY_BASE>s"` while also declaring (or not) a variable of that name; when the task actually runs, `env` passed to `render_title` is `task.env`, i.e. the already-`filter_envs`-restricted hash, not the raw process ENV, so a title referencing an unpermitted name should raise `KeyError` and fall into the rescue branch. Preconditions: title string contains a `%<NAME>s` placeholder for a key absent from `task.env`. Call sequence: `Task#title` -> `TaskDefinition#render_title(env)` -> `@title % env.symbolize_keys` raises `KeyError` -> rescued and replaced with `"This task (title: #{@title}) cannot be shown..."`, which echoes `@title` itself (the attacker's format string) back into the UI, not a secret value. Binding: `render_title`'s rescue message must only ever echo attacker-controlled template text (`@title`) and never an interpolated value from `env`; verify no path lets `%<NAME>s` be satisfied by a foreign key smuggled from `ENV` rather than `task.env`. Scoped impact: bounded to confirming no leak — use as a negative-control test alongside the interpolate-based leaks. Proof idea: `TaskDefinitionsTest`-style test constructing a title referencing an undeclared variable and asserting the rendered string contains only the literal format text, never a value from `ENV`.
