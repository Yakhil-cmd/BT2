`Shipit::TaskDefinition#filter_envs` (app/models/shipit/task_definition.rb) is `EnvironmentVariables.with(env).permit(variables)` where `variables` is `@variables` built once at `TaskDefinition#initialize` from the `shipit.yml` snapshot cached at `DeploySpec::FileSystem#cacheable_config` time (`app/models/shipit/deploy_spec/file_system.rb`). Attacker action: contributor's PR changes `tasks.restart.variables` to remove a previously-declared name, then before the cache refreshes, an authorized user submits a task-trigger request containing the old variable name with an attacker-supplied value hoping it is still accepted. Preconditions: `Stack#cached_deploy_spec` still reflects the pre-PR definition (stale cache window). Call sequence: `Stack#find_task_definition` reads the *cached* `TaskDefinition`, so `variables` reflects the old whitelist, not the just-merged PR's tighter one — `filter_envs` permits a name the *current* HEAD's `shipit.yml` no longer declares. Binding: the `variable_definitions` used by `EnvironmentVariables#permit` for a triggered task must equal the `deploy.variables`/`tasks.*.variables` from the exact commit currently referenced as the stack's `cached_deploy_spec`, not a name reused across a since-changed config. Scoped impact: High, stale whitelist allows a previously-declared-but-now-removed variable name through, expanding the effective `$WORD` surface described in the other findings. Proof idea: `DeploySpecTest`/`StackTest` caching a spec with variable `FOO`, updating `load_config` to remove `FOO`, asserting `find_task_definition` still returns the cached (stale) variable list rather than the current one, until `Stack#refresh_deployed_revision!`-style recache occurs.
