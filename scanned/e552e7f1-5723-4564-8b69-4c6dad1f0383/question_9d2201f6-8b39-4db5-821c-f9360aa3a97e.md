`Shipit::TaskCommands#env` merge order is `super.merge(@stack.env).merge({trusted keys...}).merge(deploy_spec.machine_env).merge(@task.env)`, placing `@task.env` — a hash filtered only by `TaskDefinition#filter_envs` via `EnvironmentVariables#permit(variables)` — last, after the trusted keys `TASK_ID`, `SHIPIT_USER`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`. Attacker action: contributor's `shipit.yml` declares a task/deploy variable literally named `IGNORED_SAFETIES` or `GIT_COMMITTER_EMAIL` in `variables`/`deploy.variables`. Preconditions: an authorized user triggers the task/deploy supplying (or defaulting) a value for that variable name. Call sequence: `Stack#trigger_task`/`#build_deploy` -> `definition.filter_envs(env)` permits the key because its name matches a declared `VariableDefinition` -> `Task#env`/`Deploy#env` stores it -> `TaskCommands#env` merges `@task.env` last, overriding the trusted `IGNORED_SAFETIES`/`GIT_COMMITTER_EMAIL` value set earlier in the same merge chain. Binding: keys reserved for Shipit-internal bookkeeping (`TASK_ID`, `IGNORED_SAFETIES`, `SHIPIT_USER`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`) must never be overridable by a name declared in the repository's own `deploy.variables`/`variables` list. Scoped impact: Critical, an attacker-declared variable name can flip `IGNORED_SAFETIES` to `'1'` for a deploy that should have required safety confirmation, or forge the git committer identity used for commits made during deploy. Proof idea: a `TaskCommands`/`DeployCommandsTest`-style test declaring a deploy variable named `IGNORED_SAFETIES`, supplying `env: {'IGNORED_SAFETIES' => '1'}` on a deploy whose `ignored_safeties?` should be false, asserting `TaskCommands#env['IGNORED_SAFETIES']` equals the attacker-supplied override rather than the trusted `@task.ignored_safeties?` value.
