In `Shipit::EnvironmentVariables#interpolate` (lib/shipit/environment_variables.rb), the regex `/(\$\w+)/` scans the raw step string for `$WORD` tokens and calls `@env.fetch(variable) { ENV[variable] }` for each match, with no check that `variable` is one of the names accepted by `#permit`. Attacker action: an unprivileged contributor opens a pull request whose `shipit.yml` adds a step such as `deploy.override: ["echo $SECRET_KEY_BASE"]` (or any host env var name not declared in `deploy.variables`). Preconditions: the stack's cached deploy spec is refreshed from that commit (e.g. it is merged to the deployed branch, or evaluated as part of `discover_deploy_steps`/`around_steps('deploy')`). Call sequence: `Stack#build_deploy` -> `TaskCommands#perform` -> `Command.new(command_line, env:, chdir:)` -> `Command#interpolated_arguments` -> `EnvironmentVariables#interpolate`. Binding: the bytes handed to the shell must equal the step string as written in `shipit.yml` with every `$WORD` substituted only from the task/deploy's own filtered `env`, never from the Shipit master process's `ENV`; here `@env.fetch(variable) { ENV[variable] }` breaks this by falling back to `ENV[variable]`. Scoped impact: Critical, exfiltration of a deploy-time host secret (e.g. `SECRET_KEY_BASE`, `RAILS_MASTER_KEY`, or any credential exported into the Shipit server's process environment) into the task's stdout, readable by anyone who can view that task's output. Proof idea: a `CommandTest` that sets `ENV['SHIPIT_TEST_SECRET'] = 'topsecret'`, builds `Command.new('echo $SHIPIT_TEST_SECRET', env: {}, chdir: '.')`, runs it, and asserts the secret string appears in `command.run`, demonstrating `EXECUTION_TRUST` is violated because the value did not originate from the approved `env` hash.
