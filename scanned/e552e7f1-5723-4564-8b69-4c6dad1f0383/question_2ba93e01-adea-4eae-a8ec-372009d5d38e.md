`Shipit::Command#parse_arguments` (lib/shipit/command.rb) keeps each configured step from `shipit.yml` as a single string element in `@args` rather than a pre-split argv array, and `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`. Attacker action: PR contributor writes a `deploy.override` step as one string, e.g. `"./script/deploy $ENVIRONMENT"`. Preconditions: `ENVIRONMENT` is one of the stack's own env values (attacker does not control its value, but controls which literal shell syntax surrounds it in the string). Call sequence: `TaskCommands#perform` -> `Command.new(step_string, env:, chdir:)` -> `PTY.spawn(env, *interpolated_arguments)` where `interpolated_arguments` is a one-element array containing the fully-substituted string, which the OS shell then re-parses for `;`, `&&`, backticks, etc. that exist verbatim in the shipit.yml text (not inside a `$VAR`). Binding: the bytes handed to the shell must equal exactly the step string as approved in `shipit.yml`, with `Shellwords.escape` applied to every interpolated value exactly once; shell metacharacters that are literal in the step text (not part of an interpolated value) are executed as written by design, so this must hold only for the *substituted* portions, not the literal template. Scoped impact: Critical/none — verifies the binding rather than breaking it. Proof idea: `CommandTest` asserting a value containing `$(...)` or `;` passed via `env:` is returned literally (escaped) in `command.run`, i.e. `Shellwords.escape` is applied to the value, while literal template characters in the step string are unescaped and run as shell syntax — establishing where the trust boundary actually sits.
