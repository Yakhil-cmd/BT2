`Shipit::Command::BASE_ENV` (lib/shipit/command.rb) is computed once at class-load time from `Bundler.unbundled_env`/`Bundler.clean_env` merged with nils for keys stripped by Bundler, and `Command#unbundled_env` does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)`. Attacker action: none needed for `BASE_ENV` itself, but confirm whether `@env` (built from `deploy_spec.machine_env` and `@task.env`, both traceable to `shipit.yml`) can supply a key already `nil`-mapped in `BASE_ENV` (e.g. a secret-bearing var Bundler strips) and resurrect it with an attacker string. Preconditions: the key existed in the Shipit master process's `ENV` before Bundler stripped it (common for keys like `RUBYOPT`, `GEM_HOME` used by Bundler's env cleanup). Call sequence: `Command#unbundled_env` -> `@env.stringify_keys` last in the merge -> `PTY.spawn(unbundled_env, ...)`. Binding: a key present in `BASE_ENV` because it was scrubbed by Bundler for safety must not be re-injectable by any key in `@env` sourced from `shipit.yml`/`machine_env`/task env. Scoped impact: Critical, resurrecting a Bundler-scrubbed variable can change the Ruby/gem resolution for every subsequent step, i.e. code execution control. Proof idea: a `CommandTest` asserting `Command.new('true', env: {'RUBYOPT' => '-e$stderr.puts(1)'}, chdir: '.').unbundled_env['RUBYOPT']` equals the attacker value even though `Command::BASE_ENV['RUBYOPT']` is `nil`.
