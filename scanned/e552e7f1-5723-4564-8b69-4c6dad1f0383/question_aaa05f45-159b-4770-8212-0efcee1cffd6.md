`Shipit::DeploySpec::FileSystem#cacheable_config` (app/models/shipit/deploy_spec/file_system.rb) sets `'machine' => { 'environment' => discover_machine_env.merge(machine_env) }` and `DeploySpec#machine_env`/`discover_machine_env` read directly from the repository's `shipit.yml` `machine.environment` section with no pass through `EnvironmentVariables#permit`. `TaskCommands#env` (lib/shipit/task_commands.rb) does `.merge(deploy_spec.machine_env).merge(@task.env)`. Attacker action: contributor's `shipit.yml` declares `machine: { environment: { GIT_ASKPASS: '/tmp/attacker_script' } }` or `machine: { environment: { GITHUB_TOKEN: '' } }`. Preconditions: this shipit.yml is the one cached for the stack (i.e., on the branch actually deployed). Call sequence: `TaskCommands#env` merges `deploy_spec.machine_env` unfiltered into the environment passed to every `Command.new(..., env:, ...)` for that task, which then becomes part of `Command#unbundled_env` merged into `PTY.spawn`. Binding: every key in `Command#unbundled_env` must originate from a ref and spec an authorized user approved AND must not be able to override Shipit-managed keys such as `GIT_ASKPASS`/`GITHUB_TOKEN` that carry deploy credentials. Scoped impact: Critical, RCE/credential-tampering — an env key from `machine_env` can shadow the credential-carrying key used by git operations, redirecting `GIT_ASKPASS` to an attacker-supplied path executed by git during checkout/fetch. Proof idea: a `TaskCommands`/`DeploySpec::FileSystem` test stubbing `load_config` to include `machine.environment.GIT_ASKPASS`, asserting `TaskCommands#env['GIT_ASKPASS']` equals the attacker value and is unconditionally passed to `Command#unbundled_env`.
