`Shipit::VariableDefinition#initialize` (app/models/shipit/variable_definition.rb) takes `name` straight from the repository's `shipit.yml` (`attributes.fetch('name')`) with no restriction on which system variable names can be declared, and `EnvironmentVariables#permit`'s `sanitize_env_vars` only checks `allowed_variables.include?(k)`. Attacker action: contributor declares `deploy.variables: [{name: 'PATH'}]` or `{name: 'BUNDLE_GEMFILE'}` in `shipit.yml`, then an authorized deployer supplies a value for it via the deploy form. Preconditions: no denylist exists in `VariableDefinition`/`EnvironmentVariables` for security-relevant names like `PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, `GIT_ASKPASS`. Call sequence: `DeploySpec#filter_deploy_envs` -> `EnvironmentVariables#permit(deploy_variables)` accepts the key because its name is in `variable_definitions.map(&:name)` -> `Stack#build_deploy` stores it in `Deploy#env` -> `TaskCommands#env` merges it in, ultimately reaching `Command#unbundled_env['PATH']` used by `PTY.spawn`. Binding: an env key permitted by `EnvironmentVariables#permit` must be limited to a namespace disjoint from process-control variables (`PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_ASKPASS`) that alter which binary/interpreter the shell resolves for subsequent steps. Scoped impact: Critical RCE — a deployer-approved but attacker-named variable can redirect `PATH` so that the next step's command resolves to an attacker-planted binary on the deploy host. Proof idea: `EnvironmentVariablesTest` declaring a `VariableDefinition` named `PATH`, asserting `permit` accepts an env hash containing `{'PATH' => '/tmp/evil:...'}`, then a `Command#unbundled_env` test showing that key overrides `BASE_ENV['PATH']`.
