In `Shipit::EnvironmentVariables#permit` (lib/shipit/environment_variables.rb) `sanitize_env_vars` computes `allowed_variables = variable_definitions.map(&:name)` and filters `@env` by key membership only, never touching the step strings executed later. Attacker action: contributor's `shipit.yml` declares `tasks.restart.variables` with a single entry `name: FOO`, but the task's `steps` array references a second, undeclared token like `$DATABASE_PASSWORD`. Preconditions: task is triggered by an authorized user via `Stack#trigger_task`, `env` submitted contains only `FOO`. Call sequence: `TaskDefinition#filter_envs` -> `EnvironmentVariables#permit(variables)` returns `{'FOO' => ...}` -> `Task` persists this filtered env -> `TaskCommands#perform` builds `Command.new(step, env: filtered_env_plus_machine_env, ...)` -> `Command#interpolated_arguments` calls `interpolate` on the raw step text which still contains `$DATABASE_PASSWORD`. Binding: every key referenced inside a step string must be a subset of the keys that passed `EnvironmentVariables#permit`; here the interpolation path is completely independent of the permit whitelist, so an env key can reach the shell without ever being permitted. Scoped impact: Critical, an env key not present in the approved/filtered env set is still substituted (falling to `ENV[variable]`), exfiltrating a Shipit process secret into task output. Proof idea: minitest asserting that `TaskDefinition#filter_envs` returns a hash without `DATABASE_PASSWORD`, yet `Command.new(step_with_that_var, env: filtered_env).interpolated_arguments` still substitutes a value from `ENV['DATABASE_PASSWORD']`.
