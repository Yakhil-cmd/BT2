Target: `Shipit::Api::BaseController#stacks` when `current_api_client.stack_id?` is false (global/unscoped token) versus `Shipit::UnlimitedApiClient#stack_id?` always returning false. Attacker action: if `Shipit.disable_api_authentication` is set (host misconfiguration is out of scope) — instead test the case where an operator issues a legitimate global `ApiClient` (no `stack_id`) intended for one integration, and attacker who has a way to reach that token (e.g. via an operator-facing page cross-linked, not via credential theft) issues `GET /api/stacks/:stack_id` for an unrelated repository's stack. Preconditions: `ApiClient` with `stack_id: nil` and `permissions: %w[read:stack]` exists (a normal, documented configuration, not a leaked secret). Call sequence: `stacks` returns `Stack.all` whenever `stack_id?` is false, then `stack` calls `stacks.from_param!(params[:stack_id])`, resolving to ANY stack. Binding: the stack an API request touches ∈ the stacks `current_api_client.stack_id` authorises — for a client with no `stack_id`, the code treats 'no scope configured' as 'all stacks authorised', which is a permissive default. Scoped impact: Critical, a token intended for one integration/repository can read/act on every tenant's stack once any request reaches it, because absence of `stack_id` is interpreted as global scope rather than denial. Proof idea: minitest creating an `ApiClient` with `stack_id: nil`, asserting `stacks` includes stacks belonging to repositories unrelated to the client's `creator`.
