Target: `Shipit::ApiClient.authenticate` and `Shipit::SimpleMessageVerifier`. Attacker action: attacker who has observed any single valid CCMenu URL (token T for `ApiClient` id N, exposed in a non-secret context such as a build-status widget) submits `GET /api/stacks/:stack_id/ccmenu.xml?token=T` unchanged. Preconditions: token T was legitimately minted for stack A with `permissions: %w[read:stack]` via `CCMenuUrlController#fetch`. Call sequence: `ApiClient.authenticate(token)` calls `message_verifier.verify(token).to_i` and `find_by(id: ...)` — the verified payload is only a decimal id, carrying no stack binding at verification time; the stack binding is enforced only by `#stacks`, which `CCMenuController` does not use. Binding: permission checked (`read:stack` on client N) == permission needed for the specific stack instance addressed by `:stack_id`; since `CCMenuController#stack` never intersects with `current_api_client.stack_id`, the check is vacuous for stack identity. Scoped impact: Critical, cross-repository stack-state read via a token whose only real restriction (its `stack_id`) is silently dropped. Proof idea: minitest asserting `ApiClient#stack_id` differs from the `:stack_id` param in a successful `ccmenu.xml` response.
