Target: Shipit::SameSiteCookieMiddleware#call. Attacker action: any response from the Shipit host that sets Set-Cookie (e.g., session cookie after github_authentication callback) is rewritten to include '; SameSite=None; Secure' unconditionally when Rack::Request.new(env).ssl? is true, regardless of cookie name (session vs CSRF cookie). Preconditions: app deployed with SSL, middleware inserted (lib/shipit/engine.rb). Call sequence: any controller sets a cookie -> SameSiteCookieMiddleware#call appends SameSite=None to every cookie including the Shipit session cookie -> browser will attach that cookie on cross-site requests (top-level navigation, form POST, image GET) to any Shipit endpoint. Binding broken: a cookie that authorizes the caller's identity should only be sent same-site unless the specific flow requires cross-site (e.g., OAuth); rewriting ALL cookies breaks identity_binding by making current_user's session usable in a forged cross-origin request context. Scoped impact: Critical, enables cross-site request forgery vector into state-changing endpoints (e.g., MergeStatusController#enqueue/#dequeue) using the victim's session cookie. Proof idea: unit test on SameSiteCookieMiddleware#call with a fake app returning multiple Set-Cookie headers (session_id and _csrf), asserting each individually gets SameSite=None applied even though only OAuth-flow cookies should.
