Target: Shipit::Commit#refresh_statuses! (app/models/shipit/commit.rb) versus Shipit::Commit#create_status_from_github! being reachable directly from an unscoped webhook rather than only from the authenticated `stack.github_api.statuses` pull path. Attacker action: attacker demonstrates that the *push* path (refresh_statuses!, which correctly scopes via `stack.github_api.statuses(github_repo_name, sha)` bound to the owning stack's own GitHub App credentials) has proper scoping, while the *webhook* path (StatusHandler#process) has none, by causing create_status_from_github! to run on a victim commit purely from an attacker payload with no equivalent github_repo_name check. Preconditions: shared-sha commit in victim stack. Call sequence: contrast refresh_statuses! (always calls stack.github_api scoped to that stack's repo) against StatusHandler#process's direct commit.create_status_from_github!(params) with no such scoping. Binding: the repository context used by the pull-based path (stack.github_repo_name, always correct) == the repository context used by the webhook push-based path (none) -- StatusHandler#process breaks this invariant that every other status-writing code path upholds. Impact: Critical, isolates the exact asymmetry that makes the webhook path the sole cross-tenant vulnerability in this class. Proof idea: unit test comparing Mocha expectations: refresh_statuses! only ever calls github_api scoped to its own stack; create_status_from_github! invoked directly (as StatusHandler#process does) requires no such scoping and mutates any matching commit.
