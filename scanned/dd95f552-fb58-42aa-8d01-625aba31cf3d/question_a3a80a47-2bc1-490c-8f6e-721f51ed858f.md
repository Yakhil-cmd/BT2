Target: `StackStxOp::check`'s `Secp256k1PublicKey::from_slice(signer_key.as_bytes())` validation. Attacker supplies a syntactically valid but attacker-chosen `signer_key` (33-byte compressed pubkey the attacker generated) that does not correspond to any registered signer's key on pox-5, attempting to have the burnchain op alone grant signing weight for a cycle's reward set entry. Preconditions: valid PreStxOp chain, `signer_key` parses as a valid secp256k1 point but is unregistered/unowned by any real signer. Call sequence: `check()` accepts any structurally valid pubkey (no registration check at the Rust layer) -> `collect_pox_4_stacking_args` forwards it as `Some(buff)` -> pox-5 `stack-stx` Clarity call records this key against the staker's reward-set entry. Equality: AUTHORITY — reward-set signing weight granted for a `(cycle, signer_key)` pair must equal weight for a signer_key the staker/signer actually intends to use for signature verification during that cycle; validate this is enforced entirely inside pox-5's Clarity logic, not assumed satisfied by the Rust-level pubkey format check. Scoped impact: High — an attacker cannot forge another party's signature, but could grant themselves signing weight under a throwaway key without ever losing STX if the corresponding lock isn't real; confirm this can't be leveraged to claim reward-set slots exceeding actually locked value (which would be Critical). Proof idea: integration test verifying that reward-set signing weight for a `signer_key` is always tied 1:1 to a `stacked_ustx` amount actually locked in `pox-locking` for that same op, with no way to register a key without a corresponding real lock.
