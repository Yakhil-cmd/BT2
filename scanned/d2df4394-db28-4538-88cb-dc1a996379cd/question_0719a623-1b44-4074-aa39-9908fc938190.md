Target: Shipit::Webhooks::Handlers::StatusHandler#process vs Shipit::Webhooks::Handlers::Handler#stacks. Attacker action: attacker sends a status webhook whose repository.full_name field names their own repo, but whose sha field is copied from a public commit of a victim repository that happens to also exist as a Commit row in some other stack (e.g. a shared vendored submodule commit, or two stacks tracking forks with common history). Preconditions: two distinct Repository records in Shipit both have a Commit row with the same sha (achievable since git SHAs are content-addressed and forks/mirrors commonly share commits). Call sequence: same as StatusHandler#process; note Handler#stacks (used by other handlers such as PushHandler/CheckSuiteHandler) resolves Repository.from_github_repo_name(repository_name)&.stacks, but StatusHandler never calls it. Binding: for every other handler that does call stacks, repository_name in payload == repository owning the stacks touched; for StatusHandler this binding does not hold at all - assert StatusHandler#process touches Commit rows whose stack.repository.full_name != params_repository_full_name is possible. Scoped impact: cross-repository CI-state corruption is systemic, not sha-collision-dependent, for any repo pair sharing a commit sha. Proof idea: minitest test creating two stacks (different repositories) each with a Commit of the identical sha, deliver one status webhook naming only one repository, assert both stacks' commits received the new status.
