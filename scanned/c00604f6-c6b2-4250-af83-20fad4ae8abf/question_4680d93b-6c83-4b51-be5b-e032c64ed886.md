Target: StackStxOp::check (stackslib/src/chainstate/burn/operations/stack_stx.rs). Attacker action: an unprivileged Bitcoin-input holder broadcasts a StackStxOp whose parse_data-derived num_cycles is 0 or > POX_MAX_NUM_CYCLES, e.g. num_cycles=200. Preconditions: a matching PreStxOp already confirmed with output == attacker-controlled Stacks address; op reaches StackStxOp::check after StackStxOp::parse_from_tx. Call sequence: burnchain.rs dispatcher -> StackStxOp::from_tx -> StackStxOp::check -> process_stack_stx_ops -> pox-N contract-call `stack-stx` -> pox-locking lock. Equality that breaks: num_cycles committed by the op (as validated by check()) == num_cycles actually accepted downstream, since check() only warns and returns Ok(()) instead of Err on out-of-range num_cycles. Impact: Critical, STX locked for an invalid/overlong or zero period, freezing the attacker's own or (if reused across ops) another op's STX beyond committed parameters. Proof idea: Rust integration test constructing a StackStxOp with num_cycles=0 and num_cycles=250, asserting check() returns Err and pox-locking never locks STX for an uncommitted duration.
