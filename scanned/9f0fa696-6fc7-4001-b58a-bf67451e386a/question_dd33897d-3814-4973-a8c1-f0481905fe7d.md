[Function: repoSync.sanityCheckWorktree] Can an attacker who controls repo content construct a worktree that passes sanityCheckWorktree's checks (e.g., presence of .git file, no obvious corruption) while containing symlinks pointing outside the worktree, such that after publishSymlink flips --link, the consumer container's readthrough of a symlinked path inside the published tree reads/writes host paths outside --root? Preconditions: none beyond default; symlinks committed into the git repo are checked out verbatim by default. Call sequence: attacker commits a symlink 'evil -> /etc/shadow' or '../../../etc' inside repo -> git checkout preserves it in worktree -> sanityCheckWorktree passes -> publishSymlink exposes worktree containing that symlink to consumer. Invariant: CONTENT_CONTAINMENT. Impact: consumer container, following the published symlink, can read/write host-mounted paths outside --root — this is the core Scope risk. Proof idea: e2e test committing a symlink to an absolute host path in the sample repo, sync it, and assert either git-sync refuses to publish worktrees containing symlinks that escape --root, or document that this is inherent to git checkout (test should reveal actual current behavior).
