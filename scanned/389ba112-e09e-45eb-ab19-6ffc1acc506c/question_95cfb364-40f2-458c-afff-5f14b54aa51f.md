[stack_stx.rs] For `StackStxOp::parse_from_tx`, `reward_addr` is taken from `outputs.get(0)` and coerced via `coerce_hash_mode()` with no check that this address is one the sender's signer actually approved as a payout address. Attacker action: submit a `StackStxOp` whose first Bitcoin output (the PoX reward address) is set to an address the attacker doesn't control, while `sender` still resolves to the attacker via PreStxOp linkage. Precondition: valid PreStxOp/StackStxOp pairing. Call sequence: op locks `stacked_ustx` for `sender`, but reward payouts route to `reward_addr` which nobody authorised as belonging to the staker's chosen signer. Equality broken: sBTC/BTC rewards paid to `reward_addr` == rewards earned by the staker who committed `stacked_ustx`, only if `reward_addr` is the staker's own address; here it can be set to anyone. Impact: Critical if this reward misdirection is irreversible and un-refundable — reward theft is only possible if the attacker sets `reward_addr` to someone else's address, but since the attacker is the one broadcasting the op and would only hurt themselves by misdirecting their own reward, the more interesting case is: does pox-5 or pox-locking ever conflate `reward_addr` with `sender` for later signer-weight bookkeeping given the two need not match? Whose funds: the staker's own reward BTC (self-harm case is out of scope) — however if `reward_addr` collision with another staker's already-registered reward address causes reward *pooling* into a shared payout, that's Critical theft of pooled rewards. Proof idea: integration test where two stackers set identical `reward_addr` and assert reward crediting is proportional to each one's own `stacked_ustx`, not double-paid to the shared address.
