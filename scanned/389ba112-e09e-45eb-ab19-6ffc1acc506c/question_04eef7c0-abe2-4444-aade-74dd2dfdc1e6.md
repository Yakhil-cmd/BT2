[stack_stx.rs] Does `StackStxOp::check` actually reject an out-of-range `num_cycles`? Attacker crafts a burnchain `StackStxOp` transaction whose `parse_data` yields `num_cycles == 0` or `num_cycles > POX_MAX_NUM_CYCLES`. Precondition: attacker controls the Bitcoin input resolved to their own Stacks address via a valid `PreStxOp`. Call sequence: `StackStxOp::parse_from_tx` succeeds, `StackStxOp::check` runs the `if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES { warn!(...) }` branch with no `return Err`, falls through to `Ok(())`, and the op is applied, locking `stacked_ustx` for an invalid cycle count. Equality broken: STX locked by the op == STX committed under a *valid* `num_cycles` parameter set the sender authorised; here it locks under parameters that should have been rejected. Impact: Critical — freezing/mis-scheduled unlock of the sender's own STX under unvalidated cycle count, and possible SINGLE UNLOCK violation if downstream pox-locking code assumes `num_cycles` is in range. Whose funds: the sender's locked STX. Proof idea: Rust unit test constructing a `StackStxOp` with `num_cycles = 0` and asserting `.check()` returns `Ok(())` instead of `Err`, then integration-test applying it and observing the resulting lock/unlock height in pox-locking.
