Target: `Commit#add_status`'s `already_deployed = deployed?` short-circuit (`stack.last_deployed_commit.id >= id`) combined with cross-repo `Commit.where(sha:)`. Attacker action: send a webhook for a sha that, in the victim's stack, corresponds to an *already deployed* commit, expecting the `already_deployed` guard to suppress hooks; then, in a second stack owned by a different, less-advanced victim tenant where the same sha is *not yet deployed*, the identical payload causes `deployable_status` hooks and continuous delivery to fire. Precondition: two distinct stacks (different orgs) contain commits with the same sha at different points in their deploy history. Call sequence: single `StatusHandler#process` invocation's `each` loop applies the same `github_status` to both `Commit` rows with different downstream effects, none of which check the payload's `repository.full_name`. Binding: the repository named in the payload must equal the repository of each `commit.stack` being evaluated for hook emission and continuous delivery; it does not, so a forged status simultaneously and silently succeeds against one tenant while loudly triggering delivery in another. Scoped impact: Critical, non-deterministic but reproducible cross-tenant deploy triggering from one forged event. Proof idea: minitest test with two stacks/commits sharing a sha, one already deployed and one not, asserting only the not-yet-deployed victim's stack gets a `ContinuousDeliveryJob` enqueued.
