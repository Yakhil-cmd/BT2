Target: `Status#enable_ci_on_stack` (`after_create` callback: `commit.stack.enable_ci!`). Attacker action: send a `status` webhook signed for their own repo for a sha matching a victim commit in a stack that currently has CI disabled (`ignore_ci: true` not yet flipped, or CI never enabled), to force-enable CI gating on that victim's stack as a stepping stone to later denial of legitimate deploys or to change `deployable?` semantics. Precondition: victim stack's CI-enablement flag responds to `enable_ci!`. Call sequence: `StatusHandler#process` -> `Commit.where(sha:)` -> `create_status_from_github!` -> `statuses.replicate_from_github!` creates `Status` -> `after_create :enable_ci_on_stack` -> `commit.stack.enable_ci!`. Binding: the repository whose `webhook_secret` verified this request must equal the repository of `commit.stack` before `enable_ci!` is called; it does not. Scoped impact: Critical, a payload for one repository mutates another tenant's `Stack` configuration flag. Proof idea: minitest test asserting `victim_stack.reload.ci_enabled?` (or equivalent flag) changes after posting an attacker-signed status webhook naming only the sha, not the victim's repository.
