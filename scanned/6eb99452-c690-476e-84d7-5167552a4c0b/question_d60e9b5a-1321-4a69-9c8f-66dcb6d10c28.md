Target: `Commit#deployable?` combined with `Stack#ignore_ci?`. Attacker action: identify (or force, via repeated fork/branch creation) a victim stack configured with `ignore_ci: true`; even though `deployable?` for such a stack does not depend on CI state, sending a `success` status for a shared sha still creates a `Status` row and fires `Hook.emit(:commit_status, ...)` and `enable_ci_on_stack`, potentially re-enabling the CI dependency Shipit uses to gate deploys later. Precondition: victim stack has `ignore_ci: true`. Call sequence: `StatusHandler#process` -> `create_status_from_github!` -> `Status#enable_ci_on_stack` -> `stack.enable_ci!` flips `ignore_ci` to false, changing `deployable?`'s branch from `stack.ignore_ci?` (always true) to `(success? && !blocked?)` (attacker-controlled). Binding: the repository whose webhook authorized this state transition must equal the repository whose `ignore_ci` flag is toggled; it does not. Scoped impact: Critical, an attacker can flip a victim stack's deploy-gating configuration and then supply the CI state that gates its deploys. Proof idea: minitest test asserting `victim_stack.reload.ignore_ci` becomes false and subsequent `deployable?` now depends on attacker-supplied status after the cross-repo webhook.
