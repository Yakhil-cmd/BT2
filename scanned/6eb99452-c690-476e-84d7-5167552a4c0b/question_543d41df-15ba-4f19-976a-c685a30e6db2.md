Target: `Stack#next_commit_to_deploy` (`deployable_commits(commits_to_deploy)`) which relies transitively on `Commit#deployable?` for every undeployed commit in the stack. Attacker action: send a batch of `status` webhooks (a `branches` array with `name: 'master'` per `StatusHandler`'s accepted params, all signed for the attacker's own repo) whose shas are crafted/collided to match every undeployed commit in a victim's stack, flipping the entire undeployed range's CI state to `success` in one attacker-controlled burst. Precondition: victim stack has several undeployed commits sharing shas reachable/collidable by the attacker (e.g. shared base history, cherry-picks, or a forked repo with identical early history). Call sequence: repeated `StatusHandler#process` calls -> `Commit#create_status_from_github!` for each -> `Stack#next_commit_to_deploy` now returns the victim's latest commit as deployable -> `Stack#trigger_continuous_delivery` ships it. Binding: the repository that authenticated each webhook must equal the repository of the `Stack` whose full undeployed commit range gets marked deployable; it does not, for any of the commits. Scoped impact: Critical, an attacker fully green-lights a victim's entire deploy queue and triggers continuous delivery. Proof idea: minitest test seeding several undeployed commits in a victim stack, posting attacker-signed status webhooks for each sha, and asserting `Stack#next_commit_to_deploy` and a subsequent `trigger_continuous_delivery` ship the top commit.
