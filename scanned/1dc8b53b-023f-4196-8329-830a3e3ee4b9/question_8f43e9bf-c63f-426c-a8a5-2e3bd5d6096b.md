Target: `Shipit::GithubAuthenticationController#callback` session[:authenticated] = true is set unconditionally after `sign_in_github`, even though `sign_in_github` can raise if `User.find_or_create_from_github` or `user.update(github_access_token:)` fails validation (e.g. blank `name`). Attacker action: attacker crafts a GitHub profile with only a login and no derivable name (name nil, no rels[:self]) causing `User#github_user=` to still assign name := login, but a downstream `validates :name, presence: true` could still fail on edge malformed unicode/blank-after-strip logins; if `sign_in_github` raises, `session[:authenticated] = true` is never reached, so this path is not exploitable, but the reverse ordering (authenticated is set only after a successful, validated user) must be confirmed since it currently occurs AFTER user.update inside `sign_in_github`'s return but is set in `callback` right after regardless of `user.id` validity (nil id if not persisted only raises, not silently continues). Preconditions: a validation failure that raises inside sign_in_github. Call sequence: `sign_in_github(auth)` raises ActiveRecord::RecordInvalid -> callback aborts -> session[:authenticated] unset. Binding: session[:authenticated] == true only when User.find_or_create_from_github successfully persisted a User matching the completed GitHub identity. Scoped impact: High - if this ordering were reversed, an authenticated flag could be set for a non-existent/invalid user id, letting unauthenticated read access through UserRequiredMiddleware-style checks. Proof idea: minitest stubbing User.find_or_create_from_github to raise and asserting session[:authenticated] is never true after the callback request.
