Target: `Shipit::Command#interpolated_arguments` combined with `Shipit::TaskDefinition#render_title` (lib/shipit/command.rb, app/models/shipit/task_definition.rb). Attacker action: declare a task variable in `shipit.yml` named identically to a Shipit internal key already present in the merged env (e.g. `GITHUB_REPO_NAME`), then trigger the task with a value like `attacker-org/attacker-repo`. Preconditions: `EnvironmentVariables#permit` only checks that `GITHUB_REPO_NAME` is a declared variable name, oblivious to it colliding with `Stack#env['GITHUB_REPO_NAME']`. Call sequence: `TaskCommands#env` merges `@stack.env` (setting the true `GITHUB_REPO_NAME`) before `.merge(@task.env)` (attacker-controlled) - the attacker's value wins in the final hash passed to `Command.new(env:)`. Binding: `Command#env['GITHUB_REPO_NAME']` used inside a step string == `stack.repository.name`, the repository the stack actually deploys, never an attacker-declared task variable of the same name. Impact: Critical - a step like `deploy-notify $GITHUB_REPO_NAME` could be redirected to reference/act on a different repository's identifier, or leak into an external webhook call naming the wrong org/repo. Proof idea: unit test declaring a task variable named `GITHUB_REPO_NAME`, triggering with an attacker value, and asserting the final `Command#env['GITHUB_REPO_NAME']` still equals `stack.repository.name`.
