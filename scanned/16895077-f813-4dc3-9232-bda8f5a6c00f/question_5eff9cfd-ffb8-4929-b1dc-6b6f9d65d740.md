Target: TaskCommands#env — 'GIT_COMMITTER_NAME' => @task.user&.name || Shipit.committer_name. Attacker action: open a PR under a GitHub display name containing shell-metacharacter-laden text (the 'name' field from Shipit::User, itself populated from GitHub user profile data fetched via Shipit.github.api.user, not from the webhook payload directly for review-stack PRs opened by new users — see OpenedHandlerTest 'creates Shipit::Users'). Preconditions: attacker controls their own GitHub profile 'name' field arbitrarily. Call sequence: OpenedHandler#process (indirectly, via PullRequest#update!)-triggered Shipit::User creation stores github_user.name verbatim -> later TaskCommands#env sets GIT_COMMITTER_NAME to this value -> passed as an env value (not interpolated into the command line/argv) to Command#unbundled_env -> PTY.spawn. Binding: values placed into Command#env (a Hash passed to PTY.spawn) are NOT shell-interpreted the way argv strings are; the binding to verify is that attacker-controlled profile/label content reaching Command's ENV HASH never also reaches Command's ARGV (Command#interpolated_arguments) where shell metacharacters could matter. Scoped impact: bounds the RCE claim — confirms attacker-controlled display-name/committer strings land only in the env hash (safe from PTY.spawn argv-based injection) rather than in @args, distinguishing this from the shipit.yml-steps RCE vector. Proof idea: minitest setting a GitHub user name to '`rm -rf /`' and asserting it appears only in command.env['GIT_COMMITTER_NAME'] and never in command.args.
