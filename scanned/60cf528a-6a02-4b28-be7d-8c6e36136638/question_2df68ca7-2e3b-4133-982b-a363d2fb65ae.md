Target: Shipit::Webhooks::Handlers::Handler#stacks and #repository_name (shared base class used by StatusHandler, CheckSuiteHandler). Attacker action: send a genuinely-signed 'status' webhook from their own org where the JSON body's repository.full_name string is set to a victim org/repo pair (feasible because GitHub computes the HMAC over the exact bytes sent by the sender's own webhook delivery infrastructure -- an attacker fully controls the JSON they push from their own repo's commit statuses via a self-hosted CI naming an arbitrary target repo string). Preconditions: victim repository/stack tracks a real commit sha the attacker guesses or copies (e.g., a public commit sha on the victim repo). Call sequence: verify_signature passes using attacker org's webhook_secret over attacker-authored bytes; Handler#stacks calls Repository.from_github_repo_name(repository_name) returning the victim's Repository, then StatusHandler creates a CommitStatus row on the victim's commit using attacker-supplied state/description/target_url/context. Binding: organization whose webhook_secret verified the bytes == organization owning the commit whose Status row is written -- broken. Scoped impact: Critical, cross-repository write -- attacker forges CI/status results (e.g., marking a victim's commit as 'success') potentially unblocking an unauthorized deploy that gates on that status. Proof idea: test posting a status webhook signed by an attacker's own configured org but with repository.full_name/sha belonging to a different fixture stack, asserting a Status row is created on the victim commit.
