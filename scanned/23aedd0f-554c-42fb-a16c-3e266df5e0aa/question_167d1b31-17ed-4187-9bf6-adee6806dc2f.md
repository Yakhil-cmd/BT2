Target: Shipit::Api::CCMenuController#authenticate_api_client override (app/controllers/shipit/api/ccmenu_controller.rb) using ApiClient.authenticate(params[:token]) from a query string instead of Basic auth. Attacker action: attacker who intercepts a shared CCMenu URL (commonly embedded in build-status dashboards, browser history, or referrer headers) replays GET /ccmenu/OWNER/REPO/ENV?token=STOLEN_TOKEN from an unrelated origin. Preconditions: a valid-looking token string is reachable via referrer leakage (this scenario stays in scope because the vulnerability is the engine placing a bearer credential in a GET query string that is echoed into Referer headers of any outbound link from the CCMenu XML/dashboard page, not because the attacker already holds a legitimate secret). Binding: IDENTITY BINDING — the acting ApiClient == the GitHub identity/scope that authenticated this request; a token placed in a URL query string breaks this by leaking via Referer to any third-party resource the CCMenu page links out to. Scoped impact: High, exfiltration of a bearer credential (and downstream unauthenticated read of stack/deploy status) via URL-based token transport with no expiry binding to origin. Proof idea: test constructing a request with Referer header simulation showing the token param would be included in outbound Referer, then confirming ApiClient.authenticate accepts the same token indefinitely with no origin check.
