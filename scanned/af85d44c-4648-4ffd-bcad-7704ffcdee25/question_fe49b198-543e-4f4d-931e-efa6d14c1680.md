Target: `Shipit::ApiClient.authenticate` and `Shipit::SimpleMessageVerifier`. Attacker action: attacker who has observed (via any non-privileged channel, e.g. an error page or referrer leak of a CCMenu URL for their OWN authorized stack) their own valid `authentication_token`, and attempts to derive another client's token by manipulating the decimal id payload without knowing `Shipit.api_clients_secret`. Preconditions: attacker only knows their own token and id. Call sequence: `authenticate` does `find_by(id: message_verifier.verify(token).to_i)`; verification depends solely on `Shipit.api_clients_secret` (falling back to `secret_key_base`). Binding: only a token whose signature was produced with the true `api_clients_secret` (never observed by the attacker) resolves to a client id. Impact: Critical if `secret_key_base` fallback is a well-known/default Rails value in some deployments, letting an attacker sign arbitrary ids themselves without ever learning the real secret. Proof idea: minitest checking `Shipit.api_clients_secret` defaulting behavior and confirming `SimpleMessageVerifier.new(guessable_secret).generate(other_client.id)` is never accepted by `ApiClient.authenticate` under the app's actual configured secret.
