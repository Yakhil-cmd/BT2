Target: `Shipit::CCMenuUrlController#fetch` and `#client`. Attacker action: an authenticated Shipit browser session (attacker with any Shipit session, e.g. via a phished operator visit to a crafted link) visits `GET /stacks/:id/cc_menu_url` for a stack the session's user CAN currently see, then the resulting `ccmenu_url` (containing `client.authentication_token`) is later shared/leaked into a public CI dashboard. Preconditions: `client = ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` -- this client is NOT bound to `stack_id`, so its token authenticates against `ApiClient.authenticate` with no stack scope at all. Call sequence: `CCMenuController#authenticate_api_client` accepts this client's token via `params[:token]`, then `#stack` uses unscoped `Stack.from_param!(params[:stack_id])`, so the same token works for ANY stack id, not just the one it was minted for. Binding: the stack a token authorises (none, since `stack_id` is nil on this client) must still be bound to the stack named at mint time in the URL; instead any `stack_id` is accepted. Impact: Critical - a single leaked CCMenu URL grants read access to every stack in the installation, not just the one displayed to the user. Proof idea: minitest creating a CCMenu client/token for stack A via `fetch`, then issuing a request with the same token but `stack_id` for stack B, asserting stack B's data is returned.
