Target: `Shipit::Api::BaseController#require_permission!` versus `#stacks`/`#stack`. Attacker action: attacker holds an `ApiClient` scoped to stack 1 with `deploy:stack` permission, and sends `POST /api/stacks/2/deploys` with a crafted body referencing stack 2's commit. Preconditions: `DeploysController` (or any controller under `Api::BaseController`) resolves `#stack` via `stacks.from_param!(params[:stack_id])` in the base implementation, but any subclass or code path that swaps in an unscoped `Stack.from_param!` (as `CCMenuController` does) breaks the narrowing. Call sequence: `require_permission!(:deploy, :stack)` only calls `current_api_client.check_permissions!('deploy:stack')` -- it never compares `stack.id` to `current_api_client.stack_id`. Binding: the permission checked (`deploy:stack`) == the permission the action needs AND the stack touched ∈ stacks authorised by `current_api_client.stack_id`; only the first half is enforced. Impact: Critical - a token scoped to stack 1 could deploy code on stack 2 if any controller resolves `stack` without `stacks.from_param!`. Proof idea: minitest constructing an ApiClient with `stack_id: 1`, permission `deploy:stack`, and asserting any controller action operating on stack 2 via a non-scoped stack lookup is rejected with 404/403.
