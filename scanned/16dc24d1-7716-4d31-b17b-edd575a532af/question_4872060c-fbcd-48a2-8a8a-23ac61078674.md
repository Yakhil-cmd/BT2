Target: `Shipit::Api::BaseController#identify_user` and `#current_user`. Attacker action: attacker with a valid but narrowly-scoped `ApiClient` token sends `POST /api/stacks/1/tasks` (or similar mutating endpoint) with header `X-Shipit-User: some-admin-login` where `some-admin-login` is an existing privileged Shipit `User`. Preconditions: a `User` record with login `some-admin-login` exists; attacker's ApiClient has `write:stack`/`deploy:stack` permission on their own stack. Call sequence: `identify_user` does `User.where('lower(login) = ?', user_login.downcase).first` purely from the unauthenticated header, setting `current_user` used for attribution (e.g. `Task#author`, `Deploy#user`) without any session or token check tying the header to that identity. Binding: `current_user` == the GitHub identity that authenticated this request (IDENTITY_BINDING); here it is set from an unauthenticated header. Impact: Critical - forged attribution of a deploy/task to an arbitrary user, and any code path that trusts `current_user`'s identity for authorization (not just display) can be spoofed. Proof idea: minitest hitting an API action with `X-Shipit-User` header set to another user's login and asserting the created record's `user`/`author` is that spoofed user despite no authentication proving the caller is them.
