Target: `pox-5.clar` `min-ustx-for-sats-amount` and `register-for-bond`'s `ERR_TOO_MUCH_SATS` guard against `protocol-bond-allowances`. Attacker action: staker calls `register-for-bond` with `btc-lockup = (err sats)` where `sats` is within their `allowance` (from `protocol-bond-allowances`) but the `stx-value-ratio` used to convert `sats` to `amount-ustx` via `min-ustx-for-sats-amount` is read from the `bond`'s config captured at a stale point if `setup-bond` for that `bond-index` is later called again by the admin (out of scope) — however, attacker can instead exploit the same effect by registering into a *newly re-used* `bond-index` after a prior bond at that index expired, if `protocol-bonds` map key reuse lets a stale `stx-value-ratio` from the old bond briefly coexist with sats credited under the old ratio while the allowance map (`protocol-bond-allowances`) was never cleared/reset for the new bond, letting the staker's `sats-total` from the old allowance apply to the new bond's (different) ratio. Preconditions: `bond-index` reused after expiry; old allowance row for that index/staker still present; new bond set up with a different `stx-value-ratio`. Call sequence: old bond at index K allows staker sats S -> bond K expires -> `setup-bond`(K, new ratio) reuses index K -> staker calls `register-for-bond`(K, ...) with `amount-ustx = min-ustx-for-sats-amount(S, OLD-ratio-cached-client-side, ...)` sent but contract now reads the *new* ratio, so `>=` check passes using a smaller floor than the new ratio actually requires if the new ratio is lower and stale allowance S is reused for more sats-equivalent value than currently backed. Equality broken: `amount-ustx` locked must equal at least `min-ustx-for-sats-amount(sats-total, CURRENT stx-value-ratio, CURRENT min-ustx-ratio)` for the bond index actually being registered into, not a value computed against a stale ratio. Impact: Critical — sats credited convert to locked-STX-equivalent value at a stale ratio, letting signing weight/reward slots exceed the STX actually locked at the bond's true current ratio. Proof idea: Clarity/Rust test: `setup-bond`(index 0, ratio R1), let it expire, `setup-bond`(index 0, ratio R2 != R1) reusing the index without clearing `protocol-bond-allowances`, register-for-bond with `amount-ustx` computed against R1, assert the contract correctly rejects with `ERR_INSUFFICIENT_STX` against R2, not R1.
