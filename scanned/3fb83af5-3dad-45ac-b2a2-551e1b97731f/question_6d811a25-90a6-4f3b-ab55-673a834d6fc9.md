Target: PullRequest::OpenedHandler#provision? combined with Shipit::ReviewStack#provisioner_class / ProvisioningHandler.fetch(provisioning_handler_name). Attacker action: open a PR from a fork branch whose shipit.yml sets 'provision.handler_name' to the name of a host-application-registered ProvisioningHandler subclass (any handler_name accepted by ProvisioningHandler.fetch, which is presumably restricted to a registry — verify). Preconditions: provision? true via the precedence bug. Call sequence: create! + provisioning_handler_name sourced from the attacker's own shipit.yml (cacheable_config's 'provision' => {'handler_name' => provisioning_handler_name}) -> stack.provisioner_class -> ProvisioningHandler.fetch(name) -> stack.provisioner.up called on the deprovisioned->provisioning transition, which may itself shell out or call cloud-provider APIs with credentials. Binding: the provisioning_handler_name executed for a stack == a handler_name an authorized operator configured for that repository, not one an attacker's own shipit.yml supplied. Proof idea: minitest registering two ProvisioningHandler subclasses in the test host app, setting one repository's shipit.yml (fixture) to reference the OTHER repository's intended handler_name, and asserting ProvisioningHandler.fetch(provisioning_handler_name) returns that other, more-privileged handler for the attacker's stack.
