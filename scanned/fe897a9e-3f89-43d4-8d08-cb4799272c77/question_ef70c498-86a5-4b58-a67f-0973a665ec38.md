Target: bytes_to_kzg_proof / bytes_to_kzg_commitment (src/common/bytes.c) as used identically by verifyKzgProof and verifyBlobKzgProof in bindings/node.js/lib/kzg.d.ts. Attacker input: proofBytes = point at infinity while commitmentBytes is a normal, non-infinity, valid commitment, with zBytes/yBytes arbitrary valid field elements. Preconditions: single verifyKzgProof call. Call sequence: JS verifyKzgProof(commitmentBytes, zBytes, yBytes, proofBytes) -> kzg.cxx -> verify_kzg_proof -> bytes_to_kzg_commitment (rejects only if not on curve/subgroup, accepts real commitment) and bytes_to_kzg_proof (accepts infinity via validate_kzg_g1) -> pairing_check computes e(Commitment - y*G1, G2) == e(Infinity, X-z*G2), where the right side pairing with the identity element is always trivially satisfiable only when the left side is also the identity, i.e., Commitment == y*G1. Equality broken: SOUNDNESS `*ok == true` iff the pairing relation holds; because infinity is an accepted proof value with no documented rule about what such a proof commits to, an attacker who can find y such that Commitment == y*G1 (only possible for a specific structured commitment, but no check anywhere forbids constructing z,y,proof=infinity combinations that satisfy the pairing incidentally for commitments the attacker chooses) can make ok==true. Impact: Critical if such a triple can be constructed for an attacker-chosen commitment (this must be tested empirically), since it would allow a forged proof to verify without the real polynomial machinery. Proof idea: C unit test attempting to construct commitment=y*G1 for attacker-chosen y (which is just committing to a constant polynomial equal to y — a legitimate case), then setting proof=infinity, and asserting whether verify_kzg_proof returns ok==true, comparing against pairing_check performed manually to confirm whether ok matches the true pairing relation for this specific degenerate but reachable case, exposing the undocumented meaning of an infinity proof.
