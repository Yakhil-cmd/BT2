Target: `Shipit::Webhooks::Handlers::Handler#stacks` vs `StatusHandler#process`. Attacker action: send any `status` webhook payload to `POST /webhooks` where `payload.dig('repository','full_name')` names a repository the attacker legitimately owns, but `params.sha` is copied verbatim from a commit SHA the attacker observed in a public Shipit dashboard/task page belonging to another tenant. Preconditions: any Stack anywhere in the Shipit instance has a `Commit` with that sha. Call sequence: `StatusHandler#process` never calls `self.stacks` (which would correctly scope to `Repository.from_github_repo_name(repository_name)`); it queries `Commit.where(sha: params.sha)` globally. Binding: `Handler#stacks` (repository-scoped commit set) must equal the actual set of `Commit` rows mutated by `process` -- it is bypassed entirely for this handler. Impact: Critical, global cross-tenant write -- any SHA collision across unrelated repositories lets one webhook mutate CI state everywhere that SHA appears. Proof: minitest test with two `Stack`/`Repository` fixtures sharing identical commit `sha`, posting one webhook, asserting both commits' `status` changed.
