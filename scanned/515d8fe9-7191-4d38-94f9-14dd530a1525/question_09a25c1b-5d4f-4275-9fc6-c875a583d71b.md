Attacker action: attacker's own repository emits a `status` webhook with `state: failure` (or any blocking context configured via `deploy_spec`) for a SHA equal to an *older* commit in a victim Stack's undeployed range, intending to poison `blocked?`'s scan (`stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?)`) and thereby block deploys/merges for the victim stack as a griefing/denial vector that also demonstrates the write crosses tenant boundaries (in-scope as a cross-repo commit mutation, not as DoS). Preconditions: Stack A has `blocking_statuses` configured and an undeployed commit range; a shared SHA exists in that range. Call sequence: webhook -> `StatusHandler#process` -> `create_status_from_github!` on the shared `Commit` -> subsequent `deployable?`/`blocked?` evaluation on Stack A's newer commits is corrupted by the injected status. Binding: repository authenticated by webhook == repository whose deploy-blocking evaluation is affected -- violated. Impact: Critical, cross-repository mutation of another tenant's commit/task-blocking state via `Status` write. Proof: minitest test asserting `blocked?` toggles for Stack A's newer commit after an off-tenant webhook writes a failing status onto the shared older commit.
