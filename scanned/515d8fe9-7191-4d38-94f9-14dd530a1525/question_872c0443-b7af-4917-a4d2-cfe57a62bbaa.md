Target: `Shipit::Commit#create_status_from_github!` invoked from `StatusHandler#process`. Attacker action: attacker crafts a `status` webhook body with `sha` equal to the SHA of a currently pending/failing commit at the HEAD of a victim Stack configured with `continuous_deployment: true`, and `state: success`. Preconditions: victim Stack has `continuous_deployment?` true and `ignore_ci?` false; the commit is not `locked?`; no `blocking_statuses` present. Call sequence: webhook -> `StatusHandler#process` -> `Commit#create_status_from_github!` -> `Status.replicate_from_github!` -> `Commit#add_status` calls `stack.schedule_merges` and `Commit#schedule_continuous_delivery` (via `after_commit` on `Status`) -> `Commit#deployable?` returns true because `success? && !blocked?` -> `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob.perform_later(stack)` since `stack.continuous_deployment? && stack.deployable?`. Binding: the repository named in the webhook's verified payload must equal the repository of the `stack` on which `ContinuousDeliveryJob` is triggered -- it is never checked. Impact: Critical, unauthorized deploy of attacker-uninfluenced but tenant-mismatched commit -- a victim's stack ships based on a foreign repository's status event. Proof: minitest test asserting `ContinuousDeliveryJob` is enqueued for the victim's `Stack` after processing a `status` webhook payload whose `repository.full_name` differs from the stack's `Repository`.
