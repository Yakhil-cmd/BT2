Target: `Shipit::MergeRequest#all_status_checks_passed?` and `StatusHandler#process`. Attacker action: attacker sends a `status` webhook (from a repository they control) with `sha` matching the `head.sha` of a pending `MergeRequest` in a victim's merge queue, `state: success`, `context` matching a `required_status` name from the victim's `shipit.yml`. Preconditions: victim Stack has `merge_queue_enabled: true` and a `MergeRequest` in `pending` state whose `head` commit's `sha` happens to equal the attacker's chosen SHA (e.g. attacker forks or reuses the exact same tree/commit). Call sequence: webhook -> `StatusHandler#process` writes a `Status` on the shared `Commit` row -> `MergeRequest::StatusChecker` (subclass of `Status::Group`) recomputes over `head.statuses_and_check_runs` -> `all_status_checks_passed?` returns true -> merge queue processing (`MergeRequest#reject_unless_mergeable!` / scheduled merge) proceeds toward `merge!`, calling `stack.github_api.merge_pull_request`. Binding: repository authenticated by the webhook signature must equal the repository whose `MergeRequest` is advanced toward merge -- unenforced. Impact: Critical, unauthorized merge of a PR in a repository the attacker never touched, triggered purely by a same-SHA webhook from an unrelated repository they own. Proof: minitest test seeding a `MergeRequest` with `head` sha X in Stack A, posting a `status` webhook for that sha from Repository B, and asserting `all_status_checks_passed?` becomes true for Stack A's `MergeRequest`.
