Target: StatusHandler params parser (requires :sha, requires :state) vs repository binding. Attacker action: POST /webhooks with event type 'status', a valid signature for attacker's own repo, and a sha value copied verbatim from a public commit visible in victim Stack A's GitHub UI (no need to even create a matching commit in their own repo -- ExplicitParameters only requires sha/state to be present strings, never validated against attacker's own repo's actual commits). Preconditions: attacker can read a target sha from Stack A's public GitHub page or Shipit UI; StatusController/WebhooksController exposes no cross-check that sha belongs to repository. Call sequence: WebhooksController#status_handler_class or dispatcher path signs against attacker's own webhook_secret -> params.sha accepted as arbitrary string -> Commit.where(sha: params.sha) matches Stack A's row regardless of which repo 'owns' that sha in GitHub's actual object graph. Binding: params.sha must be validated as belonging to repository_name's git object store before Commit.where(sha:) is scoped; this validation is absent. Impact: Critical, attacker need not even create a real colliding commit -- only knowledge of the target sha string, which is often public. Proof: minitest test posting a signed status webhook from a fixture repo with sha copied from a different fixture stack's commit, no matching commit created on attacker side, and asserting the victim commit's status is still mutated.
