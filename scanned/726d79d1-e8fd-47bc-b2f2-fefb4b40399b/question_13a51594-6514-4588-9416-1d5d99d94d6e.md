Can an attacker exploit the absence of a `stacks`/`repository_name` check in `StatusHandler#process` to mark green a commit belonging to a Stack configured with `ignore_ci?` false but `continuous_deployment?` true, in a repository they have never pushed to and do not own, purely by guessing or observing a public sha (e.g. via the target repo's public GitHub commit history, which is legal to view) and re-declaring that exact sha in a status event sent from a completely unrelated repository they do control? Precondition: victim Stack's head commit sha is publicly visible (any public GitHub repo commit page); attacker owns Repo A, unrelated to victim. Call sequence: attacker copies victim's public sha -> `POST /webhooks` from Repo A with `state:'success', sha: <victim sha>` verified by Repo A's `webhook_secret` -> `StatusHandler#process` matches by raw `sha` column with no stack/repo predicate -> victim `Commit#success?` becomes true -> `schedule_continuous_delivery` -> `ContinuousDeliveryJob`. Binding: attacker's authenticated scope (Repo A only, via their own `webhook_secret`) == the `Stack` mutated (must be Repo A's stacks per `Handler#stacks`, but is actually any stack, including the victim's) — violated. Scoped impact: Critical, unauthorized continuous deployment of a tenant's own already-merged code, timed and triggered entirely by the attacker. Proof idea: minitest test with two independently-owned stacks, sending only the attacker-owned app's signed webhook, asserting the victim stack's `ContinuousDeliveryJob` is enqueued.
