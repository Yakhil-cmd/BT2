In Shipit::Api::TasksController#trigger, params.env is passed as the `env:` hash to Stack#trigger_task and ultimately merged by TaskCommands#env into Command.new(..., env:) which becomes Command#unbundled_env merged verbatim into the PTY.spawn environment (lib/shipit/command.rb#start, #unbundled_env). Can an ApiClient whose `stack_id` is scoped to stack A submit a POST to /api/stacks/:owner/:repo/:environment/tasks/:task_name/trigger naming a task in stack A, but with an env hash containing a key like `GIT_ASKPASS` or `LD_PRELOAD` that is never checked against TaskDefinition's declared/allowed env keys before PTY.spawn(unbundled_env, ...) executes? Binding: the KEYS of params[:env] written into Command#env == a key allowlist declared by the task/stack owner (this allowlist does not exist for TasksController#trigger, only Task#env consumers apply EnvironmentVariables.permit elsewhere). Scoped impact: Critical RCE/env-injection on the deploy host under the stack's existing GITHUB_TOKEN-bearing process. Proof: integration test posting env: {'GIT_ASKPASS' => '/tmp/evil'} to /trigger with a valid but low-privilege ApiClient token scoped to that stack, and asserting the spawned Command#env contains the attacker key untouched.
