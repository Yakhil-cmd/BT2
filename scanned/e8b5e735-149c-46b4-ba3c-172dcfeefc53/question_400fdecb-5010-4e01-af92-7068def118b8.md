Target: `StackStxOp::parse_from_tx` interaction with `pox_lock_v3` (pox_3.rs) when `num_cycles` from `data.num_cycles` is attacker-chosen and unbounded at the burnchain-op parse layer. Attacker action: submit a `StackStxOp` with `num_cycles` = a very large value (e.g. u128::MAX truncated to whatever field width) so `unlock_burn_height` computed downstream overflows or wraps to a smaller value than the current burn height. Preconditions: attacker's PreStxOp/StackStxOp pair well-formed; no cap on `num_cycles` enforced in `parse_from_tx` itself. Call sequence: `parse_from_tx` returns `Ok(StackStxOp{ num_cycles: data.num_cycles, .. })`; pox-5 Clarity computes `unlock_burn_height` from `num_cycles`; if that computation overflows and wraps below `current_burn_height`, `pox_lock_v3`'s `assert!(unlock_burn_height > 0)` still passes but the lock immediately becomes unlockable. Equality: SINGLE UNLOCK — value unlocks once, at the committed height; breaks if `unlock_burn_height` wraps to a height in the past, letting the attacker unlock immediately after claiming a multi-cycle lock's reward-set weight. Impact: Critical, gaining reward-set signing weight/slots for a multi-cycle commitment while only actually locking for near-zero duration (double-counting a commitment vs. actual lock duration). Proof idea: Rust test submitting a `StackStxOp` with an extreme `num_cycles`, asserting the computed `unlock_burn_height` is validated to exceed current burn height by the full committed cycle count before `pox_lock_v3` is called.
