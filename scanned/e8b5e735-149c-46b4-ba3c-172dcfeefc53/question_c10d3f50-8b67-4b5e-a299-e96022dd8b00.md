Target: `DelegateStxOp::parse_from_tx`'s `reward_addr_index` handling (delegate_stx.rs:174-192) which silently sets `reward_addr: None` when `outputs.len() <= index`. Attacker action: craft a `DelegateStxOp` payload whose `reward_addr_index` points past the actual number of Bitcoin outputs in the transaction, forcing `reward_addr` to default to `None` while `delegated_ustx` remains fully set to a large value. Preconditions: attacker constructs the tx with minimal outputs (delegate_to only) but an out-of-range `reward_addr_index` in the data payload. Call sequence: `parse_from_tx` returns `Ok(DelegateStxOp{ reward_addr: None, delegated_ustx, delegate_to, ... })`; a delegate later calls `delegate-stack-stx` in pox-5 supplying its own `pox-addr`, and because the op carries no committed `reward_addr`, the delegate's arbitrarily chosen reward address is accepted as if the delegator had specified none (permitted by design) — but check whether this lets the delegate redirect rewards intended implicitly for the delegator's own address. Equality: reward address credited for locked STX == the reward address the delegator's op actually committed to (or explicitly allowed the delegate to choose); breaks if a malformed index silently downgrades an intended commitment to 'no preference' rather than erroring. Impact: Critical if this misroutes reward payouts away from the delegator without their authorisation (theft of rewards). Proof idea: Rust test crafting `reward_addr_index` >= `outputs.len()` and asserting the resulting `DelegateStxOp.reward_addr` is `None` only when the delegator's payload truly omitted an index, and that downstream reward routing cannot be attacker-steered by the delegate as a result.
