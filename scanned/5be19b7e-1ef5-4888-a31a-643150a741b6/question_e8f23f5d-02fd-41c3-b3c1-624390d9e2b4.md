Target: `Shipit::Commit.from_github` and `Shipit::User.find_or_create_author_from_github_commit` (app/models/shipit/user.rb). Attacker action: an unprivileged GitHub user pushes a commit to their own fork whose message body is `Merge-Requested-By: <victim-login>\n`, then opens/updates a PR so `Shipit::GithubSyncJob#append_commit` calls `Commit.create_from_github!`. Preconditions: `victim-login` already exists as a `Shipit::User` (e.g. a maintainer). Call sequence: `PushHandler#process` -> `Stack#sync_github` -> `GithubSyncJob#perform` -> `Commit.from_github` -> `User.find_or_create_author_from_github_commit` matches the `MergeRequest::MERGE_REQUEST_FIELD` regex on attacker-authored commit message text and calls `User.find_or_create_by_login!(match_info[1])`. Binding that breaks: the identity authenticated by the webhook's originating org/committer == the `author_id` written on the `Commit` row; here the commit's `author` becomes `victim-login` even though `victim-login` never authored or approved the commit. Scoped impact: Critical - a payload for one repository (attacker's fork branch pushed to a tracked stack) mutates authorship attribution on a `Commit` row, falsely attributing attacker-controlled code to a trusted identity, which can influence deploy audit trails and `SHIPIT_USER`/`GIT_COMMITTER_NAME` used later in `Command` env. Proof idea: minitest asserts `commit.author.login == 'victim-login'` while the actual git commit author/committer field is the attacker's own GitHub identity, and no field on `Commit` records that divergence.
