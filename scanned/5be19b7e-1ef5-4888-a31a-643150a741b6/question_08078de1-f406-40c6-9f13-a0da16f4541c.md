Target: `Shipit::WebhooksController#repository_owner` and `#verify_signature` (app/controllers/shipit/webhooks_controller.rb). Attacker action: POST /webhooks with `X-Github-Event: push` and a body whose top-level `repository.owner.login` names Org A (which the attacker does not control) while `repository.full_name` inside nested handler-parsed params names Org B's repo, exploiting any mismatch between the field used to select the verifying `webhook_secret` and the field used later by `PushHandler` to select stacks. Preconditions: Shipit configured with per-org GitHub Apps via `Shipit.github(organization:)`. Call sequence: `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` from `repository.owner.login`, verifies signature against that org's secret; `create` then calls `Webhooks.for_event(event).each { |handler| handler.call(params) }` where `PushHandler` filters `stacks.where(branch:)` with no re-check that `params.repository.full_name`'s owner equals `repository_owner`. Binding: org whose `webhook_secret` verified the body == org owning every `Stack` mutated by the handler; if an attacker who controls Org A's webhook secret (their own org) crafts a body naming Org B's `repository.full_name`/branch, the check never re-validates repository ownership. Scoped impact: Critical - a webhook validly signed by attacker's own org's secret can mutate/sync a different org's stack since `PushHandler#process` only filters by `branch`, not by verified owner. Proof idea: minitest integration test posts with a valid signature for org 'attacker-org' but `repository.full_name = 'victim-org/other-repo'` matching a real stack's branch, asserting `GithubSyncJob` is enqueued for the victim stack.
