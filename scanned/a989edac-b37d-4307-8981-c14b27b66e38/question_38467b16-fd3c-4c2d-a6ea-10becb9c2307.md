Target: Shipit::CCMenuUrlController#fetch and Shipit::Api::CCMenuController#authenticate_api_client/#stack. Attacker action: an authenticated low-privilege user (or anyone who obtains a link an operator visited) calls GET /stacks/:stack_id/ccmenu_url on stack A, receiving `{ccmenu_url: '.../ccmenu.xml?token=...'}}` where `client` is `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` with no `stack:` attribute set (so `stack_id` is nil); attacker then swaps `stack_id` in the URL to point at stack B and GETs /api/stacks/:stack_id/ccmenu.xml?token=<same token>. Preconditions: any two stacks A and B exist; the CCMenu client created for the user has `stack_id` nil (unscoped). Call sequence: CCMenuUrlController#client creates an ApiClient with `permissions: %w[read:stack]` and no stack scope -> CCMenuController#authenticate_api_client calls `ApiClient.authenticate(params[:token])` -> CCMenuController#stack calls `Stack.from_param!(params[:stack_id])` directly, bypassing BaseController#stacks' `current_api_client.stack_id?` narrowing entirely. Binding: the stack an API request touches ∈ the stacks `current_api_client.stack_id` authorises; this fails because CCMenuController never intersects `stack` with `stacks`. Scoped impact: Critical - unauthenticated-for-that-stack read of deploy state (`stack.deploys_and_rollbacks.last`) for a stack outside the token's authorised scope, cross-tenant read via a token minted for stack A. Proof idea: integration test creating an ApiClient with `stack_id: stack_a.id` via `authentication_token`, GET `/api/stacks/#{stack_b.to_param}/ccmenu.xml?token=...`, assert response is 200 with stack_b data instead of 403/404.
