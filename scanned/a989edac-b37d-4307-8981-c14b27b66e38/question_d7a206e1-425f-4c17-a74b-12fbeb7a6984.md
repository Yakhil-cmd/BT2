Target: Api::CCMenuController#authenticate_api_client and #stack. Attacker action: obtains (via any authorized user visiting CCMenuUrlController#fetch for stack A, e.g. by tricking an operator into loading /stacks/:id/ccmenu.xml or via a public dashboard link) a ccmenu URL of the form /api/stacks/A/ccmenu.xml?token=T, then replays GET /api/stacks/B/ccmenu.xml?token=T for a different stack B. Preconditions: CCMenuUrlController#fetch has previously minted an ApiClient with permissions read:stack and no stack_id restriction (client scoped only by name 'CCMenu Client', not stack). Call sequence: CCMenuController#authenticate_api_client -> ApiClient.authenticate(params[:token]) succeeds because the token is unscoped -> CCMenuController#stack -> Stack.from_param!(params[:stack_id]) bypasses BaseController#stacks entirely -> require_permission :read, :stack passes since check_permissions! only checks operation:scope string, not stack identity. Binding: the stack referenced by params[:stack_id] must be an element of the stacks current_api_client.stack_id authorizes, but CCMenuController#stack never applies that scope. Scoped impact: Critical, cross-repository read — a token minted for one stack's CCMenu badge reads deploy state of any other stack. Proof idea: integration test creating two stacks, minting one ccmenu URL via CCMenuUrlController#fetch for stack A, then requesting stack B's ccmenu.xml with A's token and asserting success, exercising the stack scope binding.
