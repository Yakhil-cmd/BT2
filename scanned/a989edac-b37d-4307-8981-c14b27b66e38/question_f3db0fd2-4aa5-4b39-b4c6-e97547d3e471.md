Target: ApiClient#authentication_token generation reused as a URL query param by CCMenuUrlController#fetch, and browser Referer leakage. Attacker action: an operator visits /stacks/:id/ccmenu_url in a browser, then navigates to an external attacker-controlled page linked from the rendered ccmenu_url JSON response page (if rendered in an HTML context with outbound links) or the ccmenu.xml consumer (a CI dashboard) makes a request to an attacker-supplied resource, leaking the URL (and thus the token) via the Referer header. Preconditions: the ccmenu_url endpoint returns json but some consumer of api_stack_ccmenu_url embeds it as a resource URL fetched by a third-party tool that itself makes outbound requests including Referer. Call sequence: CCMenuUrlController#fetch -> uri.query = {'token' => client.authentication_token}.to_query -> render(json: {ccmenu_url: uri.to_s}) -> token now travels in a URL rather than an Authorization header, making it subject to Referer/log leakage anywhere the URL is used as a link. Binding: a bearer credential authorizing stack reads should not be transmitted via a mechanism (URL query string) that is inherently more leak-prone than the header-based BasicAuth path used elsewhere in BaseController. Scoped impact: High, exfiltration of an ApiClient token (equivalent to api credential exfiltration) via URL leakage channels outside this engine's direct control once minted. Proof idea: test asserting CCMenuUrlController#fetch's returned URL contains the raw token in cleartext query string form, documenting the credential-in-URL exposure surface for a High-severity finding.
