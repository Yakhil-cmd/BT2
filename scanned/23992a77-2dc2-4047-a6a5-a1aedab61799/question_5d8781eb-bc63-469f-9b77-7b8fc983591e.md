In Shipit::Webhooks::Handlers::StatusHandler#process, `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` never calls the inherited `Handler#stacks` (which scopes via `Repository.from_github_repo_name(repository_name)`). If attacker A owns repo-A and creates an empty-tree commit whose SHA collides with a SHA already present as a Commit row in victim Stack B (e.g. by cherry-picking/copying the same tree onto their own branch so GitHub computes an identical SHA), and A POSTs a status webhook for repo-A verified by repo-A's own `webhook_secret`, does `Commit#create_status_from_github!` write a Status onto the Commit belonging to Stack B? Binding: repository named in the verified payload (repo-A) == repository owning the Commit row mutated (should be Stack B's repo, but isn't checked). Impact: Critical, cross-repository stack/commit corruption for any tenant sharing that SHA. Proof: integration test POSTing to /webhooks with a valid signature for repo-A, asserting Stack B's commit.statuses changed.
