Target: Shipit::Commit#blocked? (app/models/shipit/commit.rb) in combination with forged cross-repo statuses. Attacker action: forge a 'failure' state status (not just 'success') via the same StatusHandler#process path, targeting a sha shared with an EARLIER undeployed commit in a victim's stack, from a webhook signed for the attacker's own repository. Preconditions: victim stack has blocking_statuses configured (non-empty) so Commit#blocked? scans stack.commits.reachable.newer_than(last_deployed_commit).older_than(self).any?(&:blocking?). Call sequence: StatusHandler#process writes a 'failure'/blocking Status onto the shared-sha commit in the victim stack -> that commit's #blocking? becomes true -> every later undeployed commit's #blocked? becomes true -> Commit#deployable? for all of them becomes false, silently halting the victim's continuous delivery pipeline. Binding: the repository named in the payload that supplied the blocking status must equal the repository of the stack whose deploy pipeline is halted; it does not. Scoped impact (Critical - denial of legitimate deploys counts as an unauthorized state mutation/CI-state rewrite of another tenant's stack per the Scope, not as DoS): an attacker with zero relationship to the victim's stack can freeze its continuous delivery by rewriting CI state from a foreign, self-controlled repository's webhook. Proof idea: minitest test asserting stack.commits later than the forged-failure commit all report deployable? == false after a status webhook verified only for an unrelated org is posted.
