Target: Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?. Attacker opens a pull request from a fork against a repository whose Shipit::Repository#review_stacks_enabled is false but whose provisioning_behavior is 'allow_with_label' and provisioning_label_name is set; attacker adds that label to their own PR before opening it, then POSTs the pull_request 'opened' webhook. Precondition: repository.review_stacks_enabled == false, provisioning_behavior == 'allow_with_label'. Call sequence: OpenedHandler#process -> respond_to_pull_request_opened? -> provision? evaluates '(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?)' which never ANDs with review_stacks_enabled due to && / || precedence -> ReviewStackAdapter#find_or_create! -> create! builds ReviewStack with branch: params.pull_request.head.ref and queues Shipit::ReviewStackProvisioningQueue.add(stack). Binding: repository.review_stacks_enabled (false) == the gate that provision? actually enforces (true) -- these must be equal but are not. Scoped impact: Critical, unauthorized deploy - a stack is created and provisioned for a repository whose owner never enabled review stacks. Proof idea: minitest asserting Shipit::Stack.count increases via OpenedHandler.new(payload).process when review_stacks_enabled is false and provisioning_behavior is allow_with_label with the label present.
