Target: Shipit::Api::CCMenuController#stack and #authenticate_api_client. Attacker action: an unprivileged internet user obtains a legitimate CCMenu URL for stack A (e.g. via a link an operator pastes) that embeds token=<ApiClient#authentication_token for stack A>, then sends GET /api/stacks/:stack_id/ccmenu.xml with that same token but stack_id set to stack B's param. Preconditions: two Stack rows exist, an ApiClient scoped to stack A exists (stack_id set), Shipit.disable_api_authentication is false. Call sequence: CCMenuController#authenticate_api_client calls ApiClient.authenticate(params[:token]) (bypassing BaseController#stacks scoping), then require_permission :read, :stack triggers require_permission! which only calls current_api_client.check_permissions!(:read, :stack) — a name-only permission list check with no stack_id comparison — then #stack calls Stack.from_param!(params[:stack_id]) directly, never intersecting with `stacks`/current_api_client.stack_id. Binding: stack requested via params[:stack_id] == a stack ∈ Stacks authorized by current_api_client.stack_id — this equality is never checked, so it breaks. Impact: Critical — unauthenticated cross-stack disclosure of deploy status for stack B using a token that should only read stack A. Proof idea: integration test creating ApiClient(stack: stack_a, permissions: ['read:stack']), GET .../stacks/#{stack_b.to_param}/ccmenu.xml?token=..., assert response is 200 with stack_b's deploy data instead of 403/404.
