Target: `SameSiteCookieMiddleware#call`'s cookie-splitting logic `headers['Set-Cookie'].split(COOKIE_SEPARATOR)`. Attacker action: none needed from attacker directly; instead this is a precondition-verification question. If a downstream app/rack middleware sets a Set-Cookie header using ', ' (Expires date commas) rather than a bare newline, and `COOKIE_SEPARATOR = "\n"` mis-splits multi-cookie headers, the resulting mutated cookie string could corrupt the session cookie's own Expires/Path attributes when '; SameSite=None' is appended to the wrong fragment, potentially widening the cookie's Path or dropping HttpOnly. Preconditions: multiple Set-Cookie headers present in one response (common with session + CSRF + any other engine-set cookie), TLS in effect. Call sequence: `set_cookies.map!` blindly appends '; Secure' and '; SameSite=None' to whatever token the naive newline-split produced, without re-validating cookie attribute boundaries (e.g., HttpOnly, Path=/) survive intact. Binding: session cookie's HttpOnly/Path/Secure attributes as originally set by Rails session store == attributes present in the final header the browser receives (must remain equal; broken if splitting/reappending corrupts an attribute). Scoped impact (High): a corrupted session cookie attribute (e.g., broadened Path or dropped HttpOnly) increases the attack surface for session theft via unrelated XSS on the host, and independently confirms the SameSite=None weakening applies indiscriminately to the security-critical session cookie. Proof idea: unit test on `SameSiteCookieMiddleware#call` feeding a multi-cookie Set-Cookie header (session + one other) with an Expires date containing a comma, and asserting the session cookie's HttpOnly/Path attributes are unchanged aside from the intended Secure/SameSite additions.
