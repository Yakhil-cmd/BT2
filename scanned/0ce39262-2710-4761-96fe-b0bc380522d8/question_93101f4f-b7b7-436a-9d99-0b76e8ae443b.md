[Target: Shipit::User.find_or_create_from_github / #github_user=] Attacker with a fresh, never-before-seen GitHub account authenticates once, producing a legitimate `User` row (github_id = attacker's real id, login = attacker's real login). Attacker then renames their GitHub login to match an existing privileged `User` row's `login` (one created via `find_or_create_by_login!` and holding `Membership`s) and re-authenticates. Precondition: `find_from_github` matches by `github_id` first, so the attacker's own row is found/updated, not the victim's — but `github_user=` unconditionally overwrites `login: github_user.login` on the attacker's own row to now equal the privileged row's stale login, producing two `User` rows with the same login yet different `github_id`. Call sequence: `callback` -> `sign_in_github` -> `find_or_create_from_github` finds attacker's row by `github_id` -> `github_user=` sets `login` to the just-renamed value colliding with the stale privileged row -> any subsequent `find_or_create_by_login!('shared-login')` calls (webhooks) now non-deterministically match one of two rows. Binding that breaks: at most one `User` row names a given `login` at any time it is used for identity resolution. Scoped impact: Critical, ambiguous identity resolution enabling escalation into `Shipit.github_teams`-gated actions. Proof idea: ActiveSupport::TestCase creating a privileged `User` via `find_or_create_by_login!`, then calling `find_or_create_from_github` for a different `github_id` with the same `login`, asserting two rows now share that `login` with no model-level uniqueness validation raised.
