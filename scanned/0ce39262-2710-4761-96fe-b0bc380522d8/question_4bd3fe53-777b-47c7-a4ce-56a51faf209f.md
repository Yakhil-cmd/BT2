[Target: Shipit::User.create_from_github / #github_user=] Attacker triggers `create_from_github` via a genuine OAuth login where their GitHub `name` is set to a value colliding with `Shipit.committer_name` or another sentinel string used elsewhere for attribution (e.g., in commit `author`/`committer` resolution), then opens a PR so that `find_or_create_author_from_github_commit`'s `Merge-Requested-By:` commit-message regex (`/^Merge-Requested-By: ([\w\-.]+)$/`) is satisfied with a login string equal to a privileged existing `User`'s login, invoking `find_or_create_by_login!(match_info[1])` which trusts the commit message entirely (attacker-controlled, since they authored the commit). Precondition: attacker can push a commit with an arbitrary message to their own branch, and that branch is merged/considered by `MergeRequest` flows. Call sequence: attacker's commit message `Merge-Requested-By: privileged-login` -> `find_or_create_author_from_github_commit` -> `find_or_create_by_login!('privileged-login')` -> commit's author is attributed to the privileged `User` row, not the attacker. Binding that breaks: the author/committer `User` recorded for a commit == the GitHub identity that actually authored/pushed it, not an attacker-supplied commit-message claim. Scoped impact: Critical, misattribution of attacker-controlled commits to a privileged identity, potentially satisfying merge-approval logic gated on `current_user`/author identity. Proof idea: users_test-style test constructing a commit stub whose `commit.message` contains `Merge-Requested-By: <privileged-login>` while `commit.author`/`committer` are the attacker's own GitHub identity, calling `User.find_or_create_author_from_github_commit`, and asserting the returned `User` is the privileged row rather than the attacker's.
