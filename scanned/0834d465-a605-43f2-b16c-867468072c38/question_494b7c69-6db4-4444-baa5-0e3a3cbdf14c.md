In Handler#repository_name (app/models/shipit/webhooks/handlers/handler.rb) and StatusHandler, the org that authenticated the payload (repository_owner used in verify_signature) is never re-checked against payload.dig('repository','full_name') used by #stacks. Attacker action: POST /webhooks X-Github-Event=status with body {'repository':{'owner':{'login':'OrgA'},'full_name':'OrgB/other-repo'},'sha':'<real-sha-of-OrgB-commit>','state':'success',...} signed with OrgA's webhook_secret. Preconditions: OrgA and OrgB both configured with distinct webhook_secrets; OrgB/other-repo has a commit with that sha. Call sequence: verify_signature verifies against OrgA's secret and passes -> StatusHandler#process -> Handler#stacks -> Repository.from_github_repo_name('OrgB/other-repo') -> commit.statuses.create!. Binding: organization verifying the HMAC (OrgA) == organization owning the commit's repository (OrgB); breaks REPOSITORY_SCOPE. Scoped impact: Critical, cross-repository write - a forged status update (e.g., state:'success') can be injected onto OrgB's commit, potentially triggering an unauthorized deploy path once combined with other CI-gating logic. Proof idea: minitest asserting commit.statuses.count changes for OrgB's commit when payload signed only with OrgA's secret.
