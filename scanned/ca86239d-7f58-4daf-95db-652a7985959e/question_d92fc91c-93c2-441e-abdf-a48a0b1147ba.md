Target: `Shipit::Webhooks::Handlers::StatusHandler` params contract vs. `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb). Attacker action: attacker sends a `status` event body whose `repository` key is entirely absent or points at a repo different from `organization`/`repository.owner.login`; note `verify_signature` derives the signing app solely from `repository_owner` (`params.dig('repository','owner','login') || params.dig('organization','login')`), while `StatusHandler#process` never reads `repository` at all. Preconditions: attacker controls a repository under org X with the app installed; org X's `webhook_secret` will verify any body attacker constructs and signs via their own delivery mechanism for that org. Call sequence: `WebhooksController#create` -> `verify_signature` only checks organization-level HMAC, not per-repository scope -> `StatusHandler.call(params)` ignores `repository` entirely -> `Commit.where(sha:)` cross-stack write. Binding: `verify_signature`'s notion of 'authenticated organization' == the set of repositories `StatusHandler` is permitted to mutate; the handler enforces no such set. Scoped impact: Critical, org-level signature verification is necessary but not sufficient because the handler drops repository scoping downstream. Proof idea: minitest integration test signing a body for org X (whose secret is stubbed/known in test) that carries a sha belonging to a stack under org Y, asserting the request returns 200 and mutates org Y's `Commit`/`Status`.
