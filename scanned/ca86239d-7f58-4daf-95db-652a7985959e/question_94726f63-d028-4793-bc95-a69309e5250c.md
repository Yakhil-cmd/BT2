Target: `Shipit::Stack#trigger_continuous_delivery` (app/models/shipit/stack.rb) as the terminal sink of the cross-repo status bug. Attacker action: after forging the cross-sha status, wait for (or directly invoke, in test, to simulate the job runner) `ContinuousDeliveryJob#perform` on the victim stack. Preconditions: `stack.continuous_deployment?` true, `stack.cached_deploy_spec` present, `should_resume_continuous_delivery?`/`should_delay_continuous_delivery?` both false once the forged status flips the next commit to `deployable?`. Call sequence: `trigger_continuous_delivery` -> `next_commit_to_deploy` -> `deployable_commits` -> `Commit#deployable?` true because of the forged cross-repo status -> `trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)`. Binding: the organization whose webhook made `commit.deployable?` true == the organization that owns `stack`; it does not. Scoped impact: Critical, unauthorized deploy execution (which ultimately spawns `Command`/`PTY.spawn` with `GITHUB_TOKEN` for the victim's repo) triggered by an attacker who never touched the victim repository. Proof idea: minitest test asserting `Deploy.count` increases and `Shipit::PerformTaskJob` is enqueued for the victim stack after only a status webhook naming a different repository is posted.
