Target: `Shipit::Commit#blocked?` (app/models/shipit/commit.rb) consulted by `Commit#deployable?`. Attacker action: attacker forges a `success` status (via the same-sha technique) for a commit that is currently the `stack.blocking_statuses`-relevant blocking commit on an unrelated victim stack, clearing the block for all newer undeployed commits. Preconditions: victim stack has `blocking_statuses` configured and an undeployed commit whose predecessor is pending/failing and shares a sha with a commit reachable by the attacker's webhook. Call sequence: `StatusHandler#process` -> `create_status_from_github!` on the blocking `Commit` row -> `blocked?` now returns false for descendants -> `Stack#next_commit_to_deploy`/`deployable?` unblocks continuous delivery or the redeploy button. Binding: the repository whose webhook flipped the blocking commit's state == the repository that owns the blocking policy being bypassed; it does not. Scoped impact: Critical, safety gate (`blocking_statuses`) bypass causing an unauthorized deploy on a tenant's stack the attacker does not control. Proof idea: minitest test asserting `blocking_commit.blocked?` (or the descendant's `deployable?`) flips from false to true purely from a webhook whose `repository.full_name` never matches the victim stack.
