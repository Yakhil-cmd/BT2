Target: `Shipit::Api::CCMenuController#authenticate_api_client`. Attacker action: send `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` where `<token>` is a CCMenu token minted via `Shipit::CCMenuUrlController#fetch` for stack A, but `:stack_id` in the path names stack B. Preconditions: attacker obtained a CCMenu token for stack A (e.g. via a public/shared CCMenu dashboard URL for stack A) and knows the numeric/slug id of stack B. Call sequence: `authenticate_api_client` calls `ApiClient.authenticate(params[:token])` (no `stacks` scoping) -> `#stack` calls `Stack.from_param!(params[:stack_id])` directly on `Stack`, not on `stacks` (which would scope to `current_api_client.stack_id`). Binding: the stack an API request touches (`stack` resolved from `params[:stack_id]`) ∈ the stacks `current_api_client.stack_id` authorises. Scoped impact (Critical): unauthorized cross-stack read of stack B's deploy status/output via a token scoped only to stack A — this is a payload for one stack reading another stack's state. Whose stack: stack B, whose `deploys_and_rollbacks` and CI-status XML get returned to an attacker with no rights to it. Proof idea: functional test creating two `ApiClient`s each scoped to a different stack, requesting `show` for the other's `stack_id` with the wrong token, asserting `current_api_client.stack_id != stack.id` yet response is 200.
