Attacker action: broadcast PreStxOp A from Bitcoin address X (their own), then craft the StackStxOp's first input to spend PreStxOp A's second output but arrange for a *different*, unrelated PreStxOp B (also theirs, mapped from address Y) to be looked up via `pre_stx_op_map`/`burnchain_db.find_burnchain_op` if the map lookup key collides on `Txid`. Preconditions: attacker controls multiple PreStx ops in the same burn block, exploiting `pre_stx_op_map: &HashMap<Txid, PreStxOp>` keyed only by `Txid` (not also vout). Call sequence: `StackStxOp::get_sender_txid` returns `(txid, vout)` and only checks `*vout != 1`, not that it's actually output 1 of the *correct* PreStx tx; if two PreStx txids collide or the map is overwritten, `sender = &pre_stack_stx.output` could resolve to address Y while the Bitcoin coins actually spent belong to X. Equality that breaks: the Stacks address that owns/authorized the lock (`op.sender`) == the address whose Bitcoin UTXO was actually consumed as the StackStx op's input. Impact: Critical – STX locked under `sender = Y` when Y's Bitcoin output wasn't truly spent, meaning Y's STX gets locked without Y's authorization (unbacked lock / theft of locking rights). Proof idea: Rust integration test in `stackslib/src/burnchains/tests/db.rs` style constructing two PreStxOps with colliding `Txid` values inserted into `pre_stx_op_map`, then a StackStxOp spending vout=1 of the first, and asserting `op.sender` matches the txid-associated PreStxOp's `output`, not a spoofed one.
