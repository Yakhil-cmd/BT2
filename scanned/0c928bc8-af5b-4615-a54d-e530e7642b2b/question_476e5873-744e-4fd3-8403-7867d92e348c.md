`WebhooksController#event` reads `request.headers.fetch('X-Github-Event')` and `#drop_unhandled_event`/`Shipit::Webhooks.for_event(event)` gate which handler class runs, but nothing ties the `X-Github-Event` header to the shape of the JSON body beyond each handler's `ExplicitParameters::Parameters` schema (`Handler.params`). Can an attacker signed correctly for organization A (whose repo genuinely triggers, say, `push` events) instead set `X-Github-Event: membership` while keeping a `push`-shaped body but adding the minimal fields `MembershipHandler`'s `params` block requires (`action`, `team`, `organization`, `member`), all with attacker-chosen values for a DIFFERENT org's team, since the signature only covers raw bytes and not the semantic event type binding? Binding: the `X-Github-Event` header (selecting the handler) together with the verified `repository_owner`/`organization.login` must jointly authorize the specific mutation the chosen handler performs; here the handler choice is attacker-controlled independent of what org A is actually permitted to trigger. Impact: Critical, attacker uses org A's legitimately signed webhook capability to invoke an arbitrary handler (e.g. team membership mutation) unrelated to org A's own repository. Proof: minitest test signing a body (satisfying `MembershipHandler.params`) with org A's `webhook_secret`, setting header `X-Github-Event: membership`, with `team`/`organization` fields naming org B, asserting `MembershipHandler#process` mutated org B's team despite org A being the only verified signer.
