Target: Shipit::User.find_or_create_by_login! (keyed on login string) versus Shipit::User.find_or_create_from_github (keyed on github_id). Attacker action: attacker creates a GitHub account with the login 'alice' after the real 'alice' (whose Shipit `User` row already exists with a fixed `github_id`) renames her account, then attacker signs in through Shipit's OAuth callback. Preconditions: a `Shipit::User` row already exists with login: 'alice' created earlier by `find_or_create_by_login!` (e.g. from a pull_request.rb `github_pull_request.user.login`), and the real alice has since renamed. Call sequence: attacker's OAuth callback -> `sign_in_github(auth)` -> `User.find_or_create_from_github(auth.extra.raw_info)` -> `find_by(github_id: attacker.github_id)` finds nothing -> `create_from_github` creates a NEW row with attacker's github_id but the same eventual login 'alice' once refreshed, potentially colliding with historical commit/PR authorship tied to the old login-keyed row. Binding broken: User row resolved by github_id == User row resolved by login for the same handle. Impact: Critical - identity confusion where an attacker's session resolves to (or is conflated with) a `User` row carrying another account's commit/PR authorship and any associated privileges.
