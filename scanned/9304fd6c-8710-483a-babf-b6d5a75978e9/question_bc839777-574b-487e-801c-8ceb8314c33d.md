Target: Shipit::EnvironmentVariables#interpolate ENV fallback vs Shipit::Command::BASE_ENV. Attacker action: references an unset variable name in a deploy step, e.g. '$RUBYOPT' or '$BUNDLE_GEMFILE', that is unset in @env (task/stack env) but present in Shipit's own unbundled process ENV. Preconditions: BASE_ENV is derived from Bundler.unbundled_env/clean_env at class-load time and reflects the Shipit master process's own environment. Call sequence: Command#interpolate_environment_variables -> EnvironmentVariables#interpolate -> @env.fetch(variable) { ENV[variable] }, where ENV here is the Shipit process's Kernel ENV, not BASE_ENV. Binding: a variable substituted into a shell step == a value the operator explicitly configured for that stack/task, never a value implicitly present in Shipit's own master-process environment. Scoped impact: Critical, exfiltration of a Shipit-process-only secret (e.g. an internal RUBYOPT, AWS credential env var set on the Shipit host) into task output visible to the PR author. Proof idea: minitest setting ENV['RUBYOPT']='-e-leak' in test, building Command with env excluding it and a step '$RUBYOPT', asserting the interpolated argument contains the process ENV value.
