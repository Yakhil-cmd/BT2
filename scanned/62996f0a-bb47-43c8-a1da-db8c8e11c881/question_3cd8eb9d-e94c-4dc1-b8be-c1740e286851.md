Target: `stake-update` in pox-5.clar, `(asserts! (>= (get unlocked (stx-account tx-sender)) amount-increase) ERR_INSUFFICIENT_STX)`. Attacker action: calls `stake-update` with `amount-increase` equal to exactly `(get unlocked (stx-account tx-sender))` at read time, then in the same atomic transaction has that unlocked balance simultaneously reduced by another effect ordered before the lock update inside the same transaction's contract-call chain (e.g. a prior `stx-transfer?` inside a wrapper contract that calls `stake-update` after moving funds out), so the check passes on a stale read. Preconditions: attacker's own wrapper contract sequences an `stx-transfer?` out of `tx-sender`'s account followed by `contract-call? .pox-5 stake-update ...` in one transaction. Call sequence: wrapper transfers away STX -> calls `stake-update` -> `(stx-account tx-sender)` is re-read at that call point (Clarity re-reads current state per call, so this should already reflect the transfer) -> the check should correctly fail; probe is whether `pox_lock_update_v5`'s own balance check `total_amount < new_total_locked` at the Rust layer is what actually enforces sufficiency, or whether it trusts the Clarity-side check alone and could be bypassed by a race between the Clarity assertion and the Rust lock application within the same call. Equality that must hold: `new_total_locked` applied by `pox_lock_update_v5` == an amount the account's `amount_unlocked() + amount_locked()` can cover at the moment the Rust-side lock is actually written, not just at the Clarity assertion's read time. Impact: Critical, if the two checks can be split by an intervening transfer, an unbacked lock increase is created. Proof idea: Rust integration test with a wrapper contract that transfers STX out then calls `stake-update` in the same transaction and asserts `pox_lock_update_v5` returns `LockingError::PoxInsufficientBalance` rather than succeeding.
