Target: `stake` in pox-5.clar and `handle_lockup_pox_v5`/`pox_lock_v5` in pox-locking/src/pox_5.rs. Attacker action: an unprivileged staker deploys a `signer-manager-trait` contract whose `validate-stake!` always returns `(ok true)`, then calls `stake` with `amount-ustx` equal to their full `total-balance` (locked+unlocked) rather than only `unlocked`, on a fresh account with an existing pox-5 lock from a prior bond membership set up via direct state corruption test helpers. Preconditions: staker has some `locked` STX from an unrelated source plus `unlocked` STX, no active `staker-info`. Call sequence: `stake` computes `total-balance = (+ locked unlocked)`, asserts `total-balance >= amount-ustx`, returns `(ok {amount-ustx, unlock-burn-height,...})`; `parse_pox_stake_result` extracts `amount_ustx`; `handle_lockup_pox_v5` sees `already_locked=false` (if the locked STX wasn't from pox-5) and calls `pox_lock_v5` which calls `snapshot.can_transfer(lock_amount)` checking only `amount_unlocked`. Equality that breaks: contract-validated `amount-ustx <= total-balance (locked+unlocked)` != `pox_lock_v5`'s required `lock_amount <= amount_unlocked`, so a request within the contract's total-balance check but exceeding spendable balance should be rejected by `can_transfer`, but confirm no path lets a request bypass this into `PoxInsufficientBalance` being swallowed as a no-op instead of properly failing/reverting the whole tx. Scoped impact: Critical — theft or freezing of the staker's own already-locked STX if a lock is silently double counted while returning success to the caller. Proof idea: Rust integration test on booted chainstate locking `amount_unlocked=100_000`, existing non-pox5 `locked=900_000`, calling `stake` with `amount-ustx=500_000` and asserting the resulting `STXBalance.amount_locked()` equals exactly the contract-validated `amount-ustx`, never more than `amount_unlocked` at the time of call.
