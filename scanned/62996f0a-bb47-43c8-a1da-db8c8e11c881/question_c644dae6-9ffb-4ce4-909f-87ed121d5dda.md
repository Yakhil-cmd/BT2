Target: `verify-signer-key-grant` called from both `register-signer` and `stake`/`stake-update`. Attacker action: deploys their own `signer-manager` contract, obtains a `signer-key` grant via `grant-signer-key`, registers it, then lets the grant's authorizing signature (`signer-sig`/`auth-id`) be reused by a *different* signer-manager contract instance to register the same key under two different `signer` principals before the first `register-signer` call marks the grant consumed. Preconditions: attacker controls two signer-manager contracts and calls `register-self` (or the raw `grant-signer-key`+`register-signer` pair) on both with the same `signer-key`/`auth-id`/`signer-sig`. Call sequence: `grant-signer-key signer-key current-contract auth-id signer-sig` on contract A succeeds; if the grant isn't marked used-and-scoped to contract A before contract B calls `grant-signer-key` with the same signature, both could register the same `signer-key`. Equality that must hold: each `signer-key` grant authorizes registration under exactly one `signer` principal, once (AUTHORITY -- every stacking action must be one the signer actually signed for exactly those parameters). Impact: High, letting an attacker claim signing weight for a key without the true holder's fresh authorization for their own contract, though not the actual signer's private key. Proof idea: Rust/Clarity test calling `grant-signer-key` + `register-signer` for the same `signer-key`/`signer-sig` from two distinct contract principals and asserting the second registration fails with a 'grant already consumed' style error.
