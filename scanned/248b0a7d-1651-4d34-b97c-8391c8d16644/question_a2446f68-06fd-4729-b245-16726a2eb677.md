Target: Shipit::Webhooks::Handlers::MembershipHandler#process, action == 'added' branch, and Shipit::Team#add_member. Attacker action: attacker sends a validly-signed membership webhook for their own organization, with action 'added', team pointing to a Team row whose organization matches the attacker's own org but whose github_id happens to also be listed by handle collision (organization+slug) with Shipit.github_teams via Team.find_or_create_by_handle elsewhere in the app (e.g. Api::BaseController or elsewhere calling find_or_create_by_handle with the same 'organization/slug' string used for both an authorization team and a legitimate but differently-scoped team). Call sequence: verify_signature (attacker's own secret) -> find_or_create_team! -> Team.find_or_create_by!(github_id: params.team.id) creates a NEW row scoped to organization from payload (their own) with a different github_id than the trusted team, so no collision here -- confirms find_or_create_team! is keyed on github_id not slug, so this specific handle-collision path does not cross-contaminate. Binding: a Team row's (organization, github_id) as created by MembershipHandler == the (organization, github_id) of the trusted Shipit.github_teams entry are correctly kept distinct by github_id keying UNLESS the github_id itself collides (see question above), so this test should assert NO false positive occurs for slug collisions alone. Impact: High (negative control validating scope of the vulnerability), used to confirm the exploit requires github_id collision specifically, not slug collision. Proof idea: minitest test with two orgs having identically-slugged teams but distinct github_ids, asserting no cross-team membership occurs.
