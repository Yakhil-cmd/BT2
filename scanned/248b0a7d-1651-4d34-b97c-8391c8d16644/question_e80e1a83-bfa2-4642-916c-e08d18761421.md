Target: Shipit::Webhooks::Handlers::Handler#self.call and Shipit::Webhooks.for_event(event) dispatch combined with WebhooksController#create. Attacker action: attacker sends POST /webhooks with X-Github-Event: membership and a body containing multiple team/member permutations is not applicable (single object), but attacker can send an X-Hub-Signature that is valid for their own org while setting organization.login to a STRING that differs from any configured secret's org label (e.g. mixed case 'Evil-Org' vs config key 'evil-org'). Preconditions: Shipit.github_app_config downcases the organization key (github_app.rb#github_app_config: github_config.deep_transform_keys(&:downcase), organization.downcase.to_sym) for verify_signature's repository_owner lookup, but MembershipHandler stores params.organization.login verbatim (not downcased) into Team#organization on create. Call sequence: verify_signature succeeds using the downcased org key -> find_or_create_team! creates Team with organization = the exact-case string from payload -> later authorization/lookup code (Team.find_or_create_by_handle downcases organization on split) may never match this row again, or worse, a second webhook with different casing for the same real org could create a SECOND Team row with a different github_id mapping if github_id also differs, fragmenting authorization state. Binding: the organization string stored on a Team row == the canonical organization key Shipit uses elsewhere (downcased) for that same real-world org -- breaks due to inconsistent casing normalization between verify_signature's lookup and MembershipHandler's write. Impact: High, authorization-state integrity bug that can be leveraged toward the Critical escalation paths above by creating ambiguous team records. Proof idea: minitest test posting two membership webhooks with organization.login differing only in case but same team.id, asserting only one Team row exists and its organization field matches the canonical configured key.
