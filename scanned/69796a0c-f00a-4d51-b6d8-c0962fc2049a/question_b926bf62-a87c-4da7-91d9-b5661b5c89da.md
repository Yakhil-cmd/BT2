Shipit::Team.find_or_create_by!(github_id: params.team.id) trusts the attacker-supplied integer params.team.id as the sole uniqueness key, with no validation that this id was ever returned by GitHub for the signing organization's teams. Attacker action: POST /webhooks membership action 'added' with team.id set to a small/guessable integer matching a Shipit.github_teams entry, team.slug/name/url set to arbitrary attacker-chosen strings, organization.login set to the attacker's own signing org, member.login set to attacker's login, signed with attacker's genuine webhook_secret. Preconditions: no Team row currently exists for that github_id. Call sequence: verify_signature passes for attacker's org -> find_or_create_team! creates Team(github_id: <colliding id>, organization: attacker_org, name/slug from payload) -> team.add_member(attacker_user). Binding: the github_id written into a new Team row and consumed later by Shipit.github_teams.map(&:id) comparisons must have been confirmed (via an authenticated GitHub API call, not payload trust) to belong to the organization that signed the webhook. Scoped impact: Critical - attacker manufactures a Team row that numerically satisfies a Shipit.github_teams entry and grants themself membership, an authorization escalation with no real GitHub team involved. Proof idea: minitest stubbing Shipit.github_teams to include an id, posting a fresh membership webhook from a distinct verified org with team.id equal to that id, and asserting the resulting Team#organization is untrusted payload data while User#authorized? nonetheless returns true.
