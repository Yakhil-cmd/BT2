Shipit::Team.github_team=(github_team) setter, invoked inside find_or_create_team!'s creation block as `team.github_team = params.team`, assigns team.name, team.slug, team.api_url, and team.github_id directly from the untrusted params.team OpenStruct-like object, and Team#handle later renders "#{organization}/#{slug}" used for display/authorization messaging (Authentication#force_github_authentication's team_list). Attacker action: POST /webhooks membership 'added' with team.slug containing crafted markup/format-string-like content (e.g. embedded '#{...}' text or HTML) while team.id is a fresh github_id not colliding with any existing team, organization.login set to attacker's own org. Preconditions: none beyond a valid signature for attacker's org. Call sequence: find_or_create_team! -> github_team= -> Team#slug stores raw attacker string -> any later authorization-denied page renders team_handles.map(&:handle) including this slug. Binding: the slug value rendered on the 403 'You must be a member of ... ' page must equal a slug GitHub actually assigned that team, not attacker-chosen text. Scoped impact: High - if this Team's github_id happens to be in Shipit.github_teams, arbitrary text is injected into the authentication-denied page rendered to every unauthenticated visitor (stored content injection), though this only manifests if the id is also configured in Shipit.github_teams. Proof idea: minitest posting a membership webhook with an unconfigured team.id and a crafted slug, then confirming the created Team#slug equals the raw payload string with no sanitization, and checking whether that Team's id is ever compared against Shipit.github_teams before being trusted for display.
