Target: `Shipit::Api::BaseController#require_permission!` versus `Shipit::Api::CCMenuController`'s class-level `require_permission :read, :stack`. Attacker action: attacker holds any token whose `permissions` array happens to include the literal string `'read:stack'` but whose `stack_id` was set at creation time to a stack in repository X; attacker requests `cc.xml` for a stack in repository Y with `write:stack` implications irrelevant here since `#show` is read-only, but demonstrates that `check_permissions!` never receives or compares the *target* stack id, only the operation/scope pair. Preconditions: `ApiClient` A has `stack_id: X`, `permissions: ['read:stack']`; stack Y exists in a different repository. Call sequence: `before_action :authenticate_api_client` then the `require_permission` before_action calls `require_permission!(:read, :stack)` -> `current_api_client.check_permissions!('read','stack')`, which only checks the operation string, never the actual `stack` instance resolved later in `#show`; the stack-scope enforcement that exists (`#stacks` filtering by `current_api_client.stack_id`) is bypassed as shown in scenario 1 because `CCMenuController#stack` doesn't call `#stacks`. Binding: the permission checked == the permission the action needs (including target-object scope), and the stack touched ∈ stacks authorised by `current_api_client.stack_id`. Scoped impact: Critical, structurally the permission-check layer and the stack-resolution layer are decoupled, so a stack-scoped, read-only token for repository X fully reads repository Y's build state. Proof idea: minitest test with `ApiClient(stack_id: X, permissions: ['read:stack'])` requesting `cc.xml?stack_id=Y&token=...` and asserting Y's data is returned despite the client never having been granted access to Y.
