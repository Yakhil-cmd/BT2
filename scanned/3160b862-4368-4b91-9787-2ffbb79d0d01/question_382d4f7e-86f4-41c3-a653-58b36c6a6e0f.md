Target: `Shipit::Api::BaseController#identify_user` and `#require_permission!`. Attacker action: an unprivileged internet user who does not hold a Shipit session or `ApiClient` token still cannot call the API without an `Authorization` header (blocked by `authenticate_api_client`); but assume a legitimate but *unprivileged* `ApiClient` token exists (e.g. a `read:stack`-only client). The attacker sends `POST /api/stacks/:id/tasks` (or another mutating endpoint requiring `write:stack`) with `Authorization` set to that read-only client's basic-auth token AND header `X-Shipit-User: <admin-login>`. Preconditions: a user named `<admin-login>` exists in the `users` table; the `ApiClient` used lacks `write:stack`. Call sequence: `authenticate_api_client` succeeds using the low-privilege client; `#current_user` calls `#identify_user`, which does `User.where('lower(login) = ?', user_login.downcase).first` purely from the untrusted `X-Shipit-User` header and returns the admin `User` row for attribution/auditing (e.g. task `user_id`), while `#require_permission!` only calls `current_api_client.check_permissions!`, never checking `current_user`'s actual authorization. Binding: the permission checked == the permission the action needs, and additionally IDENTITY BINDING requires `current_user` == the GitHub identity that authenticated this request -- here `current_user` is spoofed via header while the authenticating identity is only the API client. Scoped impact: Critical, an unprivileged token holder can attribute a deploy/task/comment to an arbitrary victim user (identity spoofing) even though `check_permissions!` still gates the raw operation type. Proof idea: minitest test sending a request with a valid low-privilege client's basic auth and an `X-Shipit-User` header naming another user, asserting the created record's `user`/`author` association equals the spoofed identity rather than nobody/anonymous.
