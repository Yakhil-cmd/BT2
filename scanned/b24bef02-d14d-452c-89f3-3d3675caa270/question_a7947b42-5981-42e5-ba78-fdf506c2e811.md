Target: Shipit::Webhooks::Handlers::StatusHandler#process and Shipit::Commit#create_status_from_github!. Attacker action: attacker creates an empty-tree commit (sha computed identically regardless of repository, e.g. via `git commit-tree` with no parent) in a repository they own, then POSTs a `status` webhook (`X-Github-Event: status`, body `{sha: <shared_sha>, state: 'success', context: 'ci/travis', branches: [...]}`, repository block naming the attacker's own repo) signed with that repo's own valid `webhook_secret`. Preconditions: a victim stack already tracks a `Commit` row with that same `sha` (e.g. an initial empty commit shared across many forks). Call sequence: `WebhooksController#create` -> `GithubHook#verify_signature` succeeds for attacker's org -> `StatusHandler.new(params).process` -> `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` iterates every matching row regardless of stack. Binding that breaks: the organization whose `webhook_secret` verified the body == the organization owning the `Commit`/`Stack` the handler mutates -- here they differ. Scoped impact: Critical, cross-repository write -- a `Status` is created on a victim tenant's `Commit` from a payload authenticated only for the attacker's own repository. Proof idea: minitest ActionDispatch::IntegrationTest posting a signed status payload for org A while asserting a `Shipit::Status` row is created against a `Commit` belonging to stack owned by org B.
