Target: Shipit::Commit#deployable? and Shipit::Stack#trigger_continuous_delivery. Attacker action: attacker pushes the shared/empty-tree-sha commit to their own repo and POSTs a `status` webhook with `state: 'success'` for that sha, signed by their own repo's `webhook_secret`. Preconditions: victim stack has `continuous_deployment: true`, the matching `Commit` row is `next_commit_to_deploy`, and previously had no successful status (`success? == false`). Call sequence: `StatusHandler#process` -> `commit.create_status_from_github!` -> `add_status` -> commit's `state` flips to `success` -> `ProcessMergeRequestsJob`/`ContinuousDeliveryJob` observes `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) returning true -> `Stack#trigger_continuous_delivery` -> `trigger_deploy`. Binding: the repository named in the verified webhook payload == the repository whose stack's continuous delivery is triggered -- broken. Scoped impact: Critical, unauthorized deploy of the victim org's code that never actually passed their own CI. Proof idea: minitest asserting `assert_difference('Deploy.count')` after posting the cross-tenant status payload against a stack with `continuous_deployment: true`.
