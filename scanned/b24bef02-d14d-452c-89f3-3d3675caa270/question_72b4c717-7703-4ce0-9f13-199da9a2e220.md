Shipit::Api::MergeRequestsController (the file this vulnerability is filed against) exposes `#create`/`#refresh` actions gated by `require_permission :merge, :stack`, but the merge outcome itself, once queued, depends entirely on `MergeRequest#all_status_checks_passed?` which is corruptible via the unauthenticated cross-repo `StatusHandler` path with no API token needed at all. Attacker action: attacker (no API token, no Shipit account) uses only the public GitHub webhook surface to flip a queued MergeRequest's status checks green after a legitimate maintainer already called `Api::MergeRequestsController#create` to enqueue it normally. Preconditions: MergeRequest exists in `pending` state (created by a legitimate authorized call), lacking real passing CI. Call sequence: legitimate `request_merge!` queues MergeRequest -> attacker's cross-repo status webhook -> `ProcessMergeRequestsJob` picks it up on its normal schedule -> merges. Binding: `require_permission!`'s check on `Api::MergeRequestsController#create` must gate the *entire* merge decision, but the actual gating predicate `all_status_checks_passed?` is reachable and forgeable via a completely unauthenticated path (`StatusHandler#process`) that bypasses `Api::BaseController` authorization altogether - the API authorization and the true merge authorization are not the same boundary. Scoped impact: Critical, an authorization control on the merge-request API is rendered moot because the actual merge trigger condition can be forged without any API credential. Proof idea: minitest that creates a MergeRequest through the legitimate authorized controller action, then, without any `ApiClient` token, posts the cross-repo status webhook and asserts `ProcessMergeRequestsJob.perform_now` merges it.
