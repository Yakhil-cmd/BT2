Shipit::Status.replicate_from_github! is `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)`, using `commit.stack_id` derived purely from whichever `Commit` row matched the unscoped sha lookup - never validated against the webhook's own `repository.full_name`. Attacker action: attacker crafts a `context` value that spoofs a security-relevant CI check name (e.g. `security/code-review`, `soc/compliance`) required by the victim's `ci.blocking` or `merge.require` deploy-spec config, and forges it success via the cross-repo webhook. Preconditions: victim's `shipit.yml` on the target branch lists that exact context under `ci.blocking` or `merge.require`. Call sequence: `create_status_from_github!` writes a `Status` with the victim-recognized context string -> `Stack#blocking_statuses`/`DeploySpec#merge_request_required_statuses` matching by `context` string treats it as satisfied. Binding: the CI provider that is authorized to emit the `context` string configured in the victim's `shipit.yml` must equal the entity that actually posted the status (attacker's unrelated repo) - it does not, because `context` is attacker-supplied free text with no provenance check. Scoped impact: Critical, attacker names their forged status to exactly match a security-critical named check and satisfies it without ever running that check. Proof idea: minitest configuring `ci.blocking: ['soc/compliance']` in a stack's cached_deploy_spec, forging a `context: 'soc/compliance', state: 'success'` status via the cross-repo webhook, asserting `stack.blocking_statuses` no longer includes it and `commit.deployable?` becomes true.
