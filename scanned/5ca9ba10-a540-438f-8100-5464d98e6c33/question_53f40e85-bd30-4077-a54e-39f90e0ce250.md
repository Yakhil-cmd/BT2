[Function: resolve-or-create, mask-update] Attacker A calls `market.market.borrow` for asset-id X with `account` = victim B, causing `resolve-or-create` to `create` B's registry row and `mask-update` to set bit X in B's `mask` for a debt asset A chose, not B. Sequence: block N, A borrows on behalf of B for asset X (if the entrypoint's auth check does not block a caller from naming an arbitrary `account` for a genuinely-collateralized borrow using A's own collateral routed to B); block N+1, B calls `market.get-position` and finds a pre-set `mask` bit for asset X. Invariant: SANCTIONED WRITES ONLY - only liquidation and repayment are meant to write another principal's ledger; an unsolicited borrow-mask write is not one of them. B loses: the egroup/`get-egroup` resolution B is placed into on first real use no longer starts from `mask: u0`, changing B's LTV/liquidation curve group. Impact: temporary freezing (B's first legitimate deposit resolves to an egroup B never selected). Proof: simnet test comparing B's `get-egroup` mask before/after A's call to a same-account-arg entrypoint.
