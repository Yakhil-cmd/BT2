[Function: collateral-add, account] Attacker A calls `market-vault.collateral-add` (or the wrapping `market` deposit entrypoint) with `account` = victim B and a 1-unit amount of a legitimate `<ft-trait>` token A supplies from A's own wallet, at block N. This forces `resolve-or-create` to allocate B's `id` and set B's `mask` bit for whatever `asset-id` A chose, before B has ever touched the protocol. Block N+1: B calls `collateral-add` for a *different* asset expecting a fresh `mask: u0` baseline; instead B's egroup resolution (`get-egroup` on the merged mask) now includes the asset A planted. Invariant: NON-INTERFERENCE. B loses: B is placed in an egroup with different LTV/liquidation parameters than B would have entered on a clean first deposit, for as long as A's planted collateral bit remains set (until B explicitly removes that asset). Impact: temporary freezing of B's intended collateral configuration/borrowing power. Proof: two-account test comparing B's `get-egroup` result with and without A's prior `collateral-add` call naming B.
