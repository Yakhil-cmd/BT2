Target: `Shipit::Team#add_member` uniqueness guard (`members.append(member) unless members.include?(member)`). Attacker action: send a membership webhook whose `team.id` matches a privileged team but whose `member.login` is deliberately the login of an *existing legitimate* Shipit user who is not currently on that team, sourced from a public GitHub profile the attacker can see (no secret needed — logins are public). Preconditions: target login already exists as a `Shipit::User` from unrelated activity (e.g., authored a commit). Call sequence: `User.find_or_create_by_login!` finds the existing user by `login`; `team.add_member` links them to the privileged team without their consent or any GitHub-side confirmation. Binding: a `Membership` row for a team in `Shipit.github_teams` == a membership GitHub actually reports for that team; here it fails not just for the attacker but for an innocent third party who never asked to be authorized. Impact: Critical, authentication bypass affecting a third party's account (privilege granted to someone who never consented, widening blast radius and audit-trail confusion). Proof idea: minitest asserting `Membership.exists?(team: privileged, user: unsuspecting_user)` after the forged webhook, and that `unsuspecting_user.authorized?` becomes true though no real GitHub team change occurred.
