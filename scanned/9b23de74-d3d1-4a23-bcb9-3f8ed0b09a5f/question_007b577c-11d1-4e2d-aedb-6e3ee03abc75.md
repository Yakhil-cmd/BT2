Target: Shipit::User.find_or_create_from_github keyed on github_user.id versus Shipit::User.find_or_create_by_login! keyed on login, invoked from Shipit::PullRequest#github_pull_request=. Attacker action: attacker opens a pull request from a fork where the PR author's GitHub login string is crafted to collide with a login already bound to a different github_id in Shipit's User table (e.g. after a legitimate user renamed their GitHub account and a new GitHub user claimed the vacated login). Preconditions: an existing Shipit::User row has login: 'bob' and github_id: 100 (created originally via OAuth). The attacker's GitHub account has github_id: 200 and has since claimed login 'bob'. Call sequence: a webhook-driven PullRequest#github_pull_request= assignment runs self.user = User.find_or_create_by_login!(github_pull_request.user.login) which matches the existing login-keyed row (github_id 100, a different real person) and attributes the new PR to that pre-existing User row instead of creating/matching github_id 200. Binding: the User row an action is attributed to == the GitHub account (github_id) that actually performed it; find_or_create_by_login! breaks this by keying on a mutable login string. Scoped impact: Critical - PR authorship/identity misattribution lets an attacker's pull request appear as authored by another (possibly privileged) Shipit::User row, which can affect merge_request.requested_by trust decisions downstream in MergeStatusController/MergeRequest flows. Proof idea: ActiveSupport::TestCase creating a User with login: 'bob', github_id: 100, then calling PullRequest#github_pull_request= with a stub github_pull_request.user.login == 'bob' but representing a different real github_id, asserting the PullRequest#user resolves to the pre-existing (wrong) User row rather than a new one keyed on the real github_id.
