Target: GitHubApp#verify_webhook_signature algorithm gate. Attacker action: POST /webhooks with X-Github-Event: pull_request, action 'edited', a valid org name that DOES have a webhook_secret, and an X-Hub-Signature header of the form 'sha256=<anything>' (GitHub's newer default) instead of 'sha1=<hmac>'. Preconditions: org 'shopify' has webhook_secret configured; a tracked PullRequest exists for the named repository. Call sequence: verify_webhook_signature splits signature on '=', checks `return false unless algorithm == 'sha1'`, returning false and yielding head(422) - so this path is safe from bypass. However the counter-scenario is: attacker crafts algorithm='sha1' with a signature computed over a DIFFERENT body via a proxy that double-decodes; since signature is verified over request.raw_post but EditedHandler receives JSON.parse(request.raw_post) re-parsed independently in #create, any JSON key not covered by the byte-exact HMAC (e.g., duplicate JSON keys where Ruby's JSON.parse keeps the last occurrence) can diverge from what was signed. Binding broken: the bytes verified by HMAC must equal params.dig('repository','full_name') actually used, but duplicate-key JSON allows the signed first repository.full_name to differ from the parsed last repository.full_name. Scoped impact: Critical - signature covers one repository, handler writes another. Proof idea: minitest computing a valid sha1 HMAC over a payload with repository.full_name appearing twice (first entry = attacker's own repo, second = victim's), posting it, and asserting EditedHandler targets the victim repository despite the signature nominally matching the whole raw body.
