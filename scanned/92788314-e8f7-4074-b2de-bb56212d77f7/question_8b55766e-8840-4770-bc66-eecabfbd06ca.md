Target: lib/shipit/simple_message_verifier.rb SimpleMessageVerifier used wherever session/API tokens are generated (e.g. app/controllers/shipit/api/base_controller.rb token param verification) versus WebhooksController's independent HMAC verify_webhook_signature path. Attacker action: send an HTTP GET to a stack/task/commit-reading endpoint supplying a 'token' query param that is a raw, non-message-verifier string (since SimpleMessageVerifier's #decode returns data as-is and #encode is data.to_s, generate/verify round-trips are effectively pass-through for already-signed strings) hoping the verifier's ToS serializer accepts an unsigned/malformed payload without raising InvalidSignature. Preconditions: any endpoint using SimpleMessageVerifier#verified/#valid_message? with a token param taken from request params rather than a session. Call sequence: ActiveSupport::MessageVerifier#verify parses 'data--digest' format; SimpleMessageVerifier only overrides encode/decode/serializer (ToS), not the digest-comparison logic, so binding depends entirely on whether the calling controller checks the digest before trusting the decoded value. Binding: the actor authenticated by SimpleMessageVerifier's digest check (IDENTITY_BINDING) == the ApiClient/user identity the calling controller treats as current_user/session[:user_id] after decode; if a caller uses #decode-adjacent helpers without calling verify, no digest is checked. Impact: Critical, authentication bypass if any call site invokes SimpleMessageVerifier#generate/#decode-only paths (bypassing #verify's HMAC check) to accept attacker-supplied unsigned tokens as authenticated identity. Proof idea: minitest test instantiating SimpleMessageVerifier with a known secret, crafting an arbitrary unsigned string, and asserting that any controller helper relying on it raises ActiveSupport::MessageVerifier::InvalidSignature for tampered/unsigned input rather than silently decoding it.
