Attacker action: construct PreStxOp with Bitcoin keys controlled by A, then StackStxOp spending that PreStxOp's second output but whose Stacks-address resolution (external to this file, in `burnchain.rs`) yields address B. Precondition: attacker controls A's Bitcoin keys; B is any other Stacks address (including a victim's). Call sequence: `StackStxOp::get_sender_txid` only checks `vout==1`, never checks that the resolved Stacks address equals the PreStxOp's own signer; `StackStxOp::parse_from_tx` trusts the externally-supplied `sender: &StacksAddress` parameter without cross-checking against the PreStxOp originator. Equality broken: identity equality stated in scope — STX locked == STX owned by the address the op's first Bitcoin input maps to, and only with that address's committed parameters; if `sender` can diverge from the actual Bitcoin-input-derived owner, this is violated directly. Impact: Critical — locking or crediting reward-slot weight against a victim's STX without their authorisation. Whose funds: victim B's STX. Proof idea: integration/unit test in the burnchain-op parsing pipeline (not just this file) asserting that the `sender` field ultimately stored on the applied `StackStxOp` is cryptographically tied to the same key that signed the PreStxOp's Bitcoin input, and constructing a case where it is not, verifying whether the op is still applied.
