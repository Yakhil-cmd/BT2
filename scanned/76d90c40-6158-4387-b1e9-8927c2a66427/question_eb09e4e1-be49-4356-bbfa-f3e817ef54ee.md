[stack_stx.rs] Can a `StackStxOp` with `signer_key == None` still lock STX and be treated as signer-authorised? Attacker submits a Bitcoin `StackStxOp` transaction whose `data` payload is exactly 17-49 bytes so `StackStxOp::parse_data` sets `signer_key: None`. Precondition: valid `PreStxOp`/`StackStxOp` pairing with correct vout=1 linkage. Call sequence: `parse_from_tx` returns `Ok(StackStxOp{signer_key: None, ...})`; `check()` only validates `signer_key` `if let Some(signer_key) = &self.signer_key` — a `None` skips validation entirely; the op is applied and stacked_ustx is locked without any signer-key binding. Equality broken: AUTHORITY — every stacking action == one the staker's signer signed for exactly those parameters; here no signer key exists to check against reward-set authorisation. Impact: Critical — value locked/participating in reward set without a verifiable signer, letting the same uSTX be claimed for a reward slot with no `signer_key` accountability (double-counting/weight-without-signature). Whose funds: the sender's locked STX and reward-set integrity. Proof idea: integration test asserting `op.signer_key.is_none()` yet `check()` returns `Ok(())`, then following through pox-locking application to confirm the lock is applied with no signer binding recorded.
