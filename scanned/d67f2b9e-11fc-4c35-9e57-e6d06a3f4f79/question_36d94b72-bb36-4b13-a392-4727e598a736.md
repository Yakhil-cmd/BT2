Target: Shipit::User.find_or_create_by_login! vs Shipit::User.find_or_create_from_github (app/models/shipit/user.rb). Attacker then renames their GitHub login to a NEW value and signs in through Shipit::GithubAuthenticationController#callback with that renamed account; a separate, unrelated GitHub user later registers the attacker's OLD login and completes OAuth. Preconditions: find_or_create_by_login! never records github_id at creation reliably tied to the same identity as find_or_create_from_github's github_id key; both methods can independently create rows for what a human treats as 'the same login'. Call sequence: PR-created User row (login-keyed, no github_id) sits in the DB -> new GitHub owner of the recycled login completes OAuth -> User.find_or_create_from_github looks up by github_id only and creates a SECOND row, OR under a schema variant that also indexes on login, collides with and inherits the PR-created row's associations (commit authorship, task history) tied to the original attacker's contributions. Binding that breaks: the Shipit::User row that session[:user_id] names after this OAuth exchange == the same identity that authored the earlier PR-linked User row keyed by login. Scoped impact: Critical, cross-identity authorization confusion - a new GitHub account inherits authorship/team state attributed to a different GitHub account via login reuse. Proof idea: ActiveSupport::TestCase that calls User.find_or_create_by_login!('renamed_login') to create a bare user, then simulates a real OAuth callback for a different github_id but the same current login string, and asserts whether the two resolve to the SAME or DIFFERENT Shipit::User rows, and whether current_user after OAuth carries over any state from the PR-created row.
