Target: `Shipit::Webhooks::Handlers::Handler` base class `repository`/`from_github_repo_name` pattern (app/models/shipit/webhooks/handlers/handler.rb, pull_request/*_handler.rb). Attacker action: attacker submits a webhook-shaped PR payload (via opening a PR that GitHub relays, or via any handler reachable without per-repository authorization) where `params.repository.full_name` names a repository different from the one whose `webhook_secret` verified the request body, exploiting that `Repository.from_github_repo_name` trusts the payload's `full_name` string directly to resolve which `Repository`/stacks to mutate. Preconditions: two repositories tracked by Shipit under different GitHub orgs, each with its own `webhook_secret`; attacker controls org A's webhook secret (their own). Call sequence: `WebhooksController#verify_signature` authenticates using org A's secret (derived from `repository.owner.login`), then `OpenedHandler#repository` calls `Shipit::Repository.from_github_repo_name(params.repository.full_name)` which is never cross-checked against `repository_owner` used for signature verification. Binding: `repository_owner` used to select the verifying `webhook_secret` == the owner embedded in `params.repository.full_name` used to resolve the mutated `Repository`; the handler layer never asserts this equality. Scoped impact: Critical - cross-repository/cross-org stack creation: a payload validly signed by org A's secret but naming org B's `full_name` can create/mutate org B's `ReviewStack`. Proof idea: minitest integration test valid-signs a `pull_request opened` payload for org A's secret while setting `repository.full_name` to org B's tracked repo, and asserts whether a `Stack` gets created under org B's `Repository` record.
