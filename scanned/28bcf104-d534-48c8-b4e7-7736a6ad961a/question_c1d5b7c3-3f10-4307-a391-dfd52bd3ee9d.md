Target: Shipit::CCMenuUrlController#client and #fetch. Attacker action: an authenticated Shipit user (any logged-in GitHub user, not a maintainer of the target repository) sends GET /stacks/:stack_id/cc_menu_url?stack_id=<victim-stack-slug> for a stack they did not create and are not a contributor to. Preconditions: victim stack exists; no per-stack authorization check is layered on CCMenuUrlController beyond generic Shipit::Authentication login. Call sequence: #fetch calls stack (Stack.from_param!(params[:stack_id]), unscoped by owner) then client, which does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` - note this find_or_create_by! is keyed only on creator+name, NOT on stack, so if the attacker already possesses a 'CCMenu Client' ApiClient row from a previous, legitimately-authorized stack, `find_or_create_by!` will return that EXISTING record (with its original stack_id) unchanged, while #fetch still mints a URL for the newly requested victim stack via api_stack_ccmenu_url(stack_id: stack.to_param). Binding: the stack encoded in the returned ccmenu_url path must equal the stack the returned token's ApiClient#stack_id authorizes; if the memoized client's stack_id is stack A while the URL path names stack B, the two diverge. Scoped impact: Critical - a token bound to stack A is handed out embedded in a URL for stack B, and because Api::CCMenuController#stack bypasses stacks scoping (see related finding), visiting that URL discloses stack B's state via a token nominally minted for A. Proof idea: minitest creating a 'CCMenu Client' for current_user against stack_a via one #fetch call, then calling #fetch again with stack_id=stack_b.to_param, asserting the returned token's ApiClient#stack_id still equals stack_a.id while the URL path names stack_b, then replaying that URL against Api::CCMenuController and asserting stack_b data is returned, violating AUTHORIZATION_TRUTH.
