Target: Shipit::Api::BaseController#identify_user. Attacker action: sends any API request (already holding a legitimately-scoped, narrow-permission token, e.g. a 'read:stack' CCMenu client for stack A obtained via CCMenuUrlController#fetch) together with header X-Shipit-User: <victim-login>, where <victim-login> is a real Shipit User with elevated github_teams membership. Preconditions: a Shipit::User row with that login exists (e.g. any operator who ever logged in once). Call sequence: #current_user memoizes identify_user, which does `User.where('lower(login) = ?', user_login.downcase).first` with zero cross-check against current_api_client or session; the resolved current_user is then used wherever the controller/serializers call current_user (e.g. for `creator` attribution or event authorship on writes such as Api::HooksController#create, Api::DeploysController#create). Binding: current_user's identity must equal the identity that authenticated the request (the ApiClient's creator or an authenticated session), but identify_user substitutes any header-supplied login with no verification. Scoped impact: Critical - an attacker with only a narrow token can attribute a deploy/hook creation, or any current_user-stamped write, to an arbitrary victim user, forging authorship and potentially satisfying downstream checks that trust current_user's identity/team membership. Proof idea: minitest issuing an authenticated API POST (e.g. create a Hook or trigger a Deploy) with X-Shipit-User set to a victim login, asserting the created record's creator/author == the victim User rather than the token's own creator, violating IDENTITY_BINDING.
