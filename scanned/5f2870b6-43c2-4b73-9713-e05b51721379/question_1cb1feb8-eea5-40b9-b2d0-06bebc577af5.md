Target: Api::BaseController#identify_user and #current_user. Attacker action: an unprivileged HTTP client presents a valid but narrowly-scoped API token (e.g. read:hook only) alongside header X-Shipit-User: <victim-login> for an actual Shipit User row. Preconditions: a User record with login victim-login exists (e.g. any GitHub org member previously synced); attacker holds any valid token (even self-issued via CCMenuUrlController for their own stack). Call sequence: identify_user does User.where('lower(login) = ?', user_login.downcase).first with no verification that the requester is that user; current_user is later used for serialization/attribution (e.g. audit fields) though require_permission! only checks current_api_client. Binding: request X-Shipit-User header identity must equal the authenticated session/token identity; it does not. Impact: Critical, attribution/identity spoofing lets an attacker's actions be recorded/rendered as victim's GitHub identity in API responses that key off current_user. Proof idea: minitest test sending X-Shipit-User: some-admin-login with a foreign token and asserting current_user resolves to that admin's User row.
