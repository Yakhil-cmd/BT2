Target: Shipit::ReviewStackAdapter#create! and Shipit::PullRequest#github_pull_request=. Attacker action: open a PR from a fork where the PR's `base` repository is the victim org's repo but the PR's `head` repository is the attacker's own fork; the payload's `pull_request.head.ref` names a branch that exists ONLY in the attacker's fork, not in the base repository. Preconditions: `review_stacks_enabled` + `allow_all`. Call sequence: `stack_attributes` sets `branch: params.pull_request.head.ref` with no `head.repo` disambiguation recorded anywhere on the `Stack`/`ReviewStack` model, then all later `StackCommands`/`TaskCommands` git operations (`git_clone(@stack.repo_git_url, ...)`) clone the BASE repository's `repo_git_url` but attempt to check out the HEAD branch name, which is a fork-only ref. Binding that breaks: the ref recorded as `Stack#branch` must equal a ref that exists in the repository named by `Stack#repo_git_url` (a fork branch is not a ref of the base repo) — nothing marks this ReviewStack as fork-authored or resolves `head.repo.full_name` differently from `base.repo.full_name`. Scoped impact: Critical — depending on how checkout failures are handled, this can either silently deploy stale/wrong code or, if `repo_git_url` construction ever incorporates PR-supplied repo fields elsewhere in a future/alternate code path, redirect clone/fetch operations to an attacker-controlled remote. Proof idea: minitest constructing a `pull_request_opened` payload where `head.repo.full_name` differs from `base.repo.full_name`/`repository.full_name`, asserting the created `ReviewStack.branch` and demonstrating no field records the true head repository.
