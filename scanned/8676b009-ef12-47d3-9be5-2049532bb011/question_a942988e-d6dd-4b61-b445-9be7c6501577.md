Target: Shipit::Stack#base_path. Attacker action: cause a `Repository` or `Stack` record to be created where `repo_owner`/`repo_name`/`environment` contain path-traversal segments (e.g. an `environment` value of `../../other-repo/production` submitted through any endpoint that creates or updates a stack's environment field from attacker-influenced webhook or PR data, such as `ReviewStackAdapter#stack_attributes`'s `environment: \"pr#{params.number}\"` combined with a crafted `params.number`). Preconditions: `params.number` is only constrained to be numeric by the explicit-parameters schema, but any downstream code building `environment` from PR-derived strings without that constraint is in scope. Call sequence: `Stack#base_path` does `Rails.root.join('data', 'stacks', repo_owner, repo_name, environment)` with no sanitization of the interpolated segments, and this becomes `@stack.git_path`/`@stack.deploys_path`, i.e., the `chdir:` passed to `Command#start`. Binding that breaks: the filesystem path assembled from `repo_owner`/`repo_name`/`environment` must stay confined under the intended per-stack sandbox, but any of those three attacker-influenced fields can traverse it. Scoped impact: Critical — write/clone into another repository's or stack's directory (cross-repository/tenant file mutation) ahead of a deploy or rollback. Proof idea: minitest constructing a `Stack` with a crafted `environment` value and asserting whether `stack.base_path.to_s` stays inside `Rails.root.join('data','stacks', stack.repo_owner, stack.repo_name)`.
