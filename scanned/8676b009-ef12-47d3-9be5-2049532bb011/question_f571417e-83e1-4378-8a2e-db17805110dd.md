Target: Shipit::StackCommands#github and Shipit::Stack#github_app (`Shipit.github(organization: repository.owner)`). Attacker action: rename or transfer a GitHub repository (or open a PR against a repository whose `owner` string on GitHub no longer matches the org Shipit believes it belongs to) so that `Stack#repo_owner` used to select the GithubApp diverges from the org whose credentials actually govern the repository on GitHub today. Preconditions: `Shipit.github(organization: X)` returns whichever app config matches string `X`, and `Repository#owner` is only updated via `refresh_repository!` on redirect handling. Call sequence: `StackCommands#github`/`Stack#github_app` picks the `GithubApp` purely from the DB column `repository.owner`, then `Commands#base_env` injects that app's `GITHUB_TOKEN` into every `git`/`Command` invocation for the stack. Binding that breaks: the organization whose token is injected into `Command#unbundled_env` must equal the organization currently authorized on GitHub for that repository (WEBHOOK/REPOSITORY SCOPE), but the mapping is only as fresh as the last `refresh_repository!` call, with no re-validation before spawning credentialed git commands. Scoped impact: Critical — a stale/attacker-influenced `owner` column causes the wrong organization's `GITHUB_TOKEN` to be used against a repository URL derived from possibly different data, risking token exfiltration to an unintended remote. Proof idea: minitest setting `repository.owner` to org A while `repo_git_url` points at an org B repository and asserting `Commands.for(stack).env['GITHUB_TOKEN']` equals org A's token being sent toward org B's remote.
