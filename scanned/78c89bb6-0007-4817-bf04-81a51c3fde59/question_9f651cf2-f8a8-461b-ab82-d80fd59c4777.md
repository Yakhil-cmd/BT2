Target: `Shipit::Api::BaseController#authenticate_api_client`'s `BasicAuth.authenticate(request) { |*parts| token = parts.select(&:present?).join('--') }`. Attacker action: send `Authorization: Basic <base64 of '123:deadbeef...'>` where the username is a decimal id and password is an arbitrary 40-hex string, hoping the joined `'123--deadbeef...'` matches the `SimpleMessageVerifier` format even though the attacker never held the real signature. Preconditions: none beyond network access. Call sequence: `authenticate_api_client` -> `ApiClient.authenticate(token)` -> `message_verifier.verify(token)`. Binding: the token accepted must == a value actually signed by `Shipit.api_clients_secret`; a guessed id+hex string must be rejected regardless of formatting. Impact: Critical if verification is bypassed (auth bypass); expected to be safe (verifier should reject), so this test documents that the concatenation logic itself introduces no forgeable path distinct from `ApiClient.authenticate`'s own signature check. Proof idea: minitest asserting `ApiClient.authenticate('123--' + SecureRandom.hex(20))` returns nil for an existing client id 123, i.e. the basic-auth join never grants access without the real HMAC.
