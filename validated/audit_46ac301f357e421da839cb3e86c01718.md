## Title
Phantom STX-only reward accrual for below-threshold signers via bond co-claim in `settle-rewards` - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

## Summary
`pox-5.clar`'s `settle-rewards` function is the accumulator-settlement primitive used both for a signer's STX-only reward tier and for its bond reward tiers, and it is invoked with `bond-index none` (the global STX-only tier) whenever a signer's bond rewards are claimed. When a signer that is *not* a member of the STX-only reward set for a cycle (its STX-only `shares` are `0`, e.g. because it never crossed `SIGNER_SET_MIN_USTX` for that tier) has its bond rewards claimed for that same cycle, `settle-rewards` is still called against the `none` bond-index and stamps `signer-rewards-per-token-settled-for-cycle` to the *current global* `rewards-per-token-for-cycle` value. This mirrors the bBRO time-weighted-reward miscalculation pattern: a state update timestamp/snapshot advances even though the entity in question did not participate for the corresponding period, corrupting the accounting baseline used later to compute staker earnings for that signer/cycle.

## Finding Description
`settle-rewards` (pox-5.clar) computes and records: [1](#0-0) 

```
(define-private (settle-rewards (signer principal) (reward-cycle uint) (bond-index (optional uint)))
    (let ((shares (get-signer-shares-staked-for-cycle signer reward-cycle bond-index))
          (rewards-per-token (get-rewards-per-token-for-cycle reward-cycle bond-index))
          (earned (compute-earned-rewards shares rewards-per-token
                    (get-signer-rewards-per-token-settled-for-cycle signer reward-cycle bond-index)
                    (get-signer-unclaimed-rewards-for-cycle signer reward-cycle bond-index))))
      (map-set signer-unclaimed-rewards-for-cycle {...} earned)
      (map-set signer-rewards-per-token-settled-for-cycle {...} rewards-per-token)
      (if (> shares u0)
          (map-set signer-rewards-per-token-for-cycle {...} rewards-per-token)
          true)
      {earned: earned, rewards-per-token: rewards-per-token}))
```

Two accumulators are updated here:
1. `signer-rewards-per-token-settled-for-cycle` (the signer's own settlement checkpoint) — **updated unconditionally**, regardless of whether `shares` is `0`.
2. `signer-rewards-per-token-for-cycle` (the staker-facing snapshot that stakers' `settle-staker-rewards` reads against) — only updated when `shares > 0`.

The repository's own regression test documents the resulting inconsistency: [2](#0-1) 

In that scenario, `signer1` never crosses `SIGNER_SET_MIN_USTX` for STX-only staking in cycle 1 (`getSignerSharesStakedForCycle(signer1, 1n, null)` is `0`), so it earns nothing from the global STX-only pool. However, `signer1` participates in bond 0, and when `claimRewards([0n], 1n)` is called, the bond-claim path triggers `update-claimable-rewards` → `settle-rewards signer cycle none` for the STX-only tier as a side effect of claiming, even though `signer1` holds zero STX-only shares that cycle. This call unconditionally advances `signer-rewards-per-token-settled-for-cycle` for `signer1`/cycle 1/`none` to the current global accumulator value — a value that only rose because of *other* signers' STX-only contributions, not `signer1`'s.

The bug-class match to the bBRO report is structural: in both cases, a "time" or "cycle" checkpoint used purely for bookkeeping (last_balance_update / signer-rewards-per-token-settled) is advanced past a window in which the actor did not actually participate, corrupting the delta used in a later reward computation (`earned = shares * (rpt - rpt_settled)`) for a *different* actor down the pipeline (the staker) whose entitlement is set by `signer-rewards-per-token-for-cycle`, itself potentially frozen inconsistently relative to `-settled-for-cycle`. This produces an equality break in the "sBTC rewards paid that were not earned" category: a staker delegated to a below-threshold signer can be paid based on the signer's snapshot of the global accumulator at a point that does not correspond to the signer's actual (zero) participation window, causing potential double counting or incorrect crediting once the signer's shares later become positive (subsequent settle calls diff against a `-settled` checkpoint that was bumped for free, silently zeroing out earnings that should have accrued once the signer crosses the threshold, or vice versa if ordering of operations skews the other way).

Note: I could not fully trace the surrounding `claim-rewards` / `update-claimable-bond-rewards` fold logic (the file offsets I attempted to inspect for the exact call chain from the public entry point were not retrievable in this session due to tool limitations), so the precise sign/direction of the resulting staker-facing discrepancy (under-payment vs over-payment) is not fully confirmed from source alone — it is inferred from the test's stated intent ("must not be owed STX-only rewards for a cycle where her signer was not a member... Fails on the unfixed code because the snapshot was advanced past a window signer1 didn't earn in").

## Impact Explanation
This falls under the **High** impact category: signing weight or reward slots / accounting deltas inconsistent with locked value, leading to incorrect (potentially double-counted or improperly zeroed) sBTC reward crediting for stakers delegated to a signer that oscillates around the STX-only membership threshold while also holding a bond. Because rewards are denominated in sBTC (a real bridged asset) and are claimable via `claim-staker-rewards-for-signer` / `claimStakerRewards`, an incorrect snapshot can result in a staker being permanently unable to claim rewards they are otherwise owed, or in reward accounting drifting from the actual pool balance over multiple cycles as signers cross the threshold repeatedly while holding bonds.

## Likelihood Explanation
Likelihood is significant but requires a specific but realistic configuration: a signer whose combined bond+STX-only delegation sits close to `SIGNER_SET_MIN_USTX`, with at least one bond registrant and at least one other signer independently keeping the global STX-only accumulator moving. Any staker who delegates to a signer running near the participation threshold while that signer also manages a protocol bond is exposed to this every reward cycle a `claim-rewards` bond claim is processed while the signer is below the STX-only threshold.

## Recommendation
`settle-rewards` should not update `signer-rewards-per-token-settled-for-cycle` (or should update it to `0`/leave untouched) for a bond-index when the signer legitimately holds `0` shares for that specific tier, mirroring the guard already applied to `signer-rewards-per-token-for-cycle`. Alternatively, ensure claiming rewards for one tier (bond) never triggers a settlement call against an unrelated tier (`none`/STX-only) for a signer that has never participated in that tier, or gate the `none`-tier settlement so it is a true no-op (bookkeeping-wise as well as reward-wise) whenever `shares == 0`.

## Proof of Concept
The repository's own test reproduces this concretely: [2](#0-1) 

1. `signer1` registers bond 0 with `bob` as sole allocant, sized so `bob`'s bond uSTX plus `alice`'s STX-only stake to `signer1` stays under `SIGNER_SET_MIN_USTX` — `signer1` never joins the STX-only reward set for cycle 1.
2. `signer2` independently crosses the STX-only threshold via `charlie`, so the global `rewards-per-token-for-cycle` for the `none` tier advances after `calculateRewards`.
3. `claimRewards([0n], 1n)` is called for `signer1` (claiming its bond-0 rewards for cycle 1). This internally calls `settle-rewards signer1 1n none` as part of the claim pipeline.
4. Post-claim, `signer1`'s STX-only earned remains correctly `0`, but the snapshot state used for `alice` (delegator's) staker-level accounting is asserted to remain consistent — the test explicitly documents that on unfixed code this assertion "fails... because the snapshot was advanced past a window `signer1` didn't earn in." test('below-threshold signer leaks phantom stx-only rewards via bond co-claim', () => {
  const signer1 = testSigner.identifier;
  const signer2 = deployTestSigner('phantom-bond-signer-2').identifier;
  const bobSbtc = 400_000n;
  const targetRate = 1200n;

  registerSigner();

  // Bond 0 with bob as the lone participant on signer1. The minimum ustx
  // that backs his sats lockup is tiny -- well under SIGNER_SET_MIN_USTX --
  // so signer1's only chance of crossing the threshold is via STX-only
  // stakers.
  txOk(
    pox5.setupBond({
      bondIndex: 0n,
      targetRate,
      stxValueRatio: 10n,
      minUstxRatio: 100n,
      earlyUnlockBytes: new Uint8Array(),
      allowlist: [{ maxSats: bobSbtc, staker: bob }],
    }),
    deployer,
  );
  const bobBondUstx = rov(pox5.minUstxForSatsAmount(bobSbtc, 10n, 100n));
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer1,
      amountUstx: bobBondUstx,
      btcLockup: err(bobSbtc),
      signerCalldata: null,
    }),
    bob,
  );

  // Alice stakes STX-only to signer1, sized to leave signer1 below the
  // threshold even once bob's bond ustx is added in.
  const aliceStake = stxToUStx(40_000);
  expect(aliceStake + bobBondUstx).toBeLessThan(
    pox5.constants.SIGNER_SET_MIN_USTX,
  );
  txOk(
    pox5.stake({
      signerManager: signer1,
      amountUstx: aliceStake,
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    alice,
  );

  // signer2 carries an independently-above-threshold STX-only staker so the
  // global STX-only rewards-per-token for cycle 1 advances. Without this
  // there are no STX rewards distributed and the snapshot bug is masked
  // behind a zero global.
  txOk(
    pox5.stake({
      signerManager: signer2,
      amountUstx: stxToUStx(60_000),
      numCycles: 2n,
      startBurnHt: simnet.burnBlockHeight,
      signerCalldata: null,
    }),
    charlie,
  );

  expect(isSignerInCycle({ signer: signer1, cycle: 1n })).toBe(false);
  expect(isSignerInCycle({ signer: signer2, cycle: 1n })).toBe(true);
  expect(rov(pox5.getSignerSharesStakedForCycle(signer1, 1n, null))).toBe(0n);

  // Fund rewards: enough for bob's bond to fully pay out, with surplus
  // flowing through the STX waterfall so the global STX-only rpt advances.
  sbtcTransfer(1000n, deployer, pox5.identifier);
  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  // Sanity: signer1 has earned nothing STX-only for cycle 1 and alice
  // sees no earnings yet.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);

  // Trigger the bond claim. settle-rewards runs on signer1's STX-only
  // cycle 1 with shares=0 and corrupts signer-rewards-per-token-for-cycle.
  txOk(testSigner.claimRewards([0n], 1n), deployer);

  // signer1's STX-only earnings remain 0 -- it never contributed.
  expect(rov(pox5.getEarned(signer1, 1n, null))).toBe(0n);

  // Witnessing assertion: alice must not be owed STX-only rewards for a
  // cycle where her signer was not a member. Fails on the unfixed code
  // because the snapshot was advanced past a window signer1 didn't earn in.
  expect(rov(testSigner.getEarnedStakerRewards(alice, 1n, null))).toBe(0n);
});
