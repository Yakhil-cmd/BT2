### Title
CCMenu API endpoint bypasses ApiClient stack scoping, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` and the base API scoping helper in `app/controllers/shipit/api/base_controller.rb` (`stacks`/`stack` methods, lines 74-80) enforces that scoping by filtering `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true. `Api::CCMenuController`, however, overrides `stack` with its own implementation that ignores this scoping entirely.

### Finding Description
The binding that should hold is: *the set of stacks a token is authorized for == the set of stacks the token can touch*. `Shipit::ApiClient#check_permissions!` only checks that the client has the `read:stack` permission string; it never checks which stack the permission applies to [1](#0-0) . Enforcement of the stack scope is therefore left entirely to the controller's `stack`/`stacks` resolution, which is centralized in `Api::BaseController`: [2](#0-1) 

`Api::CCMenuController` bypasses this shared, scope-aware resolver and instead resolves the stack directly from the request parameter, with no reference to `current_api_client.stack_id`: [3](#0-2) 

`require_permission :read, :stack` at the top of the controller only invokes `check_permissions!(:read, :stack)`, which — as shown above — is a pure string membership check on `permissions`, independent of `stack_id`. So a valid, stack-scoped token (created with `stack_id` set to stack A) that legitimately holds `read:stack` can call `GET /api/:stack_id/cc_menu.xml` with any other stack's `stack_id` (stack B) and receive stack B's CCMenu XML (latest deploy/rollback status), because `CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` from the global `Stack` table rather than from the scoped `stacks` collection used everywhere else in the API (e.g. `Api::StacksController`, `Api::TasksController`).

This is the direct structural analogue of the report's blocklist bug: a security invariant (here, "a token only touches the stack it was scoped/authorized for") is enforced in one code path (`BaseController#stack`) but silently dropped in a sibling code path (`CCMenuController#stack`) that reimplements the same responsibility.

### Impact Explanation
This is an unauthenticated-relative-to-scope read of stack state: a token holder who is only supposed to see one stack's build/deploy status can read the latest deploy/rollback status (success/failure, build label, activity, timestamps) of every other stack in the Shipit instance, including private/internal stacks the token owner has no legitimate visibility into. Per the engine's own permission model, this is a scope-authorization escalation (a `read:stack` token scoped to stack A gains read access to stack B's state), matching the "unauthenticated read of stack state" High-impact criterion.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that creates stack-scoped `ApiClient` tokens (the `stack_id` column and the `stacks`/`stack` scoping logic in `BaseController` exist specifically to support this use case, and CCMenu tokens are commonly handed out to third-party CI-status dashboards / build radiators, which is a lower-trust consumer than the main Shipit UI). No privileged access is required beyond possessing any valid, even minimally-scoped, API token with `read:stack`; the attacker only needs to guess or enumerate another stack's `stack_id` (repo owner/name/branch), which is not secret.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scope-aware helper instead of the raw `Stack` model, e.g. `@stack ||= stacks.from_param!(params[:stack_id])` (inheriting `stacks` from `BaseController`), so that a stack-scoped `ApiClient` cannot resolve a stack outside its `stack_id`. Alternatively, add an explicit check in `require_permission!`/`check_permissions!` that validates the requested stack against `current_api_client.stack_id` whenever it is present.

### Proof of Concept
1. As an admin, create a stack-scoped API client via console/seed: `ApiClient.create!(creator: admin_user, name: 'radar', permissions: %w[read:stack], stack: stack_a)`.
2. Using `stack_a`'s token, call `GET /api/:stack_b_owner/:stack_b_name/:stack_b_branch/cc_menu.xml` (any other existing stack's identifier) with HTTP Basic Auth using the token.
3. Observe the request succeeds (HTTP 200) and returns stack B's CCMenu XML (`lastBuildStatus`, `lastBuildLabel`, `activity`, etc.), even though the token was only meant to authorize `stack_a`. Compare with `Api::StacksController#show` for the same stack B and same token, which correctly returns 404/empty because it uses the scoped `stacks.from_param!` helper — confirming the discrepancy is specific to `CCMenuController`.
