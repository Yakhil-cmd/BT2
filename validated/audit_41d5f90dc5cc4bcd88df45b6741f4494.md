### Title
`set_oracle` for Aquarius LP keys can be permanently griefed by draining the pool below `min_pool_value_wad` before governance executes - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
Registering an Aquarius LP price source requires the `ConfigureAssetOracle` governance operation to execute `set_oracle`, which both attests and probes the oracle against the pool's **live** reserves. An unprivileged attacker who holds (or briefly provides) liquidity in the target Aquarius pool can shrink a reserve or total pool value below the configured threshold at execution time, making `set_oracle` panic and the ready governance operation revert. Because the check reads manipulable on-chain pool state, the attacker can repeat this on every execution attempt, indefinitely blocking registration of that LP collateral's oracle. This is the same class as `TWAPOracleDollar3poolFacet.setPool`: an admin setter gated on a live reserve condition that anyone can violate.

### Finding Description
`admin::set_oracle` runs `attest_sources` then `engine::probe_priceable` before committing the oracle (`contracts/price-aggregator/src/admin.rs:84-92`).

`aquarius::attest` asserts on the pool's current reserves and shares (`contracts/price-aggregator/src/providers/aquarius.rs:37-48`):

```rust
// contracts/price-aggregator/src/providers/aquarius.rs:41
aquarius_pool_reserves_call(env, &lp.pool).is_some_and(|(a, b)| a > 0 && b > 0),
// contracts/price-aggregator/src/providers/aquarius.rs:46
aquarius_total_shares_call(env, &lp.pool).is_some_and(|shares| shares > 0),
```

and `read` (reached through `probe_priceable` for LP oracles) fails closed when the live pool value falls below the configured `min_pool_value_wad` (`contracts/price-aggregator/src/providers/aquarius.rs:118-122`):

```rust
if pool_value_wad < lp.min_pool_value_wad {
    return Err(OracleError::InsufficientAquariusLiquidity);
}
```

Both conditions depend on the Aquarius pool's current reserves, which any unprivileged address can change at will:

- `pool::swap` moves reserves between the two legs.
- An LP holder calling the pool's `withdraw_liquidity`/`remove_liquidity` drains both reserves and burns shares; on a thin pool an attacker can deposit, then withdraw nearly everything, driving `total_shares` and `pool_value_wad` down right before `execute`.

Governance `execute` of a ready `ConfigureAssetOracle` operation is itself permissionless once the timelock matures, so the attacker can watch for the execution transaction, sandwich the pool to a failing state via their own Aquarius trades/withdrawals, and let it revert. The operation is then dead — under the governance wiring it cannot be retried and must be re-proposed and re-timelocked, giving the attacker a fresh window to repeat the grief. Swaps can be reversed after the failed execute, so sustained grief costs only fees and slippage.

### Impact Explanation
The protocol cannot register (or re-register after `remove_oracle`-style reconfiguration) an Aquarius LP collateral oracle while the attacker is willing to keep the pool's reserves/threshold manipulated at each execute. This blocks listing of that LP token as collateral — a governance operation the protocol cannot perform, reachable entirely by unprivileged actions (own trades and LP withdrawals on Aquarius). Severity is bounded by the same argument as the original report: admin config liveness, not user funds.

### Likelihood Explanation
Requires the target pool to be thin enough that a single attacker's LP withdrawal or swap pushes `pool_value_wad` below `min_pool_value_wad` (or a reserve to zero / shares to zero). For a new or small pool this is cheap; on a deep pool it is expensive but still repeatable. The `attest`/`probe` design gives no alternative admission path — governance cannot bypass the live-state check without a contract upgrade.

### Recommendation
Do not gate oracle registration on live, manipulable pool state. `set_oracle` should validate only immutable bindings (share-token match, token pair, pool kind, decimals, amplification presence). Move the `reserves > 0`, `shares > 0`, and `min_pool_value_wad` checks out of `attest`/`probe_priceable` at registration time and keep them solely in the read path, where `read` already fails closed with `NoLastPrice`/`InsufficientAquariusLiquidity` and the pool's fail-closed behavior is the intended safety mechanism.

### Proof of Concept
1. Governance proposes `ConfigureAssetOracle(PriceKey::Token(share))` with a `PriceSource::AquariusLp` whose `min_pool_value_wad` equals, say, 90% of the pool's current WAD value; timelock matures and the operation becomes ready.
2. Attacker (LP in the pool) calls the Aquarius pool's withdraw/exit entrypoint to remove most liquidity in the same ledger, dropping `total_shares` and `pool_value_wad` below `min_pool_value_wad` (or pushes one reserve to 0 on a shallow pool via `swap`).
3. Anyone calls governance `execute`; `set_oracle` → `attest_sources` → `aquarius::attest` panics with `UnsupportedAquariusPool` (aquarius.rs:41/46), or `engine::probe_priceable` → `read` returns `InsufficientAquariusLiquidity` (aquarius.rs:121), reverting the whole execute.
4. Attacker re-adds liquidity, waits for the next ready operation, repeats — the oracle can never be registered while the attacker persists.

Uncertainty: I did not trace the exact `engine::probe_priceable` → `read` wiring beyond the call site in `set_oracle` (admin.rs:88), and the reachable-level of reserve manipulation depends on the deployed Aquarius pool's own exit semantics; the `a > 0 && b > 0` / `shares > 0` / `min_pool_value_wad` panic conditions in the in-scope code are confirmed.
