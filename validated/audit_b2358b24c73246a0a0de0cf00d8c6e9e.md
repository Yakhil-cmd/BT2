This report describes an oracle/flash-swap analog in Snowbridge's system-frontend pallet, where a real, permissionless signed extrinsic performs an on-chain AMM swap with **no slippage protection**, exposing the value transferred to a beneficiary (the relayer reward/tip) to sandwich manipulation.

### Title
Snowbridge `system-frontend` pallet swaps a user's tip asset for Ether with no minimum-output guard, allowing sandwich attacks to reduce the relayer tip/reward - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`pallet_snowbridge_system_frontend::Pallet::add_tip` and `register_token` let any signed account convert an arbitrary fungible asset into Ether via `pallet-asset-conversion`'s constant-product AMM (`Swap` trait), then burn the Ether output as a relayer tip/fee for a Snowbridge message to Ethereum. The swap call explicitly passes `amount_out_min = None`, disabling the only slippage guard the underlying AMM offers. [1](#0-0) 

### Finding Description
`swap_and_burn` invokes `T::Swap::swap_exact_tokens_for_tokens(who, swap_path, tip_amount, None, who, true)`, explicitly commented `// No minimum amount required`: [2](#0-1) 

This is called from the public, unprivileged `add_tip` extrinsic: [3](#0-2) 

and from `register_token` via `swap_fee_asset_and_burn`: [4](#0-3) 

`T::Swap` is bound to `pallet_asset_conversion::Swap`, whose `swap_exact_tokens_for_tokens` treats `amount_out_min: Option<Balance>` as fully optional — when `None`, no minimum-output check is performed and the trade executes at whatever price the pool's live reserves imply at that moment: [5](#0-4) 

Because pallet-asset-conversion pools are permissionless constant-product AMMs whose reserves any account can move with `swap_exact_tokens_for_tokens`/`add_liquidity`/`remove_liquidity` in the very same block, an attacker (no privileged role required) can:
1. Front-run the victim's `add_tip`/`register_token` extrinsic with a large swap on the `[tip_asset, ether]` pool, moving the price sharply against the tip asset.
2. Let the victim's swap execute at this manipulated price with no `amount_out_min` floor, so `ether_gained` is far below the fair-market value of `tip_amount`.
3. Back-run with the reverse swap to restore the pool and extract the price impact as arbitrage profit — all within the same block, at only gas/AMM-fee cost.

The resulting `ether_gained` — reduced by the sandwich — is what actually gets burned for teleport and forwarded on-chain to BridgeHub as the message tip/fee amount (`build_add_tip_call` / `build_register_token_call`), i.e. it directly determines the reward that accrues to the beneficiary (the relayer network) for processing that message: [6](#0-5) 

This is the direct FRAME analog of the reported bug class: a swap whose output amount is determined by a live/AMM price with no caller-supplied minimum-output bound, letting an attacker manipulate the price in the same transaction/block window and cause the intended beneficiary of the swap's output (here, the relayer reward funded by the tip) to receive less value than intended.

### Impact Explanation
The tipper's asset is spent at face value, but the resulting Ether reward credited to the relayer-incentive mechanism on Ethereum can be arbitrarily reduced by a same-block sandwich, directly reducing (or effectively nullifying) the intended relayer incentive/reward for a given spend, and enriching the attacker via the AMM fee-adjusted round-trip. This is a value-transfer/loss bug reachable by any unprivileged account, matching a Medium-severity slippage/oracle-manipulation class.

### Likelihood Explanation
Any account can call `add_tip` (fully permissionless, `ensure_signed` only) with an asset/pool of their choosing, and any other account can freely trade against the same `pallet-asset-conversion` pool in the same block since pool creation and swapping are permissionless. No governance, collator, or validator privilege is required — only ordinary extrinsic submission and enough capital to move the pool within one block, which is the standard cost profile of an AMM sandwich attack.

### Recommendation
`swap_and_burn`/`swap_fee_asset_and_burn` should not pass `None` for `amount_out_min`. Compute an acceptable minimum Ether output ahead of the swap (e.g., via `QuotePrice::quote_price_exact_tokens_for_tokens` with a caller- or protocol-defined tolerance) and pass `Some(min_out)` into `Swap::swap_exact_tokens_for_tokens`, causing the extrinsic to fail rather than silently accept an AMM-manipulated, below-market conversion rate.

### Proof of Concept
- Failed guard: `amount_out_min: None` at [7](#0-6)  means `pallet_asset_conversion::Pallet::do_swap_exact_tokens_for_tokens`'s `ensure!(amount_out >= amount_out_min, ...)` guard at [8](#0-7)  is bypassed (it only runs `if let Some(amount_out_min) = amount_out_min`).
- Deployment evidence: `system-frontend` pallet is production code wired into Snowbridge's asset-hub-side runtime configuration with `type Swap: Swap<Self::AccountId, AssetKind = Location, Balance = u128>` bound to the live `pallet_asset_conversion::Pallet` implementation, per the trait bound at [9](#0-8) .
- PoC execution status: Not executed against a live network; this analysis is based on static code tracing across `bridges/snowbridge/pallets/system-frontend/src/lib.rs` and `substrate/frame/asset-conversion/src/lib.rs`. A minimal integration test reproduction would: (1) create a `[tip_asset, ether]` pool with modest liquidity, (2) call `add_tip` with a fixed `tip_amount`, (3) in the same block/transaction batch, have a second account perform a large swap against the same pool immediately before, observing `ether_gained` (and thus the tip amount forwarded in `AddTip`) drop significantly below the pre-manipulation quote from `AssetConversion::quote_price_exact_tokens_for_tokens`.

		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
