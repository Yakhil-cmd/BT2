### Title
CCMenu API Endpoint Ignores ApiClient Stack Scope, Allowing Cross-Stack Deploy-State Disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` re-implements stack resolution instead of reusing the scoped `BaseController#stack` helper, so an `ApiClient` token that is deliberately restricted to a single stack (`ApiClient#stack_id`) can be used to read the deploy/build status of *any* stack in the installation.

### Finding Description
`BaseController` enforces the "stack a token authorises" binding through two cooperating methods: [1](#0-0) 

`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped (`stack_id?` true), and `stack` resolves `params[:stack_id]` only against that restricted relation. This is the mechanism that is supposed to guarantee: *the set of stacks a token authorises == the set of stacks it can touch*.

`CCMenuController` overrides both halves of this binding and drops the scoping: [2](#0-1) 

- `authenticate_api_client` pulls the token from `params[:token]` via `ApiClient.authenticate`, correctly identifying a legitimately-scoped client.
- `stack` then calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model class, bypassing the `stacks` scoping method entirely.
- `require_permission :read, :stack` only checks that the token has the generic `read:stack` permission bit (`ApiClient#check_permissions!`, [3](#0-2) ); it never checks that the resolved `stack` is the one bound to `current_api_client.stack_id`.

Before the request: an `ApiClient` record has `stack_id = A` and `permissions = ['read:stack']`, meaning it is only supposed to authorise reads of stack `A`.

After the request: the same token, presented with `stack_id: B` in the URL, is authenticated successfully (`authenticate_api_client` only validates the token, not the stack), and `stack` resolves to stack `B` because `Stack.from_param!` has no scoping. The equality `stacks_authorised_by_token == stacks_touched_by_request` is broken: the token authorises only `{A}` but the request touches `{B}`.

### Impact Explanation
The `show` action renders `deploy.running?`, `deploy.ended_at`/`started_at`, `deploy.id`, `stack.merge_status`, and the stack's public URL for whatever stack is requested: [4](#0-3) 

This lets a holder of a narrowly-scoped, single-stack `ApiClient` token enumerate and disclose the deploy/build status, lock state, and latest-deploy timing of every other stack managed by the Shipit instance — an unauthenticated (with respect to that other stack) read of stack state, matching the "unauthorized read of stack state" High-impact category. It escalates a credential that was explicitly restricted to one stack into cross-stack visibility.

### Likelihood Explanation
Any party who has been issued a stack-scoped `ApiClient` token (the normal, least-privileged way to integrate a single project's build status with CI dashboards, exactly what `read:stack` + CCMenu is designed for) can trivially exploit this by changing the `stack_id` in the URL/query string — no additional secrets, GitHub credentials, or elevated permissions are required beyond the token they already legitimately hold for their own stack.

### Recommendation
Make `CCMenuController#stack` respect the same scoping as the rest of the API by resolving through `stacks.from_param!(params[:stack_id])` (the `BaseController` method) instead of calling `Stack.from_param!` directly, e.g.:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Since `authenticate_api_client` is overridden to read the token from `params[:token]`, ensure `current_api_client` is set before `stacks` is evaluated (it already is, since `authenticate_api_client` runs as a `before_action`).

### Proof of Concept
1. Create/obtain an `ApiClient` with `stack_id = A` (stack "team-a/service") and `permissions = ['read:stack']`; note its `authentication_token`.
2. Note the existence of an unrelated stack `B` ("team-b/other-service") the token was never granted access to.
3. Request `GET /ccmenu/team-b/other-service/production?token=<token-for-A>` (routed to `Shipit::Api::CCMenuController#show` per `config/routes.rb` `scope '/ccmenu/*stack_id' ...`).
4. Observe that `authenticate_api_client` succeeds (token is valid) and `stack` resolves to stack `B` via `Stack.from_param!`, returning stack `B`'s XML deploy status — even though the token's `stack_id` is `A`, not `B`.
