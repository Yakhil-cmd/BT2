### Title
Arbiter can be the same party as the payer/payee in an arbiter contract, allowing self-dealing fund diversion - (File: `arbiter_contract.js`)

### Summary
The arbiter-contract escrow mechanism lets a designated `arbiter_address` unilaterally decide, via a `data_feed` message, which of the two contract parties (`my_address`/`peer_address`) receives the funds locked in the shared address. Nothing in the contract creation, offer/acceptance, or shared-address-definition logic prevents `arbiter_address` from being equal to (or controlled by) one of the contract parties themselves. This mirrors the "Operators are implicitly trusted" class of bug: a role meant to be a neutral, disinterested observer/vouching party can instead be the same entity as one of the transacting counterparties, letting it unilaterally rule in its own favor.

### Finding Description
When an arbiter contract's shared address is derived in `deriveSharedAddress`, the oscript definition grants the payout to whichever party is named by a `data_feed` message posted from `contract.arbiter_address`: [1](#0-0) 

For private assets, the resolution is even simpler — a data feed message from either counterparty declaring `CONTRACT_DONE_<hash>` is trusted directly, and the arbiter's role is to resolve public disputes by publishing `CONTRACT_<hash> = winner_address` as a `data_feed` message that is checked only for being one of `contract.my_address` or `contract.peer_address`: [2](#0-1) 

Crucially, neither the contract-offer creation path (`createAndSend`), nor the offer/acceptance handling in `wallet.js` (`arbiter_contract_offer`, `arbiter_contract_shared`), nor `deriveSharedAddress` itself ever check that `arbiter_address` differs from `my_address` or `peer_address`: [3](#0-2) [4](#0-3) 

Because the arbiter's data-feed message is authenticated purely by unit authorship (`objUnit.authors[0].address !== contract.arbiter_address` check in `parseWinnerFromUnit`), and the on-chain shared-address definition's `in data feed` oscript condition only checks that the *feed publisher* matches `arbiter_address`, a party who sets `arbiter_address` equal to their own address (or an address they control) can single-handedly resolve the "dispute" in their own favor and draw the escrowed funds from the shared address, regardless of whether they actually delivered the goods/service. This is the direct analog of the reported issue: the trusted intermediary (arbiter ≈ operator) is not prevented from simultaneously being a transacting party (buyer/seller), enabling self-serving fraud.

### Impact Explanation
An attacker acting as the payer (or payee) in an arbiter contract can set `arbiter_address` to an address they control. After the counterparty funds the shared address (`paid` status), the attacker (as "arbiter") posts a `CONTRACT_<hash>=<attacker_address>` data feed message, satisfying the `or` branch of the escrow definition in `deriveSharedAddress` and unlocking the funds to themselves — this is unauthorized spending of escrowed funds belonging to the honest counterparty, i.e. direct fund theft from a wallet-level payment primitive.

### Likelihood Explanation
This requires no protocol-level exploit — it only requires the attacker to convince (or be) the counterparty into forming a contract in which the "arbiter" is secretly controlled by the attacker, then simply signing/broadcasting a unit from that arbiter address. All of the pieces (`arbiter_contract.js` offer/accept, `deriveSharedAddress`, and the `parseWinnerFromUnit`/data-feed consumption logic) are reachable by any ordinary wallet user acting as an unprivileged party in a private-payment/arbiter-contract flow, with no special network or node access needed.

### Recommendation
Add an explicit validation, both client-side (in `arbiter_contract.js` when creating/accepting a contract, e.g. `createAndSend`, and in `wallet.js`'s handling of `arbiter_contract_offer`/`arbiter_contract_shared`) and ideally reflected in how the shared address definition is derived, to reject any contract where `arbiter_address === my_address` or `arbiter_address === peer_address`. Consider also cross-checking that the arbiter address is a recognized, independent arbiter (e.g., present in `wallet_arbiters`/`arbiters.getInfo`) rather than an arbitrary address supplied by either party.

### Proof of Concept
1. Attacker A crafts an arbiter contract offer where `my_address` = A's address, `peer_address` = victim B's address, and `arbiter_address` = an address controlled by A (or a colluding third address).
2. B accepts, unaware that "arbiter" is actually A. The shared address is derived per `deriveSharedAddress` (`arbiter_contract.js:454-574`), embedding the `in data feed` condition keyed on `contract.arbiter_address`.
3. B funds the shared address (status becomes `paid`).
4. A, controlling `arbiter_address`, posts a unit with a `data_feed` message `{"CONTRACT_<hash>": "<A's address>"}`.
5. `parseWinnerFromUnit` (`arbiter_contract.js:798-814`) and the on-chain oscript condition both accept this as valid resolution since it only checks that the message came from `contract.arbiter_address`.
6. A can now spend the escrowed funds via the `"in data feed" ... = A` branch of the definition, without B ever having agreed that A should win — full fund diversion despite B never receiving the promised goods/service.

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
