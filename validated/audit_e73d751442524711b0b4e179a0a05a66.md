### Title
Uncaught deferred exception in `decryptPackage()` crashes the node process on receipt of a device message encrypted to an unrecognized key - (File: device.js)

### Summary
`device.js:decryptPackage()` throws an `Error` inside a `setTimeout` callback when a received encrypted device message references an ephemeral key that the node does not recognize. Because the throw happens asynchronously (outside the caller's `try/catch`), it becomes an uncaught exception. `network.js` installs a global `uncaughtException` handler that deliberately re-throws to crash the process, so any peer able to deliver a device message to a node can remotely crash it — the same bug class as CVE-2022-0583 (a malformed/unexpected input field causing an unhandled crash in a parsing/dissection routine), but here the "dissector" is the ocore device-message decryption path.

### Finding Description
`decryptPackage()` validates the encrypted package's `dh.recipient_ephemeral_pubkey` against the node's current temp key, previous temp key, and permanent key. If none match, it does not return an error synchronously; instead it schedules a `throw` via `setTimeout` and returns `null`: [1](#0-0) 

This function is invoked from `handleJustsaying()`'s `hub/message` handler, which wraps the *synchronous* call in a `try/catch`: [2](#0-1) 

Because the actual `throw` fires later inside the `setTimeout` callback, it executes with a fresh call stack, completely outside the `try/catch` block that wrapped the original `decryptPackage()` invocation. The exception is therefore uncaught at the point of origin and propagates to Node's global exception handler.

`network.js` installs a process-wide handler that intentionally re-throws any uncaught exception in order to crash the process: [3](#0-2) 

The reachability of `decryptPackage()` requires very little from an attacker. To reach the `hub/message` handling code in `device.js`, an attacker only needs:
- `message_hash` to be a non-empty string,
- `objDeviceMessage.signature`/`pubkey` to be any self-consistent, attacker-generated key pair (the message is self-signed, no pre-existing pairing relationship is verified before decryption is attempted),
- `objDeviceMessage.to` set to the victim's device address (device addresses are routinely shared as part of pairing links/QR codes and are not secret),
- `encrypted_package.dh.recipient_ephemeral_pubkey` set to any value that does not equal the victim's current temp/prev-temp/permanent public key (trivial to satisfy).

The correspondent-relationship check (`SELECT ... FROM correspondent_devices WHERE device_address=?`) happens only *after* decryption succeeds; it plays no role in gating the vulnerable code path, since the crash occurs inside `decryptPackage()` itself, before that check is reached.

### Impact Explanation
Any party who can deliver a `hub/message` (or hub `deliver`) addressed to a target device — without needing an established pairing — can force `decryptPackage()` to schedule a deferred, uncaught `Error`. When it fires, the process-level `uncaughtException` handler in `network.js` re-throws it, terminating the entire ocore process (full node, hub, or wallet). This is a full denial of service: the node stops confirming/relaying units, serving light clients, and processing AA triggers or payments until manually restarted, matching the "network unable to confirm new units" impact class defined in scope.

### Likelihood Explanation
Likelihood is high: the only requirements are knowledge of the target's device address (routinely exchanged for pairing/communication) and the ability to open a websocket connection to the target's hub or the target itself (if it acts as its own hub). No valid pairing, no private keys, and no correct decryption are needed — the attacker merely needs the message to fail key-matching, which is the default outcome for any ephemeral key value they choose.

### Recommendation
Do not defer the "unknown key" error via `setTimeout(() => { throw ... })`. Instead:
- Return an error synchronously (or via a callback) so the existing `try/catch` in `handleJustsaying()` and other callers can handle it gracefully (e.g., `respondWithError`), consistent with the surrounding code's error-handling style.
- If a non-fatal notification is still desired for diagnostic/backup-recovery purposes, use `eventBus.emit('nonfatal_error', ...)` (already present but commented out) instead of throwing, so the process does not crash on receipt of adversarial input.

### Proof of Concept
1. Learn (or obtain via a normal pairing invite) the device address of the target node, `victim_device_address`.
2. Generate an arbitrary EC key pair `(pub, priv)` and craft a `hub/message` `justsaying`:
```
{
  subject: 'hub/message',
  body: {
    message_hash: <base64 hash of message below>,
    message: {
      signature: <sign(getDeviceMessageHashToSign(msg), priv)>,
      pubkey: pub,
      to: victim_device_address,
      encrypted_package: {
        dh: {
          sender_ephemeral_pubkey: <any valid EC pubkey>,
          recipient_ephemeral_pubkey: <any EC pubkey NOT equal to victim's current/prev temp key or permanent key>
        },
        encrypted_message: <any base64 string>,
        iv: <valid base64 12-byte IV>,
        authtag: <valid base64 16-byte tag>
      }
    }
  }
}
```
3. Send this justsaying to the victim node (directly, or relayed through its hub via `hub/deliver`).
4. `handleJustsaying()` passes the initial hash/signature checks, then calls `decryptPackage()`. Because `recipient_ephemeral_pubkey` matches none of the known keys, `decryptPackage()` schedules `throw Error("message encrypted to unknown key...")` via `setTimeout`.
5. ~100ms later, the scheduled throw executes uncaught; `network.js`'s `process.on('uncaughtException', ...)` handler logs it and re-throws, crashing the victim's ocore process.
