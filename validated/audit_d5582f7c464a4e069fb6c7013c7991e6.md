### Title
Unauthenticated forgery of GitHub webhooks for organizations without a `webhook_secret` allows cross-repository actions and forged team-membership escalation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate against using an attacker-supplied field (`repository.owner.login` / `organization.login`) taken from the unauthenticated JSON body, and `GitHubApp#verify_webhook_signature` silently treats the request as verified whenever that organization has no `webhook_secret` configured. Because signature *acceptance* is bound to the organization named in the payload while the actual *effect* (which repository/team/stack is mutated) is bound to a different field of the same attacker-controlled payload, an attacker can pick any configured organization that has no `webhook_secret` and forge events that act on arbitrary repositories or teams — including adding themselves to a team counted by `Shipit.github_teams`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` resolves the GitHub App config from the payload itself: [1](#0-0) 

`repository_owner` is taken straight from unauthenticated JSON: [2](#0-1) 

The signature check itself is a no-op whenever the resolved organization has no configured secret: [3](#0-2) 

This is a documented, supported configuration state — `docs/setup.md` explicitly calls the webhook secret "optional", and the shipped secrets templates leave `webhook_secret` blank by default: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (because the *authenticating* organization has no secret), `WebhooksController#create` dispatches the entire attacker-controlled JSON body to handlers, which derive the *acted-upon* target from a different field of the same payload — `repository.full_name` (unrelated to `repository.owner.login` used for authentication) or, for membership events, `organization.login` combined with an arbitrary `team` and `member` object: [6](#0-5) [7](#0-6) 

This breaks the intended binding `organization that authenticated == repository/team acted upon`. Nothing ties the "authentication passed for org X (because X has no secret)" fact to "the mutation must also target org X's resources." An attacker who knows (or brute-forces) that some configured org in a multi-org Shipit install has no `webhook_secret` can:
1. Send a forged `push`/`status`/`check_suite` event naming that org as `repository.owner.login`, but with `repository.full_name` set to a completely different, unrelated repository tracked by Shipit, triggering `GithubSyncJob`, status writes, or check-run refreshes against that repository — a cross-repository, unauthenticated action.
2. Send a forged `membership` event naming that org, with a `member.login` equal to the attacker's own (already-registered) Shipit login and a `team` payload matching a team present in `Shipit.github_teams`, causing `Team#add_member` to record the attacker as a member: [8](#0-7) 

Shipit's authorization gate then trusts that same `Team`/`Membership` state: [9](#0-8) [10](#0-9) 

An attacker who can log in through Shipit's normal GitHub OAuth (unprivileged, no team membership required to complete OAuth) but is *not* actually a member of any required GitHub team can forge a `membership` webhook to add their own `User` record to a `Team` counted in `Shipit.github_teams`, and thereby pass `authorized?` — gaining access to the whole application without ever being added to the real GitHub team.

### Impact Explanation
This maps to the report's Critical/High categories: escalation into `Shipit.github_teams` authorization (High), and, via the push/status path, unauthorized cross-repository job execution/state writes (bordering on Critical "unauthorized deploy" since `GithubSyncJob`/status updates feed directly into deploy eligibility). The root cause mirrors the external report exactly: a verification step is supposed to bind two related fields (authenticated org ↔ acted-upon resource), but the mapping/field actually used for the mutation is never covered by — and is independent from — the field used to select/skip the signature check.

### Likelihood Explanation
Requires only: (a) a multi-org Shipit deployment where at least one configured GitHub App organization has no `webhook_secret` (an explicitly documented, supported, and template-default configuration), and (b) network access to `POST /webhooks`. For the team-escalation path, the attacker additionally needs a normal (unprivileged) Shipit session obtained through standard GitHub OAuth login, which the code itself permits before the `authorized?` check runs. No `ApiClient` token, `github_access_token`, private key, or webhook secret is needed.

### Recommendation
- Do not let `webhook_secret` presence silently disable verification per-organization; require a secret (or a single globally enforced default) for every configured GitHub App, and reject webhooks for organizations lacking one instead of treating them as implicitly verified in `GitHubApp#verify_webhook_signature`.
- Bind the field used to select the verifying organization to the field(s) later used to identify the acted-upon repository/team; e.g., after verification, re-derive and cross-check `repository.full_name`'s owner (and `organization.login` for membership events) against the same organization whose secret validated the signature, rejecting mismatches.
- For `MembershipHandler`, additionally verify that the `organization.login` in the payload matches the `Team#organization` already on file rather than trusting the forged payload verbatim.

### Proof of Concept
Assume a multi-org Shipit install where `orgWithoutSecret` has `webhook_secret: nil` (per the documented/template-default configuration) and Shipit tracks a stack for `victim-org/victim-repo`. An unauthenticated attacker:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "orgWithoutSecret" },
    "full_name": "victim-org/victim-repo"
  }
}
```

`Shipit.github(organization: 'orgWithoutSecret')` resolves an app with `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally (no `X-Hub-Signature` header needed), and `PushHandler` runs `Repository.from_github_repo_name('victim-org/victim-repo')`, enqueuing `GithubSyncJob` for a stack the attacker never authenticated against.

Similarly, for privilege escalation, after obtaining an ordinary Shipit session via GitHub OAuth (`login`), the attacker posts:

```
POST /webhooks HTTP/1.1
X-Github-Event: membership

{
  "action": "added",
  "team": { "id": <id_of_required_team>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "orgWithoutSecret" },
  "member": { "login": "attacker-login" }
}
```

This adds `attacker-login`'s `User` to the `Team` referenced by `Shipit.github_teams`, after which `User#authorized?` returns `true` and `force_github_authentication` grants full application access.

**Uncertainty:** I could not fully confirm from the indexed context whether `Shipit.github(organization:)` enforces case/format restrictions beyond what's shown, or whether any additional global default `webhook_secret` fallback exists outside `lib/shipit/github_app.rb`; a full session against the repository would be needed to rule out an additional safeguard not present in the indexed files.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
