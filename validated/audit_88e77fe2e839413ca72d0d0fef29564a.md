### Title
Caller-selected `has_risks` scope lets any address restamp LTV while freezing the liquidation tuple, bypassing the health-factor gate - ([File: contracts/controller/src/risk/params.rs])

### Summary
The CVE-2018-11783 class is "attacker-controlled metadata reaches downstream consumers because the component failed to strip/reset it." The analog in XOXNO Lending is `update_account_threshold`: it takes a caller-supplied `has_risks: bool` that selects `RiskRefreshScope::LtvOnly` vs `FullTuple`. Any authenticated address — not the account owner — chooses the scope. With `has_risks=false`, stored `loan_to_value` is restamped to current config while `liquidation_threshold`, `liquidation_bonus`, and `liquidation_fees` are left stale, and the HF >= 1.05 gate that normally protects tuple changes is skipped entirely. The caller's scope flag is trusted input that should not be attacker-selectable per account, yet it directly controls which risk parameters the restamp "strips" versus keeps.

### Finding Description
`require_authorized_caller` only performs `caller.require_auth()` plus a flash-loan check — there is no ownership or relayer restriction tying `caller` to the `account_ids` being restamped (contracts/controller/src/risk/validation.rs:13). `update_account_threshold` maps the caller's `has_risks` flag to `RiskRefreshScope` (contracts/controller/src/risk/params.rs:132-136) and `refresh_supply_risk_params` unconditionally writes `position.loan_to_value = effective_config.loan_to_value`, applying the gated liquidation tuple only under `FullTuple` (params.rs:35-38). `apply_gated_liquidation_params` and `clears_min_hf` enforce HF >= 1.05 only when a liquidator-favoring change would land and debt exists (params.rs:68-93, 103-119); under `LtvOnly` neither this per-asset check nor the final `hf >= THRESHOLD_UPDATE_MIN_HF_RAW` assertion (params.rs:221-234) runs because `borrow_positions` is never even loaded (params.rs:170-174).

After governance updates a spoke asset (e.g., raises `ltv` while also lowering `liquidation_threshold`, or raises `ltv` independently while an account still holds an older, higher stored threshold tuple), an attacker calls `update_account_threshold(caller, false, [own_account_id])`. Result: the account gains the new higher LTV for the `ltv_collateral >= total_debt` borrow gate (validation.rs:41-45) while retaining the older, more favorable liquidation threshold/bonus/fees — a parameter combination that never existed in any single governance configuration. Conversely the attacker can never be forced into `FullTuple` — nobody else can restamp the tuple on the account either, since any caller may choose `LtvOnly`, so the stale tuple persists until the attacker voluntarily supplies/withdraws (supply.rs:288-296, 356-366 restamp `FullTuple` on legs).

### Impact Explanation
The attacker borrows more than the protocol's current risk parameters intend: the borrow gate uses restamped (higher) LTV, while liquidation protection uses stale (higher) threshold and lower bonus/fees. The position can sit at a health factor that current config would consider unsafe yet not be liquidatable at the intended terms, and when finally liquidated pays a smaller bonus — a direct path to protocol insolvency and theft of user funds via undercollateralized borrows that current parameters were meant to forbid.

### Likelihood Explanation
Reachable by a single unprivileged address whenever governance changes `ltv` or the liquidation tuple on a listed spoke asset — a routine operation (`EditAssetInSpoke`). No flash loan, no oracle manipulation, and no owner signature required. Severity is bounded by the delta between stale and current tuples, so Medium rather than High, but the exploit is deterministic and repeatable across all of the attacker's accounts.

### Recommendation
Remove the caller-controlled scope split: either always run `FullTuple` in `update_account_threshold`, or restrict `LtvOnly` to internal flows where borrowing is impossible afterward. Alternatively, gate `LtvOnly` calls to the account owner (NFT owner) and add a keeper-style path that restamps the full tuple with the HF check for third parties.

### Proof of Concept
1. Governance executes `EditAssetInSpoke` raising `ltv` (and/or lowering `liquidation_threshold`) on asset A.
2. Attacker's account already supplies A with the old stored tuple (`ltv_old`, `threshold_old` > `threshold_new`, `bonus_old` < `bonus_new`).
3. Attacker calls `update_account_threshold(attacker, /*has_risks*/ false, vec![attacker_account])`.
4. Position now has `ltv_new` + `threshold_old`/`bonus_old`/`fees_old`.
5. Attacker calls `borrow` up to `ltv_new`-weighted capacity; `require_post_pool_risk_gates` passes using `ltv_new`, while the liquidation snapshot still prices HF with `threshold_old`. The position is healthier-looking and more borrow-capable than any single governance configuration permits.

Uncertainty note: I could not fully trace whether a separate keeper or forced `FullTuple` restamp path exists elsewhere in the controller (e.g., inside `liquidate` or `update_indexes` call sites) that would let a third party overwrite the stale tuple against the attacker's will; if such a forced restamp exists on every borrow-relevant path, the impact narrows to a narrower window, but nothing in `update_account_threshold` itself prevents the described state.
