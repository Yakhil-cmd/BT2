### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` webhook lookup enables unauthorized deploy unlock - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook against the GitHub App configuration of the **organization named in the payload's `repository.owner.login`** field [1](#0-0) [2](#0-1) . Every other handler in the codebase re-derives the target repository from that *same* `repository.full_name` field before writing anything, keeping the "authenticated organization" and the "repository written" bound together [3](#0-2) [4](#0-3) .

`StatusHandler`, however, breaks this binding: its `process` method ignores `repository` entirely and updates **every** `Commit` row in the whole database whose `sha` matches the payload, regardless of which repository/stack that commit belongs to [5](#0-4) .

### Finding Description
The equality the engine is supposed to preserve is:

`organization authenticated by verify_webhook_signature (repository.owner.login)` == `repository/stack whose state is mutated by the handler`

For `StatusHandler` this equality does not hold. The handler's `params` block only requires `sha`, `state`, and optional cosmetic fields — no `repository` scoping at all [6](#0-5) . Its `process` method resolves target rows purely by `Commit.where(sha: params.sha)`, a global, unscoped lookup across all `Commit` records tracked by the instance, and then calls `commit.create_status_from_github!(params)` on each one [5](#0-4) .

GitHub's Statuses API allows any account with write/collaborator access to a repository to POST a commit status for an **arbitrary 40-character SHA on that repository** — GitHub does not require the SHA to actually exist in that repository's history. Consequently, an attacker who legitimately controls one repository tracked by this Shipit instance (with its own correctly configured `webhook_secret`, so `verify_signature` passes normally) can:
1. Discover or guess the SHA of a commit belonging to a *different*, victim stack/repository tracked by the same Shipit instance (commit SHAs of public repos are trivially discoverable).
2. Create a GitHub `status` event on their own controlled repository using that victim SHA and a `state: "success"` payload.
3. GitHub signs this webhook with the attacker's own repo's webhook secret; `verify_signature` looks up `Shipit.github(organization: repository_owner)` using the attacker's own org, which succeeds, because the HMAC is valid for that (attacker-controlled) secret and body [1](#0-0) .
4. `StatusHandler#process` then updates the status of **any/all** `Commit` rows across the whole instance matching that SHA — including the commit belonging to the victim's stack — via `create_status_from_github!` [5](#0-4) .

This is precisely the "organization that authenticated versus the repository that is written" binding break: the signature only proves the payload originated from a webhook configured for the attacker's org/repo, but the write touches Commit state belonging to a repository/stack the attacker never authenticated for.

### Impact Explanation
Commit/CI statuses gate Shipit's deploy readiness UI and, depending on stack configuration, its required-status-check enforcement for merges/deploys. By forging a passing `status`/`deployable_status` for a specific commit in a repository the attacker does not control, the attacker can flip the perceived CI state of a commit in a **different repository**, potentially unlocking a deploy or merge gate that should have required a real, valid CI signal from GitHub for that repository. This is a cross-repository write of authoritative deploy-readiness state and directly maps to the "cross-repository writes" / "unauthorized deploy" impact tier defined in scope.

### Likelihood Explanation
Exploitation requires only: (a) administrative/webhook control of any single repository already tracked by the target Shipit instance (an unprivileged condition relative to any other tracked stack — it does not require access to the victim repository, the Shipit session, or any API token), and (b) knowledge of a target commit SHA, which is public for public repositories. No privileged Shipit credential, GITHUB_TOKEN, or webhook secret belonging to the victim organization is needed.

### Recommendation
Scope `StatusHandler#process` (and any other handler that resolves records purely by content hash) to the repository named in the webhook payload, e.g., restrict the `Commit` lookup to `stacks` whose `repository_id` matches `Repository.from_github_repo_name(params.repository.full_name)`, mirroring the pattern already used by `Handler#stacks` / `Handler#repository_name` [3](#0-2) , so the authenticated organization/repository from `verify_signature` and the repository whose Commit rows get mutated are always the same entity.

### Proof of Concept
1. Attacker registers/owns Repo A (`attacker-org/repo-a`), which is tracked as a Shipit stack with its own webhook secret configured correctly.
2. Attacker identifies commit SHA `deadbeef...` that belongs to a commit tracked in victim Repo B's stack (`victim-org/repo-b`), e.g., from the public GitHub commit history.
3. Attacker (as a collaborator on Repo A) uses GitHub's Statuses API (or the GitHub UI/App) to create a `status` webhook event on Repo A with `sha: "deadbeef..."`, `state: "success"`, `context: "ci/required-check"`.
4. GitHub delivers the webhook to Shipit's `/webhooks` endpoint, correctly signed for Repo A/attacker-org.
5. `WebhooksController#verify_signature` succeeds using `Shipit.github(organization: "attacker-org")`.
6. `StatusHandler#process` executes `Commit.where(sha: "deadbeef...")`, matches the commit belonging to Repo B's stack, and calls `create_status_from_github!`, recording a forged "success" CI status against Repo B's commit — with no relation whatsoever to the actually-authenticated Repo A/attacker-org.
