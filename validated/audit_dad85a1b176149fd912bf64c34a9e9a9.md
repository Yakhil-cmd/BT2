### Title
Webhook signature is bound to `repository.owner.login`/`organization.login`, but every handler acts on the attacker-controlled `repository.full_name` — allowing cross-repository writes from any onboarded organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret used to authenticate an inbound GitHub webhook based on `repository.owner.login` (falling back to `organization.login`), [1](#0-0) [2](#0-1) . Once the signature check passes, every downstream `Handler` subclass resolves the target repository/stack from a *different* field of the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')` [3](#0-2) . This is the same class of bug as the report's "unchecked value used to authorize a fund transfer to a different address than the one verified" — here, the field verified by the signature (`repository.owner.login`) is not equal to the field the code actually acts on (`repository.full_name`).

### Finding Description
`Shipit.github(organization:)` resolves a per-organization webhook secret from `secrets.github[organization]` [4](#0-3) . Any organization/repository owner that has been onboarded onto the Shipit instance (i.e. has its own configured GitHub App/webhook secret) can compute a valid `X-Hub-Signature` for a JSON payload it fully controls, since the signature is just an HMAC over the raw POST body using that organization's own secret [5](#0-4) .

Nothing ties the `repository.owner.login` field (used only to pick which secret to verify with) to the `repository.full_name` field (used by every `Handler` to find the `Repository`/`Stack` to act on) [3](#0-2) . An attacker who controls the webhook secret for `OrgA` can therefore submit a payload where `repository.owner.login == "OrgA"` (so `verify_signature` succeeds using `OrgA`'s secret) but `repository.full_name == "OrgB/victim-repo"`. The handler layer never re-checks that `full_name`'s owner matches the authenticated `repository_owner`; it simply calls `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and acts on whatever `Stack`s are returned [6](#0-5) .

This breaks the binding: `organization authenticated by signature == repository actually written to`. Concretely reachable handlers that perform state changes purely from `repository.full_name`:
- `PushHandler#process` enqueues `GithubSyncJob` against any matching (non-archived) stack for the forged repo's branch [7](#0-6) , which fetches/appends commits from GitHub into `OrgB`'s stack.
- `PullRequest::OpenedHandler`, `LabeledHandler`, `LabelCapturingHandler`, `ClosedHandler` archive/unarchive/create Review Stacks and mutate PR-labels for `OrgB`'s repository based solely on `Repository.from_github_repo_name(params.repository.full_name)` [8](#0-7) [9](#0-8) .

In all these cases the "signature verified" identity (`OrgA`) and the "repository acted upon" identity (`OrgB/victim-repo`) can diverge, because GitHub itself never generated this payload — the attacker crafted it and signed it with their own legitimate secret.

### Impact Explanation
This allows an attacker who controls one onboarded organization's GitHub App/webhook secret to trigger unauthorized state-changing actions (sync/deploy pipeline triggers via `GithubSyncJob`, Review Stack provisioning/archival, PR label/state mutation) against a completely different organization's repositories/stacks that they have no access to — a cross-repository write reachable without any Shipit session, `ApiClient` token, or repository write access on the target repo, satisfying the "cross-repository writes" Critical impact bucket.

### Likelihood Explanation
Likelihood is High for any Shipit deployment that hosts more than one organization/GitHub App config (the multi-org `secrets.github` schema is a supported, documented feature [10](#0-9) ). Any tenant with legitimate, low-privilege access to configure their own organization's webhook secret can exploit this against every other tenant on the same instance without needing to compromise any secret belonging to the victim organization.

### Recommendation
After signature verification, re-derive the authenticated organization and enforce that `payload.dig('repository','owner','login')` (or `organization.login`) matches the owner segment of `payload.dig('repository','full_name')` before any handler resolves a `Repository`/`Stack`. Alternatively, have `Handler#repository_name` and `#stacks` be scoped by the already-authenticated `repository_owner` rather than trusting the raw `full_name` field independently, so the field the signature covers is always the field the code acts on.

### Proof of Concept
1. Onboard/legitimately control `OrgA` on a multi-tenant Shipit instance, giving you `OrgA`'s webhook secret.
2. Craft a `push` (or `pull_request`) webhook JSON body with:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
   - `ref`/`after` (or PR fields) targeting a branch/PR that exists on `OrgB`'s Shipit stack.
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, raw_body)`.
4. POST to `/github/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `GithubSyncJob` for `OrgB`'s stack [7](#0-6) , triggering unauthorized sync/deploy activity on a repository the attacker does not own.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
