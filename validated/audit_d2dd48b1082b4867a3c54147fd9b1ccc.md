Confirmed: when there aren't enough non-dust base outputs to cover a payment message's target amount, the code path returns `cb('not enough funds for ' + target_amount + ' bytes')` at line 1232, which bounces the trigger. This is a strong parallel to the reported vulnerability.### Title
AA byte balance includes sub-60-byte dust outputs that cannot actually be spent, causing bounced triggers and stuck AA funds - ([File: aa_composer.js])

### Summary
An Autonomous Agent's tracked base-asset (bytes) balance, exposed to oscript via `balance[base]` and used internally for bookkeeping (`aa_balances`), includes every unspent output regardless of size. However, when the AA actually composes a payment response, the code that selects spendable inputs explicitly excludes base-asset outputs smaller than `FULL_TRANSFER_INPUT_SIZE` (60 bytes) to prevent dust-spam attacks. This mirrors the reported Rio issue where ETH below a minimum threshold is counted in protocol accounting but can never be "scraped"/spent, leading to unusable funds and potential inability to fulfill payment obligations that rely on that balance.

### Finding Description
When constructing the outputs used to satisfy an AA payment message, `completePaymentPayload`'s `readStableOutputs`/`readUnstableOutputsSentByAAs` helper functions query spendable outputs with an explicit filter for the base asset: [1](#0-0) 

The comment explicitly documents the intent: "byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack." This filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) applies only to the `base` asset and only when selecting inputs to fund an outgoing payment.

Meanwhile, the AA's tracked balance (`aa_balances.balance`, exposed to formulas via `balance[address][asset]`) is computed by simply summing *all* unspent outputs for the address with no size filter, both at AA-definition time and in the periodic consistency check: [2](#0-1) [3](#0-2) 

The formula evaluator reads this same unfiltered balance for `balance[...]` expressions: [4](#0-3) 

If an unprivileged unit poster sends the AA many small (dust, e.g., 10-byte) base-asset payments over time (which the AA "silently accepts" per common patterns seen in `test/samples/*.oscript`, e.g. accepting `trigger.output[[asset=base]]`), those dust outputs raise `balance[base]` (and any AA logic that reads `balance[base]` to decide payout amounts) but can never be used as spendable inputs when the AA tries to actually send bytes out, because they fall below the 60-byte threshold.

### Impact Explanation
When an AA's oscript logic computes a payout using `balance[base]` (a very common pattern for pro-rata withdrawal/divestment logic, as seen throughout the test samples, e.g. `round($investor_share * balance[base])`), and the accumulated dust outputs make up a non-trivial fraction of the tracked balance, the actual spendable base outputs found by `readStableOutputs`/`readUnstableOutputsSentByAAs` can be strictly less than the `target_amount` required by the payment message. In that case `sendUnit`'s `completePaymentPayload` reaches: [5](#0-4) 

and, for the base asset, falls through to `return cb('not enough funds for ' + target_amount + ' bytes')`, which propagates up and causes `bounce(err)` — the AA response is bounced. This directly matches the report's impact categories: "unused bytes" that are permanently uncollectable as real spendable input, and legitimate users' triggers (and by extension any tokens/state changes tied to that trigger) being bounced/failed because the AA cannot fulfill a payout that its own accounting says it can afford. Over time, as dust outputs accumulate (each new trigger can add another sub-60-byte remainder/change output too, since change outputs as small as `storage_size` can be created), an increasing fraction of AA byte balance can become permanently unspendable, degrading the AA's ability to pay out state-tracked balances/rewards and effectively freezing those bytes inside the AA address.

### Likelihood Explanation
Likelihood is moderate: exploitation does not require any privileged access — any address can send the AA base-asset payments of any size (as small as a few bytes above the bounce-fee minimum for triggering messages, or dust attached alongside a data message that the AA doesn't route through the payment/bounce-fee path), and dust accumulation is a natural byproduct of repeated interaction, arbitrage, or a griefer deliberately sending many tiny outputs. The threshold (60 bytes) is small in absolute terms, so triggering the specific "not enough funds" bounce requires the accumulated dust to represent a large enough fraction of an on-demand payout, which is more likely in AAs whose payouts are calculated as an exact/whole fraction of `balance[base]` (e.g., final-liquidation/divest patterns) rather than AAs that always leave slack.

### Recommendation
- When computing `balance[base]` (or any `assocBalances` used in state logic/oscript), exclude or separately report unspendable dust outputs (those below `FULL_TRANSFER_INPUT_SIZE`), so that AA logic and `checkBalances` consistency checks reflect actually spendable funds, not just cumulative unspent amounts.
- Alternatively, allow the AA composer to opportunistically consolidate ("sweep") multiple dust outputs together with a spendable one in the same payment message so their combined negative cost is offset, instead of unconditionally excluding them from being ever selected.
- Document/expose a formula primitive (e.g., `spendable_balance[...]`) distinct from `balance[...]` so AA authors can write payout logic that never relies on unspendable dust.

### Proof of Concept
1. An attacker or the natural operation of the AA causes multiple sub-60-byte base-asset outputs to accumulate at the AA's address (e.g., repeatedly triggering the AA with tiny byte amounts that are accepted and added to `var[$base_key]`/`aa_balances` as in the common "silently accept coins" pattern seen in `test/samples/a_bank_without_percent.oscript` and `test/samples/order_book_exchange.oscript`, where `if (trigger.output[[asset=base]] > 10000)` is the threshold used before crediting a *tracked variable*, but the underlying `aa_balances.balance` in `insertAADefinitions`/`checkBalances` counts every output regardless of size).
2. Suppose the AA's genuine `balance[base]` (per `aa_balances`) reaches, say, 100,059 bytes, of which 59 bytes are locked in a single dust output below the 60-byte `FULL_TRANSFER_INPUT_SIZE` threshold, and the rest are spendable.
3. A legitimate withdrawal request computes `amount = balance[base]` (or a fraction thereof) intending to pay out the full recorded balance.
4. `completePaymentPayload` calls `readStableOutputs`, which SQL-filters out the dust output (`amount>=FULL_TRANSFER_INPUT_SIZE`), so `iterateUnspentOutputs` can never accumulate the full `target_amount`.
5. `bFound` remains false after checking both stable and AA-response outputs; since `asset` is null (base) the code executes `return cb('not enough funds for ' + target_amount + ' bytes')` at aa_composer.js:1232, which bounces the trigger — the user's request fails even though the AA's own state believes it has sufficient balance, and the dust bytes remain permanently stuck at the AA address.
