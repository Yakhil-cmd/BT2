### Title
Stale `is_spent` flag from a later-voided spending unit can permanently undercount vote balances used for governance tallies - ([File: main_chain.js])

### Summary
The bug reported for Lombard is a class of "premature/irreversible state mutation caused by an unconfirmed/unverified event that later turns out to be invalid, causing legitimate future processing to be permanently rejected." The closest reachable analog in `ocore` is the `is_spent` bookkeeping used for `system_votes` balance tallying in `main_chain.js`: an *unstable*, not-yet-final unit that spends a stable output immediately sets `outputs.is_spent=1` [1](#0-0) , but if that spending unit is later found to be non-serial and demoted to `final-bad` during stabilization, the `is_spent` flag on the original output is never rolled back [2](#0-1) .

### Finding Description
When a unit is written, any output it spends is immediately flagged `is_spent=1` regardless of whether the spending unit is confirmed/stable or even ultimately valid [3](#0-2) . During main-chain stabilization, `propagateFinalBad()` demotes to `final-bad` any units that spent inputs which are discovered to be non-serial/invalid, and this can cascade to future units built on top of them [2](#0-1) . However, nothing in this final-bad propagation path resets `is_spent=0` on the original outputs that were spent by the now-voided (`final-bad`) unit.

The repository's own diagnostic tool, `tools/compare_vote_balances.js`, documents this exact discrepancy: the "OLD" balance-computation method (`is_spent=0` stable-good outputs plus a `spent_rows` correction for still-good unstable spenders) undercounts a voter's balance whenever "a future unstable unit spent their stable output and was later propagated to final-bad, leaving `is_spent=1` on the output while no good unit claims it in `spent_rows`" [4](#0-3) . This is precisely analogous to the Lombard bug: an unconfirmed/unverified event (an unstable, later-invalidated spending unit — the ocore counterpart of an unconfirmed notary session) is allowed to permanently flip a persistent "already used/paid" flag, and no later correction reverses it once the underlying event is proven invalid.

### Impact Explanation
`system_votes`/vote balance tallies feed into ocore's on-chain governance (system-parameter voting) using stable-good outputs and the `is_spent` flag [5](#0-4) . If any node/tool computes voter balances using the "OLD" `is_spent`-based method illustrated in `compare_vote_balances.js`, a griefer can craft a transient unstable spend of a voter's own stable output that gets propagated to `final-bad`. This permanently zeroes out (undercounts) that voter's counted balance for governance purposes, even though the address never lost real funds — effectively disenfranchising the address from system voting, a form of fund/vote "freezing" analogous to the unstake request being permanently blocked from payout.

### Likelihood Explanation
This requires a party to construct a real but non-serial (invalid-sequence) unit spending its own stable output, then let honest nodes finalize main-chain stabilization so the spender is marked `final-bad`. Creating a losing (non-serial) double-spend against one's own output is straightforward and inexpensive to any single unit poster, matching the "unprivileged unit poster" reachability constraint, and the effect is deterministic since `is_spent` is never reset on `final-bad` propagation [6](#0-5) .

### Recommendation
When a unit's sequence is propagated to `final-bad` (in `propagateFinalBad()`), also reset `is_spent=0` on any outputs whose only spender is that now-`final-bad` unit, or compute voter/spent balances using the "NEW" method already implemented in `tools/compare_vote_balances.js` — i.e., derive spent status via `NOT EXISTS` against `good`, `is_stable=1` spenders rather than trusting the persisted `is_spent` flag [7](#0-6) .

### Proof of Concept
1. Address A holds a stable, good output O.
2. A crafts two conflicting units U1 and U2 that both spend O (a double-spend), where U1 will end up `good` and U2 `temp-bad`→eventually `final-bad` once conflicts resolve against a stable competitor.
3. When U2 is written, `writer.js` immediately sets `outputs.is_spent=1` on O regardless of U2's eventual validity [3](#0-2) .
4. During stabilization, `propagateFinalBad()` marks U2 (and any units built on it) `final-bad`, but never restores `is_spent=0` on O [6](#0-5) .
5. A vote-balance calculation using the "OLD" `is_spent=0`-filtered query (as reproduced in `balancesOldWay()`) will now omit O from A's balance even though O is unspent and O's legitimate spend never happened, undercounting A's governance voting power [8](#0-7) .

async function balancesOldWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const bal_rows = await db.query(`
		SELECT address, SUM(amount) AS balance
		FROM outputs
		LEFT JOIN units USING(unit)
		WHERE address IN(${strAddresses}) AND is_spent=0 AND asset IS NULL AND is_stable=1 AND sequence='good'
		GROUP BY address`);

	const balances = {};
	for (const { address, balance } of bal_rows)
		balances[address] = balance || 0;

	const spent_rows = await db.query(`
		SELECT inputs.address, SUM(outputs.amount) AS spent_balance
		FROM units
		CROSS JOIN inputs USING(unit)
		CROSS JOIN outputs ON src_unit=outputs.unit AND src_message_index=outputs.message_index AND src_output_index=outputs.output_index
		CROSS JOIN units AS output_units ON outputs.unit=output_units.unit
		WHERE units.is_stable=0 AND +units.sequence='good'
			AND +output_units.is_stable=1 AND +output_units.sequence='good'
			AND inputs.address IN(${strAddresses}) AND type='transfer' AND inputs.asset IS NULL
		GROUP BY inputs.address`);

	for (const { address, spent_balance } of spent_rows) {
		if (balances[address])
			balances[address] += spent_balance;
		else
			balances[address] = spent_balance;
	}

	return balances;
}

async function balancesNewWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const rows = await db.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);

	const balances = {};
	for (const { address, balance } of rows)
		balances[address] = balance || 0;

	return balances;
}
