### Title
Cross-tenant Team membership escalation via `Team.find_or_create_by!(github_id:)` in `MembershipHandler#find_or_create_team!` - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify against using `repository_owner`, which for a `membership` event falls back to `params.dig('organization','login')` since there is no `repository` key in the payload. This means the attacker's own org's `webhook_secret` legitimately verifies a payload whose `team.id` can reference a `Team` row that belongs to a completely different, victim organization, and `find_or_create_team!` never checks that the persisted `team.organization` matches the organization that just verified the request.

### Finding Description
The broken binding is: `organization_that_verified_signature (params.organization.login, verified via Shipit.github(organization: repository_owner).verify_webhook_signature)` must equal `team.organization` (the value already persisted on the `Team` row matched by `github_id`) before any mutation is allowed — but no code enforces this.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (`app/controllers/shipit/webhooks_controller.rb:59-62`). For `membership` events there is no `repository` key, so `repository_owner` == attacker's own organization login, and `Shipit.github(organization: repository_owner)` resolves to the attacker's own app config, so `verify_webhook_signature` succeeds using the attacker's own valid `webhook_secret`. [1](#0-0) [2](#0-1) 
2. `MembershipHandler#process` calls `find_or_create_team!`, then `User.find_or_create_by_login!(params.member.login)`, then for `action == 'added'` calls `team.add_member(member)`. [3](#0-2) 
3. `find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end`. The block only runs on creation of a new record; if a `Team` row already exists with that `github_id` (created earlier for another organization, e.g. via `Team.find_or_create_by_handle` or a prior legitimate membership webhook from org B), the existing row is returned unchanged — `team.organization` is never re-checked or reassigned. [4](#0-3) 
4. `team.add_member(member)` then appends the attacker's `User` (created from `member.login`, which the attacker fully controls) to that Team's memberships. [5](#0-4) 
5. If that `Team` is one of `Shipit.github_teams`, `User#authorized?` becomes true for the attacker (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`), granting access scoped to the victim organization's authorization group. [6](#0-5) 

No existing guard closes this gap: `verify_signature` only proves the request was signed by *some* configured organization, not that it's the organization owning the target `Team`; `find_or_create_team!` performs no equality check between `params.organization.login` and the persisted `team.organization` on the matched row.

### Impact Explanation
An attacker who registers/owns any GitHub organization onboarded to this Shipit instance can add themselves (or any GitHub login they choose as `member.login`) as a `Membership` on any pre-existing `Team` row, by guessing/observing its numeric `github_id`. If that team is listed in `Shipit.github_teams`, this directly escalates the attacker into the authorization group for a stack/tenant they do not own, satisfying the "High - escalation into `Shipit.github_teams` authorization" category. The action is repeatable against any known victim `Team.github_id`, cross-tenant, and requires no interaction from the victim.

### Likelihood Explanation
Requires: (a) Shipit configured for multiple GitHub organizations, each with its own `github_app_config`/`webhook_secret`; (b) attacker controls at least one onboarded organization (a low bar — Shipit is designed to onboard arbitrary orgs); (c) a target `Team.github_id` value, which is a GitHub team ID, potentially discoverable/guessable or observable via public GitHub team pages/API for the victim org. The attacker needs no Shipit credentials — only their own legitimate webhook secret for their own org, which they possess by design. This is a plausible, low-cost, and repeatable attack for anyone operating a second GitHub organization.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and `process`), compare `params.organization.login` against the persisted `team.organization` after fetching an existing row and reject (or no-op) the request if they differ, rather than only setting `organization` inside the creation block. Additionally, `WebhooksController#repository_owner`/`verify_signature` should not implicitly trust `organization.login` from the payload as authoritative proof of ownership over pre-existing cross-referenced records (`team.id`) — verification of organization identity should be paired with an authorization check that the acting organization actually owns the resource being mutated.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership event from org A cannot add members to a Team owned by org B" do
  victim_team = shipit_teams(:shopify) # organization: 'shopify', github_id: 42
  assert_equal 'shopify', victim_team.organization

  attacker_org = 'attacker-org'
  # simulate signature verified with attacker_org's own webhook_secret
  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => 'x', 'slug' => 'x', 'url' => 'x' },
    'organization' => { 'login' => attacker_org },
    'member' => { 'login' => 'attacker_login' },
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).call

  attacker_user = Shipit::User.find_by(login: 'attacker_login')
  assert Shipit::Membership.exists?(team: victim_team, user: attacker_user)
  assert_equal 'shopify', victim_team.reload.organization # organization diverges from verifying org 'attacker-org', proving the binding is never reconciled
end
```
