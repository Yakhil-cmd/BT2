### Title
`PullRequest::OpenedHandler#provision?` operator-precedence flaw bypasses `review_stacks_enabled` for `prevent_with_label` repositories - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`provision?` is written as `A && B || C || D` where only the first disjunct (`review_stacks_enabled && allow_all?`) is gated by `review_stacks_enabled`; the third disjunct, `(provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`, is evaluated independently of `review_stacks_enabled` due to Ruby's `&&`/`||` precedence. Any repository configured with `provisioning_behavior == prevent_with_label` will have `provision?` return `true` for an unlabeled pull request even when `review_stacks_enabled == false`, causing `ReviewStackAdapter#create!` to provision a stack and queue attacker-controlled branch content for execution.

### Finding Description
The broken binding: `repository.review_stacks_enabled (false) == the gate applied to the prevent_with_label branch of provision?` — this equality is false; the gate is never applied to that branch.

`provision?` is defined as: [1](#0-0) 

Due to Ruby operator precedence (`&&` binds tighter than `||`), this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first term. When `provisioning_behavior` is `prevent_with_label` and the PR carries no label, the third term alone (`prevent_with_label? && !has_label?`) evaluates to `true`, making the whole OR-chain `true` — regardless of `review_stacks_enabled`.

Call path: `process` calls `respond_to_pull_request_opened?`, which calls `provision?`: [2](#0-1) [3](#0-2) 

Once `provision?` returns true, `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` runs, and `create!` builds a `ReviewStack` with `branch: params.pull_request.head.ref` taken directly from the attacker's fork, with no re-check of `review_stacks_enabled`: [4](#0-3) 

The stack is then queued via `Shipit::ReviewStackProvisioningQueue.add(stack)`, which downstream reads `shipit.yml` at the attacker's branch and executes its steps via `Command`/`PTY.spawn` — outside this engine's own webhook-authorization scope, this is the standard review-stack provisioning task flow.

No other guard intervenes: `respond_to_pull_request_opened?` only checks `params.action == "opened"` before calling the flawed `provision?`; there is no separate `review_stacks_enabled` check anywhere else in `OpenedHandler` or `ReviewStackAdapter`. Signature verification (`verify_signature`) and `ExplicitParameters` schema validation authenticate that the payload came from the configured GitHub webhook but do not constrain the semantic decision inside `provision?`; they do not prevent this logic bug.

### Impact Explanation
An unprivileged GitHub user who can open a pull request on a repository configured with `provisioning_behavior: prevent_with_label` — even though that repository has explicitly opted OUT of review stacks (`review_stacks_enabled: false`) — can get Shipit to create a `ReviewStack` for their fork branch and queue it for provisioning. The provisioning task reads `shipit.yml` from the attacker's branch and executes its steps via `Command#start`/`PTY.spawn`, which is attacker-controlled shell execution on the deploy host. This is repeatable per pull request/branch, matches the Critical category (RCE via `Command`/`PTY.spawn`), and affects any tenant repository with this configuration.

### Likelihood Explanation
Preconditions: `repository.review_stacks_enabled == false`, `repository.provisioning_behavior == prevent_with_label`, and the PR carries no label matching `provisioning_label_name` — a plausible/default configuration state for repositories that never intended to enable review stacks (e.g., `prevent_with_label` may be a leftover or default value while `review_stacks_enabled` is false). Attacker cost is a normal `opened` pull-request webhook event from their own fork; no secrets, tokens, or elevated permissions are required. Feasibility is high and trivially repeatable.

### Recommendation
Add explicit parentheses/grouping so `review_stacks_enabled` gates the entire disjunction, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

2. Construct `params` for an `opened` action PR with `head.ref = "pwn-branch"` and `labels: []` (no matching label).
3. Instantiate `OpenedHandler.new(params)` and assert `handler.send(:provision?) == true` — demonstrating the equality `review_stacks_enabled (false) == gate applied` is violated (should be `false` but is `true`).
4. Assert that calling `process` invokes `ReviewStackAdapter#create!` and that `ReviewStack.create!` is called with `branch: "pwn-branch"`.
5. Stub `Shipit::ReviewStackProvisioningQueue.add` / `TaskCommands#perform` / `Command#start` to capture the command line that would reach `PTY.spawn`, asserting it derives from the attacker's branch content — demonstrating execution trust is violated for a repository that never enabled review stacks.
