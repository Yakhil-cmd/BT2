### Title
Liquidation of a borrower's healthy-market debt is permanently blocked when any other asset held by that borrower has a broken oracle - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` evaluates a borrower's *entire* position (every collateral asset the borrower currently holds, not just the asset pair being liquidated) before it will process a partial repay/seizure. Price resolution for that full set uses `unwrap-panic`, so if **any single asset held by the borrower** has a permanently broken oracle (stale feed, dead price source, etc.), the whole `liquidate()` call aborts — even when the liquidator is only trying to repay debt and seize collateral in a completely unrelated, healthy market. This freezes the debt-side vault's suppliers, who can never have that bad debt recovered or socialized, exactly mirroring the Perennial `BalancedVault` pattern where a break in one market locks funds tied to other, unrelated markets.

### Finding Description
`liquidate()` builds the borrower's position via `get-liquidation-position`, which uses the enabled-asset bitmap intersected with the borrower's own mask — i.e. **all** collateral/debt asset IDs the borrower currently holds: [1](#0-0) 

That mask is then passed into `get-assets(mask)`, which fetches oracle data for every one of those assets and resolves all of their prices in a single batched call: [2](#0-1) 

Crucially, the result is unwrapped with `unwrap-panic`, not a graceful `try!`/`asserts!` with a recoverable error: [3](#0-2) 

`price-multi-resolve` itself asserts that *every* entry resolved successfully or returns an error which is then panicked on by the caller: [4](#0-3) 

And `price-resolve` hard-fails (`ERR-ORACLE-INVARIANT`) whenever a price is illegal or its timestamp is not fresh relative to `max-staleness`: [5](#0-4) 

`liquidate()` calls `get-assets(mask)` on this full borrower mask before it can compute LTV, process the specific debt/collateral pair requested, or reach the bad-debt-socialization step: [6](#0-5) 

So: Alice (borrower) holds collateral in asset X (e.g. `stSTXbtc`, via a third-party/external staking protocol) and asset Y (e.g. `USDC`), and has borrowed against Y. If X's oracle permanently breaks (feed stops updating past `max-staleness`, or the external protocol integration underlying X fails such that its price can never again be resolved), then **every** future call to `liquidate(Alice, ..., Y, ...)` — even one targeting only the perfectly healthy Y market — panics inside `get-assets(mask)` before the liquidator's specific debt/collateral pair is ever evaluated. The liquidator (Bob, an unprivileged actor) cannot liquidate Alice's Y-debt at all, and the suppliers of the Y vault (a separate group of unprivileged principals who never interacted with X) are left exposed to Alice's growing, uncollectable debt.

### Impact Explanation
The victims are the depositors/suppliers of the healthy debt-side vault (e.g. `v0-vault-usdc`), whose shared pool (`total-assets`, `principal-scaled`, `index`) is the state harmed. With Alice's debt permanently unliquidatable:
- Interest keeps accruing on Alice's borrowed principal indefinitely with no seizure of collateral ever possible.
- The bad-debt-socialization path in `liquidate()` (which writes down the vault's `lindex` via `socialize-debt`) can never be reached, because the panic happens long before that code runs.
- If Alice's debt eventually exceeds what her *other*, healthy collateral could have covered, USDC-vault suppliers suffer real, unrecoverable losses/frozen redemption capacity — losses that in a working system would have been caught and (partially) covered by liquidating the healthy collateral.

This lands squarely in "temporary freezing of funds" (until/unless the oracle for the unrelated broken asset is fixed — which, per the report's premise, may be permanent) for third-party USDC-vault suppliers, and can escalate to protocol insolvency for that vault if the debt is never recovered.

### Likelihood Explanation
No malicious action is required — only that a user hold two different asset types where one's external price source degrades permanently (a scenario the underlying report explicitly treats as plausible for any oracle/external integration). Because the protocol architecture bundles *all* of a borrower's held assets into a single price-resolution call gated by `unwrap-panic`, this failure mode is triggered by the ordinary act of a user diversifying collateral across markets — a common and encouraged usage pattern (`supply-collateral-add`/multi-asset collateral is a core supported feature). Likelihood is elevated by the fact that `zstSTXbtc`/other yield-bearing collateral depends on external protocol integrations that the report explicitly calls out as an acceptable risk factor.

### Recommendation
Decouple price resolution needed for the *specific* liquidation pair from the full-position evaluation:
- Compute LTV/health using cached/last-known-good prices for assets not involved in the current liquidation call, or
- Allow `get-assets`/`price-multi-resolve` to return partial results (skip/flag unresolvable assets rather than `unwrap-panic`) when the failing asset is not the one being seized, and let `is-healthy`/liquidation logic treat an unresolvable asset's collateral value conservatively as zero rather than aborting.
- More generally, replace `unwrap-panic` in `get-assets` and `price-multi-resolve` consumers with graceful error propagation so a single frozen oracle cannot brick liquidation, borrow, or withdrawal flows for uninvolved, healthy markets.

### Proof of Concept
1. Alice deposits USDC as collateral is not needed here — instead she deposits `zstSTXbtc` (backed by an external staking protocol) as one collateral asset and separately borrows `USDC` against a second collateral asset, e.g. `sBTC`.
2. The external protocol behind `stSTXbtc`/its oracle feed permanently stops updating (staleness check in `price-resolve` at `local-testing/contracts/market/market.clar:409-410` never passes again).
3. USDC price drops (or Alice's `sBTC` price drops), making Alice's USDC debt liquidatable by normal LTV rules.
4. Liquidator Bob calls `liquidate(Alice, sBTC-ft, USDC-ft, debt-amount, ...)`.
5. Inside `liquidate()`, `get-assets(mask)` (`v0-4-market.clar:1410`/`:482-492`) is called with Alice's full mask, which includes the broken `stSTXbtc` asset; `price-multi-resolve` returns an error for that asset, and `unwrap-panic` at `v0-4-market.clar:491` aborts the entire transaction.
6. Bob's liquidation permanently fails (every retry has the same outcome), Alice's USDC debt is never repaid or her `sBTC` collateral seized, and USDC-vault suppliers bear the growing, unrecoverable bad debt.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
