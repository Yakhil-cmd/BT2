### Title
Webhook signature verification is bound to an attacker-chosen organization while the mutated repository is taken from a separate, unchecked field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to check the `X-Hub-Signature` against by reading `repository_owner`, which is parsed straight out of the untrusted JSON body. Every `Webhooks::Handlers::Handler` subclass, however, decides *which repository/stack to mutate* using a completely different field of the same untrusted body, `payload.dig('repository', 'full_name')` [1](#0-0) . Nothing in the controller or in `Handler` cross-checks that `full_name`'s owner segment matches `repository_owner`. This breaks the intended equality "organization that authenticated == repository that is written."

### Finding Description
`verify_signature` computes the org used for authentication purely from attacker-controlled JSON:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

and then:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 

`GitHubApp#verify_webhook_signature` treats an org without a configured `webhook_secret` as *always verified*:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

`webhook_secret` is explicitly documented/shipped as optional and is `nil` in the example/dev configs (`config/secrets.development.example.yml:11`, `config/secrets.development.shopify.yml:9/18`), and Shipit officially supports hosting multiple GitHub organizations behind one webhook endpoint with independently-configured secrets (`docs/setup.md` "Using Multiple Github Applications").

Once the request clears `verify_signature`, the actual event handlers never look at `repository_owner`/`organization.login` again. They resolve the target `Repository`/`Stack` solely from `full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 

For example `PushHandler`:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

and every `PullRequest::*Handler` similarly derives `repository`/`stack` from `params.repository.full_name` [6](#0-5) [7](#0-6) .

On a real GitHub webhook `repository.owner.login` and the owner segment of `repository.full_name` are always the same string, so this discrepancy is never exercised by legitimate traffic. But since the whole JSON body is attacker-supplied before verification, nothing stops an attacker from setting these two fields to *different* organizations. If Shipit is configured for multiple GitHub organizations (a documented, supported topology) and even one of them has no `webhook_secret` set, an attacker who knows that org's name can:
1. Set `repository.owner.login` (or top-level `organization.login`) to the unsecured organization, causing `verify_signature` to short-circuit to `verified = true` with no valid HMAC at all.
2. Set `repository.full_name` to `"<victim-org>/<victim-repo>"`, an entirely different, properly-secured organization's repository that Shipit tracks.

The request is accepted, `Shipit::Webhooks.for_event(event)` dispatches to the real handlers, and those handlers act on the victim organization's `Stack`/`Repository`/`PullRequest` records — even though the request never carried a valid signature for that organization.

### Impact Explanation
This lets a fully unauthenticated attacker, with no GitHub credentials, no Shipit session and no knowledge of the victim organization's `webhook_secret`, drive mutating webhook flows against a stack that belongs to a securely-configured organization, purely by naming an unrelated, unsecured organization in the `repository.owner.login`/`organization.login` field. Concretely this can:
- force `Stack#sync_github(expected_head_sha: ...)` with an attacker-chosen SHA on the victim stack via `PushHandler`, which can affect continuous-deployment scheduling and undeployed-commit tracking for that stack,
- open/close/label/unlabel `PullRequest`/review-stack objects for the victim repository via the `PullRequest::*Handler` classes, including archiving/unarchiving review stacks and provisioning behavior tied to labels,
- forge commit `Status` records for the victim repository via `StatusHandler`.

This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in scope, and the impact (forged deploy-pipeline state, unauthorized manipulation of a stack that the attacker does not control) reaches the "cross-repository writes" bar for a valid finding.

### Likelihood Explanation
Exploitability depends entirely on deployment topology: it requires (a) the Shipit instance to be configured for more than one GitHub organization, and (b) at least one of those organizations to be left without a `webhook_secret`. Both conditions are explicitly supported and shown as valid configurations in this engine's own documentation and example secrets files, so the precondition is not a hypothetical misuse of the code — it is a state the shipped configuration examples actively encourage (`webhook_secret: # nil`). No additional information (secrets, tokens, sessions) about the victim organization is needed by the attacker.

### Recommendation
In `Handler#repository_name`/`#stacks`, or centrally in `WebhooksController`, verify that the owner segment of `repository.full_name` (and `organization.login` where applicable) matches the `repository_owner` that was used to select the `GitHubApp` used for signature verification, and reject the request otherwise. Additionally, consider making `webhook_secret` mandatory (or requiring an explicit opt-in for skipping verification) for any organization entry in a multi-organization `github:` configuration, since `return true unless webhook_secret` degrades the entire authentication boundary for that org to "no verification."

### Proof of Concept
Assume `config/secrets.yml` configures two organizations, `unsecured-org` (no `webhook_secret`, per the documented optional/nil pattern) and `victim-org` (has a strong `webhook_secret` and a tracked `Stack` for `victim-org/victim-repo`):

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-omitted
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-40-char-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "unsecured-org" }
  }
}
```

Trace:
1. `WebhooksController#repository_owner` → `"unsecured-org"` [2](#0-1) .
2. `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)` → `true` immediately because that org has no `webhook_secret` [4](#0-3) .
3. Request passes `verify_signature`; `Shipit::Webhooks.for_event('push')` runs `PushHandler.call(params)`.
4. `PushHandler#stacks` resolves via `Repository.from_github_repo_name("victim-org/victim-repo")` [1](#0-0) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real, `webhook_secret`-protected stack [5](#0-4) , despite the attacker never possessing `victim-org`'s webhook secret.

Note: I could not fully trace `Stack#sync_github`'s downstream effects (e.g., whether it can trigger an actual auto-deploy) within the available context; the code above confirms the authentication/target-repository binding break and unauthorized state mutation regardless of that downstream detail.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
