## Analysis

The closest analog to the "M‑7: pausing blocks yield collection" bug class in `ocore--003` is the **`spender_attested` asset attestor‑list mechanism**. It reproduces the same root-cause pattern: a single privileged actor (the asset **definer**, analogous to Napier's "management"/admin role) can unilaterally and repeatedly overwrite a gating list that blocks unprivileged holders from spending assets they legitimately already own, with no time-lock, no multi-party check, and no alternate path for the holder to recover access.

### Title
Asset definer can permanently freeze already-issued `spender_attested` asset holders' funds by replacing the attestor list - (File: `validation.js`, `storage.js`)

### Summary
For assets defined with `spender_attested: true`, only the asset's `definer_address` can publish/replace the attestor list via an `asset_attestors` message [1](#0-0) . Every payment spending or receiving that asset requires the author/output address to be in the *current* (latest) attestor-approved set [2](#0-1) [3](#0-2) . Because the definer can post a brand-new `asset_attestors` unit at any time that fully replaces the previous list (only the single latest list is read, not a union of all historical entries), a holder who legitimately acquired coins while attested can be retroactively excluded, permanently freezing their balance with no way to appeal or bypass — mirroring the Napier `Tranche.pause()` issue where a privileged, unilateral action blocks users from accessing already-earned/owned funds.

### Finding Description
When an asset is created with `spender_attested: true`, `readAsset()` resolves the attestor list by picking the **single most recent** `asset_attestors` unit for that asset and using exactly the addresses listed there — old entries from a previous list are dropped, not merged: [4](#0-3) 

Only the asset's `definer_address` is authorized to publish this list, and there's no requirement to keep any address in it, nor any protocol-level restriction preventing the definer from shrinking or completely changing the list at will: [1](#0-0) 

Every subsequent payment then requires that the spending/output addresses appear in this list, both at message level and at input/output level: [2](#0-1) [3](#0-2) [5](#0-4) 

There is no `nonPausableCollect`-style escape hatch, no timelock on attestor-list changes, and no way for an excluded address to recover access to coins it already legitimately holds (received while attested, or issued directly by the definer). This is functionally identical to the reported bug class: a single restricted/untrusted privileged role (here, the asset definer) can unilaterally and instantly cut off unprivileged users' access to funds they already own, with the block being permanent until (and unless) that same privileged actor chooses to reverse it.

### Impact Explanation
A malicious or compromised asset definer can:
1. Issue/transfer a `spender_attested` asset to users while they are attested, causing users to accumulate legitimate balances.
2. Post a new `asset_attestors` message excluding some or all of those users.
3. Permanently prevent those users from spending, transferring, or even receiving further payments of that asset — the outputs become unspendable "stuck" balances (loss of assets for the users), exactly the M‑7 impact class ("Users are unable to collect ... resulting in a loss of assets for the victims").

This can also block payment to output addresses (since output addresses must also be attested — `validation.js:2630-2641`), meaning downstream payees (e.g., users trying to be paid out) can be selectively frozen out even without ever having transacted maliciously.

### Likelihood Explanation
Likelihood is high whenever a `spender_attested` asset is used (a supported, documented asset feature), because:
- The action requires only one single-authored unit (`asset_attestors`) from the definer address — trivially composable via existing message validation paths.
- No other consensus participant can override or veto the definer's list.
- Nothing in validation prevents the definer from excluding addresses that previously held/received the asset legitimately.

### Recommendation
Consider one or more of:
- Allowing spending/transfer of previously-acquired `spender_attested` balances even if the address is later removed from the attestor list (grandfathering already-attested holdings), so a definer cannot retroactively freeze existing balances.
- Requiring attestor-list changes to only add addresses (or introducing an explicit, disclosed revocation mechanism with a timelock) rather than allowing an unrestricted full replacement.
- Documenting this centralization risk explicitly for asset issuers/definers so wallets/users can treat `spender_attested` assets from unknown definers as high risk.

### Proof of Concept
1. Definer A creates asset X with `spender_attested: true`, `is_transferrable: true`, and publishes an initial `asset_attestors` list including address `U` (validated per `validation.js:2829-2848`, `checkAttestorList` at `validation.js:2850-2864`).
2. Definer A issues/transfers asset X to `U`. Payment passes validation because `U` is in `arrAttestedAddresses` (`validation.js:2115-2122`).
3. Definer A posts a new `asset_attestors` unit for asset X listing only a different address `V` (excluding `U`). This is valid: single-authored by A, non-empty sorted array (`validation.js:2829-2848`).
4. `storage.readAsset()` now resolves the attestor list to only `[V]`, since it reads only the latest attestors unit (`storage.js:1917-1946`).
5. `U` attempts to spend/transfer its previously acquired asset X balance. Validation fails at `validation.js:2504-2507` ("owner address is not attested") or at the message-level check `validation.js:2115-2122` ("none of the authors is attested"). `U`'s funds are now permanently stuck with no recourse, reproducing the M‑7 impact within ocore's asset framework.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
