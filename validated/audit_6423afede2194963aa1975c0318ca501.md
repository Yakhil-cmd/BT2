### Title
Webhook signature verification silently no-ops for any org missing `webhook_secret`, allowing unsigned/forged pushes to trigger deploys - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` delegates authenticity checking entirely to `Shipit::GitHubApp#verify_webhook_signature`, which explicitly returns `true` with zero signature comparison when the resolved organization's config has no `webhook_secret` set. An attacker who simply knows (or guesses) the name of an org configured without a `webhook_secret` can POST an arbitrarily-signed (or unsigned) `push` payload naming any stack under that org, causing `PushHandler#process` to call `stack.sync_github`, feeding attacker-controlled `after`/ref data into the sync/deploy pipeline.

### Finding Description
The intended binding is: `a_verified_HMAC_exists_for_this_org == true` before any webhook payload is trusted to mutate stack state.

Trace:
1. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` purely from the untrusted JSON body — `params.dig('repository','owner','login') || params.dig('organization','login')` (line 61) — with no cryptographic binding yet established.
2. It calls `Shipit.github(organization: repository_owner)` (lib/shipit.rb:170-181), which looks up `github_app_config(organization)` from `secrets.github` and raises `GithubOrganizationUnknown` (→ `head 422`) only if that org key is absent entirely.
3. It calls `github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` (lib/shipit/github_app.rb:76-83):
   ```
   def verify_webhook_signature(signature, message)
     return true unless webhook_secret
     ...
   end
   ```
   If that org's config entry has no `webhook_secret` key (`@webhook_secret = @config[:webhook_secret].presence`, line 50), the method returns `true` unconditionally — no HMAC is computed or compared at all, regardless of what (or whether) `X-Hub-Signature` is sent.
4. `head(422) unless verified` is skipped since `verified == true`; the request proceeds to `create`, which dispatches to `Shipit::Webhooks::Handlers::PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb:12-17), matching stacks by `branch` and calling `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack.
5. `stack.sync_github` (app/models/shipit/stack.rb) synchronizes the stack's known SHA/state from the (attacker-influenced) webhook data, which downstream (via `Shipit::ContinuousDeliveryJob`) can drive automatic deployment of the newly-synced ref for stacks with continuous delivery enabled.

Root cause: authenticity is delegated to a secret whose absence is treated as "trust everything" rather than "reject everything," and the org used to select that secret is itself taken from the unauthenticated payload. Existing guards (`drop_unhandled_event`, `check_if_ping`, `GithubOrganizationUnknown` handling) only reject *unknown* event types or *unconfigured* org names — they do nothing to prevent an *unsigned* payload against a *known-but-unsecured* org from being accepted as legitimate.

### Impact Explanation
Any organization entry in Shipit's `secrets.github` config that omits `webhook_secret` has effectively no webhook authentication: an attacker can send a crafted, unsigned/garbage-signed `push` event naming that org and any repository/stack under it, causing `stack.sync_github` to run and potentially triggering an automatic deploy of attacker-chosen ref/SHA data via the continuous delivery pipeline. This is repeatable per request against any stack under any such org, matching the Critical "authentication bypass (forged webhook) ... leading to an unauthorized deploy" category.

### Likelihood Explanation
The only precondition is an operator-level Shipit misconfiguration: an org present in `secrets.github` without a `webhook_secret` value. The rest of the exploit requires no secrets, tokens, or privileged access — just knowledge of the org login and a target stack's branch, both of which are typically public (GitHub org/repo names, branch names). Given that this is a config-omission-triggered bypass, likelihood depends entirely on deployment configuration, but the code provides no fallback protection (e.g., rejecting when `webhook_secret` is blank) when that omission occurs.

### Recommendation
Change `GitHubApp#verify_webhook_signature` to fail closed when `webhook_secret` is not configured (raise/log and return `false`, or refuse to boot with GitHub webhook routes enabled for an org lacking a secret), rather than returning `true` unconditionally. Additionally, require organization-level configuration to always include a `webhook_secret` as a hard validation at startup for multi-org configs.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "unsigned push webhook is accepted when org has no webhook_secret configured" do
  stack = shipit_stacks(:shipit)
  Shipit.stubs(:github).with(organization: stack.repo_owner).returns(
    Shipit::GitHubApp.new(stack.repo_owner, {}) # no :webhook_secret key at all
  )

  post :create, params: {}, body: {
    ref: "refs/heads/#{stack.branch}",
    after: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
    repository: { owner: { login: stack.repo_owner }, full_name: stack.repo_name },
    organization: { login: stack.repo_owner }
  }.to_json, as: :json, headers: {
    'X-Github-Event' => 'push',
    'X-Hub-Signature' => 'sha1=not_a_real_signature'
  }

  assert_response :ok
  stack.reload
  assert_equal "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef", stack.sha # or verify sync_github was invoked with attacker-controlled sha
end
```
Assertions on both sides of the binding: before the fix, `verify_webhook_signature` returns `true` with no HMAC computed (violating `a_verified_HMAC_exists_for_this_org == true`), and `head(:ok)` plus the stack mutation occur; after the fix, the request should be rejected with `422` and the stack must remain unchanged.
