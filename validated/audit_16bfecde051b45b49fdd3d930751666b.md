### Title
Quadratic-complexity double-spend key lookup in payment input validation enables validation-time DoS - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` in `validation.js` tracks used input/output identifiers with a plain JS array (`objValidationState.arrInputKeys` / `arrOutputAddresses`) and de-duplicates them with `Array.prototype.indexOf` inside a per-input/output loop, giving O(n²) behavior as the number of inputs/outputs in a single payment message grows — directly analogous to the reported Suricata SMTP/MIME URL-extraction quadratic-complexity bug (repeated linear scans performed once per element of attacker-controlled input).

### Finding Description
For every input in a payment message, the code builds an `input_key` and checks membership with a linear scan before pushing it onto the same array: [1](#0-0) [2](#0-1) 

The same pattern is used for output addresses in the output-validation loop: [3](#0-2) 

Both loops iterate over `payload.inputs` / `payload.outputs` (`async.forEachOfSeries(payload.inputs, ...)` and a `for` loop over `payload.outputs`), and for each element they perform an `indexOf` scan over an array that has been growing with every previously processed element: [4](#0-3) [5](#0-4) 

This is the same bug class as the Suricata report: a single unprivileged submission (there, an SMTP/MIME email; here, a single unit posted by any network participant) triggers a hidden O(n²) algorithm inside otherwise-bounded per-message processing, because the "cheap-looking" per-element check (`indexOf`) is actually linear in the number of already-seen elements.

### Impact Explanation
Every full node validates every incoming unit via `validate()` → `validatePaymentInputsAndOutputs()`, so this code runs unconditionally for all payment messages, including those from unprivileged senders. A message with a large number of inputs or outputs forces quadratic CPU cost during validation. Because unit size is only bounded by `constants.MAX_UNIT_LENGTH` (not by input/output *count* directly), and each input/output entry can be made compact (few required fields), an attacker can pack thousands of inputs/outputs into one otherwise-valid-looking message, causing disproportionate CPU consumption on every validating node compared to the message's byte size — a validation-time performance/DoS impact matching the CVE's "quadratic complexity ... leading to a performance impact" characterization. This does not itself cause double-spend or fund loss, so it should be scored as an availability/performance issue reachable by any unit poster.

### Likelihood Explanation
High: any node/user can post a unit; no special privileges, keys, or witness/AA control are required. The vulnerable loops execute unconditionally on the standard payment-validation path for every unit that reaches `validatePaymentInputsAndOutputs`, so exploitation only requires constructing one large but structurally valid payment message.

### Recommendation
Replace the array + `indexOf` de-duplication pattern for `arrInputKeys` and `arrOutputAddresses` (and any other similar accumulator arrays used for uniqueness checks in payload/message validation loops) with a `Set`/`Map` (O(1) average lookup and insert), eliminating the quadratic blowup while preserving existing semantics (order of `push` calls and duplicate-detection behavior). Additionally, consider adding an explicit cap on the number of inputs/outputs allowed per payment message (independent of total unit byte size) to bound worst-case validation cost defensively.

### Proof of Concept
1. Construct a single payment message (base or custom asset) with N distinct dummy transfer inputs (or N output addresses), each referencing minimal valid fields, keeping the serialized unit under `MAX_UNIT_LENGTH`.
2. Post this unit to a full node.
3. Observe that `validatePaymentInputsAndOutputs` spends CPU time proportional to N² while executing the `arrInputKeys.indexOf(input_key)` / `arrOutputAddresses.indexOf(output.address)` checks, measurable via wall-clock validation time compared to a linear baseline (e.g., N separate single-input messages), demonstrating the quadratic scaling as N increases.
