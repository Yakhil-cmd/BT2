### Title
Webhook signature verification organization can diverge from the organization used to mutate `Team` records - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#repository_owner` (used by the `verify_signature` before_action) and `WebhooksController#create` (which drives `MembershipHandler#process`) derive the "organization" value from two independently-parsed representations of the same HTTP request, not from a single, consistently-bound source. This allows the organization whose `webhook_secret` authenticates the HMAC to differ from the organization written into `Shipit::Team#organization`.

### Finding Description
The claimed broken binding, stated as an equality that must hold but doesn't: `organization_used_for_HMAC_verification == organization_written_to_Team.organization`.

- `verify_signature` runs as a `before_action` and calls `repository_owner`, which reads `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . Here `params` is the standard `ActionController::Parameters`, which Rails builds by merging JSON-body-derived parameters with query-string parameters (`request_parameters.merge(query_parameters)`), meaning a same-named key present in the query string can override the value present in the JSON body.
- `#create` separately does `params = JSON.parse(request.raw_post)` — a fresh hash built strictly from the raw POST body, with no query-string merging — and passes that hash into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [2](#0-1) .
- `MembershipHandler#process` validates and reads `params.organization.login` from that raw-body-only hash and uses it to set `team.organization = params.organization.login` inside `Team.find_or_create_by!(github_id: params.team.id)` [3](#0-2) .

Because `repository_owner` (signature check) and `MembershipHandler` (mutation) do not read the "organization" field from the same, singly-parsed source, an attacker who controls both the query string and the JSON body of the same POST can make the two reads diverge: put their own org's login in the query string (`?organization[login]=org-attacker`) so `verify_signature` selects `Shipit.github(organization: 'org-attacker')` and passes HMAC verification with the attacker's own legitimately-configured `webhook_secret`, while the JSON body's `organization.login` is set to `'org-victim'`, which is what `MembershipHandler` actually persists into `Team.organization`. `verify_signature`'s `GithubOrganizationUnknown` rescue and `drop_unhandled_event` do not protect against this because both organizations ("org-attacker" for the lookup, "org-victim" for the body) are valid, known values — nothing re-checks that the two are the same.

### Impact Explanation
A successful request lets an unprivileged-but-tenant-owning attacker (who legitimately controls a Shipit-configured GitHub App/org, "org-attacker") create a `Shipit::Team` row bound to `organization = 'org-victim'` and add an arbitrary GitHub-login member (`User.find_or_create_by_login!(params.member.login)`) to that team, without ever presenting a valid signature from org-victim's webhook secret [4](#0-3) . Since `User#authorized?` grants access when a user belongs to a team whose id is in `Shipit.github_teams` [5](#0-4) , this is a cross-tenant write that can feed into `Shipit.github_teams`-based authorization — matching the High severity "escalation into Shipit.github_teams authorization" category. The write only takes effect for `Team.find_or_create_by!` on first creation of a given `github_id` (the `organization=` assignment happens only in the create block), so it is exploitable primarily against team ids not yet known to Shipit, and is repeatable across arbitrary victim organizations/teams as long as the attacker controls one legitimately-onboarded org.

### Likelihood Explanation
Preconditions: attacker must operate their own legitimately Shipit-configured GitHub App/org ("org-attacker") — a real but attainable precondition for any organization/tenant that self-onboards to a shared Shipit instance. The attack requires only crafting an HTTP request with a divergent query string vs. JSON body and signing the raw body with the attacker's own known `webhook_secret` — no secrets of the victim are needed. This depends on Rails' documented parameter-merge precedence (query string parameters can override body-derived parameters of the same key in `ActionController::Parameters`); I was not able to execute code in this environment to empirically confirm this precedence for the exact Rails/Actionpack version vendored in this repo, so this specific mechanism should be validated with a live/integration test before being treated as fully confirmed.

### Recommendation
Make `#create` and `verify_signature` operate on the exact same parsed object. Parse the body once (e.g., `payload = JSON.parse(request.raw_post)`), derive `repository_owner` from that same `payload` hash (not the framework's merged `params`), and pass that same `payload` into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(payload) }`. Additionally, `MembershipHandler`/other handlers should not trust `params.organization.login` independently for anything with authorization consequences without re-deriving it from the value that was actually verified.

### Proof of Concept
Minitest plan for `test/controllers/webhooks_controller_test.rb`:
1. Configure two orgs in `Shipit.github_apps`-equivalent config: `org-attacker` with `webhook_secret_a`, `org-victim` with `webhook_secret_b`.
2. Build a JSON body: `{"action":"added","team":{"id": 999, "name":"n","slug":"s","url":"u"},"organization":{"login":"org-victim"},"member":{"login":"someuser"}}`.
3. POST to `/webhooks?organization[login]=org-attacker` with header `X-Github-Event: membership` and `X-Hub-Signature` computed as `sha1=` + HMAC-SHA1 of the raw body using `webhook_secret_a` (org-attacker's secret).
4. Assert response is `200`/`:ok` (signature verification passed using org-attacker's secret).
5. Assert `Shipit::Team.find_by(github_id: 999).organization == 'org-victim'`, proving `organization_used_for_HMAC != organization_written_to_Team`.
6. Negative control: repeat with `organization[login]=org-victim` in both query string and body, signed with `webhook_secret_b`; assert both sides equal `'org-victim'` to show the binding holds when query string and body agree.
