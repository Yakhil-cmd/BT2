### Title
Unbounded growth of `system_votes` voter set processed synchronously during MC stabilization enables consensus-stalling DoS - (File: main_chain.js, validation.js)

### Summary
The `system_vote` / `system_vote_count` mechanism lets any address cast a permanent, un-capped vote for system parameters (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`). When any unit posts a `system_vote_count` message, `countVotes()` is executed synchronously as part of main-chain stabilization and must load and process **every distinct address that has ever voted** for that subject. This is structurally identical to the reported `MAX_DELEGATES` bug class: a cheap, attacker-controlled, unbounded list (delegates in the Alchemix report; voter addresses here) is fully iterated inside a mandatory, non-skippable core operation (token transfer/withdraw in the report; MC stabilization here), with no upper bound analogous to `MAX_DELEGATES`.

### Finding Description
`system_votes` is described in the schema as "just a log of all votes, including overridden ones" [1](#0-0) , and any address can add a row to it simply by posting a `system_vote` message in a unit; only one system vote per unit-message is disallowed, but there is no global limit on the number of distinct voting addresses [2](#0-1) .

The vote counting logic is `countVotes()`, called from `markMcIndexStable()` at the end of processing each stabilized MCI, once per pending subject collected from `system_vote_count` messages that any unit author can also post [3](#0-2) [4](#0-3) .

`countVotes()` begins by pulling **all distinct addresses** that have ever voted for the subject, with no `LIMIT` or cap:
```
const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
``` [5](#0-4) 

It then builds a giant `IN(...)` clause and an `INSERT ... VALUES` statement whose size grows linearly with the number of distinct voters, creates a temporary table populated with every voter's balance, and repeatedly re-queries `system_votes` while expanding the vote time-window year by year until enough voting balance share is captured: [6](#0-5) 

For `op_list` specifically, it additionally scans and re-sorts unstable votes and reconstructs `op_votes`/`op_votes_tmp` tables from the full voter set: [7](#0-6) 

This entire computation runs inline inside `markMcIndexStable`, which is a mandatory step every node must complete before subsequent units can be marked stable — there is no equivalent of a "MAX_DELEGATES" ceiling capping the number of distinct voters that this per-subject vote count must process.

### Impact Explanation
Because `system_votes` is a pure append/override log with no cap on the number of distinct addresses (unlike, e.g., `COUNT_WITNESSES`-sized OP lists or `MAX_AUTHORS_PER_UNIT`), an attacker can cheaply generate a large number of addresses, each casting a `system_vote` (minimal-value unit, one message per unit), to grow the voter set for a subject arbitrarily. A single subsequent `system_vote_count` message (postable by anyone, including the attacker) forces every node to execute `countVotes()` over this bloated, ever-growing voter set as an unavoidable part of MC stabilization. As with the `MAX_DELEGATES` bug — where an unbounded delegate list forced excessive gas consumption during transfer/withdraw — here an unbounded voter list forces excessive query/string-construction/DB work during MC stabilization, a core, mandatory, non-optional consensus operation. Because the log never shrinks (it is "a log of all votes, including overridden ones"), the cost is permanent and cumulative across the life of the chain, unlike a per-call gas cap that resets. In the worst case this can slow or stall stabilization across the network, i.e., "a network unable to confirm new units," which matches the accepted impact categories for this class of finding.

### Likelihood Explanation
Likelihood is high in terms of reachability: casting a `system_vote` and triggering `system_vote_count` are both ordinary payload messages available to any unprivileged unit poster once the relevant feature is activated (`v4UpgradeMci`) [2](#0-1) , requiring no special role, only the cost of posting many small units to create many distinct voting addresses. The severity of the resulting slowdown depends on how expensive the resulting SQL over a very large `IN()`/`VALUES` list becomes on typical node hardware/DB engines (SQLite vs MySQL), which was not further profiled in this review.

### Recommendation
1. Introduce an explicit maximum number of distinct addresses considered per subject in `countVotes()` analogous to `MAX_DELEGATES`/`MAX_AUTHORS_PER_UNIT`, e.g., only account for the top-N addresses by balance, since only balance-weighted majority matters for the median/threshold logic.
2. Consider pruning or deduplicating stale/zero-balance voter rows from `system_votes` opportunistically instead of retaining an ever-growing log that must always be fully scanned.
3. Rate-limit or otherwise bound how often/how expensively a `system_vote_count` message can trigger the full-voter-set recomputation, and evaluate paginating/batching the `IN()`/`VALUES` construction so cost doesn't scale unbounded with total historical voter count.

### Proof of Concept
Not independently verified with a runnable PoC in this review; the conceptual PoC is: (1) create many low-balance addresses, each author a unit containing a `system_vote` message with a chosen subject to add to `system_votes`; (2) post a unit with a `system_vote_count` message for that subject; (3) observe that `main_chain.js`'s `countVotes()` must load and process the full, unbounded set of distinct voter addresses (`SELECT DISTINCT address FROM system_votes WHERE subject=?`) as a mandatory part of MC stabilization, with cost growing with the number of addresses created in step (1) and never shrinking afterward.
