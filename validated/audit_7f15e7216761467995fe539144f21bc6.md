### Title
`Pool::repay` refunds a declared overpayment that was never transferred in, draining pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` op trusts the declared `action.amount` instead of a measured inbound receipt. When the declared amount exceeds the position's outstanding debt, the excess (`overpayment`) is transferred back out of the pool's real token custody via `transfer_out`, without ever checking that the inbound transfer occurred or debiting the `cash` book. An unprivileged address can call `repay` with no debt and no inbound transfer, making the entire declared amount an "overpayment" and receiving pool funds for free. This is the same bug class as CVE-2024-46687: a resource (the repaid funds) is released along the settlement/error path, and the original caller is still credited as if the leg completed — funds are handed out twice logically: once as booked repayment semantics, once as a refund of money that never arrived.

### Finding Description
In `accounting`, `resolve_repay(amount, position)` splits the declared amount into `burned` debt shares and `overpayment`. `credit_cash(net_repay)` books only the net portion, but `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` unconditionally — the refund is derived purely from the caller-declared `amount`, not from a balance-delta measurement of what the pool actually received [1](#0-0) .

The comment "The controller transfers the repay amount into the pool before this call" is a convention, not an enforced invariant: the pool performs no `transfer_amount_measured`-style verification on the inbound leg [2](#0-1) . The `RepayRoundsToZeroShares` assert explicitly permits `net_repay == 0`, so a market with zero debt makes the whole declared amount refundable [3](#0-2) .

The in-repo test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` pins this exact drain: a direct `pool.repay` call with `amount == custody_before` on a debt-free market credits 0 and pays the entire custody balance to `payer` [4](#0-3) . `recapitalize` has the identical shape — `refund = amount - applied` is paid from custody even when `applied == 0` (fully backed market), again without an inbound-receipt check [5](#0-4) .

Contrast with the controller-side strategy leg, which does measure: `repay_debt_from_controller` uses `transfer_amount_measured` and refunds only the observed balance delta [6](#0-5) . The pool's own entrypoint lacks that measurement, so a caller bypassing the controller's pre-funding step receives an unfunded refund.

### Impact Explanation
Theft of user funds / protocol insolvency. Each call refunds `min(declared_amount, available custody)` of real tokens out of the pool while booking nothing. A single unprivileged address can repeat `repay` (or `recapitalize` on a backed market) per `(hub, asset)` book until custody is drained; suppliers' underlying is stolen directly from the physical pool balance backing their shares.

### Likelihood Explanation
Directly reachable: `repay` is a permissionless pool entrypoint (the pinned test calls `client().repay(&payer, ...)` with a freshly generated address and no funding). No price manipulation, timing, or privileged role is needed — only a market whose debt or shortfall is smaller than the pool's token balance.

### Recommendation
Measure the inbound leg inside the pool op: snapshot the pool's token balance before accounting (or require the caller to pre-transfer and verify `balance_after - balance_before >= amount`), and cap `overpayment`/`refund` at the measured receipt. Alternatively gate `repay`/`recapitalize` to the controller and have the controller pass a measured amount.

### Proof of Concept
From the pinned test `contracts/pool/tests/flows.rs:3590-3611`:
1. Attacker picks a debt-free market with pool custody `C` (`borrowed == 0`, `cash == C`).
2. Calls `pool.repay(payer = attacker, amount = C)`.
3. `resolve_repay` takes the full-close branch: `net_repay = 0`, `overpayment = C`; the `RepayRoundsToZeroShares` assert passes on the `net_repay == 0` disjunct.
4. `transfer_out(payer, C)` sends the entire custody to the attacker; the book (`cash`) is untouched, so subsequent suppliers' withdrawals fail against an empty vault.

pub(crate) fn accounting(
    env: &Env,
    hub_asset: HubAssetKey,
    amount: i128,
) -> RecapitalizationOutcome {
    require_nonneg_amount(env, amount);
    let mut cache = ops::renewed_market(env, &hub_asset);

    let applied = amount.min(guards::backing_shortfall(&cache));
    let refund = amount
        .checked_sub(applied)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));

    cache.credit_cash(applied);
    cache.commit();

    RecapitalizationOutcome {
        cache,
        mutation: PoolAmountMutation {
            actual_amount: applied,
        },
        refund,
    }
}

pub(crate) fn repay_debt_from_controller(
    env: &Env,
    account: &mut Account,
    cache: &mut Context,
    caller: &Address,
    req: StrategyRepay<'_>,
) {
    let debt_pool_addr = cache.cached_pool_address();
    let debt_tok = token::Client::new(env, &req.debt.asset);

    let received = payments::transfer_amount_measured(
        env,
        &req.debt.asset,
        &env.current_contract_address(),
        &debt_pool_addr,
        req.debt_available,
        GenericError::InternalError,
    );

    // Snapshot after funding so only repayment refunds go to the caller.
    let controller_balance_before_repay = debt_tok.balance(&env.current_contract_address());

    repay_prefunded_position(
        env,
        account,
        &env.current_contract_address(),
        req.action,
        RepaymentRequest {
            hub_asset: req.debt,
            position: req.debt_pos,
            amount: received,
        },
        cache,
    );

    refund_controller_balance_delta(
        env,
        &req.debt.asset,
        controller_balance_before_repay,
        caller,
    );
