### Title
Unrestricted swap route can add a wallet-draining call under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts caller-supplied `swap` bytes and forwards them to the configured router without the controller constraining which contracts the route invokes. [1](#0-0) [2](#0-1)  A malicious route venue can invoke a token `transfer` from the caller to an attacker; simulation records that transfer as a child of the caller’s `swap_collateral` authorization, and it executes if the caller signs that tree. [3](#0-2) [4](#0-3) 

### Finding Description
After caller and account authorization, `process_swap_collateral` withdraws collateral and calls `withdraw_and_swap_from_supply` with the caller-provided `swap` argument. [5](#0-4) [6](#0-5)  `swap_tokens` grants only a bounded controller token transfer, but then executes the opaque route through `router.execute_strategy`. [7](#0-6) [2](#0-1)  The router calls payload-selected pool and token addresses without an allowlist, so the payload can place attacker-controlled code inside the caller-authorized invocation tree. [3](#0-2) 

The test harness models the issue directly: a payload-selected pool can call `wallet_token.transfer(victim, attacker, amount)` while a router still returns a fair swap output. [8](#0-7) [9](#0-8)  The controller’s input-spend and positive-output checks do not inspect unrelated caller-token transfers and therefore do not bound this loss. [10](#0-9) [11](#0-10) 

### Impact Explanation
A crafted route can steal unrelated tokens held in the caller’s wallet while still completing a nominally valid collateral swap. [12](#0-11)  The stolen amount is not limited to the routed collateral amount because the malicious venue can request an unrelated token transfer as another child authorization. [3](#0-2)  This is theft of user funds with high impact.

### Likelihood Explanation
Any unprivileged user can deploy a malicious venue and submit or distribute a route that reaches it through `swap_collateral`. [8](#0-7) [9](#0-8)  Exploitation requires the victim to sign the simulated authorization tree containing the extra transfer, so likelihood depends on client-side route decoding and authorization-tree inspection. [13](#0-12) [14](#0-13) 

### Recommendation
Decode and validate every route venue or enforce a governance-managed venue allowlist before execution rather than treating `swap` as opaque bytes. Reject routes whose external invocations can add caller-authorization children beyond the expected router input transfer, and require clients to display and block unexpected authorization children.

### Proof of Concept
Deploy a route-selected contract implementing:

```rust
pub fn swap(env: Env) {
    let (victim, wallet_token, to, amount) = load_plan(&env);
    token::Client::new(&env, &wallet_token)
        .transfer(&victim, &to, &amount);
}
```

This mirrors the harness’s `RogueHopPool::swap`, which transfers an unrelated wallet token from the victim to the attacker. [9](#0-8) 

Call `swap_collateral(caller, account_id, current, amount, new, swap)` with `swap` naming that contract as a hop. [1](#0-0)  Simulation records the malicious `wallet_token.transfer(victim, attacker, amount)` beneath the caller’s `swap_collateral` invocation. [4](#0-3)  Signing that recorded tree executes the transfer while the route can still return fair output and satisfy the controller’s measured-output check. [14](#0-13) [11](#0-10)
