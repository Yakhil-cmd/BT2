### Title
Fork-controlled `machine.environment` (e.g. `BUNDLE_GEMFILE`) injects into `rollback.override` process env, redirecting Bundler to attacker code - (File: `lib/shipit/task_commands.rb`, `app/models/shipit/deploy_spec.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` verbatim from the checked-out `shipit.yml`, which for a `ReviewStack` is read from the fork branch's working tree. `TaskCommands#env` merges this attacker-controlled hash into the environment used for every task, including rollback, and `Command#unbundled_env` applies `@env.stringify_keys` last, on top of the sanitized `BASE_ENV` (derived from `Bundler.unbundled_env`), so an attacker-supplied `BUNDLE_GEMFILE` overrides Bundler's own env-cleaning and reaches `PTY.spawn`.

### Finding Description
The broken binding: the invariant "the process env passed to `PTY.spawn` for `rollback.override` == `Bundler.unbundled_env` (no attacker-controlled bundler variables)" is violated — in reality it equals `BASE_ENV.merge(shell_paths_path).merge(@env.stringify_keys)` where `@env` includes `deploy_spec.machine_env`, and `machine_env` is sourced straight from `config('machine','environment')` [1](#0-0)  with no key allow-list or denial-list.

Path: `TaskCommands#env` builds the merged environment used for every command (`install_dependencies`, `perform`, and by extension rollback steps executed through the same `env` accessor), merging `deploy_spec.machine_env` after the Shipit-controlled defaults and before `@task.env` [2](#0-1) . `deploy_spec` is a `DeploySpec::FileSystem` built against the task's `working_directory`, i.e. the checked-out branch content — for a review stack this is the fork PR branch, so the attacker's own `shipit.yml` supplies `machine.environment` [3](#0-2) . `Command#unbundled_env` computes `BASE_ENV.merge('PATH'=>...).merge(@env.stringify_keys)` — the attacker-controlled `@env` is merged last, so it can override any key in `BASE_ENV`, including whatever `Bundler.unbundled_env`/`Bundler.clean_env` had unset/cleaned (e.g., `BUNDLE_GEMFILE`, `BUNDLE_BIN_PATH`, `RUBYOPT`) [4](#0-3) [5](#0-4) . This merged env is passed directly to `PTY.spawn` in `Command#start` [6](#0-5) .

For rollback specifically, `RollbackCommands#perform` (confirmed via `test/unit/rollback_commands_test.rb`, which stubs `machine_env: { 'GLOBAL' => '1' }` and shows it flowing into `command.env`) builds `Command` objects using the same `deploy_spec.machine_env`-derived env merge pattern, and `rollback_steps` is itself taken from `config('rollback','override')` (i.e., attacker's `shipit.yml`) [7](#0-6) , meaning the attacker controls both the executed rollback command and its environment variables. The only filtering present, `filter_rollback_envs`/`EnvironmentVariables#permit`, is scoped to `rollback_variables` (deploy-input variables defined by the stack maintainer), not to `machine_env`, so it does not intercept this path [8](#0-7) .

Precondition: repository has review stacks enabled with `provisioning_behavior = allow_with_label`, and the attacker's PR carries the provisioning label (an action the PR author fully controls on their own fork/PR) — this is confirmed by `LabeledHandler`/`OpenedHandler` logic which provisions/archives review stacks purely based on label presence and `params.repository.full_name`, with no maintainer approval gate [9](#0-8) .

### Impact Explanation
An unprivileged fork PR author who can get review-stack provisioning (label on their own PR under `allow_with_label`) can set `BUNDLE_GEMFILE=/path/to/attacker/Gemfile` (or point at a file within the checked-out fork tree) via `machine.environment` in their branch's `shipit.yml`. When the rollback task executes `bundle exec ...` (the discovered/overridden rollback step), Bundler evaluates the attacker-designated Gemfile, executing arbitrary Ruby code on the Shipit deploy host. This is Critical: Remote Code Execution on the deploy host via `Command`/`PTY.spawn`, reachable by any GitHub user who can open a PR against a repo with review stacks + `allow_with_label` configured, repeatable per PR/label toggle, and not limited to the review stack — the same `TaskCommands#env` merge order applies to every task type (deploy, rollback, restart, etc.), broadening the blast radius across all task executions on that stack.

### Likelihood Explanation
Preconditions are entirely within repository owner configuration (review stacks enabled, `allow_with_label` behavior) plus attacker-controlled actions (open PR, add label, commit `shipit.yml`). No secrets, tokens, or privileged roles are needed — this matches the "unprivileged fork PR author" threat model explicitly in scope. The attack is deterministic and repeatable on any repository with this common review-stack configuration.

### Recommendation
Strip or allow-list `machine.environment` keys against a fixed denylist of bundler/ruby-sensitive variables (`BUNDLE_GEMFILE`, `BUNDLE_BIN_PATH`, `RUBYOPT`, `RUBYLIB`, `GEM_HOME`, `GEM_PATH`, etc.) before merging into `TaskCommands#env`, or invert the merge order in `Command#unbundled_env` so `BASE_ENV`'s bundler-cleaning values cannot be overridden by task/machine env for these specific keys. Additionally, consider requiring maintainer approval (not just a self-applied label) before provisioning review stacks for external fork PRs.

### Proof of Concept
```ruby
# minitest sketch, placed alongside existing task_commands/deploy_spec tests
test "TaskCommands#env allows fork shipit.yml to inject BUNDLE_GEMFILE which reaches Command#unbundled_env" do
  deploy_spec = stub(
    dependencies_steps!: [],
    rollback_steps!: ['bundle exec cap $ENVIRONMENT deploy:rollback'],
    machine_env: { 'BUNDLE_GEMFILE' => '/tmp/attacker/Gemfile' }, # attacker-controlled shipit.yml on fork branch
    directory: nil,
    clear_working_directory?: true
  )
  task_commands.stubs(:deploy_spec).returns(deploy_spec)

  command = Shipit::Command.new('bundle exec cap $ENVIRONMENT deploy:rollback', env: task_commands.env, chdir: '/tmp')

  # Binding under test: unbundled_env should equal Bundler.unbundled_env (no attacker key)
  # but in fact:
  assert_equal '/tmp/attacker/Gemfile', command.unbundled_env['BUNDLE_GEMFILE']
end
```
This demonstrates the two sides of the equality diverge: expected `command.unbundled_env['BUNDLE_GEMFILE']` == Bundler's clean/unset value, actual == attacker-supplied path, confirming the env-injection path into the spawned rollback process.
