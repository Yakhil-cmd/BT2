### Title
Webhook signature verification key is derived from an unauthenticated payload field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the HMAC signature against by reading `repository_owner`, which is taken directly from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')`). The processing handlers, however, resolve the target repository/stack from a *different* field of the same unauthenticated body: `payload.dig('repository', 'full_name')`. Nothing binds these two fields together, and nothing guarantees the "authenticating organization" has a non-blank `webhook_secret`. This mirrors the reported bug class: a value (`targets`/here, the org used for verification) is trusted without a check that would prevent bypass, while the value actually acted upon (the repository written to) is a separate, unchecked field.

### Finding Description
In `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` returns a `GithubApp` instance configured per organization, and `verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly bypasses verification when no secret is configured for that organization:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [2](#0-1) 

After the signature check passes (trivially, for any org without a `webhook_secret`), the event handlers determine which repository/stack to act on using an entirely separate, attacker-controlled field of the same payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` looks up any repository by owner/name globally, independent of which organization's App config verified the request:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

The binding that should hold is: `organization authenticated (repository.owner.login used to pick webhook_secret) == organization of the repository actually written to (repository.full_name)`. Because neither field is cross-checked, and any org lacking a configured `webhook_secret` causes verification to be skipped entirely (`return true unless webhook_secret`), an attacker who knows (or picks) an organization in the multi-org Shipit config that has no `webhook_secret` set can send an arbitrarily signed (or unsigned) webhook body whose `repository.owner.login` is that org, while `repository.full_name` names a completely different, victim organization's repository. The handler (`PushHandler`, `pull_request` handlers, `status`, `check_suite`, `membership`, etc.) will act on the victim repository's stacks, e.g. triggering `sync_github`, unarchiving review stacks, injecting commit statuses, etc. [5](#0-4) 

This is a direct analog of the reported class: a decision (which org's secret authorizes the request) is made on a field that is never itself cryptographically bound to the field that determines what is actually written (the target repository), and there is no guard preventing the "trusted" side from being empty/absent.

### Impact Explanation
This allows unauthenticated forgery of GitHub webhook events against any repository configured in a Shipit instance that has at least one organization without a `webhook_secret` (a supported, documented configuration — see `config/secrets.development.shopify.yml` showing `webhook_secret: # nil` as a valid setting) [6](#0-5) . Depending on the handler triggered, an attacker can force stack `sync_github` on push events (potentially triggering CD deploys), unarchive review stacks, or inject fabricated PR/CI status data used in merge decisions — i.e., cross-repository/cross-organization forged actions that can lead to an unauthorized deploy path. This aligns with the "High" bucket (escalation across authorization boundary, unauthenticated read/write of stack state).

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires at least one organization in `Shipit.github` configs with no `webhook_secret` set, in a deployment that also manages other organizations/repositories with continuous deployment enabled. This is a realistic, documented configuration (the sample secrets files ship with `webhook_secret: # nil`), so likelihood is non-trivial in multi-org deployments, though not universal — single-org deployments with a secret configured for their only org are not exposed this way.

### Recommendation
- Require `webhook_secret` to be present for every configured organization at boot (fail fast rather than silently allowing `verify_webhook_signature` to return `true`).
- Bind verification and action to the same field: after signature verification succeeds for `repository_owner`, assert that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers (i.e., reject payloads where `payload.dig('repository','owner','login')` and the owner segment of `payload.dig('repository','full_name')` disagree).
- Consider deriving the repository solely from `repository.full_name` for authentication purposes too, or verifying both fields are internally consistent before doing the lookup used for verification.

### Proof of Concept
1. Configure a Shipit instance with two orgs in `Shipit.github`, e.g. `orgA` (no `webhook_secret`) and `orgB` (a real, secret-protected org with a deployed stack `orgB/victim-repo`).
2. Send `POST /github/webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `orgA`; `Shipit.github(organization: 'orgA').verify_webhook_signature` returns `true` immediately since `orgA` has no `webhook_secret`.
4. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name('orgB/victim-repo')`, matching the real `orgB` stack, and triggers `sync_github` on it — despite the request never being validated by any secret belonging to `orgB`. [7](#0-6) [2](#0-1) [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
