## Finding: Webhook Organization Binding Is Not Enforced on the Records Handlers Act Upon

### Title
Cross-Organization Commit-Status Forgery via Webhook Signature/Repository Binding Mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Shipit's webhook signature verification is scoped to a GitHub organization (chosen from the payload itself), but the handlers that consume the payload never re-check that the object they mutate (a `Commit`, a `Stack`, a `Repository`) actually belongs to that same organization. This mirrors the report's core bug class: a delegator (here, any organization onboarded onto the Shipit instance) can supply payload fields that are never covered by the same trust check used to authenticate the request, and use them to act on a different principal's resources.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to verify the HMAC signature against using a value taken from the untrusted request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Shipit explicitly supports multiple GitHub App configs, one per organization, each with its own `webhook_secret` [3](#0-2)  — this multi-org layout is documented and tested (`test/dummy/config/secrets_double_github_app.yml`).

Once the signature check passes for organization "OrgA" (because the attacker legitimately owns a GitHub App installed on their own org/repo and therefore knows OrgA's `webhook_secret`), the event handlers process the *rest* of the same JSON body without ever re-validating that the acted-upon resource belongs to OrgA:

- `StatusHandler#process` looks up commits **globally by SHA only**, with no scoping to the organization that authenticated the request, or even to the `repository.full_name` field in the same payload: [4](#0-3) 
- The generic `Handler` base class does scope most handlers by `repository.full_name` [5](#0-4) , but that field is taken from the same untrusted body and is never cross-checked against `repository.owner.login`/`organization.login` — the field used to pick the verification secret. `Repository.from_github_repo_name` performs a plain DB lookup with no ownership assertion tying it back to the authenticating org [6](#0-5) .

The equality that should hold and is broken:
`organization whose webhook_secret authenticated the request == organization that owns the repository/commit the handler mutates`

Before the attacker's request: OrgA can only affect stacks/commits under its own repositories (verified by its own secret). After the attacker's crafted request: OrgA's valid signature (using its own secret) authorizes a payload whose `repository.full_name`/`sha` fields point at OrgB's stack/commit, and the handler acts on that target with no re-verification.

### Impact Explanation
`StatusHandler` writes GitHub commit statuses into Shipit's database via `commit.create_status_from_github!`, and Shipit's CI-gating and continuous-deployment/merge-queue logic (`ci.require`, review checks) consult these statuses to decide whether a commit is safe to merge or deploy. An attacker who legitimately administers a GitHub App for their own organization (OrgA) on a shared multi-tenant Shipit install can forge a "success" status for a commit SHA belonging to a different organization's tracked repository (OrgB), as long as they can produce/guess a matching SHA (trivial for public repos, or for any commit whose content they can reproduce). This can cause Shipit's automated merge/deploy safety checks to be satisfied for OrgB's repository despite the attacker having no access whatsoever to OrgB's GitHub organization, its App installation, or its `webhook_secret` — i.e., an unauthorized deploy/merge triggered against a repository the attacker does not own or have write access to. This satisfies the "unauthorized deploy" Critical-tier impact criterion.

### Likelihood Explanation
This requires only that: (1) the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration), and (2) the attacker legitimately controls a GitHub App/webhook secret for their own org — no access to the victim org's credentials, no session, no API token. This is a realistic deployment topology for any Shipit instance shared across multiple GitHub orgs, making the likelihood non-trivial for that class of deployment.

### Recommendation
Enforce the authentication binding explicitly: after `verify_signature` resolves the organization from the payload, every handler must scope its lookups (commits, repositories, stacks) to that same organization, and reject payloads whose `repository.full_name`/`repository.owner.login`/`organization.login` fields don't agree with each other and with the organization used for verification. Concretely, `StatusHandler` should filter `Commit.where(sha: params.sha)` by `commit.stack.repository.owner == repository_owner` (or equivalent), and the shared `Handler` base class should assert `repository.owner == verified_organization` before resolving `stacks`.

### Proof of Concept
1. Deploy Shipit with a multi-organization `secrets.yml` (as in `test/dummy/config/secrets_double_github_app.yml`), onboarding both `OrgA` (attacker-controlled) and `OrgB` (victim) as separate GitHub App installations, each with distinct `webhook_secret`s.
2. As the legitimate owner/admin of OrgA's GitHub App, compute `X-Hub-Signature` over a crafted JSON body using OrgA's own `webhook_secret`.
3. In that JSON body, set `X-Github-Event: status`, and set `sha` to a known commit SHA that exists in OrgB's tracked repository/stack (e.g., a public commit, or one the attacker can reproduce), with `state: "success"`.
4. POST to `/github/webhooks` (or the mounted webhook path). `WebhooksController#verify_signature` resolves `repository_owner` from the body (attacker can also omit/omit-mismatch the `repository`/`organization` keys used purely for that lookup, or set it to "OrgA" to pass verification) while `StatusHandler#process` matches purely on `sha` with no organization scoping, creating a forged "success" status on OrgB's commit.
5. Observe that OrgB's Shipit stack now reflects a passing CI status for that commit, satisfying `ci.require` gating it did not actually pass, without the attacker ever possessing OrgB's `webhook_secret` or any OrgB credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
