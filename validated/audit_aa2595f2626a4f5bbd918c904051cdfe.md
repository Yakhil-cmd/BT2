### Title
Webhook signature verification binds to `repository.owner.login`, not the `repository.full_name` the handlers act on, allowing cross-organization/cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while every webhook handler resolves the target `Stack`/`Repository` to mutate using the *different* field `params.dig('repository', 'full_name')`. [1](#0-0) [2](#0-1) [3](#0-2)  Nothing in the verification path enforces that the owner segment of `full_name` actually equals the `repository.owner.login` used to pick the secret. This is the "organization authenticated vs. repository written" binding, and it is broken because the two fields are read independently from attacker-suppliable JSON.

### Finding Description
The HMAC signature (`X-Hub-Signature`) covers the entire raw request body, so an attacker cannot forge a signature without knowing the correct per-organization `webhook_secret`. However, the attacker *does* know that secret for any organization/repository they legitimately administer on GitHub and for which they have configured (or can configure) the Shipit webhook themselves — this is routine, low-privilege GitHub repo-admin capability, not a Shipit credential.

`verify_signature` picks the app/secret purely from the payload's `repository.owner.login` (or `organization.login`):
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
``` [4](#0-3) 

```ruby

Once verified, `create` dispatches the raw parsed body to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

``` [5](#0-4) 

Every handler resolves the target repository/stack from a *different* payload field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

The same pattern repeats in every PR handler (`params.repository.full_name`) used to locate `Repository`/`ReviewStack` and archive/unarchive/create stacks. [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used to select the *authenticating* secret) and `repository.full_name` (used to select the *repository acted on*) are read from two independent JSON keys inside the same attacker-controlled body, an attacker who legitimately controls an organization `attacker-org` tracked by this Shipit instance (and therefore knows/sets its `webhook_secret` on GitHub's side) can:
1. Craft a JSON body with `"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}` (or, for `membership`-style events, exploit `organization.login` similarly against `MembershipHandler`, which trusts `params.organization.login` to attach/detach `Team` membership used later by `Shipit.github_teams` authorization checks [8](#0-7) [9](#0-8) ).
2. Sign that body with `attacker-org`'s known secret.
3. POST it to `WebhooksController#create`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against a secret the attacker controls.
4. The handler, however, acts on `victim-org/victim-repo`, e.g. updating commit statuses (`StatusHandler`), archiving/unarchiving review stacks, or creating pull-request-based `ReviewStack`s for a repository the attacker has no legitimate relationship with.

### Impact Explanation
This breaks the equality that should hold: `authenticated_organization == owner(repository_written)`. Exploiting it lets a low-privilege actor (admin of one tracked, low-trust org/repo) forge webhook events that are processed as if legitimately sent by GitHub for a completely different, higher-trust repository tracked by the same Shipit instance — enabling unauthorized state changes (stack archive/unarchive/provision, commit status manipulation feeding into CI/merge gating, team membership changes feeding `Shipit.github_teams` authorization) on repositories the attacker does not control. This matches the "cross-repository writes" / "escalation into `Shipit.github_teams` authorization" impact classes.

### Likelihood Explanation
Requires the attacker to control (administer webhooks for) at least one GitHub organization/repository that this specific Shipit instance already tracks — a realistic scenario for any multi-tenant/shared Shipit deployment where different teams/orgs onboard their own repos. No Shipit credentials, API tokens, or GitHub App private keys are needed; the attacker only needs the webhook secret for their own tracked org, which they legitimately possess/configure.

### Recommendation
Do not select the verification secret from an attacker-controlled field that differs from the field used for authorization decisions. Either:
- Verify the signature against every configured secret that is plausible for the event, then require the resolved organization to equal the owner segment parsed from `repository.full_name` (or `organization.login` used by the handler) before dispatching, rejecting on mismatch; or
- Derive both the verification key and the acted-upon repository from the *same* canonical field (e.g., always use `repository.full_name`'s owner segment, or the `organization.login` for org-scoped events) and fail closed if that owner has no repositories/teams currently tracked under that exact identity.

### Proof of Concept
1. Shipit tracks two orgs: `attacker-org/low-trust-repo` (attacker administers this org's GitHub webhook and therefore knows its `webhook_secret`) and `victim-org/critical-repo`.
2. Attacker crafts a `status` (or `pull_request`) webhook JSON body:
```json
{
  "sha": "<some sha in victim-org/critical-repo>",
  "state": "success",
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/critical-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and successfully verifies the attacker-known secret. [1](#0-0) 
5. `StatusHandler`/`Handler#stacks` resolves the target repository via `repository.full_name = "victim-org/critical-repo"` [3](#0-2) , and the forged commit status is applied to `victim-org/critical-repo`'s stack, potentially unblocking CI-gated deploys/merges for a repository the attacker does not control.
