### Title
`StatusHandler#process` resolves `Commit` records by bare `sha` with no repository/organization scoping, allowing an org-A-signed `status` webhook to write Statuses onto org B's Stack commits - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#create` verifies the webhook signature against the secret of `Shipit.github(organization: repository_owner)` derived from the payload's own `repository.owner.login`, then dispatches the full parsed `params` to every registered handler for the event. `StatusHandler#process` uses that trust to run `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, matching purely on `sha` with no filter on `repository.full_name`, `repository_owner`, or `commit.stack`. Any commit row in the entire `shipit_commits` table sharing that `sha` - regardless of which organization/stack it belongs to - gets a Status written.

### Finding Description
The binding that should hold is: `organization whose webhook_secret verified the request body == organization owning every Commit row the handler mutates`. Tracing the code:

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and validates the HMAC signature using `Shipit.github(organization: repository_owner)`'s secret (app/controllers/shipit/webhooks_controller.rb:24-30, :59-62). This proves only that the sender knows org-A's `webhook_secret` for the org named in the payload.
- `create` then calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (app/controllers/shipit/webhooks_controller.rb:12), passing the *entire* JSON body, unfiltered, to handlers.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This query has no `stack_id`, `repository`, or organization predicate at all - `sha` is a raw string with no per-repo namespace in the `shipit_commits` schema, so it is a global lookup across every `Stack` in the installation.
- `Commit#create_status_from_github!` → `#add_status` → `statuses.replicate_from_github!(stack_id, github_status)` writes a `Status` scoped to `commit.stack_id`, whatever stack that commit's row belongs to (app/models/shipit/commit.rb:165-169, 366-386). It also emits `commit_status`/`deployable_status` hooks and can call `stack.schedule_merges`, which is a real cross-tenant side effect - it can promote a commit toward being considered deployable in an org/stack the attacker never authenticated for.

After tracing, the two sides of the equality diverge: the org that *signed* the request (org A) is not the org that *owns* the mutated commit (org B) when a `sha` collision exists across stacks. Nothing in `drop_unhandled_event`, `ExplicitParameters` schema validation (`requires :sha, String` etc.), or model validations on `Repository`/`Stack` re-checks that the commit's stack belongs to `repository_owner`. The `ExplicitParameters` schema only validates *shape* of the payload fields, not which records they may touch.

Attack: attacker owns/administers repo A under org A and has (legitimately) org A's real `webhook_secret` configured by their own Shipit-connected org, or simply triggers their own repo's real GitHub webhook delivery for a `status` event (no secret theft needed - it's their own repo's legitimately configured webhook). They craft a commit whose `sha` intentionally collides with a `sha` already present in org B's stack (achievable via cherry-pick/rebase producing identical trees+metadata, forked history, or a monorepo/mirror scenario where the same upstream commit is tracked by multiple orgs' Stacks - `sha` collision across unrelated repositories requires either a shared ancestor commit or a crafted duplicate; GitHub validates `sha` as the actual git object id of *their* repo, so the attacker needs a commit in their own repo whose sha equals one that also exists in org B's tracked history, which is achievable when repos share history, e.g., forks/mirrors/vendored branches). They send (via real GitHub delivery or a raw HTTP POST replicating a legitimately-signed payload) a `status` event naming `repository.full_name = "orgA/repo"` but `sha` = the colliding value. `verify_signature` passes because the signature matches org A's secret and the payload correctly declares org A. `StatusHandler` then writes a `Status` onto org B's `Commit` row for that colliding `sha`, potentially affecting org B's Stack merge/deploy gating (`stack.schedule_merges`, `deployable_status` hook).

### Impact Explanation
An attacker who fully controls one legitimately onboarded repository can inject CI/status state (`success`/`error`/`pending`, arbitrary `description`, `target_url`, `context`) into another tenant's `Commit`/`Stack` whenever a `sha` collision exists, without ever authenticating for that tenant. This can flip a foreign commit's `deployable?` state and trigger `stack.schedule_merges`/continuous delivery hooks for a stack the attacker has no access to - i.e., a payload from one repository mutating another's stack/commit data, which is explicitly listed as a Critical-impact category. The blast radius is every Stack in the installation sharing a colliding `sha` with the attacker-controlled repo, and the attack is repeatable per status event.

### Likelihood Explanation
Preconditions: attacker needs to control at least one repository already connected to the Shipit instance (a low bar - many Shipit deployments are open to internal or even external contributors), and needs a `sha` collision between a commit they can push/deliver a status for and a commit tracked by a victim Stack. True cryptographic sha1 collision is infeasible, but *legitimate, non-adversarial* sha collisions across Stacks are realistic in practice: forked repositories, repository renames/migrations, or monorepo/multi-remote setups where the same git commit object is pushed to and tracked by multiple GitHub repos/orgs, each with its own Shipit Stack. In any such topology the attack requires zero secret compromise and a single crafted/real webhook delivery, making it highly feasible and fully repeatable wherever that topology exists.

### Recommendation
In `StatusHandler#process` (and any other handler resolving records purely by `sha`), scope the `Commit` lookup by the repository identified in the verified payload, e.g. join through `Stack` and filter `stack.repo_owner`/`repo_name` (or organization) to match `params.dig('repository','full_name')`/`repository_owner`, so a commit is only mutated if it belongs to a Stack whose repository matches the organization that produced a validly-signed payload.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "status webhook signed for orgA cannot write a Status onto orgB's commit sharing the same sha" do
  stub_request_signature_as_valid! # stub GithubApp#verify_webhook_signature to return true, simulating a legitimately-signed orgA payload

  colliding_sha = 'a' * 40
  stack_b = shipit_stacks(:shipit) # belongs to orgB
  commit_b = stack_b.commits.create!(sha: colliding_sha, message: 'orgB commit')

  payload = {
    'repository' => { 'full_name' => 'orgA/repo', 'owner' => { 'login' => 'orgA' } },
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci/attacker'
  }

  post :create, body: payload.to_json, params: { as: :json },
       headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => 'sha1=irrelevant-because-stubbed' }

  assert_equal 'success', commit_b.reload.status.state
  # Assert: orgA never authenticated for orgB, yet orgB's commit/stack state was mutated.
  assert_equal 'orgB', commit_b.stack.organization # binding orgA-signed != orgB-owned is violated
end
```
