### Title
Cross-repository commit-status forgery via unscoped `StatusHandler` webhook processing - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook handler updates commit CI status by SHA alone, with no check that the SHA belongs to the repository/organization that the verified webhook signature was actually issued for. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` authenticates a webhook only against the organization derived from the payload's `repository.owner.login` (or `organization.login`), using that organization's configured secret: [1](#0-0) 

This proves the request came from GitHub for *some* repository owned by that organization — nothing more. `StatusHandler#process`, however, ignores the repository entirely and matches on SHA globally across the whole Shipit installation: [2](#0-1) 

Unlike `PushHandler` and `CheckSuiteHandler`, which resolve the target through `Handler#stacks`/`Repository.from_github_repo_name(repository_name)` before touching any records: [3](#0-2) [4](#0-3) [5](#0-4) 

`StatusHandler` never uses `payload.dig('repository', 'full_name')` to scope the write — `Commit.where(sha: params.sha)` runs across every stack/repository tracked by this Shipit instance, and `commit.create_status_from_github!(params)` writes an attacker-controlled `state`/`description`/`context`/`target_url` to any matching commit found, regardless of which organization actually owns it.

Because git commit SHAs are content-addressed and deterministic, an attacker who has push access to any repository configured on the same Shipit instance (Org B) can construct a commit object identical (same tree, parents, author/committer, timestamps, message) to a target commit that exists in a different, unrelated repository/organization (Org A) also tracked by this Shipit instance, then trigger a legitimately GitHub-signed `status` webhook for Org B. `verify_signature` succeeds (it's a real webhook from Org B's real secret), but `StatusHandler` then writes the forged status onto the colliding SHA wherever it appears — including Org A's stack.

### Impact Explanation
Commit status directly gates deploy eligibility (`Commit#deployable?`, `ci.require`) and merge-queue behavior: [6](#0-5) 

By forging a `success` status on a colliding SHA in a foreign stack, an attacker in Org B can flip `deployable?` to true for a commit in Org A they have no access to, enabling `stack.trigger_deploy`/merge-queue automation to ship that commit — an unauthorized deploy driven by data written outside the trust boundary the webhook signature was meant to establish. This satisfies the "unauthorized deploy" Critical-impact bar.

### Likelihood Explanation
Exploitation requires: (1) the attacker controls a repository configured on the same Shipit instance as the victim stack (a realistic multi-tenant Shipit deployment scenario, not a privileged Shipit account), and (2) the ability to construct a byte-identical git commit object to a target commit and trigger a `status` event on it via the GitHub API for their own repo — both practical for anyone with ordinary push access to any tracked repo, no Shipit credentials or GitHub App secret needed.

### Recommendation
Scope `StatusHandler#process` to the repository the webhook was actually verified for, mirroring `PushHandler`/`CheckSuiteHandler`: restrict the `Commit` lookup to `stacks` (derived from `payload.dig('repository', 'full_name')`) instead of a bare `Commit.where(sha: params.sha)` across the whole installation.

### Proof of Concept
1. Attacker has push access to `org-b/repo-b`, which is also configured as a Shipit stack on the shared instance.
2. Attacker identifies a target commit SHA `S` in `org-a/repo-a` (another stack on the same instance) that they want marked deployable/CI-green.
3. Attacker crafts a commit in `repo-b` with identical tree/parent/author/committer/message/timestamps so its SHA equals `S` (feasible since git SHAs are just a hash of that content) and pushes/creates it.
4. Attacker triggers (or GitHub automatically sends) a `status` webhook for `repo-b` with `sha: S, state: "success", context: "ci/required"`.
5. `WebhooksController#verify_signature` validates the signature against Org B's real secret and passes.
6. `StatusHandler#process` executes `Commit.where(sha: S)`, which also matches the commit in `org-a/repo-a`, and calls `create_status_from_github!` on it, marking it successful and potentially deployable in a repository the attacker never had access to.
