### Title
Permissionless `DepositDelegatorRewards` allows griefing validators by locking their vote account and blocking withdrawal/closure - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
The Audius report describes delegators (unprivileged third parties) accumulating enough stake against a service provider that the provider's own privileged action (`deregister`) is blocked by a balance check it does not control. The Agave analog is the SIMD-0123 `DepositDelegatorRewards` vote-program instruction: **any** unprivileged signer can push lamports into `pending_delegator_rewards` on **any** vote account, and the vote program's `withdraw` handler treats that attacker-controlled field as a mandatory reserve that blocks the account's own `authorized_withdrawer` from closing or fully withdrawing the account.

### Finding Description
`deposit_delegator_rewards` in [1](#0-0)  only requires that the "source" account (whoever is paying the lamports) sign the transfer — there is no check that the caller is an actual delegator, related staker, the block-revenue collector, or otherwise authorized with respect to the target vote account: [2](#0-1) 

It transfers lamports from the caller into the vote account via CPI and then unconditionally increments `pending_delegator_rewards`: [3](#0-2) 

The vote processor dispatches this instruction with no additional relationship/authorization checks beyond the feature gate and account count: [4](#0-3) 

`withdraw` then treats `pending_delegator_rewards` as an inviolable reserve on top of rent-exemption. If the withdrawer tries to fully close the account (`remaining_balance == 0`) while `pending_delegator_rewards > 0`, the instruction fails outright; for partial withdrawals, the minimum retained balance is `rent_exempt + pending_delegator_rewards`: [5](#0-4) 

Because the deposit amount is entirely attacker-controlled and the increment has no relation to actual stake/delegation to that validator, any funded account can call `DepositDelegatorRewards` against a victim's vote account (even with a deposit of 1 lamport) and immediately prevent the `authorized_withdrawer` from closing that vote account — mirroring the Audius pattern where unprivileged delegators' stake made the SP's own `maxAccountStake`-based deregister check fail.

### Impact Explanation
This is a permanent-freeze-style griefing vector against validator vote accounts: the legitimate account owner (`authorized_withdrawer`) loses the ability to close or fully withdraw their vote account as long as `pending_delegator_rewards > 0`, and that value can be perpetually re-inflated by any unrelated third party at negligible cost (the tests confirm even a 0-lamport deposit is accepted as a no-op, and any positive deposit is accepted regardless of relation to the vote account) — see the exercised behavior in [6](#0-5)  and the direct demonstration in [7](#0-6) . This matches the "permanently frozen accounts" impact category, since an attacker can repeatedly top up `pending_delegator_rewards` faster than epoch-based reward distribution can drain it, indefinitely denying account closure/withdrawal to the rightful owner.

### Likelihood Explanation
The instruction is gated behind `commission_rate_in_basis_points`, `custom_commission_collector`, and `block_revenue_sharing` (SIMD-0123) feature flags, as enforced in the processor. Based on `feature-set/src/lib.rs`, `block_revenue_sharing` (SIMD-0123) is present as a feature ID but I could not confirm from the available index whether it is activated on any live cluster; the instruction code path is fully implemented and tested in the repository regardless. Once these features are active, exploitation requires no special privilege — only a signer and a small amount of lamports — making likelihood high in a post-activation world, but currently gated by feature-activation status (which I was unable to fully confirm within the tool budget).

### Recommendation
- Restrict `DepositDelegatorRewards` so that only the designated block-revenue collector (or another authorized/verified source tied to actual block-reward distribution) can deposit into `pending_delegator_rewards`, rather than accepting deposits from an arbitrary signer.
- Alternatively/additionally, decouple the withdraw-blocking reserve from an unbounded, permissionlessly-inflatable field: e.g., cap the amount any single unrelated caller can contribute, rate-limit deposits, or ensure `pending_delegator_rewards` is fully and promptly zeroed each epoch regardless of size so it cannot be perpetually re-grown by third parties faster than it drains.
- Consider decoupling the full-account-close check from `pending_delegator_rewards` growth caused by non-authorized depositors, e.g. only counting deposits attributable to verified block-revenue sources toward the reserve enforced in `withdraw`.

### Proof of Concept
1. Attacker (any funded keypair, no relationship to the victim validator) submits a `DepositDelegatorRewards { deposit: 1 }` instruction targeting the victim's vote account, with itself as the "source" signer and the system program, per the account layout validated in [8](#0-7) .
2. This succeeds unconditionally (no relation to the vote account required), incrementing `pending_delegator_rewards` from 0 to 1, per [9](#0-8) .
3. The victim's `authorized_withdrawer` now attempts `Withdraw(full_balance)` to close the vote account; this fails with `InstructionError::InsufficientFunds` because `pending_delegator_rewards > 0`, exactly as demonstrated in [10](#0-9) .
4. The attacker can repeat step 1 indefinitely (each deposit only costing the deposited lamports, which land in the victim's account, but the `pending_delegator_rewards` accounting lock persists), keeping the vote account perpetually un-closeable by its rightful owner.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

        // SIMD-0123: vote account cannot be closed if
        // pending_delegator_rewards > 0.

            return Err(InstructionError::InsufficientFunds);
        }

        let reject_active_vote_account_close = vote_state
            .epoch_credits()
            .last()
            .map(|(last_epoch_with_credits, _, _)| {
                let current_epoch = clock.epoch;
                // if current_epoch - last_epoch_with_credits < 2 then the validator has received credits
                // either in the current epoch or the previous epoch. If it's >= 2 then it has been at least
                // one full epoch since the validator has received credits.
                current_epoch.saturating_sub(*last_epoch_with_credits) < 2
            })
            .unwrap_or(false);

        if reject_active_vote_account_close {
            return Err(VoteError::ActiveVoteAccountClose.into());
        } else {
            // Deinitialize upon zero-balance
            VoteStateHandler::deinitialize_vote_account_state(&mut vote_account, target_version)?;
        }
    } else {
        // SIMD-0123: withdrawable balance when pending_delegator_rewards > 0
        // is lamports - pending_delegator_rewards - rent_exempt_minimum.
        let min_rent_exempt_balance = rent_sysvar.minimum_balance(vote_account.get_data().len());
        let min_balance = min_rent_exempt_balance
            .checked_add(pending_delegator_rewards)
            .ok_or(InstructionError::ArithmeticOverflow)?;
        if remaining_balance < min_balance {
            return Err(InstructionError::InsufficientFunds);
        }
    }
