### Title
`StatusHandler#process` writes a `Status` on any commit matching `sha` regardless of which organization's `webhook_secret` verified the request - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload by looking up the GitHub App/`webhook_secret` for `repository_owner` (`params.dig('repository','owner','login')`) and validates the HMAC against that org's secret only. `StatusHandler#process`, unlike `PushHandler`/`CheckSuiteHandler`, never re-scopes to the `Handler#stacks` helper (which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`); it queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match.

### Finding Description
Binding claimed safe: `verifying_org(payload) == owning_org(mutated_stack)`. Trace:
- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, verifying the HMAC using **attacker-org's own** `webhook_secret` [1](#0-0) , [2](#0-1) . This proves only that the payload was sent by someone with attacker-org's `webhook_secret` — it says nothing about which commit/stack the payload should be permitted to mutate.
- `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` with the raw, unscoped payload [3](#0-2) .
- `Handler` provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository','full_name')` [4](#0-3) . `PushHandler` and `CheckSuiteHandler` correctly use this scoping — `PushHandler#process` only touches `stacks.not_archived.where(branch:)` [5](#0-4) , and `CheckSuiteHandler#process` only touches `stacks.where(branch: ...).commits.where(sha: ...)` [6](#0-5) .
- `StatusHandler#process`, however, ignores `stacks`/`repository_name` entirely and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across every stack/organization in the Shipit instance [7](#0-6) .
- `Commit#create_status_from_github!` creates a `Status` row keyed to `commit.stack_id`, i.e. whatever stack that commit actually belongs to, with no check that the stack's owning org matches `repository_owner` [8](#0-7) , and `Status.replicate_from_github!` persists it [9](#0-8) .

Exploit: attacker controls `attacker/repo` under `attacker-org`, which has a legitimate GitHub App installation on Shipit with its own `webhook_secret`. Attacker crafts a `status` event body `{sha: X, state: 'success', repository: {full_name: 'attacker/repo', owner: {login: 'attacker-org'}}}` where `X` is the SHA of a commit currently tracked in `victim-org/victim-repo`'s stack (SHAs are 40-hex globally unique per commit content but the check performed is purely `Commit.where(sha: ...)` with no repository filter — any commit row in the Shipit DB with that SHA, from any tenant, matches). Attacker signs the payload with attacker-org's `webhook_secret` (which they legitimately possess for their own org) and POSTs to `/webhooks` with `X-Github-Event: status`. `verify_signature` passes because the signature is valid for attacker-org. `StatusHandler#process` then finds the victim's `Commit` row (matched purely by `sha` string equality) and writes a `Status` on it belonging to `victim_stack.id`.

Existing guards checked and found insufficient: `verify_signature`/`GithubApp#verify_webhook_signature` only proves the sender knows *some* org's secret, not that the org matches the target stack [10](#0-9) ; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate shape, not ownership [11](#0-10) ; there is no `require_permission!`/`stacks` scoping applied in this handler.

### Impact Explanation
An attacker who legitimately owns an org/repo with a Shipit GitHub App installed can inject a fabricated `Status` (e.g., `state: 'success'`) onto a commit belonging to any other tenant's stack, as long as they can predict/observe a SHA also tracked by another org's stack (SHAs are public on GitHub; if commits are cherry-picked, mirrored, or shared across orgs/forks, this is trivially satisfiable, and even without collision the write still occurs against whatever commit row matches — the attacker doesn't need to guess anything if they know the victim's SHA, which is often public). Because `deployable?` on `Commit` depends on `success?` from statuses [12](#0-11) , and `Status#enable_ci_on_stack`/`schedule_continuous_delivery` fire on creation [13](#0-12) , this can influence whether a victim's commit becomes deployable or trigger continuous-delivery merge logic — a cross-tenant write with a plausible path to an unauthorized deploy. This matches "a payload for one repository mutating another's stack, commit" — Critical.

### Likelihood Explanation
Preconditions: attacker needs a Shipit-registered GitHub org/repo with a valid App installation (attacker-org), which is achievable by any GitHub user if the Shipit instance's App is public/installable, or by any org onboarded onto the same multi-tenant Shipit instance. Attacker cost is low: no session, no API token, no victim secrets — only their own legitimate webhook secret and a target SHA that also exists as a `Commit` row for a victim stack. This is repeatable against any commit SHA in the database, and blast radius spans every stack/tenant hosted on the same Shipit instance since `Commit.where(sha:)` is global and unscoped.

### Recommendation
Scope `StatusHandler#process` to the requesting repository the same way `PushHandler`/`CheckSuiteHandler` do: use `stacks` (derived from `payload.dig('repository','full_name')`) to find candidate stacks, then look up `stack.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`, ensuring the mutated commit's stack always belongs to the repository that produced/signed the payload.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status from attacker org does not create a Status on a victim org's commit with colliding sha" do
  request.headers['X-Github-Event'] = 'status'

  victim_stack = shipit_stacks(:shipit) # belongs to org "shopify" per fixtures
  victim_commit = shipit_commits(:first)
  colliding_sha = victim_commit.sha

  attacker_payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  # verify_signature is stubbed true (attacker legitimately owns attacker-org's webhook_secret)
  assert_no_difference 'victim_commit.statuses.count' do
    post :create, body: attacker_payload, as: :json
  end
  # If vulnerable, the above assertion fails: commit.statuses.last.stack_id == victim_stack.id
end
```
Binding before: `verifying_org == 'attacker-org'`, `owning_org(victim_commit.stack) == 'shopify'` — unequal. Binding after (current buggy code): a `Status` row is created with `stack_id == victim_stack.id` despite the signature having verified only `attacker-org`, proving the divergence is exploited. With the recommended fix (scoping via `stacks`/`repository_name`), `Commit.where(sha:)` would be replaced by `stacks.commits.where(sha:)`, `stacks` would resolve to `Repository.from_github_repo_name('attacker/repo')` (nil/empty), and no `Status` would be created — restoring the equality.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
