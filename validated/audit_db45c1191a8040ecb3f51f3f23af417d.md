### Title
Cross-tenant webhook forgery: `repository_owner` (signature verifier selector) and `params.repository.full_name` (handler's repo resolver) are independently attacker-set, letting one organization's webhook secret provision a `ReviewStack` on another organization's repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to verify a webhook against using `repository_owner`, which falls back to `params.dig('organization','login')` whenever `repository.owner.login` is absent from the payload. `OpenedHandler`/`ReviewStackAdapter`, however, resolve the actual `Shipit::Repository`/`Stack` to mutate exclusively from `params.repository.full_name`, a field the `pull_request` schema requires only as a bare string (`requires :repository do requires :full_name, String end`) with no `owner.login` requirement. Because these two fields are populated independently by the attacker-controlled JSON body, a webhook signed with organization A's secret can be crafted to target organization B's repository.

### Finding Description
The invariant the engine relies on is:
`organization_whose_secret_authenticated_the_request == owner_of(repository_the_handler_mutates)`

i.e. `repository_owner` (as used in `Shipit.github(organization: repository_owner)`, [1](#0-0) ) should equal the owner segment of `params.repository.full_name`, the field `OpenedHandler#repository` actually uses to look up the target repository ( [2](#0-1) ).

`repository_owner` is computed as:
```ruby
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [3](#0-2) 

If the attacker's JSON omits `repository.owner.login` (only supplying `repository.full_name`, which is all the `pull_request` handler schema requires — [4](#0-3) ), verification falls back to `organization.login`, a completely separate, attacker-controlled top-level field. `Shipit.github(organization:)` then looks up per-organization webhook secrets via `github_app_config(organization)` in multi-org deployments ( [5](#0-4) ), and `verify_webhook_signature` HMAC-checks the raw body against that org's `webhook_secret` ( [6](#0-5) ).

Once signature verification passes, `OpenedHandler#process` resolves the repository purely from `params.repository.full_name` ( [7](#0-6) ) and calls `ReviewStackAdapter#find_or_create!`, which creates a real `Stack` record scoped under that repository, with `branch: params.pull_request.head.ref` and `environment: "pr#{params.number}"`, both fully attacker-controlled, then enqueues it for provisioning (`ReviewStackProvisioningQueue.add(stack)` → `stack.provisioner.up`) — [8](#0-7) .

Exploit flow: an attacker who administers their own organization "OrgA" on a shared, multi-tenant Shipit instance (and therefore knows OrgA's `webhook_secret`, since they configured that webhook themselves) sends:
```json
{
  "action": "opened",
  "number": 999,
  "pull_request": {..., "head": {"sha": "...", "ref": "attacker-branch"}, "labels": [...]},
  "repository": {"full_name": "OrgB/victim-repo"},
  "organization": {"login": "OrgA"},
  "sender": {"login": "attacker"}
}
```
signed with `HMAC-SHA1(OrgA_webhook_secret, raw_body)`. `verify_signature` resolves `repository_owner` to `"OrgA"`, verifies successfully against OrgA's real secret, but `OpenedHandler` acts on `OrgB/victim-repo` — a repository OrgA's secret was never meant to authenticate.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema only validates types/presence, not cross-field consistency between `organization.login` and `repository.full_name`; and there is no check anywhere that `repository.owner.login == organization.login` or that the authenticating organization matches the repository being mutated.

### Impact Explanation
An attacker who legitimately controls one organization/repository registered on a shared Shipit instance can use that organization's own webhook secret to create arbitrary `ReviewStack` records (and trigger their provisioning) under any other organization's repository known to the same Shipit instance, with attacker-chosen branch and PR metadata. This is a "payload for one repository mutating another's stack" — squarely a cross-tenant integrity violation, matching the Critical impact category. It is repeatable against any repository name the attacker guesses/knows, for every `pull_request`-family handler that resolves the repo from `params.repository.full_name` (e.g. `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`), not just `OpenedHandler`.

Note: `OpenedHandler`/`ReviewStackAdapter` create/provision a review stack; they do not themselves call `MergeRequest#merge!` or interact with `merge_queue_enabled`. The "green head advances the merge queue and `merge!` fires" amplification described in the question is not part of this handler's code path — merges are driven by `ProcessMergeRequestsJob`/`MergeRequest#merge!` via separate label/status handlers, not `OpenedHandler`. The demonstrable, in-scope impact here is unauthorized cross-tenant `ReviewStack` creation/provisioning.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment where `secrets.github` is keyed per-organization (so distinct webhook secrets exist per org) — this is a supported and documented configuration (`Shipit.github_app_config`); (2) the attacker administers at least one such organization/repo on the same instance (able to know its own webhook secret); (3) the victim repository has `review_stacks_enabled` and a matching `provisioning_behavior` (`allow_all`, or label-based — attacker fully controls `labels` in the forged payload). Given these, the attack costs a single crafted HTTP POST with a validly-computed HMAC and is fully repeatable.

### Recommendation
In `Shipit::WebhooksController#repository_owner`, do not silently fall back to `organization.login` when `repository.owner.login` is absent from a `pull_request`-family payload; alternatively, after signature verification, explicitly re-derive and enforce that the repository the handler will act on (`params.repository.full_name`'s owner segment) matches the organization whose secret authenticated the request, rejecting the webhook (422) on mismatch.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`), using a multi-org secrets fixture (`secrets_double_github_app.yml`, already used elsewhere per `test/unit/shipit_test.rb`):
1. Configure `Shipit.secrets.github` with two orgs, `"OrgA"` and `"shopify"`, each with distinct `webhook_secret`s.
2. Create `Repository` for `"shopify/shipit-engine"` (`review_stacks_enabled: true`, `provisioning_behavior: allow_all`) — this is `repository_owner_side_B`.
3. Build the `pull_request` `opened` payload: `repository: {full_name: "shopify/shipit-engine"}` (no `owner.login`), `organization: {login: "OrgA"}`, valid `pull_request` body with `head.ref = "attacker-branch"`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', OrgA_webhook_secret, raw_body)`.
5. POST to `/webhooks` with `X-Github-Event: pull_request` and that signature.
6. Assert:
   - `assert_equal "OrgA", controller.send(:repository_owner)` (or equivalently that `Shipit.github` was invoked with `organization: "OrgA"`) — proving verification used OrgA's secret.
   - `assert_response :ok` (signature accepted).
   - `assert_difference -> { Shipit::Stack.where(repository: shopify_repo).count }, 1` — a `ReviewStack` was created under `shopify/shipit-engine` even though the request was authenticated only against `OrgA`'s secret, demonstrating `repository_owner ("OrgA") != owner_of(params.repository.full_name) ("shopify")`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
