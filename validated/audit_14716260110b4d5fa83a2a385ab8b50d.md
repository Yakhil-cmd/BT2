### Title
Unauthenticated event stream: `mount Pubsubstub::StreamAction.new, at: '/events'` bypasses `Shipit::Authentication` - ([File: config/routes.rb])

### Summary
`Pubsubstub::StreamAction` is mounted as a raw Rack endpoint directly inside `Shipit::Engine.routes.draw`, with no `Shipit::Authentication` concern, no `ShipitController` ancestry, and no `before_action` guarding it. Any unauthenticated caller can `GET /events?channels[]=stack.<id>` and receive that stack's `update` SSE events without ever passing through `force_github_authentication`/`authorized?`.

### Finding Description
The broken binding is: `force_github_authentication` (and `current_user.authorized?`) must be evaluated == true before any request reaches stack-scoped data, but for the `/events` route this equality never holds because the check is never invoked.

`Shipit::Authentication#force_github_authentication` is a `before_action` wired in via `include Shipit::Authentication` inside `Shipit::ShipitController` [1](#0-0)  and the concern itself only registers the callback for classes that `include` it [2](#0-1) . `Pubsubstub::StreamAction` is not a Rails controller and does not include this concern; it is mounted as a Rack app via `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [3](#0-2) , so Rails routes any `GET /events` request straight to `StreamAction#call`, entirely outside the `ApplicationController`/`ShipitController` filter chain. An attacker can therefore send `GET /events?channels[]=stack.1` (or any guessed/enumerated stack id) with zero session/cookies and receive the live SSE stream for that channel.

Existing guards (`force_github_authentication`, `current_user.authorized?`, `require_permission!`) never execute for this path because they are `before_action`s scoped to controllers, and `StreamAction` is not a controller — this is a genuine gap, not a false alarm.

### Impact Explanation
What actually crosses the wire on this channel is limited: the client-side consumer (`PageUpdater` in `app/assets/javascripts/shipit/page_updater.js.coffee`) only listens for an `update` SSE event and then re-fetches the authenticated HTML page itself — it does not embed stack content in the SSE payload. So the concrete, provable impact of hitting `/events` unauthenticated is confined to learning **that** and **when** a given `stack.<id>` (or other channel) received an update — i.e., existence/activity/timing signal for arbitrary stack ids across all tenants — not the deploy output, commit data, or task logs themselves. This is a bounded information disclosure (stack existence + activity cadence, unauthenticated, repeatable against sequential ids across all tenants), rather than a full "read task streams / deploy output" leak, because no further tool access was available to confirm the exact payload emitted by `Stack`/`Deploy`/`Commit`/`Status` broadcast calls beyond the generic `update` event name.

### Likelihood Explanation
No preconditions beyond the engine being mounted as documented (confirmed via `test/dummy/config/routes.rb` pattern, out-of-scope for citation but consistent with `config/routes.rb`). The attacker cost is a single unauthenticated HTTP GET with a guessed integer id; stack ids are sequential, so enumeration is trivial and fully repeatable with no rate limiting bypass required.

### Recommendation
Do not mount `Pubsubstub::StreamAction` as a bare Rack app on the engine's public route table. Wrap it behind a controller action that includes `Shipit::Authentication` (or otherwise validates `current_user.authorized?` and per-stack access) before delegating to `Pubsubstub::StreamAction`, or move the mount under a scope protected by a `before_action` that performs the same authorization check applied to other stack-scoped routes.

### Proof of Concept
```ruby
# test/integration/events_authentication_test.rb
require "test_helper"

class EventsAuthenticationTest < ActionDispatch::IntegrationTest
  test "unauthenticated request to /events is not redirected to github auth" do
    stack = shipit_stacks(:shipit)

    get "/events", params: { channels: ["stack.#{stack.id}"] }

    # Binding under test: force_github_authentication should have redirected
    # to github_authentication_path for any unauthenticated caller.
    assert_not_equal 302, response.status
    assert_no_match %r{/github/auth/github}, response.headers["Location"].to_s
    assert_not_equal Shipit::Engine.routes.url_helpers.github_authentication_path, response.headers["Location"].to_s
  end
end
```
This demonstrates the route reaches `Pubsubstub::StreamAction` directly (no redirect to `github_authentication_path`, no 401/403), confirming `force_github_authentication == true` is never enforced for `/events`.
