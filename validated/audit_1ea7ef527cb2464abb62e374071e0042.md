### Title
`User#authorized?` grants `Shipit.github_teams` access from a `Membership` row forged via the blank-`webhook_secret` signature bypass - (File: `app/models/shipit/user.rb`, `lib/shipit/github_app.rb`)

### Summary
`Shipit::User#authorized?` never re-validates team membership against GitHub; it trusts whatever `Membership` rows exist in the database. When a GitHub App's `webhook_secret` is unset, `GitHubApp#verify_webhook_signature` treats every webhook as verified regardless of the actual signature, letting an attacker forge a `membership` webhook that inserts a `Membership` row for an arbitrary login into any team listed in `Shipit.github_teams`. `authorized?` then answers `true` for that login even though no real GitHub API call ever confirmed the membership.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`authorized?(user) == (user is currently a real member, per live GitHub data, of some Team whose github_id is in Shipit.github_teams)`

In code, `authorized?` only checks local state: [1](#0-0) 

That local state (`Membership` rows) is populated exclusively by `MembershipHandler#process`, which performs no live GitHub confirmation — it just upserts a `Team` and adds/removes a `User` based purely on webhook payload fields: [2](#0-1) 

The only gate in front of the handler is `WebhooksController#verify_signature`: [3](#0-2) 

which delegates to `GitHubApp#verify_webhook_signature`: [4](#0-3) 

`return true unless webhook_secret` means that for any organization configured with a blank/absent `webhook_secret` (a configuration explicitly shown as valid in the repo's own sample config, `webhook_secret: # nil`), *every* webhook is accepted as authentic with no HMAC check at all. Combined with `repository_owner` being taken directly from attacker-controlled JSON (`params.dig('repository','owner','login') || params.dig('organization','login')`), an attacker can:

1. POST to `/webhooks` with `X-Github-Event: membership`, no valid `X-Hub-Signature` needed.
2. Body: `{"action":"added","team":{"id":<id in Shipit.github_teams>,"name":...,"slug":...,"url":...},"organization":{"login":"<org-with-blank-secret>"},"member":{"login":"attacker-login"}}`.
3. `verify_signature` calls `Shipit.github(organization: 'org-with-blank-secret').verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank for that org.
4. `MembershipHandler#process` runs, creating `User.find_or_create_by_login!('attacker-login')` and adding it to the target `Team` via `team.add_member(member)` — a plain `Membership` row insert, with `team.github_id` matching an entry in `Shipit.github_teams`.
5. Any subsequent call to `User.find_by(login: 'attacker-login').authorized?` returns `true` since `teams.where(id: Shipit.github_teams.map(&:id)).exists?` is now satisfied — with zero live GitHub verification ever performed.

Existing guards do not stop this: `drop_unhandled_event` only screens for registered event names (membership is registered); `verify_signature` is bypassed by design once `webhook_secret` is blank; `ExplicitParameters` (`params do ... end` block in the handler) only validates payload *shape*, not provenance; and `authorized?` itself performs no re-check against GitHub at authorization time.

### Impact Explanation
Once `authorized?` returns `true` for `attacker-login`, that identity is treated as a legitimate member of a `Shipit.github_teams`-gated team. Combined with completing OAuth as `attacker-login` (a step outside the scope of this webhook flow but noted as a follow-on in the question), this becomes escalation into `Shipit.github_teams` authorization — matching the documented High severity category ("escalation into `Shipit.github_teams` authorization"). The forged `Membership` persists indefinitely and is reusable for any team id present in `Shipit.github_teams` and any attacker-chosen login, as long as the corresponding organization's `webhook_secret` is blank. The blast radius is bounded to Shipit instances/organizations configured without a `webhook_secret`, but within that scope it is a full authorization bypass, not merely theoretical: the same forged webhook path is also independently a Critical "forged webhook accepted" bypass per the rubric.

### Likelihood Explanation
The attacker needs no session, token, or secret — only knowledge that some configured GitHub organization in this Shipit instance has a blank `webhook_secret` (this is a legitimate, documented configuration state per `config/secrets.development.shopify.yml`, which ships `webhook_secret: # nil`). Given that precondition, the attack is a single unauthenticated HTTP POST, fully repeatable and scriptable, with no rate limiting or additional validation blocking it.

### Recommendation
Fail closed instead of open when `webhook_secret` is blank: `verify_webhook_signature` should reject (return `false`) all webhooks for an organization that has no configured `webhook_secret`, rather than returning `true` unconditionally (`lib/shipit/github_app.rb:76-77`). Additionally, consider having `Team#add_member`/`authorized?` require periodic re-validation against live GitHub membership (e.g., via `refresh_members!`) rather than trusting a possibly-stale/forged local `Membership` row indefinitely.

### Proof of Concept
Minitest (webhook forgery + authorization check), no live GitHub call:
```ruby
test "forged membership webhook with blank webhook_secret grants authorized? true" do
  # Precondition: target org configured with blank webhook_secret (as in config/secrets.development.shopify.yml)
  Shipit.stubs(:github_teams).returns([shipit_teams(:shopify_developers)])
  Shipit.github(organization: 'shopify').stubs(:webhook_secret).returns(nil) # blank secret -> verify_webhook_signature returns true unconditionally

  @request.headers['X-Github-Event'] = 'membership'
  # No X-Hub-Signature header sent at all
  post :create, body: {
    action: 'added',
    team: { id: shipit_teams(:shopify_developers).id, name: 'Developers', slug: 'developers', url: 'http://example.com' },
    organization: { login: 'shopify' },
    member: { login: 'attacker-login' }
  }.to_json, as: :json
  assert_response :ok

  user = Shipit::User.find_by(login: 'attacker-login')
  refute_nil user
  # Binding under test: authorized? should equal real GitHub membership (false, never checked) but returns true
  assert_equal true, user.authorized?
end
```
This demonstrates that `Shipit::User#authorized?` (`app/models/shipit/user.rb:80-82`) returns `true` for `attacker-login` purely from a forged `Membership` row created via the blank-`webhook_secret` bypass in `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-77`), with no live GitHub confirmation at any point.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
