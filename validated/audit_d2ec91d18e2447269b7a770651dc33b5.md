### Title
AA `data_feed[[...]]` price/oracle reads can pick up unstable, still-mutable feed values instead of a stabilized/averaged price - (File: `data_feeds.js`, `formula/evaluation.js`)

### Summary
The reported bug class is: a DeFi contract computes a critical amount (min-out for a swap) from an **instantaneous, manipulable spot price** instead of a robust time-weighted value, letting an attacker manipulate the price at execution time to shortchange another user's pending order. The equivalent surface in `ocore` is the `data_feed`/`in_data_feed` oscript primitive that Autonomous Agents (AAs) use to read oracle-posted exchange rates. When evaluated inside an AA, this primitive is allowed to read **unstable** (not-yet-finalized) data-feed posts and simply picks the "last" one by `latest_included_mc_index`/`level`, with no averaging, no minimum confirmation depth, and no protection against the candidate set changing between the time a victim's trigger is posted and the time the AA's response is actually computed.

### Finding Description
`readDataFeedValue()` in [1](#0-0)  is given `unstable_opts` and, when truthy, scans `storage.assocUnstableMessages` for `data_feed` messages authored by AA units that are not yet stable, collecting all matching candidates and then selecting the single most recent one (`ifseveral === 'last'`) by `latest_included_mc_index`/`level` — i.e., exactly the "current price" analog of `slot0` in the original report, with no time-averaging.

Crucially, in `formula/evaluation.js`, when the `data_feed[[...]]` formula operator is evaluated as part of AA response computation, `unstable_opts` is set to `bAA` (a boolean indicating "we are evaluating inside an AA"), unconditionally: `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, ...)` [2](#0-1) . This means every AA that reads a price/rate through `data_feed[[oracles=..., feed_name=...]]` (the exact pattern used by the futures/options/AMM oscript samples for exchange-rate lookups, e.g. `GBYTE_USD_MA`) is, by design, allowed to consume a value from a unit that has not stabilized yet and whose relative DAG order/level can still shift.

This mirrors the reported root cause: the AA is not reading a robust, already-final, averaged value; it is reading the "current"/latest candidate in an unstable, still-changeable set, selected purely by best-known ordering at evaluation time (`dataFeedExists` has the identical unstable-scan pattern for `in_data_feed`, see [3](#0-2) ).

### Impact Explanation
Any AA that relies on `data_feed`/`in_data_feed` for price-sensitive logic (exchange-rate based payouts, collateral/blackswan checks, swap-style computations as seen in the futures/option/AMM sample contracts, e.g. `$exchange_rate = data_feed[[oracles=..., feed_name=...]]` at [4](#0-3) ) computes its payout using whatever unstable value currently wins the "last" ordering. Because AA execution can occur speculatively before the triggering unit is fully stable, and the unstable-feed candidate set is re-evaluated live from `storage.assocUnstableMessages`, an oracle operator (or anyone who can get a competing data-feed-posting AA unit accepted into the unstable DAG window) can shift which value is selected between the time a victim posts a trigger and the time the AA's response for that trigger is computed/finalized. This lets an attacker manipulate the exchange rate consumed by the AA to reduce payouts to victims or extract more value than intended — directly analogous to the "receive less tokens due to manipulated price" impact in the source report, but here manifesting as AA fund loss/incorrect payout for any AA built on this primitive.

### Likelihood Explanation
No special privilege is required beyond being able to post units: the mechanism is exposed to any address that authors AA units on the network (oracles are ordinary addresses/AAs), and the vulnerable read path (`unstable_opts = bAA`) is taken unconditionally whenever `data_feed[[...]]` is evaluated inside AA execution — it is not an opt-in "unstable" mode that authors can avoid at the callsite. Any deployed AA using `data_feed` for a price/rate (a documented, encouraged pattern per the futures/option/AMM sample contracts) inherits this exposure by default.

### Recommendation
For AA-context data-feed reads used in payout-critical computations, either (a) restrict `readDataFeedValue`/`dataFeedExists` to only consider stable data-feed posts when the result affects fund movement (i.e., do not default `unstable_opts` to `bAA`), or (b) require AA authors to explicitly opt into unstable reads with clear warnings, and provide a built-in, first-class time-weighted/averaged oracle primitive (analogous to a genuine TWAP) so contract authors are not forced to build price logic on top of a single "latest unstable post" selection.

### Proof of Concept
1. Deploy an AA (e.g., the futures/option/AMM pattern in `test/samples/futures_contract.oscript`) that computes a payout using `data_feed[[oracles='ORACLE_ADDR', feed_name='RATE']]`.
2. A user posts a trigger unit intending to receive a payout based on the oracle's currently-published rate.
3. Before the trigger (and hence the AA's response unit) stabilizes, the oracle (or a colluding party able to post another AA-authored `data_feed` message that lands in `storage.assocUnstableMessages` with a higher `latest_included_mc_index`/`level`) posts a new, less favorable rate.
4. Because `readDataFeedValue` re-scans `storage.assocUnstableMessages` and picks the most recent unstable candidate (`data_feeds.js:242-272`), the AA response computed for the victim's trigger uses the newly posted, manipulated rate instead of the one visible when the trigger was submitted, reducing the victim's payout.
