### Title
Webhook signature verification selects the signing organization from `params` while event handlers act on a different organization parsed from `raw_post`, enabling cross-organization webhook forgery and `Shipit.github_teams` privilege escalation - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the per-organization `webhook_secret` using `repository_owner`, which is read from the Rails `params` object. `WebhooksController#create` instead re-parses the request body with `JSON.parse(request.raw_post)` and dispatches handlers using that independently-parsed payload. Because `params` is populated from Rails' own body/query-string parsing (which can diverge from the raw body Rails actually received), an attacker who knows the webhook secret of *any* organization configured on the instance can steer signature verification to that known secret while feeding a forged payload describing a completely different, victim organization/repository to the handlers that actually mutate state.

### Finding Description
`verify_signature` (a `before_action`, run prior to `create`) does: [1](#0-0) 

`repository_owner` used to select the signing secret is derived from the controller's `params` helper: [2](#0-1) 

`create` however builds the payload used by handlers from an *independent* parse of the raw body: [3](#0-2) 

`Shipit.github(organization:)` looks up the org-specific config (webhook secret) purely from the string passed in, with no cross-check against the payload actually being verified: [4](#0-3) 

`verify_webhook_signature` only proves that *someone holding the selected organization's secret* produced the given raw body — it makes no claim about what organization/repository that raw body describes: [5](#0-4) 

**The binding that should hold**: `organization_selected_for_signature_verification == organization_embedded_in_the_processed_payload`.

**What actually happens**: `params` (used to pick the verification secret) is populated by Rails from the query string and/or Content-Type-negotiated body parsing, while the handler-processed payload is always `JSON.parse(request.raw_post)` regardless of Content-Type. These two are not guaranteed to be the same value. Rails always merges query-string parameters into `params` independent of Content-Type, so an attacker can set `?repository[owner][login]=<org_the_attacker_controls>` in the URL while placing a JSON body describing a victim organization/repository (e.g. `{"repository":{"owner":{"login":"victim-org"}}, ...}`) in the POST body, signed with the secret of the org the attacker controls (e.g., their own installation of a publicly installable GitHub App, or a lower-security sandbox org configured alongside the victim org — this is the documented multi-org config format): [6](#0-5) 

`verify_signature` computes/validates the HMAC using the attacker's known secret and the exact raw body the attacker crafted — this succeeds because HMAC only proves possession of the secret, not anything about payload content. The engine then proceeds to `create`, which dispatches the forged payload (naming the *victim* org/repo/team) to real handlers, e.g. the membership handler that creates/updates `Team`/`Membership`/`User` records purely from payload content with no independent verification against GitHub's API: [7](#0-6) 

This is the direct structural analog of the reported bug: just as `collateralToLiquidateWithoutDiscount` (uncapped) and `collateralToLiquidate` (capped) were computed from the same nominal inputs but diverge under adversarial conditions, breaking an invariant the contract relied on (`collateralToLiquidate >= liquidationSurcharge`), here `repository_owner`-from-`params` and `repository.owner.login`-from-`raw_post` are computed from the same nominal request but can diverge under adversarial conditions (mismatched Content-Type/query-string vs body), breaking the invariant the engine relies on (the org that authenticated the request is the org described by the payload being acted on).

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding explicitly called out as in-scope. Concretely, an attacker who only controls a webhook secret for one (possibly low-value/self-installed) organization on a multi-org Shipit deployment can forge fully "signature-verified" webhook events naming a victim organization/repository/team:
- Forged `membership` events can create/modify `Team`/`Membership` records, directly escalating into `Shipit.github_teams` authorization — a High severity outcome explicitly listed in the rules.
- Forged `status`/`check_run`/`push` events can mark arbitrary victim commits as CI-passing, enabling the merge queue and continuous deployment to proceed on attacker-controlled premises, which can cascade into an unauthorized deploy — a Critical severity outcome explicitly listed in the rules.

### Likelihood Explanation
Exploitability requires: (1) a multi-organization GitHub App configuration (explicitly documented/supported), and (2) the attacker's ability to legitimately obtain one organization's `webhook_secret` (e.g., by installing a publicly installable GitHub App on their own org and configuring a Shipit deployment/team to receive it, or by compromising a lower-trust org's webhook delivery, without needing any Shipit session, `ApiClient` token, or private key). Given webhook secrets are per-organization shared secrets and the divergent parsing (`params` vs `raw_post`) is unconditional application logic, this is reachable without privileged access to the victim org.

### Recommendation
`repository_owner` used for signature verification must be derived from the exact same parsed structure that `create` uses to dispatch handlers (i.e., `JSON.parse(request.raw_post)`), not from Rails' independently negotiated `params`. Concretely, parse `raw_post` once in a `before_action`, memoize it, and have both `repository_owner` and `create` read from that single memoized parse, eliminating any possibility of divergence between the organization used to select the verification secret and the organization embedded in the payload actually processed.

### Proof of Concept
1. Deploy Shipit with a multi-organization GitHub App configuration containing at least `attacker-org` (attacker knows/controls its `webhook_secret`) and `victim-org` (target).
2. Attacker crafts a JSON body:
```json
{
  "action": "added",
  "team": {"id": 1, "name": "Admins", "slug": "admins", "url": "https://example.com"},
  "member": {"login": "attacker-github-login"},
  "organization": {"login": "victim-org"},
  "repository": {"owner": {"login": "victim-org"}}
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` (they legitimately know this secret).
4. Attacker sends:
```
POST /webhooks?repository[owner][login]=attacker-org
X-Github-Event: membership
X-Hub-Signature: sha1=<computed>
Content-Type: application/json

<body from step 2>
```
5. `verify_signature` reads `repository_owner` → `"attacker-org"` (from the query string, present in `params` regardless of body content), selects `attacker-org`'s known secret, and the HMAC check passes because the attacker computed it correctly for that secret.
6. `create` re-parses `raw_post` and dispatches the `membership` handler with the JSON body naming `victim-org`, causing a `Membership`/`Team` record to be created/updated for the victim organization's team based on entirely attacker-controlled data — escalating the attacker's GitHub identity into `Shipit.github_teams` authorization for the victim org without ever having credentials for `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
