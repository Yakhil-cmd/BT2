## Title
CCMenu API token issued for one stack can be replayed to read the status of any stack — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`Shipit::Api::CCMenuController` re-implements the `stack` lookup instead of using the scoped helper from `BaseController`, so an `ApiClient` token that is supposed to be scoped to a single stack is not actually checked against the stack being read. Any holder of a valid CCMenu token can supply an arbitrary `stack_id` and read that other stack's build/deploy status.

## Finding Description
`Shipit::Api::BaseController` implements a stack-scoping mechanism for tokens: if an `ApiClient` has a `stack_id`, it must only ever see that one stack. [1](#0-0) 

This is the mechanism by which per-stack tokens (e.g. the ones handed out to unauthenticated CCMenu dashboards) are contained to the stack they were minted for. `Shipit::CCMenuUrlController#fetch` mints exactly such a scoped, `read:stack`-only token for one specific stack and exposes it directly in a URL (`?token=...`) meant to be embedded into third-party, unauthenticated CI-status tools: [2](#0-1) 

However, `Shipit::Api::CCMenuController` overrides `authenticate_api_client` to authenticate via the raw `params[:token]` (query-string auth, as intended for unauthenticated consumers), but then defines its own private `stack` method that bypasses the scoped `stacks` helper entirely and resolves the stack straight from user-supplied `params[:stack_id]`: [3](#0-2) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(operation, scope)`, which checks the string permission list (`read:stack`), not whether the target stack matches the client's authorized `stack_id`: [4](#0-3) 

So the binding that should hold — `token.stack_id == stack_it_reads` — is broken specifically in this controller: every other stack-scoped API controller (`api/stacks_controller.rb`, `api/tasks_controller.rb`, `api/locks_controller.rb`, `api/hooks_controller.rb`) resolves the stack through the inherited, scoped `stack`/`stacks` helpers, but `CCMenuController` shadows it with an unscoped `Stack.from_param!(params[:stack_id])`.

## Impact Explanation
CCMenu tokens are designed to be handed to untrusted, unauthenticated third parties (CI badges/dashboards) and are scoped to a single stack precisely so that leaking one such token only discloses one stack's build/deploy state. Because of this bug, possession of any single CCMenu token (for stack A) lets the holder read the build/deploy status — including lock reason, last build status/label, activity — of every other stack in the Shipit instance by simply changing `stack_id` in the URL. This is an unauthenticated read of stack state across the tenant, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output."

## Likelihood Explanation
Exploitation requires no privileged access beyond a single legitimately-issued CCMenu token (which is explicitly designed for distribution to unauthenticated third-party tooling, e.g. embedded in a public README or CI dashboard). Once such a token leaks, exploitation is a single unauthenticated HTTP GET request with a modified `stack_id`; no additional secrets, sessions, or write access are required.

## Recommendation
Have `CCMenuController` reuse the inherited, scoped `stack`/`stacks` helpers from `BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so a stack-scoped `ApiClient` can never resolve a stack outside of `current_api_client.stack_id`.

## Proof of Concept
1. As an authenticated Shipit user with read access, visit `/ccmenu/<owner>/<repo>/<stack-A>` (or call `CCMenuUrlController#fetch`) to obtain a CCMenu token scoped to stack A: response contains `ccmenu_url` with `?token=<TOKEN_A>`. [5](#0-4) 
2. Confirm the token only carries `read:stack` permission and is bound to stack A: `ApiClient.find_by(...)` has `stack_id == stack_A.id` and `permissions == ['read:stack']` (per the `create_with` call).
3. Send a request to a different stack's CCMenu endpoint reusing `TOKEN_A`:
   `GET /api/stacks/<owner>/<repo>/<stack-B>/ccmenu?token=<TOKEN_A>`
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than the scoped `stacks.from_param!`, the request succeeds and returns stack B's build/deploy status, even though `TOKEN_A` was never authorized for stack B. [6](#0-5)

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
