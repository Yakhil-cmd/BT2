### Title
Webhook signature verification org is derived from an unsigned payload field decoupled from the org/team the handler actually writes to - authentication bypass into `Shipit.github_teams` authorization (`app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to verify the incoming payload against, using a value taken directly from the same unauthenticated JSON body it is about to verify. `GitHubApp#verify_webhook_signature` additionally treats a blank/unset `webhook_secret` for that organization as an automatic pass. Because Shipit supports multiple organizations, each with an independently configured (and *optional*) `webhook_secret`, an attacker can pick, via the payload, an organization that has no secret configured, causing signature verification to unconditionally succeed, while the handler that actually processes the event (e.g. `MembershipHandler`) writes state for a *different* GitHub team/organization identified by other, unverified fields in the same payload (`team.id`, `organization.login`). This breaks the binding "organization whose secret authenticated the request == organization/team the handler writes to."

### Finding Description
`WebhooksController#verify_signature` picks the verifying app by: [1](#0-0) [2](#0-1) 

`repository_owner` is computed purely from attacker-controlled JSON: `repository.owner.login`, falling back to `organization.login` when no `repository` key is present (true for the `membership` event).

`GitHubApp#verify_webhook_signature` is: [3](#0-2) 
`return true unless webhook_secret` means any organization configured with a blank/absent `webhook_secret` (explicitly documented as *optional*, and independently configurable per organization) makes signature checking a no-op for events attributed to that organization.

`Shipit.github(organization:)` resolves per-organization config: [4](#0-3) 

For the `membership` event, `MembershipHandler` never even looks at `repository`; it operates entirely on `organization.login`, `team.id`, and `member.login`, all of which are attacker-supplied and untouched by the (bypassed) signature: [5](#0-4) 

`Team.find_or_create_by!(github_id: params.team.id)` keys purely off a numeric GitHub team id supplied in the payload, and `team.add_member(member)` appends any `User` (created on the fly via `User.find_or_create_by_login!`) to that team: [6](#0-5) 

Team membership is exactly what gates application-wide authorization: [7](#0-6) [8](#0-7) 

Putting it together: `repository_owner` (used only to pick a webhook secret) and the org/team actually mutated by the handler are two independent, attacker-controlled values inside the *same unsigned* request. Verification is bound to the former; the write is bound to the latter. If any configured org (`Shipit.github(organization: X)`) has a blank `webhook_secret` — a supported, documented configuration — an attacker can set `organization.login` (or `repository.owner.login`) to `X` to make `verify_signature` pass unconditionally with **no signature at all**, while the `team.id`/`organization.login` fields used by `MembershipHandler` describe a *protected* team belonging to a real, secured organization that the attacker never authenticated against.

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" boundary explicitly called out as High severity: an unauthenticated network attacker (no Shipit session, no `ApiClient` token, no webhook secret, no GitHub App private key) can forge a `membership` webhook that adds an arbitrary GitHub user (including themselves, provided they can log in via the app's GitHub OAuth) as a member of a `Team` record matching the `github_id` of a team that is part of `Shipit.github_teams`. Once that membership row exists, `User#authorized?` returns true for that user, bypassing the team-membership gate enforced by `Shipit::Authentication#force_github_authentication`, granting full access to the Shipit UI/engine (stack management, deploy triggering, etc.) — an authorization bypass, not merely a data-integrity issue.

The precondition (one multi-tenant org configured without a `webhook_secret`) is realistic: the setup docs explicitly mark `webhook_secret` as *optional* per organization, and the multi-org support in `lib/shipit.rb#github_app_config` is a first-class, documented feature, so a mixed "some orgs secured, one org left with an empty secret" configuration is a foreseeable real-world state, not a contrived edge case.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with ≥2 GitHub App organizations where at least one has no `webhook_secret` set, (2) knowledge of the `github_id` of a `Team` already tracked by Shipit as part of `Shipit.github_teams` (obtainable via the public/team GitHub API or simple enumeration, or in Enterprise setups via any organization member), and (3) a GitHub login the attacker controls. No repository write access, no App private key, and no valid HMAC signature are required — `X-Hub-Signature` can be omitted or arbitrary. This is a config-dependent but plausible and reachable path entirely through the public `/webhooks` endpoint.

### Recommendation
- Do not let a payload field determine which secret is used to authenticate that same payload's fields for a *different* purpose. Bind the "verifying organization" strictly to the field the handler actually trusts and acts on (e.g. require `repository.full_name`/`organization.login` used by `Handler#stacks` and `MembershipHandler` to be exactly the same field used for `repository_owner`, and reject events that lack it, e.g. events like `membership` should require a consistent, verifiable owner).
- Make `webhook_secret` mandatory for every configured organization (fail closed) instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`.
- In `MembershipHandler`, additionally validate that `params.organization.login` matches the org whose secret verified the request before mutating `Team`/`Membership` records.

### Proof of Concept
1. Deploy Shipit with two organizations configured, e.g. `OrgSecure` (has `webhook_secret: s3cret`) and `OrgOpen` (no `webhook_secret` set), matching the documented optional-secret, multi-org schema (`lib/shipit.rb#github_app_config`, `docs/setup.md`).
2. Ensure `Shipit.github_teams` includes a team belonging to `OrgSecure`, e.g. `OrgSecure/admins`, already present in the DB with some `github_id` (e.g. `4242`), as produced by `Team.find_or_create_by_handle`.
3. Send, unauthenticated, with no valid `X-Hub-Signature` header:
```
POST /webhooks
X-Github-Event: membership

{
  "action": "added",
  "organization": { "login": "OrgOpen" },
  "team": { "id": 4242, "name": "admins", "slug": "admins", "url": "https://api.github.com/teams/4242" },
  "member": { "login": "attacker-github-login" }
}
```
4. `WebhooksController#repository_owner` returns `"OrgOpen"` (no `repository` key present) → `Shipit.github(organization: "OrgOpen")` → `verify_webhook_signature` returns `true` unconditionally because `OrgOpen` has no `webhook_secret`.
5. `MembershipHandler#process` runs: `Team.find_or_create_by!(github_id: 4242)` matches the existing `OrgSecure/admins` team; `User.find_or_create_by_login!('attacker-github-login')` creates/fetches the attacker's `User`; `team.add_member(member)` adds them.
6. Attacker logs in via `/github/auth/github` with their real GitHub account; `User#authorized?` now returns `true` because they belong to a `Team` in `Shipit.github_teams`, bypassing `force_github_authentication` and gaining full application access — with no valid signature ever presented.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
