### Title
Webhook signature verification key is selected from an unverified payload field that differs from the field used to identify the target repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while `Shipit::Webhooks::Handlers::Handler#stacks` (used by every event handler, e.g. `PushHandler`) resolves the target repository/stack using a *different* JSON field, `payload.dig('repository', 'full_name')`. Both fields come from the same unauthenticated, attacker-supplied JSON body, and nothing enforces that they refer to the same repository/organization. This breaks the trust binding: "the organization that authenticated" (via HMAC) must equal "the repository that is written" (via the handler).

### Finding Description
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) picks the GitHub App config with `Shipit.github(organization: repository_owner)` where `repository_owner` reads `repository.owner.login` from the raw JSON body, then verifies `X-Hub-Signature` against that organization's `webhook_secret` [1](#0-0) [2](#0-1) .
- The actual event processing never reuses `repository_owner`. Instead, `Shipit::Webhooks::Handlers::Handler#stacks` and `#repository_name` resolve the affected `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` [3](#0-2) .
- `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }`, directly acting on whatever `Stack` is found via `full_name` [4](#0-3) .
- Because Shipit explicitly supports multiple GitHub Apps/organizations sharing a single `/webhooks` endpoint (`docs/setup.md`, "Using Multiple Github Applications"), each org has its own `webhook_secret`, and the signature-check only binds the request to the org named in `repository.owner.login` — a field that is not cross-checked against `repository.full_name`. An attacker who legitimately controls one configured organization/app (and thus knows or can trigger valid signatures for it) can send a forged webhook whose `repository.owner.login` is set to their own org (so the HMAC validates against a secret they know) while `repository.full_name` is set to a victim org/repo tracked by a different stack in the same Shipit instance. The signature check passes, and the handler acts on the victim repository.

Equality that should hold but doesn't:
`organization authenticated by verify_signature (repository.owner.login)` == `repository acted on by the handler (repository.full_name)`

Before the attack: only the legitimate owning organization's signed webhooks affect its own stacks.
After the attacker's crafted payload: an app/organization the attacker controls is used to pass signature verification, but the write (sync/push/status processing) is redirected to a stack belonging to a different, victim organization/repository — a cross-repository write.

### Impact Explanation
This allows an attacker who administers (or has compromised) one GitHub App/organization configured in a multi-org Shipit deployment to forge webhook events (e.g. `push`, `status`, `check_suite`) that are processed against a completely different organization's stacks. Depending on the handler, this can:
- Trigger `GithubSyncJob` to sync arbitrary commit SHAs into a victim stack (`PushHandler`).
- Inject forged commit `status`/`check_run` records that mark victim commits as CI-passing, which combined with `deployable?`/continuous delivery logic could enable an unauthorized deploy on the victim stack.

This matches the "Critical" bucket ("cross-repository writes" / "unauthorized deploy") defined in the rubric, since it breaks the authentication↔repository binding using only credentials the attacker legitimately possesses for an unrelated org.

### Likelihood Explanation
Requires the deployment to configure multiple GitHub Apps/organizations (a documented, supported configuration in `docs/setup.md`) and requires the attacker to control (or have valid signing ability for) at least one of the configured orgs — a moderate bar, but exactly the kind of trust boundary Shipit's multi-tenant webhook design is meant to enforce. Single-org deployments are not affected by the cross-org variant, though the same code-level disconnect (verifying on one field, acting on another) remains latent.

### Recommendation
Make the field used for signature-key selection and the field used for repository/stack resolution the same, and verify them for consistency after signature validation:
- In `WebhooksController`, after fetching `params`, assert that `params.dig('repository', 'full_name')`'s owner matches the `repository_owner` used to select the webhook secret (or simplify by deriving `repository_owner` from `full_name` itself), rejecting payloads where they diverge.
- Alternatively, have `Handler#repository_name` verified against the same `Shipit.github(organization:)` selection logic used during signature verification, so a single authoritative field is used throughout the request lifecycle.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs, `AttackerOrg` (attacker-controlled app/webhook secret, known to the attacker) and `VictimOrg` (tracked stacks), per the multi-app config in `docs/setup.md`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1 of raw body using AttackerOrg's webhook_secret>` (known to them since they own `AttackerOrg`'s app) and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` and validates the signature successfully (since it was signed with `AttackerOrg`'s secret) — see `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `PushHandler#process` resolves `stacks` via `payload.dig('repository', 'full_name')` = `"VictimOrg/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — a write action performed on `VictimOrg`'s stack despite the request only being authenticated for `AttackerOrg`.

Note: full confirmation that this leads all the way to an unauthorized *deploy* would require tracing `GithubSyncJob`/`stack.sync_github` and continuous-delivery trigger conditions further, which was not fully explored within the available tool budget; the cross-repository *write* (forged sync/status ingestion into a victim's stack) itself is confirmed directly from the cited code.
