### Title
RAY `i128` value ceiling in accrual panics before the borrow-index cap, permanently freezing a market - ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs))

### Summary
Every controller verb accrues interest first via `global_sync` in `contracts/pool/src/interest.rs:20`. Accrual computes `scaled * index` in `scaled_to_original` (used by `Cache::calculate_utilization` at `contracts/pool/src/cache/scale.rs:23-24`), and the `Ray` fixed-point type panics with `GenericError::MathOverflow` whenever the `i128` result exceeds the representable range (`common/src/math/fp.rs:13-25`). A `MAX_BORROW_INDEX_RAY` cap exists (`common/src/constants/pool.rs`), but it engages on the index, not on the RAY *value* `scaled_to_original` computes, so a whale-sized market at sustained high utilization overflows the value multiplication while `borrow_index` is still far below the cap. Once the first overflow occurs, every subsequent call that accrues — supply, borrow, withdraw, repay, liquidate — panics at the same point, so all funds in that market are permanently frozen. The in-repo harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`) proves this end-to-end.

### Finding Description
- `global_sync` chunks elapsed time and calls `accrue_chunk` → `accrue_step` unconditionally on every mutating entrypoint (`contracts/pool/src/interest.rs:26-32,39-53`).
- `calculate_utilization` multiplies scaled totals by the live indexes via `scaled_to_original` (`contracts/pool/src/cache/scale.rs:23-24`); the same unscaling happens throughout withdraw/repay/liquidate paths.
- `Ray` arithmetic aborts via `panic_with_error!(env, GenericError::MathOverflow)` on `i128` overflow (`common/src/math/fp.rs:13-25`). There is no saturating branch — once `borrowed_scaled_ray * borrow_index` exceeds `i128::MAX`, the panic is deterministic and repeatable.
- The index ceiling `MAX_BORROW_INDEX_RAY` bounds the index variable only; the test asserts `last.borrow_index < MAX_BORROW_INDEX_RAY` at the moment of failure, i.e. "the index cap did not engage before the value overflow" (`large_positions_and_long_horizons.rs:350-353`).
- The test then demonstrates permanence: `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` after the cliff, because "every verb accrues first" (`large_positions_and_long_horizons.rs:354-356`).

This is the Soroban analog of CVE-2020-35381's class: a reachable arithmetic bounds panic (there: slice bounds; here: `i128` fixed-point bounds) that denies service — but unlike a per-request crash, this panic is state-persistent, so it is a permanent freeze, not a transient fail-closed DoS.

### Impact Explanation
Permanent freezing of funds: once `scaled_to_original` overflows, no unprivileged (or privileged) path can un-do it — the accrual runs before any verb touches state, so `supply`, `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, and `update_indexes` itself all abort. Suppliers cannot exit, borrowers cannot repay, liquidators cannot deleverage, and revenue shares minted into total supply are locked. The impact scales with the market's size: in the reproduced scenario a market holding ~10^9 units of an 18-decimal asset is bricked.

### Likelihood Explanation
A single unprivileged address can drive the market to the cliff: `supply` a very large principal on a high-decimal-asset market with a steep rate curve (the XLM-style curve), `supply` collateral and `borrow` to ~98% utilization, then wait. Interest accrual is permissionless (`update_indexes`), so anyone — including the attacker or a griefer — triggers the fatal accrual the moment the accumulated index growth pushes `borrowed_scaled_ray * borrow_index` over `i128::MAX`. No admin action, bad parameters, oracle manipulation, or off-chain component is needed; caps (`lift_caps`) are governance-settable limits that a legitimately configured whale market would already have. The reproduction requires a large market, so likelihood is moderate, but the freeze is unconditional once the threshold is crossed — no economic condition can reverse it.

### Recommendation
Enforce a ceiling on the *value* product, not just the index. Options:
- Cap accrual when `scaled_to_original(borrowed, borrow_index)` would exceed a safe bound (e.g. `i128::MAX / 4`) — pause index growth at a documented `MAX_BORROW_VALUE_RAY` rather than letting `mul_ceil` panic, so the market stays operational (repay/withdraw continue to work even if further interest stops accruing).
- Alternatively, engage `MAX_BORROW_INDEX_RAY` clamping inside `accrue_step` before recomputing totals, and make `scaled_to_original` saturate at the cap instead of panicking.
- Add a regression test asserting `try_repay`/`try_withdraw` succeed after the index cap is reached, covering the scenario in `large_positions_and_long_horizons.rs`.

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())

lift_caps(&t, "BIG18", 18);

let principal = BILLION * 10i128.pow(18);

// advance years; try_update_indexes_for eventually fails with MATH_OVERFLOW
// while last.borrow_index < MAX_BORROW_INDEX_RAY
// then:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);

```

All steps are unprivileged entrypoints (`supply_raw`, `borrow_raw`, `update_indexes`). Once the panic occurs, every market verb permanently reverts — funds are frozen with no recovery path.
