### Title
Missing Content Validation in `DeliverStakingInfos` Allows Any Connected Peer to Inject Arbitrary Staking Data During Fast Sync — (`datasync/downloader/queue.go`)

### Summary

The `DeliverStakingInfos` function in `datasync/downloader/queue.go` contains an explicitly stubbed-out validation callback (`// TODO-Kaia-Snapsync update validation logic`) that unconditionally returns `nil`. Unlike `DeliverBodies` and `DeliverReceipts`, which cryptographically verify received data against committed block headers, staking info received from any connected peer during fast sync is accepted and persisted to the database without any content check. A malicious peer that is selected for staking info requests can inject arbitrary `NodeIds`, `StakingAmounts`, and `RewardAddrs`, corrupting the staking database that drives validator reward distribution.

### Finding Description

**Root cause — missing validate callback in `DeliverStakingInfos`:**

**What `StakingInfo` controls:**

`StakingInfo` contains `NodeIds`, `StakingContracts`, `RewardAddrs`, and `StakingAmounts`. These fields directly determine which validators receive KAIA block rewards and in what proportion: [7](#0-6) [8](#0-7) 

**Exploit flow:**

1. Attacker runs a Kaia-protocol-compatible node and connects as a P2P peer to a victim node that is fast-syncing pre-Kaia-hardfork blocks.
2. The victim's downloader selects the attacker's peer for staking info requests (via `FetchStakingInfo`), placing the peer in `stakingInfoPendPool`.
3. The attacker responds with a `StakingInfoMsg` containing fabricated `P2PStakingInfo` entries — e.g., zeroing all `StakingAmounts` for legitimate validators, or substituting attacker-controlled `RewardAddrs`.
4. `DeliverStakingInfos` calls `validate(...)` which returns `nil` unconditionally, so the fabricated data passes.
5. `commitFastSyncData` calls `PutStakingInfoToDB`, persisting the corrupted staking records.
6. Subsequent calls to `GetStakingInfo` for those block numbers return the attacker-supplied data, which is fed into `getDeferredRewardFullKore` / `assignStakingRewards`, redirecting or zeroing KAIA block rewards.

### Impact Explanation

Corrupted staking info persistently stored in the database causes incorrect KAIA reward distribution for all affected block numbers: legitimate validators may receive zero staking rewards, and attacker-controlled addresses may receive rewards instead. This is an unauthorized transfer of KAIA block rewards affecting system-managed funds. The corruption survives node restarts because it is written to the persistent `MiscDB`.

### Likelihood Explanation

- **Attacker preconditions**: Connect as a P2P peer (open to any node on the network) and be selected by the victim for a staking info fetch during fast sync.
- **Victim preconditions**: Node must be in fast-sync mode syncing pre-Kaia-hardfork blocks. Nodes bootstrapping from genesis or recovering missing staking info via `admin_syncStakingInfo` are affected.
- **No privileged access required**: P2P peer connections are unauthenticated and open to any participant.
- The `deliver` function does require the peer to be in `pendPool` (i.e., the victim must have sent a request to that peer), but during fast sync the downloader actively selects idle peers for staking info fetches, making this reachable.

### Recommendation

Implement content validation in `DeliverStakingInfos` analogous to how `DeliverBodies` and `DeliverReceipts` validate against committed block headers. The staking info for a given block can be re-derived from the block's state root (via `PreloadFromState`) and compared against the peer-supplied data. At minimum, the `BlockNum` field in each `P2PStakingInfo` should be verified to match the header number of the corresponding request slot, and the data should be cross-checked against a locally computable hash or Merkle commitment if one is available.

Remove the `// TODO-Kaia-Snapsync update validation logic` stub and replace it with a real check before the `reconstruct` callback writes the data into the result cache.

### Proof of Concept

1. Start a victim node in fast-sync mode on a pre-Kaia-hardfork network.
2. Connect an attacker node as a P2P peer.
3. Wait for the victim to send a `StakingInfoRequestMsg` to the attacker peer.
4. Respond with a `StakingInfoMsg` containing `P2PStakingInfo` entries where `StakingAmounts` are all zero and `RewardAddrs` are replaced with attacker-controlled addresses.
5. Observe that `commitFastSyncData` calls `PutStakingInfoToDB` with the fabricated data (no error returned from `validate`).
6. After sync completes, query `GetStakingInfo` for the affected block numbers and confirm the attacker-supplied data is returned.
7. Confirm that `FinalizeState` → `GetDeferredReward` → `assignStakingRewards` uses the corrupted staking amounts, resulting in zero staking rewards for legitimate validators or rewards routed to attacker addresses.

// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
}

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
