## Analog Bug Found

### Title
DeleteAccount action leaves orphaned PromiseYield/PostponedReceipt state permanently unaccounted after refunding storage stake - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
The PoolTogether `cancelPromotion()` bug deletes a top-level promotion struct while dependent claim state (unclaimed rewards for past epochs) is left permanently orphaned and inaccessible, with no accounting for the locked value. The nearcore analog is `action_delete_account`, which deletes an `Account` and refunds its entire storage-staking balance to a beneficiary via `remove_account`, but `remove_account` never removes the account's outstanding `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id-mapping entries or `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries. These dependent trie entries are left in state, no longer backed by any account's storage-staking payment, exactly mirroring the "parent deleted, dependent claims orphaned" bug class.

### Finding Description
`action_delete_account` computes storage usage strictly from `account.storage_usage()` (adjusted only for contract code/global-contract overhead) and, if under the deletion limit, refunds the full remaining `account.amount()` to `beneficiary_id` and calls `remove_account`: [1](#0-0) 

`remove_account` only clears the `Account`, `ContractCode`, access/gas keys, and `ContractData` entries for the account: [2](#0-1) 

It does **not** remove any of the following trie keys that can exist for the same `account_id` (as receiver):
- `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceiptId` — created whenever an incoming `ActionReceipt` is waiting on missing input data [3](#0-2) 
- `TrieKey::PromiseYieldReceipt`, the yield status (`PROMISE_YIELD_STATUS`), the yield-id mappings, and the corresponding entry already enqueued in the shard-wide `PromiseYieldTimeout` queue — created by `yield_create`/`create_promise_yield_receipt` [4](#0-3)  and enqueued via `enqueue_promise_yield_timeout` [5](#0-4) 

None of these are counted in `account.storage_usage()` (they are runtime bookkeeping keys, not user-attributed storage), so the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` guard in `action_delete_account` does not prevent deletion while such entries exist, and there is no validation error analogous to `DeleteAccountStaking` that blocks deletion when a `PromiseYieldReceipt`/`PostponedReceipt` is outstanding for the account, per the documented error list for `DeleteAccountAction`: [6](#0-5) 

The account's storage-staking balance (which paid for this state while the account existed) is fully returned to `beneficiary_id` at deletion time, exactly as in `cancelPromotion` refunding nothing back to the reward pool while dependents remain. The orphaned entries continue to occupy trie storage with zero remaining economic backing, and are only resolved later, if at all — e.g. `resolve_promise_yield_timeouts` still walks and matches the queue entry by key regardless of whether the account exists [7](#0-6) , and a `PostponedReceipt` for a deleted account only clears when/if its outstanding `DataReceipt` ever arrives.

### Impact Explanation
This allows an unprivileged account to leave dead/orphaned protocol bookkeeping state in the trie (postponed receipts, yield receipts/statuses, yield timeout queue entries) that is no longer paid for by any storage-staking deposit, after having already reclaimed 100% of its storage stake via the `DeleteAccountAction` refund. This is a storage-accounting/underpricing defect: storage that should be economically backed by a staking deposit persists for free, for a duration outside the account's control (until a timeout queue processes at `expires_at`, or indefinitely for a `PostponedReceipt` whose expected `DataReceipt` never actually arrives in the deleted account's case).

### Likelihood Explanation
Reachable purely by an ordinary unprivileged account: (1) call a contract method that issues `promise_yield_create` on itself (or triggers an incoming postponed receipt via a `.then()` promise chain with pending input data), and (2) in a subsequent action on the same account, execute `DeleteAccountAction`. No validator or node privilege is required; this is a standard sequence of receipts/transactions through the runtime's action-processing path (`action_delete_account` → `remove_account`).

### Recommendation
Before allowing `DeleteAccountAction` to succeed (or as part of `remove_account`), check for and clean up (or refuse deletion if present, similar to `DeleteAccountStaking`) any outstanding `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` and `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id-mapping/`PromiseYieldTimeout` entries associated with the account_id being deleted, so that no unaccounted trie state can outlive the account that funded its storage.

### Proof of Concept
1. Deploy a contract on account `A` exposing a method that calls `promise_yield_create` (as in the yield tests, e.g. `call_yield_create_return_promise` in `runtime/near-test-contracts/test-contract-rs/src/lib.rs`), which stores a `PromiseYieldReceipt`/`PromiseYieldStatus` for `A` and enqueues a `PromiseYieldTimeout` entry [4](#0-3) .
2. In a subsequent transaction, have `A` execute `Action::DeleteAccount(DeleteAccountAction { beneficiary_id: B })`; `action_delete_account` refunds `A`'s full balance to `B` and calls `remove_account`, which does not touch the yield/postponed entries [1](#0-0) [2](#0-1) .
3. Observe that the `PromiseYieldReceipt`, `PromiseYieldStatus`, and the `PromiseYieldTimeout` queue entry for `A` remain in the trie after `A`'s `Account` record is gone, with no storage-staking balance backing them, until the timeout queue eventually processes them at `expires_at`.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })

**Outcomes**:

- The account, as well as all the data stored under the account, is deleted and the tokens are transferred to `beneficiary_id`.

### Errors

```rust
/// Invalid account ID.

- If this action is not the last action in the action list of a receipt, the following error will be returned

```rust
/// The delete action must be a final action in transaction
DeleteActionMustBeFinal
```

- If the account still has locked balance due to staking, the following error will be returned

```rust
/// Account is staking and can not be deleted
