### Title
`StatusHandler#process` writes `Status` records for any commit whose `sha` exists in Shipit, without checking that the commit's stack belongs to the webhook's `repository.full_name` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::Handler` defines a `stacks`/`repository_name` helper meant to scope webhook processing to the repository named in the payload, but `StatusHandler#process` never calls it. Instead it does a global `Commit.where(sha: params.sha)` lookup and mutates whatever commit(s) match, regardless of which repository sent the webhook.

### Finding Description
The intended binding is `commit.stack.github_repo_name == payload.dig('repository', 'full_name')`. Tracing the code:

- `Shipit::Webhooks::Handlers::Handler#stacks` computes `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , and other handlers (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*`) use this to constrain their mutations to the calling repository's stacks.
- `StatusHandler#process` does not call `stacks` or `repository_name` at all. It only does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
- `Commit#sha` is a global lookup across the entire `commits` table with no `stack_id` or repository filter, and `create_status_from_github!` immediately mutates state via `add_status`, emitting hooks and potentially calling `stack.schedule_merges` [3](#0-2) [4](#0-3) .

So the two sides of the binding (`commit.stack.github_repo_name` vs. `payload['repository']['full_name']`) are never compared — before and after the handler runs, they remain unequal for any commit sha that exists under a different stack than the one the payload claims to represent.

`verify_signature` in `WebhooksController` only checks that the payload was signed for the organization named in the payload itself (`Shipit.github(organization: repository_owner)`), which does not constrain which `sha` the payload can reference [5](#0-4) . It authenticates "this org sent this webhook," not "this sha belongs to this repository." Since GitHub commit SHAs are content-addressed and repository-independent, an attacker who owns a repository (e.g., a fork with identical history to a monitored upstream, or a repository sharing common ancestry with a tracked stack) can legitimately and validly trigger a signed `status` webhook — via the GitHub Statuses API on their own repo, or CI configured on their own fork — carrying a `sha` value that also exists as a `Commit` row under a completely different tenant's `Stack`.

### Impact Explanation
An attacker who controls any repository with the Shipit GitHub App installed (their own repo/fork) can create/update a `Status` on a commit belonging to a different stack/tenant, as long as they can produce a commit with a matching sha (trivial for unmodified forks or shared history). This can flip a victim commit's CI state to `success`, unblocking `deployable?` and triggering `stack.schedule_merges` / continuous delivery for a repository the attacker never authenticated against [6](#0-5) [7](#0-6) . This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team," potentially leading to an unauthorized deploy. It is repeatable against any stack whose tracked commits share a sha with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the attacker needs a repository (fork or otherwise) where the GitHub App/webhook is installed and can emit a genuinely-signed `status` event referencing a sha that also exists in a victim's `commits` table. This is realistic for public/open-source forks tracked by Shipit, since an unmodified fork shares identical commit shas with upstream. No Shipit secrets, sessions, or privileged roles are required — only ordinary GitHub repository ownership and the ability to set a commit status (via GitHub UI/API on one's own repo) or run CI that posts one. This is low-cost and repeatable.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the payload's repository, mirroring the pattern used by other handlers: resolve `stacks` from `Repository.from_github_repo_name(repository_name)` and constrain the query to `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or verify `commit.stack.github_repo_name == repository_name` before calling `create_status_from_github!`), skipping/no-op'ing commits that don't belong to the reporting repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not require repository binding and mutates commits from any repository" do
  victim_stack = shipit_stacks(:shipit) # some existing stack, e.g. github repo "shopify/shipit-engine"
  commit = victim_stack.commits.create!(sha: 'deadbeef' * 5, message: 'victim commit')

  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' } # unrelated repo, not victim_stack's repo
  }

  Shipit::Repository.expects(:from_github_repo_name).never

  assert_difference -> { commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  commit.reload
  assert_equal 'success', commit.statuses.last.state
  refute_equal payload.dig('repository', 'full_name'), commit.stack.github_repo_name
end
```
This demonstrates that `StatusHandler` mutates a commit belonging to a stack whose `github_repo_name` differs from the payload's `repository.full_name`, and that `Repository.from_github_repo_name` (the repository-scoping mechanism used by all other handlers) is never invoked.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
