### Title
Webhook signature is verified against the organization named in the payload while events act on the repository named in the payload - cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the request against using a field taken from the JSON body itself (`repository.owner.login`, or `organization.login`), rather than from the route or any value bound independently of the payload. The downstream event handlers, however, resolve the repository/stack to act on using a *different* field of the same JSON body (`repository.full_name`). Because the entire raw body is attacker-controlled and only the organization used for HMAC selection needs to be consistent with a secret the attacker actually knows, an attacker who legitimately knows the `webhook_secret` for one organization configured in a multi-org Shipit deployment can forge a signed payload that claims to originate from that organization while pointing `repository.full_name` at a completely different organization's repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App config using `repository_owner`, which is read straight out of the JSON payload: [1](#0-0) [2](#0-1) 

This looks up `Shipit.github(organization: repository_owner)` and verifies the HMAC using that organization's `webhook_secret`: [3](#0-2) 

The signature is computed over the *entire* raw POST body, so any attacker who possesses the `webhook_secret` for organization `OrgA` (e.g., they administer `OrgA`'s GitHub App/webhook installation on a shared, multi-org Shipit instance, as illustrated by the `secrets.development.shopify.yml` multi-org config format) can construct an arbitrary JSON body, keep `repository.owner.login`/`organization.login` set to `"OrgA"` (so the correct secret is selected and the HMAC validates), and set `repository.full_name` to `"OrgB/some-repo"`.

Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that resolve the target `Repository`/`Stack` purely from `repository.full_name`: [4](#0-3) [5](#0-4) 

For example, `PushHandler` uses this repository name to look up stacks and enqueue a GitHub sync for arbitrary matching branches: [6](#0-5) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository the handler acts on**. Before the fix this equality is never checked — `repository_owner` (authentication key) and `repository.full_name`'s owner segment (write target) are two independent, attacker-controlled fields inside the same signed blob, and nothing cross-validates them.

### Impact Explanation
This breaks repository isolation between organizations hosted on the same shared Shipit instance. An attacker who controls the webhook configuration for one onboarded organization can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are attributed to and acted upon a different organization's repositories/stacks, without ever needing that other organization's secret or GitHub credentials. Depending on the handler invoked this can enqueue GitHub sync jobs, write CI/commit statuses (which Shipit's deploy-safety checks rely on to decide whether a commit is deployable), or manipulate team/membership records tied to unrelated repositories — i.e., cross-repository writes originating from an identity that was never authenticated for that repository.

### Likelihood Explanation
The only precondition is that the attacker legitimately controls (or knows the webhook secret of) any single organization configured in the shared multi-org Shipit deployment — a realistic scenario for a self-serve/shared Shipit installation serving many teams/orgs. No repository write access, API token, or session is required; the attacker interacts solely with the public, unauthenticated `WebhooksController#create` endpoint.

### Recommendation
Do not rely on payload-controlled fields to select the verification secret and then reuse other payload-controlled fields to determine the write target without cross-validating them. Concretely: after verifying the signature with the organization derived from the payload, re-derive the target repository owner from `repository.full_name` (or `organization.login`) and reject the request (or fail closed) if it does not match the organization whose secret was used for verification.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `config/secrets.development.shopify.yml` multi-org format).
2. Attacker administers `OrgA`'s GitHub App/webhook and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body for a `push` (or `status`) event where:
   - `repository.owner.login` = `"OrgA"` (or `organization.login` = `"OrgA"`)
   - `repository.full_name` = `"OrgB/target-repo"`
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POSTs to `/github/webhooks` (or the mounted webhook path) with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully.
6. `PushHandler#stacks` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("OrgB/target-repo")` and enqueues sync jobs / writes state for `OrgB`'s stacks, even though the request was never authenticated for `OrgB`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
