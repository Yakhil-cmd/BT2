### Title
Webhook signature verified against secret chosen from an attacker-controlled field that differs from the field used to select the target repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to check the `X-Hub-Signature` against using `repository_owner`, a value read straight out of the still-unauthenticated JSON body [1](#0-0) [2](#0-1) . Every webhook handler, however, decides which `Repository`/`Stack` to mutate using a completely different field of the same body, `repository.full_name` [3](#0-2) [4](#0-3) . Nothing ties `repository.owner.login` to `repository.full_name`'s owner. On a multi-tenant Shipit install (Shipit natively supports configuring one GitHub App/secret per organization, per `docs/setup.md`'s "Using Multiple Github Applications" section), any onboarded organization's operator who knows their own org's `webhook_secret` can forge a payload whose `repository.owner.login`/`organization.login` is their own org (so the correct, known secret is selected and the HMAC passes) while `repository.full_name` names a repository belonging to a *different* onboarded organization, causing Shipit to act on that victim repository's stacks.

### Finding Description
`verify_signature` in `WebhooksController` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
head(422) unless verified
```
and `repository_owner` is:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`GitHubApp#verify_webhook_signature` HMAC-verifies the raw body against the secret of whatever organization `repository_owner` names [6](#0-5) . This step establishes only "this request's `X-Hub-Signature` is valid for organization X's secret" — it says nothing about whether organization X owns the repository the payload actually describes.

After signature verification, every handler resolves the repository/stack to act on from `repository.full_name`, not from `repository_owner`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 
This is used, e.g., by `PushHandler#process` to sync arbitrary stacks with an attacker-chosen `expected_head_sha`: [7](#0-6) 
and by the pull-request handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `EditedHandler`) to resolve `Repository.from_github_repo_name(params.repository.full_name)` and provision/archive/unarchive review stacks or mutate stored pull-request state [8](#0-7) [9](#0-8) .

**Broken equality:** "organization whose secret authenticated the request" ≠ "repository/stack the handlers act on". The signature only binds the raw bytes to *a* secret holder, but two independent fields in that same signed body (`repository.owner.login` and `repository.full_name`) are never cross-checked, so the org that authenticates is not enforced to be the owner of the repository being written.

### Impact Explanation
This lets any entity that legitimately possesses a `webhook_secret` for one tenant organization on a shared, multi-organization Shipit deployment (a configuration Shipit itself documents and supports) forge events that are accepted as authentic and are applied to a *different* organization's repositories/stacks: forcing `GithubSyncJob` to run with an attacker-chosen `expected_head_sha` against a victim stack, or archiving/unarchiving/provisioning a victim's review stacks and mutating stored pull-request records. This is a cross-repository/cross-tenant forgery of trusted GitHub events — an unauthorized write into another organization's stack state, which fits the "cross-repository writes" / unauthorized-deploy-adjacent impact class for a multi-tenant Shipit instance.

### Likelihood Explanation
Requires the attacker to control (or know the webhook secret of) at least one organization onboarded to the same Shipit instance that also hosts the victim organization — a realistic scenario explicitly enabled by Shipit's documented multi-org configuration, and requires no Shipit session, API token, or GitHub write access to the victim repository. No other authentication artifact needs to be forged. Likelihood is Medium since it depends on a multi-tenant deployment and on the attacker being a legitimate operator of at least one tenant org.

### Recommendation
After signature verification succeeds, cross-check that the organization used to select the verifying secret (`repository_owner`) matches the owner embedded in `repository.full_name` (and/or `organization.login`) before dispatching to handlers; reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` only through a path that is scoped to the authenticated organization, rather than trusting an independent `full_name` field taken from the same unauthenticated JSON body used to pick the secret.

### Proof of Concept
1. Attacker legitimately administers `attacker-org`, onboarded to a shared Shipit instance alongside `victim-org` (per Shipit's documented multi-app config in `docs/setup.md`), and therefore knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the HMAC matches that org's known secret, so `head(422)` is never invoked [10](#0-9) .
5. `PushHandler` resolves `repository_name` from `repository.full_name` = `"victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s stacks, despite the signature never having been checked against any secret belonging to `victim-org` [3](#0-2) [7](#0-6) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',

        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
