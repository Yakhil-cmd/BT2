### Title
Bridge token claim/mint path lacks the `paused` check that gates the send path, allowing illegitimate minting while the bridge is frozen - ([File: crates/sui-framework/packages/bridge/sources/bridge.move])

### Summary
This is a structural analog of the IonPool bug: two code paths derive from the same protocol state (`paused`), but only one path enforces the invariant. In the Ion Protocol report, `_accrueFee`/`totalAssets()` kept computing live interest accrual even though the pool was paused, because the read path never checked the paused flag that the write/settlement path relied on. In Sui's native bridge Move module, `send_token_internal` explicitly halts when the bridge is frozen (`assert!(!inner.paused, EBridgeUnavailable)` at [1](#0-0) ), but the token-claim internal routine that ultimately calls `inner.treasury.mint<T>(amount, ctx)` performs message-type, signature, chain, token-type and limiter checks, yet contains no equivalent `assert!(!inner.paused, ...)` before minting [2](#0-1) .

### Finding Description
The bridge's emergency-pause mechanism (`execute_emergency_op`) is the sole governance control meant to halt all bridge fund movement during an incident: `inner.paused = true` and later `inner.paused = false` on unpause [3](#0-2) . Consumers of this flag are expected to check it before any value-affecting action, exactly the pattern the outbound path follows via `send_token_internal`'s `assert!(!inner.paused, EBridgeUnavailable)` guard [1](#0-0) .

The internal claim routine (which validates the message type, signature presence, target chain, token type, and limiter, then mints from `inner.treasury`) does not re-check `inner.paused` at all before calling `inner.treasury.mint<T>(amount, ctx)` [4](#0-3) . This is the same class of bug as the external report: a derived state-changing operation (mint / fee-share creation in Ion; token mint in Sui bridge) is computed/executed without checking the same "paused" invariant that governs the sibling operation (interest accrual vs. deposit; send vs. claim).

If a `BridgeRecord` already has `verified_signatures` attached (a prior committee approval recorded before the pause, or approved concurrently by a quorum that later triggers `emergency_op_pause`), a user calling the public `claim_token`/`claim_and_transfer_token` entry points could still have the treasury mint new coins for them even though the bridge is nominally frozen — because the only pause check in the whole module lives in `send_token_internal`, not in the claim path.

### Impact Explanation
If confirmed against the full call chain (the public entry wrappers for `claim_token`/`claim_and_transfer_token`), this would allow illegitimate minting of bridged tokens while bridge governance believes all fund movement is frozen — directly matching the Critical impact category "bridge message forgery or bridge governance or upgrade bypass that enables illegitimate mint or unlock."

### Likelihood Explanation
Likelihood is Medium: it requires a `BridgeRecord` with pre-existing valid signatures (an already-approved but unclaimed transfer) at the moment of pause, and the attacker only needs to be the intended recipient (or a relayer for `claim_and_transfer_token`) calling a normal public entry point — no privileged access, node, or validator behavior is required, satisfying the unprivileged-user model.

### Recommendation
Add `assert!(!inner.paused, EBridgeUnavailable)` at the start of the internal claim function (mirroring `send_token_internal`), or centralize the pause check in `execute_system_message`/all inbound entry points so both directions of bridge value flow are consistently gated by the same invariant.

### Proof of Concept
Conceptual, not fully verified due to index limits on the surrounding public entry function bodies:
1. Bridge relayer submits `approve_token_transfer` for an Ethereum→Sui deposit, attaching sufficient committee signatures so `record.verified_signatures` becomes `Some`.
2. Before the recipient claims, the bridge committee issues an `emergency_op_pause` via `execute_system_message`, setting `inner.paused = true`.
3. Recipient (or a relayer) calls `claim_token`/`claim_and_transfer_token`, which reaches the internal routine shown above; since no `inner.paused` check exists on this path, `inner.treasury.mint<T>(amount, ctx)` succeeds and coins are minted to the recipient despite the bridge being frozen.

**Caveat:** I could not fully inspect the public `claim_token`/`claim_and_transfer_token` wrapper functions (only the internal helper at lines 540-608 was retrieved) to rule out a pause check being enforced one layer higher, in `execute_system_message`, or in a shared entry guard. Given the reasoning-effort/tool-call limits reached, this should be verified directly in `crates/sui-framework/packages/bridge/sources/bridge.move` (the public `claim_token`, `claim_and_transfer_token` functions, roughly lines 398-540 per the primer) before treating this as a confirmed exploitable Critical finding rather than a plausible analog.

fun execute_emergency_op(inner: &mut BridgeInner, payload: EmergencyOp) {
    let op = payload.emergency_op_type();
    if (op == message::emergency_op_pause()) {
        assert!(!inner.paused, EBridgeAlreadyPaused);
        inner.paused = true;
        event::emit(EmergencyOpEvent { frozen: true });
    } else if (op == message::emergency_op_unpause()) {
        assert!(inner.paused, EBridgeNotPaused);
        inner.paused = false;
        event::emit(EmergencyOpEvent { frozen: false });
    } else {
        abort EUnexpectedOperation
    };
}
