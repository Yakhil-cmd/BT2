### Title
Unauthenticated `new_shared_address` device message lets any correspondent inject arbitrary `device_address` mappings into `shared_address_signing_paths`, causing private payment chains to be leaked to an attacker-controlled device - (File: wallet_defined_by_addresses.js)

### Summary
`handleNewSharedAddress()` in `wallet_defined_by_addresses.js` accepts a `new_shared_address` message from any paired correspondent device and inserts the `device_address` values supplied in `body.signers` directly into the `shared_address_signing_paths` table, without verifying that the claimed `device_address` for each member/co-signer actually corresponds to the device that legitimately controls that member address's key. This is directly analogous to CVE-2022-30952, where Jenkins Blue Ocean allowed an actor with limited privilege to access another user's private credential store because the credential owner/ID binding supplied by the requester was trusted without verifying real ownership.

### Finding Description
The `new_shared_address` device message is handled in `wallet.js` and forwarded to: [1](#0-0) 

`handleNewSharedAddress` validates that the address hash matches the definition, and that signer addresses referenced in the definition are syntactically valid and consistent with the `["address", ...]` leaves of the address definition: [2](#0-1) 

However, none of these checks verify that the `device_address` claimed for a given member address in `body.signers[signing_path].device_address` is the device that actually possesses the private key for that member address. The mapping is trusted as supplied by the sender and persisted verbatim via `addNewSharedAddress`: [3](#0-2) 

Once persisted, `shared_address_signing_paths.device_address` is subsequently used as the sole routing key to decide where to forward private payment chains for that shared address. `forwardPrivateChainsToOtherMembersOfSharedAddresses` and `forwardPrivateChainsToOtherMembersOfAddresses` both simply `SELECT device_address FROM shared_address_signing_paths WHERE shared_address IN(?)` and forward the private elements (amounts, blinding factors, addresses - i.e., the “credentials”/secret payment data of the private asset) to that device with no additional authorization check: [4](#0-3) [5](#0-4) 

Because the `device_address` field is attacker-controlled input from the `new_shared_address` message and is never cross-checked against `wallet_signing_paths`/`extended_pubkeys` (which record the real device that owns a given address's key), a malicious correspondent can construct a `new_shared_address` definition that legitimately references the victim's own address at one signing path (satisfying the "signer address matches definition" check) while declaring themselves (attacker device) as the `device_address` for a *different* signing path in the same definition. Any future private payment made to or forwarded through this shared address will be routed by `shared_address_signing_paths.device_address` and delivered to the attacker's device via `sendPrivatePayments`/`forwardPrivateChainsToDevices`.

This mirrors the CVE root cause precisely: the requester supplies both the "credential ID" (the address) and the claimed "owner" (device_address), and the receiving system persists and later uses that owner binding to decide who gets access to private data, without validating that the binding reflects real key ownership.

### Impact Explanation
Successful exploitation discloses the plaintext contents of private (indivisible/divisible) asset payment chains - blinding factors, addresses, and amounts belonging to another wallet - to an attacker who is merely a paired correspondent device, not a legitimate co-signer of the shared address. Leaking blinding factors/amounts for a private asset payment effectively de-anonymizes and discloses confidential balances/spends, which is the direct analog of "unauthorized access to another user's stored private credentials" in the CVE. This does not itself move funds, but it breaks the confidentiality guarantee of ocore's private-payment system for shared/multisig addresses that any correspondent participates in defining.

### Likelihood Explanation
Any device that has performed pairing with the victim (a normal, low-privilege interaction most wallets allow automatically, similar to Blue Ocean's "Job/Configure" permission being a low bar) can send a `new_shared_address` message unsolicited; `handleNewSharedAddress` performs no interactive user confirmation before writing to `shared_address_signing_paths`. The only requirements are that the crafted definition's `["address", ...]` leaves match the `signers` map syntactically - both attacker-controlled - so the attack is straightforward to construct once a shared address involving the victim's real address is desired.

### Recommendation
Cross-validate the `device_address` supplied in `body.signers` for each signing path against the actual key ownership records the local node possesses (`wallet_signing_paths`/`extended_pubkeys`/`my_addresses`) whenever the member address is locally known, and only trust the sender-supplied `device_address` for addresses genuinely reachable through that specific correspondent (i.e., the direct sender of the message), rejecting shared-address definitions that claim an unrelated device controls an address that the local node has independent knowledge of. Additionally, consider requiring explicit user approval before writing new `shared_address_signing_paths` rows that reference co-signer devices not already established as correspondents of the referenced member address.

### Proof of Concept
1. Attacker device A is a paired correspondent of victim device V (a normal, unprivileged pairing).
2. A crafts an address definition `["and", [["address", V_address], ["address", A_claims_this_as_"B_address"]]]` and computes `shared_address = getChash160(definition)`.
3. A sends `new_shared_address` to V with `body.signers = { "r.0": {address: V_address, device_address: V_device}, "r.1": {address: B_address, device_address: A_device} }` (declaring itself as the device controlling `B_address`, which may just be a placeholder/attacker-owned address inserted to satisfy the definition check).
4. V's `handleNewSharedAddress` accepts this because the definition passes `Definition.validateDefinition` and signer addresses match the `["address",...]` leaves; `addNewSharedAddress` writes `shared_address_signing_paths` rows including `device_address = A_device` for the shared address.
5. Whenever V (or any counterparty) sends a private payment to/through `shared_address`, `forwardPrivateChainsToOtherMembersOfSharedAddresses`/`forwardPrivateChainsToOtherMembersOfAddresses` query `shared_address_signing_paths` and forward the private chain (containing amounts, addresses, blinding factors) to `A_device` via `sendPrivatePayments`, even though A never actually controls a legitimate co-signing key recognized by V beyond what A itself declared.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
