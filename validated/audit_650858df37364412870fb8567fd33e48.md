### Title
CCMenu API token generated per-stack is not scoped to that stack, granting cross-stack read access if leaked - ([File: app/controllers/shipit/ccmenu_url_controller.rb])

### Finding Description
The CCMenu integration endpoint is exposed per-stack: `GET /*stack_id/ccmenu_url` resolves a specific `stack` from `params[:stack_id]` [1](#0-0) , and returns a URL embedding an `ApiClient` authentication token intended for a CI dashboard tool (CCMenu) to poll that stack's status:

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [2](#0-1) 

The `find_or_create_by!` call is keyed only on `creator` and `name`, never on `stack`, and `ApiClient.create_with(permissions: ...)` never sets the `stack` attribute at all, even though `ApiClient` supports an optional `belongs_to :stack` scoping relation [3](#0-2) .

Downstream, `Api::BaseController#stacks` decides the token's authorization scope purely from whether `stack_id` is set on the `ApiClient` record:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end
``` [4](#0-3) 

Because the CCMenu client's `stack_id` is always `nil`, the token it returns authorizes `read:stack` on **every** stack in the Shipit instance (`Stack.all`), even though the URL that produced it, and the UI feature that surfaces it, is presented and consumed as belonging to one specific stack.

This is the same class of bug as the reported `GetBatchHeader` issue: a value that is implicitly assumed to be scoped/bound to one specific object (the batch header field vs. the request; here, the stack ID in the URL vs. the token's actual authorization scope) is not actually enforced at the point the credential is minted, breaking the equality "the stack a token authorizes" == "the stack a token is generated for."

### Impact Explanation
Any authenticated Shipit user can trigger the "resynchronize" / CCMenu-URL generation flow for any single stack they have visibility into (Shipit authorization is team-wide, not per-stack, per `force_github_authentication` [5](#0-4) ). The resulting token, once embedded in a third-party CI dashboard, CCMenu client config, browser bookmark, shared chat link, or wiki page (a normal usage pattern for CCMenu URLs, since they are designed to be pasted into external tooling), grants **unauthenticated read access to every stack's state, deploy history, and task data** in the entire Shipit installation via `Api::StacksController` and `Api::TasksController` (both merely `require_permission :read, :stack` and both resolve `stack` through the same unscoped `stacks` method). This satisfies the impact bar of "unauthenticated read of stack state, task streams or deploy output" once the token leaves the hands of the user who generated it, exceeding its intended single-stack scope.

### Likelihood Explanation
No special privilege is required beyond ordinary Shipit login (team membership), which is the baseline access level for all users of the app; the vulnerable code path (`CCMenuUrlController#fetch` → `#client`) is reachable from a documented, user-facing feature (the "Settings" page ccmenu link) [6](#0-5) . CCMenu tokens are explicitly designed to be exported to third parties, making accidental over-broad disclosure realistic and not reliant on any additional secret, session hijacking, or social engineering.

### Recommendation
- Persist the requested `stack` on the `ApiClient` when creating/looking up the "CCMenu Client" (`stack:` should be part of both the `create_with` and the `find_or_create_by!` lookup key), so each stack gets its own token.
- In `Api::BaseController#stacks`, do not fall back to `Stack.all` for a `nil` `stack_id` on tokens that were minted for a specific stack context; the empty/`nil` scope should only apply to client-generated (dashboard-wide) tokens, never to tokens issued from a stack-scoped endpoint like CCMenu.

### Proof of Concept
1. As any authenticated Shipit user, visit `GET /myorg/myrepo/production/ccmenu_url`. The controller returns `{ "ccmenu_url": "https://shipit.example.com/api/stacks/myorg/myrepo/production/ccmenu.xml?token=<TOKEN>" }`, minted via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` [7](#0-6) .
2. Paste `<TOKEN>` into a request for a completely different stack, e.g. `GET /api/stacks/otherorg/otherrepo/staging/ccmenu.xml?token=<TOKEN>`.
3. `Api::CCMenuController` authenticates the client via `ApiClient.authenticate(params[:token])` [8](#0-7) , then resolves `stack` directly via `Stack.from_param!` without any per-client stack check [9](#0-8) , and `require_permission :read, :stack` only checks the `read:stack` permission bit, not stack ownership [10](#0-9) . The request succeeds and returns build status for `otherorg/otherrepo`, a stack the token was never intended to expose.
