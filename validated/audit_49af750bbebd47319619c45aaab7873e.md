### Title
`provision?` operator-precedence bug lets a labeled PR create a stack even when `review_stacks_enabled` is `false` - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the three provisioning-behavior branches using unparenthesized `&&`/`||`, so `review_stacks_enabled` only gates the `allow_all?` branch. When behavior is `allow_with_label` or `prevent_with_label`, `provision?` is true regardless of `review_stacks_enabled`, so any PR carrying (or lacking) the configured label can trigger stack creation even on repositories with review stacks disabled.

### Finding Description
Binding claimed: `review_stacks_enabled == true` must be required for stack creation regardless of provisioning behavior. Actual code: [1](#0-0) 

Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. For `allow_with_label` and `prevent_with_label` behaviors, the overall truth value is fully determined by the label check `pull_request_has_provisioning_label?` — [2](#0-1)  — which just inspects `pull_request.labels[].name` strings taken directly from the webhook payload, with no authorization check on who attached the label.

Exploit flow: a repository configured with `review_stacks_enabled = false` and `provisioning_behavior = allow_with_label` (an operator presumably disabling stacks while leaving the behavior config in place) will still create a `ReviewStack` for any "opened" pull request whose labels include the configured `provisioning_label_name`. Existing tests confirm the branch semantics work as coded (behavior branches are tested independently of `review_stacks_enabled`) but there is no test combining `review_stacks_enabled: false` with `allow_with_label`/labeled PR, i.e. the regression is untested — see the test suite, which only pairs `provisioning_enabled: false` with `behavior: :allow_all` [3](#0-2) , and pairs `allow_with_label` only with the default `provisioning_enabled: true` [4](#0-3) .

This is a genuine bug in this engine's own boolean logic, independent of how the label got attached; `verify_signature`/`GitHubApp#verify_webhook_signature` in `WebhooksController` still requires a real, correctly-signed webhook [5](#0-4) , so this cannot be triggered by a forged/unsigned request — it requires a genuine GitHub webhook for a real "opened" pull request event, which means the label must genuinely exist on the PR at open time.

Note on the "unprivileged labeler" premise: GitHub does not, in general, allow an external/unprivileged contributor to attach labels to their own PR against a repository they don't have triage/write access to — label attachment on the base repository normally requires write/triage permission. The question's premise that "any contributor with a PR open against the base repo" can label it is not something verifiable or falsifiable from this engine's code; it's a GitHub permission-model claim outside this repo's control. What is verifiable and demonstrable purely from this engine's code is the operator-precedence defect itself, which causes `review_stacks_enabled` to be bypassed for the label-based behaviors.

### Impact Explanation
If exploited, a stack (`ReviewStack`) is created for a repository configured with review stacks disabled, contrary to operator intent, purely by satisfying the label predicate. This is a record-write authorization bypass local to the affected repository's own review-stack provisioning setting — it does not cross tenant boundaries (each repository's `provisioning_behavior`/`review_stacks_enabled`/`provisioning_label_name` are independent), and it does not grant deploy, merge, or credential access by itself; it only mis-provisions a review stack. This falls short of the Critical/High categories defined (RCE, auth bypass of session/webhook/API-token, secret exfiltration, cross-repo mutation, unauthorized deploy/rollback/merge, or `Shipit.github_teams` escalation) — provisioning an extra review stack is not itself one of the listed critical/high impacts, and no path to executing deploy commands or leaking secrets follows purely from this stack-creation bypass.

### Likelihood Explanation
Requires: repository with `review_stacks_enabled = false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (i.e., configuration is internally inconsistent — an operator would need to have disabled review stacks while leaving a label behavior configured), plus a genuine, correctly-signed GitHub webhook for a real "opened" PR carrying/lacking the configured label. The signature check is a hard precondition that requires a legitimate GitHub-originated event, not an attacker-forged one.

### Recommendation
Add parentheses so `review_stacks_enabled` gates the entire disjunction:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Apply the same fix to `ReopenedHandler` if it shares this logic (it appeared in the earlier grep results with matching method names).

### Proof of Concept
minitest under `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`:
```ruby
test "does not create stacks when review_stacks_enabled is false even with allow_with_label and matching label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository: repository,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix, this assertion fails (a stack is created) because `provision?` evaluates to `true` via `(allow_with_label? && has_label?)` regardless of `review_stacks_enabled == false`; after applying the parenthesization fix, `provision?` correctly evaluates to `false` and no stack is created.
