### Title
Cross-tenant webhook forgery via organization/repository binding mismatch in `WebhooksController#verify_signature` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit` supports a multi-tenant configuration where multiple GitHub organizations, each with its own `webhook_secret`, are configured under `secrets.github` and resolved via `Shipit.github(organization:)`. `WebhooksController#verify_signature` picks *which* organization's secret to verify the incoming webhook against using `repository_owner`, but the handlers that actually act on the payload resolve the target `Stack`/`Repository` using a different field (`repository.full_name`). Because these two fields are independently attacker-controlled inside the same JSON body, a party who legitimately knows one tenant's `webhook_secret` can forge a signature that validates under their own organization while pointing the payload at a different organization's repository, causing Shipit to act on that other tenant's stack.

### Finding Description
`verify_signature` derives the signing organization purely from data inside the untrusted payload: [1](#0-0) [2](#0-1) 

It calls `Shipit.github(organization: repository_owner)`, which looks up a *per-organization* secret from `secrets.github`: [3](#0-2) 

Meanwhile, every event handler resolves the actual `Repository`/`Stack` that is acted upon using a *different* field of the same payload, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

The HMAC (`OpenSSL::HMAC.hexdigest`) is computed over the entire `request.raw_post`, so the signature does cover both `repository.owner.login` and `repository.full_name` — but it only proves the payload was signed with *some* organization's secret, not that the secret belongs to the organization owning the repository named in `full_name`. Because a tenant knows their own organization's `webhook_secret` (it is configured, per-organization, by the Shipit operator/admin for that tenant, and used to sign genuine GitHub webhooks for their org), that tenant can independently compute a valid HMAC signature over an arbitrary payload of their choosing and POST it directly to the shared `/github/webhooks` endpoint — this endpoint is not tied to GitHub's origin, it just checks the HMAC. This lets them set `repository.owner.login` to their own org (so `verify_signature` selects their known secret and the check passes) while setting `repository.full_name` to `OtherOrg/other-repo` (a different tenant's repository tracked by the same Shipit instance). The equality that should hold — "organization whose secret authenticated the request" == "organization owning the repository that is written to" — is broken.

### Impact Explanation
A forged `push` webhook accepted this way causes `PushHandler#process` to invoke `stack.sync_github(expected_head_sha:)` for the victim organization's stacks, which enqueues `GithubSyncJob` to fetch and append the attacker-chosen `expected_head_sha` as new commits for that stack. Combined with continuous delivery being enabled on the victim stack, this can result in an unauthorized deploy/rollback being triggered against another tenant's repository/stack from an attacker who has no legitimate relationship with that tenant — meeting the "unauthorized deploy" bar for High/Critical impact. It also allows spoofing `membership`, `status`, `check_suite`, and `pull_request` events (team membership changes, commit status injection, PR-driven review-stack provisioning/archival) against a foreign tenant's data, since all of these handlers key off payload-embedded repository/org identifiers that are independent of the field used for signature-org selection.

### Likelihood Explanation
This requires the Shipit deployment to use the multi-organization `secrets.github` configuration (i.e., `github_default_organization` non-nil) — a supported, documented mode — and the attacker to already be a legitimate tenant with a valid `webhook_secret` for at least one configured organization on the same instance. This is a realistic scenario for shared/multi-tenant Shipit installations serving several GitHub organizations from one deployment. It does not require compromising `GITHUB_TOKEN`, API tokens, or GitHub App keys — only the webhook secret that the tenant legitimately possesses for their own org.

### Recommendation
Bind signature verification to the same identifier used for authorization of the acted-upon resource. Concretely, `verify_signature` should re-derive/require that the resolved organization matches the organization owning `repository.full_name` (or `organization.login`) before dispatching, and handlers should re-validate that `payload.dig('repository','owner','login')` matches the organization that produced a valid signature, rejecting the payload if they diverge.

### Proof of Concept
1. Configure Shipit in multi-org mode with two tenants, e.g. `secrets.github["orga"]` (secret `S_A`) and `secrets.github["orgb"]` (secret `S_B`), each owning `Stack`s for repos `OrgA/repo` and `OrgB/repo` respectively.
2. As a user who legitimately knows `S_A` (e.g. an OrgA admin who configured OrgA's GitHub webhook in Shipit), craft a push-event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "OrgB/repo"
  }
}
```
3. Compute `sha1=<HMAC-SHA1(S_A, raw_body)>` and send it as `X-Hub-Signature`, with `X-Github-Event: push`, directly to the Shipit `webhooks` endpoint (`config/routes.rb`), bypassing GitHub entirely.
4. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `Shipit.github(organization: "orga")`, and the HMAC check passes since it was signed with `S_A`.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgB/repo")` via `repository_name` (which reads `full_name`, not `owner.login`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on OrgB's stack — an org the attacker has no rights to — enqueuing a sync/deploy pipeline against OrgB's stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
