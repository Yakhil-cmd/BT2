### Title
Webhook signature is verified against the organization named in an unauthenticated field, while handlers act on a different, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using `repository_owner`, a value read straight out of the *unverified* JSON body. Once "verified", the same raw payload is dispatched to handlers that determine which `Repository`/`Stack` to act on using a *different* payload field, `repository.full_name`. Nothing binds these two fields together, so an attacker who can produce a validly-signed payload for any one configured GitHub organization (in particular one with no/blank `webhook_secret`) can freely set `repository.full_name` to target a stack belonging to a completely different, properly-secured organization.

For example `PushHandler` triggers a sync against whatever stack matches that `full_name`: [6](#0-5) 

This mirrors the report's bug class exactly: a value is "deducted"/checked against one location (the org used for signature verification) while the effect ("transfer") is applied against another, un-reconciled location (the repository/stack acted upon). The binding `organization_that_authenticated == organization_owning_the_repository_written_to` is never enforced.

### Impact Explanation
If the Shipit instance is configured for multiple GitHub organizations (a documented, supported configuration) and even one organization has no `webhook_secret` set (or a leaked/weak one), an attacker can forge a webhook that:
- Passes signature verification because `repository.owner.login` names the weakly-configured organization.
- Carries `repository.full_name` pointing at a stack under a different, securely-configured organization.

This lets the attacker drive `Handler` subclasses (push, status, check_suite, membership, pull_request, etc.) against a stack it has no legitimate authorization over — e.g., forging `status`/`check_suite` events to mark commits as green (`app/models/shipit/status.rb` handlers update `Commit` state used by the merge queue and by deploy gating), or forcing `GithubSyncJob` runs. Depending on which handler is abused, this can lead to unauthorized deploy/merge decisions being taken on a repository the attacker does not control, satisfying the "unauthorized deploy, rollback or merge" Critical-impact bucket.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where at least one configured organization has a blank/absent `webhook_secret` (a state the code explicitly tolerates via `return true unless webhook_secret`), or where an attacker otherwise knows one org's secret. Given Shipit's documented support for onboarding multiple orgs with independent, sometimes optional, `webhook_secret`, this is a realistic multi-tenant misconfiguration rather than a purely theoretical scenario.

### Recommendation
After determining the target repository/stack in a handler, re-validate that `payload.dig('repository','owner','login')` (or `organization.login`) matches the organization whose secret was used to verify the request signature, and reject the event otherwise. Alternatively, verify the signature using the *targeted* repository's owning organization instead of a value taken from the same unauthenticated payload before any cryptographic check has occurred, and disallow organizations without a configured `webhook_secret` in multi-org deployments.

### Proof of Concept
1. Configure Shipit with two organizations: `org-secure` (has `webhook_secret`) and `org-weak` (no `webhook_secret` set), each with stacks tracked.
2. Attacker crafts a `push` webhook payload: `repository.owner.login = "org-weak"`, `repository.full_name = "org-secure/some-repo"`.
3. POST to `/webhooks` with header `X-Github-Event: push` and any (or missing) `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "org-weak")`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
5. `create` runs and dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name = "org-secure/some-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues a sync/job against `org-secure`'s stack — despite the request never being validly signed by `org-secure`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
