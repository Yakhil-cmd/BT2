### Title
Hookify PreToolUse/Stop hook fails open on any parsing/import error, silently bypassing user-configured command/file "block" rules - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The externally-reported bug is a class of "unchecked-precondition trust" vulnerability: `SprinklerUpgradeable.exchangeTokenToWater` trusts that a call to a token address "succeeded" without verifying the address actually has contract code, letting an attacker exploit a no-op call as if a real transfer happened. The structurally equivalent trust-boundary bug in this repository is the `hookify` plugin's `PreToolUse`/`Stop` hook executors, which treat *any* failure during rule loading or evaluation (missing rule engine, malformed rule file, unicode errors, unexpected exceptions) as an implicit "allow", silently disabling all of the user's configured `block` rules for that tool call.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` wraps the entire rule-loading/evaluation pipeline in a broad `try/except Exception`, and unconditionally exits `0` (allow) regardless of outcome: [1](#0-0) [2](#0-1) 

The same fail-open pattern exists in the `Stop` hook executor: [3](#0-2) 

Underneath, `config_loader.load_rules`/`load_rule_file` already swallow `IOError`, `ValueError`, `KeyError`, `AttributeError`, `TypeError`, `UnicodeDecodeError`, and any other `Exception` raised while parsing a `.claude/hookify.*.local.md` rule file, logging a warning to stderr and simply skipping/continuing rather than failing the operation: [4](#0-3) [5](#0-4) 

Because `hookify.*.local.md` files are user-authored config that can be committed to a repository (and thus can come from an untrusted/cloned repo, or be corrupted/truncated), a single malformed rule file — e.g. one with unbalanced YAML-like frontmatter, an invalid regex the hand-rolled parser mis-tokenizes into unexpected types, or a `pattern`/`conditions` value of the wrong type causing a `TypeError`/`AttributeError` inside `Rule.from_dict` — causes that rule (and potentially the whole rule set, since `load_rules` swallows the exception per file but any exception inside `RuleEngine.evaluate_rules` propagates up to `pretooluse.py`'s outer catch) to be dropped, with the hook still exiting `0`. There is no fail-closed path: unlike the `security-guidance` plugin's `security_reminder_hook.py`, which explicitly documents defense-in-depth reasoning about "fails open" cases, `hookify` has no secondary enforcement — it is the *only* gate for its own rules.

This mirrors the report's root cause exactly: a security-relevant check (`SafeERC20`/existence check` in the contract; rule evaluation in Claude Code) is assumed to have run and returned a trustworthy result, but the code path that should enforce denial silently degrades to "no objection" when its input is malformed or absent, and an attacker who can influence that input (a crafted token address with no code; a crafted/corrupted rule file) can force the degraded path.

### Impact Explanation
A user who relies on `hookify` `block`-action rules (e.g., "deny writing `.env`", "deny `rm -rf`", "deny pushing to `main`") to enforce guardrails on an agentic coding session can have those guardrails silently disabled for the remainder of the session (or permanently for affected rule files) without any visible failure — the hook still exits 0 and, on the exception path, only a generic `systemMessage` is emitted (not surfaced as a deny/warning to the user in the same way a matched rule would be). Any Bash/Write/Edit/MultiEdit tool call that should have been blocked is instead allowed to execute, which is a genuine unauthorized-action/approval-bypass outcome consistent with the required impact categories.

### Likelihood Explanation
Moderate. This requires either (a) a rule file that can be crafted or corrupted to trigger an unexpected exception in the bespoke YAML-like frontmatter parser or `Rule.from_dict`/`Condition.from_dict` (both of which have no schema validation and construct dataclasses directly from arbitrary dict values pulled out of free-form text), or (b) an environment issue (e.g., `ImportError` from `sys.path` manipulation via `CLAUDE_PLUGIN_ROOT`) at the module level. Since `.claude/hookify.*.local.md` files can be checked into a project and shared/cloned from untrusted sources, an attacker who can influence repo content (e.g., a malicious PR, a compromised dependency template, or a supply-chain-planted `.claude` config) has a direct way to degrade another user's guardrails without any prompt/tool-call visibility.

### Recommendation
Change the fail mode of `pretooluse.py`/`stop.py` (and `posttooluse.py`/`userpromptsubmit.py` if they follow the same pattern) so that unexpected errors during rule loading/evaluation do not silently default to "allow" for rules with `action: block`. Options: (1) fail closed for `block`-classified rule files specifically (deny the tool call and surface the parse error prominently instead of swallowing it), (2) validate rule files at load time with a strict schema and reject/quarantine malformed files with a hard, visible error rather than a stderr warning, and (3) add a self-test/telemetry signal so users know when a configured guardrail rule failed to load rather than discovering the gap only after an unwanted operation succeeds.

### Proof of Concept
1. Add `.claude/hookify.deny-env.local.md` with a rule intended to block writes to `.env`:
   ```
   ---
   name: deny-env
   enabled: true
   event: file
   action: block
   pattern: "\.env"
   ---
   Do not write to .env files.
   ```
2. Corrupt the frontmatter in a way that causes the hand-rolled parser in `extract_frontmatter`/`Rule.from_dict` to raise (e.g., supply a `conditions:` list whose items are non-dict types, or a deeply malformed inline dict line) so `Rule.from_dict` raises `AttributeError`/`TypeError` when accessing `.get`/`.split` on an unexpected type.
3. Trigger a `Write` tool call targeting `.env`. `load_rule_file` catches the exception, logs a warning to stderr, and returns `None`; the rule is dropped from the active rule set (`plugins/hookify/core/config_loader.py:266-274`).
4. `pretooluse.py` proceeds to evaluate the now-empty/partial rule list, finds no match, and returns `{}`, exiting `0` — the intended `block` rule never fires and the `.env` write proceeds unimpeded, despite the user's guardrail configuration.

Note: I was unable to fully verify the exact byte-level input needed to force an exception inside the hand-written frontmatter parser (its lenient string-splitting logic makes it hard to statically prove without executing it), and I could not inspect `posttooluse.py`/`userpromptsubmit.py` contents to confirm whether they share the identical broad `except Exception: exit(0)` pattern — this should be confirmed by a maintainer with repository access before treating this as fully proven.

def main():
    """Main entry point for Stop hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Load stop rules
        rules = load_rules(event='stop')

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0
        sys.exit(0)
