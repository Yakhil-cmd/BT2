### Title
Unset environment variables in interpolated deploy/CI commands silently fall back to Shipit's own process `ENV`, letting an attacker leak host secrets via `shipit.yml` - ([File: lib/shipit/environment_variables.rb])

### Summary
`Shipit::EnvironmentVariables#interpolate` resolves `$VAR` tokens with `@env.fetch(variable) { ENV[variable] }`, so any variable name that is not present in the task/stack-supplied `env` hash is transparently resolved against Shipit's own Ruby process environment rather than raising. Since deploy steps and (for review/CI flows) commit-check commands originate from the repository's own `shipit.yml`, which an unprivileged contributor can edit on their own branch/PR, they can name any process-level environment variable and have its value echoed into task/check output that they can read.

### Finding Description
The claimed binding — "the value substituted for `$UNSET_SECRET_VAR` is always a value the repo's `shipit.yml` author declared, in `Task#env`/`Stack#env`/`DeploySpec#deploy_variables`" — is broken. In reality: value substituted == `ENV[variable]` (Shipit host process env) whenever `variable` is absent from the merged `@env` hash [1](#0-0) .

`Command#interpolate_environment_variables` feeds the command's `@env` (built by `TaskCommands#env`/`DeployCommands#env`, or `Shipit.env` alone for `EphemeralCommitChecks`) into `EnvironmentVariables.with(env).interpolate(argument)` before `PTY.spawn` executes the argv [2](#0-1) [3](#0-2) . `EphemeralCommitChecks#build_commands` builds these commands directly from `shipit.yml`-derived commit-check commands with only `Shipit.env` as the environment, no `deploy_variables` whitelist applied [4](#0-3) .

Exploit flow: attacker pushes a branch/PR and edits `shipit.yml` to add a step such as `echo $SECRET_KEY_BASE` (or `$RAILS_MASTER_KEY`, `$DATABASE_URL`, any credential that operators commonly inject into the Rails process via container/host environment variables). When that step runs — as a deploy step (`TaskCommands#perform`) or, for repositories with commit checks / review stacks, automatically as a CI check on the pushed commit — `interpolate` cannot find `SECRET_KEY_BASE` in the merged env hash, falls back to `ENV['SECRET_KEY_BASE']`, and the real value is shell-escaped and substituted verbatim into the argv passed to `PTY.spawn`, then echoed into the task/check output the attacker can read.

Existing guards do not stop this: `EnvironmentVariables#permit` (used for `deploy_variables`) is a separate method that is not invoked by `interpolate`, so its whitelist offers no protection here [5](#0-4) . Note: the question's specific example of `GITHUB_TOKEN`/`GIT_ASKPASS` is not actually exploitable via this fallback, because `Commands#base_env` explicitly injects `GITHUB_TOKEN` and (optionally) `GIT_ASKPASS` into the merged `@env` hash used for git commands [6](#0-5) , so `@env.fetch('GITHUB_TOKEN')` succeeds and never reaches the `ENV` fallback for that specific variable. The real, generic risk is any other secret an operator has placed in the Shipit process's own `ENV` (e.g. `SECRET_KEY_BASE`, `RAILS_MASTER_KEY`, database/cloud credentials) that is not part of the deploy/task env hash.

### Impact Explanation
An attacker who can only push a branch/PR to a repository already onboarded to Shipit can cause the Shipit host process to disclose arbitrary environment variables it happens to have set (which frequently include Rails/infra secrets) into task or CI-check output associated with that attacker's own commit. This is a host-process secret exfiltration primitive, matching the "exfiltration of deploy-time secrets" Critical category, though it is not automatically a full `GITHUB_TOKEN` leak as the question assumed, since that value is already explicitly merged into `env` by `Commands#base_env`. The blast radius is scoped to whatever secrets the operator's process actually exposes via `ENV` and are not already present in the task/stack env; it is repeatable on every run and does not require cross-tenant reach beyond the attacker's own repository/task output.

### Likelihood Explanation
Preconditions: the repository must already be a Shipit stack (or review-stack) with `shipit.yml`-defined deploy or commit-check steps sourced from the pushed branch, and the Shipit deployment must have some secret set directly in the Ruby process `ENV` that is not otherwise merged into the task/stack env. Attacker cost is a single PR/commit edit to `shipit.yml`; no privileged role, token, or webhook secret is required to have the malicious `shipit.yml` content merged into a fetched commit and executed as a CI/deploy step under existing review or CI automation.

### Recommendation
Change `EnvironmentVariables#interpolate` to raise (e.g. `KeyError`/`NotPermitted`) when a referenced variable is absent from the explicitly-provided `@env`, rather than falling back to the process `ENV`. If certain process-level variables (like `PATH`) genuinely need to be available, they should be added explicitly to the merged env hash passed into `Command.new`, not implicitly leaked through interpolation.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb
test 'interpolate leaks Shipit process ENV for unset variables' do
  ENV['UNSET_SECRET_VAR'] = 'top-secret'
  result = EnvironmentVariables.with({}).interpolate('$UNSET_SECRET_VAR')
  assert_equal 'top-secret', result # demonstrates fallback to process ENV instead of raising
ensure
  ENV.delete('UNSET_SECRET_VAR')
end
```
This runs standalone with no live GitHub and shows the substituted value equals the host process `ENV` value rather than a value declared in `Task#env`/`Stack#env`/`deploy_variables`, confirming the broken binding.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
