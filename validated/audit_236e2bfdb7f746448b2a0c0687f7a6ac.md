## Analysis Result

<title>Mints with a freeze authority allow permanent freezing of pool vaults, locking user and LP funds - (File: programs/cp-swap/src/utils/token.rs)</title>

### Title
Mints with a freeze authority (or third-party pause/permission control) allow permanent DoS/freezing of pool vault token accounts - (File: `programs/cp-swap/src/utils/token.rs`)

### Summary
The pool-creation gatekeeper `is_supported_mint` unconditionally accepts any mint owned by the legacy SPL `Token` program, and for Token-2022 mints only inspects the extension list — it never inspects whether the mint's `freeze_authority` is set. Because the mint's freeze authority can freeze any token account of that mint (including the pool's own vaults) at any time after pool creation, an attacker (or a legitimately malicious/compromised token issuer) can permanently disable `swap_base_input`, `swap_base_output`, `deposit`, `withdraw`, and `collect_creator_fee(_permissionless)` for that pool, locking both swapper and LP funds inside the vaults — the same "external token control causes fund lock" bug class as the referenced Knox `Auction.sol` finding for pausable ERC20s.

### Finding Description
Pool creation (`initialize`/`initialize_with_permission`) validates the token mints via `is_supported_mint`: [1](#0-0) 

This function:
- Returns `Ok(true)` immediately for any mint owned by the legacy `Token::id()` program, with **no check on `freeze_authority`**.
- For Token-2022 mints, only checks that extensions are limited to `TransferFeeConfig`, `MetadataPointer`, `TokenMetadata`, `InterestBearingConfig`, and `ScaledUiAmount` — it does not read the base mint's `freeze_authority` field, which is unrelated to extensions and exists on every SPL mint (both legacy and Token-2022).

This check is invoked in both pool-creation entry points reachable by any unprivileged pool creator: [2](#0-1) [3](#0-2) 

Once the pool's `token_0_vault`/`token_1_vault` accounts are created for such a mint, the mint's freeze authority (which can be any keypair chosen by the token creator, including the same entity that supplies liquidity or a colluding party) can call the standard SPL `FreezeAccount` instruction against the vault at any time — this is a first-class token-program instruction, not an extension, so it applies to both legacy `Token` and `Token-2022` mints regardless of the extension whitelist above.

All value-moving instructions rely on `transfer_checked` CPIs that will fail once a vault is frozen: [4](#0-3) [5](#0-4) 

These helpers are used unconditionally in `swap_base_input`, `swap_base_output`, `deposit`, `withdraw`, `collect_creator_fee`, and `collect_creator_fee_permissionless`: [6](#0-5) [7](#0-6) [8](#0-7) 

None of these instructions provide an alternate, transfer-free accounting path (unlike a possible mitigation of internally bookkeeping balances), so if either vault becomes frozen, every instruction that touches that vault reverts unconditionally, exactly mirroring the reported ERC20-pause bug class.

### Impact Explanation
If a vault token account is frozen by the mint's freeze authority:
- `deposit`/`withdraw` revert, permanently locking all LP principal for every liquidity provider in that pool (no recovery path exists in the program).
- `swap_base_input`/`swap_base_output` revert, freezing in-flight swapper funds transferred to the input vault before the freeze (for split/partial-fill flows) or simply DoS-ing the pool.
- `collect_creator_fee`/`collect_creator_fee_permissionless` revert, locking accrued creator fees indefinitely.

This is a permanent freezing of user/LP funds condition, satisfying the "concrete... permanent freezing of user or LP funds" validation bar, since there is no unfreeze mechanism controlled by the program or its users — only the external mint's freeze authority can reverse it.

### Likelihood Explanation
Likelihood is realistic because:
- Pool creation is permissionless (`initialize`/`initialize_with_permission` can be called by any unprivileged creator with any mint pair satisfying `is_supported_mint`).
- Standard legacy SPL `Token` mints commonly retain a freeze authority (many tokens, including regulated stablecoins, keep this capability), and the check does nothing to reject or warn about it.
- No social engineering or off-chain privilege is required beyond the attacker controlling (or acquiring) the freeze authority of a mint they induce users to pool with — a normal, expected capability of SPL tokens, not a validator/leaked-key/off-chain scenario.

### Recommendation
Extend `is_supported_mint` to reject mints whose `freeze_authority` is `Some(_)` (for both legacy `Token` and `Token-2022` mints), unless explicitly overridden by an approved `SupportMintAssociated` allowlist entry. Additionally, consider surfacing the freeze-authority status to users/front-ends prior to pool creation and deposit, and evaluate whether existing pools with freezable mints should be flagged.

### Proof of Concept
1. Attacker creates an SPL Token (legacy `Token` program) mint `M` with `freeze_authority = attacker_key`.
2. Attacker calls `initialize` (or `initialize_with_permission`) pairing `M` with a normal token; `is_supported_mint` returns `true` unconditionally for the `Token::id()` branch, so pool creation succeeds and `token_0_vault`/`token_1_vault` ATAs are created for `M`.
3. Liquidity providers call `deposit`, adding `M` and the paired token into the vaults.
4. Attacker (freeze authority of `M`) submits a standard SPL `FreezeAccount` instruction against the pool's `M` vault.
5. Any subsequent call to `deposit`, `withdraw`, `swap_base_input`, `swap_base_output`, or `collect_creator_fee(_permissionless)` touching that vault fails at the `transfer_checked` CPI in `programs/cp-swap/src/utils/token.rs`, permanently locking all LP principal and any unclaimed creator fees for that pool.

pub fn is_supported_mint(
    mint_account: &InterfaceAccount<Mint>,
    mint_associated_is_initialized: bool,
) -> Result<bool> {
    let mint_info = mint_account.to_account_info();
    if *mint_info.owner == Token::id() {
        return Ok(true);
    }
    if mint_associated_is_initialized {
        return Ok(true);
    }
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;
    let extensions = mint.get_extension_types()?;
    for e in extensions {
        if e != ExtensionType::TransferFeeConfig
            && e != ExtensionType::MetadataPointer
            && e != ExtensionType::TokenMetadata
            && e != ExtensionType::InterestBearingConfig
            && e != ExtensionType::ScaledUiAmount
        {
            return Ok(false);
        }
    }
    Ok(true)
}
