### Title
Cross-tenant Status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` across the entire `commits` table with no repository/stack scoping, unlike sibling handlers (e.g. `PushHandler`) which correctly scope through the base class's `stacks` helper. A signed webhook from one organization's repository can therefore write `Status` rows onto `Commit` records belonging to a completely unrelated stack/org that happens to share the same 40-hex sha.

### Finding Description
The binding that must hold is: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` that receives a `Status` write from a given webhook. The base class `Handler` (app/models/shipit/webhooks/handlers/handler.rb, lines 32-38) provides exactly this scoping via `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb, lines 12-17) uses it correctly: `stacks.not_archived.where(branch:).find_each { ... }`.

`StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb, lines 20-24) does not call `stacks` at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This looks up commits by `sha` alone, globally, with no join or filter against the repository that authenticated the webhook signature.

Exploit flow: `verify_signature` in `WebhooksController` (app/controllers/shipit/webhooks_controller.rb, lines 24-49) only confirms the payload's HMAC matches the secret registered for `repository_owner` (the org named in the payload's own `repository.owner.login`). It does not verify that the `sha` referenced in the payload actually belongs to a commit under that same repository. An attacker who owns/controls Repo A (any GitHub org, e.g. a personal fork) can trigger a legitimate, correctly-signed `status` webhook from GitHub for Repo A referencing a `sha` that happens to also exist in Victim Org B's tracked repository/stack (e.g., a widely-shared commit such as the git empty-tree object, a vendored/cherry-picked commit, or a coincidentally-mirrored commit). Because `StatusHandler` has no repository filter, `Commit.where(sha: params.sha)` matches Commit rows across Stack B (and any other stack sharing that sha), and `create_status_from_github!` is invoked on those foreign Commit rows too.

Existing guards do not prevent this: `verify_signature` authenticates provenance of the payload (which org sent it) but never binds that identity to which Commit rows may be mutated; `drop_unhandled_event` and `ExplicitParameters` only validate the shape of `status` payloads, not their sha ownership.

### Impact Explanation
An attacker-controlled repository's routine GitHub status events (which fire automatically for CI checks, and can also be near-freely triggered via the repository's own Statuses API by anyone with push access to that attacker-owned repo) can create/update `Status` rows on `Commit` records belonging to a different organization's `Stack`. Status rows influence Shipit's UI/CI-gating status roll-up for deploy readiness (`Commit#create_status_from_github!` / status aggregation used in deploy gating), so a victim stack could show forged CI state, forged as "success" or "failure" from an attacker-chosen `context`, without the victim's CI ever running. This is a cross-tenant write (one org's authenticated payload mutating another org's data) and matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: (1) the attacker controls a repository registered in Shipit's GitHub App/webhook config (any repo owner can install/onboard it, or simply operate against a repo whose org secret they legitimately possess since it's their own repo) — no privileged Shipit role required; (2) a matching sha must exist in both the attacker's repo history and the victim's tracked stack. This is trivially satisfiable using well-known shared commits (e.g., commits cherry-picked/rebased across mirrors, vendored subtree commits, or squash-merge commits from a shared upstream) rather than a true collision — an actual SHA-1 collision is not required, only a duplicate 40-hex string across two `Commit` rows, which is a normal and common occurrence in Shipit's history-tracking model. The attack costs a single signed webhook delivery from GitHub for the attacker's own repository (or the attacker calling GitHub's Statuses API against a repo they control), and is fully repeatable at will.

### Recommendation
Scope the lookup in `StatusHandler#process` to the requesting repository, mirroring `PushHandler`'s use of the `stacks` helper, e.g.:
```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
so that only commits belonging to stacks whose `Repository.full_name` matches the authenticated payload's `repository.full_name` can receive the forged status.

### Proof of Concept
minitest plan (test/models/shipit/webhooks/handlers/status_handler_test.rb style, no live GitHub needed since `Handler.call` just parses payload and calls `process`):
```ruby
test "does not write Status to a commit belonging to a different repository's stack" do
  sha = "a" * 40

  stack_a = shipit_stacks(:shipit) # repository X/repo-a
  stack_b = create_stack(repository: create_repository(owner: "other-org", name: "repo-b"))

  commit_a = stack_a.commits.create!(sha:, message: "a", author: create_commit_author)
  commit_b = stack_b.commits.create!(sha:, message: "b", author: create_commit_author)

  payload = {
    "sha" => sha,
    "state" => "success",
    "context" => "ci/forged",
    "repository" => { "full_name" => stack_a.repository.full_name, "owner" => { "login" => stack_a.repository.owner } },
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 1, commit_a.reload.statuses.count   # legitimate write, same repo
  assert_equal 0, commit_b.reload.statuses.count   # MUST remain 0; currently fails (1) because sha match crosses repositories
end
```
Both sides of the binding — `commit_a.stack.repository.full_name == payload["repository"]["full_name"]` (true, should write) vs `commit_b.stack.repository.full_name == payload["repository"]["full_name"]` (false, must not write) — diverge in the current code because `StatusHandler#process` ignores repository scope entirely, confirming the vulnerability.
