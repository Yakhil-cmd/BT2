Confirmed: the `Repository` model has **no** column persisting GitHub's immutable numeric repository ID [1](#0-0) . The engine binds every write action (merges, deployments, ref updates) to the mutable `owner`/`name` string pair (`github_repo_name`), and that pair can be silently rewritten by `Stack#refresh_repository!` whenever GitHub reports a redirect for the cached name.

### Title
Repository identity bound to mutable owner/name strings instead of GitHub's immutable repository ID enables cross-repository writes after a rename/redirect - (File: app/models/shipit/repository.rb, app/models/shipit/stack.rb)

### Summary
`Repository` stores only `owner` and `name` (both mutable, attacker-influenceable GitHub login/slug strings) and never persists GitHub's immutable numeric repository ID. `Stack#github_repo_name` and `Stack#github_app`/`github_api` derive both *which repository is written to* and *which GitHub App/organization credentials authenticate the call* purely from these mutable strings [2](#0-1) . When GitHub reports that a lookup for the cached name was "Moved Permanently", `refresh_repository!` overwrites the local `owner`/`name` with whatever the redirect target says, without ever verifying it is still logically "the same" resource by an immutable identifier: [3](#0-2) . This is the same bug class as the PRBProxy report: a trust-relevant binding (which repository/organization a proxy — here, a Shipit `Stack` — is allowed to act on) is not re-verified/reset when the underlying "ownership" (GitHub org/repo naming) changes hands.

### Finding Description
- `Repository#github_repo_name` is simply `"#{owner}/#{name}"` [4](#0-3) , and this exact string is used both to select GitHub App credentials (`Shipit.github(organization: repository.owner)`, i.e. `Stack#github_app`) and as the target path for privileged write operations: merging pull requests, deleting branches, creating deployments, and updating refs (`MergeRequest#merge!`, `CommitDeployment#create_deployment_on_github`, `UpdateGithubLastDeployedRefJob#perform`) [5](#0-4) [6](#0-5) [7](#0-6) .
- `Stack#handle_github_redirections` calls `refresh_repository!` whenever any GitHub API response carries `message == 'Moved Permanently'`, and blindly re-assigns `owner`/`name` from the redirected resource: `repository.update!(owner: resource.owner.login, name: resource.name)` [3](#0-2) . This behavior is exercised and asserted directly in the test suite, which shows a stack's `github_repo_name` silently flipping from `shopify/shipit-engine` to `george/shipster` after one redirected lookup [8](#0-7) .
- Because `Repository` has no `github_id` (or equivalent immutable identifier) column, there is no way for Shipit to distinguish "the same GitHub repository that was legitimately renamed" from "a different repository that now happens to occupy the same owner/name string" (a classic repo/org-squatting scenario: the original org/user renames itself, freeing the old login, and a new, unrelated account registers that exact old login and creates a same-named repository). Once that happens, any subsequent unauthenticated `owner/name`-keyed GitHub API call made by Shipit (merges, deployments, ref pushes, `github_commits`, etc.) will transparently operate on the attacker-controlled repository/organization instead of the one an admin originally configured — using whichever GitHub App credentials Shipit resolves for that (now attacker-owned) `owner` value.
- This mirrors the PRBProxy bug precisely: a security-relevant binding (proxy ↔ owner permissions; here, Stack ↔ specific GitHub repository/org) is never invalidated or re-verified against an immutable anchor when the human-readable identifier ("ownership" of the name) changes.

### Impact Explanation
If exploited, this breaks the equality `organization/repository that Shipit's GitHub App credentials are authorized for == organization/repository that Shipit actually writes to`. Successful exploitation would let write operations (PR merges, branch deletions, deployment creation, ref updates via the app's `GITHUB_TOKEN`-equivalent installation token) be redirected to a repository/organization the original administrator never intended to grant access to — this is a cross-repository write, and depending on the App's installation scope, could constitute an unauthorized "deploy"/"merge" performed with the app's GitHub credentials against an unintended target. This matches the Critical/High categories: cross-repository writes / unauthorized deploy or merge.

### Likelihood Explanation
Exploitation requires a specific, somewhat narrow real-world sequence (a tracked repository's owner or repository is renamed, its old name is subsequently squatted by an unrelated account/org that recreates a same-named repository, and Shipit's GitHub App happens to still be able to authenticate for that owner value or a multi-org config incidentally matches it). This is a known class of GitHub "repojacking" risk but is not fully under the attacker's control end-to-end (GitHub's App-installation and org-onboarding model somewhat limits blast radius in single-org deployments). I could not fully verify, within the indexed engine code, whether `github_app_config` lookups would silently succeed for an attacker-controlled organization in a typical single-org Shipit installation, or whether they would raise `GithubOrganizationUnknown` and abort — this affects how directly exploitable the scenario is in the common single-org configuration versus the multi-org configuration.

### Recommendation
Persist GitHub's immutable numeric repository ID (and ideally the owner's immutable numeric account ID) on the `Repository` record at creation time, and validate that ID on every `refresh_repository!`/redirect-follow before accepting a new `owner`/`name` pair, rather than trusting the redirect target's name strings unconditionally. Reject or flag renames where the resolved repository ID does not match the one Shipit originally recorded.

### Proof of Concept
1. Admin configures Shipit with a Stack pointing at `Repository(owner: "orgA", name: "webapp")`, with GitHub App/org credentials scoped for `orgA`.
2. `orgA` later renames its GitHub organization to `orgA-new`, freeing the `orgA` login.
3. An unrelated attacker registers a new GitHub organization named `orgA` and creates a repository named `webapp` under it.
4. Any Shipit action that triggers `Stack#handle_github_redirections` (e.g. `github_commits`) against the old cached name receives GitHub's "Moved Permanently" response for the *legitimately renamed* `orgA-new/webapp`, and `refresh_repository!` updates the local record accordingly — demonstrating that the binding is entirely name-driven rather than ID-verified [8](#0-7) ; in a variant where the attacker's newly-registered `orgA/webapp` intercepts the *un-redirected* direct API calls that don't go through `handle_github_redirections` (e.g. `MergeRequest#merge!`'s direct `github_api.merge_pull_request(stack.github_repo_name, ...)`), those calls would operate on the attacker's repository if `stack.github_repo_name` still resolves (by string) to the squatted namespace [9](#0-8) .

    def handle_github_redirections
      # https://developer.github.com/v3/#http-redirects
      resource = yield
      if resource.try(:message) == 'Moved Permanently'
        refresh_repository!
        yield
      else
        resource
      end
    end

    def refresh_repository!
      resource = github_api.repo(github_repo_name)
      resource = github_api.get(resource.url) if resource.try(:message) == 'Moved Permanently'
      repository.update!(owner: resource.owner.login, name: resource.name)
    end
