### Title
Webhook signature only authenticates the payload's organization, not the repository/commit a handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `EIG-17` report describes a trust-binding break: the entity whose authority is checked (operator/approver) is not the entity actually constrained by the action it triggers, letting it act outside its own scope. The same class of bug exists in Shipit's webhook pipeline: `WebhooksController#verify_signature` authenticates a webhook using the GitHub App/webhook secret belonging to the **organization named in the payload's `repository.owner.login`**, but at least one handler, `StatusHandler`, never re-checks that organization/repository against the record it mutates — it matches and writes to **any** `Commit` in the entire installation purely by `sha`.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the payload itself and validates the HMAC against that organization's configured `webhook_secret`: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, all delivering to the same shared `/webhooks` endpoint: [3](#0-2) 

Once signature verification passes for organization *A* (using *A*'s own secret), the raw JSON payload is dispatched unmodified to the event handler: [4](#0-3) 

Most handlers (e.g. `PushHandler`, the pull-request handlers) at least re-derive the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')`: [5](#0-4) 

But `StatusHandler` does not use the repository field at all — it looks up commits **globally by `sha`** across every stack/repository configured in the Shipit instance, and writes a GitHub-sourced CI status onto whatever `Commit` records match: [6](#0-5) 

This breaks the intended binding:
`organization whose webhook_secret authenticated the request == repository/commit the handler is authorized to mutate`

In reality the equality only holds for `organization == repository.owner.login` as claimed in the *unverified body of the same payload*, and `StatusHandler` doesn't even check that much — it never consults `repository` or `owner` at all, only the globally-unique-looking but attacker-controllable `sha` field.

### Impact Explanation
Any party that operates (or has installed) a GitHub App on **any one** of the organizations configured in Shipit's multi-org `github` secrets block can send a validly-signed `status` webhook to `/webhooks` with `sha` set to a real commit SHA belonging to a **completely different** organization/repository/stack hosted on the same Shipit instance (commit SHAs are public, guessable from GitHub's API/web UI, or discoverable via Shipit's own public/less-restricted read endpoints). This lets the attacker inject a forged `success` status for a commit they do not own. Because CI/merge/deploy gating (`MergeRequest#all_status_checks_passed?`, `Commit#deployable?`/`required_statuses`) is driven by `Status` records, this can satisfy required checks and enable an **unauthorized merge** (via `ProcessMergeRequestsJob` → `MergeRequest#merge!`, which calls the GitHub API with Shipit's own app credentials) or unblock an **unauthorized deploy** for a stack the attacker never had permission to touch. This matches the "unauthorized deploy, rollback or merge" High-impact criterion.

### Likelihood Explanation
Exploitability depends on the deployment having more than one organization/GitHub App configured (a documented, supported configuration in `docs/setup.md`), and on the attacker controlling (or having compromised) one of those secondary organizations/apps — which is not "repository write access" or a privileged Shipit credential, only ownership of an unrelated org that happens to be onboarded to the same Shipit instance. Guessing/obtaining a target commit SHA is trivial since SHAs are public. No Shipit session, `ApiClient` token, or `webhook_secret` of the *target* organization is required — only a valid secret for *any* configured organization.

### Recommendation
`StatusHandler` (and any other handler that doesn't already do so) should scope its lookup/query using the `repository.full_name` from the verified payload, and the controller/handler layer should positively confirm that the organization used to verify the signature (`repository_owner`) matches the owner encoded in the repository the handler is about to mutate, rejecting the event otherwise. In general, the webhook pipeline should not trust any payload field to select a target record unless that same field is included in the entity whose organization gated the signature check.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret`, per the multi-org example in `docs/setup.md`.
2. As an attacker who controls `org-a`'s GitHub App (e.g. by installing your own app on your own org and pointing its webhook URL at the shared Shipit `/webhooks` endpoint, entirely within your own org), craft a `status` event payload:
   ```json
   {
     "sha": "<public sha of a commit belonging to org-b/some-repo tracked in Shipit>",
     "state": "success",
     "context": "ci/required-check",
     "description": "forged",
     "created_at": "2026-09-01T00:00:00Z"
   }
   ```
3. Sign the payload with `org-a`'s webhook secret and send it with header `X-Github-Event: status` to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `repository_owner` as `nil`/`org-a` (payload has no `repository` key here) and verifies successfully against `org-a`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `org-b` commit by SHA alone, and calls `create_status_from_github!`, writing a fabricated `success` status onto it — with no verification that the requester has any relationship to `org-b`.
6. If that commit/context was blocking a merge queue entry or deploy on `org-b`'s stack, `ProcessMergeRequestsJob`/deploy gating now treats it as passing, enabling an unauthorized merge or deploy triggered entirely by the `org-a` attacker.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
