### Title
`StatusHandler#process` matches commits by SHA with no repository scoping, letting any verified webhook forge Status rows on another repository's commits, including already-deployed ones - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, without restricting to commits belonging to the repository named/verified in the webhook payload. `WebhooksController#verify_signature` only authenticates that the payload came from the GitHub organization named in `payload['repository']['owner']['login']` — it never asserts that the `Commit` rows subsequently written belong to that same repository. Consequently a webhook validly signed for repository A can write a `Status` row against a `Commit` that actually belongs to repository B, whenever the two repositories share a commit with the same SHA (e.g., a public fork/mirror sharing git history with the victim's tracked repo), and this write happens even for commits Shipit considers `deployed?`, since `Commit#add_status` (`app/models/shipit/commit.rb:366-386`) only gates hook emission on `already_deployed`, never the underlying `statuses.replicate_from_github!` write in `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`).

### Finding Description
The broken binding: `repository_name_in_verified_payload == repository_owning_commit_matched_by_sha` is assumed but never enforced.

Trace:
- `WebhooksController#create` parses the raw JSON body and dispatches to `Shipit::Webhooks.for_event(event)` handlers, gated only by `verify_signature`, which validates the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e., it proves the request came from *some* organization Shipit trusts (the one named in `payload['repository']['owner']['login']`), nothing more. [4](#0-3) 
- `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, cross-tenant lookup with **no** join/filter on `stacks`/`repository`. [1](#0-0) 
- Contrast with `CheckSuiteHandler`, `PullRequest::OpenedHandler`, etc., which correctly resolve `Repository.from_github_repo_name(params.repository.full_name)` before touching any `Stack`/`Commit`/`PullRequest` record. [2](#0-1) [5](#0-4) 
- `Handler` base class even provides a `stacks`/`repository_name` helper for exactly this purpose, but `StatusHandler` doesn't call it. [3](#0-2) 
- Inside `Commit#create_status_from_github!` → `add_status`, the write (`statuses.replicate_from_github!`) happens unconditionally via `yield`; only the two `Hook.emit` calls are wrapped by `unless already_deployed` / `if !already_deployed`. [6](#0-5) 

Attacker flow: attacker owns/controls an organization/repository that Shipit is configured to trust (webhook secret configured for that org), e.g., a public fork or mirror of the victim's repository that shares git history/commit SHAs. Attacker sends `POST /webhooks` with `X-Github-Event: status`, signed with their own repository's webhook secret, `repository.full_name` set to their own repo, but `sha` equal to a shared-history commit SHA that also exists (as a `Shipit::Commit` row) under the victim's tracked stack. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` then matches **every** `Commit` row across the entire Shipit instance with that SHA — including the victim's — and calls `create_status_from_github!` on each, persisting a forged `Status` row (state/description/context/target_url all attacker-controlled) onto the victim's commit, regardless of that commit's `deployed?` state.

Existing guards evaluated and found insufficient: `verify_signature` authenticates organization identity only, not commit-to-repository ownership; `drop_unhandled_event` and `ExplicitParameters` schema only validate payload shape/presence of required fields (`sha`, `state`, etc.), not repository scoping; `force_github_authentication`/`User#authorized?`/`require_permission!` are irrelevant to webhook ingestion; `Repository`/`Stack` model validations don't run here since no new records for those models are created; `deployed?`/`add_status` guard hook emission, not persistence — so `test/models/commits_test.rb:748-761` confirms the write still happens, only the notification is suppressed.

### Impact Explanation
Any verified webhook (from an attacker-controlled org/repo) can write falsified `Status` rows onto a **different** repository's commit records purely by SHA coincidence, corrupting that victim commit's permanent CI/audit history — including commits already marked `deployed?`, meaning there is no "it will just get re-verified before deploy" mitigating factor since the record is already historical. This matches the stated Critical category: "a payload for one repository mutating another's stack, commit, task or team." Blast radius spans all repositories/stacks hosted on a shared Shipit instance whenever any repository pair shares commit SHAs (forks, mirrors, subtree merges, repository renames/re-imports are common causes). Repeatable indefinitely, once per crafted `sha`+repository pairing available to the attacker.

### Likelihood Explanation
Preconditions: (1) attacker must control or be able to trigger a webhook-signed delivery for *some* GitHub organization/repository Shipit already trusts (i.e., have their own repo/org onboarded into Shipit with a configured `webhook_secret`/GitHub App installation — a standard, unprivileged self-service action for any repo owner in an org using Shipit); (2) that attacker's commit history must share at least one SHA with a commit that exists as a `Shipit::Commit` row for the victim's stack — trivially achievable by forking/mirroring the victim's public repository into an org the attacker controls and having Shipit track it (or by cherry-picking an existing shared commit). No secrets, sessions, or privileged roles are required beyond normal ability to push to their own tracked repository and have GitHub deliver a `status` webhook, which GitHub does automatically for any repo with a webhook configured. This is feasible and repeatable.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to stacks associated with `params.repository.full_name` (or equivalent `repository_name`), mirroring `CheckSuiteHandler`/other handlers, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) } }`, and add `requires :repository do requires :full_name, String end` to the `StatusHandler` params schema so repository identity is verifiably tied to the write.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "status webhook for repository A must not write a Status on repository B's already-deployed commit" do
          victim_commit = shipit_commits(:second) # belongs to stack/repository "shopify/shipit-engine"
          assert_predicate victim_commit, :deployed?

          foreign_payload = {
            'sha' => victim_commit.sha,
            'state' => 'failure',
            'context' => 'ci/attacker',
            'description' => 'forged',
            'repository' => { 'full_name' => 'attacker-org/attacker-repo' }
          }

          assert_no_difference 'victim_commit.statuses.count' do
            Shipit::Webhooks::Handlers::StatusHandler.call(foreign_payload)
          end
        end
      end
    end
  end
end
```
Both sides of the binding should be checked explicitly: `params.repository.full_name` ("attacker-org/attacker-repo") vs the repository actually owning `victim_commit` (`victim_commit.stack.repository.full_name`, e.g. "shopify/shipit-engine"). Currently they diverge and the test fails (statuses.count still increments), demonstrating the vulnerability; after the recommended fix scoping lookups through `stacks`/`repository_name`, the assertion passes.
