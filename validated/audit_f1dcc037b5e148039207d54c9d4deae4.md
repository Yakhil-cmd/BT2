Confirmed. The `unarchive?` boolean expression in `ReopenedHandler` gates `review_stacks_enabled` only against the `allow_all` branch due to Ruby's `&&`/`||` precedence, while `LabeledHandler`'s equivalent checks correctly wrap `review_stacks_enabled` around the entire condition at `respond_to_label_change?`.### Title
`ReopenedHandler#unarchive?` operator-precedence bug lets a disabled `review_stacks_enabled` be bypassed for `allow_with_label`/`prevent_with_label` repos, causing `ReviewStackAdapter#unarchive!` to re-provision an archived attacker stack - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReviewStackAdapter#unarchive!` itself performs no authorization check; it trusts its caller. The caller in the `pull_request.reopened` flow, `ReopenedHandler#unarchive?`, has a Ruby operator-precedence bug that makes `review_stacks_enabled` gate only the `allow_all` provisioning mode, not `allow_with_label`/`prevent_with_label`. If an operator disables `review_stacks_enabled` on a repository configured with `allow_with_label` or `prevent_with_label` (the UI presents these as independent settings), an attacker who can label their own PR and reopen it can still trigger re-provisioning of a previously archived stack.

### Finding Description
Binding claimed: `repository.review_stacks_enabled == true` must hold at the moment `Shipit::ReviewStackProvisioningQueue.add(stack)` / `stack.unarchive!` execute (re-provisioning time), not merely at original creation.

Code path:
- `ReopenedHandler#process` (`app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:41-45`) calls `stack.unarchive!` (i.e. `ReviewStackAdapter#unarchive!`) only if `respond_to_pull_request_reopened?` is true, which delegates to `unarchive?`.
- `unarchive?` (lines 70-75):
```
repository.review_stacks_enabled &&
  repository.provisioning_behavior_allow_all? ||
  (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
  (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```
Because `&&` binds tighter than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`.
`review_stacks_enabled` is therefore only ANDed with the `allow_all?` term; the `allow_with_label` and `prevent_with_label` branches evaluate independently of `review_stacks_enabled`.

Compare with `LabeledHandler#respond_to_label_change?` (`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:78-83`), which correctly wraps the whole condition: `params.action == "labeled" && pull_request_state == "open" && repository.review_stacks_enabled && (archive? || unarchive?)`. The reopened path lacks this equivalent top-level gate.

`ReviewStackAdapter#unarchive!` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:37-50`) does no independent check of `review_stacks_enabled`; once invoked on an archived stack it unconditionally does:
```ruby
stack.transaction do
  Shipit::ReviewStackProvisioningQueue.add(stack)
  stack.unarchive!(*args, &block)
end
```

Exploit flow:
1. Repository is configured with `provisioning_behavior = allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled = true`; attacker opens/labels a PR and a `ReviewStack` is created and later archived (e.g., PR closed).
2. Operator later disables dynamic provisioning by unchecking `review_stacks_enabled` in `app/views/shipit/repositories/settings.html.erb:12-13` — a control presented as independent from `provisioning_behavior` — intending to fully stop stack provisioning, while leaving `provisioning_behavior` unchanged.
3. Attacker (an unprivileged PR author who can label their own PR per the threat model) adds the provisioning label and reopens the PR, causing GitHub to emit a legitimately-signed `pull_request.reopened` webhook.
4. `unarchive?` evaluates `(false && true) || (true && true) || (false && ...) == true` because the `allow_with_label` branch is untouched by `review_stacks_enabled`.
5. `ReopenedHandler#process` calls `ReviewStackAdapter#unarchive!`, which re-adds the stack to `Shipit::ReviewStackProvisioningQueue` and unarchives it, causing re-provisioning to run attacker-controlled branch/commit content again despite the operator's intent to disable this entirely.

Existing guards do not prevent this: webhook signature verification only authenticates that GitHub sent the event, not that the payload is safe; `ExplicitParameters` schema validates payload shape, not authorization; and the only authorization gate (`review_stacks_enabled`) is broken by the boolean-precedence defect for two of the three provisioning-behavior modes.

### Impact Explanation
For repositories configured with `allow_with_label` or `prevent_with_label`, disabling `review_stacks_enabled` does not stop re-provisioning of already-created stacks via the reopened-PR path. This re-triggers provisioning/build steps sourced from attacker-controlled branch content on the deploy host for that repository, matching the "Critical" category ("an unauthorized deploy... or record written for a repository that did not authenticate it" via re-execution of provisioning that the operator explicitly disabled). Blast radius is scoped to repositories using label-based provisioning behaviors with `review_stacks_enabled` toggled off; it does not cross repository/tenant boundaries.

### Likelihood Explanation
Preconditions: repository must use `provisioning_behavior_allow_with_label` or `provisioning_behavior_prevent_with_label` (not the default straightforward `allow_all`), and the operator must disable `review_stacks_enabled` without also switching provisioning behavior. Given the settings UI (`app/views/shipit/repositories/settings.html.erb`) presents these as two independent controls, an operator disabling review stacks would reasonably not think to also change the provisioning-behavior dropdown. Attacker cost is trivial (add a label to their own PR, reopen it) and fully repeatable for as long as the misconfiguration/bug persists.

### Recommendation
Fix the operator precedence in `ReopenedHandler#unarchive?` to gate all branches on `review_stacks_enabled`, mirroring `LabeledHandler`:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```
Additionally, consider moving the `review_stacks_enabled` check into `ReviewStackAdapter#unarchive!` itself so all callers are protected regardless of caller-side logic.

### Proof of Concept
Minitest (add to `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`):
```ruby
test "does NOT unarchive/re-provision stacks when review_stacks_enabled is false, even with allow_with_label behavior and label present" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # operator disabled review stacks
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # BINDING: repository.review_stacks_enabled (false) must equal
  # "stack was re-provisioned" (should also be false)
  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
  assert_not Shipit::ReviewStackProvisioningQueue.include?(stack), "Expected provisioning queue NOT to contain the stack"
end
```
Running this against current code fails: `stack.reload.archived?` is `false` and the provisioning queue contains the stack, demonstrating `review_stacks_enabled == false` on one side of the binding while re-provisioning (`true`) occurs on the other.
