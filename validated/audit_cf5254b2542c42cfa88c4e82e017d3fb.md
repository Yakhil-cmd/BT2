### Title
Reachable unguarded `throw Error` in oscript formula evaluator crashes full node on malformed AA trigger/definition input - (File: `formula/evaluation.js`)

### Summary
The oscript evaluator used to execute AA (Autonomous Agent) formulas has a normal, catchable error-reporting path (`setFatalError(...)`, which returns `cb(false)`/`err` through the callback chain) for almost all invalid-input cases. However, several code paths instead perform a raw synchronous `throw Error(...)` instead of going through `setFatalError`. Because AA formula evaluation is reachable directly from a single posted unit that triggers an AA, an attacker can craft trigger data/output values that hit one of these unguarded throws, and because the throw happens deep inside nested async callbacks with no enclosing `try/catch`, it becomes an uncaught exception that reaches `process.on('uncaughtException')` in `network.js`, which deliberately does `throw err; // crash the process to avoid ending up in an inconsistent state`. This is directly analogous to the libtiff `tiffcp` bug class: a reachable assertion/abort triggered by attacker-supplied, malformed input causing denial of service.

### Finding Description
`formula/evaluation.js`'s `evaluate()` function is the interpreter for AA oscript formulas (`messages`, `bounce_fees`, getters, etc. defined in an AA). The normal defensive pattern used throughout the function is: [1](#0-0) 

But some branches bypass this and throw directly:
- In the `ifelse` case, if the test result is neither a `Decimal` nor a `wrappedObject` but still `typeof res === 'object'` (e.g. `null`), the code does a raw throw instead of calling `setFatalError`: [2](#0-1) 
- Similarly, unguarded throws exist for output/input-field lookups (`throw Error("unknown field requested: "+arr[2])`) reached from evaluating `input`/`output` formula constructs with attacker-controlled `arr[2]`: [3](#0-2) 
- And in `toOscriptType`/`toJsType`, used pervasively to convert values crossing the JS/oscript boundary (state vars, getter results, responseVars): [4](#0-3) 
- And in `callGetter`, when the getter-call arguments aren't an array: [5](#0-4) 

This formula evaluator is invoked from `handleTrigger`/`evaluateAA` in `aa_composer.js` while processing every primary AA trigger — i.e., any unit posted by any user that pays to an AA address: [6](#0-5) 

Trigger processing itself happens inside `handleJoint`'s `ifOk` path in `network.js` (for the dry-run pre-check) and inside `aa_composer.handleAATriggers` once the trigger is stable, both of which are on the hot path for every unit received from the network or posted locally: [7](#0-6) 

None of these call sites wrap the evaluator invocation in a `try/catch` that would convert a synchronous throw into a normal error callback; the throw therefore propagates up the JS call stack as an uncaught exception. `network.js` explicitly kills the process on any uncaught exception: [8](#0-7) 

### Impact Explanation
Any attacker who can craft a unit that (a) defines an AA (or uses an existing AA) whose formula reaches one of these unguarded throw sites, and (b) posts a trigger unit paying to that AA, can force every full node (and hub) that processes/validates that trigger to hit the raw `throw`, propagate it as an uncaught exception, and crash the node process via the explicit `throw err` in the `uncaughtException` handler. Because AA triggers are processed by all full nodes independently as part of normal consensus/stability processing (`handleAATriggers`), a single malicious unit can cause synchronized crashes across the network, i.e., a network unable to process/confirm new units until operators restart nodes — one of the accepted "network unable to confirm new units" outcomes.

### Likelihood Explanation
Reachability is high: any account can define an AA (subject to normal AA-definition rules) and any unprivileged user can post a trigger unit to it, satisfying the "unprivileged unit poster / AA trigger sender" reachability requirement. Hitting exactly one of the unguarded throw conditions (e.g., causing an `ifelse` test to evaluate to `null` typeof-object, or supplying malformed `input`/`output` field selectors) requires careful oscript construction but no special privileges, keys, or race conditions — it is a pure crafted-input bug, directly analogous to the crafted-TIFF-triggers-assertion pattern in the referenced report.

### Recommendation
Replace every raw `throw Error(...)` inside the formula evaluator's runtime evaluation path (`formula/evaluation.js`, including `evaluate()`'s `ifelse`, `input`/`output` field lookup, `toOscriptType`, `toJsType`, and `callGetter`) with the existing `setFatalError(...)` mechanism (or an equivalent callback-based error return) so that malformed-but-attacker-reachable formula states are converted into ordinary AA bounce/validation errors instead of uncaught process-crashing exceptions. As defense in depth, wrap the top-level `handleTrigger`/`evaluateAA` invocation in `aa_composer.js` in a `try/catch` that converts any unexpected exception into a bounce rather than letting it propagate to the global `uncaughtException` handler.

### Proof of Concept
Conceptual reproduction path (exact formula syntax to trigger the `null`-typeof-object branch in `ifelse` was not confirmed against the parser grammar within the scope of this analysis, so this should be validated in a Devin session with full repo/test access):
1. Define an AA whose `messages.cases[].if` (or another oscript boolean-test position) evaluates, for certain trigger data, to a getter or expression whose result is `null` rather than a `Decimal`/string/boolean/`wrappedObject` — e.g. a getter/local var that is read before assignment or a formula construct that legitimately yields JS `null` through `toJsType`/`toOscriptType` conversions.
2. Post a trigger unit to this AA supplying the crafted `trigger.data` that forces the formula down that branch.
3. When a full node stabilizes and executes the trigger via `aa_composer.handleAATriggers` → `handleTrigger` → `evaluateAA` → `formula/evaluation.js:evaluate()`, the `ifelse` case's `throw Error("test evaluated to object " + res)` fires uncaught, is not caught anywhere in the call chain, and reaches `network.js`'s `process.on('uncaughtException')`, which re-throws and crashes the node process.
