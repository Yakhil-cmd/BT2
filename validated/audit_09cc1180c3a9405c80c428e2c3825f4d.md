### Title
Oscript `unit()` getter mutates a possibly cached/shared unit object in place - ([File: formula/evaluation.js])

### Summary
The `unit` operator in the oscript evaluator fetches a joint via `storage.readJoint()` and then directly mutates the returned unit object (`delete objUnit.actual_tps_fee`, `objUnit.timestamp = 0`, `objectHash.cleanNulls(objUnit)`, and `delete m.payload.data` for `temp_data` messages) before wrapping it with `new wrappedObject(objUnit)`, with no explicit `cloneDeep` performed on the object returned from storage. [1](#0-0) 

### Finding Description
`storage.js` maintains in-memory caches for units (`assocCachedUnits`, along with `assocKnownUnits`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`) that are shared across all validation/AA-evaluation calls in the process. [2](#0-1) 

When an AA formula calls `unit($hash)`, the evaluator retrieves the joint through `storage.readJoint(conn, unit, {...})` and then mutates the returned `objUnit` in place: it deletes `actual_tps_fee`, overwrites `timestamp`, strips null fields via `objectHash.cleanNulls`, and deletes `payload.data` from any `temp_data` messages — all directly on the object handed back by the storage layer, with no defensive `cloneDeep` before mutation. [3](#0-2) 

This mirrors the root cause of CVE-2023-54094: a shared/reference-holding object (there, a cloned skb with a shared head; here, a unit object retrieved from a shared read cache) is mutated destructively by a single consumer without first ensuring exclusive/private ownership of the data (an "unshare"/clone step). If `readJoint` can return the same object reference on repeat lookups (e.g., a joint already cached from a previous read within the same or a concurrent AA/getter evaluation, or reused across nested `unit()` calls for the same unit within one trigger's message chain), the in-place deletions and field rewrites performed for one caller become visible to any other caller holding the same reference, silently corrupting fields like `timestamp`, `actual_tps_fee`, or `temp_data` payloads for subsequent unrelated reads of that unit.

Contrast this with the rest of the evaluator, which is careful to `string_utils.cloneDeep()` before exposing or mutating any object drawn from shared state (state vars, trigger data, previous AA responses, dictionaries/arrays), precisely to avoid this class of bug. [4](#0-3) [5](#0-4) 

The `unit` case is the outlier that skips this pattern for the object it pulls out of the shared joint cache.

### Impact Explanation
If the underlying cached unit object is shared by reference (as the presence of `assocCachedUnits`/`assocKnownUnits` in `storage.js` suggests it can be), a single crafted AA trigger that repeatedly calls `unit($hash)` on the same referenced unit — including through nested/remote AA calls, secondary triggers, or bounce/response chains that re-evaluate the same formula — could cause the fields of a shared unit object to be corrupted for other, unrelated evaluations that read the same unit afterward within the same node process (e.g., wrong `timestamp`/`actual_tps_fee` observed by a different AA, or `temp_data` incorrectly stripped/retained). Because AA evaluation is required to be fully deterministic across all nodes (all nodes must independently compute identical state-var updates and response outputs from the same trigger), any non-determinism introduced by cache-state-dependent corruption (which depends on evaluation order/timing/cache eviction, not just unit content) can cause different nodes to compute different AA responses or state var updates for the same trigger — i.e., node disagreement on AA execution result, which the DAG's consensus depends on for stability.

### Likelihood Explanation
Reachability requires only posting an AA trigger (or an AA definition) whose oscript formula calls `unit()` on a target unit in a way that forces re-reads of the same cached object within one or across evaluations — well within reach of any unprivileged unit poster/AA author. The likelihood the bug is actually exploitable depends on whether `storage.readJoint()`'s underlying cache returns the same object reference on repeated reads (versus a fresh parse each time); this specific detail of `readJoint`'s implementation could not be fully confirmed within the available search budget, so this should be verified against `storage.js`'s `readJoint` definition before treating this as conclusively proven.

### Recommendation
In the `unit` case of `formula/evaluation.js`, deep-clone the joint/unit object immediately after retrieval from `storage.readJoint` (e.g., `var objUnit = string_utils.cloneDeep(objJoint.unit);`) before performing any in-place mutation (`delete`, `cleanNulls`, timestamp rewrite, `temp_data` stripping), consistent with how every other branch of the evaluator clones shared/cached data before mutating or exposing it via `wrappedObject`.

### Proof of Concept
Not fully constructible without confirming `readJoint`'s caching semantics (whether it returns the same in-memory object reference across repeated calls for the same unit). Conceptually: an AA formula that calls `unit($hash)` on a unit containing a `temp_data` message, then triggers a second, independent evaluation path (e.g., a remote AA call or a secondary bounce) that also calls `unit($hash)` on the same unit within the same process lifetime — if the second read observes the mutated (temp_data-stripped, timestamp-rewritten) object from the first call's in-place edits rather than a fresh copy, this demonstrates the corruption. Confirming this requires inspecting `storage.readJoint`'s cache-return behavior, which was not available within the current investigation.
