### Title
API client stack-scope bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`ApiClient#stack_id`) can only see that one stack, by routing all stack lookups through the scoped `stacks` collection. [1](#0-0)  `Shipit::Api::CCMenuController` overrides the `stack` accessor and looks the stack up directly from the unscoped `Stack` model instead of through `stacks`, so the stack-scoping binding is never enforced on this endpoint. [2](#0-1) 

### Finding Description
`BaseController#stacks` restricts the set of visible stacks to the one referenced by `current_api_client.stack_id` when the client is stack-scoped, and `BaseController#stack` (used by every other API controller) is derived from that scoped collection:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`CCMenuController` re-defines `stack` to bypass this scope entirely, resolving the record from the top-level `Stack` class using only the request's `stack_id` parameter:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`require_permission :read, :stack` only checks that the `read:stack` permission bit is present on the token — it does not check which stack the token is bound to. [3](#0-2)  `ApiClient#check_permissions!` likewise only compares permission strings, never the client's `stack_id`. [4](#0-3) 

This is the same bug class as the report's `advance_epoch` example: the code is supposed to operate on the caller-authorized object (`stacks`, i.e. the equivalent of `oracle_stats`) but instead operates on an unrelated, unscoped object (`Stack`, i.e. the equivalent of `oracle`). The equality that should hold — "stack a token authorizes == stack a token touches" — is broken specifically on this controller.

Concretely, `ApiClient`s can be created scoped to exactly one stack (e.g. via the admin UI, `ApiClientsController#create_params` permits `:name` and `permissions`, and the `stack` fixture/column exists specifically to support this restriction, `test/fixtures/shipit/api_clients.yml:12-17`). [5](#0-4)  The `stacks_controller` tests confirm the expected invariant — "an api client scoped to a stack will only see that one stack" — for the ordinary stacks API. [6](#0-5)  `CCMenuController` never applies that invariant.

### Impact Explanation
Any holder of a stack-scoped `read:stack` API token (a token an administrator deliberately restricted to one repository/stack) can use that same token to read the CI/CD status — name, activity, last build status/label/time, web URL — of every other stack managed by the Shipit instance, by simply changing the `stack_id` path/query parameter. This is an escalation of a deliberately scoped credential into reading state of stacks it was never authorized for, i.e. unauthorized read of stack/deploy state across repositories the token holder should not have access to.

### Likelihood Explanation
Exploitation requires nothing more than possession of any valid, stack-scoped `read:stack` API token (the exact kind of "restricted" token administrators are meant to be able to hand out safely, e.g. to third-party CI dashboard tools) and knowledge/guessing of another stack's identifier — both of which are readily available to a token holder with no additional privileges. No signature forgery, code execution, or session hijacking is needed.

### Recommendation
Have `CCMenuController#stack` reuse the inherited, properly scoped `stacks` collection (i.e. `stacks.from_param!(params[:stack_id])`) instead of resolving from the unscoped `Stack` class, so that stack-scoped API clients cannot read data belonging to other stacks.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (as in `here_come_the_walrus` fixture). [5](#0-4) 
2. Attacker (holder of that token) issues:
   `GET /api/stacks/B/ccmenu.xml?token=<here_come_the_walrus token>`
3. `authenticate_api_client` in `CCMenuController` authenticates the client from the `token` param. [7](#0-6) 
4. `require_permission :read, :stack` passes because the token has `read:stack`. [8](#0-7) 
5. `stack` resolves stack `B` directly via `Stack.from_param!`, ignoring that the token is scoped to stack `A`, and the response renders stack `B`'s deploy status. [9](#0-8)
