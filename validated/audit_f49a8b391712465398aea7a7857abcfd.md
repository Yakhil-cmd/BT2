### Title
Fee-on-transfer / non-standard ERC20 tokens break XCM `ERC20Transactor` accounting, causing frozen funds and checking-account insolvency - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` (used by AssetHub Westend's `AssetTransactors`) executes real Solidity `transfer`/`transferFrom` calls against arbitrary ERC20 contracts deployed via `pallet-revive`, but only checks the boolean return value of the call — never the actual balance delta (`balanceOf` before/after) — before crediting the XCM `AssetsInHolding` ledger with the *nominal* requested `amount`. This is the same missing-invariant class as the Cooler report: “amount requested” is trusted as “amount actually moved,” with no verification against a fee-on-transfer/deflationary ERC20.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` both:
1. Encode a Solidity `IERC20::transfer(to, amount)` call with the caller-specified `amount`.
2. Execute it via `pallet_revive::Pallet::<T>::bare_call`.
3. Decode only the boolean return value (`abi_decode_returns_validate`) — treating `true` as full success.
4. On withdraw, construct `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the *requested* `amount`, not any measured delta.
5. On deposit, treat the transfer as fully satisfying `what` (the full holding) once the boolean returns `true`. [1](#0-0) [2](#0-1) 

Any ERC20 contract deployed on Asset Hub through `pallet-revive` can implement a fee/tax on `transfer`/`transferFrom` (e.g., burn X%, redirect X% elsewhere) while still returning `true`, exactly like the STA/PAXG-style tokens in the original report. There is no privileged action needed: a permissionless contract deployer creates such a token, then any user references its `AccountKey20` location as an XCM asset (matched by `ERC20Matcher`, wired into `AssetTransactors` in the AssetHub Westend XCM config) and performs ordinary `WithdrawAsset`/`DepositAsset` / `transfer_assets` operations. [3](#0-2) 

Concrete flow:
- **Withdraw path** (user → checking account): user calls an XCM extrinsic that withdraws `amount` of the fee-on-transfer ERC20 from their own account into `TransfersCheckingAccount`. The real `transferCall` deducts a fee, so the checking account actually receives `amount * (1 - fee)`. But `Erc20Credit(amount)` — the *full nominal amount* — is placed into holding and later used to build outbound `WithdrawAsset`/`ReserveAssetDeposited` XCM instructions describing `amount`, over-stating what the checking account actually holds.
- **Deposit path** (checking account → beneficiary): to satisfy an XCM `DepositAsset` for `amount`, the transactor calls `transfer(beneficiary, amount)` from the checking account. If the token is fee-on-transfer, the beneficiary again receives less than `amount`, but the executor considers the holding of `amount` fully deposited and moves on, again without reconciling against the checking account's real on-chain balance.

Because the checking account is a shared, global reserve for a given ERC20 asset serving *all* users of that asset across the chain (not per-loan like the original Cooler contract), repeated fee-on-transfer deductions steadily drain the checking account's real ERC20 balance below what the accumulated ledger of `amount`s implies is backed. Eventually a legitimate user's deposit (transfer from checking account to a beneficiary for the full nominal `amount`) will revert on-chain with an ERC20 insufficient-balance error (mirrored by OpenZeppelin's standard `_update`/`ERC20InsufficientBalance` check used in the reference ERC20 fixture), because the checking account no longer holds enough tokens to cover the nominal `amount` that other transfers assumed was fully preserved. [4](#0-3) 

This directly parallels the reported Cooler bug: the contract-holding (checking account) becomes insolvent relative to the amounts the accounting layer believes are backed, causing legitimate deposit/withdraw operations for *other, unrelated* users of the same ERC20 asset to permanently fail once the shortfall accumulates — a deterministic loss/freezing of funds rather than a mere economic griefing.

### Impact Explanation
This is a High-severity issue class: it causes systemic, permanent loss/freezing of funds for a whole asset class (not just the attacker), because the shared `TransfersCheckingAccount` becomes under-collateralized relative to what the XCM ledger believes it holds. Any subsequent XCM deposit that tries to pay out the "nominal" amount for that ERC20 asset can revert (`FailedToTransactAsset("ERC20 contract transfer failed")` or a hard revert), freezing legitimate users' funds in-flight and leaving the checking account permanently insolvent for that asset. This matches the "huge loss of funds for lender and borrower" framing of the original report, translated onto the shared reserve-account model used by Polkadot's ERC20 XCM integration.

### Likelihood Explanation
Likelihood is Medium-High: no privileged role is required. Any account can deploy an arbitrary ERC20 contract via `pallet-revive` (which explicitly supports deploying real Solidity contracts, as shown by the `MyToken`/`ERC20.sol` fixtures used in `withdraw_and_deposit_erc20s` tests) and cause it to be used as an XCM-transactable asset matched by `ERC20Matcher`. Once deployed, ordinary `transfer_assets`/`execute` extrinsics using `WithdrawAsset`/`DepositAsset` on that asset trigger the vulnerable code path with no extra requirements. [5](#0-4) 

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual `balanceOf` of the relevant account (checking account or beneficiary) before and after the `transfer`/`transferFrom` call, and use the measured delta — not the caller-requested `amount` — both to construct `Erc20Credit` on withdrawal and to determine how much of `what` has actually been satisfied on deposit (returning the unconsumed remainder as `AssetsInHolding` if the actual amount received is less than requested, similar to how `fungible`/`fungibles` traits in FRAME return the "actual" transferred amount rather than assuming the requested amount always applies verbatim). [6](#0-5) 

### Proof of Concept
No executable PoC was run (the task environment provides read-only code search, not a Rust/FRAME test harness execution). Based on static code reading:
- Confirmed `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` only decode the boolean return of `IERC20::transferCall` and never call/compare `balanceOf` before/after.
- Confirmed `ERC20Transactor` is wired into AssetHub Westend's production `AssetTransactors` tuple, so it is reachable from ordinary user-facing XCM extrinsics (`transfer_assets`, `pallet_xcm::execute`) for any ERC20 registered/matched by `ERC20Matcher`.
- Confirmed `pallet-revive` supports deploying arbitrary Solidity contracts including standard-return-value ERC20s (per the `withdraw_and_deposit_erc20s` test using a compiled `MyToken` contract), which would permit an attacker to deploy a fee-on-transfer variant.
- Did **not** verify (due to no execution access) the exact downstream consequence of a checking-account shortfall on subsequent XCM messages (e.g., whether an `ExtraSanityChecks`/reserve-balance invariant elsewhere in the runtime catches or partially mitigates this before it manifests as a stuck deposit). This should be validated with an integration test that: (1) deploys a fee-on-transfer ERC20 fixture, (2) performs a withdraw into the checking account, (3) performs deposits for multiple users of that same asset until a deposit reverts due to insufficient checking-account balance.

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});

		source: &AccountId,
		dest: &AccountId,
		amount: Self::Balance,

		Self::done_transfer(source, dest, amount);
