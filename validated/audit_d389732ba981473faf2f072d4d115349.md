### Title
Cross-tenant Commit status mutation via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up every `Commit` row whose `sha` matches the webhook payload's `sha`, with no filter tying the result set to the repository/stack that the webhook signature actually authenticated. Since `sha` is not globally unique across `Stack`s/repositories, a validly-signed webhook from one repository's own GitHub status event can mutate `Commit` rows belonging to a completely unrelated stack/repository/org.

### Finding Description
The broken binding is:
`{Commit rows iterated by StatusHandler#process}` should equal `{Commit rows where commit.stack.repository.full_name == payload['repository']['full_name']}`, but the actual code produces `{Commit rows where commit.sha == params.sha}` with no repository/stack predicate at all.

`app/models/shipit/webhooks/handlers/status_handler.rb:21` performs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This is inconsistent with the base `Handler` class, which exposes a `stacks` helper explicitly scoped to the payload's repository via `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 

Other handlers, e.g. `PushHandler`, correctly use that scoped `stacks` relation before touching any records: [3](#0-2) 

`StatusHandler` bypasses this scoping entirely and queries `Commit` directly by `sha`.

`WebhooksController#verify_signature` only authenticates *which organization's* secret signed the request (`Shipit.github(organization: repository_owner)` / `verify_webhook_signature`) — it proves the sender legitimately controls a webhook for `repository_owner`'s org, but it does nothing to restrict which DB rows `StatusHandler#process` is allowed to touch: [4](#0-3) [5](#0-4) 

Exploit flow: An attacker who owns/administers a repository that is legitimately integrated with Shipit (within the stated attacker capabilities — "emit webhooks from a repository they own") can, using ordinary GitHub Status API permissions on their own repo, cause GitHub to emit a genuinely signed `status` webhook for a commit sha in their own repository's history. If that sha happens to collide with a `Commit` row belonging to an entirely different stack/repository/org (plausible for content-identical bootstrapped/template "Initial commit" commits with fixed author/committer/timestamp — not a hash-collision attack, just identical inputs), `StatusHandler#process` will call `commit.create_status_from_github!(params)` on that unrelated commit too. `create_status_from_github!` calls `add_status`, which can trigger `ProcessMergeRequestsJob` on state transitions to success, per `commits_test.rb`: [6](#0-5) 

None of `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema check the repository/stack ownership of the `Commit` rows being mutated — they only validate the shape of the payload and the sender's org identity, not the target records.

### Impact Explanation
A single legitimately-signed webhook from an attacker-controlled repository can flip the commit status (`create_status_from_github!` → `add_status` → potentially `ProcessMergeRequestsJob`) of a `Commit` belonging to a stack owned by an unrelated GitHub org, with no cross-check that the mutated row belongs to the authenticating repository. This is a payload for one repository mutating another tenant's `Commit`/`Stack` state, potentially influencing deployability/merge decisions — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). Blast radius is N-tenant: every `Commit` row sharing that sha across the whole installation is affected by one webhook.

### Likelihood Explanation
Requires: (1) attacker controls a repository already integrated into Shipit under some org (so a genuine signed webhook can be produced without knowing another org's secret), and (2) a sha collision between a commit in that repo and a commit belonging to a different stack. The latter is not a cryptographic SHA-1 break requirement — content-identical commits (same tree, author, committer, timestamps, message) naturally hash identically, which is realistic for bot-generated/templated "Initial commit" style commits with fixed metadata. This makes the exploit low-cost and repeatable for an attacker who controls such a repository, though it depends on a specific collision existing in the target Shipit instance's database.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the payload's repository, mirroring the `stacks` helper used elsewhere, e.g. `stacks.joins(:commits).where(shipit_commits: { sha: params.sha }).flat_map(&:commits)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so that only commits within stacks belonging to the authenticated repository can be mutated.

### Proof of Concept
```ruby
test "status webhook only mutates commits belonging to the authenticated repository" do
  repo_a = shipit_repositories(:shipit) # e.g. org A
  repo_b = create_repository(name: 'other', owner: 'other-org') # org B, disjoint
  stack_a = repo_a.stacks.first
  stack_b = repo_b.stacks.create!(environment: 'production', branch: 'master')

  colliding_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: colliding_sha, message: 'Initial commit', ...)
  commit_b = stack_b.commits.create!(sha: colliding_sha, message: 'Initial commit', ...)

  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => repo_a.full_name, 'owner' => { 'login' => repo_a.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  commit_a.reload
  commit_b.reload
  assert_equal 'success', commit_a.state # expected: mutated (belongs to authenticated repo)
  refute_equal 'success', commit_b.state # currently FAILS: commit_b is also mutated despite belonging to a different repo/org
end
```
This demonstrates the equality violated: `{commits mutated}` includes `commit_b`, which is not in `{commits where stack.repository.full_name == payload['repository']['full_name']}`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
