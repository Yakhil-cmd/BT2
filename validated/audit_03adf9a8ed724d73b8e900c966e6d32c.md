### Title
Webhook signature verified against organization derived from unverified payload field, while event handlers act on a different repository field from the same payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by reading `repository_owner` straight out of the untrusted, not-yet-verified JSON body [1](#0-0) . That same field-selection logic falls back to a completely separate top-level `organization.login` field if `repository.owner.login` is absent [2](#0-1) . Because Shipit is designed to be configured for multiple GitHub organizations, each with its own `webhook_secret` in `config/secrets.yml` [3](#0-2) , the identity used to select and validate the signing secret (`repository_owner`) is not cryptographically bound to the repository that the dispatched event handlers subsequently act on.

### Finding Description
The signature check is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

`repository_owner` is derived from the same attacker-controlled JSON body whose authenticity is being checked, and it is used solely to select *which* per-organization secret to HMAC-verify against. The verification proves only "this payload was signed with organization X's secret" - it proves nothing about which repository the payload claims to describe. `create` then dispatches the full, unmodified `params` (including `repository.full_name`, independent of `repository.owner.login`/`organization.login`) to the registered handlers [5](#0-4) .

In a multi-tenant Shipit deployment (explicitly supported: multiple orgs each with `app_id`, `webhook_secret`, `oauth` in `config/secrets.yml` [3](#0-2) , and each org creates its own GitHub App with its own webhook secret per `docs/setup.md` [6](#0-5) ), a person who legitimately knows *one* organization's webhook secret (e.g., an admin/maintainer of their own org hosted on the same Shipit instance) can craft a payload where `repository.owner.login`/`organization.login` names their own org (so `verify_signature` fetches and checks against a secret they know) while `repository.full_name` (and `sha`, `state`, etc., used by handlers such as `push_handler.rb`/`status_handler.rb`) names a victim org/repository they do not own. The signature check passes because it is validated against the wrong binding; the handler then acts on the victim repository using fields never covered by that binding decision.

This breaks the trust equality the engine relies on: `organization that authenticated == organization whose repository is written`.

### Impact Explanation
If exploitable, this allows an attacker who only holds credentials for their own tenant/org (not the victim's) to forge `push` or `status` events for a different, unrelated stack hosted on the same Shipit instance. Depending on which handler is targeted this could: trigger `GithubSyncJob`/commit ingestion for a victim stack, or forge green CI `status` events for a victim commit, which combined with `continuous_deployment` could lead to an unauthorized deploy of attacker-chosen content into a repository the attacker does not control - a cross-repository write / unauthorized-deploy class impact.

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization (a documented, supported configuration, not a misuse of the engine) and requires the attacker to possess a valid `webhook_secret` for at least one configured organization (their own, legitimately). No GitHub App private key, repository write access on the victim repo, or Shipit session is needed to construct the forged HTTP POST to `/webhooks`.

### Recommendation
Bind the signature-selection identity to the same field(s) the handlers actually act on, and verify that all organization/repository identifiers in the payload are mutually consistent (e.g., recompute/verify signature using the exact same field used later for repository resolution, or explicitly reject payloads where `repository.owner.login` does not match `organization.login` when both are present, and ensure handlers cross-check the verified organization against the repository actually being mutated).

### Proof of Concept
Not independently executed; based on static review of `app/controllers/shipit/webhooks_controller.rb` (`verify_signature`/`repository_owner`) and `config/secrets.development.shopify.yml`, which together establish the field-mismatch described above. I was not able to open `app/models/shipit/webhooks/handlers/push_handler.rb` in this session to confirm the exact field(s) it uses for repository resolution (the tool call to view it was cut off before completion); this should be confirmed against that file (and `status_handler.rb`) before treating the PoC as fully proven.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
```
