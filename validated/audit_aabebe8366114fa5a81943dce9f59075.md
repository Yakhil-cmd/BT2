### Title
Race between `dryRunPrimaryAATrigger` and real unit writes corrupts shared in-memory DAG caches, bypassing the `write` mutex - ([File: aa_composer.js])

### Summary
The CVE describes a race where a background cleanup path (laundromat) mutates shared per-object state without holding the lock the rest of the system relies on, so a concurrently-running privileged path frees/derefs the same object and later code use-after-frees it. The ocore analog is `aa_composer.js`'s `dryRunPrimaryAATrigger()` (invoked automatically from `network.js` for every incoming unit that targets an AA, via the `conf.bDryRunNewTriggers` code path), which calls `writer.saveJoint()` with `objAAValidationState.bUnderWriteLock = true`, deliberately **skipping** the global `mutex.lock(["write"])` that every other unit-saving path (`network.js` real `ifOk`, `composer.js`, `divisible_asset.js`, `indivisible_asset.js`) takes before mutating the shared, unlocked, process-wide caches `storage.assocUnstableUnits`, `storage.assocBestChildren`, and `storage.assocUnstableMessages`.

### Finding Description
`writer.saveJoint()` unconditionally mutates global caches **before** the SQL transaction is known to succeed and **outside of any mutex protection for dry runs**: [1](#0-0) 

The lock that is supposed to serialize all such mutations is taken conditionally: [2](#0-1) 

`aa_composer.js`'s `handleTrigger` → `validateAndSaveUnit` explicitly sets `bUnderWriteLock = true` for AA response units, so `writer.saveJoint()` never acquires `mutex.lock(["write"])` for these paths: [3](#0-2) 

`dryRunPrimaryAATrigger()` is reachable directly from an unprivileged unit poster: any incoming unit with `count_primary_aa_triggers` causes the full node to synchronously kick off a dry run of the trigger against the real AA definition **before acquiring the `write` lock and before the real unit is saved**: [4](#0-3) 

`dryRunPrimaryAATrigger()` itself takes its own DB connection and never calls `mutex.lock(["write"])`: [5](#0-4) 

Because `writer.saveJoint()` populates `storage.assocUnstableUnits[unit]`, pushes new entries onto `storage.assocBestChildren[my_best_parent_unit]` (an array that is *shared and mutated in place*, potentially referencing a *real, existing parent unit* in the DAG), and pushes onto `storage.assocUnstableMessages[unit]`, a dry run in flight can inject synthetic/temporary props objects into these same shared structures that real, lock-protected code (`main_chain.js` MC stabilization, `writer.saveJoint` from `network.js`'s real `ifOk` path, `parent_composer.js`, validation code that trusts `conf.bFaster` cached props) is concurrently reading and mutating under the `write` lock. Cleanup only happens afterward via `revertResponsesInCaches()`, which forgets only the AA **response units**, not necessarily every mutation performed on `assocBestChildren` for parents that are touched mid-flight by concurrently-committed real units: [6](#0-5) 

`storage.forgetUnit()` uses object-identity (`indexOf`) to `_.pull` an entry out of `assocBestChildren[parent_unit]`, which is safe only if no other objects have been interleaved into concurrent execution over the same array in the meantime; the dry run's own DB round trips (`conn.query`, `db.takeConnectionFromPool`) are the same kind of async gaps that CVE-2024-50106's laundromat left when it "unlocked" before finishing revocation: [7](#0-6) 

This is precisely analogous to the kernel bug's structure: a secondary maintenance/estimation path (laundromat / dry run) manipulates the same shared list (`cl_revoked` / `assocBestChildren`, `assocUnstableUnits`) that the primary, lock-protected path (`free_stateid` / real `writer.saveJoint` under `mutex.lock(["write"])`) also manipulates, but the secondary path does not hold the coordinating lock, creating a window where entries can be pulled/pushed inconsistently, corrupting shared DAG bookkeeping used by every node running with `conf.bDryRunNewTriggers` enabled.

### Impact Explanation
Corruption of `storage.assocUnstableUnits` / `storage.assocBestChildren` / `storage.assocUnstableMessages` directly feeds `is_free`, `witnessed_level`, best-parent selection, and MC advancement logic used across `main_chain.js`, `parent_composer.js`, and validation (`conf.bFaster` fast paths compare against this exact cache and `throwError` on mismatch — see `readPropsOfUnits`/`readBestChildrenProps` consistency checks). A corrupted or torn cache can cause a node to compute a different best parent/witnessed level/free-unit set than its peers, i.e., **node disagreement on validity or stability**, or crash the node (`throwError`/`throw Error("different best children...")`), which for a public full node offering `light/dry_run_aa` (reachable from light clients, `network.js` case `'light/dry_run_aa'`) is remotely triggerable, and for `conf.bDryRunNewTriggers` full nodes is triggerable by simply posting any unit that targets an existing AA — both squarely within an "unprivileged unit poster"/"AA trigger sender" threat model.

### Likelihood Explanation
Node.js is single-threaded, but each dry run performs multiple `await`/callback-based DB round trips (`db.takeConnectionFromPool`, several `conn.query`, AA formula evaluation with sub-triggers, `kvstore.batch()`), giving many yield points during which the event loop can service other queued jobs — including real unit processing already holding the `write` lock and mutating exactly the shared maps the dry run is concurrently populating/consuming without lock protection. Triggering the code path only requires posting an ordinary unit that pays into an AA address (`count_primary_aa_triggers`), something any unprivileged network participant can do, so the precondition is trivial; the difficulty lies only in winning the timing race, similar to the kernel CVE.

### Recommendation
Make `dryRunPrimaryAATrigger()` (and any other caller of `writer.saveJoint` with `bUnderWriteLock=true` that isn't already executing while the real `write` lock is held by the same logical operation) acquire `mutex.lock(["write"])` for its entire cache-mutating window, or isolate its mutations to a private/cloned view of `assocUnstableUnits`/`assocBestChildren`/`assocUnstableMessages` that is never referenced by concurrent real-write code, merging results back only after acquiring the lock. Additionally, harden `revertResponsesInCaches()`/`forgetUnit()` to detect and hard-fail (rather than silently `indexOf`-miss) when the expected object is no longer present at the expected cache slot, surfacing any such race immediately instead of allowing silent divergence.

### Proof of Concept
1. Run a full node with `conf.bDryRunNewTriggers = true` (or expose `light/dry_run_aa`) and at least one real AA deployed with a moderately complex trigger handler (calling sub-AAs to add multiple async DB round trips).
2. From an unprivileged wallet, post unit A that pays to the AA address (this triggers `dryRunPrimaryAATrigger` in `network.js:1271-1281`, which runs unlocked).
3. Concurrently (same or next event-loop tick, before the dry run's `ROLLBACK`/`revertResponsesInCaches` completes) post/relay unit B, unrelated but sharing the same `best_parent_unit` as one of the dry run's synthesized units, through the normal `handleJoint`/`writer.saveJoint` path (which does take `mutex.lock(["write"])`).
4. Observe that `storage.assocBestChildren[best_parent_unit]` receives entries from both flows; when the dry run's `revertResponsesInCaches` runs `_.pull` based on object identity, or when `fixIsFreeAfterForgettingUnit` recomputes `is_free`, the resulting cache state can diverge from the DB truth — reproducible by asserting cache-vs-DB consistency the way `main_chain.js`'s `readBestChildrenProps`/`storage.js`'s `readPropsOfUnits` already do internally (their `throwError` assertions are the detection mechanism used by ocore's own `conf.bFaster` self-checks), confirming an exploitable inconsistency window analogous to the kernel's revoked-but-not-yet-removed state race.
