### Title
Membership webhook lets an attacker with a valid signature for *any* configured GitHub organization forge team membership for an *unrelated* `Shipit.github_teams` organization, bypassing authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from the untrusted JSON body (`repository.owner.login` or `organization.login`) — [1](#0-0) , [2](#0-1) . The `membership` event, handled by `MembershipHandler`, then trusts a *different* field of the same payload — `params.organization.login` — to attach the reported team/membership to a `Team` record, and unconditionally adds the named member to that team when `action == 'added'` [3](#0-2) . `Shipit.github_teams` — the set of teams that gate access to the whole application via `User#authorized?` — is built purely from `Team` records matched by organization/slug `handle`, with no cross-check against which GitHub App/organization actually authenticated the webhook [4](#0-3) , [5](#0-4) .

### Finding Description
The equality that should hold is:

```
organization whose webhook_secret authenticated the request == organization whose team membership is mutated
```

In a multi-organization Shipit configuration (as documented in `config/secrets.development.example.yml:18-38`), each organization can have its own `github.<org>.webhook_secret`. `Shipit.github(organization:)` looks up the app config strictly by the `organization` key passed in, independent of any other organization's config [6](#0-5) .

`WebhooksController#verify_signature` derives that `organization` argument from the untrusted payload itself (`repository_owner`), then verifies the raw body against *that* organization's secret [7](#0-6) . Because the HMAC is computed over the *entire* raw JSON body, an attacker who legitimately controls one configured organization (e.g., they have a GitHub App/organization "attacker-org" set up and are able to install their own webhook against the same Shipit instance, learning `attacker-org`'s `webhook_secret`) can freely construct the rest of the JSON payload, including a `membership` event whose `organization.login` field names a completely different, victim organization that is one of `Shipit.github_teams`.

`MembershipHandler` never re-derives or checks the authenticating organization; it simply trusts `params.organization.login` to create/find the `Team` and calls `team.add_member(member)` [8](#0-7) , `app/models/shipit/team.rb:41-43`. Since `Team.find_or_create_by!` is keyed on GitHub's numeric `team.id` (also attacker-controlled in the payload) rather than any signature-bound value, the attacker can target an existing authorized `Team` (matching a real `github_id` for a team under `Shipit.github_teams`) and add an arbitrary `member.login` (their own GitHub login) to it.

Because `User#authorized?` grants full application access to any user belonging to *any* team in `Shipit.github_teams` [5](#0-4) , this forged membership escalates the attacker into the authorization boundary that gates the entire Shipit UI/session (`Shipit::Authentication#force_github_authentication`, [9](#0-8) ).

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization — one of the explicitly listed High-severity impacts. An attacker who is not a member of any authorized GitHub team, but who is able to send a validly-signed webhook for *some* configured organization, can grant themselves membership in a `Team` object that gates access for a *different* organization, then complete GitHub OAuth as themselves and pass `authorized?` and access the full Shipit UI (stacks, tasks, deploy triggers via the session-authenticated non-API controllers).

### Likelihood Explanation
The bug is only reachable in the multi-organization configuration mode (`Shipit.github_default_organization` non-nil, per-org `webhook_secret`s in `secrets.yml`), and requires the attacker to know or control a `webhook_secret` for at least one configured organization on the instance (e.g., because they administer that org's GitHub App integration themselves, or that org's `webhook_secret` is left blank/nil, which `verify_webhook_signature` treats as "always verified" — `lib/shipit/github_app.rb:76-83`). This is a realistic scenario for a shared/multi-tenant Shipit deployment servicing several organizations, some of which may be less trusted than others, or where an operator forgets to set a per-org secret.

### Recommendation
Bind the payload's `organization`/`repository.owner` field used by handlers to the same organization value that was used to select/verify the webhook signature, and reject the event if they diverge. Concretely, thread the verified `repository_owner` (or the `GitHubApp` instance itself) from `WebhooksController` into each `Handler`, and in `MembershipHandler#find_or_create_team!` assert `params.organization.login.casecmp?(verified_organization)` before creating/mutating any `Team`/`Membership`. More generally, every handler that trusts an organization/repository field from the JSON body (`Handler#repository_name`, `MembershipHandler#find_or_create_team!`) should validate it against the organization whose secret authenticated the request.

### Proof of Concept
1. Shipit is configured with multiple GitHub organizations, e.g. `victim-org` (whose `Team` with `github_id: 1001` is included in `Shipit.github_teams` for access control) and `attacker-org` (webhook secret known to the attacker, e.g. because they administer that org's GitHub App or its `webhook_secret` is unset).
2. Attacker crafts a `membership` webhook JSON body:
```json
{
  "action": "added",
  "team": { "id": 1001, "name": "Developers", "slug": "developers", "url": "https://api.github.com/..." },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, body)` and sets `X-Github-Event: membership`.
4. `WebhooksController#verify_signature` reads `repository_owner` — falls back to `params.dig('organization', 'login')` since there is no `repository` key present here, so it actually resolves to `"victim-org"` in this exact payload shape; to make this concrete for the two-different-fields case, attacker instead includes a `repository` key with `owner.login: "attacker-org"` (verified against the known `attacker-org` secret) while `organization.login` remains `"victim-org"` for the handler — [2](#0-1)  shows `repository_owner` prefers `repository.owner.login` over `organization.login`, confirming the two fields can diverge.
5. Signature check passes (verified against `attacker-org`'s secret) [1](#0-0) .
6. `MembershipHandler#process` runs, finds `Team` with `github_id: 1001` (a real `victim-org` team in `Shipit.github_teams`), and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))` [10](#0-9) .
7. Attacker completes GitHub OAuth as `attacker-github-login`; `User#authorized?` now returns true because of the forged `Membership` row, granting full Shipit access [5](#0-4) .

Note: full confirmation of step 4's exact field precedence for every payload shape (whether `repository` is required to be present alongside `organization` for a `membership` event in real GitHub payloads) could not be verified against GitHub's actual webhook schema from the code alone; this is stated as a limitation. The root architectural flaw — that `verify_signature`'s organization selection and `MembershipHandler`'s organization trust are two independent, unbound reads of the same untrusted JSON body — is confirmed directly in the cited code.

          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action

            team.add_member(member)
          when 'removed'

          end
        end

          end
        end
