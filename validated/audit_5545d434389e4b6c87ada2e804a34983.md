### Title
Insecure Default File Permissions on Saved Private Textcoin Payload (Mnemonic + Private Payment Chains) - (File: wallet.js)

### Summary
`storePrivateAssetPayload()` in `wallet.js` writes a ZIP file containing the plaintext mnemonic and the full private payment chain for a private/indivisible-asset textcoin to disk using `fs.writeFile()` with no explicit file mode, relying entirely on the OS default `umask`. On typical Linux/desktop deployments (`umask 022`), this results in a world-readable file (`-rw-r--r--`) containing spendable secret material.

### Finding Description
When a user sends a private or fixed-denomination asset ("textcoin") to a recipient who is not reachable by device address (e.g., paying to an email/offline recipient), the wallet must serialize the mnemonic and private payment chain to a file that will later be handed to the recipient out-of-band: [1](#0-0) 

That serialization happens in `storePrivateAssetPayload`, which builds a ZIP archive containing the `mnemonic` and `chains` (the private payment elements proving ownership of the asset outputs) and writes it with Node's `fs.writeFile`, which does not set an explicit mode and therefore inherits the process `umask`: [2](#0-1) 

Unlike `kvstore.js`, which explicitly hardens its data directory to `0700` when creating it: [3](#0-2) 

no equivalent hardening is applied to the file produced by `storePrivateAssetPayload`. The mnemonic embedded in this file is the sole secret required to claim/spend the enclosed private asset outputs — anyone who can read the file can redeem the funds, exactly as `receiveTextCoin`/`handlePrivatePaymentFile` later do when the intended recipient imports it: [4](#0-3) 

This mirrors the reported filebrowser class of bug (CWE-276): a file holding sensitive, directly-usable secrets is created without an explicit restrictive permission mask, so any other local OS account (or any other application/process on the same machine, e.g., another user of a shared server, a malicious app on the same desktop, or a compromised process) can read the mnemonic and drain the private textcoin before the legitimate recipient claims it — a real unauthorized-spending / theft-of-funds outcome, not merely an information leak.

### Impact Explanation
Any local process/account other than the wallet owner that can read the output path can extract the `mnemonic`, independently construct a claim transaction, and steal the entire value of the private asset payment before (or instead of) the intended recipient — i.e., unauthorized spending of funds that the legitimate sender/recipient believed were protected until out-of-band delivery. This is a concrete fund-loss scenario reachable through a completely normal, unprivileged wallet operation (sending a private/indivisible-asset textcoin), not requiring any malicious peer, hub, or node.

### Likelihood Explanation
Any wallet user who sends a private or fixed-denomination asset to an address not associated with a known device (the standard "textcoin" flow) triggers this code path. On any multi-user machine, shared/cloud desktop, or any environment where the storage path is synced/shared, or where any other local process has default read access (the common case on Linux, macOS default umask, and many desktop environments), the created file is immediately readable by others, making exploitation trivial once the file exists — no race condition or special privileges are required, just local file read access at any point before the recipient collects it.

### Recommendation
Explicitly set restrictive permissions when creating the private-payload file, e.g. pass `{ mode: 0o600 }` to `fs.writeFile` (and consider `fs.chmod` immediately after creation as a defense-in-depth measure for platforms where `mode` on `writeFile` is ignored), analogous to the `0700` directory mode already used in `kvstore.js`. Additionally, document that any pre-existing insecurely-created files should be remediated via `chmod` after upgrade, since applying the fix does not retroactively correct existing files.

### Proof of Concept
1. On a Linux system with default `umask 022`, run a wallet built on this ocore version and send a private asset ("textcoin") to a recipient not connected via device address, providing a `getPrivateAssetPayloadSavePath` callback that resolves to e.g. `/home/alice/textcoin.zip`.
2. `storePrivateAssetPayload` (`wallet.js:2850-2864`) writes the archive via `fs.writeFile(fullPath, zipFile, cb)` with no mode specified.
3. As a different local OS account (or any other local process), run `ls -l /home/alice/textcoin.zip` and observe `-rw-r--r--`, confirming world-readability.
4. Read/unzip the file to extract `private_textcoin` → `{ mnemonic, chains }`, then call `receiveTextCoin(mnemonic, attacker_address, ...)` to claim the funds to the attacker's own address before the intended recipient does.
