### Title
Double-callback crash when a malformed private-payment payload is received from a payment counterparty - ([File: network.js])

### Summary
`network.js:handleSavedPrivatePayments()` invokes the per-row `async.each` iteratee callback (`cb`) twice when the private-payment payload hashing throws. The `catch` block calls `deleteHandledPrivateChain(..., cb)` but does not `return`, so execution falls through and later calls `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError` callbacks invoke `cb` a second time. This is the same bug class as CVE-2021-21375: a first "response" (here, the hash-failure error path) already resolves/terminates handling of the item, but code continues on as if nothing happened, and a second, later "response" for the same item runs into inconsistent/duplicated state and crashes the process.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` iterates queued private-payment rows with `async.each(rows, function(row, cb){ ... })`. Inside, `validateAndSave` computes a payload hash: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
```

There is no `return` statement after the `catch` block's `deleteHandledPrivateChain(..., cb)` call. This means that once `getBase64Hash()` throws (analogous to the first PJSIP `183` response that already fails negotiation), execution continues into the normal validation path and ultimately calls `cb` a second time via one of `ifOk`/`ifError`/`ifWaitingForChain` (analogous to the second `183` response being processed against a state that has already been finalized). `deleteHandledPrivateChain` itself is also asynchronous, so the second `cb` call from the fall-through path can race with / follow the first one, giving `async.each` two callback invocations for the same iteration.

`getBase64Hash` (via `object_hash.js`/`string_utils.js`, using `getSourceString`) throws on malformed strings such as those containing lone UTF-16 surrogates — precisely the kind of "invalid string" check that `validation.js` elsewhere treats as a rejectable error (`isObjectWellFormed` / "unit contains invalid string (lone surrogate or null byte)"), but private-payment payloads reaching `handleSavedPrivatePayments` are attacker-supplied JSON from a device/private-payment counterparty and are not pre-filtered by that check before `getBase64Hash` is called here.

Modern `async` (as used elsewhere in this codebase) wraps each iteratee callback with an "only-once" guard and throws (`Error: Callback was already called`) if the same callback is invoked more than once. Because `handleSavedPrivatePayments` has no surrounding `try/catch`, this thrown error becomes an uncaught exception that crashes the Node.js process — a full denial of service, not merely a rejected unit.

### Impact Explanation
Any private-payment counterparty (a device that a user has ever interacted with, e.g. through `wallet.js`/`handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → `unhandled_private_payments` → `handleSavedPrivatePayments`) can craft a private payment chain whose head payload contains a malformed string field (lone surrogate) that makes `objectHash.getBase64Hash` throw. This deterministically drives execution into the double-callback path and crashes the receiving wallet/hub process, matching the "network unable to confirm new units" / node-availability impact bucket required by the rules. This is reachable purely by an unprivileged private-payment counterparty sending a private_payment message — no hub/peer/node privilege is required.

### Likelihood Explanation
Likelihood is high: constructing a JSON payload with a lone surrogate character is trivial, and the attack requires only being a private-payment counterparty of the victim (a normal, low-trust relationship in this protocol, e.g. any device the user has paid or received payment from). No race condition or timing precision is needed — the fall-through is unconditional once the hash call throws.

### Recommendation
Add a `return` after the `catch` block in `network.js`'s `validateAndSave` (inside `handleSavedPrivatePayments`) so execution does not continue to compute `key` and call `privatePayment.validateAndSavePrivatePaymentChain` after `deleteHandledPrivateChain(..., cb)` has already been scheduled. Additionally, validate private-payment payloads for well-formedness (reuse `isObjectWellFormed`-style checks) before calling `objectHash.getBase64Hash`, and wrap `handleSavedPrivatePayments`'s per-row processing in error handling so a thrown hash error cannot escape as an uncaught exception.

### Proof of Concept
1. As a device paired with the victim's wallet (a private-payment counterparty), send a `private_payment` message via the hub whose `chains[0][0].payload` contains a string field crafted with an unpaired UTF-16 surrogate (e.g. `"\uD800"` embedded in an output or asset field), while keeping the JSON schema checks in `wallet.js:handlePrivatePaymentChains` satisfied (non-empty arrays/objects/strings).
2. The message is queued via `network.handleOnlinePrivatePayment` → inserted into `unhandled_private_payments`, then processed later by `handleSavedPrivatePayments`.
3. In `validateAndSave`, `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws due to the invalid string.
4. `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` is called (queues `cb` invocation #1), but execution falls through (no `return`) into `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifError`/`ifOk` callback eventually calls `cb` again (invocation #2).
5. `async.each`'s only-once wrapper detects the double call and throws, crashing the wallet/hub Node.js process (uncaught exception) — denial of service against the victim node.
