### Title
Asset issuer (or AA) can freeze already-held balances of a `spender_attested` asset by publishing a new attestor list that excludes previous holders, mirroring the ERC-20 blocklist fund-lock pattern - (File: `validation.js`, `storage.js`)

### Summary
ocore lets an asset definer (a regular unit-posting address, or an AA acting as definer) create an asset with `spender_attested: true` plus an initial `attestors` list [1](#0-0) . Anyone can obtain/hold this asset while they are on the attestor list, but the definer alone can later publish an `asset_attestors` message that replaces the whole list, and the codebase enforces no rule preventing removal of addresses that already own a balance of the asset [2](#0-1) . Once removed, both (a) spending the address's existing (already-held) outputs and (b) receiving further transfers/change to that address are permanently rejected by validation, so any coins already resting at that address in this asset become unspendable forever — the exact “blocklisted-receiver locks the victim’s already-committed funds” pattern described in the Sherlock report, just implemented via ocore’s native attestor mechanism instead of an ERC-20 blocklist.

### Finding Description
When validating a payment of a `spender_attested` asset, ocore requires that:
- the author/owner address of every input being spent is currently attested: [3](#0-2) 
- every output address of the payment is currently attested, otherwise the whole payment is rejected: [4](#0-3) 
- for issuance, the issuer must be attested: [5](#0-4) 

The attestor list is not fixed at asset-creation time — `storage.readAsset`/`addAttestorsIfNecessary` always resolves to the *latest* stable `asset_attestors` unit for that asset, i.e., attestation is a moving target that the definer controls indefinitely: [6](#0-5) .

Updating that list is gated only by "author is the asset definer" and basic list well-formedness (sorted, valid addresses, non-empty, within `MAX_ATTESTORS_PER_ASSET`) — there is no check that removing an address is safe, no grandfathering of holders, and no requirement that removed addresses have zero balance: [7](#0-6) .

Critically, this asset type (and the attestor list update) is fully reachable by an ordinary unprivileged unit poster — the `asset` message and `asset_attestors` message are validated the same way regardless of whether the definer is a normal wallet or an AA [8](#0-7) . For AAs specifically, the `attestors` field on the `asset` definition and the `asset_attestors` message can be driven by formulas evaluated at execution time [9](#0-8)  and [10](#0-9) , meaning an AA can programmatically add users to the attestor list to entice them to accept/hold the asset, and later silently exclude them once they hold a meaningful balance.

This is directly analogous to the FixedStrikeOptionTeller bug: in both cases, a party other than the current fund-holder controls an address-eligibility gate (a "receiver"/attestor address) that is fine at the time the victim commits value, but can be changed afterward to make the victim's already-locked-in value permanently unrecoverable, with no bypass or reclaim path in either codebase.

### Impact Explanation
Once an address is dropped from the attestor list of a `spender_attested` asset it already holds a balance in:
- It cannot spend those outputs (`owner address is not attested`) [3](#0-2) .
- Nobody can even send it further payments in that asset that it could later try to move (`some output addresses are not attested`) [11](#0-10) .

The result is a permanent freeze of the affected holder's funds in that asset — a concrete "asset issuance/transfer condition" fund-freezing bug reachable by any unprivileged asset creator (or an AA definer), matching the accepted Medium severity class of the analog report (value already committed by users becomes unredeemable due to a later, unilateral change by the counterparty who set up the terms).

### Likelihood Explanation
Any address can author an `asset` message with `spender_attested:true`, entice counterparties (via favorable issue/transfer conditions, airdrops, or AA rewards) to accept/hold it while attested, then publish a single `asset_attestors` unit dropping them. There is no cooldown, no consent from affected holders, and no automatic entitlement to reclaim value — the check is purely "am I the definer" [12](#0-11) . This requires only routine, already-supported message types (`asset`, `asset_attestors`, `payment`) and no special privilege beyond being the asset's own definer, making it straightforward to execute.

### Recommendation
Consider one or more of:
- Disallow removing an address from the attestor list while it still holds a nonzero balance of the asset (require it to transfer out first), or
- Add a timelocked/notice period before an `asset_attestors` update takes effect, giving current holders a window to move funds, or
- Provide a fallback/reclaim path (e.g., allow attested-at-issuance holders to always redeem back to the definer, similar to the "expiry + burn to reclaim" recommendation in the analog report) so balances aren't unconditionally strandable.

### Proof of Concept
1. Address D creates asset A with `spender_attested: true`, `is_transferrable: true`, initial `attestors: [D, U]`.
2. User U receives/holds a balance of asset A (validation passes because U is attested, per `validation.js` lines 2504-2507 and 2630-2641).
3. D publishes `asset_attestors` for asset A with `attestors: [D]` only (valid per `validateAttestorListUpdate`, `validation.js` lines 2829-2848 — no check on U's balance).
4. `storage.readAsset` now resolves U as no longer attested for any future validation of asset A (`storage.js` lines 1917-1946).
5. Any subsequent attempt by U to spend their existing asset-A output fails validation with `"owner address is not attested"` (`validation.js` line 2506-2507), and no other address can even receive a transfer from U in that asset because the output-address check also fails (`validation.js` lines 2634-2639). U's balance of asset A is permanently frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
