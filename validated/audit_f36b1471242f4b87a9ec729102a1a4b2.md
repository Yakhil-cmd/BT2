### Title
Missing webhook secret disables HMAC verification entirely, allowing forged `push` events to drive `ContinuousDeliveryJob` - (File: lib/shipit/github_app.rb, app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`GitHubApp#verify_webhook_signature` fails open: if no `webhook_secret` is configured for an organization, it returns `true` for *any* signature (including none) rather than rejecting the request. `WebhooksController#verify_signature` uses this result as the sole authentication gate before dispatching to `PushHandler`, which syncs all non-archived stacks on the matching branch via `stack.sync_github(expected_head_sha: params.after)` — feeding continuous deployment.

### Finding Description
The intended binding is: `verify_webhook_signature(signature, body) == true` should only hold when `signature` is a valid HMAC-SHA1 of `body` keyed by the organization's `webhook_secret`. The actual code breaks this equality: [1](#0-0) 

`return true unless webhook_secret` means that for any organization configured in `Shipit.github(organization:)` without a `webhook_secret`, every request — signed or not — passes verification.

`WebhooksController#verify_signature` treats this return value as authoritative and only short-circuits with `head(422)` when it is `false`: [2](#0-1) 

The `repository_owner` used to select the `GitHubApp` instance, and the `repository.full_name` used later to select which stacks to sync, both come directly from the attacker-controlled JSON body — there is no cross-check tying the verified signature to a specific repository beyond the org-level secret lookup: [3](#0-2) 

Once past `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `PushHandler`, whose `stacks` scope is derived from `payload.dig('repository', 'full_name')`: [4](#0-3) 

`PushHandler#process` then syncs every non-archived stack for that repository on the branch named in `params.ref`, passing the attacker-supplied `params.after` as the `expected_head_sha`: [5](#0-4) 

If the targeted stack has `continuous_deployment` enabled, newly-synced green commits are auto-shipped via `ContinuousDeliveryJob` without any further human approval, per Shipit's continuous deployment design (`app/jobs/shipit/continuous_delivery_job.rb`, `app/models/shipit/stack.rb`).

None of the existing guards (`drop_unhandled_event`, `check_if_ping`, `ExplicitParameters` schema in `PushHandler`) authenticate the request — they only validate shape/event-type, not origin. `verify_signature` is the only authentication gate, and it is bypassed by design whenever the targeted organization's `webhook_secret` is unset.

### Impact Explanation
For any organization whose Shipit configuration omits `webhook_secret`, an unauthenticated attacker can submit an arbitrary forged `push` payload naming that organization's real repository. This triggers `sync_github` against every non-archived stack tracking the pushed-to branch, and for stacks with `continuous_deployment` enabled, this can drive `ContinuousDeliveryJob` to deploy newly-synced commits automatically — an unauthorized deploy triggered by a party that never authenticated as GitHub. This matches the Critical impact category "authentication bypass (forged webhook ... accepted)" and "unauthorized deploy". The blast radius is scoped to organizations lacking `webhook_secret` but is repeatable against every stack/branch under that organization for every request.

### Likelihood Explanation
The sole precondition is an operator misconfiguration: an organization entry in Shipit's GitHub app config without `webhook_secret` set. Given that precondition, exploitation is trivial and free — no secrets, tokens, or GitHub privileges are required; the attacker only needs to know (or guess) the target organization/repository name and branch, both of which are typically public information. The attack is fully repeatable and requires no interaction with real GitHub infra since the endpoint trusts the raw POST body.

### Recommendation
Fail closed instead of failing open: `GitHubApp#verify_webhook_signature` should return `false` (or raise) when `webhook_secret` is blank, and `WebhooksController` should require every configured organization to have a non-empty `webhook_secret` (raising/refusing to serve webhooks otherwise), rather than treating an absent secret as implicit trust.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure a fake organization in `Shipit.github` config with `webhook_secret` explicitly blank/nil.
2. Create a `Stack` for that organization's repository with `continuous_deployment: true` and a matching `branch`.
3. `POST /webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, JSON body: `{"ref": "refs/heads/<branch>", "after": "<some sha already reachable on the real repo>", "repository": {"full_name": "<org>/<repo>", "owner": {"login": "<org>"}}}`.
4. Assert response is `200 OK` (not `422`), i.e. `GitHubApp#verify_webhook_signature(nil-or-garbage, body) == true` when `webhook_secret` is blank — the broken equality.
5. Assert `stack.sync_github` was invoked (e.g., stub/mock `Stack#sync_github` and assert it received `expected_head_sha: "<sha>"`), demonstrating state change on a stack that never authenticated the request, and further assert `ContinuousDeliveryJob` is enqueued for the newly-synced commit given `continuous_deployment: true`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
