### Title
API client scoped to a single stack can read the CI/deploy status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single `Stack` (`belongs_to :stack, optional: true`), and this scope is meant to be the boundary enforced by `Api::BaseController#stacks`/`#stack`. `Api::Ccmenu::CCMenuController` bypasses that boundary by redefining `#stack` to resolve directly from the URL parameter instead of from the client-scoped `stacks` relation, so a token authorized only for stack A can be used to read the state of any stack B.

### Finding Description
`Api::BaseController` establishes the authorization boundary between an `ApiClient` and the stacks it may touch: [1](#0-0) 

`current_api_client.stack_id?` is true when the `ApiClient` was created scoped to one particular `Stack` (see fixture `here_come_the_walrus`, which is scoped to `stack: shipit` and has only the `read:stack` permission): [2](#0-1) 

Every other stack-scoped API controller (`CommitsController`, `StacksController`, `TasksController`, `MergeRequestsController`, `OutputsController`) resolves the target stack through this inherited, scope-checked `#stack`/`#stacks` method — e.g. `StacksController` only overrides `#stack` to look up by `params[:id]` but still starts from the scoped `stacks` relation: [3](#0-2) 

`Api::CCMenuController`, however, defines its own `#stack` that resolves directly against `Stack.from_param!(params[:stack_id])`, completely independent of `current_api_client.stack_id`: [4](#0-3) 

It still only requires the generic `read:stack` permission (not a per-stack check): [5](#0-4) 

The binding that should hold is: **stack a token authorizes == stack a token touches**. Before an attacker's request: a token scoped to stack A can only read/act on stack A through every API endpoint. After hitting `/api/stacks/*stack_id/ccmenu`: the same token can read the CI status of any stack B, because `CCMenuController#stack` never consults `current_api_client.stack_id`. This is exactly the analog of the referenced Ajna bug: a value (`params[:stack_id]`) that should be constrained by an already-authorized/verified scope (`current_api_client.stack_id`) is instead used unconditionally, silently widening what a narrowly-scoped credential can touch.

### Impact Explanation
This is an authorization-scope escalation: a holder of a low-privilege, single-stack `read:stack` token can enumerate/observe the deploy/build state (`lastBuildStatus`, `activity`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) of every stack in the Shipit instance, not just the one it was provisioned for. This falls in the "escalation into authorization... unauthenticated read of stack state" category, since the token was never authorized to read state for stacks outside its scope.

### Likelihood Explanation
Any environment that creates per-stack scoped `ApiClient`s (the codebase explicitly supports and tests this via `stack_id?` in `BaseController#stacks`, and ships a fixture demonstrating a stack-scoped, `read:stack`-only client) is affected. Exploitation only requires changing the `stack_id` path segment on a request that already carries a legitimately-scoped token — no additional privilege, session, or secret is needed beyond the token itself, and the token's own permission model does not gate this.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the inherited, scope-enforcing `stacks`/`stack` methods from `Api::BaseController` (i.e., remove the local override and rely on `stacks.from_param!(params[:stack_id])`), so the per-client `stack_id` scoping is applied consistently across every API controller, not just most of them.

### Proof of Concept
1. Create (e.g., via Rails console/seed, as supported by the model) an `ApiClient` scoped to `stack_a` with permission `read:stack` only, and obtain its `authentication_token`.
2. As the holder of that token (no other privilege), issue: `GET /api/stacks/<stack_b_owner>/<stack_b_repo>/<stack_b_env>/ccmenu?token=<token>` where `stack_b` is a different, unrelated stack.
3. Observe the response returns `200 OK` with `stack_b`'s CI/deploy XML (name, activity, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl), even though the token is scoped only to `stack_a`. Compare with the same token hitting `/api/stacks/<stack_a_...>/commits` or `/api/stacks/<stack_b_...>/commits`, which correctly return `403 Forbidden`/empty results for `stack_b` because those controllers use the inherited, scope-checked `#stack`.
