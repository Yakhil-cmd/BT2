### Title
Unsanitized PR labels become process environment variables reaching `PTY.spawn` - (File: app/models/shipit/review_stack.rb)

### Summary
`ReviewStack#env` converts every GitHub PR label into an environment variable (`LABEL_NAME.upcase => "true"`) with no allow-list, and `Command#unbundled_env` merges the caller-supplied `@env` last, overriding `BASE_ENV`/`PATH`. A PR author who can attach a label such as `ld_preload` to their own review-stack PR gets `LD_PRELOAD=true` injected into every subsequent deploy/rollback command executed via `PTY.spawn` on the shared deploy host.

### Finding Description
Broken binding: the set of keys accepted by `Command#unbundled_env` is claimed to equal `deploy_spec.machine_env` / `VariableDefinition::name` keys, i.e. `keys(Command#unbundled_env's @env) == keys(deploy_spec.machine_env)`. This is false.

Trace:
1. `LabelCapturingHandler#capture_labels` persists arbitrary label strings from the webhook payload onto `PullRequest#labels` with no validation against a known set: `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`.
2. `ReviewStack#env` unconditionally folds every label into the env hash: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` (`app/models/shipit/review_stack.rb:84-93`). There is no allow-list check against `deploy_spec.machine_env`/`VariableDefinition::name`.
3. `TaskCommands#env` merges `@stack.env` (`lib/shipit/task_commands.rb:35`) before its own fixed keys and `deploy_spec.machine_env`/`@task.env` (`lib/shipit/task_commands.rb:46-47`); since `deploy_spec.machine_env` normally does not define an `LD_PRELOAD` key, the label-derived value survives untouched to the final hash.
4. That hash becomes `Command`'s `@env` (`lib/shipit/command.rb:34`), and `unbundled_env` merges `@env.stringify_keys` last: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` (`lib/shipit/command.rb:103-105`), so it takes precedence over the trusted `BASE_ENV`.
5. `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` (`lib/shipit/command.rb:92`), so `LD_PRELOAD=true` is present in the environment of every process invoked for that task's remaining steps (checkout, dependency installation, deploy steps, etc.).

Existing guards do not stop this: `labeled_active_stack?` only checks the stack is present and not archived (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:62-64`); there's no `EnvironmentVariables#permit`-style filtering applied to `ReviewStack#env`'s label-derived keys (that filtering, `filter_task_envs`/`filter_deploy_envs`, only applies to explicitly user-submitted task/deploy `env:` params on `Stack#trigger_task`/`build_deploy`, not to `ReviewStack#env`). No signature or authentication check is relevant here — the label data itself is the injected payload, not a forged webhook. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

### Impact Explanation
Once a task (deploy/rollback/other step) runs for this review stack, every command run via `Command#start`/`PTY.spawn` inherits `LD_PRELOAD=true`. On its own this only forces the dynamic loader to attempt loading a shared object literally named `true`, which normally just fails to resolve and is often silently ignored or causes command failure — not automatically full RCE. However, combined with any other label-controlled variable that affects loader search paths (e.g. a label yielding a path-like value merged similarly), or if `machine_env`/deploy scripts consult these injected variables, this constitutes unauthorized environment control over commands executed on the shared deploy host for that stack, which is a real integrity violation of the deploy execution environment. This affects only the specific review stack (scoped to that repository/PR), not cross-tenant, since `ReviewStack#env` is instance-scoped to `pull_request.labels` of that stack's PR.

### Likelihood Explanation
Preconditions: a review stack must exist for the PR and not be archived (`labeled_active_stack?`), and the actor must be able to attach a label to the PR. On GitHub, adding a label to a PR normally requires `triage`/`write` collaborator permission on the repository, not merely being the PR's author — an unprivileged outside contributor typically cannot self-label a PR unless the repository has been configured to allow it. This is a meaningful precondition gap versus the stated "any unprivileged PR author" threat model, and could not be verified from the engine code alone (label ACL enforcement is entirely on GitHub's side, outside this repo). Assuming an attacker with label-adding rights on a review-stack-enabled repository, the attack is cheap and repeatable (add/remove labels freely, one webhook per relabel).

### Recommendation
In `ReviewStack#env`, do not blindly upcase and inject every PR label as an environment variable. Restrict label-derived env vars to a repo/deploy-spec-defined allow-list (e.g. only labels matching `deploy_spec.review_variables`/`VariableDefinition` names), and reject or ignore any label name colliding with reserved/sensitive variable names (`LD_PRELOAD`, `BUNDLE_PATH`, `PATH`, `LD_LIBRARY_PATH`, etc.). Alternatively, route label-derived values through the same `filter_task_envs`/`EnvironmentVariables#permit` mechanism already used for explicit task/deploy `env:` parameters.

### Proof of Concept
Add to `test/models/shipit/review_stack_test.rb` (or a new task_commands test):
1. Build a `ReviewStack` with an associated `PullRequest` whose `labels` include `"ld_preload"`.
2. Build a `Deploy`/`Task` for that stack and instantiate `Shipit::TaskCommands.new(task)`.
3. Build a `Shipit::Command.new("true", env: task_commands.env, chdir: ...)`.
4. Assert `command.unbundled_env.key?("LD_PRELOAD")` is `true` even though `deploy_spec.machine_env` does not define `LD_PRELOAD` — demonstrating the binding `keys(Command#unbundled_env's env) == keys(deploy_spec.machine_env)` is violated:
```ruby
assert_not_includes stack.cached_deploy_spec.machine_env.keys, "LD_PRELOAD"
assert_equal "true", command.unbundled_env["LD_PRELOAD"]
```
