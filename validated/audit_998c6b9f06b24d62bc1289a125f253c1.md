### Title
`PYTHONPATH` env-hijack via uppercased pull-request label reaches `pip install -r requirements.txt` subprocess - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) as an environment variable with value `"true"` and no allowlist, and `TaskCommands#env` merges that stack env unfiltered into the environment used for `install_dependencies`/`perform`, which is then passed straight to `Command#unbundled_env` and `PTY.spawn`. Because label names are attacker-controlled (via `LabelCapturingHandler#capture_labels`, sourced directly from the webhook `pull_request.labels`), a fork PR author can create a label named `pythonpath` to inject `PYTHONPATH=true` into the spawned `pip install -r requirements.txt` process's environment.

### Finding Description
The broken binding claimed is: `Command#unbundled_env["PYTHONPATH"]` should equal `nil`/absent for any subprocess spawned from a `ReviewStack` task, but instead `Command#unbundled_env["PYTHONPATH"]` can equal `"true"` when the PR has a label named `pythonpath`.

Trace:
1. `LabelCapturingHandler#capture_labels` persists `params.pull_request.labels.map(&:name)` verbatim from the webhook payload onto `pull_request.labels` [1](#0-0) . This handler is reachable by any PR author who can label their own PR/fork — labeling their own PR is an action available to the PR author (no maintainer permission required to add labels to their own PR in many repo configs, and the webhook itself just reports the current label state); the params schema only requires basic structural fields (`String` types) with no content allowlist [2](#0-1) .
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` into the stack's env hash with no key allowlist [3](#0-2) . This is directly confirmed by the test asserting labels become uppercased env keys with value `"true"` [4](#0-3) .
3. `TaskCommands#env` merges `@stack.env` (which includes the label-derived env for `ReviewStack`) with no filtering before adding fixed keys like `SHIPIT_USER`, `EMAIL`, etc. [5](#0-4) .
4. `TaskCommands#install_dependencies` builds `Command.new(command_line, env:, chdir: steps_directory)` for each dependency-installation step (e.g., `pip install -r requirements.txt`), passing the merged, unfiltered env [6](#0-5) .
5. `Command#unbundled_env` merges `@env.stringify_keys` on top of `BASE_ENV`/`PATH`, with no key denylist/allowlist, and `Command#start` passes this directly to `PTY.spawn` [7](#0-6) .

Existing guard `EnvironmentVariables#permit` exists in the codebase and enforces an explicit allowlist (`sanitize_env_vars` raises `NotPermitted` for any key not in `variable_definitions`) [8](#0-7) , but this permit/allowlist mechanism is **not applied** to the `env` hash built by `TaskCommands#env` / `ReviewStack#env` before it reaches `Command.new`/`unbundled_env`/`PTY.spawn`. It is only used for `interpolate` (shell variable substitution inside command strings), not for gating which env keys are passed to the spawned process. No other guard (`verify_signature`, `require_permission!`, model validations) restricts label *names*, since `PullRequest#labels` has no format validator preventing values like `pythonpath`.

Because `PYTHONPATH` (once uppercased and matched case-insensitively by Python's interpreter, which reads `PYTHONPATH` exactly) is attacker-settable, and the deploy spec step is literally `pip install -r requirements.txt` (or any Python-invoking step) executed with this hijacked environment, an attacker-controlled module search path can be prepended, causing subsequent python code execution to import attacker-supplied modules — RCE on the deploy host.

### Impact Explanation
An unprivileged fork PR author who can label their own PR triggers a webhook that flows through `LabelCapturingHandler` to persist the label, then any subsequent review-stack task/deploy run (`TaskCommands#install_dependencies`/`perform`) executes with `PYTHONPATH` set from that label. If a Python-based step (e.g., `pip install -r requirements.txt`, or any script invoked via `python`) runs during that deploy, the attacker's module path is honored, allowing arbitrary code execution on the Shipit deploy host under whatever privileges the deploy user has. This is scoped to the specific repository's ReviewStack (blast radius limited to repositories that have review stacks enabled and Python-based deploy specs), but it is repeatable for every PR/label change and does not require any Shipit credentials — matching the Critical RCE-on-deploy-host category.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a deploy spec containing a Python/pip-based dependency-install or deploy step, since that is the vulnerable trigger; the attacker must be able to open a PR and add a label named `pythonpath` (case-insensitive, since `.upcase` is applied) to that PR. No Shipit secrets, session, or API token are required — merely a GitHub account able to open a PR against the target repo and apply a label (which is often permitted for the PR author or is auto-applied by bots/CI on many repos). This is low-cost and fully repeatable.

### Recommendation
Apply an explicit allowlist (reusing or mirroring `EnvironmentVariables#permit`) to the label-derived environment variables in `ReviewStack#env` before merging, rejecting or dropping any key matching dangerous/reserved interpreter and loader variables (`PYTHONPATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `NODE_OPTIONS`, `PATH`, etc.), or namespace label-derived variables under a fixed prefix (e.g., `LABEL_<NAME>`) so they can never collide with interpreter-sensitive variable names.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test)
test "#install_dependencies env does not leak attacker-controlled PYTHONPATH from PR labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["pythonpath"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  # Broken binding demonstrated: label becomes PYTHONPATH=true
  assert_equal "true", env["PYTHONPATH"]

  command = Shipit::Command.new("pip install -r requirements.txt", env:, chdir: ".")
  # Invariant violated: unbundled_env carries PYTHONPATH into the spawned process
  assert_equal "true", command.unbundled_env["PYTHONPATH"]
end
```
This demonstrates the equality `Command#unbundled_env["PYTHONPATH"]` (expected `nil`) actually equals `"true"`, confirming the label-name-to-env-key injection path from `ReviewStack#env` through `TaskCommands#env` into `Command#unbundled_env`.

    def permit(variable_definitions)
      return {} unless @env
      raise "A whitelist is required to sanitize environment variables" unless variable_definitions

      sanitize_env_vars(variable_definitions)
    end

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    private

    def initialize(env)
      @env = env
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
