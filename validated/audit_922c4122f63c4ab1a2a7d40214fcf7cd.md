### Title
Webhook signature is verified against the org derived from the payload, but stack/repository resolution trusts a different, unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App deployment of Shipit (one `webhook_secret` per organization, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to HMAC-verify against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Handlers, however, resolve the target `Repository`/`Stack` using a *different* field, `payload.dig('repository', 'full_name')`, via `Handler#repository_name` and `Repository.from_github_repo_name`. Nothing ties these two fields together: `verify_signature` never checks that `repository.full_name`'s owner segment equals `repository.owner.login`/`organization.login` used for verification.

### Finding Description
The webhook flow is:

1. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-30):
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
`repository_owner` (line 61) reads `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`.

2. Once the signature check passes, `create` dispatches the raw parsed JSON to handlers (`app/controllers/shipit/webhooks_controller.rb` lines 10-15):
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```

3. Handlers (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`) resolve the target repository/stack via `Handler#stacks`/`#repository_name` in `app/models/shipit/webhooks/handlers/handler.rb` (lines 32-38):
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
and `Repository.from_github_repo_name` (`app/models/shipit/repository.rb` lines 53-56) splits `full_name` on `/` to get `owner`/`name` and looks up the `Repository` by those values — completely independent of `repository.owner.login`/`organization.login`.

Because the HMAC signature covers the entire raw body, forging a valid signature still requires knowledge of the correct `webhook_secret` for whichever organization is picked by `repository_owner`. However, the binding the ERC4626 analog calls out — "an organization that authenticated versus the repository that is written" — is broken here: the field used to *select the trust boundary* (`repository.owner.login` / `organization.login`, which decides *whose secret* must sign the payload) is not the same field used to decide *which repository/stack is acted upon* (`repository.full_name`). Nothing in `verify_signature` enforces `repository.full_name.start_with?("#{repository_owner}/")`.

In a multi-org install where two organizations, `OrgA` and `OrgB`, are both configured with independent `webhook_secret`s under `secrets.github.OrgA` / `secrets.github.OrgB` (this is a documented, in-scope configuration — see `docs/setup.md` "Use this configuration schema if you are configuring multiple Github applications" and `test/dummy/config/secrets_double_github_app.yml`), any party capable of producing a validly-signed webhook body for `OrgA` (e.g. GitHub itself delivering an `OrgA` webhook, or anyone who legitimately controls an `OrgA`-installed repository and can trigger arbitrary webhook payload construction through GitHub's own webhook redelivery/test mechanisms, or any other verified `OrgA` sender) can set `repository.full_name` to `OrgB/some-other-repo` while keeping `repository.owner.login`/`organization.login` equal to `OrgA` (or vice-versa in the `organization` fallback path for `membership` events). The signature check passes because it is validated using `OrgA`'s secret over the tampered body content, but the handler then acts against a `Stack` that belongs to `OrgB`, whose webhook secret was never used and whose consent was never obtained.

Concretely this affects:
- `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) — triggers `stack.sync_github(expected_head_sha:)` for a stack under `OrgB` from a payload only signed by `OrgA`'s secret.
- `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler` — same class of issue, all keyed off `repository_name`/`full_name` or `organization.login` independent of what `verify_signature` checked.

### Impact Explanation
This crosses the "unauthenticated read of stack state" / cross-org write boundary called out in scope: an entity that is only authenticated as an `OrgA` webhook sender can cause Shipit to enqueue `GithubSyncJob`, update commit statuses, or otherwise mutate state for a `Stack` belonging to a completely different organization (`OrgB`) that never authorized or signed that action. This is a High-severity escalation: it lets a webhook sender for one tenant/org act on another tenant's stack state without ever possessing that tenant's `webhook_secret`, breaking the intended per-organization isolation that the multi-app config (`docs/setup.md`, `secrets_double_github_app.yml`) is designed to provide.

### Likelihood Explanation
This requires Shipit to be configured with the multi-organization GitHub App schema (more than one org key under `secrets.github`), which is an explicitly documented and supported configuration, not a misconfiguration outside scope. Any actor able to produce a validly-signed webhook for one configured org (which in practice is GitHub's own webhook delivery infrastructure for that org, but the check is purely mechanical string/field based and never cryptographically binds `repository.full_name` to the verified organization) can exploit this. The likelihood is moderate: it needs a multi-org deployment and control of/insight into one org's outbound webhook content, but no privileged Shipit credentials, `ApiClient` token, or GitHub App private key are needed — exactly the class of unprivileged-attacker analog specified in scope.

### Recommendation
In `WebhooksController#verify_signature`, after determining `repository_owner` for choosing the correct `webhook_secret`, also assert that `repository.full_name`'s owner segment (and/or `organization.login`) is consistent with `repository_owner` before dispatching to handlers, e.g. reject the webhook (422) if `payload.dig('repository', 'full_name')&.split('/')&.first&.downcase != repository_owner&.downcase`. More robustly, `Handler#repository_name`/`Repository.from_github_repo_name` should be passed the already-verified `repository_owner` explicitly (rather than re-deriving repository ownership from the same untrusted JSON body a second time), so the value used for authentication and the value used for authorization/action are provably the same field.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (per `docs/setup.md` multi-org schema / `test/dummy/config/secrets_double_github_app.yml`), and a `Stack` for repository `OrgB/target-repo`.
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` using `OrgA`'s webhook secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and successfully verifies the signature against `OrgA`'s secret.
6. `PushHandler#process` resolves `repository_name == "OrgB/target-repo"` via `payload.dig('repository', 'full_name')`, finds the `OrgB/target-repo` `Repository`/`Stack`, and enqueues `stack.sync_github(expected_head_sha: 'deadbeef')` — a write performed on `OrgB`'s stack despite the request being authenticated solely with `OrgA`'s webhook secret.
