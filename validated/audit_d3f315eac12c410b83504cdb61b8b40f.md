### Title
AA-generated payments to `spender_attested`/`transfer_condition`-gated assets cause the entire trigger response (including state updates) to bounce and be discarded if the recipient fails the check — ([File: aa_composer.js])

### Summary
The Sherlock finding describes a pattern where a single atomic operation both performs a critical state transition (canceling a stream) and sends tokens to a recipient; if the token transfer to that recipient is blocked (USDC blacklist), the whole transaction reverts, and the state transition never happens, permanently freezing funds and blocking the payer's ability to cancel.

The analogous pattern in `ocore` exists in the Autonomous Agent (AA) trigger-handling flow. When an AA sends a payment message as part of its response, the resulting unit — which also carries any state variable updates (`objStateUpdate`) that the AA logic computed — must pass through full protocol validation (`validation.js`) before being saved. If the payment is denominated in an asset that is `spender_attested` or has a `transfer_condition`, and the intended recipient becomes unattested or otherwise fails that condition, unit validation fails and the whole AA response is discarded via `bounce()`, wiping out the state changes.

### Finding Description
When an AA processes a trigger and decides to send an asset payment, `sendUnit()` builds the response unit and calls `validateAndSaveUnit`; if validation returns an error, the whole response is thrown away via `bounce(err)`: [1](#0-0) 

`bounce()` explicitly discards the computed state update (`objStateUpdate = null`) and, outside of `bAir`/dry-run mode, restores `stateVars`/balances to their pre-trigger values, meaning any legitimate state transition the AA was going to perform (e.g. marking an obligation as paid/canceled) is lost: [2](#0-1) 

The validation step that can reject the generated payment unit — and thus trigger this bounce — is the standard asset payment check in `validatePaymentInputsAndOutputs`, which enforces both the `spender_attested` attestation list and any `transfer_condition`/`issue_condition` on the output addresses: [3](#0-2) 

For `spender_attested` assets, the set of attested addresses is dynamic: attestors publish attestation lists via `asset_attestors` messages, and the list of currently-attested addresses is looked up at validation time (`storage.filterAttestedAddresses`). If the AA's intended output address was attested when the AA's fund-holding logic began but the attestor later revokes/changes attestation, subsequent AA-issued payments to that same address will fail the `"some output addresses are not attested"` check. Likewise, an evaluated `transfer_condition` (an address-definition-style spending condition attached to the asset) can reference conditions tied to the recipient's identity/definition, which the recipient or an attestor effectively controls and can change to permanently fail: [4](#0-3) 

Because the AA's payment message and its state-changing logic are compiled into one atomic response unit, a party who can influence the attestation/transfer-condition outcome for the payout address (the “blacklist” analog) can force every future trigger that needs to pay that address to bounce indefinitely, discarding the state update each time.

### Impact Explanation
Any AA that is designed to release funds of a `spender_attested` or `transfer_condition`-restricted asset to a specific counterparty as part of finalizing a state change (e.g., closing a deal, canceling a subscription/vesting-like schedule, releasing escrow) can become permanently unable to complete that state change if the recipient's attestation is revoked or the transfer condition evaluates to false for that recipient. This is a fund-freezing/state-inconsistency issue: the AA's balance keeps the asset locked, the intended cancellation/finalization never records, and every retry simply burns the bounce fee while reverting state, mirroring the "payer cannot cancel and recover funds" impact of the original finding.

### Likelihood Explanation
This requires the asset in question to have `spender_attested: true` or a non-trivial `transfer_condition`, and requires whoever controls the attestor list (or whichever party the transfer condition depends on) to un-attest/revoke the specific output address. For attested assets used in AA-based financial logic (subscriptions, streaming payments, KYC-gated assets), this is a realistic scenario since attestor lists are explicitly designed to be updatable at any time via `asset_attestors` messages, and this is a normal, permitted on-chain action, not a malicious protocol violation.

### Recommendation
Avoid bundling a mandatory payout to a potentially-restricted asset address with the AA's core state transition in the same atomic response. Where an AA must both update its important state (e.g. record an obligation as settled) and pay out a `spender_attested`/`transfer_condition` asset, decouple these: perform the state update unconditionally in the primary response, and route the actual asset payout through a claimable balance/withdrawal pattern (e.g., record how much the recipient is owed in a state variable and let a separate trigger pay it out later, after re-checking attestation), rather than making the finalized state change depend on the payment succeeding within the same unit.

### Proof of Concept
1. Define an asset A with `spender_attested: true` and an attestor address `ATT`.
2. Deploy an AA `S` designed to hold/stream asset A to some recipient `R`, whose logic (like a vesting/cancel function) both (a) finalizes internal state (e.g., zeroes out `remainingBalance`) and (b) sends the vested amount of asset A to `R` in the same response payment message, per the asset-payment message rules validated in `validatePaymentInputsAndOutputs`: [5](#0-4) .
3. `ATT` initially attests `R`, allowing normal streaming payments to succeed.
4. Once a state-finalizing trigger (e.g., a "cancel" trigger) needs to fire, `ATT` publishes an `asset_attestors` update that removes `R` from the attested list before the trigger unit's `last_ball_mci`.
5. The payer/recipient sends the cancel trigger. `sendUnit()` builds the response unit including both the state update and the payment to `R`; `validateAndSaveUnit` fails with `"some output addresses are not attested"` from `validatePaymentInputsAndOutputs`, and `bounce(err)` discards `objStateUpdate`, per [2](#0-1) .
6. Every subsequent retry of the cancel trigger bounces the same way as long as `R` remains unattested, leaving the AA's held funds and cancellation state permanently stuck — the analog of the payer being unable to `cancel()` because the recipient is blacklisted.
