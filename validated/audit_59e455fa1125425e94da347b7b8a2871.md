### Title
Cross-tenant `Team` mutation via attacker-controlled `team.id`/`organization.login` in `membership` webhook - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler` trusts the GitHub-supplied `team.id` and `organization.login` fields to locate or create a `Team` row, looking it up only by the global `github_id` column with no check that the team's `organization` matches the organization whose secret validated the webhook signature. An attacker who owns any GitHub organization onboarded into Shipit's multi-tenant `github` config can send a correctly-signed `membership` payload for their own org but with a `team.id` that collides with a `Team` belonging to a different tenant, causing that other tenant's team membership to be mutated.

### Finding Description
The claimed binding is: `Shipit#github(organization: repository_owner)` selecting per-org `webhook_secret`/`GitHubApp` (tenant boundary asserted) == the tenant boundary enforced on which `Team` row a webhook may mutate (tenant boundary enforced). Tracing the code shows this equality does not hold.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) picks the `GitHubApp` via `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . For a `membership` event there is no `repository` key, so `repository_owner` resolves to the attacker-supplied `organization.login` field itself [2](#0-1) . This value both selects which tenant's `webhook_secret` verifies the HMAC signature, and is later stored as `team.organization` if the team doesn't yet exist. It is *not* used to constrain which existing team may be mutated.

`MembershipHandler#find_or_create_team!` does:
```
Team.find_or_create_by!(github_id: params.team.id) do |team| ... end
``` [3](#0-2) 
This lookup is keyed solely on the global `github_id` column, with no `where(organization: repository_owner)` scoping. `params.team.id` is fully attacker-controlled (an `Integer` from the JSON body) and is never validated to belong to the organization that produced a valid signature. If a `Team` row already exists for tenant B with `github_id = X` (learned e.g. by observing tenant B's team page, or simply guessed/brute-forced since GitHub team IDs are small sequential integers), an attacker who legitimately owns tenant A can:

1. Create their own throwaway GitHub org (tenant A) and install a GitHub App there, with Shipit operator configuring it under `Shipit.github` (multi-tenant `github:` config keyed by org name, `Shipit#github_app_config` / `TOP_LEVEL_GH_KEYS`) [4](#0-3) .
2. Send `POST /webhooks` with header `X-Github-Event: membership`, signed with tenant A's real `webhook_secret` (attacker owns tenant A and can trigger a genuine `membership` event, or forge one and self-sign because they hold their own webhook secret — either way this is a legitimately signed delivery from *their* app).
3. Set `organization.login` = tenant A's org (so `verify_signature` picks tenant A's secret and the signature checks out), but set `team.id` = tenant B's `github_id` for an already-existing `Team` row.
4. `MembershipHandler#process` finds tenant B's `Team` by that `github_id`, and calls `team.add_member(member)` or `team.members.delete(member)` [5](#0-4) , adding/removing an arbitrary GitHub login (which Shipit will `find_or_create_by_login!`) from tenant B's team.

None of the existing guards stop this: `verify_signature` only proves the request was signed by *some* onboarded org's secret, not that the org matches the team being touched; the `ExplicitParameters` schema (`params do ... end` block) only type-checks fields, it enforces no cross-field relationship between `organization.login` and `team.id`'s ownership [6](#0-5) ; `drop_unhandled_event` and `force_github_authentication` are irrelevant to this flow.

### Impact Explanation
This crosses the tenant boundary explicitly claimed by `Shipit.github(organization:)`: a payload signed for organization A mutates a `Team` belonging to organization B. `Team.members` gates `User#authorized?` (`Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [7](#0-6) , which is Shipit's global login-authorization gate when `Shipit.github_teams` is configured. If tenant B's team is one of the configured `Shipit.github_teams`, the attacker can add an arbitrary GitHub login as a "member" of that team, which — once that login authenticates via OAuth — grants that user full Shipit login authorization (`User#authorized?` returns true), i.e. escalation into `Shipit.github_teams` authorization across tenants. This matches the "escalation into `Shipit.github_teams` authorization" High severity category. It is repeatable against any `Team` row whose `github_id` the attacker can enumerate or guess, and the write does not require any secret beyond the attacker's own tenant's webhook secret.

### Likelihood Explanation
Preconditions: the Shipit deployment must be configured for multi-tenant GitHub Apps (`github:` config keyed by multiple organizations) as documented in `docs/setup.md`'s "Using Multiple GitHub Applications" section, and the attacker must own/control at least one onboarded GitHub organization with a registered GitHub App (satisfying "a repository/org they own"). The attacker needs to know or guess a target `Team`'s `github_id` (GitHub team IDs are sequential integers and are often discoverable via the GitHub API/UI for any team the attacker can view, or brute-forceable). No Shipit session, API token, or cross-tenant secret is required — only the attacker's own legitimately provisioned webhook secret. This is a low-cost, repeatable attack once org onboarding exists.

### Recommendation
Scope the `Team` lookup/creation in `MembershipHandler#find_or_create_team!` by both `github_id` and the verified `organization` (i.e., `repository_owner`/`params.organization.login` as authenticated by signature), and reject/no-op if an existing `Team` with that `github_id` belongs to a different organization than the one whose secret verified the signature.

### Proof of Concept
Minitest plan (functional/controller test, no live GitHub):
1. Fixtures: two `GithubHook::Organization` entries (or equivalent multi-tenant `github` config) for `org_a` and `org_b`, each with distinct `webhook_secret`; a `Team` fixture `team_b` with `organization: 'org_b'`, `github_id: 999`.
2. Compute a valid `X-Hub-Signature` for a `membership` payload using `org_a`'s `webhook_secret`, with body: `{ action: 'added', team: { id: 999, name: 'Team B', slug: 'team-b', url: '...' }, organization: { login: 'org_a' }, member: { login: 'attacker_controlled_user' } }`.
3. POST to `/webhooks` with that signature and `X-Github-Event: membership`.
4. Assert response is `:ok` (200), proving signature verification passed using `org_a`'s secret.
5. Assert `Shipit::Team.find_by(github_id: 999).organization == 'org_b'` still (team wasn't reassigned) but `team_b.members.map(&:login)` now includes `'attacker_controlled_user'` — demonstrating a payload signed for `org_a` mutated `org_b`'s team, crossing the tenant boundary asserted by `Shipit.github(organization:)`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
