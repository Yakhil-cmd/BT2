### Title
Ambiguous non-greedy `a/(.+?) b/(.+)` header regex lets a crafted filename corrupt `file_path` resolution, breaking the identity binding between displayed path and reviewed hunk content - (File: `plugins/security-guidance/hooks/gitutil.py`)

### Summary
`extract_file_paths_from_diff` and `parse_diff_into_files` both derive `file_path` from the same brittle regex `^a/(.+?) b/(.+)$` applied to the `diff --git a/... b/...` header line [1](#0-0) [2](#0-1) . Because group 1 is lazy and group 2 is greedy, a real file whose path contains an embedded `" b/"` substring (a space followed by `b/`) causes the regex to split at the first occurrence rather than the true a/b boundary, producing a corrupted `file_path` that no longer matches the actual tracked git path.

### Finding Description
Both functions split the diff on `"diff --git "` and match the first line of each chunk against `^a/(.+?) b/(.+)$` [3](#0-2) . For an ordinary (non-renamed) file, git emits `a/<path> b/<path>`, i.e., the same literal path twice. If `<path>` itself contains a `" b/"` sequence (e.g. a file literally named `notes b/decoy.py`), the header line becomes:
```
a/notes b/decoy.py b/notes b/decoy.py
```
The lazy `.+?` for group 1 stops at the *first* `" b/"` it can match, so `group(1)` resolves to `notes` and the greedy `group(2)` swallows the remainder of the line: `decoy.py b/notes b/decoy.py`. This is neither the true tracked path nor a clean impersonation — it is a corrupted string that no longer represents the real git path (`notes b/decoy.py`). The same corrupted value is used identically by `_is_reviewable_source(file_path)` in both `extract_file_paths_from_diff` [4](#0-3)  and `parse_diff_into_files` [5](#0-4) , and the hunk content that follows is still attached to whatever corrupted string was computed [6](#0-5) .

Because the corrupted string retains the attacker-chosen filename as a substring (e.g. it still contains `decoy.py`), and its trailing extension (`.py`) still drives the `_is_reviewable_source` extension check [7](#0-6) , an attacker can manipulate whether a given hunk is included/excluded from the review filter, or cause the label shown alongside reviewed content to differ from the true git path. No existing check verifies `file_path` against `--- a/` / `+++ b/` lines or against an authoritative `git diff --name-only -z` listing, so nothing in the code catches or corrects this corruption.

### Impact Explanation
This is a path-parsing correctness bug, not a clean "swap the label for an innocent one" spoof: the resulting `file_path` is a visibly malformed string containing duplicated fragments, so a careful reviewer would likely notice something is off. The exploitable consequence is narrower than a perfect content-disclosure/consent bypass: it is a filter-evasion / attribution-corruption bug — a crafted filename can shift which extension/basename the `_is_reviewable_source` gate evaluates, potentially causing hunks from a legitimately sensitive file to be silently dropped from review (bypassing the security-guidance scan) or mis-attributed under a corrupted path string in whatever review UI/log consumes this output.

### Likelihood Explanation
Exploitation requires the attacker to control a file whose literal path contains a space immediately followed by `b/` (e.g. `notes b/decoy.py`), and for that file's diff to be processed by `extract_file_paths_from_diff`/`parse_diff_into_files`. This is an unusual but git-legal filename that an unprivileged contributor can create in their own branch/PR. It is also uncertain whether git's own diff-header generation would quote such an ambiguous path in some configurations (in which case the line would fail to match `^a/` entirely and the file would simply be dropped from review rather than mislabeled) — this reduces confidence in the precise exploit shape but does not eliminate the underlying parsing defect.

### Recommendation
Do not parse file paths from the freeform `diff --git a/... b/...` header text. Instead, derive `file_path` from the unambiguous `--- a/<path>` / `+++ b/<path>` lines (or better, drive the whole extraction from `git diff --name-only -z` / `git diff --raw -z`, which are NUL-delimited and unambiguous), and cross-validate that the header-derived path matches. Reject or safely handle diff chunks where the header cannot be unambiguously parsed instead of silently accepting a best-effort greedy/lazy regex split.

### Proof of Concept
Add a fuzz/invariant test in the test suite for `gitutil.py`:
1. Create a temp git repo, add a file literally named `notes b/decoy.py` with recognizable content, commit, modify it, and generate `diff_output = subprocess.check_output(["git","diff"])`.
2. Independently compute ground truth via `git diff --name-only -z`.
3. Call `extract_file_paths_from_diff(diff_output)` and `parse_diff_into_files(diff_output)`.
4. Assert `file_path == "notes b/decoy.py"` for both functions and that it matches the ground-truth `--name-only -z` output.
5. Expect failure: the returned `file_path` will be `"decoy.py b/notes b/decoy.py"` (or similar), demonstrating the header regex does not correctly recover the true git path.
