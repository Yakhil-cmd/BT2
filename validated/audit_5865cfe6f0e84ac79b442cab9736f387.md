### Title
`EnvironmentVariables#interpolate` falls back to the Shipit host process `ENV` for any `$VAR` name found in an attacker-controlled shipit.yml step - (File: `lib/shipit/environment_variables.rb`)

### Summary
`EnvironmentVariables#interpolate` substitutes `$VAR` tokens found in a command line using `@env.fetch(variable) { ENV[variable] }`, so any variable name that is not part of the task's approved environment silently falls back to the Shipit Rails process's own `ENV`. Because `deploy`/`review.checks`/task steps are read verbatim from the repository's (or, for review stacks, the PR branch's) `shipit.yml`, an unprivileged PR author can name any variable and have Shipit's host-process environment value spliced literally into the executed command, independent of the deliberately filtered child-process environment.

### Finding Description
Broken binding: the value substituted for `$VAR` in a step SHOULD equal `stack/task approved env[VAR]` (i.e., a value the repository/task explicitly declared via `deploy.variables`/`tasks[].variables`/`@stack.env`), but instead `interpolate` allows `substituted[VAR] == Shipit_process.ENV[VAR]` whenever `VAR` is absent from the task's `@env`: [1](#0-0) 

This is invoked from `Command#interpolate_environment_variables` / `Command#interpolated_arguments`, which builds the exact literal shell arguments passed to `PTY.spawn`: [2](#0-1) [3](#0-2) 

Crucially, the child process's *actual* environment is deliberately narrowed: `unbundled_env` merges `BASE_ENV` (which nils out any host `ENV` key not present in Bundler's clean/unbundled env) with the task's own `@env`: [4](#0-3) [5](#0-4) 

That filtering is bypassed entirely by `interpolate`, because it reads `ENV[variable]` directly in the *host Ruby process* before spawning, and bakes the value into the literal argument string (which is then executed and, if the step echoes/logs the variable, appears in the task's streamed output).

The behavior is intentional/tested (`test/unit/command_test.rb:29-36`, "fallback to ENV"), but its security consequence is not bounded by any whitelist: `EnvironmentVariables#permit` (which enforces an allowed-variable whitelist) is a separate code path used only for validating user-submitted deploy/task variables, and is never invoked by `interpolate`.

Attack path: an attacker opens a PR against a repository with `review_stacks_enabled` (e.g., `provisioning_behavior_allow_all?`), whose `shipit.yml` on their own PR branch is used to build `deploy_steps`/`review.checks` for the resulting `ReviewStack` (`ReviewStackAdapter#create!`, branch = `pull_request.head.ref`): [6](#0-5) [7](#0-6) 

The attacker adds a step such as `echo $SOME_GUESSED_HOST_SECRET_VAR`. If that name is set in the Shipit host process's `ENV` (e.g., a Rails config secret, DB credential, or internal token used by the Shipit app itself) but is not part of `TaskCommands#env`/`@stack.env`, it is substituted verbatim and echoed into the review/task output that the attacker (as the task's triggering user) can view.

### Impact Explanation
This exposes secrets held in the Shipit host process's own `ENV` (distinct from, and broader than, what the deliberately-filtered child process environment would ever contain) to an attacker who merely needs to know or guess the variable's name. If the leaked value is a deploy-time secret or internal credential, this matches "exfiltration of ... deploy-time secrets" (Critical). The blast radius is bounded to whatever the Shipit host process itself has in `ENV` (shared across all stacks/tenants on that instance), so a successful guess on one repository's PR can leak a secret affecting the whole Shipit installation, not just that repository.

### Likelihood Explanation
Requires: (1) the target repository has review stacks enabled with a provisioning policy the attacker can satisfy (e.g. `allow_all`, or `allow_with_label` if they can self-label their own PR); (2) the Shipit host process happens to have a sensitive value set under a guessable/blindly-triggerable `ENV` key not already exposed via `@stack.env`/`Shipit.env`. Attacker cost is low (open a PR, add one line to `shipit.yml`), but success is probabilistic since the attacker cannot inspect the host's actual `ENV` keys in advance and must guess conventional names (`DATABASE_URL`, `SECRET_KEY_BASE`, `RAILS_MASTER_KEY`, etc.). Repeatable per repository/PR with review stacks enabled.

### Recommendation
Remove the implicit fallback to the host process `ENV` in `EnvironmentVariables#interpolate` (`lib/shipit/environment_variables.rb:23-26`); only substitute variables explicitly present in the task/stack's approved `@env`, defaulting unset variables to an empty string (consistent with the existing "coerce nil to empty string" test) rather than leaking the Shipit host process's own environment.

### Proof of Concept
minitest in `test/unit/command_test.rb` style (do not modify test/, this is illustrative for the fix validation):
```ruby
test "#interpolate_environment_variables does not leak Shipit host ENV" do
  previous = ENV['SECRET_HOST_VAR']
  ENV['SECRET_HOST_VAR'] = 'leaked'
  command = Command.new('echo $SECRET_HOST_VAR', env: {}, chdir: '.')
  refute_includes command.run, 'leaked'
ensure
  ENV['SECRET_HOST_VAR'] = previous
end
```
Assert LHS (`command.run` output) does NOT equal/contain RHS (`ENV['SECRET_HOST_VAR']`) when `SECRET_HOST_VAR` is absent from the `Command`'s own `env:` hash — currently this assertion fails, confirming the leak via `@env.fetch(variable) { ENV[variable] }` at `lib/shipit/environment_variables.rb:25`.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
