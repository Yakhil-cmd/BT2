### Title
Webhook organization used for HMAC-secret selection is decoupled from the repository actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization `webhook_secret` to validate a GitHub webhook against using `repository_owner`, a value pulled from the untrusted, unsigned-at-selection-time JSON body (`repository.owner.login` or `organization.login`). The event handlers, however, act on a *different* field of the same payload — `repository.full_name` — to resolve the `Repository`/`Stack` that gets mutated. In a multi-organization Shipit deployment (`Shipit.github(organization:)` / `github_app_config`), these two fields are never cross-checked against each other, so a valid HMAC signature from one organization's secret can be paired with a `repository.full_name` belonging to a different organization's tracked repository.

### Finding Description
`verify_signature` picks the `GitHubApp` (and its `webhook_secret`) purely from `repository_owner`: [1](#0-0) [2](#0-1) 

The signature check itself is a plain HMAC-SHA1 comparison of the raw body against that organization's secret: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its own independent secret, selected by name: [4](#0-3) 

Once the signature passes, every webhook handler resolves the target repository/stacks from a *different* JSON field — `repository.full_name` — with no linkage back to the `repository_owner`/secret that was used to authenticate the request: [5](#0-4) [6](#0-5) 

Because an attacker who owns/administers their own GitHub organization (call it `attacker-org`, tracked in the same Shipit instance) legitimately knows `attacker-org`'s `webhook_secret` (it's configured by them when they set up their GitHub App/webhook), they can construct an arbitrary payload where:
- `repository.owner.login` = `attacker-org` (drives secret selection and passes HMAC validation, since they sign with their own secret), and
- `repository.full_name` = `victim-org/victim-repo` (drives the actual handler logic against a repo they do not own).

The binding that is broken is: *organization authenticated* (`repository_owner` → secret used to verify HMAC) *should equal* *repository written* (`repository.full_name` → repository/stack acted upon by the handler). Nothing enforces `repository.owner.login == repository.full_name.split('/').first`.

### Impact Explanation
This lets a "confused deputy" webhook be delivered to any organization's tracked repositories using credentials that only match a completely different, attacker-controlled organization. Concretely, using handlers already present:
- `PushHandler`/push event → enqueues `GithubSyncJob` for the victim's stack based on `repository.full_name`, causing unwanted git sync activity against the victim's stack.
- `StatusHandler` → creates a commit `Status` on a victim commit SHA the attacker names in the payload.
- `CheckSuiteHandler` → enqueues `RefreshCheckRunsJob` for the victim's stack.
- `pull_request` handlers (`ClosedHandler`, etc.) → can archive/mutate the victim's `Stack` state, keyed only off `repository.full_name`.

This is High severity: it constitutes an unauthenticated write (state mutation on unowned repository/stack objects) crossing an organizational trust boundary, matching the "cross-repository writes" / "escalation" impact classes, achieved purely by control of one's own legitimately-configured organization secret rather than any credential belonging to the victim.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration via `github_app_config`), and (2) the attacker to control at least one such organization/app registered in that instance (e.g., a public open-source foundation or platform where multiple external orgs register their own GitHub App/webhook secret with a shared Shipit deployment). Given that requirement, exploitation needs no special access beyond crafting an HTTP POST with correctly-computed HMAC using the attacker's own secret — no repository write access, no session, and no API token for the victim org are needed.

### Recommendation
After signature verification succeeds, verify that the *authenticated* organization matches the owner encoded in the same `repository.full_name` (or `organization.login`) that the handler will actually operate on, e.g. in `verify_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified && repository_owner_matches_full_name?
  ...
end

def repository_owner_matches_full_name?
  full_name_owner = params.dig('repository', 'full_name')&.split('/')&.first
  full_name_owner.nil? || full_name_owner.casecmp(repository_owner).zero?
end
```
Alternatively, resolve the signing organization strictly from `repository.full_name`'s owner segment instead of `repository.owner.login`, eliminating the two independent lookup paths entirely.

### Proof of Concept
1. Configure Shipit (`secrets.github`) with two organizations, `attacker-org` (secret `S_A`, controlled by the attacker) and `victim-org` (secret `S_V`, tracks `victim-org/victim-repo` as a Stack).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "after": "<attacker-chosen sha>",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` using their own known secret `S_A`.
4. POST to `/github/webhooks` (or the mounted webhook path) with this body/header.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, verifies successfully against `S_A`.
6. `PushHandler` (invoked via `Shipit::Webhooks.for_event(event)`) resolves `repository_name` = `"victim-org/victim-repo"` via `Handler#repository_name`/`Repository.from_github_repo_name`, and enqueues `GithubSyncJob` for the victim's stack — despite the request never being authenticated with `victim-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
