Confirmed multi-organization support: `Shipit.github(organization:)` picks a per-organization `GitHubApp` config (each with its own `webhook_secret`) based on `github_app_config(organization)` [1](#0-0) , and `WebhooksController#verify_signature` selects which app config to verify against using `repository_owner`, a value read straight out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`) [2](#0-1) .

### Title
Webhook signature is verified against an organization key chosen from unverified payload data, decoupling the authenticating org from the repository being written - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-org Shipit deployments, the HMAC signature check picks which organization's `webhook_secret` to verify against by reading `repository.owner.login`/`organization.login` directly from the raw JSON body, before that body has been authenticated. Handlers then act on the repository named in that same unverified body (e.g. `params.repository.full_name`), so the field selecting "whose secret authenticates this request" and the field selecting "which repository gets written to" are the same untrusted values, but nothing binds them to a single, consistent, previously-configured relationship enforced at verification time.

### Finding Description
`Shipit.github(organization:)` supports one `GitHubApp`/`webhook_secret` per organization key present in `secrets.github` [1](#0-0) . `WebhooksController#verify_signature` computes `repository_owner` purely from `params` (the parsed, not-yet-verified JSON body) and uses it to select which org's secret is used to verify `X-Hub-Signature`: [2](#0-1) 
Because the org name used to pick the verification key comes from the attacker-controlled payload rather than from any pre-existing, trusted routing/binding (e.g. URL path, prior repository registration), an attacker who knows organization A's `webhook_secret` (e.g. a compromised or lower-trust org onboarded to the same Shipit instance) can sign a payload with A's secret while filling in `repository.full_name` for a *different* tracked repository/org B. The signature check passes (it validates against A's secret because `repository_owner` says "A"), and then the event handler (e.g. `PushHandler`, `ReopenedHandler`) resolves the target repository/stack from `repository.full_name` in that same payload and acts on it [3](#0-2) [4](#0-3) . The equality that should hold — "organization whose key authenticated the request" == "organization owning the repository the handler mutates" — is never enforced; both sides are read from the same unauthenticated JSON before signature verification uses either of them.

### Impact Explanation
This allows an attacker with only one organization's webhook secret (not the target's) to forge events (`push`, `pull_request`, `status`, `check_suite`, etc.) for stacks belonging to a different organization tracked by the same Shipit instance. Depending on handler, this can trigger `sync_github` with attacker-chosen `expected_head_sha` [5](#0-4) , unarchive review stacks, or otherwise manipulate stack state for a repository the attacker does not control — an authorization-boundary break across organizations that were meant to be isolated by separate webhook secrets.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization (multi-tenant `secrets.github` schema), and (2) the attacker possessing (or controlling) the `webhook_secret` for at least one onboarded organization, while the target repository belongs to a different organization on the same instance. This is a real configuration Shipit explicitly supports (`github_organizations`, `github_app_config`) [6](#0-5) , so the precondition is plausible in shared/multi-org Shipit installations, though it does not apply to single-organization deployments where `github_default_organization` is `nil`.

### Recommendation
Do not derive the signature-verification key from attacker-supplied payload fields. Bind the webhook endpoint (or an unguessable per-organization/per-repository path/token) to a specific organization's `webhook_secret` at routing time, or verify the signature against *every* configured org secret and only proceed if the payload's own `repository.full_name`/`organization.login` matches the org whose secret actually validated — i.e., enforce the equality `verified_org == payload_repository_owner` explicitly instead of using the unverified value to pick the key.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` in `secrets.github` [1](#0-0) .
2. Attacker knows `org-a`'s `webhook_secret` (e.g. leaked, or attacker's own onboarded org).
3. Attacker crafts a `push` payload with `repository.owner.login = "org-a"` but `repository.full_name = "org-b/target-repo"`.
4. Attacker computes `X-Hub-Signature` using `org-a`'s secret over the raw body and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")`, verifies successfully against `org-a`'s secret [7](#0-6) .
6. `PushHandler#process` looks up stacks by `repository.full_name = "org-b/target-repo"` and calls `sync_github(expected_head_sha: params.after)`, acting on `org-b`'s stack despite the request only being authenticated for `org-a` [5](#0-4) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
