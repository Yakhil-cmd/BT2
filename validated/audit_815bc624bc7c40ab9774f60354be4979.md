### Title
Cross-tenant commit-status forgery in `StatusHandler` lets any organization authenticated by webhook signature verification write CI status onto commits belonging to any other repository/stack, enabling an unauthorized deploy - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub `status` webhook against the secret configured for **one specific organization**, derived from the payload's `repository.owner.login` (or `organization.login`) field. [1](#0-0)  Once that check passes, the event is dispatched to `Shipit::Webhooks::Handlers::StatusHandler`, which never re-checks which repository/organization the target commit belongs to: it looks up matching `Commit` rows by SHA alone, across the entire Shipit database, and writes a GitHub-reported CI status onto them. [2](#0-1)  This breaks the trust binding *organization authenticated == repository being written*, matching the analog bug class (accounting/authorization performed on one quantity while the effect is applied to a different, uncorrelated quantity).

### Finding Description
In `WebhooksController`, the signature is verified per-organization:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

This only proves that the request body was signed with the webhook secret of whatever organization the attacker names in `repository.owner.login`. In a multi-tenant Shipit instance (one install serving several GitHub organizations, each with its own configured `webhook_secret` in `secrets.yml`, as documented in `docs/setup.md`), an org admin legitimately possesses their *own* organization's webhook secret and can therefore produce a validly-signed payload while putting **any** value in other payload fields, including `repository.full_name` / commit `sha`, since those fields are not covered by the org-selection logic and are never cross-checked against the authenticated organization.

The `status` event is then routed to `StatusHandler`:

```ruby
class StatusHandler < Handler
  params do
    requires :sha, String
    requires :state, String
    ...
  end

  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
``` [4](#0-3) 

Unlike other handlers (`PushHandler`, the pull-request handlers), which resolve a `Repository` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` before touching any stack-scoped data, [5](#0-4)  `StatusHandler#process` performs **no repository/stack scoping at all** — `Commit.where(sha: params.sha)` searches every commit in every stack in the database. Any commit anywhere with a matching SHA gets a forged status written via `create_status_from_github!`, which ultimately determines `Commit#deployable?` (`success? && !blocked?`) and, if the target stack has continuous deployment enabled, triggers an automatic deploy through `schedule_continuous_delivery` → `ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery`. [6](#0-5) [7](#0-6) [8](#0-7) 

**Before the attack:** authenticated organization = attacker's own org (e.g. `attacker-org`); commits written = only commits belonging to `attacker-org`'s repositories, as GitHub itself would only ever send status webhooks for commits in that org's repos.

**After the attack:** authenticated organization = `attacker-org`; commits written = any commit row in the Shipit database whose SHA is known/guessed by the attacker, regardless of which organization/stack it belongs to. The equality *authenticated org == repo of written commit* is broken.

### Impact Explanation
This crosses a hard tenant boundary between organizations hosted on the same Shipit instance. By forging a `success` status for a specific commit SHA in a victim stack that has `continuous_deployment` enabled, an attacker who is only a legitimate maintainer of an unrelated, lower-trust organization configured on the same Shipit instance can flip `Commit#deployable?` to true and cause Shipit to automatically deploy that commit — an **unauthorized deploy** of code that never actually satisfied the victim repository's CI/status requirements. This falls squarely into the Critical bucket ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) the target Shipit instance hosts more than one GitHub organization/tenant (a documented, supported configuration — see `docs/setup.md` multi-org examples and `config/secrets.development.shopify.yml`), (2) the attacker controls (or is an admin of) at least one of those lesser-trusted organizations and thus legitimately possesses that org's own `webhook_secret` (not the victim's), and (3) the attacker knows or can obtain the target commit SHA (often public, e.g. from the victim's public GitHub repo) and that the target stack has continuous deployment enabled. No compromise of the victim's credentials, GitHub App, or repository is required — only cross-tenant confusion caused by the missing repository-scoping check in `StatusHandler`.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the repository the webhook was verified for, e.g. resolve `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (as `Handler#stacks` already does) and restrict the `Commit.where(sha: params.sha)` query to `stacks.map(&:commits)` / a join on that repository's stacks, so a status can only ever be applied to commits belonging to the same repository whose organization was authenticated by `verify_signature`.

### Proof of Concept
1. Attacker is an admin of `attacker-org`, one of several organizations configured in this Shipit instance's `secrets.yml`, and therefore holds `attacker-org`'s legitimate `webhook_secret`.
2. Attacker learns (e.g. from GitHub's public API) the SHA of a commit `abcdef123...` in `victim-org/victim-repo`, a stack tracked by the same Shipit instance with `continuous_deployment: true`.
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "abcdef123...",
     "state": "success",
     "context": "ci/tests",
     "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}
   }
   ```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s real `webhook_secret` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s config, and the signature check passes. [9](#0-8) 
6. `StatusHandler#process` runs `Commit.where(sha: "abcdef123...")`, finds the victim's commit (belonging to a different org/stack entirely), and writes a fabricated `success` status onto it. [10](#0-9) 
7. If that commit now satisfies `deployable?` and the victim stack's `continuous_deployment?` is enabled, `ContinuousDeliveryJob` deploys it automatically. [6](#0-5) [8](#0-7)
