## Title
Rounding-order mismatch between `getLocalTpsFee` and `getCurrentTpsFeeToPay` can make a composed unit's `tps_fee` insufficient at validation time - (File: storage.js)

### Summary
The reported Arcadia bug is caused by two functions that are supposed to compute the *same* economic quantity (liquidation value) but apply rounding/conversion in a different order, so that a value which is "just liquidatable" in one function is "just not liquidatable" in the other. ocore has an analogous pattern in the TPS-fee subsystem: `storage.getLocalTpsFee()` and `storage.getCurrentTpsFeeToPay()` both compute a "TPS fee per unit" from the same three inputs (`base_tps_fee`, `tps_fee_multiplier`, `tps`), but they round at different points in the arithmetic, and the composer relies on the max of these differently-rounded values when deciding how much `tps_fee` to attach to a unit, while the enforcement path (`validateTpsFee`) uses only one of the two formulas as the hard minimum.

### Finding Description
`storage.getLocalTpsFee` (used by both the composer, via `parent_composer.getLocalTpsFee`, and by unit validation in `validateTpsFee`) computes: [1](#0-0) 
```
const tps_fee_per_unit = Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1));
return count_units * tps_fee_per_unit;
```
i.e. it multiplies `tps_fee_multiplier` into the expression *before* rounding, and rounds exactly once.

`storage.getCurrentTpsFeeToPay`, which the composer also folds into its decision of what fee to pay, computes the "same" quantity in a different order: [2](#0-1) 
```
function getCurrentTpsFee(shift = 0, count_units = 1) {
	const tps = getCurrentTps(shift, count_units);
	const base_tps_fee = getSystemVar('base_tps_fee', last_stable_mci);
	const tps_interval = getSystemVar('tps_interval', last_stable_mci);
	return Math.round(base_tps_fee * (exp(tps / tps_interval) - 1));
}
function getCurrentTpsFeeToPay(shift = 0, count_units = 1) {
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_stable_mci);
	return Math.round(tps_fee_multiplier * getCurrentTpsFee(shift, count_units));
}
```
Here `base_tps_fee * (exp(tps/interval) - 1)` is rounded *first*, and the (already-rounded) result is then multiplied by `tps_fee_multiplier` and rounded *again* — a double-rounding of the same underlying formula that `getLocalTpsFee` rounds only once. For non-integer `tps_fee_multiplier` values (a system-configurable variable via `getSystemVar('tps_fee_multiplier', ...)`) these two code paths can diverge by one or more units of `base_tps_fee`.

The composer (`parent_composer.getTpsFee`) picks the *maximum* of both formulas as the fee to attach to a newly composed unit: [3](#0-2) 
```
async function getTpsFee(conn, parent_units, last_ball_unit, timestamp, count_units = 1) {
	return Math.max(
		await getLocalTpsFee(conn, parent_units, last_ball_unit, timestamp, count_units),
		storage.getCurrentTpsFeeToPay(0, count_units) * count_units,
		storage.getCurrentTpsFeeToPay(1, count_units) * count_units
	);
}
```
while the hard enforcement check in `validateTpsFee` compares the unit's declared `tps_fee` (plus balance) strictly against `storage.getLocalTpsFee(conn, objUnitProps, count_units)`: [4](#0-3) 
```
const min_tps_fee = await storage.getLocalTpsFee(conn, objUnitProps, count_units);
...
if (tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share)
	return callback(`tps_fee ${objUnit.tps_fee} + tps fees balance ${tps_fees_balance} less than required ${min_tps_fee} for address ${address} whose share is ${share}`);
```
Because `getLocalTpsFee` is itself also based on live network state (`getLocalTps`, i.e., counting currently-unstable units at evaluation time), the value computed by the composer at compose time and the value re-derived by validating nodes at validation time are not guaranteed to be identical even before considering the rounding difference — the rounding-order discrepancy compounds this gap in the same direction as the Arcadia bug: the "decision helper" (composer, deciding whether a fee is enough to be broadcast/accepted) and the "enforcement" function (`validateTpsFee`, which actually rejects the unit) do not use bit-for-bit the same rounding path for equivalent inputs.

### Impact Explanation
If the composed `tps_fee` (derived via the max of the three differently-rounded candidates) is off by even 1 from what `validateTpsFee`'s hard check subsequently requires via `getLocalTpsFee`, an honest unit author who composed a unit believing its fee was sufficient can have that unit **rejected by validating/witness nodes** with `AccountErrors`-style rejection (`"tps_fee ... less than required ..."`), i.e. the network is momentarily unable to confirm a legitimately-composed unit, mirroring the "liquidator cannot start liquidation despite the account really being liquidatable" scenario from the source report (here: "unit author cannot get the unit accepted despite believing the fee was computed to be sufficient").

### Likelihood Explanation
This requires `tps_fee_multiplier` (or the interaction of `base_tps_fee`/`tps`) to produce values where rounding order actually changes the integer result, which is a fairly narrow numeric window (analogous to the original report's "off by one" rounding scenario), and additionally requires that the composer's `getCurrentTpsFeeToPay` branch (rather than `getLocalTpsFee`) be the binding `max()` term at compose time while the network's live TPS state shifts unfavorably by the time of validation. This makes it a low-probability, hard-to-trigger-deterministically edge case rather than a routinely reachable condition, consistent with a Medium-severity classification.

### Recommendation
Make `getCurrentTpsFeeToPay` round using the same single-rounding order as `getLocalTpsFee` (i.e. `Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps/tps_interval) - 1))` computed in one expression), or otherwise ensure both formulas used for "is this fee enough" decisions are always derived through one shared, single-rounding code path so that composer and validator can never disagree by a rounding artifact.

### Proof of Concept
Not independently confirmed with a runnable reproduction in this pass — the analysis is based on static comparison of the two rounding formulas in `storage.js` (`getLocalTpsFee` lines 1339-1349 vs. `getCurrentTpsFee`/`getCurrentTpsFeeToPay` lines 1397-1408) and their consumption in `parent_composer.js` (`getTpsFee`, lines 537-543) and `validation.js` (`validateTpsFee`, lines 1070-1089). A concrete PoC would require choosing `tps_fee_multiplier`/`base_tps_fee`/`tps` system-variable values (via `getSystemVar`) for which `Math.round(m*x*(e-1))` differs from `Math.round(m*Math.round(x*(e-1)))`, then simulating a compose/validate cycle across a shift in live TPS state — this was not executed in this session and should be validated with a live test harness before treating this as confirmed rather than a plausible analog.
