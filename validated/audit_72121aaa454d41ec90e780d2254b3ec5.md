### Title
Webhook signature verification keys off `repository.owner.login` while the acted-upon repository/stack is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but every event handler resolves the actual repository/stack to mutate using the separate `repository.full_name` field. Nothing ties these two fields together, so a valid signature computed with organization A's webhook secret can be replayed on a forged payload naming organization B's repository, letting an attacker who controls one onboarded GitHub organization on a multi-tenant Shipit install forge webhook events (push syncs, commit statuses, pull_request/check_suite/membership events) against stacks owned by a different organization.

### Finding Description
`WebhooksController` verifies webhooks like this: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` from the raw JSON body, and that string is used to pick the `GitHubApp` (and therefore the `webhook_secret`) via `Shipit.github(organization: repository_owner)`. The signature is verified against `request.raw_post` using that org's secret.

Once verification passes, `create` re-parses the same raw body and dispatches it to handlers: [3](#0-2) 

Handlers resolve the affected repository/stacks from a *different* key in the same payload, `repository.full_name`, via `Handler#repository_name`/`#stacks`: [4](#0-3) 
which is looked up with `Repository.from_github_repo_name`: [5](#0-4) 

For example, `PushHandler#process` syncs the resolved stack from an attacker-chosen SHA: [6](#0-5) 
and `StatusHandler#process` writes commit statuses for any commit matching the attacker-supplied `sha`, independent of which org "owns" that commit: [7](#0-6) 

Because `verify_signature` never checks that `repository.owner.login` (the field used to pick the signing secret) is the same organization that owns `repository.full_name` (the field used to pick the target repository/stack), the HMAC signature only proves "this body was signed with organization X's secret" — it does not prove "organization X is authorized to act on the repository named in this body." An organization admin who legitimately knows their own org's `webhook_secret` (configured per-org in `Shipit.github_organizations`/`config/secrets.yml`, see `lib/shipit/github_app.rb` and `docs/setup.md`) can therefore self-sign a POST directly to `/webhooks` with `repository.owner.login` set to their own org (so the correct secret/app is selected) but `repository.full_name` set to `"other-org/other-repo"`, and the forged event will be processed against a stack they do not control.

This exactly reproduces the class of bug in the report: an action recomputes/derives state from one part of a data structure (here, target repository from `full_name`) while a security check earlier only validated a different, unrelated part of the same structure (`owner.login`) — an equality that the report's `updateErcDebt`-before-flag-check violation also broke (checked field ≠ acted-upon field).

### Impact Explanation
This breaks the binding "organization authenticated == repository written." A single onboarded organization's webhook secret can be used to:
- Force `GithubSyncJob` runs and (via `push`) trigger deploy-relevant re-syncs of another organization's stacks,
- Inject arbitrary commit statuses for another organization's commits, potentially flipping `deployable?` state and unblocking deploys/merges (`StatusHandler`),
- Trigger check_suite refreshes, membership changes, and pull_request driven merge-queue actions scoped by `repository.full_name` while validated under a foreign org's key.

This is a cross-repository/cross-organization write achieved without holding a Shipit session, `ApiClient` token, or the *target* organization's webhook secret — matching the Critical impact bucket ("cross-repository writes, unauthorized deploy/merge").

### Likelihood Explanation
Exploitability requires the instance to be configured with more than one GitHub organization (`Shipit.github_organizations`), and requires the attacker to control (i.e., know the `webhook_secret` of) at least one onboarded organization — a realistic scenario for shared/multi-tenant Shipit deployments where different teams each control an org's GitHub App/webhook config. No repository write access, GitHub App private key, or Shipit login is needed for the target org.

### Recommendation
In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), require that the organization used to select the signing secret matches the owner embedded in `repository.full_name` (and, ideally, look up the target `Repository`/`Stack` and re-derive the organization from that persisted record rather than trusting body fields at all). Reject the webhook if `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
Not executed (no sandbox access); conceptual reproduction based on code inspection:
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. As an attacker who administers `org-a`'s GitHub App and therefore knows `org-a`'s `webhook_secret`, craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac_sha1(org-a-webhook-secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` looks up `Shipit.github(organization: "org-a")` and successfully verifies the signature, since it was computed with `org-a`'s real secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/victim-repo")` — a repository belonging to `org-b`, not `org-a` — and triggers `stack.sync_github(expected_head_sha: "deadbeef")`, i.e., a cross-organization action authorized by the wrong org's credential.     def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
