### Title
Webhook Signature Verified Against Attacker-Chosen `repository.owner.login`, But Payload Processed Against Independent `repository.full_name` — Cross-Organization Trust Confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate a request against using `repository.owner.login` (falling back to `organization.login`) pulled straight out of the *unauthenticated* request body. Once verification passes, every event handler resolves the repository/stack to act on using a **different, independently attacker-controlled** field: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb#repository_name`). Because the field used to pick the verifying organization is never bound to the field used to pick the target repository, and because `GitHubApp#verify_webhook_signature` silently returns `true` when the resolved organization has no `webhook_secret` configured (an explicitly optional setting per `docs/setup.md`), an attacker who can reach any organization/installation lacking a webhook secret can forge events for a completely different, properly-secured organization's repositories.

### Finding Description
`verify_signature` computes the signing organization purely from request-controlled JSON:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`app/controllers/shipit/webhooks_controller.rb` lines 24-62.

`GitHubApp#verify_webhook_signature` bypasses HMAC checking entirely for organizations that don't have a secret configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
`lib/shipit/github_app.rb` lines 76-83. The docs explicitly mark this field optional (`docs/setup.md` line 30: "Webhook secret (optional)"), and Shipit natively supports multiple organizations sharing one install with independent secrets (see `test/dummy/config/secrets_double_github_app.yml`), so an org with no secret configured is a realistic, in-scope configuration state — not a hypothetical.

Once `head(422)` isn't triggered, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs (`create` action, same file). Every handler resolves its target repository from a *second, unrelated* field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
`app/models/shipit/webhooks/handlers/handler.rb` lines 36-38, used by `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`), all `PullRequest::*Handler`s (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb` line 52, `reopened_handler.rb` line 51, `unlabeled_handler.rb` line 61, etc.), and the status handler.

**Binding broken (equality that must hold but doesn't):**
`organization_that_authenticated_the_request(repository.owner.login) == organization_owning(repository.full_name)`

Before the attack: for a genuine GitHub-originated webhook these two fields always describe the same repository, so the equality trivially holds.
After the attack: the attacker crafts a raw JSON body where `repository.owner.login` names an org with no configured `webhook_secret` (verification auto-passes) while `repository.full_name` names an arbitrary Shipit-managed repository belonging to a different, properly-secured organization. The equality is broken and Shipit processes the event as if it legitimately originated from GitHub for that other repository.

### Impact Explanation
This crosses the "organization authenticated vs repository written" trust boundary explicitly in scope. Concretely, an attacker can inject forged `push` events (`PushHandler`) causing `GithubSyncJob` to run against a target stack with an attacker-chosen `expected_head_sha`, or forge `status`/`check_suite` events, or forge `pull_request` events driving `ReviewStackAdapter` to create/archive/unarchive review stacks — all against a repository whose organization never authorized or signed the request. If the targeted stack has `continuous_deployment` enabled, a forged sync/status sequence can lead to an unauthorized deploy, matching the Critical impact bar ("an unauthorized deploy"). This is a direct analog of the reported `BasePool.mint()` issue: a verification/authorization check (`onlyRouter` / HMAC signature) is anchored to one identity while the actual state-changing operation is keyed off a separate, unchecked field, letting the caller bypass the intended input validation binding.

### Likelihood Explanation
Exploitability requires only that at least one organization/installation configured in `secrets.github` lacks a `webhook_secret` — a state the documentation itself presents as optional and acceptable (`docs/setup.md` line 30), and one that's structurally supported for multi-org deployments (`test/dummy/config/secrets_double_github_app.yml`). No GitHub App private key, no `webhook_secret`, no `ApiClient` token, and no Shipit session are needed by the attacker — they only need network access to `POST /webhooks` and knowledge of any org name in the install that omitted a secret, satisfying the "unprivileged attacker" requirement.

### Recommendation
Bind the signature-verification identity to the same repository that handlers subsequently act on: derive `repository_owner` and the processing target from a single, consistently-verified field (e.g., always use `repository.full_name`'s owner segment for both signature lookup and dispatch), and reject payloads where `repository.owner.login`/`organization.login` disagree with the owner segment of `repository.full_name`. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank in multi-organization configurations — require an explicit secret per organization or fail closed.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. mirroring `test/dummy/config/secrets_double_github_app.yml`, where `OrgWithoutSecret` has `webhook_secret: nil` and `OrgSecured` (owning a real, continuously-deployed stack `OrgSecured/target-repo`) has a strong secret.
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   # arbitrary/invalid
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
     "owner": { "login": "OrgWithoutSecret" },
     "full_name": "OrgSecured/target-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner` = `"OrgWithoutSecret"`, calls `Shipit.github(organization: "OrgWithoutSecret").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank for that org (`lib/shipit/github_app.rb` line 77).
4. `PushHandler#process` resolves the target via `repository_name` = `"OrgSecured/target-repo"` (`handler.rb` line 37) and enqueues `GithubSyncJob` for that stack, with `expected_head_sha` fully attacker-controlled — despite the request never being authenticated by `OrgSecured`'s webhook secret.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
