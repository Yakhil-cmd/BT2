### Title
Arbiter contract shared-address split can be front-run by an ArbStore fee increase - (File: arbiter_contract.js)

### Summary
The arbiter-contract shared-address definition that governs how a contract's funds are split at settlement embeds a "cut" percentage that is fetched live from the arbiter's ArbStore server rather than being fixed and committed at the time the two counterparties negotiate and hash the contract. Because this fee is fetched fresh (and only cached in-memory) each time `deriveSharedAddress` is called, an ArbStore operator can raise its `cut` between contract negotiation and shared-address derivation/settlement, silently taking a larger share of the contract funds than the parties agreed to — the same "fee front-run before settlement" pattern described in the referenced TurboSafe `slurp` finding.

### Finding Description
Two unprivileged counterparties (offeror/acceptor) negotiate an arbiter contract whose committed, hashed terms (`title`, `text`, `my_address`, `peer_address`, `creation_date`, party names, `me_is_payer`, `arbiter_address`, `amount`, `asset`) never include the ArbStore's cut percentage. [1](#0-0) 

The actual split of funds, however, is computed later, when each party independently calls `deriveSharedAddress`, which fetches the arbiter's ArbStore `cut` live over HTTPS via `arbiters.getArbstoreInfo` and bakes it directly into the multisig "has output" conditions of the shared address definition: [2](#0-1) [3](#0-2) 

`getArbstoreInfo` only validates that `0 <= cut < 1`; there is no upper bound, no signature/commitment tying the fetched cut to the original contract negotiation, and the value is cached only in a process-local in-memory map (`arbStoreInfos`), meaning it can change at any time the ArbStore chooses to serve a different value: [4](#0-3) 

At settlement time, `complete()` re-reads whatever cut ended up encoded in the on-chain shared address definition (via `readSharedAddressDefinition`) to build the final payout outputs, rather than re-validating it against the cut that was in effect (or disclosed) when the contract was accepted: [5](#0-4) 

Because the cut used to build the definition is fetched independently and asynchronously by each party (offeror when deriving/offering the shared address, acceptor separately), and is never part of the immutable, mutually-signed contract hash, the ArbStore/arbiter can effectively change the economic terms of the contract after the parties have already agreed to `amount`/`asset`/`title`/`text`, simply by updating the `cut` value its server returns before the shared address is derived or before `complete()` reads the definition.

### Impact Explanation
An ArbStore operator (who is not one of the trusted multisig signers of the contract in the cryptographic sense, but who does control the value that ends up encoded in the payout condition) can raise its `cut` right before a shared address is generated or right before completion, capturing more of the contract's `amount` than either counterparty consented to when they signed off on the contract terms. This is a direct, unauthorized diversion of funds from a private-payment counterparty to the ArbStore/arbiter's own address (`arbstoreInfo.address`), matching the "unauthorized spending" impact class. Because the disputed value never enters the cryptographically committed contract hash, victims have no on-chain proof of the fee they agreed to, and the discrepancy is only visible by manually decoding the shared address definition.

### Likelihood Explanation
The condition is trivial to trigger: it does not require any race with the network or a malicious peer — the ArbStore is by design the trusted service run by (or on behalf of) the arbiter counterparty, and it fully controls the HTTP response used to compute the cut. Any point in time between contract negotiation (`createAndSend`/`respond`) and shared-address derivation, or between derivation and `complete()`, is an opportunity to change the served cut. No governance timelock or on-chain bound (unlike the `base_tps_fee`/`tps_fee_multiplier` system-vote parameters elsewhere in ocore, which are capped and delayed via `system_vote`/`countVotes`) protects the counterparties here. [6](#0-5) 

### Recommendation
Commit the ArbStore `cut` (and `arbstoreInfo.address`) into the contract's cryptographically hashed terms (`getHash`) at the moment the contract is created/accepted, so both parties cryptographically agree to the exact fee before payment. `deriveSharedAddress` and `complete` should use this committed value instead of re-fetching it live from the ArbStore, and any mismatch between the committed cut and a freshly fetched one should be treated as a contract violation and refused, analogous to adding a `MAX_FEE`-style bound and pre-commitment recommended for the TurboSafe finding.

### Proof of Concept
1. Arbiter `A` runs an ArbStore that currently advertises `cut = 0.01` (1%).
2. Payer and payee negotiate and sign an arbiter contract for `amount = 1,000,000` with `arbiter_address = A`; the signed/hashed contract fields do not include `cut`. [1](#0-0) 
3. Before the offeror calls `deriveSharedAddress` (or before `complete()` runs), the ArbStore operator changes the value returned by `/api/get_info` to `cut = 0.20` (20%). [7](#0-6) 
4. `deriveSharedAddress` bakes the new 20% cut into the shared address definition's payout conditions, and/or `complete()` reads a definition containing the inflated cut. [3](#0-2) 
5. The payer's `amount` is unchanged, but at settlement the ArbStore/arbiter address receives `amount * 0.20` instead of the `amount * 0.01` implicitly expected when the contract was negotiated, with no on-chain record of the originally agreed rate to dispute the change.

function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
