### Title
Cross-organization/cross-repository commit status forgery leading to unauthorized deploy trigger - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook handler resolves the target `Commit` purely by SHA, with no binding to the repository/organization whose signature was actually verified. In a multi-GitHub-App deployment, this lets anyone who legitimately controls a repository (and therefore a real, GitHub-signed webhook) on **any** configured organization write a commit status onto a commit belonging to a completely unrelated stack/organization, potentially triggering an unauthorized continuous deployment.

### Finding Description
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using data taken from the webhook payload itself: [1](#0-0) [2](#0-1) 

This is fine as far as authenticating *that the request came from GitHub for organization X* — but nothing else in the pipeline binds the verified organization/repository to the entity that gets mutated. `Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) using only the `sha` field, with **no scoping to the repository/organization that the webhook claims to originate from**: [3](#0-2) 

`Commit.where(sha: params.sha)` searches across the *entire* commits table, i.e. across every stack/repository/organization configured in this Shipit instance, not just the repository referenced in the webhook payload. This is the same class of bug as the CryptoPunks issue: the entity that is cryptographically authenticated (the organization owning the webhook secret) is not the same entity that the code acts on (any commit whose SHA happens to match, in any stack, in any organization).

Shipit explicitly supports hosting multiple GitHub organizations behind one instance, each with its own `webhook_secret`, as documented in `docs/setup.md` ("Using Multiple Github Applications") and implemented via `Shipit.github_app_config`/`Shipit.github`: [4](#0-3) 

Because commit SHAs are public/guessable (any observer of the target repo knows valid SHAs), an attacker who administers a repository under Organization A can:
1. Create a real commit status on their own repository, using the SHA of a commit in an unrelated Organization B's repository that also happens to be tracked by the same Shipit instance.
2. Let GitHub deliver this genuinely-signed webhook to Shipit's `/webhooks` endpoint.
3. `verify_signature` validates the signature against Organization A's secret (correctly, since GitHub really sent it for A).
4. `StatusHandler#process` then matches `Commit.where(sha: ...)` against Organization B's commit and creates a `Status` on it, with attacker-controlled `state`, `description`, `context`, `target_url`.

### Impact Explanation
Creating a `Status` record fires side effects that are not scoped by organization at all: [5](#0-4) 

which calls `Commit#schedule_continuous_delivery`: [6](#0-5) 

If the victim stack (belonging to the unrelated organization) has `continuous_deployment` enabled and the injected `success` status makes the commit `deployable?`, this enqueues `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** of a stack the attacker has no legitimate access to — meeting the Critical bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
This requires:
- The Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and
- The attacker to control (or have push/status access on) at least one repository/organization mounted on that instance, and
- Knowledge of a target commit SHA in another organization's tracked repository (trivial for public repos, and often knowable/leakable for private ones via CI logs, PR links, etc.), and
- The victim stack to have continuous deployment enabled.

This is a realistic configuration for shared internal Shipit deployments serving several teams/organizations, making the likelihood moderate-to-high in that deployment topology.

### Recommendation
Scope commit lookups in webhook handlers (in particular `StatusHandler`, and any other handler resolving records purely by payload-supplied identifiers) to the repository/organization that was actually verified for that request — i.e. join through `Commit -> Stack -> Repository` and require `repository.full_name`/owner to match the verified `repository_owner`, not just match on `sha` globally. Consider passing the verified organization down from `WebhooksController` into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` so handlers can enforce this binding explicitly.

### Proof of Concept
1. Configure Shipit with two GitHub organizations (`OrgA`, `OrgB`) as per `docs/setup.md`'s "Using Multiple Github Applications" section, each tracking at least one stack.
2. As an admin of a repo in `OrgA`, use the GitHub Status API to set a commit status on your own repo but with `sha` equal to a known commit SHA of a stack tracked under `OrgB`.
3. GitHub delivers a `status` webhook, signed with `OrgA`'s `webhook_secret`, to Shipit's `/webhooks` endpoint.
4. `WebhooksController#verify_signature` succeeds (signature is valid for `OrgA`).
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matches the `OrgB` commit, and creates a `Status` on it — potentially triggering `ContinuousDeliveryJob` for `OrgB`'s stack. [7](#0-6)

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
