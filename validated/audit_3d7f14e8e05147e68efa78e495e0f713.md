The vulnerability class in the report — a caller-controlled field (`route`) being trusted and acted upon without validating it against the values that were actually authorized (`trade.sellToken`/`trade.buyToken`) — maps to a concrete authorization binding break in this engine: an `ApiClient` token's authorized stack scope vs. the stack it is actually allowed to touch.

### Title
Stack-scoped API token can read any stack's CI/deploy status via CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the inherited `#stack` resolver to bypass the stack-scoping enforced by `Shipit::Api::BaseController`, allowing an `ApiClient` token that is authorized (`stack_id`-scoped) for one stack to read CI/deploy status of any other stack by simply changing the `stack_id` request parameter.

### Finding Description
`Shipit::Api::BaseController` enforces stack-scoping for every API endpoint through: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the token is scoped to a specific stack, and `stack` resolves `params[:stack_id]` only within that restricted set. This is the binding: `ApiClient#stack_id` (the stack the token authorizes) must equal the stack that is actually read.

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 
Instead of using the scoped `stacks` collection, it calls `Stack.from_param!(params[:stack_id])` directly against the global `Stack` table. The `require_permission :read, :stack` before_action only checks that the token's `permissions` array contains `read:stack` via `ApiClient#check_permissions!`: [3](#0-2) 
It never checks `current_api_client.stack_id` against the requested stack. Since `check_permissions!` is scope-name-based (`"read:stack"`) rather than instance-based, any token with `read:stack` permission — including ones intentionally scoped to a single stack, such as the "CCMenu Client" created per-stack — can be replayed against an arbitrary `stack_id`.

The intended design is visible in `CCMenuUrlController`, which mints a token scoped to exactly one stack: [4](#0-3) 
That per-stack scoping is meaningless in `CCMenuController` because the `stack_id` param is trusted independently of the token's `stack_id`.

### Impact Explanation
Before the break: a "CCMenu Client" token minted for stack A (`ApiClient#stack_id == A.id`) is only usable, per `BaseController#stacks`, to read stack A. After the break: the same token, presented against `/api/stacks/:stack_id/ccmenu.xml?token=...` with any other `stack_id`, resolves and renders that other stack's latest deploy/rollback status (build success/failure, lock state, activity) via `Stack.from_param!`. This is an authenticated-but-unscoped cross-stack disclosure of deploy/build state, i.e., an escalation beyond the authorization the token was granted — the category explicitly named in scope ("a stack a token authorises versus a stack it touches").

### Likelihood Explanation
Any holder of a valid `read:stack`-scoped CCMenu token (a credential routinely embedded in CI dashboard tools, distributed as a plain URL with the token in the query string per `CCMenuUrlController#fetch`) can trivially swap the `stack_id` path segment to enumerate and read status for every other stack in the installation. No special privilege beyond possessing one legitimate scoped token is required.

### Recommendation
In `CCMenuController`, resolve `stack` through the inherited, properly-scoped `stacks` collection (i.e., remove the private `stack` override, or change it to `stacks.from_param!(params[:stack_id])`) so that a stack-scoped `ApiClient#stack_id` is enforced identically to every other API controller.

### Proof of Concept
1. As an authenticated user, visit `/stacks/A/ccmenu_url` (`CCMenuUrlController#fetch`) to mint a `read:stack`-scoped token `T` bound to stack A (`ApiClient.stack_id == A.id`).
2. Request `GET /api/stacks/A/ccmenu.xml?token=T` — succeeds, returns stack A's status (expected).
3. Request `GET /api/stacks/B/ccmenu.xml?token=T` for an unrelated stack B — `authenticate_api_client` accepts `T` (valid token), `require_permission :read, :stack` passes (`T` has `read:stack` in its permissions list), and `stack` resolves via `Stack.from_param!('B')` regardless of `T.stack_id == A.id`. Stack B's deploy/build status is returned despite `T` never being authorized for stack B.
