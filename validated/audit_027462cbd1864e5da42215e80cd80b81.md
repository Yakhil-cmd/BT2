Confirmed: there is no persistent, contract-wide map tracking previously-consumed L1 Bitcoin lockup outpoints. The only outpoint dedup, `seen-outpoints` in `verify-l1-lockups`/`validate-l1-lockup`, is a local `(list 10 …)` accumulator scoped to a single call's `fold`. No map such as `used-l1-outpoints` exists in `pox-5.clar` [1](#0-0) , and the same real Bitcoin UTXO can be re-presented in a later, separate `register-for-bond` call once the staker's prior bond position has ended, since `register-for-bond`'s only reuse guard is `ERR_ALREADY_REGISTERED`, which blocks only an *overlapping* existing membership, not reuse of the underlying Bitcoin proof [2](#0-1) .

### Title
Unbounded replay of a spent L1 BTC lockup proof double-counts sats across successive bonds - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond`'s L1 path credits `sats-total` purely from a Bitcoin merkle-inclusion proof of a historical transaction output, with no persistent record of which (txid, output-index) pairs have already been used to back a bond. The dedup check (`seen-outpoints`, `ERR_DUPLICATE_LOCKUP_OUTPOINT`) only prevents reuse *within a single call*, not across calls or across time.

### Finding Description
`verify-l1-lockups` folds over the caller-supplied outputs via `validate-l1-lockup`, which checks: the lockup script matches the staker's committed timelock script, the amount matches, the header authenticates against the burnchain (`verify-block-header`), the merkle proof is valid, and the outpoint hasn't appeared twice *in this same list* [3](#0-2) . Nowhere is it checked that this specific Bitcoin outpoint has never been submitted to pox-5 before, in any prior `register-for-bond` call, by this staker or (since the output's script is staker-specific, at minimum by this staker across multiple bonds).

Once a staker's bond matures or is exited (`unstake-sbtc`/timelock maturity on the Bitcoin side), `existing-membership` no longer overlaps a new bond, so `bond-overlaps-new-position?` permits a fresh `register-for-bond` call [2](#0-1) . The staker can supply the exact same `tx`/`header`/`leaf-hashes` from their original, now-historical Bitcoin lockup transaction. `validate-l1-lockup` re-derives the same script hash, the same txid, the same amount, and the same valid merkle proof — all of which are static facts about a transaction that was mined once — and re-credits `sats-total` for a brand-new bond, with no on-chain (Stacks-side) mechanism verifying the underlying BTC is still actually locked/unspent. This lets a single real BTC lockup (a single, finite pool of sats) be counted as collateral for bond after bond indefinitely, since Clarity/pox-5 has no way to check current UTXO-spent status and doesn't persist a "consumed" flag.

This mirrors the Nomad bug class at the level of "acceptable proof" checks: Nomad's replica trusted a *root-equality* check that could be satisfied more than intended due to missing/reset replay-prevention state; here, pox-5 trusts a *merkle-inclusion* proof of BTC custody with no cross-call replay-prevention state, so a stale/already-spent commitment is accepted as fresh collateral repeatedly.

### Impact Explanation
Each successful `register-for-bond(L1)` call credits `sats-total` into `protocol-bonds-total-staked`, sets `amount-sats` on the membership, and factors into `min-ustx-for-sats-amount` and signer-weight/reward-eligibility computations. Replaying the same BTC lockup proof across sequential bonds double-counts (in fact, N-times-counts) a single real Bitcoin commitment, letting a staker claim reward-eligible collateral and bond membership that is not backed by additional locked BTC. This is a double-counting-of-a-commitment finding (Critical impact per the given rubric), since the same sats are treated as valid collateral for multiple, sequential bond terms without any corresponding new BTC lock.

### Likelihood Explanation
No privileged role is needed — any unprivileged staker who once completed a legitimate L1 lockup can reuse the exact same public, mined Bitcoin transaction data indefinitely for future `register-for-bond` calls, since all inputs (`tx`, `header`, `leaf-hashes`, `tx-index`, `tx-count`) are already public once the original transaction was broadcast and once used successfully. The only friction is that the staker's existing bond must not overlap the new one, which is a normal state reached by simply waiting for a bond to mature — a routine, always-reachable path, not requiring any BTC-side action at all.

### Recommendation
Add a persistent map (e.g., `used-l1-lockup-outpoints`) keyed by `(txid, output-index)` (or by staker + outpoint) that is checked and set inside `validate-l1-lockup`/`verify-l1-lockups`, rejecting any outpoint that has ever been credited toward any bond by any staker, not just within the current call's `seen-outpoints` list.

### Proof of Concept
1. Staker locks `X` sats in the canonical P2WSH timelock output for `unlock-burn-height` `H1`, matching `construct-lockup-output-script(staker, H1, staker-unlock-bytes, early-unlock-bytes)`.
2. Staker calls `register-for-bond(bond-index=A, ..., btc-lockup=(ok {outputs: [thatOutput], ...}))`; `validate-l1-lockup` succeeds, `sats-total = X` is credited, bond A membership is created [4](#0-3) .
3. Bond A matures (BOND_LENGTH_CYCLES pass); `existing-membership` no longer overlaps a later bond B, satisfying `bond-overlaps-new-position?`.
4. Staker calls `register-for-bond(bond-index=B, ..., btc-lockup=(ok {outputs: [the SAME output as step 1], ...}))`. `validate-l1-lockup` re-validates the same script/amount/merkle-proof/header (all still true, since these are static facts about a past transaction) and again credits `sats-total = X` toward bond B — with no map lookup anywhere rejecting the replayed outpoint across calls.
5. The staker now holds bond-B membership backed by `X` sats of "L1 collateral" without having locked any additional BTC beyond the original single lockup.
