### Title
Cross-repository CI-state contamination via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, without scoping to the repository that authenticated the webhook. Since `verify_signature` only proves the request came from the org owning the sha's *own* GitHub repository, and shared ancestor commits between a fork and its upstream have identical shas, a webhook from a fork's org can update `statuses` on the upstream repository's `Commit` row for that shared sha.

### Finding Description
The broken binding: `repository_that_authenticated_webhook == repository_owning_commit_row_updated` is expected but not enforced. `WebhooksController#verify_signature` only checks that the signature matches `Shipit.github(organization: repository_owner)` for the org named in the payload's `repository.owner.login` [1](#0-0) , i.e. it authenticates that "org X sent this webhook", not that "org X owns every `Commit` row with this sha".

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This is unscoped by repository/stack — it matches every `Commit` row across all `Repository`/`Stack` tenants sharing that sha. Contrast with the base `Handler` class, which provides a `stacks` helper explicitly scoped by `Repository.from_github_repo_name(repository_name)` [3](#0-2) , a pattern other handlers (e.g. `push_handler.rb`, the `pull_request/*` handlers) use to constrain effects to the authenticated repository — but `StatusHandler` does not use `stacks` at all, bypassing this scoping entirely.

Since `Commit` rows are keyed by `sha` + `stack_id` (via `belongs_to :stack`) with no uniqueness constraint tying sha to a single repository [4](#0-3) , an upstream repo and its fork — each onboarded as separate `Shipit::Repository`/`Stack` records with independent `webhook_secret` verification — can each have a `Commit` row for the same shared ancestor sha (normal fork topology). The attacker controls only their fork's webhook delivery (push a branch containing the shared ancestor sha to their fork and trigger CI, or directly `POST /webhooks` with a valid signature for their own org since they own their fork's GitHub App/webhook config). GitHub sends a `status` event from the fork's org, which passes `verify_signature` (correctly, since it is genuinely from the fork's org), reaches `StatusHandler`, and `Commit.where(sha: params.sha)` matches both the fork's own `Commit` row and the upstream's `Commit` row for that sha, calling `create_status_from_github!` on both — mutating the upstream tenant's CI state with attacker-controlled `state`/`description`/`target_url`/`context`.

No existing guard prevents this: `verify_signature` validates webhook authenticity per-org but not per-commit-ownership; `ExplicitParameters` schema only validates payload shape, not scope; there is no `repository_id`/`stack_id` filter added before `create_status_from_github!` is invoked.

### Impact Explanation
An attacker who controls a fork can inject fabricated CI status (success/failure/pending, arbitrary description/target_url) onto the upstream repository's tracked `Commit` for any shared ancestor sha. Since `Commit#deployable?` and `Stack` continuous-delivery logic depend on status state [5](#0-4)  and `add_status` schedules merges/continuous delivery on status changes [6](#0-5) , this can influence deploy/merge gating on the upstream repo's Shipit-tracked commit — a payload for one (attacker-controlled) repository mutating another (victim) repository's commit/CI state, matching the "Critical" category of cross-tenant record mutation. It is repeatable against any upstream/fork pair sharing an ancestor sha, and against any Shipit tenant onboarding both an upstream and permitting forks to be onboarded (or simply sharing common history, e.g. via a merged-in vendor/library commit).

### Likelihood Explanation
Preconditions: both the upstream and the fork must be onboarded as separate `Shipit::Repository` records in the same Shipit installation, each with its own working GitHub App/webhook_secret for their respective owning orgs — a normal, expected Shipit deployment pattern for open-source or multi-fork setups. The attacker only needs control of their own fork (push access, standard for any GitHub user) and does not need any Shipit credential. Cost is trivial: push a commit/tag to a shared ancestor sha or replay a `status` webhook naturally generated by fork CI. Fully repeatable, no rate limiting needed since it's triggered by normal git/CI activity on the attacker's own fork.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository that authenticated the webhook, e.g. via the `stacks` helper already provided by `Handler`:
```ruby
def process
  stacks.flat_map { |stack| stack.commits.where(sha: params.sha) }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ensures only commits belonging to stacks under the repository named in the authenticated webhook payload are updated.

### Proof of Concept
Minitest plan (no live GitHub):
1. Create two `Stack`/`Repository` fixtures with distinct repository full names, e.g. `upstream/repo` and `attacker/fork`.
2. Create `Commit` records with the same `sha` value under each stack (`Commit.create!(stack: upstream_stack, sha: shared_sha, ...)` and `Commit.create!(stack: fork_stack, sha: shared_sha, ...)`).
3. Build a `status` webhook payload with `repository.full_name = "attacker/fork"`, `sha: shared_sha`, `state: "success"`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (bypassing controller-level signature verification, which is legitimately satisfied by the attacker's own org in a real attack).
5. Assert: `upstream_commit.reload.statuses.last.state == "success"` — i.e., the upstream repository's commit was updated despite the webhook being authenticated only for `attacker/fork`. Compare against expected binding `webhook_authenticated_repo (attacker/fork) == commit_owning_repo (upstream/repo)`, which is false, demonstrating the violation.
6. Also assert `fork_commit.reload.statuses.last.state == "success"` to show the legitimate update also occurred, proving both rows were mutated from a single fork-authenticated webhook.
