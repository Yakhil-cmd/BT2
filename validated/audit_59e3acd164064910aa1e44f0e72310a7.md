## Finding

### Title
Stale approval votes from removed owners are not purged when multisig owner set changes, letting `validate_multisig_transaction` execute against a wrong approval set - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

### Summary
The external report's bug class is: a contract lets a state-affecting parameter (`protocolSafetyFee`, `vestingPeriod`) be updated via `setParams` without first accruing/settling the pre-existing state, so already-earned state is evaluated under the wrong parameters. The Aptos-native analog is in `multisig_account.move`: the owner set and `num_signatures_required` can be changed via `update_owner_schema` (invoked by `add_owners`, `remove_owners`, `swap_owner(s)`, `update_signatures_required`) at any time, but pending `MultisigTransaction.votes` are never reconciled against the new owner set before that pending transaction is later validated for execution.

### Finding Description
`update_owner_schema` [1](#0-0)  mutates `multisig_account_ref_mut.owners` (add/remove) and optionally `num_signatures_required`, but it never iterates over `multisig_account_ref_mut.transactions` to purge votes cast by owners who are being removed. Each `MultisigTransaction` stores `votes: SimpleMap<address, bool>` recorded independently via `vote_transanction` [2](#0-1) .

When a transaction is later executed, `validate_multisig_transaction` — called both during mempool VM validation and at execution time, per its own doc comment — re-checks `can_be_executed`/`can_execute` and tallies `num_approvals_and_rejections` [3](#0-2) . This is functionally the same admission-boundary problem as the Angle finding: the approval count that determines whether a transaction is allowed to execute (an admission decision) is derived from state (`votes`) that was never "settled"/reconciled at the moment the owner set (a decisive parameter) changed. If a removed owner's earlier "approve" vote remains in `transaction.votes` and is not filtered against the *current* owner list when counting, a pending transaction can reach the required signature threshold using a vote from an address that is no longer an authorized owner — i.e., the approval-set validation would accept the wrong signer set, which is the exact bug class the Admission Pivots call out ("Authenticator, WebAuthn, multisig, or approval validation accepting the wrong signing material or wrong approval set").

### Impact Explanation
If stale votes are counted, a multisig transaction could execute as the multisig account's signer even though it never received the intended number of approvals from the account's *current* owner set — this is unauthorized execution under the wrong signer set, directly matching the Admission Impact Gate's first bullet. Because `validate_multisig_transaction` gates whether the transaction is even admitted for execution (it's invoked in the prologue used for both mempool validation and execution), a wrong approval count is a pre-validation mismatch that lets a transaction which should fail admission execute and commit.

### Likelihood Explanation
I was not able to fully verify, within the available tool budget, whether `num_approvals_and_rejections` (the vote-tallying function) filters `transaction.votes` against the *current* `owners` vector before counting, or whether it blindly sums all entries in the `SimpleMap`. I confirmed that `update_owner_schema` itself performs no cleanup of any transaction's `votes` map when owners are removed. If `num_approvals_and_rejections` does not cross-check vote authors against the live owner list, the vulnerability is directly exploitable by any set of owners that (a) approves a transaction, (b) later removes one of the approving owners for an unrelated reason, and (c) executes the still-pending transaction — the removed owner's vote would still count toward the threshold. This should be verified by reading the implementation of `num_approvals_and_rejections`, `can_be_executed`, and `can_execute` before treating this as confirmed; I flag it as the strongest local candidate but not fully proven.

### Recommendation
- When owners are removed in `update_owner_schema`, either (a) purge/invalidate votes cast by removed owners across all pending transactions, or (b) ensure `num_approvals_and_rejections`/`can_be_executed`/`can_execute` only count votes from addresses present in the *current* owner list at evaluation time.
- More generally, apply the Angle-style mitigation: before changing `owners` or `num_signatures_required`, "settle" (reconcile) any pending transactions' vote tallies against the new configuration rather than lazily re-evaluating stale vote maps at execution time.

### Proof of Concept
Conceptual PoC (pending verification of `num_approvals_and_rejections`):
1. Create multisig account with owners `{A, X, B}`, `num_signatures_required = 2`.
2. Owner `A` calls `create_transaction` (implicit self-approval) and `X` calls `approve_transaction` — 2 approvals recorded in `transaction.votes`.
3. Owners execute `remove_owners([X])` via the normal multisig flow, updating `owners = {A, B}` — `transaction.votes` for the earlier pending transaction is untouched (per `update_owner_schema` code).
4. `A` (or `B`) invokes execution of the earlier transaction; `validate_multisig_transaction` tallies votes, potentially still counting `X`'s stale approval, and the transaction executes despite `X` no longer being an authorized owner. [1](#0-0) [2](#0-1) [3](#0-2)

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
