This confirms the vulnerability. `Shipit::Api::BaseController#stack` correctly scopes lookup through `stacks.from_param!`, where `stacks` filters by `current_api_client.stack_id` when the client is stack-scoped [1](#0-0) . `Shipit::Api::CCMenuController` overrides both `authenticate_api_client` (to accept a `params[:token]` instead of Basic auth) and `stack` (to call `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scoping helper entirely) [2](#0-1) . `ApiClient#check_permissions!` only checks that the required permission string (e.g. `read:stack`) is present in `permissions`; it has no awareness of which stack is being requested [3](#0-2) .

### Title
Stack-scoped API token can read CCMenu status of any stack, bypassing its `stack_id` scope - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController#stack` does not honor `ApiClient#stack_id` scoping the way every other API controller does, letting a token that was only authorized for one stack read the deploy/build status of any stack in the installation.

### Finding Description
`ApiClient` records can be scoped to a single stack via `stack_id`, and `Shipit::Api::BaseController#stacks`/`#stack` enforce that scope for every controller that inherits the default implementation: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` followed by `stacks.from_param!(params[:stack_id])` [1](#0-0) . This is the invariant the app relies on: `token.stack_id == stack_id_being_served` whenever a client is not global.

`CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, entirely skipping the `stacks` scoping method [4](#0-3) . It also overrides `authenticate_api_client` to accept the token via `params[:token]` (as used by `CCMenuUrlController`, which mints tokens for the CCMenu integration) [5](#0-4) . The `require_permission :read, :stack` before_action only checks that the string `read:stack` is in the token's permission list [3](#0-2) ; it performs no comparison against `stack_id`.

Equality that should hold but doesn't: `current_api_client.stack_id` (the stack the token authorizes) vs. the `stack_id` param actually resolved into `stack` in `CCMenuController#show` (the stack whose data is returned). Every sibling API controller (e.g. `Stack#stack` used by `StacksController`) enforces this equality through `stacks.from_param!`; `CCMenuController` alone does not, exactly mirroring the audit report's pattern of one sibling function having the guard and another lacking it.

### Impact Explanation
Any holder of a stack-scoped `read:stack` token (for example the "CCMenu Client" token generated per-user by `CCMenuUrlController`, or any API client an admin scoped to one stack for least-privilege) can supply a different `stack_id` in the URL and receive that other stack's CCMenu XML — including last build status/label/time, lock status, and repository/environment name — for stacks outside their authorized scope. This is an unauthenticated-for-that-resource read of stack state, matching the High-severity criterion "unauthenticated read of stack state."

### Likelihood Explanation
Any user who legitimately holds a stack-scoped token (a normal, documented feature) can trivially trigger this by changing the `stack_id` segment of the CCMenu URL; no privileged access beyond having any scoped token is required.

### Recommendation
Make `CCMenuController#stack` use the inherited scoping helper instead of resolving directly against `Stack`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the `current_api_client.stack_id` vs. requested `stack_id` equality enforced everywhere else in the API.

### Proof of Concept
1. As an admin, create (or have `CCMenuUrlController` create) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']`, and note its `authentication_token`.
2. Send `GET /api/stacks/<Stack-B-owner>/<Stack-B-name>/<Stack-B-env>/ccmenu?token=<Stack-A-token>` where Stack B is a different stack the token was never scoped to.
3. `authenticate_api_client` accepts the token (valid signature, valid `ApiClient` record) [5](#0-4) ; `require_permission :read, :stack` passes because the token's permission list contains `read:stack` [3](#0-2) ; `stack` resolves Stack B directly via `Stack.from_param!` with no ownership check [4](#0-3) .
4. The response renders Stack B's `deploys_and_rollbacks.last` and status in the CCMenu XML, leaking Stack B's deploy/lock state to a token never authorized for it.
