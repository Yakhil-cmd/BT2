### Title
Attacker-controlled swap routes can inject unauthorized token transfers into a caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
User-supplied `StrategySwap` bytes are forwarded to the configured router without venue or pool allowlisting at the controller boundary. A route can therefore place attacker-deployed contract code below an authorized strategy invocation, where that code can request additional token transfers from the transaction signer. Simulation records those transfers as children of the signer’s authorization tree, and they execute if the signer approves the poisoned tree. The controller’s router settlement checks only cover the controller’s input and output balances, not unrelated assets withdrawn from the caller’s wallet.

### Finding Description
`swap_collateral` accepts a caller-controlled `swap` argument, authenticates the caller, and routes the operation through `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1) 

`swap_tokens` passes the opaque route bytes directly to `SwapAggregatorClient::execute_strategy`. [3](#0-2) [4](#0-3) 

The controller’s protection is limited to one exact controller-to-router token authorization and measured input/output deltas. [5](#0-4) [6](#0-5) 

A `SwapHop` contains a payload-supplied pool address, and venue dispatch calls the selected pool implementation. [7](#0-6) [8](#0-7) 

The repository’s adversarial test demonstrates the resulting authorization behavior: a route-selected pool can call `token.transfer(victim, attacker, amount)`, simulation records it under the victim’s `swap_collateral` authorization entry, and the signed tree permits the transfer. [9](#0-8) [10](#0-9) 

### Impact Explanation
A malicious route can steal arbitrary SEP-41 token balances from the signer, including assets unrelated to the lending position and assets never listed by the protocol. The malicious pool can also satisfy the router’s measured-output requirement, so the lending strategy completes normally while the extra wallet transfer is included in the signer’s authorization tree. This is theft of user funds.

The affected strategy surface includes every controller entrypoint that accepts route bytes: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`.

### Likelihood Explanation
Likelihood is moderate. The attacker cannot unilaterally spend from an account without its signature, but routes are opaque XDR payloads normally produced or selected off-chain. A malicious quote, frontend, route provider, or phishing flow can cause the victim to submit a poisoned route and sign an authorization tree containing the extra transfer. The exploit does not require protocol privileges, leaked keys, contract upgrades, or compromised production contracts.

### Recommendation
Do not allow swap payloads to select arbitrary venue contracts. Maintain a governance-approved pool registry keyed by venue and asset pair, or include a trusted route hash/policy commitment that the router verifies before dispatch. At minimum, enforce venue allowlists for production routes and make wallets/clients reject any signed authorization tree containing children beyond the expected input transfer. The controller should also expose route-verification expectations so integrators do not treat opaque `swap` bytes as safe merely because controller balances and final account risk are checked.

### Proof of Concept
1. Deploy a malicious pool implementing the selected venue’s expected metadata and swap functions. Store `(victim, wallet_token, attacker, steal_amount)` in the pool.
2. In its swap callback, execute:

```rust
token::Client::new(&env, &wallet_token)
    .transfer(&victim, &attacker, &steal_amount);
token::Client::new(&env, &token_out)
    .transfer(&env.current_contract_address(), &router, &required_output);
```

3. Construct a route whose `assets` registry contains the malicious pool, legitimate `token_in`, and `token_out`, and whose instruction selects a venue adapter that invokes the payload’s pool address.
4. Have the victim call `swap_collateral(caller=victim, account_id, current, amount, new, swap=route_xdr)`.
5. The malicious pool receives execution during route dispatch and requests the unrelated wallet-token transfer. Simulation records it as a child of the victim’s `swap_collateral` authorization entry; signing that tree authorizes the theft.
6. The pool simultaneously returns sufficient `token_out`, so the router’s output checks and the controller’s measured-output and account-risk checks pass while the unrelated wallet funds are transferred to the attacker.
