### Title
`is_valid_signed_package()` accepts signed packages that skip on-chain address-definition verification, letting stale/revoked keys authorize AA fund transfers - (File: `formula/evaluation.js`, `signed_message.js`)

### Summary
AAs that hold funds in trust for counterparties (payment channels, order-book exchanges, etc.) authenticate off-chain instructions via the oscript primitive `is_valid_signed_package()`, which delegates to `signed_message.validateSignedMessage()`. When the signed package omits `last_ball_unit`, `validateSignedMessage()` never checks the address's current on-chain definition — it only verifies that the supplied definition hashes to the claimed address. If the address owner has since rotated/changed their address definition (e.g. via `address_definition_change`, for instance after a key compromise), an attacker who still holds the old, now-revoked private key can produce a package that `is_valid_signed_package()` will still accept as valid, exactly as the Alephium bridge accepted forged messages that bypassed the intended authorization checks.

### Finding Description
`is_valid_signed_package(pkg, address)` is implemented in the AA formula evaluator: [1](#0-0) 

Note that the `last_ball_unit` field is only checked *if present* (`typeof signedPackage.last_ball_unit === 'string'`); it is not mandatory. The package is then handed to `signed_message.validateSignedMessage()`.

Inside `validateSignedMessage()`, whether `last_ball_unit` was supplied determines the verification mode via `bNetworkAware`: [2](#0-1) 

When `bNetworkAware` is true, the code looks up the address's actual on-chain definition as of `last_ball_mci` via `storage.readDefinitionByAddress`, so a rotated/updated definition is correctly enforced: [3](#0-2) 

But when `bNetworkAware` is false (no `last_ball_unit` given), the code takes a completely different path that performs **no lookup of the address's current on-chain state at all** — it only checks that the caller-supplied definition hashes to the target address: [4](#0-3) 

Since an Obyte address is defined as `chash160(initial_definition)`, this self-consistency check will always succeed for the address's *original* definition, even if the address owner has since executed an `address_definition_change` to rotate keys (e.g., because the original private key was compromised or a cosigner was removed). The verifier (`is_valid_signed_package`) has no way to know whether the definition it just accepted is still the address's authoritative one, because it never consults `last_ball_mci`/on-chain state in this mode.

This is used directly by AA templates to authorize the release of AA-held funds based purely on an off-chain-obtained signed message, e.g. the shipped payment-channel example: [5](#0-4) [6](#0-5) 

The peer's identity is authenticated *solely* by `is_valid_signed_package(trigger.data.sentByPeer, $addressA/$addressB)`. There is nothing in the oscript or in the AA's constructor that forces the client to supply a `last_ball_unit`, and `is_valid_signed_package` itself does not require it, so an attacker can freely construct a package without `last_ball_unit` to force the vulnerable, non-network-aware code path.

### Impact Explanation
Any AA that authorizes state transitions or fund payouts using `is_valid_signed_package()` against a peer address whose definition may change over time (multisig wallets, wallets that rotate keys after compromise, shared/vote-controlled addresses) can be tricked into accepting authorization from a stale, no-longer-valid key. This directly maps to "concrete unauthorized spending" / "AA fund loss": an attacker holding an old, revoked signing key for a counterparty address can forge a state update (e.g., a payment-channel `sentByPeer` message or an `order_book_exchange` order) that the AA will honor as if it were freshly and validly authorized, draining AA-held funds — the same root-cause class (backend/verifier accepting forged authorization because current authoritative state isn't checked) as the Alephium bridge incident.

### Likelihood Explanation
Exploitation requires: (1) an AA design relying on `is_valid_signed_package()` for authorization against an address capable of definition changes (a normal, supported Obyte usage pattern, exemplified by the shipped `payment_channels.oscript` and `order_book_exchange.oscript` samples), and (2) possession of an old/rotated key for that address. Since the AA/oscript language does not force callers to include `last_ball_unit`, and no built-in check rejects packages without it, an attacker fully controls whether the vulnerable code path is used — likelihood is driven entirely by whether a targeted AA's counterparty ever rotates keys, which is a realistic and even security-motivated event (e.g., in response to suspected key compromise).

### Recommendation
Require `last_ball_unit` (i.e., always run in `bNetworkAware` mode) whenever `is_valid_signed_package()` is evaluated inside AA/oscript context, or otherwise force `validateSignedMessage()` to always resolve and check the address's up-to-date definition (via `storage.readDefinitionByAddress` against the current stable MCI) regardless of whether `last_ball_unit` was supplied, so that a superseded/rotated address definition can never be used to authenticate a signed package.

### Proof of Concept
1. Address `P` is initially defined as `["sig", {pubkey: K1}]`; attacker obtains `K1` (e.g., leaked/compromised).
2. Owner of `P` detects the compromise and issues an `address_definition_change` unit switching `P`'s active definition to `["sig", {pubkey: K2}]`.
3. Attacker (still holding `K1`) crafts a `signed_message` package for the payment-channel AA:
   ```
   {
     signed_message: { channel: <AA_address>, period: <current_period>, amount_spent: <favorable_value> },
     authors: [{ address: P, definition: ["sig", {pubkey: K1}], authentifiers: { r: <sig_by_K1> } }]
     // note: no last_ball_unit field
   }
   ```
4. AA evaluates `is_valid_signed_package(trigger.data.sentByPeer, P)`. Since `last_ball_unit` is absent, `signed_message.validateSignedMessage` takes the `else` branch at `signed_message.js:241-252`, verifies only `chash160(["sig",{pubkey:K1}]) === P` (true, since that was `P`'s original definition), and accepts the signature — despite `K1` no longer being `P`'s authoritative key on-chain.
5. The AA processes the forged package as legitimate, releasing channel funds according to the attacker-controlled `amount_spent`, achieving unauthorized fund loss from the AA.
