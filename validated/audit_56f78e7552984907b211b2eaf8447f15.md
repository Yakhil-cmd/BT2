### Title
Cross-organization commit-status forgery bypasses signature-org binding, enabling unauthorized continuous deployment - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used to validate an inbound webhook based on the organization derived from the payload's `repository.owner.login` (or `organization.login`) field. Once the signature check passes, the parsed JSON is dispatched to a handler by event type. `StatusHandler`, however, applies the resulting `status` event to **any** `Commit` in the entire database matching the payload's `sha`, with no check that the commit's stack/repository belongs to the organization whose secret was used to authenticate the request. This breaks the binding: "organization that authenticated" == "repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the verification key like this: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret`/GitHub App config per organization, a documented multi-tenant configuration: [3](#0-2) 

Once the signature is verified for organization `A` (`repository_owner`), the raw JSON payload is dispatched purely by `X-Github-Event` type: [4](#0-3) 

`StatusHandler#process`, unlike other handlers (e.g. `PushHandler`, which scopes to `stacks` derived from `repository.full_name`), performs an unscoped, global lookup by commit SHA and applies the status to every matching commit, regardless of which repository/organization it belongs to: [5](#0-4) 

Compare this to `Handler#stacks`, which other handlers use to scope actions to the repository named in the payload: [6](#0-5) 

`StatusHandler` never calls `stacks` or `repository_name` — it is not bound to any repository at all. Since `Commit#sha` is not unique per organization/installation and the same Shipit instance can host stacks for many organizations, any request that passes signature verification for **any one** configured organization can forge a status for a commit belonging to a **completely different** organization's stack.

`create_status_from_github!` (via `Commit#add_status`) has real side effects: it fires `commit_status`/`deployable_status` hooks and schedules merges/CI enablement: [7](#0-6) 

`Status#enable_ci_on_stack` and `Status#schedule_continuous_delivery` are triggered on creation: [8](#0-7) [9](#0-8) 

And a commit transitioning to `success` state with `continuous_deployment` enabled on the stack actually creates a `Deploy` and enqueues `ContinuousDeliveryJob`, per the test suite behavior: [10](#0-9) 

### Impact Explanation
Being able to inject a fabricated "success" CI status for an arbitrary commit SHA belonging to a repository/organization the attacker does not control — merely by holding valid webhook credentials for any *other* organization configured on the same shared Shipit instance — satisfies CI gating and can trigger an unauthorized deploy on that victim stack (`schedule_continuous_delivery`), or unblock merges (`stack.schedule_merges`). This crosses the "unauthorized deploy" / "cross-repository writes" boundary defined as Critical impact.

### Likelihood Explanation
Requires the attacker to control (or have access to trigger) a webhook whose signature validates against *any one* of the organizations configured on a multi-tenant Shipit install (a documented, supported deployment mode), and to know/guess the target commit's SHA (SHAs of public/forked/mirrored repositories are often discoverable). No access to the victim organization's GitHub account, webhook secret, or Shipit session is required. This is a realistic scenario for shared/multi-org Shipit deployments.

### Recommendation
Scope `StatusHandler#process` (and any other handler that doesn't already do so) to the repository named in the payload and cross-check that repository against the organization whose secret validated the signature, mirroring the `stacks`/`repository_name` scoping already used by `PushHandler` and the `pull_request` handlers.

### Proof of Concept
1. Configure Shipit with `github:` containing two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (as documented in `docs/setup.md`).
2. Attacker controls/administers `org-a`'s GitHub App/webhook (legitimate for their own tiny repo tracked by the same Shipit instance) and thus can compute a valid `X-Hub-Signature` using `org-a`'s `webhook_secret`.
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login` is `org-a` (so `verify_signature` selects and validates against `org-a`'s secret), but with `sha` set to a commit SHA that actually belongs to a stack owned by `org-b` (a repository/org the attacker has no access to), and `state: "success"`.
4. `verify_signature` passes because it only checks the signature against `org-a`'s secret; it never validates that `sha`/commit actually belongs to `org-a`.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, finds the `org-b` commit, and creates a `success` `Status` on it.
6. If `org-b`'s stack has `continuous_deployment` enabled, this triggers `Deploy`/`ContinuousDeliveryJob` for a repository the attacker never had access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
