## Title
Signature malleability in oscript `is_valid_sig` / `vrf_verify` PEM-based ECDSA verification allows replay of "single-use" signature-gated AA logic - (File: `signature.js`)

### Summary
The `is_valid_sig(message, pem_key, signature)` and `vrf_verify(seed, proof, pem_key)` oscript primitives are implemented on top of `signature.verifyMessageWithPemPubKey()`, which for any non-secp256k1 curve falls back to Node's `crypto.createVerify('SHA256').verify(...)` [1](#0-0) . Unlike the dedicated secp256k1 path, this generic ECDSA verification path does not normalize the signature's `s` value (no low-S enforcement), so it accepts both `(r, s)` and the mathematically equivalent `(r, n-s)` as valid signatures for the same message/key — the classic malleability defect referenced in the external report (SWC-117 / OpenZeppelin ECDSA advisory).

### Finding Description
`signature.js` exposes two verification code paths:
- The address/unit/device signature path (`verify()`), which uses the `secp256k1` npm binding's `ecdsaVerify` [2](#0-1) . libsecp256k1's `secp256k1_ecdsa_verify` rejects non-normalized (high-S) signatures by design, so this path (used by `sig` authentifiers in `definition.js` and by device/hub messages in `network.js`/`device.js`) is not malleable.
- The generic PEM-key path (`verifyMessageWithPemPubKey`), used exclusively by the oscript builtins `is_valid_sig` and `vrf_verify` in `formula/evaluation.js` [3](#0-2)  and [4](#0-3) . For any curve other than the specially-handled secp256k1-DER case, it calls `crypto.createVerify('SHA256').verify({key: pem_key}, signature, encoding)` directly [5](#0-4) , with no post-processing to enforce a canonical low-S signature or strict DER re-encoding check.

Even the secp256k1-specific PEM branch (`verifyMessageWithSecp256k1PemPubKey`) actively *normalizes* the signature before verifying via `ecdsa.signatureNormalize(rawCompact)` [6](#0-5) , which means it will accept whichever of the two symmetric `s` values (and their alternate DER encodings) is submitted, confirming that both variants are treated as valid for a given message.

Because `is_valid_sig`/`vrf_verify` are the intended building blocks for AA authors to implement custom off-chain-signature-gated logic (e.g., claim tickets, oracle attestations, bridge withdrawal authorizations) inside `oscript`/`ojson` AA definitions, any AA that treats a particular signature value as a unique, single-use token (for example storing `signature` or its hash in a state variable to prevent re-processing of the same signed message) can be tricked: an attacker who has observed one valid signature for a message can derive a second, byte-different but equally valid signature for the exact same `(message, pem_key)` pair and resubmit it in a new trigger, bypassing an "already used" check keyed on the literal signature value.

### Impact Explanation
Any AA that relies on `is_valid_sig`/`vrf_verify` plus a state-variable dedup keyed on the raw signature bytes to gate one-time fund releases (e.g., "pay bearer of a valid signature over this claim, once") can have that guard bypassed via the malleable counterpart signature, allowing the same authorization to be replayed and draining AA-held funds — an AA fund loss condition.

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender: this only requires posting a trigger unit whose `data` includes the alternate `(r, n-s)` signature and invoking the AA's `is_valid_sig`/`vrf_verify`-gated branch. No privileged access, hub/peer compromise, or key leak is needed — only that the AA design uses raw signature bytes as an anti-replay identifier, a natural pattern for signature-authorized AA workflows.

### Recommendation
In `signature.js`, before calling `crypto.createVerify(...).verify(...)` in `verifyMessageWithPemPubKey`, normalize/validate the ECDSA signature: parse `r`/`s` from the DER signature and reject (or canonicalize to) the low-S form for all supported curves, mirroring what is already done for the secp256k1 PEM branch, and additionally enforce strict DER encoding (reject non-minimal encodings) so a single logical signature maps to exactly one accepted byte representation. Document for AA authors that `is_valid_sig`/`vrf_verify` signatures must not be relied upon as unique anti-replay identifiers unless this normalization is guaranteed.

### Proof of Concept
1. Generate an EC key pair on a non-secp256k1 curve (e.g. `prime256v1`) and sign message `M`, producing DER signature `S1 = (r, s)`.
2. Compute `s' = n - s` (curve order minus `s`), re-encode as DER signature `S2 = (r, s')`.
3. Call `is_valid_sig(M, pem_key, S1)` and `is_valid_sig(M, pem_key, S2)` from an oscript AA formula (as exercised by `test/pem_sig.test.js`, e.g. the `prime256v1`/`secp224r1` test cases) — both evaluate to `true` via `signature.verifyMessageWithPemPubKey` [5](#0-4) .
4. In an AA that stores `var['claimed_' + signature] = true` after accepting `S1` to gate a one-time payout, an attacker resubmits with `S2`; since it's a different string, the dedup check passes and the payout logic executes a second time.

```javascript
function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}
```

```javascript
function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
```
