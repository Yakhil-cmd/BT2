### Title
Unauthorized Binding of Arbitrary `pool_creator` Identity in `initialize_with_permission` Enables Cross-Account Creator-Fee Hijack - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` accepts a fully attacker-controlled `creator` account with no signer requirement and no constraint tying it to the transaction `payer` or to the `permission` PDA that gates pool creation. This unchecked value is written directly into `PoolState.pool_creator`, which is the sole authorization anchor used later by `collect_creator_fee` and `collect_creator_fee_permissionless` to route the pool's accumulated creator-fee stream. This mirrors the FreeScout root cause: an attacker-supplied identifier (`creator`, analogous to `customer_id`) is used to bind privileged, persistent state without verifying the caller is authorized to make that binding.

### Finding Description
In `InitializeWithPermission`, the `payer` is required to be a `Signer` and must hold a valid `permission` PDA derived from `[PERMISSION_SEED, payer.key()]`: [1](#0-0) 

However, `creator` is declared as a plain, unconstrained `UncheckedAccount`: [2](#0-1) 

Unlike `initialize.rs`, where the analogous field is a `Signer` and therefore self-attested: [3](#0-2) 

`initialize_with_permission` takes this arbitrary, non-signing `creator` pubkey and writes it verbatim into the persistent `PoolState.pool_creator` field via `pool_state.initialize(...)`: [4](#0-3) 

That field is later the sole authorization gate for who can claim accumulated creator fees: [5](#0-4) 
and the destination for permissionless collection, where the payer only funds the ATA but the tokens go to whatever address was recorded as `pool_creator`: [6](#0-5) 

Because `creator` is never checked to equal `payer`, never required to sign, and never cross-checked against the `permission` account that authorized the call, a permissioned payer can silently attribute pool ownership/fee-earning rights for a newly created pool to any third-party pubkey they choose — or, conversely, an attacker who only controls the `payer`/`permission` role can set `creator` to their own separate wallet while using someone else's or a shared liquidity/fee infrastructure, decoupling the permission check from the actual privileged identity the protocol intends to record.

### Impact Explanation
The `pool_creator` field controls an ongoing, unauthorized privileged effect: all creator-fee revenue accrued on every trade against the pool is routed based on this attacker-chosen value, with no verification step at pool creation time that the entity is aware of or consents to being named creator, nor that it is the same principal that satisfied the `permission` gate. This breaks the authorization invariant that "only the party proven eligible via `permission` can be recorded as the fee-earning creator," directly paralleling the FreeScout flaw where a caller-supplied identifier bypassed an authorization boundary to attach state to an unintended principal.

### Likelihood Explanation
`initialize_with_permission` is reachable by any account holding (or having been granted) a `Permission` PDA, and `creator` is a completely free-form account slot supplied in the same transaction with no additional signature or cross-check — making the manipulation trivial to trigger in a single call with attacker-chosen accounts and data.

### Recommendation
Require `creator` to either be a `Signer` (as in `initialize.rs`) or add an explicit `constraint = creator.key() == payer.key()` (or a constraint tying it to a field on the `permission` account) so that the `pool_creator` binding can only be set to a principal that has actually authorized the association.

### Proof of Concept
1. Attacker (or any actor holding a valid `permission` PDA) calls `initialize_with_permission`, supplying `payer` = their own signer, but `creator` = an arbitrary pubkey `X` (a victim wallet, a PDA they don't control, or any address) — no signature from `X` is required and no constraint rejects the mismatch.
2. `pool_state.initialize(...)` persists `pool_creator = X`.
3. On every subsequent `swap_base_input`/`swap_base_output`, creator fees accumulate in `PoolState.creator_fees_token_0/1`.
4. `collect_creator_fee_permissionless` can be invoked by anyone; it creates ATAs for `creator = X` and transfers the accumulated creator fees there, per `programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs:91-130`, cementing the unauthorized binding's economic effect without `X` ever having consented or signed.
