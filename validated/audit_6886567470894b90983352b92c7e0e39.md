### Title
Unvalidated `omniauth.origin` causes open redirect after GitHub OAuth login - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` redirects the user to `request.env['omniauth.origin']` without validating that it is a same-host, relative path, allowing an attacker to craft a login link (`/github/auth/github/?origin=https://attacker.example/`) that, after the victim completes real GitHub OAuth, sends their authenticated browser straight to an attacker-controlled site.

### Finding Description
The broken binding is: `return_url` used in `redirect_to(return_url)` at [1](#0-0)  should equal a URL scoped to the Shipit host, but it is populated unfiltered from `request.env['omniauth.origin']`, which OmniAuth sets from the `origin` request parameter on the initial `/github/auth/github/` request (this codebase relies on the stock `omniauth-github`/`omniauth` gem's default origin-param handling, required via `omniauth-github` in [2](#0-1) , with no engine-side override or validator).

The engine itself builds and issues login redirects with an `origin` parameter equal to `request.original_url` in `force_github_authentication` — see [3](#0-2)  — but nothing constrains that parameter to same-origin values when an attacker supplies it directly on a crafted link to the OmniAuth request-phase route. `callback` then does:
```
return_url = request.env['omniauth.origin'] || root_path
...
redirect_to(return_url)
```
with no `_url_is_local?`/host allow-list check, at [1](#0-0) .

Exploit flow: attacker sends a victim a link `https://shipit.example/github/auth/github?origin=https://attacker.example/`. Victim, already trusting the Shipit domain, completes the real GitHub OAuth consent (their own account). `callback` sets `session[:user_id]` and `session[:authenticated] = true` for the victim's real account, then issues `redirect_to('https://attacker.example/')`. The victim's browser is silently sent off-host immediately after authenticating to Shipit, while the session cookie itself remains scoped to the Shipit domain (it is not exposed to the attacker page). The existing guards (`force_github_authentication`, `current_user.authorized?`, `Shipit.github_teams` checks) only gate access to *Shipit* pages after login; none of them validate the `origin`/redirect target, and OmniAuth's own CSRF `state` protection only protects the OAuth handshake, not the post-login redirect destination.

### Impact Explanation
This is an open redirect chained onto a real, successful login — the attacker does not obtain the victim's session cookie, `github_access_token`, or any Shipit credential directly, because cookies are host-scoped and not sent to `attacker.example`. The practical impact is limited to using the trusted Shipit domain as a redirector for phishing (forced completion of an OAuth flow immediately followed by navigation to an attacker page that could impersonate Shipit and solicit further action from the now-authenticated victim). It does not by itself allow forging a session, escalating into `Shipit.github_teams`, reading stack/task data, or triggering deploys/rollbacks/merges — those still require the attacker to have or trick the victim into taking further authenticated actions on Shipit itself, which this bug does not grant.

### Likelihood Explanation
Trivial to trigger: any unauthenticated internet user can send a victim a link with `origin=<external URL>` pointing at the engine's mounted OmniAuth path; no Shipit or GitHub secret is needed, and the victim only needs to click the link and complete a normal GitHub login they'd otherwise perform anyway. Repeatable against any victim/any number of times.

### Recommendation
Validate `return_url` before redirecting — restrict to a relative path (e.g., `Rails.application.routes.recognize_path` check or `URI.parse(return_url).host.blank?`) or an explicit allow-list of the app's own host(s), falling back to `root_path` otherwise, in `GithubAuthenticationController#callback`.

### Proof of Concept
```ruby
test ":callback does not redirect to an attacker-controlled external origin" do
  auth = OmniAuth::AuthHash.new(
    credentials: OmniAuth::AuthHash.new(token: 's3cr3t'),
    extra: OmniAuth::AuthHash.new(raw_info: OmniAuth::AuthHash.new(
      id: 44, name: 'Shipit User', email: 'shipit-user@example.com',
      login: 'shipit-user', avatar_url: 'https://example.com',
      api_url: 'https://github.com/api/v3/users/shipit-user'
    ))
  )
  @request.env['omniauth.auth'] = auth
  @request.env['omniauth.origin'] = 'https://attacker.example/'

  get :callback

  assert session[:authenticated]
  # Binding check: return_url (Location header) must equal a Shipit-scoped URL, not the attacker origin
  refute_equal 'https://attacker.example/', response.headers['Location']
end
```
Currently this assertion fails: `response.headers['Location']` equals `'https://attacker.example/'` unfiltered, confirming the divergence.
