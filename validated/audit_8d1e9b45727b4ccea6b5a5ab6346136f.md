### Title
Cross-tenant commit status forgery via `StatusHandler#process` global `Commit.where(sha:)` lookup, unscoped by webhook signer's organization - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` only proves that the HMAC signature matches the `GitHubApp#webhook_secret` for the organization named in `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . `StatusHandler#process`, however, never checks `repository.full_name`/`repository_name` at all — it looks up commits purely by SHA across the entire `commits` table and writes a GitHub status onto whatever `Commit`/`stack` it finds [3](#0-2) . Any tenant that legitimately controls one `GitHubApp`/`webhook_secret` on a shared Shipit instance can therefore forge a "status" webhook that writes a `Status` onto a commit belonging to a completely different organization's stack.

### Finding Description
The binding the code should enforce is: **organization whose `webhook_secret` verified the HMAC == organization that owns the `Commit`/`Stack` being mutated**. Trace:

1. `verify_signature` computes `repository_owner = params.dig('repository','owner','login')` and resolves `github_app = Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that app's `webhook_secret` [1](#0-0) . This only proves the caller knows organization A's secret; it says nothing about which repository/stack the payload's `sha` belongs to.
2. `Handler#repository_name`/`#stacks` exist as the intended way to scope a payload to the owning repository [4](#0-3) , but `StatusHandler#process` does not call either. It only does:
```ruby
Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
``` [3](#0-2) 
No comparison is made between the signing organization and `commit.stack`'s owning organization.
3. `Commit#create_status_from_github!` unconditionally creates the status and can trigger downstream side effects such as `stack.schedule_merges` / continuous delivery scheduling via `add_status` [5](#0-4) [6](#0-5) .

**Attacker's exact request:** Attacker controls (or administers) organization A, which is registered in Shipit with its own `GitHubApp`/`webhook_secret` (a normal, legitimate multi-tenant configuration — the attacker is "unprivileged" with respect to organization B's stacks, but is a normal owner of A's own Shipit integration). They can:
- Read organization B's public commit SHAs from GitHub (no secret needed), or otherwise learn a SHA present in B's stack.
- POST directly to `/webhooks` with `X-Github-Event: status`, a body containing `repository.full_name`/`repository.owner.login` = anything belonging to org A (so `Shipit.github(organization: ...)` resolves to org A's app), `sha` = the target commit in org B's stack, and `state`/`context` of their choosing.
- Sign the raw body with org A's own `webhook_secret`, which they legitimately possess.

Because `StatusHandler#process` never checks `repository_name`/`stacks`, the forged status is attached to org B's `Commit`, potentially triggering `schedule_continuous_delivery`/`schedule_merges` on org B's stack.

Existing guards do not stop this: `verify_signature` only authenticates the signer's own organization, not the target of the payload; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` (`sha`, `state`, etc.) has no repository field to validate against [7](#0-6) ; and `Handler#repository_name`/`#stacks` are simply unused by this handler.

### Impact Explanation
An attacker who legitimately administers one org's Shipit/GitHubApp integration can write arbitrary, fabricated GitHub commit statuses (`success`, `failure`, custom `context`, `target_url`, `description`) onto any other organization's `Commit` records on the same shared Shipit instance, as long as they know or can guess the target SHA (trivial for public repos). Because `Status` changes can flip a commit's `deployable?`/blocking state and schedule continuous delivery (`stack.schedule_merges`, `ContinuousDeliveryJob`), this can force or unblock an unauthorized deploy/merge on a stack the attacker does not own — matching the Critical category "a payload for one repository mutating another's stack, commit... or an unauthorized deploy". This is fully repeatable against any commit SHA and any stack on the instance.

### Likelihood Explanation
Preconditions: Shipit must be running in a multi-tenant configuration with more than one `GitHubApp`/organization configured (documented, common setup), and the attacker must control at least one such organization's Shipit-registered webhook secret (i.e., be a legitimate admin of *some* org on the shared instance — not a Shipit operator, not privileged over org B). Given that, the attack costs one HTTP POST with a correctly computed HMAC using the attacker's own known secret — no brute forcing, no dependency on TLS interception or stolen credentials. This is highly feasible and fully repeatable.

### Recommendation
In `StatusHandler#process` (and any other handler that queries by SHA/global identifiers), scope the `Commit` lookup to the stacks legitimately owned by `repository_name` from the payload, e.g. `stacks.commits.where(sha: params.sha)`, reusing `Handler#stacks`/`#repository_name`, and reject/no-op when the commit's stack's repository does not match the payload's declared repository. More generally, `verify_signature` should also assert that `repository_owner` derived for signature verification matches the repository actually referenced in the handler payload before any handler runs.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two `GitHubApp`s in `Shipit.github_apps` for `org-a` and `org-b`, each with distinct `webhook_secret`.
2. Create `Stack`/`Repository` for `org-b/repo-b` and a `Commit` with a known `sha` belonging to that stack.
3. Build a JSON body: `{"repository": {"full_name": "org-a/repo-a", "owner": {"login": "org-a"}}, "sha": "<org-b commit sha>", "state": "success", "context": "ci"}`.
4. Compute `X-Hub-Signature` using **org-a's** `webhook_secret` over the raw body.
5. POST to `/webhooks` with `X-Github-Event: status` and that signature.
6. Assert `response.status == 200`.
7. Assert equality check both sides: signing organization (`org-a`) does **not** equal the organization owning `sha`'s `Commit`/`Stack` (`org-b`), yet assert a `Shipit::Status` row was created on `org-b`'s `Commit` (`commit.statuses.last.state == 'success'`), proving the binding is broken and the write crossed tenant boundaries.
