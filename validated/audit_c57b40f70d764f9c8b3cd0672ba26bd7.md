### Title
Fork PR label named `PATH` overrides the safe `PATH` in `Command#unbundled_env`, letting `rollback.override` (and any other stack/task command) resolve bare binaries from the attacker-controlled checkout — ([File: lib/shipit/command.rb])

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) into the stack's environment hash with no key allowlist. That environment flows unfiltered through `TaskCommands#env` / `DeployCommands#env` / `RollbackCommands#env` into `Command.new(env:)`, and `Command#unbundled_env` merges the caller-supplied `@env` **last**, after it sets a safe `PATH`. A label literally named `path` (case-insensitive, becomes `PATH` after `.upcase`) therefore overwrites the safe `PATH` for every command Shipit spawns for that stack, including the `rollback.override` steps.

### Finding Description
The broken binding is: `Command#unbundled_env`'s `PATH` should always equal `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, but it can instead equal an attacker-chosen string.

- `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into `super` with **no key allowlist**: [1](#0-0) 
- `LabelCapturingHandler#capture_labels` persists label names straight from the webhook `pull_request.labels[].name` field, an unprivileged fork PR author fully controls this (they can name their own label anything, e.g. `path`): [2](#0-1) 
- `TaskCommands#env` (parent of `DeployCommands`/`RollbackCommands`) merges `@stack.env` directly with no whitelist filtering (`filter_rollback_envs`/`filter_deploy_envs` are never invoked here): [3](#0-2) 
- `RollbackCommands#env` (used to build the `rollback.override` step commands) is `super.merge('ROLLBACK' => '1')`, inheriting the tainted hash unchanged: [4](#0-3) 
- `Command#unbundled_env` sets a safe `PATH` first, then merges `@env.stringify_keys` **last**, so any `PATH` key in `@env` wins: [5](#0-4) 
- `Command#start` spawns the process with this env: `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and `@chdir` is the checked-out working directory of the fork's own branch, which the PR author fully controls: [6](#0-5) 

Root cause: `ReviewStack#env` treats arbitrary PR label names as trusted environment variable names, and none of the intermediate `env` methods (`StackCommands#env`, `TaskCommands#env`, `DeployCommands#env`, `RollbackCommands#env`) apply `EnvironmentVariables#permit`/`filter_rollback_envs` before handing the hash to `Command.new`. The whitelist mechanism (`EnvironmentVariables#permit`, `Stack#filter_rollback_envs`) exists but is only invoked in the API/HTML controllers for user-submitted rollback `env` overrides (`app/controllers/shipit/api/rollbacks_controller.rb` line 18, `app/controllers/shipit/rollbacks_controller.rb` line 30) — it does not sit between `stack.env`/`ReviewStack#env` and the internally constructed `Command`s used to actually execute `rollback.override`, `deploy.override`, `fetch`, or task steps.

Exploit flow: an unprivileged attacker opens a PR from their own fork against a repo with review stacks enabled, adds a label named `path` to that PR (any PR author can label their own PR), and the `LabelCapturingHandler`/`OpenedHandler` webhooks persist it via `Shipit::PullRequest#labels`. When Shipit later runs any command for that review stack — deploy, rollback (`rollback.override`), fetch, or task — `ReviewStack#env` injects `'PATH' => 'true'` (or if crafted with the exact label text, any directory string) into the merged env, which survives all the way to `Command#unbundled_env`, overriding the safe `PATH`. If the attacker points `PATH` at the checked-out repository directory (which is exactly `@chdir` for these commands, populated from the attacker's own fork content), any bare command name used in a `shipit.yml` step (e.g., `cap`, `make`, or a step defined by the repo's own `shipit.yml`, which for review stacks/forks can itself be attacker-influenced depending on inheritance rules) resolves to an attacker-supplied executable in that directory, achieving code execution on the Shipit deploy host.

Existing guards do not catch this: `verify_signature`/webhook signature checks only prove the payload came from GitHub, they do not restrict label content; `capture_labels`/`ExplicitParameters` schema only requires labels to be `String` — no format or key restriction; `EnvironmentVariables#permit` and `filter_rollback_envs` are real safeguards but are simply never called along this path.

### Impact Explanation
This allows Remote Code Execution on the Shipit deploy host under the identity that runs deploy/rollback commands (the Shipit worker), triggered purely by an unprivileged fork-PR author labeling their own PR — no maintainer or operator action required beyond enabling review stacks. Because `ReviewStack#env`/`TaskCommands#env` apply to every command executed for that stack (deploy, rollback, fetch, tasks), the blast radius covers all commands run for that review stack, and is repeatable indefinitely (attacker can relabel/reopen the PR). This matches the Critical RCE class described (`Command`/`PTY.spawn`).

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`review_stacks_enabled`), and the stack under attack must have an associated `pull_request` (true for any `ReviewStack`). The attacker needs only the ability to open a PR and label it in their own fork — no Shipit credentials, no privileged GitHub team membership. This is a low-cost, highly repeatable attack for any repo owner using Shipit review stacks, matching the `allow_with_label` scenario described in the question (the label-driven provisioning gate does not restrict what labels are captured into `env`).

### Recommendation
Do not merge arbitrary pull-request label names as environment variable keys in `ReviewStack#env`. At minimum:
- Apply an allowlist/prefix scheme (e.g., only accept labels matching a configured prefix, or route them through `EnvironmentVariables#permit` against `deploy_variables`/`rollback_variables`) before merging into `env`.
- Explicitly strip or reject reserved/dangerous keys such as `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `IFS`, `BASH_ENV`, etc., in `ReviewStack#env` and generally in `TaskCommands#env`.
- In `Command#unbundled_env`, force the safe `PATH` last (or use a dedicated non-overridable constant) instead of letting `@env` override it: e.g. `@env.stringify_keys.merge('PATH' => safe_path)`.

### Proof of Concept
```ruby
# test/unit/rollback_commands_path_injection_test.rb
require "test_helper"

module Shipit
  class RollbackCommandsPathInjectionTest < ActiveSupport::TestCase
    test "rollback.override command env cannot have PATH overridden by a PR label" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["path"] # attacker-controlled label on their own fork PR

      deploy = stack.trigger_continuous_delivery
      rollback = deploy.build_rollback
      rollback.save!

      commands = RollbackCommands.new(rollback)
      commands.stubs(:deploy_spec).returns(stub(
        rollback_steps!: ["echo pwned"],
        machine_env: {},
        directory: nil
      ))

      command = commands.perform.first

      # BROKEN BINDING: PATH should always equal the safe Shipit-controlled PATH,
      # never a value derived from an untrusted PR label.
      safe_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
      assert_equal safe_path, command.unbundled_env["PATH"],
        "PR label named 'path' must not override the process PATH for rollback.override"
    end
  end
end
```
This test exercises `ReviewStack#env` (label injection) → `RollbackCommands#env` → `Command#unbundled_env`, and fails on current code because `command.unbundled_env["PATH"]` becomes `"true"` (the label-derived value) instead of the safe path.
