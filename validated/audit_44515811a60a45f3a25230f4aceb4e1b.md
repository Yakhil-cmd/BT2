### Title
Webhook signature verification is keyed by an unverified `repository.owner.login` payload field, allowing cross-organization webhook event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The externally reported bug class is a value-binding mismatch: a raw numeric constant is used without being checked against the unit/scale it is supposed to represent. The structurally equivalent, exploitable analog in this engine is in `WebhooksController#verify_signature`: the GitHub organization used to select the webhook HMAC secret is derived from an **unverified** field of the incoming JSON payload (`repository.owner.login`), while the data that handlers subsequently act on/write (`repository.full_name`, i.e. the actual repo/stack being mutated) is never checked for equality with that authenticating organization.

### Finding Description
`WebhooksController` runs `verify_signature` as a `before_action`: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the JSON body (`params.dig('repository', 'owner', 'login')`), and that value is used to pick *which organization's* configured `webhook_secret` to validate the HMAC against:

```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

The verification itself only proves "this body was signed with the secret belonging to whatever organization `repository.owner.login` claims to be" — it never proves that `repository.owner.login` equals the owner of `repository.full_name`, which is the field the event handlers actually key their side effects off of (e.g. `GithubSyncJob`, status/pull_request handlers look up the `Stack`/`Repository` by full name): [3](#0-2) [4](#0-3) 

In a Shipit deployment onboarding multiple GitHub organizations (each with its own `webhook_secret` configured under `Shipit.github(organization:)`), an attacker who administers **any one** of those onboarded organizations knows that organization's `webhook_secret` (they configured the GitHub App/webhook themselves). They can craft a payload where:
- `repository.owner.login` = their own org (`OrgA`) — so `verify_signature` selects `OrgA`'s secret and the HMAC they compute with that known secret validates successfully.
- `repository.full_name` = a victim repository under a different, unrelated org (`OrgB`) that is also configured on the same Shipit instance.

Nothing in `verify_signature` or in the downstream event handlers enforces that the organization whose secret validated the signature is the same organization that owns the repository being acted upon. The equality that should hold is:

`organization that authenticated (secret owner) == organization owning the repository that is written`

and this analog breaks it, exactly matching the allowed "organization authenticated vs repository written" binding.

### Impact Explanation
A forged, signature-valid webhook for an arbitrary victim repository/stack can be delivered by anyone who legitimately controls one unrelated org connected to the same Shipit instance. Depending on which event type is forged this enables, e.g.:
- Forged `push` events causing `GithubSyncJob` to run against the victim stack with attacker-chosen `sha`/branch data.
- Forged `status`/`check_suite` events injecting fake "success" statuses on a victim commit, defeating `Commit#deployable?`'s CI gate and enabling an **unauthorized deploy**.
- Forged `pull_request`/`membership` events manipulating merge-queue state or team membership for a victim stack.

This satisfies the Critical/High bar of "unauthorized deploy" / "cross-repository writes" without the attacker ever needing write access to the victim repository, an `ApiClient` token, or the victim's `webhook_secret` — only administrative control of one other, unrelated org already onboarded to the same Shipit instance.

### Likelihood Explanation
Requires: (1) the target Shipit instance manages more than one GitHub organization, and (2) the attacker controls the GitHub App/webhook configuration for at least one of those organizations (a normal, low-privilege situation for any org admin who legitimately onboarded their own org to a shared Shipit instance). No credentials belonging to the victim organization are needed. This is a realistic multi-tenant configuration for Shipit.

### Recommendation
After verifying the HMAC, re-derive the organization strictly from the *verified* raw body and cross-check it against the owner of `repository.full_name` (or, more robustly, bind each configured GitHub App installation to an explicit allow-list of repository full names/orgs it may report events for) before dispatching to any handler. Reject the request if the signing organization does not match the owner of the repository referenced in the payload.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-administered, webhook secret known to attacker) and `orgB` (victim, has a Stack tracking `orgB/victim-repo`).
2. Attacker crafts a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
     "after": "<attacker-chosen sha>",
     ...
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, raw_body)>` using the secret they legitimately know for `orgA`.
4. Attacker sets `X-Github-Event: push` (or `status`, etc.) and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and validates successfully against `orgA`'s secret.
6. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs, and the push handler locates/mutates the Stack for `orgB/victim-repo` based purely on `full_name`, with no check that `orgA` (the authenticated org) owns that repository.
