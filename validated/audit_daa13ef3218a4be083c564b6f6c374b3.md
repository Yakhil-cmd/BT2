### Title
Cross-organization stack mutation via `repository.owner.login` / `repository.full_name` divergence in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub organization (and thus the `webhook_secret`) used to validate the HMAC signature from `params.dig('repository','owner','login')`, while the actual mutation target in `Shipit::Webhooks::Handlers::Handler#stacks` (used by `PushHandler#process`) is resolved from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`. These two fields are never checked for consistency, so a payload can be signed as belonging to org-a while its `full_name` targets org-b's repository. [1](#0-0) [2](#0-1) 

### Finding Description
The broken binding: `organization_that_signed = params.dig('repository','owner','login')` must equal `organization_that_owns_full_name = payload.dig('repository','full_name').split('/').first` for the request to legitimately authorize mutation of that repository's stacks — but the code never enforces this.

- `verify_signature` builds a `GitHubApp` for `repository_owner` (`repository.owner.login`, falling back to `organization.login`) and calls `verify_webhook_signature(signature, raw_post)` against that org's configured `webhook_secret`. [3](#0-2) [4](#0-3) 
- `create` then parses the raw body again and dispatches to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PushHandler`. [5](#0-4) 
- `PushHandler#process` resolves the affected stacks through `Handler#stacks`, which reads `payload.dig('repository', 'full_name')` — a completely independent field from the one used for signature verification — and calls `Repository.from_github_repo_name(repository_name)`. [6](#0-5) [2](#0-1) [7](#0-6) 
- The resolved stacks then have `stack.sync_github(expected_head_sha: params.after)` invoked, which enqueues `GithubSyncJob` for that stack, which will fetch commits and mutate stack state for org-b's repository. [8](#0-7) 

Exploit precondition: this attack requires the attacker to already possess a valid `webhook_secret` for *some* organization configured on this Shipit instance (org-a) — e.g. because they are a legitimate tenant of a multi-organization Shipit deployment and configured that webhook themselves in GitHub, or GitHub itself signs the request for a push to their own org-a repo but the attacker is free to modify the JSON body's `full_name` before GitHub's signature covers it (in the GitHub model, the signature is computed over the actual delivered body — an attacker with control over their own org's webhook secret can freely construct and self-sign an arbitrary body, since they know their own secret). Given that secret, the attacker computes `HMAC-SHA1(webhook_secret_org_a, body)` over a **crafted** body where `repository.owner.login = "org-a"` (or `organization.login = "org-a"`) but `repository.full_name = "org-b/private-repo"`, and POSTs it to `/webhooks` with header `X-Github-Event: push`. `verify_signature` validates against org-a's secret and passes. `PushHandler` then acts on `org-b/private-repo`'s stacks using the attacker-controlled `after` SHA.

No other guard closes this gap: `drop_unhandled_event` only checks the event type exists, `ExplicitParameters` only validates the shape of `ref`/`after`, and `Repository.from_github_repo_name` performs no ownership cross-check against the verifying organization. [9](#0-8) [10](#0-9) 

### Impact Explanation
An attacker who legitimately controls (or has the `webhook_secret` for) one tenant organization on a shared Shipit instance can trigger `GithubSyncJob` for any other tenant's stack by simply changing the `full_name` field in a self-signed payload, forcing `sync_github`/`GithubSyncJob` to run against an `expected_head_sha` of the attacker's choosing for a repository they do not own. This is a payload for one repository (org-a's signed request) mutating another's stack (org-b), matching the "Critical" category explicitly listed in scope. The attack is fully repeatable against any repository/organization onboarded to the same Shipit instance, as long as `Repository.from_github_repo_name` can resolve a matching `Repository` record. Blast radius is bounded by all other tenants (organizations/repositories) configured on the same shared Shipit deployment.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (`Shipit.github_organizations` with more than one org configured, each with its own `webhook_secret`), and (2) attacker control of one org's `webhook_secret` (as a legitimate tenant admin of that org, which the threat model explicitly allows since they can "emit webhooks from a repository they own"). Given that, forging the payload and computing the HMAC is trivial (no GitHub interaction needed, just a raw HTTP POST with a hand-crafted JSON body and correct HMAC header). Cost is very low and fully repeatable.

### Recommendation
In `WebhooksController#verify_signature` or in `Handler#stacks`/`repository_name`, enforce that the organization used to select the `webhook_secret` (`repository_owner`) matches the resolved target repository's owner (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner`). Reject the request (422) if they diverge. Alternatively, resolve the target `Repository`/`GitHubApp` strictly from a single trusted field (e.g., always derive both the signing org and the mutation target from `repository.full_name`'s owner segment), rather than from two independently attacker-controlled JSON paths.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":push signed by org-a mutates org-b's stack via mismatched owner/full_name" do
  # Setup: two orgs "org-a" and "org-b" configured with distinct webhook_secret in Shipit secrets
  # org_b_repo/org_b_stack exist and belong to "org-b"

  request.headers['X-Github-Event'] = 'push'

  payload = {
    'ref' => 'refs/heads/master',
    'after' => 'deadbeef' * 5,
    'repository' => {
      'owner' => { 'login' => 'org-a' },       # used by verify_signature
      'full_name' => 'org-b/private-repo'       # used by PushHandler#stacks
    }
  }
  body = payload.to_json
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', ORG_A_WEBHOOK_SECRET, body)
  request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: org_b_stack.id, expected_head_sha: payload['after']]) do
    post :create, body:, as: :json
  end
  # Assertion demonstrates: repository_owner ("org-a") used for signature verification
  # != full_name owner ("org-b") whose stack was mutated -> binding violated.
end
```

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
