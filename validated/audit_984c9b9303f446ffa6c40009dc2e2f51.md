### Title
Cross-repository commit-status forgery via unscoped `sha` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook against the GitHub App/organization derived from the payload's `repository.owner.login` (or `organization.login`), using that organization's `webhook_secret` to validate the HMAC signature. [1](#0-0)  That verification only proves the request was signed by *some* configured organization — it never re-validates that the `repository`/commit the payload actually mutates belongs to that same organization. `StatusHandler`, unlike `PushHandler` and `CheckSuiteHandler`, does not scope its side effect to `repository.full_name` at all: it looks up commits globally by `sha` across the entire `Commit` table and writes a status onto whatever it finds. [2](#0-1)  Compare this to `Handler#repository_name`/`#stacks`, which other handlers use to scope lookups to the repository named in the payload. [3](#0-2) 

### Finding Description
The binding that should hold is: *the organization whose secret signed the webhook == the repository/commit being written to*. It is broken as follows:

- `verify_signature` resolves `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` purely to pick which configured org's `webhook_secret` to check the signature against. [4](#0-3) 
- Once the signature check passes, the raw payload is dispatched unmodified to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 
- `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, un-scoped-by-repository query. [2](#0-1) 
- `create_status_from_github!` immediately persists the attacker-controlled `state`/`description`/`target_url`/`context` as a `Status` row tied to the found commit's stack, and this can trigger deploy-gating side effects (`schedule_merges`, `deployable_status` hook emission) via `Commit#add_status`. [6](#0-5) [7](#0-6) 

Because Shipit is documented/configured to support multiple independent GitHub organizations simultaneously in the same install (see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`, each with its own `webhook_secret`), [8](#0-7)  an attacker who controls (or has push/status-API access on) a repository under **any** one of those configured organizations can deliver a legitimately-signed `status` webhook — signed correctly with *their own* org's `webhook_secret` — whose `sha` field happens to match a commit that exists under a **different** organization's stack (e.g., because the commit content, hence its content-addressed SHA, is duplicated by replaying an identical commit tree/parent chain into their own repo). `StatusHandler` will apply that attacker-authored status to the victim commit regardless of the organization that actually authenticated the request, since there's no organization/repository cross-check.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding required by the review rules. The consequence — an attacker-authored `success` status forced onto a victim commit in an unrelated stack/organization — can flip `Commit#deployable?`/`Stack#merge_status` gating logic (`add_status` calls `stack.schedule_merges` and emits `deployable_status`), which is exactly the kind of state that gates automatic deploys/merges via `ProcessMergeRequestsJob`/continuous delivery. [9](#0-8)  This can enable an unauthorized deploy/merge of a commit that never actually passed CI in its real repository, satisfying the "unauthorized deploy, rollback, or merge" Critical impact bucket in scope.

### Likelihood Explanation
Requires: (a) Shipit configured for multiple GitHub orgs/apps sharing one `Commit` table (a supported, documented configuration), and (b) the attacker being able to reproduce an identical commit SHA (same tree/parents/author/committer metadata) inside a repo they control, then trigger a `status` event for it (e.g., via GitHub's Statuses API on their own repo, or a CI integration they control). Reproducing an exact SHA is feasible when the target commit's full content (including parent hash, author/committer, timestamps, message) is public or otherwise known, which is common in open-source or forked-history scenarios. This is a non-trivial but concrete and unprivileged (no Shipit session, no `webhook_secret` of the *victim* org, no target repo write access) path, so likelihood is assessed as medium rather than trivial.

### Recommendation
Scope `StatusHandler#process` (and any other handler relying on global lookups) to the repository named in the payload, consistent with `Handler#stacks`/`#repository_name`, e.g. restrict the `Commit.where(sha: params.sha)` query to commits whose `stack` belongs to `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. More generally, `verify_signature`'s resolved `repository_owner` should be threaded through to every handler and asserted to match the repository owner of any record being mutated, closing the gap between "who signed this" and "what gets written."

### Proof of Concept
1. Shipit instance configured with two organizations, `OrgA` (victim, owns `orgA/app`) and `OrgB` (attacker-controlled, owns `orgB/app`), each with distinct `webhook_secret`s, per the documented multi-org secrets format. [10](#0-9) 
2. Attacker, with write access to `orgB/app`, crafts a commit with tree/parent/author/committer/message identical to a known commit `C` in `orgA/app` (SHA is content-addressed, so identical content yields identical SHA), and pushes it into `orgB/app`.
3. Attacker triggers (or has GitHub trigger) a `status` webhook event on `orgB/app` for that commit, with `state: "success"`, and their own valid `X-Hub-Signature` computed with `OrgB`'s `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgB"`, fetches `Shipit.github(organization: "orgB")`, and successfully verifies the signature — the request is accepted. [11](#0-10) 
5. `StatusHandler#process` executes `Commit.where(sha: C.sha)`, finds commit `C` under `orgA/app`'s stack (no ownership check), and calls `create_status_from_github!`, injecting a forged `success` status onto `orgA`'s commit. [2](#0-1) 
6. This forged status can satisfy `Commit#deployable?`/`Stack#merge_status` checks for `orgA/app`, potentially triggering an unauthorized continuous deploy or merge.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end

    end
