### Title
Fixed-point overflow during interest accrual permanently freezes a large market - ([File: common/src/rates/scaling.rs](common/src/rates/scaling.rs))

### Summary
A sufficiently large market can reach a state where index accrual panics from `i128` overflow before the borrow-index cap can protect it. After that, every operation touching the market—including `update_indexes`, `repay`, `withdraw`, liquidation and bad-debt cleanup—reverts during the mandatory accrual step.

### Finding Description
Every pool mutation loads the market through `synced_market` or `renewed_market`, which calls `interest::global_sync` before the requested operation executes. [1](#0-0) 

`global_sync` calls `accrue_step` for every elapsed-time chunk and updates the borrow index, supply index and revenue shares. [2](#0-1) [3](#0-2) 

The accrual path converts aggregate scaled balances back to RAY-denominated values with `scaled.mul(env, index)`. [4](#0-3)  This is used for total borrowed and supplied value when calculating utilization. [5](#0-4) 

The configured borrow-index cap is applied only after multiplying the old index by the interest factor, so multiplication overflow also bypasses the intended cap. [6](#0-5) 

The repository’s native test demonstrates the reachable cliff: at very large raw supply and high utilization, accrual panics with `MathOverflow`, the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, and subsequent withdrawal and repayment calls hit the same error. [7](#0-6) 

### Impact Explanation
Once the market enters this state, its last accrual timestamp remains behind ledger time because the transaction rolls back. Every later operation therefore retries the overflowing accrual and fails again.

This permanently freezes supplier withdrawals, borrower repayments, liquidations, flash loans, index updates and bad-debt cleanup for that market absent a contract upgrade. User funds remain locked rather than being recoverable through an alternative controller path.

The permissionless controller entrypoints expose the affected paths directly: `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `update_indexes` and `recapitalize`. [8](#0-7) [9](#0-8) 

### Likelihood Explanation
Triggering the overflow requires a listed market whose caps and token supply permit aggregate scaled balances large enough for `scaled * index` to exceed `i128::MAX`, followed by sustained high-utilization accrual. A single caller can create multiple accounts with `account_id = 0`, supply the debt asset through one account and collateral through another, then borrow the debt asset at high utilization. [10](#0-9) 

The economic prerequisite is substantial, so this is a Medium-severity availability vulnerability rather than a universally reachable instant shutdown. No privileged call, malformed packet, token malfunction or budget exhaustion is required after the market reaches the vulnerable state.

### Recommendation
Use overflow-safe arithmetic for aggregate share-to-value conversions during accrual:

- Replace `scaled * index` in utilization and interest-total calculations with saturating or wide-precision `mul_div` logic.
- Apply `MAX_BORROW_INDEX_RAY` without first executing a multiplication that can overflow.
- Bound utilization calculations independently of the raw aggregate value where the only required result is a utilization ratio.
- Add a recovery path that commits the capped index even when the pre-cap mathematical value exceeds `i128::MAX`.
- Extend `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` to assert that accrual saturates and that repayments, withdrawals and liquidations remain executable. [11](#0-10) 

### Proof of Concept
The native test already implements the exploit path:

```rust
// One caller can own both accounts created with account_id = 0.
supply(caller, 0, spoke_id, [(debt_asset, principal)]);
supply(caller, 0, spoke_id, [(collateral_asset, sufficient_collateral)]);
borrow(caller, debt_account_id, [(debt_asset, principal * 98 / 100)], None);

// Repeat until accrual reaches the overflowing state.
update_indexes(caller, [debt_asset]);

// All subsequently fail with MathOverflow during mandatory accrual.
update_indexes(caller, [debt_asset]);
repay(caller, debt_account_id, [(debt_asset, 1)]);
withdraw(supplier, supply_account_id, [(debt_asset, 1)], None);
```

The test seeds `principal = 1_000_000_000 * 10^18` raw units, borrows 98%, advances ledger time until `update_indexes` fails, verifies that the stored borrow index is still below the cap, and confirms that both withdrawal and repayment fail with `MathOverflow`. [12](#0-11)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```markdown
### Accounts and authorization

Account id `0` creates an account on `supply`, `multiply`, `flash_position`, `migrate_from_blend`, and liquidation with `Credit(0)`. An account's spoke binding is permanent. `multiply` and `flash_position` require Multiply, Long or Short mode, and an existing account must match the requested mode. Blend migration creates a Normal account; an existing destination need not be Normal.

Delegates belong to the granting owner. An NFT transfer disables that owner's grants; a transfer back can reactivate them unless a later owner has replaced or deleted the list. NFT ownership, including control of collateral and the debt obligation, transfers atomically.

Ordinary payment lists sum duplicate markets in first-appearance order and reject negative amounts. `supply`, `borrow` and `repay` reject zero. In `withdraw`, zero means the full balance and overrides positive amounts for the same market. Flash-position declaration lists reject duplicates.
```
