## Title
Incomplete worktree admin cleanup on ref reversion causes stale `.git/worktrees/<hash>` metadata reuse and possible sync denial - (File: main.go)

### Summary
The external report describes `killGauge()` deleting only some of the state associated with a gauge (`isAlive`, `claimable`, and `totalWeightsPerEpoch`) while leaving other related state (`weightsPerEpoch[epoch][pool]`) intact. When the gauge is later "revived," the stale, un-cleaned state causes the accounting logic to misbehave. The analogous pattern in `git-sync` is in the worktree lifecycle management in `main.go`, where a worktree's on-disk directory can be removed without correspondingly cleaning up git's own administrative bookkeeping (`.git/worktrees/<hash>`), leaving inconsistent state that is silently reused the next time the same commit hash needs a worktree (e.g., when the tracked ref moves backward to a previously-synced commit).

### Finding Description
`repoSync.SyncRepo` removes a stale/obsolete current worktree directory directly with `os.RemoveAll`, bypassing the normal removal helper: [1](#0-0) 

Compare this to the normal removal path, `removeWorktree`, which is supposed to be the single place that keeps the on-disk directory and git's internal worktree admin state (under `.git/worktrees/<hash>`, tracked via `git worktree prune`) in sync: [2](#0-1) 

Critically, `removeWorktree` only runs `git worktree prune` when the directory *still exists* on disk; if `os.Stat` reports `os.IsNotExist`, it returns `nil` immediately without pruning: [3](#0-2) 

Because the `SyncRepo` code path at line 1992 removes the directory via bare `os.RemoveAll` (not through `removeWorktree`, and without ever invoking `git worktree prune`), the git-level administrative record for that hash under `.git/worktrees/<hash>` is left dangling — analogous to `killGauge()` deleting `isAlive`/`claimable`/`totalWeightsPerEpoch` but forgetting to clear `weightsPerEpoch[epoch][pool]`.

The next time `createWorktree` is invoked for that same hash (which happens naturally if the upstream `--ref` moves backward to a commit that was previously synced — the "revival" case directly mirrored from the original report), it first calls `removeWorktree`: [4](#0-3) 

Since the directory no longer exists on disk, `removeWorktree`'s stat check short-circuits and skips `git worktree prune`, so the stale `.git/worktrees/<hash>` admin entry is never cleared before `git worktree add --force --detach ...` is executed. `--force` masks the immediate symptom, but the pre-existing stale administrative metadata (which may reference now-invalid HEAD/index/lock state for that worktree) is exactly the kind of "silently reused stale state" that the original report flags as the root cause of the miscalculation — here it can bias subsequent worktree configuration (e.g. sparse-checkout state, lock files) and worktree "add" behavior in ways that do not correspond to a fresh checkout.

### Impact Explanation
If the stale `.git/worktrees/<hash>` metadata interferes with a later `git worktree add --force`, this can manifest as sporadic sync failures (`fatal: ... is already registered worktree` / lock errors) that recur across sync attempts because the underlying admin directory is never pruned by this path, producing persistent sync denial for that container. It could also, depending on git version behavior with `--force` re-adding over stale metadata, cause the checked-out content or its `.git` sparse-checkout/index state to diverge from a truly fresh worktree, resulting in publishing of inconsistent content via the atomic symlink contract that `git-sync` promises consumers.

### Likelihood Explanation
This requires the tracked `--ref` to move backward (or otherwise re-target a hash whose worktree directory was previously torn down through the `os.RemoveAll` path at line 1992) within a window where the stale git worktree admin metadata has not yet been pruned by an unrelated `cleanup()` cycle (`cleanup()` only runs `worktree prune` when `removeStaleWorktrees` actually deleted something in the same pass). Upstream repositories that force-push or reset branches backward, or fast-moving branches with commit churn, make this reachable without any special privilege — it is triggered purely by ordinary upstream ref/commit history that `git-sync` is designed to follow.

### Recommendation
Route the removal at `main.go:1992` through `removeWorktree` (which already stats and calls `git worktree prune`) instead of a bare `os.RemoveAll`, and additionally have `removeWorktree` unconditionally attempt `git worktree prune` (or `worktree remove --force`) even when the directory is already missing from disk, so that git's internal admin state is never left orphaned regardless of which code path deleted the on-disk directory first.

### Proof of Concept
1. Start `git-sync` tracking a branch; let it sync commit `A`, publishing worktree `.worktrees/A` and updating the symlink.
2. Advance the branch to commit `B`; `git-sync` syncs `B`, and per the `changed` branch removes the old worktree for `A` via the bare `os.RemoveAll` at `main.go:1992` (this is the "upgrade path from older worktree naming" cleanup, but the same code executes whenever `currentWorktree != git.worktreeFor(currentHash)`).
3. Reset the upstream branch back to `A` (`git reset --hard A~` style force-push), so `git-sync`'s next poll fetches `A` again and calls `createWorktree(ctx, A)`.
4. `createWorktree` calls `removeWorktree` for path `.worktrees/A`; since the directory is already gone, the stat check returns `os.IsNotExist` and the function returns immediately without ever invoking `git worktree prune` to clear the stale `.git/worktrees/A` admin entry left over from step 2.
5. `git worktree add --force --detach .worktrees/A A --no-checkout` is executed against a repo that still has dangling internal bookkeeping for the `A` worktree, reproducing the "stale, never-cleaned state gets silently reused on revival" pattern from the original report and risking sync errors or inconsistent published content.

// removeWorktree is used to remove a worktree and its folder.
func (git *repoSync) removeWorktree(ctx context.Context, worktree worktree) error {
	// Clean up worktree, if needed.
	_, err := os.Stat(worktree.Path().String())
	switch {
	case os.IsNotExist(err):
		return nil
	case err != nil:
		return err
	}
	git.log.V(1).Info("removing worktree", "path", worktree.Path())
	if err := os.RemoveAll(worktree.Path().String()); err != nil {
		return fmt.Errorf("error removing directory: %w", err)
	}
	if _, _, err := git.Run(ctx, git.root, "worktree", "prune", "--verbose"); err != nil {
		return err
	}
	return nil
}

// createWorktree creates a new worktree and checks out the given hash.  This
// returns the path to the new worktree.
func (git *repoSync) createWorktree(ctx context.Context, hash string) (worktree, error) {
	// Make a worktree for this exact git hash.
	worktree := git.worktreeFor(hash)

	// Avoid wedge cases where the worktree was created but this function
	// error'd without cleaning up.  The next time thru the sync loop fails to
	// create the worktree and bails out. This manifests as:
	//     "fatal: '/repo/root/nnnn' already exists"
	if err := git.removeWorktree(ctx, worktree); err != nil {
		return "", err
	}

	git.log.V(1).Info("adding worktree", "path", worktree.Path(), "hash", hash)
	_, _, err := git.Run(ctx, git.root, "worktree", "add", "--force", "--detach", worktree.Path().String(), hash, "--no-checkout")
	if err != nil {
		return "", err
	}

	return worktree, nil
}
