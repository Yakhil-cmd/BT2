Based on my research, I found a real analog in the `pallet-revive` ERC20 integration layer that mirrors the DAO Pool bug exactly: trusting an attacker-supplied contract's boolean return value instead of verifying the actual balance delta after a low-level `transfer` call.

### Title
Unverified ERC20 `transfer` return value lets an attacker fake XCM/fungibles credit without moving real tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` and `pallet_revive`'s `fungibles::Mutate::burn_from` / `mint_into` all move value into/out of a "checking account" by issuing a low-level `bare_call` to an arbitrary, user-deployed contract at an `H160` address treated as an ERC20 token, and then trust only the ABI-decoded boolean return of that call. Neither location re-reads `balanceOf` before/after to confirm the claimed amount actually moved, exactly the missing-check pattern described in the report.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` calls the token contract's `transfer(checking_address, amount)` on behalf of the withdrawing account and treats a decoded `true` as proof that `amount` tokens were moved into the checking account, immediately minting an equivalent `AssetsInHolding` credit: [1](#0-0) 

The mirrored `deposit_asset_with_surplus` does the same on the way out, moving funds from the checking account to a beneficiary based solely on the decoded boolean: [2](#0-1) 

The same pattern exists in `pallet-revive`'s generic `fungibles::Mutate` implementation, used by `FungiblesAdapter` (per the file's own doc comment): [3](#0-2) [4](#0-3) 

Because `pallet_revive::Config::InstantiateOrigin = EnsureSigned<Self::AccountId>` on Asset Hub Westend, any unprivileged signed account can deploy an arbitrary contract and register it as an "ERC20" simply by being referenced via `AccountKey20`/`H160` in an asset location: [5](#0-4) 

`ERC20Transactor` is wired directly into the runtime's live `AssetTransactors` tuple used by the XCM executor for `WithdrawAsset`/`DepositAsset`, so this is on the real, reachable execution path for any signed XCM `execute` or incoming XCM message referencing an `AccountKey20` asset: [6](#0-5) 

A malicious contract can implement `transfer`/`transferFrom` to unconditionally return `true` (ABI-encoded) without decrementing any balance mapping — the repo's own `MyTokenFake.sol` fixture demonstrates that pallet-revive readily tolerates non-standard/dishonest return semantics from arbitrary bytecode: [7](#0-6) 

The pallet's own `fungibles::Inspect::balance` for these ERC20-backed assets is itself just a delegated `balanceOf` call to the same attacker-controlled contract, so there is no independent on-chain ledger the runtime can use to cross-check the transfer: [8](#0-7) 

### Impact Explanation
The `withdraw_asset_with_surplus` path mints an `Erc20Credit(amount)` inside the XCM holding register purely from a boolean the attacker's own contract chose to return, with no verification that the checking account's real backing actually increased: [9](#0-8) 
This is structurally identical to the reported bug: a fake/no-op "transfer" is accepted as proof of custody, allowing the attacker to fabricate XCM-holding value that is not actually backed in the checking account. Any downstream consumer of that holding (deposit to a beneficiary, further XCM instructions, or any integration that treats "successful ERC20 transfer to checking account" as proof of genuine custody) is deceived exactly as the naive DAO-sale participants were in the original report.

I was **not able to fully verify** within this investigation whether the same H160/ERC20 asset kind can be paired against a real-backed asset (e.g. native WND) inside `pallet_asset_conversion`'s pools on Asset Hub Westend — the asset-conversion precompile's `decode_asset_kind` appears scoped to `NativeOrWithId<u32>` (i.e. `pallet_assets` ids), which would mean ERC20 (`H160`) assets are not directly poolable there. If that scoping holds, the practical monetary-drain path (fabricated credit exchanged for real backed value in an AMM) is not currently demonstrated, and the confirmed impact is limited to internal accounting/holding-register integrity within the ERC20-wrap/unwrap subsystem itself (self-contained to assets whose "ledger" is the attacker's own contract). This should be treated as **unresolved/uncertain** rather than proven, and would need explicit confirmation of the Asset Hub `AssetKind`/pool wiring to elevate severity to a direct fund-drain.

### Likelihood Explanation
Deploying a contract via `pallet-revive` is a fully permitted, unprivileged action (`EnsureSigned`), and crafting a `transfer` function that always returns `true` while skipping real balance bookkeping is trivial Solidity/PVM code — no special role, governance, or validator/collator compromise is required. The `ERC20Transactor` and `impl_fungibles` code paths are both on the live, production XCM/asset-transfer execution path on Asset Hub Westend.

### Recommendation
In `withdraw_asset_with_surplus`, `deposit_asset_with_surplus` (erc20_transactor.rs), and `burn_from`/`mint_into` (impl_fungibles.rs), record the checking/target account's real `balanceOf` before and after the low-level `bare_call`, and require the observed delta to equal the claimed `amount` before minting any `AssetsInHolding` credit or reporting success — mirroring the report's recommended before/after balance check, rather than trusting the decoded boolean return value alone.

### Proof of Concept
No PoC was executed against a live network or test harness; this analysis is based on static code inspection only. A minimal reproduction would require: (1) deploying a `MyTokenFake`-style contract via `pallet_revive::instantiate` whose `transfer` returns `true` without mutating `_balances`, (2) submitting a signed `pallet_xcm::execute` with a `WithdrawAsset` for that contract's `AccountKey20` location, and (3) asserting that `AssetsInHolding` now contains an `Erc20Credit` while the checking account's real (contract-reported, but for an honest token this would be independently verifiable) balance never increased. This reproduction was **not run**; guard-failure and deployment evidence for this specific path remain unverified, and the value-extraction endpoint (pairing with a real-backed asset pool) is unconfirmed as noted above.

// We implement `fungibles::Mutate` to override `burn_from` and `mint_to`.
//
// These functions are used in [`xcm_builder::FungiblesAdapter`].
impl<T: Config> fungibles::Mutate<<T as frame_system::Config>::AccountId> for Pallet<T> {
	fn burn_from(
		asset_id: Self::AssetId,
		who: &T::AccountId,
		amount: Self::Balance,
		_: Preservation,
		_: Precision,
		_: Fortitude,
	) -> Result<Self::Balance, DispatchError> {
		let checking_account_eth = T::AddressMapper::to_address(&Self::checking_account());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, .. } = Self::bare_call(
			OriginFor::<T>::signed(who.clone()),
			asset_id,
			U256::zero(),
			TransactionLimits::WeightAndDeposit {
				weight_limit: WEIGHT_LIMIT,
				deposit_limit:
					<<T as pallet::Config>::Currency as fungible::Inspect<_>>::total_issuance(),
			},
			data,
			&ExecConfig::new_substrate_tx(),
		);
		log::trace!(target: "whatiwant", "{weight_consumed}");
		if let Ok(return_value) = result {
			if return_value.did_revert() {
				Err("Contract reverted".into())
			} else {
				let is_success =
					bool::abi_decode_validate(&return_value.data).expect("Failed to ABI decode");
				if is_success {
					let balance = <Self as fungibles::Inspect<_>>::balance(asset_id, who);
					Ok(balance)
				} else {
					Err("Contract transfer failed".into())
				}
			}
		} else {
			Err("Contract out of gas".into())
		}
	}
