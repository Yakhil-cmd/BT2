Webhook signature bound to `repository.owner.login`, but repository resolution keyed by unverified `repository.full_name` — cross-organization forged webhook events - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-organization Shipit deployments, `WebhooksController#verify_signature` selects the HMAC secret used to authenticate a webhook by reading `repository.owner.login` (or `organization.login`) from the JSON body, but every event `Handler` resolves the target `Repository`/`Stack` from a *different* field of the same body: `repository.full_name`. Because both fields live in the same attacker-controlled, unauthenticated-until-verified payload, an operator who legitimately administers one organization's GitHub App (and therefore legitimately knows that organization's `webhook_secret`) can craft a payload whose `repository.owner.login` matches their own org (so it passes signature verification) while `repository.full_name` names a repository belonging to a *different* organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the verifying `GitHubApp`/secret using only the owner login: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization secret from `secrets.github`, keyed by the (lowercased) organization name — this is the multi-org config schema explicitly supported by the engine: [3](#0-2) 

Once the signature check passes, `create` blindly dispatches the raw JSON body to all registered handlers for the event, with no re-check that `repository_owner` (used to pick the secret) matches the repository actually referenced in the payload: [4](#0-3) 

Every handler resolves its target repository/stack purely from `payload.dig('repository', 'full_name')`: [5](#0-4) [6](#0-5) 

This is used, for example, by `PushHandler` (triggers a git sync/deploy-relevant `sync_github` job): [7](#0-6) 

and by `StatusHandler`/`CheckSuiteHandler`, which write commit CI status / trigger check-run refresh purely keyed by `sha`, with no repository-ownership cross-check at all: [8](#0-7) [9](#0-8) 

**Broken equality binding:** the organization whose credential authenticated the request (`repository.owner.login`, matched against `Shipit.github(organization:)`'s secret store) is not required to equal the repository whose state is mutated (`repository.full_name`, resolved via `Repository.from_github_repo_name`). Both values are attacker-supplied fields inside the same signed byte string, so nothing outside the payload itself ties them together.

### Impact Explanation
An attacker who is a legitimate administrator of Organization A's GitHub App (installed on this Shipit instance alongside other orgs) knows Org A's `webhook_secret`. Using it, they can forge a signed webhook whose `repository.owner.login` is `"orgA"` (so `verify_signature` selects and validates against Org A's secret) but whose `repository.full_name` is `"orgB/victim-repo"` (a repository belonging to an unrelated tracked organization). The engine will process this as a legitimate event for `orgB/victim-repo`:
- `push` events can trigger `stack.sync_github`, forcing syncs on Org B's stacks under attacker-chosen `after` SHAs.
- `status` events let the attacker inject fabricated commit statuses (`create_status_from_github!`) for any commit SHA across the whole instance, independent of repository ownership — this can make an otherwise-red/pending commit appear green/deployable, influencing an authorized user to trigger an unauthorized deploy of that commit.
- `check_suite` events can force check-run refresh cycles on Org B's stacks.

This crosses an organizational trust boundary the multi-org config is explicitly designed to enforce (`Shipit.github(organization:)` exists specifically to give each org its own secret) and can lead to state corruption / spoofed deployability signals on repositories the attacker has no legitimate access to — matching the High/Critical impact classes ("unauthorized deploy" enablement, unauthenticated write of stack state) defined in scope.

### Likelihood Explanation
Likelihood is Medium: it requires the target Shipit instance to run the multi-organization github config (`secrets.github` keyed by org names rather than the single top-level schema) and requires the attacker to legitimately control at least one tracked organization's GitHub App/webhook secret — a realistic scenario for shared Shipit deployments serving multiple business units/orgs, which is the exact use case the multi-org schema exists for. No stolen credentials, session, or API token are needed beyond the attacker's own legitimately-held org secret.

### Recommendation
In `WebhooksController#verify_signature` (or `#create`), after successfully verifying the signature for `repository_owner`, re-derive the repository/organization actually referenced by `repository.full_name` (or `organization.login` for org-scoped events) and reject the request (422) if it does not match the organization whose secret validated the signature. Equivalently, each `Handler` should assert that the resolved `Repository#owner` equals the authenticated `repository_owner` before mutating any state.

### Proof of Concept
1. Shipit is configured with the multi-org schema, e.g.:
```yaml
github:
  orga:
    webhook_secret: "orgA-secret"
    ...
  orgb:
    webhook_secret: "orgB-secret"
    ...
```
Both `orga/repo1` and `orgb/victim-repo` are tracked stacks.
2. Attacker administers Org A's GitHub App and thus knows `orgA-secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgb/victim-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA-secret, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "orgA")`, finds Org A's config, and validates the signature successfully against Org A's secret.
6. `WebhooksController#create` dispatches the parsed body to `PushHandler`, whose `repository_name`/`stacks` resolve `Repository.from_github_repo_name("orgb/victim-repo")` — an Org B repository the attacker does not control — and `sync_github` is invoked for it, with no check that Org B's secret was used.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
