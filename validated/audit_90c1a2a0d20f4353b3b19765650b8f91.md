### Title
Secretary Salary payouts are debited from the Fellowship Salary sovereign account instead of a dedicated Secretary account - ([File: system-parachains/collectives/collectives-polkadot/src/secretary/mod.rs])

### Summary
`SecretarySalaryPaymaster` is configured with `crate::fellowship::FellowshipSalaryInteriorLocation` as its `PayOverXcm` interior location instead of a Secretary-specific `PalletInstance` location. Because every other collective salary/treasury paymaster (Fellowship Salary, Fellowship Treasury, Ambassador Salary, Ambassador Treasury) derives its own dedicated interior location from its own pallet index, this is a copy‑paste account confusion: any unprivileged Secretary member who successfully claims a salary causes AssetHub to debit the Fellowship Salary pallet's sovereign account rather than a Secretary-dedicated account.

### Finding Description
`SecretarySalaryPaymaster` is defined as: [1](#0-0) 

Compare with the analogous, correctly-scoped definitions for the Fellowship Salary paymaster (deriving its interior location from its own pallet, `crate::FellowshipSalary`): [2](#0-1) 

and the Ambassador Salary paymaster (deriving its own location from `crate::AmbassadorSalary`): [3](#0-2) 

Every other instance builds its `InteriorLocation` as `PalletInstance(<own pallet's index>)`, but Secretary's paymaster reuses `crate::fellowship::FellowshipSalaryInteriorLocation`, i.e. `PalletInstance(<FellowshipSalary index, 64>)`. `PayOverXcm`'s first type parameter is used to `DescendOrigin` on the target chain (AssetHub) before executing the payout `TransferAsset`, which determines the sovereign source account that gets debited — this pattern is shown explicitly in the analogous encointer implementation (`DescendOrigin(from_location.interior.clone())` before `TransferAsset`): [4](#0-3) 

Consequently, when a registered Secretary member calls the unprivileged `pallet_salary::Pallet::<Runtime, SecretarySalaryInstance>::claim` extrinsic, the resulting XCM descends into `PalletInstance(FELLOWSHIP_SALARY_PALLET_INDEX)` on AssetHub and debits the sovereign account `(Parent, Parachain(Collectives), PalletInstance(64))` — the Fellowship Salary pallet's account — not any Secretary-specific account. This is confirmed directly by the existing test's own comment and setup, which funds the Fellowship interior location's derived account to make a Secretary salary payment succeed: [5](#0-4) 

No barrier, filter, or origin check in the salary-claim path validates which sovereign account is actually being drained; `pallet_salary::claim` is callable by any account registered for a salary in that instance, and the paymaster's account selection is purely a compile-time type parameter, not something checked against instance identity at runtime.

### Impact Explanation
Asset-accounting isolation between the Fellowship Salary and Secretary Salary instances is broken: an unprivileged Secretary member's routine salary claim silently spends from the Fellowship Salary pool's sovereign account on AssetHub instead of a dedicated Secretary account. This can (a) drain the Fellowship Salary sovereign account of funds intended only for Fellowship members' salaries, reducing/denying legitimate Fellowship payouts, and (b) make Secretary claims fail with "insufficient balance" if only a Secretary-specific account (matching the documented intent of a per-instance sovereign account) is funded, since that account is never referenced by the paymaster. Both are violations of the intended asset segregation between the two `pallet_salary` instances, even though both pools are governance/treasury-controlled funds rather than arbitrary third-party user assets.

### Likelihood Explanation
The bug requires no special privilege — it is triggered automatically by any Secretary Collective member performing the ordinary, unprivileged salary `claim` flow (`pallet_salary::Pallet::<Runtime, SecretarySalaryInstance>::claim`). It is deterministic and 100% reproducible on every claim, since the account used is fixed at compile time via the type alias, and requires no attacker crafting of messages — it is a pure runtime configuration defect that is always triggered as soon as governance funds the Fellowship Salary account and Secretary claims occur.

### Recommendation
Define a dedicated `SecretarySalaryInteriorLocation` parameter type in `secretary/mod.rs`, mirroring the Fellowship/Ambassador pattern:
```rust
parameter_types! {
    pub SecretarySalaryInteriorLocation: InteriorLocation =
        PalletInstance(<crate::SecretarySalary as PalletInfoAccess>::index() as u8).into();
}
```
and use `SecretarySalaryInteriorLocation` (not `crate::fellowship::FellowshipSalaryInteriorLocation`) as the first generic parameter of `SecretarySalaryPaymaster`. Update deployment/funding runbooks and the `AssetHubPolkadot` `FellowshipTreasuryPaymasterEntities`/fee-waiver contains-checks (`xcm_config.rs`) if the Secretary pallet index needs to be added to those allow-lists.

### Proof of Concept
Extend the existing xcm-emulator test suite (`integration-tests/emulated/tests/collectives/collectives-polkadot/src/tests/collectives_salary.rs`) with a test that:
1. Computes `secretary_expected_account = LocationToAccountId::convert_location(&(Parent, Parachain(CollectivesPolkadot::para_id()), PalletInstance(SECRETARY_SALARY_PALLET_ID)).into())`.
2. Computes `fellowship_account = LocationToAccountId::convert_location(&(Parent, Parachain(CollectivesPolkadot::para_id()), PalletInstance(FELLOWSHIP_SALARY_PALLET_ID)).into())`.
3. On `AssetHubPolkadot`, mints USDT only into `secretary_expected_account` (leaving `fellowship_account` at 0).
4. On `CollectivesPolkadot`, calls `SecretarySalaryPaymaster::pay(&pay_to, (), pay_amount)` (simulating a Secretary member's `claim`).
5. Asserts the payment **fails** (or the XCM `TransferAsset` at destination fails / no `Transferred` event) because the funded account (`secretary_expected_account`) is never actually debited — proving isolation is broken since the paymaster instead attempts to debit `fellowship_account`.
6. Conversely, mint USDT into `fellowship_account` only, call the same `pay`, and assert `pallet_assets::Event::Transferred` shows `fellowship_account` as the source — proving Secretary claims spend Fellowship's funds, matching the finding.
