### Title
Autonomous Agents silently drop fixed-denomination (indivisible/NFT-like) asset payments, permanently trapping such assets sent to an AA - (File: aa_composer.js)

### Summary
Obyte's Autonomous Agents (`AA`s) are the closest analog to smart contracts in ocore. When an AA tries to construct any outgoing `payment` message for a `fixed_denominations` asset (the ocore equivalent of a non-fungible/indivisible token), `aa_composer.js` deliberately skips completing that payload and then strips the message out of the response unit entirely, treating the AA as having simply "eaten" the funds. This is functionally the same failure mode as the ERC-721 report: value that reaches a contract-like recipient can become permanently unrecoverable because the recipient's code path has no way to move it onward — except here it applies even to the AA's own bounce/refund mechanism, so the asset can never leave the AA once received.

### Finding Description
In `handleTrigger`'s `sendUnit` function, when building outgoing payment messages for a non-base asset, the code explicitly special-cases `fixed_denominations` assets by skipping payload completion and adding a comment that it "will skip it later": [1](#0-0) 

Shortly after, any message that still references a `fixed_denominations` asset is filtered out of the outgoing message set entirely, and if no messages remain the AA finishes with an empty, "successful" response instead of an error: [2](#0-1) 

Critically, the same `sendUnit` code path is used by the AA's own automatic bounce/refund logic (`bounce()`), which iterates the trigger's received outputs per asset and builds refund payment messages to send back to the sender: [3](#0-2) 

Because `bounce()` calls `sendUnit(messages)` just like any AA-authored response, a refund message carrying a `fixed_denominations` asset goes through the exact same filtering in `sendUnit` and is silently dropped rather than refunded. The framework even acknowledges this pattern generically: when all messages are filtered out, the AA "eat[s] the received coins and sends no response, state changes are still performed": [4](#0-3) 

The AA definition/oscript layer has no visibility into or workaround for this — an AA author cannot construct a valid `payment` message moving a `fixed_denominations` asset, whether for a deliberate transfer/forward, a refund, or a bounce. The `trigger.outputs` aggregation used by triggers does not distinguish asset type, so nothing prevents a fixed-denomination asset from being sent to an AA address as part of a trigger unit: [5](#0-4) 

### Impact Explanation
Any indivisible/fixed-denomination asset (ocore's analog to an NFT) sent to an AA address — whether intentionally, by user error, or as part of a multi-output unit that also funds an AA trigger — becomes permanently and irrecoverably stuck in that AA's balance. There is no way for the AA (via oscript `messages`) or the built-in bounce mechanism to move it back out, since both paths funnel through the same `sendUnit` logic that strips fixed-denomination payment messages. This is a permanent freezing of AA-held funds, matching the "AA fund loss or freezing" impact category, and for a valuable indivisible asset this loss can be significant and total.

### Likelihood Explanation
This triggers on any ordinary interaction: any unit that pays a `fixed_denominations` asset to an AA address (e.g., a user mistakenly sending an indivisible asset to an AA expecting a swap/forward, or an AA-composed protocol that intends to route such assets through intermediate AAs) reaches this code path deterministically — there is no attacker-controlled or malicious-peer precondition required, only a normal payment output to an AA.

### Recommendation
Either:
1. Support constructing valid single-input payment messages for `fixed_denominations` assets from AAs (respecting the "exactly 1 input" and denomination-divisibility constraints enforced in `validatePaymentInputsAndOutputs`), so AAs can transfer/forward/bounce them like any other asset, or
2. If genuinely unsupported, reject/bounce such units before they can credit the AA's balance (e.g., during `validateAATrigger`/`checkAAOutputs`) with a clear error, rather than silently accepting the funds into an unrecoverable state via `handleSuccessfulEmptyResponseUnit`.

### Proof of Concept
1. Define an asset with `fixed_denominations: true` (an indivisible/NFT-like asset) and issue one unit of it.
2. Post a unit paying that asset (and enough `base` to cover `bounce_fees`) to an AA address, where the AA's `messages` template attempts to forward or refund that asset in a `payment` message.
3. Observe in `aa_composer.js` that during `sendUnit`, the payload for the fixed-denomination asset is never completed (`fixed_denominations` branch at aa_composer.js:1327) and the message is filtered out at aa_composer.js:1356, so the AA "eats" the asset with no error and no refund.
4. Observe that even if `bounce_fees` includes this asset, `bounce()` (aa_composer.js:930-940) builds a refund `payment` message for it, but that message is routed through the identical `sendUnit`/filtering logic and is likewise dropped — the asset can never be returned to the sender or moved anywhere else, leaving it permanently stuck in the AA's balance.
