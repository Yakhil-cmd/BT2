### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-repository forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to use for HMAC verification from one field of the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), while every webhook `Handler` resolves the actual `Stack`/`Repository` to mutate from a *different* field of the same body (`repository.full_name`). These two fields are never bound to each other by the signature check itself, so an attacker who can satisfy the signature check for *any one* onboarded organization can freely set `repository.full_name` to point at a completely different, victim repository/stack.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` instance used for signature verification using only the organization login extracted from the untrusted body: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` is a no-op — it returns `true` unconditionally — whenever the resolved organization's config has no `webhook_secret` set: [3](#0-2) 

Meanwhile, every `Handler` subclass resolves the target repository/stack from a **different** field of the same JSON body — `repository.full_name` — completely independent of whatever organization was used to pass (or bypass) the signature check: [4](#0-3) 

`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, and the pull-request handlers all inherit this behaviour, and mutate state (enqueue `GithubSyncJob`, create `Status` records, enqueue `RefreshCheckRunsJob`, mutate `PullRequest`/review stacks) purely based on `repository.full_name`: [5](#0-4) 

This breaks the intended binding: **the organization whose secret authenticated the request must equal the repository whose state gets written.** Since the JSON body is fully attacker-controlled when POSTing directly to the public, unauthenticated `/webhooks` endpoint, an attacker who satisfies the signature check for organization A (e.g., because A's config has no `webhook_secret`, which the engine explicitly treats as "always valid") can set `repository.full_name` to `victim-org/victim-repo` — a completely unrelated organization's repository, tracked by the same Shipit instance — and have handlers act on it as if GitHub had authentically delivered that event for the victim repository.

### Impact Explanation
This is a cross-repository write / effective authentication-bypass: a request that is only "authenticated" for organization A can drive create/update operations (commit statuses, sync jobs, pull-request/review-stack state, check-run refreshes) against organization B's stacks. Forged commit `Status` webhooks are particularly dangerous because `ci.require`/`ci.blocking` deploy gating in `shipit.yml` relies on these `Status` records; an attacker able to forge statuses for a victim repository can satisfy CI requirements and enable an otherwise-blocked deploy to proceed — an unauthorized deploy path.

### Likelihood Explanation
Requires that at least one organization onboarded to the Shipit instance has signature verification effectively disabled (missing `webhook_secret`) or that the attacker otherwise satisfies the check for any org — a configuration explicitly supported by `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` short-circuit. No GitHub credentials, Shipit session, or API token are required — only the ability to send an HTTP POST to the public `/webhooks` route.

### Recommendation
Bind the two fields together: after selecting the organization used for signature verification (`repository.owner.login` / `organization.login`), require that every field the handlers key off (`repository.full_name`'s owner segment) matches that same organization before processing, or resolve the target repository/stack using the same field that was cryptographically verified. Additionally, consider making `webhook_secret` mandatory (fail closed rather than fail open) rather than treating an absent secret as automatically valid.

### Proof of Concept
1. Shipit instance tracks two orgs: `attacker-org` (webhook_secret unset/blank) and `victim-org` (any config).
2. Attacker POSTs directly to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and `verify_webhook_signature` returns `true` unconditionally because `attacker-org` has no `webhook_secret` configured — [6](#0-5) .
4. `PushHandler#process` resolves stacks via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [4](#0-3)  and enqueues `GithubSyncJob` for the victim's stack, entirely unauthenticated with respect to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
