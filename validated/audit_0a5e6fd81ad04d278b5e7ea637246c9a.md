### Title
Disabled trust-level check lets indirect (introduced) correspondents send privileged wallet/contract messages as if directly paired - (File: wallet.js)

### Summary
The Theia advisory describes a failure to verify the communication channel of an incoming `postMessage()`, letting content that arrived through an untrusted path (compromised webview) be treated as if it came from the trusted extension host. The ocore analog is in the device-messaging trust model in `wallet.js`'s `handleMessageFromHub`: the code computes `bIndirectCorrespondent` (whether the sender was only learned about indirectly, e.g. as a shared-address cosigner, rather than through an explicit pairing exchange) but the check that was supposed to restrict what an indirect correspondent may say is commented out, so the "channel type" is never actually verified before dispatching privileged subjects.

### Finding Description
`device.js`'s `handleJustsaying` for `hub/message` looks up the sender in `correspondent_devices` and passes `rows[0].is_indirect` to `handleMessage`, which emits `handle_message_from_hub` with `bIndirectCorrespondent` as a parameter: [1](#0-0) 

`wallet.js`'s `handleMessageFromHub` receives this flag but the intended enforcement is dead code: [2](#0-1) 

Once inside `doHandle()`, the `switch(subject)` dispatches every subject — `sign`, `private_payments`, `arbiter_contract_offer`, `arbiter_contract_response`, `removed_paired_device`, etc. — purely based on cryptographic authenticity of the sender's permanent key (verified earlier in `device.js`), with no differentiation between a correspondent who was explicitly paired (channel verified by the user scanning/accepting a pairing code, see `handlePairingMessage`) and one who was only indirectly introduced (e.g., a cosigner discovered while creating a shared wallet, added via `addUnconfirmedCorrespondent`/wallet-defined-by-keys flows) and is marked `is_indirect=1`: [3](#0-2) [4](#0-3) 

The commented-out line explicitly documents the original security intent — restrict indirect correspondents to a narrow allow-list of subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`) — i.e., the "channel" through which the correspondent's identity was established was meant to gate which message types are trusted. That gate is disabled, so the channel-of-introduction is never verified, and an indirect correspondent is treated identically to a fully-paired one for all message subjects, including `sign` (which drives the `signing_request` UI confirmation flow) and `arbiter_contract_offer`/`arbiter_contract_response` (which drive shared/arbiter-contract fund flows).

### Impact Explanation
An indirect correspondent — someone the user never explicitly paired with but who became known only because they cosign a shared/multisig address with the user — can send `sign` requests for arbitrary units/addresses that reach the wallet's signing-request UI as if from a trusted peer, and can send `arbiter_contract_offer`/`arbiter_contract_response` messages that mutate arbiter-contract state (`arbiter_contract.store`, `arbiter_contract.setField`) attributed to that address. Because the intended restriction gating these subjects to trusted, directly-paired correspondents is inert, this weakens the multisig/shared-address trust boundary: a user relying on the "indirect correspondent" distinction to avoid acting on requests from parties they never verified out-of-band can be presented with signing/contract prompts that appear to come from a legitimately-known cosigner path, increasing the risk of a user being socially engineered into co-signing/approving a transaction that spends from a shared address (unauthorized spending) or corrupts arbiter-contract negotiation state.

### Likelihood Explanation
Reaching this requires the attacker to already be a device correspondent recorded with `is_indirect=1` — attainable simply by being included as a cosigner address in any shared wallet definition the victim participates in (a low bar, since shared address setup routinely adds counterpart devices as unconfirmed/indirect correspondents before any explicit pairing confirmation). No hub or node compromise is needed; the attacker only needs to be a message sender over the normal encrypted device-messaging channel, and user interaction (confirming the signing dialog) is still required to realize a spending impact, matching the original advisory's `UI:R` characteristic.

### Recommendation
Re-enable and enforce the trust-based subject allow-list for `bIndirectCorrespondent`: reject (or fail closed) messages carrying `sign`, `private_payments`, `arbiter_contract_offer`, `arbiter_contract_response`, `removed_paired_device`, or other consequential subjects when the sender is only an indirect correspondent, unless the wallet explicitly upgrades that correspondent to a directly-paired/confirmed status. At minimum, restore the original check at `wallet.js:92-93` and audit all `case` branches in `doHandle()` to classify which subjects are safe to accept from unconfirmed/indirect correspondents versus which require full pairing trust.

### Proof of Concept
1. Attacker device becomes a cosigner in a shared wallet with the victim (a normal, low-privilege interaction that adds attacker as `correspondent_devices` with `is_indirect=1`), without the victim ever completing an explicit pairing/QR exchange with the attacker.
2. Attacker sends a `hub/message`-wrapped device message with `subject: "sign"` and a crafted `body.unsigned_unit`/`body.address`/`body.signing_path` referencing a shared address the victim controls.
3. Because `bIndirectCorrespondent` gating is commented out (`wallet.js:92-93`), the message reaches the same `case "sign"` handling as a fully-trusted, directly-paired correspondent would, triggering the `signing_request` UI event for the victim as if it came from a verified channel.
4. If the victim approves the resulting UI prompt (believing it originates from a trusted cosigning flow), funds from the shared address can be spent per the attacker's crafted terms — an outcome the disabled check was specifically designed to prevent for indirectly-known correspondents.
