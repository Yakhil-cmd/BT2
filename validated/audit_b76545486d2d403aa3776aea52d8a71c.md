### Title
Unvalidated route pools can inject unauthorized wallet-token transfers into the caller’s signed authorization tree - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
`swap_collateral` accepts caller-provided route bytes and forwards them to the configured router after only authorizing the intended collateral transfer. The router resolves pool addresses from those route bytes and invokes venue-specific functions without validating the pool against an allowlist. A malicious pool can therefore execute `token.transfer(victim, attacker, amount)` while the victim’s authorization is active. Simulation records that transfer as a child of the victim’s `swap_collateral` authorization; if the victim signs the resulting tree, the unrelated wallet-token transfer executes.

### Finding Description
`process_swap_collateral` authenticates the caller and verifies ownership/delegation, then withdraws collateral and calls `withdraw_and_swap_from_supply`. [1](#0-0)  That leg swaps the withdrawn collateral through `swap_tokens_or_passthrough`. [2](#0-1) 

For a cross-token route, the controller snapshots input/output balances, authorizes only `token_in.transfer(controller, router, amount_in)`, and invokes `router.execute_strategy(controller, amount_in, swap)`. [3](#0-2)  The checks afterward constrain controller-held input/output balances and positive output, but do not constrain other calls made below the router. [4](#0-3) 

The router decodes the attacker-controlled `assets` registry and dispatches each swap to `hop.pool`, `hop.token_in`, `hop.token_out`, and `hop.venue`. [5](#0-4)  Venue selection is by opcode only; there is no check that the selected pool belongs to the venue or an approved registry. [6](#0-5)  For example, the Soroswap adapter invokes `get_reserves` and `swap` on the payload-selected pool. [7](#0-6) 

A contract implementing the selected venue ABI can therefore execute arbitrary logic during the hop, including a token transfer from the original caller. The regression test demonstrates a payload-selected pool calling `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. [8](#0-7)  Recording simulation attaches that token transfer beneath the caller’s `swap_collateral` authorization entry. [9](#0-8)  In enforcing mode, a root-only authorization rejects it, but the poisoned authorization tree returned by simulation authorizes and executes it. [10](#0-9) 

### Impact Explanation
The attacker can steal any wallet token held by the victim, including tokens unrelated to the supplied collateral and not listed by the protocol. The controller’s `RouterOverspend` and `NoSwapOutput` checks only measure the routed input/output tokens and do not bound unrelated token transfers. The test loses the victim’s entire `WALLET_BALANCE` while still producing a valid collateral output. [11](#0-10) 

This is theft of user funds. The same authorization-tree injection pattern applies to every controller strategy that forwards caller-controlled route bytes to the router, not only `swap_collateral`.

### Likelihood Explanation
An unprivileged attacker can deploy the malicious pool contract and construct route bytes naming it. The remaining prerequisite is victim interaction: the victim must submit a transaction built with the malicious route and sign the authorization tree containing the injected transfer. Wallets or integrations that present only the root operation, or users who do not inspect nested authorization entries, make this practical. An honest root-only signature prevents the transfer. [12](#0-11) 

### Recommendation
Do not execute payload-selected pool addresses without validation. Maintain an on-chain registry keyed by venue, token pair, and pool address, populated through governance after verifying the pool ABI and token ordering. Alternatively, derive pool addresses from a trusted venue factory/registry on-chain rather than accepting them directly in route bytes.

Additionally, wallets and transaction builders must reject a strategy authorization tree containing any child outside the expected protocol token pull. An honest composed strategy should have no caller child transfer; a direct router swap should contain only the intended input transfer. This client-side check is necessary but does not replace pool allowlisting, since benign-looking or opaque authorization presentation can still hide malicious children.

### Proof of Concept
1. Alice supplies USDC and owns `WALLET_BALANCE` of an unrelated token.
2. Attacker deploys a pool implementing the selected venue’s query and swap ABI.
3. The malicious `swap` implementation calls `unrelated_token.transfer(alice, attacker, WALLET_BALANCE)` and returns enough `token_out` for the router’s measured-output and minimum-output checks.
4. Attacker supplies route bytes whose `assets` registry names that pool.
5. Alice calls:

```text
swap_collateral(
    caller = alice,
    account_id = alice_account,
    current = USDC HubAssetKey,
    from_amount = 5_000 USDC,
    new = ETH HubAssetKey,
    swap = route_bytes_naming_malicious_pool,
)
```

6. The controller withdraws USDC, calls the router, and the router calls the malicious pool. [13](#0-12) 
7. Simulation records an authorization tree containing the unrelated `transfer(alice, attacker, WALLET_BALANCE)` beneath Alice’s `swap_collateral` root. [14](#0-13) 
8. If Alice signs that tree, the token transfer succeeds: Alice’s unrelated-token balance becomes zero and the attacker receives `WALLET_BALANCE`, while the strategy still deposits the expected ETH collateral. [15](#0-14)

    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),

        sub_invocations: std::vec![stolen_transfer],
    };

    assert_eq!(s.wallet(&s.alice), 0);
