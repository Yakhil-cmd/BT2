### Title
AA constant-product/ratio exchange formulas relying on live `balance[...]` state without a mandatory minimum-output slippage check enable sandwich attacks on legitimate traders - (File: formula/evaluation.js, aa_composer.js)

### Summary
Any AA that implements a spot-balance-based exchange/AMM (as documented in `test/samples/uniswap_like_market_maker.oscript`) computes a payout using `balance[asset]` values read at the moment the trigger is executed [1](#0-0) , without oscript providing any built-in mechanism to specify or enforce a minimum acceptable output for a trigger. Because AA triggers within a stabilized MCI are processed in a fully deterministic order (`ORDER BY units.level, units.unit, address`) that is influenced by the unit's position/level rather than protected pricing [2](#0-1) , an attacker can post a manipulating trigger designed to land immediately before a victim's exchange trigger, shifting `balance[$asset]`/`balance[base]` just before the victim's formula runs, and then reverse the manipulation afterward — a classic sandwich, mirroring the Velocimeter `exerciseLP` bug where a fixed input amount combined with a spot-reserve-derived counter-amount and no minimum-output check let an attacker degrade the victim's received value.

### Finding Description
The vulnerable pattern is:
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
$p = $asset_balance * $bytes_balance;
$new_asset_balance = round($p / balance[base]);
$amount = $asset_balance - $new_asset_balance;
``` [3](#0-2) 

`$amount` (the payout) is entirely a function of the *current* on-chain balances of the AA address, which `formula/evaluation.js`'s `balance` operator reads live from `objValidationState.assocBalances` / `aa_balances` at execution time [4](#0-3) . The trigger sender has no way to encode "minimum acceptable `$amount`" that the AA is required to honor — the language and this reference design provide no slippage-bound primitive, exactly as `OptionTokenV4.exerciseLP` supplied a fixed `_amount` and let `paymentAmountToAddLiquidity` float with spot reserves.

Combined with the deterministic trigger-processing order derived from unit `level`/`unit` hash rather than from timestamp of trigger submission by the trader [2](#0-1) , and the fact that `aa_composer.handleAATriggers` processes all triggers for a newly-stable MCI in that fixed order before moving to the next MCI [5](#0-4) , a unit author can arrange (via parent selection / unit hash grinding, or simply by having their manipulating unit stabilize in the same or an earlier MCI with a lower `level`) to have their own balance-shifting trigger execute right before the victim's, then reverse it right after, capturing the difference at the victim's expense.

### Impact Explanation
A victim exchanging bytes/asset through such an AA receives a payout computed against an attacker-manipulated ratio instead of the ratio they observed when submitting their unit, resulting in concrete fund loss to the victim and profit to the attacker — the same "loss of value" impact class as the H-5 report (undervalued liquidity/output from unprotected spot-based formulas). Because state variables like `var['mm_asset_outstanding']` and balances are also mutated as part of this flow, repeated exploitation can also skew share-accounting for other depositors.

### Likelihood Explanation
Likelihood is Medium: exploitation requires an AA actually deployed with this spot-balance exchange design (which ocore ships as its canonical example/tutorial for building a market maker), and requires the attacker to win DAG ordering against the victim's trigger, which is achievable by any unprivileged unit poster using normal parent selection, without any special privilege, network position, or protocol upgrade.

### Recommendation
Provide an oscript primitive (or strongly recommend in AA design guidance) for traders to pass a `min_amount`/`max_slippage` parameter in `trigger.data` that the AA's `if`/`init` formula must validate against the computed `$amount` before sending the payment message, bouncing the trigger if the computed output falls short of the trader-specified minimum — mirroring how `addLiquidity`'s `amountAMin`/`amountBMin` should be wired to user intent rather than left at `1`. Additionally, consider documenting in the reference `uniswap_like_market_maker.oscript` sample that spot balances are manipulable within the same DAG-ordering window and that production AMM-style AAs must implement slippage protection via `trigger.data`.

### Proof of Concept
1. Deploy an AA using the `uniswap_like_market_maker.oscript` pattern (or an author-written equivalent) with case `// exchange bytes to asset` [3](#0-2) .
2. Victim broadcasts a unit sending `1e5+` bytes to the AA, expecting `$amount` of `$asset` based on the balances they observed.
3. Attacker, before the victim's trigger is processed (by controlling parent selection so their unit's `level`/`unit` sorts earlier per the `ORDER BY units.level, units.unit, address` rule in `handleAATriggers` [2](#0-1) ), sends a large "asset-to-bytes" trigger to the same AA, shifting `$asset_balance`/`$bytes_balance` unfavorably for the upcoming bytes-to-asset exchange.
4. Victim's trigger executes against the now-skewed balances, computing a smaller `$amount` of `$asset` per `formula/evaluation.js`'s live `balance[]` read [4](#0-3)  than the victim intended, with no mechanism in the trigger to reject the unfavorable result.
5. Attacker reverses their position with a follow-up trigger, netting the difference extracted from the victim.
