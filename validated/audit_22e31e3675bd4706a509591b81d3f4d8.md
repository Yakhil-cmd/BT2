### Title
Cross-organization webhook confused-deputy: signature verified against one GitHub org's `webhook_secret`, but the effect is applied to any repository/commit on the instance - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to verify the HMAC signature against using an attacker-controlled JSON field (`repository.owner.login` / `organization.login`) taken from the same unverified payload that the handlers later act on. Handlers such as `Shipit::Webhooks::Handlers::StatusHandler` never re-check that the commit/repository being mutated actually belongs to the organization whose secret produced a valid signature. The binding "organization that authenticated" == "repository/commit that is written" is never enforced.

### Finding Description
`verify_signature` derives the org used for HMAC verification purely from payload content: [1](#0-0) [2](#0-1) 

So `Shipit.github(organization: repository_owner)` — and therefore which `webhook_secret` is used to `verify_webhook_signature` — is chosen by a field the attacker fully controls inside the very payload being signed. [3](#0-2) 

Once the signature checks out for *that* org, `create` dispatches the parsed JSON to all handlers for the event with no further binding to the org that was actually authenticated: [4](#0-3) 

`StatusHandler#process` then looks up commits **globally by SHA**, with no repository/organization scoping at all: [5](#0-4) 

Consequently, an attacker who legitimately controls (and thus knows) the `webhook_secret` for **any one organization/App** configured on a shared Shipit instance can:
1. Build a `status` event JSON body containing `repository.owner.login` (or `organization.login`) = their own org (to select their own known secret), plus `sha`/`state` fields pointing at a commit belonging to a **different** organization/repository tracked by the same instance.
2. Sign the raw body with their own known secret and POST it to `/github/webhooks` (or whichever route mounts `WebhooksController`).
3. `verify_signature` succeeds because the signature is valid for the org the attacker selected.
4. `StatusHandler` updates `Commit.where(sha: params.sha)` for *any* matching commit across the whole instance via `commit.create_status_from_github!`, regardless of which org "authenticated."

Other handlers (`PushHandler`, `PullRequest::*Handler`) are similarly susceptible: they resolve the target repository from `payload.dig('repository', 'full_name')`, a field independent of `repository.owner.login`/`organization.login` used for secret selection, so the same top-level payload can select org A's secret while acting on org B's repository: [6](#0-5) [7](#0-6) 

### Impact Explanation
This breaks the binding: `organization whose signature authenticated the request` == `repository/commit that is written`. The most severe consequence is via `StatusHandler`: forged CI status is written for a commit that does not belong to the authenticating org, and `Commit#deployable?` depends directly on that status: [8](#0-7) 

and `schedule_continuous_delivery` triggers `ContinuousDeliveryJob` as soon as the commit becomes `deployable?`: [9](#0-8) 

An attacker who controls a legitimate, low-privilege org/App webhook secret on a multi-tenant Shipit deployment can therefore forge a "success" CI status for a commit in a completely unrelated, higher-privilege repository/stack, unblocking continuous deployment and causing an unauthorized deploy — matching the High-impact category "escalation ... unauthorized deploy" defined in scope. Secondarily, `PushHandler`/PR handlers allow triggering `GithubSyncJob`, archiving/unarchiving review stacks, or creating fake `Team`/`User` records for stacks outside the attacker's own organization.

### Likelihood Explanation
This requires the attacker to legitimately possess (not steal) the `webhook_secret` for at least one organization configured on the same multi-tenant Shipit instance — a realistic precondition for any Shipit deployment onboarding multiple orgs/teams, none of which needs privileged access to the *target* org/repository being spoofed. `sha` values are not secrets (visible on GitHub, in commit messages, CI logs, etc.), so guessing/obtaining a target commit sha is trivial. No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only the org-scoped `webhook_secret` of any one tenant.

### Recommendation
After `verify_webhook_signature` succeeds, thread the authenticated `repository_owner`/organization through to `Shipit::Webhooks.for_event` and have every handler assert that the payload's actual `repository.full_name` owner (and, for `StatusHandler`, the resolved `Commit#stack#repository`) matches the organization whose secret verified the signature; reject/discard events where they diverge instead of trusting the payload's self-reported repository fields uniformly.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `acme` (attacker-controlled, webhook secret known to attacker) and `victim` (target org with an existing tracked stack/commit).
2. Attacker builds JSON body:
```json
{
  "repository": {"owner": {"login": "acme"}, "full_name": "victim/app"},
  "organization": {"login": "acme"},
  "sha": "<victim commit sha, publicly known>",
  "state": "success",
  "context": "ci/tests"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(acme_webhook_secret, raw_body)>` and POSTs to the webhooks endpoint with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"acme"` from the payload, fetches `Shipit.github(organization: "acme")`, and the signature verifies successfully against `acme`'s known secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the `victim/app` commit regardless of the `acme` binding — and calls `commit.create_status_from_github!`, writing a forged `success` status for a commit the attacker does not control, potentially satisfying `Commit#deployable?` and triggering `ContinuousDeliveryJob` for the `victim` stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
