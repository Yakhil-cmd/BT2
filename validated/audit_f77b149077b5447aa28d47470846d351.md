### Title
Webhook organization used for HMAC-signature selection is decoupled from the repository the event handlers actually mutate - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/`webhook_secret` to validate the incoming payload against using an organization name pulled from the untrusted request body itself, while the individual `Handler` subclasses that execute the side effects (creating commits, syncing stacks, merging pull requests, etc.) key off a completely different attacker-controlled field: `payload['repository']['full_name']`. Because Shipit supports multiple GitHub organizations each with their own (optional) `webhook_secret`, an attacker can pick whichever configured organization has no secret set, authenticate "successfully" against that organization, and then supply a `repository.full_name` belonging to a *different*, secret-protected organization's stack.

### Finding Description
- `verify_signature` resolves the app/secret to check against like this: [1](#0-0) [2](#0-1) 

  `repository_owner` is read directly from the JSON body (`params.dig('repository','owner','login')`), falling back to `params.dig('organization','login')` if the `repository` key is absent — both are attacker-controlled fields inside the unauthenticated POST body.

- `Shipit.github(organization: repository_owner)` looks up the per-organization config (each organization may or may not have a `webhook_secret` configured — the setup docs and example secrets files explicitly show `webhook_secret: # nil` as a valid, supported configuration): [3](#0-2) 

- `verify_webhook_signature` short-circuits to `true` whenever the selected organization has no secret configured: [4](#0-3) 

- Once signature verification passes (using the *secret-less* organization's config), the actual event `Handler` never re-checks which organization was authenticated. It instead resolves the target `Stack`/`Repository` purely from `payload['repository']['full_name']`: [5](#0-4) 

  For example `PushHandler` calls `stack.sync_github(expected_head_sha: params.after)` for every stack matching that repository name/branch: [6](#0-5) 

The equality that should hold is:
`organization used to select/validate the webhook secret == owner of the repository whose stacks are mutated`

but nothing enforces this. The signature check authenticates "some configured organization identified by attacker-supplied JSON," while the handlers act on "whatever repository full_name the same attacker-supplied JSON contains." These two fields are never cross-validated against each other.

### Impact Explanation
In any Shipit deployment configured for multiple GitHub organizations (the multi-org config format is first-class, documented, and shown in `config/secrets.development.shopify.yml`/`config/secrets.development.example.yml`), if even one organization is configured without a `webhook_secret` (an explicitly supported, documented state), an unauthenticated attacker can:
1. Set `repository.owner.login` (or `organization.login`) to the secret-less organization to pass `verify_webhook_signature` trivially.
2. Set `repository.full_name` to a repository belonging to a *different*, secret-protected organization.
3. Have the resulting webhook processed as if it legitimately originated from GitHub for that protected repository — e.g. forging `push` events to trigger `GithubSyncJob`/`sync_github`, forging `status` events to inject/alter commit `Status` rows via `StatusHandler`, or driving `pull_request`/`membership` handlers — all against repositories the attacker has no relationship with and without ever possessing that organization's real webhook secret, an `ApiClient` token, a Shipit session, or GitHub credentials of any kind.

This crosses exactly the "unauthorized deploy" / cross-repository-write boundary the rules call out: attacker-forged commit/status/sync state for a repository outside the attacker's control, achieved purely by exploiting a decoupling between the authentication field and the acted-upon field.

### Likelihood Explanation
Likelihood is conditional but realistic: it only manifests in multi-organization Shipit installations, and only if at least one configured organization omits `webhook_secret`. Since the documented/example configs (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`) present `webhook_secret` as commented-out/optional per-organization, and nothing in the codebase enforces that either all organizations must configure a secret or that all must configure the *same* secret, this is a plausible, unprivileged, network-reachable misconfiguration-triggered vector rather than a purely theoretical one.

### Recommendation
- Bind the webhook signature verification to the specific route/organization context rather than trusting an organization name extracted from the unauthenticated payload, or
- After selecting the organization based on the payload for secret lookup, re-validate that the resolved `Repository`'s owner (from `payload['repository']['full_name']`) matches the same organization that was used to select/verify the secret, rejecting the request otherwise, or
- Require that all configured GitHub organizations either all define a `webhook_secret` or none does, and fail fast/refuse to boot in a mixed configuration to eliminate the secret-less-organization bypass path.

### Proof of Concept
1. Configure Shipit for two GitHub organizations: `org-open` (no `webhook_secret`) and `org-secret` (has a `webhook_secret`), each with stacks tracking their own repos, per `config/secrets.development.shopify.yml`.
2. Send an unauthenticated POST to `/github_webhooks` (`X-Github-Event: push`) with body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "org-secret/protected-repo", "owner": { "login": "org-open" } }
}
```
3. `verify_signature` computes `repository_owner` = `"org-open"`, loads `org-open`'s (secret-less) `GithubApp`, and `verify_webhook_signature` returns `true` unconditionally per [7](#0-6) , regardless of the (missing/garbage) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-secret/protected-repo")` — i.e. the real, secret-protected repository — and calls `sync_github` on it, per [6](#0-5) , even though the request was never authenticated against `org-secret`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
