### Title
`Commit.where(sha:)` in `StatusHandler#process` fans out one signed webhook's status write to every stack sharing that SHA, regardless of the payload's named repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no scoping to the repository named in the payload, so `create_status_from_github!` is applied to every `Commit` row across every `Stack`/repository that happens to share that SHA. Signature verification only proves the request came from *an* organization configured in Shipit (matched via `repository_owner`), not that the sender is authorized for every stack whose commit shares that SHA.

### Finding Description
The broken binding is: `one verified payload from repository R == mutation limited to Commit rows belonging to R's Stack(s)`. In code, `StatusHandler#process` is: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` has no `stack_id`, `repository`, or organization filter — it is a global lookup keyed only on the 40-character SHA. `verify_signature` in `WebhooksController` computes the HMAC using `Shipit.github(organization: repository_owner)`, i.e., it authenticates that the payload came from someone who knows the webhook secret configured for that specific GitHub organization: [2](#0-1) [3](#0-2) 

This proves authenticity of the sender for organization `repository_owner`, but it says nothing about which `Stack`/`Commit` rows should be affected — `StatusHandler` never re-checks `params.dig('repository', ...)` against the stacks it mutates. `Commit#create_status_from_github!` unconditionally writes a `Status` row via `add_status`/`statuses.replicate_from_github!`: [4](#0-3) 

Given a genuine GitHub status webhook (real signature, from an org actually configured in Shipit, e.g. because the attacker owns/administers a repository within that org or the org uses one shared webhook secret across many repos, per `docs/setup.md`'s "Using Multiple Github Applications" note and `secrets_double_github_app.yml` showing secrets are keyed per-organization, not per-repository), if the payload's SHA collides with a commit belonging to an unrelated tenant's stack (vendored dependency, cherry-pick, empty/initial commit, or any duplicated history), `Commit.where(sha:)` will match and mutate all of them in the same request. The attacker only "names" one repository in the payload body, but the handler ignores that field entirely for scoping.

Existing guards do not prevent this: `verify_signature` authenticates organization-level sender identity only, not per-stack/per-repository authorization; `drop_unhandled_event` and the `ExplicitParameters` schema (`params.sha`, `params.state`, etc.) validate shape, not scope; there is no `require_permission!`, `stacks` scope, or repository-name check anywhere in `StatusHandler`.

### Impact Explanation
A single legitimately-signed status webhook (attacker needs only the ability to trigger a GitHub status event for a repository/org that already has a valid Shipit webhook secret — e.g., their own repo under an org that shares that secret across repos, which the docs explicitly support) writes `Status` rows for every `Commit` across every `Stack` sharing the SHA, corrupting CI/deploy-readiness state (`deployable?`, `blocked?`, continuous-delivery scheduling) for unrelated tenants in one request. This matches the "payload for one repository mutating another's stack/commit" Critical category. Repeatable on any SHA collision the attacker can arrange or find (vendored/shared commits, cherry-picks, or coincidental identical trees), and scales to an unbounded number of matching stacks in a single HTTP request.

### Likelihood Explanation
Requires: (a) Shipit configured with an organization whose webhook secret is valid for the sender's request (a real precondition, but explicitly supported multi-repo/single-secret-per-org setup per `docs/setup.md`), and (b) a SHA that exists as a `Commit` in more than one `Stack`'s history — plausible for shared vendored dependencies, monorepo mirrors, or duplicated/rebased history across tenant repos on the same Shipit instance. No Shipit session, API token, or GitHub App private key is needed beyond the ability to trigger a genuine webhook for an already-integrated org/repo. Feasibility is moderate-to-high in any multi-tenant Shipit deployment sharing a webhook secret or GitHub App across repositories.

### Recommendation
Scope the lookup in `StatusHandler#process` to commits whose stack's repository matches the payload's `repository.full_name` (or `owner`+`name`), e.g. `Commit.joins(:stack).merge(Stack.where(repository: repo)).where(sha: params.sha)`, rejecting/ignoring matches outside that repository.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`):
1. Create three `Stack`s with distinct `Repository` records (different `owner`/`name`), each with a `Commit` sharing identical `sha: "abc123..."`.
2. Build a status webhook payload naming only stack #1's repository (`repository.full_name` = stack 1's repo), with `sha: "abc123..."`, `state: "success"`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(params)` directly (bypassing controller-level signature, as the finding is in the handler's scoping, not the signature check).
4. Assert: `Status.where(state: 'success').count == 3` even though only one repository was named in the payload — demonstrating `commit.stack.repository == payload.repository` fails to hold for 2 of the 3 mutated rows, i.e., the binding "one verified payload from one repository == mutation of exactly one repository's data" is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
