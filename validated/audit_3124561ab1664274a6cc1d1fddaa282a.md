### Title
Missing `return` after exception in private-payment hash computation causes duplicate/corrupted callback invocation - ([File: network.js])

### Summary
`handleSavedPrivatePayments`'s inner `validateAndSave` function in `network.js` computes a hash of an attacker-controlled private-payment payload and, on failure, both finalizes the chain via `deleteHandledPrivateChain(..., cb)` *and* falls through to invoke `privatePayment.validateAndSavePrivatePaymentChain(...)` again, calling the `async.each` iteratee callback `cb` a second time.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` iterates over saved/unhandled private payment chains and, for each one, calls an internal `validateAndSave` closure: [1](#0-0) 

The `try` block computes `json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true)`. If this throws, the `catch` block sends an error result and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which itself invokes `cb`, completing this iteration of `async.each`. However, there is **no `return` statement after the `catch` block**, so execution continues past it: `json_payload_hash` is `undefined`, a `key` string is built from it, and `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` is invoked a second time on the same data, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers each call `cb` again.

This is directly analogous to CVE-2019-12312's root cause: the code assumes a particular linear control-flow / message sequence (hash succeeds → proceed) but fails to account for the alternate branch (hash throws → chain already finalized), and continues executing state-mutating logic that was designed only for the "normal" path — exactly like `send_v2N_spi_response_from_state()` dereferencing state that was never properly established because an unexpected message (bogus INFORMATIONAL instead of IKE_AUTH) short-circuited the expected flow. Here, the "unexpected message" is a private-payment chain whose head payload cannot be canonically hashed by `getBase64Hash`/`getSourceString` (e.g., due to unusual value types, oversized structures, or other inputs accepted by `JSON.parse` but rejected by `string_utils.getSourceString`/`getJsonSourceString`), which a **private-payment counterparty** fully controls when constructing and sending the private chain payload via `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`.

Calling `cb` twice inside `async.each` in Node's `async` library throws `Error: Callback was already called`, which is an **uncaught exception** in this code path (not wrapped in try/catch at this call site), and by default crashes the Node.js process — the direct analog of "assertion failure leading to daemon restart" in the CVE.

### Impact Explanation
An uncaught exception here crashes the local ocore node/wallet process (Node's default `uncaughtException` behavior terminates the process unless a global handler exists). Because `handleSavedPrivatePayments` runs during normal processing of legitimately-received private payments (from a counterparty in a private transaction or forwarded chain), a malicious private-payment counterparty can repeatedly trigger this crash, causing denial of service against the specific node/wallet handling the transaction — preventing it from confirming new units or processing further private payments until restarted. This matches the CVE class of "unauthenticated remote input triggers state-machine mismatch → crash restart."

### Likelihood Explanation
The attack requires only that a counterparty craft a private-payment payload whose `payload` cannot be canonically source-stringified/hashed by `getBase64Hash(..., true)` while still passing the earlier lightweight structural checks in `handlePrivatePaymentChains` (`isNonemptyObject`, `isNonemptyString`, `isNonemptyArray` on `inputs`/`outputs`). Reaching the exact throw condition inside `string_utils.getSourceString`/`getJsonSourceString` was not independently confirmed within the indexed files, so likelihood should be treated as **medium and not fully verified** — the control-flow bug (missing `return`, double `cb()` call) is definitively present and reachable once any exception occurs in that `try` block, but the precise malformed-payload trigger for `getBase64Hash` to throw was not confirmed against `string_utils.js`, which was not available in the indexed context.

### Recommendation
Add a `return` immediately after `deleteHandledPrivateChain(...)` inside the `catch` block in `network.js`'s `validateAndSave` (around [2](#0-1) ) so execution does not fall through to compute `key` and re-invoke `privatePayment.validateAndSavePrivatePaymentChain`, which would call `cb` a second time. Additionally, wrap the whole `async.each` iteratee body in a try/catch (or ensure all internal exceptions are funneled through a single `cb(err)` call) to prevent any single malformed private-payment chain from crashing the entire node process.

### Proof of Concept
1. As a private-payment counterparty, construct a private-payment chain (`arrPrivateElements`) whose head element's `payload` passes the structural checks in `handlePrivatePaymentChains` (`isNonemptyObject`, `isNonemptyString(e.payload.asset)`, `isNonemptyArray(e.payload.inputs/outputs)`), but which causes `objectHash.getBase64Hash(payload, true)` → `string_utils.getJsonSourceString` to throw (e.g., by including a value type/shape not handled by the source-string serializer).
2. Send this chain to the victim node via the private-payment message flow (`handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → stored in `unhandled_private_payments` → later processed by `handleSavedPrivatePayments`).
3. When `handleSavedPrivatePayments` processes the row, `getBase64Hash` throws inside the `try` block at [3](#0-2) ; the `catch` calls `deleteHandledPrivateChain(..., cb)` (first `cb()` call), then execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again, whose callback invokes `cb()` a second time.
4. The second `cb()` call inside `async.each` throws `Error: Callback was already called`, propagating as an uncaught exception that crashes the node process.
