### Title
Memory leak of shared scheduler allocation on error path in `ExternalCheckWorker::check_resolve_pubkeys` / `check_batch` - ([File: core/src/banking_stage/transaction_scheduler/check_worker.rs])

### Summary
`check_batch` allocates a `CheckResponseRegion` from the shared `rts_alloc::Allocator` before doing per-transaction resolution work, then calls `check_resolve_pubkeys`, which itself allocates additional per-transaction `SharablePubkeys` regions from the same allocator inside a loop. Both functions propagate allocator-exhaustion failures with the `?` operator without freeing any of the allocations made earlier in the same call, so on an `AllocationFailure` the already-allocated response region and any already-allocated pubkey regions are never freed.

### Finding Description
`check_batch` first allocates the response array via `allocate_check_response_region`: [1](#0-0) 

Later, if the `LOAD_ADDRESS_LOOKUP_TABLES` flag is set, it calls `check_resolve_pubkeys` with the `?` operator, so any `Err` bubbles straight out of `check_batch` without freeing the response region allocated above: [2](#0-1) 

Inside `check_resolve_pubkeys`, for each transaction with address-lookup-table accounts, a new `SharablePubkeys` allocation is requested from the same shared allocator: [3](#0-2) 

If the allocator runs out of space while resolving the pubkeys for transaction *N* in the batch, the function returns `Err(ExternalCheckWorkerError::AllocationFailure)` via `ok_or(...)?`: [4](#0-3) 

At this point, every `pubkeys_allocation` made for transactions `0..N-1` in the same batch, as well as the outer response region allocated at the top of `check_batch`, is unreachable but never returned to the allocator with `Allocator::free`. This propagates further: `process_message` calls `check_batch` with `?`, `iterate` calls `process_message` with `?`, and `run` calls `iterate` with `?` in its main loop: [5](#0-4) 

This mirrors the CVE's bug class exactly ("missing unwind goto" — an early error return skips freeing resources already acquired earlier in the same function), except the "leaked" resource here is a bounded shared-memory arena (`rts_alloc::Allocator`) used for external-scheduler IPC rather than kernel heap memory.

I was unable to fully verify, within the available tool budget, (a) whether `rts_alloc::Allocator::allocate`/`free` are implemented such that leaked offsets can never be reclaimed (no garbage collection/generation reset), and (b) the exact call site in `core/src/banking_stage.rs` that wires `ExternalCheckWorker` into production leader startup, though the type and its worker loop are present and gated only by `#[cfg(unix)]`, not `#[cfg(test)]`, indicating it is production code reachable from a real leader.

### Impact Explanation
If the shared arena backing check-worker responses is a fixed-size region (as suggested by the `TRANSACTION_BATCH_SIZE_ASSERT: () = assert!(Self::TRANSACTION_META_END <= 4096)` invariant in the related `TransactionPtrBatch` type and the fixed `allocator_size` configured at session setup), repeatedly triggering this leak path (e.g., via transactions with many address-lookup-table entries under load) would permanently shrink the usable capacity of the allocator. Once exhausted, all subsequent `allocate` calls fail, and — more severely — the failure propagates all the way up through `run()`'s `?` chain, terminating the check-worker thread entirely rather than just skipping the offending message. Repeating this against every check-worker thread on a leader would degrade or halt that leader's ability to process/check transactions, a leader-side DoS reachable from ordinary unprivileged transaction submission (crafted ALT-heavy transactions).

### Likelihood Explanation
Reaching the leak requires driving the shared allocator into an actual `AllocationFailure`, which needs either sustained load or transactions engineered to maximize per-transaction allocation (e.g., transactions using the maximum number of address-lookup-table-resolved accounts) submitted repeatedly against a leader. This is plausible for an unprivileged sender but requires sending enough traffic/specific shapes to exhaust the bounded arena, which is a more probabilistic/DoS-style trigger rather than a single-transaction deterministic exploit.

### Recommendation
Add explicit `Allocator::free` cleanup on the error paths in `check_batch` and `check_resolve_pubkeys`: track all allocations made so far in the batch (response region and any per-transaction `pubkeys_allocation`) and free them before propagating `AllocationFailure`/other errors, instead of relying on the `?` operator to short-circuit without cleanup. Consider wrapping these allocations in an RAII guard type that frees on drop so early returns cannot leak allocator capacity.

### Proof of Concept
Conceptual reproduction (not a full harness, given ask-only/read-only constraints):
1. Configure/observe a leader running the external scheduler with a fixed-size `rts_alloc::Allocator` (`allocator_size` set at `ClientLogon` time, e.g. as in the test harness `setup_check_worker_test_frame` at [6](#0-5) ).
2. Submit a stream of ordinary (unprivileged, sanitization-passing) transactions that each reference the maximum number of address-lookup-table accounts, forcing `check_resolve_pubkeys` to allocate a `SharablePubkeys` region per transaction.
3. Continue submitting until the shared allocator has no free capacity; at that point some transaction's `pubkeys_allocation` call returns `None`, triggering `ok_or(ExternalCheckWorkerError::AllocationFailure)?` at [4](#0-3) .
4. Observe that the response region allocated earlier in `check_batch` (line 285-289) and any prior per-transaction pubkey allocations in the same call are never freed, and that the error propagates through `process_message` → `iterate` → `run`, terminating the check-worker thread.
