### Title
Unbounded private-payment chain length lets a counterparty DoS chain validation and block receipt of funds - ([File: indivisible_asset.js])

### Summary
`parsePrivatePaymentChain()` in `indivisible_asset.js` iterates the entire `arrPrivateElements` array supplied by the sending counterparty with no upper bound on its length, performing a DB query and a possibly expensive DAG-inclusion check for every element in strict series. A malicious (or merely careless) private-payment counterparty can construct an arbitrarily long ownership chain before finally sending the asset, forcing the recipient's node to walk the whole chain synchronously every time it tries to validate/accept the payment.

### Finding Description
Indivisible ("blackbyte") private assets track full transfer lineage back to issuance. `buildPrivateElementsChain()` recursively walks the chain of prior transfers with no depth limit [1](#0-0) , and the resulting `arrPrivateElements` array (ordered in reverse chronological order) is handed to the recipient.

When the recipient's wallet receives this chain (via `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`), the fixed-denomination (indivisible) branch calls `assetModule.validateAndSavePrivatePaymentChain(conn, arrPrivateElements, ...)` [2](#0-1) , which delegates to `parsePrivatePaymentChain`: [3](#0-2) 

This function has no check on `arrPrivateElements.length` and processes every element with `async.forEachOfSeries`, sequentially calling `validatePrivatePayment()` for each one. Each call performs a DB query for the spend proof and, for non-light nodes, `graph.determineIfIncluded()` to prove the input unit is included in the current unit's DAG history [4](#0-3)  — an operation whose cost also scales with the number of intervening units in the main DAG, not just the chain length.

No length cap for `arrPrivateElements` was found anywhere in the codebase (searches for `MAX_*_CHAIN`/chain-length constants returned no hits in `indivisible_asset.js`, `private_payment.js`, or `network.js`), unlike other places in ocore that explicitly bound arrays (e.g., 100-element caps in `formula/evaluation.js` and `formula/validation.js`). A sender who controls both ends of a chain of transfers (e.g., bouncing a blackbyte coin among their own addresses hundreds/thousands of times) can inflate the chain to an arbitrary size before finally sending it to a victim.

### Impact Explanation
This is directly analogous to the `CrabNetting` bug class: a per-payment array that only grows and is walked in full on every validation attempt. The victim's node must synchronously process the entire chain (DB queries + DAG inclusion proofs) inside `async.forEachOfSeries`, which is executed while holding the `handleJoint`/`saved_private` mutex path in `network.js` (`handleSavedPrivatePayments`) [5](#0-4) . A sufficiently long chain can stall validation of that private payment (and, because processing is serialized under mutexes, potentially delay other private-payment handling on the same node), and because `arrPrivateElements` never shrinks, every retry (e.g., after the process restarts and `handleSavedPrivatePayments` reprocesses `unhandled_private_payments`) must redo the full walk, effectively freezing the recipient's ability to accept/spend the funds carried in that payment.

### Likelihood Explanation
Any private-payment counterparty (an unprivileged party the report explicitly allows: "private-payment counterparty") can trivially construct such a chain themselves before initiating the transfer to the victim — no special privilege, hub cooperation, or protocol violation is required, since chained transfers of blackbyte coins are a normal, validator-accepted operation.

### Recommendation
- Enforce a maximum length on `arrPrivateElements` (e.g., reject chains beyond a small constant, similar to the 100-element caps used elsewhere in ocore for arrays/dictionaries) before beginning validation in `parsePrivatePaymentChain` / `validateAndSavePrivatePaymentChain`.
- Consider capping how deep `buildPrivateElementsChain` will recurse when composing outgoing private payments, and/or memoizing/caching `graph.determineIfIncluded` results across chain elements to bound per-element cost.

### Proof of Concept
1. Attacker issues (or owns) an indivisible private asset coin.
2. Attacker repeatedly sends the coin between two addresses they control, producing N private-payment elements chained via `inputs[0].unit/message_index/output_index` references (each accepted individually by `validatePrivatePayment`, since nothing limits total chain depth).
3. Attacker finally sends the coin to the victim and forwards the full `arrPrivateElements` chain (length N) via `handlePrivatePaymentChains`.
4. Victim's node calls `parsePrivatePaymentChain`, which processes all N elements in series, each requiring a DB round trip plus `graph.determineIfIncluded`, stalling validation/acceptance of the payment in proportion to N with no cap enforced anywhere in the code path.

function parsePrivatePaymentChain(conn, arrPrivateElements, callbacks){
	var bAllStable = true;
	var issuePrivateElement = arrPrivateElements[arrPrivateElements.length-1];
	if (!issuePrivateElement.payload || !issuePrivateElement.payload.inputs || !issuePrivateElement.payload.inputs[0])
		return callbacks.ifError("invalid issue private element");
	var asset = issuePrivateElement.payload.asset;
	if (!asset)
		return callbacks.ifError("no asset in issue private element");
	var denomination = issuePrivateElement.payload.denomination;
	if (!denomination)
		return callbacks.ifError("no denomination in issue private element");
	async.forEachOfSeries(
		arrPrivateElements,
		function(objPrivateElement, i, cb){
			if (!objPrivateElement.payload || !objPrivateElement.payload.inputs || !objPrivateElement.payload.inputs[0])
				return cb("invalid payload");
			if (!objPrivateElement.output)
				return cb("no output in private element");
			if (objPrivateElement.payload.asset !== asset)
				return cb("private element has a different asset");
			if (objPrivateElement.payload.denomination !== denomination)
				return cb("private element has a different denomination");
			var prevElement = null; 
			if (i+1 < arrPrivateElements.length){ // excluding issue transaction
				var prevElement = arrPrivateElements[i+1];
				if (prevElement.unit !== objPrivateElement.payload.inputs[0].unit)
					return cb("not referencing previous element unit");
				if (prevElement.message_index !== objPrivateElement.payload.inputs[0].message_index)
					return cb("not referencing previous element message index");
				if (prevElement.output_index !== objPrivateElement.payload.inputs[0].output_index)
					return cb("not referencing previous element output index");
			}
			validatePrivatePayment(conn, objPrivateElement, prevElement, {
				ifError: cb,
				ifOk: function(bStable, input_address){
					objPrivateElement.bStable = bStable;
					objPrivateElement.input_address = input_address;
					if (!bStable)
						bAllStable = false;
					cb();
				}
			});
		},
		function(err){
			if (err)
				return callbacks.ifError(err);
			callbacks.ifOk(bAllStable);
		}
	);
