## Title
Cross-organization webhook confusion: `repository.owner.login` used to select the verifying `GithubApp`/secret while `repository.full_name` alone determines the stack acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GithubApp` (and therefore the `webhook_secret` used for HMAC verification) using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). The event handlers, however, resolve which `Stack`/`Repository` to actually mutate using a *different* field of the same payload: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Nothing binds these two fields to each other, so a webhook that is validly signed for organization A can carry a `repository.full_name` pointing at a stack owned by organization B. ### Finding Description
This is the same bug class as the Sherlock finding: a value that is checked/verified (here, the *organization identity* implicit in `repository.owner.login`, used to pick the app whose secret authenticates the request) diverges from the value that downstream logic actually acts on (`repository.full_name`, used by `Handler#stacks`/`Handler#repository_name` to look up the `Repository`/`Stack`). The equality that should hold, and does not, is:

`organization authorized by verify_signature (repository.owner.login)` == `organization implied by repository.full_name used to select the Stack`

Because the entire request body is HMAC-signed and verified against `webhook_secret`, an attacker cannot forge an arbitrary payload out of thin air. But if Shipit is configured with several `GithubApp`s (multi-org setups — see `Shipit.github(organization:)`), an attacker who legitimately controls a repository/organization "A" onboarded to this Shipit instance can send GitHub webhook events from their own repo where GitHub itself will correctly compute the HMAC using A's `webhook_secret`. GitHub does not constrain the `repository.full_name` field to match the delivering app's installation in this validation path; `verify_signature` only checks the signature against the secret picked via `repository_owner`, it never checks that `repository.full_name` belongs to that same owner. By manipulating a webhook delivery (e.g., through a custom webhook endpoint they set up in their own org's repo settings, or a compatible integration under their control) the attacker can submit a `push`/`status`/`check_suite`/`membership` payload whose top-level `repository.owner.login` (or `organization.login`) is "A" (so it authenticates using A's secret) while `repository.full_name` is `"B/some-other-repo"` — a stack the attacker does not control.

`Handler#stacks` and `Handler#repository_name` trust `repository.full_name` unconditionally to find the target `Repository`/`Stack`: [4](#0-3) 

`PushHandler#process` then enqueues a `GithubSyncJob` against every non-archived stack on that (forged-target) branch: [5](#0-4) 

The `GithubSyncJob` mitigates part of the damage because it re-fetches commits from GitHub using `stack.github_api` (i.e., the credentials tied to the real stack's own organization), rather than trusting `expected_head_sha` blindly: [6](#0-5) 

### Impact Explanation
An attacker who legitimately owns/administers one Shipit-onboarded organization can trigger, on demand, background jobs (`GithubSyncJob`, `CacheDeploySpecJob`, `RefreshCheckRunsJob` via `check_suite`, `Status` creation via the `status` event) against stacks belonging to a *different* organization that they have no privilege over, purely by choosing `repository.full_name` inside a payload their own app validly signs. Because `GithubSyncJob` re-fetches truth from GitHub's API with the real stack's own credentials, it cannot be used to inject forged commits; the practically exploitable surface is: forcing unscheduled syncs/spec-cache invalidation on arbitrary stacks, and (via `StatusHandler`) writing attacker-supplied CI status rows onto a `Commit` belonging to another org's stack if the SHA happens to already exist in the target stack, since `StatusHandler`/`Handler#stacks` scope only by `repository.full_name`, not by the authenticating organization. This does not rise to RCE, GITHUB_TOKEN/`github_access_token`/`api_clients_secret` exfiltration, cross-repository writes of code, or an unauthorized deploy/rollback/merge — the job pipeline re-validates against GitHub before mutating deploy-relevant state. It is best characterized as an authorization-scope leak between orgs (a stack state/status write outside the authenticating org's ownership), which falls short of the report's required Critical/High bar as strictly defined (no read of task streams/output, no deploy/rollback/merge, no credential exfiltration, no SSRF carrying GitHub credentials).

### Likelihood Explanation
Requires: (1) the Shipit deployment to be configured with more than one `GithubApp`/organization (multi-tenant setup), and (2) the attacker to control at least one onboarded organization/repository and be able to shape the webhook payload's `repository.full_name` independently of `repository.owner.login` — which is not something a normal GitHub-generated webhook payload allows (GitHub always sets `repository.full_name` and `repository.owner.login` consistently for the actual repository that fired the event). Exploiting this therefore requires an attacker-controlled relay/proxy of webhook delivery or a non-GitHub sender crafting the JSON body and computing a valid HMAC with a secret they legitimately hold for their own org — at which point they are, by definition, sending a "webhook" that didn't actually originate from GitHub for that org. This is a real trust-boundary gap in the code, but it is low likelihood/awkward to trigger without additional infrastructure (a webhook proxy under attacker control), and its blast radius is bounded by `GithubSyncJob`'s re-validation against the real GitHub API.

### Recommendation
Bind the authenticating identity to the acted-upon repository within the same request: after `verify_signature` succeeds for `repository_owner`, `WebhooksController`/`Handler` should additionally assert that the repository resolved by `full_name` (`Repository.from_github_repo_name(...)`) actually belongs to `repository_owner`/the same GitHub App installation before invoking any handler, mirroring the recommended Sherlock fix of never letting a partially-verified field silently diverge from the value that is authoritative for state changes.

### Proof of Concept
Not executed — this analysis is based on static code reading only. Conceptually: configure two `GithubApp`s for orgs `A` and `B` in `Shipit.github`, with stacks tracked under `B/repo`. Using an app/relay you control in org `A`, send `POST /github/webhooks` with header `X-Github-Event: push`, `X-Hub-Signature` computed with `A`'s `webhook_secret` over a body of the form `{"repository": {"owner": {"login": "A"}, "full_name": "B/repo"}, "ref": "refs/heads/master", "after": "<sha>"}`. `verify_signature` picks `Shipit.github(organization: "A")` and accepts the signature; `Handler#stacks` then resolves and enqueues sync work for org `B`'s stack.

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
