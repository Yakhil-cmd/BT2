### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while every event handler acts on `repository.full_name` or bare commit `sha` from the same untrusted body — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/HMAC secret to validate the request against using `repository_owner`, a field read straight out of the attacker-controlled JSON body [1](#0-0) [2](#0-1) . Nothing binds that "authenticating organization" to the repository/commit that the dispatched handler actually mutates in `create`, which re-parses the same raw body and hands it to `Shipit::Webhooks.for_event(event)` handlers [3](#0-2) . `PushHandler` resolves the target `Stack` from `payload.dig('repository', 'full_name')` [4](#0-3) [5](#0-4) , and `StatusHandler` matches commits by bare `sha` with **no repository/organization scoping at all** [6](#0-5) . If any configured GitHub organization has `webhook_secret` unset — explicitly documented as optional (`Webhook secret (optional): Fill it with some randomly generated string...`) [7](#0-6)  — then `verify_webhook_signature` trivially returns `true` for that organization regardless of what signature (or lack thereof) is presented [8](#0-7) .

### Finding Description
The equality that should hold is: **organization that authenticated the request == repository/commit that the request mutates**. Instead:

- Left side (authenticated identity): `repository_owner` (from `params.dig('repository','owner','login')` or `params.dig('organization','login')`), used only to pick the `Shipit.github(organization: ...)` app whose secret verifies the HMAC [1](#0-0) .
- Right side (data acted upon): a completely independent field in the same JSON body — `repository.full_name` for push/pull_request handlers, or nothing at all (just `sha`) for `StatusHandler` [9](#0-8) .

Because both fields live in the same attacker-supplied body and neither is cross-checked against the other, an attacker who can get the signature check to pass for *some* organization (trivially true for any org without a configured `webhook_secret`, which the docs mark optional) can set `repository.owner.login`/`organization.login` to that unsecured org while setting `repository.full_name` (push/pull_request handlers) or `sha` (status handler) to point at a completely unrelated, victim stack/commit elsewhere in the same Shipit installation. `X-Github-Event` is also attacker-controlled via a plain HTTP header, so the attacker chooses which handler runs [10](#0-9) .

The `status` event path is the most severe: `StatusHandler` never calls the `Handler#stacks`/`repository_name` scoping helper that other handlers use — it does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) , so it operates on any commit in the entire database matching that sha, in any stack, regardless of which organization's secret was used to authenticate the request. Commit status directly feeds `Commit#deployable?` (`success? && !blocked?`) and the auto-`ContinuousDeliveryJob` trigger via `schedule_continuous_delivery` [11](#0-10) [12](#0-11) .

### Impact Explanation
By exploiting an organization with no `webhook_secret` configured (a documented, supported configuration for multi-org Shipit deployments), an unauthenticated attacker can inject a forged `state: "success"` commit status for an arbitrary commit sha belonging to a completely different, victim organization's stack. Since `deployable?` and continuous-delivery scheduling key off commit status/check state, this can make an unreviewed/malicious commit appear CI-green and trigger an automatic (continuous) deploy — an unauthorized deploy achieved with zero credentials against the victim repository, only requiring knowledge that some other org in the same Shipit instance has no webhook secret set.

### Likelihood Explanation
Requires: (1) the Shipit instance is configured for multiple GitHub organizations (documented, supported feature in `config/secrets.*.yml`) [13](#0-12) , and (2) at least one of those organizations has an empty `webhook_secret`, which the setup docs explicitly call optional [7](#0-6) . Under that (documented, non-misconfiguration) setup, exploitation is a single unauthenticated POST to `/webhooks` — no session, API token, or GitHub write access required.

### Recommendation
Bind the verified identity to the acted-upon resource: after `verify_signature` succeeds for organization `O`, every handler must confirm that the repository/commit it is about to mutate actually belongs to organization `O` (e.g., compare `repository.full_name`'s owner segment, or the stack's repository owner, against `repository_owner` before dispatch), and `StatusHandler` must scope its `Commit` lookup by the repository derived from the payload the same way other handlers do via `Handler#stacks`/`repository_name`, rather than a bare, unscoped `sha` match.

### Proof of Concept
1. Configure Shipit with two orgs: `victim-org` (has `webhook_secret` set) and `unsecured-org` (no `webhook_secret`, per the documented optional field).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
(no X-Hub-Signature, or any garbage value)

{
  "repository": { "owner": { "login": "unsecured-org" } },
  "organization": { "login": "unsecured-org" },
  "sha": "<victim commit sha, obtainable from public GitHub history>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged"
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/invalid) signature [8](#0-7) .
4. `create` dispatches to `StatusHandler`, which finds `Commit.where(sha: params.sha)` — matching the victim's commit in `victim-org`'s stack — and creates a "success" status on it, with no verification that the request came from `victim-org` [6](#0-5) .
5. If `victim-org`'s stack has continuous delivery enabled, `Commit#schedule_continuous_delivery` fires, potentially triggering an automatic deploy of the (now falsely "passing") commit [12](#0-11) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
