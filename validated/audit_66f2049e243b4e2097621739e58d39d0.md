### Title
Attacker-controlled repository content (unbounded/expensive `.gitmodules` submodule tree) can cause persistent sync denial in `configureWorktree` - (File: main.go)

### Summary
`git-sync`'s per-cycle work budget is a single `--sync-timeout` context that must cover fetch, worktree creation, and — critically — recursive submodule initialization. Because submodule update/init cost is driven entirely by the content of the tracked repository (number of submodules, nesting depth, size of each submodule), a party who can push a commit to the synced repository (or a malicious upstream the operator points `--repo` at) can craft a commit whose `.gitmodules`/submodule tree takes longer than `--sync-timeout` to process on every single attempt. This mirrors the `NodeOperatorManager.initializeOnUpgrade()` griefing pattern (an operation whose cost scales with attacker-influenced input size, executed inside a single unit of work with no per-item bound), but here the "gas" is wall-clock time inside `git-sync`'s sync loop instead of EVM gas.

### Finding Description
Each sync attempt is bounded by a single context: [1](#0-0) 

That same `ctx` is passed all the way into `configureWorktree`, which performs the potentially expensive, content-driven work: [2](#0-1) 

`configureWorktree` is only reached after `createWorktree` has already materialized a new worktree for the remote hash, and the symlink publish (`beforePublish`/`publishSymlink`) happens only **after** `configureWorktree` returns successfully: [3](#0-2) 

If `configureWorktree`'s `git submodule update --init [--recursive] [--depth N]` does not complete before the shared `ctx` (bounded by `--sync-timeout`, default 120s) expires, the whole `SyncRepo` call returns an error. The outer loop increments `failCount`, logs the error, and retries on the next `--period` tick: [4](#0-3) 

Because the remote hash (and therefore the expensive submodule tree) does not change between retries, the same timeout recurs on every attempt. If `--max-sync-failures` is exceeded the process exits(1) (which, under a Kubernetes restart policy, simply crash-loops and repeats the same failure indefinitely); if unset/unlimited, the loop retries forever without ever publishing.

Because submodule work is driven by `.gitmodules` and nested submodule refs — content that is fully controlled by whoever can push to the tracked branch/ref — an attacker with push access to the repository (or a malicious/compromised upstream the operator points at) can construct a commit with a very large number of submodules, deeply nested recursive submodules, or submodules pointing at slow/huge external repositories, so that the recursive `git submodule update --init --recursive` step alone reliably exceeds `--sync-timeout` on every attempt.

### Impact Explanation
This blocks the atomic-symlink contract from ever advancing past the last-good commit: the consumer container keeps serving stale content and never sees the new (good or bad) commits pushed after the poisoned one, for as long as the poisoned commit remains the tip of the tracked ref. If `--one-time` isn't used and `--max-sync-failures` is exceeded, the container repeatedly crashes/restarts, consuming CPU/network on every retry (repeated `git fetch` + `git reset` + worktree creation + submodule clone attempts) — a resource-griefing pattern directly analogous to the "protocol can lose huge gas fees" impact in the source report, translated to "the sidecar can lose CPU/time/network and be perpetually denied publishing." This is a persistent sync denial, matching the accepted-impact class of the assessment ("persistent sync denial").

### Likelihood Explanation
Likelihood depends entirely on the trust model of the tracked repository/ref: any principal capable of pushing a commit that becomes the head of the ref `git-sync` follows (a co-maintainer, a compromised CI bot, or an untrusted upstream when `--repo` points to a third-party project) can trigger this without any special git-sync flags beyond the default submodule handling (`--submodules=recursive` is the documented default). No credential leak or code execution is required — only ordinary push/commit capability to the synced repository, which is one of the explicitly in-scope "untrusted repo content" vectors.

### Recommendation
- Apply a dedicated, independently-configurable timeout/budget for submodule initialization (and ideally a limit on submodule count/recursion depth) separate from the top-level `--sync-timeout`, so a single oversized submodule tree cannot indefinitely block every sync attempt on the same commit.
- Consider allowing forward progress on `--period` even when `configureWorktree` fails, e.g., surfacing a fetch-succeeded/worktree-partial state distinctly from a hard failure, so operators can diagnose the specific ref causing failures without full sync starvation.
- Document that `--submodules=recursive` (the default) combined with `--sync-timeout` creates a content-driven DoS surface for any repo whose submodule graph is not fully trusted, and recommend `--submodules=off`/`shallow` plus explicit depth limits when tracking less-trusted repositories.

### Proof of Concept
1. Start `git-sync` tracking a repository/branch you control (or that an untrusted collaborator can push to), e.g.:
   `git-sync --repo=... --ref=main --root=$ROOT --link=link --period=30s --sync-timeout=30s`
2. Push a commit to `main` that adds many submodules (or one/several submodules with deep recursive submodule chains and/or large history), such that `git submodule update --init --recursive` on that commit alone reliably takes >30s.
3. Observe that every sync attempt logs `error syncing repo, will retry` from the loop at `main.go:1056-1063`, the symlink at `--link` is never advanced to the new commit, and (if `--max-sync-failures` is bounded) the process eventually calls `os.Exit(1)` at `main.go:1061`.
4. Confirm via `--verbose=5`/`6` that the failing step is the `submodule update --init --recursive` invocation issued from `configureWorktree` (`main.go:1733-1747`), not the fetch/reset/worktree-add steps, and that the failure recurs deterministically as long as the poisoned commit remains the tip of the tracked ref.
