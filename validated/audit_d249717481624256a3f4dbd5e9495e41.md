### Title
Block Revenue commission (SIMD-0123/SIMD-0291) can be instantly "rugged" to 100% via `update_commission_bps`, bypassing the anti-rug delay that protects the legacy inflation commission - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
The Wildcat report describes a borrower who reduces the promised APR to zero while lenders are locked into a fixed term and cannot withdraw, silently rugging future interest. The Agave analog is the vote account's block-revenue commission: `update_commission_bps` (SIMD-0291) removes the timing restriction that historically protected commission changes, and — unlike the legacy/inflation-rewards commission — no epoch-delay mechanism was added to protect `BlockRevenue` commission when it feeds `pending_delegator_rewards`. A validator can therefore instantly divert all block revenue away from delegators for every subsequent block, while delegated stakers cannot immediately exit (stake deactivation requires waiting through the cooldown/deactivation process), mirroring the fixed-term lock in the original finding.

### Finding Description
`update_commission_bps` explicitly states there is no update-time restriction for either `InflationRewards` or `BlockRevenue` commission kinds: [1](#0-0) 

By contrast, the legacy `update_commission` path is guarded by an update-time rule (only allowed to increase in the first half of an epoch) and, once the `delay_commission_updates` feature is active, the *effective* commission used for reward calculation is fetched from a full-epoch-old snapshot specifically "to prevent last minute commission rugs": [2](#0-1) 

This snapshot-delay protection is applied to `inflation_rewards_commission_bps` in `redeem_delegation_rewards`: [3](#0-2) 

However, `calculate_block_reward` (which computes each delegator's share of `pending_delegator_rewards`, the SIMD-0123 block-revenue-sharing pool) reads directly from `distribution_epoch_vote_accounts` — the vote account state at the *current* processing point, with no epoch-delay/snapshot indirection: [4](#0-3) 

Since `block_revenue_commission_bps` controls how much of the block revenue accrues to `pending_delegator_rewards` versus the validator/collector, and this commission has "no commission update rule, per SIMD-0249 and SIMD-0291" and is not fed through the `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` delay used for inflation commission, a validator can raise `block_revenue_commission_bps` to 10000 (100%) at any slot and have it apply to `pending_delegator_rewards` immediately for subsequent blocks in the same epoch.

Delegators cannot react in time: unstaking requires deactivation and passes through the stake warmup/cooldown accounting (`delegation_activation_status`, referenced when adjusting delegations for rent) before funds/exposure are fully removed: [5](#0-4) 

so their already-delegated stake keeps generating block-revenue exposure that is diverted to the operator, exactly as fixed-term lenders in the Wildcat report kept accruing interest exposure that could be zeroed by the borrower while they were locked out.

### Impact Explanation
Delegators/stakers lose block-revenue rewards they were entitled to for the current and immediately following blocks, with the change taking effect with no epoch-boundary delay (unlike the equivalent protection Agave explicitly built for the legacy/inflation commission "to prevent last minute commission rugs"). This is a reward-misattribution issue in the reward distribution path (SIMD-0123 block-revenue-sharing), not a validator-operational nuisance: unprivileged delegators bear the loss while the vote-account operator gains it.

### Likelihood Explanation
`update_commission_bps` requires only the vote account's authorized withdrawer signature and, per the code comment, has "no commission update rule" — no epoch-half restriction, no feature-gated delay, unlike `update_commission`. Any vote account with `block_revenue_sharing` enabled can trigger this at will, at any slot, making this trivially and repeatedly reachable.

### Recommendation
Extend the same anti-rug delay mechanism used for `inflation_rewards_commission_bps` (fetching commission from `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts` when `delay_commission_updates`-equivalent protection is active) to `block_revenue_commission_bps` before it is used in `calculate_block_reward`/`deposit_delegator_rewards`, so that changes to the block-revenue commission only take effect after a full epoch, consistent with the protection already documented for inflation commission.

### Proof of Concept
1. Delegator stakes to vote account V, which has `block_revenue_sharing` active and `block_revenue_commission_bps` = 0 (delegator receives 100% of block revenue share accrued in `pending_delegator_rewards`).
2. Vote account authority calls `UpdateCommissionBps(10000, CommissionKind::BlockRevenue)` mid-epoch; `update_commission_bps` applies this instantly with no timing check (`programs/vote/src/vote_state/mod.rs:827-859`).
3. For every subsequent block in the same epoch, `calculate_block_reward` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`) computes the delegator's share of `pending_delegator_rewards` using the vote account's *current* state — now reflecting 100% commission to the operator — with no snapshot delay comparable to the `delay_commission_updates` path used for inflation rewards.
4. The delegator, whose stake is still active (deactivation not yet processed through warmup/cooldown), cannot avoid this loss and receives zero block-revenue share going forward, despite having delegated under a different commission expectation.

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}

        rewarded_epoch: Epoch,

    ) -> CachedVoteAccounts<'a> {

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
