## Finding

### Title
Commit-status webhook writes are not scoped to the authenticating organization's repository, enabling cross-repository CI-status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit verifies inbound GitHub webhooks by looking up the signing secret for the organization named in the payload's `repository.owner.login` field, then checks the HMAC signature against that org's own secret. That only proves "the request was signed by *some* org's webhook secret," not "the state being modified belongs to that org's repositories." The `status` webhook handler ignores this binding entirely and updates commit rows by bare SHA, with no repository/stack scoping at all, unlike the sibling `push` handler.

### Finding Description
Signature verification in `app/controllers/shipit/webhooks_controller.rb` derives the verifying organization purely from attacker-controlled payload content: [1](#0-0) [2](#0-1) 

This only guarantees the message was signed with the webhook secret belonging to *whatever organization the attacker named in the payload*. Since anyone who administers a GitHub organization/repository connected to this Shipit instance legitimately possesses that org's own webhook secret, they can produce a validly-signed `status` event naming their own org while putting an **arbitrary SHA** in the body.

Compare the two event handlers that consume post-verification payloads:

- `PushHandler` correctly scopes writes to the stacks that belong to the repository derived from the verified org/payload, via the `stacks` scope and branch match: [3](#0-2) 

- `StatusHandler`, however, looks up commits **globally by SHA with no repository or stack scoping whatsoever**: [4](#0-3) 

`Commit.create_status_from_github!` then writes a `Status` record used to gate deploys and the merge queue: [5](#0-4) 

The binding that should hold is: *organization that authenticated the webhook == repository/stack whose commit is being written*. `StatusHandler` breaks this equality — the verified identity is "some org," but the write target is "any `Commit` row anywhere in the Shipit database matching an attacker-chosen SHA."

### Impact Explanation
CI/status checks gate two security-relevant flows: `deploy` triggering (`ci.require`/`ci.blocking` in `shipit.yml`, read via `DeploySpec`) and the merge queue's `all_status_checks_passed?`/`any_status_checks_failed?` on `MergeRequest`, which are evaluated straight from `Commit#statuses_and_check_runs` populated by this same webhook path: [6](#0-5) 

An attacker who controls (or can name in a forged-but-validly-signed-for-their-own-org payload) any GitHub organization onboarded to the shared Shipit instance can inject a fabricated `success` status for a commit SHA that happens to exist in a completely unrelated stack/repository they do not control, satisfying required-status checks and enabling an unauthorized deploy or an unauthorized PR merge in that other repository — this matches the "unauthorized deploy, rollback, or merge" Critical-impact category defined in scope.

### Likelihood Explanation
Exploitation requires: (1) administering some GitHub organization/repo that already has a webhook pointed at this Shipit instance (an ordinary, unprivileged action for the owner of their own repository, not requiring any Shipit credential), and (2) knowing or engineering a commit SHA that is also tracked in the target stack (e.g., a shared ancestor commit, a cherry-pick, or a commit crafted with identical tree/parent/committer metadata to collide the SHA in a different repo history). Point (2) is the main constraint on real-world exploitability, but the validation gap itself — a completely unscoped `Commit.where(sha:)` lookup driven by an attacker-controlled event — is a concrete, code-verifiable break of the organization/repository binding, not a theoretical concern.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler` does: restrict the commit lookup to `stacks` derived from the verified `repository`/`organization` in the payload (e.g., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker owns/administers `github.com/attacker-org/some-repo`, which has a webhook configured to POST to the shared Shipit instance's `/github/webhooks` endpoint (this is normal repo-owner configuration, requiring no Shipit account).
2. Attacker computes/obtains the `X-Hub-Signature` using `attacker-org`'s own legitimate webhook secret over a crafted `status` event body:
   ```json
   {
     "sha": "<sha_of_commit_in_victim_stack>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" } }
   }
   ```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and validates the signature successfully because it matches `attacker-org`'s real secret.
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — with no repository/org filter — and finds the commit in the victim's unrelated stack, writing a forged `success` status for it.
5. That status now counts toward `ci.require`/merge-queue checks on the victim stack, potentially allowing an unauthorized deploy or PR merge there. [4](#0-3) [2](#0-1)
