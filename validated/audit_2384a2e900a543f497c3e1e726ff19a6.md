### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App while every event handler acts on `repository.full_name` — cross-organization forged webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to check the `X-Hub-Signature` against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). All webhook handlers, however, resolve the target `Repository`/`Stack` using an entirely different field: `payload.dig('repository', 'full_name')`. Because a JSON payload can freely set these two fields to different values, the signature check binds trust to one identity (`owner.login`) while the mutation binds to a different identity (`full_name`), breaking the equality `organization authenticated == repository written`.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
using `repository_owner`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

This selects the GitHub App configuration (and thus the `webhook_secret` used for HMAC verification) purely from `repository.owner.login`, over `request.raw_post` in its entirety.

Every base `Handler` and event handler, by contrast, resolves the repository/stack to act on from a different field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`Repository.from_github_repo_name` splits `full_name` on `/` and looks up by `owner`/`name` independently of anything checked during signature verification:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [4](#0-3) 

Shipit supports multiple GitHub organizations, each with its own `webhook_secret`, configured independently under `github.<org>.webhook_secret` [5](#0-4) . Any organization onboarded this way is, from Shipit's perspective, an unprivileged tenant relative to any *other* onboarded organization's repositories — it has no legitimate reason to be able to act on another organization's stacks.

Because nothing ties `repository.owner.login` (used to pick the verifying secret) to `repository.full_name` (used to pick the mutated `Stack`), an attacker who legitimately controls organization `attacker-org` (and therefore knows `attacker-org`'s `webhook_secret`, since it is provisioned to them by the GitHub App installation flow) can craft a raw JSON body where:
- `repository.owner.login = "attacker-org"` — makes `verify_signature` pick `attacker-org`'s app/secret, against which the attacker can trivially compute a valid HMAC signature since they know the secret.
- `repository.full_name = "victim-org/victim-repo"` — is what every handler (`PushHandler`, `EditedHandler`, `ClosedHandler`, `LabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`, etc.) uses to look up the `Repository`/`Stack` to mutate.

The signature check passes (it is mathematically valid for the body under `attacker-org`'s key), yet the handler acts on `victim-org/victim-repo`, a stack the attacker's organization was never authorized to touch.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written," satisfying the Critical impact bucket for cross-repository writes. Concretely, once past `verify_signature`, an attacker can:
- Trigger `stack.sync_github(expected_head_sha: ...)` on a victim stack via `PushHandler#process` [6](#0-5) .
- Archive/unarchive a victim review stack via `UnlabeledHandler#handle` / `ReopenedHandler#process` [7](#0-6) [8](#0-7) .
- Overwrite a victim's tracked pull request metadata via `EditedHandler#process` (`pull_request.update(github_pull_request: params.pull_request)`) [9](#0-8) .

These are direct, unauthorized writes into a repository/stack the calling organization does not own, meeting the "cross-repository writes" Critical criterion.

### Likelihood Explanation
Any tenant organization that has legitimately installed the Shipit GitHub App (and thus knows its own `webhook_secret`) can perform this attack against any other organization tracked by the same Shipit instance, with no need for a Shipit session, API token, or GitHub write access to the victim repository — only knowledge of one's own already-provisioned webhook secret and the ability to send an HTTP POST to the public `WebhooksController#create` endpoint. This is a realistic multi-tenant deployment scenario explicitly documented in `docs/setup.md`'s "Using Multiple Github Applications" section.

### Recommendation
Bind signature verification to the same field the handlers actually act on. Either:
- Verify the signature using the GitHub App resolved from `repository.full_name`'s owner segment (not `repository.owner.login`), or
- After verification, assert `repository.owner.login == repository.full_name.split('/').first` (case-insensitively) and reject (422) on mismatch, or
- Have handlers derive the target repository strictly from the same identity used for signature verification instead of an independent `full_name` field.

### Proof of Concept
1. Attacker legitimately operates GitHub organization `attacker-org`, which has a Shipit GitHub App installation with `webhook_secret = S` (per `docs/setup.md` multi-org config) [5](#0-4) .
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, raw_body)>` using their own known secret `S`.
4. POST to `/github/webhooks` with `X-Github-Event: push` and the computed signature.
5. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and validates successfully against `S` [1](#0-0) .
6. `PushHandler#process` resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack [6](#0-5)  — a write the attacker's organization was never authorized to trigger.
