### Title
Webhook signature verified against `repository.owner.login` while the write target is resolved from the independent `repository.full_name` field, enabling cross-organization writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a delivery against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')`. Once verification passes, every event handler (`Handler#stacks`, and PR handlers) resolves the actual `Repository`/`Stack` to mutate using a *different* payload field: `payload.dig('repository', 'full_name')`. These two fields are never checked for consistency, so the binding "organization whose secret authenticated the request" == "repository being written to" is not enforced.

### Finding Description
`verify_signature` computes the HMAC-authenticating organization from one field: [1](#0-0) [2](#0-1) 

The signature check only proves the raw body was signed by *some* organization's configured `webhook_secret` — the org identified by `repository.owner.login` (or `organization.login`) inside that same attacker-suppliable JSON body. In a multi-tenant Shipit deployment (`Shipit.github(organization: ...)`, per-organization `webhook_secret` config), the operator/admin of organization A knows organization A's `webhook_secret` because they configure it themselves when creating their GitHub App (per `docs/setup.md`, "Webhook secret ... Fill it with some randomly generated string"). That means org A's admin can independently craft an arbitrary JSON body, set `repository.owner.login = "org-A"` (so verification resolves and succeeds against A's secret), while setting `repository.full_name = "org-B/victim-repo"` in the very same payload.

Every handler ignores `repository.owner.login` for the write path and instead resolves the target strictly from `repository.full_name`: [3](#0-2) [4](#0-3) 

For example, `PushHandler` will look up stacks under whatever `full_name` says and trigger a GitHub sync against them: [5](#0-4) 

And PR handlers resolve the `Repository` (and thus the review-stack provisioning target) purely from `params.repository.full_name`: [6](#0-5) 

This breaks the trust binding: **organization authenticated (via `repository.owner.login` + its `webhook_secret`) ≠ repository actually written (via `repository.full_name`)**. In genuine GitHub deliveries these two fields are always consistent (GitHub itself sets both from the real repo), so the divergence is only reachable by an attacker who can forge a signed delivery — i.e., an org admin who legitimately possesses their own org's webhook secret, replaying/crafting a request against Shipit's public `/webhooks` endpoint.

### Impact Explanation
An organization that is a legitimate, but only supposed to be scoped to its own repositories, tenant of a shared Shipit instance can use its own known `webhook_secret` to forge webhook deliveries that make Shipit act on a *different* organization's repository/stack: trigger `GithubSyncJob` (`push` event) or create/close review stacks and pull-request state for another org's `Stack` (`pull_request` events), or write commit statuses (`status` handler resolves purely by `sha`, compounding the issue since any org's secret could inject a status onto any commit sha across stacks). This is a cross-repository/cross-tenant write achieved purely by exploiting the mismatched authentication/target binding — matching the required "cross-repository writes" impact class.

### Likelihood Explanation
Requires a multi-organization Shipit deployment where more than one GitHub organization's `webhook_secret` is configured (the documented, supported configuration for `Shipit.github(organization: ...)`), and requires the attacker to be an admin/owner of one such organization who set up the GitHub App and therefore already knows that org's `webhook_secret`. This is a realistic threat model for any Shipit instance serving multiple GitHub orgs/tenants, since the webhook secret is chosen and known by each org's own GitHub App configurer, not the Shipit operator.

### Recommendation
Enforce that `repository.owner.login` (used to select the verifying webhook secret) is identical to the owner portion of `repository.full_name` (used to resolve the target `Repository`/`Stack`) before dispatching to any handler; reject the request (422) on mismatch. Alternatively, derive both the verification organization and the write target from the same single field.

### Proof of Concept
1. Shipit is configured for two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (`secret_a`, `secret_b`), both installed against the same Shipit instance.
2. An admin of `org-a` (who knows `secret_a`) crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Computes `X-Hub-Signature: sha1=<HMAC-SHA1(secret_a, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches `Shipit.github(organization: "org-a")`, verifies the signature successfully against `secret_a`.
5. `PushHandler#process` runs, calling `stacks` → `Repository.from_github_repo_name("org-b/victim-repo")` → the real `org-b/victim-repo` `Stack`s are found and `sync_github(expected_head_sha: "deadbeef")` is enqueued/executed against them, even though the request was never signed by `org-b`'s secret.

**File:** app/controllers/shipit/webhooks_controller.rb (L24-49)
```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
