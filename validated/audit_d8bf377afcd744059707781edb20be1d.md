### Title
Unaccounted / unrefundable deposits silently inflate AA `balance[...]`, corrupting balance-based accounting in oscript AAs - (File: aa_composer.js)

### Summary
GMX's `TransferReceiver` allowance is derived from the contract's raw WETH balance, so an attacker can inflate it by sending WETH directly, poisoning the rewards accounting that assumed all balance changes came from GMX. Ocore has a structurally analogous footgun for Autonomous Agents (AAs): a trigger's payment is unconditionally credited to the AA's balance the instant it arrives, before any `if`/`case` logic runs, and if the AA subsequently cannot compose a bounce (e.g. because the trigger did not carry enough base bytes to pay the bounce fee), the deposit is never refunded and never explicitly accounted for by the AA's own state variables. Any subsequent oscript code that queries `balance[asset]` (a documented, commonly-used accounting primitive, e.g. in the bundled `uniswap_like_market_maker.oscript` and `fundraising_proxy.oscript` templates) will treat this "donated" value as legitimate reserve, exactly like the WETH-donation issue in the report.

### Finding Description
When a unit triggers an AA, `getTrigger()` sums all payment outputs addressed to the AA into `trigger.outputs` [1](#0-0) , and `updateInitialAABalances()` immediately adds those amounts into `aa_balances` / `objValidationState.assocBalances` for the AA address, before any `if` condition of any `case`/message is evaluated [2](#0-1) .

If no message matches (or the trigger fails formula evaluation), `bounce()` is invoked to try to refund the sender. Critically, if the trigger did not include enough base-asset bytes to pay the configured `bounce_fees.base`, the function gives up silently and produces **no response unit at all**:

```
if ((trigger.outputs.base || 0) < bounce_fees.base)
    return finish(null);
``` [3](#0-2) 

Because no response unit is created, the funds that were already credited into the AA's balance in `updateInitialAABalances()` are never sent back and never subtracted. They remain permanently part of the AA's on-chain spendable balance, yet the AA's own oscript state (its `var[...]` bookkeeping) has no record of having received or accepted them — the deposit bypassed every `if`/`case` that the author wrote to track deposits.

This is architecturally the same root cause as the GMX bug: an accounting mechanism (`balance[asset]` in oscript, exposed via `formula/evaluation.js`'s `readBalance()` [4](#0-3) ) is fed from the AA's raw balance rather than from an amount explicitly accounted for by the contract's own logic. Any oscript AA that uses `balance[...]` for pricing/ratio math — a pattern explicitly demonstrated and shipped by ocore itself in `test/samples/uniswap_like_market_maker.oscript` — inherits the same "outside/unaccounted value enters the accounting system" flaw:

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
...
$current_ratio = $asset_balance / $bytes_balance;
``` [5](#0-4) 

Any bytes/asset silently absorbed by a prior unaccountable trigger (as described above) permanently shifts `$asset_balance`/`$bytes_balance`, and thus every future `$current_ratio`, `$expected_asset_amount`, and share-issuance calculation, without ever being reflected in `var['mm_asset_outstanding']`.

### Impact Explanation
An attacker who can post an ordinary unit (unprivileged, single-poster reachable) can:
1. Send a custom asset to a `balance[]`-based AMM/rewards AA together with insufficient base bytes to trigger a bounce refund, permanently donating value into the AA's reserve without it being reflected in the AA's state (`AA fund loss/freezing` for the depositor, and unaccounted-for value for the AA).
2. Repeat this (or perform a single well-timed donation) immediately before interacting with the AA's `balance[...]`-driven pricing formula (as in the shipped Uniswap-like market maker template) to skew `$current_ratio` / `$p` and extract more shares/assets than a fair contribution would allow, at the expense of other investors — a concrete case of AA fund loss for legitimate users.

### Likelihood Explanation
Reaching this requires only posting a normal payment unit with a small/insufficient base output to an AA address — no special privileges, no hub/network cooperation, and no reliance on a malicious peer. The vulnerable pattern (`balance[...]` used for ratio-based accounting) is not merely hypothetical; it is the exact pattern shipped as an official sample/template (`uniswap_like_market_maker.oscript`) in this very repository, meaning any AA author following ocore's own examples inherits the exposure.

### Recommendation
- In `aa_composer.js`, when a trigger cannot be bounced because it lacks enough base bytes (`bounce()`'s `finish(null)` path at aa_composer.js:928-929), the AA's balance should not silently retain the deposit as unaccounted value; at minimum, this edge case should be clearly documented as an intentional trust boundary, and templates/guides should warn AA authors never to base financial/pricing formulas on raw `balance[asset]` without subtracting a state-tracked "accounted" quantity.
- For AAs computing invariants (AMM reserves, staking pools, reward pools), recommend/standardize a pattern of tracking deposits exclusively via `var[...]` state updated inside matching cases (i.e., the before/after style check recommended in the original report), rather than trusting `balance[asset]` directly, and update the bundled `uniswap_like_market_maker.oscript` sample to demonstrate this safer pattern since it is used as a reference by third-party developers.

### Proof of Concept
1. Deploy an AA modeled on `test/samples/uniswap_like_market_maker.oscript`.
2. Attacker posts a unit sending only the pool's non-base asset (`$asset`) to the AA address with `base` output value below `bounce_fees.base` (e.g. a few hundred bytes) and no data matching any `if` condition.
3. `updateInitialAABalances()` credits the asset into `aa_balances` for the AA [6](#0-5) ; no case matches, `bounce()` is invoked, and because `trigger.outputs.base < bounce_fees.base`, it returns `finish(null)` with no refund unit [3](#0-2) .
4. The donated asset amount is now permanently part of `balance[$asset]` but was never added to `var['mm_asset_outstanding']`.
5. Attacker (or an accomplice) immediately calls the "invest in MM" case; `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` now includes the donation, skewing `$current_ratio` and the resulting `$issue_amount` of MM shares relative to genuine prior investors' shares.
