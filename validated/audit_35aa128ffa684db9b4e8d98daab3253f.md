### Title
Legacy `pattern:` rule frontmatter silently fails to block `Write` tool file content, unlike equivalent explicit `conditions:` rule - (File: `plugins/hookify/core/config_loader.py` / `Rule.from_dict`)

### Summary
`Rule.from_dict` converts a legacy `pattern:` frontmatter field for `event: file` rules into a single `Condition` with `field='new_text'`, but `RuleEngine._extract_field` in `plugins/hookify/core/rule_engine.py` only maps `new_text`/`new_string` to the `Edit` tool's `new_string` key, never to the `Write` tool's `content` key. An explicitly authored rule using `conditions: [{field: content, ...}]` matches both `Write` and `Edit`, while the semantically-equivalent legacy `pattern:` rule silently never matches `Write` operations. This breaks the invariant that legacy and explicit rule forms produce equivalent security semantics.

### Finding Description
In `Rule.from_dict`, the legacy conversion path infers the condition field purely from `event`: [1](#0-0) 
For `event == 'file'` this always sets `field = 'new_text'`, regardless of whether the target tool is `Write` or `Edit`.

In `RuleEngine._extract_field`, the field-resolution logic first checks whether the field name is a literal key present in `tool_input`: [2](#0-1) 
`Write` tool inputs use the key `content`; `Edit` tool inputs use `new_string`. `new_text` is not a literal key in either, so this direct check fails and execution falls through to the tool-specific branch: [3](#0-2) 
For `Write`, the `new_text`/`new_string` branch resolves to `tool_input.get('new_string', '')`, which is always `''` for `Write` (it has no `new_string` key) — it returns an empty string, not `None`, so `_check_condition` proceeds to run the regex against `''`, which will not match any non-empty pattern. A rule expressed with the same intent via explicit `conditions: [{field: content, operator: regex_match, pattern: ...}]` instead hits the literal-key check (`content` is present in `Write`'s `tool_input`) and correctly evaluates the actual written content.

Consequently, a block rule authored with the simple/legacy `pattern:` field for `event: file` (e.g., generated by `/hookify` rule generation, or shipped in a repo's `.claude/hookify.*.local.md` file) will never actually block dangerous content delivered via the `Write` tool, even though the identical policy expressed with explicit `conditions` and `field: content` would correctly block it. Any content that would trigger the block rule when arriving via `Edit` silently bypasses the same rule when the agent instead uses `Write` (e.g., writing a whole new file instead of patching an existing one), letting disallowed content reach disk unblocked.

### Impact Explanation
This allows an unauthorized file write to bypass a security control the user believed was blocking dangerous file content (e.g., secret exfiltration snippets, malicious scripts, writes outside an approved scope) whenever the write happens through the `Write` tool rather than `Edit`. Because rule authoring guidance / generation naturally produces the simpler legacy `pattern:` form, this is a realistic, silent policy bypass, directly matching "Unauthorized file read or write outside the user-approved workspace or target scope."

### Likelihood Explanation
No special privileges are required beyond normal use of hookify: any repo-shipped `.claude/hookify.*.local.md` rule file or any rule produced by `/hookify` generation that uses the legacy `pattern:` field with `event: file` is affected. The bug is deterministic and always reproducible for `Write`-tool operations — it requires no race condition or timing, only that the victim's write path uses `Write` instead of `Edit`, which is a very common code path.

### Recommendation
Make legacy pattern conversion tool-aware or field-agnostic: either (a) generate two conditions (or a field alias set) covering `content`/`new_text`/`new_string` so both `Write` and `Edit` are covered, or (b) fix `_extract_field` so `new_text`/`content` resolve consistently across `Write` and `Edit` regardless of the exact key name, and add a regression test asserting that a legacy `pattern:` block rule and its equivalent explicit `conditions` block rule produce identical `_rule_matches` results for both `Write` and `Edit` tool inputs.

### Proof of Concept
Unit test to add to `plugins/hookify/tests` (or equivalent):
```python
from hookify.core.config_loader import Rule
from hookify.core.rule_engine import RuleEngine

legacy_frontmatter = {
    "name": "block-secret",
    "enabled": True,
    "event": "file",
    "pattern": "SECRET_TOKEN",
    "action": "block",
}
explicit_frontmatter = {
    "name": "block-secret-explicit",
    "enabled": True,
    "event": "file",
    "action": "block",
    "conditions": [{"field": "content", "operator": "regex_match", "pattern": "SECRET_TOKEN"}],
}

legacy_rule = Rule.from_dict(legacy_frontmatter, "blocked")
explicit_rule = Rule.from_dict(explicit_frontmatter, "blocked")

engine = RuleEngine()
write_input = {
    "tool_name": "Write",
    "tool_input": {"file_path": "/tmp/x", "content": "leak SECRET_TOKEN here"},
}

# Explicit form correctly blocks:
assert engine._rule_matches(explicit_rule, write_input) is True
# Legacy form silently fails to block the same content via Write:
assert engine._rule_matches(legacy_rule, write_input) is False  # demonstrates the differential/bypass
```
Expected result confirms the differential: the explicit-conditions rule blocks the `Write` call while the semantically identical legacy `pattern:` rule does not, demonstrating the security-semantics divergence and bypass path.
