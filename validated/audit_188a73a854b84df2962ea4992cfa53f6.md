### Title
Cross-organization webhook secret confusion allows spoofed events to act on repositories outside the authenticated organization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a request against using an organization name pulled straight out of the *unverified* JSON body, while the downstream event handlers resolve which `Repository`/`Stack` to act on using a *different* field of that same unverified body. In a multi-organization Shipit deployment, this lets a party who only controls a webhook secret for one configured organization forge a signed request whose "authenticating" org differs from the repository actually targeted by the handler logic.

### Finding Description
`verify_signature` computes the trust anchor for the whole request from the payload itself, before the signature has been checked: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up the app config (and thus `webhook_secret`) for that specific organization key in `config/secrets.yml`, as supported by the "Using Multiple Github Applications" configuration documented for this engine [3](#0-2)  and implemented in [4](#0-3) .

The HMAC signature itself is computed over the *entire raw request body* with that organization's secret [5](#0-4) . Because the signing/verification step never binds the "organization whose secret authenticated the request" to the "repository the payload actually references," an attacker who knows (or controls) the `webhook_secret` for **any one** configured organization (call it `OrgA`) can craft an arbitrary JSON body where:
- `repository.owner.login` = `OrgA` (so `verify_signature` picks OrgA's secret and the HMAC computed with OrgA's known secret passes), but
- `repository.full_name` = `OrgB/some-repo` (a different, unrelated organization/repository also configured on the same Shipit instance).

The event handlers never re-check the authenticating organization; they resolve the actual target purely from `repository.full_name`: [6](#0-5) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

and similarly in the pull-request handlers, e.g. `PullRequest::OpenedHandler#repository` resolves via `params.repository.full_name` alone [7](#0-6) , then acts on it (`ReviewStackAdapter#find_or_create!`) [8](#0-7) .

The binding that should hold is: **organization whose secret authenticated the request == organization owning the repository the handlers write to**. This engine breaks that equality because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon `Repository`/`Stack`) are two independent, unauthenticated fields of the same attacker-controlled JSON body, and only one of them is ever cross-checked against the signature's originating org.

Before the attacker's crafted request: OrgA's secret only authenticates events for OrgA's own repositories; OrgB's stacks are only ever mutated by OrgB's own signed webhooks.
After the crafted request: a party holding only OrgA's `webhook_secret` produces a request that passes signature verification "as OrgA" but whose handler-visible repository is `OrgB/some-repo`, so Shipit performs webhook-driven actions (e.g., `GithubSyncJob` push processing, PR-review-stack provisioning/closing, label handling) against OrgB's stack.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" binding explicitly called out as in-scope. Depending on which event type is forged, an attacker can drive `GithubSyncJob` (push events) or PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) against a stack belonging to an organization the attacker has no legitimate relationship to, resulting in unauthorized cross-organization/cross-repository writes to Shipit's state for stacks it doesn't own (e.g. forcing sync of a bogus head SHA, opening/closing review-stack provisioning, manipulating merge-queue-adjacent PR label state). This matches the "cross-repository writes" / "unauthorized deploy" class of Critical impact for this analysis.

### Likelihood Explanation
This requires: (1) a Shipit deployment configured with the multi-organization `github:` schema (explicitly documented and supported), and (2) the attacker possessing the `webhook_secret` of at least one of the configured organizations (e.g., because they are a legitimate admin/integrator for that one org, or that secret leaks) — this is exactly the "unprivileged relative to the *other* organization" attacker envisioned by the rules, since owning a webhook secret for OrgA confers no privilege over OrgB's repository/stack under a correctly-scoped design. Given multi-org support is a first-class, documented configuration, likelihood is Medium.

### Recommendation
Bind the two identity checks together: after selecting the GitHub App/secret via `repository_owner`, `verify_signature` (or the handler dispatch) should additionally assert that `repository.full_name`'s owner matches `repository_owner`/the resolved `github_app`'s organization before invoking handlers, rejecting (422) any payload where the two disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. As an attacker who only knows `OrgA`'s `webhook_secret` (e.g., a legitimate GitHub App admin for OrgA), craft a `push` (or `pull_request`) JSON body where:
   - `repository.owner.login` = `"OrgA"`
   - `repository.full_name` = `"OrgB/target-repo"`
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_webhook_secret, raw_body)>` and POST it to `/github/webhooks` (or the engine's mounted webhook path) with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies successfully against `OrgA`'s secret, and passes.
5. `Shipit::Webhooks.for_event('push')` handler resolves the target via `payload.dig('repository', 'full_name')` = `"OrgB/target-repo"`, and processes the push against OrgB's stack — despite the request only ever having been authenticated by OrgA's secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
