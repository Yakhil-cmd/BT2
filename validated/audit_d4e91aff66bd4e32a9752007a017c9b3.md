### Title
Stack-scoped ApiClient tokens can read the CCMenu status of any stack, bypassing per-token stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to look up the requested stack directly via `Stack.from_param!(params[:stack_id])`, instead of using the base controller's stack-scoped lookup. This means an `ApiClient` token that is bound to a single stack (`stack_id`) can be used to read the deploy/build status of *any* stack in the system, not just the one it is authorized for.

### Finding Description
`Shipit::Api::BaseController#stack` correctly scopes stack lookups to the token's authorized stack: [1](#0-0) 

`current_api_client.stack_id?` limits the `stacks` relation to the single stack the `ApiClient` was created with, so `stacks.from_param!` will raise/404 if a caller supplies a `stack_id` outside that scope. This is the intended binding: *the stack a token authorizes == the stack a controller action touches*.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely and resolves any stack from the raw params: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only checks that the token has the `read:stack` permission string — it does not check *which* stack the token is scoped to: [3](#0-2) 

As a result, any token with `read:stack` permission (even one created with a `stack_id` restricting it to a single, non-sensitive stack) can pass an arbitrary `stack_id` param to `CCMenuController#show` and read the deploy status of a stack it was never authorized to see.

### Impact Explanation
This breaks the binding "a stack a token authorizes vs. a stack it touches" and results in unauthenticated-scope read of stack state / deploy output for stacks the token holder is not permitted to see — matching the High-severity class explicitly listed in the rules ("escalation into ... unauthenticated read of stack state, task streams or deploy output"). A token intentionally minted for one stack (e.g., handed out via `CCMenuUrlController#fetch`, which mints tokens scoped with `permissions: %w[read:stack]` bound to a specific stack) can be reused to enumerate/observe the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of every other stack in the installation.

### Likelihood Explanation
Any holder of a legitimately-issued, stack-scoped API token (for example a CI status widget URL created by `CCMenuUrlController`, which is routinely embedded in dashboards/CCTray clients and is not treated as a highly sensitive secret) can trivially exploit this by changing the `stack_id` query parameter. No additional privileges, session, or GitHub credentials are required beyond the token itself, and the token was designed to be narrowly scoped — this bug defeats that scoping outright.

### Recommendation
Remove the `CCMenuController#stack` override, or reimplement it using the scoped lookup (`stacks.from_param!(params[:stack_id])`) so that stack-restricted tokens cannot access stacks outside their authorized scope:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. As an authorized Shipit user, request a CCMenu URL for `stack_a` via `CCMenuUrlController#fetch`; this mints an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to `stack_a`'s id.
2. Take the resulting token (`?token=...`) and call `GET /api/stacks/:owner/:repo_of_stack_b/ccmenu.xml?token=<token>` (i.e., substitute `stack_id`/params to point at `stack_b`, a different, non-authorized stack).
3. Because `CCMenuController#stack` calls `Stack.from_param!` on the unscoped `Stack` relation rather than `stacks.from_param!`, the request succeeds with `200 OK` and returns `stack_b`'s deploy status/lock state, even though the token was only ever authorized for `stack_a`. [4](#0-3)
