### Title
Cross-repository CI status forgery via SHA-only lookup breaks the webhook-org / repository-written binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `send`/`call` finding in the report maps to a real class of "trust-binding" bug in this engine: the field the webhook signature is checked against is not the field that is actually acted upon. `WebhooksController#verify_signature` selects the GitHub App/secret using `repository.owner.login` (or `organization.login`) from the payload [1](#0-0) , while `Shipit::Webhooks::Handlers::StatusHandler#process` writes GitHub status data to **every** `Commit` row across **every** stack/repository whose `sha` matches the payload, without ever checking `repository.full_name` [2](#0-1) .

### Finding Description
`Handler` (the base class most handlers use) computes the acted-upon repository/stack from `payload.dig('repository', 'full_name')` [3](#0-2) , and `PushHandler` correctly scopes to `stacks` derived from that repository name [4](#0-3) . `StatusHandler`, however, does **not** inherit this repository scoping at all — it queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on every match [2](#0-1) , which persists a new `Status` row via `Commit#create_status_from_github!` → `statuses.replicate_from_github!` [5](#0-4) .

The binding that should hold is: **organization/repository that authenticated the webhook == repository whose commit state is written**. Instead:
- Signature verification is keyed off `repository.owner.login` from the (still-unverified-until-HMAC-check) payload [6](#0-5) .
- The actual write target (`Commit.where(sha: ...)`) is keyed off nothing but the commit SHA, a value that is **not scoped to any repository** in the database query.

Git SHA1 identifiers are content hashes, not secrets: two different repositories/stacks tracked by the same Shipit instance can legitimately contain a commit with an identical SHA (shared history, forks, vendored/cherry-picked commits, or an attacker deliberately reproducing a target commit's exact tree/parents/author/committer/timestamps in a repo they control). Because the Shipit GitHub App's webhook secret is fixed per organization (or globally, in the common single-org configuration shown in the docs and `test/dummy/config/secrets.yml` where `Shipit.github(organization: ...)` ignores the passed organization entirely and always uses the one configured secret) [7](#0-6) , any legitimate `status` webhook that arrives with a valid signature — including one legitimately triggered by an attacker's own repository/CI within an org that has the app installed — is processed against the global `Commit` table.

### Impact Explanation
An attacker who has push/CI access to any single repository monitored by the Shipit installation (or who controls a service that posts commit statuses to GitHub for a repo in the trusted org) can craft a commit whose SHA collides with a target commit belonging to a *different, unrelated stack*, then have a `status` event fire (a normal, validly-signed webhook for their own repo). `StatusHandler` will write that forged status (e.g. `state: success`, arbitrary `context`/`description`/`target_url`) onto the victim stack's commit. Combined with `Commit#deployable?` (`success? && !blocked?`) and `Commit#schedule_continuous_delivery` (`stack.continuous_deployment?`) [8](#0-7) , this can cause an **unauthorized deploy** to be enqueued for a stack the attacker never had write access to. This matches the "High/Critical - unauthorized deploy" impact bucket in scope.

### Likelihood Explanation
This requires only ordinary GitHub push/CI access to one repository already onboarded to the Shipit instance (not a Shipit session, API token, or knowledge of `webhook_secret`), since the webhook signature is legitimately produced by GitHub for the attacker's own repo/commit. The main precondition — a SHA collision with a target commit — is straightforward for an attacker to engineer against a known target commit (attacker can reproduce identical tree, parent, author, committer, and timestamp metadata locally to reproduce the exact SHA1 in their own repository) or opportunistic (shared/forked base commits, vendored libraries, empty/initial commits reused across many repos).

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up `Commit`/`Stack` state independent of `Handler#stacks`) to the repository named in the payload, e.g. restrict the `Commit` lookup to commits belonging to stacks resolved via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, mirroring what `PushHandler` already does through `Handler#stacks`. Additionally, tie the app/secret selected in `WebhooksController#verify_signature` to the same repository field used by the handlers, so a webhook is only ever attributed to (and permitted to mutate) the repository it was actually signed for.

### Proof of Concept
1. Configure Shipit for two independent stacks/repositories, `victim-org/victim-repo` (tracked stack, `continuous_deployment: true`, CI required) and `attacker-org/attacker-repo` (an org where the attacker has ordinary push/CI access, using the same or any configured GitHub App webhook secret).
2. Attacker observes/knows the target commit `C` in `victim-org/victim-repo` (tree, parents, author/committer identity and timestamps are all public via the GitHub API/UI).
3. Attacker reproduces an identical commit object (same tree hash, parent SHA, author/committer name+email+date) inside `attacker-repo`, yielding the identical SHA1 as `C`.
4. Attacker's CI (or attacker directly, if they run their own CI reporting) posts a `status` webhook for `attacker-repo` with `sha = C`, `state = success`. GitHub signs this payload with the legitimate webhook secret for `attacker-org`.
5. `WebhooksController#create` dispatches to `StatusHandler`, which executes `Commit.where(sha: C).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) , writing a `success` status onto the victim stack's commit `C` even though the webhook was never sent by/for `victim-org`.
6. If `victim-org`'s stack has continuous deployment enabled, `Commit#schedule_continuous_delivery` now sees `deployable?` true and enqueues a deploy for `victim-repo` [9](#0-8) , resulting in an unauthorized deploy triggered entirely from the attacker's own, unrelated repository.
