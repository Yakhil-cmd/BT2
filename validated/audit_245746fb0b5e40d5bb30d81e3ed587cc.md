### Title
Webhook signature verified against attacker-chosen organization while handlers act on an unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured for multiple GitHub organizations, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a request against using a field taken directly from the untrusted JSON body, while the event handlers that actually mutate state use a *different* field from that same untrusted body to decide which repository/stack to act on. Nothing ties these two fields together, so a signature that is valid for org A can be replayed with a payload whose `repository.full_name` points at org B.

### Finding Description
`verify_signature` computes the org used to pick the HMAC secret purely from the request body: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up a distinct `webhook_secret`/app per organization key, as shown by the multi-org config support: [3](#0-2) 

Once the signature is validated for whatever organization `repository_owner` names, `create` dispatches the **entire raw JSON body** to all registered handlers: [4](#0-3) 

The handlers, however, resolve the repository to act on from `params.repository.full_name` — a separate, independently-controlled JSON field that is never cross-checked against `repository.owner.login`: [5](#0-4) [6](#0-5) 

The binding that is broken is:
```
organization whose secret authenticated the request  ==  organization implied by repository.full_name that handlers act on
```
Both `repository.owner.login` (used for signature-org selection) and `repository.full_name` (used for the actual DB lookup/write) are attacker-supplied strings inside the same unauthenticated-until-verified JSON blob. The HMAC only proves "this byte stream was signed with organization X's secret" — it says nothing about which values are self-consistent inside that byte stream, and the code never checks that `repository.full_name` starts with `repository.owner.login`.

### Impact Explanation
An operator who legitimately controls a GitHub App installation for one configured organization (org A) — and therefore possesses/observes org A's `webhook_secret` from GitHub's app settings, which they are entitled to configure — can craft an arbitrary payload, sign it with org A's secret, but set `repository.full_name` to `orgB/some-repo`, `orgB/some-repo` being any other organization's stack managed by the same Shipit install. Because Shipit's per-organization webhook secrets exist precisely to segregate orgs (`docs/setup.md`'s "Using Multiple Github Applications" section), this breaks that isolation:
- `PushHandler`-driven `GithubSyncJob` can be triggered against org B's stack, refreshing/potentially advancing its deploy spec caches and CI status.
- Pull-request handlers (`OpenedHandler`, `ClosedHandler`, `Labeled/UnlabeledHandler`) can create, archive, or unarchive `ReviewStack`s for org B repositories, and `ReviewStackAdapter#user` mints/looks up `Shipit::User` records based on attacker-supplied `sender.login`.
- `membership` events (seen in `webhooks_controller_test.rb`) create/delete `Team`/`Membership` records, which feed directly into `Shipit.github_teams` authorization checks (`User#authorized?`), i.e. an attacker signing with org A's secret but injecting org B (or a spoofed team) membership data could manipulate authorization state used across the whole deployment.

This lands squarely in the "High" bucket described by the scope rules: escalation into `Shipit.github_teams` authorization / unauthenticated write of stack state across an organization boundary the attacker does not control.

### Likelihood Explanation
Requires an attacker who is a legitimate admin of at least one GitHub App installation configured in the same Shipit deployment (a realistic scenario for any Shipit instance shared across many teams/orgs, which is the exact use case `docs/setup.md`'s multi-org section documents). No repository write access, no `ApiClient` token, and no privileged Shipit account is needed — only the ability to send an HTTP POST to `/webhooks` with a body signed with a secret the attacker legitimately possesses for their own org. This matches the required "unprivileged-attacker" analog: the attacker is unprivileged with respect to org B, yet influences org B state.

### Recommendation
After signature verification, re-derive the organization from the same field(s) used for authentication and enforce that the repository/stack referenced by handlers belongs to that verified organization. Concretely:
- Extract `repository.full_name` inside `verify_signature` (not just `repository.owner.login`) and confirm they refer to the same owner before accepting the webhook.
- Alternatively, pass the verified `repository_owner` into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization: repository_owner) }` and have each handler assert `params.repository.full_name.split('/').first.casecmp?(verified_organization)` before performing any lookup/mutation, rejecting mismatches with a `422`.

### Proof of Concept
Conceptual (cannot be executed without a running multi-org deployment and access to org A's configured `webhook_secret`):
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers the GitHub App installed for `OrgA` and therefore has `OrgA`'s `webhook_secret`.
3. Attacker builds a `pull_request` (or `push`) JSON payload where:
   - `repository.owner.login = "OrgA"`
   - `repository.full_name = "OrgB/victim-repo"`
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the HMAC (it was signed with `OrgA`'s real secret).
6. `WebhooksController#create` dispatches the full payload to `Shipit::Webhooks.for_event('pull_request')`; `OpenedHandler` resolves `Shipit::Repository.from_github_repo_name("OrgB/victim-repo")` and creates/mutates a `ReviewStack` under `OrgB`, despite the request never being authenticated by `OrgB`'s GitHub App/secret.
