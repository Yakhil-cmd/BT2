### Title
Self-labeling on PR creation bypasses `allow_with_label` provisioning gate, causing unauthorized ReviewStack provisioning of attacker-controlled fork ref - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` treats the mere presence of the configured provisioning label in the `pull_request.labels` array of a genuine, correctly-signed GitHub `opened` webhook as sufficient authorization to provision a `ReviewStack` for that PR's head ref, without checking who applied the label or whether that actor is distinct from/more privileged than the PR author. Since the label check (`pull_request_has_provisioning_label?` at line 72-74) only reads `pull_request['labels']`, it cannot distinguish "a maintainer vetted this PR" from "the PR author labeled their own PR."

### Finding Description
The broken binding: the code implicitly assumes `label_added_by == authorized_maintainer`, but the code never reads or checks that binding — it only checks `label ∈ pull_request.labels`, which is silent on the identity of who added the label. Concretely:

- `provision?` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70`) OR's together `provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?`.
- `pull_request_has_provisioning_label?` (lines 72-74) and `pull_request_label_names` (lines 76-78) read `pull_request["labels"]` straight from the webhook payload, with no reference to `params.sender` at all.
- `ReviewStackAdapter#find_or_create!` → `create!` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:72-94`) then creates the `ReviewStack` with `branch: params.pull_request.head.ref` — i.e., the attacker's own fork branch — and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`, which is later provisioned by the cron worker (`lib/tasks/cron.rake:11`, `app/models/shipit/review_stack_provisioning_queue.rb:29-31`), ultimately running deploy steps (`lib/shipit/deploy_commands.rb`) against that ref.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only authenticates that the payload came from GitHub (via `X-Hub-Signature` and `Shipit.github(...).verify_webhook_signature`) — it says nothing about whether the *content* of the payload (i.e., who applied the label before the PR was opened) reflects maintainer intent. Per the audit's attacker model, the attacker is explicitly granted the ability to "label their own PR" and "emit webhooks from a repository they own," so a real, validly-signed GitHub webhook is produced. No other guard in this file, `Repository`, or `ReviewStackAdapter` checks `sender.login != pull_request.user.login`, checks repository collaborator/team status of whoever applied the label, or otherwise verifies EXECUTION_TRUST (label authorized by someone other than the ref owner). `LabeledHandler` has the identical `pull_request_has_provisioning_label?` pattern (`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:95-101`), showing this is a design pattern shared across all provisioning-label handlers, not a one-off typo.

### Impact Explanation
An attacker who opens a PR with the provisioning label already attached (or whose PR-creation request bundles the label) causes Shipit to auto-create and enqueue a `ReviewStack` bound to `branch: <attacker's fork ref>` (`review_stack_adapter.rb:89`). Once provisioned by the queue worker, deploy steps from `lib/shipit/deploy_commands.rb` execute against attacker-supplied code/commands defined in that ref's deploy spec, on the deploy host, with the repository's real GitHub/deploy credentials — an unauthorized deploy of attacker code, matching the "Critical: unauthorized deploy" category. This is repeatable per-PR against any repository configured with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: true`, i.e., any tenant repo using this common review-stack labeling convention, not limited to one victim.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled = true` and `provisioning_behavior = allow_with_label` with a known `provisioning_label_name` (label names are typically visible/discoverable, e.g. via the repo's label list or Shipit settings UI at `app/views/shipit/repositories/settings.html.erb`). The attacker cost is one PR-open action; per the audit's defined attacker capabilities they are explicitly permitted to label their own PR and to open pull requests from a fork — no Shipit secrets, sessions, or GitHub org membership are required. Whether real-world GitHub actually permits an external, non-collaborator contributor to attach an existing label to their own newly opened PR (this normally requires `triage`/`write` permission on the base repo) is a GitHub-platform permission question outside this engine's code; the audit's threat model stipulates this capability is available to the attacker, so within the given rules the precondition is satisfied.

### Recommendation
Do not derive provisioning authorization solely from the static label list in the `opened`/`pull_request` sub-object. Require that the authorizing label be attributed to an actor other than `pull_request.user.login` and that this actor have write/triage privileges on the repository (e.g., only honor provisioning-label authorization sourced from a `labeled` event whose `sender.login` differs from the PR author and is verified as a collaborator via the GitHub API, rather than trusting the `labels` array embedded at PR-open time). At minimum, `OpenedHandler#provision?`'s `allow_with_label` branch should reject labels present at PR creation time when `params.sender.login == pull_request.user.login`.

### Proof of Concept
Minitest plan (extending `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` patterns):
1. Configure repository: `repository.review_stacks_enabled = true; repository.provisioning_behavior = :allow_with_label; repository.provisioning_label_name = "pull-requests-label"`.
2. Build `payload_parsed(:pull_request_opened)` and set `payload["sender"]["login"] = payload["pull_request"]["user"]["login"]` (attacker is both PR author and label-adder) and `payload["pull_request"]["labels"] = [{ "name" => "pull-requests-label" }]`.
3. Assert the binding before: `assert_equal payload["sender"]["login"], payload["pull_request"]["user"]["login"]` (same unprivileged actor).
4. Call `OpenedHandler.new(payload).process`.
5. Assert `assert_difference -> { Shipit::ReviewStack.count }, 1` and that the created stack's `branch == payload["pull_request"]["head"]["ref"]` and `awaiting_provision? == true`, demonstrating provisioning was triggered purely by the self-applied label with no distinct authorizing sender.
