### Title
Cross-repository status webhook injection via unscoped `Commit.where(sha:)` lookup lets an attacker-controlled repo trigger `stack.schedule_merges`/`Hook.emit(:deployable_status, ...)` on an unrelated victim stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, without ever checking that the SHA belongs to the repository named in the verified webhook payload. Since git commit SHAs are content-addressed and identical across any repository that shares that commit (forks/clones), an attacker who owns a Shipit-configured repository can replay a victim commit's SHA in a validly-signed status webhook from their own repo and cause `Commit#add_status` to fire `Hook.emit(:deployable_status, stack, ...)` and `stack.schedule_merges` (enqueuing `ProcessMergeRequestsJob`) for the victim's stack, which their payload never named.

### Finding Description
The claimed binding is: `stack == repository_named_in(verified_webhook_payload)`, i.e., the `Stack`/`Commit` that gets mutated by a status webhook should be scoped to the repository that GitHub's signature actually vouches for.

Tracing the path:
- `WebhooksController#verify_signature` selects the GitHub App config via `Shipit.github(organization: repository_owner)` where `repository_owner = params.dig('repository','owner','login')`, and verifies HMAC signature against that organization's `webhook_secret`. [1](#0-0)  This only proves the request came from *some* organization/repo the attacker legitimately controls — it does not bind the payload's repository to the commits touched downstream.
- `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`. [2](#0-1) 
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no filter on `repository`, `stack_id`, or `full_name` at all; the `params` schema doesn't even require a `repository` field. [3](#0-2) 
- `Commit#stack` is a `belongs_to :stack` set at commit-import time (by `GithubSyncJob`), i.e. it reflects whichever repository originally imported that commit — not the repository named in the current webhook. [4](#0-3) 
- `Commit#create_status_from_github!` → `#add_status` then unconditionally acts on `stack` (the commit's own stack), calling `Hook.emit(:deployable_status, stack, ...)` and `stack.schedule_merges`, which enqueues `ProcessMergeRequestsJob.perform_later(self)` for that stack. [5](#0-4) [6](#0-5) 
- `ProcessMergeRequestsJob#perform` then refreshes/merges pending merge requests on that stack if `stack.allows_merges?`. [7](#0-6) 

Attacker's exact steps: the attacker owns/administers a repository under an organization that is already configured in this Shipit instance's secrets (i.e. one of the tenant orgs, which is a normal multi-tenant Shipit deployment scenario — multiple orgs each with their own `webhook_secret`/GitHub App config, per `lib/shipit/github_app.rb`). [8](#0-7)  They clone or fork the victim's public repository (or otherwise obtain a commit object identical to one already imported into a victim stack elsewhere on the same Shipit instance) and push it into their own repository. GitHub then sends (and correctly HMAC-signs, using the attacker's own legitimate org secret) a `status` event for that SHA, naming the attacker's own `repository.full_name`. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler` then matches `Commit.where(sha: same_sha)` across the whole database, hitting the victim's `Commit` row (belonging to an entirely different `Stack`/`Repository`), and drives `add_status` → `Hook.emit(:deployable_status, victim_stack, ...)` and `victim_stack.schedule_merges` → `ProcessMergeRequestsJob.perform_later(victim_stack)`.

Existing guards do not stop this: `verify_signature` authenticates the sender's organization, not the target record; `drop_unhandled_event` only checks the event type exists a handler; the `ExplicitParameters` schema for `StatusHandler` never requires/validates a `repository` field to cross-check against the resolved `Commit#stack.repository`; there is no `Repository`/`Stack` scoping in the `Commit.where(sha:)` query.

### Impact Explanation
A payload verified only for repository/organization B mutates state (commit statuses, hook emissions, and merge-queue processing) belonging to stack/repository A, matching "a payload for one repository mutating another's stack, commit, task or team." Concretely: an attacker-controlled, unrelated repository's status webhook can force `ProcessMergeRequestsJob` to run against a victim stack, potentially causing that stack's queued merge requests to be evaluated/merged earlier than intended, and firing `deployable_status`/`commit_status` hooks (which may drive external automation/notifications) for a stack the attacker never controls. This is repeatable against any commit SHA the attacker can reproduce in their own repository (any public commit, or any commit they can otherwise learn the SHA of), across every stack/tenant hosted on the same Shipit instance, since `Commit.where(sha:)` is global and unscoped.

### Likelihood Explanation
Preconditions: (1) the Shipit instance hosts multiple organizations/repositories (multi-tenant), each with its own configured GitHub App/`webhook_secret`; (2) the attacker administers at least one such organization/repository (a normal, low-privilege tenant, not a Shipit operator); (3) the victim commit's SHA is discoverable/reproducible by the attacker (trivial for public repos, or repos the attacker can fork/clone). No Shipit secrets, sessions, or API tokens are required — only a legitimately signed webhook from the attacker's own, already-onboarded repository. This is realistically feasible in any Shipit deployment shared across multiple teams/orgs.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and any other webhook handler using `Commit.where(sha:)`) to the repository named in the verified payload, e.g. join through `stack.repository` and compare `full_name`/`owner`+`name` from `params.dig('repository', ...)` before calling `create_status_from_github!`. Reject or ignore matches where the resolved commit's stack repository does not match the payload's repository.

### Proof of Concept
Minitest plan (e.g. in `test/controllers/webhooks_controller_test.rb` or a new `status_handler_test.rb`):
1. Create two `Repository`/`Stack` pairs: `victim_stack` (repo `victim-org/repo`) and `attacker_stack`/no stack at all for `attacker-org/repo`.
2. Create a `Commit` with `sha: "deadbeef..."` belonging to `victim_stack`, and set up its `merge_requests` such that `victim_stack.allows_merges?` would become true after a passing status.
3. Stub `Shipit.github(organization: 'attacker-org')` to return a `GitHubApp` whose `verify_webhook_signature` returns `true` (simulating a correctly-signed webhook from the attacker's own org).
4. POST to `/webhooks` with `X-Github-Event: status`, body `{ "sha" => "deadbeef...", "state" => "success", "repository" => { "owner" => { "login" => "attacker-org" }, "full_name" => "attacker-org/repo" }, "branches" => [...] }`.
5. Assert: `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_stack])` — proving the victim stack (named nowhere in the attacker's payload) receives `schedule_merges` purely because of the shared SHA.
6. Before/after equality check: assert `victim_stack.repository.full_name != 'attacker-org/repo'` (the two sides of the claimed binding), yet `ProcessMergeRequestsJob` is enqueued for `victim_stack`, demonstrating the binding is broken.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
