### Title
Cross-tenant PullRequest write: webhook signature verified against `repository.owner.login`, but data written using unrelated `repository.full_name` - ([File: app/models/shipit/webhooks/handlers/pull_request/edited_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository.owner.login` extracted from the raw JSON body, while `EditedHandler#repository` (and every other `PullRequest` handler) resolves the target `Repository` using the independent `repository.full_name` field from the same body. Nothing enforces that these two fields are consistent, so an org that legitimately owns a webhook secret for its own tenant can forge a payload naming a different tenant's repository and have Shipit persist attacker-controlled PR title/body onto that victim's `PullRequest` record.

### Finding Description
The broken binding: `repository_owner (verified) == full_name.split('/').first (repository whose row is mutated)` is assumed but never checked.

- `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it to pick the GitHub App config/secret via `Shipit.github(organization: repository_owner)`: [1](#0-0) 
- `Shipit.github(organization:)` only succeeds for organizations explicitly configured in `secrets.github`, each with its own independent `webhook_secret`, confirming this is a multi-tenant design where each onboarded org has its own credential: [2](#0-1) 
- Once the signature is accepted, `EditedHandler#process` calls `pull_request.update(github_pull_request: params.pull_request)`, where `pull_request` is looked up via `Repository.from_github_repo_name(params.repository.full_name)` — a field entirely independent of `repository.owner.login` used above: [3](#0-2) 
- `Repository.from_github_repo_name` simply splits `owner/name` and does a DB lookup, with no cross-check against the authenticated organization: [4](#0-3) 
- `PullRequest#github_pull_request=` copies `title`, `state`, `additions`, `deletions`, `user`, `assignees`, `labels`, and `head` verbatim from the attacker-supplied payload onto the resolved record: [5](#0-4) 

Exploit flow: attacker controls a legitimately onboarded tenant org ("attacker-org") in this Shipit instance and knows its `webhook_secret` (each org's secret is independently configured, per `github_app_config`). They POST to `/webhooks` with `X-Github-Event: pull_request`, HMAC signed with attacker-org's secret over a body where `repository.owner.login = "attacker-org"` (so `verify_signature` picks attacker-org's secret and passes) but `repository.full_name = "victim-org/repo"` and `action = "edited"` with a real PR number belonging to victim-org's stack. `EditedHandler` resolves `repository` via `full_name`, finds victim-org's `Repository`, finds the matching `PullRequest` by `number` + `repository.id`, and overwrites its `title`/etc. with attacker content.

This is not blocked by any existing guard: `drop_unhandled_event` only checks the event name is handled; the `ExplicitParameters` schema only validates types/presence, not cross-field consistency between `owner.login` and `full_name`; `Repository` validations only check character-set format of `owner`/`name`, not membership consistency; there is no `force_github_authentication`, session, or API-client check in this webhook path at all — the entire trust boundary rests on the (broken) implicit assumption that `owner.login` and `full_name` in one payload always refer to the same repository, which is true for genuine GitHub-relayed webhooks but not enforced for directly-POSTed forged requests.

### Impact Explanation
A payload from one tenant's verified webhook secret can overwrite another tenant's `PullRequest.title` (and `state`, `additions`, `deletions`, `assignees`, `labels`, `head` commit linkage) with fully attacker-chosen content. This is a cross-repository/cross-tenant write ("a payload for one repository mutating another's ... commit, task or team" per the Critical category) and is repeatable against any repository/PR number the attacker can guess or enumerate, across every tenant configured on the instance. Stored title/body content is later surfaced to victim-org operators (e.g., in the UI or deploy notes), giving a secondary stored-content risk to a party with elevated operational trust.

### Likelihood Explanation
Requires the Shipit instance to be multi-tenant (multiple orgs configured in `secrets.github`, each with distinct `webhook_secret`) and the attacker to be a legitimate holder of one tenant's own webhook secret — plausible in any self-service/multi-org Shipit deployment, since that's precisely what the per-org secret design (`github_app_config`) supports. No Shipit session, API token, or GitHub-team membership is needed; only knowledge of a PR number in the victim repo (often small integers, easily brute-forced) and the target `full_name`. The attack is a single crafted HTTP POST, fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), assert that `repository.full_name`'s owner segment matches the `repository_owner`/organization whose secret validated the signature, and reject (422) on mismatch before dispatching to any handler. Alternatively, resolve the target `Repository` strictly by the same trusted `repository_owner` value used for signature verification rather than an independently attacker-controlled `full_name` field.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "cross-tenant pull_request 'edited' webhook cannot mutate another org's PullRequest" do
  # victim repo/stack/pull_request fixtures belong to owner "victim-org"
  victim_pr = shipit_pull_requests(:review_stack_review) # belongs to victim-org repo
  attacker_secret = "attacker-secret"
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    action: "edited",
    number: victim_pr.number,
    pull_request: { id: 1, number: victim_pr.number, url: "x", title: "PWNED", state: "open",
                     additions: 0, deletions: 0,
                     head: { sha: victim_pr.head.sha, ref: "x" },
                     user: { login: "attacker" }, assignees: [], labels: [] },
    repository: { owner: { login: "attacker-org" }, full_name: victim_pr.stack.repository.full_name },
    sender: { login: "attacker" }
  }.to_json

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, payload)}"

  assert_no_changes -> { victim_pr.reload.title } do
    post :create, body: payload, as: :json
  end
end
```
Assertion: with only `attacker-org`'s secret validated, `victim_pr.title` must remain unchanged; if it changes to `"PWNED"`, the vulnerability is confirmed.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
