In `validateDefinition`'s handling of `definition template` this is properly wrapped in try/catch and the `NoVarException` is caught explicitly [1](#0-0) . However, the second occurrence of `definition template` evaluation — inside `validateAuthentifiers`'s `evaluate` function, which is executed after `validateDefinition` has passed and is used to actually check which signature paths are satisfied — calls `replaceInTemplate(arrTemplate, params)` **without any try/catch** [2](#0-1) .

## Finding: unhandled `NoVarException` thrown from `replaceInTemplate` during authentifier evaluation crashes the node process

`replaceInTemplate` throws a `NoVarException` whenever a template placeholder (`"$name"`) is not present in the supplied `params` object [3](#0-2) . The `params` come directly from the address definition (`['definition template', [unit, params]]`), which is validated only for type shape (each param must be a string or number, must be non-empty) but not for whether it actually satisfies every placeholder used by the referenced template [4](#0-3) .

Because `validateDefinition` is required to pass before `validateAuthentifiers.evaluate` ever runs the `definition template` branch again [5](#0-4) , an attacker's crafted definition would normally be rejected at the `validateDefinition` stage if `replaceInTemplate` throws there — but the two evaluations use **independently-selected `params` values** only in the sense that they read the *same* stored `arrDefinition` and the *same* stored `template` row; the important discrepancy is that `validateDefinition`'s copy is wrapped in try/catch (`definition.js:330-339`) while `validateAuthentifiers`'s copy at `definition.js:814-816` is not. If any code path reaches the unguarded `evaluate` in `validateAuthentifiers` with a template/params combination that differs from what `validateDefinition` saw (e.g., because the referenced "definition_template" unit's payload can change interpretation depending on `last_ball_mci` used in the SQL query, or because the object is mutated in-place by `replaceInTemplate`/`assignField`, or because a re-validation happens against a different current chain-tip state), the thrown `NoVarException` propagates uncaught out of an asynchronous `conn.query` callback, crashing the Node.js process — a full node-availability DoS reachable simply by posting a unit that authenticates against such an address, i.e., by an unprivileged unit poster.

This is the same underlying bug class as CVE-2017-12966: a lookup/substitution routine (`asn1f_lookup_symbol_impl` in asn1c, analogous to `replaceInVar`'s `params[name]` lookup in `replaceInTemplate`) that can fail on crafted attacker-controlled input, and the failure (there, a segfault; here, an uncaught JS exception) is not defensively handled at every call site, only at one of the two call sites.

### Impact
An uncaught exception thrown inside a database-query callback in Node.js is not caught by any surrounding `try/catch` (Node's event loop unwinds without a synchronous call stack to catch it), so it becomes an unhandled exception at the process level, crashing the ocore node performing validation. Because unit validation (including authentifier/signature evaluation for definitions referencing `definition template`) is triggered by any newly received/posted unit, this is remotely triggerable by any unit poster whose unit is validated by an honest node.

### Uncertainty
I could not fully verify from the indexed code that the two `definition template` evaluation paths (`validateDefinition` vs. `validateAuthentifiers`) can actually observe different `params`/`template` content for the same unit during a single validation pass — this would need runtime tracing to confirm the exception is reachable despite the earlier `validateDefinition` guard. The general asymmetry (one guarded, one unguarded call to `replaceInTemplate`) is confirmed directly in the code, but whether it is exploitable end-to-end (i.e., whether `validateAuthentifiers`'s `evaluate` can hit this branch with a `NoVarException`-throwing template that `validateDefinition` did not already reject) is not fully established from static reading alone. I recommend a Devin session with the ability to run the ocore test suite / trace the validation flow to confirm reachability of the unguarded `throw` in `definition.js:814-818`.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
