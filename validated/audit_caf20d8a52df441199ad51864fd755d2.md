### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, so a `status` webhook signed and verified for Repo A can create a `Status` record on a `Commit` belonging to Repo B whenever the two repositories contain a commit object with the identical SHA. Because git commit hashes are content-addressed (not namespaced per repository), an attacker who can read the target commit's tree/parents/metadata (trivial for any public PR) can reproduce an identical commit object in a repository they control and push a `state: success` status for it, flipping `MergeRequest#all_status_checks_passed?` for Repo B's queued merge request and triggering `stack.schedule_merges`.

### Finding Description
The broken binding: the question implies `repository(webhook_payload) == repository(commit.stack)`. In the code this equality is never enforced.

- `WebhooksController#verify_signature` only checks that the webhook signature is valid for `repository_owner` derived from the payload [1](#0-0) . It verifies the request truly came from GitHub for that owner/org — it does **not** bind the payload's `sha` to that repository anywhere downstream.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query is global across all stacks/repositories tracked by the Shipit instance — it is keyed only by `sha`, with no `stack_id`/`repository_id` filter. Other handlers (e.g. `pull_request` handlers) resolve to `stacks` via `Repository.from_github_repo_name(repository_name)` as defined in the base `Handler` class [3](#0-2) , but `StatusHandler` never calls this `repository_name`/`stacks` scoping helper at all.
- `Commit#create_status_from_github!` → `add_status` creates the `Status` row and, on a `pending`/`success` transition, calls `stack.schedule_merges` [4](#0-3) , which enqueues `ProcessMergeRequestsJob` and re-evaluates merge eligibility for the owning stack (Repo B's stack in the attack scenario), even though the webhook was authenticated only for Repo A.
- Git commit SHAs are content hashes of `(tree_sha, parent_sha(s), author, committer, message, timestamps)`. They are not scoped or salted per-repository. Any repository, including one the attacker fully owns, can contain a commit object whose SHA is bit-identical to a commit in a completely unrelated repository, provided the attacker reproduces the same tree/parents/metadata (all of which are visible via GitHub's API/UI for any public commit or PR).

Attacker's exact request: attacker pushes/creates in Repo A (which they own and on which the Shipit GitHub App/webhook is installed) a commit object identical to Repo B's pending `head` commit, then causes a `status` event with `state: success` for that SHA to be delivered to `POST /webhooks` (e.g., via their own CI reporting a commit status, or by using the GitHub Status API directly against their own repo). GitHub signs this webhook correctly for Repo A's org, so `verify_signature` passes. `StatusHandler#process` then matches Repo B's `Commit` row by `sha` and writes a `success` `Status` against it, and `stack.schedule_merges` on Repo B's stack sees `all_status_checks_passed?` return true.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) all check only that the webhook is validly signed for *some* repository and that it minimally matches the expected params shape (`sha`, `state`, etc.) — none of them check that the `sha` belongs to the repository that emitted the webhook, because `StatusHandler` never consults `payload.dig('repository', 'full_name')`/`stacks` at all.

### Impact Explanation
A `Status` row (and consequent `stack.schedule_merges` re-evaluation) is written against Repo B's commit/stack based solely on a webhook that Repo B's tenant never authorized — this is a payload for one repository mutating another's commit/stack state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized...merge"). If Repo B's queued `MergeRequest` was only waiting on this CI status, the forged `success` status can make `all_status_checks_passed?` true and let the queued PR proceed to merge without real CI having run in Repo B. This is repeatable against any repository tracked by the same Shipit instance, as long as the attacker can reconstruct an identical commit object (feasible for public commits/PRs), and requires no elevated Shipit role, session, or secret — only the ability to control a GitHub repo with the Shipit app/webhook installed and to author a status webhook for it.

### Likelihood Explanation
Preconditions: (1) both Repo A (attacker-controlled) and Repo B (victim) are onboarded to the same Shipit instance and Repo B has a `MergeRequest` in `pending`/`revalidating` waiting on CI for its `head` commit; (2) the attacker can reproduce Repo B's target commit's exact tree/parent chain/metadata in Repo A — feasible for any public commit/PR since git objects are fully inspectable via GitHub's API, and git hashing has no repo-bound salt; (3) Repo A must have GitHub's webhook delivering `status` events to the Shipit host (true for any repo Shipit tracks, which the attacker can arrange by using/registering their own repo under the same GitHub org/installation if the deployment allows self-service onboarding, or simply already-onboarded low-trust repos). Cost to the attacker is moderate (constructing an identical git commit object is mechanical but requires precise reproduction of tree/parents/timestamps) but is a one-time, repeatable technique against any repo pair sharing a Shipit instance.

### Recommendation
Scope the commit lookup in `StatusHandler#process` by the reporting repository, not just `sha`. Use the base `Handler#stacks` (which resolves `Repository.from_github_repo_name(repository_name)`) to restrict the query, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or join `Commit` to `Stack`/`Repository` via the webhook's `repository.full_name`, so a status can only be attached to commits belonging to the stack(s) of the repository that actually emitted the webhook.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from Repo A cannot flip merge eligibility for Repo B's commit with colliding sha" do
  repo_a_stack = shipit_stacks(:repo_a)         # attacker-controlled tenant
  repo_b_stack = shipit_stacks(:repo_b)         # victim tenant
  colliding_sha = "deadbeef" * 5

  repo_a_commit = repo_a_stack.commits.create!(sha: colliding_sha, ...)
  repo_b_commit = repo_b_stack.commits.create!(sha: colliding_sha, ...)
  merge_request = repo_b_stack.merge_requests.create!(head: repo_b_commit, merge_status: :pending)

  refute merge_request.all_status_checks_passed?

  payload = {
    'sha' => colliding_sha,
    'state' => 'success',
    'repository' => { 'full_name' => repo_a_stack.repository.full_name, 'owner' => { 'login' => repo_a_stack.repository.owner } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # EQUALITY CHECK: repository(payload) == repository(commit.stack) ?
  refute_equal repo_a_stack.repository.full_name, repo_b_stack.repository.full_name

  # yet Repo B's commit/merge request was mutated by Repo A's webhook:
  assert repo_b_commit.reload.statuses.exists?(state: 'success')
  assert merge_request.reload.all_status_checks_passed?, "Repo A's status flipped Repo B's merge request"
end
```
This demonstrates the write occurring against Repo B's `Commit`/`MergeRequest` from a webhook authenticated only for Repo A, with no live GitHub network calls (using `StatusHandler.call` directly with an in-process payload, as the existing `webhooks_controller_test.rb` does with `payload(:status_master)` fixtures).
