### Title
Webhook signature verification binds the wrong organization to the repository/stack that is actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate an inbound webhook against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), while the event handlers that perform the actual writes (`PushHandler`, `MembershipHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers) key off a *different* field of the very same attacker-supplied JSON body — `repository.full_name` (via `Handler#repository_name`) or `organization.login` independently. Nothing cross-checks that the organization whose secret validated the signature is the same organization/repository that ends up being mutated. This mirrors the PoolKeeper report's root cause: a value used at one point (verification) diverges from the value relied on for subsequent effects (state mutation), because the two paths pull from different representations of what should be the same fact.

After this "verification" step, the controller re-parses the *same* raw JSON and dispatches it to handlers unmodified: [5](#0-4) 

The handlers, however, do not use `repository_owner` at all — they resolve the repository/stack to mutate from `repository.full_name`: [6](#0-5)

`PushHandler` uses `stacks` (built from `repository.full_name`) to invoke `stack.sync_github`: [8](#0-7) 

and the `PullRequest::*` handlers use `params.repository.full_name` to archive/unarchive review stacks (which deprovisions/reprovisions live infrastructure): [9](#0-8) [10](#0-9) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` / `organization.login` (used to pick the mutated target) are separate JSON fields inside the same unauthenticated request body, an attacker who controls the raw POST can set them independently. If **any** configured organization in a multi-org Shipit deployment has no `webhook_secret` set (an explicitly documented, supported configuration — see `docs/setup.md` "Webhook secret (optional)"), an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to that secret-less organization, so `verify_webhook_signature` short-circuits to `true` regardless of the (even absent/garbage) `X-Hub-Signature` header.
2. Set `repository.full_name` to a **different** organization's repository (one that does have deploy-managed stacks/review stacks), and set `team`/`member`/`action` etc. as needed.
3. The handler layer, which never re-validates that the authenticated org matches the repository being acted upon, performs writes against the victim organization's stacks/teams.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope. Concretely reachable, unprivileged (no Shipit session, no ApiClient token, no GitHub write access) impacts:
- Forced `stack.sync_github` calls and check-run refresh scheduling for arbitrary victim stacks (`PushHandler`, `CheckSuiteHandler`), letting an attacker desynchronize a stack's known commit state.
- Forced archive/unarchive of review stacks belonging to a victim repository via `PullRequest::LabeledHandler`/`ReopenedHandler`/`ClosedHandler`, which calls `stack.deprovision` / re-provisions infrastructure (`ReviewStackAdapter#archive!` / `#unarchive!`) — an unauthorized deploy/rollback-equivalent action on infrastructure that is not the attacker's.
- Creation/deletion of `Team`/`Membership` records scoped to an arbitrary `organization.login`, independent of which org's secret authenticated the request, effectively forging organization membership/authorization data that other authorization checks (`Shipit.github_teams`) rely on.

This lands in the "High" bucket defined by the rules: escalation into `Shipit.github_teams` authorization data, plus cross-organization/cross-repository writes bordering on the "Critical: cross-repository writes / unauthorized deploy or rollback" bucket, since review-stack archive/unarchive directly triggers deprovisioning/provisioning of deployed infrastructure for a repository the attacker doesn't control.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint — no session, no API token, no GitHub credentials. The precondition (one organization among several configured without a `webhook_secret`) is explicitly documented as an optional, supported configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`), so it is a realistic and even encouraged setup for multi-org Shipit deployments (e.g., internal/low-risk orgs skipping secret setup while higher-value orgs configure one). No changes to how the host mounts the engine are required.

### Recommendation
After parsing the JSON payload, re-derive `repository_owner` (or `organization.login`) from the same payload used by the handlers, and require it to exactly match the organization whose secret was used to verify the signature. Equivalently, verify the signature using the organization/app resolved from `repository.full_name`'s owner (the same field the handlers use), not a separately-read field, so there is a single source of truth for "which org authenticated this request" that is enforced consistently through to the write path. Additionally, consider rejecting webhook processing entirely when `webhook_secret` is unset for an organization involved in multi-tenant configurations, rather than silently treating it as "always verified."

### Proof of Concept
Preconditions: Shipit configured with two GitHub orgs, e.g. `orgA` (no `webhook_secret`) and `orgB` (has stacks/review stacks and a webhook secret), as in `config/secrets.development.shopify.yml`.

```
POST /webhooks HTTP/1.1
X-Github-Event: pull_request
X-Hub-Signature: sha1=anything-or-empty

{
  "action": "labeled",
  "number": 42,
  "pull_request": { ... "state": "open", "labels": [{"name": "shipit:deprovision-review-stack"}] ... },
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" },
  "sender": { "login": "attacker" }
}
```

- `verify_signature` computes `repository_owner == "orgA"`, calls `Shipit.github(organization: "orgA")`, whose `verify_webhook_signature` returns `true` unconditionally because `orgA` has no `webhook_secret`.
- `LabeledHandler#repository` resolves `Shipit::Repository.from_github_repo_name("orgB/victim-repo")`, and `handle` archives `orgB`'s review stack, deprovisioning it — despite the request never being signed by `orgB`'s secret. [11](#0-10)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
