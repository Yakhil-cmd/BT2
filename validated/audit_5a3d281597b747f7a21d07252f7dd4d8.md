### Title
Per-recipient rounding in headers-commission split allows byte supply inflation - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a parent unit's fixed `headers_commission` pot among the recipients listed in the winning child unit's `earned_headers_commission_recipients` array. Each recipient's share of the pot is rounded independently with `Math.round()` (JS path) / SQL `ROUND()` (MySQL path), instead of computing the last recipient's amount as a remainder. This is the same class of bug as the Napier `Tranche::withdraw()` finding: rounding is applied per-unit-of-work instead of tracking the total remaining, so the sum of the rounded parts can exceed the amount actually available, silently minting extra bytes.

### Finding Description

and, on the SQLite path, per external recipient: [2](#0-1) 

Each `amount = Math.round(full_amount * share / 100.0)` (equivalently `ROUND(punits.headers_commission*earned_headers_commission_share/100.0)` on MySQL, see [3](#0-2) ) is computed independently for every recipient address, and all these independently-rounded amounts are inserted as separate rows into `headers_commission_contributions`, which are later spendable as MC (`headers_commission`) inputs. There is no cross-check that `sum(amount) == full_amount`; only the *percentage shares* are validated to sum to exactly 100 at unit-validation time: [4](#0-3) 

Critically, `validateHeadersCommissionRecipients()` does not require the recipient addresses to be authors of the unit, does not cap the number of recipients, and does not require more than one author for the recipient list to be present — it only enforces the presence of the field when `authors.length > 1`, but nothing prevents a single-author unit from also declaring an arbitrary multi-recipient `earned_headers_commission_recipients` list, as long as the shares sum to 100: [5](#0-4) 

Because each recipient's `Math.round()` is independent, an attacker who fully controls the recipient list (which is trivial for a single author) can choose share percentages that each individually round *up* from the true fractional value, so the sum of rounded amounts exceeds `full_amount`. For example, with `full_amount = 3` and 5 recipients each with `share = 20`: `3*20/100 = 0.6` rounds to `1` for every recipient, giving a total distribution of `5` instead of `3` — a 67% inflation of that unit's headers commission. The more recipients an attacker adds (bounded only by unit-size limits, not by any explicit recipient-count cap), the larger the absolute inflation per parent unit processed.

An attacker does not need to win a competitive "best child" race against other users: if their own unit is the *only* child referencing a given parent (e.g., in a private, self-authored chain of units), `getWinnerInfo()` trivially selects it as the winner, so the attacker fully controls both `full_amount` (indirectly, via the parent unit's header size, which they also author) and the skewed `earned_headers_commission_recipients` split that maximizes rounding-up gains.

### Impact Explanation
This allows any unpriviledged unit poster to mint bytes out of thin air by repeatedly authoring parent→child unit chains with crafted `earned_headers_commission_recipients` splits, each cycle extracting more `headers_commission` than the parent unit ever actually paid. The excess amounts are inserted into `headers_commission_contributions` and become genuinely spendable MC inputs (validated later against this same table via `mc_outputs.calcEarnings`), i.e. real, usable byte balance. This is a supply-inflation bug reachable purely by posting ordinary units — no privileged role, no network/consensus attack, and no reliance on peer or node misbehavior.

### Likelihood Explanation
High. The attack requires only standard unit composition capability (setting `earned_headers_commission_recipients` with a hand-picked list of addresses/shares) available to any wallet/user, and can be repeated indefinitely with self-authored parent/child chains where the attacker's own unit is the sole (hence winning) child, removing any dependency on external tie-breaking or timing.

### Recommendation
Compute the amount for all recipients but the last by rounding down (or `Math.floor`), and assign the last recipient the *remainder* (`full_amount - sum_of_previous_amounts`), guaranteeing `sum(amount) === full_amount` for every payer unit, mirroring the standard "round all but the last, give remainder to the last" pattern. Apply the same remainder-based approach to both the MySQL `ROUND()` SQL path and the JS in-memory computation path in `headers_commission.js` and `paid_witnessing.js` (which has an analogous `Math.round`/`ROUND` split for `payload_commission` divided among witnesses).

### Proof of Concept
1. Attacker author creates unit `A` (self-authored) that will serve as a parent; note its `headers_commission` = H (determined by A's own header size).
2. Attacker creates a single child unit `B` of `A` (the only child referencing `A`, so it trivially wins the headers-commission race via `getWinnerInfo`).
3. In `B`, set `earned_headers_commission_recipients` to `N` distinct attacker-controlled addresses, with integer percentage shares summing to exactly 100, each chosen so that `H * share / 100` has a fractional part ≥ 0.5 (e.g., `H=3`, 5 recipients at `share=20` each).
4. When `calcHeadersCommissions()` runs (triggered on MC stabilization), each recipient receives `Math.round(3*20/100) = 1`, for a total of `5` inserted into `headers_commission_contributions` for payer unit `A`, versus the true `headers_commission` of `3` — a net inflation of `2` bytes.
5. Attacker later spends these `headers_commission` MC inputs normally (validated against the same `headers_commission_contributions`/`calcEarnings` data, see [6](#0-5) ), realizing the inflated bytes as real spendable balance. Repeating this with self-authored parent/child chains scales the inflation arbitrarily.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
