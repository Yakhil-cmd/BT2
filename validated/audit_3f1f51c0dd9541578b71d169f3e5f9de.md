### Title
Cross-repository status forgery via bare-SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes GitHub `status` events to every `Commit` row matching the raw `sha`, without scoping the lookup to the repository that authenticated the webhook. Unlike other handlers (`PullRequest::*Handler`, `PushHandler`, `CheckSuiteHandler`) which use the base `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) to constrain effects to the repository named in the payload, `StatusHandler` queries `Commit.where(sha: params.sha)` globally, so any stack sharing that commit SHA (e.g. via a fork with an identical, content-addressed commit) is affected.

### Finding Description
The intended invariant is: `commit.stack.repository.full_name == payload['repository']['full_name']` for every commit mutated by a webhook, i.e. a status should only ever affect the repository that sent it. This is what `Handler#stacks` enforces: [1](#0-0) 

But `StatusHandler#process` never calls `stacks`; it resolves target commits purely from the attacker-supplied `sha`: [2](#0-1) 

`Commit.create_status_from_github!` then writes the status and re-evaluates deployability/blocking through `add_status`, which can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`: [3](#0-2) [4](#0-3) 

`WebhooksController#verify_signature` only checks that the payload is signed by the GitHub App/webhook secret associated with `repository_owner` (the org in the payload's own `repository`/`organization` object) — it never cross-checks that the `sha` in the `status` payload actually belongs to that same repository: [5](#0-4) 

**Exploit flow:** An attacker who owns/administers any GitHub repository (e.g., a fork of the victim's repository) that is also configured as a Shipit stack can send a correctly-signed `status` webhook for their own org/repo with `context: ci/kubernetes`, `state: failure`, and a `sha` that is shared with the victim's stack. Git commit SHAs are content-addressed, so a base commit that exists identically in both the upstream (victim) repo and the attacker's fork carries the same SHA in both. Because `Commit.where(sha: params.sha)` is unscoped, the same SHA can match a `Commit` row belonging to the victim's stack. The status is written there, flipping `deployable?`/`blocked?` for the victim's stack. If that stack is `continuous_deployment?` and has `bot_login` configured (`Shipit.user`), deploy/merge actions run automatically as the bot identity via `schedule_continuous_delivery`/`stack.schedule_merges`, turning the forged `failure` status into an unauthorized block, or a correspondingly forged `success` into an unauthorized ship/merge.

None of the existing guards prevent this: `verify_signature` authenticates only the sender's own org, `drop_unhandled_event` does not filter by repository, `ExplicitParameters` only validates payload shape (not repo ownership), and `StatusHandler` performs no `Repository`/`Stack` scoping at all — a clear behavioral asymmetry from the other handlers in the same directory that do call `Repository.from_github_repo_name(repository_name)`/`stacks`.

### Impact Explanation
A payload authenticated for repository A can mutate `Commit`/`Status` state — and downstream deployability/merge/block decisions — for a completely unrelated stack B, as long as a SHA collision (shared commit, typical for forks/PRs) exists. Combined with `bot_login` (auto-triggered deploy/merge running as `Shipit.user`), this becomes an unauthorized deploy, rollback, or block of arbitrary victim stacks, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). This is repeatable against any stack that shares a commit SHA with an attacker-controlled repository (trivial via forking).

### Likelihood Explanation
Preconditions: attacker needs (1) a GitHub repository they control added as a Shipit stack (or any repo whose webhook they can trigger with a valid signature for that org), and (2) a commit SHA shared with the victim stack (naturally achieved by forking the victim repo, since the shared history's commits keep identical SHAs). The victim stack must require/watch a `ci/kubernetes` status and have `bot_login` configured for auto-triggered deploy/merge to matter. Attacker cost is low — sending one webhook — and the action is fully repeatable and scriptable against any repository sharing commit history with the attacker's own repo.

### Recommendation
In `StatusHandler#process`, scope the query to the repository that authenticated the webhook, mirroring the other handlers' use of `stacks`, e.g. restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` (or add a `stack_id: stacks.pluck(:id)` condition) derived from `Repository.from_github_repo_name(repository_name)`, so a status can only ever be recorded for commits belonging to stacks of the repository that sent the webhook.

### Proof of Concept
Minitest plan (illustrative, to be adapted to existing fixtures/helpers in `test/models/commits_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create two `Stack`s, `victim_stack` (repository `acme/victim`, `bot_login` configured, `required_statuses` including `ci/kubernetes`) and `attacker_stack` (repository `evil/fork`).
2. Create a `Commit` with `sha: "deadbeef..."` under `victim_stack`, and a separate `Commit` with the same `sha` under `attacker_stack` (simulating a shared/forked commit).
3. Before assertion: `assert victim_commit.deployable?` (or record baseline `state`/`blocked?`).
4. Build a `status` webhook payload with `repository.full_name = "evil/fork"`, `sha: "deadbeef..."`, `context: "ci/kubernetes"`, `state: "failure"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, as permitted for unit testing the handler logic).
6. Assert: `victim_commit.reload.blocked?` (or `.deployable?` becomes `false`, or `.status.state == "failure"`) even though the payload's `repository.full_name` was `evil/fork`, proving the write crossed repository boundaries — i.e., `victim_commit.stack.repository.full_name != payload['repository']['full_name']` yet the victim's status/deployability changed.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
