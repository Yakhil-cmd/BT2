## Title
Signature Verification Keyed by `repository.owner.login` While the Handler Acts on the Independently-Trusted `repository.full_name` — Cross-Organization Webhook Confusion - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-GitHub-App deployment, `WebhooksController#verify_signature` selects which webhook secret to verify the HMAC signature against using `repository_owner`, a value read straight out of the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, the event handlers (`PushHandler`, pull-request handlers, etc.) determine *which repository/stack to act on* using a different field of that same untrusted body: `payload.dig('repository', 'full_name')`. Because the field used to pick the verification key is not cryptographically bound to the field used to select the acted-upon repository, a request signed with Org A's webhook secret can carry an arbitrary `repository.full_name` pointing at Org B's repository, and the handler will act on Org B's stack.

### Finding Description
`WebhooksController` verifies signatures like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from the request body, with no relation yet established to the repository that will actually be acted upon. `Shipit.github(organization:)` resolves this owner string to a per-organization `GitHubApp` config (webhook secret, private key, etc.), which is exactly the "Using Multiple GitHub Applications" scenario documented and fixture-tested in this engine: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (i.e., the HMAC matches Org A's `webhook_secret`), `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked directly on the same `params` hash — the field that determined *authentication* (`repository.owner.login`) is never re-checked against the field that determines *action* (`repository.full_name`): [5](#0-4) 

Every handler resolves its target purely from `repository.full_name`: [6](#0-5) 

and `PushHandler` uses that to enqueue a sync/deploy-relevant job against whichever `Stack` matches: [7](#0-6) 

This mirrors the `vMaia`/`UtilityManager` pattern in the report: one code path (`claimBoost`) is overridden/scoped to a specific trust domain, but the sibling path (`forfeitBoost`) that shares the same underlying state is not re-derived from the same verified input — it trusts a different, unguarded field. Here, "verified organization" (used to pick the HMAC key) and "acted-upon repository" (used to pick the `Stack`) are two different unauthenticated fields of the same payload that are never cross-checked to be consistent with one another.

### Impact Explanation
An attacker who can obtain (or is legitimately entitled to, e.g., they administer their own org's GitHub App installation and thus know) the `webhook_secret` for **any one** organization configured on a shared Shipit instance can forge a webhook whose `repository.owner.login`/`organization.login` matches that known org (so the signature check passes) while `repository.full_name` names a repository belonging to a **different** organization/stack hosted on the same Shipit instance. Handlers such as `PushHandler` will then enqueue `GithubSyncJob`/deploy-relevant work for that unrelated stack, and pull-request handlers can similarly manipulate merge-queue/label state for a repository outside the attacker's authenticated org — an unauthorized action against a stack the attacker has no legitimate GitHub relationship with. This breaks the intended binding: "organization whose secret authenticated the request" == "repository the request is allowed to mutate."

### Likelihood Explanation
This requires a Shipit deployment configured with the "Using Multiple GitHub Applications" feature (multiple orgs, multiple webhook secrets) hosting stacks for more than one organization — a configuration the engine explicitly documents and supports. The attacker needs knowledge of one org's `webhook_secret` (their own org's app, which they administer) but zero access to the victim org's secret or any Shipit session/API token. Given that webhook secrets are routinely known by any of the several organizations' GitHub App admins on a shared instance, likelihood is moderate for multi-tenant deployments and nil for single-org deployments (where `repository_owner`/org keying is irrelevant).

### Recommendation
After resolving `repository_owner` and verifying the signature, re-derive and cross-check that the organization owning the signature actually matches the owner segment of `repository.full_name` (and `organization.login` when present) before dispatching to handlers, e.g., reject the webhook if `repository.full_name.split('/').first.casecmp(repository_owner) != 0`. Alternatively, resolve the target `Stack`/`Repository` first via `repository_owner` and refuse to act on any repository whose owner differs from the authenticated organization.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `OrgA` and `OrgB`, each with stacks tracking their own repos (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker administers `OrgA`'s GitHub App and thus knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": {"login": "OrgA"},
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` and the HMAC matches → passes. [1](#0-0) 
6. `PushHandler#process` resolves `stacks` via `repository_name = payload.dig('repository', 'full_name')` = `"OrgB/victim-repo"` and enqueues `sync_github` for OrgB's stack, even though the request was never authenticated by OrgB's secret. [6](#0-5) [7](#0-6)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
