### Title
Front-runnable permission revocation lets a denylisted creator still initialize a permissioned pool - ([File: programs/cp-swap/src/instructions/admin/close_permission_pda.rs])

### Summary
`initialize_with_permission` gates pool creation on the existence of a `Permission` PDA keyed solely by the `payer` pubkey [1](#0-0) . The only way to revoke that grant is the privileged `close_permission_pda` instruction, callable by `admin::ID` or `create_permission_pda_owner::ID` [2](#0-1) . Because the PDA is a static, address-derived account with no nonce/commit-reveal or freeze step, a payer who is about to be denylisted can see the pending `close_permission_pda` transaction and front-run it with their own `initialize_with_permission` transaction while the permission account is still live, exactly mirroring the FairSide `setConvictionless` front-running pattern (privileged denylist call targeting a specific address, defeated by racing a transaction that only requires the targeted, still-unprivileged, address to sign).

### Finding Description
Permission is stored as a single boolean-like PDA per authority: `create_permission_pda` initializes `Permission{ authority }` at seeds `[PERMISSION_SEED, permission_authority]` [3](#0-2) , and `close_permission_pda` removes it via the same seeds, closing lamports back to `owner` [4](#0-3) .

`initialize_with_permission` only checks that a `Permission` account exists at the PDA derived from `payer.key()`; it never checks a nonce, timestamp, or any other one-time-use token [1](#0-0) . Pool creation itself moves user funds into freshly created vaults and mints LP tokens, and separately records a `pool_creator` field that subsequently entitles that account to `collect_creator_fee`/`collect_creator_fee_permissionless` on every swap through the pool [5](#0-4) [6](#0-5) .

If the `admin`/`create_permission_pda_owner` decides to revoke a payer's permission (e.g., because the payer is misbehaving, spamming pools, or otherwise should be denylisted) and submits `close_permission_pda`, that payer can observe the pending transaction and submit `initialize_with_permission` first — a completely unprivileged instruction that only requires the payer's own signature and the still-existing PDA. This lets the targeted actor create one more permissioned pool (and become its `pool_creator`, entitled to ongoing creator-fee extraction) after the intent to revoke access has already been formed, defeating the purpose of the permission gate — the same "denylist can be front-run" bug class as the FairSide `setConvictionless` finding.

### Impact Explanation
Successful front-running lets an actor who should no longer be trusted still gain `pool_creator` status on a new pool, granting them a permanent, unauthorized entitlement to `creator_fees_token_0`/`creator_fees_token_1` collected from every swap through that pool [7](#0-6) . This is an unauthorized privileged effect on the fee-ledger accounting of the pool going forward, and defeats the entire purpose of the permissioned-pool-creation gate that the protocol relies on (`disable_create_pool`/permission checks in `initialize_with_permission`) [8](#0-7) .

### Likelihood Explanation
Exploitation requires only that the targeted payer notice a pending `close_permission_pda` transaction (via RPC/mempool-equivalent visibility or simply by observing an on-chain revocation pattern) and race it with a higher-priority-fee `initialize_with_permission` transaction signed with their own key — no admin cooperation or leaked keys are needed on the attacker's side. This is a realistic, cheap TOCTOU race rather than a privileged-signer path, since the winning transaction is fully unprivileged.

### Recommendation
Do not rely solely on the static existence of the `Permission` PDA at instruction time. Options: (1) require the admin's revocation to also flip pool-creation-blocking state that is checked independently (e.g., a global/per-payer freeze flag set-and-effective before any grace period), (2) add a commit/reveal or time-locked revocation so a pending revoke cannot be raced by the same address, or (3) make `close_permission_pda` also mark future uses of that seed as permanently denylisted (e.g., write a tombstone account) rather than simply closing/freeing the account so it can be silently reused/raced.

### Proof of Concept
1. Admin observes payer P should be denylisted and submits `close_permission_pda` for P's `Permission` PDA [9](#0-8) .
2. Before that transaction lands, P submits `initialize_with_permission` with `payer = P`, using P's still-existing `Permission` PDA (seeds `[PERMISSION_SEED, P]`) which passes the seeds constraint [1](#0-0) .
3. P's pool-creation transaction lands first (e.g., with a higher priority fee), successfully creating a pool and setting P (or an address P controls) as `pool_creator` [5](#0-4) .
4. The admin's `close_permission_pda` then lands, closing the PDA — but too late: P already created the pool and is entitled to `collect_creator_fee_permissionless` indefinitely on that pool [6](#0-5) .

#[derive(Accounts)]
pub struct CreatePermissionPda<'info> {
    #[account(
        mut,
        constraint = (owner.key() == crate::admin::ID || owner.key() == crate::create_permission_pda_owner::ID) @ ErrorCode::InvalidOwner
    )]
    pub owner: Signer<'info>,

    /// CHECK: permission account authority
    pub permission_authority: UncheckedAccount<'info>,

    /// Initialize config state account to store protocol owner address and fee rates.
    #[account(
        init,
        seeds = [
            PERMISSION_SEED.as_bytes(),
            permission_authority.key().as_ref()
        ],
        bump,
        payer = owner,
        space = Permission::LEN
    )]
    pub permission: Account<'info, Permission>,

    pub system_program: Program<'info, System>,
}

pub fn create_permission_pda(ctx: Context<CreatePermissionPda>) -> Result<()> {
    let permission = ctx.accounts.permission.deref_mut();
    permission.authority = ctx.accounts.permission_authority.key();
    Ok(())
}

pub fn collect_creator_fee_permissionless(
    ctx: Context<CollectCreatorFeePermissionless>,
) -> Result<()> {
    let mut pool_state = ctx.accounts.pool_state.load_mut()?;
    let creator_fees_token_0 = pool_state.creator_fees_token_0;
    let creator_fees_token_1 = pool_state.creator_fees_token_1;
    if creator_fees_token_0 == 0 && creator_fees_token_1 == 0 {
        return err!(ErrorCode::NoFeeCollect);
    }

    let signer_seeds: &[&[u8]] = &[crate::AUTH_SEED.as_bytes(), &[ctx.bumps.authority]];

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_0_vault.to_account_info(),
        ctx.accounts.creator_token_0.to_account_info(),
        ctx.accounts.vault_0_mint.to_account_info(),
        ctx.accounts.token_0_program.to_account_info(),
        creator_fees_token_0,
        ctx.accounts.vault_0_mint.decimals,
        &[signer_seeds],
    )?;

    transfer_from_pool_vault_to_user(
        ctx.accounts.authority.to_account_info(),
        ctx.accounts.token_1_vault.to_account_info(),
        ctx.accounts.creator_token_1.to_account_info(),
        ctx.accounts.vault_1_mint.to_account_info(),
        ctx.accounts.token_1_program.to_account_info(),
        creator_fees_token_1,
        ctx.accounts.vault_1_mint.decimals,
        &[signer_seeds],
    )?;

    pool_state.creator_fees_token_0 = 0;
    pool_state.creator_fees_token_1 = 0;
    pool_state.recent_epoch = Clock::get()?.epoch;

    Ok(())
}
