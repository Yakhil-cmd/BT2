### Title
Webhook signature verification keys on `repository.owner.login` while all event handlers act on the unrelated `repository.full_name` field, letting a webhook credential valid for one GitHub organization forge cross-organization Stack events - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/repository.rb`)

### Summary
`WebhooksController#verify_signature` selects *which* organization's `webhook_secret` to verify a delivery against by reading `repository.owner.login` straight out of the still-unverified JSON body [1](#0-0) . Once the signature passes, every `Handler` subclass resolves the target `Stack`/`Repository` from a *different* field of that same body, `repository.full_name` [2](#0-1) , and `Repository.from_github_repo_name` splits that string on `/` with no relationship enforced to the org that authenticated the request [3](#0-2) . Because `owner.login` and `full_name` are independently attacker-controlled sub-fields of the same payload, a delivery signed with the webhook secret belonging to organization A can freely claim `full_name = "orgB/some-repo"` and drive handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, …) against Stacks that belong to organization B, whose secret was never involved in the verification.

### Finding Description
This is the ZKsync `BLOCK_PERIOD`/`PRIORITY_EXPIRATION` bug class translated to this engine's trust boundary: a value used for a security-relevant computation (there, the block-time constant used to derive an expiry; here, the organization identity used to select the signing secret) is inconsistent with the value that the rest of the logic actually acts on (there, real 12s blocks vs. assumed 13s; here, `repository.full_name`, the field every handler actually consumes).

Concretely, in a multi-organization Shipit deployment (`config/secrets.yml` keyed per-org, as documented in `docs/setup.md`), each org gets its own `Shipit::GitHubApp` instance and its own `webhook_secret` [4](#0-3) . `verify_signature` does:

```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 

`repository_owner` is derived purely from the payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

The equality that this design implicitly relies on is:
`organization whose secret validated the HMAC == organization of the repository the handler subsequently writes to`

but nothing enforces it. `Handler#stacks` looks the target repository up from a *different* payload field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`Repository.from_github_repo_name` simply splits `owner/name` from that string and performs a lookup with no cross-check against the org whose secret signed the request:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [3](#0-2) 

Before verification and after verification, the two sides of the equality diverge:
- Before the attacker's request: `repository.owner.login == A`, `repository.full_name == "A/foo"` → signature checked with A's secret, handler acts on A's repo — consistent.
- After the attacker's crafted request: `repository.owner.login == A` (so A's secret still validates the HMAC), `repository.full_name == "B/bar"` → handler resolves and mutates Stacks belonging to organization B, whose secret was never checked.

### Impact Explanation
An actor who legitimately administers/operates the GitHub App for organization A (and thus knows A's `webhook_secret`, which they need only to authenticate their own org's traffic) can forge signed webhook deliveries that are accepted by Shipit's `WebhooksController` and then dispatched by handlers against Stacks/Repositories that belong to organization B — a target they have no authorization over in Shipit. Depending on handler and stack configuration this yields cross-organization writes: e.g. `PushHandler` triggers `stack.sync_github` for B's stacks [6](#0-5) , and `StatusHandler` creates commit statuses for B's commits via `commit.create_status_from_github!` [7](#0-6) , which can make otherwise-non-deployable commits deployable and, on stacks with `continuous_deployment` enabled, trigger an unauthorized deploy. This satisfies the "cross-repository writes / unauthorized deploy" impact bar for a High/Critical finding, because the boundary crossed is the org-to-secret binding that the multi-org webhook feature is supposed to enforce, not simple possession of a stolen secret.

### Likelihood Explanation
Exploitation requires only knowledge of a webhook secret for *any one* organization configured in a multi-org Shipit instance — a secret the attacker legitimately possesses as that org's GitHub App owner/administrator — plus knowledge of the target org/repo's `full_name`, which is public information. No access to organization B, no Shipit session, and no API token are required. This is a low-effort, single-request attack once the attacker controls their own org's app configuration, and it specifically defeats the multi-organization isolation feature documented in `docs/setup.md`.

### Recommendation
After the HMAC is verified with the `webhook_secret` selected for `repository_owner`, enforce that every field the handlers subsequently rely on (in particular `repository.full_name`'s owner segment) matches that same `repository_owner`, rejecting the delivery (422) otherwise. Equivalently, have `Handler#repository_name` derive the owner solely from the already-verified `repository_owner` rather than trusting `full_name` independently, or have `Repository.from_github_repo_name`/`WebhooksController` cross-check `full_name`'s owner segment against `repository_owner` before any handler runs.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`) [8](#0-7) .
2. As the legitimate administrator of the GitHub App for `OrgA`, obtain `OrgA`'s `webhook_secret`.
3. Craft a `push` event JSON body:
   ```json
   { "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
     "ref": "refs/heads/main", "after": "<sha under OrgB stack>" }
   ```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgA_secret, body)>` and `X-Github-Event: push`, then `POST /webhooks`.
5. `verify_signature` resolves `repository_owner == "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and the HMAC validates [1](#0-0) .
6. `PushHandler#process` runs `Handler#stacks`, which resolves `Repository.from_github_repo_name("OrgB/victim-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack [6](#0-5)  — a write to `OrgB`'s Stack performed using only `OrgA`'s credentials.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
