### Title
Operator precedence bug in `provision?` allows `allow_with_label`/`prevent_with_label` branches to bypass `review_stacks_enabled` gate - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#provision?` combines `repository.review_stacks_enabled` with the `provisioning_behavior_allow_all?` check using `&&`, then `||`s the remaining two branches, so Ruby operator precedence parses the expression as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. This means the `allow_with_label` and `prevent_with_label` branches are evaluated completely independently of `review_stacks_enabled`, letting any fork PR provision a `ReviewStack` on a repository where an operator explicitly left review stacks disabled.

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == true` must gate all `ReviewStack` provisioning branches, i.e. `provision? => review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`. What is actually evaluated in [1](#0-0)  is `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` due to `&&` binding tighter than `||`. When `review_stacks_enabled == false` and `provisioning_behavior == 'allow_with_label'`, the first term is `false`, but the second term `allow_with_label? && has_label?` can still be `true` independent of `review_stacks_enabled`, making the whole disjunction `true`.

Attacker flow: an unprivileged fork owner opens a pull request against a repository configured with `provisioning_behavior: allow_with_label` and `review_stacks_enabled: false`, attaching the operator-configured `provisioning_label_name` to their own PR (labels on a PR from a fork can be applied by the PR author if they have write access to their own fork/PR, or if a maintainer/bot applies labels automatically — regardless, the label content itself is attacker-controlled input reaching `provision?`). GitHub emits a `pull_request` `opened` webhook, which reaches `OpenedHandler#process` [2](#0-1) , which calls `respond_to_pull_request_opened?` → `provision?`, returns `true` despite `review_stacks_enabled == false`, and then `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` creates a `ReviewStack` with `branch: params.pull_request.head.ref` taken directly from the attacker's fork branch name/ref [3](#0-2) .

Existing guards do not stop this: webhook signature verification only authenticates that the payload came from GitHub for *that* repository — it does not enforce Shipit-side authorization policy such as `review_stacks_enabled`. `ExplicitParameters` only validates payload shape, not business logic. No other check in `provision?` re-verifies `review_stacks_enabled` for the label-based branches.

### Impact Explanation
A repository owner/operator who disabled review stacks (`review_stacks_enabled: false`) still gets an unauthorized `ReviewStack` created and queued for provisioning (`Shipit::ReviewStackProvisioningQueue.add(stack)`), with `branch` fully attacker-controlled from the fork's PR head ref. Downstream provisioning of review stacks runs the repository's `shipit.yml`/deploy steps for that branch, which is executed via `Command`/`PTY.spawn` on the deploy host — i.e., this is a path to command execution on the deploy host using content the attacker controls (their own fork branch), on a repository whose operator explicitly opted out of exactly this behavior. This is repeatable against any repository configured with `allow_with_label` (or `prevent_with_label`) and `review_stacks_enabled: false`, matching the Critical impact category (RCE on the deploy host via attacker-controlled review-stack provisioning) for that repository.

### Likelihood Explanation
Preconditions are configuration-only and plausible: `provisioning_behavior` set to `allow_with_label` (or `prevent_with_label`) while `review_stacks_enabled` is `false` — a reasonable state if an operator is staging/testing provisioning behavior or transitioning settings without re-verifying the interaction between the two flags. The attacker cost is minimal: open a PR from a fork and (for `allow_with_label`) apply the configured label, or (for `prevent_with_label`) simply not apply it — no Shipit credentials, GitHub App keys, or webhook secrets required. It's fully repeatable for every PR opened against any repository in this misconfigured-but-plausible state.

### Recommendation
Fix operator precedence in `provision?` by explicitly grouping the `review_stacks_enabled` gate around the entire disjunction:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
Minitest in a handler test (structure matches existing `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not provision a review stack when review_stacks_enabled is false, even with allow_with_label + label present" do
  repository = shipit_repositories(:shipit) # or create one
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: "allow_with_label",
    provisioning_label_name: "ship-it"
  )

  payload = payload_parsed(:pull_request_opened) # ensure repository.full_name matches, labels include "ship-it"

  assert_no_difference "Shipit::Stack.count" do
    Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::Stack.count` changes by 1 (bug reproduced — `provision?` returns `true` despite `review_stacks_enabled == false`). After applying the recommended fix: no `ReviewStack`/`Stack` is created, matching the intended binding `review_stacks_enabled == gating condition evaluated`.
