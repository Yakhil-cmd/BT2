### Title
Unguarded `onERC20Received` / `onERC721Received` Callbacks Allow Any Registered Token Contract to Emit Fake `RequestValueTransfer` Events, Draining Counterpart Bridge Assets — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

The `onERC20Received` and `onERC721Received` functions in the Kaia service-chain bridge contracts are `public` with no access control beyond requiring `msg.sender` to be a registered token. Any registered token contract can call these functions directly — without actually depositing tokens into the bridge — causing the bridge to emit `RequestValueTransfer` / `RequestValueTransferEncoded` events. The bridge operator on the counterpart chain processes these events and transfers or unlocks real bridged assets to the attacker-specified recipient, draining the counterpart bridge's reserves.

---

### Finding Description

`BridgeTransferERC20.onERC20Received` is declared `public` with no access-control modifier:

```solidity
// onERC20Received function of ERC20 token for 1-step deposits to the Bridge.
function onERC20Received(
    address _from,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
)
    public          // ← no onlyRegisteredToken, no onlyOwner, no onlyOperators
{
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
``` [1](#0-0) 

The intended design is a 1-step deposit: the token contract first transfers tokens to the bridge, then calls `onERC20Received` as a callback. The bridge has no mechanism to verify that a token transfer actually preceded the callback.

`_requestERC20Transfer` (the internal function called by `onERC20Received`) enforces only:

1. `onlyRegisteredToken(msg.sender)` — `msg.sender` must be a registered token address
2. `onlyUnlockedToken(msg.sender)` — token must not be locked
3. `isRunning` — bridge must be running
4. `_value > 0` [2](#0-1) 

None of these checks verify that the bridge's token balance actually increased before the event is emitted. In non-`modeMintBurn` (lock/unlock) mode, no burn is attempted, so the function proceeds unconditionally to:

```solidity
emit RequestValueTransfer(
    TokenType.ERC20, _from, _to, _tokenAddress, _value, requestNonce, fee, _extraData
);
requestNonce++;
```

The same pattern exists for ERC721:

```solidity
function onERC721Received(
    address _from,
    uint256 _tokenId,
    address _to,
    bytes memory _extraData
)
    public   // ← no access control
{
    _requestERC721Transfer(msg.sender, _from, _to, _tokenId, _extraData);
}
``` [3](#0-2) 

In non-`modeMintBurn` mode, `_requestERC721Transfer` also emits `RequestValueTransferEncoded` and increments `requestNonce` without verifying the bridge holds the NFT. [4](#0-3) 

The bridge operator (`BridgeInfo.handleRequestValueTransferEvent`) monitors these events and unconditionally calls `handleERC20Transfer` / `handleERC721Transfer` on the counterpart bridge, which transfers or unlocks real assets to `_to`:

```go
case ERC20:
    handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to,
        ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
``` [5](#0-4) 

`handleERC20Transfer` on the counterpart bridge is gated by `onlyOperators` and performs the actual token transfer/mint:

```solidity
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [6](#0-5) 

---

### Impact Explanation

**In non-`modeMintBurn` (lock/unlock) mode:**

A registered token contract calls `bridge.onERC20Received(victim_address_on_counterpart, attacker_address_on_counterpart, large_value, 0, "")` directly, without transferring any tokens to the bridge. Provided `feeOfERC20[token] == 0` or `feeReceiver == address(0)`, `_payERC20FeeAndRefundChange` returns 0 without reverting. The `RequestValueTransfer` event is emitted with `_value = large_value`. The bridge operator processes it on the counterpart chain and calls `handleERC20Transfer`, which calls `IERC20(_tokenAddress).safeTransfer(_to, _value)`, transferring real tokens from the counterpart bridge's reserves to the attacker-controlled address.

**Corrupted bridge nonce:** `requestNonce` is incremented for every fake event, permanently corrupting the nonce sequence used for recovery and replay protection. [7](#0-6) 

---

### Likelihood Explanation

The attacker must control a registered token contract. Token registration is performed by the bridge owner (`onlyOwner`), so the attacker must have deployed a token that was subsequently registered, or must have compromised a registered token contract. This is a semi-trusted but not fully privileged position — the bridge owner trusts the token address, not the token contract's internal logic. A malicious or upgradeable registered token contract can exploit this without any further privilege.

---

### Recommendation

Add a balance check in `_requestERC20Transfer` to verify the bridge's token balance increased by at least `_value + _feeLimit` before emitting the event:

```solidity
uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
// ... existing fee logic ...
uint256 balanceAfter = IERC20(_tokenAddress).balanceOf(address(this));
require(balanceAfter >= balanceBefore + _value, "tokens not received");
```

Alternatively, restrict `onERC20Received` and `onERC721Received` to only be callable from within a `safeTransfer` / `transferFrom` callback context (e.g., by verifying the bridge's balance increased), or add an `onlyRegisteredToken` modifier that also validates the transfer occurred atomically.

---

### Proof of Concept

1. Bridge owner deploys bridge in non-`modeMintBurn` mode and registers `MaliciousToken` at address `0xMAL`.
2. Counterpart bridge holds 1,000,000 units of the counterpart token.
3. Attacker (controlling `0xMAL`) calls:
   ```solidity
   bridge.onERC20Received(
       address(0),          // _from (irrelevant)
       attackerOnCounterpart, // _to
       1_000_000,           // _value
       0,                   // _feeLimit
       ""                   // _extraData
   );
   // called from 0xMAL, which is a registered token
   ```
4. `_requestERC20Transfer(0xMAL, address(0), attackerOnCounterpart, 1_000_000, 0, "")` passes all checks.
5. `_payERC20FeeAndRefundChange` returns 0 (fee is 0, feeLimit is 0).
6. No burn (non-modeMintBurn).
7. `RequestValueTransfer` event emitted; `requestNonce` incremented.
8. Bridge operator on counterpart chain calls `handleERC20Transfer(txHash, address(0), attackerOnCounterpart, counterpartToken, 1_000_000, nonce, blockNum, "")`.
9. Counterpart bridge executes `IERC20(counterpartToken).safeTransfer(attackerOnCounterpart, 1_000_000)`.
10. Attacker receives 1,000,000 counterpart tokens. Source bridge received 0 tokens. [1](#0-0) [3](#0-2) [8](#0-7)

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}
