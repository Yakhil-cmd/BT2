### Title
Concurrent `light/dry_run_aa` Requests Race on Shared In-Memory Storage Caches, Allowing Data Mix-Up and Corruption Between Unrelated AA Estimations - ([File: network.js])

### Summary
`network.js`'s `light/dry_run_aa` handler lets any unprivileged peer trigger `aa_composer.dryRunPrimaryAATrigger()`, which performs a full AA execution against a real DB connection and then "reverts" its effects both in the DB (`ROLLBACK`) and in process-wide, in-memory caches (`storage.assocUnstableUnits`, `assocStableUnits`, `assocBestChildren`, `assocUnstableMessages`, `assocStableUnitsByMci`, etc.) via `revertResponsesInCaches()`. This mirrors the CVE-2011-1475 bug class: shared, mutable per-connection/per-request state that is not properly isolated across concurrently interleaved operations, so effects meant for one "request" can leak into or corrupt another. [1](#0-0) 

### Finding Description
`dryRunPrimaryAATrigger()` takes a **fresh DB connection** and local `stateVars`/`arrResponses`, but the AA-response write path (`writer.saveJoint`, invoked deep inside `handleTrigger`) mutates **global, process-wide JS objects** in `storage.js` (`assocUnstableUnits`, `assocBestChildren`, `assocUnstableMessages`, `assocStableUnits`, `assocStableUnitsByMci`) that are shared across *all* connections and all concurrently running AA executions — both real (`handlePrimaryAATrigger`) and dry-run (`dryRunPrimaryAATrigger`) ones. [2](#0-1) 

`writer.js` shows these caches being written to directly during unit save, keyed by unit/parent identifiers, not scoped to a particular in-flight request: [3](#0-2) 

At the end of a dry run, `revertResponsesInCaches(arrResponses)` presumably deletes/reverses whatever was written to these same global maps for the units created during that particular dry run. However, `handlePrimaryAATrigger()` (the real, non-dry-run AA processing path invoked from `handleAATriggers`) is serialized only under the `'aa_triggers'` mutex, and `dryRunPrimaryAATrigger()` does **not** appear to take the same `'aa_triggers'`/`'write'` mutex before mutating these shared caches — it only takes a DB connection and issues `BEGIN`/`ROLLBACK` on that connection, which does not protect the in-process JS object caches from concurrent access by another dry run or by the real AA trigger processor running in parallel (Node's event loop interleaves the async I/O callbacks of both).

Because `light/dry_run_aa` is reachable by any unprivileged remote peer and can be invoked repeatedly and concurrently (multiple simultaneous websocket requests), two interleaved dry runs (or a dry run interleaved with real AA processing) can:
- Both add temporary unit-props for units with colliding/derived state to the same global maps.
- Have one dry run's `revertResponsesInCaches` delete/overwrite entries that were actually inserted by the other, still in-flight request (or by real trigger processing), since the same in-memory keys (units, `assocBestChildren` mapping by best-parent-unit) are shared.
- Leave the storage caches in a state inconsistent with the database, since the rollback only affects one connection's transaction while the JS caches are shared mutable state touched by both flows.

This is directly analogous to the Tomcat BIO connector bug: a shared, insufficiently-isolated buffer/state structure processed by concurrent request-handling paths, causing data belonging to one logical "request" (dry run A) to bleed into or corrupt the state of a concurrent one (dry run B or the real trigger pipeline).

### Impact Explanation
If the in-memory caches diverge from actual DB content because of this race, subsequent legitimate AA trigger validation/execution (`handleAATriggers` → `handlePrimaryAATrigger` → `writer.saveJoint` → `main_chain.updateMainChain`) can read stale, wrong, or partially-reverted unit properties (`is_free`, `main_chain_index`, `best_parent_unit`, stability flags) from `storage.assocUnstableUnits` / `assocBestChildren` / `assocStableUnits`. This can cause a node to compute wrong main-chain/stability decisions for AA-generated units — i.e., **node disagreement on validity or stability** — and, since AA execution directly produces payment/balance-changing units, a corrupted best-parent or stability computation for an AA chain can also translate into incorrect AA balance/state bookkeeping (**AA fund loss/freezing** or double application of a state update) for real (non-dry-run) triggers processed around the same time.

### Likelihood Explanation
`light/dry_run_aa` is reachable by any peer/light client with no rate limiting or serialization against the AA cache other than the DB connection's own transaction; nothing in the reviewed code path shows it acquiring the `'aa_triggers'`/`'write'` mutex before mutating `storage.js`'s global associative caches. An attacker (or even a busy legitimate light-wallet workload) firing multiple `light/dry_run_aa` requests in quick succession, potentially timed against ordinary AA trigger activity, is a low-cost, remotely-triggerable condition, making the likelihood non-trivial. However, I was **not able to fully verify** (due to running out of tool calls) the exact contents of `revertResponsesInCaches()`, nor whether `dryRunPrimaryAATrigger` might in fact be implicitly serialized elsewhere (e.g. an outer mutex in `network.js` around `handleRequest`, or a global "in dry run" flag not surfaced by my searches). This uncertainty should be resolved by reading `aa_composer.js`'s `revertResponsesInCaches` implementation and the full `light/dry_run_aa` call chain in `network.js` before treating this as confirmed.

### Recommendation
- Serialize `dryRunPrimaryAATrigger()` (and `estimatePrimaryAATrigger()`) against the same `'aa_triggers'`/`'write'` mutex used by `handlePrimaryAATrigger()`, so dry runs cannot interleave with each other or with real AA trigger processing at the level of the shared `storage.js` caches.
- Alternatively, make dry-run execution operate on a deep-cloned, request-local snapshot of the relevant `storage.js` caches rather than mutating the shared global maps directly, eliminating the need for revert-based cleanup entirely.
- Add invariant checks (as already partly done in tests comparing `storage.assocUnstableUnits` etc. before/after a dry run) that run in production/debug builds to detect cache divergence after a `light/dry_run_aa` call, and fail loudly (or self-heal via `storage.resetMemory`) if divergence is detected.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end due to tool budget):
1. Attacker connects two websocket sessions to a full node.
2. From session 1, send `light/dry_run_aa` for AA address `X` with a trigger designed to create a chain of secondary AA calls (maximizing time spent inside `handleTrigger`/`writer.saveJoint` before rollback).
3. Concurrently, from session 2, send another `light/dry_run_aa` for an AA that shares a `best_parent_unit`/adjacent MC unit with session 1's dry run (e.g., trigger via the same `objMcUnit`, since `dryRunPrimaryAATrigger` reuses `readLastStableMcUnit`), so both dry runs' internal `writer.saveJoint` calls touch the same `assocBestChildren[my_best_parent_unit]` / `assocUnstableUnits` keys.
4. Observe (via `storage.assocUnstableUnits`/`assocBestChildren` snapshots, as done in `test/aa_composer.test.js`'s `fixCache`/`t.deepEqual` assertions) that after both dry runs complete, the caches do not match their pre-test state, or that a subsequent real AA trigger (`handleAATriggers`) computes a different main-chain/stability result than it would have without the concurrent dry run. [4](#0-3)
