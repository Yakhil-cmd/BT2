### Title
`min-ustx-for-sats-amount` truncated double division lets a staker register a protocol bond with zero (or negligible) STX locked while receiving full sBTC reward shares - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond` gates the amount of STX a staker must lock by calling `min-ustx-for-sats-amount`, which computes the minimum required uSTX via two chained integer divisions. For sufficiently small `sats-amount` relative to `stx-value-ratio`, the first division already truncates to `0`, forcing the whole calculation to `0` regardless of `min-ustx-ratio`. A staker can then call `register-for-bond` with `amount-ustx = 0` and be credited the full `sats-total` as bond shares, which drive both signer voting weight and sBTC reward distribution — with no STX collateral backing that share.

### Finding Description
`min-ustx-for-sats-amount` is defined as: [1](#0-0) 

```
(/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
```

The inner term `(/ (* stx-value-ratio sats-amount) u100)` is evaluated with integer (floor) division *before* being multiplied by `min-ustx-ratio`. If `stx-value-ratio * sats-amount < 100`, this inner division rounds down to `0`, and the outer division of `0 * min-ustx-ratio / 10000` is also `0` — independent of how large `min-ustx-ratio` is. This is the same rounding-class defect as the `LiquidityPool.borrow` bug cited in the report: a floor-division on a small numerator collapses the derived "required collateral" to zero.

`register-for-bond` uses this value as the sole floor check for how much STX the staker must lock: [2](#0-1) 

```
;; Verify that they're sending enough STX
(asserts!
    (>= amount-ustx
        (min-ustx-for-sats-amount sats-total (get stx-value-ratio bond)
            (get min-ustx-ratio bond)
        ))
    ERR_INSUFFICIENT_STX
)
```

and the subsequent balance check only verifies `total-balance >= amount-ustx`: [3](#0-2) 

If `min-ustx-for-sats-amount(sats-total, ...)` rounds to `0`, both checks are trivially satisfied with `amount-ustx = 0`. The staker is then registered with `sats-total` full sats credited as their bond size: [4](#0-3) 

```
(map-set protocol-bond-memberships tx-sender {
    bond-index: bond-index,
    amount-ustx: amount-ustx,
    signer: signer,
    is-l1-lock: (is-ok btc-lockup),
    amount-sats: sats-total,
})
(map-set protocol-bonds-total-staked bond-index
    (+ current-total-staked sats-total)
)
...
(try! (add-staker-to-bond-cycles tx-sender signer bond-index first-reward-cycle
    BOND_LENGTH_CYCLES sats-total
))
```

`sats-total` (the bond's share size, used for both signer weight and sBTC reward computation via `calculate-bond-rewards`/`compute-earned-rewards`) is credited in full, even though `amount-ustx` (the actual STX collateral securing the position) is `0`. The bond-yield distribution logic pays sats-denominated rewards purely proportional to `sats-total`, with no re-check against `amount-ustx`: [5](#0-4) 

This breaks the equality that reward shares/signing weight are supposed to be backed 1:1 (per the configured ratio) by locked STX — a staker gets `sats-total` worth of shares for `0` uSTX locked, i.e. unbacked reward/voting weight.

Note: for the `is-ok btc-lockup` (L2/sBTC) path, `new-sbtc = sats-total`, so real sBTC is transferred into the contract via `roll-sbtc`, meaning the sBTC-value side of the position is still funded. But for the L1-lockup path (`btc-lockup` is `err`), `new-sbtc` is `u0` and no sBTC/STX collateral is pulled at all — the entire position is represented only by `amount-ustx` (the STX side), which this bug allows to be zero. In that case the staker obtains full bond shares (signer delegation weight and reward eligibility) with literally nothing locked on either chain.

### Impact Explanation
This is a "signing weight or reward slots exceeding locked value" class issue (High per the provided impact rubric): a staker can obtain sats-denominated bond shares (driving reward payouts and signer voting weight) without locking the STX collateral that the protocol's own accounting model requires as backing. It does not require the bond/pause admin's key or malicious admin behavior — the truncation is a structural property of the formula that arises for any admin-chosen `stx-value-ratio`/`min-ustx-ratio` pair whenever a staker chooses a small enough `sats-amount`.

### Likelihood Explanation
Likelihood is High: any unprivileged staker who has been allowlisted for a bond (a normal, non-privileged operation once `setup-bond`/allowlist exist) can trivially pick a `sats-amount` small enough (e.g. `sats-amount` such that `stx-value-ratio * sats-amount < 100`) to zero the STX floor. On the L1-lockup path, this can be repeated/scaled by aggregating many such under-collateralized registrations (subject to per-staker one-bond-at-a-time and allowance limits, but the underlying rounding defect is unconditional and repeatable across bonds/cycles).

### Recommendation
Round the required STX collateral **up**, not down, and avoid chaining truncating divisions. E.g., compute the numerator as a single product before any division, or apply ceiling division at each step:

```
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    ;; ceil( stx-value-ratio * sats-amount * min-ustx-ratio / (100 * 10000) )
    (/ (+ (* stx-value-ratio sats-amount min-ustx-ratio) (- (* u100 u10000) u1))
       (* u100 u10000))
)
```
or equivalently use a `mulDiv`-style rounding-up helper, ensuring `min-ustx-for-sats-amount(sats, ratio, min-ratio) > 0` whenever `sats > 0`.

### Proof of Concept
1. `setup-bond` is created (by the bond admin, a normal privileged setup step, not attacker-controlled at exploit time) with `stx-value-ratio = 10` (as used in the repo's own test fixtures, e.g. `contrib/core-contract-tests/tests/pox-5/pox-5.test.ts` "waterfall distributions" scenario) and any `min-ustx-ratio`.
2. Attacker (an allowlisted staker) calls `register-for-bond` with `btc-lockup = (err sats-amount)` (L1 path) where `sats-amount = 9` (or any value with `stx-value-ratio * sats-amount < 100`), and `amount-ustx = 0`.
3. `min-ustx-for-sats-amount(9, 10, min-ustx-ratio)` = `(/ (* (/ (* 10 9) 100) min-ustx-ratio) 10000)` = `(/ (* (/ 90 100) min-ustx-ratio) 10000)` = `(/ (* 0 min-ustx-ratio) 10000)` = `0`.
4. The assertion `(>= amount-ustx 0)` passes trivially; `total-balance >= 0` passes trivially.
5. `protocol-bond-memberships` and `protocol-bonds-total-staked` are updated with `amount-sats: 9`, and `add-staker-to-bond-cycles` credits `9` sats of bond shares to the attacker's signer for the bond's cycles — all while `amount-ustx = 0` and (on the L1 path) no sBTC is custodied either.
6. At reward-distribution time, `calculate-bond-rewards` pays out sBTC proportional to `sats-total` (which includes the attacker's unbacked `9` sats), diluting/mis-crediting rewards that should scale with real locked value, and the attacker's signer gains delegation weight from an uncollateralized position.
