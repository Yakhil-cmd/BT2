### Title
Missing `DenyRecursively` wrapper on `DenyReserveTransferToRelayChain` allows nested-instruction bypass of the reserve-transfer-to-Relay deny rule - (File: system-parachains/bridge-hubs/bridge-hub-kusama/src/xcm_config.rs)

### Summary
BridgeHubKusama's `Barrier` wraps `DenyReserveTransferToRelayChain` directly in `DenyThenTry`, without the `DenyRecursively` combinator that the sibling `bridge-hub-polkadot` (and `bulletin-polkadot`) chains apply to the same deny rule. `DenyReserveTransferToRelayChain`'s `ShouldExecute` implementation (from `staging-xcm-builder`) only inspects the top-level instruction sequence, so a program that hides `ReserveAssetDeposited`/`InitiateReserveWithdraw` targeting the Relay Chain inside a `SetAppendix`, `SetErrorHandler`, or `ExportMessage` sub-program is not inspected by the deny check and falls through to the "allow" side of `DenyThenTry`.

and to `bulletin-polkadot`, which does the same: [3](#0-2) 

`DenyRecursively` was introduced upstream specifically to close the gap where `DenyReserveTransferToRelayChain`'s `ShouldExecute::should_execute` only scans the top-level instruction list of an `Xcm` program and does not recurse into the nested `Xcm<Call>` payloads carried by `SetAppendix`, `SetErrorHandler`, or `ExportMessage`. Without the recursive wrapper, an attacker can construct a top-level program whose visible instructions are benign (e.g., `ClearOrigin`, `SetAppendix(...)`) while the actual `ReserveAssetDeposited`/`InitiateReserveWithdraw` targeting the Relay Chain is nested inside the appendix/error-handler/export payload. The `DenyReserveTransferToRelayChain` check at the top level sees nothing to deny and returns "not applicable," so `DenyThenTry` proceeds to the "then" tuple (`TakeWeightCredit`, `AllowKnownQueryResponses`, `WithComputedOrigin<...>`), which independently evaluates weight/origin conditions and can allow the top-level program to execute — including its nested appendix/error-handler, which the XCM executor runs regardless of whether the barrier "saw" it.

The attacker-reachable path is `pallet_xcm::execute` called by a signed extrinsic, where `ExecuteXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalSignedOriginToLocation>` converts the signer into a local `AccountId32` XCM origin usable to run arbitrary user-supplied XCM programs through the same `XcmExecutor`/`Barrier` used for message queue processing (config referenced at `system-parachains/bridge-hubs/bridge-hub-kusama/src/xcm_config.rs`, matching the pattern used in other system chains for `ExecuteXcmOrigin`/`LocalSignedOriginToLocation`). I was not able to directly view the `ExecuteXcmOrigin` declaration in `bridge-hub-kusama/src/xcm_config.rs` in this pass (the grep for that file specifically returned no matches, unlike other chains where it's present), so this is inferred from the consistent config pattern in sibling chains and cannot be 100% confirmed for this exact file without further inspection — flagged as a residual uncertainty.

### Impact Explanation
If confirmed, this opens the deny-listed reserve-transfer-to-Relay-Chain path from BridgeHubKusama via a crafted `pallet_xcm::execute` call, bypassing an explicit security control (`DenyReserveTransferToRelayChain`) that the runtime maintainers intended to enforce globally. This matches the scoped impact: unauthorized reserve transfer path opened toward the Relay Chain from BridgeHubKusama.

### Likelihood Explanation
The precondition is simply calling `pallet_xcm::execute` as a signed, unprivileged account — no special permissions, proxy setup, or governance action required. The bug is reproducible deterministically: it is a structural gap between the deny-list definition and the recursive-inspection wrapper, not a race condition or probabilistic exploit. The only uncertainty is whether the remaining barrier stages (`TakeWeightCredit`, `WithComputedOrigin<AllowTopLevelPaidExecutionFrom<Everything>, ...>`) would still permit the crafted top-level program to pass (e.g., requiring the message to pay for its own execution) — this is likely satisfiable by a normal user paying execution fees, since `AllowTopLevelPaidExecutionFrom<Everything>` accepts any origin that fronts payment.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively` in BridgeHubKusama's `Barrier`, consistent with `bridge-hub-polkadot` and `bulletin-polkadot`:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```
This should also be audited/applied across the other affected chains identified with the same gap (`asset-hub-kusama`, `asset-hub-polkadot`, `collectives-polkadot`, `coretime-kusama`, `coretime-polkadot`, `encointer`, `people-kusama`, `people-polkadot`), though those are outside this question's scope.

### Proof of Concept
xcm-emulator integration test targeting BridgeHubKusama:
```rust
#[test]
fn nested_reserve_transfer_to_relay_via_appendix_should_be_denied() {
    let signer: AccountId = /* funded unprivileged account on BridgeHubKusama */;

    let nested_deny_triggering = Xcm(vec![
        InitiateReserveWithdraw {
            assets: Wild(All),
            reserve: Location::parent(), // targets the Relay Chain
            xcm: Xcm(vec![]),
        },
    ]);

    let program = Xcm(vec![
        WithdrawAsset((Here, 1_000_000_000_000u128).into()),
        BuyExecution { fees: (Here, 1_000_000_000_000u128).into(), weight_limit: Unlimited },
        SetAppendix(nested_deny_triggering), // hides the denied instruction from top-level scan
        ClearOrigin,
    ]);

    BridgeHubKusama::execute_with(|| {
        let result = <BridgeHubKusama as BridgeHubKusamaPallet>::PolkadotXcm::execute(
            RuntimeOrigin::signed(signer),
            bx!(VersionedXcm::from(program)),
            Weight::from_parts(10_000_000_000, 1_000_000),
        );

        // Expected (fixed) behavior: barrier rejects the whole program (Filtered/Barrier error).
        // Current (vulnerable) behavior: call succeeds and the appendix's reserve-withdraw
        // targeting the Relay Chain executes.
        assert!(result.is_err(), "nested reserve-transfer-to-relay via SetAppendix must be denied, not executed");
    });
}
```
Expected assertion under the fix: the barrier returns `Barrier`/`Filtered` before any weight is consumed and before the appendix executes. Under the current code, the test would need to additionally assert that no relay-chain-directed reserve-withdraw accounting event fired, to confirm the bypass.
