### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login`, but handlers act on unrelated fields (`repository.full_name`, or no repository at all) — allowing cross-organization/cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, a value taken from the *payload itself* (`repository.owner.login` or `organization.login`). The handlers that subsequently execute the webhook (`PushHandler`, `StatusHandler`, etc.) act on a different, independently-controlled field of the same payload (`repository.full_name`) — or, in `StatusHandler`'s case, on no repository scope at all. In a multi-organization Shipit deployment, this breaks the binding `organization that authenticated == repository that is written`, letting an unauthenticated caller pick a weakly-configured (or secret-less) organization to satisfy the signature check while directing the resulting side effects at a different, unrelated organization's stacks/commits.

### Finding Description
`verify_signature` resolves the GitHub App used for HMAC verification purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected app has no `webhook_secret` configured — and Shipit's own example configs document `webhook_secret: # nil` as an acceptable per-organization setting, alongside explicit support for multiple organizations each with independent `app_id`/`webhook_secret`: [3](#0-2) 

Once the signature step passes (trivially, if the chosen `repository_owner` maps to an org with no secret, or to any org whose secret the caller knows), the actual work is dispatched to handlers, which resolve their target scope from a *different* field of the same JSON body: [4](#0-3) 

`PushHandler` uses that repository/branch scope to trigger a GitHub sync (which can drive continuous deployment) for whatever stack matches `repository.full_name`: [5](#0-4) 

`StatusHandler` is even less scoped — it doesn't filter by repository/organization at all, it matches purely on commit SHA across the entire instance: [6](#0-5) 

So the equality actually enforced is `repository_owner (used to pick the verifying secret) == repository_owner (used to pick the verifying secret)` — a tautology — while the intended security property is `organization that authenticated == repository/commit that is mutated`. Nothing cross-checks that the owner used to select the verifying `webhook_secret` matches the owner of the repository/commit the handler subsequently writes to.

### Impact Explanation
In a multi-org deployment (explicitly supported per `config/secrets.development.shopify.yml` / `lib/shipit.rb#github_app_config`), an attacker can craft a `push` or `status` webhook body where `repository.owner.login` (or `organization.login`) names an organization with a blank/unset `webhook_secret`, while the payload's `repository.full_name` (for push) or `sha` (for status, unscoped) targets a victim organization's stack/commit. The signature check passes for the weak org, but the handler mutates state belonging to the victim org: `PushHandler` triggers `Stack#sync_github`, which can enqueue continuous-deployment-driven deploys, and `StatusHandler` can forge a passing CI `Status` on an arbitrary commit instance-wide, which can be used to satisfy status-check gates that authorize merges/deploys. This falls under "unauthorized deploy, rollback, or merge" and "escalation" impact categories.

### Likelihood Explanation
Requires only that the Shipit instance host webhooks for at least one organization with no (or a known/leaked) `webhook_secret` — a configuration explicitly documented as valid in the repo's own example secrets files — while other organizations host higher-value repositories. No session, API token, or GitHub write access is required; the webhook endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`).

### Recommendation
Bind the verified organization to the field(s) the handler actually consumes: after selecting the GitHub App/secret by `repository_owner`, re-derive `repository_owner` from `repository.full_name`'s owner segment (and reject if they differ), or better, require them to be identical inputs used consistently by both `verify_signature` and every `Handler#repository_name`/`stacks` lookup. Additionally, `StatusHandler` should scope status updates to commits belonging to stacks under the verified organization, not globally by SHA.

### Proof of Concept
1. Configure Shipit with two organizations: `weak-org` (no `webhook_secret`) and `victim-org` (has a stack tracking `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "weak-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret) regardless of the actual `X-Hub-Signature` header.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — an action the attacker was never authorized to trigger for `victim-org`.
5. A similar unauthenticated `status` event (also verified against `weak-org`) can forge a `success` status for any commit SHA instance-wide via `StatusHandler`, since it performs no repository/organization filtering at all.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
