### Title
Unauthenticated P2P Peer Can Forge `ServiceChainReceiptResponseMsg` to Corrupt Anchored Block Number and Drain BridgeTxPool — (`node/sc/sub_bridge_handler.go`)

---

### Summary

Any node that can establish a P2P connection to a SubBridge (passing only a trivially-satisfied network-ID/protocol-version handshake) can send a forged `ServiceChainReceiptResponseMsg`. Because the SubBridge broadcasts pending anchoring tx hashes to every connected peer and `handleParentChainReceiptResponseMsg` performs zero per-message signature or origin verification, the attacker can supply those hashes back in a fabricated receipt, causing the SubBridge to permanently record a false anchored block number, write a fake parent-chain receipt to its DB, and remove the real anchoring transaction from the BridgeTxPool — all without the anchoring transaction ever having been executed on the parent chain.

---

### Finding Description

**Step 1 — Permissionless peer admission.**

`SubBridge.handle()` registers any peer that passes the bridge handshake: [1](#0-0) 

The handshake (`baseBridgePeer.Handshake`) only validates `NetworkId` and `ProtocolVersion` — both public constants. The `ChainID` field is **self-reported** by the connecting peer: [2](#0-1) 

The `RegisterNewPeer` chainID check at line 466 is the only guard, but its return value is **silently discarded** at the call site: [3](#0-2) 

So even a chainID mismatch does not prevent the peer from entering the message-handling loop.

**Step 2 — SubBridge leaks pending tx hashes to all peers.**

On every local chain head event, `broadcastServiceChainReceiptRequest` sends the full list of pending BridgeTxPool hashes to **every** connected peer: [4](#0-3) 

The attacker receives these hashes for free.

**Step 3 — No-auth receipt response processing.**

`handleParentChainReceiptResponseMsg` decodes the incoming `[]*types.ReceiptForStorage` and immediately passes them to `writeServiceChainTxReceipts` with no signature check, no origin validation, and no cross-reference against actual parent-chain state: [5](#0-4) 

**Step 4 — State corruption.**

`writeServiceChainTxReceipts` looks up each receipt's `TxHash` in the BridgeTxPool. If found and the tx is a chain-data-anchoring type, it:

1. Calls `WriteReceiptFromParentChain` — writes the forged receipt to the child-chain DB.
2. Calls `WriteAnchoredBlockNumber` — **persistently overwrites** the anchored block number with the value embedded in the anchoring tx's payload.
3. Calls `RemoveTx` — **permanently removes** the real anchoring tx from the pool. [6](#0-5) 

The attacker does not need to forge any receipt content beyond setting `TxHash` to a known pending hash; the block number and block hash written to the DB are taken from the **legitimate anchoring tx's own payload**, so the corruption is internally consistent and will not be detected by any local sanity check.

---

### Impact Explanation

- **Persistent DB corruption**: `WriteAnchoredBlockNumber` writes to the canonical chain DB. The SubBridge now believes service-chain blocks up to that number have been anchored on the parent chain when they have not.
- **BridgeTxPool drain**: The real anchoring tx is removed and will never be rebroadcast or retried, so the anchoring gap is permanent unless the operator manually intervenes.
- **Fake parent-chain receipt**: `WriteReceiptFromParentChain` stores a fabricated receipt keyed by the service-chain block hash, corrupting any downstream logic that reads it to verify parent-chain execution.

This satisfies the "persistent corruption of state data that breaks settlement" impact gate: the anchoring invariant — that `ReadAnchoredBlockNumber()` reflects only legitimately executed parent-chain transactions — is permanently violated.

---

### Likelihood Explanation

- The SubBridge's bridge P2P port is reachable by any node that knows the network ID and protocol version (both public).
- The attacker learns the exact tx hashes to forge from the SubBridge's own `ServiceChainReceiptRequestMsg` broadcast.
- No cryptographic material (private keys, signatures) is required.
- The attack is repeatable: a new anchoring tx added to the pool will again be broadcast and can again be forged.

---

### Recommendation

1. **Authenticate receipt responses**: Require each `ServiceChainReceiptResponseMsg` to carry an ECDSA signature from the known MainBridge operator key, verified before calling `writeServiceChainTxReceipts`.
2. **Verify receipts against parent-chain state**: Before accepting a receipt, query the remote backend (`remoteBackend.TransactionReceiptRpcOutput`) to confirm the tx was actually mined on the parent chain.
3. **Restrict peer admission**: Maintain an allowlist of trusted MainBridge node IDs (derived from operator keys) and reject peers not on the list during `RegisterNewPeer`, propagating the error back to `handle()`.
4. **Fix the ignored error**: The return value of `sb.handler.RegisterNewPeer(p)` must be checked and, on error, the peer must be disconnected before entering the message loop. [3](#0-2)

### Proof of Concept

```
1. Attacker node starts a devp2p listener advertising:
      NetworkId  = <SubBridge's networkId>
      ProtocolVersion = 2  (SCProtocolVersion)
      ChainID    = <configured ParentChainID>

2. SubBridge connects (or attacker dials SubBridge's bridge port).
   Handshake succeeds; peer is registered.

3. SubBridge calls broadcastServiceChainReceiptRequest() on the next
   local chain head event, sending:
      ServiceChainReceiptRequestMsg → [txHash_A, txHash_B, ...]

4. Attacker constructs:
      receipts := []*types.ReceiptForStorage{
          {TxHash: txHash_A, Status: 1},
      }
   and sends ServiceChainReceiptResponseMsg(receipts).

5. handleParentChainReceiptResponseMsg decodes without verification,
   calls writeServiceChainTxReceipts:
      - BridgeTxPool.Get(txHash_A) → returns the real anchoring tx
      - WriteReceiptFromParentChain(blockHash, forgedReceipt)
      - WriteAnchoredBlockNumber(blockNum)   ← DB permanently corrupted
      - BridgeTxPool.RemoveTx(tx)           ← tx silently dropped

6. Assert: chainDB.ReadAnchoredBlockNumber() == blockNum
           even though no parent-chain tx was ever mined.
```
