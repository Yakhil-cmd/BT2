### Title
Webhook signature is validated against the organization named in `repository.owner.login`, but every event handler resolves its target Stack from the unvalidated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` picks which GitHub App/`webhook_secret` to verify a delivery against using `repository.owner.login` (or `organization.login`) taken from the raw JSON body, but the HMAC signature only proves the *entire byte blob* was signed with *that* secret - it says nothing about internal consistency between `repository.owner.login` and `repository.full_name`. Every webhook handler (`Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) resolves the repository/Stack to act on using `repository.full_name`, a sibling field in the same payload that is never cross-checked against `repository.owner.login`. This is the same "field acted on but not covered by the binding" pattern as the `acceptedCurrency`/`offerCurrency` bug: the signature "authenticates" one field (owner login) while a *different* field (full_name) drives the actual write.

### Finding Description
`WebhooksController#verify_signature` selects the `GithubApp` instance (and therefore the HMAC secret) solely from `repository_owner`: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` just HMACs the raw request body against the secret configured for that organization: [2](#0-1) 

Once verified, the *entire* parsed body is dispatched unchanged to handlers: [3](#0-2) 

Every handler, however, looks up the Stack/Repository to act on via `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Handlers such as `PushHandler` use this to enqueue syncs against arbitrary stacks: [5](#0-4) 

and PR handlers independently re-derive the repository from `params.repository.full_name` for provisioning/archival actions: [6](#0-5) 

Because Shipit supports multi-organization configuration (each org configuring its own `app_id`/`installation_id`/`webhook_secret`, as documented in `secrets.development.example.yml`), an attacker who is the admin of "org A" — a legitimate, independently-onboarded GitHub organization that installed its own Shipit GitHub App and therefore knows/controls its own `webhook_secret` — can:

1. Craft an arbitrary JSON payload with `repository.owner.login = "org-a"` (so `repository_owner` resolves to their own org and `Shipit.github(organization: "org-a")` returns the app/secret they legitimately possess).
2. Set `repository.full_name = "victim-org/victim-repo"` in the same payload (an entirely different, unaffiliated Stack tracked by this Shipit instance).
3. Sign the raw body with their own known `webhook_secret` for `org-a` and POST it to the shared, unauthenticated `/github/webhooks` endpoint.

`verify_signature` passes (secret matches), but `PushHandler`/`StatusHandler`/`CheckSuiteHandler`/PR handlers all act on `victim-org/victim-repo` because they never re-check that `repository.full_name`'s owner matches the org that authenticated the request.

### Impact Explanation
This lets an attacker who controls only their own (unrelated) GitHub organization/app installation forge webhook deliveries that are processed as if they came from GitHub for a completely different, victim-owned repository tracked by the same Shipit instance:
- Forge `push` events to trigger `GithubSyncJob`/`sync_github` against the victim stack, injecting attacker-controlled commit SHAs into the victim's commit history via the sync path.
- Forge `status`/`check_suite` events to mark arbitrary commits on the victim stack as passing CI (`deployable?`), enabling an unauthorized deploy to succeed against safety gates.
- Forge `pull_request` events to trigger review-stack provisioning/archival actions against a victim repository.

Marking commits deployable on a stack that isn't yours and driving unauthorized syncs directly maps to "unauthorized deploy/rollback" and "cross-repository writes" territory called out as valid High/Critical impacts, achieved purely by crossing an organizational trust boundary via an unauthenticated webhook endpoint (no Shipit session, ApiClient token, or repository write access to the victim repo required).

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to run/administer their own GitHub organization/App that is *also* configured as a trusted org on the target Shipit instance (a realistic scenario for shared/internal multi-tenant Shipit deployments where different teams/orgs self-register their GitHub Apps), but requires no compromise of the victim org, no Shipit credentials, and no interaction with GitHub's real webhook delivery for the victim repo — only a single crafted, self-signed HTTP POST.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), validate that `repository.owner.login` (the field used to select the signing secret) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the request (e.g. `head(422)`) on mismatch. Alternatively, derive the repository/organization used by handlers from the same validated field (`repository.owner.login` + repo name) rather than trusting `full_name` independently.

### Proof of Concept
1. Attacker legitimately owns/admins GitHub org `org-a`, which has installed the Shipit GitHub App with a webhook secret `S_A` known to the attacker (they configured it).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(S_A, body)` and sends:
```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
<body above>
```
4. `WebhooksController#repository_owner` returns `"org-a"`; `Shipit.github(organization: "org-a")` returns the attacker-known app, and `verify_webhook_signature` succeeds — see `app/controllers/shipit/webhooks_controller.rb:24-49` and `lib/shipit/github_app.rb:76-83`.
5. `PushHandler#process` calls `stacks` which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (see `app/models/shipit/webhooks/handlers/handler.rb:32-38` and `app/models/shipit/webhooks/handlers/push_handler.rb`), enqueuing `GithubSyncJob`/`sync_github` against the victim's Stack, despite the attacker having no relationship to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
