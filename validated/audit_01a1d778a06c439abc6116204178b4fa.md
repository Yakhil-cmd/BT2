### Title
Webhook signature verification keys off a different field than the one used to select the affected repository/stack, allowing cross-organization webhook forgery in multi-app deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-GitHub-App deployments, `WebhooksController#verify_signature` selects *which organization's webhook secret* to validate a payload against using a fallback field (`organization.login`) that is decoupled from the field actually used by the event handlers to decide *which repository/stack the event is applied to* (`repository.full_name`). This breaks the binding "organization that authenticated == repository that is written," analogous to the referenced report's core issue where two independently-derived quantities (creator payment vs. `buyToken` minimum) are assumed—but not enforced—to be consistent, causing a trust-boundary failure when the values diverge.

### Finding Description
`Shipit.github_app_config`/`Shipit.github` support hosting multiple GitHub Apps, one per organization [1](#0-0) . Each org has its own optional `webhook_secret` [2](#0-1) , and `verify_webhook_signature` **skips verification entirely when a secret is not configured**: `return true unless webhook_secret` [3](#0-2) . The docs explicitly mark `webhook_secret` as optional for every configured org [4](#0-3) .

The controller picks the org used for verification like this:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 
and uses it to fetch the app/secret to verify with: `Shipit.github(organization: repository_owner)` [6](#0-5) .

Once verification passes, the actual event handlers determine the target stack(s) from a **completely different field**, `repository.full_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 

Because `repository_owner` falls back to the top-level `organization.login` node when `repository.owner.login` is absent, and because the signature check is scoped per-org (not per-repository), a payload can be crafted where:
- `organization.login` = an org configured in Shipit whose webhook secret is unset (satisfying `return true unless webhook_secret`), or whose secret the attacker otherwise possesses, and
- `repository.full_name` = any *other* repository/organization already registered as a Shipit stack.

The signature check passes (because it's keyed to the attacker-controlled/no-secret org), but `PushHandler`, `MembershipHandler`, `StatusHandler`, and `CheckSuiteHandler` all act on the unrelated `repository.full_name` value [8](#0-7) [9](#0-8) . This is the exact analog class called out in the rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who controls (or has installed) any single low-privilege GitHub App/organization entry that Shipit is configured with—one where the operator left `webhook_secret` blank, which the docs treat as a normal supported configuration—can forge webhook deliveries claiming to originate from that org while targeting `repository.full_name` belonging to a *different, privileged* stack managed by the same Shipit instance. Depending on handler:
- `status` events let the attacker write arbitrary commit statuses onto commits of a victim stack (`StatusHandler`), which can influence CI-gated merge/deploy eligibility (`Commit#create_status_from_github!`).
- `push` events can trigger `sync_github` against a victim stack, forcing Shipit to re-fetch/interpret the victim's branch state.
- `membership` events create/modify `Team`/`User` records tied to whatever `organization.login`/`team` is asserted, which can affect `Shipit.github_teams` authorization checks that gate access to the whole app [10](#0-9) .

This does not directly grant RCE, but it crosses a repository/organization authorization boundary and can corrupt commit-status-based deploy gating and team membership, both of which back critical authorization/deploy decisions elsewhere in the engine. This is scoped to multi-organization deployments (the `secrets.github` multi-app schema); single-org configurations are not affected because `Shipit.github` ignores the passed `organization:` argument when `github_default_organization` is nil [11](#0-10) .

### Likelihood Explanation
Requires: (1) the operator to run Shipit with the documented multi-organization GitHub App configuration, and (2) at least one configured org to have no `webhook_secret` set (explicitly documented as optional) or a leaked/weak secret for one org. Given the docs present this as a normal, supported setup, this is a plausible but operator-dependent (misconfiguration-driven) condition, similar to the original report's root cause being flagged as "owner misconfiguration... within allowed boundaries."

### Recommendation
Verify the webhook signature using the same repository-derived scope that handlers use to select the target stack, i.e., always compute the org from `repository.full_name`/`repository.owner.login`, never fall back to the separate `organization.login` field for signature key selection. Additionally, require `webhook_secret` to be non-blank for every configured GitHub App and reject requests otherwise, rather than defaulting to "verified" when absent.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema: org `low-trust-org` (webhook_secret left blank) and org `victim-org` (used by a real Shipit stack, e.g. stack for `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "organization": { "login": "low-trust-org" },
  "repository": { "full_name": "victim-org/victim-repo" }
}
```
(no `repository.owner.login` present, so `repository_owner` resolves to `low-trust-org`.)
3. `verify_signature` calls `Shipit.github(organization: "low-trust-org")`; since that org has no `webhook_secret`, `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header sent.
4. `StatusHandler#process` looks up `Commit.where(sha: ...)` for the sha, unrelated to `low-trust-org`, and writes a forged success status onto the victim commit—despite the attacker never possessing `victim-org`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
