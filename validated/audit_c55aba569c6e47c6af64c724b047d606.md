### Title
`Api::CCMenuController` bypasses stack-scoped `ApiClient` authorization, allowing cross-stack read of deploy state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` overrides `#stack` to resolve the target stack directly from `Stack.from_param!(params[:stack_id])` instead of using `Api::BaseController#stacks`, which restricts lookups to `current_api_client.stack_id` when the client is scoped to a single stack. This breaks the binding "stack authorized for a token == stack the token can read," analogous to the M-12 report's core bug class: a value (`ptRate`/decimals assumption) is trusted in one code path but not verified/consistent in another, causing the wrong "market"/scope to be used. Here, a per-stack-scoped `ApiClient` token has its authorization check reduced to a permission-name check (`read:stack`) without re-verifying that the requested stack matches the one the token is bound to.

### Finding Description
`Api::BaseController` defines the stack lookup that other API controllers rely on for correct scoping: [1](#0-0) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This is the correct binding: `ApiClient#stack_id` (the stack the token is authorized for) constrains which stacks `#from_param!` can resolve to. Other controllers such as `Api::StacksController` and `Api::DeploysController` rely on this inherited `#stack`/`#stacks` method (confirmed by the test `"an api client scoped to a stack will only see that one stack"`) [2](#0-1) .

`Api::CCMenuController`, however, overrides `#stack` and ignores the scoping entirely: [3](#0-2) 

```ruby
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end
  ...
```

The authorization check performed via `require_permission :read, :stack` only verifies that the `ApiClient`'s `permissions` array contains `"read:stack"` — a global grant name, not a stack-specific one: [4](#0-3) 

```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
```

The narrowing to a specific stack is supposed to happen via `ApiClient#stack_id` and `BaseController#stacks`, exactly as done for the standard `Api::StacksController`. `CCMenuController` bypasses that narrowing by calling `Stack.from_param!` unscoped, so any stack ID passed in the URL is resolved — not just the one the token is bound to.

This is a direct analog to the reported bug class: the "authorized" binding (client → stack_id) is verified in one location (`BaseController#stacks`) but not consistently enforced at the point where data is actually acted upon/rendered (`CCMenuController#stack`), similar to how `_getPTRate` assumed a fixed format that didn't hold for all markets.

### Impact Explanation
An `ApiClient` token created via `CCMenuUrlController#fetch` — which is specifically designed to be handed out embedded in a CCMenu URL (e.g. pasted into third-party CI dashboard tools) and scoped only to `read:stack` for one particular stack — can be reused to read deploy/build status (`lastBuildStatus`, `activity`, `webUrl`, lock status, etc.) of **any other stack** in the Shipit instance, including private/internal stacks the token holder was never granted access to: [5](#0-4) 

This is an unauthorized cross-stack read of stack/deploy state via a token whose intended authorization scope was a single stack — matching the "High: escalation into authorization... unauthenticated read of stack state" impact category, since the exposed CCMenu token effectively becomes a global `read:stack` credential rather than a single-stack credential.

### Likelihood Explanation
Likelihood is high for any deployment using the CCMenu integration feature: any user with access to one stack's CCMenu URL/token (a credential explicitly designed to be shared with external tooling and is not treated as highly sensitive) can trivially change the `stack_id` in the request path to enumerate and read the build/deploy status of arbitrary other stacks, without needing any additional privileges, a full Shipit session, or any other credential. The only requirement is possessing one legitimately-scoped CCMenu token, which by design is meant to be embedded in a URL.

### Recommendation
In `Api::CCMenuController`, remove the overridden `#stack` method and use the inherited `Api::BaseController#stack`/`#stacks` methods so that stack resolution is constrained by `current_api_client.stack_id` exactly like every other API controller. If the override exists because `CCMenuController` needs a different lookup strategy, it must still intersect with `stacks` (the client-scoped relation) rather than calling `Stack.from_param!` unscoped.

### Proof of Concept
1. Create/obtain a stack-scoped CCMenu token for `stack-a` via the normal flow (`CCMenuUrlController#fetch`, which creates an `ApiClient` with `permissions: %w[read:stack]` and no explicit `stack_id` restriction unless one is set) — note the token embeds `read:stack` only, not a hard binding at the authorization layer beyond `ApiClient#stack_id`.
2. As an attacker who obtained this token (e.g., found in a public CI dashboard config), issue:
   `GET /api/stacks/<other-org>/<other-repo>/<other-env>/ccmenu.xml?token=<stolen-token>`
3. Observe that `Api::CCMenuController#stack` resolves `<other-org>/<other-repo>/<other-env>` via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction enforced in `Api::BaseController#stacks`, and the XML response discloses that stack's build/lock/deploy status.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
