### Title
Webhook signature is verified against `repository.owner.login` while stack mutation targets `repository.full_name`, allowing cross-tenant `GithubSyncJob` injection - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC using `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')` (or `organization.login`). `Handler#stacks` (used by every handler, including `PushHandler`) resolves the target stacks using a different field from the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Nothing forces these two fields to refer to the same repository/org, so a forged request that authenticates as one org can name an arbitrary victim repository's `full_name` to drive `sync_github` on that victim's stack.

### Finding Description
The broken binding is:

`verifying_org (payload.repository.owner.login, used in Shipit.github(organization: repository_owner))` == `owning_org(payload.repository.full_name, used by Repository.from_github_repo_name in Handler#stacks)`

This is never enforced.

- `verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and uses it purely to select which `GitHubApp`/secret to HMAC-verify the raw body against: [1](#0-0) [2](#0-1) 
- Once verified, the raw parsed JSON (the same attacker-controlled body) is handed unchanged to the handler: [3](#0-2) 
- `Handler#stacks` resolves the target repository/stacks from a *different* key of that same body, `repository.full_name`, with no cross-check against `repository_owner`: [4](#0-3) 
- `PushHandler#process` then calls `sync_github(expected_head_sha: params.after)` on every non-archived stack of the resolved repository matching the attacker-supplied branch: [5](#0-4) 

Exploit flow: attacker crafts a raw HTTP POST to `/webhooks` with `X-Github-Event: push` and a JSON body where `repository.owner.login` = `"attacker-org"` (an org whose webhook secret the attacker can produce a valid signature for, per the question's granted precondition) but `repository.full_name` = `"victim-org/victim-repo"`, `ref` = `"refs/heads/master"`, and `after` = an attacker-chosen sha. `verify_signature` validates the HMAC against `attacker-org`'s secret and passes. `PushHandler#process` then resolves stacks via `victim-org/victim-repo` and enqueues `GithubSyncJob` with the attacker-chosen `expected_head_sha` against the victim's production stack — a payload authenticated for one repository mutates another repository's stack.

None of the existing guards catch this: `ExplicitParameters` only validates types/presence of `ref`/`after`, not cross-consistency with the owner used for signing; `drop_unhandled_event` only checks the event type exists; `verify_signature` never re-reads `repository.full_name`; and `Repository.from_github_repo_name` performs no comparison to `repository_owner`.

### Impact Explanation
A verified webhook body for one tenant/org can drive `GithubSyncJob` (and by extension `sync_github`) against an arbitrary victim stack owned by a different tenant, injecting an attacker-chosen `expected_head_sha`. This is a cross-tenant write: a request that only proved control of `attacker-org`'s webhook secret results in a job enqueued and state mutated against `victim-org`'s stack — a payload for one repository mutating another's stack, matching the Critical impact category. It is repeatable against any victim repository/branch combination the attacker can name in the JSON body, for every push event received by the shared `/webhooks` endpoint.

### Likelihood Explanation
The attacker must be able to produce a valid signature for *some* org configured in Shipit (their own, per the question's stated precondition) and know the victim's `repository.full_name` and tracked branch (both public/discoverable information for any Shipit-tracked repo). No Shipit session, API token, or victim secret is required. The main practical constraint is obtaining a valid signature for any org at all — if that org's `webhook_secret` is unset, `verify_webhook_signature` returns `true` unconditionally [6](#0-5) , making this trivial in that configuration; if the org's secret is genuinely private to Shipit operators, the attacker's ability to satisfy this precondition depends on deployment specifics not fully verifiable from this engine's code alone.

### Recommendation
After signature verification succeeds, `Handler#stacks` (or `WebhooksController#create`) must verify that the repository named in `payload.repository.full_name` actually belongs to the same organization/owner (`repository_owner`) that was cryptographically verified, rejecting the request (e.g., `head(422)`) if they diverge, before resolving stacks or enqueueing any sync job.

### Proof of Concept
In a minitest under `test/controllers/webhooks_controller_test.rb` (not part of this analysis's deliverable but describing the required assertions):
1. Configure two orgs in `Shipit.github_apps` test config: `attacker-org` (with a known `webhook_secret`) and `victim-org`.
2. Create a `Stack` for `victim-org/victim-repo` tracking branch `master`, `archived: false`.
3. Build a push payload: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/master"`, `after = "<attacker-chosen-sha>"`.
4. Sign the raw body with `attacker-org`'s secret and POST to `/webhooks` with `X-Github-Event: push`.
5. Assert response is `200 OK` (signature accepted for `attacker-org`) AND assert `GithubSyncJob` is enqueued with `stack_id` equal to the victim stack's id and `expected_head_sha` equal to the attacker-chosen sha — demonstrating that verification under `attacker-org` == authorization to mutate `victim-org`'s stack, which should not hold.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
