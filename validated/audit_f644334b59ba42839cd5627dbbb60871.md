### Title
Webhook signature verification keys off `repository.owner.login` while event handlers dispatch on `repository.full_name` — cross-organization webhook forgery in multi-tenant deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit configuration (multiple GitHub Apps, one per org, each with its own `webhook_secret`), `WebhooksController#verify_signature` selects which HMAC secret to verify the payload against using `repository.owner.login` (or `organization.login`) taken from the *same untrusted, unsigned-at-selection-time* JSON body, then verifies the HMAC over the whole raw body with that secret. Once the signature check passes, every event handler (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, etc.) determines *which repository/stack the event actually acts on* using `repository.full_name` — a different field of the same payload — via `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`. Nothing enforces that `repository.owner.login` and the owner portion of `repository.full_name` refer to the same organization. An attacker who legitimately controls one org's GitHub App webhook secret in a shared Shipit install can therefore forge a payload that authenticates as "their" org but whose `full_name` targets a stack belonging to a *different* org's repository, causing Shipit to act on that other repository's stacks (trigger syncs, inject fake CI statuses, etc.) without ever possessing that org's secret.

### Finding Description
The equality that should hold, and is broken, is:

`organization used to select/verify the webhook secret (repository.owner.login) == organization that the acted-upon repository/stack belongs to (owner portion of repository.full_name)`

- `verify_signature` resolves the app/secret purely from the payload's `repository.owner.login`: [1](#0-0) [2](#0-1) 

- The HMAC is verified with `Shipit.github(organization: repository_owner)`'s configured `webhook_secret`, using generic sha1 HMAC comparison over the raw body: [3](#0-2) 

- Once verification passes, `create` dispatches the *entire params hash* to registered handlers, without re-checking which org it came from: [4](#0-3) 

- Handlers resolve the affected `Repository`/`Stack` set using a completely different field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

- `PushHandler` then triggers `sync_github` on any matching, non-archived stack with the attacker-chosen branch, and `StatusHandler` creates a commit status on any commit matching the attacker-chosen `sha`: [6](#0-5) [7](#0-6) 

Multi-org configuration is an explicitly supported deployment mode with distinct secrets per organization: [8](#0-7) [9](#0-8) 

Before/after the attack:
- **Before**: an event delivered from GitHub for `OrgA/repo` is signed with `OrgA`'s `webhook_secret`; `repository.owner.login == OrgA` and `repository.full_name == "OrgA/repo"` are consistent, so `verify_signature` and the handler's `repository_name` agree.
- **After**: an attacker who administers `OrgB`'s GitHub App (and thus knows `OrgB`'s `webhook_secret`) crafts a raw JSON body with `repository.owner.login = "OrgB"` (so `verify_signature` picks `OrgB`'s secret, which they can correctly HMAC-sign) but `repository.full_name = "OrgA/repo"` (so the handler acts on `OrgA`'s stack). The signature check passes because it only validates that the bytes were signed with `OrgB`'s secret — it says nothing about which repository the payload claims to describe internally.

### Impact Explanation
This breaks the deployment-trust binding between "the organization that authenticated the webhook" and "the repository/stack the engine actually writes to," directly matching the allowed analog class ("an organization that authenticated versus the repository that is written"). Concretely, in a multi-tenant Shipit instance, an attacker who is a legitimate admin of one onboarded organization's GitHub App can:
- Force `Stack#sync_github` on another organization's stack with an attacker-chosen `expected_head_sha`/branch (`PushHandler`).
- Inject fabricated commit statuses (`state`, `context`, `target_url`) onto commits belonging to another organization's stack (`StatusHandler`), which can be used to satisfy `ci.require` checks and enable an unauthorized deploy of that stack.

This crosses the "cross-repository writes" / "unauthorized deploy" bar for Critical/High impact, since the write (sync, fabricated CI status enabling deploy safety bypass) occurs on a repository/stack the attacker's own credentials were never meant to authorize.

### Likelihood Explanation
Requires the attacker to hold a `webhook_secret` for at least one organization configured on a shared, multi-org Shipit instance — a legitimate, unprivileged-relative-to-other-tenants position (they are simply an admin of their own GitHub App, not of Shipit or of the targeted org). No `ApiClient` token, no Shipit session, no GitHub App private key, and no access to the *target* org's secret are needed. The only barrier is that GitHub itself would never naturally produce a payload with mismatched `owner.login`/`full_name`, but nothing in the engine enforces this — the attacker crafts and signs the raw HTTP body directly (this is a raw HMAC-signed HTTP POST to `/github/webhooks`, not something proxied through the real GitHub webhook delivery pipeline that would keep the fields consistent). Likelihood is moderate and specific to multi-organization deployments (single-org deployments do not create the org-vs-full_name mismatch since there is only one secret to check against).

### Recommendation
- Derive the organization used for `Repository`/`Stack` lookup and the organization used for signature verification from the same field. Either verify the signature using the owner parsed out of `repository.full_name` (not `repository.owner.login`/`organization.login`), or after selecting the app/secret from `repository.owner.login`, assert that `repository.full_name` starts with `"#{repository.owner.login}/"` before dispatching to handlers.
- Reject webhooks whose `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps for `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an attacker who is the admin of `OrgB`'s GitHub App (knows `OrgB`'s `webhook_secret`), craft a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "OrgB" },
       "full_name": "OrgA/target-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgB_webhook_secret, raw_body)>` and POST to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgB")`, whose `verify_webhook_signature` succeeds because the attacker legitimately knows `OrgB`'s secret [3](#0-2) .
5. `Webhooks.for_event('push')` dispatches to `PushHandler`, whose `repository_name` resolves to `"OrgA/target-repo"` via `payload.dig('repository', 'full_name')` [5](#0-4) , and `sync_github(expected_head_sha: ...)` is invoked on `OrgA`'s stack — despite the request only ever being signed with `OrgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
