### Title
Unhandled synchronous `throw` inside asynchronous oscript evaluation crashes the node process - (File: formula/evaluation.js)

### Summary
CVE-2021-46322 is a crash (SEGV) in Duktape's `duk_push_tval` triggered by a malformed/unexpected internal value reaching a code path that has no graceful error handling, only a hard abort. The `ocore` oscript/AA formula evaluator (`formula/evaluation.js`) contains an analogous class of bug: several branches of the recursive `evaluate()` interpreter use a bare `throw Error(...)` for "should never happen" conditions instead of routing through `setFatalError()`/`cb()`, the interpreter's normal error-handling convention. Because `evaluate()` is heavily asynchronous (it yields via `setImmediate` every 100 recursive calls, see the throttle at [1](#0-0) ), any `throw` that fires after such a yield executes on a fresh call stack with no enclosing `try/catch`, producing an uncaught exception that crashes the whole Node.js process rather than failing just the one formula.

### Finding Description
Throughout `evaluate()`, most invalid states are handled safely via `setFatalError(...)`, which propagates the failure through the callback chain, e.g. [2](#0-1) . However, a number of branches instead use a raw `throw`, for example the `parse_date` handler: [3](#0-2) 

and the catch-all `default` case of the switch statement: [4](#0-3) 

as well as the `replace()` walker in `aa_composer.js` used to substitute formulas inside an AA definition: [5](#0-4) 

All callers of `formulaParser.evaluate()` — `aa_composer.js`'s `evaluateAA`/`replace`/`executeStateUpdateFormula` [6](#0-5) [7](#0-6) , and `definition.js`'s authentifier `formula` case [8](#0-7)  — pass a plain callback and never wrap the call in `try/catch`, because the interpreter is expected to always report errors asynchronously via the callback rather than throw. There is no `process.on('uncaughtException', ...)` handler in the AA/validation code paths; the only such handler in the repo is in `network.js` for socket handling, unrelated to formula evaluation.

Because `evaluate()` resumes via `setImmediate` after every 100 recursive steps, by the time a rarely-reachable `throw` fires (e.g. from a deeply nested or looping formula that reaches the `parse_date`/`default` branch after a yield boundary), it is no longer inside the original synchronous call stack of `handleTrigger`/`validateAuthentifiers`. The exception becomes an uncaught exception at the event-loop level, which by default terminates the Node.js process — the functional analog of the Duktape SEGV: attacker-controlled interpreter input reaching a hard-abort code path instead of a recoverable error path.

### Impact Explanation
Any account can post a unit that triggers an Autonomous Agent, or an AA author can define an AA whose formula construction leads through one of these `throw` paths (e.g. by crafting an oscript AST/value combination that reaches the `default: throw Error('unrecognized op '+op)` or the `replace()`'s `throw Error('unknown type of value...')` after a `setImmediate` yield). If reached, this crashes the full-node process evaluating the trigger. Since AA trigger processing happens on every node that keeps up with the DAG, a crafted unit/trigger could crash multiple nodes simultaneously, causing the network to become unable to process/confirm new AA-triggered units — a network-availability impact matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Reaching these specific `throw` statements requires the attacker to construct an oscript formula/AST or a definition-replacement object whose value falls outside all handled type-checks at exactly one of these locations, which is non-trivial but not proven impossible since the surrounding validation (`formula/validation.js`) is a separate parallel implementation of the same grammar and could plausibly miss a case that the evaluator's exhaustive `switch`/type checks reject only via `throw`. The `parse_date` throw could not be conclusively confirmed to be reachable through the current regex/`Date` construction, so likelihood is assessed as low-to-moderate without a demonstrated triggering formula.

### Recommendation
Replace every bare `throw Error(...)` inside `evaluate()` (and analogous walkers like `replace()` in `aa_composer.js`) with the standard `setFatalError(...)` / `cb(...)` error-reporting convention so that malformed-but-attacker-reachable states fail the single formula/trigger instead of throwing past all yield boundaries. Additionally, add a top-level `try/catch` around the synchronous portions of `formulaParser.evaluate()`/`callFunction()` and a process-level safety net (e.g., converting any escaping exception during AA/formula evaluation into a bounced trigger) so a single malformed formula can never crash the whole node process.

### Proof of Concept
Not fully demonstrated: I could not construct within static analysis a concrete oscript formula input guaranteed to (a) pass `formula/validation.js`'s pre-checks and (b) hit one of the identified `throw` statements after a `setImmediate` yield boundary (i.e., after the 100th recursive `evaluate` call) so that the exception occurs outside any synchronous stack. This would need to be confirmed by fuzzing formulas that are deeply nested/looping (to cross the `count % 100 === 0` yield point) combined with edge-case values feeding the `parse_date`, `default` switch case, or `replace()` unknown-value path.
