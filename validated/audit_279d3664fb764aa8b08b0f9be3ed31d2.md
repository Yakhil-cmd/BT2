### Title
`isRunning` Emergency-Stop Flag Not Enforced in `handle*Transfer` Functions, Allowing Continued Asset Drain After Bridge Is Stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge exposes an `isRunning` state variable and a privileged `setRunningStatus(false)` / `start(false)` function intended to halt all bridge operations in an emergency. However, `isRunning` is only checked in the **outbound request** path (`_requestKLAYTransfer`, `_requestERC20Transfer`, `_requestERC721Transfer`). The three **inbound handle** functions — `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — contain no `isRunning` guard at all. Bridge operators can therefore continue to execute handle transfers and drain KLAY and ERC-20/ERC-721 tokens from the bridge contract even after the owner has activated the emergency stop.

---

### Finding Description

`BridgeTransfer.sol` declares the stop flag and the setter:

```solidity
bool public isRunning = true;

function setRunningStatus(bool _status) public onlyOwner {
    isRunning = _status;
    emit RunningStatusChanged(_status);
}
``` [1](#0-0) 

The outbound request helpers correctly enforce the flag:

```solidity
// BridgeTransferKLAY.sol _requestKLAYTransfer
require(isRunning, "stopped bridge");

// BridgeTransferERC20.sol _requestERC20Transfer
require(isRunning, "stopped bridge");

// BridgeTransferERC721.sol _requestERC721Transfer
require(isRunning, "stopped bridge");
``` [2](#0-1) [3](#0-2) [4](#0-3) 

The inbound handle functions carry **no such check**:

```solidity
// BridgeTransferKLAY.sol
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    // ← no require(isRunning) here
    ...
    (bool ok, ) = _to.call.value(_value)("");
    require(ok, "handleKLAYTransfer: transfer failed");
}
``` [5](#0-4) 

```solidity
// BridgeTransferERC20.sol
function handleERC20Transfer(...) public onlyOperators {
    _lowerHandleNonceCheck(_requestedNonce);
    if (!_voteValueTransfer(_requestedNonce)) { return; }
    // ← no require(isRunning) here
    ...
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [6](#0-5) 

```solidity
// BridgeTransferERC721.sol

    _lowerHandleNonceCheck(_requestedNonce);

The Go-layer `BridgeInfo` reads `isRunning` from the contract into a local field but uses it only for informational purposes; it unconditionally calls `HandleKLAYTransfer` / `HandleERC20Transfer` / `HandleERC721Transfer` regardless of that field: [8](#0-7) [9](#0-8) [10](#0-9) 

---

### Impact Explanation

When the bridge owner calls `setRunningStatus(false)` to halt the bridge (e.g., because the counterpart chain bridge has been exploited and is emitting fraudulent `RequestValueTransfer` events), bridge operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer`. Each successful call transfers KLAY or tokens from the bridge contract to an arbitrary `_to` address. The emergency stop therefore provides only half-protection: it blocks new user deposits but does not stop the outflow of already-held assets. The corrupted protected state is the KAIA/token balance of the bridge contract, which can be drained to zero despite `isRunning == false`.

---

### Likelihood Explanation

The scenario is realistic: a service-chain bridge operator node runs an automated relay loop. If the parent-chain bridge is compromised and emits fraudulent `RequestValueTransfer` events, the operator's relay will automatically call `handleKLAYTransfer` on the child-chain bridge. The owner's only recourse — `setRunningStatus(false)` — does not stop these calls. The operator set is small and semi-trusted, but the attack does not require operator collusion: a single compromised operator node (or the automated relay acting on fraudulent events from the counterpart chain) is sufficient to trigger the drain.

---

### Recommendation

Add an `isRunning` guard to all three handle functions, mirroring the pattern already used in the request functions:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    require(isRunning, "stopped bridge");   // ← add this
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

function handleERC20Transfer(...) public onlyOperators {
    require(isRunning, "stopped bridge");   // ← add this
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

function handleERC721Transfer(...) public onlyOperators {
    require(isRunning, "stopped bridge");   // ← add this
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}
```

This makes `setRunningStatus(false)` a true bilateral emergency stop that halts both inbound and outbound asset movement.

---

### Proof of Concept

1. The bridge owner detects an exploit on the counterpart chain and calls `bridge.setRunningStatus(false)` → `isRunning` is now `false`.
2. A bridge operator (or the automated relay acting on fraudulent events) calls `handleKLAYTransfer(fakeTxHash, attacker, attacker, drainAmount, nonce, blockNum, "")`.
3. `handleKLAYTransfer` passes `onlyOperators`, skips the (absent) `isRunning` check, passes `_lowerHandleNonceCheck`, reaches `_to.call.value(_value)("")`, and transfers `drainAmount` KLAY to the attacker.
4. Steps 2–3 repeat for every valid nonce until the bridge balance is zero, despite `isRunning == false`.

The exact corrupted value is the KAIA/token balance of the bridge contract, reduced from its pre-stop amount to zero by operator-submitted handle transactions that the `isRunning` flag was intended to block.
