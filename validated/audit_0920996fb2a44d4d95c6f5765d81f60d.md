### Title
Webhook signature verification is keyed on `repository.owner.login`/`organization.login` while every handler resolves the target stack from `repository.full_name`, letting a payload signed for one GitHub App act on any other configured organization's repositories - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to validate the payload against using `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  and passed into `Shipit.github(organization: repository_owner)` before calling `verify_webhook_signature` [2](#0-1) . Every registered handler, however, resolves the repository/stack to act on using a *different* field of the same payload: `payload.dig('repository', 'full_name')` in the base `Handler#repository_name` [3](#0-2)  or `params.repository.full_name` in the pull-request handlers [4](#0-3) . Nothing ties `repository.owner.login` to `repository.full_name`'s owner segment; a raw JSON payload is entirely attacker-controlled, so these two fields can be made inconsistent.

### Finding Description
The security-relevant equality the engine implicitly relies on is:

`organization whose GithubApp/webhook_secret authenticated the request == owner of the repository the handler subsequently mutates`

Before the fix this equality is never enforced. Concretely:
- `verify_signature` looks up the `GithubApp` config via `repository_owner` (from `repository.owner.login`, or `organization.login`) and checks the raw HMAC signature against that org's `webhook_secret` [5](#0-4) .
- `GithubApp#verify_webhook_signature` explicitly returns `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [6](#0-5) . The setup docs mark `webhook_secret` as optional [7](#0-6) , and the packaged multi-org config template ships with it blank/nil (`webhook_secret: # nil`) [8](#0-7) .
- Once `verify_signature` passes (either because an org has no secret configured, or the attacker knows one org's secret), the `create` action dispatches the full raw payload to every handler for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [9](#0-8) .
- Handlers independently derive the acted-upon repository/stack from `repository.full_name` via `Repository.from_github_repo_name`, which just splits on `/` with no relation back to the `owner.login` field used for signing [10](#0-9) , or via `Handler#stacks` [11](#0-10) .

So an attacker who can produce a validly-signed webhook for **any** configured GitHub org (either because that org has no `webhook_secret` set, or its secret leaked) can set `repository.owner.login` to that (weak) org while setting `repository.full_name` to `victim-org/victim-repo`, and every handler will act on the victim stack as if GitHub itself sent the event.

Concrete handler impacts once the signature check is bypassed this way:
- `PushHandler#process` runs `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` for the victim stack [12](#0-11) , forcing a sync toward an attacker-chosen `after` SHA.
- `StatusHandler#process` writes forged CI statuses onto real commits by SHA alone (`Commit.where(sha: params.sha)`), with no repository/stack ownership check at all [13](#0-12) , which can flip a commit to "success" and unblock deploy gating that depends on CI status.
- `CheckSuiteHandler#process` similarly schedules check-run refreshes for a victim stack's commits keyed only by branch/SHA [14](#0-13) .
- Pull-request handlers (`ClosedHandler`, `ReopenedHandler`, labeled/unlabeled handlers) archive/unarchive review stacks belonging to the victim repository based purely on `params.repository.full_name` [15](#0-14) .

This is a direct analog of the `remove_gauge` bug class: the report's `_remove_gauge_weight` used `gauge_types_[_gauge]` (a value that had already been reset to 0 by the time it needed it) — a stale/mismatched key drives a security-relevant calculation. Here, the "key" used to select the trust boundary (`repository.owner.login`) is disjoint from the "key" used to perform the privileged action (`repository.full_name`'s owner), and the code never re-derives or cross-checks one from the other.

### Impact Explanation
This crosses exactly the boundary called out in the rules: "an organization that authenticated versus the repository that is written." An unprivileged external attacker (no Shipit session, no `ApiClient` token, no repository write access) who can produce one validly-signed (or unsigned-but-accepted, for orgs without `webhook_secret`) webhook can forge deploy-relevant state — fake CI statuses, forced re-syncs, and review-stack archival/unarchival — for a repository/organization that is *not* the one whose credentials were used to authenticate the request. Forged CI/status data can unblock or influence automated deploys, which maps to High/Critical impact ("escalation... unauthenticated... task streams", "unauthorized deploy") under the stated impact classes, particularly via the `StatusHandler` write path which has essentially no authorization boundary beyond the top-level signature check.

### Likelihood Explanation
Likelihood is high in any multi-org Shipit deployment: the documented and templated configuration explicitly supports (and ships examples with) organizations that have no `webhook_secret` configured, since it's marked optional [7](#0-6) [8](#0-7) . Any such org lets `verify_webhook_signature` short-circuit to `true` for arbitrary attacker payloads [16](#0-15) . The webhook endpoint is public (it's the GitHub webhook receiver), requires no authentication of its own, and the payload's `repository.owner.login`/`organization.login` versus `repository.full_name` fields are fully attacker-controlled JSON body content, not covered by any signature scoping.

### Recommendation
- After signature verification passes for a given `repository_owner`, re-validate that the payload's `repository.full_name` owner segment matches `repository_owner` before dispatching to handlers, rejecting mismatches with `422`.
- Alternatively/additionally, have handlers resolve the repository/stack and then assert its `owner` equals the organization whose `GithubApp` verified the signature, rather than trusting `full_name` unconditionally.
- Require `webhook_secret` to be present for every configured organization (fail startup/registration if missing) rather than silently treating it as "no verification needed."

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `weak-org` (no `webhook_secret` set) and `victim-org` (properly secured, hosting a real Shipit stack `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no/garbage `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<real sha of a commit on victim-org/victim-repo>",
  "state": "success",
  "context": "ci/forced"
}
```
3. `verify_signature` computes `repository_owner = "weak-org"`, looks up `Shipit.github(organization: "weak-org")`, and `verify_webhook_signature` returns `true` because `weak-org` has no `webhook_secret` [16](#0-15) .
4. `create` dispatches to `StatusHandler`, which writes a forged "success" status onto the real `victim-org` commit purely by SHA match [13](#0-12) , with no check that `weak-org` has any relationship to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
