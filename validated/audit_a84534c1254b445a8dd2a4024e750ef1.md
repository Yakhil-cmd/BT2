### Title
Extension binary install skips integrity/checksum verification of downloaded release asset - (File: pkg/cmd/extension/manager.go)

### Summary
The reported bug class is a missing invariant/integrity check after a computed/downloaded artifact is produced, allowing an unverified value to be trusted and used. In the `gh extension install` flow, the CLI downloads a binary asset from an attacker-influenced GitHub repository release and installs it without ever validating its content against any expected digest, in contrast to the sibling Copilot CLI download path in the same codebase which explicitly fetches and checks a `SHA256SUMS.txt` checksum before trusting the downloaded artifact.

### Finding Description
`Manager.installBin` in `pkg/cmd/extension/manager.go` resolves a release asset for the current platform and downloads it with `downloadAsset`, then immediately writes a manifest and completes installation: [1](#0-0) 

`downloadAsset` (in `pkg/cmd/extension/http.go`) performs a plain HTTP GET and streams the response body directly to disk with no digest computation or comparison step at all: [2](#0-1) 

The only post-download integrity-adjacent step is a macOS-only `codesignBinary` call, and only for the ARM64 fallback-to-amd64 case — it is not a checksum/digest verification and does not run for the common non-ARM-fallback path: [3](#0-2) 

By contrast, the Copilot CLI installer in the same repository — `pkg/cmd/copilot/copilot.go` — explicitly fetches an expected checksum from `SHA256SUMS.txt` and is designed to validate downloaded archive content before use: [4](#0-3) 

This demonstrates the codebase's own established pattern of asserting an invariant ("the downloaded bytes must match a known-good digest") before trusting downloaded, execution-bound content — a pattern that is absent from the binary-extension install path. Just as the Aftermath Finance report showed that omitting the `new_invariant >= old_invariant` assertion let the Newton method silently accept an invalid state, omitting a digest check here lets `gh extension install` silently accept and later execute whatever bytes are returned for the release asset URL.

### Impact Explanation
`gh extension install owner/gh-extension` resolves a binary from the target repository's latest (or pinned) GitHub Release and executes it on subsequent `gh <ext>` invocations. Since there is no checksum/digest verification tying the downloaded bytes to an attested value (e.g., a signed manifest, attestation, or checksums file as used elsewhere in the codebase), any compromise of the release asset in transit or at rest (e.g., a malicious or compromised GHES/Enterprise instance, a compromised release asset without HTTPS pinning issues, or a race where the asset is swapped between resolution and download) results in unverified code being written to disk and later executed as a trusted extension binary — this is a full local code-execution primitive for the CLI user, driven entirely by an attacker-influenced remote release asset.

### Likelihood Explanation
`gh extension install <owner>/<repo>` is a normal, commonly documented user-invoked command (see `pkg/cmd/extension/command.go`), and the vulnerable code path (`installBin`) is the default path taken whenever a release contains a matching platform binary asset — no special configuration or privileged access is required. The attacker only needs to control (or man-in-the-middle, or otherwise influence) the content served for the resolved release asset URL of a repository the victim chooses to install from; the victim's normal `gh extension install` invocation does the rest with no user prompt to confirm asset integrity.

### Recommendation
Introduce an integrity check in `Manager.installBin` (and `downloadAsset`) analogous to the Copilot installer's checksum verification: fetch or derive an expected digest for the resolved release asset (e.g., from a companion `SHA256SUMS.txt`/checksums manifest, GitHub Attestations, or the release asset's `digest` field already modeled elsewhere in this codebase — see `ReleaseAsset.Digest` in `pkg/cmd/release/shared/fetch.go`), compute the digest of the downloaded bytes, and assert they match before writing the manifest / marking the extension installed. Fail closed (return an error) if no expected digest can be obtained or if it does not match, mirroring the assert-and-abort remediation pattern from the referenced report.

### Proof of Concept
Conceptual PoC (cannot be executed in this environment, but demonstrates the missing-invariant class):
1. Publish/control a GitHub repository release whose asset name matches the victim's platform naming convention (e.g., `gh-ext-linux-amd64`).
2. Victim runs `gh extension install owner/gh-ext`.
3. `isBinExtension` → `installBin` resolves the asset via `fetchLatestRelease`/`fetchReleaseFromTag` and calls `downloadAsset(m.client, safeurl.NewImmutableSafeURL(asset.APIURL), binPath)` [5](#0-4) .
4. `downloadAsset` writes the HTTP response body to `binPath` verbatim with no digest check [6](#0-5) .
5. The manifest is written and the extension is marked installed with no verification step ever having run [7](#0-6) , after which `gh owner-gh-ext` will execute the unverified binary on the victim's machine.

// downloadAsset downloads a single asset to the given file path.
func downloadAsset(httpClient *http.Client, assetURL safeurl.SafeURL, destPath string) (downloadErr error) {
	var req *http.Request
	if req, downloadErr = http.NewRequest("GET", assetURL.String(), nil); downloadErr != nil {
		return
	}

	req.Header.Set("Accept", "application/octet-stream")

	var resp *http.Response
	// TODO(api-client-rollout)
	// This has been deferred from moving to api.Client due to its custom Accept header and binary response streaming.
	if resp, downloadErr = httpClient.Do(req); downloadErr != nil {
		return
	}
	defer resp.Body.Close()

	if resp.StatusCode > 299 {
		downloadErr = api.HandleHTTPError(resp)
		return
	}

	var f *os.File
	if f, downloadErr = os.OpenFile(destPath, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, 0755); downloadErr != nil {
		return
	}
	defer func() {
		if err := f.Close(); downloadErr == nil && err != nil {
			downloadErr = err
		}
	}()

	_, downloadErr = io.Copy(f, resp.Body)
	return
}

// fetchExpectedChecksum downloads the SHA256SUMS.txt file and returns the expected checksum for the given archive name.
func fetchExpectedChecksum(httpClient *http.Client, checksumsURL safeurl.SafeURL, archiveName string) (string, error) {
	resp, err := httpClient.Get(checksumsURL.String())
	if err != nil {
		return "", err
	}
	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return "", fmt.Errorf("failed to download checksums: %s", resp.Status)
	}

	// Parse the checksums file. Possible formats are:
	// - "<checksum>  <filename>" (two whitespaces)
	// - "<checksum> <filename>"
	scanner := bufio.NewScanner(resp.Body)
	for scanner.Scan() {
		line := scanner.Text()
		fields := strings.Fields(line)
		if len(fields) >= 2 {
			checksum := fields[0]
			filename := fields[1]
			if filename == archiveName {
				return checksum, nil
			}
		}
	}
	if err := scanner.Err(); err != nil {
		return "", fmt.Errorf("failed to read checksums: %w", err)
	}

	return "", fmt.Errorf("checksum not found for %s", archiveName)
}
