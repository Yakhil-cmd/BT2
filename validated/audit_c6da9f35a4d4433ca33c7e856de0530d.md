### Title
Earned but unpaid epoch rewards are silently burned with no retry/refund when a stake account is closed between reward calculation and partitioned distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
Solana's partitioned epoch-rewards mechanism computes each staker's inflation/block reward once, at the epoch boundary, from a `StakesCache` snapshot, but actually credits (stores) those rewards to accounts over many subsequent blocks. If, between calculation and the account's scheduled distribution block, the staker performs a normal, permitted stake operation that removes their delegation from `StakesCache` (e.g. withdrawing a fully-inactive/closed stake account, or merging it away), the distribution step cannot find the account and the reward is permanently burned instead of paid or retried — mirroring exactly the reported bug class of "no refund nor retry mechanism" for on-chain execution that no longer matches the state assumed when the value was computed.

### Finding Description
Reward calculation happens once at the epoch boundary in `calculate_stake_rewards_and_commissions` / `redeem_delegation_rewards`, using a snapshot of `StakesCache` delegations [1](#0-0) . The resulting `PartitionedStakeReward`s are not applied immediately; they are split into partitions and applied gradually across up to `num_partitions` following blocks by `distribute_partitioned_epoch_rewards` / `distribute_epoch_rewards_in_partition` [2](#0-1) .

Each block's partition is applied by `store_stake_accounts_in_partition`, which looks up the *current* `StakesCache` for each stake account still awaiting payment: [3](#0-2) 

`build_updated_stake_reward` returns `DistributionError::AccountNotFound` if the pubkey it was recorded against at calculation time is no longer present in the live `stakes_cache_accounts` map. `store_stake_accounts_in_partition` handles this by **burning** the reward rather than crediting it or deferring it for a later attempt: [4](#0-3) 

The comment on the function explicitly assumes this is unreachable — "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned" [5](#0-4)  — yet `DistributionError::AccountNotFound` is a defined, handled variant precisely for the case where the account disappears from `StakesCache` between calculation and distribution [6](#0-5) .

A staker whose delegation is entitled to a reward for the just-ended epoch can legitimately close or merge away their stake account in the window between the calculation block and their assigned distribution block/partition (reward calculation and distribution can span hundreds of blocks/multiple partitions, as shown by the test scaffolding around `distribution_starting_block_height` and `num_partitions` [7](#0-6) ). Once removed from `StakesCache`, that user's already-earned reward for the prior epoch is unrecoverable — it is subtracted from the `EpochRewards` sysvar total as "distributed" but actually burned [8](#0-7) , with no code path to detect this and pay the staker (e.g., to their withdrawal destination) or retry the credit against a resurrected/renamed account.

This is precisely the structural bug pattern in the report: reward eligibility ("source-chain deposit") is computed against on-chain state that can legitimately move before the payout executes ("destination-chain execution"), the payout can fail as a result, and there is no refund or retry mechanism for the affected user — the value is simply lost.

### Impact Explanation
Impact is a real, unrecoverable loss of value owed to a staker: lamports that were already calculated as earned (and reflected as "distributed_rewards" bookkeeping in the sysvar) are burned instead of credited, and the affected user has no way to claim or retry. This is a fund-loss / misattributed-reward bug affecting reward distribution accounting, not a mock or theoretical scenario — it is directly reachable via ordinary stake account lifecycle instructions (withdraw/merge) available to any unprivileged staker, during a window (partitioned distribution) that can span many blocks by design.

### Likelihood Explanation
Likelihood is moderate: it requires a staker to time a stake-account-closing action (full withdrawal once fully deactivated, or merge) to land after reward calculation for an epoch but before their specific partition's distribution block. Since distribution is intentionally spread over `num_partitions` blocks (potentially large validator sets → many partitions/blocks), and stakers control exactly when they submit such instructions, this is achievable without any race against validators or special privileges — either accidentally (a routine unstake around epoch boundary) or via targeted self-inflicted/adversarial reward denial.

### Recommendation
Before dropping a stake account from `StakesCache` during a `Withdraw`/`Merge`/`Deactivate`-adjacent flow, check (or otherwise plumb through) any still-pending `PartitionedStakeReward` obligation for that pubkey in the active `EpochRewardStatus`, and either (a) pay out the pending reward immediately as part of removing the account, or (b) defer/redirect the reward to the account's authorized withdrawer/destination instead of silently burning it in `store_stake_accounts_in_partition`. At minimum, `DistributionError::AccountNotFound` should not translate to a permanent burn without an explicit, auditable fallback destination for the lamports.

### Proof of Concept
1. Delegate a stake account and earn credits during epoch N.
2. At the epoch N→N+1 boundary, `calculate_stake_rewards_and_commissions` computes and records a `PartitionedStakeReward` for this stake pubkey, placing it into some partition index `i` scheduled for block `distribution_starting_block_height + i` (per `distribute_partitioned_epoch_rewards`).
3. Before block `distribution_starting_block_height + i` is reached, submit a `Deactivate` (if not already inactive) followed by `Withdraw` for the full balance (or a `Merge` into another stake account) — both are ordinary permitted staker operations once the stake is fully inactive — removing the pubkey's delegation entry from `StakesCache`.
4. When block `distribution_starting_block_height + i` executes, `store_stake_accounts_in_partition` calls `build_updated_stake_reward`, which returns `Err(DistributionError::AccountNotFound)` because the pubkey is absent from `stakes_cache_accounts`.
5. The reward amount is added to `stake_reward_lamports_burned` instead of being credited to the staker; `distribute_epoch_rewards_in_partition` reduces capitalization/sysvar bookkeeping accordingly, and the staker permanently loses the reward with no mechanism to reclaim or retry it.

    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }
