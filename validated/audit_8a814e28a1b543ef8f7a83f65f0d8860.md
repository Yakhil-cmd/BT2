### Title
`DenyReserveTransferToRelayChain` only scans top-level instructions, allowing reserve-transfer bypass via `SetAppendix`/`SetErrorHandler` nesting - (File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs)

### Summary
Asset Hub Kusama's `Barrier` wraps `DenyReserveTransferToRelayChain` directly (not `DenyRecursively<DenyReserveTransferToRelayChain>`), unlike Bridge Hub Polkadot and Bulletin Polkadot which explicitly use the recursive wrapper for the same deny rule. Because the underlying filter's `should_execute` only iterates the top-level `message: &mut [Instruction<RuntimeCall>]` slice, a `DepositReserveAsset`/`InitiateReserveWithdraw`/`TransferReserveAsset` instruction targeting the Relay Chain that is nested inside `SetAppendix`/`SetErrorHandler` is never inspected, letting it slip past the deny check while `AllowTopLevelPaidExecutionFrom<Everything>` still authorizes the outer program.

### Finding Description
The Barrier for Asset Hub Kusama is: [1](#0-0) 

Compare this to Bridge Hub Polkadot and Bulletin Polkadot, which wrap the same deny rule in `DenyRecursively`: [2](#0-1) [3](#0-2) 

The existence of `DenyRecursively` as a distinct wrapper (imported from `xcm_builder`) implies the base `DenyReserveTransferToRelayChain::should_execute` implementation only checks the top-level instruction list for `InitiateReserveWithdraw { reserve: (1, Here), .. }`, `DepositReserveAsset { dest: (1, Here), .. }`, or `TransferReserveAsset { dest: (1, Here), .. }`, and does not recurse into the nested `Xcm` payloads carried by `SetAppendix(xcm)` or `SetErrorHandler(xcm)`. Asset Hub Kusama, Asset Hub Polkadot, Bridge Hub Kusama, Collectives Polkadot, Coretime Kusama/Polkadot, and the People chains all use the plain (non-recursive) form: [4](#0-3) [5](#0-4) 

Attacker flow: a signed user calls `PolkadotXcm::execute` (or triggers execution via `send`/XCMP from a location matched by `AllowTopLevelPaidExecutionFrom<Everything>`) with a program such as:
```
WithdrawAsset(ksm)
BuyExecution(ksm_fee, Unlimited)
SetAppendix(Xcm(vec![DepositReserveAsset { assets: Wild(All), dest: Parent.into(), xcm: Xcm::new() }]))
DepositAsset(..., beneficiary)
```
`DenyThenTry<DenyReserveTransferToRelayChain, ...>` scans the four top-level instructions (`WithdrawAsset`, `BuyExecution`, `SetAppendix`, `DepositAsset`) - none of them match the deny patterns directly, since `SetAppendix` is a distinct enum variant, so the deny check passes. `AllowTopLevelPaidExecutionFrom<Everything>` then approves execution because the message begins with `WithdrawAsset`/`BuyExecution`. During execution, the appendix runs and executes `DepositReserveAsset { dest: Parent, .. }`, which withdraws the held KSM from holding and sends a `ReserveAssetDeposited` message to the Relay Chain - exactly the operation the deny rule exists to prevent.

### Impact Explanation
KSM (or other assets) are burned/locked out of the sender's Asset Hub balance via `DepositReserveAsset`, and a `ReserveAssetDeposited` message is dispatched to the Relay Chain claiming Asset Hub now holds them in reserve. The Relay Chain does not treat Asset Hub as a legitimate reserve for its own native KSM (KSM is teleported, not reserve-backed, between Relay and AH), so the message is likely trapped or rejected on the Relay Chain side while the debit on Asset Hub is already final. This produces the exact asset-accounting desync between AH and the Relay Chain that `DenyReserveTransferToRelayChain` is designed to prevent, potentially resulting in loss/freezing of user funds.

### Likelihood Explanation
- Precondition: any signed account with enough balance to pay XCM execution fees; no special privilege required.
- Reachable via `pallet_xcm::execute`, a normal, permissionless extrinsic already exercised in the repo's own emulator tests for related reserve-transfer paths (e.g. `reserve_withdraw_from_untrusted_reserve_fails`). [6](#0-5) 
- The bypass technique (`SetAppendix`/`SetErrorHandler` nesting) requires no special tooling beyond constructing a `VersionedXcm` and is fully repeatable/deterministic.
- The fact that the fellows/maintainers already introduced `DenyRecursively` and applied it to Bridge Hub Polkadot/Bulletin Polkadot, but not to Asset Hub Kusama/Polkadot or the other system chains, strongly suggests this is a genuine, currently-unpatched gap in this repository's configuration rather than a hypothetical concern.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively` in the `Barrier` definitions of `asset-hub-kusama`, `asset-hub-polkadot`, `bridge-hub-kusama`, `collectives-polkadot`, `coretime-kusama`, `coretime-polkadot`, `people-kusama`, and `people-polkadot`, matching the pattern already used in `bridge-hub-polkadot` and `bulletin-polkadot`:
```rust
pub type Barrier = TrailingSetTopicAsId<
    DenyThenTry<
        DenyRecursively<DenyReserveTransferToRelayChain>,
        ( ... )
    >,
>;
```

### Proof of Concept
xcm-emulator / runtime integration test plan (add to `integration-tests/emulated/tests/assets/asset-hub-kusama/src/tests/reserve_transfer.rs`):
```rust
#[test]
fn reserve_transfer_ksm_to_relay_via_appendix_bypass() {
    let signed_origin = <AssetHubKusama as Chain>::RuntimeOrigin::signed(AssetHubKusamaSender::get());
    let amount: Balance = ASSET_HUB_KUSAMA_ED * 1000;
    let ksm: Assets = (Parent, amount).into();

    AssetHubKusama::execute_with(|| {
        let xcm: Xcm<asset_hub_kusama_runtime::RuntimeCall> = Xcm(vec![
            WithdrawAsset(ksm.clone().into()),
            BuyExecution { fees: (Parent, amount / 2).into(), weight_limit: Unlimited },
            SetAppendix(Xcm(vec![DepositReserveAsset {
                assets: Wild(All),
                dest: Parent.into(),
                xcm: Xcm::new(),
            }])),
            DepositAsset { assets: Wild(All), beneficiary: AssetHubKusamaSender::get().into() },
        ]);
        let result = <AssetHubKusama as AssetHubKusamaPallet>::PolkadotXcm::execute(
            signed_origin,
            bx!(VersionedXcm::V5(xcm)),
            Weight::MAX,
        );
        // Expected (fixed) behavior: barrier should deny this, e.g. Filtered/Unsupported error.
        // Current (vulnerable) behavior: result is Ok and a ReserveAssetDeposited is sent to Relay.
        assert!(result.is_err(), "DenyReserveTransferToRelayChain bypass via SetAppendix succeeded");
    });
}
```
Assert that after applying the fix (`DenyRecursively<DenyReserveTransferToRelayChain>`), the call returns `Filtered`/`Unsupported`, and before the fix it succeeds and emits an outbound `ReserveAssetDeposited` XCM to the Relay Chain.
