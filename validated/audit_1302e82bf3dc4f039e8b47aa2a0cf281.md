## Title
CCMenu API endpoint bypasses the stack scoping enforced on `ApiClient` tokens - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` re-implements the `stack` lookup method to resolve the target stack directly from `params[:stack_id]` via `Stack.from_param!`, instead of using the `stacks`-scoped lookup inherited from `Shipit::Api::BaseController`. Every other stack-scoped API endpoint in the engine (`TasksController`, `OutputsController`, `MergeRequestsController`, `StacksController`, etc.) resolves the stack through `stacks.from_param!`, which restricts the lookup to `current_api_client.stack_id` when the authenticating `ApiClient` is scoped to a single stack. Because `CCMenuController#stack` skips that scoping filter entirely, a token that is supposed to be limited to one stack can be used to read the CI/deploy status of any stack in the installation.

### Finding Description
`ApiClient` records can optionally be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The intended authorization binding is: **a token authorizes only the stack it is bound to** (`current_api_client.stack_id`), enforced centrally by `BaseController#stacks`/`#stack`: [2](#0-1) 

This is exactly the pattern the test suite documents as the expected behaviour ("an api client scoped to a stack will only see that one stack") for the `StacksController#index` endpoint.

`CCMenuController`, however, overrides `stack` and drops the scoping check: [3](#0-2) 

`require_permission :read, :stack` only verifies that the token carries the `read:stack` *permission string*; it never checks that `current_api_client.stack_id` matches the requested `stack_id`. The `check_permissions!` method used for that check is scope-string based, not stack-instance based: [4](#0-3) 

So any token that has the `read:stack` permission — including one deliberately created and distributed for a single stack's CCMenu widget, as generated by `CCMenuUrlController#client` — can be replayed against `/api/stacks/:stack_id/ccmenu` for a *different* `stack_id` and will successfully return that other stack's name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` (per the fields asserted in the CCMenu template/tests).

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches." A token holder who is only supposed to see the CI status of one stack (e.g., an engineer or a CI dashboard given a CCMenu URL/token scoped to their project) can pivot that same token to read the deploy/CI status of every other stack managed by this Shipit instance, including stacks belonging to unrelated teams/repositories. This is an unauthorized cross-stack read of stack state, matching the "High - unauthenticated/unauthorized read of stack state" impact category, since it grants read access far beyond what the token was scoped and issued for.

### Likelihood Explanation
Likelihood is high for any deployment that issues `stack`-scoped `ApiClient` tokens (the engine explicitly supports and tests this scoping model, see the `here_come_the_walrus` fixture scoped to a single stack) and exposes CCMenu URLs, which are commonly embedded in CI dashboards/status widgets and are not treated with the same secrecy as admin API credentials. No special privilege beyond possessing any valid `read:stack`-scoped token is required, and the target `stack_id` is a simple guessable/enumerable route parameter (`owner/name/environment`).

### Recommendation
Change `CCMenuController#stack` to use the inherited, scope-aware `stacks.from_param!(params[:stack_id])` (i.e., remove the private `stack` override, or reimplement it to filter through `current_api_client.stack_id` the same way `BaseController#stacks` does) so that a stack-scoped token cannot resolve any stack other than the one it is bound to.

### Proof of Concept
1. As an authorized user, create (or have an admin create) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack_id: A.id` (this is the exact shape produced by `CCMenuUrlController#client`, and mirrors the `here_come_the_walrus` fixture used in tests) [5](#0-4) .
2. Obtain that client's `authentication_token` (e.g., from the generated CCMenu URL).
3. Send `GET /api/stacks/<owner>/<name-of-stack-B>/<environment>/ccmenu?token=<TOKEN>`, where stack B is a stack the token was never scoped to.
4. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of the scoped `stacks.from_param!`, the request succeeds (HTTP 200) and returns stack B's deploy/CI status, even though the token's `stack_id` only authorizes stack A.

module Shipit
  class ApiClient < Record
    InsufficientPermission = Class.new(StandardError)

    belongs_to :creator, class_name: 'User'
    belongs_to :stack, optional: true

    validates :creator, :name, presence: true

    serialize :permissions, coder: Shipit.serialized_column(:permissions, type: Array)
    PERMISSIONS = %w[
      read:stack
      write:stack
      deploy:stack
      lock:stack
      read:hook
      write:hook
    ].freeze
    validates :permissions, subset: { of: PERMISSIONS }
