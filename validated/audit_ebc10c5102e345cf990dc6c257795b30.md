I'll investigate the codebase for the specific trust bindings mentioned before drawing any conclusions.### Title
Webhook signature validated against attacker-selected organization while the event is applied to a different organization's repository, enabling cross-tenant commit-status/CI forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (multiple GitHub Apps/orgs configured under `secrets.github`), the webhook signature is verified against a GitHub App config selected from an **unverified** field of the JSON body (`repository.owner.login`), while the event is subsequently applied to a stack/repository resolved from a **different, also-unverified** field of the same body (`repository.full_name`). Nothing binds these two fields together, so a party who legitimately controls one organization's webhook secret can forge a signed webhook that is processed as belonging to a totally different organization's repository.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to check the HMAC against using a value taken straight from the untrusted request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, taken from the raw, not-yet-authenticated JSON payload. `Shipit.github(organization: repository_owner)` looks up the app config for that org name: [3](#0-2) 

Once the HMAC passes (using whatever secret belongs to the *claimed* `repository.owner.login`), the payload is dispatched unmodified to handlers: [4](#0-3) 

Handlers, however, resolve the *target* stack/repository from a **different** field of the same attacker-controlled body — `repository.full_name` — with no cross-check against the field used for signature selection: [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the affected repo) are two independent JSON keys in the same untrusted body, an attacker who legitimately controls Org A's webhook secret (e.g., they administer Org A's GitHub App/webhook settings, a normal capability for any org onboarded to a shared multi-tenant Shipit instance) can:
1. Sign the payload using Org A's secret (`X-Hub-Signature` computed with Org A's `webhook_secret`).
2. Set `repository.owner.login = "org-a"` so `verify_signature` picks Org A's app/secret and passes.
3. Set `repository.full_name = "org-b/some-repo"` (or any sha/status fields for a commit under an org-b-owned stack) so the handler processes the event as belonging to Org B.

This breaks the equality that should hold: `organization whose signature was verified == organization whose repository/commit is mutated`. Before the attacker's request, only Org A can produce events that affect Org A's stacks. After, Org A can forge events that are attributed to and mutate state for Org B's stacks, without ever knowing Org B's secret.

The `status` webhook handler is the most damaging concrete instance: it writes attacker-supplied CI status fields (`state`, `description`, `target_url`, `context`) directly onto a `Commit` looked up by `sha`, as shown by the controller test that exercises this path end-to-end: [6](#0-5) 

Since Shipit gates deploys on CI/commit status, an attacker abusing this cross-org confusion could inject a forged "success" status onto a commit belonging to a stack they do not own, potentially satisfying deploy-safety checks for that stack.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. A tenant that only controls their own organization's webhook secret can write commit-status data (and trigger sync/refresh jobs) for another organization's repositories/stacks hosted on the same shared Shipit instance, which can contribute to an unauthorized deploy being unlocked on someone else's stack — matching the Critical impact bar ("unauthorized deploy") for a multi-tenant install, or at minimum unauthenticated write of commit-status state for another tenant's repo (High).

### Likelihood Explanation
Exploitability depends entirely on the deployment running the multi-organization GitHub App configuration schema (`secrets.github` keyed by org name, see `Shipit.github_default_organization`/`github_app_config`): [7](#0-6) 

In that configuration, any onboarded organization's webhook admin (an ordinary, low-privilege position relative to Shipit itself — no Shipit account, GitHub App private key, or `ApiClient` token is needed) can trivially construct the crafted payload and signature. In the single-org configuration (most common today, per `config/secrets.development.example.yml`), `repository_owner` and the app config are effectively fixed to one org, so this specific cross-org path does not apply — the analog is only reachable in the documented multi-org key schema.

### Recommendation
Bind the field used to select the verifying webhook secret to the same field used to resolve the target repository/stack (e.g., derive both from `repository.full_name`, or verify that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching), and reject the webhook if they diverge, for every org configured under the multi-org schema.

### Proof of Concept
1. Deploy Shipit with two orgs configured in `secrets.github`: `org-a` and `org-b`, each with a distinct `webhook_secret`.
2. As an administrator of `org-a`'s GitHub App (a normal, unprivileged-to-Shipit party), craft a `status` (or `push`) webhook JSON body with:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/target-repo"`
   - `sha` = a commit SHA belonging to an `org-b` stack
   - `state = "success"`, forged CI context/description
3. Sign the raw body with `org-a`'s `webhook_secret` (HMAC-SHA1) and send it as `X-Hub-Signature` to `POST /webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "org-a")` and successfully verifies the signature.
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs `StatusHandler`, which resolves the target repo via `repository.full_name` ("org-b/target-repo") — different from the org whose secret was checked — and writes the forged status onto the `org-b` commit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
