### Title
Unvalidated Peer-Supplied Staking Info Written to DB During Fast Sync Corrupts Reward Distribution — (`datasync/downloader/queue.go`)

### Summary

During fast sync, staking info received from P2P peers is accepted and persisted to the local database with **no cryptographic or state-based validation**. A `TODO` placeholder in `DeliverStakingInfos` always returns `nil`, bypassing the standard derivation path that reads from the actual AddressBook contract state. A malicious peer connected during fast sync can inject arbitrary `StakingInfo` (wrong reward addresses, wrong staking amounts, wrong node IDs), which is then used by `FinalizeState` to distribute KAIA block rewards to attacker-controlled addresses.

---

### Finding Description

In `datasync/downloader/queue.go`, `DeliverStakingInfos` contains a `validate` function that is a no-op stub: [1](#0-0) 

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
```

Compare this to `DeliverReceipts`, which validates each receipt batch against the cryptographically committed `ReceiptHash` in the block header: [2](#0-1) 

```go
validate := func(index int, header *types.Header) error {
    if types.DeriveReceiptsRoot(types.Receipts(receiptList[index]), header.Number) != header.ReceiptHash {
        return errInvalidReceipt
    }
    return nil
}
```

Staking info has no equivalent commitment in the block header, so peer-supplied data passes through unverified.

**Attack path:**

1. During fast sync, the downloader calls `fetchStakingInfos`, which sends `StakingInfoRequestMsg` to connected peers.
2. Any connected peer responds with a `StakingInfoMsg` containing arbitrary `P2PStakingInfo` payloads.
3. `handleStakingInfoMsg` in `node/cn/handler.go` decodes the message and calls `pm.downloader.DeliverStakingInfos`: [3](#0-2) 

4. `DeliverStakingInfos` stores the unvalidated data in `fetchResult.StakingInfo`.
5. `commitFastSyncData` and `commitPivotBlock` call `PutStakingInfoToDB` directly: [4](#0-3) 

6. `PutStakingInfoToDB` writes the peer-supplied data verbatim to the key-value store: [5](#0-4) 

7. On subsequent block processing, `GetStakingInfo` for pre-Kaia blocks **prefers the database** over re-deriving from state: [6](#0-5) 

8. `FinalizeState` uses the corrupted `StakingInfo` to call `state.AddBalance` for each reward recipient: [7](#0-6) 

The standard derivation path (`getFromStateByNumber` → `getFromState` → MultiCall on AddressBook) is completely bypassed for any block whose staking info was written to the DB during fast sync. [8](#0-7) 

---

### Impact Explanation

A malicious peer can supply `P2PStakingInfo` with:
- **`RewardAddrs`** replaced with attacker-controlled addresses → KAIA block rewards (minting + fees) are sent to the attacker instead of legitimate validators.
- **`StakingAmounts`** set to zero for all validators → all staking rewards collapse to the proposer (or are misdirected).
- **`NodeIds`** / **`StakingContracts`** corrupted → validator set selection for subsequent epochs is broken.

The corrupted values are written to the persistent `stakingInfo` key-value store and cached, so the impact persists across node restarts and affects every block processed using that staking epoch's data.

---

### Likelihood Explanation

- Fast sync is the default mode for new nodes joining the network.
- Any node in the P2P network can respond to `StakingInfoRequestMsg`; no special privilege is required.
- The `TODO-Kaia-Snapsync update validation logic` comment in the production code explicitly acknowledges the missing guard.
- The attack window is the entire fast sync duration, which can span thousands of blocks.

---

### Recommendation

Implement content validation in `DeliverStakingInfos` analogous to `DeliverReceipts`. Since staking info is not committed in the block header, the node should re-derive the staking info from the local chain state for the requested block and compare it against the peer-supplied data before persisting:

```go
validate := func(index int, header *types.Header) error {
    derived, err := stakingModule.getFromStateByNumber(header.Number.Uint64())
    if err != nil {
        return err
    }
    if !derived.Equal(stakingInfoList[index]) {
        return errInvalidStakingInfo
    }
    return nil
}
```

Alternatively, include a Merkle commitment to the staking info in the block header so that peer-supplied data can be verified cryptographically without re-executing state.

---

### Proof of Concept

```
1. Attacker runs a Kaia node (no special role required).
2. Victim node starts fast sync and connects to attacker's node.
3. Victim sends StakingInfoRequestMsg for block hashes [h1, h2, ...].
4. Attacker responds with StakingInfoMsg containing:
     P2PStakingInfo{
       BlockNum:     <legitimate block number>,
       RewardAddrs:  [attacker_address, attacker_address, ...],
       StakingAmounts: [5_000_000, 5_000_000, ...],  // valid-looking amounts
       NodeIds:      [<legitimate node IDs>],          // copied from real chain
     }
5. handleStakingInfoMsg → DeliverStakingInfos (validate = nil) → fetchResult.StakingInfo = fake data
6. commitFastSyncData → PutStakingInfoToDB → DB["stakingInfo" || blockNum] = fake JSON
7. Fast sync completes; node begins normal operation.
8. GetStakingInfo(num) for pre-Kaia blocks reads from DB → returns fake StakingInfo.
9. FinalizeState → spec.Rewards = {attacker_address: full_block_reward}
10. state.AddBalance(attacker_address, block_reward) — KAIA minted to attacker.
```

```go
func (s *StakingModule) getFromStateByNumber(num uint64) (*staking.StakingInfo, error) {
	header := s.Chain.GetHeaderByNumber(num)
	if header == nil {
		return nil, fmt.Errorf("failed to get header for block number %d", num)
	}

	// If found in side state, no bother getting from the state.
	if si := s.preloadBuffer.GetInfo(header.Root); si != nil { // Try side state
		return si, nil
	}

	// Otherwise bring up the state from the database.
	statedb, err := s.Chain.StateAt(header.Root)
	if err != nil {
		return nil, fmt.Errorf("failed to get state for block number %d: %w", num, err)
	}
	return s.getFromState(header, statedb)
}
```
