### Title
Webhook signature is verified against the org derived from `repository.owner.login`, but handlers act on the unverified `repository.full_name` field, letting a trusted-but-unprivileged org's signature authorize actions on any other org's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-GitHub-App deployments, `WebhooksController#verify_signature` picks which organization's `webhook_secret` to validate the HMAC against using an **unverified** field of the payload, but every event handler subsequently acts on a **different, still-unverified** field of the same payload to determine which repository/stack to operate on. Nothing ties the two fields together, so a request that is legitimately signed for organization A can be crafted to target organization B's repository.

### Finding Description
`WebhooksController#verify_signature` resolves the org used for HMAC verification purely from JSON body content, before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), and `Shipit.github(organization: repository_owner)` selects that org's independent `webhook_secret` from `secrets.github` per `github_app_config` [3](#0-2) . The HMAC is computed over the raw request body using `GitHubApp#verify_webhook_signature` [4](#0-3) , which only proves the body was signed with *that org's* secret — it says nothing about which repository the body claims to describe.

Every handler, however, resolves its target repository/stack from a **separate** field, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` that was used for signature routing: [5](#0-4) 

For example `PushHandler` uses this to look up and sync arbitrary stacks: [6](#0-5) 

Binding that should hold but doesn't:
`organization_that_authenticated(repository.owner.login) == organization_of(repository.full_name)`

Before the attacker's request: an attacker who legitimately administers their own GitHub App installation (`attacker-org`, one of the orgs configured in `secrets.github`) can only sign webhooks that are supposed to describe `attacker-org`'s repositories.

After the attacker's request: the attacker sends a JSON body where `repository.owner.login` (or `organization.login`) = `attacker-org` (so `verify_signature` selects and validates against `attacker-org`'s known/controlled `webhook_secret`), but `repository.full_name` = `victim-org/victim-repo`. The signature check passes, and the handler proceeds to run `Repository.from_github_repo_name("victim-org/victim-repo").stacks` and trigger actions (e.g. `stack.sync_github`) on `victim-org`'s stacks.

### Impact Explanation
This crosses a trust boundary the multi-org configuration is meant to enforce: each organization's webhook secret should only authorize actions on that organization's own repositories. Because handlers key off `repository.full_name` instead of the org used for signature selection, a single configured (but otherwise unprivileged relative to other tenants) organization can force Shipit to process synthetic push/pull_request/check_suite/membership events for stacks belonging to a completely different, unrelated organization on the same Shipit instance — a cross-repository write/action performed without the victim org's authorization. If the affected stack has continuous deployment enabled, this can trigger unauthorized resyncs/deploy pipeline activity for a repository the attacker does not own, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability requires the attacker to control one legitimately configured GitHub App/org in a multi-org Shipit deployment (`config/secrets.yml`'s multi-organization `github:` schema, see `docs/setup.md`), which is a realistic scenario for shared/multi-tenant Shipit installs where different teams each install their own GitHub App. No compromise of the victim's secret, no privileged Shipit account, and no `ApiClient` token is needed — only the attacker's own already-trusted webhook secret and control over the JSON fields that are independent of that trust decision.

### Recommendation
Bind the signature-verification identity to the identity actually acted upon: after selecting `repository_owner` for `Shipit.github(organization:)`, require that the resolved `Repository`/stack's owner (from `full_name`) matches `repository_owner`/`organization.login` used to pick the secret, and reject the webhook (422) otherwise. Alternatively, derive the org used for handler dispatch strictly from the same field used for the signature lookup, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with the multi-org GitHub App schema (`secrets.github: { attacker-org: {...}, victim-org: {...} }`), matching `docs/setup.md`'s "Using Multiple Github Applications" section.
2. As the (legitimate) owner/admin of `attacker-org`'s configured GitHub App, know its `webhook_secret`.
3. Craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<any sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org_webhook_secret, body)` and POST it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the signature validates. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on its stacks — actions the attacker's org was never authorized to trigger.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
