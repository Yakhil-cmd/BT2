### Title
Interest accrual panics on unscaled-value overflow before the index cap can engage, permanently freezing a high-utilization market - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` unscales `borrowed` and `supplied` with a checked `Ray::mul` before `update_borrow_index` clamps the index to `MAX_BORROW_INDEX_RAY`. On a large market, the product `scaled × index` overflows `i128` and panics while the index is still far below the cap. Since every pool mutation runs `global_sync` first, the market becomes permanently uncallable: no supply, repay, withdraw, liquidation, or bad-debt cleanup ever succeeds again. This is the same bug class as CVE-2016-8864 — a reachable state where processing panics and the service dies — mapped onto the pool's accrual step.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs` computes utilization from unscaled values:

```text
borrowed_original = scaled_to_original(env, borrowed, borrow_index)   // scaled.mul(index), checked
supplied_original = scaled_to_original(env, supplied, supply_index)
```

`scaled_to_original` (`common/src/rates/scaling.rs:14-16`) is `scaled.mul(env, index)`, which panics with `MathOverflow` on `i128` overflow. Only *after* this does `update_borrow_index` (`common/src/rates/index.rs:13-19`) apply `min(new_index, MAX_BORROW_INDEX_RAY)`. The cap therefore protects the index but not the `scaled × index` product: with `scaled ≈ 1e36` raw (≈1 billion whole tokens of an 18-decimal asset, i.e. `1e27` units × `1e9` ray-scaling), the index need only reach ~`170×RAY` before `1e36 × 1.7e29 > i128::MAX` (~`1.7e38`).

The repository's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`) demonstrates this end-to-end: an 18-decimal market at 98% utilization on the XLM curve overflows inside `scaled_to_original` while `borrow_index < MAX_BORROW_INDEX_RAY`, and afterwards `try_withdraw_raw` and `try_repay` both revert with `MATH_OVERFLOW` — the market is frozen, including to liquidations, since liquidation repayment also accrues first.

Reachable path for a single unprivileged address:

1. `controller.supply` a very large amount into a high-decimals market and `controller.borrow` to ~98% utilization (or simply supply; organic borrowing suffices).
2. Permissionless `update_indexes` accruals (anyone can call) grow the index along the curve's steep segment until `borrowed × borrow_index` or `supplied × supply_index` overflows `i128`.
3. From that point every entrypoint that touches the market — `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`, `claim_revenue`, `flash_loan`, `update_indexes` — panics in `global_sync` → `accrue_step` → `scaled_to_original`, with no recovery path (bad-debt write-down and `recapitalize` also require a successful `Cache::load` + accrual).

### Impact Explanation
Permanent freezing of all funds in the affected market: suppliers can never withdraw, borrowers can never repay, liquidators cannot repay or seize, and `recapitalize` cannot rescue it because it too runs `global_sync` first. This satisfies the "permanent freezing of funds" / "contract unable to operate" acceptance criteria for the affected `(hub, token)` book.

### Likelihood Explanation
Requires a very large book on a steep-rate curve at sustained high utilization — the test uses ~10⁹ tokens of an 18-decimal asset at 98% utilization, and accrual must run long enough (tens of years at that shape, faster for larger books since `scaled` is bigger and the overflow threshold in index terms is lower). The cost is large but not impossible for 18-decimal tokens with huge supply, and the attacker needs only unprivileged `supply`/`borrow` plus the permissionless `update_indexes` cadence. The caps check uses saturating `mul_div_floor_saturating` for caps (`calculate_scaled_cap`), so supply caps degrade rather than prevent entry once `scaled × index` nears the ceiling. Medium likelihood, high severity outcome.

### Recommendation
Make the unscale and index-growth paths saturating/capped rather than panicking:

- In `accrue_step`, compute `borrowed_original`/`supplied_original` with a saturating multiply (or clamp `scaled`/`index` so the product fits), so utilization saturates at `RAY` instead of reverting.
- Alternatively, in `update_borrow_index`/`update_supply_index`, clamp the *index* to a level where `supplied × index` and `borrowed × index` cannot overflow for the market's actual scaled balances — i.e. enforce the cap before the unscale, not only on the stored index.
- Consider an early-return in `accrue_step` when `borrow_index` is already at `MAX_BORROW_INDEX_RAY` before performing the unscales, so a saturated index stops accruing cleanly (the unit test `at_the_borrow_index_ceiling_is_sticky_and_accrues_nothing` only exercises the case where the unscale itself still fits).

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360`. pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
