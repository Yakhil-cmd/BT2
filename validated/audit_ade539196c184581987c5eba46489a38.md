### Title
Reentrancy in `_requestERC20Transfer` Allows Unauthorized Cross-Chain Token Minting via Callback Tokens — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20._requestERC20Transfer` makes external calls to the registered ERC20 token contract (fee payment and refund) **before** incrementing `requestNonce`. Unlike the KLAY path (`_requestKLAYTransfer`), it carries no `nonReentrant` guard. If the registered token implements a transfer-hook mechanism (ERC777-style `tokensReceived`, or any custom `transfer` override), the hook can reenter `onERC20Received` on the bridge during the refund transfer, causing the bridge to emit a second `RequestValueTransfer` event without having received the backing tokens for it. The counterpart bridge processes both events and mints/unlocks tokens twice, breaking the source-bridge collateral invariant.

---

### Finding Description

`BridgeTransferKLAY._requestKLAYTransfer` is explicitly marked `nonReentrant` and the comment in `BridgeFee.sol` acknowledges this requirement:

```
// Caller of this function must be nonReentrant.
// - BridgeTransferKLAY._requestKLAYTransfer() is nonReentrant
``` [1](#0-0) 

The ERC20 counterpart `_requestERC20Transfer` carries **no such guard**: [2](#0-1) 

Inside `_requestERC20Transfer`, `_payERC20FeeAndRefundChange` is called first. That function performs two external token transfers — one to `feeReceiver` and one back to `from` (the refund): [3](#0-2) 

The `safeTransfer(from, feeRefund)` call (line 78) hands control to the token contract. If the token implements a hook that fires on receipt (e.g., ERC777 `tokensReceived`), the hook executes inside the token contract with `msg.sender == bridge`. The hook can then call `bridge.onERC20Received(...)`: [4](#0-3) 

`onERC20Received` has no access control beyond `onlyRegisteredToken(msg.sender)`. When called from inside the token's hook, `msg.sender` is the token contract itself — which is registered — so the check passes. This re-enters `_requestERC20Transfer` while `requestNonce` has not yet been incremented.

Execution order during the attack:

1. Outer call: `requestNonce = N`. `_payERC20FeeAndRefundChange` triggers hook.
2. Reentrant call: `requestNonce` is still `N`. Emits `RequestValueTransfer(nonce=N)`. `requestNonce++` → N+1.
3. Outer call resumes: `requestNonce` is now N+1. Emits `RequestValueTransfer(nonce=N+1)`. `requestNonce++` → N+2.

The reentrant call (step 2) emits a valid cross-chain transfer event with **no additional tokens deposited** into the bridge — the bridge's balance only increased by `value + feeLimit` from the outer `safeTransferFrom` in `requestERC20Transfer`: [5](#0-4) 

The counterpart bridge's `handleERC20Transfer` processes both nonces (N and N+1) as independent, valid requests and mints/unlocks `value` tokens for each. [6](#0-5) 

---

### Impact Explanation

The source bridge holds `value` tokens as collateral (after fee deduction) but the counterpart chain mints `2 × value` tokens. This permanently breaks the 1:1 peg invariant of the bridge. In mint/burn mode the counterpart mints unbacked tokens; in lock/unlock mode the counterpart unlocks more tokens than the source bridge holds, eventually draining the counterpart bridge's reserves. This is an **unauthorized mint/unlock of bridged assets**.

---

### Likelihood Explanation

The precondition is that the bridge owner registers an ERC20 token that implements a transfer hook. ERC777 tokens are a widely-used standard and are legitimate candidates for cross-chain bridging. The bridge owner need not be malicious — registering an ERC777 token is a normal operational action. Once such a token is registered, any user can trigger the exploit by calling `requestERC20Transfer` with a `_feeLimit > fee` (so a refund transfer occurs) or `_feeLimit > 0` with `fee == 0`.

---

### Recommendation

Add the `nonReentrant` modifier from `ReentrancyGuard` to `_requestERC20Transfer` (or to its public entry points `requestERC20Transfer` and `onERC20Received`), mirroring the protection already applied to `_requestKLAYTransfer`: [7](#0-6) 

Alternatively, follow the checks-effects-interactions pattern by incrementing `requestNonce` **before** any external token calls.

---

### Proof of Concept

```solidity
// MaliciousERC20: registered on the bridge, has a tokensReceived hook
contract MaliciousERC20 is ERC20 {
    address public bridge;
    address public attacker;

    // Called by bridge during _payERC20FeeAndRefundChange → safeTransfer(attacker, feeRefund)
    function _afterTokenTransfer(address, address to, uint256) internal override {
        if (to == attacker && msg.sender == bridge) {
            // Reenter bridge.onERC20Received — msg.sender here is this token (registered)
            IBridge(bridge).onERC20Received(
                attacker,   // _from
                attacker,   // _to (counterpart recipient)
                1000 ether, // _value — attacker-chosen, no tokens deposited
                0,          // _feeLimit
                ""
            );
        }
    }
}

// Attack sequence:
// 1. Bridge owner registers MaliciousERC20.
// 2. Attacker approves bridge for value+feeLimit tokens.
// 3. Attacker calls bridge.requestERC20Transfer(maliciousToken, to, 1000e18, feeLimit, "").
//    - Bridge pulls 1000e18 + feeLimit tokens from attacker.
//    - _payERC20FeeAndRefundChange refunds feeRefund → triggers hook.
//    - Hook calls bridge.onERC20Received(attacker, attacker, 1000e18, 0, "").
//      → Emits RequestValueTransfer(nonce=N, value=1000e18). requestNonce→N+1.
//    - Outer call emits RequestValueTransfer(nonce=N+1, value=1000e18). requestNonce→N+2.
// 4. Counterpart bridge operators call handleERC20Transfer for nonce N and N+1.
//    → 2000e18 tokens minted/unlocked on counterpart chain.
//    → Source bridge only holds 1000e18 tokens.

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
```
