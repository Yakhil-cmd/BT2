### Title
Webhook signature verification binds to `repository.owner.login`, but handlers act on the independently-controlled `repository.full_name`, allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against using `repository_owner`, derived from the attacker-controlled JSON body (`repository.owner.login` or `organization.login`). Once verification succeeds, every `Handler` subclass instead resolves the actual `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Because these two fields are never required to agree, a tenant who legitimately knows their own org's `webhook_secret` (a normal artifact of Shipit's documented multi-org configuration) can craft a signed payload where `repository.owner.login` names their own org (to pass verification) while `repository.full_name` names an entirely different org's repository (to select the target of the mutation). This is the same class of defect as the `FeeManager` report: a value is used to authorize an action, while the action itself is applied against a different, unchecked value taken from the same message.

### Finding Description
- `verify_signature` computes the verifying organization from the raw payload before/independently of confirming which repository will actually be mutated: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization: repository_owner)` returns the `GithubApp`/`webhook_secret` configured for that organization, and `verify_webhook_signature` only proves that *some* known secret produced this exact byte string — it says nothing about which repository field inside that byte string should be trusted for authorization purposes: [3](#0-2) 

- Every webhook `Handler` then locates the `Stack`/`Repository` to mutate using `repository.full_name`, a field independent from `repository.owner.login`/`organization.login` used for verification: [4](#0-3) [5](#0-4) 

- `PushHandler`, for example, uses that repository lookup to synchronously trigger `stack.sync_github` for whatever stack `full_name` resolves to, regardless of which org's secret authenticated the request: [6](#0-5) 

- Multi-organization configuration, where each org has its own independent `webhook_secret`, is an explicitly documented and supported deployment mode: [7](#0-6) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by webhook_secret (repository_owner)` == `repository/stack actually written by the handler (repository.full_name)`

Before the attacker's request: for genuine GitHub-originated webhooks, GitHub itself guarantees `repository.owner.login` is the owner prefix of `repository.full_name`, so the two fields always agree.
After the attacker's request: the attacker directly POSTs a hand-crafted JSON body (not relayed through GitHub) to Shipit's `/github_webhooks` endpoint, HMAC-signed with their own org's legitimately-known secret. Nothing in `WebhooksController` or `Handler` enforces that `full_name`'s owner segment matches `repository_owner`, so the two fields can be made to diverge arbitrarily.

### Impact Explanation
An operator of one tenant org — with zero privileges inside Shipit itself (no `ApiClient` token, no `Shipit::User`, no GitHub write access to the victim org/repo) — can forge webhook events that mutate state belonging to any other org/repository configured on the same Shipit instance. Depending on the handler exercised this enables:
- Forcing arbitrary `Stack#sync_github` calls (`PushHandler`), which can seed the sync pipeline with attacker-chosen `expected_head_sha`, feeding into deploy/rollback eligibility logic for a repository the attacker doesn't own — an unauthorized cross-repository write.
- Forging `pull_request` lifecycle events (open/close/label) against foreign repositories/stacks via the `pull_request/*` handlers, which manipulate `MergeRequest` state and can drive automatic review-stack provisioning/deprovisioning for repositories the attacker has no access to.

This is a cross-repository/cross-tenant write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization — a Critical-class impact per the accepted categories (unauthorized deploy/cross-repository writes).

### Likelihood Explanation
Low-to-Medium. It requires a Shipit deployment configured for multiple GitHub organizations (a documented, supported configuration) where at least one tenant org is not fully trusted by others. Any user who administers that org's GitHub App integration inherently knows their own `webhook_secret` as part of normal onboarding, so no secret needs to be stolen or brute-forced — only crafted independently of GitHub's own guarantee that `owner.login` matches `full_name`'s owner.

### Recommendation
Bind the two identities together instead of trusting them independently:
- In `WebhooksController#verify_signature`/`repository_owner`, and in `Handler#repository_name`, require that `payload.dig('repository', 'full_name')` starts with `#{repository_owner}/` (case-insensitively) before proceeding, rejecting the webhook (HTTP 422) otherwise.
- Alternatively, resolve the target `Repository`/`Stack` using the *same* organization value that selected the verifying secret, rather than trusting `full_name` independently.

### Proof of Concept
1. Configure Shipit with two orgs, e.g. `orgA` (attacker-administered, `webhook_secret: secretA`) and `orgB` (victim, some `stack` exists for `orgB/victim-repo`).
2. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(secretA, body)` using their own known `secretA`, and `X-Github-Event: push`.
4. `POST /github_webhooks` with this body/headers.
5. `verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature with `secretA`.
6. `PushHandler#stacks` resolves `Repository.from_github_repo_name("orgB/victim-repo")` and calls `sync_github(expected_head_sha: "deadbeef...")` on `orgB`'s stack, even though the request was never signed by `orgB`'s app/secret — demonstrating the cross-organization write.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
