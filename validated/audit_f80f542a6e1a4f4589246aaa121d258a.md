This confirms the vulnerability. The multi-tenant `Shipit.github(organization:)` config binds each organization to its own `webhook_secret`, `app_id`, `private_key`, `installation_id`, etc. `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using `repository_owner`, which is read straight from the attacker-controlled JSON body — `params.dig('repository', 'owner', 'login')` (or `organization.login`) — but the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` using a *different* field of the same attacker-controlled body: `payload.dig('repository', 'full_name')`. Because GitHub's real webhooks always keep `repository.owner.login` and `repository.full_name`'s owner segment consistent, this discrepancy is never exercised by legitimate traffic, but nothing in the code enforces that the two fields agree.

### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on the independent `repository.full_name` field, allowing a legitimate GitHub-App organization to forge writes against any other tenant's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-tenant configurations, Shipit resolves a GitHub App/webhook secret per organization via `Shipit.github(organization: ...)`, keyed by `TOP_LEVEL_GH_KEYS`-scoped config including `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which organization's secret to validate the signature against solely from `repository_owner`, itself parsed out of the untrusted JSON body [2](#0-1) [3](#0-2) . Once the HMAC check passes for that organization's secret, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire raw payload to handlers [4](#0-3) . Handlers (e.g. `PushHandler`, `Handler#stacks`) never re-check `repository.owner.login`; they resolve the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name` [5](#0-4) [6](#0-5) [7](#0-6) .

### Finding Description
The binding that should hold is: `organization whose secret authenticated the signature == owner of the repository being written to`. The controller only proves the former, but the handlers act on the latter, and both are read from attacker-supplied JSON with no cross-field consistency check.

Concretely, `repository_owner` is computed as:
```
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
``` [3](#0-2) 

This selects the `GitHubApp` (and its `webhook_secret`) for that specific organization: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [8](#0-7) . The signature is only checked against the raw body via HMAC-SHA1 with `secure_compare`, so the check proves "this body was signed by organization X's configured secret" — nothing more [9](#0-8) .

But downstream handlers use an unrelated field, `repository.full_name`, to look up which `Repository`/`Stack` to mutate:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [10](#0-9) 

`Repository.from_github_repo_name` splits this into `owner/name` and does a plain `find_by`, with no requirement that `owner` matches `repository_owner` used for signature verification [6](#0-5) .

Attack sequence: an attacker who administers a legitimate GitHub organization ("attacker-org") that has installed the Shipit GitHub App (i.e., has a valid, correctly-configured `webhook_secret` for `attacker-org` in `Shipit.secrets.github[:attacker-org]`) can send a webhook whose signature is computed with `attacker-org`'s own secret, but whose JSON body sets:
- `repository.owner.login = "attacker-org"` (or `organization.login`) — used only for secret selection
- `repository.full_name = "victim-org/victim-repo"` — used by the handler to find the real stack

`verify_signature` fetches `attacker-org`'s `webhook_secret` and validates successfully (the attacker legitimately knows this secret). `PushHandler#process` then resolves `stacks` for `victim-org/victim-repo` and calls `stack.sync_github(expected_head_sha: params.after)` on it [7](#0-6) , forcing an unauthorized sync/deploy trigger against a repository the attacker does not own and for which they hold no valid signing secret.

### Impact Explanation
`sync_github` with an `expected_head_sha` the attacker controls can drive `next_commit_to_deploy`/continuous-delivery logic on the victim stack, and other handlers keyed the same way (e.g. `commit_status`/`check_run`/`membership` handlers, all resolved from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) can inject fabricated CI statuses or check-run conclusions for a repository the attacker never controls. Fabricated green CI status is one of the standard levers Shipit uses to gate/trigger deploys, so this crosses into "unauthorized deploy" territory as defined by the impact bar (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires only that the attacker operates any organization onboarded to this Shipit instance with the GitHub App installed for that org (i.e., knows its own legitimate `webhook_secret`/app credentials) — no privileged Shipit account, no victim credentials, and no `ApiClient` token. This is a normal "unprivileged attacker" scenario in a multi-tenant Shipit deployment where multiple organizations share one instance, matching the analog rule's requirement of "an organization that authenticated versus the repository that is written."

### Recommendation
After verifying the signature, re-derive the acting repository/organization strictly from the verified `repository_owner` (or reject if `repository.full_name`'s owner segment doesn't case-insensitively match `repository_owner`) before handlers resolve stacks — i.e., enforce `repository.full_name.split('/').first == repository_owner` in `WebhooksController` or in `Handler#stacks`/`Handler#repository_name` before use.

### Proof of Concept
1. Operate GitHub organization `attacker-org`, with the Shipit GitHub App installed and its `webhook_secret` configured server-side under `secrets.github[:attacker-org]`.
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already present as a commit on victim-org/victim-repo>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own known secret [2](#0-1) .
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `stack.sync_github(expected_head_sha: ...)` on the victim's stack [7](#0-6) , an action the attacker was never authorized to perform on `victim-org/victim-repo`.
