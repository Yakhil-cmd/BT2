### Title
Cross-tenant stack read via `CCMenuController#authenticate_api_client` bypassing stack scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides both `authenticate_api_client` and `stack`, and the overridden `stack` method resolves `params[:stack_id]` against `Stack.from_param!` directly instead of the scoped `stacks.from_param!` defined in `BaseController`. Any valid `ApiClient` token — regardless of which single stack it was issued for — can therefore read CCTray build/deploy status for any stack on the install.

### Finding Description
The intended binding is: `current_api_client.stack_id == requested stack.id` (or `current_api_client.stack_id` is nil, meaning unrestricted). `BaseController#stacks` at [1](#0-0)  enforces exactly this by scoping `Stack.where(id: current_api_client.stack_id)` when `stack_id?` is true, and `#stack` calls `stacks.from_param!`.

`CCMenuController` however defines its own `stack` method that ignores this scope entirely: [2](#0-1) . It calls `Stack.from_param!(params[:stack_id])` against the full `Stack` table, with no reference to `current_api_client.stack_id` at all.

The overridden `authenticate_api_client` at [3](#0-2)  just authenticates the token via `ApiClient.authenticate(params[:token])`; it never re-checks stack scope, and only falls back to `super` (Basic-Auth path) if authentication via the query-string token fails.

The only other gate is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!` at [4](#0-3) . That method only checks that the string `"read:stack"` is present in the client's `permissions` array — it performs no comparison against `stack_id` whatsoever, so it does not close the gap.

Attacker request: `GET /api/stacks/<victim_stack_id>/cc.xml?token=<token belonging to ApiClient A whose stack_id = stack A, with read:stack permission>`. Because `stack` never consults `current_api_client.stack_id`, `Stack.from_param!(victim_stack_id)` resolves the victim's stack and `show` renders its latest deploy/rollback status, ended_at, running state, etc. — data belonging to a stack the token was never scoped to.

### Impact Explanation
An attacker holding any single-stack-scoped `ApiClient` token (e.g., one legitimately issued to them for their own stack) can enumerate `stack_id`/slug values and read CCTray XML for every other stack in the install, exposing build/deploy status, activity, and running state cross-tenant. This is an unauthenticated-for-that-resource read of stack build/deploy state, matching the "High" impact category (unauthorized read of stack state across tenant boundaries via a token not scoped to that resource). It is fully repeatable against any stack ID and requires no additional privilege escalation per request.

### Likelihood Explanation
Preconditions are minimal and match realistic operation: any two `ApiClient` records with distinct `stack_id`s and the `read:stack` permission (a normal, non-privileged CI-token setup). The attacker only needs one legitimately-issued scoped token (their own, for their own stack) and knowledge/guessing of another stack's `stack_id` or slug — no secrets, GitHub credentials, or session are required. This is trivially and repeatably exploitable via a single unauthenticated GET.

### Recommendation
Change `CCMenuController#stack` to use the inherited scoped lookup, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, removing the private override that calls `Stack.from_param!` directly, so cc.xml requests are subject to the same `current_api_client.stack_id` scoping as the rest of the API.

### Proof of Concept
Minitest plan (`test/controllers/api/ccmenu_controller_test.rb`):
1. Create `stack_a` and `stack_b` (`Shipit::Stack`), and `api_client_a = ApiClient.create!(stack: stack_a, permissions: ['read:stack'], creator: user)`.
2. Assert binding before: `api_client_a.stack_id == stack_a.id` and `api_client_a.stack_id != stack_b.id`.
3. `get shipit.api_stack_ccmenu_url(stack_b), params: { token: api_client_a.authentication_token }`.
4. Assert response is `200` and body contains `stack_b`'s project name — demonstrating the token scoped to `stack_a` was accepted for `stack_b`, i.e., the binding `current_api_client.stack_id == stack.id` is violated (response should have been `404`/`403` per intended scoping in `BaseController#stacks`, but is not, because `CCMenuController#stack` bypasses it).
