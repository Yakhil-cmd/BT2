### Title
Cross-repository status manipulation via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes GitHub `status` events into the database by looking up commits with a bare, global `Commit.where(sha: params.sha)` query that has no repository or stack scoping, so any commit row across all stacks sharing that SHA gets its status updated from a single webhook payload. `Shipit.github(organization:)` picks the HMAC secret to verify based on the attacker-controlled `repository.owner.login`/`organization.login` field in the payload, so signature verification is scoped per-organization config, not per-stack/per-repository, which is a distinct control from the actual DB write path.

### Finding Description
The broken binding: the handler should enforce `commit.stack.repository.full_name == payload.repository.full_name` (or at minimum scope by the stack that authenticated the webhook), but instead the code only enforces `sha == commit.sha`: [1](#0-0) 

`Commit#create_status_from_github!` then unconditionally creates a status row on that commit and re-evaluates deployability/merge triggers: [2](#0-1) [3](#0-2) 

Since `Commit` rows belong to a `Stack` (`belongs_to :stack`) and the `sha` column is only unique per `(stack_id, sha)` (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, not globally unique), two different stacks (potentially backed by two different `Repository` records/owners) can legitimately hold `Commit` rows with the identical `sha` value — e.g., when one repository is a fork of the other and shares history, a normal, non-adversarial GitHub occurrence. `StatusHandler#process` has no awareness of which repository authenticated the incoming webhook; it blindly updates every `Commit` row across the whole database whose `sha` column matches.

Webhook authentication in `Shipit::WebhooksController#verify_signature` only proves that the request was signed with the secret associated with the *organization named in the payload itself* (`repository_owner` is read directly from attacker-controlled `params`): [4](#0-3) [5](#0-4) 

This proves "a valid webhook secret exists for org X" — it does **not** prove that the specific `sha`/`context` in the payload belongs to a commit that actually lives in a repository under org X. `StatusHandler` never re-checks `payload['repository']['full_name']` against `commit.stack.repository.full_name` before writing.

Attack flow: an attacker who legitimately controls a repository (or fork) registered as its own Shipit stack — and thus can generate genuinely signed webhooks for that repo/org — pushes a commit whose SHA is shared with a commit already present in a victim stack's history (trivially achievable via a fork sharing ancestor commits, since git commit hashes are content+parent addressed). The attacker then triggers (or fabricates, since they control their own repo's CI) a `status` event with `context: deploy/production`, `sha: <shared-sha>`, `state: success`, signed with their own legitimate org's webhook secret. `StatusHandler#process` finds **all** `Commit` rows with that SHA — including the victim's — and calls `create_status_from_github!` on each, flipping the victim's `deploy/production` status and potentially unblocking a deploy or continuous-delivery merge (`stack.schedule_merges`, `ContinuousDeliveryJob`) on a stack the attacker never authenticated for.

### Impact Explanation
A payload signed for one repository/organization mutates commit/status state belonging to a different, victim repository's stack — this is the "payload for one repository mutating another's stack/commit" category (Critical). Concretely it can flip `deploy/production` (or any required/blocking CI context) to `success`, which feeds `Commit#deployable?` and `Stack#schedule_merges`/`ContinuousDeliveryJob`, potentially triggering an unauthorized deploy or merge-queue action on the victim stack. The attack is repeatable for every future push to the attacker's fork whose SHA happens to match a commit still referenced by the victim stack (e.g., shared history commits, or commits the attacker deliberately reproduces bit-for-bit, which is possible since git commits are deterministic from author/committer/timestamp/tree/parents/message).

### Likelihood Explanation
Preconditions: the attacker needs a repository (e.g., a fork of the victim's repo, or any repo under their control) that is itself onboarded as a Shipit stack so that a `Shipit.github(organization:)` config with a real webhook secret exists for that org — this is realistic in multi-tenant Shipit deployments and for open-source forks where CI apps post statuses. They also need a SHA collision, which for related repositories (forks) is common at shared history points and can be engineered by crafting identical commits (same tree/parents/author/committer metadata) even without any real relationship. No GitHub App private key, session, or API token is required — only the ability to have GitHub deliver (or to directly POST, if the attacker can compute/replicate a valid HMAC signature using a secret they already legitimately hold for their own onboarded org) a `status` webhook. This is a moderate-cost but fully unprivileged and repeatable attack against any co-hosted stack sharing commit SHAs.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogously in `CheckRunHandler`/other handlers using bare SHA lookups) by the repository that authenticated the webhook, e.g., resolve the `Repository`/`Stack` from `payload['repository']['full_name']` first, then query `commit.stack.repository.id`-scoped commits, or join through `Stack`/`Repository` and filter `where(stacks: { repository_id: repository.id })`. Additionally, verify in the handler that `commit.stack.repository.full_name == params.dig(:repository, :full_name)` before calling `create_status_from_github!`, defensively rejecting cross-repository collisions even if callers change in the future.

### Proof of Concept
minitest plan (add to `test/models/webhooks/handlers/status_handler_test.rb` or similar):
1. Create two `Repository`/`Stack` fixtures for different owners/orgs (`victim/repo` and `attacker/repo`), both with `Stack#required_statuses`/`blocking_statuses` including `deploy/production`.
2. Create a `Commit` under the victim stack with `sha: "deadbeef" * 5` (40 hex chars) and no existing `deploy/production` status, and assert `commit.deployable?` is `false` (binding LHS: victim commit not deployable).
3. Create a `Commit` under the attacker stack with the **same** `sha` value (simulating shared SHA / fork history).
4. Build a `status` webhook payload with `sha` set to the shared value, `context: "deploy/production"`, `state: "success"`, and `repository.full_name` set to `attacker/repo` (i.e., payload only ever references the attacker's repository).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(params).call` (or invoke the equivalent handler entrypoint) directly — bypassing HTTP signature layer, since the vulnerability is in the handler's DB scoping, not in `verify_signature`.
6. Assert that the victim commit now has a `deploy/production` status of `success` (`victim_commit.reload.status.success?` is `true`), and separately assert that `payload['repository']['full_name'] != victim_stack.repository.full_name` (proving the write happened for a repo that never authenticated it) — this demonstrates the two sides of the equality (`commit.stack.repository.full_name` vs. `payload.repository.full_name`) diverge while the write still succeeds, confirming the missing binding check.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
