## Title
Membership webhook trusts `organization.login` for `Team#organization` while signature verification is keyed on `repository_owner`/`organization.login` from the same untrusted payload — no cross-field binding enforced - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

## Summary
`WebhooksController#verify_signature` selects the GitHub App config (and therefore the `webhook_secret` used to validate `X-Hub-Signature`) using a value it reads out of the *same, attacker-controlled* JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` (`repository_owner`). For `membership` events there is no `repository` key at all, so the org used to select the verifying secret is exactly `params['organization']['login']` — the very same field the `MembershipHandler` later trusts unconditionally to create/attribute a `Team` (`team.organization = params.organization.login`) which feeds `Shipit.github_teams` / `User#authorized?`.

## Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` picks the app config like this: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly no-ops when `webhook_secret` is blank: [3](#0-2) 

The docs and shipped example configs show `webhook_secret` as an optional, frequently-nil field, including in multi-org deployments: [4](#0-3) [5](#0-4) 

For the `membership` event, `MembershipHandler` trusts `params.organization.login` to create (or reuse) a `Team` bound to that organization, and mutates its membership without ever re-deriving/confirming that organization from a separately-verified source: [6](#0-5) 

The binding being broken is: *"the organization whose secret authenticated the request" (repository_owner, derived from `params['organization']['login']` when no `repository` key is present) versus "the organization that gets written into `Team#organization`"* — both are read from the exact same JSON field of the exact same unsigned-until-verified payload, with no independent verification that the writer of the webhook actually controls that organization beyond possessing *some* configured `webhook_secret`. In a multi-org Shipit instance, if any one configured organization has `webhook_secret` left blank (a documented, common configuration, e.g. during setup or for low-friction orgs), `verify_webhook_signature` returns `true` unconditionally for *any* payload whose `organization.login`/`repository.owner.login` matches that blank-secret org — and the attacker fully controls every other field of that same JSON body, including `team`, `member`, and (for other events) `repository.full_name`, which are used by handlers to write into other, unrelated stacks or `Shipit.github_teams`-controlling `Team` records.

## Impact Explanation
If any organization configured in `Shipit.github`'s multi-org config has no `webhook_secret` set, an unauthenticated network attacker can POST a forged `membership` webhook naming that organization in `organization.login` (satisfying `verify_signature`), while freely choosing `team.id`, `team.slug`, `member.login`, and `action`. This directly creates/mutates `Team` records and `Membership` rows via `Team#add_member`, which are the exact objects `Shipit.github_teams`/`User#authorized?` rely on for gating access to the whole application: [7](#0-6) [8](#0-7) 

Depending on how `Shipit.github_teams` is configured (by team handle, which is derived from `organization/slug`), an attacker able to forge a `membership added` event for a team matching a configured `Shipit.github_teams` handle could add an arbitrary GitHub login as a member of that authorizing team record in Shipit's database — escalating into `Shipit.github_teams` authorization, which matches the "High" impact bucket defined in the rules. The same weak binding (no cross-validation between the org used for signature selection and the object actually written) also applies to `push`/`status`/`pull_request` handlers via `repository.full_name`, enabling cross-repository stack syncs for orgs other than the one nominally verified, when that other org shares the "blank secret" org used to pass the signature check.

## Likelihood Explanation
This depends entirely on operator configuration: it requires (a) a multi-organization Shipit deployment, and (b) at least one configured organization having no `webhook_secret`. This is explicitly documented and shown as the default/example in `docs/setup.md` and `config/secrets.development.example.yml`, so it is a plausible, even encouraged, configuration path rather than a theoretical edge case. Given that, the likelihood of an attacker being able to identify a blank-secret org (e.g., trial/staging org) and pivot to writing into a differently-named, protected org's `Team`/`Stack` records is realistic in this class of deployment.

## Recommendation
- Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is blank; require an explicit "unauthenticated/public" opt-in that is scoped and does not let one blank-secret org's requests write into other organizations' data.
- Bind every handler write to the same organization value that was actually verified/authenticated for the request (pass the verified `repository_owner`/organization into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization) }` and have handlers reject payloads whose internal `organization.login`/`repository.owner.login` don't match the verified organization).
- For `MembershipHandler` specifically, verify `params.organization.login` equals the organization used to select the webhook secret before creating/updating `Team`.

## Proof of Concept
1. Configure Shipit with two orgs in `github:` config, e.g. `trusted-org` (with `webhook_secret` set) and `sandbox-org` (with `webhook_secret` left blank, per the documented example).
2. As an unauthenticated attacker, POST to `/github/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": <id_of_team_matching_a_configured_Shipit.github_teams_handle>, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "sandbox-org" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header (or any garbage value) is required, because `Shipit.github(organization: 'sandbox-org')` resolves to an app config whose `webhook_secret` is blank, so `verify_webhook_signature` short-circuits to `true`: [9](#0-8) 
3. `MembershipHandler#process` runs unconditionally, calling `find_or_create_team!` and `team.add_member(member)` for the `team.id`/`slug` chosen by the attacker, even though `team.id` may correspond to a team the attacker has no relationship to on GitHub: [10](#0-9) 
4. If that team's handle is part of `Shipit.github_teams`, `attacker-github-login`'s corresponding Shipit `User` (created on next login) will pass `User#authorized?`, granting it full application access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
```
