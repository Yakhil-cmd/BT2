### Title
Webhook signature verification is keyed by an attacker-controlled organization field that is disjoint from the repository/team fields the handlers actually act on - `Shipit.github_teams` authorization bypass - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a delivery against using a field taken from the **unauthenticated** request body itself (`repository.owner.login` / `organization.login`), before any signature has been checked. Every downstream handler, however, acts on *other* fields of that same body (`repository.full_name`, `team.id`, `team.name`, `organization.login`, `member.login`) to decide which `Stack`, `Repository`, `Team` or `User` to mutate. Because the "authenticated organization" and the "entity written" are two independent, non-cross-checked fields of the same attacker-influenced JSON document, a request that is accepted as "verified" for one loosely-configured (or secret-less) organization can still drive writes against completely unrelated repositories/teams.

### Finding Description
`verify_signature` computes `repository_owner` purely from the JSON payload and immediately uses it to pick the app config: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` explicitly trusts any request unconditionally when the org's `webhook_secret` is blank — a documented, "optional" configuration value: [3](#0-2) [4](#0-3) 

Once `verified` is true (either because the secret matched, or — critically — because no secret is configured for the org named in the payload's `repository.owner.login`/`organization.login`), `create` dispatches the *entire, attacker-shaped* body to the handler for the event, without ever re-checking that `repository.full_name` (or `team`/`organization` for membership events) is consistent with the organization that was just "authenticated": [5](#0-4) 

Handlers resolve their target purely from these other, unverified-against-`repository_owner` fields: [6](#0-5) [7](#0-6) [8](#0-7) 

The `MembershipHandler` is the most sensitive: it creates/updates a `Team` keyed by `team.id`/`team.name`/`organization.login` taken straight from the body, and adds/removes a `member.login` (auto-vivified via `User.find_or_create_by_login!`) to/from that team: [9](#0-8) 

`Team` membership directly gates authorization in Shipit whenever `Shipit.github_teams` is configured: [10](#0-9) 

The binding that should hold is:
`verified-organization (repository_owner used to pick webhook_secret) == organization/repository actually mutated by the handler (repository.full_name / team.organization)`

Before the attacker's request: the mapping only ever holds because real GitHub deliveries are internally consistent (GitHub always signs a payload whose `repository.owner` matches the repository it describes). After an attacker who can reach `/webhooks` crafts an arbitrary JSON body (which is trivial, since the endpoint has no other authentication and `verify_signature` explicitly allows unsigned requests when `webhook_secret` is unset for the organization named in the body): the binding breaks — `repository_owner` (used solely to choose which secret/config check to perform, and bypassable to a no-secret org) is completely decoupled from `team.organization` / `repository.full_name` (used to decide what gets created/modified).

### Impact Explanation
This is the same missing-scope-checking bug class as the reported Solidity issue (a value is consumed by security-relevant logic — here, "which config/secret authorizes this write" — without any explicit, verified relationship to the value that is actually acted upon). In Shipit this crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope:
- Any organization configured in `Shipit.github` (single- or multi-org `secrets.yml`) without a `webhook_secret` (an officially "optional" field per `docs/setup.md`) turns `/webhooks` into an effectively unauthenticated endpoint for any event, because `repository_owner` can be set to that org's name to route the request through the no-secret path, while `team`, `organization.login`, `member.login`, and `repository.full_name` used by the handler can name any team/user/repository already known to Shipit.
- Via `membership` events this allows an unauthenticated party to fabricate `Team`/`Membership` records and add an arbitrary `member.login` to a team, directly manipulating `User#authorized?`'s `Shipit.github_teams` check — an authorization escalation into `Shipit.github_teams`, matching the High-severity bullet in scope.
- Via `push`/`status`/`pull_request` events, the same gap lets a request "authenticated" against one org's (missing) secret drive `PushHandler`/`StatusHandler`/`PullRequest::*Handler` actions (sync, status writes, review-stack archive/unarchive) against a `Stack`/`Repository` resolved solely from `repository.full_name`, independent of `repository_owner`.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: if every configured GitHub App has a non-blank `webhook_secret`, HMAC signing forces the entire raw body (including `repository.full_name`/`team`/`organization`) to be internally consistent with a value only GitHub (or a secret holder) could produce, and the analog does not yield exploitable divergence for an outsider without the secret. The exposure is real whenever any one organization in the deployment omits `webhook_secret` (explicitly documented as optional), which is a plausible and easy-to-hit misconfiguration, especially in `secrets_double_github_app.yml`-style multi-org setups where a low-risk org might be left unsecured while others are secured — the controller does not require all configured orgs to have a secret, nor does it validate that the fields consumed by handlers correspond to the organization that was "verified."

### Recommendation
- Require `webhook_secret` to be present for every configured GitHub organization (fail closed instead of `return true unless webhook_secret` in `lib/shipit/github_app.rb`).
- After signature verification succeeds, explicitly assert that every organization-identifying field consumed by the handler (`repository.full_name`'s owner, `team.organization`, `organization.login`) matches the `repository_owner` value that selected the verifying secret, rejecting the webhook otherwise.
- Consider binding the verified webhook to a single canonical organization identifier at the controller level and threading it through to `Handler#repository_name`/`MembershipHandler#find_or_create_team!`, rather than letting handlers re-derive organization/repository identity independently from the same untrusted payload.

### Proof of Concept
Given a Shipit deployment configured with two orgs, e.g. `test/dummy/config/secrets_double_github_app.yml`-style config where `OrgLow` has `webhook_secret: nil` (optional per docs) and `OrgHigh` (containing sensitive teams/repos) has a real secret:

```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=anything   # ignored: verify_webhook_signature returns true, webhook_secret blank for OrgLow
Content-Type: application/json

{
  "action": "added",
  "team": { "id": 999, "name": "OrgHigh Admins", "slug": "orghigh-admins", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "OrgLow" },
  "member": { "login": "attacker-controlled-login" }
}
```
`verify_signature` resolves `repository_owner` to `"OrgLow"` and finds it has no `webhook_secret`, so `verify_webhook_signature` returns `true` unconditionally regardless of the `X-Hub-Signature` header. `MembershipHandler#process` then creates/looks up a `Team` (`github_id: 999`, name/slug matching whatever `Shipit.github_teams` references) and adds `member.login` to it, letting the attacker satisfy `User#authorized?`'s `Shipit.github_teams` membership check without ever touching `OrgHigh`'s real secret or GitHub API. Note: I did not have terminal/runtime access to actually execute this request against a running instance; this trace is based on static analysis of the cited files.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
