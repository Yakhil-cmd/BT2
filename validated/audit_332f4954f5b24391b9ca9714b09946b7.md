### Title
Webhook signature verification is scoped to the wrong field, letting any onboarded GitHub organization forge webhook events for repositories belonging to a different organization on the same Shipit instance - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to verify the request signature against using one field of the untrusted JSON payload (`repository.owner.login`, falling back to `organization.login`), but the code that actually acts on the webhook (`Shipit::Webhooks::Handlers::Handler#stacks`) resolves the target repository using a *different, unconstrained* field of the same payload (`repository.full_name`). Nothing binds these two fields together, so a valid signature computed with organization A's secret can be attached to a payload that targets organization B's repository.

### Finding Description
`verify_signature` derives the organization used to look up the GitHub App/webhook secret purely from the payload: [1](#0-0) [2](#0-1) 

Once `verified` is true, the raw payload is dispatched unchanged to every registered handler: [3](#0-2) 

But handlers such as `PushHandler` resolve the affected `Stack`/`Repository` from a *different* payload key, `repository.full_name`, with no cross-check against the `repository.owner.login` that was used for signature verification: [4](#0-3) [5](#0-4) 

Shipit explicitly supports multi-tenant configuration where each GitHub organization has its own, independently-known `webhook_secret`: [6](#0-5) 

This is the exact class of bug the external report hints at: a "field acted on" (`repository.full_name`, which drives which `Stack` gets mutated) is never covered by the value that was actually authenticated (`repository.owner.login`, which selects the HMAC secret). The binding that should hold is:

`organization authenticated by signature == owner of the repository the handler writes to`

but the code never enforces `payload.dig('repository','owner','login') == payname.dig('repository','full_name').split('/').first`.

### Impact Explanation
Any organization that is legitimately onboarded to a shared/multi-tenant Shipit instance (and therefore knows its own `webhook_secret`, since that value is chosen by whoever configures that org's GitHub App) can compute a valid `X-Hub-Signature` for a crafted payload where `repository.owner.login` is set to their own org (to pass the secret lookup) while `repository.full_name` is set to `victim-org/victim-repo`. This event is then routed to the real handlers and acts on the victim's `Stack`:
- `push` events call `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to the victim repository, letting the attacker drive the victim's stack's "expected head" state.
- `status`/`check_suite`/`membership`/`pull_request` handlers similarly resolve their target via `repository.full_name`, so commit statuses, check-suite refreshes, or pull-request-linked review stacks for a completely different, unrelated repository can be manipulated.

This breaks the deployment-trust boundary between organizations sharing one Shipit deployment: an org's own valid webhook credential should only ever be able to affect that org's own repositories/stacks, not another org's. Depending on which handler is exercised, this can influence deploy readiness signals or trigger stack synchronization against attacker-supplied state for a stack the attacker has no legitimate access to.

### Likelihood Explanation
The prerequisite is that the attacker controls (knows) the `webhook_secret` for at least one organization configured in this Shipit instance — which is the normal, expected condition for any org legitimately onboarded onto a shared instance, not a privileged compromise of the target's credentials. No access to the victim's `webhook_secret`, `api_clients_secret`, GitHub App private key, or any Shipit session/API token is required. The attack is a single crafted HTTP POST to the public `/github/webhooks` (or equivalent) endpoint with attacker-computed HMAC over attacker-chosen JSON.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the signature, assert that the organization used for the lookup (`repository_owner`/`organization.login`) is the *same* organization as the owner segment of `repository.full_name` that handlers will actually act on, rejecting (422) any payload where they diverge. Alternatively, resolve the target `Repository`/`Stack` first from `full_name`, look up that repository's *own* owning organization, and require the signature to verify against that organization's secret — rather than trusting an organization name supplied directly in the payload for secret selection.

### Proof of Concept
1. Configure Shipit (as documented) with two organizations, e.g. `orga` and `orgb`, each with distinct `webhook_secret`s (see `config/secrets.development.shopify.yml` pattern) and each with a tracked `Stack` for a repository they own.
2. As a user who legitimately administers `orga`'s GitHub App (and thus knows `orga`'s `webhook_secret`), craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, raw_body)>` and `X-Github-Event: push`, then POST to the Shipit webhooks endpoint.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: 'orga')` (from `repository.owner.login`) and successfully verifies the signature against `orga`'s secret.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name('orgb/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'deadbeef...')` on `orgb`'s stack — an org that never authorized this request nor issued the credential that authenticated it.
