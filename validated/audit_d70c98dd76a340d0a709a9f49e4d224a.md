### Title
AA data-feed-priced payouts lack caller-specified slippage/minimum-output protection, exposing trigger senders to fund loss on delayed execution - (File: `formula/evaluation.js`, `data_feeds.js`, `aa_composer.js`)

### Summary
Autonomous Agents (AAs) that price a swap/exchange using `data_feed[[...]]` (e.g. the shipped `futures_contract.oscript` and `fundraising_proxy.oscript` templates) compute the payout amount using whatever oracle value is current **at the moment the trigger unit's MCI becomes stable and is processed**, not at the moment the trigger sender composed and broadcast the unit. There is no protocol-level mechanism for the trigger sender to specify a minimum acceptable output amount, so a delayed trigger, or an oracle update that lands between composition and stabilization, can silently change the payout the sender receives — the same "swap with no slippage protection" bug class as the reported `FeeCollector.claimFees` issue.

### Finding Description
When a trigger unit is composed by a user, it references `data_feed[[...]]` calls inside the target AA's oscript formula, but the actual value used is resolved only when the trigger is executed by `handleTrigger`, which happens after the triggering unit's MCI becomes stable via `handleAATriggers` in `main_chain.js` [1](#0-0) . Formula evaluation resolves `data_feed[[...]]` through `dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, ...)`, where `mci` is the trigger's `last_ball_mci` at execution time [2](#0-1) , and `readDataFeedValue`/`readDataFeedByAddress` simply return the latest feed value at or before that MCI, both from stable storage and from any qualifying unstable AA-authored units [3](#0-2) . New data-feed values are only durably indexed once the posting unit stabilizes, via `addDataFeeds` in `main_chain.js` [4](#0-3) .

The gap between when a user composes a trigger (seeing a particular oracle price) and when that trigger's MCI actually stabilizes and is executed can be substantial — it requires the unit itself, and its last ball, to become stable through further DAG growth and witnessing, exactly analogous to the "delayed or front-run transaction" scenario described in the report. During this window, the oracle (or any address whose data feed the AA references) can legitimately post a new value, or a same-mci/earlier-mci AA state change from a third party can shift a balance-derived ratio, changing the computed payout with no recourse for the original trigger sender. This is demonstrated in the shipped example `futures_contract.oscript`, where the payout in bytes is computed as `round($bytes_per_usd_asset * $usd_asset_amount + $bytes_per_gb_asset * $gb_asset_amount)` directly from `data_feed[[oracles=...,feed_name='GBYTE_USD_MA_2019_04_30']]` [5](#0-4) , and in `fundraising_proxy.oscript` where a payout share depends on `balance[$destination_aa][base]` and pooled totals that other triggers can move before finalization [6](#0-5) .

Unlike Ethereum, where a caller can at least bound worst-case slippage to a single block via `deadline`/`minAmountOut`, oscript's trigger message format provides no reserved, protocol-enforced field for "abort unless payout >= X" — this must be manually implemented by the AA author using `trigger.data`, and the AA engine offers no default protection, guidance-enforced pattern, or built-in primitive comparable to Uniswap's `amountOutMinimum`.

### Impact Explanation
Any trigger sender interacting with an oracle-priced or balance-ratio-priced AA (asset issuance-for-bytes swaps, fundraising proportional payouts, prediction-market payouts, etc.) can receive a payout that is worse than expected at composition time, with the difference effectively captured by whichever party benefits from the changed exchange rate or ratio (a competing trigger sender, or an oracle operator/relayer with visibility into pending price changes). This is a concrete AA fund loss for the trigger sender — the counterpart-side impact explicitly listed as in-scope (AA fund loss). Because these payment-for-payout AA patterns are the officially documented/recommended way to build exchanges on top of oscript, the exposure is systemic to any AA author who does not manually re-implement slippage checks.

### Likelihood Explanation
Likelihood is high for any actively used oracle-priced or pooled-ratio AA: oracle updates and competing triggers occur routinely and are visible pre-stabilization in `storage.assocUnstableMessages`/`assocUnstableUnits`, meaning a well-positioned participant (including the oracle operator itself, or a bot watching unstable DAG state) can observe an unfavorable/favorable rate shift before the victim's trigger stabilizes and can react (e.g., withhold vs. rush their own competing trigger) without needing any privileged network position — this only requires normal unit-posting capability.

### Recommendation
Add an oscript-level, first-class mechanism for trigger senders to bound outcome risk, e.g. allow the trigger's `data` payload to carry an author-agnostic minimum-expected-output convention that the engine surfaces to the formula (similar to `min_mci` already supported for `data_feed[[...]]`), and update the official AA templates/documentation to require or default to bounce-on-slippage checks (e.g. `if (computed_amount < trigger.data.min_amount) bounce('slippage');`) for any AA that prices outputs from data feeds or shared pool balances. Short of a language-level primitive, ship the recommended bounce-check pattern in the reference documentation/templates (including `futures_contract.oscript` and `fundraising_proxy.oscript`) so AA authors and wallet/bot builders implement consistent protection, mirroring the guidance ultimately adopted for `FeeCollector.claimFees`.

### Proof of Concept
1. AA author deploys an oscript AA modeled on `test/samples/futures_contract.oscript`, which pays out bytes computed from `data_feed[[oracles=ORACLE, feed_name='RATE']]` [7](#0-6) .
2. Trigger sender observes `RATE = R1` in the currently stable data feed and composes/broadcasts a trigger unit sending assets, expecting a payout computed with `R1`.
3. Before the trigger unit's MCI stabilizes, the oracle (or an actor who front-runs by delaying propagation) posts a new `RATE = R2` unit that gets included with an earlier/equal `latest_included_mc_index`; per `readDataFeedValue`'s "last" resolution logic [8](#0-7) , `R2` is what gets used once the trigger's MCI (`handleAATriggers`) finally executes [1](#0-0) .
4. The trigger sender's response unit is composed using `R2`, yielding a payout different (lower) than what they expected when broadcasting under `R1`, with no way to have specified `min_amount` to force a bounce, since no such reserved trigger field/check exists in the base engine.

function readDataFeedValue(arrAddresses, feed_name, value, min_mci, max_mci, unstable_opts, ifseveral, timestamp, handleResult){
	var bLimitedPrecision = (max_mci < constants.aa2UpgradeMci);
	var start_time = Date.now();
	var objResult = { bAbortedBecauseOfSeveral: false, value: undefined, unit: undefined, mci: undefined };
	var bIncludeUnstableAAs = !!unstable_opts;
	var bIncludeAllUnstable = (unstable_opts === 'all_unstable');
	if (bIncludeUnstableAAs) {
		var arrCandidates = [];
		for (var unit in storage.assocUnstableMessages) {
			var objUnit = storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit];
			if (!objUnit)
				throw Error("unstable unit " + unit + " not in assoc");
			if (!objUnit.bAA && !bIncludeAllUnstable)
				continue;
			if (objUnit.sequence !== 'good')
				continue;
			if (objUnit.latest_included_mc_index < min_mci || objUnit.latest_included_mc_index > max_mci)
				continue;
			if (_.intersection(arrAddresses, objUnit.author_addresses).length === 0)
				continue;
			storage.assocUnstableMessages[unit].forEach(function (message) {
				if (message.app !== 'data_feed')
					return;
				var payload = message.payload;
				if (!ValidationUtils.hasOwnProperty(payload, feed_name))
					return;
				var feed_value = payload[feed_name];
				if (value === null || value === feed_value || value.toString() === feed_value.toString())
					arrCandidates.push({
						value: string_utils.getFeedValue(feed_value, bLimitedPrecision),
						latest_included_mc_index: objUnit.latest_included_mc_index,
						level: objUnit.level,
						unit: objUnit.unit,
						mci: max_mci // it doesn't matter
					});
			});
		}
		if (arrCandidates.length === 1) {
			var feed = arrCandidates[0];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			if (ifseveral === 'last')
				return handleResult(objResult);
		}
		else if (arrCandidates.length > 1) {
			if (ifseveral === 'abort') {
				objResult.bAbortedBecauseOfSeveral = true;
				return handleResult(objResult);
			}
			arrCandidates.sort(function (a, b) {
				if (a.latest_included_mc_index < b.latest_included_mc_index)
					return -1;
				if (a.latest_included_mc_index > b.latest_included_mc_index)
					return 1;
				if (a.level < b.level)
					return -1;
				if (a.level > b.level)
					return 1;
				if (bIncludeAllUnstable) // still ambiguous, sort randomly (it's OK outside AAs)
					return 1;
				throw Error("can't sort candidates "+a+" and "+b);
			});
			var feed = arrCandidates[arrCandidates.length - 1];
			objResult.value = feed.value;
			objResult.unit = feed.unit;
			objResult.mci = feed.mci;
			return handleResult(objResult);
		}
