Confirmed: `repository.owner.login` (used to select the GitHub App / webhook secret) and `repository.full_name` (used by every event handler to locate and act on the stack) are two independent, attacker-controlled JSON fields in the same unauthenticated request body, and the signature-verification bypass (`return true unless webhook_secret` in `lib/shipit/github_app.rb`) makes the org-selection field trivially exploitable when any configured organization has no `webhook_secret` set — an explicitly documented "optional" setting.

### Title
Cross-Organization Webhook Spoofing via Signature-Verification Bypass on Unconfigured Organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which `GitHubApp` (and thus which webhook secret) to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), a field taken directly from the unauthenticated, attacker-controlled JSON body. Every actual event handler (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, PR handlers, etc.) instead resolves the target repository/stack using the *different* field `repository.full_name`. Because `GithubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically verified, an attacker who knows of any configured GitHub organization that has no webhook secret set can forge a payload whose `repository.owner.login`/`organization.login` names that unsecured org while `repository.full_name` names a repository belonging to a fully secured organization, bypassing signature verification entirely and driving handlers against the victim organization's stacks.

### Finding Description
`verify_signature` computes the org used for verification purely from the request body: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization:)` looks up the per-org config, and `GitHubApp#verify_webhook_signature` **short-circuits to `true` whenever no `webhook_secret` is configured** for that org: [3](#0-2) 

The setup docs explicitly describe the webhook secret as **optional** and support multiple independently-configured organizations: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `create` hands the entire raw body to the event handlers, unrelated to whatever "verified" org was used: [6](#0-5) 

Every handler resolves its target repository from `repository.full_name`, not `repository.owner.login`: [7](#0-6) [8](#0-7) 

This breaks the binding: **organization authenticated (`repository.owner.login`/`organization.login`) ≠ repository actually written to (`repository.full_name`)**. The two fields are never cross-checked, and the signature that supposedly binds them together is bypassed entirely whenever the "authenticating" organization has an empty `webhook_secret`.

### Impact Explanation
An unprivileged external attacker with network access to the public `/webhooks` endpoint (no GitHub credentials, no Shipit session, no API token required) can:
1. Identify (or guess) that a Shipit deployment hosts multiple GitHub organizations, one of which has no `webhook_secret` configured (an explicitly supported/optional configuration per `docs/setup.md`).
2. Send a crafted POST to `/webhooks` with `X-Github-Event: push` (or `pull_request`, `membership`, `status`, etc.), setting `repository.owner.login` to the unsecured org and `repository.full_name` to a repository belonging to a different, fully-secured organization.
3. Because `verify_webhook_signature` returns `true` for the unsecured org regardless of the actual HMAC, `verify_signature` passes and the handler processes the payload against the victim org's stack, e.g. triggering `GithubSyncJob` (`PushHandler#process` → `stack.sync_github`), archiving/unarchiving review stacks, or creating spoofed PR/label state — all without ever possessing the victim org's real webhook secret.

This is a cross-organization write into another tenant's stack/task state driven entirely by forged, unauthenticated webhook data, satisfying the "unauthorized deploy/rollback" and "cross-repository writes" high/critical impact bar.

### Likelihood Explanation
Requires only: (a) a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration), and (b) at least one of those organizations left without a webhook secret (explicitly documented as optional). No credentials, no GitHub App private key, and no valid HMAC signature are needed by the attacker — a single crafted HTTP POST suffices.

### Recommendation
After signature verification, re-derive the organization from `repository.full_name` (or otherwise validate that `repository.owner.login`/`organization.login` matches the owner segment of `repository.full_name`) before processing the payload, and require handlers to reject events whose declared owner does not match the actually-verified organization. Alternatively, disallow `webhook_secret` from being blank when multiple organizations are configured, so verification cannot be silently skipped for any tenant.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `unsecured_org` (no `webhook_secret`) and `victim_org` (`webhook_secret: real-secret`), each with a stack tracking a real repository, e.g. `victim_org/app`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured_org" },
    "full_name": "victim_org/app"
  }
}
```
No `X-Hub-Signature` header (or an arbitrary value) is required — `verify_signature` resolves `Shipit.github(organization: 'unsecured_org')`, whose `verify_webhook_signature` returns `true` unconditionally per [3](#0-2) .
3. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim_org/app')` per [7](#0-6)  and enqueues `GithubSyncJob` for `victim_org`'s stack with an attacker-chosen `expected_head_sha`, despite the request never being signed by `victim_org`'s webhook secret.
