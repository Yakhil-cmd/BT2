### Title
Arbiter contract hash uses an unfiltered delimiter, allowing field-splitting collisions between different contract terms - (File: arbiter_contract.js)

### Summary
`getHashSrc()` in `arbiter_contract.js` builds the contract hash by joining `title`, `text`, `creation_date`, `payer_address`, `payer_name`, `arbiter_address`, `payee_address`, `payee_name`, `amount`, and `asset` with a fixed delimiter string `exports.DELIMITER = "[|#|]"`, and none of the free-text, attacker/peer-influenced fields (`title`, `text`, `my_party_name`/`peer_party_name`) are checked for containing that delimiter before being concatenated. [1](#0-0) [2](#0-1)  This is the same bug class as the hyper header-injection advisory: values are serialized into a delimited format without escaping/rejecting the delimiter, so a value can "split" the message and be reinterpreted as different fields.

### Finding Description
`getHashSrc(contract)` concatenates `contract.title`, `contract.text`, `contract.creation_date`, `payer_address`, `payer_name`, `contract.arbiter_address`, `payee_address`, `payee_name`, `contract.amount`, `contract.asset` using `exports.DELIMITER` for contracts created after `NEW_HASH_DATE` [3](#0-2) . `getHash()` then just SHA-256s this joined string to produce the `contract.hash` used everywhere as the canonical contract identifier (stored, sent to the peer, used to derive the shared address's oscript definition via `"CONTRACT_" + contract.hash` data-feed keys in `deriveSharedAddress()`, and shown/relied upon by the arbiter and arbstore during dispute resolution) [4](#0-3) [5](#0-4) .

Unlike `string_utils.getSourceString()`, which explicitly throws if any string component contains the join character before hashing [6](#0-5) , and unlike the data-feed validators in `validation.js`/`aa_validation.js` which explicitly reject `\n` in feed names/values to avoid exactly this kind of delimiter-splitting in the `df\n...` kv-store key scheme [7](#0-6) [8](#0-7) , `getHashSrc()` performs no such check on `title`, `text`, or the party names. These fields are free-form text supplied by either counterparty (`objContract` is populated from UI/peer-supplied data via `createAndSend`/`store`), so a party can embed the literal bytes `[|#|]` inside `title` or `text` to make the concatenation of one set of field values produce the exact same joined source string (and thus the exact same SHA-256 hash) as a different combination of field values.

### Impact Explanation
The contract `hash` is the single value the peer, cosigners, and — critically — the arbiter/arbstore use to identify "which contract" a dispute or resolution concerns (`CONTRACT_<hash>` / `CONTRACT_DONE_<hash>` data-feed keys gate the payout oscript in `deriveSharedAddress()` at lines 475-492). Because the hash does not uniquely bind to the semantic content when the delimiter can be injected, a malicious counterparty could construct two textually-different contracts (e.g., different `text`/`amount` claims sent to the peer vs. to the arbiter) whose `getHashSrc()` output — and therefore `getHash()` — collide, letting them present a contract with one set of terms to their peer for the payer side while the arbiter's stored/encrypted contract snapshot (from `openDispute`, which independently forwards `title`/`text`/party names) legitimately differs, undermining the arbiter's ability to verify contract terms unambiguously and enabling a dispute-resolution based fund release under manipulated terms. This affects genuine peer-to-peer fund flow (the shared address holding real payment, gated on oscript conditions keyed by this hash), which is in-scope wallet/contract message handling reachable by an unprivileged counterparty.

### Likelihood Explanation
Any user entering the `title` or `text` field for an arbiter contract offer can trivially include the literal string `[|#|]` (it's ordinary printable text, not restricted by any input validation shown in `createAndSend`/`store`). No special privileges are needed — this is reachable by any wallet user initiating or responding to an arbiter contract.

### Recommendation
Reject (or escape) occurrences of `exports.DELIMITER` within `title`, `text`, and party-name fields before computing `getHashSrc()`, mirroring the approach already used in `string_utils.getSourceString()` (throw/reject on delimiter presence) or in the data-feed validators (reject if the value contains the reserved character).

### Proof of Concept
1. Party A crafts `objContract` where `title = "Short deal[|#|]cheaptext[|#|]2024-01-01[|#|]<payer_addr>[|#|]Alice[|#|]<arbiter_addr>[|#|]<payee_addr>[|#|]Bob[|#|]100[|#|]base"` (embedding the delimiter and forged trailing fields) while the remaining real fields (`text`, `creation_date`, addresses, `amount`, `asset`) are chosen so that the full joined string in `getHashSrc()` reproduces the same byte sequence as a legitimate, differently-priced contract B.
2. `getHash()` on both objects yields the identical SHA-256 digest despite different intended terms (e.g., different `amount`/`asset`), because `getHashSrc()` never rejects delimiter-containing `title`/`text` values, at `arbiter_contract.js` lines 199-207.
3. Party A sends the "colliding" version to the peer/arbiter, exploiting the shared `contract.hash` used across `deriveSharedAddress()`'s oscript conditions and the arbiter dispute API, to make the arbiter/arbstore's record and the peer-visible contract terms diverge while carrying the same identifying hash.

```javascript
function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
```
