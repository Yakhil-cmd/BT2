### Title
Missing `return` after hash-computation error causes double processing / double callback of a private-payment chain - ([File: network.js])

### Summary
`handleSavedPrivatePayments()` in `network.js` iterates over queued private-payment chains (each supplied by a private-payment counterparty or forwarded via a paired device/hub) and, for each one, calls an inner `validateAndSave()` closure. When the head element's payload hash computation throws, the `catch` block deletes the pending record and invokes the `async.each` iteratee callback `cb()`, but execution then falls through (no `return`) into the code that computes `key` (using the now-`undefined` `json_payload_hash`) and calls `privatePayment.validateAndSavePrivatePaymentChain()` a second time on the very same element, which itself will call `cb()` again on completion.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` processes an array of stored, attacker-supplied private-payment chains fetched from `unhandled_private_payments` (populated from `handleOnlinePrivatePayment`, reachable from a private-payment counterparty or via paired-device/hub forwarding): [1](#0-0) 

```
async.each( // handle different chains in parallel
    rows,
    function(row, cb){
        ...
        var validateAndSave = function(){
            var objHeadPrivateElement = arrPrivateElements[0];
            try {
                var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
            }
            catch (e) {
                console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
                if (ws)
                    sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
                deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
            }
            var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
            privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
        };
``` [2](#0-1) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g. because a crafted `payload` object is not serializable in the form `getBase64Hash` expects), the `catch` block schedules an async delete (`deleteHandledPrivateChain(..., cb)`), but there is **no `return` statement**. Execution continues synchronously past the `catch`, builds a `key` containing the literal string `"undefined"`, and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` a second time for the same crafted element — even though this attempt is known to be malformed. That second call's `ifOk`/`ifError` callback also ends by calling `deleteHandledPrivateChain(..., cb)`, i.e. `cb` (the `async.each` iteratee callback) is invoked twice for the same row.

This is structurally analogous to the Envoy bug class: a single message that packages a first “sub-item” whose handling completes/tears down shared per-item state (here: the `cb` callback contract and the DB row via `deleteHandledPrivateChain`), while the code unconditionally continues to process the same message as if the first handling never happened, re-entering another asynchronous completion path (`validateAndSavePrivatePaymentChain`) that also releases/uses the shared resource (`cb`) a second time.

### Impact Explanation
`async.each`'s per-item callback (`cb`) has a single-invocation contract; the underlying `async` library detects and throws on a callback invoked more than once ("Callback was already called"). Because this call site is not wrapped defensively, a double-callback triggered by an attacker-controlled malformed private-payment chain results in an unhandled exception inside `handleSavedPrivatePayments`, which is invoked repeatedly whenever new private payments are queued (from private-payment counterparties, textcoin claims, or paired-device forwarding). This can crash/hang the wallet-node's private-payment processing path, effectively freezing (denial of further processing for) legitimate private payments queued in `unhandled_private_payments`, since the crash occurs before `unlock()` is reached and before other queued rows in the same batch are processed, and the malformed row is never cleanly finished (it may be deleted once but the enclosing batch never completes normally, leaving `mutex` lock state for `"saved_private"` and the outer callback chain in an inconsistent condition).

### Likelihood Explanation
Any counterparty in a private payment (or a device forwarding textcoin/private-payment chains) can supply the `payload` of the head private element with content that is well-formed enough to pass the initial array/object shape checks in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment` (which check for `isNonemptyObject(e.payload)` etc.) but that still causes `objectHash.getBase64Hash()` to throw (e.g., unexpected nested value types that the hashing code doesn't tolerate). This does not require any privileged or hub/node-level access — an ordinary wallet user sending a crafted private-payment chain to another wallet is sufficient to trigger the code path once the recipient processes its `unhandled_private_payments` queue.

### Recommendation
Add a `return;` after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `validateAndSave()` in `network.js`, so that once the hash computation fails and the chain is deleted (and `cb` invoked), execution does not continue to call `privatePayment.validateAndSavePrivatePaymentChain()` a second time on the same data:
```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, consider guarding all `async.each`/`async.eachSeries` iteratee callbacks throughout this file against double invocation (e.g., via a one-shot wrapper) to prevent similar "process-after-teardown" bugs when malformed but structurally valid data reaches these batch-processing loops.

### Proof of Concept
1. As device A (a private-payment counterparty of device B), construct a private-payment chain `arrPrivateElements` whose head element's `payload` passes the shape checks in `handlePrivatePaymentChains` (`isNonemptyObject`, `isNonemptyString(asset)`, non-empty `inputs`/`outputs` arrays of objects) but contains a value that causes `objectHash.getBase64Hash(payload, true)` to throw (for example, a deeply-nested or otherwise unsupported value type inside `outputs`/`inputs` that the hashing routine cannot process, based on the exact type constraints of `object_hash.js`).
2. Send this chain to device B via the normal private-payment/device-message flow so that it is queued into B's `unhandled_private_payments` table (or delivered such that `handleSavedPrivatePayments` processes it directly).
3. When B's node calls `handleSavedPrivatePayments()`, the row is picked up, `getBase64Hash` throws inside `validateAndSave()`, the `catch` block deletes the row and calls `cb()`, but without a `return` the function proceeds to call `privatePayment.validateAndSavePrivatePaymentChain()` again, which upon completion calls `cb()` a second time — triggering the `async` library's double-callback error and crashing/hanging B's private-payment processing.

Note: I was not able to fully verify from the indexed code exactly which payload shapes cause `objectHash.getBase64Hash()` to throw (the object_hash.js implementation details were not fully retrievable through the available search), so the precise crafted payload needed for step 1 could not be confirmed with full certainty — a Devin session with full repository access would be needed to construct and validate a concrete reproducer.
