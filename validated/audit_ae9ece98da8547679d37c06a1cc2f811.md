### Title
Cross-organization webhook forgery — signature verified against `repository.owner.login`, but write target resolved from independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a request against using one field of the attacker-supplied JSON body (`repository.owner.login`, falling back to `organization.login`), while every event handler (`PushHandler`, the `PullRequest::*Handler`s, `MergeRequest#merge!`, etc.) determines which `Stack`/`Repository` actually gets written to using a **different, independently-controlled** field of the same body: `repository.full_name`. GitHub's real payloads always keep these fields consistent, but nothing in the code enforces that. This is the same bug class as the reported `pairTransferERC20From()` issue: a field that gates the authorization check (`variant`/`repository.owner.login`) does not match the field describing the asset actually acted upon (the ERC1155 token/`repository.full_name`).

### Finding Description

It picks the app/secret with: [2](#0-1) 

and verifies via `GitHubApp#verify_webhook_signature`, which **skips verification entirely if the resolved organization has no `webhook_secret` configured**: [3](#0-2) 

Once verification passes (or is skipped), the raw parsed `params` (the full, attacker-controlled JSON body) are handed unchanged to the handler: [4](#0-3) 

Every handler then resolves the *actual* repository/stack to act on from a **separate** field, `repository.full_name`, with no cross-check against the `repository.owner.login`/`organization.login` used for verification: [5](#0-4) [6](#0-5) 

`Repository.from_github_repo_name` independently splits `full_name` on `/` and looks the repo up directly, with no relation to the org used for the signature check: [7](#0-6) 

`PushHandler#process` triggers `sync_github` (which fetches new commits and can advance continuous delivery/deploys) purely off this looked-up stack, and pull-request handlers similarly locate the repo/stack via `params.repository.full_name` to archive/unarchive review stacks or update pull-request records, and `MergeRequest#merge!` (reached via `ProcessMergeRequestsJob`) will call the GitHub API to merge a pull request for whatever stack/repo the merge-queue processing finds.

**The broken binding is:** *organization that authenticated the webhook* (`repository.owner.login` / `organization.login`, used to pick a `GitHubApp`/secret) **must equal** *the repository whose Stack is written to* (derived from `repository.full_name`). Nothing enforces this equality.

**Concretely exploitable path:** If a Shipit instance is configured with multiple GitHub organizations (as `docs/setup.md`/`config/secrets.*.yml` explicitly support), and even one configured organization has no `webhook_secret` set (an optional field per the setup docs), then `verify_webhook_signature` unconditionally returns `true` for any payload whose `repository.owner.login`/`organization.login` names that unsecured organization — regardless of the actual signature header. An attacker with no credentials at all can then POST a forged webhook to the single, shared `/webhooks` endpoint with:
- `repository.owner.login` (or `organization.login`) = the unsecured org (to bypass verification), and
- `repository.full_name` = `"<victim-org>/<victim-repo>"` (a completely different, properly-secured org's repository)

Because the handler resolves its target purely from `repository.full_name`, the forged event is processed as if it legitimately originated from the victim organization's repository, even though the signature check never touched that organization's secret at all.

### Impact Explanation
This crosses a real authentication boundary the same way as the analog ERC1155 bug crosses an asset-variant boundary: the check verifies one entity, but the action is performed on a different one. Consequences on the victim's properly-secured stack include:
- Forcing spurious `GithubSyncJob`/`CacheDeploySpecJob` runs and continuous-delivery triggers on the victim's stack (`Stack#sync_github`, `Stack#trigger_continuous_delivery`), i.e. unauthorized deploy triggering.
- Forging `pull_request` events to archive/unarchive review stacks or overwrite cached PR state (`ReviewStackAdapter`, `PullRequest::*Handler`).
- Influencing merge-queue state (statuses/check_runs webhook spoofing) that feeds `MergeRequest#reject_unless_mergeable!`/`merge!`, which calls `stack.github_api.merge_pull_request(...)` using the app's installation token — i.e., an unauthorized merge on the victim repository.

This matches the "unauthorized deploy, rollback or merge" Critical impact bucket, achieved with zero credentials against the shared multi-tenant webhook endpoint.

### Likelihood Explanation
Requires only that: (1) the Shipit instance is configured for more than one GitHub organization (explicitly documented/supported: `docs/setup.md`, `config/secrets.development.shopify.yml`), and (2) at least one of those configured organizations has no `webhook_secret` set — a state the code explicitly tolerates by design (`return true unless webhook_secret`). No token, session, or private key is needed; the endpoint (`WebhooksController`) skips CSRF and has no other authentication.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret is consistent with the repository owner encoded in `repository.full_name` before dispatching to handlers, e.g. reject the request if `repository.owner.login` (or the derived org) does not match the owner segment of `repository.full_name`. Additionally, do not allow signature verification to silently succeed (`return true unless webhook_secret`) for any configured organization when the instance hosts multiple organizations — require an explicit secret per org, or scope handler dispatch strictly to the organization that was actually verified.

### Proof of Concept
Given a multi-org `secrets.yml` where `orgA` has `webhook_secret: <configured>` and `orgB` has no `webhook_secret`:

```
POST /webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=anything   # ignored because orgB has no webhook_secret

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha claimed to exist>",
  "repository": {
    "owner": { "login": "orgB" },       // used only for signature-org selection -> bypassed
    "full_name": "orgA/victim-repo"     // used to resolve the actual Stack to act on
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "orgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-83`). The request proceeds to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("orgA/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`, `app/models/shipit/repository.rb:53-56`) and calls `stack.sync_github(...)` on `orgA`'s real, properly-secured stack — despite the request never being verified against `orgA`'s secret.

Note: I could not find code that enforces owner/full_name consistency anywhere in the webhook or handler pipeline; this was verified by tracing every handler's repository-resolution method (`repository_name`/`params.repository.full_name`) back to `WebhooksController#verify_signature`'s independent `repository_owner` method.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
