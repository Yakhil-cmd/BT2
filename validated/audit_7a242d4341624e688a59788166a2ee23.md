### Title
`ReopenedHandler#unarchive?` shares `OpenedHandler#provision?`'s operator-precedence bug, allowing PR reopen to bypass `review_stacks_enabled` and re-trigger provisioning - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` uses the identical flawed boolean expression as `OpenedHandler#provision?`: `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Because `&&` binds tighter than `||` in Ruby, the `review_stacks_enabled` check only gates the first disjunct, so an attacker whose repository has `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (defaults are enum-based, not requiring `review_stacks_enabled`) can reopen a PR to unarchive/re-provision a stack even when `review_stacks_enabled` is false.

### Finding Description
The claimed binding is: `unarchive? == true` should require `repository.review_stacks_enabled == true` in all cases. Tracing `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb:70-75`:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Due to Ruby precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. The second and third disjuncts never reference `review_stacks_enabled`, so if `provisioning_behavior` is `allow_with_label` (attacker adds the provisioning label to their own PR) or `prevent_with_label` (attacker simply omits the label — the default state for a new PR), `unarchive?` returns `true` regardless of `review_stacks_enabled`.

`process` (line 41-45) calls `stack.unarchive!` unconditionally when `respond_to_pull_request_reopened?` is true, which delegates to `ReviewStackAdapter#unarchive!` [1](#0-0) . Notably, if no stack exists yet, `unarchive!` calls `create!`, which runs `scope.create!(stack_attributes)` and enqueues the stack for provisioning via `Shipit::ReviewStackProvisioningQueue.add(stack)` [2](#0-1) . If a stack exists and is archived, it removes it from any queue, unarchives it, and re-adds it to the provisioning queue [3](#0-2) . Provisioning then proceeds via `ReviewStackProvisioningQueue`/`ProvisioningHandler`, which is the same downstream `Command`/`PTY.spawn` chain used for `OpenedHandler`.

This is confirmed to be the same class of bug as `OpenedHandler#provision?`, which has an identical operator-precedence structure [4](#0-3) , and the pattern also recurs in `LabeledHandler`/`UnlabeledHandler` (`provisioning_behavior_allow_with_label` / `prevent_with_label` grep matches). No signature verification, `ExplicitParameters` schema, or model validation blocks this — the params schema only validates payload shape/types, not that `review_stacks_enabled` gates provisioning [5](#0-4) . `Repository#review_stacks_enabled` and `provisioning_behavior` are independent, unrelated columns with no cross-field validation enforcing the intended "AND" relationship [6](#0-5) , so the divergence is real: an operator intending `review_stacks_enabled == false` to always suppress provisioning/unarchiving is not what the code enforces when `provisioning_behavior` is `allow_with_label` or `prevent_with_label`.

The attacker's exact action: open a PR (creating the archivable stack scenario requires an operator to have first allowed opening — but per the companion `OpenedHandler` bug, the attacker can already create a stack the same way), have it closed/archived by an operator remediation, then send a webhook with `action: "reopened"` for the same PR number. As long as `provisioning_behavior` is `allow_with_label` (with the label present) or `prevent_with_label` (with the label absent — the default), `unarchive?` returns true and the stack un-archives and re-enters the provisioning queue, regardless of `review_stacks_enabled`.

### Impact Explanation
This allows an unprivileged GitHub user (anyone who can open/label/reopen a PR against a tracked repository, or send a forged-looking `reopened` payload if signature verification is bypassable — that part is out of scope of this specific question but the precedence bug itself is confirmed) to re-provision/un-archive a `ReviewStack` after an operator has archived it, without `review_stacks_enabled` ever being true. Provisioning ultimately drives `ProvisioningHandler`/`Command`/`PTY.spawn` execution on the deploy host, matching the Critical RCE category. This also creates a persistence/remediation-bypass angle: archiving a stack (a common incident response action) does not stop the attacker from repeatedly reopening the PR to re-trigger the same unauthorized provisioning.

### Likelihood Explanation
Preconditions: the target repository must be tracked by Shipit (`Shipit::Repository.from_github_repo_name` must resolve) and have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` (not the default-safe combination of `review_stacks_enabled: false` with `allow_all`, which is the only combination the bug does not affect). This mirrors the `OpenedHandler` bug's likelihood profile exactly — same misconfiguration surface, same attacker capability (open/label/reopen a PR), repeatable indefinitely against the same PR/stack.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `OpenedHandler#provision?` and audit `LabeledHandler`/`UnlabeledHandler` for the identical pattern.

### Proof of Concept
Minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` style, extending existing fixtures already present in the repo):
```ruby
test "does not unarchive stacks when review_stacks_enabled is false, even with prevent_with_label default" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :prevent_with_label, provisioning_label_name: "pull-requests-label")

  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = [] # label absent -> prevent_with_label condition true

  assert_equal false, repository.review_stacks_enabled
  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  # Binding under test: review_stacks_enabled == false should imply archived? stays true
  assert stack.reload.archived?, "Stack should remain archived since review_stacks_enabled is false"
end
```
Currently this assertion fails (stack un-archives) because `unarchive?` evaluates the `prevent_with_label` branch independent of `review_stacks_enabled`, demonstrating the bug.
