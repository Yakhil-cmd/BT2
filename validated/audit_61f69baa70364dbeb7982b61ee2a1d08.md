### Title
GitHub username reuse lets `MembershipHandler` bind organization-team membership to the wrong `Shipit::User`, decoupling `Shipit.github_teams` authorization from the `github_id` that OAuth login actually verifies - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
### Finding Description
Shipit resolves a user's identity in two different, non-equivalent ways:

- On OAuth login, `GithubAuthenticationController#sign_in_github` binds the session to a `User` looked up/created by the immutable numeric `github_id`: `User.find_or_create_from_github(auth.extra.raw_info)` → `find_from_github` → `find_by(github_id: github_user.id)`. [1](#0-0) [2](#0-1) 

- Team authorization (`current_user.authorized?`, gating access to the whole engine per `Shipit.github_teams`) is derived from `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, i.e. from `Membership` rows attached to a specific `User` row. [3](#0-2) 

- But those `Membership` rows are created by the `membership` webhook handler using a completely different, *mutable* identity key: the GitHub `login` string, via `User.find_or_create_by_login!(params.member.login)`. [4](#0-3) [5](#0-4) 

This is the same bug class as the AA-wallet report: the engine assumes that "the identity that authenticates a session" (`github_id`) is always the same as "the identity that a downstream trust decision is written to" (`login`). GitHub allows accounts to rename their `login`, and once a `login` is freed it can be claimed by a different account. `find_or_create_by_login!` performs `find_or_create_by!(login:)`, so if a `Shipit::User` row already exists with that `login` (created earlier from an OAuth login, a commit-author lookup, or a previous membership event), any new `membership` webhook event referencing that `login` string is silently applied to the *pre-existing row*, regardless of which real GitHub account (i.e., which `github_id`) currently owns that username. The webhook signature only proves that GitHub sent this exact payload at delivery time (`WebhooksController#verify_signature` / `GitHubApp#verify_webhook_signature`); it says nothing about whether the `login` field still designates the same real-world identity as when the corresponding `Shipit::User` row was created. [6](#0-5) [7](#0-6) 

The equality the engine implicitly (and incorrectly) relies on is:

`User row addressed by webhook `login`` == `User row bound to the session via `github_id``

which does not hold once a `login` is reassigned between GitHub accounts, exactly mirroring the report's `msg.sender` (source-chain address) vs. destination-chain AA-wallet-address mismatch.

### Impact Explanation
Because `Team#add_member`/`Membership` rows created off a stale `login` are attached to whatever pre-existing `User` row matches that string, an organization's legitimate, previously-authorized `User` record can be silently re-populated with team memberships that actually belong to a different, currently-controlling GitHub account, and vice-versa: an attacker who claims a `login` formerly used by an authorized team member can, in some ordering of events, cause new `Membership`/`User` state to be attributed under a `github_id` that a session lookup will later match. This directly implicates the "High" impact category of escalation into `Shipit.github_teams` authorization, since `authorized?` is computed purely from `Membership` rows keyed off the fragile `login`-based resolution rather than the `github_id`-based identity the OAuth flow actually verifies. [3](#0-2) 

### Likelihood Explanation
Exploitation only requires: (1) a legitimate, previously-tracked Shipit user to rename their GitHub `login` (a routine, self-service GitHub action), and (2) an unprivileged attacker to register the vacated `login`. No Shipit credentials, `webhook_secret`, or repository write access are needed by the attacker — they only need control of a GitHub account with the reused username; the `membership` webhook itself is fired by GitHub for legitimate org events. Because Shipit stores/looks up users primarily by `login` in this codepath while treating `github_id` as authoritative elsewhere (`find_from_github`, `refresh_from_github!`), the two identity resolution paths can diverge without any explicit detection or reconciliation logic in the codebase. [8](#0-7) 

### Recommendation
Make `MembershipHandler` (and any other webhook-driven identity resolution such as the `Merge-Requested-By` trailer path in `User.find_or_create_author_from_github_commit`) resolve identity by the stable `member.id` (GitHub's numeric user ID), the same key used by `find_from_github`, instead of `member.login`. The `membership` payload GitHub sends includes a numeric member ID; require and use it so all identity bindings converge on `github_id`, and treat a `login` collision with a different `github_id` as a rename to reconcile, not a match. [9](#0-8) [10](#0-9) 

### Proof of Concept
1. Legitimate user `carol` (`github_id=100`) logs into Shipit at least once; `sign_in_github` creates `Shipit::User#5` with `login: "carol"`, `github_id: 100`, and is added to org team `T` (a `Shipit.github_teams` entry) via a normal `membership` webhook, so `Membership(user_id: 5, team_id: T)` exists. [1](#0-0) 
2. `carol` renames her GitHub account to `carol2`. Shipit's local `User#5.login` remains `"carol"` until an explicit `refresh_from_github!` run. [8](#0-7) 
3. Attacker registers the now-free GitHub username `carol`.
4. Any legitimate `membership` webhook event referencing `member.login: "carol"` (e.g., attacker being added/removed from an unrelated team, or an org resync) is delivered to `/webhooks`, correctly HMAC-verified for the organization. [11](#0-10) 
5. `MembershipHandler#process` calls `User.find_or_create_by_login!("carol")`, which matches the *pre-existing* `User#5` row (the real `carol`'s stable record, `github_id: 100`), not the attacker's actual GitHub identity, and mutates that record's team memberships — attributing/altering `Shipit.github_teams`-relevant `Membership` state under an identity resolved from a mutable string the attacker now controls, rather than the `github_id` that the account's session/OAuth trust is actually anchored to. [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
