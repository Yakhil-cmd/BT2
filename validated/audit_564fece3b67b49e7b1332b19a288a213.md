### Title
Webhook signature verification is scoped to `repository.owner.login`, not to the `repository.full_name` the handlers actually act on, letting an unsigned/unauthenticated payload write state for any tracked repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Just as the Fenix bribe-reassignment bug let a user's stake stay bound to the *old* briber contract instead of the one the vote is now recorded against, Shipit's webhook pipeline lets the entity used to authenticate a payload (the organization derived from `repository.owner.login`/`organization.login`) diverge from the entity the payload is actually applied to (`repository.full_name`, looked up independently by every `Webhooks::Handlers::Handler`). The verified/authenticated key and the acted-upon key are two different payload fields with no cross-check.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the HMAC against using only the organization login: [1](#0-0) [2](#0-1) 

```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` then calls `verify_webhook_signature`, which is a no-op when no secret is configured for that org: [3](#0-2) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

The docs explicitly present `webhook_secret` as *optional* per GitHub App/organization (`docs/setup.md` line 30: "Webhook secret (optional)"), and the shipped example secrets files even ship with `webhook_secret: # nil` as the default value. This means "no signature check for this organization" is a documented, supported configuration state, not a misconfiguration.

Once past `verify_signature`, every handler resolves the record to mutate using a *different* payload field, `repository.full_name`, via `Handler#repository_name`/`Handler#stacks`: [4](#0-3) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

Nothing in `WebhooksController` or `Handler` enforces that `repository.owner.login` (the field used to pick/skip the signature check) is consistent with `repository.full_name` (the field the handler actually uses to find the `Stack`/`Repository` to mutate). Handlers such as `membership`, `push`, `status`, and `check_suite` all act purely on `full_name`/embedded team and member logins: [5](#0-4) 

The `membership` handler creates `Team`/`Membership` rows straight from the payload with no re-verification against the resolved organization, as shown by the controller tests exercising unauthenticated-style flows once `verify_signature` is stubbed: [6](#0-5) 

### Impact Explanation
If any organization configured on the instance (single or as one entry of a multi-org `github:` map) is run with the documented-optional `webhook_secret` unset, `verify_webhook_signature` returns `true` unconditionally for any payload whose `repository.owner.login`/`organization.login` resolves to that organization - regardless of what repository/organization the rest of the payload (`repository.full_name`, `team`, `member.login`, `sha`, `state`) claims to describe. An unauthenticated internet client can then:
- Send a forged `status` event with `full_name` pointing at a fully-secured, unrelated stack, injecting a fake passing `Status`; `MergeRequest#all_status_checks_passed?` and `Stack#deployment_checks_passed?` consume these `Status` rows directly, which can trigger an **unauthorized deploy or an unauthorized merge** via `ProcessMergeRequestsJob#perform` → `merge_request.merge!`.
- Send a forged `membership` event granting an attacker-controlled login membership in an arbitrary `Team`, escalating into `Shipit.github_teams` authorization used for login/session gating.
- Send a forged `push`/`check_suite` event to force `GithubSyncJob`/`RefreshCheckRunsJob` to run against arbitrary tracked stacks.

This lands squarely on the impact list's "unauthorized deploy, rollback or merge" (Critical) and "escalation into `Shipit.github_teams` authorization" (High) categories, achieved by an unprivileged, unauthenticated actor - no session, ApiClient token, or webhook secret is required.

### Likelihood Explanation
Requires only that one configured GitHub organization on the instance is running the explicitly documented "optional" no-webhook-secret mode (or, more narrowly, any signature bypass path in `verify_webhook_signature`/`Shipit.github`), and that the attacker knows or guesses a tracked `repository.full_name` (which is public information - GitHub org/repo names). No credentials, cookies, or private keys are needed; a bare `POST /webhooks` request is sufficient. Likelihood is Medium-High for instances that followed the documented "optional" secret guidance, and the underlying design flaw (signature scoped to `repository_owner`, mutation scoped to `repository.full_name`, no cross-binding) exists regardless of configuration.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than optional per organization; never let `verify_webhook_signature` return `true` when no secret is configured.
- After signature verification succeeds for a given organization, assert that `repository.full_name`'s owner (and any `organization.login`/`team` fields used later) is exactly the organization the signature was verified for, rejecting the payload otherwise.
- Have `Webhooks::Handlers::Handler#repository_name` be fed from the same `repository_owner` value validated by the controller instead of re-deriving it independently from the raw payload.

### Proof of Concept
1. Deploy Shipit with a multi-org (or single-org) `github:` config where one organization, say `weak-org`, has `webhook_secret:` left blank, per `docs/setup.md`'s "optional" guidance, while `victim-org` is fully configured and tracked by Shipit with an active stack `victim-org/critical-repo`.
2. As an anonymous client, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "weak-org" }, "full_name": "victim-org/critical-repo" },
  "sha": "<known deployed/undeployed commit sha of victim-org/critical-repo>",
  "state": "success",
  "context": "ci/required-check",
  "branches": [{"name": "main"}]
}
```
No `X-Hub-Signature` header is required, since `Shipit.github(organization: "weak-org")` resolves to a `GitHubApp` with `webhook_secret` nil, and `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:77`).
3. `WebhooksController#create` dispatches to the `status` handler, which resolves the target via `payload.dig('repository', 'full_name')` = `"victim-org/critical-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:37`), creating a forged passing `Status` on `victim-org`'s commit despite the request never being authenticated for `victim-org`.
4. If `victim-org/critical-repo`'s stack has `merge_queue_enabled` or `continuous_deployment` gated on that status context, the next `ProcessMergeRequestsJob`/deploy scheduler run treats the forged status as legitimate and proceeds to merge/deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
