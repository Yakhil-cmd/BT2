### Title
Webhook signature is bound to the GitHub organization, not to the repository the payload mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to check *only* by the organization name embedded in the JSON body, and once the HMAC matches, the *entire unfiltered body* is handed to event handlers that pick the target repository/commit purely from other, unverified body fields. The signature therefore proves "this request was signed with org X's webhook secret," never "the repository/commit this payload names belongs to org X." Any actor who knows (or legitimately owns) one org's webhook secret can forge events that mutate state belonging to a completely different repository/stack.

### Finding Description
`verify_signature` resolves the signing key exclusively from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

`repository_owner` comes straight from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback), and is used to pick which `GitHubApp`/`webhook_secret` to validate the signature against: [3](#0-2) 

The `webhook_secret` is configured per-organization, not per-repository, in `Shipit.github(organization:)`'s config. Passing this check only proves the request was signed with *some org's* secret — it never verifies that the repository/commit information inside the body actually belongs to that org.

Once `verify_signature` passes, the raw, unrestricted body is dispatched to handlers: [4](#0-3) 

Handlers then resolve the mutated entity purely from body fields with no cross-check against the org that was actually authenticated. For example, `Handler#repository_name`/`#stacks` trust `repository.full_name` verbatim: [5](#0-4) 

Worse, `StatusHandler` doesn't even scope by repository — it matches commits **instance-wide by SHA alone**: [6](#0-5) 

This directly creates a CI status via `Commit#create_status_from_github!`, which feeds `deployable?`/deploy gating logic (`required_statuses`, `blocking_statuses`) used across the deploy flow: [7](#0-6) [8](#0-7) 

and gates the deploy API and continuous delivery: [9](#0-8) [10](#0-9) 

**Broken equality:** `organization authenticated by verify_signature` ≠ `repository/commit acted on by the dispatched handler`. The webhook endpoint verifies a per-org HMAC but blindly trusts unrelated repository/commit identifiers in the same payload to decide what gets written.

### Impact Explanation
An attacker who can produce a validly-signed webhook body for *any one* organization onboarded to the Shipit instance (e.g., because they are the admin who configured that org's `webhook_secret` when wiring up its GitHub integration) can forge a `status` event naming a SHA belonging to a **different** organization's tracked stack. Because `StatusHandler` matches by SHA globally with no repository scoping, this injects a fabricated `success` status on a victim commit, which can flip `Commit#deployable?` to true and bypass `require_ci` gating in `Api::DeploysController#create`, or trigger `Stack#trigger_continuous_delivery` for continuous-deployment-enabled stacks — resulting in an unauthorized deploy of a commit the attacker never had CI or write access to. This matches the Critical "unauthorized deploy" impact category.

### Likelihood Explanation
Exploitation only requires knowledge of one organization's `webhook_secret` used to feed Shipit — a value the org's own integrator necessarily possesses when setting up the webhook, and which is shared across every repository in that org rather than scoped per-repo. No GitHub API access, no push access to the victim repo, and no privileged Shipit account is required; the target commit SHA and required CI context name are ordinarily public/discoverable information.

### Recommendation
- Have handlers cross-validate that `repository.full_name` (and any commit `sha`) actually belongs to the organization/App installation that produced a valid signature, rejecting mismatches.
- Scope `StatusHandler`'s (and similar handlers') commit lookup by the verified repository, not by SHA alone, e.g. `stacks.commits.where(sha: params.sha)` instead of a global `Commit.where(sha: ...)`.
- Prefer verifying via GitHub App installation identity bound one-to-one with the specific repository, rather than an org-wide shared webhook secret, wherever supported.

### Proof of Concept
1. Configure/observe that `attacker-org` is one of the organizations wired to this Shipit instance, and obtain its `webhook_secret` (known to whoever set up that org's integration).
2. Identify a target commit SHA belonging to `victim-org/victim-repo`, a stack tracked by the same Shipit instance, and its required CI `context` (e.g. `ci/travis`).
3. Build a JSON body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/decoy"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/travis"
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org-webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner = "attacker-org"`, validates using that org's secret, and passes — `check.rb` code path never inspects `sha`'s true owner.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim commit regardless of the forged `attacker-org/decoy` repository field, and calls `create_status_from_github!`, marking the victim commit's required CI context as `success`.
7. The victim commit is now `deployable?`, letting an attacker-influenced deploy proceed (e.g., via `require_ci: true` bypass or continuous delivery) despite no legitimate CI success and no access to `victim-org/victim-repo`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
