### Title
Blacklisted correspondent device auto-unblocked ("blackhole" bypass) via unauthenticated pairing message re-send - ([File: device.js])

### Summary
`ocore`'s device pairing handler unconditionally clears the `is_blackhole` flag for any device address that successfully presents a pairing secret, without checking whether that device address was previously blacklisted by the user. This mirrors the external report's bug class ("could ignore per-account disablement... resulting in unauthorized operations") applied to the paired-device message-handling surface.

### Finding Description
`is_blackhole` is the per-correspondent disablement mechanism in ocore: it is set to `1` to stop a device from being able to interact with the user again (e.g. after `removed_paired_device` handling in `wallet.js`, `conf.bIgnoreUnpairRequests` branch sets `is_blackhole=1` instead of fully removing the correspondent): [1](#0-0) 

The flag is enforced only on the *outgoing* path, in `sendMessageToDevice()`, which refuses to deliver messages to a device marked `is_blackhole`: [2](#0-1) 

However, `handlePairingMessage()` — invoked whenever a `pairing` justsaying is received from any device presenting a valid (or permanent `'*'`) `pairing_secret` — unconditionally resets this flag back to `0` for the sending device address, with no check of the previous `is_blackhole` state: [3](#0-2) 

Because a pairing message is one of the very small set of subjects accepted from *unknown or blackholed* correspondents (`arrSubjectsAllowedFromNoncorrespondents = ["pairing", "my_xpubkey", "wallet_fully_approved"]` in the hub message dispatcher, and there is no separate blackhole check gating this path), a device that has already been blacklisted by the user can simply resend a `pairing` message (reusing a still-valid pairing secret it obtained earlier, or the node's permanent pairing secret if one exists) and have its `is_blackhole` flag silently cleared, re-enabling full two-way device-message interaction (signing requests, shared-address negotiation, arbiter-contract messages, textcoin/auth flows, etc.): [4](#0-3) 

This is a direct analog of the CVE's root cause: a policy/authorization state (`is_blackhole`, the per-account disablement) that should gate whether a lower-trust remote party (a paired device) can act is silently overwritten/ignored by another code path (the pairing handler) that a lower-trust caller can trigger on demand.

### Impact Explanation
Re-enabling communication from a device the user explicitly disabled restores the attacker's ability to reach the "sign", "arbiter_contract_shared", "new_shared_address", "approve_new_shared_address" and other device-message handlers in `wallet.js`, which drive real wallet/contract actions (e.g., triggering signing-request UI flows, shared-address/co-signing negotiation, arbiter contract state changes). While most of these still require additional user confirmation or possession of private keys, the vulnerability defeats the explicit trust-revocation mechanism the wallet exposes to end users, exposing them again to social-engineering, spam, and contract/negotiation abuse from a device they intentionally blocked — undermining the wallet/contract message-handling authorization model that `is_blackhole` is meant to enforce.

### Likelihood Explanation
Exploitation only requires the blacklisted device to still hold a previously valid (non-expired) pairing secret, or knowledge of a permanent pairing secret if the victim uses one (`getOrGeneratePermanentPairingInfo`). No additional privileges, keys, or hub cooperation beyond normal message delivery are needed — this is reachable by any paired device acting as a lower-trust counterparty, matching the "paired device" reachability criterion.

### Recommendation
In `handlePairingMessage()`, before resetting `is_blackhole=0`, check the correspondent's current `is_blackhole` state and either (a) refuse to auto-clear it, requiring an explicit user action to un-blacklist, or (b) emit a user-facing event so the wallet can prompt for confirmation instead of silently restoring trust.

### Proof of Concept
1. Device B pairs with device A normally; A obtains B's device address and later blacklists it: `wallet.js` handles `removed_paired_device` with `conf.bIgnoreUnpairRequests` true, setting `is_blackhole=1` for B in `correspondent_devices`. [1](#0-0) 
2. B still possesses a pairing secret it obtained before being blocked (or A's permanent pairing secret).
3. B resends a `pairing` justsaying message to A's hub with `{pairing_secret, device_name}`.
4. A's node processes it via `handlePairingMessage()`, which matches the secret in `pairing_secrets` and unconditionally executes `UPDATE correspondent_devices SET is_blackhole=0 WHERE device_address=?` for B. [3](#0-2) 
5. B is now un-blackholed and `sendMessageToDevice()` will again deliver messages to/from B, restoring full device-message interaction despite A's earlier block. [2](#0-1)

function sendMessageToDevice(device_address, subject, body, callbacks, conn){
	if (!device_address)
		throw Error("empty device address");
	conn = conn || db;
	conn.query("SELECT hub, pubkey, is_blackhole FROM correspondent_devices WHERE device_address=?", [device_address], function(rows){
		if (rows.length !== 1 && !conf.bIgnoreMissingCorrespondents)
			throw Error("correspondent not found");
		if (rows.length === 0 && conf.bIgnoreMissingCorrespondents || rows[0].is_blackhole){
			console.log(rows.length === 0 ? "ignoring missing correspondent " + device_address : "not sending to " + device_address + " which is set as blackhole");
			if (callbacks && callbacks.onSaved)
				callbacks.onSaved();
			if (callbacks && callbacks.ifOk)
				callbacks.ifOk();
			return;
		}
		sendMessageToHub(rows[0].hub, rows[0].pubkey, subject, body, callbacks, conn);
	});
}
