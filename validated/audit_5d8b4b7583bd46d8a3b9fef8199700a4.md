### Title
Webhook signature verification binds to `repository.owner.login`, but stack resolution binds to `repository.full_name` — cross-repository status/push forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which per-organization GitHub App secret to verify a webhook against using `repository.owner.login` from the *same, attacker-writable JSON payload*. Once verified, `Shipit::Webhooks::Handlers::Handler#stacks` resolves the target `Stack`/`Repository` using a **different** field from that same payload, `repository.full_name`. Nothing cross-checks that `full_name`'s owner segment matches `repository.owner.login`. This breaks the equality the deployment-trust model assumes: `organization that authenticated == organization/repository that gets written to`.

### Finding Description
`verify_signature` computes the expected HMAC using the org identified from the payload itself: [1](#0-0) [2](#0-1) 

Meanwhile, every webhook handler resolves the affected stacks purely from `repository.full_name`, with no relation to `repository_owner`: [3](#0-2) [4](#0-3) 

Because Shipit explicitly supports multiple GitHub organizations, each configured with its own `webhook_secret` (see the multi-org example in `docs/setup.md` and `config/secrets.development.shopify.yml`), an attacker who legitimately administers **their own** GitHub organization/App installed on this Shipit instance knows their own org's `webhook_secret` and can freely construct the JSON body sent to `/webhooks`. They can set `repository.owner.login` to their own org (so `verify_signature` selects and validates against a secret they know) while setting `repository.full_name` to `"other-org/other-repo"` — any other repository configured on the same Shipit instance. The HMAC covers the raw JSON bytes they crafted, so the signature check passes, yet the handler acts on a repository outside their organization.

`PushHandler` then triggers `sync_github` (GitHub sync / undeployed-commit tracking) for the target stack based on a forged `after` SHA, and `StatusHandler` creates commit statuses for arbitrary SHAs on any tracked commit matching `params.sha`, for the victim repository: [5](#0-4) [6](#0-5) 

This is a direct analog of the report's binding-mismatch bug class: the report's fork DAO trusted "tokens claimed" without accounting for "tokens actually escrowed" (`adjustedTotalSupply()` vs `remainingTokensToClaim()`); here, Shipit trusts "organization whose secret verified" without checking it equals "organization/repository the handler writes to."

### Impact Explanation
An attacker who controls one legitimately-configured GitHub organization on a multi-org Shipit deployment can forge webhook events (`push`, `status`, `check_suite`, etc.) that are processed as if they came from GitHub for a *different* organization's repositories that they have no legitimate access to. This allows injecting forged commit statuses (`StatusHandler`) and triggering `sync_github`/undeployed-commit recomputation (`PushHandler`) against stacks belonging to other organizations, which can influence merge-queue eligibility, CI status gating for deploys, and continuous-delivery triggers for repositories the attacker does not own — a cross-repository write achieved without any repository or Shipit account access to the target repo.

### Likelihood Explanation
Requires: (1) the Shipit instance be configured for multiple GitHub organizations (an explicitly documented and supported configuration), and (2) the attacker control/administer one of those configured organizations (i.e., know its `webhook_secret`) — which is a normal, low-privilege condition for a "webhook-capable" org owner, not a Shipit account holder. No `ApiClient` token, session, or repository write access on the target repo is required. Single-org deployments (the common case) are not affected because there is only one secret to choose from, but any multi-org Shipit installation is exposed.

### Recommendation
In `WebhooksController#verify_signature`, after verifying, cross-check that `repository_owner` (or `organization.login` for org-level events) is consistent with the repository actually referenced (`repository.full_name`'s owner segment). Alternatively, in `Handler#stacks`, require that the resolved `Repository#owner` match the previously-authenticated `repository_owner`, rejecting the event if they diverge. GitHub's own webhook delivery guarantees this consistency, so the fix should reinstate that guarantee explicitly rather than relying on it implicitly from two independently-read payload fields signed by the same signature.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled, webhook installed with secret `S_A`) and `OrgB` (contains a tracked stack, e.g. `orgb/victim-repo`).
2. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "sha": "<any tracked commit sha in orgb/victim-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using their own known `OrgA` secret.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orga")` (from `repository.owner.login`) and the signature verifies successfully.
5. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching commits belonging to `orgb/victim-repo` — and creates a forged success status on them, even though the attacker only controls `OrgA`.
