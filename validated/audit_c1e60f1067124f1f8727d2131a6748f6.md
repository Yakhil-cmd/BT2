### Title
Cross-organization signature/authorization confusion in webhook dispatch allows attacker-org to mutate victim-org's PullRequest labels - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb)

### Summary
`WebhooksController#verify_signature` derives the signing organization from `repository.owner.login` (or `organization.login`) in the raw JSON body, while `LabelCapturingHandler` (and sibling `pull_request` handlers) resolve the target `Repository`/`Stack` using the completely independent `repository.full_name` field. Because these two attacker-controlled fields are never cross-validated, an attacker who legitimately owns a distinct "attacker-org" GitHub App registered in `Shipit.github` can sign a payload with their own `webhook_secret` while pointing `repository.full_name` at a victim organization's repository, causing the victim's `PullRequest#labels` to be overwritten.

### Finding Description
The broken binding: `organization used to verify HMAC signature (derived from repository.owner.login)` == `organization owning the Repository/Stack whose PullRequest is mutated (derived from repository.full_name)` — this is **false** in the code, and nothing enforces the equality.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and looks up `Shipit.github(organization: repository_owner)` to verify the `X-Hub-Signature` HMAC [2](#0-1) .
2. If the attacker sets `repository.owner.login = "attacker-org"` and signs the raw body with attacker-org's own `webhook_secret`, `verify_webhook_signature` succeeds using attacker-org's `GitHubApp` [3](#0-2) .
3. `WebhooksController#create` then dispatches the same raw, unvalidated hash to `Shipit::Webhooks.for_event('pull_request')`, which includes `LabelCapturingHandler` [4](#0-3) .
4. `LabelCapturingHandler#repository` resolves the target repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, with no reference at all to `repository.owner.login` [5](#0-4) .
5. `Repository.from_github_repo_name` simply splits `full_name` on `/` and does a `find_by(owner:, name:)` lookup — it never checks the JSON's `owner.login` sub-object [6](#0-5) .
6. For an `opened` event, `opened_active_stack?` only requires the resolved `stack` to be present (no archive check needed) [7](#0-6) , matching the precondition of an existing active `ReviewStack` on `victim-org/prod-repo`.
7. `capture_labels` then calls `pull_request.update!(labels: params.pull_request.labels.map(&:name))` on the victim's `PullRequest` record, using the attacker's fully-controlled `labels` array [8](#0-7) .

No guard in `drop_unhandled_event`, `ExplicitParameters` schema (which only `requires :full_name, String` under `repository`, never `owner`) [9](#0-8) , or elsewhere ties the verified organization to the repository being mutated. This is a genuine authorization-binding gap in a codebase that explicitly supports multiple GitHub Apps per organization (`config/secrets.development.shopify.yml`) [10](#0-9) .

### Impact Explanation
An attacker who controls only their own GitHub App/`webhook_secret` for "attacker-org" can forge a valid-signature webhook that mutates `PullRequest#labels` belonging to any other tenant repository ("victim-org/prod-repo") known to have an active `ReviewStack`. Since `ReviewStack#pull_request.labels` drives environment variable injection into deploy/CI commands elsewhere in the codebase (labels map to `stack.env`, as seen in `test/models/shipit/review_stack_test.rb`), this is a cross-tenant write with potential downstream effect on the victim's automated stack behavior — this is a "payload for one repository mutating another's stack" scenario, matching the Critical severity bucket. It is fully repeatable against any repository whose `full_name` the attacker can guess/know, using only credentials the attacker legitimately possesses for their own org.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub Apps/orgs (a documented, supported configuration) [11](#0-10) , (2) attacker owns/registers one such app ("attacker-org") legitimately, (3) victim repository has an active `ReviewStack`, and (4) attacker knows the victim's `repository.full_name`. All of these are realistic in a shared, multi-tenant Shipit deployment; the attacker needs no victim secrets, sessions, or team membership — only their own `webhook_secret`, matching the stated unprivileged-attacker threat model.

### Recommendation
In `WebhooksController#verify_signature`, or in each `pull_request` handler's `repository` resolution, cross-validate that `repository.owner.login` matches the owner segment of `repository.full_name` before trusting either for lookup, and/or resolve the target `Repository`/`Stack` using the same organization value that was used to verify the signature (not an independently attacker-supplied `full_name`). Reject the webhook (422) if these values diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_cross_org_test.rb
require 'test_helper'

module Shipit
  class WebhooksControllerCrossOrgTest < ActionController::TestCase
    tests Shipit::WebhooksController

    test "attacker-org signed payload cannot mutate victim-org's PullRequest labels" do
      # Setup: two GitHubApp configs
      Shipit.stubs(:github).with(organization: 'attacker-org').returns(
        Shipit::GitHubApp.new('attacker-org', webhook_secret: 'attacker-secret')
      )

      victim_stack = shipit_stacks(:review_stack) # victim-org/prod-repo, active, non-archived
      victim_pr = victim_stack.pull_request
      victim_pr.update!(labels: [])

      payload = {
        action: 'opened',
        number: victim_pr.number,
        pull_request: {
          id: 1, number: victim_pr.number, url: 'x', title: 't', state: 'open',
          additions: 1, deletions: 1,
          head: { sha: 'a' * 40, ref: 'feature' },
          user: { login: 'attacker' },
          assignees: [],
          labels: [{ name: 'attacker-controlled-label' }]
        },
        repository: {
          full_name: 'victim-org/prod-repo', # points at victim
          owner: { login: 'attacker-org' }   # used only for signature org lookup
        },
        sender: { login: 'attacker' }
      }.to_json

      signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', payload)

      request.headers['X-Github-Event'] = 'pull_request'
      request.headers['X-Hub-Signature'] = signature

      # Equality claimed by the binding: verifying org == mutated stack's org
      assert_equal 'attacker-org', 'attacker-org' # signature org
      assert_equal 'victim-org', victim_stack.repository.owner # actual mutated org
      # These differ -> binding is broken

      post :create, body: payload, as: :json

      victim_pr.reload
      assert_includes victim_pr.labels, 'attacker-controlled-label' # demonstrates the vuln
    end
  end
end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
