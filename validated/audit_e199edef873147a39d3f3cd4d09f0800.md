### Title
`recalculate_stake_rewards` omits closed stake accounts entirely, causing `EpochRewards` sysvar (`distributed_rewards`) divergence between a restarted and a non-restarted node - (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs`)

### Summary
`recalculate_stake_rewards` (invoked via `recalculate_partitioned_rewards_if_active` on snapshot restore) rebuilds the pending-reward list from the *live* `StakesCache` instead of the frozen state used by `calculate_rewards_for_partitioning` at the epoch boundary. If a stake account with a still-pending reward is closed by its owner before a node restarts, the restarted node's recalculated reward list silently drops that entry, while a non-restarted node keeps the original entry and later marks it "burned" when the account is found missing at distribution time. Both paths differ in how they update the `EpochRewards` sysvar's `distributed_rewards` counter, producing divergent account state and therefore a different bank hash for the same block.

### Finding Description
`calculate_rewards_for_partitioning` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:471-532`) computes the full stake reward list once, at the epoch boundary, from the parent-bank's `StakesCache`, and this list (`all_stake_rewards`) is carried in `Bank::epoch_reward_status` across all subsequent in-memory (non-restarted) blocks until distribution finishes.

`recalculate_stake_rewards` (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1038-1095`), called only via `recalculate_partitioned_rewards_if_active` from `initialize_after_snapshot_restore` (`runtime/src/bank.rs:6063-6084`) after a snapshot restore/restart, rebuilds the same list but sources delegations from `self.stakes_cache.stakes()` at the *current, live* moment via `get_epoch_params_for_recalculation` (`calculation.rs:582-608`, specifically `stakes.stake_delegations_vec()` at line 589). Because `calculate_stake_rewards_and_commissions` only produces an entry for delegations present in `stake_delegations` (`calculation.rs:813-892`), a stake account that has been fully closed (deactivated + withdrawn to zero lamports) between the epoch boundary and the restart is silently absent from the recalculated `all_stake_rewards`/`partition_indices`.

In contrast, on a node that never restarts, the original entry for that same stake account remains in `all_stake_rewards`. When its turn to be distributed arrives, `store_stake_accounts_in_partition` looks up the account from the *live* `StakesCache` (`distribution.rs:361-362, build_updated_stake_reward` at `distribution.rs:239-261`) and, finding it missing, returns `DistributionError::AccountNotFound` (`distribution.rs:29-32`). This is treated as a "burn": the amount is added to `stake_reward_lamports_burned`, not to `stake_reward_lamports_minted`, so capitalization is unaffected — but the burned amount is still folded into the `EpochRewards` sysvar's `distributed_rewards` counter via `update_epoch_rewards_sysvar(stake_reward_lamports_minted + stake_reward_lamports_burned, ...)` (`distribution.rs:200-204`).

For the restarted node, since the closed account's entry was never included at all, its amount never touches `stake_reward_lamports_burned` or `stake_reward_lamports_minted` for any partition — the running `distributed_rewards` field in the on-chain `EpochRewards` sysvar account therefore ends up lower than on the non-restarted node from that block onward. `set_epoch_rewards_sysvar_to_inactive` (`sysvar.rs:113-145`) only asserts `total_rewards >= distributed_rewards` (`sysvar.rs:117`), not that they are equal, so no panic occurs — the discrepancy instead becomes silently-persisted differing account data on the `EpochRewards` sysvar account.

Since the `EpochRewards` sysvar is a normal on-chain account, this difference changes the accounts-delta hash / bank hash for the affected and all subsequent blocks in the same epoch's reward-distribution window, causing consensus divergence between the two otherwise-honest nodes.

### Impact Explanation
This is a cross-node state divergence (bank hash mismatch) triggerable purely by an unprivileged user closing their own stake account during the multi-block reward-distribution window, combined with the ordinary, expected operational event of any single validator restarting/rejoining from a snapshot mid-distribution (a routine, non-privileged occurrence, not attacker-controlled validator behavior). A bank-hash mismatch between validators executing identical transaction sets is a consensus-safety violation and falls under Agave's highest-severity "loss of consensus / safety violation" bounty category.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled for the state-mutation part: the attacker only needs to own a stake account that is scheduled (via `hash_rewards_into_partitions`) for a later distribution partition, and deactivate + withdraw it (or otherwise close it) before that partition is processed. The only "external" precondition — some validator restarting mid-epoch-reward-distribution — is a common, non-adversarial operational event (crash-restart, fast-boot from snapshot, new node join with a mid-epoch snapshot). No validator/leader control or special privilege is needed by the attacker themselves; they simply exploit an existing test-documented asymmetry (`test_epoch_credit_rewards_and_history_update` explicitly tests "non-existent account" burn accounting on the *non-recalculated* path, but no test exercises this same scenario across a `recalculate_stake_rewards` boundary).

### Recommendation
Make `recalculate_stake_rewards` preserve entries for delegations that were part of the original reward computation but have since disappeared from the live `StakesCache`, or otherwise ensure that account-closure accounting (mint vs burn vs "never counted") is handled identically regardless of whether recalculation occurred. Concretely, `get_epoch_params_for_recalculation`/`recalculate_stake_rewards` should reconcile against the previously known set of reward-eligible pubkeys (e.g., diff against the pre-restart pending list persisted in `EpochRewardStatus`) so that a stake account closed mid-distribution is still represented as a "to be burned" entry rather than silently omitted, keeping the `EpochRewards` sysvar's `distributed_rewards` running total consistent across restart/no-restart execution paths.

### Proof of Concept
Integration test plan (extending the existing `test_recalculate_partitioned_rewards` harness in `runtime/src/bank/partitioned_epoch_rewards/calculation.rs`):
1. Create a reward bank with several delegations (`create_reward_bank_with_specific_stakes`) distributed over multiple blocks (`num_rewards_per_block` small enough to require ≥3 partitions).
2. At the epoch boundary, call `calculate_rewards_for_partitioning` to capture `expected_stake_rewards` and partition assignment (as in `test_recalculate_partitioned_rewards`), and record the stake pubkey assigned to a *later* (not-yet-distributed) partition, call it `victim_pubkey`.
3. Advance one block into distribution (so the first partition is paid) similar to the existing test.
4. Before the block containing `victim_pubkey`'s partition, submit a `Deactivate` + `Withdraw` transaction sequence (or directly manipulate the bank via the same public entrypoints an attacker would use) that fully closes `victim_pubkey`'s stake account (drops it out of `StakesCache`).
5. Branch into two banks from this point:
   - **Bank A (no restart)**: continue advancing blocks normally via `Bank::new_from_parent`, letting `distribute_partitioned_epoch_rewards` run to completion using the original `all_stake_rewards`.
   - **Bank B (restart)**: call `recalculate_partitioned_rewards_if_active(|| &thread_pool)` at this point (simulating `initialize_after_snapshot_restore`), then continue advancing blocks to completion.
6. After both banks finish the distribution (`epoch_reward_status == Inactive`), read the `EpochRewards` sysvar account's `distributed_rewards` field from each bank's history at the block where `victim_pubkey`'s partition was processed, and assert `bank_a_distributed_rewards != bank_b_distributed_rewards` (expected assertion demonstrating the bug: they diverge by `victim_pubkey`'s stake_reward amount), then assert the two banks' overall `hash()`/`bank_hash()` at that slot differ, proving cross-node divergence.
