## Title
Multisig-approved transaction can be executed with a different, unapproved payload when full payload is stored on-chain and `abort_if_multisig_payload_mismatch` is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction`, the VM-prologue function that gates execution of an approved `MultisigTransaction`, only verifies that the executed payload matches the on-chain-approved one when the transaction was stored as a **hash** (`payload_hash`). When the **full payload** is stored on-chain (`transaction.payload`), the equality check against the payload actually supplied at execution time is gated behind the `abort_if_multisig_payload_mismatch_enabled` feature flag: [1](#0-0) 

If that feature is not enabled on a given chain/network, an owner who has already obtained enough approvals for sequence number N (approved against the *stored* payload) can execute the transaction using an **arbitrary different payload** at the executable/EntryFunction level, because the executor derives the executed bytes from the transaction's own `executable_ref()`, not from the on-chain stored payload: [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the referenced report (`createMarket` missing a check against pre-existing state before allowing an overwrite): here, the "state that must be checked before allowing an action" is the on-chain-stored `MultisigTransaction.payload` that owners voted on, and the "overwrite" is substituting a different, unapproved payload at execution time.

Flow:
1. An owner calls `create_transaction` and stores the full entry-function payload on-chain via `MultisigTransaction.payload`.
2. Other owners call `approve_transaction` against that stored payload/sequence number, believing they are authorizing exactly that call.
3. When quorum is reached, any owner executes the `MultisigTransaction`. The VM prologue calls `validate_multisig_transaction(owner, multisig_account, provided_payload)` where `provided_payload` is derived from the *transaction currently being submitted* (its `executable_ref()`), not from storage [2](#0-1) .
4. `validate_multisig_transaction` checks `payload_hash` (hash-only case) unconditionally, but only checks the full `payload` equality if `features::abort_if_multisig_payload_mismatch_enabled()` is true [4](#0-3) .
5. If that feature is disabled, quorum/timelock/sequence checks pass regardless of whether `provided_payload` matches the approved `payload`, and `execute_multisig_transaction` in the VM then executes the attacker-supplied `provided_payload` (not the stored one) [3](#0-2) [5](#0-4) .

This breaks the admission invariant that "the executed instruction must correspond to the set of signers/approvers who authorized it" — the multisig approval set effectively becomes decoupled from what actually executes as the multisig account's signer.

### Impact Explanation
Any single multisig owner (with sufficient approval-count quorum reached against some benign payload) could unilaterally substitute and execute a completely different entry function as the multisig account — e.g. draining funds, changing owners, or granting themselves privileges — without the other owners ever approving that specific call. This is a critical break of the multisig's core security guarantee (k-of-n approval of a specific action) and matches the Admission Impact Gate's "authenticator/multisig approval validation accepting the wrong approval set" and "pre-validation mismatch causing an unapproved transaction to execute and commit."

### Likelihood Explanation
The impact is entirely gated by whether the `abort_if_multisig_payload_mismatch_enabled` feature flag is turned on for a given deployment. I was not able to fully confirm from the available index whether this flag defaults to enabled on mainnet/testnet or is still being rolled out (its presence in `aptos-release-builder/src/components/feature_flags.rs` and `features.move` suggests it is a governance-gated flag, implying it may not be active everywhere/at all times, e.g. during upgrade windows, on new networks, or test/devnet deployments). This uncertainty affects the practical likelihood but does not change the fact that the code path itself performs no such check when the flag is off, which is a genuine local, unprivileged root cause.

### Recommendation
Make the full-payload equality check in `validate_multisig_transaction` unconditional (remove the `features::abort_if_multisig_payload_mismatch_enabled()` gate), so that whenever `transaction.payload.is_some()`, the `provided_payload` used for execution must always equal the stored, approved payload — mirroring the unconditional hash-check behavior already applied to the `payload_hash` case.

### Proof of Concept
1. Owner A calls `create_transaction(multisig_account, payload = transfer(1 AptosCoin, victim))`, which stores the full payload on-chain.
2. Owners B, C approve sequence number N against that stored payload, reaching quorum.
3. On a network where `abort_if_multisig_payload_mismatch_enabled` is disabled, Owner A submits a `MultisigTransaction` execution with `executable = EntryFunction(transfer(all_funds, attacker))` instead of the originally approved payload.
4. `validate_multisig_transaction` passes because: `payload_hash` is `None` (full payload was stored, not hash-only) and the payload-equality branch is skipped entirely since the feature flag is off [6](#0-5) .
5. `execute_multisig_transaction` executes the attacker's payload as the multisig account's signer [5](#0-4) , transferring the multisig account's funds to the attacker despite B and C never approving that action.

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }

    fn execute_multisig_payload(
        &self,
        resolver: &impl AptosMoveResolver,
        code_storage: &impl AptosCodeStorage,
        mut session: UserSession,
        gas_meter: &mut impl AptosGasMeter,
        traversal_context: &mut TraversalContext,
        multisig_address: AccountAddress,
        payload: &MultisigTransactionPayload,
        change_set_configs: &ChangeSetConfigs,
        trace_recorder: &mut impl TraceRecorder,
    ) -> Result<UserSessionChangeSet, VMStatus> {
        let serialized_signers =
            SerializedSigners::new(vec![serialized_signer(&multisig_address)], None);

        // If txn args are not valid, we'd still consider the transaction as executed but
        // failed. This is primarily because it's unrecoverable at this point.
        session.execute(|session| match payload {
            MultisigTransactionPayload::EntryFunction(entry_function) => self
                .validate_and_execute_entry_function(
                    code_storage,
                    session,
                    &serialized_signers,
                    gas_meter,
                    traversal_context,
                    entry_function,
                    trace_recorder,
                ),
            MultisigTransactionPayload::Script(script) => self.validate_and_execute_script(
                session,
                &serialized_signers,
                code_storage,
                gas_meter,
                traversal_context,
                script,
                trace_recorder,
            ),
        })?;
