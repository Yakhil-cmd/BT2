### Title
Cross-repository/cross-review-stack status bleed via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no filter on the webhook's `repository.full_name`, unlike its sibling handlers (`PushHandler`, `CheckSuiteHandler`) which scope through `stacks` (derived from `Repository.from_github_repo_name`). Because `Commit` rows are only unique on `(sha, stack_id)` and not globally unique on `sha`, any legitimately-signed `status` webhook whose sha happens to also exist under a *different* stack's commit history (e.g., a sibling PR review-stack on the same base repository sharing a commit object) will flip that unrelated commit's/stack's deployability too.

### Finding Description
The claimed binding is: `status_webhook.repository == commit.stack.repository ∧ status_webhook.pull_request_head == commit` should hold for every `Commit` row that gets a new `Status` created from a given webhook.

The actual code:
```ruby
# app/models/shipit/webhooks/handlers/status_handler.rb
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Commit.where(sha: params.sha)` performs a global table scan with no `repository_name`/`stacks` filter, in contrast to `PushHandler#process`, which scopes to `stacks` (repository-derived) before matching branch/sha: [2](#0-1) 
and `CheckSuiteHandler#process`, which likewise scopes via `stacks.where(branch:)`: [3](#0-2) 

Both of those handlers use the base `Handler#stacks` helper, which explicitly resolves the repository from the payload before returning any records: [4](#0-3) 

`StatusHandler`'s own `params` block never even requires a `repository` field, and never calls `stacks`/`repository_name` at all — confirming the omission is structural, not incidental.

The DB schema confirms `sha` is only unique per-stack, not globally:
```
t.index ["sha", "stack_id"], name: "index_commits_on_sha_and_stack_id", unique: true
``` [5](#0-4) 

meaning the schema itself anticipates the same `sha` existing under multiple `stack_id`s — a condition that is completely ordinary in review-stack setups where multiple open PRs against the same base repo share a common ancestor/cherry-picked commit as their head. No cryptographic SHA-1 collision is required: two independent PR branches whose head is *literally the same git commit object* (identical tree/parents/author/committer/message — trivially reproducible by fetching a public PR branch and pushing it into another fork) will have identical shas. Each PR, once provisioned as a review stack (`OpenedHandler` → `ReviewStackAdapter#find_or_create!`), gets its own `Commit` row for that same sha under its own `stack_id`.

When a legitimately-signed `status` webhook (with a valid signature for the correct organization/repository, verified upstream by `GithubHook#verify_signature`) reports success for that shared sha, `StatusHandler` matches **every** `Commit` row with that sha across **every** stack, and calls `commit.create_status_from_github!(params)` on each:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [6](#0-5) 

Each new `Status` row triggers `schedule_continuous_delivery` on its own commit/stack after commit: [7](#0-6) 
and `Commit#deployable?` becomes true purely from `success? && !blocked?`, independent of which PR's CI actually produced the status: [8](#0-7) 

None of the existing guards prevent this: `verify_signature`/`GithubApp#verify_webhook_signature` only validates that the payload came from the correct GitHub org — it says nothing about which `Stack`/`Commit` rows the payload is allowed to mutate. `ExplicitParameters` for `StatusHandler` doesn't even require a `repository` field to check against. There is no `stacks`/`repository_name` scoping call anywhere in `StatusHandler`.

### Impact Explanation
A `success` status legitimately generated by CI for one contributor's PR/review-stack can silently mark a **different** contributor's review-stack commit (same base repository, unrelated PR) as `deployable?`, causing `schedule_continuous_delivery` to fire for that other stack. If that other review stack has `continuous_deployment` enabled, this can trigger an actual unauthorized deploy of code that was never validated by its own CI run — a write for a party ("PR"/tenant) that did not authenticate that status. This matches the Critical category: "a payload for one repository[/PR] mutating another's stack, commit ... or an unauthorized deploy." It is repeatable against any pair of open PRs on any review-stack-enabled repository whose heads happen to share a commit object (a routine occurrence, not attacker-exclusive), and it also generalizes to full cross-repository bleed if two unrelated stacks anywhere in the Shipit instance happen to share a sha (astronomically unlikely by chance, but the code path performs no exclusion).

### Likelihood Explanation
Preconditions: `review_stacks` enabled on the base repository with at least two concurrently open PRs whose heads resolve to the same underlying git commit object (achievable without cryptography by simply fetching a public branch/commit and reusing it in a separate fork/PR — e.g., both PRs cherry-pick or rebase onto the exact same upstream commit as their tip). The attacker needs no Shipit credentials, only ordinary GitHub PR/fork capability, and needs a real (correctly-signed) CI status to be posted for that shared sha — which happens naturally through the base repo's already-configured CI integration. Cost is low and the outcome is deterministic once the shared-sha precondition holds.

### Recommendation
Scope `StatusHandler#process` to the webhook's originating repository/stack, mirroring `PushHandler`/`CheckSuiteHandler`: require `repository.full_name` in the params schema, resolve `stacks` via `Repository.from_github_repo_name`, and only update commits belonging to those stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), so a status can never mutate a `Commit` row outside its own repository's stacks — and ideally further scope to the specific PR/branch when in review-stack mode.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack` fixtures (`stack_a`, `stack_b`) under the *same* `Repository`, simulating two review stacks (`environment: "pr1"`, `environment: "pr2"`).
2. Create a `Commit` under each stack with the **same** `sha` (e.g., `"deadbeef..."`), representing a shared upstream commit that is each PR's head.
3. Assert precondition: `assert_not commit_a.deployable?` and `assert_not commit_b.deployable?`.
4. Build a `status` webhook payload for `stack_a`'s repository only, with `sha: shared_sha, state: "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
6. Assert the broken binding: `assert commit_a.reload.deployable?` (expected, own repo/PR) **and** `assert commit_b.reload.deployable?` (this is the violation — `stack_b`'s commit became deployable from a status meant only for `stack_a`'s PR), i.e. `assert_not_equal commit_a.stack_id, commit_b.stack_id` while both are now `success?`/`deployable?` true from a single webhook scoped to only one repository/PR.
