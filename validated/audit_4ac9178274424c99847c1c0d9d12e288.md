### Title
Missing Zero-Address Guard on Validator Reward Recipients Causes Silent KAIA Burn During Block Reward Distribution — (`kaiax/reward/impl/getter.go`, `kaiax/staking/staking_info.go`)

### Summary

The Kaia reward distribution pipeline (`assignStakingRewards`, `assignStakingRewardsFlex`, `specWithProposerAndFunds`, `specWithProposerAndFundsFlex`) never validates that a validator's `RewardAddr` or a consensus-liquidity pool's `CLPoolAddr` is non-zero before crediting KAIA to it. If either address is zero — sourced from the AddressBook or CLRegistry on-chain contracts — the corresponding KAIA staking reward is silently transferred to `address(0)` (effectively burned) every block, with no revert and no error.

### Finding Description

**Root cause — no zero-address guard in the Go reward pipeline**

`consolidateNodes()` in `kaiax/staking/staking_info.go` builds a `consolidatedNode` keyed on `RewardAddr` without any zero-address check:

```go
// kaiax/staking/staking_info.go:131-147
for i, n := range si.NodeIds {
    r := si.RewardAddrs[i]          // r can be common.Address{} — never checked
    nToR[n] = r
    if cn, ok := cmap[r]; ok {
        ...
    } else {
        cmap[r] = &consolidatedNode{
            RewardAddr:    r,        // zero address stored as-is
            StakingAmount: si.StakingAmounts[i],
        }
        rList = append(rList, r)
    }
}
``` [1](#0-0) 

Similarly, `CLPoolAddr` from `CLStakingInfo` is never validated:

```go
// kaiax/staking/staking_info.go:151-159
for _, clsi := range si.CLStakingInfos {
    if r, ok := nToR[clsi.CLNodeId]; ok {
        cmap[r].CLStakingInfo = clsi   // clsi.CLPoolAddr never checked for zero
    }
}
``` [2](#0-1) 

In `assignStakingRewards` (Kore/Prague path), rewards are allocated directly to these unchecked addresses:

```go
// kaiax/reward/impl/getter.go:521-525
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // CLPoolAddr never checked
}
``` [3](#0-2) 

The same pattern appears in `assignStakingRewardsFlex`: [4](#0-3) 

And in `specWithProposerAndFunds` / `specWithProposerAndFundsFlex` for the proposer's CL split: [5](#0-4) 

The `RewardSpec.Validate()` function only checks for negative amounts — it does not reject zero-address recipients:

```go
// kaiax/reward/spec.go:118-125
func (spec *RewardSpec) Validate() error {
    for addr, amount := range spec.Rewards {
        if amount.Sign() < 0 {
            return errNegativeRewardAmount(addr, amount)
        }
    }
    return nil
}
``` [6](#0-5) 

`FinalizeState` then unconditionally calls `state.AddBalance` for every entry in `spec.Rewards`, including any zero-address entry:

```go
// kaiax/reward/impl/blockstate.go:53-55
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)   // zero address accepted silently
}
``` [7](#0-6) 

Unlike Solidity's ERC-20 `_mint` (which reverts on `address(0)`), Go's `state.AddBalance` silently credits the zero address. The block finalizes normally; the KAIA is permanently burned.

**Parsing layer also has no guard**

`parsePermissionlessCallResult` and `parseCallResult` in `kaiax/staking/impl/getter.go` copy `RewardAddress` and `CLPoolAddr` from on-chain results without zero-address filtering: [8](#0-7) [9](#0-8) 

The only sanity check in `parseCallResult` validates `kefAddr`/`kifAddr` (fund addresses), not individual validator reward addresses: [10](#0-9) 

### Impact Explanation

Every block in which a validator's `RewardAddr` or `CLPoolAddr` is `address(0)`:

- The validator's (or CL pool's) proportional share of the staking reward is computed correctly but credited to `address(0)`.
- The KAIA is permanently burned — it leaves the validator's expected balance and enters an unrecoverable address.
- No error is returned; `FinalizeState` succeeds; the block is accepted by all nodes.
- The loss is proportional to the validator's staking weight and repeats every block until the address is corrected on-chain.

This matches the allowed impact: **unauthorized burn/loss of KAIA affecting system-managed reward funds**.

### Likelihood Explanation

The trigger requires a zero `RewardAddr` or `CLPoolAddr` to reach the Go layer. Two realistic paths:

1. **AddressBook / AddressBookV2**: The AddressBookMock in this repository (`contracts/testing/reward/AddressBookMock.sol`) registers validators without any zero-address check on `_cnRewardAddress`, demonstrating the contract interface permits it. If the production AddressBook or AddressBookV2 similarly omits the check (or if a validator's reward address is unset/cleared), the Go layer provides no fallback.
2. **CLRegistry**: `CLPoolAddr` is read from the CLRegistry via `MultiCallDPStakingInfo`. If the CLRegistry allows a zero pool address (e.g., during a misconfigured registration), the Go code has no defense.

The trigger is semi-trusted (a registered validator), matching the Celo analog exactly.

### Recommendation

1. In `consolidateNodes()` (`kaiax/staking/staking_info.go`), skip any entry whose `RewardAddr` is zero.
2. In `parsePermissionlessCallResult` and `parseCallResult` (`kaiax/staking/impl/getter.go`), filter out profiles with zero `RewardAddress`.
3. In `parseCallResult` / `parsePermissionlessCallResult`, reject any `CLStakingInfo` entry whose `CLPoolAddr` is zero.
4. In `RewardSpec.Validate()` (`kaiax/reward/spec.go`), add a check that rejects zero-address recipients with non-zero amounts.
5. Optionally add a guard in `FinalizeState` before calling `state.AddBalance`.

### Proof of Concept

```
Setup (Prague/Permissionless hardfork active, WeightedRandom policy):

1. Validator V registers in AddressBook with RewardAddr = address(0)
   (or CLRegistry registers V's CL pool with CLPoolAddr = address(0)).

2. At staking snapshot block N, GetStakingInfo(N) returns:
     NodeIds       = [V]
     RewardAddrs   = [0x0000...0000]   ← zero
     StakingAmounts = [minStake + X]   ← eligible for staking reward

3. consolidateNodes() creates:
     consolidatedNode{RewardAddr: 0x0000...0000, StakingAmount: minStake+X}

4. assignStakingRewards() computes reward R for V and sets:
     alloc[0x0000...0000] = R

5. FinalizeState() calls:
     state.AddBalance(0x0000...0000, R)   ← no error, no revert

6. Result: R KAIA is burned every block. V's expected reward balance
   never increases. The block is accepted by all honest nodes.
```
