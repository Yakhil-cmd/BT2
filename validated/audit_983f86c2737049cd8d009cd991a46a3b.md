### Title
StatusHandler#process writes CI status onto any repository's Commit matching an attacker-supplied sha, bypassing repository scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` queries `Commit.where(sha: params.sha)` with no repository/stack scoping whatsoever, unlike every other handler (`PushHandler`, `PullRequest::*Handler`) which restrict their effects to `stacks` derived from `Handler#repository_name` (`payload.dig('repository','full_name')`). This means a `status` webhook whose signature is validly verified for repository/organization B can still mutate a `Commit` row that belongs to a Stack in an unrelated repository A, as long as `params.sha` matches an existing `Commit#sha` in the database, since `sha` is only unique per `(sha, stack_id)` pair, not globally.

### Finding Description
The broken binding: `payload.dig('repository','full_name')` (the authenticated/signed repository, B) is never compared to `Commit#stack.repository.full_name` (the repository actually mutated, A) — i.e. **`payload.dig('repository','full_name') != commit.stack.repository.full_name` is never checked**, yet the write still happens.

Code path:
- `WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) parses the raw JSON and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`), which validates the HMAC signature using `Shipit.github(organization: repository_owner)` where `repository_owner` is `payload.dig('repository','owner','login')` — i.e., validation is scoped to the **organization** named in the payload, not to a specific repository or Stack.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This never calls `Handler#stacks` or `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), unlike `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), which correctly scopes via `stacks.not_archived.where(branch:)`.
- `Commit#sha` is unique only per `(sha, stack_id)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), not globally, so the same sha value can legitimately exist across multiple Stacks/repositories (e.g., forked repositories sharing history, or any repo where a commit with identical byte content — hence identical git SHA — has been pushed).
- `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) writes a `Status` record scoped to `commit.stack_id`, which is fixed at commit-creation time and derived from the Commit's own owning Stack — not from the webhook's payload repository.

Exploit: attacker owns repository B (in an organization that is a legitimate, independently configured tenant of the same Shipit instance, so `verify_signature` succeeds using B's own webhook secret). Attacker forks/replicates a commit whose SHA-1 collides with (or is identical to, via shared git history/forking) a `Commit` already tracked under a Stack in repository A. Attacker sends `POST /webhooks` with `X-Github-Event: status`, `repository.full_name` = B, and `sha` = the colliding value. The signature check passes (it only checks B's org secret), `drop_unhandled_event` passes (status is handled), and `StatusHandler#process` finds and mutates the `Commit` belonging to Stack A, creating a `Status` for stack A's commit — without ever consulting `repository_name`/`stacks` to confirm the commit actually belongs to a stack of repository B.

Existing guards fail because: `verify_signature` only proves the request cryptographically originated from repository B's org, not that repository B is authorized to write to repository A's data; `ExplicitParameters` schema only validates payload shape (`sha`, `state`, etc.), not repository ownership; there is no model validation on `Status`/`Commit` tying the status write back to the payload's `repository.full_name`.

### Impact Explanation
A `Status` row is created for a `Commit` belonging to a Stack owned by a repository the attacker never authenticated against, matching the "payload for one repository mutating another's commit" Critical impact category. This can flip a `Commit#state` to `success`, satisfying `deployable?` checks (`app/models/shipit/commit.rb:227-229`) and enabling downstream effects such as triggering `ContinuousDeliveryJob`/`ProcessMergeRequestsJob` for stack A (see `Status#schedule_continuous_delivery` and `after_create :enable_ci_on_stack` in `app/models/shipit/status.rb:18-19,42-44`), potentially causing an unauthorized deploy of stack A. The attack is repeatable against any commit sha the attacker can reproduce or guess, and is not limited to one target — any Stack anywhere on the shared Shipit instance is reachable this way, so blast radius spans all tenants sharing the instance.

### Likelihood Explanation
Preconditions: attacker must control a repository/organization that is already a configured, independent tenant on the shared Shipit instance (so its own webhook secret verifies), and must produce a commit SHA that also exists in a target Stack's `Commit` table — most practically achieved by forking a target repository (git SHAs are content-addressed and identical across forks/clones of the same commit) or by any scenario where identical commit content is pushed to two different repos tracked by the same Shipit instance. This is a realistic scenario for any Shipit deployment that hosts multiple orgs/tenants (a common real-world Shipit topology), making the attack low-cost and repeatable per request.

### Recommendation
Scope `StatusHandler#process` to only commits belonging to the requesting repository, e.g. filter `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { id: Repository.from_github_repo_name(repository_name)&.id })` or restrict the query through `stacks.joins(:commits).where(shipit_commits: { sha: params.sha })`, mirroring the pattern already used in `PushHandler` via `Handler#stacks`/`Handler#repository_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from repository B does not mutate a Commit belonging to repository A's stack" do
  stack_a = shipit_stacks(:shipit) # belongs to repository A
  commit_a = stack_a.commits.create!(sha: 'deadbeef' * 5, ...)

  payload = {
    'sha' => commit_a.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/repo-b', 'owner' => { 'login' => 'attacker-org' } }
  }

  # repository.full_name (B) != commit_a.stack.repository.full_name (A)
  refute_equal payload.dig('repository', 'full_name'), commit_a.stack.repository.full_name

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_equal 'success', commit_a.reload.state # currently TRUE -- demonstrates the cross-tenant write
end
```
This proves the equality `payload.dig('repository','full_name') == commit.stack.repository.full_name` is false, yet the write to `commit_a` (owned by repository A's stack) still occurs, confirming the vulnerability.
