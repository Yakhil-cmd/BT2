### Title
Unhandled `throw Error` on crafted duplicate address-defining authors crashes the node during unit validation - (File: definition.js)

### Summary
`definition.js`'s `evaluate()` functions inside `validateDefinition` and `validateAuthentifiers` both contain an unconditional `throw Error("more than 1 address definition")` when more than one author in a submitted unit defines the same referenced address with a matching definition hash: [1](#0-0) [2](#0-1) 

### Finding Description
When an `'address'` opcode in an address/asset spending condition references another address that has no stable definition yet, ocore falls back to looking for that address's definition among the current unit's `authors`: [3](#0-2) 
It filters `objUnit.authors` for entries whose `address` matches and whose `definition` hashes to the expected `chash`. If more than one such author exists, the code assumes this is an "impossible" state and unconditionally `throw`s a plain `Error`, rather than returning a validation failure via `cb(...)`. The same pattern is repeated in the authentifier-evaluation pass used for the actual signature check: [4](#0-3) 

A `throw` inside this deeply-nested async callback is not wrapped by a local `try/catch`, so it propagates as an uncaught exception. ocore's `network.js` global handler explicitly re-throws to intentionally crash the process on any uncaught exception: [5](#0-4) 

This is structurally analogous to WildMIDI's bug: an internal invariant about the shape of untrusted input ("only one definition-defining author can exist") is enforced with an unconditional/unsafe operation instead of a input validation check, and a violation crashes the process.

### Impact Explanation
I could not fully confirm, given my remaining tool budget, whether an earlier validation step (e.g., inside `validateAuthors`, which I could not fully inspect) rejects a unit with duplicate author addresses before this code path is reached. `objUnit.authors` is an array and I found no explicit "authors must have unique addresses" check in the portion of `validation.js` I was able to read: [6](#0-5) . If duplicate author addresses (or two authors coincidentally both matching the "other_address" filter) are not rejected earlier, an attacker could post a single unit that reaches this `throw`, crashing every full node that validates it — a network-wide denial of confirmation, not just the sending peer's connection.

### Likelihood Explanation
Moderate to Low confidence: reachability depends on unit-level author validation rules I could not fully verify due to tool-call limits. The `'address'` opcode is only reachable when `objValidationState.bNoReferences` is false, which is the normal case for spending-condition evaluation of authors' own definitions and of "asset condition"/deeper referenced conditions, so the code path itself is clearly attacker-reachable in principle.

### Recommendation
Replace both unconditional `throw Error("more than 1 address definition")` statements in `definition.js` with a soft validation failure (`return cb("more than 1 address definition")` / `return cb2(false)`), and add an explicit, early check that unit authors do not contain duplicate addresses, so that malformed/duplicate-author units are rejected as ordinary "unit error" cases rather than crashing the process.

### Proof of Concept
I was not able to fully construct and confirm an end-to-end PoC unit within the available tool budget, because I could not verify whether `validateAuthors` (in `validation.js`, not fully read) already rejects duplicate author addresses before authentifier/definition evaluation is reached. A concrete PoC would require: (1) confirming duplicate-address authors are not rejected earlier, (2) crafting a unit with two authors at the same address (or a definition that legitimately allows two authors to define the same referenced "other address" with an identical definition chash), and (3) referencing that address via an `['address', other_address]` opcode inside a spending condition being validated. This requires deeper repository access than the ask-mode index search allowed me to complete with certainty.
