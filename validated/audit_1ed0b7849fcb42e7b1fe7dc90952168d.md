### Title
Cross-repository status forgery unblocks victim stack's deploy gate via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to using only the raw `sha` from the webhook payload, with no filter on the repository that sent the webhook. Any repository whose org has the Shipit GitHub App installed (and therefore produces a signature that `verify_signature` accepts) can forge a `success` status for an arbitrary `context`/`sha`, flipping `Commit#blocked?` to `false` for a victim stack's blocking commit and unblocking downstream deploys that the victim's own CI never approved.

### Finding Description
The broken binding is: **the stack that owns the commit whose status is written == the stack identified by the webhook's `repository.full_name`**. In every other event handler in this codebase, that binding is enforced via `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from the payload before touching any records: [1](#0-0) 

`StatusHandler#process`, however, never calls `stacks` or filters by repository at all — it resolves commits purely by `sha`: [2](#0-1) 

`Commit.where(sha: params.sha)` is a global, cross-tenant query with no `stack_id`/repository scoping. Any commit row in any stack whose `sha` matches the attacker-supplied value receives the forged status via `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!`.

`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` only proves the payload came from GitHub for the org identified by `repository.owner.login` in the *attacker's own payload* — it says nothing about which commit/stack the event is allowed to mutate: [3](#0-2) 

Downstream, `blocking?` is computed per status/context as "not successful and context is in the stack's `blocking_statuses`": [4](#0-3) 

and `Commit#blocked?` scans reachable, undeployed ancestor commits for any `blocking?` status: [5](#0-4) 

Because `blocking?` requires `!success?`, an attacker who forges a `state: "success"` status for the same `context` that is currently failing/pending on the victim's blocking commit will overwrite the effective state for that context (statuses are grouped/most-recent-per-context, per `Status::Group.compact` used in `Commit#status`), causing `blocking?` to become `false` for that commit and `blocked?` to become `false` for every downstream commit in the victim stack — enabling `deployable?` to become `true`: [6](#0-5) 

**Attack request:** an attacker owns/controls a repository in an org where the Shipit GitHub App is installed (any org onboarded to this Shipit instance qualifies — the attacker's own repo need not have any relation to the victim's stack). They send `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org, and a payload:
```json
{
  "sha": "<victim commit sha, known/public>",
  "state": "success",
  "context": "<the blocking context configured in the victim stack's .shipit.yml>",
  "repository": { "full_name": "attacker/unrelated-repo", "owner": { "login": "attacker-org" } }
}
```
This passes `verify_signature` (their own org's real signature), passes `drop_unhandled_event` (status is handled), and is dispatched to `StatusHandler`, which matches the victim's `Commit` row purely by `sha` and writes the forged `success` status onto it — with no verification that `attacker/unrelated-repo` is the repository backing the victim stack.

**Why existing guards fail:** `verify_signature`/`GitHubApp#verify_webhook_signature` validate the sender's identity for their *own* org/repo, not authorization over the target commit. `drop_unhandled_event` only checks event type. The `ExplicitParameters` schema in `StatusHandler.params` validates payload shape, not repository ownership. None of `force_github_authentication`, `User#authorized?`, `require_permission!`, or the `stacks` scoping helper (which exists in this codebase specifically to bind webhook mutations to the sending repository) are invoked in this handler.

### Impact Explanation
An attacker with a webhook-capable repository in any onboarded GitHub org can write a forged `success` status onto an arbitrary victim commit in any other stack, overriding a currently-failing/pending blocking CI context. This flips `Commit#blocked?` from `true` to `false` for the victim stack, allowing `deployable?` to become `true` and letting `ContinuousDeliveryJob`/manual deploys proceed on commits that never actually passed the victim's required blocking check. This is a payload from one repository mutating another repository's commit/stack state and enabling an unauthorized deploy — matching the "Critical: payload for one repository mutating another's stack/commit ... or an unauthorized deploy" category. It is repeatable against any commit sha/context combination and is not limited to one victim.

### Likelihood Explanation
Preconditions: the attacker needs a repository under any org where the Shipit-connected GitHub App is installed (this may be a low bar in multi-tenant/GitHub-org-wide installations), knowledge of the victim commit's `sha` (public for public repos, or leaked/observable otherwise), and knowledge of the blocking `context` name (often a well-known CI check name, e.g. `ci/circleci`, discoverable from the victim repo's status checks or `.shipit.yml` if visible). No Shipit session, API token, or secrets are required. Given these are all low-cost/observable pieces of information, exploitation is straightforward and fully repeatable.

### Recommendation
Scope `StatusHandler#process` to only mutate commits belonging to stacks resolved from the webhook's own `repository.full_name`, mirroring the `stacks` helper used by the `pull_request/*` handlers, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or filtering `Commit.where(sha: params.sha)` by `stack_id: stacks.select(:id)` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` (victim) backed by `Repository` `victim/repo`, with deploy spec `blocking_statuses: ['ci/blocking']`.
2. Create `blocking_commit` in `stack_a` with a `Status` `context: 'ci/blocking', state: 'failure'`.
3. Create `downstream_commit` in `stack_a`, newer than `blocking_commit`, with a passing required status.
4. Assert baseline: `downstream_commit.blocked?` is `true` and `downstream_commit.deployable?` is `false` (binding intact: victim stack's own blocking status controls its own gate).
5. Build a webhook payload for the `status` event with `sha: blocking_commit.sha`, `context: 'ci/blocking'`, `state: 'success'`, and `repository: { full_name: 'attacker/unrelated-repo' }` — a repository unrelated to `stack_a`.
6. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, as the flaw is in the handler regardless of signature validity for the attacker's own repo).
7. Reload `blocking_commit` and `downstream_commit`.
8. Assert the broken binding: `blocking_commit.blocking?` is now `false` and `downstream_commit.blocked?` is now `false`, and `downstream_commit.deployable?` is `true` — proving a status forged under `attacker/unrelated-repo` altered `stack_a`'s (`victim/repo`) deploy gate.
