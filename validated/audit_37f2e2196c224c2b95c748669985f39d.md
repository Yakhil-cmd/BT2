### Title
Membership webhook signature is verified against `repository.owner.login` but `MembershipHandler` grants team membership based on `params.team.id`, letting any org with a valid `webhook_secret` add its own users to a team belonging to a different, already-privileged organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to verify a webhook against solely from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), which is attacker-controlled JSON, not derived from anything cryptographically tied to the actual event. `MembershipHandler#process` then trusts `params.team.id` / `params.member.login` from the same payload to add a user to an existing `Team` record via `Team.find_or_create_by!(github_id: params.team.id)` followed by `team.add_member(member)`, with no check that the org whose secret validated the signature matches the team's `organization`.

### Finding Description
The broken binding, stated explicitly: the code implicitly assumes
`repository_owner (org whose webhook_secret verified the request) == params.team's actual owning organization`,
but nothing enforces this equality.

Code path:
- `WebhooksController#repository_owner` [1](#0-0)  reads `params.dig('repository','owner','login') || params.dig('organization','login')` — both fully attacker-controlled JSON fields.
- `verify_signature` uses that value to pick the `GitHubApp` (and thus which `webhook_secret` to check against) via `Shipit.github(organization: repository_owner)` [2](#0-1) . If the attacker owns `attacker-org` in Shipit's config, they know `attacker-org`'s real `webhook_secret`, so they can set `repository.owner.login = 'attacker-org'` and sign correctly — this only proves "sender knows attacker-org's secret", not anything about the `team` or `organization` fields elsewhere in the body.
- `MembershipHandler#find_or_create_team!` looks the team up **only by `github_id`** [3](#0-2) . If a `Team` with that `github_id` already exists (i.e., it's already a real, configured team, e.g. one listed in `Shipit.github_teams`), the `find_or_create_by!` block (which sets `organization`) does **not** run — the existing team's `organization` is untouched, and the attacker-supplied `organization.login` value is irrelevant to which team gets modified.
- `MembershipHandler#process` then unconditionally does `team.add_member(User.find_or_create_by_login!(params.member.login))` [4](#0-3) , creating/reusing the attacker's own GitHub login as a `Shipit::User` and inserting a `Membership` row linking it to the targeted `Team`.
- `Team#add_member` performs the insert unconditionally if not already a member [5](#0-4) .
- `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , so membership in any `Team` object listed in `Shipit.github_teams` grants authorization regardless of which org the webhook was actually signed for.

Existing guards checked and found insufficient: `verify_signature`/`verify_webhook_signature` only proves possession of *some* configured org's secret, not that that org owns the `team`/`organization` referenced in the payload [7](#0-6) ; `drop_unhandled_event` and the `ExplicitParameters` schema in `MembershipHandler` only validate shape/presence of `action`, `team`, `organization`, `member`, not cross-field consistency [8](#0-7) ; nothing in `Team.find_or_create_by!` re-validates `organization` against `repository_owner` for pre-existing teams.

### Impact Explanation
An attacker who legitimately owns any GitHub organization configured in Shipit (holding its real `webhook_secret`) can forge a `membership` event that adds their own GitHub login as a member of **any pre-existing `Team` row in the database**, including one tied to `Shipit.github_teams` for a completely different ("victim") organization. Once added, `User#authorized?` returns `true` for that attacker account, granting Shipit-level authorization (deploy/rollback/merge access gated on `authorized?`) that was meant to be restricted to the victim org's real team members. This matches "escalation into `Shipit.github_teams` authorization" (High/Critical per the rubric's own escalation category), and is repeatable for any team `github_id` the attacker can learn or guess, across arbitrary configured organizations, since the check is entirely bypassable by controlling unrelated JSON fields in a signed payload.

### Likelihood Explanation
Preconditions: attacker must own (or control the webhook secret configuration of) at least one GitHub organization that Shipit is configured to trust (i.e., present in Shipit's per-org GitHub App config with a `webhook_secret`); a target `Team` record with a known `github_id` must already exist (e.g., listed in `Shipit.github_teams`, which is realistic since these are the very teams worth escalating into, and team `github_id`s are discoverable via GitHub's own team APIs/UI). No other privileged access, session, or Shipit secret is required — the attacker only needs their own legitimate webhook secret and knowledge of the target team's numeric GitHub team ID. Cost is a single crafted signed HTTP POST; the attack is trivially repeatable.

### Recommendation
In `MembershipHandler`, verify that the org used to authenticate the webhook (`WebhooksController#repository_owner`) matches the `organization` of the `Team` being modified (existing or new), e.g., reject/no-op the event if `team.organization.casecmp?(repository_owner)` is false, or better, pass the verified `repository_owner` explicitly into the handler and use it (not the payload's own `organization.login`) as the sole source of truth for which org's team is affected, refusing to modify a `Team` whose `organization` doesn't match.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` style):
1. Fixture: `shipit_teams(:shopify_developers)` has `organization: 'shopify'`, `github_id: 1`.
2. Configure Shipit (via test config or `Shipit.stubs(:github)`) so org `'attacker-org'` is also known/configured with its own webhook secret, and stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return `true` (simulating the attacker's real, valid secret) while leaving other orgs' verification untouched.
3. POST `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "repository": { "owner": { "login": "attacker-org" } },
  "organization": { "login": "victim-org" },
  "team": { "id": 1, "name": "Developers", "slug": "developers", "url": "http://example.com" },
  "member": { "login": "attacker" }
}
```
4. Assertions:
   - `assert_response :ok`
   - `assert_difference -> { Shipit::Membership.count }, 1` around the request.
   - After request: `team = shipit_teams(:shopify_developers).reload; user = Shipit::User.find_by(login: 'attacker'); assert team.members.include?(user)`.
   - `assert_equal 'shopify', team.organization` (proving the pre-existing team's real org was never `'attacker-org'` or `'victim-org'`, i.e., the signed org has no relation to the modified team).
   - If `Shipit.github_teams` includes `team`, assert `user.authorized?` is `true`.

This demonstrates the divergence: `repository_owner == 'attacker-org'` (verified) while the actually-modified `team.organization == 'shopify'` — an inequality that the code never checks, resulting in an unauthorized cross-organization membership grant.
