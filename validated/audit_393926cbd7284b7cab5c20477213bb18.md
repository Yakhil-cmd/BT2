### Title
Missing newline sanitization of `feed_name`/`value` in the `in data feed` address-definition operator allows data-feed key smuggling - ([File: definition.js])

### Summary
The CVE describes a protocol-framing bug: an attacker-controlled field is not checked for the delimiter used to separate logical units in a stream, letting the attacker "smuggle" content that is later reparsed as a distinct record. `ocore` has the same bug class in the `in data feed` address-definition operator: unlike every other place that stores or validates a data-feed `feed_name`/`value`, this code path never rejects the `\n` delimiter that is used to build the LevelDB lookup key.

### Finding Description
Data-feed records are stored and queried as flat strings joined with `\n` as the field separator, e.g. the range-scan prefix built in `dataFeedByAddressExists`: [1](#0-0) 

Whenever a `data_feed` message is actually posted to the DAG, `feed_name` and string `value` are validated to reject embedded `\n` so they cannot corrupt this key format — both for ordinary units: [2](#0-1) 
and for AA-emitted `data_feed` messages: [3](#0-2) 

However, the `in data feed` operator used inside **address definitions** (a spending/authentication condition, e.g. in a multi-party or oracle-gated address) validates `feed_name` and `value` for length and type but never checks for an embedded `\n`: [4](#0-3) 

This same `feed_name`/`value` pair from the definition is later fed into `dataFeeds.dataFeedExists()` → `dataFeedByAddressExists()`, which blindly concatenates it with `\n` separators to build the LevelDB key prefix and range bounds (`key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value`, and the `>=`/`>`/`<=`/`<` bounds built from `'df\n'+address+'\n'+feed_name+'\n'+type+...`): [5](#0-4) 

Because the address-definition author fully controls `feed_name` (and `value`) at definition time, and this string is never checked for `\n`, an attacker can craft a `feed_name` that embeds additional `\n`-separated components. Those extra components are interpreted by the downstream range-query code as if they were the `type`/`value`/`mci` fields of the key, i.e. exactly the "smuggling" pattern from the CVE: a single logically-atomic field is split by the parser into multiple fields because the delimiter wasn't stripped/rejected from user-controlled input.

### Impact Explanation
An address using an `in data feed` spending condition intends the condition to be satisfied only by a specific `feed_name` posted by a specific oracle address. By embedding `\n` in the definition's `feed_name`/`value`, the author of that address definition can shift the key-range boundaries used by `dataFeedByAddressExists`, so the "matches an existing data feed record" check evaluates against a differently-scoped or differently-named record than the one all co-signers of the address agreed on. This can allow an address's spending condition to be satisfied in a way not intended/authorized by the other parties to a multi-signature or oracle-gated contract, leading to unauthorized spending of funds locked under that address definition. This is a concrete fund-safety impact reachable purely from a self-defined address (no privileged/peer access needed), matching the "unauthorized spending" bar required for a valid analog.

### Likelihood Explanation
Any user can define an address with an `in data feed` condition (this is a standard, commonly-used oscript definition primitive for oracle-gated escrow/exchange contracts) and choose an arbitrary `feed_name` string, since the length/type checks in `definition.js` do not reject `\n`. No cooperation from a hub, peer, or node operator is required — only a specially crafted definition and normal data-feed activity from the oracle(s) named in the condition.

### Recommendation
Add the same `\n`-rejection checks used elsewhere (`validation.js:1936`, `aa_validation.js:100`, `aa_validation.js:109`) to the `in data feed` operator's validation in `definition.js`:
- Reject `feed_name.indexOf('\n') >= 0`
- Reject `value.indexOf('\n') >= 0` when `value` is a string

so that address definitions cannot embed the `\n` key-separator into fields that are later concatenated into LevelDB lookup keys/ranges.

### Proof of Concept
1. Create an address whose definition includes: `["in data feed", [[oracle_address], "myfeed\nn\n<crafted-encoded-number>", "=", "1", 0]]`. The current `definition.js` validation (lines 401–444) accepts this because it never checks `feed_name` for `\n`.
2. When the address tries to authenticate a spend, `dataFeedExists`/`dataFeedByAddressExists` builds a LevelDB key prefix `'df\n'+oracle_address+'\n'+feed_name+'\n'+prefixed_value` using the raw, `\n`-laden `feed_name` (`data_feeds.js:119-164`).
3. Because the embedded `\n` sequences realign the positional fields the range-scan expects (`type`, encoded value, mci), the query can match on a different logical scope than the literal `feed_name` string "myfeed\nn\n<...>", allowing the condition to be satisfied by data-feed records the contract designer did not intend to authorize spending against.

Note: I was not able to inspect the exact runtime call site in `definition.js` that invokes `dataFeedExists` during authentifier evaluation (tool budget exhausted before that read completed), so the precise range-collision mechanics are inferred from the confirmed key-construction code in `data_feeds.js` and the confirmed validation gap in `definition.js`; a Devin session with full file access should verify the exact evaluate()-side call before patching.
