### Title
Webhook organization/repository binding is never validated, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for signature verification from an attacker-controlled field (`repository.owner.login`), but every downstream webhook handler resolves the actual `Stack`/`Repository` to act on from a *different* field of the same payload (`repository.full_name`). Nothing ties these two fields together, so the "organization that authenticated" is never proven to be the "repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` instance to verify the request with based on `repository_owner`, extracted straight from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

That organization's `webhook_secret` is then used to validate the `X-Hub-Signature` header against the raw body: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally whenever the resolved organization has no `webhook_secret` configured — a state explicitly supported and documented as optional (`Webhook secret (optional)`, `test/dummy/config/secrets_double_github_app.yml` sets `webhook_secret:` to nil per-org for exactly this multi-app setup).

Meanwhile, every event handler resolves the *actual* repository/stack acted on via a completely different payload field, `repository.full_name`, not `repository.owner.login`: [4](#0-3) [5](#0-4) 

The equality that should hold — `organization used to authenticate == organization owning repository.full_name` — is never checked anywhere in `WebhooksController` or `Handler`. As a result, an attacker can send a POST to `/webhooks` where `repository.owner.login` names an organization with no configured `webhook_secret` (bypassing signature verification entirely per `verify_webhook_signature`'s early return), while `repository.full_name` names an arbitrary *other* stack's repository (e.g. a victim organization's repo) tracked by the same Shipit instance. This is directly analogous to the audited bug: a struct field (`pythAddress`) that exists in the config but is never actually wired into the code path that matters (`Configuration::set`) — here, the field that *should* bind trust (`repository.owner.login`) is used only for signature routing and is never cross-checked against the field that actually determines the mutated resource (`repository.full_name`).

### Impact Explanation
Once signature verification is bypassed for an organization with no secret configured, an unauthenticated remote attacker can forge any supported webhook event (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) targeting a stack that belongs to a *different, unrelated* organization in the same Shipit deployment. Concretely:
- Forged `push` events can trigger `GithubSyncJob` against a victim stack, invoking `stack.github_api`/`stack.sync_github` with the app's real GitHub credentials for that repository.
- `StatusHandler` resolves the target purely by commit `sha` with no repository scoping at all, so forged `status` events can inject fake CI statuses on commits belonging to any tracked stack.
- Forged `pull_request`/`check_suite` events can manipulate review-stack lifecycle and merge status logic.

This crosses the "unauthorized deploy/merge across repositories" bar because the write target (which `Stack`/`Repository` is mutated) is decoupled from the identity that was actually authenticated.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires a Shipit deployment configured with multiple GitHub organizations (`config/secrets.yml` "Using Multiple Github Applications", documented and supported) where at least one configured organization has no `webhook_secret` set — an explicitly optional and thus realistic configuration state, not a deviation from documented setup. No token, session, or secret of any kind is required by the attacker.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handlers::Handler`), enforce that the organization used to select/verify the webhook signature matches the organization that owns `repository.full_name` before dispatching to handlers. Additionally, `verify_webhook_signature` in `lib/shipit/github_app.rb` should not silently return `true` when `webhook_secret` is blank for events that will mutate state for repositories outside that organization; at minimum, cross-validate `repository.owner.login` against the owner segment of `repository.full_name` and reject on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `AttackerOrg` (no `webhook_secret` set) and `VictimOrg` (tracked stacks in Shipit).
2. Send `POST /webhooks` with header `X-Github-Event: push` and no/invalid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/master",
  "after": "<victim commit sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally regardless of the (missing/garbage) signature header.
4. `PushHandler` resolves stacks via `payload.dig('repository', 'full_name')` = `"VictimOrg/victim-repo"`, and queues `GithubSyncJob` for the victim's stack — despite the request never having been authenticated as originating from `VictimOrg`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
