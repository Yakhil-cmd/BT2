### Title
Unhandled `throw Error` in `data_feed[[]]` oracle-candidate sorting crashes the node - ([File: data_feeds.js])

### Summary
The MySQL replication CVE describes a hard-to-exploit, high-privilege but network-reachable bug that causes a hang/crash (availability-only) of the database server. The closest reachable analog in ocore is a code path in the oscript `data_feed[[]]` evaluator that, when given a plausible but ambiguous set of unstable AA data-feed candidates, executes an unconditional `throw Error(...)` inside a synchronous `Array.prototype.sort()` comparator. This throw is not guarded by any `try/catch` on the call chain from unit/AA-trigger processing, and ocore's top-level `process.on('uncaughtException', ...)` handler deliberately re-throws to **crash the whole node process**. Any address that is used as a `data_feed[[]]` oracle inside an AA definition can be driven into this state by an ordinary unit poster / AA trigger sender, causing every node that evaluates the trigger to crash — a network-wide denial of confirmation, analogous in impact to the Oracle CVE's "hang or crash (complete DOS)".

### Finding Description
`dataFeeds.readDataFeedValue()` [1](#0-0)  collects "unstable" AA data-feed candidates whose author address matches one of the requested oracle addresses, and are still unstable but were posted with `app: 'data_feed'` [2](#0-1) .

When more than one candidate is collected and `ifseveral` is not `'abort'`, the function sorts candidates by `latest_included_mc_index`, then `level`:

```
arrCandidates.sort(function (a, b) {
    if (a.latest_included_mc_index < b.latest_included_mc_index) return -1;
    if (a.latest_included_mc_index > b.latest_included_mc_index) return 1;
    if (a.level < b.level) return -1;
    if (a.level > b.level) return 1;
    if (bIncludeAllUnstable) // still ambiguous, sort randomly (it's OK outside AAs)
        return 1;
    throw Error("can't sort candidates "+a+" and "+b);
});
``` [3](#0-2) 

`bIncludeAllUnstable` is only true when the caller passes the literal string `'all_unstable'` as `unstable_opts`. The oscript `data_feed[[]]` evaluator always calls this function with the boolean `bAA` flag as `unstable_opts`:

```
dataFeeds.readDataFeedValue(arrAddresses, feed_name, value, min_mci, mci, bAA, ifseveral, objValidationState.last_ball_timestamp, function(objResult){ ... });
``` [4](#0-3) 

Because `bAA` is a boolean, `bIncludeAllUnstable` is always `false` on this path, so the fallback branch (`return 1`) is never taken — instead `throw Error("can't sort candidates ...")` fires whenever two or more still-unstable candidate units authored by the oracle address(es) end up with the **same `latest_included_mc_index` and the same `level`** while carrying a matching `data_feed` message/value. Two sibling DAG units frequently share the same `level`/`latest_included_mc_index` (this is normal, not adversarial DAG topology), so an oracle address (which can itself be an AA, since AA response units can legitimately emit `app: 'data_feed'` messages) that emits two such data-feed messages from unstable sibling units puts any AA referencing it via `data_feed[[oracles=...]]` on a guaranteed crash path.

This `throw` propagates synchronously out of the `Array.sort` callback, out of `readDataFeedValue`, and up through the un-guarded async chain used by AA trigger processing (`aa_composer.handleTrigger` → `evaluateAA` → formula `evaluate`). There is no `try/catch` around this call chain, so the exception becomes an uncaught exception. ocore's own top-level handler explicitly turns this into a full node crash:

```
process.on('uncaughtException', (err) => {
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [5](#0-4) 

This is precisely the same design tension the developers acknowledge elsewhere: they run a defensive "dry run" of a primary AA trigger before saving the triggering unit specifically because trigger execution can crash — *"if it would crash, let it crash now, not when we execute the trigger for real"* [6](#0-5) . The dry run only protects the poster's own node at submission time; every other full node in the network still executes the real trigger through `handlePrimaryAATrigger` → `handleTrigger` at consensus time and will hit the identical uncaught `throw`, crashing independently.

### Impact Explanation
Any full node that stabilizes the main-chain unit containing the qualifying trigger will execute `handleTrigger`, hit the unguarded `throw`, and crash via the `uncaughtException` handler. Since crash is deterministic given the same DAG state and formula, this is not a local/one-node problem — every up-to-date full node (including witnesses) that processes the same stabilizing unit will crash in the same place. That halts confirmation of new units network-wide until node operators patch/restart with the offending trigger removed or excluded, matching the "network unable to confirm new units" impact bar and the CVE's "hang or frequently repeatable crash (complete DOS)" characterization.

### Likelihood Explanation
Reaching the crash requires an attacker to control (or use) an oracle address that is an AA emitting `data_feed` messages from its own response units, and to arrange for two sibling unstable units carrying a matching data-feed value/name at equal `level`/`latest_included_mc_index` — both realistic and reproducible conditions in ocore's DAG (equal `level` between concurrent sibling units is common, not adversarial). No hub/peer compromise, TLS, or catch-up/sync path is needed — only an ordinary AA author defining the vulnerable `data_feed[[]]` reference and an ordinary unit poster sending the triggering payment. This matches the CVSS profile of the analog (network-reachable, no special peer privilege, but some precondition/complexity to arrange the exact race in candidate mci/level).

### Recommendation
In `readDataFeedValue`, when `bIncludeAllUnstable` is false and candidates cannot be strictly ordered, do not `throw`; instead treat the ambiguity the same way `ifseveral === 'abort'`/`bAbortedBecauseOfSeveral` is handled elsewhere (return an aborted/ambiguous result so the oscript evaluator can fail the AA response gracefully with a bounce, rather than crashing the process) — see `data_feeds.js:255-267`. More generally, ensure AA trigger execution (`aa_composer.js` `handleTrigger`/`evaluateAA`) cannot allow a single crafted trigger/oracle interaction to produce an uncaught exception that reaches `process.on('uncaughtException')` in `network.js:4530-4543`; wrap formula evaluation entry points so any internal invariant violation from feed data is converted into a bounce/error response instead of a fatal process crash.

### Proof of Concept
1. Deploy AA `Oracle` whose response template includes a `data_feed` message (e.g., `messages: [{app: 'data_feed', payload: {price: "{trigger.data.p}"}}]`), and deploy AA `Consumer` whose formula includes `data_feed[[oracles=Oracle_address, feed_name='price', ifseveral='last']]`.
2. Send two independent triggering units to `Oracle` in quick succession such that the two resulting unstable AA-response units become siblings sharing the same `level` and the same `latest_included_mc_index` in the DAG (both include the same parent set / are composed before either stabilizes) — both units include a `data_feed` `price` message.
3. Send a triggering unit to `Consumer` (any unprivileged unit poster) causing it to evaluate `data_feed[[oracles=Oracle_address, feed_name='price', ...]]`.
4. On every full node, `readDataFeedValue` collects both `Oracle` response units as `arrCandidates` with equal `latest_included_mc_index` and `level`; the `sort()` comparator hits `throw Error("can't sort candidates ...")`, which is uncaught and triggers `process.on('uncaughtException')` in `network.js`, crashing the node process.
