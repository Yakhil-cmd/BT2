### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the repository actually written to is resolved from the independent, unverified `repository.full_name` field, allowing cross-organization webhook forgery in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and therefore the HMAC secret) used to validate `X-Hub-Signature` based on `repository.owner.login` (or `organization.login`) taken from the raw JSON body. All webhook handlers, however, resolve which `Repository`/`Stack` to act on using `repository.full_name`, a separate, uncorrelated field of the same body [1](#0-0) [2](#0-1) [3](#0-2) . Nothing enforces that `repository.full_name` is prefixed by `repository.owner.login`. In a "Multiple GitHub Applications" deployment (explicitly documented and supported, one App/webhook secret per GitHub organization) [4](#0-3) , an attacker who knows/controls one organization's own App webhook secret can forge a signed payload whose `repository.owner.login` is their own org (so the signature check passes) but whose `repository.full_name` names a stack belonging to a completely different organization, causing Shipit to act on that other organization's data.

### Finding Description
This is the same class of bug as the reported ERC4626 `maxDeposit`/`maxMint` vs `maxWithdraw`/`maxRedeem` inconsistency: two logically related guards/lookups that are supposed to refer to the *same* entity diverge, and only one of them is actually protected/verified.

- `verify_signature` picks the signing organization exclusively via:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 
and verifies the raw body's HMAC using `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) .

- Every handler resolves the target `Repository`/`Stack` via a *different* field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

The same disjunction exists in the pull-request handlers, which resolve `Repository.from_github_repo_name(params.repository.full_name)` independently of the field used to select the verifying App [5](#0-4) [6](#0-5) .

Because JSON is attacker-supplied plaintext and the HMAC only proves "whoever produced this exact byte sequence knew organization A's webhook secret," nothing prevents that byte sequence from containing `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/some-repo"` simultaneously. The signature check equality is effectively:

`verified organization (repository.owner.login) == organization whose secret was used to sign`

while the actually consumed equality by the rest of the pipeline is:

`acted-upon repository (repository.full_name) == whatever the attacker wrote`

These two are never checked against each other, breaking the intended binding "organization that authenticated == repository that is written."

Per `docs/setup.md`, Shipit explicitly supports one GitHub App (and one webhook secret) per organization for exactly this multi-tenant scenario [4](#0-3) , confirmed by the `GithubApp#initialize`/`webhook_secret` per-organization config resolution [7](#0-6)  and by the test fixture demonstrating two independently-configured orgs/apps/secrets [8](#0-7) . Any customer/organization onboarded onto such a shared Shipit instance is, by design, entrusted only with their own App's webhook secret — not with the ability to write into other tenants' stacks.

### Impact Explanation
Using a secret that belongs only to their own organization's GitHub App, an attacker can forge webhook events that are processed as if they originated from any other organization's repository configured on the same Shipit instance:
- `StatusHandler` directly writes a `Status` on any existing commit whose sha the attacker guesses, purely from unverified payload fields (`state`, `description`, `target_url`, `context`), with no additional call back to GitHub [9](#0-8) . Faking a green CI status on someone else's commit can flip `Commit#deployable?` and enable/unblock deploys for a stack the attacker does not own.
- `PushHandler` enqueues `GithubSyncJob`/continuous delivery for any target org's stack on demand [10](#0-9) , letting an attacker force out-of-schedule deploys of another organization's stacks.
- `PullRequest::EditedHandler`/`ClosedHandler`/`ReopenedHandler` mutate PR-tracked state (`github_pull_request`, archive/unarchive review stacks) for another organization's repositories using only attacker-controlled JSON [11](#0-10) [12](#0-11) .

This meets the required Critical bar of "unauthorized deploy, rollback, or merge" and cross-tenant/cross-repository writes, since a party that legitimately controls only Organization A's GitHub App secret can trigger state changes and deploy pipelines for Organization B's stacks on the same Shipit instance.

### Likelihood Explanation
This requires the operator to run Shipit in the officially documented "Multiple GitHub Applications" mode with more than one tenant organization sharing a single Shipit instance — a supported, non-exotic configuration explicitly documented for multi-org use [4](#0-3) . Any org administrator in that shared instance (who legitimately knows/controls their own org's App webhook secret because they configured the GitHub App) is an "unprivileged attacker" with respect to every other org's stacks, and can craft the forged body and signature entirely offline (no interaction with GitHub, no privileged Shipit session or `ApiClient` token needed) before POSTing to `/github/webhooks`.

### Recommendation
In `WebhooksController#verify_signature`, ensure the field used to select the signing App/secret is the same field the handlers subsequently trust to resolve the target repository, and reject requests where they disagree — e.g., derive the App from `repository.full_name`'s owner segment (or cross-check `repository.owner.login` against the owner segment of `repository.full_name`) before dispatching to handlers. Handlers should also refuse to act if `repository.full_name`'s owner does not match the verified organization for the request.

### Proof of Concept
1. Operator runs Shipit configured for two GitHub organizations, `OrgA` and `OrgB`, each with its own GitHub App and webhook secret, per the documented multi-app setup [4](#0-3) .
2. Attacker legitimately administers `OrgA`'s GitHub App (or otherwise possesses `OrgA`'s `webhook_secret`) and knows `OrgB` has a stack tracked in this Shipit instance (e.g., `orgb/service`).
3. Attacker builds a `push` (or `status`) webhook JSON body with:
   ```json
   {
     "repository": { "owner": {"login": "OrgA"}, "full_name": "orgb/service" },
     "ref": "refs/heads/main",
     "after": "<some sha>"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
5. `verify_signature` computes `repository_owner = "OrgA"` [2](#0-1) , loads `Shipit.github(organization: "OrgA")`, and the HMAC check passes because the attacker signed with `OrgA`'s real secret [1](#0-0) .
6. `PushHandler`/`Handler#repository_name` reads `repository.full_name = "orgb/service"` [13](#0-12) , resolves `OrgB`'s real `Stack`, and enqueues `GithubSyncJob`/continuous delivery for it, even though the attacker has no relationship to `OrgB` [10](#0-9) .
