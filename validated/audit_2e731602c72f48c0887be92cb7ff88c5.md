### Title
Webhook `status` events are applied to commits by SHA alone, letting an attacker with their own valid GitHub App installation forge CI status for commits belonging to a stack/repository they don't own - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
This is the same trust-binding break described in the report: two pieces of data are extracted from a signed message, but only one of them is bound to the verification step, so the "verified" value and the "acted-upon" value can diverge. In `mod.nr`, the verified header covers the whole sequence, but `header_field_name` (used to decide where the value starts) is never checked against what was actually signed, so an attacker can shift the boundary. In shipit-engine, `WebhooksController#verify_signature` selects the webhook secret to check the HMAC using `repository_owner` (`params.dig('repository', 'owner', 'login')`), i.e. it authenticates *who signed this payload*. But `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that binding when deciding *what to write*: it looks up commits purely by `sha`, globally, across every stack/repository in the installation.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/organization config with `Shipit.github(organization: repository_owner)` and verifies the HMAC signature against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the controller dispatches to handlers with the raw parsed payload, with no additional scoping: [3](#0-2) 

`StatusHandler#process` then resolves target `Commit` records purely by `sha`, with no filter on repository or stack ownership: [4](#0-3) 

`Commit belongs_to :stack`, and `Status` records are attached to whichever stack the found commit actually belongs to, not to any stack derived from the verified `repository_owner`: [5](#0-4) 

Compare this with every other handler (`push`, `pull_request`, etc.), which correctly re-derive the repository from the payload and scope their side effects to `Repository.from_github_repo_name(...)`: [6](#0-5) [7](#0-6) 

The equality that should hold but doesn't:
`organization authenticated by verify_signature (repository_owner)` == `stack/repository whose commit status StatusHandler writes to`.

`StatusHandler` breaks this binding because it resolves the target purely from an attacker-controlled `sha` string, which is not tied at all to the signing organization. Any entity that can obtain a validly-signed webhook for *some* organization/installation known to Shipit (e.g., they administer their own GitHub organization/repo that has the Shipit GitHub App installed, and thus legitimately possess/can trigger use of that org's `webhook_secret`) can send a `status` event whose `sha` matches a commit that exists under a completely different stack/repository. Shipit will happily record the fabricated status (e.g., `state: success`) against that unrelated commit, because `Commit.where(sha: params.sha)` is global.

### Impact Explanation
CI status gates deploys: `Commit#deployable?` and downstream `blocked?`/`required_statuses` checks rely on `Status` records to decide whether commits are safe to deploy or block continuous delivery: [8](#0-7) 

By forging a successful status for a commit SHA that belongs to a stack the attacker has no legitimate access to, an attacker can clear a required/blocking CI check on someone else's stack, enabling an unauthorized deploy of a commit that never actually passed the real CI pipeline for that repository. This matches the accepted "unauthorized deploy" impact category, achieved purely by exploiting a payload field (`sha`) that is never bound to the verified signer.

### Likelihood Explanation
The likelihood depends on the attacker being able to name a commit `sha` that exists in the target stack's `commits` table. This is realistic in common scenarios: forked repositories share commit SHAs with the upstream/target repo until history diverges, and commit SHAs of public/target repositories are often directly observable (GitHub API, git log) even by an outsider. The attacker only needs their own org/repo with the Shipit GitHub App or webhook configured (an unprivileged, self-service action, not requiring any access to the victim's stack, GITHUB_TOKEN, or an ApiClient/session), then send a normal `status` webhook naming the target SHA.

### Recommendation
Scope `StatusHandler` (and any other handler that looks up by cross-stack-unique identifiers) to the repository/stack derived from the verified organization, mirroring what `Handler#stacks`/`Repository.from_github_repo_name` already do for other handlers. Concretely, `StatusHandler#process` should restrict `Commit.where(sha: params.sha)` to `stacks` (i.e. commits whose `stack_id` belongs to `Repository.from_github_repo_name(repository_name).stacks`), so a status can only be attributed to a commit in a repository whose ownership matches the organization that produced the signature.

### Proof of Concept
1. Attacker creates/controls a GitHub organization `attacker-org` and installs/enables the Shipit GitHub App/webhook on a repository they own there, obtaining a legitimately signed webhook channel (their own `webhook_secret`).
2. Attacker identifies (via public GitHub history, a fork, or prior observation) the git `sha` of a commit that exists in a target stack belonging to a different, unrelated organization `victim-org` tracked by the same Shipit instance.
3. Attacker triggers (or crafts, if they control raw delivery) a `status` event payload:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" } }
   }
   ```
   signed with `attacker-org`'s webhook secret.
4. `WebhooksController#verify_signature` validates the signature successfully because it only checks that the payload was signed by `attacker-org`'s secret.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (regardless of stack/org), and calls `create_status_from_github!`, recording a fabricated `success` status against `victim-org`'s stack.
6. If that status was a required/blocking check for `victim-org`'s stack, the victim commit can now be deployed even though it never passed real CI.
