### Title
Authentication bypass in arbiter dispute "mutually signed" check via string-prefix path matching - (File: wallet.js)

### Summary
The `arbiter_dispute_request` handler in `wallet.js` verifies that a shared-address signing unit was actually co-signed by both contract parties before accepting a dispute, using a `startsWith`-based prefix check on signing paths instead of exact/structural path matching. This mirrors the Alpine `AuthenticationFilter` bug class: a security decision is made by testing whether one string is a *prefix* of another rather than verifying the actual structural/semantic boundary, allowing a crafted value to satisfy the check without providing the intended proof.

### Finding Description
In the `arbiter_dispute_request` case, after locating the shared-address author in the referenced signing unit, the code determines whether both parties signed with: [1](#0-0) 

```
const signing_paths = Object.keys(author.authentifiers);
const isMutuallySigned = signing_paths.find(p => p.startsWith('r.0.0')) && signing_paths.find(p => p.startsWith('r.0.1'));
if (!isMutuallySigned)
    return callbacks.ifError(...);
```

This uses `String.prototype.startsWith` on dot-separated oscript definition paths (e.g. `r.0.0`, `r.0.1`, `r.0.10`, `r.0.100`, etc.) instead of an exact match or a proper path-segment boundary check (e.g. `p === 'r.0.0' || p.startsWith('r.0.0.')`). Because oscript/definition paths are built by appending numeric indices with `path+'.'+index` (see the recursive definition evaluator in `definition.js`), sibling branches under the same parent can have path strings that are literal string-prefixes of each other without being nested under one another — e.g. `r.0.1` is a literal prefix of `r.0.10`, `r.0.100`, etc., even though `r.0.10` is a completely different branch of the "and"/"or" tree than `r.0.1`.

The signing_paths and their signatures come entirely from the referenced unit's `author.authentifiers`, whose keys are attacker-influenceable via how the offeror constructs/signs their own branch of the mutual-signing definition (which is itself a nested `and`/`or`/`r of set` structure per party, as seen in `definition.js`'s path-building logic for `or`/`and`/`r of set`/`weighted and`). A party fully controlling one side of a "mutual signing" 2-of-2 structure (or any nested sub-condition under their own branch that happens to have a numeric index producing a path like `r.0.10`) can produce a unit where every real signature belongs to only one party, yet `signing_paths` contains an entry that is a string-literal-prefix match for `r.0.1` (intended to represent the *other* party's branch) purely due to numeric path collision, satisfying `isMutuallySigned` without genuine co-signature from the counterparty.

### Impact Explanation
If `isMutuallySigned` is bypassed, the arbiter's wallet will accept a dispute request as valid (`arbiter_contract.insertDispute`) and proceed to notify the arbiter of a dispute over a shared-address contract that was not actually mutually agreed/signed by both parties. This is a business-logic authentication bypass on a private-payment/contract flow reachable by an unprivileged peer (an "arbstore"/counterparty) that gates access to arbiter dispute handling — the same trust-check pattern (and same bug class: prefix-based path/URL matching used for an authorization decision) as the referenced Alpine CVE. It allows one party to a shared/multisig arbiter contract to fabricate the appearance of "mutual signing" and push a dispute into the arbiter's workflow that could ultimately influence a fund release decision through the arbiter, without the counterparty's true participation.

### Likelihood Explanation
Medium: exploitation requires the attacker to control the "arbstore" role (or compromise/spoof the arbstore device address check) or otherwise get a shared-address signing unit accepted by the arbiter's wallet with crafted paths, and to engineer their own signed branch of the multisig definition so that a numeric path segment coincides as a string-prefix of the sibling branch's path (e.g., index `10` under the same parent as index `1`). This requires no special network position, no key compromise, and no privileged role beyond being one of the two contracting parties — it is reachable purely by constructing/signing a specially-shaped address definition and associated unit.

### Recommendation
Replace the `startsWith` prefix check with an exact match or an explicit path-boundary check, e.g.:
```js
const isMutuallySigned =
    signing_paths.some(p => p === 'r.0.0' || p.startsWith('r.0.0.')) &&
    signing_paths.some(p => p === 'r.0.1' || p.startsWith('r.0.1.'));
```
More robust: derive the expected offeror/acceptor sub-paths from the actual parsed `definition` structure (as already done a few lines later for `offeror_address`/`acceptor_address`) rather than assuming fixed literal path prefixes, and verify signatures are present at the exact expected sub-paths.

### Proof of Concept
1. Party A (offeror) and Party B (acceptor) create a shared address whose definition places branch 0 at path `r.0.0` (A's signing condition) and branch 1 at path `r.0.1` (B's signing condition), per the standard arbiter mutual-signing template.
2. Instead of a simple `sig` at `r.0.0`, Party A negotiates/uses (or is able to construct, e.g. via a multi-option `or`/`r of set` under their own branch) a definition where one of A's own sub-conditions resolves to signing path `r.0.10` (an 11th option in an `or`/`r of set` under `r.0`, or any nested structure that numerically produces this string) — entirely within A's own control, requiring no cooperation from B.
3. Party A signs the unit only with their own key(s), producing `author.authentifiers` containing keys such as `r.0.0` and `r.0.10`, with no genuine `r.0.1`-rooted signature from B.
4. Party A (posing as, or via, the arbstore/counterparty flow) sends `arbiter_dispute_request` referencing this unit.
5. In the arbiter's wallet, `signing_paths.find(p => p.startsWith('r.0.1'))` matches `r.0.10`, so `isMutuallySigned` evaluates to true even though B never signed, and the dispute is inserted and forwarded to the arbiter as if it were a legitimately mutually-signed contract.
