### Title
First-investor share-price manipulation in the sample Uniswap-like market-maker AA drains market-maker balance - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The "invest in MM" message case in the bundled Uniswap-like market-maker autonomous agent mints `mm_asset` shares to a trigger sender whenever *either* side of the pool (asset or bytes) is momentarily zero, without verifying that `var['mm_asset_outstanding']` (the actual outstanding-shares accounting variable) is also zero. This mirrors the CouncilMember/Sablier bug: a payout/mint routine trusts a raw balance snapshot instead of the tracked-accrual state variable, so whoever is first to trigger while the two are out of sync can mint shares worth far more than their real economic stake and later redeem them for a disproportionate share of the pool.

### Finding Description
In the "invest in MM" case: [1](#0-0) 

the code computes:
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
```
This "initial deposit" branch is keyed purely off the AA's live coin `balance[...]`, not off `var['mm_asset_outstanding']`, which is the actual bookkeeping variable used everywhere else (divest, in `$investor_share = $mm_asset_amount / var['mm_asset_outstanding']` at line 73) to determine each holder's claim on the pool. Any state in which `asset_balance` or `bytes_balance` is (momentarily) 0 — for example immediately after the pool's `$asset` inventory is fully swapped out via the "exchange asset to bytes"/"exchange bytes to asset" cases, or before the second side of a fresh deposit is fully accounted for — causes `$issue_amount` to be set to the *entire current byte balance* of the AA rather than a value proportional to `mm_asset_outstanding`. Because divestment later pays out `$investor_share * balance[...]` using this same outstanding-shares denominator, whoever manages to trigger during this zero-balance window is minted shares that materially over-represent their contribution relative to existing/outstanding shares, and can then divest to claim assets belonging to other depositors — directly analogous to the report's "first CouncilNFT holder retrieves before the pool is fully populated, capturing the whole stream."

### Impact Explanation
An unprivileged AA trigger sender who races to trigger the "invest in MM" case at a moment when `asset_balance` or `bytes_balance` transiently equals zero (a state reachable through normal use of the AA's own exchange cases, not requiring any privileged access) can be issued `mm_asset` shares equal to the AA's full byte balance instead of a value consistent with `var['mm_asset_outstanding']`. Subsequent divestment (`$investor_share * balance[...]`) then pays out real asset/byte holdings disproportionate to actual contribution, draining funds that belong to other liquidity providers — an AA fund-loss scenario consistent with the required "concrete unauthorized spending / AA fund loss" impact bar.

### Likelihood Explanation
The zero-balance condition is reachable purely through normal, permissionless interaction with the AA (deposits, and the "exchange asset to bytes"/"exchange bytes to asset" cases can fully drain one side of the pool), so no privileged role or off-chain assumption is required — an attacker simply needs to time (or trigger) a unit when the imbalance condition holds, exactly like the original report's front-run of the first mint.

### Recommendation
Gate the "initial deposit" branch on `var['mm_asset_outstanding'] == 0` (the tracked share-accounting state) rather than on the raw, momentarily-zero `balance[...]` values, so that share issuance is always computed against the accrual variable and cannot be manipulated by transient zero-balance states caused by normal pool activity.

### Proof of Concept
1. Bootstrap the market maker AA and let a legitimate investor deposit, receiving `mm_asset` proportional to `var['mm_asset_outstanding']`.
2. Trigger the "exchange asset to bytes" case repeatedly (or via a single large trigger) until `balance[$asset]` (net of the current trigger's own output) reaches 0, while `var['mm_asset_outstanding']` remains non-zero and bytes remain in the pool.
3. Immediately send an "invest in MM" trigger with only bytes (no `$asset` in the payload beyond the required check bypass) so that `$asset_balance == 0` is true; the AA falls into the "initial deposit" branch and sets `$issue_amount = balance[base]` — the entire byte balance of the pool — even though `var['mm_asset_outstanding']` is non-zero and other holders' shares still exist.
4. Immediately divest with the newly minted `mm_asset`, receiving `$investor_share * balance[...]` computed against the now-inflated `mm_asset_outstanding`, capturing value that rightfully belongs to the earlier depositor.
