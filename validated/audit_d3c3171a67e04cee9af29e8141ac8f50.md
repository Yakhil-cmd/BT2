**Analysis:** `ConcurrentSupplyResource` in [1](#0-0)  is a plain `Deserialize`/`Serialize` derive struct wrapping `AggregatorResource<u128>`. Its only usages in the codebase are in benchmark and testing tooling — `execution/executor-benchmark/src/native/parallel_uncoordinated_block_executor.rs`, `execution/executor-benchmark/src/db_access.rs`, `execution/executor-benchmark/src/native/native_vm.rs`, `aptos-move/e2e-tests/src/executor.rs`, and `aptos-move/replay-benchmark/src/diff.rs` — none of which are part of the transaction admission path (mempool prevalidation, `vm-validator`, or VM prologue).

The actual gas-affordability check used during transaction admission is performed on-chain in Move via `aptos_account::is_fungible_balance_at_least(gas_payer_address, max_transaction_fee)` inside the prologue, e.g. `unified_prologue_v3`/related functions in [2](#0-1)  and the epilogue's fee-charging check in [3](#0-2) . These balance assertions read on-chain state through the Move VM's global storage abstraction, not through Rust-side BCS deserialization of `ConcurrentSupplyResource`, so a malformed/truncated payload fed to `ConcurrentSupplyResource::deserialize` has no bearing on mempool's or vm-validator's gas-affordability decision — there is no code path where mempool prevalidation deserializes this specific struct to compute or default a payer balance.

Since the struct is never on the admission/validation path (no mempool code, no `vm-validator` code, no prologue-related Rust deserialization uses it), the premised exploit path does not exist in this codebase.
