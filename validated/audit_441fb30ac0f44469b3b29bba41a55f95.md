## Finding

Based on my investigation, the strongest admission-boundary analog to the reported bug (stale cumulative state not reset on remove+re-add) is a **stale multisig approval reactivation** in `multisig_account.move`.

### Title
Stale owner approvals are silently reactivated when an owner is removed and later re-added to a multisig account - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MultisigTransaction.votes` records approvals/rejections keyed by owner address. Approval counting (`num_approvals_and_rejections_internal`) is computed dynamically by intersecting the **current** owner list with the stored votes map, rather than by tracking approvals tied to owner-membership epochs. `update_owner_schema` — the function backing `add_owners`, `remove_owners`, and `swap_owner` — only mutates `owners`, `num_signatures_required`, and timelock override state; it never touches `transactions` or any per-transaction `votes` map.

### Finding Description
The vote-counting logic: [1](#0-0) 
counts a vote for `owner` if `owner` is present in the *current* owners vector and has an entry in `transaction.votes`, regardless of when that vote entry was created.

`update_owner_schema`, which implements owner removal/re-addition, never clears or invalidates any pending transaction's `votes` map when an owner is removed: [2](#0-1) 

The existing test suite confirms the intended safety property only for the "removed and never re-added" case — a removed owner's vote is excluded because they're absent from the current owner list: [3](#0-2) 

However, this same test demonstrates the mechanism that creates the flaw: the safety check is purely membership-based, not vote-timestamp/epoch based. Since the `votes` map entry is never purged from the pending `MultisigTransaction` on removal, if that same owner address is later re-added (via `add_owners`/`swap_owner`), their old, stale approval automatically counts again toward quorum for any transaction that was pending across the removal/re-addition window — without the owner casting a new vote.

### Impact Explanation
This is a stale-approval-set confusion analogous to the external report's stale-accumulator issue: state associated with a revoked participant is not reset, and reactivating that participant silently restores unearned "credit" (here, an approval) toward a security threshold. This could let a multisig transaction execute with fewer *genuine, current* approvals than `num_signatures_required` mandates — i.e., the wrong approval set is accepted at execution. This is High impact because it undermines the fundamental multisig guarantee that N-of-M *current* owners must independently authorize an action.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) a transaction proposed and partially approved, (b) an owner-set change removing then re-adding the same address while that transaction remains pending (not yet executed/expired), and (c) the multisig's own governance process to legitimately perform such a remove+re-add sequence (e.g., temporarily removing a suspected/compromised owner, then reinstating them after verification) — a plausible real-world administrative action.

### Recommendation
Clear or invalidate `votes` entries for owners removed via `update_owner_schema`'s `owners_to_remove` path (iterate pending `transactions` and remove/expire the departed owner's vote), or track vote validity per owner-membership generation rather than by raw address membership.

### Proof of Concept (conceptual, based on observed code)
1. Multisig account with owners `[A, B, C]`, threshold 2.
2. `create_transaction` proposes `T` (sequence number N); `A` (proposer) auto-votes yes.
3. `B` calls `approve_transaction(B, multisig, N)` is NOT done yet — only `A`'s vote exists; `can_be_executed` is false.
4. Owners execute a governance multisig transaction calling `remove_owners([A])` — `A` removed for review, `T` remains pending, `votes[A]=true` untouched in storage.
5. Owners later execute `add_owners([A])`, restoring `A` to the owner list.
6. `num_approvals_and_rejections` now counts `A`'s stale vote from step 2 again (since `A` is back in `owners` and `votes` still has the entry) plus any single legitimate new vote, reaching quorum without `A` re-affirming intent on `T`, potentially executing a transaction `A` never actually endorsed post-reinstatement.

### Caveat
I was unable to retrieve the full source of the `vote()` helper function and the exact `create_transaction`/`approve_transaction` entry points in this session (tool budget exhausted), so the precise mechanics of vote insertion could not be fully cross-checked beyond what is cited above; the `update_owner_schema` code and `num_approvals_and_rejections_internal` code shown are the direct, verified evidence for this finding.

    inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
        let num_approvals = 0;
        let num_rejections = 0;

        let votes = &transaction.votes;
        owners.for_each_ref(|owner| {
            if (simple_map::contains_key(votes, owner)) {
                if (*simple_map::borrow(votes, owner)) {
                    num_approvals += 1;
                } else {
                    num_rejections += 1;
                };
            }
        });

        (num_approvals, num_rejections)
    }

    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
