### Title
Webhook signing organization is decoupled from the repository the event is applied to, allowing forged cross-repo/cross-org webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate the inbound HMAC signature against based on `repository_owner`, a value read straight out of the untrusted, unsigned-at-selection-time JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Every downstream `Webhooks::Handlers::Handler` instead resolves the target `Stack`/`Repository` using a *different* field from that same body, `payload.dig('repository', 'full_name')`. Because Shipit supports hosting multiple GitHub organizations with independently configured (and individually optional) `webhook_secret`s, these two fields are never cross-validated against each other.

### Finding Description
`verify_signature` picks the app/secret to check with: [1](#0-0) 

`repository_owner` comes from the JSON body itself: [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats an unset (optional, per `docs/setup.md`) secret as automatically valid: [3](#0-2) 

Meanwhile, the handler base class resolves the `Stack`/`Repository` that is actually mutated using `repository.full_name`, a completely independent field of the same untrusted body: [4](#0-3) 

`PushHandler` uses this to trigger `stack.sync_github`, and `MembershipHandler` uses the (also attacker-controlled) `organization.login` field to create/join `Team`/`Membership` records that feed directly into `Shipit.github_teams` authorization checks: [5](#0-4) [6](#0-5) 

The equality this breaks: **`repository_owner`, the organization whose secret authenticates the request, is never proven equal to `repository.full_name`/`organization.login`, the repository/organization whose state the handler actually writes.** This is analogous to the AppChain report's core defect — a value that is checked in one code path (`register_appchain`'s `sender_id != owner` check) is not enforced in the parallel code path (`transfer_appchain_ownership`) that performs the equivalent privileged action. Here, the "authorization key selection" field (`repository_owner`) and the "entity acted upon" field (`repository.full_name` / `organization.login`) are structurally parallel but never reconciled, exactly matching the allowed analog class: "an organization that authenticated versus the repository that is written."

Because Shipit explicitly supports multi-org deployments (see `config/secrets.development.shopify.yml`) where `webhook_secret` is documented as **optional** per org (`docs/setup.md` line 30, `secrets.development.example.yml` line 11), any org onboarded to the same Shipit instance without a configured `webhook_secret` becomes a skeleton key: an attacker only needs to know that org's login to satisfy `verify_signature` (since `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank), while freely setting `repository.full_name`/`organization.login` to point at a victim repository/org whose stacks and teams are managed by this same instance.

### Impact Explanation
* Forging a `push` event lets an unprivileged external attacker trigger `GithubSyncJob`/`stack.sync_github` for arbitrary stacks not owned by the organization used to pass signature verification — effectively unauthorized state manipulation of a stack's commit history tracking, which drives what commits are deployable.
* Forging a `membership` event lets an attacker create arbitrary `Team`/`Membership` records and add an arbitrary `User` (attacker-controlled GitHub login previously authenticated via OAuth) to any team, including ones listed in `Shipit.github_teams`, which is exactly the authorization gate checked in `User#authorized?`: [7](#0-6) 
This is a direct escalation into `Shipit.github_teams` authorization — an explicitly listed High-severity impact.

### Likelihood Explanation
Exploitation requires: (1) the deployed Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) at least one onboarded organization to have no `webhook_secret` set (explicitly documented as optional) — or an attacker who already knows/has one org's `webhook_secret` (e.g., a low-privilege org they control) but targets a *different* org's stacks/teams. Given the engine explicitly documents `webhook_secret` as optional and ships example multi-org configs, this is a realistic, reachable configuration, not a purely theoretical one.

### Recommendation
`WebhooksController#verify_signature` and every `Handler` must derive the authorizing organization and the acted-upon repository/organization from the same trusted binding. Concretely:
- After selecting the `github_app` via `repository_owner`, require that `repository.full_name`'s owner segment (and `organization.login` for org-level events) equals `repository_owner` before dispatching to handlers, rejecting mismatches with `422`.
- Do not treat a blank/unset `webhook_secret` as automatically valid for organizations that host writable resources (stacks/teams) shared with other orgs on the same instance; at minimum, log/alert and require an explicit opt-in for "no signature verification" per organization.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two GitHub orgs, e.g. `victim-org` (has stacks/teams, `webhook_secret` set) and `attacker-org` (onboarded, but `webhook_secret` left blank as documented "optional").
2. As an unauthenticated external attacker, POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 1, "name": "victim-team", "slug": "victim-team", "url": "https://api.github.com/..." },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header (`lib/shipit/github_app.rb:76-83`).
4. `MembershipHandler#process` is invoked with `organization.login == "victim-org"`, creating/joining the attacker's account to `victim-team` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-43`), which, if that team is listed in `Shipit.github_teams`, grants the attacker's already-authenticated Shipit `User` account authorization to the instance.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
