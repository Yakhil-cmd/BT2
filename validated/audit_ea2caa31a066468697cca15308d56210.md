## Title
AA payments to spender-attested / condition-restricted assets cause the entire trigger response to bounce, permanently freezing state and funds - (File: `aa_composer.js`)

### Summary
The Sherlock report describes a lending contract that unconditionally pushes leftover collateral back to the borrower in USDC during liquidation. If USDC has blacklisted that borrower, the `transfer()` reverts, the whole liquidation transaction reverts, and the loan can never be liquidated, creating permanent bad debt.

Obyte's Autonomous Agents (AAs) have an exact structural analog: an asset can be defined with `spender_attested` (only addresses currently on an attestor's whitelist may receive/hold it) or a `transfer_condition`/`issue_condition` formula. If an AA's business logic (e.g. a lending/marketplace/escrow AA) is coded to unconditionally pay some address (typically `trigger.address`, i.e. the counterparty) in such a restricted asset, and that address later fails the attestation/condition check, the AA response unit fails validation and the **entire trigger is bounced** — all of the AA's intended state changes (marking a loan as repaid/liquidated, releasing a listed item, etc.) are rolled back, while the underlying protocol state remains stuck in the same condition forever.

### Finding Description
When an AA composes its response, `aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` only checks that an asset is not private and not fixed-denomination before adding it to the payload; it does **not** pre-check `spender_attested` or `transfer_condition` against the actual recipient addresses: [1](#0-0) 

The payload is only fully validated later, when the composed unit is run through the ordinary unit-validation pipeline via `validateAndSaveUnit()`: [2](#0-1) 

That validation path is `validatePaymentInputsAndOutputs()` in `validation.js`, which enforces, for any asset with `spender_attested`, that *all* output addresses are currently attested, and for any `issue_condition`/`transfer_condition`, that the condition formula evaluates true: [3](#0-2) 

If either check fails, `ifUnitError` fires and returns the error to the composer's callback, which triggers `bounce(err)`: [4](#0-3) 

`bounce()` discards all pending state changes (`objStateUpdate = null`) and, at best, refunds the trigger sender's bytes minus the bounce fee — it does **not** perform the payment nor advance any of the AA's application-level state: [5](#0-4) 

So exactly like the JOJO/USDC case, a mandatory payout embedded in the "happy path" logic of the AA (e.g., "return collateral to `trigger.address`" or "return leftover proceeds to `trigger.initial_address`") becomes an unconditional dependency on a third party's attestor list or transfer-condition formula for that specific address. If that dependency becomes false for the intended recipient (attestor revokes attestation, condition formula becomes false, e.g., due to KYC revocation, sanction, or any oracle-driven condition), every subsequent attempt to trigger that AA logic bounces identically, and the underlying position (loan, escrow, listed item, locked funds) can never be resolved.

### Impact Explanation
The AA's held funds/asset become permanently stuck and the business logic it implements (e.g., liquidation, settlement, escrow release) becomes permanently non-executable for that address, matching the "AA fund loss or freezing" impact class. Because the freeze is deterministic (every future trigger produces the exact same bounce), there is no way for the counterparty or protocol to recover without an out-of-band, off-protocol change to the attestor list or condition formula — this is a design footgun baked into how `sendUnit`/`bounce` interact with `spender_attested`/`transfer_condition`, not something the AA author can defend against generically (there's no supported pattern for "credit an internal balance the recipient can withdraw later instead of forcing a push payment").

### Likelihood Explanation
Any AA author building on top of a `spender_attested` or `transfer_condition`-gated asset (which are first-class, commonly used ocore features intended precisely for compliance/whitelisting use cases) and coding a mandatory payout to `trigger.address`/`trigger.initial_address` is exposed. The trigger sender does not need to be malicious — the condition can become false through the ordinary operation of the attestor or condition, exactly mirroring how USDC's blacklist is an ordinary, foreseeable operational event, not an exploit by the borrower.

### Recommendation
- In AA-authoring guidance/documentation, warn against unconditional payouts of `spender_attested`/condition-gated assets to trigger-controlled addresses; recommend crediting an internal, address-keyed state variable that the recipient can pull via a separate trigger, so a failed condition only blocks that specific withdrawal trigger, not the whole settlement/liquidation logic.
- Consider adding an oscript-level helper/getter (e.g., `is_valid_recipient(asset, address)`) so AA logic can pre-check `spender_attested`/condition status before composing the payment, and branch to an alternative "credit-only" path if the check fails, instead of relying on validation-time bounce.

### Proof of Concept
1. Definer publishes asset `A` with `spender_attested: true` and an attestor `X`.
2. An AA is deployed that implements, e.g., a simple escrow/lending pattern: on a qualifying trigger it always pays out remaining balance of asset `A` to `trigger.initial_address`.
3. User `U` (attested by `X`) locks/deposits with the AA, expecting to later trigger the payout.
4. Attestor `X` revokes `U`'s attestation (analogous to USDC blacklisting).
5. `U` sends the trigger to claim the payout. `aa_composer.js` composes the payment message without pre-checking attestation (`aa_composer.js:1323-1330`), builds the unit, and calls `validateAndSaveUnit`.
6. `validation.js`'s `validatePaymentInputsAndOutputs` (`validation.js:2630-2641`) finds `U`'s address is not in `arrAttestedOutputAddresses`, returns `"some output addresses are not attested"`.
7. `aa_composer.js` calls `bounce(err)` (`aa_composer.js:1388-1411`), discarding all state changes; `U`'s locked asset/position remains stuck, and every future retry produces the identical bounce as long as `U` remains unattested.
