### Title
`pull_request` webhook signature verified against `repository.owner.login` while `LabelCapturingHandler` mutates the stack resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/org whose `webhook_secret` authenticates the request using `repository_owner`, which reads `params.dig('repository','owner','login')` [1](#0-0) . The `pull_request` handlers, including `LabelCapturingHandler`, instead resolve the target repository/stack via `Repository.from_github_repo_name(params.repository.full_name)` [2](#0-1) . Because `owner.login` and `full_name`'s owner segment are independently attacker-controlled fields in the JSON body and are never cross-checked, an attacker who owns/controls a repository under an org with no `webhook_secret` configured (so `verify_webhook_signature` returns `true` unconditionally, per `return true unless webhook_secret` [3](#0-2) ) can pass signature verification while pointing `full_name` at a victim org/repo whose stack is then mutated.

### Finding Description
The broken binding: the request should only be able to affect `Repository.find_by(owner: X, name: Y)` where `X` is the same org that authenticated the request via its `webhook_secret`. In code: **the org used in `Shipit.github(organization: repository_owner)` must equal the org embedded in `params.repository.full_name`**. This is never enforced — verification uses `params.dig('repository','owner','login')` while every `PullRequest` handler (`LabelCapturingHandler`, `ClosedHandler`, `OpenedHandler`, `ReopenedHandler`, etc.) uses `params.repository.full_name` via `Repository.from_github_repo_name` [4](#0-3) . These two fields are both simple attacker-controlled strings in the same JSON body and are not required to be consistent by any validation, `ExplicitParameters` schema, or controller code.

Exploit flow:
1. Attacker registers/controls GitHub org `attacker-org` in Shipit with no `webhook_secret` set (or an org they otherwise know the secret for) — a config state, not a secret, they can influence by choosing which org's config Shipit uses.
2. Attacker crafts a `pull_request` webhook body: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `action = "reopened"`, with attacker-chosen `pull_request.labels[].name`.
3. `POST /webhooks` with header `X-Github-Event: pull_request`. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `verify_webhook_signature` returns `true` because that org has no secret configured [5](#0-4) .
4. `create` dispatches to `Shipit::Webhooks.for_event('pull_request')` handlers with the parsed params [6](#0-5) .
5. `LabelCapturingHandler#process` calls `reopened_active_stack?` → resolves `stack` via `review_stack` → `repository` from `params.repository.full_name` = `victim-org/victim-repo`, finds the victim's `ReviewStack`, and persists `pull_request.update!(labels: params.pull_request.labels.map(&:name))` on the **victim's** `PullRequest` [7](#0-6) .
6. `ReviewStack#env` merges those labels, uppercased, as `"true"`-valued env vars into the deploy/rollback environment for that victim stack [8](#0-7) .

Existing guards checked and found insufficient: `drop_unhandled_event` only filters by event type, not payload consistency [9](#0-8) ; `verify_signature` never compares `repository_owner` against `repository.full_name`'s owner segment; the `ExplicitParameters` schema on `LabelCapturingHandler` only validates types/presence of `full_name`, `action`, `labels`, not cross-field integrity with the authenticating org [10](#0-9) .

### Impact Explanation
An unprivileged internet attacker who controls (or names) any org with no webhook secret configured in Shipit can inject arbitrary attacker-chosen "labels" into any other org's `ReviewStack`'s `PullRequest`, which become uppercased environment variables merged into that stack's deploy/rollback `env` [8](#0-7) . Since `ReviewStack < Shipit::Stack`, and the question specifies the affected stack has `environment` set to `production`, this env-variable injection reaches the production deploy/rollback command execution path, constituting a payload for one repository (`attacker-org`) mutating another's stack (`victim-org/victim-repo`) — matching the Critical category "unauthorized deploy/rollback/merge of attacker-controlled code" via injected environment variables reaching `Command`/`PTY.spawn`. This is repeatable against any org/repo combination as long as the attacker's chosen `repository_owner` value maps to an org config with no (or a known) `webhook_secret`.

### Likelihood Explanation
Preconditions: (1) Shipit must have at least one configured GitHub org/app entry with no `webhook_secret` set, or the attacker must otherwise possess/guess that org's secret; (2) the victim repository/org must exist in Shipit as a `Repository` with an active, non-archived `ReviewStack` and an associated `PullRequest` record matching `params.number`; (3) attacker needs no Shipit credentials, session, or API token — only the ability to send an HTTP POST with a forged JSON body and a signature that validates against the no-secret/known-secret org. This is a low-cost, fully repeatable attack requiring only knowledge of Shipit's org configuration (which org lacks a webhook secret) — a config-discovery step, not a secrets-compromise step.

### Recommendation
In `Shipit::WebhooksController#verify_signature`, or earlier in `create`, enforce that the org used to select the `GitHubApp`/secret (`repository_owner`) matches the owner segment parsed from `params.dig('repository','full_name')` before dispatching to handlers; reject the webhook (422) on mismatch. Additionally, every handler resolving `Repository.from_github_repo_name(params.repository.full_name)` should be passed/validated against the already-authenticated organization rather than trusting `full_name` independently.

### Proof of Concept
Minitest plan (in `test/controllers/webhooks_controller_test.rb`, addition — not shown as code since out-of-scope paths excluded per rules, but described):
1. Configure two orgs in `Shipit.github_apps`: `"attacker-org"` with no `webhook_secret`, and `"victim-org"` with a `webhook_secret` set.
2. Create `Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")`, a `Shipit::ReviewStack` under it with `environment: "production"`, and an associated `Shipit::PullRequest` with `number: 42`, `labels: []`.
3. Build a `pull_request` JSON payload: `action: "reopened"`, `number: 42`, `repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }`, `pull_request: { ..., labels: [{ name: "malicious_env_flag" }] }`.
4. `post shipit.webhooks_path, params: payload.to_json, headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => "sha1=anything" }` (no valid signature needed since `attacker-org` has no secret).
5. Assert response is `:ok` (200/204), then assert `victim_pull_request.reload.labels == ["malicious_env_flag"]` and `review_stack.env["MALICIOUS_ENV_FLAG"] == "true"` — proving the equality `authenticating_org (attacker-org) == mutated_repo_org (victim-org)` is false yet the write succeeded, confirming the vulnerability.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
