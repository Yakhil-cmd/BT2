### Title
Webhook signature verified against `repository.owner.login`'s org secret while target stack/repository is resolved from the independent `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify the HMAC signature against based on `params.dig('repository', 'owner', 'login')`, a field taken from the unauthenticated request body. Every event handler, however, resolves the actual `Stack`/`Repository` to act on using `payload.dig('repository', 'full_name')`, a separate field in the same attacker-controlled JSON. Because the two fields are never cross-checked against each other, an attacker who legitimately possesses the `webhook_secret` for one configured organization ("Org A") can sign a payload whose `repository.owner.login` is `"orgA"` (so the signature check passes) while `repository.full_name` is `"orgB/target-repo"` (so the handler acts on Org B's stack).

### Finding Description
`Shipit.github(organization:)` is a multi-tenant lookup: each organization key in `secrets.github` has its own `webhook_secret` [1](#0-0) . The controller's before_action derives which organization's secret to check purely from the payload:

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

Once verification passes, `create` dispatches the same raw params to every registered handler for the event [3](#0-2) . `Handler#stacks` resolves the target repository from a *different* field of the same payload:

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

`Repository.from_github_repo_name` simply splits `full_name` on `/` and looks up by `owner`/`name`, with no relation to `repository.owner.login`: [5](#0-4) 

The equality the code implicitly assumes but never enforces is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization whose repository is written (repository.full_name owner)`

Before the attack: for legitimate GitHub-originated webhooks these two fields always describe the same repository, so they coincide. After the attack: an attacker who controls Org A's `webhook_secret` (because they are an authorized admin/integrator of Org A, itself onboarded to this Shipit instance) crafts a raw JSON body with `repository.owner.login = "orgA"` but `repository.full_name = "orgB/some-repo"`, computes the HMAC over that exact raw body using Org A's secret, and sends it to `/webhooks`. `verify_signature` picks Org A's `GitHubApp`, the signature matches (it was computed correctly for that body), and processing proceeds against Org B's stack — an organization the attacker never authenticated for.

### Impact Explanation
This breaks a deployment-trust binding this engine is expected to preserve in multi-org configurations: proof of a valid signature for organization A is treated as authorization to act on organization B's repositories/stacks. Handlers reachable this way include `PushHandler` (enqueues `GithubSyncJob`, which pulls new commits into another org's stack and appends them to its commit history) and `StatusHandler` (creates/updates commit `Status` records) and `CheckSuiteHandler` (enqueues `RefreshCheckRunsJob`), all keyed off the forged `full_name`. Because Shipit's deploy gating (`deployable_status`, merge/rollback eligibility) is driven by exactly these commit statuses/check-run records, an attacker can inject or corrupt the status/check-run state that another organization's stack uses to decide whether commits are deployable — i.e., cross-organization writes into deploy-gating data without ever holding that organization's own webhook secret.

### Likelihood Explanation
Exploitation requires the attacker to already hold a valid `webhook_secret` for *some* organization configured on the Shipit instance (a realistic scenario for any self-service/multi-tenant Shipit install where multiple teams/orgs configure their own GitHub Apps against the same Shipit deployment), but requires no privileged access to the target organization, its GitHub repo, or its secret. Crafting the payload only requires knowledge of the target's `owner/name` string, which is public.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler#stacks`), enforce that the organization whose secret validated the signature matches the owner encoded in `repository.full_name` (and any `organization.login` field) before dispatching to handlers; reject the request (422) on mismatch.

### Proof of Concept
1. Attacker is an admin of `orgA`, which is configured in this Shipit instance with its own `webhook_secret` (`secretA`).
2. Attacker builds a JSON body for a `push` event where `repository.owner.login = "orgA"` but `repository.full_name = "orgB/target-repo"` (an org/repo the attacker does not control).
3. Attacker computes `sha1=HMAC-SHA1(secretA, raw_body)` and sets it as `X-Hub-Signature`.
4. `POST /webhooks` with `X-Github-Event: push`. `verify_signature` resolves `Shipit.github(organization: "orgA")` from `repository.owner.login`, and the signature matches — request passes verification.
5. `PushHandler`/`Handler#stacks` resolves `Repository.from_github_repo_name("orgB/target-repo")` and enqueues `GithubSyncJob` for `orgB`'s stack, letting the attacker's forged push data affect `orgB`'s commit history/deploy-gating state despite never possessing `orgB`'s webhook secret.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
