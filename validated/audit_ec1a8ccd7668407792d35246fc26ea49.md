### Title
`StackStxOp::check()` fails to reject out-of-range `num_cycles` (only logs a warning, never returns `Err`) - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`StackStxOp::check()` validates that `num_cycles` is in `(0, POX_MAX_NUM_CYCLES]`, but on failure it only calls `warn!()` and falls through to `Ok(())` instead of returning an error. This lets a burnchain `StackStxOp` with `num_cycles == 0` or `num_cycles > POX_MAX_NUM_CYCLES` (e.g. `255`) pass validation and be forwarded as a lock-period argument into the pox-5 `stack-stx` call path.

### Finding Description
The broken equality is: **cycles for which STX is locked (as reported/consumed by pox-locking / pox-5) == `num_cycles` the sender specified in the burnchain op**.

In `StackStxOp::check`:
```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(
        "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
        self.num_cycles, POX_MAX_NUM_CYCLES
    );
}
``` [1](#0-0) 

Unlike the sibling check three lines above it (`stacked_ustx == 0` → `return Err(op_error::StackStxMustBePositive)`), this branch has no `return Err(...)`, so execution falls through to the final `Ok(())`. Every other malformed-input branch in this same file (`PreStxOp::parse_from_tx`, `StackStxOp::parse_from_tx`) correctly returns `Err(op_error::InvalidInput)` after `warn!`, making this omission an outlier/regression rather than intentional behavior.

Attacker's exact call: craft a Bitcoin burnchain transaction carrying a valid `PreStxOp` output, followed by a `StackStxOp` payload with the `num_cycles` byte (offset 16 of the OP_RETURN payload, per the wire format documented at lines 178-188) set to `0x00` or a value `> POX_MAX_NUM_CYCLES` (e.g. `0xFF`/255). `StackStxOp::check()` is invoked during burnchain op processing/validation and returns `Ok(())` despite the out-of-range value, so the op is accepted into the sortition-derived operation set and forwarded toward the pox-5 contract-call translation layer that ultimately calls `stack-stx` (or the pox-locking Rust glue in `pox-locking/src/pox_4.rs`/equivalent pox-5 handler) with the attacker-supplied `num_cycles`.

Existing guards that could stop this: the `<=`/range guard in `check()` itself is present but structurally broken (no `Err` return). Whether pox-5.clar's own Clarity-side lock-period bound check (the contract has its own `lock-period`-related assertions, mirroring the pattern seen in pox-2/3/4.clar) independently re-validates and rejects `num_cycles == 0` or `> POX_MAX_NUM_CYCLES` before actually locking STX could not be fully confirmed with the tools available in this session. If pox-5.clar performs no independent bound re-check equivalent to the Rust-side one (relying on the Rust burnchain-op layer as the sole gate, as is the typical design intent signaled by the dead code in `check()`), the malformed `num_cycles` would reach pox-locking's stacking-lock computation unfiltered.

### Impact Explanation
If unguarded downstream, a `num_cycles = 0` op could result in STX being "locked" for zero cycles (an unbacked stacking credit with no real time-locked commitment), and a `num_cycles > POX_MAX_NUM_CYCLES` value could produce a lock duration exceeding the intended bound, potentially freezing the sender's own STX for far longer than the protocol's maximum reward-cycle window (or interacting incorrectly with the `SINGLE_UNLOCK` height calculation in pox-locking, since that unlock height is derived directly from `num_cycles`). This falls into the Critical category (permanent/erroneous freezing of staked STX, or unbacked stacking credit for zero real lock time) if reached, and is repeatable by any attacker who can submit a burnchain stacking op with their own BTC inputs.

### Likelihood Explanation
Preconditions are minimal and fully within the "unprivileged attacker" capability set described: a valid `PreStxOp` followed by a `StackStxOp` with a single crafted byte for `num_cycles`. No privileged role, no signer/miner assumptions, and no reentrancy tricks are needed — it is a pure input-validation gap in `StackStxOp::check`. The remaining uncertainty for confirmed exploitability is whether pox-5.clar's `stack-stx` (or the pox-locking Rust dispatch calling into it) independently bounds-checks `lock-period`/`num_cycles` before locking; that could not be verified with the available tool budget in this session, so the concrete chainstate-level impact (test 2 in the proof idea) remains unconfirmed even though the Rust-level defect (test 1 in the proof idea) is unambiguous and directly observable in the source.

### Recommendation
Fix `StackStxOp::check` to return an error on the invalid-`num_cycles` branch, mirroring the pattern used for `stacked_ustx == 0`:
```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(...);
    return Err(op_error::StackStxInvalidCycles); // or equivalent existing variant
}
```
Additionally, add/verify a redundant Clarity-side bound assertion in pox-5.clar's `stack-stx` for defense-in-depth, so a future regression in the Rust burnchain-op validator cannot alone cause an invalid lock duration.

impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
