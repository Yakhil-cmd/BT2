### Title
Cross-repository/cross-tenant webhook forgery via organization/repository binding mismatch in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to authenticate an inbound webhook from a payload field (`repository.owner.login` / `organization.login`) that is *independent* of the field the event handlers use to decide **which repository's `Stack` gets written to** (`repository.full_name`, or, for `status` events, no repository field at all). An attacker who legitimately controls a webhook secret for *any* organization/App configured on the shared Shipit instance can forge a webhook whose signature verifies against their own org's secret while its "target" fields point at a completely different organization's repository, causing Shipit to write commit/status/check-run data into a stack it does not own.

### Finding Description
`Shipit` supports multiple GitHub Apps/organizations on one instance (`Shipit.github(organization:)`, confirmed by `lib/shipit/github_app.rb` and the multi-org test fixture `secrets_double_github_app.yml`). Each org can have its own `webhook_secret`.

The webhook signature check picks which org's secret to verify against purely from attacker-controlled JSON fields: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This is the *authentication* binding: "which org's secret proves this request is genuine."

The *write* binding used by event handlers is a completely different field: [2](#0-1) 

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` and `CheckSuiteHandler#process` use this `stacks` scope, and `full_name` need not match `repository.owner.login`/`organization.login` at all — nothing in the code enforces that the two fields describe the same repository/org: [3](#0-2) [4](#0-3) 

Worse, `StatusHandler` enforces **no repository binding whatsoever** — it matches purely by commit SHA across the entire instance: [5](#0-4) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

So the equality that should hold — *"organization whose secret authenticated this request" == "organization/repository whose data gets mutated"* — is never enforced. The signature only proves the payload was signed by some registered org's secret; it says nothing about which repository the payload's `repository.full_name`/`Commit` lookups reference.

### Impact Explanation
An entity that legitimately administers *any* organization/App entry configured on a shared multi-tenant Shipit instance (a normal, unprivileged relationship for that feature — they only know their own org's webhook secret, not any victim org's credentials) can:
- Forge `push`/`check_suite` events whose `repository.full_name` names a **different** organization's repository, triggering `stack.sync_github` / `schedule_refresh_check_runs!` on a stack they do not control — a cross-repository, cross-tenant write.
- Forge `status` events with an attacker-chosen `state`/`context`/`target_url` for **any** commit SHA in **any** stack instance-wide (SHAs are public git hashes), since `StatusHandler` performs no repository check at all. Forged "success" statuses can satisfy `any_status_checks_missing?`/`any_status_checks_failed?` checks used by `MergeRequest#reject_unless_mergeable!` and deploy safety gating, enabling an unauthorized merge or deploy of unreviewed/untested code — matching the Critical criterion "unauthorized deploy, rollback or merge" and "cross-repository writes."

### Likelihood Explanation
Requires only that the attacker controls one legitimately-configured, low-privilege org/App entry on a shared Shipit deployment (a documented, supported configuration) and can guess/observe a target commit SHA (trivial for public repos). No Shipit session, `ApiClient` token, or victim-org secret is needed — only knowledge of the attacker's own org's webhook secret, which is by design something they possess.

### Recommendation
Bind the org/repository used to select the verifying secret to the same identifier used by handlers to select the target `Stack`/`Commit`. Concretely:
- After signature verification, re-derive the repository from `repository.full_name` and require its owner to equal `repository_owner` before dispatching to handlers.
- In `StatusHandler` (and any other handler lacking repository scoping), restrict `Commit.where(sha:)` to commits belonging to stacks whose repository matches the authenticated organization, instead of a global SHA lookup.

### Proof of Concept
1. Shipit configured with two orgs, `OrgA` (attacker-administered, webhook secret `secretA` known to attacker) and `OrgB` (victim, stack `OrgB/victim-repo`).
2. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, body:
```json
{
  "organization": { "login": "OrgA" },
  "sha": "<victim commit sha, e.g. head of an open PR in OrgB/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `X-Hub-Signature: sha1=<HMAC(secretA, raw_body)>` computed with the attacker's own known `secretA`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')` and verifies successfully (attacker knows `secretA`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the OrgB commit with no organization check — and marks it `success`, even though the request was never authorized by OrgB.
6. This forged status can clear CI/merge-queue gating for `OrgB`'s pull request/deploy, resulting in an unauthorized merge/deploy of code the attacker does not control.

      ].join(' '))
    end
