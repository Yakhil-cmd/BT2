## Title
`Shipit::Webhooks::Handlers::StatusHandler` writes commit statuses without scoping the lookup to the webhook-authenticated repository — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only authenticates that the request signature matches the `webhook_secret` configured for the organization named in `params.dig('repository','owner','login')`. `StatusHandler#process` then looks up commits by `sha` across the *entire* `Commit` table with no relation to that organization, so a payload authenticated for OrgA can create a `Status` on a commit belonging to OrgB's stack if the attacker knows/guesses that commit's sha.

### Finding Description
The broken binding: `organization whose webhook_secret verified the payload (repository_owner from payload.repository.owner.login)` must equal `organization owning the commit/stack the handler mutates (commit.stack.repository.owner)`. In this code, these are never compared.

- `WebhooksController#verify_signature` selects `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes from the top-level `repository.owner.login` (or `organization.login`) field of the JSON body, and only checks the HMAC signature against that org's secret: [1](#0-0) , [2](#0-1) .
- `Shipit::Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler`: [3](#0-2) .
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global lookup with **no** join/filter on repository or stack: [4](#0-3) .
- Notably, the base `Handler` class already provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks` using `payload.dig('repository','full_name')`: [5](#0-4) . `StatusHandler` does not use this helper at all, unlike other handlers (e.g. `push_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) which reference `stacks`.

Exploit flow: attacker registers/owns a GitHub App or webhook secret for `orga` (a legitimate, attacker-controlled org configured in Shipit's multi-org `github_app` config). Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body whose `repository.owner.login == "orga"` (so `verify_signature` picks and validates against `orga`'s secret, succeeding), but whose `sha` field is a real/guessed sha belonging to a commit tracked under a completely different org's (`shopify`/OrgB) stack. `StatusHandler.process` finds that commit via the global `Commit.where(sha: ...)` and calls `commit.create_status_from_github!(params)`, writing a `Status` row for OrgB's commit — mutating OrgB's build/CI state, which can affect `commit.state`, CI gating, and downstream `deployable_status`/merge-request scheduling (`schedule_continuous_delivery`, `enable_ci_on_stack`) as seen in `Status`: [6](#0-5) .

No existing guard prevents this: `verify_signature` only checks the signature against the org named in the payload, it does not compare that org to the org that owns the target commit's stack; `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, etc., not ownership: [7](#0-6) ; and `drop_unhandled_event`/`check_if_ping` are unrelated to this check.

### Impact Explanation
An attacker who legitimately controls one tenant/org in a multi-org Shipit deployment can forge a `status` webhook that writes a `Shipit::Status` record against a commit belonging to a foreign tenant's stack, provided they know or can guess that commit's sha. This is a cross-tenant write ("a payload for one repository mutating another's ... commit"), matching the Critical impact category. Repeated for any sha, this could pollute CI status of arbitrary commits in any other org's stack, potentially unblocking/blocking deploys or corrupting audit history, since `Status` creation feeds into deploy gating logic (`enable_ci_on_stack`, `schedule_continuous_delivery`).

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub Apps/orgs (the documented multi-org `github` config, e.g. `docs/setup.md` "Using Multiple Github Applications"), (2) the attacker legitimately controlling at least one of those orgs' webhook secret (which is plausible if Shipit is a shared/multi-tenant instance where different customer orgs each install their own GitHub App), and (3) knowledge of a target sha in another org's repository (shas are often discoverable — e.g., via public repos, PRs, CI logs, or brute force since they're not secret). Given these preconditions this is straightforward and repeatable — a single crafted POST per target sha.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository/stacks derived from the authenticated payload, mirroring the base `Handler#stacks` helper, e.g. replace `Commit.where(sha: params.sha)` with a query joined against `stacks` (`Commit.where(sha: params.sha, stack_id: stacks.pluck(:id))` or equivalent), so a status can only be applied to commits belonging to the repository that authenticated the webhook.

### Proof of Concept
minitest plan (in `test/controllers/webhooks_controller_test.rb` style, illustrative — actual file is out of scope per rules but described for verification):
1. Set up two orgs' configs in test (`shopify` and `orga`), each with a `webhook_secret`; stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` or specifically stub `Shipit.github(organization: 'orga').expects(:verify_webhook_signature).returns(true)`.
2. Take an existing commit fixture belonging to a `shopify`-owned stack, e.g. `commit = shipit_commits(:first)` (owned by `shopify`).
3. POST `/webhooks` with `X-Github-Event: status`, body `{ 'sha' => commit.sha, 'state' => 'success', 'repository' => { 'owner' => { 'login' => 'orga' }, 'full_name' => 'orga/some-unrelated-repo' } }`.
4. Assert the equality that should hold: `repository_owner` from payload (`'orga'`) must equal the owner of `commit.stack.repository` (`'shopify'`) before a write is allowed — they do not match.
5. Assert `commit.statuses.count` changes (currently it *does* increase by 1, demonstrating the bug) — `assert_difference('commit.statuses.count', 0) { post :create, body:, as: :json }` would **fail** on current code, proving the foreign-tenant write occurs. [4](#0-3) [1](#0-0)
