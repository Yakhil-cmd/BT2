### Title
Cross-org webhook signature verification lets an attacker toggle `archive!`/`unarchive!` on a victim repository's review stack via forged `pull_request.labels` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to validate the HMAC against using `repository_owner`, a value read straight out of the *same unsigned JSON body* (`params.dig('repository','owner','login')`). `UnlabeledHandler` (and the sibling `labeled_handler.rb`/`opened_handler.rb`/`reopened_handler.rb`) instead resolves the target `Repository` from a different field of that same body, `params.repository.full_name`, with no check that the two agree. An attacker who controls an org with no (or a known) `webhook_secret` can set `repository.owner.login` to their own org (satisfying/bypassing signature verification) while setting `repository.full_name` and `pull_request.labels` to whatever they want for a real victim repository, fully controlling whether `archive!` or `unarchive!` fires on that victim's stack.

### Finding Description
The intended binding is: `repository_owner_used_for_signature_check == owner(params.repository.full_name)` — i.e., the org whose secret validated the webhook must be the same org that owns the repository the handler acts on.

- `verify_signature` derives the org purely from payload content: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the configured org has no `webhook_secret`: [3](#0-2) 

- `UnlabeledHandler` then resolves the acted-upon `Repository` from a *different* field of the same body (`params.repository.full_name`), independent from `repository.owner.login`: [4](#0-3) 

- The archive/unarchive decision is driven entirely by the attacker-supplied `pull_request.labels` array compared against the victim repository's real `provisioning_label_name`: [5](#0-4) [6](#0-5) 

Exploit flow: attacker owns/controls org `attacker-org` for which Shipit's GitHub App config has no `webhook_secret` set (or a secret the attacker knows). Attacker crafts a JSON body with `X-Github-Event: pull_request`, HMAC signed with `attacker-org`'s (absent/known) secret, and:
```json
{
  "action": "unlabeled",
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "pull_request": { "state": "open", "labels": [] , ... },
  "sender": { "login": "attacker-org" }
}
```
`verify_signature` calls `Shipit.github(organization: "attacker-org")` and passes (secret blank → always verified, or attacker knows their own secret). The handler then loads the real `victim-org/victim-repo` repository via `from_github_repo_name(params.repository.full_name)` and, depending on the attacker-chosen `labels` array vs. the repository's configured `provisioning_label_name`, drives `archive?`/`unarchive?` to call `stack.archive!` or `stack.unarchive!` on the victim's real review-stack.

None of the existing guards catch this: `verify_signature`/`verify_webhook_signature` only validate that the sender knows a valid secret for *the org named in the unsigned payload itself*, not that this org matches `repository.full_name`'s owner; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema only enforces types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `require_permission!`/session/API-token check on this unauthenticated webhook endpoint by design.

### Impact Explanation
An unprivileged attacker can force `Shipit::Stack#archive!` or `#unarchive!` to run against any real, targeted repository's review-stack that has review stacks enabled, without ever authenticating as that repository's org. This is a cross-tenant confused-deputy: a payload nominally from one org (attacker's) mutates another org's stack state. This matches the Critical category "a payload for one repository mutating another's stack" and can be used to repeatedly tear down (denial of a legitimate deploy environment) or force provisioning of arbitrary victim repositories' PR review stacks, as long as the victim repo has `review_stacks_enabled` and a `provisioning_behavior` requiring a label.

### Likelihood Explanation
Preconditions: (1) the Shipit instance is configured for multiple GitHub orgs/apps and at least one org entry attacker controls has no `webhook_secret` configured (or a secret known to attacker) — the scenario explicitly grants this; (2) the victim repository has review stacks enabled with `allow_with_label`/`prevent_with_label` provisioning behavior. Given those, the attack is a single unauthenticated `POST /webhooks` request with no GitHub secrets required, fully repeatable against any repository whose `full_name` the attacker knows.

### Recommendation
In `WebhooksController#verify_signature`, after signature verification, additionally verify that the org used to select the webhook secret matches the owner embedded in `params.repository.full_name` (and reject if they diverge), or better, derive the org solely from `repository.full_name`'s owner segment rather than the separate `repository.owner.login`/`organization.login` fields. Reject payloads where `repository.owner.login` doesn't match the owner portion of `repository.full_name`. Also disallow/alert on orgs configured without a `webhook_secret` in multi-tenant environments.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (or a handler-level test bypassing controller, per repo's existing test patterns) two minitest cases:

1. Configure two orgs in test config: `attacker-org` with `webhook_secret: nil` (or a known test secret) and `victim-org` with review stacks enabled on `victim-org/victim-repo`, `provisioning_behavior: :allow_with_label`, `provisioning_label_name: "deploy"`. Create an existing active stack for `victim-org/victim-repo`.
2. Case A: POST an `unlabeled` event payload with `X-Github-Event: pull_request`, HMAC signed for `attacker-org`, body containing `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, `pull_request.labels = []` (no provisioning label) → assert response is `200`/processed and `victim_stack.reload.archived?` is `true`.
3. Case B: identical forged envelope but `pull_request.labels = [{"name" => "deploy"}]` → assert `victim_stack.reload.archived?` is `false` (unarchived), demonstrating the attacker fully controls the outcome via the unsigned label array while keeping the cross-org signature bypass constant.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

          def respond_to_label_change?
            params.action == "unlabeled" &&
              pull_request_state == "open" &&
              repository.review_stacks_enabled &&
              (archive? || unarchive?)
          end

          def archive?
            (repository.provisioning_behavior_allow_with_label? && !pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && pull_request_has_provisioning_label?)
          end

          def unarchive?
            (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
          end

          def pull_request_has_provisioning_label?
            pull_request_label_names.include?(repository.provisioning_label_name)
          end

          def pull_request_label_names
            Array.new(pull_request.labels).map(&:name)
          end
