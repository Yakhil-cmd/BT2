### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The GMX report's bug class is an "incorrect interface" that lets an action operate on a parameter the calling code never actually validated against the real, authoritative constraint (the true `updateOrder` signature). The engine analog is `StatusHandler#process`, which trusts a webhook's `sha` field to select **any** `Commit` row in the entire database, without checking that the commit belongs to the repository/organization whose signature was actually verified.

### Finding Description
Webhook signature verification in `WebhooksController#verify_signature` selects the GitHub App/secret to check against based on the payload's `repository.owner.login` (or `organization.login`), and only proves that the HTTP request was genuinely sent by GitHub for **that** organization's installation: [1](#0-0) [2](#0-1) 

Every other handler that mutates repository-scoped state derives its target set through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from the same verified payload's `repository.full_name`, e.g. `PushHandler` and `CheckSuiteHandler`: [3](#0-2) [4](#0-3) 

`StatusHandler`, however, never uses `stacks`/`repository_name` at all — it looks up commits globally by `sha` across the whole instance: [5](#0-4) 

`Commit#sha` is only unique per `(sha, stack_id)`, not globally, confirming multiple stacks/repositories can legitimately hold rows with the same `sha` (e.g., forks, shared upstream commits, or vendored/cherry-picked commits): [6](#0-5) 

**The broken binding, as an equality:**
`organization/repository authenticated by the webhook signature` should equal `repository whose Commit record is written`, but `StatusHandler` writes to every `Commit` matching `sha` regardless of which repository it belongs to.

- **Before the attack**: A victim stack (belonging to Org B) has a `Commit` row with sha `S` (e.g., shared with an upstream/forked repo, or reused because Shipit places no cross-repo uniqueness constraint on `sha`). The attacker only has legitimate GitHub access to their own Org A repo, on which Shipit's GitHub App is also installed (a normal, unprivileged multi-tenant configuration described in `docs/setup.md`'s "Using Multiple GitHub Applications" section).
- **The action**: The attacker creates/updates a real commit status via the GitHub API on a commit in their own Org A repository whose `sha` matches (or collides with, e.g. through a forked/shared history) the victim's commit `S`. GitHub sends a genuine `status` webhook, HMAC-signed with Org A's `webhook_secret`. `WebhooksController#verify_signature` correctly validates this signature for Org A.
- **After the attack**: `StatusHandler#process` executes `Commit.where(sha: params.sha)`, which matches the victim's `Commit` row in Org B's stack too, and calls `commit.create_status_from_github!(params)` on it — writing attacker-controlled `state`, `description`, `target_url`, and `context` onto a commit that has nothing to do with the organization that was actually authenticated.

### Impact Explanation
Commit statuses drive Shipit's deployability logic (`required_statuses`, CI gating, merge-queue eligibility). By forging a `success` status on a shared/colliding-sha commit that belongs to a stack the attacker never authenticated for, the attacker can flip a victim stack's commit into a deployable state it should not have, enabling an unauthorized deploy path once combined with existing deploy triggers (manual or continuous-deployment). This lands on "unauthorized deploy" territory under the Critical impact bucket, and at minimum is an unauthenticated cross-tenant write of task/commit state (High: escalation into deploy-state authorization). The realistic likelihood of an exact-sha collision across unrelated repos is limited in the general case, but is concretely reachable whenever repositories share history (forks, mirrors, migrated repos, monorepo splits) that are onboarded as separate Shipit stacks/organizations — a supported, documented multi-tenant configuration in this engine.

### Likelihood Explanation
Requires only: (1) the operator's multi-org GitHub App configuration (documented, normal setup), and (2) an attacker with ordinary write/status access to any one onboarded repository whose commit history overlaps with a victim repository (fork, shared upstream, migrated history). No `ApiClient` token, GitHub App private key, or webhook secret theft is needed — the attacker uses their own legitimate GitHub credentials to generate a validly-signed webhook that the engine itself mis-scopes.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve the target `stacks` from the verified payload's `repository.full_name` via `Handler#stacks`, and constrain the `Commit` lookup to `stacks.flat_map(&:commits)` (or an equivalent `Commit.joins(:stack).where(stacks: { id: stacks })`) instead of an unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Configure Shipit with two GitHub Apps for Org A (attacker-controlled) and Org B (victim), per `docs/setup.md`'s multi-org example.
2. Fork/mirror Org B's repository into Org A so that a commit `S` exists identically in both repositories' git history (or otherwise contrive `sha` reuse).
3. Onboard both `orgA/repo` and `orgB/repo` as separate Shipit stacks; ensure `orgB/repo` has a `Commit` row for `S`.
4. As an ordinary contributor to `orgA/repo`, use the GitHub API/UI to post a commit status (`state: success`) on commit `S` in `orgA/repo`.
5. GitHub delivers a `status` webhook to Shipit, signed with Org A's `webhook_secret`; `WebhooksController#verify_signature` accepts it.
6. Observe `StatusHandler#process` (`Commit.where(sha: params.sha)`) updates the `Commit` row belonging to `orgB/repo`'s stack, granting a forged `success` status the attacker was never authorized to set on Org B's stack.
