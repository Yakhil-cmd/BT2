### Title
`StatusHandler#process` writes GitHub status webhooks to commits by SHA with no repository scoping, letting an attacker mutate a victim stack's commit status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Commit#create_status_from_github!` is safe when called from `Commit#refresh_statuses!`, because that path fetches statuses from `stack.github_api` scoped to `github_repo_name` and applies them only to `self` (the commit already known to belong to that stack). `StatusHandler#process`, however, looks up commits globally via `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, with no check that the matched commit's `stack`/`repository` corresponds to the webhook's originating repository.

### Finding Description
The broken binding: the question posits `create_status_from_github!` is only invoked with data scoped to `commit.stack`'s repository == true for `refresh_statuses!` (confirmed: `stack.github_api.statuses(github_repo_name, sha, ...)` [1](#0-0) ) and == false for `StatusHandler#process` (confirmed).

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This queries **all** `Commit` rows across **all** stacks/repositories matching the SHA, with no filter on `repository_name`/`stacks`. Contrast with the base `Handler` class, which already provides a `stacks` helper that scopes to the correct repository via `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and which `CheckSuiteHandler` actually uses (the only handler that calls `stacks.` per the grep). `StatusHandler` does not use `stacks` at all.

Upstream guards do not prevent this: `WebhooksController#verify_signature` only checks that the request signature matches the org derived from the payload's own `repository.owner.login` [4](#0-3) . It authenticates *that the sender controls the repo named in the payload*, not that the SHA in the payload actually belongs to that repo. Because Git commit SHAs are content-addressed, an attacker who forks (or otherwise obtains) a repository containing the same commit history as a Shipit-tracked victim repository can send a `status` webhook event from their own repo/organization (which they can legitimately register and sign, since it is their own repository), while setting `sha` to a value that also exists in the victim's tracked commit history. The signature check passes because it validates against the attacker's own org, but `Commit.where(sha:)` matches the victim's `Commit` row belonging to a different `Stack`.

Exploit flow:
1. Attacker forks or otherwise controls a public GitHub repository containing a commit SHA that is also tracked by a victim Shipit stack (e.g. by forking the victim repo before Shipit onboarding, or any repo sharing a common ancestor commit).
2. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for their own org/repo, `repository.full_name` = their own repo, and `sha` equal to the shared/colliding commit SHA, `state: success` (or any state), arbitrary `context`, `description`, `target_url`.
3. `verify_signature` passes (their own webhook secret for their own org).
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and finds the victim's `Commit` (unscoped by repo), then calls `commit.create_status_from_github!(params)`, writing a forged `Status` onto the victim's commit/stack.
5. Depending on the victim stack's CI/CD configuration (`ignore_ci`, `deployable_status` webhooks, continuous deployment), this forged status can mark a commit `success`, enabling it to become deployable and potentially trigger continuous deployment (`ProcessMergeRequestsJob`, `schedule_continuous_delivery`), as seen in `create_status_from_github!`'s `add_status` side effects [5](#0-4) .

### Impact Explanation
A payload originating from and authenticated for one repository (the attacker's) can write a `Status` record for a **different** stack/repository/tenant, satisfying the "payload for one repository mutating another's stack/commit" Critical category. In the worst case (continuous deployment enabled, `state: success` on a context that was previously blocking), this can push a victim's commit into a deployable state and trigger an unauthorized deploy, matching the Critical impact bar for "unauthorized deploy" as well. The blast radius spans every stack in the Shipit instance whose commit history shares any SHA with a repository the attacker controls (forks are the trivial case, since fork commit SHAs are identical to the upstream repo's SHAs until they diverge).

### Likelihood Explanation
Preconditions: attacker needs (a) a GitHub repository they administer (any free GitHub account can create/fork one) whose commit history includes a SHA also present in a Shipit-tracked repository, and (b) the ability to configure/trigger a webhook on that repo pointing at the Shipit host (trivial — either register a real GitHub webhook, or, since the signature is verified only against the attacker's own secret, any request signed correctly for the attacker's own registered app/org). Forking a public open-source repo tracked by Shipit is the most direct route: the fork shares the exact same commit SHAs as the upstream at fork time. No Shipit session, API token, or `webhook_secret` for the *victim* org is required — only the attacker's own credentials for their own repo. This is a low-cost, repeatable, and precisely targetable (by choosing which upstream commit to fork/replicate) attack.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring the `Handler#stacks` helper used by `CheckSuiteHandler`. For example, restrict the commit lookup to commits belonging to `stacks` (i.e., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of a global `Commit.where(sha:)`, so `create_status_from_github!` is only ever invoked on commits whose stack's repository matches `repository_name` from the payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossRepoTest < ActiveSupport::TestCase
        test "does not write status onto commit belonging to a different repository" do
          victim_stack = shipit_stacks(:shipit) # tracks repo "shopify/shipit-engine"
          victim_commit = shipit_commits(:first)
          victim_commit.update!(sha: "deadbeef00000000000000000000000000000000")

          attacker_payload = {
            "sha" => victim_commit.sha,
            "state" => "success",
            "context" => "attacker/forged",
            "repository" => { "full_name" => "attacker/unrelated-repo" }
          }

          assert_no_difference -> { victim_commit.statuses.count } do
            StatusHandler.call(attacker_payload)
          end
        end
      end
    end
  end
end
```
Contrast with the trusted path:
```ruby
# app/models/shipit/commit.rb:156-163 (refresh_statuses!) — trusted, repo-scoped
test "#refresh_statuses! only pulls statuses for the commit's own stack/repo" do
  stack = shipit_stacks(:shipit)
  commit = shipit_commits(:first)
  Shipit.github.api.expects(:statuses)
    .with(stack.github_repo_name, commit.sha, per_page: 100)
    .returns([])
  commit.refresh_statuses!
end
```
Before the fix, the first test fails (`assert_no_difference` is violated because `StatusHandler#process` writes the status regardless of repository); after adding repository scoping to `StatusHandler#process`, the assertion passes.
