## Analog Found

### Title
Non-deterministic emergency OP-list vote counting causes permanent node disagreement on consensus / stability ([File: main_chain.js])

### Summary
ZenCash's incident was a classic PoW reorg/double-spend enabled by an attacker temporarily controlling enough hash power to rewrite recent history and get two conflicting chains accepted by different parts of the network. Ocore has no PoW, but it has an analogous "who decides the canonical chain" parameter: the **order-provider (OP) list**, which plays the role that miners/hash-power plays in Bitcoin-like chains — it determines `witnessed_level`, main-chain determination, and stability (`storage.getOpList`, `main_chain.js` `findMinMcWitnessedLevel`/`determineIfStableInLaterUnits`). Any unprivileged address can trigger an **emergency** recount of this OP list, and the recount logic reads non-deterministic, node-local in-memory state (unstable, not-yet-final units), so different full nodes can permanently commit *different* OP lists for the same MCI — a genuine, irreversible fork in what each node considers canonical, mirroring the "network can no longer agree on validity" outcome from the ZenCash-style attack.

### Finding Description
Any address can post a `system_vote` message (`app: "system_vote", payload:{subject:"op_list", value:[...]}`) validated in [1](#0-0)  and a `system_vote_count` message validated in [2](#0-1) . The latter's validation only checks that `payload` is one of the known subjects — it performs **no check on global network state or on whether an emergency recount is actually warranted**.

When the `system_vote_count` unit for `op_list` is written and its sequence is `good`, `writer.js` immediately triggers an emergency OP-list recount for the *current* MCI: [3](#0-2) 

`applyEmergencyOpListChange` only gates on wall-clock time since the last stable unit (`EMERGENCY_OP_LIST_CHANGE_TIMEOUT`), not on any globally-agreed state: [4](#0-3) 

It then calls `countVotes(..., is_emergency=1, ...)`, which builds the vote tally not just from stable `system_votes` rows but also from **unstable votes still in memory** via `getUnstableVotes`: [5](#0-4) 

`getUnstableVotes` iterates `storage.assocUnstableMessages`/`storage.assocUnstableUnits`, an **in-process, per-node cache that is populated as units are received and validated** (see `writer.js` populating it on every write of a unit carrying a `system_vote` message): [6](#0-5) 

Because DAG unit propagation across peers is asynchronous (no global synchronization point), the set of "currently known, currently-`good`-sequence, currently-unstable `system_vote` units" seen by node A at the exact moment it processes the `system_vote_count` unit can differ from what node B sees at the moment it processes the very same unit. `countVotes` for `op_list` requires and consumes exactly `constants.COUNT_WITNESSES` (12) top-voted addresses: [7](#0-6) 

and immediately, unconditionally persists the result with `REPLACE INTO system_vars` (no cross-node agreement or supermajority requirement beyond the votes each node itself happened to observe): [8](#0-7) 

Once persisted, `storage.getOpList(mci)` is used everywhere stability and main-chain selection are computed — `readWitnesses`, `determineBestParent`, witnessed-level calculations, `findLastStableMcBall`, etc. — so a node that computed a different OP list at this MCI will subsequently diverge in `is_on_main_chain`, `witnessed_level`, and `is_stable`/`sequence` for essentially all later units: [9](#0-8) [10](#0-9) 

There is no later reconciliation mechanism to detect or correct this divergence — `system_vars` for `op_list` is keyed by `(subject, vote_count_mci DESC)` and just accumulates whatever each node individually decided, and `hasUnstableOpVoteCount`/`bOpListCanChange` logic in `determineIfStableInLaterUnitsAndUpdateStableMcFlag` explicitly assumes the OP list "can change" and re-derives stability per node using its own (possibly already-diverged) `getOpList`: [11](#0-10) [12](#0-11) 

### Impact Explanation
This produces the DAG-consensus equivalent of a chain-split/double-spend event: nodes that computed different OP lists at the same MCI will build different main chains and reach different `is_stable`/`sequence='good'` conclusions for the same units going forward. A payment that is "stable and good" (final) on one partition of the network may never become stable, or resolve to `final-bad`, on the other — enabling a party to have a payment accepted as final by part of the network (e.g., an exchange or merchant relying on one node) while other nodes disagree, and the network as a whole loses a single canonical notion of validity/stability until/unless one branch is manually abandoned. This matches the accepted impact class "node disagreement on validity or stability, or a network unable to confirm new units," which is the closest ocore analog to the ZenCash reorg/double-spend impact.

### Likelihood Explanation
The attack is triggerable by any unprivileged address:
1. Post enough balance-weighted `system_vote` messages (`op_list` subject) for the attacker-controlled set of 12 OP addresses — reachable by anyone holding the voting share required by `SYSTEM_VOTE_MIN_SHARE`/timeframe logic in `countVotes` ( [13](#0-12) ), and
2. Wait `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` (3 days) after the network is "stuck" (last stable unit stale), then post a `system_vote_count` unit for `op_list`.

Both messages are ordinary, unprivileged unit content validated purely per-unit in `validation.js`; nothing about triggering the emergency path requires special privilege, only patience and the ability to get votes into the (non-finalized) DAG in a way that different peers observe at different times — an inherent property of gossip-based propagation, so exploitation does not need to defeat any cryptography, just exploit natural network timing variance (arguably easier than assembling 51% hash power in PoW).

### Recommendation
- Base emergency OP-list vote counting only on **stable** `system_votes` (already-finalized), never on `assocUnstableMessages`/`assocUnstableUnits`, to remove node-local non-determinism from a value that gets permanently written to `system_vars`.
- If unstable votes must be counted for genuine liveness reasons, require the vote-casting units themselves to be included/confirmed by all nodes performing the recount (e.g., require them to already be present in the last stable ball's cone) before counting, so `getUnstableVotes` cannot diverge between nodes.
- Add a supermajority/consistency check after an emergency `op_list` change — e.g., require the emergency-derived list to be corroborated by additional stable evidence before nodes actually swap witnesses (`network.js` `onSystemVarUpdated`) — to bound the blast radius of a mistaken/malicious emergency recount.

### Proof of Concept
1. Attacker accumulates the balance share needed to be the top-12 `op_list` voter and posts `system_vote` units for its own 12 addresses (`validation.js:1861-1883`), keeping the votes just barely on the main branch (`sequence='good'`) but deliberately unstable.
2. Attacker (or any actor) waits for `EMERGENCY_OP_LIST_CHANGE_TIMEOUT` after the last stabilized unit, then posts a `system_vote_count` unit for `op_list` and broadcasts it to the network with deliberately staggered timing/relay paths so different peers receive/validate the preceding `system_vote` units in different order/at different completeness before processing the `system_vote_count` unit.
3. Each node independently calls `applyEmergencyOpListChange` → `countVotes(..., is_emergency=1, ...)` → `getUnstableVotes(objUnit.timestamp)` (`main_chain.js:1936-1946`, `1915-1933`), using whatever `system_vote` units happen to be in its own `storage.assocUnstableMessages` at that instant.
4. Nodes persist differing 12-address `op_list` values to `system_vars` (`main_chain.js:1910`) for the same `vote_count_mci`, causing them to diverge in `storage.getOpList`, `determineBestParent`, `witnessed_level`, and ultimately in which units are `is_stable`/`sequence='good'` — a persistent fork in what each side of the network considers the final, confirmed transaction history.

function getUnstableVotes(emergency_count_command_timestamp) {
	let votes = [];
	for (let unit in storage.assocUnstableMessages) {
		for (let m of storage.assocUnstableMessages[unit]) {
			if (m.app === 'system_vote' && m.payload.subject === 'op_list') {
				const { timestamp, author_addresses, sequence, level } = storage.assocUnstableUnits[unit];
				if (sequence !== 'good')
					continue;
				if (emergency_count_command_timestamp - timestamp < constants.EMERGENCY_COUNT_MIN_VOTE_AGE) {
					console.log('unstable vote from', author_addresses, 'is too young');
					continue;
				}
				const arrOPs = m.payload.value;
				votes.push({ timestamp, level, author_addresses, arrOPs });
			}
		}
	}
	return votes;
}
