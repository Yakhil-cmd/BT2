### Title
Relayer fee is transferred unconditionally before the underlying Eth-emulated transaction executes, allowing fee payment even when the emulated action fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In `inner_rlp_execute`, when processing an emulated `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero relayer `fee`, the wallet contract immediately fires a separate `promise_batch_action_transfer` to pay the relayer's `fee` to `predecessor_account_id` before the actual emulated action (the base-token transfer or the `ft_transfer` call) has been attempted or confirmed successful.

### Finding Description
The fee-payment promise is created eagerly and unconditionally, independent of the outcome of the main action: [1](#0-0) 

The main action (base token transfer, or NEP-141 `storage_deposit`+`ft_transfer` chain) is only scheduled afterward as a separate promise chain, ending in `rlp_execute_callback`: [2](#0-1) 

`rlp_execute_callback` does check `env::promise_result(0)` for the *action* promise and, on failure, refunds the caller's *attached deposit* (`caller_deposit`) — but it has no knowledge of, and does not reverse, the separately-dispatched fee transfer that was already sent to the relayer: [3](#0-2) 

Because the fee transfer and the action-execution promise are two independent, sibling receipts created from the same `rlp_execute` call (not chained with `.then()` on each other), the fee payment to the relayer is committed regardless of whether:
- the base-token transfer/ERC-20 `ft_transfer` succeeds,
- the NEP-141 target account registration/`storage_deposit` fails,
- or the final `action_to_promise` execution reverts.

This is structurally identical to the reported analog: a value transfer (`RelayPolymarketSDK::transferUsdc` fee transfer to `masterFeeAddress`) whose success is never verified before continuing/accounting downstream state — here, the wallet contract commits the relayer's fee payment before verifying that the corresponding user-intended action actually executed.

### Impact Explanation
A malicious or buggy `target`/token contract, or any transient failure of the emulated action (e.g., insufficient gas for `ft_transfer`, non-existent token method, or a reverting ERC-20 contract), causes the wallet owner to pay the relayer fee even though the user's intended transfer never took effect. The user's NEAR balance is unconditionally decremented via `promise_batch_action_transfer` (which calls `deduct_balance` at dispatch time regardless of the sibling action's eventual outcome — see `promise_batch_action_transfer` in `runtime/near-vm-runner/src/logic/logic.rs`), while the intended transfer of funds/tokens to the real recipient can fail. This is a direct loss of user funds with no user-facing recourse, since `has_in_flight_tx` is cleared and the nonce is already incremented, preventing retry/replay protection from catching the discrepancy.

### Likelihood Explanation
Likelihood is moderate: it requires a non-zero fee (`!fee.is_zero()`) and a distinct predecessor from the current account, both of which are typical/expected relayer configurations for this contract's intended use case (fee-compensated relaying of Eth-emulated transactions). No malicious actor collusion is required — any legitimate failure of the downstream action (target contract logic reverting, unregistered NEP-141 receiver edge cases, gas exhaustion) triggers the loss.

### Recommendation
Do not dispatch the relayer fee transfer as an independent sibling promise. Instead, chain the fee-transfer action after (or as part of) the same promise/receipt that performs the emulated action and only execute it once success is confirmed — e.g., move the fee transfer into `rlp_execute_callback` (or an intermediate callback) gated on `env::promise_result` being `Successful`, mirroring the existing failure-path refund logic for `caller_deposit`.

### Proof of Concept
1. Relayer submits an RLP-encoded Ethereum transaction representing an `ERC20Transfer` with a non-zero `fee` and `receiver_id` for a token contract `target`.
2. `inner_rlp_execute` parses this into `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, receiver_id, .. })`.
3. Since `fee` is non-zero and `predecessor_account_id != current_account_id`, the contract immediately creates `refund_promise` and calls `env::promise_batch_action_transfer(refund_promise, fee)` — dispatching the fee to the relayer [4](#0-3) .
4. Separately, the contract calls `token_id::storage_balance_of` then `nep_141_storage_balance_callback`, which may schedule `storage_deposit` + `ft_transfer` on the token contract.
5. If the token contract's `ft_transfer` reverts (e.g., insufficient balance, paused contract, malicious/incompatible token contract), `rlp_execute_callback` observes `PromiseResult::Failed` and only refunds `caller_deposit` (the attached NEAR deposit) — it has no reference to, and cannot undo, the already-executed fee transfer from step 3.
6. Net result: the relayer is paid the fee, but the user's ERC-20 token transfer never happened — a direct, unauthorized loss of user funds.

            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))

            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
