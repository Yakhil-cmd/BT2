### Title
Inconsistent DER/PEM AlgorithmIdentifier parsing between key-approval and signature-verification paths enables curve-safety bypass - ([File: signature.js])

### Summary
`signature.js` contains two independent, hand-rolled DER parsers over the same PEM public-key material: `validateAndFormatPemPubKey()` (used to *approve* a PEM key, e.g. when an AA formula or address definition registers/uses a `pem_key`, enforcing `bPostPemCurvesFix` against `objSafePemTypes`) and `verifyMessageWithPemPubKey()`/`verifyMessageWithSecp256k1PemPubKey()` (used to actually *verify* a signature at spend time). These two parsers disagree on how to locate/validate the AlgorithmIdentifier bytes inside the DER blob, which is structurally the same class of bug as CVE-2017-6891: an ASN.1/DER "find node" routine that does not fully validate length/structure before trusting derived offsets, so two different consumers of the same encoded structure can disagree about what it means.

### Finding Description
`validateAndFormatPemPubKey()` (signature.js:117-188) manually walks the DER TLV header to compute `identifiersStart`/`identifiersLength`, extracts the AlgorithmIdentifier hex at that offset, and requires it to be a key of `objSupportedPemTypes` and, when `bPostPemCurvesFix` is set, a member of `objSafePemTypes` (the curve allow-list) [1](#0-0) . For ECDSA it additionally checks that the total key length matches `hex_pub_key_length`, but for RSA there is no such length check at all [2](#0-1) .

`verifyMessageWithPemPubKey()` (signature.js:27-48), which is invoked to actually validate a signature at spend/trigger time, uses a *different*, much looser routine: it only looks at `der[1]` to guess `algIdStart` and directly compares 17 bytes at that offset against the single hard-coded `SECP256K1_ALG_ID` constant — it never checks the inner SEQUENCE tag (`der[2]`/`der[3]`/`der[4]`) nor any length/identifier field the way `validateAndFormatPemPubKey` does [3](#0-2) . If that narrow secp256k1 pattern match fails, the function falls straight through to Node's OpenSSL-backed `crypto.createVerify('SHA256').verify({key: pem_key}, signature, encoding)` on the *raw, unvalidated* PEM string [4](#0-3) .

Because the "approval" parser and the "verification" parser read the same byte blob with different, incomplete logic (neither one performs a full/authoritative ASN.1 decode with cross-checked lengths, exactly analogous to the two flawed length/offset lookups in `asn1_find_node()` from the CVE), a PEM key can be crafted where:
- `validateAndFormatPemPubKey()` classifies/approves it under one entry of `objSafePemTypes` (e.g. a "safe" curve OID) based on its own offset computation, while
- `verifyMessageWithSecp256k1PemPubKey`/OpenSSL, which does its own independent (and authoritative) structural interpretation of the DER (e.g. locating the `03 42 00 04` BIT STRING via `der.indexOf`, or OpenSSL's own ASN.1 decoder in the fallback path) — extracts different key material or a different curve/algorithm than what was "approved" for the address/AA.

This mirrors the CVE root cause exactly: a length/offset-driven ASN.1 traversal that trusts attacker-controlled bytes to compute the next read position without a second, consistent structural validation, causing different consumers of the same encoded object to disagree about its content.

### Impact Explanation
If the curve/algorithm effectively used to *verify* a signature differs from the curve that was *approved* by `validateAndFormatPemPubKey` (which enforces the `bPostPemCurvesFix` safety allow-list meant to block insecure/ambiguous curves), the safety gate is bypassed: an attacker-controlled PEM public key nominally restricted to a "safe" curve at definition time can be verified through a completely different, unvetted code path (`verifyMessageWithSecp256k1PemPubKey`'s loose `indexOf`-based BIT STRING search, or the OpenSSL fallback parsing whatever curve is actually embedded). This is a signature-verification/authentication logic flaw reachable directly from a unit poster who defines a PEM-based address/AA authentifier — a mismatch here can lead to acceptance of a signature that should have been rejected under the curve-safety policy, i.e., unauthorized authentication for spending from that address, which the enforcement (`bPostPemCurvesFix`) exists specifically to prevent.

### Likelihood Explanation
Reachable by any unprivileged unit poster or AA author who supplies a `pem_key` as part of an address/AA definition or `is_valid_signature`-style formula check; no special node/hub/peer position is required. Crafting the exact byte pattern that satisfies `validateAndFormatPemPubKey`'s offset math while causing `verifyMessageWithPemPubKey`'s independent offset math (or OpenSSL's decoder) to resolve to different key material requires DER-encoding skill but no cryptographic break — it is a structural/parsing confusion, not a cryptanalytic attack, which keeps likelihood in the medium range.

### Recommendation
Replace both hand-rolled byte-offset DER walkers with a single authoritative ASN.1/DER parse (e.g. via a vetted ASN.1 library) performed once, and derive both the "approved curve" decision and the "verification key material" from that single parse result, so the two code paths can never disagree about which AlgorithmIdentifier/key bytes are in effect. Add the same length/consistency checks (including for RSA) that exist for ECDSA in `validateAndFormatPemPubKey`, and make `verifyMessageWithPemPubKey` reject (rather than silently fall back to unrestricted OpenSSL parsing) any PEM key whose curve/algorithm cannot be unambiguously confirmed to match what was approved.

### Proof of Concept
Not fully constructible from static review alone: proving exploitability requires generating two DER byte sequences that (a) pass `validateAndFormatPemPubKey`'s offset/length checks and map to an `objSafePemTypes` entry, and (b) cause `verifyMessageWithSecp256k1PemPubKey`'s `der.indexOf([0x03,0x42,0x00])` scan (or the OpenSSL fallback in `verifyMessageWithPemPubKey`) to extract a *different* key/curve than the one approved. This would need to be validated empirically (e.g., with a Devin session that can run Node.js, `openssl asn1parse`, and the repo's own test harness) to confirm a concrete divergent-verification case exists; I could not execute code to construct and confirm such a byte sequence in this read-only analysis.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);
