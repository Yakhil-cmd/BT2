### Title
Webhook signature verified against `repository.owner.login`, but `PullRequest::OpenedHandler` resolves the target `Repository` from the unrelated `repository.full_name` field, letting an attacker who controls org A forge a signature that authorizes provisioning a review stack under org B's repository - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check using `params.dig('repository', 'owner', 'login')`, while `OpenedHandler#repository` resolves the actual `Shipit::Repository` to act on using `params.repository.full_name` - a separate, attacker-supplied field in the same JSON body. Because nothing cross-validates that `full_name`'s owner segment matches `owner.login`, an attacker who legitimately administers org A (and thus knows A's configured `webhook_secret`) can sign a payload whose `repository.full_name` names a repo belonging to org B, causing Shipit to provision a new review stack under B using attacker-controlled `head.sha`/`head.ref`/`title`.

### Finding Description
The broken binding, stated explicitly: `repository_owner_used_for_signing == repository_owning_org_acted_upon` is assumed but never enforced. In code:

- `verify_signature` computes `repository_owner` purely from the raw JSON body: [1](#0-0) , then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` at [2](#0-1) .
- `OpenedHandler#repository` independently resolves the target `Repository` from a *different* JSON field, `params.repository.full_name`, with no reference back to `owner.login`: [3](#0-2) .
- `process` then unconditionally provisions/finds a review stack scoped to whatever `repository` was resolved, once `provision?` (driven by that repository's `review_stacks_enabled` / `provisioning_behavior_allow_all?`) is true: [4](#0-3) .

Since the controller parses `request.raw_post` as arbitrary attacker-controlled JSON (this is a raw HTTP POST to `/webhooks`, not a GitHub-mediated call), the attacker fully controls both `repository.owner.login` and `repository.full_name` independently within the same body, and nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema in `OpenedHandler` (which only requires `full_name` to be a `String`, not that it agrees with `repository.owner.login`) rejects a mismatch between them: [5](#0-4) .

`Shipit.github(organization:)` requires the organization to be a pre-configured key in `secrets.github` (raising `GithubOrganizationUnknown` otherwise, caught and turned into a 422): [6](#0-5) . So the attack requires a multi-tenant Shipit deployment where the attacker legitimately controls org A's GitHub App/webhook configuration (and therefore knows A's `webhook_secret`), while org B is a *different* tenant of the same Shipit instance with `review_stacks_enabled` and `provisioning_behavior_allow_all?` true.

### Impact Explanation
A successful forged POST causes `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` to create a new `Stack` row scoped to org B's repository, using attacker-chosen `pull_request.head.sha`, `head.ref`, and `title` - i.e., a payload nominally "belonging" to org A ends up mutating org B's stack set, which is exactly the "payload for one repository mutating another's stack ... unauthorized deploy" category classified as Critical. This is repeatable for any org B configured with `review_stacks_enabled` + `allow_all` provisioning as long as the attacker controls one properly-configured org A on the same Shipit instance, and it directly leads to a subsequent build/deploy of attacker-supplied `head.sha` under B's environment via the normal review-stack pipeline.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (`secrets.github` keyed by org), (2) attacker control of one configured org A (its `webhook_secret` known to the attacker, e.g., because they are an admin of A's GitHub org/App integration), and (3) target org B's repository configured with `review_stacks_enabled: true` and `provisioning_behavior_allow_all?`. Given those preconditions - both plausible in a shared/multi-tenant Shipit installation - the attack costs a single crafted HTTP POST with a valid HMAC-SHA1 signature computed against A's secret, no GitHub interaction required, and is fully repeatable against any similarly configured victim repository.

### Recommendation
In `OpenedHandler#repository` (and the analogous PR handlers: `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `AssignedHandler`, `EditedHandler`, `LabelCapturingHandler`), verify that the resolved `Repository`'s owner matches the `repository_owner`/organization used to authenticate the webhook (i.e., that `params.repository.owner.login` equals the segment of `full_name` before `/`, and that this equals the org key used in `verify_signature`) before acting on it. Alternatively, pass the authenticated organization from the controller into the handler and have handlers reject any payload whose `repository.full_name` owner differs from it.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "opened event with mismatched owner.login and repository.full_name provisions stack under the wrong org" do
  # org A: attacker-controlled, configured in Shipit
  org_a_secret = "org-a-secret"
  Shipit.stubs(:github).with(organization: "org-a").returns(
    stub(verify_webhook_signature: true)
  )

  repo_b = shipit_repositories(:shipit) # existing fixture, review_stacks_enabled: true, allow_all
  assert repo_b.review_stacks_enabled?
  assert repo_b.provisioning_behavior_allow_all?

  payload = {
    action: "opened",
    number: 42,
    pull_request: {
      id: 1, number: 42, url: "http://example.com", title: "attacker pr",
      state: "open", additions: 1, deletions: 0,
      head: { sha: "deadbeef", ref: "attacker-branch" },
      user: { login: "attacker" }, assignees: [], labels: []
    },
    repository: {
      full_name: repo_b.github_repo_name, # names org B's repo
      owner: { login: "org-a" }           # but claims org A ownership for signing
    },
    sender: { login: "attacker" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_secret, payload)

  assert_difference -> { repo_b.stacks.count }, 1 do
    post shipit.webhooks_path,
      params: payload,
      headers: { "X-Github-Event" => "pull_request", "X-Hub-Signature" => signature },
      as: :json
  end
end
```
Both sides of the equality (`repository_owner` used to select the signing secret = "org-a"; owning org of the `Repository` actually mutated = org B, derived solely from `full_name`) diverge, and the test demonstrates a new `Stack` is created under B's repository despite the signature only proving knowledge of A's secret.

          end

          def provision?

              (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
              (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
          end
