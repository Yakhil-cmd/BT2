## Analog Found

### Title
Permanent lock of `pending_delegator_rewards` lamports when a vote account has zero total active stake - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
This is a direct structural analog of the `UpdateGlobalExchangeRate`/`totalGlobalShares == 0` bug: a per-validator reward pool (`pending_delegator_rewards`) is accounted against a denominator (`total_active_stake`) that can legitimately be zero. When that denominator is zero, the distribution function returns `0` instead of handling the edge case, so the reward pool is never drained — while the funds backing it are already irreversibly held in the vote account and withdrawal is explicitly blocked while `pending_delegator_rewards > 0`.

### Finding Description
`calculate_block_reward` computes each stake account's share of a vote account's `pending_delegator_rewards` using `total_active_stake` (the sum of currently-active delegated stake to that vote account) as the divisor: [1](#0-0) 

When `total_active_stake == 0`, the function short-circuits and returns `0` for every stake delegation — meaning **no lamports from `pending_delegator_rewards` are ever distributed** in that reward epoch, exactly mirroring the `totalGlobalShares == 0` short-circuit in the reported `DelegatedStaking` bug.

Critically, `pending_delegator_rewards` can be populated by **any unprivileged signer**, not just the vote account's authorities. The `DepositDelegatorRewards` (SIMD-0123) instruction only requires the *source* account to sign; it performs a real CPI lamport transfer into the vote account and then increments `pending_delegator_rewards` unconditionally: [2](#0-1) 

There is no check that the target vote account currently has any delegated/active stake. A vote account can trivially have `total_active_stake == 0` — e.g., immediately after creation before any stake is delegated to it, or after all delegators have fully deactivated their stake (analogous to "unstake" in the original report).

Once lamports are deposited into such a zero-stake vote account, they become permanently stuck:
- The reward-distribution path (`calculate_block_reward`) will always return `0` for this vote account as long as `total_active_stake` remains `0`, so `pending_delegator_rewards` is never reduced through the normal reward-distribution flow.
- `Withdraw` on the vote account explicitly forbids withdrawing below `pending_delegator_rewards` and forbids closing the account entirely while `pending_delegator_rewards > 0`, as verified by the program's own test suite: [3](#0-2) 

This is the same "leak value / lock funds" mechanism the C4 judge described for the original finding: a zero-denominator condition on a share/points accounting variable causes deposited value to become forever irredeemable, because the redemption path is gated by the same zero-valued denominator that prevents payout.

### Impact Explanation
Lamports deposited via `DepositDelegatorRewards` into a vote account with zero total active stake become permanently locked:
- They cannot be paid out to delegators (block reward calculation always yields `0` for this vote account while `total_active_stake == 0`).
- They cannot be withdrawn by the vote account's authorized withdrawer (the `Withdraw` instruction enforces `lamports - pending_delegator_rewards - rent_exempt` as the withdrawable ceiling, and blocks closing the account outright).

This is a concrete, permanent loss of funds triggerable by a single unprivileged transaction (`DepositDelegatorRewards`), matching the "Assets... leak value with a hypothetical attack path... under specific conditions" Medium-severity classification given to the original report.

### Likelihood Explanation
- No special privileges are required: any keypair holding lamports can call `DepositDelegatorRewards` against any vote account, including one it does not control.
- A zero-total-active-stake vote account is a normal, non-adversarial state (e.g., freshly created vote accounts, or validators whose delegators have fully unstaked) — no malicious leader or validator collusion is needed to create the precondition.
- The attacker (or an honest but careless user) simply needs to identify or create such a vote account and submit one `DepositDelegatorRewards` transaction, making this readily reachable from ordinary transaction traffic.

### Recommendation
- `DepositDelegatorRewards` should reject deposits (or route the funds elsewhere, e.g., directly to the vote account's block-revenue/commission collector) when the target vote account currently has `total_active_stake == 0`, rather than silently accepting funds that can never be distributed.
- Alternatively, `calculate_block_reward`'s zero-denominator branch should not simply return `0`; if `total_active_stake == 0` when `pending_delegator_rewards > 0` (post distribution period), the sysvar/vote-program state should provide an explicit reclamation path (e.g., allow the authorized withdrawer to reclaim `pending_delegator_rewards` once it is proven that no possible delegator can claim it), similar to the judge's recommendation to decouple share accounting from the condition that prevents redemption.

### Proof of Concept
1. Create (or locate) a `VoteStateV4` vote account that currently has zero total active delegated stake (e.g., a freshly initialized vote account before any `DelegateStake`, or one whose sole delegator has fully deactivated and cooled down).
2. As any funded, unprivileged account, submit a transaction invoking `VoteInstruction::DepositDelegatorRewards { deposit: N }` against that vote account:
   - `deposit_delegator_rewards` CPIs a System `transfer` of `N` lamports into the vote account, then sets `pending_delegator_rewards += N` — see [4](#0-3) .
3. Advance epochs and allow the (Alpenglow) reward-distribution machinery to run. For every stake delegation associated with this vote pubkey, `calculate_block_reward` observes `total_active_stake == 0` and returns `0` — see [1](#0-0) . `pending_delegator_rewards` is never decremented.
4. As the vote account's authorized withdrawer, attempt `VoteInstruction::Withdraw` for any amount that would reduce the balance below `pending_delegator_rewards + rent_exempt_reserve`, or attempt to close the account entirely: both fail with `InstructionError::InsufficientFunds`, as demonstrated by the existing unit test — see [3](#0-2) .
5. The `N` lamports deposited in step 2 remain permanently locked in the vote account: unreachable by delegators (no stake to distribute against) and unreachable by the withdrawer (blocked by the `pending_delegator_rewards` floor).

```rust
/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
```
