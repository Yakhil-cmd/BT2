### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit(s) to attach an incoming `status` webhook to using a global, repository-agnostic query, `Commit.where(sha: params.sha)`. Because the webhook signature check only proves that *some* organization's GitHub App sent the payload, but never that the payload's `sha`/`context` actually belongs to that organization's own repository, any legitimately onboarded tenant/organization can post a real (or the GitHub Status API's own arbitrary-sha-accepting) status against a `sha` string that happens to equal a victim stack's commit, mutating that victim's `Status` records and therefore `Shipit::MergeRequest::StatusChecker`.

### Finding Description
The broken binding is: *"the repository whose GitHub App/organization signed the webhook" == "the repository/stack whose `Commit` row the resulting `Status` is attached to."* These are never checked to be equal.

- `WebhooksController#verify_signature` derives `repository_owner` from the payload and validates the HMAC against that organization's configured `webhook_secret`: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [1](#0-0) [2](#0-1) . This only proves the sender legitimately controls *some* onboarded organization's GitHub App installation — it says nothing about which `sha` was reported or which stack it should apply to.
- `StatusHandler#process` then does a completely global lookup with no repository/stack scoping at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
- The `Commit` table is indexed on `(stack_id, sha)`, not uniquely on `sha` alone (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning two different stacks/tenants can legitimately have `Commit` rows sharing an identical `sha` value — the schema does not prevent this cross-tenant collision.
- `create_status_from_github!` simply records the reported state/context against whichever `Commit` row(s) matched, with no cross-check against the commit's owning repository/organization [4](#0-3) .
- The GitHub commit-status API historically accepts and forwards statuses for arbitrary `sha` strings on the reporting repository without validating that the sha is actually reachable in that repository's object graph, so a legitimately onboarded org member (someone with push access to *any* repo covered by that org's GitHub App installation — not necessarily the victim stack's repo) can trigger a real, correctly-signed `status` webhook naming any `sha` and `context` string they choose.
- `Shipit::MergeRequest::StatusChecker` (`Status::Group` subclass) then evaluates `#all_status_checks_passed?` / `#any_status_checks_failed?` purely off the `Status` rows attached to the victim `Commit`, with no knowledge of which organization actually authored them, so the forged status is indistinguishable from a real one and `ProcessMergeRequestsJob` proceeds to call `merge!`.

Existing guards do not close this gap: `verify_signature` authenticates *the sender's own organization*, not the *target* of the payload; `drop_unhandled_event` only filters unregistered event types; there is no `ExplicitParameters` validation binding `params.sha`/`params.context` to `repository_owner`; and no model validation ties `Commit#sha` uniqueness across stacks.

### Impact Explanation
A caller who legitimately controls even one onboarded organization/repository on a shared Shipit instance can write `Status` rows into an entirely different tenant's `Commit`/`Stack`, satisfying `merge_request.required_statuses` and causing `ProcessMergeRequestsJob` to merge a pull request in the victim repository without that repository's real CI ever reporting success. This is a cross-tenant "payload for one repository mutating another's stack/commit" — squarely in the Critical impact category (unauthorized merge). It is repeatable against any stack/tenant sharing the Shipit instance, for any `sha` the attacker can predict (which is always public/visible on the target PR).

### Likelihood Explanation
Requires: (1) a Shipit deployment hosting multiple tenants/organizations, or an organization structure where a non-maintainer can control a repository whose GitHub App-signed status webhooks reach the shared Shipit instance; (2) knowledge of the victim `MergeRequest`'s head `sha` (trivially visible, since the attacker is the PR author); (3) the victim stack's `merge_request.required_contexts` context string (also typically visible/guessable, e.g. `ci/travis`). No Shipit secrets, sessions, or GitHub App keys are needed by the attacker directly — only legitimate control of one onboarded repo's own signed webhook channel. This is a realistic configuration for any shared/multi-tenant Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and the analogous `CheckSuiteHandler`) so that incoming statuses are only applied to `Commit` rows belonging to stacks whose repository matches the webhook's authenticated `repository_owner`/`repository.full_name`, e.g. `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_owner: repository_owner_from_payload }).each { ... }`, instead of a bare global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` (org `"victim-org"`) and `stack_b` (org `"attacker-org"`), both configured in `Shipit.github_apps` with distinct `webhook_secret`s.
2. Create a `MergeRequest` on `stack_a` whose head `Commit#sha == "deadbeef...".freeze`, with `merge_queue_enabled: true` and cached deploy spec `required_contexts: ["ci/travis"]`.
3. Create a second, unrelated `Commit` with the identical `sha` under `stack_b`.
4. Build a `status` webhook payload: `{ sha: "deadbeef...", state: "success", context: "ci/travis", repository: { owner: { login: "attacker-org" } } }`, signed with `stack_b`'s legitimate `webhook_secret`.
5. `POST /webhooks` with that signature; assert `response.status == 200`.
6. Assert `stack_a`'s `MergeRequest#head.statuses.last.context == "ci/travis"` and `StatusChecker.new(stack_a_head, stack_a.required_statuses).success?` is now `true`.
7. Stub `stack_a.github_api.merge_pull_request`; run `ProcessMergeRequestsJob.perform_now(stack_id: stack_a.id)` and assert `merge_pull_request` was called — proving the victim stack's PR merges off a status forged via the unrelated `stack_b`/`attacker-org` webhook.
