### Title
Textcoin mnemonic (spendable private key) logged in plaintext to console/log on claim-back failure or success - ([File: wallet.js])

### Summary
`claimBackOldTextcoins()` in `wallet.js` logs the full textcoin mnemonic — the BIP39 seed phrase that deterministically derives the private key controlling a textcoin's funds — to `console.log` on every claim attempt, whether it succeeds or fails. [1](#0-0) 

### Finding Description
A textcoin is a payment sent to an address derived from a mnemonic (`expandMnemonic()`), and possessing the mnemonic is equivalent to possessing the private key that can spend the coin (`addrInfo.xPrivKey`, derived via `mnemonic.toHDPrivateKey()`). [2](#0-1) 

`claimBackOldTextcoins(to_address, days)` reads unclaimed mnemonics from the `sent_mnemonics` table and, for each one, calls `receiveTextCoin()`. Regardless of outcome, the raw mnemonic string is concatenated directly into a `console.log` message:
```
console.log("failed claiming back old textcoin "+row.mnemonic+": "+err);
console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
``` [3](#0-2) 

This is directly analogous to CVE-2014-1948 (Glance logging a sensitive credential — the Swift backend password embedded in a URL — to WARNING-level logs on authentication failure). Here, ocore logs a spending credential (the mnemonic/seed) unconditionally to stdout/console on both success and failure paths of an unprivileged, automatic wallet operation (claiming back stale textcoins sent by the wallet owner). Node.js `console.log` output is commonly captured to persistent log files by process managers (pm2, systemd journal, docker logs, `> log.txt` redirection used by many ocore-based headless wallets/hubs), making this a durable on-disk secret leak reachable by any local user or process with log access, not just an attacker with direct DB access.

### Impact Explanation
Anyone who can read the wallet's console output/log files (local users, log aggregation systems, crash reporters, support/ops tooling, container log drivers) obtains the mnemonic and can independently derive `addrInfo.xPrivKey` and sign a transaction moving the textcoin's remaining funds, before or in a race with the legitimate owner's claim-back. This is a concrete unauthorized-spending vector: exposure of a spending secret through a low-privilege side channel (logs) that is entirely disconnected from normal DB access controls, matching the "unauthorized spending" impact class in scope.

### Likelihood Explanation
`claimBackOldTextcoins` runs automatically/periodically as part of textcoin lifecycle management on any full wallet that sends textcoins and is not gated by any special privilege — it fires for every stale unclaimed textcoin. Every such invocation logs the mnemonic, so exposure is deterministic and not conditional on an attacker action, only on log-file/console accessibility, which is a very common deployment configuration (redirected stdout, pm2 logs, docker logs) for ocore/headless-wallet based node.js services.

### Recommendation
Remove the mnemonic from the log messages in `claimBackOldTextcoins` (log only the destination address, unit, asset, and a redacted/hashed identifier instead of the raw mnemonic), e.g.:
```js
console.log("failed claiming back old textcoin (address "+addrInfo_address+"): "+err);
console.log("claimed back textcoin, unit "+unit+", asset "+asset);
```
More generally, audit all `console.log`/`console.error` calls that interpolate mnemonics, private keys, or pairing/authentication secrets (similar patterns exist for pairing secrets in `device.js`, though those are less directly fund-controlling) and scrub them before logging.

### Proof of Concept
1. Attacker obtains read access to the target's ocore/headless-wallet process logs (e.g., via a misconfigured log aggregator, shared hosting, container log driver, or `pm2 logs`).
2. Wallet owner sends a textcoin (creates a row in `sent_mnemonics`) that later goes unclaimed for the configured number of days.
3. The wallet's scheduled job invokes `claimBackOldTextcoins(to_address, days)`.
4. On every iteration, `wallet.js` logs `"claimed back mnemonic "+row.mnemonic+...` or `"failed claiming back old textcoin "+row.mnemonic+...` to console/log file. [3](#0-2) 
5. Attacker reads the mnemonic from the log, runs it through `expandMnemonic()`/`toHDPrivateKey()` logic (same code available in `wallet.js`) to derive the private key, and signs and broadcasts a transaction spending any remaining balance at that address before the legitimate claim-back completes.

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}
```

```javascript
// if a textcoin was not claimed for 'days' days, claims it back
function claimBackOldTextcoins(to_address, days){
	if (typeof days !== 'number')
		throw Error("bad days: " + days);
	db.query(
		"SELECT mnemonic FROM sent_mnemonics LEFT JOIN unit_authors USING(address) \n\
		WHERE mnemonic!='' AND unit_authors.address IS NULL AND creation_date<"+db.addTime("-"+days+" DAY"),
		function(rows){
			async.eachSeries(
				rows,
				function(row, cb){
					receiveTextCoin(row.mnemonic, to_address, function(err, unit, asset){
						if (err)
							console.log("failed claiming back old textcoin "+row.mnemonic+": "+err);
						else
							console.log("claimed back mnemonic "+row.mnemonic+", unit "+unit+", asset "+asset);
						cb();
					});
				}
			);
		}
	);
}
```
