Based on my research, I found a valid analog to the reported vulnerability class: an "owner"-controlled parameter that can be updated instantly, with no timelock, and that is trusted at validation time by counterparties who have no way to know it changed before their transaction confirms.

### Title
Asset definer can front-run pending attested-asset payments by instantly changing the `asset_attestors` list - (File: validation.js, definition.js)

### Summary
The reported bug class is "owner changes a live, security-critical parameter with no timelock, exploiting the gap between a victim's pending transaction and its confirmation." The closest reachable analog in `ocore` is the `asset_attestors` message: the definer of a `spender_attested` asset can update the list of trusted attestors at any moment, and this list is evaluated live (against `last_ball_mci`) whenever anyone tries to spend the asset, exactly like the "exchange" address in the report was swapped right before `gulp()`.

### Finding Description
When an asset is created with `spender_attested: true`, only addresses attested by one of the asset's `attestors` may issue/spend it, checked in `validatePayment`: [1](#0-0) . The list of trusted attestors is not fixed at asset-definition time; the definer can update it at will via an `asset_attestors` message, and the only check is that the sender is the definer: [2](#0-1) . There is no cooldown, no timelock, and no on-chain signalling period before the new list takes effect for units whose `last_ball_mci` already covers the update — the same "instant change, no timelock" pattern flagged in the external report about `exchange`/fee parameters.

Because attestor-list changes and ordinary attested payments compete for stabilization in the DAG (much like two transactions competing for block inclusion), the definer ("owner" of the asset) can watch the network for a pending attested payment or issuance and post a conflicting `asset_attestors` update that removes the attestor who vouched for the sender, or adds a colluding attestor who vouches for an address the definer controls, then race it to confirm first. This mirrors the report's core issue: `validateAttestorListUpdate` grants the definer unrestricted, immediate control over a parameter (`attestors`) that other unprivileged unit posters unconditionally rely on when constructing their payment, with `objAsset.arrAttestedAddresses` recomputed from the latest stable list [3](#0-2) .

### Impact Explanation
If exploited, a malicious asset definer can:
- Retroactively invalidate an honest spender's in-flight attested payment by revoking the attestor that had attested them, causing the payment to fail stability/validity for other nodes or get stuck, effectively freezing user funds tied up in that payment.
- Insert a colluding attestor at the last moment to instantly qualify an address they control as "attested," letting them siphon or redirect asset issuance/transfers that are gated by `spender_attested`, comparable to the reported theft-via-malicious-exchange scenario.

This can cause node disagreement about payment validity depending on the exact stabilization order (a "node disagreement on validity" outcome) and can result in legitimate spenders' fund flows being blocked or hijacked.

### Likelihood Explanation
The precondition is a `spender_attested` asset controlled by a malicious/compromised definer — this is not a hypothetical add-on since `spender_attested`, `attestors`, and `asset_attestors` are first-class, documented parts of the asset-definition and validation logic [4](#0-3) , and any asset definer can invoke this update at any time with a single, cheaply-composed unit [5](#0-4) . Exploiting the race requires only normal DAG-monitoring capability (watching the network for a pending payment referencing the asset), which any unprivileged posting party — including the asset definer itself — already has.

### Recommendation
Introduce a timelock / delayed-activation period for `asset_attestors` updates (e.g., require the new list to only take effect after N main-chain indices, or require it to be co-signed/notified in advance), analogous to the report's core recommendation. Alternatively, bind attested-payment validity to the attestor list version referenced at the time the payment unit was composed, so the definer cannot retroactively change the rules for a payment already broadcast.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Attestor `X` attests address `V` (a normal user, `attestation` message).
3. `V` composes and broadcasts a payment spending `A` from address `V`.
4. Before `V`'s payment stabilizes, `D` broadcasts an `asset_attestors` update removing `X` from `attestors` (or replacing it with a colluding attestor `Y` that immediately attests `D`'s own address).
5. Depending on the final DAG ordering/stabilization, either:
   - `V`'s payment now fails `spender_attested` validation (`objAsset.arrAttestedAddresses.indexOf(issuer_address) === -1` at `validation.js:2120-2121`) causing loss of expected transfer, or
   - `D` immediately issues/spends the same asset using the newly-attested address `Y`-vouched address, front-running `V`.

This exactly parallels the external report's "owner changes a live routing/permission parameter right before the victim's transaction confirms" bug class, transplanted onto `ocore`'s asset-attestor mechanism. [2](#0-1) [6](#0-5)

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
