This confirms the vulnerability. Let me check the routes to finalize understanding of the endpoint structure.### Title
CCMenu API token issued for one stack authorizes read access to every stack on the instance - (File: `app/controllers/shipit/ccmenu_url_controller.rb`)

### Summary
`CCMenuUrlController#fetch` mints an `ApiClient` token intended to expose the build status of a *single* stack via the public CCMenu XML endpoint. The generated `ApiClient` is never scoped to that stack (`stack_id` is left `nil`), and the consuming endpoint, `Api::CCMenuController#show`, looks up the target stack with a global `Stack.from_param!(params[:stack_id])` instead of the stack-scoped `stacks` helper used everywhere else in the API. The result is a token, handed out for embedding in third-party CI dashboard tools, that in fact authorizes reading the deploy status of any stack in the Shipit instance simply by changing the `stack_id` in the URL.

### Finding Description
This mirrors the OpenVM finding's bug class: a value is supposed to be constrained/bound (byte-decomposed limbs bound to the immediate value) but the constraint is missing, so the checked property and the actually-enforced property diverge. Here the analogous equality that should hold is:

```
stack the token authorizes == stack the token is allowed to touch
```

`CCMenuUrlController#fetch` creates the token like this: [1](#0-0) 

Note `ApiClient.create_with(permissions: %w[read:stack])` does not set `stack:`, and `find_or_create_by!(creator: current_user, name: 'CCMenu Client')` reuses (or creates) a single client per *user*, not per *stack*. Since `ApiClient#stack` is `optional: true` and left blank here, `stack_id` on this client is `nil`. [2](#0-1) 

Everywhere else in the API, stack lookups go through the scoped helper: [3](#0-2) 
which restricts `Stack.all` down to `Stack.where(id: current_api_client.stack_id)` only if `stack_id` is present — but for a CCMenu client, `stack_id` is `nil`, so `stacks` resolves to **all stacks**.

Crucially, `Api::CCMenuController` doesn't even rely on that scoping: it overrides `stack` to bypass it entirely: [4](#0-3) 

It only enforces the coarse permission string via `require_permission :read, :stack`, which checks that the client's `permissions` array includes `"read:stack"` — it does not check *which* stack the client is scoped to: [5](#0-4) 

Because the token itself carries no `stack_id` binding, and the endpoint that consumes it does no stack-scoping check, the same URL/token that a user fetches for "Stack A" (`GET /ccmenu_url?stack_id=A`) can be replayed against `/api/stacks/B/ccmenu.xml?token=...` for any other stack `B` on the instance, and it will succeed.

### Impact Explanation
This breaks the deployment-trust binding "a stack a token authorizes vs. a stack it touches." An attacker who obtains a CCMenu token (these tokens are explicly designed to be embedded in third-party/public CI dashboard widgets — i.e., lower-trust exposure surfaces, e.g. pasted into CCMenu client apps, status dashboards, Slack integrations, etc.) gains unauthenticated read access to the deploy state of every stack on the Shipit instance: last deploy id, whether it's running, when it ended, and stack details rendered by the `shipit/ccmenu/project` view — not just the one stack the URL was generated for. This satisfies the "High" impact bar: "unauthenticated read of stack state, task streams or deploy output" across stacks the token holder was never meant to see, including stacks belonging to unrelated repositories/environments.

### Likelihood Explanation
Any Shipit user with UI access can generate one of these CCMenu tokens for a stack they have legitimate access to view (this is a self-service feature — `stacks_controller`/`settings.html.erb` exposes the "Get CCMenu URL" action to any authenticated user). If that token then leaks (which is expected, since it's designed to be pasted into external monitoring tools), the leaker/attacker can pivot from "read access to one stack's build badge" to "read access to every stack's deploy status," widening the blast radius of what should have been a narrowly-scoped credential. No GitHub write access, webhook secret, or existing `ApiClient` privileges are required beyond obtaining any one CCMenu token.

### Recommendation
- Scope the generated `ApiClient` to the requested stack: `ApiClient.create_with(permissions: %w[read:stack], stack:).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')` so `stack_id` is non-nil and tied to the specific stack.
- In `Api::CCMenuController#stack`, use the stack-scoped lookup (`stacks.from_param!(params[:stack_id])` as done in `Api::BaseController`) instead of the unscoped `Stack.from_param!(params[:stack_id])`, so a client's `stack_id` binding is actually enforced.

### Proof of Concept
1. As user Alice, visit Stack A's settings page and request its CCMenu URL: `GET /stacks/org/repo/environment_a/ccmenu_url`. This creates (or reuses) an `ApiClient` named "CCMenu Client" for Alice with `permissions: ["read:stack"]` and `stack_id: nil`, and returns `https://shipit.example.com/api/stacks/<A_id>/ccmenu.xml?token=<TOKEN>`.
2. Take `<TOKEN>` and request a different stack B (owned by a different repository/environment Alice may not otherwise have visibility into via this integration):
   `GET /api/stacks/<B_id>/ccmenu.xml?token=<TOKEN>`
3. `Api::CCMenuController#authenticate_api_client` authenticates the token successfully (it's a valid `ApiClient`), `require_permission :read, :stack` passes because the client's `permissions` includes `read:stack`, and `stack` resolves via unscoped `Stack.from_param!(<B_id>)` — returning Stack B's deploy status, contradicting the intended one-token-per-stack design.
