This confirms the vulnerability: the base `Handler` class defines a `stacks` helper that scopes lookups to the repository named in the webhook payload [1](#0-0) , but `StatusHandler#process` does not use it — it queries `Commit.where(sha: params.sha)` across the entire `commits` table with no stack/repository filter at all [2](#0-1) .

### Title
Cross-tenant SHA collision in `StatusHandler#process` allows unauthorized merge via `MergeRequest#merge!` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` creates a `Status` on every `Commit` row in the database whose `sha` matches the webhook payload, regardless of which repository/org the webhook's signature was verified against. An attacker who controls a repository monitored by the same Shipit instance can trigger a legitimately-signed `status` webhook naming an arbitrary `sha`/`context`, and if that sha collides with the `head` commit of a pending `MergeRequest` on a *different, victim* stack with `merge_queue_enabled?`, the forged status flips `MergeRequest#all_status_checks_passed?` to true for the victim, causing `ProcessMergeRequestsJob` to call `merge_request.merge!` and merge the victim's pull request via `stack.github_api.merge_pull_request` without any of the victim's own CI ever running.

### Finding Description
The broken binding: the equality that should hold is `webhook.repository.full_name == commit.stack.repository.full_name` for any `Status` created from that webhook, but `StatusHandler#process` never enforces it. Instead of using the `Handler#stacks` scoping helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers rely on [1](#0-0) , `StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit#create_status_from_github!` then writes a `Status` scoped to that commit's own `stack_id`, using `stack_id:` taken from `commit.stack_id`, not from the webhook's authenticated repository [3](#0-2) [4](#0-3) .

`WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App belonging to `repository_owner` (`params.dig('repository','owner','login')`) [5](#0-4) . It proves the payload came from *some* org onboarded to Shipit; it proves nothing about which `sha` values that org is entitled to report statuses for. `sha` is attacker-controlled free text in the JSON body and is not otherwise validated against the reporting repository.

Exploit flow:
1. Attacker owns/controls a repository (`attacker/repo`) that is itself connected to Shipit (a legitimate stack, so a real webhook secret exists for their org).
2. Attacker discovers (or brute-forces/observes) that a victim Stack B has a pending `MergeRequest` whose `head.sha` equals some commit sha `S` (e.g., by referencing/cherry-picking a well-known public commit, or because Shipit's git history is shared/forked so shas collide legitimately).
3. Attacker triggers (or directly POSTs, since GitHub will properly sign whatever status event fires for their own repo) a `status` webhook with `sha: S`, `state: success`, `context:` equal to one of victim stack B's `merge_request_required_statuses`.
4. `StatusHandler#process` finds `Commit.where(sha: S)` — this returns the commit row belonging to victim Stack B (not attacker's repo) and calls `create_status_from_github!`, writing a `Status` with `stack_id` = Stack B's id [3](#0-2) .
5. `Status#after_create` fires `commit.schedule_continuous_delivery`, and (per existing test coverage) transitions to `success`/`pending` enqueue `ProcessMergeRequestsJob` for the commit's actual stack [6](#0-5) .
6. `ProcessMergeRequestsJob#perform(stack_b)` calls `merge_request.refresh!`, then `merge_request.all_status_checks_passed?`, which evaluates `StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?` [7](#0-6)  — now true because of the forged status.
7. `merge_request.merge!` calls `stack.github_api.merge_pull_request(stack.github_repo_name, number, ...)` [8](#0-7)  — merging the victim's pull request into the victim's protected branch, using Shipit's own GitHub credentials for stack B, with no CI from stack B ever having run.

Existing guards do not catch this: `verify_signature` validates org-level HMAC only, not sha-to-repository binding [5](#0-4) ; the `ExplicitParameters` schema for `StatusHandler` only validates types/presence of `sha`, `state`, etc., not ownership [9](#0-8) ; and `Handler#stacks`/`Repository.from_github_repo_name` scoping — which would have prevented this — is simply not used by `StatusHandler`.

### Impact Explanation
A payload authenticated for repository/org A causes a database write (`Status`) and ultimately a privileged action (`merge_pull_request`) against stack B, a different tenant that never authorized or interacted with the request. This is a cross-tenant integrity violation matching "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy, rollback or merge," both listed as Critical impact categories. It is repeatable against any victim stack with `merge_queue_enabled?` and a pending `MergeRequest`, as long as the attacker can find/produce a sha collision with that stack's `head` commit and the correct required-status context. The GitHub PR is genuinely merged into the victim's real repository, bypassing all CI enforcement.

### Likelihood Explanation
Preconditions: victim Stack must have `merge_queue_enabled?` true, an open `MergeRequest` in `merge_status: 'pending'`, and the attacker needs a commit sha that already exists as `head` for that MergeRequest (the hard part — `sha` values are 160-bit git hashes, so exact collision is not attacker-chosen in general; however, if the attacker can get their own repository to reference/import/fork the exact same commit — e.g., cross-repository cherry-picks, common merge-bot patterns, monorepo forks tracked by multiple stacks, or attacker simply pushing the victim's known public commit sha as a `pull_request` head into a repo they control that's also tracked by Shipit — the collision is fully achievable with attacker-controlled effort, not brute force). Given these preconditions, the exploit requires only a single genuinely-signed webhook from the attacker's own onboarded repository — no secrets, no privileged role, and no interaction with the victim's stack. This is a real, code-level authorization gap rather than a purely theoretical hash-collision attack, since same-sha references across differently-owned Shipit-tracked repositories are a normal occurrence (shared open-source commits, forks, cherry-picks).

### Recommendation
Scope `StatusHandler#process` to the webhook's authenticated repository, mirroring other handlers: iterate `stacks.flat_map(&:commits).where(sha: params.sha)` (or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) using the `stacks` helper derived from `Repository.from_github_repo_name(repository_name)` instead of an unscoped `Commit.where(sha: ...)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not create a status for a commit belonging to a different repository" do
  stack_a = shipit_stacks(:shipit)         # attacker's onboarded stack (org A)
  stack_b = shipit_stacks(:cyclimse)       # victim stack (org B), merge_queue_enabled
  victim_commit = stack_b.commits.create!(sha: "deadbeef" * 5, ...)
  merge_request = shipit_merge_requests(:some_pending_mr_on_stack_b)
  merge_request.update!(head: victim_commit)

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'ci/required',
    'repository' => { 'full_name' => stack_a.repository.github_repo_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Additional integration-level assertion per the audit prompt: stub `Shipit.github.api.merge_pull_request`, post the forged `status` webhook (authenticated for org A) with `sha` equal to stack B's pending MR head, run `ProcessMergeRequestsJob.perform_now(stack_b)`, and assert `merge_pull_request` was **not** called for stack B's repo once the fix (scoping by `Repository.from_github_repo_name`) is applied — currently, without the fix, it **is** called, demonstrating the vulnerability.
