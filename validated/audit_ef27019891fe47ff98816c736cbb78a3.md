### Title
Fail-open `verify_webhook_signature` lets unauthenticated `pull_request`/`unlabeled` payload archive or unarchive a review stack for any org lacking a `webhook_secret` - (File: lib/shipit/github_app.rb)

### Summary
`Shipit::WebhooksController#verify_signature` resolves the GitHub App config to check against by reading `repository.owner.login`/`organization.login` straight from the attacker-supplied JSON body, then calls `GitHubApp#verify_webhook_signature`, which returns `true` whenever no `webhook_secret` is configured for that org, regardless of the actual signature header. For any org configured without a `webhook_secret`, this makes signature verification a no-op, so `UnlabeledHandler` will archive/unarchive review stacks purely from forged input.

### Finding Description
The broken binding: `verified == (HMAC(webhook_secret, raw_body) matches X-Hub-Signature)` is expected to hold for every accepted event, but the real implementation is `verified == (webhook_secret.blank? || HMAC(...) matches signature)` — see `lib/shipit/github_app.rb:76-83`:

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

`Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) picks the `GitHubApp` instance using `repository_owner`, itself taken from the unauthenticated payload (`params.dig('repository','owner','login')`, line 61). If that org's config in `Shipit.github(organization: ...)` has no `webhook_secret` set, `verify_webhook_signature` short-circuits to `true` no matter what `X-Hub-Signature` header is sent (or omitted).

Once past `verify_signature`, `Shipit::Webhooks.for_event('pull_request')` dispatches to `UnlabeledHandler#process` (`app/models/shipit/webhooks/handlers/pull_request/unlabeled_handler.rb:41-98`). It resolves `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (same attacker-controlled JSON field) and, based on `provisioning_behavior` and label presence, calls `stack.archive!` or `stack.unarchive!` on the `ReviewStackAdapter`-wrapped `ReviewStack` for that repo/PR number (`environment: "pr#{params.number}"`). `ReviewStackAdapter#archive!`/`#unarchive!` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb:23-50`) call `stack.deprovision`, `remove_from_provisioning_queue`, `Shipit::ReviewStackProvisioningQueue.add`, and `stack.archive!`/`unarchive!` — real state-mutating operations on the stack.

Downstream, `blocked?`/forced-status gating on `Stack`/`Commit` (`app/models/shipit/stack.rb`, `app/models/shipit/commit.rb`, `blocking_statuses`) reads the stack's live state; archiving/unarchiving toggles provisioning and deploy eligibility for that stack, so the forged event amplifies into a real gate change for deploys tied to that stack.

Existing guards do not stop this: `drop_unhandled_event` only checks the event is registered; `ExplicitParameters` schema only validates shape, not authenticity; there is no `force_github_authentication`/session check on this unauthenticated webhook endpoint by design. The only real gate is `verify_signature`, and it is bypassed entirely once an org has no `webhook_secret` — this is a pure configuration precondition, not a logic flaw that lets one *authenticated* org's payload write to *another* org's stack. The `repository_owner` used to pick the verifying `GitHubApp` and the `repository.full_name` used to resolve the actual `Repository`/`Stack` come from the same forged JSON body and must reference the same org, so this is not a cross-tenant/cross-repo forgery (an attacker cannot use org A's valid signature to hit org B's stack); it is a full unauthenticated-write bypass restricted to whichever org(s) the operator left without a `webhook_secret`.

### Impact Explanation
For any org whose `Shipit.github` config omits `webhook_secret`, an unauthenticated internet request to `POST /webhooks` with a crafted `pull_request`/`unlabeled` JSON body and an arbitrary/absent `X-Hub-Signature` will pass `verify_signature` and let `UnlabeledHandler` archive or unarchive any review stack belonging to that org's repositories that has `review_stacks_enabled` and a matching PR-numbered environment. This deprovisions/reprovisions infrastructure and toggles deploy gating (`blocking_statuses`/`blocked?`) for that stack — matching the "authentication bypass (forged webhook accepted)" Critical category, but scoped to the misconfigured org, not cross-tenant across orgs that do have a secret configured.

### Likelihood Explanation
Requires an org with `review_stacks` enabled and no `webhook_secret` configured in `Shipit.github` — an operator misconfiguration/omission, not a default. Given that precondition, the attack is trivial and free: no credentials, no signature computation, one HTTP POST, fully repeatable against any PR number/environment on that org's repositories.

### Recommendation
Make `verify_webhook_signature` fail closed: return `false` (reject) when no `webhook_secret` is configured instead of `true`, or require `webhook_secret` to be present for every configured org at boot/config-validation time so this state is unreachable in production.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
