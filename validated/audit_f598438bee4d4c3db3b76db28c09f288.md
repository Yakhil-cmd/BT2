The reported bug class is an unbounded-loop / gas-exhaustion DoS in Solidity's `Staking._claimRewards()`, where a staker's reward calculation cost scales with the number of `stakingConditions` updates that occurred since their last interaction, and the number of iterations is only limited by an owner-configurable soft cap.

I looked for an analogous unbounded-loop-since-last-update pattern in FRAME's staking implementations:

- `pallet-staking`'s reward payout path (`do_payout_stakers_by_page` / `do_payout_stakers`) does **not** iterate over the caller's history since their last claim. Each call operates on a single `era` and a single `page`, bounded by `T::MaxExposurePageSize`, with the `era` range gated by the fixed `HistoryDepth` config value rather than by "time since last claim." [1](#0-0) 
- `pallet-nomination-pools` avoids iteration entirely by using an O(1) "reward counter" accounting model: `pending_rewards()` computes a member's payout as a single multiplication between the delta of two fixed-point counters, with no loop over eras or updates since the member's last claim. [2](#0-1) 
- `staking-async`'s era reward manager similarly bounds storage/iteration by a fixed `HistoryDepth` window and uses explicit permissionless `prune_era_step` extrinsics (weight-metered, one bounded step per call) rather than doing unbounded cleanup/iteration inside a user-facing reward-claim call. [3](#0-2) 

More fundamentally, FRAME's dispatch model differs from EVM gas: each extrinsic's weight is fixed via `#[pallet::weight(...)]` and enforced by benchmarking-derived `WeightInfo`, not by an open-ended, caller-triggerable growing loop whose cost is bounded only by an admin-settable "cap" parameter analogous to `maxStakingConditions`. None of the reward-claim paths I found have a loop whose iteration count is proportional to "time since the user's last interaction" that a low-privilege attacker/owner-configurable parameter could grow unboundedly.

Per the analysis rules, unbounded-loop / storage-growth / gas-only optimization findings are explicitly excluded, and I found no exact structural analog (a user-facing extrinsic whose cost scales unboundedly with elapsed updates since the caller's last interaction) in the scoped FRAME staking/nomination-pools code.

	/// The pending rewards of this member.
	fn pending_rewards(
		&self,
		current_reward_counter: T::RewardCounter,
	) -> Result<BalanceOf<T>, Error<T>> {
		// accuracy note: Reward counters are `FixedU128` with base of 10^18. This value is being
		// multiplied by a point. The worse case of a point is 10x the granularity of the balance
		// (10x is the common configuration of `MaxPointsToBalance`).
		//
		// Assuming roughly the current issuance of polkadot (12,047,781,394,999,601,455, which is
		// 1.2 * 10^9 * 10^10 = 1.2 * 10^19), the worse case point value is around 10^20.
		//
		// The final multiplication is:
		//
		// rc * 10^20 / 10^18 = rc * 100
		//
		// the implementation of `multiply_by_rational_with_rounding` shows that it will only fail
		// if the final division is not enough to fit in u128. In other words, if `rc * 100` is more
		// than u128::max. Given that RC is interpreted as reward per unit of point, and unit of
		// point is equal to balance (normally), and rewards are usually a proportion of the points
		// in the pool, the likelihood of rc reaching near u128::MAX is near impossible.

		(current_reward_counter.defensive_saturating_sub(self.last_recorded_reward_counter))
			.checked_mul_int(self.active_points())
			.ok_or(Error::<T>::OverflowRisk)
	}
