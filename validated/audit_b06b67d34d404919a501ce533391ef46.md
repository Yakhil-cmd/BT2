## Title
Uncaught `throw Error("more than one output...")` in `private_payment.js` crashes the entire node process on duplicate/retried private-payment delivery — (File: `private_payment.js`)

## Summary
`private_payment.js`'s duplicate-check query in `validateAndSavePrivatePaymentChain` can legitimately return more than one row for the same `(unit, asset, message_index)` key whenever the private message being validated is a **divisible** private asset payment (i.e. not `fixed_denominations`), because such messages commonly have more than one output (payment + change) and the duplicate-detection SQL does not filter by `output_index` in that case. When this happens, the code executes an unguarded `throw Error(...)` inside a `db.query` callback. This exception is never caught, propagates to Node's `uncaughtException` handler in `network.js`, which explicitly re-throws to **crash the whole process**.

## Finding Description
`validateAndSavePrivatePaymentChain` in `private_payment.js` runs a de-duplication check before actually validating/saving a private payment chain: [1](#0-0) 

For fixed-denomination (indivisible) private assets, the query additionally filters on `output_index`, so at most one row can match. For **divisible** private assets (`objAsset.fixed_denominations` is falsy), no `output_index` filter is applied, meaning the query intentionally returns *all* outputs belonging to that message — which for a typical payment (recipient output + change output) is normally **2 or more rows**.

The very next line does:
```
if (rows.length > 1)
    throw Error("more than one output "+sql+' '+params.join(', '));
``` [2](#0-1) 

This is a synchronous `throw` inside an asynchronous `db.query` callback, so it cannot be caught by any surrounding `try/catch` in the call chain (`network.handleOnlinePrivatePayment` → `handlePrivatePaymentChains` in `wallet.js`).

Reachability: this code path is invoked whenever a private payment chain is processed for the **second time** with outputs already inserted from the first processing — a scenario the code itself acknowledges as a normal occurrence: [3](#0-2) 

The wallet device-message handler `handlePrivatePaymentChains` (subject `"private_payments"`, reachable from any paired device / private-payment counterparty) forwards chains into `network.handleOnlinePrivatePayment`, which for known units re-invokes `privatePayment.validateAndSavePrivatePaymentChain`: [4](#0-3) [5](#0-4) 

Once the process reaches the `uncaughtException` handler, `network.js` deliberately re-throws to terminate: [6](#0-5) 

## Impact Explanation
Any private-payment counterparty (a paired device, cosigner, or peer who has previously exchanged/forwarded a private divisible-asset payment) can trigger this by simply re-delivering (or having the protocol naturally re-deliver, as explicitly anticipated by the code comment) the same private-payment chain a second time after it has already been saved. Because the SQL that performs deduplication omits the `output_index` filter for divisible assets, the very first successful save of a 2-output payment sets up the crash condition for the very next delivery attempt of the same chain. The resulting unhandled exception crashes the entire wallet/full node process — a full denial of service, forcing a restart and leaving the node/wallet unable to process further units, private payments, or confirm new transactions until manually restarted.

## Likelihood Explanation
High. No cryptographic breaking, no race condition, and no privileged access is required — an ordinary chat/wallet correspondent who is a legitimate party to a private payment (recipient, cosigner, or forwarding peer) can cause this merely by resending a previously-processed chain (a scenario the codebase itself documents as expected, e.g. "we may receive the same unit and message index but different output indexes ... we also receive the same (unit, message_index, output_index) twice"). It requires only a divisible private asset with more than one output in the message, which is the common case (payment output + change output).

## Recommendation
- Remove the unconditional `throw` and instead route through the `ifError`/`ifOk` callback chain so a duplicate detection never crashes the process; specifically, when duplicate rows are legitimately expected for divisible assets, compare against `payload.outputs` (as already done a few lines later for the single-row case) instead of asserting `rows.length <= 1`.
- Alternatively, restrict the duplicate-check SQL to also consider `output_index` (or iterate rows and match against `payload.outputs`) for divisible assets so that multiple genuine outputs per message don't trip the `rows.length > 1` invariant.
- More broadly, audit `db.query` callbacks across `private_payment.js`, `validation.js`, `definition.js`, etc. for synchronous `throw` statements guarding conditions that are actually reachable via attacker/peer-supplied or naturally-retried data, and convert them to graceful error callbacks, consistent with the TensorFlow `CHECK`-fail fix pattern (replace unconditional assertions with proper error returns).

## Proof of Concept
1. Set up two paired devices/wallets, A (sender) and B (recipient), with a divisible private asset.
2. A sends B a private payment chain for that asset with a message containing 2 outputs: one to B's address and one change output back to A. B processes and saves it via `wallet.js`'s `"private_payments"` handler → `network.handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain`, which inserts 2 rows into `outputs` for `(unit, asset, message_index)`.
3. A (or B, replaying the same message, e.g. by resending the identical `chains` payload through a different `handledChainsCache` key, or simply because the protocol re-delivers it — as the code comment anticipates) causes B to process the same `(unit, asset, message_index)` chain again.
4. The duplicate-check SQL in `private_payment.js` (no `output_index` filter for divisible assets) now returns 2 rows, hitting `throw Error("more than one output ...")` inside the `db.query` callback.
5. The exception is uncaught, bubbles to Node's `process.on('uncaughtException', ...)` handler in `network.js`, which re-throws and crashes B's node/wallet process entirely.
