### Title
Unbounded `eventBus` Listener / Closure Leak in Private-Payment Chain Handling Leads to Memory-Exhaustion DoS - ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in [1](#0-0)  registers a one-shot `eventBus.once(key, …)` listener for every private-payment chain whose validation result is not immediately known (`ifQueued`). The listener — and the closure it captures (`arrChains`, `assocValidatedByKey`, `body`, `from_address`, etc.) — is only released when the corresponding `key` event is eventually emitted by `network.js`'s `handleSavedPrivatePayments()`. If the chain references a unit that never actually arrives on the network, that event is never emitted, and the listener plus its captured data are retained in memory forever. This mirrors the root cause of CVE-2020-6080: on an incomplete/erroneous parse path, allocated per-message state is never freed, and a remote party can repeat the trigger indefinitely to exhaust memory.

### Finding Description
`handlePrivatePaymentChains()` builds a `key` per chain element from the (still unverified) unit hash and payload hash: [2](#0-1) 

For chains whose validation cannot complete synchronously (the "most likely outcome for light clients"), it registers a listener that is expected to fire once `network.js` finishes processing the referenced unit: [3](#0-2) 

The corresponding producer of that event lives in `network.js`'s `handleSavedPrivatePayments()`, which only examines rows of `unhandled_private_payments` that are **joined against the `units` table** — i.e., it only fires the event once the referenced unit is actually known/downloaded: [4](#0-3) [5](#0-4) 

`handleOnlinePrivatePayment()` only checks that the `unit` field is a syntactically valid base64 hash of the correct length; it never verifies the unit actually exists or will ever be delivered: [6](#0-5) 

A paired device/correspondent (any peer with whom the victim shares a wallet/chat, i.e., someone who can send a `private_payments` device message) can craft `private_payments` messages whose chains reference syntactically valid but non-existent unit hashes. Because:
1. Each such call generates a unique `cache_key` (hash of the whole chains array), so `handledChainsCache` dedup never suppresses new, distinct spam payloads: [7](#0-6) 
2. The referenced unit will never appear in the `units` table, `handleSavedPrivatePayments()` will never select the row and never emit `key`.
3. `cancelAllKeys()` — the only cleanup path — is invoked solely on a synchronous validation error inside the same `async.eachSeries` call, not when the awaited unit simply never shows up: [8](#0-7) 

the `eventBus.once(key, …)` listener, and everything it closes over (the full `arrChains` payload, `assocValidatedByKey`, `from_address`, etc.), remains resident in the Node.js process for the lifetime of the process. Even the DB-side row purge (`cleanBadSavedPrivatePayments`, full nodes only, after 1 day) does not touch this in-memory listener, and light nodes/wallets have no purge at all for these rows: [9](#0-8) [10](#0-9) 

### Impact Explanation
An attacker who is paired with a victim (a normal contact/correspondent relationship, not a privileged operator) can repeatedly send crafted `private_payments` messages with distinct, never-to-be-delivered unit references. Each message permanently grows the victim wallet process's heap with an un-removable `eventBus` listener and retained closure data. Sustained spam drives the victim's wallet/hub-connected node toward memory exhaustion, crashing the process and denying it the ability to process further payments/units — a legitimate denial-of-service impact under the stated criteria ("a network unable to confirm new units" for the affected node/wallet).

### Likelihood Explanation
The only precondition is an existing pairing/correspondent relationship with the victim (explicitly in scope as "paired device"/private-payment counterparty). No special privileges, node compromise, or malicious hub/peer role is required — any correspondent can trigger this repeatedly and cheaply, since crafting a syntactically valid but nonexistent unit hash is trivial.

### Recommendation
- Track and remove per-key `eventBus` listeners using a corresponding `off`/timeout mechanism so a chain awaiting an unresolved unit is eventually purged (mirroring the DB-side `cleanBadSavedPrivatePayments`/`purgeOldUnhandledJoints` timeout pattern).
- Bound the number of outstanding `assocValidatedByKey`/listener sets per correspondent/device, and rate-limit `private_payments` messages per sender.
- Ensure the in-memory listener state is cleaned up in lockstep with `unhandled_private_payments` row expiry (including for light wallets, where no expiry currently exists).

### Proof of Concept
1. Attacker device D is paired with victim wallet W (has an existing chat/wallet relationship).
2. D sends repeated `private_payments` justsaying/device messages to W (via the hub), each containing a single-element chain whose `unit` is a freshly-generated, well-formed but non-existent base64 hash (44 chars, matching `HASH_LENGTH`), with otherwise valid-looking `payload.asset/inputs/outputs` fields to pass the shape checks in [11](#0-10) .
3. For each message, W's `handlePrivatePaymentChains` → `network.handleOnlinePrivatePayment` stores the row in `unhandled_private_payments` and returns `ifQueued`, causing W to register a new `eventBus.once(key, …)` listener that will never fire because the referenced unit is never actually received.
4. Repeating step 2 indefinitely accumulates listeners/closures in W's process without bound, eventually exhausting memory and crashing/degrading W's node.

function handleOnlinePrivatePayment(ws, arrPrivateElements, bViaHub, callbacks){
	if (!ValidationUtils.isNonemptyArray(arrPrivateElements))
		return callbacks.ifError("private_payment content must be non-empty array");
	
	var unit = arrPrivateElements[0].unit;
	var message_index = arrPrivateElements[0].message_index;
	var output_index = arrPrivateElements[0].payload.denomination ? arrPrivateElements[0].output_index : -1;
	if (!ValidationUtils.isValidBase64(unit, constants.HASH_LENGTH))
		return callbacks.ifError("invalid unit");
	if (!ValidationUtils.isNonnegativeInteger(message_index))
		return callbacks.ifError("invalid message_index");
	if (!(ValidationUtils.isNonnegativeInteger(output_index) || output_index === -1))
		return callbacks.ifError("invalid output_index");

	var savePrivatePayment = function(cb){
		// we may receive the same unit and message index but different output indexes if recipient and cosigner are on the same device.
		// in this case, we also receive the same (unit, message_index, output_index) twice - as cosigner and as recipient.  That's why IGNORE.
		db.query(
			"INSERT "+db.getIgnore()+" INTO unhandled_private_payments (unit, message_index, output_index, json, peer) VALUES (?,?,?,?,?)",

			}
		);
	};

function cleanBadSavedPrivatePayments(){
	if (conf.bLight || bCatchingUp)
		return;
	db.query(
		"SELECT DISTINCT unhandled_private_payments.unit FROM unhandled_private_payments LEFT JOIN units USING(unit) \n\
		WHERE units.unit IS NULL AND unhandled_private_payments.creation_date<"+db.addTime('-1 DAY'),
		function(rows){
			rows.forEach(function(row){
				breadcrumbs.add('deleting bad saved private payment '+row.unit);
				db.query("DELETE FROM unhandled_private_payments WHERE unit=?", [row.unit]);
			});
		}
	);
	
}

function rerequestLostJointsOfPrivatePayments(){
	if (!conf.bLight || !exports.light_vendor_url)
		return;
	db.query(
		"SELECT DISTINCT unhandled_private_payments.unit FROM unhandled_private_payments LEFT JOIN units USING(unit) WHERE units.unit IS NULL",
		function(rows){
			if (rows.length === 0)
				return;
			var arrUnits = rows.map(function(row){ return row.unit; });
			findOutboundPeerOrConnect(exports.light_vendor_url, function(err, ws){
				if (err)
					return;
				requestNewMissingJoints(ws, arrUnits);
			});
		}
	);
}
