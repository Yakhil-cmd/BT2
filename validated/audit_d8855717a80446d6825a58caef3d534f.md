### Title
Webhook Signature Verification is a No-Op When an Organization Has No `webhook_secret`, Allowing Forged `membership` Events to Grant `Shipit.github_teams` Authorization - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the configured organization has no `webhook_secret`, and this is a documented, supported configuration (fixtures explicitly set `webhook_secret: # nil`). In that state, `WebhooksController` accepts **any** unsigned payload as if it came from GitHub for that organization, allowing an unprivileged attacker to forge a `membership` webhook event that creates/updates a `Team` and adds an arbitrary existing `Shipit::User` to it — directly manipulating the authorization data consumed by `Shipit.github_teams` gating.

### Finding Description
Signature verification is performed per-organization: [1](#0-0) [1](#0-0) 

The actual check is: [2](#0-1) 

`return true unless webhook_secret` means an org configured **without** a `webhook_secret` accepts unsigned/arbitrary requests unconditionally. This is not a corner case — the shipped dummy config demonstrates this as a normal, valid setup: [3](#0-2) 

The `repository_owner`/organization used to select which `GitHubApp` (and therefore which "verification", or lack thereof) applies is attacker-controlled payload data: [4](#0-3) 

Once past this check, `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler`, which trusts payload fields wholesale to create a `Team` and mutate its membership: [5](#0-4) 

`Team#organization` and team membership are the exact objects consulted by `Shipit.github_teams` authorization, as shown by the existing behavioral test asserting membership in a `Shipit.github_teams`-listed team is required to access privileged controllers such as `ApiClientsController`: [6](#0-5) 

This breaks the binding: **the organization the webhook is trusted to represent (verified, or in this configuration not verified at all) must equal the organization/team whose membership is written and later relied upon for authorization.** When `webhook_secret` is unset for an org, that equality is never enforced — anyone can claim to be GitHub and mutate `Team`/`Membership` records for that org.

### Impact Explanation
This escalates directly into `Shipit.github_teams` authorization (explicitly called out as a High-severity impact in scope): an attacker who already has (or creates, via `membership`'s `member` sub-object and `User.find_or_create_by_login!`) a Shipit `User` record can grant that user, or any other existing user login, membership in a `Team` whose `organization`/slug matches an entry in `Shipit.github_teams`, thereby bypassing the GitHub-team-membership gate that protects sensitive UI/controllers (e.g. `ApiClientsController`, which manages API tokens with `deploy:stack`/`write:stack` permissions).

### Likelihood Explanation
Likelihood is conditional on deployment configuration: it requires at least one configured organization to have no `webhook_secret` set — a configuration explicitly present in the shipped fixtures/secrets template, indicating it is a recognized, supported setup rather than a hardening failure of an individual operator. Any installation following that pattern is exploitable by any unauthenticated network client capable of reaching `/webhooks` with no credentials, tokens, or GitHub App secrets required.

### Recommendation
- Require `webhook_secret` to be present and non-blank for every configured organization; refuse to boot, or refuse all webhook traffic for that organization, if it is missing, rather than treating a missing secret as "trust everything."
- In `MembershipHandler`/`Team`, tie `organization` writes and membership grants strictly to the organization used for (and successfully validated by) signature verification, and reject events where verification was skipped.

### Proof of Concept
1. Deploy Shipit with an organization entry configured like the fixture (`webhook_secret:` left blank/nil), which is a documented supported configuration.
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and a JSON body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Attacker Team", "slug": "attacker-team", "url": "https://example.com" },
  "organization": { "login": "<victim-org-in-shipit.github_teams>" },
  "member": { "login": "<attacker-controlled-existing-user-login>" }
}
```
No `X-Hub-Signature` is required because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank [2](#0-1) .
3. `MembershipHandler#process` creates the `Team` scoped to the victim organization and adds the attacker's user as a member [5](#0-4) .
4. The attacker's user now satisfies `Shipit.github_teams` membership checks and gains access to team-gated pages/controllers, without ever authenticating to GitHub.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
