### Title
Single-step, irreversible address definition change permanently bricks the address and any funds/authority tied to it - (File: `validation.js`, `writer.js`, `storage.js`)

### Summary
Obyte's on-chain analog of "ownership" for a wallet address is its **address definition** (the `arrDefinition` bound to an address via signing/auth rules). Rotating that definition is done with an `address_definition_change` message. Unlike a safe 2-step transfer, this operation is a **single, irreversible step**: once the unit carrying the change becomes stable, the address permanently loses its old definition and must be able to produce a definition array that hashes to the new `definition_chash`. There is no staged/"pending" state and no "accept" step performed by the holder of the new definition before the switch takes effect.

### Finding Description
The `address_definition_change` message payload is validated only for basic shape and address-format correctness of the new value: [1](#0-0) 

The check on `payload.definition_chash` is merely `isValidAddress(payload.definition_chash)` — a format check confirming it is a 160-bit chash-shaped string, not a check that the sender can produce (or has already produced) a valid preimage definition that will actually hash to it.

Once the unit is written and becomes stable, `writer.js` inserts this pending change into `address_definition_changes`: [2](#0-1) 

From that point, `storage.readDefinitionChashByAddress` treats the new chash as authoritative for the address, unconditionally superseding the previous definition: [3](#0-2) 

And any subsequent signing/authentication for that address is resolved via `readDefinitionByAddress`/`readDefinitionAtMci`, which requires disclosure of a definition matching the new chash; if none is ever disclosed, the address can never again authenticate: [4](#0-3) 

This mirrors the reported bug class precisely: OZ's single-step `transferOwnership` can accidentally brick a contract by transferring control to an inoperable address with no way to walk it back. In ocore, `address_definition_change` is the equivalent "ownership transfer" primitive for an address, and it is likewise single-step and irrevocable — there is no analog of `acceptOwnership()` requiring the new definition to be proven/disclosed and accepted before the switch becomes final. A user (or wallet software with a bug) who computes or specifies a wrong `definition_chash` (e.g., from a bad definition template, an off-by-one signing-path error, or hashing the wrong array) will have that message become stable and permanently lose the ability to control the address, since the old definition is no longer valid once superseded.

### Impact Explanation
Once stable, all funds held at that address, any AA-related authority signed by that address, or shared/multisig control tied to that address become permanently frozen — nobody can produce authentifiers matching the erroneous `definition_chash`, since it does not correspond to any definition the user can actually author. This is a direct, irreversible loss/freezing of funds analogous to the "possible bricking of contracts" impact in the source report, but here it also affects fund custody directly rather than just administrative control.

### Likelihood Explanation
This requires only an unprivileged address owner posting a single `address_definition_change` message, which is a completely normal, allowed operation for any address (composer/wallet-triggered). No attacker or privileged actor is needed — the risk is purely the lack of a safety net around what is effectively an "ownership transfer" for the address, matching the exact class of accidental-bricking risk called out in the source finding.

### Recommendation
Introduce a 2-step confirmation for `address_definition_change`: require that the new definition (matching the proposed `definition_chash`) be disclosed/validated (e.g., hash-checked and structurally validated by `Definition.validateDefinition`) either in the same unit or in a companion "pending" record, and only treat the change as finalized once the new definition has been proven resolvable — otherwise reject the definition-change message before it can become stable, so a typo or bad chash can never silently and permanently strand the address.

### Proof of Concept
1. Address `A` (single-authored) posts a unit containing an `address_definition_change` message with `payload.definition_chash` set to a base32 string that is a syntactically valid chash (`isValidAddress` passes, per `validation.js:1743-1744`) but was miscomputed and does not correspond to any definition array that `A` actually holds/can produce.
2. The unit passes validation (only `isValidAddress` is checked; no proof of a matching preimage definition is required at this stage — see `validation.js:1707-1745`).
3. The unit becomes stable; `writer.js:186-191` writes the row into `address_definition_changes`.
4. From then on, `storage.readDefinitionChashByAddress` (`storage.js:754-768`) returns the erroneous `definition_chash` as current for address `A`.
5. Any future unit authored by `A` must supply a definition hashing to that erroneous chash (`storage.js:771-788`, `validation.js:1464-1483`); since no such definition exists, `A` can never again sign a valid unit — all balance and authority at `A` is permanently frozen.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});

		readDefinitionAtMci(conn, definition_chash, max_mci, callbacks);
	});

// max_mci must be stable
function readDefinitionAtMci(conn, definition_chash, max_mci, callbacks){
	var sql = "SELECT definition FROM definitions CROSS JOIN unit_authors USING(definition_chash) CROSS JOIN units USING(unit) \n\
		WHERE definition_chash=? AND is_stable=1 AND sequence='good' AND main_chain_index<=?";
	var params = [definition_chash, max_mci];
	conn.query(sql, params, function(rows){
		if (rows.length === 0)
			return callbacks.ifDefinitionNotFound(definition_chash);
		callbacks.ifFound(JSON.parse(rows[0].definition));
	});
}
