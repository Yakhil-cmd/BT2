### Title
Cross-organization webhook secret confusion allows forging events (push/status/membership) into another org's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the inbound HMAC against using `repository_owner`, derived from the *unverified* JSON body (`repository.owner.login`, falling back to `organization.login`) [1](#0-0) [2](#0-1) . Once the signature check passes, every `Shipit::Webhooks::Handlers::Handler` subclass instead resolves the *target* repository/stack from a different field of the same payload, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name` [3](#0-2) . These two payload fields are never cross-checked against each other.

### Finding Description
Shipit explicitly supports multiple GitHub organizations configured on a single instance, each with its own `webhook_secret`, as shown in the sample multi-org secrets file [4](#0-3) . `Shipit.github(organization: ...)` returns the `GithubApp` config for that specific org, and `verify_webhook_signature` HMACs the raw body against that org's secret [5](#0-4) .

The binding that should hold is: *the organization whose `webhook_secret` authenticated the request* == *the organization/repository the event is actually applied to*. This is broken because:
- Authentication org is taken from `params.dig('repository','owner','login') || params.dig('organization','login')` [2](#0-1) .
- The event target is taken from `payload.dig('repository','full_name')` in the shared handler base class used by push, status, check_suite, membership and pull_request handlers [3](#0-2) .

Nothing enforces that `repository.full_name` belongs to the org named in `repository.owner.login`/`organization.login`. An attacker who legitimately administers one org configured on this Shipit instance (Org A) knows Org A's `webhook_secret` (it's the secret Shopify staff or org admins configure when wiring the GitHub App/webhook for their own org — not a Shipit privilege). They can send a raw HTTP POST to `/webhooks` with a body where the top-level `organization.login`/`repository.owner.login` is `"OrgA"` (so the HMAC computed with Org A's secret validates) but `repository.full_name` is set to `"OrgB/some-repo"`, an org/repo they do not control that is also hosted on the same Shipit instance. `Repository.from_github_repo_name` will resolve Org B's `Repository`/`Stack` and every subsequent handler will act on it.

### Impact Explanation
This is a cross-repository/cross-organization write from an actor whose credentials were only ever valid for a different org — matching the "cross-repository writes" Critical bucket. Concretely, with a forged, correctly-"authenticated" payload the attacker can, against a stack they don't own:
- Trigger `GithubSyncJob` with an attacker-chosen `after` SHA via the `push` handler, syncing/creating commits for an arbitrary SHA on Org B's tracked branch.
- Inject/forge `status`/`commit_status` (state, description, target_url, context) for arbitrary commits on Org B's stacks, corrupting deploy-eligibility signals used to gate merges/deploys.
- Fire `check_suite` events to enqueue `RefreshCheckRunsJob` against Org B's PRs/commits.
- Abuse the `membership` handler to create/delete `Team`/`Membership` records tied to Org B's teams, which is directly security relevant because `Shipit.github_teams` membership drives `User#authorized?` and thus who may access stacks in this engine [6](#0-5) .

None of this requires an `ApiClient` token, a webhook secret for the victim org, GitHub write access to the victim repo, or a Shipit session — only a webhook secret belonging to any org configured on the same multi-tenant instance.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for more than one GitHub organization (explicitly documented/supported, see `config/secrets.development.shopify.yml`), and (2) the attacker to control at least one of those orgs' webhook secret (as an admin of their own, legitimately-onboarded org). Given multi-tenancy is an intended, documented deployment shape and no code path validates that `repository.full_name`'s owner matches the org used for signature selection, this is straightforward to exploit for anyone administering any one of the configured orgs.

### Recommendation
After `verify_signature` succeeds, re-derive `repository_owner`/`organization` used for authentication and assert it matches the owner segment of `payload.dig('repository','full_name')` (and of `organization.login` when present) before dispatching to handlers; reject with 422 on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same org identifier that was used to select the `webhook_secret`, rather than trusting `repository.full_name` independently in `Handler#repository_name`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `orga` (secret `S_A`) and `orgb` (secret `S_B`), each with a repository/stack tracked in Shipit.
2. As an admin of `orga` (who legitimately knows `S_A`), build a payload:
```json
{
  "organization": {"login": "orga"},
  "repository": {"owner": {"login": "orga"}, "full_name": "orgb/victim-repo"},
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(S_A, raw_body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"orga"`, loads `Shipit.github(organization: "orga")`, and validates the signature successfully against `S_A` [7](#0-6) .
5. `Shipit::Webhooks.for_event('push')` handlers run `PushHandler`, whose base class resolves `repository_name` from `payload.dig('repository','full_name')` = `"orgb/victim-repo"` [3](#0-2) , enqueuing a `GithubSyncJob` for Org B's stack with the attacker-supplied SHA — despite the attacker never having had access to Org B's webhook secret or repository.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
