### Title
Membership webhook `find_or_create_team!` fails to update `Team#organization` on existing record, letting an attacker's org attach a member to another org's Team - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#repository_owner` falls back to `params.dig('organization','login')` for membership events, so the webhook signature is validated against the attacker's own org's `webhook_secret`. `MembershipHandler#find_or_create_team!` uses `Team.find_or_create_by!(github_id: params.team.id)`, whose block (which sets `team.organization`) only executes on record creation, not on lookup; if a `Team` row with that `github_id` already exists under a different, trusted organization, the attacker's correctly-signed membership webhook calls `team.add_member(member)` on that trusted org's `Team` row without ever correcting/validating its `organization` field.

### Finding Description
The broken binding: `Team.find_by(github_id: X).organization == organization_whose_secret_verified_this_payload` is assumed by the authorization model (`Shipit.github_teams`, `User#authorized?` at [1](#0-0) ) but is not enforced when `github_id` collides across orgs.

Path:
1. `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs before `create`. For a `membership` event, `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [2](#0-1) . Membership events carry no top-level `repository` key, so this resolves to the attacker-controlled `organization.login`.
2. `verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the signature against that org's own configured secret [3](#0-2) . Since the attacker owns "evil-org" and configured it as a tenant, this succeeds trivially with their own secret.
3. `MembershipHandler#process` calls `find_or_create_team!` then, for `action == 'added'`, `team.add_member(member)` [4](#0-3) .
4. `find_or_create_team!` is `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }` [5](#0-4) . Rails' `find_or_create_by!` only yields the block when a new record is created; if a row with `github_id: params.team.id` already exists (e.g., `Team(organization: 'trusted-org', github_id: 42)`), the block never runs, so `organization` is left as `trusted-org` even though the request was signed by, and attributed to, `evil-org`.
5. `member = User.find_or_create_by_login!(params.member.login)` creates/loads the attacker-supplied GitHub login as a `User`, and `team.add_member(member)` attaches it to the `Team` row still labeled `organization: 'trusted-org'`.

Neither `verify_signature`'s success nor the `ExplicitParameters` schema (which only validates types/presence, not cross-org ownership) catches this, because the signature check and the team-lookup key (`github_id`) are on entirely separate trust domains: signature proves "this org sent it," `github_id` is a GitHub-global numeric ID that any org admin can read for any team they belong to, and nothing ties the two together on the FIND branch.

### Impact Explanation
An attacker who controls a configured Shipit tenant org ("evil-org") can attach an arbitrary GitHub user (including themselves) to a `Team` record whose `organization` column still reads a different, trusted org, without ever touching that trusted org's webhook secret. If `Shipit.github_teams` is configured with that trusted `Team`'s id, this is a direct escalation into `Shipit.github_teams` authorization (`User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`), granting the attacker's account authorized/maintainer-equivalent status across the Shipit installation. This matches the High category: "escalation into `Shipit.github_teams` authorization." The attack requires only knowledge of the trusted team's numeric GitHub team ID (discoverable via GitHub's public/API team listing) and control of any GitHub org configured as a Shipit tenant.

### Likelihood Explanation
Preconditions: attacker's own org must be a configured Shipit tenant (has its own `webhook_secret`/GitHub App config) — plausible in multi-tenant Shipit deployments that onboard many orgs. Attacker must also know the victim team's numeric `github_id`, obtainable via GitHub's team API/UI if teams aren't fully private, or by brute-forcing small sequential integers since GitHub team IDs are sequential and often low-value. No Shipit session, API token, or victim secret is needed — only the ability to configure a `membership` webhook on the attacker's own org and control its payload (`team.id`, `organization.login`, `member.login`, `action: 'added'`). This is fully repeatable and requires no live GitHub interaction to reproduce in tests.

### Recommendation
Do not rely on `find_or_create_by!`'s block to set/validate `organization`; instead, look up the `Team` by `github_id` AND verify (or always set/compare) `organization == params.organization.login` before performing any mutation. E.g.:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  if team
    raise SecurityError, "org mismatch" unless team.organization == params.organization.login
    team
  else
    Team.create!(github_id: params.team.id, organization: params.organization.login) do |t|
      t.github_team = params.team
    end
  end
end
```
Additionally, `repository_owner` should not blindly trust `params.dig('organization','login')` for authorizing writes to pre-existing cross-org records — the org identity used for signature verification must be the same one enforced on every subsequent write, not just at creation time.

### Proof of Concept
Minitest plan (no live GitHub, HMAC computed locally):
```ruby
test "membership webhook cannot attach members to a Team owned by a different organization" do
  trusted_team = Shipit::Team.create!(organization: 'trusted-org', github_id: 42, name: 'core', slug: 'core', api_url: 'https://api.github.com/teams/42')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'core', 'slug' => 'core', 'url' => 'https://api.github.com/teams/42' },
    'organization' => { 'login' => 'evil-org' },
    'member' => { 'login' => 'attacker' }
  }.to_json

  # sign with evil-org's own configured secret
  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', Shipit.github(organization: 'evil-org').webhook_secret, payload)

  post '/webhooks', params: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json'
  }

  assert_response :ok
  trusted_team.reload
  assert_equal 'trusted-org', trusted_team.organization  # binding claimed to hold
  assert trusted_team.members.exists?(login: 'attacker') # but attacker was still added
end
```
This demonstrates the equality `Team#organization == signing_org` is violated: the row's `organization` remains `'trusted-org'` (unchanged, as claimed) while the membership mutation was authorized purely by `evil-org`'s secret.
