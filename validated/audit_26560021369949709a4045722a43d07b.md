### Title
Organization/Repository Binding Mismatch in Webhook Signature Verification Allows Cross-Repository Stack Sync via Forged `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a payload's HMAC signature using `repository.owner.login` from the JSON body, while the downstream event handlers resolve the target `Repository`/`Stack` to act on using the independent `repository.full_name` field from the same body. Because these two fields are never checked for consistency, an entity that can produce a validly-signed payload for one configured GitHub organization can point `repository.full_name` at a different organization's repository and have Shipit act on it.

### Finding Description
The signature check picks the secret based on one field: [1](#0-0) [2](#0-1) 

`repository_owner` (`params.dig('repository', 'owner', 'login')`) is used to pick which configured GitHub App (and thus which `webhook_secret`) is used in `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`, per Shipit's documented support for multiple GitHub organizations, each with its own `webhook_secret` [3](#0-2)  and per-org `GitHubApp` instance construction [4](#0-3) .

Once the signature passes, `request.raw_post` is parsed and dispatched to handlers with the full, attacker-suppliable JSON body: [5](#0-4) 

The base `Handler` class, used by `PushHandler`, `CheckSuiteHandler`, etc., resolves the target repository from a *different* JSON field — `repository.full_name` — with no cross-check against the field used for signature routing: [6](#0-5) 

`PushHandler#process` then finds non-archived stacks for that resolved repository/branch and calls `stack.sync_github(expected_head_sha: params.after)`: [7](#0-6) 

`CheckSuiteHandler` similarly acts on stacks resolved via `repository_name` for arbitrary branch/sha values supplied in the payload: [8](#0-7) 

**The broken binding (as an equality that should hold but doesn't):**
`organization_that_authenticated_the_signature (repository.owner.login)` == `organization_that_owns_the_repository_being_acted_upon (repository.full_name)`

Before a hypothetical fix, nothing enforces this equality — the two values are read from independent, fully attacker-controlled JSON keys in the same signed blob, and the signature only proves the blob wasn't tampered with, not that its *content* is internally consistent. In a single-org deployment this is unreachable (there is only one webhook secret and effectively one owner), but in the documented multi-org configuration [9](#0-8) , each organization's GitHub App has its own secret. Since GitHub computes `X-Hub-Signature`/`X-Hub-Signature-256` over the exact raw body that the sending application (or attacker knowing that org's `webhook_secret`) constructs, whoever controls org A's webhook delivery (i.e., an org admin able to configure org A's GitHub App webhook target, or anyone who has obtained org A's `webhook_secret`) can freely author the JSON body, including setting `repository.owner.login = "org-a"` (to pass signature routing) while setting `repository.full_name = "org-b/victim-repo"` (to target a stack that only org B should control).

### Impact Explanation
This crosses a repository-ownership boundary within a single Shipit deployment that manages multiple organizations, matching the "an organization that authenticated versus the repository that is written" trust boundary the review targets. Concretely, an attacker who controls webhook delivery for one tenant organization in a multi-org Shipit instance can force `GithubSyncJob`/stack resyncs (`push`), or check-run refresh scheduling (`check_suite`) against another organization's stacks, and status updates against arbitrary commits (`status` handler matches purely on `sha` across all stacks, with no repository check at all — see `StatusHandler#process` matching `Commit.where(sha: params.sha)` globally). This can influence deployability/status gating and force synchronization behavior for repositories the attacker does not own — a cross-repository write/action performed under another organization's trust context, without ever needing that organization's webhook secret, GitHub access, or a Shipit session/API token.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (a documented, supported configuration) and requires the attacker to control legitimate webhook delivery (or know the `webhook_secret`) for at least one of the configured organizations — a much weaker requirement than compromising the target organization. This is plausible for shared/multi-tenant Shipit installs where different orgs are onboarded with their own GitHub Apps but share one Shipit instance.

### Recommendation
After signature verification, require `repository.full_name`'s owner segment (or `repository.owner.login`) to equal `repository_owner` used for signature routing, rejecting the webhook (422) on mismatch, before dispatching to any handler. Alternatively, derive the routing organization strictly from the same canonical field the handlers use for repository resolution, so a single field governs both secret selection and the repository acted upon.

### Proof of Concept
Given a Shipit instance configured with two GitHub orgs, `org-a` (attacker-controlled webhook secret `secret_a`) and `org-b` (victim, secret unknown to attacker):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(secret_a, body)>

body = {
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },       // used by verify_signature -> selects secret_a
    "full_name": "org-b/victim-repo"     // used by Handler#repository_name -> resolves org-b's stack
  }
}
```

`verify_signature` computes `repository_owner = "org-a"`, fetches `org-a`'s `GitHubApp`, and validates the signature against `secret_a` successfully (since attacker signed with it). Dispatch proceeds; `PushHandler#stacks` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack, despite the request never being authenticated by `org-b`'s webhook secret. [10](#0-9) [6](#0-5) 

**Uncertainty note:** I could not fully verify from the index whether `Repository.from_github_repo_name` performs any additional owner-scoping beyond matching `full_name` (e.g., against the `Repository`'s stored owner), which could partially mitigate this if repositories are strictly registered per-organization ahead of time in the database. The engine index did not surface the full body of `app/models/shipit/repository.rb`'s `from_github_repo_name` implementation, so this should be double-checked in a full checkout before treating this as conclusively exploitable.
