### Title
Bad-debt socialization uses `liq-penalty-max` instead of the dynamically-computed `liq-penalty`, causing premature write-off of recoverable debt onto vault suppliers - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`liquidate()` computes a graduated, position-specific `liq-penalty` (between `liq-penalty-min` and `liq-penalty-max`) that scales with the borrower's LTV, and uses this exact penalty to size the seizure for the *targeted* collateral asset. However, when deciding whether the borrower's *other* (non-targeted) collateral is enough to keep the position solvent — and therefore whether the remaining debt should be written off ("socialized") to vault depositors — the code re-uses the fixed constant `liq-penalty-max` instead of the position's actual `liq-penalty`. This mismatch between the "assumed" liquidation price/penalty and the actual applicable one is structurally the same bug class as the GroupBuy report: state consumed later (bad-debt socialization) assumes a fixed reference value that the earlier, real execution did not actually use.

### Finding Description
In `liquidate` ( [1](#0-0) ), the liquidation penalty applied to the targeted collateral/debt pair is graduated: [2](#0-1) 

For a partial liquidation just above `ltv-liq-partial`, `liq-pct-scaled` is small, so `liq-penalty` is close to `liq-penalty-min`, which can be materially lower than `liq-penalty-max`.

After the targeted collateral is seized, the contract checks whether the borrower's *other* collateral assets are worth enough to keep repaying debt, in order to decide whether to socialize the remaining debt as bad debt: [3](#0-2) 

Both `remaining-debt-to-repay` (for leftover of the *same* collateral asset) and `other-debt-repayable` (for the borrower's *other* collateral assets) are computed using the hardcoded `liq-penalty-max` constant, not the `liq-penalty` actually computed and applied for this liquidation event: [4](#0-3) 

Because `div-bps-down(x, BPS + liq-penalty-max)` produces a *smaller* debt-repayable estimate than the true applicable value computed with the lower `liq-penalty`, a borrower's small-but-nonzero remaining collateral can round down to `other-debt-repayable = u0` purely because of this wrong constant — even though, using the actual (lower) `liq-penalty` that governed this very liquidation, that collateral would still be sufficient to repay some debt. When `other-debt-repayable` hits zero and `coll-removed` is zero, `no-collateral-left` becomes true, triggering `socialize-debt-asset` ( [5](#0-4) ), which calls `vault-socialize-debt`/`socialize-debt-asset` to write off the borrower's remaining scaled debt directly against the vault's assets — a loss borne collectively by that vault's zToken (supplier) holders — while zeroing the debt entry via `debt-remove-scaled` without seizing the borrower's leftover collateral in the other asset.

### Impact Explanation
This is a socialization charged to all suppliers of the affected debt vault triggered by an unprivileged liquidator, harming a distinct victim class (vault lenders/zToken holders) rather than the caller. The borrower keeps residual collateral that was never seized because it was deemed "negligible" only due to the wrong penalty constant, while the corresponding debt is erased from the ledger and the shortfall is absorbed by the vault's liquidity pool (all suppliers). This constitutes theft/permanent loss of supplier funds — debt that was economically recoverable is written off, degrading the zToken exchange rate for every depositor in that vault, and the borrower is left holding value they never had to repay for.

### Likelihood Explanation
This requires a liquidator to trigger a partial liquidation (LTV close to `ltv-liq-partial`, so `liq-penalty` << `liq-penalty-max`) on a borrower holding two collateral assets where the non-targeted asset's USD value is just above the "true" repayable threshold but below the threshold computed with `liq-penalty-max`. This is a narrow but reachable window purely arithmetic in nature (no oracle manipulation or privileged access needed) — any liquidator (even the borrower's own alt account) can construct or wait for such a position and call `liquidate` normally.

### Recommendation
Replace `liq-penalty-max` with the position's dynamically computed `liq-penalty` in both the `remaining-debt-to-repay` calculation and the `other-debt-repayable` calculation, so the bad-debt-socialization eligibility check consistently reflects the same penalty rate actually applied to this liquidation event, preventing recoverable collateral from being ignored and debt from being prematurely socialized onto suppliers.

### Proof of Concept
1. Borrower has collateral in asset A (targeted) and a small amount of collateral in asset B, with debt in asset D. LTV sits just above `ltv-liq-partial`, so `calc-liquidation-params` yields `liq-penalty ≈ liq-penalty-min` (e.g., 2%) while `liq-penalty-max` is e.g. 15%.
2. Liquidator calls `liquidate` targeting collateral A, repaying the max partial debt allowed at `liq-penalty ≈ 2%`, fully draining asset A (`coll-removed = 0`).
3. Asset B's remaining USD value is just large enough that `div-bps-down(coll-B-usd, BPS + liq-penalty-min)` (the correct, lower-penalty calculation) would yield `other-debt-repayable > 0` (i.e., B could still repay some debt in a follow-up liquidation), but `div-bps-down(coll-B-usd, BPS + liq-penalty-max)` (the actual code path) rounds down to `u0`.
4. `no-collateral-left` evaluates true; `socialize-debt-asset` fires, calling `vault-socialize-debt` to erase the borrower's remaining scaled debt against vault D's assets.
5. Result: vault D's suppliers absorb the shortfall while the borrower's asset-B collateral remains in their position, effectively withdrawable later without ever repaying the corresponding debt — a fund transfer from lenders to the borrower/attacker enabled purely by the `liq-penalty-max` vs `liq-penalty` mismatch.
