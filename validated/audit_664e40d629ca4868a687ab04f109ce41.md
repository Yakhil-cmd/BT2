### Title
Webhook signature verification is bound to `repository.owner.login`, but write actions are bound to a different, independently-attacker-controlled field `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (or `organization.login`) inside the **unauthenticated request body**. [1](#0-0) [2](#0-1)  Once the signature check passes, every handler resolves the `Stack`/`Repository` to mutate using a *different* field of the same payload, `repository.full_name`. [3](#0-2)  Nothing enforces that these two fields describe the same repository/organization.

### Finding Description
Shipit supports multiple GitHub Apps, one per organization, each with its own `webhook_secret`, configured under `github.<org_name>.webhook_secret` in `secrets.yml`. [4](#0-3)  `Shipit.github(organization: repository_owner)` looks up the app/secret for whatever organization name is present in the payload, and `verify_webhook_signature` HMACs the raw body with that org's secret. [5](#0-4) [6](#0-5) 

Because an attacker can register/own a GitHub App on any organization they control (or on an org whose secret is otherwise known to them) and have it added to Shipit's multi-org `github` config (a legitimate, low-privilege setup step for onboarding a new org), they know that org's `webhook_secret` and can compute a valid `X-Hub-Signature` for **any payload body they choose**, including one where `repository.owner.login` (or `organization.login`) is set to their own org (so the correct secret is selected and the signature validates), while `repository.full_name` is set to `"victim-org/victim-repo"` — a completely different, already-tracked Shipit stack.

`verify_signature` only checks "was this body signed by *some* org's secret matching the `owner.login` field in the body" — it never checks that the org whose secret validated the signature is the same org that appears in `repository.full_name`, which is the field every handler actually trusts to decide what to mutate:
- `PushHandler#process` uses `stacks` (derived from `repository.full_name`) to call `stack.sync_github(expected_head_sha: params.after)` for the matching branch. [7](#0-6) 
- `StatusHandler#process` updates commit statuses for `params.sha` regardless of which org signed the request. [8](#0-7) 

The equality that should hold but doesn't:
`organization_that_signed_the_payload (repository.owner.login used for secret lookup) == organization_owning_the_repository_being_written (org embedded in repository.full_name used by handlers)`

### Impact Explanation
An attacker who legitimately controls one GitHub App/organization onboarded into Shipit's multi-tenant config can forge webhook events (`push`, `status`, `check_suite`, etc.) that Shipit will accept as authentic for **any other tracked repository/stack**, not just their own. Since `push` events drive `stack.sync_github`, and `status` events directly write CI status records used to gate merges/deploys, this is a cross-repository/cross-organization write achieved without ever compromising the victim org's actual webhook secret — an authentication-bypass class issue enabling cross-repository writes and manipulation of another tenant's deploy-readiness signals.

### Likelihood Explanation
This requires the attacker to control (or know the webhook secret of) at least one organization already configured in Shipit's `github` multi-org secrets — a realistic scenario for any Shipit deployment shared across multiple orgs/teams (the documented "Using Multiple Github Applications" setup). No compromise of the victim's own secret, API token, or session is needed, and the payload fields (`repository.owner.login` vs `repository.full_name`) are trivially independently controllable in a hand-crafted webhook POST.

### Recommendation
In `WebhooksController#verify_signature`, derive the organization used to pick the verification secret from the *same* namespace that handlers use to resolve the target repository (i.e., parse the owner out of `repository.full_name`, or explicitly assert `repository.full_name.split('/').first == repository.owner.login` before trusting the payload). Reject the request if these two values disagree, so a signature computed with org A's secret can never be replayed to affect org B's repositories.

### Proof of Concept
1. Attacker's org `attacker-org` is configured in Shipit (`config/secrets.yml`) with `webhook_secret: S`, a normal onboarding scenario.
2. Attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "victim-org/victim-repo",
       "owner": { "login": "attacker-org" }
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` since they know `S`.
4. POST to `/webhooks` with `X-Github-Event: push`. `repository_owner` resolves to `attacker-org`, `Shipit.github(organization: 'attacker-org')` returns the app configured with secret `S`, and `verify_webhook_signature` succeeds. [5](#0-4) 
5. `Shipit::Webhooks.for_event('push').each { |handler| handler.call(params) }` runs `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name('victim-org/victim-repo')` and triggers `stack.sync_github` for that unrelated stack. [3](#0-2) [7](#0-6)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
