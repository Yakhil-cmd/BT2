### Title
Delimiter injection in arbiter contract hash allows two different contract terms to collide on the same hash - ([File: arbiter_contract.js])

### Summary
The PostgreSQL CVE stems from a value being spliced into a quoted/textual construct without escaping so it can break out of its intended field boundary. `arbiter_contract.js` has an analogous unescaped-boundary bug: `getHashSrc` builds the hash source by joining several attacker/peer-controlled string fields with a fixed delimiter, but never checks that the field values themselves don't already contain that delimiter (or, in the legacy branch, uses no delimiter at all).

### Finding Description
`getHashSrc` concatenates `title`, `text`, `creation_date`, addresses, party names, `amount`, and `asset` using `exports.DELIMITER = "[|#|]"` as the join character: [1](#0-0) 

None of `title`, `text`, `my_party_name`/`peer_party_name` are checked for the presence of the delimiter substring before being joined, and the pre-`NEW_HASH_DATE` legacy branch joins with an empty string, i.e. no delimiter at all: `.join("")` [2](#0-1) . This is the same class of bug as the CVE: a value that is supposed to stay inside one “slot” of a larger textual template can be crafted (by inserting the delimiter sequence, or by shifting characters between adjacent slots) so that the resulting joined string — and therefore its SHA-256 hash — is identical to the hash produced from a different, distinct set of field values (e.g. `title="A", text="B[|#|]C"` colliding with `title="A[|#|]B", text="C"`, or an amount/asset boundary shift in the legacy no-delimiter case).

`getHash()` simply hashes this source string: [3](#0-2) , and this hash is what identifies the contract (`objContract.hash`) throughout the whole exchange: it is stored as the primary key in `wallet_arbiter_contracts`, sent to the peer in `arbiter_contract_offer`, and used by both parties/arbiter to reference "the contract" when accepting, revoking, and later composing the shared payment address [4](#0-3) [5](#0-4) .

### Impact Explanation
Because the hash is the sole identifier binding the human-readable contract terms (title/text/amount/party names) to the on-chain multisig/escrow arrangement, a malicious private-payment counterparty (payer or payee) could construct two field combinations that hash identically. One party could show/sign a version with favorable terms while the actual stored/relayed record (used later for arbitration or for constructing the shared payment address and dispute resolution) reflects different terms — a form of contract-forgery within the private/off-chain agreement layer that ocore explicitly treats as a first-class trust anchor for escrowed payments between an unprivileged private-payment counterparty and its peer. This can result in a party being held to (or paying out under) terms they never actually agreed to, i.e. unauthorized/fraudulent movement of escrowed funds in the arbiter/private-payment flow.

### Likelihood Explanation
Any user of the arbiter-contract wallet feature (an unprivileged private-payment counterparty) fully controls `title`, `text`, and (as one of the two parties) their own `my_party_name` field sent to the other side, so crafting a delimiter-colliding pair of field sets requires no special privilege — only choosing contract text/title strings that contain the literal `[|#|]` sequence (or, for contracts predating `NEW_HASH_DATE`, exploiting the complete absence of a delimiter). This is a straightforward, low-effort manipulation available to any counterparty in a normal contract negotiation.

### Recommendation
Before joining the fields, reject or escape any field value that contains `exports.DELIMITER` (or a reserved control character not permitted in user text), and use a length-prefixed or otherwise unambiguous encoding scheme instead of a fixed-string delimiter (mirroring how `getSourceString` in `string_utils.js` explicitly forbids the `\x00` join character inside string values before concatenation: [6](#0-5) ). Remove or migrate away from the delimiter-less legacy hashing branch.

### Proof of Concept
1. Party A proposes contract 1: `title = "Deal"`, `text = "pay 100[|#|]extra clause"`.
2. Party A proposes contract 2 (different intent): `title = "Deal[|#|]pay 100"`, `text = "extra clause"`.
3. Both produce the identical joined source string `"Deal[|#|]pay 100[|#|]extra clause[|#|]..."` once the remaining fixed fields (`creation_date`, addresses, `amount`, `asset`) are equal, so `getHash()` returns the same value for both, even though the human-readable `title`/`text` split differs. A peer verifying "the hash of the contract I was shown" cannot distinguish which text/title split was actually agreed, enabling substitution of contract terms without detection through the hash check.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
