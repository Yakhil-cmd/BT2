### Title
Non-governing council member bypasses single-mode vote restriction pre-Permissionless fork, enabling unauthorized `reward.mintingamount` governance ratification — (`kaiax/gov/headergov/impl/header.go`)

### Summary
In single governance mode, `VerifyVote` only enforces the governing-node-only restriction **after** the Permissionless fork is enabled. Before that fork, any council member who proposes a block can embed a governance vote for any parameter — including `reward.mintingamount` — and have it accepted and ratified at the next epoch block.

### Finding Description
`VerifyVote` contains three checks before accepting a vote:

1. Voter is in council [1](#0-0) 
2. Voter is the block proposer [2](#0-1) 
3. Single-mode governing-node check — **only when `IsPermissionlessForkEnabled` is true** [3](#0-2) 

The comment on line 101 explicitly documents the conditional scope: *"In single mode, only the governing node can write header.Vote **after Permissionless**."* When `PermissionlessCompatibleBlock == nil`, check 3 is entirely absent. A council member who is not the governing node satisfies checks 1 and 2 whenever they are the IBFT proposer, and `checkConsistency` for `RewardMintingAmount` returns `nil` unconditionally: [4](#0-3) 

The accepted vote is stored via `HandleVote` → `AddVote` and then ratified at the next epoch block through `getExpectedGovernance` → `VerifyGov`, which only checks that the epoch-block `Governance` field matches the locally derived tally of accepted votes — it does not re-validate voter authority. [5](#0-4) 

### Impact Explanation
If `reward.mintingamount` is set to `MAX_UINT64` (or any attacker-chosen value), every subsequent block mints that amount of KAIA to the block reward pool. This is an unauthorized, persistent change to the KAIA issuance rate, directly satisfying the "unauthorized mint" impact gate. `reward.ratio` manipulation similarly redirects reward distribution without authority.

### Likelihood Explanation
The attacker must be a council member (validator) on a chain running single-mode governance without the Permissionless fork. In IBFT, every council member is eventually selected as proposer in round-robin order — no collusion or key compromise is required. The attacker simply waits for their proposer slot and crafts a header with the desired `Vote` field. This is a single-actor exploit.

### Recommendation
Remove the `IsPermissionlessForkEnabled` gate from the single-mode check, or add an equivalent pre-Permissionless guard. The governing-node restriction in single mode should be enforced unconditionally regardless of fork state:

```go
// Apply single-mode restriction regardless of fork.
params := h.GetParamSet(blockNum)
if params.GovernanceMode == "single" && vote.Voter() != params.GoverningNode {
    return ErrVotePermissionDenied
}
```

func (h *headerGovModule) PostInsertBlock(b *types.Block) error {
	if len(b.Header().Vote) > 0 {
		var vb headergov.VoteBytes = b.Header().Vote
		vote, err := vb.ToVoteData()
		if err != nil {
			logger.Error("ToVoteData error", "vote", vb, "err", err)
			return err
		}
		err = h.HandleVote(b.NumberU64(), vote)
		if err != nil {
			logger.Error("HandleVote error", "vote", vb, "err", err)
			return err
		}
	}

	if len(b.Header().Governance) > 0 {
		var gb headergov.GovBytes = b.Header().Governance
		gov, err := gb.ToGovData()
		if err != nil {
			logger.Error("DeserializeHeaderGov error", "governance", gb, "err", err)
			return err
		}
		err = h.HandleGov(b.NumberU64(), gov)
		if err != nil {
			logger.Error("HandleGov error", "governance", gb, "err", err)
			return err
		}
	}

	return nil
}
