### Title
CCMenu API Controller Bypasses Api­Client Stack Scoping — Cross‑Stack Data Disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack‑resolution helper inherited from `Shipit::Api::BaseController` in a way that discards the scoping enforced by `ApiClient#stack_id`. This breaks the binding "a stack a token authorises versus a stack it touches": a token that is only supposed to be authorized for one stack can be used to read the status of any stack on the instance.

### Finding Description
`Shipit::Api::BaseController` defines the standard, scope‑respecting resolution of the target stack: [1](#0-0) 

`stacks` is restricted to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a specific stack, and `stack` is derived from that restricted collection. This is the mechanism by which a stack‑scoped `ApiClient` token (e.g. one created with `stack: shipit` as in the `here_come_the_walrus` fixture) is prevented from touching any stack other than the one it was minted for: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving directly against the full `Stack` table instead of the scoped `stacks` collection: [3](#0-2) 

The controller still relies on `require_permission :read, :stack`, which only checks that the string permission `"read:stack"` is present in `ApiClient#permissions` — it never checks whether the requested `stack_id` matches `current_api_client.stack_id`: [4](#0-3) 

This is the same class of defect as the report's oracle bug: two related quantities that are supposed to be tied together (the stack the token *authorizes* vs. the stack the endpoint *acts on*) are computed independently, and the code silently treats them as equivalent. Here, "authorized stack" (`current_api_client.stack_id`) and "accessed stack" (`params[:stack_id]` resolved without scoping) are never reconciled in `CCMenuController`, even though they are reconciled everywhere else in the API (`BaseController#stack`).

### Impact Explanation
Any holder of a valid `ApiClient` authentication token with `read:stack` permission — even one deliberately minted and scoped to a single stack (this is exactly the purpose of the "CCMenu Client" created by `CCMenuUrlController`, and of any manually scoped `ApiClient`) — can query `GET /api/stacks/:stack_id/ccmenu.xml` for an arbitrary `stack_id` belonging to a different, unrelated stack/repository, and receive that stack's build/deploy status, lock state, and latest deploy metadata: [5](#0-4) 

This is an unauthorized read of stack state via a token that was never authorized for that stack, matching the "High — unauthenticated/unauthorized read of stack state" impact bucket (the token is authenticated, but not authorized for the target stack, i.e., an authorization‑scope bypass).

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` in its `permissions` list — no elevated privilege, no GitHub credentials, and no session are needed, only a token that a legitimate integration (e.g., a CI dashboard using the CCMenu feature) already holds. Since CCMenu tokens are explicitly designed to be embedded in third‑party tooling and shared outside the main Shipit UI (see `CCMenuUrlController#fetch`, which emits the token in a URL query string), the likelihood of such a token existing and being exposed to a lower‑trust context is high.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` collection (as `BaseController` does), e.g. `stacks.from_param!(params[:stack_id])`, so a stack‑scoped `ApiClient` cannot resolve any stack outside of `current_api_client.stack_id`.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id = A` with permission `read:stack` (e.g. via `CCMenuUrlController#fetch` for stack A, or an admin‑created scoped client as in the `here_come_the_walrus` fixture).
2. Using that client's `authentication_token` as HTTP Basic auth, call `GET /api/stacks/B/ccmenu.xml`, where `B` is a different stack the token was never authorized for.
3. `Shipit::Api::CCMenuController#stack` resolves `Stack.from_param!(params[:stack_id])` directly against all stacks, ignoring `current_api_client.stack_id`, so the request succeeds and returns stack `B`'s CI/deploy status: [6](#0-5) 
   In contrast, the same token used against `GET /api/stacks/B` (handled by `BaseController#stack`/`#stacks`) is correctly rejected/empty because that path enforces `current_api_client.stack_id` scoping.
