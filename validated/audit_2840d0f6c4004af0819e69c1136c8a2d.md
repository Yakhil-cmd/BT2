### Title
`recalculate_stake_rewards` re-derives the reward set from the *current* `StakesCache` instead of an epoch-boundary snapshot, letting an attacker's own `Withdraw` mid-distribution silently drop their reward from a recalculating node's partitions while a non-recalculating node still burns and tallies it — causing `EpochRewards` sysvar (`distributed_rewards`) and bank-hash divergence - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`recalculate_stake_rewards` (used by `recalculate_partitioned_rewards_if_active`, invoked on fork switch/restart) rebuilds `stake_delegations` from `self.stakes_cache.stakes()` at the moment of recalculation, not from a fixed epoch-boundary snapshot. If an attacker fully withdraws their own stake account between the original calculation and the recalculation point, their stake account disappears from the current `StakesCache`, so a recalculating node's rebuilt `PartitionedStakeRewards` simply omits that pubkey entirely, whereas a node that never recalculates keeps the original entry and later burns it (still tallying the amount into the `EpochRewards` sysvar's `distributed_rewards`) when `store_stake_accounts_in_partition` fails to find the account. This produces different `EpochRewards` sysvar contents (and thus different account hashes / bank hashes) between the two code paths for the same logical epoch state.

### Finding Description
`recalculate_stake_rewards` at [1](#0-0)  takes `stake_delegations` from `self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes)`, which in turn calls `stakes.stake_delegations_vec()` on `self.stakes_cache.stakes()` — i.e. the bank's *live, current* stake delegation map at [2](#0-1) . `StakesCache` only tracks accounts whose deserialized `StakeStateV2` still has an active `Delegation` (`delegation().is_some()`); a fully-withdrawn/closed stake account is removed from that map. So if the attacker submits `Withdraw` on their own stake account (fully draining it after warmup/cooldown allows it, or any account no longer holding a valid stake) between the original per-epoch reward calculation and a later `recalculate_partitioned_rewards_if_active` call (triggered by `Bank::new_from_parent`/restart/fork-switch), that pubkey is simply absent from the recalculated `stake_delegations`, and thus absent from the recalculated `PartitionedStakeRewards` and its `hash_rewards_into_partitions` output.

Compare this with a node that never recalculates: its original stake_rewards (computed before the withdrawal) still contains the attacker's entry. When distribution reaches that partition, `store_stake_accounts_in_partition` → `build_updated_stake_reward` looks up the stake account in the *current* `stakes_cache_accounts` at [3](#0-2) ; since the account is gone, it returns `Err(DistributionError::AccountNotFound)`, and the reward is explicitly burned: `stake_reward_lamports_burned += stake_reward_amount;` at [4](#0-3) . That burned amount is still folded into the sysvar bookkeeping via `self.update_epoch_rewards_sysvar(stake_reward_lamports_minted + stake_reward_lamports_burned, ...)` at [5](#0-4) , i.e. `distributed_rewards` in the `EpochRewards` sysvar advances to include it.

On the recalculating node, the withdrawn pubkey's entry never exists in `partition_rewards.all_stake_rewards` at all, so it is never iterated, never burned, and never counted into `distributed_rewards`. The two nodes therefore end up with divergent `EpochRewards` sysvar account contents (`distributed_rewards` field) at the same slot, which is hashed into account state and thus into the bank hash — a consensus-relevant divergence purely from an unprivileged user's own `Withdraw` instruction timed around a fork/restart-triggered recalculation.

No existing guard prevents this: `recalculate_stake_rewards` documents only that "recalculated rewards for not-yet-distributed partitions must exactly equal originally calculated values" (verified by `test_recalculate_stake_rewards`/`test_recalculate_partitioned_rewards`), but those tests never mutate/withdraw a stake account between calculation and recalculation — they only advance blocks. The comment at [6](#0-5)  assumes "stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned" — but a plain `Withdraw` (fully closing the account) is exactly a legitimate state mutation the stake program allows and is not accounted for by the recalculation snapshot logic.

### Impact Explanation
This is a cross-node bank-state/bank-hash divergence bug caused entirely by an unprivileged user's own account operations (`Withdraw` on their own stake account) interacting with the fork-switch/restart recalculation path (`recalculate_partitioned_rewards_if_active`). Nodes that recalculate rewards mid-distribution vs. nodes that use the originally-calculated (cached) partition list will end up with different `EpochRewards` sysvar `distributed_rewards` values and potentially different total processed-reward bookkeeping for the same epoch, which is a consensus-critical divergence (matches the "cross-node state divergence" / potential "epoch-boundary halt" bounty category, since duplicate-vote/fork detection or bank-hash mismatches during epoch-reward distribution are especially disruptive).

### Likelihood Explanation
The precondition is simple and fully attacker-controlled: own a delegated stake account included in the current epoch's reward set, and issue `Withdraw` for it once cooldown/deactivation permits (or immediately if already deactivated/rent-exempt threshold allows full withdrawal) during the multi-block reward-distribution window, timed so that some validators experience a fork switch or restart (triggering `recalculate_partitioned_rewards_if_active`) after the withdrawal but before the distribution instruction has processed that partition, while other validators process the same partition without recalculating. Fork switches and restarts are routine cluster events, so this is readily reachable without needing validator/leader privileges — it merely requires favorable timing relative to naturally occurring forks, making it moderately likely and fully repeatable in a controlled test environment (deterministic given a scripted fork/restart).

### Recommendation
`recalculate_stake_rewards` should not rebuild the stake-delegation set from the bank's live `StakesCache`. Instead, recalculation should be restricted to accounts already present in the previously-calculated `PartitionedStakeRewards`/reward set (i.e., recompute only reward *amounts* for pubkeys known to be part of the current epoch's original reward set, treating any pubkey whose account has since disappeared or lost its delegation the same way distribution treats it — as a burn candidate that is still tallied consistently) rather than silently omitting them from the recalculated vector. Alternatively, persist the epoch-boundary stake-delegation snapshot needed for recalculation (already partially implied by "assume reward commissions have already been calculated and delivered") so `get_epoch_params_for_recalculation` cannot diverge in membership from the original set, and add an invariant test that intentionally withdraws/closes a stake account mid-distribution and asserts that `distributed_rewards` and burn totals match between a recalculating and non-recalculating path.
