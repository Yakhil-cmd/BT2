### Title
Membership webhook trusts `github_id` alone to locate a `Team`, letting a colliding id from any signed org add members into `Shipit.github_teams` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` solely by `github_id` (`Team.find_or_create_by!(github_id: params.team.id)`), ignoring `params.organization.login` whenever a row with that `github_id` already exists. Since `Shipit.github_teams` are `Team` rows keyed by real, sequential GitHub team ids, a validly-signed `membership` webhook from an unrelated org whose newly created team happens to reuse that same id will match the existing privileged `Team` record and `Team#add_member` will insert the attacker's `Membership` into it.

### Finding Description
The broken binding: the code assumes `team.github_id == team.organization`'s namespace is unique, i.e. it treats `github_id` as sufficient proof that `params.organization.login` is authorized to mutate that `Team`. In reality `github_id` is a global, sequential integer allocated by GitHub across all orgs, not scoped per-organization, so `github_id == X` does **not** imply `organization == Y` for the `Team` that already owns id `X`.

Code path: [1](#0-0) 

`find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }`. The block that sets `organization` only executes on **create**; if a `Team` with that `github_id` already exists (e.g. a Team seeded into `Shipit.github_teams` via `Shipit.github_teams` / `Team.find_or_create_by_handle`), `find_or_create_by!` returns the existing record unchanged and the `organization` assignment in the block never runs — the organization check is entirely absent for pre-existing rows. [2](#0-1) 

`Team#add_member` then unconditionally appends the `User` derived from `params.member.login` into `members` — no re-verification that the requesting `organization` matches `team.organization`. [3](#0-2) 

`Shipit.github_teams` membership is precisely what `User#authorized?` checks (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`), so once a `Membership` row exists on that `Team`, the (attacker-controlled) member becomes an authorized Shipit user.

Attacker flow: attacker owns org `evil-org` with a configured (real) webhook secret for their own GitHub App/org integration. They repeatedly create/delete teams in `evil-org` to cause GitHub to allocate sequential team ids until one collides with a `github_id` already present in the `teams` table for a `Shipit.github_teams` entry (these ids are discoverable/brute-forceable since they're small sequential integers, and could also be leaked via other Shipit-visible data). They then trigger a real `membership`/`added` webhook (add a real member, or themselves) for that team, correctly signed by `evil-org`'s own `webhook_secret`. The handler verifies the HMAC (which is entirely valid, since it's `evil-org`'s own secret and their own event), then executes `find_or_create_team!`, matches the existing privileged `Team` by `github_id`, and `add_member` inserts the row.

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only prove the payload came from the org whose secret was used — they say nothing about which `Team` record the payload is entitled to modify. `ExplicitParameters` schema in the handler validates types/presence, not organizational ownership. There is no `require_permission!` or org-equality check anywhere in `find_or_create_team!` or `add_member`.

### Impact Explanation
This is a High-severity escalation into `Shipit.github_teams` authorization: an attacker who fully controls a legitimate, signed webhook-emitting org can grant an arbitrary GitHub login (their own account or an accomplice's) membership in a `Team` that backs Shipit's `authorized?` gate, without ever touching Shipit secrets or GitHub App credentials belonging to the target org. This is repeatable per colliding id and, once achieved, unlocks whatever privileged actions in Shipit are gated on `authorized?`/team membership (e.g. deploy/rollback access, depending on how the host app wires `github_teams` restrictions), constituting cross-tenant privilege escalation via a legitimately signed request.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub org with a configured Shipit `GithubHook`/webhook integration (something an ordinary GitHub org owner can set up on any repo/org they administer, per the threat model's "attacker-controlled org has a valid webhook_secret" assumption) and the ability to create/delete teams in that org to search for an id collision with a `Shipit.github_teams`-configured team's `github_id`. Since GitHub team ids are small sequential integers and the target teams are typically old and low-numbered, brute forcing is plausible with moderate effort; no Shipit secret, session, or API token is required at any point. This makes the attack feasible for any org owner who can attach webhooks, matching the described attacker profile.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that the resolved `Team`'s `organization` matches `params.organization.login` before proceeding, e.g. `Team.find_by(github_id: params.team.id)` and raise/drop the event if `team.organization != params.organization.login`; only create a new `Team` when none exists for that `github_id`, and otherwise treat an organization mismatch as an unhandled/invalid event rather than silently reusing the existing row.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
