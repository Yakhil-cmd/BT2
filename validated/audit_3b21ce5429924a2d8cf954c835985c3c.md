### Title
Improper Authorization: `wallet.js` "sign" request handler allows any paired correspondent device to request a signature for an address without verifying it is an actual cosigner - ([File: wallet.js])

### Summary
The GHSA advisory describes `aedes` failing to enforce its own authorization rules when a client sets a `Last Will` — an action is executed on behalf of a client without re-validating that the client is actually permitted to trigger it. The analogous class in `ocore` is: a device-message handler performs a privileged, deferred action (asking the local wallet to produce a cryptographic signature for a shared/multisig address) while explicitly skipping the check that the requesting device is really a cosigner of that address, because that check has been commented out.

### Finding Description
`handleMessageFromHub`'s `"sign"` case in `wallet.js` processes requests from any known correspondent device to sign a unit for a given `address`/`signing_path`. After validating message shape, it calls `findAddress(body.address, body.signing_path, …)`. When the address resolves to a *local* key (`ifLocal`), the code that would confirm the requester is actually an authorized cosigner is explicitly disabled: [1](#0-0)

By contrast, the sibling `ifRemote` branch of the same handler *does* enforce that the sender is a recognized cosigner (`if (!other_device_addresses.includes(from_address)) return callbacks.ifError("you are not listed as a cosigner for this address "+body.address)`), showing the intended authorization policy exists but was deliberately (and only partially) disabled for the local-key path.

Because any correspondent device is treated the same as a trusted hub message once the outer signature/decryption checks pass (`device.js` `handleJustsaying` "hub/message"), and `handleMessageFromHub`/`findAddress` do not re-verify wallet/shared-address membership before dispatching a `signing_request` event, an attacker who is merely a *paired correspondent* (not necessarily a member of the shared/multisig address in question) can send a forged `"sign"` message for any `address`/`signing_path` that the victim's device happens to control locally, and the device will proceed to raise a `signing_request` (or, for `signed_message` requests, directly emit a signing request) without confirming the sender's authorization for that specific address. [3](#0-2) 

### Impact Explanation
If the resulting `signing_request` is auto-approved by any automated/headless component (or approved by a user who is not shown enough context to detect the discrepancy — the same "bypasses ACL" outcome as the aedes bug, where an action normally gated by authorization is executed based on unchecked attacker-supplied input), an attacker-controlled unit could obtain a valid signature from a device that never should have authorized spending from that particular shared address/signing path. This can enable unauthorized spending or corruption of a multisig transaction (fund loss for the shared-address's real owners), since the code path that should assert "sender is a cosigner of this address" is commented out only for the `ifLocal` branch while still present for `ifRemote`.

### Likelihood Explanation
The message reaches this code once basic hub-message signature/decryption checks pass and the correspondent is a known device (or the message subject is on the small allow-list for non-correspondents) — i.e., it is directly reachable from any paired device or bot without needing any special privilege on the target address. The remaining friction is the UI confirmation dialog (`signing_request` event) which a human/GUI wallet would normally show; the severity therefore depends on downstream consumers of the `signing_request`/`signed_message` events (e.g., headless wallets) that may not independently re-verify cosigner membership before signing.

### Recommendation
Restore and generalize the authorization check for the `ifLocal` branch of the `"sign"` handler in `wallet.js`: before emitting `signing_request` (or auto-signing), verify that `from_address` is actually listed as a cosigner for `body.address` at `body.signing_path` (e.g., via `wallet_signing_paths`/`shared_address_signing_paths`/`extended_pubkeys`), mirroring the check already performed in the `ifRemote` branch. Consuming applications that auto-approve `signing_request` should also independently validate cosigner membership rather than trusting the emitted event.

### Proof of Concept
1. Attacker device pairs with victim device as an ordinary correspondent (standard pairing flow; no special trust required).
2. Victim device locally holds a signing key that is part of some shared/multisig address `A` at path `r.0` (e.g., because it is a member of many shared addresses over time).
3. Attacker sends a `"sign"` device message: `{address: A, signing_path: "r.0", unsigned_unit: <attacker-crafted payment spending from A to attacker's address>}`.
4. `handleMessageFromHub` → `findAddress(A, "r.0", …)` resolves to `ifLocal` (the key lives on the victim's device).
5. Because the cosigner-membership check is commented out at [4](#0-3) , `callbacks.ifOk()` fires and a `signing_request` event is emitted for the attacker-supplied unit, without any verification that the attacker's device is actually one of the legitimate cosigners of `A`. Any downstream consumer that trusts this event flow can be tricked into producing a valid signature share for a transaction the attacker was never authorized to request.
