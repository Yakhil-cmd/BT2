The commented-out `bIndirectCorrespondent` restriction in `wallet.js` looks like a strong analog to the CSRF gap — a security check that exists in the code but is disabled, letting indirect correspondents send message subjects they shouldn't be trusted with. Let me examine the full switch statement and how indirect correspondents get established.### Title
Disabled trust check lets indirect (non-paired) correspondent devices send arbitrary wallet-protocol messages - (File: wallet.js)

### Summary
`wallet.js`'s `handleMessageFromHub()` processes every device-message `subject` from a hub-relayed sender through one unified `switch(subject)`. The function receives a `bIndirectCorrespondent` flag from `device.js` that distinguishes a directly-paired device from an "indirect" correspondent (a device that was only added because it appeared as a cosigner in someone else's multi-sig/shared-address definition, via `device.addIndirectCorrespondents`). The code contains an explicit, but commented-out, trust boundary check:

```js
//if (bIndirectCorrespondent && ["cancel_new_wallet", "my_xpubkey", "new_wallet_address"].indexOf(subject) === -1)
//    return callbacks.ifError("you're indirect correspondent, cannot trust "+subject+" from you");
``` [1](#0-0) 

Exactly like the `netmount` command that was left out of elFinder's CSRF allowlist while all other mutating commands were protected, this check exists in the codebase — signalling that the developers intended to restrict indirect correspondents to only a narrow whitelist of subjects — but it is dead code and never enforced. As a result, an indirect correspondent is treated with the same trust as a fully paired device for every subject in the switch, including state-changing ones such as `sign`, `private_payments`, `new_shared_address`, `create_new_wallet`, `prosaic_contract_offer`/`arbiter_contract_offer`, etc.

### Finding Description
`handleMessageFromHub` is invoked from `device.js`'s `handleJustsaying` (`hub/message` case) once the outer message envelope's signature and hash are verified. It emits `handle_message_from_hub` with the sender's `bIndirectCorrespondent` flag taken from `correspondent_devices.is_indirect` [2](#0-1) . `is_indirect` correspondents are added automatically and without an explicit pairing ceremony by `device.addIndirectCorrespondents`, called whenever a user learns about the *other* cosigners of a shared/multisig address they participate in [3](#0-2) . This is intentionally a weaker trust tier than devices added via `handlePairingMessage`, which requires a shared `pairing_secret` [4](#0-3) .

The dispatcher `handleMessageFromHub` was clearly meant to gate this weaker trust tier down to a small allow-list of benign, wallet-bootstrapping subjects (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`), mirroring the mitigation pattern in the external report (allow-listing sensitive commands and rejecting everything else for a less-trusted caller). That gate is commented out [1](#0-0) , so any indirect correspondent can additionally reach:
- `sign` — requests the local wallet to co-sign a unit for a shared address, with the sender-is-cosigner check itself also explicitly disabled in the same handler ("the commented check would make multilateral signing impossible") [5](#0-4) .
- `private_payments` — feeds arbitrary private-payment chains into `handlePrivatePaymentChains` [6](#0-5) .
- `new_shared_address`, `create_new_shared_address`, `approve_new_shared_address` — manipulate the victim's view of shared-address definitions and cosigner sets [7](#0-6) .
- `arbiter_contract_offer`/`prosaic_contract_offer` and related contract-state subjects, which write into `arbiter_contract`/`prosaic_contract` stores and drive UI dialogs [8](#0-7) .

Because indirect correspondence is created merely by being *named as a cosigner* in a shared-address definition supplied to `walletDefinedByAddresses.validateAddressDefinitionTemplate`/`handleNewSharedAddress`, an attacker device that manages to get itself listed once as a "cosigner" (e.g. a party the victim briefly transacted with in a multi-sig arrangement, or a device address referenced in a shared-address template the victim's software resolves) becomes indefinitely capable of sending all of these message types to the victim's wallet — well beyond the "bootstrapping-only" scope the disabled check was designed to enforce.

### Impact Explanation
This is analogous to the elFinder CSRF gap: a security check that protects most state-changing operations for a restricted-trust actor is present in source but not wired in, so the restricted-trust actor (indirect/non-directly-paired correspondent) gets full access to sensitive wallet/contract/private-payment message handling. Concretely this can let an indirect correspondent:
- Trigger unauthorized co-signing flows (`sign`) against the victim's addresses (mitigated only by a UI confirmation dialog for local addresses, but with `ifRemote` proxying to another cosigner without further authorization beyond the disabled check).
- Inject or manipulate private-payment chain data (`private_payments`) and shared-address/contract state that the wallet subsequently trusts as coming from a legitimate multisig peer.
- Impersonate a "wallet_fully_approved"/`create_new_wallet` flow tier beyond what was designed for indirect correspondents.

This falls within the "wallet and contract message handling" and "private payment chains" categories in scope, and represents a real trust-boundary violation reachable by a private-payment/multisig counterparty (an "indirect correspondent") without any additional authentication beyond having once been listed as a cosigner.

### Likelihood Explanation
Reaching `bIndirectCorrespondent = true` only requires being added via `addIndirectCorrespondents`, which happens automatically whenever the victim's wallet learns of cosigners of a shared address it is part of [3](#0-2) ; no explicit pairing secret exchange or user confirmation of the correspondent's trustworthiness is required. The disabled check is the *only* barrier that existed to limit such automatically-trusted peers, and it is entirely inert, so likelihood of reachability is high for anyone who is (or claims to be) a cosigner in any shared-address arrangement the victim participates in.

### Recommendation
- Re-enable and generalize the indirect-correspondent allow-list check at the top of `doHandle()` in `wallet.js`, restricting `bIndirectCorrespondent` senders to only the subjects that are strictly necessary for multisig bootstrapping (e.g. `cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`, and any cosigner-scoped operations that already independently verify cosigner membership from the DB, such as `sign`'s `ifRemote` cosigner check).
- Restore/implement the commented-out `sender is cosigner of this address` check in the `sign`/`ifLocal` path, or replace it with a DB-backed verification tied to the specific shared address, rather than relying on the coarse `is_indirect` correspondent flag.
- Add regression tests asserting that an indirect correspondent's `private_payments`, `new_shared_address`, `arbiter_contract_offer`, and similar subjects are rejected unless the sender is verified against the specific address/contract's cosigner list.

### Proof of Concept
Conceptual sequence (cannot be executed without live nodes/hub, but derivable directly from the code paths cited):
1. Victim wallet W is a cosigner of a shared address whose definition references attacker device D as another cosigner (e.g., learned via `new_shared_address` / `validateAddressDefinitionTemplate`), causing `device.addIndirectCorrespondents` to insert D into `correspondent_devices` with `is_indirect=1` [3](#0-2) .
2. D sends W a `hub/message` with `json.subject = "private_payments"` (or `"sign"`, `"new_shared_address"`, etc.) through the hub. `device.js` verifies only the outer envelope signature/hash and that D is a known correspondent, then dispatches to `handleMessageFromHub` with `bIndirectCorrespondent=true` [9](#0-8) .
3. Because the allow-list check is commented out [1](#0-0) , execution falls straight into the corresponding `case` in the switch (e.g. `handlePrivatePaymentChains` for `private_payments`) exactly as if D were a fully-paired, directly trusted device [6](#0-5) .

Note: I was unable to fully trace `handlePrivatePaymentChains` and `walletDefinedByAddresses.validateAddressDefinitionTemplate` in this session due to iteration limits, so the exact downstream exploitation depth (e.g., whether `handlePrivatePaymentChains` itself independently re-validates sender trust) is not fully confirmed and would need to be checked in a follow-up before treating this as fully proven end-to-end.

function handlePairingMessage(json, device_pubkey, callbacks){

	var from_address = objectHash.getDeviceAddress(device_pubkey);
	if (!ValidationUtils.isNonemptyString(body.pairing_secret))
		return callbacks.ifError("correspondent not known and no pairing secret");

		return callbacks.ifError("no device_hub when pairing");
	if (json.device_hub.length > 200)
		return callbacks.ifError("device_hub too long");
	if (!network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub))

			[correspondent.device_address, correspondent.hub, correspondent.name, correspondent.pubkey],
			function(){
				cb();
			}
		);
	}, onDone);
}
