### Title
Webhook signature verification is bound to the wrong organization, allowing cross-repository writes and CI-status forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) used to verify `X-Hub-Signature` by reading `repository.owner.login` (or `organization.login`) out of the *unverified* JSON body, then hands that same unverified body to the event handlers, which act on a completely different, independently-controlled field (`repository.full_name`, or in `StatusHandler`'s case, no repository scoping at all). The signature only proves "this request was signed with organization X's webhook secret"; it proves nothing about which repository the handler subsequently writes to.

### Finding Description
`verify_signature` picks the verifying `GitHubApp` from the payload itself: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

In a multi-org Shipit deployment (explicitly supported, see `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), each organization key has its own independent `webhook_secret`. `repository_owner` is read straight from the attacker-supplied JSON body, so an attacker who is a legitimate participant in *one* organization (e.g. they created/installed the Shipit GitHub App for their own org "AttackerOrg", or that org's `webhook_secret` is unset/blank so `verify_webhook_signature` short-circuits to `true` when `webhook_secret` is blank — see `lib/shipit/github_app.rb` `verify_webhook_signature`) can produce a validly-signed webhook for "AttackerOrg" while filling every other field of the payload arbitrarily.

The `create` action then dispatches the *entire unverified* payload to handlers: [2](#0-1) 

Handlers determine which repository/stacks to mutate from `payload.dig('repository', 'full_name')`: [3](#0-2) 

This is a different key than the one used for signature-organization selection (`repository.owner.login`), and the code never checks that they refer to the same organization. `PushHandler` and `CheckSuiteHandler` use this to resolve `stacks` and trigger `stack.sync_github` / `schedule_refresh_check_runs!` on whatever repository `full_name` names: [4](#0-3) [5](#0-4) 

Worse, `StatusHandler` doesn't even key off `repository` at all — it matches on commit SHA globally across the entire installation: [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

Since `Commit.where(sha: ...)` is not scoped to any repository/organization, an attacker who can produce a validly-signed webhook for *any* organization configured in the instance can inject/forge a GitHub commit-status (e.g., mark any known commit SHA belonging to an unrelated victim organization's stack as `success`) purely by knowing that one organization's webhook secret — which is exactly the equality the audit's "invariant" concept maps to: `organization that authenticated ≠ repository/commit that is written`.

### Impact Explanation
CI status (`ci.require` in `shipit.yml`) is used by Shipit to gate deploys — a forged "success" status on a commit can be used to make an otherwise CI-failing or unreviewed commit deployable, which maps to "an unauthorized deploy" in the accepted impact list. `PushHandler`/`CheckSuiteHandler` cross-repository writes (triggering GitHub sync / check-run refresh jobs against a repository the caller does not control) map to "cross-repository writes." Both are in the accepted High/Critical impact set. The root cause is the same class of bug as the report: a value acted upon (`repository.full_name` / commit SHA globally) is never covered by the same trust boundary as the value used to establish authenticity (`repository.owner.login` used to pick the verifying secret).

### Likelihood Explanation
This requires only unprivileged control of the webhook secret for *one* organization in a multi-org Shipit deployment (a legitimate but low-trust tenant, or an org whose `webhook_secret` was left blank, which `verify_webhook_signature` explicitly treats as always-verified — `return true unless webhook_secret`). No GitHub App private key, `api_clients_secret`, session, or repository write access is needed; only the ability to send an HTTP POST to `/webhooks` with a body they fully control. This is realistic in any Shipit instance onboarding multiple organizations/tenants, which the documentation explicitly supports.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the signature, cross-check that the organization used to select the verifying `GitHubApp` matches the organization implied by `repository.full_name` (or reject payloads where they differ).
- In `Handler#stacks`/`repository_name`, prefer the same field used for signature verification (`repository.owner.login`) and reject events whose `repository.full_name` owner doesn't match it.
- Fix `StatusHandler#process` to scope `Commit.where(sha: params.sha)` by the repository/organization that was actually verified (e.g., join through `Stack -> Repository` and filter by `repository.owner == verified_organization`), rather than matching SHAs globally.
- Stop treating a blank/unset `webhook_secret` as "verification always succeeds" (`lib/shipit/github_app.rb#verify_webhook_signature`); require an explicit opt-out instead of a silent bypass.

### Proof of Concept
Preconditions: multi-org Shipit instance with `AttackerOrg` (attacker knows/controls its `webhook_secret`, or it is unset) and `VictimOrg/victim-repo` (a real Shipit stack, unrelated org).

1. Attacker computes `signature = HMAC-SHA1(AttackerOrg_webhook_secret, body)` (or sends any signature if `AttackerOrg`'s secret is blank).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "AttackerOrg/whatever" },
  "sha": "<known commit sha belonging to VictimOrg/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "created_at": "2026-09-01T00:00:00Z"
}
```
3. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and verifies successfully using `AttackerOrg`'s secret.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of the organization used for verification — and calls `create_status_from_github!`, injecting a forged CI status onto the victim's commit, which can satisfy `ci.require` and enable an unauthorized deploy of that commit on `VictimOrg`'s stack.

Equivalently, sending `X-Github-Event: push` with `repository.owner.login = AttackerOrg` but `repository.full_name = VictimOrg/victim-repo` causes `PushHandler` to trigger `sync_github` against the victim stack, an unauthorized cross-repository write triggered under another organization's verified signature.
