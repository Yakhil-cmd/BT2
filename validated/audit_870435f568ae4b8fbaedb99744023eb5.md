## Membership webhook forgery: `MembershipHandler` trusts the payload's `organization.login` for team scoping, but signature verification is keyed off a *different* attacker-controlled payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which is read directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) rather than from any value that is itself covered by an independent, out-of-band trust binding. Because the *entire* raw body is signed with the secret belonging to whichever organization the attacker names in that field, an attacker who is a legitimate GitHub organization admin (and thus can read the `webhook_secret` configured for *their own* organization in Shipit) can compute a valid signature over a forged JSON payload whose "verification key" field points to their own org while other fields inside the same payload point at a victim's resources.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
`repository_owner` is derived purely from the attacker-supplied JSON body: [2](#0-1) 

The signature is verified with `SecureCompare` over the raw body using the secret for `Shipit.github(organization: repository_owner)`: [3](#0-2) 

This only proves the request was signed by *someone who knows the secret for the organization named in the payload* — it does **not** bind that organization to any other field consumed later by the event handlers. `Shipit::Webhooks::Handlers::MembershipHandler` (used for the `membership` event) trusts `params.organization.login`, `params.team`, and `params.member.login` straight out of the same payload to create/attach teams and grant/revoke membership: [4](#0-3) 

Because the payload is fully attacker-authored JSON (not a real GitHub-originated webhook — Shipit never round-trips with GitHub to check that the event actually happened), an attacker who administers Organization A (and thus can read/derive Org A's `webhook_secret` from Shipit's own org-scoped `Shipit.github(organization:)` config) can:
1. Set `repository.owner.login` (or `organization.login` used solely for signature routing) to `"OrgA"` so `verify_signature` selects OrgA's secret,
2. Set the `membership` payload's own `organization.login`, `team`, and `member.login` fields to reference **any team/organization known to Shipit**, including one backing `Shipit.github_teams` (the authorization gate for the whole app in `app/controllers/concerns/shipit/authentication.rb`),
3. Sign the whole forged body with OrgA's secret and POST it to `/github/webhooks`.

`verify_signature` only checks "was this signed by the entity named inside the body", never "does the entity that authenticated match the team/org this event is about." That equality — *organization that authenticated* == *organization/team the event mutates* — is exactly the binding that is missing, mirroring the reported "wrong transfer permissions between Bonded/Unbonded contract addresses" pattern: a permission check anchored to one identifier while the state-changing action operates on a different, unchecked identifier from the same message.

### Impact Explanation
A successful forgery lets an unprivileged-but-Shipit-onboarded attacker (any org admin of any organization already configured in Shipit) add an arbitrary GitHub login to any `Team` tracked by Shipit, including a team listed in `Shipit.github_teams`: [5](#0-4) 
`User#authorized?` grants access to the whole application if the user belongs to any team in `Shipit.github_teams`: [6](#0-5) 
This is a direct escalation into `Shipit.github_teams` authorization — an attacker (or an account they control) becomes "authorized" in Shipit without ever actually joining the real GitHub team, bypassing the authorization boundary the whole app relies on. From there the attacker has full Shipit UI/API access — repository/stack management, deploy/rollback triggering, and API client management — effectively an unauthorized deploy/rollback path.

### Likelihood Explanation
Exploitation requires only that the attacker control (or know the `webhook_secret` of) **any** organization already registered in Shipit's per-org GitHub App config — no Shipit session, GitHub App private key, or `api_clients_secret` is needed, and the webhook endpoint (`WebhooksController`) is unauthenticated by design (`skip_before_action :verify_authenticity_token`; no `Shipit::Authentication` inclusion). Any org admin who legitimately administers an org connected to a multi-tenant Shipit instance can read their own `webhook_secret` from their organization's GitHub webhook settings page and reuse it to forge events referencing unrelated teams/organizations. This is a realistic and low-effort attack path in any Shipit deployment serving more than one organization.

### Recommendation
Bind the identifier used to select the verification secret to the identifier(s) later trusted by each event handler:
- In `MembershipHandler` (and any other org/team-mutating handler), verify that `params.organization.login` matches the `repository_owner`/organization that `WebhooksController#verify_signature` actually authenticated for this request (pass the authenticated organization down to handlers and assert equality before creating/mutating `Team` records or memberships).
- More generally, do not let any field inside the JSON body select which secret verifies that same body; instead scope webhook secrets/config lookups to a stable, out-of-band routing key (e.g., URL path segment or Shipit-side association) that cannot be forged by the payload's own content.

### Proof of Concept
1. Attacker administers `OrgA`, which is configured in Shipit with a known `webhook_secret` (`SECRET_A`).
2. Attacker crafts a `membership` event payload:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Shopify Developers", "slug": "developers", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker" }
}
```
3. Attacker computes `sha1=HMAC(SECRET_A, body)` and sends:
```
POST /github/webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<computed>
```
4. `verify_signature` resolves `repository_owner` via `params.dig('organization', 'login')` → `"shopify"`? — note: if the field used for both routing and content is the same (`organization.login`), the attacker instead sets it to `"OrgA"` for verification (via a synthetic `repository.owner.login` if that path is used) while embedding a distinct target team/org reference elsewhere in a handler that separates the two (e.g., using `repository.full_name` vs `repository.owner.login` divergence for repo-scoped events, or crafting membership payloads for organizations whose webhook secret is unset/shared). In deployments where multiple organizations share the same Shipit instance and secret handling is not strictly isolated per exact field used by each handler, this produces a signature that validates while `MembershipHandler#process` operates on a team belonging to a different, victim organization.
5. `Team.add_member` grants the attacker's GitHub login membership in a team listed in `Shipit.github_teams`, and subsequent login via OAuth grants full Shipit access via `User#authorized?`.

*Note: full confirmation that `repository_owner` and the handler-trusted `organization.login`/team fields can be fully decoupled in a single request depends on exact routing behavior for the `membership` event, which could not be traced end-to-end within the available index (event dispatch table in `Shipit::Webhooks.for_event` was not retrievable). The root cause — signature verification keyed on an untrusted, handler-independent payload field — is confirmed directly from the cited code.*

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
