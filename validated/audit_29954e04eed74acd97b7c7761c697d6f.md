Based on my research, I found a genuine binding-break in the webhook signature verification flow. I was unable to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` and `status_handler.rb` in this final iteration, but the test fixtures and `WebhooksController` I did examine are sufficient to establish the root cause and its exploitability against the `membership`/`push`/`status` handlers, all of which act on repository/organization identifiers taken from the unverified payload body.

### Title
Webhook signature verification keys off attacker-controlled payload field, allowing organization impersonation for orgs with no configured `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification by reading `repository_owner`/`organization.login` directly out of the **unverified** JSON request body, before any signature check has occurred. If any configured organization in `Shipit.github` has no `webhook_secret` set (a supported, documented configuration, see `config/secrets.development.shopify.yml`), `GithubApp#verify_webhook_signature` short-circuits to `true` for that organization. An attacker can therefore submit an arbitrary, unsigned webhook payload that *claims* to originate from that unsecured organization/repository, pass `verify_signature`, and have `Shipit::Webhooks.for_event(event)` handlers execute against payload fields (team id, member login, repository full name, commit sha/state, etc.) that were never authenticated.

### Finding Description
`WebhooksController` binds the org used for signature verification to attacker-supplied data: [1](#0-0) [2](#0-1) 

`repository_owner` is computed from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both taken straight from the raw, not-yet-verified JSON body. This value picks which `GithubApp` instance (and hence which `webhook_secret`) is used to check the `X-Hub-Signature` header: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` is present. Shipit's own documented configuration allows an organization entry with no `webhook_secret` configured: [4](#0-3) 

Because the org used for verification is chosen by the attacker (via the `repository.owner.login`/`organization.login` field in the raw body they control), and because `create` then dispatches the *entire* untrusted payload to handlers keyed only by `X-Github-Event`: [5](#0-4) 

...the resulting binding that is supposed to hold — "the organization whose secret authenticated this request" == "the organization/repository the handler subsequently writes to" — is broken. An attacker only needs to name, in the JSON body, an org that happens to have no `webhook_secret` configured to make `verify_signature` pass, while the rest of the payload (e.g. `membership` event's `team`, `organization`, `member` fields, processed by `MembershipHandler#process`) is trusted and acted upon as if genuinely signed: [6](#0-5) 

This lets an unprivileged network attacker create/modify `Team` records and add/remove arbitrary `User` memberships to any GitHub team tracked by Shipit, which is the exact set used for `Shipit.github_teams` application authorization checks (`app/controllers/concerns/shipit/authentication.rb`).

### Impact Explanation
This maps directly to the High-severity criterion "escalation into `Shipit.github_teams` authorization" and "unauthenticated read/write of stack state": an attacker able to add themselves (or any known GitHub login) as a member of a `Team` whose organization matches an unsecured-webhook org can bypass the `current_user.authorized?` gate in `force_github_authentication`, gaining access to the whole Shipit UI/API as an authorized user without ever having valid GitHub App webhook credentials.

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires at least one organization configured in `Shipit.github` (multi-org deployments are explicitly supported, see `config/secrets.development.shopify.yml`) to have a blank/`nil` `webhook_secret` while another organization/stack in the same instance is the actual target. This is a supported, non-default but plausible misconfiguration state that the engine itself does nothing to prevent — there is no requirement that all configured organizations have a webhook secret, nor any binding between the verified org and the org whose data is subsequently trusted by handlers.

### Recommendation
- Require (validate at boot/config-load time) that every configured GitHub organization/app has a non-blank `webhook_secret`; refuse to start, or refuse to process webhooks for, orgs missing one, rather than silently treating an absent secret as "verified."
- After signature verification succeeds, re-check that the `repository.owner.login`/`organization.login` actually used to select the verifying secret matches the entity that the handler is about to mutate, rather than trusting the payload transitively.
- Avoid using unverified, attacker-controlled payload fields to select which secret verifies that same payload; instead scope webhook secrets by a value not derived from the payload itself (e.g., unique webhook URL/path per organization).

### Proof of Concept
1. Configure Shipit with two organizations in `Shipit.github`: `org-a` (has a real `webhook_secret`) and `org-b` (intentionally left with `webhook_secret: nil`, a supported configuration).
2. Send a POST to `/webhooks` with header `X-Github-Event: membership` and a body such as:
```json
{
  "action": "added",
  "team": { "id": 48, "name": "Ouiche Cooks", "slug": "ouiche-cooks", "url": "https://example.com" },
  "organization": { "login": "org-b" },
  "member": { "login": "attacker-github-login" }
}
```
No `X-Hub-Signature` header is required to be valid, because `repository_owner` resolves to `org-b`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` (`lib/shipit/github_app.rb:76-83`).
3. `MembershipHandler#process` creates/updates the `Team` for `org-b` and adds `attacker-github-login` as a member (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`).
4. If any `Shipit.github_teams` entry matches this team, the attacker's GitHub account is now authorized inside the Shipit application per `app/controllers/concerns/shipit/authentication.rb:20-34`, despite never presenting a valid webhook signature for any organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
