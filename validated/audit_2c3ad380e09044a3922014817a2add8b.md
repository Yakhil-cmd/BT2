### Title
Unallowlisted route hops can steal arbitrary wallet tokens through the signed caller authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The router-facing strategy paths allow attacker-selected pool contracts to execute beneath a user's signed authorization. A malicious hop can invoke `token.transfer(victim, attacker, amount)` for a token unrelated to the lending position. Soroban records that transfer as a child of the victim's authorization entry, so a wallet or frontend that signs the simulated authorization tree without rejecting the unexpected child authorizes the theft. This is the on-chain analogue of credentialed wildcard CORS: an attacker-selected origin/venue can use authority attached to the victim's request to take assets outside the intended action.

### Finding Description
`swap_collateral` is callable for an account by its owner or delegate and passes the route bytes into `swap_tokens`. [1](#0-0)  `swap_collateral` first requires the caller's authorization and verifies that the account belongs to the caller or an active delegate. [2](#0-1) 

`swap_tokens` then calls the configured router with the user-controlled `swap` payload. [3](#0-2)  The controller only scopes its own grant: it authorizes one exact `token_in.transfer(controller, router, amount_in)`, measures that the router did not overspend, and requires positive measured output. [4](#0-3)  Those checks protect the routed lending collateral, but they do not prevent a route-selected pool from requesting a separate `victim -> attacker` token transfer below the same caller authorization.

The project threat model confirms the reachable shape: pool and token addresses are payload-controlled, there is no pool allowlist, third-party code can execute below the caller's authorization, and an unauthorized-wallet transfer executes if the caller signs the authorization tree containing it. [5](#0-4)  The production venue adapters call the pool supplied by the route—for example, Phoenix invokes `hop.pool.swap(...)`. [6](#0-5) 

### Impact Explanation
A successful attack steals arbitrary token balances from the victim's wallet, not merely the collateral submitted to the strategy. The malicious pool can also return enough output for the strategy's measured-output and final-risk checks to pass, making the poisoned route appear economically valid while it steals an unrelated token through the authorization tree.

The affected entrypoints include at least `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, all of which accept route bytes and use the controller's router path. Direct `execute_strategy` users have the same exposure when they sign a transaction whose simulated authorization tree includes an unexpected child transfer.

### Likelihood Explanation
Exploitation requires a victim to sign an authorization tree containing the malicious child transfer. That is realistic when a wallet or frontend presents only the top-level swap and does not require the authorization tree to contain no unexpected children. The attacker does not need protocol privileges, a compromised key, an oracle manipulation, or control of governance; they only need to supply or induce use of a malicious route.

### Recommendation
Treat route-selected contracts as untrusted and constrain the authority boundary rather than relying on clients to inspect authorization trees:

- Maintain a governance-approved venue/pool registry and reject hops naming unregistered pools.
- If arbitrary venues must remain supported, isolate route execution behind a delegate contract whose authorization cannot be joined to the user's auth tree.
- Require a canonical signed route policy that explicitly binds expected pool/token/action semantics and fails closed if simulation produces additional authorization children.
- For controller strategies, reject any route whose execution requires a caller child authorization other than the exact intended lending operation.
- Update wallet/SDK verification to reject an authorization tree containing any child outside the expected token transfer set.

### Proof of Concept
1. Alice owns a healthy lending account with 10,000 USDC collateral and also holds an unrelated `WALLET_TOKEN`.
2. Attacker deploys `RoguePool`. Its `swap` implementation performs:
   ```rust
   token::Client::new(&env, &wallet_token)
       .transfer(&alice, &attacker, &alice_wallet_balance);
   ```
3. Attacker constructs a `swap_collateral` route naming `RoguePool` as a hop while arranging a positive output token receipt.
4. Simulation records the rogue `WALLET_TOKEN.transfer(alice, attacker, balance)` as a child authorization under Alice's `swap_collateral` invocation.
5. A frontend that signs the simulated tree without rejecting that child submits the transaction.
6. The transaction executes: Alice's unrelated wallet token is transferred to the attacker, while the route can still satisfy positive output and final account-risk checks.
7. The repository's auth-tree regression test demonstrates this exact distinction: an honest root-only tree rejects the rogue transfer, while the poisoned simulated tree authorizes it and moves the victim's wallet balance. [7](#0-6)
