## Finding confirmed

The vulnerability is real and reachable through the described path.

### Title
Hookify `extract_frontmatter` naive `'---'` string-split silently downgrades `action: block` rules to `warn` - (File: plugins/hookify/core/config_loader.py)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` locates the frontmatter boundaries with `content.split('---', 2)`, which splits on the first two literal occurrences of the substring `"---"` anywhere in the file, not on lines that are exactly a `---` delimiter. If a frontmatter value (e.g. `pattern`) contains a `"---"` substring before the real closing delimiter, the split truncates parsing early, and any keys written after that point in the file — including `action: block` — end up dumped into the unparsed message body instead of the frontmatter dict. `Rule.from_dict` then falls back to the default `action='warn'` (line 81), so a rule that visibly reads `action: block` in the `.claude/hookify.*.local.md` file is actually enforced as a non-blocking warning.

### Finding Description
- `extract_frontmatter` splits the file naively: [1](#0-0) 
- This is line/position-agnostic — any `"---"` substring inside a quoted or unquoted frontmatter value (e.g. `pattern: "a---b rm -rf"`) is consumed as the "closing" delimiter, so everything after it (including a later `action: block` line) is pushed into `parts[2]`, the message body, and never becomes part of the returned `frontmatter` dict.
- `Rule.from_dict` builds the `action` field with a `warn` default when the key is absent from the (now-incomplete) frontmatter dict: [2](#0-1) 
- `RuleEngine.evaluate_rules` branches purely on `rule.action == 'block'` to decide whether to emit a `permissionDecision: deny` (or `decision: block` for Stop events) versus a non-blocking `systemMessage`: [3](#0-2) 
- All hook executors (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) call `load_rules()` → `load_rule_file()` → `extract_frontmatter()` automatically on every relevant tool invocation, with no independent validation that the parsed `Rule` matches the visible file content: [4](#0-3) [5](#0-4) 
- `load_rule_file` and `load_rules` swallow parsing anomalies silently (only genuine exceptions are logged); a mis-split frontmatter is not an exception, so no warning is printed and the downgrade is completely invisible to the user, who still sees `action: block` when opening the file. [6](#0-5) 

Because rule files live under `.claude/hookify.*.local.md` in the repository itself, any content that ends up in a rule's `pattern` (or another frontmatter field) can carry this triple-dash decoy — whether the file is committed directly to a cloned repo, or generated by the `/hookify` command flow from attacker-influenced input text.

### Impact Explanation
This breaks the stated invariant that a deny/`block` rule must never be parsed into a non-blocking configuration. A rule author (or a defender reviewing `/hookify list` output or the raw `.local.md` file) believes a dangerous Bash command or file edit will be blocked (`permissionDecision: deny` / Stop `decision: block`), but the actual enforced behavior is only a `systemMessage` warning that does not prevent the tool call. This is a silent security-control bypass/downgrade of blocking, review, or permission enforcement — exactly the "Security-control bypass that silently disables or routes around blocking" impact category.

### Likelihood Explanation
- No privilege beyond normal repository content is required — this is an ordinary parsing bug in string handling, triggered purely by file content.
- Any `.claude/hookify.*.local.md` file with a `"---"` substring anywhere in a frontmatter value positioned before the intended closing delimiter reproduces the issue deterministically.
- All hookify hook scripts invoke `load_rules()` unconditionally on every matching tool call, so the miscomputed `Rule.action` is used every time, not just once.
- Detection is hard because the raw file content (what a human/reviewer sees) does not match the runtime-parsed `Rule` object, and no error/warning is emitted by `load_rule_file`.

### Recommendation
Replace the substring-based `content.split('---', 2)` with a delimiter parser that only recognizes `---` when it appears alone on its own line (e.g., using `re.split(r'(?m)^---\s*$', content, maxsplit=2)` or splitting on `content.splitlines()` and matching lines that are exactly `---`). Additionally, consider using a real YAML parser (`yaml.safe_load`) for the frontmatter block instead of the hand-rolled line parser, and add a startup/self-check that logs a warning when the parsed frontmatter dict does not account for all top-level `key:` lines present in the raw frontmatter text, to catch future desync between visible file content and parsed `Rule`.

### Proof of Concept
Unit test to add to `plugins/hookify/core/config_loader.py` tests (or a new test file):

```python
from plugins.hookify.core.config_loader import extract_frontmatter, Rule

def test_block_rule_not_downgraded_by_dash_in_pattern():
    content = '''---
name: block-dangerous-rm
enabled: true
event: bash
pattern: "start---end rm -rf"
action: block
---

This command is dangerous and must be blocked.
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Visible file clearly states action: block, but parser silently
    # downgrades it to warn because '---' inside pattern value is
    # mistaken for the closing delimiter.
    assert rule.action == 'block', (
        f"Expected 'block' action to survive parsing, got {rule.action!r}. "
        f"Parsed frontmatter: {frontmatter}"
    )
```

Expected current (buggy) behavior: `rule.action == 'warn'` because `action: block` is swallowed into the message body, demonstrating the downgrade. Integration-level validation: drop the same file as `.claude/hookify.block-rm.local.md` in a cloned repo, invoke `pretooluse.py`/`posttooluse.py` with a `Bash` tool call matching `rm -rf`, and assert the hook response contains a plain `systemMessage` (warn) instead of `hookSpecificOutput.permissionDecision == "deny"` (block), confirming the dangerous command is not actually blocked despite the file's visible `action: block`.

```python
def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None
    except UnicodeDecodeError as e:
        print(f"Error: Invalid encoding in {file_path}: {e}", file=sys.stderr)
        return None
    except Exception as e:
        print(f"Error: Unexpected error parsing {file_path} ({type(e).__name__}): {e}", file=sys.stderr)
        return None
```
