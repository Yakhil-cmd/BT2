### Title
Unstable-AA data-feed lookups skip the `sequence === 'good'` filter, letting a losing/non-serial data-feed message satisfy `in_data_feed[]` conditions - ([File: data_feeds.js])

### Summary
`dataFeeds.dataFeedExists()`, the function backing the `in_data_feed[[...]]` oscript primitive and the `in data feed` address-definition operator when reached during AA-formula evaluation, scans `storage.assocUnstableMessages` for a matching data-feed message from a trusted oracle when `bAA` is true. Unlike `readDataFeedValue()` (used by `data_feed[[...]]`), which explicitly filters candidate units with `if (objUnit.sequence !== 'good') continue;`, `dataFeedExists()`'s AA fast-path performs no such check.

### Finding Description
In `data_feeds.js`, `readDataFeedValue()` filters unstable candidate units by sequence before considering their `data_feed` message as valid evidence: [1](#0-0) 

By contrast, `dataFeedExists()`'s equivalent unstable-AA loop has no `sequence` check at all — it only checks `objUnit.bAA`, MCI range, and that the author address is one of the requested oracle addresses before matching the feed value: [2](#0-1) 

`sequence` (`good`/`final-bad`/`temp-bad`) marks whether a unit is treated as a valid, non-conflicting member of the DAG for balance/state purposes; non-`good` sequence units are excluded everywhere else specifically because their payloads (including any `data_feed` message) must not be treated as authoritative. `in_data_feed[[...]]` and `in data feed` reach this code path directly from AA-formula evaluation (`formula/evaluation.js`, case `'in_data_feed'`) and from `definition.js`'s `'in data feed'` authentifier evaluation: [3](#0-2) [4](#0-3) 

Because `dataFeedExists()` is exactly the function invoked for these primitives (`dataFeeds.dataFeedExists(arrAddresses, feed_name, relation, value, min_mci, mci, bAA, cb)`), any AA condition written as `in_data_feed[[oracles=..., feed_name=..., feed_value ...]]` can be satisfied by a data-feed message contained in an unstable unit whose `sequence` is not `good` (e.g., a unit that lost a double-spend race or is otherwise non-serial), as long as that unit is itself an AA-authored unit (`objUnit.bAA`) from one of the whitelisted oracle addresses and its `latest_included_mc_index` falls in the allowed range.

### Impact Explanation
An AA that gates fund release/state transitions on `in_data_feed[[...]]` (a very common oscript idiom for reacting to price/oracle events, e.g. "release funds if price crossed X") can be tricked into evaluating the condition as true based on a data-feed message from a unit that will never actually become the canonical/stable state (because it's not `sequence='good'`). This is the class of bug the Synthetix report highlights — a value that should not have counted as an authoritative oracle reading is nonetheless used to authorize a fund-moving decision — except here the trigger is an internal consensus-sequencing inconsistency rather than a compromised external oracle. The practical effect is a boolean condition inside an AA formula returning `true` (or `false`) inconsistently with what the eventual stable DAG state contains, which can cause **AA fund loss/incorrect release or freezing**, and, more importantly, **causes different nodes to potentially disagree on the AA's response** if they observe different unstable states at evaluation time (a stability/consensus-safety concern), since AA trigger evaluation must be deterministic across all nodes once the trigger unit is stable.

### Likelihood Explanation
The condition requires the oracle to itself be an AA (`objUnit.bAA` must be true — the loop only inspects AA-authored units), and requires a specific race where that AA-oracle unit ends up with non-`good` sequence while still being reachable in `storage.assocUnstableMessages` at the moment `in_data_feed[[...]]` is evaluated for another AA's trigger. This is a narrower precondition than a generic user oracle, but AA-to-AA oracle chaining is an explicitly supported and documented pattern in ocore (AAs reading data feeds posted by other AAs), so it is reachable by an ordinary AA author designing an oracle-consuming AA, without any special privilege. Given the discrepancy with the parallel, more careful `readDataFeedValue()` implementation, this looks like an overlooked check rather than an intentional design choice.

### Recommendation
Add the same `if (objUnit.sequence !== 'good') continue;` guard to the unstable-AA loop in `dataFeedExists()` (`data_feeds.js`, inside the `for (var unit in storage.assocUnstableMessages)` loop, mirroring the check already present in `readDataFeedValue()`), so that `in_data_feed[[...]]` and the `in data feed` operator only ever consider messages from units that are on the "good" (non-conflicting) sequence when used from AA formulas.

### Proof of Concept
1. Deploy AA `Oracle` that, in some response, posts a `data_feed` message `{price: 100}`.
2. Deploy AA `Consumer` whose formula includes `in_data_feed[[oracles="ORACLE_ADDRESS", feed_name="price", feed_value>90]]` gating a payout.
3. Construct two conflicting triggers to `Oracle` (double-spend on the same output) such that one of the resulting `Oracle` response units posts `data_feed {price: 100}` but ultimately receives `sequence='temp-bad'`/`final-bad'` once the conflict resolves.
4. While that losing unit is still present in `storage.assocUnstableMessages` (before stabilization discards it), trigger `Consumer` so that `in_data_feed[[...]]` is evaluated; because `dataFeedExists()` does not filter by `sequence`, the condition returns `true` and `Consumer` releases funds based on a `price` value that is not present in the eventually-stable DAG.

Note: I was not able to fully trace how long a non-`good`-sequence unit remains resident in `storage.assocUnstableMessages` relative to when dependent AA triggers get evaluated (this depends on `main_chain.js`/stability-advance timing not fully inspected here), so the exact timing window for exploitability should be confirmed with a live trace/test rather than assumed.
