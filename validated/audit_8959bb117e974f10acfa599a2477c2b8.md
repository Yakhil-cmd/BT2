### Title
Webhook signature verification binds to `repository.owner.login`/`organization.login` while all downstream repository state changes act on the unrelated, unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or `organization.login`), but every webhook `Handler` resolves the target `Stack`/`Repository` to mutate using a completely different, independently-attacker-controlled field: `payload.dig('repository', 'full_name')`. Because the signature is only proof that *some* organization the attacker legitimately controls signed the payload - not that the signed payload's `repository.owner.login` matches its `repository.full_name` - a party who administers their own (unrelated) GitHub App/organization integrated with the same Shipit instance can forge a payload whose `owner.login` names their own org (so verification succeeds using a secret they know) while `repository.full_name` names a victim tenant's repository, causing Shipit to act on the victim's `Stack`.

### Finding Description
Verification path: [1](#0-0) [2](#0-1) 

`repository_owner` is derived purely from unauthenticated JSON body content (`repository.owner.login`), and is used only to pick *which* organization's `webhook_secret` to validate the HMAC against via `Shipit.github(organization: repository_owner)` / `verify_webhook_signature`.

Once verification passes, `create` dispatches the full, attacker-supplied `params` to handlers: [3](#0-2) 

Every handler resolves the affected `Stack` using an entirely different payload field, `repository.full_name`, never consulted during signature verification: [4](#0-3) 

For example, the push handler acts on whatever stacks match that resolved repository/branch, using attacker-controlled `ref`/`after`: [5](#0-4) 

This is structurally identical to the Y2K `Carousel.sol` bug class: the field checked (`repository_owner`, analogous to `ownerToRollOverQueueIndex` pointing at the wrong/last index) diverges from the field actually written/acted upon (`repository.full_name`, analogous to the `_id`/queue slot that gets mutated). The binding "organization that authenticated == repository that is written" is broken: verification only proves the request was signed by *an* organization Shipit trusts, not that it was signed by the owner of the specific `full_name` repository being modified.

### Impact Explanation
Any party who is a legitimate (but unprivileged w.r.t. other tenants) administrator of one GitHub App/organization onboarded to a shared, multi-tenant Shipit instance can, using only their own known `webhook_secret`, craft POSTs to `/webhooks` that pass `verify_signature` yet drive handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`, PR handlers, etc.) against a victim organization's `Stack`/`Repository` records by simply setting `repository.full_name` to the victim's repo while keeping `repository.owner.login`/`organization.login` equal to their own org. This produces attacker-controlled cross-repository writes (forcing syncs, injecting `after`/`ref` values that get resolved via `stack.sync_github`, mutating check/status/PR/membership state) on repositories the attacker has no GitHub-side access to - a cross-tenant authorization bypass rooted in the same "verified field != acted-upon field" defect described in the report.

### Likelihood Explanation
This is exploitable by any unprivileged external actor with control of one GitHub App installation registered with the shared Shipit instance (i.e., someone who is a legitimate Shipit tenant but not privileged on the target repository) - no `ApiClient` token, no `api_clients_secret`, no GitHub App private key, and no repository write access on the victim repo are required. The only requirement is that the deployment mounts multiple organizations/tenants behind one webhook endpoint with distinct per-organization webhook secrets, which is exactly what `repository_owner`/`Shipit.github(organization:)` is designed to support.

### Recommendation
Bind verification and dispatch to the same field: after selecting the organization's secret and verifying the HMAC, additionally assert that `repository.full_name`'s owner segment (or `organization.login`) matches `repository_owner`/`organization.login`, or resolve the target `Repository`/`Stack` using the same verified owner rather than the independently attacker-controlled `full_name` string. Reject the webhook if the two disagree.

### Proof of Concept
1. Shipit is configured with two tenants: `victim-org` (webhook secret `S_v`, has repo `victim-org/app` tracked as a `Stack`) and `attacker-org` (webhook secret `S_a`, controlled by the attacker, who legitimately manages their own installation).
2. Attacker builds a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefattackerchosen",
  "repository": {
    "full_name": "victim-org/app",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S_a, raw_body)` since they know `S_a`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, loads `Shipit.github(organization: "attacker-org")`, and the HMAC check passes.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` method resolves via `payload.dig('repository','full_name')` = `"victim-org/app"`, matching the victim's real `Stack`, and calls `stack.sync_github(expected_head_sha: "deadbeefattackerchosen")` - a state-changing action on a repository the attacker never had signature authority over.
