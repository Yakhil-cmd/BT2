### Title
Offline `is_valid_signed_package` verification always trusts an address's original (possibly revoked) definition instead of its current one - ([File: signed_message.js])

### Summary
Dolomite lost $1.8M because its old, superseded contract retained trusted authorization to move user funds even though the protocol had moved on to a newer implementation — a stale-authorization/old-trust-root bug. ocore has a structurally identical bug class in `signed_message.js`: an "offline" signed package (one without a `last_ball_unit`) is verified only against the definition that hashes to the target address itself, i.e. the address's *original* key set. Any subsequent `address_definition_change` (key rotation, e.g. after a leak) that supersedes the original definition is silently ignored on this code path, so a forged/offline signed package created with the old, revoked key is still accepted as valid for that address.

### Finding Description
`validateSignedMessage()` in `signed_message.js` supports two verification modes depending on whether the signed package includes `last_ball_unit`:

- **Network-aware path** (`bNetworkAware = true`, package has `last_ball_unit`): the code looks up the *current* on-chain definition of the address at the corresponding `last_ball_mci` via `storage.readDefinitionByAddress`, correctly reflecting any `address_definition_change`. [1](#0-0) 

- **Offline path** (`bNetworkAware = false`, no `last_ball_unit`): the code takes whatever `definition` the caller embedded in the package and only checks that its hash equals the target address: [2](#0-1) 

Because `objectHash.getChash160(objAuthor.definition) !== objAuthor.address` is the *only* validity check performed in this branch, the embedded definition must be the address's very first ("initial") definition — the one whose chash equals the address itself. Any legitimate key rotation via `address_definition_change` produces a new definition whose chash differs from the address, so the *current* definition can never be supplied through this offline path; conversely, the *original* definition (and therefore the original private key) will always pass, no matter how long ago it was superseded. There is no query against `address_definition_changes` / `unit_authors` to confirm the embedded definition is still active.

The comment at line 250 makes the intent explicit but does not fix the underlying trust issue: `// no last_ball_unit of its own; before the fix, always behave as before (-1) to keep old units re-evaluating the same way`. [2](#0-1) 

This function is the verification backbone of the `is_valid_signed_package()` oscript/AA formula, which AA authors use exactly like Dolomite's collateral-authorization checks — to gate fund movement on a counterparty's signature: [3](#0-2) 

When the evaluated `signedPackage` omits `last_ball_unit` (a value fully controlled by whoever crafts the trigger's `data` payload), the AA falls straight into the offline path with no freshness check against on-chain state, and the returned `last_ball_mci` is simply set equal to `mci` after `pemCurvesFixMci` so the caller-side freshness check (`last_ball_mci > mci`) always passes trivially: [4](#0-3) 

Real AA templates rely on `is_valid_signed_package` to authorize counterparty-initiated state changes involving fund transfers, e.g. payment-channel closure signed by a peer: [5](#0-4) 

### Impact Explanation
If an address owner rotates their signing key (via `address_definition_change`, e.g. because the old key leaked or was compromised — the standard remediation) and that address is used as a counterparty identity inside an AA that trusts `is_valid_signed_package`, an attacker who still holds the old, revoked key can forge an offline (no `last_ball_unit`) signed package. The AA will accept it as a valid signature "by" that address, because `validateSignedMessage` never consults the address's current on-chain definition on this path. Depending on the AA logic (e.g., payment-channel close, order fills, off-chain-signed order books), this can let the attacker authorize spending or state transitions on behalf of the victim after the victim believed the compromised key had been revoked — a direct AA fund-loss / unauthorized-spending scenario, matching the "old, superseded authorization is still trusted" root cause of the Dolomite incident.

### Likelihood Explanation
Exploitability requires: (1) an address that has performed at least one `address_definition_change` (a normal, encouraged security practice after a key leak), (2) an AA design that authorizes actions using `is_valid_signed_package(pkg, address)` against that address, and (3) an attacker in possession of the original (now-revoked) private key material. Given that key rotation is the recommended mitigation after any key compromise, and `is_valid_signed_package` is a documented, publicly-usable oscript primitive intended precisely for peer-authorized off-chain messages (payment channels, order books), this is realistically reachable by any unprivileged AA trigger sender who has obtained a previously-valid but now-revoked private key for the counterparty address.

### Recommendation
In the offline (`!bNetworkAware`) branch of `validateSignedMessage`, do not accept the embedded definition solely because it hashes to the address. Instead, query whether that definition (or definition_chash) is still the address's *currently active* one (i.e., no subsequent stable `address_definition_change` exists for that address), or require offline packages to also carry a `last_ball_unit`/mci reference so the current definition can be verified the same way as the network-aware path. At minimum, reject offline packages for addresses that have any recorded `address_definition_change`, forcing them to use the network-aware path.

### Proof of Concept
1. Address `A` is created with definition `D0 = ["sig", {pubkey: P0}]` (so `chash160(D0) == A`).
2. `A` posts an on-chain `address_definition_change` to `D1 = ["sig", {pubkey: P1}]`, revoking `P0` after suspecting `P0` leaked. This is stable and confirmed.
3. An AA (e.g. modeled on `test/samples/payment_channels.oscript`) is programmed to trust counterparty messages via `is_valid_signed_package(trigger.data.sentByPeer, A)`. [5](#0-4) 
4. Attacker, still holding `P0`, crafts `sentByPeer = { signed_message: {...}, authors: [{address: A, definition: D0, authentifiers: {r: sig_by_P0}}] }` — deliberately omitting `last_ball_unit`.
5. `evaluateAA` calls `signed_message.validateSignedMessage(conn, sentByPeer, A, mci, cb)`; since `last_ball_unit` is absent, `bNetworkAware = false`, and the code only checks `chash160(D0) === A` (true) and the signature against `D0`/`P0` (valid, since the attacker holds `P0`). [2](#0-1) 
6. `validateSignedMessage` returns success with `last_ball_mci = mci`, satisfying the freshness check in `evaluation.js`, and `is_valid_signed_package` returns `true` despite `A`'s current definition being `D1`, not `D0`. [6](#0-5) 
7. The AA proceeds to treat the forged message as authorized by `A`, allowing the attacker to trigger fund-affecting logic (e.g. channel closure/balance assertions) using a key `A`'s owner believed was revoked.
