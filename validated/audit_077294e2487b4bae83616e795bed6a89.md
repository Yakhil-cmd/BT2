### Title
Webhook organization used for signature-secret selection is decoupled from the repository actually written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a payload against using `repository_owner`, parsed from the **unverified** request body (`params.dig('repository','owner','login')`). Once "verified", the entire raw `params` hash is handed to event handlers, which independently resolve the repository to act on via `payload.dig('repository', 'full_name')` (`Shipit::Webhooks::Handlers::Handler#repository_name`). These two fields are never checked for consistency, and the org used to pick the secret is not cryptographically bound to the repo actually mutated.

### Finding Description
The equality that should hold is:

`organization whose signature was cryptographically verified == organization owning the repository the handler writes to`

but the code only enforces:

`organization named in payload.repository.owner.login == organization used to pick which secret validated this raw body` [1](#0-0) [2](#0-1) 

`verify_webhook_signature` explicitly short-circuits to `true` when the selected organization has no `webhook_secret` configured: [3](#0-2) 

`Shipit.github_app_config` looks up per-organization config from `secrets.github`, keyed by whatever organization the attacker supplies in `repository.owner.login`/`organization.login`: [4](#0-3) 

Meanwhile, once the request passes `verify_signature`, the handler dispatch uses the **full, unauthenticated `params`** and each handler independently determines the target repository/stack from `full_name`, a separate field of the same JSON body: [5](#0-4) [6](#0-5) 

In a multi-organization deployment (supported and documented via the `github_organizations`/per-org secrets schema, as shown in the test fixture with two configured GitHub Apps, one of which has `webhook_secret: # nil`) an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to the organization that has **no** `webhook_secret` configured, causing `verify_webhook_signature` to unconditionally return `true` for arbitrary attacker-supplied payload content.
2. Set `repository.full_name` to a repo belonging to a **different**, secret-protected organization that the attacker wants to target.

Because the handler layer trusts `full_name` for repo resolution without ever confirming it belongs to the organization that "authenticated" the request, the attacker can drive any registered webhook handler against a foreign, secret-protected stack while presenting credentials (or lack thereof) for an unrelated, unprotected organization. [7](#0-6) 

The `status` handler is the most severe concrete instance because it persists attacker-controlled payload fields (`state`, `target_url`, `description`, `context`) directly into a `Status` record tied to a real commit, with no independent verification against the GitHub API - it's a database write driven purely by payload content once the (bypassable) signature gate is passed, as shown by the corresponding controller test which asserts exactly this direct-write behavior: [8](#0-7) 

### Impact Explanation
This meets the "High" bar: escalation into `Shipit.github_teams` authorization is not directly implicated, but it enables an **unauthenticated read/write of stack state**, specifically forged commit statuses (which gate merges/deploys via `ci.require`) and forced `GithubSyncJob` runs against a target stack the attacker does not control, by exploiting a configuration-permitted but engine-unenforced trust gap between the "authenticating organization" and the "repository written." Because CI status gates deploy/merge eligibility in Shipit, forging a passing status on a foreign, secret-protected repo can enable an unauthorized deploy/merge decision downstream.

### Likelihood Explanation
Requires a Shipit instance configured with the (supported, documented-as-optional) per-organization `webhook_secret` schema where at least one configured organization has no secret set. This is not a hypothetical edge case - the engine's own multi-app secrets format and test fixtures explicitly include an organization entry with a nil `webhook_secret`, so this configuration is a first-class supported state, not a misuse of the engine.

### Recommendation
- Do not decouple the organization used for signature verification from the organization implied by the repository being acted upon. After successful signature verification, re-validate that `payload.dig('repository','full_name')`'s owner matches `repository_owner` (the value the secret was selected for).
- Reconsider allowing `verify_webhook_signature` to return `true` unconditionally when `webhook_secret` is blank in a multi-organization configuration; at minimum, require a secret for every organization in a multi-app setup, or refuse to select handlers/repos across organizational boundaries when no secret was verified.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations: `OrgA` (webhook_secret set) and `OrgB` (webhook_secret unset/nil), matching `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/target-repo" },
  "sha": "<real commit sha in OrgA/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://attacker.example.com",
  "description": "forged"
}
```
No `X-Hub-Signature` (or an arbitrary one) is required, because `repository_owner` resolves to `OrgB`, whose `webhook_secret` is nil, causing `verify_webhook_signature` to return `true` unconditionally.
3. The `status` handler resolves the target stack via `repository.full_name` = `OrgA/target-repo` and writes a forged `Status` record for that stack's commit, satisfying `ci.require` checks it should not be able to satisfy without OrgA's real webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
