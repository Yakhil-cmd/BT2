### Title
Webhook `repository.owner.login` (used for HMAC org lookup) is decoupled from `repository.full_name` (used for repository targeting), allowing cross-tenant ReviewStack provisioning - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` derives the signing organization exclusively from `params.dig('repository','owner','login')` to select which org's `webhook_secret` verifies the HMAC, while `OpenedHandler#repository` derives the target `Shipit::Repository` exclusively from `params.repository.full_name`. Nothing binds these two independently-attacker-controlled JSON fields together, so a payload can be signed as "org A" while targeting "org B/repo", and still pass `verify_signature` and drive `ReviewStackAdapter#find_or_create!` against org B's repository.

### Finding Description
The claimed binding is: `organization_that_signed_the_request == owner_of(Shipit::Repository.from_github_repo_name(params.repository.full_name))`.

Tracing the code:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)` to obtain that org's `webhook_secret`, then verifies `X-Hub-Signature` against `request.raw_post` using that secret [1](#0-0) , [2](#0-1) .
- `Shipit.github(organization:)` resolves per-organization config (including `webhook_secret`) from `secrets.github` keyed by organization name [3](#0-2) .
- `PullRequest::OpenedHandler#repository` resolves the target repository purely from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name` [4](#0-3) , and `#process` immediately provisions a `ReviewStack` scoped to that repository if `provision?` (review_stacks_enabled + allow_all/label rules) is true [5](#0-4) , [6](#0-5) .
- The `params` schema for this handler only requires `repository.full_name`; it never requires or cross-checks `repository.owner.login` [7](#0-6) .
- `ReviewStackAdapter#create!` builds the stack using attacker-controlled `params.pull_request.head.ref` (branch) and creates the `PullRequest` record from `params.pull_request` (including `head.sha`), then enqueues it for provisioning [8](#0-7) .

Root cause: `repository.owner.login` (authorization/signing scope) and `repository.full_name` (data-targeting scope) are two independent, attacker-suppliable fields in the same JSON body. GitHub itself keeps these consistent in a genuine webhook, but nothing in this engine enforces that consistency for a directly-POSTed request. An attacker who administers their own onboarded organization ("attacker-org") on this multi-tenant Shipit instance knows their own org's `webhook_secret` (they configured it when wiring up the GitHub App/webhook). They can then POST directly to `/webhooks` with `X-Github-Event: pull_request`, a valid `X-Hub-Signature` computed with their own org's secret, `repository.owner.login = "attacker-org"` (to pass `verify_signature`), but `repository.full_name = "victim-org/victim-repo"` and an `action: "opened"` `pull_request` payload with attacker-chosen `head.sha`/`head.ref`. `verify_signature` passes because it only checks the org named in `repository.owner.login`. `OpenedHandler` then resolves `repository` to the victim's `Shipit::Repository` via `full_name` and, if that repository has `review_stacks_enabled` and `provisioning_behavior_allow_all` (a per-repo config set by the victim's own operators, not the attacker), provisions a new `ReviewStack` for the victim repo using attacker-supplied branch/SHA.

None of the existing guards close this gap: `verify_signature` validates HMAC correctness but binds it to the wrong/attacker-chosen scope; the `ExplicitParameters` schema validates types/presence, not cross-field consistency; `Repository#from_github_repo_name` and the `Repository` model's format validators constrain the *shape* of owner/name strings, not which org authenticated the request; and `drop_unhandled_event` / `check_if_ping` are unrelated to this binding.

### Impact Explanation
A repository record is written (a `ReviewStack` + `PullRequest`) for a victim organization's repository that never authenticated or authorized this request — the attacker only proved control of their own org's webhook secret, not the victim's. The created `ReviewStack` is queued via `Shipit::ReviewStackProvisioningQueue.add(stack)` and will later run provisioning/deploy commands against attacker-controlled `branch`/`head.sha`, which is a "payload for one repository mutating another's stack" and leads to unauthorized command/deploy execution on the victim's infrastructure. This is repeatable against any repository on the same multi-tenant instance with `review_stacks_enabled` and `allow_all`/`allow_with_label` provisioning behavior, for every `pull_request` `opened` (and similarly `reopened`/`labeled`/`unlabeled`/`closed` handlers that use the same `repository` resolution pattern). Severity: Critical, matching "a payload for one repository mutating another's stack ... or an unauthorized deploy".

### Likelihood Explanation
Preconditions: the attacker must be an onboarded, legitimate customer/org admin on this Shipit instance (i.e., they know their own org's `webhook_secret`, configured in `secrets.github[org]`), and the victim repository must have `review_stacks_enabled` with a permissive `provisioning_behavior` (`allow_all`, or `allow_with_label`/`prevent_with_label` satisfiable by attacker-controlled label fields in their own forged payload). Given those preconditions (common in a self-hosted multi-tenant Shipit deployment onboarding several GitHub orgs), the attack costs a single crafted HTTP POST with a correctly-computed HMAC using a secret the attacker legitimately possesses, and can be repeated at will against any victim repository name known to the attacker.

### Recommendation
Bind the webhook-authenticated organization to the resource being mutated: after `verify_signature` succeeds, re-derive/require that `repository.owner.login` (or the org that supplied a matching `webhook_secret`) equals the owner segment of `repository.full_name` before dispatching to handlers, and reject the request (e.g., `head(422)`) on mismatch. Alternatively, resolve `Shipit::Repository` strictly by `(owner: verified_org, name: parsed_name)` rather than by the untrusted `full_name` string.

### Proof of Concept
```ruby
test "cross-org signed payload cannot provision a ReviewStack for a different org's repository" do
  # Configure two orgs with distinct webhook secrets
  Rails.application.credentials.github = {
    "attacker-org" => { webhook_secret: "attacker-secret", app_id: 1, installation_id: 1, private_key: TEST_KEY },
    "victim-org" => { webhook_secret: "victim-secret", app_id: 2, installation_id: 2, private_key: TEST_KEY }
  }.with_indifferent_access

  victim_repo = Shipit::Repository.create!(owner: "victim-org", name: "victim-repo")
  victim_repo.update!(review_stacks_enabled: true, provisioning_behavior: :allow_all)

  payload = payload_parsed(:pull_request_opened)
  payload["repository"]["owner"] = { "login" => "attacker-org" }   # authenticates as attacker-org
  payload["repository"]["full_name"] = "victim-org/victim-repo"    # targets victim repo
  body = payload.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", body)

  # Binding under audit: signing org == owner of the targeted repository -> must be false here
  assert_not_equal "attacker-org", victim_repo.owner

  assert_difference -> { Shipit::ReviewStack.where(repository: victim_repo).count } do
    post "/webhooks", params: body, headers: {
      "X-Github-Event" => "pull_request",
      "X-Hub-Signature" => signature,
      "Content-Type" => "application/json"
    }
  end

  # Confirms victim repo now has a stack created solely from an attacker-org-signed request
  stack = victim_repo.review_stacks.last
  assert_equal payload["pull_request"]["head"]["ref"], stack.branch
end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
