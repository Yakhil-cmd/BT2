### Title
Webhook signature verification keys on `repository.owner.login` while all event handlers act on `repository.full_name` — organization/repository binding is not enforced - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The webhook signature-verification step selects which organization's `webhook_secret` to validate a request against using one field of the untrusted JSON body (`repository.owner.login`), while every downstream handler resolves the target `Repository`/`Stack` using a *different* field of that same untrusted body (`repository.full_name`). Because both fields live in attacker-controlled JSON and nothing ties them together, a party who legitimately controls a webhook secret for *one* GitHub organization already configured in Shipit can forge events that are processed as if they came from *any other* repository/organization known to the instance.

### Finding Description
`WebhooksController#verify_signature` computes the signing organization purely from the request body, before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). `Shipit.github(organization: repository_owner)` is used to pick the `webhook_secret` that `verify_webhook_signature` checks the `X-Hub-Signature` HMAC against: [3](#0-2) 

Once the signature check passes, `create` hands the *entire raw body* — unfiltered — to every registered handler: [4](#0-3) 

Every handler resolves the repository/stack to act on via a **different** JSON key, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Since `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied keys in the same JSON body (not derived from each other, and not cross-validated anywhere in the codebase I could find), the equality the system implicitly relies on — "the organization whose secret verified this request" == "the repository the handlers will mutate" — does not hold. An attacker who legitimately administers organization `attacker-org` (and therefore knows the `webhook_secret` Shipit has configured for `attacker-org`) can:
1. Build a JSON payload with `repository.owner.login = "attacker-org"` (so `Shipit.github(organization: "attacker-org")` picks the secret the attacker knows) and `organization.login` absent/irrelevant.
2. Set `repository.full_name = "victim-org/victim-repo"` (any repo/stack already tracked by the Shipit instance).
3. Sign the raw body with the known `attacker-org` secret and POST it directly to `/webhooks` (bypassing GitHub entirely — nothing requires the request to actually originate from GitHub's servers).
4. `verify_signature` succeeds (correct secret for the org named in the body), and `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` then processes the payload against the victim repository, because the handlers never re-check `repository.owner.login`.

The test suite confirms these two fields are treated completely independently: `webhooks_controller_test.rb` shows tests freely mutating `repository.owner.login` for signature-org selection and separately mutating `repository.full_name` for handler routing, with no test asserting they must match: [9](#0-8) [10](#0-9) 

### Impact Explanation
This breaks the "organization authenticated versus the repository that is written" binding called out in scope. Concrete consequences using this engine's own code:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)` for any stack under the forged `full_name` matching the pushed branch — an attacker can force GitHub-sync activity against a repository/stack they do not control.
- `StatusHandler` looks up commits purely by `sha` (global, not scoped to the forged repository) and calls `commit.create_status_from_github!(params)` — an attacker can inject arbitrary CI status (e.g., forged `success`) onto a commit belonging to a victim's stack, which can feed into deploy-readiness/CI-gating logic (`deploy.override`/`ci.require` blocking-status checks in `DeploySpec`), potentially enabling continuous-delivery or manual-deploy triggers gated on those statuses.
- `PullRequest::OpenedHandler`/`ClosedHandler`/etc. can create, archive, or otherwise mutate review stacks under `Repository.from_github_repo_name(params.repository.full_name)` for a victim repository, i.e., cross-repository writes performed by an attacker who only controls a different, unrelated organization's webhook secret.

This satisfies the required impact bar of "cross-repository writes" and potentially contributes to an "unauthorized deploy" if a forged status unblocks CI-gated deployment, both listed as Critical-tier outcomes in scope.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate webhook administrator/HMAC-secret holder for *some* GitHub organization already configured in the Shipit instance (a realistic scenario in any multi-tenant/multi-org Shipit deployment, e.g. a company allowing several business units or external partner orgs to each have their own webhook secret). No GitHub App private key, `ApiClient` token, or Shipit session is needed — only an HTTP client capable of computing an HMAC-SHA1 and POSTing to the public `/webhooks` endpoint, which by design accepts unauthenticated requests validated solely by the HMAC signature.

### Recommendation
After signature verification succeeds for a given `repository_owner`, handlers should re-derive `repository.owner.login` from the same verified payload and reject (or the controller itself should reject) any event whose `repository.full_name`'s owner segment does not match the `repository_owner` used to select the verifying secret. Equivalently, `Handler#repository_name`/`#stacks` should validate that the owner segment of `full_name` equals the verified `repository_owner`, ensuring the "verified organization" and "repository acted upon" are cryptographically bound to the same value.

### Proof of Concept
1. In a Shipit installation configured with two organizations, `attacker-org` (secret known to attacker, e.g. because they administer that org's GitHub App/webhook) and `victim-org` (unrelated, has a Shipit stack tracking `victim-org/victim-repo`).
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
     "owner": { "login": "attacker-org" },
     "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac_sha1(attacker-org secret, body)>` and sends it to `POST /webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (matches the field the attacker controls), the HMAC validates, and processing proceeds.
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the real commit by `sha` and calls `create_status_from_github!`, writing a forged `success` status for `ci/required-check` on a commit that belongs to `victim-org/victim-repo`, despite the request only having been authenticated for `attacker-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
