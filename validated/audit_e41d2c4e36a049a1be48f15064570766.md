### Title
Unbounded per-block stake-account processing at epoch reward-distribution boundary via attacker-inflated total_stake_accounts - (File: runtime/src/bank/partitioned_epoch_rewards/mod.rs)

### Summary
`get_reward_distribution_num_blocks` caps the *number* of reward-distribution blocks to `slots_per_epoch / 10`, but this cap is independent of the "target" `partitioned_rewards_stake_account_stores_per_block` (default 4096) used to compute `num_chunks`. Once `total_stake_accounts` grows large enough that `div_ceil(total_stake_accounts, stake_account_stores_per_block)` exceeds `slots_per_epoch / 10`, the clamp saturates the *block count*, but the actual number of accounts assigned to each block (via `hash_rewards_into_partitions`) grows unboundedly with `total_stake_accounts`, because rewards are hashed pseudo-randomly into a fixed number of buckets rather than being grouped by the target chunk size.

### Finding Description
`get_reward_distribution_num_blocks` computes: [1](#0-0) 
```
let num_chunks = total_stake_accounts.div_ceil(stores_per_block) as u64;
num_chunks.clamp(1, (slots_per_epoch / 10).max(1))
```
This value (`num_partitions`) is then passed to `hash_rewards_into_partitions`, which distributes every reward index into one of `num_partitions` buckets purely by hashing the stake pubkey, with no bound on bucket size: [2](#0-1) 

`store_stake_accounts_in_partition` (invoked once per block during distribution, from `distribute_partitioned_epoch_rewards`) then iterates over the *entire* index list for a partition without any additional per-block truncation: [3](#0-2) 
```
let indices = partition_rewards.partition_indices.get(partition_index as usize)...
let mut updated_stake_rewards = Vec::with_capacity(indices.len());
...
for index in indices { ... build_updated_stake_reward ... }
```
followed by a `store_accounts` call for the whole `updated_stake_rewards` batch in one block.

Because `num_partitions` is clamped to a maximum of `slots_per_epoch / 10` regardless of how large `total_stake_accounts` becomes, the *average* (and expected worst-case) number of accounts per partition is `total_stake_accounts / num_partitions`, which is **unbounded** as `total_stake_accounts → ∞`, even though the "baseline" `MAX_PARTITIONED_REWARDS_PER_BLOCK = 4096` constant is documented as the intended per-400ms-block ceiling: [4](#0-3) 

An unprivileged attacker can create arbitrarily many stake accounts, each delegated at or above the protocol minimum delegation, via ordinary `CreateAccount` + `Initialize` + `DelegateStake` instructions they fully control. Every such delegated, active stake account that earns any non-zero reward (or has a credits-observed change) becomes part of `total_stake_accounts` (`rewards.num_rewards()`) at the next epoch boundary. No signer/authority/rent-exempt/epoch checks in the reward-calculation or clamp logic limit the *count* of such accounts — those checks operate on individual account validity, not aggregate account count. As `total_stake_accounts` scales past `stake_account_stores_per_block * (slots_per_epoch / 10)`, the clamp guarantees only a bounded number of *blocks*, not a bounded amount of *work per block*, inverting the intended safety property.

### Impact Explanation
This is an epoch-boundary computational-blowup / halting-risk finding, matching the "validator divergence / epoch-boundary halt" bounty category referenced in the question. If a single reward-distribution block must process many multiples of the intended 4096-account baseline (e.g. tens or hundreds of thousands of accounts) within a single ~400ms slot budget, the block-producing/replaying validator can miss its slot deadline, causing skipped slots, degraded liveness during the reward-distribution window, or divergence between validators with differing hardware capacity to complete the oversized batch in time. It does not directly mint or steal lamports, but affects protocol availability guarantees at every epoch boundary once the attacker's stake-account population is large enough.

### Likelihood Explanation
Feasibility is bounded only by the economic cost of creating and delegating an extremely large number of stake accounts (rent-exemption reserve + minimum delegation lamports per account, no protocol-level limit on count), which is within reach for a well-funded but still fully unprivileged actor over time (accounts can be created gradually across many epochs and simply need to remain delegated/active by the target epoch boundary). No elevated permissions, validator control, or leaked keys are required — only standard System/Stake program instructions signed by the attacker's own keys, matching the stated preconditions exactly. The attack is fully repeatable every epoch as long as the attacker's stake accounts remain active and continue earning rewards.

### Recommendation
Bound work per block directly rather than only bounding block count: either (a) increase `num_partitions` without an upper clamp (or raise the clamp) when `total_stake_accounts` is large, accepting a longer reward-distribution phase instead of a heavier one, (b) chunk `hash_rewards_into_partitions` buckets further so no single partition ever exceeds `stake_account_stores_per_block`, splitting oversized buckets into multiple sub-batches processed across additional blocks even past the `slots_per_epoch/10` limit, or (c) impose and enforce a real per-block account-processing ceiling inside `store_stake_accounts_in_partition` (e.g. process at most `stake_account_stores_per_block` indices per block invocation, carrying remainder to subsequent blocks), decoupling the "10% of epoch" cap from the correctness of the per-block cap.

### Proof of Concept
Rust unit test extending the existing `test_get_reward_distribution_num_blocks_cap` pattern in `runtime/src/bank/partitioned_epoch_rewards/mod.rs`:
```rust
#[test]
fn test_per_block_work_unbounded_when_total_stake_accounts_huge() {
    // Small epoch to make the 10% clamp bite quickly.
    let mut genesis_config = create_genesis_config(1_000_000 * LAMPORTS_PER_SOL).0;
    genesis_config.epoch_schedule = EpochSchedule::custom(32, 32, false);

    let mut accounts_db_config = ACCOUNTS_DB_CONFIG_FOR_TESTING;
    accounts_db_config.partitioned_epoch_rewards_config =
        PartitionedEpochRewardsConfig::new_for_test(10); // baseline per-block target

    let bank = Bank::new_from_genesis(&genesis_config, ..., accounts_db_config, ...);
    // slots_per_epoch/10 == 3, so max num_partitions == 3

    // Simulate an attacker-inflated reward set far beyond
    // stake_account_stores_per_block * (slots_per_epoch/10) == 10*3 == 30
    let huge_num_stakes: u64 = 3_000_000; // attacker-controlled delegated stake accounts
    let stake_rewards = (0..huge_num_stakes)
        .map(|_| Some(PartitionedStakeReward::new_random()))
        .collect::<PartitionedStakeRewards>();

    let num_partitions = bank.get_reward_distribution_num_blocks(&stake_rewards);
    assert_eq!(num_partitions, 3); // clamp saturates

    let partition_indices = hash_rewards_into_partitions(
        &stake_rewards, &Hash::default(), num_partitions as usize,
    );

    // Assert (expected to FAIL, proving the bug): each partition's size should
    // stay bounded near stake_account_stores_per_block (10), but instead each
    // bucket holds roughly huge_num_stakes / num_partitions ~= 1,000,000 accounts.
    for indices in &partition_indices {
        assert!(
            indices.len() <= 10 * 2, // generous slack over baseline
            "partition has {} accounts, far exceeding the per-block baseline",
            indices.len()
        );
    }
}
```
Expected result: the assertion fails, demonstrating that `indices.len()` passed into `store_stake_accounts_in_partition` scales with attacker-controlled `total_stake_accounts` and is not bounded by `partitioned_rewards_stake_account_stores_per_block` once the `slots_per_epoch/10` block-count clamp is reached.

    pub(super) fn get_reward_distribution_num_blocks(

    stake_rewards: &PartitionedStakeRewards,

    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

            .clone()
