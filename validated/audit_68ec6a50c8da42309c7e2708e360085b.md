### Title
Commit status webhooks are matched globally by SHA, letting an authenticated-but-untrusted GitHub organization forge CI status for another organization's stack and trigger an unauthorized deploy - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` validates the `status` webhook against the GitHub App configured for the *organization that owns the repository named in the payload* [1](#0-0) [2](#0-1) . Once that per-organization signature check passes, `StatusHandler#process` ignores the repository entirely and looks up the target `Commit` purely by SHA across the whole database: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . `PushHandler`, by contrast, correctly scopes to `stacks` derived from `payload.dig('repository', 'full_name')` [4](#0-3) [5](#0-4) , showing the repository-scoping is deliberately performed elsewhere but omitted here.

### Finding Description
The binding that should hold is: `organization authenticated by X-Hub-Signature == organization whose commit/stack state is written`. `StatusHandler` breaks this equality because it never calls `stacks`/`repository_name` (the very helpers `Handler` provides for this purpose) - it resolves the target purely via `Commit.where(sha: params.sha)`, with no repository filter [3](#0-2) .

Git commit SHAs are content-derived, not secret, and are frequently identical across repositories that share history (forks, mirrors, vendored/subtree imports, monorepo splits). An attacker who legitimately controls their own GitHub organization (call it Org-Evil) that is also onboarded as a Shipit GitHub App/organization (so `Shipit.github(organization: 'org-evil')` exists and GitHub will correctly compute `X-Hub-Signature` using the real, legitimate webhook secret for that org) can:

1. Fork or otherwise obtain a repository whose history overlaps with the victim stack's repository (e.g., fork the victim's public repo, or exploit any commit SHA that is already tracked as a `Commit` for the victim's `Stack`).
2. Trigger (or directly send, since GitHub will sign it correctly for their own repo) a `status` webhook event carrying that shared SHA and `state: "success"`.
3. `WebhooksController#verify_signature` succeeds because the signature is valid *for Org-Evil*, which is a legitimate, correctly-configured organization in Shipit's `secrets.github` config [6](#0-5) .
4. `StatusHandler` then writes a `Status` to whichever `Commit` row(s) in the database share that SHA - including a commit belonging to a completely different organization's `Stack` - via `commit.create_status_from_github!(params)` [3](#0-2) .

This is precisely the "organization authenticated versus the repository actually written" trust-binding break called out by the compound-protocol analog (paused-guardian check validated one condition while a different, unguarded state mutation occurred).

### Impact Explanation
Commit statuses are the mechanism Shipit uses to determine whether a commit is "deployable"/CI-green, which feeds `required_statuses`, `soft_failing_statuses`, and continuous delivery scheduling (`Stack.schedule_continuous_delivery` / `ContinuousDeliveryJob`) [7](#0-6) . By forging a passing status for a victim's commit from an unrelated, attacker-controlled organization, an attacker can flip a victim stack's commit into a deployable state and cause continuous delivery to automatically deploy/ship that commit - an unauthorized deploy performed by Shipit itself using its own GitHub credentials for the victim stack. This satisfies the "Critical - unauthorized deploy" impact bar.

### Likelihood Explanation
The only prerequisite is that the attacker controls (or has push/webhook rights to) any GitHub organization that is already configured as a legitimate Shipit-connected GitHub App/org - not the victim organization, not the victim's webhook secret, and not a Shipit session or API token. Obtaining a commit SHA collision with a victim's tracked commit is realistic for public repos, forks, and shared-history repositories, which are common in practice. No secret material or elevated Shipit privilege is required beyond being *a* legitimate, but organizationally unrelated, GitHub App installation.

### Recommendation
`StatusHandler#process` (and any other handler resolving state purely by content-derived identifiers such as SHA) must scope its `Commit` lookup to the repository/organization the webhook was authenticated for, mirroring the `stacks`/`repository_name` scoping already implemented in `Handler` and used by `PushHandler`:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or equivalently join through `Stack`/`Repository` so a `Commit` is only updated if it belongs to a stack whose repository matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
1. Register/operate `org-evil` as a legitimate GitHub organization with a Shipit GitHub App installed (standard onboarding, no secret needed since GitHub signs webhooks correctly for the attacker's own org).
2. Identify a commit SHA `S` that is tracked as a `Commit` for a victim `Stack` (e.g., by forking the victim's public repository, which preserves identical SHAs, or through any shared-history repository).
3. From a repository under `org-evil`, create/push a commit status (via GitHub API `POST /repos/org-evil/repo/statuses/S`) with `state: success` and any `context` the victim's stack requires (see `required_statuses`) [8](#0-7) .
4. GitHub delivers the `status` webhook to Shipit, correctly signed for `org-evil`; `verify_signature` passes [1](#0-0) .
5. `StatusHandler#process` finds the victim's `Commit` row by SHA (ignoring repository) and records the forged `success` status [3](#0-2) .
6. If the victim `Stack` has `continuous_deployment: true` and this was the last required status, `ContinuousDeliveryJob` deploys the commit automatically.
