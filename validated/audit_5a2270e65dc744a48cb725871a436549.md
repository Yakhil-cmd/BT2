### Title
Null-dereference crash in private-payment chain validation via duplicate head elements - ([File: wallet.js])

### Summary
The CVE describes a Linux kernel use-after-free where a proc entry is freed while another code path still holds/uses a reference to it because unregistration ordering and refcounting were not correctly enforced. The reachable analog in `ocore--013` is in `wallet.js`'s `handlePrivatePaymentChains`, where the "validated" tracking object `assocValidatedByKey` is nulled out (freed) as a completion marker while a duplicate, still-pending `eventBus.once()` callback for the same key can fire afterward and dereference/write into the already-nulled object, throwing an unhandled exception.

### Finding Description
`handlePrivatePaymentChains` is invoked whenever a private-payment counterparty (or the hub relaying on their behalf) sends a `private_payments` message to a wallet [1](#0-0) . For each chain in the attacker-controlled `body.chains` array, a `key` string is derived purely from content the sender controls (`unit`, JSON hash of `payload`, `output_index`) and used to index `assocValidatedByKey` and to register an event listener: [2](#0-1) [3](#0-2) 

If two entries in `arrChains` produce the same head element (same `unit`, `payload`, `output_index`), the identical `key` is used twice. `network.handleOnlinePrivatePayment` responds `ifQueued` in both cases (typical for light clients), so **two separate `eventBus.once(key, ...)` listeners are registered for the same event name**. Node's `EventEmitter` does not deduplicate `once` listeners registered under the same name — both will fire when the underlying validation event is eventually emitted once.

The completion logic assumes each key's callback fires at most once: [4](#0-3) 

When all keys are marked `true`, `checkIfAllValidated` sets `assocValidatedByKey = null` as a "no more processing" guard [5](#0-4) . However, because the duplicate-key registration lets a *second* listener for the same key remain live, when the network event finally fires, both duplicate listeners execute: [6](#0-5) 

The first invocation completes validation, calls `checkIfAllValidated`, and nulls `assocValidatedByKey`. The second (duplicate) invocation for the *same key* then executes `assocValidatedByKey[key] = true;` on an already-nulled object, i.e. a write to `null`, throwing `TypeError: Cannot set properties of null`. This is conceptually the same bug class as the kernel CVE: a shared state object is torn down/freed while another registered handler still expects to use it, because the unregistration/lifecycle bookkeeping does not account for duplicate registrations tied to attacker-controlled keys.

### Impact Explanation
An uncaught `TypeError` thrown from inside an `eventBus` listener callback executed via `EventEmitter.emit` is not caught by any `try/catch` in the call chain (`checkIfAllValidated` → `eventBus.emit` → listener), so it propagates as an uncaught exception in the wallet/node process. This crashes the runtime handling private payments for the affected instance, denying it the ability to process further private payments or validate/confirm units until restarted — a remotely triggerable crash caused purely by a private-payment counterparty's message content, requiring no special privilege beyond being a paired/messaging counterparty.

### Likelihood Explanation
The trigger requires only sending a `private_payments` message whose `chains` array contains two entries that hash to the identical head-element key (same `unit`, same JSON-serialized `payload`, same `output_index`) and for which `network.handleOnlinePrivatePayment` responds `ifQueued` for both (the common path for light clients awaiting DAG dependencies) — an attacker-controlled, easily reproducible condition requiring no race with other peers or timing luck beyond constructing a duplicated array element.

### Recommendation
Deduplicate `arrChains`/head elements by key before registering listeners (skip re-registering `eventBus.once(key, ...)` if a listener for that `key` is already pending), or guard the `ifQueued` callback and `checkIfAllValidated` against `assocValidatedByKey` being `null` (check `if (!assocValidatedByKey) return;` inside the `eventBus.once` callback body before writing), and wrap the `eventBus.emit` calls that invoke external listener logic in a `try/catch` so a bad message cannot become an uncaught process-level exception.

### Proof of Concept
1. As a paired device / private-payment counterparty, send a `private_payments` message via `sendPairingMessage`/hub relay whose `body.chains` contains two chain entries with identical head `objHeadPrivateElement` (same `unit`, `payload`, `output_index`) — e.g. `chains: [[headElem], [headElem]]` with `headElem` referencing a not-yet-known unit so `network.handleOnlinePrivatePayment` returns `ifQueued` for both.
2. `handlePrivatePaymentChains` registers two `eventBus.once('private_payment_validated-...')` listeners under the same computed `key`.
3. When the referenced unit is eventually received/validated and the event is emitted once, both listeners fire; the first nulls `assocValidatedByKey` via `checkIfAllValidated`, and the second attempts `assocValidatedByKey[key] = true` on `null`, throwing an uncaught `TypeError` and crashing the wallet process.
