### Title
Unbounded per-unit best-parent chain walk in witness-level/witness-list validation enables O(N·depth) validation cost from linear attacker input - (File: storage.js)

### Summary
`storage.determineWitnessedLevelAndBestParent()` (storage.js:692-731) and `storage.buildListOfMcUnitsWithPotentiallyDifferentWitnesslists()` (storage.js:2142-2165) both walk unit-by-unit up the `best_parent_unit` chain, doing one DB/cache read and one witness-collection pass per hop, until they collect a majority of witnesses or reach the unit's `last_ball_unit`/witness-list boundary. Both are invoked from `validateWitnesses()` (validation.js:887-983) for **every** unit that reaches validation — an operation reachable by any unprivileged unit poster. ### Finding Description
`addWitnessesAndGoUp()` inside `determineWitnessedLevelAndBestParent()` recurses through best parents, reading unit props and unit authors at each hop, stopping only once `constants.MAJORITY_OF_WITNESSES` distinct witness addresses have been seen among the walked units: [4](#0-3) 

This function is called unconditionally for every unit from `checkWitnessedLevelDidNotRetreat()` inside `validateWitnesses()`: [5](#0-4) 

Similarly, pre-v4 units additionally trigger `determineIfHasWitnessListMutationsAlongMc()` → `buildListOfMcUnitsWithPotentiallyDifferentWitnesslists()`, whose `addAndGoUp()` walks the best-parent chain one unit at a time until it reaches `last_ball_unit` or finds a matching `witness_list_unit`: [3](#0-2) [6](#0-5) 

Neither walk is bounded by a fixed step count independent of the number of hops needed to collect a witness majority; in the worst case (a run of consecutive non-witness units, or a large distance between the unit's parents and its `last_ball_unit`), the number of hops per validated unit scales with the *distance* the attacker can create in the DAG, not with a constant. An attacker who can post a chain of units whose best-parent lineage keeps missing witnesses (or keeps referencing an old `last_ball_unit`) forces each newly validated unit to perform an O(depth) walk. Because every new unit independently re-walks from its own tip, a burst of N such units costs O(N·depth) total work for full/light nodes performing IDS-like validation of incoming traffic — the same class of blow-up as the Suricata stream-inspection bug, where crafted but otherwise valid-looking input causes disproportionate reprocessing cost relative to its size.

Unlike `main_chain.js`'s DAG-stability functions (`determineIfStableInLaterUnits`, `createListOfBestChildren`, etc.) which are throttled with `setImmediate` batching every 100 iterations for the heaviest hot loops, `addWitnessesAndGoUp` in `determineWitnessedLevelAndBestParent` has no such periodic yield, and `addAndGoUp` in `buildListOfMcUnitsWithPotentiallyDifferentWitnesslists` has none either, meaning each of these walks blocks the event loop of the validating node/hub for its full duration once started, compounding the DoS effect from a burst of crafted units.

### Impact Explanation
This does not break consensus safety (no forged signatures, no spend bypass) but degrades availability: hubs and full nodes validate every unit posted to them, and each validation call pays the O(depth) witness-walk cost. A sender able to arrange the DAG lineage of self-authored units (units are self-composed client-side, so the attacker fully controls their own units' `parent_units`/`last_ball_unit` subject only to normal validity constraints) can inflate the per-unit validation cost across many units in a burst, slowing down or stalling a node's ability to validate and relay legitimate traffic — a network-availability degradation consistent with the CVE-2026-31933 bug class (crafted traffic causing an IDS/validation engine to slow down).

### Likelihood Explanation
Medium-High: both functions are on the mandatory validation path for every unit (`validateWitnesses` is unconditionally called in `validate()`), require no special privileges, and the attacker only needs to control the lineage of units they themselves author/post (parents, last_ball_unit) which is standard, permitted unit-composition freedom. No malicious peer/hub cooperation, light-client trust, or protocol violation is required.

### Recommendation
- Add a hard cap on the number of best-parent hops walked in `addWitnessesAndGoUp` (storage.js) and `addAndGoUp` (`buildListOfMcUnitsWithPotentiallyDifferentWitnesslists`), independent of witness-majority collection, failing validation (or falling back to a bounded/cached computation) if the cap is exceeded.
- Add periodic `setImmediate` yielding (matching the pattern already used in `main_chain.js`'s heavy traversal loops) inside these two walks so a single deep walk cannot block the event loop.
- Consider caching witnessed-level/best-parent results per unit once computed (memoization keyed by `unit`) so repeated validations of overlapping lineages do not re-walk the same chain.

### Proof of Concept
1. As an ordinary unit-composing client, construct and self-post a long sequence of units (U1 → U2 → … → UN) where each Ui's `best_parent_unit` chain deliberately includes as many non-witness authors as protocol rules allow before finally reaching enough witness-authored ancestors (or keep referencing an old `last_ball_unit` so `buildListOfMcUnitsWithPotentiallyDifferentWitnesslists` must walk far to reach it).
2. Submit this batch of N units to a hub/full node in a short window.
3. Observe that `validateWitnesses()` → `determineWitnessedLevelAndBestParent()`/`determineIfHasWitnessListMutationsAlongMc()` performs an O(depth) unbounded, non-yielding walk for each of the N units, causing validation latency for the batch to grow well beyond what O(N) unit count alone would predict, and blocking the node's event loop for extended periods during the walk of any single deep unit.

function buildListOfMcUnitsWithPotentiallyDifferentWitnesslists(conn, objUnit, last_ball_unit, arrWitnesses, handleList){

	function addAndGoUp(unit){
		readStaticUnitProps(conn, unit, function(props){
			// the parent has the same witness list and the parent has already passed the MC compatibility test
			if (objUnit.witness_list_unit && objUnit.witness_list_unit === props.witness_list_unit)
				return handleList(true, arrMcUnits);
			else
				arrMcUnits.push(unit);
			if (unit === last_ball_unit)
				return handleList(true, arrMcUnits);
			if (!props.best_parent_unit)
				throw Error("no best parent of unit "+unit+"?");
			addAndGoUp(props.best_parent_unit);
		});
	}

	var arrMcUnits = [];
	determineBestParent(conn, objUnit, arrWitnesses, false, function(best_parent_unit){
		if (!best_parent_unit)
			return handleList(false);
		addAndGoUp(best_parent_unit);
	});
}
