### Title
Webhook signature verification binds to `repository.owner.login`, but the push handler resolves the target `Stack` from `repository.full_name` — allowing a signed webhook from one onboarded GitHub organization to force-sync commits into another organization's stack ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the request against using only `repository.owner.login` (or `organization.login`) from the JSON body, then verifies the HMAC over the whole raw body with that org's secret. [1](#0-0)  Once the signature check passes, `create` re-parses the same raw body and dispatches it to handlers such as `PushHandler`, which resolves the target `Stack` independently, via `repository.full_name`. [2](#0-1) [3](#0-2)  Nothing ties `repository.full_name`'s owner segment back to the `repository.owner.login`/`organization.login` value that authorized the request. On a Shipit instance configured for multiple GitHub organizations (a documented, supported setup) [4](#0-3) [5](#0-4) , an org admin who legitimately knows their own org's `webhook_secret` can submit a validly-signed `push` payload whose `repository.owner.login` matches their own org (so it passes `verify_signature`) but whose `repository.full_name` names a different, victim organization's repository, causing `Shipit::Webhooks::Handlers::PushHandler` to run `sync_github` against the victim's `Stack`.

### Finding Description
- `verify_signature` computes the trust anchor as `repository_owner` = `params.dig('repository','owner','login') || params.dig('organization','login')`, and looks up the GitHub App config for that organization to verify the signature: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) [6](#0-5) 
- `create` re-parses `request.raw_post` and dispatches the same JSON body to all registered handlers for the event without any additional binding check. [2](#0-1) 
- `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolves the affected repository purely from `payload.dig('repository','full_name')`, i.e. an independent field from the one used to select the verifying secret. [3](#0-2) 
- `PushHandler#process` uses that resolved `stacks` scope to call `stack.sync_github(expected_head_sha: params.after)` for every un-archived stack on the matching branch. [7](#0-6) 
- `Shipit.github` supports per-organization GitHub App configuration (`app_id`, `installation_id`, `webhook_secret`, etc., keyed by organization name), a feature explicitly documented for multi-org deployments. [5](#0-4) [4](#0-3) 

The binding that should hold is: **the organization whose secret authenticated the request == the organization owning the repository whose stacks are mutated**. Before a fix, these are two independently-read fields of the same unauthenticated-content JSON body (`repository.owner.login` vs `repository.full_name`), and only the former is covered by the HMAC-secret selection logic, not by any cross-check against the latter. Because the HMAC itself is computed over the *entire* raw body, a valid signature does prove the body wasn't tampered with in transit — but it does not prove that `repository.full_name`'s owner matches `repository.owner.login`; an attacker who legitimately controls (and thus knows the webhook secret for) one onboarded org can construct and correctly-sign an arbitrary JSON body in which those two fields disagree, since GitHub itself is not the one generating this payload — the attacker POSTs directly to the public `/webhooks` endpoint.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" trust binding called out for this analog class. The forged, validly-signed push event lets an attacker-controlled org holder trigger `GithubSyncJob`/`sync_github` for a victim organization's `Stack` with an attacker-chosen `expected_head_sha`, forcing Shipit to fetch and ingest commits for that stack outside of the legitimate owning organization's control. In a merge-queue/continuous-deployment-enabled stack this can accelerate ingestion of attacker-timed commits into the deploy pipeline of a repository the attacker does not have write access to, which can manifest as an unauthorized deploy trigger for a repo/org the attacker never had permission over. This qualifies as escalation of a legitimate credential (attacker's own org's webhook secret) into effects scoped to a different, unauthorized repository/stack — matching the High severity category "escalation ... unauthorized deploy" bucket.

### Likelihood Explanation
Likelihood is Medium-to-High for any deployment supporting multiple GitHub organizations (a first-class, documented configuration). Exploitation requires only that the attacker be a legitimate admin of one onboarded org (thus knowing that org's `webhook_secret`, which they configure themselves when creating their GitHub App) and knowledge of a target `owner/name` string for another onboarded stack (repository names/orgs are not secret). No GitHub-side cooperation is required since the webhook endpoint is a plain public HTTP endpoint that accepts any correctly-signed body, not only genuine GitHub-origin traffic.

### Recommendation
In `WebhooksController`, after determining `repository_owner` and verifying the signature, re-derive and enforce that any `repository.full_name` used later by handlers is owned by that same `repository_owner` (e.g., reject/discard the payload if `params.dig('repository','full_name')&.split('/')&.first&.casecmp?(repository_owner)` is false), or better, have `Handler#repository_name`/`#stacks` receive the authenticated organization explicitly and validate the repository owner against it before resolving stacks, rather than trusting an unrelated field of the same unauthenticated-origin JSON body.

### Proof of Concept
1. Configure Shipit with two GitHub App orgs, e.g. `attacker-org` (webhook secret known to the attacker, who created this app) and `victim-org` (any stack, e.g. `victim-org/prod-app`), per the documented multi-org config. [4](#0-3) 
2. Attacker crafts a `push` JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/prod-app",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body, per `GitHubApp#verify_webhook_signature`. [8](#0-7) 
4. POST to `/webhooks` with header `X-Github-Event: push`. `verify_signature` computes `repository_owner` = `"attacker-org"` and validates successfully against `attacker-org`'s secret. [1](#0-0) [6](#0-5) 
5. `create` dispatches the body to `PushHandler`, which resolves `stacks` from `repository.full_name` = `"victim-org/prod-app"` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — despite the request only being authenticated for `attacker-org`. [7](#0-6) [3](#0-2) 

Note: I was unable to fully trace `Stack#sync_github`'s exact behavior (in `app/models/shipit/stack.rb`) within the available context to confirm every downstream side effect (e.g., whether it can trigger an actual automatic deploy versus only ingesting commit metadata); this should be verified directly in that file before treating the downstream impact as fully proven.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
