### Title
`Api::CCMenuController` bypasses per-stack `ApiClient` scoping, allowing an `ApiClient` token restricted to one stack to read the deploy status of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts a stack-scoped `ApiClient` to its own `stack_id` through the `stacks`/`stack` helper methods, but `Api::CCMenuController` overrides `#stack` and resolves the target directly from `Stack.from_param!(params[:stack_id])`, skipping that scoping entirely. Any valid `ApiClient` token with `read:stack` permission — even one explicitly bound to a single stack — can therefore be replayed against this endpoint with an arbitrary `stack_id` to read another stack's build/deploy status.

### Finding Description
`Api::BaseController` defines the authorization boundary that ties an `ApiClient` token to the stack(s) it is allowed to touch: [1](#0-0) 

`require_permission!` only checks the coarse `operation:scope` permission string (e.g. `read:stack`) via `ApiClient#check_permissions!`, it never checks which specific stack the client is allowed to see: [2](#0-1) 

Every other API controller resolves the target stack through the scoped `stack`/`stacks` helpers, so a client created with `stack: some_stack` (see fixture `here_come_the_walrus`) cannot reach other stacks: [3](#0-2) 

`Api::CCMenuController`, however, redefines `#stack` to bypass the scoping check entirely, resolving the stack straight from the request parameter regardless of `current_api_client.stack_id`: [4](#0-3) 

The controller's only authorization gate is the generic permission check: [5](#0-4) 

The trust binding broken is: `ApiClient.stack_id` (the stack a token authorizes) ≠ `stack_id` param actually used to render CCMenu output (the stack the token touches). Before the attacker's request, a stack-scoped token can only ever produce `Stack.where(id: current_api_client.stack_id)` results through the normal `stack`/`stacks` helpers used elsewhere in the API; after hitting `Api::CCMenuController#show` with a different `stack_id`, the same token successfully resolves and renders data for a stack it was never granted.

### Impact Explanation
This is an authorization scope escalation: a token deliberately restricted to one stack (e.g., issued to a low-trust integration or partner team for a single project) can be used to enumerate and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state) of every other stack in the Shipit instance, including private/internal ones the token holder has no legitimate access to. This matches the "escalation into ... unauthenticated read of stack state, task streams, or deploy output" High-severity bucket, since it grants read access to stack state that the token's scoping was specifically designed to prevent.

### Likelihood Explanation
Medium: exploitation only requires possessing any valid `ApiClient` authentication token with `read:stack` permission (even one intentionally scoped to a single stack) and knowledge/guessing of another stack's `stack_id`/param. No privileged account, session, or additional secret is required beyond a token that is otherwise routinely distributed to less-trusted integrations (this is exactly the kind of token CCMenu-style status tools are handed out for).

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` and use the inherited, scoped `stack`/`stacks` helpers from `Api::BaseController` so the CCMenu endpoint respects `current_api_client.stack_id` the same way every other API controller does. Add regression tests asserting that a stack-scoped `ApiClient` (e.g., `here_come_the_walrus`) receives a 404/`RecordNotFound` when requesting a `stack_id` outside its scope via `Api::CCMenuController#show`.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to `stack_id: A` with `read:stack` permission (e.g. the `here_come_the_walrus` fixture pattern from `test/fixtures/shipit/api_clients.yml`).
2. Send `GET /api/stacks/:stack_id_of_B/ccmenu.xml` (per `config/routes.rb` ccmenu route) using HTTP Basic auth with that token, substituting a `stack_id` for stack `B` that the token was never granted access to.
3. `Api::CCMenuController#authenticate_api_client` accepts the token (it is valid), `require_permission :read, :stack` passes because the token does have the `read:stack` permission string, and `#stack` resolves `Stack.from_param!(params[:stack_id])` directly against stack `B`, ignoring `current_api_client.stack_id == A`.
4. The response renders `shipit/ccmenu/project` XML with stack `B`'s real deploy/build status — data the token was never authorized to read.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end
