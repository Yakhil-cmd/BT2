### Title
Webhook signature verified against `repository.owner.login`/`organization.login` while every event handler acts on the independent `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook using `repository_owner`, taken from `params.dig('repository','owner','login')` (or `organization.login`) inside the *same, attacker-suppliable* JSON body. Every `Shipit::Webhooks::Handlers::Handler` subclass, however, resolves the actual `Stack`/`Repository` to mutate using a **different** field of that same body: `payload.dig('repository','full_name')`. Nothing ties `repository.full_name` to `repository.owner.login`, so a party who legitimately controls a webhook secret for one organization configured in Shipit's multi-org `secrets.yml` (see `docs/setup.md` "Using Multiple Github Applications") can produce a validly-signed payload whose `owner.login` matches their own org but whose `full_name` names a stack belonging to a completely different, unrelated organization/repository hosted on the same Shipit instance.

### Finding Description
- Verification: `Shipit::WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` and calls `github_app.verify_webhook_signature(header, raw_post)`, where `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- Dispatch: the raw JSON body is handed unmodified to all registered handlers for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 
- Every handler's base class resolves the target repository/stack from a **different** JSON key, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) 
- `PushHandler` uses that repository resolution to locate stacks and immediately triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the target branch: [5](#0-4) 
- This enqueues `GithubSyncJob`, which fetches real commits from GitHub for the resolved stack (using the *correct* `github_app`/token for that stack's real owner via `Stack#github_app`), appends them, and — critically — commit creation triggers `schedule_continuous_delivery` on `Commit`, which can auto-deploy the stack if continuous deployment is enabled: [6](#0-5) [7](#0-6) [8](#0-7) 

Because Shipit supports hosting multiple independent GitHub organizations behind one instance, each with its own `webhook_secret` configured under `secrets.github.<organization>` (as documented), a party who is a legitimate, authenticated member/operator for **their own** configured organization — and therefore knows/controls that organization's `webhook_secret` — can forge a webhook whose `repository.owner.login` (or `organization.login`) is set to their own org (so it authenticates), but whose `repository.full_name` names a repository/stack belonging to a **different tenant organization** on the same instance. The equality that should hold — "organization that authenticated == organization whose repository is written" — is broken: verification is keyed on one field, mutation is keyed on an unrelated field within the same unauthenticated-by-cross-check JSON body.

### Impact Explanation
This lets a party with valid credentials for organization A force webhook-triggered side effects against organization B's stacks on a shared Shipit instance, without B's cooperation:
- Force a `GithubSyncJob` run on a victim stack at a time of the attacker's choosing, which — combined with `continuous_deployment` — can trigger an **unauthorized deploy** the moment new commits exist upstream (`Commit#schedule_continuous_delivery`), effectively letting one tenant dictate the deploy timing of another tenant's stack.
- Other handlers keyed the same way (e.g. `status`, `check_suite`, `membership`, `pull_request/*`) can similarly be pointed at a victim's repository/stack to create bogus commit statuses/check-runs, archive/unarchive review stacks, or manipulate PR labels/state for a repository the attacker does not control — a cross-tenant/cross-repository write.

This matches the "unauthorized deploy" / "cross-repository writes" impact bar because the binding broken is exactly "an organization that authenticated versus the repository that is written."

### Likelihood Explanation
Requires the attacker to be an operator of at least one legitimately configured organization on a multi-org Shipit deployment (i.e., they must know that org's own `webhook_secret`) — this is a realistic, non-privileged-to-Shipit-itself scenario since these secrets are typically distributed to each integrated org's own GitHub App owner, not centrally guarded from other tenants. No access to the victim org's secret, to a Shipit session, or to an `ApiClient` token is needed. This is only reachable when the multi-organization configuration (`secrets.github.<org>`) is used, which is a documented, supported deployment mode.

### Recommendation
Bind the field used for authentication to the field used for mutation: after verifying the signature for `repository_owner`, validate that `repository.full_name`'s owner segment (or the resolved `Repository#owner`) equals the authenticated `repository_owner`/`organization` before dispatching to handlers, and reject the webhook otherwise.

### Proof of Concept
1. Shipit is configured with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and each has a Stack tracking a repository in their respective org.
2. An operator of `OrgOne` (who knows `OrgOne`'s `webhook_secret`) crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Compute `X-Hub-Signature` using `OrgOne`'s webhook secret over the raw body and POST it to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully verifies the signature with `OrgOne`'s secret. [1](#0-0) 
5. `PushHandler` resolves stacks via `Repository.from_github_repo_name("OrgTwo/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgTwo`'s stack, even though the signature was never validated for `OrgTwo`. [4](#0-3) [5](#0-4)

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
