### Title
Missing Content Validation for P2P-Delivered `StakingInfo` Allows Malicious Peer to Corrupt Validator Reward Database — (`datasync/downloader/queue.go`)

---

### Summary

During fast-sync and staking-info recovery, `P2PStakingInfo` objects received from remote peers are accepted and written to the local database with **zero content validation**. Every other comparable delivery path (`DeliverBodies`, `DeliverReceipts`) cryptographically verifies the received data against the corresponding block header before accepting it. The staking-info path carries an explicit `// TODO-Kaia-Snapsync update validation logic` comment and unconditionally returns `nil`. A malicious peer can therefore inject arbitrary validator addresses and staking amounts that are then persisted and used for proposer selection and KAIA reward distribution.

---

### Finding Description

`queue.DeliverStakingInfos` in `datasync/downloader/queue.go` defines a `validate` closure that always returns `nil`:

```go
validate := func(index int, header *types.Header) error {
    // TODO-Kaia-Snapsync update validation logic
    return nil
}
``` [1](#0-0) 

Compare this to the analogous closures for bodies and receipts, which both verify the delivered data against the committed block header:

```go
// DeliverBodies
validate := func(index int, header *types.Header) error {
    if types.DeriveTransactionsRoot(types.Transactions(txLists[index]), header.Number) != header.TxHash {
        return errInvalidBody
    }
    ...
}
``` [2](#0-1) 

```go
// DeliverReceipts
validate := func(index int, header *types.Header) error {
    if types.DeriveReceiptsRoot(types.Receipts(receiptList[index]), header.Number) != header.ReceiptHash {
        return errInvalidReceipt
    }
    return nil
}
``` [3](#0-2) 

The accepted (unvalidated) `StakingInfo` is then written directly to the persistent database in two places:

**Fast-sync commit path:**
```go
if result.StakingInfo != nil {
    d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))
}
``` [4](#0-3) 

**Staking-info recovery path (`SyncStakingInfo`):**
```go
d.stakingModule.PutStakingInfoToDB(stakingInfo.BlockNum, staking.ToStakingInfo(stakingInfo))
``` [5](#0-4) 

The recovery path does check `stakingInfo.BlockNum` against the expected sequence, but does **not** verify the content (validator addresses, staking amounts, fund addresses) against any on-chain commitment:

```go
if d.stakingInfoRecoveryBlocks[0] != stakingInfo.BlockNum {
    logger.Error("failed to receive expected block", ...)
    return
}
``` [6](#0-5) 

The P2P entry point `handleStakingInfoMsg` decodes the message and forwards it directly to the downloader without any pre-filtering:

```go
var stakingInfos []*staking.P2PStakingInfo
if err := msg.Decode(&stakingInfos); err != nil {
    return errResp(ErrDecode, "msg %v: %v", msg, err)
}
if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
    logger.Debug("Failed to deliver staking information", "err", err)
}
``` [7](#0-6) 

---

### Impact Explanation

The persisted `StakingInfo` is the authoritative source for:

1. **Proposer selection** (pre-Kaia fork, `WeightedRandom` policy) — staking amounts determine how often each validator appears in the proposer list.
2. **KAIA reward distribution** — `assignStakingRewards` / `assignStakingRewardsFlex` distribute block rewards proportionally to staking amounts stored in `StakingInfo`. [8](#0-7) 

If a malicious peer injects `StakingInfo` with fabricated `CouncilStakingAmounts` or `CouncilRewardAddrs`, the syncing node will:

- Distribute KAIA block rewards to wrong addresses or in wrong proportions for all affected historical blocks when those blocks are re-executed (e.g., during a reorg or state regeneration).
- Select wrong proposers for historical blocks, causing the node to reject valid blocks from honest peers and accept invalid ones, producing **consensus divergence**.

The `StakingInfo` database is only consulted for pre-Kaia-fork blocks (`!isKaia` path in `GetStakingInfo`); post-Kaia blocks derive staking info from state. However, fast-sync nodes routinely sync through the pre-Kaia history, and the `SyncStakingInfo` admin API is explicitly restricted to pre-Kaia blocks. [9](#0-8) 

---

### Likelihood Explanation

- **Fast-sync path**: Any peer the syncing node connects to can serve staking-info responses. No privilege is required; a malicious node simply needs to be reachable and respond to `StakingInfoRequestMsg`.
- **Recovery path**: Requires the operator to call `SyncStakingInfo` with a peer ID, but the peer itself is semi-trusted (any registered P2P peer qualifies).
- The attack window is the entire fast-sync duration, which can span thousands of blocks.

---

### Recommendation

Implement content validation in `queue.DeliverStakingInfos` analogous to `DeliverBodies` and `DeliverReceipts`. The canonical approach is to re-derive a commitment from the received data and compare it against a field in the block header. If no such header field exists today, one option is to hash the canonical JSON/RLP encoding of the `StakingInfo` and compare it against a value derivable from the block state root (e.g., by calling `GetStakingInfo` locally for the same block and comparing). At minimum, the `BlockNum` field should be cross-checked against the header number of the corresponding task slot, and the array lengths (`CouncilNodeAddrs`, `CouncilStakingAddrs`, `CouncilRewardAddrs`, `CouncilStakingAmounts`) should be verified for consistency before the data is accepted.

---

### Proof of Concept

**Attack flow (fast-sync path):**

1. Attacker runs a Kaia node and connects to a victim node that is fast-syncing.
2. Victim node sends `StakingInfoRequestMsg` for block hashes `[H1, H2, ...]`.
3. Attacker's `handleStakingInfoRequestMsg` is bypassed; instead the attacker's node directly responds with a crafted `StakingInfoMsg` containing `P2PStakingInfo` objects where `CouncilRewardAddrs` are replaced with attacker-controlled addresses and `CouncilStakingAmounts` are inflated.
4. Victim's `handleStakingInfoMsg` decodes the message and calls `pm.downloader.DeliverStakingInfos`.
5. `queue.DeliverStakingInfos` calls `validate(...)` which returns `nil` unconditionally.
6. `result.StakingInfo` is set to the malicious data.
7. `commitFastSyncData` calls `d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))`.
8. The victim's staking DB now contains attacker-controlled validator addresses and amounts for the affected blocks.
9. On any subsequent state re-execution of those blocks, `assignStakingRewards` distributes KAIA to the attacker's addresses, producing a different state root than the canonical chain, causing the victim node to diverge. [10](#0-9) [11](#0-10)

// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
}

func (s *StakingModule) GetStakingInfo(num uint64) (*staking.StakingInfo, error) {
	isKaia := s.ChainConfig.IsKaiaForkEnabled(new(big.Int).SetUint64(num))
	sourceNum := sourceBlockNum(num, isKaia, s.stakingInterval)

	// Try cache first
	if si, ok := s.stakingInfoCache.Get(sourceNum); ok {
		return si.(*staking.StakingInfo), nil
	}

	// Only before Kaia, try the database
	if !isKaia {
		if si := ReadStakingInfo(s.ChainKv, sourceNum); si != nil {
			s.stakingInfoCache.Add(sourceNum, si)
			return si, nil
		}
	}

	// Read from the state
	si, err := s.getFromStateByNumber(sourceNum)
	if err != nil {
		return nil, err
	}

	// Only before Kaia, write to database
	if !isKaia {
		WriteStakingInfo(s.ChainKv, sourceNum, si)
	}

	// Cache it
	s.stakingInfoCache.Add(sourceNum, si)
	return si, nil
}
