### Title
Team founder can set an unbounded `founder_tax` at team creation to drain contributors' winnings or permanently freeze payouts - ([File: test/samples/51_attack_game.oscript])

### Summary
In the `51_attack_game.oscript` AA, any unprivileged trigger sender can create a "team" and set an arbitrary `founder_tax` value via `trigger.data.founder_tax` with no validation on its range. This value is later used unmodified to compute each contributor's payout share when that team wins, allowing the founder to set a tax that either siphons almost all of the team's winnings to himself or causes payout computations to go negative, bouncing (freezing) legitimate contributors' withdrawals — directly analogous to the referenced "market owner can set high fee" issue where an unbounded, user-settable fee parameter is used later to compute value transfers with no upper/lower bound enforcement.

### Finding Description
When a team is created, the founder tax is stored straight from trigger data with no bound check: [1](#0-0) 

```
{
	app: 'state',
	state: `{
		var['team_' || trigger.address || '_founder_tax'] = trigger.data.founder_tax otherwise 0;
		var['team_' || trigger.address || '_asset'] = response_unit;
		response['team_asset'] = response_unit;
	}`
}
```

There is no check that `founder_tax` is within `[0,1)` (or any sane range) — unlike the `setMarketFeePercent` analog in the referenced report where a similarly unbounded fee is later applied against user funds without validation. It is a free-form number supplied by the calling address (the "market owner"/team founder equivalent) at team-creation time, and is persisted as an immutable-looking state var that governs future fund distribution for every other contributor who later joins that team.

When the team eventually wins, the payout formula directly consumes this unvalidated value: [2](#0-1) 

```
{ // pay out the winnings
	if: `{ ... $asset_amount > 0}`,
	init: `{
		$share = $asset_amount / var['team_' || $winner || '_amount'];
		$founder_tax = var['team_' || $winner || '_founder_tax'];
		$amount = round(( $share * (1-$founder_tax) + (trigger.address == $winner AND !var['founder_tax_paid'] ? $founder_tax : 0) ) * var['total']);
	}`,
	messages: [
		{
			app: 'payment',
			payload: {
				asset: "base",
				outputs: [
					{address: "{trigger.address}", amount: "{$amount}"}
				]
			}
		},
		...
	]
}
```

Contributors join a team ("contribute to a team") after the team is created, at which point the founder tax is already fixed and hidden inside a state var they have no visibility or control over on-chain before contributing: [3](#0-2) 

Because `founder_tax` is unbounded:
- The founder can set `founder_tax` close to `1` (e.g. `0.999999`), causing `$share * (1-$founder_tax)` for ordinary contributors to shrink to nearly zero while the founder's own claim term `$founder_tax * var['total']` captures almost the entire pot — draining nearly all of the contributors' principal and winnings to the founder, exactly mirroring the "market owner can set high fee" pattern where an unbounded, self-serving fee is charged against counterparties' funds.
- The founder can also set `founder_tax > 1` or negative, making `(1-$founder_tax)` negative or the overall `$amount` computation produce a negative payout amount. A negative payment output amount is invalid and the AA response will bounce, meaning any contributor attempting to redeem their winning-team shares permanently fails — freezing all contributors' funds in the AA with no path to recovery, since the payout branch is the only exit route once `var['finished']` is set.

### Impact Explanation
This causes concrete unauthorized value transfer/fund loss: contributors who paid Bytes to join a winning team can have nearly 100% of their expected winnings redirected to the founder via an unbounded `founder_tax`, or have their payout entirely and permanently blocked (fund freezing) if the founder sets a tax value that drives the computed payout negative. Both outcomes fall squarely under "concrete unauthorized spending" and "AA fund loss or freezing."

### Likelihood Explanation
Likelihood is high: creating a team and setting `founder_tax` is a normal, unrestricted action available to any address via `trigger.data.create_team` and `trigger.data.founder_tax`; no privileged role or special access is required, and nothing in the AA definition validates the tax value's range before it's persisted and later applied to compute payouts, so a malicious team creator can trivially exploit unsuspecting contributors who join based on an advertised (but unenforced) tax rate.

### Recommendation
Validate `founder_tax` at team-creation time to enforce a sane bound (e.g. `0 <= founder_tax < 1`), bouncing the trigger if the value is outside that range, so contributors can trust the persisted tax rate cannot be manipulated into an unbounded value that drains their winnings or bricks the payout path.

### Proof of Concept
1. Attacker calls the AA with `{create_team: true, founder_tax: 0.999999}` and pays the `$team_creation_fee`; the AA stores this value unchecked at [4](#0-3) .
2. Victims contribute Bytes to this team via `{team: <founder_address>}`, unaware the tax will later strip nearly all their share, per [5](#0-4) .
3. The team reaches 51% and wins; `finish` is triggered, setting `var['total'] = balance[base]` at [6](#0-5) .
4. Each victim redeems shares; the payout formula at [7](#0-6)  computes `$amount ≈ $share * 0.000001 * total`, transferring virtually nothing to victims while the founder claims `founder_tax * total` (~99.9999% of the pool) via the same formula's founder-only term.
5. Alternatively, setting `founder_tax` to a value `>1` makes `$amount` negative for non-founder redemptions, causing the payment message to fail validation and permanently freezing those contributors' funds.
