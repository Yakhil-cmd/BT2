### Title
Asset definer can unilaterally freeze all `spender_attested` asset holders' funds via attestor-list replacement - ([File: validation.js])

### Summary
Any Obyte asset can be created with `spender_attested: true`, delegating to the asset's *definer* the sole authority to decide, at any later time and with a single self-signed message, which addresses are allowed to hold/spend that asset. Because the check re-reads only the *latest* attestor list at validation time and the check applies to every future transfer (not just issuance), the definer can post a single `asset_attestors` message that drops all existing holders from the list. From that point on, none of the existing coin owners can spend their balance, and outputs can no longer be sent to any address the definer has not (re)attested — permanently freezing the funds of every unattested holder. This mirrors the Folio "Owner can remove tokens from basket" pattern: a single privileged party makes a post-issuance change that unilaterally destroys value/liquidity for all other participants, without any code upgrade or multi-party consent.

### Finding Description
When an asset is defined with `spender_attested: true`, `storage.readAsset()` looks up only the most recently published attestor list for that asset: [1](#0-0) 

`validatePayment()`/`validatePaymentInputsAndOutputs()` then require every *input* owner and every *output* address of a transfer to be currently attested according to that same latest list: [2](#0-1) [3](#0-2) 

Also enforced per-input for private/fixed-denomination transfers: [4](#0-3) 

The attestor list itself can be replaced at any time, by the definer alone, via an `asset_attestors` message, whose only authorization check is that the sender is the asset's `definer_address`: [5](#0-4) 

The list-content check (`checkAttestorList`) only requires a non-empty, sorted, valid-address array — it does not require the new list to be a superset of the old one, nor does it require consent from existing holders: [6](#0-5) 

Consequently, a definer can:
1. Issue a public/transferrable asset with `spender_attested: true` and an initial attestor list that makes the asset look broadly usable (e.g., attesting many addresses or a reputable third-party attestor).
2. Let users acquire and hold the asset through normal transfers.
3. Post a single `asset_attestors` unit that replaces the list with just the definer's own attestor address, and stop attesting any address other than its own.
4. From the next unit onward, `filterAttestedAddresses`/`arrAttestedAddresses` will no longer include existing holders, so `validatePaymentInputsAndOutputs` will reject any transfer whose input owner or output address is not in the new list — freezing every existing holder's balance in place.

This is a single-signature, code-unchanged action (no consensus, no AA logic, no multisig) that destroys the fungibility/liquidity of the asset for everyone except the definer, exactly analogous to a "Role::Owner" being able to unilaterally rug the value backing other participants' holdings.

### Impact Explanation
All holders of a `spender_attested` asset can have their funds permanently frozen (unspendable, unable to receive change or new transfers) by a single message from the asset definer. This is a concrete fund-freezing impact reachable by an ordinary asset issuer/definer role — no network-level compromise, no operator/hub privilege, and no code change to the protocol is required. Because the check is enforced on every transfer (not only issuance), the blast radius covers the entire circulating supply at the time of the attack, not just newly issued coins.

### Likelihood Explanation
The precondition (asset created with `spender_attested: true`) is entirely at the definer's discretion when creating the asset, and nothing in the protocol warns holders that the attestor list — and thus their ability to ever move the coins again — can be revoked after they've acquired the asset through ordinary transfers. Any asset issuer wishing to exit-scam holders (e.g., after building up adoption of a `spender_attested` token) can execute this with a single `asset_attestors` unit, making the attack straightforward and low-cost to carry out.

### Recommendation
- Document explicitly (in asset/attestation documentation and wallet UI) that `spender_attested` assets grant the definer perpetual, unilateral power to revoke any holder's ability to transact, not just to gate initial issuance, and that this authority is *not* limited to newly acquired coins.
- Consider requiring wallets to flag/warn users when acquiring a `spender_attested` asset that the definer can later remove them from the attestor list, freezing already-held balances.
- Consider a protocol-level option to "grandfather" already-attested holders (e.g., snapshotting attested addresses at time of a given output's creation) so that revocations only affect future issuance/transfers rather than retroactively freezing existing balances.

### Proof of Concept
1. Definer `D` creates asset `A` with `is_transferrable: true`, `is_private: false`, `spender_attested: true`, and an initial `attestors` list `[D]`, then attests several user addresses (`U1`, `U2`, ...) via `attestation` messages from `D` — see the mechanics in `validateAssetDefinition`: [7](#0-6) .
2. `D` issues asset `A` to `U1..Un`, who transact normally; `validatePayment` currently allows this because `arrAttestedAddresses` includes them (via `filterAttestedAddresses`): [8](#0-7) .
3. `D` posts a single `asset_attestors` unit for asset `A` with `attestors: [D]` only (dropping the old attestations), which passes `validateAttestorListUpdate` because only `objUnit.authors[0].address === objAsset.definer_address` is checked: [9](#0-8) .
4. Any subsequent attempt by `U1..Un` to spend their existing balance of `A` fails validation, since `readAsset`/`filterAttestedAddresses` now returns only `D`'s attested set, and both input owners and output addresses must be in that set: [10](#0-9) . The previously-issued balances are permanently stuck.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
