### Title
Unvalidated, immutable `pool_creator` assignment in `initialize_with_permission` permanently freezes creator fees - (File: programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize_with_permission` sets the pool's `pool_creator` field from an `UncheckedAccount` supplied by the transaction signer (`payer`), with no requirement that the designated `creator` sign, confirm, or otherwise verify the assignment, and with no subsequent instruction to correct it. This is the same "single irrevocable critical operation without a two-step confirmation" pattern flagged in the source report for `VotingEscrow.transfer_ownership`: a permanently binding, security-critical address field is set in one unchecked call.

### Finding Description
In `initialize_with_permission`, the `creator` account is declared as an `UncheckedAccount`, not a `Signer`: [1](#0-0) 

The payer (a distinct `Signer`) drives the whole instruction and can pass any pubkey for `creator`: [2](#0-1) 

That value is written straight into `pool_state.pool_creator` in a single, one-shot call with no confirmation step: [3](#0-2) [4](#0-3) 

There is no instruction in the program to later update `pool_creator` — a search across the codebase shows it is only ever read in `states/pool.rs`, `collect_creator_fee.rs`, and `collect_creator_fee_permissionless.rs`, never reassigned after `initialize`. Once set, `pool_creator` permanently gates who benefits from creator fees:
- `collect_creator_fee` requires the signer to equal `pool_state.pool_creator`: [5](#0-4) 
- `collect_creator_fee_permissionless` always routes funds to the ATA of the recorded `pool_creator`, regardless of who calls it: [6](#0-5) 

Because `creator` is never validated against `payer`, never required to sign, and never confirmable/updatable afterward, a single mistaken account (e.g., a PDA with no controlling key, a typo'd address, an account owned by another program, or the System Program ID) permanently locks the pool's creator-fee stream: it accrues in `creator_fees_token_0`/`creator_fees_token_1` inside the vaults but can never be withdrawn by anyone, since `collect_creator_fee` cannot be signed by an uncontrollable address and `collect_creator_fee_permissionless` will keep trying to mint/transfer to an ATA whose owner cannot claim it.

### Impact Explanation
This causes permanent freezing of a real, growing fund balance (accumulated creator fees held in the pool's token vaults) with no recovery path in-protocol — matching the "unbacked/insolvent accounting or permanent freezing of user/LP funds" bar. The frozen fees also distort `vault_amount_without_fee` accounting used throughout swap/deposit/withdraw math, since `creator_fees_token_0/1` are subtracted from vault balances indefinitely: [7](#0-6) 

### Likelihood Explanation
This requires only a normal permissioned pool-creation transaction (any account holding a valid `permission` PDA can call `initialize_with_permission`), constructed with attacker/mistake-chosen `creator` account data — no privileged signer, no runtime bug, and no off-chain dependency is needed. A malicious or careless integrator/front-end could set `creator` to any address (including one the payer doesn't control) in the exact same single transaction that creates the pool, with no on-chain warning or later correction mechanism.

### Recommendation
Require `creator` to either be identical to `payer`/an explicit `Signer` at pool creation, or implement a two-step handshake: record a `pending_creator` at initialization and require that pending address to sign a separate `accept_creator_role` instruction before `pool_creator` becomes active for fee collection. This mirrors the report's short-term recommendation of a two-step procedure for non-recoverable critical operations.

### Proof of Concept
1. Attacker (or a careless UI) obtains a valid `permission` PDA for `payer` via `create_permission_pda`.
2. Attacker calls `initialize_with_permission` with `payer` as signer, `token_0_mint`/`token_1_mint`, and sets the `creator` account to an address they do not control (e.g., a PDA of an unrelated program, or a random keypair whose private key is discarded).
3. `pool_state.pool_creator` is permanently set to that address via `PoolState::initialize`: [3](#0-2) 
4. As swaps occur on this pool, `creator_fees_token_0`/`creator_fees_token_1` accrue in `pool_state` (tracked separately from protocol/fund fees) but neither `collect_creator_fee` (needs `creator` to sign) nor `collect_creator_fee_permissionless` (sends to `creator`'s ATA) can ever release funds to a party with access, permanently freezing that portion of the vault balances.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
