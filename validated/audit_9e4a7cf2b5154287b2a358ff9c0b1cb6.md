### Title
Missing `nonReentrant` Guard on `handleERC20Transfer` and `handleERC721Transfer` Enables Re-entrancy via Token Callbacks — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`handleKLAYTransfer` carries the `nonReentrant` modifier, but the structurally identical `handleERC20Transfer` and `handleERC721Transfer` do not. Both functions make external calls to token contracts after updating bridge state. If a registered ERC20 token has transfer-hook semantics (e.g., ERC777-style `tokensReceived`), the hook can call back into the bridge's unguarded `onERC20Received` entry point during the same execution frame, emitting a spurious `RequestValueTransfer` event that causes the counterpart bridge to release tokens on the other chain without a legitimate cross-chain request.

---

### Finding Description

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` explicitly carries `nonReentrant` because it makes a raw `.call.value()` to `_to`:

```solidity
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
    ...
    (bool ok, ) = _to.call.value(_value)("");
``` [1](#0-0) 

`handleERC20Transfer` follows the same pattern — state updates first, external call last — but the `nonReentrant` modifier is absent:

```solidity
function handleERC20Transfer(...) public onlyOperators {   // ← no nonReentrant
    ...
    _updateHandleNonce(_requestedNonce);
    emit HandleValueTransfer(...);
    if (modeMintBurn) {
        require(ERC20Mintable(_tokenAddress).mint(_to, _value), ...);
    } else {
        IERC20(_tokenAddress).safeTransfer(_to, _value);   // ← external call
    }
}
``` [2](#0-1) 

`handleERC721Transfer` has the same omission:

```solidity
function handleERC721Transfer(...) public onlyOperators {  // ← no nonReentrant
    ...
    _updateHandleNonce(_requestedNonce);
    emit HandleValueTransfer(...);
    if (modeMintBurn) {
        require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(...), ...);
    } else {
        IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId); // ← external call
    }
}
``` [3](#0-2) 

The re-entrancy entry point is `onERC20Received`, which is `public` with no access control beyond the implicit `onlyRegisteredToken` check inside `_requestERC20Transfer`:

```solidity
function onERC20Received(address _from, address _to, uint256 _value,
                         uint256 _feeLimit, bytes memory _extraData) public {
    _requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
}
``` [4](#0-3) 

`_requestERC20Transfer` only requires `msg.sender` to be a registered token (`onlyRegisteredToken`). If the registered token has ERC777-style transfer hooks, the hook fires on `_to` during `safeTransfer`, and `_to` can call `bridge.onERC20Received(...)` back. Because `msg.sender` at that point is the registered token, the `onlyRegisteredToken` guard passes, and the function emits a new `RequestValueTransfer` event and increments `requestNonce`. [5](#0-4) 

---

### Impact Explanation

The spurious `RequestValueTransfer` event emitted during re-entrancy is indistinguishable from a legitimate cross-chain request. Counterpart bridge operators observe it and call `handleERC20Transfer` on the counterpart chain, releasing tokens there. The result is an unauthorized token release on the counterpart chain — a double-spend of bridged assets — without any corresponding lock or burn on the originating chain.

The corrupted value is: `requestNonce` is incremented by one extra unit, and a `RequestValueTransfer` log is written to the receipt with attacker-controlled `_to` and `_value` fields, causing the counterpart bridge to transfer `_value` tokens to `_to` on the other chain.

---

### Likelihood Explanation

The attack requires:
1. A registered ERC20 token with transfer-hook semantics (ERC777 or a custom token with `onTransfer` callbacks). Token registration is owner-controlled, but ERC777 tokens are common and backward-compatible with ERC20.
2. The `_to` address passed by the operator to be a contract whose hook calls `bridge.onERC20Received(...)`.

If the operator is honest but the registered token is ERC777 and `_to` is a contract with a `tokensReceived` hook that calls back into the bridge (e.g., a DeFi contract designed to auto-bridge received tokens), the re-entrancy fires without any malicious intent. The inconsistency with `handleKLAYTransfer` (which is guarded) shows the risk was recognized for KLAY but not applied uniformly.

---

### Recommendation

Add `nonReentrant` to both `handleERC20Transfer` and `handleERC721Transfer`, mirroring the existing guard on `handleKLAYTransfer`:

```solidity
function handleERC20Transfer(...) public onlyOperators nonReentrant {
```

```solidity
function handleERC721Transfer(...) public onlyOperators nonReentrant {
```

`BridgeTransferERC20` and `BridgeTransferERC721` do not currently inherit `ReentrancyGuard`. They should be updated to inherit it (as `BridgeTransferKLAY` already does via its inheritance chain), or the guard should be added to the shared `BridgeTransfer` base contract. [6](#0-5) 

---

### Proof of Concept

```
Setup:
  - Deploy Bridge in non-mintBurn mode.
  - Register a malicious ERC777-compatible token (MalToken) that, on transfer,
    calls bridge.onERC20Received(from, attacker, stolenAmount, 0, "") on the recipient.
  - Set _to = AttackerContract, which implements tokensReceived() to call
    bridge.onERC20Received(MalToken, attacker, stolenAmount, 0, "").

Attack:
  1. Operator calls bridge.handleERC20Transfer(txHash, from, AttackerContract,
       MalToken, value, nonce, blockNum, "").
  2. Bridge updates state: closedValueTransferVotes[nonce] = true, nonces updated.
  3. Bridge calls MalToken.safeTransfer(AttackerContract, value).
  4. MalToken fires tokensReceived() on AttackerContract.
  5. AttackerContract calls bridge.onERC20Received(MalToken, attacker,
       stolenAmount, 0, "").
  6. _requestERC20Transfer passes onlyRegisteredToken (msg.sender = MalToken).
  7. Bridge emits RequestValueTransfer(ERC20, MalToken, attacker, stolenAmount,
       requestNonce, 0, "").
  8. requestNonce++.
  9. Counterpart bridge operators observe the event and call handleERC20Transfer
       on the counterpart chain, releasing stolenAmount tokens to attacker.

Result:
  - Attacker receives stolenAmount tokens on the counterpart chain with no
    corresponding lock/burn on the originating chain.
  - requestNonce is corrupted by +1, desynchronizing the bridge nonce sequence.
```
