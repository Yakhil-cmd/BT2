### Title
Hookify frontmatter parser silently drops indented `action: block` keys, downgrading deny rules to warn/ignore - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` is a hand-rolled YAML-like parser that only recognizes a top-level `key: value` line when its indentation is exactly `0`. A rule file whose `action: block` line is indented by 1–2 spaces (visually indistinguishable from a correct file in a diff/markdown render) is silently dropped by the parser, so `Rule.from_dict` falls back to its default `action = "warn"` [1](#0-0) . This breaks the invariant that a deny rule (`action: block`) must always be enforced as blocking.

### Finding Description
`extract_frontmatter` splits frontmatter lines and, for each line, decides how to interpret it based on `indent = len(line) - len(line.lstrip())`: [2](#0-1) 

Only three branches exist: `indent == 0` for top-level keys, `stripped.startswith('-') and in_list` for list items, and `indent > 2 and in_dict_item` for nested dict-item continuation lines [3](#0-2) . Any line with `indent` equal to 1 or 2 that is not a list item and not inside a dict-item context matches none of these branches and is **silently discarded** — no error, no warning.

`Rule.from_dict` reads the action with a permissive default:
```
action=frontmatter.get('action', 'warn'),
``` [4](#0-3) 

so if the `action: block` key is dropped by the parser, the resulting `Rule.action` silently becomes `"warn"`. `RuleEngine.evaluate_rules` treats `action == 'block'` as the only blocking condition; anything else is put into `warning_rules`, which only emits a `systemMessage` and **allows** the operation to proceed [5](#0-4) .

Exploit flow:
1. An unprivileged contributor (e.g. via a PR, a shared `.claude/` template, or content produced through `/hookify`, whose command spec at `plugins/hookify/commands/hookify.md` instructs the LLM to literally write `action: {warn|block}` frontmatter lines [6](#0-5) ) introduces or edits a `.claude/hookify.<name>.local.md` file intended to *block* a dangerous action (e.g. exfiltrating `.env` secrets via `cat`, `curl`, etc.).
2. The file visibly reads `action: block`, but the line carries 1–2 leading spaces (trivial to introduce accidentally in an LLM-generated file, or deliberately hidden in a reviewed diff, since single/double-space indentation differences are easy to overlook and are not flagged by any linter here).
3. `load_rule_file` → `extract_frontmatter` silently drops that line; no exception is raised, and `load_rules` treats the malformed-but-present frontmatter as valid (unlike the fully-missing-frontmatter case which does emit a warning) [7](#0-6) .
4. The parsed `Rule.action` becomes `"warn"` even though the file, and any human reviewer, would say `block`.
5. On the next matching dangerous tool call (`Bash`, `Edit`, etc.), `pretooluse.py`/`posttooluse.py` load this rule via `load_rules` and evaluate it through `RuleEngine`; since `action != 'block'`, the operation is **allowed** with only a warning message, defeating the intended guardrail and enabling the dangerous command (e.g., secret exfiltration, sensitive file read/exfil) to execute [8](#0-7) .

No existing validation catches this: there is no schema check, no re-serialization/round-trip verification, and errors from parsing are only surfaced for I/O/type exceptions, not for silently-dropped keys [9](#0-8) .

### Impact Explanation
A rule file that is supposed to hard-block a dangerous or sensitive operation (reading `.env`, `cat`-ing credentials, running `curl` to exfiltrate data, etc.) silently degrades to a non-blocking warning due to a parser indentation bug, and the attacker-controlled/malformed file still visually appears to specify `action: block`. This directly maps to the described Immunefi impact class: "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink," because the deny rule that would have stopped the dangerous tool call from running is neutralized while looking intact to reviewers/maintainers who trust the file content at face value.

### Likelihood Explanation
No admin/maintainer privilege, leaked credentials, or social engineering is required beyond the ability to introduce or modify a `.claude/hookify.*.local.md` file (e.g., via a contributed PR, a shared config template, or content generated by `/hookify` itself). The bug is deterministic and trivially reproducible: any `action:` line indented with exactly 1 or 2 spaces reliably fails to parse. Because `/hookify`'s own generation instructions are simple text templates [6](#0-5) , an LLM or a human editing the file can easily introduce or hide this whitespace discrepancy without any tooling flagging it as invalid.

### Recommendation
Replace the hand-rolled indentation-sensitive frontmatter parser with a strict, well-tested YAML parser (e.g., `yaml.safe_load`) that fails loudly (raises) on malformed structure rather than silently dropping keys. At minimum:
- Treat any line with `1 <= indent <= 2` (i.e., not matching any recognized branch) as a parse error, and reject the whole rule file (fail closed) rather than silently proceeding with default field values.
- For `action`, do not default to `'warn'` when the frontmatter is malformed/incomplete — require the field to be explicitly present and valid, and reject (drop and log loudly) rule files where required fields fail to parse cleanly.
- Add a round-trip/self-check: after parsing, re-serialize and diff against a strict YAML parse to detect divergence, or simply switch to PyYAML entirely to eliminate this class of bug.

### Proof of Concept
Unit test to add to a test suite exercising `plugins/hookify/core/config_loader.py`:
```python
from hookify.core.config_loader import extract_frontmatter, Rule

def test_indented_action_block_is_not_dropped():
    content = """---
name: block-env-read
enabled: true
event: bash
 action: block
pattern: cat\\s+\\.env
---

Blocked: attempted to read .env secrets.
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # EXPECTED (secure) behavior: action must still be 'block'
    assert rule.action == 'block', (
        f"Deny rule was silently downgraded to '{rule.action}' due to "
        f"1-space indentation on 'action: block' line"
    )
```
Running this against the current implementation fails: `frontmatter` does not contain the `action` key at all (the ` action: block` line, indent=1, matches none of the parser's branches), so `rule.action` evaluates to the default `"warn"`, confirming the block→warn downgrade.

Integration-level validation: place the same malformed file at `.claude/hookify.block-env-read.local.md` in a cloned repo, invoke `plugins/hookify/hooks/pretooluse.py` with a `Bash` tool call `{"tool_name": "Bash", "tool_input": {"command": "cat .env"}}` on stdin, and assert that the hook's JSON output does **not** contain `"permissionDecision": "deny"` (only a `systemMessage` is emitted), demonstrating the dangerous command is allowed to execute despite the file's stated intent to block it.

def load_rule_file(file_path: str) -> Optional[Rule]:
    """Load a single rule file.

    Returns:
        Rule object or None if file is invalid.
    """
    try:
        with open(file_path, 'r') as f:
            content = f.read()

        frontmatter, message = extract_frontmatter(content)

        if not frontmatter:
            print(f"Warning: {file_path} missing YAML frontmatter (must start with ---)", file=sys.stderr)
            return None

        rule = Rule.from_dict(frontmatter, message)
        return rule

    except (IOError, OSError, PermissionError) as e:
        print(f"Error: Cannot read {file_path}: {e}", file=sys.stderr)
        return None
    except (ValueError, KeyError, AttributeError, TypeError) as e:
        print(f"Error: Malformed rule file {file_path}: {e}", file=sys.stderr)
        return None

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)
