## Title
Webhook signature verified against attacker-chosen `repository.owner.login`/`organization.login`, but handlers act on the independent `repository.full_name` field — cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the `X-Hub-Signature` against using an org name pulled straight out of the untrusted JSON body, while the handlers that actually act on the payload resolve the target `Stack`/`Repository` from a completely different, also attacker-controlled field in the same body. When any configured org has no `webhook_secret` (an explicitly documented, optional setting), signature verification is bypassed for that org selector, but the payload can still name any other repository as the target of the event.

### Finding Description
`verify_signature` picks the GitHub App/secret to check with: [1](#0-0) 
where `repository_owner` is read directly from the request body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally passes verification whenever that resolved org has no secret configured: [3](#0-2) 

This is a documented, supported configuration — the webhook secret is explicitly optional per-organization: [4](#0-3) [5](#0-4) 

Once the request clears `verify_signature`, `create` dispatches the *entire, unmodified* raw payload to the event handlers: [6](#0-5) 

Every handler resolves its target `Stack` using `repository.full_name` — a field that is never cross-checked against the `repository.owner.login`/`organization.login` value used for signature selection: [7](#0-6) 

For example, `PushHandler` will sync/deploy any stack whose repository matches `full_name`: [8](#0-7) 

**Broken binding**: `organization used to authenticate the signature (repository_owner) == repository the handler writes to (repository.full_name)`. This equality is never enforced — the two fields are independently attacker-controlled within a single JSON body, so they can point at different orgs/repositories entirely.

### Impact Explanation
An attacker who knows (or registers/controls) any GitHub organization configured in Shipit's `github:` map *without* a `webhook_secret` can send a forged webhook whose `repository.owner.login`/`organization.login` names that unsecured org (satisfying `verify_webhook_signature`'s early `return true unless webhook_secret`) while `repository.full_name` names a genuinely protected repository/stack. This lets the attacker inject arbitrary, unauthenticated `push`, `status`, `check_suite`, or `pull_request` events for stacks belonging to organizations that *do* have webhook secrets configured. Depending on the target stack's configuration (continuous deployment enabled, merge queue automation), this can drive `stack.sync_github(expected_head_sha:)` to pull and potentially auto-deploy an attacker-chosen commit SHA, or manipulate merge-queue state via forged `check_suite`/`status` payloads — resulting in an unauthorized deploy or merge with no session, API token, or GitHub write access required.

### Likelihood Explanation
Requires only that a multi-org Shipit deployment leaves at least one configured organization's `webhook_secret` blank — an explicitly supported/optional setting per `docs/setup.md` and the example secrets templates — and that the attacker knows that org's name. No credential, GitHub App key, or Shipit session is needed; the request goes to the public `/webhooks` endpoint.

### Recommendation
Bind the signature-verification org strictly to the same field the handlers use to select the target repository/stack (`repository.full_name`'s owner segment), and reject the request if `repository.owner.login`/`organization.login` does not match the owner encoded in `repository.full_name`. Additionally, consider refusing verification (rather than defaulting to `true`) when no `webhook_secret` is configured for an organization that owns real stacks, or require a secret for every configured org.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `orgNoSecret` (no `webhook_secret`) and `orgWithStack` (has a stack and a `webhook_secret`).
2. POST to `/webhooks` with header `X-Github-Event: push`, an arbitrary/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "orgNoSecret" }, "full_name": "orgWithStack/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha in orgWithStack/target-repo>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgNoSecret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus signature.
4. `PushHandler` resolves `Repository.from_github_repo_name("orgWithStack/target-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker sha>")`, triggering sync/deploy logic for a stack the attacker never authenticated against.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
