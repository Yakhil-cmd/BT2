### Title
Cross-tenant webhook authentication bypass via `repository_owner` fallback to `organization.login` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using `repository_owner`, which falls back to the top-level `organization.login` field whenever `repository.owner.login` is absent from the JSON body. Because the payload is attacker-controlled JSON (not a real signed GitHub payload structure enforced by Shipit), an attacker who legitimately controls one tenant org's webhook secret (`attacker-org`) can sign a payload whose `repository.full_name` names a different tenant's repository (`victim-org/tracked-repo`), passing signature verification under `attacker-org` while `LabelCapturingHandler` resolves and mutates the actual repository/stack looked up purely from `repository.full_name`.

### Finding Description
The broken binding: `verifying_org (repository_owner used in verify_signature) == owning_org (owner of the repository/stack mutated downstream)` — this should always hold, but does not.

- `WebhooksController#repository_owner` (app/controllers/shipit/webhooks_controller.rb:59-62): `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. If the JSON body simply omits `repository.owner.login` (fully attacker-controlled, since the attacker crafts the raw JSON POST body), this falls back to `organization.login`.
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) then calls `Shipit.github(organization: repository_owner)` and checks the HMAC signature against that org's `webhook_secret`. If `repository_owner` resolves to `attacker-org`, and the attacker knows `attacker-org`'s configured `webhook_secret` (a legitimately provisioned multi-tenant org, per `lib/shipit.rb#github_app_config` / docs/setup.md "Using Multiple Github Applications"), the signature check passes.
- Downstream, `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler` (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb) only requires `repository.full_name` in its param schema (no `repository.owner.login`, no cross-check against the authenticating org) and resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (app/models/shipit/repository.rb:53-56), which does a plain `owner/name` lookup independent of which org's secret verified the request.
- `opened_active_stack?` (label_capturing_handler.rb:58-60) returns true purely from `stack.present?`, with no org ownership check, and `capture_labels` (label_capturing_handler.rb:98-102) overwrites `stack.pull_request.labels` — a record that belongs to `victim-org`, not `attacker-org`.

Exploit flow: attacker POSTs `X-Github-Event: pull_request`, body `{"action":"opened","number":<victim PR#>,"pull_request":{...,"labels":[{"name":"attacker-label"}]},"repository":{"full_name":"victim-org/tracked-repo"},"organization":{"login":"attacker-org"},"sender":{"login":"attacker"}}` (no `repository.owner.login` key) signed with `attacker-org`'s own `webhook_secret`. Signature check passes under `attacker-org`; the handler locates and mutates `victim-org/tracked-repo`'s pre-existing stack's `PullRequest#labels`.

Existing guards fail to prevent this: `drop_unhandled_event` only checks the event type exists; the `ExplicitParameters` schema in `LabelCapturingHandler` never requires or validates `repository.owner.login` against the verifying org; `GithubOrganizationUnknown` rescue only guards against unconfigured orgs, not org/repo mismatch; there is no check anywhere in the controller or handler chain binding the authenticated org back to the repository being mutated.

### Impact Explanation
An attacker who controls any legitimately provisioned tenant org in a multi-org Shipit deployment can write to (re-label) an existing PR/stack belonging to a completely different tenant's repository, using only their own valid webhook signature. This is a payload for one repository (attacker's) mutating another tenant's stack/PullRequest record — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is repeatable against any tracked repository/PR number combination across tenants once one attacker-controlled org is onboarded, and the blast radius spans all repositories on the Shipit instance, not just the attacker's own.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment (multiple orgs configured in `secrets.github`, as documented in docs/setup.md) and that the attacker has legitimate credentials for at least one configured tenant (a realistic scenario for SaaS-style or shared Shipit installs where different teams/orgs self-onboard GitHub Apps). Given that precondition, the attack requires only crafting a raw JSON HTTP POST with a correctly computed HMAC using the attacker's own known secret — no privileged Shipit session, API token, or victim secret needed. It is fully repeatable and low-cost per request.

### Recommendation
Bind webhook authentication to the actual repository being acted upon, not an independently-controlled fallback field. `WebhooksController#repository_owner` should require `repository.owner.login` (or derive owner strictly from `repository.full_name`) and never fall back to the top-level `organization.login` for events carrying a `repository` object. Additionally, handlers such as `LabelCapturingHandler`/`OpenedHandler`/etc. should require and cross-validate that the authenticated organization (used to select the `webhook_secret`) matches the owner parsed from `repository.full_name` before mutating any stack/PullRequest.

test "cross-tenant signature does not allow mutating another org's stack" do
  # victim-org/tracked-repo already has a stack/PullRequest for PR #42
  victim_repo = shipit_repositories(:shipit) # owner: victim-org
  victim_stack = create_stack_for(victim_repo, pr_number: 42, labels: ["victim-label"])

  payload = payload_parsed(:pull_request_opened)
  payload["number"] = 42
  payload["pull_request"]["number"] = 42
  payload["pull_request"]["labels"] = [{ "name" => "attacker-label" }]
  payload.delete("repository")["owner"] rescue nil
  payload["repository"] = { "full_name" => "#{victim_repo.owner}/#{victim_repo.name}" } # no owner.login
  payload["organization"] = { "login" => "attacker-org" }

  body = payload.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", ATTACKER_ORG_WEBHOOK_SECRET, body)

  @request.headers["X-Github-Event"] = "pull_request"
  @request.headers["X-Hub-Signature"] = signature

  post :create, body:, as: :json

  assert_response :ok
  # Binding check: verifying org (attacker-org) != owning org (victim-org)
  assert_not_equal "attacker-org", victim_repo.owner
  # But the victim's labels were overwritten by an attacker-signed request
  assert_equal ["attacker-label"], victim_stack.reload.pull_request.labels
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
