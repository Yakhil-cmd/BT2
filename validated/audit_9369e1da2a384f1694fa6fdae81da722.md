## Title
Attached deposit permanently locked in the Wallet Contract when a cross-contract call fails via an early-return callback path - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Trail of Bits finding describes contracts (`Entropy.sol`, `Executor.sol`) that accept native asset deposits but have no code path to return them, permanently locking funds. The `near-wallet-contract` in this nearcore checkout has an analogous pattern: it tracks an external caller's `attached_deposit` via `CallerDeposit` so it can be refunded if the emulated Ethereum transaction fails, but the refund is only issued from a single call site (`rlp_execute_callback`, on `PromiseResult::Failed`). Several other failure branches return an `ExecuteResponse` directly without ever invoking that refund logic, leaving the deposit stuck in the wallet contract's balance.

### Finding Description
`inner_rlp_execute` computes `caller_deposit` from the caller's `attached_deposit` [1](#0-0) , and this `CallerDeposit` type exists specifically "to refund the caller's deposit if the cross-contract call fails" [2](#0-1) .

The only place that actually performs this refund is `rlp_execute_callback`, and only in the `PromiseResult::Failed` branch: [3](#0-2) 

However, `address_check_callback` — which runs before `rlp_execute_callback` in the emulated EOA base-token-transfer flow when a destination address must be checked against the registrar — has two early-return branches that skip this refund entirely and never pass `caller_deposit` onward for a refund:

1. If the call to the Address Registrar contract itself fails, the function returns an `ExecuteResponse` failure directly without touching `caller_deposit`: [4](#0-3) 

2. If the target address resolves to an existing named account but the caller is not a self-call from the wallet (i.e., an external caller triggered this path), the function again returns a failure `ExecuteResponse` directly, without refunding `caller_deposit`: [5](#0-4) 

The same pattern also appears in `nep_141_storage_balance_callback`'s early-return failure branches for the NEP-141 storage-balance lookup: [6](#0-5) 

In all of these cases, the attached deposit from the external caller was already transferred into the wallet contract's account balance when the outer `rlp_execute` call was made (this is the balance backing `caller_deposit.yocto_near`), but the execution path terminates in failure without generating any `promise_batch_action_transfer` refund receipt back to `caller_deposit.account_id`. Unlike the general NEAR protocol runtime — which automatically and unconditionally refunds `attached_deposit` to the predecessor on any receipt failure per the documented refund mechanism [7](#0-6)  — this contract-level deposit tracking is a manual, best-effort mechanism implemented in application code, and it is incomplete: several failure branches simply drop the `CallerDeposit` value.

### Impact Explanation
Any external caller who attaches a deposit to `rlp_execute` targeting an emulated EOA base-token transfer whose destination requires a registrar lookup, or an ERC-20-style transfer requiring a NEP-141 storage-balance lookup, risks permanently losing that deposit if the lookup call fails or resolves to a case handled by the early-return branches. The funds remain in the Wallet Contract's account balance with no code path to reclaim them (short of a contract upgrade or a manually crafted governance/admin action, neither of which is exposed). This is a direct, unprivileged-account-reachable loss of user funds.

### Likelihood Explanation
The triggering conditions are reachable by any ordinary caller/relayer, without needing validator or node privileges: an Address Registrar call failure (e.g., transient failure or if that account doesn't exist/misconfigured) or targeting an existing named account through the EOA base-token-transfer address-check path. Given that this contract is designed to process arbitrary Ethereum-style transactions relayed by third parties, and relayers/callers routinely attach deposits for base-token and ERC-20 transfers, these branches are realistically reachable, not merely theoretical edge cases.

### Recommendation
Ensure every failure/early-return branch in `address_check_callback` and `nep_141_storage_balance_callback` (and any other callback that can terminate the flow without reaching `rlp_execute_callback`) explicitly issues the `caller_deposit` refund transfer before returning `ExecuteResponse { success: false, .. }`, mirroring the logic already present in `rlp_execute_callback`'s `PromiseResult::Failed` branch. Consider factoring the refund logic into a shared helper function that is called from every failure exit point to avoid future omissions, and add integration tests analogous to `test_caller_refunds` that specifically exercise the registrar-failure and NEP-141-lookup-failure paths.

### Proof of Concept
1. Deploy the Wallet Contract and register a relayer/caller account.
2. Craft a signed Ethereum-style transaction representing an `EOABaseTokenTransfer` whose `address_check` requires a registrar lookup (i.e., target is an eth-implicit address needing verification against `ADDRESS_REGISTRAR_ACCOUNT_ID`).
3. Have an external caller (not the wallet itself) call `rlp_execute` with a non-zero `attached_deposit`, targeting a scenario where either (a) the Address Registrar contract call fails, or (b) the resolved account exists and `env::signer_account_id() != current_account_id` (i.e., the caller is external, not the wallet acting on its own behalf).
4. Observe that `address_check_callback` returns `ExecuteResponse { success: false, .. }` directly (lines 141-148 or 161-173) without generating any `promise_batch_action_transfer` back to the caller.
5. Query the caller's account balance before and after: the attached deposit is deducted and never returned, while the Wallet Contract's balance keeps the deposit indefinitely — analogous to the `test_caller_refunds` test at [8](#0-7) , but exercising the un-covered failure branches instead of the covered `PromiseResult::Failed` path in `rlp_execute_callback`.

*Note: I was not able to fully view the beginning of `lib.rs` (the `rlp_execute` entry point's payable/deposit annotation) or `types.rs` in full due to tool errors on the final iteration, so I cannot 100% confirm the exact annotation making `rlp_execute` payable, though the presence of `env::attached_deposit()` being read in `inner_rlp_execute` and used to construct `CallerDeposit` strongly implies it is a payable method that receives and holds the deposit in the contract's own balance.*

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

## Deposit Refunds

Deposit refunds are generated when an action receipt fails to execute. All attached deposit amounts are summed together and
sent as a refund to a `predecessor_id` (because only the predecessor can attach deposits).

Deposit refunds have the following fields in the `ActionReceipt`:

- `signer_id` is `system`
- `signer_public_key` is ED25519 key with data equal to 32 bytes of `0`.

Deposit refunds are free for the user and incur no refund fee.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
