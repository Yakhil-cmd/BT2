## Title
`machine.environment` values from a fork's `shipit.yml` are merged verbatim into the shell-interpreted step environment, enabling `NODE_OPTIONS` injection — ([File: app/models/shipit/deploy_spec.rb], [File: lib/shipit/task_commands.rb], [File: lib/shipit/command.rb])

## Summary
`DeploySpec#machine_env` returns `config('machine', 'environment')` with no key/value filtering, and `TaskCommands#env` merges it directly into the hash later handed to `Command.new(..., env:)`, which `PTY.spawn` uses to execute a `shipit.yml` step through a shell. Because the review stack's working directory is checked out from the fork PR's head commit, the fork author fully controls the `shipit.yml` used to build this `machine_env`, so an attacker can set `NODE_OPTIONS` (or any other env var) that alters how a subsequent Node-based step executes.

## Finding Description
The broken binding is: `TaskCommands#env` should only contain environment variables the operator explicitly trusts, but instead
`env.merge(deploy_spec.machine_env)` == `env.merge(config('machine','environment'))` with **no whitelist**, unlike `deploy_variables`/`rollback_variables` which are filtered through `EnvironmentVariables#permit` (`DeploySpec#filter_deploy_envs`, `filter_rollback_envs`) [1](#0-0) [2](#0-1) .

`TaskCommands#env` merges this unfiltered `machine_env` into the exact hash used to spawn every step's `Command`: [3](#0-2) . That hash is passed as `env:` to `Command.new`, stored, and merged into `PTY.spawn`'s environment via `unbundled_env`: [4](#0-3) [5](#0-4) . Steps are single strings executed through a shell (`PTY.spawn(env, *interpolated_arguments)` where `interpolated_arguments` is a shell command string), so any environment variable interpreted by the invoked interpreter (e.g., Node's `NODE_OPTIONS`, or a shell's own env-based behavior) affects execution of that step.

For a `ReviewStack`, the `shipit.yml` read by `DeploySpec::FileSystem` comes from the checked-out working directory of the PR's head commit — the deploy spec is loaded from files on disk after `TaskCommands#checkout(commit)` checks out `commit.sha`, and for pull-request-driven review stacks that commit is the fork branch's head SHA set from the webhook payload (`self.head = find_or_create_commit_from_github_by_sha!(github_pull_request.head.sha)` in `PullRequest#github_pull_request=`) [6](#0-5) . This confirms the attacker (fork PR author) controls the exact `shipit.yml` content, including `machine: {environment: {NODE_OPTIONS: ...}}`, that ends up parsed by `DeploySpec::FileSystem` and merged by `machine_env`.

`provisioning_behavior = allow_with_label` only gates **whether** a review stack gets provisioned/archived based on a label on the PR (`LabeledHandler#archive?`/`unarchive?`, `Repository#provisioning_behavior_allow_with_label?`) [7](#0-6) [8](#0-7) . It does not sandbox or filter the `shipit.yml` contents used once the stack is provisioned/deployed — once unarchived, the normal task pipeline (`TaskCommands#env` → `Command#start`) runs using the fork's own `shipit.yml`, machine env included. No component in this path (`EnvironmentVariables#permit`, `filter_deploy_envs`, `filter_rollback_envs`) is applied to `machine_env`, so the divergence between "operator-trusted env" and "fork-controlled env" is real and unguarded.

## Impact Explanation
An attacker who opens a PR against a repository with review apps enabled (`allow_with_label`, requiring only the provisioning label — which, depending on repo configuration, can be applied by non-maintainers or automatically) can set arbitrary `machine.environment` values, including `NODE_OPTIONS=--require /path/to/evil.js`, in their fork's `shipit.yml`. When any deploy/install/task step in the pipeline invokes `node` (directly or via `npm`/build tooling), the injected `NODE_OPTIONS` causes that step's Node process to load attacker-controlled JavaScript, resulting in Remote Code Execution on the Shipit deploy host under the identity running Shipit tasks. This is a Critical RCE class impact per the rubric, scoped to whatever repository/stack the attacker's PR targets, and is repeatable per PR/commit.

## Likelihood Explanation
Preconditions: review apps must be enabled for the repository, `provisioning_behavior` set to `allow_with_label` (or `allow_all`), the provisioning label applied to the PR (which, per the `allow_with_label` design, is meant to be an explicit opt-in gate but does not vet file contents), and at least one pipeline step that invokes Node. Attacker cost is minimal — no secrets or elevated GitHub roles are needed, only the ability to open a PR/push a fork branch with a modified `shipit.yml`, which is exactly the capability the question grants. This is fully feasible and repeatable against any repository configured this way.

## Recommendation
Filter `machine.environment` through an explicit whitelist mechanism analogous to `EnvironmentVariables#permit`/`deploy_variables`, or entirely disallow `machine.environment` (and other unfiltered `shipit.yml` config sourced from fork branches) from influencing task execution unless the spec comes from a trusted ref (e.g., the base repository's default branch) rather than the PR head. At minimum, strip/deny well-known code-injection env vars (`NODE_OPTIONS`, `LD_PRELOAD`, `PYTHONSTARTUP`, `RUBYOPT`, etc.) before merging `machine_env` into the process environment in `TaskCommands#env`.

## Proof of Concept
Minitest plan (`test/unit/task_commands_test.rb` or `test/lib/task_commands_test.rb`, mirroring existing `deploy_spec_test.rb`/`environment_variables_test.rb` fixtures):
1. Build a `ReviewStack` with an associated `PullRequest` whose `head` commit's checked-out working directory contains a `shipit.yml` with:
   ```yaml
   machine:
     environment:
       NODE_OPTIONS: "--require /tmp/evil.js"
   ```
2. Instantiate `TaskCommands.new(task)` for a task on this stack and assert:
   ```ruby
   assert_equal "--require /tmp/evil.js", commands.env["NODE_OPTIONS"]
   ```
3. Further assert this value is what reaches `Command#start`: stub/spy `PTY.spawn` and assert the `env` hash argument (first positional arg) contains `"NODE_OPTIONS" => "--require /tmp/evil.js"`, proving the fork-controlled key reaches the shell-interpreted step's process environment unfiltered — i.e., the binding `commands.env["NODE_OPTIONS"] == deploy_spec.machine_env["NODE_OPTIONS"]` holds when it should instead be rejected/filtered.
