### Title
Webhook signature check silently returns `true` when `webhook_secret` is unset, letting unauthenticated `status`/`push`/`check_suite` events forge CI state and trigger deploys for that organization - (File: lib/shipit/github_app.rb)

### Summary
The Caviar bug is a "silent skip" of a required safety check (bounds check silently omitted before a cast). The strongest reachable analog in Shipit is `GithubApp#verify_webhook_signature`, which silently treats an unset `webhook_secret` as "verification passed" instead of rejecting the request, breaking the intended binding: *webhook accepted ⇔ HMAC signature matches the organization's configured secret*.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration for the event's claimed organization/repository owner and asks it to verify the `X-Hub-Signature` header against the raw body: [1](#0-0) 

The actual verification logic silently short-circuits to `true` whenever no `webhook_secret` is configured for that organization, instead of rejecting the request or requiring one: [2](#0-1) 

This is exactly the "silent overflow"-class bug: a guard that is supposed to gate whether attacker-controlled data is trusted is bypassed without any explicit signal, rather than failing closed. Any organization entry in `Shipit.github_apps`-style configuration that has no `webhook_secret` set effectively has **no signature verification at all**, so `WebhooksController#create` will dispatch attacker-crafted JSON straight to the registered handlers: [3](#0-2) 

Downstream, handlers act directly on payload fields with no additional authentication — e.g. `status` events create a `Status` record on an arbitrary commit using attacker-supplied `state`, `target_url`, `description`, and `context`, and `push`/`check_suite` events drive `stack.sync_github` / check-run refresh: [4](#0-3) [5](#0-4) 

The binding broken, as an equality:
`request_accepted == (HMAC-SHA1(raw_body, org.webhook_secret) matches X-Hub-Signature)`
becomes, when `org.webhook_secret` is blank:
`request_accepted == true` (unconditionally), for any organization that is configured in Shipit but did not set a secret.

### Impact Explanation
Shipit uses commit statuses/check-suites (populated exclusively via these webhooks) to decide whether a commit is "green"/deployable, and continuous-deployment-enabled stacks act on that state to trigger automatic deploys. An unprivileged attacker who can reach the public `/webhooks` endpoint (no session, no `ApiClient` token, no GitHub App private key required) can forge a `status` webhook marking an arbitrary, malicious commit SHA as `success` for any repository belonging to an org whose `webhook_secret` is unset, and forge `push`/`check_suite` events to force a resync. Combined with continuous deployment, this can result in an **unauthorized deploy** of unreviewed code — one of the explicitly accepted Critical impacts.

### Likelihood Explanation
Exploitability is conditional on at least one configured GitHub organization having no `webhook_secret` set — this is a supported, non-error configuration state in the code (the method returns `true` rather than raising or refusing), not a case of "the engine not being mounted as documented." Since `webhook_secret` is optional per `GithubApp#initialize` (`@webhook_secret = @config[:webhook_secret].presence`), any operator who provisions a GitHub App/organization without a secret (or leaves the default sample config without one) exposes this bypass with no credential requirement at all — making it a genuine unauthenticated-attacker path rather than a purely theoretical one.

### Recommendation
Fail closed instead of silently allowing: if no `webhook_secret` is configured for an organization, reject webhook delivery (422) rather than treating it as verified, and require `webhook_secret` presence in `GithubApp` configuration validation. E.g.:
```ruby
def verify_webhook_signature(signature, message)
  return false if webhook_secret.blank?
  ...
end
```

### Proof of Concept
1. Configure Shipit with an organization entry whose `github_app` config omits `webhook_secret` (a valid, non-error configuration).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<malicious-commit-sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "description": "forged",
  "context": "ci/forged",
  "branches": [{"name": "main"}],
  "repository": {"owner": {"login": "<victim-org>"}, "full_name": "<victim-org>/<repo>"}
}
```
3. `verify_signature` calls `Shipit.github(organization: "<victim-org>").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. `StatusHandler` creates a `Status` record recording `state: success` for the attacker-chosen SHA, as demonstrated by the equivalent test flow in `test/controllers/webhooks_controller_test.rb:42-59`.
5. If the stack has continuous deployment enabled and gating on this status, Shipit proceeds to deploy the attacker-chosen commit without any real CI having run.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
