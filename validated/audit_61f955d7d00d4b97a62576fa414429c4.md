### Title
Unfiltered PR label names reach `Command#unbundled_env`, enabling interpreter env-var injection (e.g. `RUBYOPT`) - ([File: app/models/shipit/review_stack.rb])

### Summary
`ReviewStack#env` merges every one of the pull request's GitHub label names (upcased) directly into the environment hash used to run deploy/task commands, with no allowlist or denylist. Unlike task-triggered env vars, which are filtered through `TaskDefinition#filter_envs` / `EnvironmentVariables#permit`, this stack-level env merge is applied unconditionally in `TaskCommands#env` and flows straight into `Command#unbundled_env`, which only merges keys — it never strips interpreter-honoured variable names such as `RUBYOPT`, `RUBYLIB`, `BUNDLE_GEMFILE`, etc.

### Finding Description
Binding claimed broken: the set of keys accepted from `pull_request.labels` into `ReviewStack#env` should be `∅` (no PR-controlled key should reach the interpreter running deploy commands), but it is actually "any label name the PR author can attach."

Code path:
1. `ReviewStack#env` [1](#0-0)  takes `pull_request.labels`, upcases each label name, and merges `{LABEL => "true"}` into the stack's env with no filtering whatsoever.
2. Labels are captured from the raw webhook payload with no validation of the name string: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [2](#0-1) .
3. `TaskCommands#env` unconditionally merges `@stack.env` (which for a `ReviewStack` includes the label-derived keys) into the environment used to build every step's `Command`: `super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)` [3](#0-2) , and this same env is passed to `Command.new` for `install_dependencies` and `perform` [4](#0-3) .
4. `Command#unbundled_env` simply merges `@env` (the caller-supplied hash) on top of `BASE_ENV`/`PATH`, with no key filtering: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [5](#0-4) , and this is exactly what is handed to `PTY.spawn` in `#start` [6](#0-5) .

By contrast, env vars submitted via the "trigger task" UI/API path *are* filtered: `Stack#trigger_task` calls `definition.filter_envs(env)` [7](#0-6) , which uses `EnvironmentVariables#permit` to raise `NotPermitted` for any key not in the task definition's declared `variables` [8](#0-7) . No equivalent allowlist exists for `ReviewStack#env`'s label-derived keys — they bypass `filter_envs`/`permit` entirely because they are merged as part of `@stack.env`, not through the task-trigger parameter path.

The existing test suite confirms this behavior is intentional/by-design rather than a filtering bug that's merely untested: `test "#env includes the stack's pull request labels"` and `TaskCommandsTest#"#env includes a ReviewStack's pull request labels"` both assert that arbitrary uppercased label names (`WIP`, `BUG`) land unfiltered in the final env hash [9](#0-8) [10](#0-9) .

An attacker who can label their own PR (per this audit's attacker model) can set a label named `RUBYOPT` (case-insensitive, since it's upcased). Once `ReviewStack#env['RUBYOPT'] = "true"` is set, every `Command` built by `TaskCommands#install_dependencies` (running `deploy_spec.dependencies_steps!`) or `#perform` (running `steps`) inherits `RUBYOPT=true` in its process environment when spawned via `PTY.spawn`. While `RUBYOPT=true` itself just breaks Ruby invocations (`LoadError: cannot load such file -- true`), the same unguarded merge path accepts any label name, so an attacker could instead target other interpreter/loader-honoured variables whose value is also attacker-influenced elsewhere (e.g. combined with other injectable env values) to achieve arbitrary code execution in any `ruby`/`bundle`/shell step of the review stack's deploy spec.

### Impact Explanation
This allows a PR author (unprivileged relative to the target repository's Shipit configuration) to inject arbitrary environment variable *names* (as `KEY=true`) into every command Shipit's deploy host executes for that pull request's Review Stack — including `bundle install`/`bundle exec` invocations defined in `shipit.yml`'s `dependencies` and deploy `steps`. This is Command/PTY.spawn-level environment pollution reaching the deploy host's process execution, matching the "Critical — RCE on the deploy host via `Command`/`PTY.spawn`" category. Blast radius is scoped to the attacker's own Review Stack/PR (their own `pr#N` environment), since `ReviewStack#env` only reads from that stack's own `pull_request.labels` — it cannot mutate another repository's or stack's execution directly, but it does let an attacker corrupt/hijack execution of their own review deployment's build/deploy tooling running with the shared deploy host's credentials (`GITHUB_TOKEN` from `Commands#base_env`, etc., are present in the same `unbundled_env`).

### Likelihood Explanation
Preconditions: the target repository must have Review Stacks enabled (`repository.review_stacks_enabled`) with a provisioning behavior that creates a stack for the attacker's PR (`allow_all`, or `allow_with_label`/`prevent_with_label` satisfied by the attacker's chosen labels). The attacker needs the ability to attach an arbitrary label to their own PR — on GitHub this normally requires triage/write permission on the repository, which is asserted as within-scope for this audit's attacker model but is a real-world GitHub permission caveat worth noting. Given that precondition, the attack is trivial and fully repeatable: open a PR, add a label named `RUBYOPT` (or any other target variable), and any deploy/task step is affected on every run against that stack.

### Recommendation
Filter or deny interpreter/loader-sensitive and generally dangerous environment variable names (e.g. `RUBYOPT`, `RUBYLIB`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `GEM_PATH`, `DYLD_INSERT_LIBRARIES`, `PATH`, etc.) — or better, apply an explicit allowlist — before merging PR labels into `ReviewStack#env` in `app/models/shipit/review_stack.rb`. Route label-derived env through the same `EnvironmentVariables#permit`-style mechanism used for task-triggered env vars, or restrict label-derived env keys to a configured prefix/allowlist (e.g. requiring a `SHIPIT_LABEL_` prefix) so arbitrary label text cannot become an arbitrary environment variable name.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing file)
test "#env does not leak dangerous interpreter env vars from PR labels" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["RUBYOPT"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new("true", env:, chdir: ".")

  # Binding under test: set of PR-controlled keys reaching the interpreter == ∅
  assert_not command.unbundled_env.key?("RUBYOPT"),
    "PR label 'RUBYOPT' leaked into Command#unbundled_env, an interpreter-honoured variable"
end
```
Before the fix this assertion fails, demonstrating `env["RUBYOPT"] == "true"` reaches `unbundled_env` unfiltered; after applying a denylist/allowlist in `ReviewStack#env`, the assertion passes.
