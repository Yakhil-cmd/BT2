### Title
Webhook Event Processing Trusts a Different Repository Field Than the One Used to Select the Verifying Signature - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify the `X-Hub-Signature` against based on `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`). Once the signature check passes, individual webhook handlers act on a *different* field of the same attacker-controlled JSON body to decide what to update. Most critically, `StatusHandler#process` doesn't scope by repository at all — it updates `Commit.where(sha: params.sha)` across the entire installation. This breaks the equality "organization whose secret authenticated the request" == "repository/commit that gets written," in a Shipit deployment configured with multiple GitHub organizations (as documented and supported, see `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md`'s "Using Multiple Github Applications" section).

### Finding Description
Signature verification and org selection: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` from the JSON body and is used purely to pick which `GitHubApp` (and its `webhook_secret`) verifies the HMAC signature via `Shipit.github(organization: repository_owner)` / `verify_webhook_signature`: [3](#0-2) 

Shipit explicitly supports multiple, independently-configured GitHub Apps/organizations, each with its own `webhook_secret`: [4](#0-3) 

Once verification succeeds, the `create` action dispatches to per-event handlers with the raw parsed body, unmodified: [5](#0-4) 

Handlers, however, resolve the target resource using a *different* payload field. The base `Handler` uses `repository.full_name`: [6](#0-5) 

`StatusHandler` is worse — it doesn't scope to any repository/stack at all, it simply matches by SHA globally: [7](#0-6) 

Because `repository.owner.login` (used to choose the verifying secret) and `repository.full_name` / `sha` (used by the handler to decide what to write) are independent, attacker-controlled fields in the same JSON body, an attacker who legitimately controls **one** organization configured in this Shipit instance (i.e., knows that org's `webhook_secret` because they installed the GitHub App there themselves) can forge a webhook whose `repository.owner.login` is their own org (so the signature check passes with their own secret) while every other field (`repository.full_name`, `sha`, `state`, etc.) targets a completely different, victim organization's repository/commit.

For `status` events specifically, since `StatusHandler#process` does `Commit.where(sha: params.sha)` with no repository scoping whatsoever, the attacker can craft a signed payload naming any SHA they know exists in a totally unrelated stack (e.g., observed on public GitHub), and inject an arbitrary CI status (`state: "success"`, arbitrary `context`) for that commit: [8](#0-7) 

This flows into `Commit#create_status_from_github!` / `add_status`, which updates the commit's simple state, can trigger `deployable_status` hooks, and schedules merges: [9](#0-8) 

Since deploy eligibility (`deployable?`), CI-gating, and the merge queue all key off commit status records populated this way, an attacker can make a victim commit in a repository they have no access to appear to have passed CI, potentially enabling an unauthorized deploy or unblocking the merge queue for that commit.

### Impact Explanation
This crosses the "unauthorized deploy" / cross-repository write bar in the Critical bucket: an attacker who is only an authorized administrator of *one* GitHub organization configured on a shared, multi-org Shipit instance can forge signed webhook events (using their own legitimate `webhook_secret`) that write state (CI status, potentially triggering deploy-gating changes) against a completely different organization's stacks/commits, because the field used to select the verifying secret (`repository.owner.login`) is never cross-checked against the field(s) the handler actually acts on (`repository.full_name`, `sha`). This is analogous to the reported currency-pool mismatch: the wrong "identity" is checked against the wrong "quantity," so the guard passes while acting on unintended data.

### Likelihood Explanation
Requires the deployment to be configured with the documented multi-organization `github:` schema (explicitly supported/documented) and requires the attacker to be a legitimate admin/owner of at least one of those configured organizations (so they know that org's `webhook_secret`) — this is not a privileged Shipit account or `ApiClient` token, just control of any one of the multiple GitHub orgs plugged into the same Shipit instance. Likelihood is moderate: single-org deployments (the common case) are unaffected because `repository_owner` and the actual target repository are always the same org in that setup, but any multi-tenant Shipit installation is exposed.

### Recommendation
When resolving the target repository/commit in `Handler#repository_name` and especially in `StatusHandler#process`, cross-validate that the resolved repository's owner matches the organization whose secret verified the signature (`repository_owner` from the controller), and reject/drop the event otherwise. `StatusHandler` in particular must scope its `Commit` lookup to the repository named in the payload (and validate that repository against the verified organization), not merely by SHA.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `OrgOne` (victim) and `OrgTwo` (attacker-controlled), per `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, who legitimately owns `OrgTwo`'s installed GitHub App, knows `OrgTwo`'s `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<sha of a real commit in OrgOne/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgTwo" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgTwo_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")` (from `repository.owner.login`) and the signature verifies successfully against `OrgTwo`'s secret.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the commit belonging to `OrgOne`'s stack (uninvolved in the signature check), and records a fabricated "success" status via `create_status_from_github!`, potentially unblocking deploy/merge gating for that commit in `OrgOne`.

Note: I was unable to fully trace whether `required_statuses`/`blocking_statuses` in `app/models/shipit/deploy_spec.rb` and `Commit#deployable?` unconditionally treat this forged status as sufficient for deploy eligibility in all configurations (this depends on the victim stack's `shipit.yml` `ci.require` settings) — this final gating logic could not be completely verified within the available tool budget.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
```
