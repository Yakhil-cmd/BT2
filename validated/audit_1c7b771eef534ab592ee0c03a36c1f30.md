### Title
Stale reward-calculation delegation snapshot vs. live `StakesCache` state causes a validator panic during partitioned epoch-reward distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
Partitioned epoch rewards in agave are computed once at the epoch boundary (`calculate_rewards`/`calculate_stake_rewards_and_commissions`) and then paid out across many subsequent blocks (`distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` → `build_updated_stake_reward`). This mirrors exactly the bug-class in the external report: a value (here, delegated stake) is computed from a **stale snapshot** at "request time" (calculation phase) but the corresponding state mutation is only committed much later ("confirmation"/distribution phase), while the underlying resource remains live and mutable by its owner in between. If a stake account owner changes their own stake delegation (e.g., via `Split`, `Merge`, `Withdraw`, or `Redelegate`) after calculation but before their specific partition is distributed, the live `StakesCache` entry used at distribution time no longer matches the value assumed during calculation.

### Finding Description
`build_updated_stake_reward` at [1](#0-0)  loads the stake account for `partitioned_stake_reward.stake_pubkey` from the **current, live** `stakes_cache_accounts` map (`self.stakes_cache.stakes()` at distribution time, not at calculation time). It then either:
- adjusts the delegation via `adjust_delegation_for_rent` when the `relax_post_exec_min_balance_check` feature is active, or
- otherwise asserts that `expected_delegation` (current live `stake.delegation.stake` + the reward amount computed at calculation time) equals `new_stake.delegation.stake` (the delegation value frozen inside `partitioned_stake_reward.inflation.stake`, produced during the earlier calculation phase): [2](#0-1) 

The reward-calculation phase (`calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards`) is run once at the epoch boundary against a snapshot of `stake_delegations`. Because reward distribution is intentionally spread over `num_partitions` subsequent blocks (see the driver in `distribute_partitioned_epoch_rewards`, [3](#0-2) ), a stake account's owner is free to submit ordinary, unprivileged stake-program transactions (split, merge, partial withdraw, or redelegate) against their own stake account in any of the intervening blocks before their account's specific partition is processed. Each such instruction synchronously updates the live `StakesCache` (`upsert_stake_delegation`, [4](#0-3) ), changing `delegation.stake` for that account.

When the account's turn for distribution finally arrives, `build_updated_stake_reward` reads the now-mutated delegation from the live cache and adds the reward amount that was computed against the *old* (stale) delegation snapshot. If `relax_post_exec_min_balance_check` is not active for the running feature set, this mismatch is checked with a hard `assert_eq!` rather than being resolved — the assertion fails and the validator process panics while executing this block.

### Impact Explanation
This is a deterministic execution path: every validator that replays the same block containing the triggering stake-mutation transaction, at the same distribution partition_index, will independently compute the same mismatch and hit the same `assert_eq!` panic. That satisfies the "epoch-boundary halt" acceptance criterion — an unprivileged staker can, without any special privilege, cause validators to crash while distributing partitioned epoch rewards, i.e., a cluster-wide halt at (or shortly after) the epoch boundary. This directly maps to the report's root cause pattern: an operation is validated/priced against a resource snapshot before an asynchronous multi-step commit finishes, and the resource is not locked in the interim, so a concurrent mutation of the same resource desynchronizes the two phases.

### Likelihood Explanation
Reachability depends on the `relax_post_exec_min_balance_check` feature not being active for the currently-processed epoch/feature set (it is listed as an ordinary, individually-activatable feature in `feature-set/src/lib.rs`, not compiled-in as mandatory, and is only checked at runtime via `feature_set.snapshot()`). On networks/environments where that feature has not yet been activated (e.g., pre-activation windows, test/custom clusters, or any fork not carrying the fix), the `assert_eq!` branch is live code, and a staker only needs to submit a normal `Split`/`Merge`/`Withdraw`/`Redelegate` instruction on their own stake account during the multi-block reward distribution window to trigger it — no special timing precision beyond "before my account's partition block" is required. I could not fully verify from the available code snapshot whether this feature is unconditionally activated on current mainnet-beta (that state lives in cluster feature-activation history, not in this repository), so the practical exploitability on mainnet-beta today is uncertain and should be independently verified.

### Recommendation
- Do not use a hard `assert_eq!` to compare a stale calculation-time delegation snapshot against the live delegation at distribution time. Instead, always recompute the reward relative to the live `StakesCache` state at distribution time (as is already done in the `adjust_delegations_for_rent` branch), regardless of feature-gate status, so a concurrent user-driven mutation cannot desynchronize the two phases into a panic.
- Alternatively, lock or snapshot each account's `delegation.stake` at calculation time and disallow (or safely reconcile) stake-mutating instructions (`Split`, `Merge`, `Withdraw`, `Redelegate`) on accounts that have a pending, not-yet-distributed partitioned reward, mirroring the "lock the resource before the async step completes" mitigation recommended in the source report.
- Add a regression test that submits a `Split`/`Merge`/`Withdraw` on a stake account between the calculation block and its assigned distribution partition block, verifying that distribution completes without panicking under both feature-flag states.

### Proof of Concept
1. Start a cluster/bank configuration where `relax_post_exec_min_balance_check` is not activated.
2. Create a delegated stake account `S` with credits earned in the rewarded epoch so it receives a non-zero stake reward.
3. Advance to the epoch boundary so `calculate_rewards_for_partitioning` computes and caches a `PartitionedStakeReward` for `S`, and set `num_partitions` > 1 so distribution spans multiple blocks (large `stake_accounts` counts naturally do this, as shown by `test_rewards_computation_and_partitioned_distribution_multi_blocks` in [5](#0-4) ).
4. Before `S`'s partition block is reached, submit an ordinary `stake_instruction::split` (or `merge`/`withdraw`/`redelegate`) transaction against `S`, changing its live `Delegation::stake` in `StakesCache`.
5. Advance to `S`'s assigned partition block and call `distribute_partitioned_epoch_rewards`; `build_updated_stake_reward` will compute `expected_delegation` from the now-mutated live cache entry and compare it against the frozen `new_stake.delegation.stake` from calculation time — triggering the `assert_eq!` panic in [2](#0-1) .

impl Bank {
    /// Process reward distribution for the block if it is inside reward interval.
    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }

        if height.saturating_add(1) >= distribution_end_exclusive {
            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("active", 0, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );

            assert!(matches!(
                self.epoch_reward_status,
                EpochRewardStatus::Active(EpochRewardPhase::Distribution(_))
            ));
            self.epoch_reward_status = EpochRewardStatus::Inactive;
            self.set_epoch_rewards_sysvar_to_inactive();
        }
    }

    fn build_updated_stake_reward(
        distribution_epoch: u64,
        stake_history: &StakeHistory,
        new_warmup_cooldown_rate_epoch: Option<Epoch>,
        stakes_cache_accounts: &imbl::HashMap<Pubkey, StakeAccount<Delegation>>,
        partitioned_stake_reward: &PartitionedStakeReward,
        rent: &Rent,
        adjust_delegations_for_rent: bool,
        use_fixed_point_stake_math: bool,
    ) -> Result<StakeReward, DistributionError> {
        let stake_account = stakes_cache_accounts
            .get(&partitioned_stake_reward.stake_pubkey)
            .ok_or(DistributionError::AccountNotFound)?
            .clone();

        let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
        let StakeStateV2::Stake(meta, stake, flags) = stake_state else {
            // StakesCache only stores accounts where StakeStateV2::delegation().is_some()
            unreachable!(
                "StakesCache entry {:?} failed StakeStateV2 deserialization",
                partitioned_stake_reward.stake_pubkey
            )
        };
        account
            .checked_add_lamports(partitioned_stake_reward.inflation.stake_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;
        account
            .checked_add_lamports(partitioned_stake_reward.block_reward)
            .map_err(|_| DistributionError::ArithmeticOverflow)?;

        let mut new_stake = partitioned_stake_reward.inflation.stake;
        if adjust_delegations_for_rent {
            let minimum_balance = rent.minimum_balance(account.data().len());
            // The rewarded epoch is right before the distribution epoch
            let rewarded_epoch = distribution_epoch.saturating_sub(1);
            // The entry in `partitioned_stake_reward` contains the rewards,
            // calculated during the calculation phase
            let delegation_with_rewards = new_stake.delegation.stake;
            adjust_delegation_for_rent(
                &mut new_stake.delegation,
                rewarded_epoch,
                delegation_with_rewards,
                account.lamports(),
                minimum_balance,
            );
        } else {
            let expected_delegation = stake
                .delegation
                .stake
                .saturating_add(partitioned_stake_reward.inflation.stake_reward);
            assert_eq!(
                expected_delegation, new_stake.delegation.stake,
                "stake reward delegation must be consistent with the updated stake account \
                 lamport balance"
            );
        }
        account
            .set_state(&StakeStateV2::Stake(meta, new_stake, flags))
            .map_err(|_| DistributionError::UnableToSetState)?;
