### Title
Unvalidated `creator` account in `initialize_with_permission` allows permanently locking creator-fee funds - ([File: programs/cp-swap/src/instructions/initialize_with_permission.rs])

### Summary
`initialize_with_permission` takes a `creator` account with no signer requirement and no address/relationship constraint, then stores it verbatim as `pool_state.pool_creator`. This value is later used as the sole access-control anchor for withdrawing accumulated creator fees, exactly mirroring the reported class of bug: a user-supplied identifier is embedded directly into an access-control-relevant field without being validated against the actual authenticated party (a signer/connection-derived value).

### Finding Description
In `InitializeWithPermission`, the `creator` account is declared as:
```rust
/// CHECK: creator of pool
pub creator: UncheckedAccount<'info>,
``` [1](#0-0) 

There is no `Signer` requirement, no `address =` constraint tying it to `payer`, and no relation to `permission.authority`. Its key is passed straight into `pool_state.initialize(...)` as the pool's `pool_creator`: [2](#0-1) 

This is the direct analog of the reported bug: in the report, an unvalidated, user-supplied `ip_address` string is placed straight into a Redpanda ACL's `host` field, which later gates access; here, an unvalidated, caller-chosen `creator` pubkey is placed straight into `pool_state.pool_creator`, which later gates access to `collect_creator_fee`:
```rust
#[account(mut, address = pool_state.load()?.pool_creator)]
pub creator: Signer<'info>,
``` [3](#0-2) 

Because `pool_creator` can be set to any arbitrary pubkey (including a PDA, a mint, or any account with no known private key), no one can ever satisfy the `Signer` constraint in `collect_creator_fee`, permanently disabling that recovery path for the accrued `creator_fees_token_0`/`creator_fees_token_1`.

The only remaining recovery path, `collect_creator_fee_permissionless`, does not require `creator` to sign — it only checks `address = pool_state.load()?.pool_creator` on an `UncheckedAccount`, and creates an ATA owned by that address to receive the funds: [4](#0-3) [5](#0-4) 

If `pool_creator` is set to a PDA/address that has no corresponding program logic ever authorized to spend from an ATA it owns, funds routed there via the permissionless path become permanently unspendable — a definitive fund-freezing outcome, not merely a mislabeling issue.

By contrast, the plain, non-permissioned `initialize` instruction correctly requires `creator: Signer<'info>` [6](#0-5) , so `pool_creator` there is guaranteed to be a real, self-authenticated key — confirming that the missing validation in `initialize_with_permission` is the anomaly, not the intended design.

### Impact Explanation
`pool_creator` is the exclusive authority the protocol relies on for withdrawing accumulated creator trading fees (`creator_fees_token_0`, `creator_fees_token_1`), which are carved out of every swap's fee split via `Fees::split_creator_fee` [7](#0-6) . Because `creator` in `initialize_with_permission` is unauthenticated and unconstrained, a pool creator (who only needs a pre-issued `Permission` PDA, not any special trust regarding fee routing) can set `pool_creator` to an address nobody controls. This permanently freezes all creator-fee revenue generated by that pool's swappers — funds that are real economic value extracted from every trade but that become unrecoverable by anyone, including the legitimate creator/payer. This satisfies the "permanent freezing of user or LP/protocol funds" impact bar.

### Likelihood Explanation
Any account holding a permissioned `Permission` PDA can trigger this in a single `initialize_with_permission` call by simply passing an arbitrary pubkey (e.g., a random PDA, the `AUTH_SEED` authority PDA, or any keyless address) for the `creator` account — no special conditions, races, or additional privileges are required beyond the normal call to create a pool. It could also happen unintentionally (a UI or client bug supplying the wrong key), making this both an intentional-abuse and an accidental-misconfiguration risk with a straightforward, single-transaction trigger.

### Recommendation
Require `creator` in `InitializeWithPermission` to be a `Signer` (as in the unprivileged `Initialize` accounts struct), or explicitly constrain it (`address = payer.key()` / `address = permission.authority`) so the on-chain `pool_creator` value is always taken from an authenticated party rather than an arbitrary caller-supplied account, consistent with the report's short-term recommendation to derive identity from the connection rather than trusting user input.

### Proof of Concept
1. Attacker (or any address holding a valid `Permission` PDA created via `create_permission_pda`) calls `initialize_with_permission`, supplying:
   - `payer` = their own signer.
   - `creator` = an arbitrary pubkey with no known private key (e.g., a PDA derived from an unrelated seed, or the pool's own `authority` PDA) — since `creator` is `UncheckedAccount` with no signer/address constraint, this is accepted.
2. `pool_state.initialize(...)` stores this pubkey as `pool_creator` [2](#0-1) .
3. Ordinary swaps against the pool accrue `creator_fees_token_0/1` via the constant-product fee split.
4. `collect_creator_fee` can never be called because the `Signer` constraint on `creator` (`address = pool_state.load()?.pool_creator`) can never be satisfied by anyone [3](#0-2) .
5. `collect_creator_fee_permissionless` can technically be invoked by anyone to move the fees into an ATA owned by the unclaimable `pool_creator` address, but since no program logic exists to move funds out of an ATA owned by that arbitrary/keyless address, the tokens become permanently locked [4](#0-3) .
