### Title
`ERC20Transactor` escrows ERC20 tokens 1:1 by nominal transfer amount instead of actual balance delta, breaking fee-on-transfer/rebasing token invariants and causing fund leakage/DoS - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
Asset Hub's `ERC20Transactor` (a `TransactAsset` implementation used by `pallet-xcm`/the XCM executor to move ERC20 tokens between XCM `Location`s via `pallet-revive`) escrows ERC20 tokens in a `TransfersCheckingAccount` on withdraw and releases them on deposit. Both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` assume the ERC20's `transfer()` call moves exactly the nominal `amount` requested, and credit/debit the XCM `AssetsInHolding`/checking-account balance based on that nominal amount rather than the actual balance delta observed on the ERC20 contract. This is the same root-cause pattern as Nibiru's M-08 finding: a hard assumption of a static 1:1 relationship between an escrowed ERC20 balance and the accounting entry that represents it, which breaks for ERC20 tokens whose balance can diverge from the nominal transferred amount (fee-on-transfer / deflationary tokens, and rebasing tokens sitting in the checking account between withdraw and deposit).

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` (source `who`) calls the ERC20 `transfer()` function to move `amount` (derived purely from the XCM `Asset` via `Matcher::matches_fungibles`) into `TransfersCheckingAccount`: [1](#0-0) 

It only checks that the `transfer()` call succeeded and returned `true`; it never queries the checking account's ERC20 `balanceOf` before/after the call to determine the *actual* amount received. It then unconditionally credits `AssetsInHolding` with the full nominal `amount`: [2](#0-1) 

This is different from Nibiru's `convertCoinToEvmBornERC20`, which explicitly queries `actualSentAmount` via balance-before/after and uses that value for burning coins — Nibiru's bug was in the *other* direction (an unstated invariant about escrow availability), but the fundamental defect class ("assume ERC20 transferred amount == nominal `amount`, and that the escrow balance always matches what accounting believes it holds") is identical, and the polkadot-sdk analog is actually *more* naive since it doesn't even query actual transferred amount on the withdraw leg.

Symmetrically, `deposit_asset_with_surplus` releases the ERC20 from `TransfersCheckingAccount` to the beneficiary using the nominal `amount` recovered from `Matcher::matches_fungibles`, again with no verification that the checking account's real balance still matches the sum of nominal amounts it is presumed to be holding: [3](#0-2) 

`TransfersCheckingAccount` is a persistent on-chain account (`Get<AccountId>`), and the withdraw and deposit legs of a reserve-style cross-chain transfer are typically executed in separate XCM messages/blocks (e.g. outbound leg withdraws from sender into the checking account when the message departs; the return leg — or another party's inbound reserve-asset-deposit request — later triggers `deposit_asset_with_surplus` against the same checking account). Between these two events, the checking account's real ERC20 balance is fully exposed to the ERC20 contract's own logic:
- For fee-on-transfer / deflationary ERC20 tokens, the checking account will receive *less* than `amount` on `withdraw_asset_with_surplus`, yet the code credits the full nominal `amount` into `AssetsInHolding` (over-crediting the abstract balance relative to the true escrow).
- For rebasing ERC20 tokens (an ERC20 behavior explicitly called out as compatible/in-scope for support in similar EVM-bridging projects, and structurally identical to Nibiru's escrowed-ERC20 scenario), the checking account's real balance can change up or down while tokens sit escrowed there awaiting a later `deposit_asset_with_surplus` call, again decoupling the tracked nominal amount from the real, on-chain ERC20 balance.

This directly parallels the invariant Nibiru violated: "if an asset is created as [ERC20] and some amount is converted [into escrow], a balance … is left inside the [escrow] account in order to convert … back" — i.e., a static 1:1 mapping between the escrowed real ERC20 balance and the internal accounting figure used to authorize future releases.

### Impact Explanation
Two symmetric failure modes result, mirroring Nibiru's M-08:
1. If the checking account's real balance ends up *lower* than the nominal amount recorded as escrowed (fee-on-transfer withdrawal, or negative rebase while escrowed), a later `deposit_asset_with_surplus` for the full nominal `amount` will revert (`ERC20 contract transfer failed` / reverted), causing legitimate cross-chain transfers to fail, an availability/DoS impact, and potentially trapping assets in the XCM holding register (handled by the XCM trap/refund mechanism, but the underlying escrow accounting is still broken).
2. If the checking account's real balance ends up *higher* than the nominal amount (positive rebase while escrowed, or an over-credit from step 1), the surplus permanently accumulates and is unrecoverable through the normal transfer flow — a leakage of value from users who deposited more real value than the accounting tracked, benefiting no one and effectively burning excess balance in `TransfersCheckingAccount`.

Because `ERC20Transactor` is wired directly into Asset Hub Westend's XCM configuration and PRDoc `pr_7762.prdoc` confirms it's intended as the general-purpose mechanism to support arbitrary ERC20 assets (including ones addressable purely by their `AccountKey20` contract address) in XCM cross-chain transfers, this reaches real, permissionless XCM execution paths (`pallet_xcm::transfer_assets`/reserve transfers) with no privileged prerequisite — any user can trigger a withdraw/deposit cycle for any registered ERC20 asset location matched by `ERC20Matcher`. [4](#0-3) [5](#0-4) 

Consistent with the original Nibiru judging outcome (Medium, "compatibility issue... risk contained to the token itself"), this is a compatibility/accounting bug limited to non-standard ERC20 tokens (fee-on-transfer/rebasing), not a generic theft-of-funds primitive against well-behaved ERC20s or native chain assets — so it should be scoped as Medium, not Critical/High.

### Likelihood Explanation
Likelihood depends entirely on whether Asset Hub allows registering fee-on-transfer or rebasing ERC20 contracts as `pallet-revive` contracts reachable through `ERC20Matcher`/`IsLocalAccountKey20`. I was unable to find, within the indexed portion of the repository, an explicit allow-list or on-chain governance gate restricting which ERC20 contract bytecodes/behaviors can be matched by `ERC20Matcher` (it matches purely by location shape: local `AccountKey20`), nor could I locate a companion invariant check (e.g., a `balanceOf` sanity check) elsewhere in the withdraw/deposit paths or in `pallet-revive`'s XCM entry points. This suggests any deployed ERC20-compatible contract on the parachain (deployed permissionlessly via `pallet-revive`) could be targeted through this transactor, making the "erc20 with a non-standard `transfer()` behavior" precondition achievable by an ordinary, unprivileged user deploying their own contract and then transacting it through XCM. However, I could not fully verify (due to index size limits truncating `xcm_config.rs`) how strictly the config filters/permissions asset registration for this transactor, so the actual reachability and any additional safety gates are not fully confirmed.

### Recommendation
- In `withdraw_asset_with_surplus`, query the checking account's ERC20 `balanceOf` before and after the `transfer()` call and credit `AssetsInHolding` with the actual observed delta, not the nominal requested `amount` (mirroring what Nibiru eventually did for the ERC20→coin leg).
- In `deposit_asset_with_surplus`, similarly verify the actual amount transferred out of the checking account (via balance delta) matches expectations, and fail/refund gracefully rather than assuming the nominal amount was moved.
- Consider maintaining an explicit, per-asset tracked "escrowed balance" invariant that is checked against the real ERC20 `balanceOf(checking_account)` at both legs, and reject registration or use of ERC20 assets whose behavior (fee-on-transfer, rebasing) is incompatible with a 1:1 escrow assumption, consistent with the "Weird ERC20 tokens" guidance referenced in the original report.
- Add tests exercising fee-on-transfer and rebasing ERC20 mocks through the full withdraw→(time passes / rebase)→deposit cycle to catch balance drift.

### Proof of Concept
A full working local reproduction (deploying a custom fee-on-transfer or rebasing ERC20 via `pallet-revive`, registering it for XCM via `ERC20Matcher`, and driving it through `pallet_xcm` reserve-transfer withdraw/deposit legs across two blocks with an intervening rebase/fee) was not executed against this sandbox; I was not able to run Rust/FRAME integration tests in this environment. The finding is derived from direct code inspection of `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` in `erc20_transactor.rs`, which structurally lacks any actual-balance verification (confirmed absent by reading the full file), unlike Nibiru's post-fix pattern of computing `actualSentAmount`. A background Devin agent with full repository/toolchain access should:
1. Write a minimal `IERC20`-compatible fee-on-transfer/rebasing mock contract compiled for `pallet-revive`.
2. Register it via `ERC20Matcher`/`IsLocalAccountKey20` in a `xcm-emulator`/`xcm-executor` test harness for asset-hub-westend (or the `polkadot/xcm/xcm-builder` mock harness pattern, similar to `xcm-builder/src/tests/locking.rs`).
3. Execute a `WithdrawAsset` via `ERC20Transactor::withdraw_asset_with_surplus`, apply a rebase/fee between legs, then execute `DepositAsset` via `deposit_asset_with_surplus`, and assert on the discrepancy between `AssetsInHolding`'s recorded amount and the real ERC20 `balanceOf(TransfersCheckingAccount)` before/after, demonstrating either a failed deposit (DoS) or a stuck surplus (leakage).
