### Title
StatusHandler#process mutates commit statuses across repositories without repository-scope check - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)`, never calling the inherited `Handler#stacks`/`#repository_name` helpers that scope by `payload.dig('repository','full_name')`. Because the `commits` table only enforces uniqueness on `[sha, stack_id]` (not globally), a sha can legitimately exist as separate `Commit` rows in multiple stacks/repositories, and a signed status webhook from one repository will write a `CommitStatus` (and trigger deploy-relevant hooks) onto the `Commit` row(s) belonging to any other stack sharing that sha.

### Finding Description
The broken binding: `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` (the set of stacks the webhook is nominally scoped to, per `Handler#stacks`, [1](#0-0)  ) is supposed to equal the set of `Commit` rows a handler mutates. `PushHandler#process` respects this binding by calling `stacks.not_archived.where(branch:)` before acting [2](#0-1) . `StatusHandler#process`, however, does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no reference to `stacks` or `repository_name` at all [3](#0-2) . The two sides of the equality diverge: the payload's `repository.full_name` binds to one stack, but the write touches every `Commit` row with a matching sha, regardless of stack/repository.

Root cause: the `commits` table's unique index is `[sha, stack_id]`, not `[sha]` alone [4](#0-3) , so identical shas across different stacks (e.g. forks, or repositories that share git history) are an expected, supported data shape — yet `StatusHandler` treats sha as if it were globally unique to one repository.

Exploit flow: an attacker owns/administers "attacker/repo", which is registered as a Shipit stack, and that repository shares commit history (e.g., is a fork of, or was created from) "victim/repo", which is also tracked as a Shipit stack, so both stacks have a `Commit` row with the identical `sha`. The attacker legitimately triggers (or has their CI system emit) a GitHub `status` webhook for "attacker/repo" for that shared sha (e.g. forcing state `success`). This webhook is genuinely signed by GitHub for the attacker's own org, so it passes `WebhooksController#verify_signature`, which only validates that the payload is authentically from `repository_owner`'s GitHub App/org — it performs no check that the sha's owning stack matches that repository [5](#0-4) . `StatusHandler#process` then runs and calls `create_status_from_github!` on **every** `Commit` row across all stacks sharing that sha — including the victim's — writing a forged status onto the victim's commit.

Why existing guards fail: `verify_signature` authenticates *which organization sent the webhook*, not *which stack's data the webhook is allowed to mutate*; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of `sha`/`state`/etc., not repository scope; and `Handler#stacks`/`#repository_name`, the mechanism that would have enforced the missing check, is defined but simply never invoked by `StatusHandler`.

### Impact Explanation
`create_status_from_github!` → `Commit#add_status` can flip a commit's `state` to `success`, and on state-change it emits `Hook.emit(:deployable_status, ...)` and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [6](#0-5) . On a victim stack configured with continuous deployment, this can move that stack toward an unauthorized merge/deploy based on a forged CI status the attacker fully controls from their own repository — this is a cross-repository write of state (commit/task status) belonging to a repository the attacker does not own, matching the "Critical" impact category (unauthorized deploy resulting from a payload for one repository mutating another's commit/stack state). The attack is repeatable against any pair of stacks that happen to share a commit sha (forks, imported history, template repos, monorepo splits), and the attacker can retry for any sha they can discover (e.g., by observing the victim's public commit history on GitHub).

### Likelihood Explanation
Preconditions required: (1) the victim repository must be tracked as a Shipit stack; (2) the attacker's own repository must also be tracked as a Shipit stack; (3) the two repositories must share at least one identical commit sha (realistic for public forks, or any repo whose history the attacker's repo shares, e.g. via `git fork`/history import). No Shipit secrets, session, or team membership are needed — the attacker only needs their own legitimately-configured GitHub App/webhook to deliver a real, correctly-signed status event, or even the ability to craft any webhook if `webhook_secret` is unset for their org (`verify_webhook_signature` returns `true` when no secret is configured) [7](#0-6) . This is low-cost and fully repeatable — every push of a CI status against a shared sha reaches every stack containing that sha.

### Recommendation
Scope `StatusHandler#process` to the stacks implied by the payload, mirroring `PushHandler`: resolve the repository via `Handler#stacks` (or `Repository.from_github_repo_name(repository_name)`) and restrict the `Commit` lookup to `stacks.flat_map(&:commits)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status webhook can only mutate commits belonging to stacks under the repository named in `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (e.g. add to `test/models/shipit/webhooks/handlers/status_handler_test.rb`, out of scope for this engine's own `test/**` per audit rules, but shown as the exploit proof):

```ruby
test "StatusHandler leaks status writes across stacks sharing a sha, unlike PushHandler" do
  victim_stack = shipit_stacks(:shipit)                 # repository: "shopify/shipit-engine"
  attacker_stack = Shipit::Stack.create!(repository: Shipit::Repository.create!(owner: 'attacker', name: 'repo'))

  shared_sha = 'a' * 40
  victim_commit   = victim_stack.commits.create!(sha: shared_sha, message: 'victim', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'attacker', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  payload = {
    'sha' => shared_sha, 'state' => 'success', 'context' => 'ci',
    'repository' => { 'full_name' => 'attacker/repo' }
  }

  # BEFORE: equality holds - victim stack has no status for this webhook
  assert_equal 0, victim_commit.statuses.count

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # AFTER: the binding is broken - the attacker's webhook wrote a status onto the victim's commit
  assert_equal 1, victim_commit.reload.statuses.count   # FAILS the security expectation: should remain 0
  assert_equal 1, attacker_commit.reload.statuses.count # legitimate write

  # Contrast with PushHandler, which is correctly scoped by repository_name and would not touch victim_stack
  push_payload = { 'ref' => 'refs/heads/master', 'after' => shared_sha, 'repository' => { 'full_name' => 'attacker/repo' } }
  Shipit::GithubSyncJob.expects(:perform_later).with(has_entry(stack_id: attacker_stack.id)).once
  Shipit::Webhooks::Handlers::PushHandler.call(push_payload) # never touches victim_stack.id
end
```

This asserts that `StatusHandler` (unscoped) causes a write on `victim_commit` for a webhook whose `repository.full_name` names only `attacker/repo`, while `PushHandler` (scoped via `stacks`) only ever acts on the stack matching `repository.full_name`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
