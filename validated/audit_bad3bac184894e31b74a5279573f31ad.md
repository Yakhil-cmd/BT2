## Analysis

The M-2 report describes a state-consistency bug: one field (`amount`) is *acted upon* conditionally, but a different, stale/zero value ends up being *written* to persistent state (`accrued`), breaking the invariant that "the amount transferred == the amount recorded."

The strongest structural analog in this Shipit engine is a **verification/write binding mismatch in the webhook pipeline**: the field used to select and verify the HMAC signature (`repository_owner`, used to pick the `GitHubApp`/`webhook_secret`) is **not the same field** that downstream handlers use to decide which `Repository`/`Stack` gets mutated (`repository.full_name`).

`WebhooksController#verify_signature` derives the signing organization from the payload itself, with a fallback: [1](#0-0) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That value is used only to look up which `GitHubApp` (i.e. which `webhook_secret`) verifies the HMAC: [2](#0-1) 

Once verification passes, the raw, attacker-supplied `params` (not the verified `repository_owner`) are handed unchanged to every registered handler: [3](#0-2) 

Every handler resolves the repository/stack to mutate from a **separate field** in the same payload, `repository.full_name`, with no cross-check against `repository_owner`/the organization whose secret validated the signature: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then writes/syncs commits for whatever stack matches that `repository_name`: [5](#0-4) , and `StatusHandler` creates commit statuses the same way: [6](#0-5) .

**Why this does not cross the required trust boundary in a multi-org Shipit deployment:** in the single-app config (`Shipit.github_default_organization` is `nil`), there is only one `webhook_secret` for the whole instance, so `repository_owner` is irrelevant to trust and any signed payload is equally trusted regardless of which "organization" or "repository" field it names — this is the documented, single-tenant model (`lib/shipit.rb#github`, `#github_default_organization`). In the **multi-org config** (`secrets.github` keyed by organization, `github_app_config(organization)`), the trust boundary is per-organization: each org's admins choose their own `webhook_secret` and only GitHub itself (or someone who possesses that org's specific secret) can sign a payload with it. But the code lets the *content of the payload itself* pick which secret is checked, and never verifies that the `repository.full_name` used later actually belongs to that same `repository_owner`. A user with legitimate push access to their own GitHub org/repo (which is a valid Shipit-connected org — not a privileged Shipit account, not an `ApiClient` token, not a leaked private key) can craft a payload where `repository.owner.login`/`organization.login` is their own org (so the signature check uses their own, valid webhook secret and succeeds), while `repository.full_name` names a **different, victim** organization/repository configured in the same Shipit instance. This is exactly the "organization that authenticated versus the repository that is written" binding break called out in the rules.

However, I could not fully verify from the available context that a genuinely unprivileged, cross-organization attacker can trigger a delivery with an attacker-chosen raw body/signature pair to this endpoint without already controlling a webhook delivery mechanism that GitHub itself would sign correctly per-org (GitHub signs with the *destination* App's registered secret, tied to the repository that actually triggered the event — GitHub does not let an org's key sign for another org's `full_name` under normal webhook delivery). Exploiting this fully requires either (a) the attacker's org's Shipit-configured GitHub App webhook secret being reused/known, and (b) being able to submit a raw HTTP POST directly to Shipit's `/github/webhooks` endpoint with a forged body (bypassing actual GitHub delivery) — which is possible since nothing but the HMAC ties the request to GitHub. Given `verify_webhook_signature` only checks HMAC-SHA1 over the raw body using a *secret the attacker's own org already knows* (it's the attacker's own webhook secret, since they administer that org's Shipit GitHub App installation), the attacker can indeed self-sign an arbitrary payload naming a victim `repository.full_name`. This does not require any Shipit session, `ApiClient` token, or private key — only administration of one org connected to the shared Shipit instance, and knowledge of that org's own webhook secret (which they own/created themselves).

This satisfies the required impact bar: cross-repository/cross-organization writes — the attacker can, e.g., cause `PushHandler` to call `stack.sync_github(expected_head_sha:)` [5](#0-4)  or inject/forge `Commit` statuses [6](#0-5)  against a victim organization's stack whose repository they do not own, using only their own organization's webhook credentials.

### Title
Webhook signature verification keys off `repository.owner.login`/`organization.login` while handlers act on the unrelated `repository.full_name`, allowing cross-organization writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used for HMAC verification from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. All handlers, however, resolve which `Repository`/`Stack` to mutate from an independent payload field, `payload.dig('repository','full_name')`. In a multi-organization Shipit deployment (`Shipit.github_app_config`), the two fields are never cross-checked, so a payload can be crafted where the "authenticating" org differs from the "written" repository.

### Finding Description
- Verification binding: `repository_owner` → `Shipit.github(organization: repository_owner)` → `verify_webhook_signature`. [2](#0-1) 
- Write binding: `Handler#repository_name` → `Repository.from_github_repo_name(repository_name)`. [4](#0-3) 
- No code path enforces `repository_owner == repository.full_name.split('/').first` (or equivalent) before dispatching to handlers in `WebhooksController#create`. [3](#0-2) 

Because each organization in a multi-org config supplies its own `webhook_secret` (`github_app_config(organization)`), the security guarantee GitHub relies on is "a payload signed with org X's secret only describes org X's repositories." Shipit breaks that guarantee: it trusts *any* repository name embedded in a payload signed by *any* configured organization's secret.

### Impact Explanation
An org administrator (unprivileged w.r.t. Shipit itself — no Shipit session, `ApiClient`, or GitHub App private key needed) who legitimately controls one org's webhook secret in a shared multi-tenant Shipit instance can forge webhook deliveries that name a victim organization's repository, causing `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc. to write/sync state (commit statuses, sync jobs, check-run refreshes) against stacks/repositories they don't own — a cross-repository write, matching the accepted High/Critical impact bar.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (`secrets.github` keyed by org) where the attacker administers at least one configured organization and can POST directly to the webhooks endpoint (which is unauthenticated except for the HMAC check). This is a realistic Shipit deployment pattern documented in `docs/setup.md`'s multi-org examples.

### Recommendation
In `WebhooksController`, after verifying the signature, assert that the resolved `repository_owner` matches the owner segment of `payload.dig('repository','full_name')` (and of `organization.login` when present) before dispatching to `Shipit::Webhooks.for_event`. Reject (422) any payload where these disagree.

### Proof of Concept
1. Configure Shipit with two organizations, `org-attacker` and `org-victim`, each with its own `github.webhook_secret` (multi-org config as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who administers `org-attacker` and therefore knows `org-attacker`'s `webhook_secret`, crafts a `push` payload JSON body with `repository.owner.login = "org-attacker"` (or omits it and sets `organization.login = "org-attacker"`) but `repository.full_name = "org-victim/some-repo"`.
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker secret, raw_body)>` and POSTs it to `/github/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-attacker")` and the signature verifies successfully. [2](#0-1) 
5. `PushHandler#process` resolves `stacks` via `repository_name = "org-victim/some-repo"` and calls `stack.sync_github(expected_head_sha:)` on the victim's stack. [5](#0-4)
