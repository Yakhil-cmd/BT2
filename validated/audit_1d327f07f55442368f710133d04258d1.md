### Title
Webhook signature verification uses `repository.owner.login`/`organization.login` while `MembershipHandler` trusts `organization.login` for the row it writes — cross-org Team forgery - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb], [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-org Shipit deployment, `WebhooksController#verify_signature` picks the signing organization from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0)  while `MembershipHandler#find_or_create_team!` writes `team.organization = params.organization.login` unconditionally [2](#0-1) . An attacker who controls the webhook secret for one configured org can put that org's login under `repository.owner.login` (for signature routing) while putting a different, victim org's login under `organization.login` (for the row that gets created), producing a `Team` record that impersonates the victim org, verified only by the attacker's own secret.

### Finding Description
The broken binding, stated as an equality that must hold but does not:

`repository_owner` (the org whose secret verified the payload, read via `params.dig('repository','owner','login') || params.dig('organization','login')` in `WebhooksController#repository_owner`) MUST equal `params.organization.login` (the org written into the `Team` row by `MembershipHandler#find_or_create_team!`).

These two reads pull from two independently attacker-controlled JSON keys (`repository.owner.login` and `organization.login`) with no cross-check anywhere in the request lifecycle:
- `WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)` and verifies the HMAC using that org's `webhook_secret` [3](#0-2) .
- The full raw JSON body (including the attacker-added `repository` key) is then handed unmodified to `MembershipHandler.call(params)` [4](#0-3) .
- `MembershipHandler`'s `ExplicitParameters` schema only declares `action`, `team`, `organization`, `member` [5](#0-4) ; it does not declare or validate `repository`, so an extra `repository` key added purely to steer signature verification passes through unnoticed (other handlers in the same file family routinely ignore undeclared GitHub payload fields, confirming `ExplicitParameters` does not reject unknown top-level keys).
- `find_or_create_team!` then uses `params.team.id` (attacker-controlled `github_id`) to decide whether to create a new `Team`, and if no row exists for that id, creates one with `organization = params.organization.login` — the victim org's login, not the org that actually signed the request [6](#0-5) .

Attack request (multi-org config required, see below): attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, signature computed with attacker-org's `webhook_secret`, and body:
```json
{
  "action": "added",
  "team": { "id": 42, "name": "x", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "victim-org" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "attacker-org" } }
}
```
`repository_owner` resolves to `attacker-org` (because `repository.owner.login` is checked first), so `verify_signature` succeeds against attacker-org's own secret. `MembershipHandler` then creates `Team(organization: 'victim-org', github_id: 42, slug: 'developers', ...)` and adds `attacker-login` as a member.

Existing guards do not stop this: `drop_unhandled_event` only checks the event type is registered [7](#0-6) ; the `ExplicitParameters` schema for `MembershipHandler` validates types/presence of `organization.login` but has no notion of "the org that signed this," so it cannot detect divergence; there is no comparison anywhere between `repository_owner`/signing org and `params.organization.login`.

### Impact Explanation
The attacker writes a `Team` row attributed to `victim-org` — an organization they neither administer nor authenticated as — and adds themselves as a member, using only credentials for a different, attacker-controlled org. If the attacker chooses `slug` to match a team handle listed in `Shipit.github_teams`'s OAuth restriction config (`Team.find_or_create_by_handle` matches by `organization`+`slug`, not by `github_id`) [8](#0-7) , the forged row can be returned to future authorization lookups instead of (or ahead of) the real team, letting the attacker's account satisfy team-based OAuth login authorization for `victim-org`. This matches the High/Critical category: escalation into `Shipit.github_teams` authorization / authentication bypass on the victim's tenant, driven by a payload for one org mutating another org's records. It is repeatable against any `github_id` not yet used and any victim org configured on the same Shipit instance, as long as the attacker controls the webhook secret of at least one other configured org on that instance.

### Likelihood Explanation
This requires the "Using Multiple GitHub Applications" deployment mode documented in `docs/setup.md`, where a single Shipit instance is configured with several orgs under `secrets.github`, keyed by org login [9](#0-8) , and the attacker legitimately administers one of those configured orgs (thus knowing its `webhook_secret`) while a different org on the same instance is the victim. Given that precondition (explicitly stated in the question), the attack cost is a single crafted HTTP POST with no privileged Shipit access, no session, and no knowledge of the victim's or any other org's secret — fully repeatable and scriptable.

### Recommendation
In `WebhooksController#verify_signature`/`repository_owner`, and in every `Handler` subclass that writes org-scoped records, require that the org used for signature verification be the same value used for record attribution. Concretely: derive `repository_owner` the same way the handler derives the org it will persist (e.g. always from `organization.login` for org-level events like `membership`, not from an unrelated/attacker-added `repository.owner.login`), and reject the payload (422) if a `repository.owner.login` is present but disagrees with `organization.login`. More robustly, pass the verified `repository_owner`/signing org into each `Handler` and have `MembershipHandler#find_or_create_team!` assert `params.organization.login == verified_organization` before creating/mutating any `Team`.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (multi-org secrets fixture, e.g. `test/dummy/config/secrets_double_github_app.yml` with `OrgOne`/`OrgTwo`):
```ruby
test ":membership webhook signed by OrgOne can forge a Team for OrgTwo" do
  @request.headers['X-Github-Event'] = 'membership'
  payload = {
    action: 'added',
    team: { id: 42, name: 'x', slug: 'developers', url: 'https://example.com' },
    organization: { login: 'OrgTwo' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'OrgOne' } } # signing org != organization.login
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', Shipit.github(organization: 'OrgOne').webhook_secret, payload)
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { Team.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  team = Team.find_by(github_id: 42)
  assert_equal 'OrgTwo', team.organization       # written org
  assert team.members.exists?(login: 'attacker-login')
  # Signature was verified only against OrgOne's secret:
  # Shipit.github(organization: 'OrgOne').verify_webhook_signature(...) == true
  # despite the created Team belonging to OrgTwo — proving the equality
  # repository_owner('OrgOne') == params.organization.login('OrgTwo') is false yet accepted.
end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
