### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while event processing trusts a separate, unverified `repository.full_name` (and, for `status`, no repository scoping at all) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload look up the target `Stack`/`Repository`/`Commit` using a *different* field of the same JSON body — `repository.full_name` for most handlers, and *no repository field at all* for `StatusHandler`. Because the HMAC covers the raw JSON body as a whole, anyone who legitimately knows the webhook secret for **any one** onboarded GitHub organization can forge a payload whose `owner.login` matches their own org (so the signature checks out) while `full_name`/`sha` reference a **different, victim** organization's repository/commit. This breaks the intended binding "organization authenticated == repository/commit written."

### Finding Description
- Signature verification: `repository_owner` is computed as `params.dig('repository','owner','login') || params.dig('organization','login')`, and this value alone selects the `GitHubApp`/secret used to verify the raw request body. [1](#0-0) 

- Event dispatch then hands the *same raw JSON* to handlers that resolve the target using unrelated fields:
  - `Handler#repository_name` reads `payload.dig('repository', 'full_name')`, independent of `owner.login`. [2](#0-1) 
  - `PushHandler#process` uses `stacks` (derived from `full_name`) and pushes an attacker-chosen `after` sha into `stack.sync_github`. [3](#0-2) 
  - `StatusHandler#process` does not scope by repository at all — it looks up `Commit.where(sha: params.sha)` **globally** across the entire Shipit instance and calls `commit.create_status_from_github!(params)`. [4](#0-3) 

- Multi-organization deployments are an explicitly supported, documented configuration (each org has its own `app_id`/`webhook_secret`), meaning distinct, independently-known secrets legitimately coexist on one Shipit instance. [5](#0-4) [6](#0-5) 

- A forged `status` event landing on a commit gates real deploy/merge safety logic: `Commit#deployable?` and `add_status` trigger `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` when the new status is `success`/`pending`, which is the exact mechanism that marks a commit safe to deploy or to auto-merge. [7](#0-6) [8](#0-7) 

**Binding broken (equality that should hold but doesn't):**
`organization authenticated by verify_signature (repository.owner.login / organization.login)` **==** `organization/repository actually mutated by the handler (repository.full_name for push/pull_request handlers, or nothing at all for status)`

Before the PR/request: an org's webhook secret can only produce events that are processed as belonging to that same org, because GitHub itself always sends `owner.login` and `full_name` consistent with the real originating repository.
After an attacker-crafted request: the attacker (an org admin/owner of any one onboarded org — a valid, low-privilege trust boundary for a multi-tenant Shipit instance) can decouple these two fields since they control the entire raw body and only need to compute HMAC-SHA1 with their own known secret.

### Impact Explanation
- For `push`: an attacker with legitimate access to organization A's webhook secret can forge a `push` event where `repository.owner.login = "A"` (passes signature check) and `repository.full_name = "victim-org/victim-repo"`. `PushHandler` calls `stack.sync_github(expected_head_sha: <attacker sha>)` on the victim's stack — this can desynchronize the victim stack's tracked head or resurface/select non-current commits, corrupting the record of "what is deployed/deployable" for a repository the attacker does not own.
- For `status`: the lack of *any* repository scoping is worse — an attacker can forge a `success` status for **any commit sha existing anywhere on the instance**, as long as they know a valid secret for *any* onboarded org. This can flip `Commit#deployable?` to true for a victim's pending/blocked commit and trigger `stack.schedule_merges`, i.e. influence automatic merge-queue behavior / mark a commit falsely "green," which lines up with the "unauthorized deploy/merge" impact bucket.
- This satisfies the required High-tier impact category: escalation of authorization/trust boundaries across repositories without holding credentials scoped to the victim repository — i.e., a cross-repository write using only your own organization's legitimately-known secret.

### Likelihood Explanation
Requires only that the attacker be a legitimate admin/owner of **one** GitHub organization onboarded to a shared, multi-org Shipit instance (a documented, supported configuration) — no compromise of Shipit internals, no `ApiClient` token, no `GITHUB_TOKEN`, and no access to the victim org's secret. This is a realistic scenario for any shared Shipit deployment servicing multiple orgs/teams, and requires no timing/race window (unlike the front-run analog in the source report) — it is a deterministic, repeatable payload-forging attack.

### Recommendation
Bind the field used for the HMAC organization lookup to the field(s) actually consumed by each handler: after signature verification, re-derive `repository_owner` from the exact `repository.full_name` (or the `sha`'s resolved commit's stack owner) that will be used downstream, and reject the request if the two disagree. For `StatusHandler`, scope the `Commit` lookup to a specific stack/repository derived from a value that was itself covered and cross-checked against the verified organization, rather than a global `sha` lookup. Alternately, verify signature per-organization only for organizations whose registered repositories match the `full_name` in the payload.

### Proof of Concept
1. Configure Shipit with two orgs (`orgA`, `orgB`) as documented in `docs/setup.md` (multi-org github config), each with its own `webhook_secret`. Assume attacker is an admin of `orgA` (knows `orgA`'s `webhook_secret`) and `orgB/victim-repo` is a Repository/Stack already onboarded.
2. Attacker crafts a `status` payload:
   ```json
   {
     "sha": "<sha-of-a-real-commit-in-orgB/victim-repo>",
     "state": "success",
     "context": "ci/forged",
     "repository": { "owner": { "login": "orgA" } }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` and POSTs to `/webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner == "orgA"`, verifies successfully against `orgA`'s secret [9](#0-8) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim commit in `orgB/victim-repo` — and calls `create_status_from_github!`, marking it `success` and potentially triggering `stack.schedule_merges` on a repository the attacker has no access to [4](#0-3) [8](#0-7) .

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
