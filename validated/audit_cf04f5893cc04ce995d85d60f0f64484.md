### Title
CCMenu API endpoint bypasses per-token stack scoping, letting a stack-scoped token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that a scoped `ApiClient` (one created with a `stack_id`) may only see the stack(s) it was authorized for, by filtering the `Stack` relation through `current_api_client.stack_id` before resolving `params[:stack_id]`. `Shipit::Api::CCMenuController` overrides this resolution and looks up the stack directly from the global `Stack` table, never checking whether the authenticated client is restricted to a specific stack.

### Finding Description
The base controller binds "stack a token authorises" to "stack a token touches" via the `stacks`/`stack` helpers: [1](#0-0) 

```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Any controller that relies on this `stack` method inherits the guarantee that a token scoped to stack A cannot resolve stack B. `CCMenuController`, however, defines its own `stack` method that queries `Stack` directly, ignoring `current_api_client` entirely: [2](#0-1) 

```
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

`require_permission :read, :stack` only checks that the `permissions` array contains `read:stack`; it never checks `stack_id` against the resolved stack: [3](#0-2) 

The result is a binding break: `client.stack_id == requested_stack.id` is asserted by `BaseController#stack`, but `CCMenuController#stack` asserts nothing, so `client.stack_id != requested_stack.id` is accepted anyway.

This is directly reachable in the intended workflow: `CCMenuUrlController` mints (or reuses) an `ApiClient` scoped with `permissions: %w[read:stack]` per user, embeds its `authentication_token` in a "CCMenu URL" tied to one specific stack: [4](#0-3) 

Whoever holds that per-stack CCMenu URL/token is expected to only be able to poll that one stack. Because `CCMenuController#stack` bypasses the `stacks` scoping, that same token can be replayed with a different `stack_id` query parameter to read the build/deploy status (name, activity, `lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of **any** stack in the installation, not just the one the URL/token was generated for. This is confirmed by tests that only exercise the "own stack" path and never assert isolation across stacks: [5](#0-4) .

### Impact Explanation
This is an unauthenticated-read-of-stack-state class of issue for any recipient of a single CCMenu URL (which is treated as a low-trust, semi-public "status badge" credential, often embedded in CI dashboards). Instead of exposing status for one stack, it exposes status of every stack managed by the Shipit instance (deploy activity, lock status, last build outcome) to anyone holding one such token, matching the High-severity criterion "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High likelihood: exploitation requires only a single valid CCMenu token (which is designed to be distributed, e.g. embedded in CI dashboard tools) and manipulation of the `stack_id` query parameter — no additional privilege, secret, or session is needed beyond what the feature already grants for one stack.

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the scoped `stacks` relation (i.e., reuse/inherit `BaseController#stack`, or explicitly filter by `current_api_client.stack_id` when present) instead of querying `Stack` directly, so the same "token authorises == token touches" invariant enforced elsewhere in the API is preserved here.

### Proof of Concept
1. As an authenticated user, visit a stack's page and fetch its CCMenu URL via `CCMenuUrlController#fetch`, obtaining a token scoped (via `stack:` association in typical deployments, or reused) with `permissions: ["read:stack"]`.
2. Call `GET /api/stacks/:stack_id_A/ccmenu.xml?token=<token>` — succeeds, returns stack A's status (expected).
3. Call `GET /api/stacks/:stack_id_B/ccmenu.xml?token=<token>` for an unrelated stack B — because `CCMenuController#stack` calls `Stack.from_param!` directly instead of the scoped `stacks` relation used by `BaseController#stack`, this also succeeds and returns stack B's status, even though the token was never authorized for stack B.
