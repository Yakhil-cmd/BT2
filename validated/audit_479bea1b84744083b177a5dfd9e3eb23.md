### Title
Unauthenticated P2P Peer Can Evict Legitimate Bridge Transactions via Spoofed `ServiceChainInvalidTxResponseMsg` — (`node/sc/sub_bridge_handler.go`)

### Summary
`handleParentChainInvalidTxResponseMsg` unconditionally removes transactions from the `bridgeTxPool` based on peer-supplied `ErrStr` and `TxHash` fields, with no verification that the sending peer is the legitimate parent-chain bridge node. Any peer that completes the SubBridge P2P handshake can forge this message and permanently evict in-flight value-transfer handle transactions from the pool.

### Finding Description

`HandleMainMsg` dispatches `ServiceChainInvalidTxResponseMsg` (code `0x09`) directly to `handleParentChainInvalidTxResponseMsg(msg)`, passing only the raw message — the peer identity `p` is dropped entirely at the dispatch site. [1](#0-0) 

Inside the handler, the only check is whether the `ErrStr` field equals `blockchain.ErrGasPriceBelowBaseFee.Error()`. If it does, `RemoveTx` is called unconditionally: [2](#0-1) 

The `bridgePeerSet.Register` function performs no identity validation — any peer that passes the protocol handshake (matching `NetworkId` and `ProtocolVersion`) is admitted: [3](#0-2) 

The handshake itself only validates `NetworkId` and `ProtocolVersion`; the `ChainID` field is accepted verbatim from the remote peer's status message: [4](#0-3) 

The SubBridge runs a dedicated `bridgeServer` (separate from the main chain P2P server) and accepts inbound connections from any peer up to `maxPeers`: [5](#0-4) 

`broadcastServiceChainTx` sends pending bridge transactions (including handle-value-transfer txs) to **all** connected peers whose `ChainID` matches `parentChainID`. An attacker sets their `ChainID` to match during the handshake and immediately receives the target tx hashes: [6](#0-5) 

### Impact Explanation

When VTRecovery is disabled (`config.VTRecovery = false`), `AddRecovery` returns immediately without starting any retry goroutine: [7](#0-6) 

With no recovery goroutine running, the evicted handle-value-transfer transaction is never re-submitted. The corresponding `RequestValueTransfer` event on the source chain remains unhandled, and the user's KAIA or ERC20 assets are permanently locked in the bridge contract. This is a durable, unauthorized loss of bridged assets caused entirely by a forged P2P message from an unauthenticated peer.

Even with VTRecovery enabled, the attacker can continuously re-connect and re-send the spoofed message faster than the recovery interval, causing sustained bridge disruption.

### Likelihood Explanation

The SubBridge's bridge P2P port is publicly reachable by default (no IP allowlist is enforced in code). The attacker only needs to know the port, match the public `NetworkId` and `ProtocolVersion`, and craft a valid RLP-encoded `[]InvalidParentChainTx`. The target tx hashes are delivered to the attacker automatically by `broadcastServiceChainTx` once they connect. No privileged access, key compromise, or validator collusion is required.

### Recommendation

1. **Authenticate the sender**: Track which peer is the legitimate parent-chain bridge peer (e.g., by static node ID or operator-configured allowlist) and reject `ServiceChainInvalidTxResponseMsg` from any other peer inside `HandleMainMsg`.
2. **Pass and check the peer in the handler**: Change `handleParentChainInvalidTxResponseMsg` to accept the `BridgePeer` argument and verify it against the known parent-chain peer before acting.
3. **Cross-validate on-chain**: Before removing a tx, verify with the parent-chain RPC that the tx was actually rejected (e.g., check that the tx is absent from the parent mempool and has no receipt), rather than trusting the peer's assertion.

### Proof of Concept

1. Connect to the SubBridge's bridge P2P port; complete the handshake with matching `NetworkId`/`ProtocolVersion` and `ChainID` set to the known parent chain ID.
2. Wait to receive a `ServiceChainTxsMsg` — this delivers the pending handle-tx hashes.
3. Send a `ServiceChainInvalidTxResponseMsg` (code `0x09`) containing `[{TxHash: <observed_hash>, ErrStr: "gas price is below the base fee"}]`.
4. Observe via logs that `handleParentChainInvalidTxResponseMsg` logs `"Removed bridge tx"` and the tx disappears from `bridgeTxPool.Get(hash)`.
5. With `VTRecovery: false` in the SubBridge config, confirm the value transfer is never completed on the parent chain and the user's assets remain locked in the bridge contract.

func (p *baseBridgePeer) readStatus(network uint64, status *statusData) error {
	msg, err := p.rw.ReadMsg()
	if err != nil {
		return err
	}
	if msg.Code != StatusMsg {
		return errResp(ErrNoStatusMsg, "first msg has code %x (!= %x)", msg.Code, StatusMsg)
	}
	if msg.Size > ProtocolMaxMsgSize {
		return errResp(ErrMsgTooLarge, "%v > %v", msg.Size, ProtocolMaxMsgSize)
	}
	// Decode the handshake and make sure everything matches
	if err := msg.Decode(&status); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	if status.NetworkId != network {
		return errResp(ErrNetworkIdMismatch, "%d (!= %d)", status.NetworkId, network)
	}
	if int(status.ProtocolVersion) != p.version {
		return errResp(ErrProtocolVersionMismatch, "%d (!= %d)", status.ProtocolVersion, p.version)
	}
	return nil
}

func (ps *bridgePeerSet) Register(p BridgePeer) error {
	ps.lock.Lock()
	defer ps.lock.Unlock()

	if ps.closed {
		return errClosed
	}
	if _, ok := ps.peers[p.GetID()]; ok {
		return errAlreadyRegistered
	}
	ps.peers[p.GetID()] = p

	return nil
}
