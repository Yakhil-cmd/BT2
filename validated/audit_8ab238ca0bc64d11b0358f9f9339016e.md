### Title
Cross-call replay of the same Bitcoin lockup outpoint allows double-counting of L1-locked sats - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`verify-l1-lockups`/`validate-l1-lockup` in `pox-5.clar` only deduplicate lockup outpoints *within a single call* (a single `list 10` of outputs folded with a `seen-outpoints` accumulator that starts empty every invocation). There is no persistent, contract-level map recording which Bitcoin outpoints have already been credited toward a bond, so the same Bitcoin transaction output can be submitted again in a later call to accrue sats-credit a second time.

### Finding Description
`verify-l1-lockups` builds its `seen-outpoints` list fresh on every call: [1](#0-0) 

and `validate-l1-lockup` only checks `(is-none (index-of? seen-outpoints outpoint))` against that call-local list before appending the outpoint and summing `amount` into `sum`: [2](#0-1) [3](#0-2) 

Nothing in the two related fold helpers that subsequently mutate the accounting state — `add-staker-to-bond-cycles`/`add-staker-to-bond-for-cycle`, which increment `total-shares-staked-for-cycle` and `signer-shares-staked-for-cycle` by `amount-sats` — checks against a global "outpoint already used" registry: [4](#0-3) 

The equality this is supposed to preserve is: `sum(sats credited to a staker's bond via L1-lockup proofs) == sum(sats actually locked in distinct, unspent Bitcoin lockup outputs)`. Because deduplication is scoped only to the list of outputs passed in a single call, a staker (or a delegate acting on the staker's behalf) can call the L1-lockup-verification/registration flow multiple times, each time re-submitting the same still-locked Bitcoin outpoint (with its still-valid header/merkle proof and unlock height), and have its `amount` re-added to `sum` — and from there into `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle` for a bond index — every time. Since the check `verify-block-header`/`verify-merkle-proof`/`get-bitcoin-tx-output?` only prove the output *exists and is unspent on the Bitcoin side*, not that it has never previously been counted on the Stacks side, the same physical BTC lockup can back multiple registrations (e.g., under multiple `bond-index` values, or the same bond re-registered), inflating recorded stacked/delegated sats beyond what is actually locked.

### Impact Explanation
This breaks the double-counting-of-a-commitment guard explicitly called out as in-scope Critical impact: the same L1-locked BTC is used to justify more sats-denominated stacking weight/rewards than were actually locked. This inflates a staker's/signer's `signer-shares-staked-for-cycle` and `total-shares-staked-for-cycle`, which feed directly into reward-per-share accounting (`settle-rewards`/`settle-staker-rewards`), letting the attacker claim sBTC rewards disproportionate to the BTC genuinely locked — an unbacked-reward / double-counting condition.

### Likelihood Explanation
Requires no special privilege — any staker who owns a valid L1 lockup UTXO can invoke the registration path more than once with the same proof data, since nothing prevents replay at the contract level; the barrier is purely how many times the off-chain caller chooses to submit the same output. Likelihood depends on whether the driving public function (not fully located within the available context) restricts callers to a single registration per bond/staker or otherwise externally enforces one-time use — this could not be conclusively confirmed from the excerpts reviewed, so this should be validated against the full public entry point that invokes `verify-l1-lockups` (e.g., a `register-for-bond`/rollover function) before treating this as certain.

### Recommendation
Maintain a persistent map (e.g., `used-l1-outpoints: {txid, output-index} -> bool` or tied to `bond-index`) that is checked and set atomically as each `validate-l1-lockup` output is accepted, rather than relying solely on the call-scoped `seen-outpoints` list, so that a given Bitcoin outpoint can only ever be credited once across the contract's lifetime (or once per bond, per the intended design).

### Proof of Concept
1. Staker locks BTC in a valid timelock output; obtains header/merkle-proof/tx data for the UTXO.
2. Staker calls the pox-5 L1-lockup registration entry point (which calls `verify-l1-lockups`) with this UTXO, successfully crediting `amount` sats toward bond A's `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle`.
3. Staker calls the same entry point again (or registers a second bond) with the identical UTXO/proof. Because `seen-outpoints` is reinitialized empty in `verify-l1-lockups` for this new call, `validate-l1-lockup` does not detect the reuse and again returns `sum = amount`, crediting the same BTC a second time via `add-staker-to-bond-cycles`.
4. The staker/signer's on-chain recorded staked sats now exceed the BTC actually locked, inflating reward-per-token claims.

Note: step 3's exact feasibility (single-registration-per-bond restriction) depends on the full body of the public function that drives `verify-l1-lockups`, which was not fully retrieved before this session's tool budget was exhausted — this should be verified directly in `pox-5.clar` to confirm there is no other unseen guard (e.g., a bond-index one-time-registration flag) that would already prevent this replay.
