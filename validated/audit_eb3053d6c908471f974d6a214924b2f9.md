### Title
AA trigger's `address`/`initial_address` is bound to the unit's first author, not the actual output owner — misdirected bounce refunds in multi-authored triggers - ([File: aa_composer.js])

### Summary
`getTrigger()` in `aa_composer.js` sets `trigger.address` to `objUnit.authors[0].address` — the first entry in the triggering unit's `authors` array — instead of resolving it from the address that actually owns the spent output(s) funding the payment to the AA. This value is then used both as the bounce-refund destination and is propagated as `trigger.initial_address` through the entire chain of secondary AA triggers. In a multi-authored triggering unit, the address that co-signs the unit and happens to occupy `authors[0]` need not be the address whose funds were actually spent to pay the AA, so on a bounce/error the refund (and any oscript logic relying on `trigger.address`/`trigger.initial_address`) can go to the wrong co-signer rather than to whoever actually funded the payment. This mirrors the ZetaChain finding where the refund beneficiary/`origin` was derived from the raw transaction signer instead of the actual caller that funded the deposit.

### Finding Description
`getTrigger()` builds the trigger object like this: [1](#0-0) 

```js
function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	...
	objUnit.messages.forEach(function (message) {
		...
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount;
				}
			});
		}
	});
	...
	return trigger;
}
```

`trigger.address` is unconditionally `objUnit.authors[0].address`. There is no cross-check that the *payer* address (the owner of the source outputs actually spent to fund the payment to the AA) equals `authors[0]`. In `validation.js`, only a much weaker constraint is enforced: the owner of a spent output must be *one of* the unit's authors, not necessarily the first one: [2](#0-1) 

This means a unit can legally be authored by two (or more) distinct addresses — e.g. address `A` and address `B` — where the payment to the AA is actually funded from an output owned by `B`, while `A` is merely a co-signing author (for example, a shared/multisig address, a private-payment counterparty, or a paired-device co-signer) that contributed no funds to the payment. Because `authors[0]` is determined only by whichever address happens to be listed/sorted first, `trigger.address` will report `A`, not `B`, as the trigger address.

`trigger.address` is subsequently:
1. Used directly as the refund destination on bounce: [3](#0-2) 
2. Captured once as `trigger.initial_address` at the start of the primary trigger and propagated unchanged through every secondary AA invocation in the chain: [4](#0-3) [5](#0-4) [6](#0-5) 

`trigger.address` and `trigger.initial_address` are also exposed to oscript authors and are used pervasively as the natural "return funds to the sender" address in AA templates (e.g. bounce logic, refund branches, and even asset-issuance payouts keyed on `trigger.initial_address`): [7](#0-6) [8](#0-7) 

Because AA authors are explicitly told to rely on `trigger.address`/`trigger.initial_address` as "who sent/originated this call," and the protocol computes this value from unit authorship order rather than from actual output ownership, any scenario where a co-signing/authorizing address differs from the funding address creates exactly the sender/beneficiary confusion described in the external report (there, `Sender` was derived from the tx signer instead of `msg.sender`, i.e., the actual caller).

### Impact Explanation
If an AA that a victim funds via a multi-authored unit (or via a chain of AA-to-AA payments seeded by such a unit) bounces — due to a business-logic condition, insufficient balance, a cap being reached, or any other `bounce()` call — the refunded bytes/asset are sent to `trigger.address`, i.e., to `authors[0]`. If the actual funder of the payment is a different co-author (a distinct address that owns the spent output but is not first in the authors list), that co-author loses the refund to the other author. Likewise, any downstream AA logic (in a chain of secondary triggers) that pays out based on `trigger.initial_address` (a documented and tested pattern, see `test/aa_composer.test.js:511-521`) will send funds to the wrong original signer if that signer is not the actual economic beneficiary of the initiating payment. This can result in concrete unauthorized redirection of AA funds/refunds to a co-signer who did not actually own the transferred coins.

### Likelihood Explanation
Exploitation requires a triggering (or chain-originating) unit with more than one author where the funding output is owned by an author other than `authors[0]`. Multi-authored units are a normal, supported ocore feature (shared/multisig addresses, private-payment counterparties, paired devices co-signing a single unit), so this is reachable by any ordinary unit poster who can construct such a unit and get the necessary co-signature — the affected party is whichever legitimate co-author ends up not in `authors[0]` position. The likelihood of accidental exploitation is moderate to high wherever AA templates and dApps rely on `trigger.address`/`trigger.initial_address` for refunds without independently verifying which author actually funded the payment.

### Recommendation
- In `getTrigger()`, derive `trigger.address` (and hence `trigger.initial_address`) from the actual owner of the output(s) that fund the payment to `receiving_address`, not simply from `objUnit.authors[0].address`. If multiple distinct funding addresses are used, either reject ambiguous triggers or expose the full set of funding addresses so AA authors can make an explicit choice.
- If changing the semantics is infeasible for backward compatibility, clearly document (and enforce at validation time) that AAs relying on `trigger.address`/`trigger.initial_address` for refunds must verify the payer address themselves (e.g., cross-check against `trigger.output[[...]]`-funding output ownership) before using it as a payout target.
- Consider requiring, for a payment message app targeting an AA address, that all authors of the triggering unit be limited to (or must include) the address(es) that own the outputs paid to the AA, so `authors[0]` cannot diverge from the actual payer.

### Proof of Concept
1. Address `B` (the actual funder) and address `A` (a co-signer that contributes no funds, e.g. a shared/paired-device address) jointly author a single unit `U`. `U` contains a payment message whose output sends bytes to AA address `X`, with the source input(s) owned by `B` only. Both `A` and `B` sign `U` as required by the definitions of their addresses.
2. `getTrigger(objUnit, X)` computes `trigger.address = objUnit.authors[0].address`. If `A`'s address sorts/lists before `B`'s in `authors`, `trigger.address = A`, even though `A` contributed none of the funds.
3. AA `X`'s bounce logic (`bounce_fees`, business-logic failure, cap check, etc.) triggers `bounce()`, which sends the refund payment to `trigger.address`, i.e., to `A`: [9](#0-8) 
4. `A` receives the refunded bytes that were actually funded and expected to be returned to `B`. In a chain of secondary AA triggers, the same `trigger.initial_address = A` also gets used by downstream AAs (e.g. an asset-issuance payout keyed on `trigger.initial_address`, as exercised in `test/aa_composer.test.js:511-521`), redirecting further payouts to `A` instead of `B`.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';

				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
