### Title
`validateSignedMessageSync` unsafely assumes synchronous completion of an inherently async validator, causing multisig/network-aware signed-message validation to crash or diverge - (File: signed_message.js)

### Summary
`signed_message.js` exposes two entry points for the same validation logic: the async `validateSignedMessage` and a wrapper `validateSignedMessageSync` that is explicitly marked by the codebase authors as "inconsistent for multisig addresses". This is a direct analog of the reported issue: two "middleware" style functions that are supposed to expose the same behavior (validate a signed message/authentifier set) do not have a consistent contract, and callers that rely on the sync wrapper being truly synchronous can silently get wrong results or crash depending on execution path (single vs. multi-author/multisig, network-aware vs. non-network-aware). [1](#0-0) 

### Finding Description
`validateSignedMessage` is fundamentally asynchronous: for network-aware messages (those carrying `last_ball_unit`) it performs a `conn.query` DB read per author and then calls `Definition.validateAuthentifiers`, iterated via `async.eachSeries` over all authors. [2](#0-1) 

For non-network-aware, single-definition-supplied messages, the definition is used directly without a DB round trip, and callbacks may return before any I/O yields control, which is what allows `validateSignedMessageSync` to "work" only in that narrow case. [3](#0-2) 

`validateSignedMessageSync` blindly trusts that the callback fires synchronously and throws an `Error` if it does not: [4](#0-3) 

The author's own comment above the function — "// inconsistent for multisig addresses" — confirms that when `authors.length > 1` (multisig) or when the message is network-aware (last_ball_unit present, forcing a `conn.query`), the callback is not guaranteed to fire before `validateSignedMessageSync` checks `bCalledBack`, producing divergent behavior: it can either throw an unhandled `Error` (since `handleResult` here just sets a flag and doesn't reject anything) or return a stale/undefined `err` depending on the DB driver's synchronicity guarantees (e.g., sqlite driver callback timing differs from mysql). This is exactly the "same generic interface, different actual contracts" defect pattern flagged in the source report about assimilators lacking a unified interface — here, two functions meant to be interchangeable diverge in observable behavior for a subset of valid inputs (multisig authors / network-aware signed packages).

Because `validateSignedMessage`/`validateSignedMessageSync` is the routine that authenticates `signed_message` app payloads and private-payment/attestation-style signed packages (verified via `Definition.validateAuthentifiers`), any node or code path that depends on this sync wrapper's return value to gate acceptance of a signed package is exposed to input-dependent inconsistency.

### Impact Explanation
If callers (e.g. oscript/AA formula evaluators that must run synchronously, or wallet-side sync validation paths referenced from `wallet.js`) rely on `validateSignedMessageSync` to determine whether a signed package/multisig-authenticated message is valid, two different nodes (or the same node under different DB backends/timing) can reach different conclusions for the same signed package: one may throw (causing an exception/crash of the calling code path), another may proceed with a stale `undefined`/incorrect error value, potentially treating an unauthenticated or malformed multisig signed message as valid or vice versa. This falls into the "node disagreement on validity" and "AA fund loss/DoS on caller" impact categories, since AA and oscript evaluation must be fully deterministic and synchronous — any code path with hidden asynchronous behavior masquerading as sync is a correctness/consensus risk.

### Likelihood Explanation
The vulnerable code path is only exercised for multisig addresses or network-aware signed messages (both attacker-triggerable input shapes an unprivileged AA-trigger sender or a private-payment counterparty can construct), and the divergence is acknowledged directly in the source comment, indicating it is a known but unresolved defect rather than a purely theoretical one.

### Recommendation
Remove `validateSignedMessageSync` or make it truly safe: either (a) restrict its use strictly to the single-author, non-network-aware definition path and add an explicit runtime assertion rejecting multisig/network-aware inputs before calling it, or (b) refactor all callers to use the async `validateSignedMessage` with a proper callback so no code assumes synchronous completion of a function whose internal implementation performs `conn.query` and `async.eachSeries` over multiple authors.

### Proof of Concept
1. Construct a `signed_message` payload with two authors (multisig) each supplying valid `authentifiers`, and with `last_ball_unit` set (network-aware).
2. Call `validateSignedMessageSync(objSignedMessage)`.
3. Because `authors.length === 2`, `async.eachSeries` triggers a `conn.query` for the second author only after the first author's `validateOrReadDefinition` callback resolves; depending on the DB driver's scheduling, `bCalledBack` may still be `false` when checked, causing `validateSignedMessageSync` to `throw Error("validateSignedMessage is not sync")` — even though the same payload, submitted with a single author, would resolve successfully through the same code path. // inconsistent for multisig addresses
function validateSignedMessageSync(objSignedMessage){
	var err;
	var bCalledBack = false;
	validateSignedMessage(objSignedMessage, function(_err){
		err = _err;
		bCalledBack = true;
	});
	if (!bCalledBack)
		throw Error("validateSignedMessage is not sync");
	return err;
}
