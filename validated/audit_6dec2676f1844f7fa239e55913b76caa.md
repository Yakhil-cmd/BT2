### Title
Webhook signature verification authenticates the payload's `repository.owner`/`organization` while handlers act on the separate, unchecked `repository.full_name` field, letting one onboarded organization's webhook secret forge events for another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports per-organization GitHub App configuration, each with its own `webhook_secret` [1](#0-0) . The webhook signature check selects which organization's secret to verify against using `repository.owner.login` (falling back to `organization.login`), but the event handlers that consume the same payload act on a different field, `repository.full_name`, without ever checking that it is consistent with the authenticated owner.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify with via `repository_owner`: [2](#0-1) [3](#0-2) 

`repository_owner` is read from `params.dig('repository','owner','login')` (or `organization.login`). This value only proves that the payload was signed with the secret belonging to whichever organization is *named in this one field*. It is never cross-checked against the rest of the payload.

Downstream handlers, however, key their side effects off a *different* field from the very same JSON body - `repository.full_name`: [4](#0-3) 

For example, `PushHandler` resolves the target stacks via `stacks` (i.e. `Repository.from_github_repo_name(repository_name)`, where `repository_name == payload.dig('repository','full_name')`) and forces a resync: [5](#0-4) 

Because `Shipit.github(organization:)` supports one distinct App/secret per organization in a multi-tenant deployment [6](#0-5) , an actor who legitimately administers *one* onboarded organization on a shared Shipit instance (and therefore knows/controls that organization's GitHub App `webhook_secret`) can compute a valid `X-Hub-Signature` for a payload where:
- `repository.owner.login` = their own organization (so `verify_signature` succeeds using their own secret), while
- `repository.full_name` = `"victim-org/victim-repo"` (a repository/stack belonging to a different tenant on the same instance).

The binding broken is: *organization authenticated* (`repository.owner.login`, checked against the HMAC) `≠` *repository the handler writes to* (`repository.full_name`, used unchecked by `Handler#stacks`/`PushHandler#process`).

### Impact Explanation
This crosses the multi-tenant organization/repository trust boundary: an operator that only has legitimate credentials for organization A can force `GithubSyncJob` to run against a stack that belongs to organization B, appending real GitHub commits into B's `Commit` records and toggling `mark_as_accessible!`/`mark_as_inaccessible!` on B's stack [7](#0-6) . The direct, confirmed effect is unauthorized cross-tenant state mutation of another organization's stack data; whether this can be chained into an actual unauthorized deploy depends on whether continuous-deployment auto-triggering is enabled for the targeted stack, which I was not able to verify with the remaining tool budget (no further tool calls were available in this session). Absent that confirmed chain, the concretely provable impact is a cross-tenant integrity violation of stack/commit bookkeeping rather than a directly demonstrated unauthorized deploy.

### Likelihood Explanation
Requires the attacker to legitimately administer at least one organization/GitHub App already onboarded onto the shared Shipit instance (so they hold a valid `webhook_secret` for that org) - this is a real, unprivileged-relative-to-other-tenants position in any multi-org Shipit deployment as documented in `docs/setup.md` and `config/secrets.development.example.yml`. No Shipit session, API token, or GitHub write access to the victim's repository is needed.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, validate that the organization used to select the webhook secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` before dispatching to handlers; reject the payload (HTTP 422) on mismatch.

### Proof of Concept
1. Attacker administers organization `attacker-org`, which is legitimately onboarded to a shared Shipit instance with its own GitHub App and known `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body with `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/victim-repo"`, `ref = "refs/heads/main"`, and an arbitrary `after` SHA.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/github/webhooks`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the HMAC check passes.
5. `PushHandler#process` resolves stacks via `repository.full_name` (`victim-org/victim-repo`) and calls `stack.sync_github(expected_head_sha: params.after)`, forcing `GithubSyncJob` to run against a stack the attacker does not own or authenticate for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
