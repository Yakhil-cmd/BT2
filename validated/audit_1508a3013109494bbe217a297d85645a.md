### Title
Webhook signature verification is scoped per-organization but downstream handlers act on a repository named by an unauthenticated payload field, allowing cross-organization event forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using `repository_owner` (`repository.owner.login`, falling back to `organization.login`), but the events are actually applied to whatever repository is named in `repository.full_name`, which is a separate, independently-attacker-controlled field in the same JSON body. If an organization is configured in `Shipit.github` with no `webhook_secret` (an explicitly supported/optional configuration per `docs/setup.md`), signature verification for that organization is a no-op, letting anyone forge a fully-controlled JSON payload whose `repository.full_name` points at a *different*, secret-protected organization's repository/stack.

### Finding Description
`verify_webhook_signature` in `lib/shipit/github_app.rb` explicitly bypasses HMAC checking when no secret is configured: [1](#0-0) 

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
```

`WebhooksController#verify_signature` picks the `GitHubApp` instance (and thus which secret, if any, is enforced) using only `repository_owner`, which is read straight from the untrusted JSON body: [2](#0-1) 

That authenticates *only* the claim "this request is legitimately from organization X" (or trivially passes if org X has no secret). It performs no check that the *repository being acted upon* belongs to organization X.

Every event handler, however, resolves the target `Stack`/`Repository` from a completely different field of the same attacker-supplied body — `repository.full_name` — via `Handler#stacks`/`#repository_name`: [3](#0-2) 

This is used directly by, e.g., `PushHandler` (triggers `stack.sync_github`, syncing/deploy-eligible commits into a target stack) and `StatusHandler` (writes CI status records used to gate deploys): [4](#0-3) [5](#0-4) 

Nothing ties `repository.owner.login` (the field used for signature-org selection) to `repository.full_name` (the field used for target resolution). `docs/setup.md` documents `webhook_secret` as "(optional)", confirming that a Shipit deployment can legitimately have one configured organization with no secret while other organizations in the same instance (with more sensitive repositories/stacks) do have one configured — a normal, supported multi-org configuration (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml` both show multiple orgs, some with `webhook_secret: # nil`).

**Equality broken**: the binding the system needs to enforce is `organization authenticated (repository_owner) == organization of repository written (repository.full_name)`. Before the attacker's request, only requests bearing a valid HMAC for the specific configured org's secret could reach handlers for that org's repos. After the exploit, an attacker who knows only that *some* configured organization on the instance has no webhook secret can forge the entire payload — including `repository.full_name` for an arbitrary *other* organization's tracked stack — and it will be processed as if it came from GitHub for that other repository.

### Impact Explanation
This is a fully unauthenticated forgery path (no `ApiClient` token, no session, no GitHub credentials needed) that lets an outside attacker:
- Forge `status` events (`StatusHandler`) to fabricate green/passing CI states for arbitrary commits on stacks the attacker does not control, which is used elsewhere in Shipit to gate whether a commit is eligible to deploy — a path toward an **unauthorized deploy**.
- Forge `push` events (`PushHandler`) to force `stack.sync_github` against an unrelated stack, and forge `pull_request`/`membership` events to archive/unarchive review stacks or manipulate team membership records, all cross-organization.

This satisfies the required "High/Critical" bar of "an unauthorized deploy, rollback or merge" via manipulation of gating status data, achieved purely by exploiting a mismatch between the field used for cryptographic authentication and the field used for authorization/target-resolution — directly analogous to the reported reentrancy bug's root cause (state relied upon for a security decision is not the same state actually protected/updated atomically/consistently).

### Likelihood Explanation
Requires only: (1) a Shipit instance configured with more than one GitHub organization (a documented, supported configuration), and (2) at least one of those organizations configured without a `webhook_secret` (explicitly called out as optional in `docs/setup.md`). Given this is a documented, legitimate configuration combination and requires zero credentials from the attacker, likelihood is high in any multi-tenant Shipit deployment where not every org owner bothered to set a webhook secret.

### Recommendation
- Require `webhook_secret` to be mandatory for every configured GitHub organization (fail closed instead of `return true unless webhook_secret`).
- Independently of secret configuration, enforce that `repository.full_name`'s owner segment matches `repository_owner` (the organization whose secret validated the request) before dispatching to handlers, or resolve the target stack strictly within the authenticated organization's known repositories.

### Proof of Concept
Given a Shipit config with:
```yaml
github:
  OrgWithoutSecret:
    app_id: 1
    installation_id: 1
    webhook_secret: # nil
  OrgWithSecret:
    app_id: 2
    installation_id: 2
    webhook_secret: some-strong-secret
```
And a tracked stack for `OrgWithSecret/sensitive-repo`, an unauthenticated attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "<target commit sha of OrgWithSecret/sensitive-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "OrgWithSecret/sensitive-repo"
  }
}
```
`verify_signature` resolves `Shipit.github(organization: "OrgWithoutSecret")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the (missing/incorrect) `X-Hub-Signature`. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb`) then looks up `Commit.where(sha: params.sha)` using the `full_name` referring to `OrgWithSecret/sensitive-repo` and creates a fabricated success status on that commit — despite the attacker never having proven any relationship to `OrgWithSecret`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
