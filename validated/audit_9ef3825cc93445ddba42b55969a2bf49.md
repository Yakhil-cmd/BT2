### Title
Missing minimum-amount / zero-value check on EVM bridge deposits allows decimal-truncation dust to be permanently locked in the vault - (File: `bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/SuiBridgeV2.sol`)

### Summary
The external report's root cause is a missing sufficiency check on a user-supplied value before it is irreversibly consumed by a cross-domain operation, so amounts too small to "cover the cost" of that operation are permanently lost. The Sui native bridge's EVM-side deposit entry points (`bridgeETH`, `bridgeERC20`, `bridgeETHV2`, `bridgeERC20V2`) have the same defect: they accept any `msg.value`/`amount` > 0 wei/token-unit, lock it in the vault, and only afterward compute the Sui-side minted amount via decimal down-scaling. There is no check that the down-scaled (Sui-decimal) amount is non-zero before committing the deposit.

### Finding Description
`bridgeETH`/`bridgeETHV2` transfer `msg.value` to the vault unconditionally and only then compute: [1](#0-0) 
`bridgeERC20`/`bridgeERC20V2` follow the identical pattern — pull the ERC20 into the vault first, then convert: [2](#0-1) 

`BridgeUtils.convertERC20ToSuiDecimal` scales the raw ERC20/ETH amount (typically 18 decimals) down to the Sui-side token decimals (e.g. 8 for wrapped ETH), which is an integer division: [3](#0-2) 

If the deposited amount is smaller than the decimal-scaling divisor (e.g. less than `10^(18-8) = 10^10` wei for ETH), `suiAdjustedAmount` truncates to `0`. The event `TokensDeposited`/`TokensDepositedV2` is still emitted with `amount = 0`, and the real (non-zero) ETH/ERC20 value has already been moved into the vault with no way to reverse it: [4](#0-3) [5](#0-4) 

Neither `bridgeETH`/`bridgeERC20` nor their V2 counterparts perform an `amount > 0` (post-conversion) check, unlike the Move-side outbound path `send_token`, which explicitly guards against zero-value transfers before burning: [6](#0-5) 

This is the direct analog of the external finding: a user-supplied value that is insufficient to "cover" the operation's real cost (here, the decimal-precision floor rather than an L2 submission fee) is accepted without validation, the deposit is irreversibly committed on one side, and the corresponding output on the other side is effectively zero/void.

### Impact Explanation
Any unprivileged depositor who calls `bridgeETH`/`bridgeETHV2`/`bridgeERC20`/`bridgeERC20V2` with an amount below the decimal-truncation threshold permanently loses those funds: the tokens/ETH are custodied by `BridgeVault` and no committee-approvable message with a non-zero amount is ever produced (the zero-amount deposit event carries no recoverable value, and there is no refund/cancel path in the bridge contracts). This is a permanent, unrecoverable loss of user funds triggered purely by public input, matching the "permanent fund lock" / unintended value-destruction class of impact.

### Likelihood Explanation
Likelihood is low-to-moderate and largely accidental/self-inflicted (similar to the original Livepeer finding, which was also rated Medium due to low probability but accepted because the impact is high). It requires a user or a front-end bug to submit a dust-sized deposit; it is not an attacker-vs-victim exploit but a missing-guard defect that silently destroys value with no recourse, which is the same qualitative issue the external report flags (insufficient-value acceptance leading to fund loss).

### Recommendation
Add an explicit check after decimal conversion in all four deposit entry points (`bridgeETH`, `bridgeERC20`, `bridgeETHV2`, `bridgeERC20V2`) that reverts if `suiAdjustedAmount == 0`, mirroring the `ETokenValueIsZero` guard already present in the Move `send_token`/`send_token_v2` functions, e.g.:
```solidity
require(suiAdjustedAmount > 0, "SuiBridge: Amount too small after decimal conversion");
```
This should be enforced before any state-changing transfer to the vault, or the conversion should be performed prior to moving funds so the revert happens before custody transfer.

### Proof of Concept
1. Attacker/user calls `bridgeETHV2(recipient, destinationChainID)` with `msg.value = 1 wei` (or any value `< 10^10` wei, assuming ETH uses 18 decimals on EVM and 8 decimals on Sui).
2. The ETH is forwarded to `vault` unconditionally: [7](#0-6) 
3. `BridgeUtils.convertERC20ToSuiDecimal(18, 8, 1)` truncates to `suiAdjustedAmount = 0`.
4. `TokensDepositedV2` is emitted with `amount = 0`; no meaningful bridge message exists for the committee to sign a non-zero mint, and the deposited wei is stuck in `BridgeVault` forever with no withdrawal path back to the depositor.
