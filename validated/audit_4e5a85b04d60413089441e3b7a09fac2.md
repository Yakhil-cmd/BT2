### Title
`flash_position` and `multiply` mint debt without the `is_borrowable`/paused/frozen check enforced on the `borrow` path - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
The direct `borrow` entrypoint gates every leg through `validate_position_entry_gates` → `require_can_borrow`, which requires the spoke listing to be active, unpaused, unfrozen, and `is_borrowable == true` (`contracts/controller/src/positions/mod.rs:201-213`, `243-252`). The strategy entrypoints `flash_position` and `multiply` mint debt on the same debt asset via `borrow_into_controller` but only validate the *collateral* side (`require_can_supply`) and, for `flash_position`, the pool's `is_flashloanable` flag — they never call `require_can_borrow` on the debt asset. This is the same bug class as the Morpho sentinel report: a borrow-disable signal enforced on one path is silently bypassed on another path that still creates debt.

### Finding Description
- `process_borrow` enforces the borrow gate: `validate_position_entry_gates(..., AccountPositionType::Borrow)` calls `require_can_borrow`, which loads `require_listed_unhalted_config` (hub active, listing active, `!paused`, `!frozen` via `FreezePolicy::BlockOnEntry`) and asserts `asset_config.is_borrowable` (`contracts/controller/src/positions/debt.rs:50-57`, `contracts/controller/src/positions/mod.rs:188-213`).
- `process_flash_position` checks `require_hub_active(debt.hub_id)` and `is_flashloanable`, then calls `mint_and_forward` → `borrow_into_controller` on `debt` (`contracts/controller/src/strategies/flash_position.rs:60-91`, `260-295`). The only per-asset permission checks are `require_can_supply` on `collaterals` (line 202). No `require_can_borrow` on `debt`.
- `process_multiply` calls `require_can_supply(collateral)` (line 60) then `borrow_into_controller(debt)` (line 76) with no `is_borrowable`/paused/frozen check on `debt` (`contracts/controller/src/strategies/multiply.rs:60-84`).

The pool contract does not independently enforce `is_borrowable` — that flag lives in controller spoke config (`contracts/pool/src` only surfaces it in views/cache), so a disabled or paused asset can still be borrowed through these paths. Caveat: `borrow_into_controller` in `contracts/controller/src/strategies/mod.rs` was not fully read; if it internally repeats `require_can_borrow`, this finding is void — but the flag checks visible at both call sites cover only supply-side and flash-loan permissions.

### Impact Explanation
An unprivileged user can open or extend debt in an asset that governance has deliberately marked non-borrowable, paused, or frozen — precisely the emergency/risk-off switch the `borrow` gate exists to enforce. Pause/freeze flags are designed to halt exposure growth during market stress; bypassing them via `flash_position`/`multiply` lets debt grow against a market the protocol intended to freeze, which can drive protocol insolvency if the disable was triggered by a broken oracle, depeg, or liquidity event.

### Likelihood Explanation
Requires governance to set `is_borrowable = false` or `paused`/`frozen` on a spoke asset while `is_flashloanable` remains set (independent flags) and collateral markets remain listed. Any user can then call `Controller::flash_position`/`multiply`. Medium likelihood, consistent with the original Medium rating.

### Recommendation
In `process_flash_position` and `process_multiply` (or centrally inside `borrow_into_controller` in `contracts/controller/src/strategies/mod.rs`), call `require_can_borrow(env, cache, account.spoke_id, debt)` — or equivalently run `validate_position_entry_gates` with `AccountPositionType::Borrow` for the debt leg — before minting debt, so spoke-asset pause/freeze and `is_borrowable` apply uniformly to every debt-creating path.

### Proof of Concept
1. Governance lists asset D on spoke S with `is_borrowable = false` (or `paused = true`) while `is_flashloanable = true` in the pool params, and lists collateral C with `is_collateralizable = true`.
2. Attacker deploys a receiver contract implementing `execute_flash_position` that, on callback, transfers C to the controller.
3. Attacker calls `Controller::flash_position(account_id=0, spoke_id=S, mode=Multiply, debt=D, amount=X, receiver=attacker_contract, collaterals=[(C, min)], refund_assets=[])`.
4. The call passes all checks (`is_flashloanable`, `require_can_supply` on C) and `mint_and_forward` borrows X of D into the controller and forwards it — debt in D is created despite `is_borrowable = false`. `try_borrow` with the same leg would have reverted with `AssetNotBorrowable`.
5. The same bypass holds via `Controller::multiply(debt=D, collateral=C, ...)`.
