Based on my analysis, this is a confirmed vulnerability.

### Title
`ReviewStack#env` allows a PR label to override `PATH` in commands executed via `PTY.spawn`, enabling RCE - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::ReviewStack#env` merges attacker-controlled GitHub PR label names, upcased, directly into the stack's environment hash with no key whitelist or blacklist. Because this hash flows unmodified through `StackCommands#env` / `TaskCommands#env` into `Command.new(..., env:)`, and `Command#unbundled_env` merges `@env.stringify_keys` **last** (after `Shipit.shell_paths`), an attacker who names a PR label `PATH` (or `path`, `Path`, etc.) can force every command in that stack's tasks to execute with `PATH=true`.

### Finding Description
The broken binding: the intended equality is `Command#unbundled_env['PATH'] == "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, but for any review stack whose PR carries a label matching `/path/i` after upcasing, the actual value is `Command#unbundled_env['PATH'] == pull_request.labels.find { |l| l.name.upcase == 'PATH' }` i.e. `'true'`.

Code path:
- `ReviewStack#env` builds `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` and merges it on top of `super` with no key filtering: [1](#0-0) 
- This unrestricted hash becomes `@stack.env`, merged into `StackCommands#env`: [2](#0-1) 
- and into `TaskCommands#env`, which is used to build every `Command.new` for deploy/rollback/task steps: [3](#0-2) 
- `Command#initialize` stores `@env` as-is (only stringifying values): [4](#0-3) 
- `Command#unbundled_env` merges `BASE_ENV`, then the intended `PATH` (`Shipit.shell_paths` + `ENV['PATH']`), then `@env.stringify_keys` **last**, so the attacker's `PATH` value wins: [5](#0-4) 
- `start` passes this exact hash to `PTY.spawn`: [6](#0-5) 

No guard prevents this. `Shipit::EnvironmentVariables#permit` exists as a whitelist mechanism, but it is only used for interpolating `$VAR` references (`interpolate_environment_variables`) and for `deploy_spec` environment variable declarations — not applied to `ReviewStack#env` or to the hash passed into `Command.new`: [7](#0-6) [8](#0-7) . Labels are attacker-controlled: any GitHub user with permission to open/label their own PR against a repository with review stacks enabled (`allow_all`, or reachable via the `allow_with_label`/`prevent_with_label` precedence logic in `LabeledHandler`/`UnlabeledHandler`) can set this via the `labeled`/`unlabeled` webhook, processed unauthenticated-content-wise by `ReviewStackAdapter` with no label name restriction: [9](#0-8) .

### Impact Explanation
Every command run against the review stack (fetch, checkout, install_dependencies, deploy/rollback steps) resolves relative binaries against `PATH=true` instead of `Shipit.shell_paths`, i.e. the attacker fully controls the deploy host's binary resolution for that stack's spawned processes. Depending on host configuration and what other relative-path binaries the deploy pipeline calls (e.g. `git`, `bundle`, custom scripts), this can be escalated to arbitrary code execution on the deploy host — Critical RCE via `Command`/`PTY.spawn`. The blast radius is scoped to the attacking repository's review stack's task processes, but since deploy hosts are frequently shared across stacks/repositories, and since `Shipit.shell_paths` is meant to be a security-relevant PATH restriction, defeating it is a meaningful host compromise vector.

### Likelihood Explanation
Preconditions are minimal: review stacks must be enabled for the target repository (`review_stacks_enabled`) with any provisioning behavior (`allow_all` trivially; `allow_with_label`/`prevent_with_label` reachable per the documented precedence). The attacker needs only the ability to open a PR and add a label named `PATH`/`path` to it — no Shipit credentials, no maintainer role, no secrets. This is a single webhook-driven, zero-cost, fully repeatable action against any repository with review stacks enabled that the attacker can PR against.

### Recommendation
Do not allow PR labels to populate arbitrary environment variable keys, especially reserved/security-sensitive ones. Filter `ReviewStack#env`'s label-derived keys through a whitelist (e.g. `EnvironmentVariables#permit` with an explicit allowed list), or at minimum reject/strip keys colliding with `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `BUNDLE_*`, `RUBYOPT`, and other security-relevant variables before merging. Additionally, `Command#unbundled_env` should compute `PATH` after merging `@env`, or explicitly re-assert `Shipit.shell_paths`-derived `PATH` as the final, non-overridable value.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_path_override_test.rb (conceptual, no live GitHub needed)
test "a PR label named PATH overrides the shell PATH used by spawned commands" do
  stack = shipit_review_stacks(:some_review_stack)
  stack.pull_request.labels = [Shipit::PullRequest::Label.new(name: "PATH")]

  env = stack.env
  assert_equal "true", env["PATH"]

  command = Shipit::Command.new(['ls'], env: { 'PATH' => env['PATH'] }, chdir: Dir.tmpdir)
  assert_equal "true", command.unbundled_env['PATH']
  refute_equal Shipit.shell_paths.join(':'), command.unbundled_env['PATH'].split(':').first
end
```
This demonstrates that `Command#unbundled_env['PATH']` diverges from the intended `Shipit.shell_paths`-derived value solely because of an attacker-supplied PR label, with the divergence surfacing exactly at the `PTY.spawn` boundary.
