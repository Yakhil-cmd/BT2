### Title
Path confinement bypass via pre-existing symlink at agent skill install directory - ([File: internal/skills/installer/installer.go])

### Summary
`registry.AgentHost.InstallDir` computes the skill install directory as `filepath.Join(gitRoot, h.ProjectDir)` (e.g. `<gitRoot>/.agents/skills`) with no filesystem check, and `installer.installSkill` / `installLocalSkill` then call `os.MkdirAll(skillDir, ...)` and `os.WriteFile(destPath, ...)` on that path without ever `Lstat`-ing it to reject a symlink. If the directory already exists on disk as a symlink to a location outside the repository, both `MkdirAll` and `WriteFile` transparently follow it, so skill files are written wherever the symlink points instead of being confined to the project.

### Finding Description
`AgentHost.InstallDir` (internal/skills/registry/registry.go:410-430) does nothing more than string-join `gitRoot` and `h.ProjectDir` — no `os.Lstat` or symlink check is performed: [1](#0-0) 

`installSkill` then does: [2](#0-1) 
followed by fetching each blob and writing it with `os.WriteFile(destPath, ...)`: [3](#0-2) 

The `safepaths.ParseAbsolute`/`.Join` calls used inside the loop only guard against `../` traversal in the *relative* file paths returned by the GitHub tree API — they do not resolve or reject symlinks in the base `skillDir` itself: [4](#0-3) 

`installLocalSkill` has the identical pattern (`os.MkdirAll(skillDir, 0o755)` then `os.WriteFile(destPath, ...)`), with the same absence of an `Lstat` check on `skillDir`: [5](#0-4) 

`checkOverwrite` in the install command also only uses `os.Stat` (which follows symlinks), never `os.Lstat`, so it provides no symlink detection either: [6](#0-5) 

Go's `os.MkdirAll` calls `Stat` on the target path; if `Stat` (which follows symlinks) reports that the path is already a directory, `MkdirAll` returns `nil` immediately without any indication that the path is actually a symlink. Subsequent `os.WriteFile` calls on paths under that directory then perform ordinary `open()`/`write()` syscalls, which the OS transparently resolves through the symlink.

**Attacker input path**: git stores symlinks as tree entries (mode `120000`), and a normal `git checkout`/`git clone` (with the default `core.symlinks=true` on Linux/macOS) faithfully recreates them on disk. An attacker who controls a repository, fork, or PR branch that a victim checks out locally can include, via an innocuous-looking commit, a symlink at `.agents/skills` (or any other agent's `ProjectDir`, e.g. `.claude/skills`) pointing to an arbitrary location outside the repo (absolute path or `../../..` relative escape). If the victim later runs `gh skill install <skill> --scope project` from within that checkout, `InstallDir` resolves to the symlinked path, and neither `installSkill` nor `installLocalSkill` detects or rejects the symlink before writing.

### Impact Explanation
This is a file-write-outside-intended-directory primitive: skill files (including a `SKILL.md` and any other files from the source skill package) end up written to whatever location the pre-planted symlink targets, rather than being confined to the project's `.agents/skills` (or equivalent) directory. If the attacker also controls (or the victim installs from) the skill source content, the attacker additionally controls the filenames and bytes written, enabling writes to sensitive locations reachable by the symlink target (e.g. shell startup files, git hooks, or other files the victim's user account can write). This maps to GitHub's "file write outside intended path" impact class.

### Likelihood Explanation
Exploitation requires the victim to have already checked out attacker-controlled repository content (a fork, PR branch, or similar) as their local working tree — a common workflow for reviewing/testing contributions — and to then run `gh skill install` with project scope while inside that checkout. No admin rights, tokens, or MITM are needed; only ordinary git checkout + `gh skill install` usage. The symlink-follow behavior in `os.MkdirAll`/`os.WriteFile` is deterministic and repeatable, so the bug reliably triggers whenever the precondition (pre-existing symlink at the target install path) is met.

### Recommendation
Before creating or writing into the resolved `skillDir` (and the per-agent `ProjectDir`/`UserDir` target in `InstallDir`), perform an `os.Lstat` on the path (and each intermediate path component) and reject installation with an explicit error if any component is a symlink, rather than relying on `os.MkdirAll`/`os.WriteFile`'s default symlink-following behavior. Apply the same check in `checkOverwrite` and in `installLocalSkill`.

### Proof of Concept
```go
func TestInstallSkill_RejectsSymlinkedInstallDir(t *testing.T) {
    repoDir := t.TempDir()
    outsideDir := t.TempDir() // sentinel location outside the repo

    // Simulate a git checkout that already contains a symlink at
    // <repoDir>/.agents/skills -> outsideDir (as git would recreate
    // from a tree entry with mode 120000).
    skillDirLink := filepath.Join(repoDir, ".agents", "skills")
    require.NoError(t, os.MkdirAll(filepath.Dir(skillDirLink), 0o755))
    require.NoError(t, os.Symlink(outsideDir, skillDirLink))

    host, _ := registry.FindByID("github-copilot")
    target, err := host.InstallDir(registry.ScopeProject, repoDir, "")
    require.NoError(t, err)
    require.Equal(t, skillDirLink, target)

    opts := &installer.Options{ /* stubbed client, Owner/Repo/Skills etc. */ }
    _, err = installer.Install(opts)

    // Expected (fixed) behavior: an explicit error rejecting the symlinked
    // install directory, and no files land in outsideDir.
    require.Error(t, err)
    entries, _ := os.ReadDir(outsideDir)
    require.Empty(t, entries, "skill files were written outside the repo via symlink")
}
```
Current behavior: `Install` succeeds and skill files (e.g. `outsideDir/code-review/SKILL.md`) are written into `outsideDir`, confirming the path confinement bypass.
