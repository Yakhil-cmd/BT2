### Title
Arbiter contract hash uses an unescaped delimiter, allowing hash collisions between different contract terms - ([File: arbiter_contract.js])

### Summary
`getHashSrc()` in `arbiter_contract.js` builds the source string used to compute an arbiter contract's identifying `hash` by joining free‑text fields (`title`, `text`) and other contract fields with a fixed, hard‑coded delimiter `exports.DELIMITER = "[|#|]"` [1](#0-0) . Neither `title` nor `text` (both attacker/user‑controlled) are checked for containing this delimiter sequence before being joined [2](#0-1) . This is the same bug class as the reported plexus-utils issue: a structural delimiter is written into a "flat" serialization without escaping/rejecting the delimiter inside untrusted field content, so attacker‑controlled field boundaries can be forged, producing the same serialized string (and thus the same hash) for objects that actually carry different terms.

### Finding Description
`getHashSrc(contract)` concatenates `title`, `text`, `creation_date`, addresses, party names, `amount`, and `asset` using `exports.DELIMITER` [3](#0-2) . `getHash()` then SHA‑256/base64-hashes this string and the result becomes the contract's canonical identity (`contract.hash`), computed and set unilaterally by the contract-creating peer in `createAndSend()` [4](#0-3) . Because `title`/`text` are attacker-controlled strings that are never checked for embedding the literal delimiter `"[|#|]"`, a malicious offeror can craft `title`/`text` values that contain delimiter-like substrings so that the joined string — and hence the resulting hash — becomes identical to the hash that would be produced from a different set of underlying field values (e.g., different `amount`, `asset`, or `payee_address`), by shifting where fields appear to conspire to the same overall byte string. This mirrors the referenced flaw: an unescaped/unvalidated separator character sequence lets attacker-controlled content be mistaken for structural boundaries, causing serialization ambiguity.

This hash is not just cosmetic — it is embedded directly into oscript payment conditions used to construct the arbiter shared address:
```
["in data feed", [[contract.arbiter_address], "CONTRACT_" + contract.hash, "=", offeror_address]]
``` [5](#0-4) 
and it is used again to match the arbiter's resolution message against the correct contract when parsing dispute winners:
```
var key = "CONTRACT_" + contract.hash;
...
winner = message.payload[key];
``` [6](#0-5) 

Because the "CONTRACT_" + hash string is the sole discriminator tying an arbiter's data-feed resolution to a specific shared address's release condition, a colliding hash between two different arbiter contracts serviced by the same arbiter address means a resolution meant for contract A's shared address can also satisfy contract B's release condition if B's hash happens to collide with A's due to unescaped delimiter injection in B's `title`/`text`.

### Impact Explanation
If an attacker (as an arbiter-contract offeror) can engineer `title`/`text` so that `getHashSrc()` produces the same output as another party's legitimately different contract (different `amount`, `asset`, or counterpart addresses), the resulting identical `contract.hash` causes the `"in data feed", [[arbiter_address], "CONTRACT_"+hash, "=", address]` condition embedded in the shared address definition to be satisfiable by an arbiter resolution intended for the other, unrelated contract. This can let funds locked in one arbiter-mediated shared address be released to the wrong party, i.e., unauthorized spending/fund diversion from a private-payment counterparty's escrow — reachable purely from a maliciously-crafted contract offer sent between two ordinary wallet users (no privileged/hub/network role needed).

### Likelihood Explanation
Exploitation requires an attacker to control the `title`/`text` fields of a contract they offer (fully attacker-controlled input), and to find field values whose concatenation collides with another target contract's fields under the same arbiter. This is a non-cryptographic (structural) collision, not a preimage attack against SHA-256 itself, so it only requires crafting delimiter-conflicting strings — significantly easier than breaking the hash function — making it feasible for a determined counterparty, though it still requires knowledge of/target alignment with an existing or simultaneously-created contract under the same arbiter.

### Recommendation
Reject (or escape) any occurrence of `exports.DELIMITER` inside `title`, `text`, or any other joined field before computing `getHashSrc()`, or switch to a collision‑safe encoding such as `string_utils.getSourceString()`/`getJsonSourceString()` (already used elsewhere in the codebase, e.g. `object_hash.js`) which length‑/type‑prefixes each field and rejects embedded join characters [7](#0-6) , guaranteeing unambiguous serialization instead of naive delimiter-joining.

### Proof of Concept
1. Party A creates contract with `title = "T"`, `text = "X[|#|]legit_creation_date[|#|]legit_payer[|#|]..."` such that the concatenated `getHashSrc` output for a forged set of downstream fields (e.g., a smaller `amount` or different `asset`) exactly matches the byte string produced for a genuine, different contract B's `getHashSrc` output (achievable because `title`/`text` are unrestricted free text and the delimiter is a fixed, discoverable constant `"[|#|]"`).
2. Both contracts end up with identical `contract.hash`, hence identical `"CONTRACT_" + hash"` data-feed keys used in their respective shared-address release conditions [5](#0-4) .
3. When the (possibly shared) arbiter posts a resolution `data_feed` unit with `payload["CONTRACT_"+hash] = winner_address` for contract A, `parseWinnerFromUnit` for contract B also matches this key and treats the same address as its winner [8](#0-7) , satisfying B's `"in data feed"` spending condition and permitting withdrawal from B's shared address using a resolution never issued for B.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
```
