### Title
Private payment chains are forwarded to *all* signing-path holders of a shared address regardless of which branch actually authorized the spend, leaking private transaction data to unrelated cosigners - (File: wallet_defined_by_addresses.js)

### Summary
When a private (blackbytes-style) payment involving a shared/multisig address is validated, `ocore` forwards the full private-element chain — which reveals output amounts, addresses and blinding factors, and by extension the whole prior spend history of the coin — to every device address that has *any* signing path registered on that shared address. The code does not check whether the specific signing path/device actually participated in signing the unit that spent the funds, so devices belonging to unrelated OR-branches of the address definition also receive and can decrypt private payment details they were never meant to see.

### Finding Description
`handlePrivatePaymentChains` in [1](#0-0)  looks up the unit's actual authors and calls `forwardPrivateChainsToOtherMembersOfSharedAddresses(arrChains, arrAuthorAddresses, from_address, true)`.

That function, in [2](#0-1) , resolves the full set of "control addresses/devices" for the paying addresses via `walletDefinedByAddresses.readAllControlAddresses` and then forwards the private chains to **all** of them with `walletGeneral.forwardPrivateChainsToDevices`.

`readAllControlAddresses` in [3](#0-2)  recursively selects every `device_address` from `shared_address_signing_paths` where `shared_address IN (?)`, with no filter on which particular `signing_path` was used to actually authorize the specific unit. Likewise `forwardPrivateChainsToOtherMembersOfAddresses` at [4](#0-3)  selects `device_address FROM shared_address_signing_paths JOIN correspondent_devices ... WHERE shared_address IN(?)` — again every registered cosigner of the shared address, independent of which branch of the address `Definition` was exercised.

An `ocore` shared address can have a `Definition` such as `["or", [["address", A], ["address", B]]]`, where A and B represent completely independent parties who are each individually able to spend the funds, but neither should be able to observe the other's activity. Because both A's and B's devices are registered in `shared_address_signing_paths` for the same `shared_address`, whenever A authors a private-asset payment from the shared address, the forwarding logic above sends the full private-element chain (amounts, blinding, addresses, and via the chain-walking in `buildPrivateElementsChain`, the whole upstream spend history, see [5](#0-4) ) to B's devices too, even though B never signed, never needs to co-sign, and per the OR semantics should have no visibility into A's use of the shared address.

The forwarded payload is delivered verbatim via `sendPrivatePayments`/`forwardPrivateChainsToDevices` in [6](#0-5) , which places the entire `arrChains` (including hidden/private outputs, blinding factors and addresses) into the `private_payments` device message with no filtering by recipient's relevance to the transaction.

### Impact Explanation
This breaks the confidentiality guarantee of `ocore` private assets: an unprivileged member of a shared address (one whose signing path was never actually used to authorize a given spend) can be handed the full private-element chain, learning transaction amounts, involved addresses, and the historical chain of previous private transfers of that coin. This is directly analogous to the MeterSphere CVE-2024-32467 pattern — a party with no legitimate relationship to a specific resource ("workspace"/spend) is nonetheless granted visibility into sensitive information belonging to it — mapped onto `ocore`'s private-payment-chain distribution model. Depending on the shared address's definition, this can leak counterparty identities and transaction amounts to business rivals or unrelated custodians who happen to share a single multi-branch address definition.

### Likelihood Explanation
Any user can construct a shared address definition (e.g. `["or", [...]]`, `["r of set", ...]`) that groups multiple unrelated parties into the same `shared_address_signing_paths` set, and each of these parties is registered as a legitimate correspondent device once the shared address is set up (a normal, expected `ocore` wallet flow). No malicious server, hub, or protocol violation is required — this triggers purely from posting a normal private-asset payment through a shared address with such a definition, making it straightforward to hit in practice for any wallet software built on this `ocore` version.

### Recommendation
When forwarding private payment chains for a shared address, only forward to devices whose signing path was part of the actual authorization branch used for the specific unit (i.e., derive `arrControlAddresses`/`arrControlDeviceAddresses` from the specific spent sub-definition/signing paths recorded for that unit, rather than from every `shared_address_signing_paths` row for the whole address). This requires tracking, at signing time, which branch of an OR/threshold definition was exercised and limiting private-chain forwarding to devices along that branch only.

### Proof of Concept
1. Create a shared address with definition `["or", [["address", A], ["address", B]]]`, where A and B are unrelated wallets/devices, and both register their `shared_address_signing_paths` for this shared address via the normal wallet setup flow (`handleNewSharedAddress` in `wallet_defined_by_addresses.js`).
2. Fund the shared address with a private asset and have device A alone author and broadcast a private payment spending from the shared address.
3. Observe that `handlePrivatePaymentChains` → `forwardPrivateChainsToOtherMembersOfSharedAddresses` → `readAllControlAddresses` resolves B's device address as a "control device address" of the shared address (since B has a `shared_address_signing_paths` row for it) and `forwardPrivateChainsToDevices` sends the full private-element chain (amounts, blinding, addresses) to B, even though B never signed and has no relation to this specific spend.

function readAllControlAddresses(conn, arrAddresses, handleLists){
	conn = conn || db;
	conn.query(
		"SELECT DISTINCT address, shared_address_signing_paths.device_address, (correspondent_devices.device_address IS NOT NULL) AS have_correspondent \n\
		FROM shared_address_signing_paths LEFT JOIN correspondent_devices USING(device_address) WHERE shared_address IN(?)", 
		[arrAddresses], 
		function(rows){
			if (rows.length === 0)
				return handleLists([], []);
			var arrControlAddresses = rows.map(function(row){ return row.address; });
			var arrControlDeviceAddresses = rows.filter(function(row){ return row.have_correspondent; }).map(function(row){ return row.device_address; });
			readAllControlAddresses(conn, arrControlAddresses, function(arrControlAddresses2, arrControlDeviceAddresses2){
				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
