### Title
Webhook signature verification is bound to `repository.owner.login`, but downstream handlers act on independently-supplied `full_name`/`organization.login` fields, breaking the "authenticated org" = "written repo/team" invariant - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the inbound signature against using only `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`), while the handlers that actually mutate state (`Handler#repository_name`, `MembershipHandler#find_or_create_team!`) read `repository.full_name` / `organization.login` independently from the same untrusted JSON body. Nothing ties the value used to pick the verifying secret to the value used to decide what gets written, so once signature verification is satisfied for any reason (most importantly: `GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that resolved organization, a state explicitly documented as "optional"), the request body is otherwise fully attacker-controlled and can target any repository/stack/team in the Shipit instance, not just the one the "verified" organization owns.

### Finding Description
`verify_signature` computes the organization/app used purely for validation purposes: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` trivially passes when the resolved app has no `webhook_secret` configured — a state the setup docs explicitly call "optional": [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (either because no secret is set, or because the same shared `webhook_secret` is used across multiple orgs), the raw JSON body is handed unmodified to every registered handler: [5](#0-4) 

Each handler independently re-derives the target repository/team from the same attacker-controlled body, with zero cross-check against the `repository_owner` value that was used for authentication: [6](#0-5) [7](#0-6) 

Most notably, `MembershipHandler#process` unconditionally adds or removes any attacker-chosen GitHub login from any attacker-chosen team, using `organization.login`/`team` fields taken straight from the payload and never checked against the value that authorized the request: [8](#0-7) [9](#0-8) 

This is structurally the same class of bug as the reported finding: the value that is checked/verified (`repository.owner.login`, used to select the signing secret) is not the same value that is ultimately acted upon (`repository.full_name` for push/status/check_suite handlers, `organization.login`/`team`/`member.login` for membership handler). The equality that should hold — "organization that authenticated" == "repository/team that is written" — is never enforced anywhere in the pipeline.

### Impact Explanation
Team membership is the authorization boundary for the whole application: `User#authorized?` and `force_github_authentication` gate every UI action on membership in `Shipit.github_teams`: [10](#0-9) [11](#0-10) 

Because `MembershipHandler` performs `team.add_member(member)` for an arbitrary `member.login` supplied in the webhook body with no binding back to the organization that was cryptographically verified (or, in the common documented case of no configured `webhook_secret`, with no cryptographic verification at all), an attacker able to reach `/webhooks` can add an arbitrary GitHub login to a `Shipit.github_teams` team. If that GitHub login is later used to complete OAuth login, the attacker escalates into full authorization on the Shipit instance — matching the High-severity "escalation into `Shipit.github_teams` authorization" impact bucket. The same binding gap also lets `push`/`status`/`check_suite` events reference a `repository.full_name` unrelated to the organization that satisfied `verify_signature`, letting an attacker trigger `stack.sync_github` / status writes / check-run refreshes against any stack in the instance rather than only the one belonging to the authenticated organization.

### Likelihood Explanation
The most direct trigger — no `webhook_secret` configured — is a first-class, documented, supported configuration ("Webhook secret (optional)"), so this does not require possessing any secret, a Shipit session, an `ApiClient` token, or the GitHub App private key; `/webhooks` is mounted with `skip_before_action :verify_authenticity_token` and no `authenticate_api_client`, so it is reachable by any unauthenticated network client. Even when a `webhook_secret` is configured, the structural gap (verification keyed on `owner.login`, action keyed on independent `full_name`/`organization.login` fields) remains latent and would be exploitable by anyone who can produce a validly-signed body for any one organization in a multi-org Shipit deployment (`config/secrets.yml` "Using Multiple Github Applications" is also a documented supported mode) — at that point they can still target teams/repos belonging to other organizations because the check and the action never compare notes.

### Recommendation
After signature verification, re-derive the acting organization/repository from the same `repository_owner` value that was used to select the verifying `webhook_secret`, and reject (or scope) any handler action whose payload-declared `repository.full_name`/`organization.login`/`team.organization` does not match that verified value. Concretely: pass the verified `repository_owner` (or resolved `GitHubApp`) into `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` and have `Handler#repository_name` / `MembershipHandler#find_or_create_team!` assert equality against it before mutating any `Team` or `Stack`/`Repository` state.

### Proof of Concept
1. Deploy Shipit without a `github.webhook_secret` (a supported, documented configuration) or in a multi-org configuration where the attacker can obtain a validly signed body for their own organization "AttackerOrg".
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Shopify Developers", "slug": "developers", "url": "https://example.com" },
  "organization": { "login": "shopify" },
  "member": { "login": "attacker-github-login" }
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"shopify"` (via the `organization.login` fallback) and, because `webhook_secret` is unset for that org config, `verify_webhook_signature` returns `true` unconditionally — no signature match is actually required.
4. `Shipit::Webhooks::Handlers::MembershipHandler#process` runs, finds/creates the `shopify/developers` `Team`, and calls `team.add_member(User.find_or_create_by_login!("attacker-github-login"))`.
5. If `Shipit.github_teams` includes `shopify/developers`, the attacker's GitHub login is now a member of an authorizing team; logging in via GitHub OAuth with that login satisfies `User#authorized?` and grants full Shipit access, per `app/controllers/concerns/shipit/authentication.rb:20-34` and `app/models/shipit/user.rb:80-82`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
