### Title
Donation attack against `balance[asset]`/`var['..._outstanding']` share accounting lets an attacker steal a victim's deposit in the bundled Uniswap-like market-maker AA - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `oscript`/AA (Autonomous Agent) sample bundled with ocore, `uniswap_like_market_maker.oscript`, implements an LP-share issuance scheme that is structurally identical to the vulnerable `TermMaxMarket.provideLiquidity` pattern described in the report: it derives the amount of new LP ("mm") shares to mint from the AA's *live* on-chain balances (`balance[$asset]`, `balance[base]`) combined with the tracked outstanding-share counter (`var['mm_asset_outstanding']`), instead of from an internal, attacker-resistant accounting of prior deposits. Because `balance[...]` in oscript reflects real, freely-transferable funds sitting at the AA address, any unprivileged party can donate assets/bytes directly to the AA address to manipulate these balances before a victim's investment trigger is processed, exactly as an attacker manipulates `balanceOf`/`totalSupply` in the Solidity report.

### Finding Description
In the "invest in MM" case of the AA: [1](#0-0) 

the code computes:
- `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` and `$bytes_balance = balance[base] - trigger.output[[asset=base]]` — the AA's pre-trigger reserves, taken straight from its live wallet balance;
- `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance`;
- `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`.

This is the oscript analog of TermMax's `calculateLpOut`, which uses `token.balanceOf(market)` and `lpToken.totalSupply()` to price new LP shares. Both designs share the same root cause: the reserve values used to price a deposit (`balance[...]`) can be inflated by an unprivileged third party simply sending funds to the contract/AA address, independent of the tracked share supply (`totalSupply()` in Solidity, `var['mm_asset_outstanding']` in oscript).

An attacker can reproduce the TermMax attack against this AA:
1. Attacker sends the very first "invest" trigger with amount X. Since `$asset_balance == 0 OR $bytes_balance == 0` (the AA is empty), the code takes the special-case branch `$issue_amount = balance[base]` for the initial deposit, minting the attacker `X` mm shares while `var['mm_asset_outstanding']` becomes `X`.
2. Attacker "divests" almost all of her shares (all but 1), driving `var['mm_asset_outstanding']` down to `1`, while the AA's `balance[base]`/`balance[$asset]` are consequently reduced to whatever the ratio computation leaves behind. Divesting is done via the branch: [2](#0-1) 
3. Attacker observes a victim's pending "invest" trigger for amount Y in the mempool/network and front-runs it by sending a plain payment (donation) of bytes/asset directly to the AA address — increasing `balance[base]` and/or `balance[$asset]` without going through the "invest" case (e.g., by sending only the asset without exceeding the `1e5` byte threshold, or by using a payment shape that the AA either bounces or silently accepts into its balance, since incoming outputs to an AA address always add to `balance[...]` regardless of whether the AA's response logic executes).
4. When the victim's trigger for Y is processed, `$bytes_balance` (or `$asset_balance`) is now inflated relative to `var['mm_asset_outstanding'] = 1`, so `$investor_share_of_prev_balance = Y / $bytes_balance` becomes tiny and `round(...)` rounds `$issue_amount` down to `0`. The victim's deposit is absorbed into the AA's balance without any `mm_asset` shares being minted to them.
5. The attacker, still holding the sole outstanding share, can later divest and claim essentially the entirety of `balance[base]`/`balance[$asset]`, including the victim's donated funds, via the "divest MM shares" branch, which pays out `round($investor_share * balance[...])` — and with `$investor_share = 1` (single remaining unit of `mm_asset_outstanding`), the attacker collects the full reserve.

This is a direct reachable analog: any address that can post a payment to the AA (an "unprivileged AA trigger sender") can execute steps 1–3, and any other address whose deposit races the front-run (an ordinary AA trigger sender) is the victim in step 4-5 — matching the allowed unprivileged-actor threat model (AA trigger sender).

### Impact Explanation
Successful exploitation results in outright theft of a victim's deposited funds by an unprivileged attacker who merely posts ordinary payments/triggers to the AA — a concrete unauthorized-spending / AA-fund-loss outcome. Because AAs of this general LP/market-maker shape are a documented, expected usage pattern for ocore's Autonomous Agents (this exact oscript ships as a reference sample in the repository's test suite, meant to illustrate a supported design pattern for real-world AA authors), any AA built from this template inherits the vulnerability, and losses scale with the size of the victim's deposit. This matches "High" impact in the class of the referenced report.

### Likelihood Explanation
The attack requires the attacker to be first depositor (or manufacture a near-empty-reserve state via divestment) and to front-run a victim's trigger with a donation payment before it lands on the DAG — both of which are realistic given oscript AAs process triggers unit-by-unit and unit composition/broadcast timing is visible to network participants monitoring pending activity, similar to mempool front-running in the original report. As in the source report, the attacker additionally needs a way to eventually realize her profit (a further deposit or reaching a state where withdrawal is unblocked), which is a normal part of AA operation. This corresponds to a "Medium" likelihood, mirroring the original assessment.

### Recommendation
Do not derive share-issuance ratios from an AA's raw, donation-manipulable `balance[asset]` at the moment of the trigger. Instead, maintain and use exclusively an internal state variable (e.g., `var['reserve_base']`, `var['reserve_asset']`) that is updated only through the AA's own accounted invest/divest/swap logic, never inferred from `balance[...]`, so that unsolicited direct transfers to the AA address cannot influence the pricing of new shares. Alternatively/additionally, disallow share issuance whenever `var['mm_asset_outstanding']` is anomalously small relative to historical deposits, or require a minimum-liquidity lock (burn a fixed number of shares to a dead address on first deposit) analogous to Uniswap V2's `MINIMUM_LIQUIDITY` mitigation, to prevent the outstanding-supply from ever being drivable down to `1`.

### Proof of Concept
Conceptual reproduction using the bundled sample AA `test/samples/uniswap_like_market_maker.oscript` (the same file referenced above, whose logic is validated/parsed in `test/ojson.test.js`): [3](#0-2) 

1. Deploy the AA from `uniswap_like_market_maker.oscript`; define the `mm_asset` via the `define` trigger.
2. Attacker sends trigger 1: `trigger.output[[asset=base]] = X` bytes and `trigger.output[[asset=$asset]] = 0`(initial state) → hits `$asset_balance == 0 OR $bytes_balance == 0` branch, `$issue_amount = balance[base] = X`; `var['mm_asset_outstanding']` becomes `X`.
3. Attacker sends a divest trigger returning `X-1` of `mm_asset`, dropping `var['mm_asset_outstanding']` to `1` and correspondingly draining most of `balance[base]`/`balance[$asset]` back to the attacker.
4. Attacker sends a plain donation payment of bytes/asset directly to the AA address (front-running the victim's pending invest trigger), inflating `balance[base]` and/or `balance[$asset]` without triggering the invest branch's accounting.
5. Victim's invest trigger for amount `Y` executes; `$bytes_balance` (inflated) makes `$investor_share_of_prev_balance = Y / $bytes_balance` truncate to `0` after `round()`, so `$issue_amount = 0` — victim receives no `mm_asset` shares despite having paid `Y`.
6. Attacker (still holding `1` of `mm_asset_outstanding`, i.e., 100% of outstanding shares) issues a divest trigger and receives `round(1 * balance[base])` and `round(1 * balance[$asset])`, capturing the victim's donated `Y` funds along with the AA's reserves.
