### Title
Cross-organization webhook forgery allows unauthorized commit-status injection and unauthorized stack sync in multi-org Shipit deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to verify a payload's HMAC against using `repository_owner`, a value read out of the *same untrusted, attacker-controlled JSON payload* being verified. It never confirms that the fields actually consumed downstream by event handlers (e.g. `sha` in `StatusHandler`, or `repository.full_name` in `Handler#repository_name`) belong to that same organization. In a documented multi-organization Shipit deployment, this breaks the trust binding "organization that authenticated == repository/commit that is written."

### Finding Description
`verify_signature` picks the app config purely from payload content: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')`, taken from the raw JSON body that is itself the thing being HMAC-verified. Shipit explicitly supports multiple, independently configured GitHub Apps/organizations sharing the same `/webhooks` endpoint, each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

An attacker who legitimately controls (or is a member/admin of) one low-privilege tenant organization onboarded to the same Shipit instance knows that organization's `webhook_secret` (it's their own GitHub App config) and can therefore compute a valid `X-Hub-Signature` for **any** payload body they choose, since `verify_webhook_signature` is a pure HMAC check with no binding to which repository/commit the payload's other fields describe: [5](#0-4) 

Nothing enforces that `repository.owner.login` (used only to pick the secret) matches `repository.full_name` or `sha` (used by handlers to decide what to act on). The `StatusHandler` is the clearest case — it applies the forged status to any commit matching the given `sha`, globally, without any repository/stack scoping at all: [6](#0-5) 

Similarly, generic handlers resolve the target repository purely from the payload's `repository.full_name`, a field distinct from the one used for signature-organization selection: [7](#0-6) [8](#0-7) 

Equality that should hold but doesn't: `organization_whose_secret_verified_signature == organization_owning_repository/commit_acted_upon`. Before the attack, the two are always implicitly the same for legitimate GitHub-originated events (GitHub itself signs with the correct installation's secret matching the actual repo). After the attacker's forged request, the signature is valid for tenant-org A (attacker's own), but the acted-upon commit/repository belongs to tenant-org B (a different, more privileged Shipit customer/organization on the same instance) — the binding is broken.

### Impact Explanation
With `StatusHandler`, an attacker can forge a passing (or failing) commit status for any commit sha in any repository tracked by Shipit, including repositories/organizations they have no GitHub write access to — they only need the commit sha, which is public. Shipit's merge queue and deploy safety gating rely on commit statuses (including "blocking statuses", per `CHANGELOG.md`, and `Status::Group`/`DeploySpec` logic in `app/models/shipit/commit.rb`, `app/models/shipit/status/group.rb`) to decide whether commits are deployable/mergeable. Forging a passing CI status on a victim commit can let an attacker push it through Shipit's automated merge queue or deploy safety checks, resulting in an **unauthorized merge/deploy** for a repository outside their control — meeting the Critical impact bar (unauthorized deploy/merge). The `PushHandler` path additionally lets a cross-tenant attacker trigger `GithubSyncJob`/`sync_github` against a victim stack, an unauthorized cross-repository action.

### Likelihood Explanation
Requires: (1) a Shipit instance configured for multiple GitHub organizations (a documented, supported configuration — see `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), and (2) attacker control of one tenant org's own `webhook_secret` (something they legitimately possess as an admin of their own onboarded org, not a privileged Shipit/GitHub credential for the victim). No Shipit session, API token, or victim GitHub write access is required — only the ability to compute an HMAC with a secret the attacker already knows and to send an HTTP POST to the public `/webhooks` endpoint with a known victim commit sha. This is a realistic and low-effort attack path in the supported multi-org configuration.

### Recommendation
- Cross-check that the organization used to select/verify the webhook secret matches the organization that actually owns the resource referenced by the payload (`repository.full_name` owner, or, for `status`/commit-based events, verify the commit's stack/repository belongs to the same organization) before dispatching to handlers.
- In `StatusHandler`, scope `Commit.where(sha: params.sha)` by repositories belonging to the verified organization, not globally.
- Consider deriving/authorizing the organization from the verified GitHub App installation context (e.g. installation ID) rather than trusting a payload-provided `login` field for secret selection.

### Proof of Concept
1. Deploy Shipit with multi-org config: OrgA (attacker-controlled tenant) and OrgB (victim tenant), each with distinct `webhook_secret`s, per `docs/setup.md`'s "Using Multiple Github Applications" and mirroring `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, as an admin of OrgA's GitHub App, knows OrgA's `webhook_secret`.
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgA/attacker-repo"},
     "sha": "<victim commit sha in OrgB's tracked repo>",
     "state": "success",
     "context": "required-ci-check"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` selects OrgA's app (via `repository.owner.login`), verifies successfully against OrgA's secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matches the victim's commit in OrgB regardless of the `repository` field — and calls `commit.create_status_from_github!(params)`, injecting a forged "success" status onto a commit the attacker never had access to, potentially unblocking OrgB's merge queue/deploy gating.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
