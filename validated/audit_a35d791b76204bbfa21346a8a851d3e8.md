### Title
Webhook signature verification is keyed off `repository.owner.login` while event handlers act on the (separately attacker-supplied) `repository.full_name`, allowing an unauthenticated cross-organization webhook forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization deployments, `Shipit.github(organization:)` resolves a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per GitHub organization. `WebhooksController#verify_signature` selects *which* organization's secret to verify against using `repository_owner`, which is read straight from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')`), before any signature has been proven valid. `Shipit::Webhooks::Handlers::Handler#repository_name`, used by every event handler to decide which `Stack`/`Repository` to mutate, reads a *different* field from the same body: `payload.dig('repository', 'full_name')`. Nothing in the request pipeline enforces that these two fields refer to the same repository/organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

selects the verifying `GitHubApp` using `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` looks up per-org config and instantiates a `GitHubApp` scoped to that org's own `webhook_secret`: [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` explicitly no-ops when the resolved app has no configured secret: `return true unless webhook_secret`: [5](#0-4) 

Meanwhile every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`, etc.) resolves the target `Repository`/`Stack` using `repository_name`, a different key of the same JSON body: [6](#0-5) 

Because `repository_owner` (used for auth/secret selection) and `repository_name`'s embedded owner (used for the write target) are read independently from an unauthenticated body, and because per-organization `webhook_secret` is documented as optional (`webhook_secret: # nil` appears in every example/setup config for multi-org installs): [7](#0-6) [8](#0-7) 

an attacker can pick any organization slug that (a) is configured in `secrets.github` and (b) has no `webhook_secret` set (or whose secret the attacker can otherwise satisfy), put that slug in `repository.owner.login`, and put the `full_name` of a **different**, protected organization's repository in `repository.full_name`. `verify_signature` will pass unconditionally (secretless org), and the handler will then act on the protected repository's `Stack`.

This is the direct analog of the reported bug class: the binding "organization that authenticated" (`repository_owner`, used to pick the verifying `GitHubApp`) is never checked for equality against "the repository that is written" (`repository_name`, used by handlers to select the `Stack`). Just as the Vault's `addPlugin()` trusted an unchecked address, this controller trusts an unchecked cross-reference between two independently-attacker-controlled JSON fields.

### Impact Explanation
Reachable handlers can be triggered against any target repository once the secretless (or attacker-known-secret) org gate is passed:
- `PushHandler` enqueues `GithubSyncJob` for the victim stack with an attacker-chosen `expected_head_sha`, causing the stack to fetch/append commits and recompute deploy specs: [9](#0-8) [10](#0-9) 
- `StatusHandler` writes fabricated CI/commit statuses (`create_status_from_github!`) onto the victim repo's commits, which feed directly into Shipit's deployability checks that gate automatic merges/deploys: [11](#0-10) 

Forged/poisoned status and sync state can influence which commits are considered deployable/mergeable in the targeted org's stacks, i.e. an unauthorized manipulation of deploy/merge state for a repository the attacker does not otherwise have any credential for. This matches the "unauthorized deploy" / cross-repository-write class of impact.

### Likelihood Explanation
Requires: (1) the target instance to be configured with multiple GitHub organizations (a documented, supported configuration - `docs/setup.md`), and (2) at least one configured organization to have a blank `webhook_secret` (shown as the default/example value in every sample config, and plausible for a low-priority/staging org attached to the same Shipit instance as a high-value org). Given those two facts — both are operator configuration choices, not privileged secrets — the attacker needs no token, no GitHub write access, and no knowledge of any org's real secret; only the `POST /github/auth/github/callback`-adjacent public webhook endpoint address (which is standard/documented) and the target's `full_name`. Likelihood is High in any multi-org deployment where secret enforcement isn't uniformly configured, essentially the same operator-error trigger condition the original Mycelium report and Sherlock accepted as valid.

### Recommendation
1. In `WebhooksController#verify_signature`, cross-check that the organization derived from `repository.full_name` (or `organization.login` for org-level events) matches `repository_owner` before selecting the verifying `GitHubApp`; reject mismatches with 422.
2. Do not allow `GitHubApp#verify_webhook_signature` to silently succeed (`return true unless webhook_secret`) for organizations that are expected to enforce signing; either require `webhook_secret` for all configured organizations, or fail closed and log loudly when a secret is absent.
3. In `Handler#repository_name`/`stacks`, only trust the repository looked up if it belongs to the organization that was actually used to verify the signature.

### Proof of Concept
Preconditions: instance configured with `github: { LowSecOrg: { webhook_secret: nil, ... }, HighSecOrg: { webhook_secret: "s3cr3t", ... } }` (multi-org config, per `docs/setup.md` / `secrets_double_github_app.yml`).

```
POST /events              (Shipit engine webhook endpoint)
X-Github-Event: push
X-Hub-Signature: sha1=anything      # no valid secret needed for LowSecOrg

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "LowSecOrg" },        <-- used by verify_signature to pick GitHubApp (no secret => auto-verified)
    "full_name": "HighSecOrg/critical-repo"   <-- used by PushHandler/StatusHandler to pick the real Stack
  }
}
```

`repository_owner` resolves to `"LowSecOrg"`, `Shipit.github(organization: "LowSecOrg").verify_webhook_signature` returns `true` unconditionally because that org has no `webhook_secret`. `PushHandler#stacks` then resolves `Repository.from_github_repo_name("HighSecOrg/critical-repo")` and enqueues `GithubSyncJob` for that stack — a write against `HighSecOrg`'s repository triggered without ever satisfying `HighSecOrg`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
