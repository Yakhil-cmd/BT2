Based on my research, the closest and best-documented analog in this codebase to the Discourse "read state exposure" bug class is the **self-acknowledged private-information leak to the light vendor in the private-payment chain link-proof mechanism**, in `network.js`.

### Title
Private payment chain link-proof verification leaks counterparty payment amounts to the light vendor - (File: network.js)

### Summary
When a light wallet client validates a private (indivisible/divisible) asset payment chain it receives from a payment counterparty, it calls `checkThatEachChainElementIncludesThePrevious()`, which sends the full list of private-chain unit hashes to its light vendor via `light/get_link_proofs` to prove that each element of the chain properly includes the previous one. This request-response pattern discloses to the light vendor exactly which units are linked in a specific private payment chain even though it is not a party to the private transfer, allowing the vendor (which may in fact be, or collude with, an earlier counterparty in the chain) to learn amounts and participants in a supposedly private transaction it did not participate in — mirroring the Discourse issue where per-user private state (read position, notification level) was exposed to parties who had no legitimate need to see it.

### Finding Description
Private asset payments in Obyte are designed so that only actual participants can see the amounts and chain graph; the payload/amount/blinding data are never broadcast on the public DAG. However, `updateLinkProofsOfPrivateChain()` in `network.js` unconditionally calls `checkThatEachChainElementIncludesThePrevious()` for light wallets:

This function is invoked from `updateLinkProofsOfPrivateChain()`, which is itself called every time a light wallet processes a received or restored private payment chain (e.g. from `indivisible_asset.js` `getSavingCallbacks`/private-payment reception flows), i.e. on a path directly reachable by any private-payment counterparty who sends a chain to a light-wallet recipient: [2](#0-1) 

The comment directly preceding the function is an explicit admission by the maintainers that "we are leaking to light vendor information about the full chain. If the light vendor was a party to any previous transaction in this chain, he'll know how much we received." Because the set of unit hashes in `arrUnits` corresponds one-to-one to the hop history of a specific private transfer, any entity that served as light vendor for one hop of the chain (or colludes with such a vendor) can correlate the `light/get_link_proofs` request with the amounts and blinding factors it already possesses from its own earlier participation, defeating the confidentiality guarantee that private (indivisible/divisible) assets are supposed to provide to non-participants.

### Impact Explanation
This breaks the confidentiality invariant of Obyte's private asset system: a private payment chain's amount/topology should be knowable only by the chain's participants, not by an uninvolved light vendor. A light vendor who happens to have serviced any prior hop of a chain (a realistic scenario since light vendors are commonly reused/rotated among the community, and hubs/vendors are often centralized services) can reconstruct how much a victim received in a transaction it was not part of. This is a cross-party information exposure of financial data, matching the Medium severity of the referenced Discourse CVE (private per-user state disclosed to unauthorized viewer), though here the sensitive data is a payment amount held privately by design.

### Likelihood Explanation
The leak occurs automatically and unconditionally for every light wallet receiving/restoring a private-chain payment of length > 1 — no attacker action beyond normal use of private-payment features is required, and it is explicitly triggered every time `updateLinkProofsOfPrivateChain` runs. The only precondition for exploitation is that the light vendor observing the request is (or colludes with) a party from an earlier hop in that specific chain, which is a normal operational configuration in the ecosystem (vendors serve many users and payment chains often revisit shared vendors).

### Recommendation
Avoid sending the raw ordered list of chain unit hashes to the light vendor in a single identifiable request. Options include: batching/mixing unrelated link-proof requests to prevent chain correlation, allowing the wallet to verify the chain link locally using data it already possesses whenever possible, or restructuring the protocol so the vendor only learns pairwise link facts without being able to reconstruct the full ordered chain associated with one transfer.

### Proof of Concept
1. Alice pays Bob a private asset amount X through a payment chain of 2+ hops, using Light-Vendor V1 as V1's hub during one hop.
2. Bob forwards the resulting private chain to Carol, a light-wallet user whose light vendor happens also to be V1 (or V1 colludes with Carol's vendor).
3. When Carol's wallet processes the incoming chain, `handlePrivatePaymentChains` → `updateLinkProofsOfPrivateChain` → `checkThatEachChainElementIncludesThePrevious` sends the full `arrUnits` list of the chain to V1 via `light/get_link_proofs`. [3](#0-2) 
4. V1, having serviced the earlier hop, correlates the requested unit hashes with the amount/blinding data it already recorded from that hop, thereby learning how much Carol received without ever being a party to that specific transfer.
