### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and therefore which `webhook_secret`) to verify the inbound HMAC signature against, by reading `repository_owner` straight out of the **unverified** JSON body. The actual repository/stack that the event handlers subsequently mutate (e.g. `PushHandler`) is resolved independently from other fields of that same untrusted body (`repository.full_name` / owner+name). Nothing forces these two attacker-controlled fields to refer to the same GitHub organization.

### Finding Description
`verify_signature` computes the org to verify against like this: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')`, i.e. from the JSON body itself, before the signature has been validated. Shipit supports per-organization GitHub App configuration (`Shipit.github(organization: ...)`), each with its own `webhook_secret`: [3](#0-2) [4](#0-3) 

Meanwhile, the actual write target of the event (which `Stack`/`Repository` gets synced) is resolved separately, from the same untrusted payload, based on the repository's owner/name pair used for lookup: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to pick the verification secret) and the owner/name pair backing the eventual `Repository`/`Stack` lookup both come from the same JSON body with no cryptographic linkage between them, the code implicitly assumes:

`organization(secret used to verify signature) == organization(repository actually written to)`

This equality is never enforced. An attacker who is an admin/owner of *any* GitHub organization that has installed the Shipit GitHub App (and therefore knows or can obtain that organization's `webhook_secret`, since GitHub App webhook secrets are configured by whoever creates the App per `docs/setup.md`) can compute a valid HMAC for that organization's secret over an arbitrary JSON body, then set `repository.owner.login` in that body to their own (verifiable) organization while setting other repository fields (owner/name used by the handler's repository lookup) to point at a different organization's private repository/stack.

### Impact Explanation
If successfully exploited in a multi-organization Shipit deployment, this allows a party with legitimate access to only one configured GitHub organization to forge push/status/check_suite events that are accepted as authentic for a *different* organization's stack, since the handler resolves and mutates state (e.g., triggers `stack.sync_github(expected_head_sha:)`, commit status creation) based on payload fields never covered by the org-scoped secret check. This is a cross-repository/cross-organization write performed with credentials scoped to a different repository, matching the "cross-repository writes" / "unauthorized deploy" class of Critical/High impact.

### Likelihood Explanation
Exploitation requires the target Shipit instance to be configured with more than one GitHub organization (each with a distinct `webhook_secret`) and requires the attacker to be a legitimate admin of at least one of those organizations (able to read its `webhook_secret` from the GitHub App settings). This is a real but non-trivial precondition — it is not exploitable by a fully unprivileged internet attacker against a single-org Shipit instance, but is plausible for organizations running shared/multi-tenant Shipit installs, which the codebase explicitly supports via `Shipit.github(organization:)`.

### Recommendation
After signature verification succeeds for `repository_owner`, re-derive/verify that every repository-identifying field used later by webhook handlers (`full_name`, `owner`, `name`) is consistent with the same `repository_owner` value used for verification, and reject the payload otherwise. Alternatively, scope handler-side repository/stack lookups strictly by the verified organization rather than trusting the raw payload fields independently.

### Proof of Concept
Conceptual (cannot be fully demonstrated without live multi-org secrets):
1. Attacker is an admin of `org-a`, which has the Shipit GitHub App installed with a known `webhook_secret_a`.
2. Attacker crafts a JSON push payload:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/private-repo"` (a repo they don't control, belonging to `org-b`, also onboarded onto the same Shipit instance)
   - `ref`, `after` set to attacker-chosen values.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_a, body)`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and validates successfully against `webhook_secret_a`.
5. `PushHandler#process` resolves stacks via the repository's owner/name (`org-b/private-repo`) and calls `stack.sync_github(expected_head_sha: params.after)`, mutating state for a stack the attacker never authenticated against. [7](#0-6) [8](#0-7)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
