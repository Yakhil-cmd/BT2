### Title
Unvalidated attacker-controlled public key buffer passed to native secp256k1 ECDH in `decryptPackage()` - (File: device.js)

### Summary
`decryptPackage()` only checks that `dh.sender_ephemeral_pubkey` is a `string`, then feeds the raw base64-decoded bytes straight into `deriveSharedSecret()`, which calls the native `secp256k1` binding's `ecdh()` function. No length or format check (e.g. `isValidPubKey`) is performed on the sender-supplied key before it reaches the native EC point-decoding code, unlike other pubkey inputs elsewhere in the codebase that are explicitly validated.

### Finding Description
`decryptPackage(objEncryptedPackage, depth)` validates only that `dh.sender_ephemeral_pubkey` and `dh.recipient_ephemeral_pubkey` are of `typeof 'string'`: [1](#0-0) 

It never checks that `sender_ephemeral_pubkey` decodes to a valid 33/65-byte compressed/uncompressed secp256k1 public key before using it cryptographically. The value is passed on to `deriveSharedSecret()`: [2](#0-1) 

`deriveSharedSecret()` base64-decodes the attacker-controlled string into an arbitrary-length `Buffer` and hands it directly to the native `ecdsa.ecdh()` call: [3](#0-2) 

Elsewhere in the same file, temp public keys received from a hub are explicitly checked with `isValidPubKey()` before use, showing that the codebase is aware such validation is required for values consumed by the native EC binding — but that check is missing on this particular attacker-reachable path. Passing a buffer of incorrect/attacker-chosen length into a native EC point-parsing routine is the same class of bug as the reported OpenSCAD `import_stl.cc` issue: a length/format field taken from untrusted input is trusted and used directly by lower-level (native/C) parsing logic without prior validation, which is the mechanism that produces out-of-bounds reads/writes in native code.

### Impact Explanation
`decryptPackage()` is invoked whenever any device (paired or not yet paired, since `dh.recipient_ephemeral_pubkey` may match the local permanent/temp keys, and the hub relays `hub/deliver` messages from arbitrary senders) sends an encrypted package to a node. Because the underlying EC operation is performed in a native addon (`secp256k1`), an incorrectly sized or malformed public key buffer reaching that native code without prior JS-side validation can result in out-of-bounds memory access inside the native module, which — depending on the native implementation's own internal bounds checking — can range from a crash (denial of service to the device/wallet process) up to memory corruption. This is reachable by any device that can deliver a message through a hub, i.e., an unprivileged peer with no established relationship to the victim device.

### Likelihood Explanation
Likelihood is limited by whatever internal bounds-checking exists inside the compiled `secp256k1` native binding used by the project; if that binding itself safely rejects malformed/short public keys (as most modern libsecp256k1 wrappers do), the practical exploitability is reduced to a caught exception. This could not be conclusively verified from the indexed source, since the native binding's internal validation logic is outside the JS codebase.

### Recommendation
Validate `objEncryptedPackage.dh.sender_ephemeral_pubkey` (and `recipient_ephemeral_pubkey`) with the existing `isValidPubKey()` helper (or an equivalent length/prefix check) in `decryptPackage()` before calling `deriveSharedSecret()`, mirroring the validation already applied to hub-supplied temp public keys elsewhere in `device.js`.

### Proof of Concept
Not able to fully construct/verify a concrete PoC without access to the compiled `secp256k1` native binding's internal validation behavior; the analysis is based on the traceable data flow: `hub/deliver` → `decryptPackage()` → `deriveSharedSecret()` → `ecdsa.ecdh()` with an unchecked attacker-supplied buffer. function deriveSharedSecret(peer_b64_pubkey, privKey){
```javascript
	var pubkey = new Buffer(peer_b64_pubkey, 'base64');
	var shared_secret_src = Buffer.from(ecdsa.ecdh(pubkey, privKey, {hashfn: (x, y) => x}, Buffer.alloc(32)));
	var shared_secret = crypto.createHash("sha256").update(shared_secret_src).digest().slice(0, 16);
	return shared_secret;
```
