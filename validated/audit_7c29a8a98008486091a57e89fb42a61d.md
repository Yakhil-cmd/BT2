### Title
Unsynchronized concurrent processing of private payment chains enables double-spend of private asset outputs - ([File: private_payment.js])

### Summary
`private_payment.js`'s `validateAndSavePrivatePaymentChain()` performs a check-then-write (SELECT for duplicate detection, then INSERT/UPDATE of `inputs`/`outputs`) that is not protected by any application-level mutex, while `network.js`'s `handleSavedPrivatePayments()` explicitly processes multiple private-payment chains "in parallel" via `async.each`. Two private-payment chains that spend the same private source output can race through the unsynchronized check-then-write window, analogous to the CVE-2015-8839 pattern of unsynchronized concurrent operations on shared filesystem state leading to data corruption.

### Finding Description
`validateAndSavePrivatePaymentChain` in [1](#0-0)  takes a fresh connection from the pool, begins its own transaction, runs a `SELECT` to check whether the output being claimed is a duplicate, and only then delegates to `indivisibleAsset.validateAndSavePrivatePaymentChain` / `divisibleAsset.validateAndSavePrivatePaymentChain` to insert the spend. This whole sequence runs on a private connection with no `mutex.lock` call guarding it (confirmed no `mutex` references exist in `private_payment.js`).

The actual double-spend guard for the private (indivisible) chain is the `UPDATE outputs SET ... WHERE unit=? AND message_index=? AND output_index=? AND is_spent=0` clause in [2](#0-1) , combined with `INSERT "+db.getIgnore()+" INTO inputs ...` at [3](#0-2) . The code never checks the affected-row count of that `UPDATE`; it just runs `async.series(arrQueries, ...)` and reports success unconditionally at [4](#0-3) .

Critically, `network.js`'s `handleSavedPrivatePayments` explicitly fans out to process multiple queued private-payment chains concurrently, per its own comment "handle different chains in parallel": [5](#0-4) , each on its own DB connection/transaction via `validateAndSave` at [6](#0-5) . Additionally, `handleOnlinePrivatePayment` can invoke `privatePayment.validateAndSavePrivatePaymentChain` directly (outside of the `saved_private` queue lock) when the unit is already known: [7](#0-6) .

If two private-payment chains that reference the same source private output (e.g., a coin resent to two different recipients, or replayed with a manipulated cosigner/recipient split) are processed concurrently, both transactions can independently `SELECT` the same not-yet-spent output, both pass validation based on that stale snapshot, and both attempt to write. Depending on the storage engine's isolation semantics, the second transaction's `UPDATE ... WHERE is_spent=0` can silently affect zero rows (already spent by the first transaction) while its `INSERT IGNORE INTO inputs` still succeeds in recording a second, distinct "spend" of the same output — because the code does not verify the `UPDATE` actually matched a row. The result is two separate accepted inputs referencing the same source coin, i.e., a wallet-level double-spend of a private asset unit, which the local device will treat as valid and forward/display as good balances.

### Impact Explanation
This allows a private-payment counterparty (or a device replaying/resending a crafted set of private payment chains, e.g. via `unhandled_private_payments`) to create two divergent, locally-accepted spends of the same private coin. Because private assets are validated/tracked purely on the recipient/cosigner device state (no global public ledger check is possible for `is_private` assets, as acknowledged in `checkForDoublespends`'s light-wallet branch), a successful race corrupts the local view of ownership and enables unauthorized double-spending of the affected private asset amounts — a concrete double-spend/fund-loss condition.

### Likelihood Explanation
Triggering the race requires only that a private-payment counterparty deliver (or a hub/relay replay) two conflicting private-payment chains for the same underlying private output close together in time, since `handleSavedPrivatePayments` deliberately dispatches multiple queued chains concurrently and there is no serializing mutex keyed by the underlying source output/unit across `private_payment.js`. No privileged or malicious-node access is required — an ordinary private-payment sender/counterparty can produce two conflicting spend messages.

### Recommendation
Serialize the check-then-write critical section in `private_payment.js` with a mutex keyed on the source output (e.g., `mutex.lock(["private_write", src_unit+':'+src_message_index+':'+src_output_index], ...)`) so concurrent chains competing for the same private output are processed strictly one at a time. Additionally, verify the affected-row count of the `UPDATE outputs ... WHERE is_spent=0` in `indivisible_asset.js`'s `validateAndSavePrivatePaymentChain` and treat zero affected rows as a hard validation failure (roll back) rather than silently continuing.

### Proof of Concept
1. Create a private (fixed-denomination) asset output owned by device A.
2. Have device A produce two different private-payment chains that both spend that same source output (e.g., resending the payment to two different recipients, or sending recipient and cosigner chains with conflicting data), and deliver both to a victim device B within the same tick, e.g. via two `private_payment` network messages queued to `unhandled_private_payments`.
3. `handleSavedPrivatePayments` on device B picks up both rows and processes them concurrently (`async.each`, comment "handle different chains in parallel"), each calling `privatePayment.validateAndSavePrivatePaymentChain` on its own DB connection.
4. Both transactions' duplicate-check `SELECT` in `private_payment.js` execute before either commits, both proceed to `indivisibleAsset.validateAndSavePrivatePaymentChain`, and both `INSERT IGNORE INTO inputs` succeed while at most one `UPDATE ... WHERE is_spent=0` actually matches — yet both are reported as `ifOk()` since the affected-row count is never checked.
5. Device B now has two private chains it considers valid, both spending the same underlying private coin.
