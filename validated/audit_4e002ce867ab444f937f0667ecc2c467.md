## Title
Full plaintext content of every decrypted device message is written to console/log output - (File: device.js)

### Summary
`decryptPackage()` in `device.js` unconditionally logs the complete decrypted content of every incoming device message with `console.log("decrypted: "+decrypted_message);` before any authorization or subject-whitelist check is applied. This is the same bug class as GHSA-g9qx-25vj-rf53 (CWE-532, Insertion of Sensitive Information into Log File): a normal, expected control-flow path (here, decrypting a hub-relayed message) causes secret material to be persisted into logs/console output that is more broadly accessible than the decrypted payload itself should be.

### Finding Description
When a device (this node or a wallet) receives a `hub/message` justsaying, `handleJustsaying()` in `device.js` calls `decryptPackage()` on the `encrypted_package` supplied inside the message [1](#0-0) . Inside `decryptPackage()`, immediately after AES-GCM decryption succeeds, the plaintext is dumped to the console before it is even JSON-parsed or subjected to any application-level validation: [2](#0-1) 

This decrypted content is attacker-influenced end-to-end: any correspondent (or, for a subset of whitelisted subjects such as `pairing`, `my_xpubkey`, `wallet_fully_approved`, even a *non-correspondent*) can cause this code path to execute by sending a `hub/message` addressed to the victim device, as accepted in `handleJustsaying()`'s `'hub/message'` case [3](#0-2) . The decrypted JSON body that ends up in the log routinely carries highly sensitive wallet/AA material handled elsewhere in the codebase over the same device-message channel, e.g.:
- `pairing_secret` / `reverse_pairing_secret` used to authorize new correspondents [4](#0-3) 
- signed messages/authors and `my_pairing_code` (device pubkey + hub + pairing secret) sent during arbiter contract acceptance [5](#0-4) 
- signatures, extended pubkeys, and multi-sig wallet setup data forwarded via `sendMessageToDevice`/`handleMessageFromHub` in `wallet.js` [6](#0-5) 

Because the log line fires unconditionally on every successful decryption — regardless of whether the message is later rejected for being from an unknown, non-whitelisted correspondent (`respondWithError("correspondent not known and not whitelisted subject")` at device.js:216) — even messages that the application logic explicitly refuses to trust or process still have their full plaintext (which may include a `pairing_secret` allowing further pairing, or other secret text) written to whatever destination `console.log` is captured to (log files, crash-report aggregation, remote log shipping, etc. depending on the embedding wallet/app).

### Impact Explanation
Recommended severity: **Medium**. Log files are often broader in scope than the intended recipients of the data they capture — shared for debugging/support, shipped to third-party log aggregators, stored with looser file permissions on shared hosts, or bundled into crash/bug reports. An attacker who can reach these logs (e.g., a support agent shown a redacted-looking log, a compromised log-shipping pipeline, or another local process on a wallet device with looser file permissions than the wallet's own encrypted secrets) gains plaintext access to pairing secrets, signed payloads, and other correspondence content that should only ever reach the intended device after decryption inside the application, not the logging subsystem. This can enable unauthorized device pairing/hijacking of correspondent relationships and disclosure of wallet-related secrets exchanged between paired devices, aligning with the "wallet and contract message handling" and "device message" reachability criteria in scope.

### Likelihood Explanation
High reachability: any peer that knows a device's permanent or temp pubkey (trivially obtainable — it's exchanged during normal pairing/handshake) can send it a `hub/message`/`hub/deliver` and trigger `decryptPackage()`, and thus this log line, without any prior trust relationship, since the log occurs before the correspondent-known/whitelist check [7](#0-6) . The only precondition for practical exploitation is that the deploying application/wallet captures `console.log` output to a location with a different (typically broader) trust boundary than the runtime process itself — a very common deployment pattern for Node.js wallet/hub software.

### Recommendation
Remove or gate the `console.log("decrypted: "+decrypted_message);` statement in `decryptPackage()` (device.js:466) behind an explicit, opt-in debug flag that defaults to off, and ensure it is never enabled in production builds. Apply the same review to the other unconditional plaintext logs surrounding decryption in the same function (e.g., the commented-out but easily re-enabled `prev temp private key` logs at device.js:421-423) and to `network.js`'s raw inbound-message logging in `onWebsocketMessage()` [8](#0-7) , which similarly prints truncated raw wire content that can include encrypted device-message envelopes and other identifying metadata.

### Proof of Concept
1. Attacker learns victim's permanent device pubkey/address and home hub (available whenever the victim shares a pairing code or communicates with any correspondent).
2. Attacker (or a malicious/compromised hub) sends a `hub/message`/`hub/deliver` justsaying to the victim containing an `encrypted_package` addressed to the victim's known temp or permanent ephemeral pubkey, with an arbitrary plaintext JSON body, e.g. `{"from": attacker_addr, "device_hub": "...", "subject": "pairing", "body": {"pairing_secret": "SECRET", "device_name": "x"}}`.
3. `handleJustsaying()` → `decryptPackage()` decrypts the package and executes `console.log("decrypted: "+decrypted_message)`, printing the full JSON (including `SECRET`) to the node's console/log output before any correspondent/whitelist check occurs.
4. Whoever has access to the resulting log stream (support tooling, log aggregator, crash reporter) now has the plaintext content, e.g. secrets intended to remain confidential between the two paired devices.
