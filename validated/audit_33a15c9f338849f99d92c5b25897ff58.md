### Title
Tokens transferred directly to the Pool or Controller are permanently locked — no bookkeeping credit and no recovery path - (File: contracts/pool/src/lib.rs)

### Summary
The reported class — a contract that accepts funds but exposes no withdrawal/rescue path — maps onto XOXNO Lending's custody model. The `LiquidityPool` contract custodies all market tokens but exposes no `sweep`/rescue entrypoint, and it deliberately does not credit unsolicited transfers: "Cash is an accounting book, separate from the token balance" and "direct donations do not automatically increase booked cash" (docs/reference/architecture.md; INV-ACCT-02: "token donations alone do not increase" tracked cash). The same applies to the `Controller`, where `refund_controller_balance_delta` in `contracts/controller/src/payments.rs` refunds only the measured balance delta of a single operation and explicitly "preserv[es] the pre-existing balance".

### Finding Description
In `contracts/pool/src/lib.rs` the complete mutator surface is `create_market`, `update_params`, `upgrade`, `supply`, `borrow`, `withdraw`, `repay`, `update_indexes`, `recapitalize`, `flash_loan`, `create_strategy`, `seize_positions`, `net_settle`, `claim_revenue`, plus views — all `#[only_owner]` (the controller). None of them can release tokens above the tracked cash book: every outbound leg (`borrow`, `withdraw`, `claim_revenue`, `flash_loan`) is capped by the market's `cash` field, which a direct `token.transfer(pool, amount)` never increments. There is no `sweep_balance`/`rescue` counterpart to the one that exists in `contracts/swap-aggregator/src/lib.rs` (`sweep_balance` at lines 187–203) — the lending contracts simply lack it.

At the controller, any token a user transfers directly sits on the contract balance. `refund_controller_balance_delta` (`contracts/controller/src/payments.rs:41-52`) only returns the *delta* accrued inside one call; a pre-existing stray balance is untouched, and no controller entrypoint pays arbitrary token balances to a caller. Governance operations are typed administrative proposals (`contracts/governance/src/op.rs`), not arbitrary external calls, so there is no governance path to push tokens out of the pool or controller either. The threat-model doc confirms the same posture for the DeFindex adapter ("no recovery path for arbitrary stranded assets").

### Impact Explanation
An unprivileged user who calls `token.transfer(from, pool_or_controller, amount)` — e.g., depositing to the pool address instead of going through `Controller::supply`, or sending collateral to the controller expecting it to be credited — permanently loses the funds. The tokens remain in custody but are unbooked, unclaimable by the sender, and unreachable by any entrypoint: pool outflows are bounded by the cash book, and the controller has no outbound path for stray balances. This is permanent freezing/loss of user funds, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Reachable by a single unprivileged address via an ordinary SAC/token `transfer` — explicitly listed as an in-scope analog path. Likelihood is modest because it requires user error (sending directly rather than via `supply`), but that is exactly the scenario class of the referenced finding (anyone can send ETH to `SwapRouter.receive()`). Rate it Medium, mirroring the source.

### Recommendation
Either add an owner/governance-gated `sweep`/`rescue` on the pool (and controller) that only releases balance above the sum of all markets' booked cash plus accrued obligations — analogous to the swap-aggregator's `sweep_balance` which protects `ReservedTotal` — or document the no-recovery property prominently and consider rejecting/flagging direct transfers where the token interface allows it.

### Proof of Concept
1. User calls `token::Client::transfer(user → pool, X)` on a listed asset.
2. `pool.get_reserves(hub_asset)` is unchanged (cash book untouched; INV-ACCT-02).
3. No entrypoint can release `X`: `withdraw`/`borrow`/`claim_revenue`/`flash_loan` all debit `cash`, which excludes `X`; no `sweep` exists on `LiquidityPool` (see full impl block, `contracts/pool/src/lib.rs:99-326`). Governance has only typed ops, no arbitrary-call operation.
4. Same for the controller: after a direct transfer, `refund_controller_balance_delta` on any subsequent op leaves the pre-existing balance untouched (`contracts/controller/src/payments.rs:39-52`), and no controller entrypoint returns stray balances.

Caveat: I verified the pool entrypoint list and controller refund logic, but did not exhaustively enumerate every governance operation variant in `contracts/governance/src/op.rs`; if a generic "call arbitrary contract" operation existed, it could provide a recovery path and weaken this to a UX footgun. The typed-operation design described in docs/reference/architecture.md suggests no such escape hatch exists.
