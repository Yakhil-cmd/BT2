### Title
Webhook signature verification keys on `repository.owner.login`, but every event handler resolves the target Stack from the independent, unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to validate an incoming webhook against using `repository.owner.login` (or `organization.login`), but every webhook `Handler` (PushHandler, MembershipHandler, PullRequest handlers, etc.) resolves the `Stack`/`Repository` that is actually mutated using the independent JSON field `repository.full_name`. These two fields are never checked against each other, so a valid HMAC for organization A does not guarantee the payload actually describes organization A's repository.

### Finding Description
`verify_signature` computes the organization used to select the signing secret purely from attacker-controlled JSON: [1](#0-0) [2](#0-1) 

That `repository_owner` value is used only to select which `GitHubApp`/secret to validate the HMAC signature against via `Shipit.github(organization: repository_owner)`; when a given configured organization has no `webhook_secret` set, `verify_webhook_signature` unconditionally returns `true`: [3](#0-2) 

Meanwhile, every default handler (`PushHandler`, `MembershipHandler`, PR handlers, etc.) resolves the `Stack`/`Repository` it will act on from a *different* JSON field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [4](#0-3) [5](#0-4) 

Nothing in the controller or in `Handler` cross-checks that the owner segment of `repository.full_name` matches `repository.owner.login`/`organization.login` used to select the signing secret. Since Shipit supports hosting multiple GitHub organizations in one instance (`config/secrets.yml` "Using Multiple Github Applications", see `test/dummy/config/secrets_double_github_app.yml`), this is a real cross-tenant boundary: the binding that should hold is `organization_that_authenticated == organization_of_repository_being_written_to`, but it is never enforced.

### Impact Explanation
An unprivileged attacker with a GitHub App installed on their own org "OrgA" (or, more simply, on any org that Shipit is configured to serve but for which no `webhook_secret` was set — a documented optional field, `webhook_secret: # nil`) can obtain (or need not even obtain) a valid webhook signature for OrgA, then forge a webhook body where `repository.owner.login` (or `organization.login`) is `OrgA` (or the org without a secret) but `repository.full_name` is set to `OrgB/victim-repo`, an entirely different, unrelated Stack that Shipit is deploying. The `verify_signature` check passes (either because it's checked against the attacker's own legitimate org secret, or trivially bypassed for the secret-less org), and the corresponding handler then acts on `OrgB/victim-repo` using `repository.full_name` alone:
- `PushHandler` calls `stack.sync_github(expected_head_sha: ...)`, triggering a git sync of the victim repository/stack.
- `MembershipHandler` can add/remove memberships for `Team`s resolved independent of this specific check (lower severity, team-scoped).
- PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `AssignedHandler`) can archive/unarchive/mutate `ReviewStack`s and `PullRequest` records belonging to the victim repository.

This crosses the "escalation ... unauthenticated read/write of stack state" and potentially "unauthorized deploy" bar for High severity, since it lets an attacker who only authenticated as one tenant mutate state belonging to a different tenant's repository/stack without ever needing write access to that repository.

### Likelihood Explanation
Requires (a) a multi-org Shipit deployment (documented, supported configuration) and (b) either an org configured without a `webhook_secret` (an explicitly supported, nil-by-default option in `docs/setup.md`/`config/secrets.development.example.yml`) or an attacker who legitimately controls a GitHub App installation on one of the configured orgs. Given Shipit explicitly documents and supports "Using Multiple Github Applications" with per-org optional secrets, and per-org secret is optional, this is a realistic misconfiguration/deployment scenario rather than a purely theoretical one.

### Recommendation
After signature verification, re-derive the organization/owner from the same `repository.full_name` (or `organization.login`) that handlers use, and reject the webhook (422) unless it matches the organization whose secret validated the signature. Concretely, in `WebhooksController#verify_signature`, assert that `params.dig('repository', 'full_name')&.split('/')&.first&.downcase == repository_owner.downcase` before allowing `create` to dispatch to handlers, so the authenticated organization and the repository actually acted upon are bound together.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` (attacker-controlled GitHub App install, or an org with `webhook_secret: nil`) and `OrgB` (victim org with a Stack tracking `OrgB/victim-repo`), per `test/dummy/config/secrets_double_github_app.yml` style config.
2. Attacker computes/obtains a valid `X-Hub-Signature` for `OrgA` (trivial if `OrgA.webhook_secret` is unset, since `verify_webhook_signature` short-circuits to `true`), or signs with their own known `OrgA` secret.
3. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
4. `verify_signature` validates against `OrgA`'s (attacker-known or secret-less) config and passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's Stack, despite the attacker never having authenticated as `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
