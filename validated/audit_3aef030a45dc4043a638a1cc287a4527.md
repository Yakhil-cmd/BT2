### Title
Webhook signature verified against `repository.owner.login`, but the acted-upon repository is taken from the unverified `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to check the HMAC signature against using `repository_owner`, which is read from the JSON body via `params.dig('repository', 'owner', 'login')` [1](#0-0) . However, the handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler`) looks up the target `Repository`/`Stack` using a *different* field of the same unverified body: `payload.dig('repository', 'full_name')` [2](#0-1) .

### Finding Description
In a multi-organization deployment (`Shipit.github_default_organization` non-nil, i.e. `secrets.github` keyed by organization), each organization has its own `webhook_secret`, obtained via `Shipit.github(organization: repository_owner)` → `github_app_config(organization)` [3](#0-2) .

`verify_signature` computes/validates the signature using the secret belonging to `repository_owner` (`repository.owner.login`), then, if valid, `create` parses the same raw JSON and dispatches it to handlers using `repository.full_name` to resolve the actual `Stack`/`Repository` [4](#0-3) [5](#0-4) .

`repository.owner.login` and `repository.full_name` are two independent fields inside the same attacker-controlled JSON body — nothing ties them together, and the HMAC signature itself only proves "this body was signed by the secret configured for organization X", not that field consistency holds. An attacker who controls (or compromises the low-privilege webhook secret of) one organization ("org-attacker") they legitimately administer can craft a payload where `repository.owner.login = "org-attacker"` (so the signature validates against org-attacker's real, correctly-signed webhook secret) while `repository.full_name = "org-victim/some-repo"`. The webhook then gets accepted and dispatched to any handler for events such as `push`, `status`, `check_suite`, `pull_request`, `commit_status`, `merge_status`, etc., all of which resolve their target stack purely off `repository.full_name` (via `Repository.from_github_repo_name`) [6](#0-5) .

This breaks exactly the binding class described in the rules: "an organization that authenticated versus the repository that is written." The verified field (`repository.owner.login`, used only to select which secret validates the HMAC) is not the field acted upon (`repository.full_name`, used to pick the `Stack` that gets mutated).

### Impact Explanation
Handlers dispatched off `Shipit::Webhooks.for_event(event)` can mutate state of a stack belonging to a different organization than the one whose secret validated the signature — e.g. `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for the target branch of the victim's stack based purely on `repository.full_name` and `ref`/`after` from the payload [7](#0-6) ; the `status`/`check_suite` handlers create commit statuses and can influence CI-gated deploy eligibility on the victim stack. This does not on its own grant `deploy`/`merge` (those still require an authenticated user/API client), but it does allow cross-organization forging of GitHub-originated signals (pushes, CI statuses, check-suite results, merge/pull-request state) that Shipit trusts as coming from GitHub for a specific repository, letting an org-A administrator falsify state for an org-B stack without ever compromising org B's webhook secret. This is a cross-tenant boundary crossing but requires the attacker to already legitimately administer at least one organization onboarded to the same Shipit instance (an unprivileged-relative-to-org-B attacker), which fits an "unprivileged attacker" analog to the ERC-721 report's cross-binding pattern.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (config keyed by org, not the single top-level `github` schema) — common for larger installs serving multiple GitHub orgs; (2) attacker control of a legitimate, correctly configured webhook secret for at least one onboarded organization (their own org's `webhook_secret`, which they can obtain since they can configure their org's GitHub App/webhook themselves, or via any webhook delivery replay/forwarding), and (3) knowledge of a valid `owner/repo` `full_name` for the victim stack (public info, since Shipit stacks map 1:1 to public/private GitHub repos already known to be tracked). All of these are attacker-obtainable without needing session cookies, `ApiClient` tokens, GitHub App private keys, or org-B credentials, matching the "unprivileged-attacker" scope of the rules.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, cross-check that the organization whose secret validated the signature (`repository_owner`) matches the owner segment of `repository.full_name` (and `organization.login` when present) before dispatching to handlers; reject the request (422) on mismatch instead of trusting `full_name` unconditionally in `Handler#repository_name`.

### Proof of Concept
1. Deploy Shipit with `secrets.github` keyed by two organizations, `org-attacker` and `org-victim`, each with its own `webhook_secret`.
2. As an administrator of `org-attacker`'s GitHub App/webhook, craft a `push` (or `status`/`check_suite`) event JSON body where `repository.owner.login = "org-attacker"` but `repository.full_name = "org-victim/target-repo"` and `ref`/`after` point at a commit the attacker controls.
3. Sign the raw body with `org-attacker`'s real `webhook_secret` (`sha1=` HMAC as computed in `Hook::DeliverySigner`/`verify_webhook_signature`) and POST it to `/github/webhooks` with header `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "org-attacker")` (from `repository.owner.login`), the signature matches org-attacker's secret, so verification passes.
5. `create` parses the body and dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("org-victim/target-repo")` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack — despite the request never being signed by `org-victim`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
