### Title
Cross-organization webhook confused deputy: signature verification org ≠ commit/stack acted upon - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization webhook secret to verify the incoming HMAC signature against based on an attacker-controlled field in the same untrusted JSON body (`repository.owner.login`, or `organization.login` as fallback). Once the signature check passes for *that* organization, the controller dispatches the payload to event handlers that determine *what gets written* using different, independently-controlled fields of the same body (e.g. `sha` for `status` events, or `repository.full_name` for `push`/other events). Nothing binds "the organization whose secret validated this request" to "the specific repository/commit/stack that will actually be mutated."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` resolves the signing app like this: [1](#0-0) 

`repository_owner` is read straight out of the JSON body: [2](#0-1) 

Shipit explicitly supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret` (`docs/setup.md`, "Using Multiple Github Applications"), selected via `Shipit.github(organization:)`: [3](#0-2) 

After the signature is verified against Org A's secret, `create` dispatches the *entire, attacker-authored payload* to event handlers without re-checking that the payload's other fields are consistent with Org A: [4](#0-3) 

Crucially, `StatusHandler#process` does not scope by repository/stack at all — it looks up commits **globally by `sha`**: [5](#0-4) 

`create_status_from_github!` then creates a `Status` bound to whatever `commit.stack_id` that SHA happens to belong to, regardless of which organization's secret validated the request: [6](#0-5) [7](#0-6) 

The binding that should hold is:
`organization whose webhook_secret validated the HMAC == organization/repository that owns the commit/stack being mutated`

Instead the code enforces only:
`organization named in payload.repository.owner.login == organization whose secret validated the HMAC`

and separately, unrelated to the above:
`commit acted upon == whatever commit matches payload.sha (global lookup, no org/stack scoping)`

Since both `repository.owner.login` and `sha` are independent fields inside the same attacker-supplied JSON body that gets HMAC-signed, an actor who possesses (or is issued) a valid `webhook_secret` for **their own** organization/App installation (Org A) — a normal, unprivileged position for an org admin in a multi-tenant Shipit deployment — can craft a payload where:
- `repository.owner.login` = `"OrgA"` (selects Org A's app/secret for verification)
- `sha` = a known commit SHA belonging to a stack owned by a completely different organization, Org B, that is also configured on the same Shipit instance

Sign the whole payload with Org A's `webhook_secret`, POST it to `/webhooks` with `X-Github-Event: status`. `verify_signature` passes because it only checks the HMAC against Org A's secret over the literal bytes posted — it has no way to know (and does not check) that the `sha` field belongs to a repo outside Org A. `StatusHandler` then creates/updates a `Status` (state, description, target_url, context all attacker-controlled) on the Org B commit.

The same underlying flaw generalizes to `push` (uses `payload.dig('repository','full_name')` in `app/models/shipit/webhooks/handlers/handler.rb`, `repository_name`/`stacks`), `check_suite`, `pull_request`, and `membership` handlers, all of which read repository/stack-targeting fields independently of the field used for signature-org selection.

### Impact Explanation
Forging a `success` `Status` for an arbitrary tracked commit belonging to a different, unrelated organization directly manipulates `Commit#deployable?`/`Status::Group` state: [8](#0-7) 

`Status` creation triggers `schedule_continuous_delivery` on commit and stack, which (if the target stack has `continuous_deployment` enabled) causes Shipit to automatically trigger a real deploy of that commit once it appears "deployable," even though no legitimate CI ever reported success and the actor triggering this has no relationship to that organization/repository at all. This is an unauthorized-deploy / CI-gate-bypass impact crossing an organization boundary that the multi-org webhook_secret feature is explicitly meant to isolate — i.e. cross-repository/cross-organization write access using credentials scoped to a different tenant.

### Likelihood Explanation
This requires: (1) a Shipit instance configured with multiple GitHub organizations/Apps (a documented, supported configuration), (2) the attacker controlling a legitimate `webhook_secret` for at least one of those organizations (e.g., as an org admin who configured their own GitHub App, which is not "repository write access" to the victim org and not any of the excluded privileged credentials), and (3) knowledge of a target commit SHA for a stack belonging to a different tenant on the same instance (commit SHAs are frequently public/observable via GitHub itself). Given Shipit is designed for shared, multi-tenant hosting of many organizations' deploy pipelines behind one app instance, this is a realistic configuration, and the SHA-only global lookup in `StatusHandler` makes exploitation mechanical once a valid secret for any one tenant is available.

### Recommendation
Bind webhook-driven mutations to the *same* organization/repository that was cryptographically verified:
- After determining `repository_owner` and verifying the signature against that organization's secret, re-derive and pass the verified organization/repository identity into `Shipit::Webhooks.for_event(event)` handlers, and have each handler reject/ignore any payload whose `repository.full_name`'s owner does not match the verified organization.
- In `StatusHandler` (and any handler doing global lookups), scope `Commit.where(sha: params.sha)` to commits whose `stack.repository.owner` matches the verified organization instead of a global, unscoped lookup.
- Apply the same repository/organization-consistency check uniformly across all handlers in `app/models/shipit/webhooks/handlers/**`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (per `docs/setup.md`).
2. As the admin of OrgA (legitimately possessing OrgA's `webhook_secret`), craft a `status` event JSON body:
```json
{
  "sha": "<sha of a real commit belonging to a stack under OrgB>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: status` and the computed signature.
5. `WebhooksController#verify_signature` selects `Shipit.github(organization: 'OrgA')` (see `app/controllers/shipit/webhooks_controller.rb` lines 24-30, 59-62) and the signature validates.
6. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24) finds the OrgB commit by SHA (no org scoping) and calls `create_status_from_github!`, creating a `success` `Status` on OrgB's stack — despite the request only ever being validated against OrgA's secret.
7. If OrgB's stack has `continuous_deployment: true`, the newly "successful" commit becomes `deployable?` and Shipit's continuous delivery flow can trigger an unauthorized deploy on OrgB's stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
