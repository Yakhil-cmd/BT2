### Title
Native value sent alongside a call to a "pure" (stateless) precompile in `pallet-revive` is permanently unrecoverable - (File: substrate/frame/revive/src/exec.rs)

### Summary
The reported OpenQ bug is about a `payable` function that accepts both `msg.value` (native ETH) and an ERC20 token parameter; when both are supplied, the code path for the ERC20 branch silently ignores `msg.value`, and since the contract never refunds or accounts for it, the native token is permanently lost. The violated invariant is: *"any native value accepted by a function must either be used for its stated purpose or be refundable/recoverable — it must never be silently swallowed."*

The closest demonstrable analog in `pallet-revive` is calling a "pure" precompile (`Precompile::HAS_CONTRACT_INFO = false`, e.g. `ECRecover`, `Sha256`, `Identity`, `Bn128*`, or the `ERC20`/`Vesting`/`AssetConversion`/`Xcm` precompiles) with a non-zero `value`. The call succeeds, the value is unconditionally transferred into the precompile's fixed-address account, but the precompile logic operates purely on its ABI-decoded arguments (e.g., ERC20 `transfer(to, amount)`) and never touches or forwards the received native balance. Because the precompile address is a stateless, keyless, protocol-defined address with no corresponding private key and no withdrawal logic, the deposited native currency becomes permanently stuck — functionally identical to the "value lost because the token-specific branch never processes/refunds it" pattern in the report.

### Finding Description
In `substrate/frame/revive/src/exec.rs`, `Stack::run()` unconditionally transfers `frame.value_transferred` to the destination account *before* executing the destination's logic, regardless of whether the destination is a normal contract, a plain account, or a precompile: [1](#0-0) 

This transfer happens for *any* callee, including precompiles. Separately, only precompiles with `HAS_CONTRACT_INFO = true` get special account/ED handling: [2](#0-1) 

For precompiles with `HAS_CONTRACT_INFO = false` (the "pure" precompiles), the trait documentation explicitly states "No account or any other state will be created for the address," and the entry point (`Precompile::call`, not `call_with_info`) is only given a plain `Ext`, with no access to the value that was just transferred: [3](#0-2) 

The existing test `pure_precompile_works` explicitly confirms that sending `value = 100` alongside a call into e.g. the `ECRecover` precompile succeeds, the precompile output is still produced correctly, and the balance is now sitting at the precompile's address: [4](#0-3) 

Concretely, the pallet-assets `ERC20` precompile — which is the on-chain analog of the OpenQ contract's ERC20 branch — is also `HAS_CONTRACT_INFO = false`: [5](#0-4) 

Its `transfer` implementation only moves `pallet_assets` balances via `do_transfer`; it never reads, forwards, or refunds any native `value` that accompanied the call: [6](#0-5) 

So a user calling the ERC20 precompile's `transfer(to, amount)` function while *also* attaching a non-zero native `value` (exactly the "both an ERC20 token and value specified" scenario from the OpenQ report) results in:
1. The ERC20 `amount` being transferred correctly via `pallet_assets`.
2. The native `value` being unconditionally deposited into the precompile's fixed address (via `transfer_from_origin`), with no logic anywhere in the precompile call path to move, refund, or account for it.

Because the precompile's account is derived from a hard-coded/deterministic address (not backed by any private key a user or the protocol controls, and pure precompiles are documented to have no contract info/state at all), there is no dispatchable extrinsic, precompile method, or governance call in-scope that can move funds out of that address again. This mirrors the OpenQ report's core defect: a caller-supplied native value is accepted by a call that is really intended to operate on a separate token/parameter, and the code path for that parameter never uses or returns the native value, causing deterministic, irreversible loss.

### Impact Explanation
Any signed account (no privileged role required) that calls a pure precompile (ECRecover, Sha256, Ripemd160, Identity, Modexp, Bn128Add/Mul/Pairing, Blake2F, the pallet-assets/pool-assets/foreign-assets `ERC20` precompiles, `VestingPrecompile`, `XcmPrecompile`, `pallet_asset_conversion_precompiles::AssetConversion`, etc.) with a non-zero `value` loses that value permanently and irreversibly. This is especially dangerous because:
- These are the exact addresses that Solidity/EVM tooling and contracts routinely call to interact with tokens (e.g., ERC20 wrapper contracts), so a contract author or a wallet UX that allows attaching `msg.value` to any call (as is normal in EVM tooling) can trigger this by mistake, exactly as described in the original report.
- The call does not revert or error — it succeeds silently, so the loss is easy to miss until funds are unrecoverable.

This is a fund-loss bug but it is self-inflicted by the caller (no third-party attacker profits, and no cross-account griefing is possible), which limits severity relative to a theft/unbacked-issuance bug, but is a real, deterministic, irreversible value-loss defect matching the class and severity of the original Medium-rated report.

### Likelihood Explanation
High likelihood of occurrence in practice: sending `value` alongside a `CALL`/`DELEGATECALL`-style interaction with an arbitrary destination address is a completely normal EVM pattern, and nothing in `pallet-revive`'s call path rejects or warns when the destination happens to be a precompile that cannot use that value. No special conditions, timing, or privileged role are required — a simple signed `pallet_revive::call` (or an EVM `CALL` opcode from within a contract) with `dest` set to a known precompile address and non-zero `value` is sufficient.

### Recommendation
- In `Stack::run()` (`substrate/frame/revive/src/exec.rs`), reject calls (return an error such as `Error::<T>::TransferFailed` or a dedicated `Error::<T>::PrecompileCannotReceiveValue`) when `frame.value_transferred` is non-zero and the destination resolves to a `Precompile` (particularly ones with `HAS_CONTRACT_INFO = false`, i.e., no account/state to house the funds meaningfully) unless that specific precompile explicitly declares it can accept and use value.
- Alternatively, add an explicit `Precompile::ACCEPTS_VALUE` associated constant (default `false`) and check it before performing the unconditional balance transfer at the top of `run()`, failing the call early with a clear error rather than allowing silent loss.
- Audit each shipped precompile (`ERC20`, `VestingPrecompile`, `XcmPrecompile`, `AssetConversion`, builtin EVM precompiles) to confirm none intend to receive native value; document this constraint clearly in the `Precompile` trait.

### Proof of Concept
No new test was run against a live network (out of scope). The existing repository test `pure_precompile_works` already demonstrates the mechanics needed for reproduction without any modification: [4](#0-3) 

This test shows that:
- Calling a precompile address (e.g. `H160::from_low_u64_be(1)` for `ECRecover`) with a nonzero `value = 100` via a contract's `CALL` succeeds without reverting.
- `Pallet::<Test>::evm_balance(&precompile_addr)` is asserted to equal `100` afterward — i.e., the value is deposited at the precompile's address and stays there.
- No corresponding test or code path exists anywhere in `substrate/frame/revive` that withdraws, sweeps, or refunds balance from a precompile's account, and pure precompiles (`HAS_CONTRACT_INFO = false`) are documented to have no contract logic/state to do so.

To fully confirm real-fund loss (as opposed to only the internal `evm_balance` accounting), a background Devin agent with repo access should extend this test (or write a new one) to:
1. Call the pallet-assets `ERC20` precompile's `transfer` function with a non-zero native `value` attached, from a `pallet_revive::Pallet::<Test>::bare_call`.
2. Assert the ERC20 token balance moved correctly (already covered by `precompile_transfer_works`).
3. Assert the native `Balances::free_balance` of the caller decreased by the `value`, and that this value now sits at the ERC20 precompile's mapped `AccountId`, with no dispatchable/precompile call in the codebase capable of moving it elsewhere.

I was not able to execute this extended test within the current environment (no filesystem/terminal access in ask-only mode), so the specific numeric assertions for the `ERC20` precompile combined with `value` are not independently confirmed here beyond the `pure_precompile_works` evidence already present in the repository; a Devin session with code execution would be required to run and confirm this exact scenario end-to-end.

	/// Execute the transfer call.
	fn transfer(
		asset_id: <Runtime as Config<Instance>>::AssetId,
		call: &IERC20::transferCall,
		env: &mut impl Ext<T = Runtime>,
	) -> Result<Vec<u8>, Error> {
		env.charge(<Runtime as Config<Instance>>::WeightInfo::transfer())?;

		let from = Self::caller(env)?;
		let dest = <Runtime as pallet_revive::Config>::AddressMapper::to_account_id(
			&call.to.into_array().into(),
		);

		let f = TransferFlags { keep_alive: false, best_effort: false, burn_dust: false };
		pallet_assets::Pallet::<Runtime, Instance>::do_transfer(
			asset_id,
			&<Runtime as pallet_revive::Config>::AddressMapper::to_account_id(&from),
			&dest,
			Self::to_balance(call.value)?,
			None,
			f,
		)?;

		Self::deposit_event(
			env,
			IERC20Events::Transfer(IERC20::Transfer {
				from: from.0.into(),
				to: call.to,
				value: call.value,
			}),
		)?;

		Ok(IERC20::transferCall::abi_encode_returns(&true))
	}
