### Title
Merkle "node-as-leaf" second-preimage forgery in `is_valid_merkle_proof`/`in merkle` allows forging inclusion of unauthorized elements - (File: merkle.js)

### Summary
`merkle.js` implements `getMerkleRoot`/`getMerkleProof`/`verifyMerkleProof` without any domain separation between leaf hashes and internal-node hashes: both are computed with the exact same `hash(str) = sha256(str)` function, with leaves hashed as `hash(element)` and internal nodes as `hash(child1 + child2)` [1](#0-0) . This is the classic CVE-2012-2459-style Merkle "second preimage"/node-as-leaf vulnerability, the exact bug class described in the external report (leaf structure colliding with intermediate-node structure, allowing a valid proof to be produced for content that was never an original leaf). The code even contains an explicit acknowledgment of this exact issue that was never mitigated: `// Node-as-Leaf issue might matter in some cases` in `verifyMerkleProof` [2](#0-1) .

### Finding Description
`verifyMerkleProof(element, proof)` computes `the_other_sibling = hash(element)` and then repeatedly folds it with `proof.siblings[i]` using the same `hash()` function used to build internal nodes, comparing the final value to `proof.root` [3](#0-2) . Because leaf-hashing and node-hashing use an identical, unprefixed hash function, the byte string `H(a) + H(b)` (the literal concatenation of two child hashes at some internal node) is indistinguishable from an "original leaf" content whose hash happens to equal that internal node's value. An attacker who knows (or can compute) any two sibling hashes anywhere in a published tree can submit `element = H(a) + H(b)` together with the proof path starting one level above that internal node, and `verifyMerkleProof` will report a valid inclusion for an "element" that was never one of the tree's true leaves.

This primitive is directly exposed to attacker-controlled input in two places:
- The oscript function `is_valid_merkle_proof(element, proof)`, where both `element` and the serialized `proof` (including `proof.root`, parsed straight from user-supplied trigger data via `deserializeMerkleProof`) come from AA trigger data supplied by an unprivileged trigger sender [4](#0-3) [5](#0-4) . AA authors commonly use this primitive to verify that a trigger-supplied `element` belongs to a whitelist/snapshot/airdrop tree whose root is independently pinned (e.g. compared against a stored state var or oracle-posted root); the primitive itself provides no protection against the node-as-leaf forgery, so any AA design that trusts `is_valid_merkle_proof` to authenticate an *arbitrary* trigger-controlled `element` against a known root is vulnerable to accepting a forged "element" that was never part of the original data set.
- The `'in merkle'` address-definition authentifier, which deserializes a signer-supplied proof and verifies a value against a root pulled from `data_feeds` [6](#0-5) . Here the compared `element` is fixed in the definition, which limits (but does not eliminate, depending on how definitions are constructed/reused) exploitability of this particular call site relative to the more general AA usage.

### Impact Explanation
Any AA that relies on `is_valid_merkle_proof` to gate fund release, whitelist membership, snapshot-based distribution, or similar logic based on trigger-supplied `element`/`proof` pairs can be tricked into accepting a fabricated "leaf" that never existed in the committed dataset, as long as the attacker can compute two adjacent hash values anywhere in the tree (trivially possible if the underlying element list/tree is public, as is typical for airdrop/whitelist Merkle roots). This can lead to unauthorized AA fund release/spending to addresses/values that were never actually included in the committed set — a concrete violation of the AA's funds-custody invariant.

### Likelihood Explanation
Exploitation requires only knowledge of the Merkle tree's public leaf set (or any two adjacent node hashes), which is standard for use cases like airdrops/whitelists, and requires no privileged access — a normal AA trigger sender can supply the crafted `element` and `proof`. The likelihood of exploitation is high for any AA that uses `is_valid_merkle_proof` in this pattern; the severity depends on the specific AA logic, but the underlying primitive itself is unconditionally forgeable.

### Recommendation
Add domain separation to `merkle.js`: hash leaves and internal nodes differently, e.g. `hash("\x00" + element)` for leaves and `hash("\x01" + left + right)` for internal nodes, and update `getMerkleRoot`, `getMerkleProof`, and `verifyMerkleProof` consistently. This must be a coordinated/versioned change since it changes computed roots for all future trees; existing `is_valid_merkle_proof`/`'in merkle'` usages should be gated behind an upgrade MCI similar to other consensus-affecting formula changes (e.g. `bPostPemCurvesFix`) [7](#0-6) .

### Proof of Concept
1. Build a public Merkle tree over elements `[e0, e1, ..., en]` using `merkle.getMerkleRoot`, where hashing has no leaf/node domain separation [8](#0-7) .
2. Pick any two adjacent leaf hashes `H(e_i)` and `H(e_{i+1})` (or any two sibling hashes at a higher level) and their sibling proof path from that point up to `root`.
3. Construct `forged_element = H(e_i) + H(e_{i+1})` (the literal concatenation string) and `forged_proof = { index: i/2, siblings: [<the siblings from that internal node upward>], root: root }`.
4. Call `is_valid_merkle_proof(forged_element, forged_proof)` in an AA trigger, or supply the equivalent serialized proof as an `'in merkle'` authentifier; `verifyMerkleProof` returns `true` even though `forged_element` was never one of the original tree elements [3](#0-2) , because `hash(forged_element) == hash(H(e_i) + H(e_{i+1}))`, exactly the internal node's precomputed value.

function hash(str){
	return crypto.createHash("sha256").update(str, "utf8").digest("base64");
}

function getMerkleRoot(arrElements){
	var arrHashes = arrElements.map(hash);
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
	}
	return arrHashes[0];
}

function deserializeMerkleProof(serialized_proof){

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
