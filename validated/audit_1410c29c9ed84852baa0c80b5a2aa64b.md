### Title
Unscoped SHA lookup in `StatusHandler#process` lets a status webhook from any repo mutate CI state on a victim's commit sharing that SHA - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `Commit.where(sha: params.sha)`, with no filter on the repository that the webhook payload claims to originate from. Any GitHub status webhook (valid `X-Hub-Signature` for *some* org/repo where the Shipit GitHub App is installed) that references a SHA also present in a victim stack's `commits` table will write a `Status` for the victim commit, regardless of which repository actually owns that SHA.

### Finding Description
The broken binding: the code implicitly assumes `commit.sha == params.sha ⇒ commit.stack.repository == payload.repository`, but the code never checks `commit.github_repo_name == params.dig('repository','full_name')` (or any repo attribute at all).

Path:
1. `Shipit::WebhooksController#create` dispatches the parsed JSON body to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks that the raw body/signature pair is valid for `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('repository','owner','login')`) — this authenticates "a request came from *some* GitHub App installation the operator trusts," not "this status belongs to repo X." [1](#0-0) 
2. `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
with no `github_repo_name`/stack scoping. [2](#0-1) 
3. `Commit#create_status_from_github!` writes the status directly onto whichever `Commit` record(s) matched, via `statuses.replicate_from_github!(stack_id, github_status)`, again with no repo check against the webhook payload. [3](#0-2) 
4. That status feeds `Commit#status`/`Commit#blocked?`/`Commit#deployable?`, which drive `schedule_continuous_delivery` and `stack.schedule_merges`, i.e., real ship/merge/block decisions. [4](#0-3) [5](#0-4) 

Attacker requirement: they must be able to produce a webhook that passes `verify_signature`. This only requires that the payload's `repository.owner.login` corresponds to *some* org/installation for which the operator's Shipit instance has configured a GitHub App (i.e., the attacker has write access to any single repo under that installation — a very low bar in orgs that install the app organization-wide, or in their own account if they self-host/self-install). GitHub's Statuses API lets any collaborator with write access to a repo set a status for an arbitrary SHA string on that repo, including SHAs that did not originate there. Nothing in `verify_signature`, `drop_unhandled_event`, or the `ExplicitParameters` schema in `StatusHandler` ties the asserted `sha`/`context`/`state` to the repository that authenticated the request — the schema only validates types/presence of `sha`, `state`, `context`, etc., not repo ownership. [6](#0-5) 

This matches the described exploit: with a victim stack configured `review_stacks_enabled: true, allow_all: true`, external-PR commits are auto-provisioned into review stacks that execute `shipit.yml`, so a forged/foreign `ci/coverage` status for a shared SHA can flip a review stack's commit from "blocked/pending" to "success," enabling an unauthorized deploy/merge, or force it into "failure" to block a legitimate deploy.

### Impact Explanation
A status event that only legitimately concerns Repo A ends up mutating CI/coverage state for a `Commit` record belonging to Repo B/Stack B whenever both share a SHA. Since commit success/failure state directly gates `deployable?`, `blocked?`, and `schedule_merges`, this is a cross-tenant write that can cause an unauthorized deploy or block — matching the "payload for one repository mutating another's stack/commit" Critical category. The blast radius is any Shipit instance hosting multiple stacks/repos under installations reachable by the attacker, and is repeatable per matching SHA/commit.

### Likelihood Explanation
Preconditions: attacker needs (a) write/status-setting access to at least one repository under a GitHub App installation trusted by the target Shipit instance, and (b) a SHA collision/sharing scenario between their controlled repo and the victim stack — most plausible when the victim uses `review_stacks_enabled: true, allow_all: true`, since review stacks are provisioned directly from externally-opened PR commits that live in the base repo the attacker is targeting, making the SHA trivially "shared" by design (the PR head commit is the exact commit the attacker pushed). This is a realistic, low-cost, and repeatable attack given the described configuration.

### Recommendation
Scope `StatusHandler#process` (and `Commit#create_status_from_github!`) to only update commits whose `stack.github_repo_name` (or `stack.repository.full_name`) matches `params.dig('repository', 'full_name')` from the webhook payload, rejecting/ignoring status updates for commits belonging to a different repository than the one that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` for repo `attacker/repo` and `stack_b` for repo `victim/repo`, both with a `Commit` sharing `sha: "deadbeef..."` (simulate shared SHA via review-stack provisioning from the same PR commit).
2. Configure `stack_b` with `review_stacks_enabled: true`, `allow_all: true`, and a deploy spec requiring status context `ci/coverage`.
3. Build a `StatusHandler` payload with `repository.full_name = "attacker/repo"`, `sha` = shared SHA, `context: "ci/coverage"`, `state: "success"`.
4. Call `StatusHandler.new(payload).process` (bypassing signature verification as in existing handler tests).
5. Assert equality/inequality:
   - Before: `commit_b.status.success?` is false (or unknown/pending).
   - After: assert `commit_b.status.success?` is **true**, even though the payload's `repository.full_name` (`attacker/repo`) `!=` `stack_b.repository.full_name` (`victim/repo`) — proving the write crossed repository boundaries.
   - Additionally assert `stack_b.commits.find(commit_b.id).deployable?` flips accordingly, demonstrating downstream ship/block impact.
