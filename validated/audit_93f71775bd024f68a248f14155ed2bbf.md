## Analog Identified

### Title
Shared oracle `last-update` timestamp can be advanced by any user, causing a legitimate liquidation of an unrelated borrower to revert - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` caches the "last seen" oracle publish-time per price feed in a **shared** map keyed only by `{type, ident}` (the oracle identifier), not by the calling account or position. Any unprivileged user who submits a fresh Pyth/DIA price update through any market entry point (deposit, borrow, repay, `liquidate`, etc. all call `write-feeds`/`price-resolve`) advances this shared timestamp. Any subsequent transaction — from a completely different, unrelated caller — that supplies a valid, signed, non-stale price VAA whose `publish-time` is *older* than the just-recorded value will be rejected with `ERR-ORACLE-INVARIANT`, even though that VAA is fully valid and within `max-staleness`. This is structurally identical to the referenced Wormhole bug: a value considered valid at "check time" (T1) is invalidated by a change to shared external state caused by a different, unrelated actor before "check time" (T2), causing an otherwise-legitimate transaction to fail.

### Finding Description
`price-resolve` (mainnet/contracts/market/v0-4-market.clar:373-395) validates freshness with: [1](#0-0) 

```
(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  ...
  (and (<= delta max-staleness) (>= ts prev))))

(define-private (price-resolve ...)
  (let (...
        (last-update-time (oracle-last-update key))
        ...)
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)
    (if (> timestamp last-update-time) (map-set last-update key timestamp) false)
    (ok final-price)))
```

`key` is `{ type: type, ident: ident }` — the oracle price-feed identifier — with no per-caller or per-asset-id scoping beyond the shared feed identifier itself: [2](#0-1) 

Any user (borrower, depositor, liquidator, or an attacker with no protocol position at all) can call any market entry point that accepts `price-feeds` and passes a freshly-signed Pyth VAA with a later `publish-time` for a given identifier. That single call permanently ratchets `last-update` forward for that `{type, ident}` key for all future transactions, exactly like Wormhole's guardian-set index being advanced by governance between a proposal's queue and execute phases.

A liquidator attempting to liquidate an *unrelated* borrower whose position uses the same oracle identifier (all positions sharing an asset use the same feed) must submit a signed price update to satisfy freshness/mask preconditions. If, between the moment the liquidator obtained a valid Pyth VAA off-chain and the moment their `liquidate` transaction lands, any other unprivileged party's transaction (which could simply be an ordinary deposit/borrow with a slightly newer feed) has already advanced `last-update` for that identifier, the liquidator's otherwise-valid, non-stale VAA will fail `(>= ts prev)` and the whole `liquidate` call reverts with `ERR-ORACLE-INVARIANT`.

### Impact Explanation
This lets any unprivileged third party — even one with no relationship to the position being liquidated — grief or delay liquidation of an at-risk borrower simply by routinely interacting with the market using their own freshly-fetched price update. Because `liquidate` bundles `write-feeds` and the health/liquidation checks into a single atomic call, a liquidator has no way to "lock in" the price they intend to use; a race against any other market participant's normal activity can cause repeated liquidation attempts to fail. This directly matches the whitelisted analog class "a position made unevaluable by a third party": the borrower's unhealthy position cannot be liquidated because a stranger's unrelated transaction shifted the shared oracle-freshness watermark. Delayed liquidation of undercollateralized positions is a temporary freezing-of-funds risk to lenders/suppliers whose assets back that debt, since bad debt can continue to accrue while liquidation calls keep reverting.

### Likelihood Explanation
Likelihood is moderate: it requires two independent price-feed submissions for the same oracle identifier landing in an order where the "used-for-liquidation" VAA has an older `publish-time` than one already recorded on-chain by unrelated activity. Since Pyth VAAs are refreshed frequently and the market accepts feeds from *any* caller on *any* operation (deposit/borrow/repay/liquidate), normal organic traffic on a popular asset increases the chance that a liquidator's fetched (slightly stale relative to the newest) but still valid VAA is rejected. This is exacerbated on high-traffic assets and during high volatility (exactly when liquidations are most needed).

### Recommendation
Do not use a single global `{type, ident}`-scoped monotonic timestamp watermark to gate freshness for an operation whose correctness only depends on the *submitted* VAA's own signature and staleness relative to `stacks-block-time`. Either: (1) drop the `(>= ts prev)` requirement entirely and rely solely on `<= delta max-staleness` (each VAA is independently signed and verified, so accepting a slightly older-but-still-fresh valid VAA is safe), or (2) if replay/ordering protection is needed, scope it per-transaction (e.g., only reject VAAs older than the one *the current transaction itself* already applied) rather than persisting a cross-transaction global watermark that unrelated callers can advance.

### Proof of Concept
1. Asset `X` uses oracle identifier `ident-X`. Borrower B has a position collateralized in an asset priced via `ident-X` that is undercollateralized (LTV ≥ `LTV-LIQ-PARTIAL`).
2. Liquidator L fetches a valid, signed Pyth VAA for `ident-X` with `publish-time = t1` (fresh, within `max-staleness`).
3. Before L's `liquidate` transaction is confirmed, an unrelated user U (doing an ordinary deposit or repay on asset `X`, or any asset priced by `ident-X`) submits a `price-feeds` update with `publish-time = t2 > t1` through their own transaction, calling `write-feeds -> price-resolve`, which executes `(map-set last-update key t2)` at mainnet/contracts/market/v0-4-market.clar:391-393.
4. L's `liquidate(borrower=B, ..., price-feeds=(some (list VAA_t1)))` now calls `price-resolve` with `timestamp = t1`, `last-update-time = t2`; `(>= ts prev)` is `(>= t1 t2)` = false, so `oracle-timestamp-fresh` returns false and the whole call fails with `ERR-ORACLE-INVARIANT` at mainnet/contracts/market/v0-4-market.clar:387-388, despite VAA_t1 being fully valid and fresh.
5. B's unhealthy position remains unliquidated for at least one more round-trip (fetch a newer VAA, resubmit), during which time price movement or continued interest accrual can worsen the shortfall, and any other unrelated party can repeat step 3 to keep re-griefing the liquidation attempt.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
