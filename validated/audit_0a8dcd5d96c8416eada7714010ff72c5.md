### Title
Unallowlisted route hop pool can execute arbitrary code beneath the caller's signed auth tree and drain the signer's wallet - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
The swap-aggregator dispatches every route hop to whatever `pool` address the caller-supplied `StrategyPayload` names, with no venue/pool allowlist. A malicious "pool" contract reached via `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, or a direct `execute_strategy` call can invoke `token::transfer(victim, attacker, ...)` while on the call stack. In Soroban, that transfer is recorded as a sub-invocation of the victim's own authorization entry, so a victim who signs the simulated auth tree authorizes the theft of any token in their wallet — far beyond the routed amount. This is the on-chain analog of SSRF: user-controlled destination addresses cause the protocol to invoke attacker-chosen code paths that abuse the requester's authority.

### Finding Description
`execute_op` builds each `SwapHop` from raw indices into the caller-controlled `assets` registry and calls `venues::dispatch_hop`, which invokes the venue adapter against `hop.pool` — an arbitrary, unvalidated contract address supplied in the route XDR. [1](#0-0)  No allowlist of pool or token addresses exists; the only checks are measured input/output balance deltas. [2](#0-1)  The controller side grants the router one exact input-transfer auth and then calls `router.execute_strategy` under a flash guard — but the guard only prevents reentry into the controller; it does not constrain what the named pool contract does on the stack. [3](#0-2) 

Because routes are opaque XDR blobs produced off-chain, a malicious quote/route can name an attacker-deployed pool. That pool, once invoked, can call `token.transfer(victim, attacker, amount)` on any token. Soroban records this as a child of the victim's `swap_collateral`/`execute_strategy` auth entry; if the victim signs the simulated tree (the normal flow), the transfer executes. The test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates exactly this: a `RogueHopPool` whose `swap()` transfers Alice's entire unrelated wallet token to the attacker, with the stolen transfer recorded as a sub-invocation of Alice's `swap_collateral` authorization. [4](#0-3) [5](#0-4)  The threat-model doc acknowledges the router "keeps no allowlist" and that "a route can put third-party code on the call stack below the caller's authorization." [6](#0-5) 

### Impact Explanation
Theft of user funds bounded only by the victim's total wallet holdings across all tokens — not by the routed amount, the payload `min_out`, or the final health-factor gate. A single signed `swap_collateral` or `execute_strategy` transaction can drain every token the victim owns (any SAC token, LP shares, NFTs-adjacent balances), while still completing the swap "successfully" and passing `NoSwapOutput`/`RouterOverspend` checks.

### Likelihood Explanation
Reachable by any unprivileged address: the attacker deploys a contract exposing a `swap` (or venue-matching) entrypoint that steals via `token::transfer`, then delivers a route referencing it — e.g., via phishing a malicious `routeXdr`, a compromised/malicious quote source, or social engineering. The attack requires the victim to sign the poisoned auth tree; since routes are opaque XDR and wallets/clients render only the top-level call, signing a tree with an extra child transfer is realistic. No privileged role, no oracle manipulation, and no timing dependency is needed.

### Recommendation
Whitelist hop `pool` (and ideally `token_in`/`token_out`) addresses in the router against a governance-managed venue registry before dispatch, or restrict `assets` entries to previously registered pools per venue opcode. Reject routes whose pool addresses are not registered for the declared venue. Complement on-chain enforcement by keeping `min_out`/slippage semantics unchanged — the fix must be at destination validation, since balance-delta measurement cannot detect an auth-tree rider that pays fair output while stealing unrelated tokens.

### Proof of Concept
1. Attacker deploys `RogueHopPool` configured with `(victim=Alice, wallet_token, attacker, amount)` (test lines 51-72).
2. Attacker builds a `StrategyPayload` whose `assets` registry lists the rogue pool as the hop `pool` for a normal-looking USDC→ETH swap.
3. Alice calls `controller.swap_collateral(alice, account_id, usdc_key, SWAP_IN_USDC, eth_key, route)`. The controller authorizes only its own input transfer and calls `router.execute_strategy`.
4. The router invokes `RogueHopPool::swap`, which executes `token::transfer(alice, attacker, WALLET_BALANCE)`; the host attaches this to Alice's signed auth entry and it succeeds.
5. The router returns fair ETH output; `verify_router_output` and final risk gates pass. Alice's unrelated wallet token is fully drained (test asserts `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`). [7](#0-6)

pub(crate) fn dispatch_hop(
    env: &Env,
    router: &Address,
    hop: &SwapHop,
    amount_in: i128,
    tokens_cache: &mut Map<Address, Vec<Address>>,
) -> i128 {
    let ctx = HopContext::new(env, router, hop, amount_in);
    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)
        .unwrap_or_else(|| panic_with_error!(env, Error::ZeroOutput));
    if received <= 0 {
        panic_with_error!(env, Error::ZeroOutput);
    }

    let after_in = ctx.input_balance();
    let spent = before_in
        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);
    }

    received

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
