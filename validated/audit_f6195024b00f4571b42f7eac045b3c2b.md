## Title
Race condition in concurrent private-payment chain validation/save allows double-acceptance of the same private asset output - (File: `private_payment.js`)

### Summary
The CVE describes a generic local race condition in vsomeip (unsynchronized concurrent access to shared state). The closest reachable analog in ocore is in the private-payment (indivisible/divisible private asset) save path: `network.js`'s `handleSavedPrivatePayments` intentionally processes multiple pending private-payment chains **in parallel** (`async.each`), and each chain is validated and saved through `private_payment.js`'s `validateAndSavePrivatePaymentChain`, which opens its **own independent DB connection and transaction** with **no mutex** serializing concurrent invocations for the same asset/output — unlike the public-unit path in `validation.js`, which always serializes per-author-address writes via `mutex.lock(arrAuthorAddresses, ...)` and per-write via `mutex.lock(["write"])`.

### Finding Description
`network.js` explicitly documents that multiple private-payment chains are handled concurrently: [1](#0-0) 
```
			var assocNewUnits = {};
			async.each( // handle different chains in parallel
				rows,
```

For each row, `privatePayment.validateAndSavePrivatePaymentChain` is invoked: [2](#0-1) 

Crucially, this function acquires its own connection and its own SQL transaction per call — there is no cross-call mutex (like the `"handleJoint"`/`"write"`/`arrAuthorAddresses"` locks used for public units, or the `"private_write"` mutex used elsewhere in `validation.js` for double-spend bookkeeping): [3](#0-2) 

The duplicate/spend check is a plain `SELECT` inside this transaction, followed later by `INSERT`/`UPDATE` statements executed in a second, independent function (`indivisible_asset.js`/`divisible_asset.js` `validateAndSavePrivatePaymentChain`), all still without any application-level lock coordinating the two concurrently running chains: [4](#0-3) 

Notably, the code comment itself acknowledges that unstable private elements are deliberately **not** protected by a real uniqueness guarantee: [5](#0-4) 
```
				var is_unique = objPrivateElement.bStable ? 1 : null; // unstable still have chances to become nonserial therefore nonunique
```
Since `is_unique` is set to `NULL` for unstable private elements, the `UNIQUE(src_unit, src_message_index, src_output_index, is_unique)` DB constraint referenced in the schema does not prevent duplicate inputs when `is_unique IS NULL` (NULL values do not conflict with each other in SQL unique indexes): [6](#0-5) 

Compare this to the public-unit spend-conflict handling in `validation.js`, which does use a dedicated mutex (`"private_write"`) specifically to serialize concurrent writes that touch private-asset input uniqueness: [7](#0-6) 

That mutex is never used or referenced by `private_payment.js`'s own save path, meaning the two code paths that mutate private-asset `inputs`/`outputs` uniqueness state (public-unit validation vs. private-chain saving) are not mutually synchronized, and the private-chain-to-private-chain path itself has no synchronization at all when multiple chains are processed by `async.each` concurrently.

### Impact Explanation
A malicious private-payment counterparty (a peer who legitimately learns/receives private chain elements, e.g., a payee or cosigner on a shared address) can submit two or more concurrently-processable private chains derived from the same still-unstable private output (transfer or divisible-asset spend) to a victim node/hub. Because `handleSavedPrivatePayments` fans these out via `async.each` with each chain running its own DB transaction and no shared lock, and because unstable elements use `is_unique = NULL` (a non-enforcing uniqueness value), both chains can pass their independent "is duplicate/is spent" checks before either commits. This can let the same private output be recorded as spent to two different destinations, i.e., a private double-spend that the victim's own node accepts as valid — an unauthorized-spending / double-spend outcome that directly matches the "Accept only concrete unauthorized spending, double-spend of a stable output..." validation bar (here specifically targeting the unstable/private window that the code comment explicitly calls out as unprotected).

### Likelihood Explanation
Medium. It requires: (1) private-payment/private-asset usage (already a first-class ocore feature reachable by any private-payment counterparty), (2) the private output being spent while still unstable (a normal, common condition — the code explicitly anticipates and tolerates this window), and (3) the ability to get two conflicting private chains queued for processing at roughly the same time (trivially achievable by sending both chains to the victim node close together, since `handleSavedPrivatePayments` runs on a timer/`async.each` and does not serialize by asset or output). No cryptographic breaks or privileged access are needed — only sending crafted/duplicate private-payment chains, which is within a private-payment counterparty's normal capabilities.

### Recommendation
Serialize private-chain validate-and-save operations that reference the same asset (or more precisely, the same source output / spend-proof) using a mutex (e.g., an `asset`-scoped or `spend_proof`-scoped key similar to the existing `"private_write"` mutex in `validation.js`), instead of relying solely on `is_unique` DB uniqueness, which is deliberately NULL for unstable elements. Alternatively, hold a mutex keyed by `(src_unit, src_message_index, src_output_index)` (or by `asset`) across the SELECT-then-INSERT/UPDATE sequence in `private_payment.js`'s `validateAndSavePrivatePaymentChain` and in `indivisible_asset.js`/`divisible_asset.js`'s save functions, and ensure this same key space is shared with `validation.js`'s `"private_write"` mutex usage so that public-unit and private-chain paths cannot race each other either.

### Proof of Concept
1. Issue (or acquire) a private, unstable indivisible-asset output `O` at `(unit=U, message_index=M, output_index=I)`.
2. Build two distinct private-payment chains, `ChainA` and `ChainB`, both consuming `O` as their sole input but sending to two different addresses (double-spend attempt), each internally consistent (valid spend proofs, hashes, etc. for their own claimed sub-chain).
3. Send `ChainA` to the victim node/hub via the `private_payments` device-message handler (`wallet.js` → `handlePrivatePaymentChains` → queued into `unhandled_private_payments`), and send `ChainB` immediately after, before the periodic `handleSavedPrivatePayments` interval (`setInterval(handleSavedPrivatePayments, 5*1000)` in `network.js`) processes either.
4. When the interval fires, both rows are picked up together and processed via `async.each(rows, ..., cb)` — `ChainA` and `ChainB` run their independent `validateAndSavePrivatePaymentChain` calls (separate connections/transactions) concurrently.
5. Because `O` is unstable, `is_unique` for its consuming input is set to `NULL` for both chains (`indivisible_asset.js:251`), so the DB `UNIQUE` constraint does not reject the second insert, and neither transaction's duplicate-check `SELECT` (`private_payment.js:70-107`) observes the other's uncommitted write; both chains can be accepted by the victim as `ifOk`, spending `O` twice.
