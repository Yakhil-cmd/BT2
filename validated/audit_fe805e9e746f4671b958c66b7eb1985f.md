### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets a status webhook from one repository overwrite CI status on commits belonging to a different stack/repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha`, with no filter on the repository that authenticated the webhook, then calls `create_status_from_github!` on every match. Since git commit SHAs are content-addressed and identical across forks/mirrors that share history, an attacker who owns a repository sharing a commit with a victim's tracked repository can send a validly-signed `status` webhook from their own repo and have Shipit write a `Status` row onto the victim's `Commit` record, altering that commit's `deployable?`/merge eligibility if the spoofed `context` (e.g. `ci/circleci`) is in the victim stack's required contexts.

### Finding Description
The broken binding: the code should enforce `commit.stack.repository.full_name == payload['repository']['full_name']` before writing a status, but it does not — the binding actually enforced is only `commit.sha == params.sha`, which is a strictly weaker equality.

Code path:
- `Shipit::WebhooksController#create` dispatches the raw JSON payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` after `verify_signature`, which validates the HMAC signature using the app configured for `repository_owner = params.dig('repository','owner','login')` — a value taken directly from the attacker-supplied payload (`app/controllers/shipit/webhooks_controller.rb:24-49,59-62`). This only proves the request was signed by *some* GitHub App installation matching the org named in the payload — it says nothing about which stack/commit the event is entitled to affect.
- `Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) specifically meant to scope handler effects to the repository that sent the webhook (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), but `StatusHandler` never uses it.
- `StatusHandler#process` instead does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This queries the entire `commits` table by `sha` alone — no `stack_id`, `repository_id`, or repository-name check is applied anywhere in the handler or in `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`), which just calls `statuses.replicate_from_github!(stack_id, github_status)` using the *matched commit's own* `stack_id`, not anything derived from the webhook's repository.

Exploit flow: an attacker owns/forks a repository that shares commit history (hence identical SHAs) with a repository the victim stack tracks — e.g., a public open-source repo mirrored/forked into both an attacker-controlled GitHub account and a victim's Shipit-tracked stack. The attacker installs/uses a GitHub App webhook on their own repo (a normal, unprivileged action) and sends (or lets GitHub send) a `status` event with `sha` set to a commit SHA that is also present in the victim's Shipit `commits` table, `context: ci/circleci`, `state: failure`. `verify_signature` passes because it is validated against the attacker's own org/app, not against the victim's repository. `StatusHandler#process` then finds the victim's `Commit` row (matched purely by `sha`) and writes the spoofed failing status to it via `add_status`, which recomputes `Status::Group`, potentially flipping `deployable?` (`app/models/shipit/commit.rb:227-229`) and gating/unblocking merges (`schedule_merges`) for a repository the attacker never authenticated against.

Existing guards do not prevent this: `verify_signature` authenticates the sender's identity/org, not the target commit's ownership; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape; `Handler#stacks` exists to enforce the missing scoping but is unused by this handler.

### Impact Explanation
A crafted webhook, correctly signed for the attacker's own repository, mutates `Status`/`Commit`/`Stack` state belonging to an unrelated repository whose maintainers never authorized the event — this is exactly the "payload for one repository mutating another's stack, commit, task" Critical category. Concretely, it can flip a victim commit's required CI context to `failure`, blocking deploys/merges (denial), or — the more damaging direction — an attacker could instead post `state: success` for a required context that the victim's real CI never reported, making a commit falsely `deployable?` and enabling an unauthorized deploy/merge. This is repeatable against any commit SHA that is shared between an attacker-controlled repo and a victim's tracked stack, and requires no privileges beyond owning/forking a repository and being able to fire a `status` webhook, which is standard GitHub App/webhook behavior for repository owners.

### Likelihood Explanation
Preconditions: (1) the victim stack must already have a `Commit` record for the shared SHA (i.e., Shipit previously synced that commit for the victim's repo/stack), and (2) the attacker needs a repository that shares at least one commit SHA with the victim's tracked history — trivially satisfied by forking a public upstream repo that both the attacker and the victim's Shipit stack track, or by mirrored/vendored histories, which are common. Attacker cost is minimal: fork a public repo, install a webhook/App on the fork, and send a `status` event with the shared SHA and desired `context`/`state`. No Shipit credentials, sessions, or GitHub secrets for the victim's org are required. This is fully repeatable against any commit SHA the attacker can reproduce in their own repository.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring the `stacks` helper already provided by `Handler`. For example, only update commits belonging to stacks resolved from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status event can only affect commits under the repository that actually sent (and was cryptographically verified for) that webhook.

### Proof of Concept
Minitest plan (no live GitHub, using existing test helpers such as `shipit_stack`/`shipit_commit` factories and `Shipit::Webhooks::Handlers::StatusHandler`):
1. Create `victim_stack` with `ci.require` including `ci/circleci`, and a `victim_commit` under `victim_stack` with a known `sha` (e.g. `"deadbeef" * 5`) and no existing statuses — assert `victim_commit.deployable?` returns `true` (baseline, e.g. after seeding a passing status or `stack.ignore_ci?` set true for simplicity).
2. Create `attacker_stack`/`attacker_repository` with a *different* `full_name`, and an `attacker_commit` (or no commit needed) — the key is only the payload's `repository.full_name` differs from `victim_stack.repository.full_name`.
3. Build a payload: `{ "sha" => victim_commit.sha, "state" => "failure", "context" => "ci/circleci", "repository" => { "full_name" => attacker_repository.full_name, "owner" => { "login" => "attacker" } } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature verification, since the finding is about the handler's missing repository scoping, not signature verification).
5. Assert the equality that should have held but didn't:
   - Before: `victim_commit.reload.statuses.count == 0` and `victim_commit.deployable? == true`.
   - After: `victim_commit.reload.statuses.count == 1` and `victim_commit.status.context('ci/circleci').failure?` and `victim_commit.deployable? == false`, despite the payload's `repository.full_name` never matching `victim_stack`'s repository — proving cross-repository mutation.
