### Title
Commit status webhook forges statuses on any repository regardless of the authenticating organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate a webhook against using `repository_owner`, which is read straight from the untrusted payload (`repository.owner.login`, falling back to `organization.login`). [1](#0-0) [2](#0-1)  Once the signature is accepted, the full payload is dispatched to event handlers, and `StatusHandler` looks up commits **globally by SHA with no repository/stack scoping at all**, then writes a GitHub-style status onto whatever commit matches, in whatever stack it happens to belong to. [3](#0-2)  This breaks the binding "organization that authenticated versus the repository that is written": the HMAC only proves the payload came from *an* organization configured in Shipit, not that the acted-upon commit belongs to a repository owned by that organization.

### Finding Description
- The signature verification in `WebhooksController#verify_signature` derives the signing organization purely from attacker-controlled JSON fields (`repository.owner.login` / `organization.login`), and calls `Shipit.github(organization: repository_owner)` to fetch the matching `webhook_secret` for HMAC validation. [1](#0-0) 
- This design is intentional for Shipit's multi-organization mode (`lib/shipit.rb#github_app_config`), where distinct orgs each have their own app/secret configured under `secrets.github`. [4](#0-3)  Any organization admin who has legitimately onboarded their own org to this Shipit instance therefore knows/controls a valid `webhook_secret` and can freely craft arbitrarily-shaped, correctly-signed `status` event payloads.
- Once past signature verification, `Handler#process` is invoked with the whole JSON body. [5](#0-4)  Most handlers (e.g. `PushHandler`) correctly scope to `stacks`, which is derived from `Repository.from_github_repo_name(repository_name)` (the payload's `repository.full_name`). [6](#0-5) [7](#0-6) 
- `StatusHandler`, however, never consults `repository_name`/`stacks` at all. It does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a completely global lookup across every stack/repository tracked by the Shipit instance. [3](#0-2) 
- Consequently, the "organization" whose secret authenticated the webhook has no enforced relationship to the "repository" whose commit gets a status written. Any org admin onboarded to a shared Shipit instance can sign a `status` payload with their own webhook secret but supply an arbitrary `sha` (commit SHAs are public data, trivially discoverable via any victim repo's commit history/PRs/CI) belonging to a commit tracked under a different organization's stack, and inject a fabricated status (`state`, `context`, `target_url`, `description`).

### Impact Explanation
Commit statuses drive Shipit's deploy-safety mechanics: the CHANGELOG documents "blocking statuses" that "prevent deploy even if they were reported on any of the commits in the deploy range," and `DeploySpec`/`Status::Group` model required/blocking status contexts used to gate whether a commit is deployable. [8](#0-7)  By forging a passing status for a required CI context on a commit belonging to a stack outside the attacker's own organization, an attacker who only controls their own onboarded org's Shipit webhook credentials can flip a victim commit's deployability, potentially enabling an unauthorized deploy of code that never actually passed CI in the victim's real GitHub org. This satisfies the "unauthorized deploy" High/Critical impact bar, achieved purely through a repository/organization confusion in the webhook trust boundary — no `ApiClient` token, GitHub App key, or victim credential is required.

### Likelihood Explanation
High. Multi-organization Shipit configuration is an explicitly documented, supported deployment mode. [9](#0-8)  Any organization legitimately configured on a shared instance automatically possesses everything needed (their own `webhook_secret`) to exploit this — no additional privilege escalation, secret theft, or social engineering is required. The only "unknown" is discovering a valid target commit SHA, which is public information for any repository whose commits/PRs are visible (and for private repos, is still frequently exposed via commit links, CI logs, etc., outside Shipit's control).

### Recommendation
`StatusHandler#process` (and any other handler that doesn't scope through `Repository.from_github_repo_name`) must restrict its `Commit` lookup to commits belonging to stacks under the repository identified in the payload (i.e., use `stacks.joins(...).where(sha: params.sha)` analogous to `PushHandler`), so that the repository whose commit is mutated is always constrained to the same organization that authenticated the webhook signature.

### Proof of Concept
1. Attacker legitimately configures their own GitHub organization `attacker-org` on a shared multi-tenant Shipit instance, obtaining a real `webhook_secret` for it (per `docs/setup.md`'s "Using Multiple Github Applications" support). [9](#0-8) 
2. Attacker discovers a commit SHA `S` belonging to a commit tracked in `victim-org/victim-repo`'s Shipit stack (e.g., visible from the victim's public commit history or CI output).
3. Attacker crafts a `status` event payload: `{"sha": "S", "state": "success", "context": "required-ci-check", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/attacker-repo"}}` and signs it with HMAC-SHA1 using `attacker-org`'s own `webhook_secret`.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` (matching `repository.owner.login`) and successfully verifies the signature, since it was legitimately signed with that org's own secret. [1](#0-0) 
5. `StatusHandler#process` executes `Commit.where(sha: "S")`, finds the victim's commit (unrelated to `attacker-org`), and calls `create_status_from_github!`, writing a forged "success" status onto it — with no check that `S` belongs to any stack owned by `attacker-org`. [3](#0-2) 
6. If `required-ci-check` is a blocking/required status context for `victim-org/victim-repo`'s stack, the victim commit now appears deployable, enabling an unauthorized deploy that the victim's actual GitHub checks never approved.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
