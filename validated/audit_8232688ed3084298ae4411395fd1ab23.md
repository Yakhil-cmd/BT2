### Title
Unbounded linear-scan duplicate check on `arrInputKeys` causes O(n²) CPU blow-up during payment input validation - ([File: validation.js])

### Summary
`validatePaymentInputsAndOutputs` in `validation.js` deduplicates payment inputs by pushing a computed `input_key` string into a flat array `objValidationState.arrInputKeys` and checking membership with `Array.prototype.indexOf` before every push. This mirrors the `hickory-proto` bug class: a `Vec`/array is used as the "seen" set and is linearly rescanned for every new candidate, giving O(n²) behavior in the number of inputs. Because the array is shared across *all* messages of a unit (not reset per message) and inputs across multiple payment messages accumulate into it, an attacker who posts (or an AA that emits) a unit with many payment messages/inputs can force quadratic-time validation for every node that processes the unit. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
For every input in a payment message, the code builds a string key (e.g. `asset-denomination-address-serial_number` for issues, `asset-unit-message_index-output_index` for transfers, `type-address` for headers_commission/witnessing) and does:
```
if (objValidationState.arrInputKeys.indexOf(input_key) >= 0)
    return cb("input "+input_key+" already used");
objValidationState.arrInputKeys.push(input_key);
``` [1](#0-0) 

This same anti-pattern is repeated for `transfer` inputs [2](#0-1)  and for `headers_commission`/`witnessing` inputs [3](#0-2) , and also for spend proofs, which use the identical linear-scan-on-shared-array pattern:
```
if (objValidationState.arrInputKeys.indexOf(objSpendProof.spend_proof) >= 0)
    return callback("spend proof "+objSpendProof.spend_proof+" already used");
objValidationState.arrInputKeys.push(objSpendProof.spend_proof);
``` [4](#0-3) 

`arrInputKeys` is a single array attached to `objValidationState` and is not scoped per payment message — inputs and spend proofs from *every* message in the unit accumulate into the same array over the course of `validateMessages`, which iterates all messages of the unit in series. [5](#0-4)  Each new input added to a later message in the unit must be linearly scanned against the entire growing list of keys collected from all prior inputs/messages, so total work across a unit with `n` inputs spread over its messages is O(n²) string comparisons (each comparison itself proportional to string length), not O(n).

Unlike the hickory-proto case where the compression candidate list was unbounded, here per-message input/output counts are limited by `MAX_INPUTS_PER_PAYMENT_MESSAGE` / `MAX_OUTPUTS_PER_PAYMENT_MESSAGE` — but that limit is explicitly skipped for AA-generated messages: `if (payload.inputs.length > constants.MAX_INPUTS_PER_PAYMENT_MESSAGE && !objValidationState.bAA)` [6](#0-5) , meaning AA response units (bounded instead by `MAX_MESSAGES_PER_UNIT` and the AA complexity/op budget) can carry many more inputs than a normal unit, all funneled into the same shared, linearly-rescanned `arrInputKeys` array during validation of the resulting response unit.

### Impact Explanation
This is a CPU-exhaustion (algorithmic complexity) issue that affects every full node validating the unit (not just a single malicious node) — every node processing a wide/deep AA-response or many-message unit pays the same O(n²) cost during `validateMessages`/`validatePaymentInputsAndOutputs`. Because validation happens under `mutex.lock(arrAuthorAddresses, ...)` per author address [7](#0-6) , a sufficiently crafted unit can materially delay validation throughput and, in aggregate with repeated submissions, degrade a node's ability to keep up with confirming new units — consistent with the "network unable to confirm new units" impact bucket. It does not directly cause double-spend or fund loss; the correctness checks (duplicate detection) still function correctly, only the performance characteristic is degraded.

### Likelihood Explanation
Reachable by any unprivileged unit poster or AA trigger sender who can cause an AA to emit a unit with many payment messages/inputs (bypassing per-message `MAX_INPUTS_PER_PAYMENT_MESSAGE` for AA responses), or by any author who crafts a unit with many independent payment messages, each contributing inputs that get checked against the ever-growing shared `arrInputKeys` array. The complexity/op budgets in oscript (`MAX_COMPLEXITY`, `MAX_OPS`) bound the *AA formula evaluation* cost but do not bound the cost of the subsequent unit-level `validation.js` input/spend-proof deduplication scan described here, so this path is not otherwise rate-limited by AA gas accounting.

### Recommendation
Replace the linear `Array.indexOf` membership checks on `arrInputKeys` with an O(1) hash-set/object lookup (`Set` or a plain object keyed by `input_key`), analogous to fixing hickory-proto's compression candidate list with a hashmap. Apply the same fix to spend-proof dedup, which uses the identical array/`indexOf` pattern.

### Proof of Concept
Not independently verifiable without executing the validation code against a constructed unit; based on static analysis: construct a unit (or induce an AA to emit a response unit) containing many payment messages, each with the maximum allowed number of transfer inputs, up to the `MAX_MESSAGES_PER_UNIT` bound. As `validateMessages` iterates messages serially and each message's inputs are checked via `arrInputKeys.indexOf(...)` against all previously accumulated keys, the total number of string comparisons grows quadratically with the total input count across the unit's messages, elevating unit-validation CPU time superlinearly relative to unit size.
