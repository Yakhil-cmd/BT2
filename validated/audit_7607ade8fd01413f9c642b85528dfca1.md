### Title
Unvalidated route pool can execute attacker code under the swap caller’s authorization - (File: contracts/swap-aggregator/src/execute/mod.rs)

### Summary
A caller-supplied swap route can name any contract address as a venue pool. The router decodes the address registry without binding pool addresses to an allowlist or otherwise validating that they implement the expected DEX interface, then invokes the selected address through the venue adapter. Because the venue runs inside the caller-authorized `execute_strategy` or controller strategy invocation, malicious venue code can request additional token transfers from the caller that an honest simulation records in the same authorization tree.

### Finding Description
`execute_strategy` decodes caller-controlled `StrategyPayload` bytes, whose `assets` registry explicitly contains both token and pool addresses. `Program::decode` range-checks the pool index but performs no identity, provenance, executable, or interface validation for the referenced pool. During a swap op, `execute_op` copies `assets[idx_a]` directly into `SwapHop.pool` and passes it to `venues::dispatch_hop`. [1](#0-0) [2](#0-1) [3](#0-2) 

The venue adapters then invoke the caller-selected `pool` address. For example, the Soroswap adapter calls `get_reserves`, transfers input to `ctx.hop.pool`, and invokes `swap` on that same address; the Aquarius adapter authorizes a router-token transfer and invokes `swap` on the supplied pool; Phoenix and Sushi likewise invoke caller-selected pool addresses. [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

This affects both direct router calls and controller strategies. `execute_strategy(sender, total_in, swap_xdr)` requires `sender.require_auth()` and pulls `total_in` from that sender before executing the route. [8](#0-7)  The controller also accepts route bytes in `swap_collateral`, requires the account owner or delegate, and forwards the route to the configured router. [9](#0-8)  Its router helper authorizes one exact input transfer, but that only constrains the controller’s own authorization; it does not prevent venue code from requesting a separate token transfer from the account owner. [10](#0-9) 

### Impact Explanation
An attacker can deploy a malicious contract that exposes the expected venue methods, return a nominally successful swap result, and additionally invoke `token.transfer(victim, attacker, amount)` for an unrelated token held by the victim. If the victim submits or signs a simulated authorization tree that includes that injected child transfer, the token contract accepts it and the attacker receives funds unrelated to the swap.

This is theft of user wallet funds, not merely bad routing or slippage. The attack can steal assets that were never supplied to XOXNO Lending and were not among the route’s `token_in`/`token_out` values. The measured input/output checks and the router’s minimum-output check do not bound this loss because they only account for route tokens held by the router. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Exploitation requires the victim to sign the authorization tree containing the injected transfer. That is nevertheless plausible because routes and pools are opaque contract addresses, venue execution is intentionally dynamic, and the malicious venue can still return enough output for the route and controller risk checks to pass. The vulnerability does not require administrator access, leaked keys, a compromised oracle, or control of a legitimate DEX; an unprivileged attacker only needs to deploy the malicious pool and cause the victim to execute a route containing it. [13](#0-12) [14](#0-13) 

### Recommendation
Bind each pool address to a governance-approved venue/pool registry before dispatch, or derive venue calls only from protocol-known pool identities. At minimum, reject pool addresses that are not recorded as compatible with the selected venue before creating any user authorization or pulling route input.

If arbitrary pools remain supported, add an execution boundary that cannot inherit the end user’s authority for unrelated token calls. For controller strategies, the controller should ensure that the signed invocation cannot contain user-authorized child transfers beyond the expected token pull; clients should also hard-fail on any simulated authorization children other than the exact expected route input transfer. These mitigations should be enforced contract-side where possible rather than relying on every client to inspect authorization trees. [8](#0-7) [3](#0-2) 

### Proof of Concept
1. The attacker deploys a contract exposing the venue methods used by the selected opcode, such as `get_reserves` and `swap` for a Soroswap-shaped route. The contract is configured with the victim address, an unrelated victim-held token, the attacker’s payout address, and the amount to steal.
2. The attacker constructs `StrategyPayload` with the malicious contract address in the `assets` registry and a swap instruction whose `idx_a` selects that malicious pool. The route still uses real `token_in` and `token_out` addresses and a positive `min_out`. [15](#0-14) [16](#0-15) 
3. The victim invokes `swap_collateral(caller=victim, account_id, current, amount, new, swap)` or direct `execute_strategy(sender=victim, total_in, swap_xdr)`. The owner/delegate and sender authorization checks pass because the victim is operating on their own account or spending their own input. [9](#0-8) [17](#0-16) 
4. The router resolves `idx_a` into `SwapHop.pool` and calls the attacker’s venue code. The malicious `swap` calls `token.transfer(victim, attacker, amount)` for an unrelated wallet token, then returns a positive route output so `dispatch_hop`, `min_out`, and controller settlement checks can pass. [18](#0-17) [11](#0-10) 
5. If the victim signs the simulated authorization tree containing that injected token transfer, the transaction succeeds and the unrelated wallet funds are moved to the attacker. The vulnerability is caused by treating the route’s pool address as trusted executable code without validating its identity.
