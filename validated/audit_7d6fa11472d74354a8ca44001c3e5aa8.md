### Title
Cross-tenant webhook forgery via decoupling of signature-verification org from the acted-upon repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on the payload's `repository.owner.login` (or `organization.login`) field, while the downstream webhook handlers resolve and mutate a `Stack`/`Repository` based on a *different* payload field, `repository.full_name`. Nothing binds these two fields together, so in a multi-organization Shipit deployment an attacker who legitimately knows one tenant's `webhook_secret` can forge a signed webhook payload that gets verified against their own org's secret but is processed against a different tenant's repository.

### Finding Description
`verify_signature` picks the `GitHubApp` instance — and thus the HMAC key — purely from the JSON body: [1](#0-0) [2](#0-1) 

The signature is verified with `HMAC(webhook_secret_for(repository_owner), raw_post)`: [3](#0-2) 

But once the signature check passes, the same raw JSON `params` is dispatched to handlers, and the `Handler` base class picks the target `Repository`/`Stack` using a *different* field, `repository.full_name`, completely independent of `repository.owner.login`: [4](#0-3) [5](#0-4) 

For example, `PushHandler` finds and mutates matching stacks: [6](#0-5) 

The engine explicitly supports multiple independent GitHub Apps/organizations sharing one Shipit instance, each with its own `webhook_secret`: [7](#0-6) 

**Equality that should hold but doesn't:** `organization used to select/verify the HMAC secret` (`repository.owner.login`/`organization.login`) `== organization that actually owns the repository being written to` (`repository.full_name`'s owner segment, resolved via `Repository.from_github_repo_name`). The controller never checks this equality; it trusts the caller-supplied owner field for key selection and a separate caller-supplied field for the write target.

### Impact Explanation
In a multi-tenant install (as documented and configured via `secrets_double_github_app.yml`/`docs/setup.md`), an administrator of Org A's GitHub App knows Org A's `webhook_secret` (they configured it). That party can construct a JSON body where `repository.owner.login` (or `organization.login`) = `"OrgA"` but `repository.full_name` = `"OrgB/some-repo"`, sign the whole raw body with Org A's secret, and submit it to `/webhooks`. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` and accepts the signature, then the handler resolves and mutates `Repository`/`Stack` records belonging to Org B — a tenant whose secret the attacker never possessed. This is a cross-tenant write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization/target-resolution, i.e., "an organization that authenticated versus the repository that is written" as called out in the analog rules. Depending on which event/handler is abused (e.g., `push` queuing `GithubSyncJob`, which can lead into continuous-deployment/auto-deploy flows for that stack), this can escalate to unauthorized state changes/deploy triggers on a repository the caller does not control.

### Likelihood Explanation
Requires the attacker to already legitimately administer at least one GitHub org/app configured on the shared Shipit instance (a real but bounded precondition — this is not a fully unprivileged bypass, but no privileged Shipit session, `ApiClient` token, or `GITHUB_TOKEN` is required, only knowledge of one's own org's `webhook_secret`, which such an admin controls by design). Any Shipit deployment using the documented multi-org configuration is exposed.

### Recommendation
Require that the organization used to select/verify the webhook signature be the same organization that owns the repository referenced by `repository.full_name` (and any other repository/org fields consumed by handlers) before dispatching to handlers — i.e., derive `repository_owner` consistently from the same trusted field the handlers use, and reject the request if the owner segment of `repository.full_name` does not match the verifying organization.

### Proof of Concept
1. Deploy Shipit with `secrets_double_github_app.yml`-style config: `OrgOne` and `OrgTwo`, each with distinct `webhook_secret`.
2. As the legitimate admin of `OrgOne`, craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "full_name": "OrgTwo/victim-repo",
       "owner": {"login": "OrgOne"}
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner => "OrgOne"`, verifies successfully against `OrgOne`'s secret (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`).
6. `PushHandler#process` resolves stacks via `repository.full_name = "OrgTwo/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`), queuing `GithubSyncJob` against `OrgTwo`'s stack despite the request having been authenticated with `OrgOne`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
