### Title
Cross-tenant CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only validates that the request was signed with the webhook secret of the organization named in `params.dig('repository','owner','login')` [1](#0-0) [2](#0-1) . Once that signature check passes, `StatusHandler#process` looks up commits purely by SHA with no scoping to the signed-for repository/organization, so a valid signature from org A can be used to write a `Status` onto a commit belonging to any other stack/org B whose commit happens to share that SHA [3](#0-2) .

### Finding Description
The binding that should hold is: `signed_repository_owner (from params.repository.owner.login, verified in verify_signature) == owning_org(commit matched by params.sha in StatusHandler)`. Tracing the code shows this binding is never enforced:

- `verify_signature` derives `repository_owner` from the payload's `repository.owner.login` (or `organization.login`) and resolves a `GitHubApp` for that org via `Shipit.github(organization: repository_owner)`, verifying the HMAC signature with that org's `webhook_secret` [1](#0-0) . This only proves the attacker controls org A's secret.
- After that, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the entire raw payload to the handler [4](#0-3) .
- `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no join or filter on `stack.repository`/`repository_owner` at all [3](#0-2) . `Commit.sha` has no global uniqueness constraint tying it to a single stack in this code path.
- `create_status_from_github!` writes a real `Status` row and triggers downstream effects: `stack.schedule_merges` when the new status is pending/success, and `Hook.emit(:deployable_status, ...)`, which can affect continuous-delivery/merge scheduling for stack B [5](#0-4) .

Because `Commit.where(sha:)` is unscoped, any attacker who can get org A onboarded into Shipit (with a `webhook_secret` configured) can sign an arbitrary payload — including a `sha` that they read off GitHub for a public commit tracked by an unrelated stack B — and successfully write a status to B's commit despite B's org never having validated anything.

The one caveat that limits (but doesn't eliminate) exploitability: `Shipit.github(organization:)` must resolve to a *configured* org (raising `GithubOrganizationUnknown` otherwise, handled at lines 39-48 of the controller), and if that org's `webhook_secret` is blank, `verify_webhook_signature` degrades to `return true unless webhook_secret` [6](#0-5) . Either way, the attacker only needs to satisfy the check for **their own** org A, not for B — the actual write happens on B's row purely because the sha matched, which is the root cause described in the question.

### Impact Explanation
An attacker who controls (or is a member of) any org A already configured in this Shipit instance can forge CI status (`state`, `target_url`, `description`, `context`) on any commit in any other stack/org B, as long as they know a real commit SHA tracked by B (SHAs are public GitHub data, easily discoverable). This can mark an otherwise-failing or unreviewed commit as `success`, which per `Commit#deployable?` and `schedule_continuous_delivery` can unblock or trigger continuous deployment on B's stack [7](#0-6) [8](#0-7) . This is a payload for one repository mutating another repository's stack/commit — matching the "Critical" impact category defined in the rules (a payload for one repository mutating another's stack/commit, or unauthorized deploy).

### Likelihood Explanation
Preconditions: (1) attacker's org A must be a configured Shipit GitHub org with a resolvable `GitHubApp`/webhook secret (or one with no secret configured at all, in which case verification is trivially bypassed); (2) the target commit SHA must exist in some other stack B's `commits` table, which will be true for any commit Shipit has already synced for B, and SHAs are public. The attacker never needs B's secret, B's stack ID, or any Shipit session/API token — only the ability to POST to `/webhooks` with a body signed by their own org's secret. This is fully repeatable against any known commit SHA across any stack in the instance, making it a low-cost, repeatable cross-tenant attack once org A's onboarding precondition is met.

### Recommendation
Scope the `StatusHandler` (and analogous handlers like `CheckRunHandler`, if similarly structured) commit lookup to the repository that was actually signature-verified: join `Commit` through `Stack`/`Repository` and filter by the `repository_owner`/`repository.full_name` extracted from the verified payload, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_owner: repository_owner, repository_name: repository_name })`, ensuring the org that signed the webhook matches the org that owns the target stack before writing any `Status`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook signed by org A must not mutate commit belonging to org B's stack" do
  stack_b = shipit_stacks(:some_stack_owned_by_org_b) # repository_owner == "org-b"
  commit_b = stack_b.commits.create!(sha: "deadbeef" * 5, ...)

  # Attacker only owns/controls org A, and signs the payload with org A's webhook_secret.
  payload = {
    "sha" => commit_b.sha,
    "state" => "success",
    "repository" => { "owner" => { "login" => "org-a" } }
  }.to_json
  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", org_a_webhook_secret, payload)

  request.headers["X-Github-Event"] = "status"
  request.headers["X-Hub-Signature"] = signature

  assert_difference "commit_b.statuses.count", 1 do
    post :create, body: payload, as: :json
  end

  # Binding check: the org that verified the signature (org-a) does NOT match
  # the org that owns the mutated commit's stack (org-b) -- yet the write succeeded.
  refute_equal "org-a", stack_b.repository_owner
  assert_equal "success", commit_b.statuses.last.state
end
```
This demonstrates the divergence: signature verification succeeds for `org-a`, yet the `Status` row written belongs to `commit_b`'s stack owned by `org-b`, with no equality check ever performed between the two.
