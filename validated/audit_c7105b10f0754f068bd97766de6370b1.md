### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in webhook `status` handler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The GitHub webhook signature check authenticates *which organization/App installation* sent a payload, but the `status` event handler never re-checks that the commit being updated actually belongs to the repository that was authenticated. This lets anyone who controls (or can trigger a webhook for) any GitHub repository registered with a Shipit organization forge CI/status updates for commits belonging to a completely different, unrelated stack/repository, as long as the SHA values collide (trivially achievable via forks, which share git object history/SHAs with their upstream).

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature based on `repository_owner`, which is read straight from the JSON payload (`params.dig('repository', 'owner', 'login')` or `organization.login`): [1](#0-0) [2](#0-1) 

This only proves the payload was signed by *some* organization app installation that matches the claimed `repository_owner` — it does not scope any downstream action to that specific repository.

The `status` handler processes the event by looking up commits **purely by SHA, with no repository or stack scoping whatsoever**: [3](#0-2) 

Compare this to the base `Handler` class, which does provide a `stacks` helper that correctly scopes lookups to the repository named in the payload (`Repository.from_github_repo_name(repository_name)`), and which is used correctly by `PushHandler` and `CheckSuiteHandler`: [4](#0-3) [5](#0-4) [6](#0-5) 

`StatusHandler` is the one exception: it does not call `stacks` or filter by `payload['repository']`, so `Commit.where(sha: params.sha)` matches **every commit in the database with that SHA, across every stack/repository**, and calls `commit.create_status_from_github!(params)` on all of them.

Because forked repositories share git commit objects (and therefore SHAs) with their upstream, an attacker who owns or forks any repository registered under a Shipit-connected GitHub organization can:
1. Fork the victim's target repository (or otherwise obtain a commit with an identical SHA to one already tracked in the victim's stack).
2. Configure/trigger a `status` webhook event from their own repo (signed correctly by their org's legitimate webhook secret) with `sha` equal to the shared commit and `state: "success"`.
3. Shipit's `WebhooksController` verifies the signature against the attacker's own (valid) organization credentials — passing verification — then dispatches to `StatusHandler`, which updates the status of the commit in the **victim's** stack, since the SHA is looked up globally with no repository binding.

This directly breaks the binding: *the organization/repository whose signature was verified* ≠ *the repository/stack whose commit status is written*.

### Impact Explanation
Commit statuses gate whether a commit is `deployable?`: [7](#0-6) 

and blocking/required statuses influence deploy safety checks (`blocked?`, `stack.blocking_statuses`, `required_statuses`): [8](#0-7) 

A forged "success" status can flip a commit from non-deployable (pending/failing CI) to deployable, and can also trigger continuous-deployment scheduling: [9](#0-8) 

This is a cross-repository write that can be leveraged to bypass CI/status gating and cause an unauthorized deploy of a commit in a victim stack that the attacker does not control and was never authorized to write to — matching the Critical impact category ("cross-repository writes... or an unauthorized deploy").

### Likelihood Explanation
The attacker needs: (a) the ability to have a repository registered as a GitHub App installation target within the same Shipit-connected organization structure (or any org for which a valid, working webhook secret can produce a signature — e.g. by forking a public repo the attacker doesn't otherwise control but that shares an org's webhook config), and (b) a commit SHA collision with the victim stack, which is trivially satisfied by forking the victim repository (fork commits share SHAs with upstream by git design). No special privileges beyond controlling a repository/webhook delivery are required — this is an unprivileged, low-effort attack once repository forking is possible, which is the normal open/public-repo case GitHub webhooks are used for.

### Recommendation
Scope `StatusHandler#process` to the repository indicated in the payload, exactly as `PushHandler` and `CheckSuiteHandler` already do via the inherited `stacks` helper — e.g. restrict the query to `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack`/`Repository` derived from `payload['repository']['full_name']`, rather than a bare, repository-agnostic `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Register/observe a Shipit stack tracking `victim/repo`, with a commit `abc123...` present in its `commits` table (e.g. via normal sync).
2. Fork `victim/repo` to `attacker/repo` (or otherwise obtain a repo sharing commit `abc123...`), which is registered as a separate stack or simply has a valid GitHub App/webhook installation under an org Shipit trusts.
3. Send a webhook `status` event to `/github/webhooks` claiming `repository.full_name = "attacker/repo"`, `repository.owner.login = "<attacker's org>"`, `sha = "abc123..."`, `state = "success"`, signed with the attacker org's legitimate webhook secret.
4. `WebhooksController#verify_signature` succeeds (signature is valid for the attacker's own org).
5. `StatusHandler#process` executes `Commit.where(sha: "abc123...")`, matching the commit belonging to `victim/repo`'s stack, and calls `create_status_from_github!`, injecting a forged "success" status into the victim's stack — potentially satisfying `deployable?`/`blocked?` checks and enabling an unauthorized deploy of that commit.
