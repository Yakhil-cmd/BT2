### Title
Unvalidated peer-controlled public key passed to native secp256k1 ECDH binding causes memory-unsafe operation in device message decryption - (File: device.js)

### Summary
`device.js`'s `deriveSharedSecret()` converts an attacker-controlled base64 string directly into a Buffer and hands it to the native `secp256k1` module's `ecdh()` binding without any length or format validation, mirroring the CVE-2024-40724 pattern where untrusted, specially-crafted input reaches a native memory-manipulating routine (Assimp's parser) without adequate bounds checking before use, leading to heap corruption. [1](#0-0) 

### Finding Description
`deriveSharedSecret(peer_b64_pubkey, privKey)` builds `pubkey` directly from `peer_b64_pubkey` via `new Buffer(peer_b64_pubkey, 'base64')`, with no check that the decoded buffer is a valid compressed/uncompressed secp256k1 public key (33 or 65 bytes) before it's passed into `ecdsa.ecdh(pubkey, privKey, ...)`, which is the native `secp256k1` addon: [1](#0-0) 

```
function deriveSharedSecret(peer_b64_pubkey, privKey){
	var pubkey = new Buffer(peer_b64_pubkey, 'base64');
	var shared_secret_src = Buffer.from(ecdsa.ecdh(pubkey, privKey, {hashfn: (x, y) => x}, Buffer.alloc(32)));
	...
}
```

This function is reachable from `decryptPackage()`, which is invoked whenever a device processes any incoming encrypted message (paired-device messages, hub-relayed messages, private payment chains, AA-related correspondent messages, etc.). The caller only validates that `objEncryptedPackage.dh.sender_ephemeral_pubkey` is a `string` type — it never validates its decoded byte length or that it decodes to a valid EC point: [2](#0-1) [3](#0-2) 

Because `secp256k1`'s native/WASM binding expects a public key buffer of a specific fixed length (33 or 65 bytes) and internal format, feeding it an arbitrary-length or malformed buffer derived from attacker-supplied base64 is exactly the class of bug described in CVE-2024-40724: a specially crafted input reaching low-level buffer-consuming native code without prior validation, which can lead to out-of-bounds reads/writes in the native layer.

### Impact Explanation
An unprivileged paired device (or hub-relayed peer capable of forwarding an encrypted package addressed to a victim device) can trigger `decryptPackage` → `deriveSharedSecret` with a crafted `sender_ephemeral_pubkey` value of unexpected length/format. Depending on the exact native binding's internal handling, this can crash the receiving node's process (denial of service against a wallet/hub node) or, in the worst case matching the referenced CVE's class, corrupt heap memory in the native addon, which is far more severe than a mere validation failure and undermines availability and potentially integrity of the recipient's node.

### Likelihood Explanation
The path is reachable by any peer able to send a device message to the target device (a normal, unprivileged wallet operation — pairing and messaging is a standard peer capability, not hub/node operator-only), and the malformed field requires no cryptographic secret — only a crafted base64 string of the wrong length. No additional privilege or malicious-node/hub compromise is required beyond ordinary device-to-device messaging, which any two paired counterparties (including private-payment senders) use routinely.

### Recommendation
In `deriveSharedSecret()`, validate `peer_b64_pubkey` before use: confirm it decodes to exactly 33 or 65 bytes and passes `ecdsa.publicKeyVerify()` (the `secp256k1` module's own verification routine) prior to calling `ecdsa.ecdh(...)`. Reject and log/discard the encrypted package (as is already done for other malformed-field cases in `decryptPackage`) rather than passing unvalidated data into the native binding.

### Proof of Concept
1. Establish a normal device pairing with a victim node (standard operation for any wallet user).
2. Send the victim an encrypted package payload where `dh.sender_ephemeral_pubkey` is a base64 string decoding to a buffer of an invalid length (e.g., 5 bytes or 200 bytes) rather than a valid 33/65-byte secp256k1 public key.
3. The victim's `handleMessageFromHub`/pairing message handler invokes `decryptPackage`, which calls `deriveSharedSecret(objEncryptedPackage.dh.sender_ephemeral_pubkey, priv_key)`. [3](#0-2) 
4. `deriveSharedSecret` passes the malformed buffer straight into `ecdsa.ecdh(pubkey, privKey, ...)` without validation, reaching the native `secp256k1` binding with attacker-controlled buffer contents/length. [4](#0-3) 

*Caveat: I could not directly inspect the internal C/WASM implementation of the `secp256k1` npm dependency (it is a third-party native/WASM module, not part of this repo's indexed source), so I cannot confirm from this codebase alone whether the specific version in use crashes safely or is actually memory-unsafe for malformed inputs — this is the missing link needed to fully confirm exploitability of a heap overflow versus a caught exception. The validated, in-repo defect is definitively the missing input validation before the call.*
