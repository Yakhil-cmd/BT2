## Title
Asset definer can replace the `spender_attested` attestor list at any time, permanently freezing existing coin holders' funds - (File: `validation.js`)

### Summary
The reported Biconomy bug is a class of "owner freely rebinds a state pointer that existing user funds depend on, breaking withdrawal/spend for holders who committed funds under the old pointer." In ocore, the direct analog is the `asset_attestors` message: the definer of a `spender_attested` asset can replace the entire attestor list at will, at any time, with no requirement that previously-attested holders remain attestable. Any address that already holds coins of the asset but is not attested under the *new* list becomes permanently unable to spend, transfer, or send them anywhere, because both issuance/transfer validation and the composer's payment logic hard-require the payer (and every output address) to appear in the *current* attestor-derived list.

### Finding Description
`validateAttestorListUpdate` only checks that the asset requires attestation and that the author is the current definer — it performs no continuity check against the previously published attestor list: [1](#0-0) 

`checkAttestorList` only validates format (valid addresses, sorted, count limit) — it does not require any overlap with the prior list: [2](#0-1) 

When resolving attestation status for a payment, `storage.js` uses only the *most recent* `asset_attestors` unit as the source of truth for who counts as an attestor: [3](#0-2) 

and `filterAttestedAddresses` filters candidate addresses strictly against that current attestor set (`objAsset.arrAttestorAddresses`): [4](#0-3) 

This value feeds directly into unit validation. `validatePayment` rejects a payment outright if none of the authors are attested under the current list, for both issuance and ordinary transfers: [5](#0-4) 

For each spent input, the owning address must be present in `objAsset.arrAttestedAddresses` (again, computed from the *current* attestor list), otherwise the whole unit is rejected: [6](#0-5) 

And for divisible/non-transferrable-asset outputs, every output address must also pass the current attestation filter: [7](#0-6) 

The `asset_attestors` message itself is a normal, unrestricted content joint the definer can compose and post any time via `composeAssetAttestorsJoint`: [8](#0-7) 

and is persisted unconditionally by the writer whenever validation passes: [9](#0-8) 

So the flow mirrors the LP-token report exactly: users acquire coins of a `spender_attested` asset while attested by attestor set A; later the definer (acting exactly like the `LiquidityProviders` owner calling `setLpToken`) posts a new `asset_attestors` message with attestor set B that does not (and, because attestors are independent third parties, may never again) attest the same addresses. From that point on, every existing holder whose address is not attested under set B can no longer pass `arrAttestedAddresses` checks in `validatePayment`/`validatePaymentInputsAndOutputs`, so they cannot spend, transfer, or move their coins anywhere — their balance of that asset is permanently stuck.

### Impact Explanation
Any address holding a `spender_attested=true` asset can have its coins frozen unilaterally by the asset definer simply by publishing a new `asset_attestors` list that omits it (whether maliciously or through an innocent attestor-set rotation that forgets to re-attest existing holders). Because attestation is performed by external attestor addresses and not automatically carried over, there is no guarantee affected holders can ever regain attested status, unlike the Biconomy case where the owner could revert `lpToken` to the old value — here, previously issued attestations for the removed attestors are simply no longer counted by `filterAttestedAddresses`, and the funds remain locked in the DAG with no valid spend path. This is a concrete, unauthorized freezing of user funds reachable by a normal, permissionless action (an ordinary asset definer posting an `asset_attestors` unit).

### Likelihood Explanation
`asset_attestors` is a standard, first-class message type with no special governance, timelock, or continuity requirement, and is composed via the ordinary `composeAssetAttestorsJoint` API. Any asset definer — a role obtainable simply by issuing an asset with `spender_attested: true` — can trigger this at any time after users have begun holding/transacting the asset, with no cooperation needed from anyone else. The only actor needed is the asset issuer/definer, which is explicitly an in-scope reachable role.

### Recommendation
Require that an `asset_attestors` update either (a) is monotonic/additive (new list must be a superset of, or otherwise preserve attestation continuity for, previously attested addresses that hold nonzero balances), or (b) provide an explicit migration mechanism (e.g., a grace period during which both old and new attestor sets are honored, or an explicit `remove_attestor`/`add_attestor` diff API instead of a full-list replace) so that existing holders are not silently locked out. At minimum, document/warn definers and wallets that changing the attestor list can strand existing balances, similar to how the Biconomy mitigation recommended restricting free reassignment of the pointer that existing funds depend on.

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and initial `attestors: [X]` (via the `asset` message, validated by `validateAssetDefinition`, see `validation.js` ~2725-2827).
2. Attestor `X` attests address `U` (an `attestation` message). `U` receives/holds coins of asset `A` via a normal payment; `validatePayment`/`validatePaymentInputsAndOutputs` pass because `U` is in `arrAttestedAddresses` under attestor set `{X}`.
3. Definer `D` posts a new `asset_attestors` message for asset `A` with `attestors: [Y]` (a completely different attestor). `validateAttestorListUpdate` (`validation.js:2829-2848`) only checks `D` is still the definer and the list is well-formed — it accepts this unconditionally.
4. `storage.readAsset`/`addAttestorsIfNecessary` (`storage.js:1917-1946`) now resolves `objAsset.arrAttestorAddresses = [Y]` as the current attestor set for asset `A`.
5. `U` tries to spend/transfer its existing coins of `A`. `filterAttestedAddresses` (`storage.js:1959-1974`) checks attestations only from attestor `Y`; since `Y` never attested `U`, `U` is filtered out, so `arrAttestedAddresses` no longer contains `U`.
6. `validatePayment` (`validation.js:2115-2122`) and `validatePaymentInputsAndOutputs` (`validation.js:2504-2507`) reject any unit spending `U`'s coins with "owner address is not attested" / "none of the authors is attested" — `U`'s balance of asset `A` is now permanently unspendable unless attestor `Y` (who has no obligation or relationship with `U`) chooses to attest `U`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
