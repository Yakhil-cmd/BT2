### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by SHA alone, with no constraint on the repository that sent the webhook, then calls `Commit#create_status_from_github!` on every matching row across all stacks. Since `Shipit::Commit#add_status` subsequently calls `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)` using that commit's own `stack`, an attacker who controls a repository whose commit happens to share a SHA with a commit tracked by a victim's stack can inject state/description/target_url content that gets attributed to, and triggers hooks/automation on, the victim's stack.

### Finding Description
The broken binding is:
`commit.stack == repository_that_authenticated(payload)`

which the code assumes but never enforces. Trace:

- `app/models/shipit/webhooks/handlers/status_handler.rb` lines 20-24:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This query is global across the `commits` table — it is not scoped by `stack_id`, `repository`, or any identifier tied to the webhook's source repository. `params` only validates shape (`sha`, `state`, `description`, `target_url`, `context`, `created_at`), not provenance beyond whatever repository signed the webhook. [1](#0-0) 

- `Commit#create_status_from_github!` calls `add_status`, which computes `payload = { commit: self, stack:, status: new_status.state }` using `self.stack` — the stack of *whichever commit row matched the SHA* — and emits `Hook.emit(:commit_status, stack, ...)` / `Hook.emit(:deployable_status, stack, ...)`. [2](#0-1) [3](#0-2) 

Root cause: SHA is treated as a globally unique, trustworthy join key across tenants/repos, but git SHAs are only unique within a repository's object graph; identical SHAs can legitimately or adversarially occur across independent repositories (e.g., well-known empty-tree/empty-commit SHAs, cherry-picked/rebased history reproduced bit-for-bit, or a crafted collision). Any webhook whose payload's `sha` field matches a commit SHA already recorded against a victim's stack (that stack fetched the commit at some point, e.g. via push/PR sync) will cause that victim stack's commit row to be updated with attacker-supplied `state`/`description`/`target_url`, and `Hook.emit` fires with the victim's `stack` object as the payload target.

Existing guards do not close this: webhook signature verification (if configured) only proves the request came from *some* registered repository with a valid secret — it says nothing about which commits that repository is allowed to update, because the handler never checks `commit.stack.repository == the repository identified by the incoming webhook`. The `ExplicitParameters` schema in `StatusHandler` only validates types, not ownership.

### Impact Explanation
An attacker who registers/owns any repository tracked by the same Shipit instance can send a `status` webhook naming a SHA that also exists on a victim's stack, causing:
- A `Shipit::Status` (or replicated status) to be written against the victim's `Commit`, with attacker-controlled `description`/`target_url`.
- `Hook.emit(:commit_status, victim_stack, ...)` and `Hook.emit(:deployable_status, victim_stack, ...)` to fire, driving any configured outbound integration (chat/CI notifiers, continuous-delivery triggers via `stack.schedule_merges`, `ContinuousDeliveryJob`) using the victim's stack and commit as the "authenticated" record — while the actual content came from the attacker's payload.
- This is a cross-repository record mutation for a stack that never authenticated the payload, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team").

### Likelihood Explanation
Preconditions: the attacker needs a repository registered as (or convertible into) a Shipit-tracked repo capable of sending a signed `status` webhook (own repo + own webhook secret if Shipit verifies per-repo secrets, or knowledge that the instance uses one shared secret), and a SHA collision with a commit already present in the victim's `commits` table. Practical SHA collision is nontrivial for arbitrary targeting (would require either the well-known empty-commit SHA edge case, or engineering a collision), which lowers likelihood from "trivial" but the code path itself has zero defense-in-depth — the query is unconditionally global. Given the audit's framing ("forged colliding-sha status webhook"), the collision is assumed achievable; the vulnerability is in the missing repository-scoping regardless of how the SHA match is obtained.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalently in any other handler using `Commit.where(sha: ...)`) to the repository identified by the verified webhook (e.g. `stack.repository == payload's repository` or join through `Stack` filtered by the repository the webhook signature/route is bound to), rather than matching on `sha` alone across all stacks.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual addition)
test "create_status_from_github! only affects the commit's own stack, not other stacks sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = create_stack_for_repo("attacker/evil")

  colliding_sha = "4b825dc642cb6eb9a060e54bf8d69288fbee491" # known collision-prone sha
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim commit", ...)
  attacker_commit = attacker_stack.commits.create!(sha: colliding_sha, message: "attacker commit", ...)

  payload = Webhooks::Handlers::StatusHandler::Params.new(
    sha: colliding_sha, state: "success",
    description: "ATTACKER CONTROLLED", target_url: "http://evil.example/pwn"
  )

  Hook.expects(:emit).with(:commit_status, victim_stack, anything).never
  Hook.expects(:emit).with(:deployable_status, victim_stack, anything).never

  Webhooks::Handlers::StatusHandler.new(payload).process

  # Assert equality that should hold but doesn't:
  # commit.stack == repository_that_signed(payload)
  refute_equal victim_stack.repository, attacker_stack.repository
  assert victim_commit.reload.statuses.exists?(description: "ATTACKER CONTROLLED") # demonstrates the leak/write
end
```
This test demonstrates `Hook.emit` firing with `victim_stack` from a payload whose only authenticated source is the attacker's repository, confirming the broken binding.
