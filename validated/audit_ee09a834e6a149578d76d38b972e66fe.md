## Analysis Result

### Title
Global, cross-user oracle timestamp ratchet (`last-update`) lets any caller freeze other users' price-dependent operations - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`v0-4-market.clar` tracks the most recently accepted Pyth/DIA publish-time per price feed in a single global map keyed only by `{type, ident}`, not by user or transaction. Any unprivileged account that triggers price resolution for an asset (deposit, borrow, repay, withdraw, liquidate, etc.) can advance this global watermark using a valid-but-comparatively-newer VAA. Every other account that subsequently tries to use that same asset with an equally valid, still-fresh price whose `publish-time` is lower than the ratchet value is rejected, even though their price passes every staleness/confidence check on its own.

### Finding Description
`price-resolve` reads and writes the shared `last-update` map: [1](#0-0) 

```
(last-update-time (oracle-last-update key))
...
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
(if (> timestamp last-update-time) (map-set last-update key timestamp) false)
```

`oracle-timestamp-fresh` enforces `(>= ts prev)`: [2](#0-1) 

The `last-update` map is declared with a key of just `{type, ident}` — i.e., per price feed, shared by the whole protocol, not scoped to a caller or transaction: [3](#0-2) 

Because Pyth is a pull-oracle, multiple valid, independently-fetched VAAs for the same feed can carry different (all legitimate, all within the staleness window) `publish-time` values at any given moment (Hermes nodes can lag/lead each other by seconds). Any account — including one with no privileged role — can be the first to submit the VAA with the highest `publish-time` for a given feed as an incidental part of an unrelated, cheap operation (e.g. a tiny deposit), permanently raising `last-update[ident]` for that feed until an even newer VAA appears. This is exactly the "shared cache primed by one caller and consumed by another" pattern: the attacker is the writer, every other market participant using that same asset is the involuntary reader.

Victim impact: once the ratchet is advanced past the victim's own valid VAA timestamp, every price-dependent public function the victim calls for that asset (`deposit`, `borrow`, `repay`, `redeem/withdraw`, and critically `liquidate`) will hit `ERR-ORACLE-INVARIANT` and revert, because `(>= ts prev)` fails — even though the victim's price is fresh, correctly signed, and within `max-staleness`. The victim has no way to "supply an older-but-real timestamp," and must wait for Hermes to produce (and someone to submit) a VAA whose publish-time exceeds the attacker's, which is entirely outside the victim's control.

### Impact Explanation
This lands on **temporary freezing of funds** (High): a borrower who needs to repay/withdraw before a health threshold is breached, or a liquidator who needs to liquidate an unhealthy position before it worsens/before another liquidator does, can be blocked from executing at all for that asset for an indeterminate period, purely because a third, unrelated, unprivileged party incidentally advanced the global timestamp watermark. This is not merely "ordinary shared-pool economics" — it is a concrete lock keyed to a specific victim action (their own valid price submission gets rejected) caused by another user's unrelated transaction touching the same shared oracle-state map.

### Likelihood Explanation
Likelihood is moderate: it requires no special access, no flashloan, no privileged role — only that the attacker perform any ordinary operation (e.g. a 1-unit deposit) using the freshest VAA they can pull from Hermes for a given feed. Because Pyth Hermes serves near-real-time updates continuously, an attacker (or even an unwitting active user) racing ahead of a victim's price submission is plausible, especially in periods of high price volatility precisely when other users (liquidators, borrowers protecting health) most need to act quickly.

### Recommendation
Do not enforce global monotonicity of `publish-time` across all callers. Anti-rollback protection should be scoped either (a) removed entirely and replaced by verifying only that the VAA's own `publish-time` is within `max-staleness` of `stacks-block-time` (which is already checked), or (b) scoped per-transaction/per-position rather than via a shared, ever-increasing global watermark keyed only by feed identifier. If monotonicity must be preserved to prevent oracle rollback attacks, consider only rejecting VAAs that are staler than the *previous block's* accepted timestamp (not the absolute latest seen), or allow any VAA that independently satisfies the freshness/staleness/confidence checks regardless of what timestamp another caller most recently wrote.

### Proof of Concept
1. Attacker fetches from Hermes the most recent available VAA for feed `X` with `publish-time = T2` and submits any cheap price-dependent call (e.g. `deposit` of a trivial amount) referencing feed `X`. `price-resolve` succeeds and sets `last-update[{TYPE-PYTH, X}] = T2`.
2. Victim, who fetched their own valid VAA for feed `X` slightly earlier (`publish-time = T1 < T2`, still within `max-staleness` of the current block time), attempts to `liquidate` an unhealthy position (or `repay`/`redeem` their own position) using feed `X`.
3. `price-resolve` computes `oracle-timestamp-fresh(T1, T2, max-staleness)` → `(>= T1 T2)` is `false` → the whole call reverts with `ERR-ORACLE-INVARIANT`, even though `T1` is genuinely fresh and correctly signed.
4. Victim is now blocked from any operation involving feed `X` until they (or someone) obtains and submits a VAA with `publish-time >= T2`, which is outside their control and can be repeated by the attacker to keep re-advancing the watermark.

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
