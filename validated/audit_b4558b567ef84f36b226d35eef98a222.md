### Title
Signature verification org (`repository.owner.login`) is decoupled from mutation target org (`repository.full_name`), enabling cross-tenant `pull_request` forgery when any configured org lacks a `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the secret) to verify against using `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. `LabelCapturingHandler` and `Repository#github_app`/`Stack#github_app` instead resolve the actually-mutated repository from `params.repository.full_name` (or `repository.owner`). These two attacker-supplied fields are never cross-checked for consistency, and `GitHubApp#verify_webhook_signature` unconditionally returns `true` when the resolved org's `webhook_secret` is unset. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The intended binding is: `repository_owner_used_for_signature_check == repository_owner_used_for_the_mutated_stack`. In multi-org configurations (`Shipit.github_organizations`, `TOP_LEVEL_GH_KEYS`), this binding does not hold, because the two lookups read different, independently attacker-controlled JSON paths of the same forged POST body. [5](#0-4) 

Path:
1. `WebhooksController#create` parses `request.raw_post` and dispatches to handlers only after `verify_signature` runs as a `before_action`. [6](#0-5) 
2. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (fallback `organization.login`), and uses it solely to select which `GitHubApp` config/secret to check against: `Shipit.github(organization: repository_owner)`. [7](#0-6) [8](#0-7) 
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that org's `webhook_secret` is blank, and otherwise only accepts the legacy `sha1=` header format (never `sha256`), but still requires knowledge of the secret to forge a valid HMAC when one is set. [3](#0-2) 
4. Once past this gate, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs `LabelCapturingHandler`, which resolves the target `Repository` from a completely separate field, `params.repository.full_name`, via `Repository.from_github_repo_name`. [4](#0-3) [9](#0-8) 
5. `capture_labels` then persists attacker-controlled label names onto the resolved stack's `PullRequest`: `pull_request.update!(labels: params.pull_request.labels.map(&:name))`. [10](#0-9) 

The project's own test fixture demonstrates that `repository.owner.login` (`"Codertocat"`) and `repository.full_name` (`"shopify/shipit-engine"`) are independent, uncorrelated fields in a real payload shape, confirming there is no code-level invariant tying them together. [1](#0-0) 

Exploit flow: an attacker who knows (or can guess/enumerate, e.g. via a public GitHub org name) the login of *any* org configured in Shipit's multi-org `github:` block that has no `webhook_secret` set (per the documented "optional" secret, and as shown even in the shipped example `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml`, both orgs ship with `webhook_secret: # nil`) can:
- Set `repository.owner.login` (and/or `organization.login`) to that no-secret org's login so `verify_signature` passes unconditionally (`return true unless webhook_secret`).
- Set `repository.full_name` to the victim's actual `owner/name` (a stack with `blocking_statuses` configured) and `action: "labeled"` with attacker-chosen `labels`.
- Send this to `POST /webhooks` with `X-Github-Event: pull_request` and any legacy `X-Hub-Signature: sha1=...` value (accepted format check only, no valid secret needed).

`verify_signature` never checks that `repository_owner` equals the owner embedded in `repository.full_name`, so the request is accepted, and `LabelCapturingHandler` mutates the victim stack's `PullRequest#labels` for a repository that never authenticated this request.

### Impact Explanation
The attacker can write arbitrary label names onto another repository's/organization's `PullRequest` record without ever possessing that org's `webhook_secret`, `github_access_token`, or any Shipit credential — this is exactly the "payload for one repository mutating another's stack" Critical category. Because `ReviewStack#env` uppercases label names into environment variables, and because the victim stack has `blocking_statuses` configured (gating `blocked?`/deploy eligibility on commit statuses/env-derived conditions), attacker-controlled labels reaching the victim's `PullRequest.labels` can influence downstream deploy-gating behavior for a stack the attacker does not own. This is repeatable against any repository/stack in the same Shipit instance as long as at least one configured org lacks a webhook secret, and it is not confined to the attacker's own repository.

### Likelihood Explanation
Preconditions: (1) Shipit multi-org config (`github:` keyed by org names, not the single top-level schema) — required, because the single-org schema ignores the `organization:` argument in `Shipit.github` and always checks against the one global secret, closing this path; (2) at least one configured org in that multi-org block has no `webhook_secret` set — this is explicitly an "optional" setting per the project's own docs/examples/dummy config, so it's a realistic deployment state, not a contrived one; (3) attacker must know that no-secret org's login (often discoverable, e.g. a lower-security/test org) and the victim's `owner/name`. Given these, attacker cost is a single unauthenticated HTTP POST, fully repeatable, no live GitHub interaction needed.

### Recommendation
Bind signature verification to the same owner/repository used for mutation: derive `repository_owner` and the mutated repository's owner from the same trusted field, and additionally verify `params.repository.full_name`'s owner matches the org whose secret authenticated the request before dispatching to handlers. Also treat a missing `webhook_secret` for any *specific* org as a hard failure (reject) rather than `return true unless webhook_secret`, or at minimum require an explicit `allow_unsigned: true` opt-in per org, and reject legacy `sha1` in favor of `sha256` support with per-org signature validation before any params.repository.full_name lookup is trusted.

### Proof of Concept
minitest plan (webhooks_controller_test.rb style):
1. Configure test app with multi-org secrets fixture equivalent to `test/dummy/config/secrets_double_github_app.yml` (`OrgOne` with `webhook_secret: nil`, `OrgTwo` with a real `webhook_secret`), and create a `Stack`/`Repository` owned by `OrgTwo` with `blocking_statuses` configured and an existing `PullRequest`.
2. Assert binding before: `pull_request.labels == []` (or original labels), `repository.owner == "orgtwo"`.
3. POST to `/webhooks` with headers `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=deadbeef` (or omitted), and JSON body where `repository.owner.login == "OrgOne"` (no-secret org) and `repository.full_name == "OrgTwo/victim-repo"`, `action: "labeled"`, `pull_request.labels: [{name: "MALICIOUS_ENV"}]`.
4. Assert response is `200`/`head(:ok)` (not `422`), proving `verify_signature` passed without a valid secret for `OrgTwo`.
5. Assert binding after: `pull_request.reload.labels == ["MALICIOUS_ENV"]`, proving a repository that never supplied `OrgTwo`'s secret mutated `OrgTwo`'s `PullRequest` — the invariant "a pull_request event only affects the repository/stack whose secret authenticated it" is violated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
