This confirms the vulnerability. The `CCMenuController#stack` method bypasses the stack-scoping enforcement that `BaseController#stack` normally provides.### Title
CCMenu API Controller Ignores ApiClient Stack Scope, Allowing Cross-Stack Build-Status Disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
`Shipit::Api::BaseController` implements the intended binding between an `ApiClient` token and the stack(s) it is authorised to touch: when an `ApiClient` has a `stack_id` set, the `stacks` helper restricts lookups to that single stack, and `stack` resolves `params[:stack_id]` only within that restricted relation: [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely, resolving `params[:stack_id]` against the full `Stack` table regardless of the authenticated client's `stack_id` binding: [2](#0-1) 

The controller authenticates the token either via HTTP Basic auth (inherited `authenticate_api_client`) or via a `params[:token]` query string, and only enforces the generic `read:stack` permission string, not scope to a specific record: [3](#0-2) [4](#0-3) [5](#0-4) 

`ApiClient#check_permissions!` only checks whether the string `"read:stack"` is present in the client's `permissions` array; it never checks the `stack_id` the client is bound to against the specific `stack` being accessed: [5](#0-4) 

This is exactly the kind of trust-binding this app is supposed to enforce elsewhere: `ApiClient#stack_id` is meant to constrain *which* stack a token authorises access to, but `CCMenuController` accesses whichever stack `params[:stack_id]` names — the stack the token *authorises* (as set at issuance, e.g. via `CCMenuUrlController#client`, which creates a scoped client bound to one stack: `Stack.from_param!(params[:stack_id])` scoping is absent) diverges from the stack the token actually *touches*.

`CCMenuUrlController` demonstrates the intended design: it creates/reuses an `ApiClient` scoped with `permissions: %w[read:stack]` and implicitly relies on the `stack` association/`stack_id` to constrain that token to one stack: [6](#0-5) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, a holder of any `read:stack`-scoped CCMenu token (generated for one specific stack) can substitute an arbitrary `stack_id` in the request path and read the build/deploy status of any other stack in the installation.

### Impact Explanation
This breaks the binding "a stack a token authorises versus a stack it touches." A token minted for stack A (via `CCMenuUrlController`) is meant to be readable only for stack A's CI status. Due to the missing scope check in `CCMenuController#stack`, the same token grants unauthenticated (from the perspective of stack B) read access to any other stack's latest deploy/rollback state (build status, label, activity, web URL) rendered in `app/views/shipit/ccmenu/project.xml.erb` via the `show` action. This matches the "High — unauthenticated read of stack state" impact category: an attacker who legitimately holds a token for one stack gains read access to CI status of stacks they were never granted access to, across repositories/environments in the same Shipit installation.

### Likelihood Explanation
Likelihood is high for any deployment where more than one team/stack shares a single Shipit installation with distinct CCMenu tokens. Exploitation requires only a valid (even minimally-scoped, single-stack) CCMenu token — which is routinely distributed to CI dashboard tools (CCTray/CCMenu clients) and embedded in URLs — and knowledge or guessing of another stack's `to_param` (`repository_owner/repository_name/environment`), which is often predictable/enumerable from the org's known repositories.

### Recommendation
Change `CCMenuController#stack` to resolve the stack through the same client-scoped `stacks` relation used elsewhere (i.e., `stacks.from_param!(params[:stack_id])`, matching `BaseController#stack`), so that a stack-scoped `ApiClient` can only ever resolve to the stack(s) it was actually granted (`current_api_client.stack_id`).

### Proof of Concept
1. As an admin, create a CCMenu URL for Stack A via `CCMenuUrlController#fetch`; this returns a URL containing `token=<A-scoped token>` where the underlying `ApiClient` has `stack_id = A.id` and `permissions = ["read:stack"]`. [7](#0-6) 
2. As an attacker who has legitimately obtained this token (e.g., pulled from a public CI dashboard config), send: `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu.xml?token=<A-scoped token>` where `owner/repo-B/env-B` is an unrelated stack B the token was never granted.
3. `authenticate_api_client` succeeds (token is valid), `require_permission :read, :stack` succeeds (client has `read:stack` in its permission list), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack B directly, ignoring `current_api_client.stack_id == A.id`. [8](#0-7) 
4. The response renders stack B's latest deploy/rollback status, disclosing build state for a stack the token was never authorised to touch.
