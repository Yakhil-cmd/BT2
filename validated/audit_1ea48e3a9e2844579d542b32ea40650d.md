### Title
Missing `return` after exception in `handleSavedPrivatePayments` causes double-processing/double-callback of a private-payment chain - ([File: network.js])

### Summary
In `network.js`, `handleSavedPrivatePayments()`'s inner `validateAndSave` function calls `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` inside a `try/catch`. When this call throws, the `catch` block logs the error, optionally notifies the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — but it does **not** `return` afterward. Execution falls through to the rest of `validateAndSave`, which builds `key` from the now-`undefined` `json_payload_hash` and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers each also call `cb()` (and, for `ifOk`/`ifError`, `deleteHandledPrivateChain(...)` again). This mirrors the CVE-2023-52687 bug class: a failure signal from a call (`dma_map_sg()` returning 0 / a JS function throwing) is not treated as terminal, and the code proceeds to reuse state as if the call had succeeded, ending up processing/releasing the same resource twice. [1](#0-0) 

### Finding Description
`handleSavedPrivatePayments` iterates rows from `unhandled_private_payments` (populated by `handleOnlinePrivatePayment`, reachable by any private-payment counterparty who sends a `private_payment` message over a paired device/wallet channel) and validates each stored chain: [2](#0-1) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (e.g., because the attacker-controlled `payload` stored verbatim as JSON in the DB contains a shape that the canonicalizer/hasher rejects — non-plain objects, unsupported types, or excessively deep/circular-like structures reconstructed from `JSON.parse(row.json)`), the `catch` block:
1. Logs the error,
2. Optionally sends an error result to the peer,
3. Calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)`, which itself deletes the DB row and then invokes `cb()` — the `async.each` iteratee callback.

Then, because there is no `return`, the same iteratee **keeps running**: it computes `key` using `undefined` for the hash, and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same (already "deleted") chain a second time. Each of that call's callbacks (`ifOk`, `ifError`, `ifWaitingForChain`) invokes `cb()` again, and `ifOk`/`ifError` call `deleteHandledPrivateChain(...)` a second time as well.

This causes `cb()` — the `async.each` per-item completion callback — to be invoked twice for the same row. Calling an `async` callback more than once is undefined/unsafe behavior: it can decrement the internal completion counter incorrectly, cause the final `async.each` callback (which calls `unlock()` on the `"saved_private"` mutex key and emits `"new_my_transactions"`) to fire prematurely or multiple times, and let a second, independent invocation of `privatePayment.validateAndSavePrivatePaymentChain` run concurrently with earlier processing of the same chain — effectively bypassing the intended single-pass, serialized handling of a private payment chain.

### Impact Explanation
This is reachable purely by a private-payment counterparty (no privileged/hub/network-attacker capability needed) crafting a `private_payment` payload whose head element's `payload` cannot be canonically hashed. The concrete risks:
- **Double invocation of chain validation/save logic** for the same private chain, since the second `validateAndSavePrivatePaymentChain` call executes unconditionally regardless of whether the row was already deleted by the `catch` branch, potentially re-triggering DB writes/asset-output insertion logic (`INSERT ... IGNORE` mitigates literal duplicate rows, but the double `cb()`/mutex misbehavior remains).
- **Corruption of `async.each`/mutex bookkeeping**: `unlock()` for the `"saved_private"` lock can fire out of sync with actual completion of all rows, allowing overlapping unlocked execution of private-payment processing that the mutex was meant to serialize — this can let two private-chain validations run concurrently against attacker-influenced inputs, which is the class of bug (broken mutual exclusion around fund-affecting DB writes) that historically enables inconsistent wallet/local-DB state for private, off-chain-tracked balances.
- Since this only affects private-asset bookkeeping paths reachable by a payment counterparty, and does not itself directly forge signatures or double-spend a stable public output, I rate this **Medium** rather than Critical/High — it is a genuine unchecked-error/control-flow defect analogous to the reported CVE, but its blast radius in `ocore` is confined to local wallet-side private-payment processing state rather than DAG-wide consensus.

### Likelihood Explanation
Triggering the `catch` requires the attacker to control the shape of `objHeadPrivateElement.payload` such that `objectHash.getBase64Hash` throws. Since `arrPrivateElements` originates from `JSON.parse(row.json)` where `row.json` is the attacker-supplied `private_payment` message content stored verbatim by `handleOnlinePrivatePayment`, an attacker (a device paired for a private payment) has direct control over the payload's structure and can likely construct a payload shape that fails the hash function's internal assumptions (e.g., unexpected nested types). I was not able to fully confirm from the available index which specific payload shapes make `getBase64Hash`/`getSourceString` throw (the exact body of `object_hash.js`'s `getSourceString`/`getBase64Hash` was not retrievable within the tool budget), so likelihood is assessed as **moderate but unconfirmed at the byte level**.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain(...)` call in the `catch` block of `validateAndSave` in `network.js` (around line 2476), so that a hashing failure terminates this iteration cleanly without falling through to build `key` from `undefined` and without invoking `privatePayment.validateAndSavePrivatePaymentChain` a second time on the same row. Additionally, consider guarding `deleteHandledPrivateChain`'s `cb` invocation so it cannot be triggered more than once per row (e.g., via a boolint flag), to make the iteratee robust even if similar fall-through bugs are reintroduced elsewhere.

### Proof of Concept
1. As a paired device, send a `private_payment` message via the wallet protocol (`handleOnlinePrivatePayment` → `savePrivatePayment` path) whose head private element's `payload` is a JSON structure that parses fine via `JSON.parse` but causes `objectHash.getBase64Hash(payload, true)` to throw when later reprocessed (e.g. non-canonicalizable nested structures not covered by earlier `ValidationUtils` checks in `handleOnlinePrivatePayment`/`handlePrivatePaymentChains`, since those checks validate array/object non-emptiness but not full hashability).
2. This message is queued into `unhandled_private_payments` and later processed asynchronously by `handleSavedPrivatePayments`.
3. During processing, `validateAndSave` hits the `catch` block, deletes the row, and calls `cb()` once via `deleteHandledPrivateChain` — then, due to the missing `return`, immediately also calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose completion handlers call `cb()` (and possibly `deleteHandledPrivateChain`) a second time.
4. Observe (via instrumentation of `async.each`'s final callback / the `"saved_private"` mutex unlock timing, or via duplicate `console.log('emit ...')`/duplicate `eventBus.emit(key, ...)` output) that the iteratee's completion callback fires more than once for a single row, demonstrating the broken control flow.

I could not execute this PoC against a live node within this session; the control-flow defect itself (the missing `return`) is directly confirmed by reading the source, and the exact malformed-payload shape needed to make `getBase64Hash` throw is unconfirmed due to indexing limits on `object_hash.js`'s internals. A Devin session with full repository access could confirm the exact throwing input and reproduce the double-callback behavior end-to-end.
