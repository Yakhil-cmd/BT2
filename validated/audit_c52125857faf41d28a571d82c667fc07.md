### Title
Attacker-controlled PR title/metadata printed unsanitized to terminal in `printHumanPrPreview`, allowing escape-sequence/mode-injection with no restore - ([File: pkg/cmd/pr/view/view.go])

### Finding Description
`NewCmdView` wires `viewRun` to `printHumanPrPreview` when stdout is a TTY [1](#0-0) . That function writes several attacker-controlled GraphQL fields straight to `opts.IO.Out` via `fmt.Fprintf`/`fmt.Fprintln` with no escape-sequence sanitization at all: the PR title [2](#0-1) , author/reviewer/assignee/label/milestone/project names [3](#0-2) , and the auto-merge enabler login [4](#0-3) . None of these paths route through `iostreams.Untrusted`, `iostreams.ContainsEscapeSequence`, `CopyGuardedContent`, or the `asciisanitizer` transform that the codebase uses elsewhere for exactly this purpose — e.g. gist view wraps remote content in `iostreams.NewUntrusted` before printing [5](#0-4) , `read-file` explicitly refuses content containing ESC bytes unless `--allow-escape-sequences` is passed [6](#0-5) , and `pr diff` refuses/guards escape sequences via `sanitizedReader`/`ContainsEscapeSequence` [7](#0-6) . The `Untrusted.String()` sanitizer neutralizes any `0x1B` byte by rendering it as visible caret notation (`^[`) rather than letting it reach the terminal [8](#0-7) , which is the established defense against this attack class in this codebase — but that defense is never applied to `pr.Title` and the other metadata fields printed by `printHumanPrPreview`. Only `pr.Body` is passed through `markdown.Render` [9](#0-8) , and I could not verify from the indexed code whether the vendored `glamour`/`go-gh markdown` renderer itself strips or passes through literal ESC bytes embedded in body text, since that vendored package was not present in the index.

An attacker who opens a PR/issue with a title (or a label name, milestone title, project name, or is a collaborator whose display name is attacker-influenced) containing raw ANSI/DEC private-mode escape sequences (e.g. `\x1b[?1049h` alternate screen, `\x1b[?1000h` mouse reporting, `\x1b[?25l` cursor hide) causes those bytes to reach the victim's terminal unmodified when they run `gh pr view <number>` interactively. Since `gh` never emits a terminal-reset sequence on exit in this code path, any mode switched into by the injected sequence remains active after `gh` exits.

### Impact Explanation
This can leave the victim's terminal in an altered state (alternate screen buffer, mouse tracking enabled, cursor hidden, or terminal title/response query sequences) that persists in the shell session after `gh` exits, enabling terminal output spoofing or a stuck/garbled prompt — matching the "Terminal output/prompt spoofing" High-impact class referenced in the question. This does not achieve code execution or credential exfiltration by itself, but is a legitimate terminal-injection primitive that other command paths in this codebase have specifically been hardened against.

### Likelihood Explanation
Fully unprivileged: any GitHub user can open a PR/issue with an arbitrary title, or create a label/milestone/project with a crafted name, containing raw ESC bytes. The victim only needs to run the ordinary interactive command `gh pr view <number>` on that repository/PR. No admin rights, tokens, or MITM required, making this readily repeatable.

### Recommendation
Wrap all attacker-controlled string fields printed in `printHumanPrPreview` (`pr.Title`, reviewer/assignee names, label names, milestone title, project names, `autoMerge.EnabledBy.Login`, and any other API-sourced text rendered outside `markdown.Render`) in `iostreams.NewUntrusted(...)` (or an equivalent ANSI-sanitizing pass) before writing them to `opts.IO.Out`, consistent with the pattern already used in `pkg/cmd/gist/view/view.go`. Additionally verify/fix `markdown.Render`/glamour's handling of literal escape bytes in `pr.Body`, `comment.Content()`, and `release.Body` so a raw ESC byte embedded in markdown text cannot reach the terminal unsanitized.

### Proof of Concept
```go
// pkg/cmd/pr/view/view_test.go
func TestPrintHumanPrPreview_TitleEscapeSequenceNotSanitized(t *testing.T) {
    ios, _, out, _ := iostreams.Test()
    ios.SetStdoutTTY(true)

    pr := &api.PullRequest{
        Title: "Hello\x1b[?1049hALT_SCREEN_MODE",
        // ... minimal required fields
    }
    opts := &ViewOptions{IO: ios, Now: time.Now}

    err := printHumanPrPreview(opts, ghrepo.New("OWNER", "REPO"), pr)
    require.NoError(t, err)

    // Expect: no raw ESC (0x1b) byte should reach Out; title should be
    // sanitized/caret-escaped like iostreams.Untrusted.String() does.
    assert.NotContains(t, out.String(), "\x1b",
        "PR title escape sequence reached the terminal unsanitized")
}
```
This test currently fails because `pr.Title` is written via raw `fmt.Fprintf` with no sanitization, demonstrating the gap relative to the codebase's own `Untrusted`/`asciisanitizer` pattern used elsewhere.

// String returns the content with ANSI escape sequences neutralized. It is
// called automatically by the fmt package, so printing an Untrusted value is
// safe by default on every fmt path.
func (u Untrusted) String() string {
	sanitized, _, err := transform.String(&asciisanitizer.Sanitizer{}, u.raw)
	if err != nil {
		return stripControl(u.raw)
	}
	return sanitized
}
