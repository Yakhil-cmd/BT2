Found the binding break: `WebhooksController#verify_signature` selects the GitHub App/secret to verify against using `repository_owner` — derived from `params.dig('repository','owner','login')` with a fallback to `params.dig('organization','login')` — while the actual repository that gets written to (via `PushHandler#repository_name` → `payload.dig('repository','full_name')`) is a *different, independently-controlled field of the same attacker-supplied JSON body*.

### Title
Webhook organization used for signature verification is decoupled from the repository actually written to - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to validate a webhook against based on `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while the code that acts on the payload (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target repository from `payload.dig('repository', 'full_name')` — a sibling field in the very same object, but not the same field used to select the verifying secret.

### Finding Description [1](#0-0)  verifies the signature using `Shipit.github(organization: repository_owner)`, and [2](#0-1)  shows `repository_owner` is read straight out of the untrusted JSON payload (`repository.owner.login`), with a fallback to `organization.login`. Meanwhile, the code that actually resolves which `Stack`/`Repository` a push/status/check_suite event applies to uses a *different* payload path: [3](#0-2)  looks up `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, and [4](#0-3)  uses that repository's stacks to trigger `sync_github`.

Because the HMAC signature (`X-Hub-Signature`) covers the entire raw POST body — as verified in `verify_webhook_signature` — [5](#0-4)  — an attacker cannot forge an arbitrary payload without the correct secret. In a single-organization deployment this decoupling is harmless because `repository.owner.login` and `repository.full_name`'s owner segment necessarily match for genuine GitHub-issued webhooks. However, in a **multi-organization** Shipit deployment (the engine explicitly supports multiple GitHub orgs/apps, each with its own `webhook_secret`, as shown in `config/secrets.development.shopify.yml`), this is a structural analog of the reported bug class: the field used to authenticate ("which secret proves this request") and the field the business logic trusts to select the repository being mutated ("which repository does this affect") are not the same field, and nothing in the engine cross-checks that `repository.owner.login` (the field bound to the signature check) equals the owner segment of `repository.full_name` (the field the handler actually acts on).

### Impact Explanation
This does not on its own allow forging a webhook without the correct secret — signature verification still requires knowing `webhook_secret` for whichever organization is claimed by `repository_owner`. Under the strict "unauthorized deploy" criterion, exploitation would require a valid webhook_secret for *some* configured organization plus the ability to set `repository.full_name` to a repository owned by a *different* configured organization while the outer `repository.owner`/`organization.login` fields still resolve to the attacker's own org. Given that both fields live in the same attacker-controlled JSON body under the same signature, and Shipit performs no post-verification comparison of `repository.owner.login` against the owner segment of `repository.full_name`, an operator of a compromised/malicious GitHub App installation for Org A (with a legitimate `webhook_secret` for Org A) could craft a signed `push`/`status` payload whose `repository.full_name` names a repository actually tracked under Org B's stacks in the same Shipit instance, causing `GithubSyncJob`/`sync_github` to run against Org B's stack using data attributed to a push the attacker fully controls.

### Likelihood Explanation
Requires the operator to run Shipit with multiple GitHub organizations configured (a supported, documented configuration) and requires possession of a valid `webhook_secret` for at least one of those organizations — which is itself a privileged secret, making this a defense-in-depth/cross-tenant gap rather than an unauthenticated bypass. This is a low-to-moderate likelihood finding given the precondition of holding a legitimate webhook secret for one org in a multi-org deployment.

### Recommendation
After signature verification succeeds, assert that `params.dig('repository','owner','login')` (or `organization.login`) matches the owner segment of `params.dig('repository','full_name')` before dispatching to any handler, so the field trusted for authentication and the field trusted for repository resolution are provably the same value.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `org-a` and `org-b`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema) and each with tracked stacks.
2. As holder of `org-a`'s `webhook_secret`, construct a `push` event JSON body with:
   - `repository.owner.login = "org-a"` (and/or `organization.login = "org-a"`) — used only for signature-secret selection.
   - `repository.full_name = "org-b/some-repo"` — used by `PushHandler`/`Handler#repository_name` to resolve the target `Stack`.
3. Sign the raw body with `org-a`'s webhook secret and POST to `/webhooks` with `X-Hub-Signature`.
4. `WebhooksController#verify_signature` selects `org-a`'s app via `repository_owner` and successfully verifies the signature.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-b/some-repo")`, and triggers `sync_github` against `org-b`'s stack using attacker-supplied `after` (head sha) and `ref`, despite the request never being authenticated against `org-b`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
