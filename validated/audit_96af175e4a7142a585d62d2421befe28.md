### Title
`is_valid_merkle_proof` in oscript accepts an attacker-supplied Merkle root with no binding to any trusted commitment - ([File: merkle.js], [File: formula/evaluation.js])

### Summary
The oscript primitive `is_valid_merkle_proof(element, proof)`, reachable by any AA trigger sender through formula evaluation, only verifies that a leaf hashes up to the `root` field contained *inside the attacker-supplied proof itself*. It never checks that this root equals any externally-known, trusted commitment (e.g., a value published via a data feed, hard-coded in the AA, or otherwise fixed by consensus). This mirrors the reported halo2_gadgets defect: a value that should be pinned to the "real" source is left as a free, self-consistent witness, so an internal-consistency check is mistaken for a binding check against ground truth.

### Finding Description
`merkle.verifyMerkleProof(element, proof)` recomputes a hash chain from `element` up through `proof.siblings` and simply compares the result to `proof.root`: [1](#0-0) 

Crucially, `proof.root` is not an independent, externally-verified value — it is deserialized directly from the same attacker-controlled proof string/object supplied to the check: [2](#0-1) 

In `formula/evaluation.js`, the oscript op `is_valid_merkle_proof` takes only two arguments — `element` and `proof` — and passes them straight into `merkle.verifyMerkleProof`, with no third "expected root" parameter and no lookup of a canonical root from a data feed, asset definition, or any other trusted source: [3](#0-2) 

Because the prover (trigger sender / AA-triggering unit author) fully controls both `element` and the entire `proof` object (including `proof.root` and `proof.siblings`), they can construct their own arbitrary Merkle tree, generate a self-consistent proof for it, and pass `is_valid_merkle_proof` for *any* claimed element they like. The check enforces "internal consistency of the tree" (i.e., the equivalent of the halo2 `q_mul_2` constraint that forces the loop's base values to be consistent with *each other*) but does nothing analogous to the halo2 fix's `copy_advice()` — nothing forces `proof.root` to equal the actual, previously-committed root that the AA logic is meant to be checking membership against.

This is structurally identical to the reported root cause: a value (`x_p`/`y_p` base point in halo2; `root` in `ocore`) is fed into a verification routine via free assignment (`assign_advice()`/direct field of an attacker JSON object) rather than being tied by a constraint/comparison to the actual expected value, allowing the "proof" to validate an arbitrary, self-chosen statement.

### Impact Explanation
Any AA (Autonomous Agent) that uses `is_valid_merkle_proof(element, proof)` to gate value transfer, whitelist membership, voting eligibility, or any conditional logic based on "element is a member of a known dataset" can be defeated by a trigger sender who fabricates their own tree/root and satisfies the check for an element that was never actually part of the real, trusted dataset. Depending on how the AA uses the result (e.g., releasing funds, minting/crediting balances, approving a claim), this can directly lead to **AA fund loss** or unauthorized state changes — a Medium/High impact under the categories in scope (AA fund loss or freezing, unauthorized spending via AA logic).

### Likelihood Explanation
Likelihood is tied to actual AA usage of this primitive without an additional explicit `proof.root == <trusted root>` comparison in the oscript formula. If an AA developer (reasonably, given the function's name suggests cryptographic verification) assumes `is_valid_merkle_proof` alone establishes trusted membership, the vulnerability is directly and trivially exploitable by any unprivileged trigger sender — no special access, keys, or race conditions are required, only crafting the `data` object of a normal AA trigger unit.

### Recommendation
- Update documentation/semantics of `is_valid_merkle_proof` to make explicit that callers MUST separately compare the returned `proof.root` (accessible as a property on the object) against a trusted/expected root before relying on the result for any authorization decision.
- Consider changing the primitive's signature to `is_valid_merkle_proof(element, proof, expected_root)`, binding the root check into the primitive itself so it cannot be silently omitted by AA authors, analogous to converting `assign_advice()` to `copy_advice()` in the halo2 fix.
- Audit existing/known AAs for uses of `is_valid_merkle_proof` that omit an explicit `proof.root` equality check against a trusted source.

### Proof of Concept
1. An AA is written with oscript logic intending "only allow this trigger if `element` is a member of the canonical whitelist Merkle tree with root `ROOT_X` (published, e.g., via a data feed)":
   ```
   if (is_valid_merkle_proof(trigger.data.element, trigger.data.proof))
       // pay out / approve
   ```
   without also checking `trigger.data.proof.root == ROOT_X` (or the check is performed against a value also taken from the trigger data, rather than an independently known/trusted source).
2. An attacker builds their own single-leaf (or larger) Merkle tree containing an arbitrary `element` value of their choosing, computes a self-consistent proof (`merkle.getMerkleProof`) over their own tree, and serializes it, e.g. via `serializeMerkleProof`: [4](#0-3) 
3. The attacker submits an AA trigger unit with `data.element = <arbitrary_element>` and `data.proof = <attacker's self-consistent proof, including attacker's own root>`.
4. `is_valid_merkle_proof` evaluates to `true` because `merkle.verifyMerkleProof` only checks that the element chains to the `root` embedded in the same attacker-supplied proof — never validating that root against the AA's real canonical dataset.
5. The AA proceeds to treat the attacker's arbitrary `element` as verified/whitelisted, executing whatever privileged logic (fund release, credit, etc.) was gated on that check.

function getMerkleProof(arrElements, element_index){
	if (element_index < 0 || element_index >= arrElements.length)
		throw Error("invalid index");
	var arrHashes = arrElements.map(hash);
	var index = element_index;
	var arrSiblings = [];
	while (arrHashes.length > 1){
		var arrOverHashes = []; // hashes over hashes
		var overIndex = null;
		for (var i=0; i<arrHashes.length; i+=2){
			var hash2_index = (i+1 < arrHashes.length) ? (i+1) : i; // for odd number of hashes
			if (i === index){
				arrSiblings.push(arrHashes[hash2_index]);
				overIndex = i/2;
			}
			else if (hash2_index === index){
				arrSiblings.push(arrHashes[i]);
				overIndex = i/2;
			}
			arrOverHashes.push(hash(arrHashes[i] + arrHashes[hash2_index]));
		}
		arrHashes = arrOverHashes;
		if (overIndex === null)
			throw Error("overIndex not defined");
		index = overIndex;
	}
	// add merkle root
	//arrSiblings.push(arrHashes[0]);
	return {
		root: arrHashes[0],
		siblings: arrSiblings,
		index: element_index
	};
}

function serializeMerkleProof(proof){
	var serialized_proof = proof.index;
	if (proof.siblings.length > 0)
		serialized_proof += "-"+proof.siblings.join("-");
	serialized_proof += "-"+proof.root;
	return serialized_proof;
}

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
