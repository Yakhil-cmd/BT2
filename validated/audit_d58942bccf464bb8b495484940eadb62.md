### Title
Attacker-controlled PR `branch` name is interpolated against the command's own env (including `GITHUB_TOKEN`) before reaching `PTY.spawn` - ([File: lib/shipit/command.rb])

### Summary
`ReviewStackAdapter#stack_attributes` stores an attacker-named PR `head.ref` verbatim as the stack's `branch` [1](#0-0) . That branch value is later passed as a literal git CLI argument (`--branch <branch>`) by `StackCommands#fetch_commit`/`#fetch` via `git_clone`, and `Command#interpolate_environment_variables` rewrites any `$VARNAME` substring in every argument using the command's own env hash before `PTY.spawn` executes it [2](#0-1) [3](#0-2) . That env hash is built by `Commands#base_env`, which explicitly includes `GITHUB_TOKEN` [4](#0-3) , and `StackCommands#env` merges it with the stack's own env [5](#0-4) .

### Finding Description
Broken binding: `Command#interpolated_arguments` should equal `@args` verbatim for any argument sourced from an unauthenticated, attacker-named string (e.g. a PR branch name); instead `EnvironmentVariables#interpolate` substitutes `$WORD` patterns with `@env.fetch(variable) { ENV[variable] }`, so `interpolated_arguments != @args` whenever the attacker-chosen string happens to match an environment variable name known to the command [6](#0-5) .

Path traced:
1. Attacker opens a PR from a fork naming the branch `$GITHUB_TOKEN` (or similar). GitHub's webhook payload carries `pull_request.head.ref` with that literal string.
2. `ReviewStackAdapter#stack_attributes` sets `branch: params.pull_request.head.ref` with no sanitization or format validation applied to the value before it's persisted on the `Stack` [1](#0-0) .
3. When the stack's git cache doesn't yet exist, both `StackCommands#fetch_commit` and `#fetch` fall back to `git_clone(@stack.repo_git_url, @stack.git_path, branch: @stack.branch, env:, chdir:)`, which builds `git('clone', ..., '--branch', branch, url, path, **kwargs)` [7](#0-6) [8](#0-7) .
4. `Commands#git` builds a `Command.new("git", *args, env: base_env, ...)`, where `base_env` (merged further by `StackCommands#env`) always contains the real `GITHUB_TOKEN` string [9](#0-8) .
5. `Command#start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)`, and `interpolated_arguments` runs every argument, including the `--branch` value, through `EnvironmentVariables.with(env).interpolate` [3](#0-2) . Since the branch string is literally `$GITHUB_TOKEN`, the regex `/(\$\w+)/` matches it and substitutes the real token value from `@env` before the command line is spawned [6](#0-5) .
6. The resulting `git clone ... --branch <REAL_TOKEN> ...` command is executed. On a common outcome (branch not found, since the real branch is the attacker's actual ref, not the token string) git prints a warning/error containing the branch argument verbatim (e.g. `warning: Could not find remote branch <value> to clone.`), which streams into the task's live output/log, visible on the stack's task page to any Shipit user who can view that stack/task.

Why guards don't stop this: there's no signature/authorization gap being exploited here (the webhook can be legitimately signed since it's the attacker's own repo/PR), so `verify_signature` is irrelevant. There's no validation on `Stack#branch` format restricting it to characters unable to form `$VARNAME` patterns (grep for branch validators/format checks on the `Stack` model returned no results). `EnvironmentVariables#permit` is a separate method used for spec/user-declared env whitelisting and is not invoked on this git-command path — `interpolate` is called unconditionally on every argument regardless of source or trust level.

Note on the question's exact framing: the claimed trigger via `commit.sha` in `StackCommands#fetch_commit`'s `git('fetch', 'origin', ..., commit.sha, ...)` is not itself exploitable — `commit.sha` is a genuine SHA-1 computed by GitHub, not an attacker-chosen literal, so it cannot be made to read `$GITHUB_TOKEN`. However, the same method (and `#fetch`) contains a genuinely exploitable sibling call: the `git_clone(..., branch: @stack.branch, ...)` fallback that both methods invoke when the git cache doesn't exist yet, which does carry the fully attacker-controlled `head.ref` string as a literal CLI argument through the identical `interpolate_environment_variables`/`PTY.spawn` mechanism.

### Impact Explanation
If triggered, the real `GITHUB_TOKEN` used by the deploy host for that repository's GitHub App/organization is embedded into a git command line and, on typical failure paths (branch-not-found), echoed into the task's streamed output, which is stored and rendered on the stack/task page. Any Shipit user permitted to view that stack (potentially any member of a `Shipit.github_teams`-authorized team, or any repository maintainer) can read the token from the task log. Once exposed, the token can be used to interact with GitHub as the app/token's identity — this matches the "exfiltration of `GITHUB_TOKEN`" Critical impact category. Blast radius is scoped to whichever GitHub organization/token that specific `Shipit.github(organization:)` call resolves to for the target repository, but is repeatable by any external contributor who can open a PR against a Shipit-managed repository with review-stack support, using nothing but branch naming.

### Likelihood Explanation
Precondition: the target Shipit instance must have `ReviewStack`/PR-based review-stack provisioning enabled for the repository (so `ReviewStackAdapter#create!` is reached from a webhook), and the review stack's git cache must not yet exist locally for the `git_clone` fallback path (or `#fetch` must run) to actually be invoked with `branch: @stack.branch`. GitHub does allow `$`, `(`, `)` and other shell/regex metacharacters in branch names, so crafting `head.ref = "$GITHUB_TOKEN"` costs the attacker nothing beyond opening a normal fork PR. No Shipit credentials, session, or privileged role are required — this matches the stated unprivileged-attacker threat model. I was not able to confirm within the available context whether any `Stack` model validation restricts the `branch` attribute's character set (the search for branch format validators returned no matches), which is the key uncertainty for this finding — if such a validator exists and rejects `$`/`(`/`)`, the exploit is blocked at write time.

### Recommendation
Do not interpolate environment variables into arguments whose values originate from external, unauthenticated sources (branch names, commit messages, PR titles, etc.). Either: (1) restrict `EnvironmentVariables#interpolate` to only run on the command's own template arguments (i.e., ones defined by Shipit configuration, not runtime data like `@stack.branch`), or (2) sanitize/validate `Stack#branch` to a strict allow-list (e.g. `/\A[\w\-\.\/]+\z/`) rejecting `$`, `(`, `)` and other characters, at the point where `ReviewStackAdapter#stack_attributes` sets `branch:` from `params.pull_request.head.ref`. Additionally, avoid passing secrets like `GITHUB_TOKEN` through a mutable, interpolation-visible env hash used for general argument interpolation — prefer `GIT_ASKPASS` or credential helpers that never place the raw token where `$VARNAME` substitution can reach it.

### Proof of Concept
Add to `test/unit/command_test.rb` or a new `stack_commands_test.rb` (minitest, no live GitHub):
```ruby
test "interpolate_environment_variables leaks secret-like env values from untrusted argument content" do
  command = Shipit::Command.new(
    'git', 'clone', '--branch', '$GITHUB_TOKEN', 'https://example.com/repo.git', '/tmp/x',
    chdir: '/tmp',
    env: { 'GITHUB_TOKEN' => 'super-secret-token-value' }
  )

  interpolated = command.interpolated_arguments

  # Binding under test: interpolated_arguments should equal @args verbatim
  # for attacker-controlled data; it does not.
  refute_equal command.args, interpolated
  assert_includes interpolated, 'super-secret-token-value'
  refute_includes interpolated, '$GITHUB_TOKEN'
end
```
And, to demonstrate the full path, a model-level test asserting that creating a `ReviewStack` via `ReviewStackAdapter#stack_attributes` with `params.pull_request.head.ref == "$GITHUB_TOKEN"` results in `stack.branch == "$GITHUB_TOKEN"` with no sanitization, then that `StackCommands.new(stack).fetch.args` (or `fetch_commit`'s `git_clone` fallback args) contains that literal string, which `interpolated_arguments` then rewrites into the real token when `env` includes `GITHUB_TOKEN`.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
