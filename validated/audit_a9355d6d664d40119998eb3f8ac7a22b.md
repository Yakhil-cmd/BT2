### Title
Position-NFT seller can front-run the sale and drain all borrowable value / excess collateral before the buyer receives the account - (contracts/controller/src/lib.rs)

### Summary
XOXNO Lending represents each lending account as a transferable position NFT (`account_id == token_id`). The NFT carries both collateral and debt atomically, and `borrow`/`withdraw` pay out to an arbitrary `to` address chosen by the current owner. There is no "listed for sale" state, no transfer cooldown, and no lock that prevents the owner from extracting value between the moment a buyer commits to a purchase and the moment the `transfer` executes. A seller can therefore front-run the marketplace settlement transaction with `controller::borrow` (and/or `withdraw`), pull every token of remaining borrow capacity and surplus collateral to their own address, and still receive the full sale price — the exact analog of minting all EUROs a SmartVault allows before selling its NFT.

### Finding Description
The position NFT is a stock OpenZeppelin `NonFungibleToken` (Enumerable). `transfer(from, to, token_id)` only requires `from.require_auth()`; nothing in the controller or the NFT contract freezes account activity when a token is listed or approved [1](#0-0) .

Controller authority is resolved live via `owner_of(account_id)` on every call, so until the transfer ledger entry lands, the seller keeps full owner authority [2](#0-1) . Both extraction verbs accept a `to: Option<Address>` recipient, so proceeds go directly to the seller rather than staying with the account:

- `borrow(caller, account_id, borrows, to)` — "Borrows against `account_id`'s collateral, paying `to` or the caller. Requires owner or delegate authorization and post-borrow solvency." [3](#0-2) 
- `withdraw(caller, account_id, withdrawals, to)` — pays collateral to `to`; zero withdraws the full position [4](#0-3) .

Authorization is just `require_owner_or_delegate`, which passes for `caller == owner` — i.e., whoever `owner_of` returns at execution time [5](#0-4) .

Attack path (single unprivileged address):

1. Seller owns account `A` with $10,000 LTV-weighted collateral and $0 debt — i.e., ~$7,500 of borrow capacity (or surplus withdrawable collateral if already borrowing).
2. Seller lists NFT `A` on a marketplace for, e.g., $9,000, pricing in the unencumbered collateral.
3. Buyer signs/submits the purchase transaction.
4. Seller sees the pending `transfer`/`transfer_from` and front-runs it with `controller::borrow(seller, A, [(debt_asset, max_amount)], Some(seller))` — the post-borrow check only requires HF ≥ 1 and the min-borrow-collateral floor, so the borrow succeeds — and optionally `withdraw` for any excess collateral above the borrow floor.
5. The marketplace `transfer` executes; buyer receives account `A` loaded with max debt, collateral locked, and effectively zero extractable value, while the seller keeps both the borrowed tokens and the $9,000 sale price.

Delegate grants lapse on transfer, but that does not help the buyer — the damage is done by the *owner* before the transfer [6](#0-5) .

### Impact Explanation
Theft of user funds. The buyer pays market price for a position whose extractable economic value (borrow headroom and/or surplus collateral) was drained in the same ledger sequence. The loss equals the account's remaining borrow capacity plus withdrawable excess collateral — bounded only by LTV parameters, not by anything the buyer can check, since the account state changes between the buyer's quote time and settlement. The seller's profit is strictly additive: drained tokens + sale price. This is identical in effect to the reference report's honeypot (minting all EUROs then collecting the NFT sale price).

### Likelihood Explanation
Requires only that position NFTs are traded on external marketplaces — which is the documented purpose of the NFT design ("wallets, indexers, and marketplaces can read and move it with no protocol-specific tooling" [7](#0-6) ). Any overcollateralized or under-borrowed listed position is a target. Soroban transaction ordering makes mempool-style front-running of a signed purchase feasible for the seller (who is a party to the sale and sees the pending transfer). No privileged access, oracle manipulation, or timing luck beyond ordering is needed. Medium likelihood: it requires a victim buying an NFT without simulating account state at execution, but the protocol provides no tool to prevent it.

### Recommendation
Introduce a sale/escrow-aware mechanism, e.g.:

- An owner-initiated `lock_account`/`freeze_account` flag that blocks `borrow`, `withdraw`, and all strategies while set, so a seller can credibly commit a static position before listing; or
- A controller-mediated escrow transfer (`transfer_and_settle`) that atomically moves the NFT and delivers sale proceeds only if account debt/collateral matches a buyer-declared expected state (e.g., hash of positions or max total borrow USD); or
- At minimum, document prominently that buyers must simulate `get_account_positions`/`get_total_borrow_usd` inside the same transaction as the transfer (e.g., via a wrapper contract that asserts account state before calling `transfer_from`), since a plain marketplace transfer provides no such guarantee.

### Proof of Concept
Conceptual Soroban sequence (mirrors the harness style in `tests/test-harness`):

```rust
// Setup: seller ALICE owns account `a` with 10_000 USDC supplied, 0 debt.
t.supply(ALICE, "USDC", 10_000.0);
let a = t.account_id(ALICE);

// Marketplace listing: buyer BOB agrees to buy NFT `a`.
// Front-run: ALICE borrows max ETH against the collateral, paid to herself.
let eth = hub_asset(t.resolve_asset("ETH"));
t.ctrl_client().borrow(
    &alice, &a,
    &vec![&t.env, (eth.clone(), max_ltv_amount)],
    &Some(alice.clone()),   // proceeds leave with the seller
);
// Optionally also withdraw excess collateral to self within HF >= 1.

// Settlement executes anyway:
position_nft::PositionNftClient::new(&t.env, &t.position_nft)
    .transfer(&alice, &bob, &u32::try_from(a).unwrap());

// Result: BOB owns `a`, which is now near HF == 1 with max debt;
// ALICE keeps the borrowed ETH plus the sale proceeds.
assert_eq!(t.nft_owner_of(a), bob);
assert!(t.borrow_balance_raw_for(a, "ETH") > 0);
```

All steps use only owner-reachable entrypoints (`borrow`, `withdraw`, `position-nft::transfer`) with no privileged role, and each is individually valid under existing checks — the defect is the absence of any mechanism binding the account's state to the sale.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}
