## Analysis Summary

I looked for an on-chain analog to "a helper claims to be a safe ERC20 wrapper but breaks on non-standard tokens that don't return a `bool`." I found a structurally identical assumption in `ERC20Transactor` (the XCM `TransactAsset` implementation for ERC20 tokens used by Asset Hub Westend), which ABI-decodes the return data of an arbitrary, permissionlessly-registered `transfer()` call as `bool` and treats any decode failure as a hard error.

I was not able to fully confirm within budget whether `Config::TransactionalProcessor` on Asset Hub Westend is `FrameTransactionalProcessor` (storage-transactional) — the grep only located the type alias occurrence, not its resolved value — but tests in `polkadot/xcm/xcm-executor/src/lib.rs` and `polkadot/xcm/pallet-xcm/src/tests/mod.rs` (e.g. `incomplete_execute_reverts_side_effects`, `partial_fail_withdraw_asset_preserves_total_issuance`) together with PR `pr_11910.prdoc` ("xcm-executor: rollback all side-effects of partial instruction execution") strongly suggest storage-level rollback is the intended and tested behavior for a failed `WithdrawAsset`/`DepositAsset` instruction. Given that, this analog most plausibly manifests as a **denial-of-service** rather than fund loss — I could not construct a fund-loss PoC with confidence, so I report it at the DoS severity that matches the original report's actual impact class.

### Title
Non-standard ERC20 tokens (no boolean `transfer` return) permanently break XCM asset transacting - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implement XCM's `TransactAsset` trait for arbitrary contracts matched by `ERC20Matcher` (any local `AccountKey20` location, i.e. any deployed `pallet-revive` contract can be transacted as a fungible asset via XCM). Both functions call the target contract's `transfer(address,uint256)` via `pallet_revive::Pallet::<T>::bare_call` and unconditionally require the return data to ABI-decode as `bool` via `IERC20::transferCall::abi_decode_returns_validate`. [1](#0-0) [2](#0-1) 

This is exactly the bug class of the referenced report: assuming every ERC20-like contract returns a compliant `bool` from `transfer`, when many real, non-malicious tokens (most famously USDT-style tokens) return no data at all on success.

### Finding Description
`ERC20Matcher` matches **any** local location of the form `(0, [AccountKey20{..}])` — i.e. any contract address deployed via `pallet-revive` — and converts it directly to an `H160` asset id with no allowlist/registry check: [3](#0-2) 

`ERC20Transactor` is wired into the live `AssetTransactors` tuple on Asset Hub Westend: [4](#0-3) 

When a user submits an XCM program (e.g., via `pallet_xcm::execute` or a `transfer_assets`/reserve-transfer with an asset id pointing at such a contract) that withdraws or deposits this "asset", the transactor calls `transfer()` on the target contract and requires the contract to return ABI-encoded `true`/`false`. Any contract that:
- returns no data on success (e.g. classic non-standard ERC20 tokens), or
- returns data that isn't exactly 32 bytes of `bool`,

causes `abi_decode_returns_validate` to fail, and the transactor unconditionally returns `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` — even though the underlying `transfer()` call executed successfully and (from the contract's own semantics) actually moved the balance.

### Impact Explanation
Any XCM message attempting to withdraw or deposit an ERC20-style asset whose `transfer()` does not return an ABI-encoded `bool` will deterministically fail with `FailedToTransactAsset`, regardless of correct approvals/balances/fees. This denies XCM-based asset movement for an entire, non-trivial class of otherwise valid tokens (the most widely deployed non-standard-return pattern in the ecosystem), a purely input-driven and reproducible failure with no privileged actor required — mirroring the original report's "a non standard erc20 token would always raise error... there's never a counterpart deposit" impact.

Whether this also produces a **loss of funds** (rather than pure failure) depends on whether the runtime's `Config::TransactionalProcessor` actually rolls back the underlying `pallet-revive` contract-storage mutation performed by `bare_call` together with the XCM holding/fees registers. I found strong evidence (tests and PR `11910` prdoc) that storage-transactional rollback of side effects on `WithdrawAsset`/`DepositAsset` failure is the intended and tested behavior, which would prevent fund loss and reduce this to a Medium-severity denial-of-service. I could not conclusively verify the concrete `TransactionalProcessor` type resolved for Asset Hub Westend's `XcmConfig` within the available tool budget, so I am not asserting a fund-loss claim — only the demonstrable input-validation/assumption defect and its DoS consequence.

### Likelihood Explanation
High for the DoS component: it requires no privilege, only an XCM message (or any user-facing extrinsic that routes through `pallet_xcm`) naming an asset location that resolves via `ERC20Matcher` to a real deployed contract with a non-boolean-returning `transfer`. Since `ERC20Matcher` accepts any local `AccountKey20`, an attacker or an honest integrator can trivially trigger this by deploying (or having deployed) such a contract and referencing it in an XCM asset.

### Recommendation
Do not treat ABI-decode failure of the `transfer()` return value as equivalent to a definite transfer failure. Follow the "safe ERC20" pattern used by OZ's `SafeERC20`: treat an empty return buffer as success (when the call did not revert), and only decode/validate a `bool` when return data is non-empty, e.g.:
```rust
if return_value.did_revert() {
    Err(...)
} else if return_value.data.is_empty() {
    // non-standard compliant token, `transfer` succeeded
    Ok(...)
} else {
    match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) { ... }
}
```
Additionally, consider whether `ERC20Matcher` should permit XCM-transacting for *arbitrary* deployed contracts at all, or whether it should require an allowlist/registration step analogous to `pallet-assets`' `force_create`, to reduce the blast radius of unexpected contract behavior in the asset-transacting path.

### Proof of Concept
Not executed. Reasoning: the code path is reachable through production runtime wiring (Asset Hub Westend `AssetTransactors`), and the failure condition (`abi_decode_returns_validate` failing on non-`bool` return data) is directly readable from `erc20_transactor.rs` lines 191–194 and 276–297 without requiring any mock or privileged setup. A concrete integration reproduction would deploy a `pallet-revive` contract whose `transfer(address,uint256)` returns no data (compiles to empty return buffer, no revert), register/reference it as an XCM asset via `ERC20Matcher`, and submit a `pallet_xcm::execute` with `WithdrawAsset`/`DepositAsset` naming that asset; expected result is `Outcome::Incomplete` with `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")` on every attempt. I did not run this reproduction, and I could not confirm from the index whether the underlying contract-storage transfer effect is rolled back (no fund loss) or persists (fund loss) in this exact runtime configuration — flagging this as the key open question for further investigation before treating this as more than a Medium-severity DoS.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.

	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
