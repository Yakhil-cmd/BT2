## Title
Fire-and-forget private payment delivery ignores `ifOk`/`ifError` results, allowing broadcast of the payment before delivery is confirmed - (File: `wallet_general.js`, `device.js`)

### Summary
The underlying bug class in the referenced report is that a value-transfer call's return/result is not checked, so the caller proceeds as though the operation succeeded even when it silently failed. The reachable analog in ocore is in the private-payment delivery path: `sendPrivatePayments()` in `wallet_general.js` calls `device.sendMessageToDevice()` with no-op `ifOk`/`ifError` handlers, so the caller (the payment-composing code in `wallet.js`) treats the "send" as complete based only on the message being queued to the local `outbox` table, never on whether delivery to the recipient actually succeeded.

### Finding Description
`sendPrivatePayments()` builds a body with the private-element chains and calls `device.sendMessageToDevice`, but discards the delivery result: [1](#0-0) 

`sendMessageToDevice` → `sendMessageToHub` → `reliablySendPreparedMessageToHub` only fires `onSaved` once the message is written to the local `outbox` table; the actual network delivery (`sendPreparedMessageToHub`/`sendPreparedMessageToConnectedHub`) happens afterward and asynchronously, and its `ifOk`/`ifError` results are the ones being discarded by `sendPrivatePayments`: [2](#0-1) [3](#0-2) 

This function is used as the `cb` inside `sendMultiPayment`'s `preCommitCb` for private assets, i.e. it is invoked from the pre-commit hook right before the paying unit is validated, saved, and broadcast to the network: [4](#0-3) 

Because `onSaved` (not `ifOk`) is what gates continuation of the commit flow, the "success" signal used by the whole payment flow only reflects that the private-payment chain was written to `outbox`, not that the private elements were actually delivered to the recipient's device. If delivery to the hub subsequently fails (bad pubkey handshake, hub rejects, temp-pubkey verification failure, etc.), the failure is only recorded via `db.query("UPDATE outbox SET last_error=?...")` and retried later by `resendStalledMessages` — it is never surfaced to `sendMultiPayment`'s caller, and the on-chain unit carrying the private payment has already been broadcast.

### Impact Explanation
For private (blinded) assets, the recipient can only spend the received coins if they obtain the actual private payload (inputs, outputs, blinding factors) out-of-band, since this data is not published on the DAG. If delivery to the recipient silently and repeatedly fails (e.g., persistent hub issue, stale pairing, unreachable correspondent), the sender's software reports the payment as successfully sent (the unit is stable and spends the sender's funds), while the recipient never receives the information needed to redeem the transferred private asset. This effectively freezes/loses the transferred value from the recipient's perspective while the sender's UI/API shows no error — the same "incorrect accounting due to unchecked result" failure mode described in the report, applied to ocore's private-payment transfer mechanism instead of ERC-20 `transfer`.

### Likelihood Explanation
This does not require a malicious peer or hub — it is reachable by any private-asset payment sender/AA/private-payment counterparty whenever the hub or network temporarily misbehaves, the recipient's `correspondent_devices` entry is stale, or the temp-pubkey exchange fails. The retry loop (`resendStalledMessages`) mitigates but does not eliminate the issue for the caller, since the caller's flow has already moved on with the impression of success at the point of `onSaved`.

### Recommendation
In `sendPrivatePayments()` (and any similarly structured private-payment/private-element forwarding calls), propagate the actual `ifOk`/`ifError` result of `device.sendMessageToDevice` to the caller (or expose both "saved" and "delivered" states distinctly) rather than swallowing them with no-op handlers, and have `sendMultiPayment`'s pre-commit flow surface persistent delivery failures to the application/user instead of treating queuing as final success.

### Proof of Concept
1. Pair with a recipient device whose `correspondent_devices.hub` is stale or unreachable, or whose `pubkey` no longer matches (temp-pubkey verification will fail in `sendPreparedMessageToConnectedHub`).
2. Send a private asset payment via `wallet.sendMultiPayment` with `recipient_device_address` set.
3. Observe `sendPrivatePayments` returns success (`onSaved`) immediately once the row is inserted into `outbox`; `sendMultiPayment`'s `ifOk` callback fires and the unit is broadcast, reporting the payment as sent.
4. `sendPreparedMessageToHub`/`sendPreparedMessageToConnectedHub` fails later; the error is only written to `outbox.last_error` and retried, with no propagation back to the original `handleResult` callback of `sendMultiPayment`.
5. If the failure persists (e.g., recipient never re-pairs, or hub configuration issue is not automatically fixed by retries) the recipient never learns the private payload; funds are effectively unspendable by the recipient despite the sender treating the operation as fully successful.

function sendPreparedMessageToConnectedHub(ws, recipient_device_pubkey, message_hash, json, callbacks){
	network.sendRequest(ws, 'hub/get_temp_pubkey', recipient_device_pubkey, false, function(ws, request, response){
		function handleError(error){
			callbacks.ifError(error);
			db.query("UPDATE outbox SET last_error=? WHERE message_hash=?", [error, message_hash], function(){});
		}
		if (!response)
			return handleError("empty response");
		if (response.error)
			return handleError(response.error);
		var objTempPubkey = response;
		if (!objTempPubkey.temp_pubkey || typeof objTempPubkey.temp_pubkey !== 'string' || !objTempPubkey.pubkey || !objTempPubkey.signature)
			return handleError("missing fields in hub response");
		if (objTempPubkey.pubkey !== recipient_device_pubkey)
			return handleError("temp pubkey signed by wrong permanent pubkey");
		try {
			if (!ecdsaSig.verify(objectHash.getDeviceMessageHashToSign(objTempPubkey), objTempPubkey.signature, objTempPubkey.pubkey))
				return handleError("wrong sig under temp pubkey");
		}
		catch (e) {
			return handleError("temp pub key hash failed: " + e.toString());
		}
		if (!isValidPubKey(objTempPubkey.temp_pubkey))
			return handleError("invalid temp pubkey");
		try {
			var objEncryptedPackage = createEncryptedPackage(json, objTempPubkey.temp_pubkey);
		}
		catch (e) {
			return handleError("failed to encrypt to temp pubkey: " + e.toString());
		}
		var recipient_device_address = objectHash.getDeviceAddress(recipient_device_pubkey);
		var objDeviceMessage = {
			encrypted_package: objEncryptedPackage,
			to: recipient_device_address,
			pubkey: objMyPermanentDeviceKey.pub_b64 // who signs. Essentially, the from again. 
		};
		objDeviceMessage.signature = ecdsaSig.sign(objectHash.getDeviceMessageHashToSign(objDeviceMessage), objMyPermanentDeviceKey.priv);
		network.sendRequest(ws, 'hub/deliver', objDeviceMessage, false, function(ws, request, response){
			if (response === "accepted"){
				db.query("DELETE FROM outbox WHERE message_hash=?", [message_hash], function(){
					callbacks.ifOk();
				});
			}
			else
				handleError( response?.error || ("unrecognized response: " + util.inspect(response, { depth: 5 })) );
		});
	});
