The reported CVE-2026-5760 concerns SGLang's public HTTP `/v1/rerank` endpoint rendering an attacker-uploaded model's `tokenizer.chat_template` via an unsandboxed `jinja2.Environment()`, allowing arbitrary attacker-controlled Jinja2 syntax to execute server-side. The required analog would be a real, non-privileged, network-reachable entry point in the polkadot-sdk (signed extrinsic, permitted XCM message, contract call, or public RPC) that feeds attacker-controlled data into an unsandboxed template/expression engine for server-side rendering.

Searching the codebase, the only template-engine usages found (`tera`, `handlebars`, EJS) are confined to local developer tooling: [1](#0-0)  and [2](#0-1)  render local Handlebars weight-report templates from `benchmarking-cli`, driven only by local CLI arguments/paths supplied by the person running the CLI on their own machine. Similarly, the release-note generation tooling uses `tera` purely on repo-local files: [3](#0-2)  and explicitly documents that untrusted prdoc content is substituted only *after* `tera` rendering to avoid template injection: [4](#0-3) . None of these are reachable via a signed extrinsic, XCM message, contract call, or any network-facing runtime/node entry point — they are local build/benchmarking scripts with no attacker-controlled remote input path, unlike SGLang's public `/v1/rerank` HTTP endpoint.

No other template/expression-rendering-on-untrusted-input pattern (Jinja2-equivalent) was found reachable from a permissionless runtime entry point (extrinsic, XCM, contract call, or bridge message) in FRAME, `pallet-contracts`/`pallet-revive`, `pallet-xcm`, or the bridges/Snowbridge code. Without such a reachable, non-privileged attacker entry that funnels attacker data into unsandboxed template evaluation, there is no demonstrable Polkadot SDK analog to this CVE.
