### Title
Cross-organization webhook signature confusion allows unauthorized cross-repository commit-status writes and forged CI-gated deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to authenticate a webhook based on an **unverified field of the very payload being verified** (`repository.owner.login` / `organization.login`), rather than binding it to the resource the handler will actually act on. In a multi-tenant Shipit installation (`docs/setup.md` "Using Multiple GitHub Applications", `test/dummy/config/secrets_double_github_app.yml`), each GitHub organization has its own `webhook_secret`. A webhook whose HMAC is valid for organization A's secret is accepted as long as the payload's `repository_owner` field says "A" — but nothing then constrains which `Commit`/`Stack` the event handler is allowed to touch. `StatusHandler`, in particular, resolves target records with a completely unscoped `Commit.where(sha: params.sha)` lookup across the entire instance. This breaks the intended binding: `organization that authenticated the webhook == repository/commit actually written to`.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
``` [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up a **per-organization** `webhook_secret` from `secrets.github`, supporting the documented multi-org configuration where distinct customers/orgs each have independent GitHub Apps and secrets: [3](#0-2) [4](#0-3) [5](#0-4) 

So the signature check only proves "the body was signed with the secret belonging to the org named in the body." It never proves that the org whose secret matched is actually the owner of the resource the event will mutate. Once past `verify_signature`, `WebhooksController#create` dispatches the entire raw JSON body to handlers, unmodified: [6](#0-5) 

`StatusHandler` (event `status`) then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

This lookup is **global**, unscoped by repository or organization — `Commit.where(sha:)` will match any commit with that SHA anywhere in the Shipit instance, regardless of which org's secret authenticated the request.

Attack: an attacker who legitimately controls GitHub organization "OrgTwo" (a real tenant with its own valid `webhook_secret` configured in this Shipit instance, per the documented multi-org setup) can:
1. Compute a valid `X-Hub-Signature` for organization `OrgTwo`'s webhook secret over an arbitrary payload.
2. Set `repository.owner.login` = `"OrgTwo"` (so `verify_signature` selects and successfully validates against OrgTwo's own secret — which the attacker legitimately possesses).
3. Set `event: status`, `sha` = the SHA of a commit belonging to an unrelated stack/repository under a completely different organization ("OrgOne"), and `state: success`.

The forged status is accepted and written via `commit.create_status_from_github!`, because `StatusHandler` never checks that the commit's `stack`/`repository` belongs to the organization that authenticated the webhook — only the SHA is matched.

### Impact Explanation
`Commit#deployable?` and `Commit#schedule_continuous_delivery` gate deploy eligibility directly on the injected status:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end

def schedule_continuous_delivery
  return unless deployable? && stack.continuous_deployment? && stack.deployable?
  ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)
end
``` [8](#0-7) [9](#0-8) 

By injecting a forged `success` status for a commit in a repository/organization the attacker does not control, an attacker with only their own tenant's webhook credentials can flip an otherwise CI-blocked commit into "deployable," triggering `ContinuousDeliveryJob` for a stack owned by a different organization on this shared Shipit instance — an unauthorized deploy driven by cross-tenant / cross-repository writes. This is a Critical-tier impact per the specified rules ("cross-repository writes" / "an unauthorized deploy").

The same root cause (signature-selection field != resource being written) also affects `PushHandler`, `CheckSuiteHandler`, and the PR handlers, which key off `repository.full_name`/`repository.owner.login` inside the payload rather than the org whose secret validated the request — but those are at least scoped by `Repository.from_github_repo_name`, whereas `StatusHandler`'s bare `Commit.where(sha:)` has no repository scoping whatsoever, making it the most directly exploitable path.

### Likelihood Explanation
Requires operating (or attacking) a multi-organization Shipit deployment where multiple independent GitHub orgs are configured with distinct `webhook_secret`s, as explicitly documented and supported (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`). Within that officially supported topology, the attacker only needs their own legitimate tenant's webhook secret (no privileged Shipit account, no `ApiClient` token, no GitHub write access to the target repo) — satisfying the "unprivileged attacker" requirement. The commit SHA to target must be known/guessed, which is feasible since commit SHAs are visible in public GitHub history, Shipit's public UI, or CCMenu status pages.

### Recommendation
Bind the verified webhook's organization to the resource the handler is permitted to modify:
- After signature verification succeeds for organization `O`, pass `O` (not payload-derived data) into the handler pipeline, and require handlers (especially `StatusHandler`) to only mutate `Commit`/`Stack` records whose `Repository#owner` equals the verified `O`.
- Specifically fix `StatusHandler#process` to filter via `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: verified_organization })`, mirroring the scoping already used by `Handler#stacks`/`Repository.from_github_repo_name`.
- Apply the same "verified org must equal repository owner" constraint uniformly across all webhook handlers, not just derive routing from `params.dig('repository', ...)`.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls `OrgTwo` and knows `OrgTwo`'s `webhook_secret` (legitimately, as the GitHub App installer for that org).
3. Attacker identifies a commit SHA `S` belonging to a stack under `OrgOne/some-repo` (e.g., visible via Shipit's public deploy UI or GitHub).
4. Attacker builds payload:
```json
{
  "sha": "S",
  "state": "success",
  "repository": { "owner": { "login": "OrgTwo" } }
}
```
5. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgTwo_webhook_secret, body)` and POSTs to `/webhooks` with header `X-Github-Event: status`.
6. `verify_signature` selects `Shipit.github(organization: "OrgTwo")` and successfully validates the signature.
7. `StatusHandler#process` executes `Commit.where(sha: "S")`, finds the `OrgOne` commit, and calls `create_status_from_github!`, injecting a fabricated `success` status.
8. If the `OrgOne` stack has `continuous_deployment` enabled and was otherwise CI-blocked, `Commit#schedule_continuous_delivery` now fires `ContinuousDeliveryJob`, causing an unauthorized deploy of `OrgOne`'s stack triggered entirely by `OrgTwo`'s credentials.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
