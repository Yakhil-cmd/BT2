## Title
Missing synchronization around private-payment double-spend checks allows concurrent chain saves to bypass the overlap check - ([File: private_payment.js])

## Summary
The CVE describes a Linux md/raid5 race where a "check for overlap" and the corresponding "clear the overlap flag / unlock" are not protected by the same lock, letting a second writer observe a stale state and proceed as if no conflict existed. The same *check-then-act-without-holding-a-shared-lock* pattern exists in ocore's private-payment save path: unlike public unit validation/save (which is strictly serialized by the `handleJoint` and `write` mutexes), the private-payment validate-and-save path opens its own DB connection/transaction and performs its double-spend check with no application-level mutex at all, and the caller in `network.js` even has the in-flight-unit guard explicitly commented out.

## Finding Description
For publicly broadcast units, every validate+save is serialized:
- `composer.js` / `divisible_asset.js` / `indivisible_asset.js` acquire `mutex.lock('handleJoint')` before calling `validation.validate()`, and the unlock happens only after `writer.saveJoint()` completes: [1](#0-0) 
- `writer.saveJoint()` additionally serializes all DB writes with its own `"write"` mutex: [2](#0-1) 
- `network.js`'s `handleJoint()` guards against concurrent handling of the *same* unit via `assocUnitsInWork[unit]`, held for the full duration of validation+save: [3](#0-2) 

The private-payment path lacks this protection. `private_payment.js`'s `validateAndSavePrivatePaymentChain()` takes its own DB connection and its own `BEGIN`/`COMMIT`, with **no `mutex.lock` call anywhere** in the function: [4](#0-3) 

It performs a "check if duplicate" `SELECT` on `outputs`, and only rejects when the row content is byte-identical to what is already stored; anything else falls straight through to `assetModule.validateAndSavePrivatePaymentChain`: [5](#0-4) 

That delegate (`indivisible_asset.js` / `divisible_asset.js`) calls `validation.validatePayment()`, which performs the actual double-spend detection via `checkForDoublespends()` — a plain `SELECT` against the `inputs` table followed later by an `INSERT`, with no lock spanning the read-then-write window: [6](#0-5) [7](#0-6) 

For light clients specifically, a conflicting record found by this query is unconditionally treated as an error and rejected — i.e. the code assumes this check is reliable and does not tolerate a genuine overlap: [8](#0-7) 

The problem is the caller side in `network.js`. `handleOnlinePrivatePayment()` explicitly has its `assocUnitsInWork` guard commented out for the "known unit" branch, so nothing prevents two concurrent invocations for the same unit/private chain from both calling `privatePayment.validateAndSavePrivatePaymentChain()` at once: [9](#0-8) 

`handleSavedPrivatePayments()` goes further and deliberately fans out with `async.each`, its own comment stating it "handle[s] different chains in parallel," with only a queue-level `"saved_private"` lock around the *selection* of rows, not around each chain's validate+save: [10](#0-9) 

Because each concurrent call opens its own connection/transaction, the `checkForDoublespends` `SELECT` in one transaction cannot see the uncommitted `INSERT INTO inputs` of a sibling transaction that is spending the very same hidden source output to a different address. Both transactions observe "no conflicting record," both pass validation, and both commit — mirroring the raid5 bug where `test_and_clear_bit`/`set_bit` on the shared flag executed outside a common critical section let a second thread believe there was no overlap.

## Impact Explanation
A double-spend of a private (hidden) output is a direct unauthorized-spending / stable-output double-spend scenario: the same private coin can be validly assigned to two different recipients if the two conflicting private-payment messages (e.g., one relayed via hub, one sent directly by a peer/paired device, or two chains delivered to `handleSavedPrivatePayments` in the same batch) are processed concurrently. This is reachable by any unprivileged private-payment counterparty or paired device sending private payment chains — exactly the class of actor allowed by the scope rules (private payment chains / wallet & contract message handling). Because private assets cannot be cross-checked against the public DAG the way public double-spends are (light clients unconditionally reject the *second-seen* attempt rather than resolving via the DAG), a successfully raced pair of transactions results in a hard double-spend rather than a benign non-serial marking.

## Likelihood Explanation
Triggering the race requires only sending (or relaying) two private-payment messages that reference the same source output at roughly the same time — well within the capability of a malicious payment counterparty or a compromised/malicious paired device, with no special privileges needed. The explicit removal of the `assocUnitsInWork` guard (visible as commented-out code) and the explicit "handle different chains in parallel" `async.each` in `handleSavedPrivatePayments` make the race window realistically hittable rather than purely theoretical, though winning the exact timing window (both `SELECT`s completing before either `INSERT`/`COMMIT`) still requires some effort or repeated attempts.

## Recommendation
Serialize private-payment validate-and-save the same way public joints are serialized: acquire a mutex keyed on the unit (or globally, e.g. `mutex.lock(['handleJoint'])`/a dedicated `private_payment` key) in `private_payment.js`'s `validateAndSavePrivatePaymentChain()` before opening the connection, and hold it until the transaction commits or rolls back. Remove the parallel (`async.each`) processing in `network.js#handleSavedPrivatePayments` for chains that could plausibly spend the same source output, or key the lock per source-output rather than only per outer batch. Restore (or replace with an equivalent unit-level guard) the `assocUnitsInWork` protection in `handleOnlinePrivatePayment()`.

## Proof of Concept
1. Attacker (or two colluding light-wallet peers/paired devices) constructs two private-payment chains that both spend the same private output (same `src_unit`/`src_message_index`/`src_output_index`) but pay two different destination addresses.
2. Chain A is delivered via `handleOnlinePrivatePayment` from peer connection 1; Chain B is delivered at nearly the same time via peer connection 2 (or both arrive as unhandled rows and get picked up together by `handleSavedPrivatePayments`'s `async.each`).
3. Both invocations reach `private_payment.js -> validateAndSavePrivatePaymentChain`, each opening its own DB connection/transaction with no shared mutex.
4. Both run `checkForDoublespends` (`validation.js`) before either has committed its `INSERT INTO inputs`; both see zero conflicting rows and both accept.
5. Both transactions commit: the same private output is now recorded as spent to two different addresses — a successful double-spend.

function checkForDoublespends(conn, type, sql, arrSqlArgs, objUnit, objValidationState, onAcceptedDoublespends, cb){
	conn.query(
		sql, 
		arrSqlArgs,
		function(rows){
			if (rows.length === 0)
				return cb();
			var arrAuthorAddresses = objUnit.authors.map(function(author) { return author.address; } );
			async.eachSeries(
				rows,
				function(objConflictingRecord, cb2){
					if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
						throw Error("conflicting "+type+" spent from another address?");
					if (conf.bLight) // we can't use graph in light wallet, the private payment can be resent and revalidated when stable
						return cb2(objUnit.unit+": conflicting "+type);

						if (bIncluded){

				},
				function(err){
					if (err)
