This is a genuine, provable local finding.

### Title
K-of-N MultiKey/MultiEd25519 threshold can be satisfied by a single signer via duplicate public keys, breaking the multisig admission invariant - (File: types/src/transaction/authenticator.rs)

### Summary
`TransactionAuthenticator::MultiEd25519` and `TransactionAuthenticator::SingleSender { AccountAuthenticator::MultiKey }` are supposed to enforce that at least `threshold`/`signatures_required` *independent* signers approve a transaction. Neither the Rust constructors nor the Move-side deserializers reject public-key sets containing duplicate keys, so a `t`-of-`n` account can be configured (or, if rotated, end up) with the same key repeated across multiple slots. A holder of that one key can then satisfy the entire threshold alone by supplying the same signature (or independently generated signatures over the same message, since Ed25519/ECDSA signing is deterministic or can simply be copied) at each of the duplicate indices, causing the "multi-signer" transaction to pass authenticator verification despite only one real signer's authorization.

### Finding Description
- `MultiEd25519PublicKey::new` only checks `threshold == 0`, `num_of_public_keys < threshold`, and `num_of_public_keys > MAX_NUM_OF_KEYS`; it never checks for duplicate entries in `public_keys: Vec<Ed25519PublicKey>`. [1](#0-0) 
- `MultiKey::new` (Rust, `types/src/transaction/authenticator.rs`) performs the analogous checks (`signatures_required > 0`, `len <= MAX_NUM_OF_SIGS`, `len >= signatures_required`) with no de-duplication of `public_keys: Vec<AnyPublicKey>`. [2](#0-1) 
- The Move-side `multi_key::new_multi_key_from_single_keys` and `deserialize_multi_key` similarly only validate count/threshold bounds, never key uniqueness. [3](#0-2) 
- At verification time, `MultiEd25519Signature::verify_arbitrary_msg` only checks bitmap/threshold/signature-count consistency and then independently verifies each signature against `public_key.public_keys[bitmap_index]`; it never checks that the referenced public keys across satisfied indices are distinct. [4](#0-3) 
- `MultiKeyAuthenticator::to_single_key_authenticators`/`verify` likewise iterate per-index and verify each `(public_key, signature)` pair independently, with no cross-index uniqueness check. [5](#0-4) 

The authentication key derived from the public-key set is a hash of the whole serialized set (`to_bytes`/`to_authentication_key`), so an account can legitimately be created with, e.g., `public_keys = [K, K, K]`, `threshold = 2`. Anyone holding `K` can produce two (or three) valid signatures over the *same* message and place them at two distinct bitmap indices, satisfying "2-of-3" with a single key. This directly breaks the "K-of-N" trust assumption the transaction/account model advertises for these authenticator schemes — the same class of design flaw as the DEX bug (a component silently fails to enforce an invariant it's advertised to enforce), but here the corrupted binding is the *approval set*, not a numeric range.

### Impact Explanation
This allows a transaction that should require independent approval from `t` distinct key holders to be authorized by only one, effectively defeating the security guarantee of MultiEd25519/MultiKey accounts (used for e.g. shared custody, governance-style multi-signer EOAs, or `SingleSender`-wrapped multi-key auth). Any account owner who (accidentally or via social engineering of a co-signer's key-rotation flow) ends up with duplicate keys in their `t`-of-`n` set loses the multi-party protection entirely, letting a single compromised or malicious signer execute state-changing transactions "as" the full committee. This is an authenticator/approval-set validation defect at the transaction admission boundary — accepting the wrong (insufficiently diverse) approval set.

### Likelihood Explanation
Likelihood depends on how the public-key set is constructed/rotated by SDKs, wallets, or governance flows. If any code path (SDK, CLI, on-chain key-rotation) does not itself enforce uniqueness before submitting the raw `MultiKey`/`MultiEd25519PublicKey` bytes, an attacker with influence over one signer's registered key (e.g., a co-signer proposing/rotating to a key equal to another existing signer's key, or a service that lets users self-select public keys for a shared account) can silently degrade the account's security. It requires either social engineering of the key-set construction, or a misconfigured setup tool, but the core cryptographic library and Move framework provide no defense-in-depth here — the check is entirely absent, not merely bypassable.

### Recommendation
Enforce uniqueness of public keys when constructing/validating `MultiEd25519PublicKey` (Rust), `MultiKey` (Rust and Move `multi_key.move`), and correspondingly in `VerifyInput` validation for the API types (`MultiEd25519Signature`, `MultiKeySignature` in `api/types/src/transaction.rs`). Reject construction/deserialization if any two entries in `public_keys` are byte-identical, in both the native constructors and the on-chain Move deserializers, so that "K distinct signatures" cannot be produced from fewer than K distinct keys.

### Proof of Concept
1. Construct `MultiEd25519PublicKey::new(vec![K, K, K], 2)` (or the `MultiKey` equivalent) — succeeds today with no duplicate check. [1](#0-0) 
2. Derive the authentication key from this public-key set (`to_bytes`/hash) and fund/rotate an account to it.
3. Using only the single private key for `K`, sign the transaction message twice (or reuse the identical signature) and place it at bitmap indices 0 and 1.
4. Submit via `TransactionAuthenticator::MultiEd25519 { public_key, signature }` (or the `MultiKey` `SingleSender` path); `verify_arbitrary_msg` / `MultiKeyAuthenticator::verify` accept it because each index is checked independently against `public_keys[bitmap_index]`, satisfying threshold 2 with one real signer. [6](#0-5) [7](#0-6) 

Note: I was not able to fully trace whether any upstream wallet/SDK code enforces key-set uniqueness before this point reaches the crypto library, since that would require checking every client that constructs these authenticators; the core library/framework code itself provides no such guard, which is the root cause identified here.

    fn verify_arbitrary_msg(
        &self,
        message: &[u8],
        public_key: &MultiEd25519PublicKey,
    ) -> Result<()> {
        // NOTE: Public keys need not be validated because we use ed25519_dalek's verify_strict,
        // which checks for small order public keys.
        match bitmap_last_set_bit(self.bitmap) {
            Some(last_bit) if (last_bit as usize) < public_key.public_keys.len() => (),
            _ => {
                return Err(anyhow!(
                    "{}",
                    CryptoMaterialError::BitVecError("Signature index is out of range".to_string())
                ))
            },
        };
        let num_ones_in_bitmap = bitmap_count_ones(self.bitmap);
        if num_ones_in_bitmap < public_key.threshold as u32 {
            return Err(anyhow!(
                "{}",
                CryptoMaterialError::BitVecError(
                    "Not enough signatures to meet the threshold".to_string()
                )
            ));
        }
        if num_ones_in_bitmap != self.signatures.len() as u32 {
            return Err(anyhow!(
                "{}",
                CryptoMaterialError::BitVecError(
                    "Bitmap ones and signatures count are not equal".to_string()
                )
            ));
        }
        let mut bitmap_index = 0;
        // TODO: Eventually switch to deterministic batch verification
        for sig in &self.signatures {
            while !bitmap_get_bit(self.bitmap, bitmap_index) {
                bitmap_index += 1;
            }
            let pk = public_key
                .public_keys
                .get(bitmap_index)
                .ok_or_else(|| anyhow::anyhow!("Public key index {bitmap_index} out of bounds"))?;
            sig.verify_arbitrary_msg(message, pk)?;
            bitmap_index += 1;
        }
        Ok(())
    }

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }

    /// Creates a new MultiKey public key from a vector of single key public keys and a number representing the number of signatures required to authenticate a transaction.
    public fun new_multi_key_from_single_keys(single_keys: vector<single_key::AnyPublicKey>, signatures_required: u8): MultiKey {
        let num_keys = single_keys.length();
        assert!(
            num_keys > 0,
            error::invalid_argument(E_INVALID_MULTI_KEY_NO_KEYS)
        );
        assert!(
            num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS,
            error::invalid_argument(E_INVALID_MULTI_KEY_TOO_MANY_KEYS)
        );
        assert!(
            (signatures_required as u64) <= num_keys,
            error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED)
        );
        MultiKey { public_keys: single_keys, signatures_required }
    }
