### Title
Unbounded in-memory read of attacker-controlled OCI attestation bundle layers causes memory-exhaustion denial of service - ([File: pkg/cmd/attestation/artifact/oci/client.go])

### Summary
`gh attestation verify oci://<image> --bundle-from-oci` fetches Sigstore bundle blobs directly from the OCI registry referenced by the user-supplied image URI. The registry is fully attacker-controlled (any host, image, and referrer manifest the user chooses to point `gh` at), yet the code reads the entire uncompressed layer into memory with an unbounded `io.ReadAll` call before doing anything else with it, mirroring the reported "unbounded input length" resource-exhaustion class (long password → unbounded hashing work) but here manifesting as unbounded memory allocation.

### Finding Description
In `GetAttestations`, for every OCI referrer manifest whose `ArtifactType` starts with `application/vnd.dev.sigstore.bundle`, `gh` retrieves the first layer and reads it fully into memory without any size cap: [1](#0-0) 

There is no `io.LimitReader`, `http.MaxBytesReader`, or any explicit size ceiling anywhere in the attestation OCI-fetch path (confirmed by searching the codebase for such guards — none exist in this package, unlike e.g. `pkg/cmd/skills/preview`, which does enforce a "size limit reached" cap on remote content). The `refImg.Layers()`/`layers[0].Uncompressed()` reader is produced by the `go-containerregistry` remote client talking directly to the registry named in the `oci://` URI supplied by the user, so an attacker who controls that registry (or a compromised/malicious mirror the user is pointed at) fully controls the byte stream returned to `io.ReadAll(layer0)`. A response of near-unbounded size (e.g. tens of gigabytes, potentially served via chunked transfer with no `Content-Length`) will be buffered entirely in the `gh` process's memory before the code even attempts `bundle.Bundle.UnmarshalJSON`.

This is reachable during the normal `gh attestation verify oci://<attacker-image> --owner ... --bundle-from-oci` flow documented and tested in this repo: [2](#0-1) [3](#0-2) 

### Impact Explanation
A malicious or compromised OCI registry/image referenced by the user can force the `gh` CLI process to allocate memory proportional to an attacker-chosen response size before any validation, JSON parsing, or Sigstore signature check occurs. On memory-constrained hosts (CI runners, containers) this can exhaust available memory and crash or hang the process — a straightforward, unauthenticated (from gh's perspective) denial of service against the invoking user's environment, directly analogous to the reported unbounded-password CPU/memory-exhaustion class.

### Likelihood Explanation
Likelihood is moderate: it requires the user to explicitly run `gh attestation verify` with `--bundle-from-oci` against an image URI that resolves to an attacker-influenced registry (e.g., a typosquatted registry, a compromised mirror, or any registry the user is told/tricked into pointing at). No credentials or special privileges beyond normal CLI use are needed by the attacker-controlled server; it need only respond to an OCI referrers/layer request with an oversized blob claiming the sigstore-bundle artifact type.

### Recommendation
Wrap the layer reader with a bounded reader (e.g., `io.LimitReader(layer0, maxBundleSize+1)`) before calling `io.ReadAll`, and reject/err out if the returned data hits or exceeds that cap (mirroring the pattern already used for skill preview content). Apply the same cap to any other unbounded `io.ReadAll(resp.Body)` calls that consume attacker-influenced HTTP/OCI responses in the attestation and extension download code paths, since none of them currently enforce a maximum size.

### Proof of Concept
1. Stand up a malicious/controlled OCI registry that serves an image whose digest has a `referrers` manifest containing an entry with `ArtifactType` beginning `application/vnd.dev.sigstore.bundle...`.
2. Have that referrer's first layer stream an arbitrarily large (e.g., multi-GB or unbounded chunked) response body instead of a legitimate small bundle.
3. Run: `gh attestation verify oci://<attacker-registry>/<image> --owner attacker --bundle-from-oci`.
4. Observe `GetAttestations` → `io.ReadAll(layer0)` in `pkg/cmd/attestation/artifact/oci/client.go` buffering the entire attacker-controlled stream into memory, driving the `gh` process's memory usage up until it is OOM-killed or the host becomes unresponsive, before any bundle validation ever occurs.
