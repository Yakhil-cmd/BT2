### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the mutated stack is looked up by `repository.full_name`, allowing any org's webhook secret to authorize writes against any other org's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify the HMAC with by reading `repository.owner.login` (or `organization.login`) from the untrusted, attacker-controlled JSON body, then verifies the raw bytes against that org's secret. `PushHandler` (via `Handler#repository_name`/`#stacks`) later resolves which `Stack` to mutate using a completely independent field, `repository.full_name`, with no check that the full name's owner matches the org whose secret authenticated the request.

### Finding Description
The claimed binding is: `organization_whose_secret_verified_signature == organization_owning(repository.full_name)`. Tracing the code shows this is never enforced.

- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)` to fetch that org's `GitHubApp`, then calls `github_app.verify_webhook_signature(signature, raw_post)` [1](#0-0) . `verify_webhook_signature` HMACs the raw bytes with that org's own `webhook_secret` [2](#0-1) .
- `#create` re-parses `request.raw_post` and dispatches to handlers, e.g. `PushHandler.call(params)` [3](#0-2) .
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` — a different, independently-attacker-controlled JSON field — and `#stacks` resolves `Repository.from_github_repo_name(repository_name)` to find the target stacks [4](#0-3) .
- `PushHandler#process` iterates the matched stacks on the given branch and calls `stack.sync_github(expected_head_sha: params.after)`, an attacker-controlled SHA [5](#0-4) .

Root cause: there is no code anywhere that cross-checks `repository.owner.login` (used to pick the verifying secret) against the owner implied by `repository.full_name` (used to select the stack to mutate). These are two independent reads of the same untrusted JSON body, and the app documents and supports exactly the "Using Multiple Github Applications" configuration where different orgs have distinct `webhook_secret`s [6](#0-5) , which is the precondition under which this divergence is exploitable — with a single global secret (`github_default_organization` nil) all orgs share one secret and the bug has no effect, since `Shipit.github(organization: repository_owner)` falls back to the single shared config [7](#0-6) .

**Attacker's exact request:** Attacker (owner of `Org-Evil`, which is a legitimately configured/installed GitHub App with its own `webhook_secret`) POSTs to `/webhooks` with `X-Github-Event: push`, a body where `repository.owner.login == "Org-Evil"` and `repository.full_name == "Org-Victim/prod-repo"`, `ref == "refs/heads/master"`, `after == "<attacker-chosen-sha>"`, and `X-Hub-Signature` computed as `HMAC-SHA1(Org-Evil's webhook_secret, raw_body)`.

**Exploit flow:** `verify_signature` computes `Shipit.github(organization: "Org-Evil")` and verifies successfully because the attacker legitimately knows `Org-Evil`'s secret and the org name in the payload matches the secret used — no error, `head(422)` is not triggered. `#create` proceeds to call `PushHandler`, which resolves the target repository via `full_name = "Org-Victim/prod-repo"`, finds Org-Victim's stack on `master`, and enqueues `GithubSyncJob`/triggers `stack.sync_github` with the attacker's chosen `expected_head_sha`.

**Why guards fail:** `drop_unhandled_event` only checks the event type is handled, not the payload contents [8](#0-7) . `verify_signature`'s only failure modes are a bad HMAC or an unknown org name — both of which the attacker satisfies correctly for `Org-Evil`. There is no `ExplicitParameters` validation, `Repository` model validation, or handler-level check tying `repository.owner.login` to `repository.full_name`'s owner segment.

### Impact Explanation
A request cryptographically authenticated only for `Org-Evil` results in a real write/side-effect against `Org-Victim`'s stack: enqueuing `GithubSyncJob` (and subsequently `CacheDeploySpecJob`) with an attacker-chosen `expected_head_sha` for a repository the attacker does not own and never authenticated against. This is a cross-tenant forged-webhook write, matching the Critical category ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). It is fully repeatable against any repository/org combination as long as the attacker controls (or is) an org with its own configured webhook secret in the same multi-tenant Shipit instance, and it is not limited to `push` — any handler that reads `repository.full_name` independently of `repository.owner.login` (pull_request handlers, status handler, check_suite handler) is subject to the same divergence.

### Likelihood Explanation
Requires the host to run the documented multi-organization GitHub App configuration (`secrets.github` keyed by org name, each with its own `webhook_secret`), which is an explicitly supported and documented deployment mode. The attacker only needs to be the legitimate owner/operator of one configured org's GitHub App installation (no privileged Shipit role, no knowledge of the victim org's secret) — this satisfies the "unprivileged attacker" constraints since owning a GitHub org and its own app installation requires no access to Shipit or Org-Victim's secrets. Cost is a single crafted HTTP POST with a signature computed from the attacker's own known secret. Fully repeatable.

### Recommendation
In `WebhooksController` or in `Handler`, after signature verification, enforce that the organization used to verify the signature equals the owner segment of `repository.full_name` (and of any other repository references in the payload) before dispatching to handlers — e.g., reject the request unless `repository_owner == payload.dig('repository', 'full_name')&.split('/')&.first`, or better, resolve `Repository.from_github_repo_name` first and confirm its owner matches `repository_owner` prior to acting.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` (multi-org secrets fixture, e.g. `secrets_double_github_app.yml` with `OrgOne`/`OrgTwo` each having distinct `webhook_secret`):

```ruby
test "cross-org webhook forges stack mutation" do
  # Org-Evil = OrgOne (attacker-controlled secret), Org-Victim = OrgTwo (victim's stack)
  victim_stack = shipit_stacks(:orgtwo_repo) # stack owned by OrgTwo/prod-repo, branch master

  payload = JSON.parse(payload(:push_master))
  payload["repository"]["owner"]["login"] = "OrgOne"   # verified org == attacker's own org
  payload["repository"]["full_name"] = "OrgTwo/prod-repo" # mutated repo == victim's
  payload["ref"] = "refs/heads/master"
  payload["after"] = "attackerchosen0000000000000000000sha1"
  body = payload.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "OrgOne-webhook-secret", body)

  @request.headers['X-Github-Event'] = 'push'
  @request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(
    job: GithubSyncJob,
    args: [stack_id: victim_stack.id, expected_head_sha: "attackerchosen0000000000000000000sha1"]
  ) do
    post :create, body:, as: :json
  end
end
```

This asserts: (1) the request is verified successfully using only `OrgOne`'s secret (the org named in the payload's `repository.owner.login`), and (2) the side effect (`GithubSyncJob` enqueue) targets `OrgTwo`'s stack with an attacker-chosen SHA — proving the equality `organization_whose_secret_verified == organization_owning(mutated_repo)` does not hold.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end
