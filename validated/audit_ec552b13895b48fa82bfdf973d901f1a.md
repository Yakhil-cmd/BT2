### Title
Bridge message signatures lack contract-address domain separation, enabling cross-proxy replay - (File: `bridge/evm/contracts/utils/BridgeUtils.sol`)

### Summary
The EVM bridge's message digest is computed from a hardcoded `MESSAGE_PREFIX` and does not include the proxy contract address. This mirrors the MechMarketplace `domainSeparator` bug: the signing domain is implementation-wide rather than per-proxy, so any committee-signed message valid for one UUPS proxy is also valid for every other proxy sharing the same implementation and chain ID.

### Finding Description
`BridgeUtils.encodeMessage()` and `BridgeUtils.computeHash()` build the signed digest as:

```solidity
bytes.concat(
    MESSAGE_PREFIX, message.messageType, message.version,
    message.nonce, message.chainID, message.payload
)
``` [1](#0-0) 

The `MESSAGE_PREFIX` is a constant string (`"SUI_BRIDGE_MESSAGE"`), and no field binds the digest to the proxy address that will execute it. The contracts are intended to be deployed as UUPS upgradeable proxies (`CommitteeUpgradeable` disables initializers in the constructor and inherits `UUPSUpgradeable`), so many proxy instances can share one implementation. [2](#0-1) 

`MessageVerifier.verifyMessageAndSignatures()` validates signatures against `BridgeUtils.computeHash(message)` and enforces nonces per message type, but those nonces live in each proxy's storage. [3](#0-2) 

Because the hash does not depend on `address(this)`, a message signed for Proxy A is byte-for-byte identical to the message signed for Proxy B. The only per-proxy replay guard is `isTransferProcessed[nonce]` for token transfers and the `nonces` mapping for governance messages, neither of which prevents the same signature from being submitted to a different proxy instance.

### Impact Explanation
An unprivileged user can observe a committee-signed bridge message on-chain and replay it against any other bridge proxy on the same chain that uses the same implementation. Depending on the message type, this yields:

- **Token transfer replay**: the same withdrawal can be executed on a second bridge instance if that instance's vault holds funds, causing illegitimate unlocks.
- **Governance replay**: emergency pause/unpause, blocklist updates, token price updates, limit updates, and UUPS upgrades can be re-executed on a secondary proxy using signatures intended for the primary proxy.

This falls under the allowed impact class **"bridge message forgery or bridge governance or upgrade bypass that enables illegitimate mint or unlock"**.

### Likelihood Explanation
High. The contracts are explicitly designed for UUPS proxy deployment, the message encoding and prefix are public constants, and signatures become public once a transaction is executed. The `chainID` field only separates different chains, not different proxy deployments on the same chain. Nonces prevent replay within a single proxy but not across proxies, because the signed digest is identical for every proxy sharing the implementation and chain ID.

### Recommendation
Bind the message digest to the proxy instance. Include `address(this)` (or a `domainSeparator` value set during `initialize()`) in the hashed input. For example, change `encodeMessage` to prepend the proxy address, or adopt EIP-712 and compute `_domainSeparatorV4()` using the proxy address and chain ID during initialization. Also block direct initialization of the implementation contract, which `CommitteeUpgradeable` already does via `_disableInitializers()` in the constructor.

### Proof of Concept
1. Deploy two `SuiBridge` proxies, `Proxy1` and `Proxy2`, pointing to the same implementation and initialized with the same `chainID` and committee.
2. Have the committee sign a token transfer message with nonce `1` for `Proxy1`.
3. Call `Proxy1.transferBridgedTokensWithSignatures(signatures, message)`; it succeeds and sets `isTransferProcessed[1] = true`.
4. Submit the exact same `signatures` and `message` to `Proxy2`.
5. `Proxy2` computes the same `keccak256` digest because `BridgeUtils.computeHash()` is pure and contains no proxy address; signature verification passes, `isTransferProcessed[1]` is false on `Proxy2`, and the transfer executes again.

The same replay works for `executeEmergencyOpWithSignatures`, `updateBlocklistWithSignatures`, `updateLimitWithSignatures`, `updateTokenPriceWithSignatures`, `addTokensWithSignatures`, and `upgradeWithSignatures` because their signed digests are also proxy-agnostic.

    string public constant MESSAGE_PREFIX = "SUI_BRIDGE_MESSAGE";

    /* ========== INTERNAL FUNCTIONS ========== */

    /// @notice Encodes a bridge message into bytes, using abi.encodePacked to concatenate the message fields.
    /// @param message The bridge message to be encoded.
    /// @return The encoded message as bytes.
    function encodeMessage(Message memory message) internal pure returns (bytes memory) {
        bytes memory prefixTypeAndVersion =
            abi.encodePacked(MESSAGE_PREFIX, message.messageType, message.version);
        bytes memory nonce = abi.encodePacked(message.nonce);
        bytes memory chainID = abi.encodePacked(message.chainID);
        return bytes.concat(prefixTypeAndVersion, nonce, chainID, message.payload);
    }

    /// @notice Computes the hash of a bridge message using keccak256.
    /// @param _message The bridge message to be hashed.
    /// @return The hash of the message.
    function computeHash(Message memory _message) internal pure returns (bytes32) {
        return keccak256(encodeMessage(_message));
    }
```

    modifier verifyMessageAndSignatures(
        BridgeUtils.Message memory message,
        bytes[] memory signatures,
        uint8 messageType
    ) {
        // verify message type
        require(message.messageType == messageType, "MessageVerifier: message does not match type");
        // verify signatures
        committee.verifySignatures(signatures, message);
        // increment message type nonce
        if (messageType != BridgeUtils.TOKEN_TRANSFER) {
            // verify chain ID
            require(
                message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
            );
            require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
            nonces[message.messageType]++;
