### Title
`review_stacks_enabled` toggle is bypassed for `allow_with_label`/`prevent_with_label` behaviors due to operator precedence, and existing label-name matching is moot as a result - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
The `provision?` method in `OpenedHandler` (and the equivalent `unarchive?` in `ReopenedHandler`) uses `&&`/`||` with unintended precedence, so `repository.review_stacks_enabled` only gates the `allow_all?` branch and not the `allow_with_label?`/`prevent_with_label?` branches. Consequently, an attacker opening a PR with no labels against a `prevent_with_label` repo triggers stack creation even when `review_stacks_enabled` is `false`, making the exact-match label comparison in `pull_request_has_provisioning_label?` irrelevant to the exploit.

### Finding Description
The intended binding is: `should_provision == repository.review_stacks_enabled && behavior_matches`. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` binds tighter than `||` in Ruby, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`. `review_stacks_enabled` is never combined with the second or third disjuncts. For a repository configured with `provisioning_behavior: :prevent_with_label` and `review_stacks_enabled: false`, an attacker who opens a PR with `labels: []` (the default state — they need not apply any label at all) causes `pull_request_has_provisioning_label?` to return `false`, so `!pull_request_has_provisioning_label?` is `true`, and `provision?` returns `true` regardless of `review_stacks_enabled`. `process` then calls `ReviewStackAdapter#find_or_create!`, which creates a `Shipit::ReviewStack` and enqueues it for provisioning. [2](#0-1) [3](#0-2) [4](#0-3) 

Because the bypass fires purely from label absence, the question's premise about case/whitespace-sensitive matching in `pull_request_has_provisioning_label?`/`pull_request_label_names` is technically real (exact-match, case-sensitive, whitespace-sensitive) but not independently exploitable as a distinct new vector — since absence of the label (the default, no-op state for any attacker) already satisfies the `prevent_with_label` branch irrespective of `review_stacks_enabled`. [5](#0-4) 

No existing guard prevents this: `respond_to_pull_request_opened?` only checks `params.action == "opened"` and delegates entirely to the broken `provision?`, there's no re-check of `review_stacks_enabled` elsewhere in the handler or in `ReviewStackAdapter`. [6](#0-5) 

The existing repo test suite already codifies this exact behavior as "expected": [7](#0-6) 

That test uses `configure_provisioning_behavior` with `provisioning_enabled: true` by default (it does not explicitly set `review_stacks_enabled: false`), so it does not by itself prove the toggle bypass; it only proves the label-absence path creates a stack when `review_stacks_enabled` is true. Verifying the toggle-bypass specifically requires a new test that sets `provisioning_enabled: false`, which was not present in the reviewed test files. I could not find a test file that explicitly asserts stack creation with `review_stacks_enabled: false` and `prevent_with_label` — this exact-request confirmation is only supported by static code-path tracing of `provision?`, not by an existing executed test.

### Impact Explanation
Any unauthenticated GitHub user who can open a pull request against a tracked repository configured with `provisioning_behavior: prevent_with_label` — even one with review-stack auto-provisioning nominally disabled (`review_stacks_enabled: false`) — can force Shipit to create and enqueue a `Shipit::ReviewStack` for provisioning by simply not applying any label (the default state of any PR). This is a record-write / unauthorized-provisioning path for a repository that the attacker does not otherwise control, repeatable per PR/per repository that uses this configuration. This matches "unauthorized deploy/provisioning" under the Critical category, since it results in a stack whose provisioning queue entry will drive subsequent infrastructure actions the operator explicitly intended to prevent via `review_stacks_enabled: false`.

### Likelihood Explanation
Preconditions: the target repository must have `provisioning_behavior: prevent_with_label` configured (an operator choice, not attacker-controlled), and the attacker must be able to open a pull request against it (any external contributor on a public/open repo, or a forked branch on repos accepting PRs). No secrets, tokens, or elevated GitHub permissions are needed — opening a PR with no labels is the default, zero-cost action. This is trivially repeatable across any number of qualifying repositories/PRs.

### Recommendation
Fix the operator precedence in `provision?` (and the identical bug in `ReopenedHandler#unarchive?`) by explicitly parenthesizing so `review_stacks_enabled` gates all three behaviors:

```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the equivalent fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
minitest plan (place in `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false and label is absent" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before fix, `repository.review_stacks_enabled == false` yet `Shipit::Stack.count` increases (test fails / bug present); after fix, the assertion holds (`assert_no_difference` passes), confirming `review_stacks_enabled` correctly gates the `prevent_with_label` branch.
