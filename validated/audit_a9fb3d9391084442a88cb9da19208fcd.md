### Title
`review_stacks_enabled` false is bypassed by operator-precedence bug in `provision?`/`unarchive?` allowing PR-triggered stack provisioning - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`)

### Summary
`OpenedHandler#provision?` and `ReopenedHandler#unarchive?` intend `repository.review_stacks_enabled` to be a master switch gating all review-stack provisioning, but due to missing parentheses it only gates the `allow_all` branch of a three-branch `||` expression. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, a `ReviewStack` is created/unarchived even though `review_stacks_enabled` is `false`.

### Finding Description
The broken binding is: intended `provision? == review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`, but actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby's `&&` binds tighter than `||`, so this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. If `review_stacks_enabled == false` and `provisioning_behavior == prevent_with_label`, any PR opened without the provisioning label (the default state — an attacker need do nothing special) makes `provision?` return `true`. The identical bug exists in `ReopenedHandler#unarchive?`. [2](#0-1) 

By contrast, `LabeledHandler` implements this correctly by ANDing `review_stacks_enabled` with the whole label-decision expression at the top level: [3](#0-2) 

`OpenedHandler#process` then unconditionally provisions via `ReviewStackAdapter#find_or_create!`, using attacker-supplied `params.pull_request.head.ref` as the new stack's `branch`: [4](#0-3) [5](#0-4) 

Regarding the webhook-forging premise: `GitHubApp#verify_webhook_signature` does `return true unless webhook_secret`, so for an org configured without a `webhook_secret` (documented as optional in `docs/setup.md`), `Shipit::WebhooksController#verify_signature` accepts any unsigned request: [6](#0-5) [7](#0-6) 

This is an operator configuration choice, not itself a code defect, but it removes the only origin check on the `pull_request` payload for that org, letting the precedence bug be triggered by a fully forged HTTP request rather than requiring a real GitHub-side PR.

### Impact Explanation
For a repository whose admin explicitly set `review_stacks_enabled = false` (intending to fully disable auto-provisioning) but left `provisioning_behavior` at `allow_with_label` or `prevent_with_label` (a plausible prior/partial configuration), the guard is silently bypassed: a `ReviewStack` record is created, a `PullRequest` record is attached, and `Shipit::ReviewStackProvisioningQueue.add(stack)` queues the stack for provisioning — an unauthorized state mutation and downstream deploy action against a repository configuration that explicitly opted out. If the same org has no `webhook_secret` configured, any unauthenticated internet request can trigger this for the targeted repository, repeatably, since `find_or_create!` reuses the same `pr{number}` environment. This matches the "unauthorized deploy" / unauthenticated-write class of impact, scoped to repositories that (a) are tracked by Shipit, (b) have `review_stacks_enabled=false`, and (c) use `allow_with_label`/`prevent_with_label`. It does not by itself grant new code-execution primitives beyond what the review-stacks feature (when properly enabled) already exposes to repository maintainers via their `shipit.yml`.

### Likelihood Explanation
Requires a specific, non-default repository configuration (`review_stacks_enabled=false` combined with `allow_with_label`/`prevent_with_label`) which is plausible but not guaranteed, since operators most commonly leave `provisioning_behavior` at `allow_all` (the enum's first/default value) when disabling review stacks. Exploitation via a genuine opened PR requires only the ability to open a PR against the tracked repository (fork-level access — "unprivileged" per the rules) and, for `prevent_with_label`, no special action at all. Amplification via fully forged, unauthenticated payloads additionally requires the org to have no `webhook_secret` configured, which is an operator choice documented as optional.

### Recommendation
Fix the operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` by parenthesizing so `review_stacks_enabled` gates the entire expression, matching `LabeledHandler`'s pattern, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
minitest plan (extends `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`):
```ruby
test "does not provision when review_stacks_enabled is false, even with prevent_with_label" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,      # binding under test: review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []   # no label -> prevent_with_label triggers provisioning

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::Stack.count` increases by 1 (assertion fails), proving `repository.review_stacks_enabled == false` and "a `ReviewStack` was created" diverge. After applying the recommended parenthesization, the assertion passes, restoring the invariant.
