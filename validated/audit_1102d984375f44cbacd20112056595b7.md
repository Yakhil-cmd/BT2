### Title
Cross-tenant commit-status forgery via unscoped `StatusHandler` breaks the org-authenticated-vs-repository-written binding, enabling unauthorized deploys/merges - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit supports hosting multiple independent GitHub organizations/apps on a single Shipit instance, each with its own `webhook_secret` [1](#0-0) [2](#0-1) . Inbound webhooks are authenticated per-organization: `WebhooksController#verify_signature` looks up the GitHub app config for `repository_owner` (an unauthenticated field read straight out of the request body) and verifies the HMAC signature against that organization's secret [3](#0-2) . Once the signature is accepted, the raw parsed payload is dispatched to event handlers with no further binding to the authenticating organization [4](#0-3) .

`Shipit::Webhooks::Handlers::StatusHandler`, which processes GitHub `status` events, looks up the target commit purely by SHA across the entire installation, with no repository or organization scoping at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

This breaks the equality that must hold: `organization that authenticated the webhook == repository/stack whose data is written`. The signature only proves the payload was signed with *some* registered organization's secret; it proves nothing about which stack's commits the handler is allowed to touch.

### Finding Description
Other handlers at least scope through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [6](#0-5)  — itself a different, attacker-controlled field from the `repository.owner.login` used for signature verification, but at least some scoping check happens. `StatusHandler` performs none of this: it uses `params.sha` (a bare commit SHA, required but otherwise unconstrained) to find `Commit` records globally via `Commit.where(sha: params.sha)`.

Attack precondition: the attacker only needs to legitimately control the GitHub App/webhook configuration of **their own** organization that is registered on the shared Shipit instance (e.g. they administer a small org "attacker-org" that some team onboarded to this shared Shipit deployment) — they know `attacker-org`'s own `webhook_secret`, not the victim's. This is the exact "an organization that authenticated versus the repository that is written" boundary called out as in-scope, and does not require possession of an `ApiClient` token, a privileged Shipit account, or the victim's/global `webhook_secret`.

With that secret, the attacker can:
1. Send a `POST` to `/github/webhooks` with `X-Github-Event: status`, `repository.owner.login = "attacker-org"` (so `verify_signature` looks up and validates against the attacker's own secret) and any `X-Hub-Signature` correctly computed with that secret.
2. Set `sha` in the payload to the SHA of a commit that belongs to a completely unrelated, victim-owned stack/repository tracked by the same Shipit instance (commit SHAs are public/guessable from the victim's public GitHub repo or PR).
3. Set `state: "success"` (plus a `context` matching one of the victim stack's `required_statuses`).

`StatusHandler#process` will happily create a passing `Status` on that victim commit, since it never checks that the commit's stack belongs to `attacker-org` [5](#0-4) .

### Impact Explanation
Commit statuses directly gate deploy and merge-queue eligibility:
- `Commit#deployable?` returns true once `success?` is satisfied (unless CI is ignored) [7](#0-6) .
- `MergeRequest#all_status_checks_passed?` / `#any_status_checks_missing?` are computed from `head.statuses_and_check_runs` via `StatusChecker` [8](#0-7) , and `ProcessMergeRequestsJob` calls `merge_request.merge!` once those pass [9](#0-8) , which performs a real GitHub merge via `stack.github_api.merge_pull_request` [10](#0-9) .

By forging a fake passing status for a victim's commit/PR head SHA, an attacker with no relationship to the victim's org/repo can cause an unauthorized deploy (via continuous deployment) or an unauthorized merge (via the merge queue) — this satisfies the Critical-severity criterion "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Exploitation only requires: (1) the attacker legitimately controls a GitHub org/app already registered on the shared Shipit instance (a realistic scenario for any multi-tenant/shared Shipit deployment, which the engine explicitly supports via multi-org `secrets.yml` config), and (2) knowledge of a target commit SHA on the victim stack, which is trivially obtainable from a public repository or open pull request. No Shipit session, `ApiClient` token, or the victim's secret is required — only the attacker's own webhook secret, which they legitimately possess for their own tenant. The complete absence of repository scoping in `StatusHandler#process` makes this directly and reliably exploitable, not merely theoretical.

### Recommendation
Scope `StatusHandler#process` (and ideally every handler) to the repository identified by the authenticated organization, e.g. resolve `stacks` (as `PushHandler`/`CheckSuiteHandler` partially attempt) and restrict `Commit.where(sha: params.sha, stack: stacks)` instead of a bare global lookup. More fundamentally, `WebhooksController` should thread the authenticated organization (the one whose secret validated the signature) into the handler dispatch, and every handler should assert that the `repository.full_name`/`repository.owner.login` used to select the affected stack actually belongs to that authenticated organization — closing the `organization-authenticated == repository-written` gap for all handlers, not just `StatusHandler`.

### Proof of Concept
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org's webhook_secret, body)>
Content-Type: application/json

{
  "sha": "<victim_stack_pr_head_sha>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "https://example.com",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
`verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully using the attacker's own secret [11](#0-10) ; `StatusHandler#process` then creates a passing status on the victim's commit regardless of which repository/org it actually belongs to [5](#0-4) , which can flip `deployable?`/merge-queue checks for a commit the attacker never had access to.

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
