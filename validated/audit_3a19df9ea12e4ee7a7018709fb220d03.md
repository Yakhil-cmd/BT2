### Title
Push webhook cross-tenant stack sync via decoupled authentication owner vs. authorization `full_name` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/push_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using `repository_owner` (`payload.dig('repository','owner','login')`), while `PushHandler`/`Handler#stacks` resolves the target `Repository`/`Stack` using a *different* field from the same attacker-controlled JSON body — `payload.dig('repository','full_name')` — with no check that the two agree. If any GitHub organization configured in Shipit lacks a `webhook_secret` (documented as optional in `docs/setup.md`), an attacker can authenticate as that no-secret org while pointing `repository.full_name` at a victim stack in a different, secret-protected org, causing `GithubSyncJob` to append/deploy attacker-chosen commits (`after`) to the victim stack.

### Finding Description
The intended binding is: **the organization that cryptographically authenticated the webhook == the organization owning the repository whose stacks get synced.** In code these are two independently attacker-supplied fields from the same payload:

- Authentication key: `repository_owner` in [1](#0-0) , used to pick the `GithubApp`/secret via `Shipit.github(organization: repository_owner)` in [2](#0-1) .
- Authorization key: `repository_name` = `payload.dig('repository','full_name')` in [3](#0-2) , used by `PushHandler#process` via `Repository.from_github_repo_name(repository_name)` in [4](#0-3)  and [5](#0-4) .

Nothing enforces `full_name.split('/').first == repository.owner.login`. `verify_webhook_signature` in `GitHubApp` trivially returns `true` when no `webhook_secret` is configured for the resolved organization: [6](#0-5) . `docs/setup.md` explicitly documents the webhook secret as optional per organization in the multi-org config format. `Shipit.github` resolves per-organization config in multi-org mode via `github_app_config(organization)` and raises only if the organization is entirely unknown, not if its secret is blank: [7](#0-6) .

Exploit: attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/<victim-branch>",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "no-secret-org" }
  }
}
```
`verify_signature` authenticates using `no-secret-org`'s (missing) secret and passes unconditionally. `PushHandler` then resolves stacks from `victim-org/victim-repo` (an org protected by its own real secret) via `Repository.from_github_repo_name`, and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` for the victim stack with the attacker's `after` sha, which then fetches and appends commits reachable from that sha into the victim stack (`GithubSyncJob#perform`, `append_commit`): [8](#0-7) .

The "ref prefix trick" (`branch = params.ref.gsub('refs/heads/','')`) itself is not a distinct bypass — it is the intended, expected way branches are matched and does not by itself cross any trust boundary; it only matters insofar as the attacker must supply a `ref` string that matches an existing victim branch name, which is trivial once the org/full_name decoupling above is exploited.

### Impact Explanation
A payload for one organization/repository (the unprotected "no-secret" one used only to pass signature verification) mutates another organization's stack: the victim `Stack`'s commit history is appended with commits reachable from an attacker-chosen `after` SHA, which — depending on stack configuration (continuous deployment) — leads to an unauthorized deploy/rollback of attacker-influenced code. This matches the "payload for one repository mutating another's stack/commit/task" and "unauthorized deploy" Critical impact categories. Repeatable against any victim stack whose owning organization's name can be paired with any configured no-secret organization in the same Shipit instance; blast radius covers every stack of every org sharing the Shipit installation with a misconfigured (secret-less) org.

### Likelihood Explanation
Requires: the target Shipit instance is running the multi-organization GitHub config (`Shipit.github_organizations` > 1) and at least one configured organization has `webhook_secret` unset — a configuration explicitly presented as optional in `docs/setup.md`, so plausible in real deployments that onboard low-trust or test organizations. The attacker needs only the organization handle string (public) and the victim repo's `owner/name` (public); no Shipit or GitHub secret is required. Cost is a single unauthenticated HTTP POST, fully repeatable and scriptable.

### Recommendation
Bind authentication and authorization to the same value: after `verify_webhook_signature` succeeds, require that `payload.dig('repository','full_name')`'s owner segment equals the `repository_owner`/organization used to authenticate the request (case-insensitively), rejecting the webhook (422) otherwise. Do this centrally in `WebhooksController` before dispatching to handlers, or add the check to `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":push from a no-secret org cannot sync a victim org's stack" do
  # Multi-org config: "attacker-org" has webhook_secret: nil; "shopify" (victim org)
  # owns @stack (shipit_stacks(:shipit), full_name "Shopify/shipit-engine").
  Shipit.stubs(:github_default_organization).returns("attacker-org")
  Shipit.stubs(:github).with(organization: "attacker-org").returns(
    stub(verify_webhook_signature: true) # no secret configured -> always true
  )

  request.headers['X-Github-Event'] = 'push'
  forged = JSON.parse(payload(:push_master))
  forged["repository"]["owner"]["login"] = "attacker-org"       # authenticates as no-secret org
  forged["repository"]["full_name"] = @stack.repository.github_repo_name # targets victim repo
  forged["after"] = "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"  # attacker-chosen sha

  assert_enqueued_with(
    job: GithubSyncJob,
    args: [stack_id: @stack.id, expected_head_sha: "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef"]
  ) do
    post :create, body: forged.to_json, as: :json
  end
end
```
Assert on both sides of the intended binding: `authenticated_organization` (`"attacker-org"`, derived from `repository.owner.login`) must equal `Repository.from_github_repo_name(repository.full_name).owner` (`"shopify"`) for the sync to be authorized; the test shows the job is enqueued for the victim stack even though they differ, proving the invariant is broken.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
