### Title
Missing sender authorization in `new_shared_address` device-message handler allows a paired correspondent to plant a forged shared-address definition and cosigner map, corrupting/freezing multisig wallet funds - (File: wallet_defined_by_addresses.js)

### Summary
`wallet.js`'s `handleMessageFromHub` dispatches the `"new_shared_address"` subject straight to `walletDefinedByAddresses.handleNewSharedAddress(body, callbacks)` without ever passing (or checking) `from_address` — the cryptographically-verified sender of the device message. [1](#0-0) 

Unlike the sibling handlers `create_new_shared_address` and `approve_new_shared_address`, which explicitly validate that `from_address` is one of the device addresses referenced in the definition template before acting, [2](#0-1) 
`handleNewSharedAddress` never checks that the message actually came from a device that is legitimately part of the shared address being created. It only checks internal self-consistency of the payload (definition hash, per-path address matches), never the identity of the sender against the `device_address` values embedded in the payload itself. [3](#0-2) 

### Finding Description
The handler performs these checks on `body = {address, definition, signers, forwarded}`:
1. `definition` hashes to `address` (chash160 consistency).
2. Every `signers[path].address` matches the address that `extractAddressPathsFromDefinition` derives from the definition at that path.
3. `determineIfIncludesMeAndRewriteDeviceAddress` confirms *some* member address in the definition belongs to me (`my_addresses` or `shared_addresses`).
4. `validateAddressDefinition` confirms the oscript definition is syntactically valid.

None of these checks constrain `signers[path].device_address` — the field that records *which device is responsible for producing the signature for a given member address*. This value is taken directly from the attacker-controlled `body.signers` map and is not required to equal `from_address`, nor is it checked against any pre-existing correspondent/wallet relationship for that address. [4](#0-3) 

Once accepted, `addNewSharedAddress` persists this attacker-supplied `device_address` mapping verbatim into `shared_address_signing_paths`, and then automatically propagates it to *other* correspondent devices that cosign my own member addresses referenced by the definition: [5](#0-4) [6](#0-5) 

This is the same bug class as the Hatchet advisory: a caller with a valid, weak credential (here: any paired correspondent device, the lowest trust level in ocore's device-messaging protocol, since pairing is even allowed from *non*-correspondents) supplies a resource identifier/mapping (`device_address` per signing path) whose scope should be restricted to the sender's own identity, but the handler only uses the verified sender identity (`from_address`) for logging/consistency of the "am I a member" check — never to authorize which device is recorded as the cosigner for a given signing path. The `device_address` field is fully attacker-controlled and blindly trusted.

`findAddress` later relies on this exact `shared_address_signing_paths.device_address` value to route signing requests when spending from a shared address: [7](#0-6) 

### Impact Explanation
A malicious paired device (attacker only needs to be a normal correspondent — pairing itself requires no privilege beyond knowing a pairing secret or being pre-approved, and this device does not need to be a real cosigner of the target shared address) can send a `new_shared_address` message where:
- The `definition` legitimately references the victim's own address (so `determineIfIncludesMeAndRewriteDeviceAddress` passes),
- But the `device_address` for one or more OTHER member addresses in the `signers` map is set to a bogus/attacker-controlled device address instead of the real cosigner's device.

This corrupts the victim's local `shared_address_signing_paths` table for a newly-created (and possibly funded) shared/multisig address. When the victim later tries to spend funds from that address, `findAddress`'s `ifRemote` callback will route the signing request to the wrong (attacker-chosen or non-existent) device, meaning the real cosigner is never asked to sign. Since ocore's multisig spending requires collecting signatures from the recorded `device_address` for each signing path, this results in an address whose funds can never be fully signed for — effectively freezing any coins sent to that shared address. Additionally, because `forwardNewSharedAddressToCosignersOfMyMemberAddresses` re-broadcasts this poisoned cosigner map to the victim's other legitimate cosigner devices, the corruption propagates to third-party devices that never interacted with the attacker at all — a cross-party write exactly analogous to the Hatchet cross-tenant write.

This satisfies the "AA fund loss or freezing" / node disagreement class of impact required by the validation rules, reached purely through a device message that any paired correspondent (the lowest-trust actor in the wallet protocol) can send.

### Likelihood Explanation
Reaching this code requires only:
1. Being paired with the victim device (a normal, low-privilege state — many wallets accept pairing requests from anyone holding a shareable pairing code/QR, and even non-correspondents are allowed for `pairing`, `my_xpubkey`, `wallet_fully_approved`).
2. Sending a single crafted `new_shared_address` device message with attacker-chosen `device_address` fields in `signers`.

No cryptographic signature over the individual `device_address` fields is required, and no server-side / hub-side gatekeeping restricts this subject once the sender is a known correspondent. This makes the attack straightforward for anyone who can pair with or is already paired with a victim wallet device — a routine, low-effort trust relationship in ocore's multi-device wallet model.

### Recommendation
In `handleNewSharedAddress` (and in `wallet.js`'s `new_shared_address` case), require that `from_address` be passed through and validated:
- Only permit signer `device_address` entries to be trusted if the message came from the corresponding device itself, or the device_address is cross-checked against a value that the receiving device already knows about (e.g., an existing correspondent relationship or an offer previously initiated locally via `create_new_shared_address`/`approve_new_shared_address`).
- Reuse the same authorization pattern already implemented for `approve_new_shared_address`, i.e., match `from_address` against the expected member-device set derived from the definition template, before accepting/forwarding the `device_address` mapping for any signing path other than the sender's own.

### Proof of Concept
1. Attacker device `D_evil` pairs with victim device `D_victim` (normal correspondent pairing).
2. `D_evil` crafts a definition `arrDefinition` such that one leaf address equals `D_victim`'s real payment address (so victim passes the "includes me" check), and another leaf equals some real third-party address `A_target` whose actual cosigner device is `D_real`.
3. `D_evil` sends:
```
device.sendMessageToDevice(D_victim, "new_shared_address", {
  address: chash160(arrDefinition),
  definition: arrDefinition,
  signers: {
    "r.0": { address: victim_address, device_address: D_victim },
    "r.1": { address: A_target, device_address: D_evil }   // forged: should be D_real
  }
});
```
4. `wallet.js` dispatches straight to `handleNewSharedAddress` (`wallet.js:236-245`) with no `from_address` check.
5. All structural checks pass (hash matches, per-path address matches), so `addNewSharedAddress` inserts `shared_address_signing_paths` with `device_address=D_evil` for path `r.1` (`wallet_defined_by_addresses.js:239-268`).
6. The forged mapping is auto-forwarded to `D_victim`'s other cosigner devices via `forwardNewSharedAddressToCosignersOfMyMemberAddresses` (`wallet_defined_by_addresses.js:317-336`).
7. When `D_victim` later attempts to spend from the new shared address, `findAddress`'s `ifRemote` branch (`wallet.js:1246-1249`) sends the signing request to `D_evil` instead of `D_real`, so the legitimate cosigner never signs — the funds sent to this shared address become permanently unspendable.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
