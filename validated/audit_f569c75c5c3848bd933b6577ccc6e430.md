Confirmed: `Repository.from_github_repo_name` splits `payload.dig('repository', 'full_name')` on `/` to get `repo_owner`/`repo_name` and looks up the `Repository` record purely by that pair — independent of the `repository.owner.login` field that `WebhooksController#repository_owner` used to select the webhook secret.### Title
Webhook signature verification authenticates the payload's `repository.owner.login`/`organization.login` while the push/pull-request/status handlers act on `repository.full_name`, letting an attacker with any one org's `webhook_secret` write to a repository owned by a different org - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify against based on `repository.owner.login` (falling back to `organization.login`) extracted from the *same, not-yet-verified* JSON body. `Shipit::Webhooks::Handlers::Handler#stacks` (and every handler built on it, e.g. `PushHandler`, `PullRequest::OpenedHandler`) instead resolves the target `Repository`/`Stack` from an independent field, `repository.full_name`, via `Repository.from_github_repo_name`. These two fields are never cross-checked against each other, so the "organization that authenticated" and the "repository that is written" are not bound together.

### Finding Description
- `verify_signature` computes `repository_owner` as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and looks up `Shipit.github(organization: repository_owner)` to get that org's `webhook_secret`, then verifies `X-Hub-Signature` over the raw POST body with that secret. [1](#0-0) 
- The handler base class, used by `PushHandler`, `PullRequest::*Handler`, etc., resolves the affected repository purely from `payload.dig('repository', 'full_name')`: [2](#0-1) 
- `Repository.from_github_repo_name` splits that `full_name` string on `/` and looks up the DB record by `owner`/`name`, with no relation to `repository.owner.login`: [3](#0-2) 
- `PushHandler#process` then triggers `stack.sync_github(expected_head_sha:)` for every non-archived stack of the resolved repository/branch: [4](#0-3) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the repository whose stacks get synced) are two separate JSON fields inside the same webhook body, an attacker who legitimately controls a webhook for **Organization A** (and thus knows Org A's `webhook_secret`, e.g. because they administer a Shipit-connected repo there) can craft a payload where:
- `repository.owner.login = "OrgA"` (or `organization.login = "OrgA"`) → signature verified successfully with Org A's secret, which the attacker legitimately possesses.
- `repository.full_name = "OrgB/some-repo"` → the handler resolves and mutates a `Stack` belonging to an entirely different, unrelated repository/organization (`OrgB`) that the attacker has no access to.

This breaks the intended binding: **organization authenticated == organization/repository written**. The signature is verified over the raw body, but which secret is chosen for that verification is itself derived from an attacker-controlled sub-field of the very same unverified body, decoupled from the field the business logic actually trusts to select the target repository.

### Impact Explanation
This allows an attacker who legitimately controls (or has compromised) the webhook secret for one GitHub organization/app installation configured in this Shipit instance to force `GithubSyncJob` to run against, and to trigger downstream repository-state mutations (commit ingestion, stack unlocking behavior via `lock_reverted_commits!`, review-stack creation/archival via `PullRequest::OpenedHandler`/`LabeledHandler`, etc.) for stacks belonging to a **completely different repository/organization** also configured in the same Shipit instance — a cross-repository/cross-organization write triggered without holding that target org's credentials. This matches the "cross-repository writes" Critical impact category, since the write is performed against a repository the attacker was never authorized against.

### Likelihood Explanation
Likelihood is Medium: it requires (a) the Shipit instance to be multi-tenant, i.e., configured with more than one GitHub organization/App installation (`config/secrets*.yml` supports a `github:` map keyed by org — see `somegithuborg`/`someothergithuborg` examples), and (b) the attacker to legitimately hold or leak a valid `webhook_secret` for at least one of those configured organizations. This is a realistic operational configuration for larger, shared Shipit deployments serving multiple GitHub orgs, but not universal.

### Recommendation
Bind the field used to select the verifying secret to the field used to resolve the target repository/stack:
- After computing `repository_owner`, cross-validate it against the owner segment of `repository.full_name` (i.e., `params.dig('repository', 'full_name')&.split('/')&.first`) and reject (422) the webhook if they mismatch.
- Alternatively, always derive `repository_owner` strictly from `repository.full_name`'s owner segment instead of the separate `repository.owner.login`/`organization.login` fields, so a single, consistent field determines both which secret verifies the signature and which repository is written to.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`, `OrgA` and `OrgB`, each with its own `webhook_secret`, per `docs/setup.md`'s multi-org example. [5](#0-4) 
2. Attacker holds `OrgA`'s `webhook_secret` (e.g., they are an admin of a repo/app installation under `OrgA` connected to this Shipit instance).
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-controlled sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
5. `verify_signature` resolves `repository_owner == "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check passes because the attacker used the correct (legitimately known) `OrgA` secret. [6](#0-5) 
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` as `"OrgB/victim-repo"` and looks up/mutates stacks under `OrgB`, unrelated to the org whose secret was used to authenticate the request. [7](#0-6) [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([

        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
