## Finding: Confirmed Vulnerability



### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets any repository's status webhook write Status rows onto another repository's identically-SHA'd commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other handler which uses `Handler#stacks` (scoped via `Repository.from_github_repo_name(repository_name)`). Because git commit SHAs are content-addressed and identical across forks/mirrors that share history, a signed `status` webhook legitimately originating from an attacker-owned repository can create a `Status` (context `github-actions`, arbitrary `state`) on a commit row belonging to an unrelated victim stack that happens to share the same SHA.

### Finding Description
The invariant that should hold: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Status` created by processing a `status` webhook. This invariant is never checked.

Path:
- `Shipit::WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event('status')`, which is `[Handlers::StatusHandler]` [1](#0-0) [2](#0-1) .
- `verify_signature` only checks that the payload is authentically signed by whatever `Shipit.github(organization: repository_owner)` app is configured for the `repository.owner.login` claimed in the payload — it does not check that the repository is associated with any particular stack, nor that the SHA belongs to that repository [3](#0-2) . An attacker who legitimately owns a GitHub organization/repo with the Shipit GitHub App installed can cause GitHub itself to emit a validly-signed `status` event for a commit in their own repo.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 
This is a bare, cross-tenant `Commit.where(sha:)` query with **no** repository/stack scoping — contrast with the base `Handler#stacks` helper used by every other handler (`PushHandler`, `PullRequest::*`, `CheckSuiteHandler`), which resolves `Repository.from_github_repo_name(repository_name)&.stacks` before touching any record [5](#0-4) .
- Commits are stored per-stack (`belongs_to :stack`) with a unique index on `(sha, stack_id)`, not a global-unique `sha` [6](#0-5) [7](#0-6) , confirming that identical SHAs are expected to legitimately exist across multiple, unrelated stacks (e.g., forks, mirrors, shared upstream history). Because git commit SHAs hash only tree/parents/author/committer/message/timestamps — not the repository name — any commit that is byte-identical across a victim's public repo and an attacker's fork (very common for unmodified upstream history) shares the exact same SHA.
- `Status#enable_ci_on_stack` (`after_create`) calls `commit.stack.enable_ci!`, and `Status#schedule_continuous_delivery` (`after_commit`) schedules delivery evaluation for the victim's stack [8](#0-7) [9](#0-8) . If the victim stack requires `github-actions` as a `required_status`/`blocking_status` (delegated from `Stack` via `Commit`) [10](#0-9) , an attacker-controlled `state` (`success`/`failure`/`error`) on that shared-SHA commit directly flips the victim stack's CI gate, enabling or blocking deploys without ever authenticating against the victim's repository.

Existing guards do not stop this: `verify_signature` authenticates the *sender* organization, not the *target* of the write; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape (`sha`, `state`, `context`, etc.), not repository ownership of the affected commit rows.

### Impact Explanation
An attacker who controls any repository (their own fork or org, with the Shipit GitHub App installed) can send a genuinely signed `status` event for a commit SHA that is shared with a victim stack (trivial via forking a public victim repository, since unmodified history retains identical SHAs). This creates a `Status` row attributed to the victim's `Commit`/`Stack`, flipping the CI/required-status state Shipit uses to gate deploys — a payload for one repository mutating another repository's stack/commit state, matching the "Critical: cross-repository state manipulation" category. This is repeatable against any victim stack that shares commit history (forks, mirrors, monorepo splits) with a repository the attacker controls.

### Likelihood Explanation
Preconditions: attacker needs a repository with the Shipit GitHub App/webhook installed (which is typically a low-cost self-service action for public GitHub App installations) and a commit SHA shared with the victim's tracked branch (naturally occurring for any repo that is forked from, or shares upstream history with, the victim's tracked repository — e.g. before divergence, or for cherry-picked/backported commits with identical content). No Shipit credentials, session, or `webhook_secret` of the victim's app installation are required — only a validly signed event for the attacker's own repo. This is fully repeatable and requires no privileged access to the victim's Shipit stack or GitHub org.

### Recommendation
Scope `StatusHandler#process` to only touch commits belonging to stacks associated with the authenticated `repository.full_name`, consistent with the base `Handler#stacks` helper, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "process does not create a status for a commit belonging to another repository sharing the same sha" do
  victim_repo  = shipit_repositories(:shipit) # e.g. owner/shipit
  victim_stack = shipit_stacks(:shipit)
  shared_sha   = 'deadbeefcafebabefeedfacedeadbeefcafebabe'

  victim_commit = victim_stack.commits.create!(
    sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus),
    authored_at: Time.now, committed_at: Time.now, message: "shared"
  )

  attacker_payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'github-actions',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker' } }
  }

  # Binding under test: a status for attacker/unrelated-repo must NOT affect victim_stack's commit.
  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end
end
```
Given the current implementation, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `attacker_payload['repository']`, so this assertion **fails** on current code, demonstrating the cross-repository write [4](#0-3) .
