### Title
Global, repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` allows a `status` webhook from an attacker's own authenticated organization to write a commit status onto commits belonging to any other tracked stack/repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no repository or stack scoping, unlike every other handler that derives its working set from `Handler#stacks` (which is scoped via `Repository.from_github_repo_name(repository_name)`). Because `WebhooksController#verify_signature` only authenticates that the request came from *some* organization the attacker legitimately controls in Shipit, and never checks that the `repository` field in the `status` payload matches a repository owned by that organization, an attacker can submit a `status` webhook, signed with their own org's webhook secret, whose `sha` matches a commit that belongs to a completely different, unrelated stack, and have Shipit write a fabricated CI status onto it.

### Finding Description
The broken binding, stated as an equality that should hold but does not:

`Handler#stacks` (`Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, `app/models/shipit/webhooks/handlers/handler.rb:32-38`) == the record set that `StatusHandler#process` mutates.

For every other handler this equality holds. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) mutates only `stacks.not_archived.where(branch:)`. `CheckSuiteHandler#process` (`app/models/shipit/webhooks/handlers/check_suite_handler.rb:13-17`) mutates only `stacks.where(branch:)`. `PullRequest::*Handler` classes explicitly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack (e.g. `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`).

`StatusHandler`, however, does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`params` for `StatusHandler` requires only `sha`, `state`, and optional fields — it never requires or reads `repository.full_name` [2](#0-1) , so the query is fully global across every stack/repository in the Shipit instance.

`WebhooksController#verify_signature` authenticates only the `repository_owner` (or `organization.login`) field of the payload against `Shipit.github(organization:)`'s configured webhook secret; it never cross-checks that the `repository.full_name` in a `status` payload is one actually owned by that organization/secret:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

Exploit flow: an attacker who legitimately owns/administers an organization/repository already onboarded to Shipit knows that org's `webhook_secret` (it is handed to repo owners so they can configure GitHub webhooks pointing at Shipit). They compute an HMAC signature over an arbitrary JSON body using that secret, set `repository.owner.login` (and `full_name`, if present) to their **own** org so `verify_signature` passes, but set `sha` to the commit SHA of a target commit belonging to a totally different, unrelated stack (git commit SHAs are public — visible on GitHub commit pages, PRs, and via the public API — and are not scoped to the reporting organization in any way). Because `StatusHandler` never checks `repository.full_name` against the resolved commit's stack, `Commit.where(sha: params.sha)` matches the victim commit and `commit.create_status_from_github!(params)` writes an attacker-chosen `state`/`description`/`context` status onto it via `add_status` [4](#0-3) .

None of the documented guards prevent this: `verify_signature` only binds the *organization* named in the payload to the secret, not the specific repository being mutated; `drop_unhandled_event` and the `ExplicitParameters` schema for `status` don't require or validate `repository.full_name` at all; and the `stacks` scoping mechanism used by `Handler` is simply never invoked by `StatusHandler`.

### Impact Explanation
A `state: success` status write on a victim's commit can flip that commit's aggregate `state` (see `Commit#status`/`add_status`), which fires `deployable_status` hooks and enqueues `ProcessMergeRequestsJob` when transitioning into `pending`/`success` [5](#0-4) . This is a payload from one repository/organization mutating another repository's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team," and can contribute to an unauthorized deploy/merge decision on the victim's stack since commit state feeds into deployability and merge-request automation. This is repeatable against any stack/commit whose SHA the attacker can learn (which is public information for essentially all commits), for as many organizations as the attacker administers in Shipit.

### Likelihood Explanation
Preconditions: the attacker needs a legitimate, unprivileged Shipit-onboarded org/repo of their own (to hold a valid `webhook_secret`) — the same precondition already assumed valid per the prompt. No Shipit session, API token, or GitHub App credentials of the target are required. Constructing the forged payload and HMAC signature is trivial scripting; the victim commit SHA is public. This is fully repeatable and requires no race conditions or timing tricks.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, mirroring `Handler#stacks`: require `repository.full_name` in the `status` params schema, resolve the repository via `Repository.from_github_repo_name`, and restrict the `Commit` lookup to `stacks.joins(...).where(sha: params.sha)` (or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status event from org A can write a status onto a commit belonging to org B's stack" do
          victim_commit = shipit_commits(:first) # belongs to some stack/repository, e.g. "shopify/shipit-engine"
          attacker_payload = {
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'attacker/forged',
            'repository' => { 'full_name' => 'attacker-org/some-other-repo', 'owner' => { 'login' => 'attacker-org' } }
          }

          assert_difference -> { victim_commit.statuses.count }, 1 do
            StatusHandler.call(attacker_payload)
          end

          assert_equal 'success', victim_commit.reload.state
        end

        test "PushHandler, by contrast, is scoped and cannot touch an unrelated repository's stack" do
          victim_stack = shipit_stacks(:shipit)
          attacker_payload = {
            'ref' => "refs/heads/#{victim_stack.branch}",
            'after' => 'deadbeef',
            'repository' => { 'full_name' => 'attacker-org/some-other-repo' }
          }

          assert_no_enqueued_jobs only: GithubSyncJob do
            PushHandler.call(attacker_payload)
          end
        end
      end
    end
  end
end
```
Both assertions must hold simultaneously to demonstrate the divergence: `PushHandler` (scoped via `stacks`) refuses to act on `victim_stack` when the payload's `repository.full_name` doesn't match, while `StatusHandler` (unscoped `Commit.where(sha:)`) freely mutates `victim_commit` regardless of the attacker-supplied `repository.full_name`.
