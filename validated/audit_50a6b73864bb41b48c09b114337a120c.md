### Title
Cross-organization commit-status forgery due to org-scoped webhook signature verification vs. globally-scoped status handler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify a webhook against based on the organization named in the payload's `repository.owner.login` field [1](#0-0) , but the handler that actually processes `status` events, `Handlers::StatusHandler#process`, looks up the commit to mutate purely by SHA across the entire `Commit` table, with no scoping to the organization/repository whose secret authenticated the request. [2](#0-1)  This breaks the binding "organization that authenticated == repository/commit that is written."

### Finding Description
Shipit supports multiple GitHub organizations configured in a single instance, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`, which configures `somegithuborg` and `someothergithuborg` side by side) [3](#0-2) . `Shipit::GithubApp#verify_webhook_signature` HMAC-verifies the raw request body against the secret belonging to whichever organization is named in the payload. [4](#0-3) 

`WebhooksController#verify_signature` picks that organization from the untrusted payload itself, before the signature has been checked, using `repository_owner`: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [5](#0-4)  This is correct as a way to select *which* org's secret to check against, as long as the org whose secret is used is also the org whose data is written by the handler.

However, `Handlers::StatusHandler#process` does not re-check any organization or repository binding: it looks up commits with `Commit.where(sha: params.sha)` — a global lookup across every stack/repository tracked by the Shipit instance — and calls `create_status_from_github!` on every match. [2](#0-1)  Unlike `Handlers::Handler#repository_name`/`#stacks`, which scope by `payload.dig('repository', 'full_name')` [6](#0-5) , `StatusHandler` never calls these helpers — it is entirely unscoped.

As a result, an attacker who administers (or otherwise controls the webhook configuration/secret of) **any** GitHub organization that happens to be onboarded to the same multi-tenant Shipit instance can craft a `status` webhook payload where `repository.owner.login` names their own org (so `verify_signature` selects and successfully checks against a secret they know), while `sha` is the commit SHA of a commit belonging to a completely different, victim organization's repository/stack tracked by the same Shipit instance. Git commit SHAs are not secret (they're visible via the GitHub API/commit history of the victim repo), so the attacker can target any known commit.

### Impact Explanation
Commit statuses drive Shipit's CI-gating logic for deploys (`ignore_ci`, deployable checks, etc., as documented for `review`/CI behavior in the README). Forging a `success` status for a commit in a repository/organization the attacker has no access to lets that attacker manipulate whether that commit is considered deployable in the victim's stack, without ever authenticating to the victim org, holding a Shipit session, or possessing an `ApiClient` token — only requiring knowledge of a webhook secret for an unrelated, attacker-controlled org that is also configured in the same Shipit deployment. This can result in an unauthorized/incorrectly-gated deploy of a victim stack, which falls under the Critical impact category ("unauthorized deploy") defined for this scan.

### Likelihood Explanation
Exploitation requires only that the attacker legitimately controls a GitHub org/webhook that is registered as a *separate*, unrelated tenant on the same shared Shipit installation — a realistic and common deployment topology, exactly the one the project's own sample config demonstrates by listing multiple organizations under `Shipit.github`. No repository access, Shipit account, or credentials belonging to the victim organization are required; only the target commit SHA, which is public.

### Recommendation
`Handlers::StatusHandler` (and any other handler that does a plain lookup without going through `stacks`/`repository_name`) should scope its `Commit` lookup to the repository identified in the verified webhook payload, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, ensuring the organization used to verify the HMAC signature is the same organization whose commits/stacks are mutated. More generally, `WebhooksController#verify_signature` should pin the verified organization for the remainder of request processing, and every handler should assert that the repository/stack it acts on belongs to that same organization before performing any writes.

### Proof of Concept
1. Attacker administers GitHub org `attacker-org`, which has a repository tracked by Shipit as `attacker-org/some-repo` (secret known to attacker: `S_attacker`).
2. Victim org `victim-org` has a repository `victim-org/app` tracked by the same Shipit instance, with a known public commit `abc123...`.
3. Attacker crafts a JSON body:
   ```json
   {
     "sha": "abc123...",
     "state": "success",
     "context": "ci/build",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(S_attacker, body)>` and sends it with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` to `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and the signature verifies successfully because the attacker signed with their own known secret. [1](#0-0) 
6. `Handlers::StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, finds the commit belonging to `victim-org/app`, and writes a forged `success` status onto it — despite the request never being authenticated against `victim-org`'s webhook secret. [2](#0-1)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
