### Title
Hare-round leftover apportionment in `pox_5_make_signer_set` is manipulable by splitting one stake across multiple `signer_key`s, granting weight beyond the merged-entry maximum - ([File: stackslib/src/chainstate/nakamoto/signer_set.rs])

### Summary
`NakamotoSigners::pox_5_make_signer_set` allocates the fixed `reward_slots` pool by flooring each signer's `stacked_amt / threshold` and handing out the remaining "leftover" slots one-per-signer to the entries with the largest fractional remainder, ties broken by ascending `signing_key`. Because floor is subadditive and the leftover round grants at most one bonus slot per distinct `signer_key` entry, an attacker who fragments one total stake `S` across `k` distinct `signer_key`s can win up to `k` leftover bonuses instead of the single bonus (`f` or `f+1`) available to a merged entry of the same `S`, for the same amount of STX actually locked.

### Finding Description
The claimed equality is: *total leftover-round bonus weight awarded across attacker-controlled keys ≤ 1 slot's worth of rounding credit per unit of STX actually locked* (i.e. splitting one position across `k` keys must not raise the attacker's total weight above what a single unsplit entry of the same total `S` would receive: `weight(unsplit) ∈ {f, f+1}` where `f = floor(S/threshold)`).

Tracing `pox_5_make_signer_set` ( [1](#0-0) ):
- Entries are aggregated **per `signer_key`** into a `HashMap` (line 852-855), so two different `signer_key`s controlled by the same staker are never merged - they remain two independent `Apportionment` rows.
- Base weight is `floor(stacked_amt/threshold)` per row (line 887), and `floor` is subadditive: `floor(a/t)+floor(b/t) ≤ floor((a+b)/t)`. Splitting can only reduce (never increase) the summed base weight versus keeping the stake merged.
- The reduced base sum increases the global `leftover = reward_slots - assigned` (line 894), and the leftover round (lines 896-911) grants **one +1 bonus per distinct entry**, sorted by remainder descending, ties broken by `signing_key` ascending.
- By choosing split amounts `S1, S2` (with `S1+S2=S`) so that both remainders (`S1 mod threshold`, `S2 mod threshold`) rank near the top of the leftover sort - and since the attacker also controls the `signing_key` values used for tie-breaking - the attacker can capture **both** of the two leftover slots that exist as two entries, whereas as a single merged entry it could only ever win **one** bonus.

Concrete counter-example: with `reward_slots = 2`, attacker stake `S` and a legitimate signer `B` with stake `X`, chosen so `S < threshold` and `X < threshold` (both floor to 0): merged case gives entries `{A(S), B(X)}`, `leftover = 2`, both win → `A` gets weight 1. Split case gives `{A1(S1), A2(S2), B(X)}` with the same total locked value; if `A1,A2` are crafted to have the two largest remainders, `A` wins both leftover slots (weight 2) while `B` gets 0. Formally, `split_max = f + k` (bounded only by number of distinct keys `k`) versus `merged_max = f + 1`. For `k ≥ 2` the attacker's total weight can exceed the merged maximum, i.e., signing weight exceeds what is justified per unit of locked STX.

The property test `pox_5_make_signer_set_props` ( [2](#0-1) ) only asserts a **global** bound (`total_weight <= reward_slots`) and per-key bounds (`weight ∈ {base, base+1}`) — it never asserts anything about the relationship between a single actor's total weight when the actor's own stake is fragmented across multiple keys versus kept merged, so this manipulation is not caught by existing tests or by any guard in `pox_5_compute_and_update_signers` (`stackslib/src/chainstate/nakamoto/signer_set.rs` lines 744-820), which performs no cross-key ownership analysis before calling `pox_5_make_signer_set`.

None of the reentrancy/prepare-phase/lock-period guards referenced in the question's "Validate" checklist (`verify-not-prepare-phase`, `signer-manager-call-active`, `check-pox-lock-period`, `verify-signer-key-grant`) address this — they are concerned with double-registration and reentrancy, not with the fairness of the largest-remainder apportionment across an attacker's own multiple keys.

### Impact Explanation
The affected value is **signing weight** (number of reward/signature slots), which drives how much influence a signer has over Nakamoto block signing and reward distribution. An attacker can obtain a disproportionate share of the fixed `reward_slots` pool relative to the STX they actually lock, at the direct expense of other signers who would otherwise have won those slots. This matches the "High" category: *"signing weight or reward slots exceeding locked value."* The total system-wide weight remains bounded by `reward_slots` (it is a redistribution, not a global mint), so the practical effect is one attacker capturing more of the fixed slot budget than their stake proportionally warrants, each reward cycle, for as long as they maintain the fragmented positions - i.e., it is repeatable every cycle.

### Likelihood Explanation
Exploitation only requires an unprivileged staker to lock the same total STX across two (or more) accounts/positions using two self-chosen `signer_key`s rather than one — an entirely permissionless action available to any staker at any time a cycle's signer set is computed (`pox_5_compute_and_update_signers`, invoked during prepare-phase processing). The gain per split key is capped at +1, and its magnitude relative to the honest baseline depends on the attacker's stake landing near a remainder tie against other signers and on `threshold` sizing (larger `reward_slots`/smaller `threshold` dilutes the effect), so the absolute weight gained per cycle is small (bounded by `k-1` extra slots for `k` split entries) but reliably reproducible and costs the attacker nothing beyond normal staking.

### Recommendation
Change the leftover ("Hare round") distribution so it cannot be gamed by an actor controlling multiple `signer_key`s for what is effectively one economic position: e.g., cap the number of leftover bonus slots any single beneficiary-linked group of keys can receive to one, or restructure remainder ranking to be computed against a canonical staker/beneficiary identity rather than raw `signer_key`, if such an identity is available in pox-5's data model. At minimum, document and evaluate whether this parity with real-world proportional signing power is an accepted design trade-off (as fragmentation attacks are a known general weakness of largest-remainder apportionment methods), since a complete fix may require identifying and merging related stakers before the floor/remainder computation.

### Proof of Concept
Extend `pox_5_make_signer_set_props` (or add a targeted unit test) in `stackslib/src/chainstate/nakamoto/tests/signer_set.rs`:
1. Fix `pox_constants` with `reward_slots() == 2`.
2. Construct entry `B` with `amount_ustx = X` and entry `A` (merged) with `amount_ustx = S`, both `< threshold = ceil((S+X)/2)`, so both floor to 0 and both win the two leftover slots (`weight_A_merged = 1`).
3. Run `pox_5_make_signer_set` on `[A(S), B(X)]` and record `weight_A_merged`.
4. Split `S` into `S1, S2` (`S1+S2=S`) chosen with `signer_key`s `k1 < k2` such that `S1 mod threshold` and `S2 mod threshold` both exceed `X mod threshold` (still with `threshold` unchanged since `S1+S2+X` total is identical).
5. Run `pox_5_make_signer_set` on `[A1(S1), A2(S2), B(X)]`; assert `weight_A1 + weight_A2 > weight_A_merged` (concretely `2 > 1`) and `weight_B` drops from `1` to `0` for the identical total locked STX.
6. Assert the broken equality directly: `weight(A1)+weight(A2) > merged_weight(S1+S2)`, demonstrating the invariant "total leftover slots to attacker-controlled keys ≤ 1 rounding credit per unit of STX locked" fails.

    pub(crate) fn pox_5_make_signer_set<I>(
        entries: &mut I,
        pox_constants: &PoxConstants,
    ) -> Result<Pox5SignerSetOutput, ChainstateError>
    where
        I: Iterator<Item = Result<RawPox5Entry, PoxEntryParsingError>>,
    {
        let mut signer_set = HashMap::new();
        let mut total_ustx_locked = 0u128;
        for entry_res in entries {
            let entry = match entry_res {
                Ok(x) => x,
                Err(PoxEntryParsingError::Skip(err_str)) => {
                    warn!(
                        "Error while iterating PoX-5 entries, impacting a single entry. Dropping entry from signer set";
                        "error" => err_str
                    );
                    continue;
                }
                Err(PoxEntryParsingError::Abort(err_str)) => {
                    error!(
                        "Abort-triggering error while iterating PoX-5 entries";
                        "error" => err_str
                    );
                    return Err(ChainstateError::PoxNoRewardCycle);
                }
            };

            total_ustx_locked += entry.amount_ustx;

            signer_set
                .entry(entry.signer_key)
                .and_modify(|existing_entry| *existing_entry += entry.amount_ustx)
                .or_insert_with(|| entry.amount_ustx);
        }

        // Allocate `reward_slots` weight across signers in proportion to stake using the
        // a largest-remainder method:
        //
        // The threshold is `ceil(total / reward_slots)`.
        //
        // Flooring each signer's `stacked / threshold` assigns a base weight where the sum is `<= reward_slots`
        // (the ceil makes `total/threshold <= reward_slots`).
        //
        // This leaves some unassigned ("leftover") slots, which are handed out one-per-signer
        //  in descending fractional-remainder order (ties broken by pubkey-sort order).
        //
        // This avoids degenerate modes of the floor-and-drop scheme: when more than
        // `reward_slots` distinct signers hold roughly equal stake, every base weight floors to
        // 0, and without the leftover round the entire signer set could be dropped.
        let reward_slots = u128::from(pox_constants.reward_slots());
        let threshold = std::cmp::max(1, total_ustx_locked.div_ceil(reward_slots));

        struct Apportionment {
            signing_key: [u8; SIGNERS_PK_LEN],
            stacked_amt: u128,
            weight: u128,
            remainder: u128,
        }

        let mut apportioned: Vec<Apportionment> = signer_set
            .into_iter()
            .map(|(signing_key, stacked_amt)| Apportionment {
                signing_key,
                stacked_amt,
                weight: stacked_amt / threshold,
                remainder: stacked_amt % threshold,
            })
            .collect();

        // Guaranteed `<= reward_slots` by the ceil quota, so leftover does not underflow.
        let assigned: u128 = apportioned.iter().map(|entry| entry.weight).sum();
        let mut leftover = reward_slots.saturating_sub(assigned);

        if leftover > 0 {
            // Largest fractional remainder wins the next slot; ties broken by signing_key
            // ascending so the apportionment is deterministic (and matches the final sort).
            apportioned.sort_by(|a, b| {
                b.remainder
                    .cmp(&a.remainder)
                    .then_with(|| a.signing_key.cmp(&b.signing_key))
            });
            for entry in apportioned.iter_mut() {
                if leftover == 0 {
                    break;
                }
                entry.weight += 1;
                leftover -= 1;
            }
        }
