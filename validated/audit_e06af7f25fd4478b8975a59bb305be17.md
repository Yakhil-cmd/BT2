### Title
Cross-organization status/webhook forgery via unbound `repository_owner` signature key vs. globally-scoped commit lookup - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify a webhook's HMAC signature against using `repository_owner`, a value taken straight out of the untrusted JSON payload (`params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`). The signature therefore only proves the request was signed by *some* organization configured in `Shipit.github`, not that it was signed by the organization that owns the repository/commit the payload claims to affect. Downstream handlers such as `StatusHandler` then act on data (`Commit.where(sha: params.sha)`) using fields that are never covered by that verification step and are **global**, not scoped to the authenticating organization or even to `repository.full_name`.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-38` (`verify_signature`) computes `repository_owner` from the payload body and fetches `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that organization's `webhook_secret`: [1](#0-0) [2](#0-1) 

In a multi-organization Shipit deployment (explicitly supported, see `config/secrets.development.example.yml` and `docs/setup.md`), each organization has its own independent `webhook_secret`. An attacker who administers/owns any one of these configured GitHub organizations (or any organization for which they can obtain a signed webhook, e.g. via their own GitHub App/organization membership) knows or controls that organization's `webhook_secret` and can therefore forge a validly-signed request to `/webhooks` by setting `repository.owner.login` (or `organization.login`) to their own org in the JSON body, satisfying `verify_signature`.

Once the signature check passes, `WebhooksController#create` dispatches the **entire, attacker-controlled payload** to the relevant handler based only on the `X-Github-Event` header: [3](#0-2) 

`StatusHandler#process` never re-checks any repository/organization binding — it looks up commits purely by `sha`, which is a global, cross-stack, cross-organization identifier: [4](#0-3) 

So the field that was authenticated (`repository.owner.login`/`organization.login`, used to pick the HMAC key) is never the field that is acted upon (`sha`, matched globally against `Commit.sha` regardless of which stack/repository/organization owns that commit). This is exactly the "organization that authenticated versus the repository that is written" trust binding described in scope: `organization_that_signed == organization_that_owns_repository` is assumed but never checked.

`Commit#create_status_from_github!` → `add_status` can flip a commit's simple status from pending/unknown to `success`, and on that transition calls `stack.schedule_merges` and, via `after_commit` on creation, `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` and `stack.deployable?` are true: [5](#0-4) [6](#0-5) 

Similarly `PushHandler`, `CheckSuiteHandler`, and the pull-request handlers all key off `repository.full_name` from the same unauthenticated payload region (`Handler#repository_name`) rather than the organization whose secret validated the signature: [7](#0-6) 

### Impact Explanation
For any Shipit instance configured with more than one GitHub organization (the documented and supported multi-org configuration), an attacker who controls one of those organizations (and thus its `webhook_secret`) can send a validly-signed `status` webhook whose `sha` matches a commit belonging to a *different* organization's stack. Because the commit lookup is global and not scoped by the authenticated organization, this can flip that commit's aggregate CI status to `success`, which is exactly the trigger `schedule_continuous_delivery` checks (`deployable? && stack.continuous_deployment? && stack.deployable?`). If continuous deployment is enabled on the victim stack, this results in an **unauthorized deploy** of a commit that never actually passed the victim organization's own CI — a Critical-tier impact (unauthorized deploy) per the scoped rules. The same organization-vs-repository binding gap also lets the same attacker use `push`/`check_suite`/pull-request webhooks to spoof sync, provisioning, or archival actions against stacks belonging to other organizations, since `Handler#repository_name` and `stacks` are derived purely from the unauthenticated `repository.full_name` field.

### Likelihood Explanation
Requires the deployment to have at least two organizations configured under `Shipit.github` (explicitly documented as supported) and the attacker to control one of them (their own GitHub org, or an org where they can leak/derive the `webhook_secret`, which the organization admin themselves possesses legitimately). No Shipit session, `ApiClient` token, or repository write access on the *victim* repo is required — only the ability to sign a payload with a secret the attacker legitimately owns for their own org. This is a realistic scenario for any shared/public/self-serve Shipit instance onboarding multiple external organizations.

### Recommendation
Bind the field used for handler dispatch/authorization to the field used for signature verification: after `verify_webhook_signature` succeeds for `repository_owner`, every downstream handler must re-validate that the repository/stack it is about to act on actually belongs to that same `repository_owner`/organization (e.g., pass the verified organization into `Handler.call` and have `Handler#stacks`/`StatusHandler#process` filter/reject records whose repository owner does not match). For `StatusHandler` specifically, scope the `Commit` lookup by repository/stack owned by the verified organization instead of a global `sha` match.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-org config as in `config/secrets.development.example.yml`).
2. Attacker, who legitimately administers `attacker-org`'s GitHub App and therefore knows `attacker-org`'s `webhook_secret`, crafts a JSON body:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
     "sha": "<sha of a commit belonging to victim-org's stack with continuous_deployment enabled>",
     "state": "success",
     "context": "ci/forged"
   }
   ```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this body and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-38`).
5. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) finds the commit by `sha` alone (belonging to `victim-org`'s stack) and calls `create_status_from_github!`, potentially flipping its status to `success` and triggering `schedule_continuous_delivery` → `ContinuousDeliveryJob`, causing an unauthorized deploy on the victim's stack, even though the attacker has no credentials, membership, or push access on `victim-org`.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
