### Title
`pallet-nfts` accepts `MintSettings` with `start_block` after `end_block`, permanently blocking public/collection minting - ([File: substrate/frame/nfts/src/features/settings.rs])

### Summary
`pallet_nfts::Pallet::do_update_mint_settings` writes a caller-supplied `MintSettings { start_block, end_block, .. }` into `CollectionConfigOf` without checking that `start_block <= end_block` (or that either is in the future). This is a direct FRAME analog of the reported `MerkleReserveMinter._setMintSettings` issue: a normal, non-privileged collection role (`Issuer`) can configure a mint window that can never be satisfied, or that closes before it opens, blocking legitimate minting for that collection.

### Finding Description
`update_mint_settings` is a signed extrinsic reachable by any account holding the `CollectionRole::Issuer` role for a collection (granted to any collection creator by default via `create`), i.e. a completely non-privileged, ordinary user action: [1](#0-0) 

The handler `do_update_mint_settings` only checks the `Issuer` role, then blindly overwrites `config.mint_settings` with the caller-supplied value — there is no validation that `start_block <= end_block`: [1](#0-0) 

`MintSettings` is defined with independent, unconstrained `Option<BlockNumber>` fields for `start_block` and `end_block`: [2](#0-1) 

These values are only consumed later, at mint time, in `Pallet::mint`, which checks `start_block <= now` and `end_block >= now` independently — it never validates the relative ordering of the two bounds: [3](#0-2) 

If `start_block > end_block`, then for every block number `now`:
- If `now < start_block`, `MintNotStarted` fires.
- If `now >= start_block > end_block`, then `now > end_block`, so `MintEnded` fires.

There is no value of `now` for which both conditions pass, so minting becomes permanently impossible for that collection — exactly the "mintStart chronologically later than mintEnd" scenario described in the Sherlock report for `MerkleReserveMinter`.

This is a genuine analog: same root cause (unchecked ordering of a two-sided time window on a caller-writable settings struct), same actor class (non-privileged token/collection owner-equivalent role), same consequence (self-inflicted, irreversible minting lockout).

### Impact Explanation
Impact is limited to griefing/self-DoS of a single collection's minting: the collection issuer (who chose to submit these bad settings) or third parties depending on that collection's mint (e.g., holder-of-collection claim mechanics) can no longer mint. No funds are stolen, no unbacked issuance occurs, and no cross-account/cross-pallet state is corrupted — this matches the **Medium** severity classification of the original report, not a Critical/High theft or issuance bug. It is a permanent (until another `update_mint_settings` call fixes it) integrity/availability defect confined to the affected collection.

### Likelihood Explanation
High likelihood of occurring accidentally (fat-fingered block numbers, off-by-one errors, UI misconfiguration), since any `Issuer`-role account can trigger it with a single call and no economic cost beyond the transaction fee. It requires no privileged role beyond the collection's own issuer permission, which is granted to any collection creator by default.

### Recommendation
In `do_update_mint_settings` (and equally in the `create`/`force_create` path that first establishes `CollectionConfig::mint_settings`), validate that when both `start_block` and `end_block` are `Some`, `start_block <= end_block` before persisting, returning a new `Error::<T, I>::WrongSetting` (or similar) otherwise.
