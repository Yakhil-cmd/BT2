### Title
Data-feed key construction uses unescaped `\n` as a field delimiter, allowing feed-name/value delimiter injection - ([File: data_feeds.js])

### Summary
The oscript/AA `in data feed` mechanism and the raw `data_feed` message app let any unit author post arbitrary `feed_name`/`value` strings. These strings are concatenated with a hard-coded `\n` separator to build KV-store keys (`'df\n'+address+'\n'+feed_name+'\n'+prefixed_value`), but neither `feed_name` nor `value` is checked for embedded `\n` bytes before being written or before being used to build range-scan boundaries. Downstream code recovers the fields by naive `split('\n')` with fixed index assumptions, creating the same encoder/decoder asymmetry described in the cowlib advisory: the writer emits any byte (including the delimiter) while the reader trusts positional splitting.

### Finding Description
Data feed keys are built in three places with the same unescaped pattern:
- `data_feeds.js` `dataFeedByAddressExists`/`readDataFeedByAddress`: `var key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value;` [1](#0-0) 
- `main_chain.js` `addDataFeeds` (called on stabilization for every author of a `data_feed` message): `batch.put('df\n'+address+'\n'+feed_name+'\ns\n'+strValue+'\n'+strMci, unit);` [2](#0-1) 
- `migrate_to_kv.js` mirrors the same unescaped construction. [3](#0-2) 

The reading side blindly trusts fixed-position splitting on `\n`:
- `string_utils.js` `getMciFromDataFeedKey` takes the *last* `\n`-delimited chunk as the mci. [4](#0-3) 
- `getValueFromDataFeedKey` requires exactly 6 `\n`-delimited parts and reads `m[3]` (type) and `m[4]` (value) positionally. [5](#0-4) 
- Range-scan bounds for relational queries are built by string-concatenating `feed_name` again with `\n`/`\r`: `options.lt = 'df\n'+address+'\n'+feed_name+'\n'+type+'\r';` [6](#0-5) 

The `in data feed`/`data feed` definition/oscript validators only bound the *length* of `feed_name`/`value`, not their byte content: `if (feed_name.length > constants.MAX_DATA_FEED_NAME_LENGTH) ... if (value.length > constants.MAX_DATA_FEED_VALUE_LENGTH)`. [7](#0-6) 

By contrast, the in-memory "unstable AA" lookup path treats `feed_name` as an exact JS object property key (`payload.hasOwnProperty(feed_name)` / `payload[feed_name]`), which has no notion of a `\n` delimiter at all: [8](#0-7) 

Because one code path (pre-stabilization, in-memory) resolves `feed_name` by exact object-key match while the other (post-stabilization, on-disk KV keys/range scans) resolves it via `\n`-delimited byte layout with no escaping, a `feed_name`/`value` string containing embedded `\n` bytes can be crafted so that:
1. The exact-match unstable-AA lookup sees it as one distinct feed name/value.
2. The persisted KV key, once split positionally, is parsed by `getValueFromDataFeedKey`/`getMciFromDataFeedKey` as a *different* set of fields (wrong type/value/mci boundary), and range-scan prefix/bound strings built from the same unescaped `feed_name` can unintentionally widen or shift the `gte/lt` bounds used by `>` , `>=`, `<`, `<=` relational feed lookups.

This is directly analogous to the cowlib bug class: an encoder that fails to escape/reject the structural delimiter byte, paired with a decoder that trusts strict positional parsing of that same delimiter, enabling the attacker-controlled payload to redefine field boundaries.

### Impact Explanation
`in data feed` conditions gate address-unlock authentication and `data_feed` oracle lookups are used inside AA formulas (`data_feed(...)` function) to drive fund transfers/business logic. If the pre-stabilization and post-stabilization data-feed lookup paths can disagree on whether a given `feed_name`/`value` condition is satisfied (because one reads exact JS keys and the other reads `\n`-delimited byte-shifted KV keys), different nodes — or the same node before/after stabilization — can compute different validity/response results for the same AA trigger or address-definition authentication. That is a concrete "node disagreement on validity" scenario, and if it affects AA execution it can also translate into AA fund loss/freezing if the AA takes a different bonus/branch depending on which lookup path answered `data_feed()`/`in data feed`.

### Likelihood Explanation
Reachable by an unprivileged unit poster: any author can post a `data_feed` message with attacker-chosen `feed_name`/`value` strings (subject only to `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH`, not to content restrictions), and any AA author/trigger sender can reference `in data feed`/`data_feed()` conditions that consume such feeds. No special privilege, hub cooperation, or peer compromise is required — this is purely a self-inflicted encoding bug reachable from ordinary unit/message construction.

### Recommendation
- Reject (or escape) `\n` (and any other byte used as the KV-key delimiter, e.g. `\r`) inside `feed_name` and string `value` at the same validation points that already enforce `MAX_DATA_FEED_NAME_LENGTH`/`MAX_DATA_FEED_VALUE_LENGTH` in `definition.js` (`in data feed` case) and wherever the `data_feed` app payload is validated.
- Alternatively, switch the KV key encoding to a length-prefixed or escaped scheme (similar to `getSourceString`'s `\x00`-based encoding, which already throws on embedded join characters) so the encoder rejects any value containing the delimiter, keeping encoder and decoder symmetric.
- Audit `getMciFromDataFeedKey`/`getValueFromDataFeedKey` to fail closed (throw) rather than silently mis-parsing when the number of `\n`-delimited segments doesn't match expectations for a given `address`/`feed_name` pair.

### Proof of Concept
1. Author A posts a `data_feed` message with `payload = { "real_feed\nn\n7FFFFFFF": "1" }` (embedding a fabricated `\nn\n<hex>` fragment that mimics the type/value/mci layout inside the `feed_name` string). `definition.js`'s only checks are length-based, so this passes validation. [7](#0-6) 
2. Before stabilization, `dataFeedExists`/`readDataFeedValue`'s in-memory path does an exact `payload.hasOwnProperty(feed_name)` check against the *whole* crafted string as a single JS object key — it only matches queries for the exact crafted `feed_name`. [8](#0-7) 
3. After stabilization, `main_chain.js`'s `addDataFeeds` persists the KV key `'df\n'+address+'\nreal_feed\nn\n7FFFFFFF\ns\n1\n'+strMci`. When a later oscript query for the plain `feed_name = "real_feed"` performs a `>`/`>=`/`<`/`<=` range scan, the bound string `'df\n'+address+'\n'+"real_feed"+'\n'+type+'\r'` no longer aligns with the persisted key's actual delimiter positions, causing the crafted entry to fall inside or outside the intended `feed_name` range depending on relation, producing a different boolean result than the exact-match pre-stabilization check gave for the same underlying trigger. [6](#0-5)

function getMciFromDataFeedKey(key){
	var arrParts = key.split('\n');
	var strReversedMci = arrParts[arrParts.length-1];
	var reversed_mci = parseInt(strReversedMci, 16);
	var mci = 0xFFFFFFFF - reversed_mci;
	return mci;
}
