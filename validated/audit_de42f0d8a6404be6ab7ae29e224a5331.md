### Title
Swap instructions lack transaction expiration/deadline protection - ([File: programs/cp-swap/src/instructions/swap_base_input.rs])

### Summary
The `swap_base_input` and `swap_base_output` instructions (and likewise `deposit`/`withdraw`) only enforce slippage bounds via `minimum_amount_out` / `max_amount_in`, but accept no deadline or expiration timestamp parameter from the caller. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_base_input` and `swap_base_output` check the pool's `open_time` and status bit but never validate that the transaction is being executed within a caller-specified time window. [3](#0-2)  The only price-protection mechanism is `require_gte!(amount_received, minimum_amount_out, ErrorCode::ExceededSlippage)` for base-input swaps and the analogous `max_amount_in` check for base-output swaps. [4](#0-3) [5](#0-4)  The corresponding `swap_base_input`/`swap_base_output` entrypoints in `lib.rs` also take no deadline argument. [6](#0-5) 

Because Solana transactions can remain valid/unlanded in the mempool until the referenced blockhash expires (roughly ~150 slots, on the order of a minute or more depending on validator/leader scheduling and network congestion), a signed swap transaction can sit unconfirmed while the pool's constant-product price drifts due to other trades. When it is finally landed, the trade executes at the pool's *current* price at execution time rather than the price the user intended, bounded only by the user's chosen slippage tolerance (`minimum_amount_out`/`max_amount_in`). If the user set a wide slippage tolerance (to avoid frequent failures) or if the price moves adversely within that tolerance band while still passing the check, the transaction executes at a materially worse price than intended, without any mechanism for the user to cap the maximum allowable staleness of their own request.

### Impact Explanation
This is a real economic-loss vector for swappers: value that should have gone to the user, or that the user intended to trade at a specific market condition, is instead captured by whichever price the pool is at when the delayed transaction eventually lands (e.g., after a validator/searcher intentionally delays inclusion, or after network congestion). Since slippage protection exists but no expiration/deadline exists, the user's only recourse is setting an extremely tight `minimum_amount_out`, which then risks transaction failure; there is no way to bound the time-risk independently of the price-risk. This matches the reachable, unprivileged-user path (`swap_base_input`/`swap_base_output`) called out in scope.

### Likelihood Explanation
Likelihood is moderate: it requires a delayed transaction landing (achievable via mempool congestion, or by a validator/searcher deliberately withholding and later including a profitable stale swap) combined with meaningful price movement within the slippage window during that delay. No special privileges are required to trigger it beyond normal transaction submission by any user.

### Recommendation
Add a `deadline: i64` (or `expiry_ts`) parameter to `swap_base_input`, `swap_base_output`, `deposit`, and `withdraw`, and validate `Clock::get()?.unix_timestamp <= deadline` (or block_timestamp <= deadline) at the start of each instruction, returning an error such as `ErrorCode::TransactionExpired` if the deadline has passed. This lets callers bound the maximum acceptable execution delay independently of price slippage tolerance.

### Proof of Concept
1. A user submits a `swap_base_input` transaction with `amount_in` and a `minimum_amount_out` computed from the current pool price with a slippage tolerance (e.g., 1%).
2. The transaction is not immediately included (e.g., held by a validator/searcher, or delayed due to network congestion) while still referencing a blockhash that has not yet expired.
3. During the delay, other trades move the pool price such that the user's `minimum_amount_out` is still technically satisfied at execution time but represents a materially worse rate than what was available when the user signed the transaction.
4. The transaction lands and executes at the degraded, but still slippage-compliant, price — the user has no way to have bounded this because `swap_base_input` accepts no expiration timestamp. [7](#0-6)

pub fn swap_base_input(ctx: Context<Swap>, amount_in: u64, minimum_amount_out: u64) -> Result<()> {
    let block_timestamp = solana_program::clock::Clock::get()?.unix_timestamp as u64;
    let pool_id = ctx.accounts.pool_state.key();
    let pool_state = &mut ctx.accounts.pool_state.load_mut()?;
    if !pool_state.get_status_by_bit(PoolStatusBitIndex::Swap)
        || block_timestamp < pool_state.open_time
    {
        return err!(ErrorCode::NotApproved);
    }

    let transfer_fee =
        get_transfer_fee(&ctx.accounts.input_token_mint.to_account_info(), amount_in)?;
    // Take transfer fees into account for actual amount transferred in
    let actual_amount_in = amount_in.saturating_sub(transfer_fee);
    require_gt!(actual_amount_in, 0);
