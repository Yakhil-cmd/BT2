## Title
AA trigger validation releases the author-address lock before `writer.saveJoint()` completes, allowing concurrent dry-run and real AA executions to race on shared state - (File: `aa_composer.js`)

### Summary
In `aa_composer.js`, `validateAndSaveUnit()` calls `validation_unlock()` immediately upon entering `ifOk`, **before** `writer.saveJoint()` runs and mutates process-wide caches/state (`storage.assocUnstableUnits`, balance tracking, etc.). This mirrors the FUSE CVE-2026-53388 bug class: a lock is dropped on entry to a success path instead of being held until the subsequent mutation/replace step actually completes, opening a window where a second concurrent operation can interleave with the still-in-progress mutation of shared state guarded by that very lock.

### Finding Description
`validateAndSaveUnit()` in `aa_composer.js` is used by `handleTrigger()` for both real AA trigger execution and dry-run AA execution (`dryRunPrimaryAATrigger`): [1](#0-0) 

Note the sequence in the `ifOk` callback:
1. `validation_unlock()` is called immediately - releasing the mutex lock taken on `arrAuthorAddresses` (i.e., the AA's own address) inside `validation.validate()`.
2. Only afterwards is `writer.saveJoint()` invoked, with `objAAValidationState.bUnderWriteLock = true`, which makes `writer.saveJoint()` **skip acquiring the global `"write"` mutex** entirely: [2](#0-1) 

Contrast this with every other caller of `validation.validate()` in the codebase (`composer.js`, `divisible_asset.js`, `indivisible_asset.js`, `network.js`), which all defer `validation_unlock()`/`combined_unlock()` until *after* `writer.saveJoint()` finishes: [3](#0-2) [4](#0-3) 

In `aa_composer.js`, this ordering is inverted. The address-level lock exists precisely to serialize access for a given address while its associated unit is being validated and saved (mirroring the standard `validation.js` pattern), and `bUnderWriteLock` further relies on the caller already guaranteeing serialization instead of the global `"write"` lock. Releasing that lock before `writer.saveJoint()` runs breaks this invariant.

This function is reachable concurrently from two independent paths for the *same* AA address:
- The real trigger path via `handleAATriggers()`, serialized only by the `'aa_triggers'` mutex key, not by address.
- The dry-run path `dryRunPrimaryAATrigger()`, reachable by any unprivileged peer through the `light/dry_run_aa` network request, and automatically invoked for every incoming payment unit addressed to an AA when `conf.bDryRunNewTriggers` is set: [5](#0-4) [6](#0-5) [7](#0-6) 

Both `handleAATriggers()` (real) and `dryRunPrimaryAATrigger()` (attacker-triggerable) eventually invoke `validateAndSaveUnit()` for the same target AA address, each with `bUnderWriteLock=true`, so `writer.saveJoint()` never takes the global `"write"` lock. The address-scoped lock was the only remaining serialization mechanism preventing concurrent `writer.saveJoint()` calls that mutate shared, process-global caches (`storage.assocUnstableUnits`, `storage.assocStableUnits`, balance caches, main-chain state) for the same address. Since it is released before `writer.saveJoint()` starts, an attacker can send crafted units/dry-run requests timed to overlap with real AA trigger processing for the same AA, causing two `writer.saveJoint()` executions to run concurrently against shared in-memory state without any mutual exclusion.

### Impact Explanation
Concurrent unsynchronized mutation of `storage.js`'s global caches by two overlapping `writer.saveJoint()` invocations for the same AA address can corrupt the node's view of unstable/stable units, balances, and main-chain bookkeeping for that AA. This can lead to nodes disagreeing on unit validity/stability, incorrect AA balance computation (fund loss or freezing for the AA), or a corrupted cache state that prevents the network from correctly confirming subsequent units touching that AA - satisfying the "node disagreement on validity/stability" and "AA fund loss or freezing" impact classes.

### Likelihood Explanation
The dry-run path is directly reachable by an unprivileged peer (`light/dry_run_aa` command, or automatically for every payment to an AA when `bDryRunNewTriggers` is enabled), and real AA trigger execution happens automatically whenever any unit trigger to that AA stabilizes. An attacker who controls the timing of triggers/dry-run requests to a target AA can realistically create the overlap window between the early `validation_unlock()` and the completion of `writer.saveJoint()`, especially given the asynchronous, multi-step nature of `writer.saveJoint()` (multiple DB queries, kvstore batch writes, cache updates).

### Recommendation
Move `validation_unlock()` in `aa_composer.js`'s `validateAndSaveUnit()` to occur only after `writer.saveJoint()` completes (matching the pattern used in `composer.js`, `divisible_asset.js`, `indivisible_asset.js`, and `network.js`), so the address lock is held for the entire duration of the save, preventing overlapping `writer.saveJoint()` executions for the same address.

### Proof of Concept
1. Deploy an AA at address `X`.
2. Trigger a real payment to `X` so that `handleAATriggers()` begins processing a trigger for `X` (entering `validateAndSaveUnit` → `ifOk` → `validation_unlock()` is called, then `writer.saveJoint()` starts its multi-step async work).
3. During that window, send a `light/dry_run_aa` request (or a normal payment unit to `X` while `conf.bDryRunNewTriggers` is enabled) targeting the same address `X`, invoking `dryRunPrimaryAATrigger()`, which independently reaches `validateAndSaveUnit()` for the same address and is no longer blocked by the address mutex (already released by step 2).
4. Both `writer.saveJoint()` calls now execute concurrently against shared `storage.js` caches for address `X` without the `"write"` mutex (bypassed via `bUnderWriteLock`) or the address mutex (already released) serializing them, corrupting cache state for `X`.
