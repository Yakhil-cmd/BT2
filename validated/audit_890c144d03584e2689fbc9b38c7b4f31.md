### Title
`borrow`/`withdraw`/`flash_loan` recipient check only rejects the pool and controller, allowing other protocol contracts to be passed as `to` and permanently strand the transferred tokens - (File: contracts/controller/src/positions/mod.rs)

### Summary
The external report describes a router that forwards tokens to an intermediate address without verifying the preconditions that make that address a valid terminal destination, so funds arrive at a contract that can never release them. The same bug class exists in XOXNO Lending: `require_external_recipient` validates the user-supplied `to` recipient for `borrow` and `withdraw` against only two addresses — the controller itself and the single cached pool address — while other protocol contracts that hold token balances but expose no user-facing withdrawal path (the swap aggregator, the position NFT contract, the governance contract, the price aggregator) are accepted as recipients. Tokens transferred to those addresses are permanently frozen.

### Finding Description
Every user-facing exit flow (`borrow`, `withdraw`, and the flash paths) accepts an optional `to` recipient and funnels it through `require_external_recipient` in `contracts/controller/src/positions/mod.rs:36-43`:

```rust
pub(crate) fn require_external_recipient(env: &Env, cache: &mut Context, recipient: &Address) {
    let pool = cache.cached_pool_address();
    assert_with_error!(
        env,
        *recipient != env.current_contract_address() && *recipient != pool,
        FlashLoanError::InvalidFlashloanReceiver
    );
}
```

The documented intent (comment at `mod.rs:33-35`) is exactly the bug class under audit: "Pool self-transfers debit cash without moving tokens; controller receipts would remain unclaimed by balance-delta accounting." The test suite (`tests/test-harness/tests/controller/recipient_is_protocol_contract.rs:1-5`) states the same rationale: "A borrow or withdraw addressed to the pool or the controller strands the tokens: the pool debits cash without its balance moving, and the controller holds funds no balance-delta measurement can ever claim."

However, the check is an incomplete blocklist. It only compares `recipient` against `env.current_contract_address()` and `cache.cached_pool_address()`. Other protocol contracts — in particular the swap aggregator (`storage::get_swap_aggregator`, used in `strategies/swap.rs:25`), the position NFT contract, and the governance contract — are equally incapable of releasing arbitrary token balances sent to them. The swap aggregator only moves tokens it pulls via `authorize_transfer_as_current` during `execute_strategy`, and the position NFT contract holds NFT state, not a token-redemption path. A borrow or withdraw with `to` set to any of these addresses succeeds, transfers real tokens, and strands them with no recovery path — identical impact to the GH-17 fix but for a wider set of addresses.

This mirrors the Tokemak report's root cause: the code validates the destination against the one case the developers thought of, rather than enforcing the actual invariant — "the recipient must be an address from which the tokens can be moved."

### Impact Explanation
Permanent freezing of user funds. An unprivileged account owner calling `borrow(caller, account_id, legs, Some(swap_aggregator))` or `withdraw(..., Some(position_nft))` receives a successful transaction; the tokens are transferred to a contract that has no function to return them. Unlike a wrong-EOA typo, a protocol contract cannot sign transactions, so the funds are unrecoverable by anyone, including governance, unless a rescue/sweep function exists (the aggregator's sweep is admin-only and not guaranteed to cover arbitrary stranded balances). This is the same stranded-funds outcome the codebase itself acknowledges for the pool/controller case.

### Likelihood Explanation
Medium-to-low likelihood, matching the source report's Medium severity. It requires the caller (or the integrating SDK/frontend building the transaction) to supply a protocol contract address as `to`. This is realistic for integrators: the composition docs (`skills/xoxno-lending-contracts/composing.md`) enumerate many contract addresses a wrapper handles, and an integrator mixing up "the pool" vs "the aggregator" vs "the NFT contract" as a destination is a plausible configuration error — precisely the user-input-validation gap the original finding describes. The caller harms only their own account, so there is no theft incentive, but the freeze is permanent once executed.

### Recommendation
Replace the two-address blocklist with an exhaustive protocol-contract check in `require_external_recipient`, or invert it into an allowlist. Concretely, fetch every registered protocol contract address from storage (pool, controller, `get_swap_aggregator`, position NFT, governance, price aggregator) and reject `recipient` if it matches any of them:

```rust
assert_with_error!(
    env,
    *recipient != env.current_contract_address()
        && *recipient != pool
        && *recipient != storage::get_swap_aggregator(env)
        && *recipient != storage::get_position_nft(env)
        && *recipient != storage::get_governance(env),
    FlashLoanError::InvalidFlashloanReceiver
);
```

Apply the same check in the `flash_position`/`flash_loan` receiver validation (`contracts/controller/src/strategies/flash_position.rs`), which uses the same `InvalidFlashloanReceiver` error and has the same stranding semantics for its receiver contract.

### Proof of Concept
1. Alice supplies USDC collateral and calls `Controller::borrow(alice, account_id, [(eth_key, amount)], Some(swap_aggregator_address))`.
2. `require_external_recipient` passes because the aggregator is neither the controller nor the pool (`mod.rs:38-42`).
3. The pool executes the borrow leg and transfers `amount` of ETH to the swap aggregator address.
4. The aggregator contract has no user-callable function to transfer out an arbitrary received token balance; the borrowed ETH is permanently frozen, while Alice's account now carries ETH debt — she loses both the tokens and owes the debt. The same holds for `withdraw` with `to = position_nft` or `to = governance` addresses.
