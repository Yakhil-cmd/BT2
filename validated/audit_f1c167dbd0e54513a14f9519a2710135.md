### Title
`EnvironmentVariables#interpolate` falls back to the Shipit server's own `ENV` for undeclared `$WORD` tokens, leaking host secrets into task output - ([File: lib/shipit/environment_variables.rb])

### Summary
`Shipit::EnvironmentVariables#interpolate` scans a raw step string for `$WORD` tokens and resolves each one with `@env.fetch(variable) { ENV[variable] }`, where `@env` is the task's filtered/whitelisted environment hash but `ENV` is the Shipit server process's own environment. A contributor who can control `shipit.yml` steps (e.g. via a PR merged to the deployed branch) can reference any variable name that exists in the Shipit host's process environment but was never declared in `deploy.variables`, and have its value printed to the task log.

### Finding Description
The intended binding is: for any `$WORD` interpolated in a step, the substituted value must come only from the task/deploy's filtered `env` hash that passed through `EnvironmentVariables#permit` (i.e. `value == filtered_env[WORD]` or the token is left untouched), never from the master Shipit process's environment. The code breaks this: [1](#0-0) 

`interpolate` is invoked from `Command#interpolate_environment_variables` → `Command#interpolated_arguments`, which is called right before `PTY.spawn`: [2](#0-1) [3](#0-2) 

`Command` is constructed by `TaskCommands#perform`/`#install_dependencies` with `env:` built from `Commands#env`, `@stack.env`, task metadata, `deploy_spec.machine_env`, and `@task.env` — all deliberately filtered/whitelisted sets, not the raw process `ENV`: [4](#0-3) [5](#0-4) 

The whitelisting mechanism (`TaskDefinition#filter_envs` / `EnvironmentVariables#permit`) exists precisely to reject any variable not declared in `deploy.variables`: [6](#0-5) [7](#0-6) 

However, that whitelist only constrains what keys make it into `@env` (the hash passed to `Command.new(env:)`); it does nothing to constrain which `$WORD` tokens `interpolate` will resolve. When a step string references a name absent from `@env`, the `fetch` block silently falls through to `ENV[variable]` — the Shipit server process's environment, which is not scoped per-repository, per-stack, or per-declared-variable at all.

Attacker's exact action: open a PR against a repository whose `shipit.yml` is evaluated by Shipit (via `DeploySpec`/`discover_deploy_steps` or `around_steps('deploy')`), adding or modifying a step, e.g. `deploy.override: ["echo $SECRET_KEY_BASE"]`, without declaring `SECRET_KEY_BASE` under `deploy.variables`. Once that commit is deployed (merged to the deployed branch, or the PR itself is deployed if the stack/task flow allows deploying arbitrary commits), `TaskCommands#perform` builds the `Command` with the filtered `env` (which does not contain `SECRET_KEY_BASE`), `interpolated_arguments` calls `interpolate`, `@env.fetch('SECRET_KEY_BASE')` misses, and the block returns `ENV['SECRET_KEY_BASE']` from the Shipit master process — which is then `Shellwords.escape`d and executed by `echo`, printing the secret into the task's stdout stream, viewable by anyone who can view that task's output.

None of the existing guards prevent this: `EnvironmentVariables#permit` only filters the env hash construction, it is never consulted by `interpolate`; there is no check in `Command#interpolate_environment_variables` or `Command#interpolated_arguments` that a resolved token actually originated from `@env` rather than the fallback; and no code path removes `ENV[variable]` as a fallback source.

### Impact Explanation
Any host-level secret exported into the Shipit server process's environment (e.g. `SECRET_KEY_BASE`, `RAILS_MASTER_KEY`, `GITHUB_TOKEN`/App credentials, database URLs, `api_clients_secret`) can be exfiltrated into task output readable by any user who can view that stack's task, simply by referencing its name as `$NAME` in a step. This matches the Critical category "exfiltration of deploy-time secrets," and is repeatable against any stack whose `shipit.yml` the attacker can influence and get deployed — the blast radius extends to the entire Shipit host's process environment, not just per-stack secrets.

### Likelihood Explanation
Preconditions: attacker needs their `shipit.yml` changes to actually be evaluated as a deploy step (i.e., merged/deployed, or otherwise reachable through the stack's normal deploy flow) — this requires either merge access or a deploy pipeline that runs steps from PR branches. This is a normal contributor workflow in many Shipit setups (deploying PR branches or auto-merging is common), so the barrier is low: no secrets, tokens, or special permissions are required beyond the ability to affect the deployed `shipit.yml`, which is exactly the threat model of "unprivileged contributor opens a PR."

### Recommendation
In `EnvironmentVariables#interpolate`, remove the `ENV[variable]` fallback and only substitute values present in `@env`; for unmatched tokens either leave the literal `$WORD` unexpanded or raise/warn, e.g.:
```ruby
argument.gsub(/(\$\w+)/) do |variable|
  key = variable.sub('$', '')
  @env.key?(key) ? Shellwords.escape(@env[key]) : variable
end
```
This ensures interpolation strictly honors the `permit`-filtered environment and never leaks the Shipit server process's own `ENV`.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (or command_test.rb)
test "interpolate does not leak host process ENV for undeclared variables" do
  ENV['SHIPIT_TEST_SECRET'] = 'topsecret'
  begin
    command = Shipit::Command.new('echo $SHIPIT_TEST_SECRET', env: {}, chdir: '.')
    output = command.run
    refute_includes output, 'topsecret',
      "Command output leaked ENV['SHIPIT_TEST_SECRET'] despite it not being present in the filtered env hash"
  ensure
    ENV.delete('SHIPIT_TEST_SECRET')
  end
end
```
Before the fix, `command.run` includes `"topsecret"` even though `env: {}` was passed to `Command.new`, proving the binding `interpolated_value == filtered_env[variable]` is violated (the value instead came from `ENV[variable]`). After applying the recommended fix, the assertion passes because the token is left literal (`$SHIPIT_TEST_SECRET`) or omitted, and the secret never appears in output.

      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|

      end
    end
