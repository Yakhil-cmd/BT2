### Title
Commit authorship spoofing via unauthenticated `Merge-Requested-By` commit-message trailer - ([File: app/models/shipit/user.rb])

### Summary
`Shipit::User.find_or_create_author_from_github_commit` derives a commit's `author` from a regex match on the free-text commit message rather than from GitHub's authenticated commit author/committer fields, and unconditionally calls `find_or_create_by_login!` on whatever login string it finds. Any commit reaching this path — including one later selected as a `Rollback`/`Deploy`'s `since_commit`/`until_commit` — can have its recorded author reassigned to an arbitrary GitHub account by embedding a forged `Merge-Requested-By: <login>` line in the commit message.

### Finding Description
The broken binding: `commit.author` (as persisted by Shipit) should equal `github_commit.author` / `github_commit.commit.author` (GitHub's authenticated identity for who authored/committed that SHA), but instead it is overridden by an attacker-controlled substring of `github_commit.commit.message`.

Code path:
- `Commit.from_github` calls `User.find_or_create_author_from_github_commit(commit)` to set the commit's `author` [1](#0-0) .
- `find_or_create_author_from_github_commit` matches the commit message against `/^Merge-Requested-By: ([\w\-.]+)$/` and, on match, returns `find_or_create_by_login!(match_info[1])`, completely bypassing the actual `github_commit.author`/`commit.author` fields [2](#0-1) .
- `find_or_create_by_login!` fetches (`Shipit.github.api.user(login)`) and persists a `User` record keyed to that arbitrary login [3](#0-2) .
- Commits enter this path via `GithubSyncJob#append_commit` → `stack.commits.create_from_github!(gh_commit)` → `Commit.from_github`, triggered from `PushHandler#process` after a push webhook [4](#0-3) [5](#0-4) .
- `Rollback#commits` and `#commit_range` operate purely on `id` ranges of already-persisted `Commit` rows and never re-validate `author` against GitHub [6](#0-5) .

Root cause: the `Merge-Requested-By` trailer is intended to be written only by Shipit itself, when its own merge-queue `MergeRequest#merge!` performs the GitHub merge and embeds `merge_requested_by.login` (an authenticated Shipit actor) into the merge commit title via `MergeRequest#merge_message` [7](#0-6) . However, `Commit.from_github`/`find_or_create_author_from_github_commit` trusts this trailer on **any** commit ingested from GitHub, regardless of whether it was produced by Shipit's merge flow or by an ordinary push/PR-merge containing attacker-authored commit text. Since GitHub places no restriction on commit message content, any contributor who can get a commit into the tracked branch's history (via direct push if they have write access, or via a merged pull request preserving original commit messages) can embed `Merge-Requested-By: <victim-login>` and have Shipit's ingestion pipeline silently reassign that commit's author to the named victim's `User` record, with no verification that the victim authorized or even knows about it.

None of the existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `PushHandler`, `force_github_authentication`) address this, because the webhook is only used to trigger a resync; the actual commit data is fetched from GitHub's API by `GithubSyncJob`/`stack.github_commits`, and the vulnerability lies entirely in how that authentic-but-attacker-authored commit message is parsed and trusted for identity attribution.

### Impact Explanation
The commit's `author` (a `Shipit::User`) is a data-integrity/audit field surfaced throughout the UI, API serializers, `stacks_contributed_to`, `repositories_contributed_to`, and used in `Rollback`/`Deploy` displays that show "who requested/authored" the commits being deployed or rolled back. An attacker can make any commit they get into history (including ones spanning a `Rollback`'s `since_commit`/`until_commit` range) appear to be authored/requested by an arbitrary GitHub login of their choosing — including a trusted maintainer or Shipit operator — corrupting the audit trail used to justify deploy/rollback actions. This is repeatable per commit and works against any repository the attacker can get a commit merged into. It does not, by itself, grant `PTY.spawn` execution, bypass authentication, or leak secrets — the actual deploy/rollback mechanics (`Task`/`Command`) are unaffected; the impact is confined to falsified attribution metadata rather than an executed unauthorized deploy/rollback/merge action.

### Likelihood Explanation
Precondition: the attacker's commit (with the forged trailer) must actually land in the tracked branch's history — either via direct push access to that branch, or via a normal pull-request merge that preserves original commit messages (a very common configuration; only squash-merges with edited titles would strip it). No Shipit secrets, sessions, or API tokens are required; the attacker only needs the ability any contributor already has to write a commit message. This is low-cost and highly feasible for any repository not using squash-and-rewrite merge policies.

### Recommendation
Attribute commit authorship strictly from GitHub's authenticated `commit.author`/`commit.committer` fields. If a "requested by" concept is desired, store it as a separate field (e.g., only trust `Merge-Requested-By` when it was written by Shipit's own `MergeRequest#merge!` and cross-check it against the `MergeRequest#merge_requested_by` association already recorded for that stack/number, never derive it ad hoc from arbitrary commit message text).

### Proof of Concept
Minitest plan (`test/models/commits_test.rb` style, no live GitHub — stub `Shipit.github.api`):
```ruby
test "from_github attributes authorship to forged Merge-Requested-By trailer regardless of actual commit author" do
  victim = shipit_users(:walrus) # some existing legit user with login "walrus"
  attacker_github_author = stub(id: 999, login: 'attacker', name: 'Attacker', email: 'a@example.com', url: nil)
  github_commit = stub(
    sha: 'deadbeef',
    author: attacker_github_author,
    committer: attacker_github_author,
    commit: stub(
      message: "Some change\n\nMerge-Requested-By: #{victim.login}\n",
      author: stub(date: Time.now, name: 'Attacker', email: 'a@example.com'),
      committer: stub(date: Time.now, name: 'Attacker', email: 'a@example.com')
    ),
    stats: nil,
    parents: []
  )

  Shipit.github.api.expects(:user).with(victim.login).returns(stub(id: victim.github_id, login: victim.login, name: victim.name, email: victim.email, avatar_url: nil, url: nil))

  commit = Shipit::Commit.from_github(github_commit)

  # BROKEN BINDING: commit.author (persisted identity) should equal the authenticated pusher (attacker),
  # not the unauthenticated claim embedded in the commit message.
  refute_equal attacker_github_author.login, commit.author.login
  assert_equal victim.login, commit.author.login # demonstrates spoofed attribution
end
```
This proves that `commit.author` is bound to an attacker-chosen string in the commit message rather than the actual GitHub-authenticated author/committer of the commit.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
