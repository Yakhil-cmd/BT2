### Title
Cross-repository status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` without ever filtering by the `repository` named in the webhook payload, unlike `PushHandler` which explicitly scopes lookups to `stacks` derived from `repository_name`. Because GitHub webhook signatures in this engine are verified per-organization (not per-repository, not per-stack), any repository under an onboarded organization can emit a validly-signed `status` event whose `sha` happens to match a commit that belongs to an entirely different stack, causing that unrelated stack's commit to be marked `success?` and its continuous delivery to be scheduled.

### Finding Description
The binding the security question implies is: `stack derived from payload.repository == stack whose Commit row gets mutated`. In code this binding is **not enforced**:

- `WebhooksController#verify_signature` picks the `GitHubApp` (and its `webhook_secret`) using only `repository_owner` — the organization login from the payload: [1](#0-0) [2](#0-1) 

- `StatusHandler#process` never uses `payload.dig('repository', 'full_name')` / the base `Handler#stacks` helper (which does scope by repository, see `Repository.from_github_repo_name(repository_name)`); it queries `Commit` globally by SHA: [3](#0-2) [4](#0-3) 

- Contrast with `PushHandler#process`, which correctly scopes to `stacks` resolved from the payload's repository before acting: [5](#0-4) 

- The DB index on `Commit` is `(stack_id, sha)` — a composite, non-globally-unique index — so nothing at the schema level prevents two different stacks from having rows with the identical `sha`: [6](#0-5) 

- `Commit#create_status_from_github!` → `#add_status` updates state and, on success/pending transitions, triggers `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`: [7](#0-6) [8](#0-7) 

- A new `Status` row's `after_commit :schedule_continuous_delivery` calls `commit.schedule_continuous_delivery`, which checks `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and, if `stack.continuous_deployment?` and `stack.deployable?`, enqueues `ContinuousDeliveryJob.perform_later(stack)` — for `commit.stack`, whichever stack that commit row happens to belong to, not the stack tied to the payload's `repository`: [9](#0-8) [10](#0-9) [11](#0-10) [12](#0-11) 

**Exploit flow:** Attacker owns/controls a repository under the same GitHub organization that Shipit is configured for (webhook secrets in this engine are per-organization/per-GitHub-App installation, shared across every repository the App/webhook is installed on — see `Shipit.github_app_config` keyed by organization only). The attacker crafts (or otherwise produces) a commit whose SHA-1 collides with the victim stack's pending HEAD commit — e.g., an empty-tree/root commit with matching tree, parent(s), author, committer and message fields, all attacker-controlled except that they must match the victim's exact commit metadata to get an identical SHA-1. They push this commit to their own repository, causing GitHub to fire a genuinely-signed `status` webhook (`state: success`) for their repo. Because the signature check only validates "this came from GitHub for organization X" and `StatusHandler#process` matches by `sha` alone, `Commit.where(sha: ...)` returns the victim's commit row (belonging to stack B) and marks it `success?`, flipping `deployable?` true and enqueuing `ContinuousDeliveryJob` for stack B — despite the payload never naming stack B's repository.

**Why existing guards don't help:** `verify_signature` only authenticates the organization, not the specific repository; `drop_unhandled_event`/`ExplicitParameters` only validate payload shape (`sha`, `state`, etc.), not repository ownership; there is no `Repository`/`Stack` scoping anywhere in `StatusHandler`.

### Impact Explanation
A successfully forged status can mark an unrelated, victim stack's pending HEAD commit as CI-`success`, satisfying `Commit#deployable?` and triggering `ContinuousDeliveryJob`/an unauthorized deploy for that stack — a payload for one repository mutating another's commit/stack state and causing an unauthorized deploy, matching the "Critical" impact category (payload for one repository mutating another's stack/commit, unauthorized deploy). Blast radius spans every stack under the same GitHub organization/App installation sharing one `webhook_secret`, and repeats on every attacker-controlled repository/commit they can produce.

### Likelihood Explanation
This requires: (1) the attacker to control a repository under an organization already onboarded to Shipit with a shared org/App-level `webhook_secret` (plausible for org-wide GitHub App installations, e.g., attacker has any repo — including a newly created empty one — in that org); and (2) production of a commit whose full SHA-1 (tree + parent + author + committer + timestamps + message) collides with the victim's exact pending commit — a very high-cost, largely impractical precondition absent a genuine SHA-1 collision (the "empty tree" trick alone does not produce identical *commit* SHAs across independent histories, since parent/author/committer/message must also match exactly). This sharply limits real-world exploitability even though the code-level scoping gap (`StatusHandler` never checking `repository_name`) is real and structurally distinct from `PushHandler`'s correct behavior.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or intersect with `stacks.flat_map(&:commits)`) instead of querying `Commit` globally by SHA.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event for repo A updates a commit belonging to stack B (unscoped SHA match)" do
  stack_a = shipit_stacks(:shipit)                # repo A's stack
  stack_b = shipit_stacks(:cyclimse)               # unrelated victim stack B
  colliding_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"

  commit_b = stack_b.commits.create!(sha: colliding_sha, message: "victim head", author: shipit_users(:shipit), authored_at: Time.now, committer: shipit_users(:shipit), committed_at: Time.now)
  stack_b.update!(continuous_deployment: true)
  commit_b.statuses.create!(stack_id: stack_b.id, state: "pending")

  payload = {
    "sha" => colliding_sha,
    "state" => "success",
    "repository" => { "full_name" => "attacker/repo-a", "owner" => { "login" => "shopify" } }
  }

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b]) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_predicate commit_b.reload, :success?
end
```
Assertion validates the broken binding: `payload["repository"]["full_name"] == "attacker/repo-a"` (stack A) while `ContinuousDeliveryJob` is enqueued with `stack_b` — the two sides of the binding diverge.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
