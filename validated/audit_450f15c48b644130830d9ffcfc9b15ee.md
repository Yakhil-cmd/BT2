### Title
Session fixation on GitHub OAuth callback — session ID is never rotated after authentication - (File: `app/controllers/shipit/github_authentication_controller.rb`)

### Summary
`GithubAuthenticationController#callback` binds a newly authenticated GitHub identity to the *existing* session by writing `session[:user_id]` and `session[:authenticated]` directly, without ever calling `reset_session` (or otherwise rotating the session identifier). `logout` explicitly calls `reset_session`, but the far more security-sensitive login path does not, breaking the expected binding of "one session identifier per authentication event."

### Finding Description
The OmniAuth callback is: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true

  redirect_to(return_url)
end
```

Contrast with the logout path, which rotates the session: [2](#0-1) 

The `current_user` binding used everywhere downstream reads only from `session[:user_id]`: [3](#0-2) 

The trust binding that should hold is: `session_id (before login) ≠ session_id (after login)` — a fresh session identifier must be minted whenever a `User` becomes bound to a session, so that an identifier obtained/known prior to authentication (e.g. handed to a victim by an attacker, or observed unauthenticated) cannot later be reused by the attacker once the victim authenticates through it. Because `callback` never rotates the session, this binding does not hold: `session_id (before) == session_id (after)`, and the `User` identity established via GitHub OAuth (`auth.extra.raw_info`, `auth.credentials.token`) is attached to whatever session identifier the browser presented at callback time, regardless of who set it.

This is a general Rails/OWASP session-management requirement independent of the specific session store configured by the host application: shipit-engine is designed to be mounted into an arbitrary host Rails app (see `docs/setup.md`), and the host app — not this engine — chooses the session store backend. Because the engine cannot assume a client-side-only cookie store is used everywhere it is deployed, failing to rotate the session on login is a real gap in the engine's own authentication code, not merely a deployment misconfiguration.

### Impact Explanation
If an attacker can get a target session identifier fixed in a victim's browser prior to authentication (a well known technique when the deployment uses a server-side session store, or via cookie-jar/subdomain tricks in cookie-store deployments), and the victim subsequently completes the GitHub OAuth flow, the attacker's held session identifier becomes bound to the victim's `Shipit::User` — including `session[:user_id]` and the `authenticated` flag consumed by `UserRequiredMiddleware` for `/events` and `/sidekiq`. The attacker then acts as the victim: creating/approving deploys, rollbacks, merges, and API clients, i.e. an unauthorized deploy/rollback/merge as defined as Critical impact, achieved by escalating into the victim's session rather than the victim's raw GitHub credentials.

### Likelihood Explanation
Exploitability depends on the host application's session-store choice and cookie scoping, which this analysis could not fully confirm from the engine index alone (the `test/dummy` session-store config is out of scope and not authoritative for real deployments). Independent of that caveat, the missing `reset_session` on the authentication path is a concrete, unconditional defect in the engine's own controller code and is the standard root cause cited for session-fixation class bugs in Rails apps; it is asymmetric with the `logout` action, which does perform the rotation, showing the omission is not intentional.

### Recommendation
Call `reset_session` (or otherwise regenerate the session ID while preserving needed OmniAuth state, e.g. `omniauth.origin`) at the start of `GithubAuthenticationController#callback`, before assigning `session[:user_id]` and `session[:authenticated]`, mirroring the `logout` action's behavior.

### Proof of Concept
1. Attacker visits the Shipit instance unauthenticated and obtains a session identifier/cookie `S` from the server (or otherwise fixes a chosen `S` in the victim's browser, depending on the host's session-store).
2. Attacker delivers `S` to the victim's browser (session fixation delivery vector).
3. Victim, using session `S`, navigates to `/github/auth/github` and completes the GitHub OAuth flow; `GithubAuthenticationController#callback` executes and sets `session[:user_id] = victim.id` and `session[:authenticated] = true` on session `S` without rotating it (`app/controllers/shipit/github_authentication_controller.rb:7-21`).
4. Attacker resumes using the still-known session `S`; `Shipit::Authentication#current_user` (`app/controllers/concerns/shipit/authentication.rb:36-42`) resolves `session[:user_id]` to the victim's `User`, granting the attacker full authenticated access as the victim, including triggering deploys/rollbacks per the victim's team authorization.
