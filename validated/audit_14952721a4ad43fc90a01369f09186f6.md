## Analog Vulnerability Found

### Title
Final-bad status is not propagated to units spending private-asset outputs, permanently legitimizing funds descended from an invalid source unit - (File: `main_chain.js`)

### Summary
When a unit is discovered to be a losing double-spend and is marked `sequence='final-bad'` after stabilization, `main_chain.js` is supposed to cascade this "poisoned" status to every later unit that already spent an output of that now-invalid unit, so descendants of invalid money can never be treated as legitimate. This propagation deliberately skips spends of **private assets**, so a unit that consumed an output of a unit that later turns final-bad keeps `sequence='good'` forever if it is a private-asset spend, even though the money it spent never actually existed.

### Finding Description
`propagateFinalBad()` finds all units that spent (`src_unit IN(?)`) an output of a unit that just became `final-bad`, and marks them `final-bad` too, cascading recursively so the entire descendant chain is invalidated: [1](#0-0) 

The query that selects these descendant units explicitly excludes private-asset spends via `(is_private=0 OR inputs.asset IS NULL)`: [2](#0-1) 

This means only base-asset and public-custom-asset descendants are cascaded to `final-bad`. A unit that privately spent an output of a unit that later becomes `final-bad` keeps whatever sequence it was independently assigned by `handleNonserialUnits()` (typically `good`, since that resolution only checks conflicts on the *unit's own* author address, not on the validity of its inputs' source unit): [3](#0-2) 

When such a private chain is (re)validated — e.g., resent by the sender, forwarded, or revalidated on the recipient's device — `initPrivatePaymentValidationState()` only checks whether the *unit carrying the message itself* has a non-good sequence while stable; it never checks whether the src_unit that funded the input became final-bad: [4](#0-3) 

Since the spending unit's `sequence` column was never flipped to `final-bad` by `propagateFinalBad`, this check passes, and the recipient's `validateAndSavePrivatePaymentChain` accepts and stores the chain as fully valid, spendable private-asset coins: [5](#0-4) 

Because private outputs/inputs are opaque (blinded) and their `src_unit` no longer represents a "good" unit once the source is proven a double-spend loser, this asymmetry lets a private-asset chain that is provably descended from invalid (non-existent) money remain permanently accepted as legitimate, spendable value.

### Impact Explanation
This allows creation of private-asset value that is not backed by any real, valid issuance — the same class of impact as inflation/double-spend of a stable output. A user (or a colluding pair of private-payment counterparties) can engineer a fork/double-spend of the base unit funding a private-asset transfer, letting one branch become `final-bad` while the private-asset descendant chain retains `good` sequence forever, since it is never cascaded. Nodes that later see and store this private chain will treat it as valid, stable, and spendable, and it can be further spent, mixed with other private-asset funds, or exchanged for other value — a fund-loss/inflation condition affecting the entire private-asset accounting for anyone who accepts payments in that asset.

### Likelihood Explanation
Reachable by any ordinary private-payment counterparty: the only prerequisite is causing an author-address unit that a private payment's input traces back to (`src_unit`) to end up on the losing side of the normal nonserial/double-spend resolution during stabilization — a scenario the protocol explicitly anticipates and normally reconciles for base/public assets, but not for private assets. No privileged network position, hub, or node compromise is required; a single unit poster who creates a genuine (but ultimately losing) fork and simultaneously builds a private-asset chain on top of the losing branch's output can trigger this.

### Recommendation
Remove the `(is_private=0 OR inputs.asset IS NULL)` filter from the `propagateFinalBad` query (or add an equivalent mechanism for private assets), so that any unit consuming an output of a unit that becomes `final-bad` is itself marked `final-bad`, regardless of the asset's privacy flag. Additionally, `initPrivatePaymentValidationState`/`validatePrivatePayment` should independently re-verify, at (re)validation time, that every unit in the private chain's ancestry has not since become `final-bad`, rather than relying solely on the cached `sequence` column of the immediate unit.

### Proof of Concept
1. Attacker controls address A and crafts two conflicting units U1 and U2 both spending the same base-asset output from address A, submitted into two different, initially-unmerged parallel branches (a genuine fork/double-spend).
2. Before the fork resolves, attacker (or a colluding recipient) builds a private-asset payment chain P whose earliest input references an output of U2.
3. P is sent to a counterparty, who validates it via `validateAndSavePrivatePaymentChain` (`indivisible_asset.js`/`divisible_asset.js`); since U2 is still unstable, `is_serial`/`sequence` inheritance may mark P `temp-bad` momentarily but `handleNonserialUnits()` later resolves P's own address conflicts (there are none) to `good`.
4. The DAG stabilizes; `findStableConflictingUnits` determines U2 loses to U1 and sets U2's `sequence='final-bad'`; `propagateFinalBad` is invoked with `arrFinalBadUnits=[U2]`.
5. Because P's input is a private-asset input, the `SELECT ... WHERE src_unit IN(?) AND (is_private=0 OR inputs.asset IS NULL)` query never returns P, so P keeps `sequence='good'` in the `units` table.
6. The counterparty (or anyone P's private chain is later forwarded to) revalidates the chain; `initPrivatePaymentValidationState` only checks P's own `sequence`/`is_stable`, sees `good`/stable, and accepts the chain as valid, permanently legitimizing value that was never actually funded (U2 no longer exists as a valid source).
