### Title
`OpenedHandler#provision?` bypasses `review_stacks_enabled` due to `&&`/`||` operator precedence, allowing stack provisioning on repositories where review stacks are disabled - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` intends `repository.review_stacks_enabled` to gate all three provisioning behaviors, but Ruby's `&&`/`||` precedence only applies it to the `allow_all` branch. For repositories configured with `provisioning_behavior: allow_with_label` or `provisioning_behavior: prevent_with_label`, a pull request can trigger review-stack creation even when `review_stacks_enabled` is `false`. The same flawed pattern is duplicated in `ReopenedHandler#unarchive?`.

### Finding Description
The intended binding is: `review_stacks_enabled == true` must hold for provisioning to occur, regardless of `provisioning_behavior`. The code in [1](#0-0) 
is:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Because `&&` binds tighter than `||`, this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

`review_stacks_enabled` is only ANDed into the first disjunct. When `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, provisioning proceeds independent of `review_stacks_enabled`'s value. The same pattern is repeated in `ReopenedHandler#unarchive?` at [2](#0-1) 
.

Exploit flow: an attacker opens a pull request (which requires no write access to the target repository) against a public repository mounted on the Shipit instance and configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` (attacker applies the provisioning label to their own PR, which any PR author/triage-enabled user can do) or `prevent_with_label` (attacker simply omits the label). GitHub delivers a correctly-signed `pull_request` `opened` webhook (no signature forgery needed since this is a genuine GitHub-originated webhook). `OpenedHandler#process` calls `provision?`, which returns `true` despite `review_stacks_enabled` being `false`, and proceeds to [3](#0-2) 
`ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!`, creating/activating a review stack tracking the attacker's branch.

None of the documented guards prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` only validate that GitHub sent the payload (they do, legitimately, since the attacker triggers a real PR event), and `ExplicitParameters` only validates payload shape, not authorization semantics. The authorization decision is made entirely by the flawed `provision?`/`unarchive?` boolean logic, which is the actual bug.

The existing test suite does not catch this: `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` only asserts "only provision stacks for repos with auto-provisioning enabled" using `behavior: :allow_all` [4](#0-3) 
, leaving the `allow_with_label`/`prevent_with_label` combined with `review_stacks_enabled: false` case untested.

### Impact Explanation
Once a review stack is created/unarchived for the attacker's branch, Shipit's standard review-stack pipeline (`ReviewStackProvisioningQueue` → task execution) runs the deploy pipeline sourced from the PR branch's `shipit.yml`, using the repository's real deploy environment (including `GITHUB_TOKEN`/`GIT_ASKPASS`-bearing env passed to `Command`/`PTY.spawn`). This is a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`) still ending up executing attacker-authored deploy steps with production deploy credentials — this is an unauthorized-deploy / RCE-with-deploy-credentials scenario, matching the Critical impact category ("a payload... mutating another's stack... or an unauthorized deploy"). It is repeatable against any repository sharing this misconfiguration, and the `ReopenedHandler` variant provides a second trigger path.

### Likelihood Explanation
Requires only that a target repository be registered in Shipit with `review_stacks_enabled: false` and `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` — a plausible admin configuration if `provisioning_behavior` and `review_stacks_enabled` are set independently in the settings UI [5](#0-4) 
, e.g. before finishing enabling review stacks, or while temporarily disabling them without resetting `provisioning_behavior`. No GitHub write access, Shipit session, or secret is needed — only the ability to open a PR (and optionally label it) on the public repository, which is achievable by any GitHub user via a fork.

### Recommendation
Fix operator precedence in both `OpenedHandler#provision?` and `ReopenedHandler#unarchive?` (and audit `LabeledHandler`/`UnlabeledHandler` for the same pattern) so `review_stacks_enabled` gates all three behavior branches, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not provision stacks when review_stacks_enabled is false, even for allow_with_label with label present" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :allow_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end

test "does not provision stacks when review_stacks_enabled is false, even for prevent_with_label with label absent" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Both assertions currently fail (stacks ARE created) against the unpatched `provision?`, confirming `review_stacks_enabled: false` is bypassed for the two label-based provisioning behaviors.
