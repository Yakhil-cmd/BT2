## Analog Finding: Temporary-data payload size limit undercounted by 2x, allowing oversized units to bypass MAX_UNIT_LENGTH check

### Summary
`ocore` enforces a hard unit-size ceiling (`constants.MAX_UNIT_LENGTH = 5e6`) by comparing `headers_commission + payload_commission` against it in `validation.js`. However, for `temp_data` messages, the payload-size calculator only counts **half** of the actual data length (`TEMP_DATA_PRICE = 0.5`) toward `payload_commission`, while the raw literal `data` field must still be included verbatim in the unit's JSON to satisfy the `data_length`/`data_hash` checks. This lets any unprivileged unit poster craft a unit whose *counted* size passes the `MAX_UNIT_LENGTH` gate while its *actual* wire/storage size is roughly double the intended cap — the same root-cause pattern as the `@hapi/subtext` advisory: a size limit is enforced against a derived/metadata value instead of the real payload bytes.

### Finding Description
`object_length.js` computes payload size by stripping the actual `data` field from `temp_data` messages and substituting a discounted proxy: [1](#0-0) 

`extractTempData` deletes the literal `data` from the message copy used for length calculation, and only `Math.ceil(temp_data_length * constants.TEMP_DATA_PRICE)` (i.e. 50% of `data_length`) is added back: [2](#0-1) 

`TEMP_DATA_PRICE` is fixed at 0.5: [3](#0-2) 

`validation.js` enforces the hard unit-size limit purely against this discounted `payload_commission` metric, for any unit poster (not just AA/genesis): [4](#0-3) 

Meanwhile, the `temp_data` payload validation only checks that `data_length` matches the actual length of `payload.data` and that `data_hash` matches — it imposes no independent maximum on `data_length`/`data` itself: [5](#0-4) 

Because the real literal `data` (up to `data_length` bytes) is present in the unit's serialized JSON — it must be transmitted over the wire, parsed, hashed (`objectHash.getBase64Hash(payload.data, true)`), and stored (at least temporarily, until `TEMP_DATA_PURGE_TIMEOUT` = 24h) — but only half of its length is counted against `MAX_UNIT_LENGTH`, an attacker can double the effective bytes any node must handle relative to the documented/intended 5,000,000-byte ceiling, without tripping "unit too large".

### Impact Explanation
This is a resource-exhaustion (CWE-400) issue reachable by any ordinary unit poster (no privileged role required): a unit can be built with one or more `temp_data` messages whose combined `data_length` is up to ~2× `MAX_UNIT_LENGTH` while `headers_commission + payload_commission` still reports ≤ `MAX_UNIT_LENGTH`. Every full node that receives, validates (hashing/parsing the full literal payload), and temporarily stores the unit is forced to process roughly double the intended maximum unit size. Repeated posting of such units (bounded only by the normal headers/payload commission fee paid, not by the true byte cost) inflates bandwidth, memory, and temporary-storage consumption network-wide beyond the size envelope the protocol was designed to guarantee, degrading the network's ability to timely receive/validate/confirm new units — matching the "network unable to confirm new units" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: constructing such a unit requires no special privileges — only a valid address, sufficient fee to cover the (discounted) commission, and correctly computed `data_hash`/`data_length` fields, all of which are straightforward to compute client-side. No AA, asset issuer, or hub/peer trust is required, satisfying the "unprivileged unit poster" reachability constraint.

### Recommendation
Compute `payload_commission` (and the `MAX_UNIT_LENGTH` comparison) using the *full* length of `temp_data.data`, not the discounted `temp_data_length * TEMP_DATA_PRICE` value, or alternatively enforce a separate, explicit hard cap on cumulative `temp_data` `data_length` per unit (and possibly network-wide per time window) independent of the price-discount mechanism, so that the discount affects only the fee charged and never the byte-size ceiling used for the anti-spam/anti-DoS `MAX_UNIT_LENGTH` check.

### Proof of Concept
1. As any funded address, build a unit for a version ≥ `v4UpgradeMci` (where `temp_data` is allowed).
2. Add one or more `temp_data` messages whose `payload.data` totals just under `2 * constants.MAX_UNIT_LENGTH` (~9.99 MB) of literal content, with correctly computed `data_length` (`objectLength.getLength(payload.data, true)`) and `data_hash` (`objectHash.getBase64Hash(payload.data, true)`).
3. Compute `headers_commission` via `objectLength.getHeadersSize` and `payload_commission` via `objectLength.getTotalPayloadSize`; because `extractTempData` divides the temp-data contribution by 2, the sum stays ≤ `constants.MAX_UNIT_LENGTH` (5,000,000) even though the actual serialized unit is nearly twice that size.
4. Submit the unit; `validation.js`'s "unit too large" check (`objUnit.headers_commission + objUnit.payload_commission > constants.MAX_UNIT_LENGTH`) passes, and every receiving node must download, hash-verify, and temporarily persist the full ~10 MB payload.

function getTotalPayloadSize(objUnit) {
	if (objUnit.content_hash)
		throw Error("trying to get payload size of stripped unit");
	var bWithKeys = (objUnit.version !== constants.versionWithoutTimestamp && objUnit.version !== constants.versionWithoutKeySizes);
	const { temp_data_length, messages_without_temp_data } = extractTempData(objUnit.messages);
	return Math.ceil(temp_data_length * constants.TEMP_DATA_PRICE) + getLength({ messages: messages_without_temp_data }, bWithKeys);
}

function extractTempData(messages) {
	let temp_data_length = 0;
	let messages_without_temp_data = messages;
	for (let i = 0; i < messages.length; i++) {
		const m = messages[i];
		if (m.app === "temp_data") {
			if (!m.payload || typeof m.payload.data_length !== "number") // invalid message, but we don't want to throw exceptions here, so just ignore, and validation will fail later
				continue;
			temp_data_length += m.payload.data_length + 4; // "data".length is 4
			if (m.payload.data) {
				if (messages_without_temp_data === messages) // not copied yet
					messages_without_temp_data = _.cloneDeep(messages);
				delete messages_without_temp_data[i].payload.data;
			}
		}
	}
	return { temp_data_length, messages_without_temp_data };
}
