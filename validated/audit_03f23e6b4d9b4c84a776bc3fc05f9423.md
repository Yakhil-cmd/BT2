### Title
Webhook Signature is Verified Against the Payload's `repository.owner.login`, But `StatusHandler` Writes Commit Statuses Without Any Repository Check — Breaking the Binding Between the Authenticated Organization and the Repository Acted On - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from the payload's own `repository.owner.login` (or `organization.login`) field. This is the same field that GitHub actually embeds in the payload it signs, so the check by itself is not forgeable for a *single-org* deployment. However, once the signature is accepted, the handler that performs the actual write, `Shipit::Webhooks::Handlers::StatusHandler`, never re-validates that the `repository` field of the payload corresponds to the organization whose secret validated the request — in fact it doesn't consult `repository` at all. It looks up commits **globally by `sha`** across the entire `commits` table and mutates them.

### Finding Description
In a multi-organization Shipit deployment (explicitly supported per `docs/setup.md`, "Using Multiple Github Applications"), each GitHub organization configured under `Shipit.github` has its own independent `webhook_secret`: [1](#0-0) 

`WebhooksController#verify_signature` picks the app/secret to check against solely from the untrusted JSON body: [2](#0-1) [3](#0-2) 

Once `verified` is true for *any* configured organization, `create` dispatches the entire parsed payload to every registered handler for the event, with no additional scoping of the payload to the organization that just authenticated: [4](#0-3) 

`StatusHandler`, unlike `PushHandler`/`Handler#repository_name` (which at least scope lookups by `repository.full_name`), does not require or use a `repository` field at all — it matches by `sha` across **every stack in the installation**: [5](#0-4) 

`Commit#create_status_from_github!` then persists the attacker-controlled `state`, `description`, `target_url`, and `context` directly as a new `Status` row for that commit: [6](#0-5) 

The equality that should hold is: `organization authenticated by verify_signature == organization owning the repository/stack that the handler mutates`. Because `StatusHandler` performs a global `Commit.where(sha:)` lookup with no join back to `repository_owner`/`repository.full_name`, this equality is never enforced. An operator of *any* organization configured in this Shipit instance (with its own legitimately-issued `webhook_secret` for their own, unrelated GitHub org/repo) can sign an arbitrary `status` payload with their own secret and target a commit `sha` belonging to a completely different organization's stack, as long as they can guess or observe that sha (e.g., from a public commit, a previous status webhook, or the target stack's public UI).

### Impact Explanation
`Status` creation feeds directly into deploy/merge gating logic. `Commit#add_status` fires `stack.schedule_merges` when the injected state is `pending` or `success`: [7](#0-6) 

and `Commit#deployable?`/`MergeRequest::StatusChecker` treat commit CI status as authoritative for whether a commit may be deployed or a pull request may be auto-merged: [8](#0-7) [9](#0-8) 

By forging a fake "success" CI status for a commit in a repository/organization the attacker does not own or have write access to, the attacker can cause that commit to be considered CI-green, triggering `ProcessMergeRequestsJob`/auto-merge of a queued pull request, or unblocking a manual deploy that was gated on that status — i.e., an unauthorized merge/deploy across an organization boundary the attacker has no legitimate access to. This maps to the "cross-repository writes" / "unauthorized deploy, rollback or merge" Critical impact tier.

### Likelihood Explanation
The only prerequisite is that the attacker controls (or is simply the legitimate owner/operator of) any single organization configured in the same multi-org Shipit deployment — a standard, documented, unprivileged configuration relative to the victim's organization. No access to the victim's repository, GitHub App, `webhook_secret`, or Shipit account is needed; the attacker signs the forged request with their own valid secret. The only additional requirement is knowledge of a target commit `sha`, which is routinely public (commit hashes are not secrets) or observable via the victim stack's UI/API.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already scope by `repository.full_name`), require the `repository` field and verify that `Repository.from_github_repo_name(payload.dig('repository','full_name'))` matches the organization used in `verify_signature`, scoping the `Commit` lookup to that repository's stacks rather than a global `sha` match. More generally, `WebhooksController` should pass the authenticated `repository_owner`/organization down to handlers and every handler should filter its writes to repositories belonging to that organization, closing the gap between "which secret validated this request" and "which repository/stack this request is allowed to mutate."

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` (own webhook_secret known to the attacker, who administers that org's GitHub App) and `victim-org` (target, unrelated org with its own stack and commits tracked by Shipit).
2. Attacker learns a commit `sha` belonging to a `victim-org` stack tracked by Shipit (e.g. a public commit hash).
3. Attacker crafts a `status` event JSON body: `{"sha": "<victim-sha>", "state": "success", "context": "ci/travis", "repository": {"owner": {"login": "attacker-org"}}}` and computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` (`Hook::DeliverySigner`/`OpenSSL::HMAC.hexdigest('sha1', attacker_webhook_secret, raw_body)`).
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `repository_owner` to `attacker-org` and successfully verifies the signature against the attacker's own secret.
5. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: "<victim-sha>")` — matching the commit in `victim-org`'s stack — and calls `create_status_from_github!`, inserting a forged `success` `Status` for that commit, potentially triggering `stack.schedule_merges` and an unauthorized merge/deploy in `victim-org`, despite the attacker never having a `webhook_secret`, API token, or any access to `victim-org`.
