### Title
`snowbridge-pallet-outbound-queue-v2::submit_delivery_receipt` pays out relayer rewards with no pallet-level pause/halt gate - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The reported EVM bug is that `addGasFee` moves user funds (fee tokens) even when the protocol's gateway is supposed to be paused, because the function never checks the pause flag before transferring value. The structural analog in this repo is `snowbridge-pallet-outbound-queue-v2`: unlike its sibling `snowbridge-pallet-inbound-queue-v2` (which explicitly checks `OperatingMode::<T>::get().is_halted()` before doing any state-changing work, see `submit` at [1](#0-0) ), the v2 outbound queue pallet has **no `OperatingMode` storage item, no `set_operating_mode` call, and no halt check of its own at all**. `submit_delivery_receipt`, the extrinsic that pays relayer rewards, only depends on whatever the injected `T::Verifier` happens to report: [2](#0-1) 

### Finding Description
`process_delivery_receipt` fetches the `PendingOrder` for a nonce and unconditionally calls `T::RewardPayment::register_reward` if `order.fee > 0`, with no pallet-owned pause check anywhere in the call path: [3](#0-2) 

Compare this with `snowbridge-pallet-outbound-queue` (v1), which does have its own `OperatingMode`/`BasicOperatingMode` storage and a `set_operating_mode` call, and whose `deliver`/`validate` path is gated (`SendError::Halted` is returned when halted) — see the v1 test proving governance messages bypass the halt while regular sends are rejected: [4](#0-3) . The v2 outbound pallet dropped this pallet-level control surface entirely.

The unit test `poc_m1` in this same file appears to have been added specifically to probe this bug class, and it demonstrates the gap rather than closing it: it only shows that `submit_delivery_receipt` fails *when the underlying `T::Verifier` (e.g. the beacon/ethereum-client pallet) is itself halted*: [5](#0-4) 

That is an incidental side effect of the *verifier's own* halt flag (`bridges/snowbridge/pallets/ethereum-client`), not a protection owned by `snowbridge-pallet-outbound-queue-v2`. If a chain governance/root operator wants to specifically pause reward payouts or message processing in this pallet — for example during an incident affecting `do_process_message`, fee accounting, or reward ledger logic, independent of whether the Ethereum light client itself is healthy — there is no `Halted`/`OperatingMode` mechanism to do so. The pallet's own `Error::Halted` variant exists in the `Error` enum, but it is dead code — nothing in `lib.rs` ever emits it: [6](#0-5) .

### Impact Explanation
This is a genuine functional/operational gap, not proven theft: if the light-client verifier stays healthy but operators still need to halt v2 outbound-queue-specific processing (e.g. due to a bug discovered in `do_process_message`, the fee/reward accounting, or `AddTip`), they have no on-chain lever — `set_operating_mode` simply does not exist for this pallet. In the worst case this could let an attacker keep triggering `submit_delivery_receipt`/reward payouts (or `do_process_message` enqueuing) during an incident that operators believe they have "paused," because there is nothing to pause at this pallet's own level. This matches the spirit of the reported bug (pause is bypassed for the fee-moving path) but is weaker: it requires the verifier to remain "up" while some other flaw is being mitigated, so I rate it Medium rather than Critical/High.

### Likelihood Explanation
Low-to-Medium. Exploiting this requires a scenario where governance wants to pause v2 outbound-queue reward payouts/processing specifically, while the Verifier (ethereum-client) is not itself halted — a believable but narrower operational-incident window than the original report's straightforward "pause the whole gateway" scenario. It also requires that this pallet is deployed live with real value moving through `RewardPayment`, which needs to be confirmed against the currently deployed/live Snowbridge Parity bounty scope for v2 (I could not verify from the index whether `outbound-queue-v2` is already live on a bounty-eligible network).

### Recommendation
Add an `OperatingMode`/`BasicOperatingMode` storage item and `set_operating_mode` extrinsic to `snowbridge-pallet-outbound-queue-v2`, mirroring the pattern already used by `inbound-queue-v2` and v1 `outbound-queue`, and gate both `do_process_message` (or `validate`/`deliver`) and `submit_delivery_receipt`/`process_delivery_receipt` on `!OperatingMode::<T>::get().is_halted()`, returning the (currently unused) `Error::Halted`.

### Proof of Concept
Not executed. I did not run a reproduction; this finding is based on static code review of `lib.rs`, `send_message_impl.rs`, `mock.rs`, and `test.rs` in `bridges/snowbridge/pallets/outbound-queue-v2`, and comparison against `inbound-queue-v2` and v1 `outbound-queue`. Confirmed facts: (1) no `OperatingMode` storage/config exists in `outbound-queue-v2::lib.rs`; (2) `Error::Halted` is declared but never constructed/returned anywhere in that crate; (3) the existing `poc_m1` test only exercises the verifier's own halted state, not a pallet-owned pause. What remains unverified: whether this pallet is currently deployed on a live, bounty-eligible Snowbridge network (needed to establish in-scope bounty eligibility), and whether higher-level runtime wiring (e.g. `pallet-message-queue`'s `QueuePausedQuery`, or a filter added at the runtime `construct_runtime!`/`BaseCallFilter` level) compensates for the missing pallet-level check — this would require inspecting the actual BridgeHub runtime configuration, which I did not have in scope for this analysis.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.
#[test]
fn poc_m1() {
	new_tester().execute_with(|| {
		let nonce = 1;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_event_proof());

		set_verifier_halted(true);

		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
		assert_eq!(order_after.fee, fee);
