### Title
Missing wallet-membership check lets any paired device inject/overwrite wallet address records - ([File: wallet.js])

### Summary
The Plone advisory describes state-changing methods (`changeMemberPortrait`, `deletePersonalPortrait`) that are reachable by any user without verifying that the caller actually owns the resource being modified. The analogous pattern exists in `wallet.js`'s `new_wallet_address` handler: it accepts a `wallet` id and address data from *any already-paired device* and forwards it to `walletDefinedByKeys.addNewAddress()` **without ever checking that the sending device (`from_address`) is actually a cosigner/member of that wallet**.

### Finding Description
In `handleMessageFromHub`'s `doHandle()`, the `new_wallet_address` case only validates the shape of the fields, but never checks that `from_address` (the device that sent the message) is associated with `body.wallet`: [1](#0-0) 

Compare this with the sibling handler `my_xpubkey` a few lines above, and with `arbiter_contract_shared`/`prosaic_contract_update`, which explicitly verify the sender is a legitimate party before mutating stored state, e.g.: [2](#0-1) [3](#0-2) 

`new_wallet_address` has no equivalent ownership check — `from_address` is computed from the sender's device pubkey but is discarded; it is not passed into `walletDefinedByKeys.addNewAddress(body.wallet, body.is_change, body.address_index, body.address, callback)` at all: [4](#0-3) 

Since `"new_wallet_address"` is *not* in the whitelist of subjects allowed from unknown correspondents (`arrSubjectsAllowedFromNoncorrespondents = ["pairing", "my_xpubkey", "wallet_fully_approved"]`), the message must come from an already-paired device — but pairing establishes only that the device is a known correspondent, not that it is a member of any particular multisig wallet: [5](#0-4) 

Any correspondent device (e.g., one paired for an unrelated purpose, or a wallet cosigner on a completely different wallet) can therefore send a crafted `new_wallet_address` message referencing a `wallet` id it does not belong to, letting it insert/overwrite the mapping between `wallet`, `address_index`, `is_change`, and `address` in the local wallet database of the victim device — this is the same class of bug as the Plone advisory: a state-mutating handler with no ownership/authorization gate protecting per-resource membership.

### Impact Explanation
If `addNewAddress` performs an insert/overwrite keyed by `(wallet, is_change, address_index)` without an independent check that the caller is a registered cosigner of `wallet` (this mirrors what `checkAndFullyApproveWallet`/`extended_pubkeys` membership implies elsewhere but is not enforced at this call site), a malicious correspondent could poison a victim's local address book for a shared/multisig wallet — causing the victim to believe a wrong or attacker-controlled address is the correct receive address at a given index/account, or overwrite existing address records for a wallet they do not co-sign. This can lead to funds being sent to attacker-influenced addresses or to state confusion for a multisig wallet (denial of correct fund custody), which is a Medium severity impact consistent with "AA/wallet fund loss or freezing" style analogs.

### Likelihood Explanation
Reaching this code only requires being a paired correspondent device (an unprivileged, low-bar precondition — pairing is routinely done with many contacts) and sending one crafted `hub/message` with subject `new_wallet_address` and a `wallet` value belonging to some other wallet (wallet ids are hashes derivable/observable, e.g. via shared contracts or public shared-address disclosures). No cryptographic break or privileged key is required, only a normal paired-device relationship, matching the reachable-actor constraints (paired device sending a message).

### Recommendation
Add an explicit membership check before calling `walletDefinedByKeys.addNewAddress`, verifying that `from_address` is present in `wallet_signing_paths` (or `extended_pubkeys`) for `body.wallet`, mirroring the checks already present in `prosaic_contract_update` (`objContract.peer_device_address !== from_address`) and `arbiter_contract_shared` (`SELECT 1 FROM my_addresses JOIN wallet_signing_paths ... WHERE device_address=?`). Reject the message with `callbacks.ifError("not a member of this wallet")` if the check fails.

### Proof of Concept
1. Attacker device D pairs normally with victim device V (standard pairing flow, no special privilege).
2. Attacker learns/derives a `wallet` id W that V participates in with a different cosigner set (wallet ids are content hashes of an xpubkey/definition and can leak via shared contracts, chat, or observed traffic).
3. Attacker sends V, through the hub, a `hub/message` with `subject: "new_wallet_address"` and `body: {wallet: W, is_change: 0, address_index: <victim's next unused index>, address: <attacker-chosen BASE32 address>}`.
4. Because `wallet.js` never verifies that D is a signer of W, V's `handleMessageFromHub` forwards this straight to `walletDefinedByKeys.addNewAddress`, which is expected (based on the missing parameter and lack of any authorization gate at the call site) to insert/overwrite the address record for wallet W at that index — corrupting V's address book for a wallet D has no relationship to.

Note: I was unable to view the full body of `walletDefinedByKeys.addNewAddress()` itself within the indexed portion of `wallet_defined_by_keys.js` to confirm the exact SQL/overwrite semantics; the finding is based on the confirmed absence of any ownership check at the `wallet.js` call site and the confirmed absence of `from_address` in the arguments passed to `addNewAddress`. A full Devin session with complete file access would be needed to verify the exact downstream `addNewAddress` implementation and confirm whether it independently re-derives/checks membership (which the reviewed call site does not).
