## Finding: Valid — Racing `migrate_v1_to_v2<T>` hijacks the V2 `Display<T>` singleton slot and permanently locks out the legitimate publisher

### Title
Unauthorized takeover of the `Display<T>` singleton via `migrate_v1_to_v2` — ([File: crates/sui-framework/packages/sui-framework/sources/registries/display_registry.move])

### Summary
`migrate_v1_to_v2<T>` performs no ownership/authorization check on the caller other than possession of a `LegacyDisplay<T>` value object. Because the legacy `sui::display::Display<T>` struct has the `store` ability, it is freely transferable independent of publisher status. [1](#0-0) 
Any address that comes to hold such an object — even long after the true publisher created/transferred it away — can call `migrate_v1_to_v2` and permanently consume the singleton `derived_object` slot reserved for `T`, binding `Display<T>.cap_id` to a `DisplayCap<T>` that only the caller controls. [2](#0-1) 

### Finding Description
`migrate_v1_to_v2` calls the internal `new_display<T>`, which asserts the `DisplayKey<T>` derived-object slot does not already exist and then claims it: [3](#0-2) 

Unlike `new_with_publisher<T>` and `claim_with_publisher<T>`, which both require `publisher.from_package<T>()` to be checked, `migrate_v1_to_v2` performs **no publisher/ownership verification whatsoever** — it only requires the caller to hold *some* `LegacyDisplay<T>` value: [4](#0-3) [5](#0-4) 

Since a `LegacyDisplay<T>` object has `key, store`, it can be created only once by the true publisher via `sui::display::new<T>(pub: &Publisher, ...)`, but afterwards it is a normal transferable/tradeable object with no further tie to publisher status: [6](#0-5) 

If such an object ever leaves the publisher's control (sale, gift, marketplace listing, multisig re-org, accidental transfer, etc.), any holder can front-run the real publisher and call `migrate_v1_to_v2<T>`, which:
1. Claims the singleton `derived_object` address for `T` in the shared `DisplayRegistry` (this claim is permanent — the underlying `derived_object` primitive does not support un-claiming).
2. Mints a fresh `DisplayCap<T>` owned by the attacker and stores its `ID` in `Display<T>.cap_id`.

Once this happens, every subsequent path for the legitimate publisher to obtain display authority over `T` aborts:
- `new_with_publisher<T>` → `new_display<T>` aborts with `EDisplayAlreadyExists` because the slot is already claimed.
- `claim<T>` / `claim_with_publisher<T>` → both abort with `ECapAlreadyClaimed` because `display.cap_id` is already `Some(attacker_cap_id)`. [7](#0-6) 

There is no recovery mechanism in the module — the registry entry for `T` is permanently bound to the attacker's `DisplayCap<T>`.

### Impact Explanation
This is a permanent, unrecoverable takeover of the on-chain metadata-management authority for type `T`: the true publisher can never create, share, or manage `Display<T>` in the new registry again through any function in this module. This constitutes unauthorized object creation and state corruption of a protected singleton slot (the `derived_object` claim for `DisplayKey<T>`), matching the "state corruption from unauthorized object creation" / protected-state-takeover impact class. It does not directly move SUI funds, so its severity is best characterized as High (harmful/irrecoverable smart-contract behavior against the registry's integrity guarantees) rather than direct fund theft.

### Likelihood Explanation
Exploitability requires only that a `LegacyDisplay<T>` object exist outside the direct control of the acting publisher at the moment of migration and that the attacker submit `migrate_v1_to_v2` before the legitimate migration/creation transaction lands — a straightforward public-transaction race with no privileged access needed.

### Recommendation
Add a publisher/authorization check to `migrate_v1_to_v2` (e.g., require `&Publisher` proof similar to `new_with_publisher`/`claim_with_publisher`, or otherwise gate migration by whoever created the legacy display, not merely whoever currently possesses the value), and/or restrict `LegacyDisplay<T>`'s transferability if it's meant to convey publisher-equivalent authority.

### Proof of Concept
1. Publisher P creates `LegacyDisplay<T>` via `sui::display::new<T>` and, for any reason, ends up transferring/selling that object to address A (non-publisher), since `Display<T>` has `store`.
2. Attacker A calls `sui::display_registry::migrate_v1_to_v2<T>(registry, legacy, ctx)` before P performs any registry action. This succeeds, claiming the `DisplayKey<T>` derived slot and setting `cap_id = Some(A's DisplayCap<T> id)`.
3. Publisher P later calls `sui::display_registry::new_with_publisher<T>(registry, publisher, ctx)` — this aborts with `EDisplayAlreadyExists` since `derived_object::exists(&registry.id, DisplayKey<T>())` is now true.
4. Any attempt by P to `claim<T>` or `claim_with_publisher<T>` using another legacy display for T also aborts with `ECapAlreadyClaimed`, since `cap_id` is already `Some`.
Result: `T`'s canonical V2 `Display` is permanently controlled by A's `DisplayCap<T>`, with no path for P to regain display-management authority. [2](#0-1)

public fun claim<T: key>(
    display: &mut Display<T>,
    legacy: LegacyDisplay<T>,
    ctx: &mut TxContext,
): DisplayCap<T> {
    assert!(display.cap_id.is_none(), ECapAlreadyClaimed);
    let cap = DisplayCap<T> { id: object::new(ctx) };
    display.cap_id.fill(cap.id.to_inner());
    legacy.destroy();
    cap
}

fun new_display<T>(
    registry: &mut DisplayRegistry,
    ctx: &mut TxContext,
): (Display<T>, DisplayCap<T>) {
    let key = DisplayKey<T>();
    assert!(!derived_object::exists(&registry.id, key), EDisplayAlreadyExists);
    let cap = DisplayCap<T> { id: object::new(ctx) };
    let display = Display<T> {
        id: derived_object::claim(&mut registry.id, key),
        fields: vec_map::empty(),
        cap_id: option::some(cap.id.to_inner()),
    };
    (display, cap)
}
