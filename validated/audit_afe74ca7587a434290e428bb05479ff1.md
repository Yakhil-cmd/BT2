### Title
MultiEdit field extraction joins edits with a space, letting split dangerous tokens bypass block rules on `new_text`/`content` - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`_extract_field` for `MultiEdit` builds the value checked against `new_text`/`content` rules via `' '.join(e.get('new_string', '') for e in edits)`, so a dangerous token can be split across two `edits` entries (e.g. `"ev"` + `"al(payload)"`) and never appear contiguous in the string that regex/contains rules evaluate, while the actual file content after applying the edits sequentially still contains the forbidden substring (e.g. `eval(payload)`). This is a real parser/tokenization differential between what hookify checks and what ends up on disk.

### Finding Description
The PreToolUse hook (`plugins/hookify/hooks/pretooluse.py`) maps `tool_name in ['Edit','Write','MultiEdit']` to `event='file'` [1](#0-0)  and passes the raw hook input straight to `RuleEngine.evaluate_rules`, which for each condition calls `_extract_field(condition.field, ...)` [2](#0-1) . For `tool_name == 'MultiEdit'` and `field in ['new_text','content']`, the engine computes `' '.join(e.get('new_string','') for e in edits)` [3](#0-2) . This value is then matched with `regex_match`/`contains` operators [4](#0-3) .

An attacker who controls the content Claude is instructed to write (e.g. via untrusted repository instructions steering Claude to perform a `MultiEdit` with several small sequential `new_string` fragments) can split a blocked contiguous token, such as `eval\(`, across edit boundaries. Because the join inserts a literal space between fragments (`"ev" + " " + "al(payload)"` = `"ev al(payload)"`), the pattern `eval\(` never matches the concatenated check string, even though when Claude actually applies the `MultiEdit` tool, each `new_string` is inserted at its own location in the target file without an inserted space, and the resulting file content can legitimately contain the contiguous substring `eval(payload)` if the edits are adjacent or otherwise combine that way in the file. The rule engine's check string diverges from the true post-edit file content, so a rule intended to always deny writes containing `eval(` can be evaded purely by fragmenting the payload across multiple `edits` entries.

### Impact Explanation
This is a policy/hook bypass: a `hookify` block rule meant to unconditionally prevent dangerous code patterns (e.g. `eval(`, `exec(`, hardcoded secrets patterns, etc.) from being written via `MultiEdit` can be silently circumvented, resulting in the forbidden pattern landing in the repository/file despite an active "deny" rule. This matches a hook/guardrail bypass impact class — the enforcement mechanism claims to deny an action but does not, undermining trust in `hookify` as a security control for file-write operations.

### Likelihood Explanation
Exploitability is high given the preconditions: it requires only (1) a hookify rule targeting `field: new_text`/`content` with `event: file` and a pattern for a contiguous token, and (2) Claude performing a `MultiEdit` call whose `edits` list happens to fragment that token — which is trivially achievable by an attacker who can influence Claude's editing behavior through untrusted content (e.g., a comment or instruction telling Claude to "make this change in two small edits"). No special privileges are needed, and the flaw is deterministic/reproducible in a unit test.

### Recommendation
Do not synthesize an approximate "joined" string for `new_text`/`content` in `MultiEdit`. Instead:
- Evaluate rules against each `edits[i].new_string` individually (and/or against `old_string`/context) rather than a single space-joined aggregate, or
- Reconstruct the actual resulting file content by applying the edits against the current file (read `file_path`, apply each `old_string -> new_string` replacement in sequence) and run the rule check against the real resulting content, matching what will actually be written to disk, or
- At minimum, join fragments with an empty string only when edits are known to be textually adjacent, and additionally check the concatenation without any separator (`''.join(...)`) in addition to per-fragment checks, so cross-fragment matches are caught.

### Proof of Concept
Unit test target: `RuleEngine.evaluate_rules` / `RuleEngine._extract_field`.

```python
from hookify.core.config_loader import Rule, Condition
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-eval",
    enabled=True,
    event="file",
    conditions=[Condition(field="new_text", operator="regex_match", pattern=r"eval\(")],
    message="eval() is forbidden",
    action="block",
)

engine = RuleEngine()

# Simulates Claude splitting "eval(payload)" across two sequential edits
test_input = {
    "tool_name": "MultiEdit",
    "tool_input": {
        "file_path": "/tmp/victim.py",
        "edits": [
            {"old_string": "X", "new_string": "ev"},
            {"old_string": "Y", "new_string": "al(payload)"},
        ],
    },
}

result = engine.evaluate_rules([rule], test_input)

# EXPECTED (if secure): result should contain a "deny"/block response
# ACTUAL (vulnerable): result == {} because ' '.join(...) produces
# "ev al(payload)" which does not match r"eval\("
assert result == {}, "Bypass confirmed: dangerous token split across edits evades block rule"
```

This demonstrates that a block rule on `new_text` matching `eval\(` fails to flag a `MultiEdit` call whose individual `new_string` fragments combine (in the real file) to contain `eval(`, confirming the parser/tokenization differential and rule-engine bypass.
