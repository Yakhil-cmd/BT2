**Analysis:** The batch verification uses a Fiat–Shamir random linear combination whose scalar `r` is derived by hashing *all* the batch inputs (every commitment, z, y, and proof in the batch) via `compute_r_powers_for_verify_kzg_proof_batch` in `src/eip4844/eip4844.c`, before any pairing check happens. [1](#0-0) 

This means `r` is a deterministic hash output that depends on the forged triple's own bytes — an attacker cannot choose `r` first and then craft a forgery to cancel against it, nor can they choose the forged triple first and then predict/control `r` to make the linear combination cancel, without breaking SHA-256 preimage resistance. The pairing check in `verify_kzg_proof_batch` (`src/eip4844/eip4844.c:697-758`) verifies `e(∑ rⁱ·Proof_i, [x]) = e(∑ rⁱ·(C_i - [y_i]) + ∑ rⁱ·z_i·Proof_i, [1])`, and this equation only holds for *all* i simultaneously (under the discrete-log assumption) unless the attacker can solve for a specific combination of forged commitment/proof/z/y that satisfies the linear system for the *specific* `r` produced by hashing the very inputs they're crafting — a circular dependency that standard Fiat-Shamir batching is designed to prevent. [2](#0-1) 

Before reaching the batch math, each commitment and proof byte string is validated as a valid G1 point via `bytes_to_kzg_commitment`/`bytes_to_kzg_proof` (which call `validate_kzg_g1`, enforcing subgroup checks via blst), and each z/y is validated as a canonical field element via `bytes_to_bls_field`, inside the per-item loop in `verify_blob_kzg_proof_batch`. [3](#0-2) 

The `n==0` and `n==1` short-circuits don't affect the 64-item batch case and don't weaken the random-combination guarantee. There is no code path where the attacker can select `r` independently of the forged triple's content — this is the exact security property Fiat-Shamir batching provides, and it is not broken by this implementation. No exploitable cancellation of a forged triple exists within this batch-verification design.

static C_KZG_RET verify_kzg_proof_batch(
    bool *ok,
    const g1_t *commitments_g1,
    const fr_t *zs_fr,
    const fr_t *ys_fr,
    const g1_t *proofs_g1,
    size_t n,
    const KZGSettings *s
) {
    C_KZG_RET ret;
    g1_t proof_lincomb, proof_z_lincomb, C_minus_y_lincomb, rhs_g1;
    fr_t *r_powers = NULL;
    g1_t *C_minus_y = NULL;
    fr_t *r_times_z = NULL;

    assert(n > 0);

    *ok = false;

    /* First let's allocate our arrays */
    ret = new_fr_array(&r_powers, n);
    if (ret != C_KZG_OK) goto out;
    ret = new_g1_array(&C_minus_y, n);
    if (ret != C_KZG_OK) goto out;
    ret = new_fr_array(&r_times_z, n);
    if (ret != C_KZG_OK) goto out;

    /* Compute the random lincomb challenges */
    ret = compute_r_powers_for_verify_kzg_proof_batch(
        r_powers, commitments_g1, zs_fr, ys_fr, proofs_g1, n
    );
    if (ret != C_KZG_OK) goto out;

    /* Compute \sum r^i * Proof_i */
    g1_lincomb_naive(&proof_lincomb, proofs_g1, r_powers, n);

    for (size_t i = 0; i < n; i++) {
        g1_t ys_encrypted;
        /* Get [y_i] */
        g1_mul(&ys_encrypted, blst_p1_generator(), &ys_fr[i]);
        /* Get C_i - [y_i] */
        g1_sub(&C_minus_y[i], &commitments_g1[i], &ys_encrypted);
        /* Get r^i * z_i */
        fr_mul(&r_times_z[i], &r_powers[i], &zs_fr[i]);
    }

    /* Get \sum r^i z_i Proof_i */
    g1_lincomb_naive(&proof_z_lincomb, proofs_g1, r_times_z, n);
    /* Get \sum r^i (C_i - [y_i]) */
    g1_lincomb_naive(&C_minus_y_lincomb, C_minus_y, r_powers, n);
    /* Get C_minus_y_lincomb + proof_z_lincomb */
    g1_add(&rhs_g1, &C_minus_y_lincomb, &proof_z_lincomb);

    /* Do the pairing check! */
    *ok = pairings_verify(&proof_lincomb, &s->g2_values_monomial[1], &rhs_g1, blst_p2_generator());

out:
    c_kzg_free(r_powers);
    c_kzg_free(C_minus_y);
    c_kzg_free(r_times_z);
    return ret;
}
