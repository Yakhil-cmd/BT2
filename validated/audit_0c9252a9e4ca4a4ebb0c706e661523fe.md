### Title
Webhook signature is verified against `repository.owner.login`'s org while state-mutating handlers act on the independent `repository.full_name` field, allowing forged cross-organization webhooks when any configured org has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository_owner`, derived from the attacker-controlled JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Every downstream `Shipit::Webhooks::Handlers::Handler` then locates the `Stack`/`Repository` to mutate using a *different*, equally attacker-controlled field from the same body: `payload.dig('repository','full_name')`. These two fields are never cross-checked against each other.

### Finding Description [3](#0-2) 

`verify_signature` computes `repository_owner` purely from the JSON payload and asks `Shipit.github(organization: repository_owner)` for that org's `GitHubApp`, then verifies the raw body's HMAC against that org's `webhook_secret`: [2](#0-1) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

If the selected organization's `webhook_secret` is blank (a supported, documented configuration — see the multi-org example where `webhook_secret: # nil` is a normal per-org entry), signature verification trivially passes regardless of the `X-Hub-Signature` header content.

Meanwhile, every default handler (e.g. `PushHandler`) resolves the actual target `Stack`s from a completely separate JSON field, unrelated to `repository_owner`: [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the actual database write / GitHub sync) are independent keys in the same unauthenticated JSON, an attacker can construct a payload where `repository.owner.login` names an organization configured in Shipit with no `webhook_secret`, while `repository.full_name` names any other tracked repository (belonging to a fully-secured organization). The signature check passes unconditionally (because that org has no secret to validate), yet the handlers act on the unrelated, victim repository named in `full_name`.

This is the exact analog to the report's binding break — "the organization that authenticated versus the repository that is written" is never checked to be the same entity, mirroring how the original Golom bug let an attacker's authorized action (delegating their own NFT) mutate a completely different, unrelated principal's (the delegatee's) state.

### Impact Explanation
An unauthenticated, unprivileged attacker (no `webhook_secret`, no `ApiClient` token, no GitHub session) can forge `push`/`status`/`check_suite`/`pull_request`/`membership` webhook deliveries for any repository tracked by Shipit, as long as any one organization configured in the multi-org `github:` secrets block lacks a `webhook_secret`. This can trigger `GithubSyncJob` against arbitrary stacks, inject fabricated commit statuses (`StatusHandler`), fabricate `check_suite` results, or manipulate team membership (`MembershipHandler`) for organizations the attacker has no relationship with — an authentication-bypass class issue directly analogous to the High-impact bucket ("escalation into `Shipit.github_teams` authorization" and "unauthenticated read/mutation of stack state").

### Likelihood Explanation
Likelihood depends on operator configuration: it requires the deployment to run Shipit in the multi-organization mode (`secrets.github` keyed by org) with at least one configured organization missing a `webhook_secret`. This is an explicitly documented, first-class configuration path (present verbatim in `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml`), not an undocumented misuse of the engine, making it a realistic operational scenario for larger, multi-org Shipit deployments where some low-value/internal orgs are configured without secrets for convenience.

### Recommendation
Bind webhook signature verification to the specific repository being mutated, not merely to the organization name embedded in the same untrusted payload:
1. After computing `repository_owner`, re-derive the org from `payload.dig('repository','full_name')` (splitting on `/`) and assert it matches `repository_owner` before proceeding — reject on mismatch.
2. Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for an organization that has other, secured organizations configured; require every configured organization to define a secret, or fail closed instead of open.
3. Alternatively, pass the expected organization explicitly into the handler's repository lookup so the resolved `Stack`'s owner is asserted equal to `repository_owner` prior to any mutation.

### Proof of Concept
1. Operator configures Shipit with `github:` keyed by two orgs: `LowValueOrg` (no `webhook_secret` set) and `SecuredOrg` (tracked stack, e.g. `SecuredOrg/prod-app`, with a real `webhook_secret`).
2. Attacker (no credentials) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "LowValueOrg" },
    "full_name": "SecuredOrg/prod-app"
  }
}
```
Any (or no) `X-Hub-Signature` header value.
3. `verify_signature` resolves `Shipit.github(organization: 'LowValueOrg')`, whose `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank.
4. `Shipit::Webhooks::Handlers::PushHandler` resolves stacks via `Repository.from_github_repo_name('SecuredOrg/prod-app')` and enqueues `GithubSyncJob` for `SecuredOrg`'s real stack — despite the attacker never possessing `SecuredOrg`'s webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
