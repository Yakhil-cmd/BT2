### Title
Arbitrary theft of any Stacks address's unlocked STX via attacker-crafted `PreStxOp`/`TransferStxOp` pair - (File: stackslib/src/chainstate/burn/operations/transfer_stx.rs)

### Finding Description
The broken equality is: *"the STX moved by a `TransferStxOp` == STX owned by the address whose Bitcoin key actually authorized the op."* In practice, `sender` is set purely from `PreStxOp.output` [1](#0-0) , and `PreStxOp.output` is derived only from the first Bitcoin output address of the PreStx transaction converted via `try_into_stacks_address()` [2](#0-1) . Any Bitcoin transaction can pay to an arbitrary output address — a sender does not need to control the private key of an address it pays to. There is no cryptographic proof anywhere in this path that the entity broadcasting the `PreStxOp`/`TransferStxOp` pair controls the Stacks (or Bitcoin) private key behind `output`.

`TransferStxOp::parse_from_tx` then takes this attacker-supplied `sender` verbatim and pairs it with `recipient` derived from the transfer tx's own first output (fully attacker-controlled) [3](#0-2) . `TransferStxOp::check()` only rejects a zero amount or `sender == recipient`; it performs no authorization/consent check on `sender` [4](#0-3) . `check_transaction` in the sortition-handling path calls exactly this `check()` and nothing more [5](#0-4) . Finally, `process_transfer_ops` unconditionally calls `run_stx_transfer(sender, recipient, transfered_ustx, ..)` for every accepted `TransferStxOp` [6](#0-5) .

Exploit flow: attacker (using only their own BTC UTXOs) crafts (1) a `PreStxOp` whose `output` is set to `victim_addr` (they merely pay dust BTC to that translated address; no private key needed) and (2) a `TransferStxOp` spending vout=1 of that same PreStx tx (which they do control), with the transfer's own first output resolving to `attacker_addr` and `transfered_ustx` = victim's full unlocked balance. `classify_transaction` will bind `sender = victim_addr` from the `PreStxOp` map/`BurnchainDB` lookup [7](#0-6) , `check()` passes trivially, and `run_stx_transfer` executes the transfer of the victim's real balance to the attacker.

### Impact Explanation
This is theft of unlocked STX belonging to any addressable Stacks principal, moved to an attacker-chosen recipient with zero consent from the victim — matching the Critical category ("theft ... of locked STX" / value the contract did not validate; here even broader since unlocked STX is drained). It is repeatable against any address with a positive unlocked balance for the cost of a couple of dust-value Bitcoin transactions.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only their own Bitcoin UTXOs (no special role, no signer/bond-admin privilege, no need to control the victim's private key at all) and knowledge of the victim's Stacks address (public information). The op-processing pipeline (`get_stacking_and_transfer_and_delegate_burn_ops` family) applies these ops in every epoch from 2.05 onward for every canonical Stacks block, so the attack is broadly and repeatably feasible, limited only by real-world Bitcoin transaction fees.

### Recommendation
Do not treat `PreStxOp.output` as an unauthenticated "sender" claim. Either require a Stacks-side signed authorization from the address named as `sender`/`output` (e.g., require a companion Stacks transaction or witness signature proving ownership of the private key for that address), or restrict `TransferStxOp`/`StackStxOp`/`DelegateStxOp` derivation so that `sender` can only be an address cryptographically tied to the actual Bitcoin key that funded/broadcast the PreStx transaction (verify the PreStx input's scriptSig/key hashes to `output`, rather than accepting an arbitrary output address).

### Proof of Concept
1. Boot chainstate; fund `victim_addr` with N unlocked STX (no involvement from victim beyond existing balance).
2. As attacker, using only attacker's BTC keys, submit `PreStxOp { output: victim_addr }` on regtest (mirroring existing test patterns in `stacks-node/src/tests/epoch_21.rs` and `neon_integrations.rs`, but setting `output` to a *victim*-controlled address instead of the attacker's own).
3. Submit `TransferStxOp { sender: (derived from PreStxOp), recipient: attacker_addr, transfered_ustx: N }`, spending vout=1 of the PreStx tx with only attacker keys.
4. Mine blocks; assert `get_balance(victim_addr) == 0` and `get_balance(attacker_addr) == N`, proving `stx_transfer_consolidated`/`run_stx_transfer` executed the drain — i.e., the equality "funds moved == funds owned by the authorizing key" is broken (recipient balance increases by victim's full balance despite zero victim signature or consent).

impl TransferStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.transfered_ustx == 0 {
            warn!("Invalid TransferStxOp, must have positive ustx");
            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {
            warn!("Invalid TransferStxOp, sender is recipient");
            return Err(op_error::TransferStxSelfSend);
        }
        Ok(())
    }
}
