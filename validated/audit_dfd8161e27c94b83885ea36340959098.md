### Title
`handledRequestTx` Replay Guard Set But Never Checked — Allows Same Source Tx Hash to Be Replayed with a Fresh Nonce, Causing Duplicate Bridge Transfers - (`contracts/service_chain/bridge/BridgeHandledRequests.sol`)

---

### Summary

`BridgeHandledRequests.sol` declares a `handledRequestTx` mapping that is written after every successful handle call but is **never read** before executing a transfer. The only active replay guard is `closedValueTransferVotes[nonce]`, which is keyed on the destination-side nonce, not on the source-chain tx hash. A single operator (threshold = 1, the default) can therefore submit the same source-chain tx hash a second time under a fresh, unused nonce and receive a second payout from the bridge.

---

### Finding Description

`BridgeHandledRequests.sol` defines the replay-protection contract:

```solidity
mapping(bytes32 => bool) public handledRequestTx;

function _setHandledRequestTxHash(bytes32 _requestTxHash) internal {
    handledRequestTx[_requestTxHash] = true;
}
``` [1](#0-0) 

Every handle function calls `_setHandledRequestTxHash` after the vote threshold is reached:

```solidity
_setHandledRequestTxHash(_requestTxHash);   // marks hash as handled
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);
// ... transfer executes
``` [2](#0-1) [3](#0-2) [4](#0-3) 

A repository-wide search for `handledRequestTx` returns **only** the three lines inside `BridgeHandledRequests.sol` itself (declaration, setter, public getter). There is no `require(!handledRequestTx[_requestTxHash])` guard anywhere in the production contract code.

The only active guard is `closedValueTransferVotes[_requestNonce]` inside `_voteValueTransfer`:

```solidity
require(!closedValueTransferVotes[_requestNonce], "closed vote");
``` [5](#0-4) 

This guard is keyed on the **destination-side nonce**, not on the source-chain tx hash. An operator can therefore replay the same source tx hash under any unused destination nonce and bypass the guard entirely.

Additionally, `_updateHandleNonce` deletes `closedValueTransferVotes[i]` for cleaned-up nonces:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) {
    delete closedValueTransferVotes[i];
}
lowerHandleNonce = i;
``` [6](#0-5) 

Once a nonce window is cleaned up, `lowerHandleNonce` advances past it, so those nonces cannot be reused. However, any **future** unused nonce (above `lowerHandleNonce`) remains open, and the missing `handledRequestTx` check means the same source tx hash can be submitted against any of them.

---

### Impact Explanation

**High.** A malicious operator with threshold = 1 (the deployment default) can drain the bridge by replaying a single legitimate source-chain tx hash against successive unused destination nonces. Each replay triggers a full KLAY transfer (`_to.call.value(_value)("")`), ERC-20 `safeTransfer`/`mint`, or ERC-721 `transferFrom`/`mintWithTokenURI`. The bridge contract holds all locked or minted assets, so repeated replays can exhaust its entire balance. The `handledRequestTx` mapping was clearly designed to prevent exactly this — the parent contract is named `BridgeHandledRequests` — but the guard was never wired in.

---

### Likelihood Explanation

**Low-to-medium.** Exploitation requires a registered operator key to be compromised or malicious. With the default threshold of 1, a single operator suffices; no collusion is needed. Operators are registered by the bridge owner, so the attack surface is limited to the operator set, but the default single-operator configuration is common in service-chain deployments.

---

### Recommendation

Add the missing check at the top of every handle function, before the vote:

```solidity
require(!handledRequestTx[_requestTxHash], "already handled");
```

This should be placed before `_lowerHandleNonceCheck` so that a replayed tx hash is rejected immediately regardless of nonce state. The existing `_setHandledRequestTxHash` call after the vote can remain as-is.

---

### Proof of Concept

Setup: bridge deployed with default threshold = 1, operator = `op1`, bridge holds 10 KLAY.

1. Source chain emits `RequestValueTransfer` with `txhash = H`, `nonce = 0`, `value = 1 KLAY`, `to = alice`.
2. `op1` calls `handleKLAYTransfer(H, from, alice, 1e18, 0, blockNum, "")`.
   - `_lowerHandleNonceCheck(0)` passes (`lowerHandleNonce == 0`).
   - `_voteValueTransfer(0)`: `closedValueTransferVotes[0]` is `false` → vote passes, sets it `true`.
   - `_setHandledRequestTxHash(H)` → `handledRequestTx[H] = true` (never checked again).
   - 1 KLAY transferred to alice. ✓
3. `op1` calls `handleKLAYTransfer(H, from, alice, 1e18, 1, blockNum, "")` — **same `H`, nonce = 1**.
   - `_lowerHandleNonceCheck(1)` passes.
   - `_voteValueTransfer(1)`: `closedValueTransferVotes[1]` is `false` → vote passes, sets it `true`.
   - `handledRequestTx[H]` is `true` but **never checked** → no revert.
   - 1 KLAY transferred to alice again. ✓ (duplicate)
4. Repeat step 3 with nonce = 2, 3, … until bridge is drained. [7](#0-6) [8](#0-7) [9](#0-8)
