### Title
Unsanitized OAuth token injected into `git credential approve` heredoc allows cross-host credential store poisoning - ([File: pkg/cmd/auth/shared/gitcredentials/updater.go])

### Summary
`(*Updater).Update` builds the stdin payload for `git credential approve` by directly interpolating the caller-supplied `hostname`, `username`, and `password` into a heredoc with no escaping of newlines. The `password` argument is the raw OAuth access token returned by the host's token-exchange response, which is fully attacker-controlled when the victim points `gh` at an attacker-run GitHub Enterprise-style host. Because the git credential helper protocol parses stdin line-by-line as `key=value` pairs with last-value-wins semantics, an attacker-crafted token containing embedded `\n` sequences can inject or override `host=`, `protocol=`, and `username=` attributes in the same `git credential approve` invocation, letting the attacker dictate which host/user/password tuple gets persisted in the victim's OS credential store or `~/.git-credentials`.

### Finding Description
The call chain is: `shared.Login` (`pkg/cmd/auth/shared/login_flow.go`) obtains `authToken` from `authflow.AuthFlow`, which returns `token.Token` straight from the OAuth flow response with no validation of its contents [1](#0-0) . `Login` then calls `opts.CredentialFlow.Setup(hostname, username, authToken)` when the flow determined a non-gh credential helper is configured [2](#0-1) . `GitCredentialFlow.Setup` forwards straight to `Updater.Update(hostname, username, authToken)` whenever an existing (non-gh) credential helper is already configured for the host [3](#0-2) .

`Update` then builds the `git credential approve` stdin via `heredoc.Docf` string interpolation with no sanitization of any of the three arguments: [4](#0-3) 

Since `password` is the literal attacker-controlled OAuth token string, an attacker who controls the token-exchange response can set it to something like:
```
"realtoken\nhost=github.com\nprotocol=https\nusername=attacker\npassword=evilpass\n"
```
Git's credential protocol reads stdin as sequential `key=value` lines up to a blank line/EOF, and duplicate keys within the same block simply overwrite the previous value. As a result, the additional injected `host=`, `protocol=`, and `username=` lines silently override the legitimate `hostname`/`username` values already written earlier in the same heredoc, and the trailing `password=evilpass` overrides the intended password line too — giving the attacker full control of the final `host`/`protocol`/`username`/`password` tuple sent to `git credential approve`. No output sanitization, escaping, or use of `--` /NUL-delimited encoding exists anywhere on this path.

### Impact Explanation
This breaks credential confinement: a credential record for an attacker-chosen host (including `github.com` or any other host the victim uses) gets implanted into the victim's persistent credential store (OS keychain, Windows Credential Manager, or `~/.git-credentials` via `git-credential-store`) via the victim's already-configured, trusted credential helper. Because the injected record silently overwrites the tuple bound for the intended host, subsequent `git` operations against that other host will use the attacker-supplied username/password instead of the victim's real credentials — a wrong-host/wrong-account credential routing and credential-store poisoning primitive. This matches the "wrong-host or wrong-account request routing" and "file write outside the intended path" impact classes named in the rules.

### Likelihood Explanation
The preconditions are narrow but realistic: the victim must run `gh auth login --hostname <attacker-host>` (or configure an Enterprise host) pointing at a server fully controlled by the attacker, and must already have a non-gh git credential helper configured (common on macOS/Windows by default, or via Git Credential Manager). Given those two conditions — both squarely within the described attacker model ("host the victim points gh at") — the exploit is fully deterministic and repeatable: the attacker's token endpoint simply returns a crafted `access_token` string.

### Recommendation
Sanitize/validate the OAuth token, username, and hostname before embedding them in the credential-helper protocol payload — at minimum reject or escape any `\n`/`\r`/NUL bytes in `hostname`, `username`, and `password` in `Updater.Update`, and validate `authToken` immediately after the OAuth exchange in `authflow.AuthFlow` to ensure it does not contain control characters before it is ever passed downstream.

### Proof of Concept
Go test using the existing `run.Stub()` git-stub harness (as in `pkg/cmd/auth/shared/git_credential_test.go`):
```go
func TestUpdate_PasswordInjection(t *testing.T) {
    cs, restoreRun := run.Stub()
    defer restoreRun(t)
    cs.Register(`git credential reject`, 0, "")
    cs.Register(`git credential approve`, 0, "", func(args []string) {})

    u := &Updater{GitClient: &git.Client{GitPath: "some/path/git"}}
    maliciousToken := "realtoken\nhost=github.com\nprotocol=https\nusername=attacker\npassword=evilpass\n"
    err := u.Update("example.com", "monalisa", maliciousToken)
    require.NoError(t, err)

    // Capture approveCmd.Stdin content and parse it per git-credential
    // line protocol (key=value, last-value-wins). Assert the parsed
    // attribute set equals {host: "example.com", username: "monalisa",
    // password: maliciousToken} — i.e., no attribute is overridden by
    // attacker-embedded newline content. This assertion will FAIL against
    // current code, proving the injection.
}
```
Expected/actual: the parsed final attribute set from stdin resolves to `host=github.com`, `username=attacker`, `password=evilpass` instead of the intended `host=example.com`, `username=monalisa`, `password=<realtoken>`, confirming injection.
