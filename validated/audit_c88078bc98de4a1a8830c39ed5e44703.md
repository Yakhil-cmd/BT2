## Title
Poll question field has no length limit before being written to a fixed-size MySQL column, allowing a single posted unit to crash every full MySQL-backed node - (File: `validation.js`)

### Summary
The external report describes a MySQL/MariaDB `InnoDB` bug where network-reachable, low-privilege input can crash or hang the database engine (DoS). `ocore` has an analogous class of bug: the `poll` message's `question` field is validated for type and trimming, but never for length, before being inserted into a `VARCHAR(4096)` column in the `polls` table. A single valid, correctly-signed unit posted by any unprivileged user can carry a `question` string many megabytes long (up to the overall `MAX_UNIT_LENGTH` cap), which the DB layer will reject with a SQL error at write time. Because the SQL wrapper is intentionally configured to convert *any* query error into an uncaught exception that kills the process, this directly crashes the node — mirroring the "network-reachable, low-privileged actor triggers DB engine hang/crash" pattern of the CVE.

### Finding Description
`validateInlinePayload`'s `"poll"` case checks that `question` is a string and is trimmed, and checks `choices` against `constants.MAX_CHOICE_LENGTH`, but performs **no length check on `question` at all**: [1](#0-0) 

Contrast this with the `choices` field, which is explicitly bounded via `constants.MAX_CHOICE_LENGTH` — there is no equivalent `MAX_QUESTION_LENGTH` constant anywhere in the codebase: [2](#0-1) 

The only remaining bound on `question` size is the overall unit size limit, `MAX_UNIT_LENGTH` (5,000,000 bytes by default), enforced generically in `validate()`: [3](#0-2) 

When the unit is written, `writer.saveJoint` inserts the raw, unbounded `poll.question` string directly into the `polls` table: [4](#0-3) 

But the MySQL schema defines the `question` column as fixed-size `VARCHAR(4096)`: [5](#0-4) 

Any `question` longer than 4096 characters causes MySQL to raise a data-truncation/`ER_DATA_TOO_LONG`-class error on `INSERT`. The MySQL connection wrapper is explicitly designed to convert *every* query error into a thrown exception that is intended to "kill the program": [6](#0-5) 

Because this exception is thrown asynchronously inside the query callback (not inside a `try/catch` that validation/writer code can intercept), it becomes an uncaught exception. The global uncaught-exception handler logs diagnostics but ultimately re-throws to crash the process: [7](#0-6) 

This crash happens identically on every full node running on MySQL storage that processes this unit — both when the original poster's node commits the unit via `saveJoint`, and on every peer node that receives, validates, and writes the same unit as part of normal DAG propagation (`handleJoint` → `validation.validate` → `writer.saveJoint`): [8](#0-7) 

### Impact Explanation
A single unprivileged unit poster can craft one validly-signed `poll` unit whose `question` field exceeds 4096 bytes (well under the 5MB unit-size cap). Once broadcast, this unit propagates through the DAG like any other transaction and every MySQL-backed full node that attempts to persist it (`INSERT INTO polls`) will hit a data-too-long SQL error, which the custom MySQL wrapper converts into a fatal, process-killing exception. This can crash the poster's own node and any peer node (including witnesses/hub-adjacent full nodes) that accepts and writes the unit, disrupting the network's ability to validate and confirm new units until operators identify and patch/restart affected nodes — matching the accepted impact category "a network unable to confirm new units."

### Likelihood Explanation
Likelihood is high: no special privileges, AA execution, or race conditions are required. Any unit poster can include a `poll` message with an oversized `question` in an otherwise normal, correctly signed and hashed unit; all other structural validation checks (`hasFieldsExcept`, type, trim) pass. The bug is purely a missing length bound compared to the sibling `choices` field, which is bounded.

### Recommendation
Add an explicit length check for `payload.question` in `validateInlinePayload`'s `"poll"` case, e.g. introduce `constants.MAX_POLL_QUESTION_LENGTH` (aligned with the `VARCHAR(4096)` schema column, accounting for UTF-8 byte expansion) and reject payloads exceeding it, mirroring the existing `constants.MAX_CHOICE_LENGTH` check for `choices`. Additionally, harden `mysql_pool.js` so DB-level constraint/data errors surface as validation failures instead of unconditionally throwing and crashing the process.

### Proof of Concept
1. Construct a unit with a single `payment` message plus a `poll` message where `payload.question` is a string of, e.g., 100,000 characters (still well under `MAX_UNIT_LENGTH`).
2. Sign and post the unit normally; it passes `validateInlinePayload`'s `"poll"` case since no length check exists (`validation.js:1784-1813`).
3. When `writer.saveJoint` executes `INSERT INTO polls (unit, message_index, question) VALUES(?,?,?)` with this oversized string on a MySQL-backed node (`writer.js:195`), MySQL returns a data-too-long error.
4. `mysql_pool.js`'s query wrapper (`mysql_pool.js:34-48`) throws this error unconditionally, producing an uncaught exception that crashes the node process (`network.js:4530-4543`), reproducing on every MySQL-backed node that processes the same unit.
