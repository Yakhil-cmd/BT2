### Title
Hardcoded `bAllowUnresolvedInnerDefinitions = true` Silently Disables Signature-Requirement Guard for Unresolved `address` References in Definition Validation - (File: definition.js)

### Summary
`validateDefinition()` in `definition.js` enforces that every branch of an address (or asset) spending-condition definition contains at least one real authentifier (`sig`/`hash`), rejecting any definition where a branch could be satisfied without proof of key ownership. For the `'address'` opcode, when the referenced address's definition cannot be resolved (not yet posted on-chain and not co-signed in the same unit), the code was clearly designed to consult a validation-state flag to decide whether to treat that as satisfied. Instead, the flag check is commented out and replaced with a hardcoded `true`, unconditionally treating any unresolved nested address reference as "has a signature," regardless of what the caller/validation context actually intended. [1](#0-0) 

### Finding Description
Inside `validateDefinition()`'s `evaluate()` function, the `'address'` case resolves a referenced address's definition via `storage.readDefinitionByAddress`. When the definition is not found in storage, `ifDefinitionNotFound` is invoked:

```js
ifDefinitionNotFound: function(definition_chash){
//	if (objValidationState.bAllowUnresolvedInnerDefinitions)
//		return cb(null, true);
	var bAllowUnresolvedInnerDefinitions = true;
	...
	if (arrDefiningAuthors.length === 0) // no address definition in the current unit
		return bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb("definition of inner address "+other_address+" not found");
	...
}
``` [2](#0-1) 

The commented-out line shows the intended logic: whether to allow an unresolved inner address reference should depend on `objValidationState.bAllowUnresolvedInnerDefinitions`, a value presumably set (or left unset/false) by the caller based on validation context (e.g., strict validation of a brand-new address's own definition vs. more permissive contexts such as composing/pre-checking a definition on a wallet client, referenced also in `wallet_defined_by_addresses.js`). By hardcoding the flag to `true`, the code unconditionally short-circuits to `cb(null, true)` — i.e., it reports the branch as satisfying the "has a signature" requirement — even in strict contexts (e.g., during `validateAuthor`'s call chain `Definition.validateAuthentifiers` → `validateDefinition`, invoked at `validation.js:1243-1254` when a brand-new address definition is submitted with a unit). [3](#0-2) 

This directly parallels the reported bug class: a security-relevant conditional (approval/authorization gate keyed off configuration/context) is replaced by a hardcoded bypass value, defeating the intended check regardless of the actual validation context that should have governed it.

The top-level enforcement this weakens is:
```js
if (!bHasSig && !bAssetCondition)
	return handleResult("each branch must have a signature");
``` [4](#0-3) 

which exists specifically to prevent an address definition from having any branch that can be satisfied without proof of key ownership.

### Impact Explanation
The structural `bHasSig` guard is meant to be an invariant enforced uniformly regardless of calling context; hardcoding it bypasses whatever contextual restriction the flag was meant to enforce (the comment strongly implies stricter contexts should NOT get the free pass). Because this validation path is reached from `validateAuthor` when a unit defines a brand-new address (`objAuthor.definition`), a definition consisting of (or containing an `'or'` branch of) `['address', X]` referencing a not-yet-existing address `X` is structurally accepted as satisfying the signature requirement even though, in isolation, that branch can never be proven with a real signature until `X` itself is defined and resolves to a definition — and there is no compile-time guarantee that `X`'s eventual real definition will itself contain a valid signature everywhere it's needed, since forward "address" delegation composes trust chains whose final signature adequacy is only checked far downstream, at authentifier-evaluation time for whichever unit later supplies `X`'s authentifiers. Removing the intended conditional here removes a defense-in-depth check that was meant to make such deferred/forward-referencing definitions provably safe under specific validation contexts, weakening the structural guarantee that "every address definition, on its face, requires proof of a private key" for any code path that relies on `validateDefinition`'s structural verdict (rather than solely on the separate, independent `validateAuthentifiers` real-evaluation pass).

### Likelihood Explanation
The path is reachable by an unprivileged unit poster: anyone can post a unit that defines a new address (`author.definition`) whose spending-condition array contains an `['address', 'SOME_ADDRESS_NOT_YET_DEFINED']` branch. No special privileges, hub/peer trust, or node compromise is required — only crafting an ordinary DAG unit, which matches the in-scope "unit validation, address definitions and authentifiers" attack surface.

### Recommendation
Restore the intended conditional check instead of the hardcoded override:
```js
ifDefinitionNotFound: function(definition_chash){
	if (!objValidationState.bAllowUnresolvedInnerDefinitions)
		return cb("definition of inner address " + other_address + " not found");
	...
	if (arrDefiningAuthors.length === 0)
		return objValidationState.bAllowUnresolvedInnerDefinitions ? cb(null, true) : cb("definition of inner address "+other_address+" not found");
	...
}
```
Ensure `objValidationState.bAllowUnresolvedInnerDefinitions` is explicitly and correctly set (or left falsy) by every caller of `validateDefinition`/`Definition.validateAuthentifiers`, matching the strictness required by each specific validation context (e.g., strict for on-chain author-definition validation, permissive only where genuinely safe, such as isolated composer-side pre-checks). Add or restore a regression test asserting that a definition whose only branch is an unresolved `['address', X]` reference (with no co-signing author) is rejected as "each branch must have a signature" in the strict validation context used by `validateAuthor`.

### Proof of Concept
1. Craft a unit that, in its `authors` array, includes an author entry with:
   - `address`: freshly-chosen address whose `chash160` matches the definition below (never used on-chain before).
   - `definition`: `["address", "GRANDMA_ADDRESS_NEVER_SEEN_ON_CHAIN"]` (a syntactically valid, never-before-posted address, not co-authored in this same unit).
2. Submit/post this unit for validation (`validation.js` → `validateAuthor` → `Definition.validateAuthentifiers` → `validateDefinition`). [5](#0-4) 
3. In `validateDefinition`'s `evaluate()`, the `'address'` case calls `storage.readDefinitionByAddress`; since `GRANDMA_ADDRESS_NEVER_SEEN_ON_CHAIN` has no stored definition, `ifDefinitionNotFound` fires.
4. Because `bAllowUnresolvedInnerDefinitions` is hardcoded `true`, `arrDefiningAuthors.length === 0` (no such author in this unit) still returns `cb(null, true)` — i.e., the definition is reported as containing a valid signature branch — instead of the properly-conditioned behavior that would depend on `objValidationState.bAllowUnresolvedInnerDefinitions`. [1](#0-0) 
5. `validateDefinition` therefore does NOT reject the definition with `"each branch must have a signature"`, even though structurally the branch requires no attacker-provided signature at all in this validation pass — demonstrating the guard is bypassed by the hardcoded flag rather than being governed by validation context as originally intended.

Note: I was not able to fully trace every downstream caller/consumer that sets or expects `objValidationState.bAllowUnresolvedInnerDefinitions` (e.g., the reference in `wallet_defined_by_addresses.js`) within the available search budget; a full audit of all call sites of `validateDefinition`/`Definition.validateAuthentifiers` would be needed to enumerate every concrete authorization outcome affected by this hardcoded bypass. Due to index size limits, some file contents (in particular the full body of `wallet_defined_by_addresses.js`) were not available for deeper inspection — a Devin session with full repository access would be needed to confirm every downstream effect.
