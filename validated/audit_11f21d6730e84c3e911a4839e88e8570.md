This confirms the vulnerability. Every other handler (`PushHandler`, `PullRequest::*Handler`, etc.) scopes its query through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` using `payload.dig('repository', 'full_name')` before touching any records [1](#0-0) [2](#0-1) . `StatusHandler#process` alone bypasses this scoping and queries `Commit.where(sha: params.sha)` directly against the global `commits` table with no repository/stack filter at all [3](#0-2) .

### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no repository/stack scoping, unlike every other webhook handler which resolves the target stacks through `Repository.from_github_repo_name(payload['repository']['full_name'])`. A tenant that owns any Shipit-tracked repository (and therefore legitimately knows their own org's `webhook_secret`) can send a validly-signed `status` webhook for their own repository citing a `sha` value that also exists as a `Commit` row belonging to a different stack/tenant, causing Shipit to write a forged CI status onto the victim's commit.

### Finding Description
The broken binding: the question asks whether `repository claimed in payload == repository of matched commit`. Tracing the code shows this equality is never checked. `verify_signature` only confirms that the payload was signed with the secret belonging to `repository_owner` (`params.dig('repository','owner','login')`) [4](#0-3) ; it never confirms that the claimed repository actually owns the commit referenced by `sha`. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) , which matches every `Commit` row in the entire `commits` table with that `sha`, regardless of `stack_id`/repository, because the `Commit` model itself provides no cross-repository uniqueness guarantee (`belongs_to :stack` is the only scoping and it isn't applied here) [5](#0-4) .

A git commit SHA is not a secret and is not cryptographically bound to one repository — the same SHA legitimately recurs across forks, mirrors, or shared-history repositories that Shipit tracks as separate stacks. This is distinct from every other handler: `Handler#stacks` explicitly resolves via `Repository.from_github_repo_name(repository_name)` before any stack is touched [1](#0-0) , and `PushHandler#process` filters `stacks.not_archived.where(branch:)` before acting [2](#0-1) . `StatusHandler` never calls `stacks`, so its own `params` schema and `Handler` base class provide no protection here — `ExplicitParameters` only validates types/presence of `sha`/`state`, not repository ownership [6](#0-5) .

Exploit flow: attacker owns/operates repository A, onboarded as its own Shipit tenant with a legitimately known `webhook_secret` for their org (multi-org GitHub App config resolved via `Shipit.github(organization: repository_owner)` / `github_app_config` [7](#0-6) ). Repository A shares commit history (fork, mirror, or common ancestor commit) with victim repository B, tracked as a different stack in the same Shipit instance. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own known secret, `repository.owner.login` set to their own org (so `verify_signature` passes), and `sha` set to the shared commit's SHA with `state: success` (or `failure`). `StatusHandler#process` finds and updates the `Commit` row belonging to victim stack B, since the `sha` column has no repository scoping. `commit.create_status_from_github!` then writes a `Status`, potentially enabling CI, triggering `deployable_status`/`commit_status` hooks, and feeding `schedule_continuous_delivery`, which can affect real deploy/merge automation on the victim's stack [8](#0-7) [9](#0-8) .

### Impact Explanation
An attacker who is a legitimate (but hostile) tenant of a multi-tenant Shipit instance can forge success/failure CI status for another tenant's commits, as long as the commit SHA is shared/known (trivial for forks/mirrors, or any commit whose SHA the attacker can observe on GitHub). This is a cross-tenant record write: a status row is created for a stack the attacker never authenticated against, potentially flipping `deployable?`/`continuous_deployment?` gating and triggering deploys via `schedule_continuous_delivery` — matching the Critical criterion "a payload for one repository mutating another's stack, commit, task or team" and possibly leading to "an unauthorized deploy." The attack is repeatable against any Shipit-tracked stack whose commit history overlaps with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the attacker must be an onboarded tenant of the same Shipit instance (own at least one Shipit-tracked repository with a working GitHub App/webhook integration and thus know their own `webhook_secret`), and the target victim stack must share at least one commit SHA with the attacker's repository (forks, mirrors, or vendored/shared-history repos — common in monorepo-splits or org migrations). This is not a same-org requirement if Shipit runs in single-secret (non-multi-org) mode, where every payload is validated with one shared secret regardless of the claimed `repository.owner.login`, making the exploit reachable by any tenant of that single-secret installation without cross-referencing organizations at all. Attacker cost is a single crafted HTTP POST with no need for a GitHub session, API token, or privileged role.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve stacks via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (i.e., use the inherited `stacks` helper) and restrict the `Commit` lookup to `stacks.map(&:id)`/`stack_id` in addition to `sha`, e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status webhook can only affect commits belonging to the repository that authenticated the request.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack` fixtures/records in different repositories (e.g. `stack_a` in `attacker/repo`, `stack_b` in `victim/repo`).
2. Insert two `Commit` rows with the identical `sha` value `"deadbeef" * 5`, one belonging to `stack_a`, one to `stack_b`.
3. Stub/allow `verify_signature` (as existing tests do via `GithubHook.any_instance.stubs(:verify_signature).returns(true)`) to simulate a validly-signed request from the attacker's own org.
4. `POST :create` with `X-Github-Event: status`, body `{ sha: <shared_sha>, state: 'success', repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } } }`.
5. Assert the equality that should hold but doesn't: `stack_b.commits.find_by(sha: shared_sha).status.state` changed from its prior state to `'success'`, i.e. `refute_equal previous_state, victim_commit.reload.status.state`, while the request payload's `repository.full_name` (`attacker/repo`) never equals `stack_b.repository.full_name` (`victim/repo`) — proving the write landed on a repository that never authenticated it.
