## Title
Meta-transaction bundles containing a `DelegateAction` can be forced to revert via front-running of the `SignedDelegateAction`'s nonce — ([File: runtime/runtime/src/actions.rs])

### Summary
NEAR's meta-transaction (`DelegateAction`/`SignedDelegateAction`) mechanism is structurally analogous to `PermitSubmitterHook`: a user signs an authorization off-chain (bound to a monotonically-increasing nonce) and hands it to a third party — a relayer — to submit on-chain. Because the signed payload is not restricted to being submitted only by the original signer, and because it is consumed by a strict "nonce must be greater than stored nonce" check, anyone who obtains the `SignedDelegateAction` bytes can front-run the relayer, submit it first, and permanently invalidate it for the intended relayer's transaction — forcing that (potentially multi-action) transaction/receipt to fail, exactly like the `permit()` front-running griefing in the report.

### Finding Description
A `DelegateAction` is a NEP-366 meta-transaction: the sender signs it off-chain and gives it to a relayer, who wraps it in a `SignedTransaction` and submits it, paying gas/deposit on the sender's behalf. This is defined in [1](#0-0) , and the intended flow (off-chain signature handed to a relayer) is documented at [2](#0-1) .

Validation of the `DelegateAction` happens on-chain in `apply_delegate_action`, which checks the signature, expiry, sender match, then calls `validate_delegate_action_key`: [3](#0-2) .

`validate_delegate_action_key` enforces the same one-time-use nonce semantics as an ERC-20 `permit()` signature: the nonce must be strictly greater than the currently stored access-key (or gas-key) nonce, otherwise the action fails with `DelegateActionInvalidNonce`, and the check/update happens unconditionally regardless of who submitted the wrapping transaction: [4](#0-3) [5](#0-4) .

Because a `SignedDelegateAction` is just signed data (not access-controlled to be submitted only by the designated relayer), **any account** can wrap the exact same `SignedDelegateAction` bytes in its own `Action::Delegate`/`Action::DelegateV2` transaction and submit it first. Once processed, the sender's access-key nonce (or gas-key nonce) advances, so when the legitimate relayer's transaction carrying the identical `SignedDelegateAction` is later applied, `validate_delegate_action_key` will reject it with `DelegateActionInvalidNonce`, exactly mirroring `PermitSubmitterHook.compose()` reverting because `permit()` was already consumed by a front-runner.

Critically, per the runtime's action-execution model, actions within a receipt are executed sequentially and if any one action fails, the entire receipt fails: [6](#0-5) . This is enforced in `apply_action_receipt`, which breaks out of the action loop and marks the whole result as an error as soon as one action errors: [7](#0-6) . So if a relayer bundles the `DelegateAction` together with other actions (e.g. a payment-to-relayer action plus the delegated payload) in one outer transaction/receipt, front-running the nonce forces the **entire bundle** to revert — the direct analog of "Bundles ... can be forced to revert."

A test in the repository already demonstrates the underlying mechanic (replay/front-run of the same signed delegate action is rejected due to nonce reuse), confirming the on-chain check is deterministic and triggerable by any submitter: [8](#0-7) .

### Impact Explanation
This is a griefing/DoS vector against relayers and end users relying on meta-transactions:
- A relayer's bundled transaction (which may combine the delegate action with a self-payment action or other actions) can be forced to fail entirely by a third party who observes the `SignedDelegateAction` (e.g., via mempool/gossip, or because the user broadcasts it to multiple relayers).
- The relayer still pays the base execution/verification gas for the failed action per `apply_delegate_action`'s cost-accounting comments, so front-running wastes relayer funds and denies the user's intended action, without giving the attacker any direct financial gain — the classic "no-cost griefing" pattern flagged in the original report.
- This does not directly cause fund theft, but it is a legitimate, concrete availability/DoS impact on a core protocol feature (meta-transactions/gas keys), reachable by any unprivileged account submitting an ordinary transaction.

### Likelihood Explanation
Any account can observe a `SignedDelegateAction` once it has left the signer's control (handed to a relayer, or visible once broadcast/gossiped) and re-wrap it in its own `Action::Delegate`/`DelegateV2` transaction, requiring no special privilege, validator role, or node access — only knowledge of publicly transmitted signed data, matching the report's "front-run and directly call... beforehand" pattern.

### Recommendation
Consider mitigations analogous to the reporter's recommendation of wrapping `permit()` in a try/catch: e.g., allow the relayer-submitted transaction to tolerate/absorb a "nonce already consumed" `DelegateAction` failure without aborting the entire bundle (for instance, by not bundling unrelated payment actions together with the `Delegate` action in the same receipt, or by giving relayers a way to detect/pre-check nonce state before finalizing a bundle), and/or documenting to relayers that they should check the live access-key/gas-key nonce immediately before submission and treat delegate actions as racy, single-attempt operations rather than embedding them in multi-action atomic bundles.

### Proof of Concept
1. Sender signs a `SignedDelegateAction` (nonce N) and hands it off-chain to Relayer R, who plans to submit `[PaymentToRelayer, Delegate(signed_delegate_action)]` in one transaction (`apply_delegate_action`, [3](#0-2) ).
2. Attacker A observes the same `SignedDelegateAction` bytes (e.g., from network gossip) and submits its own transaction `[Delegate(signed_delegate_action)]` with a higher priority, which is processed first and advances the sender's access-key nonce via `validate_delegate_action_key` ( [9](#0-8) ).
3. When R's transaction executes, the identical `SignedDelegateAction` now fails with `DelegateActionInvalidNonce` because `delegate_nonce.nonce() <= current_nonce` ( [4](#0-3) ).
4. Because action-receipt execution aborts the entire receipt on the first failing action ( [7](#0-6) ), R's whole bundled transaction — including the unrelated `PaymentToRelayer` action — reverts, exactly matching "Bundles ... can be forced to revert" from the source report.

    pub delegate_action: DelegateAction,
    pub signature: Signature,

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
