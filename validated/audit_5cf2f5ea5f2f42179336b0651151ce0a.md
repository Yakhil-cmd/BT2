### Title
Crafted router payload can inject an unauthorized token transfer into the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Medium-severity authorization-tree injection: `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` forward caller-supplied `swap: Bytes` into the configured router, and the router executes pool and token addresses named by that payload without an allowlist. [1](#0-0) [2](#0-1) 

A route-selected contract can therefore invoke an unrelated token transfer from the account that authorized the controller operation, and Soroban records that transfer as a child of the caller's authorization entry. [3](#0-2) [4](#0-3) 

### Finding Description
`swap_collateral` authenticates the caller, withdraws collateral, and passes its `swap` bytes into `swap_tokens`. [5](#0-4) 

`swap_debt` follows the same pattern: it authorizes the caller, borrows into the controller, and forwards `swap` to the router-backed swap helper. [6](#0-5) 

`swap_tokens` authorizes only the exact controller-to-router input transfer, but then passes the caller-controlled payload to `execute_strategy` without independently validating the contracts that the payload names. [1](#0-0) 

The router resolves each hop's `pool`, `token_in`, and `token_out` from the payload's attacker-influenceable `assets` registry and dispatches the selected venue adapter against that pool. [2](#0-1) [7](#0-6) 

Measured router balances detect missing hop output or incorrect input spend, but they do not prevent route-invoked code from issuing an additional token call that requires the original caller's authorization. [8](#0-7) [9](#0-8) 

This is analogous to CVE-2018-12561 because a structured input field supplies extra target behavior that executes in the context of the original privileged authorization rather than merely selecting economic parameters. [10](#0-9) 

### Impact Explanation
A malicious route can cause an unrelated wallet token transfer from the victim to an attacker while still returning enough listed output for the lending operation to pass its balance and account-risk checks. [11](#0-10) [12](#0-11) 

The recorded authorization places the injected transfer under the caller's `swap_collateral` root, so a client that signs the returned tree authorizes theft beyond the expected lending strategy. [13](#0-12) 

The exploit causes direct theft of user funds, including tokens that are not listed or deposited in the lending protocol. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
The route bytes are ordinary caller-controlled arguments for `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, so an attacker can supply a poisoned route without protocol privileges. [16](#0-15) [17](#0-16) 

Execution requires the victim to sign the authorization tree that simulation reports, because an unsigned injected transfer fails and rolls back the entire call. [18](#0-17) 

The practical precondition is therefore a route source, interface, or user that accepts the poisoned authorization tree rather than rejecting unexpected child invocations. [19](#0-18) 

The dedicated test demonstrates that signing the same simulation-produced tree makes the injected transfer execute successfully and move the victim's entire unrelated token balance. [15](#0-14) 

### Recommendation
Restrict executable route hops to a governance-controlled venue or pool registry, or encode venue contract identities separately from arbitrary payload-controlled addresses. [20](#0-19) 

At minimum, enforce an authorization-shape invariant at integration boundaries by rejecting any simulation tree whose controller or `execute_strategy` root contains unexpected child invocations. [19](#0-18) 

The controller-side authorization should also document and monitor the exact expected child invocation for each strategy, since its balance checks only bound the controller's routed funds and not unrelated wallet transfers authorized under the same root. [21](#0-20) [22](#0-21) 

### Proof of Concept
The existing adversarial test registers a router double that pulls the expected input, invokes a payload-selected hop pool, and returns a fair output so the outer swap can succeed. [23](#0-22) 

The attacker-controlled hop pool stores the victim, arbitrary wallet token, recipient, and amount, then calls `transfer(victim, attacker, amount)` during the route. [24](#0-23) 

The test constructs the malicious `swap` bytes with that hop pool while using listed USDC and ETH markets for the normal `swap_collateral` operation. [25](#0-24) 

In recording mode, the simulated `swap_collateral` authorization includes a child `wallet_token.transfer(victim, attacker, WALLET_BALANCE)` invocation. [13](#0-12) 

If the victim signs only the benign root without children, the unauthorized transfer fails and state rolls back. [18](#0-17) 

If the victim signs the poisoned tree that simulation returned, the call succeeds, the victim's wallet balance becomes zero, and the attacker receives `WALLET_BALANCE`. [15](#0-14)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```

```markdown
### INV-STRAT-01 — Controller router authority binds one input transfer

The controller authorizes one exact
`token_in.transfer(controller, configured_router, amount_in)` invocation,
without sub-invocations. This grants invocation authority, without a token
allowance.

The controller ignores the router's return value, rejects input-balance growth
and rejects measured spending above `amount_in`.
```
