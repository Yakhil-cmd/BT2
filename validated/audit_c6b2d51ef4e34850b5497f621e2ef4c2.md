### Title
Webhook signature verification selects the HMAC secret from an attacker-controlled `repository.owner.login`/`organization.login` field, decoupling the authenticated organization from the repository that handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC signature against by parsing it out of the untrusted JSON body itself (`repository.owner.login`, falling back to `organization.login`), rather than from any authenticated, out-of-band context (e.g. a fixed per-endpoint secret). The event handlers that actually mutate state (e.g. `PushHandler`, `Repository.from_github_repo_name`) instead key off a different field in the same payload, `repository.full_name`. Because Shipit is designed to host multiple GitHub organizations, each with its own `webhook_secret` [1](#0-0) , an entity that legitimately owns the webhook secret for *one* configured organization can forge a payload whose `owner.login`/`organization.login` names their own org (so the signature check passes with their own secret) while `repository.full_name` names a *different* organization's/repository's stack, which is what the handler acts on.

### Finding Description
`verify_signature` computes the verification target from payload data before the signature has been validated: [2](#0-1) 

`repository_owner` is derived purely from request JSON, with no cryptographic binding: [3](#0-2) 

`verify_webhook_signature` then just checks the raw body's HMAC against whichever organization's `webhook_secret` was selected by that untrusted field: [4](#0-3) 

Once the signature is accepted, the actual event handlers dispatch to repositories/stacks using a *different* payload field, `repository.full_name`, not `repository.owner.login`: [5](#0-4) [6](#0-5) 

This is the same class of bug as the report: a value used to authenticate/authorize (`repository.owner.login`, used to choose the signing secret) is not the same value that is subsequently acted upon (`repository.full_name`, used to select the target `Stack`), and nothing forces them to agree. The equality that should hold but does not is:

`organization authenticated by verify_signature (repository.owner.login) == organization/repository actually written by the handler (repository.full_name)`

Concretely, Shipit supports hosting several GitHub organizations side by side, each with an independently configured `webhook_secret` (as shown by the `github:` config example with multiple orgs, and by test fixtures defining separate hooks/secrets per org) [1](#0-0) [7](#0-6) . An attacker who legitimately controls the webhook secret for org A (e.g. they administer their own GitHub org configured on the shared Shipit instance) can:

1. Take a real `push` (or `status`, `check_suite`, etc.) payload shape.
2. Set `repository.owner.login` (or `organization.login`) to `"org-A"` so `Shipit.github(organization: repository_owner)` resolves to their own app config.
3. Set `repository.full_name` to `"org-B/victim-repo"` (a different organization's stack that they do not control).
4. Sign the raw body with org A's `webhook_secret`.
5. POST to `/webhooks`.

`verify_signature` computes `repository_owner == "org-A"`, fetches org A's `GitHubApp`, and the HMAC matches because the attacker signed with org A's real secret — the check passes. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name(repository_name)` where `repository_name` is `payload.dig('repository', 'full_name')` = `"org-B/victim-repo"`, and triggers `stack.sync_github(expected_head_sha: params.after)` against org B's stacks with attacker-chosen `after` sha, even though org B never signed anything and the attacker has no legitimate relationship to org B's repository.

### Impact Explanation
This lets a party who is only trusted for organization A forge webhook events that are treated as authentic for organization B's stacks. Handlers such as `PushHandler` and `StatusHandler` operate directly on `Stack`/`Commit` records for the spoofed repository — `sync_github` can be driven with an attacker-chosen `expected_head_sha`, and (depending on which handler paths are reachable) forged commit statuses can be injected for arbitrary shas. Since Shipit gates deploys/merges on commit status and undeployed-commit bookkeeping, this crosses into unauthorized manipulation of another organization's deploy pipeline state, which lines up with the "unauthorized deploy/rollback/merge" and "authenticated read/write of stack state" impact classes called out in scope.

### Likelihood Explanation
Requires only that the attacker be a legitimate holder of the webhook secret for *any one* organization configured on a multi-tenant Shipit deployment — not a privileged Shipit account, not a `GITHUB_TOKEN`, not repository write access to the victim org. This is realistic for shared/hosted Shipit instances serving multiple GitHub organizations, which is an explicitly documented and supported configuration.

### Recommendation
Do not select the verification secret (or any authorization decision) from fields inside the unauthenticated JSON body. Either: (a) verify the signature against every configured organization's secret and require the `repository.full_name`'s organization to match the one whose secret validated, or (b) bind webhook endpoints to a single organization per secret/path so the secret used for verification is fixed independently of payload content, and (c) after verification, re-check that `repository.owner.login`/`organization.login` is consistent with `repository.full_name` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit with two orgs, `org-A` and `org-B`, each with distinct `webhook_secret`s (as in `config/secrets.development.shopify.yml`).
2. As an entity holding `org-A`'s webhook secret, craft a `push` payload: `{"ref": "refs/heads/master", "after": "<attacker-chosen-sha>", "repository": {"full_name": "org-B/victim-repo", "owner": {"login": "org-A"}}}`.
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-A-secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. Observe `WebhooksController#verify_signature` selects `org-A`'s `GitHubApp` (`repository_owner` == "org-A"), the signature check passes, and `PushHandler` subsequently calls `Repository.from_github_repo_name("org-B/victim-repo")` and enqueues `sync_github` on org B's stack with the attacker-chosen `after` sha — despite org B never having signed the request.     def verify_signature
```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
