### Title
Unhandled TypeError from missing/malformed input object crashes node during asset payment validation - (File: validation.js)

### Summary
`CVE-2021-45846` describes a crash in Slic3r's AMF parser caused by blindly accessing an attribute (`type`) on a metadata tag without first checking that it exists. The equivalent bug class in ocore is code that accesses a nested property of a payment-input element without first validating that the element is actually a non-empty object, which can be reached by an unprivileged unit poster.

### Finding Description
In `validatePayment()`, before validating the individual shape of each input element, the code only checks that `payload.inputs` is a non-empty array: [1](#0-0) 

For asset payments, `validatePayment()` then reads asset info and, still before any element-level structural check of `payload.inputs[0]`, directly dereferences a `.type` property on it: [2](#0-1) 

`isNonemptyArray()` (in `validation_utils.js`) only verifies that the value is an array with `length > 0`; it does not verify that the array's elements are objects, let alone that they contain a `type` field: [3](#0-2) 

Because of this, an attacker can post a unit containing an asset `payment` message whose `payload.inputs` array has `null` (or another non-object primitive) as its first element, e.g. `payload.inputs = [null]`. `isNonemptyArray(payload.inputs)` passes, `loadAssetWithListOfAttestedAuthors` proceeds, and then `payload.inputs[0].type` throws an uncaught `TypeError: Cannot read properties of null (reading 'type')`. Just like the AMF parser blindly reading a missing `type` attribute and crashing, this code blindly reads a `.type` property of an unchecked element.

The proper per-input structural checks (`isNonemptyObject(input)`, `hasFieldsExcept`, etc.) only happen later, inside `validatePaymentInputsAndOutputs`'s per-input `switch(type)` handling — but by then it is too late, because the crash already occurs earlier at line 2099 while determining `bIssue`.

### Impact Explanation
This code path runs inside an asynchronous DB callback (`storage.loadAssetWithListOfAttestedAuthors`) that is not wrapped in a try/catch. An uncaught `TypeError` thrown from inside a Node.js callback typically becomes an unhandled exception that crashes the node process (unless a global uncaught-exception handler swallows it, in which case the message is simply left unprocessed and validation state can also become inconsistent). Because unit validation is on the primary path every full node uses to accept/relay units, a single malformed unit that references an existing asset and puts a non-object as the first payment input can potentially crash any full node (or a subset of nodes running an unmodified version) that attempts to validate it. This does not require any special privilege — any user can post a unit; hence, this matches "node crash/DoS reachable from a single posted unit," analogous in root cause and severity class to the CVE's crash-from-missing-attribute bug.

### Likelihood Explanation
The trigger requires only: (1) a previously-defined, existing asset (any user's or the AA's own issued asset), and (2) a hand-crafted payment message referencing that asset where `payload.inputs[0]` is not an object (e.g. `null`). No signatures are checked before this point in the async flow relative to `type` access, since only high-level array-non-emptiness of `inputs`/`outputs` is validated earlier in `validate()`. This is straightforward for any peer capable of composing custom unit JSON (bypassing the standard wallet software that always creates well-formed inputs) and does not require witness or hub cooperation.

### Recommendation
Before dereferencing any property of `payload.inputs[0]` (or any input) in `validatePayment()`, validate that each element of `payload.inputs` is a non-empty object (e.g., `isNonemptyObject(payload.inputs[0])`) prior to reading `.type`. More generally, move (or duplicate) minimal per-element structural validation of `payload.inputs`/`payload.outputs` to occur immediately after the `isNonemptyArray` checks in `validatePayment`, before any element property access, so that malformed elements are rejected with `callback("bad input")` instead of throwing.

### Proof of Concept
1. Choose (or issue) any existing asset `A` for which `objAsset` will be loaded successfully by `storage.loadAssetWithListOfAttestedAuthors`.
2. Construct a unit with a `payment` message whose payload is:
```json
{
  "asset": "A_ASSET_HASH_44_CHARS_BASE64==",
  "inputs": [null],
  "outputs": [{"address": "SOME_VALID_ADDRESS", "amount": 1}]
}
```
3. `isNonemptyObject(payload)`, `isNonemptyArray(payload.inputs)`, and `isNonemptyArray(payload.outputs)` all pass since the array has one (non-object) element.
4. Post/relay this unit to a full node for validation.
5. When `validatePayment()` reaches `var bIssue = (payload.inputs[0].type === "issue");`, the node throws `TypeError: Cannot read properties of null (reading 'type')`, which is uncaught inside the async DB callback, crashing (or otherwise destabilizing) the validating node's process.

Note: I was not able to trace, within the available index, whether a global `process.on('uncaughtException')` handler exists elsewhere in the codebase that might catch this and merely log it instead of crashing the process outright; if such a handler exists, the impact would be reduced to validation-state corruption/DoS on that connection rather than a full process crash. This should be verified directly against the deployed error-handling wrapper (e.g., in `network.js` or the main process entry point) before finalizing severity.
