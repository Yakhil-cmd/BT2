Based on my investigation, I found a concrete analog to the report's bug class in the pox-5 L1-BTC-lockup path.

### Title
Missing minimum-confirmation-depth check lets a Bitcoin reorg credit `register-for-bond` with sats never durably locked - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 branch credits `sats-total` (and thereby a bond membership, signer voting weight, and STX unlock schedule) as soon as a caller supplies a Bitcoin block header and a merkle proof showing a P2WSH timelock output for that block [1](#0-0) . The per-output validation (`validate-l1-lockup`) only checks: the header parses, the unlock height is in the future, the output script/amount match the expected timelock script, the outpoint is not a duplicate, `verify-block-header` accepts the header/height pair, and the merkle proof (or single-tx shortcut) is valid [2](#0-1) . None of these checks require that the referenced Bitcoin block has accumulated any confirmations beyond itself — there is no comparison against the node's synced/buried burnchain tip, no minimum-depth parameter, and no analog to an `ETHBlockDelay`-style waiting period.

### Finding Description
This mirrors the external report's bug class: a bridge/lockup mechanism that credits a Bitcoin-side lock as soon as a single block including it is observed, without waiting for a safe confirmation depth, is vulnerable to a miner (or a well-resourced actor able to mount even a short selfish-mining/reorg attack) presenting a block that is later orphaned. In this codebase, `register-for-bond`'s L1 path takes a raw 80-byte header and height supplied directly by the caller [3](#0-2)  and, once `verify-block-header`, the merkle proof, and script/amount checks pass, immediately treats the sats as staked: it accumulates `sats-total`, sets `new-sbtc`/`old-sbtc` bookkeeping, and (per `register-for-bond`) proceeds to update bond membership and lock the staker's STX for a full stacking cycle [1](#0-0) . If the attacker (or a colluding miner) then reorgs the Bitcoin chain to drop or rewrite that block before it becomes buried, the referenced P2WSH output — and thus the underlying BTC "lock" — never durably exists on the canonical Bitcoin chain, yet the staker has already been credited sats-total, STX has been locked (or unlocked on the staker's terms), and signer/reward weight has been allocated based on it.

### Impact Explanation
This breaks the equality that L1-credited sats must correspond to BTC actually and durably locked on Bitcoin. A successful reorg after a single-block proof lets an attacker obtain bond membership, signer stacking weight, and reward-cycle credit for sats that were never permanently locked — this is "sats credited by an L1 proof that were never locked on Bitcoin," an in-scope Critical-tier impact class (unlocking/crediting value never actually committed, and double-counting a commitment that vanished from the canonical chain).

### Likelihood Explanation
I could not locate and fully inspect the implementation of `verify-block-header` within my remaining search budget (it appears solely referenced, not defined, in `pox-5.clar` in the indexed content I retrieved), so I cannot confirm with certainty whether it performs any difficulty/PoW-chain continuity check beyond hash format validation, or whether some confirmation-depth gate exists elsewhere in the calling stack (e.g., in `stacks-node`) that I did not locate. Based on the contract-level code I could inspect, no confirmation-depth parameter exists in the `validate-l1-lockup`/`verify-l1-lockups` path itself, and the header/height are attacker-supplied inputs rather than values read from the node's own synced burnchain view. This uncertainty should be resolved by inspecting `verify-block-header`'s definition directly, since the severity of this finding hinges on whether it enforces cumulative-work/burial requirements.

### Recommendation
Require a minimum number of confirmations (buried depth) on top of the referenced Bitcoin block before `register-for-bond` credits L1 sats — e.g., compare the lockup block's height against the node's own confirmed Bitcoin/burnchain tip height (via `get-burn-block-info?` or equivalent) and reject proofs referencing blocks that are not buried at least N (e.g., 6+) blocks deep, analogous to the recommended mitigation in the source finding.

### Proof of Concept
1. Miner/attacker constructs and mines a Bitcoin block containing the P2WSH timelock output required by `construct-lockup-output-script` for `staker`.
2. Immediately (before any further confirmations), attacker submits `register-for-bond` with that block's 80-byte header, the merkle proof (or the single-tx shortcut when it is the only tx), and the outpoint details, per the `validate-l1-lockup` checks at [4](#0-3) .
3. `register-for-bond` accepts this proof, locks the staker's STX, and grants bond membership / signer weight based on `sats-total` [1](#0-0) .
4. Attacker (or a colluding Bitcoin miner) reorgs the Bitcoin chain to orphan that block, e.g. via selfish mining, before the network is deep enough to consider it final.
5. The claimed BTC lockup never durably exists, yet the Stacks-side stacking weight/lock granted in step 3 persists — sats were credited without ever being locked on Bitcoin.
