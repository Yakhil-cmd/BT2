### Title
Fee-on-transfer ERC20 tokens desynchronize XCM holding-register credit from real custody in `ERC20Transactor` - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` credit the XCM `AssetsInHolding` register with the full requested `amount` whenever the underlying ERC20 `transfer` call returns `true`, without verifying that the `TransfersCheckingAccount` balance actually changed by `amount`. Any `pallet-revive` contract implementing fee-on-transfer/deflationary semantics (legal, attacker-controlled contract logic) can return `true` while moving less than `amount`, causing the XCM VM to believe it holds more real value than actually exists in the checking account.

### Finding Description
`ERC20Matcher` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:159-160`) matches *any* `Location` of the shape `(0, [AccountKey20{key}])` via `IsLocalAccountKey20`/`AccountKey20ToH160` [1](#0-0) . There is no allowlist — any attacker-deployed `pallet-revive` contract address is automatically a valid XCM fungible asset id. `ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` tuple [2](#0-1) , so it is reachable from any signed user through `pallet-xcm::execute` (`WithdrawAsset`/`DepositAsset` instructions) with no privileged role required.

In `withdraw_asset_with_surplus`, the code calls `IERC20::transferCall{to: checking_address, value: amount}` on the attacker's own contract, then only checks `did_revert()` and the boolean ABI return value; if `true`, it unconditionally constructs `Erc20Credit(amount)` — the *requested* amount, not the amount actually credited to the checking account: [3](#0-2) 

The symmetric `deposit_asset_with_surplus` has the identical pattern — it transfers from the checking account to the beneficiary and trusts the boolean return, not an actual balance delta: [4](#0-3) 

This is the direct structural analog of the reported Allo `_fundPool` bug: an internal accounting variable (`poolAmount` there; the XCM `AssetsInHolding` credit here) is set to the *requested* transfer amount rather than the *measured* balance delta, while the underlying token's `transfer` can silently deliver less. Nothing in FRAME's own `fungible`/`fungibles` traits has this flaw (their `transfer`/`do_transfer` implementations return the *actual* credited amount computed from internal ledger arithmetic, e.g. `substrate/frame/assets/src/functions.rs:741-747`), because those tokens' storage is directly owned and computed by the pallet. The `ERC20Transactor` breaks this invariant specifically because it delegates trust to an external, attacker-controlled contract's return value instead of measuring its own effect.

### Impact Explanation
Because the XCM holding register believes it possesses `amount` while the checking account (a shared PalletId-derived account, `ERC20TransfersCheckingAccount`, used by *all* ERC20 XCM operations) only actually received `amount - fee`, subsequent instructions in the same or later XCM programs (`DepositAsset`, `InitiateReserveWithdraw`, `InitiateTeleport`, or any downstream logic treating this credited amount as backing, e.g. cross-chain reserve transfers or liquidity operations) operate on inflated, unbacked value. This can manifest as: (a) the checking account eventually running out of real balance to satisfy legitimate deposit calls for a shared malicious-asset id used by other unrelated interactions, causing failed transfers/griefing of the shared checking account's accounting, or (b) if an attacker can chain this fake-inflated credit into a swap/deposit against real backing assets (e.g., via `pallet-asset-conversion` or further XCM hops), realize value they did not actually deposit. This is a Medium-severity accounting-integrity break in cross-chain custody bookkeeping, matching the severity class of the original report.

### Likelihood Explanation
Deploying a custom fee-on-transfer `pallet-revive` contract requires only standard, unprivileged contract deployment (evm-compatible `instantiate`), a capability available to any Asset Hub user. Invoking it through XCM requires only `pallet_xcm::execute` with a `WithdrawAsset`/`DepositAsset` referencing the attacker's own `AccountKey20` location — again unprivileged and requires no governance, no malicious validator/collator, and no forged inherents. The `ERC20Matcher`'s unconditional acceptance of any `AccountKey20` location makes this trivially reachable.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of the relevant account (checking account or beneficiary) before and after the `bare_call`, and use that measured delta — not the requested `amount` — to construct the `AssetsInHolding`/`Erc20Credit`, or to determine surplus. Alternatively, explicitly document and restrict this transactor to standards-compliant, allowlisted ERC20 contracts, and reject/verify with a `balanceOf` call before and after (analogous to the Allo fix's before/after balance check pattern), i.e.:
```rust
let balance_before = balance_of(checking_address);
// ... perform transferCall ...
let balance_after = balance_of(checking_address);
let actual = balance_after.saturating_sub(balance_before);
// credit AssetsInHolding with `actual`, not `amount`
```

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}
