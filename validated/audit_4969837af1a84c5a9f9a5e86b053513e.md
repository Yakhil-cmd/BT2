### Title
A malicious/uncooperative counterparty in a shared AA payment can permanently freeze all parties' funds via `spender_attested` asset attestation gating - ([File: validation.js])

### Summary
When an Autonomous Agent (AA) distributes shared funds to multiple parties in a single `payment` message (as is required by the AA response format, since messages are merged per-asset), and the payment is denominated in a `spender_attested` asset, `validation.js` requires **every** output address of the message to be attested before the unit — and therefore the *entire* multi-party payment — is considered valid. A malicious or simply uncooperative party who is never attested can indefinitely block validation of the shared payment, freezing the funds owed to the honest counterparty as well as their own.

### Finding Description
`validatePaymentInputsAndOutputs()` enforces, for `spender_attested` assets, that *all* recipients in the outputs array are attested, not just the sender/issuer: [1](#0-0) 

```js
async.series([
    function(cb){
        if (!objAsset.spender_attested)
            return cb();
        storage.filterAttestedAddresses(
            conn, objAsset, objValidationState.last_ball_mci, arrOutputAddresses, 
            function(arrAttestedOutputAddresses){
                if (arrAttestedOutputAddresses.length !== arrOutputAddresses.length)
                    return cb("some output addresses are not attested");
                cb();
            }
        );
    },
    ...
```

Because `arrOutputAddresses` is computed over *all* outputs of the message (`validation.js` line ~2193), a single unattested address anywhere in the outputs makes the whole message — and thus the whole unit — invalid.

On the AA side, when an AA needs to pay out to more than one address in the same asset (e.g. a payment channel closing and paying both parties, an order-book withdrawal, or an escrow/arbiter-style settlement AA), the composer merges all outputs for the same asset into a single `payment` message: [2](#0-1) 

This merging is mandatory from `pemCurvesFixMci` onward, so an AA author cannot separate the two parties' payouts into independent units to isolate one party's failure from the other's. Templates such as `payment_channels.oscript` and `order_book_exchange.oscript` show exactly this "settle and pay two parties in one payment message" pattern: [3](#0-2) 

If such an AA (or an escrow/arbiter contract) is built on top of a `spender_attested` asset, the response `sendUnit()` fails validation as soon as one of the recipient addresses is not attested; the AA's `bounce()` path fires and no funds move at all: [4](#0-3) 

Since attestation is an external, discretionary act (a KYC-style attestor must publish an `attestation` message for the address, or the address owner must complete some off-chain requirement), a party can simply refuse or fail to become attested, permanently preventing the AA from ever assembling a valid combined payout. This mirrors the reported Stream.sol bug class: bundling a transfer to a potentially adversarial party together with a transfer to an honest party in the same atomic operation, letting the adversary hold the honest party's funds hostage.

### Impact Explanation
Any AA-based multi-party payout (payment channel closure, order-book settlement, arbiter/escrow-like AA) that distributes a `spender_attested` asset to more than one address in a single payment message can be griefed: the uncooperative party's failure to be attested blocks the message for everyone, freezing the AA's balance for both parties indefinitely (AA fund freezing). This is a Medium/High severity fund-freezing condition depending on asset design and value locked.

### Likelihood Explanation
Requires an AA to use a `spender_attested` asset for multi-recipient payouts and requires one recipient to withhold their attestation. This is fully reachable by an ordinary AA trigger sender/asset issuer combination — no privileged or node-level access is needed; the attacker only needs to be one of the parties owed funds by the AA and simply never obtain attestation.

### Recommendation
- For AAs that must pay multiple independent parties, avoid combining outputs to different, mutually-untrusted parties into a single payment message when the asset is `spender_attested`.
- Consider changing `validatePaymentInputsAndOutputs()` to allow attested-only aggregation, or provide a mechanism for an AA to pay attested and unattested recipients via separate response units (currently prevented by mandatory per-asset message merging in `aa_composer.js`'s `mergeMessagesAndOutputs`), so that one party's missing attestation cannot block payouts to already-attested parties in the same settlement.

### Proof of Concept
1. Issuer defines a `spender_attested` asset `X` with attestor `Att`.
2. An AA (e.g., a payment-channel/escrow AA analogous to `payment_channels.oscript`) accumulates balances of `X` on behalf of partiers A and B.
3. Settlement logic composes a single `payment` message paying both A and B out of the shared AA balance (as the composer always merges same-asset outputs, per `aa_composer.js` `mergeMessagesAndOutputs`).
4. Party B refuses to obtain attestation from `Att` for asset `X`.
5. When the AA tries to send the settlement unit, `validatePaymentInputsAndOutputs()` rejects it because B's output address is not attested (`validation.js` line 2637-2638), causing the whole unit — including A's legitimate payout — to bounce.
6. Because messages cannot be split per-recipient (mandatory merge), A's funds remain permanently locked in the AA as long as B withholds attestation.

	function mergeMessagesAndOutputs(messages) {
		const arrMergedMessages = [];
		const assocMergedMessagesByAsset = Object.create(null);
		for (let message of messages) {
			if (message.app !== 'payment') {
				arrMergedMessages.push(message);
				continue;
			}
			const payload = message.payload;
			const asset = payload.asset || 'base';
			let objMergedMessage = assocMergedMessagesByAsset[asset];
			if (!objMergedMessage) {
				objMergedMessage = { app: 'payment', payload: { outputs: [] } };
				if (payload.asset)
					objMergedMessage.payload.asset = payload.asset;
				assocMergedMessagesByAsset[asset] = objMergedMessage;
				arrMergedMessages.push(objMergedMessage);
			}
			for (let output of payload.outputs) {
				if (output.amount === undefined) { // send-all output, don't merge with anything
					objMergedMessage.payload.outputs.push(output);
					continue;
				}
				const existing_output = objMergedMessage.payload.outputs.find(o => o.address === output.address && o.amount !== undefined);
				if (existing_output)
					existing_output.amount += output.amount;
				else
					objMergedMessage.payload.outputs.push(output);
			}
		}
		return arrMergedMessages;
	}
