### Title
Unfiltered pull-request-label-derived environment variable keys (e.g. `RUBYLIB`) reach `PTY.spawn` during `bundle install` - (File: app/models/shipit/review_stack.rb, lib/shipit/task_commands.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` turns every pull-request label name into an environment-variable *key* (uppercased, value fixed to `"true"`) and merges it into the stack env with no key allowlist. This flows unfiltered through `TaskCommands#env`/`DeployCommands#env` into `Command#unbundled_env`, which is passed directly to `PTY.spawn` when executing deploy-spec steps such as `bundle install`. Unlike the explicit API-submitted task env (which is whitelisted via `EnvironmentVariables#permit`), label-derived keys have no such filter.

### Finding Description
The broken binding is:

`Command#unbundled_env.keys` for a review-stack task step SHOULD equal `BASE_ENV.keys ∪ {allowlisted deploy/task variable names}`, but in practice it equals `BASE_ENV.keys ∪ {any uppercased PR label name the fork PR author chooses}`.

Path:
- `ReviewStack#env` builds `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" }` and merges it into the stack's env with no key restriction [1](#0-0) .
- Labels are persisted straight from the webhook body by `LabelCapturingHandler#capture_labels`, with only a `String` type check, no character/key restriction [2](#0-1) .
- `TaskCommands#env` merges `@stack.env` in directly, with no `filter_envs`/`EnvironmentVariables.permit` step applied to it [3](#0-2) . `DeployCommands#env` inherits the same unfiltered merge [4](#0-3) .
- `Command#unbundled_env` merges `@env` (which includes the label-derived keys) on top of `BASE_ENV` with no key allowlist: `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` [5](#0-4) .
- `Command#start` passes this hash directly as the environment to `PTY.spawn` [6](#0-5) .

An existing test already demonstrates the unfiltered pass-through of arbitrary label names into `env`: [7](#0-6) .

By contrast, the *explicit* API-submitted env (task/deploy `env` params) is filtered through `EnvironmentVariables#permit` against `deploy_variables`/`variables` before being merged: `TaskDefinition#filter_envs`, `DeploySpec#filter_deploy_envs`/`#filter_rollback_envs` [8](#0-7) [9](#0-8) [10](#0-9) . This allowlist mechanism exists precisely to prevent dangerous variable names, but it is never applied to the label-derived portion of `stack.env`, which is architecturally treated as trusted.

Important caveat that limits severity: the *value* assigned to any label-derived key is hardcoded to the literal string `"true"` (`labels[label_name.upcase] = "true"`), not an attacker-chosen path. So an attacker can set `RUBYLIB=true` in the `bundle install` subprocess's environment, but cannot directly supply an arbitrary directory path via the label mechanism alone. For this to translate into `require` hijacking a Ruby `LOAD_PATH` entry of a bare relative directory literally named `true` would need to exist under the task's working directory (`chdir`) containing a file that shadows a library required during `bundle install`. Since the attacker (fork PR author) also controls the checked-out repository content for their own review stack, they can plant such a directory/file in their fork. This combination is plausible but was not demonstrated live in this audit — it depends on Ruby/Bundler's actual `require` resolution order treating `RUBYLIB=true` as a relative-path entry, which was not independently verified against a live ruby/bundler process here.

### Impact Explanation
If exploitable to completion, the attacker gets code execution during the `bundle install` step run by `Command#start`/`PTY.spawn` on the Shipit deploy host, for the specific review stack corresponding to their own fork PR (i.e., a repository/stack they already control via the fork branch that gets checked out and executed). This does not cross tenant boundaries into other repositories' stacks since `ReviewStack#env` only reads that stack's own `pull_request.labels`. This matches the "Critical - RCE on deploy host via Command/PTY.spawn" category, but scoped to the attacker's own review-stack task execution, which they already control the working-directory contents of.

### Likelihood Explanation
Preconditions: `review_stacks_enabled` for the target repository (an opt-in feature), the deploy spec must have a step such as `bundle install`, and the attacker must be able to add a label named `rubylib` (case-insensitive) to their own PR — the audit's stated threat model grants this, though on real GitHub, adding labels typically requires triage/write permission on the base repository, not just being the PR author; this is a meaningful real-world friction not covered by the audit's assumed attacker capability. Additionally, achieving load-path hijacking (not just setting `RUBYLIB=true`) requires the attacker to also engineer a `true/`-named directory with a colliding library file in their fork's checkout, which was not verified to actually intercept a `bundle install` require in this codebase/version of Ruby/Bundler.

### Recommendation
Apply the same `EnvironmentVariables#permit` allowlist mechanism (or a dedicated denylist of dangerous keys such as `RUBYLIB`, `RUBYOPT`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `GEM_HOME`, `PATH`, `GIT_SSH_COMMAND`, etc.) to the label-derived portion of `ReviewStack#env` before it is merged into task/deploy commands, or namespace label-derived variables under a fixed prefix (e.g. `LABEL_<NAME>`) so they can never collide with security-sensitive interpreter/toolchain environment variable names.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_test.rb (extend existing test)
test "#env does not leak dangerous interpreter env var keys from PR labels into Command" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["rubylib"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  command = Shipit::Command.new("bundle install", env: env, chdir: ".")

  # Binding under test: unbundled_env should never carry attacker-controlled
  # interpreter-hijacking keys derived from PR labels.
  refute_includes command.unbundled_env.keys, "RUBYLIB",
    "PR-label-derived RUBYLIB key reached the bundle install subprocess environment"
end
```
This assertion currently fails (i.e., `RUBYLIB` key is present with value `"true"`), confirming the unfiltered key propagation described above; full RCE via `require` hijacking would require an additional, unverified step of shadowing a library in a `true/`-named directory in the attacker's fork checkout.
