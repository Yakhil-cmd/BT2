### Title
Cross-repository commit-status forgery bypasses `MergeRequest#all_status_checks_passed?` — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by SHA (`Commit.where(sha: params.sha)`), with no check that the payload's repository matches the `Commit`'s own stack/repo. `MergeRequest#all_status_checks_passed?` then reads that (potentially poisoned) `Commit`'s local `statuses`/`check_runs` without ever comparing them to `stack.github_repo_name`, allowing a status emitted by an unrelated repository to satisfy a victim stack's merge queue.

### Finding Description
The broken binding is:
`status.source_repository (the repo whose webhook produced the Status row) == merge_request.stack.github_repo_name`

This equality is never checked anywhere in the path.

- `StatusHandler#process` finds commits solely by `sha`, across **all stacks**, and unconditionally attaches the incoming status: [1](#0-0) 

- `Commit#create_status_from_github!` writes the status using `stack_id` (the *found commit's own stack*, not the webhook payload's repository), then calls `add_status`: [2](#0-1) 

- `Commit#add_status` triggers `stack.schedule_merges` as soon as the aggregated `status` becomes `pending` or `success`: [3](#0-2) 

- `MergeRequest#all_status_checks_passed?` only inspects the local `head` commit's own `statuses_and_check_runs`; it never consults `stack.github_repo_name` or any repository-identity check: [4](#0-3) 

- Signature verification (`WebhooksController#verify_signature`) only authenticates that the payload was signed by *some* org's webhook secret — the org named in `payload['repository']['owner']['login']` — it does nothing to bind that org/repo to the commit rows the handler will subsequently mutate: [5](#0-4) 

Exploit flow: an attacker who is a member of (or controls a repo within) any GitHub organization/app already onboarded to the same Shipit instance can create/push a commit in their own repository whose SHA matches the SHA of a victim's PR HEAD commit (trivial for public commits, since git SHAs are pure content hashes — copying the identical tree/parents/author/committer/timestamps/message into any repo reproduces the same SHA). Any real (or attacker-triggered) CI run on that commit in the attacker's own repo causes GitHub to POST a legitimately-signed `status` webhook to the shared Shipit host. `StatusHandler#process` matches the SHA against `Commit.where(sha: ...)`, finds the victim's `Commit` row (belonging to the victim's stack), and writes a `success` status onto it — with no cross-check that the webhook's repository is the victim's `github_repo_name`. This flips the victim commit's aggregated `status`, `Commit#add_status` calls `stack.schedule_merges`, `ProcessMergeRequestsJob` runs, and `MergeRequest#all_status_checks_passed?` reports true using the poisoned status, queuing/executing a merge based on CI that never ran against the victim's repository.

None of the existing guards close this gap: `verify_signature` authenticates an organization, not a repository-to-commit binding; the `Commit` lookup and `Status`/`CheckRun` write path never re-derive or compare `github_repo_name`; `StatusChecker`/`Status::Group` (used by `all_status_checks_passed?`) work purely off the `Commit`'s attached status records with no repo-identity check.

### Impact Explanation
An attacker controlling any onboarded repository can forge a passing CI signal for an arbitrary victim `Stack`'s pull request, as long as they can reproduce (or predict) the SHA of the victim's HEAD commit, causing `MergeRequest#merge!` to execute against the victim repository via `stack.github_api.merge_pull_request` — an unauthorized merge performed by Shipit's GitHub App credentials against a repository the attacker does not control. This is a payload for one repository mutating another repository's stack/commit/merge state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The blast radius spans every stack/commit hosted on the same multi-tenant Shipit instance, since the commit lookup is entirely global and unscoped by repository.

### Likelihood Explanation
Preconditions: (1) the victim stack has `merge_queue_enabled` with a pending `MergeRequest` whose head SHA is known/reproducible by the attacker (trivial for public commits, since GitHub SHAs are deterministic content hashes and public commit content is visible); (2) the attacker has push/webhook access to any repository under an organization already onboarded to the same shared Shipit instance so that a genuinely GitHub-signed `status` webhook for their own repo reaches the host. No Shipit secrets, sessions, or API tokens are required — only ordinary access to a GitHub repository whose org has an app/webhook already pointed at the Shipit host, which is a realistic configuration for any multi-tenant Shipit deployment. This is fully repeatable against any stack whose commit SHAs can be reproduced by the attacker.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and the analogous `check_suite`/other status-derived handlers) by the webhook payload's `repository.full_name`/owner, matching it against `commit.stack.github_repo_name`, and reject/ignore statuses whose originating repository does not match the stack owning the matched `Commit`. Additionally, `MergeRequest#all_status_checks_passed?` (and `any_status_checks_failed?`/`any_status_checks_missing?`) should not trust status rows that cannot be attributed to `stack.github_repo_name`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks, `victim_stack` (repo `victim-org/victim-repo`) and `attacker_stack`/no stack at all for `attacker-org/attacker-repo`.
2. Create a `MergeRequest` on `victim_stack` with `head` commit `sha = "deadbeef..."` and no `Status` rows (so `all_status_checks_passed?` is false).
3. POST to `/webhooks` with `X-Github-Event: status`, a valid signature for `attacker-org` (stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return true, simulating a legitimately signed attacker-repo event), and a body `{ "sha" => "deadbeef...", "state" => "success", "repository" => { "owner" => { "login" => "attacker-org" } } }`.
4. Assert: `merge_request.reload.head.statuses.count` increased by 1, and `merge_request.all_status_checks_passed?` is now `true`.
5. Assert: no status was ever posted with `repository.owner.login == "victim-org"`, proving the merge readiness was derived purely from the attacker-signed webhook — demonstrating `merge_request.stack.github_repo_name` ("victim-org/victim-repo") was never compared to the signing repository ("attacker-org/attacker-repo").

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
