### Title
Data-feed key delimiter confusion causes uncaught `RangeError` on double decode - (File: string_utils.js, data_feeds.js)

### Summary
`decodeLexicographicToDouble()` in `string_utils.js` unconditionally calls `buf.readDoubleBE(0)` on a `Buffer` built from a hex substring extracted from a `\n`-delimited storage key, without ever checking that the buffer is exactly 8 bytes long [1](#0-0) . The hex value is obtained by splitting the on-disk data-feed key on the `\n` character and taking a fixed positional field [2](#0-1) . Because a `data_feed` message's `feed_name` (posted by any unit author) is used verbatim as one of the `\n`-joined segments of that same key when the unit is written to the key-value store [3](#0-2) , an attacker who includes a literal `\n` character inside `feed_name` (or inside a string feed value) shifts the split-array indices used later by `getValueFromDataFeedKey()`/`getMciFromDataFeedKey()`, causing a field of unexpected length to be passed to `decodeLexicographicToDouble`, which then throws a `RangeError` instead of gracefully failing.

### Finding Description
The class of bug in CVE-2016-7520 is a length-unchecked read of attacker-supplied bytes at a fixed/derived offset in a parser that assumes a well-formed record structure. The ocore analog is the composite key format used for data feeds: `df\n<address>\n<feed_name>\n<type>\n<value>\n<strReversedMci>` (and `dfv\n<address>\n<feed_name>\n<strReversedMci>`), built with plain string concatenation and `\n` as the field delimiter [4](#0-3) . On read-back, the key is split by `\n` and specific positional indices are trusted to contain the type and value fields [2](#0-1) . There is no validation anywhere in the reviewed data-feed write/read path that rejects `\n` characters inside `feed_name` or inside string data-feed values before they are concatenated into the key. If `feed_name` (fully attacker-controlled by any unit author posting a `data_feed` message) contains an embedded `\n`, the number and boundaries of fields recovered by `key.split('\n')` no longer match what the writer intended, so `m[3]` (expected type marker `'n'`/`'s'`) and `m[4]` (expected 16-hex-char lexicographic double) can end up containing attacker-chosen substrings of arbitrary length. When such a corrupted "value" reaches `decodeLexicographicToDouble`, `Buffer.from(hex, 'hex')` produces a buffer that is not the expected 8 bytes, and the unconditional `buf.readDoubleBE(0)` call throws `RangeError: Attempt to access memory outside buffer bounds` (Node's guarded analog of an out-of-bounds heap read) rather than returning an error result [5](#0-4) .

### Impact Explanation
`readDataFeedByAddress`/`dataFeedByAddressExists` invoke this decode path while iterating a `kvstore` read stream inside the `data_feed()` oscript/AA function used during main-chain stabilization and AA trigger evaluation [6](#0-5) [7](#0-6) . An uncaught exception thrown from inside a `kvstore` stream `'data'` handler is not caught by the surrounding `try/catch` in the formula evaluator (which only guards synchronous evaluate calls), so it propagates as an unhandled exception in the Node.js event loop and can crash the full node process. Because `data_feed()` reads are triggered by ordinary AA evaluation and main-chain stability processing that every full node performs, this can stop a node from confirming/evaluating new units that reference the poisoned data feed — matching the "network unable to confirm new units" impact bucket.

### Likelihood Explanation
Any unpermissioned unit author can post a `data_feed` app message and choose an arbitrary `feed_name` string (and arbitrary string feed values), which is the entire attack surface — no privileged position, hub role, or malicious peer is required. The remaining uncertainty is whether `validateMessages`/`validateInlinePayload` (not located in the reviewed portion of `validation.js`) already rejects `\n` characters in `feed_name`/data-feed values before they reach storage; if such a check exists, this specific analog is mitigated. I was unable to locate the `data_feed` app case inside `validation.js` in the available index to confirm or rule this out, so this should be verified before treating the finding as fully confirmed.

### Recommendation
- In `string_utils.js`, make `decodeLexicographicToDouble` defensive: verify `buf.length === 8` before calling `readDoubleBE`, and throw/return a clear validation error rather than letting a `RangeError` propagate uncaught.
- Wrap the `kvstore` stream `'data'` handlers in `data_feeds.js` (`dataFeedByAddressExists`, `readDataFeedByAddress`) in `try/catch` so a malformed key cannot crash the process; convert failures into `stream.destroy()` + `handleResult`/error propagation.
- Explicitly forbid the `\n` delimiter (and any other byte used as a field separator in composite keys) in `feed_name` and in string `data_feed` values during unit validation, so the on-disk key format's field boundaries can never be manipulated by unit content.

### Proof of Concept
1. Craft and post a unit with a `data_feed` message where `payload = { "a\nb": "1" }` (i.e., `feed_name` contains an embedded `\n`).
2. Once the unit stabilizes, `main_chain.js`'s `addDataFeeds` writes keys such as `df\n<address>\na\nb\ns\n1\n<strMci>` — one extra `\n`-separated field compared to what the reader expects [8](#0-7) .
3. Any subsequent oscript/AA call to `data_feed(...)` for an oracle/feed-name pattern that iterates this key range causes `getValueFromDataFeedKey`/`decodeLexicographicToDouble` to operate on a misaligned field, producing a non-8-byte buffer and throwing `RangeError` inside the `kvstore` read-stream callback [1](#0-0) , which is unhandled and can terminate the node process.

function decodeLexicographicToDouble(hex){
	var buf = Buffer.from(hex, 'hex');
	if (buf[0] & 0x80) // first bit set: positive
		buf[0] ^= 0x80; // flip the sign bit
	else
		for (var i=0; i<buf.length; i++)
			buf[i] ^= 0xff; // flip the sign bit and reverse the ordering
	var float = buf.readDoubleBE(0);
	if (float === -0)
		float = 0;
	return float;
}
