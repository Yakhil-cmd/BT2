## Verdict

Confirmed vulnerability found. The bug-class analog (a value trusted for one purpose being substituted with a different, attacker-controlled value used for the actual write) maps cleanly onto how `WebhooksController` selects which GitHub App/organization's secret to use for signature verification versus which repository the resulting event handlers actually act on.

### Title
Webhook signature verification is scoped to `repository.owner.login`/`organization.login` while event handlers act on `repository.full_name` — cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the GitHub App (and therefore the `webhook_secret` used for HMAC verification) from `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 

The actual event handlers, however, resolve which `Repository`/`Stack` to write to using a *different* field entirely: `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `Handler#stacks`. [3](#0-2) 

`verify_webhook_signature` short-circuits to `true` whenever the selected app has no configured `webhook_secret`: [4](#0-3) 

The equality that should hold is: **organization authenticated by the signature check == organization owning the repository actually written to**. This is broken because the two lookups read independent, attacker-controlled JSON fields (`repository.owner.login` vs `repository.full_name`) from the *same unauthenticated request body*. An attacker who knows (or exploits the absence of) the `webhook_secret` for **any one** organization configured in the Shipit instance (documentation and secrets templates explicitly show `webhook_secret` as optional/`nil`) can craft a payload where `repository.owner.login` names that org (satisfying/bypassing signature verification) while `repository.full_name` names an entirely different, unrelated repository/stack hosted by another organization in the same instance. [5](#0-4) 

Once past `verify_signature`, `create` re-parses the same raw body and dispatches to handlers keyed only by event type, with no re-check that the acted-upon repository belongs to the organization that was authenticated: [6](#0-5) 

The `status` handler is a concrete, high-impact instance: it looks up commits purely `Commit.where(sha: params.sha)` (no stack/org scoping at all) and creates a `Status` on any matching commit across the entire instance: [7](#0-6) [8](#0-7) 

That status is then used by `MergeRequest#all_status_checks_passed?` / `ProcessMergeRequestsJob` to decide whether a pending PR is auto-merged: [9](#0-8) [10](#0-9) 

The `push` handler similarly triggers `GithubSyncJob` for any stack whose branch matches, and other handlers touch statuses/check-runs, all without validating that the org used for signature selection matches the repository actually referenced in the payload. [11](#0-10) 

### Impact Explanation
An attacker who has (or can trigger absence of) a valid webhook secret for *any single organization* configured on the Shipit instance can forge `status` events that mark arbitrary commits (identified only by SHA, guessable/known from public GitHub history) as `success` for *any other* stack in the instance — enabling `ProcessMergeRequestsJob` to auto-merge a pull request whose real CI never passed. This is an unauthorized merge, matching the Critical-impact criterion ("unauthorized deploy, rollback, or merge"). It can also be used to forge `push` events that force `GithubSyncJob` re-syncs on victim stacks, or inject fabricated commit/check statuses across organizations that the attacker has no legitimate relationship with.

### Likelihood Explanation
Exploitability requires: (1) the Shipit instance to host multiple GitHub organizations (an explicitly documented, supported configuration — "Using Multiple Github Applications" — with `docs/setup.md` and `config/secrets.development.shopify.yml` both showing `webhook_secret` as an optional/nullable field), and (2) knowledge of, or absence of, the webhook secret for at least one of those organizations. Because `webhook_secret` is optional per-org and the verification silently passes when unset, a misconfigured or intentionally-unsecured low-value organization becomes a skeleton key for forging events against every other organization/stack hosted by the same Shipit deployment. No GitHub session, `ApiClient` token, or repository write access is needed — only crafting an HTTP POST with a chosen JSON body.

### Recommendation
Bind signature verification and event dispatch to the *same* repository/organization value. Concretely: derive `repository_owner` for app selection from the same field the handlers use (`repository.full_name`'s owner segment), and additionally have each handler re-validate that the resolved `Repository`'s owner matches the organization whose secret was used to verify the signature before processing the payload. Do not allow signature verification to pass silently (`return true unless webhook_secret`) for organizations that also host stacks reachable by cross-referencing `repository.full_name` from a different org's payload; at minimum, require secrets to be configured for every org, or explicitly reject payloads where `repository.owner.login` disagrees with the owner segment of `repository.full_name`.

### Proof of Concept
1. Configure/observe a Shipit instance with two organizations, `org-a` (no `webhook_secret` set, or secret known to attacker) and `org-b` (victim, hosting stack `org-b/victim-repo`).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything   # irrelevant, org-a has no secret

{
  "sha": "<head sha of an open PR on org-b/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. `verify_signature` computes `repository_owner = "org-a"`, fetches `Shipit.github(organization: "org-a")`, and `verify_webhook_signature` returns `true` unconditionally because `org-a`'s `webhook_secret` is blank.
4. `StatusHandler#process` matches `Commit.where(sha: ...)` for the victim commit (belonging to `org-b`'s stack) and creates a `success` `Status` on it, independent of the `org-a` app used for verification.
5. `ProcessMergeRequestsJob` subsequently observes `all_status_checks_passed?` as true and merges the pull request via `stack.github_api.merge_pull_request`, an unauthorized merge triggered without ever authenticating against `org-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
