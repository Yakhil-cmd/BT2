### Title
Webhook signature scoped to `repository.owner.login` while all handlers act on `repository.full_name` — cross-repository status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate an inbound webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). Every event handler, however, determines the *target* repository/stack independently, using `payload.dig('repository', 'full_name')` (in `Handler#repository_name`) or, for the `status` event, no repository scoping at all (`Commit.where(sha: params.sha)`). Because HMAC verification only proves that "whoever holds organization X's `webhook_secret` produced this exact JSON body," and does not enforce that `owner.login` and `full_name` refer to the same repository, an attacker who legitimately controls the webhook secret for one configured GitHub organization/app on a multi-tenant Shipit instance can forge a payload whose `owner.login` matches their own org (satisfying signature verification) while `full_name` / `sha` reference a completely different, unauthorized stack or commit.

### Finding Description [1](#0-0) 
`verify_signature` fetches the app config via `Shipit.github(organization: repository_owner)` and verifies `X-Hub-Signature` against the raw body using that organization's `webhook_secret` — but `repository_owner` is read from a single JSON field (`repository.owner.login`) inside the very body being authenticated. [2](#0-1) 
`Handler#repository_name` (used by `PushHandler`, `PullRequest::*Handler`s) resolves the actually-affected repository from a *different* field, `repository.full_name`, with no cross-check that it is consistent with `repository.owner.login`. [3](#0-2) 
`StatusHandler#process` is worse: it does not consult the repository at all. It looks up `Commit.where(sha: params.sha)` globally across the entire database and calls `commit.create_status_from_github!(params)`, meaning any commit sha in any stack can be targeted merely by knowing it, independent of which organization's key signed the request. [4](#0-3) 
Shipit officially supports multiple GitHub organizations configured under one instance (`github_app_config`/`github_organizations`), each with its own `webhook_secret`, as documented in `config/secrets.development.shopify.yml` and `docs/setup.md`. An entity that legitimately administers/owns one configured org (and therefore knows or can derive that org's `webhook_secret` — e.g., because they created the GitHub App installation for their own org) is an "unprivileged attacker" with respect to any *other* org/repo hosted on the same Shipit instance, yet the code lets them pass `verify_signature` using their own org's key while acting on another org's data.

This is the same class of bug as the reported Aave issue: two values that are supposed to move in lock-step (the org used to authenticate vs. the org/repo the code actually operates on) are computed from independently-controlled inputs instead of being cryptographically bound together, so the "authenticated" side and the "acted-upon" side can diverge.

### Impact Explanation
Exploiting `StatusHandler` lets the attacker inject arbitrary/forged commit statuses (`state`, `context`, `target_url`, `description`) for any commit `sha` in the shared Shipit instance, without ever having credentials for the victim's organization/repo. This directly feeds `Commit#deployable?`/`required_statuses` gating logic (`app/models/shipit/commit.rb` `deployable?`) and merge-queue gating (`MergeRequest::StatusChecker`), which are used to decide whether a commit may be deployed or a pull request merged. A forged "success" status can therefore enable an **unauthorized deploy or merge** on a stack the attacker does not control — matching the report's "Critical" impact bucket. `PushHandler`/`PullRequest` handlers additionally let a cross-org attacker trigger `GithubSyncJob`/review-stack creation on stacks they do not own by supplying a crafted `full_name`, which is at minimum an unauthorized-write/DoS vector against foreign stacks.

### Likelihood Explanation
Exploitability is fully gated on the deployment being multi-tenant (multiple orgs configured under `secrets.github`), which is a documented, supported configuration rather than a misconfiguration. Given that, no privileged Shipit session, `ApiClient` token, or GitHub write access to the *victim* repository is required — only knowledge of a webhook secret for *some* org hosted on the same instance, which that org's own administrators legitimately possess. This is a believable, low-effort attack path when Shipit is shared across mutually-untrusted teams/orgs, which is exactly the scenario the multi-org feature is designed for.

### Recommendation
Bind the authenticating organization to the acted-upon repository: after verifying the HMAC, re-derive the target repository/stack strictly from `repository.full_name` and require that its owner match the organization whose secret validated the signature (i.e., compare `repository.full_name.split('/').first` against `repository_owner` and reject on mismatch) before dispatching to any handler. Additionally, scope `StatusHandler` (and any handler that doesn't already do so) to the payload's `repository`/stack, rather than performing an unscoped `Commit.where(sha: ...)` lookup across all stacks.

### Proof of Concept
Given a Shipit instance configured with two orgs, `attacker-org` (attacker is its GitHub App admin, knows its `webhook_secret`) and `victim-org` (hosts the target stack), the attacker can:
1. Locate/guess a commit `sha` belonging to a `victim-org` stack (commit shas for public repos are trivially discoverable).
2. Construct a JSON body:
```json
{
  "sha": "<victim-org commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
3. Sign it with `HMAC-SHA1(attacker-org_webhook_secret, raw_body)` and POST it to `/github_hooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s app, and the signature matches (attacker controls that secret), so the request passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged "success" status onto the victim commit — with no reference back to `attacker-org` at all — potentially unblocking a deploy/merge gated on that status.

Note: I could not fully trace `Commit#create_status_from_github!` (defined further down in `app/models/shipit/commit.rb`, beyond the lines retrieved) to confirm it performs no additional repository check; based on `StatusHandler`'s query (`Commit.where(sha: params.sha)`, no `stack` filter) and the delegated `required_statuses`/`deployable?` logic reviewed, this appears unguarded, but a full read of that method would be needed to rule out an internal safeguard.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
