## Title
Cross-organization Team hijack via `github_id`-only lookup in `MembershipHandler` grants unauthorized `Shipit.github_teams` membership - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Shipit::Team` solely by `github_id`, without verifying that the webhook's authenticated organization (`params.organization.login`, the same value used to select the signing secret in `verify_signature`) matches the `organization` already stored on that `Team` row. An attacker who controls a tenant organization already onboarded in Shipit (and thus its own valid webhook secret) can forge a `membership` webhook naming a victim org's `Team.github_id` and inject their own GitHub login into that team's `memberships`, corrupting the authorization data consumed by `User#authorized?`.

### Finding Description
The broken binding, stated as an equality that must hold but doesn't:
`Team.find_or_create_by!(github_id: params.team.id).organization == params.organization.login` (the org that produced a valid signature).

Trace:
- `WebhooksController#verify_signature` resolves the signing config via `Shipit.github(organization: repository_owner)`, where `repository_owner` falls back to `params.dig('organization', 'login')` when no `repository` key is present [1](#0-0) . A real `membership` webhook has exactly this shape (no `repository` key), so signature verification is scoped to whatever organization the attacker names in `organization.login` — the attacker's own tenant, signed with the attacker's own configured secret.
- `MembershipHandler#process` then calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [2](#0-1) . The block (which sets `organization`) only runs on *creation*; if a `Team` row with that `github_id` already exists (e.g., the victim org's legitimately created team), the existing record — with the victim's `organization` value — is returned unchanged.
- `process` then unconditionally calls `team.add_member(member)` where `member` is a `User` created/found purely from the attacker-supplied `member.login` [3](#0-2) , `app/models/shipit/team.rb` lines 41-43. This writes a `Shipit::Membership` linking the attacker-controlled login to the victim org's `Team`, with no check that the org that signed the request owns that team.
- `User#authorized?` trusts team membership directly: `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [4](#0-3) . If the hijacked `Team` is one of `Shipit.github_teams`, the attacker's `User` becomes authorized, which is enforced app-wide in `force_github_authentication` [5](#0-4) .

Exact attacker request: `POST /webhooks` with header `X-Github-Event: membership`, `X-Hub-Signature` computed with the attacker's own org's webhook secret, and body:
```json
{"action":"added","team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"http://x"},"organization":{"login":"attacker-org"},"member":{"login":"attacker_login"}}
```
`victim_team_github_id` is the numeric GitHub team id of a pre-existing `Shipit::Team` for the victim org, discoverable via GitHub/Shipit UI as stated in the question's preconditions.

Why existing guards fail: `verify_signature` only proves the request was signed by *some* organization known to Shipit (the attacker's own org) — it never checks that this organization is authorized to mutate a `Team` belonging to a different `organization` value. `ExplicitParameters` only validates payload shape/types, not cross-field/ownership consistency. No model validation or handler code cross-checks `params.organization.login` against `team.organization` for pre-existing team rows.

### Impact Explanation
A successful forged `membership` webhook lets an attacker (who is not a member of the victim org and holds no Shipit session/token) insert their own GitHub login as a member of a `Shipit::Team` belonging to an unrelated org. If that team is referenced by `Shipit.github_teams`, `User#authorized?` becomes true for the attacker's login, granting the attacker access to deploy/rollback/merge functionality gated by `force_github_authentication` and `authorized?` across the whole Shipit instance — an escalation into `Shipit.github_teams` authorization (High per the stated severity categories). This is repeatable against any `Shipit::Team` whose `github_id` the attacker can learn, and does not require any GitHub-side team membership at all, only knowledge of a numeric team id.

### Likelihood Explanation
Preconditions: (1) attacker must control at least one organization already configured as a tenant in Shipit with a known/self-supplied `webhook_secret` (so `verify_signature` succeeds for `organization.login = attacker-org`); (2) attacker must know the numeric `github_id` of a victim `Shipit::Team`, obtainable via GitHub's public/team API or the Shipit UI as stated in the question. Given these (explicitly assumed as in-scope preconditions by the question), the attack is a single unauthenticated HTTP POST, fully repeatable, and requires no privileged Shipit role.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and the authenticated `organization`, and reject (or `head 422`/raise) when an existing `Team` for that `github_id` has a different `organization` than `params.organization.login`. For example, find by `github_id: params.team.id, organization: params.organization.login` and refuse to mutate/add members when a `github_id` collision maps to a different organization.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Create `victim_team = shipit_teams(:shopify_developers)` (organization: `shopify`, existing `github_id`).
2. Configure `Shipit.github_teams` to include `victim_team` (e.g. stub `Shipit.stubs(:github_teams).returns([victim_team])`).
3. Configure a second tenant org `attacker-org` in `Shipit.github(organization:)` test config with its own `webhook_secret` known to the test (simulating attacker-controlled secret).
4. POST to `/webhooks` with `X-Github-Event: membership`, signature computed with `attacker-org`'s secret, and body `{"action":"added","team":{"id":victim_team.github_id,"name":"x","slug":"x","url":"http://x"},"organization":{"login":"attacker-org"},"member":{"login":"mallory"}}`.
5. Assert response is `:ok`.
6. Assert `victim_team.reload.members.map(&:login)` includes `"mallory"`.
7. Assert `Shipit::User.find_by(login: "mallory").authorized?` is `true` — proving the binding `team.organization == signing organization` was violated and authorization was corrupted.
