### Title
Cross-repository SHA collision in `StatusHandler#process` allows unauthenticated repo B to flip victim commit's `deployable?` from `true` to `false` via forged `state: failure` status - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` records by SHA alone (`Commit.where(sha: params.sha)`), with no scoping to the repository that emitted the webhook. An attacker who owns an unrelated, Shipit-onboarded repository B can copy a victim's public commit SHA into repository B and push a signed `status` webhook with `state: failure`/`error`, corrupting the CI state of the same commit as tracked by an unrelated victim stack A. This is the exact same binding break previously identified for false-positive approval, now demonstrated for false-negative sabotage — confirming the vulnerability is bidirectional.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`commit.stack.github_repo_name == payload.dig('repository', 'full_name')`

is never checked. Instead:

- `Handler#stacks`/`repository_name` resolve `payload.dig('repository', 'full_name')` only for handlers that use `stacks` [1](#0-0) , but `StatusHandler` does **not** use `stacks` at all — it looks up commits globally by SHA: [2](#0-1) 

- `Commit.where(sha: params.sha)` matches every `Commit` row across every `Stack`/repository in the Shipit install that happens to share that SHA — there is no `repository_id`/`stack_id`/`github_repo_name` filter.
- `WebhooksController#verify_signature` only validates that the *signing organization* (derived from `payload.dig('repository','owner','login')`) has a valid GitHub App/webhook secret configured in Shipit [3](#0-2) . It proves the webhook truly came from repository B (which the attacker owns and configured), but it says nothing about whether the SHA inside the payload legitimately belongs to repository B. Signature verification and SHA-to-repository binding are two independent, uncorrelated checks, and only the first is enforced.

Attacker request: attacker owns/controls repository `attacker/repo-b`, which is legitimately onboarded to the same Shipit instance (a precondition already established as trivial in the prior finding — any repo the attacker owns can be onboarded). Attacker creates a commit/reference in `repo-b` reusing the victim's known public SHA (e.g., by fetching the victim's public commit and pushing it into their own repo, which preserves the SHA since Git SHAs are content-addressed and repository-independent), then sends a correctly-signed `status` event for `repo-b` with `state: failure` for that SHA:

```
POST /webhooks  (X-Github-Event: status, valid X-Hub-Signature for repo-b's org)
{
  "sha": "<victim's public sha, reused in attacker's repo-b>",
  "state": "failure",
  "repository": { "full_name": "attacker/repo-b", "owner": { "login": "attacker" } }
}
```

`StatusHandler#process` finds the victim's `Commit` row (belonging to stack A) purely by SHA match and calls `commit.create_status_from_github!(params)` on it [4](#0-3) , writing a new `failure` status for the *victim's* commit. This flips `status.success?` to `false`, which flips `Commit#deployable?`: [5](#0-4) 

No existing guard catches this: `verify_signature` validates only the emitting org's signature, not SHA ownership; `ExplicitParameters` (`params do ... end`) only validates payload shape, not repository binding; there is no `Repository`/`Stack` lookup step in `StatusHandler` at all to compare against `payload['repository']`.

### Impact Explanation
A single unsigned-trust-boundary request from an attacker-controlled, Shipit-onboarded repository B mutates CI state belonging to an unrelated victim repository/stack A, without any authentication of the SHA-to-repository relationship. Effects are bidirectional:
- `state: success` on repo B → falsely marks victim's commit `deployable?` (previously established finding — false positive, enabling unauthorized deploy).
- `state: failure`/`error` on repo B → falsely marks victim's commit not `deployable?` even though its real CI passed (this finding — false negative, denial/sabotage of legitimate deploys), and can also trigger `blocked?` cascades on subsequent commits in stack A via `stack.blocking_statuses`.

This is a payload for one repository mutating another's commit/stack state — matching the Critical category explicitly listed in scope. It is repeatable against any repository/stack pair sharing (or made to share, via SHA reuse) a commit SHA, and any attacker who can onboard a throwaway repository to the same Shipit instance can target arbitrary victim stacks, making the blast radius cross-tenant.

### Likelihood Explanation
Preconditions: attacker needs a Shipit-onboarded repository they control (same precondition as the previously validated success-flip finding), knowledge of a victim's public commit SHA (trivial — GitHub commit SHAs on public repos are public), and the ability to push/reference that SHA in their own repo (achievable by fetching and re-pushing the object, or referencing an existing shared ancestor commit such as a shared base branch). No Shipit session, API token, or GitHub secret is required — only a legitimately signed webhook from the attacker's own onboarded repository. This is low-cost and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by both `sha` and the repository identified in the payload, e.g. resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))` first, then only update `Commit` rows belonging to stacks under that repository, mirroring the pattern already used by `Handler#stacks`/`repository_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "cross-repository forged failure status flips victim commit deployable? from true to false" do
  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')
  victim_commit.statuses.create!(stack: victim_stack, state: 'success', context: 'ci')
  assert victim_commit.reload.deployable?

  # Attacker's unrelated repo shares the same sha and sends state: failure
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'failure',
    'context' => 'ci',
    'repository' => { 'full_name' => 'attacker/repo-b', 'owner' => { 'login' => 'attacker' } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  refute victim_commit.reload.deployable?
end
```
This demonstrates that `commit.deployable?` for victim stack A flips from `true` to `false` purely from a signed webhook belonging to an unrelated repository B, with no live GitHub calls, proving the SHA-based lookup in `Commit.where(sha: params.sha)` ( [2](#0-1) ) is unscoped to the originating repository.
