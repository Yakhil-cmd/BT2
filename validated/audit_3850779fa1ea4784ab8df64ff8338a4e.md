### Title
Return Data Cross-Instruction Leakage: `TransactionContext::push()` Never Resets `return_data_bytes`/`return_data_pubkey` - (File: transaction-context/src/transaction.rs)

### Summary
`TransactionContext::push()` advances the instruction stack for every new top-level instruction and every CPI, but it never clears `return_data_bytes` or `transaction_frame.return_data_pubkey`. As a result, return data set by one instruction (or one CPI) remains visible via `get_return_data()` to a completely unrelated, later instruction in the same transaction — the exact same "state that should be reset on a new logical unit-of-work but is never reset" bug class as the Jetty `_trailers` cross-request leakage.

### Finding Description
`set_return_data()` mutates two connection/transaction-scoped fields: [1](#0-0) 

`get_return_data()` simply reads them back without any staleness check: [2](#0-1) 

Crucially, `push()` — the function that is called at the start of *every* instruction invocation, both top-level instructions and CPIs (called from `InvokeContext::process_instruction` via `self.push()?`) — never resets these fields: [3](#0-2) [4](#0-3) 

The codebase's own test suite documents the *intended* invariant that return data must be cleared on entry to a new instruction: the invoked program asserts `get_return_data() == None` at the very start of its entrypoint, and the caller's test explicitly sets bogus return data beforehand specifically to verify it gets cleared: [5](#0-4) [6](#0-5) 

This is structurally identical to the Jetty bug: `_trailers`/`return_data_bytes` is a "connection"-scoped (here: transaction-scoped) mutable field that is populated by one logical unit (a request / an instruction) and is expected to be reset at the boundary of the next logical unit, but the boundary-crossing function (`messageComplete()`/`push()`) never performs the reset.

### Impact Explanation
`get_return_data()` is a primitive many on-chain programs use to pass results between CPI calls (e.g., oracle price responses, guard/validator programs checking that a specific callee "answered" before proceeding). Because `push()` does not clear return data at instruction boundaries, a single attacker-crafted, multi-instruction transaction can:
1. In instruction N, CPI into a program that legitimately sets return data (e.g., an oracle or validator program), leaving `return_data_pubkey`/`return_data_bytes` populated.
2. In instruction N+1 (or a later CPI under a different top-level instruction), invoke a program that reads `get_return_data()` expecting it to reflect the *immediately preceding* call, but instead observes stale data from step 1 because no intervening call ever reset or overwrote it (e.g., the intervening callee errored out before calling `set_return_data`, or simply never calls it).

This is exactly the TOCTOU pattern flagged in the external report: a security-relevant check ("did the oracle/guard program answer, and what did it say?") can pass using data that was never produced by the call the checking program believes it came from. Depending on how a given on-chain program consumes `get_return_data()` for authorization/validation decisions, this can lead to CPI-privilege-adjacent decision bypass (a program acting on stale/attacker-influenced return data as if it were fresh), which falls into "CPI privilege escalation"-class impact reachable by a single unprivileged transaction sender.

### Likelihood Explanation
The root-cause defect (missing reset in `push()`) is directly confirmed by reading the full body of the function — there is no line touching `return_data_bytes` or `transaction_frame.return_data_pubkey`. Triggering the stale-read condition itself requires nothing more than constructing a normal multi-instruction transaction with CPIs, which is fully within reach of any unprivileged transaction sender — no special privileges, leader status, or malicious peer/validator behavior are required. The downstream *severity* (whether some specific deployed program's logic is actually misled by this) depends on how individual programs consume `get_return_data()`, which I could not exhaustively verify across the whole ecosystem within this investigation; the finding here is scoped to proving the runtime-level invariant violation.

### Recommendation
Reset `return_data_bytes` and `transaction_frame.return_data_pubkey` (e.g., to `Pubkey::default()` and an empty `Vec`) inside `TransactionContext::push()`, before or immediately after pushing the new instruction frame, so that every new instruction invocation (top-level or CPI) starts with no return data, matching the invariant already asserted by the SBF test suite.

### Proof of Concept
Conceptual reproduction (consistent with the existing test expectations in `programs/sbf/rust/invoke/src/lib.rs` / `invoked/src/lib.rs`, but showing the violated case):
1. Transaction with instruction A that CPIs into program X, which calls `set_return_data(b"real_answer")`.
2. Instruction A completes; instruction B (a second top-level instruction in the same transaction, or a CPI under a different call path) is expected to start with `get_return_data() == None` per the codebase's own invariant.
3. Because `TransactionContext::push()` (`transaction-context/src/transaction.rs:406-458`) never clears `return_data_bytes`/`return_data_pubkey`, instruction B's program observes `get_return_data() == Some((X, b"real_answer"))` even though X was never invoked during instruction B — i.e., stale cross-instruction leakage, verifiable purely by inspecting `push()`'s implementation against `set_return_data()`/`get_return_data()`.

    /// Pushes the next instruction
    pub fn push(&mut self) -> Result<(), InstructionError> {
        let nesting_level = self.get_instruction_stack_height();
        if !self.instruction_stack.is_empty() && self.accounts.get_lamports_delta() != 0 {
            return Err(InstructionError::UnbalancedInstruction);
        }
        {
            let instruction = self
                .instruction_trace
                .last_mut()
                .ok_or(InstructionError::CallDepth)?;
            instruction.nesting_level = nesting_level as u16;
        }

        if self.number_of_called_instructions_in_trace() >= self.instruction_trace_capacity {
            return Err(InstructionError::MaxInstructionTraceLengthExceeded);
        }

        let (index_in_trace, current_top_level_instruction) = if self.instruction_stack.is_empty() {
            let index = self.next_top_level_instruction_index;
            self.next_top_level_instruction_index =
                self.next_top_level_instruction_index.saturating_add(1);
            (index, index)
        } else {
            let index = self.get_instruction_trace_length();
            self.transaction_frame.number_of_cpis_in_trace = self
                .transaction_frame
                .number_of_cpis_in_trace
                .saturating_add(1);
            self.instruction_trace.push(InstructionFrame::default());
            (
                index,
                self.next_top_level_instruction_index.saturating_sub(1),
            )
        };

        if nesting_level >= self.instruction_stack_capacity {
            return Err(InstructionError::CallDepth);
        }
        self.transaction_frame.current_executing_instruction = index_in_trace as u16;
        self.instruction_stack.push(index_in_trace);
        if let Some(index_in_transaction) = self.find_index_of_account(&instructions::id()) {
            let mut mut_account_ref = self.accounts.try_borrow_mut(index_in_transaction)?;
            if mut_account_ref.owner() != &solana_sdk_ids::sysvar::id() {
                return Err(InstructionError::InvalidAccountOwner);
            }
            instructions::store_current_index_checked(
                mut_account_ref.data_as_mut_slice(),
                current_top_level_instruction as u16,
            )?;
        }
        Ok(())
    }
