### Title
Attacker-declared `deploy.variables`/`variables` name can override trusted `IGNORED_SAFETIES`/`GIT_COMMITTER_*` env vars - (File: lib/shipit/task_commands.rb)

### Summary
`Shipit::TaskCommands#env` merges trusted, Shipit-internal keys (`TASK_ID`, `SHIPIT_USER`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`) before `@task.env`, so any repository-declared variable with one of those exact names silently overrides the trusted value. Since `EnvironmentVariables#permit`/`TaskDefinition#filter_envs` only checks that a submitted key's name matches a declared `VariableDefinition.name` — with no reserved-name blocklist — a `shipit.yml` author can declare `variables: [{name: IGNORED_SAFETIES}]` and supply that value at trigger time to flip the safety-bypass flag or forge the git committer identity used during the deploy.

### Finding Description
The broken binding: `TaskCommands#env['IGNORED_SAFETIES']` should always equal `@task.ignored_safeties? ? '1' : '0'` (and similarly `GIT_COMMITTER_EMAIL`/`GIT_COMMITTER_NAME` should always equal `@task.user&.email/name || Shipit.committer_*`), but the merge order breaks this equality.

Code path:
- `lib/shipit/task_commands.rb` `env` method: `super.merge(@stack.env).merge({... 'IGNORED_SAFETIES' => @task.ignored_safeties? ? '1' : '0', 'GIT_COMMITTER_NAME' => ..., 'GIT_COMMITTER_EMAIL' => ... }).merge(deploy_spec.machine_env).merge(@task.env)` [1](#0-0) . `@task.env` is merged last, so any key it contains wins.
- `@task.env` is populated by `Stack#trigger_task`/`Stack#build_deploy` via `definition.filter_envs(env)` / `filter_deploy_envs(env.to_h)` [2](#0-1) .
- `TaskDefinition#filter_envs` delegates to `EnvironmentVariables.with(env).permit(variables)` [3](#0-2) .
- `EnvironmentVariables#permit`/`sanitize_env_vars` only checks membership against `variable_definitions.map(&:name)` — the declared names from `shipit.yml` — with no exclusion of reserved names like `IGNORED_SAFETIES`, `TASK_ID`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `SHIPIT_USER` [4](#0-3) .
- `VariableDefinition` simply reads whatever `name` is specified in the YAML config with no restricted-keyword validation [5](#0-4) .

Exploit: A contributor (who can modify `shipit.yml` in their own fork/PR, or who is any authorized user able to trigger a task/deploy on the target stack once such a `shipit.yml` is merged) declares `deploy.variables: [{name: 'IGNORED_SAFETIES'}]` (or `GIT_COMMITTER_EMAIL`). When a deploy/task is triggered supplying `env: {'IGNORED_SAFETIES' => '1'}`, `filter_deploy_envs`/`filter_envs` permits it because the name matches the declared variable, it's stored on the task, and `TaskCommands#env` merges it last — overriding the trusted `ignored_safeties?` computed value or the trusted git committer identity used for commits made by the deploy process.

Existing guards (`verify_signature`, `require_permission!`, `EnvironmentVariables#permit`) do not close this gap: `permit` performs exactly the check that lets this through — it validates the key is declared, not that it avoids reserved bookkeeping names. No other check in the reachable path enforces the binding that these five keys must remain fixed regardless of `@task.env` content.

### Impact Explanation
An attacker who controls (or convinces a maintainer to merge) a `shipit.yml` with a maliciously-named variable can, on subsequent deploys triggered by any legitimate/authorized user, force `IGNORED_SAFETIES=1` (bypassing safety confirmation gates intended to block risky deploys) or forge `GIT_COMMITTER_NAME`/`GIT_COMMITTER_EMAIL` used for commits made during the deploy process (identity spoofing in the deploy's git history). This is scoped to the repository/stack whose `shipit.yml` declares the conflicting variable name — it is not a cross-tenant attack by itself, but it undermines a safety control that Shipit operators rely on to gate deploys, matching "unauthorized deploy" impact when combined with an authorized triggering action. `TASK_ID` and `SHIPIT_USER` overrides have lower severity (informational/audit fields) but the same root cause applies.

### Likelihood Explanation
Requires the target stack's `shipit.yml` to declare a task/deploy variable with one of the reserved names, and requires an authorized user to trigger the task/deploy supplying (or defaulting) that variable's value — this can occur if a maintainer unknowingly accepts a PR modifying `shipit.yml`, or if `shipit.yml` is contributor-editable and deploys are auto-triggered with defaults (`variables_with_defaults`) without careful review, as seen in `Stack#trigger_task`'s use of `variable.default` [6](#0-5) . Attacker cost is low (edit a config file); however, it depends on the config change being merged and a trigger to occur, so it is not directly self-triggerable by a fully unprivileged actor without at least one cooperating merge/trigger action.

### Recommendation
Reserve internal bookkeeping variable names (`TASK_ID`, `SHIPIT_USER`, `IGNORED_SAFETIES`, `GIT_COMMITTER_NAME`, `GIT_COMMITTER_EMAIL`, `EMAIL`, `BUNDLE_PATH`, `SHIPIT_LINK`) at declaration time: reject `VariableDefinition`s using these names in `TaskDefinition`/`DeploySpec` parsing, and/or reorder `TaskCommands#env` to merge `@task.env` before the trusted-keys hash so the trusted values always take precedence regardless of declared/attacker-controlled variables.

### Proof of Concept
```ruby
# test/unit/task_commands_test.rb (conceptual)
test "#env does not allow declared variables to override reserved trusted keys" do
  stack = shipit_stacks(:shipit)
  definition = TaskDefinition.new('deploy', 'variables' => [{ 'name' => 'IGNORED_SAFETIES' }])
  task = stack.deploys.build(env: { 'IGNORED_SAFETIES' => '1' }, ignored_safeties: false)
  task.stubs(:definition).returns(definition)
  commands = TaskCommands.new(task)

  refute task.ignored_safeties?
  assert_equal '0', commands.env['IGNORED_SAFETIES'] # currently fails: returns '1'
end
```
