Confirmed: `Api::StacksController#stack` correctly scopes lookups through `stacks.from_param!` (the `stacks` helper defined in `BaseController`, which restricts to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped). But `Api::CCMenuController#stack` bypasses that scoping entirely and calls `Stack.from_param!(params[:stack_id])` directly against all stacks. [1](#0-0) [2](#0-1) 

### Title
API token scoped to one stack can read CCMenu deploy status of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` establishes the binding "the set of stacks an `ApiClient` token authorizes equals `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`", enforced through the private `stacks`/`stack` helpers used by `Api::StacksController` and other resource controllers. `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id`, so the permission check (`require_permission :read, :stack`) only validates the scope-name `read:stack` and never validates that the specific stack being read is the one the token is bound to.

### Finding Description
`ApiClient` records can be created with an optional `stack_id`, which is meant to restrict what stacks the resulting bearer token can touch, as documented by `BaseController#stacks`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`Api::StacksController` uses this pattern correctly (`stacks.from_param!(params[:id])`), so a scoped token can only reach its bound stack. [3](#0-2) 

`Api::CCMenuController`, however, overrides `stack` and resolves it from the raw `Stack` model, independent of `current_api_client`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [4](#0-3) 

`require_permission :read, :stack` only calls `current_api_client.check_permissions!(:read, :stack)`, which checks whether `"read:stack"` is present in the token's `permissions` array — it never compares the requested `stack.id` to `current_api_client.stack_id`. [5](#0-4) [6](#0-5) 

This exact pattern is the intended, narrowly-scoped-by-design token created by `CCMenuUrlController`, which mints a per-stack, read-only `ApiClient` and hands its token to any logged-in user for embedding in third-party CI-dashboard tools (`CCMenu`):
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [7](#0-6) 

Note this client is created *without* `stack_id`, so by default it's global; but the vulnerability affects any `ApiClient` intentionally scoped to a stack via the admin UI (`app/views/shipit/api_clients/show.html.erb` lets an admin restrict permissions but the model supports `stack_id` scoping through `belongs_to :stack, optional: true`) — [8](#0-7)  — any token holder possessing a `read:stack`-scoped token bound to stack A can present that Basic-Auth token against `GET /api/stacks/:stack_id/cc_menu.xml` for stack B and receive B's deploy/lock status.

### Impact Explanation
This breaks the equality "stack a token authorizes = stack it touches": a credential explicitly restricted to a single stack (by an administrator, or by any workflow relying on stack-scoped `ApiClient`s) can be replayed to read deploy status, lock state, and last-build metadata for every stack in the Shipit instance. This satisfies the "unauthenticated read of stack state" class of High severity impact called out in the rules — here the attacker is authenticated as a low-privilege, single-stack token but reads state belonging to stacks outside their granted scope, which is a cross-tenant confidentiality break for any Shipit deployment hosting multiple teams/stacks behind scoped tokens.

### Likelihood Explanation
High. Any holder of a valid `read:stack`-scoped, stack-restricted `ApiClient` token (a credential type the product explicitly supports and that legitimate low-trust integrations, e.g. CI dashboards, are expected to use) can trivially exploit this by changing the `stack_id` route parameter — no additional privilege, signature forgery, or session is required beyond the token they already legitimately possess for their own stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` helper from `BaseController`, matching `Api::StacksController`:
```diff
 def stack
-  @stack ||= Stack.from_param!(params[:stack_id])
+  @stack ||= stacks.from_param!(params[:stack_id])
 end
```

### Proof of Concept
1. As an admin, create an `ApiClient` scoped to Stack A with permission `read:stack` (via `POST /api_clients` with `permissions: ["read:stack"]`, then updating `stack_id` to Stack A, or via any workflow that produces a stack-scoped token).
2. Using that token's Basic-Auth credentials, issue `GET /api/stacks/:stack_b_id/cc_menu.xml` where `stack_b_id` is a different stack the token was never authorized for.
3. `require_permission :read, :stack` passes because the token has the `read:stack` permission string; `stack` resolves via `Stack.from_param!` without checking `current_api_client.stack_id`, and the response renders Stack B's `lastBuildStatus`/`lastBuildLabel`/deploy info — data outside the token's intended scope.
