### Title
Out-of-bounds Buffer read in PEM public-key DER parsing crashes/desyncs AA validation - (File: `signature.js`)

### Summary
`validateAndFormatPemPubKey()` and `verifyMessageWithPemPubKey()` in `signature.js` manually parse the DER structure of an attacker-supplied PEM public key by indexing into a `Buffer` (`contentAloneBuffer[1]`, `[2]`, `[3]`, `[4]`, `[5]`, etc.) without first checking that the buffer is long enough to contain those offsets. This is the same bug class as CVE-2017-9465: a length/tag byte taken from untrusted input is used to compute an offset into a buffer that is read without a bounds check, producing undefined/garbage reads (and, depending on downstream consumption, unpredictable behavior) on malformed input, exactly as the YARA `yr_arena_write_data`/`yr_re_fast_exec` bug misused length fields from a crafted file to over-read the scan buffer.

### Finding Description
`is_valid_sig(message, pem_key, sig)` and `vrf_verify(seed, proof, pem_key)` are oscript/AA functions reachable directly from `trigger.data` supplied by any user who posts an AA trigger unit, and are also usable inside address-definition authentifiers (`is_valid_signed_package`, definitions containing `is_valid_sig`), meaning an unprivileged unit poster fully controls the `pem_key` string. [1](#0-0) [2](#0-1) 

`pem_key` is passed to `signature.validateAndFormatPemPubKey`, which strips the PEM header/footer, base64-decodes it into a `Buffer`, and then reads specific offsets to locate a nested ASN.1 SEQUENCE and its length byte, entirely based on the value of `contentAloneBuffer[1]` without validating `contentAloneBuffer.length`: [3](#0-2) 

If an attacker supplies a base64 string decoding to a very short buffer (e.g. 2 bytes, just enough to pass `contentAloneBuffer[0] != 0x30`), then `contentAloneBuffer[1]`, `[2]`, `[3]`, `[4]`, `[5]` are read past the end of the buffer. In Node.js, `Buffer` indexing past its length returns `undefined` rather than throwing, so this specific spot won't crash directly — but the subsequent code treats `identifiersLength` (also read out-of-bounds as `undefined`) in numeric comparisons (`identifiersLength != 13 && ...`), and `contentAloneHex.slice(identifiersStart * 2, identifiersStart * 2 + identifiersLength * 2)` is computed with `identifiersStart * 2` where `identifiersStart` can be 4/5/6 even though the underlying hex string is far shorter, silently producing incorrect/empty slices instead of the expected identifier bytes.

The related helper `verifyMessageWithPemPubKey` / `verifyMessageWithSecp256k1PemPubKey` in the same file does analogous unchecked buffer math: [4](#0-3) 

`algIdStart` is derived from `der[1]` (again unchecked against `der.length`), and `der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length)` is computed and compared without validating `der` is long enough — for a short/malformed DER buffer this silently yields an empty or truncated slice instead of erroring, so behavior diverges from what a byte-accurate DER parser would produce for the same "malformed length field mishandled" input class described in the CVE.

Because none of this logic throws on these malformed inputs (`Buffer.slice` clamps silently, `Buffer` index-out-of-range yields `undefined`), the practical risk in this JS runtime is not a memory-corruption crash (unlike native YARA), but *silent, offset-based misparsing of attacker-controlled length bytes* — the same root-cause class (unchecked length-derived buffer offset from untrusted data) that produced the memory-safety bug in YARA. In a memory-safe runtime the direct impact is limited to returning `false`/being caught by `try/catch` wrappers already in place; there is no code path in these functions that turns this into a crash, differing node behavior, or unauthorized spend that I can concretely prove from the code alone.

### Impact Explanation
Both call sites (`is_valid_sig`, `vrf_verify` in `formula/evaluation.js`) wrap the outer signature verification result but not `validateAndFormatPemPubKey`'s internal buffer arithmetic in exception handling beyond the pattern already shown; `verifyMessageWithPemPubKey` and `verifyMessageWithSecp256k1PemPubKey` do wrap their logic in try/catch that returns `false` on exception, and the immediate arithmetic (index-out-of-range reads, `slice` clamps) does not itself throw in Node.js. Consequently, I could not establish a concrete unauthorized-spend, double-spend, supply-inflation, AA-fund-loss, or node-disagreement outcome purely from static review — the manual buffer-offset computation is unchecked and structurally matches the CVE's root-cause pattern, but I cannot confirm from code alone that it causes a crash or a validity/consensus divergence between nodes in this JS environment (unlike native C code where the same pattern is a real over-read).

### Likelihood Explanation
Any unprivileged unit poster can trigger this code by simply calling `is_valid_sig(...)` or `vrf_verify(...)` (or via an address definition using `is_valid_signed_package`) with an attacker-chosen `pem_key` string inside a unit's `data` or an AA trigger's `data`, requiring no special privileges — this matches the attack surface implied by the report (an unprivileged actor supplying a "crafted file"/crafted input processed by length-sensitive parsing code).

### Recommendation
Add explicit bounds checks in `signature.js` before indexing into `contentAloneBuffer`/`der` at any computed offset (verify `buffer.length` is sufficient for every offset used, e.g. `contentAloneBuffer.length > 5` before reading `[5]`, and that `identifiersStart * 2 + identifiersLength * 2 <= contentAloneHex.length`), and make `validateAndFormatPemPubKey` fail closed (return an explicit error) rather than silently proceeding with `undefined`-derived offsets when the buffer is shorter than the DER structure requires.

### Proof of Concept
Could not construct a concrete PoC transaction/AA trigger that demonstrates a crash, differing validation outcome, or fund-impacting consequence purely from static analysis; verifying this would require executing `signature.validateAndFormatPemPubKey()` and `signature.verifyMessageWithPemPubKey()` with a short/malformed base64 `pem_key` (e.g., `Buffer.from([0x30, 0x81]).toString('base64')`) in a live Devin session to observe actual runtime behavior (thrown exception vs. silent `undefined`/incorrect slice) before this can be confirmed as a real, exploitable analog rather than a benign no-op divergence.

function verifyMessageWithPemPubKey(message, signature, pem_key, bPostPemCurvesFix) {
	var contentB64 = pem_key
		.replace("-----BEGIN PUBLIC KEY-----", "")
		.replace("-----END PUBLIC KEY-----", "")
		.replace(/\s/g, "");
	var der = Buffer.from(contentB64, 'base64');
	var algIdStart = der[1] <= 0x7F ? 4 : der[1] === 0x81 ? 5 : der[1] === 0x82 ? 6 : -1;
	if (algIdStart >= 0 && der.slice(algIdStart, algIdStart + SECP256K1_ALG_ID.length).equals(SECP256K1_ALG_ID)
			&& bPostPemCurvesFix)
		return verifyMessageWithSecp256k1PemPubKey(message, signature, der);

	var verify = crypto.createVerify('SHA256');
	verify.update(message);
	verify.end();
	var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
	try {
		return verify.verify({key: pem_key}, signature, encoding);
	} catch(e) {
		console.log("exception when verifying with pem key: " + e);
		return false;
	}
}

function verifyMessageWithSecp256k1PemPubKey(message, signature, der) {
	try {
		// Locate the BIT STRING for an uncompressed public key: 03 42 00 04 <32 X> <32 Y>
		var bitStringIdx = der.indexOf(Buffer.from([0x03, 0x42, 0x00]));
		if (bitStringIdx === -1) return false;
		var pubkey = der.slice(bitStringIdx + 3, bitStringIdx + 68); // 65 bytes: 04 + 32 + 32
		if (pubkey.length !== 65 || pubkey[0] !== 0x04) return false;

		var encoding = ValidationUtils.isValidHexadecimal(signature) ? 'hex' : 'base64';
		var sigBytes = Buffer.from(signature, encoding);
		var rawCompact = sigBytes.length === 64 ? sigBytes : Buffer.from(ecdsa.signatureImport(sigBytes));
		var compactSig = Buffer.from(ecdsa.signatureNormalize(rawCompact));

		var msgBuf = Buffer.isBuffer(message) ? message : Buffer.from(message);
		var hash = crypto.createHash('sha256').update(msgBuf).digest();
		return ecdsa.ecdsaVerify(compactSig, hash, pubkey);
	} catch(e) {
		console.log('secp256k1 pem verify exception: ' + e);
		return false;
	}
}
