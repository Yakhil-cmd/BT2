This confirms multi-tenant configuration: `Shipit.github(organization:)` looks up a per-organization config block under `secrets.github` (`github_app_config`) [1](#0-0) , each with its own `webhook_secret` used by `verify_webhook_signature` [2](#0-1) . So a Shipit instance can legitimately host several organizations, each with its own webhook secret — exactly the multi-tenant boundary this finding crosses.

### Title
Membership webhook handler grants team membership without verifying the requesting org owns the team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#process` never consults `Team#github_hooks` (the `GithubHook::Organization` scoped by `organization`/`event: 'membership'`) to confirm that the organization whose signature was verified for the request actually owns the target team. Because `find_or_create_team!` looks up teams solely by the attacker-supplied `params.team.id` (GitHub team ID), any org with a valid, independently-provisioned webhook secret on a multi-tenant Shipit instance can mutate another org's team memberships.

### Finding Description
The binding that should hold is: `verified_organization (the org whose secret validated X-Hub-Signature via Shipit.github(organization: repository_owner))` == `team.organization (the org that owns the Team row being mutated, as enforced by Team#github_hooks)`.

Trace:
1. `WebhooksController#verify_signature` derives the verifying organization from `params.dig('repository','owner','login') || params.dig('organization','login')` and validates the raw body signature against `Shipit.github(organization: repository_owner).verify_webhook_signature` [3](#0-2) , using a webhook secret configured per-organization [1](#0-0) .
2. Once verified, the raw parsed body (including any attacker-controlled fields) is dispatched unchanged to `MembershipHandler.call(params)` for the `membership` event [4](#0-3) .
3. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` — an existing `Team` row is matched purely by numeric `github_id`, and if found, the block (which would set `team.organization = params.organization.login`) is **not** executed [5](#0-4) .
4. `process` then unconditionally calls `team.add_member(member)` or `team.members.delete(member)` [6](#0-5) , with no reference anywhere to `team.github_hooks`, `Team::REQUIRED_HOOKS`, or any comparison between the verified organization and `team.organization`.
5. `Team#github_hooks` exists precisely to bind a team's organization to a registered `GithubHook::Organization` for the `membership` event [7](#0-6) , but this association is never queried by the handler — it is dead code for authorization purposes.

Exploit: an attacker who legitimately controls an organization already onboarded to a multi-tenant Shipit instance (their own `secrets.github` entry, hence a real webhook secret for their own org) sends a signed POST `/webhooks` with `X-Github-Event: membership`, `repository.owner.login`/`organization.login` set to their own org (so signature verification passes), but `team.id` set to the numeric GitHub team ID of a victim team belonging to a completely different organization (team IDs are discoverable/public on GitHub), and `member.login` set to any GitHub username they control. Because lookup is by `github_id` only, `find_or_create_team!` returns the *existing* victim `Team` row, and `team.add_member(member)` writes a `Membership` linking the attacker-chosen user into the victim org's team — without ever checking `team.github_hooks` or that the attacker's org matches `team.organization`.

Existing guards do not stop this: `verify_signature` only proves the request was signed by *some* configured organization's secret, not that this organization is authorized for *this* team; the `ExplicitParameters` schema only validates types/presence, not cross-field organization identity; and `Team#github_hooks`, though defined, is never invoked from `process`.

### Impact Explanation
A cross-tenant authorization bypass: an authenticated (signature-valid) but unauthorized organization can add or remove arbitrary users from another organization's `Team`, i.e., mutate a resource (`Team`/`Membership`) that belongs to a different tenant/organization than the one that authenticated the request. Since `Shipit.github_teams` (`Shipit.github_teams`) drives authorization elsewhere in the app (see `lib/shipit.rb#github_teams`), team membership is a security-relevant resource — injecting members into or removing legitimate members from a team can affect downstream authorization decisions gated on team membership. This is repeatable per request against any team whose GitHub team ID is known, across all tenants of the same Shipit deployment, matching the "escalation into `Shipit.github_teams` authorization" / cross-tenant mutation impact categories.

### Likelihood Explanation
Requires a multi-tenant Shipit deployment where `secrets.github` has multiple organization entries (i.e., `github_default_organization` is non-nil) [8](#0-7) , and the attacker must control one such legitimately-configured organization (own webhook secret) — a precondition consistent with "emit webhooks from a repository/org they own." No Shipit session, API token, or victim-org secret is needed. The victim team's GitHub numeric ID must be known or guessed (small integer space, and IDs are often discoverable via GitHub's public API). Cost is a single signed HTTP POST, fully repeatable.

### Recommendation
In `MembershipHandler#process` (and `find_or_create_team!`), verify that the request's authenticated organization matches `team.organization` (or that `team.github_hooks` contains a matching `GithubHook::Organization` record for the verifying org and `membership` event) before calling `team.add_member`/`team.members.delete`. Additionally, scope `find_or_create_by!` by `organization` in addition to `github_id` to prevent cross-org team-ID collision, and pass the verified organization from the controller into the handler so it can be checked against `params.organization.login` / `team.organization`.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Fixture: `shipit_teams(:shopify_developers)` with `organization: 'shopify'`, `github_id: <known>`, and `shipit_github_hooks(:shopify_membership)` bound to `organization: 'shopify'`.
2. Stub `Shipit.github(organization: 'attacker-org')` to return a `GitHubApp` whose `verify_webhook_signature` returns `true` (simulating attacker's own valid secret), while `Shipit.github(organization: 'shopify')` is not stubbed/invoked.
3. POST `/webhooks` with header `X-Github-Event: membership`, body:
   `{ action: 'added', team: { id: shipit_teams(:shopify_developers).github_id, name: '...', slug: '...', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'mallory' }, repository: { owner: { login: 'attacker-org' } } }`, with a signature valid only for `attacker-org`'s secret.
4. Assert: `team.organization == 'shopify'` and `verified_org == 'attacker-org'` — these are unequal — yet `assert_difference -> { Shipit::Membership.count }, 1` shows the write succeeds, and `shipit_teams(:shopify_developers).members.map(&:login)` includes `'mallory'`. This demonstrates the binding failure: an org other than the team's own organization successfully mutated the team's membership.
