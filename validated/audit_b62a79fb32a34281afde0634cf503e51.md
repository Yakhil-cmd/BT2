### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, without constraining to the repository that authenticated the webhook. Any repository owner can forge a `status` webhook signed with their own org's `webhook_secret` and flip the state of any other tenant's `Commit` row that happens to share the same sha, since git shas are content-addressed and can trivially collide across unrelated repos/forks (e.g., the empty tree sha, or any fork/mirror sharing history).

### Finding Description
The broken binding: `repository_owner-that-signed-the-webhook == repository-that-owns-the-mutated-Commit-row` is assumed by the system, but never enforced.

`WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) only proves that the payload was signed by the org identified in `params.dig('repository','owner','login')` — i.e., it proves "attacker/repo's org sent this." It does not, and cannot, prove anything about which `Commit` rows the payload is entitled to mutate.

`Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) provides a `stacks`/`repository_name` helper specifically meant to scope handler logic to the repository declared (and signature-verified) in the payload, via `Repository.from_github_repo_name(repository_name)&.stacks`. Several handlers use this correctly, but `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does not call it at all:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This queries `Commit` globally by `sha` across every stack/repository in the installation. Since git commit shas are content hashes, an attacker who controls `attacker/repo` can:
1. Push (or already have) a commit whose sha collides with a commit sha that also exists in `victim/repo` (trivial for identical content such as the well-known empty tree `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, an empty commit, a cherry-picked/forked commit, or any file-identical commit).
2. POST `/webhooks` with `X-Github-Event: status`, a body whose `repository.full_name` is `attacker/repo`, `sha: X`, `state: "success"`, signed with `attacker/repo`'s own org's `webhook_secret` (which the attacker legitimately possesses/controls as the repo owner).
3. `verify_signature` succeeds because it only checks against `attacker`'s org.
4. `StatusHandler.call` runs `Commit.where(sha: X)`, which returns **every** `Commit` row across all stacks with that sha, including the victim's, and calls `commit.create_status_from_github!(params)` on each — mutating `victim/repo`'s commit status via `Commit#create_status_from_github!` → `Status::Group` (`app/models/shipit/commit.rb:165-169`).

Downstream, `Commit#add_status` (`app/models/shipit/commit.rb:366-386`) triggers `Hook.emit` and `stack.schedule_merges`, and `Commit#schedule_continuous_delivery` (`app/models/shipit/commit.rb:281-287`) can queue `ContinuousDeliveryJob` if the victim stack has `continuous_deployment?` enabled and the commit becomes `deployable?`, potentially triggering an unauthorized deploy of the victim stack.

None of the listed guards prevent this: `verify_signature` only authenticates the org, not the scope of the mutation; `drop_unhandled_event` and the `ExplicitParameters` schema only validate the shape of `sha`/`state`, not repository ownership; there is no `Repository`/`Stack` scoping check anywhere in `StatusHandler`.

### Impact Explanation
An attacker who owns any GitHub repository registered with Shipit can flip the CI status of a commit in a completely unrelated tenant's stack to `success`, purely by controlling sha collisions on their own side. This is a cross-repository write where the repository that authenticated the request differs from the repository whose data is mutated — matching the "Critical: a payload for one repository mutating another's stack, commit, task or team" / "unauthorized deploy" impact category. If the victim stack is configured for continuous deployment, this can directly cause an unauthorized deploy via `Stack`'s continuous delivery path. This is repeatable against any repository sharing a sha with the attacker's repo (forks, shared history, or degenerate content like empty commits/trees).

### Likelihood Explanation
Preconditions: the attacker needs any repository registered in Shipit with a valid `webhook_secret` for its org (trivial — they can register their own repo/org), and a commit sha collision with a target victim commit. Exact sha collisions across unrelated content are cryptographically infeasible, but *content-identical* commits are common in practice (forks of the same upstream, shared vendored commits, or degenerate objects like the git empty tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical across every git repository in existence). This makes the attack readily achievable for the "any fork/shared-history" and "empty tree" cases without requiring any secret from the victim.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stacks/repository authenticated by the webhook, using the existing `Handler#stacks` helper, e.g.:

```ruby
def process
  Commit.where(sha: params.sha, stack_id: stacks.select(:id)).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

This mirrors the pattern intended by `Handler#stacks`/`repository_name` and ensures only commits belonging to the repository that signed the webhook are mutated.

### Proof of Concept
Minitest plan (no live GitHub required):
1. Create two `Repository`/`Stack` records, `attacker_stack` (repository `attacker/repo`) and `victim_stack` (repository `victim/repo`), each with distinct orgs and their own `webhook_secret` stubbed via `Shipit.github(organization:)`.
2. Create `Commit.create!(stack: attacker_stack, sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904", ...)` and `Commit.create!(stack: victim_stack, sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904", ...)`.
3. Build a status payload: `{ "sha" => "4b825dc642cb6eb9a060e54bf8d69288fbee4904", "state" => "success", "repository" => { "full_name" => "attacker/repo", "owner" => { "login" => "attacker" } } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller signature verification, which is orthogonal — it only proves the attacker's org sent it).
5. Assert: `victim_stack.commits.find_by(sha: "4b825...").state == "success"` even though the payload's `repository.full_name` is `"attacker/repo"`, i.e. assert `payload_repository_owner ("attacker/repo") != commit.stack.repository.full_name ("victim/repo")` while the mutation still occurred — demonstrating the broken binding.
6. After applying the fix (scoping by `stacks`), re-run the same test and assert `victim_stack.commits.find_by(sha: ...).state` remains unchanged (e.g., `"unknown"`/pending), while `attacker_stack`'s commit correctly updates to `"success"`.
