### Title
Webhook signature verification is bound to `repository.owner.login`, but the acted-upon repository is taken from the unverified `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Stack`/`Repository` from a completely different, unauthenticated field: `repository.full_name`. Nothing binds these two fields together, so a payload signed correctly for organization A can claim to affect a repository belonging to organization B.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used to verify `X-Hub-Signature`) purely from: [1](#0-0) 
```
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value is used to look up the correct per-organization `GitHubApp` and verify the signature against that organization's `webhook_secret`: [2](#0-1) 

Each configured organization has its own independent `webhook_secret` (multi-tenant config is explicitly supported, see `config/secrets.development.example.yml` showing separate `github: someorg: { webhook_secret }` blocks), and `GitHubApp#verify_webhook_signature` only checks the HMAC of the raw body against that one secret: [3](#0-2) 

However, once the signature check passes, the actual event handler determines *which repository/stack to act on* using a different, unrelated field of the same JSON body: [4](#0-3) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler#process` then uses this `stacks` scope to sync a stack to whatever `after` SHA is supplied: [5](#0-4) 

Since `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon repository/stack) are two independent, attacker-supplied strings inside the same raw JSON body, nothing in `WebhooksController` or `Handler` enforces that `full_name` actually starts with `owner.login`. The binding the system implicitly relies on -
`organization that authenticated == repository that is written`
- is never checked.

### Impact Explanation
An attacker who legitimately administers/controls organization A's GitHub App on a shared, multi-org Shipit instance (and therefore knows organization A's `webhook_secret`) can forge a webhook whose `repository.owner.login`/`organization.login` is `"orgA"` (so it passes signature verification using org A's secret) but whose `repository.full_name` is `"orgB/victim-repo"` and whose `ref`/`after` fields name an arbitrary branch/SHA. This payload will be correctly signature-verified, then dispatched to `PushHandler`, which resolves and mutates org B's `Stack` via `stack.sync_github(expected_head_sha: params.after)`, potentially triggering continuous-deployment logic for a repository/organization the attacker has no legitimate access to. This is an unauthorized cross-repository/cross-organization write and can result in an unauthorized deploy being triggered for a stack the attacker does not control - explicitly listed as a Critical/High impact category (cross-repository writes, unauthorized deploy).

### Likelihood Explanation
Exploitability requires the attacker to control one organization configured on the same multi-tenant Shipit instance (knowledge of that org's `webhook_secret`), which is a realistic scenario for shared/self-hosted Shipit deployments serving multiple GitHub organizations (a configuration explicitly documented and supported, see the multi-org example in `config/secrets.development.example.yml`). No GitHub App private key, session, or `ApiClient` token is needed - only the ability to send an HTTP POST to `/webhooks` with a body signed using the attacker's own known org secret.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the organization used to select/verify the webhook secret matches the owner segment of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers - e.g., reject the payload if `repository.owner.login` differs from the leading segment of `repository.full_name`, or better, verify the signature using the secret associated with the actual target repository's owner rather than a field that can diverge from it.

### Proof of Concept
1. Assume a shared Shipit instance configured with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `config/secrets.development.example.yml`'s multi-org schema).
2. As an administrator of `orgA`'s GitHub App, the attacker knows `orgA`'s `webhook_secret`.
3. Attacker crafts a JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha already present in orgB/victim-repo that attacker wants deployed>",
  "repository": { "full_name": "orgB/victim-repo", "owner": { "login": "orgA" } }
}
```
4. Attacker signs this exact raw body with `orgA`'s `webhook_secret` using HMAC-SHA1 and sets `X-Hub-Signature` accordingly, `X-Github-Event: push`.
5. `WebhooksController#verify_signature` computes `repository_owner == "orgA"`, loads `Shipit.github(organization: "orgA")`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb` lines 24-30).
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb` lines 32-38) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` (`app/models/shipit/webhooks/handlers/push_handler.rb` lines 12-17) - acting on org B's stack despite the signature only proving authenticity for org A.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
