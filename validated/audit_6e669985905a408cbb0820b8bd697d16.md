## Title
`is_valid_signed_package()` accepts signatures verified against arbitrarily old, attacker-chosen address definitions, allowing a revoked/rotated key to keep authorizing AA actions indefinitely (rollback of address-definition state) - ([File: formula/evaluation.js])

### Summary
`is_valid_signed_package` (used inside oscript/AA formulas) and the underlying `signed_message.validateSignedMessage()` verify an off-chain "signed package" against the address definition that was in force *as of the `last_ball_unit` embedded inside the package itself*, rather than the definition currently in force at the moment the AA evaluates the package. Since `last_ball_unit` is fully attacker-controlled data supplied inside the signed package (which is itself supplied by an untrusted AA trigger sender/data provider), an attacker who has obtained a **previously valid but since-revoked** private key for an address can keep signing brand-new packages that anchor to an old, pre-revocation `last_ball_unit`, and these packages will still validate successfully, even though the address owner has performed an `address_definition_change` to rotate away from that key long ago.

### Finding Description
`is_valid_signed_package` calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)`: [1](#0-0) 

Inside `validateSignedMessage`, when the package is "network aware" (has `last_ball_unit`), the code looks up `main_chain_index`/`timestamp` of that `last_ball_unit` and then reads the address definition **as of that historical MCI**: [2](#0-1) 

`storage.readDefinitionByAddress(conn, objAuthor.address, last_ball_mci, ...)` resolves the definition that was in effect at `last_ball_mci`, i.e. whatever key/definition the address had *at that point in the past*, not the definition currently in effect. The signature is then verified against that historical definition: [3](#0-2) 

Crucially, `last_ball_unit` and the rest of the `signed_message` structure (`signed_message`, `authors`, `timestamp`, `version`) are entirely attacker-supplied content inside the package that is passed into the AA (e.g. as trigger data, or as a value evaluated by the oscript formula). The only constraints enforced are that `last_ball_unit` exists, is stable, and is on the main chain, and that `main_chain_index <= mci`: [4](#0-3) 

There is no check anywhere in this path that the address's definition used for verification is still the **current** definition of the address, nor any check that no `address_definition_change` has occurred between `last_ball_mci` and the AA's current `mci`. This mirrors the CVE-2024-23332 pattern precisely: an "artifact" (here, a signed authorization package) that was valid in the past can be replayed by a party controlling old, no-longer-trusted key material, and a "permissive" verification path (one that does not enforce that the material is still current/unrevoked) accepts it.

Contrast this with unit-authoring signature verification in `validation.js`'s `validateAuthor`, which always uses `storage.readDefinitionByAddress(conn, objAuthor.address, objValidationState.last_ball_mci, ...)` where `last_ball_mci` is derived from the *actual unit currently being validated*, not from attacker-chosen data embedded in an arbitrary payload: [5](#0-4) 

For ordinary units this is safe because `last_ball_mci` reflects the unit's own position in the DAG (it cannot be rolled back by the author). But for `is_valid_signed_package`, the "unit" being verified (the signed package) is a free-floating object controlled by whoever calls the oscript formula (an AA trigger sender, or a data feed provided to the AA) with an `last_ball_unit` value of their choosing, decoupled from when the AA is actually evaluating it.

### Impact Explanation
Obyte's oscript documentation explicitly recommends `is_valid_signed_package` as a mechanism for delegated/off-chain authorization: e.g. an AA-based vault, escrow, or custody contract that releases funds or performs privileged actions when presented with a signed package proving that the address owner authorized the action, without requiring an on-chain unit from that address. Any AA that uses `is_valid_signed_package(package, "AUTHORIZED_ADDRESS")` as an authorization gate is vulnerable: if the private key behind `AUTHORIZED_ADDRESS` is ever compromised, and the legitimate owner reacts by rotating to a new key via `address_definition_change`, the attacker retains the ability to indefinitely forge new "signed packages" that reference the old (pre-rotation) `last_ball_unit`, still get validated by `is_valid_signed_package`, and thus continue to authorize withdrawals/actions from the AA. This defeats the entire security purpose of key rotation/revocation and directly leads to unauthorized spending / AA fund loss.

### Likelihood Explanation
Exploitation requires the attacker to have obtained the address's private key at some point (the same precondition needed to justify rotating it in the first place), which is a realistic threat model (leaked/backed-up key, employee offboarding, hot-wallet compromise later remediated by rotation). Once that precondition holds, forging a new valid signed package referencing an old `last_ball_unit` is trivial and entirely within reach of a single AA trigger sender - no special network position or privileged role is needed, satisfying the "unprivileged poster/AA trigger sender" reachability requirement.

### Recommendation
When verifying a signed package intended to authorize a present-time AA action, the definition used to verify the signature should be tied to the *current* state of the address (e.g., the definition at `mci`, or additionally require that no `address_definition_change` for that address has occurred between `last_ball_mci` (from the package) and `mci` (current)), rather than trusting an arbitrary, attacker-chosen historical anchor. Concretely, `is_valid_signed_package`/`validateSignedMessage` could require the caller to specify (or the code to check) that `readDefinitionByAddress(address, mci)` (current) yields the same `definition_chash` as the one resolved via the package's `last_ball_unit`, or expose an explicit "must be current definition" mode for use by `is_valid_signed_package`.

### Proof of Concept
1. Address `A` is controlled by key `K1`. Attacker obtains `K1`.
2. Owner detects compromise and issues `address_definition_change` for `A`, rotating to key `K2`, stabilized at MCI `M2`.
3. Attacker crafts a brand-new `signed_message` payload (e.g., `{"authorize": "withdraw"}`), signs it with the still-known but now-revoked `K1`, and sets `last_ball_unit` to some stable unit `U1` with `main_chain_index = M1 < M2` (from before the rotation).
4. Attacker submits this package as trigger data to an AA whose oscript contains something like:
   `if (is_valid_signed_package($data.package, "A")) { ... release funds ... }`
5. `validateSignedMessage` resolves the definition of `A` as of `M1` (still `K1`), verifies the signature successfully, and `is_valid_signed_package` returns `true` even though `A`'s current definition (at the AA's current `mci > M2`) no longer trusts `K1`. The AA executes the privileged branch based on a key the owner believed was revoked.
