### Title
Spender-attested assets permanently freeze user balances when attestor list is updated after tokens are already held - ([File: validation.js])

### Summary
`spender_attested` assets in ocore require that both the input owner and the output addresses of a payment be currently on an attestor-approved list, evaluated at validation time against the *latest* on-chain attestor list rather than the list in effect when the funds were received. A definer can update the attestor list at any time via an `asset_attestors` message, and any address dropped from the list instantly loses the ability to move (or even return/burn) tokens it legitimately holds — this mirrors the reported pattern where a permission check meant for *entry* into a flow is incorrectly re-applied to *exit*/settlement of an already-completed position.

### Finding Description
When an asset is defined with `spender_attested`, every payment spending or receiving that asset is checked against the current attestor set: [1](#0-0) 

The same requirement is enforced on the recipient side as well, in `validatePaymentInputsAndOutputs`: [2](#0-1) 

The attestor list itself is not fixed at issuance time — `readAsset`/`filterAttestedAddresses` always resolve the *latest* attestor-list unit relative to `last_ball_mci`, so any later `asset_attestors` update immediately changes who is allowed to spend already-existing balances: [3](#0-2) [4](#0-3) 

The attestor list can be freely replaced by the definer at any later point, with no constraint that previously-attested holders remain attested, and no special-casing to let a now-unattested holder still move or destroy funds they already legitimately received: [5](#0-4) 

This is structurally the same defect as the reported bug: an allow-list gate (`onlyAllowedProviders` / here, `spender_attested`) is enforced not only at the point of entering a flow (issuing/receiving tokens while attested), but is also retroactively re-applied to the act of exiting/settling a position the user already legitimately holds (spending, transferring, or even returning to the definer to destroy the token via `auto_destroy`). Because `auto_destroy` and `spender_attested` checks are independent (lines 2504-2506), a de-attested address cannot even redeem/burn its balance by sending it back to the definer — there is no bypass.

### Impact Explanation
Any holder of a `spender_attested` asset who is later removed from the attestor list by the definer has their entire balance of that asset permanently frozen: they cannot transfer it, cannot sell it, and cannot even return it to the definer to destroy it (since the same `spender_attested` gate blocks the input regardless of destination). This is an unconditional loss of access to funds that were legitimately acquired while compliant, triggered unilaterally by a third party (the asset definer) after the fact, matching the report's core concern of a completed/held position becoming unwithdrawable due to a mutable allow-list.

### Likelihood Explanation
Any asset definer who issues a `spender_attested` asset (a documented, commonly-used ocore feature for regulated/whitelisted tokens) can trigger this by publishing an updated `asset_attestors` message that drops an address, whether intentionally (compliance delisting) or accidentally (list rotation, key compromise recovery, etc.). No special conditions or race are required — the very next payment validation for that holder will fail with "owner address is not attested."

### Recommendation
Decouple the spend-side attestation check from the definer's ability to unilaterally revoke access to already-held balances. For example: only enforce `spender_attested` on the *receiving* side (as currently done for outputs) so that new value cannot flow to unattested addresses, but allow existing holders to always redeem/return their balance to the definer address (bypass the attested check specifically for the `auto_destroy`-to-definer redemption path), analogous to removing the restrictive check from a withdrawal/settlement path once the underlying position is already established.

### Proof of Concept
1. Definer creates asset A with `spender_attested=true` and `auto_destroy=true`, attestor list = [Attestor1].
2. Attestor1 attests address U (a normal user). U legitimately receives a payment of asset A while attested — this succeeds because at validation time U is on `arrAttestedAddresses` (`validation.js:2637-2638`, `2118-2121`).
3. Definer later publishes an `asset_attestors` update removing U (validated via `validateAttestorListUpdate`, `validation.js:2829-2848` — no consent from U required).
4. U attempts to spend its previously-received output, either to another address or back to the definer to redeem/destroy it. `validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses` against the new list, U is no longer in `arrAttestedAddresses`, and the payment is rejected with `"owner address is not attested"` (`validation.js:2506`).
5. U's balance of asset A is now permanently frozen with no on-chain path to recovery.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);

	);
