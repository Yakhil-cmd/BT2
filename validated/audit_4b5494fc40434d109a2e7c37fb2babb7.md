### Title
`StatusHandler#process` writes commit statuses to any commit matching `sha`, with no repository binding to the webhook's `repository.full_name` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Commit#refresh_statuses!` always fetches statuses through `stack.github_api.statuses(github_repo_name, sha, ...)`, binding the write strictly to the calling stack's own repository. `StatusHandler#process`, which handles the `status` webhook event, instead resolves the target commit(s) purely with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match, with no check that `payload.dig('repository', 'full_name')` corresponds to that commit's `stack.github_repo_name`.

### Finding Description
The invariant that should hold is: `commit.stack.github_repo_name == payload.dig('repository', 'full_name')` for every commit whose status is mutated by a webhook. This holds implicitly on the pull path because `refresh_statuses!` (`app/models/shipit/commit.rb:156-163`) only ever queries GitHub for `github_repo_name` scoped to `self.stack`, so the fetched statuses can only ever pertain to that stack's own repo/sha combination.

`StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) breaks this:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
It never calls `repository_name` (`payload.dig('repository', 'full_name')`, defined in the base `Handler` class at `app/models/shipit/webhooks/handlers/handler.rb:36-38`) or the `stacks` scoping helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) that other handlers (e.g. the `pull_request/*` handlers) use to restrict matching to the repository named in the payload. Instead it matches purely by `sha` across the entire `commits` table, i.e. across every stack/tenant in the installation, and unconditionally calls `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`), which writes a new `Status` row and triggers `Hook.emit(:commit_status, ...)`/`:deployable_status` and `stack.schedule_merges` (`app/models/shipit/commit.rb:366-386`).

Webhook signature verification (`GitHubApp#verify_webhook_signature`) confirms only that the payload was signed with Shipit's configured, installation-wide webhook secret - it authenticates that *some* GitHub repository configured against this Shipit instance sent the payload, not that the `repository` field inside the JSON body matches the commit being mutated. An attacker who controls a repository connected to this Shipit instance (any repository they can install the Shipit GitHub App/webhook on, or a public repo an operator has already onboarded) can therefore send a legitimately-signed `status` event whose `sha` happens to match a commit that belongs to a *different* stack (e.g., an identical cherry-picked/rebased commit, a shared vendored commit, or any sha collision across forks with common history), and `StatusHandler#process` will write/replace that victim commit's status and trigger downstream `deployable_status`/`schedule_merges` behavior with no repository check whatsoever.

### Impact Explanation
A cross-tenant write: an attacker-controlled webhook can create a `Status` record on a commit belonging to a stack/repository the attacker does not own, and that status can affect deployability determination (`Commit#deployable?`, `Status::Group`) and can trigger `stack.schedule_merges` when the injected status is `success`/`pending` (`app/models/shipit/commit.rb:383`). This can mark a victim's commit as green/passed CI when it hasn't actually passed, potentially unblocking an unauthorized deploy or merge for that victim stack - matching the "payload for one repository mutating another's stack/commit" and "unauthorized deploy" Critical impact categories. It is repeatable against any commit sha shared between the attacker's connected repository and any victim stack in the installation.

### Likelihood Explanation
Preconditions: the attacker needs a repository already connected to this Shipit instance (so their webhook is validly signed) and a commit sha that is also present in a victim stack's `commits` table. Since `Commit#sha` is a git SHA identifying content+history rather than being scoped per-repository at the database level (`Commit.where(sha: params.sha)` has no stack/repo predicate), any commit shared across forks, mirrors, or cherry-picked/rebased branches (a common occurrence in shared-history or monorepo/fork workflows) satisfies this. No secrets, sessions, or elevated GitHub permissions are required - only the ability to emit a `status` webhook event from a repository already wired to Shipit.

### Recommendation
Scope `StatusHandler#process` (and any other sha-only-matching handler) to only the commits belonging to stacks for the webhook's own repository, using the existing `stacks` helper in the base `Handler` class, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This restores the same binding that `refresh_statuses!` already enforces via `stack.github_api.statuses(github_repo_name, sha, ...)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`), no live GitHub required:
```ruby
test "process does not mutate a commit belonging to a different repository" do
  victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
  attacker_stack = create_stack(repository: create_repository(owner: 'attacker', name: 'evil-repo'))

  shared_sha = 'a' * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'victim commit', ...)
  attacker_stack.commits.create!(sha: shared_sha, message: 'attacker commit', ...)

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/evil-repo' }, # attacker's own, validly-signed repo
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  victim_commit.reload
  assert_not_equal 'success', victim_commit.status.state
end
```
Assert on both sides of the binding: `payload.dig('repository', 'full_name')` ("attacker/evil-repo") must equal `commit.stack.github_repo_name` ("shopify/shipit-engine") before `create_status_from_github!` is invoked on that commit; currently, the code performs no such comparison, so the test fails against the current implementation (the victim's status count changes) and passes once the fix scopes matching through `stacks`/`stack.commits`.
