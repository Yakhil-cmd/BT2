### Title
Unhandled `throw` in Private-Asset Double-Spend Handling Crashes the Node — ([File: validation.js])

### Summary
When validating a private indivisible-asset payment, `validatePaymentInputsAndOutputs()` calls `checkInputDoubleSpend()`, which resolves conflicting inputs through `checkForDoublespends()`. If the double-spend check for a *private* asset fails and the node is not light, the code path throws an unrecoverable `Error` instead of returning a validation error to the caller: [1](#0-0) 

This mirrors the bug class in CVE-2017-6498: a crafted/incorrect input (there, a malformed TGA file; here, a crafted private-payment double-spend) reaches an internal invariant check implemented as an unconditional `throw`/assertion rather than a graceful error path, resulting in denial of service.

### Finding Description
`validatePaymentInputsAndOutputs()` iterates a unit's inputs via `async.forEachOfSeries` and, for each input, calls `checkInputDoubleSpend()`: [2](#0-1) 

`checkForDoublespends()` looks up conflicting spend records and either accepts the double-spend (marking prior spends non-unique) or returns an error to `onDone`. For private assets, if `acceptDoublespends`'s attempt to resolve the conflict does not succeed and an `err` is still present, `onDone` unconditionally throws:
```js
function onDone(err){
    if (err && objAsset && objAsset.is_private && !conf.bLight)
        throw Error("spend proof didn't help: "+err);
    cb2(err);
}
```
This `throw` occurs deep inside async callbacks (`async.forEachOfSeries` → `async.series` in `validate()`), with no enclosing `try/catch` up the chain to `validation.validate()`'s caller in `network.js`'s `handleJoint()`: [3](#0-2) 

Because the throw happens asynchronously (inside a DB-query callback), it becomes an uncaught exception. `network.js` installs a top-level handler that logs the error and then deliberately re-throws to crash the process, on the theory that continuing after an assertion failure risks leaving the node in an inconsistent state: [4](#0-3) 

The same `getSavingCallbacks().ifOk` validation path used when a node receives/relays a private indivisible-asset payment (`indivisible_asset.js`) reaches the identical `validation.validate()`/`validatePaymentInputsAndOutputs()` machinery: [5](#0-4) 

Thus, any unprivileged private-payment counterparty who sends a private indivisible-asset payment chain containing an input that appears to double-spend a prior private spend, in a way the "spend proof" resolution cannot clear (`checkForDoublespends`'s `acceptDoublespends`/`graph.determineIfIncludedOrEqual` path returning an error that persists to `onDone`), can trigger this `throw`, crashing the recipient/processing node.

### Impact Explanation
An uncaught exception in a core validation path causes the entire ocore process to terminate via the `uncaughtException` handler's deliberate re-throw. This is a denial-of-service against any full node (wallet, hub, or witness) that validates the crafted private payment — matching the "network unable to confirm new units" / node-crash class explicitly allowed by the validation rules. Unlike a benign validation failure (`callback(err)`), this path bypasses graceful error handling entirely.

### Likelihood Explanation
The path is reachable by an ordinary private-payment counterparty sending a private indivisible-asset payment chain — no special privileges, hub, or peer position are required. Triggering the exact double-spend/proof-resolution failure state requires a specific sequence (a prior conflicting private spend combined with an unresolved graph inclusion check), so exploitation requires some setup but no privileged access, consistent with a Medium severity DoS.

### Recommendation
Replace the unconditional `throw Error("spend proof didn't help: "+err)` with a call to `cb2(err)` (or a dedicated validation error), so a validation failure on private-asset double-spend resolution results in `ifUnitError`/`ifError` being invoked instead of crashing the process. Add regression tests that submit private indivisible-asset payments designed to hit this branch, and audit other unconditional `throw Error(...)` statements inside async validation callbacks in `validation.js` for the same failure mode.

### Proof of Concept
1. As a private-payment counterparty, construct two private indivisible-asset payment chains that spend the same underlying private output/input but are unresolvable by `graph.determineIfIncludedOrEqual` (e.g., by presenting chains whose head units are not related by inclusion to the recipient's parent set at validation time).
2. Send the second (conflicting) chain to a full node (e.g., via `indivisible_asset.js`'s private payment handling, which calls `getSavingCallbacks().ifOk` → `validation.validate`).
3. `checkForDoublespends()` resolves the conflicting record as not included and not excluded via `arrAddressesWithForkedPath`, causing `err` to propagate to `onDone`, which throws `Error("spend proof didn't help: "+err)` inside the async chain with no surrounding try/catch.
4. The exception surfaces as `uncaughtException` in `network.js`, which logs it and re-throws, terminating the node process — denial of service. [1](#0-0) [4](#0-3)
