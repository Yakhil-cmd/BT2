### Title
Webhook signature verification is keyed by an attacker-controlled organization field that is never cross-checked against the repository the event handlers actually act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App's `webhook_secret` to HMAC-verify a webhook against using a field taken from the still-unverified JSON body (`repository.owner.login`, falling back to `organization.login`). Once that check passes, the event handlers that actually mutate state (`Stack` sync, `Commit` statuses, PR/label state, etc.) resolve the target repository from a *different* field of the same body (`repository.full_name`). In a multi-organization Shipit deployment these two fields are never required to agree, so a party holding a valid webhook secret for one configured organization can forge a payload that authenticates as "their" org while writing state for a repository belonging to a completely different organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` picks the verification key like this: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the `GitHubApp` instance (and thus the `webhook_secret`) for whatever organization name is embedded in the payload: [3](#0-2) 

Each configured organization has its own independent `webhook_secret`, as documented for multi-org setups: [4](#0-3) 

`verify_webhook_signature` only proves that the raw body was signed with *some* organization's secret - the one chosen by `repository_owner`: [5](#0-4) 

Crucially, once the signature check passes, the base `Handler` class - used by every registered webhook handler - resolves the repository to act on from a **separate field of the same payload**, `repository.full_name`, with no re-validation against `repository.owner.login`: [6](#0-5) 

`PushHandler`, for example, uses that repository/stack resolution to trigger a GitHub sync job for any stack matching the payload's branch: [7](#0-6) 

Other handlers (`StatusHandler`, PR handlers) follow the same pattern of resolving state purely from `repository.full_name`/`sha`/`number` fields inside the payload, as shown by the existing test suite creating a `Commit::Status` purely from payload fields merged with `repository_params`: [8](#0-7) 

The equality that should hold is:

```
organization whose secret validated the HMAC == organization that owns the repository/stack being mutated
```

but the code only enforces:

```
organization whose secret validated the HMAC == organization name embedded in the same untrusted payload
```

with no link back to `repository.full_name` (or `organization.login` for non-repository events such as `membership`). Because `repository.owner.login` and `repository.full_name` are two independent, attacker-supplied JSON fields in the same POST body, they can be set to different organizations: one that matches a real, weakly-held webhook secret, and one that names the actual victim repository/stack tracked by the shared Shipit instance.

### Impact Explanation
Any tenant (organization) legitimately configured on a shared, multi-organization Shipit installation can forge webhook events that pass signature verification as themselves but cause the engine to write state for a *different* organization's stacks:
- Trigger `GithubSyncJob`/`stack.sync_github` for arbitrary tracked stacks (`push_handler.rb`).
- Create/alter `Commit::Status` records for arbitrary commits in another org's repository (`status` event, confirmed by the existing test creating a `Status` from webhook payload). Since Shipit's deploy gating relies on GitHub commit statuses to decide deployability, this can be used to forge a passing CI status for a commit belonging to another tenant's stack, undermining the deploy safety checks and enabling an unauthorized deploy of that commit.
- Archive/unarchive review stacks or mutate PR-derived state belonging to another org's repositories via the PR label/assignment handlers.

This is a cross-tenant trust boundary break: the organization whose credential validated is not required to equal the organization whose data is mutated, which the rules classify as High/Critical (cross-repository writes / unauthorized deploy path via forged CI status).

### Likelihood Explanation
Exploitability depends on the deployment running Shipit with more than one GitHub organization configured (a documented, supported feature) and the attacker being one of the legitimately onboarded tenants with their own valid `webhook_secret`. Given that setup, forging the payload is trivial: it is a single POST to `/webhooks` with a correctly-HMAC-signed body where `repository.owner.login`/`organization.login` matches the attacker's own org and `repository.full_name` names the victim's repository. No additional credentials, sessions, or privileged access to the victim organization are required.

### Recommendation
After `verify_signature` succeeds, re-derive the "authenticated organization" once and pass it down to the handler layer; reject (or refuse to process) any event whose `repository.full_name` owner, `organization.login`, or other actor fields do not match the organization whose secret validated the signature. Concretely, `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks` should assert `payload.dig('repository', 'owner', 'login') == verified_organization` (or the equivalent for non-repository events) before resolving stacks/repositories, rather than trusting `repository.full_name` unconditionally.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` (attacker's own, with `webhook_secret: S1`) and `VictimOrg` (tracked stacks, `webhook_secret: S2`), per the documented multi-org config shown in `docs/setup.md`.
2. Attacker builds a `push` payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "VictimOrg/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S1, body)>` using their own known `S1`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and verifies successfully against `S1`.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves stacks via `Repository.from_github_repo_name("VictimOrg/victim-repo")` (unrelated to `AttackerOrg`) and enqueues `GithubSyncJob`/other side effects for VictimOrg's stack - despite the request never being signed by `VictimOrg`'s secret.

**Note on completeness:** I was unable to fully inspect `app/models/shipit/webhooks/handlers/membership_handler.rb` and `app/models/shipit/webhooks/handlers/status_handler.rb` bodies before running out of tool calls, so the exact downstream write for the `membership`/`status` events is inferred from `app/models/shipit/webhooks.rb` registrations and the existing controller test rather than direct code reading; the `push_handler.rb`/`handler.rb` mismatch, which is sufficient to demonstrate the vulnerability, was fully verified.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
