Confirmed the binding break: in multi-organization mode, `Shipit.github(organization: ...)` requires an exact key match against configured organizations, but `WebhooksController#verify_signature` derives that key purely from attacker-controlled JSON fields (`repository.owner.login` / `organization.login`), while the handlers that execute side effects key off a *different* field in the same payload (`repository.full_name`, used by `Repository.from_github_repo_name` in `app/models/shipit/webhooks/handlers/handler.rb`). Nothing ties these two fields together, and critically, `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's `webhook_secret` is blank/unset (`lib/shipit/github_app.rb:76-83`), a configuration explicitly shown as valid/expected in the shipped config examples (`webhook_secret: # nil`).

### Title
Webhook signature verification is keyed off an attacker-controlled organization field that is decoupled from the repository field the handlers act on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to verify the HMAC signature against using `repository_owner`, a value read directly from the untrusted JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). The event handlers, however, resolve *which repository/stack to mutate* using a different field of the same body, `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`, used transitively by `PushHandler`, `PullRequest::*Handler`, etc.). No code enforces that `repository.owner.login` is consistent with `repository.full_name`. This is the same class of bug as the reported Checkpoints issue: a value used to authorize/verify the request is not cryptographically or logically bound to the value the sensitive action actually keys off, letting an attacker satisfy the check for one entity while causing effects against another.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb:24-30`:
```ruby
def verify_signature

  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`lib/shipit/github_app.rb:76-83`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
In a multi-organization Shipit deployment (the schema explicitly documented in `config/secrets.development.shopify.yml` and `docs/setup.md`), each org can have its own `webhook_secret`, and it is documented/shown as acceptable for `webhook_secret` to be left `nil`. If *any* configured organization has no `webhook_secret` set, an unauthenticated attacker can:
1. Craft a raw JSON webhook body where `repository.owner.login` (or `organization.login`) is set to that no-secret organization's name, so `verify_signature` resolves `Shipit.github(organization: <no-secret-org>)` and `verify_webhook_signature` short-circuits to `true` regardless of the (even absent/garbage) `X-Hub-Signature` header.
2. In the very same body, set `repository.full_name` to `victim-org/victim-repo` — a completely different, secret-protected organization/repository that is actually tracked by Shipit with real stacks.
3. Send the crafted POST to `/webhooks`. The signature check passes (step 1), and the dispatched handler (e.g. `PushHandler`) resolves `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — the victim's repository — and executes `stack.sync_github(expected_head_sha: params.after)` for it.

Because Shipit trusts GitHub webhook payload data (commit SHAs, PR state, statuses, membership changes) as ground truth for driving deploy pipeline state, an attacker can inject falsified `push`, `status`, `check_suite`, `pull_request`, or `membership` events against a fully-protected organization's stacks merely by controlling one weakly configured sibling organization in the same Shipit instance.

### Impact Explanation
This crosses a repository-write / cross-tenant boundary: the verified organization ("who authenticated") is not the entity whose data is written ("the repository that is acted upon"). Concretely this enables cross-repository/cross-organization event injection without holding the victim organization's webhook secret, GitHub App credentials, or Shipit session — satisfying the report's "authenticated organization vs. written repository" binding. Depending on which handler fires, this can force `GithubSyncJob` (via forged `push`), forge commit `status`/`check_suite` results influencing deploy gating, or forge `membership` events adding/removing arbitrary GitHub users to/from `Shipit.github_teams`-backed `Team` records, escalating into `Shipit.github_teams` authorization (`MembershipHandler#process`, `app/models/shipit/webhooks/handlers/membership_handler.rb:22-33`). This meets the High-severity bar ("escalation into Shipit.github_teams authorization") and, through forged push/status events feeding automatic deploy pipelines, can contribute to an unauthorized deploy.

### Likelihood Explanation
Requires the operator to run Shipit in the documented multi-organization mode with at least one organization configured with a blank `webhook_secret` — an option the project itself ships as a valid example (`config/secrets.development.shopify.yml:9`, `config/secrets.development.example.yml:11`). Given this is a documented, supported configuration rather than a hypothetical misconfiguration, and requires no credentials at all, likelihood is non-trivial for any multi-org deployment following the shipped examples literally, though single-org deployments (the more common case) are not exposed by this specific path.

### Recommendation
Bind the signature-verification identity to the same identity used for repository resolution: after verifying the signature for the resolved `github_app`, re-validate that the app's configured organization actually owns `repository.full_name`'s owner segment (case-insensitive) before dispatching handlers, and reject the webhook otherwise. Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is unset in multi-organization mode — require every configured organization to have a non-blank `webhook_secret`, or explicitly deny requests for organizations lacking one instead of treating them as always-verified.

### Proof of Concept
Given Shipit configured with two organizations, e.g.:
```yaml
github:
  attacker-org:
    app_id: 1
    installation_id: 1
    webhook_secret: # nil
  victim-org:
    app_id: 2
    installation_id: 2
    webhook_secret: some-strong-secret
```
and a tracked stack for `victim-org/victim-repo`, an unauthenticated attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
`repository_owner` resolves to `"attacker-org"`, `Shipit.github(organization: "attacker-org")` has a blank `webhook_secret`, so `verify_webhook_signature` returns `true` (`lib/shipit/github_app.rb:77`) regardless of the bogus `X-Hub-Signature`. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack — a forged event injected into a securely-configured organization's pipeline using only knowledge of a sibling organization's (secret-less) configuration.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

    github_config[github_organization]
  end
