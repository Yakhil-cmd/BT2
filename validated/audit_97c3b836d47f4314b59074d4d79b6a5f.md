### Title
CCMenu API endpoint bypasses per-stack scoping of `ApiClient` tokens, allowing unauthorized cross-stack read of build/status information - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true`, and `Api::BaseController` enforces that scope by resolving the target stack through the token-scoped `stacks` relation. `Api::CCMenuController` overrides `#stack` to bypass that scoped relation and resolve the stack directly from the global `Stack` table, so a token that is authorized (and intended to be limited) to one stack can be used to read CI/build status of any other stack.

### Finding Description
`ApiClient` supports scoping a token to a specific stack: [1](#0-0) . This is exercised in fixtures, e.g. `here_come_the_walrus` is scoped to the `shipit` stack with only `read:stack` permission: [2](#0-1) .

`Api::BaseController` enforces this scope binding by computing `stacks` from `current_api_client.stack_id` and resolving `stack` only from within that scoped relation: [3](#0-2) 

`Api::CCMenuController`, however, redefines `stack` to resolve directly from the unscoped `Stack` model, completely bypassing the `stacks` scoping performed by the base controller: [4](#0-3) 

The controller still enforces the coarse `read:stack` permission check via `require_permission :read, :stack`, and still authenticates the client (either via HTTP Basic auth from `BaseController#authenticate_api_client`, or via the `token` query parameter override): [5](#0-4) [6](#0-5) . But permission and stack-scope are two independent bindings: `permissions` governs *what operation* the token may do, while `stack_id` governs *which stack* it may act on. `CCMenuController#stack` breaks the second binding — the stack a token is authorized for is no longer the stack it actually touches, because `Stack.from_param!(params[:stack_id])` accepts any `stack_id` in the URL regardless of `current_api_client.stack_id`.

This maps directly to the report's underlying bug class: a verified/authorized credential (there: an oracle price feed value; here: an `ApiClient` token) is legitimate for one narrow purpose, but the code path acts on an unconstrained/broader target (there: the entire RSR balance instead of the amount actually needed; here: any stack instead of the one the token is bound to) because the enforcement of the narrowing constraint was skipped in one specific code path.

### Impact Explanation
An attacker who obtains (or is issued) a stack-scoped API token with only `read:stack` permission for stack A can call `GET /api/stacks/:stack_id/ccmenu.xml` with any other stack's identifier (stack B) and receive that stack's build/deploy status: name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, and lock reason (rendered from `app/views/shipit/ccmenu/project`). This is an unauthorized read of stack state across stacks the token was never granted access to, matching the "unauthenticated/unauthorized read of stack state" High-impact category, since the token's authorization boundary (the specific stack) is silently widened to every stack in the installation.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `read:stack` tokens (a supported and tested configuration, e.g. fixture `here_come_the_walrus`) and exposes the CCMenu endpoint. No privileged access beyond possession of one such valid, narrowly-scoped token is required; the attacker only needs to change the `stack_id` path segment of an otherwise legitimate authenticated request.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (i.e., reuse `Api::BaseController#stack` / `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, so the per-token stack scope enforced elsewhere in the API is also enforced for the CCMenu endpoint.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack `shipit` (`stack_id` set) with permission `read:stack` (as in fixture `here_come_the_walrus`).
2. Authenticate to the API using that client's Basic-auth credentials or `authentication_token`.
3. Request `GET /api/stacks/<some-other-stack>/ccmenu.xml` using the *other* stack's `stack_id` (any stack the token was never scoped to).
4. Observe the response returns HTTP 200 with that other stack's CI status data, because `Api::CCMenuController#stack` at [7](#0-6)  resolves via unscoped `Stack.from_param!` rather than the `current_api_client`-scoped `stacks` relation used by `Api::BaseController#stack` at [8](#0-7) .
