### Title
`hop_submit` RPC leaks per-account authorization/quota status via distinguishable pre-signature error before proof-of-key-ownership is checked - ([File: substrate/client/hop/src/rpc.rs])

### Summary
The `hop_submit` JSON-RPC method in the new `sc-hop` (Hand-Off Protocol) client checks `HopRuntimeApi::can_account_promote(account_id, data_len)` for an attacker-supplied `signer` **before** verifying that the caller actually controls the corresponding private key. This produces the same "check status before proving identity" oracle pattern described in the AVideo report: an unauthenticated caller can distinguish "target account is authorized to promote"/"has quota" from "target account is not authorized"/"quota exhausted" using nothing but the target's public account id, without any signature that only the real owner could produce, and with no fee, captcha, or rate limit protecting the check itself.

### Finding Description
`HopRpcServer::do_submit` in [1](#0-0)  decodes the SCALE `signer` bytes into a `MultiSigner`, derives `account_id` from it, and calls `HopRuntimeApi::can_account_promote(account_id, data_len)` — all **before** the submitted `MultiSignature` is verified against that account: [2](#0-1) 

The code comment even documents the intentional ordering rationale ("a flood of unauthorized requests must not force a signature verification per submit") but does not consider that the `signer` field is fully attacker-controlled and need not be the caller's own key — `MultiSigner`/`AccountId32` are public values, so anyone can supply *any* real user's public key as `signer`. The three possible outcomes are distinguishable HopError variants surfaced to the RPC caller:

- `HopError::NotAuthorized` — target account is unknown to HOP, or its per-account authorization/quota check (`can_account_promote`) returned `false` — documented as covering "unknown account, exhausted quota, size outside a per-account tier, etc." in [3](#0-2) 
- `HopError::InvalidSignature` — the target account *passed* the authorization/quota check, but the attacker's forged signature (since they don't hold the private key) fails verification.
- `HopError::DataTooLarge` — independent of account, checked even earlier at [4](#0-3) .

This is a direct structural analog of the AVideo bug: `userRecoverPass.php` checked user-existence/status (an unauthenticated, attacker-supplied "user" parameter) before validating the captcha (proof of legitimate interaction), producing three distinguishable JSON error branches. Here, `can_account_promote` checks account authorization/quota for an attacker-supplied `signer` (any public key) before validating the signature (proof of key ownership), producing three distinguishable RPC error branches.

Per-account rate limiting in [5](#0-4)  is keyed by `SenderId` and, per the module's own design docs and the RPC flow, is only consulted inside `HopDataPool::insert`, which is reached only *after* both the authorization check and the signature check succeed (`self.pool.insert(...)` at [6](#0-5) ). Requests that fail at the `NotAuthorized` or `InvalidSignature` stage never reach the rate limiter, so probing many different target `signer` values for their authorization/quota status is not throttled by the HOP-specific limiter at all; only the node's blanket `--rpc-rate-limit` connection-level throttle applies (documented in the README: "All HOP RPC methods are also subject to the node-global `--rpc-rate-limit`" — [7](#0-6) ), which is not account-aware and does not prevent enumerating other users' status.

### Impact Explanation
This is an information-disclosure issue, not fund theft or consensus-affecting: an unauthenticated RPC caller can enumerate, for any known public account id, whether that account is currently authorized/has quota to use HOP promotion — a distinction the runtime deliberately keeps as private per-account policy (`can_account_promote` is described as encoding "an existing on-chain authorization, a dedicated HOP allowlist, or any other policy"). Depending on what the runtime's `can_account_promote` implementation encodes (allowlist membership, KYC-like gating, quota exhaustion history), this can leak account-level status decisions similarly to the "active/inactive/banned" disclosure in the original report. It does not by itself enable theft, unbacked issuance, unauthorized dispatch, or chain failure, and requires no privileged access or private key. This places it well below Critical/High and in the Medium/Low information-disclosure category consistent with the reference report's own severity rating.

### Likelihood Explanation
Likelihood is moderate-to-high wherever a node operator enables `--enable-hop` and a runtime implements `HopRuntimeApi`, since `hop_submit` is a public, unauthenticated JSON-RPC method reachable by anyone who can talk to the node's RPC endpoint, requiring no on-chain transaction, fee, or valid signature to trigger the oracle — an attacker only needs the target's public `AccountId`/`MultiSigner`, which is generally public knowledge on a chain. The severity is bounded because it only discloses a boolean-ish per-account promotion-authorization state, not funds or private data content, and this is a new, not-yet-widely-deployed feature (documented in `prdoc/stable2606/pr_11662.prdoc`) whose actual bounty-program applicability I could not confirm.

### Recommendation
Reorder `do_submit` so signature verification against the claimed `account_id` happens strictly before the `can_account_promote` authorization/quota lookup, mirroring the AVideo fix of validating the "proof" step first. If the DoS-avoidance rationale (avoid signature-verification cost for floods) must be kept, gate `can_account_promote` behind a per-connection or global-IP token check that is independent of the attacker-supplied `signer`, so that authorization-status probing across many different target accounts cannot bypass rate limiting the way it currently does by only exercising the pre-insert code path. Alternatively, collapse `NotAuthorized` and `InvalidSignature` (and ideally `DataTooLarge` account-independent cases) into one generic error for external callers while still logging the specific reason internally/in metrics.

### Proof of Concept
I was not able to execute a live reproduction (no filesystem/terminal access in this session); this assessment is based on static code review of `substrate/client/hop/src/rpc.rs`, `substrate/client/hop/src/runtime_api.rs`, `substrate/primitives/hop/src/lib.rs`, and `substrate/client/hop/src/rate_limit.rs`, cross-checked against the existing unit tests `submit_unauthorized_account_returns_error` and `submit_bad_signature_returns_error` in [8](#0-7)  and [9](#0-8) , which confirm the two distinguishable error paths (`NotAuthorized` vs `InvalidSignature`) exist and are reachable with attacker-controlled `signer`/`signature` bytes and no valid proof of key ownership. A concrete PoC would call `hop_submit` twice against a running HOP-enabled node — once with a target's real public `signer` (any known `AccountId`) and a syntactically valid but forged signature, and once with a `signer` known to be unauthorized/exhausted — and diff the returned error codes (`1012 NotAuthorized` vs `1007 InvalidSignature`) per the error table in [10](#0-9) . I did not run this against a live network, per the "no execution against public networks" constraint, and cannot independently confirm whether this feature is in scope for a live Parity bounty program at this time — flagging that as an open verification item.

```rust
	fn do_submit(
		&self,
		data: Bytes,
		recipients: Vec<Bytes>,
		signature: Bytes,
		signer: Bytes,
		submit_timestamp: u64,
	) -> Result<SubmitResult, HopError> {
		let recipient_keys: RecipientVec = recipients
			.into_iter()
			.map(|r| {
				MultiSigner::decode(&mut &r.0[..])
					.map(|signer| Recipient { signer, claimed: false })
					.map_err(|_| HopError::InvalidRecipientKey)
			})
			.collect::<Result<Vec<_>, _>>()?
			.try_into()
			.map_err(|v: Vec<Recipient>| HopError::TooManyRecipients {
				provided: v.len(),
				limit: MAX_RECIPIENTS as usize,
			})?;

		let signer =
			MultiSigner::decode(&mut &signer.0[..]).map_err(|_| HopError::InvalidSigner)?;
		let multi_sig = MultiSignature::decode(&mut &signature.0[..])
			.map_err(|_| HopError::InvalidSignature)?;

		let chain_info = self.client.info();
		let best_hash = chain_info.best_hash;

		let data_len = data.0.len();

		// Reject oversized payloads before the per-account authorization lookup so
		// a flood of too-big submits cannot force runtime state reads. The cap is
		// the runtime-declared `max_promotion_size`; the runtime is authoritative.
		let runtime_max = runtime_api::max_promotion_size::<Block, _>(&*self.client, best_hash)
			.map_err(HopError::from)?;
		if data_len > runtime_max as usize {
			return Err(HopError::DataTooLarge(data_len, runtime_max).into());
		}

		// Check authorization before verifying the signature: a flood of unauthorized
		// requests must not force a signature verification per submit.
		// `can_account_promote` returns false for any reason the runtime rejects:
		// unauthorized account or exhausted per-account quota.
		let account_id: AccountId32 = signer.clone().into_account();
		let authorized = runtime_api::can_account_promote::<Block, _>(
			&*self.client,
			best_hash,
			account_id.clone(),
			data_len as u32,
		)
		.map_err(HopError::from)?;
		if !authorized {
			return Err(HopError::NotAuthorized);
		}

		// Domain-separated payload so a submit signature cannot be replayed as claim/ack,
		// and bound to `submit_timestamp` so an old signature can't be replayed long
		// after the fact (the runtime enforces a tolerance window on the timestamp).
		let hash = H256(blake2_256(&data.0));
		let submit_payload = submit_signing_payload(&hash, submit_timestamp);
		if !multi_sig.verify(&submit_payload[..], &account_id) {
			return Err(HopError::InvalidSignature);
		}
```

```rust
	/// Check whether this account may submit `data_len` bytes right now.
	///
	/// Returns `Ok(())` on admission (tokens consumed) or `Err(retry_after_secs)`
	/// when either bucket is empty.
	pub fn check(&self, sender_id: &SenderId, data_len: u64) -> Result<(), u64> {
		if !self.cfg.enabled {
			return Ok(());
		}

		let now = Instant::now();
		let state = self.get_or_create(sender_id, now);
		let mut state = state.lock();
		state.last_touch = now;

		let req_wait = state.requests.try_consume(1.0, now).err();
		if let Some(wait) = req_wait {
			return Err(wait.as_secs().max(1));
		}

		// If the bandwidth bucket is exhausted, reject immediately and refund the request
		// token so both buckets stay consistent.
		if let Err(wait) = state.bandwidth.try_consume(data_len as f64, now) {
			// Refund the request token we just took so the two buckets stay consistent.
			state.requests.tokens = (state.requests.tokens + 1.0).min(state.requests.capacity);
			return Err(wait.as_secs().max(1));
		}

		Ok(())
	}
```
