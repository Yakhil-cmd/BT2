## Analysis

Shipit-engine supports **multi-tenant** GitHub App configuration: `Shipit.github(organization:)` looks up a distinct `webhook_secret`/`private_key`/etc. per organization key in `secrets.github`, and `Shipit.github_organizations` enumerates all configured orgs [1](#0-0) .

The webhook signature check and the actual "target repository" resolution are derived from **two different fields of the same untrusted payload**, and are never cross-validated:

- `WebhooksController#verify_signature` picks *which* organization's `webhook_secret` to check the signature against using `repository_owner`, which reads `params.dig('repository', 'owner', 'login')` (or `organization.login`) straight from the JSON body [2](#0-1) .
- Every event `Handler` (push, status, check_suite, membership, pull_request/*) instead resolves the repository to act on via `payload.dig('repository', 'full_name')` [3](#0-2) , and looks it up with `Repository.from_github_repo_name`, which just splits `"owner/name"` and does a DB lookup with no relation back to which webhook secret verified the request [4](#0-3) .

**Binding that should hold:** `organization whose webhook_secret signed the request == owner of the repository the handler mutates`. Nothing enforces this equality — the controller signs against `repository.owner.login`, the handler acts against `repository.full_name`, and these can be made to disagree in a single crafted payload.

### Exploit path
A user/attacker who is a legitimate tenant of this shared Shipit instance (i.e., owns/administers *their own* onboarded GitHub organization, with its own known `webhook_secret` — no privileged Shipit account, no `GITHUB_TOKEN`, no repo write access to the victim org is required) can:

1. Craft a JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, "sha": "<victim commit sha>", "state": "success", "context": "ci/required-check", ...}`.
2. Sign it with `attacker-org`'s own webhook secret and send it to the shared `WebhooksController#create` endpoint with `X-Github-Event: status`.
3. `verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature (the attacker owns that secret) [5](#0-4) .
4. The `StatusHandler` (built on the same `Handler` base) resolves the target repository from `full_name = "victim-org/victim-repo"`, finds the real `Stack`, and creates a `Status` row with `state: 'success'` [6](#0-5) .
5. `Status#schedule_continuous_delivery` fires, and if `victim-org/victim-repo`'s stack has continuous deployment enabled, this directly triggers `Stack#trigger_continuous_delivery` → `ContinuousDeliveryJob` → an actual unauthorized deploy of the victim's commit, as demonstrated by the equivalent test flow [7](#0-6) .

This mirrors the analog rule "an organization that authenticated versus the repository that is written": the HMAC only proves the request came from *some* onboarded org, but the handler trusts the `full_name` field of the same untrusted payload to select which stack/repo to mutate.

### Title
Webhook signature verified against `repository.owner.login` but events applied to `repository.full_name`, letting one onboarded organization forge webhooks (and trigger deploys) for another organization's repositories — (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
Shipit's multi-org GitHub App support (`Shipit.github(organization:)`) means each onboarded organization has its own webhook secret. `WebhooksController#verify_signature` selects the verifying secret using `repository.owner.login` from the payload, while every `Webhooks::Handlers::Handler` subclass resolves the actual repository/stack to mutate using `repository.full_name` from the same payload. These two fields are never checked for consistency, so a party who legitimately controls one organization's webhook secret can sign a payload whose `owner.login` matches their own org but whose `full_name` names a repository belonging to a different, unrelated organization tracked by the same Shipit instance.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-30` calls `Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository', 'owner', 'login')` (`webhooks_controller.rb:59-62`). Meanwhile, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every handler, including `push_handler.rb`, `status_handler.rb`, `check_suite_handler.rb`) reads `payload.dig('repository', 'full_name')` (`handler.rb:36-38`) and passes it to `Repository.from_github_repo_name`, which trusts the `owner/name` split verbatim (`app/models/shipit/repository.rb:53-56`). No code ties the `full_name`'s owner segment back to the organization whose secret validated the HMAC.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. A forged `status` webhook for a victim repository can flip a commit to `state: 'success'`, which `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:19,42-44`) propagates into `Stack#trigger_continuous_delivery` (`app/models/shipit/stack.rb:210-229`), causing an unauthorized deploy on any stack with continuous deployment enabled — matching the "Critical: unauthorized deploy" impact bucket. It can equally forge `push` events to trigger sync jobs or `membership`/`pull_request` events against arbitrary tracked repositories.

### Likelihood Explanation
Requires only that the attacker administers their own legitimate, distinct organization already onboarded to the same shared Shipit instance (a normal, unprivileged multi-tenant scenario the engine itself supports via `github_app_config`/`github_organizations`), and that a victim organization/repo with continuous deployment is also onboarded to the same instance. No GitHub App private key, no `GITHUB_TOKEN`, no Shipit session, and no write access to the victim repository is needed — only the attacker's own webhook secret, which they legitimately possess.

### Recommendation
After parsing the payload, verify that the organization derived for signature verification (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to any handler; reject the webhook (422) on mismatch. Alternatively, resolve the target `Repository`/`Stack` using the same organization key that was used to validate the signature rather than trusting `full_name` independently.

### Proof of Concept
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<hmac using attacker-org's webhook_secret>

{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "<victim head sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://ci.example.com/1",
  "description": "forged",
  "created_at": "2026-09-01T00:00:00Z",
  "branches": [{"name": "master"}]
}
```
`verify_signature` succeeds because it checks against `attacker-org`'s secret; `StatusHandler` then creates a `Status(state: success)` against `victim-org/victim-repo`'s stack, which — if continuous deployment is enabled — schedules `ContinuousDeliveryJob` and triggers a real deploy the attacker never had permission to initiate.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping

    end

    end
