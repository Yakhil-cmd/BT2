### Title
Webhook signature is verified against the payload's `repository.owner.login`/`organization.login`, but every event handler acts on the independent `repository.full_name` field, letting a holder of any one configured org's webhook secret forge events for a different repository/stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC with based on `repository.owner.login` (or `organization.login`) pulled straight out of the untrusted JSON body, while every `Shipit::Webhooks::Handlers::Handler` subclass resolves the actual `Stack`/`Repository` to act on from the sibling field `repository.full_name` in that same body. Nothing in Shipit cross-checks that these two fields refer to the same repository.

### Finding Description
`verify_signature` computes the signing identity purely from payload content: [1](#0-0) [2](#0-1) 

Once verified, `create` dispatches the raw JSON body to every registered handler for the event: [3](#0-2) 

But `Handler#stacks`/`#repository_name` (used transitively by `PushHandler`, `CheckSuiteHandler`, and the `repository` methods in `PullRequest::OpenedHandler`/`ClosedHandler`, etc.) resolve the target repository from a completely different field, `repository.full_name`: [4](#0-3) [5](#0-4) 

In multi-org configuration, `Shipit.github(organization:)` looks up per-organization secrets keyed by whatever `organization` string was passed in: [6](#0-5) 

For genuine GitHub-generated webhooks, `repository.owner.login` and the owner segment of `repository.full_name` always match because GitHub derives both from the same repository object, so this discrepancy is normally invisible. It only becomes exploitable for an actor who independently possesses a valid webhook secret for *some* configured organization (e.g., they are a legitimate admin/installer of the Shipit GitHub App on Org A, which the deploying company has configured in the `github:` multi-org secrets block), but has no privileges on the Shipit instance itself and no session/API token. Such an actor can craft an entirely synthetic JSON payload (not a real GitHub webhook) that sets `repository.owner.login`/`organization.login` to `OrgA` (satisfying `verify_signature`, since they know Org A's secret) while setting `repository.full_name` to `OrgB/some-other-repo` — a stack/repository belonging to a different organization entirely configured in the same Shipit instance. Because the HMAC covers the full raw body they control, the forged payload passes signature verification, and the handler then acts on `OrgB/some-other-repo` using Shipit's own service credentials for that repo.

### Impact Explanation
This breaks the equality the deployment implicitly relies on: `verified_organization(repository.owner.login) == acted_upon_repository_owner(repository.full_name)`. Concretely reachable effects with only knowledge of one org's webhook secret (no Shipit account, no `ApiClient` token, no GitHub write access to the target repo):
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for an arbitrary stack in a different org, forcing Shipit to hit the target repository's GitHub API using Shipit's own installation credentials and to record/append fabricated commit history state.
- `CheckSuiteHandler` and `StatusHandler` can inject/replay CI status/check-run state for arbitrary commits in a stack that does not belong to the signing organization, potentially affecting deploy-gating logic (`release_status`, deploy blocking) for stacks the attacker has no access to.
- `PullRequest::OpenedHandler`/`ClosedHandler` can create or archive review stacks tied to a completely different repository's pull requests.

This crosses the "cross-repository writes" impact bar defined by the rules, since it lets an attacker use credentials scoped to one repository's trust boundary to cause writes/state changes against a different, unrelated repository's Shipit resources.

### Likelihood Explanation
Likelihood is low-to-moderate and conditioned on Shipit being deployed with the multi-organization GitHub App configuration (`docs/setup.md` "Using Multiple Github Applications") and on at least one configured org's webhook secret being known to an otherwise-unprivileged party (e.g., a departed admin, a leaked secret, or a org whose GitHub App installation is self-managed by a less-trusted team). This is the same "off-chain trust vs on-chain enforcement" class as the referenced report: the engine trusts that the field it verifies against matches the field it acts upon, but never enforces that binding itself, exactly as the judge in the analog report noted should be handled on-chain/in-code rather than relied upon as an environmental assumption.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the signature, assert that the organization used to select the webhook secret matches the owner segment of `repository.full_name` (and of `organization.login` for org-scoped events) before dispatching to handlers. Reject (422) any payload where these fields diverge, rather than only comparing the verified secret's owner in isolation.

### Proof of Concept
1. Deploy Shipit with multi-org GitHub App config containing `OrgA` (secret known to attacker, e.g. attacker manages Org A's GitHub App installation) and `OrgB` (a stack the attacker has no access to).
2. Attacker crafts a JSON body for a `push` event:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "full_name": "OrgB/target-repo", "owner": { "login": "OrgA" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using Org A's known webhook secret over this exact body, and `X-Github-Event: push`.
4. `POST /webhooks` with this body/signature.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")` and verifies successfully with Org A's secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/target-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on a stack the attacker never had signing rights over. [7](#0-6) [8](#0-7)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
