## Analog Found: Reusable Bitcoin Lockup Outpoint Allows Double-Counting of L1 Sats in `pox-5.clar`

### Title
Missing global tracking of consumed Bitcoin lockup outpoints allows the same L1 BTC lock to be credited to multiple bond registrations - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s L1 path relies on `verify-l1-lockups`/`validate-l1-lockup` to prove that a Bitcoin transaction output locked a given amount of sats under the staker's timelock script. The only double-spend protection (`seen-outpoints`) is a **local accumulator scoped to a single contract call**, not a persistent on-chain record of outpoints that have already been credited. Because Clarity/pox-5 cannot observe whether a Bitcoin UTXO has actually been spent, and because nothing in the contract state permanently marks a `(txid, output-index)` pair as "already used," a staker can re-present the *same* still-valid, never-actually-spent Bitcoin lockup proof across separate calls (e.g. after exiting one bond membership and opening a new one) to be credited `amount-sats` again, without any additional BTC ever being locked.

### Finding Description
`validate-l1-lockup` (`stackslib/src/chainstate/stacks/boot/pox-5.clar:2031-2113`) folds over the caller-supplied list of Bitcoin outputs and checks: the output's script matches `construct-lockup-output-script` for `(staker, unlock-burn-height, staker-unlock-bytes, early-unlock-bytes)`, the amount matches, the header is a real burnchain header, and a merkle proof (or single-tx shortcut) proves the output is included in that block: [1](#0-0) 

Deduplication of outpoints is only performed via `seen-outpoints`, a list that is initialized fresh in the `accumulator` at the top of `verify-l1-lockups` for each call, and is never persisted: [2](#0-1) [3](#0-2) 

Scanning the contract's map definitions (`protocol-bond-allowances`, `protocol-bond-memberships`, `protocol-bonds-total-staked`, `protocol-bond-l1-early-exit-announced`, `signer-key-grants`, `used-signer-key-grants`, `signers`, `signer-delegated-per-cycle`, `signer-pending-staked-ustx-per-cycle`) there is **no map that records previously-credited `(txid, output-index)` outpoints across calls**: [4](#0-3) 

`protocol-bond-memberships` is keyed by `principal`, so a staker can only hold one *concurrent* membership, and a fresh `register-for-bond` call while a membership exists fails with `ERR_ALREADY_REGISTERED`. However, a staker's Bitcoin timelock script (built by `construct-lockup-script`, which commits only to `staker`, `unlock-burn-height`, `staker-unlock-bytes`, `early-unlock-bytes` — not to a nonce, a bond-index binding that can't be reused, or any consumption flag) remains a valid, unspent, real on-chain UTXO indefinitely until the staker actually broadcasts a spending transaction on Bitcoin: [5](#0-4) 

Because pox-5 has no way to check Bitcoin UTXO-spent status (it only verifies historical block inclusion via `verify-block-header`/`verify-merkle-proof`), and because there is no persistent outpoint ledger, a staker can:
1. Lock `S` sats into the P2WSH derived from `construct-lockup-output-script`.
2. Call `register-for-bond` with a valid merkle proof of that output, get `protocol-bond-memberships` created crediting `S` sats and locking STX for bond N.
3. Exit/unregister from that bond (freeing the `principal`-keyed membership).
4. Call `register-for-bond` again, submitting the exact same (still on-chain, still unspent, still valid) Bitcoin output as proof for a new bond membership (bond N or M), again crediting `S` sats — without any new BTC ever being locked.

Each cycle of exit+re-register credits `S` sats of stacking/reward weight backed by the same single real BTC lock. This breaks the equality that "sats credited by an L1 proof" must correspond 1:1 to sats actually and currently locked on Bitcoin.

### Impact Explanation
This is a double-counting of an L1 commitment: the protocol's accounting of `total-sats` staked per bond period (used in `calculate-bond-rewards`'s `target-yield = (totalSats * apy) / 50`, see `stackslib/src/chainstate/stacks/boot/pox-5.clar:2262-2266`) and any signer-weight/slot calculations derived from `get-total-shares-staked-for-cycle` can be inflated using a single real BTC lock replayed across multiple registration cycles. This lets an attacker earn sBTC rewards, and/or reward/signing weight, proportional to `k * S` sats for `k` repeated registrations while only ever having locked `S` sats on Bitcoin — meeting the "Critical: double-counting a commitment or reward" bar defined in the rules.

### Likelihood Explanation
The attack requires only: (1) a genuine one-time L1 Bitcoin lock of `S` sats into the canonical timelock script, (2) the ability to `register-for-bond`, wait for the merkle proof/header to be minable, and be granted a membership, then exit the bond (a normal, unprivileged lifecycle action available to any staker), and (3) resubmit the identical, never-invalidated proof to a subsequent `register-for-bond` call. No admin, signer, or third-party key is required — only the attacker's own staking/exit transactions and their own previously-created Bitcoin UTXO, which remains reusable as proof material indefinitely (or at least until the staker chooses to actually spend it).

### Recommendation
Add a persistent map (e.g., `used-l1-lockup-outpoints: {txid: (buff 32), output-index: uint} -> bool`) that is checked and permanently set the first time an outpoint is credited in `validate-l1-lockup`/`verify-l1-lockups`, across *all* calls and stakers, not just within a single call's `seen-outpoints` accumulator. Reject any lockup whose outpoint has already been recorded as used, regardless of whether the staker's prior membership has since been exited.

### Proof of Concept
1. Staker locks `S` sats into the canonical L1 timelock P2WSH (as constructed by `construct-lockup-output-script`) for `unlock-burn-height H`.
2. Staker calls `setup-bond`/`register-for-bond` with a valid merkle proof of that output; `validate-l1-lockup` passes all checks (script, amount, header, merkle proof, local dedup), and `protocol-bond-memberships` is created crediting `S` sats.
3. Staker performs the normal exit path to clear their `protocol-bond-memberships` entry (freeing them to register again), while never broadcasting a Bitcoin transaction that spends the lockup output.
4. Staker calls `register-for-bond` again, submitting the identical Bitcoin output/merkle-proof tuple as before. `validate-l1-lockup`'s `seen-outpoints` check only prevents duplicates *within this call's* output list, which contains this single output once, so it passes; a fresh `protocol-bond-memberships` entry is created, crediting `S` sats again.
5. Repeat step 3-4 arbitrarily many times: the contract's aggregate stated `total-sats`/reward-weight accounting grows by `S` each cycle while the real, single Bitcoin lock of `S` sats never changes.
