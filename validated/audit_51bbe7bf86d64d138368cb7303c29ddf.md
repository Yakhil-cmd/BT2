Found it: `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) breaks exactly the binding class described in the report — a value ("the organization that authenticated" the webhook) that is checked for one purpose but not carried through to the actual write operation.

### Title
Cross-repository commit status writes via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the HMAC secret used to authenticate the webhook) using `repository_owner`, derived from the payload's `repository.owner.login` [1](#0-0) [2](#0-1) . This authenticates that the payload genuinely originated from that specific organization's GitHub App installation. However, `StatusHandler#process` never re-checks that binding when acting on the payload: it looks up commits purely by `sha`, globally across the entire `commits` table, with no scoping to the repository/organization that was actually authenticated [3](#0-2) .

### Finding Description
The binding that should hold is: `organization authenticated by verify_signature == organization whose data is mutated by the handler`. For `PushHandler`, `CheckSuiteHandler`, and the `pull_request` handlers, this binding is enforced because they all resolve the target via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` [4](#0-3) , and `full_name` embeds the same owner login that was used to pick the webhook secret, so any signed payload for org A can only affect rows owned by org A.

`StatusHandler` breaks this: it takes `params.sha` from the (correctly-signed) payload and does `Commit.where(sha: params.sha)` with no `repository`/`stack` scoping at all, then calls `commit.create_status_from_github!(params)` on every matching commit across every stack in the Shipit instance [3](#0-2) . Since git SHA-1 values are content-derived and 40 hex chars, a commit with an identical SHA can legitimately exist in more than one repository (e.g., cherry-picks, common history, forks, or shared base commits between unrelated repos configured in the same Shipit instance). Any GitHub organization/app that Shipit trusts (i.e., is configured in `Shipit.github`) can therefore send a validly-signed `status` webhook for **its own** repository containing a SHA that happens to match a commit belonging to a **different** organization's stack, and Shipit will write CI status onto that unrelated stack's commit — directly affecting `ci.require`/`ci.blocking` gating used to allow deploys (`README.md` "CI" config), i.e., an unauthorized deploy-gate bypass across repository/organization boundaries.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" boundary explicitly called out as in-scope. A status forged (via a legitimately-signed webhook from an unrelated, lower-trust org) can flip a commit belonging to a *different, higher-value* stack's required CI check to `success`, enabling an unauthorized deploy of that other stack once the pipeline treats the check as passed. This matches the "High" impact bucket (escalation affecting deploy gating across repositories) and, depending on how `ci.blocking`/`ci.require` is consumed downstream, can enable an unauthorized deploy.

### Likelihood Explanation
Requires only that the attacker control (or have push access to) any single repository/organization that is legitimately configured as a Shipit GitHub App installation — no privileged Shipit account, API token, or webhook secret of the *target* organization is needed. The attacker just needs to cause a `status` webhook to fire with a `sha` value that collides with a commit tracked under a different stack (achievable deliberately by, e.g., cherry-picking or rebasing a commit from the public/shared history of the target project into their own controlled repo, then posting a commit status against that SHA from their own CI). This is a realistic, low-effort scenario for engines hosting multiple orgs/monorepo forks.

### Recommendation
Scope the `StatusHandler` lookup to the repository/organization identified in the payload, matching the pattern used by `Handler#stacks`/`Repository.from_github_repo_name`, e.g. restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` (or a `joins` through `Stack -> Repository` filtered on `payload.dig('repository','full_name')`) so that a status update can only ever mutate commits that belong to the repository actually authenticated by `verify_signature`.

### Proof of Concept
1. Configure Shipit with two orgs/apps: `victim-org` (installed on `victim-org/app`, has a stack with `ci.require: ["ci/tests"]`) and `attacker-org` (installed on `attacker-org/fork`, attacker has push access).
2. Attacker rebases/cherry-picks a commit `C` (SHA `abc123...`) from `victim-org/app`'s history into `attacker-org/fork` (or otherwise obtains a commit that already exists, unmerged, with the same SHA in both repos — trivial if the fork shares history) so that Shipit's `commits` table contains a row with `sha = abc123...` tied to the victim stack.
3. Attacker's own CI posts a `status` webhook for `attacker-org/fork` at SHA `abc123...` with `state: success`, `context: "ci/tests"`. This webhook is correctly signed with `attacker-org`'s own `webhook_secret`, so `verify_signature` passes using `Shipit.github(organization: 'attacker-org')`.
4. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which returns the victim's commit row too, and calls `create_status_from_github!` on it — marking the victim stack's commit `ci/tests` check as `success` even though the victim's own CI never ran or reported it.
5. If `victim-org/app`'s deploy pipeline treats `ci/tests` as satisfied, the commit becomes deployable, achieving an unauthorized-deploy precondition without ever touching `victim-org`'s webhook secret or Shipit credentials.
