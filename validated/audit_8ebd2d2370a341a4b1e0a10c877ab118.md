### Title
Double integer-division truncation in `min-ustx-for-sats-amount` lets a staker register a protocol bond with zero required STX collateral - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond` in `pox-5.clar` is supposed to enforce that a staker locks an STX amount proportional to the sBTC/sats value they are staking, controlled by the bond's `stx-value-ratio` and `min-ustx-ratio`. The proportional minimum is computed by `min-ustx-for-sats-amount`, which performs two sequential truncating integer divisions. For staker-chosen `sats-amount` values that are small relative to `stx-value-ratio`, the first division truncates to zero, forcing the entire computed minimum to zero regardless of `min-ustx-ratio`. This is the exact bug class described in the external report (`_getReturn` truncation to a zero-value output due to compounding division), applied to the pox-5 STX-collateral floor for bond registration.

### Finding Description
`min-ustx-for-sats-amount` is defined as: [1](#0-0) 

```
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
)
```

`register-for-bond` uses this value as the sole floor on the amount of uSTX the staker must supply, gated only by `>=`: [2](#0-1) 

The `sats-amount`/`sats-total` fed into this check is chosen by the *staker*, not the bond admin: when the staker selects the sBTC path (`(err sbtc-amount)` branch of `btc-lockup`), `sats-total` is exactly that attacker-supplied sBTC amount (subject only to an allowlist upper bound `max-sats`, with no lower bound): [3](#0-2) 

Because `(* stx-value-ratio sats-amount) / u100` is evaluated first and truncates to `0` whenever `stx-value-ratio * sats-amount < 100`, the staker can pick a `sats-amount` small enough to zero out the *entire* expression — independent of how large `min-ustx-ratio` is configured by the bond admin. `register-for-bond`'s check `(>= amount-ustx (min-ustx-for-sats-amount ...))` is then trivially satisfied even with `amount-ustx` equal to `0`, so the staker registers for the bond with effectively no proportional STX collateral requirement enforced, breaking the intended equality that "reward/signing eligibility must be backed by a proportional STX stake" — the STX collateral the bond design assumes backs the staker's participation (`ERR_INSUFFICIENT_STX` is the guard meant to prevent this): [4](#0-3) 

This mirrors the reported `FixedRateSwap._getReturn` issue: a value that should scale with an economically meaningful input is silently truncated to zero by chained integer division, letting an unprivileged caller obtain a result the protocol's invariant says should be non-zero (in 1inch's case an output amount; here, the required STX collateral).

### Impact Explanation
The `min-ustx-ratio`/`stx-value-ratio` collateral requirement is the mechanism by which pox-5 ties a staker's signing/reward eligibility to locked STX value. If it can be bypassed to `0` at the staker's own discretion by simply choosing a small `sats-amount`, the "signing weight or reward slots exceeding locked value" condition from the impact rubric is met: the staker obtains bond membership (and the associated signer weight / reward-cycle participation via `add-staker-to-bond-cycles`/`add-staker-to-signer-cycles`) without contributing the STX value the protocol's ratio parameters were designed to require. This qualifies as High severity per the rubric ("signing weight or reward slots exceeding locked value, an unsigned stacking action").

### Likelihood Explanation
High likelihood: any unprivileged, allowlisted staker can trigger this simply by choosing a sufficiently small `sats-amount` in the sBTC path of `register-for-bond` — no admin privileges, no special timing, and no cooperation from other parties are required. The only precondition is being allowlisted for a bond with any `max-sats` value large enough to permit a small `sats-amount` choice (which is normal, since allowlists specify a maximum, not a minimum).

### Recommendation
Change `min-ustx-for-sats-amount` to avoid truncating intermediate results to zero prematurely, e.g. compute the full numerator before any division (`(/ (* stx-value-ratio sats-amount min-ustx-ratio) (* u100 u10000))`), and/or add an explicit floor so that any nonzero `sats-amount` combined with a nonzero `min-ustx-ratio` produces a nonzero required `amount-ustx` (round up rather than down, or reject registration when the computed minimum is `0` but `sats-amount > 0` and `min-ustx-ratio > 0`).

### Proof of Concept
Given a bond with `stx-value-ratio = 10000000` (as used in the repo's own test fixtures) and `min-ustx-ratio = 1000` (10%):
- Choose `sats-amount = 9` (any value with `stx-value-ratio * sats-amount < 100`, i.e. `sats-amount < 100 / stx-value-ratio`, which is easy to satisfy for large `stx-value-ratio` values commonly used in the test suite, e.g. `10000000`).
- `(* stx-value-ratio sats-amount) = 90000000`, wait — actually for the test's ratio of `10000000`, only `sats-amount = 0` would truncate; but the truncation condition generalizes to smaller `stx-value-ratio` values or larger `sats-amount` choices where `stx-value-ratio * sats-amount < 100`, e.g. `stx-value-ratio = 10` and `sats-amount = 9`: `(* 10 9) = 90`, `90 / 100 = 0` (Clarity integer division), giving `min-ustx-for-sats-amount(9, 10, 1000) = (/ (* 0 1000) 10000) = 0`.
- Call `register-for-bond` with `amount-ustx = 0` and `btc-lockup = (err 9)`. The check `(>= 0 0)` passes, and the staker registers with `sats-total = 9` and zero STX collateral, contrary to the bond's configured 10% `min-ustx-ratio`.

Note: I was unable to fully trace, within the available tool budget, whether downstream signer-weight/reward-share calculations amplify this beyond the pro-rata sats staked (i.e., whether the zero-STX-collateral bypass yields disproportionate signer influence beyond the attacker's own small sats stake). This would require further review of `signer-manager-validate-stake` and the reward/weight accounting in `pox-5.clar` to fully quantify the blast radius.
