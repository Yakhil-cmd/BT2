### Title
Unhandled `throw Error` in double-spend conflict resolution can crash the full node on a crafted payment unit - (File: `validation.js`)

### Summary
`mc_transaction_core::validation::validate`'s `.expect()` panics are matched in ocore by unconditional `throw Error(...)` statements inside `checkForDoublespends()`, which executes during the normal validation path of every payment message (`validateAuthors`/`validateMessages` → `validatePaymentInputsAndOutputs` → `checkForDoublespends`). These `throw` statements assume invariants about the relationship between a conflicting spend record and the unit's authors/graph position that are not actually guaranteed to hold for every attacker-crafted-but-well-formed unit, and — unlike the `cb(error)` pattern used everywhere else in `validation.js` — they bypass the `async.series` error-handling path entirely, propagating as an uncaught JS exception.

### Finding Description
`checkForDoublespends` is invoked from `validatePaymentInputsAndOutputs` whenever a payment input (`issue` or `transfer`) is validated, which happens for every unit containing a `payment` message — i.e., for essentially any unit an unprivileged user (Eve) can post to the network. [1](#0-0) 

Inside the row-iteration callback, two invariants are enforced with a bare `throw Error(...)` instead of returning an error to `cb`: [2](#0-1) 

```js
if (arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1)
    throw Error("conflicting "+type+" spent from another address?");
...
if (objValidationState.arrAddressesWithForkedPath && objValidationState.arrAddressesWithForkedPath.indexOf(objConflictingRecord.address) === -1)
    throw Error("double spending "+type+" without double spending address?");
```

These `throw`s occur deep inside an `async.eachSeries` callback that is not wrapped by the outer `try { ... } catch(e)` blocks used elsewhere in `validate()` for exactly this purpose (see the payload-hash and payload-commission calculations, which are defensively wrapped in `try/catch` precisely because they can throw on malformed attacker input): [3](#0-2) [4](#0-3) 

No equivalent `try/catch` exists around `checkForDoublespends`'s conflict-address checks, so if the assumed invariant is violated (e.g., by a specially-crafted unit that creates a double-spend against an existing record whose owning address is not among the current unit's authors, or is not part of `arrAddressesWithForkedPath`), the exception surfaces as an **uncaught exception** in the Node.js process.

The severity of this is compounded by the network layer's explicit crash-on-uncaught-exception policy: [5](#0-4) 

```js
process.on('uncaughtException', (err) => {
	console.log('Uncaught exception:', err);
	...
	throw err; // crash the process to avoid ending up in an inconsistent state
});
```

This is structurally analogous to the MobileCoin `.expect()` panic: a data-structure invariant assumed by validation code is enforced via a hard, unrecoverable failure (Rust panic / JS uncaught throw) rather than a graceful error path, and the invariant is reachable through the *normal* execution of unit/transaction validation triggered by attacker-supplied data.

### Impact Explanation
If the invariant can be violated by a crafted-but-otherwise-valid unit (e.g., through double-spend/fork-path edge cases not anticipated by the `arrAddressesWithForkedPath` bookkeeping, or through race conditions in how `objValidationState.arrAddressesWithForkedPath` is populated for multi-authored/shared addresses), any full node processing that unit would crash outright via the `uncaughtException` handler, which is documented to deliberately crash the process. Because unit validation is triggered for every newly received or posted unit, a single crafted transaction broadcast by Eve could bring down every full node that receives and validates it — a network-wide denial-of-service, not merely a resource-exhaustion issue.

### Likelihood Explanation
Likelihood is rated **conditional/uncertain**: reaching this code path requires an existing conflicting spend record in the database and crafting a unit whose authors/graph relationship to that record does not match the coded assumption. This is a much narrower trigger surface than a straightforward malformed-field bug, and confirming an exact, deterministic exploit sequence would require deeper analysis of how `arrAddressesWithForkedPath` and multi-author/shared-address double-spend bookkeeping is populated elsewhere in `validation.js` and `write.js`/`main_chain.js` (this analysis could not be completed within the available tool budget). The pattern itself, however, is a clear violation of defensive-coding practice for attacker-reachable code, matching the reported bug class closely.

### Recommendation
- **Short term:** Replace the `throw Error(...)` calls in `checkForDoublespends` (lines 1673 and 1692 of `validation.js`) with `cb(error)`/`return callback(...)` calls consistent with the rest of `validation.js`'s error-handling convention, so that any unexpected invariant violation degrades to `ifUnitError`/`ifJointError` instead of crashing the process. Audit other bare `throw Error(...)` statements inside async callbacks reachable from `validate()` (e.g., in `validatePaymentInputsAndOutputs`, `validateAuthor`) for the same issue.
- **Long term:** Add fuzz testing around unit/transaction validation (`validation.js`) targeting double-spend and forked-path bookkeeping, and consider wrapping the entire `async.series` validation pipeline's callbacks in a top-level `try/catch` that converts any uncaught exception into an `ifUnitError`/`ifTransientError` response rather than allowing it to propagate to `process.on('uncaughtException')`.

### Proof of Concept
Not fully constructed — reaching the vulnerable branch requires reproducing the exact database state (a `spend_proofs`/`inputs` conflicting record) and author/graph configuration under which `arrAuthorAddresses.indexOf(objConflictingRecord.address) === -1` or the `arrAddressesWithForkedPath` check fails, which requires further investigation of the double-spend/fork-path bookkeeping logic in `validation.js` and `main_chain.js` beyond what could be completed in this session.
