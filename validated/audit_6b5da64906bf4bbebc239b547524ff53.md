## Finding: `EncryptedPayload` sender/signer binding (`Ciphertext::verify` against `PayloadAssociatedData`) is enforced only at the REST API layer, not in the VM prologue, mempool, or vm-validator

### Summary

The Aptos encrypted-transaction feature binds an encrypted payload's ciphertext to a specific `(sender, signer_auth_keys)` set via `PayloadAssociatedData`, checked by `EncryptedPayload::verify()` → `Ciphertext::verify()`. This binding check is invoked exactly once, in the REST submission handler `TransactionsApi::validate_signed_transaction_payload` [1](#0-0) , gated behind `allow_encrypted_txns_submission`. It is not called anywhere in the VM's prologue path (`run_prologue_with_payload`) [2](#0-1) , nor in `vm-validator`, mempool's `add_txn`/`insert`, or the consensus decryption pipeline. Those paths only check the transaction's Ed25519/authenticator signature (`TransactionAuthenticator::verify`) and the `payload_hash`/`claimed_entry_fun` consistency after decryption [3](#0-2) , but never re-check that the ciphertext's embedded associated data matches the transaction's actual sender and signer authentication keys.

### Finding Description

`EncryptedInner.ciphertext` is a `Ciphertext` whose integrity is protected by an internal ed25519 signature over `(bibe_ct, associated_data_bytes)`, using a throwaway `vk` embedded in the ciphertext itself [4](#0-3) . `Ciphertext::verify(associated_data)` only checks that the *caller-supplied* `associated_data` matches what's embedded, and that the embedded signature is internally self-consistent [5](#0-4) . This does **not** cryptographically bind the ciphertext to the actual transaction's sender/signers — that binding is supposed to be enforced externally by calling `verify()` with the correct `(sender, signer_auth_keys)` derived from the concrete `SignedTransaction`.

That external binding check exists in exactly one place: the REST API's `validate_signed_transaction_payload`, which derives `signer_auth_keys` from `signed_transaction.authenticator().all_signer_auth_keys(signed_transaction.sender())` and calls `payload.verify(signed_transaction.sender(), signer_auth_keys)` [1](#0-0) .

Everywhere else a `SignedTransaction` carrying an `EncryptedPayload` can enter the system — `vm-validator`'s `validate_transaction` (used by mempool for gatekeeping before insertion) [6](#0-5) , mempool's `add_txn`/`TransactionStore::insert` [7](#0-6) , and the VM's own prologue (`run_prologue_with_payload`, `run_script_prologue`) [8](#0-7)  — there is no call to `EncryptedPayload::verify`/`Ciphertext::verify` with the transaction's actual sender/authenticator. The VM only cares that the transaction's outer authenticator signature verifies against `raw_txn.as_encrypted_variant()` (which signs over the `Encrypted` ciphertext bytes, not over the semantic sender/signer-key binding) and, post-decryption, that `payload_hash`/`claimed_entry_fun` match the decrypted plaintext [9](#0-8) .

### Impact Explanation

Since Aptos transaction admission has multiple entry points beyond the REST API (peer-to-peer mempool broadcast via `MempoolSyncMsg`, direct submission to `vm-validator`, or any client bypassing the `api` crate and submitting BCS transactions through another interface), and since the semantic association-data binding is checked only inside `api/src/transactions.rs`, a transaction whose ciphertext's associated data does not match its declared sender/signer set can still pass:
- outer signature verification (which only certifies who signed the *opaque ciphertext bytes*, not who the plaintext execution is "meant for"), and
- VM prologue/execution (which never checks the associated-data binding at all).

This means the guarantee "the encrypted payload's associated data is bound to this specific sender and signer key set" — the entire security purpose of `PayloadAssociatedData` — is not actually enforced as an on-chain/VM/mempool admission invariant; it is enforced only as an optional REST gateway convenience check. Any path that reaches mempool or the VM without going through that specific REST handler function admits and can commit an encrypted transaction whose semantic sender/signer binding was never validated.

### Likelihood Explanation

This requires reasonably specific circumstances: `allow_encrypted_txns_submission` must be enabled (the encrypted transaction feature is still nascent/gated), and an attacker or misbehaving node must be able to submit a `SignedTransaction` with an `EncryptedPayload` into mempool or directly into `vm-validator` without going through the REST `validate_signed_transaction_payload` gate — e.g., via mempool's inbound P2P broadcast handling path (`process_incoming_transactions`), which flows into `validate_and_add_transactions` → `vm_validator.validate_transaction` without any association-data check [10](#0-9) . Given how new and narrowly gated the encrypted-transaction feature is, I could not fully confirm from static reading alone whether some other layer (e.g., inside `FPTXWeighted`/decryption pipeline) enforces this binding a second time; the consensus decryption code I inspected (`decryption_pipeline_builder.rs`) only checks `payload_hash`/`epoch`/`claimed_entry_fun`, not the associated-data/sender binding.

### Recommendation

- Move the `EncryptedPayload::verify(sender, signer_auth_keys)` associated-data check into the VM prologue (`run_prologue_with_payload`) or into `run_script_prologue`, so it is enforced as a hard admission invariant regardless of transaction ingress path (REST, P2P mempool broadcast, or direct submission to `vm-validator`).
- Alternatively/also enforce it in `vm-validator`'s `validate_transaction` so mempool never accepts an encrypted transaction whose ciphertext's associated data diverges from its authenticator's sender/signer set.
- Add explicit tests exercising the P2P mempool ingestion path (not just `api/src/tests/*`) with a mismatched associated-data ciphertext to confirm rejection.

### Proof of Concept

Conceptual PoC (not fully verified end-to-end due to index limitations on the full encryption pipeline):
1. Build a valid `RawTransaction` with sender `S` and an `EncryptedPayload::Encrypted` whose `Ciphertext` was encrypted with `PayloadAssociatedData::new(S2, other_auth_keys)` for a different sender/signer set `S2` (rather than `S`'s own keys).
2. Sign the outer `RawTransaction` (still `sender = S`) normally with `S`'s private key — this succeeds because `TransactionAuthenticator::verify` only checks the signature over `raw_txn.as_encrypted_variant()`, unrelated to the ciphertext's internal associated data.
3. Submit this `SignedTransaction` directly to `vm-validator::validate_transaction` (bypassing `api/src/transactions.rs::validate_signed_transaction_payload`), or inject it via a simulated P2P mempool broadcast path (`validate_and_add_transactions`).
4. Observe that neither `vm-validator` nor `run_prologue_with_payload` calls `EncryptedPayload::verify`, so the mismatched-binding transaction is accepted into mempool and eventually decrypted/executed without the associated-data invariant ever being checked.

Because I was not able to execute this in a live environment and could not fully trace whether the batch-encryption/decryption pipeline itself independently re-derives and checks the associated data at decrypt time (I found no such call in `decryption_pipeline_builder.rs`), this should be verified with an actual runtime reproduction before treating it as fully confirmed; a Devin session with repo execution access would be needed to run the mempool/vm-validator paths concretely and confirm no other layer performs this check.

impl<EK: BIBECTEncrypt> CTEncrypt<EK::CT> for EK {
    fn encrypt<R: RngCore + CryptoRng>(
        &self,
        rng: &mut R,
        plaintext: &impl Plaintext,
        associated_data: &impl AssociatedData,
    ) -> Result<Ciphertext<EK::CT>> {
        // Doing this to avoid rand dependency hell
        let mut signing_key_bytes: [u8; SECRET_KEY_LENGTH] = [0; SECRET_KEY_LENGTH];
        rng.fill_bytes(&mut signing_key_bytes);

        let signing_key: SigningKey = SigningKey::from_bytes(&signing_key_bytes);
        let vk = signing_key.verifying_key();
        let hashed_id = Id::from_verifying_key_and_ad(&vk, associated_data);
        let bibe_ct = self.bibe_encrypt(rng, plaintext, hashed_id)?;

        // So that Ciphertext doesn't have to be generic over some AD: AssociatedData
        let associated_data_bytes = bcs::to_bytes(&associated_data)?;

        let to_sign = (&bibe_ct, &associated_data_bytes);
        let signature = signing_key.sign(&bcs::to_bytes(&to_sign)?);

        Ok(Ciphertext {
            vk,
            bibe_ct,
            associated_data_bytes,
            signature,
        })
    }

impl<PCT: InnerCiphertext> Ciphertext<PCT> {
    pub fn verify(&self, associated_data: &impl AssociatedData) -> Result<()> {
        let hashed_id = Id::from_verifying_key_and_ad(&self.vk, associated_data);

        (self.associated_data_bytes == bcs::to_bytes(associated_data)?)
            .then_some(())
            .ok_or(BatchEncryptionError::CTVerifyError(
                CTVerifyError::AssociatedDataDoesNotMatch,
            ))?;

        (self.bibe_ct.id() == hashed_id).then_some(()).ok_or(
            BatchEncryptionError::CTVerifyError(CTVerifyError::IdDoesNotMatchHashedVKAndAD),
        )?;

        let to_verify = (&self.bibe_ct, &self.associated_data_bytes);

        self.vk
            .verify(&bcs::to_bytes(&to_verify)?, &self.signature)
            .map_err(|e| {
                BatchEncryptionError::CTVerifyError(CTVerifyError::SigVerificationFailed(e))
            })?;

        Ok(())
    }
