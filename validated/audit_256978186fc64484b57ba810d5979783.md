### Title
CCMenu endpoint ignores an `ApiClient`'s stack scope, letting a single-stack token read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `CCMenuController` re-implements authentication and stack lookup instead of using the shared, properly scoped helpers from `Api::BaseController`, breaking the binding "the stack a token authorizes == the stack it touches."

### Finding Description
`Api::BaseController#stack` resolves the requested stack through the `stacks` helper, which restricts the result set to the `ApiClient`'s own `stack_id` when the client is stack-scoped: [1](#0-0) 

`CCMenuController`, however, overrides both authentication and stack resolution. It authenticates via a bare `params[:token]` and then resolves the stack directly with `Stack.from_param!(params[:stack_id])`, completely bypassing the `current_api_client.stack_id` scoping applied everywhere else in the API: [2](#0-1) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`, not that the requested `stack_id` matches the token's own `stack_id`: [3](#0-2) 

So the equality that should hold — `current_api_client.stack_id == stack.id` for any stack-scoped token — holds in `BaseController#stack` (used by every other API controller) but is broken specifically in `CCMenuController#stack`.

### Impact Explanation
An `ApiClient` created with a narrow scope (`stack: A`, `permissions: ['read:stack']` — exactly the kind of low-privilege token meant to be embedded in a CI dashboard/CCMenu widget URL) can be used to read the CI/deploy status of *any* stack in the Shipit instance, not just stack `A`. This is an authorization-scope escalation matching the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-impact class, since the token was never meant to expose data belonging to other teams/repositories.

### Likelihood Explanation
CCMenu tokens are specifically designed for embedding in third-party tools via a URL query parameter, which is the credential form most likely to be shared, logged, or leaked outside the person who created it. Any leaked/shared token, however narrowly scoped, converts into read access to every other stack's deploy/task status by simply changing `stack_id` in the URL — no other prerequisite beyond having any one valid (even minimally scoped) token.

### Recommendation
Make `CCMenuController` reuse `BaseController`'s scoped `stack`/`stacks` helpers instead of calling `Stack.from_param!` directly, so a stack-scoped `ApiClient` cannot resolve any stack other than the one it is bound to.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to stack `A` with permission `read:stack` (e.g. the token embedded by an admin into a CCMenu-compatible CI dashboard for stack A).
2. As an attacker who only has that token, request another stack `B`'s status:
   `GET /stacks/:B_id/ccmenu.xml?token=<token-scoped-to-A>`
3. `authenticate_api_client` in `app/controllers/shipit/api/ccmenu_controller.rb` accepts the token (it is a valid `ApiClient`), and `stack` resolves `B` directly via `Stack.from_param!(params[:stack_id])`, so `show` renders stack `B`'s deploy status even though the token was never granted access to `B`.
