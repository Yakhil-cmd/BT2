### Title
Private-asset payments sent to an Autonomous Agent address are silently excluded from AA balance tracking and can never be spent or refunded, permanently locking user funds - (File: main_chain.js, storage.js, aa_composer.js)

### Summary
The external report describes a class of bug where funds that accrue to a contract-controlled address are never tracked or exposed by the on-chain logic, so nobody — neither the contract nor its users — can ever claim or move them. The analogous root cause exists in ocore's Autonomous Agent (AA) balance-accounting logic: every code path that computes an AA's spendable balance (trigger detection, `aa_balances` initialization/maintenance, and the balance-consistency checker) explicitly excludes private-asset outputs with `is_private=0`/`IS NULL` filters. Because private assets can still legally be paid to any address, including an AA address, a private payment sent to an AA is accepted by the DAG but is invisible to the AA and to the `aa_balances` table forever.

### Finding Description
An AA is only "triggered" and only has its balance updated by outputs that satisfy `(outputs.asset IS NULL OR is_private=0)`, as seen in the trigger-selection query in `main_chain.js`: [1](#0-0) 

The same exclusion is enforced when initial AA balances are populated for a newly-defined AA: [2](#0-1) 

and again in the periodic balance-consistency checker (`checkBalances`), which reconciles `aa_balances` against ledger outputs using the identical `(is_private=0 OR is_private IS NULL)` filter: [3](#0-2) 

Because an AA address is not controlled by any private key — it can only spend funds via its oscript logic, driven entirely by the values in `aa_balances` and by triggers computed from non-private outputs — a private-asset output sent to an AA address is a dead end:
- It never appears in `trigger.outputs`, so the AA is never invoked to process it (`getTrigger` in `aa_composer.js` only reads plain `payment` messages' outputs, and the trigger-selection query above filters private outputs out of consideration entirely).
- It is never added to `aa_balances`, so even if the AA were invoked for another reason, its oscript could never reference or move this balance (`balance[asset]` and `trigger.output[[asset=...]]` are backed by `aa_balances`/`trigger.outputs`, both of which exclude private outputs).
- The AA cannot send a private payment back either — AA-originated private payments are explicitly disallowed since the AA has no way to prove ownership via a private-payment chain (`sending private asset from AA` is rejected in `aa_composer.js`).

Since the depositor also has no private key for the AA address, and the AA can never see or spend the funds, the coins are permanently unspendable/unrecoverable by anyone — the private-payment analogue of "the pool contract cannot claim funds sitting in an external system it manages."

### Impact Explanation
Any private asset sent to an AA address results in a complete, permanent loss of those funds: no participant (the sender, the AA owner/author, or any oscript logic) has a path to move, refund, or otherwise account for the coins. This is a concrete unauthorized/permanent fund-loss condition (funds vanish from all spendable accounting despite the funds objectively existing on the DAG), matching a High-severity impact.

### Likelihood Explanation
Likelihood is significant because sending a private asset to any valid address, including an AA address, requires no special privilege — it's a standard `payment` message to a private asset. Users interacting with AAs that also handle private assets, or that simply are unaware their AA address should not receive private assets, could trigger this unintentionally. There is no validation-layer safeguard preventing a private-asset payment from naming an AA address as recipient.

### Recommendation
- In `validation.js`, when validating a private-asset payment (or the corresponding private-payment chain handling in `private_payment.js`), reject or otherwise disallow outputs whose destination address is a known AA address (`aa_addresses` table), similar to how AA-originated private sends are already rejected in `aa_composer.js` ("sending private asset from AA").
- Alternatively, extend the AA trigger/balance accounting to accept and correctly account for private-asset outputs sent to AAs (this is architecturally more complex, since it requires the AA to receive spend proofs and the private-payment chain, which conflicts with AAs having no interactive off-chain component).
- At minimum, surface a wallet-level warning/rejection when a user attempts to send a private asset to an address that is registered as an AA.

### Proof of Concept
1. Define any simple AA (e.g., one that just accepts base coins and updates state, such as the sample AAs in `test/samples/a_bank_without_percent.oscript`).
2. Issue a private asset (`is_private: true`) and send a `payment` with that asset's outputs to the AA's address using the standard private-payment flow.
3. Observe that:
   - `handleAATriggers` in `main_chain.js` never selects this unit as a trigger for the AA because its only output is `is_private=1`.
   - `aa_balances` for the AA address is never updated with this asset (confirmed by the `is_private=0 OR is_private IS NULL` filter used both when populating balances in `storage.js::insertAADefinitions` and when reconciling in `aa_composer.js::checkBalances`).
   - The AA's oscript can never reference `balance[asset]` for this asset because it is not present in `aa_balances`, and cannot construct a payment to send it back since sending private assets from an AA is explicitly rejected.
4. The private-asset coins remain permanently locked at the AA address with no code path — AA logic or otherwise — capable of spending them.
