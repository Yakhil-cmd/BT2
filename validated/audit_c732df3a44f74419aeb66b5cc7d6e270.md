### Title
Cross-organization webhook confusion allows repository takeover via mismatched signature-org and payload repository - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` derives the GitHub App/organization whose `webhook_secret` is used to validate the HMAC signature exclusively from `params.dig('repository', 'owner', 'login')` (or `organization.login`), while every downstream handler resolves the target `Stack`/`Repository` from a completely separate field, `payload.dig('repository', 'full_name')`, without re-checking that this repository actually belongs to the organization that was cryptographically verified.

### Finding Description
`verify_signature` looks up the GitHub App config with `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that organization's `webhook_secret`. [1](#0-0) 
`repository_owner` is read straight from the JSON body (`repository.owner.login`, falling back to `organization.login`). [2](#0-1) 

Once the signature check passes, `create` dispatches the **entire raw JSON body** to the matching handler(s), with no re-derivation or cross-check of the organization used above. [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) independently re-reads the repository to act on from `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks`, and resolves it with `Repository.from_github_repo_name`, which just splits `"owner/name"` and does a DB lookup — with zero relation to `repository_owner` used during signature verification. [4](#0-3) [5](#0-4) 

Because these two lookups (`repository.owner.login` used for HMAC-secret selection vs. `repository.full_name` used for the actual DB/stack action) are never bound together, an attacker who can produce a validly-signed payload for **organization A** (e.g. because they administer/control a repo hooked into org A, or org A's webhook secret was leaked/weak) can set `repository.full_name` to `"orgB/some-repo"` inside that same signed payload. The signature still verifies (it's computed over the whole raw body and validated against org A's secret, and nothing ties the secret used to the `full_name` value), yet the handler will act on org B's `Repository`/`Stack`, e.g. triggering `PushHandler#process` → `stack.sync_github(expected_head_sha: params.after)` for a repository the attacker does not control at all. [6](#0-5) 

This breaks the binding: **organization authenticated (via `webhook_secret` lookup keyed by `repository_owner`) == repository written (looked up via `repository.full_name` inside handlers)**. These two are supposed to be the same repository/org, but the code never enforces that equality.

### Impact Explanation
An attacker with the ability to generate a validly-signed webhook body for any one configured GitHub organization (e.g., because they own a repo under that org and can trigger/forge a webhook, or that org's secret is weaker/leaked independent of the target org) can forge cross-organization events (`push`, `status`, `check_suite`, etc.) that get processed as if they originated from GitHub for a completely different, unrelated repository/stack. This can trigger `sync_github`, commit-status updates, or check-run refreshes on stacks belonging to other organizations/repositories that the attacker has no legitimate relationship with — a cross-repository write triggered without proper authentication scoping to that repository.

### Likelihood Explanation
Requires the attacker to have a validly signed payload for *some* organization configured in `Shipit.secrets.github` (multi-org GitHub App setups are explicitly supported per `Shipit.github_organizations`/`github_app_config`), and to control the `repository.full_name`/`repository.owner.login` mismatch in the JSON body while keeping the byte-for-byte body identical for the signature. Since the signature is computed over the raw body and the attacker fully controls the JSON they submit (as long as they know one org's secret), this is achievable without any GitHub-side cooperation — it's a same-request field substitution, not a replay-only attack. Likelihood is elevated in any deployment mounting multiple GitHub organizations/apps behind the same webhook endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), after resolving the target repository/stack, assert that `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.owner` equals the `repository_owner` that was used to select the `webhook_secret`/GitHub App config, and reject (422) on mismatch. Alternatively, always resolve the target repository's own configured organization/secret directly from the persisted `Repository` record (looked up by `full_name`) rather than trusting `repository.owner.login`/`organization.login` from the unauthenticated part of the payload for secret selection.

### Proof of Concept
1. Suppose Shipit is configured with two GitHub Apps/organizations, `org-a` and `org-b`, each with its own `webhook_secret`, per `Shipit.github_app_config`.
2. Attacker knows/controls `org-a`'s `webhook_secret` (e.g. it's their own org, or the secret leaked/was brute-forced independently of `org-b`).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha that exists in org-b's repo>",
  "repository": { "full_name": "org-b/target-repo", "owner": { "login": "org-a" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, raw_body)` and POSTs to `/webhooks`.
5. `verify_signature` computes `repository_owner` = `"org-a"` (from `repository.owner.login`), fetches `org-a`'s `webhook_secret`, and the signature validates successfully.
6. `create` parses `params` and dispatches to `Shipit::Webhooks.for_event('push')` → `PushHandler.call(params)`.
7. `PushHandler#stacks` calls `Repository.from_github_repo_name('org-b/target-repo')`, finds the real `org-b` repository/stack, and calls `stack.sync_github(expected_head_sha: params.after)` — acting on `org-b`'s stack despite the request only ever being authenticated against `org-a`'s secret.

      verified = github_app.verify_webhook_signature(
