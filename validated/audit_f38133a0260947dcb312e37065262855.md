### Title
Webhook signature is verified against the GitHub App bound to `repository.owner.login`, while the event handlers act on `repository.full_name` / a global `Commit.sha` lookup — an authenticated organization can forge state for repositories it does not own - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify the HMAC signature with by reading `repository_owner`, which is taken from the same untrusted JSON body: `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). It then calls `Shipit.github(organization: repository_owner)` and verifies the raw body against that organization's `webhook_secret`. [1](#0-0) [2](#0-1) 

Once the signature check passes, the body is dispatched to handlers that determine *which repository/commit to act on* from a different, independently-controlled field of the same payload:
- `Webhooks::Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')`, unrelated to the `owner.login` used for signature selection. [3](#0-2) 
- `PushHandler#process` uses that `repository_name` to locate `stacks` and triggers `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack. [4](#0-3) 
- `StatusHandler#process` doesn't even look at `repository` at all — it matches purely on `Commit.where(sha: params.sha)` **globally across the whole database**, and calls `commit.create_status_from_github!(params)` with attacker-controlled `state`, `description`, `target_url`, `context`. [5](#0-4) 

This is the same trust-binding mismatch pattern as the referenced report: one field (`Claim()`'s caller / here, `repository.owner.login`) is what's checked/authorized, while a different field or scope (the vested user / here, `repository.full_name` or a global `sha`) is what's actually mutated. Deployments using Shipit's documented multi-organization configuration are directly exposed: `Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github`, one entry per org that has installed its own GitHub App. [6](#0-5) [7](#0-6) 

An attacker who legitimately administers **their own** GitHub organization/App registered on the same Shipit instance (a normal, supported multi-tenant setup, not requiring any Shipit session or stolen secret) knows their own org's `webhook_secret` and can therefore produce a validly-signed request. They can set `repository.owner.login` to their own org (so `verify_signature` picks their own webhook secret and passes), while setting `repository.full_name` (for `push`) to any other tracked repository, or simply supplying an arbitrary `sha` (for `status`, which ignores repository entirely) belonging to a commit in a completely different organization's stack.

### Impact Explanation
- Via the `status` webhook, an attacker (owner of any one organization's webhook secret on the instance) can forge CI/commit statuses (`state`, `description`, `target_url`, `context`) for **any commit sha across all stacks in the whole Shipit installation**, since `Commit.where(sha:)` is not scoped by repository at all. Forged "success" statuses can satisfy deploy-checklist/CI gating and enable an unauthorized deploy of an otherwise unvetted commit for a repository the attacker does not own.
- Via the `push` webhook, an attacker can trigger `stack.sync_github` for stacks belonging to a repository/org they do not own, by crafting `repository.full_name` independently of the `owner.login` used for signature selection.

This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in scope, and can lead to an unauthorized deploy path (forged status gating).

### Likelihood Explanation
Requires the attacker to control at least one organization/GitHub App already configured in the target Shipit instance's multi-org `secrets.github` (a legitimate, low-privilege scenario supported by the documented multi-org configuration), and knowledge of standard webhook payload shapes (public GitHub documentation). No Shipit session, `ApiClient` token, or admin access is required — only knowledge of one's own already-provisioned webhook secret. This is realistic in shared/multi-tenant Shipit deployments serving several GitHub organizations.

### Recommendation
Bind signature verification and payload interpretation to the *same* trusted identifier: after verifying the signature with the organization derived from the request, re-derive `repository_owner`/`repository_name` used by handlers strictly from that same verified organization, and reject payloads whose `repository.full_name` owner does not match the organization the signature was verified against. For `StatusHandler`, scope the `Commit` lookup by the repository resolved from the verified organization instead of a global `sha` match.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret`. Attacker administers `attacker-org` and knows its `webhook_secret`.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<victim commit sha tracked by victim-org stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` (`X-Hub-Signature: sha1=...`) and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, verifies successfully against `attacker-org`'s secret. [1](#0-0) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (no repository scoping) and applies the forged status to the victim's commit. [8](#0-7)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
