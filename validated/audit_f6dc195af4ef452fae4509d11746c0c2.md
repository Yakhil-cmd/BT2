## Title
Webhook signature is verified against the organization in `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, allowing cross-organization/cross-repository forged webhooks in multi-tenant installs - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (an officially supported configuration where each GitHub organization has its own GitHub App and its own `webhook_secret`), the `WebhooksController` selects *which* organization's secret to use for HMAC verification from one JSON field (`repository.owner.login` / `organization.login`), but every webhook `Handler` subsequently resolves the record to act on from a *different*, unguarded JSON field (`repository.full_name`). Because these two fields are never cross-validated, an attacker who legitimately knows the webhook secret for their own onboarded organization can forge a signed payload whose `owner.login` matches their org (so the signature check passes) while `full_name` points at a totally different tenant's repository, causing Shipit to act on that victim repository's stacks.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using only the repository owner (or fallback organization) login: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct config (and thus a distinct `webhook_secret`) per organization key when the multi-app schema is used: [3](#0-2) 

This multi-org, per-organization-secret configuration is an officially documented and tested feature (each org configures/knows its own App's webhook secret, set "on the side" at App-creation time): [4](#0-3) [5](#0-4) 

Once the HMAC over `request.raw_post` validates for *that* organization, `WebhooksController#create` dispatches the entire raw JSON body to the registered handlers: [6](#0-5) 

Every base `Handler` (and thus `PushHandler`, all `PullRequest::*Handler`s, `StatusHandler`, `CheckSuiteHandler`) resolves the target `Repository`/`Stack` purely from `repository.full_name`, a sibling field of `repository.owner.login` inside the same attacker-controlled JSON body — with no check that it belongs to the organization whose secret produced the valid signature: [7](#0-6) [8](#0-7) [9](#0-8) 

**Binding broken:** `organization_authenticated_by_signature (repository.owner.login) == organization_owning_repository_written_to (repository.full_name)`. GitHub itself always keeps these consistent in real webhook deliveries, but the controller trusts raw client-supplied JSON for both, so nothing in the code enforces this equality for forged requests signed with a *different, but valid,* organization secret.

### Impact Explanation
An attacker who is an administrator of their own organization's Shipit-connected GitHub App (i.e., knows *their own* org's `webhook_secret`, which the docs explicitly tell them to keep) can forge a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
}
```
signed with `attacker-org`'s known secret, sent with `X-Github-Event: push`. `verify_signature` selects `Shipit.github(organization: "attacker-org")` and the signature passes, then `PushHandler` runs `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stacks, forcing an out-of-band sync/potential deploy trigger for a repository the attacker never owns. The same class of forgery lets an attacker archive/unarchive a victim's review stacks (`pull_request` labeled/closed handlers) or inject fake commit statuses (`status` handler) that gate deploys — i.e., cross-repository writes and interference with another tenant's deploy pipeline, without any repository write access or Shipit session of their own on the victim repo.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (a documented, supported configuration) and requires the attacker to be a legitimate admin of at least one onboarded organization (so they know that org's own webhook secret) — a low bar in shared/hosted Shipit installs serving several independent teams/orgs. No GitHub write access to the victim repo, no Shipit session, and no victim credentials are needed.

### Recommendation
In `WebhooksController`, after verifying the signature, cross-check that the organization used to select the webhook secret (`repository_owner`) matches the owner segment of `repository.full_name` (and of `organization.login` for org-level events) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, have handlers look up the `Repository`/`Stack` scoped to the verified organization rather than trusting `full_name` alone.

### Proof of Concept
1. Configure Shipit with the documented multi-org schema, e.g. `OrgOne` and `OrgTwo`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and onboard a stack for `OrgTwo/victim-repo`.
2. As an admin who legitimately created/owns `OrgOne`'s GitHub App (and thus knows `OrgOne`'s `webhook_secret`), build a JSON body:
   `{"ref":"refs/heads/master","after":"<sha>","repository":{"owner":{"login":"OrgOne"},"full_name":"OrgTwo/victim-repo"}}`.
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(OrgOne_webhook_secret, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgOne")` and validates successfully (`lib/shipit/github_app.rb#verify_webhook_signature`).
5. `PushHandler#process` resolves `Repository.from_github_repo_name("OrgTwo/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: "<sha>")` for the victim's stack, despite the request having been signed with `OrgOne`'s secret — demonstrating the cross-organization write.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
