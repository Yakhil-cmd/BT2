### Title
Unvalidated swap route addresses enable arbitrary venue callbacks that can steal caller wallet funds - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts caller-supplied `StrategySwap` bytes and forwards them to the configured router without constraining the pool addresses encoded in the route. [1](#0-0)  The router resolves a hop's `pool`, `token_in`, and `token_out` directly from the payload and dispatches the named pool as a venue. [2](#0-1)  A malicious venue contract can therefore execute code beneath the caller's authorization tree and request unrelated token transfers from that caller, analogous to an attacker-controlled SSRF target. [3](#0-2) 

### Finding Description
Controller strategies such as `swap_collateral` pass the user-supplied `swap` argument into `swap_tokens`, which invokes `router.execute_strategy(controller, amount_in, swap)`. [4](#0-3)  The controller protects only its own exact `token_in.transfer(controller, router, amount_in)` authorization and measures the resulting balances; it does not inspect or restrict the venue addresses embedded in `swap`. [5](#0-4) 

During route execution, each swap instruction treats payload-selected addresses as a callable pool. [6](#0-5)  For example, the Soroswap adapter invokes `get_reserves` and then `swap` on the supplied pool address, while the Aquarius adapter likewise invokes `swap` on that address. [7](#0-6) [8](#0-7) [9](#0-8) 

The repository's adversarial test demonstrates the consequence: a router hop to an unlisted pool performs `wallet_token.transfer(victim, attacker, amount)`, and Soroban simulation records that transfer as a child of the victim's `swap_collateral` authorization. [10](#0-9) [11](#0-10)  If the victim signs the simulated transaction without detecting that extra child invocation, the unrelated wallet-token transfer executes and the swap can still satisfy the protocol's measured-output and risk checks. [12](#0-11) 

### Impact Explanation
An attacker who supplies a malicious route can cause the victim's signed strategy transaction to transfer arbitrary unrelated tokens from the victim to the attacker while still producing a nominally valid swap output. [13](#0-12)  This is theft of user funds beyond the collateral amount intentionally routed through the lending operation, so it is more than poor route quality or ordinary slippage. [14](#0-13) 

### Likelihood Explanation
Any unprivileged route producer can encode an attacker-deployed contract as a venue pool because hop addresses are payload inputs rather than an allowlisted registry. [6](#0-5)  The attack requires the victim to submit and sign a strategy transaction containing the malicious route, which is realistic where route bytes are generated by a quote service, aggregator UI, keeper, or copied transaction template and the unexpected authorization subtree is not clearly displayed. [15](#0-14) 

### Recommendation
Restrict router hop pools to a governance-approved venue registry or otherwise cryptographically bind each route to approved venue addresses before execution. [2](#0-1)  At a minimum, reject authorization trees containing any caller token transfer other than the exact strategy input pull expected by the controller, and make wallets/SDKs surface all nested authorization children before signing. [16](#0-15) 

### Proof of Concept
The repository contains an executable model of the attack in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`. [17](#0-16) 

1. Deploy a contract implementing the expected venue callbacks and store `(victim, wallet_token, attacker, amount)` in its state. [18](#0-17) 
2. Construct route bytes whose hop pool is that contract and whose `token_in`, `token_out`, and `min_out` produce a valid-looking swap. [19](#0-18) 
3. Have the victim invoke `swap_collateral(caller, account_id, current, from_amount, new, route)`. [20](#0-19) 
4. During venue dispatch, the malicious pool calls `wallet_token.transfer(victim, attacker, amount)`. [10](#0-9) 
5. Simulation records the transfer as a child of the victim's `swap_collateral` authorization rather than rejecting it as unrelated to the swap. [11](#0-10) 
6. After the signed transaction succeeds, the victim's unrelated wallet-token balance is zero, the attacker has received it, and the account still received the expected swap output. [12](#0-11)

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {

        let route = RoutedSwap::from_xdr(&env, &swap_xdr).expect("route must decode");
        let router = env.current_contract_address();

        token::Client::new(&env, &route.token_out).transfer(&router, &sender, &route.min_out);
        route.min_out
    }

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),

        )),
        sub_invocations: std::vec![stolen_transfer],
    };

    assert_eq!(s.wallet(&s.alice), 0);
