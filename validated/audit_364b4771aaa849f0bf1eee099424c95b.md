### Title
Uncaught-exception DoS in serial AA-trigger queue processing halts main-chain stabilization - (File: aa_composer.js)

### Summary
`handleAATriggers` in `aa_composer.js` processes the `aa_triggers` queue (populated whenever a unit sends outputs to an AA address) with `async.eachSeries`, invoking `handlePrimaryAATrigger` for each row one at a time. [1](#0-0) 
This function is called synchronously as part of `stabilizeMci`/`markMcIndexStable`/`saveJoint`'s MC-stabilization flow, i.e. it runs inside the critical path that advances main-chain stability for every node. [2](#0-1) [3](#0-2) 

This is structurally the same pattern as the reported `processWithdrawalQueue` bug: a serial, all-or-nothing loop over externally-triggerable queue entries, where a single bad entry can stop forward progress for the whole node.

### Finding Description
`handleTrigger` and its helper `validateAndSaveUnit` contain multiple `throw Error(...)` statements inside async callbacks (e.g. `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`, and the `"nonserial AA"` check on `objAAValidationState.sequence`). [4](#0-3) 
These are not passed to the `cb()`/`bounce()` error-handling path used for ordinary AA formula/bounce errors; they are raw JS `throw` statements executed inside asynchronous callbacks, which in Node.js become uncaught exceptions that crash the process (or, depending on the runtime, permanently abort the pending `async.eachSeries` chain without ever calling `onDone`).

Any unprivileged user can post a unit whose payment output targets an AA address, which unconditionally inserts a row into `aa_triggers` (no permission or amount screening at insertion time other than "non-private asset" and "not sent from another AA"). [5](#0-4) 
Because `handleAATriggers` walks this queue with `async.eachSeries` and the per-item connection/transaction is only released inside the success path, if a single trigger's execution throws instead of calling back, the `eachSeries` iteration series never completes: the final `function () { ...unlock(); onDone(); }` callback is never invoked, the `aa_triggers` mutex lock (`mutex.lock(['aa_triggers'], ...)`) is never released, and `onDone()` for the whole `handleAATriggers()` promise is never resolved. [1](#0-0) 
Since `stabilizeMci`/`saveJoint` `await`s `aa_composer.handleAATriggers()` before continuing (updating TPS fees, releasing connections, continuing to stabilize further MCIs, and eventually unlocking the write mutex), a stuck or crashing trigger permanently blocks:
- Processing of every other (unrelated, legitimate) trigger already queued for that MCI and any future MCI, since the `aa_triggers` mutex is never released.
- Advancement of main-chain stability past that MCI, and by extension the ability of the node to accept/finalize new units, because `saveJoint`'s write-mutex-protected flow never completes. [3](#0-2) 

This mirrors the report's core defect: a single misbehaving/attacker-crafted item in a serially-processed queue that must fully succeed for the loop to make forward progress, causing the entire pipeline (here: main-chain stabilization / AA processing for the whole node, not just a single vault) to freeze.

### Impact Explanation
If an attacker can construct a trigger unit or nested-AA response that reaches one of these `throw Error` branches (for example, forcing `objAAValidationState.sequence !== 'good'` via a crafted double-spend race on inputs consumed by the response unit, or another edge case reaching `ifNeedParentUnits`/`ifTransientError`), the resulting uncaught exception halts `handleAATriggers`, which halts main-chain stabilization node-wide. This is more severe than a single-vault freeze: it is a "network unable to confirm new units" condition for any node that processes the poisoned trigger, since the write/stabilization pipeline is serialized behind the AA-trigger queue.

### Likelihood Explanation
Reaching the network-wide freeze requires finding an input that actually causes one of the internal `throw Error` invariants to fire from externally influenced state (e.g., a race that makes the composed AA response unit non-serial, or an edge case in parent selection that requires unknown parent units). This is not proven with a concrete crafted payload in this scan — the invariant-violation paths are intended to be unreachable under normal validation, and I could not confirm within the available context that attacker-controlled trigger data can actually drive `handleTrigger`/`validateAndSaveUnit` into one of these `throw` branches (as opposed to the graceful `bounce()`/`cb(err)` paths that the code otherwise uses pervasively). Confirming likelihood requires deeper tracing of `updateInitialAABalances`, `pickParents`, and the double-spend/sequence-determination logic to find a concrete externally-triggerable path into one of the `throw Error` statements.

### Recommendation
- Wrap `handlePrimaryAATrigger`/`handleTrigger` per-item execution in `handleAATriggers`'s `async.eachSeries` with a defensive `try/catch` (or equivalent async error boundary) so that an unexpected internal error for one trigger cannot abort the whole queue or leave the `aa_triggers` mutex locked.
- Ensure the mutex acquired in `handleAATriggers` (`mutex.lock(['aa_triggers'], ...)`) is released via a `finally`-style guarantee even when a per-trigger processing step throws.
- Route the "should never happen" invariant violations (`ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`, `"nonserial AA"`) through the same recoverable-error path (`cb(err)`/skip-and-log) used elsewhere, rather than raw `throw Error`, at minimum for the AA-trigger execution context, so a single problematic trigger degrades gracefully instead of stalling MC stabilization for the entire node.

### Proof of Concept
Not established. I was not able to construct or confirm, from the indexed code alone, a concrete externally-triggerable input that reaches one of the `throw Error` branches in `validateAndSaveUnit`/`handleTrigger` (e.g., forcing `objAAValidationState.sequence !== 'good'`). A background Devin session with full repo/test access would be needed to trace `pickParents`, input/double-spend sequencing (`validation.js`), and `updateInitialAABalances` to determine whether an attacker-controlled trigger or crafted secondary-AA chain can deterministically drive one of these invariant-violation throws, which would turn this into a concrete, reproducible network-freeze exploit.
