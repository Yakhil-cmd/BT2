Based on the investigation, I found a concrete analog in the AA (Autonomous Agent) trigger execution path.

### Title
Dangling unit reference in `assocUnstableUnits`/`assocBestChildren` on AA response write failure — ([File: writer.js])

### Summary
`writer.saveJoint()` optimistically registers a new unit into the global in-memory caches `storage.assocUnstableUnits` and `storage.assocBestChildren` *before* the asynchronous follow-up operations (`updateBestParent`, `updateLevel`, `updateWitnessedLevel`, `main_chain.updateMainChain`, and `preCommitCallback`) complete. If any of those operations fails, the code path only calls `storage.resetMemory(conn)` and deletes `assocUnstableMessages[unit]` — it never calls `storage.forgetUnit(unit)`/`fixIsFreeAfterForgettingUnit()` to unlink the half-registered unit object from `assocBestChildren[parent]`, mirroring the exact bug class in the report: an object is added to a tracked list on the "happy path" of a multi-step registration, but the error-cleanup path takes a shortcut that does not walk back through the same removal function, leaving a stale/dangling reference to an object whose backing DB row was rolled back. [1](#0-0) [2](#0-1) 

### Finding Description
When `writer.saveJoint()` builds a new AA-response (or regular) unit, it immediately inserts the new unit props object into `storage.assocUnstableUnits[objUnit.unit]` and pushes the same object reference into `storage.assocBestChildren[my_best_parent_unit]` [3](#0-2) . This happens synchronously, prior to the `arrOps` async series that performs `updateMainChain`, `updateLevel`, `updateWitnessedLevel`, and `preCommitCallback` [4](#0-3) .

If any operation in `arrOps` returns an error, the transaction is rolled back and the "err" branch executes: it resets `headers_commission`, deletes `assocUnstableMessages[objUnit.unit]`, and calls `await storage.resetMemory(conn)` [5](#0-4) . Unlike the dedicated cleanup helper `storage.forgetUnit()` (used everywhere else in the codebase for this purpose — e.g. in `archiveJointAndDescendants` and `purgeUncoveredNonserialJoints`) [6](#0-5) [7](#0-6) , this path relies on `resetMemory`, whose implementation I could not locate/confirm in the indexed portion of `storage.js` — I was unable to verify whether it fully rebuilds `assocUnstableUnits`/`assocBestChildren` from the DB or is a narrower routine. This is the key unresolved uncertainty in this analysis; without confirming `resetMemory`'s scope, I cannot prove the stale-reference window is actually exploitable to corrupt subsequent AA processing versus being safely healed.

Separately, the dedicated AA-response cleanup function `revertResponsesInCaches()` — invoked from `handleTrigger`'s `revert()` when `updateStorageSize` fails after `addResponse()` already registered a response unit — only computes `parent_units` from the **first** response unit in `arrResponses`, then calls `fixIsFreeAfterForgettingUnit(parent_units)` once for that unit only, even though `arrResponseUnits.forEach(storage.forgetUnit)` forgets *all* accumulated response units in the chain (each of which may have distinct parent units, especially for chains involving secondary AA triggers) [8](#0-7) . This is structurally the same "partial/short-cut cleanup" pattern as the CVE: full removal (`forgetUnit`) is performed for every affected object, but the associated secondary state fix-up (`is_free` recomputation via `fixIsFreeAfterForgettingUnit`) is only applied to one out of potentially several parents, analogous to the missing `xe_hw_engine_group_del_exec_queue()` call for one of the two exec-queue linkage lists in the report.

### Impact Explanation
If the caches end up in an inconsistent state (a `assocUnstableUnits` entry present for a unit whose DB row was rolled back, or an `is_free` flag not correctly restored on a parent unit of an aborted AA response chain), subsequent AA trigger executions and stability/parent-selection logic (`pickParents`, `main_chain.updateMainChain`, best-parent computations) that read these caches could compute incorrect free/parent state. This could, in principle, lead to node disagreement about which units are free/spendable parents or bad AA-chain bookkeeping, which maps to the "node disagreement on validity or stability" / fund-accounting-affecting AA class in scope. However, I could not confirm an end-to-end concrete state corruption (e.g., a specific double-count or double-spend) because I lack visibility into `storage.resetMemory()`'s exact behavior.

### Likelihood Explanation
Triggering the `arrOps` failure path requires an untrusted AA trigger (postable by any address) whose execution reaches `writer.saveJoint()` for the AA's response unit and then fails a downstream operation (e.g., `updateMainChain`) or a `preCommitCallback`. AA triggers are fully attacker-controlled (any unit can trigger any AA), so the reachability bar is low, but actually forcing one of these specific internal operations to fail (as opposed to `evaluateAA`/formula-level errors, which are handled by `bounce()`/`revert()` earlier and don't reach this code) is non-trivial and would require a specific, currently-unidentified trigger condition.

### Recommendation
- Confirm the exact behavior of `storage.resetMemory()` and, if it does not fully purge the optimistically-added `assocUnstableUnits`/`assocBestChildren` entry for the failed unit, replace/augment the error-path cleanup in `writer.js` (around line 708-713) with an explicit `storage.forgetUnit(objUnit.unit)` + `storage.fixIsFreeAfterForgettingUnit(objUnit.parent_units)` call, matching the pattern used elsewhere in `storage.js`.
- In `aa_composer.js`'s `revertResponsesInCaches()`, compute and fix `is_free` for the parent units of **every** unit being forgotten (not just the first), e.g. by collecting the union of `parent_units` across all `arrResponseUnits` before calling `fixIsFreeAfterForgettingUnit`.

### Proof of Concept
I could not construct a concrete, verifiable end-to-end PoC without further confirming the internals of `storage.resetMemory()` (not found in the indexed portion of `storage.js`) and without being able to force one of the specific downstream `arrOps` (`updateMainChain`, `preCommitCallback`) to fail from an attacker-controlled AA trigger. Given the significant unresolved uncertainty about actual exploitability (as opposed to a code-hygiene inconsistency), this should be treated as a **candidate for further investigation** rather than a proven high/critical finding — a background engineering session with full repository/runtime access would be needed to trace `resetMemory()` and attempt to reproduce cache corruption via a crafted AA definition.
