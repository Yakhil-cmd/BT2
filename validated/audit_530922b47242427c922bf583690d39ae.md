### Title
Unrestricted, delay-free `address_definition_change` allows unilateral rewriting of shared/conditional address spending rules to defraud counterparties - (File: validation.js, definition.js, writer.js)

### Summary
Any address owner can attach an `address_definition_change` message that swaps the address's spending-condition definition for an arbitrary new one, and the change takes effect as soon as the unit becomes stable — with no cooling-off period and no way for counterparties who already deposited funds under the old definition to opt out. This mirrors the SetToken finding: a privileged party can silently change the rules governing funds that other users have already committed under different, agreed-upon terms.

### Finding Description
`address_definition_change` payloads are validated in `validateInlinePayload` in [1](#0-0) . The only checks performed are that the payload has the expected shape and that `definition_chash` is a syntactically valid address hash — there is no check that the new definition is "compatible" with, a subset of, or previously disclosed/committed to by the counterparties who rely on the address.

The change is recorded and takes effect through `address_definition_changes` as soon as the declaring unit stabilizes, as seen in `writer.js` [2](#0-1)  and `storage.readDefinitionChashByAddress`, which always returns the latest stable definition chash for an address [3](#0-2) . Authorization to redefine only requires satisfying the *current* definition's own authentifiers (via `validateAuthor` → `checkNoPendingChangeOfDefinitionChash`) [4](#0-3) , not any special separate approval from parties who transacted with the address under the old rules.

This is functionally identical to the SetToken bug class: a party (the manager / address controller) has a privileged ability to swap the "module"/definition governing funds, and no delay or notification window is enforced before the new rule becomes binding on everyone who already interacted with that address (e.g., deposited into it) trusting the previous condition. Definitions frequently encode conditional escape clauses meant as promises to counterparties — e.g. `in data feed`, `attested`, or `seen definition change` conditions (validated in `definition.js` [5](#0-4)  and evaluated at spend time in [6](#0-5) ). Because these are just boolean branches inside an `or`/`and` tree, whoever alone controls a branch sufficient to sign the *current* definition can redefine the whole address, stripping out the conditional branch that was supposed to protect other participants (e.g. "anyone can claim if data feed confirms event X" or "definition of address must be attested by escrow service Y"), before that branch is ever exercised.

### Impact Explanation
A user who deposits funds into a shared/conditional address (e.g. an escrow, bet, insurance-style payout, or crowd-funded pool secured by an `or` definition combining the operator's key with a fallback condition benefiting depositors) can have that fallback silently and instantly removed by the operator once their branch alone is sufficient to authorize a definition change. Since no delay exists between declaring the change and it becoming effective/spendable, depositors have zero window to react, withdraw, or dispute — resulting in direct unauthorized diversion/loss of already-committed funds. This is a concrete unauthorized-spending / fund-loss scenario matching the validation rules for this task.

### Likelihood Explanation
This requires no special privilege beyond what any address's own definition already grants its controller — no witness collusion, no hub/peer compromise, no protocol upgrade. Any address owner offering a "smart"/conditional address to third parties (a common oscript/definition pattern) can exploit this at will, making it a realistic, self-serviceable attack vector by an ordinary user acting in bad faith against counterparties who trusted the originally published/disclosed definition.

### Recommendation
Introduce a stabilization/notice delay between when an `address_definition_change` is declared and when it becomes effective for spending, proportional to how the address is used as a shared/conditional address (e.g. require some minimum number of MC indices or a fixed on-chain time delay before the new definition can be used to authorize spends), and/or require that funds sent to an address be tagged/locked to the definition chash that was current at deposit time so depositors relying on a specific condition are not retroactively affected by a later, unrelated redefinition. At minimum, wallets/AAs that treat definitions as durable commitments (e.g. escrow/bet contracts) should be warned that `address_definition_change` is instantaneous and unrestricted.

### Proof of Concept
1. Alice publishes address `A` with definition `["or", [["address", "ALICE_KEY"], ["in data feed", [["ORACLE"], "event_happened", "=", "1"]]]]`, advertising it as "anyone can claim once the oracle confirms the event" (e.g., a payout/insurance promise).
2. Bob and others send funds to `A`, relying on the oracle-condition branch to eventually unlock the funds if Alice refuses to pay.
3. Before the oracle posts the confirming data feed value, Alice — who alone can satisfy the `["address","ALICE_KEY"]` branch — posts an `address_definition_change` message for address `A` with a new `definition_chash` pointing to a definition consisting only of `["address","ALICE_KEY"]` (validated purely as an address-hash format check per [7](#0-6) ).
4. Once this unit stabilizes, `storage.readDefinitionChashByAddress` [3](#0-2)  resolves `A`'s definition to the new Alice-only definition; the oracle-condition escape clause Bob relied on is gone, with no delay or notice, and Alice can now spend all previously deposited funds unilaterally.

function readDefinitionChashByAddress(conn, address, max_mci, handle){
	if (!handle)
		return new Promise(resolve => readDefinitionChashByAddress(conn, address, max_mci, resolve));
	if (max_mci == null || max_mci == undefined)
		max_mci = MAX_INT32;
	// try to find last definition change, otherwise definition_chash=address
	conn.query(
		"SELECT definition_chash FROM address_definition_changes CROSS JOIN units USING(unit) \n\
		WHERE address=? AND is_stable=1 AND sequence='good' AND main_chain_index<=? ORDER BY main_chain_index DESC, level DESC LIMIT 1", 
		[address, max_mci], 
		function(rows){
			var definition_chash = (rows.length > 0) ? rows[0].definition_chash : address;
			handle(definition_chash);
	});
}
