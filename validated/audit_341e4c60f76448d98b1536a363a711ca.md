### Title
Unbounded accumulation of un-swept AA outputs can permanently break an Autonomous Agent's ability to compose payment responses - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload` (inside `sendUnit`) gathers spendable outputs belonging to an AA address via `readStableOutputs`/`readUnstableOutputsSentByAAs` and feeds every returned row into `iterateUnspentOutputs`, which unconditionally pushes each row into `payload.inputs` until the target amount is reached. Neither query applies a `LIMIT`, and there is no cap on how many outputs/inputs can be accumulated in a single response unit, unlike the analogous dust-gathering logic in `pickDivisibleCoinsForAmount` (`inputs.js`) which caps rows with `LIMIT constants.MAX_INPUTS_PER_PAYMENT_MESSAGE-2` [1](#0-0) , or `pickIndivisibleCoinsForAmount`, which explicitly checks `arrPayloadsWithProofs.length >= constants.MAX_MESSAGES_PER_UNIT - 1` and aborts with an error [2](#0-1) .

### Finding Description
Any unprivileged actor can send an unlimited number of small payments (each above the `FULL_TRANSFER_INPUT_SIZE` dust-exclusion threshold used in the query) directly to any AA address [3](#0-2) . Every one of these outputs stays "unspent" from the AA's perspective until the AA itself spends them in a response.

When the AA is triggered and needs to send a `send_all`/payment response, `readStableOutputs` selects **all** unspent, sequence-good outputs at the AA address with no `LIMIT` clause [4](#0-3) , and `readUnstableOutputsSentByAAs` likewise selects all unstable outputs sent by other AAs with no `LIMIT` [5](#0-4) . Both result sets are passed to `iterateUnspentOutputs`, which loops through every row and pushes an input for each one until `total_amount >= target_amount`, with no check against `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` or `constants.MAX_MESSAGES_PER_UNIT` [6](#0-5) .

This mirrors the reported bug class exactly: a per-entity collection (`lendingPoolDetail.activeProtectionIndexes` in the report; here, the set of unspent outputs owned by an AA address) grows without bound because an unprivileged party controls additions to it, and a critical function that must fully iterate the collection is invoked repeatedly (every AA response), with no mechanism to prune or cap it before iteration.

Because ocore units are size-limited and validated against `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` / message-count limits in `validation.js`, if an attacker sprays enough small outputs (e.g., via `send_all`-style micro-payments to the AA, each just above the dust threshold) so that clearing the AA's target amount requires collecting more inputs than fit in one message/unit, the composed response unit becomes invalid and `sendUnit` will fail/bounce. Since the same unswept outputs remain unspent and are re-selected on every subsequent trigger, the AA becomes permanently unable to produce a valid `send_all`/large payment response — its funds are effectively stuck behind an ever-growing set of dust-like outputs it can never fully consume in one unit.

### Impact Explanation
This can permanently freeze an AA's ability to pay out funds it legitimately owns, once its outstanding output set exceeds the per-unit input/message limits, since the composer greedily and un-cappedly tries to consume the entire unspent-output set in one message. This matches the accepted impact category "AA fund loss or freezing," since deposits/balances held by the AA can become permanently non-withdrawable through affected code paths, and the condition is triggerable by anyone able to send outputs to the AA's address (no privilege required).

### Likelihood Explanation
Any user or contract can send bytes/assets to a known AA address in small increments; this requires no special access and is economically feasible for an attacker who wants to disable a specific AA's payout capability (e.g., a competitor, or someone seeking to grief a DeFi-style AA on ocore). The condition worsens monotonically as more triggers/outputs accumulate, matching the "will stop working eventually" nature of the original report.

### Recommendation
Bound the number of outputs consumed per response the same way `pickDivisibleCoinsForAmount` and `pickIndivisibleCoinsForAmount` already do: add a `LIMIT` to the `readStableOutputs`/`readUnstableOutputsSentByAAs` queries (e.g., `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`), and make `iterateUnspentOutputs` stop and fail gracefully (bounce with an informative reason, or automatically split into a "sweep" pattern across multiple responses) once the accumulated inputs approach the per-unit limit, instead of attempting to fit unlimited outputs into a single payment message.

### Proof of Concept
1. Deploy/target an existing AA address `A`.
2. From many independent addresses (or one address across many units), send payments to `A` in small amounts just above `FULL_TRANSFER_INPUT_SIZE`/dust-exclusion thresholds, repeated thousands of times, so that `A` accumulates a huge number of unspent outputs.
3. Trigger `A` in a way that causes it to issue a `send_all` or large payment response requiring more than `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` inputs to satisfy from its available unspent outputs (verifiable via `validation.js`'s enforcement of that constant, referenced at [7](#0-6) , though exact line could not be pinned down in this session).
4. Observe that `completePaymentPayload`/`iterateUnspentOutputs` in `aa_composer.js` gathers all rows without limiting count, producing an oversized/invalid payload that fails unit validation, bouncing the AA response.
5. Confirm that because the same unspent outputs remain unspent, every subsequent trigger requiring similar payout logic repeats the same failure, permanently freezing that payout path for AA `A`.

Note: I was not able to fully confirm within this session the exact line number in `validation.js` where `MAX_INPUTS_PER_PAYMENT_MESSAGE`/`MAX_MESSAGES_PER_UNIT` limits are enforced against composed AA-response units (only that matches exist in that file) — a full Devin session with file access would be needed to pinpoint that exact validation path and confirm the precise unit-size/message-count threshold at which `sendUnit` responses begin failing.
