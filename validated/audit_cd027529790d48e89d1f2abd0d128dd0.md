## Title
Webhook signature is verified against the payload's `repository.owner.login`, but the acted-upon repository is looked up from `repository.full_name` — signature scope and write target are not bound - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub-app secret to verify against based on `repository_owner`, which is extracted from the untrusted payload itself (`params.dig('repository', 'owner', 'login')`), while every event handler resolves the stack/repository to act on from a *different* payload field, `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`). These two fields are never cross-checked against each other, so the field that determines *whose secret authenticates the request* is decoupled from the field that determines *which repository's stacks get mutated*.

### Finding Description
`verify_signature` computes the org used for HMAC verification purely from attacker-supplied JSON: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
``` [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback). Meanwhile, every `Handler` subclass resolves the actual `stacks` to modify using a *separate* field, `repository.full_name`: [3](#0-2) 

For a multi-organization Shipit deployment, each organization has its own `webhook_secret` (`lib/shipit/github_app.rb:50`, `lib/shipit.rb:196-200`). Since the JSON body is fully attacker-controlled prior to verification, an attacker who is a legitimate GitHub App/webhook sender for `OrgA` (i.e., knows `OrgA`'s `webhook_secret`, e.g. because they administer a repo hosted under OrgA that is *also* configured in this Shipit instance) can craft a payload where:
- `repository.owner.login = "orga"` (so `verify_signature` picks `OrgA`'s secret and the HMAC — computed by the attacker with the real `OrgA` secret over this exact body — validates), and
- `repository.full_name = "orgb/victim-repo"` (a completely different, victim organization's repository that also has a `Stack` configured in this instance).

Because `verify_signature` never checks that `repository.owner.login` matches `repository.full_name`'s owner segment, and the handler layer only consults `full_name`, the signed-and-verified request (verified under OrgA's trust) is dispatched to act on OrgB's stacks. For `push`, this triggers `stack.sync_github(expected_head_sha: params.after)` on `orgb/victim-repo`'s stacks — an attacker-chosen `after` SHA is treated as the "expected head", which is the exact push/sync trust decision that governs whether a deploy proceeds against that revision — using a signature the victim org never produced and a secret the victim org never leaked.

### Impact Explanation
This breaks the binding "organization whose secret authenticated the webhook == repository whose stacks are written to by the webhook", which is exactly the trust-binding class the analog targets. An attacker with legitimate/valid credentials for one configured organization can forge webhook events (`push`, `status`, `check_suite`, `membership`, `pull_request`) that are processed as authenticated for a different organization's stacks, without ever possessing that victim organization's `webhook_secret`. Depending on which handler is targeted this can influence sync/merge/CI state for another repository's stacks (`PushHandler`, `StatusHandler`, `CheckSuiteHandler` all key off `Handler#stacks`, i.e., `full_name`), which can affect what SHA is considered deployable and cross-repository state — landing in the "cross-repository writes" impact bucket via a genuine authentication-binding failure, not a configuration mistake.

### Likelihood Explanation
Requires: (a) a Shipit instance configured with multiple GitHub organizations each having their own `webhook_secret`, and (b) the attacker legitimately controls/administers at least one org configured in that instance (so they know that org's secret) while another org's repo is also tracked. This is a realistic multi-tenant Shipit deployment scenario and needs no privileged Shipit credentials, no `ApiClient` token, and no access to the victim's secret — only knowledge of one's own org's webhook secret, which is not itself privileged relative to Shipit.

### Recommendation
In `WebhooksController#verify_signature`, derive the organization used for verification the same way the handler derives the acted-upon repository (from `repository.full_name`'s owner segment, or `organization.login`), and reject the request if `repository.owner.login` (when present) does not match the owner segment of `repository.full_name`. Equivalently, make `Handler#repository_name` and `WebhooksController#repository_owner` reference the exact same trusted field so the org used for HMAC verification is provably the owner of the repository that will be mutated.

### Proof of Concept
1. Configure Shipit with two orgs, `orga` (secret `S_A`) and `orgb` (secret `S_B`), each with a tracked stack (`orga/repoA`, `orgb/repoB`).
2. Attacker (who administers `orga` and thus knows `S_A`) builds a `push` JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "orgb/repoB",
    "owner": { "login": "orga" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, body)>` using the legitimately-known `S_A`.
4. `WebhooksController#verify_signature` computes `repository_owner` = `"orga"` from the body, fetches `Shipit.github(organization: "orga")`, and verifies the HMAC using `S_A` — which succeeds, since the attacker signed with the real `S_A`.
5. `create` dispatches to `PushHandler`, which calls `Handler#stacks`, resolving `Repository.from_github_repo_name("orgb/repoB")` — i.e., the victim org's stacks — and invokes `stack.sync_github(expected_head_sha: params.after)` on them, despite the request never being signed by `orgb`'s secret `S_B`.
