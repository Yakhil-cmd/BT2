### Title
Attacker-controlled swap route can inject unauthorized token transfers into the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy operations accept caller-supplied opaque swap bytes and pass them to the configured router while executing under the caller’s authorization. Because the controller only constrains its own input-token transfer and measured output, a malicious route can place arbitrary token transfers from the caller inside the transaction’s simulated authorization tree. If the caller signs that generated tree, the unrelated transfer executes even though it is unnecessary for the lending operation. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all accept caller-controlled `swap` bytes and require owner or delegate authorization. [3](#0-2) [4](#0-3) [5](#0-4) 

The controller authorizes only the exact `token_in.transfer(controller, router, amount_in)` invocation that the router needs. [6](#0-5) [7](#0-6) 

However, it treats the route as opaque and does not constrain which pool, token, or other contract calls occur beneath the router invocation. [8](#0-7) 

A malicious route can therefore include a third-party contract that invokes `token.transfer(caller, attacker, amount)` while the caller-authorized strategy call is active. [9](#0-8) 

Transaction simulation records that transfer as a child authorization under the caller’s strategy invocation; if the caller signs the complete simulated tree, the malicious transfer succeeds. [2](#0-1) 

The controller’s post-call checks only reject input growth, spending above `amount_in`, and missing positive output; they do not detect that route code transferred unrelated caller assets. [10](#0-9) 

### Impact Explanation
A malicious route can steal any token balance for which the victim signs a malicious child `transfer` authorization while performing an otherwise valid lending strategy. [11](#0-10) 

This is theft of user funds outside the routed collateral or debt amount, and the final account-risk checks do not bound the additional wallet transfer. [12](#0-11) 

### Likelihood Explanation
The attack requires the victim or an authorized delegate to submit and sign a transaction containing the malicious route and its generated authorization tree. [13](#0-12) 

That is plausible where routes are produced by an external quoter or UI and the signer does not inspect every nested authorization. [14](#0-13) 

The attacker does not need protocol privileges, leaked keys, upgraded contracts, or control over the configured router; control over the submitted route is sufficient. [15](#0-14) 

### Recommendation
Do not expose unbounded user-selected execution environments under the caller’s strategy authorization. [8](#0-7) 

Constrain routes to governance-approved pool and token addresses, or provide a decoded route manifest that the controller can validate before invoking the router. [16](#0-15) 

At minimum, wallets and integrations should decode the route and reject any authorization tree containing child invocations beyond the expected strategy call and input transfer. [7](#0-6) 

### Proof of Concept
1. A victim owns a debt-free account with supplied USDC and also holds an unrelated token `WALLET` in the same Stellar address.
2. The attacker deploys a contract whose route-selected pool callback invokes `WALLET.transfer(victim, attacker, victim_balance)`.
3. The attacker supplies that contract address inside the `swap` argument to `swap_collateral(caller=victim, account_id, current=USDC, amount, new=ETH, swap=malicious_route)`.
4. `process_swap_collateral` authenticates the victim, verifies account ownership or delegation, withdraws USDC, and calls `swap_tokens` with the attacker-controlled bytes. [17](#0-16) 
5. `swap_tokens` authorizes only the expected controller-to-router input transfer and invokes the router while the victim’s authorization context is active. [6](#0-5) 
6. During route execution, the malicious pool calls `WALLET.transfer(victim, attacker, victim_balance)`; simulation places that transfer beneath the victim’s `swap_collateral` authorization. [2](#0-1) 
7. The malicious route still returns enough ETH for the controller to observe a positive output and pass final account risk. [10](#0-9) [12](#0-11) 
8. If the victim signs the simulated tree, the strategy succeeds, the victim receives the swapped collateral, and the attacker also receives the victim’s unrelated `WALLET` balance. [10](#0-9)

pub(crate) fn swap_tokens(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    require_positive_amount(env, amount_in);
    assert_with_error!(env, !swap.is_empty(), GenericError::InvalidPayments);

    let controller = env.current_contract_address();
    let router_addr = storage::get_swap_aggregator(env);
    let router = SwapAggregatorClient::new(env, &router_addr);
    let token_in_client = token::Client::new(env, token_in);

    // Snapshot before router execution to measure its spend and output.
    let in_before = token_in_client.balance(&controller);
    let out_before = token::Client::new(env, token_out).balance(&controller);

    // Authorize only this token transfer to this router for this exact amount.
    authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);

    storage::with_flash_guard(env, || {
        let _ = router.execute_strategy(&controller, &amount_in, swap);
    });

    // Reject input gains or overspending; refund only this swap's unused input.
    let in_after = token_in_client.balance(&controller);
    assert_with_error!(env, in_after <= in_before, StrategyError::RouterOverspend);
    let actual_spent = in_before - in_after;
    assert_with_error!(
        env,
        actual_spent <= amount_in,
        StrategyError::RouterOverspend
    );
    let leftover = amount_in - actual_spent;
    if leftover > 0 {
        token_in_client.transfer(&controller, refund_to, &leftover);
    }

    verify_router_output(env, token_out, out_before)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
