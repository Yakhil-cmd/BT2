## Title
Webhook signature is bound only to the sending organization's secret, not to the repository the event writes to — cross-repository CI-status forgery leading to unauthorized deploy triggers - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The reported bug class is a "verified-versus-acted-upon" mismatch: Chainlink's price feed (verified/trusted input) diverges from the actual Dex state (what is acted upon), letting an attacker exploit the gap between what was validated and what actually gets moved. The reachable analog in this engine is a mismatch between **which organization's secret validated a webhook's HMAC signature** and **which repository/commit the resulting handler actually mutates**.

### Finding Description
`WebhooksController#verify_signature` picks the HMAC secret to validate against using only the `repository.owner.login` (or `organization.login`) field taken from the *unverified-until-this-point* JSON body, then verifies the whole raw body with that org's secret: [1](#0-0) [2](#0-1) 

Because the HMAC only proves "this payload was signed with organization X's webhook secret," it says nothing about whether the *content* the handlers act on (a `sha`, a `full_name`, etc.) actually belongs to organization X. `Shipit.github_app_config` shows this engine explicitly supports multiple independent organizations, each with its own `webhook_secret`: [3](#0-2) 

Once the signature is accepted, `StatusHandler#process` looks up commits **globally by `sha` alone**, with no scoping to the repository/organization whose secret validated the request: [4](#0-3) 

Contrast this with `PushHandler`, which at least scopes to `stacks` derived from `payload.dig('repository', 'full_name')`: [5](#0-4) [6](#0-5) 

The binding that should hold is:
`organization whose secret authenticated the request == organization/repository whose state is written`

`StatusHandler` breaks this equality outright (no repository scoping at all — any known commit SHA anywhere in the Shipit instance can be targeted), and even `PushHandler`/`Handler#stacks` only checks the `full_name` embedded in the *same signed body*, without cross-validating it against the `repository.owner.login` used to pick the secret — so a body can be crafted (and signed with organization A's own legitimate secret) where `repository.owner.login = "A"` (used for signature selection) while `repository.full_name = "B/victim-repo"` (used for the actual write), since both fields live inside the one raw body that A can freely construct and sign with its own key.

### Impact Explanation
This is reachable by anyone who legitimately controls a webhook secret for **any single organization/repository** tracked by the Shipit instance (i.e., an org admin of one of many onboarded orgs — not a Shipit session, not an `ApiClient` token, not the app's own GitHub App key). Using that legitimately-owned secret, they can forge a `status` webhook event for a commit `sha` belonging to a **different** organization's stack. `Commit#create_status_from_github!` records the forged CI state ("success") directly into the database as if GitHub had reported it, without ever calling GitHub's API to validate it: [4](#0-3) 

If the target stack has continuous deployment enabled, a forged "success" status can flip the commit's aggregate status to deployable, and `Commit#schedule_continuous_delivery` enqueues an automated deploy: [7](#0-6) 

This maps to the Critical impact category "an unauthorized deploy" — an attacker with no privileges on the victim repository/stack can trigger a deploy of it by exploiting the fact that signature verification is bound to organization identity while the write path (`Commit.where(sha:)`) is bound to nothing at all.

### Likelihood Explanation
Requires only ownership of one legitimate webhook secret for any org/repo tracked by the Shipit instance — no access to the victim's secrets, sessions, or GitHub credentials, and no reliance on the host misconfiguring or not mounting the engine. In any Shipit deployment onboarding more than one organization (explicitly supported per `github_app_config`), this is directly exploitable. I was not able to fully trace the exact call site that transitions a `Status` write into `schedule_continuous_delivery` within `app/models/shipit/status.rb` (I could not retrieve its full contents), so the automated-deploy trigger chain is inferred from `Commit#schedule_continuous_delivery`'s guard conditions rather than confirmed end-to-end; the unscoped-by-repository `Commit.where(sha:)` write itself, however, is directly confirmed in the code shown above.

### Recommendation
- In `StatusHandler#process` (and any other handler that doesn't already do so), scope the `Commit` lookup to the stacks belonging to `repository_name`/`repository_owner` derived from the same verified payload, mirroring `Handler#stacks`.
- In `WebhooksController#verify_signature`, after signature verification, assert that `repository_owner` (used to select the secret) is consistent with the organization component of `repository.full_name`, rejecting payloads where they diverge.

### Proof of Concept
1. Attacker legitimately owns/administers `OrgA`, which is one of several organizations configured under `Shipit.secrets.github` with its own `webhook_secret`.
2. Attacker crafts a `status` event JSON body with `sha` set to a known commit SHA belonging to `OrgB`'s tracked stack (commit SHAs are visible via the public/private repo history or CI logs) and `state: "success"`.
3. Attacker computes `X-Hub-Signature` using `OrgA`'s own `webhook_secret` (via `Hook::DeliverySigner`/`OpenSSL::HMAC` logic mirrored in `verify_webhook_signature`).
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` using the payload's `repository.owner.login` = `"OrgA"`, and the signature check passes since it truly was signed with `OrgA`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit (no ownership check), and calls `commit.create_status_from_github!(params)`, recording a forged "success" CI status on a commit the attacker does not control.
6. If `OrgB`'s stack has continuous deployment enabled and this pushes the commit to "deployable," `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, triggering an unauthorized deploy of `OrgB`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
