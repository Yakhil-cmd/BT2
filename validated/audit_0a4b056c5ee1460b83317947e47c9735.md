### Title
Service Chain Bridge Value Transfer Recovery Disabled by Default — Single Operator with No Automatic Retry on Tx Drop - (File: `node/sc/sub_bridge_handler.go`, `node/sc/config.go`)

### Summary

The Kaia service chain bridge relies on a single `SubBridge` node (hard-coded `MaxPeer: 1`) and a single operator account (`pAccount`) to relay all value transfers between the service chain and the parent chain. When a bridge handling transaction is rejected by the parent chain (e.g., `ErrGasPriceBelowBaseFee`), the transaction is silently removed from the `BridgeTxPool`. The only recovery path — `VTRecovery` — is **disabled by default** in `DefaultServiceChainConfig`. This means that in the default deployment, a dropped value-transfer handling transaction leaves the user's bridged assets permanently locked in the source-chain bridge contract with no automatic retry.

---

### Finding Description

**Root cause — `node/sc/config.go`:**

`DefaultServiceChainConfig` returns an `SCConfig` where `VTRecovery` is the Go zero-value `false`. No other field enables recovery.

```go
func DefaultServiceChainConfig() *SCConfig {
    return &SCConfig{
        NetworkId: 1,
        MaxPeer:   1, // Only a single main-bridge and sub-bridge pair is allowed.
    }
}
``` [1](#0-0) 

**Single-operator account — `node/sc/bridge_accounts.go`:**

`BridgeAccounts` holds exactly one `pAccount` (parent operator) and one `cAccount` (child operator). All bridge transactions are signed by this single key.

```go
type BridgeAccounts struct {
    pAccount *accountInfo
    cAccount *accountInfo
    db       feePayerDB
}
``` [2](#0-1) 

**Tx-drop path with no retry — `node/sc/sub_bridge_handler.go`:**

When the parent chain rejects a bridge tx with `ErrGasPriceBelowBaseFee`, the handler removes the tx from the pool. The code comment explicitly acknowledges the gap:

``` [3](#0-2) 

**VTRecovery guard — `node/sc/vt_recovery.go`:**

`Start()` returns `ErrVtrDisabled` immediately when `config.VTRecovery == false`, so no recovery goroutine is ever launched in the default configuration.

```go
func (vtr *valueTransferRecovery) Start() error {
    if !vtr.config.VTRecovery {
        return ErrVtrDisabled
    }
``` [4](#0-3) 

**`AddRecovery` also short-circuits — `node/sc/bridge_manager.go`:**

```go
func (bm *BridgeManager) AddRecovery(localAddress, remoteAddress common.Address) error {
    if !bm.subBridge.config.VTRecovery {
        logger.Info("value transfer recovery is disabled")
        return nil
    }
``` [5](#0-4)

### Impact Explanation

A user initiates a `requestKLAYTransfer` / `requestERC20Transfer` on the child-chain bridge contract, locking their KAIA or ERC-20 tokens. The single SubBridge operator picks up the `RequestValueTransfer` event and submits a `handleKLAYTransfer` (or equivalent) transaction to the parent-chain bridge. If the parent chain's base fee has risen above the operator's cached gas price, the parent-chain node rejects the tx and sends back a `ServiceChainInvalidTxResponse`. The SubBridge handler removes the tx from `BridgeTxPool`. With `VTRecovery = false` (the default), no goroutine re-scans the bridge contract logs and re-submits the pending transfer. The user's assets remain locked in the child-chain bridge contract indefinitely, with no on-chain mechanism to release them.

The corrupted state is: `bridge.requestNonce > bridge.lowerHandleNonce` on the parent-chain bridge — i.e., there are unhandled requests — while the SubBridge's pool is empty and no recovery is running.

---

### Likelihood Explanation

The trigger is realistic: any base-fee spike on the parent chain (Kaia mainnet) between the time the operator caches the gas price and the time the tx is submitted causes `ErrGasPriceBelowBaseFee`. The Magma hard fork introduced dynamic base fees, making this scenario more likely than in the fixed-unit-price era. The default `MaxPeer: 1` means there is no redundant SubBridge node to compensate. [6](#0-5) 

---

### Recommendation

1. **Enable `VTRecovery` by default** in `DefaultServiceChainConfig`:
   ```go
   return &SCConfig{
       NetworkId:          1,
       MaxPeer:            1,
       VTRecovery:         true,
       VTRecoveryInterval: 60,
   }
   ```
2. **Add a retry path for all bridge tx types** in `handleParentChainInvalidTxResponseMsg`, not just value-transfer txs covered by VTRecovery. Anchoring txs currently have no retry at all.
3. **Document the manual recovery runbook** (re-enable VTRecovery, or call `subbridge_getUnhandledRequestEvents` and re-submit) so operators can act when the automated path is absent.
4. **Consider allowing `MaxPeer > 1`** so a secondary SubBridge node can take over if the primary fails.

---

### Proof of Concept

1. Deploy a service chain with the default `SCConfig` (`VTRecovery: false`).
2. User calls `requestKLAYTransfer` on the child-chain bridge, locking 1 KAIA. The child-chain bridge emits `RequestValueTransfer(nonce=N)`.
3. The SubBridge operator builds a `handleKLAYTransfer` tx with the cached (stale) gas price and broadcasts it to the parent chain.
4. The parent chain's base fee has risen; the tx is rejected with `ErrGasPriceBelowBaseFee`. The main bridge sends `ServiceChainInvalidTxResponse` back.
5. `handleParentChainInvalidTxResponseMsg` calls `BridgeTxPool.RemoveTx(tx)`. The pool is now empty.
6. Because `VTRecovery == false`, `AddRecovery` returned early at startup and no recovery goroutine exists.
7. Verify: `subbridge_getUnhandledRequestEvents` returns nonce N as pending. The user's 1 KAIA remains locked in the child-chain bridge contract. No automatic mechanism releases it.
