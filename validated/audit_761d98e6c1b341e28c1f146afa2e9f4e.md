### Title
AA asset `cap` formulas bypass `MAX_CAP` validation at definition time, permanently bricking that asset's issuance path - ([File: aa_validation.js])

### Summary
When an Autonomous Agent (AA) defines an `asset` message, a numeric `cap` is bound-checked against `constants.MAX_CAP` at AA-definition time, but a formula-based `cap` (e.g. `cap: "{trigger.data.cap}"`) is not, since only the syntax of the formula is validated [1](#0-0) . When the AA is triggered and actually issues that asset, `aa_composer.js` uses the evaluated `objAsset.cap` verbatim as the issue amount [2](#0-1) . The resulting payment message is then subject to the network-wide unit validation rule that rejects any issue input whose amount exceeds `MAX_CAP` [3](#0-2) . Because the two checks are inconsistent (one enforced at definition, the other only at usage), an AA whose formula-derived cap evaluates above `MAX_CAP` can never successfully issue that asset — exactly the same "unchecked-at-init, checked-at-use" pattern as the reported Sense `ifee`/`ISSUANCE_FEE_CAP` bug.

### Finding Description
`validateAADefinition` in `aa_validation.js` handles the `asset` app message. For a numeric `cap`, it enforces `isPositiveInteger(payload.cap) && payload.cap <= constants.MAX_CAP`. For a string (formula) `cap`, it only checks that the string parses as a valid formula — there is no bound on what the formula could evaluate to at runtime [1](#0-0) . Formula-based caps are an explicitly supported, common pattern, as shown by AA test fixtures such as `cap: "{trigger.output[[asset=base]]}"` and `cap: "{trigger.data.cap otherwise ''}"` [4](#0-3) [5](#0-4) , meaning the cap value is fully attacker/trigger-controllable up to whatever the AA's own logic allows.

Later, when the AA is triggered to issue units of this asset, `aa_composer.js`'s `issueAsset()` takes `objAsset.cap` (the evaluated value) directly as the `issue_amount` for the `type: "issue"` input, without re-checking it against `MAX_CAP` [2](#0-1) . The composed response unit then goes through standard consensus validation in `validatePaymentInputsAndOutputs`, where any issue input greater than `constants.MAX_CAP` is rejected outright with `"issue amount too large"` [3](#0-2) .

Because the AA-definition-time check for formula caps never bounds the eventual runtime value, an AA author can unintentionally (or a malicious trigger author can, if the cap formula derives from trigger data/state and is not independently bounded by the AA's own logic) cause the evaluated cap to exceed `MAX_CAP`. From that point on, every attempt by the AA to issue that asset fails validation and the AA response bounces, permanently breaking the asset-issuance code path defined in that AA.

### Impact Explanation
This freezes the AA's fund/asset-issuance functionality for the affected asset: any trigger that reaches the `asset`-issuing branch of the AA will always fail unit validation and bounce (with bounce fees consumed from the triggering party), and the asset can never be issued through that code path. This is a permanent denial of an important AA function analogous to Divider.issue() being permanently non-functional in the reference report — it is a fund/functionality freezing bug reachable purely from a posted AA definition plus a subsequent trigger, with no privileged access required.

### Likelihood Explanation
Formula-based `cap` values are a normal, documented AA feature (seen in the project's own test suite and samples), so this is not a contrived edge case. Any AA author who derives `cap` from `trigger.data`, `trigger.output`, or state variables without independently clamping it to `MAX_CAP` will hit this bug the first time a trigger causes the evaluated cap to exceed the limit — after which the AA's issuance functionality for that asset is permanently broken. The `bAssetDefinition` validation logic gives no early warning of the misconfiguration, since it only validates that the field is a well-formed formula, not its bounded runtime output.

### Recommendation
Enforce `MAX_CAP` at the point where the AA's asset `cap` formula is evaluated for use in the actual asset definition message (in `aa_composer.js`, before composing the `asset` app message), rejecting/bouncing early with a clear error rather than allowing an unbounded value to be committed as the asset's cap. Alternatively, add a runtime check in `issueAsset()` (`aa_composer.js`) that validates `objAsset.cap <= constants.MAX_CAP` before using it as `issue_amount`, so the failure is surfaced immediately when the asset is defined rather than silently bricking every future issuance attempt.

### Proof of Concept
1. An AA author defines (or a trigger dynamically parameterizes) an `asset` app message with `cap: "{trigger.data.cap}"` similar to the pattern in `test/samples/create_an_asset.oscript` [5](#0-4) .
2. A user (or the AA's own internal logic) triggers the AA with `trigger.data.cap` set to a value greater than `constants.MAX_CAP`. Because only formula syntax is checked at definition time [1](#0-0) , the asset definition message is accepted with this oversized cap.
3. On a subsequent trigger that causes the AA to issue this asset, `issueAsset()` sets `issue_amount = objAsset.cap` (the oversized value) and composes an issue input with that amount [6](#0-5) .
4. When this composed unit is validated, `input.amount > constants.MAX_CAP` triggers rejection of the payment message [7](#0-6) , causing the AA response to bounce every time this code path is executed, permanently disabling the AA's ability to issue that asset.
