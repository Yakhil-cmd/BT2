## Analog Found [1](#0-0) 

### Title
CCMenu API endpoint ignores `ApiClient#stack_id` scope, letting a stack-scoped token read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
Like the merit-circle bug where `curve.length` changed but the derived `unit` was never recalculated, `Shipit::Api::CCMenuController` redefines `stack` to bypass the client-scoping logic that `Api::BaseController` otherwise enforces, so the "stack a token authorises" and "stack it actually touches" fall out of sync.

### Finding Description
`Api::BaseController` implements token scoping for stack-restricted `ApiClient`s: [2](#0-1) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the client is scoped to a single stack, and every other API controller (`Api::StacksController`, `Api::MergeRequestsController`, `Api::TasksController`, etc.) resolves the target stack through this scoped `stacks` relation via `stack`.

`Api::CCMenuController`, however, overrides `stack` and resolves it directly from the global `Stack` collection, ignoring the api-client scoping entirely: [3](#0-2) 

It also overrides `authenticate_api_client` to accept the token from a `token` query-string parameter instead of a `Basic` auth header, which is exactly the intended flow for CCMenu/CI badge-style clients minted by `CCMenuUrlController`: [4](#0-3) 

Those clients are created with `permissions: %w[read:stack]` and a `stack_id` set to a single stack — the entire design intent is that this token can only report status for that one stack (e.g. embedded in a README badge or CI dashboard URL). `require_permission :read, :stack` only checks the generic permission string via `ApiClient#check_permissions!`: [5](#0-4) 

`check_permissions!` never inspects `stack_id`; the per-stack restriction is supposed to be enforced purely by the controller resolving `stack` through the scoped `stacks` collection — which `CCMenuController` does not do.

**Binding broken (equality)**
- Before: `token.stack_id == A` and the controller only ever serves `stack == A`.
- After: an attacker holding a token minted for stack `A` sends `GET /api/stacks/:stack_id/cc_menu.xml?token=<A's token>&stack_id=B`. `authenticate_api_client` authenticates the token (valid, scoped to `A`), but `stack` resolves `Stack.from_param!(params[:stack_id])` = `B`, unrelated to the token's `stack_id`.
- The binding `token.stack_id == stack_served` is broken: `A != B`.

### Impact Explanation
This is an authorization-scope escalation: a token intentionally minted to expose build status for a single stack (and typically distributed in a semi-public context, such as a CI status badge URL) can be reused to read `deploys_and_rollbacks`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` for every stack in the Shipit instance, including ones the token holder was never meant to see. This matches the "unauthenticated/unauthorized read of stack state" High-impact category — the token is not a general API credential but a narrowly-scoped, low-trust one, and this bug voids that scoping.

### Likelihood Explanation
Any holder of a legitimately-issued CCMenu token (which is routinely embedded in URLs, dashboards, or README badges — exactly the class of "low sensitivity" tokens the `stack_id` scoping mechanism exists to constrain) can trivially exploit this by changing the `stack_id` route parameter. No additional secret, session, or privilege is required beyond possessing one such token, which itself requires no privileged Shipit account (it can be generated by any authenticated Shipit user for a stack via `CCMenuUrlController#fetch`, and then leaked/shared without granting recipients real user access).

### Recommendation
Have `Api::CCMenuController#stack` resolve through the same scoped `stacks` collection used by `Api::BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` can never resolve a stack outside its `stack_id`.

### Proof of Concept
1. As a legitimate Shipit user, visit a stack `A` and let the app mint a CCMenu client via `CCMenuUrlController#fetch`, producing a URL like `.../api/stacks/A/cc_menu.xml?token=<T>` where `T` is scoped to `stack_id = A` with `permissions: [read:stack]`.
2. Share/leak `T` (as intended, e.g. in a README badge).
3. An attacker who only has `T` requests `.../api/stacks/B/cc_menu.xml?token=<T>` for an arbitrary other stack `B`.
4. `authenticate_api_client` succeeds (valid signature for `T`), `require_permission :read, :stack` succeeds (generic permission present), and `stack` resolves `B` directly via `Stack.from_param!`, returning `B`'s deploy/build status — despite `T` being scoped to `A` only.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
