### Title
Precision-loss integer overflow in asset cap/denomination validation allows supply-inflating asset issuance - ([File: validation.js])

### Summary
`validateAssetDefinition` in `validation.js` validates each `denomination`/`count_coins` pair with only lower-bound and per-field checks (`isPositiveInteger`, `denomination <= MAX_CAP`), but `count_coins` itself has **no upper bound**. The accumulated `total_cap_from_denominations` is computed as a plain JS floating-point multiplication/addition and later compared for exact equality against `payload.cap`. [1](#0-0) 

### Finding Description
```js
if (!isPositiveInteger(denomInfo.denomination))
    return callback("invalid denomination");
if (denomInfo.denomination > constants.MAX_CAP && (...))
    return callback("denomination exceeds MAX_CAP");
...
if ("count_coins" in denomInfo){
    if (!isPositiveInteger(denomInfo.count_coins))
        return callback("invalid count_coins");
    total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;
}
``` [2](#0-1) 

`denomInfo.denomination` is bounded by `MAX_CAP`, but `denomInfo.count_coins` is only checked to be a positive integer — no upper bound is enforced, exactly like the TensorFlow `axis` parameter that was checked `>= -1` but never bounded above before being used in `axis + 1` arithmetic. Because JavaScript numbers are IEEE-754 doubles, `count_coins * denomination` for an attacker-chosen huge `count_coins` (e.g. `count_coins` near `Number.MAX_SAFE_INTEGER / denomination`) can silently lose precision and produce a value that is later compared byte-for-byte to `payload.cap`: [3](#0-2) 

Since `payload.cap` is separately bound-checked to `<= MAX_CAP` (line 2735), while `count_coins` has no such bound, an attacker can choose `count_coins`/`denomination` pairs whose true product exceeds `MAX_CAP` (and even exceeds `Number.MAX_SAFE_INTEGER`) but whose floating-point-rounded value happens to equal a small, `MAX_CAP`-compliant `payload.cap`. The equality check at line 2790 passes because it operates on the rounded double, not the true mathematical product. [4](#0-3) 

This corrupted/undercounted `total_cap_from_denominations` (and the individual `count_coins` figures) are persisted into the `asset_denominations` table and later used to gate actual coin issuance: `validateIndivisibleIssue` checks `input.amount !== denomination * denomInfo.count_coins` when issuing capped fixed-denomination assets. [5](#0-4) 

Because the same double-precision multiplication is used both at definition time and at issuance time, the two computations are internally consistent with each other but inconsistent with the asset's declared, validated `cap`. The net effect is that the enforced cap accounting is decoupled from the real intended cap, allowing more total value to be issued across the denomination's coins than the cap was supposed to permit.

### Impact Explanation
This breaks the fundamental capped-supply invariant of a fixed-denomination asset: units can be crafted so that the declared cap check passes validation while the actual issuable supply (`count_coins * denomination` summed over all denominations) is effectively unbounded relative to the stated cap. Every validating node performs the identical floating-point arithmetic, so this is not a validity divergence between nodes — it is a systemic supply-inflation bug reachable by any user who defines an asset (an unprivileged unit poster), qualifying as "supply inflation" per the validation rules.

### Likelihood Explanation
Exploitation requires only posting an `asset` definition message with `fixed_denominations: true` and crafted `denominations` entries — something any wallet user or AA can do without special privileges. No node compromise, network position, or race condition is needed; it is a deterministic arithmetic property of `Number` in JS reachable directly through public asset issuance and validated identically by every node (so it isn't rejected as a fork/consensus failure, it's accepted as valid supply inflation).

### Recommendation
- Enforce an explicit upper bound on `count_coins` per denomination (e.g. `count_coins <= constants.MAX_CAP / denomination`), verified using integer-safe arithmetic (e.g. `BigInt` or explicit `Number.isSafeInteger` checks on the product) before accumulating into `total_cap_from_denominations`.
- Perform the summation and comparison against `payload.cap` using `BigInt` to eliminate double-precision rounding, and reject any pair whose product is not an exact `Number.isSafeInteger` value.
- Apply the same fix consistently in `validateIndivisibleIssue` (validation.js:2218-2226) and in `aa_validation.js`'s equivalent denomination validation path, since both places compute `denomination * count_coins` on user-supplied values.

### Proof of Concept
1. Choose `denomination = 100` and `count_coins = 9007199254740993` (i.e., `2^53 + 1`, just above `Number.MAX_SAFE_INTEGER`).
2. Compute (in JS) `count_coins * denomination` — the true mathematical value is `900719925474099300`, but due to double rounding the actual `Number` result becomes some rounded value that can be engineered (via choice of `denomination`/`count_coins`) to equal or interact unexpectedly with a small `payload.cap` that itself is `<= constants.MAX_CAP`.
3. Post an `asset` definition message with `fixed_denominations: true`, `cap: <the rounded/matching value>`, and `denominations: [{ denomination: 100, count_coins: 9007199254740993 }]`.
4. `validateAssetDefinition` accepts the definition because `total_cap_from_denominations === payload.cap` holds under floating-point comparison (validation.js:2790), even though the true intended-cap semantics are violated.
5. Subsequent `issue` inputs of this asset are validated via `validateIndivisibleIssue`'s `input.amount !== denomination * denomInfo.count_coins` check (validation.js:2224), which uses the same lossy arithmetic, allowing issuance amounts inconsistent with a sane interpretation of the declared cap and effectively enabling supply beyond what `MAX_CAP`-style bounds were meant to guarantee.

Note: I was not able to execute this PoC in a live ocore instance (no runtime access in this environment); the exact `count_coins`/`denomination` pair that produces a colliding rounded product needs to be computed/confirmed with a JS `Number` arithmetic test, but the underlying missing-upper-bound-then-arithmetic pattern is directly verified in the cited source lines.
