### Title
Unchecked return value of `os.RemoveAll` for legacy worktree cleanup - (File: main.go)

### Summary
The reported Solidity issue is about an unchecked return value from an external call (`adminProxy.execute()`), where every other similar call in the contract checks `success` but one instance does not, risking silent failure of a state-changing operation. The closest reachable analog in `git-sync` is in `repoSync.SyncRepo`, where the return value of `os.RemoveAll` used to delete a stale, previous-format worktree directory is discarded, unlike every other filesystem/git operation in the same function, which is checked and propagated as an error.

### Finding Description
In `(*repoSync).SyncRepo`, after a successful sync and symlink publish, the code attempts to remove an old worktree directory that used a legacy on-disk layout: [1](#0-0) 

```go
if currentHash != "" && currentWorktree != git.worktreeFor(currentHash) {
    // The old worktree might have come from a prior version, and so
    // not get caught by the normal cleanup.
    os.RemoveAll(currentWorktree.Path().String())
}
```
Every other filesystem or git operation performed in `SyncRepo` and the functions it calls (`initRepo`, `fetch`, `createWorktree`, `configureWorktree`, `publishSymlink`) explicitly checks the returned error and propagates it as a sync failure, for example: [2](#0-1) 

By contrast, this `os.RemoveAll` call's error is silently dropped. `currentWorktree.Path()` is derived from following the on-disk symlink (`currentWorktree()` reads `git.link` via `os.Readlink`), so its value is influenced by whatever was previously published, and `RemoveAll` can fail for reasons like permission issues, a stale NFS handle, a busy mount, or a directory containing a nested mount point — none of which will be surfaced to the operator or affect `syncCount`/failure-count bookkeeping.

### Impact Explanation
If the `RemoveAll` fails, the stale legacy-layout worktree directory is left on disk indefinitely, with no error logged and no failure counted toward `--max-failures`. This is a persistent, low-visibility disk-space leak in the `--root` volume shared with the consumer container, and it means operators/monitoring relying on git-sync's error reporting (logs, `/metrics`, exit codes, `--max-failures`) have no way to detect the problem. Because this is only invoked in an in-place-upgrade edge case (worktree path differs from the current expected layout) it does not provide code execution or credential disclosure, so it does not rise to the severity of the original credit-bearing findings, but it is a genuine unchecked-error inconsistency matching the reported bug class.

### Likelihood Explanation
This code path only triggers when `currentHash != ""` and the on-disk worktree path doesn't match `git.worktreeFor(currentHash)` — i.e., during an upgrade from an older git-sync version or after unusual link tampering. It requires no attacker privilege beyond normal git-sync operation triggering this cleanup branch, but it is a narrow, edge-case condition rather than something hit on every sync.

### Recommendation
Check and log (or return) the error from `os.RemoveAll(currentWorktree.Path().String())`, consistent with how `removeWorktree` and other cleanup paths handle `os.RemoveAll` errors elsewhere in `main.go`, e.g. wrap it as `git.log.Error(err, "can't remove stale legacy worktree", "path", currentWorktree.Path())` rather than discarding it silently.

### Proof of Concept
1. Set up a `--root` where `.git/worktrees` layout differs from expectations (simulate an in-place upgrade scenario), so `currentWorktree != git.worktreeFor(currentHash)`.
2. Make `currentWorktree.Path()` unremovable during the sync (e.g., mount a read-only bind mount or nested volume inside that directory, common in Kubernetes sidecar setups sharing `--root`).
3. Run a sync; observe that `SyncRepo` returns success (`changed`, `remoteHash`, `nil`) with no error logged for the failed `RemoveAll`, and the stale directory persists across every subsequent sync cycle indefinitely, consuming disk space with no operator-visible signal.
