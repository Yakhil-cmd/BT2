### Title
Overly-broad `Bash(git add:*)` allow-list in commit.md enables silent staging/exfiltration of untracked secret files - ([File: plugins/commit-commands/commands/commit.md])

### Summary
The `/commit` command's frontmatter grants blanket access to `Bash(git add:*)`, `Bash(git status:*)`, and `Bash(git commit:*)` with no path or flag restriction, and its instructions merely say "Stage and create the commit" without constraining staging to the files the user actually intends to commit. Since `git status` output (attacker-controlled via a dropped untracked file) is fed into the model's context, the model can legitimately invoke `git add -A` or `git add .` under this allow-list, staging and then committing any untracked secret-bearing file placed in the working directory by an attacker, before the diff/message is sent to the model provider.

### Finding Description
The command's `allowed-tools` line is a wildcard glob on the git subcommand only, not on arguments/paths: [1](#0-0) 

The `git add:*` pattern matches any invocation of `git add`, including `-A` or `.`, which stage the entire working tree rather than only the hunks/files relevant to the change the user is reviewing. The task instructions reinforce broad staging without scoping guidance: [2](#0-1) 

The context block runs `git status` and `git diff HEAD` and injects their output directly into the model's prompt: [3](#0-2) 

If an attacker (e.g., via a malicious repo, a build script, or a prior compromised dependency install step that is not itself privileged) drops an untracked secret file into the working directory before the user invokes `/commit`, `git status` will list it as untracked. Nothing in the command prevents the model from choosing `git add -A`/`git add .` (both fully permitted by the `git add:*` allow-list) to "stage the changes," which will pick up the attacker's file. The subsequent `git commit`, also permitted unconditionally, then commits it into history — and the diff content (now containing the secret) is used for commit-message drafting, meaning it is included in the model context/network round-trip. There is no allowlist restriction limiting `git add` to specific tracked paths, no approval step confirming the file list before staging, and no workspace guard filtering untracked files out of the "changes to be staged." This directly breaks the stated invariant that "consent is explicit and scoped to user-approved target": the user approved running `/commit` on their intended changes, not on staging arbitrary untracked files revealed only at the time of git status inspection.

### Impact Explanation
This allows unauthorized broadening of commit scope and secret disclosure: attacker-planted credentials, tokens, or other untracked sensitive files can be silently committed to the repository (and pushed if a subsequent push step or auto-push behavior exists) and are also exposed to the model/network sink used for commit-message generation. This matches a "secret disclosure" / "unauthorized file action via git automation" impact class for Claude Code bounty scope, since it bypasses the expected human-in-the-loop review of exactly what is being staged/committed.

### Likelihood Explanation
Requires only an unprivileged ability to place a file in the working directory (e.g., via a repository the user clones/builds, a script executed as part of a normal workflow, or a dependency that writes to the tree) and for the user to subsequently run `/commit`. No admin/maintainer privilege, leaked keys, or social engineering is needed — the untracked file simply needs to exist at invocation time. The exploit is deterministic and repeatable because `git add -A`/`git add .` unconditionally match the `git add:*` allow-list every time.

### Recommendation
Scope `allowed-tools` for `git add` to explicit, previously-reviewed paths (e.g., disallow `-A`/`.`/`--all` via a narrower pattern or an explicit deny-list), and require the command to first present the untracked/modified file list to the user for confirmation before staging. Alternatively, instruct the model to only stage files that already appear in `git diff HEAD` (i.e., tracked, modified files) and explicitly exclude untracked files unless the user names them.

### Proof of Concept
Unit/integration test plan:
1. Initialize a git repo with one tracked file modified as the "approved" change.
2. Before invoking the `/commit` flow, create an untracked file `secret.env` containing a fake credential in the working directory.
3. Run the `/commit` command's underlying tool-call sequence as the model would (per allowed-tools): `git status`, then `git add -A` (or `git add .`), then `git commit -m "..."`.
4. Assert that `git show --stat HEAD` / `git diff-tree --no-commit-id --name-only -r HEAD` includes `secret.env`, demonstrating the untracked secret file was captured into the commit despite not being part of the user-approved diff.
5. Expected (fixed) behavior: the committed file set should equal exactly the pre-approved diff's file list, excluding `secret.env`, i.e., the assertion `committed_files == {approved_file}` should hold only after the allow-list/instruction fix is applied.
