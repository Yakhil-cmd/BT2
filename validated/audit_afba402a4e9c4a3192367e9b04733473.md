### Title
Webhook signature is verified against the `repository.owner.login`/fallback organization while handlers act on an unrelated `organization.login` (or `repository.full_name`) field, allowing cross-organization Team-membership forgery and `Shipit.github_teams` authorization bypass - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to use for HMAC verification based on `repository_owner`, computed as `params.dig('repository','owner','login') || params.dig('organization','login')`. This value is never bound to what the event handlers actually act on. `Shipit::Webhooks::Handlers::MembershipHandler` never reads `repository` at all — it uses `params.organization.login` directly to create/locate a `Team` and add/remove arbitrary GitHub logins as members. Because Shipit supports multiple configured GitHub organizations (`Shipit.github(organization:)`), each with its own independent `webhook_secret`, an attacker who legitimately controls the webhook secret of *any* configured organization can sign a payload whose `repository.owner.login` matches that organization (so signature verification passes) while setting `organization.login` to a *different*, victim organization whose GitHub team gates `Shipit.github_teams` authorization. The handler then adds an attacker-controlled GitHub login as a member of that victim `Team`, which directly grants `User#authorized?` (`Shipit.github_teams` membership) — an authentication bypass.

### Finding Description
Signature verification and event-content organization resolution are decoupled: [1](#0-0) [2](#0-1) 

`verify_signature` computes `repository_owner` from the *unverified* raw payload and uses it purely to pick which per-organization `webhook_secret` to validate the HMAC against: [3](#0-2) 

Nothing ties the organization selected for verification to the organization value the handler ultimately consumes. `MembershipHandler` declares its own required parameters — `organization.login`, `team`, `member` — completely independent of `repository`: [4](#0-3) 

So a single JSON body can legitimately contain both a `repository.owner.login` (used only for picking the HMAC secret) and an unrelated `organization.login` (used to create/lookup the `Team` and mutate its membership). Team membership feeds directly into authorization: [5](#0-4) [6](#0-5) 

and `Shipit.github_teams` is built from the configured OAuth teams, resolved to local `Team` records purely by `organization`/`slug` string match: [7](#0-6) 

Shipit explicitly supports hosting multiple GitHub organizations from one instance, each with its own `webhook_secret`/`app_id` (confirmed by the multi-org secrets template and the `Shipit.github(organization:)` lookup): [8](#0-7) [9](#0-8) 

**Binding that should hold but doesn't:** `organization used to select/verify the webhook secret == organization whose Team/authorization state the handler mutates`. Before the attack, for org B's genuine traffic, `repository_owner == organization.login == "B"`. An attacker who administers org B's GitHub App (having set up their own legitimate webhook secret for org B) can send `repository.owner.login = "B"` (verifies fine against B's secret) together with `organization.login = "A"` (the victim org gating `Shipit.github_teams`), breaking the equality and letting the attacker write into org A's `Team` membership using only org B's credentials.

### Impact Explanation
This is an escalation into `Shipit.github_teams` authorization (explicitly listed High-impact category): an unprivileged attacker who controls the webhook secret of any one configured GitHub organization on a multi-tenant Shipit instance can forge a `membership` event that adds an arbitrary GitHub login (including their own) to a `Team` bound to a *different* organization referenced by `Shipit.github_teams`, thereby granting themselves `User#authorized?` and full access to the Shipit UI/stacks gated by that team, without ever being a real member of the victim's GitHub team or organization.

### Likelihood Explanation
Likelihood is Low/Moderate: it requires the attacker to legitimately control a webhook secret for at least one org configured on the Shipit instance (a realistic scenario for shared/multi-tenant deployments, or when an org's `webhook_secret` is left blank per `verify_webhook_signature`'s `return true unless webhook_secret`). No repository write access, GitHub App private key, or Shipit session/API token is required — only knowledge of one org's webhook secret and the target org's team handle, both of which are discoverable from Shipit's own configuration conventions and public GitHub org names.

### Recommendation
Bind the organization used for signature verification to the organization the handler is permitted to mutate: reject events where `organization.login` (or `repository.owner.login`) used by the handler differs from the `repository_owner` value that selected the verifying `webhook_secret`. For `MembershipHandler` specifically, verify that `params.organization.login` equals the same value used in `WebhooksController#verify_signature`, and reject the event otherwise.

### Proof of Concept
1. Attacker administers GitHub org `B`, configured in Shipit's `secrets.yml` with its own `webhook_secret`, and legitimately knows that secret (or `B`'s `webhook_secret` is blank, in which case `verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb`).
2. Victim org `A` is configured with `oauth.teams: [A/developers]`, used by `Shipit.github_teams` to gate access (`app/models/shipit/user.rb#authorized?`).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "organization": { "login": "A" },
  "team": { "id": 1, "name": "developers", "slug": "developers", "url": "https://api.github.com/teams/1" },
  "member": { "login": "attacker-github-login" },
  "repository": { "owner": { "login": "B" } }
}
```
4. `X-Hub-Signature` is computed with org `B`'s known webhook secret over this exact raw body.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"B"` (from `repository.owner.login`), fetches `Shipit.github(organization: "B")`, and the HMAC verifies successfully.
6. `MembershipHandler#process` runs using `params.organization.login == "A"`, creating/locating `Team(organization: "A", slug: "developers")` and adding `attacker-github-login` as a member via `team.add_member(member)`.
7. The attacker's Shipit `User` record (created on their next GitHub OAuth login) now belongs to that `Team`, satisfying `Shipit.github_teams` and `User#authorized?`, granting them access to Shipit despite never being part of org `A`'s real GitHub team.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
```
