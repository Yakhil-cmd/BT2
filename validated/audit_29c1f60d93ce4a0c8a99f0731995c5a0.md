### Title
CCMenuController bypasses per-token stack scoping, letting a stack-restricted ApiClient read any stack's build/deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via the `stack_id` column, and every other `Api::BaseController` subclass resolves the requested stack through the scoped `stacks` relation. `Api::CCMenuController` overrides `#stack` to resolve directly against the global `Stack` model, ignoring the token's `stack_id` scope, so a token authorized only for stack A can read CCTray status/build data for any other stack.

### Finding Description
`Shipit::Api::BaseController#stacks` intentionally narrows the queryable stack set to the token's assigned stack when one is configured: [1](#0-0) 
and `#stack` is built on top of that scoped relation (`stacks.from_param!(...)`), so any controller relying on the inherited `#stack` can only ever resolve the stack the `ApiClient#stack_id` permits.

`Api::CCMenuController`, however, defines its own `#stack` that bypasses `stacks` entirely and resolves against the unscoped `Stack` model using attacker-supplied `params[:stack_id]`: [2](#0-1) 

Its permission check only enforces the generic `read:stack` scope, not stack identity: [3](#0-2) 

`ApiClient#check_permissions!` only compares `"#{operation}:#{scope}"` against the client's permission list — it never checks `stack_id` against the requested stack: [4](#0-3) 

This is exactly the "stack a token authorises versus a stack it touches" binding: the token is provisioned to authorize reads for one specific stack (`ApiClient#stack_id`), but `CCMenuController#show` touches whichever stack is named in the request parameters.

### Impact Explanation
Any holder of a valid, stack-scoped `read:stack` ApiClient token (e.g., the `here_come_the_walrus`-style token created by `CCMenuUrlController`, seen in [5](#0-4) ) can call `/api/stacks/:stack_id/ccmenu.xml` with any other stack's identifier and receive that stack's build status, activity, last build time/label and web URL: [6](#0-5) 
This is a cross-stack read of deploy/build state using a token never authorized for that stack, matching the High-severity criterion for "unauthenticated/unauthorized read of stack state ... or deploy output."

### Likelihood Explanation
Exploitation requires only possession of any legitimate, narrowly-scoped `read:stack` ApiClient token (routinely handed out, e.g. via the CCMenu URL flow) and knowledge/guessing of another stack's `to_param` identifier — no privileged account, GitHub credentials, or session is required, satisfying the in-scope "unprivileged attacker" constraint.

### Recommendation
Have `Api::CCMenuController#stack` resolve through the inherited, scope-aware `stacks` relation (i.e., delete the controller-local override, or explicitly re-implement it as `stacks.from_param!(params[:stack_id])`) so token-level stack scoping is enforced consistently across all API controllers.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (as produced by `CCMenuUrlController#client`).
2. Send `GET /api/stacks/<stack_B_permalink>/ccmenu.xml?token=<clientA_token>` where Stack B is a different stack the client was never authorized for.
3. Observe the request succeeds (200) because `authenticate_api_client` only verifies the token, `require_permission :read, :stack` only checks the generic permission string, and `#stack` resolves Stack B directly via `Stack.from_param!`, bypassing the `ApiClient#stack_id` scoping applied everywhere else in `Api::BaseController`.
