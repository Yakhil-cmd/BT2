### Title
Unauthorized creation of a shared (multisig) address record via forged `new_shared_address` device message - (File: wallet_defined_by_addresses.js)

### Summary
The `new_shared_address` message handled by `wallet.js` calls `handleNewSharedAddress()` in `wallet_defined_by_addresses.js` directly, which persists a new `shared_addresses`/`shared_address_signing_paths` record whenever the supplied `definition` and `signers` are internally self-consistent — with no check that the local user (or their device) actually initiated or approved the creation of this specific shared address. Any paired device (a correspondent who already exchanged pairing info with the victim, i.e. an "unprivileged" peer with no special authority) can push an arbitrary multisig definition into the victim's wallet as long as it hashes to the claimed address and its embedded `["address", ...]` leaves match the `signers` map.

### Finding Description
`wallet.js` routes the `"new_shared_address"` hub message straight into `wallet_defined_by_addresses.js`: [1](#0-0) 

`handleNewSharedAddress()` performs only structural/consistency checks — that `definition` hashes to `address`, that `signers` addresses are syntactically valid, and that the `["address", ...]` leaves of the definition match the `signers` map — but never verifies that the receiving device (or one of its own addresses) actually requested or agreed to be part of this particular address composition: [2](#0-1) 

Compare with `createNewSharedAddress()`, the *outbound*/self-initiated path, which explicitly requires `includesMyDeviceAddress(assocSignersByPath)` before calling the same `handleNewSharedAddress()`: [3](#0-2) 

That `includesMyDeviceAddress` guard is absent from the inbound network path. Instead, `determineIfIncludesMeAndRewriteDeviceAddress()` merely rewrites the `device_address` field to `getMyDeviceAddress()` for any member address that already belongs to the receiver (`my_addresses`/`shared_addresses`), it does not reject unsolicited definitions: [4](#0-3) 

Once accepted, `addNewSharedAddress()` inserts the row and, in light mode, starts watching the address and pushes it into `unprocessed_addresses`, and additionally forwards the (attacker-chosen) address/definition/signers to the victim's own cosigner devices of any of the victim's addresses referenced in the definition: [5](#0-4) 

Because one of the victim's own real addresses (previously learned by the peer through normal correspondence, e.g. a payment address the peer has seen) can be embedded as an `["address", ...]` leaf, the attacker fully controls every other party/condition in the `or`/`and` tree (e.g. an `"or"` branch requiring only the attacker's own signature, or additional data-feed/attested conditions favorable to the attacker). The victim's wallet will silently register this attacker-crafted address as a legitimate "shared address" resource, exactly analogous to the Superset bug class where an unprivileged/low-trust actor can make the application create/register a resource it should not be entitled to create on the victim's behalf.

### Impact Explanation
This maps to the "AA definitions and triggers ... or wallet and contract message handling" reachable surface named in the rules. The concrete harm:
- A shared/multisig address the victim never agreed to is silently added to the victim's wallet database and, in light clients, actively watched — potential resource/data pollution and UI confusion (victim may be shown balances/requests to sign for an address they never consented to co-own).
- Because the composition of the "shared address" (who else can spend, what conditions unlock it) is entirely attacker-controlled apart from the one leaf that matches the victim's real address, if the victim (or a correspondent socially engineered into trusting the appearance of a legitimate multisig UI entry) ends up funding this address, spending assumptions the wallet UI implies (e.g., "requires N-of-M my cosigners") may not hold, risking fund loss.
- The forwarding logic (`forwardNewSharedAddressToCosignersOfMyMemberAddresses`) propagates the forged address/definition further to the victim's other devices tied to that address, amplifying the spoofed resource across the victim's device set without any of them having agreed to it.

### Likelihood Explanation
Any device that has previously paired/corresponded with the victim (a routine, low-trust relationship in Obyte) can send this message at will; no cryptographic proof of victim intent, request, or corresponding outbound offer is required by `handleNewSharedAddress()`. The only real address the attacker needs is one already known to them via normal contact (e.g., a payment address the victim previously shared), which is trivial to obtain in any commerce/payment-request flow.

### Recommendation
In `handleNewSharedAddress()` (network/inbound path), require and validate that the local user actually initiated or explicitly pre-approved this shared-address composition (e.g., match against a pending/offered `pending_shared_addresses` record created by `createNewSharedAddressByTemplate`/an equivalent approval flow) instead of accepting any well-formed `{address, definition, signers}` triple unconditionally. At minimum, require `includesMyDeviceAddress(assocSignersByPath)` (as already enforced on the outbound `createNewSharedAddress` path) plus an explicit user confirmation/event before persisting to `shared_addresses`, mirroring the confirmation dialog gating used in `create_new_shared_address`/`approve_new_shared_address`.

### Proof of Concept
1. Attacker device pairs with victim device (standard Obyte pairing) and learns one of the victim's real addresses `V` from a prior payment request.
2. Attacker crafts `arrDefinition = ["or", [["address", V], ["address", A_attacker]]]` (or any structure granting attacker sole spend rights while still embedding `V`), computes `address = chash160(arrDefinition)`, and builds `signers = {"r.0": {address: V, device_address: <victim_device>}, "r.1": {address: A_attacker, device_address: <attacker_device>}}`.
3. Attacker sends `device.sendMessageToDevice(victim_device, "new_shared_address", {address, definition: arrDefinition, signers})`.
4. Victim's `wallet.js` handler dispatches to `walletDefinedByAddresses.handleNewSharedAddress`, all structural checks pass (hash matches, addresses valid, leaves match signers), and `addNewSharedAddress()` persists the record into the victim's `shared_addresses` table without any confirmation dialog or check that the victim requested it. function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}

function createNewSharedAddress(arrDefinition, assocSignersByPath, callbacks){
	if (!includesMyDeviceAddress(assocSignersByPath))
		return callbacks.ifError("my device address not mentioned");
	var address = objectHash.getChash160(arrDefinition);
	handleNewSharedAddress({address: address, definition: arrDefinition, signers: assocSignersByPath}, {
		ifError: callbacks.ifError,
		ifOk: function(){
			// share the new address with all cosigners
			var arrDeviceAddresses = [];
			for (var signing_path in assocSignersByPath){
				var signerInfo = assocSignersByPath[signing_path];
				if (signerInfo.device_address !== device.getMyDeviceAddress() && arrDeviceAddresses.indexOf(signerInfo.device_address) === -1)
					arrDeviceAddresses.push(signerInfo.device_address);
			}
			arrDeviceAddresses.forEach(function(device_address){
				sendNewSharedAddress(device_address, address, arrDefinition, assocSignersByPath);
			});
			callbacks.ifOk(address);
		}
	});
}
