### Title
`flash_loan` lets a caller name any `receiver`, then steals that contract's tokens via its standing `transfer_from` allowance to the pool - (File: contracts/pool/src/ops/flash.rs)

### Summary
The bug class is "funds pulled from a user-supplied `from` address using an existing allowance/approval, instead of `msg.sender`". The exact analog lives in the pool's flash-loan settlement: `flash_loan(caller, hub_asset, receiver, amount, data)` forwards an unprivileged-caller-chosen `receiver` down to `ops::flash::apply`, which pays the principal to that `receiver`, invokes `execute_flash_loan` on it, and then calls `token::transfer_from(pool, receiver, pool, amount + fee)` — spending whatever allowance `receiver` previously granted the pool, with no `require_auth` on `receiver`. Any WASM contract that once approved the pool (the documented repayment flow for legitimate flash receivers) can be designated as `receiver` by an attacker and charged `amount + fee` per call while receiving only `amount` back.

### Finding Description
`apply` at `contracts/pool/src/ops/flash.rs:40-71` takes `receiver` as a pure argument. Its only validation is `require_wasm_receiver` (line 49), which checks the address is a WASM contract — not that it authorized this call or consented to the loan. Settlement in `collect_repayment` (lines 165-180) is:

```rust
asset.allowance(receiver, pool) >= terms.total_repayment   // line 175
asset.transfer_from(pool, receiver, pool, &terms.total_repayment);  // line 178
```

So the pull is gated solely by the victim's pre-existing token allowance to the pool — the same pattern as `VaderPoolV2.mintFungible(from, ...)`, where a caller-supplied `from` was spent via its ERC-20 approval. Here `transfer_from` spends the victim's `approve(pool, …)` grant without any `receiver.require_auth()`. The controller `flash_loan` entrypoint is permissionless (caller-auth only; `INV-FLASH-01/02` in `scripts/permissionless_entrypoints.txt:77`), so any unprivileged address chooses `receiver`.

The victim set necessarily overlaps with legitimate usage: the documented repayment flow is "Receiver approves `amount + fee` to the pool" (`skills/xoxno-lending-contracts/abi.md:56`, pool README table line 80). A receiver contract that approved with headroom — a larger-than-needed amount, a long `live_until_ledger`, or a residual allowance left by an earlier loan whose executed repayment was smaller — carries a spendable balance the pool can `transfer_from` at any time. Such a contract also necessarily implements `execute_flash_loan`, so `require_wasm_receiver` and the callback do not filter it out.

### Impact Explanation
Each attacker-submitted call moves `amount` into the victim and pulls `amount + fee` out of it via its allowance. Net victim loss per call is the flash fee, credited to protocol revenue (`book_fee`, line 124-128). The attacker's cost is zero and the loop is bound only by the victim's remaining allowance and the market's cash: with a near-maximum `amount`, the allowance is consumed at `amount + fee` per iteration while the victim bleeds `fee` each time — a slow, unilateral drain of tokens the victim contract only ever approved for its own loans. This is theft of user funds caused by an approval given to the contract — the identical impact class to H-26 — reduced in magnitude per call (fee only) but repeatable until the allowance is exhausted.

### Likelihood Explanation
Requires a victim WASM contract with (a) an `execute_flash_loan` implementation whose callback does not revert when invoked with attacker-controlled `initiator`/`data`, and (b) a positive remaining `allowance(receiver, pool)`. Condition (b) is the normal state for any flash receiver that over-approved (a common `i128::MAX`/long-TTL approval pattern) or that was interrupted mid-flow; the codebase itself instructs integrators to approve `amount + fee` before the call, and the allowance persists if a subsequent invocation fails after approval or approves more than the executed repayment. Severity is bounded by allowance size and per-call fee, which argues Medium rather than High.

### Recommendation
Stop collecting repayment by allowance against a caller-supplied address. Either (a) require the receiver callback to `transfer` principal + fee back directly — which `collect_repayment` currently rejects indirectly by using `transfer_from` — so only the receiver's own execution can spend its balance, or (b) have the controller pin `receiver` to a caller-authorized address (`receiver.require_auth()` or the flash guard pattern), mirroring H-26's fix of substituting `msg.sender` for the user-supplied `from`. The strict-equality balance check in `require_balance` (line 183-189) already proves exact receipt, so a direct-transfer model is compatible with the existing reconciliation.

### Proof of Concept
1. Victim contract `V` is a legitimate flash receiver that previously ran `token.approve(V, pool, large_amount, far_future_ledger)` (per the documented approve-then-borrow flow) and still holds allowance `A` and token balance `B`.
2. Attacker `E` calls `controller::flash_loan(E, hub_asset, receiver = V, amount = X, data = arbitrary)` where `X + fee(X) ≤ allowance(V, pool)` and `X ≤ pool cash`.
3. `apply` pays `X` to `V` (line 60), invokes `V.execute_flash_loan(E, asset, X, fee, pool, data)` (line 150-162) — `V`'s normal handler runs or no-ops, `V` never authenticates this transaction.
4. `collect_repayment` sees `allowance(V, pool) ≥ X + fee` and executes `transfer_from(pool, V, pool, X + fee)` (line 178). `V` loses `fee(X)` net; the fee is booked as protocol revenue. The balance assertions at lines 61/66/179 all pass.
5. Repeat with `X` near the cash cap until `allowance(V, pool)` is consumed; cumulative stolen fees approach `A · fee_bps / (fee_bps + 1)`-scaled drain of `V`'s approval without any auth from `V`.
