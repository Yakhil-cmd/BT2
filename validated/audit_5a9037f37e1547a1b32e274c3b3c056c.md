### Title
Webhook signature verified against `repository.owner.login` while the acted-upon repository comes from unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/secret to check the `X-Hub-Signature` against using an organization login pulled directly out of the unverified JSON body, but the handlers that actually act on the payload (create commits, update statuses, trigger syncs) key off a *different* unverified field, `repository.full_name`. These two fields are never checked against each other, so the "organization whose secret authenticated the request" and "the repository that gets written to" can diverge.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, not-yet-authenticated body and uses it solely to select which `Shipit::GitHubApp` (and thus which `webhook_secret`) to validate the signature against: [1](#0-0) [2](#0-1) 

If that selected organization has no `webhook_secret` configured, `GitHubApp#verify_webhook_signature` short-circuits to `true` unconditionally, accepting the request with no cryptographic check at all: [3](#0-2) 

Shipit natively supports hosting multiple GitHub organizations under one instance, each with its own independently configured `webhook_secret` (some intentionally left blank in examples/dev configs): [4](#0-3) [5](#0-4) 

Once the (weak) signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the **same raw payload** to handlers, none of which re-check that `repository.owner.login` matches `repository.full_name`'s owner: [6](#0-5) 

Every handler resolves the target `Stack`(s) purely from `repository.full_name`: [7](#0-6) 

`PushHandler` then triggers a real Git sync against the resolved stack's actual GitHub repo using `after` (attacker supplied) as the expected head SHA, and `StatusHandler` writes a commit status that can gate deploy eligibility: [8](#0-7) [9](#0-8) 

This is the same class of bug as the referenced report: the field the "authorization" is checked against (`repository.owner.login`, used to pick the `webhook_secret`) is not the field that determines what gets acted upon (`repository.full_name`, used to select the `Stack`/repo). An attacker who knows (or guesses) that one configured organization has a blank/misconfigured `webhook_secret` can forge `repository.owner.login` to that lightly-secured org while setting `repository.full_name` to point at a repository belonging to a *different, properly secured* organization — bypassing that organization's webhook secret entirely.

### Impact Explanation
This breaks the equality "organization authenticated by signature == organization owning the repository being written to." A successful forgery lets an unprivileged network attacker inject fabricated `push`, `status`, `check_suite`, or `membership` events for a stack/repository they do not control, causing Shipit to sync repository state and record commit statuses from forged data for a repo protected under a different org's secret. This maps to the High-impact category "unauthenticated read/write of stack state" via a webhook-secret bypass; it does not on its own achieve an unauthorized deploy/merge (deploys still require separate authorization gates), so it should be scoped as High rather than Critical.

### Likelihood Explanation
Requires a specific misconfiguration precondition: a Shipit instance hosting multiple GitHub organizations where at least one organization's `webhook_secret` is left blank/absent while others are secured — a configuration Shipit itself documents and supports (see the multi-org secrets examples). Given that example/dev configs default `webhook_secret` to nil, this is a plausible, not purely theoretical, real-world misconfiguration, but it is conditional rather than universally exploitable out of the box.

### Recommendation
After verifying the signature, re-derive and cross-check that the organization implied by `repository.full_name` (or `organization.login`) matches the organization (`repository_owner`) whose secret was used to validate the signature, rejecting the request on mismatch. Additionally, avoid the `return true unless webhook_secret` short-circuit for organizations expected to be secured, or require `webhook_secret` to be present for any organization accepted in multi-org configurations.

### Proof of Concept
1. Configure Shipit with two orgs: `SecureOrg` (has `webhook_secret` set, hosts `SecureOrg/app`) and `OpenOrg` (no `webhook_secret` configured), as supported by [4](#0-3) .
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "full_name": "SecureOrg/app",
    "owner": { "login": "OpenOrg" }
  }
}
```
No valid `X-Hub-Signature` is supplied (or an arbitrary one is supplied).
3. `verify_signature` resolves `repository_owner` = `"OpenOrg"`, loads `Shipit.github(organization: "OpenOrg")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally per [10](#0-9) .
4. The request passes verification and `PushHandler` resolves the stack via `repository.full_name = "SecureOrg/app"` [11](#0-10) , calling `stack.sync_github(expected_head_sha: "deadbeef")` on the secured org's stack despite never having presented a valid signature for `SecureOrg`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
