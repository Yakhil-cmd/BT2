### Title
Webhook signature validated against `repository.owner.login`/`organization.login` but the acted-upon repository is taken from the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), but every event handler subsequently determines which `Repository`/`Stack` to mutate using a completely different, independently-attacker-controlled JSON field: `payload.dig('repository','full_name')`. Nothing ties these two fields together, so the "organization whose secret authenticated the request" and "the repository that gets written to" are never cross-checked, breaking the equality the modifier `onlyAllowed()`-style pattern is supposed to enforce (verified identity == identity actually acted upon).

### Finding Description
`Shipit.github(organization:)` supports multiple GitHub Apps/organizations, each with its own `webhook_secret`, keyed by organization login (`lib/shipit.rb` `github_app_config`, used at `lib/shipit.rb:170-180`). In `verify_signature`: [1](#0-0) 

the organization used to pick the secret comes from `repository_owner`: [2](#0-1) 

Once the signature is accepted, every `Handler` subclass (push, pull_request opened/labeled/reopened/assigned, etc.) resolves the target repository from a *different* field of the same JSON body, `repository.full_name`, via `Handler#repository_name` / `Repository.from_github_repo_name`: [3](#0-2) [4](#0-3) [5](#0-4) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for action) are two independent, attacker-supplied strings in the same raw JSON payload, and GitHub's HMAC signature only proves the payload as a whole came from a holder of *some* configured `webhook_secret` (not that the two fields agree), an operator of a Shipit instance configured with multiple organizations (`config/secrets.yml` `github` map, as documented for multi-app setups) is exposed to this class of confusion: a request validly signed with **Org A**'s webhook secret can carry `repository.owner.login = "org-a"` (so `verify_signature` passes) while `repository.full_name = "org-b/some-repo"` (so the push/pull_request handler mutates Org B's stack). The pull_request handlers additionally use `params.repository.full_name` directly for the same purpose: [6](#0-5) [7](#0-6) 

### Impact Explanation
This breaks the "organization authenticated" vs. "repository written" trust binding called out in the report's bug-class analog. If an attacker controls (or can trigger arbitrary deliveries for) any organization configured on a shared Shipit instance, they can forge webhook events (push syncs, pull-request opened/labeled/reopened archiving/unarchiving review stacks, merge/commit-status updates) targeting a *different* organization's repositories/stacks, none of which they are authorized for — e.g. forcing `GithubSyncJob` to run against another org's stack, or archiving/unarchiving another org's review stacks via crafted `pull_request` events. This matches the "unauthorized... cross-repository writes" high/critical impact category in scope.

### Likelihood Explanation
This is only exploitable on deployments where `Shipit.github` is configured with multiple organizations/webhook secrets (the "double github app" style configuration referenced in `test/dummy/config/secrets_double_github_app.yml` and `lib/shipit.rb#github`); for the common single-org setup the ambiguity collapses because there is only one secret. On qualifying multi-org deployments, no privileged Shipit session, `ApiClient` token, or GitHub write access is required — only the ability to deliver (or replay) a validly-signed webhook for one of the configured organizations, e.g. by installing the app or triggering its own repository events.

### Recommendation
In `WebhooksController#verify_signature` and in `Shipit::Webhooks::Handlers::Handler#repository_name` (and every handler that independently reads `params.repository.full_name`), derive the acted-upon repository/organization consistently from a single verified source, and explicitly assert that `repository.owner.login` (or `organization.login`) used to select the webhook secret matches the owner segment of `repository.full_name` before dispatching to handlers. Reject the request (422) on mismatch.

### Proof of Concept
Not independently runnable without a live multi-organization Shipit deployment (two configured GitHub Apps/orgs sharing one Shipit instance), which the index does not let me set up here; however, the mismatch is demonstrable purely by code inspection:
1. Configure `secrets.yml` `github:` with two orgs, `org-a` and `org-b`, each with its own `webhook_secret`.
2. Craft a `push` (or `pull_request`) payload where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/target-repo"`.
3. Sign the raw body with `org-a`'s `webhook_secret` and send it with header `X-Hub-Signature`.
4. `verify_signature` computes `repository_owner == "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature check passes.
5. The dispatched handler (e.g. `PushHandler`) resolves `stacks` via `Repository.from_github_repo_name("org-b/target-repo")`, acting on Org B's stack despite the request only being authenticated for Org A.

Because I could not execute this against a running dummy instance from within the ask-only tooling, treat step 4/5 as a structural proof from the cited code paths rather than an executed exploit trace.
