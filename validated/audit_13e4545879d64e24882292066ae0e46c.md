### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire database, without verifying that the matched commit belongs to a stack whose repository matches the `repository.full_name` in the verified webhook payload. Any attacker who can get a validly-signed "status" webhook accepted for their own org/repo, and who can produce a commit SHA that also exists on a victim's stack (trivially true for forked commits sharing history, or a crafted identical commit), can inject a forged `success` status onto the victim's commit and flip its `deployable?` state.

### Finding Description
The broken binding is: `commit.stack.repository.full_name` (the actual owner of the matched `Commit` row) **should equal** `payload.dig('repository', 'full_name')` (the repository asserted and signature-verified in the webhook), but `StatusHandler#process` never checks this.

`app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This is inconsistent with the base `Handler` class, which provides a `stacks` helper explicitly scoped to the repository named in the payload:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Other handlers (push, pull_request, check_suite) use this `stacks` scoping so that a payload can only affect stacks belonging to the repository it claims to be from. `StatusHandler` does not use it at all — it queries `Commit` globally by `sha`.

`WebhooksController#verify_signature` only checks that the payload's *own* named organization/owner signed the request:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
``` [3](#0-2) 

This proves the request came from *some* organization Shipit trusts (the attacker's own org, using the attacker's own webhook secret), but it says nothing about which `Commit`/`Stack` rows the `sha` in the body is allowed to touch. `Status.replicate_from_github!` then persists using the matched commit's real `stack_id`:
```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(stack_id:, state: github_status.state, ...)
end
``` [4](#0-3) 

Exploit flow:
1. Victim stack tracks commit `C` (sha `S`) with state `pending`/`failure`. `C` originates in ancestry shared with a public/forkable repo (or an attacker crafts an identical no-op commit with matching tree/author/committer/timestamps/message so the SHA is literally `S` — this is not a hash "break," it's how Git objects work: identical content ⇒ identical SHA).
2. Attacker pushes to their own fork/org repo where they legitimately control the webhook secret Shipit uses for their org (`repository_owner` = attacker's org).
3. Attacker sends `POST /webhooks` with `X-Github-Event: status`, a signature valid for their own org, and body `{"sha": S, "state": "success", "repository": {"full_name": "attacker/their-repo", ...}}`.
4. `verify_signature` passes (correctly, for the attacker's own org).
5. `StatusHandler#process` runs `Commit.where(sha: S)`, matching the victim's `Commit` row (unscoped by repository/stack), and calls `commit.create_status_from_github!(params)`, writing a `success` `Status` on the victim's stack.
6. `Commit#deployable?` for the victim's commit flips to true, enabling an unauthorized deploy.

Existing guards do not catch this: `verify_signature` validates org-level authenticity, not the association between the claimed repository and the matched `Commit`/`Stack`; the `ExplicitParameters` schema only validates types/shape, not sha-ownership; there is no `stacks`-style scoping applied in `StatusHandler` unlike sibling handlers.

### Impact Explanation
An attacker fully controlling only their own repository/org's webhook credentials can write a forged `success` (or any) CI status onto a *different* tenant's `Stack`/`Commit`, directly flipping `Commit#deployable?` and enabling an unauthorized deploy of the victim's stack. This is a cross-tenant write (a payload for one repository mutating another's commit/stack), matching the "Critical: unauthorized deploy... a payload for one repository mutating another's stack, commit" category. It is repeatable against any stack containing a commit whose SHA is also reachable/producible by the attacker (very plausible for any forked or shared-history repository, and trivially achievable by crafting an empty/no-op commit with identical fields).

### Likelihood Explanation
Preconditions: Shipit is multi-tenant (multiple orgs/repos with distinct webhook secrets registered, as stated), the attacker owns a repo/org onboarded to Shipit, and the victim stack has a commit with `pending`/`failure` state whose SHA is reachable/reproducible by the attacker (forks trivially share commit history and thus SHAs; a synthetic identical commit is also easy to produce). No Shipit or GitHub secret belonging to the victim is needed — only the attacker's own credentials for their own org, which they legitimately possess. This makes the attack low-cost and repeatable.

### Recommendation
Scope `StatusHandler#process` the same way other handlers scope events: verify that the matched `Commit`'s stack belongs to `Repository.from_github_repo_name(repository_name)` (i.e., restrict `Commit.where(sha: params.sha)` to `stacks.flat_map(&:commits)` or equivalent, using the `stacks` helper already defined on `Handler`), rejecting/ignoring any matched commit whose stack's repository does not match the payload's `repository.full_name`.

### Proof of Concept
Minitest plan (e.g., in `test/controllers/webhooks_controller_test.rb`):
```ruby
test ":status from an unrelated repository must not mark another stack's commit as deployable" do
  victim_commit = shipit_commits(:first) # belongs to :shipit stack, state pending/failure
  refute victim_commit.deployable?

  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate attacker's own valid signature for their org

  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  post :create, body: forged_payload, as: :json

  victim_commit.reload
  refute victim_commit.deployable?, "commit from victim stack must not become deployable via a status webhook claiming an unrelated repository"
end
```
Before the fix, `victim_commit.deployable?` flips `false -> true` because `Commit.where(sha:)` matches across stacks regardless of `repository.full_name`; after applying the recommended scoping, the assertion holds.
