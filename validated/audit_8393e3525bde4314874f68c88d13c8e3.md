### Title
Order-dependent diff-byte-cap in `cap_diff_for_prompt` lets attacker-sized diffs push vulnerable code past the review window - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_investigate_prompt` builds the Stage-1 investigate prompt from `cap_diff_for_prompt`, which truncates each file's diff at a fixed per-file byte cap and drops/omits whole files once a fixed total-byte budget is exhausted, in file-list order. [1](#0-0)  Because the caps are purely positional (head-preserved, tail-dropped; earlier files in `diff_files` win the shared budget over later ones), an attacker who controls the diff content and its per-file ordering/size (e.g. a prompt-injected agentic coding session, or a large PR) can deterministically push the actual vulnerable hunk past `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES` so the reviewer LLM never sees it.

### Finding Description
`build_investigate_prompt` (`plugins/security-guidance/hooks/review_api.py:156-176`) calls `cap_diff_for_prompt(diff_files)` before rendering the diff into the Stage-1 investigate prompt. [2](#0-1)  `cap_diff_for_prompt` enforces two caps:
- `DIFF_PER_FILE_BYTES` (default 80000): content beyond this length is truncated and replaced with a `"...[truncated ...]"` marker appended after the cut, i.e. only the tail is dropped. [3](#0-2) 
- `DIFF_TOTAL_BYTES` (default 400000): once the running `total` exceeds this, subsequent files in `diff_files` are entirely replaced with a generic `"[omitted by security-guidance: total diff byte cap reached]"` placeholder that carries no code content at all. [4](#0-3) 

Both caps are strictly positional: whichever bytes/files come first in `diff_files` survive, and whatever comes later (in file order, or later in a single large file's content) is what gets truncated or omitted. Since the diff content and file ordering originate from the code change under review — which in a compromised/prompt-injected agentic session, or a malicious external contributor's commit, is attacker-influenceable — an attacker can pad the diff with large benign-looking content (vendored files, generated code, verbose comments) placed before the true malicious hunk, or grow a single file past 80KB with the vulnerable line placed after the cutoff. The result is that the vulnerable file/line is either fully omitted (no `filePath`-scoped content reaches the model at all) or silently truncated away, so the investigate-stage system prompt's instruction to "Read EVERY changed file in full" and "trace every new sink" cannot fire — the model was never given the bytes.

This differs from a normal LLM false-negative: it is a deterministic, code-level failure to deliver the relevant bytes into the prompt at all, independent of model reasoning quality.

### Impact Explanation
If this path is exercised in a production review flow (it is exposed as the importable public API per the module's own docstring, intended for "external agentic harnesses" to reuse verbatim), an attacker who controls diff shape can guarantee that a specific dangerous change is excluded from LLM review, defeating the security-guidance plugin's core detection guarantee and enabling smuggled vulnerable/malicious code (backdoors, secret exfiltration paths, sink integrations) to pass an "AI reviewed" commit undetected. This matches the "review/export logic bypass leading to sensitive code disclosure/undetected malicious behavior" impact category, since the omitted diff content is effectively hidden from the intended reviewer sink.

### Likelihood Explanation
Requires only that the attacker (or a prompt-injected agent writing the diff) can shape the byte size/ordering of the changed files — no privilege escalation, no auth bypass, and no dependency on model behavior. The defaults (80000/400000 bytes) are well within reach of ordinary large diffs (vendored dependency bumps, generated code, minified assets, large data files), making the padding technique practical without appearing anomalous. It is fully deterministic and repeatable given the same `diff_files` ordering.

### Recommendation
- Do not silently drop or omit content past the cap without surfacing that omission as a hard-fail/hold rather than a fail-open "review passed" state; e.g., mark the overall review as `incomplete` and require re-review of the omitted files.
- Prioritize which files/hunks get the byte budget by a content-risk heuristic (files containing new sinks, `+`-line count, dangerous file extensions) rather than raw file-list order, and always keep the changed lines with highest a-priori risk (e.g., `+` lines with process/exec/network keywords) within the budget over unchanged context or the largest file.
- Consider capping per-file AND ensuring every touched file gets at least a minimum guaranteed slice of the total budget, rather than first-come-first-served.

### Proof of Concept
Unit test against `review_api.build_investigate_prompt` / `cap_diff_for_prompt`:
1. Construct `diff_files = [("padding1.py", "A"*300000), ("padding2.py", "B"*150000), ("malicious.py", "+os.system(attacker_input)  # SENTINEL_DANGEROUS_LINE")]` — total exceeds `DIFF_TOTAL_BYTES` (400000) once padding files are counted.
2. Call `capped, dropped = cap_diff_for_prompt(diff_files)`.
3. Assert that `capped` for `"malicious.py"` equals the omission marker `"[omitted by security-guidance: total diff byte cap reached]"` and does **not** contain `"SENTINEL_DANGEROUS_LINE"`.
4. Call `build_investigate_prompt(["malicious.py"], diff_files)` and assert `"SENTINEL_DANGEROUS_LINE"` is absent from the returned prompt string — proving the dangerous line never reaches the reviewer LLM.
5. Repeat with a single file whose content is `"A"*80000 + "+os.system(attacker_input) # SENTINEL_DANGEROUS_LINE"` to demonstrate the per-file cap has the same effect.

```python
DIFF_PER_FILE_BYTES = int(os.environ.get("DIFF_PER_FILE_BYTES", "80000"))
DIFF_TOTAL_BYTES = int(os.environ.get("DIFF_TOTAL_BYTES", "400000"))


def cap_diff_for_prompt(
    files: list[tuple[str, str]],
) -> tuple[list[tuple[str, str]], int]:
    """Cap per-file and total diff bytes; return (capped_files, bytes_dropped).

    Truncation markers are written inside the content so the reviewer
    knows the file is incomplete.
    """
    out: list[tuple[str, str]] = []
    dropped = 0
    total = 0
    for fp, content in files:
        if len(content) > DIFF_PER_FILE_BYTES:
            dropped += len(content) - DIFF_PER_FILE_BYTES
            content = (
                content[:DIFF_PER_FILE_BYTES]
                + "\n... [truncated by security-guidance: file exceeds per-file byte cap]"
            )
        room = DIFF_TOTAL_BYTES - total
        if room <= 0:
            dropped += len(content)
            out.append(
                (fp, "[omitted by security-guidance: total diff byte cap reached]")
            )
            continue
        if len(content) > room:
            dropped += len(content) - room
            content = (
                content[:room]
                + "\n... [truncated by security-guidance: total diff byte cap reached]"
            )
        total += len(content)
        out.append((fp, content))
    return out, dropped
```

def build_investigate_prompt(
    touched_paths: list[str],
    diff_files: list[tuple[str, str]],
    *,
    context_note: str = "",
) -> str:
    capped, _ = cap_diff_for_prompt(diff_files)
    diff_text = "\n\n".join(
        f"=== DIFF: {fp} ===\n{content}" for fp, content in capped
    )
    return (
        "Review this change for security vulnerabilities.\n\n"
        "Changed files (you may Read these and any other file in the repo):\n"
        + "\n".join(f"  - {p}" for p in touched_paths[:50])
        + context_note
        + "\n\nUnified diff (only + lines are new):\n\n"
        + diff_text
        + extensibility.guidance_block()
        + "\n\nInvestigate per the method in your instructions, then return "
        "the findings list."
    )
