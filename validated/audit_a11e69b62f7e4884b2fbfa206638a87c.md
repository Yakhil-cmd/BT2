### Title
`SingleKeySignature` → `AccountAuthenticator` conversion mislabels `FederatedKeyless` public keys as `Keyless` - ([File: api/types/src/transaction.rs])

### Summary
`impl TryFrom<&SingleKeySignature> for AccountAuthenticator` in [1](#0-0)  builds an `AnyPublicKey::Keyless` from a `PublicKey::FederatedKeyless` input instead of `AnyPublicKey::federated_keyless(...)`, unlike the sibling (and correct) conversion `impl TryFrom<&PublicKey> for AnyPublicKey` a few lines above at [2](#0-1) .

### Finding Description
The API-facing `PublicKey` enum has distinct `Keyless` and `FederatedKeyless` variants [3](#0-2) , and `TryFrom<&PublicKey> for AnyPublicKey` correctly maps each to its matching internal `AnyPublicKey` variant, keeping `FederatedKeyless -> AnyPublicKey::federated_keyless` [4](#0-3) . However, the separate conversion path used to build an `AccountAuthenticator` from a `SingleKeySignature` (public key + signature pair submitted through the API type layer) collapses `PublicKey::FederatedKeyless` into `AnyPublicKey::keyless(key)` — the wrong enum variant — while its doc string even says "as AnyPublicKey::FederatedKeyless" [1](#0-0) . `AnyPublicKey` is a discriminated enum whose BCS serialization (and therefore the `AuthenticationKey`/account address derived from it) differs by variant, and `FederatedKeyless` additionally carries a distinct JWK-issuer address binding not present in plain `Keyless`. Producing the wrong variant corrupts the authenticator's public-key binding relative to what the real `FederatedKeyless` sender intended.

### Impact Explanation
If this conversion path is reached with attacker- or client-supplied API-shaped input to construct a `SignedTransaction`/`AccountAuthenticator` for keyless accounts, a `FederatedKeyless` key would be serialized/interpreted as a plain `Keyless` key. This breaks the binding between the signer's declared JWK-issuer account (federated) and the produced authenticator, potentially causing either a hard validation failure (safe failure mode) or, in the worst case, confusion between the federated-JWK trust domain and the Aptos-managed keyless JWK trust domain during authentication key / address derivation. This is exactly the "authenticator accepting wrong signing material" class called out in the admission gate.

### Likelihood Explanation
I could not fully confirm, within the available search budget, that this conversion function is actually reachable from an untrusted/unprivileged external input path (e.g., a JSON `submit_transaction` request) versus being used only in low-risk contexts such as indexer/gRPC proto conversion or internal test helpers. My searches found call-site references concentrated in `ecosystem/indexer-grpc/indexer-grpc-fullnode/src/convert.rs`, `protos/*`, and `api/types/src/lib.rs`, but I was not able to trace definitively whether `api/src/transactions.rs`'s JSON transaction-submission handling invokes `TryFrom<&SingleKeySignature> for AccountAuthenticator` specifically (as opposed to only `TryFrom<&SingleKeySignature> for TransactionAuthenticator`, used perhaps only for read-side JSON rendering). Without that confirmation, I cannot certify this as an admission-boundary-reachable, unprivileged root cause with concrete impact — it may instead be a self-consistency/data-modeling bug isolated to non-admission code paths (e.g., indexer conversion, or read-only JSON transaction display).

### Recommendation
1. Fix the branch to use `AnyPublicKey::federated_keyless(key)` instead of `AnyPublicKey::keyless(key)` at [1](#0-0) .
2. Confirm (with full repository/build access) whether `TryFrom<&SingleKeySignature> for AccountAuthenticator` is reachable from any transaction-admission path (JSON transaction submission, transaction simulation encode/decode, or wallet-facing signing helpers) versus being confined to indexer/display conversions.
3. Add a round-trip test (`PublicKey::FederatedKeyless -> AccountAuthenticator -> back`) asserting the variant is preserved, and add negative tests ensuring a `FederatedKeyless`-signed transaction is never accepted as if it were plain `Keyless` or vice versa.

### Proof of Concept
Given the code as-is:
```rust
PublicKey::FederatedKeyless(ref p) => {
    let key = p.value.inner().try_into().context(
        "Failed to parse given public_key bytes as AnyPublicKey::FederatedKeyless",
    )?;
    AnyPublicKey::keyless(key)   // BUG: should be AnyPublicKey::federated_keyless(key)
},
```
Constructing a `SingleKeySignature { public_key: PublicKey::FederatedKeyless(...), signature: Signature::Keyless(...) }` and converting it via `AccountAuthenticator::try_from(&single_key_signature)` yields an `AccountAuthenticator::SingleKey` whose inner `AnyPublicKey` is tagged `Keyless` rather than `FederatedKeyless`, even though `TryFrom<&PublicKey> for AnyPublicKey` on the identical input correctly preserves `FederatedKeyless`. I was unable to execute this in a live environment within the current session to observe the downstream authentication-key mismatch or rejection behavior — this should be validated in a Devin session with full build/test access.
