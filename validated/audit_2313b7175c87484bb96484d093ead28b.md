## Analysis Result [1](#0-0)  selects which GitHub App/webhook secret verifies an inbound webhook based on `repository_owner`, computed from the **unverified** JSON body itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. Every event `Handler`, however, resolves the actual `Repository`/`Stack` to act on from a *different* field of that same unverified body: `payload.dig('repository', 'full_name')`. [2](#0-1) 

Nothing cross-checks that `repository.owner.login` (used to pick the verifying org/secret) matches the owner segment embedded in `repository.full_name` (used to pick the Stack that gets written to).

`verify_webhook_signature` short-circuits to `true` whenever that org's `webhook_secret` is blank — an explicitly documented "optional" setting: [3](#0-2) [4](#0-3) 

Shipit natively supports multiple GitHub App/organization configs, each with its own independent `webhook_secret`: [5](#0-4) [6](#0-5) 

**The binding that breaks:** `organization-that-authenticated == organization-of-repository-written`. Concretely, given a multi-org install where at least one configured org has no `webhook_secret` (a supported/documented configuration), an unauthenticated attacker can submit a single webhook payload with `repository.owner.login` (or `organization.login`) set to the org that has *no* secret — making `verify_webhook_signature` return `true` unconditionally — while setting `repository.full_name` to `"secured-org/victim-repo"`, an entirely different, secured organization's repository that Shipit tracks. ### Title
Cross-organization webhook forgery via decoupled signature-org selection and target-repository resolution — ([File: app/controllers/shipit/webhooks_controller.rb])

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App config used to validate `X-Hub-Signature` from `repository_owner` (`repository.owner.login`/`organization.login`), a value read straight out of the still-unverified JSON body. Separately, `Webhooks::Handlers::Handler#repository_name` resolves the `Stack`/`Repository` actually mutated by the handler from `repository.full_name` in the same unverified body. These two fields are never cross-validated. In a multi-org Shipit deployment (a first-class, documented configuration — see `Shipit.github_organizations`, `github_app_config`, and `test/dummy/config/secrets_double_github_app.yml`), if any single configured organization has a blank `webhook_secret` (explicitly documented as "optional" in `docs/setup.md`), `GitHubApp#verify_webhook_signature` unconditionally returns `true` for events attributed to that org. An attacker can therefore submit a forged webhook naming the unsecured org in `repository.owner.login`/`organization.login` (satisfying verification) while pointing `repository.full_name` at a completely different, secured organization's tracked repository, causing state-changing handlers (push sync, PR-driven review-stack creation/archival, label-driven provisioning) to execute against that victim repository/stack.

### Impact Explanation
This breaks the "organization that authenticated vs. repository that is written" trust boundary called out for this class of finding. The most severe path (`PullRequest::OpenedHandler` → `ReviewStackAdapter#create!`) results in Shipit creating a `Stack` and enqueueing it into `ReviewStackProvisioningQueue`, i.e., triggering an unauthorized deploy/provisioning cycle for a repository/PR combination the attacker fabricated and never had GitHub access to. Other handlers (push → `GithubSyncJob`, label handlers → archive/unarchive/provisioning-queue changes) similarly let the attacker manipulate real stacks belonging to a different, properly-secured organization, purely by exploiting a weakly-configured sibling organization.

### Likelihood Explanation
Exploitability is gated on a realistic, explicitly-supported configuration state: a multi-organization Shipit install where at least one org intentionally omits `webhook_secret` (documented as optional, and shown unset in the repo's own multi-org example config). No GitHub credentials, `ApiClient` token, or Shipit session are needed — only knowledge that such an org exists (discoverable from public webhook delivery behavior/HTTP responses) and the target's `owner/repo` full name.

### Recommendation
Verify the webhook signature using the organization actually referenced by the event's `repository.full_name` (not a separately-controlled `owner.login`/`organization.login` field), and/or require that `repository.owner.login` match the owner segment parsed from `repository.full_name` before dispatching to handlers. Consider also making `webhook_secret` mandatory for every configured organization rather than optional, since a single unsecured org effectively disables authentication for all other message content sharing that endpoint.

### Proof of Concept
1. Configure Shipit with two orgs: `OrgA` (no `webhook_secret`) and `OrgB` (secured, hosts a tracked `victim-repo` with review stacks enabled).
2. POST to `/webhooks` with header `X-Github-Event: pull_request` and no/garbage `X-Hub-Signature`, body:
```json
{
  "action": "opened",
  "number": 9999,
  "organization": {"login": "OrgA"},
  "repository": {"owner": {"login": "OrgA"}, "full_name": "OrgB/victim-repo"},
  "pull_request": { "...": "attacker-controlled head/branch/user" },
  "sender": {"login": "attacker"}
}
```
3. `repository_owner` resolves to `OrgA`; `Shipit.github(organization: "OrgA").verify_webhook_signature` returns `true` because `OrgA` has no `webhook_secret`.
4. `OpenedHandler` resolves the repository via `params.repository.full_name` = `OrgB/victim-repo`, and calls `ReviewStackAdapter#find_or_create!`, provisioning a new review stack/deploy for `OrgB`'s repository despite the request never being authenticated by `OrgB`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
