### Title
Webhook `status` events are authenticated per-organization but write to commits with no repository scoping, allowing cross-organization commit-status forgery - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit supports configuring multiple independent GitHub Apps/organizations, each with its own `webhook_secret` [1](#0-0) . The `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature with using the payload's own `repository.owner.login` (falling back to `organization.login`) field [2](#0-1) [3](#0-2) . Once the signature check succeeds for *that* organization, the parsed payload is dispatched, unscoped, to event handlers. `StatusHandler`, unlike every other handler, never restricts its lookup to the repository/organization that authenticated the request — it looks up commits globally by `sha` alone and writes an attacker-controlled status onto them.

### Finding Description
The binding that should hold is:

`organization that authenticated the webhook (via its own webhook_secret) == organization whose repository/commit data gets written`

`WebhooksController#verify_signature` derives the app/secret used for verification from `repository_owner`, taken straight out of the untrusted JSON body: [4](#0-3) [3](#0-2) 

All other handlers that touch repository-scoped data resolve the target strictly through `repository_name` (`payload.dig('repository', 'full_name')`), e.g. the base `Handler#stacks` helper [5](#0-4) , and `PushHandler`/`CheckSuiteHandler`/the PR handlers all filter through that repository-derived scope before touching any record [6](#0-5) [7](#0-6) .

`StatusHandler` breaks this pattern completely — it never references `repository_name`/`stacks` at all, and instead performs a global lookup by commit SHA across the entire instance: [8](#0-7) 

Because signature verification is keyed to `repository.owner.login` while `StatusHandler` acts on whatever `sha` appears in the same payload with zero repository/organization scoping, an attacker who legitimately controls one onboarded organization ("Org A", with its own valid `webhook_secret` in a multi-org Shipit deployment) can craft a `status` event whose `repository.owner.login` is `"OrgA"` (so the signature is verified against Org A's own secret, which the attacker legitimately knows/controls) but whose `sha` is a commit SHA belonging to a completely different organization's ("Org B") stack. Because `Commit.where(sha: params.sha)` is not filtered by repository at all, the forged status (`state`, `description`, `target_url`, `context` — all attacker-controlled payload fields) is written onto Org B's commit via `commit.create_status_from_github!(params)`.

This is precisely analogous to the reported `NativeVault` bug: there, the field verified (`assetSlashingHandlers[asset]`) and the field actually enforced (`slashStore`, freely chosen by the operator) were allowed to diverge, silently breaking a security invariant. Here, the organization identity verified by the HMAC signature (`repository.owner.login`) and the organization whose data is actually mutated (implicitly, whichever org owns the commit matching `sha`) are allowed to diverge, because `StatusHandler` omits the repository-scoping check every sibling handler performs.

### Impact Explanation
Commit statuses are used by Shipit to gate deploy/merge safety (`ci.require`, `release_status_context`, etc., per README) [9](#0-8) . An attacker who controls a legitimately-configured tenant organization in a multi-org Shipit instance can forge a passing/failing CI status on a commit belonging to an unrelated organization's repository, without any GitHub-side involvement — purely by sending a self-signed webhook whose `repository.owner.login` matches their own org while embedding a foreign `sha`. This constitutes a cross-organization write of state that can satisfy status-based deploy gating in another organization's stack, matching the "unauthorized deploy" / "cross-repository writes" impact tier.

### Likelihood Explanation
Requires the Shipit instance to be configured with more than one GitHub organization (the documented multi-org configuration) and requires the attacker to know/guess a target commit SHA belonging to another org's repository — SHAs of commits on any repository the attacker can view (e.g. a public repo, or one they have any read access to through GitHub itself) are trivially obtainable. No secrets belonging to the victim organization are needed; the attacker only ever uses their own organization's legitimately-configured `webhook_secret`.

### Recommendation
`StatusHandler#process` (and any other handler that doesn't already do so) must scope its lookup to the repository identified in the payload before touching any `Commit`, e.g. by joining through `Repository.from_github_repo_name(payload.dig('repository','full_name'))`/`stacks` the same way `PushHandler`, `CheckSuiteHandler`, and the pull-request handlers already do, and by asserting that the resolved repository's `owner` matches the `repository_owner` used to verify the signature.

### Proof of Concept
1. Configure Shipit with two organizations, `orga` and `orgb`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md`'s "Using Multiple Github Applications" section).
2. As the operator/attacker of `orga` (who legitimately knows `orga`'s `webhook_secret`), craft a `status` event payload:
```json
{
  "sha": "<sha of a commit belonging to a stack under orgb/some-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "repository": { "owner": { "login": "orga" } }
}
```
3. Compute `X-Hub-Signature` using `orga`'s own `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "orga")` and verifies successfully [4](#0-3) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `orgb` commit regardless of the authenticated organization — and calls `commit.create_status_from_github!(params)`, writing the forged status onto `orgb`'s commit [8](#0-7) .

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
