### Title
Pre-funding a predictable AA address before its definition is posted forces an unbounded genesis-to-date balance scan on every node - ([File: storage.js])

### Summary
The reported Olas bug is a "reference-before-existence" gas-griefing pattern: an attacker predicts the deterministic address of a not-yet-created entity, registers it early, and forces whoever later interacts with that entity to iterate a large, useless range accumulated since registration. Obyte's Autonomous Agent (AA) address space has the exact same predictability property — an AA address is `chash160(definition)`, fully deterministic and computable off-chain before the definition is ever posted — and `storage.insertAADefinitions()` performs an unbounded backward aggregation over the `outputs` table for that address once the AA is finally defined.

### Finding Description
An AA's address is derived purely from `objectHash.getChash160(definition)` (as used throughout `test/aa_composer.test.js`, e.g. `objectHash.getChash160(bouncer_aa)` [1](#0-0) ), so anyone who knows (or can guess/observe) the future AA's definition JSON can compute its address long before the AA author actually posts the `definition` message that activates it.

When the defining unit finally stabilizes (for a "regular" AA, i.e. one defined by a normal address, not by another AA), `storage.insertAADefinitions()` inserts the AA into `aa_addresses` and then computes its initial `aa_balances` by summing **all** matching rows in the `outputs` table for that address: [2](#0-1) 

For the regular-AA path (`bForAAsOnly` is false, i.e. `bImmediatelyVisible` is always false), the condition used is the unbounded one:
```
const mci_cond = bImmediatelyVisible
    ? "(main_chain_index<=? OR is_aa_response=1) AND outputs.unit!=?"
    : "(main_chain_index<? " + or_sent_by_aa + ")";
``` [3](#0-2) 

This means the query
```sql
SELECT address, IFNULL(asset,'base'), SUM(CAST(amount AS DOUBLE)) AS balance
FROM outputs
CROSS JOIN units USING(unit)
LEFT JOIN assets ON asset=assets.unit
WHERE address=? AND is_spent=0 AND sequence='good' AND main_chain_index<? AND (is_private=0 OR is_private IS NULL)
GROUP BY address, asset
```
scans **every unspent output ever sent to that address since genesis**, with no lower MCI bound tied to when the AA was actually created — exactly mirroring the staking report's `firstClaimedEpoch = mapLastClaimedStakingEpochs[nomineeHash]` being frozen at the (early) registration epoch instead of the entity's real creation epoch.

Because the address is not yet an AA when these outputs are posted, ordinary wallets/users can freely send tiny "dust" payments to it (it behaves like any normal address until the definition unit lands). An attacker can therefore:
1. Compute the address of a soon-to-be-deployed popular AA (or any AA whose source code/definition becomes public/predictable ahead of deployment, e.g. open-source dApps, template-based AAs, or AAs created as children of other AAs whose `base_aa`+params are guessable).
2. Flood that address with a very large number of low-value payment outputs over an extended period before the definer's `definition` unit is posted and stabilizes.
3. When the AA is finally defined, every full node processing the stabilizing unit must run the unbounded `SUM` aggregation over all of those attacker-created rows as part of `insertAADefinitions()`, which itself runs inside the unit-writing pipeline under the global `write` mutex (`writer.js` `saveJoint`), i.e. synchronously blocking further unit processing on the node.

Note that a partial mitigation (`pemCurvesFixMci` / `bImmediatelyVisible`) already exists for the "AA-defined AA" case (an AA created by another AA's `definition` message), bounding the scan to `main_chain_index<=trigger_mci OR is_aa_response=1`. But this bound is only applied when `bForAAsOnly` is true; the common human-authored AA definition path still uses the unbounded `main_chain_index<?` condition with no floor at all.

### Impact Explanation
This is not merely a single caller's gas cost (as in the original finding) but a synchronous, consensus-path cost imposed on **every full node** that processes the AA-defining unit's stabilization, inside the write-lock critical section. A sufficiently large volume of pre-funding dust outputs could turn a normally cheap AA activation into an expensive, node-stalling aggregation query, delaying subsequent unit processing/stabilization network-wide for that node — a griefing/DoS vector against AA deployment that is strictly worse in blast radius than the original per-claimer gas bug, since it affects consensus-critical unit processing rather than an optional claim call by one party.

### Likelihood Explanation
Likelihood is moderate: it requires (a) an attacker to learn/guess an AA's definition (and hence its address) before it is deployed, and (b) the attacker to spend real bytes creating many small payment outputs to that address, which has an ongoing cost to the attacker (dust outputs still cost network fees) but is much cheaper than the aggregate query cost it imposes on every node, and cheaper than the value it can lock or delay. AAs deployed from open-source templates, factory-created child AAs with `base_aa`+deterministic params, or any AA whose deployment is anticipated (e.g. announced in advance) are prime targets, making this a realistic, not purely theoretical, scenario.

### Recommendation
- Bound the balance-recalculation query for regular (non-AA-defined) AAs by the address's actual "birth" reference point, analogous to the `bImmediatelyVisible` fix already applied to AA-defined AAs, rather than scanning from genesis (`main_chain_index<?` with no lower bound).
- Alternatively, cap/paginate the number of pre-existing outputs credited to a newly-activated AA, or require outputs sent to an as-yet-undefined address that later becomes an AA to be handled lazily (accounted for on first AA execution) rather than via a single unbounded aggregate at definition time.
- Add safeguards (e.g., a maximum number of qualifying rows, or a maximum lookback window) so that the cost of activating an AA cannot be inflated by third parties independent of the AA author's actions.

### Proof of Concept
1. Compute `address = chash160(definition)` for an AA whose definition is known in advance (e.g. copied from a public template or a child AA created via `base_aa` with predictable params, as shown in `test/aa_composer.test.js` where `child_aa_address = objectHash.getChash160(child_aa)` is derivable before the AA is actually posted [4](#0-3) ).
2. Before the legitimate author posts the `definition` message for this address, send a large number of separate small payment units to `address` (ordinary payments; the address is not yet marked as an AA so this is accepted like any regular address).
3. Wait until the author posts the unit containing `{app: 'definition', payload: {definition: ...}}` for that address and it stabilizes.
4. Observe that `storage.insertAADefinitions()` runs the unbounded query at [5](#0-4)  with `mci_cond = "main_chain_index<?"` (no lower bound), aggregating over all of the attacker's injected outputs — with cost scaling with however many dust outputs the attacker chose to send, executed synchronously under the write lock on every full node.
