### Title
Webhook org selected for signature verification is decoupled from the repository acted upon, allowing forged status/push events for any tracked repo when any configured organization has no `webhook_secret` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's HMAC secret to verify a webhook against using the attacker-supplied `repository.owner.login` (or `organization.login`) field of the raw JSON body, but every event handler then acts on a completely different field of that same untrusted body — `repository.full_name` — to decide which `Stack`/`Repository`/`Commit` to mutate. Because these two fields are never checked for consistency, and because `GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatic success, an attacker can pick an organization value that has no configured secret to sail through verification while pointing `repository.full_name` at any other repository tracked by the instance.

### Finding Description
Verification selects the app/secret from the payload itself: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` short-circuits to `true` whenever the resolved organization has no `webhook_secret` configured: [3](#0-2) 

The engine explicitly supports multiple organizations, each with its own independent config (including independently blank/absent `webhook_secret`), as shown by the multi-app fixture: [4](#0-3) [5](#0-4) 

Once verification passes, every handler resolves the target repository/stacks using a *different* field of the same attacker-controlled body — `repository.full_name` — with no re-check against `repository.owner.login`: [6](#0-5) 

For example, `PushHandler` triggers `sync_github` for whatever stacks match that (attacker-chosen) `full_name`/branch: [7](#0-6) 

`StatusHandler` writes a commit status record straight from attacker-supplied `state`/`description`/`target_url` for any commit matching `sha`, without any relation to the org used for verification: [8](#0-7) 

**The broken binding, as an equality that should hold but doesn't:**
`organization used to select webhook_secret for HMAC verification (repository.owner.login)` == `organization/repository actually mutated by the handler (repository.full_name)`

Before the attack: an operator assumes a request that passes `verify_signature` is a genuine GitHub-originated event *for the repository the handler will act on*.
After the attack: an unauthenticated caller crafts a POST to `/webhooks` (this endpoint has no session/API-token requirement, only `verify_signature`) with `repository.owner.login = "<org-with-no-secret-or-unmapped>"` (or omits/mismatches it) so the HMAC check trivially passes (`return true unless webhook_secret`), while setting `repository.full_name = "<victim-org>/<victim-repo>"`. All downstream handler logic (`Handler#repository_name`, `PushHandler`, `StatusHandler`, `pull_request/*` handlers, `merge_status`, `check_suite`, etc.) acts on the victim repo/stack, with zero requirement to know that org's real webhook secret.

### Impact Explanation
This lets an unprivileged, unauthenticated network attacker forge GitHub events for any stack tracked by the Shipit instance, as long as *any* configured organization on that instance lacks a `webhook_secret` (a supported and demonstrated configuration in this codebase). Concretely:
- `StatusHandler` lets the attacker fabricate a `success` CI status for an arbitrary commit sha in the victim repo/stack, which can satisfy `release_status?`/CI gating and unlock a deploy the real CI never approved.
- `PushHandler` can force premature `sync_github` calls, and combined with `continuous_deployment`, can push forward the deployed head based on forged event timing.
- Other handlers (`pull_request/*`, `merge_status`, `check_suite`) let the attacker manipulate PR/merge-queue/review-stack state for repositories they have no access to.

This crosses the "cross-repository writes" / "unauthorized deploy" impact bar from the rules, because state belonging to one organization's stacks is mutated by a request that was only ever authenticated (trivially, due to blank secret) against an unrelated organization.

### Likelihood Explanation
Requires: (1) at least one organization configured on the Shipit instance with no `webhook_secret` (the codebase ships/tests this exact configuration), and (2) knowledge of a tracked victim repo's `full_name` and a valid commit `sha` (both are public GitHub information). No credentials, API tokens, or GitHub App secrets are needed — the `/webhooks` endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`) and relies solely on `verify_signature`, which this bug bypasses. This is directly reachable by an unprivileged external attacker.

### Recommendation
Bind verification and processing to the same trusted identity: after signature verification succeeds for organization `O`, require that `repository.full_name`'s owner segment equals `O` (or, better, resolve the target `Repository`/`Stack` first, look up which organization it belongs to, and verify the signature using exactly that organization's secret — rejecting the request if no such organization/secret is configured, rather than treating a missing secret as automatic success). Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank for organizations that host production stacks.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. as in `test/dummy/config/secrets_double_github_app.yml`, where `OrgOne` has no `webhook_secret` and `OrgTwo` is the victim org with tracked stacks (or simply have any org without a `webhook_secret` alongside the target org).
2. `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<real commit sha of victim stack>",
  "state": "success",
  "description": "forged",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
`repository_owner` resolves to `OrgOne`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of `X-Hub-Signature` (`lib/shipit/github_app.rb:76-83`).
3. `StatusHandler#process` runs and creates a `success` status on the matching commit belonging to `OrgTwo/victim-repo` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), even though the request was never validated against `OrgTwo`'s secret.
4. If `OrgTwo`'s stack has `release_status?` gating tied to this status context and `continuous_deployment` enabled, this can trigger an unauthorized deploy.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
