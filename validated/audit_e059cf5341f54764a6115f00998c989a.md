### Title
Missing team-authorization check in `MergeStatusController#show` discloses merge/lock state to any logged-in-but-unauthorized GitHub user - (File: app/controllers/shipit/merge_status_controller.rb)

### Summary
`MergeStatusController` uses `skip_authentication only: %i[check show]` to bypass the `force_github_authentication` before_action, which is the only place `current_user.authorized?` (Shipit.github_teams membership) is enforced. `#show` only checks `current_user.logged_in?`, so any GitHub account that completes OAuth sign-in - regardless of team membership - can read merge queue/lock status for any stack by supplying a `referrer` URL, bypassing the authorization gate applied everywhere else in the app.

### Finding Description
The broken binding is: everywhere else in the app, access requires `current_user.authorized?` == true (i.e., `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?`), enforced by `force_github_authentication` in [1](#0-0) . `MergeStatusController` skips this before_action for `show`/`check` via [2](#0-1) , and `#show` substitutes only `current_user.logged_in?` [3](#0-2) . `User#logged_in?` unconditionally returns `true` for any persisted `User` record created via GitHub OAuth [4](#0-3) , while `authorized?` is a separate, stricter, team-membership check [5](#0-4) . Any GitHub user can complete the OAuth flow via `GithubAuthenticationController#callback`, which creates/finds a `User` and sets `session[:user_id]` with no team check at all [6](#0-5) ; only the subsequent `force_github_authentication` before_action (skipped here) would block non-team-members. `#stack` resolves the target purely from the unauthenticated `referrer`/`branch` query params against `repositories.owner/name`, with no per-repository or per-team check [7](#0-6) [8](#0-7) . The resulting render exposes `stack_status` (merge_status computed from queue/lock state) and `queue_enabled?`/`merge_request` state to that unauthorized-but-logged-in caller.

Existing guards fail here specifically because they are implemented as a single controller-wide before_action (`force_github_authentication`) that is entirely skipped for this action, rather than a per-action authorization check; the only remaining gate (`current_user.logged_in?`) checks authentication, not authorization/team membership.

### Impact Explanation
A GitHub user who is not a member of any `Shipit.github_teams` (and therefore is blocked from every other page: `StacksController#index`, etc., per `StacksControllerTest#"current_user must be a member of at least a Shipit.github_teams"` behavior [9](#0-8) ) can nonetheless repeatedly query `/merge_status?referrer=...&branch=...` for any repository/stack in the Shipit instance and learn its merge queue enabled state, lock state, and merge-request queue status. This is a cross-tenant authorization escalation matching the "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state" High severity category, since it discloses operational state for repositories/orgs the caller has no legitimate access to, repeatably and for arbitrary stacks.

### Likelihood Explanation
Preconditions are low-cost for the attacker: they only need any GitHub account (to complete OAuth once) and knowledge/guessability of a target repo owner/name and branch (which is often public information, e.g. from a public GitHub PR URL). No Shipit secrets, webhook signing keys, or repository membership are required. The `Shipit.github_teams` restriction exists precisely to gate the rest of the app, making this a real, demonstrated bypass rather than a theoretical one.

### Recommendation
In `MergeStatusController#show`, check `current_user.authorized?` (not just `logged_in?`) before rendering stack status, or remove `show`/`check` from `skip_authentication` and instead render the `logged_out` page for genuinely anonymous users while still enforcing `force_github_authentication`'s authorization branch for authenticated-but-unauthorized users.

### Proof of Concept
In `test/controllers/merge_status_controller_test.rb`:
1. Create/authenticate a `User` who is logged in (`session[:user_id] = user.id`) but is **not** a member of any team in `Shipit.github_teams` (mirror the setup from `StacksControllerTest#"current_user must be a member of at least a Shipit.github_teams"`).
2. `Shipit.stubs(:github_teams).returns([shipit_teams(:shopify_developers)])` (a team the test user does not belong to).
3. `GET :show, params: { referrer: "https://github.com/Shopify/shipit-engine/pull/1", branch: "master" }`.
4. Assert `response` is **not** `logged_out` (i.e., not rendering the `logged_out` template) and instead renders `stack_status`/merge state (e.g. `assert_select` for lock/queue markup, or assert `response.body` includes stack status content) — demonstrating that `current_user.authorized?` is `false` (equality broken: `authorized? == false` but response still discloses stack state) while an equivalent request to `StacksController#index` for the same user returns `403 Forbidden`.

    class ReferrerParser
      URL_PATTERN = %r{\Ahttps://github\.com/([^/]+)/([^/]+)/pull/(\d+)}

      attr_reader :repo_owner, :repo_name, :pull_request_number

      def initialize(referrer)
        unless (match_info = URL_PATTERN.match(referrer.to_s))
          raise ArgumentError, "Invalid referrer: #{referrer.inspect}"
        end

        @repo_owner = match_info[1].downcase
        @repo_name = match_info[2].downcase
        @pull_request_number = match_info[3].to_i
      end
    end
