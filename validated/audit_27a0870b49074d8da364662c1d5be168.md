This confirms every element of the reported chain. Multi-tenant orgs are configured under `secrets.github` keyed by org (e.g. `github_organizations`), each with its own `webhook_secret` [1](#0-0) . `Shipit.github(organization: repository_owner)` looks up the config for whatever org name is in the payload, and `GitHubApp#verify_webhook_signature` returns `true` immediately if that org's `webhook_secret` is blank/not configured [2](#0-1) . The controller uses that unsigned result to gate the request, but then dispatches the parsed body without any repository-scoping check [3](#0-2) . `StatusHandler#process` runs `Commit.where(sha: params.sha)` — a global query with no join/filter on `stack_id`/`repository` — so it will update *any* commit across *any* stack in the whole install that happens to share that SHA, or attacker can simply reuse/guess a victim stack's known SHA [4](#0-3) . The written status feeds `Status::Common#blocking?` and `Commit#blocked?`, which is consulted by `deployable?` and `UndeployedCommit#deploy_state`, directly gating whether a stack can deploy [5](#0-4) [6](#0-5) .

### Title
Cross-tenant `status` webhook forgery via no-secret organization forges/clears blocking statuses and gates deploys - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
When a GitHub organization is registered in Shipit's multi-tenant config without a `webhook_secret`, `GitHubApp#verify_webhook_signature` accepts any unsigned request for that org. Because `StatusHandler` resolves the target commit purely by SHA with no ownership/repository check, an attacker who merely names a payload's `repository.owner.login` as that no-secret org can write a forged `status` for a commit belonging to a completely different (victim) stack, directly manipulating `blocked?`/`deployable?` gating for that victim's deploys.

### Finding Description
The broken binding: the invariant the engine relies on is `authenticated_org == status.repository.owner` (the org whose secret validated the HMAC must be the same org whose commit is mutated). In practice the code enforces `verified == true` where `verified = GitHubApp(new_org_from_payload).verify_webhook_signature(sig, body)` [7](#0-6) , and `verify_webhook_signature` returns `true` unconditionally `unless webhook_secret` [2](#0-1) , so an org entry present in `secrets.github` but missing `webhook_secret` authenticates *any* payload naming it, with no signature at all.

Once past `verify_signature`, `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('status')`, invoking `StatusHandler#process`, which executes `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` [4](#0-3) . This query has zero scoping by `repository_owner`/`stack_id`/`repository` — any commit row in the entire database matching the attacker-supplied SHA is mutated, regardless of which org or repository it actually belongs to.

Attacker request: `POST /webhooks` with header `X-Github-Event: status`, no `X-Hub-Signature` (or garbage), and body `{"repository": {"owner": {"login": "no-secret-org"}}, "sha": "<victim-commit-sha>", "state": "failure", "context": "<victim's-blocking-context>"}`. Since `no-secret-org` is a configured organization with a blank `webhook_secret`, `verify_signature` passes; `StatusHandler` then finds the victim's `Commit` by SHA and writes a new `Status` for it.

This status feeds `Status::Common#blocking?` (`!success? && commit.blocking_statuses.include?(context)`) [5](#0-4)  and `Commit#blocked?`, which scans reachable, undeployed commits for any `blocking?` status [8](#0-7) . `deployable?` and `UndeployedCommit#deploy_state`/`deploy_disallowed?` consult `blocked?` directly, so forging a failing/blocking context status can freeze a victim stack's deploy pipeline; conversely forging a passing status for the correct `context` can clear a legitimate block and unlock deploys the victim's real CI intended to prevent.

Existing guards fail because: `verify_signature` treats "org is configured" as sufficient trust regardless of whether that org actually has a shared secret; `drop_unhandled_event` only checks the event type is registered, not the repository; `StatusHandler`'s `ExplicitParameters` schema validates payload shape (`sha`, `state`, etc.) but never asserts the target `Commit#stack`'s repository/owner matches `repository_owner` from the payload.

### Impact Explanation
The attacker causes a **payload for one repository (any no-secret configured org) to mutate another repository/stack's `Commit`/`Status` records**, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Concretely, it can: (1) block a victim's continuous deployment by forging a failing status in a `blocking_statuses` context, denying legitimate releases (denial of legitimate deploy), or (2) clear a real block by forging a `success` status in the exact blocking context, potentially enabling an unauthorized deploy of code that failed a compliance/security gate. This is repeatable against any commit SHA in the install (SHAs are often public/guessable from PR/branch history) as long as at least one configured org lacks a `webhook_secret`, and the blast radius spans every stack/repository in the Shipit instance, not just the attacker's own.

### Likelihood Explanation
Preconditions: Shipit must be running the multi-tenant `github_organizations` configuration (`secrets.github` keyed by org name, per `github_default_organization`/`github_app_config`) [9](#0-8) , and at least one configured organization entry must have no `webhook_secret` set (an operator misconfiguration, not attacker-controlled). Given that precondition, attacker cost is minimal: a single unauthenticated `curl` POST with a known/guessed victim SHA and context name, repeatable at will. No Shipit or GitHub secrets are required. Likelihood is entirely contingent on this specific multi-tenant misconfiguration existing.

### Recommendation
Reject webhooks for organizations configured without a `webhook_secret` (treat blank secret as "deny", not "allow") in `GitHubApp#verify_webhook_signature`, or require every entry in `secrets.github` to define a non-blank `webhook_secret` at boot. Additionally, scope `StatusHandler` (and other handlers using bare `sha`/`ref` lookups) by the authenticated `repository_owner`/`repository.full_name`, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { owner: repository_owner, name: params.dig('repository','name') })`, so a payload can only ever touch commits belonging to the repository that actually authenticated it.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status event from a no-secret configured org cannot mutate another repository's commit" do
  # Arrange: configure a second org "attacker-org" in secrets.github with no webhook_secret,
  # and the victim stack's org "shipit" WITH a webhook_secret (already the default fixture).
  victim_commit = shipit_commits(:soc_second) # belongs to a stack with blocking_statuses configured
  refute victim_commit.blocked? # baseline: binding holds -- authenticated_org == commit.stack.repository.owner

  request.headers['X-Github-Event'] = 'status'
  forged_body = {
    repository: { owner: { login: 'attacker-org' }, full_name: 'attacker-org/unrelated-repo' },
    sha: victim_commit.sha,
    state: 'failure',
    context: victim_commit.stack.blocking_statuses.first
  }.to_json

  # No X-Hub-Signature header at all (unsigned)
  assert_difference '-> { victim_commit.reload.statuses.count }', 1 do
    post :create, body: forged_body, as: :json
  end

  assert_response :ok
  assert_predicate victim_commit.reload, :blocked? # binding broken: attacker-org's payload mutated victim stack's commit
end
```
This demonstrates the equality `authenticated_org == commit.stack.repository.owner` no longer holds after the request: the request was authenticated (trivially) as `attacker-org`, yet it wrote a `Status` on, and altered `blocked?` for, a commit belonging to an entirely different repository/stack.
