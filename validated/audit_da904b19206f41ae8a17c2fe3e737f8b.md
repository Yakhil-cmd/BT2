### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, allowing a stack-scoped token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by `Shipit::Api::BaseController` and resolves the target `Stack` directly from `params[:stack_id]` with no scoping applied, whereas every other API controller uses the scoped `stacks` helper. This breaks the equality "the stack an `ApiClient` token authorizes == the stack the request touches," allowing a legitimately-issued, narrowly stack-scoped token to read the CI/build status of any stack in the Shipit instance.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` enforces this scope for every resource lookup through the `stacks` helper, which restricts the queryable set of stacks to the client's bound `stack_id` when one is present, before resolving `params[:stack_id]`: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, defines its own private `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, completely bypassing the `stacks` scoping helper: [3](#0-2) 

The controller's only authorization check is `require_permission :read, :stack`, which merely verifies the client's `permissions` array includes `'read:stack'` — it does not verify which stack the permission applies to [4](#0-3) . Because `stack` resolves against the global `Stack` relation instead of the scoped `stacks` relation, any client holding `read:stack` — even one deliberately bound to a single stack via `stack_id` — can supply any other stack's `id`/slug in `params[:stack_id]` and receive that stack's CCMenu XML payload, which includes the latest deploy/rollback status, timestamps, and running state [5](#0-4) .

The scoping bypass is specific to this controller: the equivalent `stack` resolution in `BaseController` (used by `StacksController`, `TasksController`, `DeploysController`, etc.) is correctly scoped, confirming that stack-scoped `ApiClient` tokens are meant to be confined to their bound stack across the API surface.

### Impact Explanation
This is an unauthenticated-relative-to-other-stacks read of stack state / deploy output: a token that was deliberately restricted to one stack (e.g., handed to a third-party CI dashboard integration for a single, non-sensitive stack) can be used to enumerate and read the deploy status of every other stack managed by the Shipit instance, including stacks the token holder was never granted visibility into. This matches the "High" impact category of "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission can trigger this with a single unauthenticated (from the target stack's perspective) HTTP GET, using only knowledge or guessing of another stack's id/slug — no additional privilege, signature forgery, or race condition is required. Stack ids/slugs are low-entropy and often predictable (repo/environment names), making enumeration straightforward.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` helper (as `BaseController#stack` and all other API controllers do), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that stack-scoped tokens cannot query stacks outside their bound `stack_id`.

### Proof of Concept
1. An admin creates (or a user obtains via `CCMenuUrlController#fetch`) an `ApiClient` scoped to `stack_id = A` with `permissions: ['read:stack']`, intended only for a CI dashboard integration monitoring stack A.
2. The token holder issues:
   `GET /api/stacks/<STACK_B_SLUG>/ccmenu.xml?token=<TOKEN_SCOPED_TO_A>`
3. `CCMenuController#authenticate_api_client` authenticates the token successfully (`ApiClient.authenticate` only checks token validity, not stack binding) [6](#0-5) .
4. `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, irrespective of which stack it is bound to.
5. `stack` resolves `STACK_B_SLUG` via unscoped `Stack.from_param!`, returning stack B even though the token is bound to stack A.
6. The response renders stack B's latest deploy/rollback status, disclosing deployment state the token was never authorized to see.
