### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on the independently-read `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and its `webhook_secret`) to validate an inbound webhook's HMAC using `repository_owner`, computed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1)  Once the signature is accepted, the actual event handlers (e.g. `PushHandler`, `CheckSuiteHandler`) resolve the target `Repository`/`Stack` from a *different* JSON field in the same payload: `repository.full_name`, via `Handler#repository_name` / `#stacks`. [3](#0-2) 

### Finding Description
In a multi-organization Shipit deployment (`config/secrets.yml` supports multiple GitHub orgs, each with its own `app_id`/`webhook_secret`, as shown in `test/dummy/config/secrets_double_github_app.yml`), the trust boundary that should hold is:

`organization whose webhook_secret authenticated the request == organization owning the repository the handler acts on`

The code breaks this equality because the two fields are read independently from the same attacker-influenceable JSON body, and nothing cross-validates `repository.owner.login` against `repository.full_name`:
- Signature selection: `repository_owner` = `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`. [2](#0-1) 
- Handler dispatch target: `repository_name` = `payload.dig('repository', 'full_name')`, used to look up `Repository.from_github_repo_name` and thus the `Stack`s to act on. [3](#0-2) 

Because the HMAC in `verify_webhook_signature` covers the raw POST body, a party who legitimately controls one configured organization (and therefore possesses/can produce a validly-signed payload for that org, e.g. by installing/administering their own GitHub App instance under that org as an app owner) can build a payload where `repository.owner.login` = "their org" (so the correct low-privilege secret authenticates it) while `repository.full_name` = "victim-org/victim-repo" (a different, higher-value repository tracked by the same Shipit instance). `verify_signature` only checks that the body was signed by the org named in `repository.owner.login`; it never asserts that this org actually corresponds to the repository named in `repository.full_name`.

For the `push` event, `PushHandler#process` uses `stacks` (derived from `repository.full_name`) and, for any non-archived stack on the matching branch, calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing `GithubSyncJob` against the victim stack. [4](#0-3)  `GithubSyncJob` fetches commits via the stack's own GitHub API credentials and, if the reported `expected_head_sha` isn't found, retries; if commits are found it appends them and enqueues `CacheDeploySpecJob`. [5](#0-4)  If the victim stack has continuous deployment enabled, a forged push notification can prompt Shipit to believe new commits/HEAD exist, feeding into the continuous-delivery pipeline (`Stack.schedule_continuous_delivery`, `trigger_continuous_delivery`) without the attacker having any access to the victim's actual GitHub organization, repo, or its real webhook secret. [6](#0-5) 

`CheckSuiteHandler` has the identical pattern: it resolves `stacks` from `repository.full_name` and schedules `schedule_refresh_check_runs!` on the victim's commits using attacker-supplied `head_sha`/`head_branch`. [7](#0-6) 

### Impact Explanation
This crosses the "organization authenticated versus repository written" boundary called out in the review guidance. It allows an attacker who controls one organization onboarded to a shared Shipit instance (a low-privilege, legitimately-configured tenant) to forge webhook-driven side effects (sync jobs, check-run refreshes, and potentially continuous-delivery triggers) against a completely different organization's stack that they have no access to. Depending on the victim stack's continuous-deployment configuration, this can escalate into an unauthorized deploy being kicked off from forged commit-sync state, which matches the Critical "unauthorized deploy" impact bucket.

### Likelihood Explanation
Exploitability requires the attacker to be an actual GitHub App owner/admin of one of the organizations configured in Shipit's `secrets.yml` (multi-tenant deployments) — this is a lower-privilege boundary than a Shipit account or `ApiClient` token, matching the "unprivileged-attacker" framing relative to the victim org. Single-organization deployments are not exploitable this way because there is only one `webhook_secret` and `repository_owner` always matches the repo being acted on. I was not able to fully verify from the available files whether `Stack#sync_github`-driven appended commits can autonomously reach `trigger_continuous_delivery` without additional CI status webhooks also being forged (this depends on `deployable?`/CI check logic not fully traced here), so the "unauthorized deploy" escalation should be treated as likely but not fully confirmed from the indexed code alone.

### Recommendation
In `WebhooksController#verify_signature` and/or `Handler#repository_name`, cross-check that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting the webhook (HTTP 422) on mismatch.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with its own GitHub App/`webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As the owner/admin of `AttackerOrg`'s GitHub App, craft a `push` webhook JSON body where:
   - `repository.owner.login = "AttackerOrg"`
   - `repository.full_name = "VictimOrg/victim-repo"`
   - `ref = "refs/heads/<victim-stack-branch>"`, `after = "<attacker-chosen sha>"`
3. Sign the raw body with `AttackerOrg`'s webhook secret and POST to `/webhooks` with `X-Github-Event: push` and the resulting `X-Hub-Signature`.
4. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and confirms the HMAC — request passes. [1](#0-0) 
5. `PushHandler` resolves stacks via `repository.full_name = "VictimOrg/victim-repo"` and enqueues `GithubSyncJob` against the victim's stack, entirely outside `AttackerOrg`'s actual authorization scope. [4](#0-3)

```ruby
    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
```
