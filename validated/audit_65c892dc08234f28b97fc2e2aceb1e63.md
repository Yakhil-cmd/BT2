### Title
Asset metadata (ticker/name) spoofing lets any asset issuer impersonate a known asset in wallet UI - (File: wallet.js)

### Summary
CVE‑2020‑6502 is a Chrome bug where a malicious page could spoof a security‑relevant permission UI, tricking the user into believing they were interacting with a different, trusted origin. The closest reachable analog in `ocore` is asset‑metadata handling in `wallet.js`: an unprivileged asset issuer can publish a `data` message naming their newly‑issued asset with the same human‑readable ticker/name as an existing, trusted asset. The wallet UI (via `readAssetMetadata`/`fetchAssetMetadata`) displays this attacker‑chosen `name` field to the user without binding it uniquely to a single asset, so the user can be shown a spoofed asset identity ("security UI spoof") and be induced to send funds to what looks like a well‑known token but is actually the attacker's worthless one.

### Finding Description
`readAssetMetadata()` in `wallet.js` reads cached rows from the `asset_metadata` table and exposes `name` (optionally with `.suffix`) to the wallet UI as the token's display label: [1](#0-0) 

New metadata is populated by `fetchAssetMetadata()`, which fetches `{metadata_unit, registry_address, suffix}` from the hub via `hub/get_asset_metadata`, then reads the actual unit and pulls `payload.name` straight out of a `data` message whose only real requirement is that `objJoint.unit.authors[0].address === registry_address` and `payload.asset === asset`: [2](#0-1) 

Crucially, the `asset_metadata` schema's only uniqueness constraint is `UNIQUE(name, registry_address)`, not `UNIQUE(name)`: [3](#0-2) 

This means any address can act as its own "registry," issue a brand‑new asset, and self‑publish a `data` message giving it `name: "GBYTE"` (or the name of any other reputable asset/registry-managed token), as long as that name/registry_address pair is unique for that registry. Because the uniqueness key includes `registry_address`, a rogue registry address colliding on `name` with a legitimate, different registry is not prevented — the client stores both rows and will display whichever metadata it fetches/updates for the given `asset` id, with no cross-check that the `name` is globally unique or reserved. The wallet trusts and renders `payload.name` from any self-declared registry as the canonical human-readable label of an asset, which is the "security UI" (the identity of what asset you're paying/holding) being spoofed.

### Impact Explanation
A user who receives or is offered a spoofed asset with a name colliding with a well-known token (e.g., a stablecoin or popular custom asset) can be shown that name in balances, payment confirmation dialogs, and asset pickers. This can cause the user to unknowingly accept a payment in a worthless asset believing it is the reputable one, or send real funds intending to interact with the "real" registry-endorsed asset while actually engaging with the attacker's asset (loss of user funds / spend to wrong counterparty), i.e., unauthorized/misdirected spending caused by UI spoofing of asset identity, matching the Medium-severity bug class of the CVE.

### Likelihood Explanation
Any actor can issue a new asset (`asset` message) and register self-declared metadata (`data` message with `app: "data"`) for it — this requires no special privilege, matching the requirement that the attack surface be reachable by an "asset issuer." The hub-served `hub/get_asset_metadata` response is only checked for structural validity (`ValidationUtils.isValidAddress(registry_address)`, hash length of `metadata_unit`) and that the unit's author equals the claimed `registry_address` — but nothing stops the attacker from being the registry_address for their own asset. The remaining requirement is social engineering (getting a victim wallet to look at the spoofed asset, e.g., via a private/AA-triggered payment offering it), which parallels the "UI:R (user interaction required)" vector in the original CVE.

### Recommendation
- Do not treat self-declared registries as authoritative for a global namespace; require an explicit allow-list of trusted registry addresses recognized by the wallet before their `name` claims are rendered without qualification.
- Always display the `registry_address` (or a truncated/verified identity of it) alongside the asset `name` in the UI, rather than the bare `name`, so users can distinguish assets with colliding names from different registries.
- Enforce global uniqueness of `name` in `asset_metadata` only for recognized/trusted registries, and visually flag/mark metadata coming from unknown or newly-seen registries distinctly (e.g., "unverified asset name").

### Proof of Concept
1. Attacker issues a new `asset` unit (any user can post `asset` messages via `composer`/`indivisible_asset.js`/`divisible_asset.js`), obtaining `asset_X`.
2. Attacker uses their own address `R` as `registry_address` and posts a `data` message (`app: "data"`) with payload `{asset: asset_X, name: "GBYTE", decimals: 9}` inside unit `M`, authored by `R`.
3. Attacker runs (or convinces) a hub to serve `hub/get_asset_metadata` for `asset_X` returning `{metadata_unit: M, registry_address: R, suffix: undefined}` — this is exactly what `network.js`'s `hub/get_asset_metadata` handler serves from the `asset_metadata` table populated by the attacker's own client/registration flow: [4](#0-3) 
4. Victim wallet calls `fetchAssetMetadata('asset_X', ...)`, which validates only that `objJoint.unit.authors[0].address === R` and stores `name: "GBYTE"` for `asset_X` in `asset_metadata`, then displays it via `readAssetMetadata` as "GBYTE" to the user — spoofing the well-known asset's identity in the wallet UI.
