### Title
Cross-repository `Status` mutation via SHA collision in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and never restricts the result to the stacks/repository named in the incoming webhook payload, unlike the `Handler#stacks` helper defined in the base class. This lets a `status` webhook that names an attacker-owned repository still mutate `Status` rows attached to commits belonging to an entirely different, real tracked repository, as long as the commit `sha` values collide.

### Finding Description
The binding that should hold is:
`Handler#stacks` (i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`) `== the set of stacks whose commits receive a new Status in StatusHandler#process`.

In code: [1](#0-0) 
`process` never calls `stacks` or `repository_name` — it only does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. Meanwhile `Handler#stacks`/`#repository_name` exist precisely to scope work to the repository named in the payload: [2](#0-1) 

`Commit#sha` is a global git content hash, not a Shipit-scoped identifier, and multiple `Stack`s (potentially for entirely different repositories) can have `Commit` rows sharing the same `sha` if the same commit object (same tree/parents/author/committer/message/timestamps) exists in more than one repository. This is achievable by an attacker who can read a target commit's content from a public repo (or a fork) and recreate/import that exact commit object into their own, unrelated repository (git commit hashes are deterministic, so identical content yields an identical `sha`). The attacker then sets a GitHub commit status on that sha in their own repository. GitHub emits a legitimately signed `status` webhook (`repository.full_name` = attacker's own repo) to Shipit.

`WebhooksController#verify_signature` only validates that the webhook is authentically from GitHub for `repository_owner` (derived from the payload) using `Shipit.github(organization: repository_owner)`: [3](#0-2) 
This check authenticates *that GitHub sent it for that org*, but does nothing to verify that the named repository/org is the same one that owns the target `Commit` rows being mutated. It provides no cross-repository scoping guarantee at all — it is orthogonal to the vulnerability.

Since `StatusHandler#process` never intersects `Commit.where(sha: params.sha)` with `stacks`/`repository_name`, any commit row anywhere in the database sharing that `sha` gets `create_status_from_github!` called on it — including commits belonging to stacks tied to a completely different repository the attacker does not own. This calls `Commit#create_status_from_github!` → `add_status` → `Hook.emit(:commit_status, ...)` / `:deployable_status` and can flip `deployable?`/scheduling of `ContinuousDeliveryJob` and `stack.schedule_merges`, i.e. it can influence deploy/merge decisions for a stack the attacker doesn't control.

### Impact Explanation
An attacker who owns/controls any repository monitored by (or merely webhooked to) this Shipit instance can inject a forged-looking but authentically-signed `status` event for a commit sha that also exists on an unrelated tracked repository/stack, causing Shipit to write a `Status` record and fire `commit_status`/`deployable_status` hooks for that other repository's commit. Because `Status` state feeds into `Commit#deployable?` and `Stack#schedule_merges`, this can incorrectly mark a commit on another team's stack as passing/failing CI, potentially unblocking an unauthorized deploy or merge — a cross-repository/cross-tenant mutation matching the "payload for one repository mutating another's stack/commit" Critical category. The blast radius spans every stack/repository tracked by the same Shipit instance since the query has no repository scoping whatsoever.

### Likelihood Explanation
Preconditions: attacker needs (a) a repository of their own that is capable of sending a legitimately signed webhook to this Shipit instance (i.e., its org is configured with the GitHub App/webhook secret Shipit expects), and (b) the ability to produce/import a commit object with a `sha` matching one already present as a `Commit` row for a different tracked stack (achievable for any commit whose content is publicly known, since git hashes are deterministic over content+metadata). Both conditions are plausible for an unprivileged GitHub user in a shared organization or App installation, and the attack is repeatable against any commit sha they can reproduce. No Shipit secrets, sessions, or API tokens are required.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the stacks derived from the payload's repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the scoping already established by `Handler#stacks`/`#repository_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test 'process does not scope commits by the payload repository' do
          victim_stack = shipit_stacks(:shipit) # real tracked stack/repo
          victim_commit = victim_stack.commits.create!(sha: 'a' * 40, message: 'victim commit')

          payload = {
            'repository' => { 'full_name' => 'attacker/unrelated-repo' }, # does not resolve to victim_stack
            'sha' => victim_commit.sha,
            'state' => 'success',
            'context' => 'ci/attacker',
            'description' => 'forged'
          }

          handler = StatusHandler.new(payload)

          # Binding check: Handler#stacks resolves to Stack.none (no Repository for attacker/unrelated-repo)
          assert_equal Stack.none.to_a, handler.send(:stacks).to_a

          assert_difference -> { victim_commit.statuses.count }, 1 do
            handler.process
          end

          # Victim commit, belonging to a stack the attacker does not control, was mutated
          assert_equal 'success', victim_commit.reload.status.state
        end
      end
    end
  end
end
```
This demonstrates: `handler.send(:stacks)` (the repository-scoped set) is empty/`Stack.none`, yet `process` still creates a `Status` on `victim_commit`, proving the two sides of the binding diverge and confirming the cross-repository mutation.
