This confirms the multi-organization GitHub App setup: `Shipit.github(organization:)` selects a distinct `GitHubApp` config (with its own `webhook_secret`) per organization key, as demonstrated by `secrets_double_github_app.yml` with separate `OrgOne`/`OrgTwo` sections and `github_app_config` in `lib/shipit.rb`.

The vulnerability is in how `WebhooksController` binds signature verification to one payload field (`repository.owner.login`) while every event handler acts on a different, independently-attacker-controlled field (`repository.full_name`), with no cross-check that the two agree.

### Title
Cross-organization webhook forgery via mismatched signature-selection key and repository-action key in `WebhooksController` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to verify a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')`. But every `Shipit::Webhooks::Handlers::Handler` (e.g. `PushHandler`) determines which `Repository`/`Stack` to act on using a *different* field of the same payload: `payload.dig('repository', 'full_name')`. Because Shipit supports multiple GitHub organizations/apps each with their own `webhook_secret` (see `secrets_double_github_app.yml`, `Shipit.github_app_config`), an attacker who controls a repository in one configured organization (and thus knows/can trigger a validly-signed webhook for that org) can forge a payload whose `repository.owner.login` matches their own org (so signature verification passes) but whose `repository.full_name` names a stack belonging to a different, victim organization also configured on the same Shipit instance.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

This chooses the HMAC secret to verify against based on `repository.owner.login`. Once verification passes, `create` dispatches the *entire raw payload* to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

Handlers, however, resolve the target `Repository`/`Stack` using `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`PushHandler#process` uses this to sync a stack to an attacker-specified `after` SHA:
```ruby
def process
  stacks
    .not_archived
    .where(branch:)
    .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 

`Shipit.github(organization:)` and `github_app_config` confirm that each organization key in `secrets.github` maps to an independently configured `GitHubApp`, each with its own `webhook_secret`:
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  ...
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [5](#0-4) 

The equality that the design implicitly assumes but never enforces is:
`organization used to select verify_webhook_signature key == owner(repository.full_name acted on by the handler)`

Before the attack: an attacker who owns/administers a repository under an organization "AttackerOrg" (configured in Shipit alongside a victim org "VictimOrg") can generate a legitimately signed webhook for AttackerOrg (e.g. by pushing to their own repo, or by directly POSTing with the known AttackerOrg webhook secret if they have access to it via their own GitHub App settings/repo admin).

After the attack: the attacker crafts (or replays and edits before the HMAC step is meaningless, since HMAC is over the whole raw body — but the attacker controls the *entire* body of their own legitimate webhook payload since it's their own repository firing it, or they configure their own webhook delivery for their own repo) a JSON body where:
- `repository.owner.login = "AttackerOrg"` (drives secret selection → signature passes with AttackerOrg's known/attacker-controlled secret)
- `repository.full_name = "VictimOrg/victim-repo"` (drives which `Stack` gets synced/deployed)

Because nothing ties these two fields together, `verify_signature` succeeds while the handler acts on the victim's repository/stack.

### Impact Explanation
This breaks the trust binding between "which organization's cryptographic secret authenticated this request" and "which repository's deployment state the request is permitted to mutate." A successful forgery lets an attacker trigger `stack.sync_github(expected_head_sha: ...)` for a `VictimOrg` stack they do not control, which can advance the stack's known head SHA to an attacker-chosen commit. If any auto-deploy/continuous-delivery is configured on that victim stack (`ContinuousDeliveryConfiguration`, `sync_github` → deploy pipeline), this can lead to an **unauthorized deploy** of attacker-chosen code/commit SHA on the victim's stack — this satisfies the Critical/High impact bar ("an unauthorized deploy").

### Likelihood Explanation
Requires: (1) the target Shipit instance to be configured with more than one GitHub organization/app (the multi-org `github:` config schema demonstrated by `secrets_double_github_app.yml` and supported by `github_app_config`), and (2) the attacker to control a repository/webhook delivery under one of the configured organizations. This is a realistic deployment pattern (a single Shipit instance shared across multiple orgs) but is not the default single-org setup, and requires the attacker to already have delivery rights to one of the trusted orgs — still an unprivileged position relative to the victim org's stacks.

### Recommendation
In `verify_signature`, after selecting the `GitHubApp` by `repository_owner` and verifying the signature, additionally verify that the resolved `repository.full_name`'s owner matches `repository_owner` (or, more robustly, look up the target `Repository`/`Stack` first and verify the signature using the webhook secret configured for *that* repository's actual organization, not a value taken from the unauthenticated fields being trusted before signature verification completes).

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with its own `webhook_secret` (mirrors `test/dummy/config/secrets_double_github_app.yml`).
2. As an admin/webhook-owner of a repo under `AttackerOrg`, craft (or have GitHub deliver, then replay with modification disabled since HMAC covers raw body — so instead configure a custom webhook on the attacker's own repo pointing at Shipit, and control the payload GitHub sends by controlling repository settings) a `push` event body where:
   - `repository.owner.login = "AttackerOrg"`
   - `repository.full_name = "VictimOrg/victim-repo"`
   - `ref = "refs/heads/<victim-stack-branch>"`, `after = "<attacker-chosen-sha>"`
3. Sign the raw body with `AttackerOrg`'s webhook secret and send `X-Hub-Signature: sha1=...` to `/github_webhooks` (per `config/routes.rb`).
4. `verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` and successfully verifies since the signature matches AttackerOrg's secret.
5. `PushHandler#process` resolves `Repository.from_github_repo_name('VictimOrg/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'attacker-chosen-sha')` on the victim's stack, as shown in [4](#0-3) , without any check that `AttackerOrg == VictimOrg`.
