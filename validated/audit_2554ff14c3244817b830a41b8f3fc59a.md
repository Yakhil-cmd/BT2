### Title
Attacker-controlled PR label overrides `BUNDLE_GEMFILE` in deploy subprocess environment, bypassing `Command::BASE_ENV`'s intentional unset - (File: lib/shipit/command.rb)

### Summary
`Shipit::Command::BASE_ENV` deliberately clears `BUNDLE_GEMFILE` (by setting it to `nil`) using `Bundler.unbundled_env`/`Bundler.clean_env` so that spawned subprocesses resolve bundler dependencies against the intended `Gemfile`. However, `Command#unbundled_env` merges the per-command `@env` hash last, and `TaskCommands#env`/`ReviewStack#env` derive part of that hash from GitHub PR labels attached to a `ReviewStack`'s pull request, letting an attacker who can label their own PR inject `BUNDLE_GEMFILE=true` into the subprocess environment used for `bundle install`/`bundle exec cap` steps.

### Finding Description
The broken binding is: `Command::BASE_ENV['BUNDLE_GEMFILE']` (intentionally `nil`, cleared by `Bundler.unbundled_env`/`Bundler.clean_env`) should equal the `BUNDLE_GEMFILE` key present in the env hash passed to `PTY.spawn` in `Command#start`. It does not, because `Command#unbundled_env` merges `@env` last: [1](#0-0) [2](#0-1) [3](#0-2) 

`@env` is populated through `ReviewStack#env`, which upcases every PR label name and sets its value to `"true"`, merged into `Stack#env` for the review stack: [4](#0-3) 

`TaskCommands#env` merges `@stack.env` into the final task environment used to build every `Command` for `install_dependencies` and `perform` (the bundler/`bundle exec cap` steps): [5](#0-4) 

Labels are captured from unauthenticated GitHub webhooks (label add/PR opened/reopened) by `LabelCapturingHandler#capture_labels`, which writes `params.pull_request.labels` verbatim into `pull_request.labels`: [6](#0-5) 

No sanitization, allow-list, or reserved-key filtering exists between PR labels and the merged env hash — `EnvironmentVariables#permit` (a strict allow-list mechanism) is a separate opt-in used elsewhere for interpolation, not applied to `ReviewStack#env`/`TaskCommands#env`: [7](#0-6) 

So attacker labeling `bundle_gemfile` on their own PR results in `stack.env['BUNDLE_GEMFILE'] == "true"`, which survives every subsequent `.merge` in `TaskCommands#env` (none of the later hardcoded keys re-set `BUNDLE_GEMFILE`), and reaches `Command#unbundled_env` as the final override of the intentionally-cleared `BASE_ENV` entry, ending up in the `PTY.spawn` env for `bundle install --jobs 4 --retry 2` and `bundle exec cap ...` steps (from `BundlerDiscovery`): [8](#0-7) 

Because the attacker also controls the PR branch contents (their own fork/repo), they can additionally commit a file literally named `true` in the deploy working directory. When bundler is invoked with `BUNDLE_GEMFILE=true`, it will attempt to load and `eval` that file as a Gemfile DSL script, resulting in arbitrary Ruby code execution on the deploy host — this is `Command`/`PTY.spawn`-driven RCE, matching the Critical severity category in the rules.

### Impact Explanation
An attacker who can label their own PR (an explicitly granted unprivileged capability per the audit rules) can inject an arbitrary `BUNDLE_GEMFILE` value into the subprocess environment for every bundler-related deploy/task step (`bundle install`, `bundle exec cap ...`) on a `ReviewStack` tied to their PR. Combined with attacker-controlled repository contents (a file named `true` acting as a malicious Gemfile), this can drive Bundler to evaluate attacker-supplied Ruby code during the deploy, i.e., RCE on the Shipit deploy host under the identity/privileges of the deploy process — Critical impact. The blast radius is scoped to review-stack deploys for the affected repository/PR, and is repeatable on every deploy/task triggered for that stack while the label remains present.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled (`allow_all` or label opt-in) and use bundler-based deploy steps (`BundlerDiscovery`), and the attacker's PR/stack must be unarchived — all explicitly given as preconditions in the question. The attacker cost is low: open a PR (or push to their own fork/repo), add a label named `bundle_gemfile` (case-insensitive, since `ReviewStack#env` upcases it), and include a file named `true` in the working directory of their branch. No secrets, sessions, or elevated GitHub permissions are required beyond what the rules grant (labeling their own PR). This is fully repeatable for any repository/stack configured this way.

### Recommendation
In `ReviewStack#env` (or `TaskCommands#env`), exclude reserved/dangerous environment variable names (e.g., anything with a `BUNDLE_`, `RUBYOPT`, `GEM_`, `LD_PRELOAD`, `PATH` prefix, or an explicit denylist/allowlist) from the PR-label-derived environment before merging it into the task/command environment. Alternatively, apply `EnvironmentVariables#permit` with an explicit allow-list to label-derived variables, or re-assert `Command::BASE_ENV`'s cleared bundler-related keys after merging `@env` in `Command#unbundled_env` so untrusted input cannot resurrect intentionally-unset bundler control variables.

### Proof of Concept
```ruby
# test/unit/command_bundle_gemfile_test.rb
require 'test_helper'

module Shipit
  class CommandBundleGemfileTest < ActiveSupport::TestCase
    test "BASE_ENV intentionally clears BUNDLE_GEMFILE" do
      assert Shipit::Command::BASE_ENV.key?('BUNDLE_GEMFILE')
      assert_nil Shipit::Command::BASE_ENV['BUNDLE_GEMFILE']
    end

    test "attacker-controlled env overrides the cleared BUNDLE_GEMFILE at spawn time" do
      command = Shipit::Command.new('true', env: { 'BUNDLE_GEMFILE' => 'true' }, chdir: '.')
      assert_equal 'true', command.unbundled_env['BUNDLE_GEMFILE']
    end

    test "PR label 'bundle_gemfile' propagates into TaskCommands env reaching Command#unbundled_env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ['bundle_gemfile']
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env
      assert_equal 'true', env['BUNDLE_GEMFILE']

      command = Shipit::Command.new('bundle install', env:, chdir: '.')
      assert_equal 'true', command.unbundled_env['BUNDLE_GEMFILE']
    end
  end
end
```
This demonstrates: (1) `Command::BASE_ENV` deliberately unsets `BUNDLE_GEMFILE`; (2) a PR label named `bundle_gemfile` on a `ReviewStack`'s pull request flows unsanitized through `TaskCommands#env` into `Command#unbundled_env`, resurrecting `BUNDLE_GEMFILE` with an attacker-chosen value that will be passed to `PTY.spawn` for bundler-invoking deploy steps.
