Confirmed: `store_stake_accounts_in_partition` iterates over the entire `indices` slice for the given partition with no secondary bound — it processes every reward in that partition unconditionally, so if a partition holds far more than `stake_account_stores_per_block` entries, that whole set is processed in a single block.

### Title
Epoch-boundary reward distribution work is unbounded because `get_reward_distribution_num_blocks`'s partition-count cap decouples `num_partitions` from `stake_account_stores_per_block` once the 10%-of-epoch clamp is hit, letting attacker-created stake accounts inflate per-block work in `store_stake_accounts_in_partition` - ([File: runtime/src/bank/partitioned_epoch_rewards/mod.rs], [File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`get_reward_distribution_num_blocks` computes `num_chunks = total_stake_accounts.div_ceil(stake_account_stores_per_block)` and then clamps it to `[1, slots_per_epoch / 10]`. When `total_stake_accounts` is large enough that `num_chunks` exceeds `slots_per_epoch / 10`, the number of partitions stops growing but the number of rewarded accounts keeps growing, so the average (and hash-distributed, non-uniform) number of accounts per partition grows without bound. Since `store_stake_accounts_in_partition` processes an entire partition's indices unconditionally in one block with no further sub-chunking, the per-block work is no longer bounded by `stake_account_stores_per_block`.

### Finding Description
`get_reward_distribution_num_blocks` in [1](#0-0)  is the sole source of `num_partitions`, which is passed unchanged into `hash_rewards_into_partitions` at both calculation time (`begin_partitioned_rewards` via `create_epoch_rewards_sysvar`) and recalculation time [2](#0-1) . `hash_rewards_into_partitions` assigns each stake reward to a partition purely by hashing the stake pubkey [3](#0-2) , with no per-partition size cap. `store_stake_accounts_in_partition` then unconditionally iterates the full `indices` vector for a partition in a single block [4](#0-3) , storing every rewarded stake account and updating capitalization for that whole set within one `distribute_epoch_rewards_in_partition` call [5](#0-4) .

The clamp `num_chunks.clamp(1, (slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1))` bounds `num_partitions` to at most `slots_per_epoch/10`, which is a *fixed* quantity for a given epoch schedule (e.g., 43,200 for a 432,000-slot epoch), independent of `total_stake_accounts`. `stake_account_stores_per_block` is intended to bound per-block work (default 4096, from `MAX_PARTITIONED_REWARDS_PER_BLOCK`, see [6](#0-5) ), but this bound is only respected while `num_chunks <= slots_per_epoch/10`. An attacker who creates enough delegated stake accounts (each just at `stake_utils::get_minimum_delegation`, i.e., 1 SOL when the v5 stake program upgrade is active, see [7](#0-6) ) so that `total_stake_accounts` far exceeds `stake_account_stores_per_block * (slots_per_epoch/10)` forces `num_partitions` to stay pinned at the cap while the average partition size (and, due to hashing, the size of the largest partition) grows linearly with the number of attacker-created accounts. Since every account with the minimum delegation earns nonzero rewards, none of them are filtered out as `None` entries by `get_reward_distribution_num_blocks`'s counting logic [8](#0-7) .

No signer, authority, rent-exempt, or arithmetic-overflow guard mitigates this — those guards operate on individual stake-delegate transactions, not on aggregate epoch-boundary compute cost. The check is purely a partition-count formula that assumes `total_stake_accounts` is naturally bounded, which is false since delegation creation is permissionless and only requires funding rent-exempt-reserve + minimum delegation per account.

### Impact Explanation
Once the clamp is engaged, a single block's `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` call must process a partition whose size scales with total attacker-created stake accounts rather than the configured `stake_account_stores_per_block`. This directly violates the intended invariant that epoch-boundary distribution work per block is bounded, and since this code runs during normal block production for every validator, an attacker can drive per-block execution time for reward distribution blocks arbitrarily high, i.e. a cluster liveness ("epoch-boundary halt / divergence") issue as described in the Agave bounty program's DoS/liveness category. This matches the "epoch-boundary divergence or halt via unbounded per-partition-block work" scoped impact.

### Likelihood Explanation
Feasibility depends entirely on the attacker's economic cost: creating N stake accounts each requiring rent-exempt reserve plus the minimum delegation (1 SOL post-upgrade, effectively 1 lamport pre-upgrade) is unprivileged and requires only `CreateAccount` + `DelegateStake` instructions, fully within the "normal user" threat model. To exceed the `slots_per_epoch/10` partition cap with real per-block impact, the attacker needs `total_stake_accounts` on the order of `stake_account_stores_per_block * slots_per_epoch/10` (with default config, roughly 4096 * 43200 ≈ 177 million accounts for a 432,000-slot epoch) — a very large but not architecturally impossible number given the low per-account minimum delegation, though the SOL cost (1 SOL/account under the v5 minimum) would be enormous. Under the legacy 1-lamport minimum delegation (feature not yet active), the cost per account is negligible and feasibility is much higher. This affects the calculation whenever the pre-upgrade minimum-delegation feature is inactive or the attacker has substantial capital.

### Recommendation
Change `get_reward_distribution_num_blocks` to never clamp `num_partitions` below what's needed to keep the *maximum* partition size within `stake_account_stores_per_block`, or alternatively bound `store_stake_accounts_in_partition`/`distribute_epoch_rewards_in_partition` to process at most `stake_account_stores_per_block` entries per invocation regardless of partition size (splitting oversized partitions across multiple blocks). Additionally, consider enforcing a maximum total number of stake delegations per validator/vote account or per epoch, independent of the per-block partitioning math, to bound the underlying `total_stake_accounts` value.

```rust
    let slots_per_epoch = 32;
    let stake_account_stores_per_block = 2; // small, to trigger clamp early

    // Case 1: at the clamp boundary
    let num_stakes_at_boundary = stake_account_stores_per_block * max_partitions; // 6
    // Case 2: far beyond the boundary, simulating attacker-created accounts
    let num_stakes_attacker = num_stakes_at_boundary * 1000; // 6000

    for num_stakes in [num_stakes_at_boundary, num_stakes_attacker] {
        let stake_rewards = (0..num_stakes)
            .map(|_| Some(PartitionedStakeReward::new_random()))
            .collect::<PartitionedStakeRewards>();
        let num_partitions = bank.get_reward_distribution_num_blocks(&stake_rewards); // stays at max_partitions=3

        let partition_indices = hash_rewards_into_partitions(
            &stake_rewards,
            &Hash::default(),
            num_partitions as usize,
        );
        let max_partition_size = partition_indices.iter().map(|p| p.len()).max().unwrap();

        // Assert: the maximum work assigned to a single block-partition
        // must stay within the configured stake_account_stores_per_block.
        // This assertion is expected to FAIL for num_stakes_attacker,
        // demonstrating unbounded per-block work.
        assert!(
            max_partition_size <= stake_account_stores_per_block as usize * 2, // generous slack for hash variance
            "partition size {} exceeds bound for num_stakes={}",
            max_partition_size,
            num_stakes
        );
    }
}
```

```rust
    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
```

```rust
pub(in crate::bank::partitioned_epoch_rewards) fn hash_rewards_into_partitions(
    stake_rewards: &PartitionedStakeRewards,
    parent_blockhash: &Hash,
    num_partitions: usize,
) -> Vec<Vec<usize>> {
    let hasher = EpochRewardsHasher::new(num_partitions, parent_blockhash);
    let mut indices = vec![vec![]; num_partitions];

    for (i, reward) in stake_rewards.enumerated_rewards_iter() {
        // clone here so the hasher's state is reused on each call to `hash_address_to_partition`.
        // This prevents us from re-hashing the seed each time.
        // The clone is explicit (as opposed to an implicit copy) so it is clear this is intended.
        let partition_index = hasher
            .clone()
            .hash_address_to_partition(&reward.stake_pubkey);
        indices[partition_index].push(i);
    }
    indices
}
```

```rust
            .fetch_sub(block_reward_lamports_burned, Relaxed);

            total_stake_accounts_count: partition_rewards.all_stake_rewards.num_rewards(),
            total_num_partitions: partition_rewards.partition_indices.len(),

            store_stake_accounts_us,
```
