## Title
Unilateral `unstake()` by one delegator can evict an entire signer's other stakers from the reward set for cycles they never withdrew from - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

## Summary
`pox-5.clar`'s `unstake()` lets a single staker remove themselves from a signer's future cycles. This triggers `remove-staker-from-cycles` → `remove-staker-from-signer-for-cycle`, which checks whether the *signer's total delegated uSTX* (across **all** stakers/bonds delegated to that signer) still meets `SIGNER_SET_MIN_USTX` after subtracting only the caller's own amount. If it does not, the code calls `remove-staker-from-set-for-cycle` and zeroes the signer's `signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle` entries for that cycle — an action that affects every other staker still delegated to that signer, none of whom took any action or gave consent.

## Finding Description
`unstake()` [1](#0-0)  calls `remove-staker-from-cycles`, which folds over `remove-staker-from-signer-for-cycle` for each affected cycle [2](#0-1) .

Inside `remove-staker-from-signer-for-cycle`, the function computes `new-delegated` by subtracting *only the calling staker's own delegated amount* from `cur-delegated-for-signer` (the signer's aggregate delegated uSTX across all its stakers/bonds) [3](#0-2) . If `new-delegated < SIGNER_SET_MIN_USTX`, the code unconditionally removes the *signer* from the signer set for that cycle and zeroes the signer's aggregate staked totals (`signer-shares-staked-for-cycle` and `total-shares-staked-for-cycle`) [4](#0-3) .

This mirrors the reported bug class exactly: an action taken on one "collateral"/stake position (a single staker's own withdrawal) triggers a state transition that unilaterally strips a shared resource (the signer's membership in the signer set, and the aggregated reward-accounting totals) out from under *other, uninvolved* stakers who are still delegated to the same signer and never called `unstake`. Those other stakers' `staker-shares-staked-for-cycle` entries are left pointing at a signer that:
1. Is no longer in the signer set for that cycle (loses eligibility to be selected/weighted in that reward cycle's signer computation), and
2. Has its aggregate `signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle` zeroed out, even though those other stakers' individual `staker-shares-staked-for-cycle` entries are untouched by this branch (only the caller's own entry is deleted later in the function, at lines 1586-1616).

This breaks the equality that a staker's committed uSTX for a given cycle should continue to count toward the signer's total stake/eligibility unless that specific staker withdraws — instead, an unrelated staker's `unstake` call can zero out the signer's aggregate accounting for a cycle while other stakers' individual records still claim to be staked with that signer.

## Impact Explanation
This is a "stacking action the staker/signer never authorised" class of issue: other stakers delegated to the same signer have their reward/weight eligibility altered by a third party's unilateral action, without their consent, and without their own principal-based check. Depending on how downstream reward settlement (`settle-rewards`/`settle-staker-rewards`, called before the mutation at line 1543-1544 for the *acting* staker only) reconciles this state for the *other* remaining stakers in later cycles, this can produce a mismatch between recorded shares and actual signer-set eligibility (i.e., signer weight and reward slots not matching the actual locked value — a High-severity condition per the scope's impact list), or a temporary loss of reward eligibility for the remaining stakers' funds for that cycle even though their STX remain locked.

## Likelihood Explanation
This requires no privileged role — any staker delegated to a signer can call `unstake()` on their own bond, which is a routine, expected action [1](#0-0) . The triggering condition (aggregate signer delegation dropping below `SIGNER_SET_MIN_USTX`) is easily reachable whenever a signer is close to the minimum threshold with multiple small stakers, which is a normal, non-adversarial configuration, making this readily triggerable in practice.

## Recommendation
When removing a signer from the signer set due to one staker's `unstake` action, either (a) leave the remaining stakers' `staker-shares-staked-for-cycle` and per-signer aggregate accounting internally consistent by recomputing them from the actual remaining membership set rather than just zeroing the aggregate totals, or (b) require the aggregate zero-out to be reconciled against the actual sum of remaining `staker-signer-cycle-memberships` for that signer/cycle, so other stakers' recorded shares cannot silently diverge from the signer's now-zeroed aggregate. At minimum, add an invariant check/test verifying that after any single staker's `unstake`, the sum of remaining stakers' `staker-shares-staked-for-cycle` for a signer equals that signer's `signer-shares-staked-for-cycle` for every affected cycle.

## Proof of Concept
1. Signer `S` has three stakers, `A`, `B`, `C`, each delegating uSTX to `S` such that the sum is just above `SIGNER_SET_MIN_USTX` (e.g., `SIGNER_SET_MIN_USTX + amount(A)`), and `S` is in the signer set for reward cycle `N`.
2. Staker `A` calls `unstake()` [1](#0-0) , which computes `new-delegated = cur-delegated-for-signer - amount(A)`, which now falls below `SIGNER_SET_MIN_USTX`.
3. `remove-staker-from-signer-for-cycle` executes the branch at lines 1546-1565, calling `remove-staker-from-set-for-cycle` and zeroing `signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle` for `S`/cycle `N` — even though `B` and `C` never called `unstake` and their own `staker-shares-staked-for-cycle` entries for `S`/cycle `N` are left unmodified by this branch.
4. `S` is no longer counted in the signer set for cycle `N`, and the signer-level aggregate stake accounting no longer reflects `B` and `C`'s still-locked stake, breaking the invariant that a staker's continued (non-withdrawn) delegation should continue to count toward their signer's reward-cycle eligibility.

Note: I was not able to fully trace how `settle-rewards`/reward distribution downstream reconciles this divergence for `B` and `C` in a later cycle (i.e., whether they eventually recover correct rewards or the loss is permanent), since the reward-settlement logic spans a large portion of `pox-5.clar` that I could not fully review within the available iterations. This should be verified against the full `settle-rewards`/`settle-staker-rewards` implementation before treating the severity as final.
