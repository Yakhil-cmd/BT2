### Title
Webhook signature verification is scoped to `repository.owner.login`/`organization.login` but the event handlers act on the unrelated, unverified `repository.full_name` field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`), but the field that actually determines *which repository/stack gets mutated* — `repository.full_name`, read later by every `Webhooks::Handlers::Handler` — is never bound to, or cross-checked against, the identity that was authenticated. Combined with the fact that `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization (a supported, documented configuration), an unauthenticated request can forge webhook events (push, status, check_suite, membership) that are processed against an arbitrary `repository.full_name`, including repositories belonging to a different, properly-secured organization on the same Shipit instance.

### Finding Description
Signature verification: [1](#0-0) 
picks the app/secret using `repository_owner`: [2](#0-1) 

The actual HMAC check trivially passes when no secret is configured for that organization: [3](#0-2) 

This "no secret = accept" behavior is a first-class supported configuration, shown as the documented default (`webhook_secret: # nil`) both in the single-org and multi-org examples: [4](#0-3) [5](#0-4) 

After (weak/absent) verification, every handler resolves the stack to operate on using a *different* field of the same untrusted body — `repository.full_name` — with no relation to `repository_owner`: [6](#0-5) 

For example, `StatusHandler` creates a commit status for *any* `sha` present in the datastore, regardless of which organization "authenticated" the request: [7](#0-6) 
and `PushHandler` triggers a GitHub sync for any stack matching `repository.full_name` + branch: [8](#0-7) 

The binding that is broken is: **organization authenticated (`repository_owner` checked against a per-org `webhook_secret`) ≠ repository actually written (`repository.full_name` used by `Handler#stacks`)**. There is no requirement that these two identities match, and when the authenticating organization has no secret configured, the check is a no-op — so the `repository.full_name` field driving all downstream writes is effectively attacker-controlled.

### Impact Explanation
A forged `status` webhook processed via `Commit#create_status_from_github!` can flip a commit's CI state to `success` for any tracked repository, and per the observed continuous-deployment logic this can trigger an actual deploy: [9](#0-8) 
This satisfies the "unauthorized deploy" Critical-impact criterion, reached with zero credentials against any organization on the instance whose `webhook_secret` is left blank (the documented default), while still writing into the state of any repository referenced by `full_name` in the forged payload.

### Likelihood Explanation
Likelihood is high for any Shipit deployment following the documented example configuration (`webhook_secret: # nil`) for at least one configured organization — no GitHub App credentials, session, or `ApiClient` token is required, only knowledge of the public `/webhooks` (or engine-mounted) endpoint and the JSON shape expected by `ExplicitParameters` in each handler.

### Recommendation
- Require `webhook_secret` to be present (reject/log instead of silently passing) for every configured organization, or fail closed at boot if any org has no secret.
- Bind the field used to select the verifying organization to the field used to resolve the target repository: verify that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers.
- Consider verifying against the actual `Repository`/`Stack`'s configured organization rather than trusting `repository.owner.login` supplied in the same unverified body.

### Proof of Concept
1. Deploy Shipit with multi-org config where OrgA has `webhook_secret: nil` (per documented example) and OrgB (the real target) has stacks tracking `orgb/victim-repo`.
2. POST to the webhooks endpoint with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "orga"}, "full_name": "orgb/victim-repo"},
  "sha": "<known deployable commit sha in orgb/victim-repo>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orga")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally. [3](#0-2) 
4. `StatusHandler#process` creates the status against the real commit in `orgb/victim-repo` looked up purely by `sha`, with no organization binding, potentially triggering continuous deployment. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
