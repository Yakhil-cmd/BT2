### Title
Cross-organization webhook forgery via mismatched signature-selection field and stack-resolution field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-App configurations, `WebhooksController#verify_signature` selects which organization's HMAC secret to verify the inbound webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`). All downstream event handlers instead resolve the target `Stack`/`Repository` using a *different* field from the same attacker-supplied JSON body: `payload.dig('repository', 'full_name')`. Because these are two independently-trusted fields inside one unauthenticated JSON payload, an attacker can pick which organization's secret is used to "authenticate" the request while directing the actual side effects (sync, archive/unarchive, membership changes) at a repository/stack belonging to a completely different, victim organization.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 
selecting the `GitHubApp` via `Shipit.github(organization: repository_owner)` where [2](#0-1) 
`repository_owner` is read straight out of the unauthenticated JSON body.

`Shipit.github` resolves the app config for that organization key from `secrets.github`: [3](#0-2) 

Signature verification is a no-op if that organization's `webhook_secret` is not configured: [4](#0-3) 
The docs explicitly present `webhook_secret` as optional per organization in the multi-org schema: [5](#0-4) 

Meanwhile, `create` dispatches to handlers using the same raw, unauthenticated JSON: [6](#0-5) 
and every handler resolves the acted-upon repository/stack from `payload.dig('repository', 'full_name')`, not from `repository.owner.login`: [7](#0-6) 
e.g. `PushHandler`, which triggers a git sync to an attacker-chosen SHA for the resolved stacks: [8](#0-7) 
and PR label handlers that archive/unarchive review stacks based on the same `repository.full_name` field: [9](#0-8) 

Because `repository.owner.login` and `repository.full_name` are both plain, independently-readable keys in one unsigned/unauthenticated attacker-controlled JSON body, nothing enforces that they refer to the same repository. An attacker who knows (or guesses) that some organization `OrgA` configured in `secrets.github` has no `webhook_secret` set (an explicitly supported, documented configuration) can craft a webhook payload with `repository.owner.login = "OrgA"` (making `verify_webhook_signature` return `true` unconditionally, bypassing authentication entirely) while setting `repository.full_name = "VictimOrg/victim-repo"` so that the actual handler logic acts on the victim's tracked stack.

This is exactly the "organization that authenticated versus the repository that is written" binding break: before the request, the equality `organization_that_signed_request == organization_owning_written_repository` holds for legitimate GitHub-originated webhooks (GitHub always signs with the secret matching the repository's actual owner/installation). After this crafted request, that equality is broken: the signing/authenticating organization (`OrgA`, unauthenticated because no secret) differs from the organization whose repository/stack is actually mutated (`VictimOrg`).

### Impact Explanation
Depending on which event type is spoofed, this yields:
- Unauthorized deploy/sync: `push` events invoke `stack.sync_github(expected_head_sha: ...)` on stacks under the victim's tracked repository, letting the attacker drive commit-status/CI state processing and downstream automated deploy eligibility for a repo they don't control.
- Unauthorized archive/unarchive of review stacks and pull-request state manipulation (`pull_request` handlers), deprovisioning or reprovisioning environments for the victim's PRs.
- `membership` events change `Shipit::Team`/`Shipit::Membership` records, which is used by `User#authorized?` to gate access via `Shipit.github_teams` — i.e., this can be leveraged to escalate/tamper with authorization records, matching the "escalation into `Shipit.github_teams` authorization" High-severity impact class named in scope.

The root cause is a genuine credential-boundary crossing (an unauthenticated request is treated as authenticated for one org, but effects land on another org's resources), reachable by any unauthenticated network attacker who can POST to `/webhooks` — no session, API token, or GitHub write access is required.

### Likelihood Explanation
Exploitability requires:
1. The deployment to use the multi-organization GitHub App config schema (documented, supported feature).
2. At least one configured organization to have `webhook_secret` unset (explicitly documented as optional).
3. The attacker to know/guess that organization's name.

This is a realistic, not merely theoretical, configuration since the project's own setup docs describe `webhook_secret` as optional and multi-org setups as a supported pattern for companies deploying code from several GitHub orgs (e.g., subsidiaries/teams), whose names are often discoverable. The vulnerable code path (`verify_signature`, `Shipit.github`, `verify_webhook_signature`, and every handler's `repository_name`) is unconditionally reachable by any unauthenticated POST to `/webhooks`.

### Recommendation
- Short term: Derive the organization used for signature verification from the same field(s) used for repository/stack resolution (i.e., always verify using the organization implied by `repository.full_name`, not `repository.owner.login`/`organization.login`), and reject the request if `repository.owner.login` and the owner segment of `repository.full_name` disagree.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank in multi-org configurations; require every configured organization to have a secret (or explicitly disable/log-and-reject such organizations at startup).
- Long term: Bind webhook authentication to a single canonical repository identifier extracted once, and thread that same value through both `verify_signature` and every handler's `stacks`/`repository` resolution, so no two independently-controlled JSON fields can be played against each other.

### Proof of Concept
Preconditions: `secrets.github` configured with two orgs, `OrgA` (no `webhook_secret`) and `VictimOrg` (tracked stacks, real secret).

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   # irrelevant, verification is skipped for OrgA

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },        # selects OrgA's (secret-less) GithubApp for verification
    "full_name": "VictimOrg/victim-repo" # actually resolved/acted upon by PushHandler
  }
}
```

`verify_signature` calls `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`), passing the `before_action`. `WebhooksController#create` then dispatches to `Shipit::Webhooks.for_event('push')`, and `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` (`handler.rb:32-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's real stack — despite the request never being validated against `VictimOrg`'s webhook secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))

module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after

        def process
          stacks

        end

        private

          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
