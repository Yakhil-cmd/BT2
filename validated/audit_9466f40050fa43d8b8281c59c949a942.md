### Title
Creator fee funds become permanently frozen if the immutable `pool_creator` recipient account is unable to receive tokens (frozen/blacklisted mint) - ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs])

### Summary
`pool_creator` is recorded once at pool initialization and can never be changed. Both permissioned and permissionless creator-fee collection instructions hard-code the transfer destination to an ATA owned by this immutable address. If that recipient's token account becomes non-transferable (e.g., frozen via the mint's freeze authority, or blocked by a Token-2022 transfer hook / permanent delegate that enforces an address blocklist), the accumulated `creator_fees_token_0`/`creator_fees_token_1` can never be withdrawn from the vault, permanently freezing those funds in the protocol.

### Finding Description
`PoolState::initialize` sets `self.pool_creator = pool_creator.key()` once at pool creation and this field is never updated anywhere else in the program. [1](#0-0) 

Both fee-collection instructions constrain the creator account to this immutable value and derive/require an associated token account owned by that same creator: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The actual transfer uses `transfer_checked` via `transfer_from_pool_vault_to_user`, which is a standard SPL/Token-2022 CPI that will fail if the destination account is frozen or if a Token-2022 extension (transfer hook / permanent delegate acting as a blocklist) rejects the transfer to that specific address: [6](#0-5) [7](#0-6) 

Since there is no instruction anywhere in the program to change `pool_creator`, and `collect_creator_fee`/`collect_creator_fee_permissionless` are the only paths that can zero out `creator_fees_token_0`/`creator_fees_token_1`, once the creator's token account for a given mint cannot receive transfers, the accrued creator fee for that token becomes permanently stuck in the pool vault with no recovery path — analogous to the reported issue where a fixed, non-updatable `recipientAddress` becomes blacklisted and freezes funds that can only be sent to that one address.

### Impact Explanation
This is a fund-freezing issue rather than theft: the creator fee balances (`pool_state.creator_fees_token_0`/`creator_fees_token_1`) are legitimately owed to the pool creator but permanently unreachable once the creator's associated token account is frozen or blocked by a Token-2022 extension (default account frozen state, freeze authority action, or transfer-hook/permanent-delegate blocklist on the mint). Both the permissioned and permissionless collection paths are affected since both route to the same fixed `pool_creator`-owned ATA, and there is no admin/rescue mechanism to redirect or reset these accrued fees. This qualifies as Medium severity: permanent freezing of legitimately owed funds for a single, non-privileged actor path.

### Likelihood Explanation
Reachability requires a Token-2022 mint used in the pool to have (or later acquire) an extension capable of blocking transfers to a specific address — e.g., freeze authority freezing the creator's ATA, or a transfer-hook/permanent-delegate program enforcing an allow/deny list. Since `initialize`/`initialize_with_permission` allow arbitrary Token-2022 mints as long as they pass `is_supported_mint`, and freeze authority / hooks are legitimate, permissible mint configurations, this condition is realistically reachable without any privileged action on the swap program itself — the mint issuer (or a future freeze action) is enough to trigger it.

### Recommendation
Allow the pool creator (or an authorized party) to update the fee-recipient token account/address at any time, independent of the original `pool_creator` field, or add a fallback/rescue mechanism (e.g., allow the creator to specify a different valid destination account per collection call, validated only by `associated_token::authority = creator` semantics being relaxed to any account the creator signs for) so that accrued creator fees are not permanently locked to a single address that could become blacklisted or frozen.

### Proof of Concept
1. Initialize a pool where `token_0_mint` is a Token-2022 mint with a freeze authority (or a transfer-hook program implementing an address blocklist), and `creator` is the pool creator's key.
2. Perform swaps that accrue `creator_fees_token_0 > 0` in `pool_state`.
3. The mint's freeze authority freezes the `creator`'s associated token account for `token_0_mint` (or the transfer-hook blocklists the creator's address) — a legitimate action outside the swap program's control.
4. Call `collect_creator_fee` or `collect_creator_fee_permissionless`; the `transfer_checked` CPI in `transfer_from_pool_vault_to_user` fails because the destination account is frozen/blocked. [8](#0-7) 
5. Since `pool_creator` cannot be changed and no alternate recipient path exists, `creator_fees_token_0` remains non-zero and permanently unwithdrawable, freezing those funds in the `token_0_vault` indefinitely.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}
