### Title
Webhook signature is verified against the organization derived from `repository.owner.login`, while the stack actually acted upon is selected by the independent `repository.full_name` field, letting a holder of one organization's webhook secret target another organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks which GitHub App / webhook secret to validate the incoming payload against based on `repository.owner.login` extracted from the *same, attacker-controlled* JSON body, then verifies the HMAC over the raw body using that secret. Once the signature check passes, the actual event handler (`Handler#stacks`) resolves which `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Because these two fields are never cross-checked, a party who legitimately knows the webhook secret for organization `A` (e.g., because they administer a GitHub App installed on `A` that this Shipit instance is configured to trust) can craft a payload where `repository.owner.login = "A"` (so the signature validates against `A`'s secret) while `repository.full_name = "B/some-repo"` (so the handler acts on organization `B`'s stack).

### Finding Description
- Signature verification: `Shipit.github(organization: repository_owner)` selects the `GitHubApp` config/secret using `repository_owner`, defined as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, then calls `verify_webhook_signature(signature, raw_post)` against that org's secret. [1](#0-0) [2](#0-1) 
- Handler dispatch: after signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` invokes the registered handler with the full parsed JSON body. [3](#0-2) 
- Repository resolution for the actual mutation: `Handler#stacks` resolves the target `Repository`/`Stack` set using `repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely separate field from the one used to pick the verifying secret. [4](#0-3) 
- `PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack on the branch named by `ref`. [5](#0-4) 

The equality the code assumes but never enforces is:
`organization authenticated by signature (repository.owner.login)` == `organization/repository whose stacks are mutated (repository.full_name)`

Because the HMAC covers the full raw body, this only prevents *third parties* with no secret from forging any payload. It does **not** prevent a party who legitimately possesses the secret for organization `A` (a valid tenant of this multi-organization Shipit instance) from self-signing a payload that lies about `repository.full_name`, pointing at organization `B`'s repository instead of `A`'s.

### Impact Explanation
An attacker who controls (or has compromised) the webhook secret for one organization configured on this Shipit instance can force `GithubSyncJob`/`sync_github` to run against another organization's stacks by simply changing `repository.full_name` in an otherwise correctly-signed webhook body. Depending on stack configuration (e.g., continuous delivery / auto-deploy enabled), this cross-tenant sync trigger can cause an unauthorized deploy pipeline to advance for a repository the attacker was never authorized to touch, crossing the "organization authenticated vs. repository written" boundary called out in scope.

### Likelihood Explanation
Requires the attacker to already legitimately hold a webhook secret for *some* organization trusted by this Shipit instance (a realistic scenario in any multi-tenant Shipit deployment serving several GitHub organizations, each with its own App/secret, since each org's own administrators know their own secret). No Shipit session, `ApiClient` token, or GitHub write access to the *target* repository is required — only knowledge of a signature secret for a different, unrelated organization on the same instance.

### Recommendation
In `verify_signature`, after determining the signature is valid for `repository_owner`, additionally assert that `repository_owner` matches the organization portion of `repository.full_name` (and of `organization.login` when present) before dispatching to handlers, or resolve `Repository`/`Stack` lookups using the same `repository_owner` value that was used to select the verifying secret rather than re-reading `full_name` independently.

### Proof of Concept
1. Attacker legitimately administers organization `attacker-org`, which has installed this Shipit's GitHub App and knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` selects `Shipit.github(organization: "attacker-org")`, verifies the HMAC successfully (using the correctly known `attacker-org` secret over the whole body), and passes. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on the victim organization's stack, even though the signature was never verified against `victim-org`'s secret. [4](#0-3) [5](#0-4)
