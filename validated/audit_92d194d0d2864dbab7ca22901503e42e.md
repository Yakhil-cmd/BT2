### Title
Scoped API tokens can read the CCTray status of any stack, bypassing per-stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController` scopes stack lookups to the specific stack an `ApiClient` token is bound to, but `Shipit::Api::CCMenuController` overrides that lookup with an unscoped query, breaking the binding between "the stack a token authorizes" and "the stack it actually touches."

### Finding Description
`ApiClient` tokens can be created with an optional `stack_id`, restricting the token to a single stack, alongside a coarse permission string such as `read:stack`: [1](#0-0) 

`Shipit::Api::BaseController` enforces this binding by scoping the `stacks` relation to the client's `stack_id` before resolving `params[:stack_id]`: [2](#0-1) 

`check_permissions!` only validates the coarse `"operation:scope"` string (e.g. `read:stack`) — it never checks *which* stack is being accessed: [3](#0-2) 

So the only place enforcing "this token may only touch its own stack" is the scoped `stacks`/`stack` helper in `BaseController`. `CCMenuController` requires `read:stack` via the same class-level `require_permission` macro, but then **redefines `#stack` to bypass the scoping entirely**, resolving the stack directly and unscoped: [4](#0-3) 

Compare this to `BaseController#stack`, which is the pattern every other API controller relies on: [2](#0-1) 

The equality that should hold is: `token.stack_id == stack_being_rendered.id` (when the token is stack-scoped). `CCMenuController#stack` breaks this by evaluating `Stack.from_param!(params[:stack_id])` against the full `Stack` table instead of `stacks.from_param!(params[:stack_id])`.

### Impact Explanation
An `ApiClient` deliberately scoped to a single stack (the documented mechanism for issuing least-privilege tokens, e.g. the `here_come_the_walrus` fixture with `stack: shipit`, `permissions: [read:stack]`) can read the CCTray XML feed — including stack name, last build status/label, last build time, activity, and web URL — for **any** stack in the Shipit instance by simply supplying a different `stack_id` in the URL and its own valid, narrowly-scoped token: [5](#0-4) 

This is an unauthorized read of stack state via a token that was explicitly authorized for only one stack, matching the "unauthorized read of stack state" High-impact category.

### Likelihood Explanation
Any legitimate holder of a stack-scoped, `read:stack`-permissioned API token (a routine, low-privilege credential meant for CI status badges/CCTray integrations) can trigger this by changing the `stack_id` path parameter — no additional privilege, secret, or session is required beyond the token they were already issued for their own stack.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` (or make it call `stacks.from_param!(params[:stack_id])` like `BaseController`) so that the per-token `stack_id` scope enforced elsewhere in the API is also enforced for the CCTray endpoint.

### Proof of Concept
1. Create/obtain an `ApiClient` token scoped to `stack_id: <stack A>` with only the `read:stack` permission (the standard "least privilege" pattern shown in `test/fixtures/shipit/api_clients.yml`).
2. Call the CCMenu endpoint with a different stack's identifier and the same token, e.g.:
   `GET /api/stacks/<stack-B-owner>/<stack-B-name>/<env>/cctray.xml?token=<stack-A-scoped-token>`
3. `authenticate_api_client` succeeds (token is valid) and `require_permission :read, :stack` passes because the client has `read:stack` in its permission list.
4. `stack` resolves via `Stack.from_param!(params[:stack_id])` (unscoped), returning stack B's data even though the token's `stack_id` column points to stack A.
5. The response renders stack B's build/deploy status, disclosing information about a stack the token was never authorized to see.
