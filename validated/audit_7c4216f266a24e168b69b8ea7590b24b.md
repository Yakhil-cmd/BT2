### Title
Webhook signature verification org is decoupled from the repository the payload actually targets, allowing cross-repository webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` validates the inbound GitHub HMAC signature using one JSON field (`repository.owner.login` / `organization.login`), while every webhook `Handler` subsequently decides *which Shipit repository/stack to mutate* using a **different, independently-attacker-controlled** JSON field (`repository.full_name`). Nothing ties these two fields together, so a valid signature only proves "signed with organization A's secret," not "this payload is about organization A's repository."

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 
the app looks up the GitHub App/secret with `Shipit.github(organization: repository_owner)` and verifies the raw request body against that org's secret. `repository_owner` is read directly from the untrusted payload: [2](#0-1) 

Meanwhile, every `Handler` (e.g. `PushHandler`, the `PullRequest::*Handler`s) resolves the target Shipit `Repository`/stacks from a **separate** field of the same payload: [3](#0-2) 

and `Repository.from_github_repo_name` performs a global, unscoped lookup with no relation back to the verified organization: [4](#0-3) 

`PushHandler` then acts on whatever stacks that lookup returns: [5](#0-4) 

Shipit supports multi-tenant configuration where distinct organizations each have their own `webhook_secret`: [6](#0-5) 

**Binding that should hold:** `repository_owner` (the field whose secret validated the HMAC) `==` owner segment of `repository.full_name` (the field the handler acts on). For a genuine GitHub delivery these are always equal because GitHub only ever signs a repository's own webhook with that repository's/org's configured secret.

**Binding broken by the attacker:** An attacker who administers (or has configured a webhook for) any organization "A" that is itself onboarded to the same multi-tenant Shipit instance knows/controls "A"'s `webhook_secret` (they set it up themselves). They can craft an arbitrary JSON body, set `repository.owner.login`/`organization.login` = `"A"` (so `verify_signature` selects and successfully validates against `A`'s real secret), but set `repository.full_name` = `"victim-org/victim-repo"` — a repository under a completely different organization "victim-org" also configured in the same Shipit instance. `verify_signature` passes because the HMAC really was computed with `A`'s secret; the handler then unconditionally targets `victim-org/victim-repo`'s stacks.

### Impact Explanation
This is an authentication-binding break exactly analogous to "an organization that authenticated versus the repository that is written." Concretely, with a forged `push` event the attacker can invoke `GithubSyncJob`/`stack.sync_github(expected_head_sha:)` on any non-archived stack of a completely unrelated organization's repository, supplying an attacker-chosen `expected_head_sha` and branch — without ever needing `victim-org`'s webhook secret, GitHub App credentials, or a Shipit session. Because Shipit stacks can be configured for continuous deployment (auto-deploy triggered by newly synced commits), this gives an attacker who controls no more than their own onboarded organization a way to force resyncs/deploy-triggering events against a victim organization's stacks that they have no legitimate access to — an unauthorized-deploy vector reachable purely by crafting an HTTP request, satisfying the "unauthorized deploy" Critical-impact criterion. The same unscoped `repository.full_name` lookup pattern (`Handler#stacks`, `Repository.from_github_repo_name`) is reused by the `PullRequest::*Handler` classes, so the same primitive lets an attacker archive/unarchive review stacks or manipulate PR-driven state belonging to a victim organization's repository.

### Likelihood Explanation
Requires the attacker to legitimately administer/configure a webhook for at least one organization already onboarded into the same multi-tenant Shipit deployment (a realistic scenario for shared/self-service Shipit instances using the `github_organizations`/`github_app_config` multi-org feature). No access to the victim organization, its GitHub App private key, or a Shipit user session is required — only a crafted HTTP POST to `/webhooks` (or wherever `WebhooksController` is mounted) with a body signed using the attacker's own organization's secret.

### Recommendation
In `WebhooksController#verify_signature`, cross-check that the organization used to select the webhook secret matches the owner segment of `payload.dig('repository', 'full_name')` (and, for org-level events, `organization.login`) before dispatching to handlers; reject the request if they diverge. Alternatively, have `Handler#stacks`/`Repository.from_github_repo_name` scope repository resolution to the already-verified `repository_owner` rather than trusting the payload's `full_name` independently.

### Proof of Concept
1. Attacker legitimately owns/administers GitHub organization `attacker-org`, which is configured in Shipit's `github.attacker-org.webhook_secret`.
2. Attacker computes `sha1=HMAC-SHA1(webhook_secret_attacker_org, body)` over a crafted JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha, e.g. victim's real current HEAD>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. POST to the webhooks endpoint with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and validates successfully because the HMAC really was computed with that org's secret.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` — a repository the attacker does not own or administer — and enqueues `sync_github(expected_head_sha: ...)` for its matching, non-archived stacks, with no further authorization check.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
