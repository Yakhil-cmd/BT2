### Title
Cross-repository status/check-run spoofing via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit(s) purely by `sha`, with no scoping to the repository named in the webhook payload, then calls `commit.create_status_from_github!` which forwards `commit.stack_id` (the DB-trusted stack, not anything derived from the payload) into `Status.replicate_from_github!`. Because `Commit.sha` is only uniquely indexed per `(stack_id, sha)` — not globally — a webhook whose signature is validly signed for organization/repo *A* can create/replicate a GitHub status onto a `Commit`/`Stack` belonging to an unrelated repository *B*, as long as a commit row with the same `sha` exists for *B* (trivially reproducible for tiny/empty/initial commits as described in the preconditions).

### Finding Description
The intended binding should be:
`stack_id passed to Status.replicate_from_github! == Stack.id whose Repository.full_name matches the verified payload's repository.full_name`

The actual code violates this: [1](#0-0) 
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
`Commit.where(sha: params.sha)` is unscoped by repository — it returns every `Commit` row across every tenant/stack whose sha string matches, regardless of the payload's `repository.full_name`. This then flows into: [2](#0-1) 
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
```
and: [3](#0-2) 
```ruby
def replicate_from_github!(stack_id, github_status)
  find_or_create_by!(
    stack_id:,
    state: github_status.state,
    ...
  )
end
```
`stack_id` here is `commit.stack_id`, sourced entirely from whichever pre-existing `Commit` row matched the sha — never re-derived or cross-checked against the payload's own `repository.full_name`.

Contrast with `PushHandler`, which correctly scopes via the base `Handler#stacks` helper: [4](#0-3) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
```
`StatusHandler` never calls `stacks`/`repository_name` at all, so this scoping is entirely absent for status events.

The DB schema confirms `sha` is not globally unique — the only relevant index is `[stack_id, sha]` (added in migration `20170524104615_index_commits_on_stack_id_and_sha.rb`), meaning duplicate shas across unrelated stacks are an expected, supported condition, not an edge case guarded against elsewhere.

`ExplicitParameters` for `StatusHandler` requires only `sha`, `state`, and optional `context`/`description`/etc. — it never requires or validates `repository`: [5](#0-4) 

Exploit flow: attacker reproduces a commit sha identical to one queued in `victim/prod` (trivial for empty/initial commits) in a repository they control under a GitHub organization already integrated with this Shipit instance (so `verify_signature`'s `Shipit.github(organization: repository_owner)` lookup succeeds and GitHub computes a genuine HMAC for the real webhook). They then trigger (or directly emulate) a `status` event with `context` equal to a name leaked via the victim stack's public `shipit.yml`, `state: 'success'`. `StatusHandler#process` finds the victim's `Commit` row by sha and creates a `Status` bound to the victim's `stack_id`, satisfying `DeploySpec#required_statuses`/`merge_request_required_statuses` for `victim/prod` without ever touching that repository.

`verify_signature` only authenticates that *some* payload came from a GitHub organization already onboarded to this Shipit instance — it does not bind the payload's claimed repository to the resulting DB writes, so it does not prevent this divergence.

### Impact Explanation
A required CI status can be forged for `victim/prod`'s commit/stack from an attacker-controlled repository, bypassing `DeploySpec#required_statuses`/merge-queue gating and enabling an unauthorized merge/deploy decision on a repository the attacker never had write access to — this is a payload for one repository mutating another's stack/commit state, matching the Critical impact category. It is repeatable against any stack whose queued commit sha the attacker can reproduce, and blast radius spans all tenants sharing the Shipit instance and GitHub organization/App installation.

### Likelihood Explanation
Requires: (1) the victim's queued commit sha to be publicly knowable (true, per precondition — commits in a public/observable merge queue), (2) the ability to reproduce that exact sha in an attacker-owned repo (trivial for empty/initial commits, whose sha depends only on tree/parents/timestamps, all copyable from public GitHub API data), (3) a genuinely GitHub-signed webhook for the organization the attacker's repo belongs to, which requires that organization to already have Shipit's GitHub App installed (a real-world common setup where one org hosts many repos/teams, not all of which are tracked by Shipit). No Shipit secrets, sessions, or tokens are needed. Cost is low and the attack is fully repeatable across arbitrary target stacks sharing the same duplicate-sha condition.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup by the payload's own repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.find_each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
and add `requires :repository do requires :full_name, String end` to the `StatusHandler` params schema so the repository is verified rather than implicit. Add a DB-level or application-level assertion in `Status.replicate_from_github!`/`Commit#create_status_from_github!` that the `stack_id` used matches a `Stack` whose `Repository.full_name` equals the verified payload repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not create a status for a commit belonging to an unrelated repository/stack" do
  victim_stack = shipit_stacks(:shipit) # tracks e.g. "shopify/shipit-engine"
  attacker_repo = Shipit::Repository.create!(owner: "attacker", name: "evil-repo")
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: "production", branch: "master")

  shared_sha = "d0d0d0d0d0d0d0d0d0d0d0d0d0d0d0d0d0d0d0d0"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "init")
  attacker_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "init")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "required-check",
    "repository" => { "full_name" => attacker_repo.full_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  victim_status = victim_commit.reload.statuses.last
  # BUG: this currently passes, proving the divergence -- a status was written
  # against the victim's stack_id even though the payload named attacker_repo.
  assert_equal victim_stack.id, victim_status.stack_id

  # Correct binding that SHOULD hold and currently fails:
  expected_stack_ids = Shipit::Repository.from_github_repo_name(attacker_repo.full_name)&.stacks&.pluck(:id) || []
  assert_includes expected_stack_ids, victim_status.stack_id # fails: victim_stack.id not in [attacker_stack.id]
end
```
