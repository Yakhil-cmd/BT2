### Title
Unrestricted path traversal via `inherit_from` in `DeploySpec::FileSystem#build_config` allows arbitrary host file read merged into executed deploy config - (File: `app/models/shipit/deploy_spec/file_system.rb`)

### Summary
`DeploySpec::FileSystem#build_config` resolves `inherit_from` with `path.dirname.join(...)` and only checks `inherits_from_path.exist?` before reading and deep-merging the target file's YAML into the deploy spec, with no containment check against `@app_dir`/`@task.working_directory`. Because `Pathname#join` performs no `..` sanitization, and filesystem calls (`exist?`, `read`) resolve `..` components at the OS level, an attacker-controlled `shipit.yml` can traverse outside the checkout root to read and merge arbitrary host-readable YAML files into the deploy spec.

### Finding Description
Binding claimed vs actual: the code assumes `inherits_from_path == a path inside @app_dir tree`, but the actual binding is `inherits_from_path == path.dirname.join(attacker_string)` with no `expand_path`/`realpath` comparison back to `@app_dir`, so `inherits_from_path` can equal any path on the filesystem reachable via `..` segments that the process user can read.

Code path: `TaskCommands#deploy_spec` constructs `DeploySpec::FileSystem.new(@task.working_directory, @stack)` [1](#0-0)  → `load_config` reads `config_file_path` and calls `build_config` [2](#0-1)  → `build_config` computes `inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))`, checks only `.exist?`, and if true reads/deep-merges it, recursing further [3](#0-2) . There is no code anywhere in `file_system.rb` that calls `.expand_path` and asserts the resolved path is still under `@app_dir`.

Attacker action: on a repository where a review stack has been (or is) provisioned from their fork/branch, the attacker's checked-out `shipit.yml` sets `inherit_from: ../../../../../../etc/some-readable-file.yml` (or any relative traversal string). When `build_config` runs during a deploy/task, `path.dirname.join(...)` produces a path outside the checkout, and the OS-level `exist?`/`read` calls follow the `..` segments and succeed if the target is readable by the Shipit process user and parses as YAML.

Reachability caveat: this deploy-spec code path is invoked for any stack whose working tree contains the attacker's `shipit.yml`, which for review stacks depends on `provision?` in `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb` (and the equivalent `unarchive?`/`ReopenedHandler` logic) actually creating/unarchiving the stack. That method has a genuine operator-precedence bug: `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)` [4](#0-3) . Only the `allow_all` branch is gated by `review_stacks_enabled`; the `allow_with_label`/`prevent_with_label` branches are not, so a repository with `review_stacks_enabled=false` but `provisioning_behavior` set to `allow_with_label`/`prevent_with_label` will still auto-provision stacks from PR labels the attacker controls (`pull_request_label_names` is read straight from the webhook payload) [5](#0-4) . This confirms the precondition the question assumes is a real, separate defect, making the `inherit_from` code path reachable under that specific repository configuration (review stacks off, but a non-default `provisioning_behavior`), not on a fully "review stacks off, default config" repository.

Why existing guards don't stop it: `file()`/`config_file_path` only search a fixed, non-attacker-controlled list of filenames within `@app_dir` [6](#0-5) , but once the *initial* file is located inside the checkout, `build_config`'s recursive `inherit_from` resolution has no equivalent containment check — it is the one place where an attacker-supplied string directly participates in path construction without validation. `SafeYAML.load` restricts what YAML *types* can be parsed but does not restrict *which file* is read.

### Impact Explanation
Successful traversal lets the attacker's own `shipit.yml` merge in the contents of any YAML file readable by the Shipit worker process into the deploy spec (e.g. `deploy`, `machine.environment`, `rollback` keys). Because `config_obj.deep_merge` gives the attacker's own inline config priority over the inherited file's keys, this cannot be used to *override* attacker-set deploy steps, but it can pull in **additional** unset keys (notably `machine.environment` variables) from the target file, which the attacker can then exfiltrate by adding a step that dumps environment variables/config to the task log — a log the attacker (as PR author/reviewer of their own stack) can view. Combined with the fact that all merged config content ultimately becomes shell steps run via `Command`/`PTY.spawn` on the deploy host [7](#0-6) , this is realistically a confidentiality issue (host file read of e.g. secrets/config files reachable by the Shipit OS user) layered on top of the already-existing RCE an attacker has via directly-controlled `deploy.override` steps. It does not by itself grant new command execution beyond what the attacker already has once a review stack is provisioned from their branch.

### Likelihood Explanation
Requires: (1) the target repository to have `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` (a non-default, specific misconfiguration exploiting the `provision?` precedence bug) or, more simply, any repository with review stacks legitimately enabled where the attacker can open/label a PR; (2) the attacker's checked-out working directory to contain a `shipit.yml` with `inherit_from` set to a traversal string; (3) a target file outside the checkout that is both filesystem-readable by the Shipit process user and parses as YAML. Attacker cost is a single PR/branch push and label toggle — no secrets or privileged roles required. Repeatable per deploy/task run.

### Recommendation
In `build_config`, resolve `inherits_from_path` with `.expand_path` and reject it (raise or skip) unless it is still a descendant of `@app_dir` (e.g. `inherits_from_path.expand_path.to_s.start_with?("#{@app_dir.expand_path}/")`). Apply the same containment check to `config_file_path`/`file()` resolution defensively.

### Proof of Concept
Minitest plan (add to `test/models/shipit/deploy_spec/file_system_test.rb` scope, illustrative — not adding to repo):
```ruby
test "build_config does not follow inherit_from outside app_dir" do
  Dir.mktmpdir do |outside_dir|
    secret_path = File.join(outside_dir, "secret.yml")
    File.write(secret_path, { "deploy" => { "override" => ["cat /etc/shadow"] } }.to_yaml)

    Dir.mktmpdir do |app_dir|
      FileUtils.mkdir_p(app_dir)
      relative_traversal = Pathname.new(app_dir).relative_path_from(Pathname.new(outside_dir)).to_s
      File.write(File.join(app_dir, "shipit.yml"), { "inherit_from" => File.join("..", File.basename(outside_dir), "secret.yml") }.to_yaml)

      spec = Shipit::DeploySpec::FileSystem.new(app_dir, shipit_stacks(:shipit))
      config = spec.send(:load_config)

      # BEFORE fix: assert_equal ["cat /etc/shadow"], config.dig("deploy", "override")  -- currently succeeds (vulnerable)
      # AFTER fix:  assert_nil config.dig("deploy", "override")  -- traversal must be rejected
    end
  end
end
```
Assert on both sides of the binding: `inherits_from_path` computed by `build_config` vs. `@app_dir.expand_path` — before the fix these diverge (traversal succeeds and merges), after the fix the method must refuse to read/merge paths where `inherits_from_path.expand_path` is not a descendant of `@app_dir.expand_path`.

      SHIPIT_CONFIG_INHERIT_FROM_KEY = "inherit_from"
      def build_config(path, config_obj)
        return config_obj if config_obj.blank? || !config_obj.key?(SHIPIT_CONFIG_INHERIT_FROM_KEY)

        inherits_from_path = path.dirname.join(config_obj.delete(SHIPIT_CONFIG_INHERIT_FROM_KEY))
        if inherits_from_path.exist?
          inherits_config_obj = read_config(inherits_from_path)
          config_obj = inherits_config_obj.deep_merge(config_obj)
          path = inherits_from_path
        end

        build_config(path, config_obj)
      end

      def read_config(path)
        SafeYAML.load(path.read) if path.exist?
      end
