### Title
Webhook signature verification is bound to `repository.owner.login`, but event handlers act on `repository.full_name` — cross-organization forgery of pushes/statuses - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature against using `params.dig('repository', 'owner', 'login')` (or `organization.login`), but the handlers that actually act on the payload (creating statuses, syncing branches, provisioning/archiving review stacks) resolve the target `Repository`/`Stack` using an entirely separate JSON field, `repository.full_name`. These two fields are never cross-checked against each other, so a signature that is valid for organization A can be replayed with a payload whose `repository.full_name` points at organization B's repository.

### Finding Description
`verify_signature` computes the signing organization from the payload and fetches that organization's `GithubApp` config to validate the `X-Hub-Signature`: [1](#0-0) [2](#0-1) 

Each organization's `GithubApp` instance carries its own independent `webhook_secret` used for HMAC verification: [3](#0-2) [4](#0-3) 

Once the signature is accepted, the raw JSON `params` (not re-derived, not re-scoped) is dispatched unchanged to every registered handler for the event: [5](#0-4) 

Every handler resolves the repository it will act on from a *different* field of the same payload — `repository.full_name` — rather than `repository.owner.login`: [6](#0-5) 

`PushHandler`, for example, uses that resolved repository's stacks to trigger a GitHub sync for an attacker-chosen `after` SHA: [7](#0-6) 

Pull-request handlers likewise resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/create Review Stacks or update pull-request/label state accordingly: [8](#0-7) [9](#0-8) 

This breaks the intended equality: `organization authenticated by verify_signature (repository.owner.login / organization.login) == organization whose repository is written by the handler (repository.full_name)`. GitHub's real webhooks keep these two fields consistent, but nothing in the engine enforces that binding — an attacker forging the raw JSON body only needs a valid signature for *any* organization configured in this Shipit instance, then can freely set `repository.full_name` to name a *different* organization's repository.

### Impact Explanation
In a multi-organization Shipit deployment (one `GithubApp`/`webhook_secret` per org, as modeled by `Shipit.github(organization:)` and `GithubApp#initialize`), an attacker who can produce a valid signature for their own (low-privilege) organization's webhook secret can forge webhook events that are processed as if they came from a completely different organization's repository. Concretely:
- A forged `status` event can create/overwrite a `Status` record on a commit belonging to another organization's stack, which is used by `ci.require` checks to gate deploy safety — this enables bypassing deploy safeguards, i.e. an unauthorized deploy path.
- A forged `push` event can trigger `stack.sync_github` for another organization's stack.
- Forged `pull_request` events can archive/unarchive/create Review Stacks belonging to another organization's repository.

This is a cross-repository write / unauthorized-deploy-enabling primitive crossing an organization boundary that the signature check was supposed to enforce, matching the Critical impact bucket ("cross-repository writes" / "an unauthorized deploy").

### Likelihood Explanation
Exploitability requires the attacker to already control (or know) a valid `webhook_secret` for at least one organization configured in the target Shipit instance — e.g., an org they administer, or a leaked/rotated secret for a low-trust org onboarded to the same Shipit deployment. Given that, forging the raw JSON body with a mismatched `repository.owner.login` vs `repository.full_name` requires no other privilege: `verify_signature` never checks that the two fields agree, and none of the handlers re-verify the signing organization against the resolved `Repository`.

### Recommendation
- In `WebhooksController#verify_signature` (or in `Webhooks::Handlers::Handler`), after establishing the signing organization, assert that `repository_name`'s owner segment (from `payload.dig('repository', 'full_name')`) matches the `repository_owner` used to select the webhook secret; reject (422) on mismatch.
- Alternatively, resolve the target `Repository` using the same authenticated organization identity used for signature verification, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` (attacker-controlled/known secret) and `org-b` (victim), each with distinct `webhook_secret` values via `Shipit.github(organization: ...)`.
2. Attacker crafts a `push` (or `status`) webhook JSON body where:
   - `repository.owner.login = "org-a"`
   - `repository.full_name = "org-b/victim-repo"`
3. Attacker computes `X-Hub-Signature` using `org-a`'s known `webhook_secret` over the raw body.
4. `WebhooksController#verify_signature` resolves `repository_owner = "org-a"`, fetches `org-a`'s `GithubApp`, and successfully verifies the signature.
5. `PushHandler#process` (or the relevant status/pull_request handler) resolves the target repository via `payload.dig('repository', 'full_name') = "org-b/victim-repo"`, and performs the write (`stack.sync_github`, `Status` creation, or Review Stack archive/create) against `org-b`'s stacks — despite the signature only proving control of `org-a`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
