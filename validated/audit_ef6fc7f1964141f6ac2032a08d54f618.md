### Title
NULL/undefined dereference in `is_valid_merkle_proof` oscript operator via unguarded `objProof.siblings` access - (File: formula/evaluation.js)

### Summary
CVE-2021-44505 describes a NULL pointer dereference reachable through `ZPrint` on attacker-crafted input in YottaDB/GT.M. The analogous bug class in ocore is a property access on a value that has not been validated to be an object, reachable from oscript formulas evaluated during AA trigger/definition processing — specifically the `is_valid_merkle_proof` operator in `formula/evaluation.js`.

### Finding Description
The `is_valid_merkle_proof` case evaluates a `proof` expression and builds `objProof` from it: [1](#0-0) 

If `proof` is a `wrappedObject`, `objProof` is taken directly from `proof.obj` with no check that it is a non-null object: [2](#0-1) 

Immediately afterward, when the post-PEM-curves-fix flag is active, the code dereferences `objProof.siblings` outside of any `try/catch`: [3](#0-2) 

Only the subsequent call to `merkle.verifyMerkleProof` is wrapped in `try/catch`: [4](#0-3) 

If `proof.obj` evaluates to `null`, `undefined`, or a primitive (not an object), then `objProof.siblings` at line 1793 throws an uncaught `TypeError: Cannot read properties of null/undefined (reading 'siblings')`, exactly analogous to the NULL-pointer dereference in the reported CVE — an unchecked field access on a value the code assumed would always be a valid object. This mirrors the `deserializeMerkleProof` path in `merkle.js`, which also builds a proof object from arbitrary string content with only shallow structural assumptions and no null/type checks: [5](#0-4) 

### Impact Explanation
`is_valid_merkle_proof` is an oscript formula primitive usable inside AA definitions and AA trigger-time formula evaluation (`formula/evaluation.js`'s `evaluate` function, invoked whenever an AA processes a trigger unit or during AA definition validation). An uncaught exception thrown mid-evaluation on a validating/AA-executing node can propagate out of the asynchronous evaluation chain, which is a crash/DoS vector for any node running the AA — including nodes forced to process a maliciously crafted AA response/formula. Because AA execution is a mandatory, consensus-relevant path (it determines a node's view of unit/AA-response validity), a crash here can stall a node's ability to validate and confirm new units, which is squarely within the accepted impact categories (a network unable to confirm new units due to node divergence/crash on a specific formula input).

### Likelihood Explanation
The `is_valid_merkle_proof` operator is reachable by any account able to define/trigger an Autonomous Agent using oscript, which per the analog scope is "AA author" / "AA trigger sender" reachable surface — no special privilege beyond posting a valid AA definition/trigger is required. Crafting a formula sub-expression that evaluates to a `wrappedObject` wrapping a non-object (`null`/primitive) is plausible depending on which built-in formula constructs can yield such wrapped values (e.g., object-returning getters/parsing functions in the oscript grammar); I was not able to fully enumerate every formula path that produces a `wrappedObject` around a null value within the available indexed code, so exploitability specifics (which exact oscript expression yields `wrappedObject(null)`) remain unconfirmed and should be verified against `formula/evaluation.js`'s full `wrappedObject` construction sites.

### Recommendation
Add an explicit type/nullity check on `objProof` immediately after it is derived from `proof.obj`, before accessing `.siblings`, e.g. `if (typeof objProof !== 'object' || objProof === null) return cb(false);`. Alternatively, move the `Array.isArray(objProof.siblings)` check inside the existing `try/catch` block (or wrap the whole `is_valid_merkle_proof` case body in try/catch and route errors to `setFatalError`/`cb(false)`), consistent with how errors are handled everywhere else in `evaluate()`.

### Proof of Concept
Not independently verified end-to-end (would require confirming which oscript construct produces a `wrappedObject` wrapping `null`/non-object). Conceptually: an AA formula such as `is_valid_merkle_proof('x', <expr yielding wrappedObject(null)>)` would cause `objProof.siblings` at `formula/evaluation.js:1793` to throw an uncaught `TypeError`, since only the `merkle.verifyMerkleProof` call (not the siblings-array check) is guarded by `try/catch`. function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
