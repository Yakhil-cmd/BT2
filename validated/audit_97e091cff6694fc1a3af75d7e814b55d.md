### Title
`ReopenedHandler#unarchive?` ignores `review_stacks_enabled` for non-`allow_all` provisioning behaviors due to `&&`/`||` precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` duplicates the exact same boolean-grouping bug present in `OpenedHandler#provision?`: Ruby's `&&` binds tighter than `||`, so `repository.review_stacks_enabled` is only ANDed with the `provisioning_behavior_allow_all?` branch, not with the `allow_with_label` or `prevent_with_label` branches. As a result, reopening (or, since `unarchive!` creates the stack if it's missing, opening-via-reopen) a labeled PR provisions/unarchives a `Shipit::ReviewStack` even when the repository has explicitly disabled review stacks.

### Finding Description
The intended binding is: `stack gets (re)provisioned == repository.review_stacks_enabled is true`. The actual code in `unarchive?` is: [1](#0-0) 

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Because `&&` has higher precedence than `||`, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label) || (prevent_with_label? && !has_label)`

With `review_stacks_enabled: false`, `provisioning_behavior: :allow_with_label`, and the PR carrying the provisioning label:
- Term 1: `false && allow_all?` → `false`
- Term 2: `true && true` → `true`
- Result: `unarchive?` → `true`, even though `review_stacks_enabled` is `false`.

`process` then calls `stack.unarchive!` via `ReviewStackAdapter#unarchive!` [2](#0-1) , which, if no stack row exists yet, calls `create!` [3](#0-2) , creating a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` and immediately calling `Shipit::ReviewStackProvisioningQueue.add(stack)` [4](#0-3) . Nothing downstream in `ReviewStackProvisioningQueue#work`/`#provision` or `Shipit::ReviewStack` re-checks `review_stacks_enabled` [5](#0-4)  — the only gate for `review_stacks_enabled` in the codebase is this handler-level `&&`, and it fails to guard two of the three OR branches.

This is the identical defect pattern as `OpenedHandler#provision?` [6](#0-5) , confirming the question's premise that the bug is duplicated across handlers.

Attack: an attacker who owns/controls a PR on a repository configured with `review_stacks_enabled: false` and `provisioning_behavior: allow_with_label` applies their own provisioning label (labeling is attacker-controlled on their own PR) and closes+reopens the PR (or simply reopens it once), sending a `pull_request` webhook with `action: "reopened"`. This causes creation/unarchival of a `Shipit::ReviewStack` and enqueues it for provisioning, ultimately leading to `shipit.yml`-driven command execution via `Command#start`/`PTY.spawn` on the deploy host for a repository that explicitly opted out of review stacks.

None of the existing guards prevent this: signature verification (`verify_signature`/`drop_unhandled_event`) only authenticates that GitHub sent the webhook, not that the *feature* is enabled; `ExplicitParameters` schema validates payload shape, not business logic; there is no separate `review_stacks_enabled` check anywhere else in the provisioning pipeline.

### Impact Explanation
An attacker-controlled label on the attacker's own PR causes the engine to create and queue provisioning for a `Shipit::ReviewStack` on a repository where the operator has disabled review stacks (`review_stacks_enabled: false`). This leads to execution of the repository's `shipit.yml` review-stack provisioning steps via `Command#start`/`PTY.spawn` on the deploy host — RCE-class impact on infrastructure the operator believed was protected by disabling the feature. It is repeatable against any repository with this specific but plausible configuration combination (`review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label`), not limited to a single PR or repo.

### Likelihood Explanation
Requires a specific, non-default configuration: `review_stacks_enabled: false` combined with `provisioning_behavior: allow_with_label` (label present) or `prevent_with_label` (label absent, which is the default state for any PR). The `prevent_with_label` branch is especially concerning because it requires *no* attacker action beyond opening/reopening a PR without a label — the default case for most PRs. Attacker cost is minimal (open a PR, optionally add a label they control, reopen it); no privileged credentials are needed.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def unarchive?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `OpenedHandler#provision?` and any other handler duplicating this pattern (`labeled_handler.rb`, `unlabeled_handler.rb` should also be audited for the same grouping).

### Proof of Concept
minitest plan (in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, following existing test fixture conventions in that file):
1. Create a `Shipit::Repository` with `review_stacks_enabled: false` and `provisioning_behavior: :allow_with_label`, `provisioning_label_name: "deploy-preview"`.
2. Build a `pull_request` `reopened` webhook payload whose `labels` array includes `{name: "deploy-preview"}`, with no pre-existing `Shipit::ReviewStack` for that PR's environment.
3. Invoke `Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload...).process` (or dispatch via the webhooks entrypoint used by existing tests in the file).
4. Assert `Shipit::ReviewStack.find_by(environment: "pr#{number}")` is **nil** (expected/correct behavior, binding: `review_stacks_enabled == false` should imply `provisioning triggered == false`).
5. Currently this assertion fails: a `ReviewStack` is created and `awaiting_provision` is `true`, demonstrating `review_stacks_enabled: false` does not equal `provisioning triggered: false`, confirming the vulnerability.
