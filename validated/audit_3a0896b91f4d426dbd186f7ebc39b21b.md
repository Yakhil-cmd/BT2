### Title
Unauthenticated SSE access to stack pubsub channels via `mount Pubsubstub::StreamAction.new, at: "/events"` - (File: config/routes.rb)

### Summary
`Pubsubstub::StreamAction` is mounted directly as a Rack endpoint at `/events` in `config/routes.rb`, bypassing every Rails controller filter chain in the engine. Since `Shipit::Authentication#force_github_authentication` is only wired in as a controller `before_action` (included by `Shipit::ShipitController` / `Shipit::Api::BaseController`), it never runs for this Rack-mounted app, so any unauthenticated client can subscribe to arbitrary `stack.<id>` (or other) pubsub channels and receive live update events.

### Finding Description
The broken binding is: `force_github_authentication` (and thus `current_user.authorized? == true`) MUST run before any request reaches application data, but for `/events` it never runs at all.

- `config/routes.rb` line 9: `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` — this mounts a plain Rack application, not a Rails controller action. [1](#0-0) 
- `Shipit::Authentication` only guards requests through `included do before_action :force_github_authentication end`, which is a controller-level hook that only applies to classes that `include Shipit::Authentication` (e.g. `ShipitController`, `Api::BaseController`). [2](#0-1) 
- Because `Pubsubstub::StreamAction` is mounted as a raw Rack endpoint rather than routed to a controller action, Rails' dispatch never instantiates a controller and never runs `before_action` callbacks — `force_github_authentication` is architecturally unreachable for this route.
- The application relies on this pubsub channel to push live stack/task/deploy update events to browsers via the `subscribe` helper and `page_updater.js`, meaning `channels=stack.<id>` subscriptions carry real update payloads for that stack. [3](#0-2) 

An unprivileged attacker with no session cookie can send `GET /events?channels=stack.<id>` for any numeric/guessable stack id and receive an open SSE/long-poll stream of that stack's update events, with no code path checking `current_user.authorized?`, team membership, or per-repository authorization for this specific route.

### Impact Explanation
The attacker gains unauthenticated real-time read access to another tenant's stack update events (task/deploy/merge-request status changes) pushed over the pubsub channel, repeatable for any stack id without cost, credentials, or prior access — matching the "unauthenticated read of stack state, task streams" High-severity category. Blast radius spans all stacks/tenants hosted by the instance, since the mount point applies globally and is not scoped per-repository.

### Likelihood Explanation
No Shipit credentials, GitHub secrets, or privileged role are required; the attacker only needs network access to the Shipit host and knowledge/guessability of a stack id (numeric or slug-based `stack.<id>` channel names used by the front-end JS). This is trivially reachable with a single unauthenticated HTTP GET request, making exploitation low-cost and fully repeatable.

### Recommendation
Wrap the `/events` mount with an authentication/authorization check before the Rack app is reached — e.g., replace the direct `mount` with a controller action (or a Rack middleware performing the same `force_github_authentication`/`current_user.authorized?` check plus per-channel stack authorization) so that channel subscriptions are validated against the requesting user's access to the specific stack before the stream is established.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb (conceptual, no live GitHub)
class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
  test "unauthenticated GET /events establishes stream for arbitrary stack channel" do
    stack = shipit_stacks(:shipit)
    # No session cookie set, no ApiClient token
    get "/events", params: { channels: "stack.#{stack.id}" }
    assert_response :success
    assert_equal "text/event-stream", @response.media_type
    # Binding check: current_user.authorized? was never evaluated for this request
    assert_nil session[:user_id]
  end
end
```
Both sides of the claimed equality (`current_user.authorized? == true` required before stream open) diverge: the left side is never computed (no controller, no `before_action`), while the right side (stream established) is true — confirming the vulnerability.
