### Title
Accrued market-value overflow permanently freezes borrowing, repayment, withdrawal, and liquidation - ([File: common/src/rates/index.rs])

### Summary
The accrual path can permanently freeze a sufficiently large market before the borrow-index ceiling is reached. `accrue_step` converts scaled debt and supply to RAY values with `scaled_to_original`, which panics when `scaled * index / RAY` exceeds `i128::MAX`; `calculate_supplier_rewards` then repeats the multiplication against the newly accrued borrow index. Because every market mutation performs accrual first, an unprivileged caller can create a very large, highly utilized position and later make repayments, withdrawals, liquidations, and even `update_indexes` consistently revert.

### Finding Description
`Controller::supply`, `borrow`, `withdraw`, `repay`, `liquidate`, and `update_indexes` are reachable without administrative privileges, subject to normal authorization and market rules. [1](#0-0) [2](#0-1) 

The pool stores supply and debt as scaled RAY amounts and applies indexes to recover their current value. [3](#0-2)  `global_sync` unconditionally executes `accrue_step` for each elapsed chunk before committing accrued indexes and revenue. [4](#0-3)  `accrue_step` first computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`, then computes the next borrow index and the rewards from `borrowed * old_index` and `borrowed * new_index`. [5](#0-4)  `scaled_to_original` is a direct `Ray::mul`. [6](#0-5) 

The multiplication eventually calls `mul_div_half_up`, which returns `MathOverflow` if the exact result cannot fit in `i128`. [7](#0-6)  The borrow index itself is capped at `MAX_BORROW_INDEX_RAY`, but that cap only bounds the index; it does not bound `borrowed * borrow_index`. [8](#0-7)  `calculate_supplier_rewards` also evaluates the uncapped market-value products `borrowed.mul(old_index)` and `borrowed.mul(new_index)`, so a large scaled-debt book can overflow while the index remains below its configured cap. [9](#0-8) 

For an 18-decimal asset, supplying one billion whole tokens creates approximately `1e36` scaled RAY units because the conversion multiplies the native amount by `10^(27-18)`. [10](#0-9)  With roughly `9.8e35` scaled debt, the debt value exceeds `i128::MAX` once the borrow index reaches approximately `173.6 * RAY`, far below the `1e36` raw index ceiling. Once the next accrual would cross that value, it reverts and no state transition commits; all later calls reach the same multiplication and revert again. [11](#0-10) 

### Impact Explanation
This permanently freezes all funds and debt in the affected market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize collateral, `claim_revenue` cannot settle accrued claims, and governance cannot use `update_params` to apply a safer curve because pool parameter replacement also accrues first. [12](#0-11) [13](#0-12) 

The freeze is not limited to the attacker's account: every user position sharing that `(hub_id, token)` market is blocked by the market-wide `borrowed` and `supplied` totals. Bad-debt cleanup does not provide a reliable escape because liquidation and cleanup paths still operate through the same market accrual before reducing the book. [14](#0-13) 

### Likelihood Explanation
The attack requires a listed market whose configured supply and borrow caps admit balances near the `i128` numeric boundary, sufficient collateral to establish high utilization, and enough elapsed time for the borrow index to cross the market-specific value ceiling. No privileged call, oracle manipulation, leaked key, or malformed parameter is required; the attacker can use ordinary `supply`, `borrow`, and permissionless `update_indexes` calls. [15](#0-14) [2](#0-1) 

The capital requirement is substantial, particularly for high-decimal assets where the RAY scaling factor is largest. Nevertheless, admitted caps are only bounded by the token-to-RAY representation domain, and the current index cap does not prevent a large book from crossing the separate value ceiling first. [16](#0-15) [17](#0-16) 

### Recommendation
Enforce a joint bound on scaled book size and accrued index rather than bounding only the index. In particular:

- Before updating indexes, compute the maximum index that keeps both `borrowed * borrow_index / RAY` and `supplied * supply_index / RAY` within `i128`.
- Apply that dynamic ceiling inside `accrue_step`, before `scaled_to_original` and `calculate_supplier_rewards`.
- Alternatively, use exact `I256` arithmetic for market totals and rewards, while still enforcing explicit protocol ceilings before converting results back to `i128`.
- Ensure repayment, withdrawal, liquidation, bad-debt cleanup, and governance parameter changes remain executable when accrual reaches a configured or representable ceiling, for example by treating index growth as saturated rather than reverting.
- Add a regression case matching the transaction sequence below and assert that repay, withdraw, liquidation, and rate-model replacement remain possible at the boundary.

### Proof of Concept
Let `BIG18` be a listed 18-decimal borrowing asset and `COL` a listed collateral asset, with caps and the interest-rate model admitting the following exposure:

1. An unprivileged attacker calls `supply(caller, 0, spoke_id, [(BIG18, 1_000_000_000 * 10^18), (COL, sufficient_collateral)])` to create an account and supply both assets. [18](#0-17) 
2. The attacker calls `borrow(caller, account_id, [(BIG18, 980_000_000 * 10^18)], Some(caller))`, producing 98% utilization subject to the market's collateral rules. [19](#0-18) 
3. After time passes, any caller invokes `update_indexes(caller, [BIG18])`; the pool calls `accrue_step`, which computes `borrowed * new_borrow_index / RAY`. [2](#0-1) [11](#0-10) 
4. When the new borrow index is above approximately `173.6 * RAY`, the `9.8e35` scaled-debt book produces a value larger than `i128::MAX`, and `mul_div_half_up` raises `MathOverflow`. [20](#0-19) 
5. The transaction reverts before committing the index. Subsequent `update_indexes`, `repay`, `withdraw`, `liquidate`, `claim_revenue`, and rate-model update calls repeat accrual first and revert identically, permanently locking the market's collateral and debt. [21](#0-20) [22](#0-21)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.

    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);

pub fn accrue_step(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    supplied: Ray,
    borrow_index: Ray,
    supply_index: Ray,
    delta_ms: u64,
) -> AccrualStep {
    let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
    let supplied_original = scaled_to_original(env, supplied, supply_index);
    let util = utilization(env, borrowed_original, supplied_original);
    let borrow_rate = calculate_borrow_rate(env, util, params);
    let interest_factor = compound_interest(env, borrow_rate, delta_ms);

    let new_borrow_index = update_borrow_index(env, borrow_index, interest_factor);

    let (supplier_rewards, protocol_fee) =
        calculate_supplier_rewards(env, params, borrowed, new_borrow_index, borrow_index);

    let new_supply_index = update_supply_index(env, supplied, supply_index, supplier_rewards);

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
