### Title
`uint64`→`int64` Narrowing Cast in `Split()` Corrupts CN/CL Staking Reward Distribution — (File: `kaiax/staking/staking_info.go`)

---

### Summary

The `Split()` function in `kaiax/staking/staking_info.go` unsafely narrows `uint64` staking amounts to `int64` when computing the proportional reward split between a Consensus Node (CN) and its Consensus Liquidity (CL) pool. If a consolidated node's `StakingAmount` or `CLStakingAmount` exceeds `math.MaxInt64` (~9.22 × 10⁹ KAIA), the cast silently produces a negative `big.Int`, corrupting the denominator and numerator of the split formula and causing incorrect KAIA reward distribution at every block finalization.

A structurally identical overflow exists in `assignStakingRewards` and `assignStakingRewardsFlex`, where `totalExcessInt` (a bare `uint64`) accumulates excess stakes across all validators without overflow protection — the direct analog of the UTXO `inputSatoshis` accumulation bug in the external report.

---

### Finding Description

**Root cause 1 — `int64` narrowing cast in `Split()`** [1](#0-0) 

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }
    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))                    // ← unsafe cast
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))    // ← unsafe cast
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )
    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount  = clAmount.Div(clAmount, totalAmount)
    cnAmount  := big.NewInt(0).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

Both `c.StakingAmount` and `c.CLStakingInfo.CLStakingAmount` are declared `uint64` in KAIA units. [2](#0-1) [3](#0-2) 

`uint64` holds up to ~18.4 × 10⁹ KAIA; `int64` holds only up to ~9.22 × 10⁹ KAIA. Any value above that threshold wraps to a negative integer. `big.NewInt(negative)` then propagates a negative weight into the split formula, producing one or more of:

| Condition | Result |
|---|---|
| `totalAmount == 0` | division-by-zero panic |
| `totalAmount < 0` | `clAmount` is negative; `cnAmount = amount − clAmount > amount` |
| `clAmountBig < 0, totalAmount > 0` | `clAmount` is negative; CN receives more than `amount` |

`Split()` is called in three reward-critical sites: [4](#0-3) [5](#0-4) [6](#0-5) 

These cover staking rewards (Kore path), flex staking rewards (Osaka/Prague path), and proposer rewards (Prague path).

**Root cause 2 — `uint64` accumulation overflow in `totalExcessInt`**

This is the direct structural analog of the external UTXO bug. [7](#0-6) 

```go
totalExcessInt = uint64(0)
...
cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount  // uint64 + uint64, no overflow check
totalExcessInt += cnTotalStakingAmount - minStake          // uint64 accumulation, no overflow check
...
totalExcess = new(big.Int).SetUint64(totalExcessInt)       // wraps silently if overflowed
```

The same pattern appears in `assignStakingRewardsFlex`: [8](#0-7) 

If `totalExcessInt` wraps to a small value, `totalExcess` becomes an artificially small denominator. Every per-validator reward `excess * stakersReward / totalExcess` is then inflated, the sum of all allocations exceeds `stakersReward`, and `remaining` goes negative. That negative remainder is added to the proposer: [9](#0-8) 

reducing the proposer's reward below zero and corrupting the `RewardSpec` written to state.

**How staking amounts enter the system**

Amounts are read from on-chain contracts, divided by `params.KAIA` (10¹⁸), and stored as `uint64`: [10](#0-9) [11](#0-10) [12](#0-11) 

The consolidation step also accumulates `uint64` amounts without overflow protection: [13](#0-12) 

---

### Impact Explanation

- **Root cause 1**: When triggered, `Split()` returns a `cnAmount` larger than the total reward allocated to that validator. The excess is deducted from `remaining`, which becomes negative and is propagated as `kip82Remainder` to the proposer, reducing the proposer's reward. Net effect: unauthorized redistribution of KAIA block rewards between CN stakers, CL pools, and the block proposer at every block where the affected validator participates.

- **Root cause 2**: An overflowed `totalExcessInt` denominator causes every staker's individual reward to be over-allocated. The sum of staker allocations exceeds the staker budget; the negative remainder reduces the proposer's reward. Same unauthorized redistribution impact.

Both affect `FinalizeState` reward distribution — a protected asset accounting path.

---

### Likelihood Explanation

**Current likelihood is low.** Staking amounts are stored in KAIA units (divided by 10¹⁸). The `int64` overflow threshold is ~9.22 × 10⁹ KAIA; the `uint64` accumulation threshold is ~18.4 × 10⁹ KAIA. The current total KAIA supply (~5.4 billion KAIA initial + ~200 million KAIA/year inflation) does not yet reach these thresholds for a single consolidated node.

However:
- The supply grows continuously via block inflation.
- Multiple staking contracts sharing one reward address are consolidated by `consolidateNodes`, summing their `uint64` amounts — a single logical validator can aggregate across many contracts.
- CL staking amounts from the CLRegistry are added on top of CN staking amounts with no combined-cap check.
- No guard exists anywhere in the call chain to detect or reject amounts approaching these thresholds.

The vulnerability is latent and will become exploitable as the total supply grows, or if a validator consolidates enough staking contracts.

---

### Recommendation

Replace all `uint64` intermediate accumulators and narrowing casts with `*big.Int` throughout the staking reward path:

1. **`Split()`** — use `new(big.Int).SetUint64(c.StakingAmount)` and `new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)` instead of `big.NewInt(int64(...))`.

2. **`assignStakingRewards` / `assignStakingRewardsFlex`** — replace `totalExcessInt uint64` and `cnTotalStakingAmount uint64` with `*big.Int` accumulators, mirroring the fix applied to the external UTXO bug.

3. **`consolidateNodes`** — replace `StakingAmount uint64` in `consolidatedNode` with `*big.Int`, or at minimum add an overflow check on the accumulation `cn.StakingAmount += si.StakingAmounts[i]`.

### Proof of Concept

```go
package main

import (
    "fmt"
    "math"
    "math/big"
)

func main() {
    // Simulate Split() with a StakingAmount just above math.MaxInt64
    // (e.g., a validator with 9.3 billion KAIA staked, reachable as supply grows)
    cnStake := uint64(math.MaxInt64) + 1_000_000_000 // 9,223,372,037,854,775,807 KAIA
    clStake := uint64(1_000_000_000)                  // 1 billion KAIA

    // Current (buggy) code
    cnAmountBig := big.NewInt(int64(cnStake)) // wraps negative!
    clAmountBig := big.NewInt(int64(clStake))
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)

    reward := big.NewInt(6_400_000_000_000_000_000) // 6.4 KAIA in kei

    fmt.Println("cnAmountBig:", cnAmountBig) // negative
    fmt.Println("totalAmount:", totalAmount) // negative or near-zero

    if totalAmount.Sign() == 0 {
        fmt.Println("PANIC: division by zero")
        return
    }
    clAmount := new(big.Int).Div(new(big.Int).Mul(clAmountBig, reward), totalAmount)
    cnAmount := new(big.Int).Sub(reward, clAmount)

    fmt.Println("clAmount:", clAmount) // negative
    fmt.Println("cnAmount:", cnAmount) // > reward (unauthorized excess)

    // Correct code
    cnAmountBigCorrect := new(big.Int).SetUint64(cnStake)
    clAmountBigCorrect := new(big.Int).SetUint64(clStake)
    totalAmountCorrect := new(big.Int).Add(cnAmountBigCorrect, clAmountBigCorrect)
    clAmountCorrect := new(big.Int).Div(new(big.Int).Mul(clAmountBigCorrect, reward), totalAmountCorrect)
    cnAmountCorrect := new(big.Int).Sub(reward, clAmountCorrect)
    fmt.Println("correct clAmount:", clAmountCorrect)
    fmt.Println("correct cnAmount:", cnAmountCorrect)
}
```
