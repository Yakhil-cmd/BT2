### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by SHA across the entire database, with no filter tying the status to the repository that emitted the webhook. If a commit with the same SHA (e.g. from a shared history, cherry-pick, rebase, or coincidental hash reuse across a fork lineage) exists in another stack, an attacker's own repository's `status` webhook can create/replicate a `Status` on a victim stack's commit, and because `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery` unconditionally checks `stack.continuous_deployment?` and queues `ContinuousDeliveryJob`, a forged `success` status can trigger an actual deploy on the victim stack. [4](#0-3) [5](#0-4) 

### Finding Description
The broken binding: `Status.stack_id` should equal `commit.stack_id` should equal the `stack_id` derived from the webhook's authenticated `repository.full_name`. Instead, `StatusHandler#process` does:

```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 

This never consults `repository_name`/`stacks` (available via the `Handler` base class, and used correctly by `PushHandler`), so any commit row anywhere in the database whose `sha` column matches the attacker-supplied `sha` parameter receives a new `Status` row scoped to *that commit's own stack* — not the stack that actually authenticated the webhook. `Status#schedule_continuous_delivery` (an `after_commit` callback) then calls `commit.schedule_continuous_delivery`, which checks only `stack.continuous_deployment?` and `stack.deployable?` before queuing `ContinuousDeliveryJob`, with no verification of which repository originated the status. [5](#0-4) [6](#0-5) 

Root cause: the `Handler` base class already provides a `stacks` helper, scoped to `Repository.from_github_repo_name(repository_name)`, that other handlers (`PushHandler`) correctly use to restrict effects to the authenticated repository. `StatusHandler` omits this scoping entirely. [3](#0-2) 

`verify_signature` in `WebhooksController` only proves that the payload came from the organization named in `repository.owner.login` of the payload — it does not, and cannot, prove that the `sha` field actually belongs to a commit in that same organization/repository. It only limits *who* can send the payload, not *which commit rows it may mutate*. [7](#0-6) 

**Caveat on exploitability**: to trigger this, an attacker needs a commit SHA collision between their own repository (which they control and can send authenticated status webhooks for) and a commit that already exists in the victim's stack's `commits` table. Git SHA-1 collisions are not attacker-controllable in practice (this is not the classic same-repo/fork scenario where SHAs are trivially shared, e.g., forks of the same upstream history, cherry-picked commits, or commits synced across multiple stacks tracking the same underlying repository/branch under different Shipit `Stack` records). The realistic exploitation path is when **two Shipit `Stack` records track the same or overlapping GitHub repository** (e.g., a stack per environment, or a stack tracking a fork/mirror with shared commit history) — in that legitimate configuration, the same commit SHA genuinely exists in multiple stacks' `commits` tables, and a status webhook authenticated for one repository will silently apply to the commit row in *all* stacks sharing that SHA, including ones the webhook's repository owner does not administer.

### Impact Explanation
A webhook correctly authenticated for repository A can create/replicate `Status` rows against commit records belonging to a different `Stack` (potentially a different repository/organization) whenever that commit's SHA is also present in that other stack's `commits` table. If the victim stack has `continuous_deployment: true`, this results in an unauthorized deploy trigger via `ContinuousDeliveryJob` — matching the "unauthorized deploy" Critical impact category, since a payload for one repository is mutating another's commit/stack state and driving deploy automation it did not authenticate. [4](#0-3) [5](#0-4) 

The blast radius is limited to stacks that share commit SHAs with the attacker-controlled repository (multi-stack/fork/mirror setups), not arbitrary unrelated tenants, since SHA-1 preimage/collision attacks against an arbitrary target SHA are not practically feasible.

### Likelihood Explanation
Requires: (1) the attacker owns/controls a repository with a working Shipit webhook (an org already onboarded to Shipit, which the attacker does not need elevated Shipit privileges for — they only need GitHub push/CI access to their own repo), (2) a genuine SHA overlap between the attacker's repository and the victim stack's commit table (realistic mainly for multiple `Stack`s tracking the same or forked/mirrored codebase), and (3) the victim stack has `continuous_deployment` enabled and required status context matching `ci/circleci`. This is not exploitable against an arbitrary, unrelated victim repository without a genuine SHA collision, which lowers likelihood versus the "unscoped" framing implies for fully unrelated repos, but is realistic for the common multi-stack-per-repo topology.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `PushHandler`:

```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

or more efficiently, join `Commit` to `Stack`/`Repository` via `stacks` and filter `Commit.where(sha: params.sha, stack: stacks)` before iterating, ensuring a status webhook can only ever affect commits belonging to stacks tied to the repository named in the payload.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status handler does not write statuses for commits belonging to a different repository's stack" do
  attacker_repo = shipit_repositories(:attacker_repo) # full_name = 'attacker/evil'
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(continuous_deployment: true)
  shared_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared sha', author: shipit_users(:shipit))

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/circleci',
    'repository' => { 'full_name' => attacker_repo.github_repo_name, 'owner' => { 'login' => 'attacker' } }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  assert_no_enqueued_jobs(only: Shipit::ContinuousDeliveryJob) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Before the fix, this assertion fails: `victim_commit.statuses.count` increases and a `ContinuousDeliveryJob` is enqueued for `victim_stack`, even though the webhook's `repository.full_name` never named `victim_stack`'s repository. After scoping `StatusHandler` to `stacks`, both assertions pass.
