### Title
Push-payment ETH claim on Sui→ETH bridge can be permanently stuck if recipient rejects raw ETH - ([File: bridge/evm/contracts/BridgeVault.sol])

### Summary
`BridgeVault.transferETH` unwraps WETH and forwards native ETH to the claim recipient with a low-level call, then hard-`require`s success. The recipient address is fixed inside the signed bridge message and cannot be altered after the fact, so if it cannot accept a raw ETH push (a non-payable contract, a contract that reverts, or one whose `receive`/fallback consumes more gas than what remains after the vault's own withdraw/transfer path), the claim transaction always reverts and `isTransferProcessed[nonce]` is never set. This is the same push-payment failure mode described in the Aave finding, reproduced almost verbatim in `BridgeVault.sol`.

### Finding Description
`_transferTokensFromVault` in `bridge/evm/contracts/SuiBridge.sol` (and the V2 equivalent in `SuiBridgeV2.sol`) calls `vault.transferETH(payable(recipientAddress), amount)` when the bridged token is ETH: [1](#0-0) 

`BridgeVault.transferETH` implements exactly the push-payment pattern flagged in the Aave report — it unwraps WETH and immediately forwards the ETH to `recipientAddress` via a raw call, reverting the whole transaction if the call fails: [2](#0-1) 

The claim is driven by `transferBridgedTokensWithSignatures`, which only marks the message processed *after* `_transferTokensFromVault` succeeds: [3](#0-2) 

The `recipientAddress` is decoded straight from the signed cross-chain message payload (`BridgeUtils.decodeTokenTransferPayload`) and is never validated to be an EOA or a contract capable of accepting ETH. Because this address is embedded in the message that the Sui-side committee already signed (derived from what the depositor supplied on the Sui side when locking tokens), it is immutable for that nonce — there is no way to resubmit the claim with a different, ETH-capable recipient. If:
- the recipient is a contract with no `receive`/payable fallback, or
- the fallback always reverts, or
- the fallback needs more gas than remains in the transaction (which, unlike the ETH mainnet 2300-gas `transfer()` pattern, would need to be extremely gas-hungry since the raw `call` forwards all remaining gas — but a contract can still deliberately consume excess gas or revert),

then `require(success, "ETH transfer failed")` reverts every future attempt at `transferBridgedTokensWithSignatures` for that nonce. The ETH is already unwrapped from WETH but stuck: it cannot be delivered, the message can never be marked processed, and there is no emergency recovery/retry path found in the vault, bridge, or limiter contracts (no “convert to WETH transfer instead” fallback, no owner-only sweep for stuck native ETH tied to a specific nonce).

### Impact Explanation
This produces a **permanent fund lock**: SUI-side funds are already escrowed/locked against this specific bridge message, and the corresponding ETH-side claim can never succeed for a recipient that cannot receive raw ETH. This matches the explicitly allowed High/Medium impact category "permanent fund lock" in the bounty scope. It does not rise to Critical (no unauthorized minting, no theft, no verifier/runtime bypass, no exceeding supply caps) — it is a fund-lock/DoS on a specific bridge transfer.

### Likelihood Explanation
Reachable entirely from unprivileged, public input: any ordinary user (or an attacker griefing another user by controlling which EVM address is set as recipient, e.g. in integrations where recipient addresses come from user-supplied strings) can trigger this by bridging SUI→ETH ETH transfers to a contract address that cannot accept raw ETH pushes. No special privileges, malicious validators, or bridge authority collusion are required — this is purely a consequence of the vault's push-payment design, matching the root cause of the referenced Aave report.

### Recommendation
- Do not hard-revert the whole claim on a failed raw ETH push. Instead, on failure, fall back to transferring WETH (ERC20) to the recipient instead of unwrapped ETH, so the recipient can retrieve value through a pull-based ERC20 transfer regardless of fallback behavior.
- Alternatively, adopt a pull-payment pattern: on failure, credit the amount to an internal "pending withdrawal" mapping that the recipient (or anyone on their behalf) can claim later via a separate `withdrawStuckETH` function, rather than looping forever on the same failing push.
- Still mark the nonce as processed once funds are credited (even via the fallback path), so the message doesn't stay in limbo, and emit an event distinguishing "delivered as ETH" vs "delivered as WETH/pending" so downstream tooling and users are aware.

### Proof of Concept
1. On the Sui side, initiate a token bridge transfer of ETH with a destination `recipientAddress` set to a freshly deployed Solidity contract with no `receive()`/`fallback()` function (or one that unconditionally reverts).
2. Once committee signatures are gathered, call `SuiBridge.transferBridgedTokensWithSignatures` (or `SuiBridgeV2` equivalent) with those signatures.
3. Execution reaches `_transferTokensFromVault` → `vault.transferETH(recipientAddress, amount)` → `wETH.withdraw(amount)` succeeds, but `recipientAddress.call{value: amount}("")` fails because the contract cannot accept ETH.
4. `require(success, "ETH transfer failed")` reverts the whole transaction; `isTransferProcessed[nonce]` remains `false`.
5. Any subsequent call to `transferBridgedTokensWithSignatures` with the same message/nonce will fail identically forever — the ETH is permanently unrecoverable through the intended claim path, and no alternate recovery function exists in `BridgeVault.sol`, `SuiBridge.sol`, or `SuiBridgeV2.sol`.

    function _transferTokensFromVault(
        uint8 sendingChainID,
        uint8 tokenID,
        address recipientAddress,
        uint256 amount
    ) private whenNotPaused limitNotExceeded(sendingChainID, tokenID, amount) {
        address tokenAddress = committee.config().tokenAddressOf(tokenID);

        // Check that the token address is supported
        require(tokenAddress != address(0), "SuiBridge: Unsupported token");

        // transfer eth if token type is eth
        if (tokenID == BridgeUtils.ETH) {
            vault.transferETH(payable(recipientAddress), amount);
        } else {
            // transfer tokens from vault to target address
            vault.transferERC20(tokenAddress, recipientAddress, amount);
        }

        // update amount bridged
        limiter.recordBridgeTransfers(sendingChainID, tokenID, amount);
    }
