### Title
Webhook signature is checked against the organization derived from `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, allowing cross‑organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to HMAC-verify a request against by reading `repository.owner.login` (or `organization.login`) straight out of the *unverified* JSON body. [1](#0-0)  Once the signature check passes, the actual event handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolve which `Stack`/`Commit` to mutate using a completely different field, `repository.full_name`, taken from the very same attacker-supplied body. [2](#0-1)  Nothing ties the two fields together, so a party who legitimately knows the `webhook_secret` for one organization/App configured on a shared Shipit instance can forge a signed payload whose `repository.owner.login` matches their own org (to pass verification) while `repository.full_name` names a completely different org/repo's stack, causing Shipit to process forged push/status/check-suite events against that unrelated stack.

### Finding Description
Shipit supports hosting multiple GitHub organizations from one instance, each configured with its own `webhook_secret` under `Shipit.github(organization: ...)`. [3](#0-2)  The webhook signature check for an incoming request is:

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

`verify_webhook_signature` is a standard HMAC-SHA1 comparison of the raw body against the configured secret for whatever organization name is embedded in the JSON body. [5](#0-4)  This equality binding — "the organization that authenticated" (i.e., whose secret validated the HMAC) — is supposed to equal "the repository that is written" (i.e., whose stacks get mutated by the event handler). But the handler base class instead reads a *different* JSON key to select the target:

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

Because both `repository.owner.login` and `repository.full_name` are attacker-controlled fields inside the same JSON body that is signed by the attacker themselves (using a webhook secret they legitimately possess for their own tenant/org on the shared instance), the attacker can decouple them: set `repository.owner.login` to their own org (so the correct, known secret validates the signature) while setting `repository.full_name` to `"victim-org/victim-repo"` (so the handler operates on a totally different tenant's stack). `Repository.from_github_repo_name` performs no cross-check against `repository_owner`/`repository.owner.login`; it simply splits `full_name` on `/` and looks up whatever `Repository` matches. [6](#0-5) 

The `StatusHandler` is especially exposed: it doesn't even scope by stack/repository, just `Commit.where(sha: params.sha)`, and writes an arbitrary CI status (`state`, `description`, `target_url`, `context`) straight from the forged payload:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

That forged status directly feeds `Commit#deployable?`, which gates CI-required deploys:
```
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [8](#0-7) 

and the deploy API explicitly relies on this flag when `require_ci` is requested:
```
param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?
``` [9](#0-8) 

`PushHandler` and `CheckSuiteHandler` are similarly reachable via the same `repository.full_name` mismatch, letting the attacker trigger `stack.sync_github` / `schedule_refresh_check_runs!` on an unrelated stack. [10](#0-9) [11](#0-10) 

### Impact Explanation
This breaks the trust boundary: "the organization that authenticated" (whose `webhook_secret` validated the request) ≠ "the repository that is written" (whose `Stack`/`Commit` records get mutated). On a multi-tenant Shipit deployment, any party who is a legitimate administrator of one small/low-trust GitHub App/org configured on the shared instance can forge webhook events that write into a completely different, higher-value organization's stacks — most critically, forging a passing (`success`) CI status for an arbitrary commit SHA via `StatusHandler`, which can satisfy `require_ci` checks and enable an unauthorized deploy. This matches the Critical category "an unauthorized deploy" and the High/Critical category of "cross-repository writes."

### Likelihood Explanation
Exploitation requires the attacker to legitimately possess a `webhook_secret` for at least one organization/App configured on the shared Shipit instance (e.g., they administer their own low-privilege project hosted on the same instance) — this is not "no credential at all," but it is far short of the privilege needed to write to the victim organization's repository or Shipit account. Given Shipit's documented support for hosting many orgs on one instance via the `github: {org: {...}}` map, this is a realistic deployment pattern, and the only thing separating tenants from writing into each other's stacks is this un-enforced binding between `repository.owner.login` and `repository.full_name`.

### Recommendation
Enforce that the field used to select the verification secret is the same field used to resolve the target repository/stack: derive both from `repository.full_name`'s owner segment (or require exact equality between `repository.owner.login` and the owner portion of `repository.full_name`) before dispatching to any handler. Additionally, scope `StatusHandler`'s `Commit.where(sha: ...)` lookup to commits belonging to stacks whose repository owner matches `repository_owner`, rather than allowing an unscoped, instance-wide SHA lookup.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-evil` and `org-victim`, each with its own `webhook_secret` (a realistic multi-tenant configuration per `docs/setup.md`).
2. As the legitimate administrator of `org-evil`'s GitHub App, know `org-evil`'s `webhook_secret`.
3. Craft a JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-evil" }, "full_name": "org-victim/victim-repo" }
}
```
4. Compute `X-Hub-Signature: sha1=HMAC_SHA1(org-evil-secret, body)` and POST to `/github/webhooks` with `X-Github-Event: status`.
5. `verify_signature` reads `repository.owner.login` = `"org-evil"`, fetches `org-evil`'s secret, and the signature verifies successfully. [12](#0-11) 
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged `success` status into `org-victim`'s repository. [7](#0-6) 
7. If `org-victim`'s stack requires CI (`require_ci: true`), a subsequent deploy request against that commit now passes `commit.deployable?` due to the forged status, resulting in an unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
