### Title
Unbounded RAY debt valuation can permanently freeze an entire market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
`accrue_step` converts scaled debt and supply into RAY-denominated values before applying the configured borrow-index ceiling. When either multiplication exceeds `i128::MAX`, accrual panics with `MathOverflow`, even though the borrow index itself may remain below `MAX_BORROW_INDEX_RAY`. Because every pool mutation and controller position operation accrues the touched market first, one oversized/high-utilization market can become permanently unusable. [1](#0-0) [2](#0-1) 

### Finding Description
The overflow occurs in `scaled_to_original`, which evaluates `scaled.mul(index)` for both borrowed and supplied totals. [3](#0-2)  That conversion runs before `update_borrow_index` clamps the next index to `MAX_BORROW_INDEX_RAY`, and before `calculate_supplier_rewards` separately multiplies debt by the old and new indexes. [4](#0-3) [5](#0-4) 

The vulnerable sequence is:

1. A whale market accumulates enough scaled debt that `borrowed * borrow_index` eventually exceeds `i128::MAX` / RAY precision.
2. Any address calls `Controller::update_indexes(caller, assets)` with `assets = [vulnerable_hub_asset]`.
3. `markets::update_indexes` forwards the market to `pool.update_indexes`. [6](#0-5) 
4. `ops::market::accrue` loads the market and calls `global_sync`. [7](#0-6) 
5. `global_sync` calls `accrue_step`, whose first `scaled_to_original` call overflows and aborts the transaction. [8](#0-7) 

The regression test demonstrates this terminal state: after the overflow, both withdrawal and repayment continue to fail because they accrue first. [9](#0-8) [10](#0-9) 

### Impact Explanation
This is a permanent market-level denial of service, not merely a transaction limit or budget failure. Once the checked multiplication overflows, every operation that loads and accrues the market encounters the same arithmetic state: repayment, withdrawal, borrowing, liquidation, revenue accounting, bad-debt handling, and parameter updates cannot complete. The pool can still hold token cash, but neither suppliers nor borrowers can move it through the protocol. This matches permanent freezing of user funds and can leave bad debt unliquidatable.

### Likelihood Explanation
The trigger requires an unusually large market and sustained interest accrual, so it is not a one-call attack on a normally sized market. Nevertheless, the reachable trigger is permissionless: `Controller::update_indexes` only requires caller authorization and accepts arbitrary listed `HubAssetKey` values. [11](#0-10)  Market caps admit asset amounts up to the asset-decimal domain rather than ensuring that future scaled-value growth remains representable, so sufficiently large configured caps and balances can reach this state. The missing guard is deterministic: once debt value no longer fits `i128`, there is no recovery path through ordinary entrypoints.

### Recommendation
Add representability-aware index ceilings in addition to the fixed `10^36` index caps. For each market, cap `borrow_index` and `supply_index` at the largest value for which all required products—`borrowed * borrow_index`, `supplied * supply_index`, and their directed ceiling/floor variants—remain representable. When the dynamic ceiling is reached, accrual should commit the state at that ceiling and safely report the market as interest-saturated instead of repeatedly attempting an overflowing accrual. Add regression coverage proving that after saturation, `update_indexes`, `repay`, `withdraw`, `liquidate`, and `clean_bad_debt` continue to execute.

### Proof of Concept
The existing test constructs the terminal condition with approximately one billion 18-decimal tokens supplied and 98% borrowed, advances time until accrual fails, and confirms that the configured index cap did not engage before the value overflow. It then verifies that both `withdraw` and `repay` revert with `MathOverflow`. [12](#0-11) 

Condensed execution path:

```text
supply(BIG18, ~1e9 tokens)
supply(collateral)
borrow(BIG18, ~98% of supplied)
wait until interest raises the index sufficiently
update_indexes([hub_asset(BIG18)])
  -> pool.update_indexes
  -> Cache::load
  -> global_sync
  -> accrue_step
  -> scaled_to_original(borrowed, borrow_index)
  -> i128 overflow / MathOverflow
```

After the failed update, the stored index remains below `MAX_BORROW_INDEX_RAY`, while every subsequent market operation repeats the same overflowing conversion and aborts.

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
