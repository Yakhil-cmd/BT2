### Title
First-depositor share-price manipulation in the bundled Uniswap-like market-maker AA template - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` template bundled and documented in ocore's AA Template Examples lets the **first depositor unilaterally set the exchange rate** between the pooled `base`/`$asset` reserves and the newly-issued `$mm_asset` shares, with no validation of the deposited ratio and no minimum-liquidity floor. This mirrors exactly the Numoen "first liquidity provider" bug class: the invariant/ratio that must hold between deposited amounts and minted "liquidity" is enforced only for *subsequent* deposits, not for the initial one.

### Finding Description
In the "invest in MM" case of the template:

```
init: `{
    $asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
    $bytes_balance = balance[base] - trigger.output[[asset=base]];
    if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
        $issue_amount = balance[base];
        return;
    }
    $current_ratio = $asset_balance / $bytes_balance;
    $expected_asset_amount = round($current_ratio * trigger.output[[asset=base]]);
    if ($expected_asset_amount != trigger.output[[asset=$asset]])
        bounce('wrong ratio of amounts, expected ' || $expected_asset_amount || ' of asset');
    ...
}`
``` [1](#0-0) 

For every deposit after the first, the AA strictly checks that the deposited `base`/`$asset` ratio matches the pool's current reserve ratio, exactly analogous to how `Pair.invariant()` must hold in the Numoen contract. However, for the **initial deposit** (`$asset_balance == 0 OR $bytes_balance == 0`), no such check exists: `$issue_amount` is simply set to `balance[base]`, regardless of how much (or how little) of `$asset` was actually deposited alongside it. This is the direct analog of `LiquidityManager.addLiquidity()` letting the caller pick `amount0Min`/`amount1Min` for the first deposit without any on-chain relationship check against `liquidity`.

The subsequent "exchange" cases derive the AA's internal price purely from the ratio of `balance[$asset]` to `balance[base]`:
```
$p = $asset_balance * $bytes_balance;
$new_asset_balance = round($p / balance[base]);
``` [2](#0-1) 

Because the initial reserve ratio is entirely attacker-controlled (an attacker can be, or front-run, the first depositor by sending an arbitrarily skewed ratio of `base` to `$asset`, e.g. depositing the required `>1e5` bytes together with only 1 unit of `$asset`), the attacker can mint `$mm_asset` shares while establishing a wildly mispriced pool. All later depositors are then forced to match this manipulated ratio (via the `bounce('wrong ratio...')` check), or an attacker can immediately use the "exchange" cases to extract value from the skewed pool before honest liquidity arrives.

### Impact Explanation
This is a fund-loss vector for any AA that reuses or is derived from this documented template: the attacker who controls the first deposit can set an arbitrary implicit exchange rate between the AA's issued share asset and its underlying reserves, allowing them to mint disproportionate shares relative to real economic value contributed, and to extract value from subsequent investors who must conform to the now-manipulated ratio. This is a well-known "first depositor / share-price manipulation" class of vulnerability (same root cause acknowledged as Medium severity in the cited Numoen report) and results in concrete fund loss for later, honest depositors.

### Likelihood Explanation
Likelihood is high in practice: any observer watching the mempool/DAG for the AA-defining unit or the first genuine "invest" trigger can trivially front-run it with a minimal-cost transaction (bytes fee only) that sets an extreme ratio, since the initial-deposit branch performs no ratio validation and the required threshold (`trigger.output[[asset=base]] > 1e5`) is very low. No special privilege is needed — this is reachable by any ordinary AA trigger sender.

### Recommendation
- Require the first depositor to also supply/lock a minimum amount of both `base` and `$asset` reserves and validate a sane, documented ratio (or accept an oracle/initial-price parameter set at AA-definition time via `init`), analogous to Uniswap's permanent `MINIMUM_LIQUIDITY` burn.
- Alternatively, compute the initial `$issue_amount` as a function of both `$asset` and `base` deposited (e.g., geometric mean) rather than `balance[base]` alone, so no single asset dimension can be starved to manipulate the price.
- Document this risk prominently in the AA Template Examples so that AA authors copying this pattern are aware they must add their own first-deposit protection.

### Proof of Concept
1. AA is defined and `$mm_asset` created via the "define share asset" case. [3](#0-2) 
2. Attacker sends a trigger with `trigger.output[[asset=base]] = 100001` and `trigger.output[[asset=$asset]] = 1` (satisfies `> 1e5` and `> 0`).
3. Since `$asset_balance == 0`, the "initial deposit" branch fires: `$issue_amount = balance[base]` = 100001, and 100001 `$mm_asset` are minted to the attacker for depositing only 1 unit of `$asset`. [4](#0-3) 
4. The pool's `$asset:base` ratio is now 1:100001, wildly divorced from any real market price. All future "invest" deposits must match this ratio or bounce, and the "exchange" cases immediately price trades off this ratio, letting the attacker profit at the expense of subsequent participants. [5](#0-4)
