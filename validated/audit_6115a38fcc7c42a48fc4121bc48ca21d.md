### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but events are dispatched using the unrelated `repository.full_name` field — allowing a forged push/status webhook to be accepted for any organization that lacks a `webhook_secret` while still targeting a *different*, secret-protected repository's stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, attacker-supplied JSON body, and `GitHubApp#verify_webhook_signature` vacuously returns `true` when no `webhook_secret` is configured for that organization. The event handlers, however, resolve the actual `Stack`/`Repository` to act on using a completely different field from the same body: `repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb`). Nothing binds these two fields together. This breaks the intended trust equality "organization whose secret authenticated the request == repository that is written to", analogous to the reNFT finding where a field consumed by application logic (the tokens transferred) was never covered by the same validation path (the pausable-token precheck) that gated the action.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end

`Repository.from_github_repo_name` looks up strictly by the `owner/name` string embedded in `full_name`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

Because `repository_owner` (used to pick the secret/verification path) and `repository_name`/`full_name` (used to pick the stack that is actually acted on) are two independently attacker-controlled fields inside the same unauthenticated JSON body, there is no cryptographic binding forcing them to refer to the same repository. If any organization configured in `Shipit.github` has no `webhook_secret` set (an explicitly supported, documented configuration — `config/secrets.development.example.yml` shows `webhook_secret: # nil`), `verify_webhook_signature` returns `true` unconditionally for a payload whose `repository.owner.login` names that organization, regardless of the actual signature header or body content. The attacker can set `repository.full_name` in that same body to any other organization/repo that Shipit tracks, and the `push`, `status`, or `check_suite` handlers will act on that unrelated stack.

### Impact Explanation
This maps to "High: unauthenticated read of stack state / task streams" and can extend further: an unauthenticated request can trigger `GithubSyncJob` (via `PushHandler#process` → `stack.sync_github`) for an arbitrary tracked stack it doesn't own, or inject forged commit `status`/`check_suite` payloads (`status_master`, `check_suite_master` handlers) that influence merge-request CI gating (`MergeRequest#reject_unless_mergeable!`, `StatusChecker`), potentially allowing a merge request to appear to pass CI checks it never actually passed for a stack the attacker has no relationship with — i.e., an unauthorized/forged deploy-gate manipulation entirely from an unauthenticated network position, contingent on the deployment having at least one org configured without a webhook secret.

### Likelihood Explanation
Requires a specific, but explicitly documented and supported, misconfiguration: at least one organization entry in the Shipit multi-org `github` config with no `webhook_secret`. Given the sample config ships that field as optional/nil and the app never warns/refuses to operate without it, this is a realistic operational state, not a purely theoretical one. However, exploitation is fully gated on that admin choice and does not represent a code-only "unprivileged attacker" bypass unless such a no-secret org exists — this is the key open uncertainty I could not resolve further from static code alone (e.g., I could not confirm whether the shipped app enforces a mandatory webhook_secret elsewhere, such as in setup docs/health-checks, that would prevent this in practice).

### Recommendation
Bind the field used to select/verify the webhook secret to the same field used to resolve the target repository/stack — i.e., verify the signature using the organization derived from `repository.full_name` (the actual field consumed by handlers), and/or reject events for organizations without a configured `webhook_secret` rather than treating a missing secret as an automatic pass. At minimum, do not silently bypass verification (`return true unless webhook_secret`) — require an explicit "unauthenticated mode" opt-in per organization, and cross-check that `repository.owner.login` and the owner segment of `repository.full_name` are identical before dispatching handlers.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs: `orgA` (no `webhook_secret` set) and `victim-org` (has `webhook_secret` set, tracks a real stack).
2. Attacker (no credentials) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "orgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` needed.
4. `create` dispatches the body to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's real, secret-protected stack — entirely bypassing `victim-org`'s configured signature verification.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
