### Title
Webhook signature verification is bound to an attacker-controlled organization field, not to the repository the handler actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the request against using a field taken from the unauthenticated request body (`repository.owner.login` / `organization.login`), while the handlers that actually mutate state (`PushHandler`, `StatusHandler`, etc.) key their side effects off a *different* body field (`repository.full_name`) or, in the case of `StatusHandler`, off no repository field at all. The HMAC signature check therefore authenticates "some org configured in `Shipit.github`", not "the repository being written to", breaking the equality `organization authenticated == repository written`.

### Finding Description
The webhook signature is verified like this: [1](#0-0) 

`repository_owner` is read straight from the JSON body the caller supplies (`params.dig('repository','owner','login')` or `params.dig('organization','login')`): [2](#0-1) 

That value picks the `GitHubApp` instance/secret to verify with: [3](#0-2) 

Note `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that organization — a configuration explicitly supported and documented for multi-org setups where the `webhook_secret` key can be left empty per org: [4](#0-3) 

Once (a) an org with no configured secret is named in `repository.owner.login`/`organization.login`, or (b) an attacker otherwise knows any one configured org's secret, `verify_signature` passes for the whole request regardless of which repository the rest of the payload references.

The handlers never re-check that the verified organization matches the repository they act on:
- The generic `Handler` base class resolves the target repository from `payload.dig('repository','full_name')` — a field distinct from the one used for signature selection: [5](#0-4) 
- `StatusHandler` doesn't even filter by repository — it matches **every** `Commit` row across the whole Shipit instance whose `sha` equals the attacker-supplied `sha`: [6](#0-5) 

Because `Commit#sha` values for real Git commits are public information (visible on GitHub for the target repo), an attacker can name a victim's commit sha in the payload while satisfying signature verification via an org that has no `webhook_secret` configured (or one whose secret leaked), and write a forged commit status onto the victim stack's `Commit` record.

### Impact Explanation
This breaks the binding between "the organization that authenticated the webhook request" and "the repository/commit that the handler writes to", matching the report's bug class (an update/write path trusts an unverified linkage between what was authenticated and what gets mutated). Concretely:
- `StatusHandler` lets an attacker forge a CI status (e.g. `success`) on a `Commit` belonging to any stack in the Shipit instance, as long as they can reference an org whose `webhook_secret` is unset or otherwise known, and know/guess the victim commit's sha (trivial for public repositories). Forged passing statuses can satisfy `ci.require` checks that gate whether a commit is deployable, contributing to an **unauthorized deploy**.
- `PushHandler` and other handlers key off `repository.full_name`, a field never tied to the signature-selected org, so a request "authenticated" for org A can trigger sync/webhook side effects for a stack backed by org B's repository — a **cross-repository write** in the sense used by the ruling criteria.

### Likelihood Explanation
Exploitability requires either (1) at least one organization configured in `Shipit.github` with a blank `webhook_secret` (an explicitly documented, supported configuration for multi-org installs), or (2) knowledge of any one org's webhook secret. Given (1) is a normal, non-privileged operational state (not a compromise), an unprivileged internet attacker who can reach the public `/webhooks` endpoint can exploit this without any Shipit session, API token, or GitHub App credentials — satisfying the "unprivileged attacker" bar in scope. I was not able to fully trace `ci.require`/deploy-gating logic in `app/models/shipit/stack.rb` and `app/models/shipit/commit.rb` within the remaining budget to confirm the exact mechanics of how a forged status flips a stack to deployable; this should be verified directly in those files before treating the "unauthorized deploy" escalation as fully proven. The cross-repository `Commit`/`Status` write itself is confirmed directly from the code cited above.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the HMAC, re-derive the acting repository/org strictly from the same trusted field used for verification, and have every `Handler` subclass (especially `StatusHandler`) filter its target records (`Commit`, `Stack`, `Repository`) by that verified organization/repository — not by a second, independently attacker-controlled field of the same unauthenticated JSON body.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank; require a secret to be configured for every org in `Shipit.github`, or fail closed.
- Scope `StatusHandler#process` (and any other handler that queries by `sha` alone) to commits belonging to the repository named/verified in the payload, not to all commits in the database.

### Proof of Concept
1. Configure (or find already configured) a Shipit multi-org setup where org `low-priv-org` has an empty `webhook_secret` (per `docs/setup.md` example format), while org `victim-org` has commits tracked by Shipit.
2. As an unprivileged attacker, `POST /webhooks` with header `X-Github-Event: status`, and body:
```json
{
  "repository": { "owner": { "login": "low-priv-org" }, "full_name": "low-priv-org/anything" },
  "sha": "<known public sha of a commit in victim-org's tracked repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `repository_owner` = `low-priv-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is required.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, matches the victim's commit (in `victim-org`'s stack) purely by sha, and calls `create_status_from_github!`, writing a forged CI status onto a commit the attacker has no relation to.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
