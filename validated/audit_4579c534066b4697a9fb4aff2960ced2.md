### Title
Cross-repository PR data forgery via disjoint `repository.owner.login` (auth) and `repository.full_name` (mutation target) fields in `pull_request` webhooks - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/secret used to validate a webhook using `params.dig('repository','owner','login')`, while `AssignedHandler` (and sibling PR handlers) look up and mutate the target `Shipit::Repository`/`PullRequest` using the independent `params.repository.full_name` field from the same attacker-controlled JSON body. `GithubApp#verify_webhook_signature` additionally returns `true` unconditionally when the selected org has no `webhook_secret` configured. Combining these, an attacker can name a configured-but-secretless org in `repository.owner.login` (which trivially "verifies") while pointing `repository.full_name` at a completely different, victim-owned tracked repository, causing the handler to write attacker-controlled PR state onto the victim's stack.

### Finding Description
The broken invariant should be: *the organization whose secret verified the webhook == the organization that owns the repository the handler mutates*. In code these are two separate, independently attacker-controlled reads of the same JSON body:

- Verification org: `params.dig('repository', 'owner', 'login')` (fallback `organization.login`) in `repository_owner` [1](#0-0)  feeds `Shipit.github(organization: repository_owner)` and `verify_webhook_signature` [2](#0-1) .
- Mutation target: `params.repository.full_name`, used by `AssignedHandler#repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` [3](#0-2) , then joined to find and `update` the matching `PullRequest` record [4](#0-3) .

`AssignedHandler`'s `ExplicitParameters` schema only `requires :repository { requires :full_name }` — it never requires or cross-checks `repository.owner.login` [5](#0-4) , so nothing forces `full_name`'s owner segment to match the `owner.login` used for signature selection.

Root cause in `verify_webhook_signature`: if the selected org has no configured secret, verification is a no-op that always passes, regardless of any signature header content: [6](#0-5) 

Exploit request: attacker POSTs to `/webhooks` with `X-Github-Event: pull_request`, any `X-Hub-Signature` value (or even a malformed one, since it's never checked when `webhook_secret` is blank), and body:
```json
{
  "action": "assigned",
  "number": <victim PR number>,
  "pull_request": { "...": "attacker-controlled fields" },
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-configured-org-with-no-secret" }
  },
  "sender": { "login": "attacker" }
}
```
`verify_signature` resolves `Shipit.github(organization: "attacker-configured-org-with-no-secret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally. The request proceeds to `Webhooks.for_event('pull_request')`, and `AssignedHandler` resolves the real, victim-owned repository via `full_name` and updates the victim's tracked `PullRequest.github_pull_request` with attacker-supplied data (title, head sha/ref, assignees, labels, additions/deletions) — all without ever presenting a valid signature for the victim org.

None of the existing guards stop this: `drop_unhandled_event` only checks the event name exists a handler for it [7](#0-6) ; `verify_signature` checks a different field than the one the handler trusts for the write target; the `ExplicitParameters` schema validates types/presence but not cross-field consistency; `Repository` model validations only constrain format/uniqueness of `owner`/`name`, not consistency with the webhook's asserted `owner.login` [8](#0-7) .

### Impact Explanation
An attacker with no Shipit credentials can write attacker-chosen `PullRequest` state (title, head SHA/ref, assignees, labels, diff stats) onto a real, unrelated victim repository's review stack, as long as at least one org configured in Shipit lacks a `webhook_secret` (explicitly documented as "optional" in `docs/setup.md`). This is a cross-tenant/cross-repository state manipulation — the exact "payload for one repository mutating another's stack" Critical category. The same disjoint-field pattern (`repository.owner.login` for auth vs `params.repository.full_name` for mutation) recurs in the other PR handlers (`OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`), so the blast radius extends to opening/archiving/unarchiving review stacks on arbitrary tracked repositories, not just `assigned`.

### Likelihood Explanation
Preconditions: Shipit must have at least one org configured without a `webhook_secret` (an officially supported, "optional" configuration per `docs/setup.md`), and the victim repository must be tracked by Shipit with an open PR/stack matching the forged `number`. No Shipit session, API token, or GitHub secret is required — only knowledge of a valid no-secret org's login name (often discoverable or guessable in multi-tenant deployments) and the victim's public repo full name/PR number. The request is trivially repeatable against any number of tracked repositories.

### Recommendation
Require that the org used for authentication is the same org that owns the mutated repository: derive `repository_owner` and pass it into every handler's context, and have `AssignedHandler`/`OpenedHandler`/`LabeledHandler`/`UnlabeledHandler`/`LabelCapturingHandler` verify `params.repository.full_name.split('/').first == verified_repository_owner` before acting (or better, look up the `Repository` strictly by the verified owner + repo name pair, not solely by attacker-supplied `full_name`). Additionally, do not allow `verify_webhook_signature` to silently pass when `webhook_secret` is blank for orgs that receive mutating webhook events — require a configured secret for any org with tracked review-stack repositories, or reject `pull_request` events for secretless orgs.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "pull_request assigned from a no-secret org can mutate a victim repo's PullRequest" do
  # Precondition: Shipit config has org "no-secret-org" with no webhook_secret,
  # and a tracked "victim-org/victim-repo" repository/stack/PR exists.
  pull_request = shipit_pull_requests(:review_stack_review)
  pull_request.assignees.clear
  victim_repo_full_name = pull_request.stack.repository.github_repo_name

  payload = payload_parsed(:pull_request_assigned)
  payload["number"] = pull_request.number
  payload["pull_request"]["number"] = pull_request.number
  payload["repository"]["full_name"] = victim_repo_full_name
  payload["repository"]["owner"]["login"] = "no-secret-org" # attacker-chosen, secretless org

  @request.headers['X-Github-Event'] = 'pull_request'
  @request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # bogus, never actually checked

  post :create, body: payload.to_json, as: :json

  assert_response :ok
  # Binding under test: verified_org ("no-secret-org") != repository_owner_of_mutated_record ("victim-org")
  assert_not_equal "no-secret-org", pull_request.stack.repository.owner
  assert_equal [shipit_users(:codertocat)], pull_request.reload.assignees # victim's PR mutated by attacker payload
end
```
This demonstrates the divergence: the org that "verified" (`no-secret-org`) is not the org that owns the mutated record (`victim-org`), and the mutation succeeds anyway.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
