### Title
Cross-organization webhook forgery: signing-org selected from the same unverified payload field the handlers later trust to pick the target repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App (and thus which `webhook_secret`) to verify the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the **unverified** JSON body. All webhook handlers then trust a **different** field of that same unverified body — `repository.full_name` — to decide which `Stack`/`Repository` to act on. Nothing binds the two together, so in a multi-organization Shipit deployment an attacker who legitimately controls one configured organization can forge a signed payload that verifies as "from OrgA" but whose `repository.full_name` points at OrgB's repository, causing Shipit to perform writes against a repository/organization the signature never actually authenticated.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`repository_owner` is read from the raw, not-yet-verified JSON body and used to select which configured GitHub App's `webhook_secret` is used to compute the expected HMAC (`GitHubApp#verify_webhook_signature` in `lib/shipit/github_app.rb`). Shipit explicitly supports multiple GitHub Apps keyed by organization (see `test/dummy/config/secrets_double_github_app.yml`, `Shipit.github(organization:)`), each with its own `webhook_secret`.

Once the signature check passes, `create` dispatches the same untrusted body to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [2](#0-1) 

Every handler resolves its target `Repository`/`Stack` from a **different** field of the body, `repository.full_name`, e.g. the base `Handler` class:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

and the pull-request handlers similarly:
```ruby
def repository
  @repository ||=
    Shipit::Repository.from_github_repo_name(params.repository.full_name) ||
    Shipit::NullRepository.new
end
``` [4](#0-3) 

**Broken binding:** `organization authenticated (via webhook_secret keyed by repository.owner.login)` ≠ `repository actually written (repository.full_name)`. Both fields live in the same attacker-supplied JSON body; the signature only proves "this body was produced with knowledge of OrgA's secret," it proves nothing about consistency between `repository.owner.login` and `repository.full_name` inside that body.

### Impact Explanation
An attacker who legitimately owns/administers a repository under an organization configured in Shipit (OrgA) — and therefore knows or can trigger genuine deliveries carrying OrgA's `webhook_secret`-derived HMAC — can craft a raw JSON body where:
- `repository.owner.login` / `organization.login` = `"OrgA"` (so `Shipit.github(organization: "OrgA")` selects OrgA's secret for verification), and
- `repository.full_name` = `"OrgB/some-private-or-restricted-repo"` (a repository under a different, unrelated organization also configured in this Shipit instance).

Because the attacker controls OrgA's secret, they can compute a valid `X-Hub-Signature` over this crafted body themselves. `verify_signature` passes. `create` then hands the body to the registered handlers for the given `X-Github-Event`, which resolve the target `Stack`/`Repository` using `repository.full_name` = OrgB's repo, e.g.:
- `PushHandler` enqueuing `GithubSyncJob` against OrgB's stack,
- PR handlers creating/archiving/unarchiving review stacks (spawning deploy/provisioning tasks) for OrgB,
- `StatusHandler` writing commit statuses on OrgB commits,
- `MembershipHandler` creating/removing team memberships.

This is a cross-organization/cross-repository write triggered purely by a forged (but "validly signed under a different, unrelated secret") webhook — matching the rules' Critical-impact category "cross-repository writes."

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub App/organization (an explicitly supported and documented configuration — see `docs/setup.md` and `secrets_double_github_app.yml`), and (2) an attacker who is a legitimate webhook source for at least one of those organizations (e.g., controls a repo under OrgA, or otherwise can produce a body whose HMAC they can compute with OrgA's secret). Single-organization deployments (the common case) are not exploitable this way because there is only one secret. This narrows applicability but is a real, unprivileged-relative-to-OrgB attack path that requires no session, API token, or GitHub App private key access to the *target* organization.

### Recommendation
Bind the verified secret to the field actually used downstream: derive `repository_owner` for secret selection from the same value used by handlers to select the repository (`repository.full_name`'s owner segment), or better, after verifying the signature with a given org's secret, reject the payload unless every organization-identifying field in the body (`repository.owner.login`, `organization.login`, and the owner segment of `repository.full_name`) is consistent with the org whose secret validated the signature.

### Proof of Concept
Given Shipit configured with two orgs, `OrgA` (secret `SA`) and `OrgB` (secret `SB`), where the attacker only knows `SA`:
1. Attacker builds `raw_post` JSON: `{"action":"opened","number":1,"pull_request":{...},"repository":{"owner":{"login":"OrgA"},"full_name":"OrgB/private-repo"},"sender":{"login":"attacker"}}`.
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SA, raw_post)>` and sends `POST /github/webhooks` with `X-Github-Event: pull_request`.
3. `verify_signature` calls `Shipit.github(organization: "OrgA")` → uses `SA` → `verify_webhook_signature` succeeds.
4. `create` parses the body and calls `Handlers::PullRequest::OpenedHandler.call(params)`, which resolves `Shipit::Repository.from_github_repo_name("OrgB/private-repo")` and creates/updates a review stack for OrgB — despite the request only ever being authenticated against OrgA's secret.
