### Title
Unbounded download of gist raw file content leads to memory/disk exhaustion - (File: pkg/cmd/gist/shared/shared.go)

### Summary
`gh gist view` fetches truncated gist file content via `GetRawGistFile`, which performs `io.ReadAll(resp.Body)` with no size cap, content-length check, or streaming limit. An attacker who publishes a gist with a very large (or endlessly streaming) file can cause the victim's `gh` process to consume unbounded memory when they run `gh gist view` against that gist.

### Finding Description
In `pkg/cmd/gist/view/view.go`, `viewRun`'s `render` closure calls `shared.GetRawGistFile(client, safeurl.NewImmutableSafeURL(gf.RawURL))` whenever the GitHub API marks a gist file as `Truncated` [1](#0-0) . The `RawURL` and `Truncated` flag both come directly from the attacker-controlled gist API response (`GistFile.RawURL`, `GistFile.Truncated`) [2](#0-1) .

`GetRawGistFile` performs the HTTP GET and then reads the entire response body into memory with a plain `io.ReadAll(resp.Body)`, with no `io.LimitReader`, no `Content-Length` pre-check, and no timeout/size guard: [3](#0-2) . The only safety mechanism applied to the URL is `safeurl.NewImmutableSafeURL`, which addresses SSRF-style host validation, not response size. Because a gist owner fully controls the content of their own gist files (which GitHub's raw content endpoint will happily serve as any size the owner uploaded, and could even be a slow/endless stream if the attacker controls the serving infrastructure indirectly via a redirect not caught by safeurl, or simply a very large legitimate raw file), this read has no upper bound.

The subsequent binary-detection, markdown render, and raw output paths all operate on the fully-buffered `[]byte`, meaning the entire object must already reside in memory before any of the size-related checks (like `IsBinaryContents`) run.

### Impact Explanation
An attacker (any GitHub user, since gists are publicly creatable) can upload a gist containing an extremely large file. When the victim runs `gh gist view <id>` on that gist (a completely ordinary, expected use of the CLI), the `gh` process will attempt to buffer the entire file into memory via `io.ReadAll`, with no bound. This can exhaust the victim's memory, causing the process (or worse, if swap is enabled, the box) to become unresponsive — a High severity unbounded resource consumption issue, matching the requested Immunefi impact class ("Unbounded resource consumption on the victim's machine from a single attacker-published object").

### Likelihood Explanation
Feasible and repeatable: no privileges beyond a free GitHub account are required to create a public gist with an oversized file. The victim only needs to be induced to run `gh gist view` against the gist ID/URL (e.g., shared via a link, similar to any other social gist-sharing scenario). The `Truncated` flag is set automatically by GitHub when a gist file exceeds the inline content size threshold, so any sufficiently large attacker file naturally triggers this code path.

### Recommendation
Bound the download in `GetRawGistFile`: wrap `resp.Body` in `io.LimitReader` with a sane maximum (e.g., a few MB, consistent with GitHub's gist file size limits), check `resp.ContentLength` before reading when available, and return a clear "file too large" error when the limit is exceeded instead of silently truncating or buffering unbounded data. Consider also enforcing a read timeout via context to guard against slow/endless streaming responses.

### Proof of Concept
```go
func TestGetRawGistFile_UnboundedRead(t *testing.T) {
    // httptest server that streams an endless/huge body
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
        buf := make([]byte, 1<<20) // 1MB chunk
        for {
            if _, err := w.Write(buf); err != nil {
                return
            }
            w.(http.Flusher).Flush()
        }
    }))
    defer srv.Close()

    u, _ := safeurl.NewImmutableSafeURL(srv.URL)
    _, err := shared.GetRawGistFile(http.DefaultClient, u)

    // Expected (after fix): a bounded "file too large" error is returned
    // Actual (current behavior): call never returns / OOMs, demonstrating
    // the unbounded io.ReadAll in GetRawGistFile.
    require.Error(t, err)
}
```
This test demonstrates that `shared.GetRawGistFile` (reached via `NewCmdView` → `viewRun` → `render`) has no bound on response size, confirming the finding.

func GetRawGistFile(httpClient *http.Client, rawURL safeurl.SafeURL) (iostreams.Untrusted, error) {
	req, err := http.NewRequest("GET", rawURL.String(), nil)
	if err != nil {
		return iostreams.Untrusted{}, err
	}

	resp, err := httpClient.Do(req)
	if err != nil {
		return iostreams.Untrusted{}, err
	}

	defer resp.Body.Close()

	if resp.StatusCode != http.StatusOK {
		return iostreams.Untrusted{}, api.HandleHTTPError(resp)
	}

	body, err := io.ReadAll(resp.Body)

	if err != nil {
		return iostreams.Untrusted{}, err
	}

	return iostreams.NewUntrustedBytes(body), nil
