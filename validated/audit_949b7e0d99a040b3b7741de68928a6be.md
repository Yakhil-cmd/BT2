### Title

Scaled-value overflow in interest accrual permanently freezes an oversized market - (File: common/src/rates/index.rs)

### Summary

The pool can reach a state in which `scaled_balance * index / RAY` no longer fits in `i128`. Interest accrual panics before the index ceiling protects the market, causing repayment, withdrawal, liquidation, and index maintenance to fail permanently absent a privileged contract upgrade. [1](#0-0) [2](#0-1) 

### Finding Description

Every existing-market operation first loads the market and calls `interest::global_sync`, so a failure during accrual prevents the underlying operation from running. [2](#0-1) 

`global_sync` calls `accrue_step`, which computes old and new total debt by multiplying scaled debt by the borrow index. [3](#0-2) [4](#0-3) 

The supply-side calculation similarly computes `supplied * supply_index` before applying the configured supply-index ceiling. [5](#0-4) 

`Ray::mul` produces an `i128` fixed-point result and panics when that result exceeds the representable range. [6](#0-5) 

The configured `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` caps are applied to the index, but they do not prevent the scaled-balance-times-index result from overflowing first. [7](#0-6) [8](#0-7) 

Once this condition is crossed, `update_indexes`, `repay`, `withdraw`, and liquidation paths that accrue the market all revert before any recovery action can reduce the scaled balances. [9](#0-8) [10](#0-9) [11](#0-10) 

### Impact Explanation

This permanently freezes supplier principal and prevents borrowers from repaying, while liquidators cannot execute a liquidation that requires the pool to synchronize the affected market. [2](#0-1) 

The harness demonstrates the exact failure: after the scaled value crosses the `i128` ceiling, index updates fail below the configured index cap, and both withdrawal and repayment fail with `MathOverflow`. [12](#0-11) 

Because every state-reducing path performs accrual first, the failed accrual cannot be bypassed through ordinary user operations. [13](#0-12) 

### Likelihood Explanation

A single attacker can establish the prerequisite state by supplying the target asset, supplying collateral, and borrowing a large fraction of the target market through the ordinary `supply` and `borrow` entrypoints. [14](#0-13) 

The attacker can then use the permissionless `update_indexes` entrypoint to advance accrual until `borrowed * borrow_index` or `supplied * supply_index` exceeds `i128`. [11](#0-10) [15](#0-14) 

The required market size is very large and depends on configured caps, token decimals, available collateral, and sustained utilization, so this is a Medium-severity availability failure rather than an easily triggered theft. [16](#0-15) 

### Recommendation

Bound index growth by the market’s scaled-balance headroom, not only by the fixed `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` constants. [7](#0-6) [5](#0-4) 

Pass the relevant scaled balance into index accrual, calculate the largest index for which the resulting RAY value still fits `i128`, and clamp the new index before deriving supplier rewards or total debt. [1](#0-0) 

Alternatively, reduce the index ceilings or enforce stricter market caps so every admitted scaled balance remains representable at the maximum reachable index. [16](#0-15) 

Add monitoring or a recovery path for markets approaching the representable-value ceiling, since ordinary repayment and withdrawal cannot recover once the boundary has been crossed. [2](#0-1) 

### Proof of Concept

1. Create or select an 18-decimal market whose caps admit a very large balance.
2. The attacker supplies `D` units of that asset.
3. The attacker supplies sufficient collateral and calls `borrow(account_id, [(hub_asset, debt)], to)` with debt near the market’s available balance.
4. The attacker calls `update_indexes(caller, [hub_asset])`; the pool loads the market and synchronizes interest before returning.
5. When accrual makes `borrowed * borrow_index / RAY` or `supplied * supply_index / RAY` exceed `i128::MAX`, `Ray::mul` panics inside `accrue_step`.
6. Subsequent `withdraw`, `repay`, `liquidate`, and `update_indexes` transactions fail before they can reduce the oversized scaled balances. [17](#0-16) [3](#0-2) [2](#0-1) 

The repository’s scenario test uses a billion-unit 18-decimal market at 98% utilization, observes `MathOverflow` before `MAX_BORROW_INDEX_RAY`, and confirms that both withdrawal and repayment remain blocked. [18](#0-17)

```rust
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
```

```rust
pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```markdown
| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
