### Title
Integer overflow in `ThrowOnInvalidLength` size checks lets a crafted negative `count` bypass validation while `(UInt64)count` sign-extends to a massive value passed to native code - ([File: bindings/csharp/Ckzg.Bindings/Ckzg.cs])

### Summary
`VerifyBlobKzgProofBatch(blobs, commitments, proofs, count, ckzgSetup)` validates buffer sizes using unchecked `int` multiplication (`BytesPerBlob * count`, `BytesPerCommitment * count`), which silently wraps modulo 2^32. A specific negative `count` exists for which these wrapped products exactly equal realistic, small buffer sizes (one blob/commitment/proof), so all three `ThrowOnInvalidLength` checks pass, yet `(UInt64)count` at the P/Invoke call sign-extends the negative `int` into an astronomically large `UInt64` forwarded to the native `verify_blob_kzg_proof_batch`.

### Finding Description
The broken equality is:
`count` validated by `ThrowOnInvalidLength(blobs/commitments/proofs, ..., BytesPerX * count)` **==** `count` forwarded as `(UInt64)count` to native code.

Tracing the arithmetic: `BytesPerBlob = 131072 = 2^17` and `BytesPerCommitment = BytesPerProof = 48 = 2^4·3`. In C#, integer arithmetic is unchecked by default, so `BytesPerBlob * count` and `48 * count` are computed modulo 2^32 [1](#0-0) , and the equality test itself is a plain `int` comparison [2](#0-1) .

Using modular decomposition (multiplying by 2^k mod 2^32 depends only on the low `32-k` bits of the multiplicand), it is possible to solve for a `count` where both wrapped products land on realistic, legitimately-allocatable buffer sizes. Concretely, `count = -2147483647` (i.e. `int.MinValue + 1`) satisfies:
- `BytesPerBlob * count` (mod 2^32, reinterpreted as `int`) = `131072` — exactly one legitimate blob buffer.
- `BytesPerCommitment * count` and `BytesPerProof * count` (mod 2^32) = `48` each — exactly one legitimate commitment/proof buffer.

With `blobs.Length == 131072`, `commitments.Length == 48`, `proofs.Length == 48`, all three `ThrowOnInvalidLength` calls pass without throwing, even though `count` is deeply negative. Execution then reaches:
`VerifyBlobKzgProofBatch(out var result, blobsPtr, commitmentsPtr, proofsPtr, (UInt64)count, ckzgSetup)` [3](#0-2) .

Casting the negative `int count = -2147483647` to `UInt64` sign-extends it to `0xFFFFFFFF80000001` (~1.8×10^19), which is passed as `n` to the native `verify_blob_kzg_proof_batch` via the P/Invoke declaration expecting `UInt64 count` [4](#0-3) . The native function has no way to know the real buffer sizes are 1 element each; it will index/iterate over `n` elements far beyond the actual 131072/48/48-byte allocations, producing an out-of-bounds read/crash.

None of the existing guards prevent this: `ThrowOnUninitializedTrustedSetup` only checks the setup pointer [5](#0-4) ; `ThrowOnInvalidLength` performs no range/sign check on `count` itself, only compares against the (already-overflowed) expected length [2](#0-1) ; there is no `count >= 0` assertion anywhere in this function.

### Impact Explanation
Once reached, the native call receives `n ≈ 1.8×10^19` while only 1 blob/commitment/proof worth of memory was actually allocated and pinned via `fixed`. The native code will read far past the pinned buffers, causing an out-of-bounds read and crash (access violation / segfault) on any node process using this C# binding (e.g. Nethermind) that passes such a `count` through to `VerifyBlobKzgProofBatch`. This matches "High" severity: a crash/OOB read reachable through the binding.

### Likelihood Explanation
This requires the caller to pass the specific crafted negative `count = -2147483647` value into the public `VerifyBlobKzgProofBatch` API alongside a correctly-sized single blob/commitment/proof triple. It does not require malformed blob/commitment/proof *content* — the flaw is purely in how the `count` integer is validated and then reinterpreted for the native call. Under the audit's attacker model (attacker controls "item counts"), this is directly reachable and deterministically reproducible each time with the exact same `count` value; it is not dependent on external randomness. In a real client deployment, `count` is normally derived internally from the number of blobs the node itself collected, so exploitation depends on how far attacker-supplied data can influence that integer before this API boundary — but as posed by the audit's own attacker model (counts are attacker-controlled), the bypass condition is real and fully demonstrable in the binding.

### Recommendation
Validate `count` (and other size-derived parameters) as non-negative and perform the multiplication in a widened, checked context (e.g., `checked` arithmetic or `long`/`UInt64` multiplication) before comparing to `data.Length`, e.g.:
```csharp
if (count < 0) throw new ArgumentException(...);
long expected = (long)BytesPerBlob * count;
if (blobs.Length != expected) throw ...
```
Apply the same fix to `numCells`-based checks (`ComputeCells`, `RecoverCellsAndKzgProofs`, `VerifyCellKzgProofBatch`), which have the identical unchecked-multiplication pattern.

### Proof of Concept
```csharp
[Fact]
public void VerifyBlobKzgProofBatch_NegativeCountBypassesLengthCheck()
{
    int count = -2147483647; // int.MinValue + 1

    // Sanity check the broken equality claimed by the bug:
    int expectedBlobLen = Ckzg.BytesPerBlob * count;       // wraps to 131072
    int expectedCommLen = Ckzg.BytesPerCommitment * count; // wraps to 48
    Assert.Equal(131072, expectedBlobLen);
    Assert.Equal(48, expectedCommLen);

    var blobs = new byte[131072];        // exactly one blob
    var commitments = new byte[48];      // exactly one commitment
    var proofs = new byte[48];           // exactly one proof

    // ThrowOnInvalidLength passes (no ArgumentException) despite count < 0.
    // (UInt64)count is sign-extended to ~1.8e19 and forwarded to native code,
    // causing an out-of-bounds read / crash instead of a graceful ArgumentException.
    Assert.Throws<AccessViolationException>(() =>
        Ckzg.Ckzg.VerifyBlobKzgProofBatch(blobs, commitments, proofs, count, ckzgSetup));
}
```
This demonstrates that the validated equality (`ThrowOnInvalidLength` passing) diverges from the value actually sent to native code (`(UInt64)count`), confirming BOUNDS_TRUTH is violated.
