### Title
Cross-repository status forgery via unscoped SHA lookup enables blocking/unblocking of a victim stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes a GitHub `status` webhook to every `Commit` row that shares the reported `sha`, with no filter on the repository/stack that authenticated the webhook. Because git commit SHAs are content-addressed, an attacker who owns a fork of a victim's public repository can trigger a genuinely-signed webhook from their own fork whose `sha` matches a commit that also exists in the victim's tracked stack, and the resulting `Status` row is created against the victim's commit and stack, changing `blocking?`/`required?` evaluation used to compute `blocked?`.

### Finding Description
The broken binding: the code implicitly assumes `status.stack_id == authenticated_repository.stack_id`, but the handler never enforces `Commit#stack_id == webhook_repository.stack_id`.

Trace:
1. `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) dispatches the raw JSON payload to `Shipit::Webhooks.for_event('status')`, i.e. `Handlers::StatusHandler`.
2. `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks that the HMAC signature matches the secret configured for `repository_owner` (`params.dig('repository','owner','login')`) — i.e., it authenticates *which organization/app installation* sent the payload, but does nothing to scope which `Commit`/`Stack` rows may be touched.
3. `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` by bare `sha` across the entire `commits` table — across every repository/stack ever tracked by this Shipit instance — with no `repository`/`stack_id` predicate.
4. `commit.create_status_from_github!` → `Status.replicate_from_github!` (app/models/shipit/status.rb) creates a `Status` scoped to `commit.stack_id`, and `Status::Common#blocking?` (app/models/shipit/status/common.rb:46-48) checks `commit.blocking_statuses.include?(context)`, which feeds `UndeployedCommit#blocked?` (app/models/shipit/undeployed_commit.rb:55-59) used by `deploy_state`.

Exploit: An attacker forks a victim's public GitHub repository (a normal, unprivileged GitHub action). Fork commits that are unmodified from upstream retain identical git SHAs to the corresponding commits in the upstream (victim) repository, because git object hashes are content-addressed and independent of the remote/repo they live in. The attacker's own fork has (or the attacker installs/enables) the Shipit-integrated GitHub App/webhook for their own org, so GitHub emits a legitimately-signed `status` webhook for the attacker's own repository/organization with `context: ci/circleci`, an attacker-chosen `state` (`success`/`failure`), and `sha` equal to the shared commit. `verify_signature` passes because it is validated against the attacker's own organization's secret — the attacker never needed the victim's secrets. `StatusHandler#process` then matches `Commit.where(sha: ...)` against *all* commits with that SHA, including the row belonging to the victim's stack, and creates a `Status` there. If the victim stack has `blocking_statuses` configured to include `ci/circleci`, this status write flips `blocked?` for that commit — either unblocking a deploy that should have been blocked, or blocking a deploy that should have proceeded — entirely from a payload the victim repository never authenticated.

Existing guards do not catch this: `verify_signature` authenticates the org/app that sent the request but is organization-scoped, not stack/commit scoped; `ExplicitParameters` (`params do ... end` in `status_handler.rb`) only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `stacks`/`repository` scope applied in `StatusHandler#process`'s `Commit.where`.

### Impact Explanation
A payload authenticated for one repository/organization mutates `Status`/`Commit` state belonging to a completely different repository's stack, satisfying the "payload for one repository mutating another's stack/commit" Critical category. Because `blocking_statuses` gates `blocked?` (via `Status::Common#blocking?` and `UndeployedCommit#blocked?`), this can force a stack to appear unblocked (enabling an unauthorized deploy) or force it blocked (denial of legitimate deploys) without any interaction with the victim repository's real CI or Shipit configuration. This is repeatable against any stack whose tracked commits share SHAs with a repository the attacker controls (any public repo the attacker can fork), and the blast radius spans all tenants/stacks on the same Shipit instance that happen to track overlapping commit history (e.g., shared upstream/fork relationships, monorepo splits, or vendored/cherry-picked commits).

### Likelihood Explanation
Preconditions: the victim stack must have `blocking_statuses` configured for a context the attacker can control (e.g., `ci/circleci`), and the victim's tracked commit SHA must exist verbatim in a repository the attacker owns/controls (trivial via forking any public repo tracked by Shipit, or via any content-identical commit). Attacker cost is very low — no Shipit credentials, GitHub App keys, org membership, or Shipit session are required; only the ability to fork a public repo and trigger (or fake, via any CI integration) a status event on it. This is fully repeatable, and works against any victim repository that is public (forkable) and tracked by the same Shipit instance.

### Recommendation
Scope `StatusHandler#process` (and generally any handler that looks up `Commit` by bare `sha`) to the repository that authenticated the webhook, e.g. restrict the `Commit.where(sha: params.sha)` lookup to commits whose `stack.repository` matches the `repository`/`organization` from the verified payload (join through `Stack` and filter by `github_repo_name`/`repo_owner`+`repo_name`), so a status can only ever be applied to commits belonging to the stack(s) tracking the exact repository that signed the webhook.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (new or extended)
test "status for shared SHA does not affect a different repository's stack" do
  victim_stack = shipit_stacks(:shipit) # repo e.g. "shopify/shipit-engine"
  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:other_repo)) # different repo, e.g. "attacker/fork"

  shared_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  victim_stack.update!(deploy_spec: ... blocking_statuses: ['ci/circleci'] ...)

  # Binding under test:
  # victim_commit.blocking?('ci/circleci') BEFORE == victim_commit.blocking?('ci/circleci') AFTER
  # a status "authenticated" only for attacker_stack's repository must not create a Status on victim_commit

  params = ActionController::Parameters.new(
    sha: shared_sha, state: 'success', context: 'ci/circleci'
  )
  # Simulate webhook authenticated for the attacker's repo only
  Shipit::Webhooks::Handlers::StatusHandler.new.process(params) # or via controller w/ repository = attacker/fork

  assert_equal 0, victim_commit.reload.statuses.where(context: 'ci/circleci').count,
    "status for attacker's repo must not write to victim's commit/stack"
  assert_equal 1, attacker_commit.reload.statuses.where(context: 'ci/circleci').count
end
```
Currently, `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` (app/models/shipit/webhooks/handlers/status_handler.rb:21-23) has no repository filter, so this assertion fails: both `victim_commit` and `attacker_commit` receive the `Status`, demonstrating the cross-repository write and the resulting change to `blocked?`/deploy gating on the victim stack.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end
