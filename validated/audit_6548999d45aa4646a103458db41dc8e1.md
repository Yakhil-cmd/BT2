The proposed exploit requires an attacker to submit "crafted bytecode invoking the native with non-standard arity ... via a malformed module bypassing the Move verifier." That precondition is not itself an unprivileged-transaction admission path — it presupposes a pre-existing, separate bug in the Move bytecode verifier that would let malformed arity bytecode load and execute in the first place. Native functions like `native_write_to_event_store` in [1](#0-0)  are only ever reached through `MicroOp::CallNative`/`ExitCode::Call` dispatch after the function has been loaded and verified, and Aptos's execution model explicitly runs the bytecode verifier on scripts prior to execution and guarantees loaded module code is already verified before it reaches native dispatch: [2](#0-1) . The verifier enforces that call sites match the declared native signature's arity and types, so a normal (verifier-compliant) bytecode module cannot construct a call with 2 or 4 arguments to a native declared to take 3.

Because the described attack requires "a malformed module bypassing the Move verifier," it depends on a different, unproven vulnerability (a verifier bypass) rather than being reachable from unprivileged REST/BCS transaction submission through the normal admission stack (mempool → vm-validator → VM). Per the boundary conditions, this is out of scope: it needs a pre-existing broken invariant elsewhere (an already-compromised verifier) rather than a direct unprivileged admission-path defect, and it doesn't demonstrate any sender/signer/fee-payer/replay/domain confusion reachable via legitimate transaction input.
