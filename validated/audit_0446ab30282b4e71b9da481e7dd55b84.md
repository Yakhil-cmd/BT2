### Title
Cross-tenant webhook forgery via mismatched repository-owner (signature) and repository.full_name (data write) bindings - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`), while every webhook `Handler` resolves which `Stack`/`Repository` to mutate using a *different* field from the very same payload: `payload.dig('repository', 'full_name')` [1](#0-0) . These two values are never cross-checked against each other, so in Shipit's multi-tenant configuration (`Shipit.github_app_config(organization)` in `lib/shipit.rb`, which stores a distinct `webhook_secret`/App per organization) an attacker who legitimately controls one tenant organization can forge events that are authenticated as "their" organization but written against a completely different organization's repository/stack.

### Finding Description
`Shipit.github(organization:)` looks up a per-organization GitHub App config (`github_app_config`) containing an independent `webhook_secret` for each configured organization [2](#0-1) . `WebhooksController#verify_signature` picks that organization purely from `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [3](#0-2) , and only checks that the raw body's HMAC matches that organization's `webhook_secret` [4](#0-3) .

Once the signature is accepted, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handlers on the raw, attacker-supplied JSON [5](#0-4) . Every handler resolves its target `Stack`/`Repository` using `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` [6](#0-5) .

Nothing enforces `repository.full_name.split('/').first == repository.owner.login`. Because a legitimate GitHub webhook payload always keeps these consistent, this discrepancy is unreachable normally — but an attacker does not need GitHub to deliver the request. Anyone can `POST` directly to the Shipit `/github/webhooks` endpoint with an arbitrary JSON body and a signature computed with a secret *they* know. If the attacker is a legitimate tenant of this multi-org Shipit instance (i.e., they own/administer their own `attacker-org` GitHub App installation and know its `webhook_secret`), they can craft a payload where:
- `repository.owner.login = "attacker-org"` (so `verify_signature` selects and successfully validates against the attacker's own known secret), and
- `repository.full_name = "victim-org/victim-repo"` (an unrelated repository/stack belonging to a different tenant on the same Shipit instance).

The equality broken is: **organization authenticated (`attacker-org`, whose secret validated the HMAC) ≠ repository written (`victim-org/victim-repo`, whose `Stack` is mutated by the handler)**.

### Impact Explanation
Depending on which handler is targeted, this enables cross-tenant state forgery on repositories the attacker does not control:
- `status_handler.rb` / `check_suite_handler.rb`: forge CI status/check results for a victim commit, which `DeploySpec#required_statuses`/`hidden_statuses` and merge-request gating logic rely on — this can make Shipit believe an unreviewed/failing commit is CI-green, feeding into "unauthorized deploy" conditions.
- `push_handler.rb`: forge a push event enqueuing a `GithubSyncJob` for the victim stack, causing Shipit to sync from a spoofed `after` SHA.
- `pull_request/*` handlers (`OpenedHandler`, `LabelCapturingHandler`, etc.): create/label/close review stacks belonging to a victim repository they don't administer.

This crosses the "cross-repository writes" / "escalation into stack state" boundary called out as in-scope High/Critical impact, since it is a genuine cross-tenant authentication/data binding break, not merely a DoS or best-practice issue.

### Likelihood Explanation
Requires the attacker to be a legitimate tenant on a Shipit instance configured with **multiple** GitHub organizations (each with its own `webhook_secret` via `github_app_config`) — i.e., they must know their own org's webhook secret, which is normal and available to any org admin who installed a GitHub App/webhook against this Shipit deployment. No GitHub-side spoofing is needed; the attacker sends the crafted, self-signed request directly to Shipit's public webhook endpoint. Single-tenant (single global `secrets.github`) deployments are not affected because there is only one secret to verify against regardless of which org name is claimed, so this affects only multi-organization installations.

### Recommendation
In `WebhooksController#verify_signature`, or in `Handler#repository_name`, validate that `payload.dig('repository', 'owner', 'login')` matches the owner portion of `payload.dig('repository', 'full_name')` before allowing any handler to act, and reject the webhook (422) on mismatch.

### Proof of Concept
1. Attacker is an admin of `attacker-org`, a tenant configured in this Shipit instance's `secrets.github` map with their own `webhook_secret` (`S_attacker`).
2. Attacker crafts payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim_commit_sha>",
  "state": "success",
  "target_url": "https://ci.example.com/fake",
  "context": "ci/required-check",
  "branches": [{"name": "main"}]
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S_attacker, raw_body)>` and sends:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=...
```
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and validates successfully against `S_attacker` [7](#0-6) .
5. The status handler resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` [6](#0-5)  and writes a forged successful CI status for `victim-org/victim-repo`'s commit, even though the attacker has no access to that organization or repository.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

    rescue Shipit::GithubOrganizationUnknown => e

        "repository_owner=#{repository_owner}",

    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
