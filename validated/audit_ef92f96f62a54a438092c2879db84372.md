### Title
Webhook signature verified against payload-derived organization, but handlers act on unrelated payload data - cross-repository webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to validate `X-Hub-Signature` based on `repository_owner`, a value read out of the same untrusted JSON body it is trying to authenticate, and then hands the *entire* raw `params` hash to the event handlers instead of scoping processing to the verified organization/repository.

### Finding Description
`verify_signature` computes `repository_owner` from the payload itself: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and uses that to look up which GitHub App config (and thus which `webhook_secret`) to check the signature against: `github_app = Shipit.github(organization: repository_owner)` / `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

Once the signature check passes, `create` dispatches the *whole* parsed body to every handler registered for the event: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [3](#0-2) 

Handlers such as `PushHandler`/`StatusHandler`/`CheckSuiteHandler` then look up the target `Stack`/`Repository` from fields inside that same payload (e.g. `repository.full_name`, `sha`, `branches`) without re-verifying that the resolved stack's organization matches the organization whose secret produced a valid signature.

This is the same class of bug as the report: a value is used to authorize/authenticate (here, the organization used to pick the HMAC secret) that is different from the value actually acted upon (the repository/stack embedded elsewhere in the payload), because both are read from the same attacker-controlled JSON body without cross-validation. In a deployment where Shipit is configured with multiple GitHub Apps/organizations (as documented and tested in `secrets_double_github_app.yml`), an attacker who legitimately controls a repository/organization in one configured GitHub App (and thus can produce a validly-signed webhook using *that* org's `webhook_secret`) can set `repository.owner.login` to their own org (so the signature check passes) while setting a different `repository.full_name`/`sha`/branch data elsewhere in the payload to target a stack belonging to a different, unrelated organization also configured in the same Shipit instance.

### Impact Explanation
If exploitable, this would let an attacker with legitimate push/webhook rights to Organization A forge webhook events (e.g. `push`, `status`, `check_suite`) that get processed as if they concerned a stack under Organization B, without ever needing valid credentials for B. Depending on which handler is reached, this could trigger unwanted `GithubSyncJob`s, commit status writes, or check-run refreshes against Organization B's stacks — i.e., a cross-organization/cross-repository state-poisoning primitive that could contribute to an unauthorized deploy (e.g., poisoning commit status used as a deploy gate).

### Likelihood Explanation
This requires: (1) the target Shipit deployment to be configured with more than one GitHub App/organization sharing the same webhooks endpoint (a documented, supported configuration — see `test/dummy/config/secrets_double_github_app.yml`), and (2) the attacker to control a repository/org that is itself one of the configured organizations, so they can generate a validly-signed payload. This is a narrower precondition than the original report's single-vault scenario, and I could not fully trace, due to tool failures on this final iteration, whether the individual handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`) perform any additional organization/stack cross-check before acting (e.g., matching `Repository#owner` against the authenticated org) that would neutralize this. I was not able to open `app/models/shipit/webhooks/handlers/push_handler.rb`, `status_handler.rb`, `handler.rb`, or `lib/shipit.rb` in this session to confirm this detail with certainty.

### Recommendation
In `WebhooksController`, after verifying the signature, re-validate that every repository/stack referenced by the payload actually belongs to the same `repository_owner`/organization that was used to select the verifying secret, before dispatching to handlers — rather than trusting `repository.full_name` or other nested identifiers independently.

### Proof of Concept
Not able to construct a concrete, verified end-to-end PoC in this session because handler-level code (`push_handler.rb`, `status_handler.rb`, `handler.rb`) could not be retrieved due to a tool error on the final iteration; the root-cause code path in the controller is cited above, but confirmation that a downstream handler lacks a same-organization check on the resolved `Stack`/`Repository` is unverified.
