Confirmed: the webhook signature is verified against an organization selected via `repository_owner` (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`), while the actual write target — the `Stack`/`Repository` the event mutates — is looked up via a completely different, unvalidated field: `payload.dig('repository', 'full_name')` in `Handler#repository_name`, and `Commit.where(sha: params.sha)` (with no repository scoping at all) in `StatusHandler`. These two payload fields are never cross-checked against each other.

### Title
Webhook signature is verified against `repository.owner.login`, but events are applied using unrelated, unverified `repository.full_name` / commit-`sha` fields, allowing cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App / HMAC secret to verify against using `repository_owner`, taken from the untrusted JSON body itself. Once the signature check passes, the entire raw payload — including `repository.full_name` and `sha` — is handed unchecked to the event handlers, which use those separate fields to decide which `Stack`/`Commit` to mutate.

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

The signature is HMAC-SHA1 over the raw body, keyed by the `webhook_secret` configured for whatever organization `repository_owner` names — an attacker-controlled string, since it is read directly out of the JSON body (`lib/shipit/github_app.rb#verify_webhook_signature`) [3](#0-2) .

After this check passes, `create` dispatches the same raw payload to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers resolve the target `Stack` via a *different* field, `repository.full_name`, with no relation enforced to `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler` uses this to call `stack.sync_github(expected_head_sha: params.after)` for every matching stack/branch [6](#0-5) , and `StatusHandler` is even less scoped — it updates **any** `Commit` matching a `sha`, across the entire installation, with no repository filter at all:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

**The broken binding as an equality:**
`organization authenticated (repository.owner.login used to pick the webhook secret) == repository written (repository.full_name / sha used by the handler to mutate state)`

Before the attacker's request: for legitimate GitHub-originated webhooks these two fields always agree, because GitHub itself populates both from the same repository object.
After the attacker's request: an attacker who has push access to *any* single repository under an organization that is configured with a Shipit `webhook_secret` they can compute/know (e.g., their own org/repo installation, if the org uses a shared or discoverable webhook secret, or in a per-organization multi-tenant Shipit config where they control one tenant) can produce a validly-signed payload for their own `repository.owner.login`, while setting `repository.full_name` (and, for status webhooks, `sha`) to point at a stack/commit belonging to a **different** repository/organization entirely. The signature check only proves "this body was signed by whoever holds org A's secret" — it proves nothing about which repository the body claims to describe for state-mutation purposes, because that's a second, unvalidated field.

### Impact Explanation
This breaks the trust boundary between "authenticated as organization A" and "may write to repository/stack B." `StatusHandler` in particular allows forging a commit-status update (`create_status_from_github!`) for **any** SHA present in Shipit's database regardless of which stack/org it belongs to, which can flip a commit's CI/deployable state used by `Commit#deployable?` and continuous delivery gating — a cross-repository write with no repository scoping whatsoever. `PushHandler` similarly can trigger `sync_github` / `GithubSyncJob` for any stack whose repository's `full_name` the attacker chooses, independent of the org the signature was verified for. This matches the report's Critical criterion of "cross-repository writes."

### Likelihood Explanation
Requires the attacker to control at least one legitimately signed webhook (i.e., push/GitHub-App access to some repository configured in Shipit, or knowledge of one org's `webhook_secret` in a multi-org deployment) but not access to the target repository/organization at all — this is exactly the kind of "unprivileged relative to the target" attacker the scope allows (no `ApiClient` token, no session, no target-repo write access needed). Likelihood is moderate: it depends on Shipit being configured with more than one GitHub organization/webhook secret (the `github_app_config`/`github_organizations` per-org secrets path in `lib/shipit.rb`) [8](#0-7) , but that is a documented, supported configuration, not a misconfiguration.

### Recommendation
After signature verification, re-derive the authorized organization from the verified `github_app`/config and assert that every field used by handlers to select the mutation target (`repository.full_name`'s owner segment, and for `StatusHandler`, scope `Commit.where(sha:)` to `commit.stack.repository` matching that organization) is consistent with `repository_owner`. Reject the webhook if `repository.full_name.split('/').first` (case-insensitively) does not match the verified `repository_owner`/organization.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Attacker has GitHub App/webhook signing capability for `org-a` (e.g. they administer a repo there and can trigger real webhooks, or otherwise know `org-a`'s `webhook_secret`).
3. Attacker crafts a `status` event body:
```json
{
  "sha": "<sha of a commit belonging to org-b/important-repo>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-a/some-repo" }
}
```
4. Signs it with `org-a`'s `webhook_secret` and sends it to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `org-a`, verifies successfully against `org-a`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `org-b` commit — and calls `commit.create_status_from_github!(params)`, forging a `success` CI status on `org-b`'s commit despite the attacker having no relationship to `org-b` at all.
