### Title
CCMenu API token stack-scope bypass allows cross-stack deploy status disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stack` restricts lookups to the API client's authorized stack set, but `Shipit::Api::CCMenuController` overrides `#stack` with an unscoped lookup, so a token minted for one stack can read the deploy status of any stack in the instance.

### Finding Description
`ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) , as seen in the fixture `here_come_the_walrus` which is bound to the `shipit` stack [2](#0-1) . The base API controller enforces this scoping by intersecting the requested stack with the client's `stack_id`: [3](#0-2) 

`CCMenuController`, however, authenticates via a bare `params[:token]` (bypassing HTTP Basic auth) and then defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, never touching the scoped `stacks` relation: [4](#0-3) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string [5](#0-4)  — it never checks `current_api_client.stack_id` against the requested `stack_id`. The binding that breaks is: *the stack a token is authorized for* (`ApiClient#stack_id`) versus *the stack the token can actually touch* (`params[:stack_id]` in `CCMenuController#stack`). Any holder of a stack-scoped CCMenu-style token (e.g. minted by `CCMenuUrlController#client`, which stores the token in the URL) can substitute an arbitrary `stack_id` and read another stack's CI/CD status.

### Impact Explanation
An attacker holding a token scoped to Stack A can pass `stack_id=B` and receive Stack B's `#show` XML, including `lastBuildStatus`, `lastBuildLabel`, and lock state [6](#0-5) . This is an unauthenticated-for-that-resource read of stack/deploy state across a repository/stack boundary the token was never granted — matching the High-severity criterion "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Exploitation requires only possession of any valid CCMenu token (these are embedded directly in a CCMenu URL query string, per `CCMenuUrlController#fetch` at app/controllers/shipit/ccmenu_url_controller.rb:7-11, so they are more widely distributed than typical Basic-auth API credentials) and knowledge/guessing of another stack's `to_param`. No repository write access, session, or GitHub credentials are needed — only the token itself, which this class of endpoint is designed to hand out liberally.

### Recommendation
Change `CCMenuController#stack` to reuse the inherited scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot read any stack other than the one it was created for.

### Proof of Concept
1. Create a stack-scoped token for Stack A, e.g. via the app's `CCMenuUrlController#fetch` (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator:, name:)`, then manually set `stack_id` to Stack A, mirroring the `here_come_the_walrus` fixture).
2. Request `GET /api/stacks/:B_id/ccmenu.xml?token=<Stack-A-token>` where `B_id` refers to a different stack.
3. Observe the response returns Stack B's deploy status XML, even though the token's `stack_id` is Stack A — confirmed by the existing test helper pattern in `test/controllers/api/ccmenu_controller_test.rb:26-31`, which shows the token is the sole authorization gate and `stack_id` is taken unchecked from the URL.
