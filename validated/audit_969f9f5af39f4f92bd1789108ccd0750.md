### Title
Multisig transaction payload mismatch is only checked when the executor supplies a non-empty payload, allowing execution of a payload different from what owners approved when `abort_if_multisig_payload_mismatch_enabled` is not set - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`MinipoolManager`'s bug class is "amount computed independent of what was actually collateralized/approved is later validated too loosely, letting a party bypass the intended check." The Aptos-native admission analog is in `validate_multisig_transaction`, the VM-prologue function that gates whether a k-of-n approved multisig transaction is allowed to execute: the check that the *payload being executed* matches the payload the owners actually voted for is conditionally skipped, creating a path where the wrong payload can be admitted for execution under a valid multisig approval.

### Finding Description
`validate_multisig_transaction` is invoked by the VM prologue both during mempool validation and at the start of execution: [1](#0-0) 

After verifying quorum/timelock, it performs payload-integrity checks in two independent branches:

1. If the pending transaction was created with only a payload **hash** (`create_transaction_with_hash`), the hash is checked unconditionally against the incoming `payload` argument: [2](#0-1) 

2. If the pending transaction was created with the **full payload stored on-chain** (`create_transaction`), the match between the incoming `payload` argument and the on-chain stored payload is only checked when the feature flag `abort_if_multisig_payload_mismatch_enabled` is on, **and** the incoming `payload` is non-empty: [3](#0-2) 

The intent of the empty-payload exception is to let an executor omit the payload when relying on the on-chain stored copy for execution. But because the payload-equality check is gated on the `abort_if_multisig_payload_mismatch_enabled` feature flag, if that flag is disabled, **no comparison is performed at all** when a transaction was created via `create_transaction` (stored payload, no hash). In that state, any owner invoking execution can supply an arbitrary non-empty `payload` argument in the actual transaction they submit, and `validate_multisig_transaction` will admit it into execution without verifying it matches what the other owners approved (voted on) via `approve_transaction`/`create_transaction`.

This is a pre-admission binding failure precisely matching the required impact class: "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit," and "approval validation accepting the wrong approval set" — the k-of-n quorum was collected for payload A, but the admitted/executed transaction can carry payload B.

### Impact Explanation
If a multisig account's owners approve a benign transaction (e.g., a small transfer) via `create_transaction`/`approve_transaction`, and the feature `abort_if_multisig_payload_mismatch_enabled` is not enabled, any owner with execution rights (which is any owner reaching quorum, not necessarily a "privileged" governance actor) could submit the execution transaction with a different, unapproved payload (e.g., draining funds or calling an arbitrary entry function) that was never actually voted on by the required quorum of owners. This is a state-transition executed under the wrong "approval set" — matching a High-severity admission-boundary defect, since it defeats the entire purpose of the multisig quorum/approval mechanism for stored-payload transactions.

### Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled` is active on a given network/version. I was not able to determine, within the scope of this analysis, whether this flag defaults to enabled on current mainnet/testnet deployments; the flag's existence (and being separately gated) strongly suggests it was added later to backfill a real gap, and it may not be enabled everywhere the `multisig_account` module is deployed (e.g., older or non-Aptos-mainnet chains built from this codebase). Given the flag is a `std::features` runtime-gated flag rather than a compile-time constant, its state must be checked on-chain per network before treating this as definitively live; I flag this as the key uncertainty for this finding.

### Recommendation
Remove the feature-flag gating on the payload-match check for the stored-payload case, or at minimum make the check unconditional whenever `transaction.payload.is_some()`, regardless of `abort_if_multisig_payload_mismatch_enabled`. The `!payload.is_empty()` short-circuit should also be reconsidered: an executor relying on the stored payload should have a well-defined, always-verified path (e.g., by never accepting a *different* non-empty payload as authoritative when a stored payload exists), so that the payload used to reach quorum is always the payload that executes.

### Proof of Concept
1. Ensure `abort_if_multisig_payload_mismatch_enabled` is not enabled on the target network.
2. Owner A calls `create_transaction(multisig_account, payload_A)` (a benign transfer), stored on-chain in `transaction.payload`, with `transaction.payload_hash = None`.
3. Owners B, C, ... vote via `approve_transaction` until quorum for `sequence_number` is reached, based on payload_A.
4. Instead of executing with `payload_A` (or empty payload, deferring to stored payload), the executing owner submits the actual on-chain transaction using `payload_B` (a malicious entry function call) as the `payload` argument to `validate_multisig_transaction`.
5. Because `transaction.payload_hash.is_some()` is `false` (this transaction used `create_transaction`, not `create_transaction_with_hash`) and `abort_if_multisig_payload_mismatch_enabled()` is `false`, both the line 1365-1371 hash check and the line 1375-1384 payload-equality check are skipped.
6. `validate_multisig_transaction` returns success, and the transaction is admitted for execution with `payload_B`, which was never approved by quorum. [4](#0-3)
