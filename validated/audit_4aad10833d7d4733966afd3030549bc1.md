### Title
Cross-tenant status forgery via unscoped org signature check and repository-agnostic `StatusHandler` - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to verify a webhook using only `repository.owner.login` (or `organization.login`), and `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that org has no configured `webhook_secret`. Nothing in the pipeline ever checks that the org used to authenticate the request actually owns the `repository.full_name`/commit the handler subsequently mutates, and `StatusHandler` writes to `Commit.where(sha: params.sha)` with zero repository scoping.

### Finding Description
The broken binding, stated as an equality that the code never enforces:

`org_used_to_verify_signature == org_that_owns(params.repository.full_name)`

**Trace:**
- `WebhooksController#verify_signature` computes `repository_owner` purely from `params.dig('repository','owner','login')` and looks up `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` if that org config has no `webhook_secret` set: `return true unless webhook_secret`. [3](#0-2) 
- The rest of the payload (`repository.full_name`, `sha`, etc.) is never cross-checked against `repository_owner`; `full_name` is used only downstream by handlers to resolve the actual repository/stack.
- `StatusHandler#process` ignores repository entirely: `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }`, matching purely on `sha` across the whole `commits` table regardless of stack/repository. [4](#0-3) 

**Attack:** An attacker crafts a `POST /webhooks` `status` event with `X-Github-Event: status`, `repository.owner.login` set to any org that is configured in `Shipit.github` without a `webhook_secret` (verification then trivially passes for *any* signature header, including a garbage one), and `sha` equal to the sha of a commit belonging to a victim stack in a completely different org. Because the commit lookup is global and unscoped, the forged status is written to the victim's `Commit`/`Status` records.

**Why existing guards fail:** `drop_unhandled_event` only checks event type is handled. `verify_signature` authenticates the *sender* against one org's secret but never authenticates that the *payload content* (repository/commit) belongs to that org — there is no `Repository`/`Stack` scoping anywhere in this controller or in `StatusHandler`.

The `ignore_ci: true` framing in the question does not actually amplify impact the way it claims: `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — when `ignore_ci?` is true, deployability is *already* independent of any CI status, so a forged status changes nothing about deployability on such a stack. [5](#0-4)  The real, demonstrable impact is narrower than "unauthorized deploy": it is an unauthorized write of a `Status` row (and associated hooks such as `deployable_status`/`commit_status`) onto a commit belonging to a repository/organization that did not authenticate the request.

### Impact Explanation
Any attacker who can get an org with no `webhook_secret` configured in the Shipit deployment to exist (a Shipit/host operator misconfiguration, not attacker-controlled) can forge `status` webhooks that mutate `Commit`/`Status` records for *any* commit sha across *any* tenant/stack in the same Shipit instance, because `StatusHandler` performs no repository scoping. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team." It does not, by itself, cause an unauthorized deploy/rollback/merge — those still require a separate authenticated/authorized request to `DeploysController` (`require_permission :deploy, :stack`) or a `continuous_deployment?`-enabled stack, which is an additional victim-side precondition beyond `ignore_ci: true`.

### Likelihood Explanation
Exploitability strictly requires that at least one org configured under `Shipit.github` in the deployment lacks a `webhook_secret` — this is a deployment/config precondition, not something the attacker controls directly. If that precondition holds, the attack is trivial and repeatable: no signature computation is needed at all (`return true unless webhook_secret`), and the attacker only needs the target `sha` (obtainable from any public commit) to write bogus statuses cross-tenant.

### Recommendation
- In `WebhooksController`, resolve the repository/stack from `repository.full_name` and require that the org owning that repository matches `repository_owner` used to select the verification secret, rejecting mismatches.
- Do not allow `verify_webhook_signature` to return `true` when no secret is configured for an org that has repositories registered in Shipit; either require every configured org to have a secret, or fail closed.
- Scope `StatusHandler` (and other handlers) lookups by the repository resolved from the verified payload (e.g., `stack.repository`), not merely by global `sha` match.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs in test credentials: `org_no_secret` (no `webhook_secret`) and `org_victim` (has `webhook_secret`), each with a repository/stack.
2. Create `shipit_stacks(:victim)` under `org_victim` with `ignore_ci: true`, and a `Commit` with a known `sha`.
3. POST to `/webhooks` with `X-Github-Event: status`, body `{"sha" => victim_commit.sha, "state" => "failure", "repository" => {"owner" => {"login" => "org_no_secret"}, "full_name" => "org_victim/some-repo"}}`, and an arbitrary/garbage `X-Hub-Signature`.
4. Assert `response` is `:ok` (not `422`) — proving signature check was bypassed via the no-secret org.
5. Assert `victim_commit.reload.statuses.last.state == 'failure'` — proving a status was written to a commit belonging to `org_victim` despite the request being "authenticated" against `org_no_secret`.
6. Assert equality check: `repository_owner_used_for_verification ("org_no_secret") != org_owning_full_name ("org_victim")` yet the write still occurred — demonstrating the missing binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
