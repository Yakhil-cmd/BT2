### Title
Full-node hub permanently caches unconfirmed/unstable AA definitions and serves them to light clients as trusted, before the definition ever stabilizes - ([File: network.js])

### Summary
The Hugging Face CVE writes an untrusted remote artifact to a persistent cache *before* the consent/trust check that is supposed to gate it, so an unverified artifact can later be served/executed as if it were trusted. `ocore`'s `network.js` handler for `light/get_definition` has the analogous inversion: it reads and permanently memoizes an **unstable, unconfirmed** AA definition (one that has not yet reached finality on the DAG) into a process-lifetime in-memory cache, and will keep answering all future light-client lookups from that cache even if the defining unit is later voided (becomes non-serial / `final-bad`) or never stabilizes at all.

### Finding Description
In `network.js`, the `light/get_definition` request handler works as follows: [1](#0-0) 
```
case 'light/get_definition':
    ...
    if (definitions[params])
        return sendResponse(ws, tag, definitions[params]);
    db.query("SELECT definition FROM definitions WHERE definition_chash=? UNION SELECT definition FROM aa_addresses WHERE address=? LIMIT 1", [params, params], function(rows){
        var arrDefinition = rows[0]
            ? JSON.parse(rows[0].definition)
            : storage.getUnconfirmedAADefinition(params);
        if (arrDefinition) // save in cache
            definitions[params] = arrDefinition;
        sendResponse(ws, tag, arrDefinition);
    });
    break;
```
When the definition is not yet present in the confirmed `definitions`/`aa_addresses` tables, the code falls back to `storage.getUnconfirmedAADefinition(params)`, which scans `storage.assocUnstableMessages` for a `'definition'` message belonging to a **still-unstable** unit whose current sequence happens to be `'good'`: [2](#0-1) 
```
function getUnconfirmedAADefinition(address) {
	for (var unit in assocUnstableMessages) {
		var objUnit = assocUnstableUnits[unit] || assocStableUnits[unit];
		if (!objUnit) throw Error(...);
		if (objUnit.sequence !== 'good') continue;
		var messages = assocUnstableMessages[unit];
		for (var i = 0; i < messages.length; i++) {
			var message = messages[i];
			if (message.app !== 'definition') continue;
			var payload = message.payload;
			if (payload.address === address) return payload.definition;
		}
	}
	return null;
}
```
This "unconfirmed" definition is what such an AA-creation flow produces: an AA trigger sender fires a primary trigger that causes a triggered AA to emit an app `'definition'` message defining a new child AA (this is a normal, attacker-reachable flow — see the `'AA with generated definition of new AA'` test), and the message is recorded into `storage.assocUnstableMessages` at write time: [3](#0-2) 

The unstable-message record is only cleaned up when the unit's MCI actually stabilizes, at which point `main_chain.js` checks the final sequence and deletes the entry if the unit turned out `final-bad`: [4](#0-3) 
```

	if (!arrUnstableMessages) return cb();

		delete storage.assocUnstableMessages[unit];
		return cb();
	}

```
The bug is the ordering/persistence inversion: the hub's `network.js` handler reads and **permanently caches** (`definitions[params] = arrDefinition`) this pre-finality data into an in-process object (`definitions`) that is never invalidated, evicted, or re-checked against the eventual on-DAG outcome. Unlike `storage.assocUnstableMessages`, which is properly cleared on `final-bad` resolution, the `network.js` `definitions` cache has no corresponding cleanup path anywhere in the codebase, so a definition observed while the defining unit was merely "currently good but not yet stable" is served to every light client that asks, indefinitely — even after the defining unit is later displaced by a conflicting/double-spending unit and resolved to `final-bad`, meaning the child AA address in fact was never legitimately created on the DAG.

This mirrors the CVE class exactly: an unauthenticated/untrusted, not-yet-finally-verified artifact (the AA definition of an address that has not passed the DAG's actual finality/trust check — main-chain stabilization) is written into a durable cache before the "trust check" (stabilization to `final-bad`/`good`) completes, and that stale, potentially-invalid cache entry persists and continues to be trusted/served afterward.

### Impact Explanation
Light wallets rely on `light/get_definition` to discover whether an address is a valid AA and to obtain its definition (getters, messages, etc.) before composing payments or invoking triggers against it. If a hub serves a phantom/never-finalized AA definition:
- A light wallet may believe an address is a live AA and send funds to it expecting the AA logic to execute and respond (e.g., refund logic, conditional payout logic). If the underlying "definition" unit never stabilizes as `good` (attacker deliberately double-spends/forks it to `final-bad` after luring wallets to pay into the phantom AA address), funds sent to that address will never be processed by any AA trigger logic, because the address was never actually registered as an AA on the authoritative `aa_addresses` table/DAG state. This results in **AA fund loss / freezing** — the payment is permanently stuck at an address that looks like an AA to light clients but functionally is not one.
- The cache also creates a **node disagreement on validity**: full nodes correctly treat the child AA as nonexistent (rolled back), while any light client that queried the hub during the unstable window continues to be told the AA exists, indefinitely.

### Likelihood Explanation
The chain of events (AA-issued child-AA `'definition'` message, unstable-but-currently-good sequence, later reversal to `final-bad` via a conflicting/double-spend unit) is a normal, previously-tested code path in the codebase (see `test/aa_composer.test.js` "AA with generated definition of new AA"), reachable by any ordinary AA trigger sender who can afford the trigger fee — no privileged, hub-operator, or network-level attacker role is required to *create* the vulnerable condition. Triggering the finality-reversal window requires timing a conflicting/double-spend unit, which is achievable by a unit poster with normal DAG-posting capability. The remaining requirement — a light client querying during that unstable window — is a routine, expected wallet behavior, not something requiring social engineering.

### Recommendation
1. In `network.js`, do not cache (`definitions[params] = arrDefinition`) any value obtained via `storage.getUnconfirmedAADefinition()`; only cache confirmed rows from the `definitions`/`aa_addresses` tables.
2. If unconfirmed definitions must be served for UX responsiveness, tag the response as unconfirmed/provisional and never store it in the long-lived `definitions` object; alternatively store it in a structure keyed by unit and invalidate it exactly the way `storage.assocUnstableMessages` is invalidated (on stabilization, checking `sequence === 'final-bad'`).
3. Add tests that simulate: (a) a child-AA `'definition'` message from a still-unstable, currently-`good` unit; (b) a light-client `light/get_definition` query during that window; (c) the defining unit later resolving to `final-bad`; and (d) assert that a subsequent `light/get_definition` query returns "not found" rather than the stale cached definition.

### Proof of Concept
1. AA trigger sender fires a trigger causing a target AA to emit an app `'definition'` message defining a new child AA address `X` (as in the existing test `'AA with generated definition of new AA'`), while also, in the same unstable region of the DAG, constructing a conflicting/double-spend sibling unit chain intended to make the defining unit's sequence resolve to `final-bad` once stabilized.
2. While the defining unit is unstable and currently `sequence === 'good'`, a light wallet sends `light/get_definition` for address `X` to the hub. `storage.getUnconfirmedAADefinition('X')` returns the definition (since `objUnit.sequence === 'good'` at that moment), and `network.js` stores it permanently: `definitions['X'] = arrDefinition`.
3. The attacker completes the conflicting unit chain so that, upon stabilization, the defining unit is marked `final-bad`; `storage.assocUnstableMessages[unit]` is correctly deleted per `main_chain.js`, and `X` never appears in `aa_addresses`.
4. Any light wallet (the same or a different one) subsequently queries `light/get_definition` for `X` again; the hub's `network.js` short-circuits at `if (definitions[params]) return sendResponse(ws, tag, definitions[params]);` and returns the stale definition as if `X` were a valid, live AA — despite it never having been legitimately created — inducing the wallet to send/trust payments to a nonexistent AA address.
