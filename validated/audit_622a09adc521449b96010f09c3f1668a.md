### Title
Capped-asset issuance cap is enforced per-address, not per-asset, when `issued_by_definer_only=false`, allowing unbounded supply inflation - (File: `validation.js`)

### Summary
For a capped asset that does **not** restrict issuance to the definer (`issued_by_definer_only=false`), the double-spend/uniqueness check that is supposed to guarantee a single, global issuance of the capped amount is silently narrowed to a per-issuer-address scope. Any unprivileged user can become an "issuer" for such an asset simply by posting a unit that authors an `issue` input, and each distinct address they control can independently mint the full `cap` amount, exactly mirroring the Chakra bug where a uniqueness/counter key that should have included an extra dimension (the handler) was missing it and could be manipulated by any caller.

### Finding Description
When an asset is defined with a `cap` and `!fixed_denominations`, the issuer must supply an `issue` input whose `amount` equals the *entire* `cap`, and whose `serial_number` is forced to `1`: [1](#0-0) [2](#0-1) 

The uniqueness of that issuance is enforced by building a "double-spend" query key from `type='issue'`, `denomination`, and `serial_number`, but the `address` column is only added to that key **when the asset is not `issued_by_definer_only`**: [3](#0-2) 

This mirrors the DB-level unique constraint, which also always includes `address` in the key used to prevent "double issue": [4](#0-3) 

For an `issued_by_definer_only=false` capped asset, this means the uniqueness check is effectively: "this `(asset, denomination, serial_number=1)` triple has not been issued **by this particular address** yet" rather than "has not been issued by anyone yet." Since nothing restricts who may act as the issuing address for such an asset (any author of the unit qualifies, checked only via `arrAuthorAddresses.indexOf(input.address) === -1` at [5](#0-4) ), an attacker can generate as many fresh addresses as desired and, for each one, author a unit that issues the full `cap` amount of the asset. Each such unit passes validation because the per-address key has never been used before.

This is structurally identical to the H-07 root cause: a value meant to represent a single, globally-scoped invariant (the Chakra `nonce_manager` mapping keyed only by user, meant to be unique per settlement flow; here, the asset `cap` meant to be a single global issuance limit) is checked using a key that omits the dimension needed to make it globally unique (the handler address in Chakra; here, omitting a "no per-address scoping" requirement for capped assets), and the function/path that can trigger the mismatch is reachable by any unprivileged party (anyone calling `send_cross_chain_msg` in Chakra; here, any user who can author a unit and pick an arbitrary fresh address as an "issuer").

### Impact Explanation
Any user can inflate the supply of a capped asset with `issued_by_definer_only=false` far beyond its declared `cap`, simply by repeating the issuance from new addresses. This directly falls under "asset issuance and transfer conditions" and produces "supply inflation" — one of the explicitly accepted concrete impacts. It breaks the fundamental scarcity guarantee that `cap` is supposed to provide for an asset, and since it is validated identically by all full nodes, it does not cause node disagreement, but it does let the asset issuer/participants create unlimited additional coins of a token advertised as capped, defrauding holders/counterparties who trust the `cap` field.

### Likelihood Explanation
The precondition is simply defining (or finding) an asset with `cap` set and `issued_by_definer_only=false` and `fixed_denominations=false` — an entirely valid, unprivileged combination per the asset-definition validator, which does not forbid this combination: [6](#0-5) 
No special privilege, hub/peer trust, or race condition is required — a single attacker with normal wallet access can trigger the full exploit by posting several standard units, each from a different self-controlled address, each issuing the full `cap` amount. This makes exploitation straightforward and repeatable.

### Recommendation
When building the double-spend/uniqueness key for `issue` inputs of a capped asset, do not scope by `address` regardless of `issued_by_definer_only` — a capped asset's issuance uniqueness must always be enforced at the `(asset, denomination, serial_number)` granularity globally, not per-address:
```js
// validation.js, around line 2366-2373
if (objAsset){
    doubleSpendWhere += " AND serial_number=?";
    doubleSpendVars.push(input.serial_number);
}
if (objAsset && !objAsset.issued_by_definer_only && !objAsset.cap) {   // only allow per-address scoping for UNCAPPED assets
    doubleSpendWhere += " AND address=?";
    doubleSpendVars.push(address);
}
```
Correspondingly, the DB unique index `byAssetDenominationSerialAddress` should be split so that capped-asset issuance uniqueness is enforced without the `address` column (e.g., a separate unique index on `(asset, denomination, serial_number)` for `cap IS NOT NULL` assets), preventing more than one successful issuance of the capped amount regardless of which address performs it.

### Proof of Concept
1. Post an asset-definition unit: `{app:'asset', payload:{cap: 1000000, is_transferrable:true, fixed_denominations:false, issued_by_definer_only:false, ...}}`. This passes `validateAssetDefinition` since no rule ties `cap` to `issued_by_definer_only` ( [6](#0-5) ).
2. From address `A1` (an author the attacker controls), post a payment unit with an `issue` input: `{type:'issue', serial_number:1, amount:1000000}` (equal to `cap`, as required at [2](#0-1) ). This validates and is accepted; the double-spend key becomes `type='issue' AND denomination=? AND serial_number=1 AND address=A1`.
3. From a fresh address `A2` controlled by the same attacker, repeat step 2 with `serial_number:1, amount:1000000`. Because `objAsset.issued_by_definer_only` is `false`, the double-spend key includes `address=A2`, which has never issued before, so this second full-cap issuance also validates and is accepted ( [3](#0-2) ).
4. Repeat from `A3, A4, …, An` — total minted supply becomes `n * cap`, unboundedly exceeding the asset's declared cap.
