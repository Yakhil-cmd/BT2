### Title
Team hijack via cross-organization membership webhook - global `github_id` lookup with attacker-controlled org authentication (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` records solely by `github_id`, with no check that the webhook's `organization.login` actually owns that team. Because `WebhooksController#verify_signature` derives the signing organization from the same attacker-controlled `organization.login` field, an attacker who owns any GitHub organization with a configured Shipit `webhook_secret` can sign a `membership` event naming an existing, unrelated victim team's `github_id` and add themselves as a member.

### Finding Description
The broken binding: the code implicitly assumes `params.team.id → organization == params.organization.login`, i.e. that the team identified by `github_id` in the payload belongs to the organization named in the same payload. No such equality is ever checked.

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` as `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) . A `membership` payload has no `repository` key, so `repository_owner` resolves entirely to the attacker-supplied `organization.login`. It then fetches `Shipit.github(organization: repository_owner)` and verifies the HMAC using **that org's own configured `webhook_secret`** [2](#0-1) . Since the attacker owns that org and configured its Shipit integration, they legitimately hold this secret and can produce a valid signature.
- `MembershipHandler#find_or_create_team!` then does `Team.find_or_create_by!(github_id: params.team.id)`, which is a **global, unscoped lookup** across all teams regardless of the organization used for signature verification [3](#0-2) .
- `#process` then calls `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'` [4](#0-3) , and `Team#add_member` simply appends the member with no ownership/authorization check [5](#0-4) .

Exploit flow: attacker owns `attacker-org`, configures Shipit's GitHub App integration for it (legitimately obtaining its own `webhook_secret`). They discover/guess an existing victim `Team#github_id` (e.g., via `lib/tasks/teams.rake` output, prior public webhook, or brute force of small integer IDs). They POST to `/webhooks` with header `X-Github-Event: membership`, a body `{"action":"added","team":{"id":<victim_github_id>,...},"organization":{"login":"attacker-org"},"member":{"login":"attacker"}}`, signed with `attacker-org`'s `webhook_secret`. `verify_signature` passes because it authenticates against `attacker-org`, not the victim org. `find_or_create_team!` finds the pre-existing victim `Team` by `github_id` and returns it unchanged (the `organization` assignment in the block only runs on creation, not on find). `team.add_member` adds the attacker as a member.

None of the existing guards prevent this: `verify_signature` only proves the request was signed by *some* org's secret, not the org that owns the named team; `drop_unhandled_event` and `ExplicitParameters` schema only validate payload shape, not provenance; there is no `require_permission!`/`User#authorized?` check in the webhook path at all.

### Impact Explanation
If `Shipit.github_teams` is configured for authorization gating (per `Shipit::User#authorized?`, `app/models/shipit/user.rb` lines 80-82), and the targeted victim team is one of those `github_teams`, the attacker escalates from an unauthenticated internet user into an authorized Shipit user/operator — able to trigger deploys, rollbacks, or other privileged UI actions gated by that authorization check. This matches the "High - escalation into `Shipit.github_teams` authorization" impact category. The attack is repeatable against any team whose numeric `github_id` the attacker can learn or guess, and is not scoped to a single tenant — any victim team in the shared Shipit instance is reachable as long as the attacker controls one legitimately-configured organization's webhook secret.

### Likelihood Explanation
Preconditions: Shipit must be configured to serve at least two GitHub organizations (attacker's and the victim's) via `Shipit.github`, which is a normal multi-tenant Shipit deployment pattern; the attacker needs their own org onboarded with a working `webhook_secret` (a legitimate, low-cost action any org admin can do); and they need to know a victim `Team#github_id` (a small monotonically-assigned GitHub integer, often discoverable via prior webhook traffic, GitHub API, or brute-forceable). No GitHub App private key, session, or victim secret is required. This is feasible and cheaply repeatable — a single crafted HTTP POST per attempt.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` and `organization` (`Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise when an existing team with that `github_id` has a different `organization` than the one in the payload. More generally, `WebhooksController#verify_signature` should not trust attacker-supplied `organization.login`/`repository.owner.login` as the sole basis for both signature-key selection and downstream authorization — the org used to select the signing secret must be cross-checked against the org owning any referenced resource before mutating records.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "membership event cannot hijack a team belonging to a different organization" do
  victim_team = shipit_teams(:the_a_team) # fixture: github_id: 1, organization: 'victim-org'
  attacker = shipit_users(:walrus) # or User.create!(login: 'attacker')

  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => 'x', 'slug' => 'x', 'url' => 'http://x' },
    'organization' => { 'login' => 'attacker-org' }, # attacker's own org
    'member' => { 'login' => attacker.login }
  }

  Shipit::Webhooks::Handlers::MembershipHandler.new.call(payload)

  refute_includes victim_team.reload.members, attacker,
    "attacker should not be added to a team owned by a different organization"
end
```
Assert both sides of the binding: before the call, `victim_team.organization == 'victim-org'` and `payload['organization']['login'] == 'attacker-org'` (unequal); after the call, the test should show the handler currently ignores this inequality and adds the member anyway, demonstrating the vulnerability (the fix would make the assertion pass by rejecting cross-org matches).
