### Title
Scaled-source oracle prices a wrapped/derivative asset as `factor × underlying quote`, overvaluing collateral after a secondary-market depeg - (File: contracts/price-aggregator/src/engine.rs)

### Summary
The price-aggregator supports a `Scaled` source that derives an asset's price as `factor_feed × quote_price`, where the factor is an exchange-rate feed and the quote is the underlying asset's price key. `read_scaled` multiplies the two WAD prices and returns the result as the asset's sole market value; the only guard is `min_factor_wad`/`max_factor_wad` bounding the *factor feed*, not the asset's traded price. This is the exact structure of the WBTC/BTC bug class: the collateral token is valued at its redemption/exchange rate rather than at what the market pays for it. A listed wrapped asset (e.g., a BTC-pegged token priced via a `Scaled` source over the `Ref("BTC")` quote, or an LST over XLM) that depegs below the factor-implied price keeps its full oracle value, letting a borrower post it at inflated value and drain borrowed liquidity into bad debt.

### Finding Description
`PriceSource::Scaled(ScaledSource)` is defined in `common/src/types/composable_oracle.rs` as `{ factor: FeedSource, quote: PriceKey, min_factor_wad, max_factor_wad }`. In `engine.rs`, `evaluate_source` dispatches `PriceSource::Scaled` to `read_scaled` (lines 592-593), which:

1. Reads the factor feed and rejects only if it lies outside `[min_factor_wad, max_factor_wad]` (`FactorOutOfBounds`, lines 634-640).
2. Resolves the quote key via `resolve_nested` (line 642).
3. Returns `factor.price_wad × quote.price_wad` as the observation (lines 644-656).

No component of this composition reflects the asset's own secondary-market price. The blended-leg tolerance check in `blend` (lines 419-440) only applies when the oracle declares *two* sources; a single-`Scaled`-source oracle (`Legs::One`, line 417) takes the scaled value unconditionally, subject only to the wide `min_sanity_price_wad`/`max_sanity_price_wad` band enforced in `Outcome::failure` (lines 142-146). Sanity bands are deliberately broad (`MIN_SANITY_BAND_BPS`-bounded, e.g. BTC ref band 20,000-300,000 USD WAD in `configs/mainnet/markets.json:49-50`), so a 10-50% depeg sits comfortably inside them.

Because `resolve_nested`/`force` fail only on configuration errors, staleness, deviation between *two configured legs*, or sanity-band breaches, an honest factor feed reporting the true redemption ratio produces a "valid" price that is decoupled from the asset's real market value indefinitely.

### Impact Explanation
The controller's health factor, `min_borrow_collateral_usd`, LTV checks and liquidation thresholds all consume `prices()` output for the collateral token. If a scaled-priced collateral asset trades 30% below `factor × quote`:

- An attacker buys the depegged token on the open market (or already holds it), supplies it via `supply`, and calls `borrow` up to the LTV-weighted limit computed from the inflated oracle price.
- The borrowed amount exceeds the real collateral value; the position is born undercollateralized.
- Liquidations cannot restore solvency because the seized collateral sells for less than the repaid debt; residual debt is written down through `clean_bad_debt`/`recapitalize` without minting shares, i.e., direct loss socialized onto suppliers - protocol insolvency.

This is theft of user funds / protocol insolvency reachable entirely by an unprivileged address via `supply`, `borrow`, `withdraw`, and the depeg itself requires no privileged action.

### Likelihood Explanation
- Requires a market-listed collateral asset whose oracle uses a `Scaled` composition without a second independent market-priced leg, and whose token trades below its redemption rate. Wrapped/bridged assets and liquid-staking tokens depeg routinely during liquidity crunches, bridge exploits, or redemption halts; the WBTC scenario in the referenced report is precisely this pattern.
- The depeg need not be caused by the attacker; the vulnerability converts an exogenous market event into insolvency. Alternatively, an attacker can manufacture a temporary depeg by selling the wrapped token on Aquarius/Soroswap (allowed venues) if liquidity is thin relative to the borrowable depth.
- Cost to the attacker is bounded by the discounted collateral purchased; profit is the excess borrowable value.

Uncertainty noted: the specific `Scaled` markets in `configs/mainnet/markets.json` were not fully enumerated, so the finding's trigger condition depends on which listed assets rely solely on a scaled source - but the code path unconditionally trusts the composition whenever it is configured.

### Recommendation
- For any collateral asset priced via `PriceSource::Scaled`, configure a second independent source that reflects the token's actual secondary-market price (e.g., a direct Reflector/RedStone market feed or an `AquariusLp`-derived leg), with a non-trivial `OracleTolerance` band so `blend` flags `UnsafePriceNotAllowed` when `factor × quote` diverges from market price.
- Alternatively, bound the *scaled result* against a market price inside `read_scaled`, or add a config option `max_depeg_bps` comparing the scaled output to an optional market reference.
- Tighten `min_sanity_price_wad`/`max_sanity_price_wad` for scaled assets, acknowledging this only bounds extreme cases.

### Proof of Concept
1. Governance has registered `Token(W)` (wrapped BTC analogue) with a single `Scaled` source: `factor` = Reflector feed returning `~1.0e18` (honest redemption rate), `quote` = `Ref("BTC")`, `min/max_factor_wad` = `[0.9e18, 1.1e18]`.
2. BTC trades at $60,000 → oracle reports `W = $60,000`.
3. W depegs on secondary markets to $45,000 (redemption paused/thin liquidity). The factor feed still reports ~1.0, so `prices([Token(W)])` still returns `$60,000` - within the sanity band, no staleness flag, no deviation (only one source).
4. Attacker acquires 100 W for $4.5M market cost, calls `supply(hub, Token(W), 100e7)` then `borrow(hub, USDC, ~$5M)` up to the LTV limit priced at $6M collateral.
5. Attacker abandons the position. Liquidation repays at most the $4.5M real collateral value; `clean_bad_debt` writes down the remainder, leaving the pool insolvent.
