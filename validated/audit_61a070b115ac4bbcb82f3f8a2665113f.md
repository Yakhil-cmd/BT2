### Title
Unbounded Bridge KLAY Fee Enables Operator Frontrun of Fallback Transfers, Draining User KAIA to Fee Receiver — (File: `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

The `BridgeTransferKLAY` fallback function passes the live `feeOfKLAY` storage value as the user's `_feeLimit` at execution time. Because `feeOfKLAY` has no upper bound and can be changed instantly by a single operator (default threshold = 1), a malicious operator can frontrun any pending fallback transaction, raise the fee to just below `msg.value`, and redirect nearly all of the user's KAIA to the `feeReceiver` while emitting a bridge request for only 1 wei.

---

### Finding Description

**Root cause — no upper bound on `feeOfKLAY`:**

`BridgeFee._setKLAYFee` accepts any `uint256` value with no cap:

```solidity
function _setKLAYFee(uint256 _fee) internal {
    feeOfKLAY = _fee;
    emit KLAYFeeChanged(_fee);
}
``` [1](#0-0) 

**Root cause — default operator threshold is 1:**

The `BridgeOperator` constructor sets `operatorThresholds[Configuration] = 1`, meaning a single operator can execute `setKLAYFee` in one transaction with no multi-sig delay:

```solidity
constructor() internal {
    for (uint8 i = 0; i < uint8(VoteType.Max); i++) {
        operatorThresholds[uint8(i)] = 1;
    }
    ...
}
``` [2](#0-1) 

**Vulnerable sink — fallback uses live `feeOfKLAY` as `_feeLimit`:**

```solidity
function () external payable {
    _requestKLAYTransfer(msg.sender, feeOfKLAY, new bytes(0));
}
``` [3](#0-2) 

Inside `_requestKLAYTransfer`, the only guard is `msg.value > _feeLimit`. Because `_feeLimit` is set to the current `feeOfKLAY` at execution time, if an operator raises `feeOfKLAY` between the user's broadcast and inclusion, the user's `msg.value` is split at the new (higher) fee boundary:

```solidity
require(msg.value > _feeLimit, "insufficient amount");
uint256 fee = _payKLAYFeeAndRefundChange(_feeLimit);
emit RequestValueTransfer(..., msg.value.sub(_feeLimit), ...);
``` [4](#0-3) 

Inside `_payKLAYFeeAndRefundChange`, the check `require(_feeLimit >= fee)` is trivially satisfied because `_feeLimit == feeOfKLAY == fee` at that moment — the entire `_feeLimit` is transferred to `feeReceiver`:

```solidity
uint256 fee = feeOfKLAY;
if (feeReceiver != address(0) && fee > 0) {
    require(_feeLimit >= fee, "insufficient feeLimit");
    (bool ok, ) = feeReceiver.call.value(fee)("");
    ...
}
``` [5](#0-4) 

**Note:** `requestKLAYTransfer` and `requestERC20Transfer` are NOT vulnerable because the user explicitly supplies `_feeLimit`; if the fee exceeds it the transaction reverts and no funds are lost. Only the fallback path is affected.

---

### Impact Explanation

A malicious operator sets `feeOfKLAY = msg.value - 1` (one wei below the user's sent value). The fallback executes successfully (`msg.value > _feeLimit` passes by 1 wei), pays `msg.value - 1` KAIA to `feeReceiver`, and emits a `RequestValueTransfer` event for only **1 wei** to be minted/released on the counterpart chain. The user loses nearly all their KAIA to the fee receiver while receiving a negligible cross-chain transfer. This is an unauthorized fee charge affecting KAIA and bridged assets.

---

### Likelihood Explanation

- The default `operatorThresholds[Configuration] = 1` means **a single operator** can execute the fee change in one transaction with no additional approvals.
- Service-chain bridge operators are semi-trusted entities registered by the bridge owner; a compromised or malicious operator key is a realistic threat.
- The attack requires only standard mempool visibility (pending transaction observation) and a higher-gas `setKLAYFee` transaction — no special on-chain state is needed.
- Users who interact with the bridge via the fallback (plain KAIA send) are the most common and least sophisticated users, making them the most likely victims.

---

### Recommendation

1. **Add an upper bound on `feeOfKLAY`** (e.g., a percentage of a maximum transfer value or an absolute cap set at deployment) inside `_setKLAYFee`.
2. **Require a timelock or two-step commit** for fee changes so users can observe and react before the new fee takes effect.
3. **Remove the implicit `_feeLimit = feeOfKLAY` pattern** in the fallback. Instead, revert if `msg.value` is insufficient for the current fee, or require users to pass an explicit slippage-protected `_feeLimit`.

---

### Proof of Concept

```
Setup:
  feeOfKLAY = 0.1 KAIA
  feeReceiver = attacker-controlled address
  operatorThresholds[Configuration] = 1 (default)
  Operator = attacker

Step 1: User broadcasts fallback tx:
  bridge.call{value: 1.1 KAIA}("")
  // User expects: fee=0.1 KAIA, transferred=1.0 KAIA

Step 2: Attacker (operator) sees pending tx in mempool, broadcasts with higher gas:
  bridge.setKLAYFee(1.099999 KAIA, configurationNonce)
  // Single-operator threshold=1: executes immediately

Step 3: setKLAYFee mines first → feeOfKLAY = 1.099999 KAIA

Step 4: User's fallback mines:
  _feeLimit = feeOfKLAY = 1.099999 KAIA
  require(1.1 KAIA > 1.099999 KAIA) ✓ (passes by 1 wei)
  fee paid to feeReceiver = 1.099999 KAIA
  RequestValueTransfer emitted with value = 1 wei

Result:
  User loses 1.099999 KAIA to feeReceiver
  User receives 1 wei on the counterpart chain
  Net loss: ~1.0 KAIA (the intended transfer amount)
```

The corrupted value is `RequestValueTransfer.valueOrTokenId = 1 wei` instead of the intended `1.0 KAIA`, and `feeReceiver` balance increases by `1.099999 KAIA` instead of `0.1 KAIA`.
