## Title
Stack-scoped API token authorizes reads on any stack, not just the one it was issued for - (File: app/controllers/shipit/api/ccmenu_controller.rb)

## Summary
`Shipit::ApiClient` tokens can be created scoped to a single stack (`belongs_to :stack, optional: true`), and `Api::BaseController` is designed to enforce that scoping for every request by resolving the target stack through the `stacks` helper, which filters `Stack.where(id: current_api_client.stack_id)` when the client is stack-restricted. `Api::CCMenuController` breaks this binding by overriding `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!(params[:stack_id])` used everywhere else, so the `read:stack` permission check passes but the actual record fetched is never filtered by the token's `stack_id`.

## Finding Description
`ApiClient` permission checks are supposed to enforce the equality: *stack a token authorises == stack a controller action touches*. `Api::BaseController` implements this by scoping the `stack` lookup through `stacks`: [1](#0-0) 

`Api::CCMenuController` requires only `read:stack` permission and, critically, overrides the `stack` accessor to bypass that scoping entirely, looking the stack up globally by its URL param: [2](#0-1) 

`require_permission :read, :stack` only verifies that the authenticated `ApiClient` has the `read:stack` permission string in its `permissions` array — it does not verify which stack that permission applies to: [3](#0-2) 

Fixtures confirm stack-scoped tokens are an intended, first-class authorization mechanism (e.g. `here_come_the_walrus` is scoped to the `shipit` stack with only `read:stack`): [4](#0-3) 

Because `CCMenuController#show` calls `stack.deploys_and_rollbacks.last`, and `stack` resolves via the unscoped `Stack.from_param!`, any holder of a stack-scoped, `read:stack`-only token can pass an arbitrary `stack_id` in the URL and get back build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, lock state, etc.) for a stack the token was never authorized to touch.

## Impact Explanation
This crosses the "stack a token authorises vs. stack it touches" trust boundary: an `ApiClient` deliberately restricted to one stack (a common pattern for handing scoped read-only tokens to third parties, e.g. CI dashboards) gains unauthenticated-for-that-stack read access to the deploy/build status of every other stack in the Shipit instance. This matches the High-severity impact class of "unauthenticated read of stack state ... " since the token's authorization for the target stack was never actually verified, only its possession of a `read:stack` permission string that was meant to be stack-scoped.

## Likelihood Explanation
Any actor holding a legitimately-issued, stack-scoped `ApiClient` token (which by design has minimal `read:stack` permission and is meant to be handed out more freely than an unscoped admin token, e.g. embedded in a CI status badge URL or CCMenu client) can trivially exploit this by simply changing the `stack_id` path segment. No additional privilege, secret, or race condition is required — it is a straightforward parameter substitution against a documented, reachable endpoint (`config/routes.rb` mounts `get '/' => 'ccmenu#show', as: :ccmenu` under `/api/stacks/*stack_id/ccmenu`). [5](#0-4) 

## Recommendation
Remove the `CCMenuController#stack` override (or change `authenticate_api_client`'s query-string token support without also reintroducing the base `stacks` scoping) so the action resolves the stack via the scoped `stacks.from_param!(params[:stack_id])` helper inherited from `Api::BaseController`, ensuring a stack-restricted `ApiClient` can never resolve a stack outside `current_api_client.stack_id`.

## Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id: <stack A>` with only `read:stack` permission, e.g. the `here_come_the_walrus` fixture.
2. Send `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<here_come_the_walrus token>` where stack B is a different stack than the one the token is scoped to.
3. Observe the request succeeds (`assert_response :ok` in the existing test pattern) and returns stack B's `lastBuildStatus`/`lastBuildLabel`/deploy info, even though the token's `stack_id` only authorizes stack A. Compare with `Api::DeploysController`/`Api::TasksController`, which correctly use the inherited scoped `stack` method and therefore return `404` for a stack outside the token's scope.

      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end
