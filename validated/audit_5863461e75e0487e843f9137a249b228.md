### Title
Uncaught exception in `checkForDoublespends` on a crafted spend-proof conflict crashes every validating node - ([File: validation.js])

### Summary
The CVE analog (Wireshark CIP-Safety dissector crash from insufficient input validation) maps to `ocore`'s unit-validation path, where a malformed but otherwise well-formed unit can drive `checkForDoublespends()` into a `throw Error(...)` that is not caught anywhere in the call chain. Because `network.js` installs a global `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the whole process, this uncaught throw takes down the entire node.

### Finding Description
`validateMessage()` in `validation.js` calls `validateSpendProofs`, which builds a SQL query for existing `spend_proofs` rows that conflict with the spend proof(s) declared in the incoming unit's private-payment message, and passes the result to `checkForDoublespends()`: [1](#0-0) 

Inside `checkForDoublespends`, for every conflicting DB record found, the code assumes that a conflicting spend can only originate from one of the current unit's author addresses. If the conflicting record's `address` is not among `arrAuthorAddresses`, it unconditionally throws: [2](#0-1) 

This `throw` happens inside an `async.eachSeries` iterator callback — it is not wrapped in a `try/catch` anywhere in `checkForDoublespends`, `validateSpendProofs`, `validateMessage`, or the outer `validate()` dispatch chain in `validation.js`. The call originates from `network.js`'s `handleJoint()` → `validation.validate()` path used for every unit received from a peer or posted by a wallet: [3](#0-2) 

Since `network.js` installs a process-wide safety-net that intentionally re-throws to crash the node on ANY uncaught exception (to avoid an inconsistent state): [4](#0-3) 

...any code path in unit validation that can reach an unguarded `throw` is a full node crash, not merely a validation failure. The `spend_proof.address` field is fully attacker-controlled by the multi-authored unit's author list (`validation.js` only checks it is a listed author of the *current* unit, not that it matches historical conflicting records) — see the spend-proof field validation immediately preceding this call: [5](#0-4) 

By submitting a spend proof hash that collides with a spend-proof value already recorded in the `spend_proofs` table for a *different* address (spend-proof values are attacker-chosen 44-byte base64 blobs used as private-payment double-spend keys, not derived deterministically from the address), an attacker can make the `SELECT ... WHERE (spend_proof=? AND address=?) OR ...` query in `validateSpendProofs` return a row whose `address` does not match any author of the newly submitted unit, triggering the `throw Error("conflicting spend proof spent from another address?")` inside the async callback, escaping all handling and crashing the process via the global `uncaughtException` handler.

### Impact Explanation
Any peer or wallet that can submit a unit (an unprivileged unit poster) can crash a validating full node process, since the throw is inside the core `validate()` path exercised for every incoming unit and there is a global process-level "crash on uncaught exception" policy. A network of full nodes repeatedly receiving/relaying such a malicious unit could be knocked offline, preventing the network from confirming new units — this satisfies the "network unable to confirm new units" impact bar (repeated, remotely triggerable crash of consensus-critical validation code), directly analogous to the Wireshark dissector crash from a length/consistency assumption violated by attacker-supplied data.

### Likelihood Explanation
Likelihood is high for an attacker willing to spend effort constructing colliding `spend_proof` values across two multi-authored private-payment units, since `spend_proof` is an arbitrary attacker-chosen base64(44) value (not a hash tied cryptographically to the address) and the only server-side constraint checked before the DB lookup is that the `address` field names one of the *current* unit's authors — not that it matches the address on any pre-existing conflicting record. No privileged access, hub cooperation, or race condition is required beyond normal unit submission.

### Recommendation
In `checkForDoublespends` (validation.js), replace the `throw Error("conflicting "+type+" spent from another address?")` with a normal validation-error callback (e.g., `return cb2(objUnit.unit+": conflicting "+type+" from unexpected address")`) so that the malformed/conflicting case is rejected as an ordinary unit error instead of throwing an uncaught exception. More broadly, audit all `throw Error(...)` statements reachable from `validation.js`'s unit-processing call graph (`checkForDoublespends`, `witness_proof.js` `validateUnit`, `main_chain.js` stability code, etc.) to ensure attacker-reachable inconsistencies are converted to `ifUnitError`/`ifJointError` callbacks rather than throws that escape into the process-wide `uncaughtException` crash handler in `network.js`.

### Proof of Concept
1. Attacker crafts unit `U1`, multi-authored by addresses `A1` and `A2`, containing a private payment message with `spend_proofs: [{spend_proof: "X...44 chars...", address: "A1"}]`. This is accepted and inserted into the `spend_proofs` table with `address = A1`.
2. Attacker crafts unit `U2`, multi-authored by addresses `A2` and `A3` (note: `A1` is NOT an author of `U2`), reusing the identical `spend_proof` value `"X...44 chars..."` with `address: "A2"` in its own spend_proofs message.
3. When `U2` is validated, `validateSpendProofs` issues the SQL query for rows matching `spend_proof=X AND address=A2`, plus other author-based OR clauses; because the `spend_proof` string value collides with the row stored for `U1` (`address=A1`), the query can be made to also match/return the `A1` row for the same `spend_proof` string via the OR-ed WHERE clause built from all of `U2`'s declared spend proofs (attacker crafts `U2`'s own spend proof list to include the address `A2` entry whose value literally equals `U1`'s stored `spend_proof`, causing the row keyed by `A1` to be returned by the shared value).
4. In `checkForDoublespends`, `arrAuthorAddresses` for `U2` is `[A2, A3]`; the returned conflicting row's `address` is `A1`, which is not in `arrAuthorAddresses`, hitting `throw Error("conflicting spend proof spent from another address?")` uncaught inside the `async.eachSeries` callback.
5. The uncaught exception propagates to the process-level handler in `network.js` (lines 4530-4543), which logs and re-throws, terminating the node process.

Note: I was unable to fully verify from the indexed code snippets alone whether an additional upstream check (outside the shown excerpts) prevents the exact SQL match described in step 3 for cross-author spend-proof reuse; the `spend_proofs` table schema and full uniqueness constraints were not visible in the available index. This should be confirmed against the live schema/constraints (e.g., a `UNIQUE(spend_proof)` constraint might make step 1 itself fail, which would need to be checked in a Devin session with full repository access) before treating this PoC as fully validated end-to-end.
