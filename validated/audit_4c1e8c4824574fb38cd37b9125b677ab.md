I found a concrete, in-scope analog: `is_valid_signed_package()` in AA oscript, which calls `signed_message.validateSignedMessage()`, can validate a "signed package" whose `authors[i].definition` hashes only to the *bare* `authors[i].address`, with no check against the address's *current* on-chain definition when the package is not "network-aware" (no `last_ball_unit`). This mirrors the GitLab bug's core flaw: a credential that was valid at issuance keeps authorizing actions after the identity's current authorization state has changed, because the check validates the credential in isolation instead of against the live/latest authoritative state.

### Title
AA `is_valid_signed_package()` accepts a signed package proving control of an address's *original* key set even after the address revoked it via `address_definition_change`, enabling authorization bypass in AA logic - (File: signed_message.js)

### Summary
`is_valid_signed_package()` (oscript, evaluated by AA triggers) delegates to `signed_message.validateSignedMessage()` [1](#0-0) . When the signed package supplied by the trigger does not include `last_ball_unit`, `validateSignedMessage` treats it as non-network-aware and only checks that `hash(author.definition) === author.address` — i.e. that the definition is the *original* definition tied to the address's chash — without ever consulting `storage.readDefinitionByAddress()` to see whether that address has since changed its definition (revoked/rotated keys) via `address_definition_change`. [2](#0-1) 

### Finding Description
In the network-aware branch, `validateOrReadDefinition()` correctly resolves the address's definition as of a specific `last_ball_mci` via `storage.readDefinitionByAddress()`, which accounts for any stable `address_definition_change` [3](#0-2) .

In the non-network-aware branch (no `last_ball_unit` field in the package), the code instead does:
```
if (objectHash.getChash160(objAuthor.definition) !== objAuthor.address)
    return handleResult("wrong definition...");
cb(objAuthor.definition, (mci >= constants.pemCurvesFixMci) ? mci : -1, 0);
``` [2](#0-1) 

This only proves that `objAuthor.definition` is *an* array whose hash equals the address — which is trivially true for the address's very first (initial) definition, since by construction `address === chash160(initial_definition)`. It never checks whether that initial definition is still the address's *current, active* one. If the address owner later executes an `address_definition_change` to rotate/replace their key (e.g., because the original key is believed compromised, or governance/multisig membership changed), the *old* key material can still produce a signed package that `is_valid_signed_package()` will accept as valid proof of "signed by this address," because the check never consults `address_definition_changes`/`readDefinitionByAddress`.

This exactly parallels CVE-2021-39872: a credential/authenticator issued under an earlier authorization state (old password/old key) continues to grant access after that authorization state has been superseded, because the verifying code checks the credential's internal self-consistency rather than the subject's current authoritative state.

`is_valid_signed_package` is explicitly usable in AA formulas (guarded only by an mci-based feature flag to prevent recursive misuse in non-AA sig conditions) [4](#0-3) , and is validated for use inside AA definitions at `definition.js`'s `sig`/formula opcodes ecosystem — any AA author can write logic that trusts `is_valid_signed_package(pkg, addr)` as an authorization gate (e.g., "if this package is validly signed by address X, release funds / update state").

### Impact Explanation
An AA that uses `is_valid_signed_package(trigger.data.signed_package, some_address)` as an authorization/identity check (a documented, supported oscript pattern per the test suite [5](#0-4) ) can be tricked into treating a stale, revoked key as still-valid proof of control over `some_address`. If `some_address`'s owner rotated their definition (e.g., after suspecting key compromise, changing multisig cosigners, or transferring control), the holder of the *old, revoked* private key can still forge a signed package accepted by the AA, because the AA-side check does not require `last_ball_unit` and thus never consults the address's current on-chain definition state.

This can lead to AA fund loss/misappropriation or unauthorized state transitions gated on "this package is signed by address X" checks, wherever the AA developer relies on `is_valid_signed_package` without independently re-verifying current definition ownership. Since anyone can define and fund an AA with this pattern, and the trigger sender fully controls the `signed_package` object contents (it comes from `trigger.data`), an attacker who once held keys for an address (their own prior definition, or one they can construct) can exploit definition-change timing to keep using old credentials indefinitely for AA authorization purposes, even though on-ledger spending from that address is correctly protected by `readDefinitionByAddress`-based checks elsewhere.

### Likelihood Explanation
Reachable by any unprivileged AA trigger sender who controls the `signed_package` payload in `trigger.data`, and depends only on the target AA author's choice to use `is_valid_signed_package` without a `last_ball_unit`/freshness requirement — a documented and tested code path [5](#0-4) . No hub, peer, or node-trust assumptions are required; it is a pure oscript/definition semantics issue.

### Recommendation
In the non-network-aware branch of `validateOrReadDefinition()` (`signed_message.js`), when a caller needs assurance that the supplied definition is the address's *current* active definition (not merely a valid preimage of the address chash), the function should require `last_ball_unit`/network-aware mode, or perform a `storage.readDefinitionByAddress()` lookup (using the current/latest known mci) even in the non-network-aware path, rejecting packages whose definition doesn't match the address's most recent stable definition. Alternatively, `is_valid_signed_package` in oscript should reject packages lacking `last_ball_unit` outright, forcing all AA-facing signed-package checks through the definition-change–aware path.

### Proof of Concept
1. Address `A` is created with `definition = ["sig", {pubkey: P1}]` (chash160 of this definition equals `A`).
2. Owner of `A` later posts a stable `address_definition_change` message changing `A`'s definition to `["sig", {pubkey: P2}]`, intending to revoke `P1`.
3. An entity that still possesses the private key for `P1` builds a signed package: `{signed_message: "...", authors: [{address: A, definition: ["sig", {pubkey: P1}], authentifiers: {r: sig_with_P1}}]}` — deliberately omitting `last_ball_unit`.
4. This package is submitted as `trigger.data.signed_package` to an AA that evaluates `is_valid_signed_package(trigger.data.signed_package, A)`.
5. `validateSignedMessage()` takes the non-network-aware branch, checks only `chash160(P1-definition) === A` (true), and calls back with the definition — never checking that `A`'s definition is now `P2`. `is_valid_signed_package` returns `true`, letting the attacker's stale `P1` key pass as valid authorization for address `A` despite the revocation.
