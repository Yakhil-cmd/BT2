### Title
Insertion of Sensitive Private-Payment and Correspondence Data into Log Files via Unconditional `console.log` of Decrypted/Outgoing Device Messages - (File: device.js)

### Summary
`device.js` unconditionally logs the full plaintext content of every device message it sends or receives — including private-payment chains (with blinding factors), textcoin mnemonics, and wallet/asset data — via bare `console.log` calls that are not gated by a debug flag. This mirrors CVE-2023-0815 (OpenNMS logging Jetty request bodies containing credentials at debug level): here, ocore permanently writes sensitive payment/asset secrets to the node's log output on every message exchange, not only under a special debug mode.

### Finding Description
When a paired correspondent (a legitimate private-payment counterparty) sends a device message — e.g. a private-payment chain via `sendPrivatePayments`/`forwardPrivateChainsToDevices` — the receiving node decrypts it in `decryptPackage()` and immediately logs the entire decrypted plaintext: [1](#0-0) 

This decrypted payload for private asset transfers contains the `blinding` factor and other secret payment fields, as seen in the structure saved/consumed elsewhere in the private-payment pipeline: [2](#0-1) [3](#0-2) 

Symmetrically, on the sending side, `reliablySendPreparedMessageToHub()` logs the full outgoing JSON body (before encryption) to console, which can include `private_payloads` (blinding factors, private outputs) for `sign` and `private_payments` messages: [4](#0-3) [5](#0-4) [6](#0-5) 

Additionally, redeemable textcoin mnemonics (bearer secrets that grant control of funds) are printed in plaintext to the log on claim-back: [7](#0-6) 

None of these logging statements are conditioned on a debug/verbose flag — they execute on every normal message send/receive in production, unlike the OpenNMS advisory where the leak required an operator to explicitly raise the log level to `DEBUG`. This makes the exposure broader: any deployment that persists stdout/stderr (common for server/wallet-hub processes run under systemd, pm2, Docker, or shell redirection) will accumulate private payment blinding factors and textcoin mnemonics in plaintext log files by default.

### Impact Explanation
Blinding factors and textcoin mnemonics are the cryptographic secrets that authorize spending of private (indivisible/divisible) asset outputs and bearer textcoins, respectively. Persisting them in log files:
- Exposes them to anyone with read access to logs (log aggregation systems, support/debug bundles, backup archives, misconfigured log servers) — exactly the class of exposure CVE-2023-0815 addresses.
- Enables an attacker who obtains the logs to reconstruct/steal private-asset outputs or unclaimed textcoins, resulting in concrete unauthorized spending/fund loss for the wallet operator and its correspondents.

This satisfies the "concrete unauthorized spending" / "private-payment counterparty" impact bar (Medium severity, matching the CVSS profile of the source advisory: confidentiality-impacting, no direct integrity/availability impact, network-reachable, low complexity).

### Likelihood Explanation
The logging is unconditional (not debug-gated), so it triggers on every ordinary private-payment message exchange or textcoin claim-back that occurs as part of normal wallet operation — a paired correspondent needs only to send a legitimate private-payment chain or textcoin, both routine actions, to cause the counterparty's node to persist the associated secrets to disk. No malicious peer/hub/network behavior is required, satisfying the in-scope actor constraints (private-payment counterparty, paired device).

### Recommendation
- Remove or redact `console.log` statements that print full decrypted/outgoing device-message bodies (`device.js` `decryptPackage`, `reliablySendPreparedMessageToHub`, `createEncryptedPackage`).
- Never log `assocPrivatePayloads`, `blinding`, or `mnemonic` fields, even partially; log only non-sensitive metadata (message subject, hash, sizes).
- If verbose message tracing is needed for debugging, gate it behind an explicit, off-by-default debug flag and strip sensitive fields before logging.

### Proof of Concept
1. Pair two wallets (A and B) as private-payment counterparties.
2. From wallet A, send a private (indivisible/divisible) asset payment chain to wallet B using the normal payment flow (`sendPrivatePayments`/`forwardPrivateChainsToDevices`), or send a textcoin later claimed back via `claimBackOldTextcoins`.
3. On wallet B's (or the claiming node's) host, inspect the process's stdout/log file.
4. Observe the full decrypted JSON body, including `payload.outputs[].blinding` and/or the plaintext `mnemonic`, printed via the `console.log("decrypted: "+decrypted_message)` / `console.log("claimed back mnemonic "+row.mnemonic...)` lines cited above — demonstrating the secret is now recoverable from log storage independent of the encrypted channel.
