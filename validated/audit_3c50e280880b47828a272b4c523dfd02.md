## Title
Burnchain `stack-stx` operations always bypass signer signature verification and rely solely on prior on-chain authorization - (File: stackslib/src/chainstate/stacks/db/blocks.rs, stackslib/src/chainstate/stacks/boot/pox-4.clar)

### Summary
`collect_pox_4_stacking_args` hard-codes `signer-sig` to `none` for every Bitcoin-originated `stack-stx` operation [2](#0-1) . This forces `verify-signer-key-sig` in `pox-4.clar` into its "no signature" branch, which does not cryptographically bind the on-chain `signer-key` to the actual stacker's authorization — it instead checks the `signer-key-authorizations` map for a pre-existing `allow-signer-key-authorization` entry [3](#0-2) .

### Finding Description
The wallet report describes an unvalidated external-data trust issue: a client trusted an unauthenticated payload (the server's token list) to decide what value gets added to a user's balance, without validating it against the "true" state. The analogous pattern here is that the Bitcoin `StackStxOp` payload — an unauthenticated, attacker-controlled field set (`signer_key`, `max_amount`, `auth_id`) parsed straight out of arbitrary burnchain transaction data via `StackStxOp::parse_data` [4](#0-3)  — is fed into the PoX-4 contract's `stack-stx` entry point with `signer-sig` forced to `none`, meaning the contract never verifies a `secp256k1-recover?` signature proving the named `signer-key` actually endorses this specific `pox-addr`/`reward-cycle`/`amount`/`auth-id` combination [5](#0-4) .

Because `signer-sig` is `none`, `verify-signer-key-sig` requires only that an entry already exists in `signer-key-authorizations` for that exact `(signer-key, reward-cycle, period, topic, pox-addr, auth-id, max-amount)` tuple — meaning the *only* thing anchoring `signer-key` to the transaction is whatever the burn-op sender chose to write into the Bitcoin transaction's data field, since `sender` (the Stacks principal locking STX) comes from the `PreStxOp` and is otherwise unrelated to `signer_key`. This lets any Bitcoin-transaction sender specify an arbitrary `signer-key` for the `stack-stx` call, as long as a matching authorization was separately added (typically by that same signer via `set-signer-key-authorization`), but the burn-op path itself performs no proof that this particular `stack-stx` (with this specific `amount-ustx`, `pox-addr`, `reward-cycle`) was actually approved by the entity holding the signer key beyond the coarse pre-existing authorization record.

### Impact Explanation
This breaks the equality "a stacking action that credits reward-set weight to `signer-key`" must be "authorised by the entity controlling `signer-key`". Since burnchain `stack-stx` ops always skip cryptographic signature verification (forced `none`), the security boundary collapses entirely onto whether an `allow-signer-key-authorization` entry was pre-populated — which is a coarser, reusable authorization rather than a per-transaction cryptographic proof tying `amount-ustx`/`pox-addr`/`reward-cycle` to signer intent. An attacker who can get an authorization entry created for a `signer-key` (e.g. via social engineering, a leaked authorization, or a previous `signer-sig`-consuming flow that inserts an authorization) could reuse it to stack an unintended `pox-addr`/`amount` combination against that signer's weight in the reward set, since the burnchain path bypasses the signature that would otherwise bind the intent precisely.

### Likelihood Explanation
Requires that some `signer-key-authorizations` entry exist and be reusable via the burnchain path with attacker-chosen `sender`/PreStxOp; exploitability depends on whether such authorizations are ever added without `signer-sig` in practice (e.g., via `set-signer-key-authorization`, an admin/pool operator action). It is not clear from available code whether `set-signer-key-authorization` requires the signer's own tx-sender, which would limit but not eliminate the risk given the burn-op path's unconditional `none` sig.

### Recommendation
Require that `collect_pox_4_stacking_args` pass through an actual `signer-sig` recovered from the burnchain operation payload (extend `StackStxOp::parse_data` to carry a signature field), or otherwise cryptographically bind the `signer_key` field in the Bitcoin transaction to the specific `stacked_ustx`/`reward_addr`/`num_cycles` via a verifiable signature before calling `stack-stx`, rather than relying purely on the coarser `signer-key-authorizations` map lookup for burn-chain-originated stacking.

### Proof of Concept
1. Attacker (or colluding signer) causes a `signer-key-authorizations` entry to be inserted for `signer-key` X covering `(pox-addr, reward-cycle, period, topic="stack-stx", auth-id, max-amount)`.
2. Attacker crafts a Bitcoin `PreStxOp` + `StackStxOp` pair with the desired `stacked_ustx`, `pox-addr`, `num_cycles`, and sets the `signer_key` field in the op data to X, per `StackStxOp::parse_data` wire format [6](#0-5) .
3. `process_stacking_ops` calls `stack-stx` with `signer-sig = none` via `collect_pox_4_stacking_args` [7](#0-6) .
4. `verify-signer-key-sig` succeeds via the map-lookup branch without any per-transaction cryptographic check binding this exact `stack-stx` call to signer X's intent [3](#0-2) , crediting signer X's weight/reward-slot to a stacking action it may not have specifically authorized.

**Note on confidence**: This analysis is limited by not being able to confirm the exact call-site/authorization conditions for `set-signer-key-authorization` (who can call it and under what constraints) within the indexed context, which affects how easily the coarse authorization entry can be created by an attacker in the first place. A full Devin session with complete file access would be needed to trace all callers of `signer-key-authorizations` map writes to conclusively determine exploitability severity.

    pub fn collect_pox_4_stacking_args(op: &StackStxOp) -> Result<Vec<Value>, String> {
        let signer_key = match &op.signer_key {
            Some(signer_key) => match Value::buff_from(signer_key.as_bytes().to_vec()) {
                Ok(signer_key) => signer_key,
                Err(_) => {
                    return Err("Invalid signer_key".into());
                }
            },
            _ => return Err("Invalid signer key".into()),
        };

        let max_amount_value = match op.max_amount {
            Some(max_amount) => Value::UInt(max_amount),
            None => return Err("Missing max_amount".into()),
        };

        let auth_id_value = match op.auth_id {
            Some(auth_id) => Value::UInt(u128::from(auth_id)),
            None => return Err("Missing auth_id".into()),
        };

        Ok(vec![
            Value::none(),
            signer_key,
            max_amount_value,
            auth_id_value,
        ])
    }

    fn parse_data(data: &[u8]) -> Option<ParsedData> {
        /*
            Wire format:
            0      2  3                             19           20                  53                 69                        73
            |------|--|-----------------------------|------------|-------------------|-------------------|-------------------------|
            magic  op         uSTX to lock (u128)     cycles (u8)     signer key (optional)   max_amount (optional u128)  auth_id (optional u32)

             Note that `data` is missing the first 3 bytes -- the magic and op have been stripped

             The values ustx to lock and cycles are in big-endian order.

             parent-delta and parent-txoff will both be 0 if this block builds off of the genesis block.
        */

        if data.len() < 17 {
            // too short
            warn!(
                "StacksStxOp payload is malformed ({} bytes, expected {} or more)",
                data.len(),
                17
            );
            return None;
        }

        let stacked_ustx = parse_u128_from_be(data.get(0..16)?).unwrap();
        let num_cycles = *data.get(16)?;

        let mut signer_key: Option<StacksPublicKeyBuffer> = None;
        let mut max_amount: Option<u128> = None;
        let mut auth_id: Option<u32> = None;

        if data.len() >= 50 {
            signer_key = Some(StacksPublicKeyBuffer::from(data.get(17..50)?));
        }
        if data.len() >= 66 {
            let Some(amt) = parse_u128_from_be(data.get(50..66)?) else {
                return None;
            };
            max_amount = Some(amt);
        }
        if data.len() >= 70 {
            let Some(id) = parse_u32_from_be(data.get(66..70)?) else {
                return None;
            };
            auth_id = Some(id);
        }

        Some(ParsedData {
            stacked_ustx,
            num_cycles,
            signer_key,
            max_amount,
            auth_id,
        })
