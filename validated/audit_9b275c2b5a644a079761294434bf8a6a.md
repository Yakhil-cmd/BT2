### Title
Attacker-controlled swap route executes arbitrary contract code under the caller's authorization tree, draining unrelated wallet funds - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Analogous to the MaxKB MCP RCE (untrusted input reaching a code-execution sink), the controller's router strategies execute venue/pool contracts whose addresses come entirely from the user-supplied `StrategySwap` payload. Neither the controller nor the router keeps an allowlist of the pool/token addresses a route names, so a crafted route places attacker-deployed code on the call stack *inside* the victim's `require_auth` tree. Simulation records any `token.transfer(victim, …)` the rogue contract makes as a child of the victim's signed authorization, so signing the swap silently authorizes theft of the victim's entire unrelated wallet balances — far beyond the routed amount.

### Finding Description
`swap_tokens` in `contracts/controller/src/strategies/swap.rs:13-55` forwards the caller-supplied `swap` payload verbatim to `router.execute_strategy(&controller, &amount_in, swap)` after granting only a single exact input transfer. The threat model confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" (`docs/explanation/threat-model.md:154-165`). All router-mediated entrypoints are affected: `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and any direct `execute_strategy` call.

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` proves the end-to-end path: `RogueHopPool::swap` (line 62-71) calls `token::Client::transfer(&victim, &to, &amount)` on an unrelated wallet token, and the recorded auth tree at lines 206-222 shows that stolen transfer appearing as a `sub_invocation` of the victim's `swap_collateral` root — the swap still pays fair output and passes all risk gates while Alice's wallet is emptied.

Root cause: payload-supplied contract addresses are invoked without allowlisting, and Soroban's authorization model folds the rogue contract's `require_auth` calls into the caller's signed tree. Neither the controller's measured output check (`verify_router_output`), the router's `min_out`, nor the final health-factor gate bounds this loss, because the stolen funds never touch the routed amounts.

### Impact Explanation
Theft of user funds beyond the operation's scope. A victim who signs a malicious route loses arbitrary balances of arbitrary tokens in their wallet (bounded only by what the token contracts allow `transfer` on), while the swap itself settles correctly. This applies to every swap-using strategy and to direct router users.

### Likelihood Explanation
Requires the victim to submit an attacker-built route payload — analogous to the CVE's `UI:R`/`AC:H` rating. Routes are opaque packed XDR produced off-chain, and `simulateTransaction` automatically constructs the full auth tree including the poisoned child, so a wallet or client that does not decode and inspect the route's venue addresses and the recorded sub-invocations will present a normal-looking signature. The threat model explicitly assigns the mitigation to clients ("a client must decode the route it signs"), which is an ecosystem assumption rather than an on-chain control.

### Recommendation
Enforce on-chain rather than relying on client-side route inspection: maintain a governance-managed venue/pool allowlist in the swap-aggregator (or pin per-venue pool registries), and reject routes naming unlisted contracts. Alternatively, have the controller sandbox the router call so that sub-authorizations for `token.transfer` from the caller cannot attach — e.g., require the router to pull input via `transfer_from`/allowance from a dedicated authorization context rather than nesting under the caller's auth tree. Short of contract changes, document that wallets must refuse authorization trees containing children beyond the single expected input transfer.

### Proof of Concept
The repository already contains a working demonstration: `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs:194-227`. A router/pool double pays fair `token_out` output so `swap_collateral` succeeds and the account stays healthy, while the pool contract named by the payload transfers the victim's unrelated `wallet_token` balance to the attacker. The assertion at line 222 confirms the stolen transfer is recorded as a child of the victim's `swap_collateral` auth entry — a signature produced by ordinary simulation therefore authorizes the drain.
