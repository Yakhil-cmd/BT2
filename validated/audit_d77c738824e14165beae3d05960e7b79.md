### Title
Webhook signature is verified against the organization declared in the payload, but `StatusHandler`/`PushHandler` write to repositories/commits with no matching repository check - cross-organization commit-status forgery enabling unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using a field taken from the attacker-controlled JSON body itself (`repository.owner.login`, falling back to `organization.login`), not from any value bound independently to the signature. The handlers that subsequently mutate state (`PushHandler`, `StatusHandler`, etc.) use a *different* field from that same body (`repository.full_name`, or for `StatusHandler`, only `sha` with no repository scoping at all) to decide what to write. Nothing enforces that the organization used to select/verify the secret matches the repository/commit that is actually acted upon.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) [2](#0-1) 

```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This picks the `webhook_secret` to check the signature against based on a value the attacker fully controls inside the very payload being verified. In a multi-org Shipit deployment (supported and documented via `secrets_double_github_app.yml`, `Shipit.github_organizations`, `Shipit.github_app_config`), each organization has its own independent `webhook_secret`. An attacker who legitimately administers the GitHub App/webhook for **any one** of the configured organizations (e.g. their own, lower-trust org) knows that org's `webhook_secret` and can craft an arbitrary JSON body, sign it with their own secret, and set `repository.owner.login` to their own org so `verify_signature` picks their own secret and passes.

Once past `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs the handler on the raw JSON, using different fields: [3](#0-2) 

`Handler#stacks` resolves the target repository via `payload.dig('repository', 'full_name')`, completely independent from the `owner.login` field used for signature-org selection - an attacker can set `full_name` to any other organization's repository string without breaking their own signature.

`StatusHandler` is worse - it performs **no repository check whatsoever**: [4](#0-3) 

```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit` is looked up globally by `sha` across the entire installation, regardless of which repository/stack it belongs to. So any organization whose `webhook_secret` the attacker legitimately possesses is sufficient to forge a `status` event and set an arbitrary CI status (`success`/`failure`/state, `context`, `target_url`, `description`) on **any commit tracked by any stack in the whole Shipit instance**, including stacks belonging to organizations the attacker has no relationship with.

The binding being broken is exactly: **the organization that authenticated the webhook request (via its own `webhook_secret`) versus the repository/commit that is actually written** by the handler.

### Impact Explanation
`deploy_spec.rb` gates deploys using commit statuses (`required_statuses`, `blocking_statuses`, `soft_failing_statuses`, `release_status_context`), and `Commit#deployable?`/status checks determine whether a deploy can be triggered: [5](#0-4) 

By forging a "success" status for a required/blocking CI context on a target commit belonging to a different organization's stack, an attacker who only controls their own org's `webhook_secret` can unblock or force through an otherwise CI-gated deploy on a completely unrelated repository - an unauthorized deploy, matching the Critical impact bar defined by the rules. `PushHandler`/other handlers using `repository.full_name` similarly allow triggering `stack.sync_github` on repositories outside the attacker's own organization by decoupling the signing-org field from the acted-upon-repository field.

### Likelihood Explanation
Requires only that the attacker legitimately controls a GitHub App/webhook configuration for at least one organization hosted on the same shared Shipit instance (a normal, unprivileged-relative-to-other-tenants scenario supported by this engine's multi-org config, evidenced by `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github_organizations`). No access to the victim organization's secret, no Shipit session, and no API token is needed - only crafting a raw JSON body and signing it with a secret the attacker already legitimately owns. This is a realistic likelihood for any deployment onboarding more than one GitHub organization.

### Recommendation
- In `WebhooksController#verify_signature`, after verifying the signature, cross-check that the resolved `Repository`/`Stack` referenced by the payload (`repository.full_name`) actually belongs to the same organization (`repository_owner`) whose secret validated the signature; reject if they diverge.
- In `StatusHandler#process`, scope the `Commit` lookup to a repository/stack derived from the verified organization instead of a global `Commit.where(sha: params.sha)` across the whole installation.
- More generally, bind webhook verification and the payload attributes used for mutation to the same, single source of truth (e.g., always resolve org from `repository.full_name`'s owner segment) rather than allowing independent attacker-controlled fields.

### Proof of Concept
1. Stand up Shipit with two configured GitHub organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as supported by `secrets_double_github_app.yml`).
2. As the legitimate administrator of `OrgA`'s GitHub App, obtain `OrgA`'s `webhook_secret`.
3. Craft a `status` event JSON body:
   ```json
   {
     "sha": "<sha of a commit belonging to a stack under OrgB>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/some-repo" }
   }
   ```
4. Sign the raw body with `OrgA`'s `webhook_secret` using HMAC-SHA1, and POST it to `/github/webhooks` with headers `X-Github-Event: status` and `X-Hub-Signature: sha1=<signature>`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and verifies successfully since the attacker signed with `OrgA`'s real secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `OrgB` commit (no repository scoping), and calls `commit.create_status_from_github!(params)`, marking a required CI check as `success` on a commit that belongs to an organization the attacker has no legitimate access to - potentially unblocking a deploy gated on that status.
