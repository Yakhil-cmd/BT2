### Title
`GITHUB_TOKEN` (and other secret-bearing keys) present in `Command#env` are interpolated into literal argv via `$VAR` syntax in attacker-controlled `shipit.yml` steps - ([File: lib/shipit/command.rb], [File: lib/shipit/commands.rb], [File: lib/shipit/environment_variables.rb])

### Summary
`Command#interpolate_environment_variables` calls `EnvironmentVariables#interpolate`, which substitutes any `$WORD` token in a shell step string with the corresponding value from the full `env` hash supplied to `Command.new`, with no whitelist. That `env` hash is built by `Commands#base_env` and always includes `GITHUB_TOKEN`, so a step string that is attacker-controlled (via `shipit.yml`'s `deploy.override`/`rollback.override`/task steps on a stack whose spec resolution can be influenced by the attacker) can contain literal `$GITHUB_TOKEN` and have the real token substituted into the process argv, which is then streamed as task output.

### Finding Description
The binding claimed safe is: `set(env keys interpolatable into argv via $VAR) == set(env keys safe for an attacker to read)`. That binding is false.

- `Commands#base_env` unconditionally injects the credential into every command's environment: [1](#0-0) 
- `TaskCommands#env` / `DeployCommands#env` merge `super` (which includes `base_env`'s `GITHUB_TOKEN`) with stack env, task env and deploy-spec `machine_env`, and this merged hash is passed as `env:` to every `Command.new(command_line, env:, chdir:)` built from `steps`: [2](#0-1) 
- `Command#interpolate_environment_variables`/`interpolated_arguments` run over `@args` (the raw step strings) right before `PTY.spawn`: [3](#0-2) [4](#0-3) 
- `EnvironmentVariables#interpolate` performs a blanket `gsub` substitution of any `$WORD` pattern against `@env` with no permit/whitelist check: [5](#0-4) 
- The only whitelist mechanism in this class, `EnvironmentVariables#permit`, is applied elsewhere — solely to *user-supplied deploy/rollback variables* (`DeploySpec#filter_deploy_envs`/`filter_rollback_envs`), not to the set of keys eligible for `$VAR` interpolation inside step strings: [6](#0-5) 

Root cause: the step strings (`deploy.override`, `rollback.override`, task `steps`, `dependencies.override`, `fetch`) are taken directly from `shipit.yml`'s `config('deploy','override')` etc. with no sanitization of `$VAR` tokens, and are combined with a full-privilege env hash that includes `GITHUB_TOKEN`. There is no separate "public" vs "secret" env namespace; `interpolate` treats the entire `Command#env` as fair game for substitution, so any key present at spawn time — including credentials — is interpolatable, confirmed by the existing test asserting interpolation of arbitrary `$FOO`-style variables: [7](#0-6) 

This finding is scoped as downstream of the review-stack precedence bug referenced in the prompt: whatever mechanism lets an attacker's `shipit.yml` content take effect for a stack (review stack or otherwise) also lets them control the exact step string executed with the privileged env, e.g. a step of `echo $GITHUB_TOKEN`.

None of the listed guards (`verify_signature`, `force_github_authentication`, `EnvironmentVariables#permit`, model validators) address this: `permit` is never invoked on the path from `steps` → `Command.new` → `interpolate_environment_variables`, only on the separate deploy/rollback "variables" feature.

### Impact Explanation
If reachable (i.e., if the referenced review-stack precedence bug indeed lets an attacker's `shipit.yml` step content execute against a stack with a real `GITHUB_TOKEN` in scope), the attacker's step is spawned with the literal token value substituted into argv, and that argv/output is streamed back as task output visible to the PR author viewing their own task/stack page. This is credential exfiltration of `GITHUB_TOKEN`, matching the Critical impact category ("exfiltration of GITHUB_TOKEN ... or deploy-time secrets"). It is repeatable on every deploy/task run against any stack whose spec resolution is influenced by the attacker-controlled branch/PR, and the token scope (org/repo level GitHub App or PAT token) determines blast radius across that org's repositories.

### Likelihood Explanation
Preconditions: the attacker must be able to get an arbitrary step string into effect for a stack run (this is the separate "review-stack precedence bug" referenced by the prompt, not re-verified here) and the task/deploy must actually run (an unprivileged PR author cannot themselves trigger a deploy on stacks they don't control, but review-stack automatic provisioning/CI runs may execute steps without additional authorization). Given that precondition holds, crafting the payload is trivial (`echo $GITHUB_TOKEN` or embedding it in any override step) and the exploit is deterministic and repeatable every time the vulnerable step runs.

### Recommendation
- Do not interpolate arbitrary `$VAR` tokens from the full privileged env hash into step strings sourced from repository-controlled `shipit.yml`. Restrict `EnvironmentVariables#interpolate` to a whitelist (reuse `permit`) built from `deploy_variables`/`rollback_variables`/`machine_env` only — i.e., attacker-declared variables, never `GITHUB_TOKEN`, `GITHUB_DOMAIN`, or other Shipit-injected credentials.
- Alternatively, pass credential-bearing keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, etc.) to the spawned process only via `unbundled_env` merge at `PTY.spawn` time (already done) while excluding them from the `@env` hash used for `$VAR` string interpolation, so they remain available to the invoked program's actual environment but are never substitutable into argv/logs.
- Add a hard denylist in `EnvironmentVariables#interpolate` rejecting any variable name that is not explicitly permitted.

### Proof of Concept
```ruby
# test/unit/command_test.rb (extend existing suite)
test "#interpolate_environment_variables can leak secret-bearing env keys into argv" do
  command = Shipit::Command.new(
    'echo $GITHUB_TOKEN',
    env: { 'GITHUB_TOKEN' => 'super-secret-token' },
    chdir: '.'
  )
  # Binding under test: env keys interpolatable into argv == env keys safe for attacker to read.
  # LHS: keys reachable through interpolation
  interpolated = command.interpolated_arguments
  # RHS: keys that must never be exposed to an attacker-controlled step string
  assert_includes interpolated.join(' '), 'super-secret-token', "secret value leaked into literal argv"
  output = command.run
  assert_includes output, 'super-secret-token', "secret leaked into task output stream"
end
```
This demonstrates that whatever key is present in `Command#env` at spawn time — including `GITHUB_TOKEN` as populated by `Commands#base_env` in production — is interpolatable into argv/task output with no whitelist, confirming the broken binding.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
