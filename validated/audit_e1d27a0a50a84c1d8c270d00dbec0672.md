### Title
Commit-status webhook handler writes state for any tracked commit unscoped by the organization/repository that authenticated the request - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's webhook signature verification is bound to the *organization* named in the payload's `repository.owner.login` field, which is used only to select which GitHub App configuration (and its `webhook_secret`) to verify against. Once verification passes, the `status` event handler mutates state using a completely different, unbound key — the raw commit `sha` — with no check that the SHA actually belongs to the organization/repository that was authenticated. This is the same class of bug as the report: the value used to authenticate ("coverage"/health, or here, org+secret) is decoupled from the value that is actually acted upon ("slashable"/state-mutating scope, here the `Commit` row), letting an attacker write CI status data for commits outside the boundary that was verified.

### Finding Description
`WebhooksController#verify_signature` resolves which GitHub App/secret to use purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

The actual byte-for-byte signature check is delegated to `GitHubApp#verify_webhook_signature`, which contains an unconditional bypass when no `webhook_secret` is configured for the resolved organization: [3](#0-2) 

A blank `webhook_secret` is an explicitly supported configuration value (shown in `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`, and `docs/setup.md`), and multiple GitHub organizations/App configs can coexist in one Shipit instance (`Shipit.github(organization:)`), each independently keyed off the attacker-controlled `repository.owner.login`/`organization.login` field of the payload.

Once past `verify_signature`, `WebhooksController#create` dispatches the parsed, unauthenticated-content `params` to the registered handler for the event, with no additional scoping: [4](#0-3) 

`StatusHandler#process` — unlike `PushHandler`, which scopes stacks via `Repository.from_github_repo_name(repository_name)` — looks up commits **globally by SHA only**, with no repository or organization scoping at all: [5](#0-4) [6](#0-5) [7](#0-6) 

This breaks the binding: **organization asserted in the payload and used to select the verification secret** ≠ **repository/stack whose commit status is actually mutated**. The webhook endpoint itself requires no session, `ApiClient` token, or any Shipit credential — it is a public, unauthenticated HTTP endpoint by design (`skip_before_action :verify_authenticity_token`), so the only gate is `verify_signature`, which the blank-secret path defeats entirely for the organization it resolves to, while the mutation performed afterward is not bound to that organization at all.

### Impact Explanation
`Commit#create_status_from_github!` persists attacker-controlled `state`/`context`/`description`/`target_url` fields directly onto a `Status` record for any commit SHA present in the `commits` table, regardless of which stack/repository/organization it belongs to. Shipit's documented `ci.require` / `ci.blocking` safety gates key deploy eligibility off these exact commit statuses (see README `ci.require`), so forging a `success` status for a required CI context lets an attacker cause a stack's continuous-delivery pipeline (or a human operator relying on the green check) to proceed to deploy a commit that never actually passed CI — an unauthorized deploy triggered purely through the public webhook endpoint. This satisfies the High-impact criterion "an unauthorized deploy."

### Likelihood Explanation
Exploitation requires either (a) at least one configured GitHub App/org in the Shipit instance to have a blank `webhook_secret` — a state the codebase and shipped example/test configs explicitly treat as valid and which unconditionally disables signature verification for that organization key — combined with attacker knowledge of a target commit SHA tracked by any stack (easily obtainable since Shipit stack/commit views are often broadly visible), or (b) any actor able to trigger a genuinely signed `status` webhook (e.g. any low-privilege contributor on any one repository sharing the App installation) referencing a SHA shared with another tracked repository's history (e.g. via forks/shared ancestry). Path (a) requires zero credentials of any kind and is directly reachable at the public `/webhooks` endpoint, making likelihood moderate-to-high in any multi-tenant or loosely-configured deployment.

### Recommendation
- Scope `StatusHandler#process` (and any other handler that mutates state) to the repository asserted in the same payload object that was authenticated (`payload.dig('repository', 'full_name')`), mirroring `Handler#stacks`/`Repository.from_github_repo_name`, and reject/ignore statuses for commits outside that repository.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank outside of explicitly non-production/test environments; require an explicit, logged opt-in for unsigned webhook acceptance.
- Bind the organization resolved for signature verification to the same identifier used by every downstream handler mutation, so authentication and the acted-upon scope can never diverge.

### Proof of Concept
1. Configure (or find) a Shipit deployment with ≥2 GitHub App organizations, where at least one (`OrgB`) has `webhook_secret` unset — a state shown as valid in `config/secrets.development.example.yml` / `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` (no auth) with headers `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/anything" },
  "sha": "<sha of a commit belonging to a totally different stack, e.g. OrgA/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged"
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of the (even absent) `X-Hub-Signature` header. [1](#0-0) 
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matching the victim commit in `OrgA/victim-repo`'s stack and writing a forged `success` status for the required CI context on it, with no relation to `OrgB` ever checked. [5](#0-4) 
5. If that context is listed in the victim stack's `ci.require`, the stack's deploy safety check now treats the commit as CI-green, enabling an unauthorized deploy.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
