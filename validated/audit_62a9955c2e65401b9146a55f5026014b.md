### Title
Opaque swap routes can smuggle a caller-signed token transfer through a strategy hop - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept opaque `swap` bytes and execute them through the configured router while the account owner's authorization is active. [1](#0-0)  A route can name a malicious pool contract that returns a valid-looking swap result but also requests `caller.require_auth()` for an unrelated `token.transfer(caller, attacker, amount)`; Soroban simulation records that transfer as a child of the caller's strategy authorization, and it executes if the poisoned tree is signed. [2](#0-1) 

### Finding Description
The controller validates the strategy input amount, authorizes one exact input-token transfer to the configured router, and invokes `execute_strategy(controller, amount_in, swap)` under the flash guard. [3](#0-2)  It then verifies only the controller's input spend, bounded by `amount_in`, and a positive measured `token_out` balance delta. [4](#0-3) 

Neither check interprets the callee addresses embedded in `swap` or limits nested calls made by route-selected code. [5](#0-4)  The analogous boundary violation is therefore request/authorization smuggling: attacker-controlled route bytes introduce a downstream contract that issues an unrelated authenticated request under the caller's root authorization. [6](#0-5) 

The regression test demonstrates the exact primitive: a route-selected `swap` implementation calls `token.transfer(victim, attacker, amount)`, simulation attaches that call beneath the victim's `swap_collateral` authorization, and enforcement succeeds when that recorded child is signed. [7](#0-6) 

### Impact Explanation
A malicious route can steal unrelated wallet assets from the account owner, not merely consume the collateral amount routed through the swap. [8](#0-7)  The forged transfer is independent of the swap input, output, minimum-output, residual, and final-account-risk checks. [4](#0-3) 

The affected funds are the caller's wallet tokens because token contracts authorize `transfer(from, to, amount)` against `from`; the malicious downstream call supplies the strategy caller as `from` and the attacker as `to`. [9](#0-8) 

### Likelihood Explanation
An unprivileged attacker only needs to get the victim to submit a `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` transaction containing the crafted route. [10](#0-9)  Simulation displays or encodes the malicious token transfer as a nested authorization rather than as part of the human-readable route amount, so a client that validates only the requested pair and amount can produce a poisoned signature tree. [6](#0-5) 

Execution does require the victim's signature or authorization entry to include the injected child transfer, and an honest authorization tree without that child makes the host reject the transfer and roll back the strategy. [11](#0-10) 

### Recommendation
Do not allow strategy payloads to select arbitrary downstream pool addresses. [12](#0-11)  Bind each route hop to a governance-registered venue/pool identity, or have the router expose a signed route manifest that the client can compare with the exact authorization tree before signing. [6](#0-5) 

Clients should also decode every strategy `swap` payload, verify its token pair and minimum output, simulate the complete controller transaction, and reject any authorization child other than the route's expected token movement. [13](#0-12) 

### Proof of Concept
1. Alice owns a debt-free account with USDC collateral and holds `WALLET_TOKEN`, which need not be listed by the lending protocol. [14](#0-13) 
2. The attacker deploys `RogueHopPool` with `(victim=alice, wallet_token, to=attacker, amount=WALLET_BALANCE)` in its constructor storage. [15](#0-14) 
3. The crafted `swap` payload names that contract as a route pool while reporting USDC as input and ETH as output. [16](#0-15) 
4. Alice calls `swap_collateral(alice, account_id, usdc_hub_key, 50_000_000_000, eth_hub_key, route)`. [17](#0-16) 
5. The controller authorizes the router input transfer and invokes the route; inside the route, `RogueHopPool::swap` executes `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [5](#0-4) 
6. Recording-mode authorization shows the wallet-token transfer attached under Alice's `swap_collateral` invocation; signing that returned tree drains `WALLET_TOKEN` while Alice receives the advertised ETH output. [18](#0-17)

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
