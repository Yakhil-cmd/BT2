### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook purely by `Commit.where(sha: params.sha)`, with no scoping to the repository/stack that authenticated the request via `Shipit::WebhooksController#verify_signature`. Because signature verification is keyed off the attacker-controlled `repository.owner.login`/`organization.login` field in the JSON body rather than any server-side binding between "who signed this" and "which stack this status may mutate," an attacker who controls (or can forge webhooks for) any GitHub App organization configured in Shipit can flip the CI status of a commit belonging to a completely different, victim stack, as long as the two stacks happen to share a commit `sha` (trivially achievable by forking a public repo, since git commits are content-addressed).

### Finding Description
The broken binding is: `authenticated_organization(repository_owner) == organization_that_owns(commit.stack)` is assumed but never enforced.

Trace:
- `Shipit::WebhooksController#verify_signature` computes `repository_owner` straight from the untrusted JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , then verifies the HMAC signature using the webhook secret configured for *that* organization: `github_app = Shipit.github(organization: repository_owner); github_app.verify_webhook_signature(...)` [2](#0-1) . This only proves the attacker knows the webhook secret for *some* Shipit-configured organization (e.g., their own), not that they are authorized to mutate any particular stack.
- Once signature verification passes, `WebhooksController#create` dispatches the entire raw JSON body to every registered handler for the event, with no repository/stack context passed along: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
- `StatusHandler#process` then does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This query is global across the `commits` table — it is not filtered by `stack_id`, `repository`, or any value tied to the organization that just authenticated the request.
- `Commit#create_status_from_github!` writes a `Status` row for whatever commit(s) matched, tied to that commit's own `stack_id` [5](#0-4) , and `Status#after_create`/`after_commit` callbacks (`enable_ci_on_stack`, `schedule_continuous_delivery`, `broadcast_update`) immediately act on the victim stack [6](#0-5) .
- Because commit SHAs are content-addressed by git, an attacker can create identical SHAs in a second stack simply by forking the victim's public repository and adding that fork to Shipit under an organization they control (with an App/webhook secret they know). The attacker then sends a validly-signed webhook for their own org, but with `sha` equal to the victim's commit hash and `context: ci/jenkins`, `state: failure`.
- `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and `Commit#blocked?` (checking `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`) are driven by the `Status` rows just forged [7](#0-6) , so the forged `failure` status on a `required`/`blocking` context can force the victim's (production) stack commit range into a blocked state, or a forged `success` can clear a real failure and trigger `schedule_continuous_delivery` [8](#0-7) .

None of the existing guards prevent this: `verify_signature` only proves the request was signed by *an* App the attacker has access to, not that the App owns the target stack; `drop_unhandled_event` and `check_if_ping` are irrelevant; the `ExplicitParameters` schema in `StatusHandler.params` only validates types/presence of `sha`/`state`/etc., not repository ownership; there is no `require_permission!`, `stacks` scope, or model validation anywhere in this path that ties the incoming organization to the `Commit`'s `stack`.

### Impact Explanation
An attacker who can get any organization onto Shipit's configured GitHub Apps list (which for a multi-tenant Shipit deployment can be as easy as installing/owning a fork repo whose org has its own App/webhook secret they control) can write `Status` records — and thereby flip `deployable?`/`blocked?` — for **any other stack's commit that shares a SHA**, including a victim's production stack. This is a cross-tenant write: "a payload for one repository mutating another's stack/commit," which the rules classify as Critical (unauthorized deploy/rollback/block of a production stack they do not own). The attack is repeatable against any stack/commit combination where a shared SHA can be engineered (trivial via forking a public repo), and the blast radius spans all stacks configured in the same Shipit instance, not just one tenant.

### Likelihood Explanation
Preconditions: the attacker needs webhook-signing capability for *some* organization already configured in `Shipit.github_apps` (this is the case for any organization/App the attacker legitimately owns or controls on the same Shipit instance — a realistic scenario in a multi-tenant Shipit deployment where many teams each register their own org/App). The victim stack must contain a commit whose SHA is also reachable/importable into a stack the attacker controls — straightforward for public repos via forking. No GitHub team membership, Shipit session, or API token is required; the request is a raw signed `POST /webhooks`. This is a low-cost, fully repeatable attack limited only by the requirement that the attacker control at least one Shipit-registered GitHub App identity.

### Recommendation
Scope the `StatusHandler` (and any other SHA-keyed handler) lookup to the repository/stack that the verified webhook belongs to, e.g. resolve `Stack`s via `repository.full_name` from the payload (as is presumably done for `push`) and restrict `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` instead of a bare global `sha` match. More generally, `WebhooksController` should pass the authenticated `repository_owner`/`repository.full_name` down to handlers so they can verify the target stack's repository matches the organization that signed the webhook.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook does not affect a commit belonging to a different stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit) # e.g. production environment
  attacker_stack = Stack.create!(repository: shipit_repositories(:other), environment: 'production', ...)

  shared_sha = "6d9278037b872fd9a6690523e411ecb3aa181355"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, ...)
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

  assert victim_commit.deployable? # baseline: LHS == RHS holds before attack

  # Attacker signs with their own org's webhook secret (verify_signature passes for attacker's org)
  Shipit::Webhooks::Handlers::StatusHandler.call(
    'sha' => shared_sha, 'state' => 'failure', 'context' => 'ci/jenkins'
  )

  victim_commit.reload
  refute victim_commit.deployable?, "victim stack's commit should not be mutated by a webhook authenticated for a different organization"
end
```
This demonstrates the binding `authenticated_org(repository_owner) == owner_of(commit.stack)` is violated: the equality does not hold, yet `StatusHandler#process` still writes the `Status` and mutates `victim_commit`'s deployability, confirming the cross-tenant write described above.
