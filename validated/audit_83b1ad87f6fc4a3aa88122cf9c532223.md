## Title
Duplicate members inside `r of set` / `weighted and` multisig definitions let one signer satisfy a multi-party signature threshold - (File: `definition.js`)

## Summary
`Definition.validateDefinition` and `Definition.validateAuthentifiers` accept `r of set` (and `weighted and`) spending-condition arrays that contain duplicate sub-definitions (e.g. the same `["sig", {pubkey}]` entry repeated). Because a signature is verified against the unit hash and is *not* bound to the authentifier path it is placed under, a single private key can be used twice (once per duplicated set slot) to satisfy `required` count that was meant to represent independent co-signers. This is the address-definition analog of the reported "duplicate slate entries defeat a threshold check" bug class.

## Finding Description
`validateDefinition`'s `r of set` handler only checks array length, `required <= set.length`, and complexity/op limits — it never checks that the elements of `args.set` are distinct: [1](#0-0) 

At authentication time, `validateAuthentifiers`'s `evaluate` function walks the same `set` array and, for a `sig` leaf, looks up `assocAuthentifiers[path]` and verifies it against `objValidationState.unit_hash_to_sign`: [2](#0-1) 

The signature value itself is a signature over the whole unit hash — it does not encode or depend on the `path` string it's attached to. If the same `["sig", {pubkey: X}]` sub-definition appears at two different indices of the `set` (e.g. `path 'r.0'` and `path 'r.1'`), the holder of key `X` can copy the single valid signature into `authentifiers['r.0']` and `authentifiers['r.1']`, satisfying two "independent" branches of the threshold with only one real signer. `count_options_with_sig`/`count` in the `r of set` (and `weighted and`) evaluators then reaches `required` even though fewer than `required` distinct keys actually signed: [3](#0-2) 

This directly affects multi-device shared/joint addresses built via `wallet_defined_by_addresses.js`. `getMemberDeviceAddressesBySigningPaths` walks `r of set`/`weighted and`/`and`/`or` templates and records `device_address` per path without deduplicating or verifying that each threshold branch corresponds to a distinct device: [4](#0-3) 

`validateAddressDefinitionTemplate`, which is used when creating a shared address, only requires that the *overall* set of member device addresses (deduplicated with `_.uniq`) has at least 2 entries — it does not require that every "required" slot inside an `r of set`/`weighted and` be filled by a distinct participant: [5](#0-4) 

So a participant proposing a "2-of-3" (or similar) shared address template can place their own `$address@device` placeholder into two of the three `set` slots and a single honest co-signer's placeholder into the third. `arrDeviceAddresses.length` is still `2` (attacker + honest party), passing the "less than 2 member devices" check, yet the attacker alone can satisfy `required=2` by reusing their own signature under both of their assigned paths, without any cooperation from the honest co-signer.

## Impact Explanation
This breaks the fundamental security assumption of an m-of-n multisig/shared address: that at least `m` *independent* keyholders must cooperate to authorize spending. An attacker who participates in constructing (or is delegated to construct) the address definition template can unilaterally gain full, unassisted spending authority over funds that other participants believe require joint approval — i.e., unauthorized spending / theft of funds from a shared address, with no cryptographic break required, only a duplicate-entry definition that passes all current validation checks.

## Likelihood Explanation
Any wallet user proposing a shared address (an address-definition author, in-scope per the rules) can construct such a template; nothing in `validateDefinition`, `validateAuthentifiers`, or `validateAddressDefinitionTemplate` rejects duplicate sub-definitions inside `r of set`/`weighted and`. The exploit requires no race condition, no third-party cooperation beyond the honest party agreeing to join a shared address (a normal, expected flow), and is deterministic once the address is created and funded.

## Recommendation
When validating `r of set` and `weighted and` definitions (in `definition.js`'s `validateDefinition`), reject sets containing duplicate/structurally-identical sub-definitions (e.g. by comparing `JSON.stringify` of each `arg`/`arg.value`, similar to how `checkSlate` should dedupe proposal ids). Additionally, in `wallet_defined_by_addresses.js`, when deriving member device addresses from a template (`getMemberDeviceAddressesBySigningPaths`/`validateAddressDefinitionTemplate`), verify that each `set`/`and`/`or` branch that counts toward a `required` threshold is bound to a distinct device/participant address, not just that the template globally mentions ≥2 unique devices.

## Proof of Concept
1. Party B proposes a shared address using a template such as:
```
["r of set", {
  required: 2,
  set: [
    ["address", "$address@DEVICE_B"],
    ["address", "$address@DEVICE_B"],   // duplicated placeholder for the same device/attacker
    ["address", "$address@DEVICE_A"]
  ]
}]
```
2. `validateAddressDefinitionTemplate` computes `arrDeviceAddresses = _.uniq(['DEVICE_B','DEVICE_A'])` → length 2, passes the "less than 2 member devices" check, and party A (unaware of the duplication's implication) agrees and co-creates the shared address (`definition.js`'s `validateDefinition` also accepts the template unmodified since it never checks for duplicate `set` entries).
3. When spending, party B signs the unit once with their key, satisfying `sig` at their own inner `address` definition; because paths `r.0` and `r.1` both resolve (through the `address` indirection) to the same address/definition, the same signature/authentifier data validates both branches, so `count_options_with_sig` in the `r of set` handler reaches `required = 2` using only B's participation.
4. Party B spends funds from the shared address without any signature or approval from party A, violating the intended 2-of-3 threshold.

function getMemberDeviceAddressesBySigningPaths(arrAddressDefinitionTemplate){
	function evaluate(arr, path){
		var op = arr[0];
		var args = arr[1];
		if (!args)
			return;
		switch (op){
			case 'or':
			case 'and':
				for (var i=0; i<args.length; i++)
					evaluate(args[i], path + '.' + i);
				break;
			case 'r of set':
				if (!ValidationUtils.isNonemptyArray(args.set))
					return;
				for (var i=0; i<args.set.length; i++)
					evaluate(args.set[i], path + '.' + i);
				break;
			case 'weighted and':
				if (!ValidationUtils.isNonemptyArray(args.set))
					return;
				for (var i=0; i<args.set.length; i++)
					evaluate(args.set[i].value, path + '.' + i);
				break;
			case 'address':
				var address = args;
				var prefix = '$address@';
				if (!ValidationUtils.isNonemptyString(address) || address.substr(0, prefix.length) !== prefix)
					return;
				var device_address = address.substr(prefix.length);
				assocMemberDeviceAddressesBySigningPaths[path] = device_address;
				break;
			case 'definition template':
				throw Error(op+" not supported yet");
			// all other ops cannot reference device address
		}
	}
	var assocMemberDeviceAddressesBySigningPaths = {};
	evaluate(arrAddressDefinitionTemplate, 'r');
	return assocMemberDeviceAddressesBySigningPaths;
}

function validateAddressDefinitionTemplate(arrDefinitionTemplate, from_address, handleResult){
	try{
		var assocMemberDeviceAddressesBySigningPaths = getMemberDeviceAddressesBySigningPaths(arrDefinitionTemplate);
	}
	catch (e) {
		return handleResult("failed to get member device addresses of new shared address: " + e.toString());
	}
	var arrDeviceAddresses = _.uniq(_.values(assocMemberDeviceAddressesBySigningPaths));
	if (arrDeviceAddresses.length < 2)
		return handleResult("less than 2 member devices");
	if (arrDeviceAddresses.indexOf(device.getMyDeviceAddress()) === - 1)
		return handleResult("my device address not mentioned in the definition");
	if (arrDeviceAddresses.indexOf(from_address) === - 1)
		return handleResult("sender device address not mentioned in the definition");
