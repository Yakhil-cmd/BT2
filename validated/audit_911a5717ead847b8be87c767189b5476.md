### Title
Webhook signature is verified against the organization derived from the payload's `repository.owner.login`, but every handler (notably `StatusHandler`) trusts other unauthenticated fields of the same payload (`repository.full_name`, or nothing at all) to decide what gets written — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App / webhook secret to validate the HMAC using only `params.dig('repository','owner','login')` (or `organization.login`), then hands the *entire* raw JSON body to the registered handlers unmodified. The handlers do not re-derive or re-validate that the rest of the payload actually belongs to the organization whose secret was used to authenticate the request. This breaks the trust binding "organization that authenticated" == "repository/commit that is written."

### Finding Description
`verify_signature` computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [1](#0-0) 
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`verify_webhook_signature` only checks that the HMAC-SHA1 of the raw body matches the secret configured for that one organization key:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Because the signature is a keyed HMAC over the *entire* raw body, and the attacker controls the entire body (they only need to know the secret for **their own** GitHub App/org, which they legitimately possess after installing a GitHub App on a repository/org they control), they can freely set every other field of the JSON payload — including `repository.full_name`, `sha`, `state`, etc. — to reference a victim stack, while keeping `repository.owner.login` equal to their own org so the correct (attacker-known) secret is selected.

Once past `verify_signature`, `create` calls all registered handlers with the raw params:
```ruby
Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
``` [4](#0-3) 

`Handlers::StatusHandler` performs no scoping to the authenticated organization or even to `repository.full_name` at all — it matches purely on commit SHA across the entire instance:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 

Even `PushHandler`, which does look up `repository.full_name`, derives that repository name from the same unauthenticated field the attacker forged:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [7](#0-6) 

None of these values (`repository.full_name`, `sha`, `state`) are covered by any binding to the organization key used in `verify_signature` — the equality that should hold, `authenticated_org == written_repository`, is never checked.

### Impact Explanation
An attacker who creates their own (free) GitHub App/organization, obtains its `webhook_secret`, and points a crafted HTTP POST at the shared `/webhooks` endpoint can forge a `status` event for any commit SHA hosted on any stack tracked by this Shipit instance (SHAs are public via `git log`/GitHub API for public repos, or leaked via CI/PR links). The forged status is written directly via `Commit#create_status_from_github!`, which feeds `Status::Group`/`Commit#status`, and in turn `Commit#deployable?`:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [8](#0-7) 
By injecting a `success` status for a required CI context, an attacker can flip a commit from non-deployable to deployable, satisfying `ci.require` gating and enabling continuous-delivery/manual deploy of a commit that never actually passed CI on the victim's repository — an unauthorized deploy through a forged trust signal, without ever holding a `Shipit` session, `ApiClient` token, or the victim repository's own webhook secret.

### Likelihood Explanation
Any unprivileged actor can create a personal GitHub App/org (no special privilege needed), install it anywhere (even a throwaway repo), and thereby legitimately obtain a `webhook_secret` value accepted by `Shipit.github(organization: <their org>)`. Crafting the JSON body with a mismatched `repository.full_name`/`sha` requires no more than basic HTTP tooling. The only "unknown" fact needed is the target commit SHA, which is public for any public repository. This is a low-effort, directly reachable attack path.

### Recommendation
- Do not use a field inside the unauthenticated JSON body to select which secret verifies that same body. Bind the webhook's organization/app identity out-of-band (e.g., via `X-GitHub-Hook-Installation-Target-ID`/App ID from headers, or by requiring the payload's `repository.owner.login` used for verification to also be the same value every downstream handler is scoped to).
- In every handler, after verifying the signature for organization `O`, assert that `repository.full_name`'s owner equals `O` before doing any lookup/write, and reject the event otherwise.
- For `StatusHandler` specifically, never match commits by `sha` alone across the whole instance; require and check `repository.full_name` maps to the commit's `stack.repository`, and that this repository's owning organization matches the one whose secret authenticated the request.

### Proof of Concept
1. Attacker creates GitHub App "AttackerApp" on their own org `attacker-org`, sets `webhook_secret = S`, and configures it in `Shipit.github(organization: 'attacker-org')`'s config (this is exactly the deployment-documented flow in `docs/setup.md`, not a privileged Shipit action).
2. Attacker looks up a public commit SHA `deadbeef...` on the victim stack `victim-org/victim-repo` that is required by `ci.require` but currently failing/pending.
3. Attacker builds a JSON body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"},
  "sha": "deadbeef...",
  "state": "success",
  "context": "required-check-name"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` → `attacker-org`, fetches `attacker-org`'s app, and the HMAC matches (attacker knows `S`), so the request passes.
6. `StatusHandler.process` executes `Commit.where(sha: 'deadbeef...')` and writes a fabricated `success` status onto the victim's commit, potentially satisfying `ci.require` and allowing an unauthorized deploy on `victim-org/victim-repo`.
