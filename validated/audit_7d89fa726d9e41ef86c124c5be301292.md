### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the repository actually acted upon is derived from the independent `repository.full_name` field — allowing forged cross-organization webhook events ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate an incoming webhook's HMAC signature against using a value pulled straight out of the *unauthenticated* request body, while the handlers that subsequently act on that webhook resolve the target `Stack`/`Repository` from a *different* field of the same unauthenticated body. Nothing ties these two fields together, so a party who knows (or controls) the webhook secret for one organization configured in a Shipit installation can forge a validly-signed webhook that is processed against a repository belonging to an entirely different organization/stack.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret like this: [1](#0-0) 

and [2](#0-1) 

`repository_owner` (`repository.owner.login`, falling back to `organization.login`) is read directly from `request.raw_post` before any signature check has taken place, and is used to look up which `GitHubApp`/webhook secret (`Shipit.github(organization: repository_owner)`) must match the `X-Hub-Signature` header.

Once the signature check passes, the event is dispatched to a handler via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` (`create` action). The base `Handler` class, used by e.g. `PushHandler` and `StatusHandler`, resolves the actual `Stack` to operate on from a **different** field: [3](#0-2) 

`repository_name` is `repository.full_name`, independent of `repository.owner.login` used for signature selection. `PushHandler` then directly calls `stack.sync_github(...)` for every matching stack: [4](#0-3) 

Because Shipit supports per-organization GitHub App configuration (`TOP_LEVEL_GH_KEYS` including `webhook_secret`, looked up per `organization`): [5](#0-4) [6](#0-5) 

an attacker who legitimately controls (or has leaked) the webhook secret for **Organization A** can submit a payload where `repository.owner.login` = `"org-a"` (so signature verification succeeds against Org A's secret) but `repository.full_name` = `"org-b/victim-repo"` (so the handler acts on a stack belonging to Org B). The binding that should hold — *the organization whose secret authenticated the request* == *the repository the handler writes to* — is never enforced.

### Impact Explanation
This breaks the deployment-trust binding "an organization that authenticated versus the repository that is written." A forged, validly-signed `push` event can trigger `Stack#sync_github` for a victim stack outside the attacker's authorized organization, and forged `status`/`check_suite` events can influence CI-gating state (`branch_status`, `deployable?`) used to permit continuous delivery. Where continuous delivery is enabled on the victim stack, this can result in an unauthorized deploy being triggered against a repository the attacker does not control — meeting the "Critical: unauthorized deploy" bar.

### Likelihood Explanation
Requires the attacker to already control a webhook secret for at least one organization configured in the same Shipit instance (a realistic scenario in any multi-tenant/multi-org Shipit deployment, since each org owner independently manages their own GitHub App/webhook secret but shares the same Shipit engine and stack namespace). No repository write access, GITHUB_TOKEN, or `ApiClient` token is required — only knowledge of one org's webhook secret and the ability to send an HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Enforce that the organization used to validate the signature is the same organization that owns the repository resolved by the handler — e.g., derive both from `repository.full_name` (or cross-validate `repository.owner.login` against the owner portion of `repository.full_name`) before dispatching to handlers, and additionally verify per-repository/per-organization webhook secrets against the specific `GithubHook` record tied to the target `Stack`, not just a globally-selected app secret.

### Proof of Concept
1. Configure Shipit with two orgs, `org-a` and `org-b`, each with its own `github.webhook_secret` (`Shipit.github(organization: 'org-a')` vs `Shipit.github(organization: 'org-b')`).
2. Attacker (who administers `org-a` and thus knows `org-a`'s `webhook_secret`) crafts a `push` webhook payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` = `"org-a"`, fetches `org-a`'s secret, verification succeeds.
5. `PushHandler#process` resolves `Repository.from_github_repo_name("org-b/victim-repo")` and calls `sync_github` on `org-b`'s stack(s), even though the attacker never had `org-b`'s secret or any authorization on that repository. [7](#0-6) [3](#0-2)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
