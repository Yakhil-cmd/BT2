### Title
Webhook signature validation is keyed to an attacker-suppliable "organization" field that is never cross-checked against the "repository" field the event handler actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which GitHub App configuration (and thus which `webhook_secret`) to validate a request against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted request body, then verifies the signature against that org's secret. The event handler that actually performs the privileged action (`Handler#stacks` / `Handler#repository_name`) instead resolves its target `Repository`/`Stack` using a *different* field of the same payload: `repository.full_name`. These two fields are never cross-validated against each other. When any tenant configured in `Shipit.github` has no `webhook_secret` set (a state the project's own templates ship with, e.g. `webhook_secret: nil`), `verify_webhook_signature` short-circuits to `true`, and an unauthenticated caller can submit an arbitrary, unsigned payload whose `repository.owner.login` matches the secret-less org while `repository.full_name` points at a completely unrelated stack, causing the handler to act on that unrelated stack.

### Finding Description
The equality the code is supposed to enforce is:
`org that authenticated the request == org that owns the repository being written to`

`verify_signature` derives the authenticating org purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-org App config and its `webhook_secret`, and `verify_webhook_signature` trivially passes when no secret is configured for that org: [3](#0-2) 

Multi-tenant configuration files in this repo demonstrate that a secret-less org is a supported/documented state, not a misconfiguration: [4](#0-3) 

Meanwhile, the handler that performs the write (looking up the `Repository`/`Stack` to sync) uses an entirely separate payload field, `repository.full_name`, with no re-validation against the org used for signature selection: [5](#0-4) 

`PushHandler` then triggers a sync on whatever stack that lookup returns: [6](#0-5) 

Because `repository_owner` (used to pick a validation key) and `repository.full_name` (used to pick the object acted on) are independent, unrelated fields of the same untrusted JSON body, an attacker who knows any org in the Shipit deployment has no `webhook_secret` configured can set `repository.owner.login` to that org (making `verify_signature` bypass entirely) while setting `repository.full_name` to the full name of a stack belonging to a *different*, properly-secured org, and have the handler act on that victim stack without ever presenting a valid signature for it.

### Impact Explanation
This breaks the trust boundary between "which tenant authenticated this webhook" and "which repository/stack the event is applied to." In a Shipit deployment hosting multiple GitHub organizations (the exact scenario the shipped config templates demonstrate), it allows an unauthenticated party to trigger `GithubSyncJob`/`stack.sync_github` (and, depending on handler, other webhook-driven behaviors such as membership/team creation, PR/merge-queue state changes, or check-run refresh) against a stack that belongs to an organization whose webhook secret was never compromised or even known to the attacker. This can force premature synchronization ahead of continuous-deployment triggers, effectively giving the attacker influence over *when* an otherwise-legitimate deploy is kicked off for a target stack, and more generally lets an attacker impersonate events for a repository they have no relationship with, satisfying the "unauthorized deploy" / cross-repository-write class of impact called out in scope.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or sessions: only that at least one org configured on the instance has a blank `webhook_secret`, a state explicitly present in this repo's own shipped configuration examples and setup docs, meaning it's realistic for real deployments (e.g., a newly onboarded org before its secret is filled in, or an org intentionally left open for internal testing). Once that condition holds, the attacker only needs to know one victim stack's `owner/repo` full name (public information) to target it.

### Recommendation
Do not let `repository.full_name` (used to select the write target) be independent from `repository_owner`/`organization.login` (used to select the verification key). Concretely:
- After verifying the signature, re-derive/validate that the org portion of `repository.full_name` matches the `repository_owner` used for the signature lookup, rejecting the request otherwise.
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; instead require an explicit, documented opt-in flag before disabling signature verification for an org, and reject cross-org payload combinations regardless.

### Proof of Concept
1. On a multi-tenant Shipit instance, org `unsecured-org` is configured in `Shipit.github` with `webhook_secret: nil` (as templated in `config/secrets.development.shopify.yml`), while org `victim-org` has a real secret and an active stack `victim-org/app`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<sha>",
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/app" }
}
```
(no valid `X-Hub-Signature` needed).
3. `WebhooksController#verify_signature` resolves `repository_owner` = `unsecured-org`, calls `Shipit.github(organization: "unsecured-org")`, and `verify_webhook_signature` returns `true` immediately because that org's `webhook_secret` is blank. [1](#0-0) 
4. `PushHandler.call(params)` then resolves the target via `payload.dig('repository', 'full_name')` = `victim-org/app`, and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's real stack, despite the request never having been validated against `victim-org`'s secret. [5](#0-4) [6](#0-5)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
