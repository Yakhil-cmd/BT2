### Title
Session fixation on GitHub OAuth login completion - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a newly authenticated GitHub identity to the current session (`session[:user_id]`) without first calling `reset_session`, unlike the `logout` action and the forced-re-login path in `Authentication#force_github_authentication`, both of which do call `reset_session`. This breaks the intended equality between "the session identifier that existed before authentication" and "the session identifier that should be trusted as bound to a specific `User` after authentication" — analogous to the reported bug where a piece of state (`lastTimestamp` / here, the session id) is left at its pre-trust default instead of being reset at the moment a new trust relationship (liquidity position / authenticated user) is established.

### Finding Description
`force_github_authentication` redirects unauthenticated visitors to `github_authentication_path`, which starts the OmniAuth GitHub flow [1](#0-0) . When OmniAuth completes, `GithubAuthenticationController#callback` looks up or creates the `User` from the GitHub profile and stores its id directly into the *existing* session without regenerating it: [2](#0-1) 

Compare this to `logout`, which does call `reset_session` [3](#0-2) , and to the "stale credential" branch of `force_github_authentication`, which also calls `reset_session` before re-prompting login [4](#0-3) . The `callback` action — the one place where a *brand-new* trust binding (anonymous session → authenticated `User`) is created — is the only login-related code path that skips `reset_session`.

If the host application's session store issues a session identifier before authentication (as most non-purely-stateless stores do, and as `test/dummy/config/initializers/session_store.rb` configures via `:cookie_store` with a fixed key — note the underlying session mechanics depend on how the host app configures/serves `Shipit::Engine`) [5](#0-4) , an attacker who can plant a known session identifier in a victim's browser prior to login (classic session fixation preconditions: subdomain cookie tossing, a non-HttpOnly/overwritable cookie, or a shared session store) can force the victim's subsequent GitHub OAuth login to populate `session[:user_id]` into that already-known session. The attacker can then use the same fixed session identifier to access the application as the victim, without needing the victim's GitHub token, `webhook_secret`, or an `ApiClient` token, and without exploiting the host application's own bugs — the vulnerability is entirely inside `Shipit::GithubAuthenticationController`.

### Impact Explanation
This maps to the report's "First liquidity provider" pattern: a piece of state that should be *initialized fresh* at the moment a new trust relationship begins (`pool.lastTimestamp` there, `session id` here) is instead left in its pre-existing/default form, letting an outside party benefit from a binding it did not itself establish. Here, the practical effect is that an unprivileged attacker can end up holding a session that the engine now considers to be the authenticated `User`'s session, i.e. session fixation, which the task's own impact taxonomy explicitly lists as a High-severity outcome ("session fixation / forced OAuth completion").

### Likelihood Explanation
Exploitability depends on the session-fixation preconditions being met by the host application (ability to set/predict a session identifier for the victim before OAuth completes, which requires more than the cookie_store used only in the test dummy app, or additional attacker capability such as cookie-tossing/subdomain control). This is a real gap in the engine's own login-completion code — the fix is a two-line, unconditional `reset_session` before establishing the new authenticated session — but full exploitability is host/environment dependent, and I could not verify how the shipping (non-dummy) host applications configure their `session_store` (Redis/DB-backed vs. purely cookie-based) from within this repository, since that configuration lives in the host app, not the engine.

### Recommendation
Call `reset_session` in `GithubAuthenticationController#callback` before assigning `session[:user_id]` / `session[:authenticated]`, mirroring the pattern already used in `logout` and in the stale-credential branch of `force_github_authentication`, so that every successful authentication (not just logout or forced re-login) issues a fresh session identifier.

### Proof of Concept
1. Attacker obtains/knows a session identifier (via any mechanism available to them against the host app's session store) and gets the victim's browser to adopt it (e.g., by setting a cookie the browser will send to the Shipit host, dependent on host cookie scoping).
2. Victim, using that session, navigates to `Shipit::Engine` and is redirected to `github_authentication_path` by `force_github_authentication`.
3. Victim completes the real GitHub OAuth flow; `GithubAuthenticationController#callback` runs and sets `session[:user_id] = sign_in_github(auth)` on the *same* (attacker-known) session, without calling `reset_session` [2](#0-1) .
4. Attacker reuses the known session identifier and is now treated as the authenticated victim by `Shipit::Authentication#current_user` [6](#0-5) .

    def force_github_authentication
      if current_user.logged_in? && current_user.requires_fresh_login?
        Rails.logger.warn("User #{current_user.id} requires a fresh login, logging out...")
        reset_session
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      elsif Shipit.authentication_disabled? || current_user.logged_in?
        unless current_user.authorized?
          team_handles = Shipit.github_teams.map(&:handle)
          team_list = team_handles.to_sentence(two_words_connector: ' or ', last_word_connector: ', or ')
          render(plain: "You must be a member of #{team_list} to access this application.", status: :forbidden)
        end
      else
        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))
      end
    end

    def callback
      return_url = request.env['omniauth.origin'] || root_path
      auth = request.env['omniauth.auth']

      return render('failed', layout: false) if auth.blank?

      session[:user_id] = sign_in_github(auth)

      # We need to set this so that the /events and /sidekiq endpoint
      # which leverage `UserRequiredMiddleware` will recognize the user
      # is authenticated.
      session[:authenticated] = true

      redirect_to(return_url)
    end
