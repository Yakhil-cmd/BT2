### Title
Webhook signature verification is keyed off an unsigned payload field, letting an attacker forge events for any repository under a multi-org install with a mismatched/blank `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` config (and thus which HMAC secret) to validate a webhook against by reading `repository_owner`, a field taken directly from the still-unverified JSON body, then uses that org's `webhook_secret` to check `X-Hub-Signature`. The org used to authenticate the request is not the same value later used to decide which repository/stack the payload is applied to (`payload.dig('repository', 'full_name')` in `Handler#repository_name`). This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`repository_owner` is computed before signature verification, straight from attacker-controlled JSON: [1](#0-0) 

It is then used to select the `GitHubApp` instance whose secret verifies the signature: [2](#0-1) 

Crucially, `verify_webhook_signature` treats a blank/unset `webhook_secret` as automatically verified: [3](#0-2) 

In a multi-org deployment (`Shipit.github(organization:)` supports per-org configs), an operator can have one organization fully configured with a `webhook_secret` and another organization present in config but with `webhook_secret` left blank (this is literally shown as the default/example state): [4](#0-3) [5](#0-4) 

Once past `verify_signature`, the actual event processing looks at a *different* field of the same JSON body - `repository.full_name` - to decide which `Repository`/`Stack` the event applies to, completely independent of the `repository_owner` value that was used for authentication: [6](#0-5) [7](#0-6) 

So the equality that should hold - "the organization whose secret validated this request == the organization owning the repository the event will be applied to" - does not hold. An attacker who knows (or guesses) that org B has no `webhook_secret` configured can submit a forged, unsigned payload with `repository.owner.login = "B"` (satisfying the signature check trivially, since `webhook_secret` is blank) while setting `repository.full_name` to any repository belonging to org A that Shipit tracks, and the corresponding handler (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) will process it as if it legitimately came from GitHub.

### Impact Explanation
Handlers triggered this way include `PushHandler` (queues `GithubSyncJob` to sync a stack's deployed state to an attacker-chosen `after` SHA), `StatusHandler` (forges commit CI status), `MembershipHandler`/`Team` handling (creates/deletes team memberships), and `pull_request` handlers (affects review-stack lifecycle, merge status). Forged push/status events can directly influence what commit is considered "deployable" and can be chained into an unauthorized deploy of an attacker-chosen ref, which maps to Critical impact (unauthorized deploy) in the rubric; at minimum it is unauthenticated write of stack/commit state, which is a High-severity authorization boundary bypass ("authentication bypass" - forged webhook processed as authentic GitHub event).

### Likelihood Explanation
This requires: (1) a Shipit deployment configured for multiple GitHub organizations (a supported, documented mode via `Shipit.github(organization:)`/`TOP_LEVEL_GH_KEYS`), and (2) at least one configured organization with no `webhook_secret` set - which the shipped example/development secrets files show as the default placeholder value. Given that operators frequently onboard additional orgs incrementally and the "no secret configured" state silently short-circuits verification (`return true unless webhook_secret`) rather than failing safe, this is a plausible misconfiguration rather than a purely theoretical one. It does not require compromising any credential, token, or session - only knowledge/guessing of a second org name present in the install with a missing secret.

### Recommendation
Do not let attacker-controlled payload fields select the verification secret. Either verify against every configured org's secret and reject if none matches (rather than trusting the payload's claimed owner), or bind the webhook endpoint to a fixed organization per GitHub App installation (e.g., via URL/route parameter set at install time, not payload content) so the value used to select the secret cannot diverge from the value later used to select the repository/stack. Additionally, `verify_webhook_signature` should fail closed (reject) when `webhook_secret` is blank rather than treating it as automatically verified, unless that behavior is an explicit, intentional "no webhook" opt-out for that org.

### Proof of Concept
1. Deploy Shipit with two orgs configured: `orgA` (has a real repo/stack tracked, `webhook_secret` set) and `orgB` (added to config, e.g. for OAuth-only purposes, but `webhook_secret` left blank as in `config/secrets.development.shopify.yml`).
2. Attacker sends `POST /github/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or an arbitrary bogus value), and JSON body:
   ```json
   {
     "repository": { "owner": { "login": "orgB" }, "full_name": "orgA/real-repo" },
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>"
   }
   ```
3. In `verify_signature`, `repository_owner` resolves to `"orgB"` → `Shipit.github(organization: "orgB")` → `verify_webhook_signature` returns `true` immediately because `orgB`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. `WebhooksController#create` dispatches to `PushHandler.call(params)`, which resolves the target stack via `payload.dig('repository', 'full_name')` = `"orgA/real-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `GithubSyncJob` for `orgA`'s real stack with the attacker-supplied `after` SHA - despite the request never being signed by `orgA`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
