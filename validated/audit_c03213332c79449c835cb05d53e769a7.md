### Title
Cross-Stack Information Disclosure via `CCMenuController#stack` Bypassing ApiClient Stack Scope Binding - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor used by all other `Shipit::Api::BaseController` subclasses, replacing the scope-checked lookup with a raw, unscoped `Stack.from_param!` call. This breaks the binding `stack a token authorises == stack it touches`: an `ApiClient` token restricted to a single stack (`api_client.stack_id`) can be used to read build/deploy status information for *any* stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting accessor: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` is scoped to a specific stack — this is exactly the mechanism that ties "stack a token authorises" to "stack it touches" for every other API controller (`DeploysController`, `TasksController`, `CommitsController`, `LocksController`, `OutputsController`, `RollbacksController`, etc., all of which call the inherited `stack` method).

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly against the global `Stack` relation instead of the api-client-scoped `stacks` relation. The controller still enforces `require_permission :read, :stack`: [3](#0-2) 
which only checks that the token carries the `read:stack` permission string — it never verifies that the specific `params[:stack_id]` being requested is the one the token was actually scoped to create/read.

The controller additionally supports authenticating via a `token` query-string parameter rather than HTTP Basic Auth: [4](#0-3) 
so a leaked or shared CCMenu URL for one stack (which necessarily contains a valid, functioning `read:stack` token) is sufficient to enumerate and read the deploy/build status of every stack managed by the install, including stacks that token was never provisioned to see.

### Impact Explanation
This maps to the "High - unauthenticated read of stack state, task streams or deploy output" category: an `ApiClient` token that was deliberately scoped by an administrator to a single, low-sensitivity stack (`api_client.stack_id`) can be replayed against the `ccmenu` endpoint with an arbitrary `stack_id` to read `lastBuildStatus`, `activity` (building/sleeping), `lastBuildTime`, `lastBuildLabel` (deploy id), lock status, and stack existence for other stacks: [5](#0-4) 
This is a direct cross-tenant/cross-stack read that the `stack_id` scoping on `ApiClient` was specifically designed to prevent, mirroring the reported bug class where a check binding one entity (the order's side / here, the token's authorized stack) to the resource actually acted upon (the vault / here, the stack being read) is missing on one specific code path while present everywhere else in the same class hierarchy.

### Likelihood Explanation
Any party holding a working `ApiClient` token with `read:stack` permission — even one intentionally scoped to a single, unrelated stack — can trigger this by simply changing the `stack_id` route/query parameter of the CCMenu request. No write access, no webhook secret, and no elevated privileges are required beyond possessing a token that was legitimately (if narrowly) issued. The `token` query-string path makes exploitation trivial since these tokens are commonly embedded in externally-shared CI dashboard URLs.

### Recommendation
Make `CCMenuController#stack` use the inherited, scope-respecting `stacks` relation (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the `ApiClient.stack_id` restriction is enforced consistently with every other API controller.

### Proof of Concept
1. Admin issues API client "CI-Widget-A" with `permissions: ['read:stack']` and `stack_id` pinned to Stack A only (intended to only expose Stack A's CCMenu feed).
2. Using `GET /api/<stack_A_or_any>/ccmenu?token=<CI-Widget-A token>` confirms normal, intended access to Stack A.
3. Attacker who obtains the "CI-Widget-A" token (e.g., from a publicly embedded CI dashboard URL) requests `GET /api/<stack_B>/ccmenu?token=<CI-Widget-A token>` where Stack B is an unrelated, more sensitive stack.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly rather than the api-client-scoped `stacks.from_param!`, the request succeeds and returns Stack B's `lastBuildStatus`, `activity`, `lastBuildTime`, and lock status — data the token was never authorized to access. # frozen_string_literal: true

```ruby
module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
```
