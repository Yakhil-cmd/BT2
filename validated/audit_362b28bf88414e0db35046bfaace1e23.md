### Title
`CheckReplacable` Bypasses `AccountKeyFail` Permanent Lock When New Key Type Differs — (`blockchain/types/accountkey/account_key.go`)

---

### Summary

`CheckReplacable` only calls `oldKey.CheckUpdatable()` when `oldKey.Type() == newKey.Type()`. When the types differ it falls through to `newKey.CheckInstallable()`. Because `AccountKeyFail.CheckInstallable()` returns `nil`, any holder of a live `RoleAccountUpdate` key can replace an `AccountKeyFail` slot inside an `AccountKeyRoleBased` with a live signing key, permanently restoring signing authority that was supposed to be irrevocably locked.

---

### Finding Description

**`CheckReplacable` — the type-mismatch branch skips the old key's updatability check entirely:** [1](#0-0) 

When `oldKey` is `AccountKeyFail` and `newKey` is any other type (e.g. `AccountKeyPublic`), the types differ, so the function returns `newKey.CheckInstallable(currentBlockNumber)` — which is `nil` for a valid public key — without ever consulting `AccountKeyFail.CheckUpdatable`.

**`AccountKeyFail.CheckUpdatable` is supposed to be an absolute barrier:** [2](#0-1) 

It unconditionally returns `ErrAccountKeyFailNotUpdatable`. But this method is never reached when the new key type differs.

**`AccountKeyFail.CheckInstallable` returns `nil`:** [3](#0-2) 

So `newKey.CheckInstallable()` on a valid `AccountKeyPublic` succeeds, and the check passes.

**`AccountKeyRoleBased.CheckUpdatable` calls `CheckReplacable` per-slot:** [4](#0-3) 

For each role slot where the new key is non-nil and non-composite, it delegates to `CheckReplacable((*a)[i], (*newKey)[i], ...)`. When slot `i` holds `AccountKeyFail` and the new slot holds `AccountKeyPublic`, the type-mismatch branch fires.

**`TxInternalDataAccountUpdate.Validate` is the public entry point:** [5](#0-4) 

Any user can submit a `TxTypeAccountUpdate` through the public RPC. The transaction is signed with the `RoleAccountUpdate` key (role 1), which is live. Validation calls `CheckReplacable(oldRoleBasedKey, newRoleBasedKey, ...)`, which recurses into the per-slot check above.

---

### Impact Explanation

**Concrete scenario:**

| Role | Old key | New key (attacker submits) |
|---|---|---|
| 0 — RoleTransaction | `AccountKeyFail` | `AccountKeyPublic_new` |
| 1 — RoleAccountUpdate | `AccountKeyPublic_update` (live) | `AccountKeyPublic_update` |

1. Attacker controls the `RoleAccountUpdate` key.
2. Submits `TxTypeAccountUpdate` with `AccountKeyRoleBased{AccountKeyPublic_new, AccountKeyPublic_update}`.
3. Signature validation passes (signed with role-1 key).
4. `CheckReplacable(AccountKeyFail, AccountKeyPublic_new, ...)` returns `nil` (type mismatch → `CheckInstallable` → nil).
5. `AccountKeyRoleBased.Update` writes `AccountKeyPublic_new` into slot 0 in state.
6. The account can now sign value-transfer transactions with `AccountKeyPublic_new`.

The `AccountKeyFail` invariant — that a locked role can never be replaced — is violated. KAIA balance and nonce-consumption authority are restored to a role that was supposed to be permanently inaccessible.

---

### Likelihood Explanation

Any account that has `AccountKeyRoleBased` with `AccountKeyFail` at `RoleTransaction` and a live key at `RoleAccountUpdate` is exploitable by whoever controls the update key. This is a reachable, permissionless public-RPC path requiring no privileged access beyond holding the `RoleAccountUpdate` key for the target account.

---

### Recommendation

In `CheckReplacable`, add an explicit guard before the type-mismatch branch:

```go
func CheckReplacable(oldKey AccountKey, newKey AccountKey, currentBlockNumber uint64) error {
    if oldKey.Type() == newKey.Type() {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    // AccountKeyFail must never be replaceable regardless of new key type.
    if oldKey.Type() == AccountKeyTypeFail {
        return kerrors.ErrAccountKeyFailNotUpdatable
    }
    return newKey.CheckInstallable(currentBlockNumber)
}
```
