### Title
Organization-scoped webhook signature check does not bind to the repository a `status` event writes to, allowing cross-organization CI status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to check the `X-Hub-Signature` against based solely on `params.dig('repository','owner','login')` (or `organization.login`) taken from the untrusted JSON body. [1](#0-0)  Once that check passes (or is skipped because the selected organization has no `webhook_secret` configured — an explicitly supported/"optional" configuration), the request body is dispatched to handlers that do their own, *independent* lookup of the target record. `StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)` with **no scoping to the repository/organization that was used for signature verification at all**. [2](#0-1)  This is precisely the analog of the Ajna bug class: the field that is verified (the organization used to pick/validate the signature) is not the same field that is acted upon (the commit sha, resolved globally across every repository hosted on the Shipit instance).

### Finding Description
`verify_signature` computes `repository_owner` from the payload and uses it purely to pick a `GithubApp` config (secret) to validate against:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`GithubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

Shipit's own setup docs and shipped example configs describe `webhook_secret` as optional and ship examples with it left blank for multiple organizations onboarded to the same instance. [5](#0-4) [6](#0-5) 

Meanwhile, `StatusHandler`, the handler invoked for `status` events, does not filter by any organization/repository at all — it resolves target `Commit` rows globally by `sha`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

The equality that is supposed to hold, but is broken, is:
`organization authenticated by verify_signature (repository_owner) == organization/repository whose data is mutated by the handler (Commit resolved by sha, unscoped)`

Before the attack: signature verification is scoped per organization, so an attacker without any org's `webhook_secret` cannot post events at all (assuming secrets are always configured).
After the attack: because at least one organization onboarded to the shared instance can have (and, per documentation, is expected to be allowed to have) no `webhook_secret`, the attacker authenticates trivially as "OrgWithNoSecret" and then supplies a `sha` belonging to a commit that lives in a completely unrelated repository/stack ("OrgWithSecret/private-repo"), causing a forged `Status` (`state: success`, etc.) to be written for that commit even though the request was never verified against that organization's/repository's own secret.

### Impact Explanation
`Status` records created via `create_status_from_github!` feed `Commit#last_release_status`/CI checks used by `DeploySpec#required_statuses`/`blocking_statuses` to gate whether a commit is safe to deploy, and `Status#after_commit :schedule_continuous_delivery` can trigger continuous deployment logic. [7](#0-6)  By forging a `success` status for an arbitrary commit sha on a target stack, an attacker who only ever authenticated as a *different*, unrelated organization can make an unrelated repository's commit appear CI-green, which can unblock or trigger an unauthorized deploy — matching the "Critical: unauthorized deploy" impact category. `CheckSuiteHandler` has a narrower but related issue: it does scope to `stacks` (branch-filtered) derived from `repository_name` taken from the payload, independent from the signature-verification organization, so a request authenticated as "OrgWithNoSecret" can still target `stacks` under any other repository name embedded in the same payload, scheduling `RefreshCheckRunsJob` for it. [8](#0-7) 

### Likelihood Explanation
This requires no privileged credential: the `webhooks` endpoint is unauthenticated by design (it is meant to be called by GitHub) and skips CSRF protection. [9](#0-8)  The only precondition is that at least one organization configured on the Shipit instance has no `webhook_secret` set — a state the project's own setup documentation calls out as optional and ships as the default in example secrets files for multiple orgs. [10](#0-9)  Multi-tenant Shipit deployments hosting many GitHub organizations behind one instance are an explicitly supported configuration (`Shipit.github(organization:)` dispatch), making this a realistic operational state rather than a hypothetical misconfiguration.

### Recommendation
- Scope every webhook handler's data lookups (in particular `StatusHandler`, `CheckSuiteHandler`, and any handler using `Commit.where(sha:)`/`stacks` without repository binding) to the *same* organization/repository identity that was validated during signature verification, not a value re-read independently from the untrusted payload.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is unset; either require a `webhook_secret` for every configured organization, or make an organization without a secret unable to affect any repository other than its own (impossible to enforce meaningfully, so it should not be treated as an implicit “skip verification” state).
- Ensure `repository_owner` used for the signature check exactly matches the repository/organization on which the handler subsequently operates before any state-mutating side effect (status creation, check-run refresh, sync) is applied.

### Proof of Concept
1. Shipit is configured for two organizations: `OrgA` (no `webhook_secret` set, per documented "optional" configuration) and `OrgB` (has a private stack tracking commits with `sha = S`, gated by `required_statuses`).
2. Attacker (who has no relationship with `OrgB` and no valid `webhook_secret` for it) sends:
   ```
   POST /webhooks
   X-Github-Event: status
   Body: {
     "sha": "S",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/whatever" }
   }
   ```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which returns `true` unconditionally because `OrgA`'s `webhook_secret` is nil. [11](#0-10) 
4. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the commit belonging to `OrgB`'s protected stack (no organization/repo check anywhere), and creates a forged `success` `Status` for it. [2](#0-1) 
5. `OrgB`'s commit now appears to have passed the `ci/required-check`, potentially satisfying `DeploySpec#required_statuses`/`blocking_statuses` and enabling an unauthorized deploy of that commit.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
