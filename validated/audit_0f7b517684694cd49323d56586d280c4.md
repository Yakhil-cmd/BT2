### Title
Unvalidated route venues let caller-supplied swap payloads invoke arbitrary contracts under the caller's authorization tree, draining unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
Controller strategy entrypoints (`swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`) accept a caller-supplied `StrategySwap` payload and forward it verbatim to the configured router. Neither the controller nor the router allowlists the pool/token addresses the payload names, so an attacker can craft a route whose "hop pool" is a malicious contract. When that rogue contract calls `token.transfer(victim, attacker, x)`, Soroban records the transfer as a child of the victim's authorization entry; a victim who signs the simulation-produced tree authorizes theft of any token in their wallet — unbounded by the routed amount. This mirrors the reported `safeFunctionCall` class: an open path that executes arbitrary calls to non-allowlisted targets, with privileges (`require_auth` scope) extending beyond what the caller intended.

### Finding Description
`swap_tokens` builds a router client from storage, authorizes only one exact input transfer via `authorize_transfer_as_current`, then invokes `router.execute_strategy(&controller, &amount_in, swap)` where `swap` is entirely caller-controlled [1](#0-0) . The post-call checks (`RouterOverspend`, `NoSwapOutput`, leftover refund) only bound the controller's own balances; they say nothing about which contracts the route touches [2](#0-1) . The threat model confirms the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization," and that "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [3](#0-2) . The harness test `rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates the full kill chain: a `RogueHopPool` reached via a route hop executes `token::Client::transfer(&victim, &to, &amount)` for an unrelated wallet token, the host records it under the caller's `swap_collateral` auth entry, and signing that tree drains the wallet [4](#0-3) [5](#0-4) .

### Impact Explanation
Theft of user funds. The stolen amount is any token balance/allowance the victim's address holds — entirely outside the protocol's accounting — and is bounded only by what the rogue contract requests and the victim signs. All four swap-bearing strategy entrypoints expose the surface.

### Likelihood Explanation
Requires the victim to sign a transaction whose authorization tree contains the extra child transfer. Standard flow is: receive `routeXdr` → simulate → sign the simulation-produced auth entries. A malicious or compromised quote/route source can inject the rogue hop; the simulation happily records the poisoned tree [6](#0-5) . Protection depends entirely on client-side route decoding, which the protocol documents but does not enforce on-chain. Medium likelihood, High+ impact.

### Recommendation
Constrain route execution at the contract layer: maintain a governance-managed allowlist of venue/pool addresses (or venue adapter contracts) and reject hops whose pool is not listed, analogous to the ERC-165/interface-conformance fix applied to `safeFunctionCall`. At minimum, enforce in the router that a hop may only invoke registered venue adapters rather than payload-named addresses, so third-party code can never sit below the caller's `require_auth` entry.

### Proof of Concept
1. Attacker deploys a contract with a `swap()` method that calls `token.transfer(victim, attacker, wallet_balance)` on a token the protocol never listed (the `RogueHopPool` fixture).
2. Attacker produces a route payload naming that contract as a hop pool, with honest `token_in`/`token_out` and a fair `min_out`.
3. Victim calls `controller::swap_collateral(victim, account_id, USDC_key, amount, ETH_key, route)`. The controller grants its own input transfer auth; the router invokes the rogue pool during the route.
4. Simulation records `token.transfer(victim → attacker, wallet_balance)` as a child invocation under the victim's `swap_collateral` auth entry; enforcing mode confirms the signed tree executes the transfer (`try_swap_with_signed_tree` with the rogue child succeeds and Alice's wallet goes to 0) [7](#0-6) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
