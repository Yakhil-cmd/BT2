### Title
Forged GitHub webhooks accepted for any repository when a multi-org Shipit installation contains one organization configured without a `webhook_secret` - ([File: lib/shipit/github_app.rb])

### Summary
In a multi-GitHub-App Shipit deployment, `Shipit::WebhooksController#verify_signature` picks which `GithubApp` (and therefore which HMAC secret) is used to validate an inbound webhook based on the *organization/owner login* field of the JSON payload, while the actual repository/stack that gets mutated by the event handler is selected independently from the `repository.full_name` field of the same payload. `GithubApp#verify_webhook_signature` unconditionally returns `true` when that organization's `webhook_secret` is blank. Because the two fields (`repository.owner.login` / `organization.login` vs `repository.full_name`) are both attacker-controlled and are never cross-checked against each other, an attacker can pick an organization with no configured `webhook_secret` to bypass signature verification entirely, then set `repository.full_name` to point at a stack belonging to a *different*, strictly-configured organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb` resolves the app used for verification purely from the payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`), and that value selects the `GithubApp` instance (and its secret) via `Shipit.github(organization: repository_owner)`, which in turn calls `github_app_config(organization)` to look up the per-org config in `secrets.yml`: [3](#0-2) 

Signature verification itself is a no-op whenever that organization's config has no `webhook_secret` set: [4](#0-3) 

The test fixtures for multi-org setups show this is a supported/expected configuration, where different organizations can have different (or absent) `webhook_secret` values: [5](#0-4) 

However, the field used to select the verifying organization (`repository.owner.login` / `organization.login`) is completely decoupled from the field each webhook `Handler` uses to determine which `Repository`/`Stack` to act on: `payload.dig('repository', 'full_name')`: [6](#0-5) 

For example, `PushHandler` triggers a GitHub sync for any matching stack based purely on `repository.full_name` derived stacks and `ref`/`after`: [7](#0-6) 

`MembershipHandler` creates/deletes team memberships based on `organization.login`, `team`, and `member.login` fields taken from the same unauthenticated-if-secret-absent payload: [8](#0-7) 

**The broken equality is:** `organization used to select the verifying GithubApp/secret` ≠ `repository/organization actually written to by the handler`. Nothing in `verify_signature` or in any `Handler` enforces that the `repository.owner.login`/`organization.login` used for authentication matches the `repository.full_name`/`organization.login` used for the mutation. If any one organization in a multi-org Shipit install has `webhook_secret: nil` (a supported and documented configuration, as shown in `secrets_double_github_app.yml` and `config/secrets.development.example.yml`), an attacker can:
1. Send a forged webhook with `X-Github-Event` set to `push`, `membership`, `pull_request`, etc.
2. Set `repository.owner.login` (or `organization.login`) to the name of the organization that has no `webhook_secret` configured — this causes `verify_webhook_signature` to short-circuit to `true` regardless of the (missing/garbage) `X-Hub-Signature` header.
3. Set `repository.full_name` (for push/PR events) or `organization.login`+`team`+`member` (for membership events) to target a *different* organization's repository/team that is under stricter (secret-protected) configuration.
4. The handler executes against the targeted stack/team without any real GitHub authentication, because the check that "verified" the request was scoped to an unrelated, secret-less org.

### Impact Explanation
This breaks the credential/authentication boundary between GitHub organizations in a single Shipit deployment: an attacker who can identify (or guess) that any one configured organization lacks a `webhook_secret` can forge webhooks that are treated as authentic GitHub events for a completely different organization's repositories. Depending on the handler this can:
- Trigger unauthorized `GithubSyncJob`/deploy pipeline actions on push events for arbitrary stacks (`PushHandler`).
- Add or remove arbitrary users from `Shipit.github_teams`-backing `Team`/`Membership` records via the `membership` event, which is used elsewhere to gate `User#authorized?` and team-based authorization (`app/models/shipit/user.rb`), potentially escalating a forged identity into a privileged team.
- Archive/unarchive or provision review stacks via `pull_request` events for arbitrary repositories.

This matches the "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy" impact classes.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: this is only exploitable when the Shipit installation is configured with more than one GitHub App/organization and at least one of them has no `webhook_secret` set (an allowed, documented configuration per `docs/setup.md` and the example secrets files). Single-org, single-secret deployments (`config/secrets.development.example.yml` with a set `webhook_secret`) are not affected because there is only one app to select and it always requires the secret. In multi-org setups where operators leave one org's `webhook_secret` blank (e.g., to disable verification intentionally for a low-risk org, or due to misconfiguration), the whole installation's cross-org isolation collapses, since the org selection field is never bound to the org actually mutated.

### Recommendation
- Require `webhook_secret` for every configured organization app (fail hard, don't silently return `true`), or
- After signature verification, re-validate that the organization/owner used to select the signing app matches the `repository.owner.login`/`organization.login` actually referenced by the event's target repository/organization before dispatching to handlers, rejecting mismatches with `422`.

### Proof of Concept
Given a `secrets.yml` with two orgs, `OrgOne` (has `webhook_secret: "s3cr3t"`) and `OrgTwo` (has `webhook_secret: nil`), and a Shipit stack for `OrgOne/private-repo`:

```
POST /github/webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   # arbitrary/invalid, doesn't matter

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgTwo" },      // selects OrgTwo's GithubApp -> no webhook_secret -> verify_webhook_signature returns true
    "full_name": "OrgOne/private-repo"    // handler acts on OrgOne's stack
  }
}
```

`WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")`, whose `verify_webhook_signature` returns `true` unconditionally because `OrgTwo`'s `webhook_secret` is blank [9](#0-8) 
. The request proceeds to `Webhooks::Handlers::PushHandler`, which resolves the stack from `repository.full_name = "OrgOne/private-repo"` [6](#0-5) 
and triggers `stack.sync_github(expected_head_sha: params.after)` for `OrgOne`'s stack — despite the request never being validated against `OrgOne`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

        def process
          stacks

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
