### Title
Silent swallowing of `Currency::transfer` failure in `pallet-child-bounties::claim_child_bounty` (and `pallet-bounties::claim_bounty`) permanently strands beneficiary/curator funds - ([File: substrate/frame/child-bounties/src/lib.rs])

### Summary
This is a direct FRAME analog of the reported ERC20 issue: a token-moving call's `Result` is generated but never propagated — only checked with `debug_assert!`, which is compiled out in release/production builds. If the transfer fails, the pallet still deletes the payout record and emits a "Claimed" success event, silently stranding the funds.

### Finding Description
In `Pallet::claim_child_bounty` [1](#0-0) , the fee and payout transfers are performed like this:

```rust
let fee_transfer_result = T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath);
debug_assert!(fee_transfer_result.is_ok());

let payout_transfer_result = T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath);
debug_assert!(payout_transfer_result.is_ok());
``` [2](#0-1) 

`debug_assert!` is a no-op in release builds (the configuration used by real chains). The `Result` returned by `T::Currency::transfer` (a `DispatchResult`, exactly analogous to the ignored ERC20 `bool` return value in the report) is computed and then discarded with `let _`-equivalent semantics instead of using `?`. Immediately afterward the code unconditionally:
- emits `Event::Claimed { ... payout, beneficiary }` claiming the beneficiary was paid [3](#0-2) 
- decrements the parent's child-bounty counter [4](#0-3) 
- removes the `ChildBounty` record via `*maybe_child_bounty = None` [5](#0-4) 

Once the record is removed there is no state left to retry the payment — the funds left behind in `child_bounty_account` become permanently orphaned from the perspective of the intended recipient (the `reclaim_bounty_funds` machinery only recovers funds to the *treasury*, not to the beneficiary, and even that requires the bounty to already be closed — which it now is, incorrectly).

A concrete, non-privileged, attacker/ordinary-user-reachable trigger for the transfer to actually fail: `Currency::transfer` with `AllowDeath` only permits the **source** account to be reaped below the existential deposit; it does **not** waive the requirement that a **new destination account** must receive at least the `ExistentialDeposit` to be created. If the `beneficiary` set via `award_child_bounty` (an arbitrary `AccountId` chosen by the curator, who is not root/governance and has no special trust beyond normal curator permissions) has never held a balance before, and the computed `payout = balance.saturating_sub(curator_fee)` is non-zero but below `ExistentialDeposit`, the transfer to `beneficiary` fails. The identical pattern also exists in the parent pallet, `pallet-bounties::claim_bounty`: [6](#0-5) .

Compare this to `pallet-bounties::reclaim_bounty_funds`, added specifically to recover *treasury* funds stranded by paths like this [7](#0-6)  and to `prdoc/pr_13040.prdoc`, which documents that `pallet-broker` had exactly this class of bug fixed by propagating the transfer error instead of discarding it [8](#0-7) . `pallet-bounties`/`pallet-child-bounties` were not fixed with the same rigor and still rely on `debug_assert!`.

### Impact Explanation
If the payout transfer silently fails:
- The intended beneficiary receives nothing, yet a `Claimed` event is emitted asserting they were paid — an integrity violation of the payout accounting.
- The `ChildBounty` (or `Bounty`) record is deleted, so there is no dispatchable path left to retry payment for that specific beneficiary/amount.
- The value remains locked in the `child_bounty_account`/`bounty_account`, and can, at best, later be swept to the *treasury* (not to the rightful beneficiary) via `reclaim_bounty_funds`, once the bounty is closed — which happened only because of this bug.

This is a fund-loss / stuck-fund bug for a legitimate, non-privileged actor (the beneficiary), matching the Medium severity classification of the underlying report.

### Likelihood Explanation
Likelihood is limited by the fact that a normal, well-funded, pre-existing beneficiary account will not trigger the failure — the two transfers together consume exactly `free_balance(child_bounty_account)`, so under typical conditions they succeed. However, the failure is deterministically reachable whenever the curator (via `award_child_bounty`) sets a beneficiary account that has zero prior balance and the residual `payout` after subtracting `curator_fee` is smaller than the chain's `ExistentialDeposit` — a realistic scenario for very small child bounties or bounties whose fee consumes most of the value. No privileged role, forged proof, or malicious validator is required; it is triggerable by the normal `claim_child_bounty`/`claim_bounty` extrinsics available to any signed account once the payout unlock block is reached.

### Recommendation
Replace the `debug_assert!`s with proper error propagation using `?`, e.g.:
```rust
T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath)?;
T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)?;
```
so that on failure the whole `try_mutate_exists` closure aborts, the `ChildBounty`/`Bounty` record is preserved, and the claimer can retry (e.g. after the beneficiary account is funded elsewhere to satisfy the existential deposit). Apply the same fix to the mirrored code path in `pallet-bounties::claim_bounty`.

### Proof of Concept
- Not executed against a live network; no test was run and no result is being claimed as such.
- Code-level evidence supporting the failure path:
  - Discarded `DispatchResult` from `T::Currency::transfer`, guarded only by `debug_assert!` (no-op in release builds): [2](#0-1) 
  - Unconditional event emission and irreversible state removal following the (potentially failed) transfers: [9](#0-8) 
  - Identical pattern in the parent pallet: [6](#0-5) 
  - Confirmed prior-art fix for the same bug class in `pallet-broker`, showing this exact pattern ("discarded the transfer error... removed the entitlement without payment") is a recognized, fixable defect in this codebase: [8](#0-7) 
- A minimal reproduction would require constructing a `pallet-child-bounties` mock runtime, creating a child bounty whose `value - fee` payout is smaller than the configured `ExistentialDeposit`, awarding it to a beneficiary account with zero prior balance, and calling `claim_child_bounty`; in a release-mode build (`debug_assert!` disabled) this would need to be confirmed to leave `payout_transfer_result` as `Err(_)` while the call still returns `Ok(())`. This reproduction was not executed here — flagging as unverified but structurally supported by the code and by the analogous confirmed fix in `pallet-broker`.

			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
