### Title
Webhook signature verified against one organization while `LabelCapturingHandler` mutates another organization's `PullRequest` row - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository_owner`, which is read from the attacker-controlled `repository.owner.login`/`organization.login` JSON fields. `LabelCapturingHandler#repository` (and every other `pull_request` handler) resolves the actual `Shipit::Repository`/`Stack` to mutate using a *different* attacker-controlled field, `params.repository.full_name`. Nothing binds these two fields together, so a webhook whose signature is valid for tenant "attacker-org" can carry a `repository.full_name` pointing at "victim-org/victim-repo" and have its label payload written into the victim's `PullRequest` row.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `organization_used_to_verify_signature (params.dig('repository','owner','login') || params.dig('organization','login'))` **==** `organization_owning_the_repository_mutated (owner parsed from params.repository.full_name)`.

Code path:
- `WebhooksController` runs `verify_signature` before `create`: [1](#0-0) . It picks the GitHub App config by `repository_owner`, itself taken straight from the JSON body: [2](#0-1)  and [3](#0-2) .
- `Shipit.github(organization:)` looks up per-organization app config (`github_app_config`), a documented multi-tenant feature where each GitHub org has its own `webhook_secret`: [4](#0-3) .
- Once the HMAC check against that organization's secret passes, `handler.call(params)` runs regardless of which repository the payload claims to target.
- `LabelCapturingHandler#repository` looks up the real `Shipit::Repository` purely from `params.repository.full_name`: [5](#0-4) , and `Repository.from_github_repo_name` just splits that string into `owner`/`name` and does a DB lookup with no relation to `repository_owner`: [6](#0-5) .
- `#stack` then resolves the review stack via `ReviewStackAdapter` scoped to that (victim) repository's `review_stacks`: [7](#0-6)  and `ReviewStackAdapter#stack` finds it by `environment` ("pr#{number}"): [8](#0-7) .
- `#capture_labels` then writes attacker-supplied strings straight onto the victim's `PullRequest` row with no further validation: [9](#0-8) .

Root cause: signature verification authenticates "a request signed by *some* configured organization's secret," but every downstream handler (`LabelCapturingHandler`, `OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler` - all sharing the same `params.repository.full_name` lookup pattern) trusts a completely separate, unauthenticated field to decide *which tenant's data* to touch. `Repository#owner` is only used for outbound API calls (`github_app` in `app/models/shipit/repository.rb:100-102`), never checked against the inbound `repository_owner` used at verification time.

Attacker's exact request: a POST to `/webhooks` with `X-Github-Event: pull_request`, body `action: "labeled"`, `repository.full_name: "victim-org/victim-repo"`, `repository.owner.login`/`organization.login: "attacker-org"`, `pull_request.labels: [{name: "<attacker-string>"}]`, `pull_request.number` matching a real, non-archived review stack in victim-org, signed with `X-Hub-Signature` computed using attacker-org's own `webhook_secret`.

Existing guards fail because: `verify_signature` never cross-checks `repository_owner` against `repository.full_name`; `drop_unhandled_event` only checks the event type is registered, not payload consistency; no `ExplicitParameters` schema constrains `owner.login` to equal the owner segment of `full_name`; `Repository` validations only constrain character format of `owner`/`name`, not tenant provenance.

### Impact Explanation
The attacker achieves an unauthorized, attacker-controlled database write on `Shipit::PullRequest#labels` belonging to a repository/organization they do not control and never authenticated against - a cross-tenant record mutation matching the "payload for one repository mutating another's stack" Critical category. Because `LabeledHandler`/`UnlabeledHandler` consult these same labels to decide whether to `stack.archive!`/`stack.unarchive!` the victim's review stack (`app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb:85-93`), forged labels can also trigger unintended archive/unarchive/deprovision actions on the victim's review stack — an unauthorized state change beyond simple data corruption. The attack is repeatable against any repository/PR number known to the attacker (repository names and open PR numbers are public GitHub information) as long as the Shipit deployment hosts more than one GitHub organization with distinct secrets and the attacker legitimately operates one of those tenant organizations.

### Likelihood Explanation
Requires the target Shipit instance to be configured in the documented multi-organization mode (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.*.yml` per-org `github:` blocks) with the attacker being a legitimate onboarded tenant (knows their own org's `webhook_secret`) and the victim being a different tenant on the same instance with an active, non-archived review stack for a guessable/public PR number. This is a realistic scenario for any shared/hosted Shipit deployment serving multiple organizations, and the attacker cost is a single crafted HTTP POST with a validly-computed HMAC using their own secret — no privileged access, session, or victim secret needed.

### Recommendation
In `WebhooksController#verify_signature`, or in each `pull_request` handler, enforce that the organization used to select the signing secret matches the owner segment of `params.repository.full_name` (and reject/`head(422)` otherwise) before any handler processes the payload. Alternatively, derive the repository/stack scope exclusively from the same organization identity used for signature verification rather than from an independently attacker-suppliable `full_name` field.

### Proof of Concept
Minitest plan (controller-level, no live GitHub):
1. Configure test secrets with two orgs, `attacker-org` and `victim-org`, each with distinct `webhook_secret` (reuse `test/dummy/config/secrets_double_github_app.yml` pattern).
2. Create a `Shipit::Repository` owned by `victim-org` with `review_stacks_enabled`, and a `ReviewStack` with an attached `PullRequest` for PR number `N`, `labels: []`.
3. Build a `pull_request`/`labeled` JSON payload: `repository.full_name = "victim-org/victim-repo"`, `repository.owner.login = "attacker-org"`, `organization.login = "attacker-org"`, `pull_request.number = N`, `pull_request.labels = [{name: "attacker-label"}]`.
4. Compute `X-Hub-Signature` using `attacker-org`'s `webhook_secret` over the raw JSON body.
5. POST to `/webhooks` with `X-Github-Event: pull_request` and that signature.
6. Assert response is `:ok` (signature accepted because `repository_owner == "attacker-org"` resolves to the attacker's valid secret): equality `organization_verifying_signature ("attacker-org") == organization_verifying_signature ("attacker-org")` holds.
7. Assert `victim_stack.reload.pull_request.labels == ["attacker-label"]`, demonstrating `organization_verifying_signature ("attacker-org") != organization_owning_mutated_row ("victim-org")` while the write still succeeded — proving the binding is broken.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
