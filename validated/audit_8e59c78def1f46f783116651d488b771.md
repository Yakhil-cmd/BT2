### Title
CCMenu API Token Scoped to One Stack Can Read Status of Any Stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The external report's root cause is that a credential ("API key") is authenticated but the backend fails to check that the credential is *authorized for the specific resource* named in the request (the `address_key`), letting any valid credential act on an arbitrary target. The same class of bug exists in this engine's `Shipit::Api::CCMenuController`: an `ApiClient` token that is scoped to a single stack (`stack_id` set) authenticates successfully, but the controller resolves the target stack from the *unscoped* `Stack` relation instead of the token-scoped one, so the token can read CCMenu status for any stack in the installation, not just the one it authorizes.

### Finding Description
`Shipit::Api::BaseController` establishes the binding "stack a token authorizes == stack it touches" via: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped, and `stack` looks the requested `params[:stack_id]` up only within that restricted set — this is how `ApiClient` records such as the `here_come_the_walrus` fixture (which has `stack: shipit` and no other stacks) are meant to be confined: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [3](#0-2) 

It calls `Stack.from_param!(params[:stack_id])` directly on the full `Stack` relation rather than through `stacks.from_param!` from the base controller. The controller only requires `read:stack` permission (a scope check, not a stack-identity check): [4](#0-3) 

The controller also supports authenticating via a plain query-string `token` param (in addition to Basic Auth), which is exactly how these single-stack-scoped tokens are normally distributed to third parties via `CCMenuUrlController`: [5](#0-4) [6](#0-5) 

Before the attacker's request: `ApiClient#stack_id` == stack A, `stacks` scope == `{A}`, so any legitimate use of `stack` in the base controller (or the other API controllers like `HooksController`, which reuse the scoped `stack`) is confined to `A`. After the attacker's request against `CCMenuController#show` with `params[:stack_id] = B` (any other stack, even one belonging to a different organization/repository), `stack` resolves to `B` via the unscoped `Stack.from_param!`, breaking the equality "stack authorized by the token == stack touched by the request."

### Impact Explanation
This allows a party holding a legitimately-issued, narrowly-scoped API token (e.g., a `here_come_the_walrus`-style CCMenu token meant only for stack A, often distributed as an unauthenticated-looking public CI badge URL) to read stack state (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) for any other stack in the Shipit installation, including stacks belonging to other repositories/environments the token holder has no legitimate access to. This matches the "High - unauthenticated read of stack state" impact category, since the CCMenu token is a low-privilege, often loosely-guarded credential (embedded in CI dashboard URLs) whose entire purpose is supposed to be restricted to one stack.

### Likelihood Explanation
Any holder of a valid `ApiClient` CCMenu token (which can be a `read:stack`-only, single-stack-scoped credential deliberately handed out for a CI status badge) can trivially exploit this by changing the `stack_id` path segment of the request URL — no additional privilege or secret is required beyond possessing one legitimately-scoped token.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the token-scoped `stacks` relation inherited from `BaseController` (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` on the unscoped relation, so a stack-scoped token cannot be used to read another stack's status.

### Proof of Concept
1. Create/obtain a CCMenu-only `ApiClient` scoped to stack A (`stack_id` set, `permissions: ['read:stack']`), as issued normally through `CCMenuUrlController#fetch`.
2. Send `GET /api/stacks/<owner>/<repo-B>/<env-B>/ccmenu?token=<tokenForStackA>` where `B` is any other stack in the installation.
3. Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` relation rather than the client-scoped `stacks` relation, the request succeeds and returns stack B's CCMenu XML (name, last build status, etc.), even though the token was only ever authorized for stack A.
