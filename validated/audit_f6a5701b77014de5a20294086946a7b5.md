### Title
Confidential divisible-asset payments leak co-recipients' blinding factors and change amounts to unrelated wallet peers - ([File: divisible_asset.js])

### Summary
When a private (confidential) divisible asset payment is composed with multiple outputs in a single message (e.g. a payment to an external recipient plus the sender's own change output, or multiple `asset_outputs` to several recipients in one message), the entire `payload.outputs` array — containing every output's `address`, `amount`, and `blinding` factor — is forwarded as one indivisible private-element chain to *every* wallet/device that controls *any* one of the output addresses. This lets a counterparty who is only entitled to see their own output learn the confidential amount and blinding factor of the other output(s) in the same message, enabling them to later compute the public `spend_proof` hash for that other output and thereby deanonymize/link a third party's subsequent spend on the public ledger.

### Finding Description
`composeDivisibleAssetPaymentJoint` builds a single `payload` object containing all outputs of the divisible-asset message (the destination output(s) plus the change output), and generates a `blinding` value per output: [1](#0-0) 

This payload is stored as `private_payload` / `assocPrivatePayloads[payload_hash]` and later split, after saving, into per-output chains only for *bookkeeping* purposes (`arrChains = arrPrivateElements.map(...)`), but each chain element still carries the **entire unredacted `payload.outputs` array**, i.e. it is never redacted to hide sibling outputs: [2](#0-1) 

Contrast this with the indivisible-asset path, which explicitly redacts all but the recipient's own output by hashing the rest (`output_hash`) and only revealing `our_output.address`/`blinding` for the interesting output: [3](#0-2) 

For divisible assets there is no equivalent redaction — the validation code even documents this as accepted behavior ("divisible outputs are never hidden individually"): [4](#0-3) 

On receipt, `forwardPrivateChainsToOtherMembersOfOutputAddresses` collects **all** `payload.outputs[*].address` values from the chain (not just the address belonging to the receiving wallet) and forwards the same unredacted chain to every wallet/device controlling any of them: [5](#0-4) [6](#0-5) 

The stored spend proof for a divisible-asset transfer is `hash(asset, unit, message_index, output_index, address, amount, blinding)`, and this proof is publicly recorded on the DAG in the `spend_proofs` table when the output is later spent: [7](#0-6) [8](#0-7) 

Because a co-recipient (or the recipient's cosigner/wallet peer) receives the full `{address, amount, blinding}` triple of a sibling output they were never meant to see, they can precompute that sibling's future spend-proof hash and match it against the public `spend_proofs` table once it appears on-chain — deanonymizing which public spend belongs to that address/amount, defeating the confidentiality guarantee of the private asset.

### Impact Explanation
This breaks the confidentiality property of private (is_private=1) divisible assets for any output that shares a payment message with another output whose address is controlled by a different wallet/device (a very common case: recipient output + sender's own change output, or multi-recipient `asset_outputs`/`outputs_by_asset` payments). An uninvolved but reachable party (any wallet sharing control of one of the output addresses, including shared-address cosigners and paired devices) obtains enough secret material (amount + blinding) to later link a specific address's future public spend, violating the privacy/anonymity contract that private assets are designed to provide. This is an information-disclosure impact directly analogous to CVE-2020-3996 (identifiers not scoped/redacted per recipient, leaking data to unauthorized viewers), reachable by a normal private-payment counterparty without any privileged network/hub role.

### Likelihood Explanation
Any two-output confidential divisible-asset payment (payment + change, or multi-recipient in one message) automatically triggers this exposure — no attacker action beyond normal wallet usage is required, because `composeDivisibleAssetPaymentJoint` always batches outputs into one payload and `forwardPrivateChainsToOtherMembersOfOutputAddresses`/`sendPrivatePayments` always forward the complete unredacted chain to any wallet controlling one of the output addresses. The only requirement is that at least one of the outputs is controlled by a shared/multisig address or a device other than the payer, which is a normal usage pattern (shared wallets, paired devices, multi-recipient payments).

### Recommendation
Redact private divisible-asset chains per recipient the same way indivisible assets do: when constructing or forwarding a private-element chain destined for a given output address, replace all sibling outputs' `address`/`blinding` fields with a committed `output_hash` (as already done in `indivisible_asset.js`), revealing only the output belonging to the receiving wallet/device in cleartext. Only fully reveal all outputs' cleartext data to a peer if that peer is proven to be a legitimate co-owner of all the addresses involved (e.g. a true cosigner group encompassing every output address), not merely a controller of one output address in a multi-output message.

### Proof of Concept
1. Wallet W1 has address A1; Wallet W2 (recipient) has address A2 which is a shared address with a cosigner device D3 that W1 does not know/trust.
2. W1 sends a confidential divisible-asset payment: output[0] = {A2, amount=100, blinding=b0} (to W2), output[1] = {A1_change, amount=50, blinding=b1} (change back to W1), built in `composeDivisibleAssetPaymentJoint` (divisible_asset.js:259-272).
3. After saving, the full unit's private chain (both outputs, both blindings) is sent to W2 via `sendPrivatePayments`; `handlePrivatePaymentChains` in W2 then calls `forwardPrivateChainsToOtherMembersOfOutputAddresses`, which detects that A2 is a shared address and forwards the *same, unredacted* chain (containing W1's change output address `A1_change`, `amount=50`, and `blinding=b1`) to cosigner D3 (wallet.js:1082-1114).
4. D3, who has no legitimate claim to W1's change output, now holds `{A1_change, 50, b1}` and can compute `spend_proof = hash(asset, unit, message_index, output_index, A1_change, 50, b1)`.
5. When W1 later spends that change output, the resulting `spend_proof` appears publicly in the `spend_proofs` table; D3 matches its precomputed hash against it, linking the on-chain spend to `A1_change` and `amount=50` — information D3 was never authorized to learn.

function forwardPrivateChainsToOtherMembersOfOutputAddresses(arrChains, bForwarded, conn, onSaved){
	console.log("forwardPrivateChainsToOtherMembersOfOutputAddresses", arrChains);
	var assocOutputAddresses = {};
	arrChains.forEach(function(arrPrivateElements){
		var objHeadPrivateElement = arrPrivateElements[0];
		var payload = objHeadPrivateElement.payload;
		payload.outputs.forEach(function(output){
			if (output.address)
				assocOutputAddresses[output.address] = true;
		});
		if (objHeadPrivateElement.output && objHeadPrivateElement.output.address)
			assocOutputAddresses[objHeadPrivateElement.output.address] = true;
	});
