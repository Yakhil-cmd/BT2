### Title
Cross-organization webhook forgery via decoupled signature-verification org and payload-processing repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body, while the handlers that actually act on the payload (creating commits, statuses, deploys, archiving review stacks, adding team memberships, etc.) key off `repository.full_name`, a separate, independently-controlled JSON field. In a multi-organization Shipit install (a documented, tested configuration — see `docs/setup.md` "Using Multiple Github Applications" and the `secrets_double_github_app.yml` fixture), if any one configured organization has no `webhook_secret` set (also documented as "optional"), an attacker can send a forged webhook whose `repository.owner.login`/`organization.login` points at the secret-less org (bypassing HMAC verification entirely) while `repository.full_name` points at a stack belonging to a different, secret-protected organization.

### Finding Description
`verify_signature` computes `repository_owner` purely from the attacker-controlled payload and uses it to pick the `GitHubApp`/secret for verification: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` unconditionally accepts the request when that organization's `webhook_secret` is blank: [4](#0-3) 

Once verification "passes" (or is bypassed), the raw, unauthenticated `params` are handed to every registered handler: [5](#0-4) 

Handlers resolve the target stack/repository from `repository.full_name`, a field completely independent of `repository.owner.login` used for verification: [6](#0-5) [7](#0-6) [8](#0-7) 

Because nothing ties `repository.owner.login` (the field the signature check is scoped to) to `repository.full_name` (the field the write actually targets), an attacker who knows any org in the install lacks a `webhook_secret` can freely forge `repository.owner.login`/`organization.login` = that org while setting `repository.full_name` = `<protected-org>/<target-repo>`. The binding broken is: `org authenticated (repository.owner.login used for HMAC selection) == repo written (repository.full_name used by handlers)`. Before the attack these are always equal for legitimate GitHub-originated payloads (GitHub sets both consistently); the attacker's forged request breaks that equality since the payload is entirely attacker-controlled JSON with no signature covering this cross-field consistency (the signature check is skipped, not merely miscomputed).

### Impact Explanation
This allows unauthenticated cross-organization forgery of GitHub events against stacks owned by a fully-secured organization, using only the fact that some other org in the multi-tenant install has no webhook secret. Depending on handler, this yields: forced `push`/`status`/`check_suite` events that trigger `sync_github`/continuous deployment on unreviewed commits, forged `pull_request`/`membership` events that create `Shipit::Team`/`Membership` records or manipulate review-stack lifecycle (archive/unarchive/provision), and other stack-state mutations — all without possessing any organization's real webhook secret. This matches the "unauthorized deploy" and "authorization escalation via `Shipit.github_teams`" impact tiers.

### Likelihood Explanation
Exploitability only requires the attacker to know that at least one organization configured in the Shipit installation has no `webhook_secret` (an explicitly documented, supported, and unit-tested configuration per `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), and to know the `owner/name` of the target stack in another organization (public information for any public repo). No GitHub credentials, API tokens, or session access are needed — only network access to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification to the same identity used for locating the target resource: verify the HMAC using the `GitHubApp` resolved from `repository.full_name`'s owner (not a possibly different `repository.owner.login`/`organization.login`), and reject requests where these fields diverge. Additionally, consider requiring `webhook_secret` to be present for all configured organizations (fail closed) rather than treating a blank secret as "always verified".

### Proof of Concept
1. Configure Shipit with two organizations as in `test/dummy/config/secrets_double_github_app.yml`: `OrgOne` (no `webhook_secret`) and `OrgTwo` (`webhook_secret` set), each with existing stacks.
2. As an unauthenticated attacker, POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha already known to be reachable>",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/protected-repo" }
}
```
3. `verify_signature` resolves `repository_owner` = `"OrgOne"`, loads `Shipit.github(organization: "OrgOne")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` immediately per `lib/shipit/github_app.rb:76-83`, regardless of the header contents.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgTwo/protected-repo")` and syncs/deploys the `OrgTwo` stack based entirely on attacker-supplied `after`, achieving state changes on an organization whose webhook secret was never disclosed to or known by the attacker.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
