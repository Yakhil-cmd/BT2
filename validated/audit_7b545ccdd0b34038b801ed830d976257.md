### Title
`ReopenedHandler#unarchive?` operator-precedence bug bypasses `repository.review_stacks_enabled` gate - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == true` must gate **all** re-provisioning paths, i.e. `unarchive?` should be `review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`.

The actual code at [1](#0-0)  is:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby's `&&` binds tighter than `||`, so this parses as:

`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` is only ANDed into the first disjunct. The third disjunct — `prevent_with_label? && !has_label?` — is fully independent of `review_stacks_enabled`. So on a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, if the PR has no provisioning label, `unarchive?` still evaluates to `true`.

Exploit flow: attacker opens/owns a PR against a repo configured with `review_stacks_enabled: false`, `provisioning_behavior: prevent_with_label`, no label applied. Attacker sends `action=closed` (triggers `ClosedHandler#process` → `review_stack.archive!` [2](#0-1) ), then `action=reopened`. `ReopenedHandler#process` calls `respond_to_pull_request_reopened?` → `unarchive?`, which returns `true` via the third disjunct regardless of `review_stacks_enabled` [3](#0-2) . `stack.unarchive!` is then invoked on the `ReviewStackAdapter`, which — if the stack is archived (or absent) — enqueues `Shipit::ReviewStackProvisioningQueue.add(stack)` and calls `stack.unarchive!` [4](#0-3) , re-triggering provisioning from the attacker-controlled `head.ref`/`shipit.yml`.

Existing guards do not stop this: `verify_signature` only validates the GitHub webhook HMAC (or is a no-op if no `webhook_secret` configured) and has nothing to do with per-repository provisioning policy [5](#0-4) ; `drop_unhandled_event` only checks that a handler exists for the event type, not the payload's fields [6](#0-5) ; the `params` schema in the handler validates payload shape/types but has no bearing on `repository.review_stacks_enabled` [7](#0-6) . None of these validate or enforce the disabled-review-stacks invariant — that responsibility rests solely on `unarchive?`, which is broken.

An unprivileged attacker (owner of the PR / the fork) can send these two webhook POSTs to their own PR — a repository maintainer's decision to disable review stacks (`review_stacks_enabled: false`) is fully bypassable by the PR author for repos also using `prevent_with_label` provisioning behavior.

### Impact Explanation
On a repository where the maintainer explicitly disabled review-stack provisioning (`review_stacks_enabled: false`) and also configured `provisioning_behavior: prevent_with_label`, an attacker who owns a PR can force `stack.unarchive!` and re-queue provisioning (`ReviewStackProvisioningQueue.add`), leading to re-execution of the repository's provisioning task from the attacker's branch/ref. This is a command-execution/RCE-adjacent path on the deploy host through the standard task-execution pipeline (`TaskCommands`/`Command`), for a repository whose owner explicitly opted out of this feature — an authorization bypass of the `review_stacks_enabled` control. This affects only the specific repository the attacker has a PR on (not cross-tenant), but is fully repeatable (close/reopen any number of times) against any repository with this specific configuration combination.

### Likelihood Explanation
Preconditions: repository has `review_stacks_enabled: false` AND `provisioning_behavior: prevent_with_label` AND the PR carries no provisioning label. This is a plausible, even likely, real-world configuration (operator wants review stacks off by default, but still sets a provisioning-behavior enum value, not realizing the two settings interact incorrectly). Attacker cost is trivial: open/own a PR, close it, then reopen it — two ordinary, unauthenticated-by-Shipit webhook events triggered by normal GitHub PR actions. No secrets or elevated privileges are required.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` is ANDed across the entire disjunction:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (
      repository.provisioning_behavior_allow_all? ||
      (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
      (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
    )
end
```

### Proof of Concept
Minitest plan in `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb` (existing suite file):
1. Create a `Repository` fixture/record with `review_stacks_enabled: false`, `provisioning_behavior: "prevent_with_label"`.
2. Create an archived `ReviewStack` for `environment: "pr#{number}"` on that repository (or none, to test the `create!` branch).
3. Build a `reopened` webhook payload for that repository/PR with an empty `labels` array.
4. Assert, before the fix: `Shipit::ReviewStackProvisioningQueue.expects(:add)` and `stack.expects(:unarchive!)` (or equivalent) ARE invoked, and `repository.review_stacks_enabled` is `false` — demonstrating the two disagree (violating the intended equality that `unarchive?` should equal `review_stacks_enabled && behavior_condition`).
5. After the fix, assert `ReopenedHandler.new(payload).process` (or `unarchive?`) returns `false`/does not call `unarchive!`/`ReviewStackProvisioningQueue.add` when `review_stacks_enabled` is `false`, for all three provisioning-behavior branches.
