### Title
Webhook signature verification selects the signing organization/secret from an untrusted payload field that differs from the field used to select the repository/stack acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and thus which `webhook_secret`) to verify a webhook against using `params.dig('repository', 'owner', 'login')` (or `organization.login`), a value read straight out of the same JSON body the signature is supposed to protect. Once "verified," the actual handler (e.g. `PushHandler`, via `Shipit::Webhooks::Handlers::Handler#stacks`) resolves the target `Repository`/`Stack` from a *different* field in that same body: `repository.full_name`. In a multi-organization Shipit deployment (a documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`), each organization has its own independent `webhook_secret`. Nothing binds `repository.owner.login` (used to choose the secret) to `repository.full_name` (used to choose the stack that gets written to).

### Finding Description
`config/routes.rb` exposes a single shared `/webhooks` endpoint for all configured GitHub organizations [1](#0-0) . `Shipit.github(organization:)` looks up per-organization app configs, each with an independently configured `webhook_secret` [2](#0-1) , exactly as documented for multi-org setups [3](#0-2)  and exercised in tests with `OrgOne`/`OrgTwo` each having their own `webhook_secret` [4](#0-3) .

`WebhooksController#verify_signature` derives the organization used to select the verifying secret purely from the incoming payload:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

`GitHubApp#verify_webhook_signature` performs a standard HMAC compare against that organization's own `webhook_secret` [6](#0-5) .

After the signature check passes, `create` parses the body and dispatches to registered handlers [7](#0-6) . The base `Handler` class resolves the target repository/stacks not from `repository.owner.login`, but from a separate field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [8](#0-7) 

`PushHandler#process` uses this to enqueue a real state-mutating sync on whatever stack matches, keyed only on branch:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [9](#0-8) 

This dispatches `GithubSyncJob`, which fetches commits from GitHub and appends them to the stack's commit history, transactionally mutating the target stack's state (detaching/creating commits, locking reverted commits, refreshing the cached deploy spec) [10](#0-9) .

**The binding that is broken**: verification binds "signature valid" to `organization == repository.owner.login` (as read from the unverified body), but the write path binds "stack acted upon" to `repository.full_name` (also read from the same unverified body) — with no cross-check that these two fields agree, and no check that `repository.full_name`'s owner is actually the organization whose secret validated the request.

**Concrete equality that should hold but doesn't**: `organization_whose_secret_verified_signature == owner_of(repository.full_name_used_for_dispatch)`. Because both values are taken from attacker-supplied JSON before/independent of any binding between them, an attacker who is a legitimate, low-privilege participant in *any one* configured GitHub organization (i.e., they know or can trigger that organization's `webhook_secret`, e.g. because they administer that org's GitHub App or can capture its webhook deliveries) can sign a payload whose `repository.owner.login`/`organization.login` matches their own org (so `Shipit.github(organization: their_org)` picks a secret they can produce a valid HMAC for) while setting `repository.full_name` to `victim-org/victim-repo`, an entirely different, already-configured Shipit stack belonging to another tenant organization.

### Impact Explanation
This crosses the "cross-repository writes" bar explicitly listed as Critical impact. An attacker who only controls (or can forge signatures for) one tenant organization in a multi-org Shipit deployment can, without any Shipit session, `ApiClient` token, or repository write access to the victim's actual GitHub repository, inject a forged `push` (or other) webhook that is accepted as authentic and dispatches `GithubSyncJob`/`PushHandler` against an unrelated victim stack. This can append attacker-influenced commit records, lock/unlock reversion state, and force deploy-spec cache refresh on a repository/organization the attacker has no legitimate relationship to — an unauthorized, cross-tenant mutation of deployment state.

### Likelihood Explanation
Requires: (1) Shipit configured with more than one GitHub organization (a documented, supported, non-default configuration), and (2) attacker access to at least one configured organization's `webhook_secret` (e.g., as an admin of their own small/low-trust org onboarded onto the same Shipit instance, or via leaked webhook secret for one tenant). This is a realistic multi-tenant SaaS/shared-Shipit-instance scenario and requires no Shipit account, API token, or GitHub write access to the victim organization — matching the "unprivileged attacker" threat model. Likelihood is Medium-to-High specifically in shared/multi-org deployments, which is the deployment mode this feature exists to support.

### Recommendation
Bind signature-secret selection to the same field(s) used for dispatch, and re-validate consistency after verification:
- After determining `repository_owner` for secret selection, re-derive the acting repository from `repository.full_name` and require that its owner segment matches `repository_owner` (case-insensitively) before dispatching to handlers; reject (422) on mismatch.
- Alternatively/additionally, verify the payload against the webhook secret of the organization that actually owns the target `Repository` record resolved via `Repository.from_github_repo_name(repository.full_name)`, rather than trusting an unauthenticated `owner.login`/`organization.login` field to pick the verifying key.
- Add regression tests asserting that a webhook signed with Org A's secret but referencing Org B's `repository.full_name` is rejected.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`), and a legitimately provisioned stack for `OrgB/victim-repo`.
2. As an attacker who knows `OrgA`'s `webhook_secret` (e.g., an admin of the low-trust `OrgA` GitHub App), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-or-real-sha>",
     "repository": {
       "owner": { "login": "OrgA" },
       "full_name": "OrgB/victim-repo"
     }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>`.
4. POST to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, verifies the HMAC successfully against `OrgA`'s secret [11](#0-10) .
6. `create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("OrgB/victim-repo")` [8](#0-7)  and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s stack [9](#0-8) , enqueuing `GithubSyncJob` which mutates `OrgB`'s commit/deploy-spec state [10](#0-9) .

Note: I could not fully trace how every event handler (beyond `PushHandler`) resolves its target repository, nor confirm the exact production behavior of GitHub's own webhook delivery for multi-org installs (e.g., whether GitHub itself would ever emit a body with mismatched `owner.login` vs `full_name`) — this analysis assumes the attacker crafts the HTTP request directly rather than relying on GitHub's own webhook delivery, which is consistent with the "unprivileged attacker" threat model (no GitHub write access required, only knowledge of one tenant's webhook secret).

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      verified = github_app.verify_webhook_signature(

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end
