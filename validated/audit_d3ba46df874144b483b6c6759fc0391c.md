### Title
Webhook signature verification selects the signing organization from `repository.owner.login`, but handlers act on the unbound `repository.full_name` (and global commit sha), allowing any onboarded organization's webhook secret to forge events for other organizations' stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to use for HMAC validation based on a field read out of the *same, attacker-suppliable* JSON body (`repository.owner.login`, falling back to `organization.login`), while the handlers that actually mutate state key off a *different* field in that same body (`repository.full_name`, or in `StatusHandler` a bare, cross-stack `sha` lookup with no repository scoping at all). Nothing enforces that `repository.full_name` belongs to the organization named in `repository.owner.login`. Anyone who knows the `webhook_secret` for *any* organization configured in `Shipit.github` (a normal, unprivileged fact for a customer/org-admin operating their own GitHub App/webhook on a shared, multi-tenant Shipit install) can craft an arbitrary payload signed with their own secret and drive handlers against a completely different organization's repositories/stacks.

### Finding Description
The controller resolves the verification secret like this: [1](#0-0) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

The secret used for HMAC comparison is chosen from the attacker-controlled body itself, then `Shipit::GithubApp#verify_webhook_signature` does a `secure_compare` against that org's configured secret: [3](#0-2) 

Once "verified", every handler resolves the *repository/stack to act on* from a **different** payload key, `repository.full_name`, via the base `Handler` class: [4](#0-3) 

There is no check anywhere that `repository.full_name.split('/').first == repository.owner.login` (or `organization.login`). Both fields sit inside the same HMAC-covered raw body, but the HMAC only proves "whoever crafted this body knows the secret for the org named in `owner.login`" — it does not prove that `full_name` is scoped to that org. Since `Shipit.github(organization: ...)` config supports multiple independently-configured organizations, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml`), a party that legitimately controls one onboarded organization's webhook secret can forge a signature for a payload that names a victim organization's repository in `full_name`.

This breaks the binding: **organization authenticated (`repository.owner.login` used to select the verifying secret) = organization actually written (derived from `repository.full_name` used by handlers to locate the `Stack`/`Repository`)**. Before this "PR" (i.e., in the current code), these two are never checked for equality; only "after" a fix would `repository_owner` and `repository_name`'s org component be required to match.

Concrete exploitable handlers:
- `Handlers::PushHandler#process` calls `stack.sync_github` for every non-archived stack matching the forged `full_name`/branch, regardless of which org's secret validated the request: [5](#0-4) 
- `Handlers::StatusHandler#process` is even less scoped: it looks up commits **globally by `sha`** with no repository/stack check at all, and creates a GitHub status on them from fully attacker-controlled `state`/`context`/`description`: [6](#0-5) 

A forged `state: "success"` status on an arbitrary victim commit sha feeds directly into the auto-deploy pipeline: [7](#0-6) [8](#0-7) 
which schedules `ContinuousDeliveryJob`, and `Stack#trigger_continuous_delivery` will call `trigger_deploy` if the commit becomes `deployable?`: [9](#0-8) 

### Impact Explanation
This is an **unauthorized deploy** path (Critical per the rubric): by knowing only one organization's `webhook_secret` (a credential an org-admin plausibly controls for their own GitHub App on a shared/multi-tenant Shipit deployment), an attacker can forge a validly-signed webhook whose `repository.owner.login`/`organization.login` matches their own org (so signature check passes) while `repository.full_name` (PushHandler/PullRequest handlers) or the bare `sha` (StatusHandler, which doesn't even check `full_name`) targets a victim organization's stack/commit. This can force a CI status of `success` onto an arbitrary commit belonging to a different, unrelated stack, which — for stacks with `continuous_deployment: true` — triggers an unauthorized deploy of that victim's code. It also lets the attacker force `GithubSyncJob` runs against arbitrary victim stacks via `PushHandler`, and (via `MembershipHandler`, scoped to `organization.login` rather than `repository`) manipulate `Team` membership records tied to `Shipit.github_teams` authorization if the attacker's own org name happens to collide with/alias a team's org field.

### Likelihood Explanation
Requires no privileged Shipit session, `ApiClient` token, or GitHub repository write access — only knowledge of a `webhook_secret` for *some* organization already onboarded onto the shared Shipit instance (which the report and `config/secrets.*.yml` confirm is a normal per-organization, admin-controlled secret in multi-tenant configurations, not a Shipit-instance-wide secret). Crafting the forged JSON body and computing an HMAC over it are trivial once that secret is known; no interception, TLS bypass, or social engineering is needed. This is realistically exploitable on any Shipit deployment hosting multiple organizations/GitHub Apps behind the single shared `/webhooks` endpoint.

### Recommendation
Bind the field used to select the verification secret to the field used to locate the target resource:
- After computing `repository_owner` for secret selection, also derive the organization portion of `repository.full_name` (or `organization.login` used by handlers) and reject the request (422) unless they are equal.
- In `Handlers::Handler#repository_name`/`#stacks`, additionally verify the resolved `Repository`'s owner/org matches the `X-Hub-Signature`-verified organization, not just parse `full_name` blindly.
- Fix `StatusHandler` specifically to scope its `Commit.where(sha: ...)` lookup by the repository named in the payload (joined through `stack.repository`), not a bare global sha lookup.
- Consider moving to GitHub App-level signature verification tied to the installation, so the signing party is cryptographically bound to the specific installation/repository rather than a free-text JSON field.

### Proof of Concept
1. Shipit instance is configured (per `config/secrets.*.yml`) with two organizations, e.g. `victim-org` and `attacker-org`, each with its own `webhook_secret`.
2. Attacker (an admin of `attacker-org`, who legitimately knows `attacker-org`'s `webhook_secret` from configuring their own GitHub App/webhook) crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha, e.g. taken from victim-org's public repo>",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` and the signature validates successfully.
5. `Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit in an entirely different stack — and creates a `success` status on it, independent of `attacker-org` having any relationship to that commit/stack.
6. If the victim stack has `continuous_deployment: true` and the commit becomes `deployable?`, `schedule_continuous_delivery` / `ContinuousDeliveryJob` triggers `Stack#trigger_continuous_delivery`, resulting in an unauthorized deploy of the victim's code.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
