### Title
Cross-organization webhook forgery — GitHub org used to select the signing secret differs from the repository the webhook handler actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to validate a webhook against using a field read straight out of the *unverified* JSON body, while the handlers that actually process the same body pick the target repository/stack using a *different, independently-controlled* field of that body. An attacker who legitimately knows the `webhook_secret` for one configured GitHub organization on a multi-tenant Shipit instance can therefore produce a validly-signed payload whose “owning organization” is their own, but whose acted-upon `repository.full_name` belongs to a different organization/stack, letting them forge push/status/PR events against stacks they do not control. This mirrors the `sDaiStrategy` bug class: one gate (the pause / here, the signature check) is keyed to a value that is not the same value the rest of the logic subsequently trusts, so satisfying the gate for “your own” resource silently authorizes action on someone else's.

### Finding Description
`verify_signature` derives the org used to look up the signing secret entirely from the untrusted request body: [1](#0-0) [2](#0-1) 

`repository_owner` is `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a value inside the JSON body that is covered by the HMAC signature bytes, but whose *semantic meaning* (“which org’s secret to check against”) is chosen by the attacker before verification happens. Shipit supports configuring multiple GitHub orgs, each with its own `webhook_secret`, precisely so `Shipit.github(organization: ...)` can select the right one — see the multi-org secrets layout. [3](#0-2) 

Once the signature check passes (because the attacker used the secret of an org they legitimately administer), the actual event handlers resolve the target repository/stack from a *separate* field of the same body — `repository.full_name` — via `Handler#stacks`/`#repository_name`: [4](#0-3) 

For example `PushHandler` looks up stacks purely by that resolved repository and the pushed branch/ref, and syncs them to the attacker-supplied `after` SHA: [5](#0-4) 

Nothing ties `repository.owner.login` (the field that selected the verifying secret) to `repository.full_name` (the field that selects the stack actually mutated). An attacker can set them to different organizations in the same payload:
- `repository.owner.login = "attacker-org"` → signature validated with `attacker-org`’s known `webhook_secret`.
- `repository.full_name = "victim-org/victim-repo"` → the stack that is actually synced/updated.

This breaks the intended binding: **organization authenticated == organization/repository written**, exactly the equality class called out in scope (“an organization that authenticated versus the repository that is written”).

### Impact Explanation
Using this mismatch, an attacker who is a legitimate committer/admin on any one GitHub organization hosted on the shared Shipit instance (and therefore knows that org's `webhook_secret`) can forge signed webhooks that affect a completely different organization's stacks:
- `push` events can force `GithubSyncJob`/`sync_github` on a victim stack with an attacker-chosen `after` SHA, corrupting the stack's notion of `HEAD`/deployable commits.
- `status`/`check_suite` events (same `Handler#stacks` resolution pattern) can forge green CI statuses/check runs on a victim commit, defeating the `ci.require` gate documented for deploys and enabling an **unauthorized deploy** of a commit that never actually passed CI on the real repository.

This lands in the "unauthorized deploy" bucket of the accepted High/Critical impacts, achieved purely by an unprivileged-to-the-victim-org attacker who only needs legitimate access to one, unrelated, configured GitHub organization.

### Likelihood Explanation
Medium: it requires Shipit to be configured for multiple GitHub organizations (a documented, supported configuration) and requires the attacker to control/administer at least one such org (enough to read the `webhook_secret` they configured for their own repo/app). Given that requirement, crafting the divergent payload is trivial (no exploitation of any other service needed, plain HTTP POST with correct HMAC).

### Recommendation
Bind the field used to select the verifying secret to the field used to resolve the target repository — they must be the same value, checked before any handler runs. Concretely, have `Handler#repository_name`/`#stacks` reuse the exact `repository_owner` (or its full `owner/name`) that `WebhooksController#verify_signature` already resolved and validated, rejecting the request if the two disagree, instead of independently re-parsing `repository.full_name` deep inside each handler.

### Proof of Concept
1. Configure Shipit with two orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as supported by `config/secrets.*.yml`).
2. Attacker, who administers `attacker-org` and therefore knows `attacker-org`'s `webhook_secret`, crafts a `push` (or `status`) event body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. Computes `X-Hub-Signature: sha1=HMAC(attacker-org-secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s app, and the signature validates successfully. [1](#0-0) 
5. `PushHandler#process` resolves stacks via `repository_name = "victim-org/victim-repo"` (independent of the value used above) and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on victim-org's stack, despite the attacker having no credentials or webhook secret for `victim-org`. [4](#0-3) [5](#0-4)
