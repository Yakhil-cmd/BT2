### Title
Unauthenticated task trigger when `Shipit.disable_api_authentication` is true - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
When `Shipit.disable_api_authentication` is set, `authenticate_api_client` unconditionally assigns `@current_api_client = UnlimitedApiClient.new` with no check of the `Authorization` header or `params[:token]`. `UnlimitedApiClient#check_permissions!` is a no-op, so `require_permission!(:deploy, :stack)` on `Shipit::Api::TasksController#trigger` never raises, letting the request proceed with `current_user` defaulting to `AnonymousUser` since no `X-Shipit-User` header was supplied.

### Finding Description
The binding that should hold is: for any action gated by `require_permission!`, either `current_api_client` is a real authenticated `ApiClient` (verified via `ApiClient.authenticate(token)`/`BasicAuth.authenticate`) **or** `current_user` is a real, session/header-identified `User` — i.e. `authenticated?(current_api_client) || authenticated?(current_user)` must be true before task-mutating code executes. Tracing `authenticate_api_client`: [1](#0-0) 

shows that when `Shipit.disable_api_authentication` is truthy, `@current_api_client` is set to `UnlimitedApiClient.new` regardless of any request headers — no `Authorization` parsing, no `params[:token]` check occurs on this branch. `UnlimitedApiClient` is a stub whose `check_permissions!` is intentionally a no-op: [2](#0-1) 

`require_permission!` simply forwards to `current_api_client.check_permissions!`, so it always succeeds: [3](#0-2) 

`TasksController` declares `require_permission :deploy, :stack, only: %i[trigger abort]`, and `trigger` calls `stack.trigger_task(params[:task_name], current_user, env: params.env)`, rendering `202 Accepted`: [4](#0-3) 

`current_user` falls back to `AnonymousUser.new` when `X-Shipit-User` is absent or unmatched: [5](#0-4) 

Root cause: the `disable_api_authentication` branch bypasses the authentication check entirely (not just relaxes permission checks) and there is no separate gate ensuring `current_user` is a real, identified user before a deploy/abort task is created. Existing guards (`verify_signature`, `ExplicitParameters` schema, model validations) are irrelevant here — they don't touch controller-level authentication/authorization, and none of them intercepts this path.

Attacker request: any unauthenticated `POST /api/stacks/:id/tasks/deploy` (or any stack id resolvable via `stacks.from_param!`) with zero auth headers. Since `stack_id?` is `false` on `UnlimitedApiClient`, `stacks` resolves to `Stack.all`, so any stack is reachable; `require_permission!` never raises; `trigger` creates a real `Task` with `user == AnonymousUser` and returns `202`.

### Impact Explanation
An unauthenticated attacker can trigger arbitrary deploy/rollback/lock tasks on any stack, which is an unauthorized-deploy scenario — Critical severity per the rubric's "unauthorized deploy, rollback" category. The task record is created and processed by the normal task pipeline (potentially invoking `Command`/`PTY.spawn` on the deploy host), meaning this can lead to command execution using the host's deploy credentials, not merely a data-read issue. It is fully repeatable against any stack ID and not scoped to a single tenant, since `UnlimitedApiClient#stack_id?` returns `false`, granting cross-stack reach.

### Likelihood Explanation
This requires `Shipit.disable_api_authentication` to be enabled on the deployment; the question's Scope explicitly permits assuming this as an engine-code-path precondition (not host misconfiguration) since the vulnerable logic — the unconditional `UnlimitedApiClient.new` assignment and the no-op `check_permissions!` — lives entirely inside this engine's controller and model code. Given that precondition, the attacker cost is a single unauthenticated HTTP POST with no token, header, or secret of any kind, making exploitation trivial and fully repeatable.

### Recommendation
When `disable_api_authentication` is enabled, still require some form of caller identification (e.g., derive `current_user` from `X-Shipit-User` and reject if absent), or restrict `UnlimitedApiClient` to read-only permissions instead of a blanket no-op `check_permissions!`, so that mutating actions (`trigger`, `abort`) cannot proceed with an `AnonymousUser`. At minimum, document and enforce that this flag must never be enabled without another authentication layer (e.g., a reverse proxy), and add an explicit check in `trigger`/`abort` requiring `current_user` to be a real, non-anonymous `User`.

### Proof of Concept
Minitest plan (`test/controllers/shipit/api/tasks_controller_test.rb`-style, hypothetical):
```ruby
test "#trigger creates a task for an anonymous caller when api authentication is disabled" do
  Shipit.stubs(:disable_api_authentication).returns(true)
  stack = shipit_stacks(:shipit)
  assert_difference -> { stack.tasks.count }, 1 do
    post api_stack_tasks_path(stack), params: { task_name: 'deploy' }
    # no Authorization header, no params[:token], no X-Shipit-User header set
  end
  assert_response :accepted
  task = stack.tasks.last
  assert_kind_of Shipit::AnonymousUser, task.user
end
```
Before fix: assertion passes (202, task created, `user` is `AnonymousUser`) — demonstrating the bypass. After fix: the request should be rejected (e.g., `401`/`403`) or `current_user` must be a real identified `User`, i.e. the equality `current_api_client == UnlimitedApiClient.new && current_user == AnonymousUser.new` reaching `trigger`'s task-creation code must no longer hold.
