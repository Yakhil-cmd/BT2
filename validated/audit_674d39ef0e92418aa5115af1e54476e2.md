### Title
Webhook signature verification is scoped to the wrong organization, allowing cross-repository forged commit statuses to unblock deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using an unverified field taken directly from the request body itself, while the handlers that subsequently act on that same body determine *what* gets written using an entirely different, unbound field (or no repository scoping at all). This is the same class of bug as the Krystal DeFi report: two steps of a workflow (approve vs. reset-approve; here, "which secret authenticates" vs. "what gets mutated") are supposed to be tied to the same identity but are not, breaking the trust binding.

### Finding Description
`WebhooksController#verify_signature` picks the signing secret with: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`) *before* the signature has been proven valid — it is only used to pick which org's secret to check the signature against. Once `verify_webhook_signature` succeeds (i.e., the request was actually signed with the org named in that field), the full `params` hash — including `repository.full_name` and any other field — is handed unmodified to every registered handler: [3](#0-2) 

Handlers determine the target stack/commit from a *different* part of the same payload. Most handlers scope via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`: [4](#0-3) 

But `StatusHandler`, which processes the GitHub `status` event, doesn't even use that repository scoping — it looks up commits **globally by SHA across every stack in the Shipit instance**: [5](#0-4) 

This creates two separate binding breaks:
1. Organization-that-authenticated (`repository_owner`, used to fetch the correct `webhook_secret` and verify the HMAC) ≠ repository written (`repository.full_name`, freely chosen by the sender in the same signed body).
2. `StatusHandler` doesn't consult repository/org scoping at all — any organization that owns *any* stack tracked by the Shipit instance, and therefore knows its own legitimate `webhook_secret`, can sign a `status` payload naming any `sha` value and have it applied to whichever commit(s) match that SHA in **any** stack, including ones belonging to unrelated organizations.

Creating a `Status` record is not inert: `Commit#create_status_from_github!` → `add_status` runs `after_create :enable_ci_on_stack` and fires the `commit_status`/`deployable_status` hooks and `schedule_continuous_delivery`, which gates whether a commit is eligible for automatic/continuous deployment: [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
An org that legitimately owns one repository tracked by the Shipit instance (and thus legitimately knows its own `webhook_secret`) can forge a `status` webhook, signed with its own secret, whose `sha` matches a commit that also belongs to a *different* organization's stack (this occurs whenever the same commit exists in more than one tracked repo — e.g. forks, mirrors, or repos migrated/renamed within the same Shipit install). Because `StatusHandler` performs no per-repository/org authorization check, it will happily write a forged `success` CI status onto that victim commit. Since commit statuses drive `required_statuses`/`blocking_statuses` checks that gate `deployable?` and `continuous_delivery`, this can cause an unauthorized/automated deploy of a commit that never actually passed CI in the correct repository — matching the "Critical: unauthorized deploy" bar. It is a cross-organization write of trust-relevant state without possession of the target organization's credentials.

### Likelihood Explanation
Exploitation requires the attacker to control (or already legitimately administer) a GitHub organization/repository that is separately onboarded into the same Shipit instance — i.e., they need to be a "confused" but otherwise-legitimate tenant of the multi-tenant Shipit deployment, not an anonymous internet attacker with zero relationship to the system. This is a real but narrower privilege boundary than a fully unauthenticated attacker, so likelihood is assessed as moderate: it applies specifically to Shipit deployments that host stacks for multiple, mutually-distrusting GitHub organizations (a supported and documented configuration, since `Shipit.github(organization:)` is keyed per-organization).

### Recommendation
Bind the signature-verifying organization to the object actually being mutated:
- In `WebhooksController`, after verifying the signature, verify that `repository.owner.login`/`organization.login` used to select the secret matches `repository.full_name`'s actual owner before dispatching to handlers.
- In `StatusHandler#process`, scope the `Commit.where(sha: params.sha)` lookup to `stacks` (i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) exactly as `Handler#repository_name`/`#stacks` already does for other handlers, rather than querying commits globally by SHA.

### Proof of Concept
1. Organization `attacker-org` legitimately owns repository `attacker-org/foo`, which is tracked as a Shipit stack, and knows its own `webhook_secret` (configured through the normal GitHub App / webhook setup for that org).
2. Organization `victim-org` owns `victim-org/foo`, also tracked in the same Shipit instance, whose commit history shares a SHA with `attacker-org/foo` (e.g., because it's a fork/mirror or a shared vendored history).
3. Attacker crafts a GitHub `status` webhook body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/foo"}, "sha": "<shared-sha-also-in-victim-org/foo>", "state": "success", "context": "ci/required-check", ...}`.
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s own `webhook_secret` over the raw JSON body and POSTs it to `/webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature (it *is* correctly signed by that org's real secret) — the request passes verification.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns the matching commit belonging to `victim-org/foo`'s stack (not `attacker-org/foo`'s), and calls `commit.create_status_from_github!(params)`, writing a forged `success` status onto the victim's commit and potentially unblocking its deploy.
