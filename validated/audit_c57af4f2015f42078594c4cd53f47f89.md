### Title
Asset issuer can retroactively revoke/replace the trusted attestor list, freezing spending rights of already-issued and already-attested asset holdings - (File: `validation.js`, `storage.js`)

### Summary
For any asset created with `spender_attested: true`, the asset *definer* retains permanent, unilateral control over who counts as an "attested" spender, even long after the asset has been issued and distributed to holders. The definer can publish a new `asset_attestors` message at any time that completely replaces the previously trusted attestor list, instantly making previously-valid attestations irrelevant for future spends. This is the same "excess issuer control after the fact" bug class as the reported OpenQ finding: a party who is supposed to have only set up the initial terms can unilaterally change who is eligible to receive funds, at any point, including after tokens are already held by users who relied on the original terms.

### Finding Description
When an asset is created, the definer sets `spender_attested` and an initial `attestors` list in the `asset` message, validated in `validateAssetDefinition` (`validation.js:2725-2755`), which only checks that the list is well-formed via `checkAttestorList` — it is never fixed or locked for the life of the asset.

The definer can later change this list at will via an `asset_attestors` message. Validation only requires that the asset requires attestation and that the sender is the definer — there is no restriction based on issuance history, elapsed time, or number of holders already depending on the previous list: [1](#0-0) 

At spend time, `readAsset`/`addAttestorsIfNecessary` in `storage.js` does not use the attestor list that was in effect when the asset units were issued — it looks up only the single most-recent `asset_attestors` unit before `last_ball_mci` and treats it as a full replacement of the trusted set: [2](#0-1) 

`filterAttestedAddresses` then checks payment authors' attestations only against this current, possibly newly-narrowed, attestor set: [3](#0-2) 

Finally, `validatePayment` enforces that a spend is only valid if the author is in `objAsset.arrAttestedAddresses` (derived from the *current* attestor list) — spends by holders attested only under the old, now-superseded list are rejected: [4](#0-3) 

Because the check is always evaluated against "the latest attestor list as of the current last-ball MCI" rather than "the attestor list in effect when the funds were issued/attested," a definer can:
1. Issue/allow distribution of an asset while attestor X is trusted, so holders get attested and believe they can freely transact.
2. Later post a new `asset_attestors` message that drops attestor X (or replaces the whole list), which is a normal, always-permitted operation for the definer.
3. Any holder whose attestation came only from the now-removed attestor immediately loses the ability to spend their previously valid, already-issued asset outputs — with no on-chain recourse, since the attestor list update is a fully valid, unrestricted definer action.

This mirrors the OpenQ pattern precisely: the party that set the initial "payout" conditions (attestation requirement) retains standing, unbounded authority to redefine those conditions after value has already changed hands, and this can be used to selectively freeze specific holders' funds or effectively "rug" the token's usability at any time.

### Impact Explanation
This is an asset-level fund-freezing vector: legitimately issued and previously-attested token balances can become permanently unspendable at the sole discretion of the asset definer, with no time-lock, no grandfathering of previously attested holders, and no way for holders to protect themselves once they've accepted the asset. This falls under "AA/asset fund loss or freezing" — holders lose access to funds they legitimately hold through unilateral, after-the-fact issuer action, which was explicitly listed as an acceptable impact category.

### Likelihood Explanation
Likelihood is high for any asset that uses `spender_attested: true` (a supported, documented feature), since:
- No special conditions are required beyond being the asset definer.
- The `asset_attestors` message has no cooldown, holder-notification, or immutability window.
- It is a normal, expected operation from ocore's own design (comment in schema: "must subsequently publish and update the list of trusted attestors"), meaning this exact control surface is guaranteed to be used in practice by attested-asset issuers, and abuse is indistinguishable from legitimate list maintenance at the protocol level.

### Recommendation
- Consider grandfathering: honor attestations that were valid at the time a specific output was issued/last transferred, rather than always re-checking against the current attestor list at spend time.
- Alternatively, require that attestor-list changes only add attestors (never fully replace/remove) unless an explicit, bounded revocation mechanism with holder protections (e.g., minimum notice period enforced by MCI delay) is used.
- Document/expose this control clearly to wallets so holders of `spender_attested` assets are warned that their ability to transfer is contingent on the definer's continued goodwill, not fixed at issuance.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Attestor `X` attests address `H` (holder). Definer or someone issues asset `A` output to `H`.
3. `H` now holds a valid, attested balance of asset `A` and can spend per `validatePayment` (`validation.js:2115-2122`), since `H` is in `arrAttestedAddresses` derived from the current attestor list.
4. Definer posts a new `asset_attestors` message for asset `A` with `attestors: [Y]` (dropping `X`), a fully valid message per `validateAttestorListUpdate` (`validation.js:2829-2848`) — no other approvals or delays required.
5. `storage.readAsset`'s `addAttestorsIfNecessary` (`storage.js:1917-1946`) now returns only `[Y]` as the asset's `arrAttestorAddresses`.
6. `H` attempts to spend the previously issued balance. `filterAttestedAddresses` (`storage.js:1959-1974`) no longer includes `H` (since `H` was only attested by removed attestor `X`), so `validatePayment` (`validation.js:2115-2122`) rejects `H`'s payment with "none of the authors is attested" — `H`'s funds are now frozen solely due to the definer's unilateral list change, with no time limitation or safeguard.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
