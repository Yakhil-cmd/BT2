### Title
AA cannot refund/return a `spender_attested` asset if the depositor's address is not (or is no longer) attested, permanently freezing the deposited asset - (File: `validation.js`, `aa_composer.js`)

### Summary
An Autonomous Agent (AA) that accepts a `spender_attested` asset as a deposit and later tries to pay/refund the same asset back to the depositor's address will have its response unit rejected by network-wide validation if that address is not on the asset's attested list at the time of sending. Because the AA has no way to choose an alternative recipient or bypass this check, and the bounce mechanism reverts all state changes atomically, the depositor's asset balance remains stuck inside the AA indefinitely, with recovery depending entirely on a third party (the asset's attestor) whom neither the AA author nor the depositor control.

### Finding Description
When a `spender_attested` asset is defined, every payment that spends or transfers it must have **all output addresses attested**, enforced in `validatePaymentInputsAndOutputs`: [1](#0-0) 

This check is performed unconditionally during unit validation for any spender of the asset, including AAs, since `objAsset.spender_attested` is evaluated the same way regardless of the payer: [2](#0-1) 

When an AA composes a response unit that sends this asset to the trigger address (e.g., a refund/withdraw path), `aa_composer.js` looks up asset info only for its **own** address (to check whether it can cover a negative balance) — it never checks whether the destination/output address is attested: [3](#0-2) 

If the recipient (the depositor) is not attested at broadcast time — e.g., because the third-party attestor never attested them, revoked the attestation, or simply hasn't gotten to it — the resulting unit fails the `spender_attested` output check in `validatePaymentInputsAndOutputs` and the whole AA response bounces via `bounce()`, which rolls back all state changes: [4](#0-3) 

Since the AA's logic is deterministic and re-evaluates the same trigger data on every retry, the refund will keep failing for as long as the depositor remains unattested — this is exactly analogous to the reported "funder blacklisted, cannot receive refund" bug class: the depositor deposited funds while eligible (or attestation status was irrelevant at the time), but is later unable to get them back because the attestor list is outside their and the AA's control. The AA's asset/definition validation (`aa_validation.js`) explicitly allows AA-issued assets to be `spender_attested`: [5](#0-4) 

and the storage layer confirms attested-address filtering is fully dynamic and re-evaluated per unit, per current attestor list, with no fallback: [6](#0-5) 

### Impact Explanation
This causes permanent AA fund freezing: coins legitimately deposited into an AA-managed `spender_attested` asset become unrecoverable by the depositor whenever the depositor's address fails the attestation check at refund/withdrawal time. There is no mechanism in the AA layer to specify an alternate recipient address (unlike the recommendation in the original report to let the funder specify a `to` address), and the AA cannot detect or work around the failure in advance since `aa_composer.js` never validates output-address attestation before composing the unit. The funds sit frozen in the AA balance with no path to recovery except the depositor obtaining attestation from a third party they do not control.

### Likelihood Explanation
Any AA design pattern that uses a `spender_attested` asset for deposits and refunds/payouts to depositors (a natural pattern for compliance-gated assets, similar to KYC/whitelisted stablecoins) is affected. `spender_attested` is a first-class, fully supported asset feature reachable by any unprivileged asset issuer or AA author, and the failure mode triggers under ordinary conditions (attestor hasn't attested the user yet, or revokes attestation) rather than requiring any malicious actor.

### Recommendation
- When an AA sends a `spender_attested` asset, check the destination address's attestation status (analogous to the existing `loadAssetWithListOfAttestedAuthors`/`filterAttestedAddresses` calls) before composing/sending, and bounce with a clear, actionable error rather than silently locking funds after the fact.
- Consider allowing AA definitions to route `spender_attested` refunds through an escrow/holding output or to expose the ability to redirect to an alternate, currently-attested address, so that a depositor is not permanently locked out of their deposit due to circumstances outside the AA's or their own control.
- Document this asset-feature interaction clearly for AA authors so they avoid combining `spender_attested` deposits with automatic refund/withdrawal logic without an escape hatch.

### Proof of Concept
1. Define an asset `spender_attested: true` with an attestor `X` (as in `test/samples/create_an_asset.oscript`, or an AA-issued asset per `aa_validation.js` lines 225-300).
2. Deploy an AA (similar to `a_bank_without_percent.oscript`/`fundraising_proxy.oscript`) that accepts this asset as a deposit and has a "withdraw"/"refund" case that sends the same asset back to `trigger.address`.
3. User `U`, who is currently attested by `X`, deposits the asset into the AA. AA state records the balance.
4. Attestor `X` stops attesting `U` (or never attests `U`'s specific address used for withdrawal) before `U` calls the withdraw/refund case.
5. `U` triggers the withdraw case. `aa_composer.js` composes a payment message to `U`'s address without checking attestation (`aa_composer.js:1323-1331`), the unit is submitted, and `validatePaymentInputsAndOutputs` rejects it with `"some output addresses are not attested"` (`validation.js:2630-2641`), causing `bounce()` to revert all state changes (`aa_composer.js:909-945`).
6. `U`'s deposited asset balance remains stuck in the AA. Every subsequent identical trigger produces the same bounce, and `U` has no way to force attestation or redirect the payout — the funds are frozen indefinitely.
