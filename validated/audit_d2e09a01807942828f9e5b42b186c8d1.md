### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository.full_name` a handler actually writes to — cross-organization/cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-tenant configurations, `Shipit.github(organization:)` selects a distinct GitHub App config (and `webhook_secret`) per organization. `WebhooksController#verify_signature` picks *which* org's secret to verify against using a payload field (`repository.owner.login`, falling back to `organization.login`), while every webhook handler resolves the actual `Stack`/`Repository` to mutate from a *different* payload field, `repository.full_name`. Nothing ties these two fields together, so the "authenticated organization" and the "repository that gets written to" are two independent, attacker-influenced values.

### Finding Description
`verify_signature` derives the signing org purely from the request body itself: [1](#0-0) [2](#0-1) 

`Shipit.github` resolves a per-organization config keyed only by that string, with each organization carrying its own independent `webhook_secret`: [3](#0-2) 

Crucially, if that resolved organization's `webhook_secret` is blank/unset, signature verification is skipped entirely and any request is accepted: [4](#0-3) 

Once "verified" (against whatever organization the attacker put in `repository.owner.login`/`organization.login`), the actual target of the webhook is picked by every handler from a completely separate field: [5](#0-4) 

For example, `PushHandler` finds and mutates real stacks using only `repository.full_name`, kicking off a real sync job with an attacker-supplied `expected_head_sha`: [6](#0-5) 

`StatusHandler` similarly writes forged commit statuses to any commit matching `params.sha`, independent of which organization "verified" the request: [7](#0-6) 

The binding that should hold but doesn't: `organization_used_for_signature_check == owning_organization(repository.full_name)`. Before the attacker's request, this equality is trivially true because GitHub only ever sends webhooks whose `repository.owner.login` and `repository.full_name` are consistent. After the attacker's crafted request, `repository.owner.login`/`organization.login` can be set to *any* configured organization (in particular, one whose `webhook_secret` is unset — which is the documented default, e.g. `"webhook_secret": null` in `test/dummy/config/secrets.test.json`), while `repository.full_name` can independently name a stack belonging to an entirely different, properly-secured organization.

### Impact Explanation
This breaks the "organization authenticated versus repository that is written" binding and results in cross-repository writes to any stack tracked by the Shipit instance:
- Forged `push` events cause `GithubSyncJob` to run against a victim stack with an attacker-chosen `expected_head_sha`.
- Forged `status` events (`StatusHandler`) can create arbitrary `CommitStatus` records on a victim commit, potentially satisfying `ci.require` checks in `shipit.yml` and enabling continuous deployment to proceed on a commit that never actually passed CI, i.e. an unauthorized deploy path.
- Forged `check_suite`/`membership`/`pull_request` events can similarly desynchronize state for repositories the attacker has no relationship with.

This matches the "cross-repository writes" / "unauthorized deploy" Critical-impact criteria, and requires no Shipit session, API token, or knowledge of any specific webhook secret — only that the multi-tenant instance has at least one configured organization with no (or a guessable/blank) `webhook_secret`, which is the engine's own documented/default behavior (`return true unless webhook_secret`), not a deviation from documented mounting.

### Likelihood Explanation
Likely wherever a Shipit deployment is configured with the multi-organization GitHub App schema (`secrets.github` keyed by org) and any one of those organizations has not set a `webhook_secret` — a state the codebase explicitly treats as valid ("no secret configured ⇒ skip verification") rather than an error. Any anonymous internet client can POST directly to the public `/webhooks` endpoint; no GitHub-side signing is actually required once a permissive org name is supplied.

### Recommendation
- Verify the webhook signature using the secret associated with the organization that actually owns `repository.full_name` (or `repository.owner.login`), not a field chosen independently of it, and reject requests where these disagree.
- Treat a missing/blank `webhook_secret` as "reject all deliveries for this org" rather than "accept unconditionally," or require an explicit opt-in flag to run unsigned.
- Cross-check `repository.full_name`'s owner against `repository_owner` before dispatching to handlers.

### Proof of Concept
1. Configure (or find) a multi-org Shipit deployment where organization `low-sec-org` has `webhook_secret: null` and `victim-org/victim-repo` is a tracked stack under a different, properly-secured organization.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "low-sec-org" }
  }
}
```
No `X-Hub-Signature` is required because `Shipit.github(organization: "low-sec-org").verify_webhook_signature` returns `true` unconditionally.
3. `verify_signature` passes; `PushHandler` resolves the stack via `repository.full_name` ("victim-org/victim-repo") and enqueues `GithubSyncJob` for the victim stack with the attacker-supplied `expected_head_sha`, despite the request never having been authenticated against `victim-org`'s own webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
