### Title
Mandatory accrual overflows on oversized RAY balances and permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary
A market whose scaled supply or debt value exceeds `i128::MAX` cannot complete `accrue_step`, because unscaling `supplied` or `borrowed` panics before the configured index ceilings can apply. [1](#0-0) [2](#0-1) 

### Finding Description
`accrue_step` unconditionally converts `borrowed` and `supplied` to original RAY values through `scaled_to_original`, which calls `Ray::mul`. [3](#0-2) [4](#0-3) 

`Ray::mul` delegates to `mul_div_half_up`; when the widened quotient cannot convert back to `i128`, the function panics with `GenericError::MathOverflow`. [5](#0-4) [6](#0-5) 

The configured `MAX_BORROW_INDEX_RAY` and `MAX_SUPPLY_INDEX_RAY` only bound index growth and do not bound the independently scaled market totals passed to those multiplications. [2](#0-1) [7](#0-6) 

Every normal pool leg first calls `synced_market`, and `synced_market` invokes `interest::global_sync` before mutation logic runs. [8](#0-7) [9](#0-8) 

The permissionless controller entrypoint `update_indexes` forwards caller-selected assets to `pool_update_indexes_call`, whose pool implementation loads each market and calls `global_sync`. [10](#0-9) [11](#0-10) 

### Impact Explanation
Once the market reaches this state, every operation requiring accrual permanently reverts, including user withdrawals, repayments, liquidations, bad-debt settlement, recapitalization, revenue claims, and further index updates. [12](#0-11) [13](#0-12) 

The stored `last_timestamp` is only marked current after all accrual chunks succeed, so a failed accrual cannot advance past the overflowing state or skip it on a later call. [14](#0-13) [15](#0-14) 

This creates permanent freezing of user funds and prevents the market from operating, satisfying the accepted impact classes. [16](#0-15) [17](#0-16) 

### Likelihood Explanation
An unprivileged caller can trigger the final failure by calling controller `update_indexes(caller, assets)` with the affected `HubAssetKey`; the call only requires ordinary caller authorization. [18](#0-17) [10](#0-9) 

Reaching the state requires a validly admitted market with sufficiently large supply or debt relative to its index; the protocol permits very large caps, while the index ceilings do not guarantee that `scaled_shares * index` remains representable. [19](#0-18) [20](#0-19) 

Likelihood is medium rather than high because the attack depends on substantial liquidity or debt accumulation and enough accrual to cross the RAY-value boundary, but no privileged action is needed to trigger the resulting denial once that state exists. [21](#0-20) [18](#0-17) 

### Recommendation
Accrual should bound scaled market values before calling `scaled_to_original`, or use saturating/widened market-total accounting that cannot leave the market permanently unable to sync. [22](#0-21) 

The borrow-index cap should also be applied without first computing an unrepresentable Ray product, and protocol-level admission or runtime caps should enforce `supplied * supply_index` and `borrowed * borrow_index` below `i128::MAX`. [2](#0-1) [23](#0-22) 

### Proof of Concept
1. Use a valid high-decimal market and accumulate a very large supplied position, then establish a large borrow against collateral in another market. [24](#0-23) [25](#0-24) 
2. Let interest accrue until `borrowed * borrow_index` or `supplied * supply_index` no longer fits `i128`. [1](#0-0) [5](#0-4) 
3. Call controller `update_indexes(attacker, vec![HubAssetKey { hub_id, asset }])`. [10](#0-9) 
4. The controller forwards the request to pool `update_indexes`, which loads the market and enters `global_sync`. [26](#0-25) [11](#0-10) 
5. `accrue_step` panics during market-value conversion, so the call reverts before committing a new timestamp. [1](#0-0) [14](#0-13) 
6. Subsequent `withdraw`, `repay`, `liquidate`, `recapitalize`, and `update_indexes` paths repeat the same mandatory accrual and revert, leaving market funds frozen. [12](#0-11) [13](#0-12)

pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```
