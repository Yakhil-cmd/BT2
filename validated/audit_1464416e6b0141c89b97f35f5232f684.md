### Title
Governance vote weighting uses instantaneous address balance instead of time-held stake, enabling vote-weight sniping in `countVotes` - (File: main_chain.js)

### Summary
The system-parameter voting mechanism (`op_list`, `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) weighs a voter's ballot by the address's **current spendable balance at the moment the vote tally runs**, not by any historically-committed or time-weighted stake. This mirrors the BellumNursery flaw: reward/voting power is assigned by "current share ratio" rather than duration of commitment, letting an attacker acquire a large balance immediately before a vote count and receive full voting weight for an already-cast, low-value vote.

### Finding Description
`countVotes()` in [1](#0-0)  selects the set of addresses that have ever cast a vote on a subject (`SELECT DISTINCT address FROM system_votes WHERE subject=?`) and then computes each address's voting weight from its **live, unspent balance at the current stable state** of the DAG:

```
SELECT outputs.address, SUM(outputs.amount) AS balance
FROM outputs JOIN units ...
WHERE outputs.address IN(...) AND outputs.asset IS NULL
  AND units.is_stable = 1 AND units.sequence = 'good'
  AND NOT EXISTS (... spent by good stable unit ...)
GROUP BY outputs.address
```

This balance snapshot (`voter_balances`) is then joined against the address's votes within a rolling time window (`since_timestamp`) to compute `total_balance` per candidate/value, e.g. for `op_list`: [2](#0-1) 
and for numeric subjects: [3](#0-2) 

Crucially, the weight used is the balance **at the time the tally executes** (triggered deterministically whenever a new unit stabilizes and the vote-count threshold, `constants.SYSTEM_VOTE_MIN_SHARE`, is reached), not the balance the address held when it cast its vote, nor any duration-weighted average. An address that voted long ago with a trivial balance is counted with whatever balance it holds *right now*, exactly analogous to BellumNursery's flaw where a staker's reward share is computed from the current pool ratio rather than accumulated stake-time.

### Impact Explanation
Because vote weight is purely a function of instantaneous balance rather than sustained/time-weighted stake:
- An attacker can pre-position a small transaction to register a valid vote for a subject (e.g., `op_list`, or a TPS-fee-related numeric parameter) from a low-balance address, then, right before/at the point a new unit stabilizes and triggers `countVotes`, move a very large balance into that same voting address (a single-block/DAG-round transfer that is spendable and stable is enough since only stability is required, not long-term holding).
- The full incoming balance is instantly counted toward that address's already-cast vote, giving it outsized influence over consensus-critical parameters: the witness/order-provider list (`op_list`), `threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`.
- Because these are core protocol parameters that all nodes must agree on deterministically, sniping the vote lets a well-funded, short-term actor dictate `op_list`/witness membership or TPS-fee economics network-wide, without needing to hold funds during any qualifying period. This can cause network-wide disagreement risk if actors briefly acquire/lose funds around stabilization boundaries, and — more importantly — allows manipulation of consensus governance (choice of order providers / fee curve) via transient capital, undermining the intended "who has skin in the game longest" weighting and letting a temporary whale outvote long-term, committed stakeholders. This is a protocol-level, unauthorized-influence class of impact on a system that all nodes must agree on to keep confirming new units correctly.

### Likelihood Explanation
Likelihood is constrained by real-world feasibility (need enough capital to move around, and timing precision against MC stabilization), but the mechanism is fully deterministic and reachable by any unprivileged address that can send/receive base-asset payments and post a `system_vote` message — no special privilege is required. The `since_timestamp` rolling-window logic in [4](#0-3)  only decides how far back votes are counted; it does nothing to require that the balance used for weighting was held throughout that window, so the sniping vector is not mitigated by this window expansion logic. The vulnerability requires only ordinary payment/vote transactions constructible by any wallet, matching the "unfair reward/weight distribution based on current balance snapshot" bug class from the report.

### Recommendation
Adopt a checkpoint/time-weighted balance model analogous to the report's remediation:
- Record a balance (or balance history/checkpoint) for each voting address at the time the vote is cast (or use a time-weighted average balance over the qualifying window) instead of querying the live balance at tally time.
- Alternatively, require that the balance used for a given vote be locked/held (e.g., via age-of-output or minimum holding period since the corresponding `system_vote` unit) so that funds moved in immediately before a tally cannot be counted.
- When computing `voter_balances` in `countVotes` (main_chain.js), join against balances as of each vote's own timestamp/mci rather than the balance as of the current stabilization point, preventing "vote-weight sniping" of `op_list`/TPS-fee/threshold governance.

### Proof of Concept
Conceptual sequence exploiting `countVotes` in `main_chain.js`:
1. Address A casts a `system_vote` for subject `op_list` (or a numeric subject like `base_tps_fee`) while holding a minimal balance (e.g., a few bytes) — this satisfies inclusion in `address_rows`/`system_votes` at [5](#0-4) .
2. Shortly before a new MC unit stabilizes (which triggers `markMcIndexStable` → `countVotes`), an attacker sends a very large stable, unspent base-asset payment to address A.
3. When `countVotes` executes, the balance query at [6](#0-5)  picks up A's newly inflated balance and attributes the full amount to A's pre-existing vote in the `op_rows`/`rows` aggregation at [7](#0-6) .
4. A's vote — cast while nearly no funds were at stake — now dominates the tally for a network-wide governance parameter (e.g., who the order providers are, or the TPS fee curve), even though the large balance can be moved out again immediately after stabilization. [1](#0-0) [7](#0-6)

async function countVotes(conn, mci, subject, is_emergency = 0, emergency_count_command_timestamp = 0) {
	console.log('countVotes', mci, subject, is_emergency, emergency_count_command_timestamp);
	if (is_emergency && subject !== "op_list")
		throw Error("emergency vote count supported for op_list only, got " + subject);
	const address_rows = await conn.query("SELECT DISTINCT address FROM system_votes WHERE subject=?", [subject]);
	let addresses = address_rows.map(r => r.address);
	const unstable_votes = (is_emergency && mci >= constants.pemCurvesFixMci) ? getUnstableVotes(emergency_count_command_timestamp) : null;
	if (unstable_votes) {
		for (let { author_addresses } of unstable_votes) {
			for (let address of author_addresses)
				addresses.push(address);
		}
		addresses = _.uniq(addresses);
	}
	const strAddresses = addresses.map(db.escape).join(', ');
	let balances = {};
	// Count all stable-good outputs that have no stable-good spender.
	// This correctly handles outputs whose only spending unit was propagated to final-bad
	// (leaving is_spent=1 in the DB while no good unit claims the output), which the
	// previous two-query approach (bal_rows + spent_rows) silently undercounted.
	const bal_rows = await conn.query(`
		SELECT outputs.address, SUM(outputs.amount) AS balance
		FROM outputs
		JOIN units ON outputs.unit = units.unit
		WHERE outputs.address IN(${strAddresses})
			AND outputs.asset IS NULL
			AND units.is_stable = 1 AND units.sequence = 'good'
			AND NOT EXISTS (
				SELECT 1 FROM inputs
				JOIN units AS su ON inputs.unit = su.unit
				WHERE inputs.src_unit = outputs.unit
					AND inputs.src_message_index = outputs.message_index
					AND inputs.src_output_index = outputs.output_index
					AND su.sequence = 'good'
					AND su.is_stable = 1
			)
		GROUP BY outputs.address`);
	console.log('bal rows', bal_rows)
	for (let { address, balance } of bal_rows) {
		balances[address] = balance;
	}
