### Title
Webhook signature verification is scoped to an attacker-chosen organization while the acted-upon repository is read from a separate, uncross-checked field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) taken directly from the unauthenticated request body. Every event handler, however, resolves the actual `Repository`/`Stack` to mutate using a completely different, also attacker-controlled field: `repository.full_name`. Nothing ties these two fields together, so an attacker who legitimately controls *any* GitHub organization configured in Shipit's multi-org `github:` secrets (and therefore knows that organization's `webhook_secret`) can forge a signature valid for their own org while pointing `repository.full_name` at a completely different, victim-owned repository tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` picks the `GitHubApp` config (and thus the `webhook_secret`) for whatever organization name is in `repository.owner.login`/`organization.login`. `GitHubApp#verify_webhook_signature` then only checks that the HMAC matches that org's secret against the raw body: [3](#0-2) 

Once verification passes, `WebhooksController#create` hands the entire parsed JSON to the registered handler(s) unchanged: [4](#0-3) 

Every handler locates the `Repository`/`Stack` to act on via `repository.full_name`, a field independent of `repository.owner.login`: [5](#0-4) [6](#0-5) 

This is the exact binding break flagged as in-scope: "an organization that authenticated versus the repository that is written." Nothing enforces `repository.owner.login == repository.full_name.split('/').first`. Multi-org configuration is a documented, supported setup: [7](#0-6) 

**Attack sequence:**
1. Attacker owns/administers GitHub organization `AttackerOrg`, which is one of the orgs configured under Shipit's `github:` secrets (a legitimate, low-privilege installation is enough to know that org's `webhook_secret`).
2. Attacker POSTs directly to Shipit's public `/github/webhooks` endpoint (no session, no `ApiClient` token, no repository write access to the victim repo required) with:
   - header `X-Github-Event: push`
   - body containing `"repository": {"owner": {"login": "AttackerOrg"}, "full_name": "VictimOrg/victim-repo"}`, `"ref": "refs/heads/<branch>"`, `"after": "<sha>"`
3. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s known `webhook_secret` over the raw body. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and the signature validates.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` on the *victim's* real stack.
5. `GithubSyncJob` runs using the victim stack's own `github_api`/credentials (correct, privileged credentials for the real target), fetching real commits and, if the victim stack has `continuous_deployment?` enabled, can lead into `ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery`, i.e., an attacker-triggered, unauthorized deploy of a repository/organization the attacker has no relationship to.

Other handlers are similarly exploitable for cross-organization writes with the same technique: `MembershipHandler` creates/removes team membership using `organization.login` from the payload with no cross-check against the signature-verifying org either, and PR handlers (`ClosedHandler`, `OpenedHandler`, `LabeledHandler`, etc.) archive/create/update review stacks and pull-request state for `params.repository.full_name` regardless of which org's secret validated the request. [8](#0-7) [9](#0-8) 

### Impact Explanation
This crosses the "cross-repository writes" / "unauthorized deploy" Critical bar, and at minimum the "unauthenticated read of stack state" High bar, without requiring a Shipit session, `ApiClient` token, `webhook_secret` of the *victim* org, repository write access to the victim repo, or any privileged account on the victim side — only a legitimate, unprivileged relationship to *any other* org configured in the same Shipit instance's multi-org secrets. Concretely:
- Forged `push` events can force `GithubSyncJob` to run against a victim stack, and if `continuous_deployment?` is enabled, can chain into an actual unauthorized deploy (`ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery`).
- Forged `pull_request` events can archive/unarchive/create review stacks, and mutate pull request state, for repositories the attacker does not control.
- Forged `membership` events create/delete team membership records tied to an arbitrary `organization.login`, independent of which org's secret was actually used to sign the request.

### Likelihood Explanation
Requires only that the attacker legitimately controls (or has installed the GitHub App for) at least one of the multiple GitHub organizations Shipit is configured to serve — a normal, expected operating mode per `docs/setup.md`'s "Using Multiple Github Applications" section. No other credential or privileged access is needed; the endpoint is publicly reachable and unauthenticated aside from the (attacker-known) HMAC secret of their own org.

### Recommendation
After signature verification, cross-check that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner implied by `repository.full_name` (and any other repository identifiers used by handlers) before dispatching to handlers. Reject the webhook (422) on mismatch. Consider also validating that the resolved `Repository`/`Stack` actually belongs to the organization whose secret validated the signature at the point each handler performs its lookup, rather than trusting `full_name` unconditionally.

### Proof of Concept
```
POST /github/webhooks HTTP/1.1
X-Github-Event: push
X-Hub-Signature: sha1=<hmac-sha1(AttackerOrg_webhook_secret, body)>
Content-Type: application/json

{
  "ref": "refs/heads/production",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and validates the signature computed with `AttackerOrg`'s known secret — passes.
- `PushHandler` resolves the target via `payload.dig('repository', 'full_name')` = `"VictimOrg/victim-repo"`, locating and syncing the real victim `Stack`, independent of the org that authenticated the request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
