## Title
CCMenu API endpoint ignores an ApiClient's stack scope, allowing a stack-restricted token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` scopes stack access for `ApiClient` tokens that are bound to a single stack via `stacks`/`stack`, but `Shipit::Api::CCMenuController` overrides `#stack` with a version that ignores that binding, letting any authenticated, `read:stack`-permitted token read the CCMenu status of any stack, not just the one it was authorized for.

### Finding Description
`ApiClient` tokens can be created scoped to a single stack (`belongs_to :stack, optional: true`), and `BaseController` is designed to enforce that scope: [1](#0-0) 

Authorization is a two-part check in this codebase: (1) `require_permission` only checks that the operation:scope string (e.g. `"read:stack"`) is present in the client's `permissions` array — it never checks *which* stack — via `ApiClient#check_permissions!`: [2](#0-1) 
and (2) the actual restriction to the client's assigned stack happens only inside the `stacks`/`stack` helper methods in `BaseController`, which filter by `current_api_client.stack_id` before resolving `params[:stack_id]`.

`Shipit::Api::CCMenuController` declares `require_permission :read, :stack` (part 1 only) but then defines its own `#stack` method that bypasses part 2 entirely: [3](#0-2) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This resolves `params[:stack_id]` directly against the global `Stack` model, instead of `stacks.from_param!(params[:stack_id])` (which would raise/404 if the requested stack isn't the one the token authorizes).

The `here_come_the_walrus` fixture demonstrates a real client scoped to a single stack: [4](#0-3) 

The binding that should hold is: `stack the token authorizes == stack the token can act on`. In `CCMenuController#show`, that equality is broken: the token only needs `read:stack` in its permission list; the `stack_id` value in the request path/param is fully attacker-controlled and unchecked against `current_api_client.stack_id`.

### Impact Explanation
An `ApiClient` deliberately scoped to one stack (e.g. created through `CCMenuUrlController`, which mints "read only" clients) can be replayed against `GET /api/:stack_id/ccmenu.xml?token=...` with a different `stack_id` and successfully read that other stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status, etc.) — data belonging to a repository/stack that token holder was never granted access to. This is a horizontal authorization-scope escalation: a token meant to authorize reads on stack A ends up touching stack B. It matches the "escalation into authorization" / cross-scope read pattern called out as in-scope (analogous to unauthenticated/unauthorized read of stack state).

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped read tokens (the engine explicitly supports and tests this via the `here_come_the_walrus`/`stack:` fixture and `CCMenuUrlController`). No privileged access beyond possessing *any* valid, low-privilege `read:stack` API token is required, and the mismatch is a straightforward one-line difference in the `stack` method override versus the base class's scoped implementation.

### Recommendation
Remove the `CCMenuController#stack` override, or reimplement it using the scoped helper (`stacks.from_param!(params[:stack_id])`) so that the CCMenu endpoint enforces the same `current_api_client.stack_id` restriction that `BaseController` provides to every other API controller.

### Proof of Concept
1. Create (or have the engine create, e.g. via `CCMenuUrlController#client`) an `ApiClient` scoped to `stack: shipit` with permission `read:stack` only (as in the `here_come_the_walrus` fixture).
2. Obtain its `authentication_token`.
3. Issue `GET /api/soc/ccmenu.xml?token=<here_come_the_walrus_token>` (targeting a different stack, e.g. `shipit_repositories(:soc)`), instead of the authorized `shipit` stack.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `current_api_client.stack_id` filtering used everywhere else in `BaseController`), and `check_permissions!` only verifies the string `"read:stack"` is in the permission list, the request succeeds with `200 OK` and returns the `soc` stack's CCMenu XML (name, lastBuildStatus, lastBuildLabel, activity) — data outside the token's authorized stack scope.
