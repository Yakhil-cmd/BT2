### Title
Permanent market freeze from `i128` overflow during interest accrual - ([File: common/src/rates/simulate.rs](common/src/rates/simulate.rs))

### Summary
Accrual computes the current aggregate borrowed and supplied values by multiplying scaled balances by their indexes before any index-cap protection can stop growth. [1](#0-0)  When either product exceeds `i128::MAX`, `scaled_to_original` panics through `Ray::mul` and `mul_div_half_up` with `MathOverflow`. [2](#0-1) [3](#0-2) [4](#0-3)  Because the transaction reverts without committing the new timestamp, every later call repeats the same overflowing accrual and permanently freezes that market. [5](#0-4) [6](#0-5) 

### Finding Description
`accrue_step` unconditionally calls `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` to calculate utilization. [7](#0-6)  Both helpers evaluate `scaled * index / RAY` and reject a quotient that cannot fit in `i128`. [2](#0-1) [4](#0-3) 

The borrow index is clamped only after this value calculation, at `MAX_BORROW_INDEX_RAY`. [8](#0-7) [9](#0-8)  Consequently, a sufficiently large scaled book can reach an aggregate ray value above `i128::MAX` while the stored index remains below its cap. [10](#0-9) 

Every pool market mutation first loads the market and calls `global_sync`, which runs `accrue_step` for elapsed time. [6](#0-5) [5](#0-4)  This places the overflow ahead of `supply`, `borrow`, `withdraw`, `repay`, liquidation settlement, bad-debt cleanup, flash operations, recapitalization, and `update_indexes` for the affected `(hub_id, asset)` book. [11](#0-10) 

### Impact Explanation
This is a permanent freezing of user funds and protocol insolvency containment failure for the affected market: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot execute any operation requiring accrual. [6](#0-5) [11](#0-10)  The regression test explicitly demonstrates that both withdrawal and repayment fail with `MathOverflow` after the cliff is reached. [12](#0-11) 

Since the panic occurs before `last_timestamp` can be committed, waiting or repeatedly invoking permissionless controller `update_indexes` cannot move the market past the bad interval. [5](#0-4) [13](#0-12)  Even `update_params` accrues under the old model before replacing it, so it also reaches the same panic rather than providing an operational recovery path. [14](#0-13) 

### Likelihood Explanation
Any unprivileged user can build the precondition through normal `supply` and `borrow`, then trigger or expose the failure through `update_indexes`; no privileged call or callback is required. [11](#0-10)  The precondition is economically restrictive: it requires an exceptionally large high-decimal market and sustained high utilization while debt compounds. [15](#0-14) 

The repository’s own harness reaches the cliff with one billion 18-decimal tokens at approximately 98% utilization under the configured XLM stress curve, with failure occurring before `MAX_BORROW_INDEX_RAY`. [16](#0-15) [17](#0-16)  This makes the issue a Medium-severity permanent freeze rather than a cheap instantaneous DoS. [18](#0-17) 

### Recommendation
Add a checked headroom invariant to market creation and mutations so `supplied * MAX_SUPPLY_INDEX_RAY / RAY` and `borrowed * MAX_BORROW_INDEX_RAY / RAY` remain representable in `i128`. [2](#0-1) [9](#0-8)  Alternatively, clamp or safely cap the scaled aggregate before `scaled_to_original`, while preserving conservative floor/ceil accounting for utilization, debt valuation, and repayment. [1](#0-0) [19](#0-18) 

### Proof of Concept
1. Create an 18-decimal market using the XLM stress curve with a 175% maximum borrow rate and no effective utilization cap. [16](#0-15) [20](#0-19) 
2. Supply `1_000_000_000 * 10^18` raw units and borrow `98%` of it through the normal permissionless supply and borrow paths. [21](#0-20) 
3. Advance ledger time and repeatedly call controller `update_indexes` with the affected `HubAssetKey` until accrual returns `MathOverflow`. [22](#0-21) 
4. Observe that the stored borrow index is still below `MAX_BORROW_INDEX_RAY`, proving the failure is the aggregate `scaled * index` value rather than the index ceiling. [23](#0-22) 
5. Calls to `withdraw` and `repay` then fail with `MathOverflow` because both load a synced market before mutating positions. [24](#0-23) [25](#0-24)

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
```

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
