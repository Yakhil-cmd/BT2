### Title
Cross-tenant webhook forgery: organization whose `webhook_secret` authenticates a request differs from the repository whose Stack is mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which tenant's `GitHubApp` (and therefore which `webhook_secret`) is used to validate `X-Hub-Signature` based on `params.dig('repository', 'owner', 'login')`. Every webhook handler that actually mutates state (e.g. `PushHandler`) instead resolves the target `Stack` using a *different* field from the same attacker-influenced JSON body: `payload.dig('repository', 'full_name')`. In a multi-organization deployment (explicitly documented and supported via the `github: <org>: {...}` config schema), each tenant organization owns and knows its own `webhook_secret`. Because the field used to pick the verifying secret (`repository.owner.login`) and the field used to pick the mutated resource (`repository.full_name`) are independent JSON keys inside the same signed payload, an attacker who legitimately controls one tenant/organization can forge a raw POST to `/webhooks` that authenticates as their own org while acting on a completely different, victim org's repository/stack.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` (`lib/shipit.rb`) looks up the per-organization config block and returns a `GitHubApp` whose `webhook_secret` is used to HMAC-verify `X-Hub-Signature` against `request.raw_post` (`lib/shipit/github_app.rb#verify_webhook_signature`). This only proves the raw body was signed by *some* org's known secret - the org identified by `repository.owner.login`.

Once verification passes, `WebhooksController#create` dispatches the entire raw JSON body to handlers via `Shipit::Webhooks.for_event(event)`. `Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb`) resolves the target using an unrelated key:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
`PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb`) uses this to find and mutate any tracked `Stack`:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
```
The binding the system relies on is: `repository.owner.login` (used to select the secret that authenticates the request) == `repository.full_name`'s owner (the repository actually acted upon). Nothing enforces this equality - both are independent, attacker-suppliable fields inside the raw POST body. As long as the attacker can produce a *valid* signature for the body under **some** organization's secret, the `full_name` field can point to a Stack belonging to any other organization tracked by the same Shipit instance.

This is explicitly supported/expected multi-tenancy: `docs/setup.md` ("Using Multiple GitHub Applications") and `config/secrets.development.shopify.yml` / `test/dummy/config/secrets_double_github_app.yml` document per-organization `github: <org>: {app_id, installation_id, webhook_secret, ...}` blocks, each independently created ("Creating the GitHub App" - "create a new one for your organization") and thus independently known by that organization's own maintainers.

### Impact Explanation
An attacker who is a legitimate operator of Org A (one tenant on a shared Shipit instance, with zero privileges over Org B's repositories) can:
1. Craft a raw JSON push-event payload with `repository.owner.login = "org-a"` (so `Shipit.github(organization: "org-a")` and Org A's known `webhook_secret` validate the HMAC) but `repository.full_name = "org-b/victim-repo"`.
2. Sign the raw body with Org A's `webhook_secret` (`sha1=` HMAC), computed as GitHub itself would.
3. POST it directly to `/webhooks`.

`verify_signature` passes (Org A's secret correctly matches the body), and `PushHandler` then acts on `org-b/victim-repo`'s tracked `Stack`, calling `stack.sync_github(expected_head_sha: <attacker-chosen sha>)`, which enqueues `GithubSyncJob` for a stack the attacker has no privilege over. If the attacker times this with a real commit that already landed on `org-b/victim-repo` upstream (visible publicly or via any read access), this becomes cross-repository writes: an org with no authorization on the victim repository forces a re-sync/append of commits and can trigger continuous delivery pathways (`Stack#sync_github` -> `GithubSyncJob` -> commit creation, which can be wired to continuous-delivery deploy triggers) for a repository/stack it does not own. This matches the "Critical - cross-repository writes / unauthorized deploy" impact bucket, because the write and deploy trigger occur against a stack under a completely different organizational trust boundary than the one whose credential authenticated the request.

### Likelihood Explanation
Requires the deployment to use the documented multi-organization `github:` config (a supported, documented configuration, not a misconfiguration outside scope). Any operator/administrator of one onboarded tenant organization - who legitimately knows only their own org's `webhook_secret` - can exploit this with no access to the victim org, no Shipit session, no API client token, and no GitHub App private key for the victim org. The only "skill" required is crafting a raw HTTP POST with a correctly HMAC-signed body, which is trivial once the attacker's own secret is known (it is inherent to being a tenant admin in this architecture).

### Recommendation
Enforce that the organization used to select the verifying `webhook_secret` matches the actual owner encoded in the effective target of the payload before dispatching to handlers - i.e., after verifying the signature with the org derived from `repository.owner.login`, also verify that `repository.full_name` starts with that same organization login (case-insensitively) before invoking any handler, or resolve the target `Stack`/`Repository` scoped to `repository_owner` rather than independently re-parsing `repository.full_name`. Reject (422) any webhook where these two fields disagree.

### Proof of Concept
Given a Shipit instance configured with two tenant orgs, `org-a` and `org-b` (`config/secrets.yml`):
```yml
github:
  org-a:
    webhook_secret: "orgA_secret_known_to_attacker"
    ...
  org-b:
    webhook_secret: "orgB_secret_unknown_to_attacker"
    ...
```
Attacker (an operator of `org-a`, with no access to `org-b`) builds the payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha already pushed to org-b/victim-repo upstream>",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
and computes:
```
signature = "sha1=" + HMAC_SHA1("orgA_secret_known_to_attacker", raw_body)
```
Then sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<computed>
Content-Type: application/json

<raw_body>
```
`WebhooksController#verify_signature` resolves `repository_owner => "org-a"`, fetches `org-a`'s `GitHubApp`, and `verify_webhook_signature` succeeds because the attacker signed with the correct (their own) secret. `PushHandler` then resolves `repository_name => "org-b/victim-repo"` via `Handler#repository_name`, finds `org-b`'s tracked `Stack`(s) on branch `master`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, enqueuing `GithubSyncJob` for the victim stack - all without any credential belonging to `org-b`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

  module Webhooks

        end
      end
