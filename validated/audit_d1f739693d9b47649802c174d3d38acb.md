### Title
Webhook signature verified against `repository.owner.login`'s GitHub App secret while push/status handlers act on unrelated repositories/commits identified from unauthenticated payload fields - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's HMAC secret to validate a payload against using `repository_owner`, derived from `params.dig('repository','owner','login')` (or `organization.login`) inside the *same, attacker-supplied* JSON body. [1](#0-0) [2](#0-1)  Once the signature check passes, the actual side-effecting handlers (`PushHandler`, `StatusHandler`, etc.) resolve which `Repository`/`Stack`/`Commit` to act on from other, independent fields of that same unauthenticated payload (`repository.full_name` for push, or a bare `sha` lookup with no repository scoping at all for status). [3](#0-2) [4](#0-3)  The field that authenticates the request (`repository.owner.login`, used to pick the HMAC secret) is never cryptographically bound to the field that determines what gets modified (`repository.full_name`/`sha`).

### Finding Description
Shipit supports a multi-organization GitHub App configuration where each organization has its own `webhook_secret`, as documented in `docs/setup.md` and `config/secrets.development.example.yml`. [5](#0-4)  `verify_signature` looks up `Shipit.github(organization: repository_owner)` and verifies the `X-Hub-Signature` HMAC using that organization's secret:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
``` [6](#0-5) 
`repository_owner` is read straight from the JSON body being verified: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [2](#0-1) 

Signature verification only proves "this payload was signed with organization `X`'s webhook secret" — it does not prove anything about which repository the payload's other fields describe. Nothing ties `repository.owner.login` to `repository.full_name`.

Downstream, `Handler#repository_name` (used by `PushHandler`) resolves the target `Repository`/`Stack` purely from `payload.dig('repository', 'full_name')`:
```
def repository_name
  payload.dig('repository', 'full_name')
end
``` [7](#0-6) 
`PushHandler#process` then triggers `stack.sync_github` for every matching stack. [8](#0-7) 

`StatusHandler` is worse: it does not even use `repository` — it matches purely by commit `sha` across the entire `Commit` table and writes a status from attacker-controlled fields (`state`, `context`, `target_url`, `description`) to any commit sharing that SHA:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

**The broken binding, as an equality that should hold but doesn't:**
`organization authenticated via HMAC (repository.owner.login)` ⇏ `repository/commit actually written (repository.full_name / sha)`

Before the attack: an operator assumes that because a webhook passed HMAC verification for organization `attacker-org`, the payload only affects `attacker-org`'s repositories.
After the attack: the operator has organization `attacker-org` configured (their own GitHub App / webhook secret, which is not a privileged Shipit credential — it's just a self-service GitHub App setup on a repo/org the attacker controls), the attacker crafts a raw webhook body with `repository.owner.login = "attacker-org"` (to pick their own secret) but `repository.full_name = "victim-org/victim-repo"` (or omits repository entirely for a `status`/`sha` payload targeting a known victim commit SHA), signs it with `attacker-org`'s secret, and POSTs it to `/webhooks`. Verification passes, and the handler acts on the victim repository's stack/commit.

### Impact Explanation
This crosses the credential/repository boundary explicitly listed as in-scope: "an organization that authenticated versus the repository that is written." Concretely:
- Via `PushHandler`, an attacker can force `sync_github` on any stack belonging to a repository they don't own, causing Shipit to re-fetch/re-sync commits for an arbitrary tracked stack under attacker timing/control.
- Via `StatusHandler`, an attacker can forge a passing (or failing) commit status for any known commit SHA in the system, regardless of which repository/org it belongs to, because the lookup is `Commit.where(sha: params.sha)` with no repository check at all. [9](#0-8)  Forged "success" statuses feed directly into `StatusChecker`/`MergeRequest#all_status_checks_passed?`, which the merge queue (`ProcessMergeRequestsJob`) uses to decide whether to actually merge a pull request: `next unless merge_request.all_status_checks_passed? ... merge_request.merge!`. [10](#0-9) [11](#0-10)  Forging a required CI status therefore lets an attacker who controls nothing more than their own GitHub App on an unrelated repo cause an unauthorized merge of a victim's pull request — this matches the Critical "unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
Requires only that the operator has enabled multi-organization GitHub App configuration (documented, supported feature) and that the attacker controls at least one such organization's app/webhook secret (a low-privilege, self-service credential, not a Shipit account or repository-write access to the victim repo). No Shipit session, `ApiClient` token, or victim repository permissions are needed — only the ability to know/derive one configured organization's webhook secret and to send an HTTP POST to the public `/webhooks` endpoint, which is unauthenticated aside from the (bypassable-by-design) organization-selectable HMAC check.

### Recommendation
Bind the field used to select the verification secret to the field used to determine the mutation target: after selecting `github_app` via `repository_owner`, re-validate that `payload.dig('repository','full_name')` actually belongs to that same organization (e.g., assert `full_name.split('/').first.casecmp(repository_owner) == 0`) before dispatching to handlers, and reject otherwise. For `StatusHandler`, scope the `Commit` lookup by the repository declared (and verified) in the payload rather than a bare, global `sha` match.

### Proof of Concept
1. Configure Shipit with two GitHub App organizations, `attacker-org` (attacker-controlled, webhook secret known to attacker) and `victim-org` (contains the target stack/commit), per the documented multi-org config. [5](#0-4) 
2. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha, e.g. from a public PR>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/throwaway" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and verifies successfully against the attacker's own secret. [6](#0-5) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, inserting a forged "success" status. [4](#0-3) 
6. On the next `ProcessMergeRequestsJob` run, `all_status_checks_passed?` now returns true for the victim's pull request, and it is merged via `merge_request.merge!` — an unauthorized merge triggered entirely by a forged status the attacker could produce with only their own, unrelated organization's webhook credential. [10](#0-9)

## Creating the GitHub App

Shipit needs a GitHub App to authenticate users, receive Webhooks and access the API.

You can create a new one for your organization at `https://github.com/organizations/<your-org>/settings/apps/new`, or [https://github.com/settings/apps/new](https://github.com/settings/apps/new) for a regular user.

  - Homepage URL: The URL where Shipit will be deployed, e.g. `https://example.com`.
  - User authorization callback URL: It must be set to `<homepage>/github/auth/github/callback`, e.g. `https://example.com/github/auth/github/callback`.
  - Setup URL: Leave it empty.
  - Webhook URL: It must be set to `<homepage>/webhooks`, e.g. `https://example.com/webhooks`.
  - Webhook secret (optional): Fill it with some randomly generated string, and *keep it in clear on the side, you'll need it later*.
  - Repository permissions:
    - Checks: Read & write
    - Commit statuses: Read-only
    - Contents: Read & write (to allow merging)
    - Deployments: Read & write
    - Issues: Read & write (to allow closing related issues on merge)
    - Metadata: Read-only
    - Pull requests: Read & write
```
