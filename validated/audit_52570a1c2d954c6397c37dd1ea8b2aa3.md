### Title
AA distribution to multiple recipients atomically reverts on a single invalid output, allowing any recipient to permanently freeze funds for all others - (File: aa_composer.js)

### Summary
Autonomous Agents (AAs) can compose a single `payment` message with an `outputs` array that pays multiple, independently-controlled addresses in one response unit (e.g. a lottery/staking/reward-distribution AA paying out to many participants at once). The validation and construction of that outputs array is atomic: if any single output in the array is malformed, the entire response — and therefore the payout to *every other* recipient in the same message — is discarded via `bounce()`. This mirrors the reported ERC777/callback class of bug, where one malicious/careless recipient can block payment for everyone else, except here the "malicious callback" is replaced by attacker-influenced data that ends up as an invalid output address/amount at payout time.

### Finding Description
When an AA response is composed, `sendUnit()` iterates the response `messages`, and for payment messages it validates `payload.outputs` as a whole array: [1](#0-0) 

Any single bad element (invalid address, unknown field, negative/fractional amount) causes the **entire message** to fail with `bounce(...)`, not just the bad output being dropped. `bounce()` then discards the whole in-progress response: it clears the pending state update (`objStateUpdate = null`), restores balances in dry-run mode, and (for a primary trigger) either sends back the trigger's own funds or produces no response at all: [2](#0-1) 

The response is only ever committed atomically after the whole `messages` array (potentially containing outputs to many different recipients) survives validation: [3](#0-2) 

If an AA's logic derives one of several output addresses in a shared distribution message from data that is influenced by an untrusted party (e.g. a participant-registered address stored via `trigger.data`/state vars in a prior trigger, later reused as an output target in a multi-recipient payout), that party can supply a value that is syntactically acceptable at registration time but fails `ValidationUtils.isValidAddress` (or produces a negative/fractional/malformed output) at the moment the distribution payment is composed. Because outputs are validated with `.every()` over the whole array, this single bad entry bounces the complete message, so **all other legitimate recipients in the same distribution round lose their payout** for that response, and the AA's held funds cannot be distributed until the operator can somehow work around the poisoned entry (which the AA logic itself has no generic mechanism to skip).

This is directly analogous to the ERC777/callback report: a single participant, without any special privilege, can force a revert that blocks the payout intended for everyone else sharing the same distribution unit.

### Impact Explanation
Funds held by an AA that are meant to be distributed to many recipients in one message can become effectively frozen or indefinitely delayed if the batching logic keeps re-selecting the same poisoned recipient/output on every attempt (e.g. deterministic "pay everyone due" logic), denying payouts to all honest recipients until the AA author redeploys or patches the distribution logic (which oscript/AA state is otherwise immutable for). This is a fund-freezing impact scoped to AA balances, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
Likelihood depends on AA design: only AAs that (a) accept recipient addresses or output-defining data from users without strict address validation at input time, and (b) batch multiple recipients' payouts into a single `payment` message reused across triggers, are exposed. This is a common pattern for reward/dividend/lottery-style AAs listed in the codebase's own sample scripts (e.g. `test/samples/send_all.oscript`, `option_contract.oscript`) which build outputs from `trigger.data`/state vars. An unprivileged participant who can influence stored recipient data (e.g. by registering with a superficially valid-looking but ultimately malformed string, or a negative/fractional amount slipped through prior loose validation) can trigger this at will on the next batched distribution.

### Recommendation
- In AA/oscript documentation and best-practice guidance, warn AA authors against batching multiple independently-controlled recipients into a single `payment` message's `outputs` array when any component of an output (address/amount) is derived from untrusted, previously-stored data.
- Recommend/implement a pattern where each recipient's share is paid via its own separate `payment` message (or claimable independently, e.g. a pull-based withdrawal state var) so that one bad output does not `bounce()` the entire response and does not block payouts to unrelated addresses in the same unit.
- Consider making address/amount validation happen strictly at the point untrusted data is first accepted into AA state (during registration), rather than only at the point of use, to fail fast for a single bad actor rather than for the whole batch at distribution time.

### Proof of Concept
1. Deploy an AA that, in a prior trigger, stores participant-supplied strings (e.g., `trigger.data.address`) into a state var without a strict address-format check (only checking basic syntax, not `isValidAddress`/checksum), intending them as future payout targets — a natural pattern for referral/dividend/lottery-style AAs.
2. One participant supplies an address-like string that passes any loose formula checks used at registration but fails Obyte's checksum-based `isValidAddress` (used by ocore during output validation).
3. On the next distribution trigger, the AA composes a single `payment` message whose `outputs` array includes all registered participants, including the poisoned entry.
4. During `sendUnit`/`completePaymentPayload`, `payload.outputs.every(o => ValidationUtils.isValidAddress(o.address))` fails for that one entry, and `bounce("invalid addresses in outputs")` discards the whole response [4](#0-3) , so no participant in that batch — not just the attacker — receives their payout, and the AA's funds remain locked in the AA balance until the logic is fixed to bypass or exclude the poisoned recipient.
