**No vulnerability found for this question.**

The code in `execution/executor-types/src/transactions_with_output.rs:154-156` and `188-203` correctly derives `is_reconfig` purely from `TransactionOutput::has_new_epoch_event()` [1](#0-0) , and `has_new_epoch_event()` checks whether any emitted `ContractEvent` matches the `NewEpochEvent`/`NewEpoch` type tag [2](#0-1) . This is a downstream, purely-functional consumer of whatever events the VM execution actually produced — it does not itself perform any signer/privilege check, but that's fine because the privilege boundary is enforced far upstream, in Move's type and module-visibility system, not at this data-structure layer.

The `NewEpochEvent`/`NewEpoch` structs are defined inside `aptos_framework::reconfiguration` and are only ever constructed and emitted inside the `reconfigure()` function, which is `public(friend)` and can only be called by an enumerated allowlist of trusted framework modules (`aptos_governance`, `block`, `consensus_config`, `execution_config`, `gas_schedule`, `genesis`, `version`, `reconfiguration_with_dkg`) [3](#0-2) [4](#0-3) . Move's module/struct visibility rules mean no external module — including one authored and published by an arbitrary unprivileged account — can construct a value of type `reconfiguration::NewEpochEvent` or call `reconfigure()`, since the struct has no public constructor and the function is friend-scoped. The VM's `event::emit`/`emit_event` calls only succeed for events whose underlying struct the calling module is authorized to construct; an ordinary `UserTransaction` executing arbitrary Move code has no path to fabricate this specific event type.

This is corroborated by production code that specifically checks for `is_new_epoch_event()`/`is_new_epoch_event` in trusted contexts only — e.g. genesis write-set validation asserts an exact count of exactly one such event [5](#0-4) , and waypoint change-set validation requires it alongside a new-block event for privileged write-set transactions [6](#0-5) . Nowhere does regular user-transaction execution have a code path that can emit this event, so `TransactionsToKeep::is_reconfig` cannot be flipped by an unprivileged sender in the way the question hypothesizes — the exploit requires already fabricating an event that the Move VM's own type/visibility system prevents unprivileged code from producing, which falls outside the "unprivileged input" boundary condition of this review.

    /// Signal validators to start using new configuration. Must be called from friend config modules.
    public(friend) fun reconfigure() acquires Configuration {
        // Do not do anything if genesis has not finished.
        if (chain_status::is_genesis()
            || timestamp::now_microseconds() == 0
            || !reconfiguration_enabled()) { return };

        let config_ref = borrow_global_mut<Configuration>(@aptos_framework);
        let current_time = timestamp::now_microseconds();

        // Do not do anything if a reconfiguration event is already emitted within this transaction.
        //
        // This is OK because:
        // - The time changes in every non-empty block
        // - A block automatically ends after a transaction that emits a reconfiguration event, which is guaranteed by
        //   VM spec that all transactions comming after a reconfiguration transaction will be returned as Retry
        //   status.
        // - Each transaction must emit at most one reconfiguration event
        //
        // Thus, this check ensures that a transaction that does multiple "reconfiguration required" actions emits only
        // one reconfiguration event.
        //
        if (current_time == config_ref.last_reconfiguration_time) { return };

        reconfiguration_state::on_reconfig_start();

        // Call stake to compute the new validator set and distribute rewards and transaction fees.
        stake::on_new_epoch();
        storage_gas::on_reconfig();

        assert!(
            current_time > config_ref.last_reconfiguration_time,
            error::invalid_state(EINVALID_BLOCK_TIME)
        );
        config_ref.last_reconfiguration_time = current_time;
        spec {
            assume config_ref.epoch + 1 <= MAX_U64;
        };
        config_ref.epoch += 1;

        event::emit(NewEpoch { epoch: config_ref.epoch });
        event::emit_event<NewEpochEvent>(
            &mut config_ref.events,
            NewEpochEvent { epoch: config_ref.epoch }
        );

        reconfiguration_state::on_reconfig_finish();
    }
