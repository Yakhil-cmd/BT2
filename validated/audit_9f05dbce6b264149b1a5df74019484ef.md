**Rationale:** CVE-2017-15566 describes a privilege-escalation bug specific to Slurm's SPANK plugin architecture: attacker-controlled environment variables leak into root-privileged Prolog/Epilog scripts spawned by the workload manager. The violated invariant is "environment inherited by a privileged subprocess must not be attacker-controlled."

Polkadot SDK has no comparable mechanism reachable from a permissionless on-chain entry point (signed extrinsic, contract call, or XCM message). The only place in this codebase that deals with privileged subprocess spawning and environment variable inheritance is the **PVF worker security** subsystem, and it implements the *opposite* of the Slurm flaw — it actively strips environment variables before/while spawning worker and job processes that execute untrusted code (PVFs), and verifies removal: [1](#0-0) 

This check is enforced in the worker startup path before any untrusted code execution occurs, and causes shutdown in secure-validator mode if env vars are found: [2](#0-1) 

There is no "attacker-controlled environment variable inherited by a root/privileged process" pathway here: PVF workers are spawned by the validator's own node process (not by an untrusted, attacker-influenced entry point), the environment is explicitly cleared (`env_clear()`) when spawning security-check subprocesses in `polkadot/node/core/pvf/src/security.rs` (lines 285–292), and no signed extrinsic, contract call, or XCM message can inject environment variables into a privileged process. This is a node-operator/validator-local security hardening feature, not a permissionless runtime attack surface, so the CVE's threat model (privilege escalation via SPANK env vars during job scheduler script execution) has no reachable analog satisfying the required entry-point and attacker-model constraints.
