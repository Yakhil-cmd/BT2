### Title
Cross-tenant CI status forgery via webhook signature verified against the wrong repository binding — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit selects the HMAC secret used to verify an incoming webhook based on `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body, but the handlers that then act on the payload (in particular `StatusHandler`) never re-check that the event actually pertains to a repository owned by that organization. An attacker who legitimately controls a GitHub App installation for their *own* organization (an unprivileged, self-served credential documented in `docs/setup.md`'s "Using Multiple Github Applications" section) can sign an arbitrary payload with their own webhook secret while placing an arbitrary commit `sha` belonging to a *different* tenant's repository in the body. Shipit only validates that the signature matches the secret of the org named in the payload, then blindly applies the `status` event to whatever commit in the whole database matches that `sha`.

### Finding Description
`WebhooksController#verify_signature` picks the `github_app` (and thus the HMAC secret) to verify against using the organization name extracted from the same untrusted payload it is about to verify: [1](#0-0) [2](#0-1) 

This design is safe only if handlers subsequently confirm that the acted-upon resource (repository/commit) belongs to that same organization. Most handlers do this indirectly via `Handler#stacks`, which scopes lookups by `payload.dig('repository', 'full_name')`: [3](#0-2) 

However, `StatusHandler` does not go through `stacks`/`repository_name` at all — it looks up commits globally by SHA, with no repository or organization scoping whatsoever: [4](#0-3) 

The binding that should hold is:
`organization whose secret authenticated the request == organization owning the resource being mutated`

but for the `status` event this is never enforced: the signature is checked against the attacker's own org's secret (a value they legitimately possess), while the mutation (`commit.create_status_from_github!`) is applied to a commit belonging to any repository/organization configured in the Shipit instance, matched purely by `sha`.

### Impact Explanation
Commit SHAs are public, non-secret values (visible on GitHub, in PRs, CI logs, etc.), so an attacker can trivially learn the SHA of a victim's commit under a completely different, unrelated GitHub organization/repository hosted on the same Shipit instance (a common deployment scenario, as documented for "Using Multiple Github Applications"). By forging a `status` webhook, signed with their own organization's `webhook_secret`, that carries the victim's commit SHA and a `state: "success"` / matching `context`, the attacker creates a fabricated passing CI status on the victim's commit: `commit.create_status_from_github!(params)`. If that status context is one of the `required_statuses` gating Shipit's merge queue or deploy safety checks (`app/models/shipit/deploy_spec.rb`'s `required_statuses`/`blocking_statuses`), this can cause Shipit to treat an unvetted/failing commit as CI-green, enabling an unauthorized merge or deploy of that commit — without the attacker ever having credentials, membership, or write access to the victim's organization or repository. This satisfies the Critical impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
The only prerequisite is that the attacker operates their own legitimate GitHub App installation against the same multi-tenant Shipit instance (explicitly a supported, documented configuration) and knows a target commit SHA in another tenant's repository — both trivially available to any unprivileged external actor with a valid installation of their own. No repository write access, no `ApiClient` token, no session, and no access to the victim's secrets are required, matching the "unprivileged attacker" threat model. This is a straightforward, low-effort HMAC-signed HTTP POST, not requiring any race condition or resource exhaustion.

### Recommendation
For the `status` (and any other) webhook handler, cross-check that the commit/repository being mutated actually belongs to the organization/repository that supplied the verified signature, e.g. scope `StatusHandler#process` through `stacks`/`repository_name` (as `PushHandler` and the `pull_request` handlers do) instead of a global `Commit.where(sha:)` lookup, and reject the event if the resolved repository's owner does not match `repository_owner` used during signature verification.

### Proof of Concept
1. Register/own GitHub App installation for organization `attacker-org` on the shared Shipit instance, obtaining its `webhook_secret` (self-owned, unprivileged credential).
2. Identify a target commit `sha` belonging to `victim-org/victim-repo`, also hosted on the same Shipit instance, and a status `context` that is part of that stack's `required_statuses`.
3. Build the JSON body:
```json
{
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"},
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "<required-context>"
}
```
4. Compute `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_of_attacker_org, body)>`.
5. POST to `/webhooks` with `X-Github-Event: status`.
6. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s `github_app`, and successfully verifies the attacker-computed signature.
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and calls `create_status_from_github!`, injecting a forged passing status onto a commit the attacker never had access to.
