### Title
Webhook signature verification is bound to a payload-supplied organization while handlers act on a different, unverified repository/commit field — cross-repository status/sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to use for HMAC verification based on `repository.owner.login` (or `organization.login`) read directly from the untrusted JSON body, then verifies the HMAC only proves the request was signed with *that organization's* secret. It never checks that the *content* the handlers subsequently act on (a different `repository.full_name`, or in the case of `StatusHandler`, a bare commit `sha` with no repository scoping at all) actually belongs to the same organization/repository whose secret produced the signature.

### Finding Description
`verify_signature` computes the signer based on a payload field: [1](#0-0) [2](#0-1) 

The HMAC check only proves "this body was signed with `organization X`'s webhook secret" — it says nothing about which repository the body's other fields describe: [3](#0-2) 

But every downstream `Handler` resolves its target purely from body fields that are never cross-checked against `repository_owner`: [4](#0-3) 

`PushHandler` uses `repository.full_name` (a field independent from the `repository.owner.login` used for signature-org selection) to pick stacks and enqueue a resync: [5](#0-4) 

`StatusHandler` is even more decoupled: it doesn't consult `repository` at all, only a bare `sha`, and updates the status of every `Commit` in the entire installation sharing that SHA: [6](#0-5) 

**Binding broken (equality that should hold but doesn't):**
`organization whose webhook_secret authenticated the request` == `organization/repository that the handler subsequently mutates`.

Before the attack: an org's `webhook_secret` should only be able to affect that org's own repositories/stacks.
After the attack: a request signed with Org A's `webhook_secret` (read/selected from `repository.owner.login = "OrgA"`) can carry a `repository.full_name` or `sha` referencing Org B's stack/commit, and the engine will process it as legitimate, because nothing ties the signing key to the acted-upon resource.

This directly mirrors the report's bug class: a value used to select/verify one thing (`get_dy`/allowance target vs. `approve` target in the report; here, `repository_owner` used to pick the HMAC secret) is not the same value later relied upon for the state-changing action (`repository.full_name`/`sha` used by the handler) — the two are never reconciled.

### Impact Explanation
Any organization/repository legitimately onboarded to a shared Shipit instance (i.e., any tenant with a known, distinct `webhook_secret` in `Shipit.github`) can forge webhook deliveries for *any other* tracked repository/stack on the same instance:
- `StatusHandler` lets the attacker set arbitrary CI status (`state`, `context`, `description`, `target_url`) on any `Commit` row matching a guessed/observed SHA belonging to a different repository, which is exactly the signal Shipit's deployability checks (`Commit#create_status_from_github!`, `Status`/`release_status`) rely on to gate whether a commit is safe to deploy. Forging a passing status on a commit in a repo the attacker doesn't control can let an unrelated party manipulate what appears "deployable," contributing to an unauthorized deploy decision on that stack.
- `PushHandler` lets the attacker force a `GithubSyncJob` re-sync for another org's stack, an unauthorized cross-tenant trigger of internal processing.

This satisfies the required "High" impact bar (escalation affecting authorization/deploy-gating state and unauthenticated cross-repository writes to Shipit's own DB records for repos/stacks the attacker doesn't own), reachable strictly by an unprivileged party that merely needs to be a tenant on the same shared Shipit deployment with a known webhook secret for their own repo — no `ApiClient` token, no GitHub write access to the victim repo, no session.

### Likelihood Explanation
Requires a specific, moderately realistic multi-tenancy precondition: the Shipit instance must have more than one GitHub organization/App configured (as `config/secrets.yml`/`Shipit.github` explicitly supports — see `test/dummy/config/secrets_double_github_app.yml`), and the attacker must control one of those configured organizations (its `webhook_secret`) while targeting a stack belonging to a different configured organization. Given that Shipit's own docs and secrets templates support multiple orgs on one instance, this is a realistic deployment shape, not a hypothetical one.

### Recommendation
After resolving the signing organization in `verify_signature`, re-validate that every subsequent handler's resolved repository (`repository.full_name` for most handlers, and the repository owning the matched `Commit` for `StatusHandler`) belongs to that same signing organization before processing. Concretely: pass the verified `repository_owner` into `Handler.call`, and in `Handler#stacks` / `StatusHandler#process`, filter to `Repository`/`Commit` records whose owner matches the verified organization, rejecting (204/422) any mismatch.

### Proof of Concept
1. Shipit instance configured with two orgs, `AttackerOrg` (attacker is an admin, knows its `webhook_secret`) and `VictimOrg` (tracks a private stack with a known commit SHA `S`, unrelated to `AttackerOrg`).
2. Attacker crafts a `status` event body:
   ```json
   { "sha": "S", "state": "success", "context": "ci/tests",
     "repository": { "full_name": "AttackerOrg/whatever", "owner": { "login": "AttackerOrg" } } }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner == "AttackerOrg"`, fetches `Shipit.github(organization: "AttackerOrg")`, and the HMAC checks out — request is accepted.
5. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the commit that actually belongs to `VictimOrg`'s stack (unrelated to the signing org), and calls `create_status_from_github!`, injecting a forged CI status onto a commit the attacker does not own — with no organization/repository consistency check anywhere in the chain.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
