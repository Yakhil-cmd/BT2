This confirms the analog vulnerability class: the GitHub App used to verify a webhook's signature is selected via `Shipit.github_app_config(organization)`, keyed strictly by `repository_owner` (`params.dig('repository','owner','login')` or the `organization` sub-object). Once verification passes, downstream `Webhooks::Handlers::Handler#repository_name` reads a *different* payload field (`payload.dig('repository', 'full_name')`) to resolve the `Repository`/`Stack` that gets mutated. Nothing in `WebhooksController#verify_signature` binds the value used to select the secret to the value later used to select the write target beyond both fields being inside the same signed JSON body.

### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while write target is resolved from `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the per-organization `GitHubApp` (and its `webhook_secret`) using `repository_owner`, parsed from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) [1](#0-0) [2](#0-1) . Every handler that processes the (now "verified") payload instead resolves the actual repository/stack to mutate from a separate field, `repository.full_name`, via `Repository.from_github_repo_name` [3](#0-2) [4](#0-3) . This is the "organization that authenticated versus the repository that is written" binding named in scope.

### Finding Description
Shipit supports multiple GitHub organizations, each configured with its own `webhook_secret` under `secrets.github` [5](#0-4) . `verify_signature` looks up the app/secret purely by `repository_owner`, an attacker-controlled JSON field inside the very payload being verified [2](#0-1) . It computes an HMAC over the raw body using that org's secret and compares it to `X-Hub-Signature` [6](#0-5) . Because the signature check binds only "does this payload match organization X's secret," and any attacker who legitimately controls a repo/organization onboarded into Shipit (e.g., a `shipit.yml`-driven org with its own webhook secret, comparable to the "unprivileged depositor" in the analog) can produce validly-signed payloads for `repository.owner.login = X`, the equality the code actually enforces is:

`HMAC_valid(secret_for(payload.repository.owner.login), raw_body) == true`

but the mutation performed afterwards is keyed on a *different, unchecked* subfield of the same attacker-supplied body:

`target_repository = payload.repository.full_name`

There is no code path that asserts `payload.repository.full_name`'s owner equals `payload.repository.owner.login` (or `organization.login`). An attacker who owns/administers organization `X` in Shipit (a legitimate, but for this repository, unprivileged party) can send a validly-signed-by-X webhook body where `repository.full_name` is set to `"victim-org/victim-repo"` while `repository.owner.login` is `"X"`. Signature verification succeeds (it's genuinely signed with X's secret), but the handler, e.g. `PushHandler`, resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack [7](#0-6) . The same disjunction affects `PullRequest::OpenedHandler`, `LabeledHandler`, `UnlabeledHandler`, `LabelCapturingHandler`, `ClosedHandler`, etc., all of which independently re-derive `repository` from `params.repository.full_name` for provisioning/archiving decisions on `ReviewStack`s [8](#0-7) [9](#0-8) .

This mirrors the reported bug class precisely: the contract computed and enforced its check (interest-rate vote) on one state variable, while a second, unguarded consumer (vesting-time calculation) trusted a different derived value without re-validating consistency between the two. Here, the signature check validates on `repository.owner.login`, while the handlers act on `repository.full_name`, with no code asserting the two agree.

### Impact Explanation
If exploitable, this allows cross-repository writes: an org with a legitimately configured (but for the target repo, unauthorized) webhook secret can force GitHub-sync operations (`sync_github`), archive/unarchive/provision `ReviewStack`s, or otherwise mutate state belonging to a completely different repository/organization that it does not control on GitHub — an unauthorized write across repository trust boundaries, matching the "cross-repository writes" Critical-impact category.

### Likelihood Explanation
Exploitability depends entirely on whether the deployment actually configures more than one organization (i.e., `github_default_organization` is non-nil and multiple entries exist under `secrets.github`) [10](#0-9) , and whether an attacker can obtain webhook-secret-signing capability for at least one configured organization that is not the intended victim (e.g., via a GitHub App installed on an org they control, if a single Shipit instance multi-tenants across untrusted orgs). This requires a specific multi-org deployment topology; in the common single-organization (`github_default_organization.nil?`) configuration this analog does not apply, since there is only one secret and thus no owner-vs-repository confusion.

### Recommendation
After verifying the signature, assert that `payload.dig('repository','full_name')` (and `organization.login`, if present) is consistent with the `repository_owner`/organization whose secret validated the request, and reject the webhook (422) if they disagree, before any handler resolves `Repository.from_github_repo_name`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s under `secrets.github` [5](#0-4) .
2. Attacker, who controls `attacker-org`'s GitHub App/webhook secret, crafts a `push` payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha already known to exist on victim repo>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
3. Attacker signs the raw body with `attacker-org`'s `webhook_secret` and sends it as `X-Hub-Signature` to `POST /github/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker-org')` from `repository_owner` and successfully verifies the signature against `attacker-org`'s secret [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` = `victim-org/victim-repo`, and calls `sync_github(expected_head_sha: ...)` on the victim's stack [11](#0-10) [3](#0-2) , mutating a repository the attacker never authenticated for.

**Uncertainty**: I could not verify the exact structure/typical layout of `secrets.github` in a real multi-org deployment (i.e., whether `webhook_secret` is genuinely unique per-organization in practice, or whether operators commonly share one secret across all configured orgs, which would make this moot). I also could not confirm whether GitHub itself would ever deliver a payload with mismatched `repository.owner.login` vs `repository.full_name` owner in an actual webhook — the exploit requires an attacker to submit a forged raw HTTP request directly to Shipit's `/github/webhooks` endpoint (not via real GitHub delivery), which is consistent with the "unprivileged attacker" framing but its practical severity depends on the multi-tenant deployment assumption above.
