This confirms the vulnerability: the org used to select the webhook signing secret (`repository.owner.login`, read via `repository_owner` in `WebhooksController#verify_signature`) is a different field than the repository actually written to (`repository.full_name`, read via `Handler#repository_name`), and both come from the same unverified-at-that-point, attacker-supplied JSON body.

### Title
Webhook signature is verified against an organization derived from an unsigned field, letting an attacker who controls one GitHub org's webhook secret impersonate another organization's repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the `X-Hub-Signature` against by reading `params.dig('repository','owner','login')` (or `organization.login`) straight out of the still-unauthenticated JSON body [1](#0-0) . Once the signature check passes, the actual repository that gets acted upon is resolved from a *different* field of the same payload, `repository.full_name`, in `Shipit::Webhooks::Handlers::Handler#repository_name`, which is then used to look up the `Repository`/`Stack` via `Repository.from_github_repo_name` [2](#0-1) [3](#0-2) . These two payload fields (`repository.owner.login` and `repository.full_name`) are never cryptographically bound together by GitHub's HMAC scheme in a way this code enforces beyond "the whole raw body matched some org's secret" — but the org selection itself is attacker-controlled input read before the signature is verified.

### Finding Description
The binding that should hold is: **organization whose secret authenticated the request == organization owning the repository the handler writes to**. In practice the code breaks this into two independent reads of the same untrusted body:

1. `repository_owner` (used to pick `Shipit.github(organization: repository_owner)` and thus which `webhook_secret` to HMAC-check against) is taken from `params.dig('repository','owner','login')` / `organization.login` [4](#0-3) .
2. `repository_name` (used by every handler, e.g. `PushHandler`, `StatusHandler`, to find the `Stack`/`Commit` to mutate) is taken from `payload.dig('repository', 'full_name')` [5](#0-4) .

GitHub's webhook signature only proves "this exact byte-for-byte payload was HMAC-signed with organization X's `webhook_secret`" — it says nothing about internal consistency between fields inside that payload. Because Shipit installs a separate GitHub App/webhook secret per organization (`Shipit.github(organization: ...)`), an attacker who legitimately controls their own GitHub organization (and therefore possesses a valid secret for webhooks originating from it) can construct a raw JSON body where `repository.owner.login` equals their own org (so the signature check in `verify_signature` succeeds using their own secret) while `repository.full_name` is forged to name a victim's `owner/repo` combination that Shipit tracks. Since GitHub does not require these fields to be self-consistent when delivering a webhook payload, and Shipit trusts `full_name` for repository resolution independent of which org authenticated the request, `Repository.from_github_repo_name` will resolve the victim repository, and the handler (e.g., `PushHandler`) will act on the victim stack — e.g., triggering `stack.sync_github(expected_head_sha: params.after)` [6](#0-5)  — even though the request was never actually signed by the victim organization's secret.

### Impact Explanation
This falls under **cross-repository writes**: an attacker who only controls their own GitHub organization/app installation can forge webhook events (push, status, check_suite, etc.) that Shipit will process against a victim's stack, since org-based signature verification and repository resolution use two independently-attacker-controlled JSON keys instead of one. This could be used to push forged commit `status`/`check_suite` results into a victim's undeployed commits (potentially bypassing CI gating for continuous deployment) or forcing spurious `sync_github` calls against a stack the attacker does not own.

### Likelihood Explanation
Requires the attacker to already have their own valid GitHub organization/App installation registered in Shipit config (a real but plausible precondition for any multi-tenant Shipit deployment) and to know or guess a victim `owner/repo` full name tracked by the instance — both realistic. No privileged Shipit credentials, `ApiClient` tokens, or the victim's `webhook_secret` are required, only the attacker's own valid HMAC key for a different org.

### Recommendation
Bind the two lookups together: after verifying the signature, re-derive the organization strictly from the same `repository.full_name`/`Repository` record that the handler will act on (not from a separately-read `repository.owner.login`/`organization.login`), and reject the request if the org used to select the signing secret does not match the owner of the resolved `Repository`.

### Proof of Concept
1. Attacker registers/controls GitHub organization `attacker-org`, which has a valid Shipit App installation and thus a genuine `webhook_secret`.
2. Attacker crafts a `push` webhook JSON body: `{"ref": "refs/heads/master", "after": "<forged-sha>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}}`.
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s real `webhook_secret` over that exact raw body and POSTs it to `WebhooksController#create`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature using the attacker's own secret [7](#0-6) .
5. `PushHandler#process` resolves `stacks` via `repository_name` = `payload.dig('repository','full_name')` = `"victim-org/victim-repo"` [2](#0-1) , matches the victim's `Stack`, and calls `stack.sync_github(expected_head_sha: ...)` on the victim's stack — despite the request never being signed with the victim organization's secret.
