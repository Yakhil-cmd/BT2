### Title
Cross-tenant Status webhook write via unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, unlike `PushHandler` and the base `Handler#stacks` helper which correctly scope queries to the repository named in the payload. Because commit SHAs are content-addressed and can legitimately collide across unrelated repositories (shared base commits, cherry-picks, identical empty-tree commits), an attacker who owns one repository can push a `status` webhook, correctly signed with their own organization's `webhook_secret`, that mutates commit-status records — and potentially triggers continuous deployment — for a completely unrelated tenant's stack.

### Finding Description
The broken binding is: `organization_that_signed_the_webhook == organization_owning_every_Commit_mutated_by_the_handler`. It does not hold.

`WebhooksController#verify_signature` only authenticates the payload against the org identified by `repository_owner` (`params.dig('repository','owner','login')`): [1](#0-0) 

Once verified, `StatusHandler#process` ignores the `repository` field of the payload entirely and queries commits globally: [2](#0-1) 

Contrast this with the base `Handler` class, which exposes a `stacks` helper that scopes to the repository named in the payload (`Repository.from_github_repo_name(repository_name)`), and `PushHandler`, which correctly uses it: [3](#0-2) [4](#0-3) 

`StatusHandler` never calls `stacks`/`repository_name`, so any `Commit` row anywhere in the database sharing the attacker-supplied `sha` is mutated via `create_status_from_github!`, which delegates to `Status.replicate_from_github!` scoped only by `stack_id` taken from the (victim's) commit itself: [5](#0-4) [6](#0-5) 

Creating a `Status` fires `schedule_continuous_delivery` on the commit's own stack, independent of which organization sent the webhook: [7](#0-6) 

Attacker flow: attacker owns `attacker/public-repo` (any GitHub org they control), obtains/knows a commit SHA `X` that also exists as a `Shipit::Commit` row under an unrelated `victim/private-repo` stack (e.g., a shared upstream commit, cherry-pick, or reproducible empty-tree commit — no cryptographic SHA-1 break needed). Attacker POSTs `/webhooks` with `X-Github-Event: status`, a body `{sha: X, state: 'success', repository: {full_name: 'attacker/public-repo', owner: {login: 'attacker'}}}`, signed with `attacker`'s own `webhook_secret`. `verify_signature` passes because it only checks the signature against `attacker`'s org config. `StatusHandler#process` then finds *every* `Commit` with `sha == X` across all tenants, including `victim`'s, and writes a `Status` row and potentially triggers deploy scheduling on `victim`'s stack.

None of the existing guards prevent this: `drop_unhandled_event` and `verify_signature` only gate on event type and the attacker's own organization signature; `ExplicitParameters` schema in `StatusHandler.params` only validates types (`sha`, `state`, etc.), not repository ownership; there is no `stacks`/`repository_name` scoping applied in this handler at all.

### Impact Explanation
This is a payload for one repository (attacker's) mutating another organization's `Commit`/`Status` records and potentially triggering `Stack#trigger_continuous_delivery`/scheduling a deploy for a stack the attacker never authenticated against — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". Blast radius spans across all tenants/organizations hosted by the same Shipit instance, since the `Commit.where(sha:)` query is completely unscoped.

### Likelihood Explanation
The attacker needs: (1) their own GitHub repo with a configured `webhook_secret` pointing at the shared Shipit instance (or knowledge of that secret from being a legitimate low-privilege tenant), and (2) a SHA collision with a real `Shipit::Commit` in the target stack. The collision precondition is realistic (shared base commits across forks, cherry-picks, or identical empty-tree commits, which are byte-for-byte reproducible and require no cryptographic break) rather than requiring a genuine SHA-1 collision. Given multi-tenant Shipit deployments where many independent repositories share the same host, this is a plausible and repeatable attack once a matching SHA is identified.

### Recommendation
Scope `StatusHandler#process` (and any other handler doing raw `Commit`/`sha` lookups) to the repository asserted in the payload, using the same `stacks`/`repository_name` pattern already used by `PushHandler`, e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or filtering `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`.

### Proof of Concept
In `test/controllers/webhooks_controller_test.rb` (or `test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two fixtures: `stack_a` (repository `attacker/public-repo`) and `stack_b` (repository `victim/private-repo`), each with a `Commit` row sharing the same `sha: 'deadbeef...'`.
2. Stub/allow `GithubHook`/`verify_webhook_signature` for `attacker`'s org only (as in existing `WebhooksControllerTest` setup, e.g. `GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
3. POST `/webhooks` with `X-Github-Event: status` and body `{sha: shared_sha, state: 'success', repository: {full_name: 'attacker/public-repo', owner: {login: 'attacker'}}}`.
4. Assert the binding both before and after: before, `victim_commit.statuses.count == 0`; after, `assert_difference('victim_commit.statuses.count', 1) { post :create, body:, as: :json }` — showing `victim/private-repo`'s commit gained a status despite the webhook only being signed and scoped for `attacker/public-repo`.
