### Title
Webhook signature bypass when `webhook_secret` is unset for an organization allows forged `pull_request` events to create/archive `ReviewStack`s - (File: lib/shipit/github_app.rb)

### Summary
`Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the configured GitHub app entry for an organization has no `webhook_secret`, so `WebhooksController#verify_signature` accepts any unsigned (or garbage-signed) POST to `/webhooks` naming that organization's repository. This lets an attacker forge `pull_request` events that flow straight into `ReviewStackAdapter#create!`/`find_or_create!`, creating a `ReviewStack` for a repository they never authenticated as GitHub.

### Finding Description
The broken binding is: **"a webhook payload is authorized to mutate Shipit state" should imply "the payload's HMAC signature was verified against a secret owned by GitHub for that org."** In this codebase that implication does not hold when `webhook_secret` is absent.

Code path:
- `WebhooksController#verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` from the attacker-controlled `repository.owner.login`/`organization.login` field, then calls `github_app.verify_webhook_signature(header, raw_post)` and only `head(422)` if it returns false [1](#0-0) .
- `GitHubApp#verify_webhook_signature` short-circuits: `return true unless webhook_secret` [2](#0-1) .
- `webhook_secret` is set from `@config[:webhook_secret].presence` in the constructor, so any org config block with a blank/missing `webhook_secret` key (a real, documented configuration shape - see `config/secrets.development.shopify.yml` and `docs/setup.md`'s "Using Multiple Github Applications" example) yields `nil`, making verification always pass [3](#0-2) .
- Once verification passes, `WebhooksController#create` parses the raw body and dispatches to registered handlers, e.g. `OpenedHandler#process`, which resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and calls `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` [4](#0-3) .
- `ReviewStackAdapter#create!` persists a `ReviewStack` with attacker-supplied `branch`, `environment`, and `pull_request` payload with no further authentication check [5](#0-4) .

Existing tests confirm the semantics directly - the suite mocks `verify_signature` to return `true` for the "happy path" tests and only exercises the `false`/exception branches explicitly [6](#0-5) ; there is no test covering the `webhook_secret.nil?` path, and no code elsewhere enforces that a secret must be present before granting trust.

No other guard intervenes: `drop_unhandled_event` only filters by event type, not by authenticity [7](#0-6) , and `ExplicitParameters` schemas in the pull_request handlers only validate shape/types, not provenance.

### Impact Explanation
An attacker who knows (or targets) an organization whose Shipit GitHub App entry has no `webhook_secret` configured can POST arbitrary, unsigned JSON to `/webhooks` naming any repository under that org's `full_name`, and have it accepted as if it came from GitHub. This is a full authentication bypass for the webhook ingestion channel for that org: the attacker can fabricate `pull_request` `opened`/`labeled`/`reopened`/`closed` events to create, archive, or unarchive `ReviewStack` records, inject arbitrary `branch`, PR number/labels, and sender login into stack state - all without ever opening a real PR or possessing any Shipit secret. This is repeatable per request and applies to every repository under any org configured this way (multi-tenant blast radius scales with number of misconfigured/secretless orgs). It matches the Critical category "authentication bypass (forged webhook ... accepted)".

### Likelihood Explanation
The only precondition is that some org entry in `Shipit.github` config has `webhook_secret` blank - a state the code and documentation explicitly allow and even ship as an example (`config/secrets.development.shopify.yml`, `docs/setup.md`'s multi-org example, `template.rb`'s generated scaffold all show `webhook_secret:` with no value). Operators using OAuth-only app entries, or who forget to fill in the secret for a newly added org in a multi-org setup, trivially hit this. The attacker needs no credentials at all - just network access to POST to `/webhooks` - making the cost extremely low and fully repeatable.

### Recommendation
Fail closed instead of failing open: `verify_webhook_signature` should return `false` (or the controller should reject with 422) when `webhook_secret` is blank, rather than treating a missing secret as an implicit "trust everything" signal. At minimum, require a non-blank `webhook_secret` for any org configuration before that org's webhooks are processed, and add a startup/config validation that surfaces the misconfiguration loudly.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test "unsigned payload is accepted when org webhook_secret is blank" do
  secretless_app = Shipit::GitHubApp.new('shopify', webhook_secret: nil)
  Shipit.stubs(:github).with(organization: 'shopify').returns(secretless_app)

  request.headers['X-Github-Event'] = 'pull_request'
  # No X-Hub-Signature header at all, or a garbage one:
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef'

  payload = {
    action: 'opened',
    number: 999,
    pull_request: {
      id: 1, number: 999, url: 'https://x', title: 't', state: 'open',
      additions: 0, deletions: 0,
      head: { sha: 'abc', ref: 'attacker-branch' },
      user: { login: 'attacker' }, assignees: [], labels: []
    },
    repository: { full_name: 'shopify/some-repo', owner: { login: 'shopify' } },
    sender: { login: 'attacker' }
  }.to_json

  assert_difference -> { Shipit::ReviewStack.count }, 1 do
    post :create, body: payload, as: :json
  end
  assert_response :ok  # NOT :unprocessable_entity, despite invalid/absent signature
end
```
This demonstrates: left side of the binding (`verified == (signature cryptographically matches a real GitHub secret)`) is `false`, right side (`verified` as returned by `verify_webhook_signature`) is `true`, and the divergence lets an unauthenticated POST create a `Shipit::ReviewStack`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
