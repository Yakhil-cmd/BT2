### Title
Redirect scheme-downgrade (and implicit-port) bypass in `AddAuthTokenHeader`'s hostname check leaks auth token over cleartext HTTP - (File: api/http_client.go)

### Summary
`AddAuthTokenHeader` decides whether to attach the `Authorization` header to a redirected request by comparing `getHost(req)` (the original request) with `getHost(req.Response.Request)` (the request that produced the redirect). `getHost` only returns `req.URL.Host` (hostname[:port]) and never inspects `req.URL.Scheme`, so a redirect from `https://host/...` to `http://host/...` (same hostname, no explicit port) compares equal and the token is still attached, causing the credential to be sent over an unencrypted or attacker-controlled-port connection.

`getHost` never reads `r.URL.Scheme`. Go's `net/url.URL.Host` field contains only `hostname[:port]`, and when the port is the scheme's default (443 for https, 80 for http) it is typically omitted from the `Location` header value and thus from `URL.Host`. Consequently a same-hostname redirect that switches `https://api.example.com/...` to `http://api.example.com/...` produces `getHost(req) == getHost(req.Response.Request)` (`"api.example.com"` on both sides), so `redirectHostnameChange` is `false` and the `Authorization: token ...` header is re-attached by `rt.RoundTrip(req)` on the downgraded, cleartext (or attacker-chosen alternate port) connection. Go's `net/http` redirect machinery preserves headers already set on the request object across the redirect for same-host cases and here the wrapper explicitly re-adds the header on the new request each time `RoundTrip` fires, so the check is the only gate — and it is scheme-blind.

This is reachable whenever `gh` talks to a host under attacker influence (e.g. a GitHub Enterprise Server instance the victim configured, or any host `gh api` is pointed at via `--hostname`/`GH_HOST`, or a URL embedded in repository content that `gh api` is instructed to hit), where the attacker-controlled server issues a 3xx response with a `Location` header switching scheme but keeping the same hostname. The existing guard only protects against a *hostname* change; it provides no protection against a *transport/scheme* downgrade on the same hostname, nor against implicit-port changes that don't alter the `Host` string.

Regarding the other sub-claims: IDN-homograph hosts would generally produce a different literal ASCII (punycode) string in `URL.Host`, so `getHost` would already detect a difference in that case (the check errs safe, not vulnerable, for pure hostname-mismatch cases including IDN spoofing) — this part of the question does not identify a real bypass. The concrete, reachable weakness is the scheme/port blindness.

### Impact Explanation
An attacker who controls (or influences responses from) a host that `gh` is configured/instructed to send authenticated requests to can force the CLI's OAuth/PAT token to be transmitted over plaintext HTTP (or to a different port under attacker control) by issuing a same-host, scheme-changing redirect. This is a credential/token disclosure vector — matching GitHub's "leaked credentials/secrets" bounty impact class — since the bearer token becomes interceptable in transit (or is delivered to a service on a port the attacker fully controls if the "same host" resolves differently per-port in the attacker's infrastructure, e.g., self-hosted GHES with attacker-controlled reverse proxy on port 80).

### Likelihood Explanation
Requires the victim to run `gh api` (or another gh command using the authenticated HTTP client) against a host where the attacker controls response headers — realistic for self-hosted/GHES targets, custom `GH_HOST` configurations, or any attacker-operated endpoint the victim is induced to query with an authenticated `gh` client. The attack requires only issuing a normal HTTP 3xx with a `Location` header changing `https`→`http` on the same hostname; no MITM or elevated privileges are needed, and Go's default `http.Client` follows such redirects automatically. Likelihood is moderate — it depends on the victim pointing an authenticated `gh` client at attacker-influenced infrastructure, which is a supported and common scenario for GHES/custom-host users.

### Recommendation
Extend the redirect check to include scheme, not just host:
```go
redirectHostnameChange = getHost(req) != getHost(req.Response.Request) ||
    req.URL.Scheme != req.Response.Request.URL.Scheme
```
Additionally, prefer comparing normalized `req.URL.Hostname()`/`Port()` (with scheme-derived default ports resolved) rather than raw `URL.Host` strings, and consider outright refusing to forward the Authorization header on any protocol downgrade (https→http) regardless of hostname equality.

### Proof of Concept
```go
func TestAddAuthTokenHeader_SchemeDowngradeLeaksToken(t *testing.T) {
    var sawAuthOnHTTP bool
    mux := http.NewServeMux()
    mux.HandleFunc("/secure", func(w http.ResponseWriter, r *http.Request) {
        // Redirect to same-host but http:// (implicit default port, no port in Location)
        w.Header().Set("Location", "http://"+r.Host+"/insecure")
        w.WriteHeader(http.StatusFound)
    })
    mux.HandleFunc("/insecure", func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("Authorization") != "" {
            sawAuthOnHTTP = true
        }
    })
    ts := httptest.NewServer(mux) // http test server acting as both hosts (same Host header)

    cfg := &fakeTokenGetter{token: "SECRET_TOKEN"}
    client := &http.Client{Transport: AddAuthTokenHeader(http.DefaultTransport, cfg)}

    req, _ := http.NewRequest("GET", ts.URL+"/secure", nil)
    // Force scheme to https on the initial URL while keeping the same Host string,
    // simulating a https-origin request that gets redirected to plain http on the same hostname.
    client.Do(req)

    require.True(t, sawAuthOnHTTP, "Authorization header should NOT be sent after a scheme downgrade, but it was")
}
```
Expected (buggy) behavior: `sawAuthOnHTTP` is `true`, proving the token was forwarded to the `http://` (downgraded) redirect target because `getHost` treated the two requests as same-host. After applying the recommended fix (adding scheme comparison), the assertion should be inverted to confirm the header is stripped.

func AddAuthTokenHeader(rt http.RoundTripper, cfg tokenGetter) http.RoundTripper {
	return &funcTripper{roundTrip: func(req *http.Request) (*http.Response, error) {
		// If the header is already set in the request, don't overwrite it.
		if req.Header.Get(authorization) == "" {
			var redirectHostnameChange bool
			if req.Response != nil && req.Response.Request != nil {
				redirectHostnameChange = getHost(req) != getHost(req.Response.Request)
			}
			// Only set header if an initial request or redirect request to the same host as the initial request.
			// If the host has changed during a redirect do not add the authentication token header.
			if !redirectHostnameChange {
				hostname := ghauth.NormalizeHostname(getHost(req))
				if token, _ := cfg.ActiveToken(hostname); token != "" {
					req.Header.Set(authorization, fmt.Sprintf("token %s", token))
				}
			}
		}
		return rt.RoundTrip(req)
	}}
}
