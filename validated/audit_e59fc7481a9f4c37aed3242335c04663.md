## Analysis

This confirms the binding break. `WebhooksController#verify_signature` selects the GitHub App / HMAC secret to verify against using `repository_owner`, taken from the *same untrusted payload* being verified (`params.dig('repository', 'owner', 'login')` or `organization.login`) [1](#0-0) [2](#0-1) . `Shipit.github(organization:)` looks up per-organization webhook secrets via `github_app_config` [3](#0-2) . Once signature verification passes, the actual write target is resolved independently by each `Handler` using `payload.dig('repository', 'full_name')` [4](#0-3) , e.g. `PushHandler#process` (`stack.sync_github`) [5](#0-4) , `StatusHandler#process` (creates a `Status` on any `Commit` matching the sha) [6](#0-5) , and `PullRequest::OpenedHandler` (creates/updates review stacks) [7](#0-6) . Nothing ties `repository.owner.login` (used for signature-org lookup) to `repository.full_name` (used to resolve the target repository/stack) — they are independent fields inside the same attacker-controlled JSON body.

### Title
Webhook signature verification authenticates the organization but any Handler acts on an attacker-chosen `repository.full_name`, allowing cross-organization writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` binds HMAC validation to an organization identity extracted from the payload itself (`repository.owner.login` / `organization.login`), then every `Webhooks::Handlers::Handler` resolves the actual `Repository`/`Stack` to mutate from a *different* payload field, `repository.full_name`, with no cross-check that the two agree. An entity holding a valid webhook secret for *any* organization configured on the Shipit instance can forge a webhook whose `owner.login` matches their own org (so the signature passes) while `repository.full_name` names a stack belonging to a completely different organization tracked by the same Shipit instance, causing Shipit to write state (sync commits, forge commit statuses, open/close review stacks, archive/unarchive stacks) against a repository the attacker does not control.

### Finding Description
`verify_signature` computes `repository_owner` from the untrusted JSON body and uses it to pick the `GitHubApp`/secret used to check `X-Hub-Signature` [8](#0-7) . This only proves "the sender knows the webhook secret configured for organization X" — it says nothing about which repository the payload subsequently claims to describe. Every handler independently derives the repository to act on from `payload.dig('repository','full_name')` [9](#0-8) , and that string is never checked to belong to the organization that produced a valid signature. Multi-organization Shipit deployments are an explicitly supported configuration, each org with its own `webhook_secret` [10](#0-9) . This is the direct analog of the report's binding break: the report shows a safeguard checked one property (NFT ownership before/after) while the actually exploitable action (approval left over from the cancelled step) was a different, uncovered property. Here the safeguard checks one field (`owner.login`) while the actually consumed, exploitable field (`full_name`) is a different, uncovered part of the same payload — "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who legitimately controls a GitHub App installation for org A (and thus knows org A's webhook secret) can forge signed webhooks that write into any stack belonging to org B on the same Shipit instance:
- `StatusHandler` lets them create arbitrary commit statuses on org B's commits [6](#0-5) , which feed into deploy safety/status checks used to gate whether a commit is deployable — a path to an unauthorized deploy.
- `PushHandler` triggers `stack.sync_github` for org B's stack on demand [5](#0-4) .
- `PullRequest::OpenedHandler`/label handlers can create, archive, or unarchive org B's review stacks [11](#0-10) .

This is a cross-repository/cross-organization write performed by an entity that never authenticated for the target org, matching the Critical "cross-repository writes" / "unauthorized deploy" criteria.

### Likelihood Explanation
Requires the attacker to operate a legitimate GitHub App/webhook configuration for at least one organization tracked by the shared Shipit instance (i.e., knowledge of that org's own `webhook_secret`, which they legitimately possess since it's their own integration) and to know/guess another tracked org's `owner/repo` full name (visible in the Shipit UI, which is not access-restricted to org members). No other credentials, GitHub App private key, or session are needed. This is realistic for any Shipit deployment shared across multiple organizations/teams — a scenario the app explicitly supports.

### Recommendation
In `WebhooksController#verify_signature` (or immediately in `Handler#initialize`), assert that `repository.full_name`'s owner segment matches the `repository_owner`/`organization.login` used to select and validate the signing secret, rejecting the webhook (422) if they diverge. Alternatively, resolve the target `Repository`/`Stack` first, derive its configured organization, and use that organization's secret to verify the signature rather than trusting a value pulled from the same unverified payload.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `github.webhook_secret` (as documented) [10](#0-9) .
2. Attacker legitimately administers the GitHub App installed for `org-a` and thus knows `org-a`'s webhook secret.
3. Attacker crafts a `status` webhook body: `{"repository": {"owner": {"login": "org-a"}, "full_name": "org-b/private-repo"}, "sha": "<victim-commit-sha>", "state": "success", ...}`.
4. Attacker signs the raw body with `org-a`'s webhook secret and sends `X-Hub-Signature: sha1=<hmac>` plus `X-Github-Event: status` to `/webhooks`.
5. `verify_signature` computes `repository_owner == "org-a"`, fetches `Shipit.github(organization: "org-a")`, and the signature verifies successfully [1](#0-0) .
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — a commit that belongs to `org-b/private-repo` — and creates a forged "success" status on it [6](#0-5) , even though the attacker never authenticated as, or was authorized by, `org-b`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

        request.raw_post
      )
      head(422) unless verified
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
