## Finding [1](#0-0) [2](#0-1) 

### Title
CCMenu API token's stack authorization is checked at issuance but not enforced at use, allowing cross-stack reads - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds an `ApiClient`'s data access to the specific stack it was scoped to via the `stacks` helper, but `Shipit::Api::CCMenuController` bypasses that helper and resolves the target stack directly from the URL parameter, breaking the binding between "the stack a token authorizes" and "the stack the request actually touches."

### Finding Description
Every other API controller resolves the target stack through `BaseController#stack`, which is deliberately scoped to the calling `ApiClient`'s authorized stack: [3](#0-2) 

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This ensures that a client whose `ApiClient#stack_id` is set (i.e., a token deliberately scoped to a single stack) can only ever resolve that one stack, no matter what `stack_id` the caller supplies in the request.

`CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` scope, discarding the client-scoping guard entirely: [4](#0-3) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
```

The only authorization gate on this controller is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!` — a check on the *permission name* (`read:stack`) only, never on which stack the token is entitled to: [5](#0-4) 

Tokens for this feature are minted by any authenticated (team-member) user for one specific stack of their choosing, via `CCMenuUrlController`: [6](#0-5) 

```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
```

This produces an `ApiClient` with `stack_id: nil` (not scoped) since `CCMenuUrlController` never sets `stack` on creation — meaning every CCMenu token issued this way is implicitly a global `read:stack` token, and even if it were scoped, `CCMenuController#stack` would ignore that scoping anyway.

**Binding broken**: "the stack a token authorizes" (`ApiClient#stack_id`, enforced by `BaseController#stacks`) ≠ "the stack the token actually touches" (`Stack.from_param!(params[:stack_id])` in `CCMenuController#stack`). A caller in possession of any valid CCMenu token — obtained legitimately for one project they can see — can pass an arbitrary `stack_id` and read CI/deploy state for stacks they have no authorization to view.

### Impact Explanation
`CCMenuController#show` renders `stack.deploys_and_rollbacks.last`, exposing deploy status, timing, and identifying info (via the XML CCTray feed) for any stack in the installation: [7](#0-6) 

This is an unauthorized read of stack state/deploy output across stack/repository boundaries by a caller who was only ever authorized (by design of the self-service `/ccmenu_url` feature) to see one stack — matching the High-impact category "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any authenticated Shipit user (team member) can self-service mint a CCMenu token for a stack they can already see via the existing `ccmenu_url` UI action, then simply substitute a different `stack_id` in the resulting request — no privileged token theft, no repository write access, and no session hijacking is required beyond normal use of a documented, self-service feature.

### Recommendation
Change `CCMenuController#stack` to resolve through the scoped `stacks` helper (as `BaseController` does), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, and/or have `CCMenuUrlController` mint tokens with `stack:` explicitly set so scoping has an actual stack to bind to.

### Proof of Concept
1. As any team member, visit `GET /stacks/:my_stack_id/ccmenu_url` to obtain a `ccmenu_url` containing a valid `token` query parameter (per `CCMenuUrlController#fetch`).
2. Send `GET /api/stacks/:other_stack_id/cctray.xml?token=<token>` substituting any other stack's id/param — `CCMenuController#authenticate_api_client` authenticates the token, `require_permission :read, :stack` passes (permission name matches), and `#stack` resolves `other_stack_id` directly via `Stack.from_param!`, bypassing the `stacks` scoping guard.
3. The response renders `other_stack`'s latest deploy/rollback status, disclosing deploy state for a stack the token was never scoped to.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      end
    end
