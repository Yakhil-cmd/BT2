### Title
Cross-tenant status write via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target of a `status` webhook purely by matching `sha` against every `Shipit::Commit` row in the database, with no check that the event's `repository`/organization matches the `Stack`/`Repository` that owns the matched commit. Combined with the fact that GitHub webhook signatures are verified per-organization (not per-repository) via `Shipit.github(organization: repository_owner)`, any commit SHA that legitimately exists in more than one tracked `Stack` — including one whose `review_stacks_enabled`/`allow_all` config auto-provisions and runs `shipit.yml` — can have its CI state mutated by a webhook that only "authenticated" a different repository.

### Finding Description
The broken binding: the invariant "a `github-actions` status affects only the repository that authenticated it" should mean `status.repository == commit.stack.repository`, but the code enforces only `status.sha == commit.sha`.

Trace:
- `Shipit::WebhooksController#create` parses the raw JSON body and dispatches to handlers for the `X-Github-Event`; the only gate is `verify_signature` [1](#0-0) .
- `verify_signature` looks up the GitHub App/secret to check the HMAC against using `repository_owner`, itself read straight out of the untrusted parsed payload (`params.dig('repository','owner','login')`), and only rejects if the HMAC fails for that org's configured `webhook_secret` [2](#0-1) [3](#0-2) . Crucially, this check is keyed by *organization*, not by *repository* — every repository under the same GitHub App/organization shares the same `webhook_secret` [4](#0-3) [5](#0-4) .
- Once past that check, `StatusHandler#process` does: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no filter on `commit.stack_id`, `stack.repository`, or the payload's own `repository.full_name` [6](#0-5) .
- `create_status_from_github!` → `add_status`, which recomputes `status`, can flip `deployable?`/`blocked?`, emits `deployable_status`/`commit_status` hooks, and calls `stack.schedule_merges` whenever the state becomes pending/success [7](#0-6) [8](#0-7) . `deployable?` itself gates on `success?`/`blocked?` derived from `required_statuses`/`blocking_statuses` [9](#0-8) .

Any `Commit` record sharing the attacker-controlled SHA — e.g. a review stack auto-provisioned for a fork/PR that shares git history with a victim's tracked repository — has its status/deployability mutated, even though the webhook that triggered the write was only cryptographically tied to the organization that sent it, not to the specific repository/stack whose commit got mutated.

Existing guards do not close this gap: `verify_signature` authenticates the *organization*, `drop_unhandled_event` only filters by event type, and there is no `ExplicitParameters` field or model validation that ties `params.sha`'s status write back to a specific repository.

### Impact Explanation
A correctly-signed `status` webhook from one repository in an organization can flip `deployable?`/`blocked?` state, trigger `stack.schedule_merges`, and fire `deployable_status`/`commit_status` hooks for a `Commit` belonging to a *different* stack/repository that shares the SHA — this is exactly the "payload for one repository mutating another's stack/commit" Critical category. Where the affected stack has `review_stacks_enabled` `allow_all` and executes `shipit.yml` on deploy, this status flip can drive an unauthorized ship or block of that stack's task.

### Likelihood Explanation
Exploitability is gated on a real commit SHA existing in more than one `Stack`'s commit table — which is realistic for forks/mirrors of the same upstream history tracked as review stacks under the same GitHub App/organization (sharing one `webhook_secret`), but is not a generic "any two repos" attack since cross-organization forgery still requires knowing that organization's `webhook_secret`. The root cause (missing repository scoping in `StatusHandler#process`) is unconditional and code-verifiable; the practical blast radius depends on Shipit tracking multiple repositories/stacks that share commit ancestry within one organization.

### Recommendation
Scope `StatusHandler#process` (and `Commit.by_sha`/related lookups used from webhooks) to only touch commits whose `stack.repository` matches the payload's `repository.full_name`/owner, e.g. `Commit.joins(:stack).merge(Stack.for_repository(params.repository.full_name)).where(sha: params.sha)`, mirroring how `PullRequest` handlers resolve `Repository.from_github_repo_name` before touching any stack.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` (repository `org/repo-a`) and `stack_b` (repository `org/repo-b`, `review_stacks_enabled: true`, `provisioning_behavior: allow_all`, required status context `github-actions`).
2. Create `commit_a` under `stack_a` and `commit_b` under `stack_b` with the **same** `sha` value.
3. Build a `status` payload: `{ sha: <shared_sha>, state: "failure", context: "github-actions", repository: { full_name: "org/repo-a", owner: { login: "org" } } }`.
4. Assert before: `commit_b.deployable?` is `true` (or whatever baseline) and `commit_b.status.state != "failure"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).process`.
6. Assert after: `commit_b.reload.status.state == "failure"` and `commit_b.deployable? == false` — proving that a payload declaring `repository.full_name = "org/repo-a"` mutated `stack_b`'s commit/deployability despite never authenticating against `repo-b`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
