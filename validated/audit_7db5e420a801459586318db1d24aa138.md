### Title
Unsanitized delimiter injection in arbiter contract hash source allows content-boundary forgery - ([File: arbiter_contract.js])

### Summary
`arbiter_contract.getHashSrc()` builds the string that is SHA-256-hashed to produce the arbiter-contract identity hash (`objContract.hash`) by joining free-text, counterparty-controlled fields (`title`, `text`, party names) with a fixed delimiter string `exports.DELIMITER = "[|#|]"`, without ever verifying that the caller-controlled fields do not themselves contain that delimiter sequence. This is the same root-cause pattern as the reported Nodemailer CVE: a caller-controlled text field is concatenated into a security-relevant serialized value using an internal separator, without stripping/escaping occurrences of that separator inside the field, allowing the attacker to shift field boundaries in the resulting string.

### Finding Description
`getHashSrc()` computes: [1](#0-0) 

```js
const src = contract.creation_date > exports.NEW_HASH_DATE
     ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
     : ...
return src;
```
with `exports.DELIMITER = "[|#|]"` [2](#0-1) . `contract.title`, `contract.text`, and the party names are supplied directly by either counterparty when creating/offering a contract via `createAndSend()`, which stores whatever strings are handed to it and forwards them, unfiltered, to the peer device as `arbiter_contract_offer` [3](#0-2) . No validation anywhere rejects or normalizes occurrences of `[|#|]` inside `title`/`text`/party-name fields before they are hashed.

`getHash()` (`sha256(getHashSrc(contract))`) is the trust anchor used to bind a specific human-readable contract (`title`/`text`/parties/amount/asset) to a single opaque `hash` value that is later relied upon in two independent security checks:
1. On dispute intake, `wallet.js` recomputes `expectedContractHash` from the decrypted contract content received from the counterparty via `arbiter_dispute_request`, and requires it to equal the previously agreed `body.contract_hash` before trusting the dispute payload against the actual on-chain signing unit [4](#0-3) .
2. The signing/shared-address flow embeds `contract.hash` directly into the address-locking definition as an oracle data-feed key (`"CONTRACT_" + contract.hash`), so whoever the arbiter names as winner for that key controls fund release from the shared address [5](#0-4) .

Because `title`/`text` are attacker-controlled free strings with no length limit or delimiter check, and are concatenated (not length-prefixed) with a fixed, guessable delimiter, an attacker acting as one of the two contract counterparties can craft `title`/`text` values that embed the literal `[|#|]` sequence(s) so that the concatenated hash-source byte string for one (attacker-chosen, deceptively-displayed) set of contract terms is made to equal the concatenated hash-source string of a different set of terms (e.g., a different declared `amount`, `asset`, or party name) that the attacker wants accepted as authentic elsewhere in the flow. This is structurally identical to the Nodemailer bug: an internal separator character sequence is trusted as a field boundary marker while the field values that are joined by it are not required to be free of that same sequence, so attacker-supplied content can forge/shift the apparent boundary between logically distinct fields in the resulting serialized value that is subsequently hashed and relied on as an integrity anchor.

### Impact Explanation
`objContract.hash` is the sole binding between the human-displayed contract terms (title/text/amount/party) and the cryptographic value trusted by: (a) the counterparty's UI/response-signing flow (`respond()`, which signs `objContract.title` and is checked against `objContract.hash` derivation logic on the peer side), and (b) the arbiter-dispute intake logic in `wallet.js` that gates whether a purported dispute's decrypted content is accepted as matching the previously agreed-upon contract before further processing. Because the delimiter used to join fields for hashing can be smuggled inside attacker-controlled `title`/`text`, a malicious counterparty can construct a boundary-ambiguous serialization so the wallet accepts dispute/contract content whose real fields (e.g. amount/asset/party) differ from what was actually agreed and displayed, undermining the integrity guarantee `getHash()` is meant to provide for arbitration and enabling fund-affecting arbitration outcomes to be based on forged contract content.

### Likelihood Explanation
Any unprivileged, paired-device counterparty in an arbiter contract negotiation fully controls the `title` and `text` fields with no length cap or delimiter check enforced by `createAndSend()`/`store()`, so crafting boundary-colliding content requires no special privileges beyond normal use of the arbiter-contract feature between two paired devices.

### Recommendation
Reject or escape occurrences of `exports.DELIMITER` (and, separately, of `"|"` for `getContactsHash()`) inside every field that is joined into `getHashSrc()`/`getContactsHash()` before hashing — e.g. validate that `title`, `text`, `my_party_name`, `peer_party_name`, `my_contact_info`, `peer_contact_info` cannot contain the delimiter substring, or switch to a length-prefixed/JSON-canonicalized encoding (similar to `string_utils.getSourceString`, which already throws on embedded join characters) so field boundaries cannot be manipulated by field contents.

### Proof of Concept
1. As the contract offeror, call `arbiter_contract.createAndSend()` with `title`/`text` containing the literal delimiter substring `[|#|]` positioned so that `[title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset].join("[|#|]")` for these attacker-chosen fields is byte-identical to the same join for a different, victim-intended field set (e.g., different `amount`/`asset`), by absorbing the extra delimiter-bounded slots into `title`/`text`.
2. Send this crafted contract as `arbiter_contract_offer`; `getHash()` produces the same `hash` value as a legitimately-agreed different contract.
3. During dispute handling, present decrypted content (`title`/`text`/parties) whose real amount/asset/party differs from what the counterparty believes was agreed, while `expectedContractHash` computed in `wallet.js`'s `arbiter_dispute_request` handler still matches `body.contract_hash` [6](#0-5) , causing the wallet to trust forged dispute content as authentic.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}
