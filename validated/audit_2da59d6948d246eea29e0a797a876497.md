### Title
Cross-repository Status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)`, with no scoping to the repository/owner that signed the webhook, unlike other handlers (e.g. the pull-request handlers) which look stacks up by `repository.full_name`. An attacker who can produce a validly-signed webhook for a repository/org they control can set an arbitrary `sha` value belonging to a commit that already exists under a completely different, victim stack, causing a `Status` row to be written against that victim commit. This happens unconditionally and is unaffected by the victim stack's `ignore_ci` setting.

### Finding Description
Binding claimed: repository-scope of the `Status` write (i.e., "the org/repo that authenticates this webhook == the org/repo owning the commit being annotated") should hold. Trace:

- `WebhooksController#verify_signature` derives the signing org from the payload itself: `repository_owner` is `params.dig('repository','owner','login')` [1](#0-0)  and is used to select `Shipit.github(organization: repository_owner)` for signature verification [2](#0-1) . Since this field comes from attacker-controlled JSON, an attacker only needs a webhook secret valid for *some* org they administer (per the threat model, "emit webhooks from a repository they own"), and sets `repository.owner.login` to that org to pass signature verification.
- The payload's `sha` field is unconstrained relative to `repository.owner.login`: `StatusHandler#process` does not check any repository/stack scoping at all before writing:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 
- This is inconsistent with other handlers in the same directory (e.g., the `pull_request/*` handlers), which resolve the target stack via `repository.full_name`, i.e., they do bind the payload's declared repository to the affected stack. `StatusHandler` has no such binding.
- `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` creates the actual `Status` record tied to the victim commit/stack [4](#0-3) , and `add_status` also emits `Hook.emit(:commit_status, ...)`/`:deployable_status` and calls `stack.schedule_merges` based on the newly computed status [5](#0-4) .
- `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) shows `ignore_ci?` only changes whether CI state gates *deployability*; it does not gate whether `Status` rows are written [6](#0-5) . So for a victim stack with `ignore_ci: true`, the forged `Status` still lands in `statuses`/`status` (used for `stack.commits`' displayed CI state via `Status::Group.compact`) even though it can't flip `deployable?`.
- No existing guard closes this gap: `verify_signature` only proves the payload was signed by *a* known org (potentially the attacker's own), not that it matches the commit's actual owning stack; the `StatusHandler` `params do ... end` schema only requires `sha`/`state` and never validates a repository field [7](#0-6) ; `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.

Attacker request: `POST /webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with the attacker's own org's webhook secret, and JSON body `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<victim commit sha>", "state": "success", "context": "ci/attacker"}`.

### Impact Explanation
The write mutates data belonging to a stack/repository the attacker never authenticated against: a `Status` row is created on the victim's `Commit`, altering `stack.commits`' displayed CI state and firing `commit_status`/`deployable_status` hooks and `schedule_merges` for the *victim* stack. This is a cross-tenant data-integrity break — "a payload for one repository mutating another's stack/commit" — matching the Critical impact category even when `ignore_ci` neutralizes the deploy-triggering side effect, because the corrupted/misleading CI status is still visible to operators and still triggers `schedule_merges`/hook side effects on a stack the attacker does not own. It is repeatable against any commit sha the attacker can learn (trivial for public repositories) and any stack in the installation.

### Likelihood Explanation
Preconditions: the attacker needs a webhook secret valid for at least one org/repo registered on the Shipit instance that they administer (consistent with the stated threat model of "emit webhooks from a repository they own"), and knowledge of a target commit's sha (public for open-source victim repos, or discoverable). No Shipit session, API token, or victim-org secret is required. This is a single unauthenticated-relative-to-victim HTTP POST, fully repeatable and scriptable against arbitrary victim stacks/shas.

### Recommendation
In `StatusHandler#process` (and `refresh_statuses!`/related check-run handler if similarly unscoped), constrain the `Commit` lookup by the repository declared/authenticated in the webhook, e.g. join through `stack.repository` matching `params.repository.full_name`/`owner`, mirroring the scoping already done in the `pull_request/*` handlers, instead of a bare global `Commit.where(sha:)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, conceptually):
1. Seed `stack_a` (owner org `attacker-org`, `ignore_ci: false`) and `stack_b` (victim, `ignore_ci: true`), each with a `Commit` — give `commit_b` under `stack_b` a known sha `SHA`.
2. Build a status webhook payload: `{ sha: SHA, state: 'success', context: 'ci/forged' }`, simulating it arrived with `repository.owner.login == 'attacker-org'` (valid signature for `stack_a`'s org).
3. Call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).call` (or `.process`).
4. Assert: `commit_b.reload.statuses.count == 1` and `commit_b.status.context == 'ci/forged'` — i.e., the binding "Status write scope == authenticated repository scope" is violated: LHS = attacker's authenticated org (`attacker-org`), RHS = `stack_b`'s owner (victim org); they differ yet the write succeeded.
5. Additionally assert `stack_b.ignore_ci?` is `true` and `commit_b.deployable?` is unaffected/unchanged by the forged status (proving ignore_ci doesn't stop the write, only masks deploy impact), while `commit_b.status.state` (displayed CI state) is now the attacker-forged value.

      already_deployed = deployed?

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state

      end

    end
