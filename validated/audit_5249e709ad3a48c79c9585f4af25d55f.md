### Title
Stack-scoped `ApiClient` token authorises one stack but `CCMenuController` discloses the state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The analog of the "field acted on but never covered by the enforced check" bug class from the Tigris report is a scope binding break in Shipit's CCMenu API: a `token` that is supposed to authorise access to exactly one `stack_id` is checked for the `read:stack` *permission*, but the `stack_id` it is *bound to* is never enforced when resolving which stack's data to render.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting stack lookup: [1](#0-0) 
`stacks` restricts the resolvable set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id` set (i.e. it is a stack-scoped token, as opposed to an org-wide token), and `stack` looks the requested `params[:stack_id]` up only within that restricted relation.

`Shipit::Api::CCMenuController`, however, overrides `stack` with an unscoped lookup: [2](#0-1) 
`stack` is redefined as `Stack.from_param!(params[:stack_id])`, resolving against **all** stacks in the installation regardless of `current_api_client.stack_id`. The `require_permission :read, :stack` before-action only calls `current_api_client.check_permissions!('read', 'stack')`, i.e. it checks that the token *has* the `read:stack` permission string in its `permissions` array — it never checks `current_api_client.stack_id` against the `stack_id` param: [3](#0-2) 

The equality that should hold and is broken:
`current_api_client.stack_id == stack.id` (the stack the token is scoped to) is enforced by `BaseController#stack`, but `CCMenuController#stack` instead evaluates `Stack.find(params[:stack_id])`, i.e. the binding degrades to `true == true` for any stack, because the check is skipped entirely for this controller. This is architecturally the same class of bug as the Tigris finding: a piece of state (the `stack_id` scoping) that governs what the "signed"/authorised operation is allowed to touch is silently dropped in one specific code path while the higher-level permission gate (`require_permission`) gives a false sense of protection, exactly as the unchecked-decimal assumption gave a false sense of correctness in `_handleDeposit`/`_handleWithdraw`.

Authentication for this endpoint also accepts the token purely via a `?token=` query-string parameter (`ApiClient.authenticate(params[:token])`), which is the normal, intended flow for the CCMenu XML feed (designed for polling by external tools like CCTray), so no privileged session or additional secret is required beyond possessing one legitimately-issued, stack-scoped `ApiClient` token.

### Impact Explanation
An attacker who legitimately holds (or is issued) a token scoped to a *single* stack (e.g. a low-trust integration such as a CI status widget authorised only for their own team's stack) can supply any other stack's `stack_id` in the URL and receive that stack's build/deploy status: `lastBuildStatus`, `lastBuildLabel` (deploy id), `lastBuildTime`, `activity`, and lock state, as rendered by the `ccmenu/project` view for arbitrary stacks across the whole Shipit installation. This is an unauthenticated-for-that-resource read of stack/deploy state that the token was never supposed to be able to see, matching the "High - unauthenticated read of stack state / deploy output" impact bucket, because the confidentiality boundary defined by `ApiClient#stack_id` is bypassed for every stack in the instance.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped `ApiClient` tokens (a documented, intended feature — see `here_come_the_walrus` fixture with `stack: shipit`) to lower-trust integrations. No privilege escalation, session, or GitHub credentials are required beyond the scoped token itself; the request is a single unauthenticated GET with the token in the query string, and the target `stack_id` is a low-entropy, often guessable/enumerable path segment (organization/repo/environment name).

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so that stack-scoped tokens can only ever resolve the one stack they were issued for, consistent with every other API controller in the engine.

### Proof of Concept
1. As an admin, create two stacks, e.g. `org/app-a` (`stack_id` = 10) and `org/app-b` (`stack_id` = 20).
2. Issue a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack: app-a` (`stack_id` = 10). Obtain its `authentication_token`.
3. As the holder of this token (no other credentials), request:
   `GET /api/stacks/org/app-b/production/cc_menu.xml?token=<app-a-scoped-token>`
   (matching the pattern exercised in [4](#0-3)  but with a `stack_id` that does not match the token's `stack_id`).
4. Observe HTTP 200 and the XML build status for `app-b` is returned, even though the token's `stack_id` is 10 (`app-a`), demonstrating the scope-binding break: `current_api_client.stack_id (10) != stack.id (20)` yet access is still granted.
