### Title
Session fixation in GitHub OAuth callback — no session ID rotation on login ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
`GithubAuthenticationController#callback` binds a `User` to the current session by writing `session[:user_id]` after a successful GitHub OAuth handshake, but it never rotates/regenerates the session identifier before doing so [1](#0-0) . This mirrors the report's bug class: a trust binding is established (an identity is verified) but a related piece of state that should be re-anchored to that verification (the session id) is left untouched, so state set before the "L1 burn"/verification (here: the pre-auth session cookie) is blindly carried into the post-verification, privileged state.

### Finding Description
The equality that should hold after authentication is:
`session_id_after_login == a session_id newly minted for the verified GitHub identity`

Instead the code preserves the pre-login session id and merely overwrites its `user_id` value:
```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']
  return render('failed', layout: false) if auth.blank?
  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
``` [1](#0-0) 

By contrast, `logout` explicitly calls `reset_session`, showing the engine is aware that session ids need to be invalidated at trust-boundary transitions, but this discipline was not applied to login: [2](#0-1) 

Every other controller in the engine trusts `session[:user_id]` alone to resolve `current_user`, with no secondary binding (no per-login token, no IP/device check):
```ruby
def find_current_user
  session[:user_id].present? && User.find_by(id: session[:user_id])
end
``` [3](#0-2) 

If an attacker can get a known session id planted in a victim's browser before the victim completes the GitHub OAuth flow (e.g. via a session cookie set over an unauthenticated response, a shared subdomain, or a proxy/cache issue that lets the attacker set the `_session_id` cookie), the attacker's session id becomes populated with the victim's `user_id` once the victim finishes login — because the id itself is never rotated, only the payload inside it changes.

### Impact Explanation
This is a session-fixation vulnerability: an attacker who can seed a session id can subsequently use that same id, post-victim-login, to act as the authenticated victim across the whole engine (viewing stack state, deploy logs, triggering deploys/rollbacks/merges via the UI depending on `current_user`'s GitHub team authorization) [4](#0-3) . The rules explicitly list "session fixation / forced OAuth completion" as a valid High-severity analog for this engine.

### Likelihood Explanation
Exploitability depends on the attacker's ability to fix a session id in the victim's browser, which is environment/deployment-dependent (e.g. cookie scoping, subdomain takeover, or non-`HttpOnly`/insecure cookie handling upstream of Rails). The engine's own code does nothing to mitigate this at the point of authentication — it neither calls `reset_session` nor `session.id.reset` in `callback`, unlike `logout`, so the underlying flaw is concretely present and reachable by any user going through the standard, unprivileged OAuth login flow (`GET/POST /github/auth/github/callback`), requiring no pre-existing Shipit credentials [5](#0-4) .

### Recommendation
Call `reset_session` (or otherwise rotate the session id) in `GithubAuthenticationController#callback` immediately before or after setting `session[:user_id]`, mirroring the pattern already used in `logout`, so that no pre-authentication session id can carry over into an authenticated session.

### Proof of Concept
1. Attacker obtains/sets a session cookie value `S` in the victim's browser for the Shipit host (mechanism depends on deployment, e.g. cookie injection via a sibling subdomain or a response that lets the attacker set cookies for the apex domain).
2. Attacker lures the victim to visit the Shipit instance and complete GitHub OAuth login (`/github/auth/github` → GitHub → `/github/auth/github/callback`).
3. `callback` sets `session[:user_id] = <victim.id>` on the existing session identified by `S`, without rotating `S` [6](#0-5) .
4. Attacker now presents cookie `S` to the Shipit instance; `find_current_user` resolves it to the victim's `User` record [3](#0-2) , giving the attacker the victim's authenticated session and all UI-level privileges tied to that account.
