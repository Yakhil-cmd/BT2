### Title
CCMenu API token stack-scope bypass allows unauthenticated read of any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` re-implements stack resolution instead of reusing the scoped helper from `Shipit::Api::BaseController`. This causes a stack-scoped `ApiClient` token to be able to read the deploy/build status of any stack in the installation, not just the one it was authorized for, breaking the binding "stack a token authorises == stack it touches."

### Finding Description
`Shipit::Api::BaseController` scopes stack access to the token's authorization: an `ApiClient` may be bound to a single `stack_id`, and normal controllers resolve the requested stack only from that scoped relation: [1](#0-0) 

`CCMenuController`, however, authenticates via a bare query-string `token` param (no Basic Auth / session needed) and overrides `stack` to bypass the `stacks` scoping entirely, resolving the target stack from the global `Stack` relation: [2](#0-1) 

The controller only requires the generic `read:stack` permission, which `ApiClient#check_permissions!` checks against the client's `permissions` array — it never checks whether the specific stack in the request matches the client's `stack_id`: [3](#0-2) 

So, before vs after: for a stack-scoped `ApiClient` (`stack_id` set, permission `read:stack`), the intended equality is `authorized_stack_id == requested_stack_id`. Through `BaseController#stack`, that equality is enforced via `stacks.from_param!`. Through `CCMenuController#stack`, it is not enforced at all — `Stack.from_param!(params[:stack_id])` accepts any stack id regardless of the token's `stack_id`.

### Impact Explanation
An attacker who obtains a leaked CCMenu token (these tokens are designed to be embedded in plain URLs for third-party CI dashboards such as CruiseControl.rb monitors — see `CCMenuUrlController`, which mints them and returns them as a URL — and are thus exposed to logs, browser history, Referer headers, or shared dashboards) can use that single token to query the `#show` action for arbitrary `stack_id` values, obtaining the latest deploy/rollback status (`running?`, `ended_at`, etc.) of every stack in the Shipit instance, not just the one it was minted for. This is an unauthenticated (no session, no privileged account) read of stack/deploy state across stacks the token was never authorized to see, matching the High-impact category of "escalation into `Shipit.github_teams` authorization[-adjacent] scope / unauthenticated read of stack state."

### Likelihood Explanation
Any holder of one legitimate, narrowly-scoped CCMenu/API token — a credential explicitly designed for low-trust exposure in URLs — can immediately enumerate other stacks by varying `stack_id` in the request path; no additional secrets, sessions, or privileged access are required.

### Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) exactly like `BaseController#stack`, so a stack-scoped token can only ever resolve the stack it was actually authorized for.

### Proof of Concept
1. Provision (or leak) a stack-scoped API token, e.g. via `CCMenuUrlController#fetch`, which returns a URL like `.../ccmenu.xml?token=<TOKEN>` for `stack_id=A`: [4](#0-3) 
2. Send `GET /api/stacks/:other_stack_id/ccmenu.xml?token=<TOKEN>` where `other_stack_id` is any other stack the token was never scoped to.
3. `authenticate_api_client` accepts the token via `ApiClient.authenticate(params[:token])`; `require_permission :read, :stack` passes because the token has generic `read:stack` permission; `stack` resolves `other_stack_id` via unscoped `Stack.from_param!`, returning that stack's deploy status in the XML response — despite the token's `stack_id` pointing to stack A only.
