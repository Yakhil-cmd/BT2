### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but the event is processed against the (unrelated) repository named in `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository','owner','login')` (falling back to `organization.login`), but every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*` handlers, etc.) resolves the target `Repository`/`Stack` from a completely different field, `payload.dig('repository','full_name')`, via `Handler#repository_name` / `Repository.from_github_repo_name`. Nothing binds these two fields together, so the field that authorizes ("which org's secret proves this request is legitimate") is not the field that is acted on ("which repository's stack gets mutated").

### Finding Description
`Shipit` supports configuring multiple GitHub Apps/organizations, each with its own `webhook_secret` (see `test/dummy/config/secrets_double_github_app.yml`, `lib/shipit.rb#Shipit.github(organization:)`). The webhook entrypoint picks the secret to verify against like this: [1](#0-0) [2](#0-1) 

So `verify_signature` authenticates the payload as "came from organization X" purely based on the attacker-controlled JSON field `repository.owner.login` (or `organization.login`), matched against whichever org secret produces a valid HMAC over the raw body.

Once verification passes, the actual event handlers never re-check that the acted-upon repository belongs to the same organization that was authenticated. They independently derive the target repository from `repository.full_name`: [3](#0-2) 

For example, `PushHandler` uses this to find stacks and trigger a sync: [4](#0-3) 

Because `repository.owner.login` (used for signature-secret selection) and `repository.full_name` (used for locating the Stack to mutate) are two independent, attacker-controlled fields inside the same signed body, an attacker who legitimately controls the webhook secret for Organization A (e.g., they are the admin of a GitHub org/App installation that this Shipit instance also serves, per the documented multi-org configuration) can:
1. Build a webhook body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`.
2. Sign the raw body with OrgA's `webhook_secret`, which the attacker legitimately knows.
3. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and successfully verifies the signature.
4. `PushHandler` (or `StatusHandler`/`CheckSuiteHandler`) then resolves the target stack via `repository.full_name = "OrgB/victim-repo"` and performs `stack.sync_github(expected_head_sha: params.after)`, acting on a stack/repository that belongs to Organization B, which the attacker has no authorization over.

This is a direct instance of "an organization that authenticated versus the repository that is written" diverging - the equality `organization_that_signed == organization_owning_repository_acted_on` is never enforced.

### Impact Explanation
This breaks the deployment-trust binding between the authenticating organization and the repository whose Stack state gets mutated. Depending on the handler reached, an attacker who only controls one tenant/org's webhook secret can trigger `GithubSyncJob`/`sync_github` for a Stack under a completely different, unauthorized organization, or otherwise inject processing (team/user creation via `MembershipHandler`, pull request/review-stack state changes, check-run refreshes) scoped by `repository.full_name` on a repository they don't own. Depending on what `sync_github` ultimately does (fetch/compare against real GitHub state, mark commits, kick off deploy pipeline steps), this can range from spurious task/job triggering to influencing which commit/ref Shipit treats as the stack's expected head, i.e. an unauthorized/incorrect deploy trigger on another org's repository - meeting the "unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the multi-organization GitHub App configuration (explicitly documented and supported: `docs/setup.md`, `secrets_double_github_app.yml`) and requires the attacker to control at least one organization/app installation configured on the same Shipit instance (i.e., know that org's `webhook_secret`) while targeting a Stack belonging to a different, co-hosted organization. This is a realistic scenario for shared/multi-tenant Shipit deployments serving several orgs, but not exploitable against a single-organization deployment (there, `repository_owner` always resolves to the one configured org, so the mismatch degenerates to a no-op).

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the organization used to select/verify the webhook secret matches the owner of the repository actually being acted upon — e.g., derive/compare `repository.full_name.split('/').first` against `repository_owner` and reject (422) on mismatch, or have `Handler#stacks`/`#repository_name` be scoped by the authenticated organization rather than trusting `repository.full_name` in isolation.

### Proof of Concept
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },       // used by verify_signature to pick OrgA's secret
    "full_name": "OrgB/victim-repo"     // used by PushHandler to resolve the Stack acted on
  }
}
```
Because the attacker controls `OrgA_webhook_secret`, the signature check in `WebhooksController#verify_signature` succeeds; `PushHandler#process` then finds and mutates the Stack for `OrgB/victim-repo`, an organization the attacker does not control.
