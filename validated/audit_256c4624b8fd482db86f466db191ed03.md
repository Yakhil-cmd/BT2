### Title
Hookify `block` action rules silently downgrade to warnings due to inline-comment/whitespace mishandling in frontmatter parser - (File: plugins/hookify/core/config_loader.py)

### Summary
`config_loader.extract_frontmatter` parses YAML-like frontmatter with a naive line parser that only strips leading/trailing whitespace and matched quote characters from scalar values, never trailing inline comments. A rule file with `action: block  # required` (or any trailing text/whitespace after `block`) is parsed into the literal string `"block  # required"` instead of `"block"`. `rule_engine.RuleEngine.evaluate_rules` then performs an exact string comparison `rule.action == 'block'`, which fails, causing the rule to be treated as a non-blocking `warn` rule even though the file was authored to `block`.

### Finding Description
`extract_frontmatter` in `plugins/hookify/core/config_loader.py` splits each top-level `key: value` line and does:
```
value = value.strip()
...
value = value.strip('"').strip("'")
``` [1](#0-0) 
This only removes surrounding whitespace/quotes — it does not strip trailing inline `#` comments or normalize interior whitespace. Comment handling is only applied to lines that are entirely comments (`stripped.startswith('#')`), not inline trailing comments on a key/value line. [2](#0-1) 

`Rule.from_dict` then assigns this raw, uncleaned value directly to `action`:
```
action=frontmatter.get('action', 'warn'),
``` [3](#0-2) 

`RuleEngine.evaluate_rules` (`plugins/hookify/core/rule_engine.py`) then relies on exact equality to decide whether a matched rule is enforced as blocking:
```
if rule.action == 'block':
    blocking_rules.append(rule)
else:
    warning_rules.append(rule)
``` [4](#0-3) 

If `action` is anything other than the exact literal `"block"` (e.g. `"block  # required"`, `"Block"`, `"block "`), the rule is routed to `warning_rules` instead of `blocking_rules`. For `PreToolUse`/`PostToolUse` events this means the hook returns only a `systemMessage` and never sets `hookSpecificOutput.permissionDecision: "deny"`, so the tool call that the rule author intended to hard-block is instead allowed to execute with just a warning shown. [5](#0-4) 

The rule files themselves are ordinary markdown+YAML that Claude commonly authors on the user's behalf via the `/hookify` command based on conversation analysis, and documentation/examples repeatedly show `action: block` as the way to enforce hard blocking of dangerous commands. [6](#0-5) 
Because the parser silently accepts and stores the malformed value rather than rejecting it or normalizing it, there is no error, warning, or validation step that would alert the user that their intended blocking rule is not actually enforced as blocking — the systemMessage still gets shown, giving a false sense that the guard is active.

### Impact Explanation
This is a silent hook-enforcement bypass: a `.claude/hookify.*.local.md` rule configured with `action: block` to prevent destructive operations (e.g. `rm -rf`, `chmod 777`, sensitive-file edits) can be neutralized into a mere warning by a trailing inline comment or stray whitespace, with no parse error or feedback. Any dangerous command the rule was meant to hard-block will instead execute normally (only a warning message is surfaced), directly undermining the safety guardrail the user configured for themselves and enabling unauthorized command/tool execution that the user believed was blocked.

### Likelihood Explanation
Feasibility is moderate: an attacker needs the ability to influence the content of a hookify rule file, e.g. via prompt injection embedded in repository content, issue/PR text, or an MCP tool response that causes Claude (acting on the user's behalf, e.g. during a `/hookify` invocation) to author a rule using conventional YAML style such as `action: block  # required` or with trailing whitespace copy-pasted from elsewhere. This is a common and innocuous-looking authoring pattern, not an obviously malicious one, so it is unlikely to be caught in review. Given the parser accepts and silently stores the malformed value with no validation error, the bypass is fully reproducible and deterministic once such a line is present in a rule file.

### Recommendation
In `extract_frontmatter`, strip inline comments from scalar values (e.g. split on an unquoted ` #` before trimming) and normalize/validate known enum fields such as `action` against an allow-list (`{"warn", "block"}`), raising or logging a clear parse error for any other value instead of silently defaulting/mismatching. Additionally, have `Rule.from_dict` normalize `action` (`.strip().lower()`) and validate it against the allowed set, treating any unrecognized value as a hard error (fail-closed, i.e., default to `block` behavior or refuse to load the rule) rather than fail-open to `warn`.

### Proof of Concept
Unit test targeting `config_loader.extract_frontmatter` / `Rule.from_dict` and `RuleEngine.evaluate_rules`:
```python
def test_action_with_inline_comment_is_not_downgraded():
    content = """---
name: block-rm
enabled: true
event: bash
pattern: rm\\s+-rf
action: block  # required
---

Blocked!
"""
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)
    # BUG: rule.action == "block  # required", not "block"
    assert rule.action == "block"  # fails today

    engine = RuleEngine()
    input_data = {
        "hook_event_name": "PreToolUse",
        "tool_name": "Bash",
        "tool_input": {"command": "rm -rf /tmp/x"},
    }
    result = engine.evaluate_rules([rule], input_data)
    # Expect the operation to be denied
    assert result.get("hookSpecificOutput", {}).get("permissionDecision") == "deny"  # fails today, rule is treated as warn-only
```
Expected today: both assertions fail, demonstrating that a rule authored with `action: block` and a trailing inline comment is silently treated as `warn`, allowing the matched dangerous command to execute.
