### Title
Cross-Organization Webhook Confusion Allows Forged Commit Statuses to Bypass Merge/Deploy Gating - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature verification in `WebhooksController` authenticates a payload against the GitHub organization named inside the payload's own `repository.owner.login`/`organization.login` field [1](#0-0) , but the handlers that subsequently act on the payload use a *different*, unrelated field of the same payload to decide what to write, without re-validating that it belongs to the authenticated organization. `StatusHandler` is the most severe instance: it never scopes by repository or organization at all, matching purely on commit SHA across the entire Shipit install [2](#0-1) .

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (or `organization.login`) and validates the HMAC signature using that specific organization's `webhook_secret`: [1](#0-0) [3](#0-2) 

Shipit is explicitly designed as a multi-tenant engine: `config/secrets.yml`/`docs/setup.md` show multiple organizations (`somegithuborg`, `someothergithuborg`), each with its own GitHub App, its own `webhook_secret`, and its own admins [4](#0-3) . Any admin of one onboarded org can view that org's GitHub App webhook secret in GitHub settings, and can therefore craft an arbitrarily-signed POST to the shared `/github/webhooks` endpoint.

Once the signature check passes (because it only proves the sender knows *organization A*'s secret), the actual handler dispatched by `Shipit::Webhooks.for_event(event)` is chosen from `params`, and `Handler#process` implementations read *other* attacker-controlled fields of the same JSON body to decide what data to mutate:

- The generic `Handler#stacks`/`#repository_name` look up the target `Repository` via `payload.dig('repository', 'full_name')` [5](#0-4)  — a field completely independent from the `repository.owner.login` used for signature verification.
- `StatusHandler#process` goes further and doesn't consult repository/organization scoping at all — it updates status for **any** `Commit` in the entire Shipit instance whose `sha` matches the attacker-supplied `params.sha`: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .

This breaks the binding: **organization authenticated by the signature == organization/repository whose state is written**. An admin of org A (who legitimately knows org A's `webhook_secret`) can sign a payload with `repository.owner.login = "org-a"` (or `organization.login = "org-a"`) to pass `verify_signature`, while setting `sha` to a commit SHA belonging to a stack owned by victim org B. `StatusHandler` will happily create/update a `CommitStatus` on that victim commit, e.g. injecting a fake `success` state for the `shipit` merge-status context or a required CI context that Shipit's merge queue/auto-deploy gating checks (`review.checklist`/`status.context`/`merge` behavior documented in `README.md`) [6](#0-5) , since `StatusHandler` and `Handler` provide no cross-tenant isolation.

### Impact Explanation
Forging commit statuses on a repository the attacker does not control lets them mark commits as passing required checks that gate Shipit's continuous-deployment and merge-queue safety logic. Because Shipit deploys/merges are conditioned on commit status records, an attacker able to inject fabricated "success" statuses for arbitrary commits in a repo they don't have write access to can trigger an unauthorized deploy or merge on a victim stack, satisfying the Critical bar ("an unauthorized deploy, rollback, or merge"). More broadly, any handler relying on `Handler#repository_name`/`#stacks` (built from an unverified `repository.full_name` field) is likewise cross-tenant writable once any organization's webhook secret is known to the attacker.

### Likelihood Explanation
Requires the attacker to be an administrator/owner of at least one legitimate GitHub organization already onboarded into the same multi-tenant Shipit deployment (able to view that org's own webhook secret via its GitHub App settings — not a privileged Shipit account, GITHUB_TOKEN, or ApiClient token). This is a realistic scenario for shared/managed Shipit installations serving several organizations, matching the engine's own documented multi-org configuration model.

### Recommendation
Have every webhook handler (in particular `StatusHandler`) validate that the organization/repository referenced by the event body (`repository.full_name`, or the commit's owning `Stack`/`Repository`) actually belongs to the organization whose secret produced a valid signature (`repository_owner` computed in `WebhooksController`), rejecting or ignoring events where these two identities diverge, rather than trusting independent payload fields for authorization versus for action.

### Proof of Concept
1. Attacker is an admin of org `attacker-org`, which is a legitimate tenant configured in Shipit's `github:` secrets with its own `webhook_secret` (visible to them in GitHub App settings).
2. Attacker looks up a commit SHA belonging to a `Stack` under victim org `victim-org`, tracked by the same Shipit instance (SHAs are public/discoverable via GitHub).
3. Attacker crafts a JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "shipit/pre-production"
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org webhook_secret, body)` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a status on the victim's commit [2](#0-1) , with no check that the commit belongs to `attacker-org`.

*Note:* I was not able to trace `Commit#create_status_from_github!` or the exact merge/deploy-gating consumer code within the current index (it may exceed indexing limits); confirming the precise downstream effect on merge-queue auto-merge logic may require starting a full Devin session with complete repository access.

<h2 id="script-parameters">Script parameters</h2>

Your deploy scripts have access to the following environment variables:

* `SHIPIT`: Set to `1` to allow your script to know it's executed by Shipit
* `SHIPIT_LINK`: URL to the task output, useful to broadcast it in an IRC channel
* `SHIPIT_USER`: Full name of the user that triggered the deploy/task
* `GITHUB_REPO_NAME`: Name of the GitHub repository being used for the current deploy/task.
* `GITHUB_REPO_OWNER`: The GitHub username of the repository owner for the current deploy/task.
* `EMAIL`: Email of the user that triggered the deploy/task (if available)
* `ENVIRONMENT`: The stack environment (e.g `production` / `staging`)
* `BRANCH`: The stack branch (e.g `main`)
* `LAST_DEPLOYED_SHA`: The git SHA of the last deployed commit
* `DIFF_LINK`: URL to the diff on GitHub.
* `TASK_ID`: ID of the task that is running
* All the content of the `secrets.yml` `env` key
* All the content of the `shipit.yml` `machine.environment` key

These variables are accessible only during deploys and rollback:

* `REVISION`: the git SHA of the revision that must be deployed in production
* `SHA`: alias for REVISION
