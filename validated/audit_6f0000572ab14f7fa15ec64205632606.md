### Title
Webhook signature verification keyed on `repository.owner.login` while event processing is keyed on `repository.full_name`, allowing cross-organization webhook spoofing in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's HMAC `webhook_secret` to validate a payload against using `repository.owner.login` (falling back to `organization.login`), an attacker-controlled field in the unauthenticated request body. However, every downstream `Webhooks::Handlers::Handler` (push, status, check_suite, pull_request, etc.) resolves the `Repository`/`Stack` to act on using a *different* field of the same payload: `repository.full_name`. Because these two fields are never required to agree, and because per-organization `webhook_secret` is documented as optional (frequently left blank, as shown in the repo's own `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` examples), an attacker can pick any configured organization that has no `webhook_secret` set, pass signature verification trivially, and then supply a `repository.full_name` pointing at a *different*, properly-secured organization's repository to spoof pushes, commit statuses, check-suite completions, or pull-request events for stacks the attacker has no access to.

### Finding Description
`Shipit.github(organization:)` returns a distinct `GitHubApp` instance per configured organization [1](#0-0) , and each organization can have an independently-configured (and optionally blank) `webhook_secret` [2](#0-1) . `GitHubApp#verify_webhook_signature` trivially returns `true` when `webhook_secret` is blank for that organization: [3](#0-2) 

The controller determines *which* organization's secret to check purely from attacker-supplied JSON, not from any authenticated channel: [4](#0-3) [5](#0-4) 

Once verification "passes" (because the chosen organization has no secret configured), the full unauthenticated payload is dispatched to every registered handler for the event: [6](#0-5) 

But the base `Handler` class — used by `PushHandler`, `CheckSuiteHandler`, status handlers, and all `PullRequest::*Handler` classes — resolves the target `Repository`/`Stack` using `repository.full_name`, a completely independent field from the one used to pick the verifying organization: [7](#0-6) [8](#0-7) [9](#0-8) 

This is structurally the same class of bug as the reported `ReserveLogic.sol` issue: a value used for the "authorization" computation (the organization whose secret is checked, derived from `repository.owner.login`) is never actually reconciled with the value that determines the resulting state mutation (the repository/stack acted upon, derived from `repository.full_name`). The equality the code implicitly (and incorrectly) assumes is:

`organization_used_for_signature_check == organization_owning_the_mutated_repository`

This equality is never enforced. An attacker fully controls both fields independently in the same unsigned-for-that-org JSON body, so they can set them to different organizations.

### Impact Explanation
Any Shipit instance running the documented "Using Multiple GitHub Applications" configuration (`config/secrets.yml` keyed by org) is affected if at least one configured organization has no `webhook_secret` set — a configuration explicitly present as the example/default in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`. In that state, an unauthenticated attacker can:
- Forge `push` events causing `Stack#sync_github` to run against a properly-secured organization's stacks [8](#0-7) .
- Forge `status`/`check_suite` events to inject fake CI results against another organization's commits, which can feed continuous-delivery deploy gating for those stacks.
- Forge `pull_request` events (opened/closed/labeled/reopened) to create, archive, or unarchive review stacks belonging to the other organization [10](#0-9) .

This is a cross-repository/cross-organization write achieved with zero credentials (no `webhook_secret`, no `ApiClient` token, no GitHub App key), satisfying the "cross-repository writes" / "unauthorized deploy" impact tier.

### Likelihood Explanation
Likelihood is contingent on deployment configuration: the engine must be configured for multiple GitHub organizations, and at least one of them must have a blank `webhook_secret`. This is realistic because (a) `webhook_secret` is explicitly optional per the engine's own documentation and setup templates, and (b) operators frequently leave low-priority/test orgs unconfigured while securing production orgs — exactly the pattern shown in the repo's own example config files. Once that precondition holds, exploitation requires nothing more than a single unauthenticated POST to `/webhooks` with two independently-crafted repository fields.

### Recommendation
Bind signature verification and event routing to the *same* organizational identity. Concretely: after selecting the `GitHubApp` used for signature verification (via `repository.owner.login`/`organization.login`), require that the `Repository`/`Stack` resolved from `repository.full_name` inside each `Handler` belongs to that same verified organization/owner, rejecting the event otherwise. Alternatively, remove the "verification trivially passes when `webhook_secret` is blank" behavior for multi-org configurations, or require a `webhook_secret` on every configured organization when the multi-org schema is used.

### Proof of Concept
Preconditions: multi-org `config/secrets.yml` with `OrgA` (webhook_secret set, has real Shipit stacks) and `OrgB` (webhook_secret blank/unset — the documented example configuration).

```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature needed)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha-already-known-to-exist-on-OrgA-repo>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/secured-repo"
  }
}
```

- `WebhooksController#verify_signature` computes `repository_owner = "OrgB"` [5](#0-4) , fetches `Shipit.github(organization: "OrgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [11](#0-10) .
- The request proceeds to `create`, dispatching to `PushHandler`, which resolves `repository_name = "OrgA/secured-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on `OrgA`'s stack [8](#0-7) [7](#0-6) .
- The attacker never needed `OrgA`'s `webhook_secret`, achieving an unauthorized state change (github sync/deploy trigger path) on `OrgA`'s protected stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
