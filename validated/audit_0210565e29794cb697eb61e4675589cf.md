### Title
`Api::CCMenuController` bypasses stack-scoped `ApiClient` authorization, letting a stack-scoped token read any stack's build/deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The external report's bug class is "a privileged action is gated on a check that is bound to one object, but a sibling code path performs the same action using an unchecked/different lookup, letting an actor exceed the scope it was granted." In `MembershipManager`, the constraint (`minDepositGwei`/fee) that was supposed to bound minting wasn't applied uniformly at all call sites before initialization. The Shipit analog is the binding "the stack a token authorizes == the stack it touches": `Api::BaseController` scopes stack lookups to the `ApiClient`'s assigned `stack_id` via `#stacks`/`#stack`, but `Api::CCMenuController` re-defines `#stack` to bypass that scoping entirely.

### Finding Description
`Api::BaseController` enforces the "stack an ApiClient may see" binding through: [1](#0-0) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` when the authenticated `ApiClient` is stack-scoped (`stack_id` present), otherwise falls back to `Stack.all`. `stack` then resolves `params[:stack_id]` only within that pre-scoped relation. Every other API controller (`HooksController`, `OutputsController`, `StacksController`, etc.) inherits this `stack`/`stacks` implementation unmodified, so a stack-scoped `ApiClient` (one created with a specific `stack_id`, e.g. via `Shipit::CCMenuUrlController#client`) cannot read data belonging to other stacks.

`Api::CCMenuController`, however, overrides `stack` and drops the scoping check entirely: [2](#0-1) 

It resolves `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, ignoring `current_api_client.stack_id`. The only gate left is `require_permission :read, :stack`, which checks the `ApiClient#permissions` array (`read:stack`) — not which specific stack the client is bound to: [3](#0-2) [4](#0-3) 

`ApiClient#check_permissions!` only validates the permission string is in the list; it never compares `stack_id` against the requested stack. So the equality that should hold — `token.stack_id == params[:stack_id]` for any stack-scoped token — holds everywhere except in `CCMenuController`, where it is `true == true` regardless of the actual stack requested.

Concretely: `Shipit::CCMenuUrlController#client` mints a token scoped to `read:stack` only (no `stack_id` set in that particular helper, but the `ApiClient` model supports an optional `belongs_to :stack`, and any admin-issued `ApiClient` scoped to a single stack via `stack_id` — the mechanism `BaseController#stacks` is built for — is defeated by this endpoint). Any such stack-scoped credential can be replayed against `GET /stacks/:any_stack_id/ccmenu.xml`, or against `.../ccmenu.xml?token=<token>` per `CCMenuController#authenticate_api_client`'s query-string fallback, to read the build/deploy status of any stack in the installation, not just the one it was issued for.

### Impact Explanation
This is a stack-authorization boundary break: it lets a credential that is authorized for exactly one stack read task/deploy state (`stack.deploys_and_rollbacks.last`, lock status, last build label/status) of every other stack in the Shipit instance. Per the rules, this maps to the "High" bucket: escalation past the stack a token authorizes, and unauthenticated-adjacent read of stack/deploy state via a token that should have been scoped away from that data.

### Likelihood Explanation
Likelihood is moderate: it requires possession of a legitimately-issued, stack-scoped `ApiClient` token with `read:stack` permission (no privileged admin action or GitHub write access needed beyond having been granted a narrow token for one stack — e.g., a CI system or a CCMenu integration token intended for a single project). Given such a token (which by design is meant to be shared with lower-trust automation/monitoring tools), the attacker only needs to change `stack_id` in the URL/query string to pull data on unrelated stacks.

### Recommendation
Have `Api::CCMenuController#stack` reuse the inherited, scope-aware `stack`/`stacks` methods from `Api::BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so the `current_api_client.stack_id` restriction applies uniformly across all API controllers.

### Proof of Concept
1. As an admin, issue (or have the application issue, e.g. via the CCMenu URL flow) an `ApiClient` scoped to `stack_id = A` with permission `read:stack`.
2. Using that client's `authentication_token`, call `GET /stacks/:B/ccmenu.xml?token=<token>` (or via Basic auth) where `B` is a different stack the token was never scoped to.
3. `CCMenuController#authenticate_api_client` accepts the token; `require_permission :read, :stack` passes because `read:stack` is in the client's `permissions`; `stack` resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` table, ignoring `current_api_client.stack_id`.
4. The response renders stack `B`'s name, last build status/label, and deploy id — data the token was never authorized to see, unlike identical requests to `Api::HooksController`/`Api::OutputsController`/`Api::StacksController`, which correctly 404/forbid via the inherited scoped `stack` method.
