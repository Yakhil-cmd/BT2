### Title
`GitHubApp#verify_webhook_signature` bypasses HMAC verification when `webhook_secret` is unset - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever an organization's `webhook_secret` is falsy, meaning any unauthenticated POST to `/webhooks` claiming that organization in `repository.owner.login` is accepted with no signature check at all. This lets an attacker forge push (and other) events that trigger real writes such as `Stack#sync_github`.

### Finding Description
The broken binding is: `the-organization-whose-secret-verified-this-body == the-organization-that-authorized-this-write`. For any org configured with `webhook_secret` absent/nil, this binding is never enforced because verification is skipped entirely.

Code path: `WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) is gated by `before_action :verify_signature` (line 6), which calls `Shipit.github(organization: repository_owner).verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)` [1](#0-0) . `repository_owner` is read straight out of the untrusted JSON body: `params.dig('repository', 'owner', 'login')` [2](#0-1) . Inside `verify_webhook_signature`, the very first line is `return true unless webhook_secret`, before any HMAC computation or comparison [3](#0-2) . `webhook_secret` is set from config as `@config[:webhook_secret].presence` [4](#0-3) , and the shipped example config leaves this key blank/nil for both the single-org and multi-org schemas [5](#0-4) .

If `verify_signature` sets `verified = true`, `head(422)` is never called, and control proceeds to `create`, which parses the body and dispatches to `Shipit::Webhooks.for_event(event)` handlers with no further ownership check. For a `push` event, `PushHandler#process` looks up non-archived stacks matching the `branch` in the forged payload and calls `stack.sync_github(expected_head_sha: params.after)` for each match [6](#0-5) , which is a real write/enqueue action performed with no authentication of the request's origin. No other guard (session, API token, `require_permission!`, `drop_unhandled_event`, or `ExplicitParameters` schema validation) checks that the request actually originated from GitHub — `drop_unhandled_event` only filters by event type, and the `params` schema in `Handler` subclasses only validates presence/shape of fields, not their authenticity.

### Impact Explanation
An unauthenticated attacker who knows (or guesses) the name of any organization configured in `Shipit.github` without a `webhook_secret` can forge arbitrary webhook events (`push`, `status`, `membership`, `pull_request`, etc.) for that org's repositories. This is repeatable per request and per repository/stack within that organization — any stack whose `branch` matches the attacker-controlled `ref` in the payload will have `sync_github` triggered, and other handlers (membership, pull_request, status) perform their own writes based entirely on attacker-supplied JSON. This is a full authentication bypass on the webhook endpoint for any org that has not configured a secret, matching the Critical "authentication bypass (forged webhook ... accepted)" category, with blast radius limited to organizations lacking `webhook_secret` but otherwise unauthenticated and repeatable.

### Likelihood Explanation
The only precondition is that a Shipit-configured GitHub organization has `webhook_secret` absent or nil in its config — exactly the state produced by the shipped example configuration (`config/secrets.development.example.yml`) before an operator explicitly sets a secret. The attacker needs no Shipit session, API token, or GitHub secret; they only need to send a raw HTTP POST to `/webhooks` with a JSON body naming the target organization. This is a trivial, zero-cost, fully repeatable attack against any misconfigured/unconfigured deployment.

### Recommendation
`verify_webhook_signature` should never treat an absent secret as "verified." Instead, either require `webhook_secret` to be present for the endpoint to accept any events for that org (fail closed — return `false`/reject when `webhook_secret` is blank), or refuse to boot/register an organization's webhook route unless a secret is configured. At minimum, remove the `return true unless webhook_secret` short-circuit in `lib/shipit/github_app.rb` and replace it with a fail-closed check.

### Proof of Concept
Minitest plan (illustrative, not run):
```ruby
test "push webhook with no webhook_secret configured is not authenticated and should not enqueue sync" do
  Shipit.github_config = { 'no-secret-org' => { app_id: 1, installation_id: 1, private_key: 'x', webhook_secret: nil } }
  stack = shipit_stacks(:shipit)
  stack.update!(repo_owner: 'no-secret-org', branch: 'master')

  payload = { repository: { owner: { login: 'no-secret-org' } }, ref: 'refs/heads/master', after: 'deadbeef' }.to_json

  assert_no_enqueued_jobs(only: Shipit::GithubSyncJob) do
    post shipit.webhooks_path, params: payload,
      headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => 'sha1=garbage', 'Content-Type' => 'application/json' }
  end

  assert_response :unprocessable_entity
end
```
This asserts the equality that should hold — `organization-that-signed(request) == organization-in(payload)` — by showing the current code makes the request succeed (`GithubSyncJob` enqueued, `200 OK`) instead of rejecting it, because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is nil [7](#0-6) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
