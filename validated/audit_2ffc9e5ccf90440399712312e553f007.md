### Title
Content-Type spoofing bypasses terminal escape-sequence/binary guard in `gh api` - (File: pkg/cmd/api/api.go)

### Summary
`processResponse` in `pkg/cmd/api/api.go` decides whether to apply the escape-sequence/binary-content guard (`iostreams.CopyGuardedContent`) purely based on the server-supplied `Content-Type` header. When a response is labeled `application/json` (or any `*/*+json` type) but color output is not active, the body is written to the terminal via a plain `io.Copy` with zero sanitization, letting an attacker-controlled host smuggle ANSI escape sequences or binary data straight to the victim's TTY.

### Finding Description
`processResponse` computes `isJSON` solely from the regex match against `resp.Header.Get("Content-Type")`: [1](#0-0) 
The escape-sequence/binary guard is applied only in the `!isJSON` branch: [2](#0-1) 

When `isJSON` is true and `opts.IO.ColorEnabled()` is true, the body goes through `jsoncolor.Write`, which decodes it with `encoding/json.Decoder` and re-marshals scalar values via `json.Marshal`. Since `encoding/json` escapes control bytes (e.g. `\x1B` becomes `\u001b`) and a non-JSON top-level payload fails immediately with a decode error, that path is not exploitable for raw escape injection.

However, when `isJSON` is true but `opts.IO.ColorEnabled()` is false (e.g., `NO_COLOR` set, `--color=never`/`--no-color` semantics, a terminal that isn't detected as color-capable, or any other reason color is disabled while stdout is still a TTY), execution falls into the `else` branch and does a raw, unsanitized `io.Copy(bodyWriter, responseBody)`: [3](#0-2) 
This is the same code path used for legitimate JSON bodies, so there is no additional binary/escape check anywhere else in this branch. An attacker-controlled HTTP server (i.e., a host the victim explicitly points `gh api <url>` at, or a GHES/Enterprise endpoint under attacker influence) can respond with `Content-Type: application/json` and a body that is plain text/binary containing ANSI escape sequences (e.g. cursor movement, screen clear, OSC sequences, terminal title injection, or sequences abused by vulnerable terminal emulators). Because `isJSON` is (falsely) true, the `CopyGuardedContent` guard — which is specifically designed to catch exactly this class of content — is never invoked, and the bytes are written verbatim to the user's terminal.

### Impact Explanation
This allows terminal escape-sequence injection into the victim's TTY when running `gh api` against an attacker-influenced host, with color disabled. Depending on the victim's terminal emulator, this can range from denial-of-service/terminal corruption (screen clear, garbled state) to more severe outcomes on vulnerable terminal emulators (e.g., title-bar/clipboard manipulation, or advanced escape-sequence abuse). This maps to GitHub's "content injection / terminal escape sequence injection" impact class, matching the exact concern the `CopyGuardedContent` guard was introduced to prevent — the vulnerability here is that the guard can be trivially bypassed by mislabeling the `Content-Type` header.

### Likelihood Explanation
Preconditions: (1) the victim runs `gh api <path-or-url>` against a host they point `gh` at, where the attacker controls responses (a plausible scenario for `gh api https://attacker-host/...` or a compromised/malicious GHES-like endpoint); (2) output is to a TTY; (3) color output is disabled (`NO_COLOR` env var, `--color` config set to never, `GH_NO_COLOR`, or a terminal not detected as color-capable). Condition (3) narrows likelihood — the standard "plain `gh api <path>` to a TTY" default has color enabled, in which case the `jsoncolor.Write` path is used and is not exploitable this way. The bug is real and easily triggered under a common but non-default configuration (many CI/terminal environments set `NO_COLOR`), but it is not the fully unconditional default-path bypass suggested in the audit prompt.

### Recommendation
Do not rely solely on the `Content-Type` header to select the code path. In the non-color, `isJSON`-true branch, still route the body through `CopyGuardedContent` (or validate that the content is well-formed JSON before doing a raw copy), so the escape-sequence and binary-terminal guards apply regardless of whether the server's declared `Content-Type` is trusted.

### Proof of Concept
Go test using `httpmock`/a stub HTTP transport for `gh api`:
1. Set up a fake `RoundTripper` that returns `Content-Type: application/json` with body `"\x1b]0;pwned\x07not actually json"` (invalid JSON, so it fails decode if ever routed through `jsoncolor.Write`, but is not routed there in this repro).
2. Configure `ApiOptions` with `opts.IO` simulating a TTY (`SetStdoutTTY(true)`) and color disabled (`opts.IO.SetColorEnabled(false)` or run with `NO_COLOR=1`).
3. Run `apiRun(opts)` and capture `opts.IO.Out`.
4. Assert that the raw ESC byte (`0x1B`) and OSC sequence appear unmodified in `opts.IO.Out`, proving `CopyGuardedContent` was bypassed — compare against the same body served with `Content-Type: text/plain`, where `CopyGuardedContent` correctly returns `iostreams.ErrEscapeSequence` and refuses to print.
