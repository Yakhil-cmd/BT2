### Title
Webhook signature verification is bound to an attacker-controlled field that differs from the field used to select the target repository/stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a GitHub webhook against using `repository.owner.login` (or `organization.login`) taken directly from the untrusted JSON body. Every webhook handler, however, resolves the `Stack`/`Repository` to act on using a *different* field of the same body: `repository.full_name`. Because Shipit supports multiple independent GitHub App configurations (one per organization, each with its own `webhook_secret`), any org onboarded to the instance can compute a valid HMAC signature over a forged payload and use it to act on a completely different organization's repository, since nothing binds `owner.login` (used for auth) to `full_name` (used for authorization/target selection).

### Finding Description
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore its `webhook_secret`) to validate against based on: [1](#0-0) [2](#0-1) 

`Shipit.github` looks up per-organization webhook secrets when multiple GitHub App configs are configured: [3](#0-2) 

Once the signature is accepted, the raw JSON body is handed unchanged to every registered handler: [4](#0-3) 

Every handler resolves the target `Stack`/`Repository` using an entirely different key of the same body, `repository.full_name`, not `repository.owner.login`: [5](#0-4) 

`PushHandler` then triggers a repository sync for the resolved stacks using an attacker-supplied `after` (expected head SHA): [6](#0-5) 

The equality the app implicitly (and incorrectly) assumes is:
`organization authenticated by verify_signature (repository.owner.login)` == `repository actually written by the handler (repository.full_name)`.

Because both fields live in the same attacker-forgeable JSON body, and the signature only proves the body was HMAC-signed with *some* org's secret (not that the two fields agree), an attacker who legitimately knows one organization's `webhook_secret` (e.g., because they administer their own low-trust org/repo onboarded to the same multi-tenant Shipit instance) can:
1. Set `repository.owner.login` = `"attacker-org"` so `verify_signature` selects and validates against the secret they know.
2. Set `repository.full_name` = `"victim-org/victim-repo"` so the handler's `Repository.from_github_repo_name` resolves a completely unrelated stack.
3. Sign the crafted body with their own known secret and POST it to `/webhooks`.

The request passes signature verification and is processed against the victim stack.

### Impact Explanation
This breaks the deployment-trust binding between "the organization whose credential validated this webhook" and "the repository/stack that webhook is authorized to mutate." Via `PushHandler`, an attacker can force a `GithubSyncJob` for a victim stack with an attacker-chosen `expected_head_sha`, on stacks they have no legitimate relationship with — an authorization bypass across organizational/repository boundaries reachable by any unprivileged party who merely controls one onboarded org's webhook secret. This maps to the "unauthorized deploy/rollback" and "cross-repository writes" impact categories, since a forced sync against an attacker-chosen SHA on a `continuous_deployment`-enabled stack can trigger an unintended/attacker-timed deploy pipeline run for a repository the attacker does not own.

### Likelihood Explanation
Exploitability requires the attacker to legitimately possess a `webhook_secret` for at least one organization configured on the Shipit instance — a low bar in multi-tenant deployments where several teams/orgs each install their own GitHub App integration on a shared Shipit instance, since none of them are expected to be trusted with each other's repositories. No GitHub access to the victim org, no Shipit session, and no API token are required — only the ability to send a signed webhook using credentials scoped to a *different* org.

### Recommendation
Bind the field used for signature-secret selection to the field used for target resolution: verify that `repository.full_name`'s owner segment equals the `repository_owner` used to select the `webhook_secret` (or, better, verify the signature using the secret associated with the resolved target `Repository`/`Stack`'s own organization rather than a value taken from the untrusted payload before verification). Alternatively, resolve the `Repository` first from a value trusted only after signature verification, and reject payloads where `repository.owner.login` does not match the owner segment of `repository.full_name`.

### Proof of Concept
1. Assume Shipit is configured with two GitHub App organizations: `attacker-org` (attacker knows `webhook_secret_A`) and `victim-org` (tracks stack `victim-org/victim-repo`).
2. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature against the attacker's own known secret [1](#0-0) .
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's stack using the attacker's chosen SHA [7](#0-6) , despite the request never having been authenticated by, or for, `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
