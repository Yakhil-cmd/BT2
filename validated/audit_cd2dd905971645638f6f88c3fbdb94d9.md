### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from one repository overwrite CI status on another repository's identical-SHA commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by SHA, with no repository/stack scoping, then calls `commit.create_status_from_github!(params)` on every match. Because Git SHAs are content-addressable and are reused whenever a commit is shared/forked/mirrored across repositories, an attacker who owns a repository that legitimately shares a commit SHA with a victim's stack can push a `status` webhook (signed by their own repo's webhook secret) that mutates the victim stack's `Commit`/`Status` records.

### Finding Description
The broken binding: the invariant that should hold is
`webhook.repository.full_name == commit.stack.repository.full_name` for every `Commit` mutated by a given webhook event.

In `app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

there is no `stack_id`/`repository` filter at all — the query is global across the entire `commits` table. `WebhooksController#verify_signature` only authenticates that the payload came from GitHub for `repository_owner` (the org/app tied to the payload's own `repository.owner.login`) via `Shipit.github(organization: repository_owner).verify_webhook_signature`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
end
``` [2](#0-1) 

That check proves the request truly originated from GitHub for the attacker's own organization/repo — it says nothing about which `Commit` rows in Shipit's database the event is allowed to touch. `StatusHandler` never re-checks that the matched `Commit#stack`'s repository equals the payload's `repository.full_name`.

`create_status_from_github!` then writes and recomputes state using the found commit's own `stack_id`:
```ruby
def create_status_from_github!(github_status)
  add_status do
    statuses.replicate_from_github!(stack_id, github_status)
  end
end
``` [3](#0-2) 

and `add_status` recomputes `Status::Group`, fires `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` [4](#0-3) . `deployable?` directly depends on the recomputed `status`:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [5](#0-4) 

Exploit flow: attacker owns Repo A, pushes/forks a commit whose SHA is identical to one that also exists as a `Commit` row belonging to victim Stack B (e.g., a shared upstream commit, a forked/mirrored repo, or a cherry-picked/rebased commit that happens to collide because it was copied verbatim into both histories). Attacker sends `POST /webhooks` with `X-Github-Event: status`, a body `{ "sha": "<shared sha>", "context": "ci/jenkins", "state": "failure", "repository": {"owner": {"login": "attacker-org"}} }`, signed with attacker-org's own webhook secret (which the attacker legitimately possesses because they configured their own repo's webhook). `verify_signature` passes because it only checks signature validity for `attacker-org`. `StatusHandler#process` then finds **all** `Commit` rows with that SHA — including the victim's — and forces `ci/jenkins` to `failure` on the victim commit, flipping `deployable?` to `false` and blocking merges/deploys, even though the victim repository never sent this event.

No other guard intervenes: `drop_unhandled_event` only checks event type presence, `ExplicitParameters` (`params do ... end`) only validates payload shape, and there is no `Repository`/`Stack` lookup tying the SHA to a specific repo anywhere in this handler.

### Impact Explanation
A payload authenticated for one repository (attacker's) writes state (`Status`, `Status::Group`, `deployable?`, merge-eligibility) belonging to a different repository/stack (victim's) that never authenticated it. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team." The attacker can force a required context (e.g. `ci/jenkins`) to `failure` on a shared-SHA commit in a victim stack, blocking deploys/merges, or conversely force it to `success` to bypass a CI requirement (deployability/merge-eligibility manipulation). This is repeatable for every commit whose SHA is shared between an attacker-controlled repository and a victim stack (forks, mirrors, or any repo cherry-picking/replaying the same commit object).

### Likelihood Explanation
Preconditions: the attacker must own/administer a GitHub repository (any unprivileged GitHub user can do this) and the target SHA must exist as a `Commit` row in some other victim stack — which happens naturally with forks, mirrors, or shared history. No Shipit credentials, session, or API token are required; only the attacker's own repo's webhook secret, which they legitimately hold. Cost is a single crafted `status` payload; the attack is fully repeatable against any repository configured in Shipit as long as a shared SHA exists.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` (and analogous handlers) to the repository that authenticated the event, e.g. join `Commit` to `Stack`/`Repository` and filter by the payload's `repository.full_name`, mirroring the check already done in `WebhooksController#repository_owner`/`verify_signature`. Do not rely on SHA alone as a global key.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create two stacks/repositories: `victim/repo` with `ci.require` including `ci/jenkins`, and `attacker/repo` (no special config).
2. Create a `Commit` with `sha: "deadbeef..."` under `victim/repo`'s stack, with an existing successful `ci/jenkins` status so `commit.deployable?` is `true`.
3. Create a second `Commit` with the *same* `sha` under `attacker/repo`'s stack (simulating a shared/forked commit).
4. Build a `status` event payload: `{ sha: "deadbeef...", context: "ci/jenkins", state: "failure" }` and call `Shipit::Webhooks::Handlers::StatusHandler.new(payload).call` (or `.process`) directly — bypassing only the controller-level signature check, since that check is per-organization and does not scope by SHA/commit.
5. Assert, BEFORE: `victim_commit.deployable?` == `true` and `attacker_commit.deployable?` (or its status) reflects no failure.
6. Assert, AFTER processing: `victim_commit.reload.status.failure?` == `true` and `victim_commit.deployable?` == `false`, proving the victim commit — never touched by `victim/repo`'s webhook — was mutated by a payload only ever authenticated for `attacker/repo`.
