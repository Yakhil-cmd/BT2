### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for the `prevent_with_label` branch due to Ruby `&&`/`||` operator precedence - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
The guard method `provision?` in `OpenedHandler` was written assuming `review_stacks_enabled` gates all three provisioning behaviors, but Ruby's operator precedence (`&&` binds tighter than `||`) makes it gate only the `allow_all` branch. As a result, a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label` will still auto-create a `Shipit::ReviewStack` for any opened pull request that lacks the provisioning label.

### Finding Description
Broken binding: the code intends `repository.review_stacks_enabled == true` to be a prerequisite for `ReviewStack.create!`, but this is false for the third disjunct.

The method reads: [1](#0-0) 

Due to Ruby precedence, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

The third clause `(prevent_with_label? && !has_label?)` has no dependency on `review_stacks_enabled` at all. So if a repository operator sets `provisioning_behavior: :prevent_with_label` and `review_stacks_enabled: false` (e.g., temporarily disabling auto-provisioning while leaving the behavior enum untouched, since no model validation ties these two fields together — see [2](#0-1) ), any ordinary "opened" pull-request webhook without the provisioning label causes `provision?` to evaluate `true`, and `process` calls: [3](#0-2) 
which invokes `ReviewStackAdapter#find_or_create!`, creating a real `Shipit::ReviewStack` record.

The attacker's action is simply opening a normal pull request (with no labels) against the tracked repository — a fully legitimate GitHub action that any contributor can perform. GitHub then sends a legitimate, correctly-signed `opened` webhook (no signature forgery needed), so `verify_signature`/`GitHubApp#verify_webhook_signature` do not block this: the request is authentic, only the *authorization intent* encoded in `review_stacks_enabled` is bypassed by the buggy boolean logic.

Downstream, `ReviewStackProvisioningQueue#provision` will later call `stack.provision`, which runs the repository's provisioning tasks (commands executed via `Command`/`PTY.spawn` per Shipit's task execution model) — i.e., the operator's decision to fully disable review-stack provisioning for the repository is silently overridden.

### Impact Explanation
An attacker who can merely open a pull request (no write access needed) triggers stack creation and subsequent provisioning task execution on a repository whose operator explicitly disabled review stacks (`review_stacks_enabled: false`). This causes unintended repository state mutation (a `Stack`/`ReviewStack`/`PullRequest` record created) and unauthorized triggering of provisioning tasks, which in Shipit's execution model run shell commands. This is repeatable for every PR the attacker opens (each becomes an environment/stack) as long as the misconfiguration (`prevent_with_label` + `review_stacks_enabled: false`) persists on that repository — it does not cross repository boundaries, so blast radius is confined to the misconfigured repository, but the write occurs against explicit operator intent (`review_stacks_enabled == false`), which the model was supposed to enforce.

### Likelihood Explanation
Requires the specific repository configuration `review_stacks_enabled: false` combined with `provisioning_behavior: :prevent_with_label`. Since `Repository` has no validation preventing this combination [2](#0-1) , and it is a plausible operational state (an operator disabling review stacks without resetting `provisioning_behavior`), the precondition is realistic. Attacker cost is trivial: open a PR without adding any label. Fully repeatable per PR.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three disjuncts:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the same fix to the structurally identical `unarchive?`/`archive?` methods in `reopened_handler.rb` and `labeled_handler.rb`/`unlabeled_handler.rb`, which share the same precedence flaw.

### Proof of Concept
```ruby
test "does not create stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  repository = shipit_repositories(:shipit)
  repository.update!(review_stacks_enabled: false, provisioning_behavior: :prevent_with_label)

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
With the current implementation this assertion fails: `assert_difference('Shipit::Stack.count')` is observed instead, confirming a stack is created despite `repository.review_stacks_enabled == false`.
