## Analysis

The Sentiment finding is about a *rounding-down attack on a share/asset accounting ratio* that lets an attacker shrink `totalDepositShares` to `1` and then repeatedly re-inflate `totalDepositAssets`, so that any subsequent depositor's minted shares round down to `0` while their deposited value is captured by the attacker's remaining share.

ocore's core DAG/consensus code (`validation.js`, `writer.js`, `headers_commission.js`, `main_chain.js` vote counting, `definition.js` weighted signatures) doesn't implement a share/pool vault at all — those subsystems distribute fixed-percentage commissions or count balances for governance, not user-deposited pools with a mintable/burnable internal share supply. The one place in the repository that reproduces the exact "totalShares / totalAssets" accounting pattern used by lending/AMM vaults is the official example AA shipped with ocore, `test/samples/uniswap_like_market_maker.oscript`, which is parsed and validated by `test/ojson.test.js` and represents the canonical pattern ocore documents for AA authors building pooled-liquidity contracts.

In that AA:
- `var['mm_asset_outstanding']` plays the role of `totalDepositShares`.
- `balance[base]` / `balance[$asset]` (the AA's live on-chain balance) plays the role of `totalDepositAssets`.
- New shares are minted as `$issue_amount = round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, i.e. `round(deposit/existing_balance * outstanding_shares)`.

If `var['mm_asset_outstanding']` is driven down to a small value (e.g. `1`, by the majority/attacker holder divesting almost all shares via the "divest MM shares" branch, which just does `var['mm_asset_outstanding'] -= trigger.output[[asset=$mm_asset]]` with no minimum-liquidity floor), while `balance[base]`/`balance[$asset]` remain large, a normal depositor whose contribution is small relative to the existing balance gets `$issue_amount` rounded down to `0`. Their base/asset payment is still absorbed into `balance[base]`/`balance[$asset]`, which is entirely backing the attacker's remaining `1`-unit share, so on divest the attacker redeems the victim's funds. This is the same rounding/first-depositor inflation primitive as the Sentiment report, reachable purely through actions of an AA trigger sender (deposit/divest triggers) against an AA built from this template.

### Title
Share-accounting rounding-down (first-depositor/inflation) attack in the example pool AA - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The `uniswap_like_market_maker.oscript` sample AA (shipped and validated in this repo) implements pool share issuance as `round(deposit_ratio * totalShares)` without any minimum-liquidity/minimum-shares safeguard when burning shares in the divest branch, allowing an attacker to shrink `var['mm_asset_outstanding']` and cause subsequent depositors' minted shares to round to zero.

### Finding Description
`test/samples/uniswap_like_market_maker.oscript` defines an AA whose invest case computes: [1](#0-0) 
new shares as `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, where `var['mm_asset_outstanding']` tracks total shares and `balance[base]`/`balance[$asset]` (the AA address's actual ledger balance) tracks total pooled assets.

The divest branch decrements `var['mm_asset_outstanding']` by exactly the amount of shares burned, with no floor: [2](#0-1) 

Because share issuance on deposit is a simple `round()` of a ratio against the *current* `mm_asset_outstanding`, an attacker who is the majority/sole shareholder can burn nearly all outstanding shares (leaving e.g. `1`), then have a large `balance[base]`/`balance[$asset]` remain backing that residual share. A subsequent legitimate depositor whose contribution is small relative to the existing pool balance will have `$issue_amount` computed as `round(small/huge * 1)`, which rounds down to `0` — they receive no shares, yet their payment increases `balance[base]`/`balance[$asset]`, which is entirely redeemable by the attacker's remaining share via the divest branch: [3](#0-2) 

This mirrors the root cause in the external report: an internal "shares vs. assets" ratio is trusted to be non-degenerate, but nothing in the AA (or in ocore's oscript primitives such as `round()`/division in `formula/evaluation.js`) enforces a minimum share supply or minimum-deposit floor, so the ratio can be pushed to a state where rounding transfers value from new depositors to the existing shareholder.

### Impact Explanation
Any AA trigger sender who deposits into a pool AA following this exact, ocore-documented pattern can lose their entire deposited base/asset payment to the attacker who previously deflated the share supply — the same "loss of funds via rounding-down share issuance" impact described in the external report (up to the full deposited amount for affected transactions, concentrated on the first depositors after the attacker's manipulation).

### Likelihood Explanation
Exploitation only requires an attacker to be an early/majority holder of the AA's own share asset, deposit and withdraw following the AA's own defined triggers (`invest`/`divest` messages), and wait for a normal user to deposit a small amount relative to the manipulated pool balance — all standard, permissionless AA-trigger interactions available to any unprivileged AA trigger sender.

### Recommendation
Enforce a minimum total-share floor (e.g., permanently lock a minimum number of shares on first mint, analogous to UniswapV2/BalancerV2 "minimum liquidity" burn-to-zero-address patterns) and reject deposits whose computed `$issue_amount` rounds to `0` (bounce instead of silently minting nothing) in the example AA and in ocore's documentation/guidance for AA authors building pooled-share contracts.

### Proof of Concept
1. Attacker deposits (`invest` case) to become sole holder of `mm_asset`, so `var['mm_asset_outstanding'] = N` backed by `balance[base]=B0`, `balance[$asset]=A0`.
2. Attacker sends `trigger.output[[asset=$mm_asset]] = N-1` to the divest case, reducing `var['mm_asset_outstanding']` to `1` while retaining most of `balance[base]`/`balance[$asset]` in the AA (the divest payout is `round($investor_share*balance)`, so a `(N-1)/N` share leaves large residual balances): [4](#0-3) 
3. A victim deposits a normal-sized `trigger.output[[asset=base]]` and matching `$asset` amount satisfying the ratio check; because `var['mm_asset_outstanding']=1` and `$bytes_balance` is large, `$issue_amount = round($investor_share_of_prev_balance * 1)` rounds to `0`: [5](#0-4) 
4. The victim's funds are added to `balance[base]`/`balance[$asset]` with no shares minted; the attacker then divests their remaining `1` share and receives `round(1 * balance[$asset])`/`round(1 * balance[base])`, capturing the victim's deposit.
