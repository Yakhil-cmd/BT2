### Title
Missing type check before merkle-proof deserialization in `in merkle` authentifier handler allows crafted unit to crash validation - (File: `definition.js`)

### Summary
The `in merkle` authentifier evaluator in `definition.js` passes an attacker-controlled authentifier value directly into `merkle.deserializeMerkleProof()` without first verifying that the value is a string, unlike the equivalent `is_valid_merkle_proof` oscript function in `formula/evaluation.js`, which explicitly type-checks its input before calling the same deserializer. This mirrors the CVE-2017-9761 bug class: a crafted, attacker-supplied blob is fed into a parsing routine that assumes well-formed input and can throw/behave unexpectedly on malformed data, producing an unhandled error during validation of untrusted data.

### Finding Description
In `definition.js`, the `in merkle` branch of `validateAuthentifiers`'s inner `evaluate` function does: [1](#0-0) 

```js
case 'in merkle':
    if (!assocAuthentifiers[path])
        return cb2(false);
    arrUsedPaths.push(path);
    ...
    var serialized_proof = assocAuthentifiers[path];
    var proof = merkle.deserializeMerkleProof(serialized_proof);
    if (!merkle.verifyMerkleProof(element, proof)){
        ...
```

`assocAuthentifiers` is populated from the `authentifiers` field of a unit author, which is attacker-controlled data supplied by whoever posts the unit. `serialized_proof` is used directly without confirming its type is `string`.

`merkle.deserializeMerkleProof` unconditionally calls `.split("-")` on its argument: [2](#0-1) 

```js
function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}
```

If `serialized_proof` is not a string (e.g. a number, boolean, array, or object placed at that path in the JSON-serialized unit), `.split` does not exist on that value and the call throws a `TypeError`. This call is **not** wrapped in a `try/catch` at this call site in `definition.js`.

By contrast, the structurally identical `is_valid_merkle_proof` oscript function in `formula/evaluation.js` explicitly guards the type before deserializing: [3](#0-2) 

```js
if (proof instanceof wrappedObject)
    objProof = proof.obj;
else if (typeof proof === 'string') {
    if (proof.length > 1024)
        return setFatalError("proof is too large", { arr }, false, cb);
    objProof = merkle.deserializeMerkleProof(proof);
}
else // can't be valid proof
    return cb(false);
...
try {
    res = merkle.verifyMerkleProof(element, objProof);
}
catch (e) {
    res = false;
}
```

The asymmetry between these two consumers of `merkle.deserializeMerkleProof` — one type-checks the input, the other does not — indicates the `in merkle` authentifier path is missing the same defensive check, making it the analog of the radare2 `find_eoq` bug class: a parser (`deserializeMerkleProof`) that assumes well-formed input, invoked on attacker-supplied data reachable from a single posted unit, without validating the input shape first.

### Impact Explanation
If the `authentifiers` value at the `in merkle`-guarded path is not enforced to be a string by earlier unit-schema validation, an attacker can post a unit whose address definition contains an `in merkle` condition and whose `authentifiers` map supplies a non-string value at that path. This throws an uncaught `TypeError` synchronously inside the authentifier-evaluation switch, which is not caught locally. Depending on how far up the call chain this propagates before being caught (validation.js's async control flow), this can result in an unhandled exception during unit validation — a denial-of-service condition where a node crashes or otherwise fails to validate/confirm units, matching the "network unable to confirm new units" impact class for this analog scan.

### Likelihood Explanation
The `in merkle` authentifier condition is a documented address-definition primitive reachable by any address owner who chooses to include it in their definition, and the `authentifiers` field is populated straight from the unit author's data by the poster of the unit. No special privilege is required beyond crafting a unit with such an address/definition and authentifiers — exactly the reachable "unprivileged unit poster" surface specified as in-scope. The likelihood hinges on whether upstream unit-schema validation strictly enforces that every value in `authentifiers` is a string before reaching `validateAuthentifiers`; this could not be conclusively confirmed with the available tooling, so it is flagged as the main residual uncertainty.

### Recommendation
Add an explicit type check before deserializing, mirroring the pattern already used in `formula/evaluation.js`:
```js
if (typeof serialized_proof !== 'string')
    return cb2(false);
```
and/or wrap the `merkle.deserializeMerkleProof` / `merkle.verifyMerkleProof` calls in `definition.js`'s `in merkle` handler in a `try/catch` that treats any exception as proof failure (`cb2(false)`), consistent with how `verifyMerkleProof` itself already defends against malformed proof objects.

### Proof of Concept
1. Construct a unit whose address definition includes an `in merkle` authentifier condition, e.g. `["in merkle", [["SOME_ADDRESS"], "feed_name", "expected_value"]]`, and derive the address from this definition.
2. Post a unit signed by/authored at that address, supplying `authentifiers` with the value at the corresponding path set to a non-string JSON value (e.g. `42`, `true`, `[]`, or `{}`) instead of a serialized merkle proof string.
3. During validation, `validateAuthentifiers` reaches the `in merkle` case, retrieves the non-string value from `assocAuthentifiers[path]`, and calls `merkle.deserializeMerkleProof(serialized_proof)`.
4. `serialized_proof.split("-")` throws a `TypeError` because `.split` is not defined on non-string types, which is not caught in this call path, producing an unhandled exception during validation of the posted unit.
