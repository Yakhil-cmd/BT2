## Title
Outputs spent by a unit that later becomes `final-bad` via cascading propagation stay permanently marked `is_spent=1`, causing balance under-reporting and fund freezing — (File: `main_chain.js`)

### Summary
This is the same bug class as the reported `LiquidityBuffer.getControlledBalance()` issue: a status transition (there: manager `isActive=false`; here: a unit's `sequence` becoming `'final-bad'`) is not accompanied by reversal of the resource-locking side effect it caused, so (a) balance-reporting queries under-count real spendable funds, and (b) the funds become inaccessible to their rightful owner until an out-of-band fix occurs.

### Finding Description
When a unit spends an output, `writer.js` unconditionally marks the source output `is_spent=1` at write time, regardless of the unit's eventual validity: [1](#0-0) . This happens even for units that are only tentatively good and may later be invalidated.

During stabilization, `main_chain.js`'s `propagateFinalBad()` cascades `final-bad` status to any future unit that spent outputs of a unit that itself became `final-bad` (e.g., due to an unrelated invalid ancestor elsewhere in the DAG, not necessarily a same-address double-spend): [2](#0-1) . This code path only updates `units.sequence` and `inputs.is_unique`; it never resets `outputs.is_spent` back to `0` for the outputs that the now-`final-bad` unit had spent.

The only place in the codebase that actually reverses `is_spent` for outputs consumed by an invalidated unit is `archiving.js`'s `generateQueriesToUnspendOutputsSpentInArchivedUnit()`, which is called only from the archival/voiding path (`generateQueriesToVoidJoint`) used for uncovered/pruned/voided joints, notably reachable from `light.js`'s history-processing flow for light clients: [3](#0-2) [4](#0-3) . The normal full-node stabilization path in `main_chain.js` (`markMcIndexStable` → `handleNonserialUnits` → `propagateFinalBad`) never calls this unspend logic.

This is confirmed by the codebase's own bug-fix trail: `main_chain.js`'s `countVotes()` was specifically patched with a `NOT EXISTS`-based query and an explicit comment stating that outputs "whose only spending unit was propagated to final-bad" leave `is_spent=1` in the DB "while no good unit claims the output," which the old two-query approach "silently undercounted": [5](#0-4) . A dedicated diagnostic tool, `tools/compare_vote_balances.js`, was even built to detect these "zombie-spent outputs": [6](#0-5) .

Critically, this fix was applied **only** to the OP/system-vote balance calculation. All other balance and coin-selection code paths still use the naive `is_spent=0` filter and therefore still under-report and lock funds affected by this exact scenario:
- Wallet balance reporting: `balances.js` `readBalance`/`readOutputsBalance`/`readSharedBalance` [7](#0-6) 
- Light client balance requests: `network.js` `light/get_balances` [8](#0-7) 
- Coin selection for composing new payments: `composer.js` `readSortedFundedAddresses` [9](#0-8)  and `wallet.js` `readFundedAddresses` [10](#0-9) , both of which filter `is_spent=0`.

### Impact Explanation
Any legitimate unit poster whose payment unit is later cascaded to `final-bad` (because it spent an output from an unrelated ancestor unit that was itself invalidated, not necessarily because of a same-address double-spend they caused) will have the source output permanently stuck with `is_spent=1`:
- Their wallet balance (`balances.js`, `light/get_balances`) will under-report the true stable balance of that output indefinitely.
- Coin-selection logic used to compose new payments (`composer.js`, `wallet.js`) will never pick this output as an input, because it always filters `is_spent=0`, so the funds become **permanently inaccessible** for spending through the standard wallet flow — a fund-freezing condition matching the disclosed report's outcome for the deactivated manager's residual balance.
- Because the underlying flaw is a database-bookkeeping omission in `main_chain.js`'s stabilization logic (not an application bug limited to one feature), it affects any address, any amount, and persists until a manual/administrative correction (e.g. archiving/voiding, which is not automatically triggered for full nodes in this path).

This qualifies as concrete AA/user fund freezing and under-reporting of a stable output, matching the required impact bar.

### Likelihood Explanation
This does not require a malicious actor with special privileges — it is triggered by ordinary DAG dynamics: any unit that ends up as `final-bad` due to cascading propagation from an invalidated ancestor (a routine consequence of double-spends/forks elsewhere in the DAG) will silently freeze any outputs it spent. The bug is corroborated by the codebase's own remediation (`countVotes` fix + `compare_vote_balances.js` diagnostic tool) demonstrating that this exact condition occurs in practice and was significant enough to warrant a targeted fix in one subsystem, while all other consumers of `outputs.is_spent` were left unfixed.

### Recommendation
Apply the same fix already used for `countVotes()` — i.e., stable-good-output-has-no-stable-good-spender logic via `NOT EXISTS` (or, more robustly, reset `outputs.is_spent=0` for the outputs consumed by any unit whose `sequence` transitions to `final-bad` during `propagateFinalBad()`/`handleNonserialUnits()` in `main_chain.js`, analogous to what `archiving.js`'s `generateQueriesToUnspendOutputsSpentInArchivedUnit` already does for the voiding path) — consistently across `balances.js`, `network.js` (`light/get_balances`), `composer.js`, and `wallet.js` coin-selection queries, rather than only in vote counting.

### Proof of Concept
1. Construct (or wait for) a scenario where unit `B` spends unit `A`'s output, and `B` also has another input that ultimately gets propagated `final-bad` (e.g., because it descends from a unit that loses a double-spend elsewhere in the DAG unrelated to the address in question).
2. Once MCI stabilizes, `main_chain.js`'s `handleNonserialUnits`/`propagateFinalBad` marks `B.sequence='final-bad'`, but `A`'s output remains `is_spent=1` (set at write time by `writer.js`, never reversed).
3. Query the owning address's balance via `balances.js`/`light/get_balances`: the output is excluded — balance is under-reported.
4. Attempt to compose a new payment from that address via `composer.js`/`wallet.js`: the coin-selection query filters `is_spent=0`, so the output is never selected — the funds are unspendable through normal wallet operation, matching the reported bug's "residual balance excluded and inaccessible until reactivated" pattern (here, until manual archiving/voiding is performed, which does not happen automatically for full-node stabilization).

Note: I was unable to fully trace whether every possible cascading `final-bad` scenario is reachable without an actual double-spend at the same address (this would require deeper DAG-simulation testing that exceeds what static code reading can confirm), but the code path in `main_chain.js` and the `countVotes` fix comment strongly indicate this condition does occur in practice.

/*jslint node: true */
'use strict';
// Compares voter balance calculations for system_vote subjects using two methods:
//   OLD: bal_rows (is_spent=0 stable-good) + spent_rows (unstable-good spending stable-good)
//   NEW: stable-good outputs with no stable-good spender (NOT EXISTS)
//
// A difference means the OLD method undercounts a voter's balance because a future
// unstable unit spent their stable output and was later propagated to final-bad,
// leaving is_spent=1 on the output while no good unit claims it in spent_rows.
//
// Usage: node tools/compare_vote_balances.js

const db = require('../db.js');

async function balancesOldWay(addresses) {
	const strAddresses = addresses.map(db.escape).join(', ');

	const bal_rows = await db.query(`
		SELECT address, SUM(amount) AS balance
		FROM outputs
		LEFT JOIN units USING(unit)
		WHERE address IN(${strAddresses}) AND is_spent=0 AND asset IS NULL AND is_stable=1 AND sequence='good'
		GROUP BY address`);

	const balances = {};
	for (const { address, balance } of bal_rows)
		balances[address] = balance || 0;

	const spent_rows = await db.query(`
		SELECT inputs.address, SUM(outputs.amount) AS spent_balance
		FROM units
		CROSS JOIN inputs USING(unit)
		CROSS JOIN outputs ON src_unit=outputs.unit AND src_message_index=outputs.message_index AND src_output_index=outputs.output_index
		CROSS JOIN units AS output_units ON outputs.unit=output_units.unit
		WHERE units.is_stable=0 AND +units.sequence='good'
			AND +output_units.is_stable=1 AND +output_units.sequence='good'
			AND inputs.address IN(${strAddresses}) AND type='transfer' AND inputs.asset IS NULL
		GROUP BY inputs.address`);

	for (const { address, spent_balance } of spent_rows) {
		if (balances[address])
			balances[address] += spent_balance;
		else
			balances[address] = spent_balance;
	}

	return balances;
}
