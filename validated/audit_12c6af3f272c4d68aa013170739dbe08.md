### Title
Missing Zero-Address Guard on `CLPoolAddr` Causes KAIA Staking Rewards Sent to `address(0)` — (`kaiax/staking/impl/getter.go`, `kaiax/reward/impl/getter.go`)

---

### Summary

After the Prague hardfork, the Kaia reward-distribution pipeline reads `CLPoolAddr` from the CLRegistry via `MultiCallDPStakingInfo` and stores it verbatim in `CLStakingInfo` without any zero-address validation. Every downstream reward-calculation function (`assignStakingRewards`, `assignStakingRewardsFlex`, `specWithProposerAndFunds`, `specWithProposerAndFundsFlex`) then uses that address as a direct recipient. `FinalizeState` calls `state.AddBalance(addr, amount)` for every entry in `spec.Rewards`; if `addr` is `address(0)`, the KAIA is credited to the zero address and permanently lost.

---

### Finding Description

**Root cause — `parseCallResult` / `parsePermissionlessCallResult`**

Both parsing functions copy `clRes.ClPools[i]` directly into `CLStakingInfo.CLPoolAddr` with no zero-address check:

```go
// kaiax/staking/impl/getter.go  lines 293-302
for i := range clRes.NodeIds {
    clStakingInfos[i] = &staking.CLStakingInfo{
        CLNodeId:        clRes.NodeIds[i],
        CLPoolAddr:      clRes.ClPools[i],   // ← no address(0) guard
        CLStakingAmount: ...,
    }
}
```

The same pattern appears in `parsePermissionlessCallResult` (lines 211-221).

**Propagation — `assignStakingRewards` / `assignStakingRewardsFlex`**

When `isPrague && cn.CLStakingInfo != nil`, the CL portion of the staking reward is keyed directly on `CLPoolAddr`:

```go
// kaiax/reward/impl/getter.go  lines 521-525
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount  // ← address(0) if unset
}
```

Identical pattern in `assignStakingRewardsFlex` (lines 474-477).

**Propagation — `specWithProposerAndFunds` / `specWithProposerAndFundsFlex`**

The proposer-split path also calls `IncRecipient` with the unvalidated address:

```go
// kaiax/reward/impl/getter.go  lines 633-637
cnAmount, clAmount := cn.Split(proposer)
newSpec.IncRecipient(cn.RewardAddr, cnAmount)
newSpec.IncRecipient(cn.CLStakingInfo.CLPoolAddr, clAmount)  // ← address(0) if unset
```

**Execution — `FinalizeState`**

```go
// kaiax/reward/impl/blockstate.go  lines 53-55
for addr, amount := range spec.Rewards {
    state.AddBalance(addr, amount)   // ← state.AddBalance(address(0), clAmount)
}
```

`StateDB.AddBalance` calls `GetOrNewStateObject(addr)` which happily creates or updates the zero-address account; no revert occurs.

**No existing guard**

The sanity check in `parseCallResult` (lines 304-311) validates `kefAddr` and `kifAddr` for emptiness but **does not validate any `CLPoolAddr`**. The `consolidateNodes()` function in `staking_info.go` (lines 124-167) also performs no zero-address filtering on `CLPoolAddr`.

---

### Impact Explanation

If the CLRegistry returns `address(0)` as a pool address for any registered validator — whether due to a bug in the CLRegistry contract, an uninitialized entry, or a validator deliberately registering with a zero pool address — the corresponding CL staking reward (`clAmount`) is credited to `address(0)` in the world state every block. Those KAIA tokens are permanently inaccessible (effectively burned without being accounted as burnt in `spec.BurntFee`), causing:

- **Unauthorized loss of KAIA staking rewards** — the CL pool operator receives nothing; the tokens vanish into `address(0)`.
- **Accounting divergence** — `spec.Rewards` sums correctly but the zero-address balance grows silently, breaking the invariant that all distributed rewards reach their intended recipients.

---

### Likelihood Explanation

The CLRegistry is a system contract whose source is not present in this repository; only mocks are available. The mocks return hardcoded non-zero addresses. Whether the production CLRegistry validates `clPool != address(0)` on registration is unknown from this codebase alone. However:

1. The Go layer provides **zero defensive validation** at any point in the pipeline.
2. Any future CLRegistry upgrade, misconfiguration, or bug that emits a zero pool address would silently corrupt reward distribution with no error or revert.
3. The pattern is directly analogous to the seeded bug class (calls/transfers to unvalidated zero addresses).

Likelihood is **low-to-medium** given the CLRegistry is a privileged system contract, but the missing guard makes the impact unconditional once the condition is met.

---

### Recommendation

Add a zero-address guard in both `parseCallResult` and `parsePermissionlessCallResult` before storing `CLPoolAddr`:

```go
for i := range clRes.NodeIds {
    if common.EmptyAddress(clRes.ClPools[i]) {
        logger.Error("CLRegistry returned zero CLPoolAddr, skipping", "nodeId", clRes.NodeIds[i])
        continue  // or return nil, staking.ErrCLRegistryResult
    }
    clStakingInfos[i] = &staking.CLStakingInfo{
        CLNodeId:        clRes.NodeIds[i],
        CLPoolAddr:      clRes.ClPools[i],
        CLStakingAmount: ...,
    }
}
```

Additionally, add a defensive check in `assignStakingRewards`, `assignStakingRewardsFlex`, `specWithProposerAndFunds`, and `specWithProposerAndFundsFlex` before calling `IncRecipient` or writing to `alloc`:

```go
if !common.EmptyAddress(cn.CLStakingInfo.CLPoolAddr) {
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
} else {
    // fall back: give clAmount to the CN reward address
    alloc[cn.RewardAddr].Add(alloc[cn.RewardAddr], clAmount)
}
```

---

### Proof of Concept

1. Deploy a CLRegistry mock that returns `address(0)` as `clPools[0]` for a validator that is otherwise valid (non-zero `nodeId`, non-zero `stakingAmount`).
2. Activate Prague hardfork; the staking module calls `MultiCallDPStakingInfo` and stores `CLPoolAddr = address(0)` in `CLStakingInfo`.
3. `consolidateNodes()` attaches this `CLStakingInfo` to the consolidated node.
4. `assignStakingRewards` computes `clAmount > 0` and writes `alloc[address(0)] = clAmount`.
5. `FinalizeState` calls `state.AddBalance(address(0), clAmount)`.
6. Verify: `state.GetBalance(address(0))` grows by `clAmount` each block; the CL pool operator's balance never increases.
