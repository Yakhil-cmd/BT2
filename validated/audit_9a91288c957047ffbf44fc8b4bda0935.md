Webhook signature is verified against the organization named in `repository.owner.login`, while the actual write target is resolved from the unrelated `repository.full_name` field - allowing cross-organization stack/commit injection - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the inbound HMAC signature against using `repository_owner`, derived purely from the JSON body the caller supplies (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). But the actual mutation performed by every webhook handler (`Shipit::Webhooks::Handlers::Handler#stacks`, used by `PushHandler` and others) resolves the target `Repository`/`Stack` from a *different* field in the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Because Shipit supports multiple GitHub organizations configured side-by-side in `secrets.github` (see `lib/shipit.rb#github_app_config`), an attacker who legitimately controls one configured organization (and thus knows/can compute a valid signature with that organization's `webhook_secret`) can forge a payload whose `repository.owner.login` names their own org (so `verify_signature` picks their own webhook secret and passes) while `repository.full_name` names a repository belonging to a completely different, victim organization also hosted on the same Shipit instance.

### Finding Description
- `verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) does:
  ```ruby
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ```
  where `repository_owner` (line 59-62) is:
  ```ruby
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
  ```
  This value is taken directly from the untrusted request body and used only to pick which per-organization `webhook_secret` (`lib/shipit/github_app.rb#verify_webhook_signature`) HMAC-verifies the raw POST bytes.
- Once verification succeeds, `WebhooksController#create` dispatches the full raw JSON to `Shipit::Webhooks.for_event(event)` handlers, e.g. `PushHandler#process` (app/models/shipit/webhooks/handlers/push_handler.rb):
  ```ruby
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
  ```
  `stacks` is defined in the shared base class `Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38):
  ```ruby
  def stacks
    @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
  end

  def repository_name
    payload.dig('repository', 'full_name')
  end
  ```
  This is a completely independent lookup from `repository_owner`; nothing re-validates that `full_name`'s owner segment matches the organization whose secret validated the signature.
- The binding that should hold is: `organization authenticated (repository_owner used for signature key selection) == organization whose repository is written (owner segment of repository.full_name used to select Repository/Stack)`. The engine never enforces this equality — it treats the two fields as independent, attacker-supplied values within the same JSON body.
- Concretely: assume Shipit is configured (as documented, `docs/setup.md`, `config/secrets.development.shopify.yml`) for two organizations, `org-attacker` and `org-victim`, each with its own GitHub App and `webhook_secret`. An attacker who administers `org-attacker`'s GitHub App knows `org-attacker`'s `webhook_secret` (they set it themselves when installing their own app, a normal unprivileged step in a multi-tenant Shipit setup — no access to Shipit sessions, `org-victim`'s repo, or `org-victim`'s secrets is required). They can POST to `/webhooks` a `push` event body where:
  - `repository.owner.login = "org-attacker"` (drives secret selection ⇒ signature validates)
  - `repository.full_name = "org-victim/some-repo"` (drives the actual `Repository.from_github_repo_name` lookup and subsequent `stack.sync_github`)

  `verify_signature` succeeds because it HMACs with `org-attacker`'s secret, which the attacker legitimately possesses. The dispatched `PushHandler` then finds and mutates `org-victim`'s `Stack` (queues `GithubSyncJob`, which fetches commits `stack.github_commits` using `org-victim`'s configured GitHub API credentials and inserts them via `stack.commits.create_from_github!`), entirely under an identity (org-victim) the attacker never authenticated as.

### Impact Explanation
This breaks the binding "GitHub organization whose webhook secret authenticated the request" == "GitHub organization/repository whose Shipit `Stack` state is written," letting an attacker who controls any one organization configured on a shared/multi-tenant Shipit instance forge events (push, status, check_suite, pull_request lifecycle events, etc., since every handler shares the same `Handler#stacks`/`repository_name` resolution) against arbitrary other organizations' stacks. Depending on the event this can trigger unwanted `GithubSyncJob` fetches, spurious commit ingestion, forced archive/unarchive of review stacks (`labeled_handler.rb`, `closed_handler.rb`), or manipulation of merge/CI status bookkeeping for a victim's stack the attacker has no legitimate relationship with — a cross-repository/cross-tenant write performed without proper authentication of the acting organization.

### Likelihood Explanation
Exploitability requires only that the deployment configure more than one GitHub organization (a supported, documented feature — `Shipit.github_organizations`, `docs/setup.md`), and that the attacker control (administer) at least one of those organizations' GitHub Apps — a normal, low-privilege position for any org onboarded to a shared Shipit instance, not requiring access to the victim org, a Shipit session, or an API token. Crafting the forged payload with mismatched `owner.login` vs `full_name` requires no special tooling beyond computing an HMAC-SHA1 with a secret the attacker already knows.

### Recommendation
After verifying the signature, ensure the organization used for verification (`repository_owner`) is authoritative for the entity being mutated: either derive the target repository from the same trusted `repository_owner`/organization context rather than trusting `payload.dig('repository','full_name')` independently, or explicitly assert (before dispatching to handlers) that `repository.full_name`'s owner segment matches `repository_owner`, rejecting the webhook (422) on mismatch.

### Proof of Concept
1. Configure Shipit (per `docs/setup.md`) with two orgs in `secrets.github`: `org-attacker` (attacker-administered GitHub App, attacker knows its `webhook_secret`) and `org-victim` (has an existing `Stack` tracking `org-victim/some-repo`).
2. Attacker builds a `push` webhook JSON body (matching the shape validated by `PushHandler#params`, e.g. `ref`, `after`) with:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "org-attacker" },
       "full_name": "org-victim/some-repo"
     }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker webhook_secret, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push` and the above signature.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-attacker")` and validates successfully using the attacker's own known secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("org-victim/some-repo")`, matches `org-victim`'s stack, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, queuing a `GithubSyncJob` and mutating `org-victim`'s data — despite the attacker never having proven any relationship to `org-victim`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
