### Title
Webhook signature verification key-selection uses an unauthenticated payload field, allowing cross-organization stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to use for HMAC verification from a field inside the still-unauthenticated request body, then hands the *entire* raw body (including a different, independently-attacker-controlled field) to the handlers that decide which `Stack`/`Repository` to act on. Because the “org selector” field and the “target repository” field are two independent JSON keys inside the same signed payload, an attacker who legitimately controls the webhook secret for *one* configured GitHub organization can still get a signature accepted while making the actual handler operate on a `Stack` belonging to a *different* organization/repository present in the same Shipit instance.

### Finding Description
`verify_signature` in [1](#0-0)  does:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON body *before* the signature has been validated. It is used purely to look up which per-organization `webhook_secret` (in a multi-org `config/secrets.yml` deployment, see [3](#0-2) ) should be used to check the HMAC in `GithubApp#verify_webhook_signature` [4](#0-3) .

Once the signature check passes, `create` dispatches the *same raw body* to a handler [5](#0-4) . Handlers such as `PushHandler` resolve the target `Stack` from a **different** JSON field, `repository.full_name`:

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [6](#0-5) 

`repository.owner.login` (used to *select the verification key*) and `repository.full_name` (used to *select the acted-upon repository/stack*) are two unrelated keys of the same attacker-supplied JSON object; nothing in the engine enforces that `full_name` is prefixed by `owner.login`. A real GitHub-generated payload always keeps them consistent, but this controller/handler pair never actually checks that consistency — it only checks that *some* org's secret can validate the whole raw body.

The equality that should hold, but does not, is:

`organization whose webhook_secret authenticated the request == organization that owns the repository/stack the handler mutates`

An attacker who controls (or has leaked/guessed) the `webhook_secret` for **any one** GitHub organization configured on the Shipit instance (e.g., their own org with the Shipit GitHub App installed) can craft a payload where `repository.owner.login` equals that known organization (so `Shipit.github(organization: ...)` picks the secret they know and the HMAC verifies), while `repository.full_name` names an arbitrary, *different* organization/repository already tracked as a `Stack` in this same Shipit deployment. `PushHandler` (and any other handler resolving stacks via `Repository.from_github_repo_name`) will then act on that unrelated stack, e.g. enqueueing `GithubSyncJob` for it [7](#0-6) [8](#0-7) .

### Impact Explanation
This breaks the “organization that authenticated versus the repository that is written” binding. Forcing an out-of-band `GithubSyncJob`/status update on an arbitrary stack the attacker has no legitimate relationship with is at minimum an unauthenticated-organization-boundary crossing of trust; depending on which handler is targeted (e.g. `StatusHandler` writing forged CI statuses to a commit, or `PushHandler` triggering resyncs that can feed into continuous-deployment logic), it can influence deploy-readiness signals (CI status, commit tracking) for a stack that belongs to an organization the attacker was never authorized to touch. I was not able to fully trace, within the remaining budget, whether this can be escalated all the way to an actual unauthorized `deploy`/`merge` execution (that would require confirming `continuous_deployment` triggers purely from `Commit#create_status_from_github!` state without further gating I did not fully verify) — that part is uncertain and should be validated further before treating the impact as “Critical: unauthorized deploy.” As far as the engine code shown, the concretely provable impact is an authenticated-org-vs-acted-repository mismatch that lets a low-privilege operator of one Shipit-integrated org tamper with commit statuses / force resyncs of a stack belonging to a different org.

### Likelihood Explanation
The prerequisite is realistic only in deployments using the documented multi-organization `secrets.yml` layout (several distinct GitHub orgs, each with its own `webhook_secret`, sharing one Shipit instance) — a configuration the project explicitly documents and supports [3](#0-2) . Any party that legitimately administers the GitHub App for one of those organizations (not the target org) can exploit this without needing the target org's secret, a Shipit session, or an `ApiClient` token, since `/webhooks` is unauthenticated apart from the HMAC check.

### Recommendation
- Do not use an untrusted payload field to select the verification secret before the signature is validated. Bind the webhook endpoint (or a signed indicator) to a single known organization per configured secret, or verify the signature against *all* configured secrets and only accept if one matches, then independently verify that `repository.owner.login`/`organization.login` for the org whose secret matched is consistent with `repository.full_name` before dispatching to handlers.
- In `handler.rb`, cross-check that the resolved `Repository`'s owner matches the organization that successfully authenticated the request before enqueueing side effects.

### Proof of Concept
Given a Shipit instance configured with two organizations in `config/secrets.yml`, `orgA` (attacker-controlled webhook secret `secretA`) and `orgB` (victim org, with an existing `Stack` for `orgB/victim-repo` tracked in the same Shipit database):

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, raw_body)>` using the secret they legitimately hold for `orgA`.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC check passes because it was computed with `secretA` over this exact body [9](#0-8) .
4. `PushHandler#process` resolves stacks via `repository.full_name = "orgB/victim-repo"` [6](#0-5)  and enqueues `GithubSyncJob` for `orgB`'s stack, despite the request never being authenticated by anything belonging to `orgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
