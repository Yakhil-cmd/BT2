### Title
Path traversal in `gh release download` via unsanitized asset filename / `Content-Disposition` header allows writes outside `--dir` - ([File: pkg/cmd/release/download/download.go])

### Summary
`downloadAsset` and `destinationWriter.makePath` join a server-supplied filename directly into the destination directory without any path-confinement check, unlike the sibling `pkg/cmd/run/download` implementation which uses `internal/safepaths.Absolute.Join` to reject traversal. Both the asset `Name` field from the Releases API and the `filename` parameter parsed from the `Content-Disposition` header (for archive downloads) are attacker-controlled and reach `filepath.Join` unsanitized (aside from a single `filepath.Base` call on the Content-Disposition value only).

### Finding Description
In `downloadRun` (`pkg/cmd/release/download/download.go:196-208`), each `shared.ReleaseAsset.Name` from the Releases API is used verbatim as `downloadTarget.name` (`download.go:239-243`) and passed to `downloadAsset` (`download.go:300`). `dest.Check`/`dest.Copy` call `makePath`:

```go
func (w destinationWriter) makePath(name string) string {
	if w.file == "" {
		return filepath.Join(w.dir, name)
	}
	return w.file
}
``` [1](#0-0) 

`filepath.Join` calls `filepath.Clean`, which resolves `..` segments relative to `w.dir` but does not prevent the result from climbing above `w.dir` when the joined name contains enough `../` sequences (e.g. `name = "../../../../tmp/evil"` with `w.dir = "downloads"` cleans to a path outside `downloads`). Nothing calls `filepath.Base`, `safepaths.Absolute.Join`, or an `IsLocal`-style check on `name` before this join — contrast with `pkg/cmd/run/download/http.go`, which threads a `safepaths.Absolute` destination through `ghzip.ExtractZip` specifically to reject traversal (`internal/safepaths/absolute.go:38-57`), and `internal/zip/zip.go`, which does the same for artifact ZIP entries.

For the archive-download code path (`isArchive == true`, empty `fileName`), the server's `Content-Disposition` header is parsed and only `filepath.Base` is applied (`download.go:336-347`):
```go
if serverFileName, ok := params["filename"]; ok {
    fileName = filepath.Base(serverFileName)
}
``` [2](#0-1) 
`filepath.Base` strips directory components from a plain `../../evil` string, mitigating that specific vector, but it does not protect the far more directly exploitable `shared.ReleaseAsset.Name` path used for normal (non-archive) asset downloads, where `filepath.Base` is never applied at all.

An attacker who can publish a release in a repository the victim points `gh release download` at (their own public repo, or a repo where they can edit release asset metadata) controls the `name` field returned by the Assets API. Because `gh` uses that name directly as the on-disk filename, a name containing `../` sequences can cause `os.OpenFile` in `destinationWriter.Copy` (`download.go:416-454`) to create/overwrite a file outside `opts.Destination`.

### Impact Explanation
This allows arbitrary file write/overwrite on the victim's filesystem, constrained to paths reachable via directory traversal from the CWD/`--dir` target and to the privileges of the `gh` process. Depending on the victim's environment, this can be used to overwrite configuration files, shell profile scripts, or other files a subsequent process might execute, matching GitHub's bounty impact class of "file write outside the intended path" / "unexpected file system access."

### Likelihood Explanation
Preconditions are low: the attacker only needs to control (or set) a release asset's reported `name` on a repository (their own repo, a fork, or any repo where they can attach/edit a release asset) and get the victim to run `gh release download` against it — a common, expected workflow. Whether GitHub's actual Releases REST/GraphQL API server-side validates or rejects `/`/`..` characters in the asset `name` field is not verifiable from this repository alone; if the upstream API rejects such names, exploitability is blocked at the API layer despite the missing client-side check. This uncertainty should be validated against live GitHub API behavior, but the client-side code itself provides no defense-in-depth, which is inconsistent with the pattern already established in `pkg/cmd/run/download`.

### Recommendation
Sanitize/confine every filename before use in `destinationWriter.makePath`/`Copy`: apply `filepath.Base` to `shared.ReleaseAsset.Name` (as is already done for the Content-Disposition-derived name) and, more robustly, adopt the existing `internal/safepaths.Absolute.Join` pattern used in `pkg/cmd/run/download` to reject any joined path that escapes `opts.Destination`, regardless of source (asset `Name` or `Content-Disposition`).

### Proof of Concept
Go test sketch using `httpmock`:
```go
func TestDownloadRun_PathTraversalAssetName(t *testing.T) {
    reg := &httpmock.Registry{}
    reg.Register(
        httpmock.REST("GET", "repos/OWNER/REPO/releases/latest"),
        httpmock.JSONResponse(map[string]interface{}{
            "tag_name": "v1.0.0",
            "assets": []map[string]interface{}{
                {"name": "../../../../tmp/gh-traversal-poc", "url": "https://api.github.com/assets/1"},
            },
        }),
    )
    reg.Register(
        httpmock.REST("GET", "assets/1"),
        httpmock.StringResponse("pwned"),
    )
    // set opts.Destination = t.TempDir()/downloads, run downloadRun(opts)
    // assert.FileExists(t, filepath.Join(t.TempDir(), "..", "..", "..", "..", "tmp", "gh-traversal-poc"))
}
```
Expected (buggy) result: the file is written outside the `downloads` destination directory, at a path resolved by `filepath.Join` climbing past `opts.Destination`. A fixed implementation should return an error (e.g., a `PathTraversalError` analogous to `internal/safepaths.PathTraversalError`) instead of writing the file.
