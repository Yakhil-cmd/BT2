### Title
Webhook HMAC secret is selected using an unverified field of the same unsigned payload, allowing an org-secret holder to target a different repository's stack - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a webhook against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, not-yet-verified JSON body, then checks the HMAC signature against that same body with that secret.

### Finding Description
`verify_signature` derives the signing organization from attacker-controlled JSON before establishing trust in the payload: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves a `GithubApp` instance (and its `webhook_secret`) purely from `repository_owner`, and the multi-organization/multi-app configuration model (each org has its own independent `webhook_secret`) is demonstrated in the dummy secrets fixture: [3](#0-2) 

The HMAC comparison itself is generic and only proves "whoever sent this exact byte-for-byte body knows organization X's `webhook_secret`" — it does not prove that the repository named elsewhere in that same body (e.g., `repository.full_name`, used later by handlers such as the push handler to resolve which `Stack`/`Repository` record to act on) actually belongs to organization X: [4](#0-3) 

The equality this binding is supposed to preserve is:
`organization whose secret validated the signature == organization owning the repository the handler subsequently writes to`

Because both values come from the same attacker-supplied JSON body with no structural cross-check enforced in `WebhooksController`, and because `deliver`/handler dispatch happens on `params` parsed straight from `request.raw_post` after only this coarse check: [5](#0-4) 

an attacker who possesses (or controls) the `webhook_secret` for *any* organization configured in the running Shipit instance (e.g., they administer a small/test GitHub organization that was legitimately onboarded onto this Shipit install) can forge a signed delivery whose `repository.owner.login` matches their own org (satisfying `verify_signature`), while other repository-identifying fields in the same payload (e.g. `repository.full_name`, `repository.id`) point at a stack belonging to a different, unrelated organization/repository that they do not control. If push/status/check_suite handlers key off those latter fields to locate and mutate a `Stack` (as strongly suggested by `push_handler` enqueuing `GithubSyncJob` keyed to a specific `stack_id` derived from payload repository data, per test expectations), this results in cross-organization/cross-repository state changes using credentials scoped to a different org than the one being written to.

### Impact Explanation
If confirmed, this allows a possessor of one organization's webhook secret to trigger writes/syncs against a `Stack` belonging to a different repository/organization than the one whose secret was actually validated — a cross-repository write performed without the victim organization's own webhook secret ever being checked. This matches the Critical-tier "cross-repository writes" impact class.

### Likelihood Explanation
Exploitation requires the attacker to already hold a valid `webhook_secret` for *some* organization onboarded to the Shipit instance (not necessarily the victim's). In a multi-tenant Shipit deployment supporting several GitHub Apps/organizations (as the codebase explicitly supports via `Shipit.github(organization:)` and per-org config), this is a realistic scenario without requiring Shipit session credentials, `ApiClient` tokens, or GitHub App private keys — only knowledge of one org's webhook secret, which is a lower-privilege credential than what the "OUT OF SCOPE" exclusions rule out.

### Recommendation
Do not select the verification secret from a field embedded in the same unverified payload being checked. Instead, verify the signature using a keying scheme tied to the actual HTTP endpoint/App installation (e.g., a distinct webhook path or App ID header established out-of-band per organization), and once verified, cross-validate that all repository-identifying fields used later by handlers (`full_name`, `id`, `owner.login`) are mutually consistent and belong to the same organization whose secret validated the request.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker controls `OrgA` (a legitimate, low-trust organization onboarded to the same Shipit instance) and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a JSON body for a `push` event where `repository.owner.login = "OrgA"` (to steer `verify_signature`'s org lookup to `OrgA`), but `repository.full_name = "OrgB/victim-repo"`.
4. Attacker computes `sha1=HMAC(OrgA_webhook_secret, body)` and sends it as `X-Hub-Signature`.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` and validates the signature successfully against `OrgA`'s secret.
6. The push handler then processes the body based on `repository.full_name`, resolving and acting on `OrgB/victim-repo`'s `Stack` (e.g., enqueuing `GithubSyncJob` for that stack) — despite `OrgB`'s webhook secret never having been checked.

**Caveat on verification completeness**: I could not directly inspect `push_handler.rb`'s exact field usage for stack resolution due to a tool failure, so step 6 is inferred from the `GithubSyncJob` enqueue test behavior and the general handler dispatch flow rather than a direct line-level read of that handler. I recommend a Devin session with full file access to confirm exactly which payload fields `push_handler.rb` (and other handlers) use to resolve the target `Stack`, in order to fully close this proof.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
