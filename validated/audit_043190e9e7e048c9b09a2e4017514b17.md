## Finding

### Title
Missing authorization check on the `permission` account in `initialize_with_permission` allows bypass of the permissioned pool-creation gate - (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
`InitializeWithPermission` includes a `permission` account in its Anchor accounts struct, derived from a PDA seeded on the caller's own key, seemingly to gate who is allowed to create a "permissioned" pool. However, the instruction handler never reads or validates any field of that account — it is loaded and then completely ignored. This mirrors the Mattermost Zoom `askPMI` bug class (CWE-862, Missing Authorization): an authorization-looking account/parameter is present in the request but the handler fails to actually verify caller identity/entitlement against it before performing the privileged action.

### Finding Description
The `permission` account is declared purely as a PDA existence check: [1](#0-0) 

But nowhere in `initialize_with_permission` is `ctx.accounts.permission` referenced or its state inspected: [2](#0-1) 

The only account required to sign is `payer`, and `creator` is an entirely unchecked, non-signing account whose key is written straight into `pool_state.pool_creator` with no relation established to `payer`, to `permission`, or to any signature: [3](#0-2) [4](#0-3) 

Because the handler body never enforces any property of the `permission` account (e.g., an "is-approved"/"active" flag, an expiry, or a match against `creator`), the account's presence in the instruction is decorative. Any caller who can satisfy the PDA-existence constraint (which only requires an account owned by this program at that seed, not a specific "approved" state) can invoke this privileged, permission-gated pool-creation path and freely assign an arbitrary, unverified `creator` identity to the new pool — exactly the class of bug in the advisory: an endpoint that is supposed to validate the caller's identity/entitlement before performing a privileged write (starting a Zoom meeting as another user / overwriting a post as another user) but instead trusts caller-supplied identifiers without validation.

### Impact Explanation
This breaks the access-control invariant that `initialize_with_permission` is meant to enforce (as opposed to the open `initialize` path). Since `pool_creator` is later used as the trust anchor for `CollectCreatorFee`'s signer check and `CollectCreatorFeePermissionless`'s payout target: [5](#0-4) [6](#0-5) 

any unauthorized actor can construct permission-gated pools (with attacker-chosen `creator_fee_on` mode and attacker-chosen `pool_creator`) that the protocol's governance/admin logic assumed could only be created by permission-holders vetted via `create_permission_pda`. This is an unauthorized privileged effect on-chain (bypass of an access-control gate), matching the CWE-862 classification of the reference advisory.

### Likelihood Explanation
High reachability: `initialize_with_permission` is a single, permissionless-to-call instruction (only `payer` must sign) reachable directly from an attacker-submitted transaction with fully attacker-chosen `creator`, `amm_config`, and other accounts, requiring only that a `Permission` PDA at the derived seed exists and is owned by the program — no specific "approved" content is checked.

### Recommendation
- In `initialize_with_permission`, explicitly validate the loaded `permission` account's state before allowing pool creation (e.g., `require!(ctx.accounts.permission.approved, ErrorCode::NotApproved)`, and/or tie `creator`/`payer` identity to the fields actually stored in `Permission`).
- Ensure the `creator` field is cryptographically bound to the `permission` grantee (e.g., require `creator.key() == permission_grantee_stored_in_state`, or require `creator` to sign) rather than accepting an arbitrary `UncheckedAccount`.

### Proof of Concept
1. Have any `Permission` PDA exist at seeds `[PERMISSION_SEED, payer.key()]` owned by the program (whatever minimal state `create_permission_pda` writes).
2. Call `initialize_with_permission` as `payer`, passing an arbitrary `creator` pubkey (not required to sign, not validated).
3. The handler proceeds without ever inspecting `ctx.accounts.permission`'s contents, creating a fully functional permissioned pool with `pool_state.pool_creator` set to the attacker-chosen `creator`, regardless of whether the underlying `Permission` record actually grants creation rights. [2](#0-1) 

**Caveat:** I could not fully inspect `programs/cp-swap/src/states/permission.rs` or `create_permission_pda.rs`/`close_permission_pda.rs` within this session's tool budget, so I cannot confirm whether `Permission`'s account discriminator/type alone (without field-level checks) was intended by the developers to be a sufficient gate, or whether a field-level check was simply dropped. The core, verifiable fact is that `initialize_with_permission`'s handler body never reads any field of `ctx.accounts.permission`, which is the concrete root cause supporting this finding.
