### Title
Forged CI status injection via cross-organization webhook signature confusion enables unauthorized deploy approval - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook's HMAC signature against, based on a payload field (`repository.owner.login` or `organization.login`), but the signature itself covers the *entire raw request body*, including an independent field, `repository.full_name`, that `StatusHandler` (and other handlers) actually acts upon. Because nothing binds "the organization whose secret validated this request" to "the repository/commit the handler mutates," an attacker who legitimately controls one organization's GitHub App installation on a shared Shipit instance can forge a valid signature (using their own known `webhook_secret`) for a payload whose `sha` targets a commit belonging to a completely different, victim organization's stack.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and fetches the corresponding app config to validate the signature: [2](#0-1) [3](#0-2) . This binds "signature valid" to "some organization configured in `Shipit.github`," not to "the specific repository/commit the handler will touch."

`StatusHandler#process` then looks up commits **globally by SHA only**, with no repository or stack scoping whatsoever: [4](#0-3) . The `params` schema for this handler requires only `sha`, `state`, and optional fields — no `repository` field is required or checked at all: [5](#0-4) .

Given a Shipit instance configured for multiple organizations (a documented, supported configuration): [6](#0-5) , an attacker who is an admin of any one of those organizations knows that organization's `webhook_secret` (a value they themselves configured when creating their GitHub App, per setup docs) [7](#0-6) . They can craft an arbitrary POST body with `X-Github-Event: status`, set `repository.owner.login` (or `organization.login`) to their own org so `repository_owner` resolves to their own org's secret, and sign the whole raw body with `OpenSSL::HMAC` using that known secret — exactly the mechanism used in `GitHubApp#verify_webhook_signature`: [8](#0-7) . The signature verifies successfully because it's mathematically valid for the exact bytes sent, even though the `sha` field inside that body targets a commit that belongs to an unrelated stack from a different, victim organization the attacker does not control.

This forged status is then applied via `Commit#create_status_from_github!`, updating the commit's status: [9](#0-8) . `Commit#deployable?` treats a commit as deployable once it reaches `success?` and is unblocked: [1](#0-0) , and if the target stack has `continuous_deployment?` enabled, `schedule_continuous_delivery` will trigger an actual autonomous deploy job for the forged-successful commit: [10](#0-9) .

This directly parallels the reported RocketPool bug class: a value is authenticated/recorded (here, "which org's secret validated the request") but a second, semantically-linked value that the code actually acts upon (here, "which repository/commit gets the status applied") is never cross-checked against the first, breaking the equality `authenticated_organization == repository_being_written_to`.

### Impact Explanation
This is a High-severity issue: it allows an unauthenticated (with respect to the victim organization) attacker who only controls a different, low-trust organization on the same shared Shipit instance to write arbitrary commit-status state onto any stack/commit tracked by the instance. Combined with `continuous_deployment?`, this can escalate to triggering an unauthorized deploy of a commit that never actually passed the victim's real CI — matching the "unauthorized deploy" impact bucket.

### Likelihood Explanation
Likelihood depends on the deployment mounting Shipit for multiple GitHub organizations sharing one instance (a supported, documented configuration) and the attacker legitimately administering at least one of those organizations' GitHub App installations (so they know that org's `webhook_secret`). Within that documented multi-tenant setup, exploitation requires only crafting one raw HTTP POST with a self-computed HMAC — no other privilege is required.

### Recommendation
Bind the field used to select the verifying secret to the field(s) the handler actually mutates: require that `repository.full_name`'s owner matches `repository_owner` (or `organization.login`), and additionally scope `StatusHandler`'s (and any other handler's) commit/stack lookups to the repository/organization that authenticated the request, rather than trusting a globally-scoped `sha` (or other identifier) independent of the authenticated organization.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret`, per `docs/setup.md`'s multi-org config.
2. As an attacker admin, note `attacker-org`'s `webhook_secret` (it was manually configured, so it's known to the org owner).
3. Identify a target commit `sha` on a `victim-org` stack (e.g., visible via public Shipit UI or GitHub commit history).
4. Build a JSON body:
```json
{"sha":"<victim_commit_sha>","state":"success","repository":{"owner":{"login":"attacker-org"}}}
```
5. Compute `signature = "sha1=" + HMAC_SHA1(attacker_org_webhook_secret, raw_body)`.
6. `POST /webhooks` with headers `X-Github-Event: status`, `X-Hub-Signature: <signature>`, body from step 4.
7. `verify_signature` resolves `repository_owner` to `attacker-org`, validates successfully against `attacker-org`'s secret.
8. `StatusHandler` matches `Commit.where(sha: ...)` globally and creates a `success` status on the victim's commit, potentially unblocking/triggering deploy of that commit on `victim-org`'s stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
