### Title
Flash-position callback can execute a ready oracle governance operation and finalize debt against the stale cached price - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary
`flash_position` prefetches oracle prices before invoking the attacker-controlled receiver, but the callback can permissionlessly execute a ready governance operation against the price aggregator. Because `Context` retains the pre-callback price snapshot, post-callback collateral and solvency checks use stale valuation data even though the oracle configuration changed inside the same transaction. This is analogous to a check/use race: validation state is read, an external callback changes the referenced state, and the later risk decision uses the stale snapshot.

### Finding Description
`process_flash_position` loads the account, validates collateral declarations, and calls `prefetch_strategy_prices` before entering the receiver callback. `mint_and_forward` then mints pool debt and forwards the measured borrowed amount to the receiver. After `invoke_receiver` returns, the controller measures collateral receipts, deposits them through `process_deposit`, and calls `strategy_finalize` to apply the post-operation solvency gates.

The callback is intentionally arbitrary Wasm code. During that callback, the receiver can call `Governance::execute` with `executor = None`; governance explicitly permits anyone to execute an operation once it is ready. If the ready operation targets the price aggregator—for example, an oracle reconfiguration whose effect changes the relevant asset's valuation—the aggregator state changes while the flash-position call is still in progress.

The controller does not reread the changed oracle state. Its operation `Context` has already cached the required prices and pool indexes, so `strategy_finalize` and the health-factor/minimum-collateral checks continue to value the account using the pre-callback snapshot. Governance's permissionless executor path is at `contracts/governance/src/api.rs:53-67`, while the vulnerable ordering is at `contracts/controller/src/strategies/flash_position.rs:113-154`.

### Impact Explanation
An attacker can create or extend a leveraged account with debt priced against an obsolete oracle answer after a governance-approved oracle change has already executed in the same transaction. If the old cached valuation is more favorable than the new configuration's resulting price, the account can pass collateral and health-factor checks despite being undercollateralized under the live oracle state. The borrowed assets are already paid to the receiver and remain with the attacker, while the protocol is left with artificially valued collateral and potential bad debt.

This is theft of pool funds through undercollateralized borrowing and can also produce protocol insolvency if the resulting debt exceeds the real collateral value. The attack is bounded by the existence of a ready oracle-changing operation and the magnitude of the valuation change.

### Likelihood Explanation
The path is reachable by an unprivileged account that controls both the `flash_position` caller and receiver. The only external precondition is a governance operation affecting the relevant price configuration being in `Ready` state; governance allows `executor = None`, so no privileged signature is needed at execution time. The receiver can execute it from `execute_flash_position` after receiving the borrowed funds and before the controller's final risk checks.

This is not a generic token-semantics or reentrancy issue: the state change occurs in a separate governance/price-aggregator contract, so the controller's flash guard and Soroban same-contract reentry restriction do not block it.

### Recommendation
Treat governance-executed oracle changes as state that must invalidate the operation context. Options include:

- Record a price-aggregator configuration/version epoch before the callback and require it to be unchanged before final risk checks.
- Recreate or explicitly invalidate `Context` price/index caches after `invoke_receiver` and before collateral valuation/finalization.
- Add a controller-visible oracle configuration epoch or nonce incremented by every aggregator configuration mutation.
- As a defense in depth, document or enforce that receiver callbacks cannot invoke governance by routing governance executions through a state transition visible to the controller and checked at finalization.

The fix should ensure that the price used for admission and the price used for final solvency cannot straddle an oracle reconfiguration.

### Proof of Concept
1. Governance has a ready operation that changes the oracle configuration for collateral asset `C`, lowering its resulting USD price.
2. Attacker calls `Controller::flash_position` with:
   - `caller = attacker_contract`
   - `account_id = 0`
   - `debt = D`
   - `receiver = attacker_contract`
   - `collaterals = [(C, min_amount)]`
3. `prefetch_strategy_prices` caches the still-current favorable price for `C`.
4. The controller mints `D` debt to itself and forwards the measured borrowed amount to the receiver.
5. Inside `execute_flash_position`, the receiver calls `Governance::execute(None, price_aggregator, ..., predecessor, salt)` and executes the ready oracle-change operation.
6. The receiver buys or supplies enough `C` under the new price to transfer `min_amount` to the controller.
7. After callback return, the controller measures the `C` balance increase and deposits it, but `strategy_finalize` still uses the pre-callback cached favorable `C` price.
8. The account passes the stale health-factor check even though it is undercollateralized under the now-live oracle configuration. The attacker retains borrowed `D`, while the pool holds a riskier debt position than the final checks intended.
