### Title
`StatusHandler#process` looks up `Commit.where(sha: params.sha)` globally instead of scoping through `stacks`, allowing status forgery on another tenant's stack — (`File: app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Handler#stacks`/`Handler#repository_name` exist specifically to scope webhook processing to the stacks that belong to the repository named in the payload, and `CheckSuiteHandler#process` correctly uses `stacks.where(branch: ...)` for this purpose. `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` across the *entire* `commits` table with no repository/stack filter, so a genuinely signed `status` webhook for repository A can write a `Status` onto a `Commit` belonging to a completely unrelated stack B whenever the two share a commit SHA (e.g. via a fork).

### Finding Description
Binding checked: "presence of `stacks` scoping in `StatusHandler#process`" == "presence of `stacks` scoping in `CheckSuiteHandler#process`".

- `Handler#stacks` / `Handler#repository_name`: [1](#0-0) 
- `CheckSuiteHandler#process` (uses `stacks`): [2](#0-1) 
- `StatusHandler#process` (does NOT use `stacks`, queries `Commit` unscoped): [3](#0-2) 

LHS = false (no `stacks` call in `StatusHandler#process`), RHS = true (`CheckSuiteHandler#process` calls `stacks.where(branch: ...)`). The two sides diverge, confirming the omission is specific to `StatusHandler`, not a systemic `Handler` base-class defect — `Handler` provides the scoping primitive correctly, but `StatusHandler` never calls it.

Root cause / exploit path: `WebhooksController#create` dispatches the raw JSON payload to whichever handler is registered for the `X-Github-Event` header, after `verify_signature` checks the signature against `Shipit.github(organization: repository_owner)` for the *organization named in the payload* [4](#0-3) . This means the signature only proves the webhook genuinely originates from GitHub for the repository/org identified in `payload['repository']['owner']['login']` — it says nothing about which `Commit`/`Stack` records the `sha` in the payload should touch.

`StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This is a global, cross-tenant lookup by `sha` alone [3](#0-2) . `Commit#create_status_from_github!` unconditionally persists the incoming state/description/target_url as a `Status` row and fires `Hook.emit(:commit_status, ...)`/`schedule_merges` side effects on whatever stack that commit belongs to [5](#0-4) [6](#0-5) .

Attack: an attacker who owns/forks a public repository that shares commit history (and therefore SHA1s) with a repository tracked by a Shipit stack can push/attach the GitHub App used by Shipit to their own fork (a legitimate, self-owned webhook source), then create/update a commit status via the GitHub API on a commit in their fork whose SHA matches a commit already ingested into the target stack (typical for shared upstream history before the fork point, or a cherry-picked/rebased commit). GitHub sends a correctly-signed `status` event naming the attacker's own repository; `verify_signature` passes because the signature is validated against the attacker's own organization/app config, not against the specific commit's owning stack. `StatusHandler` then matches the SHA against *any* stack's commit table and writes the forged status/state onto the victim stack's commit, potentially flipping `deployable?`/triggering `schedule_merges` or blocking/unblocking deploys.

`Handler#repository_name`/`#stacks` exist precisely to prevent this by scoping the lookup to `Repository.from_github_repo_name(repository_name)&.stacks`, and `CheckSuiteHandler` demonstrates the correct pattern is trivially available; `StatusHandler` simply never applies it.

### Impact Explanation
A payload legitimately signed for repository A can create/alter a `Status` record on a `Commit` belonging to a stack tracking a different repository B, influencing B's deployability/merge/continuous-delivery logic (`Commit#add_status`, `#schedule_continuous_delivery`, `stack.schedule_merges`) — this is a cross-tenant "payload for one repository mutating another's stack/commit" condition, matching the Critical impact category. It is repeatable against any stack whose tracked repository shares commit SHAs with an attacker-controlled repository (common for forks/mirrors), and the attacker needs no Shipit session, API token, or secret — only the ability to legitimately emit a signed webhook from their own GitHub repo/org.

### Likelihood Explanation
Requires: (1) Shipit's GitHub App/webhook integration is installable or already installed on an org the attacker controls (so they can emit a genuinely-signed webhook), and (2) a SHA collision between the attacker's repo and the victim stack's repo, which is realistic for forks, mirrors, or cherry-picked commits rather than a cryptographic SHA1 break. Given those, the attack is a normal GitHub API call (create/update commit status) with no elevated privileges, fully repeatable and scriptable against any matching SHA.

### Recommendation
Scope `StatusHandler#process` through `stacks` the same way `CheckSuiteHandler` does, e.g. iterate `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` (or `Commit.where(sha: params.sha, stack: stacks)`), so a status webhook can only mutate commits belonging to stacks whose tracked repository matches `payload['repository']['full_name']`.

### Proof of Concept
Under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (not shown/covered by existing tests in the index):
```ruby
test "process does not scope by stacks/repository_name" do
  source = Shipit::Webhooks::Handlers::StatusHandler.instance_method(:process).source
  refute_match(/\bstacks\b/, source)
end

test "sibling CheckSuiteHandler scopes by stacks" do
  source = Shipit::Webhooks::Handlers::CheckSuiteHandler.instance_method(:process).source
  assert_match(/\bstacks\b/, source)
end

test "status webhook for repo A can write a status onto repo B's commit sharing the same sha" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:example) # different repository
  shared_sha = "deadbeef" * 5
  commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus))

  payload = {
    "repository" => { "full_name" => stack_a.github_repo_name },
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci"
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert commit_b.reload.statuses.exists?(state: "success", context: "ci")
end
```
This demonstrates that `StatusHandler` writes a status onto `stack_b`'s commit using a payload that only names `stack_a`'s repository, confirming the cross-tenant mutation and the asymmetry versus `CheckSuiteHandler`'s correct `stacks` scoping.
