### Title
Webhook signing-organization selection is decoupled from the organization whose team membership is mutated — unauthenticated escalation into `Shipit.github_teams` authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify a webhook against using `repository_owner`, a value read straight out of the unauthenticated, attacker-supplied JSON body [1](#0-0) . `repository_owner` prefers `params.dig('repository','owner','login')` and only falls back to `params.dig('organization','login')` when `repository` is absent [2](#0-1) . Meanwhile `MembershipHandler` (invoked for the `membership` event) reads `payload['organization']['login']` and `payload['team']` independently to find/create a `Team` and add/remove `Membership` records, without any coupling back to `repository_owner` — this mirrors the reference bug class, where a value the code trusted for a security check (native-token balance lookup) was decoupled from the value the code actually operated on (the native asset itself). Here, the *organization whose secret authorizes the request* and the *organization whose membership state is mutated* are two independently-controlled fields in the same POST body, so they can be made to diverge.

### Finding Description
`GitHubApp#verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for the organization resolved by `Shipit.github(organization: repository_owner)`: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations sharing one installation, each with its own (optional) `webhook_secret` — see the multi-org secrets fixture where both orgs ship with `webhook_secret: # nil` [4](#0-3) . If any configured organization on a Shipit instance lacks a `webhook_secret`, signature verification for that organization is a no-op.

An attacker with no credentials can POST directly to the public `/webhooks` endpoint (only gated by `verify_signature`, `check_if_ping`, `drop_unhandled_event` [5](#0-4) ) with a forged JSON body that:
1. sets `repository.owner.login` to the organization that has no `webhook_secret` configured — this makes `verify_signature` pick that org's (secret-less) `GitHubApp`, which auto-passes verification, and
2. sets `organization.login` (and `team`, `member`) to the *real, protected* organization whose teams gate `Shipit.github_teams` authorization.

`repository_owner` is used purely to pick the verification key; it plays no role in `MembershipHandler`'s logic, which acts solely on `payload['organization']['login']` to resolve/mutate the `Team`/`Membership` and on `payload['member']['login']` to resolve/create the `User` being added.

### Impact Explanation
`MembershipHandler` can be driven to append an arbitrary attacker-controlled `User` (auto-vivified from `member.login`) as a member of a `Team` belonging to the protected organization, via `Team#add_member` [6](#0-5) . `User#authorized?` grants full application access based purely on team membership in `Shipit.github_teams` [7](#0-6) , and this check gates the entire authenticated web UI (`force_github_authentication`) [8](#0-7) . This is exactly the listed High-severity impact: "escalation into `Shipit.github_teams` authorization" achieved with no session, no `ApiClient` token, and no privileged GitHub access — only an unauthenticated HTTP POST.

### Likelihood Explanation
The prerequisite (one configured organization in a multi-org Shipit instance without a `webhook_secret`, or an org whose secret is otherwise known/guessable) is a realistic misconfiguration explicitly permitted and documented by Shipit's own multi-org secrets format (`webhook_secret` is commented as optional in the fixture). No repository write access, GitHub App key, or TLS interception is required — only knowledge that such an org exists, which is discoverable by simply omitting a signature and observing whether a request succeeds. This is a plausible, deployable scenario for any multi-tenant Shipit install, though it depends on operator configuration rather than being universally exploitable against every install.

### Recommendation
Do not let the caller-supplied `repository.owner.login` (or `organization.login`) select the verification key while a *different* field in the same unauthenticated payload is used to determine what gets mutated. Concretely:
- Verify the webhook signature against **every** configured organization's secret (or at minimum, require a `webhook_secret` to be configured for all organizations, refusing unsigned/no-secret orgs by default) rather than trusting attacker-supplied `repository`/`organization` fields to pick which secret is authoritative.
- After signature verification succeeds against org X, ensure downstream handlers (e.g., `MembershipHandler`) only mutate state scoped to that same verified org X — i.e., bind the verified organization identity to the handler's `organization.login`/`repository.owner.login` values and reject payloads where they diverge.

### Proof of Concept
Assuming a Shipit instance configured with two organizations, `org-no-secret` (no `webhook_secret`) and `target-org` (protected, has `Shipit.github_teams` referencing one of its teams):

```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json
(no valid X-Hub-Signature required)

{
  "action": "added",
  "repository": { "owner": { "login": "org-no-secret" } },
  "organization": { "login": "target-org" },
  "team": { "id": 1, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/1" },
  "member": { "login": "attacker-github-login" }
}
```

- `WebhooksController#repository_owner` resolves to `"org-no-secret"` [2](#0-1) .
- `Shipit.github(organization: "org-no-secret").verify_webhook_signature(...)` returns `true` unconditionally because that org has no `webhook_secret` [9](#0-8) .
- `MembershipHandler` then processes the event using `payload['organization']['login'] == "target-org"`, creating/finding the `attacker-github-login` `User` and adding it to `target-org`'s `Deployers` team.
- The attacker's GitHub account now satisfies `User#authorized?` for `target-org`'s `Shipit.github_teams`, gaining full access to the Shipit web UI and its deploy/rollback/lock actions on that instance [7](#0-6) [8](#0-7) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def force_github_authentication

        redirect_to(Shipit::Engine.routes.url_helpers.github_authentication_path(origin: request.original_url))

      end
