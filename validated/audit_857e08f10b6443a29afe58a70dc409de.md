### Title
`StatusHandler` writes commit statuses without verifying the organization/repository the status belongs to matches the webhook that authenticated it - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
GitHub webhook signatures in this engine authenticate that a request came from *some* GitHub App installation for a given organization (`repository_owner`), but that binding is never propagated into how the payload's data is applied. `StatusHandler#process` looks up commits **purely by SHA, globally, across every stack/repository/organization in the Shipit instance**, and writes the attacker-supplied `state`/`description`/`target_url`/`context` onto whatever commit matches — regardless of whether that commit belongs to the organization whose signature was actually verified.

### Finding Description
The webhook signature check selects a per-organization secret using the `repository.owner.login` field of the payload: [1](#0-0) [2](#0-1) 

This only proves "this HTTP body was HMAC-signed by GitHub for organization X's installation" (or, if `webhook_secret` is left unset for that org, `verify_webhook_signature` returns `true` unconditionally): [3](#0-2) 

However, once verified, the event is dispatched to handlers that receive the entire raw `params` hash and are trusted to act on it: [4](#0-3) 

Most handlers correctly scope themselves to a `Repository`/`Stack` derived from `payload.dig('repository', 'full_name')`: [5](#0-4) 

But `StatusHandler` does not use that scoping at all — it resolves target records purely by commit SHA, with no repository/organization filter whatsoever: [6](#0-5) 

This is the direct analog of the Merkle-tree bug: the verified credential (the webhook HMAC / organization identity) is treated as authorizing an entire *tree* of data (any commit, in any repository, tracked anywhere in this Shipit instance), when it should only authorize the specific *leaf* (a commit that actually belongs to the organization/repository that was cryptographically verified). The equality the code implicitly — and wrongly — assumes is:
`organization_whose_signature_was_verified == organization_owning_commit(params.sha)`
There is no code path that enforces this equality; `Commit.where(sha: params.sha)` will match a commit belonging to **any** stack, including stacks owned by a completely different, unrelated organization.

### Impact Explanation
Commit statuses gate deploy safety decisions in this engine (`Stack#required_statuses`, `blocking_statuses`, delegated from `Commit`): [7](#0-6) 
An organization/repository whose own GitHub App installation is registered on a shared Shipit instance (a supported, documented multi-org configuration, see `config/secrets.development.shopify.yml` listing multiple orgs each with their own `webhook_secret`) can send a legitimately-signed `status` webhook for their own repository, but with a `sha` value chosen to match a commit that belongs to a **different** organization's stack tracked by the same Shipit instance. Since git SHAs for public commits are discoverable (e.g. via the Shipit UI itself, or the target repo's public GitHub page), the attacker does not need any secret belonging to the victim organization. The forged status (e.g. `"state": "success"`) gets written onto the victim's commit, which can misrepresent CI state used to gate an unauthorized deploy of that commit in the victim's stack — a cross-repository trust violation without ever needing the victim's own webhook secret.

### Likelihood Explanation
Requires: (1) the attacker controls or operates a GitHub App / repository that is already legitimately configured as one of the organizations on a shared Shipit instance (a normal, documented multi-tenant Shipit deployment), and (2) knowledge of a target commit SHA in another organization's stack tracked by the same instance (public and often directly visible in the Shipit UI). No access to the victim's secrets, tokens, or GitHub credentials is required. This is a realistic configuration for organizations sharing one Shipit deployment, which the project's own documentation explicitly supports.

### Recommendation
`StatusHandler` (and any other handler that resolves records without going through `Handler#stacks`/`repository_name`) must scope its `Commit` lookup to the stack(s) belonging to the repository named in `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`. More generally, every webhook handler must derive its target records strictly from the same `repository.full_name` binding that the signature-selection logic (`repository_owner`) used, closing the gap between "who signed this" and "what this writes."

### Proof of Concept
1. Configure two organizations on one Shipit instance, `orgA` (attacker-controlled, has valid `webhook_secret`) and `orgB` (victim, unrelated stack tracked on the same instance).
2. Attacker learns a commit SHA `S` that exists in a stack owned by `orgB` (e.g. from the public Shipit dashboard).
3. Attacker sends a `status` webhook to `/webhooks`, signed with `orgA`'s webhook secret, with body:
```json
{
  "sha": "S",
  "state": "success",
  "context": "ci/forced",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" }
}
```
4. `verify_signature` passes because the HMAC is valid for `orgA`.
5. `StatusHandler#process` executes `Commit.where(sha: S)`, finds the commit belonging to `orgB`'s stack (not `orgA`'s), and calls `commit.create_status_from_github!(params)`, writing a forged `"success"` status onto a commit owned by an unrelated organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
