### Title
Cross-repository CI status forgery via organization/repository binding mismatch in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate a webhook against using the `repository.owner.login` (or `organization.login`) field taken from the **unauthenticated** request body itself. Once that check passes, the full, un-scoped payload is handed to `Shipit::Webhooks::Handlers::StatusHandler`, which updates commit statuses purely by matching `sha` across the *entire* `commits` table — with no re-validation that the commit belongs to the organization/repository that was actually authenticated. Combined with the engine's explicitly supported "no secret configured" mode (`return true unless webhook_secret`), this lets an attacker who only needs one organization with an unset `webhook_secret` forge a passing CI status on a commit belonging to a completely different, properly-secured stack/organization, defeating the CI-gating that guards automatic deploys and PR merges.

### Finding Description
`verify_signature` derives the organization used to authenticate the webhook entirely from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves per-organization config from `secrets.github`, and `GitHubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as automatic success: [3](#0-2) 

This "no secret" mode is a first-class, documented configuration, not a misconfiguration edge case — the shipped example secrets templates and setup docs literally present `webhook_secret: # nil` as the value to use when one isn't configured, and describe running multiple independent GitHub App/organization configs side by side: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (for whichever organization the attacker chose to spoof via `repository.owner.login`), the same raw payload is dispatched to every registered handler for the event, unchanged: [6](#0-5) 

`StatusHandler` never consults `repository` at all — it matches solely on `sha` against the global `Commit` table and writes a status for every match: [7](#0-6) 

While most other handlers do scope themselves via `payload.dig('repository', 'full_name')` (see the base `Handler#repository_name`): [8](#0-7) 

`StatusHandler` is the outlier that bypasses this scoping entirely, so the binding **"organization that authenticated" == "repository that is written"** is broken twice over: (1) the org used to pick/bypass the HMAC check is attacker-declared and independent of any specific repository, and (2) the handler that actually mutates state ignores repository scoping altogether.

**Equality broken:** `organization_used_for_signature_check(payload) == organization_owning(commit_being_mutated)` — before the attack this holds by construction for genuine GitHub-originated webhooks; after the attack, an attacker can make the left side equal any organization with a permissive (`nil`) `webhook_secret` while the right side is an arbitrary commit belonging to any other configured, fully-secured organization/stack.

### Impact Explanation
CI/commit statuses are the exact signal Shipit's continuous-deployment and merge-queue logic rely on to decide whether a commit/PR is safe to auto-deploy or auto-merge (`required_statuses`, `all_status_checks_passed?`, etc., see `app/models/shipit/deploy_spec.rb` and `app/models/shipit/merge_request.rb`). Forging a `success` status on a stack's head commit can flip Shipit's gating logic to "green," enabling an unauthorized automatic deploy or an unauthorized pull-request merge on a repository the attacker has no legitimate relationship with. This matches the required Critical impact category "an unauthorized deploy, rollback, or merge."

### Likelihood Explanation
Exploitation requires no Shipit session, API token, or GitHub credential — only that the deployment has at least one configured GitHub organization without a `webhook_secret` set, which is the exact configuration shown/shipped in this engine's own example secrets files and multi-organization setup documentation. Any instance following that documented pattern (e.g. while onboarding a low-stakes org) exposes every other, fully-secured org's commit statuses to forgery through the single public `/webhooks` endpoint.

### Recommendation
- Scope `StatusHandler` (and any other handler that doesn't already do so) to the repository identified in the payload, consistent with `Handler#repository_name`/`#stacks`, instead of matching `sha` globally across all commits.
- Bind signature verification to the specific repository being mutated rather than to an attacker-declared `organization` field, or reject webhooks whose `repository.owner.login` does not match the repository actually being written.
- Reconsider allowing `webhook_secret` to be unset (`return true unless webhook_secret`) in multi-organization deployments; at minimum, warn/refuse to boot when any organization in a multi-org config has no secret while others do.

### Proof of Concept
1. Deploy Shipit with the documented multi-organization config where `org-empty` has `webhook_secret: nil` and `org-victim` has a real secret protecting a real stack (per `docs/setup.md` "Using Multiple Github Applications").
2. Attacker learns (from the public Shipit UI or GitHub) the head commit SHA of a stack belonging to `org-victim`.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-head-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-empty" }, "full_name": "org-empty/whatever" }
}
```
No `X-Hub-Signature` is required to pass, because `Shipit.github(organization: "org-empty")` resolves to a config whose `verify_webhook_signature` unconditionally returns `true`.
4. `WebhooksController#create` dispatches to `StatusHandler`, which finds the commit by `sha` (belonging to `org-victim`) and calls `commit.create_status_from_github!(params)`, writing a fabricated "success" status onto `org-victim`'s commit — independent of the organization used to pass step 3's check.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
```
