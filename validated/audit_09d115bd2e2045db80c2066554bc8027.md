### Title
Forged `Merge-Requested-By` commit-message field lets an unprivileged PR author bind a `Shipit::Commit.author` to an arbitrary existing user - ([File: app/models/shipit/user.rb])

### Summary
`User.find_or_create_author_from_github_commit` trusts a `Merge-Requested-By: <login>` line inside the raw GitHub commit message and uses it to resolve `Commit#author` via `find_or_create_by_login!`, instead of relying on the commit's actual GitHub author/committer identity. [1](#0-0)  Because this code path is reached automatically when a PR is opened against a tracked stack (via `MergeRequest#github_pull_request=` → `find_or_create_commit_from_github_by_sha!` → `Commit.create_from_github!` → `Commit.from_github`), an attacker who merely opens a pull request from their own fork can make Shipit persist a `Commit` row whose `author` is a real, unrelated victim user. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
Binding claimed: `Shipit::Commit#author` (the recorded GitHub identity that "wrote" the commit) should equal the GitHub identity that authenticated/authored the commit payload (`github_commit.author` / `github_commit.commit.author`). This is broken by:

```ruby
def self.find_or_create_author_from_github_commit(github_commit)
  if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
    begin
      return find_or_create_by_login!(match_info[1])
    rescue Octokit::NotFound
    end
  end
  find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
end
``` [1](#0-0) 

`MERGE_REQUEST_FIELD` (`'Merge-Requested-By'`) is normally emitted only by Shipit itself when it performs a merge via `MergeRequest#merge_message`, so a maintainer-triggered, Shipit-authenticated merge legitimately carries this field. [5](#0-4)  The bug is that `find_or_create_author_from_github_commit` has no way to distinguish a message line that Shipit itself generated from one an attacker typed directly into their own commit.

Reachable path without any maintainer action: when a pull request is opened/updated, Shipit fetches and stores the PR's head commit as a detached `Commit` via `MergeRequest#github_pull_request=`:
```ruby
self.head = find_or_create_commit_from_github_by_sha!(github_pull_request.head.sha, detached: true)
...
def find_or_create_commit_from_github_by_sha!(sha, attributes)
  ...
  github_commit = stack.github_api.commit(stack.github_repo_name, sha)
  stack.commits.create_from_github!(github_commit, attributes)
end
``` [2](#0-1) [3](#0-2) 

`Commit.create_from_github!` calls `Commit.from_github`, which calls the vulnerable method directly on the attacker-controlled `commit.message`:
```ruby
def self.from_github(commit)
  author = User.find_or_create_author_from_github_commit(commit)
  ...
``` [4](#0-3) [6](#0-5) 

Exploit flow: attacker forks the tracked repository, commits with a message such as `"my change\n\nMerge-Requested-By: victim-login\n"`, opens a pull request against the stack. This fires the `pull_request` `opened` webhook, which is processed without needing repository write access or any Shipit credential (only `verify_signature` on the webhook, which validates that GitHub sent the payload — it does not validate the commit message content). [7](#0-6)  The PR refresh path stores the head commit with `author == victim`, even though `github_commit.author.login == attacker`.

Existing guards do not stop this: `verify_signature` only authenticates that GitHub sent the webhook, not the content of the commit message; `find_or_create_by_login!` simply looks up (or creates) a `User` by login and does not check any relationship between that login and the commit's real author/committer. [8](#0-7) 

### Impact Explanation
This is a genuine attribution-forgery bug: the `author_id` on a `Shipit::Commit` row for the PR's head commit no longer represents the person who wrote/authenticated that commit, and can be forced to any existing Shipit `User` by an unprivileged fork/PR author, repeatably, against any repository the attacker can open a PR on. However, I could not confirm within this codebase that this specific detached PR-head commit's `author` is consumed by a deploy/merge/rollback *authorization* decision: the corresponding mainline commit that actually lands on the deployable branch has its `author` re-derived from `merge_request.merge_requested_by` in `Commit#identify_merge_request` (`self.author = merge_request.merge_requested_by if merge_request.merge_requested_by`), which is set only through the authenticated `MergeRequest.request_merge!` call — not from the raw commit message — so the forged field is overwritten once a legitimate merge occurs. [9](#0-8) [10](#0-9)  This limits (but does not eliminate, depending on any UI or reporting logic keyed off the PR head commit's `author` before merge) the severity described in the question as "Critical…feeding downstream deploy/merge authorization." Based on what is verifiable in this engine's code, the confirmed impact is a data-integrity/attribution issue on the pre-merge, detached `Commit` record rather than a demonstrated bypass of an actual deploy/merge/rollback authorization control.

### Likelihood Explanation
Attacker cost is essentially zero: fork the repo, write one commit with a crafted message line, open a PR. No Shipit session, API token, or GitHub secret is required, and no repository maintainer action is needed to trigger the write (PR open/refresh alone is sufficient). This is fully repeatable against any stack whose repository accepts external PRs.

### Recommendation
`find_or_create_author_from_github_commit` should not trust the raw commit message for anything except commits that are known to have been generated by Shipit's own merge action (e.g., match against `merge_request.merge_commit`/`base_commit` relationship rather than free-text parsing of `commit.commit.message`), or should only honor the `Merge-Requested-By` field for merge commits whose SHA matches the one Shipit itself created via `MergeRequest#merge!`. At minimum, PR head commits (`detached: true`) created from `MergeRequest#github_pull_request=` should never resolve `author` via the `Merge-Requested-By` regex — that resolution should be limited to commits fetched by `GithubSyncJob` for commits already associated with a `MergeRequest` whose `merge_requested_by` was set through the authenticated `request_merge!` flow.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual, minitest, no live GitHub)
test '.from_github attributes commit to forged Merge-Requested-By login' do
  victim = shipit_users(:walrus) # existing privileged user
  gh_commit = resource(
    sha: '2adaad1ad30c235d3a6e7981dfc1742f7ecb1e85',
    author: { login: 'attacker', id: 999 },
    committer: { login: 'attacker', id: 999 },
    commit: {
      author: { name: 'attacker', email: 'a@a.com', date: Time.now },
      committer: { name: 'attacker', email: 'a@a.com', date: Time.now },
      message: "evil change\n\nMerge-Requested-By: #{victim.login}\n"
    }
  )
  record = Shipit::Commit.from_github(gh_commit)
  assert_equal victim, record.author        # forged binding
  refute_equal 'attacker', record.author.login
end
```
