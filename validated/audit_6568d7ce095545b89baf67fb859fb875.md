## Finding

### Title
Webhook signature verification is unconditionally bypassed when an organization has no `webhook_secret` configured, letting an unauthenticated payload be trusted as GitHub - ([File: lib/shipit/github_app.rb])

### Summary
`GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the organization's `webhook_secret` is blank, which is a supported, documented configuration (`docs/setup.md` calls it "optional"). This mirrors the audit-report pattern of a disabled/absent validation gate: the check that is supposed to bind "the payload came from GitHub" to "the payload is trusted and acted upon" is effectively commented out for any organization without a secret. `WebhooksController` then dispatches the unauthenticated payload straight into handlers (e.g. the `membership` event) that create `Team`/`Membership`/`User` records from payload content alone, which directly feeds `User#authorized?` (`Shipit.github_teams` membership check).

### Finding Description
`verify_webhook_signature` is the only gate between an arbitrary HTTP POST to `/webhooks` and the engine trusting its JSON body as an authentic GitHub event: [1](#0-0) 

`WebhooksController#verify_signature` calls this method keyed off the organization derived from the payload itself, and only halts on `false`: [2](#0-1) 

Because `return true unless webhook_secret` fires whenever the org's secret is blank, the equality the code is supposed to enforce — `sender == GitHub (verified by HMAC)` — collapses to `sender == anyone`, while the payload is still fully trusted and dispatched to handlers: [3](#0-2) 

The `membership` handler is one of the consumers of this trusted-but-unverified payload; tests show it creates `Team` and `User` records straight from payload fields (`action: 'added'`, `team`, `member`): [4](#0-3) 

Team membership is what `User#authorized?` checks to decide whether a user may use the whole application (deploy, rollback, merge, lock stacks, etc.): [5](#0-4) [6](#0-5) 

### Impact Explanation
For any GitHub organization onboarded to Shipit without a `webhook_secret` (a documented, supported setup), an unauthenticated internet client can POST a forged `membership` (or other) webhook event. If the forged event names a team present in `Shipit.github_teams` and a `member.login` matching an attacker-controlled GitHub account (which the attacker can log into via normal OAuth, since Shipit is otherwise public or team-gated only by this same check), the attacker's `User` gains a `Membership` in an authorized team, bypassing `Shipit.github_teams` authorization entirely. This maps to the High-impact bullet "escalation into `Shipit.github_teams` authorization." Other events (`push`, `status`, `pull_request`, `check_suite`) can likewise be forged to influence merge-queue/CD state on the same unsecured organizations.

### Likelihood Explanation
Requires only that the deployment leaves `webhook_secret` blank for at least one configured organization — an option the project's own setup docs present as normal/optional, not a misconfiguration outside documented use. No GitHub credentials, Shipit session, or `ApiClient` token are needed; the attacker only needs network access to `/webhooks` and a self-registered GitHub OAuth identity matching the login they place in the forged payload.

### Recommendation
Treat a missing `webhook_secret` as "reject all webhooks for this organization" instead of "accept all webhooks unconditionally," or require `webhook_secret` to be mandatory at boot/configuration time rather than optional. At minimum, `verify_webhook_signature` should fail closed when no secret is configured rather than fail open.

### Proof of Concept
1. Deploy Shipit with an organization entry that has `webhook_secret:` left blank (as shown supported in `config/secrets.development.example.yml`).
2. Sign in via GitHub OAuth as any low-privilege account (`login: attacker`).
3. Without any signature header, `POST /webhooks` with `X-Github-Event: membership` and body `{"action":"added","team":{...a Shipit.github_teams team...},"member":{"login":"attacker"},"organization":{"login":"<org-without-secret>"}}`.
4. `verify_signature` passes (`webhook_secret` is nil → `verify_webhook_signature` returns `true` unconditionally), the membership handler creates the `Membership`, and `attacker`'s `User#authorized?` now returns `true`, granting full application access.

Note: I was unable to load the exact source file for the `membership` webhook handler (only its behavior via `test/controllers/webhooks_controller_test.rb`); its filename/path could not be located within the index, so the described handler behavior is verified through test-level evidence rather than direct handler code reading.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
