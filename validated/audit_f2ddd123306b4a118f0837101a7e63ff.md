This confirms the divergence: `WebhooksController#repository_owner` (used to pick the GitHub App / secret for signature verification) reads `params.dig('repository','owner','login')`, while every handler resolves the target repository via `Handler#repository_name` / `params.repository.full_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`), an independent field of the same attacker-supplied JSON body. In a multi-organization deployment (`lib/shipit.rb:170-200`, `docs/setup.md:182-209`) these two fields can be made to point at different organizations, so the signing key used to authorize the request need not match the organization whose repository is actually mutated. ### Title
Webhook organization used for signature verification is not bound to the repository the payload actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a webhook's HMAC using `repository_owner`, which is read from `params.dig('repository','owner','login')` (or `organization.login`). Every event handler, however, resolves the repository it actually acts on from a *different* field in the same JSON body: `payload.dig('repository','full_name')` (`Handler#repository_name`, and duplicated in every `PullRequest::*Handler#repository`). Nothing in the engine enforces that the organization implied by `repository.owner.login` matches the organization implied by `repository.full_name`. In a Shipit instance configured for multiple GitHub organizations (the documented "Using Multiple Github Applications" setup), an attacker who only knows/controls one organization's webhook secret (or targets an org that was configured without one, which is an explicitly supported, non-error configuration per `docs/setup.md` and `secrets.development.example.yml`) can craft a payload whose `repository.owner.login` names that org (so `Shipit.github(organization:)` picks its lax/known key) while `repository.full_name` names a repository belonging to a different, protected organization.

### Finding Description
The trust binding that should hold is:
`organization used to select the webhook signing key == organization of the repository actually written to by the handler`

`repository_owner`, which drives key selection, is computed purely from `repository.owner.login`/`organization.login`:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This selects a `Shipit::GitHubApp` instance via `Shipit.github(organization: repository_owner)` (`lib/shipit.rb:170-181`) whose `webhook_secret` is then used in `verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`). Critically, `verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank — a state the docs present as a normal, supported configuration (`webhook_secret: # nil` in `config/secrets.development.example.yml` and the multi-org example in `docs/setup.md:188-209`).

Once the request passes `verify_signature`, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the *entire* JSON body to handlers, which never re-derive or re-check `repository.owner.login`. They instead trust `repository.full_name` directly:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
and use it to look up `Repository.from_github_repo_name(repository_name)` and its `Stack`s, which drive real side effects (queuing `GithubSyncJob`, updating commit statuses, creating/archiving review stacks and pull requests, creating `Shipit::User`/`Team` records for `membership` events, etc.).

Because `repository.owner.login` and `repository.full_name` are independent, unauthenticated-until-verified JSON fields under full attacker control, an attacker can pick the "cheap" organization for signature selection while pointing the effectual `full_name` at a target organization's repository. This is exactly the class of bug described in the source report: a value used to establish trust (Maverick's pool reserves used for pricing) is not the value the trust decision is supposed to be about (the true, invariant token price) — here, the value used to select the verification key (`repository.owner.login`) is not bound to the value that determines what gets mutated (`repository.full_name`).

### Impact Explanation
If any organization configured on the instance has no `webhook_secret` set (a supported, documented configuration) or if its secret can otherwise be obtained/guessed, an unprivileged attacker can forge webhook events that are processed as if they came from GitHub for a *different, protected* organization's repositories — e.g., triggering `GithubSyncJob`, forcing check-run/status refreshes, creating or archiving review stacks/pull requests, or auto-provisioning stacks (`OpenedHandler#process`) for a target repo they don't control on GitHub. This crosses a repository trust boundary the signature check is meant to enforce and can result in unauthorized state changes (deploy-adjacent side effects) attributed to a repository outside the attacker's control, without ever needing valid GitHub webhook credentials for that repository's real organization.

### Likelihood Explanation
Requires the instance to be configured with multiple GitHub organizations, and at least one org (any org, not necessarily the target) configured without a webhook secret, or with a secret otherwise known to the attacker — both realistic given this is an explicitly documented supported setup rather than a misconfiguration outside the engine's control.

### Recommendation
Bind the organization used for signature verification to the organization actually acted upon: derive both from the same normalized source (e.g., parse `repository.full_name` for the owner instead of `repository.owner.login`, or have handlers re-validate that `repository.owner.login` matches `full_name`'s owner and reject mismatches) so a single payload cannot be verified under one organization's key while mutating another organization's data.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgOne` (no `webhook_secret` configured) and `OrgTwo` (protected, has a repository/stack tracked by Shipit).
2. POST to `/webhooks` with `X-Github-Event: push` and a body:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/target-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>"
}
```
3. `repository_owner` resolves to `OrgOne`; `Shipit.github(organization: 'OrgOne')` returns a `GitHubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of any (or no) `X-Hub-Signature` header.
4. The push handler then resolves `Repository.from_github_repo_name('OrgTwo/target-repo')` and enqueues `GithubSyncJob` for that stack — a state change on `OrgTwo`'s tracked repository triggered without ever presenting `OrgTwo`'s webhook secret.
