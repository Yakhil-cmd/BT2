### Title
Stable outputs stay permanently marked `is_spent=1` when their spending unit is proven `final-bad` but never archived, freezing funds - ([File: main_chain.js])

### Summary
When a unit becomes final-bad during main-chain stabilization, `main_chain.js`'s `propagateFinalBad()` correctly clears the double-spend uniqueness marker (`inputs.is_unique=NULL`) on the bad spending unit, but it never resets `outputs.is_spent` back to `0` on the output that the final-bad unit had claimed to spend. The only code path that resets `outputs.is_spent=0` for a bad spender is `archiving.generateQueriesToUnspendOutputsSpentInArchivedUnit()`, which runs solely when a joint is archived/voided/removed via `generateQueriesToVoidJoint`/`generateQueriesToRemoveJoint`. A final-bad unit that is never voided or purged (e.g., it has a ball, has stable content, or otherwise doesn't qualify for `purgeUncoveredNonserialJoints`) leaves the true owner's output permanently flagged as spent even though the "spend" that caused the flag is invalid.

### Finding Description
`writer.saveJoint()` (and the private/divisible-asset save paths) mark the source output `is_spent=1` as soon as a unit that spends it is saved, regardless of whether that unit is ultimately the winner of a double-spend race: [1](#0-0) 

If two units try to spend the same output, `validation.js`'s `checkInputDoubleSpend`/`acceptDoublespends` logic and `main_chain.js`'s `handleNonserialUnits()`/`propagateFinalBad()` decide the winner at stabilization time. The loser is marked `sequence='final-bad'`, and `inputs.is_unique` is set to `NULL` so it is no longer treated as a competitor for future double-spend checks: [2](#0-1) 

However, nowhere in this path is `outputs.is_spent` reset to `0` for the src output that the final-bad unit claimed. The only place that performs this reset is the archiving/voiding logic, which is invoked only when a unit is actually archived: [3](#0-2) [4](#0-3) 

Archiving of final-bad units happens only through `purgeUncoveredNonserialJoints()` (uncovered units without a ball, without dependent children, after a delay/witness condition) or through light-client voiding in `light.js`: [5](#0-4) [6](#0-5) 

A final-bad unit that already has a ball, or that has children/dependents, is excluded from `purgeUncoveredNonserialJoints`'s `cond` (`is_free=1` / no children) and `NOT EXISTS (SELECT * FROM balls ...)` conditions, so it is never archived and `outputs.is_spent` is never restored to `0`. The repository's own `tools/compare_vote_balances.js` documents and detects exactly this class of discrepancy, calling the affected rows "zombie-spent outputs": [7](#0-6) [8](#0-7) 

This is structurally the same bug class as the CVE: a "bound"/"spent" flag is set at claim time but is not cleared when the claiming entity's validity is revoked, leaving stale state that downstream consumers trust as if it were still current.

### Impact Explanation
Any code that selects spendable coins by filtering `is_spent=0` — coin-selection in `composer.js`/`inputs.js`, wallet balance computation, and AA balance queries in `aa_composer.js`/`balances.js` — will silently skip the affected output forever, even though it is a stable, good, unspent output that legitimately belongs to its owner. This effectively freezes those funds: the address owner (or an AA that owns the output) can never again see or spend that fund through normal coin-selection queries, matching the "AA fund loss/freezing" and "node disagreement on the true unspent set" impact categories. It is triggered purely by ordinary usage (a benign attempt at a double-spend race that resolves against the local node, or a locally-known final-bad unit that never gets archived) — no privileged access or malicious peer is required, only that a spending unit ends up in `sequence='final-bad'`.

### Likelihood Explanation
This can be triggered by any unprivileged unit poster who creates (even accidentally) a losing side of a double-spend on their own output while the winning unit already has a ball or otherwise prevents purge/voiding, since `propagateFinalBad` runs automatically at stabilization for every final-bad unit and never restores `is_spent`. Given that `tools/compare_vote_balances.js` was written specifically to detect and report existing occurrences of "zombie-spent outputs," this is very likely to occur in production over time rather than a purely theoretical edge case.

### Recommendation
When `propagateFinalBad()` in `main_chain.js` marks a unit `final-bad` and clears `inputs.is_unique`, it should also reset `outputs.is_spent=0` on the transfer-type (and headers_commission/witnessing) outputs that unit claimed to spend, mirroring the logic already implemented in `archiving.generateQueriesToUnspendOutputsSpentInArchivedUnit()` (i.e., only unspend if no other surviving spender claims the same output). This closes the window where a stable output remains incorrectly marked spent indefinitely for units that are proven final-bad but never archived.

### Proof of Concept
1. Post two conflicting transfer units, `A` and `B`, that both spend the same output `O` from address `X`, timed so that both are accepted locally before stabilization (a normal double-spend race, no malicious peer needed).
2. Both units set `outputs.is_spent=1` on `O` when saved (`writer.js` lines 378-383).
3. At MCI stabilization, `handleNonserialUnits()`/`findStableConflictingUnits()` determines `B` loses, sets `B.sequence='final-bad'`, and `propagateFinalBad` sets `inputs.is_unique=NULL` for `B`'s input — but `O.is_spent` remains `1` (it was already `1` from `A`, so this specific case is masked by `A` also spending it — pick instead a scenario where `A` is the same output being claimed only by `B`, e.g. `B` is the sole and eventual final-bad claimant of `O`, or `A` itself later gets purged/voided leaving `B` as an orphan final-bad claim with no counterpart to trigger the archiving-based unspend).
4. If `B` (the final-bad unit) is never archived (e.g. it already has a ball or has children units), `O.is_spent` stays `1` forever.
5. Run `tools/compare_vote_balances.js` (or equivalent coin-selection/balance query filtering `is_spent=0`) to observe that `X`'s legitimate stable balance excludes `O`, confirming the fund is inaccessible via normal spend/coin-selection paths.

Note: I was not able to fully trace every downstream consumer of `outputs.is_spent` (e.g. `balances.js`, `aa_composer.js` coin-selection queries) within the available search budget to confirm each one is affected identically; the existence of `tools/compare_vote_balances.js` as a dedicated detection script strongly corroborates that this discrepancy is a known, real condition in the codebase rather than a purely theoretical one.
