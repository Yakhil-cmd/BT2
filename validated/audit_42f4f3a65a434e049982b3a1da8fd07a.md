### Title
Unauthenticated `sender` field in `StackStxOp` allows an attacker to lock a victim's STX and redirect PoX rewards to themselves - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp.sender` is populated purely from `PreStxOp.output`, which is decoded from an arbitrary Bitcoin `P2PKH`/`P2SH` output address chosen by whoever crafts the burnchain transaction, with no proof that the crafter controls the private key behind that address. `StackStxOp::check()` and `StacksChainState::process_stacking_ops` never verify that the entity who spent `outputs[1]` of the `PreStxOp` (i.e. the party who actually authorized the Bitcoin transaction) is the same party named in `sender`. The contract call to `stack-stx` is then executed with `tx-sender` set to this attacker-chosen `sender`, so a victim's real STX balance is locked with a reward address and signer-key entirely of the attacker's choosing.

### Finding Description
Broken equality: **AUTHORIZATION == LOCK TARGET**, i.e. the STX principal that is debited/locked by `stack-stx` must be the same principal that cryptographically authorized the stacking action. Here, the party that authorizes the Bitcoin transaction (by spending `outputs[1]` of the `PreStxOp` with their own key) is the attacker, while the STX that gets locked belongs to whatever `StacksAddress` is encoded in `outputs[0]` of the `PreStxOp` — which can be any victim address, since it is just a Bitcoin legacy address (`version + hash160`) written into the attacker's own transaction, requiring no signature from the address owner: [1](#0-0) 

That `output` is copied verbatim into `PreStxOp.output`, and then used, unauthenticated, as `StackStxOp.sender`: [2](#0-1) [3](#0-2) 

`StackStxOp::get_sender_txid` only enforces that the *second* input of the StackStxOp transaction spends vout=1 of the linked PreStxOp — a normal Bitcoin UTXO spend requiring only the attacker's own key, with no relation whatsoever to `outputs[0]`'s address: [4](#0-3) 

`StackStxOp::check()` validates only `stacked_ustx > 0`, `num_cycles` bounds, and `signer_key` format — no ownership/authorization check on `sender`: [5](#0-4) 

Finally, `process_stacking_ops` executes the pox-4 `stack-stx` contract-call using this forged `sender` as `tx-sender`: [6](#0-5) 

Inside `stack-stx`, the only "authorization" performed against the stacker identity is a balance check, not a signature check: [7](#0-6) 

The pox-4 `consume-signer-key-authorization` gate, which is the only real cryptographic check in the flow, only validates that the *signer key* is authorized for the given `pox-addr`/cycle/amount tuple — it never validates the *stacker* (`tx-sender`) identity. Since `collect_pox_4_stacking_args` always passes `signer-sig = none` for burn-triggered ops, the attacker can simply self-authorize their own `signer-key` for their own `reward_addr` via a normal, unprivileged `set-signer-key-authorization` call before submitting the forged op — fully satisfying that gate without ever touching the victim: [8](#0-7) [9](#0-8) 

**Attacker's exact call sequence:**
1. Attacker crafts a Bitcoin `PreStx` transaction whose `outputs[0]` address encodes the victim's `StacksAddress` (no signature needed — the attacker owns/funds the whole transaction) and `outputs[1]` is a spendable UTXO the attacker controls.
2. Attacker (optionally) calls `set-signer-key-authorization` on-chain with their own key/signature to pre-authorize their chosen `signer-key`/`reward_addr`/cycle/amount tuple.
3. Attacker crafts a Bitcoin `StackStx` transaction spending `outputs[1]` of step 1 with their own Bitcoin key, with OP_RETURN payload containing `stacked_ustx`, `num_cycles`, their own `signer_key`, `max_amount`, `auth_id`, and `outputs[0]` set to their own PoX reward address.
4. Consensus code links these into `StackStxOp{ sender: victim, reward_addr: attacker, signer_key: attacker, ... }` and calls `stack-stx` with `tx-sender = victim`.
5. If the victim has `stacked_ustx` of spare unlocked STX and is not already stacking/delegating, the call succeeds, locking the victim's real STX for `num_cycles`, with rewards flowing to the attacker's `reward_addr` and signing weight to the attacker's `signer_key`.

None of `check-caller-allowed` (auto-satisfied because the direct contract-call sets `tx-sender == contract-caller`), `verify-signer-key-sig`, or `consume-signer-key-authorization` validate the *stacker's* consent — they only validate the *signer's* consent, which the attacker controls entirely.

### Impact Explanation
An unprivileged attacker can permanently (until cycle end) freeze any victim Stacks account's STX (any address with `stacked_ustx` of spendable balance) without the victim's knowledge or consent, while simultaneously directing all PoX/sBTC reward payouts and signing weight for that locked STX to an address and key the attacker controls. This breaks both LOCK CONSERVATION (locked STX ≠ STX owned by the authorizing party) and REWARD CONSERVATION (rewards flow to a party that put up no STX of its own). This is repeatable against any number of victim addresses with spare balance, each costing the attacker only Bitcoin transaction fees. This matches the Critical severity category ("permanent freezing of staked STX ... reward slots exceeding locked value").

### Likelihood Explanation
Preconditions: victim must hold `stacked_ustx` of unlocked STX and not already be stacking/delegating — extremely common for any active account. The attack requires no privileged role, only ordinary Bitcoin UTXO control and the ability to submit a normal Stacks transaction (`set-signer-key-authorization`) — both explicitly listed as available to the unprivileged attacker in this audit's rules. Attacker cost is minimal (BTC fees for two transactions). It is fully repeatable and can be scripted against many victim addresses at once.

### Recommendation
Require cryptographic proof that the party submitting the `StackStxOp` (or the `PreStxOp`) controls the private key corresponding to `sender`/`PreStxOp.output` — e.g., require the `PreStxOp`/`StackStxOp` pair to spend a UTXO whose scriptPubKey hash matches `sender`, or require an explicit Stacks-side signature from `sender` authorizing the specific stacking parameters (amount, reward address, signer key, cycles), analogous to the `signer-key` authorization mechanism, before allowing `stack-stx`'s native lock to execute against that principal.

### Proof of Concept
Rust test on a booted chainstate (nakamoto/neon integration harness), analogous to existing `stack_stx_op` tests:
1. Create `victim_addr` (funded, unlocked STX ≥ `min_threshold`) and `attacker_addr`/`attacker_btc_key` (funded only in BTC, no STX contribution).
2. Submit `PreStxOp{ output: victim_addr }` signed/funded solely by `attacker_btc_key`.
3. Submit `StackStxOp{ sender: (parsed=victim_addr), reward_addr: attacker_pox_addr, signer_key: attacker_signer_key, stacked_ustx: N, num_cycles: 6 }` spending `outputs[1]` of the PreStxOp tx with `attacker_btc_key`.
4. Mine blocks; assert:
   - `get_balance(victim_addr)` locked amount == `N` (victim's `STXBalance` debited/locked) even though `victim_addr` never signed any Stacks transaction.
   - PoX reward-cycle reward set / signer weight entry references `attacker_pox_addr`/`attacker_signer_key`, not any victim-controlled key.
   - At the next reward cycle, sBTC/BTC rewards for the locked slot are paid to `attacker_pox_addr`.
5. Assert the equality is broken: `locked_STX_owner (victim) != authorizing_party (attacker)` and `reward_recipient (attacker) != STX_owner (victim)`.

impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }

        };

            Value::none(),
            signer_key,
            max_amount_value,
