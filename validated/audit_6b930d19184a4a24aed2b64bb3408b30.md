### Title
Attacker-controlled `.gitmodules` submodule reference causes persistent sync denial (crash-loop) in `configureWorktree` - (File: main.go)

### Summary
`git-sync`'s worktree setup unconditionally runs `git submodule update --init` whenever submodule syncing is enabled (the default is `submodulesRecursive`, not off). Because the submodule URLs/paths are defined in `.gitmodules`, which is fully attacker-controlled content committed to the synced repository, a single malicious or broken commit can make every subsequent sync attempt fail permanently — mirroring the reported bug class where a fallback code path depends on an external resource that is not guaranteed to be reachable/available, causing a hard, unrecoverable failure of a critical operation.

### Finding Description
In `configureWorktree`, after the worktree's `HEAD` is reset to the target hash, git-sync runs submodule update whenever `git.submodules != submodulesOff`: [1](#0-0) 

This command executes `git submodule update --init [--recursive] [--depth N]` against whatever `.gitmodules` entries exist in the synced commit. Since `.gitmodules` and the submodule commit pointers are ordinary tracked content, anyone who can push a commit to the source repository (an "attacker-pushed commit", per scope) can add a submodule that:
- points to an unreachable host, a non-existent path, or a protocol that is disabled (e.g. `git://`, blocked by `protocol.*.allow`),
- points to a URL that requires credentials git-sync was never configured with, or
- points to a pathological/huge resource that always times out.

If this `git.Run(...)` call returns an error, `configureWorktree` returns an error, which propagates up through `createWorktree`/`SyncRepo` as a sync failure. Because `--max-failures` defaults to `0`, "any sync failure will terminate git-sync": [2](#0-1) 

Combined with the documented default behavior: [3](#0-2) 

the process calls `os.Exit(1)`. In a Kubernetes sidecar deployment this results in a crash-loop: the container restarts, re-attempts to sync the same broken ref/hash, fails identically at `configureWorktree`, and exits again — indefinitely, with no automatic remediation, exactly analogous to the reported "DOS till USDa is available on CDS" pattern where a required external dependency is structurally unavailable and there is no third fallback option.

### Impact Explanation
This is a persistent sync denial: once a repository under sync contains a submodule reference that cannot be resolved with the credentials/protocols git-sync has configured, no future commit can ever be synced (git-sync never gets past `configureWorktree` for that hash or any hash reachable only via a fetch/checkout that also hits the same or another broken submodule), and the process itself repeatedly terminates. This matches the "persistent sync denial" impact category. It is reachable purely by pushing content to the tracked repository — no privileged operator action, leaked key, or mocked component is required.

### Likelihood Explanation
Likelihood is high in any deployment that syncs a repository not fully trusted/controlled by the git-sync operator (e.g., CI-managed config repos, multi-tenant GitOps setups) with submodules enabled (the default `--submodules` value is not `off`). A single bad commit — even accidental, e.g. a submodule pointing to a deleted or renamed fork — triggers the condition; a malicious contributor with write access to the branch/ref being synced can trigger it deliberately.

### Recommendation
- Do not let a submodule-update failure kill the whole process when `--max-failures` is unset/0; treat it the same as any other transient fetch failure and keep retrying without publishing, rather than crash-looping the container.
- Consider making submodule failures non-fatal to the overall sync (i.e., still publish the top-level tree via the symlink) or clearly documenting that `--submodules` must be `off` when syncing repositories from untrusted contributors.
- Provide a bounded, explicit backoff/circuit-breaker specifically for submodule resolution errors, distinct from top-level repo fetch errors, so operators can diagnose and the sidecar doesn't restart indefinitely.

### Proof of Concept
1. Deploy `git-sync` with default flags (`--max-failures` unset ⇒ 0) against a repository where an untrusted contributor can push commits.
2. Attacker pushes a commit adding a submodule entry in `.gitmodules` pointing to an unreachable/blocked URL (e.g. `git://unreachable.invalid/x` or an `http://` URL requiring unknown credentials).
3. On the next poll, `git.SyncRepo` fetches the new hash, calls `createWorktree` → `configureWorktree`, which runs `git submodule update --init` and fails [4](#0-3) .
4. Because `--max-failures` defaults to 0, git-sync logs the error and calls `os.Exit(1)` [5](#0-4) .
5. Under Kubernetes, the sidecar restarts, re-fetches the same bad hash, and repeats step 3–4 indefinitely, producing a permanent crash-loop and halting all future syncs.
