### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login`/`organization.login` but repository/team actions execute against attacker-controlled `full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's HMAC secret to validate a webhook against using an attacker-supplied field from the *unverified* JSON body, while the event handlers separately trust a *different* attacker-supplied field from that same body to decide which `Repository`/`Stack` to act on. Nothing binds the two fields together, so a payload can be verified under one organization's identity while writing state that belongs to a different organization's repository.

### Finding Description
`WebhooksController#verify_signature` computes the organization used to look up the webhook secret purely from the JSON payload, before the signature has been checked: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login` (falling back to `organization.login`) to fetch the matching `GitHubApp` config via `Shipit.github(organization: ...)`, and verification passes if that organization's `webhook_secret` matches the `X-Hub-Signature` header. Critically, `GitHubApp#verify_webhook_signature` treats a blank/unset secret as automatically valid: [3](#0-2) 

The setup docs explicitly document `webhook_secret` as optional per-organization, and multi-organization installs configure independent secrets per org: [4](#0-3) 

Once `verify_signature` passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the **entire raw payload** to handlers: [5](#0-4) 

Handlers, however, resolve the target `Repository`/`Stack` from an *independent* field, `repository.full_name`, with no re-validation that it belongs to the organization that was actually authenticated: [6](#0-5) [7](#0-6) 

The equality the platform implicitly relies on is:
`organization used to select the verification secret (repository.owner.login / organization.login) == organization owning the repository actually written to (repository.full_name)`

Nothing in `WebhooksController` or `Shipit::Webhooks::Handlers::Handler` enforces this equality. An attacker can pick `repository.owner.login` (or `organization.login`) to be any organization configured in `Shipit`'s multi-app config that has no `webhook_secret` set (or whose secret they know), causing `verify_webhook_signature` to return `true` unconditionally, while setting `repository.full_name` to point at a *different*, secured organization's tracked repository. The handler for that event (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) will then locate and mutate that other organization's `Stack`/`Commit`/`ReviewStack` records using attacker-supplied data (e.g. `PushHandler` triggers `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen SHA and branch match).

### Impact Explanation
This breaks the trust boundary between distinct GitHub organizations hosted by the same Shipit instance (the exact configuration the "Using Multiple Github Applications" documentation describes). An unauthenticated network attacker who only needs to know that one configured organization has no webhook secret (or has a leaked/guessable one — separately out of scope) can forge webhook events that are accepted as "verified" under that weak organization's identity, then redirect their effects onto a different, properly-secured organization's stacks: forcing sync jobs, injecting fabricated commit statuses (`StatusHandler`), or manipulating pull-request/review-stack lifecycle (archive/unarchive, provisioning) for repositories they have no legitimate relationship to. This is a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization of the write target — matching the required "cross-repository writes" impact class.

### Likelihood Explanation
Likelihood depends on Shipit being configured for multiple GitHub organizations (documented, supported feature) where at least one organization has an optional `webhook_secret` left blank — a state explicitly permitted by the setup documentation. In that configuration, no credentials, sessions, or tokens are required at all: the attacker only needs the public `/webhooks` endpoint and knowledge of the target's tracked `repository.full_name` (also discoverable, since Shipit stack URLs embed `owner/repo/environment`). This makes exploitation straightforward once the precondition (a secret-less org sharing the instance with a secured org) holds.

### Recommendation
Bind the verified identity to the mutation target: after computing `repository_owner`/`organization` and successfully verifying the signature, re-derive and enforce that any `repository.full_name` (or `organization.login` for org-scoped events) referenced inside the payload actually belongs to the same organization/app that was used for verification, rejecting the webhook (422) otherwise. Additionally, consider disallowing "no secret" as an effectively-always-valid signature outcome, or require that this behavior only implicitly trust events whose payload organization exactly equals the app being invoked.

### Proof of Concept
Preconditions: Shipit is configured with multiple GitHub Apps (`config/secrets.yml` → `github: { orgA: {...}, orgB: { webhook_secret: <secret> } }`), where `orgA` has no `webhook_secret` configured (optional per docs), and `orgB` has a tracked stack for `orgB/target-repo`.

1. Attacker sends, with no valid signature at all:
```
POST /webhooks
X-Github-Event: push
Body:
{
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/target-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```
2. `WebhooksController#verify_signature` computes `repository_owner = "orgA"`, fetches `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of signature (`lib/shipit/github_app.rb:76-83`).
3. `PushHandler.call(params)` resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:33-38`) and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `orgB`'s stack — a write triggered under `orgA`'s (unsecured) identity against `orgB`'s protected repository.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
```
