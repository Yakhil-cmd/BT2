### Title
Cross-organization webhook forgery via mismatched signature-verification key and repository-resolution key - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (`Shipit.github_organizations` returning more than one entry, i.e. `secrets.github` keyed by organization name), the webhook signature is verified against the secret of whichever organization is named in the `repository.owner.login` (or `organization.login`) field of the *attacker-controlled* JSON body, while the object actually mutated by the event handler is resolved from a different field of that same body: `repository.full_name`. Nothing enforces that these two fields agree, so a party who legitimately knows/controls one organization's webhook secret can forge events for any other organization/repository/stack configured on the same instance.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using an attacker-supplied field, then checks the raw body's HMAC against that secret: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload the attacker is about to send: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization key when the multi-org config schema is used (`secrets.github` keyed by org name): [3](#0-2) 

Once `verify_webhook_signature` returns true (i.e. the body is correctly signed for *that* organization's secret), `create` dispatches the parsed body to the registered handler for the event: [4](#0-3) 

Every default handler, however, resolves the target `Repository`/`Stack` from a *different* field in the same body — `repository.full_name` — not from `repository.owner.login`: [5](#0-4) [6](#0-5) 

Root cause: the signature check binds the request to organization *A* (`repository_owner`), but the code that decides which repository/stack to write to trusts an independent field (`repository.full_name`) inside the same attacker-controlled JSON, with no check `repository.owner.login == repository.full_name.split('/').first`. Before the attacker's request, GitHub itself guarantees this equality because it fills in both fields from the same repository object; after the attacker's forged request, this guarantee no longer holds since the attacker fully controls the JSON body as long as they can produce a valid HMAC for *some* configured organization's secret.

### Impact Explanation
An unprivileged party who is entitled to install a GitHub App / configure a webhook for their own organization "A" on a shared multi-org Shipit instance (and therefore legitimately knows org A's `webhook_secret`) can sign a webhook body naming `repository.owner.login: "A"` for verification, but `repository.full_name: "victim-org/victim-repo"` for actual processing. This lets them:
- Trigger `PushHandler` to force `stack.sync_github(expected_head_sha: ...)` on a victim org's stack.
- Trigger `pull_request`/`membership`/`status` handlers to mutate `PullRequest`, `Commit`/`Status`, `Team`/`Membership` records belonging to a repository they do not control, and in the merge-queue flow (`MergeRequest#merge!`) potentially cause an unauthorized merge to be attempted on the victim's GitHub repository using Shipit's own GitHub App credentials.

This crosses a repository/organization trust boundary using a credential (webhook secret) the attacker is only entitled to use for their own organization — matching the "cross-repository writes / unauthorized deploy or merge" high/critical impact bar, since it results in actions being taken against a repository outside the authenticated organization's scope.

### Likelihood Explanation
This requires the deployment to be configured with the multi-organization `secrets.github` schema (documented and supported, see `docs/setup.md` / `config/secrets.development.example.yml`) and for the attacker to be one of the (potentially many, mutually untrusted) organizations onboarded to the same shared Shipit instance. This is a realistic operating mode for the engine (it explicitly supports "multiple Github applications for different Github organizations" in the same instance) and requires no privileged Shipit session, `ApiClient` token, or private key — only knowledge of one's own org's webhook secret, which by design every onboarded organization possesses.

### Recommendation
After `verify_webhook_signature` succeeds, cross-check that the organization used to select the verification secret (`repository_owner`) matches the owner encoded in the payload fields the handlers actually act on (`repository.full_name`'s owner segment, or `organization.login` for org-scoped events), and reject (422) on mismatch. Alternatively, have handlers resolve the target `Repository`/`Stack` scoped to the verified organization rather than trusting `repository.full_name` in isolation.

### Proof of Concept
1. Configure Shipit with multi-org `secrets.github`: `{ "org-a" => { webhook_secret: "secretA", ... }, "org-b" => { webhook_secret: "secretB", ... } }`, with stacks for both `org-a/repo` and `org-b/repo`.
2. As an operator of `org-a` (who legitimately knows `secretA`), craft a `push` event JSON body:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker chosen sha>",
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(secretA, body)>` and POST to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), verifies successfully against `secretA`.
5. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("org-b/repo")` (from `repository.full_name`) and calls `stack.sync_github(expected_head_sha: ...)` on `org-b`'s stack — an organization the request was never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
