### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a webhook from one repository mutate the commit-status (and hence deployability) of any other stack's commit sharing the same SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit(s) purely by `sha` with `Commit.where(sha: params.sha)`, without any constraint tying the lookup to the repository/organization that the webhook was actually verified for. Since git commit SHAs are content-addressed and are shared identically between a public repository and any fork of it (or any repository containing the same commit history prefix), an attacker who owns a fork of a victim's tracked repository can trigger a real, signature-valid `status` webhook from their own repo/org that updates the `Status` record of the victim's identical-SHA commit, potentially flipping `Commit#deployable?` to true.

### Finding Description
The broken binding is: WEBHOOK PROVENANCE (`repository_owner` verified in `WebhooksController#verify_signature`, derived from `params.dig('repository','owner','login')`, i.e. the attacker's org) should equal REPOSITORY SCOPE of the record being mutated (the `stack`/`commit` actually updated), but it does not.

Path:
1. `WebhooksController#verify_signature` verifies the HMAC using `Shipit.github(organization: repository_owner)`, i.e., using the *attacker's own org's* configured webhook secret [1](#0-0) . This only proves the request genuinely came from GitHub for the attacker's repository/org - it says nothing about which commit's `sha` field is safe to trust.
2. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query is **global across all stacks/tenants** - it never joins or filters on `params['repository']` or any stack/repo identifier matching the verified org.
3. `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, where `stack_id` is `self.stack_id` - the **matched commit's own stack**, not anything derived from the attacker's payload [3](#0-2) .
4. `Status.replicate_from_github!` writes/creates the `Status` row scoped to that `stack_id` and to `commit_id` (via the `statuses` association, i.e. the victim's commit) [4](#0-3) .
5. `Commit#add_status` recomputes `@status`, and `Commit#deployable?` becomes `true` once `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [5](#0-4)  and [6](#0-5) .

Exploit flow: The attacker forks a victim's tracked GitHub repository (forks retain identical SHAs for unmodified commit history - this is standard git/GitHub behavior, no cryptographic collision needed). The attacker connects/owns a Shipit-tracked stack for their own fork (or otherwise has a repo whose org is registered in `Shipit.github_teams`/`Shipit.github` config with a valid webhook secret) and, using their own GitHub credentials, calls the GitHub Statuses API (`POST /repos/{attacker}/{fork}/statuses/{victim_sha}`) with `state: success` and `context` equal to the specific check the victim's `DeploySpec` requires (e.g., `ci/travis`). GitHub delivers a `status` webhook to Shipit, signed with the attacker's org's webhook secret. `verify_signature` passes because the signature is genuinely valid for the attacker's org. `StatusHandler#process` then matches the victim's commit by `sha` (since the SHA is identical across the fork) and writes a new `Status` row under the victim's `stack_id`/`commit_id`, potentially unlocking `deployable?` for a commit the attacker never had any authorization over.

No existing guard closes this gap: `verify_signature` only authenticates the request's origin org, not the target record; `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `require_permission!`/`stacks` scope check in `StatusHandler`; and `Commit.where(sha:)` has no `stack_id`/repository filter at all.

### Impact Explanation
An attacker can, from a repository they legitimately own (and thus for which they control CI/API access), write `Status` records into an arbitrary victim stack/commit that shares the SHA, mutating cross-tenant state without ever authenticating against the victim's organization. Combined with `Commit#deployable?`, this can unlock deploy eligibility for a specific victim commit, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and potentially enabling an unauthorized deploy path once the commit is deployable. This is repeatable against any repository whose commit history/SHA is discoverable and forkable, and the blast radius spans any tenant/stack sharing that SHA (which, for public open-source repositories with forks, is common and predictable).

### Likelihood Explanation
Preconditions are modest for an unprivileged attacker: they need (a) their own GitHub repository connected as a Shipit stack (or otherwise belonging to an org configured in Shipit with a valid webhook secret), (b) a fork or repository that shares an identical SHA with the victim's tracked commit (trivial via GitHub's fork feature, since SHAs are deterministic and preserved for unmodified history), and (c) knowledge of the exact `context` string the victim's `DeploySpec` requires for that commit (often discoverable from public CI config, e.g. `.travis.yml`/branch protection). No Shipit secret, session, or API token is needed. This is entirely feasible with standard GitHub API access to a repo the attacker owns.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to only stacks belonging to the repository verified by the webhook signature (e.g., join `Commit` to `Stack` and filter by `stack.repository.owner`/`stack.repository.name` derived from `params['repository']`, matching the same `repository_owner`/repo full name used in `verify_signature`), rather than a bare `Commit.where(sha: params.sha)` across all tenants.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, not present today - would need adding):
```ruby
test "status webhook from attacker repo does not mutate a commit in a different stack sharing the same sha" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = Shipit::Stack.create!(repository: shipit_repositories(:attacker_repo), environment: "production")
  shared_sha = "a" * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim commit")
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: "attacker commit")

  params = ActionController::Parameters.new(
    sha: shared_sha,
    state: "success",
    context: "ci/travis",
    repository: { full_name: "attacker-org/attacker-repo", owner: { login: "attacker-org" } }
  )

  Shipit::Webhooks::Handlers::StatusHandler.new(params).call

  victim_commit.reload
  assert_not victim_commit.statuses.exists?(context: "ci/travis"),
    "expected no Status row to be written on victim_stack.id (#{victim_stack.id}) " \
    "from a webhook authenticated only for attacker-org/attacker-repo"
end
```
This asserts that `Status.create!`/`find_or_create_by!` args (`stack_id == victim_stack.id`, `commit_id == victim_commit.id`) must never occur when the verified webhook `repository.owner.login` is `attacker-org` and not the org owning `victim_stack`'s repository - currently this assertion fails because `Commit.where(sha:)` in `StatusHandler#process` matches `victim_commit` purely by SHA collision, independent of the verified webhook's repository/org.
