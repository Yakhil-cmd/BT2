### Title
KAIA Permanently Locked in Service-Chain Bridge When Recipient Contract Lacks a Payable Fallback — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY.sol` sends native KAIA to the caller-supplied `_to` address using a low-level `.call.value()`. If `_to` is a contract that has no `receive()` / payable `fallback()` function, the call returns `false`, the mandatory `require(ok, …)` reverts the entire transaction, and the KAIA deposited by the user on the parent chain is permanently locked inside the bridge with no on-chain recovery path.

---

### Finding Description

`handleKLAYTransfer` executes the following sequence:

```solidity
// BridgeTransferKLAY.sol  lines 81-99
_setHandledRequestTxHash(_requestTxHash);
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");          // line 98
require(ok, "handleKLAYTransfer: transfer failed"); // line 99
``` [1](#0-0) 

Because `require(ok, …)` causes a full EVM revert, every state mutation above it — `_setHandledRequestTxHash`, `handleNoncesToBlockNums`, `_updateHandleNonce`, and the vote recorded by `_voteValueTransfer` — is also rolled back. The nonce is therefore never marked as handled.

`_updateHandleNonce` advances `lowerHandleNonce` only through a contiguous run of nonces whose `handleNoncesToBlockNums[i] > 0`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) { … }
lowerHandleNonce = i;
``` [2](#0-1) 

Because the stuck nonce's entry is never written (the tx reverts), `lowerHandleNonce` is frozen at that nonce permanently.

The KAIA that the user deposited on the parent chain when calling `requestKLAYTransfer` is already held by the bridge contract. There is no owner-callable withdrawal function for stuck funds; `chargeWithoutEvent()` only adds liquidity. The KAIA cannot be recovered.

---

### Impact Explanation

- **Permanent asset lock**: The exact `_value` of KAIA deposited by the user is frozen inside the bridge contract on the parent chain with no on-chain recovery path.
- **Nonce freeze**: `lowerHandleNonce` is stuck at the failing nonce. The off-chain recovery daemon (`vt_recovery.go`) will loop indefinitely retrying the same failing call, consuming operator gas and producing noise, but can never advance past the stuck nonce.
- **Bridged-asset integrity broken**: The invariant that "KAIA deposited into the bridge is either delivered to the recipient or recoverable" is violated.

---

### Likelihood Explanation

Any user who initiates a cross-chain KAIA transfer to a contract address that has no payable fallback (e.g., a multisig wallet, a governance contract, a proxy without a `receive()` stub, or any contract compiled without one) triggers this condition. The user need not be malicious; the scenario arises naturally whenever a contract-to-contract cross-chain transfer is attempted. The bridge performs no pre-flight check on whether `_to` can accept native tokens.

---

### Recommendation

1. **Emit before transfer, skip on failure**: Record the nonce as handled before the `.call`, and on failure emit a `HandleValueTransferFailed` event and continue rather than reverting. This preserves nonce progress and allows off-chain tooling to flag the stuck transfer.
2. **Pull-payment pattern**: Instead of pushing KAIA to `_to`, credit a claimable balance mapping and let `_to` (or its owner) pull the funds. This is the standard mitigation for push-to-unknown-contract patterns.
3. **Add a guardian withdrawal**: Provide an `onlyOwner` function to rescue KAIA that is stuck due to failed deliveries, so funds are not permanently locked.

---

### Proof of Concept

1. On the parent chain, deploy a contract `NoReceive` with no `receive()` or `fallback()`.
2. Call `bridge.requestKLAYTransfer{value: 1 ether}(address(noReceive), 1 ether, "")` on the parent bridge. The bridge emits `RequestValueTransfer` and holds 1 KAIA.
3. The child-chain bridge operator observes the event and calls `handleKLAYTransfer(txHash, from, address(noReceive), 1e18, nonce, blockNum, "")`.
4. The EVM executes `address(noReceive).call{value: 1e18}("")` → returns `(false, "")` because `NoReceive` has no payable fallback.
5. `require(ok, "handleKLAYTransfer: transfer failed")` reverts the transaction.
6. All state changes revert; `handleNoncesToBlockNums[nonce]` remains 0; `lowerHandleNonce` stays at `nonce`.
7. The 1 KAIA remains in the parent bridge forever. Repeated retries by the recovery daemon all revert identically. [3](#0-2) [4](#0-3)
