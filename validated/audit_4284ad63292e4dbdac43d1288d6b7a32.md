### Title
Missing write-lock around `dryRunPrimaryAATrigger` allows concurrent corruption of shared DAG caches - (File: aa_composer.js)

### Summary
`aa_composer.dryRunPrimaryAATrigger()` mutates and reads the same in-memory DAG state (`storage.assocUnstableUnits`, `storage.assocBestChildren`, `storage.assocUnstableMessages`) that `writer.saveJoint()` mutates while holding the global `mutex.lock(["write"])`. The dry-run path never acquires this lock, so it can run concurrently with the real unit-writing pipeline and interleave writes/deletes on the same shared JS objects, analogous to the kernel bug where a socket's `sk_user_data` was read/freed without waiting for concurrent readers to finish.

### Finding Description
`writer.saveJoint()` takes the process-wide write lock before mutating shared caches: [1](#0-0) 
and later pushes/updates entries directly into `storage.assocUnstableUnits` and `storage.assocBestChildren`: [2](#0-1) 

`aa_composer.dryRunPrimaryAATrigger()`, however, only wraps its work in a DB transaction (`BEGIN`/`ROLLBACK`) — it never takes `mutex.lock(["write"])`: [3](#0-2) 

At the end of the dry run, `revertResponsesInCaches()` directly deletes entries from the same shared maps via `storage.forgetUnit()` and `storage.fixIsFreeAfterForgettingUnit()`, again with no locking: [4](#0-3) 
and `storage.forgetUnit()` unconditionally reads and deletes from `assocUnstableUnits`, `assocBestChildren`, etc.: [5](#0-4) 

This dry-run path is reachable by two unprivileged inputs:
1. Directly from a light client via the `light/dry_run_aa` network command, with attacker-supplied `trigger`/`address`: [6](#0-5) 
2. Automatically for **any** newly posted unit that pays to an AA address, executed inline in the `ifOk` handler of unit validation, before `writer.saveJoint` is even called for that same unit: [7](#0-6) 

Because this automatic dry run executes outside the `["write"]` mutex while other units are concurrently being validated/saved (each acquiring `["write"]` independently per `writer.saveJoint`), a race window exists in which:
- the dry run mutates/inspects `storage.assocUnstableUnits[my_best_parent_unit]` / `assocBestChildren` while a genuine `saveJoint()` for a different, concurrently-arriving unit is also pushing/popping the very same parent's `assocBestChildren` array or updating `assocUnstableUnits` entries,
- `revertResponsesInCaches()` calls `forgetUnit()` which deletes cache entries and asserts invariants (e.g. `throw Error("trying to forget stable unit")` at storage.js:2227-2228) that can be violated if another concurrent path has already mutated the same unit's stability/props between the dry run's snapshot and its rollback.

This is the same bug class as the reported kernel CVE: a shared, reference-like resource (`sk_user_data` / cached unit props objects) is read/mutated by one path while another path concurrently deletes or repurposes it, with no coordination ensuring all readers finish before the resource changes.

### Impact Explanation
Corruption of `assocUnstableUnits` / `assocBestChildren` / `assocUnstableMessages` is exactly the state used by `main_chain.js` to compute main-chain index, stability, and best-parent selection for every subsequently processed unit. A successful race can cause:
- an uncaught exception (`throw Error(...)`) crashing the node process during unit processing, and/or
- corrupted best-parent/best-children bookkeeping causing a node to diverge from other nodes on which units are on the main chain or which units are stable — i.e., node disagreement on validity/stability, which is one of the accepted high-impact outcomes.

Because the automatic dry-run trigger fires for every unit that merely pays an AA address, any unprivileged unit poster can create the race window continuously and cheaply, without needing to control a peer, hub, or light-vendor node.

### Likelihood Explanation
Triggering the race requires timing two concurrent operations (a normal unit save and an AA-address-targeted unit's automatic dry run, or an explicit `light/dry_run_aa` request) so their unlocked cache accesses interleave. This is feasible for a well-resourced attacker flooding the node with units/dry-run requests concurrently, but exact interleaving is non-deterministic (depends on event-loop/DB-callback scheduling), which is why this is rated as a race condition of medium-to-high likelihood rather than a deterministic trigger.

### Recommendation
Have `dryRunPrimaryAATrigger()` (and its cache-mutating cleanup `revertResponsesInCaches()`) acquire the same `mutex.lock(["write"])` used by `writer.saveJoint()` before touching `storage.assocUnstableUnits`, `storage.assocBestChildren`, and `storage.assocUnstableMessages`, releasing it only after `revertResponsesInCaches()` completes — mirroring the kernel fix pattern of not tearing down/mutating a shared structure until all concurrent users are guaranteed serialized against it.

### Proof of Concept
Conceptual PoC (requires a running node instance to actually demonstrate the race, not verifiable purely from static code review):
1. Deploy an AA at address `AA1`.
2. Continuously post ordinary units (from any wallet) that build on the current DAG tip, causing frequent `writer.saveJoint()` calls that mutate `assocBestChildren`/`assocUnstableUnits` for the same recent parent units.
3. Simultaneously flood the node with units paying small amounts to `AA1` (or `light/dry_run_aa` requests targeting `AA1`) so that `aa_composer.dryRunPrimaryAATrigger()` runs repeatedly and concurrently with step 2, without the write lock.
4. Observe for a thrown `Error` (e.g. "trying to forget stable unit", or `_.pull` / cache-consistency assertions in `storage.js`) crashing the node, or observe divergent `is_on_main_chain`/`is_stable` results between nodes under the same load — confirming the unsynchronized concurrent cache access. Full confirmation would require actually running node instances under load, which is outside the scope of this static analysis.
