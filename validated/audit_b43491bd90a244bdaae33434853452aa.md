Based on my research, I found a genuine admission-boundary issue in the multisig transaction prologue that is a valid local analog (an approval-validation mismatch, not a Balancer-Oracle copy).

### Title
Multisig transaction execution can proceed with a payload that differs from the one owners actually approved when `abort_if_multisig_payload_mismatch` feature is disabled - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`validate_multisig_transaction` is the VM-invoked prologue for multisig transactions, run both during mempool admission and as the first step of execution [1](#0-0) . It counts owner approvals recorded against the on-chain `transaction.payload` (or `transaction.payload_hash`) and then, only if a specific feature flag is enabled, verifies that the `payload` bytes supplied with the transaction being executed actually match the stored, approved payload [2](#0-1) .

### Finding Description
There are two distinct ways a multisig transaction can be proposed: `create_transaction` (stores the full payload on-chain) or `create_transaction_with_hash` (stores only a hash of the payload). The prologue handles them differently:

- When `transaction.payload_hash.is_some()`, the payload passed in at execution time is unconditionally checked against the stored hash via `sha3_256(payload) == *payload_hash` [3](#0-2) .
- When the transaction was instead created with a stored plaintext `transaction.payload` (no hash), the corresponding equality check `payload == *stored_payload` is only performed if `features::abort_if_multisig_payload_mismatch_enabled()` returns true [4](#0-3) .

If that feature is disabled, an executing owner (who only needs to satisfy the quorum/`can_execute` check, which is validated against votes cast for the *originally stored* payload) can submit a `SignedTransaction` whose embedded entry-function `payload` bytes are different from what other owners voted to approve. Since the payload-match assertion is skipped, the mismatch is never caught in the prologue, and the VM proceeds to execute whatever entry function the executor actually signed and submitted — not the one the other owners approved.

This breaks the "approval validation accepting the wrong approval set" invariant called out in the Admission Pivots: the quorum count/authentication was established against payload X, but a different payload Y is what actually executes and commits.

### Impact Explanation
If exploitable (i.e., if this feature flag can be off on a given network/chain or during any window before it is enabled), a single multisig owner with enough votes to reach `can_execute`/quorum on a benign proposal (e.g., "transfer 1 APT to Bob") could instead execute an entirely different, unapproved payload (e.g., "transfer all funds to attacker", or invoke a privileged admin function the multisig account controls) without needing additional owner approval for that specific action. This is a high-severity break of the multisig approval invariant — unauthorized execution under the multisig account's authority using the wrong (unapproved) instruction set.

### Likelihood Explanation
Likelihood depends entirely on the runtime state of the `abort_if_multisig_payload_mismatch_enabled` feature flag, which I was not able to confirm from the code I retrieved (I found the getter is defined in `move-stdlib/sources/configs/features.move`, but did not verify whether it is enabled by default in this repo's genesis/mainnet configuration before running out of investigation budget). The mere existence of a feature-gated bypass for a core payload-integrity check is itself a code-level admission weakness regardless of current default, since the check was clearly added later (implying older/non-upgraded networks, or any deployment where the flag remains off, are exposed).

### Recommendation
Make the payload match check for the plaintext-payload case (`transaction.payload.is_some()`) unconditional, exactly like the hash-based check, rather than gating it behind a feature flag. If the flag exists only for migration/rollout purposes, ensure it is enabled everywhere before removing the gate, and audit whether any chain/environment currently has it disabled.

### Proof of Concept
1. Owner A creates a multisig transaction via `create_transaction(owner, multisig_account, payload_X)` where `payload_X` is a benign entry function call; this stores `transaction.payload = Some(payload_X)` (not a hash).
2. Owners B and C vote to approve, reaching the required signature threshold for `payload_X`.
3. With `abort_if_multisig_payload_mismatch_enabled()` returning false, Owner A (or any owner satisfying `can_execute`) submits a `SignedTransaction` to the network whose actual multisig payload argument is `payload_Y` (a malicious/different entry function call) instead of `payload_X`.
4. `validate_multisig_transaction` finds `transaction.payload_hash` is `None` (skip hash check), and skips the plaintext match check because the feature is off; quorum/`can_execute`/timelock checks pass since they only look at vote counts for the sequence number, not the specific payload content.
5. The VM proceeds to execute `payload_Y` under the multisig account's authority, even though owners only approved `payload_X`.
