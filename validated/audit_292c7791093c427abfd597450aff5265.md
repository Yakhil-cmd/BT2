### Title
Global `http.cookiefile` config allows attacker-controlled submodule URLs to receive the cookie file - ([File: main.go])

### Summary
`SetupCookieFile` unconditionally sets `http.cookiefile` at the `--global` git config scope with no URL restriction, so the cookie file is attached to every HTTP/HTTPS request git makes for the lifetime of the process, including `git submodule update` fetches to any URL declared in a repo's `.gitmodules` file. Since git-sync's threat model treats repo content (including `.gitmodules`) as attacker-influenced, and submodules default to `recursive` processing, a malicious or compromised upstream repo can embed a submodule pointing at an attacker-controlled HTTP(S) host and receive the cookie contents in the request.

### Finding Description
`SetupCookieFile` (main.go) does: [1](#0-0) 

It runs `git config --global http.cookiefile <path>` with no `<url>` scoping (e.g. it does not use `http.<url>.cookiefile`), so the setting applies globally to all outbound HTTP(S) connections made by git for the rest of the process's life, including submodule fetches. This is invoked once from `main()` guarded only by the `--cookie-file` flag: [2](#0-1) 

Submodule updates are performed later, during worktree configuration, using the submodule URLs recorded in the fetched repo's `.gitmodules` file: [3](#0-2) 

`--submodules` defaults to `"recursive"`, so this path is taken by default whenever any submodule is present, without any non-default flag being required: [4](#0-3) 

Because `http.cookiefile` is a single global setting rather than being scoped per-URL (git does support `http.<url>.<key>` scoping, but git-sync does not use it here, unlike its documented per-URL `--credential` mechanism for passwords), any submodule URL — including one pointing to an attacker-controlled host embedded in `.gitmodules` — will receive the `Cookie` header derived from the cookie file when git fetches that submodule. Git itself provides no built-in confinement of `http.cookiefile` to the original `--repo` host; this is a config-scoping decision left to the caller, and git-sync does not make it. There is no `protocol.allow`/host allow-list restricting submodule targets either — the test suite explicitly enables `protocol.file.allow=always` for local file-protocol submodule tests, but nothing in `main.go` restricts submodule URL hosts/protocols at runtime for the http case.

### Impact Explanation
This is a secret/session disclosure to attacker infrastructure: the cookie file mounted from a Kubernetes Secret (`/etc/git-secret/cookie_file`), intended only for authenticating to the configured `--repo` host, is sent to any host reachable via a submodule URL that the attacker can place in repo content the tool fetches. This matches the "secret leakage to unintended party" impact class — an attacker who can influence repo content that git-sync fetches (e.g., a compromised or malicious upstream repo, or an intermediate branch/PR that gets synced) can exfiltrate the authentication cookie without any operator misconfiguration beyond the documented, supported combination of `--cookie-file` and default (`recursive`) submodule handling.

### Likelihood Explanation
Preconditions are minimal and use only documented, default/supported settings: `--cookie-file` is a documented flag [5](#0-4) , and `--submodules` defaults to `recursive` (no non-default flag needed) [4](#0-3) . The only requirement is that the attacker can get git-sync to fetch a repo/ref whose `.gitmodules` contains a submodule URL under attacker control — this is within the stated threat model ("attacker controls repo content and refs that git-sync fetches"). This is fully repeatable on every sync cycle that processes the malicious `.gitmodules`.

### Recommendation
Scope the cookie file to the intended remote using a URL-scoped git config key (`http.<repo-scheme>://<repo-host>/.cookiefile`) instead of the bare `http.cookiefile --global`, so it is only attached to requests targeting the operator-specified `--repo` host. Alternatively/additionally, restrict submodule URLs to an explicit allow-list of hosts/protocols (e.g., via `protocol.allow`/`GIT_ALLOW_PROTOCOL` and validating `.gitmodules` URLs against the configured repo's host) before running `git submodule update`.

### Proof of Concept
Integration test sketch:
1. Start two local HTTP servers: `origin` (serving the main test repo) and `evil` (a header-capturing HTTP server).
2. In the main repo, add a `.gitmodules` entry with a submodule URL pointing at `http://evil-host/sub.git`.
3. Mount a cookie file at `/etc/git-secret/cookie_file` with a marker value (e.g., `session=SECRET123`).
4. Run git-sync with `--repo=http://origin-host/repo.git --cookie-file --submodules=recursive` (default).
5. Assert that the `evil` server's captured request headers for the submodule fetch include a `Cookie` header containing `SECRET123`.
6. Expected secure behavior: the `evil` server should never receive the `Cookie` header (test should fail on the unpatched code and pass once cookiefile is scoped to `origin-host` only).

```go
func (git *repoSync) SetupCookieFile(ctx context.Context) error {
	git.log.V(1).Info("configuring git cookie file")

	var pathToCookieFile = "/etc/git-secret/cookie_file"

	_, err := os.Stat(pathToCookieFile)
	if err != nil {
		return fmt.Errorf("can't access git cookiefile: %w", err)
	}

	if _, _, err = git.Run(ctx, "", "config", "--global", "http.cookiefile", pathToCookieFile); err != nil {
		return fmt.Errorf("can't configure git cookiefile: %w", err)
	}

	return nil
}
```
