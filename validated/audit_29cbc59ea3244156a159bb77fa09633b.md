### Title
Webhook Authentication Bound to Attacker-Chosen `organization`/`repository.owner.login` While Writes Target an Independent `repository.full_name` Field - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the same class of bug as the reported zkLogin issue: an authentication check is performed against one identity/credential, but the privileged action is executed against a *different*, unchecked identity taken from the same untrusted payload. In `library::verify_signature()` the scheme byte selects a bypass path; here, `WebhooksController#verify_signature` selects *which GitHub App's webhook secret* to validate against using a field pulled straight out of the still-unverified JSON body, while the handlers that actually perform writes use a *different* unverified field to decide which repository/stack to mutate.

### Finding Description
`WebhooksController#verify_signature` computes the signing key to check the request against like this: [1](#0-0) 

`repository_owner` is derived purely from the raw, unauthenticated request body: [2](#0-1) 

`Shipit.github(organization:)` uses that attacker-supplied string to select which configured GitHub App (and therefore which `webhook_secret`) to validate the HMAC signature against, per the documented "Using Multiple GitHub Applications" feature: [3](#0-2) 

Separately, `GithubApp#verify_webhook_signature` trivially returns `true` if that selected app has no `webhook_secret` configured at all: [4](#0-3) 

Once the request passes this check, `WebhooksController#create` dispatches the *same untrusted payload* to handlers, and the base `Handler` class (used by `PushHandler`, all `PullRequest::*Handler`s, etc.) resolves the actual target repository/stack from a **different** payload field, `repository.full_name`, with no cross-check against the organization that was used for signature verification: [5](#0-4) 

For example `PushHandler` syncs/updates whatever stacks match `repository_name`: [6](#0-5) 

and pull-request handlers archive/unarchive review stacks or update PR state based on `params.repository.full_name`: [7](#0-6) 

**The broken equality**: "organization that authenticated" (`repository.owner.login`/`organization.login`, used only to pick a webhook secret) must equal "the repository that is written" (`repository.full_name`, used by every handler to select the Stack/Repository to mutate). Nothing in `WebhooksController` or `Handler` enforces this. An attacker who controls (or who targets) any GitHub App entry with no `webhook_secret` configured, or who can produce a valid signature for *any one* configured organization (e.g. their own org, or one with a known/weak/blank secret), can set `repository.owner.login` to that organization while setting `repository.full_name` to an arbitrary victim repository. The signature check validates the (attacker-chosen, correctly-signed-or-secret-less) organization, but the write is applied to the victim repository's Stack/PullRequest/Commit records.

### Impact Explanation
This allows cross-repository writes without ever proving the payload originated from the victim organization's GitHub App: forged `push` events can trigger `GithubSyncJob`/commit-status updates on a victim's Stack, and forged `pull_request` events can archive/unarchive review stacks or mutate PR state for repositories the attacker does not control and for which they never produced a signature verifiable against that repository's own secret. Per the rules, cross-repository writes are a Critical-severity impact.

### Likelihood Explanation
Exploitability requires: (1) at least one configured GitHub App/organization entry with a `webhook_secret` that is `nil`/blank (explicitly supported and shown as a valid config in `docs/setup.md`, and the default in `test/dummy/config/secrets.test.json`), or knowledge of one org's secret; and (2) the multi-organization webhook routing feature being used, which is a documented, first-class Shipit configuration option. No session, API token, or GitHub write access is required — only the ability to POST to the public `/webhooks` endpoint, matching the "unprivileged attacker" constraint.

### Recommendation
After parsing the payload but before dispatching to handlers, verify that the organization/app used to validate the signature actually matches the owner of `repository.full_name` (or `organization.login`) in the same payload, and reject the request if they differ. Additionally, treat a missing `webhook_secret` as "verification not configured" rather than "always verified" (`return true unless webhook_secret`), or require an explicit opt-in flag to accept unsigned webhooks for a given organization.

### Proof of Concept
1. Configure two organizations in `secrets.yml` under multi-app mode (per `docs/setup.md`'s "Using Multiple Github Applications" section): `OrgAttacker` with `webhook_secret: nil` (or a secret the attacker knows) and `OrgVictim` with a real secret and a real `victim-repo` stack.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "full_name": "OrgVictim/victim-repo", "owner": { "login": "OrgAttacker" } }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, which — because `OrgAttacker`'s `webhook_secret` is blank — returns `true` regardless of the `X-Hub-Signature` header (or the attacker computes a valid HMAC using the known `OrgAttacker` secret).
4. `Shipit::Webhooks::Handlers::PushHandler` then resolves stacks via `payload.dig('repository', 'full_name')` = `OrgVictim/victim-repo`, and enqueues `GithubSyncJob` / updates commit state for the victim stack, even though the request was never validated against `OrgVictim`'s webhook secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
