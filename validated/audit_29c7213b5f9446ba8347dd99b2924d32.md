### Title
Cross-repository `status` webhook forges CI status on unrelated stack's merge request head commit, bypassing merge-queue gate - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` matches incoming `status` webhooks to `Commit` records by SHA alone, with no check that the webhook's own `repository` field matches the repository that actually owns the target commit's stack. Because `MergeRequest#all_status_checks_passed?` and `reject_unless_mergeable!` trust whatever `Status` rows exist on `head`, a webhook delivered from an attacker-controlled repository can create a `success` `Status` attributed to a victim stack's commit and flip the merge gate open.

### Finding Description
Broken binding, stated explicitly: the code should enforce
`payload.dig('repository', 'full_name') == commit.stack.repository.full_name` (or equivalently, the webhook's declared repository must match the repository owning the `Commit`/`Stack` being written to) before persisting a `Status` that `StatusChecker` will treat as authoritative for that stack's merge gate.

In reality, no such check exists: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it looks up commits purely by `sha` across the entire database, ignoring `payload.dig('repository', 'full_name')` entirely. Note the base `Handler` class *does* provide a correctly scoped helper, `stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks`: [2](#0-1) 

but `StatusHandler` never uses it — it never validates the SHA belongs to the webhook's claimed repository.

`create_status_from_github!` then writes the `Status` using the commit's own `stack_id` (its `belongs_to :stack`), not anything derived from the incoming payload: [3](#0-2) [4](#0-3) 

Downstream, `MergeRequest#all_status_checks_passed?` blindly consumes `head.statuses_and_check_runs` (all statuses ever attached to that commit row, regardless of origin) via `StatusChecker`: [5](#0-4) 

and `reject_unless_mergeable!` relies on the same tainted checks: [6](#0-5) 

**Exploit flow**: the attacker forks the victim's public repository (a normal, unprivileged GitHub action). Because git objects are shared across forks, the victim PR's head commit SHA is identical in the attacker's fork. The attacker (per the stated threat model capability of being able to "emit webhooks from a repository they own") sends `POST /webhooks` with header `X-Github-Event: status` and a body such as:
```json
{"sha": "<victim head sha>", "state": "success", "repository": {"full_name": "attacker/other-repo", "owner": {"login": "attacker-org"}}}
```
`WebhooksController#verify_signature` calls `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload: [7](#0-6) [8](#0-7) 

Signature verification only proves the request was signed by *some* org/app config known to Shipit and matching the attacker's own claimed org — it says nothing about whether that org/repo owns the commit being mutated. Once past that gate, `StatusHandler#process` writes a `Status` onto the victim's `Commit` row using the victim's own `stack_id`, and `MergeRequest#all_status_checks_passed?` reports success.

Existing guards do not close this gap: `drop_unhandled_event` only checks the event type is registered, `verify_signature` only checks the signature validity for the *claimed* org (not commit ownership), and `ExplicitParameters` (`StatusHandler.params`) only validates field types/presence, not cross-repository consistency.

### Impact Explanation
A payload legitimately signed by/for one repository can create a `Status` record for and mutate the merge-readiness state of a completely unrelated stack's commit, satisfying the "payload for one repository mutating another's stack, commit ... or an unauthorized merge" Critical category. Concretely: `MergeRequest#all_status_checks_passed?` flips true and `reject_unless_mergeable!` returns `false` (no rejection) purely from a forged cross-repo status, letting a pull request merge into the victim stack without the victim repository's actual CI ever passing. This is repeatable against any stack/commit whose SHA the attacker can learn (trivial via fork or public PR page) and any org from which the attacker can get a validly-signed webhook delivered to the shared `/webhooks` endpoint, so the blast radius spans every tenant/stack served by the same Shipit deployment.

### Likelihood Explanation
Preconditions: the attacker needs (a) the target commit's SHA (public information for any open PR), and (b) a way to deliver a webhook that satisfies `verify_signature` — a repository/org they control that already has a valid webhook/app relationship with the Shipit deployment. Per the threat model, this is explicitly granted as an unprivileged capability ("emit webhooks from a repository they own"). No Shipit session, API token, or secret is required. This is a very low-cost, fully repeatable attack (single HTTP POST) with no rate limiting or additional authorization checks in the path.

### Recommendation
In `StatusHandler#process` (and analogously `CheckSuiteHandler`), scope the commit lookup to the repository declared in the payload instead of a bare SHA match — e.g., resolve `stacks` (as `Handler#stacks` already does via `Repository.from_github_repo_name(repository_name)`) and restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or otherwise verify `commit.stack.github_repo_name == repository_name` before calling `create_status_from_github!`.

### Proof of Concept
Add a test in `test/controllers/webhooks_controller_test.rb`:
```ruby
test "cross-repo status webhook forges Status for unrelated stack and opens merge gate" do
  merge_request = shipit_merge_requests(:shipit_pending) # pending MR on victim stack
  head = merge_request.head
  refute merge_request.all_status_checks_passed?
  refute merge_request.reject_unless_mergeable!.nil? # still gated (adjust to actual pre-state)

  request.headers['X-Github-Event'] = 'status'
  forged_payload = {
    'sha' => head.sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'branches' => [{ 'name' => 'master' }],
    'repository' => { 'full_name' => 'attacker/other-repo', 'owner' => { 'login' => 'attacker-org' } }
  }.to_json

  assert_difference 'head.statuses.count', 1 do
    post :create, body: forged_payload, as: :json
  end

  assert_predicate merge_request.reload, :all_status_checks_passed?
  assert_equal false, merge_request.reject_unless_mergeable!
end
```
Assertions on both sides of the equality: before the webhook, `head.statuses.count` reflects only statuses created for the victim repository; after the forged cross-repo webhook, it increases and `all_status_checks_passed?`/`reject_unless_mergeable!` flip, proving `payload['repository']['full_name'] != commit.stack.repository.full_name` yet the status is accepted as if it matched.
