### Title
Webhook signature is verified against an organization taken from an unauthenticated field that is never cross-checked against the repository the event actually mutates - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC signature with by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, then checks the raw body's signature against that org's `webhook_secret`. [1](#0-0)  Every event handler, however, resolves which `Stack`/`Repository` to mutate from a *different* field of the same untrusted payload: `payload.dig('repository', 'full_name')`. [2](#0-1)  Nothing in the controller or in `Handler` enforces that `repository.owner.login` (the field used to pick the signing organization) and the owner segment embedded in `repository.full_name` (the field used to pick the repository being acted on) refer to the same organization.

### Finding Description
This is the direct analog of the reported bug class: a value that is *acted upon* is never actually covered/bound by the verification step that is supposed to authorize it. In the original report, `OracleManager.setBeaconData` let value flow (profit/loss) be attributed based on timing that wasn't part of what the mechanism actually enforced. Here, the "authorization" performed (HMAC signature verified with organization X's secret) does not bind to the "authorized subject" acted upon (repository under organization Y).

Concretely:
- `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and uses it solely to select `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to validate `X-Hub-Signature` against the entire raw body. [3](#0-2) [4](#0-3) 
- Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches the full parsed payload to handlers such as `PushHandler`. [5](#0-4) 
- `PushHandler#process` resolves the target `stacks` via `Handler#stacks`, which looks up `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a completely separate JSON field from the one used for signature-org selection. [6](#0-5) [2](#0-1) 

Binding that should hold but doesn't: `organization_that_authenticates(payload) == owner(repository_that_is_written(payload))`. Before an attacker's crafted request, both fields are always consistent because GitHub itself constructs the payload. After the attacker's forged POST, they can diverge: `repository.owner.login` (and thus the HMAC secret selected) is set to an organization the attacker controls the webhook secret for, while `repository.full_name` names an entirely different, victim organization's repository that is tracked as a `Stack` in the same Shipit instance.

### Impact Explanation
Any party who legitimately knows one organization's GitHub App `webhook_secret` configured in this Shipit instance (a normal, intended credential for that org's own webhook delivery, not a privileged Shipit account) can forge a POST with a valid signature for their own org while setting `repository.full_name` to point at a different org/repo tracked by the same Shipit deployment. This lets them:
- Trigger `GithubSyncJob`/`stack.sync_github` on a victim stack via `PushHandler`, forcing sync to an attacker-chosen `expected_head_sha`. [7](#0-6) 
- Manipulate commit `Status` records or other repository-scoped state for a repository the attacker's organization was never granted control over.

This is a cross-repository / cross-organization write that breaks the intended "each organization's webhook secret only authorizes writes to that organization's own repositories" boundary, matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires the attacker to already know a `webhook_secret` for at least one organization onboarded to the same multi-tenant Shipit deployment (`Shipit.github(organization:)` supports multiple orgs, each with its own `webhook_secret` from `TOP_LEVEL_GH_KEYS`). [8](#0-7)  That is a realistic scenario for any Shipit instance shared across multiple organizations/teams, since each org's admin legitimately possesses their own org's webhook secret as part of normal GitHub App setup — no privileged Shipit account, `ApiClient` token, or repository write access on GitHub is needed, satisfying the "unprivileged attacker" scope requirement.

### Recommendation
After verifying the HMAC signature, re-derive/require that the repository the handler acts on (`repository.full_name`) belongs to the same organization whose secret validated the signature (`repository.owner.login` / `organization.login`), rejecting the request (422) on mismatch. Alternatively, verify the signature per-repository/stack using a secret scoped to the exact repository being mutated rather than one selected from an unauthenticated field of the same payload.

### Proof of Concept
1. Shipit instance is configured for two organizations, `attacker-org` and `victim-org`, each with its own GitHub App `webhook_secret` (`s_attacker`, `s_victim`) as per `config/secrets.yml`/`TOP_LEVEL_GH_KEYS`.
2. Attacker, a legitimate admin of `attacker-org`'s GitHub App (knows `s_attacker`), builds a JSON push payload:
   ```json
   {
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" }
   }
   ```
3. Computes `X-Hub-Signature: sha1=HMAC-SHA1(s_attacker, raw_body)` and POSTs directly to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` reads `repository_owner` = `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the HMAC check succeeds since the attacker signed with `s_attacker`. [3](#0-2) 
5. `PushHandler#process` resolves `stacks` via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, despite the request never having been authenticated for `victim-org`. [7](#0-6)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
