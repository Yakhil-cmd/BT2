### Title
Unvalidated `base_aa` reference in parameterized AA definition causes an uncaught exception that crashes the node on the first trigger - ([File: aa_composer.js])

### Summary
`aa_validation.js`'s `validateAADefinition()` accepts a parameterized AA definition as soon as `template.base_aa` is a syntactically valid address (`isValidAddress`), without ever checking that the referenced address actually is a registered, regular AA. `aa_composer.js`'s `handleTrigger()` later dereferences that unchecked value and, if it does not resolve to an AA, executes `throw Error("base AA not found: " + template.base_aa)` inside an asynchronous DB callback that is not wrapped by any `try/catch`. Because `network.js` installs a top-level `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the process ("crash the process to avoid ending up in an inconsistent state"), any single unprivileged unit poster can post one such AA definition unit and one small payment (trigger) to it and crash the whole node — the same bug class as the CoreDNS `PacketConn.ReadFrom` panic: a value that should have been validated/non-nil at a point in the code is used unconditionally in a "no-recovery" error/log path, and a single crafted 28-byte-equivalent packet (here, one small posted unit) reaches it before any protective validation stops it.

### Finding Description
1. **Definition-time validation gap** — In `aa_validation.js`, `validateAADefinition()` handles parameterized AAs: [1](#0-0) 
Only `isValidAddress(template.base_aa)` is checked (format/checksum only). There is no check that `base_aa` corresponds to an address that is actually a registered AA (or exists at all) at validation time. This validation result feeds directly into `validation.js`'s `validateInlinePayload` `"definition"` case, which is exactly the app-level path used to define AAs from ordinary posted units. [2](#0-1) 
Because `template.base_aa` need only satisfy the base32/checksum format `isValidAddress`, an attacker (any unprivileged unit poster) can define a parameterized AA whose `base_aa` points to an address that is not, and never will be, an AA.

2. **Trigger-time dereference without a null/found check that avoids the throw** — When any user (an "AA trigger sender") later sends a payment to this parameterized AA address, `aa_composer.js`'s `handleTrigger()` resolves `base_aa`: [3](#0-2) 
`storage.readAADefinition()` calls back with `arrBaseDefinition === undefined/null` when the address is not a known AA definition, and the code immediately does `throw Error("base AA not found: " + template.base_aa)`. This throw happens **inside an asynchronous database callback**, several stack frames removed from any caller-level `try/catch`; nothing in `handlePrimaryAATrigger`, `estimatePrimaryAATrigger`, or `dryRunPrimaryAATrigger` wraps the call to `handleTrigger` in a `try/catch` that could convert this into a graceful bounce.

3. **No recovery — the process crashes globally** — `network.js` installs a process-wide safety net that turns any uncaught exception into a hard crash: [4](#0-3) 
This is the functional analogue of CoreDNS's missing `recover()`-before-`addr.String()` ordering: a single malformed/edge-case input reaches a code path where a value that "should" have been validated (non-nil `readFrom` result / existing `base_aa` AA) is used unconditionally, and the resulting panic/exception is not contained, so it takes down the whole server process.

### Impact Explanation
Any single unit poster can post one small AA-definition unit (defining a parameterized AA with a `base_aa` that is a valid-looking but non-AA address) and then post one trivial payment unit that triggers it. As soon as the trigger is processed (which happens on every full node and light-vendor-serving hub that validates and executes AA triggers), the uncaught `Error` propagates to the top-level `uncaughtException` handler, which re-throws and crashes the Node.js process for every node that processes that trigger. This yields a network-wide, remotely-triggerable denial of service: the node stops confirming any new units until restarted, satisfying the "network unable to confirm new units" bar for a valid, high-impact analog.

### Likelihood Explanation
Likelihood is high: constructing the AA definition and the triggering payment requires no special privileges, no cooperation from other parties, and no timing race — it is a straightforward two-unit sequence (define parameterized AA → send payment to it) that any wallet/user/bot capable of posting units can perform. The only requirement is that `base_aa` pass `isValidAddress` (a purely syntactic/checksum check), which is trivial to satisfy with any freshly generated, never-before-used address.

### Recommendation
- In `aa_validation.js` `validateAADefinition()`, when `template.base_aa` is present, verify (via `storage.readAADefinition`/an async DB check) that the referenced address is actually a registered regular AA definition before accepting the AA definition, rejecting with a normal validation error (`callback("base_aa is not a valid AA")`) if not.
- Defensively, in `aa_composer.js` `handleTrigger()`, replace the `throw Error("base AA not found: " + template.base_aa)` with a call to `bounce("base AA not found: " + template.base_aa)` (or an equivalent callback-based error path) so that any inconsistency discovered at trigger time is handled as a normal bounce rather than an uncaught exception.
- More generally, audit other `throw Error(...)` statements inside asynchronous DB callbacks in `aa_composer.js`/`storage.js` that are reachable from attacker-controlled definitions or triggers, and convert them to graceful error callbacks, since the process-wide `uncaughtException` handler turns every one of them into a full node crash.

### Proof of Concept
1. Attacker generates a random address `X` that is syntactically valid (`isValidAddress(X)` true) but has never been defined as anything (not an AA, not a normal address).
2. Attacker posts a unit with a `definition` message defining a parameterized AA:
   ```json
   { "app": "definition", "payload": { "address": "<chash of def>", "definition": ["autonomous agent", { "base_aa": "X", "params": {"p":"1"} }] } }
   ```
   This passes `validateAADefinition` per `aa_validation.js:734-744` because only `isValidAddress(X)` is checked.
3. Attacker (or anyone) posts a payment unit sending bytes to the new parameterized AA's address.
4. When the trigger is processed, `aa_composer.js` `handleTrigger()` calls `storage.readAADefinition(conn, "X", mci, cb)`; since `X` is not an AA, `cb(undefined)` fires and the code executes `throw Error("base AA not found: X")` inside the DB callback (`aa_composer.js:436-438`).
5. The exception is uncaught by any local `try/catch`, propagates to `process.on('uncaughtException', ...)` in `network.js:4530-4543`, which re-throws, crashing the node process for every full node/hub that processed the trigger.
