### Title
`MultiKey::new` accepts duplicate `AnyPublicKey` entries, letting one signer satisfy a k-of-n approval threshold with fewer distinct signers than intended - ([File: types/src/transaction/authenticator.rs])

### Summary
The `MultiKey` type used for the K-of-N `MultiKeyAuthenticator` authentication scheme does not check for duplicate public keys when constructed. As a result, a single private key placed at two (or more) index slots in the `public_keys` vector can supply two "distinct" signatures (both derived from the same key) and satisfy `signatures_required`, even though the account's owners/co-signers believe N distinct approvers are required.

### Finding Description
`MultiKey::new` only validates the count relationship between keys and threshold, not uniqueness of the keys: [1](#0-0) 

`MultiKeyAuthenticator::to_single_key_authenticators`/`verify` then simply iterates over whichever indices have signatures set and checks `count == signatures_required`, with no distinctness check on the underlying public keys: [2](#0-1) 

This is reachable directly from unprivileged input: the API layer parses a `MultiKeySignature` from a submitted transaction and calls `MultiKey::new`/`MultiKeyAuthenticator::new` with attacker-controlled public keys and indices: [3](#0-2) 

The Move-level `multi_key.move` primitive used to construct the authentication key at account-creation/key-rotation time has the identical gap — no dedup check on the public key vector: [4](#0-3) 

The codebase's own unit test demonstrates and accepts exactly this outcome: a `MultiKey` is built with keys `[sender0, sender1, sender1]` (sender1's key duplicated) and `signatures_required = 2`. Signing with indices `(1, sig1)` and `(2, sig1)` — the same private key providing both "required" signatures — passes verification: [5](#0-4) [6](#0-5) 

Notably, the separate resource-based `multisig_account.move` module (a different multisig mechanism, unrelated to `MultiKey`) explicitly guards against this exact class of bug by rejecting duplicate owner addresses via `validate_owners`/`EDUPLICATE_OWNER`: [7](#0-6) 

This asymmetry indicates the missing uniqueness check in `MultiKey`/`multi_key.move` is an oversight rather than an intentional design choice.

### Impact Explanation
`MultiKey` is the general K-of-N authentication scheme used to derive authentication keys (`AuthenticationKey::multi_key`) for accounts intended to require N independent approvers (analogous to `MultiEd25519`, generalized across key types). Whoever controls the construction of the `MultiKey` public-key set (e.g., during joint account setup, key rotation to a shared/backup scheme, or any flow where a `MultiKey` is meant to represent multiple independent approvers) can insert a duplicate of their own public key into two or more slots. That single party can then satisfy `signatures_required` alone — e.g., turning an intended "2-of-3, requiring cooperation of a second key holder" account into one unilaterally controlled by one key. This breaks the "approval-set" / signer-set guarantee that the number of required signatures corresponds to the number of independent approving keys, matching the admission-impact category of "authenticator/multisig approval validation accepting the wrong signing material or wrong approval set."

### Likelihood Explanation
High practical likelihood of misuse and low likelihood of accidental self-detection: any unprivileged party assembling a `MultiKey` authentication scheme (via API-submitted transaction, SDK, or Move `multi_key::new_multi_key_from_single_keys`) can trivially include a duplicate public key with no validation error at construction, transaction-authenticator-parsing, or verification time. The codebase's own test suite exercises and accepts this exact scenario without objection, confirming the code path is live and unguarded in production logic (not test-only scaffolding).

### Recommendation
Add a uniqueness check over `public_keys` in `MultiKey::new` (types/src/transaction/authenticator.rs) and in `multi_key::new_multi_key_from_single_keys`/`deserialize_multi_key` (aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move), rejecting construction/deserialization when any two entries in `public_keys` are equal, mirroring the `EDUPLICATE_OWNER` pattern already used in `multisig_account.move`. Because `MultiKey::deserialize`/`new_public_key_from_bytes` are also reachable from BCS-encoded account data (e.g., stored authentication keys), consider whether this check should also apply on-chain deserialization paths and add corresponding native/BCS-level validation to prevent silently down-graded k-of-n guarantees for already-created accounts.

### Proof of Concept
The existing repository test is itself the proof of concept: [8](#0-7) 
It constructs `MultiKey::new(vec![any_sender0_pub, any_sender1_pub, any_sender1_pub], 2)` (duplicate `any_sender1_pub`), builds a `MultiKeyAuthenticator` with two signatures at indices `1` and `2` that are both produced by `sender1`'s single private key, and shows `to_single_key_authenticators()` succeeds and `signed_txn.verify_signature()` returns `Ok(())`, i.e., a threshold requiring "2 signatures" is fully satisfied using only one distinct signer's key.

    pub fn to_single_key_authenticators(&self) -> Result<Vec<SingleKeyAuthenticator>> {
        ensure!(
            self.signatures_bitmap.last_set_bit().is_some(),
            "There were no signatures set in the bitmap."
        );

        ensure!(
            (self.signatures_bitmap.last_set_bit().unwrap() as usize) < self.public_keys.len(),
            "Mismatch in the position of the last signature and the number of PKs, {} >= {}.",
            self.signatures_bitmap.last_set_bit().unwrap(),
            self.public_keys.len(),
        );
        ensure!(
            self.signatures_bitmap.count_ones() as usize == self.signatures.len(),
            "Mismatch in number of signatures and the number of bits set in the signatures_bitmap, {} != {}.",
            self.signatures_bitmap.count_ones(),
            self.signatures.len(),
        );
        ensure!(
            self.signatures.len() >= self.public_keys.signatures_required() as usize,
            "Not enough signatures for verification, {} < {}.",
            self.signatures.len(),
            self.public_keys.signatures_required(),
        );
        let authenticators: Vec<SingleKeyAuthenticator> =
            std::iter::zip(self.signatures_bitmap.iter_ones(), self.signatures.iter())
                .map(|(idx, sig)| SingleKeyAuthenticator {
                    public_key: self.public_keys.public_keys[idx].clone(),
                    signature: sig.clone(),
                })
                .collect();
        Ok(authenticators)
    }

    pub fn verify<T: Serialize + CryptoHash>(&self, message: &T) -> Result<()> {
        let authenticators = self.to_single_key_authenticators()?;
        authenticators
            .iter()
            .try_for_each(|authenticator| authenticator.verify(message))?;
        Ok(())
    }

        );

            "The number of public keys is greater than {}.",
            MAX_NUM_OF_SIGS
        );

        ensure!(
            public_keys.len() >= signatures_required as usize,
            "The number of public keys is smaller than the number of required signatures, {} < {}",
            public_keys.len(),
            signatures_required
        );

        Ok(Self {
            public_keys,
            signatures_required,
        })

    /// Creates a new MultiKey public key from a vector of single key public keys and a number representing the number of signatures required to authenticate a transaction.
    public fun new_multi_key_from_single_keys(single_keys: vector<single_key::AnyPublicKey>, signatures_required: u8): MultiKey {
        let num_keys = single_keys.length();
        assert!(
            num_keys > 0,
            error::invalid_argument(E_INVALID_MULTI_KEY_NO_KEYS)
        );
        assert!(
            num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS,
            error::invalid_argument(E_INVALID_MULTI_KEY_TOO_MANY_KEYS)
        );
        assert!(
            (signatures_required as u64) <= num_keys,
            error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED)
        );
        MultiKey { public_keys: single_keys, signatures_required }
    }
