### Title
Webhook signature is verified against the wrong GitHub organization, letting one tenant forge events for another tenant's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (documented in `config/secrets.development.shopify.yml` and `docs/setup.md`, each GitHub organization has its own `webhook_secret`. The `WebhooksController` selects which secret to verify the HMAC signature with based on `repository.owner.login` (or `organization.login`), but the actual event handlers resolve the repository/stack to write to using the unrelated `repository.full_name` field from the same JSON body. Since these two fields are never cross-checked, an attacker who only knows organization A's webhook secret can forge a signed payload whose `repository.full_name` points at organization B's repository, causing Shipit to act on organization B's stacks (fake CI statuses, forced re-sync, check-run refresh, PR archive/unarchive, review-stack creation) despite the request never being authenticated for organization B.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate against using only the claimed owner login: [1](#0-0) [2](#0-1) 

That is, `repository_owner` is read directly from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`), and `Shipit.github(organization: repository_owner)` is used purely to look up the secret used for HMAC comparison: [3](#0-2) 

Once the signature checks out (proving only that *some* known secret for the organization named in `repository.owner.login` was used), the event is dispatched to handlers that resolve the actual target repository from a **different** field of the same payload — `repository.full_name` — with no re-validation that it matches the owner used for signing: [4](#0-3) 

Downstream handlers use that resolved `stacks`/`repository` to mutate state, e.g.:
- `PushHandler` re-syncs a stack from GitHub (`stack.sync_github`). [5](#0-4) 
- `StatusHandler` writes a CI status onto any `Commit` matching a given `sha`, regardless of stack, purely from the claimed `state`/`context` in the payload. [6](#0-5) 
- `CheckSuiteHandler` schedules check-run refresh for arbitrary stacks/commits resolved via `repository.full_name`. [7](#0-6) 
- `PullRequest` handlers (opened/labeled/reopened/unlabeled) archive, unarchive, or auto-provision review stacks purely based on `params.repository.full_name`. [8](#0-7) 

`Repository.from_github_repo_name` performs a plain owner/name lookup with no tie back to which GitHub App/secret authenticated the request: [9](#0-8) 

**Binding broken:** `organization authenticated by HMAC (repository.owner.login)` ≠ `repository actually written to (repository.full_name)`. These are two independent JSON fields inside the same signed body; the signature over the whole body only proves *a* valid secret was used to produce the HMAC, not that the secret used corresponds to the organization named in `full_name`. A malicious tenant admin who legitimately possesses their own org's `webhook_secret` (a config value they themselves provision when creating their own GitHub App per `docs/setup.md`) can therefore forge a request that is "authenticated" as their own org but whose `repository.full_name` names a victim org's repository.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" boundary explicitly called out as in-scope. The strongest concrete impact is via `StatusHandler`: an attacker can push a forged, self-signed `status` webhook claiming `state: "success"` for an arbitrary commit `sha` belonging to a victim organization's stack. Since `Commit#deployable?` is driven by `success?` (derived from `statuses`) combined with `stack.ignore_ci?`, this fake status can make a victim's commit appear CI-green: [10](#0-9) 
Combined with `continuous_deployment?`, a falsely "successful" status can trigger `schedule_continuous_delivery` and an unauthorized deploy of a commit that never actually passed CI, on a stack the attacker was never authorized to write to: [11](#0-10) 
This matches the "unauthorized deploy" High-severity impact category. Other handlers (push resync, check-run refresh, PR archive/provisioning) provide additional cross-tenant write surface even without deploy triggering.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment (explicitly supported/documented configuration, not a misconfiguration outside scope), and (2) the attacker to be an administrator/holder of a legitimately configured `webhook_secret` for *any one* onboarded organization — not a privileged Shipit account or `ApiClient` token, and no interception of TLS or another org's secret is needed. Because `repository.owner.login` and `repository.full_name` are both attacker-controlled JSON fields and neither is cross-validated against the other or against which secret matched, exploitation is a straightforward crafted HTTP POST to `/webhooks` with a valid HMAC computed from the attacker's own secret.

### Recommendation
After the signature is verified, re-derive/validate the organization from the same field used by the handlers (`repository.full_name`'s owner segment, or `organization.login` for org-scoped events) and require it to match the organization whose secret validated the signature (`repository_owner` used in `verify_signature`). Reject the webhook (422) if they diverge, instead of trusting `full_name` unconditionally in `Handler#repository_name` and each handler's `Repository.from_github_repo_name` lookup.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `org-attacker` and `org-victim`, each with its own `webhook_secret` (per `config/secrets.development.shopify.yml` schema). Attacker legitimately administers `org-attacker`'s GitHub App and knows `org-attacker`'s `webhook_secret`.
2. Craft a `status` event JSON body:
```json
{
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "org-victim/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker secret, body)>`.
4. POST to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"org-attacker"`, looks up `org-attacker`'s app, and the HMAC passes.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — matching the victim's commit regardless of which org authenticated the request — and calls `create_status_from_github!`, writing a forged "success" status onto `org-victim`'s commit.
7. If `org-victim`'s stack has `continuous_deployment: true` and no other blocking statuses, `schedule_continuous_delivery` fires and the commit gets deployed without ever passing real CI.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
