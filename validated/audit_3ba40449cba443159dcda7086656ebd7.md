### Title
Status webhook handler mutates commits across unrelated repositories/organizations due to unscoped sha lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` with no scoping to the repository that signed the webhook. Any organization that legitimately signs a `status` webhook for its own repo will cause `create_status_from_github!` to run against **every** `Commit` row in the database sharing that sha, including commits belonging to stacks of totally unrelated repositories/organizations.

### Finding Description
The claimed binding is:
`stacks_signed_by(org) == stacks_mutated_by(webhook)`
where `stacks_signed_by(org)` is the set of stacks whose `Repository#owner` matches `repository_owner` verified by `WebhooksController#verify_signature` [1](#0-0) , and `stacks_mutated_by(webhook)` is the set of stacks whose commit rows get `create_status_from_github!` invoked.

`WebhooksController#verify_signature` only proves that the payload came from the GitHub App/organization matching `params.dig('repository','owner','login')` [2](#0-1) . It does not restrict which `Commit` rows the handler is allowed to touch afterward.

`Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that correctly scopes to `Repository.from_github_repo_name(repository_name)` [3](#0-2) , and `PushHandler` uses it properly (`stacks.not_archived.where(branch:)...`) [4](#0-3) .

`StatusHandler`, however, bypasses this scoping entirely: [5](#0-4) 

`Commit.where(sha: params.sha)` is a global, unscoped ActiveRecord query across the entire `commits` table — it does not join `stack` or filter by `stack.repository`. Any `Commit` row anywhere in the system with a matching `sha` column value gets `create_status_from_github!` invoked, which calls `add_status` and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`, ultimately capable of driving `ContinuousDeliveryJob` for the unrelated stack via `Commit#schedule_continuous_delivery` [6](#0-5) .

Sha collisions across repositories are not a cryptographic curiosity here — they occur routinely through forks (shared git history), squash/cherry-pick reuse across repos, or repositories seeded from the same template/initial commit. Any of these ordinary scenarios yields identical `sha` values in `Commit` rows belonging to entirely different `Repository`/`Stack`/organization records.

None of the existing guards address this: `verify_signature` only authenticates *that* the request came from `repository_owner`'s org, not *which commit rows* may be touched; `drop_unhandled_event` only checks the event type is handled; `ExplicitParameters` only validates the shape of `sha`/`state`/etc., not tenancy; there is no `Stack`/`Repository` filter anywhere in `StatusHandler`.

### Impact Explanation
A single, validly-signed webhook from `myorg` (owner of `myorg/app`, tracked by two Shipit stacks — staging and production) writes a `Status` row (via `statuses.replicate_from_github!`) onto **any** `Commit` row across the whole install that happens to share the sha, including a stack belonging to `otherorg/other` with no relationship to `myorg`. This is a cross-tenant, unauthorized write: a payload authenticated for one repository mutates another repository's commit/stack state, satisfying the Critical criterion "a payload for one repository mutating another's stack, commit, task or team." Because `add_status` can trigger `stack.schedule_merges` and `Commit#schedule_continuous_delivery`, this can drive `otherorg`'s stack toward an unauthorized deploy/merge decision if `otherorg`'s stack is `continuous_deployment?` and the status affects `deployable?`. The blast radius is every stack in the installation, not just repositories with the same name — repeatable on every status webhook `myorg` sends.

### Likelihood Explanation
Preconditions: (1) `myorg` legitimately owns and controls at least one repo/stack in the Shipit instance (trivial — any GitHub org can be onboarded, or an attacker who already has one legitimate low-privilege stack can leverage it), (2) some `Commit` row elsewhere in the DB shares a `sha` with a commit `myorg` controls. This is easily achievable: forking a public unrelated repo into `myorg`'s namespace preserves identical commit shas for all pre-fork history; Shipit's `PushHandler`/git ingestion will create `Commit` rows for those shas under `myorg`'s stack the moment they're pushed/synced. The attacker then triggers (or waits for) GitHub to send a `status` event for that sha (achievable by pushing a commit with that sha to a branch and having any CI system, even a no-op one, report status — or by using GitHub's API within their own repo permissions to set a commit status on their fork, which GitHub allows for a repo the attacker controls). Attacker cost is low; feasibility is high given fork-based sha reuse is common; and it is fully repeatable.

### Recommendation
Scope `StatusHandler#process` to the repository that signed the webhook, mirroring `PushHandler`'s use of the `stacks` helper, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the query never crosses the `Repository.from_github_repo_name(repository_name)` boundary established by the webhook's own `repository.full_name` field.

### Proof of Concept
Minitest plan (no live GitHub, using existing test fixtures/factories):
```ruby
test "status webhook does not mutate commits belonging to unrelated stacks with the same sha" do
  myorg_repo = shipit_repositories(:myorg_app) # or create Repository owned by myorg
  otherorg_repo = shipit_repositories(:otherorg_other) # unrelated repo/org

  myorg_stack = create_stack(repository: myorg_repo)
  otherorg_stack = create_stack(repository: otherorg_repo)

  shared_sha = 'a' * 40
  myorg_commit = myorg_stack.commits.create!(sha: shared_sha, ...)
  otherorg_commit = otherorg_stack.commits.create!(sha: shared_sha, ...)

  before_other_statuses = otherorg_commit.statuses.count

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => myorg_repo.github_repo_name, 'owner' => { 'login' => 'myorg' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Binding check: stacks_mutated_by(webhook) must equal stacks_signed_by(myorg)
  assert_equal before_other_statuses, otherorg_commit.reload.statuses.count,
    "status event signed by myorg must not mutate otherorg's unrelated commit/stack"
  assert_operator myorg_commit.reload.statuses.count, :>, 0
end
```
This test is expected to **fail** against the current `StatusHandler` implementation (asserting the violation), demonstrating that `otherorg_commit.statuses.count` increases even though the webhook was signed only for `myorg`.
