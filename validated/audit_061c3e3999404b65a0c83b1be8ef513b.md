### Title
Webhook signature is verified using an attacker-controlled organization field, letting one tenant forge events for another tenant's repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and therefore the HMAC secret) to validate a webhook against by reading `repository.owner.login` / `organization.login` straight out of the still-unverified JSON body, then checks the signature with that secret. The event handlers, however, decide *which stacks/repositories to mutate* using a different field from the very same untrusted body (`repository.full_name`). Because both fields live inside the same attacker-supplied payload, anyone who knows the webhook secret for *any one* organization configured in this Shipit instance can forge a payload that authenticates as "their" organization while pointing `repository.full_name` at a completely different organization's tracked repository, and have the handler act on it.

### Finding Description
`verify_signature` selects the signing key from the body before trusting the body: [1](#0-0) 

`repository_owner` is derived purely from the JSON payload, with no relation to who actually delivered the request: [2](#0-1) 

Once `verified` is truthy, `create` dispatches the *entire* raw payload to the registered handlers: [3](#0-2) 

Handlers locate the `Stack`(s) to modify using a different field of the same payload — `repository.full_name` — with no check that this repository belongs to the organization whose secret was used to authenticate the request: [4](#0-3) 

Shipit explicitly supports multiple organizations, each with its own independent `webhook_secret`/GitHub App, all mounted on the same instance and able to track repositories belonging to different orgs: [5](#0-4) 

So the equality the code implicitly (and wrongly) assumes is:
`organization whose secret authenticated the HTTP request == organization/repository that the handler is about to mutate`

Nothing enforces this. An attacker who administers Org A (and therefore legitimately knows Org A's `webhook_secret`, since they created that GitHub App/installation) can sign an arbitrary JSON body with Org A's secret while setting `repository.owner.login`/`organization.login` to `"org-a"` (so `verify_signature` selects Org A's secret and passes) and setting `repository.full_name` to `"org-b/victim-repo"` (a repository actually tracked by Shipit under a different, victim organization). The signature check passes, and the handler then acts on Org B's stack.

This is directly analogous to the reported `mintTo` bug: a guard (`MintStarted`, here "does the authenticated organization match the entity being written to") exists on a related code path but is missing at the point of actual state mutation, so an operation that should be blocked/scoped by the trust boundary is instead performed unconditionally on attacker-chosen state.

### Impact Explanation
The most severe reachable primitive is the `status` webhook handler, which creates a `Status` record on an arbitrary commit of the victim stack with an attacker-chosen `state` (e.g. `success`): [6](#0-5) 

If the victim stack has continuous deployment enabled, a forged `success` status is sufficient to automatically trigger a real deploy of that (possibly unreviewed / malicious) commit: [7](#0-6) 

This constitutes an unauthorized deploy/cross-repository write triggered purely by forging a webhook signed with a *different, unrelated* tenant's secret — squarely in the Critical impact bucket (cross-repository writes / unauthorized deploy). Other handlers (`push`, `check_suite`, `pull_request`, `membership`) can similarly be redirected at a victim organization's stacks/teams because none of them validate that the authenticated organization matches the repository/organization being mutated.

### Likelihood Explanation
Requires only: (1) the attacker legitimately controls one organization configured in the same multi-tenant Shipit deployment (a normal, unprivileged-relative-to-other-tenants position — they only know *their own* `webhook_secret`, never the victim's), and (2) they can send an HTTP POST to the shared `/webhooks` endpoint, which is unauthenticated by design (webhook endpoints don't require a Shipit session or `ApiClient` token). No GitHub write access to the victim repo, no Shipit account, and no knowledge of the victim's secret are needed — only crafting the JSON body and computing HMAC-SHA1 with a secret the attacker already legitimately possesses.

### Recommendation
After computing `verified`, cross-check that the organization used to select the signing key actually owns the repository/organization the payload claims to act on (e.g., re-derive `repository_owner` after verification and confirm the `Repository`/`Stack` records that the handler would touch belong to that same organization) before allowing handlers to mutate state. Reject the request if `repository.full_name`'s owner segment doesn't match the verified `repository_owner`/`organization.login` used to select the secret.

### Proof of Concept
1. Deploy Shipit configured (as documented) with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` (see `config/secrets.development.shopify.yml` structure) - `org-b/victim-repo` is a tracked Shipit stack with `continuous_deployment: true`.
2. As the administrator of `org-a` (who legitimately knows `org-a`'s webhook secret), build a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "full_name": "org-b/victim-repo", "owner": { "login": "org-a" } }
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, body)>` and POST it with `X-Github-Event: status` to `/webhooks`.
4. `verify_signature` resolves `repository_owner` to `"org-a"`, fetches `org-a`'s app, and the HMAC validates — request is accepted.
5. The status handler creates a `success` Status on `org-b/victim-repo`'s commit; since continuous deployment is enabled, `ContinuousDeliveryJob` deploys the attacker-chosen commit on `org-b`'s stack, even though the attacker never had any credential, session, or write access tied to `org-b`.
