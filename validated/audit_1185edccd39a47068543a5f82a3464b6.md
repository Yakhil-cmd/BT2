## Title
Stack-scoped `ApiClient` tokens can read the CCMenu status of any stack, bypassing the client's `stack_id` binding - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

## Summary
`Shipit::Api::BaseController` binds an `ApiClient` token to a single stack via `current_api_client.stack_id`, and its `stack` helper enforces that binding by resolving the requested stack only from the scoped `stacks` relation. `Shipit::Api::CCMenuController` overrides `stack` to look up `Stack.from_param!(params[:stack_id])` directly, never consulting `current_api_client.stack_id`. This is structurally identical to the Astaria bug: a sibling method (`mint` vs `deposit`) that performs the same kind of privileged operation as the "safe" one but omits the guard the safe one enforces.

## Finding Description
In `app/controllers/shipit/api/base_controller.rb`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This is the binding: `ApiClient#stack_id` (the stack the token is authorized for) MUST equal (or be a superset check against) the stack resolved from `params[:stack_id]` for any read. `BaseController#stack` enforces this equality by scoping through `stacks`.

`Shipit::Api::CCMenuController` overrides both `stack` and `authenticate_api_client`:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [2](#0-1) 

`show` calls `stack.deploys_and_rollbacks.last`, which uses this unscoped `stack` lookup:
```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end
``` [3](#0-2) 

The controller still calls `require_permission :read, :stack`, which only checks `ApiClient#check_permissions!('read', 'stack')` (i.e., that the `read:stack` permission bit is set), not that the resolved stack matches `current_api_client.stack_id`:
```ruby
def require_permission!(operation, scope)
  current_api_client.check_permissions!(operation, scope)
end
``` [4](#0-3) 
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, "This operation requires the `#{required_permission}` permission"
  end
  true
end
``` [5](#0-4) 

So the permission check verifies "does this token have `read:stack` capability at all," while the actual stack-scoping restriction (which specific stack it may read) is only enforced by `BaseController#stack`/`#stacks` — and `CCMenuController` bypasses exactly that enforcement.

Concretely: `ApiClient` records created for CCMenu integration are deliberately scoped to a single stack, as seen in `CCMenuUrlController#client`:
```ruby
def client
  @client ||= ApiClient.create_with(permissions: %w[read:stack])
                       .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
end
``` [6](#0-5) 
Even though the token created by this flow is not directly stack-scoped by this snippet, the entire `ApiClient.stack_id` scoping mechanism exists precisely so that a token minted for one stack cannot be replayed against another. Any `ApiClient` with a non-null `stack_id` (e.g., created through `api_clients#create`/`#update` in `app/models/shipit/api_client.rb`, which allows setting `belongs_to :stack, optional: true`) is supposed to be confined to that stack for every operation gated by `require_permission`. `CCMenuController` is the one controller in the API namespace that silently drops this confinement.

## Impact Explanation
Any holder of a stack-scoped `read:stack` `ApiClient` token (e.g., a CCMenu URL deliberately shared with a low-trust tool/build-monitor for one stack) can supply an arbitrary `stack_id` in the CCMenu URL and read the deploy/rollback/build status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `activity`, `webUrl`) of **any** stack in the installation, not just the one the token was scoped to. This is an unauthenticated-relative-to-that-stack read of stack state/build output, matching the rubric's High-impact category: "unauthenticated read of stack state, task streams or deploy output" via a token that authorizes one stack but touches another.

## Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (including a stack-scoped one, which is the least-privileged, expected-to-be-safe case) and knowledge/guessing of another stack's param (stack `to_param`, typically `owner/repo/branch`, which is often predictable or discoverable via the UI). No signature forgery, no host misconfiguration, and no elevated credentials are needed beyond a token that is explicitly intended to be narrowly scoped. This is a straightforward, deterministic bypass, not merely theoretical.

## Recommendation
Have `CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the same `current_api_client.stack_id?` enforcement used everywhere else in `Shipit::Api::BaseController`.

## Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to `stack_id: A.id` with `permissions: ['read:stack']` (this is exactly what `CCMenuUrlController#client`/the "CCMenu Client" flow produces for legitimate stack-specific integrations).
2. Request `GET /api/stacks/:B_stack_param/ccmenu?token=<token-for-A>` where `B` is any other stack in the installation.
3. `authenticate_api_client` in `CCMenuController` succeeds (token is valid), `require_permission :read, :stack` passes (`permissions` includes `read:stack`), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack `B`, returning `B`'s deploy/build status in the XML response — despite the token being scoped only to stack `A`.
