### Title
Cross-repository commit status forgery via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` with no scoping to the repository that authenticated the webhook, unlike `PushHandler`, which explicitly resolves `stacks` via `Repository.from_github_repo_name(repository_name)`. Any commit row in the database whose `sha` matches the attacker-controlled `sha` parameter — regardless of which stack/repository it belongs to — will have a `Status` created and its cached deployability/blocking state recalculated.

### Finding Description
The broken binding: the handler implicitly assumes `commit.stack.repository == payload['repository']`, but the code never checks this equality anywhere.

Code path: `Shipit::WebhooksController#create` dispatches the parsed JSON `payload` to `Shipit::Webhooks.for_event(event)` handlers, which call `StatusHandler.call(payload)` → `new(payload).process` [1](#0-0) [2](#0-1) . `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This query has no `stack_id`/`repository` filter, unlike the base `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` and is used correctly by `PushHandler` (`stacks.not_archived.where(branch:)...`) [4](#0-3) [5](#0-4) . `StatusHandler` does not use `stacks` at all, so `payload['repository']` (the field `verify_signature` uses to authenticate the sender) is never joined against the `Commit`/`Stack` it mutates.

Once a matching `Commit` row is found by bare SHA, `create_status_from_github!` inserts a `Status` (`statuses.replicate_from_github!`) and recomputes `status`, `deployable?`, `blocked?` via `add_status`, which can flip the commit's/stack's ship/block state and trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges` [6](#0-5) [7](#0-6) .

`Commit.sha` is not a global unique key across repositories in this schema — it's only meaningfully unique per `stack_id` (see `Commit#by_sha` searching by prefix without stack scoping, and `belongs_to :stack` with no repository-level uniqueness constraint enforced at the DB/model level for `sha`) [8](#0-7) [9](#0-8) . Two different stacks (victim's and an unrelated repo tracked by the same Shipit instance, e.g. a fork sharing history, or any coincidentally colliding row inserted for another repository) can have `Commit` rows with the identical `sha` string. When that happens, a `status` webhook whose signature was validated only for the sender's own `repository_owner`/org (`verify_signature` in `WebhooksController`, using `Shipit.github(organization: repository_owner)`) still causes `StatusHandler` to write a `Status` against the victim's unrelated `Commit` row, because the handler never checks that `commit.stack.repository.full_name` matches the authenticated `payload['repository']['full_name']`.

Existing guards do not stop this: `verify_signature` only proves the payload's signature is valid for *some* organization the attacker controls/authenticated against (their own or an org where the same GitHub App secret applies) — it says nothing about which `Commit` rows the handler is allowed to touch [10](#0-9) . `ExplicitParameters` only validates the shape of `sha`/`state`/`context`, not ownership. There is no `require_permission!`, `stacks` scoping, or repository-equality check inside `StatusHandler`.

### Impact Explanation
A `status` event authenticated for repository A can create a `Status` record on, and alter the deployability/blocking state of, a `Commit` belonging to a completely different stack/repository B, as long as any `Commit` row with the same `sha` exists in B's stack. This is a payload for one repository mutating another's commit/stack state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attacker can drive `state: failure` with `context: ci/integration` to flip a victim's required-status gate, blocking (or, with `state: success`, forcing) ship decisions on the victim stack, and can repeat this for every SHA collision they can arrange (e.g., forking the victim's public repo so the shared git history's commit SHAs are byte-identical, which is the "shared commit SHA with attacker repo" precondition in the prompt).

### Likelihood Explanation
Preconditions: the attacker needs (1) a way to send a webhook payload that passes `verify_signature`, which is gated by `Shipit.github(organization: repository_owner).verify_webhook_signature` against the raw body and `X-Hub-Signature` header — this requires knowledge of the correct webhook secret for the `repository_owner` in the payload, which the attacker does not have unless they control an org/repo that has legitimately registered the GitHub App/webhook with Shipit; and (2) a `Commit` row that shares the exact SHA with the victim stack, which is realistic only for genuinely shared git history (forks of the same repo) rather than an arbitrary chosen SHA. Both of these are real constraints that were not fully resolved by the tools available — specifically, whether `verify_webhook_signature`/`Shipit.github` use a single global secret shared by all installations (making attacker-controlled-repo forgery trivial) or a per-organization secret requiring the attacker to compromise/own a legitimately-configured org is not confirmed here (`GithubApp#verify_webhook_signature` was not inspected). If the app uses one shared webhook secret across all repos it's installed on, this becomes a fully unauthenticated cross-tenant attack once the attacker's own repo has the app installed and shares commit history with a victim repo (e.g., via fork). If secrets are per-tenant and unknown to the attacker, this narrows to malicious insiders/other tenants on the same Shipit instance.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the authenticated repository, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status webhook only ever mutates commits belonging to the stack(s) of the repository that the webhook signature authenticated (`payload.dig('repository','full_name')`), closing the cross-tenant write.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two stacks, `victim_stack` (repo `victim/app`) and `attacker_stack` (repo `attacker/app`), each requiring `ci/integration` as a required status.
2. Create `victim_commit = victim_stack.commits.create!(sha: 'a' * 40, ...)` and `attacker_commit = attacker_stack.commits.create!(sha: 'a' * 40, ...)` — i.e., assert the binding `victim_commit.sha == attacker_commit.sha` while `victim_commit.stack_id != attacker_commit.stack_id`.
3. Record `victim_commit.deployable?` beforehand (e.g., `true`, assuming a prior successful `ci/integration` status exists on the victim commit).
4. Build a `status` webhook payload with `repository: { full_name: 'attacker/app', owner: { login: 'attacker' } }`, `sha: 'a'*40`, `context: 'ci/integration'`, `state: 'failure'`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
6. Assert both sides of the equality diverge post-exploit: `victim_commit.reload.deployable?` changed from `true` to `false` (or `blocked?` becomes `true`) even though the payload's `repository.full_name` was `attacker/app`, not `victim/app` — proving a payload authenticated for repo A mutated repo B's commit state.
7. As a control, assert `attacker_commit.reload.status.state == 'failure'` (correctly updated) while highlighting that `victim_commit` should never have been touched (`assert_not_equal` the intended vs. actual outcome for the victim's commit).

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
