### Title
Attacker-controlled `machine.environment` in fork `shipit.yml` (e.g. `GIT_CONFIG_GLOBAL`) reaches `PTY.spawn` unfiltered on `allow_all` review stacks - (File: `lib/shipit/task_commands.rb`)

### Summary
For a `ReviewStack` provisioned under `provisioning_behavior: allow_all`, the stack's `branch` is the PR head ref of the attacker's own fork, so the working directory checked out for every task/deploy is the attacker's fork content. `DeploySpec#machine_env` reads `shipit.yml`'s `machine.environment` key straight from that checkout with no key allowlist, and `TaskCommands#env` merges it directly into the env passed to `Command`, which `PTY.spawn`s a shell-interpreted step. An attacker can therefore set arbitrary environment variables, including `GIT_CONFIG_GLOBAL`, for every command Shipit executes on the deploy host.

### Finding Description
The broken binding: `EnvironmentVariables.with(env).permit(variable_definitions)` (the allowlist sanitizer) is applied to task/deploy/rollback envs supplied via API/controller params [1](#0-0) , but it is **never** applied to `deploy_spec.machine_env`, which is merged unconditionally into the command environment:

```ruby
def env
  super.merge(@stack.env).merge(...).merge(deploy_spec.machine_env).merge(@task.env)
end
``` [2](#0-1) 

`machine_env` is defined as `config('machine', 'environment') || {}` [3](#0-2) , i.e. it is read verbatim from the `shipit.yml` file present in the checked-out working directory (`DeploySpec::FileSystem.new(@task.working_directory, @stack)` [4](#0-3) ), which is populated by `TaskCommands#clone`/`#checkout` from `@stack.git_path` at `@stack.branch` [5](#0-4) .

For a `ReviewStack`, `branch` is set to `pull_request.head.ref` when the stack is created from an `opened`/`reopened` PR webhook under `allow_all` (confirmed by tests asserting `stack.branch == payload["pull_request"]["head"]["ref"]` [6](#0-5) ), and `OpenedHandler#provision?` returns true unconditionally whenever `provisioning_behavior_allow_all?` is set, with no check on repository ownership of the PR [7](#0-6) . This means the branch/content checked out and used to compute `machine_env` is entirely attacker-controlled fork content, requiring only opening a PR against a repository configured with `allow_all`.

Once `Command.new(step_line, env:, chdir:)` is built, `parse_arguments` keeps the whole step as a single shell string [8](#0-7) , and `start` calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, where `unbundled_env` is `BASE_ENV.merge(PATH...).merge(@env.stringify_keys)` — `@env` includes the attacker's `machine_env` entries with no key filtering [9](#0-8) . Because the argument is a single string, it is executed through `/bin/sh -c`, and any `git` invocation performed subsequently (e.g. `checkout`, `clone`, or any step that shells out to `git`) will honor `GIT_CONFIG_GLOBAL` pointed at an attacker-supplied config file (which can be committed in the same fork branch) defining a `core.fsmonitor` command or similar hook, achieving code execution on the Shipit deploy host.

None of the existing guards intercept this: `EnvironmentVariables#permit`/`filter_task_envs`/`filter_deploy_envs`/`filter_rollback_envs` only sanitize env explicitly supplied through controller params (`env:` argument to `trigger_task`/`build_deploy`), not `machine_env` read from the repo's own `shipit.yml`. `ReviewStack#env` merging PR labels is a separate, lower-severity vector (values are hardcoded `"true"`, not attacker-supplied paths) [10](#0-9) , but `machine.environment` in `shipit.yml` gives full key *and* value control.

### Impact Explanation
An unprivileged GitHub user who can open a PR against a repository with review stacks enabled and `provisioning_behavior: allow_all` can commit a `shipit.yml` with `machine.environment.GIT_CONFIG_GLOBAL: <path-to-malicious-gitconfig-in-the-checkout>` plus the malicious gitconfig file itself. Every `git` invocation performed by Shipit for that stack's tasks (checkout, clone, custom steps) will pick up the attacker's global git config, enabling arbitrary command execution on the Shipit deploy host under the Shipit service account — Critical RCE, matching the target's "Remote Code Execution on the Shipit deploy host" impact category. This is repeatable against any repository with `allow_all` review stacks enabled, and the blast radius includes the shared deploy host secrets (`GITHUB_TOKEN`, other stacks' credentials on the same host).

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and `provisioning_behavior: allow_all` (documented as the "most likely" recommended setting in `docs/review_stacks.md`). Given that, the attacker only needs to open a PR from their own fork with a crafted `shipit.yml` — no Shipit session, token, or GitHub team membership is required. This is a low-cost, fully repeatable attack against any such repository.

### Recommendation
Apply an explicit allowlist (or deny sensitive keys like `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_SYSTEM`, `LD_PRELOAD`, `BUNDLE_GEMFILE`, `PATH`, etc.) to `DeploySpec#machine_env` before merging it into `TaskCommands#env`/`DeployCommands#env`, similar to how `EnvironmentVariables.permit` is used for task/deploy/rollback params. At minimum, reject `machine.environment` keys that can influence interpreter/tool behavior (e.g. any `GIT_*`, `LD_*`, `*_PATH` variable) for stacks whose source is attacker-controlled (review stacks provisioned from forks), or run review-stack tasks with `GIT_CONFIG_GLOBAL`/`GIT_CONFIG_NOSYSTEM` forcibly pinned by Shipit itself so it cannot be overridden by repo-provided env.

### Proof of Concept
```ruby
# test/unit/task_commands_review_stack_env_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsReviewStackEnvTest < ActiveSupport::TestCase
    test "attacker-controlled machine_env GIT_CONFIG_GLOBAL reaches the spawned command env unfiltered" do
      review_stack = shipit_stacks(:review_stack)
      review_stack.update!(provisioning_behavior: :allow_all) if review_stack.respond_to?(:provisioning_behavior=)

      task = review_stack.tasks.build(definition: TaskDefinition.new('deploy', 'steps' => ['echo hi']))
      commands = TaskCommands.new(task)

      # Simulate the fork's shipit.yml declaring machine.environment.GIT_CONFIG_GLOBAL
      deploy_spec = stub(
        machine_env: { 'GIT_CONFIG_GLOBAL' => '/tmp/malicious-review-stack/.gitconfig' },
        dependencies_steps!: [],
        directory: nil,
        clear_working_directory?: true
      )
      commands.stubs(:deploy_spec).returns(deploy_spec)

      command = commands.perform.first

      # Equality that must hold if the vulnerability exists: the attacker-set key/value
      # reaches Command#env unchanged, with no allowlist rejecting it.
      assert_equal '/tmp/malicious-review-stack/.gitconfig', command.env['GIT_CONFIG_GLOBAL']

      # Confirm it would reach PTY.spawn's env (unbundled_env merges @env verbatim)
      assert_equal '/tmp/malicious-review-stack/.gitconfig', command.unbundled_env['GIT_CONFIG_GLOBAL']
    end
  end
end
```
This test demonstrates that `GIT_CONFIG_GLOBAL` supplied via `machine.environment` in a fork-controlled `shipit.yml` is not filtered by any allowlist (unlike `filter_task_envs`/`filter_deploy_envs`) and reaches both `Command#env` and `Command#unbundled_env`, the hash passed to `PTY.spawn`.

    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
      @started = true
      self
    end

    def unbundled_env
      BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)
    end
