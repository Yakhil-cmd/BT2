### Title
`StatusHandler#process` writes `Status` rows without scoping to the webhook's repository, unlike sibling handlers - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely by `Commit.where(sha: params.sha)`, with no check that the commit's stack belongs to the repository named in the webhook payload. Every other handler in the same class hierarchy (`PushHandler`, `CheckSuiteHandler`) uses the base class' `stacks` helper, which scopes to `Repository.from_github_repo_name(repository_name)`. This omission is the actual broken binding, and it is independent from `Commit#locked?`, confirming the question's own framing that the lock is not a repo-scope safety.

### Finding Description
The claimed binding is: `payload['repository']['full_name'] == commit.stack.repository.full_name` must hold before a `Status` row tied to that commit is created. Tracing the code:

- `WebhooksController#create` parses the JSON body and dispatches to `Shipit::Webhooks.for_event(event)`, calling `handler.call(params)` [1](#0-0) .
- `verify_signature` only checks the HMAC signature keyed by `Shipit.github(organization: repository_owner)` (`repository_owner` derived from `payload['repository']['owner']['login']`) - it authenticates that the request came from *some* registered GitHub organization/app, not that the referenced commit `sha` belongs to *that* repository [2](#0-1) .
- `Handler` base class defines `stacks`, scoped via `Repository.from_github_repo_name(repository_name)&.stacks`, and `repository_name` reads `payload.dig('repository', 'full_name')` [3](#0-2) . `PushHandler#process` and `CheckSuiteHandler#process` correctly call `stacks.where(...)` before touching any commit, enforcing the repository binding [4](#0-3) [5](#0-4) .
- `StatusHandler#process`, however, never calls `stacks` or reads `repository_name` at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) . Since `sha` is a global column with no stack/repo scope in the query, any commit row anywhere in the Shipit instance whose `sha` matches the attacker-supplied value receives the forged status.
- `create_status_from_github!` calls `add_status` which calls `statuses.replicate_from_github!(stack_id, github_status)`, creating a `Status` row bound to the victim commit's own `stack_id` (not the attacker's stack) [7](#0-6) , and `Status` has an `after_commit :schedule_continuous_delivery` callback that calls `commit.schedule_continuous_delivery`, which fires downstream jobs regardless of whether the commit is locked [8](#0-7) .
- `Commit#locked?` only gates `deployable?` (`!locked? && ...`) [9](#0-8) ; it plays no role in `create_status_from_github!`, confirming the question's premise that lock state does not block the write.

**Why this matters for repo scoping specifically:** to exploit this, the attacker needs a `sha` collision with an existing tracked commit. This is realistic when the attacker's own repository shares history with the victim's tracked repository (e.g., attacker forked `victim/prod`, or the victim commit is a well-known public commit/tag reused across repos). The attacker sends `POST /webhooks` with `X-Github-Event: status`, a valid signature for **their own** organization/app (which they legitimately control if their fork is registered under an org Shipit is also configured for, or if Shipit uses a single shared `github` config for a whole GitHub App installation covering multiple repos as documented), a `repository.full_name` pointing to their own repo, and `sha` equal to the victim commit's SHA. `verify_signature` passes because the signature is valid for the actual sender; `StatusHandler#process` then finds the victim `Commit` purely by `sha` and writes a `Status` scoped to the victim's `stack_id`, without ever checking that `payload['repository']['full_name']` matches that stack's repository.

None of the listed guards prevent this: `verify_signature` checks HMAC per-organization but does not bind the payload's `repository` field to the resulting `Commit` lookup; the `ExplicitParameters` schema in `StatusHandler` validates only types/presence of `sha`, `state`, etc., not repository identity; `drop_unhandled_event` and `force_github_authentication` are irrelevant to this write path; `Repository`/`Stack` validations do not constrain `Status.create` because `StatusHandler` never queries through `Repository`/`stacks` in the first place.

### Impact Explanation
An attacker who controls (or whose signature verifies for) any GitHub organization/repo registered with the Shipit instance can, given a known SHA that also exists in another tenant's tracked stack, write arbitrary `Status` rows (state/description/context/target_url/created_at) against that victim commit. This corrupts CI/audit history for a repository the attacker does not own and can trigger `enable_ci_on_stack`, `schedule_continuous_delivery` -> `ProcessMergeRequestsJob`/`ContinuousDeliveryJob`, and recomputation of `blocked?` for other, unlocked sibling commits in the same stack (`Commit#blocked?` scans `stack.commits.reachable.newer_than(...).older_than(self).any?(&:blocking?)`) [10](#0-9) . This is a cross-tenant write ("a payload for one repository mutating another's stack, commit ... state") matching the Critical category. It does not itself force an unauthorized deploy of the locked commit `C` (locking still blocks `deployable?`), but it can flip `blocked?` for other undeployed, unlocked commits and can trigger continuous-delivery jobs, which is a legitimate downstream automation trigger the attacker should not control.

### Likelihood Explanation
Preconditions: (1) attacker's own repository/org must be registered with Shipit's `github` config so their webhook signature verifies (multi-org Shipit installations are explicitly documented) [11](#0-10) ; (2) the attacker needs a SHA collision with a commit Shipit already tracks in a different stack — trivially achievable if the attacker forks the victim repository (shared git history means identical SHAs for shared commits) or if the victim commit SHA is publicly known (e.g., a well-known open-source commit). No Shipit session, API token, or secret is required beyond controlling one's own registered repo/webhook endpoint, which is within the stated attacker capability ("push to a fork ... emit webhooks from a repository they own"). This is fully repeatable against any commit whose SHA the attacker can reproduce, across arbitrary stacks.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: resolve `stacks` from the payload's `repository.full_name` first, then only update commits belonging to those stacks, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or, more efficiently, `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`, model-level to avoid live GitHub):
1. Create two stacks/repositories: `stack_a` (repo `victim/prod`) and `stack_b` (repo `attacker/evil`), each with a `Commit` sharing the same `sha` value (simulating a fork/shared history) — this is the equality `payload['repository']['full_name'] == commit.stack.repository.full_name`, set up as `false` (payload names `attacker/evil`, commit belongs to `stack_a`).
2. Build a `status` webhook payload with `repository.full_name = 'attacker/evil'` and `sha` equal to the shared SHA.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (or POST through `WebhooksController` with signature stubbed as in existing tests) and assert:
   - `assert_difference('stack_a.commits.find_by(sha: shared_sha).statuses.count', 1)` — the victim's commit gained a status despite the payload naming a different repository.
   - Assert the created `Status#stack_id == stack_a.id`, proving cross-tenant write, even though the request's `repository.full_name` was `attacker/evil`.
   - Optionally lock `stack_a`'s commit via `commit.lock(user)` beforehand and show the status write still occurs (`assert commit.reload.locked?` and `assert_difference` on `statuses.count`), confirming `locked?` does not gate this path.
   - For sibling-impact, create a second undeployed commit in `stack_a` and assert its `blocked?` value changes before/after the forged status write. [12](#0-11)
