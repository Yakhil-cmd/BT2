### Title
Attestor-list-update on a `spender_attested` asset can retroactively lock previously received, already-owned coins — (File: validation.js)

### Summary
In ocore, assets can be created with `spender_attested = true`, meaning any address that owns/spends an output of that asset must currently be on the asset's attestor-approved list. The definer can publish an `asset_attestors` message at any time to replace/update the list of trusted attestors. The problem, analogous to the ThunderNFT `Pool.withdraw()` bug, is that spend-time validation re-checks whether the *current* attestor list (as of `last_ball_mci` at spend time) still attests the owner address — not whether it was attested when the coin was received. If the definer publishes a new attestor list that drops an address (or an attestor revokes/changes its attestation), every output already legitimately owned by that address for that asset becomes unspendable until the definer (or an attestor) restores the attestation, exactly mirroring the "withdraw() re-checks whitelist instead of checking it at deposit time" pattern from the report.

### Finding Description
Assets with `spender_attested` require that any address spending (or receiving, in the AA definition/issue path) an output of the asset be attested by one of the asset's attestors. The check is performed with the *live* attestor list read at validation time via `storage.readAsset()` / `filterAttestedAddresses()`: [1](#0-0) 

`loadAssetWithListOfAttestedAuthors()` builds `objAsset.arrAttestedAddresses` from the attestor list that is current as of `last_ball_mci`, not from historical attestation state at the time the coin was received: [2](#0-1) 

This live list is then enforced on every spend attempt in `validatePaymentInputsAndOutputs()`, both for public/divisible transfers and for private fixed-denomination transfers: [3](#0-2) [4](#0-3) 

It is also enforced at the top-level `validatePayment()` entry for issuance and for the general "none of the authors is attested" case: [5](#0-4) 

And again for output addresses (recipients) in the final balance/condition check: [6](#0-5) 

The attestor list itself is mutable at any time via an `asset_attestors` message, validated generically in `validateInlinePayload()`: [7](#0-6) 

and `readAsset()`'s `addAttestorsIfNecessary()` always resolves to the *latest* stable attestor-list unit for the asset (`ORDER BY level DESC LIMIT 1`), i.e., whichever list is most recently published, superseding any prior list: [8](#0-7) 

So the exact same root-cause pattern as the ThunderNFT report exists here: a condition (whitelist/attestation) that was satisfied when funds were deposited/received is re-verified against its *current* state at spend time, rather than being fixed at receipt time. If the asset definer publishes an updated attestor list that omits a previously-attested address, or the address's underlying attestation record is superseded by a newer, non-matching attestation, that address's *already owned* coins of the asset become unspendable — the address cannot transfer, and cannot even move change back to itself — until attestation is restored.

### Impact Explanation
Any holder of a `spender_attested` asset can have their existing, previously valid balance frozen the moment the definer (a party they don't control) updates the attestor list, or the address's attestation changes/expires. This is a direct freezing-of-funds impact: the owner of a stable, previously-spendable output loses the ability to spend it through no fault or action of their own, with no timeout — recovery requires the definer/attestor to re-add them to the whitelist. This matches the "Temporary freezing of funds" impact class from the original report and, unlike the Pool contract case, affects a base primitive (asset engine) used across all `spender_attested` assets on the network, not a single dApp.

### Likelihood Explanation
`spender_attested` is a documented, supported asset feature (`AA_TESTKIT`/oscript, `create_an_asset.oscript`, and multiple sample AAs reference it), so this is a legitimate, reachable configuration for any asset issuer. Any issuer (an unprivileged unit poster who defines an asset) can create such an asset, and the definer/attestors control the attestor list independently of asset holders. The freeze is triggered simply by normal management of the attestor list (e.g., replacing attestors, revoking one address, rotating attestors), which is expected administrative behavior for such assets — no attacker collusion is even required, though a malicious/careless definer could weaponize it against specific holders.

### Recommendation
Decouple the attestation check from live/current state where it affects the ability to *spend already-owned* outputs:
- For `transfer` inputs, check attestation of the owner address as of the time the source output was created/received (or skip the spender-attestation re-check entirely for transfers of coins already held, since the recipient was already validated as attested when the coin was received), rather than re-validating against the attestor list current at spend time.
- Alternatively, only enforce `spender_attested` at issuance time (mint) and rely on the transfer/issue condition mechanism (`transfer_condition`) if issuers want ongoing restrictions, making the freezing behavior an explicit, asset-level opt-in rather than an implicit side effect of attestor-list churn.
- At minimum, document/guard so that an attestor-list update cannot retroactively invalidate previously attested holders' ability to move their existing balance (e.g., allow spending to continue if the address was attested at any point before the output became stable, grandfathering existing balances).

### Proof of Concept
1. Definer creates asset A with `spender_attested = true` and publishes an initial `asset_attestors` list containing attestor `ATT1`.
2. `ATT1` attests address `U` (a normal user). `U` receives a payment of asset A; validation passes because `filterAttestedAddresses()` finds `U` in `arrAttestedAddresses` per `storage.js:1959-1974`, and the transfer/issue passes the checks in `validation.js:2115-2122` / `2504-2507`.
3. The definer later publishes a new `asset_attestors` message for asset A that lists only `ATT2` (dropping `ATT1`), per the `case "asset_attestors"` handling in `validation.js:2033-2041`. `readAsset()`'s `addAttestorsIfNecessary()` in `storage.js:1917-1946` will now resolve to this newest list as the "latest list of attestors" (`ORDER BY level DESC LIMIT 1`).
4. `U` attempts to spend their existing (previously valid, stable) output of asset A. `loadAssetWithListOfAttestedAuthors()` (`storage.js:1977-1992`) now computes `arrAttestedAddresses` using only `ATT2`'s attestations. Since `U` was never attested by `ATT2`, `U` is excluded.
5. The spend fails at `validation.js:2506` (`"owner address is not attested"`), and `U`'s already-owned funds are locked with no way to move them until the definer/attestor re-attests `U` or restores `ATT1` to the list — mirroring the ThunderNFT `Pool.withdraw()` scenario where delisting an asset locks already-deposited user funds.
