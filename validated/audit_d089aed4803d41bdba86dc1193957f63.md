### Title
`StatusHandler#process` looks up commits by `sha` alone with no repository scoping, letting a webhook from Repo A trigger `ContinuousDeliveryJob` for a Stack of Repo B - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target `Commit` with `Commit.where(sha: params.sha)`, unlike every other webhook handler (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) which scope through `stacks`/`repository` derived from the verified payload's `repository.full_name`. Because the commit is matched purely on `sha` with no constraint tying it to the webhook's own repository, a signed webhook from an attacker-controlled repository whose git history shares a commit SHA with a tracked Stack (trivially achievable by forking the target repository, since SHA-1 commit ids are content-derived and repo-independent) can flip that commit's status and trigger `schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)` for a stack belonging to a repository the attacker never authenticated against.

### Finding Description
The binding the codebase should enforce is: `payload.repository.full_name == commit.stack.repository.full_name` (or at minimum `commit.stack ∈ Repository.from_github_repo_name(payload.repository.full_name).stacks`). This binding does not hold in `StatusHandler`.

- `WebhooksController#verify_signature` only verifies that the raw payload was signed with the secret belonging to the organization/owner named in `payload['repository']['owner']` [1](#0-0) . It never checks that the sha referenced in a `status` payload actually belongs to that same repository's Stack.
- The generic `Handler` base class provides a `stacks` helper that scopes lookups to `Repository.from_github_repo_name(repository_name)&.stacks`, and `PushHandler`, `CheckSuiteHandler`, and the `PullRequest::*` handlers all use it (or an equivalent `repository`) before touching any Stack [2](#0-1) [3](#0-2) [4](#0-3) .
- `StatusHandler#process`, in contrast, queries `Commit` globally by `sha` with no repository filter at all: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [5](#0-4) .
- `Commit#create_status_from_github!` calls `add_status`, which after creating the `Status` record fires the `deployable_status` hook and (via the `Status` model's `after_commit :schedule_continuous_delivery`, and `Commit`'s own `schedule_continuous_delivery`) invokes `Commit#schedule_continuous_delivery` [6](#0-5) [7](#0-6) .
- `Commit#schedule_continuous_delivery` checks only `deployable? && stack.continuous_deployment? && stack.deployable?` and, if true, calls `ContinuousDeliveryJob.set(wait: RECENT_COMMIT_THRESHOLD).perform_later(stack)` — again with no check that `stack`'s repository matches the webhook's source repository [8](#0-7) .
- The `commits` table is indexed on `(stack_id, sha)`, not uniquely on `sha` alone (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the same SHA can legitimately exist for multiple stacks/repositories in Shipit's data model, and `StatusHandler` makes no attempt to disambiguate.

**Exploit flow:** Attacker forks/clones the public history of Stack S's repository (Repo B) into their own repository (Repo A), which they fully control and for which they can legitimately trigger webhooks with Repo A's `webhook_secret` (e.g., via GitHub's Statuses API or by pushing to their fork so GitHub emits a `status` event). Since fork history preserves commit SHAs, the attacker sends (or GitHub sends on their behalf) a `status` webhook for Repo A carrying `sha` = Stack S's head commit sha and `state: success`. `verify_signature` passes because it only checks Repo A's secret. `StatusHandler#process` finds the `Commit` row for that sha (which belongs to Stack S/Repo B) with no repository cross-check, creates a `success` `Status` on it, and — if Stack S already has `continuous_deployment?`, `deployable?`, and its most recent commit unlocked and not yet `success?` — `ContinuousDeliveryJob.perform_later(stack)` is enqueued for Stack S, unauthorized by anything Repo B's owners configured.

None of the listed guards prevent this: `verify_signature` validates only the signing secret/org, not the sha-to-repository binding; `drop_unhandled_event` only checks event type; `ExplicitParameters` only validates payload shape; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` involved since this is an unauthenticated webhook endpoint by design.

### Impact Explanation
This is a payload for one repository (Repo A) causing state mutation and an unauthorized deploy trigger for another repository's stack (Repo B) — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy". The attacker gains the ability to force `ContinuousDeliveryJob` to run for any stack whose repository they can fork/mirror and whose head commit is otherwise ready to deploy, without ever authenticating against that repository or holding any Shipit privilege. This is repeatable against any tracked Stack with `continuous_deployment` enabled, as long as the attacker can reproduce or discover the target's head commit sha (fork history sharing, or any public knowledge of the sha) and send a webhook from an unrelated repository they control.

### Likelihood Explanation
Requires: Stack S has `continuous_deployment?` true and `deployable?` true, its most recent commit unlocked and not already `success`-classified; commit sha for Stack S's head must exist in the attacker's Repo A history (trivial via forking a public repo, or otherwise known/guessable) or, more generally, any prior legitimate ingestion into Shipit's `commits` table with that sha under Stack S. Attacker cost is minimal — own any GitHub repo, configure a webhook to Shipit (already required by the engine's normal setup for any tracked repo, but the attacker only needs their own repo's `webhook_secret`, not Repo B's), and fire one `status` event. No Shipit credentials, GitHub App keys, or team membership needed. Fully repeatable across any Stack meeting the precondition.

### Recommendation
Scope `StatusHandler#process` the same way as `PushHandler`/`CheckSuiteHandler`: derive the target stacks/commits via `stacks` (built from `Repository.from_github_repo_name(repository_name)`) rather than a bare `Commit.where(sha: ...)` across the whole table, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, so a status only ever mutates a commit that actually belongs to a stack of the payload's own verified repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "does not schedule ContinuousDeliveryJob for a stack whose repository differs from the webhook's repository" do
  stack_b = shipit_stacks(:shipit) # Repo B, continuous_deployment: true
  stack_b.update!(continuous_deployment: true)
  commit = stack_b.commits.create!(sha: 'a' * 40, message: 'deployable head')

  # webhook payload signed/verified for a *different* repository (Repo A)
  payload = {
    'sha' => commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/repo-a' }, # Repo A != Repo B
    'branches' => []
  }

  assert_equal 'attacker/repo-a', payload['repository']['full_name']
  refute_equal stack_b.repository.full_name, payload['repository']['full_name']

  ContinuousDeliveryJob.expects(:perform_later).with(stack_b).never

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process
end
```
With the current implementation, `Commit.where(sha: commit.sha)` still matches `commit` (belonging to Stack S/Repo B) regardless of `payload['repository']['full_name']`, so `ContinuousDeliveryJob.perform_later(stack_b)` fires and the assertion fails, demonstrating the cross-repository trigger. After scoping the lookup to `stacks` derived from `payload['repository']['full_name']`, the job is correctly never enqueued.
