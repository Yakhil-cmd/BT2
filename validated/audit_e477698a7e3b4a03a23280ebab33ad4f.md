### Title
Webhook signature binds to `repository.owner.login`'s GitHub App while handlers act on the unrelated `repository.full_name` field, allowing cross-organization forgery of push/status events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body itself. Once the signature check passes, every webhook `Handler` resolves the actual `Repository`/`Stack` to act on using a completely different field of the same body: `repository.full_name`. Nothing ties these two fields together, so a party who legitimately controls one configured GitHub organization/App in a multi-org Shipit instance can forge a validly-signed payload for their own org while pointing `repository.full_name` at any other org's repository, causing Shipit to act on a stack the attacker never authenticated for.

### Finding Description
`verify_signature` derives the signing organization purely from payload content and fetches that org's `GitHubApp` to verify the signature: [1](#0-0) [2](#0-1) 

This only proves "the payload bytes were signed by whichever org's secret `repository.owner.login` happens to name." It does not prove anything about `repository.full_name`, which is what handlers actually use to look up the target repository/stack: [3](#0-2) 

For example `PushHandler` resolves stacks via that same `repository_name` (i.e., `full_name`) and triggers a sync against whatever stack matches, using attacker-supplied `ref`/`after`: [4](#0-3) 

The engine supports multiple independently configured GitHub Apps/organizations, each with its own `webhook_secret`, precisely so that different orgs' webhooks are cryptographically isolated: [5](#0-4) 

The broken binding, expressed as an equality that should hold but doesn't:
`organization authenticated (repository.owner.login used to pick the verifying GitHub App)` ≠ `repository actually written (repository.full_name used by Handler#stacks to pick the Repository/Stack)`.

Because both values are attacker-controlled fields of the very same JSON body whose bytes are what gets signed, an attacker who is an admin/legit webhook sender for **their own** configured organization ("OrgA", with a real `webhook_secret`) can compute a correct HMAC over a body where:
- `repository.owner.login == "OrgA"` (so `Shipit.github(organization: "OrgA")` is used and the signature check passes with OrgA's real secret), and
- `repository.full_name == "victim-org/victim-repo"` (so the `Handler` resolves and acts on a stack belonging to an entirely different, unrelated organization the attacker has no access to).

This is the same class of bug as the reported VMEX issue: a check is performed on one identity/field (the `aToken`'s claimed identity in VMEX; `repository.owner.login` here), while the privileged action is executed using a different, unverified field (the caller-supplied balances in VMEX; `repository.full_name` here) that the verification step never actually covers.

### Impact Explanation
An attacker who legitimately controls one configured organization's GitHub App webhook secret (a low/no-privilege position relative to victim stacks — they are simply another tenant of the same multi-org Shipit deployment) can forge Shipit webhook events against any other organization's stacks tracked by the instance:
- `push`: force `Stack#sync_github` on a victim stack with an attacker-chosen `after` SHA, causing Shipit to sync/refresh state and treat attacker-influenced revisions as the head of the victim's tracked branch.
- `status`/`check_suite`-class events follow the identical `repository.full_name`-based resolution pattern in `Handler`, so the same forgery lets an attacker inject fabricated CI status/check results onto commits belonging to a victim's stack. Since deployability gating (`required_statuses`/`deployable?`) in this engine relies on commit statuses, this can subvert the CI gate that normally blocks a deploy, enabling an effectively unauthorized deploy path once combined with continuous deployment or a human triggering a deploy based on the forged green status.

This satisfies the High-impact bucket of "escalation ... unauthorized deploy" via cross-repository forgery, without requiring any Shipit session, `ApiClient` token, or the victim org's own `webhook_secret`.

### Likelihood Explanation
Exploitability requires only that the attacker be a legitimate operator of any one organization already configured with a GitHub App/webhook secret in the target Shipit instance — a routine, low-privilege position in any shared/multi-tenant deployment (the engine explicitly supports multiple orgs per instance, see `test/dummy/config/secrets_double_github_app.yml`). No knowledge of the victim org's secret, no repository write access to the victim repo, and no authenticated Shipit session are needed — only the ability to send an HTTP POST to `/webhooks` with a body they control and sign with their own org's secret.

### Recommendation
After verifying the HMAC, cross-check that the organization/owner embedded in `repository.full_name` (and any other repository-identifying field a handler will use) matches the `repository.owner.login`/`organization.login` that was used to select the verifying GitHub App. Reject the webhook (422) if they diverge, so the identity that was cryptographically authenticated is provably the same identity whose resources are acted upon.

### Proof of Concept
1. Attacker is a legitimate admin of `OrgA`, which is configured in this Shipit instance with its own `github.webhook_secret` (per `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker crafts a push webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s real `webhook_secret` over the exact raw body (`OpenSSL::HMAC.hexdigest('sha1', webhook_secret, body)`), exactly as done in `GitHubApp#verify_webhook_signature`.
4. POST to `/webhooks` with `X-Github-Event: push` and that signature.
5. `WebhooksController#verify_signature` computes `repository_owner == "OrgA"`, fetches `OrgA`'s `GitHubApp`, and the signature verifies successfully.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, i.e., the victim's stack — entirely unrelated to `OrgA` — and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")`, even though the attacker was never authenticated for `victim-org`.
