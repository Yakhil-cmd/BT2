### Title
Unbounded iteration over the entire private-payment chain forces every payment recipient to re-validate the full transfer history, with no depth limit - ([File: indivisible_asset.js])

### Summary
For indivisible (blackbyte-style) private assets, every time a coin changes hands the sender must build, and every recipient must fully re-validate, the complete chain of private elements from the current output all the way back to the original issuance. There is no cap on the number of hops in this chain, so a coin that has been transferred many times (or deliberately chained many times by a malicious counterparty) forces the next recipient's node to iterate over and cryptographically/DB-validate the entire chain before the payment can be accepted and spent. This mirrors the reported skale-manager pattern: an action that should be cheap and local (accepting one payment) instead triggers processing whose cost grows with the total (attacker-influenced) history size, with no batching or per-hop cap, opening the door to resource exhaustion and effectively freezing the received funds for the victim.

### Finding Description
When an indivisible-asset payment is composed, `buildPrivateElementsChain` walks backward from the paid output through the `inputs`/`outputs` tables, following `transfer` inputs recursively until it reaches an `issue` input, pushing every hop into `arrPrivateElements`: [1](#0-0) 

This chain (potentially hundreds/thousands of elements long, one per historical transfer of that exact coin) is sent to the recipient as `arrPrivateElements`. The recipient path (`network.js` → `private_payment.js` → `indivisible_asset.js`) then validates the **whole chain in one shot**: [2](#0-1) [3](#0-2) 

`parsePrivatePaymentChain` iterates the full array with `async.forEachOfSeries`, calling `validatePrivatePayment` for *every* element: [4](#0-3) 

Each `validatePrivatePayment` call performs a spend-proof DB lookup and, for full nodes, a `graph.determineIfIncluded` call that itself walks the unit DAG (`goUp`/recursive BFS over `parenthoods`): [5](#0-4) [6](#0-5) 

No code in `findUnfinishedPastUnitsOfPrivateChains`, `validateAndSavePrivatePaymentChain`, or `parsePrivatePaymentChain` bounds `arrPrivateElements.length`; the only length constraints found in the codebase (`MAX_HISTORY_ITEMS = 2000` in `light.js`) apply to an unrelated light-wallet history request, not to private payment chains: [7](#0-6) 

This is structurally identical to the skale-manager slashing-iteration bug: a routine user action (accept a private payment / call `transfer`) transparently drags in and re-processes an unbounded, attacker-influenced history (chain of private-payment hops / list of slashes) rather than only the delta relevant to the action.

### Impact Explanation
A malicious sender (or a series of colluding intermediate holders) can pass an indivisible private coin through many private transfers before finally sending it to a victim. The victim's wallet/full node must then walk and validate the entire chain — including repeated DAG-inclusion checks — before the received output is usable. If the chain is made large enough, validation cost (DB queries + DAG traversal per hop) grows without bound, which can:
- stall or exhaust the recipient node's resources while trying to accept a single incoming payment, and
- keep the received coin practically unspendable/unconfirmed for the recipient until (if ever) validation completes,

which is a fund-freezing style denial of service targeted at a specific private-payment counterparty, directly reachable by an unprivileged peer who controls how the coin was passed to them.

### Likelihood Explanation
Building a long private-payment chain requires only ordinary wallet operations (repeated private transfers of the same coin among addresses/devices the attacker controls) — no special privileges, hub/node cooperation, or protocol violation is needed. The victim is any wallet that accepts an incoming private payment, i.e., an ordinary "private-payment counterparty," matching the reachable-actor scope for this analysis. This makes the likelihood at least Medium: an attacker fully controls the depth of the chain sent to a victim, and the recipient has no way to reject or truncate it before doing the validation work.

### Recommendation
- Enforce a maximum chain length (number of hops) for private payment chains, analogous to `MAX_HISTORY_ITEMS`, and reject (or defer as unaccepted) any private payment whose chain exceeds it.
- Consider caching/memoizing already-validated intermediate elements (by unit/message_index/output_index) so repeated validation of the same historical hops across multiple incoming payments doesn't repeat full DAG-inclusion work.
- Process very long chains in bounded batches with cooperative yielding (similar to the `setImmediate` batching used elsewhere, e.g. `goDownAndCollectBestChildrenFast` in `main_chain.js`) so a single validation call cannot monopolize the event loop indefinitely.

### Proof of Concept
1. Attacker issues a private indivisible-asset coin and, using wallets/addresses under their control, repeatedly makes private transfers of that exact coin to themselves N times (e.g., N = 50,000), each transfer appending one element to the coin's private-element chain (`buildPrivateElementsChain` logic in `indivisible_asset.js:619-721`).
2. Attacker finally sends the coin to the victim via a normal private payment.
3. The victim's node receives `arrPrivateElements` of length N and calls `privatePayment.validateAndSavePrivatePaymentChain` → `parsePrivatePaymentChain`, which serially validates all N elements, each requiring a spend-proof DB query and (for full nodes) a `graph.determineIfIncluded` DAG walk (`indivisible_asset.js:186-236`, `graph.js:131-153`).
4. With N large enough, this consumes disproportionate CPU/DB time on the victim's node for a single incoming payment, since there is no length cap anywhere in the validation path.
