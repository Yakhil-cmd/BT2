### Title
Unbounded recursion in `replaceInTemplate`/`replaceInVar` when expanding a "definition template" causes node crash on a crafted definition-template message - (File: `definition.js`)

### Summary
`replaceInTemplate` (and its inner helper `replaceInVar`) in `definition.js` recursively walks the JSON structure of a stored `definition_template` message with **no depth limit**, unlike every other recursive AST-walking function in the codebase (`evaluate` in `validateDefinition`/`validateAuthentifiers` with `MAX_COMPLEXITY`/`MAX_OPS`, `aa_validation.js`'s `validate`/`validateFieldWrappedInCases` with `MAX_DEPTH`, `formula/validation.js`'s `evaluate` with `depth > 100`). A crafted, deeply-nested template posted by an ordinary unit author and later referenced via the `'definition template'` operator triggers unbounded synchronous recursion (`_.cloneDeep` + `replaceInVar`) and crashes the validating node with "Maximum call stack size exceeded" — the same recursion-depth bug class as CVE-2017-15024 (`find_abstract_instance_name` infinite/uncontrolled recursion on crafted nested data).

### Finding Description
Any unprivileged unit author can post an `app: 'definition_template'` message whose `payload` is an arbitrarily deeply nested array/object (there is no depth check on definition_template message payloads at storage time). Later, any address definition or asset condition that uses the `'definition template'` op will fetch that stored payload and expand it: [1](#0-0) 

and [2](#0-1) 

Both call: [3](#0-2) 

`replaceInVar` recurses into every array element / object value with no depth (or node-count) guard at all, in contrast to the sibling recursive evaluators in the very same file (`evaluate` in `validateDefinition`, gated by `complexity`/`count_ops`/`MAX_COMPLEXITY`/`MAX_OPS`): [4](#0-3) 

This asymmetry means the complexity/op counters that bound the *definition* AST do not bound the *template substitution* step, which operates on attacker-controlled template JSON and expands it via unguarded recursion (plus an unguarded `_.cloneDeep` of the same structure) before `evaluate` ever gets a chance to apply its complexity counters to the result.

### Impact Explanation
Because `'definition template'` is reachable from address-definition validation (`validateDefinition`) and from authentifier/signature evaluation (`validateAuthentifiers`), *any* node that processes a unit whose author's (or co-signer's, or asset's) definition references a maliciously deep template will hit unbounded recursion and crash with a stack overflow while validating that unit. Since unit/definition validation is mandatory for every node attempting to include/confirm the unit, this can render the network (or any node reachable by the malicious unit) unable to validate/confirm new units — a network-wide denial-of-service condition, not merely a resource-exhaustion nuisance, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
Likelihood is high for any actor able to post ordinary application messages: posting a `definition_template` message and later defining/using an address whose definition contains `['definition template', [unit, params]]` referencing it are both standard, unprivileged unit-construction operations available to any wallet/AA/asset author — no special network position, hub, or privileged key is required.

### Recommendation
Add an explicit depth/node-count limit to `replaceInTemplate`/`replaceInVar` (mirroring `MAX_DEPTH`/`MAX_COMPLEXITY` checks used elsewhere in `definition.js` and `aa_validation.js`, or reusing `string_utils.isTooDeeplyNestedOrHasTooManyNodes`), and reject templates/definitions with the "expression must be 2-element array"/complexity error before recursing. Also enforce a depth/size limit on `definition_template` message payloads at storage/validation time so overly deep templates cannot be persisted in the first place.

### Proof of Concept
1. Attacker A posts a unit with `app: 'definition_template'` whose payload is an array nested to a very large depth (e.g., `[[[[...]]]]` thousands of levels deep) and gets it stable.
2. Attacker A (or any user, including A themselves) creates/uses an address definition or asset condition containing `['definition template', [<templateUnit>, {param1: 'v'}]]` and posts a unit signed with/using this definition.
3. Every node that validates this unit calls `validateDefinition`/`validateAuthentifiers` → `'definition template'` case → `replaceInTemplate(arrTemplate, params)` → `replaceInVar(_.cloneDeep(arrTemplate))`, which recurses to the template's nesting depth with no limit, exhausting the call stack and crashing the node process while validating the unit.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
