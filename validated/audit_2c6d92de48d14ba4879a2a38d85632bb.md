### Title
Uncaught exception in AA trigger execution crashes the entire full node - ([File: aa_composer.js])

### Summary
`aa_composer.js` and its call chain contain multiple bare `throw Error(...)` statements inside asynchronous callbacks that execute during autonomous-agent (AA) trigger processing, a path directly reachable by any unprivileged unit poster who sends a payment/trigger to an AA address. Because ocore is a single Node.js process and never wraps AA-trigger execution in a `domain`/global recovery mechanism, any of these throws becomes an uncaught exception that is handled by the process-wide `process.on('uncaughtException', ...)` handler, which explicitly re-throws to intentionally kill the process. This is structurally identical to the Faktory bug class: one crafted, low-privilege input reaches an unguarded panic/throw path and brings down the entire server for all users, not just the offending connection.

### Finding Description
Any node processes AA triggers whenever a stable unit pays to an AA address, via `main_chain.js`'s `handleAATriggers()`/`markMcIndexStable` → `aa_composer.handlePrimaryAATrigger()` → `handleTrigger()`. This path executes for every full node in the network on every incoming, stabilized payment to an AA, with no permission check on the trigger's author (any unit poster can trigger it).

Inside this call chain there are several `throw Error(...)` statements that are not enclosed in any `try/catch`: [1](#0-0) [2](#0-1) 

For example, `handlePrimaryAATrigger` throws `handlePrimaryAATrigger: unit ${unit} not found in cache` if `storage.assocStableUnits[unit]` is unexpectedly missing, and `handleSecondaryTriggers` throws `secondary triggers while bouncing` under certain secondary-AA chain conditions — both are plain synchronous throws deep inside async `db.query`/`conn.query` callbacks, so they cannot be caught by any surrounding `try/catch` in the caller (Node.js does not propagate exceptions thrown inside async callbacks back up the call stack).

Because these are asynchronous throws with no domain or `try/catch` around the callback, they escape as unhandled exceptions all the way to Node's global exception handler in `network.js`: [3](#0-2) 

That handler logs the error and then explicitly re-throws it ("crash the process to avoid ending up in an inconsistent state"), terminating the entire Node.js process — every connected peer, wallet, and in-flight validation is dropped simultaneously, exactly like the unrecovered Go panic in Faktory that kills the whole server on a single malformed command.

The wider `formula/evaluation.js` oscript evaluator (used to execute AA `messages`/`state` formulas from trigger data) similarly contains defensive `throw Error("unknown op: " + op)` statements inside deeply nested async evaluation callbacks: [4](#0-3) [5](#0-4) 
While these particular ones are currently unreachable dead code given the surrounding `switch`, they demonstrate the same anti-pattern throughout the AA-execution codebase: synchronous `throw` used as an assertion inside async, non-`try/catch`-wrapped callbacks that ultimately run on the shared, single-process event loop.

### Impact Explanation
Any unhandled exception raised anywhere in the AA-trigger execution pipeline (a pipeline that is invoked automatically and unconditionally whenever any user sends a payment/trigger to any AA address) terminates the entire ocore process via the `uncaughtException` handler's explicit `throw err`. This is a full denial of service: all peers are disconnected, the node stops confirming/relaying new units, and if this happens on a witness or hub node, it can degrade network-wide stability/liveness ("a network unable to confirm new units"), matching the accepted-impact criteria. Unlike per-connection errors handled through `ifUnitError`/`ifJointError` callbacks, these bare throws bypass all graceful error paths.

### Likelihood Explanation
The trigger-processing path is reached by simply posting a normal, validly-signed unit with a payment output to any AA address — something any unprivileged wallet user or the AA definition author can do at any time, with no special permissions. The specific throw conditions identified (`unit not found in cache`, `secondary triggers while bouncing`) depend on specific state/timing edge cases (e.g., chains of secondary AA calls that bounce, or race conditions around unit-cache eviction) that are plausible but not trivially reproducible with a single crafted unit; exploitability requires further investigation into exactly which state sequences deterministically trigger them. This differentiates it somewhat from the Faktory case (where a single bare command deterministically triggers the panic), but the architectural weakness — synchronous `throw` inside unguarded async callbacks on a critical, attacker-reachable path, feeding into a process-crashing global handler — is directly analogous and confirmed to exist.

### Recommendation
- Wrap AA-trigger execution (`handlePrimaryAATrigger`, `handleTrigger`, `handleSecondaryTriggers`, and the formula evaluator) in defensive `try/catch` at the boundary where they are invoked from `main_chain.js`/`writer.js`, converting unexpected internal invariant violations into bounced/failed triggers rather than process-fatal throws.
- Replace assertion-style `throw Error(...)` calls inside async callbacks reachable from attacker-controlled unit/trigger data with error callbacks (`cb(err)`) that propagate through the existing `async.series`/`async.eachSeries` error-handling machinery already used elsewhere in the same files.
- Reassess whether `process.on('uncaughtException', ...)` in `network.js` should always crash the process, or whether AA-execution-related exceptions specifically should be isolated (e.g., abort only the current trigger/connection) given that this code path is externally triggerable by any unit poster.

### Proof of Concept
Not fully reproducible without deeper investigation into the exact state/timing required to hit `storage.assocStableUnits[unit]` cache-miss or the "secondary triggers while bouncing" condition in a live node; a Devin session with code execution access would be needed to construct a concrete sequence of AA definitions/triggers that deterministically reaches one of the unguarded `throw` statements in `aa_composer.js` and confirm the resulting process crash via the `uncaughtException` handler in `network.js`.
