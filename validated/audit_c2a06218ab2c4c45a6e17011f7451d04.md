### Title
Webhook signature verified against `repository.owner.login`'s secret while handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` is used to check the `X-Hub-Signature` HMAC based on the `repository.owner.login` (or `organization.login`) field of the *unauthenticated* JSON body. But every event `Handler` (e.g. `PushHandler`, `StatusHandler`) resolves the target `Repository`/`Stack` using a *different* field of the same body: `repository.full_name` (`Handler#repository_name`). Because these two fields are never checked for consistency, an attacker who controls (or is a legitimate/authorized user of) one configured GitHub organization's webhook secret can forge a payload whose `repository.owner.login` names their own org (so signature verification passes with their own secret) while `repository.full_name` names a victim's repository, causing Shipit to act on the victim's stack as if the event genuinely originated from GitHub.

### Finding Description
- Signature check: `Shipit.github(organization: repository_owner)` looks up the per-organization webhook secret keyed by `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- Handler dispatch: `Handler#repository_name` (used by `PushHandler`, `StatusHandler`, etc.) resolves the acted-upon repository/stack from `payload.dig('repository', 'full_name')`, a completely different field of the same JSON body. [3](#0-2) 
- `github_app.rb#verify_webhook_signature` only validates the HMAC over the raw request body using the secret bound to whatever organization was extracted by `repository_owner` — it never validates that `repository.full_name`'s owner matches `repository.owner.login`. [4](#0-3) 
- This engine explicitly supports multiple, independently configured GitHub organizations, each with its own `webhook_secret`, precisely the scenario documented for "Using Multiple Github Applications". [5](#0-4) 

Binding broken (equality that should hold but doesn't): **organization that authenticated the request == organization owning the repository the handlers act on**. Concretely, the code enforces `verify(secret_of(payload.repository.owner.login))` but then dispatches based on `payload.repository.full_name`, without asserting `owner_of(payload.repository.full_name) == payload.repository.owner.login`.

Before the attack: only genuine GitHub webhook deliveries for org A, signed with org A's secret, can affect org A's own repositories/stacks (as looked up by `full_name`, which for genuine GitHub payloads always matches `owner.login`).
After the attack: a party who knows org A's `webhook_secret` (e.g., a legitimate collaborator/maintainer of an app installed for org A, or anyone who has ever seen it leak — note this does not require access to org B's or the victim stack's secret) can send `POST /github/webhooks` with `X-Github-Event: push`/`status`/etc., `repository.owner.login = "org-A"`, but `repository.full_name = "org-B/victim-repo"`. `verify_signature` passes (it only checks org A's secret against the body), and the handler subsequently looks up `Repository.from_github_repo_name("org-B/victim-repo")` and acts on that stack.

### Impact Explanation
Handlers reachable this way include `StatusHandler`, which creates a `CommitStatus` on any matching commit `sha` for the victim repository via `commit.create_status_from_github!(params)` — this can be used to mark a malicious/undeployed commit as "success" for CI, which (per Shipit's `continuous_deployment` feature) can trigger an automatic deploy of attacker-controlled state on the victim stack. `PushHandler` can also force `sync_github` on victim stacks. Forging trusted CI status to enable an unauthorized/automatic deploy pathway falls under "unauthorized deploy," matching a Critical-class impact per the rules. The severity depends on whether the deployment host actually uses `continuous_deployment` and whether the forged status covers a required context, which I could not fully confirm from the indexed code (stack/deploy trigger logic for continuous deployment was only partially retrieved).

### Likelihood Explanation
This requires the attacker to know a valid `webhook_secret` for at least one organization configured in the multi-org `github:` secrets block — a scenario the engine explicitly documents as supported. It does not require GitHub repository write access, an API token, or session compromise, only knowledge of one org's webhook secret (which is lower-privilege than the target org's secret or GitHub write access to the victim repo), so it is plausible in real multi-tenant Shipit deployments serving several organizations.

### Recommendation
In `WebhooksController#verify_signature` (or in each `Handler`), after successfully verifying the signature for `repository_owner`, additionally assert that `payload.dig('repository', 'full_name')&.split('/')&.first == repository_owner` (and similarly cross-check `organization.login` when present) before dispatching to handlers, rejecting the request with `422` otherwise.

### Proof of Concept
Not independently exploitable in a lab from the indexed context alone (would require a running multi-org Shipit deployment with two configured GitHub orgs to fully demonstrate); the described request forgery is nonetheless directly evidenced by the code paths cited above: signature keyed on `repository.owner.login` vs. dispatch keyed on `repository.full_name`, with no cross-check between them.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
