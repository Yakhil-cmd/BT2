### Title
Webhook signature is verified against the payload's `repository.owner`/`organization` login while every event handler resolves its target Stack from `repository.full_name` — allowing cross-organization payload forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported Concrete bug class is "a verification step checks one thing (`repayTokenToClaimRouter`'s intended target) while the actual mutating call acts on a different thing (`requestTokenFromClaimRouter`)" — i.e., a mismatch between what is authorized/verified and what is actually executed. The closest reachable analog in shipit-engine is the webhook signature-verification step in `WebhooksController`, which authenticates the payload against one identity (the organization derived from `repository.owner.login`/`organization.login`) while the event handlers that subsequently execute act on a different, attacker-controlled field (`repository.full_name`), breaking the binding: `organization that authenticated == repository that is acted upon`.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against, using `repository_owner`: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This is critical in the documented multi-organization configuration, where each GitHub organization has its own distinct `webhook_secret`: [3](#0-2) 

Once the signature check passes, `create` dispatches the *entire* JSON body to the registered handlers, unfiltered: [4](#0-3) 

Every handler (`PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc.) resolves the Stack/Repository it will act on via the base `Handler#repository_name`, which reads `payload.dig('repository', 'full_name')` — a completely independent field from the one used for signature verification: [5](#0-4) [6](#0-5) 

Nothing ties `repository.owner.login`/`organization.login` (used to pick the verifying secret) to `repository.full_name` (used to pick the acted-upon repository). An attacker who is a legitimate member/admin of "Org-A" (and therefore knows or can configure Org-A's `webhook_secret`, e.g. by adding their own webhook delivery endpoint or replaying a delivery from their own org) can sign a payload whose top-level `repository.owner.login`/`organization.login` is `"Org-A"` (so the signature validates against Org-A's secret) but whose `repository.full_name` is `"Org-B/some-stack"`, a repository belonging to a completely different, unrelated organization/customer configured on the same Shipit instance. The `verify_signature` check passes, and the handler then acts on Org-B's stack.

Concretely, with `PushHandler`: [7](#0-6) 

An attacker-forged `push` event (signed with Org-A's secret, but `repository.full_name` = `"Org-B/target"`) causes `stack.sync_github(expected_head_sha: ...)` to be invoked for Org-B's stacks that the attacker has no legitimate access to and no valid signature for. Similarly `StatusHandler` and `CheckSuiteHandler` will create/attach CI statuses and check-run refresh jobs onto Org-B's commits based purely on `sha`/`full_name` fields inside the forged, cross-signed payload: [8](#0-7) [9](#0-8) 

Because Shipit's continuous-delivery pipeline treats a passing/complete set of statuses and checks as a gate to auto-deploy (`schedule_continuous_delivery`, `enable_ci_on_stack`), an attacker who can inject arbitrary `Status` records for Org-B's commits (by forging cross-org-signed `status` events) can manufacture the CI conditions Shipit requires before it will automatically ship a commit on Org-B's stack: [10](#0-9) 

This breaks the required binding "the organization whose secret authenticated the delivery == the repository the handler mutates," resulting in a cross-repository/cross-organization write to another tenant's Shipit state and a route toward an unauthorized continuous-delivery deploy.

### Impact Explanation
This qualifies as Critical under the "cross-repository writes... or an unauthorized deploy" bar: an attacker who legitimately controls Org-A's webhook delivery (a low-privilege position, not requiring any Shipit session, `ApiClient` token, or the app's GitHub App private key) can forge signed deliveries that write `Commit`/`Status` records and trigger sync/check-refresh jobs against a stack belonging to a different organization hosted on the same shared Shipit instance, and can manipulate the CI-gate state that `Stack#schedule_continuous_delivery` relies on to trigger automatic deploys.

### Likelihood Explanation
Requires only that the attacker control (or previously receive/replay) a valid webhook delivery signed with *any one* organization's `webhook_secret` configured on the multi-org Shipit instance — a routine, low-privilege capability for anyone administering a GitHub App/webhook on their own org — combined with crafting the JSON body so `repository.owner.login`/`organization.login` differs from `repository.full_name`. No repository write access, GitHub App private key, or Shipit session is needed, satisfying the "unprivileged attacker" scope constraint.

### Recommendation
`verify_signature` should not just pick a secret based on an unauthenticated field of the payload — after selecting the GitHub App config and verifying the HMAC, the controller (or `Handler#repository_name`) must additionally assert that `repository.owner.login` (the identity whose secret validated the signature) matches the owner segment of `repository.full_name` before any handler is allowed to act on it. Reject (422) requests where these two fields disagree.

### Proof of Concept
Conceptual forged delivery (cannot be executed without live infra, but demonstrates the code path):

```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=<HMAC using Org-A's known webhook_secret over the raw body below>

{
  "ref": "refs/heads/master",
  "after": "deadbeef",
  "repository": {
    "owner": { "login": "Org-A" },        // used by verify_signature to pick Org-A's secret
    "full_name": "Org-B/victim-stack"     // used by PushHandler/Repository.from_github_repo_name to pick the acted-upon stack
  }
}
```

- `WebhooksController#verify_signature` computes `repository_owner = "Org-A"`, loads Org-A's `webhook_secret`, and the signature validates (attacker signed with the secret they legitimately possess for Org-A).
- `Shipit::Webhooks.for_event('push')` dispatches the full payload to `PushHandler`.
- `PushHandler#stacks` calls `Repository.from_github_repo_name("Org-B/victim-stack")`, resolving and mutating a stack in Org-B despite the signature having been verified only against Org-A's secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
