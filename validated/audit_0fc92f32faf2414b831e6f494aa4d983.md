### Title
Cross-repository status forgery poisons `Commit#deployable?` via unscoped `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits purely by `sha` (`Commit.where(sha: params.sha)`) with no repository/stack scoping, unlike every other webhook handler in the engine, which resolve `stacks`/`repository` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. Because `verify_signature` in `WebhooksController` only binds the request to a GitHub *organization* (not the specific repository), any repository whose webhooks are signed with that org/App's shared secret can inject a `success` status for a `sha` that also exists in a completely different stack's commit table, flipping `Commit#deployable?` to `true` and letting a subsequent non-forced `Stack#trigger_deploy` bypass the "CI actually passed" guarantee (`ignored_safeties == false`).

### Finding Description
The binding an operator implicitly relies on is: `ignored_safeties == false` ⇔ `until_commit.deployable?` was set by a status genuinely reported for *this stack's own repository*. That binding is `Deploy#ignored_safeties = force || !until_commit.deployable?` computed in `Stack#build_deploy`, and `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [1](#0-0) , where `success?` is delegated from `status`, which is built entirely from `statuses` records [2](#0-1) [3](#0-2) .

`Status` records are created by `StatusHandler#process`:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

This query is global across the `commits` table — it is **not** filtered by `stack_id` or by the repository named in the payload. Contrast this with the base `Handler` class's `stacks`/`repository_name` helpers, which every other handler (`PushHandler`, `PullRequest::*Handler`, `CheckSuiteHandler`) uses to scope work to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))&.stacks` [5](#0-4) . `StatusHandler`'s `params` schema does not even declare `repository` as required, and never reads it [6](#0-5) .

The only gate before `process` runs is `WebhooksController#verify_signature`, which resolves the GitHub App by **organization**, not by repository:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end
``` [7](#0-6)  combined with `repository_owner` derived only from `payload.dig('repository','owner','login')` [8](#0-7) . This means the webhook secret is shared across **every repository** covered by that GitHub App/organization installation — it authenticates "a webhook from some repo in this org," not "a webhook from the specific repository that owns this commit sha." Once a payload passes that org-level signature check, `StatusHandler` applies the reported `state` to any `Commit` row anywhere in the database whose `sha` matches, regardless of which stack/repository it actually belongs to.

`Commit#create_status_from_github!` → `Commit#add_status` then recomputes `status`, fires the `deployable_status` hook, and (crucially) leaves the commit's `deployable?` flipped for any stack holding that sha [9](#0-8) [10](#0-9) . Subsequently, `Stack#build_deploy` computes `ignored_safeties: force || !until_commit.deployable?`, and with `deployable?` now `true`, `ignored_safeties` becomes `false` even though the "success" signal came from a webhook whose payload never named this repository at all.

Existing guards do not close this gap: `drop_unhandled_event` and `verify_signature` only gate on event type and organization-level signature, `ExplicitParameters` only validates shape (`sha`, `state`, etc.), not repository identity; there is no `Repository`/`Stack` ownership check anywhere in `StatusHandler`.

### Impact Explanation
A crafted (but validly org-signed, or same-org-repo-originated) `status` webhook can flip `deployable?` for a commit belonging to a **different repository/stack** than the one that emitted the event, causing a subsequent normal (non-`force`) deploy through the UI/API to proceed with `ignored_safeties == false` on effectively unverified code. This is an unauthorized-deploy class issue (payload for one repository mutating another repository's commit/stack state), matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The practical exploit requires that the forged `sha` value actually collide with a real commit sha tracked in the victim stack (e.g., via shared git history from forking, cherry-picking, or a maintained mirror) and that both repositories are covered by the same GitHub App/organization installation in this Shipit deployment — this narrows but does not eliminate the attack surface, since forks and mirrors commonly share commit shas with their upstream by design.

### Likelihood Explanation
Exploitation requires: (1) the attacker's own repository to be part of the same GitHub organization/App installation as the victim stack (so the org-scoped signature check passes for a genuinely GitHub-signed event), and (2) a sha collision between a commit the attacker's repo can trigger a status event for and a commit tracked by the victim stack — realistic for forks/mirrors of the victim repo, which by git design retain identical commit shas for unmodified history. Given those preconditions, the attack is fully repeatable (any status event, any sha) at zero cost beyond owning/administering a repo in the shared org, with no Shipit credentials needed.

### Recommendation
Scope `StatusHandler#process` to the reporting repository: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and only update `Status` records for commits belonging to stacks under that repository (mirroring the `stacks`/`repository_name` pattern used by every other handler), e.g. `commit.stack.repository == repository` before calling `create_status_from_github!`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative):
```ruby
test "status handler does not leak cross-repository status onto a same-sha commit in another stack" do
  victim_stack = shipit_stacks(:shipit) # repo "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef", ...) # no statuses yet
  assert_equal false, victim_commit.deployable? # side A of binding: not deployable pre-attack

  forged_payload = {
    'sha' => 'deadbeef',
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)

  victim_commit.reload
  assert_equal false, victim_commit.deployable? # side B: must still be false after fix

  deploy = victim_stack.trigger_deploy(victim_commit, AnonymousUser.new, force: false)
  assert_predicate deploy, :ignored_safeties? # must remain true (safety not bypassed) after fix
end
```
Before the fix, `victim_commit.deployable?` becomes `true` and `deploy.ignored_safeties?` becomes `false`, demonstrating the broken binding; after scoping `StatusHandler` to the reporting repository, both assertions hold.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
