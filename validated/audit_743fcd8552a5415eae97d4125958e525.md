### Title
Cross-organization/cross-repository commit-status forgery via webhook signature scope mismatch - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook using only the *organization* (`repository_owner`) named in the attacker-controlled JSON body, and that check can be a no-op when the organization has no `webhook_secret` configured (an explicitly documented, supported setup). The handler that actually mutates state — `StatusHandler` — never re-checks the organization/repository at all; it looks up commits globally by `sha` across the *entire* Shipit instance. This breaks the binding "the organization that authenticated the request == the repository/commit that gets written."

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/secret to validate against purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository','owner','login')` or the `organization.login` fallback — both attacker-supplied fields in the unauthenticated POST body. `Shipit.github(organization: repository_owner)` then resolves the HMAC secret for *that named organization*, and: [3](#0-2) 

`verify_webhook_signature` returns `true` unconditionally when the organization has no configured secret. Per the setup docs, the webhook secret is optional per organization, and Shipit supports multiple organizations sharing one instance: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes (trivially, for any org without a secret, or via a mismatched `repository.owner.login` vs. `repository.full_name`/`sha` pointing at a different, protected repo), the controller dispatches the full attacker-controlled JSON to handlers with no further scoping: [6](#0-5) 

`StatusHandler` then updates commit status by SHA with **no organization or repository check whatsoever**, across the whole Shipit deployment: [7](#0-6) 

So the equality that should hold — "organization whose credential authenticated this webhook == repository/stack whose commit is written" — is not enforced anywhere in this path: authentication is scoped to an organization name embedded in the payload (or trivially bypassed if that organization has no secret), while the actual write (`Commit.where(sha: params.sha)`) is scoped to nothing but a commit SHA, which is guessable/observable (SHAs are not secret; commit SHAs of any tracked repo are visible in the public Shipit UI/API for that stack).

### Impact Explanation
An unauthenticated, unprivileged network attacker can forge a `status` webhook naming a low-security/no-secret organization (satisfying `verify_signature` for free) while supplying the `sha` of a commit that actually belongs to a different, higher-value repository/stack tracked by the same Shipit instance. `StatusHandler` will happily attach an attacker-chosen `state` (e.g. `success`), `description`, `context`, and `target_url` to that commit's status list via `Commit#create_status_from_github!`, because the lookup is global and repository-agnostic. Since commit statuses are the mechanism Shipit uses to gate deploy safety/"deployable" state, this lets an attacker inject a forged passing status for a commit they do not control CI for, undermining the deploy safety-gate binding and enabling an unauthorized deploy path for that stack — this maps to the report's "authenticated organization vs. written repository" analog and to the required Critical impact category (unauthorized deploy).

### Likelihood Explanation
Likelihood is high wherever the operator (as documented) omits a `webhook_secret` for at least one organization mounted on the shared instance, or wherever multiple organizations are configured with distinct secrets (multi-org support is a first-class, documented feature). No GitHub credential, Shipit session, API token, or webhook secret for the *target* organization is required — only knowledge of a target commit SHA, which is not treated as a secret anywhere in the engine.

### Recommendation
`StatusHandler` (and any handler acting on `repository`/`sha`) must resolve and constrain the affected `Commit`/`Stack`/`Repository` scoped to the organization/repository that was actually verified by `verify_signature`, not merely by SHA. `WebhooksController#verify_signature` should also pass the verified organization identity into every handler and require handlers to assert `payload.dig('repository','full_name')` belongs to that same verified organization before taking any action, rejecting mismatches instead of trusting attacker-supplied `full_name`/`sha` values independently of the authenticated identity.

### Proof of Concept
1. Operator configures Shipit with two organizations in `config/secrets.yml`, e.g. `low-security-org` (no `webhook_secret` set, per the documented optional setting) and `victim-org` (tracked stacks with required/blocking statuses gating deploys).
2. Attacker (no credentials at all) sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {"owner": {"login": "low-security-org"}, "full_name": "low-security-org/whatever"},
  "sha": "<sha of a commit on a victim-org stack, obtained from the public Shipit UI/API>",
  "state": "success",
  "context": "required-ci-check",
  "description": "forged",
  "target_url": "https://attacker.example"
}
```
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "low-security-org")`, whose `verify_webhook_signature` returns `true` unconditionally because no secret is configured — [8](#0-7) .
4. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no organization/repository check, writing the forged "success" status onto the victim-org commit — [7](#0-6) .
5. The victim stack's commit now reports a forged passing required status, potentially unblocking deploy/merge-queue logic that gates on commit statuses.

**File:** lib/shipit/github_app.rb (L76-83)
```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
