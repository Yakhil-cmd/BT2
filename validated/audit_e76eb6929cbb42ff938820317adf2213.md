### Title
Cross-tenant Status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` matches commits solely by `sha` (`Commit.where(sha: params.sha)`) with no join or filter on the payload's `repository`, unlike every other handler which scopes through `Handler#stacks` (`Repository.from_github_repo_name(repository_name)&.stacks`). Because git commit shas are content-addressed and identical across forks, a status webhook that is legitimately signed for one organization/repository can mutate `Status` rows — and therefore `Commit#deployable?` / `Stack#deployable?` — for a `Commit` belonging to an entirely different organization's stack (including an ephemeral `ReviewStack`) that happens to share that sha (e.g., a shared base-branch merge-base commit).

### Finding Description
The claimed binding is: repository owning the review stack (A) == repository authenticated by the webhook (attacker's repo). Tracing the code shows this equality is never checked in `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

`Handler#stacks`/`#repository_name` exists precisely to enforce this binding by resolving `payload.dig('repository','full_name')` to a `Repository` and only touching that repository's `stacks`, and `PushHandler` uses it correctly. [2](#0-1) 
`StatusHandler` neither declares `repository`/`repository.full_name` in its `params` schema nor uses `stacks` — it operates directly on the global `Commit` table by `sha` only. `Commit#create_status_from_github!` then writes the `Status` under `commit.stack_id` — the stack that legitimately owns that `Commit` row (e.g. Org A's `ReviewStack`), not the stack referenced by the webhook's own `repository` field.

Exploit flow: the attacker forks Org A's base repository, so the shared base-branch merge-base commit sha is identical in both the attacker's fork and Org A's ecosystem. Org A's `ReviewStack` GithubSyncJob walks first-parent history from the PR head and creates a local `Commit` row (scoped to the review stack's `stack_id`) for that shared merge-base sha (`GithubSyncJob#append_commit` → `stack.commits.create_from_github!`). The attacker then causes a `status` webhook whose signature verifies for a repository/organization the attacker legitimately controls (their own fork, with the app installed and its own configured `webhook_secret`), but whose JSON body's `sha` is the shared merge-base sha and `state: 'success'`. `WebhooksController#verify_signature` only checks that the HMAC matches the secret for `repository_owner` extracted from the payload — it does not verify that the commit(s) that end up mutated belong to that same repository. `StatusHandler#process` finds Org A's `Commit` row by raw sha match and writes a `success` `Status` under Org A's `ReviewStack` `stack_id`.

This flips `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) to true for that commit in Org A's stack, and `UndeployedCommit#deploy_disallowed?` (`!deployable? || !stack.deployable?`) to false, enabling `Stack#trigger_continuous_delivery` (since `continuous_deployment` is on) to build and enqueue a `Deploy` for Org A's ephemeral review stack — an unauthorized deploy triggered entirely by a cross-tenant, correctly-signed-for-a-different-repo webhook. [4](#0-3) [5](#0-4) [6](#0-5) 

Existing guards do not close this gap: `verify_signature` authenticates *a* repository owner, not *the* repository owner of the commit being mutated, and the `ExplicitParameters` schema for `StatusHandler` doesn't even require or use a `repository` field to cross-check. [7](#0-6) [8](#0-7) 

### Impact Explanation
A record (a `Status`, and transitively a `Deploy`/`Task`) is written for a stack that the webhook's authenticated repository never authorized, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". The blast radius is any `Commit` sha collision across tenants sharing history (shared base branches, forks, cherry-picks, or even coincidental identical trees) — this is systemic, not a one-off, since `StatusHandler` performs zero repository scoping for every status webhook processed, not just for review stacks. Any stack (not only review stacks) is exposed to cross-tenant status pollution.

### Likelihood Explanation
Preconditions: the target stack must have `continuous_deployment` enabled (or a human relying on `deploy_disallowed?`/`deployable?` to gate a manual deploy) and the attacker must be able to get a `status` webhook processed with a signature that verifies for *some* repository they control under the same Shipit instance (their own fork, if the operator installed the GitHub App broadly, or any other org/repo the attacker legitimately administers). No secrets belonging to Org A are needed — only a legitimately signed webhook for a completely different, attacker-controlled repository. Feasibility is high for any attacker who can open PRs / control a fork against the target's upstream repository and either has their own repo hooked to the same Shipit instance or can otherwise get a validly-signed status delivered; it is fully repeatable since it costs the attacker only a normal GitHub status update.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the webhook payload, mirroring `PushHandler`/`Handler#stacks`: resolve `Repository.from_github_repo_name(repository_name)`, restrict to that repository's stacks, and only update `Commit` rows whose `stack_id` belongs to that repository (e.g. `stacks.joins(:commits).merge(Commit.where(sha: params.sha))` or equivalent), rejecting/ignoring shas that don't belong to the authenticated repository's stacks.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or extending `webhooks_controller_test.rb`):
1. Create `stack_a = shipit_stacks(:review_stack_org_a)` (a `ReviewStack`, `continuous_deployment: true`) and `commit_a = stack_a.commits.create!(sha: 'sharedsha1234...', ...)` with no prior successful status (`refute_predicate commit_a, :deployable?`).
2. Create `stack_b = shipit_stacks(:attacker_repo)` belonging to a different `Repository`/org, with `commit_b = stack_b.commits.create!(sha: 'sharedsha1234...', ...)` (same sha, different stack, simulating shared merge-base history).
3. POST a `status` webhook whose JSON `repository.full_name` matches `stack_b`'s repository (signature stubbed/valid for that repo, per `test/controllers/webhooks_controller_test.rb` pattern using `GithubHook.any_instance.stubs(:verify_signature).returns(true)` or `Shipit.github(organization:).stubs(:verify_webhook_signature).returns(true)`), with `sha: 'sharedsha1234...'`, `state: 'success'`.
4. Assert: `commit_a.reload; assert_predicate commit_a, :deployable?` and `assert_not commit_a.stack.undeployed_commits.map { |c| UndeployedCommit.new(c, index: 0) }.first.deploy_disallowed?` — i.e., Org A's commit became deployable purely from a webhook authenticated for Org B's repository — proving the binding `repository owning stack A == repository authenticated by webhook` is violated. Additionally assert `assert_difference('Shipit::Deploy.count', 1) { stack_a.trigger_continuous_delivery }` to demonstrate the unauthorized deploy.
