### Title
Webhook signature verified against `repository.owner.login` while all downstream handlers act on the unrelated `repository.full_name` field — organization-scoped webhook secrets do not bind to the repository actually mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's webhook secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted JSON body, but every webhook handler (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) subsequently resolves the target `Stack`/`Repository`/`Commit` using a *different* field of the same untrusted body — `repository.full_name` (or, for `status`, a bare `sha` with no repository scoping at all). Nothing ties the field used to pick the verifying secret to the field used to select what gets mutated, so a valid signature computed with one organization's secret does not guarantee the payload only affects that organization's repositories.

### Finding Description
The signature check is: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

Once `verify_signature` passes, `create` blindly dispatches the entire parsed body to every registered handler for the event, with no re-derivation or cross-check of which organization it "belongs" to: [3](#0-2) 

The base `Handler` class — used by `PushHandler` and all pull-request handlers — resolves the affected `Stack`/`Repository` from a *separate* field of the same body, `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

`PushHandler` then triggers a real sync against whatever stacks match that `full_name`, using an attacker-controlled `after` SHA: [5](#0-4) 

`StatusHandler` is even less scoped — it doesn't consult `repository` at all, only `sha`, and will apply the forged CI status to any `Commit` row in the entire installation that happens to match that SHA: [6](#0-5) 

Because Shipit supports a single deployment fronting multiple GitHub organizations, each with its own configured `webhook_secret` (documented in `docs/setup.md`'s multi-org config example), the entity whose secret authenticates the request (`repository.owner.login`) is not the entity that is actually written to (`repository.full_name`). An operator of one onboarded, lower-trust organization — who legitimately knows their own org's `webhook_secret` because they created/administer their own GitHub App installation for that org — can craft a webhook body where `repository.owner.login` names their own org (so `verify_webhook_signature` succeeds using their own secret) while `repository.full_name` names a stack that belongs to a different, unrelated organization tracked by the same Shipit instance. `verify_webhook_signature` only performs an HMAC check; it never asserts that the signed organization matches the repository the handler will operate on: [7](#0-6) 

This breaks the trust binding: `{organization that authenticated the webhook} == {repository whose stacks are mutated by the handler}`. Before the attack, the two are assumed equal (implicit design assumption). After a forged cross-organization payload, they diverge: the signature is valid for org A, but the mutated stack belongs to org B.

### Impact Explanation
An attacker who legitimately administers one onboarded, lower-privilege GitHub organization (and therefore knows only that org's webhook secret) can forge `push` events against stacks belonging to a completely different, unrelated organization tracked by the same Shipit instance. This lets them:
- Trigger `GithubSyncJob` with an attacker-chosen `expected_head_sha` for a foreign stack (`PushHandler`), influencing which commits Shipit considers reachable/deployed for that stack.
- Inject or overwrite CI `Status`/`commit_status` records for arbitrary commits across any tracked repository via `StatusHandler`, since it is not scoped to a repository/organization at all — this can flip a commit from "pending"/"failing" CI to "success", which is exactly the signal `ci.require` checks rely on to gate deploys, and can enable an unauthorized deploy of a foreign repository's stack.

This crosses an organizational trust boundary that the per-org webhook secret design is meant to enforce, escalating a low-privilege organization admin into being able to influence deploy-gating state (and downstream deploy execution) for a different organization's stacks — matching the "unauthorized deploy" / cross-repository-write impact tier.

### Likelihood Explanation
Exploitability requires only that the attacker already administers/owns one GitHub organization that is legitimately configured under this shared Shipit instance (a realistic multi-tenant deployment per `docs/setup.md`), and knows that org's own `webhook_secret` — which is not "the victim's secret," it's the attacker's own, entirely expected credential for their own org. No repository write access, no ApiClient token, and no privileged Shipit account is required; only the ability to POST a webhook payload to the public `/webhooks` endpoint with a valid HMAC computed from the attacker's own known secret. The `status` path is especially easy to hit because it performs zero repository/organization scoping.

### Recommendation
Bind the value used to select the verifying secret to the value(s) used by handlers to resolve targets:
- After computing `repository_owner` for signature verification, re-verify that every repository/organization referenced anywhere else in the payload (`repository.full_name`, and any nested `organization.login`) is consistent with `repository_owner` before dispatching to handlers, rejecting mismatches with `422`.
- In `Shipit::Webhooks::Handlers::Handler#stacks`, additionally filter/assert that the resolved `Repository`'s owner matches the verified `repository_owner` passed down from the controller.
- In `StatusHandler#process`, scope `Commit.where(sha: params.sha)` to commits whose `stack.repository.owner` matches the verified organization instead of matching bare SHA across the whole installation.

### Proof of Concept
1. Shipit is configured (per `docs/setup.md`) to serve two GitHub organizations, `org-attacker` and `org-victim`, each with its own `github.webhook_secret` in `secrets.yml`.
2. The attacker legitimately administers `org-attacker`'s GitHub App and therefore knows `org-attacker`'s `webhook_secret`.
3. The attacker crafts a `push` webhook JSON body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen sha>",
     "repository": {
       "owner": { "login": "org-attacker" },
       "full_name": "org-victim/private-repo"
     }
   }
   ```
4. The attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-attacker secret, body)>` and POSTs it to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: 'org-attacker')` and the signature validates successfully, since it was computed with the correct (attacker-known) secret for `org-attacker`.
6. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `Repository.from_github_repo_name('org-victim/private-repo')` — a repository the attacker has no legitimate relationship with — and calls `stack.sync_github(expected_head_sha: '<attacker-chosen sha>')`, causing Shipit to act on `org-victim`'s stack using an organization-A-signed request.

Note: I was not able to fully trace `Shipit.github`'s exact multi-org config-loading and secret-lookup implementation (`lib/shipit.rb`) within the tool budget available, so the precise mechanics of how `webhook_secret` is scoped per-organization in a multi-org install could not be independently confirmed beyond what `docs/setup.md`'s example config and `lib/shipit/github_app.rb#verify_webhook_signature` show; this is a limitation of the investigation, not evidence against the finding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
