### Title
Missing Cosigner Authorization Check on Local Shared-Address Signing Requests Enables Cross-Device Forced Signing - (File: wallet.js)

### Summary
In the device-message handler for the `"sign"` subject, `wallet.js` validates that a *remote* signing request's sender is a listed cosigner (`ifRemote` branch), but the `ifLocal` branch — reached when the requested address/signing_path resolves to a key hosted on *this* device — performs no equivalent check that the message sender (`from_address`) is actually authorized to request a signature over that address/path. This mirrors the Termix flaw: a client-supplied identifier (`from_address`, analogous to Termix's client-controlled `sessionId`) is trusted to access another party's protected resource (here, the local signing/approval flow for a shared or multisig address) without verifying the caller legitimately owns/co-controls that resource.

### Finding Description
The message dispatcher `handleMessageFromHub` in [1](#0-0)  extracts `from_address` purely from the sender's device pubkey and passes it down to subject handlers. For the `"sign"` subject [2](#0-1) , after validating the unit structure, it calls `findAddress(body.address, body.signing_path, {...})` [3](#0-2) .

`findAddress` (in the same file) resolves whether the target address/signing_path is hosted locally (`ifLocal`) or on another cosigner's device (`ifRemote`) purely from the local DB tables (`my_addresses`, `wallet_signing_paths`, `shared_address_signing_paths`) [4](#0-3) .

Crucially, in the `ifRemote` callback, the code explicitly checks that the requester is a legitimate participant:
```
if (!other_device_addresses.includes(from_address))
    return callbacks.ifError("you are not listed as a cosigner for this address "+body.address);
``` [5](#0-4) 

But the `ifLocal` callback has the analogous check commented out, with a note that enabling it "would make multilateral signing impossible":
```
ifLocal: function(objAddress){
    // the commented check would make multilateral signing impossible
    //db.query("SELECT 1 FROM extended_pubkeys WHERE wallet=? AND device_address=?", [row.wallet, from_address], function(sender_rows){
    //    if (sender_rows.length !== 1)
    //        return callbacks.ifError("sender is not cosigner of this address");
        callbacks.ifOk();
        ...
        return eventBus.emit("signing_request", objAddress, body.address, objUnit, assocPrivatePayloads, from_address, body.signing_path);
``` [6](#0-5) 

As a result, *any* correspondent device (any device that has completed pairing with the victim device — note "pairing" is one of the subjects allowed even from non-correspondents per [7](#0-6) ) can send a `"sign"` request naming any address that the victim device hosts locally, even if that requesting device is not one of the address's actual cosigners recorded in `wallet_signing_paths` / `shared_address_signing_paths`. The handler accepts the request (`callbacks.ifOk()`), validates the unit's own well-formedness/payload hashes, and unconditionally emits the `signing_request` event carrying the unauthenticated `from_address` and the attacker-supplied `objUnit`/private payloads. Any consumer of `ocore` (wallet UI, exchange/service integration, automated multisig bot) that reacts to `signing_request` for known local shared addresses can be induced to sign or forward a signature for a transaction it never authorized as a counterparty, since the ownership/cosigner relationship for the *local* half of the request is never verified against the sender.

### Impact Explanation
Shared/multisig addresses in ocore rely on the assumption that only registered cosigner devices (tracked in `shared_address_signing_paths`/`wallet_signing_paths`) can request signatures against them. By omitting the authorization check in the `ifLocal` path, an attacker who is merely *paired* with a victim device — not necessarily a cosigner of the specific address being targeted — can impersonate a legitimate cosigner and drive the signing workflow for shared/multisig outputs, potentially causing the victim to co-sign or approve a fraudulent unit, leading to unauthorized spending from a shared address or corruption of multi-party contract flows (`arbiter_contract_shared`, prosaic/arbiter contract deposits also depend on trusting `from_address` at the shared-address confirmation layer, see `sign` handling and `getSigner`'s local-sign flow at [8](#0-7) ). This satisfies "unauthorized spending" / "AA-adjacent fund loss" criteria for shared-address funds.

### Likelihood Explanation
Exploitation requires only that the attacker's device be paired as a correspondent of the victim (a low bar — pairing secrets are commonly shared, e.g. via QR codes for onboarding cosigners, textcoins, or exchange integrations), and that the victim's device locally hosts a shared/multisig address whose definition the attacker can discover or guess via other channels (e.g. from a previously shared partial definition). No cryptographic secret is required to trigger the request; only the `signing_request` event's downstream handler (UI confirmation or automated approval logic) determines whether an actual signature is produced.

### Recommendation
Reinstate and enforce a cosigner-authorization check in the `ifLocal` branch of the `"sign"` handler in [9](#0-8) , verifying that `from_address` is actually recorded as a device cosigner for `body.address`/`body.signing_path` (e.g., via `shared_address_signing_paths`/`wallet_signing_paths`/`extended_pubkeys`) before calling `callbacks.ifOk()` and emitting `signing_request`. If multilateral signing genuinely requires accepting requests from addresses outside the local definition, that trust decision should be scoped/whitelisted explicitly (e.g., matched against the unit's own `authors` set and a verified relationship), not silently accepted for any correspondent.

### Proof of Concept
1. Device A pairs with victim Device B (via a shared pairing secret) — this alone satisfies the "correspondent known" requirement in [10](#0-9) .
2. Device A learns/guesses that Device B locally hosts a shared address `SHARED_ADDR` at signing path `r.1` where B is *not* actually one of A's assigned cosigners (A has no legitimate signing_path entry for `SHARED_ADDR`).
3. Device A sends a `hub/message` with `subject: "sign"`, `body: {address: SHARED_ADDR, signing_path: "r.1", unsigned_unit: <attacker-crafted unit paying attacker>}`.
4. B's `handleMessageFromHub` → `findAddress` resolves `SHARED_ADDR`/`r.1` as local (`ifLocal`), and — absent the removed check — proceeds directly to `callbacks.ifOk()` and emits `signing_request(objAddress, SHARED_ADDR, objUnit, assocPrivatePayloads, from_address=A, "r.1")` without ever verifying A is an authorized cosigner of `SHARED_ADDR` at that path.
5. Any listener that auto-processes `signing_request` for recognized local shared addresses (common in bots/automated cosigning services) signs the attacker-controlled unit, resulting in unauthorized fund movement.

function findAddress(address, signing_path, callbacks, fallbackInfo){
	db.query(
		"SELECT wallet, account, is_change, address_index, full_approval_date, device_address \n\
		FROM my_addresses JOIN wallets USING(wallet) JOIN wallet_signing_paths USING(wallet) \n\
		WHERE address=? AND signing_path=?",
		[address, signing_path],
		async function(rows){
			if (rows.length > 1)
				throw Error("more than 1 address found");
			if (rows.length === 1){
				var row = rows[0];
				if (!row.full_approval_date)
					return callbacks.ifError("wallet of address "+address+" not approved");
				if (row.device_address !== device.getMyDeviceAddress()) {

					wallet: row.wallet,
					account: row.account,
					is_change: row.is_change,
					address_index: row.address_index
				};
				callbacks.ifLocal(objAddress);
