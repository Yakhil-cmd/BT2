### Title
`StatusHandler#process` looks up commits by raw SHA with no repository scoping, letting a validly-signed webhook from one repository forge deployability/release-status writes onto another stack's commit - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely via `Commit.where(sha: params.sha)`, unlike every other handler which restricts itself to `stacks` scoped by `Repository.from_github_repo_name(repository_name)` from `Handler#stacks`. Because a `Status` row created this way feeds directly into `Commit#deployable?` and, through continuous deployment / `Deploy#update_release_status`, into `Commit#create_release_status!` → `ReleaseStatus#create_status_on_github!`, a webhook whose payload never named `victim/prod` can still flip that repo's commit to deployable and cause an authenticated `create_status` write on `victim/prod`'s real GitHub repository.

### Finding Description
The claimed binding is: `payload.repository.full_name == commit.stack.repository.full_name` must hold before a `Status` is attached to a `Commit` and before that status can influence `Commit#deployable?`. Tracing the code shows this equality is never checked in `StatusHandler`.

- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This ignores `payload['repository']` entirely and matches every `Commit` row across every stack/tenant sharing that SHA.

- Compare with the base class's intended scoping mechanism, used by other handlers (`app/models/shipit/webhooks/handlers/handler.rb:32-38`):
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
```
`StatusHandler` bypasses this repository-scoped lookup.

- `create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:165-169`, `:366-384`) updates `Commit#status`, emits `:deployable_status`, and calls `stack.schedule_merges` when the new status is `pending?` or `success?`.
- `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) is purely `!locked? && (stack.ignore_ci? || (success? && !blocked?))` — it has no dependency on which repository originated the status, only on the aggregate `status` derived from whatever `Status` rows are attached.
- If `victim/prod` has `continuous_deployment` enabled, `ContinuousDeliveryJob`/`Stack#schedule_merges` can trigger a real deploy of the now-"successful" commit. On completion, `Deploy#update_release_status` (`app/models/shipit/deploy.rb:272-298`) calls `append_release_status` → `Commit#create_release_status!` (`app/models/shipit/commit.rb:202-213`), gated only by `stack.release_status?`, with no check on where the underlying `Status` came from.
- `ReleaseStatus#create_status_on_github!` (`app/models/shipit/release_status.rb:20-37`) then posts via `stack.github_api.create_status(stack.github_repo_name, commit.sha, state, ...)`, i.e., authenticated, scoped-by-name to `victim/prod`, but triggered entirely by a payload from a different repository.

Attacker's request: a `status` event webhook whose `repository.full_name`/`repository.owner.login` corresponds to a repository the attacker legitimately owns/administers and for which the `X-Hub-Signature` can be produced (signature verification in `WebhooksController#verify_signature` is keyed off `repository_owner`, i.e., `Shipit.github(organization: repository_owner)` — a value the attacker fully controls in the payload and which resolves to their own org's credentials). The `sha` field is set to a commit SHA that also exists in `victim/prod`'s `commits` table (trivially achievable if `victim/prod` is a public repo the attacker has forked/cloned, since Git commit SHAs are content-addressed and identical across forks/clones sharing history).

Existing guards fail here because:
- `verify_signature` only proves the payload was legitimately signed for the named `repository_owner`'s org — it does not, and cannot, prove that the `sha` inside belongs to that same repository.
- `drop_unhandled_event` / `ExplicitParameters` schema only validate shape, not repository ownership of the SHA.
- `Handler#stacks`'s repository-scoping exists precisely to prevent this class of bug, but `StatusHandler` does not use it.

### Impact Explanation
A forged/cross-repo `status` webhook can cause `victim/prod`'s commit to become `deployable?`, potentially triggering an unauthorized deploy via continuous deployment, and unconditionally causes an authenticated `create_status` write to `victim/prod`'s real GitHub repository via `stack.github_api` credentials that belong to Shipit/the victim's org, attributable to Shipit's own bot identity. This is a payload for one repository mutating another's stack/commit/task state and causing an unauthorized deploy and outbound write under Shipit's own credentials — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy"). The attack is repeatable against any stack/commit whose SHA the attacker can reproduce or guess (trivial for public/forked repos), and scales across every tenant sharing the Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must control (own or administer) at least one repository/organization already onboarded to the target Shipit instance so that `verify_signature` succeeds for a webhook they can produce (this is consistent with the stated threat model: "emit webhooks from a repository they own"). They must also know or reproduce a SHA that exists in `victim/prod`'s `commits` table — straightforward for any public repository (fork it; forked commits share identical SHAs) or any repo whose history the attacker can read. No Shipit secrets, session, or API token are required beyond what the attacker already controls for their own repository/org's webhook signing. This makes the attack low-cost and repeatable. One caveat: I could not fully verify from the available index whether `GithubApp#verify_webhook_signature` (`lib/shipit/github_app.rb`) uses a secret unique per organization/installation that only that organization's own admin would know (making this exploitable only by attackers who control an onboarded org) or some other scheme; that file's full contents were not available for verification in this pass, so the exact set of organizations for which an attacker could forge a valid signature should be confirmed directly in `lib/shipit/github_app.rb`.

### Recommendation
Scope `StatusHandler#process` to the payload's own repository, mirroring other handlers:
```ruby
def process
  stacks.flat_map(&:commits).where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more directly, restrict the `Commit` lookup to commits belonging to `stacks` (as computed from `Repository.from_github_repo_name(repository_name)`), so a status can only ever attach to a commit whose stack's repository matches the webhook's own `repository.full_name`.

### Proof of Concept
Minitest plan (model/controller test, no live GitHub):
1. Set up two stacks: `victim_stack` (repo `victim/prod`, `continuous_deployment: true`, `release_status?` truthy) and `attacker_stack` (repo `attacker/evil`), each with a `Commit` row sharing the same `sha` value (simulating a forked commit).
2. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as existing webhook tests do) to isolate the scoping bug from signature mechanics.
3. POST to `/webhooks` with `X-Github-Event: status`, body `{"sha": SHARED_SHA, "state": "success", "repository": {"full_name": "attacker/evil", "owner": {"login": "attacker"}}, "branches": [...]}`.
4. Assert `victim_stack.commits.find_by(sha: SHARED_SHA).reload.deployable?` becomes `true` (binding LHS: payload repo `attacker/evil`; binding RHS: mutated commit's stack repo `victim/prod` — they differ, proving the break).
5. Run the deploy pipeline (`ContinuousDeliveryJob.new.perform(victim_stack)` or `victim_stack.trigger_deploy`), complete the resulting `Deploy`, and assert:
```ruby
Shipit.github.api.expects(:create_status).with('victim/prod', SHARED_SHA, anything, has_entries(context: victim_stack.release_status_context))
```
fires, proving an outbound authenticated write to `victim/prod` was produced from a payload that never named `victim/prod`.
