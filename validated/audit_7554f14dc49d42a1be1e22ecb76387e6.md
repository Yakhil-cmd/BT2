### Title
Cross-organization CI status forgery via webhook signature/scope mismatch enables unauthorized deploy - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub organization named in the payload's `repository.owner.login`/`organization.login` field [1](#0-0) , but the `status` event handler that actually mutates state never re-checks that binding: `StatusHandler#process` looks up commits globally by `sha` across the entire installation, with no repository/organization filter at all [2](#0-1) . This reproduces the `EternalHeroesFactory._buy` bug class: a verification step (organization/signature check) covers one field of the payload while a separate, unguarded action is driven by another field of the same payload that was never bound to that verification.

### Finding Description
`Shipit::Webhooks::Handlers::Handler` normally scopes handlers to a repository via `repository_name = payload.dig('repository', 'full_name')` and `Repository.from_github_repo_name(repository_name)` [3](#0-2) . `StatusHandler`, however, overrides this pattern entirely — it does not call `stacks`/`repository_name` at all, and instead does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha:)` is a global lookup with no `stack_id`/repository scoping, so any commit sharing that SHA in *any* stack in the Shipit instance is matched.

The only authorization gate before this handler runs is `WebhooksController#verify_signature`, which resolves the signing organization purely from the payload itself:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 

and then verifies the HMAC signature using the webhook secret registered for *that* organization [5](#0-4) , `lib/shipit/github_app.rb` `verify_webhook_signature` [6](#0-5) .

Nothing forces `repository.owner.login` (used to pick the signing secret) to be consistent with the SHA that `StatusHandler` acts on, and `StatusHandler`'s own `params` block doesn't even require a `repository` key [7](#0-6) . The binding that should hold — *"organization whose secret authenticated the request" == "organization owning the repository/commit being mutated"* — is broken: the controller verifies field A (`repository.owner.login`) while the handler acts on field B (`sha`), and the two are never cross-checked.

Once a forged status lands, `Commit#create_status_from_github!` records it, and `Commit#deployable?` becomes true if the new status is `success` [8](#0-7) , and `schedule_continuous_delivery` will automatically enqueue `ContinuousDeliveryJob` for the victim stack if continuous deployment is enabled [9](#0-8) , and `Stack#trigger_continuous_delivery` will trigger a real deploy [10](#0-9) .

### Impact Explanation
An attacker who legitimately owns/controls *any one* organization onboarded to the Shipit instance (and therefore knows that organization's own `webhook_secret`) can send a forged `status` webhook whose `repository.owner.login` matches their own org (so it passes signature verification) but whose `sha` corresponds to a commit belonging to a completely different, victim organization's stack. Because `StatusHandler` never re-validates that the commit's stack belongs to the authenticated organization, the attacker can:
- Mark an arbitrary victim commit as CI `success`, satisfying `deployable?` for a stack they have no access to.
- Trigger `Continuous DeliveryJob` and an unauthorized deploy of that commit on a stack outside their organization/authorization boundary.

This is a cross-repository/cross-organization write and can result in an unauthorized deploy, matching the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to control at least one organization/webhook secret already onboarded onto the shared Shipit instance (multi-tenant deployment) — a realistic scenario for a SaaS-style Shipit deployment serving multiple orgs/teams, and does not require any Shipit session, `ApiClient` token, or GitHub repository write access on the victim's side. The forged request is a normal HTTP POST to `/webhooks` with a crafted JSON body and a valid HMAC computed with the attacker's own known secret.

### Recommendation
`StatusHandler#process` (and any other handler that doesn't already scope through `Handler#stacks`) should scope commit/status lookups by the repository identified in the payload, and the controller should enforce that the organization used to verify the signature matches the owner of the repository referenced by the specific event/commit being mutated, rather than trusting the org field in isolation.

### Proof of Concept
1. Attacker owns organization `attacker-org`, which is legitimately onboarded to the shared Shipit instance with known `webhook_secret` `S`.
2. Attacker identifies a commit `sha=X` belonging to `victim-org/victim-repo`'s stack (e.g., visible via the public Shipit UI/API for that stack, or a leaked SHA from a PR).
3. Attacker crafts a `status` event JSON payload:
```json
{
  "sha": "X",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac(S, raw_body)>` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s secret, and the signature validates successfully [5](#0-4) .
6. `StatusHandler#process` runs `Commit.where(sha: "X")`, matches the victim's commit (no repository filter), and records a `success` status on it [2](#0-1) .
7. If `victim-org/victim-repo`'s stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` and `Stack#trigger_continuous_delivery` fire, deploying commit `X` without any authorization from `victim-org` [9](#0-8) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
