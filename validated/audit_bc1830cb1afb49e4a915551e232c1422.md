## Analysis

The relevant binding is the one explicitly called out in scope: **"a stack a token authorises versus a stack it touches."** `Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column, and `Api::BaseController` enforces that scope by intersecting the requested `stack_id` param with the token's authorized stack set: [1](#0-0) 

`Api::CCMenuController` reuses `require_permission :read, :stack` from `BaseController`, which only validates that the token carries the `read:stack` permission string — it never checks *which* stack the token is scoped to: [2](#0-1) 

But `CCMenuController` overrides `stack` to bypass the `stacks` scoping helper entirely, resolving the target stack directly by request parameter instead of through the token-scoped `stacks` collection: [3](#0-2) 

### Title
Stack-Scoped `ApiClient` Tokens Bypass Stack Authorization in `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController#stack` is overridden to call `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])` (the token-scoped lookup used everywhere else in the API, e.g. `Api::DeploysController`, `Api::RollbacksController`). This breaks the invariant that a stack-scoped `ApiClient` token can only touch the single stack it was issued for.

### Finding Description
`ApiClient` records can optionally be bound to one `stack` (`belongs_to :stack, optional: true`) [4](#0-3) . This is meant to let an operator hand out a token scoped to exactly one stack, with limited permissions such as `read:stack`. `BaseController` enforces that scope centrally through `stacks`/`stack`: [1](#0-0) 

`check_permissions!` (invoked via `require_permission`) only checks the permission string, not the stack identity: [2](#0-1) . So the *only* place the stack-scope binding is actually enforced is the `stacks`/`stack` helper in `BaseController`.

`CCMenuController` re-defines `stack` to skip that scoping and query `Stack.from_param!(params[:stack_id])` against the full `Stack` table: [3](#0-2) . As a result, `require_permission :read, :stack` [5](#0-4)  passes for any token carrying `read:stack`, regardless of which stack (if any) it is bound to, and `show` then renders CI/build state for whatever `stack_id` the caller supplies: [6](#0-5) 

This is the binding-break pattern analogous to the ONFT report: the "stack a token authorises" (via `stack_id` on the `ApiClient` record) diverges from "the stack it touches" (any stack resolvable by name in the URL), because one code path (`CCMenuController#stack`) omits the scoping check that the rest of the API relies on.

### Impact Explanation
An attacker holding *any* valid `ApiClient` credential with `read:stack` permission — including one deliberately scoped by an administrator to a single, low-sensitivity stack — can query `GET /api/stacks/:stack_id/ccmenu` for an arbitrary other stack's `stack_id` and receive that stack's latest deploy/rollback status (id, timestamps, running state) via the rendered CC-Menu XML. This is unauthenticated read of stack state across a trust boundary the token issuer explicitly tried to restrict, matching the "unauthenticated read of stack state" High-severity category. It does not grant write/deploy capability, but it does violate the stack-scoping guarantee that the rest of the API (`DeploysController`, `RollbacksController`, `TasksController`, etc.) correctly enforces via `stacks.from_param!`.

### Likelihood Explanation
Any holder of a stack-scoped API token (a routine, intentionally-restricted credential type supported by the engine) can trigger this with a single unauthenticated-beyond-their-own-token HTTP GET, requiring no special access beyond the credential they already legitimately possess for their own stack. No collusion, timing, or race condition is needed; the divergent `stack` method is unconditionally reachable on every request to this controller.

### Recommendation
Remove the `stack` override in `Api::CCMenuController` and use the inherited `stacks.from_param!(params[:stack_id])` from `BaseController` so CC-Menu lookups honor the `ApiClient#stack_id` scope, consistent with every other API controller.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (intended to only ever see stack A's CI status).
2. Using that client's Basic-Auth token, request `GET /api/stacks/<owner>/<repo-B>/ccmenu` for an unrelated stack B that the same Shipit instance manages.
3. `authenticate_api_client` succeeds (valid token) [7](#0-6) ; `require_permission :read, :stack` succeeds because the token has `read:stack` regardless of scope [2](#0-1) ; `stack` resolves stack B directly via `Stack.from_param!` [8](#0-7) , bypassing the `stack_id` restriction that `BaseController#stacks` would have enforced.
4. Response contains stack B's latest deploy/rollback status, which the token was never authorized to view.
