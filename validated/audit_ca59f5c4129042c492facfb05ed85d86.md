### Title
Uncaught exception in `chash.isChashValid()` on malformed address checksum crashes the whole node - (File: chash.js)

### Summary
The CVE describes a kernel panic caused by an unvalidated, attacker-controlled length value flowing into a buffer-pointer arithmetic operation (`skb_pull`) that can go negative, causing an unchecked fault that brings down the whole system from a single crafted packet. The `ocore` analog is `chash.js`'s address-checksum validator: an attacker-controlled encoded address string can drive `separateIntoCleanDataAndChecksum()` into a length branch that always `throw`s, and unlike the base32/base64 decode step, that throw is **not** wrapped in `try/catch`. Because `network.js` installs a global `uncaughtException` handler that deliberately re-throws to crash the process, this single unhandled exception brings down the entire node — the JS analog of a kernel panic from bad packet-derived length arithmetic.

### Finding Description
`isChashValid()` only guards the base32/base64 `decode` call with `try/catch`; everything downstream is unguarded: [1](#0-0) 

`separateIntoCleanDataAndChecksum()` requires the decoded bit-string to be exactly 160 or 288 bits, or it `throw`s an `Error`: [2](#0-1) 

If the base32/base64 decoding of an attacker-supplied encoded string of the "correct" outer character length (32 or 48, checked at `chash.js:153-155`) nonetheless yields a byte buffer whose bit length is not exactly 160/288 (e.g., because the decode routine silently drops/ignores out-of-alphabet characters or otherwise produces a truncated/extended buffer instead of raising an error for malformed input), `bin2buffer`/`buffer2bin` run fine but `separateIntoCleanDataAndChecksum` throws — outside of any `try/catch` in `isChashValid`.

`isChashValid` (and thus `isValidAddress` in `validation_utils.js`) is invoked throughout unit validation for every attacker-supplied address string: payment output addresses, `definition_chash`, asset issuer/definer addresses, AA trigger addresses, attestation `address` field, address-definition-change payloads, etc. Any of these are populated directly from a single posted unit's JSON with no privileged access required.

Once the exception escapes `isChashValid`, it propagates out through `validate()`'s synchronous call chain into Node's fatal-exception path. `network.js` explicitly turns any uncaught exception into a full process crash: [3](#0-2) 

This is structurally identical to the CVE's root cause: a length-derived quantity that is not properly validated before being used in a bit/byte manipulation, whose failure path is not defensively handled, and whose failure escalates into total service loss instead of a contained rejection of the single bad input.

### Impact Explanation
A successful trigger causes the full `ocore` process (hub, full node, or light node performing address validation) to crash via the intentional `throw err` in the `uncaughtException` handler. This is a network-wide denial of service: any node that receives and validates the malicious unit (a joint containing a message with a crafted address-like field) terminates. Because validation of addresses happens on ordinary, unprivileged units (payment outputs, `definition_chash`, attestation payloads, AA triggers), a single unauthenticated peer or unit poster can potentially force a crash on every node that processes that unit, preventing the network from confirming new units until operators intervene and restart affected nodes — matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Likelihood depends entirely on whether the specific base32/base64 decoding routine used by `chash.js` can be coerced into producing a byte buffer whose length disagrees with the outer encoded-string length check (32 → 160 bits, 48 → 288 bits) without itself throwing inside the `try` block at `chash.js:156-162`. I was not able to inspect the exact third-party base32 decode implementation within the available tool budget to confirm this specific decoding edge case, so this is the one unverified link in the chain. Everything else — the unguarded `throw` in `separateIntoCleanDataAndChecksum`, the broad reachability of `isChashValid`/`isValidAddress` from ordinary unit fields, and the deliberate process-crashing `uncaughtException` handler in `network.js` — is directly confirmed in the code.

### Recommendation
- Wrap the entire body of `isChashValid()` (not just the initial decode) in `try/catch`, returning `false` on any exception, consistent with how `verifyMerkleProof()` and other attacker-facing validators already guard their whole computation.
- In `separateIntoCleanDataAndChecksum()`/`mixChecksumIntoCleanData()`, treat unexpected bit-lengths as a normal "invalid input" return value rather than a thrown `Error`, since these are reachable with attacker-controlled data.
- Consider hardening the global `uncaughtException` handler in `network.js` to avoid crashing on exceptions that originate from per-unit/per-message validation of untrusted input, or ensure all such validation paths are fully exception-safe before that handler is ever reached.

### Proof of Concept
Not fully constructable without confirming the third-party base32/base64 decoder's behavior on malformed input (the specific byte-length-producing edge case is unverified). Conceptually: post/relay a unit containing an address-like field (e.g., `messages[].payload.outputs[].address`, `definition_chash`, or an AA trigger `address`) set to a 32-character string that passes `isValidBase64`-style outer-length checks but whose base32 decoding yields a byte sequence not equal to 20 bytes, then have any node call `isValidAddress()`/`isChashValid()` on it during standard unit validation, causing `separateIntoCleanDataAndChecksum` to throw uncaught and crash the process via `network.js`'s `uncaughtException` handler.
