### Title
Webhook signature check is keyed by `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, allowing cross-organization writes when any configured org has no `webhook_secret` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's secret to validate the HMAC signature against using the payload's `repository.owner.login` (falling back to `organization.login`), then verifies the signature against that org's `webhook_secret`. However, `GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that org, and every downstream event handler (`Handler#stacks`/`Handler#repository_name`) resolves the target `Repository`/`Stack` using an entirely different, unchecked payload field: `repository.full_name`. Because these two fields are never cross-validated, a payload whose `owner.login` names a configured-but-secretless organization can carry a `full_name` pointing at a stack that belongs to a completely different, secret-protected organization, letting an unauthenticated caller trigger writes (sync jobs, commit statuses, check-run refreshes, membership changes) against that other organization's stacks.

### Finding Description
The controller resolves the org used for signature verification purely from attacker-supplied JSON, before the signature is actually checked: [1](#0-0) [2](#0-1) 

`GithubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatic success, and `docs/setup.md`/`config/secrets.development.example.yml` explicitly document `webhook_secret` as optional per organization: [3](#0-2) 

Meanwhile, every handler resolves the *actual* repository/stack to mutate using a completely separate field, `repository.full_name`, with no comparison back to the `owner.login`/organization that was used to select the verification secret: [4](#0-3) 

Concretely, a `push` event resolves stacks by `full_name` and immediately enqueues a sync against arbitrary commits: [5](#0-4) 

and a `status` event writes a commit status onto any commit matching `sha`, without any organization/repo binding at all: [6](#0-5) 

The binding that should hold is:
`organization authenticated via HMAC(webhook_secret[owner.login]) == organization owning the repository/stack actually written by the handler`

Before the attacker's request, for a legitimate GitHub-originated webhook these two are always the same organization, because GitHub itself fills `repository.owner.login` and `repository.full_name` consistently. After the attacker's crafted POST, they diverge: `owner.login` is set to any org configured in Shipit that happens to have no `webhook_secret` (satisfying the "verification"), while `full_name` is set to `<other-org>/<other-repo>` — a stack tracked under a different, secret-protected organization. `verify_signature` never inspects `full_name`, and the handlers never inspect `owner.login`, so the equality silently breaks.

### Impact Explanation
This is a direct unauthorized-write / cross-repository-write primitive on an unauthenticated endpoint (`/webhooks` skips `verify_authenticity_token` and has no session/API-key requirement). An attacker who knows (a) that a Shipit instance is multi-org configured, and (b) that at least one configured organization was left without a `webhook_secret` (an explicitly "optional" setting per the docs), can forge `push`, `status`, `check_suite`, or `membership` events that reference stacks/commits/teams belonging to a completely unrelated organization that *does* have a secret configured — triggering syncs, fake commit statuses (which can gate/unblock deploys), or team/membership mutations without ever knowing that organization's real secret. This falls squarely under "cross-repository writes" / "unauthorized deploy" in the impact taxonomy.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: it requires a multi-org Shipit deployment (a documented, supported configuration in `config/secrets.development.shopify.yml`) where at least one configured org has `webhook_secret` unset — itself a documented "optional" field. Given that documentation explicitly calls the secret optional and gives multi-org examples, this misconfiguration is plausible in real deployments, but it is not guaranteed to exist on every installation; exploitability is conditional on this specific configuration gap rather than being universally present.

### Recommendation
- Make `webhook_secret` mandatory for every configured GitHub organization (reject signature verification, rather than pass it, when `webhook_secret` is blank), removing the "optional secret = auto-pass" behavior in `GithubApp#verify_webhook_signature`.
- Bind the verified organization to the acted-upon repository: after computing `repository_owner` for signature selection, require that `payload.dig('repository','full_name')` (or `organization.login`) actually belongs to that same organization/owner before dispatching to handlers, e.g. assert `repository_owner == full_name.split('/').first`.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `org-a` (no `webhook_secret` set) and `org-b` (a real `webhook_secret`, with a tracked stack `org-b/critical-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/critical-repo"
  }
}
```
No `X-Hub-Signature` header value needs to match anything real: `repository_owner` resolves to `org-a`, `Shipit.github(organization: 'org-a').verify_webhook_signature` returns `true` unconditionally per `lib/shipit/github_app.rb` lines 76-77 because `org-a` has no `webhook_secret`.
3. `WebhooksController#create` then dispatches to `PushHandler`, which resolves `stacks` via `payload.dig('repository','full_name')` = `"org-b/critical-repo"` and enqueues `GithubSyncJob` against `org-b`'s stack, even though the "authenticated" organization was `org-a`. [4](#0-3)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
