### Title
Single-step, unverified `address_definition_change` permanently locks address control - (File: `validation.js`, `composer.js`, `writer.js`)

### Summary
The external report describes an Ethereum `Ownable` contract that allows one-step transfer of ownership to an arbitrary, possibly uncontrolled, address, and recommends a two-step accept/confirm procedure to avoid permanent loss of control. Ocore has a structurally identical primitive: the `address_definition_change` message, which lets an address's current owner switch which "definition" (i.e., which set of keys/conditions) controls that address in the future. Like the reported bug, this is a single, unilateral step with no verification that the new controlling definition is actually known/reachable by anyone, and no acceptance step from the new definition holder.

### Finding Description
An address's spending authority in ocore is not fixed; it can be changed by posting an `address_definition_change` message whose payload is just `{definition_chash: <chash>}` [1](#0-0) . Composition of this message is trivial and takes an arbitrary `definition_chash` argument with no verification of possession: `composeDefinitionChangeJoint(from_address, definition_chash, signer, callbacks)` simply wraps the chash into a message [2](#0-1) .

Protocol-level validation of this message only checks the *format* of `definition_chash` (that it is shaped like a valid address/hash) — it never checks that the definition behind that hash is known, disclosed, or reachable by anyone: [1](#0-0) 

Once this unit becomes stable, the change is committed to `address_definition_changes` and becomes authoritative for the address going forward [3](#0-2) . From that point on, any future unit signed from that address must supply an `arrDefinition` whose hash matches this stored `definition_chash` exactly, or the unit is rejected: [4](#0-3) . If nobody actually holds a definition array that hashes to the chosen `definition_chash` (e.g., a malformed/mistyped/maliciously-suggested hash, or a hash for a definition template that was never actually generated with real keys), the address becomes permanently uncontrollable — exactly the "ownership transferred to an uncontrolled address" failure mode from the report, but applied to address/authority control in ocore rather than a Solidity `owner` variable.

This is structurally analogous to `Ownable.transferOwnership`: a single state-changing call, driven by whoever currently controls the authority, that reassigns future authority to a hash/address supplied by the caller, with no requirement that the new authority acknowledge or prove possession before the change takes effect.

### Impact Explanation
If an address's `address_definition_change` designates a `definition_chash` that is not actually backed by a real, held definition (through user/wallet-composer error, a buggy definition-template flow, or a socially-engineered payload crafted by an attacker who tricks a victim's wallet into signing this message), all current and future funds held at that address become permanently frozen: the address can no longer produce a valid `arrDefinition`/signature pairing accepted by validation, so it can never author a valid unit again (`validateAuthor`/`validateDefinition` in `validation.js`). This is a fund-freezing condition equivalent in class to the reported issue's "ownership lost."

### Likelihood Explanation
Triggering the message itself requires only that the address's current owner co-sign a normal `address_definition_change` unit — a standard, unprivileged operation available to any unit poster for their own address (or, for multi-authored/shared addresses, to any of the co-signers per `validateInlinePayload`'s multi-author branch) [5](#0-4) . No hub, peer, or node privilege is needed; the flaw is in the protocol's validation contract itself, not any node-trust assumption. The main friction is that a legitimate owner is unlikely to deliberately destroy their own address, but combined with wallets/AAs/templates that compute or accept an externally-supplied `definition_chash` (e.g., shared-address flows in `wallet_defined_by_addresses.js`, or an AA/oscript feeding a formula-derived chash), miscomputation or manipulation of that value leads directly to loss.

### Recommendation
Introduce a two-step confirmation for definition changes, analogous to `Ownable2Step`: require that, before a `definition_chash` can become authoritative, the corresponding `arrDefinition` be disclosed and hash-verified on-chain (e.g., require the change message to carry the full new definition inline, or require a subsequent "accept" unit signed with the new definition before the old definition's control is revoked). At minimum, wallet/composer-level tooling (`composeDefinitionChangeJoint`) should refuse to compose a definition change unless the caller can locally produce/verify the `arrDefinition` matching the target `definition_chash`.

### Proof of Concept
1. From address `A` (controlled by definition `D_old`), compose and post a unit containing an `address_definition_change` message with `payload.definition_chash = H`, where `H` is a base32 chash that does not correspond to any definition array actually held by any party (e.g., a corrupted/typo'd chash, or one derived from a `definition_template` whose real device keys were never generated) — this only requires calling `composeDefinitionChangeJoint(from_address, H, signer, callbacks)` [2](#0-1) .
2. `validateInlinePayload` accepts this because it only checks `isValidAddress(payload.definition_chash)`, not that `H`'s preimage is known [6](#0-5) .
3. Once stable, `address_definition_changes` records `H` as address `A`'s active definition chash [7](#0-6) .
4. Any subsequent unit signed from `A` must supply `arrDefinition` with `getChash160(arrDefinition) === H`; since no one holds such a definition, `validateDefinition`/`handleDuplicateAddressDefinition` will reject every future signing attempt from `A` [8](#0-7) , permanently freezing any funds at `A`.
