### Title
Cross-repo forged `success` status can flip a victim commit's `deployable?` and hijack `Stack#next_commit_to_deploy` selection under `maximum_commits_per_deploy` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` attaches an incoming GitHub `status` webhook payload to **any** `Commit` whose `sha` matches, with no check that the payload's `repository` field matches the commit's own stack/repository. Because GitHub webhook signatures in this engine are verified per-organization (not per-repository), any attacker who controls a repository within an org that Shipit has configured can emit a validly-signed `status` event referencing a victim stack's commit SHA and force a `success` `Status` row onto it, which can change `deployable?` and hijack `Stack#next_commit_to_deploy`/`next_expected_commit_to_deploy` selection under `maximum_commits_per_deploy`.

### Finding Description
The intended binding is: `Status.stack_id == Commit#stack_id` should only ever be populated from a webhook whose `payload['repository']['full_name'] == commit.stack.repository.full_name`. This binding is broken.

- `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This looks up commits **only by `sha`**, globally across every stack/repository tracked by the engine, and never calls the base class's repository-scoping helper `stacks` (built from `payload.dig('repository','full_name')`) that other handlers use: [2](#0-1) 

`commit.create_status_from_github!` then writes the status using the **commit's own** `stack_id`, with no repository cross-check: [3](#0-2) [4](#0-3) 

Signature verification in `WebhooksController#verify_signature` is scoped **per organization**, derived from `payload['repository']['owner']['login']`, not per repository: [5](#0-4) 
and `GitHubApp#verify_webhook_signature` uses a single `webhook_secret` configured per organization/app installation: [6](#0-5) 

Attacker flow: an attacker who owns/controls any repository inside an org that Shipit has an app installation for (satisfying the stated "emit webhooks from a repository they own" capability) can trigger a genuinely GitHub-signed `status` event from their own repo. Since a git commit SHA is a deterministic hash of fully public metadata (tree, parent, author/committer, message, timestamps), the attacker can reproduce the exact SHA of a victim commit in their own repository (or otherwise cause a `status` event carrying that `sha`), set `state: success` on it via their own repo's CI/API, and GitHub delivers a webhook correctly signed with the org's shared secret. `StatusHandler` accepts it and attaches a `success` `Status` to the victim's `Commit` regardless of which repository actually produced the CI result, because the handler never checks `payload['repository']['full_name']` against the commit's real stack/repository.

This directly breaks `Commit#deployable?`/`Stack#deployable?` dependencies. If the affected stack sets `maximum_commits_per_deploy` (via `deploy.max_commits`, default 8), the newly-"passing" commit can now fall inside the `commits_to_deploy.slice(0, maximum_commits_per_deploy)`/`.limit(maximum_commits_per_deploy)` window used by: [7](#0-6) [8](#0-7) 
causing `deployable_commits`/`.find(&:deployable?)` to select the forged-success commit ahead of legitimately still-pending commits queued behind it, and `Stack#trigger_continuous_delivery` will deploy it: [9](#0-8) 

None of the existing guards prevent this: `verify_signature` only proves the event came from a GitHub App installation on *some* repo of that org, not the specific repo owning the commit; `ExplicitParameters` schema on `StatusHandler` only validates types of `sha`/`state`/etc., not repository identity; there is no `Repository`/`stacks` scoping check anywhere in this handler.

### Impact Explanation
A payload genuinely originating from an attacker-controlled repository within a shared-secret organization can mutate a **different, victim** stack's `Commit`/`Status` state and cause an **unauthorized deploy** to be selected and triggered ahead of legitimately-vetted commits — this is a cross-tenant write ("a payload for one repository mutating another's stack, commit, task") and drives an unauthorized deploy decision, matching the Critical impact category. Blast radius covers every stack whose repository shares an organization/app installation with an attacker-accessible repository; repeatable per commit SHA the attacker wants to force through.

### Likelihood Explanation
Preconditions: the attacker must control (own or have push/webhook-emitting access to) at least one repository in an organization for which Shipit has a configured GitHub App/webhook secret, and the target stack must have `maximum_commits_per_deploy` configured (default 8, so commonly true) with more undeployed commits queued than would otherwise be selected. Reproducing an exact victim SHA in another repo requires only public commit metadata (no secrets), which is straightforward. This requires no Shipit session, API token, or GitHub App private key — only the stated "emit webhooks from a repository they own" capability — making the attack low-cost and repeatable against any commit SHA and any stack sharing the org.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository asserted in the payload, mirroring the `Handler#stacks` helper used elsewhere: only apply the status to commits whose `commit.stack` is included in `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`), rejecting/ignoring statuses whose payload repository does not match the commit's own stack repository.

### Proof of Concept
Minitest plan (extends `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Set up two stacks in different repositories: `@victim_stack` (with `maximum_commits_per_deploy` stubbed to e.g. 1) with commits `[c1 (older, no status), c2 (newer, no status)]`, and `@attacker_repo` (`evil/attacker-repo`) with no relation to the victim.
2. Assert baseline: `assert_not @victim_stack.next_commit_to_deploy` (no deployable commit) or that it currently resolves to none of `c2`.
3. Craft a `status` webhook payload: `{ "sha" => c2.sha, "state" => "success", "repository" => { "full_name" => "evil/attacker-repo", "owner" => { "login" => "same-org-as-victim" } } }`, stub `GithubHook`/signature verification to pass (as existing tests do with `GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
4. `post :create, body: payload.to_json, as: :json` with `X-Github-Event: status`.
5. Assert `c2.statuses.reload.last.state == 'success'` even though the payload's `repository.full_name` (`evil/attacker-repo`) never matches `c2.stack.repository.full_name`.
6. Assert `assert_equal c2, @victim_stack.next_commit_to_deploy` — proving the forged cross-repo status caused an unrelated repository's webhook to select `c2` for deploy, breaking the binding that commit selection must derive only from the deploying repository's own CI.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def next_commit_to_deploy
      commits_to_deploy = commits.order(id: :asc).newer_than(last_deployed_commit).reachable.preload(:statuses)
      if maximum_commits_per_deploy
        commits_with_max_applied = commits_to_deploy.limit(maximum_commits_per_deploy)
        deployable_commits(commits_with_max_applied) || deployable_commits(commits_to_deploy)
      else
        deployable_commits(commits_to_deploy)
      end
    end
