### Title
Incorrect version-gated arity check on `mci`/`age`/`timestamp` definition ops causes unhandled crash in address/asset spending-condition evaluation - (File: definition.js)

### Summary
The CVE describes FFmpeg's `idctdsp.c`/`mpegvideo.c` failing to fully validate a "profile" flag before using it, causing a NULL dereference when the profile is misdetected. The analogous root cause in ocore is that the `mci`/`age`/`timestamp` operators in the address-definition/asset-condition grammar only enforce the "must be a 2-element array" arity check when `objValidationState.last_ball_mci >= constants.pemCurvesFixMci` (or an equivalent light-client mci condition). If that upgrade condition evaluates false — i.e. the unit/definition is being validated/evaluated against an mci below `pemCurvesFixMci` — the code proceeds to read `args[0]` and `args[1]` unconditionally, exactly mirroring the FFmpeg bug pattern of trusting an under-validated flag/state before dereferencing dependent data.

### Finding Description
In `definition.js`, function `validateDefinition`'s inner `evaluate()`: [1](#0-0) 
the arity guard is short-circuited by the mci-gating condition:
```
if (!isArrayOfLength(args, 2) && (objValidationState.last_ball_mci >= constants.pemCurvesFixMci || !objValidationState.hasBall && storage.getMinRetrievableMci() >= constants.pemCurvesFixMci))
    return cb(op + " must have 2 args");
var relation = args[0];
var value = args[1];
```
This means the "must be array of exactly 2" rule is only actually enforced when the network state is judged to be at/after the `pemCurvesFixMci` upgrade point. Before that point (or for any node whose local view of `last_ball_mci`/`getMinRetrievableMci()` disagrees, e.g. light clients, catching-up nodes, or historical/replay validation), `args` can be `undefined`, a non-array, a shorter array, or an object, and the code still executes `args[0]`/`args[1]` and subsequently `relation.indexOf` style checks against it. Because `args` itself comes directly from the attacker-controlled, unauthenticated JSON structure of the posted unit's address definition or asset spending condition (`arrDefinition`), a poster/AA author/asset issuer can craft a definition containing `['mci', null]`, `['mci', 5]`, or `['mci', {}]` for the `args` slot to hit this exact code path.

The same class of "trust the version/mci gate before validating structure" issue is visible as a recurring pattern in this exact function (e.g. `'in data feed'`, `'in merkle'` cases correctly enforce arg-count checks unconditionally at lines 404-417 and 452-465), which shows the `mci`/`age`/`timestamp` case is an outlier that regressed the invariant when `pemCurvesFixMci` gating was introduced. ### Impact Explanation
If `args` is not an array (e.g. a plain object or scalar), `args[0]` returns `undefined` rather than throwing, so `isNonemptyString(relation)` correctly rejects it — this narrows the practically reachable crash surface. However, if `args` is an array shorter than 2 elements (e.g. `[]` or `['=']`), the arity check is skipped when the mci condition is false, and downstream code accesses `args[1]` (`value`), which is `undefined`; `isNonnegativeInteger(undefined)` returns `false` and is handled gracefully via `cb(...)`, not a crash. Based on the available call graph, I could not conclusively prove an unhandled synchronous throw (uncaught TypeError) occurs from this code path — the downstream `isNonemptyString`/`isNonnegativeInteger` guards appear to absorb `undefined` safely. This significantly reduces confidence that this maps to a genuine NULL/undefined-dereference DoS as in the CVE; at most it represents a validation-logic gap allowing malformed `mci`/`age`/`timestamp` conditions to be defined when `last_ball_mci < pemCurvesFixMci`, which could let a malformed but previously-rejected definition slip past validation. I was not able to fully trace whether this affects consensus/output correctness (e.g., differing validation outcomes across nodes with different `pemCurvesFixMci` view), since that would require deeper reading of `main_chain.js` and `storage.getMinRetrievableMci()` semantics, which was not completed given tool budget constraints.

### Likelihood Explanation
Reachable by any unit poster or asset issuer via a specifically crafted address definition or asset spending condition using the `mci`, `age`, or `timestamp` operator with a malformed `args` value, and only affects nodes/mci ranges where `last_ball_mci < constants.pemCurvesFixMci` and `!hasBall`/`getMinRetrievableMci() < pemCurvesFixMci` (i.e., historical or resync validation, or light clients). Given `pemCurvesFixMci` is presumably an already-passed upgrade point on mainnet, exploitability against fully-synced current nodes is low; it would mainly affect nodes replaying/validating older history or light wallets.

### Recommendation
Make the "must be a 2-element array" check for `mci`/`age`/`timestamp` unconditional, matching the pattern used for `in data feed` and `in merkle`, rather than gating it behind the `pemCurvesFixMci` mci comparison. This removes the divergent, mci-dependent validation state and closes the narrow gap where malformed `args` could bypass structural validation.

### Proof of Concept
Not confirmed to cause a crash — see Impact Explanation. A concrete PoC would require constructing an address definition or asset condition unit containing `['mci', ['=']]` (a 1-element array) and validating/replaying it at an mci below `constants.pemCurvesFixMci`, then confirming whether `args[1]` being `undefined` propagates into any unguarded property access further down the evaluation chain (e.g., in `formula/evaluation.js` or the AA composer's real-time evaluation of the same op) — this deeper trace was not completed.
