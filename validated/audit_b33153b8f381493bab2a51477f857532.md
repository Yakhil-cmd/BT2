### Title
Unscoped `ApiClient` created by `CCMenuUrlController#client` grants cross-stack read access - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#client` creates/reuses an `ApiClient` with `read:stack` permission but never sets its `stack:` association, leaving `stack_id` `nil`. Because `Shipit::Api::BaseController#stacks` treats a client with no `stack_id` as globally scoped (`Stack.all`), the resulting CCMenu token — generated by any user for any single stack they can view — authorizes reading every stack in the installation, not just the one requested.

### Finding Description
The intended binding is `current_api_client.stack_id == <the single stack the user requested a CCMenu URL for>`. In practice: [1](#0-0) 

`client` is built via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, keyed only on `creator` and the constant `name: 'CCMenu Client'`. No `stack:` attribute is passed, so `stack_id` is `nil`, and because `find_or_create_by!` matches on `creator`+`name` only, the *same* client record is reused across every stack that user ever requests a CCMenu URL for.

The generic API stack-scoping guard is: [2](#0-1) 

`stacks` explicitly treats an `ApiClient` with no `stack_id` as unrestricted (`Stack.all`) rather than "no access." This is presumably intended for admin-created, deliberately global tokens, but `CCMenuUrlController` never opts a token into per-stack scoping, so every CCMenu token it mints is accidentally global.

`ApiClient#check_permissions!` only checks the permission string, not stack scope: [3](#0-2) 

Attacker/exploit flow: an authenticated user with visibility of stack A only visits `GET /ccmenu/:stack_id` for stack A. This creates a `CCMenu Client` `ApiClient` with `stack_id = nil` and a `read:stack` permission, and returns a signed `authentication_token` for it. That token, presented as Basic Auth to `GET /api/stacks/:stack_id/cc.xml` (`Api::CCMenuController#show`, guarded only by `require_permission :read, :stack`), is accepted for **any** `stack_id`, because the client resolves to `Stack.all` via `stacks`/`BaseController#stack`. (Separately, `Api::CCMenuController#stack` also overrides the base `stack` method to call `Stack.from_param!` directly instead of `stacks.from_param!`, which independently bypasses scoping even for a correctly-scoped client — but that is a distinct bug in a different method. Even if that override were fixed to use `stacks.from_param!`, the nil `stack_id` produced here would still fall back to `Stack.all` and grant global read.)

None of the existing guards prevent this: `require_permission!` only checks the permission name, not stack identity; there is no validation forcing `ApiClient#stack` to be present when created through this controller; and `EnvironmentVariables#permit`/model validators are unrelated to this path.

### Impact Explanation
An authenticated user who is only supposed to see stack A can, via the normal "get CCMenu URL" UI feature, mint a durable Basic-Auth token that reads deploy/build status (`Api::CCMenuController#show`, rendering `shipit/ccmenu/project` XML with last deploy/rollback info) for every stack in the Shipit instance, including stacks that belong to repositories they have no authorization to view. This is an unauthorized cross-tenant read of stack/task state, matching the "High - unauthenticated/unauthorized read of stack state, task streams or deploy output" category (the read is unauthorized relative to the requesting user's actual, intended scope, even though it is not fully unauthenticated). It is repeatable indefinitely: the token is durable (`ApiClient.authenticate` verifies a signed id, no expiry) and reusable against any `stack_id` in the system.

### Likelihood Explanation
Preconditions are low: the attacker only needs an ordinary Shipit login session and visibility of one stack's settings page — a legitimate, low-privilege capability, not an admin or maintainer role. No GitHub secrets, webhook signatures, or Shipit operator access are required. The feature (`/ccmenu/:stack_id`) is a normal, documented convenience endpoint, so the attack cost is a single authenticated HTTP GET.

### Recommendation
Scope the generated `ApiClient` to the requested stack, and make the lookup key stack-specific so a single client/token cannot be reused across stacks: e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`. Additionally, review `Shipit::Api::BaseController#stacks` so a nil `stack_id` is not silently treated as "all stacks" for tokens that are supposed to be stack-scoped, and fix `Api::CCMenuController#stack` to use the inherited `stacks.from_param!` scoping rather than `Stack.from_param!` directly.

### Proof of Concept
```ruby
test "ccmenu url controller creates a globally-scoped api client" do
  user = shipit_users(:walrus)
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack the user has no business reading

  session[:user_id] = user.id
  get "/ccmenu/#{stack_a.to_param}"
  assert_response :success

  client = ApiClient.find_by(creator: user, name: 'CCMenu Client')
  assert_nil client.stack_id # binding broken: should equal stack_a.id

  token = client.authentication_token
  # reuse token against an unrelated stack via the API endpoint
  get "/api/stacks/#{stack_b.to_param}/cc.xml", headers: { 'Authorization' => ActionController::HttpAuthentication::Basic.encode_credentials(token, '') }
  assert_response :success # should have been :forbidden / :not_found
end
```
