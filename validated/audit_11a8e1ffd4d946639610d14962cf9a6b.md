## Title
Scoped API tokens can read the CI/build status of any stack via `CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The bug class described in the report is a broken binding: a value that governance/authorization *sets or grants* is not the same value that is actually *consulted at execution time*, letting an unprivileged party act outside the granted scope. In shipit-engine, `ApiClient` tokens can be scoped to a single stack via `stack_id`, and `Api::BaseController` is supposed to enforce `stack ∈ {api_client.stack_id}` for every request. `Api::CCMenuController` breaks that binding by resolving the requested stack directly against the whole `Stack` table instead of the client's authorized scope.

### Finding Description
`Api::BaseController` defines the scoping binding that all API endpoints are expected to honor: [1](#0-0) 

`current_api_client.stack_id?` returns true when the `ApiClient` record was created with a specific `stack` (e.g. fixture `here_come_the_walrus`, scoped to the `shipit` stack): [2](#0-1) 

`Api::CCMenuController`, however, overrides `authenticate_api_client` (to also allow a `?token=` query param) and overrides `stack` to bypass the scoped lookup entirely, resolving directly against `Stack.from_param!`: [3](#0-2) 

The only authorization check performed is `require_permission :read, :stack`, which only validates that the token carries the `read:stack` *permission string* — it never checks that the requested `stack_id` matches `current_api_client.stack_id`: [4](#0-3) [5](#0-4) 

So the binding `stack the token authorizes == stack it touches` (enforced everywhere else via `BaseController#stacks`/`#stack`) is broken specifically in this controller: a token scoped to stack A can request `stack_id=B` and get a fully rendered CCMenu project XML (build status, last build label/time, activity, web URL) for stack B.

### Impact Explanation
This is an unauthenticated-scope read of stack state: an attacker holding only a narrowly-scoped API token (issued for one repository/stack) can read build/deploy status information for any other stack in the Shipit instance, including stacks it was never granted access to. This matches the "unauthenticated read of stack state" High-impact category, since the token's authorization boundary (the specific stack it was minted for) is not enforced by this endpoint.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (the common configuration used for CI status badges, per `CCMenuUrlController#client`, which creates tokens scoped to a single stack with `read:stack` permission) can trivially exploit this by substituting a different `stack_id` in the request — no race condition, front-running, or privileged access is required beyond possessing one legitimately-scoped read-only token. [6](#0-5) 

### Recommendation
Remove the `stack` override in `Api::CCMenuController` (or reimplement it using the same `stacks` scoping helper from `Api::BaseController`) so that stack-scoped tokens can only resolve stacks within `current_api_client`'s authorized scope, consistent with every other API controller.

### Proof of Concept
1. Create/have an `ApiClient` scoped to `stack_id: shipit` with `permissions: [read:stack]` (e.g. fixture `here_come_the_walrus`).
2. Authenticate as that client and call `GET /api/stacks/:other_stack_id/ccmenu.xml` where `:other_stack_id` refers to a different, unrelated stack.
3. Observe the request succeeds with `200 OK` and returns the other stack's build status/activity/last build info, even though the token is only supposed to be authorized for the `shipit` stack — confirmed by the existing test `test/controllers/api/ccmenu_controller_test.rb` which never exercises cross-stack scoping (it only checks permission-string authorization, not stack-scope authorization) and by contrast with `test/controllers/api/stacks_controller_test.rb`'s explicit `"an api client scoped to a stack will only see that one stack"` test, which has no equivalent in the CCMenu controller test suite.
