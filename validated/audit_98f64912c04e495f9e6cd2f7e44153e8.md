### Title
Reuse of the same L1 BTC lockup proof across multiple bonds allows unbacked sBTC-collateral crediting - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path accepts a Bitcoin Merkle/header proof that a UTXO *was* locked in a `pox-5` timelock script, but it never records that outpoint as consumed once the proof is accepted. The only duplicate-outpoint check (`ERR_DUPLICATE_LOCKUP_OUTPOINT`) is scoped to the single `fold` over the outputs supplied in *one* call, via a transient `seen-outpoints` accumulator that is discarded when the transaction ends. There is no persistent map of previously-used L1 outpoints/txids checked on subsequent calls.

### Finding Description
`register-for-bond` (`pox-5.clar` ~lines 642-841) computes `sats-total` for the L1 path via `verify-l1-lockups` → `validate-l1-lockup` (lines 1981-2113). `validate-l1-lockup` checks:
- `unlock-burn-height >= minimum-unlock-height` [1](#0-0) 
- the output script matches `construct-lockup-output-script(staker, unlock-burn-height, ...)` and the amount matches [2](#0-1) 
- the outpoint is not already in `seen-outpoints`, a list built *only* inside this call's fold [3](#0-2) 
- the block header and Merkle proof are valid [4](#0-3) 

None of these checks establish that the BTC output is *still* locked/unspent at the time of the call, nor is the outpoint recorded in any contract-level map (e.g. `protocol-bond-memberships`, `protocol-bond-allowances`, or a dedicated "used-l1-outpoints" map) that would prevent the same proof from being replayed in a *future* `register-for-bond` call.

The only guard against reuse by the same staker is `bond-overlaps-new-position?`, which only blocks a *currently active, overlapping* bond membership: [5](#0-4) . Once a bond term ends (matures) and the staker's membership is no longer "overlapping" (e.g. after `update-bond-registration` rolls the staker out, or once the term naturally lapses), that guard no longer applies. Because the exact same 80-byte header + tx bytes + outpoint that were valid for the first `register-for-bond` remain valid Bitcoin-chain history forever, the identical `btc-lockup` argument can be resubmitted in a later `register-for-bond` call once the staker is otherwise eligible to register again — crediting `sats-total` a second time and setting `is-l1-lock: true` on a brand-new `protocol-bond-memberships` entry: [6](#0-5) . Meanwhile, once `unlock-burn-height` matures on the original L1 timelock, the staker is free to spend that BTC on L1 (that's the entire point of the timelock), so the second registration is backed by zero actually-locked BTC even though the contract treats it as fully collateralized.

### Impact Explanation
This double-counts an L1 BTC commitment: the sats credited to the second bond membership were never (re-)locked on Bitcoin — they are backed by a stale, already-matured/spendable proof. This inflates the staker's/bond's recorded `sats-total` (used for `min-ustx-for-sats-amount`, allowlist accounting `protocol-bond-allowances`, and `protocol-bonds-total-staked`), letting a staker obtain bond membership and signer weight backed by phantom sBTC collateral. This matches the "Critical" bucket: sats credited by an L1 proof that were never locked on Bitcoin / double-counting a commitment.

### Likelihood Explanation
Likelihood requires an attacker to: (1) perform one real L1 BTC timelock and successfully complete one bond term with it, (2) let the L1 timelock mature so the BTC is spendable/spent, and (3) later become eligible for a fresh `register-for-bond` (after their prior membership no longer "overlaps," e.g. through natural expiration or a rollover pattern) and resubmit the *same* header/tx/outpoint. All the inputs needed (header bytes, tx bytes, outpoint) are public, permanently valid Bitcoin data — no privileged access, miner cooperation, or admin action is required, only patience for the bond terms to cycle.

### Recommendation
Persist consumed L1 outpoints in a durable map (e.g. `used-l1-lockup-outpoints { txid, output-index } -> bool`) that is checked and set inside `validate-l1-lockup`/`verify-l1-lockups`, independent of any particular call's `seen-outpoints` accumulator, so that a given Bitcoin lockup output can only ever back one `register-for-bond` credit for the lifetime of the contract (not just within a single transaction's list).

### Proof of Concept
1. Staker locks `S` sats on L1 in the `pox-5` timelock script for `unlock-burn-height = H1`, matching an allowlisted bond `B0`.
2. Staker calls `register-for-bond(bond-index=B0, ..., btc-lockup=Ok({outputs:[lockup], ...}))`. `verify-l1-lockups` validates the proof and credits `sats-total = S`; membership is created with `is-l1-lock: true`.
3. Bond `B0` matures; the staker's L1 timelock also matures at `H1`; staker's `protocol-bond-memberships` entry no longer overlaps a new bond (either removed via natural progression or via `update-bond-registration`).
4. Staker optionally spends the now-unlocked BTC on L1 (irrelevant to the contract, which never re-checks UTXO liveness).
5. Staker becomes eligible for a new bond `B1` (allowlisted again, or the allowlist check is satisfied) and calls `register-for-bond(bond-index=B1, ..., btc-lockup=Ok({outputs:[<the very same lockup tuple from step1>], ...}))`.
6. `validate-l1-lockup` re-verifies the same header/tx/outpoint successfully (nothing in contract state rejects it), `sats-total = S` is credited again, and a second `protocol-bond-memberships` entry with `is-l1-lock: true` and `amount-sats: S` is created — with zero additional BTC actually locked.
