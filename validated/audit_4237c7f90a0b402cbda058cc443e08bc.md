### Title
`json_stringify()` in oscript formulas lacks a size/depth bound before recursive serialization, risking stack overflow / excessive CPU on AA evaluation - (File: formula/evaluation.js)

### Summary
`paddle.linalg.lu_unpack` was fixed because it recursively processed attacker-controlled dimensions without validating size/depth first, causing a stack overflow. The ocore `AA` formula engine has the analogous class of bug in the `json_stringify` opcode: unlike the sibling `sha256` and `chash160` opcodes, it calls the recursive serializer `string_utils.getJsonSourceString()` on an attacker-influenced object **without first checking `isTooBigObj()` / depth limits**.

### Finding Description
In `formula/evaluation.js`, the `sha256` and `chash160` cases both guard against oversized/deep objects before recursively serializing a `wrappedObject`: [1](#0-0) [2](#0-1) 

Both call `isTooBigObj(res.obj)` and bail out with a fatal error before calling `getJsonSourceString`/`getChash160`.

The `json_stringify` case, however, unwraps the `wrappedObject` and passes it directly into `string_utils.getJsonSourceString()` with **no** `isTooBigObj`/depth check beforehand: [3](#0-2) 

`getJsonSourceString` is a plain, unbounded recursive function that walks the object/array graph with no maximum-depth guard of its own: [4](#0-3) 

An AA-controlled `wrappedObject` can be grown to be deeply nested at *runtime* (not just as a static formula AST) via the `reduce` opcode, which builds a new accumulator value on every iteration by wrapping the prior one. The `reduce` implementation does check `isTooBigObj` on the accumulator after each step: [5](#0-4) 
but that check bounds total node count/length to `isTooBigObj`'s defaults (`depthLimit=100` from `string_utils.js`), so in principle deep nesting is limited there too — the actual gap is that any code path that produces a `wrappedObject` result and feeds it straight into `json_stringify` (bypassing the `sha256`/`chash160` protective check that exists in those sibling opcodes) is inconsistent, and if an attacker finds a code path returning a `wrappedObject` from `json_parse`-derived data, function-return values, or getter/remote-call results that has not passed through the `isTooBigObj` gate at the point `json_stringify` is invoked, the recursive stringifier runs unguarded.

This is structurally the same defect class as the PaddlePaddle advisory: a function performs unbounded recursive processing of a size/shape-controlled input without validating bounds first, unlike a "sibling" function in the same module that does perform the check.

### Impact Explanation
If a sufficiently deep/large object reaches `json_stringify` without going through the `isTooBigObj` gate, the recursive `stringify()` call can exhaust the V8 call stack. In Node.js this usually surfaces as a catchable `RangeError: Maximum call stack size exceeded`, which is caught by the surrounding `try { ... } catch (e) { return setFatalError(...) } ` in the `json_stringify` handler — bounding worst-case behavior to an AA bounce rather than a full node crash in most cases. Still, this represents a real defensive gap: it is inconsistent with the explicit protection added for `sha256`/`chash160`, and depending on Node/V8 version, stack size configuration and the surrounding call context (deep already from `evaluate`'s own recursive chain, `callFunction`, `async.eachOfSeries` chains, etc.), a stack overflow triggered inside nested callback machinery could occur in a context where the catch is not safely reachable, causing process-level instability. Because `evaluate()` is used both to process AA triggers (validating/executing AA definitions posted by any unprivileged unit poster) and asset/definition-formula evaluation, the attack surface is reachable from ordinary unprivileged trigger/AA-authoring flows.

### Likelihood Explanation
Medium. Reaching this bug requires constructing an oscript formula whose `json_stringify` argument evaluates to an object that is deep enough to overflow the stack yet has *not* already been blocked by `isTooBigObj` at an earlier step (e.g., depending on exactly which code path produced the `wrappedObject`, whether it is a fresh `json_parse` result checked in-line, or a value threaded through `local_var`/`func_call`/`remote_func_call` returns that were never explicitly checked before being passed to `json_stringify`). This requires no special privilege — only a normal AA trigger sender or AA author — but does require formula-crafting skill to bypass the `isTooBigObj` checks already present on the more obvious paths (`reduce`, `json_parse`).

### Recommendation
Add the same `isTooBigObj(res)` guard used in the `sha256` and `chash160` cases to the `json_stringify` case in `formula/evaluation.js`, immediately after unwrapping the `wrappedObject` and before calling `string_utils.getJsonSourceString()`. Additionally, harden `getJsonSourceString` (and `getSourceString`) themselves with an explicit recursion-depth counter that throws a catchable, well-defined error once a maximum depth is exceeded, rather than relying solely on callers to pre-check with `isTooBigObj`, so the recursion is bounded defense-in-depth regardless of which opcode calls it.

### Proof of Concept
Conceptual oscript AA formula (exact syntax/limits would need to be validated in a live Devin session against the `nearley` grammar and current `MAX_COMPLEXITY`/`MAX_OPS` limits):
```
$obj = {a: 1};
$obj = reduce(trigger.data.arr, 100, ($acc, $x) => {return {a: $acc}}, $obj);
json_stringify($obj)
```
Because `reduce`'s per-step `isTooBigObj` check only fires after each step and uses default depth/node thresholds, and because `json_stringify` performs no equivalent check of its own, a value that is at or just under the `isTooBigObj` threshold but still deep enough to be expensive/borderline for the JS call stack can be passed to `json_stringify`, exercising the recursive `stringify()` path without the protection that `sha256`/`chash160` enjoy.

Note: I was not able to fully verify within the available search iterations whether every runtime path that produces a `wrappedObject` (e.g., certain `func_call`/`remote_func_call` return values) is guaranteed to have already passed an `isTooBigObj` check before reaching `json_stringify`; confirming an end-to-end exploitable formula that bypasses all upstream size checks would require running the formula engine directly (e.g., via a Devin session with the test harness in `test/formula.test.js`) rather than static code search alone.

```javascript
function getJsonSourceString(obj, bAllowEmpty) {
	let cache = new WeakMap();  // object to stringified result
	function stringify(variable){
		if (variable === null)
			throw Error("null value in "+JSON.stringify(obj));
		switch (typeof variable){
			case "string":
				return toWellFormedJsonStringify(variable);
			case "number":
				if (!isFinite(variable))
					throw Error("invalid number: " + variable);
			case "boolean":
				return variable.toString();
			case "object":
				// return cached result if already processed
				if (cache.has(variable))
					return cache.get(variable);
				let result;
				if (Array.isArray(variable)){
					if (variable.length === 0 && !bAllowEmpty)
						throw Error("empty array in "+JSON.stringify(obj));
					result = '[' + variable.map(stringify).join(',') + ']';
				}
				else{
					var keys = Object.keys(variable).sort();
					if (keys.length === 0 && !bAllowEmpty)
						throw Error("empty object in "+JSON.stringify(obj));
					result = '{' + keys.map(function(key){ return toWellFormedJsonStringify(key)+':'+stringify(variable[key]) }).join(',') + '}';
				}
				cache.set(variable, result);  // memoize for future references
				return result;
			default:
				throw Error("getJsonSourceString: unknown type="+(typeof variable)+" of "+variable+", object: "+JSON.stringify(obj));
		}
	}

	return stringify(obj);
}
```
