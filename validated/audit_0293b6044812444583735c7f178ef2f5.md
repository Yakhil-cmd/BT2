### Title
Silent zero-output filtering in AA payment messages lets depositors lose funds to rounded-to-zero share issuance - (File: aa_composer.js)

### Summary
Obyte Autonomous Agents (AAs) commonly issue proportional shares/tokens to depositors using formulas such as `round(amount * ratio)` (bonding-curve, ICO, and market-maker style AAs). The core AA execution engine in `aa_composer.js` silently strips any payment output whose computed `amount` evaluates to `0`, and removes the entire payment message if it ends up with no outputs, rather than treating a zero-valued payout as an error condition. This mirrors the reported RioLRTCoordinator bug class: a depositor's funds are accepted, but the mint/issuance branch that should compensate them can silently produce nothing, with no revert.

### Finding Description
In `handleTrigger`'s `sendUnit` function, after all payment outputs for a message are computed from the oscript formulas, the engine performs: [1](#0-0) 

```
// negative or fractional
if (!payload.outputs.every(function (output) { return (isNonnegativeInteger(output.amount) || output.amount === undefined); }))
    return bounce("negative or fractional amounts");
// filter out 0-outputs
payload.outputs = payload.outputs.filter(function (output) { return (output.amount > 0 || output.amount === undefined); });
```
and later:
```
messages = messages.filter(function (message) { return (message.app !== 'payment' || message.payload.outputs.length > 0); });
if (messages.length === 0) {
    error_message = 'no messages after removing 0-outputs';
    ...
    return handleSuccessfulEmptyResponseUnit(null);
}
```
This behavior is exercised explicitly by the test `only 0 output` in `test/aa.test.js`, which confirms that when the only output rounds/evaluates to `0`, the AA silently swallows the trigger's funds and produces "no messages after removing 0-outputs, then no state changes": [2](#0-1) 

The oscript formula language provides `round()`, `floor()`, `ceil()` (see `formula/evaluation.js`) which are the standard building blocks used by real AA templates to compute proportional issuance, e.g. token-sale price conversion: [3](#0-2) 
and Uniswap-style share issuance from a ratio of balances: [4](#0-3) 

In both patterns, an unprivileged trigger sender who deposits a small enough amount (relative to price or ratio) causes `round(...)`/division-based amount calculations to evaluate to `0`. When that computed value is used as a payment output amount, the AA engine (`aa_composer.js:1278/1281`) drops that output and the containing payment message entirely instead of bouncing the trigger. The trigger's originally-sent coins remain part of the AA's on-chain balance (they were already paid into the AA address as a normal unit output, independent of the AA's own response), but the depositor receives no compensating asset/share output back for that trigger.

### Impact Explanation
Any unprivileged AA trigger sender interacting with a proportional-issuance AA (ICO/token-sale, bonding curve, share/vault AAs — patterns explicitly demonstrated by the codebase's own AA templates) can lose their deposited bytes/asset with zero compensation if their contribution is small enough to round to zero shares. This is a genuine, silent fund loss for the depositor and a corresponding value transfer to the AA/other participants, matching the "Depositors may receive zero restaking tokens due to small deposit" bug class. It requires no privileged access — any address can send a small-value trigger unit to a public AA.

### Likelihood Explanation
Because the oscript engine offers no built-in guard against zero-valued computed outputs (it treats it as "nothing to send" rather than an error), and because `round()`/division-based proportional-issuance patterns are the standard idiom taught/used for AA share issuance in this codebase's own test samples, the precondition (a deposit small enough relative to price/ratio to round to zero) is easily reachable by any user, especially as an AA's outstanding-share value grows over time (making per-unit share value larger and the rounding threshold larger too).

### Recommendation
At the `aa_composer.js` level, when a payment message ends up with all zero-value outputs specifically because a computed value rounded to zero (as opposed to a conditional `if:` output correctly evaluating to false), the engine should bounce the trigger by default (return the deposit, minus bounce fee) rather than silently accept it into the AA balance with no response, unless the AA definition explicitly opts into silently accepting the funds. At minimum, AA-authoring documentation and any reference/example AA templates included in the repo (`ico_with_milestones.oscript`, `uniswap_like_market_maker.oscript`, `fundraising_proxy.oscript`) should be updated to explicitly `bounce()` when a computed issuance/refund amount is `0`, so that copy-pasted AA templates don't propagate this fund-loss pattern to real deployments.

### Proof of Concept
1. Deploy (or reuse) an AA using the market-maker/ICO pattern where issued amount is computed as `round($ratio * trigger.output[[asset=base]])` or `round(trigger.output[[asset=base]] / $price)`, e.g. as in: [5](#0-4) 
2. As an unprivileged sender, submit a trigger unit whose `base` (or asset) output is large enough to satisfy the `if:` condition threshold but small enough that `round(amount / $price)` (or the balance ratio formula) evaluates to `0`.
3. The AA engine filters the zero-amount output and the containing payment message per `aa_composer.js:1277-1281`, then calls `handleSuccessfulEmptyResponseUnit`, producing no response output to the sender while the sender's originally paid coins remain in the AA's balance (test `only 0 output` in `test/aa.test.js:1024-1075` demonstrates this exact "removing 0-outputs" code path).
4. Result: the depositor's funds are consumed by the AA with zero shares/tokens issued in return, and no state variable tracking their contribution is recorded.
