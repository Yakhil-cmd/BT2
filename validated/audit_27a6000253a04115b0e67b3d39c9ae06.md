**Analysis:**

`get_ledger_commit_progress` (reads the `LedgerCommitProgress` key) and `get_synced_version` (reads `OverallCommitProgress`) are both implemented in `LedgerMetadataDb` [1](#0-0) . `LedgerCommitProgress` is written earlier in the commit pipeline (in `commit_state_kv_and_ledger_metadata`) while `OverallCommitProgress` is written last, after all shard/sub-DB commits succeed, in `pre_commit`/`commit_ledger` batches [2](#0-1) [3](#0-2) . The `StateStore::sync_commit_progress` comment makes the design intent explicit: "We commit the overall commit progress at the last, and use it as the source of truth of the commit progress" [4](#0-3) .

Crucially, `get_ledger_commit_progress` is used **only** in two contexts: crash-recovery truncation logic on node restart (`sync_commit_progress`, which asserts `ledger_commit_progress >= overall_commit_progress` and truncates back down to `OverallCommitProgress`) [5](#0-4) , and offline debug/admin tooling (`print_db_versions`, `truncate` CLI) [6](#0-5) [7](#0-6) . It is never consumed by the mempool, vm-validator, or API read paths.

The state view actually served to vm-validator/mempool/API for sequence-number checks comes from `latest_state_checkpoint_view()`, which is backed by the in-memory `current_state` (`BufferedState`) that is only advanced after a full successful commit gated by `OverallCommitProgress` — not `LedgerCommitProgress` [8](#0-7) [9](#0-8) . There is no code path where an unprivileged transaction, API request, or authenticator input can cause the vm-validator's state view or sequence-number lookup to consult `LedgerCommitProgress` instead of `OverallCommitProgress`/`get_synced_version`. The divergence between the two keys is purely an internal, transient, single-node crash-recovery bookkeeping detail with no externally reachable admission logic depending on it.
