### Title
Webhook signature verification is keyed on `repository.owner.login` while event handlers act on `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The dust-order bug class describes an incoming payload field that drives execution (`matchData.baseDelta`) while a related invariant (minimum order size) is silently violated because the check binds to the wrong quantity. The Shipit analog is a signature/authorization check that binds to one field of the webhook payload (`repository.owner.login`) while the code that actually mutates state uses a *different* field of the same payload (`repository.full_name`) that is not independently re-validated against the verified owner.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to validate the HMAC against using `repository_owner`, computed as: [1](#0-0) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This is used only to pick the correct `Shipit.github(organization: repository_owner)` app config and confirm the HMAC: [2](#0-1) 

Signature validation itself is: [3](#0-2) 

```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
```

Critically, `return true unless webhook_secret` means that for **any organization configured in Shipit without a `webhook_secret`** (which the setup docs explicitly describe as optional), signature verification is a no-op and any payload claiming that org as `repository.owner.login` is accepted unconditionally.

Meanwhile, every event handler resolves the target repository/stack **not** from `repository.owner.login`, but from `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for whatever stacks match that `full_name`: [5](#0-4) 

This breaks the binding: `repository.owner.login` (verified) ≠ `repository.full_name` (acted upon). The signature check never confirms that the org whose secret validated the request is actually the owner of the repository being mutated by the handler.

### Impact Explanation
On a multi-organization Shipit deployment (the engine explicitly supports this, see `config/secrets.development.shopify.yml` listing multiple orgs each with independent `webhook_secret`), if any one configured organization has no `webhook_secret` set, an unauthenticated party can POST directly to `/webhooks` with:
- `repository.owner.login` = the org with no secret (verification short-circuits to `true`)
- `repository.full_name` = a real, tracked repository belonging to a *different*, properly-secured organization

`Handler#stacks`/`PushHandler` will resolve and act on the real, secured repository's `Stack`, triggering `stack.sync_github` (and analogous unauthenticated triggering of `status`, `check_suite`, `membership`, `pull_request` handlers) for a repository the attacker has no relationship to or credentials for. This is a cross-repository state mutation triggered without any valid credential for the targeted repository, matching the "cross-repository writes" / "unauthorized deploy trigger" impact category, since `sync_github` drives ref/commit ingestion that downstream feeds deploy eligibility.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: the vulnerability requires the Shipit instance to host at least one organization without a configured `webhook_secret`, which the documentation explicitly allows ("Webhook secret (optional)"). This is a realistic, sanctioned configuration state, not a misuse of the engine — the engine's own code permits it and the docs advertise it as optional, so any multi-org install with even one org that skipped the secret is exposed.

### Recommendation
- Do not allow `verify_webhook_signature` to unconditionally return `true` when `webhook_secret` is blank; instead require a secret to be configured for every organization, or explicitly disable/ignore any organization lacking one.
- Cross-check that `repository.owner.login` (the field used to select the verifying app) matches the owner segment of `repository.full_name` (the field used to resolve the acted-upon `Stack`) before processing, so the two payload fields are cryptographically and logically bound to the same organization.

### Proof of Concept
1. Configure Shipit with two orgs: `secure-org` (has `webhook_secret` set, owns tracked repo `secure-org/secure-repo`) and `open-org` (no `webhook_secret` configured, per docs' optional setting).
2. Attacker (no credentials for `secure-org`) POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "secure-org/secure-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>"
}
```
3. `verify_signature` resolves `repository_owner` = `"open-org"`, fetches `Shipit.github(organization: "open-org")`, and `verify_webhook_signature` returns `true` immediately because `open-org` has no `webhook_secret` — no HMAC is checked at all. [6](#0-5) 
4. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `repository_name` from `full_name` = `"secure-org/secure-repo"`, finds the real `Stack`, and calls `sync_github(expected_head_sha: params.after)` — a mutation on `secure-org`'s stack triggered without ever validating against `secure-org`'s secret. [5](#0-4)
