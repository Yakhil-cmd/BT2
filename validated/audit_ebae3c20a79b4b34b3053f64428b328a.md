### Title
Unvalidated Peer-Supplied `StakingInfo` During Fast/Snap Sync Allows Reward Redirection and Validator-Set Manipulation — (`datasync/downloader/queue.go`)

---

### Summary

During FastSync and SnapSync, Kaia downloads `StakingInfo` objects from remote peers and persists them directly to the database without any cryptographic verification against the committed block state. The `validate` callback in `DeliverStakingInfos` is an explicit no-op (marked `TODO-Kaia-Snapsync update validation logic`). A malicious peer can supply fabricated `StakingInfo` containing attacker-controlled `RewardAddrs`, inflated `StakingAmounts`, and redirected treasury fund addresses (`KEFAddr`, `KIFAddr`, `KPFAddr`). Once persisted, this fake data is consumed by the reward and validator-set modules for all subsequent block processing, causing KAIA block rewards to be distributed to attacker-controlled addresses and validator selection to be manipulated.

---

### Finding Description

**Root cause — missing content validation in `DeliverStakingInfos`:**

In `datasync/downloader/queue.go`, `DeliverReceipts` validates each receipt batch against the cryptographic commitment in the block header (`header.ReceiptHash`): [1](#0-0) 

`DeliverStakingInfos`, by contrast, has a `validate` function that unconditionally returns `nil`: [2](#0-1) 

The comment `// TODO-Kaia-Snapsync update validation logic` confirms this is a known placeholder, not intentional design.

**Persistence path — fake data written to DB:**

In `commitFastSyncData` and `commitPivotBlock`, the unvalidated `result.StakingInfo` is written directly to the staking database: [3](#0-2) [4](#0-3) 

**Second path — `SyncStakingInfo` recovery:**

The `SyncStakingInfo` recovery function (triggered via admin API) only checks that the returned `BlockNum` matches the expected value, then writes the content directly to the database without any state-root or hash verification: [5](#0-4) 

**Downstream consumption — reward distribution:**

The persisted `StakingInfo` is read by `kaiax/reward` to determine `RewardAddrs` (where block rewards are sent) and `StakingAmounts` (which determine each validator's proportional reward share): [6](#0-5) 

The `RewardAddrs` from `StakingInfo` are used directly as the destination for `state.AddBalance` calls: [7](#0-6) 

**Downstream consumption — validator selection:**

`StakingAmounts` from the persisted `StakingInfo` are also used by `kaiax/valset` to determine which validators are qualified (meet `MinimumStake`) and their relative weight in the WeightedRandom proposer policy: [8](#0-7) 

**P2P delivery path:**

The `StakingInfoMsg` handler in `node/cn/handler.go` decodes the peer message and forwards it directly to the downloader without any pre-validation: [9](#0-8) 

---

### Impact Explanation

A malicious peer connected to a syncing node can supply a `[]*staking.P2PStakingInfo` response where:

1. **`RewardAddrs`** are replaced with attacker-controlled addresses → all KAIA block rewards for the affected staking intervals are credited to the attacker instead of legitimate validators.
2. **`StakingAmounts`** are inflated for attacker-controlled nodes → those nodes receive disproportionate staking rewards and are selected as proposers more frequently.
3. **`KEFAddr` / `KIFAddr` / `KPFAddr`** are replaced with attacker addresses → treasury fund distributions (KEF, KIF, KPF portions of every block reward) are redirected to the attacker.

The corrupted data is persisted to the database and used for every block processed after the sync completes. The victim node has no indication that its staking database has been poisoned.

**Allowed impact gate satisfied:** Unauthorized reward distribution affecting KAIA and system-managed funds (treasury addresses).

---

### Likelihood Explanation

- **Trigger**: Any node performing FastSync, SnapSync, or invoking the `SyncStakingInfo` admin recovery path is vulnerable. New nodes joining the network typically use fast/snap sync.
- **Attacker requirement**: The attacker only needs to be a connected P2P peer — no special privileges, no majority-validator collusion, no compromised keys.
- **Detectability**: The attack is silent. The syncing node logs `"Imported new staking information"` and proceeds normally. The corrupted reward addresses only become visible when block rewards are distributed to wrong addresses.
- **Scope**: Affects all pre-Kaia-hardfork staking intervals (the `StakingInfo` is interval-based before the Kaia fork). Post-Kaia-fork staking info is derived per-block from state, but the recovery path (`SyncStakingInfo`) explicitly checks `IsKaiaForkEnabled` and only operates on pre-fork blocks, which are exactly the ones using the interval-based DB-persisted staking info.

---

### Recommendation

1. **Validate `StakingInfo` content against block state**: After receiving a `P2PStakingInfo` from a peer, re-derive the expected `StakingInfo` from the local block state (using `getFromState`) for the corresponding block number and compare it against the peer-supplied data. Reject and penalize peers that supply mismatching data.

2. **Commit a hash of `StakingInfo` into block headers or a side-chain commitment**: This would allow cryptographic verification analogous to `header.ReceiptHash` for receipts.

3. **Remove the no-op `validate` placeholder**: Replace the `// TODO-Kaia-Snapsync update validation logic` stub with a real check before the feature is used in production fast/snap sync.

4. **Harden `SyncStakingInfo`**: After receiving staking info from a peer, verify the content by calling `getFromStateByNumber` locally and comparing, rather than trusting the peer's payload.

---

### Proof of Concept

**Setup**: Node A (attacker) and Node B (victim, performing FastSync from A).

**Attack steps**:

1. Node A serves valid headers and receipts to Node B (so header/receipt validation passes).

2. For each `StakingInfoRequestMsg` received from Node B, Node A responds with a crafted `StakingInfoMsg` where:
   ```go
   // Attacker-controlled addresses
   fakeStakingInfo := &staking.P2PStakingInfo{
       BlockNum:       legitimateBlockNum,
       // All other fields identical to real data, except:
       RewardAddrs:    []common.Address{attackerRewardAddr, attackerRewardAddr},
       KEFAddr:        attackerAddr,
       KIFAddr:        attackerAddr,
   }
   ```

3. Node B's `handleStakingInfoMsg` decodes the message and calls `pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos)`.

4. `DeliverStakingInfos` → `queue.DeliverStakingInfos` → `validate(...)` returns `nil` unconditionally → `result.StakingInfo = fakeStakingInfo`.

5. `commitFastSyncData` calls `d.stakingModule.PutStakingInfoToDB(result.StakingInfo.BlockNum, staking.ToStakingInfo(result.StakingInfo))`, persisting the fake data.

6. After sync completes, Node B processes new blocks. `FinalizeState` calls `r.GetDeferredReward(header, txs, receipts)` which reads the fake `StakingInfo` from DB and calls `state.AddBalance(attackerRewardAddr, amount)` for every block reward distribution.

**Result**: All KAIA block rewards for the affected staking intervals are credited to `attackerRewardAddr` instead of the legitimate validators' reward addresses. The treasury fund portions go to `attackerAddr`. Node B's state diverges from honest nodes, and the attacker accumulates KAIA that should belong to legitimate validators.

```go
// assignStakingRewards assigns staking rewards to stakers according to their staking amounts.
// Returns the allocation and the remainder.
func assignStakingRewards(config *reward.RewardConfig, stakersReward *big.Int, si *staking.StakingInfo) (map[common.Address]*big.Int, *big.Int) {
	var (
		cns               = si.ConsolidatedNodes()
		minStake          = config.MinimumStake.Uint64()
		totalExcessInt    = uint64(0) // sum of excess stakes (the amount over minStake) over all stakers
		cnTotalStakingMap = make(map[common.Address]uint64)
		isPrague          = config.Rules.IsPrague
	)
	for _, cn := range cns {
		// If the CNStaking is less than minStake, skip it.
		if cn.StakingAmount >= minStake {
			// Calculate total staking amount once
			cnTotalStakingAmount := cn.StakingAmount
			if isPrague && cn.CLStakingInfo != nil {
				cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount
			}
			totalExcessInt += cnTotalStakingAmount - minStake
			cnTotalStakingMap[cn.RewardAddr] = cnTotalStakingAmount
		}
	}

	var (
		totalExcess = new(big.Int).SetUint64(totalExcessInt)
		remaining   = new(big.Int).Set(stakersReward)
		alloc       = make(map[common.Address]*big.Int)
	)
	for _, cn := range cns {
		cnTotalStakingAmount := cnTotalStakingMap[cn.RewardAddr]
		if cnTotalStakingAmount > minStake {
			// The KAIA unit will cancel out:
			// reward (kei) = excess (KAIA) * stakersReward (kei) / totalExcess (KAIA)
			excess := new(big.Int).SetUint64(cnTotalStakingAmount - minStake)
			if reward := new(big.Int).Div(new(big.Int).Mul(excess, stakersReward), totalExcess); reward.Sign() > 0 {
				if isPrague && cn.CLStakingInfo != nil {
					// The remaining amount will be added to the cnAmount.
					cnAmount, clAmount := cn.Split(reward)
					alloc[cn.RewardAddr] = cnAmount
					alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
				} else {
					alloc[cn.RewardAddr] = reward
				}
				remaining.Sub(remaining, reward)
			}
		}
	}
	return alloc, remaining
```

```go
// handleStakingInfoMsg handles staking information response message.
func handleStakingInfoMsg(pm *ProtocolManager, p Peer, msg p2p.Msg) error {
	if pm.chainconfig.Istanbul == nil || pm.chainconfig.Istanbul.ProposerPolicy != uint64(istanbul.WeightedRandom) {
		return errResp(ErrUnsupportedEnginePolicy, "the engine is not istanbul or the policy is not weighted random")
	}

	// A batch of stakingInfos arrived to one of our previous requests
	var stakingInfos []*staking.P2PStakingInfo
	if err := msg.Decode(&stakingInfos); err != nil {
		return errResp(ErrDecode, "msg %v: %v", msg, err)
	}
	// Deliver all to the downloader
	if err := pm.downloader.DeliverStakingInfos(p.GetID(), stakingInfos); err != nil {
		logger.Debug("Failed to deliver staking information", "err", err)
	}
	return nil
```
