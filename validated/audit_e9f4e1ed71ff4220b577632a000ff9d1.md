### Title
Auto-triggered rollback bypasses the `rollback_variables` environment whitelist - (File: `app/models/shipit/deploy.rb`)

### Summary
When an in-flight `Deploy` is aborted with `rollback_once_aborted: true`, `Task#trigger_revert_if_required` re-uses the aborted deploy's already-permitted `env` to build and start a `Rollback`, without ever passing it through `Stack#filter_rollback_envs`. This breaks the binding *"an environment key permitted [against `deploy_variables`] versus an environment key spawned [in a rollback's shell steps, which should only ever see keys permitted against `rollback_variables`]"*.

### Finding Description
Two independent whitelists exist for task environments:
- `Stack#filter_deploy_envs` → `EnvironmentVariables.with(env).permit(deploy_variables)` [1](#0-0) 
- `Stack#filter_rollback_envs` → `EnvironmentVariables.with(env).permit(rollback_variables)` [2](#0-1) 

`rollback_variables` is explicitly documented to be able to differ from `deploy_variables` and stack authors are expected to use it to restrict which variables may reach rollback steps: "For backwards compatibility, fallback to using deploy_variables if no explicit rollback variables are set" [3](#0-2) .

The normal user-facing entry point correctly enforces this separation: `Api::RollbacksController#create` calls `stack.filter_rollback_envs(params.env)` before triggering the rollback [4](#0-3) .

However, `Deploy#build_rollback` never filters its `env:` argument at all — it stores whatever hash it is given verbatim on the `Rollback` record: [5](#0-4) 

And `Task#trigger_revert_if_required`, invoked automatically as an `after_transition to: :aborted` callback whenever a deploy is aborted with `rollback_once_aborted: true`, forwards the *aborted deploy's own env* (which was only ever validated against `deploy_variables`) straight into `trigger_rollback`: [6](#0-5) 

That `rollback_once_aborted_to` / `rollback_once_aborted` state is set by the same `Api::RollbacksController#create` action, when an active task exists on the stack: [7](#0-6) 

The forwarded env is subsequently merged into the spawned shell process and interpolated into `$VAR` references in rollback steps by `TaskCommands#env` and `Command#interpolate_environment_variables`/`Command#unbundled_env` [8](#0-7) [9](#0-8) [10](#0-9) .

### Impact Explanation
A user holding only the `deploy:stack` permission for a stack — who may be intentionally restricted from setting certain environment variables for *rollback* steps (e.g. dangerous flags a stack owner deliberately excluded from `rollback_variables` while still allowing them for `deploy_variables`) — can smuggle those variable values into a rollback's execution environment. Because the env is interpolated directly into shell commands defined in the repository's `shipit.yml` rollback steps, this can alter command behaviour or arguments in ways the stack owner specifically tried to prevent via the narrower `rollback_variables` whitelist, i.e., it escalates beyond the deploy-time authorization boundary into rollback execution — an unauthorized/altered deploy-adjacent action reachable purely through a documented, unprivileged-relative-to-rollback API flow.

### Likelihood Explanation
The path only requires standard `deploy:stack` permission (no admin, no GitHub write access, no token secrets): create a deploy with env keys permitted for `deploy_variables` but excluded from `rollback_variables`, then call the rollback API against a different commit while that deploy is still active, setting `rollback_once_aborted`. The abort naturally fires `trigger_revert_if_required`, which requires no further attacker action.

### Recommendation
In `Deploy#build_rollback`/`Task#trigger_revert_if_required`, always re-filter the env through `stack.filter_rollback_envs` before constructing the `Rollback`, exactly as `Api::RollbacksController#create` already does for user-initiated rollbacks, instead of trusting an env that was only validated against `deploy_variables`.

### Proof of Concept
1. Stack's `shipit.yml` declares `deploy.variables` including `RISKY_FLAG` but a narrower `rollback.variables` that excludes it.
2. Attacker with `deploy:stack` permission triggers a deploy on commit B with `env: { RISKY_FLAG: "1" }` (passes `filter_deploy_envs`, since `RISKY_FLAG` is a valid deploy variable) — deploy starts and is `active_task`.
3. Attacker calls `POST /stacks/:id/rollback` for an earlier commit A. Since a deploy is active, `Api::RollbacksController#create` calls `active_task.abort!(aborted_by:, rollback_once_aborted_to: <deploy to A>, rollback_once_aborted: true)` [11](#0-10) .
4. On the `aborted` transition, `Task#trigger_revert_if_required` calls `rollback_once_aborted_to.trigger_rollback(aborted_by, env:, force: true)` where `env` is the just-aborted deploy's env (`{RISKY_FLAG: "1"}`), unfiltered [12](#0-11) .
5. `build_rollback` stores `env: {RISKY_FLAG: "1"}` on the new `Rollback` without ever consulting `rollback_variables` [5](#0-4) .
6. The rollback task runs with `RISKY_FLAG=1` available for shell interpolation in its steps, even though the stack owner's `rollback.variables` whitelist never permitted it.
