### Title
Textcoin claim mnemonic and private payment chains are written to an unencrypted file, enabling theft of private-asset funds - (File: wallet.js)

### Summary
When a user sends a private (blackbyte) asset as a textcoin to a recipient who is not reachable over the device-to-device protocol (e.g., email/URL delivery), `wallet.js` calls `storePrivateAssetPayload()` to persist the textcoin's spending secret (`mnemonic`) together with the full private payment chain (`chains`, containing addresses, blinding factors and amounts) into a plaintext, merely-compressed ZIP file at a caller-supplied path [1](#0-0) . This mirrors the reported bug class (sensitive transaction data persisted unencrypted on disk, readable by anyone with filesystem access), but here the exposed data is not just historical metadata — the `mnemonic` is the literal spending key for the textcoin address, so its exposure enables outright fund theft rather than just a privacy leak.

### Finding Description
The `storePrivateAssetPayload` function builds `storedObj = {mnemonic, chains}` and serializes it with `JSON.stringify`, adds it to a `JSZip` archive using only `DEFLATE` compression (no encryption), then writes it to `fullPath` via `fs.writeFile` (Node) or the Cordova filesystem API [2](#0-1) . This path is invoked from `sendMultiPayment`'s `preCommitCb` whenever a private asset is being sent to recipients who are not resolvable to a `recipient_device_address` and are not local addresses — i.e., textcoin-style off-device transfers — via the caller-provided `opts.getPrivateAssetPayloadSavePath` callback [3](#0-2) .

The `mnemonic` stored in this file is not merely a label: `receiveTextCoin` derives a full private-key signer from it (`expandMnemonic(mnemonic)` yields `addrInfo.xPrivKey`, `addrInfo.address`, and `addrInfo.definition`, and `sign()` uses `addrInfo.xPrivKey.privateKey` directly to sign spends) [4](#0-3) . Any holder of the mnemonic can claim/spend the private asset funds sitting at `addrInfo.address` before the intended recipient does, as demonstrated by the "claim back" logic that treats mnemonic possession as sufficient authority to spend [5](#0-4) .

Because the export file is deliberately written outside of the wallet's protected database/storage (its whole purpose is to be handed off/shared to another party or medium), it is exactly the kind of artifact described in the report: it can persist on disk (Downloads folder, temp directories, removable media, cloud-sync folders) long after the transaction, and unlike `senttxstore.dat` it contains an actual bearer secret plus the full private chain (counterparty addresses, blinding factors, amounts) rather than just metadata.

### Impact Explanation
An attacker who gains local filesystem access to the sender's (or an intermediate storage/sync location holding) exported private-textcoin file obtains the `mnemonic`, which is a complete spending credential for the private asset output. This allows the attacker to claim/spend the private-asset funds themselves, resulting in concrete unauthorized asset theft (loss of the sent funds) and disclosure of the private payment chain (addresses, blinding factors, amounts) that should remain confidential between sender and intended recipient. This exceeds the impact of the original report because it enables fund loss, not just history disclosure.

### Likelihood Explanation
Any use of textcoin/off-device private-asset sending (a normal, documented wallet feature reachable by any private-payment counterparty interaction) triggers this code path whenever the sender is not connected device-to-device with the recipient. The resulting file is explicitly meant to leave the secured app boundary (to be emailed, uploaded, or copied), which increases the chance of it landing in a location accessible to a local attacker, cloud backup, or forensic recovery, matching the original report's exploit scenario (attacker with post-hoc access to leftover files).

### Recommendation
- Encrypt the exported private-asset payload file (mnemonic + chains) using a password/passphrase supplied out-of-band to the recipient, or a platform keystore-backed key, before writing it to disk, instead of relying solely on ZIP compression.
- Avoid persisting the raw mnemonic longer than necessary; consider deriving and exposing only the minimum data needed to claim, and clear it from memory/disk once transmitted.
- Provide guidance/warnings to callers of `getPrivateAssetPayloadSavePath` about secure temp-file handling (e.g., secure delete after transmission) and avoid default paths in cloud-synced or shared directories.

### Proof of Concept
1. Alice sends a private (blackbyte) asset as a textcoin to Bob's email address using a wallet UI that implements `getPrivateAssetPayloadSavePath`.
2. `sendMultiPayment` → `preCommitCb` invokes `storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, arrChainsOfRecipientPrivateElements, cb)` [6](#0-5) , writing an unencrypted (compression-only) ZIP containing `{mnemonic, chains}` to `fullPath` [1](#0-0) .
3. This file remains at `fullPath` (e.g., Downloads/Temp folder) after being attached/sent, or is duplicated by an OS backup/cloud-sync tool.
4. Eve, who later gains access to Alice's machine (or the sync location) — even after the wallet app and its DB have been removed — extracts the ZIP and reads the plaintext `mnemonic`.
5. Eve calls the equivalent of `receiveTextCoin(mnemonic, eve_address, ...)`, which derives `addrInfo.xPrivKey` from the mnemonic and signs a spend to her own address [4](#0-3) , claiming the funds before or instead of Bob.

function storePrivateAssetPayload(fullPath, cordovaPathObj, mnemonic, chains, cb) {
	var storedObj = {
		mnemonic: mnemonic,
		chains: chains
	};
	var bCordova = (typeof window === 'object' && window.cordova);
	var JSZip = require("jszip");
	var zip = new JSZip();
	zip.file('private_textcoin', JSON.stringify(storedObj));
	var zipParams = {type: "nodebuffer", compression: 'DEFLATE', compressionOptions: {level: 9}};
	zip.generateAsync(zipParams).then(function(zipFile) {
		if (!bCordova) {
			var fs = require('fs');
			fs.writeFile(fullPath, zipFile, cb);
		} else {
			window.requestFileSystem(LocalFileSystem.TEMPORARY, 0, function(fs) {
				window.resolveLocalFileSystemURL(cordovaPathObj.root, function(dirEntry) {
					dirEntry.getDirectory(cordovaPathObj.path, {create: true, exclusive: false}, function(dirEntry1) {
						dirEntry1.getFile(cordovaPathObj.fileName, {create: true, exclusive: false}, function(file) {
							file.createWriter(function(writer) {
								writer.onwriteend = function() {
									cb(null); 
								};
								writer.write(zipFile.buffer);
							}, cb);
						}, cb);
					}, cb);
				}, cb);
			}, cb);
		}
	}, cb);
