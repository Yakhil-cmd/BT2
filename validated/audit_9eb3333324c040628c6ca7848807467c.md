### Title
`load_rules()` resolves `.claude/hookify.*.local.md` relative to process CWD instead of the project root, allowing security rules to be silently skipped - ([File: plugins/hookify/core/config_loader.py])

### Summary
`load_rules()` builds its glob pattern with `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob(pattern)`, which is resolved relative to the current working directory of the hook subprocess rather than a fixed, verified project root. If the CWD at hook invocation time is not the repository root that contains the real `.claude/` rules directory, `glob.glob` returns an empty list and `load_rules()` returns no rules, silently disabling all warn/block enforcement for that call.

### Finding Description
`load_rules()` in `plugins/hookify/core/config_loader.py` (around lines 198-211) does:
```python
pattern = os.path.join('.claude', 'hookify.*.local.md')
files = glob.glob(pattern)
``` [1](#0-0) 

This is a bare relative path with no resolution against a known-good project directory such as `CLAUDE_PROJECT_DIR`. All four hookify hook entrypoints (`pretooluse.py`, `posttooluse.py`, `stop.py`, `userpromptsubmit.py`) call `load_rules()` directly without ever passing or anchoring to an absolute project root [2](#0-1) [3](#0-2) . Notably, even though these scripts already read `CLAUDE_PLUGIN_ROOT` from the environment for `sys.path` setup [4](#0-3) , that variable is only used for import resolution, not for anchoring the rules glob. By contrast, a sibling plugin (`security-guidance`) does reference `CLAUDE_PROJECT_DIR` when determining working context, showing the codebase is aware that CWD/project-root binding matters for hook logic, yet `hookify`'s `config_loader.py` does not apply this pattern.

Any error path in `load_rules()` also silently swallows the failure — an empty `files` list simply results in an empty `rules` list with no warning that the intended `.claude` directory was not found at all (a total miss on `.claude` yields nothing, indistinguishable from "no rules configured"). Since glob resolution is CWD-relative, a subprocess or tool invocation that changes directory (e.g., a `Bash` tool call with `cwd` set to a nested submodule, or Claude Code executing a hook while a prior tool call altered the shell's directory context) will cause the block/warn rules defined at the real project root to be invisible to this call.

### Impact Explanation
This causes attacker-crafted repository content (e.g., a nested submodule or subdirectory lacking `.claude`) to bypass `hookify`'s block/warn safety rules whenever the hook subprocess's CWD is not the repo root. Since `hookify` is explicitly a security-enforcement plugin (block/warn on dangerous commands or file edits), a rule-loading failure directly translates into an unenforced security control, letting through commands/edits that were meant to be blocked.

### Likelihood Explanation
Exploitability depends entirely on whether Claude Code hook subprocesses are ever invoked with a CWD other than the project root (e.g., via a `Bash` tool call that specifies a working directory, or a prior command that `cd`'d into a subdirectory before an Edit/Write tool triggers `PreToolUse`). This is plausible in ordinary workflows involving multi-directory repos/submodules and does not require any elevated privilege — only ordinary repository content that induces the agent to operate from a nested directory. I could not fully verify from the available code how Claude Code sets the subprocess CWD for hook scripts (whether it is always forced to the workspace root regardless of the tool's working directory) or whether an external invariant/wrapper enforces this elsewhere outside of `plugins/hookify`; this uncertainty affects the exact reproducibility bound, but within `config_loader.py` itself there is no such guard.

### Recommendation
Anchor rule discovery to a canonical project root rather than the ambient process CWD — resolve `os.environ.get('CLAUDE_PROJECT_DIR')` (already used elsewhere in the plugin ecosystem) or otherwise walk up from a known repo marker, and build the glob pattern from that absolute path (e.g., `os.path.join(project_root, '.claude', 'hookify.*.local.md')`). Additionally, log/surface a warning distinct from "no rules configured" when the `.claude` directory itself cannot be found at the resolved root, so that CWD drift is detectable instead of silently producing an empty rule set.

### Proof of Concept
Integration test plan:
1. Create a temp directory tree: `repo_root/.claude/hookify.block-test.local.md` containing a `block` rule (e.g., `event: bash`, `pattern: "rm -rf"`, `action: block`).
2. Create `repo_root/nested_submodule/` with no `.claude` directory.
3. Invoke `pretooluse.py` (or directly call `load_rules(event='bash')`) twice:
   - Once with CWD = `repo_root` — assert the block rule is loaded and `evaluate_rules` returns a block decision for `rm -rf /`.
   - Once with CWD = `repo_root/nested_submodule` — assert `load_rules()` returns `[]` and the same dangerous command is not blocked (result contains no block/deny fields).
4. Assertion demonstrating the bug: identical dangerous input produces different enforcement outcomes purely based on subprocess CWD, confirming the bypass.
