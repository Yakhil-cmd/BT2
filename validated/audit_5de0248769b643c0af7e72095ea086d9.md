### Title
Webhook signature is verified against the organization derived from the payload, but every event handler acts on a different, unbound `repository.full_name` / `organization.login` field, letting a valid webhook secret for Org A forge state changes for stacks belonging to any other org configured on the same Shipit instance - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
When Shipit is configured with the "multiple GitHub applications" schema (`docs/setup.md` §"Using Multiple Github Applications"), each organization has its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` picks which secret to verify the HMAC against using `repository_owner`, read straight from the untrusted payload (`params.dig('repository','owner','login')` or `organization.login`) [2](#0-1) [3](#0-2) . The signature only proves the raw body was HMAC'd with *that org's* secret — it does not bind the rest of the payload to that org. Every downstream handler then re-reads a *different* payload field (`repository.full_name`, `organization.login`) to decide which `Stack`, `Commit`, or `Team` to mutate [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) . Nothing checks that the org that authenticated the request equals the org whose repository/team is actually written.

### Finding Description
`Shipit.github(organization: repository_owner)` selects a `GitHubApp` instance (and its `webhook_secret`) keyed by whatever `repository_owner` value is embedded in the attacker-supplied payload [8](#0-7) . `verify_webhook_signature` then HMACs the *entire raw body* with that org's secret and compares to the `X-Hub-Signature` header [9](#0-8) .

This means: if an attacker legitimately controls/knows the webhook secret for `OrgA` (a real customer that Shipit hosts, or a leaked/rotated secret), they can craft a raw JSON body where:
- `repository.owner.login` (or `organization.login`) = `"OrgA"` → so `verify_signature` selects `OrgA`'s secret, computes a matching HMAC, and the signature check passes.
- `repository.full_name` = `"OrgB/some-other-repo"` (a completely different, unrelated organization also hosted on the same Shipit instance) — this is the field every `Handler` subclass actually uses to resolve `Repository`/`Stack` [4](#0-3) .

The `push` event handler will then call `stack.sync_github(expected_head_sha: params.after)` on `OrgB`'s stack using an attacker-chosen `after` sha [5](#0-4) . The `status` handler will create a forged CI `Status` (with arbitrary `state`, `context`, `description`) on any commit sha the attacker names, regardless of which repo it belongs to, since `StatusHandler` only filters by `Commit.where(sha: params.sha)` and never checks organization/repo ownership at all [6](#0-5) . The `check_suite` handler similarly schedules check-run refreshes for any stack matching the forged `head_branch`/`head_sha` [10](#0-9) . The `membership` handler creates/deletes team membership using `organization.login` from the payload with no cross-check against the org that produced the valid signature [11](#0-10) .

This is the exact "binding break" pattern from the reference report: the field that is verified (the org used to pick the HMAC secret) is not the field that is acted upon (the repository/organization actually written).

### Impact Explanation
Forged `status` events can inject fabricated CI success statuses for commits belonging to organizations the attacker does not control. If a stack's `shipit.yml` gates deploys/merges on required CI contexts (`ci.require`) or if continuous deployment is enabled, this can result in an **unauthorized deploy** for a repository unrelated to the attacker's own org — matching the Critical impact bucket ("an unauthorized deploy, rollback or merge"). Forged `push`/`check_suite` events can trigger sync jobs and check-run refresh jobs against arbitrary stacks, and forged `membership` events can silently add/remove arbitrary GitHub users to/from `Shipit.github_teams`-backed `Team` records, which is used for `User#authorized?` — this reaches the High-severity bucket ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
This requires the attacker to possess a valid webhook secret for *some* organization configured on the shared Shipit instance — a realistic scenario for any Shipit deployment serving multiple GitHub organizations/tenants as documented in `docs/setup.md`, since each tenant configures/knows their own `webhook_secret`. No repository write access, session, or `ApiClient` token is needed; only knowledge of one org's webhook secret and the ability to POST to `/webhooks`, which is an unauthenticated, unprivileged endpoint (`resources :webhooks, only: :create`) [12](#0-11) .

### Recommendation
After signature verification, re-derive the organization from the authenticated context (the `repository_owner`/`organization.login` used to select the secret) and require every handler to verify that `payload.dig('repository','full_name')` (and `organization.login` for the membership event) actually belongs to that same, already-authenticated organization before mutating any `Stack`, `Commit`, or `Team`. Concretely, pass the verified organization into `Shipit::Webhooks.for_event(event)` handlers and have `Handler#stacks`/`MembershipHandler#find_or_create_team!` reject records whose owning organization does not match.

### Proof of Concept
1. Configure Shipit with the multi-org schema, hosting `OrgA` and `OrgB`, each with distinct `webhook_secret`s (per `docs/setup.md`) [1](#0-0) .
2. As an entity that knows `OrgA`'s `webhook_secret` (e.g., a legitimate `OrgA` admin), craft a `status` event body:
   ```json
   {
     "sha": "<sha of a commit belonging to OrgB/some-repo>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/some-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, verifies successfully because the body was HMAC'd with `OrgA`'s real secret [2](#0-1) .
5. `StatusHandler#process` runs unconditionally against `Commit.where(sha: params.sha)`, creating a forged successful CI status on `OrgB`'s commit [6](#0-5) , which can satisfy `OrgB`'s stack's `ci.require` gate and enable an unauthorized deploy.

Note: I could not find any additional check elsewhere in `app/**`/`lib/shipit/**` that cross-validates the signature-selected organization against the handler-consumed `repository.full_name`/`organization.login`; the index coverage for this repo appeared complete for the relevant controller/model files reviewed, so this is asserted with reasonable confidence, though a full-repo grep for a possible unification point in job-level processing (`GithubSyncJob`, etc.) was not exhaustively completed.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
