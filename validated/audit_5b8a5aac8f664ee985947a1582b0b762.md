### Title
Webhook signature verified against `repository.owner.login`'s org while the mutated repo/stack is resolved from an independently-attacker-controlled `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App/org used for HMAC verification solely from `params.dig('repository','owner','login')`, but all downstream handlers (e.g. `ReopenedHandler`) resolve the repository/stack to mutate from the separate, independently-controlled `params.repository.full_name` field. An attacker who owns/controls (or simply names) any organization slug with no `webhook_secret` configured in Shipit — which causes `verify_webhook_signature` to short-circuit and return `true` — can set `repository.owner.login` to that no-secret org while setting `repository.full_name` to `victim-org/victim-repo`, bypassing signature verification entirely for an event that mutates the victim org's stack.

### Finding Description
The broken binding: the code implicitly assumes `params.repository.owner.login == params.repository.full_name.split('/').first`, but nothing enforces this equality.

Path:
1. `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository','owner','login')` [5](#0-4) .
2. `Shipit.github(organization:)` looks up that org's config via `github_app_config(organization)` [6](#0-5) . In the multi-org config format, each org (e.g. `somegithuborg`) has its own optional `webhook_secret` [7](#0-6) .
3. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank/not configured for that org [2](#0-1) .
4. `WebhooksController#create` then dispatches `params` (the full unverified JSON body) to `Shipit::Webhooks.for_event(event)` handlers [8](#0-7) .
5. `ReopenedHandler#repository` resolves the target `Repository` purely from `params.repository.full_name`, independent of `repository.owner.login` [4](#0-3) .
6. `ReopenedHandler#process` calls `stack.unarchive!`, and via `ReviewStackAdapter#unarchive!` this either unarchives an existing `ReviewStack` or creates a new one and enqueues it for provisioning [9](#0-8) , and later triggers deployments as `Shipit.user`, which is the configured `bot_login` when set [10](#0-9) .

Exploit: attacker crafts a `pull_request` webhook body with `action: "reopened"`, `repository.owner.login: "attacker-no-secret-org"` (an org configured in Shipit with no `webhook_secret`, or simply the app's default/global org if it has no secret set), and `repository.full_name: "victim-org/victim-repo"` where `victim-org/victim-repo` is a real, review-stacks-enabled Shipit repository with `bot_login` configured. The attacker sends this to `POST /webhooks` with the `X-Github-Event: pull_request` header and any (or no) `X-Hub-Signature`. `verify_signature` picks the attacker's no-secret org, `verify_webhook_signature` returns `true` unconditionally, and the request passes. The handler then acts on `victim-org/victim-repo`'s stack, unarchiving/recreating a `ReviewStack` and re-triggering provisioning/deployment, which subsequently uses the bot's GitHub identity/token for the actual victim repo.

Existing guards that fail to prevent this: `check_if_ping` and `drop_unhandled_event` don't validate ownership; `verify_signature` only validates the signature against the org named in `repository.owner.login`, never cross-checking it against `repository.full_name`; the `ExplicitParameters` schema on `ReopenedHandler` only requires `repository.full_name` be a `String`, with no format/ownership constraint tying it back to `repository.owner.login` [11](#0-10) ; `Repository.from_github_repo_name` simply does a case-insensitive DB lookup with no origin check [3](#0-2) .

This does require that Shipit is configured in the multi-org format (or otherwise has at least one org with `webhook_secret` unset) for the "no-secret org" side to exist; in the single-org config schema, `repository_owner` is not used to pick the app (`Shipit.github(organization: github_default_organization)` when `github_default_organization` is nil bypasses the per-org lookup) [12](#0-11) , so the cross-org confusion specifically applies to deployments using the multi-org `github:` config format with mismatched webhook_secret coverage.

### Impact Explanation
An unauthenticated/unprivileged attacker can force Shipit to unarchive/recreate a `ReviewStack` for an arbitrary victim organization's repository/PR without ever possessing that org's `webhook_secret`, as long as any other org configured in the same Shipit instance lacks a `webhook_secret`. This can re-trigger provisioning and CD deployments that execute as the configured bot identity against the victim repository — matching "a payload for one repository mutating another's stack" and unauthorized deploy/rollback impact (Critical). The blast radius is bounded to Shipit deployments using the multi-org config with at least one org missing `webhook_secret`, but is repeatable against any repository/stack reachable via `Repository.from_github_repo_name`.

### Likelihood Explanation
Requires: (1) Shipit configured with multiple GitHub orgs (`github:` multi-org schema), (2) at least one configured org has no `webhook_secret` set, (3) the victim org/repo has `review_stacks_enabled` and a provisioning behavior that allows unarchiving, and ideally `bot_login` configured for auto-deploy amplification. Given these preconditions, the attack costs a single unauthenticated HTTP POST with a crafted JSON body — no signature, no credentials, no GitHub account interaction needed for the request itself. It is fully repeatable against any stack/PR whose `full_name` the attacker can guess or knows.

### Recommendation
In `WebhooksController#verify_signature`, after selecting `github_app` by `repository_owner`, also verify that `params.dig('repository','full_name')` (when present) starts with `"#{repository_owner}/"` (case-insensitive) before proceeding, rejecting mismatches with 422. Alternatively, do not allow any org's `webhook_secret` to be blank in production multi-org configs (fail closed instead of returning `true`), and/or bind handler repository resolution to the same org value used for verification rather than trusting `full_name` independently.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)

    github_config[github_organization]
  end
