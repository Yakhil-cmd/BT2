### Title
Non-owner PROPOSER can strip the CANCELLER veto via `RevokeGovRole`, then pass uncancellable value-extracting operations - (File: contracts/governance/src/timelock/lifecycle.rs)

### Summary
`propose` requires the proposer to be the owner for `GrantGovRole` but not for `RevokeGovRole`: a non-owner `PROPOSER` may schedule revocation of any role held by any address other than itself and the owner, including `CANCELLER`. `cancel` additionally forbids a canceller from vetoing an operation whose recorded revocation target is itself, so when the canceller set is a single non-owner address (the normal separation-of-duties deployment, since the owner cannot be revoked), that address is structurally unable to veto its own removal. Once the revocation executes — permissionlessly, via `execute_self(executor: None)` — every subsequent `AdminOperation` a proposer can schedule (e.g. `ForceSocializeBadDebt`, `EditAssetInSpoke`, `SetSpokeLiquidationCurve`, `SetPositionManager`, `Unpause`) becomes effectively uncancellable, turning a scheduling-only role into unconstrained administration of the controller's risk surface.

### Finding Description
The privilege model is asymmetric. In `propose` (`contracts/governance/src/timelock/lifecycle.rs:39-70`), the owner-only arm covers `GrantGovRole` and other sensitive operations, but `RevokeGovRole` is handled in the earlier arm at lines 40-47, which only rejects `args.account == proposer` and `args.account == owner`. Any address holding `PROPOSER_ROLE` therefore passes the gate with `AdminOperation::RevokeGovRole { account: <canceller>, role: CANCELLER }`, and `resolve_op` maps it to a self-targeted `revoke_role` call on the Sensitive delay tier (`contracts/governance/src/op.rs:157-169`).

Two compounding details remove the defense this design relies on:

- `cancel` refuses to cancel a role-revocation op whose recorded target equals the canceller (`lifecycle.rs:146-152`, via `storage::role_revocation_target` set at `lifecycle.rs:75-77`). The only party guaranteed to be motivated to veto a revocation of the canceller — the canceller itself — is barred from doing so. With a single-canceller deployment there is no remaining veto.
- Execution is permissionless: `authorize_executor` performs no check when `executor` is `None` (`contracts/governance/src/timelock/mod.rs:77-82`), so the attacker drives `execute_self` itself once the delay elapses.

After the canceller is stripped, the same `PROPOSER` (still holding its role — `RevokeGovRole` cannot target the owner or the proposer, but nothing stops the attacker from keeping PROPOSER) schedules ops that are reachable by non-owner proposers: `ForceSocializeBadDebt` (Sensitive tier, bypasses the dust cap and writes down the supply index — `op.rs:407-411`, documented in `docs/reference/endpoints.md:157`), `EditAssetInSpoke` rewriting `ltv`/`threshold`/`bonus` subject only to `validate_risk_bounds` (`op.rs:232-239`), and `SetSpokeLiquidationCurve` (`op.rs:412-430`). This mirrors the GitLab CVE-2024-8631 class exactly: a scoped custom role mutating the role/permission set to acquire powers outside its mandate.

### Impact Explanation
Theft of user funds and protocol insolvency. With the canceller veto removed the attacker can, for example: schedule `EditAssetInSpoke` setting a collateral listing's `threshold`/`ltv` to the minimum allowed bound and `SetSpokeLiquidationCurve` to the maximum validated bonus; every account holding that collateral becomes liquidatable (`is_liquidatable` reads the restamped liquidation threshold), and the attacker liquidates them for the full configured bonus. Alternatively `ForceSocializeBadDebt(account_id)` writes the pool supply index down for any victim account without the $5 dust cap, directly impairing all suppliers in that hub market. All of this is normally vetoable; the finding is that the veto can be removed by the least-privileged operational role.

### Likelihood Explanation
Medium. It requires a `PROPOSER_ROLE` holder (or compromised proposer key) and a deployment where `CANCELLER` is held by a non-owner set the attacker can fully enumerate and revoke (each holder needs its own `RevokeGovRole` op, all on the same Sensitive delay; non-targeted cancellers can still cancel revocations of their peers, so the attack needs the whole canceller set revoked in parallel before any of them notices — feasible since all ops become executable after the same delay). It needs no capital, no oracle manipulation, and no code access. The GitLab source bug likewise required a limited role, which is why it was rated High rather than Critical.

### Recommendation
Add `AdminOperation::RevokeGovRole` to the owner-required arm in `propose` (`lifecycle.rs:48-69`), so that role-set mutation in either direction requires the owner. Independently, reconsider `cancel`'s self-revocation block (`lifecycle.rs:146-152`): barring the target from vetoing its own revocation is what makes a lone non-owner canceller helpless; permitting the target to cancel, or requiring owner-only proposal, restores the intended check.

### Proof of Concept
1. Governance deployed with `admin` (owner, all roles) and a separate `canceller` address granted `CANCELLER`; `mallory` granted `PROPOSER` — all via legitimate owner-proposed `GrantGovRole` ops.
2. `mallory` calls `propose(mallory, AdminOperation::RevokeGovRole { account: canceller, role: "CANCELLER" }, salt)`. `begin_immediate` passes (mallory holds PROPOSER); the `args.account != proposer` / `!= owner` checks pass; the op schedules on the Sensitive tier and `mark_role_revocation_target` records `canceller`.
3. `canceller` calls `cancel(canceller, operation_id)` → reverts `OperationNotCancellable` at `lifecycle.rs:146-152`. No other canceller exists; the owner's only immediate revocation lever (`revoke_role_immediate`) is restricted to `GUARDIAN`/`ORACLE` (`timelock/immediate.rs:69-75`), so it cannot strip mallory's PROPOSER in time.
4. After the delay, anyone calls `execute_self(None, RevokeGovRole{...}, salt)` → `apply_grant_role`-mirror `apply_revoke_role` removes `CANCELLER` from `canceller`. The veto set is now empty.
5. `mallory` calls `propose(mallory, AdminOperation::EditAssetInSpoke { ..threshold = minimum, bonus = maximum allowed.. })`, waits the Standard delay, executes with `execute(None, controller, "edit_asset_in_spoke", ..)` — uncancellable. All accounts supplying that asset in the spoke become liquidatable; mallory liquidates them via `controller::liquidate` and seizes collateral at the max configured bonus.
6. Alternative theft leg: `propose`/`execute` `ForceSocializeBadDebt(victim_account)` (not in the owner-only list) → `force_socialize_bad_debt` writes the market's supply index down, impairing every supplier.

Concrete precedent in the codebase's own docs that this asymmetry is unintended: the README and `endpoints.md:215` describe the owner gate as covering "role-grant ops" while `RevokeGovRole` — which mutates the same role set — is excluded, and `cancel`'s self-target block assumes multiple cancellers without enforcing that configuration.
