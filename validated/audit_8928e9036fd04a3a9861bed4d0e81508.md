### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for the `allow_with_label`/`prevent_with_label` disjuncts - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`provision?` is written as `(A && B) || C || D` where only the first disjunct (`allow_all`) is gated by `repository.review_stacks_enabled`. The second (`allow_with_label`) and third (`prevent_with_label`) disjuncts never reference `review_stacks_enabled`, so a repository with review stacks explicitly disabled will still auto-provision a stack whenever the configured label condition is met. The same defect exists in `ReopenedHandler#unarchive?`.

### Finding Description
The binding claimed by the question is: `repository.review_stacks_enabled == false` ⇒ `provision? == false` for all three provisioning-behavior enum values. Tracing `provision?`: [1](#0-0) 

Ruby operator precedence makes `&&` bind tighter than `||`, so this evaluates as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

The question's hypothesis about precedence confusion in the *first* term is not the bug — `(A && B)` is correctly grouped. The actual defect is that `review_stacks_enabled` (A) is entirely absent from the second and third disjuncts. If an operator sets `review_stacks_enabled = false` while leaving `provisioning_behavior` at `allow_with_label` (or `prevent_with_label`) — e.g., toggling review stacks off in the UI without also resetting the provisioning behavior dropdown, per `app/views/shipit/repositories/settings.html.erb` and `repositories_controller.rb` — the first disjunct is `false` (since A is false), but the second or third disjunct can still independently evaluate `true` based purely on label presence/absence, with no dependency on `review_stacks_enabled` at all.

Reachable path: attacker opens a pull request (or reopens one) against the affected repository and adds/omits their own PR label (`labeled`/no-label) to satisfy the label condition. GitHub sends the `pull_request` webhook. `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?`, and if true, invokes `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack` record with `branch: params.pull_request.head.ref` (attacker-controlled) and enqueues it via `Shipit::ReviewStackProvisioningQueue.add(stack)`. [2](#0-1) 

Existing guards do not prevent this: `verify_signature`/webhook signature checks only authenticate that the payload came from GitHub for *some* repository the attacker controls or owns — they do not gate on `review_stacks_enabled` at all. The `ExplicitParameters` schema validates payload shape, not business logic. No model validation on `Repository` or `Stack` enforces the `review_stacks_enabled` invariant across provisioning behaviors. The comparable `LabeledHandler` correctly guards this by requiring `repository.review_stacks_enabled` at the top level (`respond_to_label_change?`) before ever evaluating `archive?`/`unarchive?`, which confirms this omission in `OpenedHandler`/`ReopenedHandler` is inconsistent with intended design. [3](#0-2) 

The same pattern is duplicated in `ReopenedHandler#unarchive?`, which will re-provision or unarchive a stack the operator believed review stacks were disabled for. [4](#0-3) 

Downstream, provisioning eventually leads to `Command#start`/`PTY.spawn` execution during the stack's provisioning task (out of scope of this file, but this is the documented critical impact target for uncontrolled stack creation in this class of finding).

### Impact Explanation
An unprivileged, unauthenticated (relative to Shipit) external contributor who can merely open a PR and toggle a label on their own repository fork/branch can force `ReviewStack` creation and provisioning on a repository whose operator has explicitly disabled review stacks (`review_stacks_enabled = false`) but left `provisioning_behavior` at `allow_with_label` or `prevent_with_label`. This is repeatable per PR/branch and creates records/queues provisioning jobs that eventually execute build/deploy commands tied to attacker-controlled branch refs — matching the Critical impact category (unauthorized stack creation leading to command execution not authorized by the operator's stated configuration).

### Likelihood Explanation
Requires a specific but plausible misconfiguration: `review_stacks_enabled == false` combined with `provisioning_behavior` still set to `allow_with_label` or `prevent_with_label` (the UI/controller does not appear to force resetting `provisioning_behavior` when `review_stacks_enabled` is toggled off — confirmed by the settings view and repository model not encoding this invariant). Given this state, exploitation cost is trivial: open a PR, add/omit a label, no privileges or secrets needed.

### Recommendation
Require `repository.review_stacks_enabled` as a single top-level gate for all three disjuncts, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Apply the identical fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
In (non-`test/` scope excluded per rules, but described conceptually): a minitest test against `OpenedHandler` that builds a repository fixture with `review_stacks_enabled: false` and iterates `%w[allow_all allow_with_label prevent_with_label]` for `provisioning_behavior`, constructing PR payloads with/without the provisioning label as needed, and asserts `provision?` (via `process`/`ReviewStackAdapter.find_or_create!` not being invoked, or a public wrapper) returns `false` in all three cases. Under current code, the `allow_with_label` case (label present) and `prevent_with_label` case (label absent) both return `true`, contradicting the binding and confirming the vulnerability.
