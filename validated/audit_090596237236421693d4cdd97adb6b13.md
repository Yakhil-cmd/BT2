## Analysis

The reported bug class ("value acted on by security-critical code differs from the value actually verified/bound") has a concrete analog in Shipit's `Api::CCMenuController`.

### Title
Stack-scoped API tokens can read the CI status of any stack, not just the stack they were authorised for — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `stack_id`, and `Api::BaseController#stacks`/`#stack` enforce that scoping for every other API controller. `Api::CCMenuController` overrides `#stack` with an unscoped lookup, so a token that is only authorised for stack A can be used to read the build status of any other stack B.

### Finding Description
`ApiClient` can carry an optional `stack_id`, and the generic API access path restricts visibility to that single stack: [1](#0-0) 

This is the binding: `current_api_client.stack_id (authorised stack) == stack (touched stack)` for every stack-scoped operation reachable through `Api::BaseController`.

`Api::CCMenuController` inherits from `BaseController` and only requires the generic `read:stack` permission — it never re-checks `current_api_client.stack_id`. Worse, it completely overrides the `#stack` accessor with an unscoped lookup, and also accepts authentication via a `token` query-string parameter instead of only the `Authorization` header: [2](#0-1) 

`ApiClient#check_permissions!` only checks that the client has the `read:stack` permission string; it never checks which stack the permission applies to: [3](#0-2) 

So for any controller other than `CCMenuController`, `#stack` is `stacks.from_param!(...)` where `stacks` is filtered by `current_api_client.stack_id`. In `CCMenuController`, `#stack` is `Stack.from_param!(params[:stack_id])` — the scoping filter is dropped entirely. Any valid `read:stack` token, even one created with a specific `stack_id` (e.g. the `here_come_the_walrus` fixture, or any CI-status token minted by `CCMenuUrlController`), can be replayed against `/api/*/ccmenu` with a different `stack_id` parameter and will successfully render that other stack's build status, last build label (which includes the deployed commit SHA), lock state, and activity.

### Impact Explanation
This breaks the "stack a token authorises versus stack it touches" binding: the token's authorisation (`stack_id`) and the stack actually read (`params[:stack_id]`) are no longer equal, and the mismatch is unauthenticated to the caller who only needs any valid API token with `read:stack`. This is an unauthorized read of stack/deploy state belonging to a stack the token was never granted access to, which matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" achieved via a scope-confused, otherwise-legitimately-issued credential.

### Likelihood Explanation
Any holder of a stack-scoped `read:stack` API token (e.g. a CCMenu URL that a team shared, or any client an admin scoped to a single stack for least privilege) can trivially exploit this by changing the `stack_id` request parameter — no additional secrets, sessions, or GitHub credentials are required, only the already-issued (possibly narrowly-scoped) API token.

### Recommendation
Make `Api::CCMenuController#stack` go through the scoped `stacks` collection from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction is honored the same way it is for every other API controller.

### Proof of Concept
1. Create/observe an `ApiClient` scoped to `stack_id` = Stack A with permission `read:stack` (e.g. the `here_come_the_walrus` fixture, or a CCMenu token minted via `CCMenuUrlController#fetch` for Stack A: [4](#0-3) ).
2. Take that client's `authentication_token`.
3. Issue `GET /api/<stack-a-param>/ccmenu?token=<token>&stack_id=<stack-b-param>` (or via Basic Auth) where Stack B is a stack the client was never scoped to.
4. Observe that `Api::CCMenuController#show` renders Stack B's `deploys_and_rollbacks.last` (build status, lock state, last commit SHA) even though the token's `stack_id` only authorises Stack A, because `#stack` in this controller ignores `current_api_client.stack_id` entirely: [5](#0-4) .

```ruby
# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
```
