### Title
Global `credential.helper cache` with no `credential.useHttpPath` leaks credentials to attacker-controlled submodule/host paths, analogous to Maia's "same identifier, different owner" cross-context conflation - (File: main.go)

### Summary
`git-sync` sets a single, global git credential cache (`credential.helper = cache --timeout 3600`) and never configures `credential.useHttpPath`. Because git's `cache` credential helper matches stored credentials by `protocol://host` and (unless `useHttpPath` is set) ignores the URL path, any per-URL credential that git-sync stores via `StoreCredentials`/`git credential approve` for one repository can be replayed by git to a *different* path on the same host. This mirrors the Maia H-02 root cause: an identifier (there, an address; here, a `host`) is implicitly trusted to represent a single "owner"/context across different origins (there, different chains; here, different repo paths/submodules), when in fact different paths on the same host can be controlled by different, untrusted parties.

### Finding Description
`SetupDefaultGitConfigs` unconditionally sets: [1](#0-0) 
a global `credential.helper cache --timeout 3600`, with no corresponding `credential.useHttpPath true`.

Credentials are populated per-URL via `StoreCredentials`, which calls `git credential approve` with a `url=...` record: [2](#0-1) 
This is used both for the main `--repo` credentials, GitHub App tokens, askpass-URL responses, and — critically — for `--credential` entries meant to scope distinct usernames/passwords to distinct submodule URLs, as documented: [3](#0-2) 

Git's `credential-cache` daemon indexes cached entries by the fields it is given from `git credential fill`/`approve`. The `path` component is only forwarded to the credential subsystem when `credential.useHttpPath` is enabled for the relevant URL (git defaults this to `false`). Since git-sync never sets `credential.useHttpPath`, the cache effectively keys credentials by `protocol://host` only, for the lifetime of the 3600-second cache window.

The synced repository content (including `.gitmodules`) is attacker-influenceable data from the untrusted upstream repo: whoever can add/modify a submodule entry controls the submodule URL's *path* (and, in some deployments, its host too, if the host is shared, e.g. a self-hosted git server or a multi-tenant Git SaaS instance where different orgs share a host). Because the credential cache does not distinguish paths on the same host, when git needs credentials to fetch an attacker-added submodule that resolves to the *same host* as a previously-authenticated (legitimate) repo, git may present the cached, legitimate credential to whatever path the attacker specified — sending the secret to a server endpoint the attacker controls (e.g., their own repo under the same host, or a self-hosted instance where the attacker can create arbitrary paths).

This is the same class of bug as the H-02 finding: git-sync's `fetchVirtualAccount()` analog trusted a single "identifier" (`address`) to always represent the same principal across contexts (chains); git-sync's credential cache trusts a single identifier (`host`) to always represent the same principal across contexts (repo paths/submodules), without validating that the path-scoped owner matches.

### Impact Explanation
If exploited, this results in credential/token disclosure: the password, PAT, or GitHub App-derived token stored for a legitimate `--repo`/`--credential` entry can be transmitted by git itself to an attacker-controlled path on the same host during a submodule fetch, because the cache does not scope by path. This maps to the "credential or token disclosure" acceptable-impact category. The severity is amplified when GitHub App tokens or long-lived PATs with broad org/read access are used, since those are stored via the exact same `StoreCredentials` path and are equally subject to host-only cache scoping.

### Likelihood Explanation
Exploitability requires: (1) the attacker can influence `.gitmodules`/submodule URLs in the synced repository (this is intrinsic to how `--submodules` works — content of the tracked repo is inherently less trusted than the top-level `--repo` credential owner in multi-contributor or forked-PR scenarios), and (2) the attacker-controlled submodule resolves to the same host as a previously-cached credential within the 3600s cache window (default git-sync host reuse across submodules is explicitly documented and tested, e.g. `e2e::submodule_sync_over_http_different_passwords`). This is a realistic operational pattern for self-hosted Git servers or multi-tenant SaaS where multiple orgs/paths share one host, which is exactly the scenario git-sync's own docs anticipate by offering `--credential` per-URL. Likelihood is moderate: it requires shared-host submodules and a window where a broader-scoped legitimate credential is cached, but no privileged access or leaked keys are needed — only ordinary push/PR access to the tracked repository's submodule configuration.

### Recommendation
- Set `credential.useHttpPath=true` globally (or scope it per credential URL) in `SetupDefaultGitConfigs`, so the credential cache/helper distinguishes and confines each stored credential to its exact URL path, not just its host.
- Consider using distinct, isolated credential-helper cache sockets per repo/submodule URL, or reduce/eliminate the shared 3600s cache TTL for multi-tenant/self-hosted scenarios.
- Document that `--credential`/`--username`+password entries scoped to a host can bleed across paths on that host absent `useHttpPath`, and warn operators using self-hosted/multi-tenant Git hosts with submodules from less-trusted sources.

### Proof of Concept
1. Deploy git-sync against a legitimate `--repo=https://git.example.com/org/main-repo` using `--username`/`--password-file`, causing `StoreCredentials` to run `git credential approve` with `url=https://git.example.com/org/main-repo`: [2](#0-1) 
2. `SetupDefaultGitConfigs` has already configured the global `credential.helper cache --timeout 3600` with no `useHttpPath`: [4](#0-3) 
3. An attacker with push/PR access to `main-repo` (or a maliciously crafted upstream) adds a `.gitmodules` entry pointing to `https://git.example.com/attacker/evil-repo` — same host, different path.
4. On the next sync, git resolves and fetches the submodule; because credential lookup for the cache helper is host-scoped (no `useHttpPath`), git supplies the previously-cached `main-repo` credential to the request for `attacker/evil-repo`, and the attacker's git server (which they control) receives and can log the plaintext `username`/`password`.
5. The attacker now holds valid credentials for `org/main-repo`, which can be used well beyond the sync operation (e.g., for direct API/git access), constituting credential disclosure outside git-sync's intended trust boundary.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}
