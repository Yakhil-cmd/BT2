### Title
Operator-precedence bypass in `OpenedHandler#provision?` lets a PR author create a `ReviewStack` when `review_stacks_enabled` is false, and `CacheDeploySpecJob` unconditionally caches the attacker's `shipit.yml` into `stack.cached_deploy_spec` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` combines `review_stacks_enabled` with the provisioning-behavior checks using `&&`/`||` without parentheses, so Ruby's operator precedence only applies `review_stacks_enabled` to the `allow_all` branch; the `allow_with_label` and `prevent_with_label` branches ignore it entirely. A PR author who controls their own PR's labels can therefore get a `Stack` auto-created and provisioned even when the repository owner has `review_stacks_enabled = false`. Once created, `stack.rb`'s `after_commit :sync_github, on: :create` triggers `GithubSyncJob` → `CacheDeploySpecJob`, which checks out the attacker's branch and unconditionally writes the parsed `shipit.yml` (`tasks`/`ci`/`review`) into `stack.cached_deploy_spec`, with no re-check of `review_stacks_enabled` anywhere in that chain.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `provision_allowed == repository.review_stacks_enabled` for every `provisioning_behavior`. In code: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

Ruby's `&&` binds tighter than `||`, so this parses as:

```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```

`review_stacks_enabled` is only consulted in the first disjunct. If the repository's `provisioning_behavior` is `allow_with_label` or `prevent_with_label`, `provision?` returns `true` **regardless of `review_stacks_enabled`**, as long as the attacker's own PR does/doesn't carry the configured label. The identical bug is duplicated in `ReopenedHandler#unarchive?` [2](#0-1) .

Exploit flow:
1. Repository owner sets `provisioning_behavior = :allow_with_label` (or `:prevent_with_label`) and `review_stacks_enabled = false` (intending review-stack auto-provisioning to be off).
2. Attacker, an unprivileged GitHub user, opens a pull request from a branch they control and adds (or omits) the configured label on their own PR — no Shipit credentials needed, this reaches Shipit via the `pull_request` `opened` webhook.
3. `OpenedHandler#process` calls `ReviewStackAdapter#find_or_create!` [3](#0-2) , which creates a `Stack` with `branch: params.pull_request.head.ref` [4](#0-3)  — i.e., the attacker's own branch, and enqueues it for provisioning.
4. `Stack`'s `after_commit :sync_github, on: :create` callback [5](#0-4)  fires `GithubSyncJob`, which appends the attacker's commits and enqueues `CacheDeploySpecJob` whenever a spec is missing or commits changed [6](#0-5) .
5. `CacheDeploySpecJob#perform` checks out `stack.commits.reachable.last` (the attacker's HEAD) and writes `DeploySpec::FileSystem.new(path, stack)` into `stack.cached_deploy_spec` unconditionally — it only guards on `stack.inaccessible?`, never on `review_stacks_enabled` [7](#0-6) . `DeploySpec::FileSystem#cacheable_config` folds the attacker's `tasks`, `ci`, and `review` sections from `shipit.yml` straight into the cached spec [8](#0-7) .
6. `Stack#task_definitions` is delegated to `cached_deploy_spec` [9](#0-8)  and rendered to any authenticated Shipit user who opens the stack view (`app/views/shipit/stacks/_header.html.erb` and `all_tasks.html.erb`) [10](#0-9) [11](#0-10) , with no re-check of `review_stacks_enabled` at render time.

`CacheDeploySpecJob` itself is not buggy in isolation — it is *designed* to cache whatever `shipit.yml` exists on the tracked branch for any existing stack, and `review_stacks_enabled` is a creation-time gate, not a caching-time gate, for legitimately-created stacks too. The real defect enabling the attacker path is the precedence bug in `provision?`/`unarchive?`, which lets a stack exist (and thus get spec-cached) in a configuration the operator explicitly disabled.

### Impact Explanation
An unprivileged PR author against a repository configured with `provisioning_behavior: allow_with_label`/`prevent_with_label` and `review_stacks_enabled: false` can force creation of a live, provisioned `ReviewStack` tracking their own branch, with their `shipit.yml` `tasks`/`ci`/`review` config cached into `stack.cached_deploy_spec` and surfaced to any authenticated Shipit user (maintainers/operators) who views that stack's task list. If an operator later triggers one of the attacker-defined custom tasks, its `steps` execute as shell commands via `Command`/`PTY.spawn` on the deploy host — this is a Critical, repeatable authorization-bypass path (bypassing the intended `review_stacks_enabled` gate) leading to attacker-controlled command execution surfaced to legitimate operators. It is repeatable for any repository whose owner uses `allow_with_label`/`prevent_with_label` with `review_stacks_enabled` disabled.

### Likelihood Explanation
Requires the target repository to be configured with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible, documented configuration (e.g., an admin temporarily disabling review-stack auto-provisioning without changing the behavior/label settings). The attacker needs no privileges beyond opening a PR (and, for `allow_with_label`, adding a label to their own PR, which any PR author can do on their own pull request in many GitHub setups, or which could also be applied by a triaging maintainer inadvertently). No secrets, tokens, or webhook signature forgery are needed — the webhook is genuine.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all branches:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```
Apply the same fix to `ReopenedHandler#unarchive?`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb
test "does not create a stack when review_stacks_enabled is false, even with allow_with_label + matching label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Currently this assertion fails (a stack **is** created), proving the bypass. To demonstrate downstream caching:
```ruby
# test/jobs/cache_deploy_spec_job_test.rb
test "bypass-created stack caches attacker shipit.yml despite review_stacks_enabled=false" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }
  Shipit::Webhooks::Handlers::PullRequest::OpenedHandler.new(payload).process
  stack = repository.stacks.last

  dir = Pathname(Dir.tmpdir) # dir containing attacker's shipit.yml with malicious `tasks`
  StackCommands.any_instance.stubs(:with_temporary_working_directory).yields(dir)

  CacheDeploySpecJob.new.perform(stack)

  assert_equal false, repository.reload.review_stacks_enabled
  assert stack.reload.cached_deploy_spec["tasks"].key?("evil_task")
end
```
