### Title
PSM reserve accounting caps redemption by internal debt, not live external-asset balance, permanently locking rebasing-token yield - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm` lets any signed account deposit an "external" fungible asset into a per-instance reserve account and mint a 1:1 "internal" stablecoin, later burning the internal token to redeem the external asset back. Redemption is capped by an internally tracked debt counter (`PsmDebt`), not by the reserve account's live balance. If the configured external asset is a rebasing token (balance grows over time for all holders, e.g. an Aave-aToken-style asset), the surplus balance that accrues in the PSM's reserve account is unreachable by any extrinsic: neither depositors, the fee destination, nor governance can withdraw it. This is the direct FRAME analog of the Cally "vaults steal rebasing tokens' rewards" finding — a custodial pot that records a fixed accounting unit while the underlying asset silently grows, permanently orphaning the surplus.

### Finding Description
`mint` (`substrate/frame/psm/src/lib.rs:703-768`) transfers `effective_external` units of the external asset from the user into the PSM's per-instance reserve account (`psm_account`) and records the corresponding **internal-asset-denominated** debt in `PsmDebt::<T>::insert(&internal_asset, &external_asset, new_debt)` (line 757). This debt is a fixed accounting figure fixed at mint time and only moves via subsequent mints/redeems — it has no mechanism to track appreciation of the underlying external asset's balance.

`redeem` (lines 810-903) burns internal tokens and pays out external asset from the reserve, but the amount available is explicitly gated by `PsmDebt`, not by the reserve's live balance:
```rust
let current_debt = PsmDebt::<T>::get(&internal_asset, &external_asset);
ensure!(current_debt >= effective_internal_net, Error::<T>::InsufficientReserve);

let reserve = Self::get_reserve(&internal_asset, &external_asset);
if reserve < external_out {
    defensive!("PSM reserve is less than expected output amount");
    return Err(Error::<T>::Unexpected.into());
}
```
`get_reserve` (lines 1588-1593) queries the *live* fungible balance of `psm_account`:
```rust
pub(crate) fn get_reserve(...) -> BalanceOf<T> {
    T::Fungibles::balance(external_asset.clone(), &Self::psm_account(internal_asset))
}
```
This live-balance check is a defensive lower bound only — it never lets a redeemer take out **more** than `PsmDebt` allows. So if the external asset rebases upward (every holder's `balance()` including the PSM's reserve account increases passively, without any `mint`/`transfer` call), `get_reserve()` returns a growing number while `PsmDebt` remains unchanged. Redemptions are still bounded to `PsmDebt`, so the growing delta between live reserve balance and `PsmDebt` is money that no call in the pallet can ever release: there is no "sweep excess", "skim yield", or governance withdrawal function over the `psm_account` balance (confirmed by inspecting all dispatchables: `mint`, `redeem`, `create_psm`, `remove_psm`, `set_minting_fee`, `set_redemption_fee`, `set_max_debt`, `set_asset_ceiling_weight`, `set_asset_status`, `add_external_asset`, `remove_external_asset` — none touch `psm_account`'s balance directly). `remove_psm` even requires `total_psm_debt == 0` before removing the PSM, but it never verifies or drains the reserve account's actual token balance, and there's no path to reclaim the (now-orphaned) rebased surplus sitting in `psm_account`.

This mirrors the Cally report precisely: the vault (here, `psm_account`) records a fixed unit of account (`tokenIdOrAmount` in Cally, `PsmDebt` here) at deposit time, and later payouts are bounded by that stored figure rather than the live, possibly-inflated balance of the underlying token.

### Impact Explanation
Any yield/rebase interest accrued by an external asset used in a PSM instance is permanently and irrecoverably locked in the PSM's reserve account. No signed extrinsic, admin call (`full_admin`/`emergency_admin`), or root/governance-controlled path in `pallet-psm` can extract that surplus. This is a frozen-funds/lost-value bug rather than an attacker-exploitable theft: no privileged party benefits, and the loss simply accumulates as dead weight forever, unrecoverable even by future governance action (unless a runtime migration is shipped). Because the finding requires the runtime integrator to actually configure a rebasing token as an "external asset" for a PSM instance — a deployment/configuration choice rather than a protocol-level guarantee that is violated by an unprivileged attacker — this is best characterized as a Low/Informational design limitation for any deployment that lists a rebasing token, consistent with how the original Cally report was resolved ("acknowledged... we have no intention of supporting rebase tokens"). It does not fit the "Critical/High theft, unbacked issuance, unauthorized dispatch" categories requested by the analog method, because there is no unauthorized dispatch or economic attacker action — the mechanism only fires if a PSM operator deliberately approves a rebasing asset.

### Likelihood Explanation
Low. This requires a PSM `full_admin` to call `add_external_asset` with a rebasing token, which is a configuration decision, not something an unprivileged attacker can trigger. `pallet-psm`'s own documentation and onboarding checks (decimals snapshot, `MAX_DECIMALS_DIFF`, `Fungibles` metadata requirement) do not screen for rebasing behavior, so the risk is real if such an asset is ever listed, but no external adversary can force this outcome.

### Recommendation
Either (a) document that `pallet-psm` external assets must have non-rebasing/static-balance semantics (equivalent to Cally's "no intention of supporting rebase tokens" stance), or (b) add reserve-balance reconciliation: track `PsmDebt` and periodically/permissionlessly compare it against `get_reserve`, exposing a governed `sweep_excess_reserve(internal_asset, external_asset)` call that transfers `reserve.saturating_sub(PsmDebt-equivalent)` to `fee_destination` or back to depositors pro-rata, analogous to the mitigation Cally's reporters suggested (“track total amounts currently deposited and allow vault creators to withdraw excess on a pro-rata basis”).

### Proof of Concept
No PoC was executed. This finding is derived purely from static code review of `substrate/frame/psm/src/lib.rs` (`mint`, `redeem`, `get_reserve`) and an exhaustive scan of all dispatchables in the pallet's `#[pallet::call]` block, confirming the absence of any reserve-sweep/rebalance extrinsic. A concrete FRAME integration-test reproduction would require: (1) a mock `Fungibles` implementation whose `balance()` for the `psm_account` grows independent of `transfer`/`mint_into` calls (simulating a rebasing token), (2) calling `mint` to record `PsmDebt`, (3) advancing the mock rebase, (4) calling `redeem` to the full extent of `PsmDebt`, and (5) asserting `Fungibles::balance(external_asset, psm_account) > 0` with no remaining call path to retrieve it. This mock/test-harness construction was not built or run as part of this analysis, so the "guard failure" is established analytically from the source (no matching sweep/withdraw symbol found), not from an executed test with observed pass/fail output. Given the acknowledged-but-out-of-scope nature of the original Cally issue and the configuration-dependent (non-attacker-triggerable) nature of this analog, I am not confident this rises to a bounty-eligible severity under the stated Critical/High bar, and flag it primarily as a documented Low/Design-limitation analog rather than a definitively bounty-eligible submission.
