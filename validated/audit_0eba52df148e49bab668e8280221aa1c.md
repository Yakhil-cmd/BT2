### Title
Webhook signature verified against the organization named in `repository.owner.login`/`organization.login`, not against the repository/stack the payload actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification purely from attacker-controlled JSON fields inside the same unauthenticated request body: `params.dig('repository','owner','login')` or, as a fallback, `params.dig('organization','login')`. [1](#0-0) [2](#0-1) 

The signature check itself only proves that *some* secret configured for the organization named by that field produced the HMAC over the full raw body: [3](#0-2) 

This mirrors the analog bug class from the report: too little (or the wrong) surface of the payload is bound by the check relative to what is later trusted and acted on. In the smart-contract report, `dexFuncSignatureAllowList` checked 8 bytes when only the first 4 bytes (the actual selector used to route the call) mattered, decoupling the verified data from the data acted upon. Here, the verified/selected field (`repository.owner.login` / `organization.login`) is not cryptographically or logically bound to the field the downstream handlers use to resolve *which* repository/stack to write to (`repository.full_name`, commit SHAs, PR numbers, etc., as consumed by handlers such as `PushHandler`, `StatusHandler`, `PullRequest::*Handler`). Both fields live in the same attacker-supplied JSON blob; nothing forces `repository.owner.login` to equal the owner segment of `repository.full_name`.

In a single-organization Shipit deployment this is not exploitable because there is only one webhook secret. But Shipit explicitly supports multiple GitHub organizations configured with independent `webhook_secret`s under the `github:` config key (see `docs/setup.md` "Using Multiple GitHub Applications" and `config/secrets.development.shopify.yml`), each looked up through `Shipit.github(organization: ...)`. [4](#0-3) [5](#0-4) 

In that configuration, an attacker who legitimately controls (or has compromised) the GitHub App/webhook secret for one configured organization ("Org A") can forge an arbitrary JSON payload, set `repository.owner.login` (or `organization.login`) to `"Org A"` so `verify_signature` selects and successfully validates against Org A's secret, while setting `repository.full_name` (and other repository identifiers consumed later by the event handlers) to point at a stack belonging to a *different* configured organization, "Org B". The equality that should hold — `organization whose secret authenticated the request == organization/repository the handler subsequently mutates` — is broken.

### Impact Explanation
This crosses the credential boundary the rules call out explicitly: "an organization that authenticated versus the repository that is written." If exploitable end-to-end, it allows cross-repository writes/state changes (queued sync jobs, commit statuses, PR labels/merges depending on which handler processes the forged event) on a stack belonging to an organization the attacker does not control, using only credentials scoped to a different organization. That satisfies the Critical-impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability is conditional: it requires (a) the deployer to run Shipit in the documented multi-organization mode with more than one `github.<org>.webhook_secret` configured, and (b) the attacker to hold a legitimate webhook secret for at least one of those configured organizations. Given that Shipit explicitly documents and supports this multi-org configuration as a first-class feature, this is a realistic operating mode, not a hypothetical misconfiguration, and the attacker's own org's stacks are never protected data - it is the *other* organizations' stacks that get impacted. No `ApiClient` token, session, or GitHub App private key theft is required beyond the attacker's own (out-of-scope, self-owned) org credential.

### Recommendation
Do not derive the organization used for signature-secret selection from a field inside the same unauthenticated, attacker-controlled body that is later used to determine *what gets written*. Bind them: after choosing the organization for verification, re-validate that every repository-identifying field the handler will act on (`repository.full_name`, `repository.owner.login`) is actually owned by that same verified organization before dispatching to `Shipit::Webhooks.for_event(event)`, or reject the request if they diverge. Alternatively, verify the payload independently against every configured organization's secret and only trust the organization whose secret matches, then cross-check that this organization matches `repository.owner.login` used anywhere downstream.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `orgA` and `orgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-org instructions). [4](#0-3) 
2. As an entity that legitimately controls `orgA`'s GitHub App webhook secret, craft a `push` (or other handled) event payload with:
   - `repository.owner.login = "orgA"`
   - `repository.full_name = "orgB/some-tracked-repo"`
3. Compute `X-Hub-Signature: sha1=<hmac>` using `orgA`'s webhook secret over the full raw JSON body, per `DeliverySigner`/`verify_webhook_signature` logic. [3](#0-2) 
4. POST to `/webhooks`. `verify_signature` computes `repository_owner` as `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the HMAC check passes because it was signed with `orgA`'s own valid secret. [6](#0-5) 
5. `Shipit::Webhooks.for_event('push')` dispatches the parsed params, whose `repository.full_name` points at `orgB/some-tracked-repo`, to the push handler, which resolves and mutates the `orgB` stack, e.g., queuing a `GithubSyncJob`, exactly as shown for legitimate pushes in the test suite. [7](#0-6) 

Note: I was unable to fully inspect `app/models/shipit/webhooks/handlers/push_handler.rb` in this session due to a tool error on the final iteration, so the exact stack-resolution code path (how `repository.full_name` maps to a `Stack`/`Repository` record) is inferred from the test fixtures and naming conventions rather than directly cited; a follow-up review of that handler is recommended to fully confirm the downstream write path.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
