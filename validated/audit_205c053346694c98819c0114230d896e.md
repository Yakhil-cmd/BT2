### Title
`liquidate` has no minimum-seized parameter: a front-running partial liquidation can leave a liquidator repaying debt while seizing nothing - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
The bug class in the external report is "the liquidation path hard-codes the caller's minimum acceptable output to zero, so a sandwich/front-run turns the liquidator's swap into a gift." XOXNO Lending's `liquidate` has the same shape: the liquidator supplies `debt_payments` and a `seize_mode`, but no minimum-seized-collateral floor. The plan is recomputed at execution against live state, `require_non_empty_payments` is only enforced on `repaid`, and the protocol deliberately accepts a plan whose `seized` vector is empty while `repaid` is non-zero. A competing liquidator (an unprivileged address) can front-run a victim liquidation with a partial liquidation that shrinks the account's collateral to dust legs whose seizure rounds to zero; the victim's transaction then repays real debt tokens and receives nothing.

### Finding Description
`process_liquidation` in `contracts/controller/src/positions/liquidation/mod.rs` takes `debt_payments: Vec<HubPayment>` and `seize_mode` but no `min_seized`/`min_out` argument [1](#0-0) . The plan is built fresh inside the call from current account state via `build_liquidation_plan` [2](#0-1) , so any state change between the liquidator's simulation and execution silently reprices the deal.

Only the repayment side is required to be non-empty: `require_non_empty_payments(env, &result.repaid)` guards `repaid`, while `result.seized` is applied unconditionally — an empty seizure vector is a no-op in `apply_liquidation_seizures` / `apply_liquidation_share_credit` [3](#0-2) . In `build_liquidation_plan`, the only place an empty seizure is compensated is the *unbacked* insolvency branch (`unbacked_usd > 0 && seized.is_empty()` releases the repayment); on a solvent or partially-backed account with collateral legs that all round to zero seized units/shares, the repayment stands [4](#0-3) . The liquidation skill documentation confirms the executable behavior: "The contract accepts a liquidation that repays debt and seizes nothing, so the liquidator would pay and receive no collateral," and notes legs are dropped when seizure rounds to zero tokens or zero shares [5](#0-4) .

There is no compensation elsewhere: the repayments are pulled and the account's debt is written down before seizures are applied, and the measured-receipt rescaling `scale_seizures_to_received` only *reduces* seizure, never adds a floor [6](#0-5) .

### Impact Explanation
Theft of liquidator funds. The victim's debt-token transfers are real, irreversible repayments that improve the borrower's position, while the victim receives zero collateral — the exact payoff asymmetry of the zero min-out liquidation in the report, with the "sandwich" instantiated as a front-running partial liquidation plus the victim's stale-plan execution. The borrower (or the front-runner, who captures the bonus on their own leg) benefits at the victim's expense. Because `liquidate` is permissionless and `require_auth` is the liquidator's own [7](#0-6) , any unprivileged account can be the front-runner and any unprivileged account can be the victim.

### Likelihood Explanation
Soroban executes intra-ledger ordering decided by validators/sequencing, and liquidation bots necessarily simulate → sign → submit, leaving a window in which account state drifts. The front-running cost is low: the attacker runs an ordinary `liquidate` (or even `clean_bad_debt`-adjacent partial) that trims the collateral legs to sub-unit/dust sizes. Every seizure leg that "rounds to zero tokens or zero shares" is dropped from the plan [8](#0-7) ; once all legs are dropped the victim's accepted repayment is still pulled because only `repaid` is checked for emptiness. Repeated identical debt-token legs across hubs and Credit-mode share rounding widen the set of plans that collapse to zero seized legs. The protocol itself instructs integrators to defensively "reject an estimate whose `seized_collaterals` is empty," confirming the contract provides no such guard.

### Recommendation
Add an explicit minimum-seized floor to `liquidate`, e.g. `min_seized: Vec<HubPayment>` or a scalar `min_seized_usd_wad`, and revert (e.g. `InvalidPayments` or a dedicated `SeizureBelowMinimum`) when the executed plan's seized totals fall below it. At minimum, revert when `result.repaid` is non-empty but `result.seized` is empty — mirror the existing `unbacked_usd > 0 && seized.is_empty()` release path in `build_liquidation_plan` so a zero-seizure plan can never consume a repayment. Document the front-running surface (competing liquidations, oracle index restamps via `update_account_threshold`, borrower's own supply/dust manipulation) for integrators.

### Proof of Concept
1. Alice's account is below HF = 1 with two collateral legs: a large USDC leg and a tiny low-decimal leg, and ETH debt.
2. Victim liquidator simulates `get_liquidation_estimate`, sees a profitable seizure, signs `liquidate(victim, alice_id, [(ETH, x)], Transfer)` authorizing the ETH transfer.
3. Attacker (any unprivileged address) front-runs in the same ledger with `liquidate(attacker, alice_id, [(ETH, y)], Transfer)` sized so the remaining collateral legs each round to zero seized units/shares (the documented dropped-leg behavior).
4. Victim's transaction executes: `build_liquidation_plan` recomputes on the new state, `result.repaid` is still non-empty (debt remains, still below HF or in the band where partials are accepted), `result.seized` is empty.
5. `require_non_empty_payments(&result.repaid)` passes, `apply_liquidation_repayments` pulls the victim's ETH, `apply_liquidation_seizures` applies an empty vector, and the event records the repayment [9](#0-8) . The victim paid debt tokens and received nothing; the borrower's debt was repaid for free.

They are **not** index-aligned with the supply snapshot. The contract drops a
leg whose seizure rounds to zero tokens or zero shares (see
[math](../xoxno-lending/math.md#seizure-and-fees-per-collateral)), so the estimate is an ordered
**subsequence** of the supply positions. A borrower can hold a one-unit leg, and
every partial liquidation of that account then returns fewer legs than
positions. Do not reject such an account: a bot that requires one estimate leg
per supply position can be switched off by any borrower for the cost of one
stroop.

Estimate tuples omit hub ids, so recover each leg's `(hub_id, asset)` by walking
the ordered snapshot and matching each estimate leg, in order, to the next
supply position with the same asset. A supply position with no matching leg had
nothing seized from it. Reject the estimate only when a leg matches no remaining
supply position, or when the estimate is out of order.

Reject an estimate whose `seized_collaterals` is empty. The contract accepts a
liquidation that repays debt and seizes nothing, so the liquidator would pay
and receive no collateral.
