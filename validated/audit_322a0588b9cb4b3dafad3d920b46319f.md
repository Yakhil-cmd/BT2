### Title
Membership Handler never re-validates `Team#organization` against `params.organization.login` on repeat/lookup, letting a forged cross-org `Membership` grant persistent `Shipit.github_teams` access unaffected by legitimate removals - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` only sets `team.organization` inside the `find_or_create_by!` creation block, and `Team#add_member`/`Team#members.delete` never check `organization` at all, so once a `Team` row for a given `github_id` exists, every subsequent `added`/`removed` membership webhook mutates that same row regardless of which organization's webhook secret validated the request. Combined with `WebhooksController#verify_signature` selecting the HMAC secret via the attacker-controllable `organization.login` field of the payload itself, an attacker who controls a webhook secret for an unrelated Shipit-configured org can forge `added` events naming a real team's `github_id` and their own GitHub login as `member.login`, creating a `Membership` row that is never reconciled by the real owning organization's legitimate `removed` events for other users.

### Finding Description
The broken binding: `Team#organization` (set once, at row-creation time, to `params.organization.login`) must equal `params.organization.login` on every later membership event that mutates that same `Team` row — this is never checked.

Path:
- `WebhooksController#verify_signature` picks the verifying `GitHubApp` via `Shipit.github(organization: repository_owner)`, and `repository_owner` falls back to `params.dig('organization', 'login')` [1](#0-0) . For a `membership` event this "organization" value is entirely attacker-supplied JSON; if Shipit is configured with multiple GitHub apps (`Shipit.github(organization:)`/`github_app_config`), an attacker who legitimately owns a webhook secret for **their own** configured org can sign the payload with their own secret while claiming any `organization.login` string and any `team.id`/`member.login` values [2](#0-1) .
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` — the block (and thus the `organization` assignment) only executes on **creation**; on every later call with the same `github_id` the existing row is returned untouched [3](#0-2) .
- `Team#add_member` and the `removed` branch (`team.members.delete(member)`) operate purely through the `has_many :members, through: :memberships` association scoped by `team_id`; neither checks `organization` [4](#0-3) .
- `Membership` uniqueness is scoped to `user_id` + `team_id` only [5](#0-4) , so a forged membership for the attacker's own user and a legitimate membership for a real member coexist independently — deleting one never touches the other.
- `User#authorized?` (used by `force_github_authentication` on every request) is satisfied by `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [6](#0-5) , and `force_github_authentication` gates the entire app on this check [7](#0-6) .

No guard reconciles `Team#organization` against the currently-authenticating org on repeat webhook deliveries; `drop_unhandled_event` and `ExplicitParameters` only validate presence/shape of fields, not their provenance.

### Impact Explanation
Once the forged `Membership` exists, the named GitHub login gains standing in `Shipit.github_teams` for as long as that row exists. If that team is one of the configured `Shipit.github_teams`, and the attacker (or a colluding real GitHub account they control the login for) completes a genuine GitHub OAuth login with that login, `current_user.authorized?` returns true, unlocking the entire Shipit UI/API for every stack — deploy/rollback/lock actions across tenants, matching "escalation into `Shipit.github_teams` authorization" (High), bordering on Critical if that authorization is subsequently used to trigger unauthorized deploys. The forged row is not cleaned up by legitimate `removed` webhooks from the real organization because those only delete the specific real member's `Membership` row, leaving the attacker's row untouched — so the unauthorized standing persists indefinitely and independently of the real team's actual membership state, and is repeatable for any `github_id` the attacker can learn.

### Likelihood Explanation
Requires: (a) Shipit configured with the multi-org GitHub app schema (`github_app_config`) so the attacker legitimately controls a webhook secret for at least one configured org, (b) knowledge of the target team's numeric `github_id` (an integer, often enumerable/predictable or leaked via prior legitimate webhooks/API responses), and (c) the target team being listed in `Shipit.github_teams`. Attacker cost is a single signed HTTP POST to `/webhooks` per event, fully automatable and repeatable; no session, API token, or the real org's secret is ever needed. This is the same root cause as the previously-established cross-org collision precondition (attacker-controlled `organization.login` selecting the signing key in `verify_signature`); this question additionally shows the forged state is durable and cannot be self-healed by legitimate traffic.

### Recommendation
- In `WebhooksController#verify_signature`, do not let the payload's own `organization`/`repository.owner.login` value silently select which secret validates the signature for events whose target scope (team, repository) doesn't match; verify against the resource's actual known/persisted organization when one already exists.
- In `MembershipHandler#find_or_create_team!`, always compare the existing `Team#organization` (or the org that owns `github_id` per GitHub) against `params.organization.login` and raise/drop the event on mismatch instead of silently reusing the row.
- Scope `Team#add_member` / `team.members.delete` operations to also assert `team.organization == params.organization.login` before mutating, and consider scoping `Team.find_or_create_by!` lookups by `[organization, github_id]` rather than `github_id` alone.

module Shipit
  class MembershipForgeryPersistenceTest < ActiveSupport::TestCase
    test "a forged cross-org membership survives legitimate removal events for other members" do
      team = shipit_teams(:shopify_developers) # organization == "shopify"
      real_member = shipit_users(:walrus)      # legitimately added by shopify
      attacker_member = User.find_or_create_by_login!("attacker-login")

      # Precondition (established elsewhere): forged 'added' event, signed with an
      # unrelated org's webhook secret, claiming organization.login != team.organization,

      Shipit::Webhooks::Handlers::MembershipHandler.call(
        "action" => "added",
        "team" => { "id" => team.github_id, "name" => team.name, "slug" => team.slug, "url" => team.api_url },

      # Binding claimed broken: team.organization ("shopify") == params.organization.login ("attacker-org") -> false, never enforced

        "member" => { "login" => real_member.login }
      )

      team.reload
      refute team.members.include?(real_member), "real member should be removed"
      assert team.members.include?(attacker_member), "forged attacker membership must persist unaffected"
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
