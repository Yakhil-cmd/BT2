This is confirmed by `filterAttestedAddresses`, which finds *any* historical attestation unit ever issued by the given attestors up to `last_ball_mci`, with no mechanism to check whether the attestor has since revoked or superseded that attestation. This is the closest structural analog to the Keycloak bug: once a grant (an offline session / an attestation) is issued, the system treats it as permanently valid because there is no revocation record in the DB schema/query — only additive "attestation" units exist, and the `attested` opcode (`definition.js:904-915`) only checks for existence of *some* attestation, not the *latest* status.

### Title
Permanent trust from `attested` address-definition condition — no revocation of issued attestations - (File: definition.js)

### Summary
The oscript `attested` condition, used inside address definitions and asset spend conditions, grants authorization to any address for which *any* attestation unit was ever posted by a listed attestor. There is no concept of attestation revocation or expiry in the underlying data model, so once an attestor (e.g., a KYC/whitelist provider) attests an address, that authorization can never be withdrawn — mirroring the Keycloak flaw where a granted scope/session keeps being honored after the grantor revokes it.

### Finding Description
`validateAuthentifiers`'s `evaluate` function handles the `'attested'` opcode by calling `storage.filterAttestedAddresses(conn, {arrAttestorAddresses: arrAttestors}, objValidationState.last_ball_mci, [attested_address], cb)` and treating a non-empty result as satisfying the condition: [1](#0-0) 

`filterAttestedAddresses` performs a pure existence check against the `attestations` table for `main_chain_index <= last_ball_mci`, with no notion of "latest" state or revocation — any historically confirmed attestation unit is sufficient to satisfy the condition forever, exactly like an offline_access grant that keeps being honored by Keycloak after the scope is removed from the client.

Address definitions using `['attested', [address, [attestor,...]]]` are commonly used to build KYC-gated addresses, whitelists, or asset transfer conditions (`spender_attested` for assets). If an attestor mistakenly attests an address and later wants to revoke that trust (e.g., after finding fraud, sanctions, or a compromised identity), the protocol provides no mechanism to invalidate the previous attestation. The attestor can post additional "unattestation" data but there is no defined opcode/schema field that consumers of `attested` check to see if a *later* attestation superseded or nullified an earlier one — the query only requires *a* matching row to exist.

### Impact Explanation
Any asset issuer or address-definition author that relies on `attested` conditions to gate spending, KYC, or whitelist logic (a common oscript-level defined pattern, and explicitly supported by the `spender_attested` asset flag) cannot actually revoke access once granted. An attacker who obtained a legitimate attestation (later revoked by the attestor for cause) can continue to spend a KYC-gated asset or pass a whitelist-controlled definition indefinitely, since the validation logic in `definition.js` never distinguishes "current" attestation status from "any attestation ever posted." This can lead to unauthorized spending of KYC/whitelist gated assets after the intended revocation.

### Likelihood Explanation
This affects a single address-definition/asset-spend evaluation path reachable by any unit poster whose address (or whose output) is subject to an `attested` condition; no privileged network position or hub compromise is required — only a previously-issued attestation from the (currently or formerly) trusted attestor and a normal unit submission. Because attestations are a first-class oscript primitive intentionally used for asset-level and address-level access control, the reachable surface is broad and the trigger conditions (attestor revoking, address attested in error, compromised private key later revoked from attestor's whitelist) are realistic operational scenarios.

### Recommendation
Introduce a way to represent attestation revocation/expiry in the data model (e.g., a `revoked` flag or a "most-recent attestation wins" semantics with explicit un-attest payloads), and change `filterAttestedAddresses`/the `attested` opcode evaluation to consult only the latest, non-revoked attestation state for the given address/attestor set instead of any historical match.

### Proof of Concept
1. Attestor `A` posts an `attestation` unit attesting address `X` is KYC-approved.
2. Address `X`'s definition (or an asset with `spender_attested: true`) uses `['attested', ['this address', [A]]]` to gate spending.
3. `X` spends freely because the condition, evaluated via `definition.js:904-915` → `storage.filterAttestedAddresses`, finds the historical attestation row.
4. Attestor `A` later determines `X` should no longer be trusted (fraud/compliance) and stops vouching for it — but there is no on-chain mechanism to remove the previous attestation record, so step 3 continues to succeed indefinitely, i.e. the "session"/grant is never invalidated despite the issuer's intent.
