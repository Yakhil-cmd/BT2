### Title
Reentrant creator-fee draining via check-effects-interactions violation in `collect_creator_fee` / `collect_creator_fee_permissionless` — ([File: programs/cp-swap/src/instructions/collect_creator_fee.rs] / [File: programs/cp-swap/src/instructions/collect_creator_fee_permissionless.rs])

### Summary
Both `collect_creator_fee` and `collect_creator_fee_permissionless` snapshot `pool_state.creator_fees_token_0/1` into local variables, perform the token transfer CPIs, and only *afterwards* zero the `creator_fees_token_0/1` fields in `pool_state`. This is the same root-cause pattern as the reported bug (state that gates/limits a token release is not updated *before* the value-releasing operation), which allows the "amount owed" accounting to be consumed more than once when the outbound transfer can re-enter the instruction before the state is cleared.

### Finding Description
`collect_creator_fee` reads the accrued fees, calls `transfer_from_pool_vault_to_user` (which issues `token_2022::transfer_checked`), and only resets `pool_state.creator_fees_token_0/1 = 0` after both transfers complete: [1](#0-0) 

`collect_creator_fee_permissionless` follows the identical pattern, and is callable by anyone (fees always flow to the fixed `pool_creator`): [2](#0-1) 

The transfer is executed via `token_2022::transfer_checked`: [3](#0-2) 

If the mint used for `vault_0_mint`/`vault_1_mint` carries the SPL Token-2022 `TransferHook` extension, `transfer_checked` performs a CPI into the hook program configured on the mint before returning control to the caller. A malicious pool creator who controls the mint (and hence the hook program) can make that hook CPI re-invoke `collect_creator_fee_permissionless` (or `collect_creator_fee`) again — at that point `pool_state.creator_fees_token_0/1` has *not yet* been zeroed by the outer call, so the inner call reads the same non-zero balance and issues a second transfer from the vault for the same accrued fee amount. This mirrors the report's core flaw: increasing/consuming a bounded quantity without first confirming (and locking) that it hasn't already been consumed in the current call chain.

### Impact Explanation
A pool creator (unprivileged role explicitly in scope) who creates a pool with a Token-2022 mint carrying a transfer hook can drain more from the pool vault than the amount of fees actually accrued, at the expense of LPs — this is a direct theft of LP/vault funds and produces an insolvent pool (vault balance falls below what `vault_amount_without_fee` and LP redemption math assume), since `withdraw()` computes `total_token_0_amount`/`total_token_1_amount` by subtracting the (now stale/duplicated) fee bookkeeping from the vault balance: [4](#0-3) 

### Likelihood Explanation
Requires the attacker to be the pool creator (controls the mint used in the pool and its optional transfer-hook program) and to call the permissionless or creator-only collection instruction once fees have accrued from normal swap activity. Solana's CPI depth limit (max depth 4) bounds the re-entry to a single extra invocation per outer call, so the amplification is limited (roughly 2x per collection call) rather than unbounded, but it is fully attacker-triggered from a single transaction with no privileged signer needed beyond the pool-creator role the attacker already occupies by having created the pool.

### Recommendation
Apply checks-effects-interactions: zero out `pool_state.creator_fees_token_0` and `pool_state.creator_fees_token_1` (and update `recent_epoch`) *before* issuing the `transfer_from_pool_vault_to_user` CPIs in both `collect_creator_fee` and `collect_creator_fee_permissionless`, so any re-entrant call observes an already-cleared balance, analogous to the fix recommended in the report (verify/consume state prior to, not after, transferring value).

### Proof of Concept
1. Attacker creates a pool via `initialize_with_permission` using a Token-2022 mint for `token_0` that has the `TransferHook` extension pointing at an attacker-controlled hook program, and is granted the `Permission` PDA required for that path.
2. Normal swaps occur, accruing `pool_state.creator_fees_token_0 = F`.
3. Attacker (or anyone) calls `collect_creator_fee_permissionless`. Inside `transfer_from_pool_vault_to_user`'s `token_2022::transfer_checked` CPI, the Token-2022 program invokes the attacker's transfer-hook program (per the mint's `ExtraAccountMetaList`).
4. The hook program CPIs back into `collect_creator_fee_permissionless` with the same accounts; `pool_state.creator_fees_token_0` is still `F` (not yet zeroed by the outer call), so the vault transfers `F` again to `creator_token_0`.
5. Outer call resumes and finally zeroes the field, but `2F` has already been transferred to the creator instead of `F`, drained from the vault at LPs' expense.

pub fn transfer_from_pool_vault_to_user<'a>(
    authority: AccountInfo<'a>,
    from_vault: AccountInfo<'a>,
    to: AccountInfo<'a>,
    mint: AccountInfo<'a>,
    token_program: AccountInfo<'a>,
    amount: u64,
    mint_decimals: u8,
    signer_seeds: &[&[&[u8]]],
) -> Result<()> {
    if amount == 0 {
        return Ok(());
    }
    token_2022::transfer_checked(
        CpiContext::new_with_signer(
            *token_program.key,
            token_2022::TransferChecked {
                from: from_vault,
                to,
                authority,
                mint,
            },
            signer_seeds,
        ),
        amount,
        mint_decimals,
    )
}

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }
