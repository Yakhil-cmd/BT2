### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` triggers `Hook.emit(:deployable_status, victim_stack, ...)` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by SHA, without checking that the webhook's `repository.full_name` matches the repository owning the target `Commit`/`Stack`. `Commit#add_status` (via `create_status_from_github!`) then unconditionally fires `Hook.emit(:deployable_status, stack, ...)` for whatever stack that commit belongs to, using the victim stack's real hook configuration. Because Git SHAs are content-addressed and identical across forks/mirrors, an attacker who owns any repository sharing a commit SHA with a tracked victim repository (e.g. by forking it) can send a validly-signed webhook for their own repo and forge a `deployable_status` event that downstream consumers attribute to the victim's stack.

### Finding Description
The broken binding: the code implicitly assumes `payload.repository.full_name == commit.stack.repository.full_name` for any `Commit` matched by SHA, but this equality is never checked.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e., it authenticates that the payload genuinely came from **the org named in the payload's own `repository.owner.login`**. It proves nothing about any *other* repository.
2. `Webhooks.for_event('status')` dispatches to `Handlers::StatusHandler` (`app/models/shipit/webhooks.rb:19`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries **globally** across all stacks/repositories by `sha` alone — unlike, e.g., `Handlers::Handler#stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) or `PullRequest::OpenedHandler#repository`, which correctly scope lookups via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. `StatusHandler` never calls `repository_name`/`stacks` at all.
4. `Commit#create_status_from_github!` → `#add_status` (`app/models/shipit/commit.rb:165-169, 366-386`) fires:
```ruby
Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
```
using `stack` = whatever stack the SHA-matched `Commit` record belongs to — the victim's stack — sourced entirely from the attacker's own webhook delivery.

Attacker's exact request: fork or otherwise obtain a repository (`attacker/evil-repo`) that shares at least one commit SHA with a repository tracked by a victim Shipit stack (trivial via `git fork`, since forks retain identical SHAs, or by cherry-picking/rebasing a known commit). Configure that repo's own GitHub webhook (attacker controls their own repo's webhook secret entirely) to POST a `status` event to the Shipit host with `repository.full_name = "attacker/evil-repo"` and `sha` = the shared commit SHA, `state = "success"`. The signature check passes because it's verified against `attacker`'s own org/app credentials, which the attacker legitimately controls. `Commit.where(sha: ...)` matches the victim's `Commit` row (created from ingestion of the victim's real repo), and `Hook.emit(:deployable_status, victim_stack, ...)` fires, delivered to the victim stack's configured hooks (Slack, PagerDuty, custom CD trigger, etc.) with the attacker-controlled `state`/`description`/`context`.

Existing guards fail to close this: `verify_signature` only proves origin authenticity for the *named* repository in the payload, not that the named repository is the one actually owning the matched commit; `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape, not repository identity; there is no `repository`/`stack` scoping check in `StatusHandler` (contrast with `Handler#stacks` and `PullRequest::OpenedHandler#repository`, which do scope by `repository.full_name`).

### Impact Explanation
An attacker who owns/controls any GitHub repository (with a GitHub App/webhook they fully control) can inject arbitrary `deployable_status`/`commit_status` events for a victim's Shipit stack, as long as a shared commit SHA exists (a common occurrence for forks, vendored code, or shared history). This is a payload for one (attacker) repository writing state (`Status` records) and emitting hooks for another (victim) stack — matching the **Critical** category "a payload for one repository mutating another's stack, commit, task or team." Downstream hook consumers that trust the `stack` field of the `deployable_status` payload (Slack notifications, PagerDuty alerts, or third-party CD systems that gate deploy/promote/rollback actions on this webhook) can be manipulated into taking action (e.g., triggering an "auto-deploy on green CI" workflow) for the victim stack based on a forged status the attacker fully controls. This is repeatable against any stack whose repository shares a commit with an attacker-accessible repository.

### Likelihood Explanation
Preconditions: (1) the victim stack must already have ingested the shared commit (normal operation — commits are synced from GitHub pushes/PRs), (2) attacker needs their own GitHub repo with a webhook configured to POST to the Shipit host's `/webhooks` endpoint — entirely within attacker's own control, no victim or Shipit secrets required, (3) a shared commit SHA — trivially obtained by forking the victim's (often public) repository. Attacker cost is low and the attack is fully repeatable/scriptable against any stack.

### Recommendation
In `Shipit::Webhooks::Handlers::StatusHandler#process`, scope the `Commit` lookup by the repository named in the payload, mirroring `Handler#stacks`/`repository_name`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
(or otherwise verify `commit.stack.repository == Repository.from_github_repo_name(payload.dig('repository','full_name'))` before applying the status), so a webhook can only affect commits belonging to the repository it was authenticated for.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
```ruby
test "status webhook for repo A cannot forge deployable_status for repo B's stack with same sha" do
  victim_stack = shipit_stacks(:shipit) # tracks "shopify/shipit-engine"
  attacker_repo_full_name = "attacker/evil-fork"

  shared_sha = shipit_commits(:first).sha
  victim_stack.commits.first.update!(sha: shared_sha) unless shipit_commits(:first).sha == shared_sha

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # attacker legitimately owns evil-fork's webhook secret

  Hook.expects(:emit).with(:deployable_status, victim_stack, has_entries(commit: shipit_commits(:first))).never
  # Assert equality BEFORE: payload.repository.full_name ("attacker/evil-fork") != victim_stack.repository.full_name ("shopify/shipit-engine")
  # Assert AFTER fix: no Hook.emit(:deployable_status, victim_stack, ...) fires when repository.full_name mismatches commit's owning stack.

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'success', context: 'ci/attacker',
    repository: { full_name: attacker_repo_full_name, owner: { login: 'attacker' } }
  }.to_json
  post :create, body:, as: :json
end
```
This test asserts the binding `payload.repository.full_name == commit.stack.repository.full_name` and shows it is currently violated (current code fires `Hook.emit(:deployable_status, victim_stack, ...)` regardless of the mismatch, since `StatusHandler` never checks repository identity).
