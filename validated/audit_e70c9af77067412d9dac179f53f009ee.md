### Title
Missing slippage protection in AA-based exchange/AMM logic enables MEV sandwich attacks against AA trigger senders - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The reported issue concerns an AMM contract that computes swap output purely from pool reserves at execution time, with no user-supplied minimum-output ("slippage") parameter, allowing MEV bots to sandwich the trade. ocore ships an analogous pattern in its official AA example template, `uniswap_like_market_maker.oscript`, and the underlying execution model of Autonomous Agents (deterministic ordering of triggers by DAG `level` within one MCI) gives an attacker a concrete, low-cost way to guarantee their front-run/back-run units are processed immediately before and after a victim's swap trigger — reproducing the same MEV/sandwich risk described in the report.

### Finding Description
The bundled AMM template computes the swapped amount from the current on-chain balances at the moment the AA formula executes, with no bound supplied by the trigger sender: [1](#0-0) 

```
{ // exchange bytes to asset
	if: `{trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] == 0 AND var['mm_asset_outstanding']}`,
	init: `{
		$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
		$bytes_balance = balance[base] - trigger.output[[asset=base]];
		$p = $asset_balance * $bytes_balance;
		$new_asset_balance = round($p / balance[base]);
		$amount = $asset_balance - $new_asset_balance;
	}`,
	messages: [ ... pays $amount of $asset to trigger.address ... ]
}
```

There is no `trigger.data.min_amount` (or equivalent) check to bounce the trigger if the computed `$amount` falls below a sender-specified threshold. Any address (an "AA trigger sender") can trivially trigger this code path just by sending bytes to the AA.

Compounding this, AA trigger execution order in ocore is fully deterministic and computable in advance by any observer: once a unit's MCI becomes stable, all AA triggers addressed to AAs are collected and executed in this order: [2](#0-1) 

and later re-read/executed in the same order: [3](#0-2) 

Both orderings are `ORDER BY mci, level, unit, address` — i.e., ordered primarily by the DAG `level` of the trigger unit. An attacker who observes a pending (not-yet-stable) large swap unit in the DAG can:
1. Post a "front-run" unit with a `level` lower than the victim's swap (by choosing parents that exclude the victim unit, or by parenting off units earlier in the DAG) so it is executed first within the same MCI, moving the pool price against the victim.
2. Post a "back-run" unit with a `level` higher than the victim's swap (parenting the victim unit or units that include it) to be executed immediately after, capturing the price reversion.

Because MCI stabilization typically takes multiple units/some time to finalize, and the ordering rule is public and deterministic, an attacker does not need to win any fee auction (unlike Ethereum MEV) — they only need to control their unit's `level` relative to the victim's, which is achievable by choosing parent units appropriately before the batch becomes stable.

### Impact Explanation
Any user who interacts with an AA implementing this common (officially-documented) swap/AMM pattern can have their swap sandwiched: the attacker buys ahead of the victim (worsening the victim's execution price) and sells back afterward, extracting value directly from the victim's trade. This is a direct, unauthorized transfer of value from the victim's expected proceeds to the attacker, matching the "AA fund loss" impact category. Since this is a documented example template that AA authors are likely to copy or adapt when building token exchanges/AMMs on Obyte, the exposure is systemic to any deployed AA following this pattern, not merely a theoretical templating artifact.

### Likelihood Explanation
Likelihood is medium: the attack requires monitoring the DAG for large pending swap triggers and constructing appropriately-parented front-run/back-run units before the target MCI stabilizes — a capability well within reach of an automated bot, similar to mempool-watching MEV bots on other chains. No special privileges are required; any address can post AA triggers. The complexity is somewhat higher than a simple gas-price auction because `level` control requires DAG parent selection, but this is a mechanical, scriptable step, not a fundamental protocol restriction.

### Recommendation
- Update the official AMM/exchange AA example (and document the requirement clearly for AA authors) to require a `trigger.data.min_amount` (or `max_amount` for the paying side) and `bounce()` the trigger if the calculated output/input violates the caller-specified bound.
- Consider adding a companion "periphery" example AA/wallet flow that pre-computes the expected output off-chain and supplies the slippage bound in `trigger.data`, mirroring how Uniswap's router enforces `amountOutMin`.
- In general documentation for AA authors, explicitly call out that AA execution order is a public, deterministic function of DAG `level`, and that any AA whose behavior depends on mutable shared state (reserves, prices) accessed without a caller-supplied bound is inherently sandwich-able.

### Proof of Concept
1. AA `M` implements the bundled `uniswap_like_market_maker.oscript` swap logic (or an author-adapted version of it) holding `asset` and `base` reserves.
2. Victim posts unit `V` with `trigger.output[[asset=base]] = 10e9` bytes to `M`, expecting a computed `$amount` of `asset` based on current reserves. `V` is not yet part of a stable MCI.
3. Attacker observes `V` in the (unstable) DAG, and before its MCI stabilizes, posts:
   - Unit `F` (front-run): a small trigger to `M` selling `base` for `asset`, parented so its `level < level(V)`, guaranteeing it executes before `V` per the `ORDER BY level` rule in `main_chain.js`/`aa_composer.js`.
   - Unit `B` (back-run): parented on top of `V` (or units that include `V`), guaranteeing `level(B) > level(V)`, so it executes after `V` and sells the `asset` bought in `F` back for `base` at the now-inflated price.
4. When the MCI containing `F`, `V`, and `B` stabilizes, `handleAATriggers` executes them in `F → V → B` order, since the victim's `init` block computes `$amount` purely from `balance[$asset]`/`balance[base]` at execution time with no protection — the victim receives a worse rate than expected, and the attacker profits from the price round-trip, exactly reproducing the sandwich-attack scenario from the original report.
