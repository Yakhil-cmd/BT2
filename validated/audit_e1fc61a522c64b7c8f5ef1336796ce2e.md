### Title
Git credential cache is never revoked/rejected on rotation — stale or compromised credentials remain usable for the full cache timeout - (File: main.go)

### Summary
`git-sync` configures git's built-in `credential.helper` as an in-memory cache with a fixed one-hour timeout, and only ever calls `git credential approve` to add/refresh entries. There is no code path that ever calls `git credential reject` to invalidate a previously cached credential, so a rotated or compromised credential remains valid to any consumer of that cache for up to the full `--timeout` window, with no revocation mechanism — the same "approval granted but never revocable" bug class described in the external report.

### Finding Description
`SetupDefaultGitConfigs` sets `credential.helper` to `cache --timeout 3600` globally for the process: [1](#0-0) 

`StoreCredentials`, which is used by every credential-refresh path (static `--username`/`--password`, `--credential`, `--askpass-url`, and GitHub App token refresh), only ever calls `git credential approve`: [2](#0-1) 

The `refreshCreds` closure is invoked on every sync loop iteration to re-read password files and re-fetch dynamic credentials (askpass URL, GitHub App tokens), but it always calls `StoreCredentials`/`approve` — it never calls `git credential reject` on the old value before storing the new one: [3](#0-2) 

`git credential approve` for the `cache` helper simply re-inserts/overwrites the entry keyed by URL in the cache daemon; it does not invalidate any credential that has already been handed out via `git credential fill` to some other git operation that is mid-flight or that reads from the same cache socket. There is no `reject` call anywhere in the codebase, so once a credential is approved into the cache it stays valid until the 3600-second timeout expires, a full process restart is *not* sufficient to purge it (the `cache` helper backs onto a long-lived `git-credential-cache--daemon` process/socket which outlives a single `git-sync` invocation's temporary `GIT_CONFIG_GLOBAL` file), or the token naturally expires on the remote side.

### Impact Explanation
If a credential source is rotated because it was compromised (e.g., a leaked `--password-file` token, a compromised `--askpass-url` response, or a GitHub App installation token that should be revoked early), `git-sync`'s only remedy is to `approve` the new value — the old value is not explicitly purged from the cache daemon. Any process capable of querying the same `git-credential-cache--daemon` socket (same UID/user namespace as the git-sync container, e.g. via shared PID/IPC namespace, a compromised exec/webhook hook, or another process reachable within the same container) can still `git credential fill` and receive the stale/compromised credential for up to an hour after rotation. This is a persistent-authorization/credential-disclosure risk analogous to the reported NFT approval issue: authorization is granted once and cannot be actively revoked, only allowed to time out.

### Likelihood Explanation
This requires that some other reachable process share access to git-sync's git-credential-cache socket during the container's lifetime (e.g. through `--exechook-command`, a compromised process in the pod's namespace, or the operator relying on `--add-user`/shared filesystem configurations). It is not exploitable purely from a malicious upstream repo, ref, or webhook payload alone, and requires a pre-existing local foothold or misconfiguration to read from the cache socket. Likelihood is therefore low-to-moderate; the more directly attacker-reachable component is the missing reject/revoke logic itself, which is present in all configurations that use `--credential`, `--askpass-url`, or GitHub App auth.

### Recommendation
- Call `git credential reject` for the previous credential value/URL before or immediately after approving a rotated one in `refreshCreds` and in `RefreshGitHubAppToken`/`CallAskPassURL`.
- Consider lowering or making `credential.helper cache --timeout` configurable, and reject cached credentials on graceful shutdown or whenever a fetch/auth failure is observed (to force immediate re-fetch rather than reuse of a possibly-invalid cached secret).

### Proof of Concept
Not directly demonstrable purely as a remote/untrusted-repo attack in this codebase — this is a design gap (missing `git credential reject` calls) rather than a triggerable exploit path from attacker-controlled repo content, ref names, or HTTP requests to git-sync. It is included as it maps to the reported bug class (approvals granted and never revocable) but the practical exploitation requires an additional local access vector to the cache daemon that is outside git-sync's own attack surface.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

// SetupDefaultGitConfigs configures the global git environment with some
// default settings that we need.
func (git *repoSync) SetupDefaultGitConfigs(ctx context.Context) error {
	configs := []keyVal{{
		// Never auto-detach GC runs.
		key: "gc.autoDetach",
		val: "false",
	}, {
		// Fairly aggressive GC.
		key: "gc.pruneExpire",
		val: "now",
	}, {
		// How to manage credentials (for those modes that need it).
		key: "credential.helper",
		val: "cache --timeout 3600",
	}, {
		// Never prompt for a password.
		key: "core.askPass",
		val: "true",
	}}

	for _, kv := range configs {
		if _, _, err := git.Run(ctx, "", "config", "--global", kv.key, kv.val); err != nil {
			return fmt.Errorf("error configuring git %q %q: %w", kv.key, kv.val, err)
		}
	}
	return nil
}
