## Analysis

This maps to the report's core bug class — **a value used to authenticate/select a trust context is never checked against the value that is actually acted upon** — onto Shipit's webhook signature verification.

### The binding that should hold but doesn't
`organization whose secret validated the signature == organization/team actually mutated by the event handler`

`WebhooksController#verify_signature` selects *which* GitHub App/webhook secret to validate against using a field pulled straight out of the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` reads `repository.owner.login`, falling back to `organization.login` — but nothing forces these two independent JSON keys to refer to the same org in a given payload, and the attacker fully controls the raw body before it is ever verified.

`GitHubApp#verify_webhook_signature` trivially returns `true` whenever the selected tenant has no `webhook_secret` configured: [3](#0-2) 

Multi-tenant lookup of that config is by exact org name in `secrets.github`: [4](#0-3) 

Meanwhile, `MembershipHandler#process` decides which `Team` record to mutate purely by `params.team.id` (GitHub's numeric team id), and only sets `organization`/other fields **on creation** — if the team already exists (e.g., a real `Shipit.github_teams` entry synced earlier), the payload's `organization.login` is never consulted or cross-checked at all: [5](#0-4) 

That team membership feeds directly into authorization: [6](#0-5) [7](#0-6) 

### Exploit sketch
1. Deployment is multi-tenant (`secrets.github` keyed by org, as shown in `config/secrets.development.shopify.yml`) and at least one configured org has `webhook_secret: nil` (a directly supported, documented config value).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: membership`, body:
```json
{
  "action": "added",
  "team": { "id": <real github_id of an existing, authorized Team>, "name": "x", "slug": "x", "url": "x" },
  "organization": { "login": "<real target org>" },
  "member": { "login": "<attacker's own github login>" },
  "repository": { "owner": { "login": "<weak-org-with-no-webhook-secret>" } }
}
```
3. `verify_signature` resolves `repository_owner` → `"weak-org-with-no-webhook-secret"`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no valid `X-Hub-Signature` is even required.
4. `MembershipHandler` looks up the *real* Team by `github_id` (found, not created, so `organization.login` from the payload is discarded), and calls `team.add_member(member)`, adding the attacker's GitHub identity to a team listed in `Shipit.github_teams`.
5. Attacker completes normal GitHub OAuth login; `User#authorized?` now returns `true` because their `teams` include an id in `Shipit.github_teams`, granting them full authenticated access to the Shipit instance (deploys, rollbacks, API client creation, etc.) without ever holding a valid session, token, or the target org's webhook secret.

### Title
Webhook signature verification keys off an attacker-controlled organization field decoupled from the organization/team actually mutated by the handler, enabling authorization-team injection - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` chooses the GitHub App/webhook secret to validate a webhook against using `repository.owner.login` (falling back to `organization.login`) taken from the unauthenticated request body itself. `MembershipHandler` separately determines which `Team` record to update using only `team.id`, never cross-checking it against the org that was used to select the verification secret. In multi-tenant configurations, an attacker can pick an arbitrary configured tenant with no (or an attacker-known) `webhook_secret` to satisfy signature verification, while pointing the actual payload contents at a completely different, legitimate team/organization.

### Finding Description
The signature check and the effectual authorization mutation are bound to two different, independently attacker-supplied fields of the same unauthenticated JSON body: `repository.owner.login` (verification) vs. `team.id`/`organization.login` (mutation). `GitHubApp#verify_webhook_signature` returns `true` without checking anything when `webhook_secret` is blank for the org selected by `repository_owner`. `MembershipHandler#find_or_create_team!` only assigns `organization` on creation; for pre-existing teams (which is the case for any team already listed in `Shipit.github_teams`), the payload's claimed organization is not validated against the team being modified.

### Impact Explanation
This breaks the "organization authenticated == entity written" trust binding. It lets an unprivileged external requester add an arbitrary GitHub login to any pre-existing `Shipit::Team`, including ones enumerated in `Shipit.github_teams`. Following normal GitHub OAuth login as that identity, `User#authorized?` returns true, granting full authenticated access to the Shipit application — escalation into `Shipit.github_teams` authorization, matching the High severity bar in scope.

### Likelihood Explanation
Requires the target deployment to use Shipit's multi-tenant GitHub config (`secrets.github` keyed by organization, as documented/shipped in `config/secrets.development.shopify.yml` and `docs/setup.md`) and at least one configured tenant with an unset `webhook_secret`, or an org whose secret is otherwise known/controllable by the attacker. GitHub team ids are not secret and can typically be discovered via the GitHub API. No Shipit session, API token, or repository write access is required — only an HTTP request to the public `/webhooks` endpoint.

### Recommendation
Bind signature verification and event processing to the same, single authenticated organization value: require `verify_signature` to record which org's secret actually validated the request, and have every handler (starting with `MembershipHandler`) reject or ignore payload claims (`organization.login`, `team` identity) that don't match that authenticated org. Additionally, treat a missing/blank `webhook_secret` for a configured tenant as a hard misconfiguration (reject the request) rather than an implicit bypass.

### Proof of Concept
See exploit sketch above: craft a `membership` "added" webhook whose `repository.owner.login` selects a tenant with no `webhook_secret`, while `team.id` references an existing authorized team and `member.login` is the attacker's own GitHub account; POST it to `/webhooks` with any (or no valid) `X-Hub-Signature`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
