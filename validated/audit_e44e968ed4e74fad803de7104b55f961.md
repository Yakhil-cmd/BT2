### Title
Bridge `handle*Transfer` Functions Bypass `isRunning` and Locked-Token Status Checks, Allowing Asset Transfers When Bridge Is Stopped or Locked — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge exposes two asymmetric operation paths: a **request path** (user-initiated, outbound) and a **handle path** (operator-initiated, inbound). The request path enforces `isRunning`, `isLockedKLAY`, and `lockedTokens` status guards as emergency circuit-breakers. The handle path — `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — enforces **none** of these guards. When the bridge owner stops the bridge or locks specific assets as an emergency measure, bridge operators can still call the handle functions to transfer KLAY, ERC20, or ERC721 tokens out of the bridge contract, bypassing the owner's security controls entirely.

---

### Finding Description

The `BridgeTransfer` base contract defines `isRunning` as a global circuit-breaker: [1](#0-0) 

`BridgeTransferKLAY` adds a per-asset lock `isLockedKLAY`: [2](#0-1) 

The **request path** enforces both guards before any outbound transfer: [3](#0-2) [4](#0-3) [5](#0-4) 

The **handle path**, however, checks only `onlyOperators` and `nonReentrant`. Neither `isRunning`, `isLockedKLAY`, nor `lockedTokens` is checked before transferring assets to the recipient: [6](#0-5) [7](#0-6) [8](#0-7) 

The Go-layer relay (`handleRequestValueTransferEvent`) calls these handle functions unconditionally whenever a `RequestValueTransfer` event is observed on the counterpart chain, with no status pre-check: [9](#0-8) 

---

### Impact Explanation

When the bridge owner invokes `setRunningStatus(false)` or `lockKLAY()` / `lockToken(token)` as an emergency response (e.g., exploit detected, oracle manipulation, counterpart chain compromise), the intent is to halt all asset movement through the bridge. However:

- `handleKLAYTransfer` will still send KLAY from the bridge contract to any `_to` address specified by operators.
- `handleERC20Transfer` will still `safeTransfer` or `mint` ERC20 tokens to recipients.
- `handleERC721Transfer` will still `transferFrom` or `mintWithTokenURI` NFTs to recipients.

The exact corrupted value is the KLAY balance or ERC20/ERC721 token balance of the bridge contract: assets are drained to arbitrary recipients despite the owner's emergency stop being active. This is an unauthorized transfer of KAIA and bridged assets affecting system-managed funds.

---

### Likelihood Explanation

The bridge operator role is semi-trusted: operators are registered by the owner and must reach a configurable threshold to execute a handle transfer. In normal operation, the Go relay (`handleRequestValueTransferEvent`) automatically calls handle functions for every pending cross-chain request. If the owner stops the bridge mid-flight, the relay continues processing the backlog of pending `RequestValueTransfer` events from the counterpart chain, calling `handleKLAYTransfer` / `handleERC20Transfer` / `handleERC721Transfer` without any awareness of the stopped state. No malicious intent is required — the relay's normal operation is sufficient to trigger the bypass.

---

### Recommendation

Add `isRunning` and the relevant locked-token checks to each handle function, mirroring the request path:

```solidity
// In handleKLAYTransfer:
require(isRunning, "stopped bridge");
require(!isLockedKLAY, "locked");

// In handleERC20Transfer:
require(isRunning, "stopped bridge");
require(!lockedTokens[_tokenAddress], "locked token");

// In handleERC721Transfer:
require(isRunning, "stopped bridge");
require(!lockedTokens[_tokenAddress], "locked token");
```

Alternatively, introduce a shared `onlyRunning` modifier in `BridgeTransfer` and apply it to all six transfer entry points (both request and handle paths).

---

### Proof of Concept

1. Owner stops the bridge: `bridge.setRunningStatus(false)` — `isRunning` is now `false`.
2. Confirm: `bridge.connect(user).fallback({value: parseEther("1.0")})` reverts with `"stopped bridge"` (request path blocked).
3. Operator calls `bridge.connect(op1).handleKLAYTransfer(txhash, from, victim, parseEther("100"), nonce, blockNum, "0x")` — **succeeds**, emits `HandleValueTransfer`, and sends 100 KLAY to `victim`.
4. The bridge's KLAY balance decreases by 100 despite `isRunning == false`.

The same sequence applies with `lockKLAY()` active: `_requestKLAYTransfer` reverts with `"locked"`, but `handleKLAYTransfer` still executes the transfer. [6](#0-5) [7](#0-6) [8](#0-7)
