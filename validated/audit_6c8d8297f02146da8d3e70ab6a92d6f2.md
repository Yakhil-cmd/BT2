### Title
Cross-repository stack mutation via signature/target divergence in webhook owner vs. repository.full_name binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` used for HMAC verification solely from `repository.owner.login`, while every `Handler` subclass (via `Handler#stacks`/`repository_name`) resolves the target `Repository`/`Stack` solely from the independent `repository.full_name` field. Because both fields are attacker-controlled JSON in the same signed body, an attacker who legitimately controls `attacker-org` (and thus its real `webhook_secret`) can set `repository.owner.login = "attacker-org"` (so their own valid signature passes) while setting `repository.full_name = "victim-org/prod-stack"` (so the handler acts on the victim's stack).

### Finding Description
The broken binding: `repository_owner` (used for HMAC key selection) == organization owning `repository.full_name` (used by the handler to select the `Stack`). This equality is never enforced.

- `WebhooksController#verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [1](#0-0) [2](#0-1) , then calls `github_app.verify_webhook_signature(signature, request.raw_post)`, which just HMACs the raw body with that org's configured `webhook_secret` [3](#0-2) .
- Once verification passes, `create` dispatches the same raw JSON payload to handlers [4](#0-3) .
- Every `Handler` resolves its target stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')` — a completely separate JSON field from `repository.owner.login` [5](#0-4) .
- `PushHandler#process` uses `stacks` to call `stack.sync_github` [6](#0-5) , and `CheckSuiteHandler#process` uses `stacks` to call `schedule_refresh_check_runs!` on matched commits [7](#0-6) .
- `Repository.from_github_repo_name` simply splits the given `owner/name` string and looks it up, with no cross-check against the org that signed the request [8](#0-7) .

Exploit flow: attacker legitimately owns `attacker-org` in GitHub and it is configured in Shipit with its own real `webhook_secret`. Attacker crafts a JSON body where `repository.owner.login = "attacker-org"` but `repository.full_name = "victim-org/prod-stack"` (and for `PushHandler`, valid `ref`/`after` fields; for `CheckSuiteHandler`, a `check_suite.head_branch`/`head_sha` matching an existing victim commit). Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` — material they legitimately possess — and POSTs to `/webhooks` with `X-Github-Event: push` (or `check_suite`). `verify_signature` looks up `attacker-org`'s `GitHubApp`, verifies successfully, and the request proceeds. The dispatched handler then resolves `victim-org/prod-stack` via `full_name` and mutates it (triggers `sync_github`, or schedules check-run refresh) — no ownership check ties the org that signed the payload to the org named in `full_name`.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` schema in each handler only validates fields like `ref`/`after`/`check_suite.head_sha`, not that `repository.full_name`'s owner matches `repository.owner.login`; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` check in this unauthenticated webhook path at all — the whole model of this endpoint depends entirely on the (broken) signature-to-repository binding.

### Impact Explanation
An attacker with a legitimately-registered GitHub organization in Shipit (i.e., anyone who can get themselves added as a configured `GitHubApp` — a normal onboarding, not a privileged internal position) can forge fully-signed webhooks that mutate an arbitrary victim `Stack`'s state: triggering `Stack#sync_github` (which updates the stack's known commits/HEAD from GitHub using the app's real credentials) or forcing check-run refresh scheduling on the victim's commits. This is a cross-repository stack mutation — an unrelated tenant's webhook validly signed with attacker material causes state changes on a target repository/stack the attacker does not control. This is repeatable against any repository name in the system merely by changing `repository.full_name` while keeping the same valid attacker signature, and it works across all repositories/orgs currently registered in Shipit — full blast radius across tenants sharing this Shipit instance. This matches the Critical category: "a payload for one repository mutating another's stack."

### Likelihood Explanation
Preconditions: the attacker must have at least one `GitHubApp`/organization legitimately configured in the host Shipit instance (its own real `webhook_secret`), which is a normal, low-privilege configuration state for any org onboarded to the multi-tenant Shipit instance — not a privileged Shipit or GitHub role. The attacker needs no Shipit session, no `github_access_token`, no `api_clients_secret`, and no permissions on the victim's repository. Cost is trivial: craft one JSON body, compute one HMAC with their own known secret, and send an HTTP POST to `/webhooks`. It is fully repeatable and scriptable against arbitrary victim `owner/name` strings that exist as `Repository` records in the target Shipit instance.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`), enforce that the organization implied by `repository.full_name` (or by `organization.login` for events without an explicit repository) matches `repository.owner.login`/the org whose `webhook_secret` verified the signature, before dispatching to handlers. Concretely, derive the owner from `repository.full_name.split('/').first` and require it to equal `repository.owner.login` used in `verify_signature`, rejecting (422) any mismatch. Additionally, `Handler#stacks`/`repository_name` should validate that the resolved `Repository#owner` matches the verified signing organization rather than trusting `full_name` unconditionally.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Configure two `GitHubApp`s via `Shipit.github_apps`/`Shipit.stub(:github_apps, ...)` (or equivalent `Rails.application.config.x.shipit.github_apps` fixture used elsewhere in this test file): `attacker-org` with `webhook_secret: "attacker-secret"`, and `victim-org` with `webhook_secret: "victim-secret"`.
2. Create a `Shipit::Repository` and `Shipit::Stack` for `owner: "victim-org", name: "prod-stack"`, `branch: "master"`.
3. Build a `push` event JSON body: `{"ref": "refs/heads/master", "after": "<victim-sha>", "repository": {"full_name": "victim-org/prod-stack", "owner": {"login": "attacker-org"}}}`.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest('sha1', "attacker-secret", body)`.
5. POST to `/webhooks` with `X-Github-Event: push` and `X-Hub-Signature: signature`, raw body as constructed.
6. Assert response is `200 OK` (not `422`), i.e., `verify_signature` accepted attacker-org's own secret.
7. Assert `Shipit::Stack#sync_github` was called/enqueued for the `victim-org/prod-stack` stack (e.g., stub/mock `stack.sync_github` and assert it was invoked with `expected_head_sha: "<victim-sha>"`), proving attacker-controlled signature material against `attacker-org` mutated `victim-org`'s stack.
8. Equality check both sides: before — `repository_owner` (`"attacker-org"`) used for signature verification vs. owner of `repository.full_name` (`"victim-org"`) used by the handler — they diverge and the request is still accepted; after fix — the controller should reject when these differ, producing `422` instead of dispatching to `victim-org`'s stack.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
