## Finding

### Title
On-chain TWAP oracle (`ObservationState`) can be poisoned via a single-transaction vault-balance donation before `swap_base_input`/`swap_base_output` — ([File: programs/cp-swap/src/states/oracle.rs])

### Summary
The pool's cumulative price oracle treats the *instantaneous* spot price computed from live vault balances as representative of the *entire* elapsed time since the last observation, with no cap on price deviation per update. An unprivileged user can, within a single transaction, directly transfer tokens into a pool vault (a legitimate SPL token transfer to the vault ATA, bypassing `deposit`/`swap` accounting) immediately before invoking `swap_base_input` (or `swap_base_output`), skewing the spot price used to seed the next `Observation`. Because that skewed price is multiplied by the full `time_since_last_update` duration, it corrupts the pool's TWAP for as long as the gap between swaps, at the cost of only a temporary donation the attacker can recover in the same transaction (e.g. via a reverse swap). This mirrors the reported UniswapV2 `sync()`-based flashloan manipulation, mapped onto Raydium's own reserve-derived observation mechanism.

### Finding Description
`swap_base_input` computes swap parameters, including `token_0_price_x64`/`token_1_price_x64`, directly from the **live** vault token account balances passed in as `ctx.accounts.input_vault.amount` / `ctx.accounts.output_vault.amount`: [1](#0-0) 

These prices are computed via `PoolState::token_price_x32`, which is a pure ratio of the current (live) vault balances with no protection against a same-block/same-transaction balance skew: [2](#0-1) 

After the swap executes, this pre-trade spot price is written into the oracle via `observation_state.update(...)`: [3](#0-2) 

Inside `Observation::update`, the supplied price is multiplied by the *entire* `time_since_last_update` (the time since the last observation write, which can be arbitrarily long for low-activity pools) and accumulated — there is no bound on how much a single reported price can move the cumulative sum, and no requirement that intervening price movement be smoothed or capped: [4](#0-3) 

Because Solana executes instructions within a transaction sequentially against shared, mutable account state, an attacker can compose a single transaction that: (1) performs a raw SPL Token `transfer` (or `transferChecked`) directly into `token_0_vault` or `token_1_vault` (these are plain token accounts owned by the pool's PDA authority, with no restriction on who can receive tokens into them), then (2) calls `swap_base_input`/`swap_base_output` with a minimal trade amount. The pool program has no way to distinguish "organic" vault balance from a same-transaction donation, since `token_price_x32` is derived purely from the live balance. This is structurally identical to the reported attack: instead of calling Uniswap's `sync()` to force `reserves == balances` after a direct transfer, the attacker simply relies on Raydium always reading live balances, achieving the same effect for free.

### Impact Explanation
The `ObservationState` cumulative price is Raydium's on-chain analog of Uniswap V2's `price0CumulativeLast`/`price1CumulativeLast`, intended to give downstream consumers (lending markets, derivatives, other integrators) a manipulation-resistant TWAP. This mechanism can be poisoned at low cost by any unprivileged swapper: the attacker temporarily inflates one vault, executes a token-swap-triggering `update()` call that bakes the skewed price into the cumulative sum weighted by the full idle duration since the last swap, and then reverses the donation. Any protocol or off-chain consumer that reads this pool's TWAP for valuation, collateral pricing, or liquidation decisions can be misled, enabling theft or insolvent accounting in those integrations — the exact impact class described in the source report, reachable through in-scope instructions (`swap_base_input`/`swap_base_output`, `ObservationState` update) with attacker-chosen accounts and data in a single transaction.

### Likelihood Explanation
Likelihood is highest on newly created, low-volume, or thinly traded pools where the time gap between swaps (`time_since_last_update`) is large, maximizing the leverage of a short-lived balance skew. The attack requires no privileged access — only a standard SPL token transfer instruction and a normal `swap_base_input` call composed in one transaction — and the cost is bounded to slippage/fees on the reversing trade plus the temporary capital used for the donation (which can be flash-loaned).

### Recommendation
Do not let a single instantaneous, potentially-donation-skewed spot price be applied as constant over the full elapsed interval in `Observation::update`. Options include: sourcing the price strictly from state mutated only through accounted instructions (e.g., using `total_input_token_amount`/`total_output_token_amount` as tracked in `PoolState` rather than raw live token-account balances for oracle purposes), enforcing a maximum per-update price deviation/clamp, or requiring a minimum elapsed time/no-donation invariant check (e.g., reconciling vault balance against internally tracked reserves plus fees before trusting it for the oracle write) before permitting a price sample to be recorded.

### Proof of Concept
1. Identify a pool with a stale `ObservationState` (long `time_since_last_update`).
2. Build one transaction containing:
   - Instruction A: SPL Token `transfer`/`transferChecked` sending a large amount of `token_0` directly into `pool.token_0_vault` (no interaction with the Raydium program required).
   - Instruction B: `swap_base_input` with a minimal `amount_in` on the same pool.
3. Inside instruction B, `pool_state.get_swap_params` reads `input_vault.amount`/`output_vault.amount`, which already reflect the donation from Instruction A, producing a skewed `token_0_price_x64`/`token_1_price_x64` — see [5](#0-4) .
4. `observation_state.update()` bakes this skewed price into the cumulative sum weighted by the full idle duration since the last observation — see [4](#0-3) .
5. Instruction C (optional, same transaction): reverse-swap or withdraw the donated tokens back, leaving the attacker's net cost limited to fees/slippage while the pool's TWAP now reflects the manipulated price for the entire elapsed window until the next legitimate swap.

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
        Ok((
            token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,
