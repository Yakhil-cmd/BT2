## Analog Found

### Title
AA bounce() and default response payments hardcode the recipient to `trigger.address`, permanently locking assets whose issuer-defined `transfer_condition`/`is_transferrable` rule rejects that address - (File: `aa_composer.js`)

### Summary
The C4 report concerns `LiquidityPosition.collectLiquidity()`, which can only ever send withdrawn tokens back to `msg.sender`; if that address is blacklisted for one of the two tokens, both tokens become permanently unretrievable because no alternate recipient can be specified. The same "recipient is hardcoded, no override possible" pattern exists in ocore's Autonomous Agent (AA) engine: whenever an AA needs to refund/bounce received coins, it can only send them back to `trigger.address` — the very address that sent the funds — with no way to redirect to a different address. If the asset received has an issuer-defined `transfer_condition` (or `is_transferrable=false`) that rejects `trigger.address` as a valid recipient, neither the AA's normal response path nor its bounce fallback can ever successfully pay the asset out, and the funds become permanently stuck in the AA.

### Finding Description
`bounce()` in `aa_composer.js` builds refund messages for every asset present in `trigger.outputs` and always targets `trigger.address`, with no parameter to choose another recipient: [1](#0-0) 

The normal (non-bounced) AA response path is equally constrained: an AA script can only choose output addresses that it controls via `oscript`, but if it also can't satisfy an asset's transfer condition for any address it tries, the same failure occurs. Whichever asset payment message fails validation causes `sendUnit()`'s validation callback to error out, and the trigger's `revert()`/`bounce()` machinery is invoked, which again attempts to pay the same asset back to the same `trigger.address`: [2](#0-1) 

The reason a payment to `trigger.address` can be rejected is defined in core validation: an asset can have `is_transferrable=false` and/or a `transfer_condition` formula (evaluated via `Definition.evaluateAssetCondition`) that must be satisfied by the transfer's inputs/outputs: [3](#0-2) [4](#0-3) 

These conditions are fully attacker-controlled at asset-definition time (`transfer_condition` accepts arbitrary Definition-language filters on `address`, e.g. requiring the recipient to be a specific address, be attested, etc.): [5](#0-4) [6](#0-5) 

Because the recipient of a bounce/refund is always `trigger.address` and never configurable, any asset issuer can define an asset whose `transfer_condition` deliberately excludes the sending address as a valid recipient of a future transfer (for instance, requiring the output address to be attested, or to be one of a fixed whitelist that the actual trigger sender is not part of). If a user then sends such an asset into an AA (together with enough bytes to trigger it) in a way the AA cannot immediately forward onward to a satisfying address, both the AA's success path and its bounce path will fail the same `transfer_condition`/`is_transferrable` check when trying to pay it back to `trigger.address`. There is no mechanism in `bounce()` or the response-composition logic to pick a different, condition-satisfying recipient, so the asset balance remains stuck in the AA forever, exactly mirroring the `collectLiquidity()` issue where only `msg.sender` can ever be paid, and no alternate/whitelisted recipient can be supplied to break out of a blacklist-like restriction.

### Impact Explanation
Assets with restrictive `transfer_condition`/`is_transferrable=false` rules can become permanently frozen inside any AA that receives them and cannot itself satisfy the condition for a further transfer. This is an unrecoverable fund-freezing condition for AA balances — analogous to Medium severity fund lock-up in the reference finding — because the protocol offers no way (via oscript, bounce, or otherwise) to specify an alternate, condition-satisfying recipient for the refund/response payment.

### Likelihood Explanation
Reachable by any unprivileged user: an attacker (or even an unwitting asset issuer) defines an asset with a `transfer_condition` that excludes ordinary trigger senders as valid recipients, then sends that asset plus bytes to any AA whose logic would otherwise try to pay it straight back to `trigger.address` (the common, idiomatic AA refund/response pattern seen throughout the sample AAs, e.g. `test/samples/simple_aa.oscript`, `just_a_bouncer.oscript`). This requires no privileged access, only posting a normal payment/trigger unit. [7](#0-6) 

### Recommendation
Allow AA developers (and the core bounce mechanism) to redirect refunds/responses to an address other than `trigger.address` when the default recipient fails an asset's transfer condition — e.g., expose a configurable fallback/recipient in `bounce_fees`/AA definition, or let `oscript` explicitly override the bounce recipient per asset, similar to how Uniswap's `collect()` exposes a `recipient` parameter instead of implicitly using `msg.sender`.

### Proof of Concept
1. Attacker defines an asset A with `is_transferrable: true`, `transfer_condition` requiring the output address to be in a fixed set that does not include the attacker's own address (e.g., `["and", [[{"what":"output","field":"address"},{"address":"SOME_OTHER_ADDRESS"}]]]`-style filter via `Definition.validateDefinition`), following the rules validated in `validation.js` lines 2794-2827 and `aa_validation.js` lines 289-336.
2. Attacker sends units to fund the asset, then posts a payment of asset A (plus bytes) to a generic AA whose messages simply forward received non-base assets back to `trigger.address` (the common oscript idiom, cf. `test/samples/simple_aa.oscript`).
3. The AA's payment message to `trigger.address` fails the `transfer_condition` check in `validatePaymentInputsAndOutputs` (validation.js lines 2643-2658), causing `sendUnit()` to error and `revert()`/`bounce()` (aa_composer.js lines 1759-1783, 909-945) to run — which again tries to pay asset A back to the same `trigger.address` and fails identically.
4. Asset A's balance remains permanently stuck at the AA address; no oscript logic or protocol mechanism exists to redirect it to a condition-satisfying address.
