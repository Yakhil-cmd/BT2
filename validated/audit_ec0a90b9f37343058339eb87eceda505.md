## Analysis: Cross-domain replay of off-chain signed packages via `is_valid_signed_package`

The reported bug class (signed authorization data lacking a domain/chain identifier, allowing replay of a valid signature into an unintended verification context) maps onto ocore's off-chain signed-message primitive used by Autonomous Agents.

### Finding Description

Off-chain signatures accepted by AAs are built and verified through:
- `signMessage()` / `getSignedPackageHashToSign()`, which hashes only `{signed_message, authors, last_ball_unit, version}` — nothing that identifies *which* AA or *which* usage context the signature is meant for. [1](#0-0) 

- The oscript primitive `is_valid_signed_package(signed_package, address)` in the formula evaluator, which only checks that `address` signed `signed_package.signed_message` — it never binds the check to `this_address` (the consuming AA) or to any other execution-context identifier. [2](#0-1) 

- `signed_message.validateSignedMessage()`, which computes `unit_hash_to_sign` purely from the signed package contents via `getSignedPackageHashToSign` and validates the author's authentifiers against it — again with no reference to the specific AA/domain that will consume the signature. [3](#0-2) 

Because the hashed/signed payload carries no built-in domain separator (equivalent to `block.chainid` or a contract address in the EVM world), any two AAs (or two independent instances of the same AA template, e.g. two payment channels between the same pair of addresses) that accept a `signed_message` from the same counterparty address will accept an *identical* signature interchangeably, unless the AA author manually embeds a distinguishing field inside `signed_message` and explicitly checks it in the trigger logic.

The shipped `payment_channels.oscript` example demonstrates that this manual check is required and is easy to omit:
```
if (trigger.data.sentByPeer.signed_message.channel != this_address)
    bounce('signed for another channel');
if (trigger.data.sentByPeer.signed_message.period != var['period'])
    bounce('signed for a different period of this channel');
``` [4](#0-3) 

The presence of this manual guard in the official example confirms that the underlying primitive (`is_valid_signed_package`) itself provides no such protection — the guard is left entirely to each AA author, exactly as in the reported `claimBySignature` case where `chain.id` was omitted from the hashed data by the contract author.

### Impact Explanation

Any AA that verifies peer-signed off-chain messages via `is_valid_signed_package` without independently embedding and checking a unique domain identifier (its own address, asset, channel id, nonce/period, etc.) inside `signed_message` is vulnerable to replay: a signature a counterparty produced for one channel/instance/period can be resubmitted as a trigger to another instance (or a later state of the same instance) that shares the same signing address, causing unauthorized state transitions such as premature/duplicate fund release, double payment of the "spent" balance, or acceptance of stale/out-of-date balances — i.e., concrete unauthorized spending or fund loss for one of the counterparties.

### Likelihood Explanation

Likelihood is Medium: it requires an AA definition that (a) uses `is_valid_signed_package` to authorize a fund-moving action and (b) fails to embed and check a domain/instance-specific field in the signed message. This is a genuine, easy-to-miss omission for AA authors, since the base primitive gives no built-in protection and the correct pattern (as seen in the bundled sample) is non-obvious and must be reproduced by every AA author independently.

### Recommendation

Provide (or strongly encourage via documentation) a built-in domain-separation mechanism for `is_valid_signed_package`, e.g., automatically requiring/incorporating the verifying `this_address` (and optionally `asset`/AA version) into the hash computed by `getSignedPackageHashToSign`, or add a dedicated oscript check that binds a signed package to the calling AA address by default rather than leaving it entirely to manual embedding inside `signed_message`.

### Proof of Concept

1. AA "Channel-A" and AA "Channel-B" are both instantiated from the same payment-channel-style oscript template but omit the `channel != this_address` check that the reference implementation includes.
2. Peer signs a `signed_message` such as `{period: 3, amount_spent: 100}` intended for Channel-A, producing signature `S` over `getSignedPackageHashToSign`.
3. Because the hash never referenced `this_address`/channel, an attacker (the counterparty or a colluding party who obtained the message) submits the same `{signed_message, authors: [{address, authentifiers: {r: S}}]}` package as `trigger.data.sentByPeer` to Channel-B.
4. Channel-B's `is_valid_signed_package(trigger.data.sentByPeer, peer_address)` returns `true` since the signature and content check out for `peer_address`, even though it was never intended for Channel-B, letting the attacker force an unauthorized balance update/fund release there.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
