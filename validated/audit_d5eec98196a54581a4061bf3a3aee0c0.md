### Title
Arbitration service ("cut") fee accepted with only a loose `< 1` bound and no cap on the actual fee amount, allowing near-total user fund loss - (File: `arbiters.js`, `arbiter_contract.js`)

### Summary
When a user creates an arbiter contract, the wallet fetches the arbstore's fee ("cut") over HTTP and only validates that it is a number `>= 0` and `< 1`, with no meaningful upper bound and no confirmation flow shown to the trigger/payer before the shared address definition (which embeds this cut) is derived and used to move funds.

### Finding Description
`getArbstoreInfo` retrieves the arbstore's `cut` from an external endpoint and performs only a coarse sanity check: [1](#0-0) 

The only requirement is `cut >= 0 && cut < 1` — there is no reasonable ceiling (e.g. 5%, 10%, 50%), so a value like `0.999999` passes validation. This `cut` is then used directly, unmodified, to compute how the contract `amount` is split between the peer and the arbstore address inside the smart-contract shared address definition: [2](#0-1) 

There is no independent, protocol-level bound tying the cut to a small percentage; the only remaining sanity check is `arbstore_amount > peer_amount` in the completion path, which still allows the arbstore to receive up to 50% of the funds: [3](#0-2) 

This mirrors the reported bug class: a fee value is controlled by a party outside the paying user's control, validated with an overly permissive bound, and directly encoded into the payment/definition logic that moves the user's funds — with no user-facing cap or opt-out at the point the shared address (and therefore the payment split) is fixed.

### Impact Explanation
A user entering into an arbiter contract implicitly trusts the arbiter's declared arbstore `cut`. Because the accepted range is `[0, 1)` rather than a small bounded percentage, a malicious or compromised arbstore endpoint can advertise a cut approaching 100% (e.g., 99.9999%), causing the shared-address definition to route almost the entire contract `amount` to the arbstore address instead of the intended counterparty. This is a direct, protocol-enforced loss of user funds once the contract is paid and completed, not merely an off-chain trust issue, since the payment split is baked into the address definition that governs spending.

### Likelihood Explanation
Any user pairing with an arbiter is subject to whatever `cut` value that arbiter's arbstore reports at the time of `getArbstoreInfo`/`getInfo` (this value is fetched over HTTP and cached in-memory without further revalidation or on-chain attestation), so the trigger for the loss requires only that a user create/accept a contract routed through the affected arbstore — no privileged access is needed by the party setting the fee.

### Recommendation
Enforce a tight, protocol-defined upper bound for `cut` (e.g., a small single-digit percentage) instead of the current `< 1` check in `getArbstoreInfo`, and surface the exact cut value prominently to both contract parties before they sign, requiring explicit confirmation whenever the cut exceeds a conservative default threshold.

### Proof of Concept
1. Stand up (or compromise) an arbstore HTTP endpoint used by an arbiter and have it respond to `/api/get_info` with `{"address": "<valid_address>", "cut": "0.999999"}`.
2. A user creates an arbiter contract with that arbiter; `getArbstoreInfo` in `arbiters.js` accepts the value since `0 <= 0.999999 < 1`.
3. `deriveSharedAddress` in `arbiter_contract.js` computes `arbstore_amount = contract.amount - Math.floor(contract.amount * (1 - 0.999999))`, sending nearly the entire `contract.amount` to `arbstoreInfo.address` in the shared address definition.
4. When the payer completes the contract normally, the resulting payment sends almost all funds to the arbstore instead of the counterparty, per the logic in `complete()`.
