### Title
Unvalidated swap routes can execute attacker-controlled code under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts opaque caller-supplied swap routes and authorizes only the controller’s exact input-token transfer before invoking the configured router. Because route instructions select pool and token addresses dynamically, a malicious route can invoke an attacker-controlled pool that requests an unrelated token transfer from the account owner while that owner’s controller authorization is active. If the owner signs the simulated authorization tree containing that child transfer, the transaction can both satisfy the swap’s measured-output checks and steal unrelated wallet funds.

### Finding Description
`swap_tokens` snapshots the controller’s token balances and registers a single exact `token_in.transfer(controller, router, amount_in)` authorization, but the caller-controlled `StrategySwap` remains an opaque byte payload passed to `execute_strategy`. [1](#0-0) 

The controller checks only that the router did not overspend controller-held input and produced a positive controller output; it does not inspect pool addresses or other calls reachable through the route. [2](#0-1) 

On the router side, each swap instruction resolves `pool`, `token_in`, and `token_out` from the payload-controlled asset registry and dispatches to the selected venue. [3](#0-2)  The Aquarius adapter invokes the payload-selected pool’s `swap` entrypoint. [4](#0-3) 

Account strategy calls first require the named caller’s authorization. For example, `swap_collateral` reaches this route path after `caller.require_auth()`; consequently, a nested contract that invokes `token.transfer(victim, attacker, amount)` adds a victim-address authorization child to the simulated tree. If the victim signs that poisoned tree, the host accepts the transfer even though it is unrelated to the lending operation. The existing harness demonstrates this Soroban authorization behavior and shows the transfer succeeding when the signed tree contains the rogue child invocation. [5](#0-4) 

### Impact Explanation
A malicious route supplied through a compromised interface, quote provider, phishing flow, or malicious transaction builder can steal unrelated tokens held by the account owner while executing an apparently successful lending strategy. The malicious pool can satisfy router accounting by consuming the authorized input and returning enough output to satisfy the route minimum, so neither the controller’s balance-delta checks nor final account-risk checks prevent the theft.

This is theft of user funds rather than merely a bad exchange rate: the stolen transfer can name a token and amount outside the routed collateral entirely. Loss is bounded by what the victim signs in the authorization tree, but ordinary wallet UX may not make a nested transfer under a lending invocation sufficiently obvious.

### Likelihood Explanation
Exploitation requires the victim to authorize a transaction whose simulation-generated authorization tree includes the malicious child transfer. An attacker cannot call `swap_collateral` for a victim without that victim’s signature, so this is not a fully unauthenticated theft.

The attack surface is nevertheless realistic because `swap` is deliberately opaque and externally constructed, while users commonly rely on route bytes produced by an off-chain service or frontend. The controller provides no protocol-level venue or pool admission check to prevent arbitrary contracts from running under the caller’s authorization context.

### Recommendation
Do not allow opaque strategy routes to invoke arbitrary pool or token contracts from a call tree protected by the account owner’s authorization. Prefer governance-managed venue/pool admission, or have the controller decode and enforce a strict allowlist of expected venue contract addresses and token addresses before invoking the router.

Additionally, consider separating user account authorization from downstream swap execution where Soroban authorization semantics permit it, and require clients to reject any simulated authorization tree containing children other than the expected protocol token movements.

### Proof of Concept
1. Deploy a malicious contract exposing an Aquarius-compatible `swap` function.
2. Construct a controller `swap_collateral` call for a victim account, with a payload whose `pool` index resolves to the malicious contract and whose declared output meets the route minimum.
3. The controller authorizes only its own input transfer and invokes the configured router. [6](#0-5) 
4. The router resolves the malicious pool from the supplied asset registry and invokes its `swap` function. [7](#0-6) [8](#0-7) 
5. The malicious pool:
   - accepts or pulls the authorized router input so the measured spend matches;
   - invokes `VictimToken.transfer(victim, attacker, victim_balance)`;
   - returns or transfers enough `token_out` for the route to pass measured-output and minimum-output checks.
6. Simulation places the victim-token transfer under the victim’s authorization tree. If the victim signs that tree, the pool call executes the unrelated transfer; the harness’s malicious-pool test demonstrates that the signed poisoned tree permits the transfer and drains the victim wallet balance. [9](#0-8)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
