### Title
`status` webhook flips checks/deployability for commits in *any* stack sharing a SHA, not just the authenticated repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, which is a bare, unscoped lookup across the entire `commits` table — not filtered by the repository that the webhook's signature was verified against. `WebhooksController#verify_signature` only checks that the payload's `repository.owner.login` matches a configured GitHub App/org; it never confirms that the commit being updated actually belongs to that repository/stack. Any commit sharing the attacker's SHA in a different stack (e.g. because of shared git history, forks, or cherry-picks/identical trees) will have its status/check state mutated by the attacker's legitimately-signed webhook for their own repo.

### Finding Description
The broken binding is: `commit.stack.repository == repository_owner_from_verified_webhook_payload` should always hold for any commit whose status is mutated by a webhook. In `StatusHandler#process`: [1](#0-0) 

`Commit.where(sha: params.sha)` is a global, unscoped ActiveRecord query with no join/filter on `stack` or `repository`, so it iterates over every commit row across every stack in the Shipit instance that shares the given SHA, and calls `commit.create_status_from_github!(params)` on each one.

`WebhooksController#verify_signature` only establishes that the raw payload was signed by the GitHub App belonging to `repository_owner` (derived from `params.dig('repository','owner','login')`): [2](#0-1) 

This proves the webhook came from GitHub for *some* repo owned by that org/user — the attacker's own repo, which they legitimately control. It proves nothing about which commits the `sha` field is allowed to affect. `StatusHandler` never re-checks `params.repository` against the commit's `stack.repository`.

Attack flow: the attacker owns (or controls) a GitHub repository registered with Shipit (or any org Shipit trusts). They arrange for a commit with the same SHA as a commit that also exists in a victim's stack — this happens naturally with forks (shared git history/objects), cherry-picked/squashed commits with identical trees, or content-identical empty/no-op commits — then trigger (or replay) a real, GitHub-signed `status` event with `context: shipit/checks`, `state: success` for that SHA from their own repository. `verify_signature` passes because the signature is valid for the attacker's own org. `StatusHandler#process` then updates `create_status_from_github!` on *every* `Commit` record matching that SHA, including the victim's, via `Commit#add_status` → `statuses.replicate_from_github!` → recomputes `status`/`deployable?` and triggers `stack.schedule_merges` when the new status is `success`: [3](#0-2) [4](#0-3) 

For a victim stack with `review_stacks_enabled true, allow_all`, external PRs auto-provision review stacks that execute `shipit.yml`; forcing `shipit/checks` to `success` via this cross-tenant write can force `deployable?` to flip and `schedule_merges`/continuous delivery to run, i.e. drive a deploy/merge on a stack the attacker never authenticated against.

None of the existing guards prevent this: `verify_signature` authenticates the webhook's origin org, not the target of the `sha`; `drop_unhandled_event` only filters unrecognized event types; the `ExplicitParameters` schema on `StatusHandler` only validates types (`sha`, `state`, etc.), not ownership; there is no `Repository`/`Stack` scoping anywhere in the `process` method.

### Impact Explanation
This is a payload for one (attacker-controlled) repository mutating another (victim) stack's commit status — exactly the "payload for one repository mutating another's stack/commit" Critical class. Concretely, an attacker can force a `shipit/checks`/other required-context status to `success` (or `failure`/`error` to block) on a victim's commit that they never authenticated for, potentially triggering `schedule_merges`/continuous deployment and, when combined with `review_stacks_enabled: true, allow_all`, execution of `shipit.yml` in an auto-provisioned review stack. This is repeatable against any stack/commit whose SHA the attacker can reproduce or predict, and the blast radius spans all tenants/stacks hosted on the same Shipit instance whose commits happen to share a SHA with attacker-controlled repos.

### Likelihood Explanation
Preconditions: attacker needs a GitHub repository (or org) already recognized/configured for a `Shipit::GithubApp` in the target Shipit deployment (this is typically low-cost — any repo under an org Shipit is configured to service, or a public fork of the victim's repo, which shares git object history/SHAs by construction). No Shipit session, API token, or secret is required — the webhook signature is real, generated by GitHub for the attacker's own event. The main constraint is producing/observing a SHA collision with the victim's stack, which is trivially satisfiable via forking (identical parent commits share SHAs) or through content-identical commits. Given forks are the most common Shipit review-stack workflow, this is highly feasible and repeatable at will.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and analogously in `CheckRun`/other SHA-based handlers) to the repository the webhook was verified for, e.g. join through `stack` to `repository` and filter by `params.repository.full_name` (or the equivalent verified owner/name) before applying `create_status_from_github!`, mirroring how other handlers scope by `Repository.find_by!(...)`.

### Proof of Concept
minitest plan:
1. Create two stacks `victim_stack` (repository `victim/repo`, `review_stacks_enabled: true`, `allow_all`, `required_statuses: ['shipit/checks']`) and `attacker_stack` (repository `attacker/repo`).
2. Create a `Commit` in each stack with the identical `sha` value (simulating shared git history/content).
3. Build a `status` webhook payload with `sha` = shared SHA, `context: 'shipit/checks'`, `state: 'success'`, `repository.owner.login` = `attacker`.
4. Stub `verify_signature`/`GithubApp#verify_webhook_signature` to succeed for `attacker` org only (as it legitimately would).
5. POST to `/webhooks` with `X-Github-Event: status` and the above payload.
6. Assert: BEFORE — `victim_commit.deployable?` is `false` / `victim_commit.status.state != 'success'`. AFTER — `victim_commit.reload.deployable?` becomes `true` and/or `victim_commit.status.state == 'success'`, proving the attacker's webhook (signed only for `attacker/repo`) mutated `victim/repo`'s commit and stack (`stack.schedule_merges` invoked), violating "a `shipit/checks` status affects only the repository that authenticated it."

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
