### Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while every event handler acts on the attacker-controlled `repository.full_name` - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is an analog of the Hats "claim vs. reconcile use different, inconsistent state" bug class: one code path checks/authenticates against field A, while the code path that actually performs the privileged action uses field B, and nothing binds A to B. In Shipit, `WebhooksController#verify_signature` authenticates the *organization* using `repository_owner`, but `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` (used by every handler, e.g. `PushHandler`) resolves the *repository to act on* using a different, independently attacker-supplied field, `repository.full_name`.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App config (and thus which `webhook_secret`) to use for HMAC verification based on: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

That value is only used to select `Shipit.github(organization: repository_owner)` for signature verification (`verify_webhook_signature`) at [3](#0-2) . It is never checked against the repository that is actually operated on.

Every event handler instead determines the target repository/stacks from a completely separate JSON field, `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler`, for example, uses `stacks` (resolved from `repository.full_name`) to trigger `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack whose branch matches: [5](#0-4) 

The binding that should hold is: `organization authenticated by signature == organization of repository acted upon`. It does not hold, because:
- `repository_owner` (used for signature selection) reads `repository.owner.login` (or `organization.login`).
- `repository_name`/`stacks` (used for action) reads `repository.full_name`, an independent string field.

This matters specifically in Shipit's documented multi-org configuration, where each GitHub organization has its own `webhook_secret` (see `lib/shipit.rb#github_app_config`, `github_organizations`, and the multi-org example in `docs/setup.md`). An attacker who legitimately controls one onboarded GitHub organization (`attacker-org`) — and therefore genuinely knows `attacker-org`'s `webhook_secret` and can produce a valid `X-Hub-Signature` — can craft a webhook payload where:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
`verify_signature` will select `Shipit.github(organization: "attacker-org")` and compute a valid HMAC using `attacker-org`'s real secret — which the attacker knows — over `request.raw_post` (the whole crafted body, so the signature stays valid regardless of what `full_name` says). The signature check passes. `PushHandler` then resolves stacks via `repository.full_name = "victim-org/victim-repo"` and calls `stack.sync_github(expected_head_sha: <attacker-controlled sha>)` on the victim's stack — an organization Shipit never authenticated this request for.

### Impact Explanation
This crosses the "organization authenticated versus the repository that is written" trust boundary explicitly called out in scope: a signature genuinely produced with organization A's real webhook secret is accepted as authorization to act on organization B's repository/stack state (triggering GitHub syncs, commit-status writes, check-run refreshes, membership/team writes, pull-request-driven merge-queue actions, etc., depending on which handler is invoked). Depending on the handler this can influence merge-queue behavior and deploy readiness computations (`merge_status`, CI status records) for a repository the attacker was never granted access to, and in aggregate weakens the webhook trust boundary used across the entire `Shipit::Webhooks::Handlers` tree, since `Handler#repository_name`/`#stacks` is the base class used by all handlers (push, status, check_run/check_suite, membership, pull_request/*).

### Likelihood Explanation
Exploitation only requires the attacker to control (own an app installation for) at least one GitHub organization that is configured in Shipit's multi-org `secrets.github` block — a scenario the codebase explicitly supports and documents (`github_app_config`, `TOP_LEVEL_GH_KEYS`, multi-org example in `docs/setup.md`). No Shipit session, API token, or repository write access to the victim org is needed; the attacker only needs to be able to send an HTTP POST to `/webhooks` with a body they sign using their own org's known secret. This is a realistic, low-effort setup for any Shipit deployment onboarding more than one organization.

### Recommendation
Bind the authenticated organization to the repository actually acted upon. In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), after verifying the signature for `repository_owner`, additionally require that `repository.full_name`'s owner segment matches the authenticated `repository_owner` (case-insensitively) before dispatching to handlers; reject (422) on mismatch. Equivalently, `Handler#repository_name`/`#stacks` should be constrained to repositories belonging to the same organization that was used to select the webhook secret, not an independently attacker-controlled field.

### Proof of Concept
1. Deploy Shipit with the multi-org config schema (`secrets.github` keyed by organization, per `docs/setup.md`), including a legitimate, attacker-owned organization `attacker-org` (with its own `app_id`/`webhook_secret`) alongside the victim's `victim-org`.
2. Attacker computes `sig = HMAC-SHA1(attacker-org.webhook_secret, raw_body)` for a crafted `raw_body`:
```json
{"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/main","after":"<any_sha>"}
```
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<sig>`.
4. `WebhooksController#verify_signature` computes `repository_owner == "attacker-org"`, calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(sig, raw_body)`, which succeeds because the attacker used the correct (their own) secret.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, whose `stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<any_sha>")` on the victim's stack — an action performed on `victim-org` despite the request only ever being authenticated for `attacker-org`.

Note: I was not able to fully trace downstream effects of `sync_github`/`GithubSyncJob` for every possible handler type within the available index (e.g., exact side effects of membership/team or check-run handlers under this same mismatch), so the concrete blast radius per event type should be validated in a live/staging Shipit instance with a background Devin session if a full exploit chain confirmation is needed.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

    rescue Shipit::GithubOrganizationUnknown => e

    end
