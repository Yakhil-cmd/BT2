### Title
Integer/Precision Overflow in Asset Denomination Cap Validation Allows Declared Asset Cap to Mismatch True Issuable Supply - (File: validation.js)

### Summary
`validateAssetDefinition()` computes the sum of per-denomination caps (`count_coins * denomination`) using plain JavaScript floating-point arithmetic with **no upper bound on `count_coins`**, while `denomination` is only bounded to `MAX_CAP` (close to the JS safe-integer limit). An attacker defining an asset can choose `count_coins`/`denomination` pairs whose true mathematical product exceeds `Number.MAX_SAFE_INTEGER`, causing the accumulated `total_cap_from_denominations` to silently lose precision. Because the same lossy floating-point value is compared for equality against the declared `payload.cap` [1](#0-0) , an attacker can make an inflated real per-denomination supply pass the "cap doesn't match sum of denominations" check while declaring a much smaller, MAX_CAP-compliant `cap`.

### Finding Description
`validateAssetDefinition` validates asset issuance parameters for any asset-definition message posted by an unprivileged unit author (the "asset issuer"): [2](#0-1) 

Key gaps:
- `denomInfo.denomination` is checked with `isPositiveInteger` and bounded by `constants.MAX_CAP` [3](#0-2) .
- `denomInfo.count_coins` is checked **only** with `isPositiveInteger` — no upper bound at all [4](#0-3) .
- `isPositiveInteger`/`isInteger` in `validation_utils.js` only test `Math.floor(value) === value` on a JS double [5](#0-4) ; this accepts any integer-valued double, including values far beyond `Number.MAX_SAFE_INTEGER` (2^53), which are still "integer-valued" as IEEE-754 doubles even though they can't represent all integers precisely.
- The accumulation `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination` is done in plain floating-point, not `Decimal`. When the true product for one or more denomination tiers exceeds 2^53, precision is silently lost.
- The final check `total_cap_from_denominations !== payload.cap` [1](#0-0)  only requires the *lossy floating-point sum* to equal the declared cap, not the true mathematical sum of the per-tier limits that will actually be enforced later at issuance time via the `asset_denominations.count_coins` column (checked per-denomination in `validateIndivisibleIssue`) [6](#0-5) .

Because issuance of each denomination tier is bound only by that tier's own `count_coins` value in the `asset_denominations` table (not by re-checking against the original `cap`), an attacker can craft denominations where the JS-computed sum happens to equal a small declared `cap` (satisfying validation) while the actual, mathematically-correct sum of `count_coins * denomination` across tiers — and therefore the true maximum issuable quantity of the asset — is materially larger. This breaks the invariant that `cap` represents the true maximum supply of the asset, which downstream consumers (AAs reading `asset[...].cap`, wallets, exchanges) rely on for supply accounting.

### Impact Explanation
This is an asset-issuance validation bypass reachable by any asset issuer (an unprivileged unit poster defining a new asset with `fixed_denominations` and multiple denomination tiers). It allows the declared `cap` (relied upon by AAs and wallets as the asset's guaranteed total supply) to diverge from the true maximum quantity mintable across the asset's denomination tiers — a form of supply-inflation-adjacent inconsistency for the asset. Any AA or contract logic that trusts `cap` as an upper bound on total issuable supply of the asset (e.g., collateral/backing calculations, cap-based pricing formulas) can be deceived, potentially leading to fund loss for counterparties who rely on the stated cap. Because the computation is deterministic floating-point arithmetic executed identically on every node, this does not directly cause a consensus fork, but it produces a supply/accounting invariant violation with real economic (fund-loss) consequences for AAs and wallets that trust `cap`.

### Likelihood Explanation
Exploitation requires only posting a standard `asset` definition message with `fixed_denominations: true` and multiple denominations whose `count_coins` values are chosen near/above `Number.MAX_SAFE_INTEGER` boundaries relative to `denomination` — something any user can do without special privileges, using only public APIs (`composer.js`/`validation.js` asset-definition flow). No coordination with hubs, witnesses, or other nodes is needed.

### Recommendation
- Bound `count_coins` explicitly (e.g., to `constants.MAX_CAP` or to a value that guarantees `count_coins * denomination` stays within `Number.MAX_SAFE_INTEGER` and within `MAX_CAP`), not just check `isPositiveInteger`.
- Perform the cap-sum accumulation and comparison using the same arbitrary-precision `Decimal` arithmetic already used elsewhere in formula evaluation (`formula/common.js`), rather than native JS floating point, and reject the definition if any intermediate product exceeds `MAX_CAP`.
- Add an explicit check that each `count_coins * denomination` product individually does not exceed `constants.MAX_CAP`, in addition to the aggregate `cap` equality check.

### Proof of Concept
1. Attacker posts a unit with an `asset` message: `fixed_denominations: true`, `cap: <small value ≤ MAX_CAP>`, and `denominations` containing two or more tiers where `count_coins` values are chosen to be extremely large integer-valued doubles (e.g., `count_coins: 9007199254740993` paired with a `denomination` value), such that the true product `count_coins * denomination` for at least one tier exceeds `Number.MAX_SAFE_INTEGER`.
2. Due to floating-point rounding in the `total_cap_from_denominations += ...` accumulation loop [7](#0-6) , the computed sum coincidentally equals the small declared `cap`, passing the check at [1](#0-0) .
3. The asset definition is accepted; `asset_denominations` rows are populated per denomination tier with the large `count_coins` values.
4. Subsequent issuance transactions are validated per-tier against `asset_denominations.count_coins` [8](#0-7) , allowing the issuer to mint quantities whose true total exceeds the declared, MAX_CAP-compliant `cap` that other participants (AAs, wallets) rely on as the asset's maximum supply.
