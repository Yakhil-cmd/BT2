### Title
Webhook signature verification authenticates the payload's organization, not the repository being written to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate an inbound webhook's HMAC signature against based on `repository_owner`, a value read from the *same, attacker-controlled* JSON payload (`repository.owner.login`, falling back to `organization.login`). Once that signature check passes, the entire raw `params` hash — including whatever `repository.full_name` the payload contains — is handed unmodified to every registered event handler. Nothing re-checks that the repository actually written to belongs to the organization whose secret was used to authenticate the request.

### Finding Description
`verify_signature` computes the verifying GitHub App from the payload itself: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a `GitHubApp` instance whose `webhook_secret` is used for the HMAC check: [3](#0-2) 

Shipit explicitly supports multiple organizations, each with its own independently configured `webhook_secret` in `secrets.yml` (confirmed by the multi-org fixture with `OrgOne` / `OrgTwo`, each carrying a distinct `webhook_secret`): [4](#0-3) 

After the signature check passes, `create` dispatches the *unmodified* `params` (parsed straight from `request.raw_post`) to every handler registered for the event: [5](#0-4) 

The binding that should hold is:
`organization whose secret authenticated the request == organization that owns the repository the handlers act on`

But the controller only derives `repository_owner` for secret *selection*; it never re-validates that `repository.full_name` (the field handlers/`GithubSyncJob` use to look up the target `Stack`/`Repository`) belongs to that same organization. Since `repository.owner.login` and `repository.full_name` are both attacker-supplied fields inside one JSON body signed as a whole, an attacker who legitimately controls one organization's webhook secret (e.g., they administer their own GitHub App installation "OrgB" registered in this Shipit instance) can produce a validly-signed payload where `repository.owner.login` (and `organization.login`) says `"OrgB"` — satisfying `verify_signature` — while `repository.full_name` says `"OrgA/victim-repo"`, a repository belonging to a different organization/stack tracked by the same Shipit instance.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" binding called out as in-scope. A holder of one organization's webhook secret can forge events (e.g. `push`, `status`, `check_suite`, `membership`) that are processed as if they legitimately originated for a *different* organization's repository/stack, since the downstream sync/status/membership handlers key off `repository.full_name` inside the same trusted-by-signature payload rather than the organization used to select the secret. Depending on which handler runs, this can drive `GithubSyncJob` to sync a stack from attacker-chosen commit data, flip commit statuses, or manipulate team membership for a repository the attacker does not otherwise control — a cross-organization/cross-repository write via a forged but "validly signed" webhook.

### Likelihood Explanation
Requires the attacker to already control a legitimate GitHub App installation (and its `webhook_secret`) registered as one of the organizations configured in this Shipit instance's `secrets.yml` — a realistic scenario for any Shipit deployment serving multiple organizations/teams with independent GitHub Apps, since none of these organizations are meant to trust each other. No repository write access, `ApiClient` token, or session privileges on the target organization are needed.

### Recommendation
After parsing `params`, re-derive the organization/repository the payload claims to act on (`repository.full_name`) and verify its owner matches the organization (`repository_owner`) whose secret validated the signature; reject the webhook (422) on mismatch before dispatching to handlers.

### Proof of Concept
1. Attacker operates GitHub App "OrgB", which the target Shipit instance trusts with its own `webhook_secret_B` (as in `secrets_double_github_app.yml`).
2. Attacker crafts a `push` payload:
   ```json
   {
     "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgA/victim-repo" },
     "after": "<attacker-chosen-sha>"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_B, body)` and POSTs to `/github_hooks` (or the configured webhook route) with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgB")` — using `webhook_secret_B` — and the signature validates successfully. [1](#0-0) 
5. `create` forwards the full `params` (with `repository.full_name = "OrgA/victim-repo"`) to registered `push` handlers, which act on `OrgA/victim-repo` despite the request only ever being authenticated for `OrgB`. [5](#0-4)

      verified = github_app.verify_webhook_signature(

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
