### Title
Webhook authentication is bound to `repository.owner.login`/`organization.login` while the write action is bound to `repository.full_name`, letting an attacker forge events for any organization by picking a secret-less org as the "authenticator" - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate a webhook against using `repository_owner`, taken from `params.dig('repository', 'owner', 'login')` (or `organization.login`) [1](#0-0) [2](#0-1) . However, the handler that actually performs the write, `PushHandler`, resolves the target `Repository`/`Stack` using an entirely different, independently-controlled field: `repository.full_name` [3](#0-2) [4](#0-3) . Since the whole JSON body is attacker-supplied (not per-field signed), and `GithubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the selected organization [5](#0-4) , an attacker can pick any organization onboarded to the Shipit instance without a configured `webhook_secret` (a documented, valid configuration state — see `config/secrets.development.shopify.yml`) as `repository.owner.login`/`organization.login`, while setting `repository.full_name` to point at a *different*, secured organization's real repository/stack.

### Finding Description
The binding that should hold is: `organization that authenticated the webhook == organization whose repository state is written`. This engine breaks that equality:
1. `verify_signature` computes `repository_owner` and fetches `Shipit.github(organization: repository_owner)` [1](#0-0) .
2. `GithubApp#verify_webhook_signature` skips verification entirely (`return true unless webhook_secret`) if that organization's config has no secret set [5](#0-4) .
3. `Handler#stacks`/`PushHandler#process` never re-checks `repository_owner`; it looks up the target `Repository` purely from `payload.dig('repository', 'full_name')` [3](#0-2)  and calls `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack [4](#0-3) .

Because `repository.owner.login`/`organization.login` and `repository.full_name` are two independent JSON fields inside the same unsigned/attacker-controlled request body, an attacker who knows (or guesses) that at least one onboarded org lacks a `webhook_secret` can craft a request that "authenticates" as that low-value org while writing to a stack belonging to an entirely different, secured org.

### Impact Explanation
This is an authentication-bypass primitive: the signature check that is supposed to gate all webhook-driven writes can be routed around for any repository in the Shipit instance, as long as one other onboarded organization is configured without a secret. The immediate consequence demonstrated here is forcing a `sync_github` call (enqueuing `GithubSyncJob`) against arbitrary stacks without ever possessing the target organization's `webhook_secret`. This meets the "authentication bypass" impact tier called out in scope.

### Likelihood Explanation
Likelihood depends on at least one organization configured in `Shipit.github_config` lacking a `webhook_secret` — an explicitly supported and documented state (`config/secrets.development.shopify.yml` shows `webhook_secret: # nil`), commonly true for staging/test orgs or orgs onboarded before secrets were set. No credential, GitHub App access, or Shipit session is required by the attacker; only knowledge/guessing of an onboarded organization login without a secret and the target repository's `owner/name`.

### Recommendation
Bind the signature-verification organization to the same value used by every downstream handler for looking up the target Repository/Stack (i.e., always resolve and verify against `repository.full_name`'s owner, not a separately-dug `organization.login` fallback), and/or require that every configured GitHub App used by the engine always have a non-blank `webhook_secret`, removing the `return true unless webhook_secret` bypass in `GithubApp#verify_webhook_signature`.

### Proof of Concept
1. Shipit is configured with two orgs: `org-secured` (has `webhook_secret` set, owns `org-secured/prod-app` with an existing `Stack`) and `org-unsecured` (onboarded without a `webhook_secret`, e.g. a sandbox org).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "org-unsecured" }, "full_name": "org-secured/prod-app" }
}
```
No valid `X-Hub-Signature` header is required.
3. `verify_signature` computes `repository_owner = "org-unsecured"`, fetches that org's `GithubApp` (no secret), and `verify_webhook_signature` returns `true` unconditionally [5](#0-4) .
4. `PushHandler#process` resolves `Repository.from_github_repo_name("org-secured/prod-app")` and calls `sync_github` on its stacks, even though the request never presented `org-secured`'s webhook secret [4](#0-3) .

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
