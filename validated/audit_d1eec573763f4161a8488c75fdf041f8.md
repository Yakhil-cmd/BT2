### Title
Webhook signature is verified against the organization inferred from the payload, but handlers act on a different, unvalidated scope — allowing cross-organization / cross-repository forged webhook writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App / webhook secret to validate the HMAC signature against by reading `repository.owner.login` (or, as a fallback, `organization.login`) straight out of the same untrusted JSON body it is about to verify. Once the signature check passes for that inferred organization, the request is dispatched to the event handlers, several of which resolve the actual data to mutate (`Commit`, `Stack`) using **other, independent fields** of the same payload (`repository.full_name`, or, for `status` events, no repository field at all). Because nothing ties "the organization whose secret validated this request" to "the repository/commit that is written," a party who only holds the webhook secret for one organization configured on a shared/multi-org Shipit instance can forge writes that affect a different organization's repositories.

### Finding Description
The verification and dispatch flow: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and thus a distinct `webhook_secret`) per organization when Shipit is configured for multiple GitHub organizations — an explicitly documented and supported deployment mode: [3](#0-2) 

The signature check only proves that the raw body was HMAC-signed with *some* configured organization's secret — the organization identified by `params.dig('repository','owner','login')`. It does not constrain what other fields of the same body may contain.

Event handlers then act on different, independently-attacker-controlled fields:
- The base `Handler` resolves the target `Stack`s via `repository.full_name`, a sibling field to `repository.owner.login` but not the same value used for signature routing: [4](#0-3) 
- `PushHandler` uses that scope to trigger `stack.sync_github`: [5](#0-4) 
- `StatusHandler` is worse: it never requires or consults any `repository` field at all — it looks up commits **globally by SHA** and writes a `Status` to whatever commit matches, regardless of organization: [6](#0-5) 

The only case where the two identities happen to coincide is `MembershipHandler`, which (for events with no `repository` key) uses `organization.login` for both signature routing and as the team's `organization`: [7](#0-6) 

**Binding broken:** `organization authenticated by verify_webhook_signature ≠ repository/commit written by the handler`. Concretely: `params.dig('repository','owner','login')` (used to select the secret) is not required to equal `params.dig('repository','full_name')`'s owner (used by `PushHandler`/other repository-scoped handlers), and for `status` events there is no repository binding whatsoever.

### Impact Explanation
On a Shipit installation configured with `Using Multiple Github Applications` (each organization has its own `webhook_secret`, a documented and supported setup — `docs/setup.md` "Using Multiple Github Applications"), an attacker who legitimately administers/knows the webhook secret of *one* onboarded organization (Org A) — but has no access whatsoever to a different onboarded organization's repos (Org B) — can:
1. Craft a raw JSON body for the `status` event containing an arbitrary `sha` (commit SHAs are not secrets — visible to anyone with read access to a repo, public or otherwise) and `state: "success"`.
2. Sign it with Org A's webhook secret and POST it to the shared `/webhooks` endpoint.
3. `verify_signature` resolves `repository_owner` to `nil`/absent (no `repository` key required by `StatusHandler`) or to Org A if a bogus `repository.owner.login: "OrgA"` block is added, and validates successfully against Org A's secret.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` globally and writes a fabricated `Status` on a commit that may belong to Org B's `Stack`, with zero verification that Org A owns that commit/repo.

This is a genuine cross-organization write: a credential scoped to Org A is used to mutate state belonging to Org B. Depending on stack configuration (e.g., `continuous_deployment`, required-status gating for deploys), forging a "success" CI status for the latest commit of a victim stack can unblock or trigger an otherwise-unauthorized deploy — squarely within the Critical impact bucket ("cross-repository writes, or an unauthorized deploy"). Even absent continuous deployment, it is an unauthenticated (with respect to the victim org) write of authoritative CI state, corrupting merge/deploy safety signals for repositories the attacker has no authorization over.

The `push`/`pull_request`/`check_suite` handlers exhibit the same class of issue at a lesser severity: they do consult a `repository` field, but it is a *different* field (`full_name`) than the one used for signature-secret selection (`owner.login`), so nothing prevents an attacker signing with Org A's secret from pointing `repository.full_name` at an Org B repository to trigger `stack.sync_github` for it.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured with the documented multi-organization GitHub App feature (distinct `webhook_secret` per organization), and (b) the attacker to legitimately hold the webhook secret for at least one onboarded organization (which any org admin who installed the Shipit GitHub App for their own org effectively controls/knows), while having no privileges on the target organization. This is a realistic "unprivileged attacker" scenario for any SaaS-style shared Shipit deployment serving multiple customer/internal organizations, and requires no session, API token, or GitHub App private key — only knowledge of one's own org's webhook secret and the ability to POST directly to the public `/webhooks` endpoint.

### Recommendation
Do not rely on attacker-controlled payload fields to select the verification key and then use a *different* attacker-controlled field to determine what gets written. Concretely:
- After choosing `github_app` by `repository_owner`, re-derive the same organization scoping used by every handler (`repository.full_name`'s owner, or for `status` events, resolve the commit's stack and its repository) and reject the request (422) if they disagree.
- For `StatusHandler`, require and validate a `repository` block and confirm the resolved `Commit`'s `Stack#repo_owner` matches the organization whose secret validated the signature, instead of matching commits globally by SHA alone.

### Proof of Concept
Given a Shipit instance with `secrets.github` containing both `OrgA` (attacker's own org, secret known to attacker) and `OrgB` (victim org, unrelated to attacker), and a `Stack`/`Commit` belonging to `OrgB/victim-repo` with SHA `deadbeef...`:

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>
Content-Type: application/json

{
  "sha": "deadbeef1234...",   // real commit SHA belonging to OrgB's repo
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "OrgA" }   // only field controller uses for secret selection
}
```
- `verify_signature` resolves `repository_owner` from `organization.login` = `OrgA`, uses OrgA's `webhook_secret` to validate, which succeeds since the attacker signed with that secret. [8](#0-7) 
- `StatusHandler#process` never checks organization/repository ownership and writes a `Status` on the matching commit belonging to `OrgB`: [9](#0-8) 

Result: an entity authenticated only as `OrgA` has written CI status data (and potentially unblocked deploy/merge gating) for a repository under `OrgB`, which it has no authorization over — a cross-organization write breaking the "organization authenticated vs repository written" binding.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

          Team.find_or_create_by!(github_id: params.team.id) do |team|
