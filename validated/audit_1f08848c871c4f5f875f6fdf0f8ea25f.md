### Title
Fork-controlled `machine.environment.BUNDLE_PATH` in `shipit.yml` overrides Shipit's hardcoded `BUNDLE_PATH`, redirecting bundler loads on the deploy host - ([File: lib/shipit/task_commands.rb])

### Summary
`TaskCommands#env` sets a hardcoded, safe `BUNDLE_PATH` and then merges `deploy_spec.machine_env` *after* it, letting any key from the checked-out branch's `shipit.yml` `machine.environment` section silently override that hardcoded value. Because `DeploySpec::FileSystem` reads `shipit.yml` from the task's `working_directory` (the checked-out commit of the branch being run — the fork PR's head branch for a `ReviewStack`), an unprivileged fork PR author fully controls this override, and the resulting `BUNDLE_PATH` is passed unfiltered to `Command#unbundled_env`/`PTY.spawn`.

### Finding Description
The broken binding: Shipit intends `TaskCommands#env['BUNDLE_PATH'] == Rails.root.join('data', 'bundler').to_s` (the fixed, safe vendor path) to always hold for every command executed for a task. In practice: [1](#0-0) 

`env` merges the hardcoded `'BUNDLE_PATH' => Rails.root.join('data', 'bundler').to_s` (line 39) and then `.merge(deploy_spec.machine_env)` (line 46) — a later `Hash#merge` argument always wins, so any `BUNDLE_PATH` key present in `deploy_spec.machine_env` silently replaces the hardcoded value.

`deploy_spec.machine_env` comes straight from the checked-out `shipit.yml`: [2](#0-1) 

and `DeploySpec::FileSystem` is instantiated on `@task.working_directory`, i.e., the file tree of the exact commit being run: [3](#0-2) 

For a `ReviewStack`, that working directory is the fork branch's checkout, which the PR author fully controls. The same override also happens one layer earlier at the config-caching level, where the auto-discovered `BUNDLE_PATH` (from `BundlerDiscovery#discover_machine_env`) is itself overridden by the user-supplied `machine_env`: [4](#0-3) [5](#0-4) 

The resulting env hash is passed to `Command.new(..., env:)`, and `Command#unbundled_env` merges `@env` last over `BASE_ENV`, so nothing downstream re-sanitizes it before `PTY.spawn`: [6](#0-5) [7](#0-6) 

Attack flow: attacker opens a fork PR with a `shipit.yml` containing:
```yml
machine:
  environment:
    BUNDLE_PATH: vendor/attacker_gems
```
and commits a malicious pre-populated `vendor/attacker_gems` tree (a gem with load-time side effects, e.g. a native extension or a `require` in `lib/`). Under `provisioning_behavior: prevent_with_label`, once a maintainer applies the safelist label to provision the review stack (a normal, expected workflow step, not a privileged secret), Shipit checks out the fork branch and runs `install_dependencies`/`deploy_steps` (`bundle install`, `bundle exec ...`) with the attacker's `BUNDLE_PATH`, causing bundler to resolve/activate/require gems from the attacker-controlled path — executing arbitrary Ruby code on the Shipit deploy host.

Existing guards do not block this: `EnvironmentVariables#permit` only governs `${VAR}` interpolation inside command strings, not which keys can populate the process environment itself; there is no allowlist/denylist on `machine.environment` keys in `DeploySpec`; and no code re-asserts the hardcoded `BUNDLE_PATH` after merging `deploy_spec.machine_env`.

### Impact Explanation
Arbitrary attacker-supplied Ruby/native code executes on the Shipit deploy host during `bundle install`/`bundle exec` invocations for the review stack's dependency-install and deploy steps — full RCE with the privileges of the Shipit worker process, including access to `GITHUB_TOKEN`, deploy secrets, and other stacks' checkout directories on the same host. This is repeatable by any fork PR author against any repository configured with review stacks, once the review stack is provisioned (which under `prevent_with_label` requires only a label a maintainer applies as part of normal review, not a security decision about the PR's `shipit.yml` content).

### Likelihood Explanation
Requires: a repository with review stacks enabled and `provisioning_behavior: prevent_with_label`; the attacker needs only to open a PR from a fork with a crafted `shipit.yml` and a vendored malicious gem tree, then wait for/trigger the usual labeling workflow that provisions the review stack and runs a deploy. No secrets, tokens, or special repository permissions are required — this is squarely within the "unprivileged fork PR author" threat model. Cost is low and outcome is deterministic given the merge-order bug.

### Recommendation
In `TaskCommands#env` (and in `DeploySpec::FileSystem#cacheable_config`), merge `deploy_spec.machine_env` (attacker-controlled) *before* the Shipit-enforced values, or explicitly strip/deny security-sensitive keys (`BUNDLE_PATH`, `BUNDLE_GEMFILE`, `GEM_HOME`, `GEM_PATH`, `RUBYOPT`, etc.) from `machine_env`/`@task.env` before the final merge so Shipit's own values always win, regardless of merge order elsewhere.

### Proof of Concept
```ruby
test 'fork-controlled machine.environment BUNDLE_PATH overrides the hardcoded sandboxed value' do
  deploy = shipit_deploys(:shipit_pending) # or a ReviewStack-backed deploy
  stack = deploy.stack
  deploy_spec = stub(
    dependencies_steps!: ['bundle install'],
    deploy_steps!: ['bundle exec cap $ENVIRONMENT deploy'],
    machine_env: { 'BUNDLE_PATH' => 'vendor/attacker_gems' }, # simulates fork shipit.yml
    directory: nil,
    clear_working_directory?: true
  )
  commands = DeployCommands.new(deploy)
  commands.stubs(:deploy_spec).returns(deploy_spec)

  safe_bundle_path = Rails.root.join('data', 'bundler').to_s
  attacker_bundle_path = 'vendor/attacker_gems'

  # Binding under test: env['BUNDLE_PATH'] should equal the hardcoded safe path.
  assert_equal safe_bundle_path, safe_bundle_path # invariant as intended
  assert_equal attacker_bundle_path, commands.env['BUNDLE_PATH'] # actual observed value

  refute_equal safe_bundle_path, commands.env['BUNDLE_PATH'],
    'fork-controlled machine.environment.BUNDLE_PATH overrode the sandboxed BUNDLE_PATH'

  command = commands.install_dependencies.first
  assert_equal attacker_bundle_path, command.env['BUNDLE_PATH']
end
```
This demonstrates the env hash reaching `Command#env` (and ultimately `Command#unbundled_env`/`PTY.spawn`) carries the fork-supplied `BUNDLE_PATH`, contradicting the intended invariant that no fork-controllable key such as `BUNDLE_PATH` reaches the spawned process.
