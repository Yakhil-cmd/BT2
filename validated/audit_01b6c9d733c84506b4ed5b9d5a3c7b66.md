### Title
Improper Verification of Unstable `last_ball_unit` Timestamp/MCI in Signed-Message and `is_valid_signed_package()` Validation Allows Consensus-Diverging AA Execution - ([File: signed_message.js], [File: formula/evaluation.js])

### Summary
`validateSignedMessage()` in `signed_message.js` and the `is_valid_signed_package` opcode in `formula/evaluation.js` both derive `last_ball_mci`/`last_ball_timestamp` from a `last_ball_unit` supplied inside an attacker-controlled signed package, but neither query checks `is_stable` before trusting the unit's `main_chain_index`/`timestamp`. These values are then fed into `objValidationState.last_ball_mci` / `last_ball_timestamp`, which drive the `mci`, `age`, and `timestamp` address-definition operators in `definition.js`. This is directly analogous to CVE-2025-67109's root cause: a time-derived value used for an authorization decision is accepted without verifying it is final/certified, allowing the check to be bypassed or to be evaluated inconsistently.

### Finding Description
`validateOrReadDefinition()` in `signed_message.js` resolves the network-aware branch with: [1](#0-0) 
It selects `main_chain_index, timestamp FROM units WHERE unit=?` for the caller-supplied `last_ball_unit` and immediately uses `main_chain_index` as `last_ball_mci` and `timestamp` as `last_ball_timestamp` — with no `is_stable` (or `is_on_main_chain`) filter, unlike the equivalent and properly-guarded logic in `validateParents()`: [2](#0-1) 
which explicitly reads `is_stable`, `is_on_main_chain`, and the joined `balls` row, and only trusts the ball as final once `is_stable === 1` and the ball hash matches.

The same missing-stability pattern exists in the `is_valid_signed_package` opcode used inside AA/oscript formula evaluation: [3](#0-2) 
Here the code checks `main_chain_index > mci`, `main_chain_index === null`, and `is_on_main_chain`, but never checks `is_stable`. An unstable unit can already have a provisional `main_chain_index` and `is_on_main_chain=1` before it (and the main chain view around it) is finalized, and this provisional assignment can differ between nodes or be revised as the DAG grows (main-chain reorganization prior to stabilization), i.e. it is not yet a "certified" timestamp/index the way a stable, ball-hashed unit is.

The resolved (unverified) `last_ball_mci`/`last_ball_timestamp` is then passed into `Definition.validateAuthentifiers()`: [4](#0-3) 
where address-definition operators evaluate against it directly: [5](#0-4) 
and `age` op: [6](#0-5) 

Because a signed package (with its own `last_ball_unit`, `authors`, `authentifiers`) is attacker-supplied data that can be embedded in AA trigger `data` (as seen in the `order_book_exchange.oscript` sample using `is_valid_signed_package(trigger.data.order1, ...)`), an unprivileged AA trigger sender or off-chain counterparty fully controls which `last_ball_unit` is referenced. By pointing to a unit whose `main_chain_index`/`timestamp` is only provisionally assigned (not yet stable), the attacker can:
- Cause different full nodes/oracles to compute different `last_ball_mci`/`last_ball_timestamp` for the identical signed package at the moment of AA execution, since the provisional MC assignment for an unstable unit is not guaranteed identical across all nodes' views until stabilization.
- Make a `timestamp`/`mci`/`age`-gated address definition (e.g., time-locked multisig, expiring order, escrow condition) pass or fail depending on which node evaluates it, because the check is validated against an unfinalized value rather than the network-agreed stable ball.

### Impact Explanation
Since AA state transitions must be byte-for-byte deterministic and identical on every full node for the network to agree on stability, any avenue where two honest nodes can compute different results for `is_valid_signed_package()` (or any `validateAuthentifiers` call reachable from a trigger/order/private-payment signed message) constitutes a node-disagreement-on-validity bug: nodes could disagree on whether an AA response is bounced or not, or a time-gated authentifier passes, leading to divergent primary/secondary trigger units and DAG forks in interpretation, i.e. the network becomes unable to reliably confirm/agree on the resulting units. In a concrete exploitation (e.g., the order-book exchange pattern shown in the repo's own sample oscript), an attacker could time a signed order/package to a not-yet-stable `last_ball_unit` so that some nodes accept the signed package as valid (and process a trade / release funds) while others reject it, or so that an expiring/time-locked condition is bypassed on some nodes, resulting in unauthorized spending or fund loss/freezing at the AA.

### Likelihood Explanation
Any unprivileged AA trigger sender, private-payment counterparty, or off-chain order signer can construct the `signed_message`/`last_ball_unit` payload themselves (as demonstrated by the built-in `order_book_exchange.oscript` sample which calls `is_valid_signed_package(trigger.data.order1, $order1.address)` directly on trigger-supplied data). No special privileges, hub/peer position, or node compromise is required — only the ability to choose a recent, not-yet-stable unit as `last_ball_unit` when constructing the signed package, which is a normal wallet/composer operation.

### Recommendation
In both `signed_message.js` (`validateOrReadDefinition`) and `formula/evaluation.js` (`is_valid_signed_package`), require the referenced `last_ball_unit` to be `is_stable = 1` (and, where relevant, `is_on_main_chain = 1` with the corresponding `ball` present) before trusting its `main_chain_index`/`timestamp`, mirroring the stability checks already performed in `validateParents()` in `validation.js`. Reject or defer validation (return a transient/retry error) for signed packages whose `last_ball_unit` is not yet stable, exactly as `validateParents` does via `main_chain.determineIfStableInLaterUnitsAndUpdateStableMcFlag`.

### Proof of Concept
1. Attacker crafts a `signed_message` package (or an AA trigger `data.order`) with `last_ball_unit` set to a very recent unit `U` that already has `main_chain_index` and `is_on_main_chain=1` assigned but `is_stable=0`.
2. Attacker signs the package such that the address definition contains a `timestamp`/`mci`/`age` condition intended to fail if evaluated against the true (future, stable) MC position of `U`, but that currently passes against `U`'s provisional (pre-stabilization) MC position.
3. Attacker submits the package as part of an AA trigger (e.g., to `order_book_exchange.oscript`'s `is_valid_signed_package(trigger.data.order1, $order1.address)`) or as an off-chain order to two different counterparties/oracles.
4. Because `validateOrReadDefinition()` in `signed_message.js` and the `is_valid_signed_package` handler in `formula/evaluation.js` never verify `is_stable`, different nodes evaluating the trigger at different times (before/after `U` stabilizes, or with different final MC assignment for `U`) compute different `last_ball_mci`/`last_ball_timestamp`, yielding different authentifier/`is_valid_signed_package` results and consequently different AA responses — a node disagreement on validity that a purely-honest, unprivileged trigger sender can trigger deterministically by timing the submission around `U`'s stabilization.
