### Title
Cross-repository status webhook forgery flips `MergeRequest#all_status_checks_passed?` and triggers unauthorized merge - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` and `Commit#create_status_from_github!` write a `Status` for any commit matched purely by SHA, with no check that the webhook's `repository`/organization matches the `Commit`'s own `stack.repository`. Since `MergeRequest#all_status_checks_passed?` builds its `StatusChecker` from `head.statuses_and_check_runs` (i.e. every `Status` row ever attached to that commit, regardless of who wrote it), a webhook that is validly signed for *any* GitHub organization Shipit trusts can inject a `success` status onto a commit belonging to a completely different stack/repository, flipping the merge-queue gate.

### Finding Description
The broken binding, stated as an equality that the code never enforces:
`params.dig('repository','full_name') (or repository.owner.login used only for signature routing) == merge_request.stack.repository.full_name` — this equality is never checked anywhere between webhook receipt and status persistence.

Path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) resolves `Shipit.github(organization: repository_owner)` from `params.dig('repository','owner','login')` and verifies the HMAC using that organization's `webhook_secret` [1](#0-0) . This only proves the request came from *some* org GitHub app Shipit knows about (the `organization` key of `Shipit.github(organization:)`), not that it came from the specific repository owning the target commit/stack — see `Shipit.github` / `github_app_config` [2](#0-1) .
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . This lookup is global across all stacks/repositories — it never filters by `params['repository']['full_name']`.
3. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) creates the `Status` scoped to `commit.stack_id` — i.e. the *victim* commit's own stack, using attacker-controlled `state`/`context`/`description` from the payload [4](#0-3) .
4. `MergeRequest#all_status_checks_passed?` then reads `head.statuses_and_check_runs` (`statuses + check_runs`, `app/models/shipit/commit.rb:144-146`) unconditionally, feeding it into `StatusChecker` [5](#0-4) . Nothing there filters out statuses that came from a different repository's webhook.
5. `ProcessMergeRequestsJob` (queue processing) will then act on `merge!`, which calls `stack.github_api.merge_pull_request` against the *victim* stack's real repository [6](#0-5) .

Root cause: none of `verify_signature`, `drop_unhandled_event`, or `StatusHandler`'s `ExplicitParameters` schema validates that the webhook's repository matches the repository owning the commit being updated. The schema only requires `sha`/`state`, not `repository.full_name` cross-checked against `commit.stack`.

Exploit precondition: the attacker needs a validly signed status webhook, from an organization Shipit trusts (i.e. one for which `Shipit.github(organization: X)` has a configured `webhook_secret`), whose `sha` collides with the SHA of the target commit already stored in Shipit's DB. Because the merge-queue head commit SHA is the attacker's own PR head (attacker fully controls its content, parents, author/committer timestamps), if the attacker also controls or can install a GitHub App/webhook on another repo under an org Shipit trusts, they can push an identical commit object (same tree/parents/timestamps ⇒ identical SHA) into that second repository and fire a genuine, correctly-signed `status` event for that SHA. `StatusHandler` will then match the (identical) SHA on the victim commit and write a `success` status to it, satisfying `all_status_checks_passed?` without the target stack's actual CI ever running.

Whether "any org Shipit trusts" reduces to "the same org as the victim repo" depends on deployment: many Shipit installs use a single GitHub App/org config (`github_default_organization`), in which case any repository under that same org (which could include an attacker-controlled fork/repo the org allows arbitrary members to create webhooks or push to) can trigger this. In multi-org configs (`secrets.github` keyed by org), a signed webhook from *any* configured org is accepted equally by `verify_signature`, and `StatusHandler` still does a completely global, cross-org SHA lookup — so the missing repository binding is a bug regardless of single- or multi-org deployment.

### Impact Explanation
A forged/legitimate-but-misdirected status webhook can inject an arbitrary `Status` (state, context, description, target_url all attacker-controlled) onto any `Commit` row in the entire Shipit instance as long as the attacker knows/controls the matching SHA, without any verification that the originating repository owns that commit. When the affected commit is a pending merge-queue `MergeRequest#head`, this can flip `all_status_checks_passed?` to `true` and let `ProcessMergeRequestsJob` invoke `MergeRequest#merge!`, causing `stack.github_api.merge_pull_request` to merge the attacker's PR into the victim repository's real branch — an unauthorized merge of attacker-controlled code performed with Shipit's own `GITHUB_TOKEN`/App installation credentials. This matches the "payload for one repository mutating another's stack/commit" and "unauthorized merge" Critical impact categories. It is repeatable against any stack whose merge queue is enabled, for every attacker-known/controlled SHA, and its blast radius spans every stack sharing a trusted GitHub org config on the Shipit instance.

### Likelihood Explanation
Preconditions: the attacker must be able to send a webhook whose HMAC signature validates against an org Shipit trusts (i.e., they need a repository — theirs or one they can attach a webhook to — under a github-app-configured org), and must produce a commit whose SHA exactly matches the victim commit's SHA (feasible for their own PR head, since they authored that commit and know its exact tree/parents/timestamps and can replicate it byte-for-byte in another repo). This is moderate-cost but fully within reach of an "unprivileged GitHub user who can open a PR / push to a repo they own / emit webhooks," matching the stated attacker model; no Shipit session, API token, or secret is required. The exploit is deterministic and repeatable per matching SHA.

### Recommendation
In `StatusHandler#process` (and the analogous `check_run`/`check_suite` handlers) and/or `Commit#create_status_from_github!`, require that `params.dig('repository', 'full_name')` (or equivalent) equals `commit.stack.repository.full_name` before writing the `Status`/`CheckRun`, discarding non-matching commits from the `Commit.where(sha: ...)` scan. Alternatively scope the lookup itself: `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { full_name: params.dig('repository','full_name') })`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or `test/controllers/webhooks_controller_test.rb`):
1. Create two stacks/repositories: `victim_stack` (with a merge queue enabled, `merge_request` fixture in `pending`/`waiting` state whose `head` commit has `sha = S`) and `attacker_stack`/`attacker_repo` (a distinct `Repository` record, unrelated `full_name`).
2. Create a `Commit` on `attacker_stack` with the same `sha = S` (simulating the identical-content-commit scenario), or directly assert the handler-level bug by posting to `WebhooksController#create` a `status` payload with `sha: S`, `state: 'success'`, and `repository.full_name` set to the attacker's unrelated repo, stubbing `verify_signature` to true (as existing tests do via `GithubHook.any_instance.stubs(:verify_signature).returns(true)`).
3. Assert before: `merge_request.reload.all_status_checks_passed?` is `false` (or `any_status_checks_missing?` true).
4. POST the forged status webhook.
5. Assert after: a new `Status` row exists on `merge_request.head` (`assert_difference 'merge_request.head.statuses.count', 1`), and `merge_request.reload.all_status_checks_passed?` is now `true`, despite the webhook payload's `repository.full_name` never matching `victim_stack.repository.full_name`.
6. Stub `Stack#github_api` on `victim_stack` and assert `ProcessMergeRequestsJob.new.perform(victim_stack)` calls `merge_pull_request` (e.g. `Shipit.github.api.expects(:merge_pull_request).once`), proving the forged cross-repo status led to an unauthorized merge attempt.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
