This confirms the bug: `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) resolves `stack` via `Stack.from_param!(params[:stack_id])` directly, bypassing `Api::BaseController#stacks`/`#stack` (`app/controllers/shipit/api/base_controller.rb:74-80`), which is the only place `ApiClient#stack_id` scoping is enforced. Combined with `CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) minting an `ApiClient` with no `stack:` attribute at all, the token that a session-authenticated user obtains for "their" CCMenu widget is both unscoped at creation and unenforced at read time — a bearer token meant to authorize status reads for one stack ends up authorizing status reads for every stack in the installation, with no `Shipit.github_teams` check at all (that check only happens at the web-session layer via `Authentication#force_github_authentication`, never on the API token path).

### Title
CCMenu API token authorizes cross-stack deploy/status disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` re-defines `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of using the stack-scoped lookup (`stacks.from_param!`) that every other `Api::BaseController` subclass relies on for per-`ApiClient` authorization. Because the token minted by `CCMenuUrlController` is also created with no `stack:` attribute, any holder of a single CCMenu token can read deploy/lock status for any stack in the Shipit instance, including stacks belonging to organizations/teams the token's creator was never authorized to see.

### Finding Description
`CCMenuUrlController#fetch` (`app/controllers/shipit/ccmenu_url_controller.rb:7-11`) is reached through a normal web session (`ShipitController`, gated only by `Shipit::Authentication#force_github_authentication`). It builds a public "CCMenu" status URL embedding a bearer token: [1](#0-0) 

The token comes from `client`, which does `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` is set, so `ApiClient#stack_id` is `nil` for this client, i.e. it is a global, org/team-unaware, `read:stack` bearer token shared by name across every stack the user has ever fetched a CCMenu URL for.

On the consuming side, `Api::CCMenuController` authenticates that token via `ApiClient.authenticate(params[:token])` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`), then only enforces the coarse `require_permission :read, :stack` check, which is just `permissions.include?('read:stack')` — it never checks `current_api_client.stack_id`: [2](#0-1) 

Crucially, `stack` is resolved with `Stack.from_param!(params[:stack_id])` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), completely bypassing `Api::BaseController#stacks`, which is the only mechanism in the codebase that restricts a scoped `ApiClient` to a single `Stack`: [3](#0-2) 

Every other API resource controller (`DeploysController`, `TasksController`, `StacksController`, etc.) inherits and uses this scoped `stack`/`stacks` method, so an `ApiClient` bound to Stack A cannot touch Stack B there. `CCMenuController` is the one place that breaks that invariant — for it, `stack_id` on the token is never consulted, and even a client with no `stack_id` at all (as produced by `CCMenuUrlController`) gets equally unchecked access to `params[:stack_id]` supplied by the request.

The binding that should hold is: **stack a token authorizes == stack a request touches**. Before hitting `#show`, the request is only authenticated (valid signature/token) and permission-checked (`read:stack` present in the `permissions` array); the `stack_id` actually acted upon is never compared to the token's authorized stack. After the fix would be applied, `stack` would go through `stacks.from_param!` like every other controller, restoring the equality.

There is also no organizational check at all on this path: `Shipit.github_teams` membership is enforced only in `Shipit::Authentication#force_github_authentication` (web session), never for API requests authenticated via `ApiClient.authenticate`, so the resulting token is not even implicitly limited to stacks the creating user's GitHub team could see once it is used against the API directly.

### Impact Explanation
An attacker who obtains any single CCMenu token (these are, by design, embedded in a plain query string URL meant to be pasted into third-party CI-status widgets/dashboards — a "quasi-public" bearer credential with intentionally minimal scope: `read:stack` for one stack) can enumerate `stack_id` values and read `deploys_and_rollbacks`, lock state, and deployment status for every stack in the Shipit installation, including stacks in repositories/organizations the token's own creator has no access to. This is an unauthenticated-relative-to-scope read of stack state and deploy output across the whole instance, matching the "High — unauthenticated read of stack state, task streams or deploy output" impact bucket.

### Likelihood Explanation
Any authenticated Shipit user can trigger `CCMenuUrlController#fetch` for a stack they can see and obtain a token; that single token then works for `GET /api/stacks/*/ccmenu` for any other stack's `to_param`. `stack_id` format (`owner/name/environment`) is discoverable/guessable from public repository names, so no privileged credential beyond one legitimately-issued CCMenu token is required to pivot across stacks. This makes the analog directly comparable to the underlying report's theme: a check ("is this token permitted at all") is performed on a narrower/different quantity than what is actually acted upon (which specific stack).

### Recommendation
Make `Api::CCMenuController#stack` use the inherited, scoped lookup (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, and have `CCMenuUrlController#client` create/find the `ApiClient` scoped to the specific `stack:` being fetched (e.g. include `stack:` in `create_with`/lookup key) so each CCMenu token is bound to exactly one stack, restoring the "token authorizes == stack touched" invariant enforced everywhere else in the API.

### Proof of Concept
1. As any logged-in Shipit user with access to `stack-a`, call `GET /ccmenu/stack-a/owner/environment` (`CCMenuUrlController#fetch`) to obtain `ccmenu_url` containing `?token=<T>`.
2. Using `<T>`, call `GET /api/stacks/other-org/other-repo/production/ccmenu?token=<T>` for a *different* stack the user never had access to.
3. Observe the response renders that stack's latest deploy/lock/status XML (`shipit/ccmenu/project`), because `Api::CCMenuController#stack` resolves `params[:stack_id]` via `Stack.from_param!` without ever checking that `<T>`'s `ApiClient` is scoped (or even exists as scoped) to `other-org/other-repo/production`.
