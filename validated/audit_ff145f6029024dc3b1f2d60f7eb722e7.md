### Title
Webhook signature verification binds to `repository.owner.login`, but handlers act on `repository.full_name` — cross-organization forgery in multi-tenant deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App (multi-tenant) Shipit deployment, `WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against using the organization taken from `repository.owner.login` (or `organization.login`) in the payload. [1](#0-0) [2](#0-1)  But the handlers that actually act on the payload resolve the target `Repository`/`Stack` from a *different* field in the same JSON body — `repository.full_name` — via `Handler#repository_name`/`#stacks`. [3](#0-2)  These two fields are never checked for consistency with each other.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp` (and thus the `webhook_secret`) purely from `repository.owner.login`: [1](#0-0) . The docs explicitly support a multi-org setup where each GitHub organization has its own `app_id`/`webhook_secret` in `secrets.yml`: [4](#0-3) , confirmed by `Shipit.github`/`github_app_config` looking up per-organization config keyed by name: [5](#0-4) .

Once `verify_signature` passes, `WebhooksController#create` parses the raw JSON and dispatches to handlers using the raw payload hash, not the value used for signature selection: [6](#0-5) . Handlers such as `PushHandler` and `CheckSuiteHandler` locate the target stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`: [3](#0-2) , [7](#0-6) , [8](#0-7) .

`repository.owner.login` and `repository.full_name` are independent JSON fields under the attacker's full control when they craft the raw POST body themselves (this is what the HMAC signs — the raw bytes, not a validated data model). GitHub itself would always populate these consistently, but the webhook endpoint accepts any correctly-signed HTTP POST, not only ones proxied through GitHub. Anyone who legitimately knows one organization's `webhook_secret` (e.g., a tenant admin who configured that org's own GitHub App entry in `secrets.yml`, as the multi-org feature is designed to allow) can therefore forge a payload where:
- `repository.owner.login` (or `organization.login` for events without a `repository` object) = the org whose secret they know → passes `verify_signature`.
- `repository.full_name` = an arbitrary victim repository belonging to a *different* configured organization on the same Shipit instance.

This breaks the binding: `organization that authenticated == organization whose repository is written`.

### Impact Explanation
Using this mismatch, a tenant that legitimately controls one organization's webhook secret can act on any other tenant's stacks tracked by the same Shipit instance:
- Via `StatusHandler`, forge an arbitrary GitHub commit-status (e.g. "success") for any commit sha belonging to another organization's tracked repository: `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` [9](#0-8) . Because Shipit gates deployability/merge-queue eligibility on required commit statuses, this can be used to force a commit into a "deployable"/mergeable state it should not have — an unauthorized-deploy-adjacent primitive.
- Via `PushHandler`, force `stack.sync_github(expected_head_sha:)` on another organization's stack with an attacker-chosen SHA [10](#0-9) , manipulating that stack's tracked git state.
- Via `CheckSuiteHandler`, trigger check-run refresh for arbitrary commits on other tenants' stacks [11](#0-10) .

This is a cross-tenant/cross-organization boundary break reachable by an unprivileged actor relative to the victim organization (they have no access to the victim org or its stacks), satisfying the "unauthorized deploy" impact class.

### Likelihood Explanation
Requires: (1) the target Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration — `docs/setup.md`), and (2) the attacker to be a legitimate holder of one tenant org's `webhook_secret` (e.g., that org's own administrator who configured their GitHub App entry). This is a real, no-additional-privilege position for a *different tenant* relative to the victim tenant on a shared Shipit deployment, matching the "unprivileged attacker" framing (unprivileged with respect to the victim org, not the whole system) and the explicitly allowed binding "organization that authenticated versus the repository that is written."

### Recommendation
After signature verification, cross-check that the organization used to select the `webhook_secret` matches the owner embedded in `repository.full_name` (or `organization.login` used by the specific handler) before dispatching to handlers, rejecting the request (422) on mismatch.

### Proof of Concept
1. Shipit configured with two orgs in `secrets.yml`: `OrgOne` (attacker-controlled tenant, attacker knows `webhook_secret_1`) and `OrgTwo` (victim tenant with a tracked stack for `OrgTwo/victim-repo`), per the multi-org config shape in `docs/setup.md`.
2. Attacker crafts a raw JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha in OrgTwo/victim-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_1, raw_body)>` and POSTs to the shared `/webhooks` endpoint with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgOne')` and validates successfully against `webhook_secret_1` [1](#0-0) .
5. `StatusHandler#process` then applies the forged "success" status to the commit under `OrgTwo/victim-repo` [9](#0-8) , despite the request never having been authenticated for `OrgTwo`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
module Shipit
  module Webhooks
    module Handlers
      class CheckSuiteHandler < Handler
        params do
          requires :check_suite do
            requires :head_sha, String
            requires :head_branch, String
          end
        end
        def process
          stacks.where(branch: params.check_suite.head_branch).each do |stack|
            stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
          end
        end
      end
```
