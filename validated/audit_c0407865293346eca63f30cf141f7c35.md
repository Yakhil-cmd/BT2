Found it: the `MembershipHandler` trusts the `organization.login` field of the webhook payload to attribute a team, but the signature-verification step that gates access to the webhook endpoint validates against a *different* field derived from the payload — creating a binding mismatch between "the organization whose secret validated this request" and "the organization that gets recorded as owning the created Team."

### Title
Membership webhook trusts an unverified `organization.login` field to create/attribute Teams used for `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check against using `repository_owner`, which is derived from the payload itself (`params.dig('repository','owner','login') || params.dig('organization','login')`) [1](#0-0) . For `membership` events there is no `repository` key at all, so `repository_owner` falls back to `params.dig('organization','login')` — the very same field that `MembershipHandler` later trusts to create/attribute the `Team.organization` used for authorization decisions [2](#0-1) .

### Finding Description
When a `membership` webhook is delivered, `verify_signature` calls `Shipit.github(organization: repository_owner)` to look up which webhook secret to HMAC-verify against, and `repository_owner` for this event type equals `params['organization']['login']` [3](#0-2) . If a Shipit deployment configures **multiple GitHub organizations sharing behavior through `Shipit.github(organization:)`**, or the same webhook secret is reused, the equality the engine relies on is:

`organization used to select/verify the HMAC secret == organization.login trusted by MembershipHandler to attribute the Team`

Because both sides read from the *same untrusted, unauthenticated JSON field* before the signature has actually been proven to correspond to that specific organization, an attacker who has legitimate ability to trigger a `membership` webhook delivery for **any one** configured organization (e.g., is a member of Organization A with an installed Shipit GitHub App) can forge the JSON body's `organization.login` value to name a different, victim organization B, while keeping the signature computed with Organization A's secret — as long as `Shipit.github(organization: repository_owner)` resolves both names to configurations sharing a secret (a very common single-tenant default where all "per-org" configs fall back to one global `github:` secret, since `Shipit.github` supports both single and multi-org configuration modes) [4](#0-3) . In that default single-secret configuration, `verify_signature`'s organization-based secret lookup is a no-op distinguishing factor: any successfully-signed payload for the one configured org can carry an attacker-chosen `organization.login`, and `find_or_create_team!` will happily create a `Team` record stamped with that fabricated organization [5](#0-4) .

This directly feeds `Shipit.github_teams`, which resolves configured team handles (`org/slug`) to `Team` records used to gate all authenticated controller access via `User#authorized?` [6](#0-5) , and via `force_github_authentication` [7](#0-6) . Team membership (`added`/`removed`) additions are also entirely driven by this handler with no re-validation of the organization boundary [8](#0-7) .

### Impact Explanation
If successful, this allows an attacker to fabricate `Team`/`Membership` records that don't correspond to real GitHub organization state, which can escalate into `Shipit.github_teams` authorization — the High severity impact category explicitly listed in scope — potentially granting an unauthorized `User` access to the whole Shipit instance if the fabricated team's org/slug happens to match a configured `Shipit.github_teams` entry, or polluting team membership used elsewhere.

### Likelihood Explanation
Exploitability depends heavily on deployment topology: it requires (a) the attacker to already be able to trigger a genuine, signed webhook delivery for at least one organization Shipit trusts (i.e., a `membership` event fires for a repo/org they belong to), and (b) that organization's configured secret being indistinguishable from — or identical to — the secret used for the victim organization referenced in the forged `organization.login` field (true by default in the common single-org/global-secret configuration shown in `secrets.development.example.yml`, since `Shipit.github(organization:)` doesn't require per-org secrets). In genuinely multi-tenant configurations with distinct `webhook_secret` per organization, this analog does not hold because the HMAC would fail. This makes the likelihood **conditional on the (very common) single-secret configuration**, which I could not fully verify is the deployed default in all cases — flagging this as an area of uncertainty.

### Recommendation
`MembershipHandler` should not trust `organization.login` from the payload body to attribute the Team's organization without independently confirming it against the organization that was cryptographically proven by the signature check (i.e., use the same `repository_owner`/verified-organization value the controller already computed, passed down explicitly, rather than re-reading `params.organization.login` inside the handler). Additionally, `Shipit.github(organization:)` configurations should be validated to disallow secret reuse across distinct organization names when multi-org config is active.

### Proof of Concept
1. Deploy Shipit with the common single `github:` secret configuration (no per-org `webhook_secret` map) as shown in `config/secrets.development.example.yml`.
2. Attacker is a member of Organization A, which has the Shipit GitHub App installed, and can cause GitHub to deliver a genuine, correctly-signed `membership` webhook (e.g., by being added/removed from a team in Org A).
3. Attacker intercepts or replays this delivery mechanism (or, more directly, since the signature only depends on the shared secret and raw body, crafts their own POST to `/webhooks` with `X-Github-Event: membership`), setting the JSON body's `organization.login` to `"victim-org"` while the HMAC in `X-Hub-Signature` is computed with the shared secret over that same crafted body.
4. `verify_signature` calls `Shipit.github(organization: "victim-org")`, which resolves to the same shared secret/config, and the signature check passes.
5. `MembershipHandler#find_or_create_team!` creates a `Team` with `organization: "victim-org"` [5](#0-4) , and the attacker-controlled `member.login` user is added to it.
6. If `Shipit.github_teams` is later configured to include `victim-org/<slug>`, or an admin runs `teams:fetch`, this fabricated team can influence authorization decisions.
