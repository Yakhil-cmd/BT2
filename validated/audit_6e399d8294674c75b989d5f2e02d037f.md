### Title
Webhook organization used for signature verification is not bound to the repository/stack the handler acts on - cross-repository webhook forgery ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate the HMAC signature against using `repository_owner`, a value read straight out of the untrusted JSON payload (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check passes, the full attacker-controlled payload — including the `repository.full_name` field used by the actual event handlers — is passed to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` without any re-validation that the repository/stack being mutated belongs to the same organization whose secret was used to authenticate the request.

### Finding Description [1](#0-0) 

The `organization` used to pick the verification secret is derived from `repository_owner`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` further weakens this binding: if the resolved organization has no `webhook_secret` configured, verification is **unconditionally skipped** (`return true unless webhook_secret`): [3](#0-2) 

The engine explicitly supports multi-organization configuration where each org has its own (optional) `webhook_secret` and credentials, as documented in `docs/setup.md` and shown in the fixture config with `OrgTwo` having `webhook_secret: # nil`: [4](#0-3) 

Once the request clears `verify_signature`, `create` forwards the entire raw payload — unfiltered and un-scoped to the verified organization — to the registered handlers: [5](#0-4) 

Handlers then act on repository/commit data taken from that same payload, independent of the `repository_owner`/`organization` value that was actually used for authentication. For example, `PushHandler` resolves `stacks` (scoped via `repository.full_name`, looked up through `Repository.from_github_repo_name`) and syncs any matching, non-archived stack for the pushed branch: [6](#0-5) [7](#0-6) 

`StatusHandler` is even less scoped: it looks up commits purely by SHA across the entire installation, with no repository filter at all: [8](#0-7) 

**The broken binding, stated as an equality that the code fails to enforce:**
`organization used to select webhook_secret for verify_webhook_signature` (`repository_owner`) **≠** `repository/stack that PushHandler/StatusHandler/etc. actually mutate` (`repository.full_name` / commit `sha` taken from the same untrusted payload).

Nothing in `WebhooksController` or `Handler` re-checks that the `full_name`/commit ownership used by a handler matches the org that was cryptographically verified. An attacker who controls (or is a member of) any organization configured in this Shipit installation — particularly one with `webhook_secret` unset, which the engine explicitly allows per-org — can sign (or trivially satisfy, since no secret is required) a webhook whose `repository.owner.login`/`organization.login` field names their own org, while the `repository.full_name` field (or a commit `sha` belonging to another stack) names a victim repository/stack managed by a completely different, legitimately secured organization.

### Impact Explanation
This breaks the deployment-trust binding between "GitHub organization that authenticated the webhook" and "repository/stack whose state is written," resulting in cross-repository writes: an attacker can trigger `GithubSyncJob` for a foreign stack, forge `status`/`check_suite` events that mark arbitrary commits (across the whole installation) as passing CI, or influence merge/deploy eligibility for stacks that are not part of the org the attacker actually authenticated as. Where continuous deployment or the merge queue relies on `commit_status`/`check_suite` state, this can enable an unauthorized deploy or merge on a stack the attacker does not control — matching the "Critical: unauthorized deploy/merge" and "High: unauthenticated read/write of stack state" impact classes.

### Likelihood Explanation
Requires only that the target Shipit deployment configures more than one GitHub organization (a documented, supported configuration) and that the attacker controls (or can install a webhook against) at least one of those organizations, ideally one with `webhook_secret` left blank — an explicitly supported and shown-in-fixtures configuration state. No GitHub App private key, `ApiClient` token, or Shipit session is needed; only the ability to send an HTTP POST to `/webhooks` with a crafted JSON body.

### Recommendation
Bind the verified organization to every subsequent lookup: after `verify_signature` succeeds, restrict handler processing so that `repository.full_name` (and any commit SHA lookups) are scoped to repositories owned by the exact `repository_owner`/`organization` that was authenticated, rejecting or ignoring events whose payload repository owner does not match the verified organization. Additionally, require `webhook_secret` to be present for all configured organizations in production (fail closed instead of `return true unless webhook_secret`).

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (no `webhook_secret` set, or one known to the attacker) and `victim-org` (properly secured), as supported by the documented multi-org config format.
2. Attacker sends `POST /webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": {"login": "attacker-org"},
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `Shipit.github(organization: 'attacker-org')`, and either has no `webhook_secret` (auto-pass) or is signed correctly by the attacker with their own known secret.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name('victim-org/victim-repo')` and calls `sync_github(expected_head_sha: ...)` on that victim stack, even though the request never proved control of `victim-org`.

**File:** lib/shipit/github_app.rb (L76-83)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
