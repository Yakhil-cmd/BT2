### Title
Stack-scoped API tokens bypass their stack restriction in `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts a scoped `ApiClient` to the single `Stack` it was issued for by filtering the `Stack` collection before resolving `params[:stack_id]`. `Shipit::Api::CCMenuController` re-implements its own `stack` resolver that ignores this scoping and looks the stack up directly from the global `Stack` table, letting any valid token read the CCMenu/build-status of a stack it was never authorized for.

### Finding Description
`ApiClient` can be bound to a single stack: `belongs_to :stack, optional: true` [1](#0-0) . `Shipit::Api::BaseController` is meant to enforce this binding for every API endpoint by scoping the `Stack` relation the token is allowed to touch:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

The binding this establishes is: `token.stack_id (if set) == params[:stack_id] resolved`. Every controller that inherits `stack` from `BaseController` (e.g. `Api::StacksController`) respects it.

`Api::CCMenuController`, however, overrides `stack` with its own private method that bypasses the scoped `stacks` collection entirely and queries the model directly:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

`authenticate_api_client` only validates that `params[:token]` decodes to *some* `ApiClient` and that it holds the `read:stack` permission (`require_permission :read, :stack` [4](#0-3) ); it never checks that the resolved `stack` matches `current_api_client.stack_id`. `show` then renders build/deploy status for whatever `stack_id` is supplied in the URL:

```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end
``` [5](#0-4) 

This breaks the equality that `BaseController` establishes elsewhere: `stack a token authorizes == stack a token touches`. A token minted with `stack_id` set to stack A (and `read:stack` permission) can be replayed against `/api/{owner}/{repo}/{env}/cc.xml` for any stack B by simply changing the `stack_id` path segment; `CCMenuController` will happily resolve and render stack B's data.

### Impact Explanation
This is a cross-stack authorization escalation: possession of a token legitimately scoped to one stack grants unauthenticated-for-that-stack read access (build status, last deploy status/time, lock state) to every other stack in the Shipit instance, matching the High-impact category "escalation into `Shipit.github_teams` authorization" / "unauthenticated read of stack state". The information disclosed (deploy status, lock reason, activity) can reveal deployment cadence and incident status of stacks/environments the token holder has no legitimate visibility into.

### Likelihood Explanation
Likelihood is High for any deployment that issues stack-scoped `ApiClient` tokens (the `stack_id`/`belongs_to :stack` column exists specifically to support this scoping model, and `BaseController#stacks` implements it for the rest of the API). No special privilege beyond holding *any* valid `read:stack` token is required — the attacker only needs to change the `stack_id` in the request path, an action fully available to an unprivileged token holder.

### Recommendation
Remove the private `stack`/`authenticate_api_client` overrides in `Api::CCMenuController` (or make them delegate to the inherited, scope-respecting implementations in `BaseController`) so that `stack` is always resolved from `stacks` (the token-scoped collection) rather than `Stack` directly.

### Proof of Concept
1. Configure Shipit with two stacks, `org/repoA/production` (Stack A) and `org/repoB/production` (Stack B).
2. Create/obtain an `ApiClient` with `stack_id` set to Stack A and `permissions: ['read:stack']` (e.g. via the stack-scoped token creation path that persists `stack:` on the `ApiClient`).
3. As the holder of that Stack-A-scoped token, request:
   `GET /api/org/repoB/production/cc.xml?token=<stack-A-scoped-token>`
4. `authenticate_api_client` accepts the token (valid signature, sufficient `read:stack` permission) [6](#0-5) ; `stack` resolves Stack B directly via `Stack.from_param!` [7](#0-6) , without checking `current_api_client.stack_id`.
5. The response renders Stack B's CCMenu XML (deploy status, lock state, last build info), despite the token being authorized only for Stack A.
