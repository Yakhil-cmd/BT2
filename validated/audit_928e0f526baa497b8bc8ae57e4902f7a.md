### Title
Token holders lose the ability to spend previously-attested `spender_attested` asset funds when the current attestor list or attester's address definition changes ([File: storage.js])

### Summary
For assets defined with `spender_attested: true`, ocore determines whether a coin owner is allowed to spend it by checking the **current** (as of `last_ball_mci`) attestor list and the **current** validity of any attestation, rather than the compliance status that was valid when the tokens were legitimately received. This mirrors the reported bug class: a state that should be "locked in" at the time value was acquired (an attestation / compliance check) is instead re-evaluated against present-day rules every time a spend is attempted, which can silently freeze previously compliant, legitimately-held balances.

### Finding Description
When a payment spends or issues a `spender_attested` asset, `validatePayment` loads the asset together with the list of *currently* attested authors via `storage.loadAssetWithListOfAttestedAuthors`, which internally calls `readAsset` and `filterAttestedAddresses`: [1](#0-0) 

`readAsset`'s `addAttestorsIfNecessary` always fetches the **latest** attestor-list unit as of `last_ball_mci` — not the attestor list that was in force when a holder's tokens were issued or transferred to them: [2](#0-1) 

`filterAttestedAddresses` then checks whether an address is attested by one of these *current* attestors, and additionally invalidates any attestation that predates the address's most recent `address_definition_changes` entry: [3](#0-2) 

This "current-state" attested list is then used to gate every subsequent spend of the asset, both when consuming an existing output as an input and when producing outputs of an issuance/transfer: [4](#0-3) [5](#0-4) 

The definer can permissionlessly update the attestor list at any time with an `asset_attestors` message, validated by `validateAttestorListUpdate`, which does not consider or grandfather holders who already received tokens while a *previous* attestor list was in effect: [6](#0-5) 

As a result, a holder who legitimately acquired tokens while properly attested under attestor-list version N can become unable to spend that same balance later, purely because:
1. The definer publishes a new `asset_attestors` list (version N+1) that no longer includes the attestor who vouched for the holder, or
2. The holder rotates their address definition (e.g., a routine key change/multisig update), which per the `address_definition_changes` join in `filterAttestedAddresses` retroactively invalidates the previously valid attestation.

In both cases, the check is re-derived from data current at `last_ball_mci`, not from the compliance state that applied when the tokens were received — the same "apply present rules to historical holdings" flaw described in the external report.

### Impact Explanation
Balances of a compliance-gated (`spender_attested`) asset can become permanently or temporarily unspendable for reasons entirely outside the holder's control (an attestor-list update by the definer, or a routine address-definition change by the holder), even though the holder's compliance status was valid at acquisition time. This is a fund-freezing condition reachable by any ordinary participant (asset issuer updating attestors, or any holder rotating keys) without any malicious actor being required, and it directly denies legitimate transfer of already-owned tokens — matching the accepted "fund freezing" impact category.

### Likelihood Explanation
This requires no adversarial coordination: an asset definer routinely updating its attestor list (an expected, supported operation per the schema comment "must subsequently publish and update the list of trusted attestors"), or any wallet performing a normal address-definition/key-rotation, is sufficient to trigger the freeze for otherwise-honest holders. Both operations are core, frequently-used ocore features (`asset_attestors` message, `definition_change` message), making the likelihood of hitting this condition in production compliance-token deployments realistic.

### Recommendation
Record, at issuance/transfer time, which attestor-list version (and/or attestation state) authorized the spend, and persist that snapshot with the output (similar to how `issuancesTimestamps` should be paired with the lock period applicable at issuance in the original report). When validating a later spend of that output, check against the attestor list/attestation state that was valid when the output was created rather than re-deriving compliance from the attestor list and attestations valid as of the current `last_ball_mci`. Alternatively, explicitly grandfather already-attested addresses so that subsequent attestor-list updates or address-definition changes cannot retroactively invalidate previously-valid attestations for balances already held.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true` and `attestors: [X]`.
2. Attestor `X` attests holder `H`'s address; `H` receives a transfer of asset `A` — validated successfully via `filterAttestedAddresses`/`validatePaymentInputsAndOutputs` because `H` is attested by `X` and no later `address_definition_changes` exist for `H`.
3. Later, the definer publishes an `asset_attestors` message removing `X` from the attestor list (replacing it with `Y`), per `validateAttestorListUpdate` — this is fully valid and requires no wrongdoing.
4. `H` now attempts to spend the previously received `A` tokens. `readAsset`/`addAttestorsIfNecessary` fetches the new attestor list `[Y]`; `filterAttestedAddresses` finds no attestation of `H` by `Y`, so `objAsset.arrAttestedAddresses` no longer contains `H`.
5. `validatePaymentInputsAndOutputs` rejects the spend with `"owner address is not attested"` (validation.js:2506-2507), even though `H`'s tokens were legitimately compliant at the time of receipt — `H`'s funds are now frozen.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){

		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
