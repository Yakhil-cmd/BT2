### Title
Global cross-repository/cross-stack Commit mutation via unscoped `sha` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) with `Commit.where(sha: params.sha)`, without any join or filter on the repository/stack identified by the webhook's `repository.full_name`. Any commit sharing that sha across any stack in the installation is mutated, so an attacker who controls a throwaway Shipit-tracked repository can forge a `status` webhook whose sha collides with a commit that already exists under a victim stack, injecting a forged `Status` there.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`repository_name_from_verified_payload (payload.dig('repository','full_name')) == stack_id_of_every_Commit_mutated_by_process`

In every other handler that touches `Commit`/`Stack` records, this equality is enforced through the `Handler#stacks` helper: `Repository.from_github_repo_name(repository_name)&.stacks`, e.g. `CheckSuiteHandler#process` does `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [1](#0-0)  and `PushHandler#process` scopes through `stacks.not_archived.where(branch:)` [2](#0-1) .

`StatusHandler`, however, never calls `stacks` or filters by repository at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 
Its `params` schema doesn't even require `repository` [4](#0-3) , confirming the repository binding is never consulted in this handler's logic. The base `Handler` class exposes `stacks`/`repository_name` precisely for this purpose [5](#0-4) , but `StatusHandler` opts out of using it.

Root cause: `sha` is treated globally unique, but `Commit#sha` is only unique per `stack_id` (as evidenced by `Commit.by_sha` operating within `where('sha like ?', ...)` on the model's default scope and by `children` using `self.class.where(stack_id:)...` for stack-scoped lookups) [6](#0-5) . `create_status_from_github!` calls `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` which creates a `Status` scoped to `commit.stack_id`, i.e., whichever stack that particular `Commit` row belongs to [7](#0-6) [8](#0-7) .

Exploit flow: the attacker registers/owns a Shipit-tracked repository (any repo they can push to), constructs a git commit whose sha exactly matches a target commit's sha in a victim's tracked stack (feasible for any commit hash whose full git object — tree, parent, author/committer date, message — the attacker can replicate, e.g. an orphan/duplicated public-repo commit), and sends one `status` webhook naming their own repository with that sha, any `state`. `WebhooksController#create` verifies the signature belongs to the attacker's own repo (a legitimate check that only proves origin, not sha ownership) and dispatches to `StatusHandler.call`. `StatusHandler#process` matches all `Commit` rows across all stacks with that sha, including the victim's, and calls `create_status_from_github!` on each, writing a forged `Status` row under the victim's stack.

Existing guards do not stop this: signature verification (`verify_signature`) only authenticates that the payload came from the attacker's own registered repository/webhook secret, it says nothing about which `Commit` rows may be touched; `ExplicitParameters` schema validates types, not repository scope; there is no `stacks`/repository join anywhere in `StatusHandler`.

### Impact Explanation
A single forged webhook from an attacker-controlled repository writes a `Status` record (and, via `add_status`, potentially fires `deployable_status`/CI-state-derived hooks and unblocks `deployable?` checks) against every stack that happens to have a `Commit` with the matching sha — this includes stacks unrelated to the attacker's repository. This is a payload-for-one-repository mutating another repository's commit/stack state, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). Blast radius scales with the number of stacks sharing that sha (e.g., mirrored/forked repos tracked as separate stacks, or any sha collision the attacker can engineer), and CI status forgery can influence deploy gating (`deployable?`) for the victim stack.

### Likelihood Explanation
Preconditions: the attacker must (a) have some repository tracked by the target Shipit instance (a low bar — anyone can add a public repo/fork as a Shipit stack if the instance allows self-service repo registration, or exploit an existing throwaway/test stack), and (b) produce a commit with an identical sha to a targeted victim commit. Sha collision is trivial when the attacker can push an exact copy of a public commit's underlying git object data (tree, parents, author/committer timestamps, message) into their own repo — this reproduces the identical sha without any hash-collision cryptography, only requires the target commit's full metadata to be public/known. This does not require any Shipit secret, session, or privileged role — only a single unauthenticated `POST /webhooks` with a valid signature from the attacker's own repo's webhook secret (which the attacker owns since it's their repository). Repeatable against any repository/commit whose sha the attacker can reconstruct.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: require `repository` in the params schema, resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`, and restrict the `Commit` lookup to `stacks.joins(...).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerTest < ActiveSupport::TestCase
        test "status webhook for one repository does not mutate commits belonging to other stacks" do
          shared_sha = 'a' * 40

          attacker_stack = shipit_stacks(:shipit) # attacker-controlled stack/repo
          victim_stack_1 = create_stack_with_commit(sha: shared_sha)
          victim_stack_2 = create_stack_with_commit(sha: shared_sha)
          attacker_commit = attacker_stack.commits.create!(sha: shared_sha, ...)

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/forged',
            'repository' => { 'full_name' => attacker_stack.github_repo_name },
          }

          assert_no_difference -> { Status.where(stack_id: [victim_stack_1.id, victim_stack_2.id]).count } do
            StatusHandler.call(payload)
          end
        end
      end
    end
  end
end
```
Expected today (bug present): the `assert_no_difference` fails — `Status.where(stack_id: [victim_stack_1.id, victim_stack_2.id]).count` increases by 2, proving the single webhook from the attacker's repository created `Status` rows for commits belonging to unrelated victim stacks that share the same sha.
