### Title
Webhook signature verification uses `repository.owner.login` while handlers resolve the target repository from `repository.full_name`, allowing cross-organization ReviewStack provisioning - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook using the GitHub App config keyed by `params.dig('repository','owner','login')`, but the dispatched handlers (e.g. `OpenedHandler`) resolve the affected `Shipit::Repository` from a completely different field, `params.dig('repository','full_name')`. These two values are never checked for consistency, so an attacker who controls a webhook secret for *any* organization configured on the Shipit instance can self-sign a payload whose `full_name` names a repository belonging to a different, victim organization.

### Finding Description
Binding claimed by the code (implicitly, never enforced): `organization_verifying_signature == organization_owning(full_name)`, i.e. `params.dig('repository','owner','login') == full_name.split('/').first`.

Trace:
- `WebhooksController#verify_signature` derives `repository_owner` from `params.dig('repository', 'owner', 'login')` and fetches `Shipit.github(organization: repository_owner)`, then verifies `X-Hub-Signature` against that org's `webhook_secret` over the raw body: [1](#0-0)  and [2](#0-1) .
- `Shipit.github(organization:)` looks up the app config by the supplied org name only, with no relation to `full_name`: [3](#0-2) .
- On success, `#create` re-parses the same raw body and dispatches to handlers for the event: [4](#0-3) .
- `OpenedHandler`'s param schema only `requires :repository { requires :full_name, String }` — it does not require or cross-check `repository.owner.login`: [5](#0-4) .
- `OpenedHandler#repository` resolves the target `Repository` purely from `params.repository.full_name`: [6](#0-5) , via `Repository.from_github_repo_name`, which just splits the string on `/`: [7](#0-6) .
- `OpenedHandler#process` then provisions a `ReviewStack` for that repository if `review_stacks_enabled` and the provisioning-behavior conditions are met: [8](#0-7) .

Exploit flow: the Shipit operator has configured multiple GitHub organizations (a documented, supported feature — [9](#0-8) ), one of which (`attacker-org`) belongs to the attacker with its own `webhook_secret`, and another (`victim-org`) tracks a repository with review-stack provisioning enabled. The attacker sends `POST /webhooks` with `X-Github-Event: pull_request`, body `{"action":"opened", ..., "repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...}`, self-signing `X-Hub-Signature` with `attacker-org`'s real, attacker-known `webhook_secret`. `verify_signature` succeeds because it only checks the `attacker-org` HMAC. `OpenedHandler` then resolves and provisions/mutates `victim-org/victim-repo`'s `ReviewStack` using attacker-controlled PR fields.

Existing guards do not catch this: `drop_unhandled_event` and `check_if_ping` are irrelevant, `verify_signature`'s `GithubOrganizationUnknown` rescue only rejects unconfigured *signing* orgs (it never inspects `full_name`), and `ExplicitParameters` schemas in every `pull_request` handler validate types/presence of `full_name` but never compare it against `repository.owner.login`.

### Impact Explanation
An attacker who legitimately controls one tenant organization on a multi-org Shipit deployment can trigger repository-scoped side effects (ReviewStack creation via `OpenedHandler`, archive/unarchive via `ClosedHandler`/`ReopenedHandler`, label capture/PR metadata writes) on **any other tenant's tracked repository**, purely by crafting `full_name` in a self-signed webhook. This is a cross-tenant confused-deputy bug: a payload authenticated for one repository/org mutates another's stack/records, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The attack is fully repeatable against any tracked victim repository with review-stack provisioning enabled, for every `pull_request` sub-event handler that resolves via `full_name` (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `AssignedHandler`, `LabelCapturingHandler`, etc.).

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported), where the attacker owns/administers at least one of the configured GitHub App organizations (and thus its `webhook_secret`), and the victim organization's repository has `review_stacks_enabled` with a compatible `provisioning_behavior`. Given these preconditions — realistic for any Shipit instance hosting multiple independent teams/orgs — the attacker's cost is a single crafted HTTP POST with a correctly computed HMAC-SHA1 over a body they fully control; no GitHub API access, session, or Shipit credentials are needed.

### Recommendation
In `WebhooksController` (or in `Shipit::Webhooks::Handlers::Handler`), after signature verification, extract the organization portion of `repository.full_name` and assert it matches `repository.owner.login`/the organization used to verify the signature; reject the request (422) on mismatch before dispatching to handlers.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Stub `Shipit.github_apps`/`secrets.github` with two orgs: `attacker-org` (webhook_secret: `"attacker-secret"`) and `victim-org` (webhook_secret: `"victim-secret"`).
2. Create `Shipit::Repository.create!(owner: "victim-org", name: "victim-repo", review_stacks_enabled: true, provisioning_behavior: "allow_all")`.
3. Build a `pull_request` "opened" JSON body with `repository: { owner: { login: "attacker-org" }, full_name: "victim-org/victim-repo" }` plus required PR fields.
4. Compute `signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-secret", body)`.
5. `post :create, body: body, as: :json` with headers `X-Github-Event: pull_request`, `X-Hub-Signature: signature`.
6. Assert `response.status == 200` (signature accepted) and `assert_difference -> { Shipit::ReviewStack.count }, 1` — then assert the created `ReviewStack.repository.full_name == "victim-org/victim-repo"`, proving cross-org provisioning occurred using only `attacker-org`'s secret.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

    someothergithuborg:
