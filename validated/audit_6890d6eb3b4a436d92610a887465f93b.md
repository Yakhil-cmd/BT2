### Title
Type-coercion mismatch between the unstable and stable "in data feed" lookup paths causes AA oracle-condition results to flip between provisional and final execution - ([File: data_feeds.js])

### Summary
The CVE describes CUPS treating `localhost.localdomain` as an equivalent, trusted identity to `127.0.0.1` even though the name can resolve to something else — i.e. two representations that are treated as "the same" for a security decision without a strict, canonical equality check. `data_feeds.js` has an analogous class of bug: for **unstable** (not-yet-final) data feeds used by AA address/data-feed conditions, values are compared using loose, cross-type coercion (`value === feed_value || value.toString() === feed_value.toString()`), whereas the **stable**, on-disk key-value lookup path strictly separates numeric and string data feed values by type-prefixed keys (`'n\n...'` vs `'s\n...'`). A `feed_name`/`value` pair that "matches" via the loose unstable-path comparison is not guaranteed to match via the strict stable-path lookup (and vice versa), so an AA's `in data feed` / `data_feed` condition can evaluate differently depending on whether the referenced oracle unit is still unstable or has become stable.

### Finding Description
`dataFeedExists()` in `data_feeds.js` has two code paths:

1. When `bAA` is true and the oracle unit(s) are still unstable, matching is done in-memory by iterating `storage.assocUnstableMessages` (lines 34–94). For the `=` relation it does:
```
if (value === feed_value || value.toString() === feed_value.toString())
    bFound = true;
``` [1](#0-0) 
This treats `5` (number) and `"5"` (string) as equal, purely via `toString()` coercion.

2. Once the oracle unit is stable, the lookup falls through to `dataFeedByAddressExists()`, which builds a **type-tagged** key:
```
var key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value;
```
where `prefixed_value` is prefixed with `'n\n'` for anything that looks numeric and `'s\n'` otherwise: [2](#0-1) 
This is a strict range/prefix scan over the key-value store, so a query for value `5` (interpreted as numeric, `'n\n...'` key) will never match a stored feed value that was written/queried as the string `"5"` under the `'s\n...'` namespace — unlike the unstable path, which considers them equal via `toString()`.

The same asymmetry exists in `readDataFeedValue()`'s unstable-candidate branch, which also uses the loose check `value === feed_value || value.toString() === feed_value.toString()`: [3](#0-2) 

Because AAs are evaluated speculatively/provisionally while their trigger's or referenced oracle's units are still unstable (bounce-vs-execute previews, wallet/GUI previews, and any consumer relying on `bAA` fast-path results), and then re-evaluated deterministically once MC advances and the same units become stable, the same `in data feed` / `data_feed` expression can return **true while unstable** and **false once stable** (or vice versa) purely because of this type-coercion mismatch — with no attacker action against the oracle needed, only an oracle innocently posting a value whose runtime type doesn't match what the AA/asset condition author assumed.

### Impact Explanation
An AA definition (or an asset/address spending condition) using `in data feed` / `data_feed` with a numeric-looking value can be triggered/allowed based on the transient (unstable) result and then invalidated once the network reaches consensus on the final (stable) result, or the reverse. This is a **node/consensus disagreement on evaluation outcome depending on timing (stability) of oracle data**, which can:
- Cause an AA to release/lock funds based on a provisional trigger evaluation that differs from what all nodes will agree on once the unit stabilizes, leading to fund loss/freezing or bounced-vs-executed mismatches perceived by users/services that trust the provisional result.
- Cause different observers (light wallets/services previewing AA state while units are unstable vs. full nodes after finality) to disagree on whether a condition (spending condition, definition condition using `in data feed`) is satisfied, undermining validity guarantees relied upon for accepting/relaying units.

This falls under "AA fund loss or freezing" and "node disagreement on validity/stability" per the scope rules, and is reachable purely by an unprivileged AA author writing a normal `in data feed` condition and an oracle innocently posting a differently-typed value — no privileged/hub/peer access required.

### Likelihood Explanation
Any AA author can add an `in data feed` condition or `data_feed[...]` formula referencing an oracle and a numeric-looking value; oracles routinely post values that can be either numeric or string depending on their feed implementation (the type is not pinned by protocol — `data_feeds.js`/`formula/evaluation.js` accept both `typeof value === 'string'` and `typeof value === 'number'`). Any AA trigger that lands while a relevant oracle unit is still unstable, and any component previewing/estimating AA results before finality, will hit this asymmetric-matching code path. This requires no adversarial control of the network, hub, or oracle beyond normal, everyday feed-posting behavior.

### Recommendation
Make the unstable/in-memory matching in `dataFeedExists()` and `readDataFeedValue()` use the exact same type-discrimination rules as the stable KV-store lookup: only consider `value` and `feed_value` equal for `'='`/`'!='` if their runtime types match (both numeric or both non-numeric strings), mirroring the `'n\n'`/`'s\n'` prefix split used in `dataFeedByAddressExists()`. Remove or gate the `value.toString() === feed_value.toString()` fallback so it cannot introduce matches that the stable path would reject (or vice versa), ensuring provisional and final AA evaluation of `in data feed`/`data_feed` are always consistent.

### Proof of Concept
1. Oracle `O` posts a `data_feed` message with `{"price": "100"}` (string) in unit `U1`.
2. An AA (or an asset spending condition) contains `['in data feed', [['O'], 'price', '=', 100]]` (numeric `100`).
3. While `U1` is still unstable, an AA trigger referencing this condition is evaluated via the `bAA` branch of `dataFeedExists()`:
   - `value = 100` (number), `feed_value = "100"` (string, from `payload['price']`).
   - `value.toString() === feed_value.toString()` → `"100" === "100"` → `true`, so the condition is satisfied and the AA executes the "true" branch (e.g., releases funds).
4. Once `U1` becomes stable, the exact same query is re-evaluated (e.g., by another node performing full validation, or by the same node re-checking) via `dataFeedByAddressExists()`:
   - The query key is built from numeric `100` → `'n\n...'` prefix.
   - The stored feed value `"100"` was written/keyed as a string → `'s\n...'` prefix.
   - The prefix-range scan for `'n\n...'` never touches the `'s\n...'` entry → `bFound = false`.
5. Result: the condition that was satisfied (and acted upon) while unstable is not satisfied once the unit is final — a concrete divergence between provisional and final AA/condition evaluation for the same oracle post and the same `in data feed` expression. [4](#0-3) [5](#0-4) [6](#0-5)
