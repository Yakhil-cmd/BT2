### Title
Webhook signature only authenticates the payload's declared `repository.owner.login`, but event handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is the same trust-binding class of bug as the Solidity C-04 finding: a security-relevant decision (there, session liveness; here, "which GitHub organization signed this request") is computed from one representation of the data, while the state-mutating logic downstream consumes a *different, unchecked* representation of the same conceptual field. In Shipit, `WebhooksController#verify_signature` selects the signing key/app by reading `repository.owner.login` out of the raw JSON body, but the handler pipeline that actually creates jobs, updates commits, or unlocks provisioning reads `repository.full_name` from that same attacker-supplied body — and the two are never cross-checked.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to pick the verifying `GitHubApp`/secret from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) purely to select which `Shipit.github(organization: ...)` app/secret to HMAC-verify against — it does not constrain which repository is subsequently acted upon.

Once the signature check passes, `create` re-parses the same raw body and dispatches it to handlers unconditionally: [3](#0-2) 

Every handler determines the target repository/stacks using a *different* key from the identical payload: [4](#0-3) 

`repository_name` reads `payload.dig('repository', 'full_name')`, not `repository.owner.login`. Nothing in `Handler`, `Handler.call`, or any subclass (e.g. `PullRequest::OpenedHandler#repository`) re-derives or validates that `repository.full_name`'s owner matches the organization whose secret validated the HMAC: [5](#0-4) 

The HMAC itself is computed over the entire raw body: [6](#0-5) 

so the check only proves "whoever crafted this exact JSON knows organization X's `webhook_secret`" — it proves nothing about which `repository.full_name` is inside that JSON. Because `Shipit.github(organization:)` is a multi-tenant lookup, distinct organizations configured in Shipit have distinct app configs/secrets. An attacker who legitimately knows (or controls) the `webhook_secret` for **their own** organization can freely set `repository.owner.login` to their own org (so the correct/known secret is selected and the signature validates) while setting `repository.full_name` to any other tracked repository's `owner/name`, since that field is read from a completely separate JSON path never covered by the authentication decision.

**Binding broken:** `organization authenticated (repository.owner.login, used to pick the verifying secret) == repository written (repository.full_name, used by every handler to select stacks/commits/jobs)`. Before the fix this equality is implicitly assumed by the security model; after crafting the payload as above, it is false, and the engine still processes the event as legitimate for the attacker-chosen `full_name`.

### Impact Explanation
Because handlers key off `repository.full_name` for the `push` (`GithubSyncJob` enqueue), `status`, `check_suite`, and other events, an attacker who has valid signing credentials for any organization/app registered with this Shipit instance can forge push/status/check_suite/deployment webhook events that are attributed to and processed against **any other tracked repository/stack**, regardless of organization boundaries. This can trigger unwanted sync jobs, fabricate commit statuses/check-run results that feed into deploy-gating logic, or drive review-stack provisioning for pull requests on repositories the attacker does not own — an unauthorized influence over another repository's stack state and, transitively, its ability to ship.

### Likelihood Explanation
Exploitation requires the attacker to control (or know) the `webhook_secret` for at least one organization/app configured in this Shipit instance — a materially lower bar than repository write access or an `ApiClient`/session token on the *target* repository, since Shipit is explicitly multi-tenant (`Shipit.github(organization: ...)`) and organizations can differ in trust level. No repository write access, GitHub App private key, or session is needed for the target repository; only for the attacker's own, unrelated organization.

### Recommendation
After signature verification, re-derive (or validate) the organization from the same field used by the handlers (`repository.full_name`'s owner segment, or `repository.owner.login`) and reject the webhook if the two disagree, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) and return unless verified
  head(422) and return unless repository_owner_matches_full_name?
  ...
end
```
and make `Handler#repository_name` cross-check that the resolved repository's owner equals the authenticated `repository_owner`.

### Proof of Concept
1. Attacker registers/uses their own GitHub organization `attacker-org`, which is a configured organization in this Shipit instance (`Shipit.github_apps` includes `attacker-org` with a known `webhook_secret`).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_for_attacker_org, body)` — computable because they know `attacker-org`'s secret.
4. `verify_signature` calls `repository_owner` → `"attacker-org"`, looks up `Shipit.github(organization: "attacker-org")`, and the HMAC check passes since the attacker used exactly that secret.
5. `create` dispatches the parsed payload to `Shipit::Webhooks.for_event('push')`, whose handler reads `repository.full_name` → `"victim-org/victim-repo"` and enqueues `GithubSyncJob` (or otherwise mutates state) for the victim's tracked stack, despite the request never being authenticated against `victim-org`'s credentials.

**Note on verification confidence:** I confirmed the code-level mismatch (`repository_owner` vs `repository_name`/`full_name`) directly in `app/controllers/shipit/webhooks_controller.rb` and `app/models/shipit/webhooks/handlers/handler.rb`. I was not able to fully inspect `lib/shipit.rb`'s `Shipit.github_apps`/`github` multi-tenant configuration structure in this pass (only located via grep, not read in full) to conclusively confirm that webhook secrets are always organization-scoped and attacker-obtainable in a real deployment; this detail affects exploitability but not the underlying architectural flaw, which is clearly present in the reachable code.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
