### Title
ERC20Transactor credits nominal (not actual) transfer amount into XCM holding, allowing fee-on-transfer/deflationary ERC20 tokens to desync the shared checking-account balance from XCM accounting - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` (wired into Asset Hub Westend's `AssetTransactors`) is the FRAME analog of the BvB `matchOrder`/`settleContract` bug: it moves ERC20 tokens via `pallet_revive::bare_call` to/from a shared `ERC20TransfersCheckingAccount`, but never verifies the actual amount the checking account gained/lost. It only checks that the `transfer()` call returned `true`. For fee-on-transfer/deflationary ERC20 contracts (fully attacker-controllable, matched purely by contract address with no registry/allow-list) this causes the XCM executor's `AssetsInHolding` register to be over-credited relative to the checking account's real token balance, exactly mirroring the report's root cause: "no check to determine the actual amount received."

### Finding Description
`ERC20Matcher` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:159-160`) matches *any* `Location` of the form `AccountKey20 { key, .. }` to an ERC20 contract address, with no permission list — any user can deploy an arbitrary "ERC20" contract via `pallet_revive` and reference it in an XCM `Asset::id`.

In `withdraw_asset_with_surplus` (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:150-216`), the transactor:
1. Calls the contract's `transfer(checking_address, amount)` from the user's mapped account.
2. Checks only that the call succeeded and returned `true`.
3. Unconditionally credits the XCM holding register with the full nominal `amount`:
```
Ok((
    AssetsInHolding::new_from_fungible_credit(
        what.id.clone(),
        Box::new(Erc20Credit(amount)),
    ),
    surplus,
))
```
There is no balance-before/balance-after check on `TransfersCheckingAccount`. If the contract implements a transfer fee/burn/rebase (deflationary token), the checking account actually receives `amount - fee`, yet the XCM executor believes `amount` was received.

Symmetrically, `deposit_asset_with_surplus` (lines 225-306) instructs the checking account to `transfer(beneficiary, amount)` for the full nominal `amount` taken from holding, again without verifying what the beneficiary actually received or whether the checking account's real balance can cover it.

`TransfersCheckingAccount` (`ERC20TransfersCheckingAccount`, `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs:213-237`) is a single shared pooled account (`PalletId(*b"py/revch")`) used for *all* ERC20 assets processed by this transactor, across all users and all XCM programs (local `execute`, and cross-chain reserve transfers routed through Asset Hub). Because the transactor trusts the nominal amount rather than measuring the real delta, every fee-on-transfer ERC20 interaction silently skims real tokens out of the checking account while the XCM accounting (and any downstream logic built on `AssetsInHolding`, e.g. depositing to a beneficiary, or reserve-transferring to another chain) still operates on the un-discounted nominal amount. This is the direct analog of BvB's `matchOrder` crediting `takerPrice`/`makerPrice` without checking actual `safeTransferFrom` proceeds.

### Impact Explanation
Over repeated use, the shared checking account's real ERC20 balance drifts below the sum of nominal amounts the protocol believes it holds/has moved. This can:
- Cause subsequent, unrelated users' `deposit_asset` legs to fail (the checking account cannot fulfill the nominal `transfer(beneficiary, amount)` because its real balance is short due to earlier fee-skimmed withdrawals) — denial of service/stuck funds for honest users, matching the report's "functions become uncallable" impact.
- More severely, since `AssetsInHolding` credited from `withdraw_asset_with_surplus` can be consumed by other parts of the XCM program (e.g., `deposit_asset` to a different beneficiary within the same message, or forwarded onward), a user can withdraw nominal `amount` of a fee-on-transfer token they deployed themselves and have the executor believe/act as if the full `amount` moved, effectively extracting more value out of the shared checking account pool than they actually deposited into it, at the expense of the account's balance backing other users' assets.

This matches the Sherlock report's Medium classification: no complete unbacked issuance of a system-wide asset (the token itself is fully attacker-controlled and self-issued, not a system-backed asset like DOT/USDT), but a genuine integrity break/fund-loss vector localized to the shared `ERC20TransfersCheckingAccount` and the ERC20-token users of it.

### Likelihood Explanation
- The entry point is fully permissionless: a normal signed account can call `pallet_xcm::execute`/`transfer_assets` (confirmed reachable via the existing test `non_existent_erc20_will_error`, `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1938-1976`, which drives exactly this code path with `withdraw_asset` on an `AccountKey20` asset).
- No privileged role, governance action, or malicious validator/collator is required — the attacker only needs to deploy an ordinary Solidity/PolkaVM contract implementing `IERC20` with a transfer fee (a common, legitimate pattern), then reference that contract's address as an XCM asset id.
- `ERC20Matcher`/`IsLocalAccountKey20` impose no allow-list, so any deployed contract is automatically eligible.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the checking account's (or beneficiary's) actual ERC20 balance via `balanceOf` immediately before and after the `transfer` call, and use the observed delta — not the requested `amount` — to construct the `AssetsInHolding` credit (in `withdraw_asset_with_surplus`) and to determine success/failure (in `deposit_asset_with_surplus`). Alternatively, explicitly document and enforce (e.g., via a runtime-level allow-list of known-safe ERC20 contracts) that only asset contracts with strictly conforming, non-fee, non-rebasing `transfer` semantics may be registered as ERC20 assets for this transactor, since `MatchesFungibles` currently accepts any `AccountKey20`-shaped location without such a check.

### Proof of Concept
No local Rust/FRAME reproduction was executed in this session (tool access ended before I could write/run a new integration test). Existing test infrastructure demonstrates the reachable path and the mechanism precisely: `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs:1938-1976` (`non_existent_erc20_will_error`) and `:2026-2081` (`smart_contract_does_not_return_bool_fails`) both show a signed user calling `PolkadotXcm::execute` with a `withdraw_asset` targeting an `AccountKey20` ERC20 location, which is dispatched into `ERC20Transactor::withdraw_asset_with_surplus`. A full PoC would extend these tests by deploying a minimal PolkaVM/Solidity ERC20 contract whose `transfer` function moves `amount - fee` to the recipient while still returning `true`, then asserting: (1) the XCM program completes as `Complete`/`Ok`, (2) `Erc20Credit`/holding register reflects the full nominal `amount`, and (3) `IERC20::balanceOf(checking_account)` only increased by `amount - fee`, demonstrating the accounting mismatch. This construction was not executed; its outcome is inferred from direct code reading of `withdraw_asset_with_surplus`'s unconditional `Erc20Credit(amount)` construction, not from an actual test run.
