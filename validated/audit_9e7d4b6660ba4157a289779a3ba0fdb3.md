### Title
Missing global replay protection on L1 Bitcoin lockup proofs allows double-counting the same BTC lock across multiple pox-5 bond registrations - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`register-for-bond`'s BTC-lockup verification path (`verify-l1-lockups` → `validate-l1-lockup`) only de-duplicates outpoints *within a single call*, via a `seen-outpoints` accumulator that is freshly initialized to `(list)` on every invocation. There is no contract-wide map recording which `(txid, output-index)` outpoints have already been consumed by a previous `register-for-bond`/roll-over. A staker can therefore present the exact same, still-valid L1 lockup proof to register a second (or later) protocol bond while an earlier bond that already counted that same BTC output is still active, causing the same locked BTC to be counted as `amount-sats` for two separate bond commitments simultaneously.

### Finding Description
`verify-l1-lockups` initializes the fold accumulator per call: [1](#0-0) 

`validate-l1-lockup` rejects only outpoints already seen *within that same accumulator* (`ERR_DUPLICATE_LOCKUP_OUTPOINT` against `seen-outpoints`, which starts empty each call): [2](#0-1) 

Nothing in this function, or in `register-for-bond`, records the outpoint in persistent contract state (e.g., a `used-l1-lockup-outpoints` map) so that a later, independent call to `register-for-bond` (potentially for a different `bond-index`) can detect that the exact same Bitcoin output was already relied upon for an existing, still-active bond membership: [3](#0-2) 

`register-for-bond` writes the new bond's `amount-sats` into `protocol-bond-memberships` via `map-set` (overwriting, not `map-insert`), and unconditionally *adds* `sats-total` to the new bond-index's running total in `protocol-bonds-total-staked`: [4](#0-3) 

Because the `roll-sbtc` accounting path only reconciles the *sBTC-custodied* balance delta (`old-sbtc`/`new-sbtc`), which is `u0` for `is-l1-lock` bonds, there is no mechanism reconciling or decrementing the prior bond's staked-sats total when the same L1 output is reused to open a new membership. The only protections on the L1 lockup are: minimum unlock height, BTC locktime threshold, script-hash match, amount match, intra-call outpoint uniqueness, header verification, and merkle proof — none of which prevent reusing an already-counted, still-locked BTC output for a second bond.

### Impact Explanation
This breaks the equality between "sats locked on Bitcoin" and "sats credited to the staker/signer inside pox-5." The same BTC lockup can be double-counted across bond memberships, inflating `protocol-bonds-total-staked`, the staker's `amount-sats` used for reward-share computation, and the signer's aggregate stake used for reward-weight/threshold calculations — without any additional Bitcoin ever being locked. This is a direct "double-counting a commitment" bug per the specified impact categories (Critical: double-counting a commitment or reward), since it lets a staker or colluding signer claim reward shares proportional to sats that were never doubled on the Bitcoin chain.

### Likelihood Explanation
Exploitation requires only an unprivileged staker with a valid, still-unspent L1 timelock output and the ability to call `register-for-bond` more than once (e.g., for a second bond period, or via a signer-manager the attacker controls) while citing the identical `(tx, output-index, header)` proof. No admin, miner, or other-user key is required — only the staker's own transactions. The primary uncertainty (not fully confirmed due to time/tool limits) is whether `update-bond-registration` or other bond-lifecycle logic elsewhere in `pox-5.clar` independently reconciles/decrements the old bond's staked-sats when the underlying L1 output is reused; I was not able to inspect the full `get-protocol-bond`/`update-bond-registration` bodies to rule this out definitively.

### Recommendation
Add a persistent, contract-wide map (e.g., `used-l1-lockup-outpoints: {txid, output-index} -> bool`) and check/insert it inside `validate-l1-lockup` (or immediately after `verify-l1-lockups` succeeds) instead of, or in addition to, the per-call `seen-outpoints` list, so that a given Bitcoin outpoint can only ever back one live bond/stake commitment for its entire locked duration. Clear or allow re-use of the entry only once the bond period naturally unwinds (i.e., once the previous membership crediting that outpoint has been fully unwound in `protocol-bonds-total-staked`).

### Proof of Concept
1. Staker locks BTC output `O` on L1 with a timelock script committing to their principal, per `construct-lockup-output-script`.
2. Staker calls `register-for-bond(bond-index=0, ..., btc-lockup=ok({outputs:[O], ...}))`. `validate-l1-lockup` succeeds; `protocol-bond-memberships[staker] = {bond-index:0, amount-sats: X, ...}`; `protocol-bonds-total-staked[0] += X`.
3. While bond 0 is still active (BTC output `O` is still locked/unspent), the staker registers for a second bond: `register-for-bond(bond-index=6, ..., btc-lockup=ok({outputs:[O], ...}))` using the exact same proof for `O`.
4. `verify-l1-lockups` re-initializes `seen-outpoints` to `(list)`, so `O` passes all checks again; `protocol-bond-memberships[staker]` is overwritten to bond-index 6 with `amount-sats: X`, and `protocol-bonds-total-staked[6] += X`, while `protocol-bonds-total-staked[0]` (still reflecting bond 0's now-stale membership) is never decremented for output `O`.
5. Result: the single BTC-locked amount `X` is now counted toward staked totals for both bond 0 and bond 6 simultaneously, inflating aggregate stake and reward eligibility beyond what is actually locked on Bitcoin.
