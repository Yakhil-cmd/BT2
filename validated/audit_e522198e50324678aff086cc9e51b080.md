### Title
Webhook organization used for signature verification is decoupled from the repository the event acts upon, allowing unauthenticated forgery of GitHub events for arbitrary tracked stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the untrusted JSON payload [1](#0-0) . Every event handler, however, resolves *which stack to act on* using a completely different, independently-controlled payload field: `repository.full_name` [2](#0-1) . Nothing enforces that these two fields describe the same repository. Combined with the fact that `verify_webhook_signature` unconditionally accepts the request when the resolved organization has no `webhook_secret` configured [3](#0-2) , an attacker can pick an organization entry that is present in `Shipit.github` config but has a blank secret (the shipped default templates literally configure `webhook_secret: # nil` [4](#0-3) [5](#0-4) ), and set `repository.full_name` in the same payload to point at a *different* repository/stack that Shipit actually tracks.

### Finding Description
The trust binding that should hold is:
`organization authenticated by verify_webhook_signature (payload.repository.owner.login) == organization that owns the repository the handler mutates (derived from payload.repository.full_name)`

This equality is never checked:
- `WebhooksController#repository_owner` reads `params.dig('repository','owner','login')` (fallback `organization.login`) purely to pick a `Shipit.github(organization:)` instance for HMAC verification [6](#0-5) .
- `Shipit::GithubApp#verify_webhook_signature` returns `true` immediately if that organization's config has no `webhook_secret` set [7](#0-6) , meaning any signature (or none) is accepted for that org.
- After verification, `WebhooksController#create` blindly hands the raw JSON to every registered handler for the event [8](#0-7) .
- Handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*Handler`s, `MembershipHandler`, etc.) all locate the target `Stack`/`Repository` via `Handler#repository_name`, i.e. `payload.dig('repository','full_name')` [2](#0-1)  — a field completely separate from the one used to pick the verifying secret, and one the attacker fully controls since the whole request body is attacker-supplied.

Because the Shipit config format explicitly supports multiple independent GitHub orgs, each with its own (possibly-empty) `webhook_secret` [9](#0-8) , any single misconfigured/blank-secret org entry becomes a skeleton key: an unauthenticated caller sends `X-Github-Event`, `repository.owner.login = <org-with-blank-secret>`, and `repository.full_name = <victim-org/victim-repo>`. Signature verification passes unconditionally (no secret to check against), yet the event is processed against the victim repository's stacks.

### Impact Explanation
This lets an unauthenticated attacker (no `ApiClient` token, no Shipit session, no GitHub credentials) forge arbitrary GitHub webhook events for any repository/stack Shipit tracks, as long as one org entry in the deployment's config lacks a `webhook_secret` (the documented/shipped default). Concretely this allows:
- Forged `push` events causing `GithubSyncJob` to ingest attacker-chosen commit SHAs into a victim stack's history [10](#0-9) .
- Forged `status` events creating fabricated "success" CI statuses on arbitrary commits, which downstream deployability/continuous-deployment logic relies on to gate/kick off deploys.
- Forged `pull_request`/`membership` events manipulating review-stack creation, PR labels, or team/user membership.

Since continuous-deployment stacks act on synced commits/statuses without further human review, this chain can escalate into an unauthorized deploy of attacker-influenced state, matching the Critical/High impact bar (unauthorized deploy, or at minimum unauthenticated manipulation of stack/task state).

### Likelihood Explanation
Likelihood is Medium-to-High: it requires no credentials at all, only that the operator's `Shipit.github` config contain at least one organization entry with a blank/unset `webhook_secret` — which is exactly what every shipped configuration template defaults to (`webhook_secret: # nil`) [4](#0-3) [11](#0-10) . Multi-org deployments (explicitly supported and documented) are especially exposed since onboarding any new tenant org before its webhook secret is configured immediately weakens the entire instance's webhook trust boundary for *every* tracked repository, not just that tenant's.

### Recommendation
Bind the two identities together before dispatching to handlers: verify that `repository.owner.login` (used to select the signing organization) matches the owner segment of `repository.full_name` (used to resolve the target stack), and reject the request otherwise. Additionally, do not treat a missing `webhook_secret` as automatic verification success — require every configured organization to have a non-blank secret, or refuse to process events for organizations without one.

### Proof of Concept
1. Deploy Shipit with a multi-org config where `OrgWithoutSecret` has `webhook_secret: nil` (default) and `VictimOrg/victim-repo` is a tracked stack with its own properly-secured webhook secret.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
No `X-Hub-Signature` header (or any garbage value) is required, since `verify_webhook_signature` short-circuits to `true` for `OrgWithoutSecret` [7](#0-6) .
3. `WebhooksController#verify_signature` passes; `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` from `payload.dig('repository','full_name')` = `"VictimOrg/victim-repo"` [2](#0-1)  and enqueues `GithubSyncJob` against the victim's real stack — despite the request never having been authenticated by `VictimOrg`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
