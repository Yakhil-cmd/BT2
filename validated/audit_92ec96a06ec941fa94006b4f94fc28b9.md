### Title
Leading-zero iteration/max_iterations values pass regex but crash bash's octal arithmetic evaluator, bypassing Stop enforcement - ([File: plugins/ralph-wiggum/hooks/stop-hook.sh])

### Summary
`ITERATION` and `MAX_ITERATIONS` are validated only against `^[0-9]+$` [1](#0-0)  before being used in bash `[[ ]]` numeric comparisons and `$(( ))` arithmetic, both of which apply bash's octal-on-leading-zero parsing rules. A state-file value such as `max_iterations: 09` or `iteration: 08` passes the regex but is an invalid octal literal, causing bash's arithmetic evaluator to throw a fatal error and terminate the script before the loop-cap check or the JSON `"decision":"block"` output is produced.

### Finding Description
The regex `^[0-9]+$` [2](#0-1)  and `^[0-9]+$` for `MAX_ITERATIONS` [3](#0-2)  only check that the string is composed of decimal digits; it does not exclude leading zeros. These values are then fed directly into bash arithmetic contexts:
- `[[ $MAX_ITERATIONS -gt 0 ]] && [[ $ITERATION -ge $MAX_ITERATIONS ]]` [4](#0-3) 
- `NEXT_ITERATION=$((ITERATION + 1))` [5](#0-4) 

Bash's arithmetic evaluator interprets any numeral with a leading `0` as octal. A value like `08` or `09` is not a valid octal literal (digits 8/9 don't exist in base 8), and bash raises a fatal "value too great for base" error during arithmetic evaluation. In a non-interactive shell this is a hard/fatal parsing error distinct from an ordinary non-zero exit status caught by `set -e`; it aborts script execution immediately at that point, regardless of `set -euo pipefail` semantics for compound commands like `if`.

Because the crash happens either inside the `if [[ ... ]]` max-iterations check (line 51) or in the unconditional `$(( ITERATION + 1 ))` expansion (line 131), execution never reaches the code paths that either (a) `rm` the state file and cleanly stop the loop, or (b) emit the `jq -n ... '{"decision":"block", ...}'` JSON that is supposed to feed the prompt back and block the Stop event [6](#0-5) . The script instead dies with an uncaught bash arithmetic error, producing no valid hook JSON output and a non-zero/undefined exit status. Additionally, even for "valid" octal literals like `0123` (all digits 0-7), the comparison silently uses the octal value (83 decimal) instead of the intended decimal value (123), corrupting the iteration/cap semantics without any crash or warning.

An attacker who can influence the repository's `.claude/ralph-loop.local.md` (e.g., via a committed/malicious repo state, or any flow that writes attacker-controlled content into this file) can set `iteration: 09` or `max_iterations: 08` to trigger this crash path.

### Impact Explanation
This is a Stop-hook safety mechanism whose entire purpose is to prevent premature session exit and enforce a max-iteration safety cap. A crash before the block-decision JSON is emitted means the hook fails to communicate a blocking decision to Claude Code for that Stop event; depending on how the hook runner treats an unparseable/erroring hook, this results in either the intended "continue loop" blocking behavior being skipped (fail-open on Stop enforcement) or the max-iteration safety cap silently not being applied (since the crash occurs inside the very check meant to enforce it). This matches a hook/deny-enforcement bypass via crash rather than a clean, auditable stop.

### Likelihood Explanation
Preconditions are narrow but plausible per the question's scope: the attacker needs write access to `.claude/ralph-loop.local.md` (e.g., a committed malicious state file in a repository consumed via `/ralph-loop`). Given that, triggering the bug is deterministic and repeatable — any value like `08`, `09`, `018`, `0009`, etc. reliably reproduces the bash octal-parse fatal error every time the Stop hook runs while that state file is present.

### Recommendation
Reject or normalize leading zeros before use in arithmetic: change the validation regex to `^(0|[1-9][0-9]*)$` (disallowing leading zeros except literal `0`), or strip leading zeros with `10#` forced-base parsing (e.g., `$((10#$ITERATION))`) before any `[[ ]]` or `$(( ))` usage, and wrap all arithmetic in explicit error handling so a parse failure is caught and reported as state-file corruption (consistent with the existing corruption-handling pattern) rather than allowed to crash the script silently.

### Proof of Concept
Unit/fuzz test plan for `stop-hook.sh`:
1. Create `.claude/ralph-loop.local.md` with frontmatter `iteration: 1` and `max_iterations: 08`, plus a valid prompt body.
2. Pipe a minimal valid hook JSON (`{"transcript_path": "..."}`) to `stop-hook.sh` via stdin and run it, capturing stdout, stderr, and exit code.
3. Assert expectation: the script should NOT crash with a bash "value too great for base" error; it should either emit the corruption warning and `rm` the state file with `exit 0`, or correctly perform the `-gt`/`-ge` comparison and emit a proper JSON decision.
4. Repeat with `iteration: 09`, `max_iterations: 018`, and other invalid-octal leading-zero values, and separately with valid-octal-looking values like `iteration: 0123` to assert the comparison uses the intended decimal semantics (123) rather than octal (83).
5. Fail the test if any of these inputs cause the script to terminate via an uncaught bash arithmetic error before reaching either the corruption-handling `rm`+`exit 0` path or the `jq -n '{"decision":"block", ...}'` output.
