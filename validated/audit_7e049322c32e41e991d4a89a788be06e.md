### Title
Incomplete range-overlap check for `headers_commission`/`witnessing` inputs allows double-crediting of stable MC-output commissions - ([File: validation.js])

### Summary
`nouveau/uvmm` computed the unmap range for a remap by mixing fields from two different (prev/next) range descriptors instead of consistently deriving `[start,end)` from one object, so the resulting unmap window did not match the range that was actually being replaced, corrupting memory outside the intended boundary. `ocore`'s `validatePaymentInputsAndOutputs` has an analogous boundary-calculation gap for `headers_commission`/`witnessing` inputs: the range `[from_main_chain_index, to_main_chain_index]` claimed by an input is checked for overlap against a peer/competing unit using only the `from_main_chain_index` endpoint, not the full range, so two competing (non-including) units can claim overlapping-but-differently-anchored MC-index ranges without being flagged as double-spenders of the same commission funds.

### Finding Description
For `type === "headers_commission"` or `"witnessing"` inputs, the code builds the double-spend detection predicate using only the `from_main_chain_index` and `address`: [1](#0-0) 

```
doubleSpendWhere = "type=? AND from_main_chain_index=? AND address=? AND asset IS NULL";
doubleSpendVars = [type, input.from_main_chain_index, address];
```

This is used later to find other, non-excluded competing units claiming the same commission input and to decide which one stays “good”: [2](#0-1) 

The only genuine overlap protection is `readNextSpendableMcIndex`, which computes the next allowed `from_main_chain_index` as `MAX(to_main_chain_index)+1` over already-accepted (non-conflicting) inputs for that address/type: [3](#0-2) 

and is enforced as a strict lower bound: [4](#0-3) 

```
mc_outputs.readNextSpendableMcIndex(conn, type, address, objValidationState.arrConflictingUnits, function(next_spendable_mc_index){
    if (input.from_main_chain_index < next_spendable_mc_index)
        return cb(type + " ranges must not overlap");
```

The overlap protection only prevents a *single* unit's descendant chain from re-using MCIs already claimed by units it includes (because `arrConflictingUnits` excludes competing units from that computation). For two units on parallel, non-including branches (bona fide "conflicting units" in Obyte's nonserial-resolution sense), each independently computes its own `next_spendable_mc_index` while excluding the other, so each can pick a `from_main_chain_index` that differs from the other's, even though their `[from,to]` windows overlap in the underlying `headers_commission_outputs`/`witnessing_outputs` rows. Because the double-spend SQL predicate only matches on the exact `from_main_chain_index` value (not a range/overlap test against `to_main_chain_index`), such overlapping-but-differently-anchored claims are never linked as double-spends of the same commission money, and `calcEarnings`/`calcWitnessEarnings` will independently sum the same underlying MCI rows into `total_input` for both units: [5](#0-4) [6](#0-5) 

This mirrors the kernel bug class: a range/boundary computation that is derived from a partial/mismatched subset of the fields that define the interval (`addr`+`range` vs `start`/`end` in nouveau; `from_main_chain_index` alone vs the full `[from,to]` interval here), leading the validator to miss the true overlap between two claims on the same underlying resource.

### Impact Explanation
If two parallel, mutually non-including units by the same author address each successfully claim overlapping `headers_commission`/`witnessing` ranges (different `from_main_chain_index` but overlapping windows), and both branches later stabilize as `good`/serial (e.g., because the "temp-bad"/"final-bad" nonserial resolution never triggers for this particular pair, since the double-spend join never matched them), the same pool of header/witnessing commission funds is credited twice to the network's units. That is a supply-inflation-style bug: `total_input` for two different valid units is backed by the same real commission money in `headers_commission_outputs`/`witnessing_outputs`, letting the attacker (as an ordinary unit poster) extract commission value that does not exist, i.e., unauthorized creation of spendable balance.

### Likelihood Explanation
Reachability requires only posting two units from the same address that fork (are mutually non-descendant) and choosing `from_main_chain_index`/`to_main_chain_index` windows that overlap without sharing an identical `from_main_chain_index` — something purely under the poster's control (an ordinary unit author, no privileged access needed). The harder part is arranging for `readNextSpendableMcIndex`, computed separately for each branch with the other branch excluded via `arrConflictingUnits`, to permit two different, overlapping windows; this depends on the specific state of already-spent commission ranges on the two branches at the time of validation, so it is not trivial to trigger deterministically, but it is a plausible race condition reachable by a single account without requiring cooperation of witnesses/hubs.

### Recommendation
Change the double-spend predicate for `headers_commission`/`witnessing` inputs to detect true interval overlap rather than exact-match on `from_main_chain_index`, e.g. `type=? AND address=? AND asset IS NULL AND from_main_chain_index<=? AND to_main_chain_index>=?` (comparing against the candidate input's `to_main_chain_index`/`from_main_chain_index` respectively), so that any two claims whose `[from,to]` windows intersect — regardless of which endpoint matches — are correctly linked and resolved through the existing nonserial/double-spend machinery.

### Proof of Concept
Conceptual (not executed against a live node):
1. Address `A` has accrued headers-commission outputs for MCIs 100–200 (all unspent).
2. Author two units `U1` and `U2` from `A` on parallel DAG branches that do not include each other.
3. `U1`'s payment message claims a `headers_commission` input with `from_main_chain_index=100, to_main_chain_index=150`.
4. `U2`'s payment message claims a `headers_commission` input with `from_main_chain_index=120, to_main_chain_index=170`.
5. When each unit is validated, `arrConflictingUnits` for that validation excludes the other unit, so `readNextSpendableMcIndex` returns `0` (or another value permitting each unit's chosen `from_main_chain_index`) for each branch independently; both pass the `input.from_main_chain_index < next_spendable_mc_index` check.
6. The double-spend lookup `type=? AND from_main_chain_index=? AND address=? AND asset IS NULL` with `input.from_main_chain_index` = 100 for `U1` and 120 for `U2` never matches the other unit, so `checkForDoublespends` never links them.
7. Both units validate as `good`, each crediting `total_input` with commissions for the overlapping MCIs 120–150, effectively double-counting that segment of commission funds across two independently valid units.

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
