### Title
Unhandled exception in `handleSavedPrivatePayments` causes double-processing of a private payment chain, race-unlocking the validation mutex - ([File: network.js])

### Summary
`network.js`'s `handleSavedPrivatePayments()` refactoring analog of CVE-2024-50211's `inode_bmap()`: when an intermediate step (`objectHash.getBase64Hash`) throws, the error is caught and partially handled, but the enclosing function does not `return` after handling the error, so execution falls through and continues the "traversal" (chain validation flow) with corrupted/incomplete state, invoking the callback (`cb`) twice and starting a second, redundant validation of the same private-payment chain.

### Finding Description
In `network.js`, `handleSavedPrivatePayments()` iterates unhandled private-payment chains stored in `unhandled_private_payments` and validates each one via the inner `validateAndSave` closure: [1](#0-0) 

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... });
};
```

If `objectHash.getBase64Hash()` throws, the `catch` block correctly deletes the handled chain from `unhandled_private_payments` and invokes `cb` (the `async.each` iteratee callback). However, there is no `return` statement inside or after the `catch` block, so control flow continues to the next line, which:

1. Computes `key` using the now-`undefined` `json_payload_hash`.
2. Calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again for the same chain, which internally calls `cb()` a second time from one of its own callbacks (`ifOk`, `ifError`, or `ifWaitingForChain`), and also invokes `deleteHandledPrivateChain` again.

This is directly analogous to the root cause fixed by CVE-2024-50211: `udf_next_aext()`/`inode_bmap()` failed to check/propagate an error from a traversal/parsing step and continued processing with stale state, instead of aborting the operation. Here, the error from `objectHash.getBase64Hash()` (an analog of `udf_next_aext()` failing to parse the next chain element/extent) is not used to unwind the call — the function proceeds to re-enter the validation/traversal logic (`validateAndSavePrivatePaymentChain`) using data derived from a state that should have been treated as a fatal, unresolvable error for this iteration.

The internal `validateAndSavePrivatePaymentChain` call chain (`private_payment.js` → `indivisible_asset.js`/`divisible_asset.js`) takes its own DB connection, begins a `BEGIN`/`COMMIT` transaction, and mutates the `outputs`/`inputs` tables (marking outputs as spent), while `handleSavedPrivatePayments` runs multiple chains concurrently via `async.each`: [2](#0-1) 

Because `async.each` treats a double call to the same `cb` as undefined/erroneous behavior (in the `async` library, calling the iteratee callback twice can prematurely trigger the completion callback, unlocking the `"saved_private"` mutex early, or throw/skip further error handling), the currently-processing item's completion signal can race with the second, redundant validation attempt that is still in flight and touching shared DB state.

### Impact Explanation
- Concurrency/mutex-lock corruption: the double `cb()` invocation causes `async.each`'s final callback (`unlock()`) to potentially fire before the second, still-in-flight `validateAndSavePrivatePaymentChain()` completes, releasing the `"saved_private"` mutex early. This can let a subsequent `handleSavedPrivatePayments()` invocation run concurrently against the same in-flight chain/output rows, undermining the serialization the mutex was meant to guarantee for private-payment output state (`is_spent`, `is_unique`) updates.
- This can allow the same private (indivisible/divisible asset) output to be processed by two overlapping transaction contexts, risking a double-mark or inconsistent double-spend bookkeeping of a private-asset output — matching the "double-spend of a stable output" acceptance criterion.
- Because the trigger is a malformed/adversarial `payload` in a `private_payment` message (attacker-controlled JSON sent to a wallet, as validated at `handleOnlinePrivatePayment` and stored via `unhandled_private_payments`), an unprivileged private-payment counterparty who can cause `objectHash.getBase64Hash()` to throw (e.g., by sending a payload whose structure the hash serializer cannot handle, such as unexpected types/`NaN`/`Infinity` or excessive nesting) can trigger this code path from a normal device message, without needing any elevated access.

### Likelihood Explanation
The `payload` is attacker-supplied and only shallowly validated before reaching `handleSavedPrivatePayments`/`validateAndSave` (only `isNonemptyObject`, string/array checks in `handlePrivatePaymentChains`, `handleOnlinePrivatePayment`), so a crafted payload that causes `objectHash.getBase64Hash` to throw is plausible. Reaching the vulnerable code path only requires sending a `private_payment`-type message to a device (wallet), which is a normal, low-privilege interaction (private-payment counterparty), satisfying the "reachable by ... private-payment counterparty" criterion. The exact conditions needed to make `getBase64Hash` throw were not confirmed against the `object_hash.js` implementation (not inspected in this session), so likelihood is assessed as plausible but not proven with a concrete crafted payload.

### Recommendation
Add a `return` immediately after handling the error in the `catch` block (and ensure `cb` is invoked exactly once per iteration), e.g.:
```js
try {
    var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
}
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
This prevents the fallthrough into `validateAndSavePrivatePaymentChain` and the associated double invocation of `cb`, matching the upstream UDF fix pattern of aborting the traversal/operation as soon as an error is detected rather than continuing with an inconsistent state.

### Proof of Concept
1. As a private-payment counterparty (or hub-forwarded sender), send a `private_payment` device message whose `payload` is a well-formed-enough object to pass the shallow validation in `handlePrivatePaymentChains`/`handleOnlinePrivatePayment`, but which causes `objectHash.getBase64Hash(payload, true)` to throw when re-hashed inside `handleSavedPrivatePayments` (e.g., by including a value type not supported by the hashing routine, discovered by inspecting `object_hash.js`, which was not available for direct confirmation in this analysis).
2. The message is queued into `unhandled_private_payments` and later processed by `handleSavedPrivatePayments()`.
3. `validateAndSave()` throws inside the `try`, the `catch` block deletes the row and calls `cb()`, but execution falls through and calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` again, which eventually calls `cb()` a second time.
4. Observe (via logging/instrumentation of `async.each`) that the `"saved_private"` mutex is released before the second validation transaction completes, allowing a concurrent `handleSavedPrivatePayments()` run to process overlapping output rows — demonstrating the race window that can lead to inconsistent spend-state bookkeeping for the private asset output.
