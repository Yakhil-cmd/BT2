Cross-tenant commit-status mutation via unscoped `Commit.where(sha:)` in StatusHandler - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no filter on the repository or organization that authenticated the webhook, and mutates every matching `Commit` row across the entire instance. Since `Commit#sha` is only unique per `(sha, stack_id)` (not globally), any org whose webhook secret an attacker can satisfy can inject a GitHub `status` event referencing a SHA that also exists on an unrelated stack (e.g., the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any collided/duplicated merge SHA) and thereby write status/state onto a commit belonging to a completely different, unauthenticated repository/organization.

### Finding Description
The broken binding is: **`webhook_secret organization that signed the request` == `organization owning every Commit row mutated by the handler`**. This holds only for the attacker's own stack and is false for any other stack whose `Commit` shares the same `sha`.

Path:
1. `Shipit::WebhooksController#create` (`app/controllers/shipit/webhooks_controller.rb:10-15`) calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` after `verify_signature` (line 24) validates the HMAC using `Shipit.github(organization: repository_owner)` — this only proves the payload was signed by *some* trusted organization/repo config (`repository_owner`), not that the referenced commit belongs to that organization. [1](#0-0) 
2. `Handler.call` (`app/models/shipit/webhooks/handlers/handler.rb:15-24`) instantiates the handler and parses params, but does not itself restrict lookups to the requesting repository. [2](#0-1) 
3. `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query against every stack in the database. [3](#0-2) 

Contrast with every other handler in the same directory, which explicitly scope to the authenticated repository before touching any record: `Handler#stacks` uses `Repository.from_github_repo_name(repository_name)&.stacks`, and `CheckSuiteHandler#process` filters `stacks.where(branch: ...)` before touching commits. [4](#0-3) [5](#0-4) 
The pull-request handlers likewise resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting. [6](#0-5) 

`StatusHandler` is the outlier: it never calls `stacks` or resolves `Repository.from_github_repo_name`, so nothing ties the mutated `Commit` rows back to the authenticated `repository_owner`. The uniqueness constraint on `commits` is `(sha, stack_id)` — unique per stack, not globally — confirmed by the migration `add_index :commits, %i(sha stack_id), unique: true`, meaning identical SHAs across unrelated stacks/orgs are a normal, expected occurrence (e.g., the canonical empty-tree SHA, or any commit cherry-picked/merged identically into multiple stacks). [7](#0-6) 

`create_status_from_github!` → `add_status` triggers real side effects: it emits `Hook.emit(:commit_status, ...)`, potentially `Hook.emit(:deployable_status, ...)`, and calls `stack.schedule_merges` when the new state is `pending` or `success` — all against the victim stack, not the attacker's. [8](#0-7) 

Attacker exploit: register/own any GitHub org or repo that Shipit already trusts via its `webhook_secret`/GitHub App config (satisfying `verify_signature` for that org), push a commit whose SHA collides with a commit that exists in an unrelated victim stack (trivially the empty-tree SHA, which arises naturally from merges/no-op commits), then POST a validly-signed `status` event referencing that SHA. `verify_signature` passes because the signature matches the attacker's own trusted org; `StatusHandler#process` then updates the status of the victim's `Commit` row, potentially advancing the victim stack's merge queue.

### Impact Explanation
An attacker with no access to the victim stack, repository, or GitHub org can write commit status data onto another tenant's `Commit`, trigger `Hook.emit(:commit_status/:deployable_status)` webhooks for that tenant, and cause `stack.schedule_merges` to run against the victim stack — potentially advancing merges/deploys based on forged CI state. This is a cross-tenant integrity violation ("a payload for one repository mutating another's stack, commit") and matches the Critical impact category. It is repeatable against any stack/commit sharing a SHA with an attacker-controlled stack, and the empty-tree SHA guarantees at least one universally-available collision candidate.

### Likelihood Explanation
Preconditions: the attacker needs to control (or register) any GitHub org/repo already configured in Shipit's webhook secrets (a low bar — many Shipit deployments allow self-service repo onboarding), and needs a SHA collision with a victim `Commit` row, which is trivially satisfied by the empty-tree SHA or any no-op/merge commit shared across many repos. No Shipit secrets, session, or API token are required — only the ability to produce a validly signed webhook for the attacker's own trusted org and knowledge of a plausible/common SHA. This is a cheap, repeatable attack requiring only HTTP access to `POST /webhooks`.

### Recommendation
Scope `StatusHandler#process` to the authenticated repository, mirroring `CheckSuiteHandler` and the PR handlers: resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, restrict the `Commit` lookup to `stacks.flat_map(&:commits)` (or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`), so only commits under the requesting repository's stacks can be mutated by that webhook.

### Proof of Concept
Minitest plan (no live GitHub):
```ruby
test "status webhook for org A must not mutate commits belonging to org B's stack" do
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature already trusted for org A

  org_a_repo = shipit_repositories(:org_a_repo) # attacker-owned, trusted org
  org_b_stack = shipit_stacks(:org_b_stack)     # unrelated victim stack/org
  shared_sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904"

  org_b_commit = org_b_stack.commits.create!(sha: shared_sha, ...)

  request.headers['X-Github-Event'] = 'status'
  body = {
    sha: shared_sha, state: 'success', context: 'ci',
    repository: { full_name: org_a_repo.github_repo_name, owner: { login: org_a_repo.owner } }
  }.to_json

  assert_difference -> { org_b_commit.statuses.count }, 1 do
    post :create, body:, as: :json
  end
  # Demonstrates: signing org (A) != owning org of mutated Commit (B) — binding violated.
end
```
After the fix, the same test should assert `assert_no_difference -> { org_b_commit.statuses.count }` because the lookup would be scoped to org A's stacks only.
