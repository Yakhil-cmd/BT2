### Title
Stack-scoped API tokens can read CCMenu build status of any stack, bypassing the API client's stack authorization - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides `stack` to query `Stack.from_param!(params[:stack_id])` directly instead of routing through the `stacks` helper used by every other API controller, which filters by `current_api_client.stack_id` when the client is scoped to a single stack.

### Finding Description
`Api::BaseController#stacks` defines the authorization boundary for scoped API clients: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) . `Api::BaseController#stack` (the default used by most endpoints) then calls `stacks.from_param!(params[:stack_id])` [2](#0-1) , and `Api::StacksController#stack` follows the same pattern with `stacks.from_param!(params[:id])` [3](#0-2) . This is exactly the binding equality the whole authorization scheme depends on: `stack a token authorizes == stack it touches`.

`Api::CCMenuController` requires only `read:stack` permission and overrides `stack` to bypass the scoping entirely: [4](#0-3) [5](#0-4) 

`require_permission!` only checks that `"read:stack"` is present in the token's `permissions` array — it never checks which stack is being requested: `current_api_client.check_permissions!(operation, scope)` → `permissions.include?(required_permission)` [6](#0-5) [7](#0-6) . Because `CCMenuController#stack` never consults `current_api_client.stack_id`, an `ApiClient` created with `stack: some_stack` (scoped to a single stack, as in the `here_come_the_walrus` fixture: `stack: shipit`, `permissions: [read:stack]` [8](#0-7) ) can pass any other stack's `stack_id` param and still successfully load and render that stack's deploy/build status.

Before/after the equality:
- Before (intended): `stack a token authorizes` = `{stack_id bound to ApiClient}` = `stack it touches` (enforced via `stacks.from_param!` everywhere else).
- After (this controller): `stack it touches` = `Stack.from_param!(any params[:stack_id])`, decoupled from `stack a token authorizes`.

### Impact Explanation
This is an unauthenticated-scope escalation: a legitimately-issued, narrowly-scoped credential is used to read stack state (deploy status, last build outcome, lock status) belonging to a stack the token holder was never granted access to. This matches the High-impact criterion "unauthenticated read of stack state, task streams or deploy output" in the sense that it is a read of state outside the credential's authorized boundary — the token was never meant to authorize access to that stack.

### Likelihood Explanation
Any holder of a valid, stack-scoped API token (the normal, lowest-privilege kind of Shipit API credential, e.g. the one auto-generated by `CCMenuUrlController` for embedding in CI dashboards) can trigger this by simply changing the `stack_id` in the request URL. No secrets, GitHub credentials, or special access are required beyond possessing one legitimate scoped token, which is the standard credential class this endpoint is designed to accept.

### Recommendation
Change `Api::CCMenuController#stack` to use the same scoped lookup as the rest of the API surface:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This aligns `CCMenuController` with `Api::BaseController#stack` / `Api::StacksController#stack`, restoring the invariant that a token's `stack_id` scope always bounds the stacks it can touch.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to stack A with `permissions: ['read:stack']` and `stack_id: A.id` (e.g. via `CCMenuUrlController#fetch`, or the `here_come_the_walrus` fixture pattern).
2. Authenticate to the API as that client (`Authorization: Basic <base64(token)>` or `?token=<token>` per `CCMenuController#authenticate_api_client` at [9](#0-8) ).
3. Request `GET /api/stacks/:stack_id_of_B/ccmenu.xml` where B is a different, unrelated stack the client was never granted access to.
4. Observe `require_permission :read, :stack` passes (the token does have `read:stack` somewhere), and `stack` resolves via `Stack.from_param!(params[:stack_id])` to stack B, returning stack B's build/deploy status in the XML response — despite the token being scoped only to stack A.
