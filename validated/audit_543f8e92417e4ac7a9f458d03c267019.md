### Title
Membership webhook `repository.owner.login` / `organization.login` field-source mismatch lets an attacker forge a `Team` record for an org they do not own - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the organization used for HMAC verification via `params.dig('repository','owner','login') || params.dig('organization','login')`, while `MembershipHandler#find_or_create_team!` writes `team.organization = params.organization.login` unconditionally. Because these are two independently-readable JSON fields, an attacker who owns any GitHub org can add a spurious top-level `repository.owner.login` key (pointing at their own org, so the signature check passes with their own webhook secret) while setting `organization.login` to an arbitrary victim org name, forging a `Team` row bound to an organization they never proved ownership of.

### Finding Description
The intended binding is: **the organization whose webhook secret validated the request == the organization written into `team.organization`**. `verify_signature` computes `repository_owner` as: [1](#0-0) 
and uses it to pick which org's `webhook_secret` verifies the HMAC: [2](#0-1) 

`MembershipHandler`, however, never consults `repository_owner`; it reads `params.organization.login` directly to populate `team.organization`: [3](#0-2) 

The membership handler's declared schema requires only `action`, `team`, `organization`, `member` - it never requires or restricts a `repository` key: [4](#0-3) 

Because `verify_signature`'s `repository_owner` prefers `repository.owner.login` over `organization.login`, an attacker can craft a JSON body containing **both** keys:
- `repository.owner.login = "attacker-org"` (an org the attacker owns and can compute a valid `X-Hub-Signature` for, using their own `webhook_secret`)
- `organization.login = "victim-org"` (arbitrary, unowned)
- `team.id` = an unused integer
- `team.slug` chosen to match a real/target team slug

`verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature verifies successfully against the attacker's own secret. The controller then dispatches to `MembershipHandler`, which is oblivious to `repository`, and creates a `Team` row with `organization: "victim-org"` using the attacker-supplied `team.id`, `slug`, `name`, `url`, and adds the attacker's own GitHub login as a member via `team.add_member(member)`.

The declared params schema on `MembershipHandler` does not forbid extra top-level keys such as `repository`; extraneous JSON keys not part of the declared schema are simply not read by the handler, so their presence does not cause request rejection - only the controller-level `repository_owner` helper, which operates on the raw parsed body/`ActionController::Parameters` independent of the handler schema, is influenced by it.

No existing guard closes this gap: `verify_signature` only proves the requester controls *some* organization's secret, not the organization named inside `organization.login`; `ExplicitParameters` on `MembershipHandler` validates presence/type of declared fields, not cross-field consistency with the outer envelope; there is no validation on `Team` tying `organization` to the signing party.

### Impact Explanation
A forged `Team` row can later be matched by `Team.find_or_create_by_handle`, which is `find_by(organization:, slug:) || fetch_and_create_from_github(...)`: [5](#0-4) 
This is invoked from `Shipit.github_teams`, which is memoized and used by `User#authorized?` to gate application access: [6](#0-5) [7](#0-6) 
If the attacker predicts or learns the `organization/slug` handle configured in `Shipit.secrets.github[...].oauth.teams` for the victim org, they can pre-seed a matching forged `Team` and add their own GitHub login as a member before `Shipit.github_teams` is first resolved, causing the memoized authorization set to return the attacker-controlled row instead of hitting GitHub - escalating the attacker into the authorized team set without ever being a real member of the victim org's team. This matches the High-severity category "escalation into `Shipit.github_teams` authorization." It is repeatable against any org handle the attacker can guess, and requires the attacker to control only their own org's webhook secret.

### Likelihood Explanation
Preconditions: the attacker must own/administer some GitHub organization (to author a validly-signed webhook of their own) and must guess or know the `organization/slug` handle string configured in `Shipit.github_teams` for the target instance (an operator-configured, not necessarily secret, value). Attacker cost is a single crafted HTTP POST to `/webhooks` with a self-signed body; no Shipit session, API token, or GitHub App key is required. The race against `Shipit.github_teams`'s per-process memoization means the attack must land before that memo is first computed (e.g., shortly after a deploy/restart) or requires the operator to add a new `oauth.teams` handle later - reducing but not eliminating reliability.

### Recommendation
In `MembershipHandler#find_or_create_team!` (and any other handler that writes an `organization` field from payload data), do not trust `params.organization.login` for authorization-relevant writes; instead derive/validate the organization from the same `repository_owner`/verified-signing-organization value used in `WebhooksController#verify_signature`, and reject the webhook if they diverge. More generally, make `repository_owner` and any org value used inside handler `process` methods reference a single verified source of truth (e.g., pass the verified organization into the handler and assert equality with `params.organization.login` before creating/updating records).

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (illustrative)
test "cannot forge a Team for an org whose signature was not verified" do
  # Attacker owns 'attacker-org' and knows its webhook_secret; victim org is 'shopify'.
  payload = {
    'action' => 'added',
    'team' => { 'id' => 999_999, 'name' => 'Evil', 'slug' => 'developers', 'url' => 'https://example.com' },
    'organization' => { 'login' => 'shopify' },      # value written to team.organization
    'member' => { 'login' => 'attacker-login' },
    'repository' => { 'owner' => { 'login' => 'attacker-org' } } # value used for signature verification
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', ATTACKER_ORG_WEBHOOK_SECRET, payload)}"

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = signature

  # verify_signature resolves repository_owner => 'attacker-org' and verifies successfully
  assert_difference -> { Shipit::Team.count }, 1 do
    post :create, body: payload, as: :json
    assert_response :ok
  end

  forged_team = Shipit::Team.find_by(github_id: 999_999)
  # Broken binding: forged_team.organization == 'shopify' even though only 'attacker-org's secret was verified
  assert_equal 'shopify', forged_team.organization
  refute_equal 'attacker-org', forged_team.organization
end
```
This demonstrates that a request whose HMAC was verified against `attacker-org`'s secret results in a persisted `Team` record bound to `shopify`, breaking the equality `signing_organization == team.organization`.
