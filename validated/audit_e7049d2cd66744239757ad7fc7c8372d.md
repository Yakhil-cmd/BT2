### Title
Webhook signature verification is keyed off an unauthenticated field, allowing forged webhooks to escalate into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The reported bug class is "a value is trusted without checking that it is actually backed by the thing that is supposed to guarantee its integrity" (Chainlink price used without checking the guarantee — the timestamp — that makes it trustworthy). The equivalent binding in this engine is: *the organization whose `webhook_secret` is used to verify a webhook's HMAC signature* must equal *the organization/team the payload is subsequently acted upon as*. `WebhooksController` breaks this equality by deriving the verification key from the same untrusted JSON body it is trying to authenticate, and by silently no-op'ing verification whenever that organization has no `webhook_secret` configured.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App / secret to validate against using data taken directly from the unauthenticated request body, before any signature check has occurred: [1](#0-0) [2](#0-1) 

`repository_owner` is read via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — entirely attacker-controlled. This value picks the `GithubApp` instance, and thus the `webhook_secret` used for HMAC verification: [3](#0-2) 

Critically, `verify_webhook_signature` **returns `true` unconditionally when `webhook_secret` is blank** ("return true unless webhook_secret"). Example and dummy configurations routinely ship with `webhook_secret` left empty: [4](#0-3) 

So for any organization configured without a `webhook_secret` (a documented, supported configuration, not a misconfiguration outside scope), signature verification is a no-op regardless of payload content. Once verification "passes," the *entire unauthenticated payload* — not just the organization field used for verification — is handed to handlers: [5](#0-4) 

Handlers then act on other, never-independently-verified payload fields. For example `Handler#repository_name` derives the target repository purely from `payload.dig('repository', 'full_name')`, decoupled from whatever `repository_owner` was used at verification time: [6](#0-5) 

The most severe consequence is the `membership` event path, which is used to populate `Team`/`Membership` records that directly gate application authorization: `User#authorized?` grants access purely based on membership in a `Shipit.github_teams`-listed `Team`: [7](#0-6) [8](#0-7) 

The existing test suite confirms that a `membership` webhook event creates the referenced `Team` on the fly and adds/removes arbitrary `member.login` entries with no additional cross-check against GitHub's actual team roster: [9](#0-8) 

Because the signature-verification key (`repository_owner`) and the data actually consumed by `MembershipHandler` (`organization.login`, `team`, `member.login`) are independent, unverified fields of the same JSON body, an attacker who can reach `/webhooks` and target an organization whose `webhook_secret` is unset (or otherwise not itself compromised) can forge a `membership` event claiming a legitimate `Shipit.github_teams` team, adding their own GitHub login as a member — with no interaction with GitHub at all.

### Impact Explanation
This breaks the binding "a GitHub identity versus the `User` bound to the session" and "escalation into `Shipit.github_teams` authorization" — one of the explicitly accepted High-impact categories. A forged `Membership` row makes `User#authorized?` return `true` for the attacker's GitHub login the next time they complete the (unprivileged, public) OAuth login flow, granting full access to the Shipit UI/app for stacks the attacker has no legitimate GitHub authorization for.

### Likelihood Explanation
No Shipit session, `ApiClient` token, `webhook_secret`, `api_clients_secret`, GitHub App private key, repository write access, or privileged account is required — the request is a single unauthenticated `POST /webhooks`. The only prerequisite is that at least one configured GitHub organization has no `webhook_secret` set, which is the default/documented example configuration (`config/secrets.development.example.yml`, `test/dummy` fixtures) and a state operators can easily be in for organizations where a webhook secret was never rotated in. This is a realistic, low-effort attack path rather than a theoretical one.

### Recommendation
- Do not derive the signature-verification key from the same untrusted payload being verified; require a stable, out-of-band identifier (e.g., a `X-GitHub-Hook-Installation-Target-ID` header or configured routing key) to select the app/secret.
- Do not treat a missing `webhook_secret` as automatic verification success; fail closed (reject with 422) if no secret is configured for an organization the payload claims to represent, or require a secret to be mandatory in all supported configurations.
- After verification, revalidate that every organization/repository identifier consumed by a handler (`repository.full_name`, `organization.login`, `team.organization`) matches the organization whose secret actually verified the request, rejecting mismatches.
- For `MembershipHandler` specifically, cross-check membership changes against a live GitHub API call (as `Team#refresh_members!` already does) rather than trusting webhook payload contents outright for authorization-relevant state.

### Proof of Concept
1. Configure (or find) a Shipit deployment using the documented multi-org format where one organization, e.g. `victim-org`, has `webhook_secret` left blank (as shown in `config/secrets.development.example.yml`).
2. Send, without any authentication and without any GitHub-issued signature:
```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "organization": { "login": "victim-org" },
  "team": { "id": 1, "name": "Ops", "slug": "ops", "url": "https://example.com" },
  "member": { "login": "attacker-login" },
  "repository": { "owner": { "login": "victim-org" } }
}
```
3. `verify_signature` calls `Shipit.github(organization: "victim-org").verify_webhook_signature(...)`, which returns `true` immediately because `webhook_secret` is blank for `victim-org` (`lib/shipit/github_app.rb:76-77`).
4. `MembershipHandler` runs on the unverified body, creating/looking up the `Team` `victim-org/ops` and creating a `User`/`Membership` for `attacker-login` (behavior confirmed by `test/controllers/webhooks_controller_test.rb:129-149`).
5. If `victim-org/ops` is listed in `Shipit.github_teams`, the attacker logs in via the normal public OAuth flow with their real GitHub account (`attacker-login`); `User#authorized?` now returns `true` due to the forged `Membership`, granting them access to the Shipit application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
