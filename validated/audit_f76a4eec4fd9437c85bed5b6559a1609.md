### Title
StatusHandler#process writes GitHub Status to any Commit sharing a SHA regardless of owning repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Handler#stacks`/`#repository_name` establish the invariant that a handler only mutates rows belonging to `Repository.from_github_repo_name(payload['repository']['full_name'])`, and `PushHandler#process` honors this via `stacks.not_archived.where(branch:)`. `StatusHandler#process` never calls `stacks` or `repository_name`; it runs `Commit.where(sha: params.sha)` unscoped by repository and calls `commit.create_status_from_github!(params)` on every match, so a status webhook naming the attacker's own repo can still write a `Status` onto a `Commit` belonging to a completely different stack/repository if the SHA matches.

### Finding Description
The claimed broken binding, stated as an equality: for every handler, `repository_scope(mutated_row) == Repository.from_github_repo_name(payload.repository.full_name)`. `Handler#stacks` and `#repository_name` at [1](#0-0)  implement this equality by deriving the target `Repository`/`Stack` set strictly from the payload's `repository.full_name`. `PushHandler#process` upholds it: it scopes writes through `stacks.not_archived.where(branch:)` before calling `sync_github` [2](#0-1) . `StatusHandler#process`, however, queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on each match, with no reference to `stacks` or `repository_name` anywhere in the class [3](#0-2) . Thus the equality is broken by construction: the "repository named in the payload" and "repository owning the mutated `Commit`" are never checked against each other for this handler.

The reachable path: `POST /webhooks` with `X-Github-Event: status` is dispatched by `WebhooksController#create` to `Shipit::Webhooks.for_event('status')`, gated only by `check_if_ping`, `drop_unhandled_event`, and `verify_signature` [4](#0-3) . `verify_signature` resolves the GitHub App/secret to use via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the attacker-controlled payload (`payload.repository.owner.login`) [5](#0-4) . Each configured GitHub App has its own `webhook_secret` (`@config[:webhook_secret]`) [6](#0-5) , so an attacker who owns a repo under an organization that has a Shipit GitHub App installed (their own org/repo, using their own org's app credentials) can send a validly-signed `status` event using their own organization's `webhook_secret` — signature verification only proves the request came from *some* installed org, not that it came from the org owning the target `Commit`.

Once signature-verified, `StatusHandler.call(params)` runs `Commit.where(sha: params.sha)` — a global, unscoped lookup across the entire `commits` table for every stack/repository configured in this Shipit instance. If a `Commit` row with that SHA exists for a victim's stack (this happens naturally for shared history: a fork of a public repo tracked by Shipit shares SHAs with the upstream repo that is also tracked by Shipit, or simply due to any commit having been synced under any tracked repository with that hash), the handler calls `commit.create_status_from_github!(params)` on it [3](#0-2) , which persists a `Status` via `statuses.replicate_from_github!` [7](#0-6) . This status feeds `Commit#deployable?` / `blocked?` and `schedule_continuous_delivery`, meaning a forged "success" status can make a victim commit appear CI-green and trigger continuous deployment or unblock a manual deploy for a stack the attacker never authenticated against [8](#0-7) , [9](#0-8) .

None of the existing guards close this gap: `verify_signature` only authenticates "some installed org sent this," not "the target commit's owning repo sent this"; `drop_unhandled_event` and the `status` `ExplicitParameters` schema (`requires :sha, :state`, etc.) do not reference repository at all [10](#0-9) ; there is no `force_github_authentication`, `require_permission!`, or `stacks` scope call inside `StatusHandler#process`.

### Impact Explanation
A successful request causes a `Status` row to be written against a `Commit` belonging to a repository/stack that never authenticated the request — this is a cross-tenant write ("a payload for one repository mutating another's commit"), matching the Critical impact category. Repeatable per-SHA against any commit whose SHA is guessable or discoverable (public repo history, forks, cherry-picks, shared upstream commits), and blast radius spans every stack configured in the same Shipit instance, since `Commit.where(sha:...)` is global across all tenants of the installation.

### Likelihood Explanation
Preconditions are minimal per the threat model: attacker only needs a repository with the Shipit GitHub App installed (owning valid signing credentials for their own org's webhook secret) and knowledge of a target commit SHA that also exists as a `Commit` row for a victim stack (trivially available for forks/shared history of public repositories, or any commit whose SHA was already synced). No Shipit session, API token, or team membership is required. This is fully attacker-controlled and repeatable at will.

### Recommendation
Scope `StatusHandler#process` by repository the same way `PushHandler` does: resolve `stacks` from `repository_name` first (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), and only call `create_status_from_github!` on commits belonging to a stack under the payload's `repository.full_name`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "StatusHandler does not create a status for a commit belonging to an unrelated repository" do
  victim_stack = shipit_stacks(:shipit) # repo: "shopify/shipit-engine"
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)

  attacker_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/unrelated-repo' }
  }

  Handler.any_instance.expects(:stacks).never # documents PushHandler's invariant is absent here

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)
  end
end
```
Currently this assertion fails: `StatusHandler.call` mutates `victim_commit.statuses` even though `repository.full_name` is `attacker/unrelated-repo`, proving the repository-scoping invariant enforced by `Handler#stacks`/`#repository_name` and honored by `PushHandler` is not enforced by `StatusHandler`.
