## Analysis

This is a solid analog to the Sherlock finding. The Solidity bug is: a privileged `onlyOwner` setter can unilaterally change a critical address (`nft`) that other unprivileged users' in-flight actions depend on, with no protection for users who already committed funds based on the old value.

The equivalent pattern in `ocore` is the **asset attestor list**, controlled exclusively by the asset `definer` (the "owner"/issuer of a `spender_attested` asset), which can be changed at will, at any time, even while other unprivileged users are actively holding/transferring the asset.

### Root cause

When an asset is defined with `spender_attested: true`, only addresses attested by one of the asset's trusted attestors are allowed to hold/spend it [1](#0-0) . The list of trusted attestors is **not fixed at asset-definition time** — the definer can freely republish it later via a single-authored `asset_attestors` message, and the only checks are "asset must exist and require attestors" and "must be the definer": [2](#0-1) 

This update is accepted unconditionally for `validateInlinePayload`, with no restriction tied to whether the asset is actively in use / has outstanding balances: [3](#0-2) 

Crucially, validation of spends does **not** pin to the attestor list that was active when a holder received/attested their balance. Instead, `storage.readAsset` always resolves the **latest** attestor list as of the current validation MCI: [4](#0-3) 

That "latest" list is then used to filter which output/input addresses count as attested, both for outgoing payment outputs and for spending existing balances: [5](#0-4) [6](#0-5) [7](#0-6) 

### Title
Asset definer can retroactively change the trusted attestor list of a `spender_attested` asset, freezing legitimately-attested holders' funds — (File: `validation.js`)

### Summary
For a `spender_attested` asset, the definer (analogous to the "owner" in the Solidity report) can publish a new `asset_attestors` list at any time via a single-authored message, with no restriction preventing this while the asset is actively circulating among third-party holders. `validation.js#validateAttestorListUpdate` (`validation.js:2829-2848`) only checks that the sender is the definer and that the new list is well-formed; it never checks whether the asset already has outstanding, previously-attested balances that depend on the old attestor set.

### Finding Description
Ordinary holders of a `spender_attested` asset become "attested" via attestation records published by attestors that were trusted by the definer at the time. However, spend/transfer validation always re-resolves attestor trust against the **current, latest** attestor list (`storage.js#readAsset` → `addAttestorsIfNecessary`, `storage.js:1917-1946`), not the list that was valid when the holder's attestation was recorded or when they received the funds. `filterAttestedAddresses` (`storage.js:1960-1974`) and the input/output checks in `validatePaymentInputsAndOutputs` (`validation.js:2504-2507`, `validation.js:2630-2642`) all key off this live-resolved list.

Because the definer can swap out the attestor list unilaterally and at any time — exactly like the audited `setNFT` owner function that changes a dependency other users rely on mid-flight — a legitimately attested holder who already received/holds the asset can suddenly find their address no longer covered by the (new) attestor set, and any attempt to spend their balance is rejected with `"owner address is not attested"`.

### Impact Explanation
This is a fund-freezing vector directly analogous to the report's "user forced to receive/interact with a worthless resource because the owner changed the dependency mid-flight": the definer, acting after users have already acquired/hold the asset, can effectively freeze any holder's balance by dropping the attestor that vouched for them, with no on-chain protection, timelock, or grandfathering of already-attested holders. This matches the "AA fund loss or freezing" acceptance criterion, since AAs and ordinary users alike hold and transact in such assets and have no way to prevent or anticipate this unilateral change.

### Likelihood Explanation
Any asset definer of a `spender_attested` asset can trigger this at will with a single, cheap, single-authored `asset_attestors` unit — no special permissions beyond being the asset's own definer are required, and no protocol rule prevents doing so while the asset has outstanding attested balances in the hands of unprivileged holders (including AAs receiving/holding such assets as trigger payments).

### Recommendation
Either (a) do not retroactively invalidate previously-recorded attestations for addresses that already hold a balance when the attestor list changes (e.g., grandfather attestations valid at the MCI when the balance was received), or (b) require the definer to prove no outstanding attested balances exist before changing the attestor list, similar to the `cap`-already-issued check pattern used elsewhere in the codebase (`validatePaymentInputsAndOutputs`, `validation.js:2321-2327`).

### Proof of Concept
1. Definer `D` issues asset `A` with `spender_attested: true` and `attestors: [X]`.
2. Attestor `X` attests address `U`'s address via an `attestation` message.
3. `U` receives a payment in asset `A` (validated successfully since `U` is attested by `X`, per `validation.js:2630-2642`).
4. `D` posts a new `asset_attestors` message for asset `A` with `attestors: [Y]` (dropping `X`) — accepted unconditionally per `validation.js:2829-2848`.
5. `U` now attempts to spend their previously-valid balance of `A`. `storage.js#readAsset` resolves the *new* attestor list `[Y]`; `filterAttestedAddresses` finds `U` is not attested by `Y`; `validatePaymentInputsAndOutputs` (`validation.js:2506`) rejects the input with `"owner address is not attested"`.
6. `U`'s previously legitimate balance is now permanently unspendable — a definer-triggered freeze exactly mirroring the "owner changes a dependency mid-flight, harming users who already committed" bug class from the report.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
