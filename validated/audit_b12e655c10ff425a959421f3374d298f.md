### Title
Unfiltered `machine.environment` from fork-controlled `shipit.yml` reaches `PTY.spawn`, allowing `LD_PRELOAD` injection into deploy processes - (File: `app/models/shipit/deploy_spec.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`DeploySpec#machine_env` returns the `machine.environment` section of `shipit.yml` verbatim, with no whitelist filtering, unlike deploy/rollback/task variables which are always passed through `EnvironmentVariables#permit`. `TaskCommands#env` merges this unfiltered hash into the environment given to `Command`, which is then merged into `PTY.spawn`'s child process environment, so any key (including `LD_PRELOAD`) set in `machine.environment` is passed straight to every process the deploy/task spawns.

### Finding Description
The broken binding: for ordinary deploy/rollback/task variables, `env_reaching_PTY.spawn == EnvironmentVariables.with(user_supplied_env).permit(variable_definitions)` — i.e. only whitelisted keys defined in `shipit.yml`'s own `variables:` sections survive (see `DeploySpec#filter_deploy_envs`/`filter_rollback_envs`, `TaskDefinition#filter_envs`, and `EnvironmentVariables#permit` at [1](#0-0)  and [2](#0-1) ). But for `machine.environment`, the binding is `env_reaching_PTY.spawn == config('machine','environment')` with **no permit/filter step at all**: [3](#0-2) .

This unfiltered hash is merged directly into the command environment in `TaskCommands#env`: [4](#0-3) . That merged hash is passed into `Command.new(..., env:, ...)` (e.g. in `install_dependencies`/`perform`, line 17-27 of the same file), stored as `@env`, and ultimately merged into `PTY.spawn`'s environment via `Command#unbundled_env`/`Command#start`: [5](#0-4) .

Root cause: the deploy-spec author's own `shipit.yml` is the *only* source of `machine.environment`, and Shipit treats it as fully trusted config, unlike deploy/rollback/task `env`, which comes from an external caller (API/UI) and is explicitly considered attacker-controlled and thus filtered. For a `ReviewStack`, however, the effective `shipit.yml` (or `shipit.<environment>.yml`) is checked out from the fork PR's head branch (`DeploySpec::FileSystem` reads it from the working directory checked out at `branch:` — the fork branch, per `stack_attributes` in `app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb` line 89: `branch: params.pull_request.head.ref`). Thus a pull-request author from a fork fully controls the content of `machine.environment` that ends up in `machine_env`, and by extension in every spawned process's environment for that review stack's tasks/deploys, including `LD_PRELOAD=/tmp/evil.so`.

Existing guards do not stop this: `verify_signature`/webhook checks only gate whether the PR event is accepted, not the content of `shipit.yml`; `EnvironmentVariables#permit` is applied to explicit `env` params from API/UI callers but is never called on `machine_env`; there is no model validation restricting `machine.environment` keys.

However, one precondition that materially reduces (but does not eliminate) the risk for `ReviewStack` specifically: newly created review stacks default to `continuous_deployment: false` (`app/models/shipit/webhooks/handlers/pull_request/review_stack_adapter.rb` line 92), so an automatic deploy is not triggered purely by opening the PR — some task/deploy still needs to run against that stack (e.g. a custom task, a manual/automatic deploy once CD is later enabled, or the initial provisioning process if the provisioning handler executes commands that read `deploy_spec`). I was not able to fully trace whether the default provisioning flow (`ProvisioningHandler::Base`/custom handlers) executes any `Command`/`PTY.spawn`-based step using `deploy_spec.machine_env` immediately upon PR creation without any deploy being explicitly triggered — this would determine whether the attack is fully "zero-click" or requires a subsequent deploy/task trigger (which for a review stack could still be self-triggered by the same PR author via `POST /webhooks` retriggering CI or via the review stack's own deploy/task endpoints once provisioned, since PR authors on their own fork/PR are not restricted from triggering deploys on stacks tied to their own PR in typical Shipit review-app setups).

### Impact Explanation
If a deploy or task is executed against the review stack (deploy, rollback, or custom task), the attacker-controlled `LD_PRELOAD` (or any other environment variable, e.g. `PATH`, `RUBYOPT`, `BUNDLE_GEMFILE`, `GIT_SSH_COMMAND`) is injected verbatim into the environment of every subprocess spawned by `Command#start` via `PTY.spawn` for that task, on the shared Shipit deploy host. This is arbitrary code execution on the deploy host under the Shipit worker's privileges — Critical severity (RCE via `Command`/`PTY.spawn`). Because review stacks are provisioned per-PR and the deploy host is shared infrastructure, this could affect other tenants' data/credentials reachable from that host (e.g. `GITHUB_TOKEN`, `secrets.yml` env) if the host runs tasks for multiple repos/stacks.

### Likelihood Explanation
Preconditions: Shipit must be configured to allow review-stack style flows (fork PR triggering shipit.yml checkout) and some deploy/task must be executed for that review stack (either by the PR author themselves once the review stack is provisioned, or by CD once enabled, or by any user/CI process running a task against that stack). Attacker cost is low: they only need to open a PR from their own fork with a crafted `shipit.yml` — no Shipit session, API token, or GitHub-team membership required. This is fully repeatable per PR/stack.

### Recommendation
Apply the same whitelist-based filtering to `machine.environment` that is already applied to deploy/rollback/task variables, or restrict which environment variable names may be set via `machine.environment` (e.g., disallow well-known dangerous names like `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_INSERT_LIBRARIES`, `PATH`, `BUNDLE_GEMFILE`, `RUBYOPT`, `GIT_SSH_COMMAND`), and/or require repo-maintainer approval (e.g., pin `machine.environment` to the base repository's own trusted `shipit.yml`, not the fork branch's, for review stacks) before values reach `TaskCommands#env`/`Command#unbundled_env`.

### Proof of Concept
```ruby
# test/lib/shipit/task_commands_ld_preload_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsLdPreloadTest < ActiveSupport::TestCase
    test "machine_env LD_PRELOAD reaches Command#unbundled_env verbatim" do
      stack = shipit_stacks(:review_stack) # or any stack
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      commands = Shipit::TaskCommands.new(task)
      commands.stubs(:deploy_spec).returns(
        stub(
          machine_env: { 'LD_PRELOAD' => '/tmp/evil.so' },
          directory: nil,
          clear_working_directory?: true
        )
      )

      env = commands.env
      # Binding under test: config('machine','environment')['LD_PRELOAD'] == env['LD_PRELOAD']
      assert_equal '/tmp/evil.so', env['LD_PRELOAD']

      command = Shipit::Command.new('true', env: env, chdir: Dir.tmpdir)
      # Assert it survives into the hash passed to PTY.spawn
      assert_equal '/tmp/evil.so', command.unbundled_env['LD_PRELOAD']
    end
  end
end
```
This demonstrates that, unlike deploy/rollback/task `env` (which raises `EnvironmentVariables::NotPermitted` for unlisted keys), `machine.environment`'s `LD_PRELOAD` is never filtered and lands unchanged in the exact hash consumed by `PTY.spawn`.
