### Title
Reward calculation snapshots current stake instead of time-weighting it, letting a staker flash-stake sBTC/STX to capture rewards it never earned — ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`pox-5.clar`'s reward-distribution engine (`calculate-rewards` / `calculate-bond-rewards`) computes each cycle's payable yield from the amount currently recorded in `total-shares-staked-for-cycle` / `signer-shares-staked-for-cycle` **at the instant the distribution call executes**, not from a time-weighted average of stake held over the accrual period. Because a staker can register a bond and later `unstakeSbtc`/`unstake` mid-cycle, and both actions immediately mutate the current cycle's share totals (settling rewards against the "rewards-per-token" snapshot at that moment), a participant can insert a large stake just before someone calls `calculate-rewards`, capture a share of the accrued `available-rewards`/`target-yield` proportional to their now-dominant share, and withdraw immediately afterward — echoing the Hubble Exchange bug where a trader could skew a shared, snapshot-based calculation (the mark-price TWAP feeding `settleFunding`) at will to divert value from counterparties who were exposed for the full period.

### Finding Description
`calculate-rewards` distributes newly accrued sBTC rewards using this snapshot pattern: [1](#0-0) 

and for each bond, `calculate-bond-rewards` sizes both the bond's target yield and its accrued-rewards-per-sat purely off `total-sats`, the value returned by `get-total-shares-staked-for-cycle` **as of the calculation call**, with no accounting for how long that stake had actually been present during the period being paid out: [2](#0-1) 

Both stake registration and unstaking mutate this same current-cycle bucket immediately and settle rewards against the *current* `rewards-per-token` snapshot rather than a duration-weighted contribution: [3](#0-2) [4](#0-3) 

The contract's own test suite confirms rewards are earned based on the shares present at the moment `calculateRewards` runs, and that partial unstakes/signer moves immediately re-shape the current cycle's buckets used for that computation: [5](#0-4) [6](#0-5) 

`calculate-rewards` is gated only by `calculation-height > last-calc`, i.e. it can be invoked repeatedly as new burn-height progress and new sBTC inflow occur, with no restriction tying a participant's payable share to how long their stake had actually backed the protocol during that increment: [7](#0-6) 

This is structurally the same weakness as the Hubble AMM bug: a value that other participants rely on being an honest, duration-weighted reflection of market/stake state (`getMarkPriceTwap` there, `total-shares-staked-for-cycle` here) is instead dominated by the most recent state change, letting anyone who can time a large, brief position around the settlement/calculation call divert value that should have accrued to parties who held their position/stake throughout the full accrual window.

### Impact Explanation
If a staker (or bond participant) can add a disproportionately large stake shortly before a `calculate-rewards` call and withdraw shortly after, they capture a share of the finite `available-rewards`/`target-yield` pool proportional to their now-dominant instantaneous share rather than their actual time-weighted contribution. This directly dilutes the sBTC/STX rewards that genuine, continuously-staked bond participants and signers should have earned for that period, and can even starve the `reserve-balance` allocation, since `remaining-rewards`/`reserve-cut` are computed off the same distorted totals. This is a theft of stacking rewards from other stakers — matching the Critical/High impact bucket for "theft ... of ... sBTC rewards" / "signing weight or reward slots exceeding locked value."

### Likelihood Explanation
Exploitability depends on parameters I could not fully confirm from the available index within the time budget: (1) whether bond registration (`register-for-bond`) and `unstakeSbtc` can be executed within the same reward cycle with no minimum holding/lockup delay before rewards are settled against them, and (2) how frequently `calculate-rewards` can practically be triggered (it is gated only by `calculation-height > last-calc`, suggesting it is permissionless and can be called often). The test suite's patterns (register → mine partway into the cycle → `calculateRewards` → immediate partial unstake, all within the same reward cycle) are consistent with no minimum dwell time being enforced, which would make this attack straightforward for any account able to post sufficient sBTC/STX collateral for a brief window. Given this uncertainty, this should be treated as a **likely but not fully verified** finding requiring confirmation against the exact eligibility/lockup checks in `register-for-bond`/`stake`/`unstake`/`unstakeSbtc` before being treated as conclusively exploitable.

### Recommendation
Time-weight reward accrual within a cycle rather than snapshotting `total-shares-staked-for-cycle` at the moment of `calculate-rewards`. Options: (a) accrue rewards continuously per block based on integral of stake-over-time (a proper "reward-per-token-stored" checkpoint scheme that updates on every stake/unstake, weighting each interval by the balance held during that interval, as in a correctly implemented Synthetix-style `StakingRewards` contract), or (b) enforce a minimum holding/lockup period before newly added stake is eligible to receive rewards from a distribution, or (c) require that `calculate-rewards` cannot be triggered opportunistically around a stake/unstake pair by the same actor within a short window. This closes the same class of gap as the Hubble bug's recommendation of reducing the weight placed on the most recent state change in a shared settlement calculation.

### Proof of Concept
Conceptual sequence, contingent on confirming there is no dwell-time restriction (needs verification against `register-for-bond` in `pox-5.clar`):
1. Wait until sBTC/STX rewards have accrued in the contract (`gross-accrued-rewards`/`available-rewards` builds up since `last-reward-compute-height`).
2. Attacker calls `register-for-bond` (or `stake`) with a large amount right before calling `calculate-rewards`, inflating `total-shares-staked-for-cycle`/`signer-shares-staked-for-cycle` for the current cycle.
3. Attacker (or anyone) calls `calculate-rewards`; `calculate-bond-rewards`/`calculate-rewards` computes `target-yield`/`accrued-rewards-per-ustx` using the now-inflated total, crediting the attacker a large share of `rewards-per-token-for-cycle` proportional to their now-dominant stake.
4. Attacker immediately calls `unstakeSbtc`/`unstake`, which calls `settle-rewards`/`settle-staker-rewards` against the just-updated snapshot, crystallizing the reward entitlement before withdrawing their collateral.
5. Repeat around each future `calculate-rewards` call, extracting rewards proportional to momentary stake rather than actual time-at-risk, at the expense of legitimate long-term stakers/signers and the reserve.

(define-private (calculate-bond-rewards
        (bond-index uint)
        (accumulator-res (response {
            ;; Used to ensure that the list of bonds are sorted correctly
            last-bond-stx-value-ratio: (optional uint),
            ;; Used as a tie-breaker in the case of bonds with the same
            ;; stx-value-ratio
            last-bond-index: (optional uint),
            ;; How much rewards are available to be distributed
            available-rewards: uint,
            calculation-height: uint,
            reward-cycle: uint,
        }
            uint
        ))
    )
    (let (
            (accumulator (try! accumulator-res))
            (bond (unwrap! (map-get? protocol-bonds bond-index) ERR_BOND_NOT_FOUND))
            (reward-cycle (get reward-cycle accumulator))
            (total-sats (get-total-shares-staked-for-cycle reward-cycle (some bond-index)))
            (available-rewards (get available-rewards accumulator))
            ;; How much sBTC the bond is supposed to earn per calculation,
            ;; which is (totalSats * apy) / 50
            (target-yield (/ (/ (* total-sats (get target-rate bond)) u10000) u50))
            ;; If there is enough to cover the target yield, use that. Otherwise,
            ;; this bond gets the remaining rewards.
            (earned (if (>= available-rewards target-yield)
                target-yield
                available-rewards
            ))
            (stx-value-ratio (get stx-value-ratio bond))
            (current-rewards-per-token (get-rewards-per-token-for-cycle reward-cycle (some bond-index)))
            ;; Prevent divide-by-zero
            (accrued-rewards-per-sat (if (is-eq total-sats u0)
                u0
                (/ (* earned PRECISION) total-sats)
            ))

test('bond rewards split across signers by staked sats', () => {

  txOk(

      minUstxRatio: 100n,

  );

    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer1,
      amountUstx: rov(pox5.minUstxForSatsAmount(aliceSbtc, 10n, 100n)),
      btcLockup: err(aliceSbtc),
      signerCalldata: null,
    }),
    alice,
  );
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer2,
      amountUstx: rov(pox5.minUstxForSatsAmount(bobSbtc, 10n, 100n)),
      btcLockup: err(bobSbtc),
      signerCalldata: null,
    }),
    bob,
  );

  txOk(
    sbtc.transfer({
      recipient: pox5.identifier,
      amount: 1000n,
      sender: deployer,
      memo: null,
    }),
    deployer,
  );

  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  const totalBondRewards = bondTargetYieldPerCalculation({
    sats: aliceSbtc + bobSbtc,
    targetRate,
  });
  expect(totalBondRewards).toBe(960n);
  expect(rov(pox5.getEarned(signer1, 1n, 0n))).toBe(
    claimableRewards({
      rewards: totalBondRewards,
      shares: aliceSbtc,
      totalShares: aliceSbtc + bobSbtc,
    }),
  );
  expect(rov(pox5.getEarned(signer2, 1n, 0n))).toBe(
    claimableRewards({
      rewards: totalBondRewards,
      shares: bobSbtc,
      totalShares: aliceSbtc + bobSbtc,
    }),
  );
  // When no STX-only stake exists, the staker cut is
  // rerouted to reserve rather than stranded, so reserve receives the
  // full `remaining-rewards` (1000 - 960 = 40), not just 15% of it.
  expect(rov(pox5.getReserveBalance())).toBe(1000n - totalBondRewards);

test('sbtc bond participant can partially unstake and only earns on remaining sats', () => {
  const signer = testSigner.identifier;
  const aliceSbtc = 480000n;
  const unstakedSbtc = 120000n;
  const targetRate = 1600n;

  registerSigner();

  txOk(
    pox5.setupBond({
      bondIndex: 0n,
      targetRate,
      stxValueRatio: 10n,
      minUstxRatio: 100n,
      earlyUnlockBytes: new Uint8Array(),
      allowlist: [{ maxSats: aliceSbtc, staker: alice }],
    }),
    deployer,
  );
  txOk(
    pox5.registerForBond({
      bondIndex: 0n,
      signerManager: signer,
      amountUstx: stxToUStx(50_000),
      btcLockup: err(aliceSbtc),
      signerCalldata: null,
    }),
    alice,
  );

  txOk(
    pox5.unstakeSbtc({
      signerManager: signer,
      amountToWithdrawalSats: unstakedSbtc,
    }),
    alice,
  );

  const remainingSbtc = aliceSbtc - unstakedSbtc;
  // The reduced sats must be reflected across every cycle of the bond
  // (bond-index 0 spans reward cycles [1, 13)), not just the first cycle.
  for (let cycle = 1n; cycle < 13n; cycle++) {
    expect(
      rov(pox5.getStakerSharesStakedForCycle(alice, cycle, 0n, signer)),
    ).toBe(remainingSbtc);
    expect(rov(pox5.getSignerSharesStakedForCycle(signer, cycle, 0n))).toBe(
      remainingSbtc,
    );
    expect(rov(pox5.getTotalSharesStakedForCycle(cycle, 0n))).toBe(
      remainingSbtc,
    );
  }
  expect(rov(pox5.getTotalSbtcStaked())).toBe(remainingSbtc);

  txOk(
    sbtc.transfer({
      recipient: pox5.identifier,
      amount: 1200n,
      sender: deployer,
      memo: null,
    }),
    deployer,
  );

  mineUntil(rov(pox5.rewardCycleToBurnHeight(1n)) + HALF_CYCLE_LENGTH);
  txOk(pox5.calculateRewards([0n]), deployer);

  expect(rov(pox5.getEarned(signer, 1n, 0n))).toBe(
    bondTargetYieldPerCalculation({ sats: remainingSbtc, targetRate }),
  );
});
