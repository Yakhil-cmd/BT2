### Title
Coretime revenue is permanently stranded in the Broker pallet's account when a timeslice has zero total InstaPool contributions - (File: substrate/frame/broker/src/tick_impls.rs)

### Summary
`pallet_broker::Pallet::process_revenue` (`substrate/frame/broker/src/tick_impls.rs:97-151`) converts on-demand coretime revenue reported for a timeslice into a payout record (`InstaPoolHistoryRecord::maybe_payout`) that is later distributed to Pool contributors via `do_claim_revenue`. If, for that timeslice, the sum of `system_contributions` and `private_contributions` is zero (i.e., no core was assigned to the `Pool` for that timeslice, either by the system or by a private contributor), the function takes the `else` branch and simply calls `InstaPoolHistory::<T>::remove(when)` and emits `Event::HistoryDropped`, discarding the entire `revenue` amount with no transfer anywhere. This mirrors TRST-M-2: an aggregate "claimable" balance is zeroed/discarded instead of being distributed when there are no eligible recipients ("partners"), except here the money involved is already resident in the Broker pallet's own account. [1](#0-0) 

### Finding Description
`process_revenue` withdraws the funds this pallet already holds as part of routine bookkeeping:
- `Self::charge(&Self::account_id(), system_payout)` withdraws the system's share *from the Broker pallet's own account* (`Self::account_id()`), proving the on-demand revenue for the timeslice is already sitting in the pallet's pot by the time this function executes. [2](#0-1) [3](#0-2) 

- When `total_contrib` (`system_contributions + private_contributions`) is zero, `system_payout` is forced to `Zero::zero()`, and since `r.private_contributions > 0` is also false, the code takes the `else` branch:
```
} else {
    InstaPoolHistory::<T>::remove(when);
    Self::deposit_event(Event::<T>::HistoryDropped { when, revenue });
}
``` [4](#0-3) 

No `T::Currency::transfer`/`mint_into`/`OnRevenue::on_unbalanced` call happens for the `revenue` amount in this branch — it is simply dropped from bookkeeping. Because the currency corresponding to that on-demand revenue was already deposited into `Self::account_id()` by the relay-chain-notified on-demand revenue mechanism (the same account from which `system_payout` is withdrawn above, and the same account `do_claim_revenue` later pays private claims out of, confirmed by the pot()/revenue() test helpers in `tests.rs` showing accumulated balances tracked in `Self::account_id()` prior to any claim), this discarded `revenue` value represents real currency that stays permanently in the Broker pallet's account with no code path left to move it out — neither to the system, to a treasury, nor to any private contributor. This is structurally identical to TRST-M-2: an aggregated claimable amount is zeroed without distribution when the "recipient set" (here, InstaPool contributors — the analog of "partners") is empty for that period, permanently locking the funds in the contract/pallet.

Compared to the sibling code path for `do_claim_revenue`, which was hardened (per `substrate/frame/broker/src/tests.rs:3361-3409`, `claim_revenue_reverts_when_pot_cannot_pay`) to make sure a claim is never silently lost even if the transfer fails, the `process_revenue` zero-contribution branch has no equivalent protection — it always drops the value. [5](#0-4) 

### Impact Explanation
On-demand coretime revenue collected during any timeslice in which no core happens to be assigned to `Pool` (neither system-provided idle cores nor privately pooled regions) becomes permanently unrecoverable — it stays in the Broker pallet's account with no extrinsic or internal logic capable of moving it out. This is a loss of funds that should have gone either to the treasury/system payout or to future private claimants; instead they are silently orphaned. This matches the reported bug class ("anybody can forfeit partner fees if there are no partners") almost exactly, differing only in that here the trigger is a natural/no-privileged-actor timeslice state (zero InstaPool contributions) rather than a directly-called permissionless function.

### Likelihood Explanation
This requires no privileged role or attacker action beyond ordinary permissionless usage: any account can purchase on-demand coretime (`do_purchase_credit`) during a period when no core has been reserved/sold into the `Pool` assignment for that timeslice (e.g., early in a chain's life, or any window where the `Reserve`d Pool core schedule and the `SaleInfo` schedule leave the InstaPool without contributions for that specific timeslice). Given that InstaPool contribution levels vary block-to-block and are not guaranteed non-zero at all times, this is a realistically reachable state.

### Recommendation
In `process_revenue`, when `total_contrib.is_zero()`, do not simply `remove` the history record and drop `revenue`. Instead route the entire `revenue` amount through `T::OnRevenue::on_unbalanced` (the same sink used for `system_payout`) or transfer it to a defined fallback (e.g., treasury), analogous to how the reviewed mitigation of TRST-M-2 kept the funds rather than zeroing an unclaimed distribution ledger.
