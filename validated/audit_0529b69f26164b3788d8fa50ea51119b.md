### Title
Unchecked RAY-value overflow permanently freezes an oversized market - ([File: contracts/pool/src/interest.rs])

### Summary
Interest accrual can overflow `i128` while converting scaled debt to its indexed value, permanently locking the affected market. [1](#0-0) [2](#0-1) 

### Finding Description
Every pool mutation loads the market through `synced_market`, which calls `interest::global_sync` before executing the requested operation. [3](#0-2)  `global_sync` accrues one or more chunks and calculates utilization from `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [4](#0-3) [1](#0-0) 

For a sufficiently large scaled book, a borrow-index increase can make `borrowed * borrow_index` exceed `i128::MAX` even though the configured borrow-index cap has not been reached. [5](#0-4)  The public `update_indexes` path forwards directly to pool accrual, so any caller can trigger the arithmetic cliff once enough time has elapsed. [6](#0-5) [7](#0-6) 

Because the panic occurs before the new accrual timestamp is committed, subsequent calls begin from the same stale timestamp and overflow again. [8](#0-7) [9](#0-8)  The repository’s boundary test demonstrates that after this failure both withdrawal and repayment continue to revert with `MathOverflow`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [10](#0-9) 

### Impact Explanation
Once the overflow is reached, every operation that syncs the affected market is blocked, including withdrawal, repayment, liquidation, borrowing, supplying, flash loans, recapitalization, and `update_indexes`. [3](#0-2) [11](#0-10) 

Suppliers cannot withdraw their principal or accrued yield, borrowers cannot repay, liquidators cannot reduce underwater debt, and recapitalization cannot repair the book because all of those paths first execute the same accrual. [12](#0-11) [13](#0-12) [14](#0-13)  This is a permanent freezing of user funds and an inability to operate the affected market, rather than a transient transaction-resource failure. [2](#0-1) 

### Likelihood Explanation
The trigger requires a valid market to accumulate a very large token book and sustained high utilization long enough for the borrow index to push its indexed RAY value over `i128::MAX`. [15](#0-14)  An unprivileged whale can create that state through ordinary `supply` and `borrow` calls when the listed caps and collateral permit it, and any caller can later invoke `update_indexes` to hit the overflow. [16](#0-15) [17](#0-16) [18](#0-17) 

The repository reproduces the condition with an 18-decimal market containing one billion whole tokens at 98% utilization and shows the cliff is reached before the intended index bound. [19](#0-18)  The required scale makes this less likely than an ordinary arithmetic boundary, but it is within the protocol’s accepted numeric and market-parameter domain. [20](#0-19) [2](#0-1) 

### Recommendation
Clamp or chunk indexed-value calculations before multiplication can overflow, or cap aggregate scaled balances at a value that preserves `scaled * index <= i128::MAX` for every index permitted by `MAX_BORROW_INDEX_RAY`. [1](#0-0) [21](#0-20) 

At minimum, accrual should commit progress up to the last safe timestamp or switch the index to its configured cap before evaluating utilization, ensuring repayment and withdrawal remain available after the cliff. [8](#0-7) [3](#0-2)  Market caps should also be validated against the maximum reachable borrow index rather than only token units. [2](#0-1) 

### Proof of Concept
1. A whale supplies one billion whole units of an 18-decimal asset to the market. [22](#0-21) 
2. Through an account with sufficient separate collateral, the whale borrows 98% of that liquidity. [23](#0-22) 
3. After sustained high-utilization accrual, an arbitrary caller submits `update_indexes(caller, [BIG18])`; accrual reaches `scaled_to_original` with `borrowed * borrow_index > i128::MAX` and reverts with `MathOverflow`. [6](#0-5) [24](#0-23) 
4. The stored borrow index remains below `MAX_BORROW_INDEX_RAY`, so the configured index ceiling does not prevent the overflow. [25](#0-24) 
5. Later `withdraw` and `repay` calls still execute accrual first and revert with the same `MathOverflow`, leaving supplier funds and debt operations permanently blocked. [3](#0-2) [11](#0-10)

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index

        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

    aggregated: &AggregatedPayments,
    cache: &mut Context,

    let pool_addr = cache.cached_pool_address();
    let mut actions: Vec<PoolAction> = Vec::new(env);

            payer,
            &pool_addr,

            GenericError::AmountMustBePositive,
        );
        actions.push_back(make_pool_action(&position, amount_in, hub_asset.clone()));
    }

        env,
        account,
        payer,
