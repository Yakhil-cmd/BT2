### Title
AA payment messages for fixed-denomination assets are silently dropped, causing state/ledger desync and fund loss - (File: aa_composer.js)

### Summary
An Autonomous Agent (AA) cannot actually deliver a payment in a fixed-denomination ("indivisible") asset to a recipient: when composing the response unit, `sendUnit()` silently strips out any `payment` message whose asset is `fixed_denominations`, with no error and no bounce. If the AA's own `state` formula (evaluated as part of the same trigger) has already updated internal bookkeeping variables (e.g., decrementing a tracked balance) on the assumption that the payment would go out, the recipient never receives the tokens while the AA's internal ledger records the debit as done — an unrecoverable, silent fund-loss/state-desync condition, directly analogous to the reported bridge issue where a token-type mismatch causes an unhandled path and effectively locks/loses funds without any revert being surfaced to the caller.

### Finding Description
`getTrigger`/`handleTrigger` build `trigger.outputs` for whatever asset the trigger sender pays in, and an AA's oscript can construct arbitrary outbound `payment` messages, including ones denominated in any asset known to the network — including fixed-denomination ("indivisible", NFT-like/coin-denomination) assets [1](#0-0) .

When `sendUnit()` processes the AA's outgoing messages, it loads asset info for each non-base payment and, if the asset is `fixed_denominations`, simply calls `cb()` without building any inputs/outputs for it (`if (objAsset.fixed_denominations) // will skip it later \n return cb();`) [2](#0-1) .

After the per-message loop finishes, the composer performs a second filtering pass that unconditionally removes any payment message referencing a `fixed_denominations` asset from the final unit:
`messages = messages.filter(function (message) { return (message.app !== 'payment' || !message.payload.asset || !assetInfos[message.payload.asset].fixed_denominations); });`
If that empties the message list, the AA quietly finishes with `handleSuccessfulEmptyResponseUnit(null)` — a "success," not a bounce [3](#0-2) .

Critically, the AA's `state` message (which updates the AA's own `var[...]` bookkeeping, e.g. decrementing a user's tracked balance as in the sample bank AA `test/samples/a_bank_without_percent.oscript`) is evaluated and included as part of the same trigger response independent of whether the corresponding `payment` message survived this filtering [4](#0-3) . There is no mechanism that ties the success of state-variable updates to the actual delivery of a fixed-denomination payment output — the payment payload is dropped after `template.messages` has already been evaluated by the oscript engine, so the AA logic has no way to detect or react to the drop.

This mirrors the external report's bug class exactly: a downstream/expected transfer mechanism (native token receive call vs. ERC-20 approve/transfer) silently fails to execute because the target does not support the given asset representation, and because there is no fallback/handling for that mismatch, value that the higher-level accounting believes was moved is instead lost or stuck.

### Impact Explanation
Any AA author (an unprivileged, permissionless oscript author) that builds payout logic without being aware of this limitation will cause real user funds to be permanently lost: the AA's internal ledger (`var[...]`) is decremented as if the payout succeeded, but no unit is ever emitted carrying the fixed-denomination asset to the recipient, and the trigger sender receives no error/bounce indicating failure. Because AA response building always proceeds via `sendUnit`/`sendDummyUnit`, this affects every live AA on the network that attempts to distribute an indivisible asset, not just a hypothetical one. This satisfies the "AA fund loss or freezing" impact bar.

### Likelihood Explanation
The trigger for the bug is trivial and requires no special privilege: any user can define an AA whose payout logic references a fixed-denomination asset (a common asset type, e.g., collectible/NFT-like tokens), and any trigger sender can invoke it normally. No malicious peer/node/hub behavior is needed — it's a straightforward consequence of AA definitions/oscript/triggers interacting with a specific, well-supported asset type (`fixed_denominations`), so likelihood is high whenever such an AA is deployed and used.

### Recommendation
Either (a) implement genuine support for composing fixed-denomination payment messages from AAs (mirroring `indivisible_asset.js`'s coin-selection/spend logic), or (b) fail loudly: bounce the trigger (reverting all state changes) whenever a `payment` message targeting a `fixed_denominations` asset cannot be delivered, instead of silently filtering it out and returning a "successful" empty response. At minimum, `aa_validation.js` should statically reject AA templates that attempt to send `payment` messages for assets known to be fixed-denomination, so the failure mode is caught at AA-definition time rather than silently corrupting bookkeeping at execution time.

### Proof of Concept
1. Issue an asset with `fixed_denominations: true` (e.g., following the pattern in `test/samples/create_an_asset.oscript`).
2. Deploy an AA modeled on `test/samples/a_bank_without_percent.oscript`, but configured so the withdrawal branch pays out in the fixed-denomination asset instead of `trigger.data.asset` being restricted to divisible assets: on trigger, it emits `{app:'payment', payload:{asset: <fixed_denom_asset>, outputs:[{address: trigger.address, amount: X}]}}` together with a `state` message that unconditionally decrements `var[$key]` by `X`.
3. A user with a positive tracked balance sends a withdrawal trigger.
4. Trace through `aa_composer.js`: `assetInfos[asset].fixed_denominations === true` → the payment message is skipped in the first pass [5](#0-4)  and stripped in the second filter pass [6](#0-5) . If no other payment message remains, `handleSuccessfulEmptyResponseUnit(null)` is invoked [7](#0-6)  — the response unit is finalized successfully, `var[$key]` is permanently decremented, yet the user never receives the fixed-denomination tokens. The funds are unrecoverable through normal AA interaction.
