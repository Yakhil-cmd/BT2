### Title
Webhook signature verified against `repository.owner.login` while every handler acts on the unverified `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/organization config (and therefore the `webhook_secret` used to validate the HMAC signature) using `repository_owner`, derived from the JSON body itself (`repository.owner.login` or `organization.login`). However, none of the event handlers use that field to decide which `Stack`/`Repository` to mutate — they instead use the sibling field `repository.full_name`, which is covered by the same JSON body but never cross-checked against the field that selected the signing key. In a multi-organization Shipit deployment (`Shipit.github_organizations`/`github_app_config`), this breaks the equality "organization that authenticated == repository that is written."

### Finding Description
`Shipit::WebhooksController#verify_signature` resolves the signing secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted, attacker-supplied JSON body (`params.dig('repository', 'owner', 'login')`), and is used only to pick which `GitHubApp`/`webhook_secret` (`Shipit.github(organization: repository_owner)`) is used to validate `X-Hub-Signature`: [3](#0-2) 

Once the signature is accepted, the raw payload is dispatched to every registered handler: [4](#0-3) 

But every handler resolves the target `Repository`/`Stack` from a *different* field in the very same JSON body: `payload.dig('repository', 'full_name')`: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

`Repository.from_github_repo_name` splits `owner/name` from that unverified `full_name` string and looks up the DB record by owner+name, with no relation at all to `repository_owner`/the app config that validated the signature: [9](#0-8) 

In the single-organization/single-webhook-secret deployment (the default `github_default_organization.nil?` path in `Shipit.github`), this is not exploitable because there is only one secret for the whole instance. But Shipit explicitly supports a **multi-organization** configuration keyed by organization (`TOP_LEVEL_GH_KEYS`, `github_app_config`, `github_organizations`), each with its own independent `webhook_secret`: [10](#0-9) [11](#0-10) 

In that configuration, whoever legitimately controls org A's webhook secret (e.g. because they administer the GitHub App/webhook installation for their own org/repo that Shipit is configured to serve) can compute a *valid* signature for org A while placing an arbitrary `repository.full_name` (e.g. `"OrgB/other-repo"`) in the body. `verify_signature` only checks that the HMAC matches org A's secret; it never confirms that the `full_name` used by the handlers actually belongs to org A. The handler then happily resolves and mutates `OrgB/other-repo`'s stacks (triggers `sync_github`, archives/unarchives review stacks, updates pull request state, etc.) even though the signature never authenticated anything about `OrgB`.

This is the exact analog of the reported bug class: a value used by downstream logic (`fantiumFeeBPS` used unchecked in the claim math) that is never actually bound/validated by the mechanism meant to guarantee its safety (owner-restricted setter) — here, `repository.full_name` used by all handlers is never bound to `repository_owner`, the field that the HMAC signature check actually authenticates.

### Impact Explanation
This allows an attacker who legitimately controls one organization's webhook secret in a multi-tenant Shipit instance to forge trusted-looking webhook events that mutate stacks belonging to a *different* organization/repository they do not own — e.g. force `PushHandler` to trigger `sync_github` on another org's stack, or force `LabeledHandler`/`OpenedHandler` to archive/unarchive/create review stacks for another org's repository. This is a cross-repository state mutation authenticated by the wrong tenant's credential, matching the "cross-repository writes" high/critical impact category.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with multiple GitHub organizations, each with distinct `webhook_secret`s, and (2) attacker control of one such organization's own delivery secret (a low bar — anyone owning/administering that org's GitHub App/webhook config satisfies it, and this is treated as unprivileged relative to the *other* org being attacked). Single-organization deployments (the common case, `github_default_organization.nil?`) are not affected since there's only one shared secret. Likelihood is therefore conditional on multi-tenant configuration, but where present, the exploit path is straightforward (single crafted HTTP POST).

### Recommendation
In `WebhooksController#verify_signature`, after establishing which organization's secret validated the signature, ensure every downstream handler is constrained to operate only on repositories belonging to that same `repository_owner` — e.g. pass the authenticated organization alongside the payload and have `Handler#repository_name`/`stacks` reject or scope lookups where `full_name`'s owner segment does not match the authenticated organization.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` and `orgB`, each with its own `webhook_secret` (per `github_app_config`).
2. As the legitimate owner/admin of `orgA`'s webhook secret, craft a `push` (or `pull_request`) JSON payload where:
   - `repository.owner.login` = `"orgA"` (so `verify_signature` resolves `Shipit.github(organization: "orgA")` and the HMAC validates against `orgA`'s known secret), and
   - `repository.full_name` = `"orgB/target-repo"`.
3. POST the payload to `/webhooks` with `X-Hub-Signature` computed using `orgA`'s secret and `X-Github-Event: push`.
4. `verify_signature` passes (signature is valid for `orgA`). `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` and triggers `sync_github` on `orgB`'s stack, even though the signature never authenticated anything belonging to `orgB`.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
