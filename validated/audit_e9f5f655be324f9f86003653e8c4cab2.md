### Title
`Api::CCMenuController#stack` uses unscoped `Stack.from_param!`, bypassing `BaseController#stacks` tenant scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`BaseController#stacks` restricts stack lookups to `Stack.where(id: current_api_client.stack_id)` when the API client is stack-scoped, and `BaseController#stack` (line 79) correctly calls `stacks.from_param!`. `CCMenuController` overrides `#stack` and instead calls `Stack.from_param!` directly on the class, never invoking the scoped `stacks` relation, so any authenticated `read:stack`-permissioned API client can fetch CC.xml data for any stack ID regardless of the client's own `stack_id`.

### Finding Description
The intended binding is: `requested_stack.id ∈ current_api_client.stack_id? ? {current_api_client.stack_id} : Stack.all` — enforced by `stacks.from_param!(params[:stack_id])` in `app/controllers/shipit/api/base_controller.rb:78-80`.

`CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) overrides this method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```
This calls the class method `Stack.from_param!` directly, never touching `current_api_client.stack_id` at all. `require_permission :read, :stack` (line 6) only calls `current_api_client.check_permissions!('read', 'stack')`, which (per `app/models/shipit/api_client.rb:38-45`) merely checks that the string `"read:stack"` is present in the client's `permissions` array — it performs no comparison against `stack_id`. There is no other guard in the request path that re-establishes the scoping.

Attacker flow: attacker holds an `ApiClient` token scoped to `stack_id = 1` with permission `read:stack`. They issue `GET /api/stacks/999999/cc.xml?token=<token>` where stack `999999` belongs to a different repository/org. `authenticate_api_client` in `CCMenuController` (line 33-36) authenticates the token via `ApiClient.authenticate(params[:token])`, succeeds, and `#stack` resolves `Stack.from_param!(999999)` unconditionally, returning the victim's stack object. `#show` then renders `deploys_and_rollbacks.last` for that stack into `cc.xml`, leaking cross-tenant deploy state (stack name, latest deploy id/status/branch).

Existing guards do not prevent this: `require_permission!` checks only the permission-name string, not the stack-id binding; `stacks` scoping exists but is dead code for this controller.

### Impact Explanation
Any repository/stack-scoped API client with only `read:stack` permission can read deploy/task state (`deploys_and_rollbacks.last`, i.e., stack name, environment, latest deploy status/branch) for **any** stack on the Shipit instance, not just its own. This is an unauthenticated-for-that-tenant read of stack state across tenant boundaries — matching the High severity category "escalation ... unauthenticated read of stack state, task streams or deploy output." It is fully repeatable against arbitrary stack IDs (simple enumeration of `stack_id` in the URL) with no additional privilege required beyond holding any valid stack-scoped API token.

### Likelihood Explanation
Preconditions: attacker must already hold a valid `ApiClient` token (of `read:stack` permission, scoped to any stack) — this is a legitimate, low-privilege credential type in Shipit's own model. No GitHub secrets, session, or operator privileges are needed. Given such a token (which the question's threat model presumes the attacker as a "stack-scoped ApiClient" holder possesses), exploitation is trivial: change the `stack_id` in the URL path. This is a single unauthenticated-relative-to-target-tenant HTTP GET, fully deterministic and repeatable.

### Recommendation
Change `CCMenuController#stack` to use the scoped lookup, consistent with `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id` scoping (when present) is enforced identically to every other API controller inheriting from `BaseController`.
