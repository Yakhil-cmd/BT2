### Title
Silent `CLStakingInfo` Overwrite in `consolidateNodes` Causes Incorrect Prague-Era Reward Distribution — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidateNodes()` in `kaiax/staking/staking_info.go` silently overwrites a consolidated node's `CLStakingInfo` when two or more `NodeIds` that share the same `RewardAddr` each appear in the `CLStakingInfos` slice. The code relies on an unvalidated external invariant ("One CLStakingInfo per validator is guaranteed by CLRegistry") without enforcing it. If the CLRegistry returns entries for two NodeIds that belong to the same GC node (same `RewardAddr`), the first CL pool's staking amount is silently dropped from all reward calculations, causing incorrect KAIA distribution to that pool.

---

### Finding Description

In `consolidateNodes()`, the first loop builds a `nToR` map (`NodeId → RewardAddr`) and a `cmap` map (`RewardAddr → consolidatedNode`). The second loop iterates over `CLStakingInfos` and assigns:

```go
// One CLStakingInfo per validator is guaranteed by CLRegistry.
cmap[r].CLStakingInfo = clsi   // line 157 — plain assignment, not a guard
``` [1](#0-0) 

There is no check for whether `cmap[r].CLStakingInfo` is already set. If two `CLStakingInfo` entries in the slice have `CLNodeId` values that both resolve to the same `RewardAddr` `r` (because a GC node registered multiple NodeIds in AddressBook), the second entry silently overwrites the first. The first CL pool's `CLStakingAmount` is permanently lost.

The test suite explicitly documents this behavior and dismisses it as "not feasible in real":

```go
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
``` [2](#0-1) 

The upstream parsers that populate `CLStakingInfos` perform no deduplication either:

```go
clStakingInfos = make(staking.CLStakingInfos, len(clRes.NodeIds))
for i := range clRes.NodeIds {
    clStakingInfos[i] = &staking.CLStakingInfo{
        CLNodeId:        clRes.NodeIds[i],
        ...
    }
}
``` [3](#0-2) [4](#0-3) 

The "one CL per GC" invariant is assumed to be enforced by the CLRegistry on-chain contract, but the Go layer never validates it before using the data for reward computation.

---

### Impact Explanation

After the Prague hardfork, `assignStakingRewards` and `assignStakingRewardsFlex` call `si.ConsolidatedNodes()` and use `cn.CLStakingInfo` to split block rewards between the CN staking contract and the CL pool:

```go
cnAmount, clAmount := cn.Split(reward)
alloc[cn.RewardAddr] = cnAmount
alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount
``` [5](#0-4) 

`Split()` uses `cn.CLStakingInfo.CLStakingAmount` as the CL weight:

```go
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
clAmount := new(big.Int).Mul(clAmountBig, amount)
clAmount = clAmount.Div(clAmount, totalAmount)
``` [6](#0-5) 

When the first CL pool's entry is overwritten, its `CLStakingAmount` is excluded from `totalAmount`. The surviving entry's pool receives rewards calculated against a different (wrong) staking weight. The dropped CL pool receives zero KAIA rewards for that block, despite having staked. This is a direct incorrect reward distribution affecting KAIA and system-managed funds.

---

### Likelihood Explanation

A GC node legitimately registers multiple NodeIds in AddressBook (all sharing one `RewardAddr`). If the CLRegistry contract permits each NodeId to independently register a CL pool — or if the CLRegistry is upgraded, buggy, or returns stale data — the Go layer will silently drop all but the last CL entry for that GC. The Go code contains no guard, no error, and no log for this case. The README itself documents that multiple NodeIds per GC is a supported and expected configuration:

> Sometimes a node would register multiple NodeIds in AddressBook, in which each entry has different StakingAddr and same RewardAddr. [7](#0-6) 

---

### Recommendation

Add a duplicate-detection guard in `consolidateNodes()` before assigning `CLStakingInfo`:

```go
if r, ok := nToR[clsi.CLNodeId]; ok {
    if cmap[r].CLStakingInfo != nil {
        // Log an error and skip or aggregate — do not silently overwrite.
        logger.Error("duplicate CLStakingInfo for RewardAddr", "rewardAddr", r,
            "existing", cmap[r].CLStakingInfo.CLNodeId, "duplicate", clsi.CLNodeId)
        continue
    }
    cmap[r].CLStakingInfo = clsi
}
```

Additionally, `parseCallResult` and `parsePermissionlessCallResult` should validate that `clRes.NodeIds` contains no duplicates before constructing `CLStakingInfos`, so the invariant is enforced at the boundary where external contract data enters the Go layer rather than deep inside reward computation.

---

### Proof of Concept

Given:
- AddressBook: `NodeIds=[N1, N3]`, `RewardAddrs=[R1, R1]`, `StakingAmounts=[10M, 40M]`
- CLRegistry returns: `[{CLNodeId:N1, CLPoolAddr:P1, CLStakingAmount:1M}, {CLNodeId:N3, CLPoolAddr:P2, CLStakingAmount:3M}]`

After `consolidateNodes()`:
- `cmap[R1].CLStakingInfo = {N3, P2, 3M}` — P1's 1M is silently dropped

In `assignStakingRewards`, `cn.Split(reward)` uses only `3M` as CL weight against `50M` CN staking. Pool P1 receives `0` KAIA. Pool P2 receives a reward calculated with `3M / (50M + 3M)` weight instead of the correct `(1M + 3M) / (50M + 4M)` split across both pools. [8](#0-7) [9](#0-8)

// consolidatedNode is the refined staking information suitable for proposer selection.
// Sometimes a node would register multiple NodeIds in AddressBook,
// in which each entry has different StakingAddr and same RewardAddr.
// We treat those entries with common RewardAddr as one GC node.
//
// For example,
//
//	NodeIds          = [N1, N2, N3]
//	StakingContracts = [S1, S2, S3]
//	RewardAddrs      = [R1, R1, R3]
//	StakingAmounts   = [A1, A2, A3]
//
// can be consolidated into
//
//	CN1 = {[N1,N2], [S1,S2], R1, A1+A2}
//	CN3 = {[N3],    [S3],    R3, A3}
//
// If the node has CLStakingInfo, it will be added to the consolidatedNode.
type consolidatedNode struct {
	NodeIds          []common.Address
	StakingContracts []common.Address
	RewardAddr       common.Address // The common RewardAddr
	StakingAmount    uint64         // Sum of the staking amounts from CNStaking

	CLStakingInfo *CLStakingInfo // The CLStakingInfo if any
}

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

	// CLStakingInfo can only exist after Prague HF.
	if len(si.CLStakingInfos) > 0 {
		for _, clsi := range si.CLStakingInfos {
			// If the nodeId of CLStakingInfo is not found in nToR, it means the validator is not in the AddressBook.
			// So we skip it.
			if r, ok := nToR[clsi.CLNodeId]; ok {
				// One CLStakingInfo per validator is guaranteed by CLRegistry.
				cmap[r].CLStakingInfo = clsi
			}
		}
	}

	carr := make([]consolidatedNode, 0, len(cmap))
	for _, r := range rList {
		carr = append(carr, *cmap[r])
	}
	return &carr
}

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
```
