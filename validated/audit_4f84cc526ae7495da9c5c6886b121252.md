Based on my research, this is an authentic and currently un-patched analog of the reported bug class, but it is the exact same bug pattern that was already found and fixed once in this codebase for a different pair (`NonTransfer`/`Governance`, PR #12769) — and it reappears for `NonTransfer`/`SudoBalances`.

### Title
`ProxyType::NonTransfer` on the Westend relay-chain runtime (and the analogous `rc` runtime) falsely claims `SudoBalances` as a subset, letting a `NonTransfer` proxy grant itself Sudo-balance privileges its own filter explicitly denies - (File: `polkadot/runtime/westend/src/lib.rs`)

### Summary
`pallet_proxy` authorizes `add_proxy`/`remove_proxy` purely through `InstanceFilter::is_superset` [1](#0-0) . In the Westend relay runtime, `ProxyType::is_superset` declares `NonTransfer` a superset of *every* other proxy type via a catch-all `(ProxyType::NonTransfer, _) => true` [2](#0-1) , but `NonTransfer`'s own `filter` explicitly omits the entire Sudo pallet ("`// Specifically omitting Sudo pallet`") [3](#0-2) , while `ProxyType::SudoBalances` admits `Sudo::sudo(Balances(..))` calls [4](#0-3) . This is precisely the class of bug fixed by [PR #12769](https://github.com/paritytech/polkadot-sdk) for `NonTransfer`/`Governance` on Asset Hub Westend [5](#0-4) , left unpatched here.

### Finding Description
`pallet_proxy::do_proxy` builds a call filter for the proxied origin that special-cases `add_proxy`/`remove_proxy`: it blocks the call only `if !def.proxy_type.is_superset(proxy_type)`; otherwise it falls through to the generic `def.proxy_type.filter(c)` [6](#0-5) . `NonTransfer`'s generic filter admits `RuntimeCall::Proxy(..)` wholesale [7](#0-6) , so once `is_superset` returns `true` the `add_proxy`/`remove_proxy` call is permitted.

Because `is_superset` uses an unconditional catch-all for `NonTransfer` [8](#0-7) , a `NonTransfer` delegate can call `Proxy::add_proxy{ proxy_type: SudoBalances, .. }` on behalf of the delegator, even though `NonTransfer`'s own `filter` denies `Sudo` calls outright. The newly created `SudoBalances` proxy can then dispatch `Sudo::sudo(Balances::force_set_balance/transfer_keep_alive/...)` as the delegator, a capability `NonTransfer` was designed to exclude.

The identical structural flaw (same `ProxyType` shape, same `SudoBalances` filter, same unconditional `(ProxyType::NonTransfer, _) => true` superset relation) exists in `substrate/frame/staking-async/runtimes/rc/src/lib.rs` [9](#0-8) .

The impact is realized only when the delegator (`real`) is the account configured as the chain's `pallet_sudo::Key`, since `pallet_sudo::sudo` re-checks `ensure_signed(origin) == Key::<T>::get()` regardless of proxy machinery — but that is exactly the scenario `NonTransfer`'s explicit Sudo-omission comment is meant to guard against (an ops/automation delegate that must never reach Sudo-gated balance moves).

### Impact Explanation
If the Sudo key holder has granted any account a `NonTransfer` proxy (a documented, encouraged usage pattern for "non-fund-moving" delegation), that delegate can silently escalate to a `SudoBalances` proxy and move/force-set the Sudo key holder's balances via `Sudo::sudo(Balances::force_set_balance{..})`/similar — a capability the delegator never intended to grant and that `NonTransfer`'s filter is documented to exclude. This mirrors CWE-269 (privilege escalation via inherited administrative scope) in the report: a restricted delegated credential silently inherits a more privileged capability that its own explicit deny-list forbids.

### Likelihood Explanation
Likelihood is bounded by the precondition that the delegator account is the runtime's configured Sudo key and has granted a `NonTransfer` proxy to some account — a plausible but narrower prerequisite than the previously-fixed `Governance` case (Sudo keys exist mainly on testnets/staging runtimes such as Westend, and production Polkadot/Kusama relay runtimes do not include `pallet_sudo`). No privileged role, governance action, or stolen keys are required by the attacker beyond already being a legitimately delegated `NonTransfer` proxy — the escalation step itself requires no special permission.

### Recommendation
Remove `SudoBalances` (and any other type whose filter reaches pallet calls `NonTransfer` explicitly omits) from `NonTransfer`'s superset relation in `polkadot/runtime/westend/src/lib.rs` and `substrate/frame/staking-async/runtimes/rc/src/lib.rs`, following the same fix pattern and add a lattice-covering regression test (as added for Asset Hub Westend in PR #12769) that asserts, for every declared `(superset, subset)` pair, that every call admitted by `subset.filter` is also admitted by `superset.filter`.

### Proof of Concept
Failed guard trace (`substrate/frame/proxy/src/lib.rs:1005-1021`):
1. Delegator `R` (= `pallet_sudo::Key::<T>::get()`) calls `Proxy::add_proxy(R, D, ProxyType::NonTransfer, 0)`, funding the deposit — an ordinary, intended delegation.
2. `D` calls `Proxy::proxy(D, R, None, Box::new(RuntimeCall::Proxy(pallet_proxy::Call::add_proxy{ delegate: D, proxy_type: ProxyType::SudoBalances, delay: 0 })))`.
3. In `do_proxy`, `c.is_sub_type()` matches `Call::add_proxy{ proxy_type: SudoBalances }`; guard `!NonTransfer.is_superset(&SudoBalances)` evaluates `!true = false`, so this arm is skipped; execution falls to `_ => NonTransfer.filter(c)`, which returns `true` because `RuntimeCall::Proxy(..)` is unconditionally admitted. `add_proxy_delegate` succeeds — `D` is now a `SudoBalances` proxy for `R`.
4. `D` calls `Proxy::proxy(D, R, Some(ProxyType::SudoBalances), Box::new(RuntimeCall::Sudo(pallet_sudo::Call::sudo{ call: Box::new(RuntimeCall::Balances(pallet_balances::Call::force_set_balance{ who: D, new_free: X })) })))`. `SudoBalances.filter` admits this per its match arm; `pallet_sudo::sudo` then checks `ensure_signed(origin) == Key` where `origin = Signed(R)` — succeeds because `R` is the real Sudo key holder — and executes the privileged balance mutation.

This is a static code-path trace through the exact production `filter`/`is_superset`/`do_proxy` symbols; no test harness was executed and no claim of a completed test run is made. Reachability depends on the runtime including `pallet_sudo` with an active `Key` (true for the Westend testnet runtime as configured at `polkadot/runtime/westend/src/lib.rs:899-903`); production Polkadot/Kusama do not configure `pallet_sudo`, which should be factored into bounty-program scope/severity assessment.
