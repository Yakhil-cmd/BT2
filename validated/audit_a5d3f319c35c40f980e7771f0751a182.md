### Title
Cross-organization webhook authentication bypass via `repository.owner.login` vs `repository.full_name` binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to verify a webhook's HMAC signature against using `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON payload, while the event handlers that actually act on the payload look up the target `Stack`/`Commit` using the separate `repository.full_name` field. These two fields are never checked for consistency, and when the organization selected for verification has no `webhook_secret` configured, signature verification is a no-op that returns `true` unconditionally.

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload and fetches that organization's `GitHubApp`: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations, each with its own independently configured (and optional) `webhook_secret`: [4](#0-3) [5](#0-4) 

Meanwhile, every event handler (`Handler#stacks`, `PushHandler`, `StatusHandler`, pull_request handlers) resolves the actual repository/stack to mutate using the *separate* `repository.full_name` payload field, not `repository.owner.login`: [6](#0-5) [7](#0-6) 

The binding the system implicitly relies on is:
`organization used to select webhook_secret (repository.owner.login)` == `organization whose repository/stack is written (repository.full_name)`

Nothing in `verify_signature` or in `Handler` enforces this equality. If the Shipit deployment has multiple organizations configured (per `docs/setup.md`'s "Using Multiple Github Applications" section) and any one of them has `webhook_secret` left blank (shown as the default/example value `# nil` in every sample config), an attacker can:
1. Craft an arbitrary webhook JSON body with `repository.owner.login` (or `organization.login`) set to the organization that has **no** `webhook_secret` configured.
2. Set `repository.full_name` (and any other handler-consumed fields) to point at a **different**, secret-protected organization's repository/stack.
3. Send it to `POST /github/webhooks` with any `X-Hub-Signature` value (or none).

`verify_signature` looks up the no-secret organization's `GitHubApp`, calls `verify_webhook_signature`, which short-circuits to `true` because `webhook_secret` is blank — regardless of the actual signature — and the request proceeds to the handler with attacker-controlled payload content targeting the other organization's repositories.

### Impact Explanation
The `status` webhook handler creates a `Status` for any commit matching the attacker-supplied `sha`/`state`/`context`, using only the unauthenticated payload: [8](#0-7) [9](#0-8) 

This status feeds directly into merge-queue gating (`MergeRequest#all_status_checks_passed?`) and deploy gating (`Commit#deployable?`), both of which drive automatic merges and deploys: [10](#0-9) [11](#0-10) 

An attacker exploiting this bypass on a multi-org Shipit instance (where at least one configured org has no `webhook_secret`) can forge a passing CI status for an arbitrary commit belonging to a *different, protected* organization's repository, causing `ProcessMergeRequestsJob` to auto-merge a pull request or `trigger_continuous_delivery` to auto-deploy a commit that never actually passed CI — an unauthorized merge/deploy without holding any Shipit session, `ApiClient` token, or the target organization's `webhook_secret`.

### Likelihood Explanation
Likelihood depends entirely on operator configuration: this is only exploitable when (a) the Shipit instance is configured with multiple GitHub organizations (an explicitly documented, supported configuration) and (b) at least one of those organizations has `webhook_secret` unset — which is the value shown in every provided config example/template. Given the documentation and examples default to a blank `webhook_secret`, this is a plausible real-world misconfiguration rather than a purely theoretical one, but it does require that specific multi-org + missing-secret combination to exist.

### Recommendation
Enforce that the organization used to verify the webhook signature matches the organization whose repository the handlers will act on, e.g., derive/validate `repository.full_name`'s owner against `repository_owner` before dispatching to handlers, and/or treat a missing `webhook_secret` as a hard misconfiguration error in multi-organization mode rather than silently succeeding in `verify_webhook_signature`.

### Proof of Concept
Given a `config/secrets.yml` configured as:
```yaml
github:
  OrgNoSecret:
    app_id: ...
    installation_id: ...
    webhook_secret: # left blank
  OrgProtected:
    app_id: ...
    installation_id: ...
    webhook_secret: "s3cr3t"
```
Send:
```
POST /github/webhooks
X-Github-Event: status
X-Hub-Signature: sha1=anything-or-omitted

{
  "sha": "<victim-commit-sha-in-OrgProtected/repo>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "OrgNoSecret" }, "full_name": "OrgProtected/repo" }
}
```
`repository_owner` resolves to `OrgNoSecret` → `Shipit.github(organization: 'OrgNoSecret').verify_webhook_signature` returns `true` unconditionally (per `lib/shipit/github_app.rb:76-83`) → request passes to `StatusHandler`, which creates a `success` status for the targeted commit in `OrgProtected/repo`, potentially unblocking an auto-merge/auto-deploy for a repository the attacker never had credentials for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
