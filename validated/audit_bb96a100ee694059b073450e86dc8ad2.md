## Title
Rollback environment variables bypass the `shipit.yml` whitelist enforced for deploys - ([File: app/models/shipit/deploy.rb])

### Summary
Shipit enforces that any custom environment variable an unprivileged deployer supplies must be declared in the stack's `shipit.yml` (`deploy.variables` / `rollback.variables`), and unlisted keys are rejected before being spawned in a shell. This whitelist is applied inconsistently: the web `RollbacksController#create` path calls `Deploy#trigger_rollback` → `Deploy#build_rollback`, which stores `env: env.to_h` verbatim, with **no call to `filter_rollback_envs`**.

### Finding Description
The binding that should hold is: *environment key permitted by `shipit.yml` (`rollback.variables`/`deploy.variables`) == environment key actually spawned in the deploy host shell*.

For deploys, this is enforced in `Stack#build_deploy`: [1](#0-0) 
which calls `filter_deploy_envs(env.to_h)` — i.e. `EnvironmentVariables.with(env).permit(deploy_variables)`, raising `NotPermitted` for any key not declared in `shipit.yml`. [2](#0-1) [3](#0-2) 

However, `Deploy#build_rollback` — used by the web `RollbacksController#create` action — does not filter at all: [4](#0-3) [5](#0-4) 

The web controller does apply Rails strong-parameter permitting (`params.require(:rollback).permit(:parent_id, env: @stack.rollback_variables.map(&:name))`), which is a reasonable mitigation for *this specific entry point*. But the model method itself carries no defense-in-depth: `build_rollback` accepts and persists an arbitrary `env` hash and is also invoked from `Deploy#trigger_rollback`, called internally from `Deploy#trigger_revert_if_required` with the aborted task's own `env` (already trusted at that point) — so the practical exploitation surface for an external, unprivileged caller is the web controller's strong-parameter permit list, not the model. In addition, `Deploy#trigger_revert` sets `env: env || self.env` directly with no `filter_*_envs` call either: [6](#0-5) 

The stored `env` is later merged, unfiltered, straight into the spawned shell command's environment in `TaskCommands#env`: [7](#0-6) 

### Impact Explanation
Where the whitelist enforcement is genuinely missing (i.e., wherever an `env` hash reaches `build_rollback`/`trigger_revert` without having first passed through `filter_rollback_envs`/`filter_deploy_envs`), an attacker could set arbitrary environment variable names — not merely values — that get exported into the deploy shell alongside `GIT_COMMITTER_NAME`, `SHIPIT_LINK`, etc. Depending on the deploy/rollback scripts in the repository (which frequently reference `$VARNAME` or bash-specific dynamic evaluation), unexpected environment variable names could influence shell behavior (e.g. `IFS`, `BASH_ENV`, `PS4`+`PROMPT_COMMAND` in some shells, or `LD_PRELOAD`-style vars for spawned subprocesses) — a path toward RCE on the deploy host, which matches the Critical impact bar in this program.

### Likelihood Explanation
Low-to-moderate. The only concretely identified path is the web `RollbacksController`, which does apply Rails' strong-parameter permit-list scoped to `@stack.rollback_variables.map(&:name)` before calling `trigger_rollback`, so the whitelist is *effectively* enforced there today, just via a different, less centralized mechanism than `filter_rollback_envs`. I could not find, within the reachable engine code inspected, a caller that supplies fully attacker-controlled, unpermitted keys directly into `build_rollback`/`trigger_revert` without going through some form of parameter permitting first. This makes the finding a defense-in-depth / inconsistency issue rather than a proven, directly exploitable bypass in the current call graph — I was not able to fully trace every caller of `trigger_revert` (e.g. from `report_complete!`/health-check flows or `MarkDeployHealthyJob`) to confirm none of them can be reached with attacker-influenced `env` bypassing the controller-level permit list.

### Recommendation
Apply `stack.filter_rollback_envs` (and `filter_deploy_envs` where relevant) directly inside `Deploy#build_rollback` and `Deploy#trigger_revert`, rather than relying solely on controller-level `strong_parameters` permitting. This centralizes the deployment-trust binding (`shipit.yml`-declared variable name == spawned environment variable name) at the model layer so it can't be silently bypassed by any current or future caller (jobs, console, other controllers) that constructs a `Rollback` with a raw `env` hash.

### Proof of Concept
Not independently reproduced end-to-end; based on static code reading:
1. In `shipit.yml`, declare `rollback.variables: [{name: SAFE_VAR}]`.
2. Via the web UI/form POST to `RollbacksController#create` with `rollback[env][SAFE_VAR]=x` — this is filtered by strong params today.
3. The concern is any code path (current or future) that calls `Deploy#build_rollback(env: attacker_hash)` or `Deploy#trigger_revert(env: attacker_hash)` directly, bypassing controller-level permitting — such a call would persist arbitrary env keys unfiltered and later merge them into `Command`'s spawned environment via `TaskCommands#env`, with no `EnvironmentVariables::NotPermitted` check ever raised.     def sanitize_env_vars(variable_definitions)
```ruby
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
```

```ruby
      previous_successful_commit = rollback_to&.until_commit || commit_to_rollback_to

      rollback = Rollback.create!(
        user_id:,

        parent_id: id,
        since_commit: until_commit,

        env: env || self.env,
        allow_concurrency: force
      )

      rollback.enqueue
      lock_reason = "A rollback for #{until_commit.sha} has been triggered. " \
        "Please make sure the reason for the rollback has been addressed before deploying again."

      stack.emit_lock_hooks
      rollback
    end
```
