### Title
Bridge `send_token`/`send_token_v2` accept a zero EVM target address, permanently locking bridged funds - (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

### Summary
The Sui bridge’s outbound token entry points accept a 20-byte EVM `target_address` but only verify its length, not that it is non-zero. [1](#0-0)  A caller can therefore bridge tokens to the zero Ethereum address; the Sui side burns the coin and emits a bridge message, and the EVM claim path will deliver assets to `0x0`, locking them forever. [2](#0-1) [3](#0-2)  This is the same missing zero-address validation class as the reported `_stETH` initializer bug.

### Finding Description
In `bridge::bridge::send_token` and `send_token_v2`, the only validation on `target_address` is `target_address.length() == EVM_ADDRESS_LENGTH`. [1](#0-0) [4](#0-3)  There is no assertion that `target_address` is not `0x00..00`. The message builder serializes the address verbatim. [5](#0-4)  On the EVM side, `transferBridgedTokensWithSignatures` decodes `recipientAddress` and dispatches to `BridgeVault` without a non-zero check. [6](#0-5)  `BridgeVault.transferETH` and `transferERC20` also do not reject a zero recipient. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)  Thus a zero address propagates from unprivileged user input through the bridge message to the destination chain.

### Impact Explanation
High. Any bridge user can permanently destroy or lock their own bridged assets by setting `target_address` to 20 zero bytes. [11](#0-10)  For Sui-native bridged coins the treasury burn is irreversible; for the EVM unlock path ETH sent to `0x0` is irrecoverable and ERC20 transfers to `0x0` may be silently accepted by non-standard tokens. [12](#0-11)  This is a public-input permanent fund lock / harmful smart-contract behavior.

### Likelihood Explanation
High. The function is public and unprivileged, and the zero address satisfies the only validation (`target_address.length() == 20`). [1](#0-0)  No production guard rejects it.

### Recommendation
Add a non-zero check in `send_token` and `send_token_v2` rejecting `target_address == x"0000000000000000000000000000000000000000"`, and add `recipientAddress != address(0)` validation in the EVM `transferBridgedTokensWithSignatures` / `BridgeVault` path before any token transfer.

### Proof of Concept
A Move transaction:
```move
let zero_evm = x"0000000000000000000000000000000000000000";
bridge.send_token(chain_ids::eth_sepolia(), zero_evm, coin, ctx);
```
passes all assertions, burns `coin`, and emits a `TokenDepositedEvent` with `target_address` all zeros. [11](#0-10) [3](#0-2)  If later approved and claimed on EVM, `BridgeVault.transferETH` will call `0x0000...0000` with the amount, locking the ETH. [12](#0-11)
