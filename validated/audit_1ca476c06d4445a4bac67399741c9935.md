### Title
Missing delimiter in `getHashSrc` legacy (pre-`NEW_HASH_DATE`) contract hash construction allows hash collisions between different arbiter contract contents - (File: `arbiter_contract.js`)

### Summary
The reported Dinari bug is a malformed EIP-712 type-hash string (missing closing bracket) that produces an incorrect/collidable `OrderRequest` hash. The analogous defect class in `ocore` is unsafe concatenation of variable-length fields without a delimiter when building a hash preimage, which likewise produces colliding/ambiguous hashes for different logical inputs.

### Finding Description
`arbiter_contract.js` computes the contract identity hash via `getHash()` → `getHashSrc()`: [1](#0-0) 

For contracts whose `creation_date` is **not** after `exports.NEW_HASH_DATE` (`'2026-11-01'`, i.e. all contracts created up to and including today, 2026-09-15), the hash source string is built with plain concatenation and **no delimiter**:
```
[contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("")
```
Because `.join("")` inserts no separator between variable-length string fields (`title`, `text`, `payer_name`, `payee_address`... etc.), two contracts with different field boundaries but the same concatenated byte sequence produce an identical SHA-256 hash — e.g. `title="AB", text="CD..."` collides with `title="ABC", text="D..."` when the remaining fields are unchanged. This is the same root-cause class as the reported issue: an improperly constructed hash preimage that fails to uniquely bind to its logical input, undermining the integrity guarantee the hash is supposed to provide. `getHash()` simply hashes this ambiguous source string: [2](#0-1) 

The resulting `contract.hash` is not just a display identifier — it is embedded directly into the oscript definition of the actual escrow shared address that holds real funds, as the key of an `in data feed` condition that gates fund release to the arbiter's ruling: [3](#0-2) [4](#0-3) 

It is also used to authenticate the on-chain "signing" data message that both parties rely on to confirm they agreed to the same contract text: [5](#0-4) 

### Impact Explanation
Because the legacy (currently active, pre-`2026-11-01`) hash path can produce identical `contract.hash` values for contracts with different `title`/`text`/party-name content, a malicious counterparty (a paired device negotiating an arbiter contract) can craft two distinct contract texts that collide under this hash. Since `contract.hash` is what appears as the `CONTRACT_<hash>` / `CONTRACT_DONE_<hash>` data-feed key baked into the escrow shared-address definition and into the `contract_text_hash` field validated in `handleReceivedSigningUnit`, this breaks the binding between the agreed contract terms and the on-chain identifier used to release/settle funds under that identifier. This falls into the "AA/contract fund loss or freezing" and "node disagreement on validity" category: peers, cosigners, and the arbiter can be made to believe they are referencing the same unique agreement when the underlying textual terms actually differ, undermining the integrity of the escrow's release conditions and dispute resolution keyed on that hash.

### Likelihood Explanation
Exploitation requires an unprivileged counterparty (the "peer" in the wallet-to-wallet contract negotiation, i.e., an unprivileged paired device) to choose `title`/`text`/party-name values that create the necessary byte-boundary collision — this is straightforward to engineer since the attacker fully controls the contract's free-text fields on their side of the negotiation. The vulnerable code path is also the *default* one today, since `NEW_HASH_DATE` (`2026-11-01`) has not yet been reached, meaning every arbiter contract created currently uses the delimiter-less `getHashSrc` branch.

### Recommendation
Always use the already-present `exports.DELIMITER` (or another byte sequence guaranteed not to occur in the fields, e.g. length-prefixing or the STRING_JOIN_CHAR scheme used in `object_hash.js`) for the legacy hash branch as well, or simply retire the no-delimiter branch entirely and force all contracts through the delimited hash computation regardless of `creation_date`.

### Proof of Concept
1. Party A (attacker) proposes an arbiter contract with `title = "AB"`, `text = "X"`, fixed `creation_date`, `payer_name`, `arbiter_address`, `payee_name`, `amount`, `asset`.
2. Compute `getHashSrc()` for this contract via `arbiter_contract.js:194-201` (legacy branch, `join("")`).
3. Craft a second contract with `title = "A"`, `text = "BX"` and identical remaining fields; its `getHashSrc()` output is byte-identical to step 1's, so `getHash()` in `arbiter_contract.js:205-207` yields the same SHA-256/base64 hash for both.
4. Use contract #2's colliding hash as the `CONTRACT_<hash>` data-feed key embedded in the shared-address definition (`arbiter_contract.js:475-492`) and as `contract_text_hash` in the signing data message (`arbiter_contract.js:670-676`), while showing the victim contract #1's text — the victim's client cannot detect the substitution because the hash check in `handleReceivedSigningUnit` (`arbiter_contract.js:673-676`) passes for both texts.

```javascript
function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
```
