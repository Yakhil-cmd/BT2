### Title
CCMenu API endpoint fails to enforce the stack scope bound to an `ApiClient` token, allowing cross-stack disclosure of build/deploy status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single stack via `belongs_to :stack, optional: true` / `stack_id`, and every other API controller enforces that scope through `BaseController#stacks`/`#stack`, which filters by `current_api_client.stack_id` before resolving the requested resource. [1](#0-0) [2](#0-1)  `Api::CCMenuController` overrides that `stack` accessor with an unscoped lookup, `Stack.from_param!(params[:stack_id])`, that ignores `current_api_client.stack_id` entirely. [3](#0-2) 

### Finding Description
The binding that should hold is: **the stack a token authorizes == the stack it can touch**, enforced in `BaseController` via
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController` only checks the *permission scope* (`read:stack`) via `require_permission :read, :stack`, which validates the string `"read:stack"` is in `ApiClient#permissions` — it never checks *which* stack the client is bound to. [4](#0-3)  It then redefines `stack` to bypass the `stacks` scoping helper entirely:
```ruby
private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [3](#0-2) 

Because `Stack.from_param!` resolves any stack by its `owner/name/environment` param without any relation to `current_api_client`, an `ApiClient` created with `stack_id` set to stack A (e.g. the record `here_come_the_walrus` used in tests, which has `stack: shipit`, `permissions: [read:stack]`) [5](#0-4)  can be replayed against `GET /api/stacks/:stack_id/ccmenu.xml` with any other stack's `stack_id` param and still succeed, because:
1. `authenticate_api_client` only verifies the signed token itself, not its `stack_id` binding.
2. `require_permission :read, :stack` only checks the permission string is present.
3. `stack` resolves the *requested* stack directly from the URL param, never comparing it against `current_api_client.stack_id`.

This is a direct analog of the reported bug class: a value that must be re-derived/verified against an authoritative index (here, `ApiClient#stack_id`) is instead trusted from unrelated attacker-controlled input (the `stack_id` URL param), breaking the "stack a token authorizes vs. stack it touches" binding described in the report's remediation pattern (verify the index/binding rather than trusting the caller-supplied value).

### Impact Explanation
This is a High-impact issue: unauthenticated (session-less, token-only) read of another stack's state — specifically the latest deploy/build activity, status, and label exposed by the CCMenu XML feed (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) — for any stack in the Shipit instance, using a token that was only meant to be scoped to one stack. [6](#0-5)  This matches the rules' High-impact category "unauthenticated read of stack state ... or task streams".

### Likelihood Explanation
Any legitimate holder of a stack-scoped `ApiClient` token (e.g. an automation/read-only integration granted access to a single stack via the stack-scoped `ApiClient` mechanism used in the fixture `here_come_the_walrus`) can trivially perform this attack by simply changing the `stack_id` route/query parameter. No additional secrets, GitHub credentials, or session are needed beyond the token itself, which is exactly the intended low-privilege credential for this endpoint (`CCMenuController` supports query-string token auth precisely so it can be embedded in third-party CI dashboards). [7](#0-6) 

### Recommendation
- Remove the `stack` override in `Api::CCMenuController` and use the inherited, scope-aware `stacks`/`stack` helpers from `BaseController`, or explicitly re-implement the check: `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`. [8](#0-7) 
- Alternatively/additionally, have `require_permission!`/`check_permissions!` also validate that `current_api_client.stack_id` (when present) equals `stack.id` before rendering.

### Proof of Concept
1. Create/obtain a stack-scoped `ApiClient` bound to Stack A with permission `read:stack` (equivalent to the `here_come_the_walrus` fixture). [5](#0-4) 
2. Compute its `authentication_token` (`id--hmac`). [9](#0-8) 
3. Send `GET /api/stacks/<owner>/<name>/<environment>/ccmenu.xml?token=<token>` where `<owner>/<name>/<environment>` identifies Stack B (a stack the client was never scoped to).
4. Observe `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!` (unscoped) and `#show` renders Stack B's build/deploy status, even though the token is only supposed to authorize Stack A. [10](#0-9)
