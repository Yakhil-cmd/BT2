### Title
Unauthenticated webhook signature bypass allows forged `membership` events to escalate arbitrary GitHub users into `Shipit.github_teams` authorization - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates inbound GitHub webhooks by checking `X-Hub-Signature` against the org-specific `webhook_secret`, but `GitHubApp#verify_webhook_signature` unconditionally returns `true` when `webhook_secret` is blank [1](#0-0) . Since `webhook_secret` is documented and templated as optional (blank by default) [2](#0-1) [3](#0-2) , any organization run without a configured secret accepts unsigned, attacker-forged payloads. This breaks the binding "organization that is claimed to have authenticated the payload" == "organization whose data (team membership) is written," letting an unprivileged attacker forge a `membership` webhook that adds their own GitHub login into any `Team` record — including teams referenced by `Shipit.github_teams`, which gate authorization to the whole application.

### Finding Description
`before_action :check_if_ping, :drop_unhandled_event, :verify_signature` runs `verify_signature`, which resolves the target `GitHubApp` from the attacker-controlled `repository_owner` (taken straight from the JSON body: `params.dig('repository','owner','login') || params.dig('organization','login')`) and calls `verify_webhook_signature(signature, raw_post)` [4](#0-3) .

`verify_webhook_signature` is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

If `webhook_secret` is not configured for that org (the documented default — `webhook_secret: # nil` in every example/secrets template) [5](#0-4) [6](#0-5) , the "verification" step is a no-op: **no cryptographic binding exists between the claimed sender and the payload**. Any unauthenticated actor can `POST /webhooks` with `X-Github-Event: membership` and an arbitrary body.

`MembershipHandler#process` then trusts the body directly:
```ruby
team = find_or_create_team!               # keyed by params.team.id
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member) if params.action == 'added'
``` [7](#0-6) 

`Team#find_or_create_by_handle`/`Team.github_id` is how `Shipit.github_teams` are resolved (`oauth.teams` config → `Team.find_or_create_by_handle(t)`) [8](#0-7) [9](#0-8) , and `User#authorized?` grants app-wide access solely based on membership in one of `Shipit.github_teams` [10](#0-9) . Because `find_or_create_team!` matches purely on `params.team.id` (a value the attacker fully controls in the forged payload) rather than on any server-verified relationship to the real GitHub team, the attacker can supply the exact `id`/`slug`/`name`/`url` of the real authorized team (public/discoverable information for most orgs) and their own `login`, causing Shipit to record them as a team member — without ever authenticating via OAuth or holding real GitHub team membership.

This is the same class of defect as the referenced `safeApprove` finding: a security-relevant state transition (allowance increase / team-membership grant) is gated by a check whose *pass* condition includes a state (`current allowance == 0` / `webhook_secret blank`) that silently disables the intended protection instead of enforcing it, breaking the equality "authenticated organization" == "organization whose privileged records (team membership) get mutated."

### Impact Explanation
A successful forged `membership` event lets an unauthenticated remote attacker add themselves (or anyone) to a `Team` matching one of `Shipit.github_teams`. This directly grants `authorized?` == `true`, bypassing the GitHub-team authorization gate used across `StacksController` and other controllers (`"You must be a member of ... to access this application"`) [11](#0-10) . Combined with the OAuth login flow that trusts `User.find_or_create_from_github`, an attacker who can complete the (unauthenticated) OAuth handshake as any GitHub identity, or who already has a Shipit `User` record, gains authorization to view/trigger deploys, rollbacks and merges — an escalation into `Shipit.github_teams` authorization, matching the High-severity impact class.

### Likelihood Explanation
Likelihood is high wherever an organization is configured without `webhook_secret` (the documented default/optional state across `config/secrets.development.example.yml`, `template.rb`, and `docs/setup.md`). No credentials, tokens, or network position are required — only knowledge of the `/webhooks` URL, the target org's login, and the target team's `id`/`slug`/`name`/`url` (typically discoverable via the public GitHub API for the org). No signature, secret, or session is needed to reach `MembershipHandler`.

### Recommendation
- Do not treat a missing `webhook_secret` as "trust everything." Require a configured secret before processing security-sensitive events (`membership`, `push`, `status`, `check_suite`), or fail closed (`head(422)`) when no secret is configured instead of `return true`.
- In `MembershipHandler`, do not trust attacker-supplied `team.id`/`member.login` in isolation: cross-check against `Shipit.github(organization:).api` (e.g. verify the acting organization actually owns a team with that id/slug via an authenticated GitHub API call) before mutating `Team`/`Membership` records, mirroring how `Team.find_team_on_github` already performs an authoritative GitHub API lookup elsewhere.
- Emit a startup/ops warning (and ideally refuse to boot in production) when `Shipit.github_teams` authorization is configured but any configured organization lacks a `webhook_secret`, since that combination silently disables the membership hook's integrity guarantee.

### Proof of Concept
1. Configure Shipit with an org `acme` in `secrets.github.acme` where `webhook_secret` is left blank (the documented default) and `oauth.teams: ["acme/deployers"]`.
2. Without any authentication, send:
```
POST /webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": { "id": <real acme/deployers github_id>, "name": "deployers", "slug": "deployers", "url": "https://api.github.com/teams/123" },
  "organization": { "login": "acme" },
  "member": { "login": "attacker-github-handle" }
}
```
3. `verify_signature` calls `Shipit.github(organization: "acme")`; `verify_webhook_signature` returns `true` because `webhook_secret` is blank — no signature header is even required [12](#0-11) .
4. `MembershipHandler#process` runs, creating/matching the `Team` by `github_id` and adding `User` `attacker-github-handle` as a member [7](#0-6) .
5. If `attacker-github-handle` subsequently completes GitHub OAuth login on Shipit, `authorized?` returns `true` via membership in `acme/deployers`, granting full app access despite never truly belonging to the GitHub team [10](#0-9) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
