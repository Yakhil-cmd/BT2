### Title
Untrusted swap payload can execute attacker code and steal unrelated caller tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts caller-provided swap XDR and forwards it to the configured router while only explicitly authorizing the exact protocol input-token transfer. [1](#0-0)  The decoded route selects pool addresses from the payload’s arbitrary `assets` registry, and each swap hop invokes the selected venue adapter against that payload-controlled pool address. [2](#0-1) [3](#0-2)  Consequently, an attacker-supplied route can name a malicious pool contract whose code performs an unrelated token transfer from the account owner to the attacker. [4](#0-3) 

### Finding Description
`swap_collateral` is reachable by an unprivileged account owner: it authenticates the caller, verifies ownership or delegation, withdraws collateral, invokes the router route, and deposits the measured output. [5](#0-4)  The controller records input/output balances and authorizes only `amount_in` to the router, but those checks do not constrain other token transfers performed by code reachable through the route. [6](#0-5)  A successful route only has to return a positive measured output; there is no check that the route touched only expected contracts. [7](#0-6) 

The payload-controlled pool need not be a genuine liquidity pool: it only needs to implement the venue call surface and return enough output to satisfy the route. [8](#0-7)  During that venue call, arbitrary contract code can request `token.transfer(victim, attacker, amount)` for an unrelated token held by the caller. [4](#0-3)  Because the malicious transfer becomes a child of the caller’s signed authorization tree, it executes when the caller signs the simulated authorization for the poisoned route. [9](#0-8) 

### Impact Explanation
An attacker can steal unrelated wallet tokens held by the account owner, not merely misprice the routed collateral or produce a poor fill. [10](#0-9)  The test demonstrates that the attacker receives the full unrelated token balance while the protocol still receives the expected collateral output, so all controller balance and final-position checks can pass. [11](#0-10)  This is theft of user funds.

### Likelihood Explanation
The attacker cannot invoke `swap_collateral` for another account without owner or delegate authorization, so exploitation requires the victim to execute and authorize a malicious route. [12](#0-11)  A malicious route provider can nevertheless make the attack look like a successful fair swap because the rogue venue pays the expected output while embedding the extra transfer in the recorded authorization tree. [13](#0-12)  The regression test confirms that simulation records the theft under the caller’s `swap_collateral` authorization and that signing that tree executes it. [14](#0-13) 

### Recommendation
Do not allow route payloads to select arbitrary executable pool contracts under the caller’s root authorization; constrain venue calls to protocol-verified pool addresses or an independently verified pool registry. [3](#0-2)  Until routes are structurally constrained, clients must decode `StrategyPayload`, validate every pool address and venue call, simulate the transaction, and reject any authorization child beyond the expected exact input transfer. [15](#0-14) [16](#0-15) 

### Proof of Concept
1. Deploy a malicious contract that implements the selected venue call and, during that call, executes `token::Client::transfer(victim, attacker, WALLET_BALANCE)` for a token unrelated to the swap. [17](#0-16) 
2. Encode a `StrategyPayload` whose `assets` registry contains that malicious contract as the hop pool and whose route returns at least the declared minimum output. [2](#0-1) [18](#0-17) 
3. Have the victim invoke `swap_collateral(caller, account_id, current, from_amount, new, swap)` with the poisoned route. [19](#0-18) 
4. Simulation records the malicious unrelated-token transfer as a child authorization under the victim’s `swap_collateral` invocation. [9](#0-8) 
5. Signing the recorded authorization allows the transfer: the victim’s unrelated token balance becomes zero, the attacker receives the full amount, and the account still receives the expected swapped collateral. [14](#0-13)
