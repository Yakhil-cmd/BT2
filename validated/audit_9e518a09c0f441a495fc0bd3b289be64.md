### Title
Unauthenticated `hop_submit` RPC leaks per-account authorization status via distinguishable error codes - ([File: substrate/client/hop/src/rpc.rs])

### Summary
The `sc-hop` node service exposes a public JSON-RPC method `hop_submit` that any caller can invoke without proving ownership of the `signer` account's private key. Before verifying the submitted signature, the handler already evaluates the runtime's `can_account_promote` authorization check against the *unauthenticated* `signer` argument, and returns a distinct error (`NotAuthorized`) if that check fails, versus `InvalidSignature` if the check passes but the (attacker-supplied, unverifiable) signature is wrong. This lets any unprivileged caller who knows or guesses a target account id (SS58 address, typically public on-chain) enumerate accounts that are authorized to promote data via `HopRuntimeApi::can_account_promote`, without owning that account's key — an access-control failure analogous to LibreNMS's `graph.php` returning device-existence information to any authenticated-but-unprivileged user.

### Finding Description
`HopRpcServer::do_submit` in [1](#0-0)  performs, in order:
1. Decode `recipients`, `signer`, `signature` (format-only checks).
2. Query the runtime for `max_promotion_size` and reject oversized data.
3. Derive `account_id` directly from the caller-supplied, **unverified** `signer` bytes: [2](#0-1) .
4. Call `HopRuntimeApi::can_account_promote(account_id, data_len)` and return `HopError::NotAuthorized` if it returns `false` — **before** any cryptographic proof that the caller controls `account_id`'s key.
5. Only afterwards verify `multi_sig.verify(&submit_payload[..], &account_id)`, returning `HopError::InvalidSignature` on failure: [3](#0-2) .

Because steps 4 and 5 return different, distinguishable error variants (`NotAuthorized` vs `InvalidSignature`), and the RPC method `hop_submit` is defined without any `with_extensions`/`DenyUnsafe`/`check_if_safe` gate (unlike sensitive Substrate RPC calls such as `state_storage_pairs` or `state_traceBlock`, which explicitly call `check_if_safe(ext)` per [4](#0-3)  and [5](#0-4) ), any network caller can probe arbitrary account ids and learn their authorization/allow-list status maintained by the runtime, with zero possession of the target's signing key. This is comparable to `graph.php` checking only "is authenticated" and not "is this the caller's own device," and thereby leaking device existence to any low-privileged user — here the resource is "is account X on the HOP promotion allow-list" rather than "does device N exist."

The rate-limit ordering, the `MAX_RECIPIENTS`/size checks, and the deliberate `NotRecipient → NotFound` collapsing in `claim`/`ack` (see [6](#0-5)  and [7](#0-6) ) show the authors were aware of and deliberately closed similar existence-oracle issues for claim/ack, but the same discipline was not applied to the authorization check inside `do_submit`.

### Impact Explanation
An attacker with no privileged role and no stolen keys can determine which accounts are authorized (and implicitly, by binary-searching `data_len`, what per-account size tier or quota state a target has) to promote HOP data on-chain, without needing that account's private key. This is a confidentiality/information-disclosure issue (CWE-200) about the runtime's authorization policy state — it does not by itself cause theft, unbacked issuance, or unauthorized dispatch, but it defeats the intended secrecy of the allow-list/authorization mechanism and could be chained with other reconnaissance (e.g., targeting specific collators/accounts for further attacks or DoS given knowledge of who is a "high-value" authorized submitter).

### Likelihood Explanation
High likelihood of exploitability if `hop_submit` is reachable on a "safe" RPC endpoint without additional gating, since the check ordering unconditionally exposes the two distinct error codes to any caller who can reach the JSON-RPC port and supply a syntactically valid (but not necessarily *correct*) signer/signature pair. I could not confirm from available context whether `sc-hop` deployments always expose `hop_submit` on a public-facing endpoint or restrict it to `--rpc-methods=unsafe`/localhost only, since the trait definition (`#[rpc(client, server)] pub trait HopApi<BlockHash>`) shown does not carry a safety annotation, unlike `substrate/client/rpc-api/src/dev/mod.rs`'s `dev_getBlockStats`, which is explicitly documented as unsafe-only. This is a material open question that materially affects real-world exploitability and should be verified against actual node CLI wiring (`HopParams`, `--enable-hop`) before triage.

### Recommendation
Reorder `do_submit` to verify the submitted signature against `account_id` *before* calling `can_account_promote`, or make both checks return an identical, non-distinguishing error (e.g., always `NotAuthorized`/generic `SubmitRejected`) regardless of whether the failure was due to authorization or invalid signature — mirroring the `NotRecipient → NotFound` collapsing pattern already used in `claim`/`ack`. Additionally, confirm and document whether `hop_submit` should require `deny_unsafe`/local-only access, and add it if the intended threat model assumes public exposure is safe only for genuinely-owned accounts.

### Proof of Concept
Not independently executed against a running node; this is a static-code-path finding based on [8](#0-7) . A minimal reproduction would be: construct a `hop_submit` RPC call with `signer = <target_account_pubkey_bytes>`, `signature = <64 arbitrary bytes that decode as MultiSignature>`, small `data`; observe `NotAuthorized` for non-allow-listed targets versus `InvalidSignature` for allow-listed targets, without ever needing the target's private key. I was unable to run this against a live node/test harness in this session; the existing unit tests in [9](#0-8)  (`submit_unauthorized_account_returns_error`) already demonstrate the `NotAuthorized` branch is reachable and distinct from the `InvalidSignature` branch, which supports (but does not fully substitute for) the described oracle.

```rust
	fn do_submit(
		&self,
		data: Bytes,
		recipients: Vec<Bytes>,
		signature: Bytes,
		signer: Bytes,
		submit_timestamp: u64,
	) -> Result<SubmitResult, HopError> {
		let recipient_keys: RecipientVec = recipients
			.into_iter()
			.map(|r| {
				MultiSigner::decode(&mut &r.0[..])
					.map(|signer| Recipient { signer, claimed: false })
					.map_err(|_| HopError::InvalidRecipientKey)
			})
			.collect::<Result<Vec<_>, _>>()?
			.try_into()
			.map_err(|v: Vec<Recipient>| HopError::TooManyRecipients {
				provided: v.len(),
				limit: MAX_RECIPIENTS as usize,
			})?;

		let signer =
			MultiSigner::decode(&mut &signer.0[..]).map_err(|_| HopError::InvalidSigner)?;
		let multi_sig = MultiSignature::decode(&mut &signature.0[..])
			.map_err(|_| HopError::InvalidSignature)?;

		let chain_info = self.client.info();
		let best_hash = chain_info.best_hash;

		let data_len = data.0.len();

		// Reject oversized payloads before the per-account authorization lookup so
		// a flood of too-big submits cannot force runtime state reads. The cap is
		// the runtime-declared `max_promotion_size`; the runtime is authoritative.
		let runtime_max = runtime_api::max_promotion_size::<Block, _>(&*self.client, best_hash)
			.map_err(HopError::from)?;
		if data_len > runtime_max as usize {
			return Err(HopError::DataTooLarge(data_len, runtime_max).into());
		}

		// Check authorization before verifying the signature: a flood of unauthorized
		// requests must not force a signature verification per submit.
		// `can_account_promote` returns false for any reason the runtime rejects:
		// unauthorized account or exhausted per-account quota.
		let account_id: AccountId32 = signer.clone().into_account();
		let authorized = runtime_api::can_account_promote::<Block, _>(
			&*self.client,
			best_hash,
			account_id.clone(),
			data_len as u32,
		)
		.map_err(HopError::from)?;
		if !authorized {
			return Err(HopError::NotAuthorized);
		}

		// Domain-separated payload so a submit signature cannot be replayed as claim/ack,
		// and bound to `submit_timestamp` so an old signature can't be replayed long
		// after the fact (the runtime enforces a tolerance window on the timestamp).
		let hash = H256(blake2_256(&data.0));
		let submit_payload = submit_signing_payload(&hash, submit_timestamp);
		if !multi_sig.verify(&submit_payload[..], &account_id) {
			return Err(HopError::InvalidSignature);
		}

		let sender_id: [u8; 32] = account_id.into();
		self.pool
			.insert(data.0, recipient_keys, sender_id, signer, multi_sig, submit_timestamp)?;
		Ok(SubmitResult { pool_status: self.pool.status() })
	}
```

```rust
	pub fn ack(&self, hash: &HopHash, signature: &[u8]) -> Result<(), HopError> {
		// Phase 1: idempotent fast-path read; no lock acquired.
		{
			let meta = self.fetch_meta(hash)?.ok_or(HopError::NotFound)?;
			let idx = Self::find_recipient_idx(&meta, hash, signature, HOP_ACK_CONTEXT)
				.map_err(|_| HopError::NotFound)?;
			if meta.recipients[idx].claimed {
				return Ok(());
			}
		}

		// Phase 2: RMW under rmw_lock; re-run the lookup as the meta may have changed.
		let _guard = self.rmw_lock.lock();
		let mut meta = self.fetch_meta(hash)?.ok_or(HopError::NotFound)?;
		let idx = Self::find_recipient_idx(&meta, hash, signature, HOP_ACK_CONTEXT)
			.map_err(|_| HopError::NotFound)?;
```
