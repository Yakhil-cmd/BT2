### Title
Capped assets with `issued_by_definer_only=false` can be independently re-minted by every issuing address, inflating supply past the declared cap - (File: validation.js)

### Summary
`FootiumAcademy.sol` inconsistency in the report (one minting path keys uniqueness off a global `tokenId`, the other off a per-`playerId` merkle-tracked flag) has a structural analog in ocore's asset-issuance validation: the double-spend/uniqueness check used to prevent re-issuing a capped asset's `issue` input is scoped **per authoring address** whenever `issued_by_definer_only` is `false`, instead of being scoped globally per asset. This lets multiple distinct addresses each successfully post an `issue` input for the same capped asset, each for the full `cap` amount, none of which conflict with each other.

### Finding Description
`validateAssetDefinition()` in [1](#0-0)  never requires `issued_by_definer_only === true` when `cap` is set for a normal (non-AA) asset definition — that constraint is only enforced inside the AA-specific branch, and even there it only forbids `is_private`/`fixed_denominations` combinations, not the `cap` + `issued_by_definer_only=false` combination.

During issue-input validation, `serial_number` is forced to `1` for any capped asset regardless of `issued_by_definer_only`: [2](#0-1) . The double-spend predicate that is supposed to prevent re-issuing the same capped supply only adds an `asset`/`serial_number` filter unconditionally, but adds the address filter only when the asset is **not** definer-only-issued: [3](#0-2) . For a capped, non-fixed-denomination asset, the amount is forced to equal the full `cap`: [4](#0-3) .

Combining these: for an asset defined with `cap = X`, `issued_by_definer_only = false`, `fixed_denominations = false`, the effective double-spend key becomes `(asset, denomination, serial_number=1, address)`. Any address can post an `issue` input of the full `cap` amount once without conflicting with an issuance from any other address, because the uniqueness check is address-scoped, not asset-scoped. This is reflected consistently in the wallet composer's issuance helper (which mirrors the same address-scoped logic) at [5](#0-4)  and the AA composer's issuance helper at [6](#0-5) , and is backed by the DB uniqueness index that includes `address` in the key: [7](#0-6) .

The only code path that treats a capped asset atomically as "issue once, ever" is the address-independent check `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` used opportunistically by composer helpers to decide whether to *attempt* an issue at all, but this is a client-side/composer optimization, not an enforced validation rule — the actual consensus validation in `validation.js` only prevents the *same author address* from re-issuing, not a different address.

### Impact Explanation
An attacker can define a "capped" asset with `issued_by_definer_only=false` (a config the protocol permits without warning or restriction) and then, using multiple different addresses (e.g. many funded accounts, or addresses controlled by a Sybil), independently post `issue` units each carrying the full `cap` amount. Every node in the network will validate and accept each of these issuances as legitimate distinct units because the double-spend/uniqueness check is address-scoped. The result is uncontrolled inflation of an asset's supply that was represented as capped, undermining any economic assumptions (e.g., wallets, exchanges, or AAs) that rely on `cap` being an enforced hard limit on total issuance.

### Likelihood Explanation
This does not require any special privilege — any user can define such an asset with a single unit, and any set of addresses can each post a valid `issue` unit for it. No malicious peer/node/hub behavior is needed; it's purely a consequence of how ordinary, honestly-relayed units are validated by `validation.js`. The only "cost" to the attacker is posting additional units from different addresses, which is trivial.

### Recommendation
When `payload.cap` is set (and the asset is not `fixed_denominations`), require `issued_by_definer_only === true` in `validateAssetDefinition()` (mirroring the AA-only restriction, but without the `is_private`/`fixed_denominations` carve-out), so a "cap" can only ever be issued once, by one address. Alternatively, keep the asset-scoped-only doublespend key (drop `address` from `doubleSpendWhere`) whenever `objAsset.cap` is set, regardless of `issued_by_definer_only`, ensuring the uniqueness constraint that guarantees "one issue per capped asset" actually holds network-wide rather than per issuing address.

### Proof of Concept
1. Author A defines asset `ASSET` with `cap = 1000000`, `issued_by_definer_only = false`, `fixed_denominations = false`, `is_private = false`.
2. Address B posts a unit with message `payment` for `ASSET` containing an `issue` input `{type: "issue", amount: 1000000, serial_number: 1, address: B}`. This validates and is accepted (per `validation.js` lines 2311-2384).
3. Address C (unrelated address) posts another unit with an `issue` input `{type: "issue", amount: 1000000, serial_number: 1, address: C}` for the same `ASSET`. Because the double-spend `doubleSpendWhere` includes `address=?` (since `issued_by_definer_only` is false), this does not conflict with B's issuance and is also accepted.
4. Repeat with additional addresses D, E, ... Each issuance succeeds independently, so the total circulating supply of `ASSET` becomes `1000000 * N` for `N` distinct issuing addresses — far beyond the declared `cap` of `1000000`.
