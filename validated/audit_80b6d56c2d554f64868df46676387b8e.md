## Analysis Result [1](#0-0) 

CVE-2015-8027 describes a Node.js HTTP parser bug where malformed/unexpected pipelined input triggers an `uncaughtException` that crashes the whole process (DoS). `ocore` has a directly analogous pattern: a remotely reachable code path that deliberately throws inside an asynchronous `setTimeout` callback when processing an incoming device message, which cannot be caught by the surrounding `try/catch`, and which is wired to a global `uncaughtException` handler that re-throws and crashes the entire node process.

### Title
Remote unauthenticated device message crashes the recipient's node via uncaught async exception in `decryptPackage` - (File: device.js)

### Summary
Any device that can send a `hub/message` (or direct `hub/deliver`) addressed to a target device can force that target's whole `ocore` process to crash by including an `encrypted_package.dh.recipient_ephemeral_pubkey` value that does not match the recipient's current temp/previous-temp/permanent device key. This causes `decryptPackage()` to schedule a `throw Error(...)` inside a `setTimeout`, which escapes all surrounding `try/catch` blocks and reaches the module-level `process.on('uncaughtException', ...)` handler in `network.js`, which itself re-throws to intentionally crash the process.

### Finding Description
The message-handling flow is:
1. `handleJustsaying(ws, 'hub/message', body)` in device.js verifies only that the message has the required fields and a valid self-signature from the *sender's own* `pubkey`/`signature` (fields fully attacker-controlled), then calls `decryptPackage(objDeviceMessage.encrypted_package)` inside a `try/catch`. [2](#0-1) 
2. Inside `decryptPackage`, if `recipient_ephemeral_pubkey` doesn't match `objMyTempDeviceKey.pub_b64`, `objMyPrevTempDeviceKey.pub_b64`, or `objMyPermanentDeviceKey.pub_b64`, the function logs "message encrypted to unknown key" and schedules:
```js
setTimeout(function(){
    throw Error("message encrypted to unknown key, device "+my_device_address+...);
}, 100);
return null;
``` [3](#0-2) 
Because the `throw` happens inside a `setTimeout` callback, it executes on a fresh tick of the event loop, completely outside the `try { var json = decryptPackage(...) } catch(e) {...}` block at the call site — the exception cannot be caught there.
3. This unhandled exception is caught only by the module-level handler:
```js
process.on('uncaughtException', (err) => {
    console.log('Uncaught exception:', err);
    ...
    throw err; // crash the process to avoid ending up in an inconsistent state
});
``` [4](#0-3) 
which explicitly re-throws to terminate the whole Node.js process.

Any correctly self-signed device message (the sender signs with their own freshly generated keypair, which trivially passes signature verification) that is addressed to the victim's device address, with a garbage/unknown `recipient_ephemeral_pubkey` in the DH fields, reaches this code before any correspondent/whitelist check is even performed.

### Impact Explanation
This is a concrete, unauthenticated remote denial-of-service: a single attacker-crafted message crashes the entire `ocore` node process (full node, hub, or wallet), taking down all of its network services simultaneously — the same "uncaughtException and service outage" impact class as CVE-2015-8027. For a full/hub node this halts unit relay/validation for all connected peers until manually restarted; for a wallet it aborts local operation. It requires no prior pairing and only knowledge of the target device address (which is routinely shared for payments/chat).

### Likelihood Explanation
Likelihood is high: the attacker only needs to know the victim's device address (a normal, often-shared public identifier), generate an ad-hoc keypair to self-sign the message, and set an arbitrary base64 string as `recipient_ephemeral_pubkey`. No cryptographic break, no privileged position, and no correspondence relationship are required, and the crash is deterministic ~100ms after delivery.

### Recommendation
Wrap the `setTimeout` throw in `decryptPackage` (or the entire `hub/message`/`hub/deliver` processing pipeline) so that unknown-key errors are reported via the existing `callbacks.ifError` / `sendError` mechanism instead of an uncatchable asynchronous `throw`; alternatively, emit a `nonfatal_error` event (as already partially implemented but commented out at device.js line 434) rather than crashing the process, reserving process termination for genuinely unrecoverable states.

### Proof of Concept
1. Obtain victim's device address (public identifier).
2. Generate an attacker keypair; build `objDeviceMessage` with `to = victim_device_address`, `pubkey`/`signature` self-signed correctly, and `encrypted_package` containing syntactically valid strings for `iv`, `authtag`, `encrypted_message`, `dh.sender_ephemeral_pubkey`, and `dh.recipient_ephemeral_pubkey` set to a random base64 string not matching any of the victim's known keys.
3. Send this via `hub/message` justsaying (through the hub) or directly via `hub/deliver` request to the victim.
4. Victim's `decryptPackage` hits the "unknown key" branch, schedules the `setTimeout` throw, and ~100ms later the victim's process crashes via the `uncaughtException` handler's `throw err`.
