### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits by bare SHA with no repository scoping, then writes a GitHub status record onto every matching `Commit` regardless of which repository the webhook actually authenticated for. An attacker who controls a repository that shares a commit SHA with a victim's stack (e.g. via a shared history, cherry-pick, or a crafted commit with identical content) can send a signed-for-their-own-repo `status` webhook and have it flip `blocked?`/`deployable?` state on the victim's stack.

### Finding Description
The invariant that should hold is: `status.repository.full_name == commit.stack.repository.full_name` for every `Commit` record mutated by a `status` webhook. This is exactly what `Handler#stacks` enforces for other handlers — it scopes lookups through `Repository.from_github_repo_name(repository_name)&.stacks`, tying webhook payload repository to the correct stack [1](#0-0) .

`StatusHandler#process`, however, bypasses this helper entirely:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This queries `Commit` globally by `sha`, with no `stack_id`/`repository` filter, unlike every other handler in the directory which iterates `stacks` scoped to the payload's repository (`pull_request/*_handler.rb`, `check_suite_handler.rb`, `push_handler.rb`, `membership_handler.rb` all reference `stacks`).

`Commit#create_status_from_github!` calls `add_status`, which replicates the GitHub status into `statuses` and recomputes `status`, then evaluates `deployable?`/`blocked?`/`schedule_merges` based on the newly written status [3](#0-2) [4](#0-3) . `blocked?` walks `stack.commits.reachable...any?(&:blocking?)`, and `deployable?` gates on `success? && !blocked?` [5](#0-4) . If the victim stack has `blocking_statuses` configured for context `release/gate`, an attacker-controlled `failure` status for that context on a shared SHA sets `blocking?` true for that commit, which can flip `blocked?` for later commits in the victim stack and stop `deployable?`/continuous delivery, or conversely a forced `success` can clear it.

`verify_signature` in `WebhooksController` only checks that the *sender's own* GitHub organization's webhook secret matches the payload — it authenticates that the payload genuinely came from GitHub for the attacker's own repository/org, not that the `sha` referenced belongs to that repository [6](#0-5) . Nothing downstream re-checks that the `Commit` rows returned by `Commit.where(sha: params.sha)` belong to the repository that signed the request. `ExplicitParameters` in `StatusHandler.params` only validates shape/types of `sha`, `state`, `context`, etc.; it performs no repository/ownership check [7](#0-6) .

Exploit flow: attacker owns/controls repository `attacker/repo` registered as a Shipit repository (or any repository whose webhook secret they can trigger legitimately, i.e., their own GitHub repo with the Shipit GitHub App/webhook installed). They craft or discover a commit whose SHA collides with a commit already ingested into a victim stack (trivial if the victim stack tracks a public/forked repo sharing history — same SHA across fork and upstream is normal in git). They push a `status` event context `release/gate`, `state: failure` for that SHA from their own repo. The signature check passes (it's a legitimately signed webhook for `attacker/repo`). `StatusHandler#process` then finds the `Commit` row(s) with that SHA irrespective of `stack_id`, including the victim's, and writes the forged status onto the victim's commit.

### Impact Explanation
This is a payload from one repository mutating another repository's `Commit`/`Status` records and downstream deploy-gating state (`blocked?`, `deployable?`, `schedule_merges`), matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attacker can force a victim's release pipeline to block (denial of legitimate deploys) or, if it clears a previously-blocking status, allow a deploy to proceed that shouldn't have — cross-tenant state manipulation with no privileges on the victim's repository or Shipit instance. It's repeatable against any victim stack whose commits share a SHA with a repository the attacker controls or can trigger.

### Likelihood Explanation
Preconditions: attacker needs a repository registered with Shipit's GitHub App/webhook (any repo they own with a signed webhook secret), a victim stack with `blocking_statuses` configured for some context, and a shared commit SHA between attacker's triggerable repo and the victim's ingested commit history — achievable via forks, shared upstream history, or cherry-picked/rebased commits. Attacker cost is a single signed webhook POST from their own repo; no Shipit session, API token, or GitHub org membership on the victim's side is required. This is directly supported by the unscoped query in `status_handler.rb` line 21.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the webhook's own repository, e.g. use the `stacks` helper (join through `Stack`/`Repository` matching `repository_name`) and filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring how other handlers use `stacks`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` — not present in provided index, to be added):
1. Create `repository_a` (`attacker/repo`) and `repository_b` (`victim/repo`) as separate `Shipit::Repository` records with distinct `stacks` (`stack_a`, `stack_b`).
2. Configure `stack_b`'s deploy spec / `blocking_statuses` to include `release/gate`.
3. Create a `Commit` with the same `sha` (`"deadbeef...".freeze`) under both `stack_a` and `stack_b`.
4. Assert before: `commit_b.reload.blocked?` == `false` (equality binding: `commit_b.stack.repository.full_name` ("victim/repo") != payload `repository.full_name` ("attacker/repo")).
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => sha, 'state' => 'failure', 'context' => 'release/gate', 'repository' => { 'full_name' => 'attacker/repo' })`.
6. Assert after: `commit_b.reload.blocked?` == `true` (or `deployable?` flips), proving `attacker/repo`'s webhook mutated `victim/repo`'s commit state — violating the invariant that a status only affects the repository that authenticated it.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

      ].join(' '))
