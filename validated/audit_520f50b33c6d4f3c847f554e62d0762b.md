Confirmed. The vulnerability is real and matches the described exploit path.

### Title
Cross-organization webhook forgery via `organization` fallback lets one org's secret authorize state mutation on another org's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (`config/secrets.yml` keyed by GitHub org, e.g. `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#repository_owner` selects which org's webhook secret verifies the request, while `LabeledHandler` independently resolves the target repository/stack from `params.repository.full_name`. An attacker who controls (or targets) an org with no/known `webhook_secret` can forge a request that authenticates as that org but mutates a completely different org's review stack.

### Finding Description
The broken binding: the code assumes `repository_owner used to select GitHubApp/secret == organization owning repository.full_name used by the handler`, but these are read from independent, attacker-controlled JSON paths.

- `repository_owner` is computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0)  and used to pick the `GitHubApp`/secret via `Shipit.github(organization: repository_owner)` in `verify_signature` [2](#0-1) .
- `Shipit.github` looks up per-organization config only when a multi-org schema is configured (`github_app_config(organization)`); otherwise it uses the single global config regardless of the `organization:` argument [3](#0-2) .
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally if that org's `webhook_secret` is unset — a state explicitly presented as valid/optional in shipped config templates (`webhook_secret: # nil`) [4](#0-3) [5](#0-4) .
- `LabeledHandler` never consults `repository.owner.login` or `organization.login`; it resolves the target repository purely from `params.repository.full_name` [6](#0-5) , then archives/unarchives the corresponding review stack based on attacker-controlled PR labels [7](#0-6) .

Exploit request: POST `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` needed (or computed with a known/empty secret for org `attacker-org`), body:
```json
{
  "action": "labeled",
  "organization": {"login": "attacker-org"},
  "repository": {"full_name": "victim-org/victim-repo"},
  "pull_request": {"state": "open", "labels": [{"name": "<provisioning label>"}], ...}
}
```
`repository.owner` is omitted, so `repository_owner` falls back to `organization.login = "attacker-org"`, an org configured in the same multi-tenant Shipit instance with no/weak `webhook_secret`. Signature check passes trivially for org `attacker-org`. The handler then reads `repository.full_name = "victim-org/victim-repo"` and calls `stack.archive!`/`stack.unarchive!` on `victim-org`'s review stack — a repository never covered by the credential that authenticated the request.

No existing guard closes this gap: `drop_unhandled_event` only checks the event type; the `ExplicitParameters` schema for `LabeledHandler` requires `repository.full_name` but not `repository.owner`, so the attacker can supply `repository.full_name` for any org while keeping `organization.login`/`repository.owner.login` pointed at a different, weakly-secured org; there is no cross-check between the two.

### Impact Explanation
Impact: an unarchive/archive of a victim organization's review stack triggered by a payload authenticated under a different organization's (weaker) secret — a payload for one repository mutating another's stack, matching the Critical category "a payload for one repository mutating another's stack." Combined with `blocking_statuses`, forcing `unarchive!`/`archive!` toggles provisioning and can indirectly influence `blocked?`/deploy gating for the victim stack. This is repeatable against any repository in the same Shipit instance whose `full_name` the attacker knows, as many times as desired.

### Likelihood Explanation
Requires the Shipit instance to use the multi-organization secrets schema (`github: {org1: {...}, org2: {...}}` as documented in `docs/setup.md` "Using Multiple Github Applications") and at least one configured organization to have `webhook_secret` unset (explicitly supported by example configs) or a secret the attacker otherwise knows. Given that, the attack costs a single unauthenticated HTTP POST with no GitHub interaction required, fully repeatable, and requires no privileges of any kind on the victim organization.

### Recommendation
Bind signature verification to the same field the handler uses for repository resolution: derive `repository_owner` strictly from `params.dig('repository','owner','login')` and reject (422) when the `pull_request`/`labeled` event payload lacks it, rather than falling back to `organization.login`. Additionally, after selecting the `GitHubApp` used for verification, assert that the org in `repository.full_name` matches the organization whose secret verified the request before allowing any handler to mutate stack state.

### Proof of Concept
Minitest plan (`test/controllers/shipit/webhooks_controller_test.rb` or `test/models/shipit/webhooks/handlers/pull_request/labeled_handler_test.rb`):
1. Configure `Shipit.stubs(:secrets)` with a multi-org config mirroring `test/dummy/config/secrets_double_github_app.yml`, where `OrgOne.webhook_secret` is `nil` and `OrgTwo.webhook_secret` is set.
2. Create `repository = shipit_repositories(:shipit)` belonging to `OrgTwo/shipit`, with `provisioning_behavior` and a review stack under review-stacks enabled and `blocking_statuses` configured.
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature`, and JSON body: `{"action": "labeled", "organization": {"login": "OrgOne"}, "repository": {"full_name": "OrgTwo/shipit"}, "pull_request": {..., "labels": [{"name": provisioning_label}]}}`.
4. Assert equality-before: `stack.archived?` at baseline state.
5. Assert response is `200 OK` (not `422`).
6. Assert equality-after: `stack.reload.archived?` (or `not_archived?`) flipped — i.e., `OrgTwo`'s stack was mutated by a request that verified against `OrgOne`'s (absent) secret, proving the two "equality" sides (`repository_owner used for auth` vs `organization owning the mutated repository`) diverge.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

    end
```
