### Title
Missing reentrancy guard on `stake`/`stake-update`/`update-bond-registration` allows double-counting of staker reward-cycle commitments via a malicious signer-manager trait callback - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`pox-5.clar` accepts a caller-supplied `<signer-manager-trait>` implementation and calls into it (`signer-manager-validate-stake`) from `stake`, `stake-update`, and `update-bond-registration` before the staker's map state (`staker-info` / `protocol-bond-memberships`) is written. The contract's own authors recognized that trait dispatch into an attacker-controlled contract is a reentrancy vector — `register-signer` explicitly guards against it with `(try! (validate-no-reentrancy))` — but the same guard is absent from `stake`, `stake-update`, and `update-bond-registration`, even though these functions make the identical external call and then mutate shared reward-cycle-total state.

### Finding Description
`register-signer` contains an explicit reentrancy guard immediately before doing any trait-implementation-dependent logic: [1](#0-0) 

By contrast, `stake` calls the same kind of external, attacker-suppliable trait method (`signer-manager-validate-stake`) with no reentrancy guard at all, prior to any of its state-mutating map writes: [2](#0-1) 

`stake-update` has the identical structure — external trait call first, `staker-info`/reward-cycle map mutation afterward — again with no guard: [3](#0-2) 

`update-bond-registration` follows the same pattern (`signer-manager-validate-stake` then `remove-staker-from-cycles` / `add-staker-to-signer-cycles` / `map-set`): [4](#0-3) 

This is the direct structural analog of the reported SQL-injection bug: one code path (`register-signer`) was "sanitized" against the dangerous input source (external trait re-entry), while sibling code paths that reach the exact same untrusted input source (`signer-manager` trait dispatch) were not — an inconsistent security pattern introduced by omission rather than by a deliberate design decision, exactly like the `prepare()` call being applied to one `UNION` branch and forgotten on the other.

The equality broken is: `reward-cycle-total-stacked.total-ustx` (and per-signer reward-cycle entries) must equal the sum of STX amounts actually and singularly locked by stakers who successfully pass the `is-none (get-staker-info tx-sender)` gate exactly once. Because `signer-manager-validate-stake` is invoked on an attacker-controlled contract *before* `staker-info` is written, a malicious `signer-manager` implementation can call back into `stake` (or `stake-update`) for the same `tx-sender` while the outer call's `staker-info` write is still pending. The inner call still observes `(is-none (get-staker-info tx-sender))` as true and passes the "not already staked" check, so `add-staker-to-signer-cycles` runs a second time and increments the shared reward-cycle totals a second time for one underlying stake amount, while `staker-info` map (last-write-wins) only ever records a single entry. This produces reward-cycle accounting that is inflated relative to the STX actually and durably locked for that staker.

### Impact Explanation
This double-counts a staker's committed amount in the reward-cycle totals used to compute reward-slot allocation/signing weight, without the underlying locked STX being doubled — i.e., "signing weight or reward slots exceeding locked value" / "double-counting a commitment," which the rules classify as Critical/High impact. It does not require the bond/pause admin, a miner, or another user's key — only a self-deployed contract implementing `signer-manager-trait` and calling `stake`/`stake-update` normally as `tx-sender`.

### Likelihood Explanation
Exploitation requires the attacker to author and deploy a `signer-manager-trait`-implementing contract (unprivileged, permissionless), and have that contract's `validate-stake` implementation call back into `pox-5`'s `stake`/`stake-update` before returning. This is a standard reentrancy technique available to any Stacks user, and the vulnerability is directly reachable through the public entry points with no bond/pause admin or other privileged role.

### Recommendation
Add the same `(try! (validate-no-reentrancy))` guard used in `register-signer` to the top of `stake`, `stake-update`, and `update-bond-registration`, before any call into a caller-supplied `signer-manager` trait implementation, so that a nested call back into these functions during trait dispatch is rejected.

### Proof of Concept
1. Deploy a contract `evil-signer-manager` implementing `signer-manager-trait`, whose `validate-stake` method, on first invocation, calls back into `pox-5.stake` (or `stake-update`) with the same `tx-sender`/parameters before returning its own result.
2. Call `pox-5.stake` supplying `evil-signer-manager` as `signer-manager`.
3. During the outer call's `(try! (signer-manager-validate-stake ...))` at [5](#0-4) , the reentrant inner call executes: `staker-info` for `tx-sender` is still unset from the outer call's perspective, so `(asserts! (is-none (get-staker-info tx-sender)) ERR_ALREADY_STAKED)` passes again, and `add-staker-to-signer-cycles` runs, crediting the reward-cycle totals with `amount-ustx` a second time.
4. The outer call then completes and also runs `add-staker-to-signer-cycles` and `map-set staker-info` (overwriting to a single entry), leaving `reward-cycle-total-stacked` inflated by one extra `amount-ustx` relative to the single amount actually reflected/locked for the staker.

(define-public (register-signer

        ;; ensure no reentrancy through signer-manager trait calls
