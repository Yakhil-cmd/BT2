Webhook signature is verified against `repository.owner.login`, but the handled repository is resolved from `repository.full_name` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature with using `repository.owner.login` (or `organization.login`) pulled from the *unverified* JSON body. Once the signature check passes, the raw, still-unverified `params` hash is handed to the event handlers, which instead resolve the target `Repository`/`Stack` using `repository.full_name` (`"owner/name"`). Because these two fields are never cross-checked, an attacker who legitimately controls one configured GitHub organization in a multi-org Shipit deployment can sign a forged payload with their own organization's secret while spoofing `repository.full_name` to point at a completely different organization's stack.

### Finding Description
In a multi-org Shipit setup (`config/secrets.yml` keyed by organization, as documented in `docs/setup.md` and exercised by `test/dummy/config/secrets_double_github_app.yml`), each organization has an independent `webhook_secret`.

`verify_signature` computes the signing organization purely from payload content: [1](#0-0) [2](#0-1) 

That resolves to `Shipit.github(organization: repository_owner)`, whose config lookup is keyed only by that organization name: [3](#0-2) [4](#0-3) 

After the HMAC check succeeds, the controller dispatches the same raw, attacker-controlled `params` to every registered handler: [5](#0-4) 

But the handlers (base `Handler`, `PushHandler`, PR handlers) never look at `repository.owner.login` again — they resolve the acted-upon repository purely from `repository.full_name`: [6](#0-5) [7](#0-6) 

This is the same bug class as the report's `addInterest()` issue: a value that should be re-derived from a trusted/canonical source (here, the field the signature was actually computed against) is instead read from an independent, unchecked field, breaking the intended binding `signing_organization == acted_upon_repository_owner`.

### Impact Explanation
An attacker who is a legitimate admin of Organization B (one org among several configured in `Shipit.github`) knows Organization B's `webhook_secret` (they configured it when wiring up their GitHub App/webhook). They can POST directly to Shipit's `/github/webhooks` endpoint with:
- `X-Hub-Signature` computed with Org B's secret,
- `repository.owner.login = "OrgB"` (so `verify_signature` picks Org B's secret and passes),
- `repository.full_name = "OrgA/critical-repo"` (an unrelated, victim organization's stack).

Because handlers key off `full_name` only, this forged, "verified" webhook is processed as if it legitimately came from GitHub for Org A's repository — e.g. `PushHandler` will call `stack.sync_github(expected_head_sha: ...)` for Org A's stack using an attacker-supplied `after` SHA, and the `status`/`check_suite` handlers can inject fabricated CI state for Org A's commits. Combined with `continuous_deployment`, spoofed successful CI status can trigger an unauthorized deploy via `Stack#trigger_continuous_delivery`, satisfying the "unauthorized deploy" high-impact criterion.

### Likelihood Explanation
Likelihood is limited to deployments using the multi-organization `github:` config (explicitly documented and tested via `secrets_double_github_app.yml`), and requires the attacker to be a legitimate stakeholder of at least one configured organization — not an arbitrary unprivileged internet attacker with zero standing in the system. It requires no compromise of Org A's credentials, secrets, or GitHub App, only knowledge of Org B's own (self-configured) webhook secret, which they possess by design.

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after signature verification, validate that the payload's `repository.owner.login` (the field the signature was verified against) matches the owner embedded in `repository.full_name` before dispatching to handlers, e.g.:

```ruby
def create
  params = JSON.parse(request.raw_post)
  owner_from_full_name = params.dig('repository', 'full_name')&.split('/')&.first
  if owner_from_full_name && repository_owner && owner_from_full_name.casecmp(repository_owner) != 0
    return head(:unprocessable_entity)
  end
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
Alternatively, have handlers resolve the repository via `Repository.where(owner: repository_owner)` intersected with `full_name`, ensuring the same field used for signature-org selection is authoritative for the acted-upon resource.

### Proof of Concept
Given Shipit configured for two orgs, `OrgA` and `OrgB`, with distinct `webhook_secret`s (per `test/dummy/config/secrets_double_github_app.yml` pattern) and Org A owning stack `OrgA/critical-repo`:

1. Attacker (an admin of OrgB, knows OrgB's webhook secret) builds a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/critical-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(OrgB_webhook_secret, body)>` and POSTs to `/github/webhooks` with `X-Github-Event: push`.
3. `verify_signature` calls `Shipit.github(organization: "OrgB")` and successfully verifies the signature against OrgB's secret.
4. `PushHandler.call(params)` resolves the stack via `Repository.from_github_repo_name("OrgA/critical-repo")` (from `full_name`, per `Handler#repository_name`) and invokes `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on Org A's stack — despite the request never having been signed by anything related to Org A.
