### Title
Wrong-host request routing via unconditional trust of github.com in `remoteResolver.Resolver` - ([File: pkg/cmd/factory/remote_resolver.go])

### Summary
`remoteResolver.Resolver` always adds `ghinstance.Default()` (`github.com`) to the set of "trusted" hosts used to filter git remotes, regardless of whether the victim is authenticated to github.com. When a repository/submodule the victim opens contains only a `github.com` remote (e.g. attacker-controlled dependency/submodule) and the victim is authenticated only to an enterprise host, the secondary "filter by default host" step does not remove that remote (because it only excludes non-default hosts *when a same-host match already exists*), so gh silently resolves `BaseRepo` to the attacker's `github.com` repo and issues requests there using whatever `ActiveToken("github.com")` returns, which may be `GH_TOKEN`/`GITHUB_TOKEN` from the environment rather than a token the user intended to send to that host.

### Finding Description
`remoteResolver.Resolver()` builds the set of hosts remotes are matched against as: [1](#0-0) 
`hostsSet` always contains `ghinstance.Default()` ("github.com") in addition to `authedHosts` and `defaultHost`, even when the victim has never authenticated to github.com. `FilterByHosts(hosts)` is then applied unconditionally, admitting any `github.com` remote: [2](#0-1) 

A secondary filter narrows to `defaultHost` only, but crucially **falls back to the unfiltered set when no remote matches the default host**: [3](#0-2) 

Concretely: if the victim is logged in only to `ghe.io`, `DefaultHost()` returns `("ghe.io", "hosts")` (not `"default"`), so `src != "default"`. If the specific repository (e.g. an attacker-supplied submodule/vendor directory) has **no** `ghe.io` remote — only a `github.com` remote picked up by the first, always-permissive filter — then `filteredRemotes` (filtered to `ghe.io`) is empty, `isHostEnv(src)` is false, and `len(filteredRemotes) > 0` is false, so the `if` body is skipped and `rr.cachedRemotes` **remains the github.com-containing result** from the first filter. No error is raised (the `len(rr.cachedRemotes) == 0` guard doesn't trigger), and the github.com remote is returned as a valid, resolvable repo.

Once selected as `BaseRepo`, any command issuing API requests will resolve credentials via `AuthConfig.ActiveToken("github.com")`: [4](#0-3) 
This checks `GH_TOKEN`/`GITHUB_TOKEN` env vars first (which are documented as applying specifically to github.com/ghe.com), before falling back to keyring/config — both of which will be empty for a host the victim never logged into. [5](#0-4) 

The proof-idea's underlying claim — that `ActiveToken('github.com')` could silently return "an unrelated/env-fallback credential not meant for that repo" — is only partially borne out: `GH_TOKEN`/`GITHUB_TOKEN` are semantically defined as github.com/ghe.com credentials, so if these are set, sending them to github.com is not a wrong-host leak of an enterprise credential; it is instead the CLI silently interacting with an attacker's untrusted github.com repo when the user only intended to use their enterprise remote, and doing so with whatever ambient github.com credential happens to be present (e.g., a CI job's `GITHUB_TOKEN`). If no such env var is set, `ActiveToken` returns an empty token and downstream API calls will simply fail unauthenticated (no exploitable secret disclosed in that case, though the wrong-host targeting itself still occurs).

### Impact Explanation
This is a **wrong-host/wrong-account request-routing** bug: gh silently treats an attacker-supplied, github.com-hosted remote as the resolved base repository even though the user never authenticated to github.com. Concrete impact is bounded to: (a) unintended API calls/actions directed at an attacker-controlled github.com repository (e.g., `gh pr create`, `gh issue create`, `gh repo view` acting on the wrong repo), potentially using an ambient `GITHUB_TOKEN`/`GH_TOKEN` that was present for unrelated purposes (e.g. CI environment token), and (b) confusing/incorrect command behavior that could cause the victim to leak information (comments, PR content) to the attacker's repo, or perform authorized actions against it using a valid but misdirected credential. This does not constitute leaking an *enterprise* token to github.com, since `GH_TOKEN`/`GITHUB_TOKEN` are, by gh's own env-var contract, github.com-scoped credentials.

### Likelihood Explanation
Requires the victim to: (1) be authenticated to an enterprise host only (or in general have no `github.com` entry in the resolved default-host remote), (2) have a git repository/submodule directory whose *only* remote is attacker-influenced and points at `github.com` (plausible for third-party dependencies, forks-of-forks, or nested submodules), and (3) have a `GH_TOKEN`/`GITHUB_TOKEN` environment variable set (common in CI, but less common on a developer workstation). All-remotes-github.com-only submodule scenarios are realistic in monorepos with vendored code. The unconditional `ghinstance.Default()` addition is unconditional/code-level, so the routing behavior itself is 100% reproducible whenever preconditions (1)–(2) hold; actual credential exposure additionally requires (3).

### Recommendation
Do not unconditionally add `ghinstance.Default()` to the trusted hosts set in `pkg/cmd/factory/remote_resolver.go`. Only include `github.com` if it is actually present in `authedHosts` (or resolves as the authenticated default host), and ensure the secondary default-host filter (lines 75-80) does not silently fall back to a host-set that includes hosts the user has no credentials for. Consider making the `len(filteredRemotes) > 0` fallback in the config-sourced-default-host branch also require that the fallback candidate hosts are within `authedHosts`, not the broader `hosts` set that always includes github.com.

func (c *AuthConfig) ActiveToken(hostname string) (string, string) {
	if c.tokenOverride != nil {
		return c.tokenOverride(hostname)
	}
	token, source := ghauth.TokenFromEnvOrConfig(hostname)
	if token == "" {
		var user string
		var err error
		if user, err = c.ActiveUser(hostname); err == nil {
			token, err = c.TokenFromKeyringForUser(hostname, user)
		}
		if err != nil {
			// We should generally be able to find a token for the active user,
			// but in some cases such as if the keyring was set up in a very old
			// version of the CLI, it may only have a unkeyed token, so fallback
			// to it.
			token, err = c.TokenFromKeyring(hostname)
		}
		if err == nil {
			source = "keyring"
		}
	}
	return token, source
}
