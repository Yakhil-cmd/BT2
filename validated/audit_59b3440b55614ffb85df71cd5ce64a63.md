### Title
CCMenu XML endpoint bypasses per-token stack scoping, allowing a `read:stack`-only token restricted to one stack to read any stack's build data - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController#stack` scopes lookups through `#stacks`, which restricts to `current_api_client.stack_id` when the token has one, but `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping that scoping [1](#0-0) . `check_permissions!` only checks that `"read:stack"` is present in the token's `permissions` array; it never compares the requested stack to `current_api_client.stack_id` [2](#0-1) . As a result, a token with `read:stack` permission scoped (via `stack_id`) to stack A can still read the CCMenu XML (deploy status/build info) of any other stack B by simply passing B's param.

### Finding Description
The broken binding: the intended invariant is `current_api_client.stack_id == requested_stack.id` (when `stack_id` is set) AND `"read:stack" ∈ current_api_client.permissions`. The base controller enforces this correctly via `#stacks`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [3](#0-2) 

`CCMenuController` overrides `#stack` and drops the `stacks` scoping entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [1](#0-0) 

`require_permission :read, :stack` still runs as a `before_action` and only calls `current_api_client.check_permissions!('read', 'stack')`, which checks `permissions.include?('read:stack')` with no relation to which stack is being requested [4](#0-3) [5](#0-4) [2](#0-1) .

Attack: an operator issues an `ApiClient` scoped to stack A (`stack_id: stack_a.id`, `permissions: ['read:stack']`) intending it to only read stack A's CI status. The holder of that token instead requests `GET /stack_b_owner/stack_b_repo/stack_b_branch/ccmenu.xml?token=...` (or via Basic Auth). Because `#stack` no longer filters by `current_api_client.stack_id`, `Stack.from_param!` resolves stack B directly, the permission check passes (token has `read:stack`), and stack B's deploy/build XML is rendered and returned — an unauthorized read of another repository's stack state through a token that was supposed to be confined to a single stack.

Existing guards do not prevent this: `check_permissions!` is a global permission-string check, not a per-resource check; `authenticate_api_client` only validates the token signature; no other before_action re-applies `stacks` scoping for this controller.

### Impact Explanation
A `read:stack`-scoped token intended for one stack can enumerate/read the deploy status, last build label, and web URL of every other stack in the Shipit instance, defeating the purpose of `ApiClient#stack_id` scoping. This is an unauthenticated-for-that-resource read of stack state across tenants — matches "High: unauthenticated read of stack state" since the token was never authorized to read stack B. It is fully repeatable for any stack whose `to_param` (owner/repo/branch) the attacker can guess or enumerate, and requires no interaction beyond issuing GET requests with a valid but narrowly-scoped token.

### Likelihood Explanation
This requires possession of a legitimately issued `ApiClient` token with `read:stack` permission and a `stack_id` restriction — i.e., an attacker who already holds a scoped API token (e.g., a CI integration granted read-only access to their own stack). Given the prompt's threat model (attacker holds no `ApiClient` token at all), this specific bypass is only exploitable by a party who possesses *some* valid stack-scoped token — a lower-privileged but still credentialed actor, not the fully unauthenticated attacker described in the rules. Under the strict "unprivileged attacker holds no ApiClient token" constraint, this bug is not directly reachable; it requires being a legitimate stack-A token holder attacking stack B, which is a real but adjacent privilege-escalation scenario (cross-tenant token holder) rather than a zero-credential exploit.

### Recommendation
Have `CCMenuController#stack` reuse the base class's scoped lookup instead of `Stack.from_param!` directly, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that a `stack_id`-restricted `ApiClient` cannot resolve stacks outside its assigned scope.

### Proof of Concept
```ruby
test "a stack-scoped read:stack token cannot read another stack's ccmenu xml" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
  @client.update!(permissions: ['read:stack'], stack_id: stack_a.id)

  get :show, params: { stack_id: stack_b.to_param, token: @client.authentication_token }

  assert_response :forbidden # or :not_found
  # currently: assert_response :ok, leaking stack_b's deploy/build data
end
```
This test would currently fail (returns 200 with stack B's XML) given the controller's `#stack` override, demonstrating the scope/permission decoupling.

Note: this finding is valid as a scoping bug in the controller's code, but per the stated attacker model (zero Shipit credentials, no `ApiClient` token), full exploitation additionally requires holding a legitimately-issued, stack-restricted token — a precondition not satisfied by a completely unauthenticated attacker.
