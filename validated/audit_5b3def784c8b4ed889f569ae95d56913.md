## Finding [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Manipulable `timestamp` (last-ball timestamp) used as a deadline/expiry oracle in AA formulas - (File: formula/evaluation.js, validation.js)

### Summary
The oscript builtin `timestamp`, which AA authors commonly use to enforce time-locks, maturity dates, and challenge/closing periods, does not reflect real wall-clock time. It is populated from `objValidationState.last_ball_timestamp`, i.e. the timestamp of whatever `last_ball_unit` the trigger sender chose to reference. The only consensus constraint on this choice is that its MCI must not retreat below the MCI already committed to by the chosen parents; there is no requirement that the referenced last ball be close to the real current time. This mirrors the reported bug class of a "deadline" value that is trivially/always satisfiable by whoever constructs the transaction rather than an externally-fixed, tamper-resistant reference.

### Finding Description
In the formula evaluator, the `timestamp` keyword resolves directly to `objValidationState.last_ball_timestamp`: [3](#0-2) 

`last_ball_timestamp` is set during parent/ball validation from the timestamp of the unit the trigger's author nominated as `last_ball_unit`: [4](#0-3) 

The only guard on the chosen `last_ball_unit`/its MCI is monotonicity relative to the parents already selected by the same author, not proximity to "now": [1](#0-0) 

By contrast, the field that actually gets checked against wall-clock time is the unit's own `timestamp` field (with only a few seconds of tolerance) — this is a *different* field from the `timestamp` builtin used inside AA formulas: [5](#0-4) 

Because the trigger sender freely picks both `parent_units` and `last_ball_unit` (subject only to DAG consistency and the "must not retreat" rule), they can reference an older, already-stable ball whose `timestamp` is far less than the real time at which the trigger is actually posted/executed — effectively "holding the deadline in the past" — as long as such an older last ball is reachable and consistent with the chosen parents. Numerous production AA samples in the codebase treat this `timestamp` value as an authoritative deadline/maturity/expiry oracle:
- `option_contract.oscript` / `futures_contract.oscript`: `timestamp < 1556668800` gates blackswan/maturity logic [6](#0-5) 
- `ico_with_milestones.oscript`: `timestamp > $expiry_ts` finishes the ICO [7](#0-6) 
- `payment_channels.oscript` uses `timestamp` for `close_start_ts` and the challenge timeout comparison `timestamp > var['close_start_ts'] + $close_timeout` [8](#0-7) 
- `51_attack_game.oscript` uses `timestamp` to gate the end of a challenging period: `timestamp < var['challenging_period_start_ts'] + $challenging_period` [9](#0-8) 

None of these AAs (nor the core `timestamp` implementation) distinguish "the sender's chosen last ball timestamp" from a trustworthy, hard-to-manipulate clock, so an unprivileged trigger sender who controls which stable ball to reference effectively controls the AA's notion of "now."

### Impact Explanation
An AA trigger sender can bias the `timestamp` value seen by the AA logic toward an earlier point in time than the real submission time by choosing to anchor on an older (but still valid/stable) `last_ball_unit`. For AAs that gate fund release, expiry, maturity, or dispute/closing windows on `timestamp` comparisons (as in the futures/option/ICO/payment-channel/attack-game patterns shipped as first-class AA examples), this allows:
- Extending "too early" windows (e.g., bypassing a `challenging_period`/`close_timeout` check that should have elapsed), which is a direct funds-freezing/fund-loss vector for a counterparty relying on the timeout logic in `payment_channels.oscript` and `51_attack_game.oscript`.
- Satisfying maturity/expiry conditions (`timestamp < X` / `timestamp > X`) inconsistently with real elapsed time, letting one party record events (e.g., "blackswan", "finish ICO") earlier or later than intended, causing incorrect fund distribution.

This is a Medium-severity design gap: it does not directly let an attacker steal funds outright, but it undermines the time-lock assumptions that AA authors are implicitly encouraged to build on (per the shipped sample contracts), leading to AA fund loss/freezing or a party unfairly winning a timing-dependent dispute.

### Likelihood Explanation
Any user can act as an "unprivileged AA trigger sender" and has full control over which `parent_units`/`last_ball_unit` they include, limited only by the "last ball mci must not retreat" rule relative to their own chosen parents — not by proximity to real time. Exploitability depends on the attacker being able to locate/construct parents whose already-committed `last_ball_mci` is low enough to anchor an old `last_ball_timestamp`; this is easier during periods of lower network activity or via intentionally withheld/older free units, making it a plausible but not always trivially available manipulation window.

### Recommendation
Do not rely on the oscript `timestamp` builtin (last-ball timestamp) as a strict deadline oracle without also constraining how far it may lag behind the unit's own `timestamp`/real submission time. Consider requiring `last_ball_timestamp` to be within a bounded window of `objUnit.timestamp` (analogous to the `max_seconds_into_the_future_to_accept` check already used for the unit's own timestamp), or clearly document that `timestamp` in AA formulas is sender-selectable within DAG-consistency bounds and must not be treated as tamper-resistant for security-critical time-lock logic. AA authors relying on `timestamp` for maturity/expiry/challenge-period logic should be warned, and reference AAs (`payment_channels.oscript`, `51_attack_game.oscript`, `futures_contract.oscript`, `option_contract.oscript`, `ico_with_milestones.oscript`) should be revisited/hardened.

### Proof of Concept
1. Author a trigger unit whose `parent_units` reference an intentionally low-MCI (older) free unit chain, so that `max_parent_last_ball_mci` is small.
2. Set `last_ball_unit`/`last_ball` in the composed trigger unit to that same old, already-stable ball (satisfying `last_ball_mci >= max_parent_last_ball_mci`), while the unit's own `timestamp` field is set close to real "now" (which passes the `max_seconds_into_the_future_to_accept` check, see [10](#0-9) ).
3. Post this trigger to a deployed AA such as `payment_channels.oscript`'s "confirm closure" case, whose guard is `timestamp > var['close_start_ts'] + $close_timeout` — because `timestamp` resolves to the old `last_ball_timestamp` rather than real time, the "too early" bounce still fires even though real elapsed time already exceeds `$close_timeout`, letting the initiating party delay confirmation, or conversely letting a party time an action to land right when the illegitimately-old `timestamp` satisfies a condition that shouldn't yet be true.
