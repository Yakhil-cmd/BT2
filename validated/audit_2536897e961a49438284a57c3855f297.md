### Title
Unchecked division in `PoolState::token_price_x32` can permanently panic and brick swaps once available liquidity on one side reaches zero — (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`token_price_x32`, invoked from `get_swap_params` on every `swap_base_input`/`swap_base_output` call, performs raw (non-checked) `u128` division using `vault_amount_without_fee` results as the denominator. If either side's fee-adjusted vault balance becomes exactly `0`, the division panics and aborts the transaction. Because the panic occurs before any state mutation, once the pool reaches this state every future swap transaction (by any user) will panic identically, since the on-chain vault balances that drive the computation never change. This is structurally the same bug class as the reported `faceValueRemaining` issue: a reachable, attacker-influenced state causes an unconditional/uncontrolled revert inside a core distribution/exchange path, permanently trapping the contract's core functionality.

### Finding Description
`vault_amount_without_fee` returns `vault_amount - (protocol_fees + fund_fees + creator_fees)` for a token side: [1](#0-0) 

`token_price_x32` then divides using these fee-adjusted amounts with plain `/` operators instead of `checked_div`: [2](#0-1) 

This function is called unconditionally from `get_swap_params`, which both swap entrypoints call before performing any curve math: [3](#0-2) [4](#0-3) [5](#0-4) 

If `token_0_amount` or `token_1_amount` (i.e., the fee-adjusted balance of either vault) is exactly `0`, the expression `token_0_amount as u128 * Q32 as u128 / token_1_amount as u128` (or its counterpart) triggers a division-by-zero panic. Unlike the rest of the codebase, which consistently uses `checked_*` arithmetic and propagates `Option`/`Result` errors gracefully (e.g. `Fees::*`, `ConstantProductCurve::*`), this specific computation is unguarded.

Because `swap_base_input`/`swap_base_output` read the *current* vault token account balances (`ctx.accounts.input_vault.amount`, `ctx.accounts.output_vault.amount`) each call, and a panicking transaction reverts all state changes, reaching this all-zero-liquidity-minus-fees condition once means the vault balances that trigger the panic persist forever — every subsequent swap attempt from any account will panic in the exact same way. Since fees (`protocol_fees_token_x`, `fund_fees_token_x`, `creator_fees_token_x`) accumulate deterministically based on attacker-chosen trade amounts and the pool's (attacker-influenced, if using `initialize`) fee configuration, an attacker who controls the sequence of swap sizes can, in principle, drive one side's vault balance down to precisely equal its accrued fee total, landing the pool in this permanently bricked state.

### Impact Explanation
Once triggered, `swap_base_input` and `swap_base_output` become permanently unusable for the affected pool — no swaps can ever succeed again, since the panic occurs deterministically given the frozen vault state. This constitutes permanent freezing of the pool's trading functionality and, transitively, of LP funds' usability for exchange purposes (deposit/withdraw are unaffected since they don't call `get_swap_params`, but the AMM's core purpose — swapping — is permanently disabled). This matches the "permanent freezing of user or LP funds" acceptance criterion.

### Likelihood Explanation
Reaching the exact zero-fee-adjusted-balance condition requires precise engineering of trade sizes relative to accumulated fees, which is only practically feasible for very low-decimal or low-liquidity pools, or via carefully chosen fee-rate/pool combinations (fee rate is fixed per `AmmConfig`, chosen by an admin, but pool liquidity/trade sizes are fully attacker-controlled). This makes exploitation non-trivial but not implausible for a determined attacker targeting a specific low-liquidity pool, especially since Solana transactions allow exact integer arithmetic and simulation before submission, letting an attacker precompute the exact sequence of swap amounts needed to land the fee-adjusted balance at zero.

### Recommendation
Replace the unchecked divisions in `token_price_x32` with `checked_div` (or `checked_mul`/`checked_div` chained via `Option`), returning a `Result` error (e.g. `ErrorCode::ZeroTradingTokens` or a new `InsufficientLiquidity` error) instead of panicking when either fee-adjusted vault amount is zero. This converts an unrecoverable panic into a graceful instruction failure and, more importantly, should be paired with logic that prevents/rejects swaps that would drive `vault_amount_without_fee` to exactly zero, so a permanently un-tradeable pool state can never be reached at all.

### Proof of Concept
1. An attacker (or pool creator via `initialize`) sets up a low-liquidity pool.
2. The attacker repeatedly calls `swap_base_output` with output amounts precisely chosen (using off-chain simulation of `vault_amount_without_fee` and the deterministic fee formulas in `curve/fees.rs`) such that after a final swap, `output_vault_amount - (protocol_fees + fund_fees + creator_fees)` for one side equals exactly `0`.
3. The transaction that produces this state itself succeeds, because `token_price_x32` is evaluated using the *pre-swap* vault amount, which was still nonzero.
4. Any subsequent call to `swap_base_input` or `swap_base_output` (by the attacker or any other user) now evaluates `token_price_x32` with the fee-adjusted amount equal to `0`, causing an unconditional division-by-zero panic in: [6](#0-5) 
5. Because the panic reverts the transaction before any state changes, the vault balances remain unchanged forever, so every future swap attempt on this pool panics identically — the pool's swap functionality is permanently bricked.

    pub fn vault_amount_without_fee(&self, vault_0: u64, vault_1: u64) -> Result<(u64, u64)> {
        let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

    pub fn token_price_x32(&self, vault_0: u64, vault_1: u64) -> Result<(u128, u128)> {
        let (token_0_amount, token_1_amount) = self.vault_amount_without_fee(vault_0, vault_1)?;
        Ok((
            token_1_amount as u128 * Q32 as u128 / token_0_amount as u128,
            token_0_amount as u128 * Q32 as u128 / token_1_amount as u128,
        ))
    }

    pub fn get_swap_params(
        &self,
        input_vault_key: Pubkey,
        output_vault_key: Pubkey,
        input_vault_amount: u64,
        output_vault_amount: u64,
    ) -> Result<SwapParams> {
        let (
            trade_direction,
            total_input_token_amount,
            total_output_token_amount,
            token_0_price_x64,
            token_1_price_x64,
            is_creator_fee_on_input,
        ) = if input_vault_key == self.token_0_vault && output_vault_key == self.token_1_vault {
            let (total_input_token_amount, total_output_token_amount) =
                self.vault_amount_without_fee(input_vault_amount, output_vault_amount)?;
            let (token_0_price_x64, token_1_price_x64) =
                self.token_price_x32(input_vault_amount, output_vault_amount)?;

            (
                TradeDirection::ZeroForOne,
                total_input_token_amount,
                total_output_token_amount,
                token_0_price_x64,
                token_1_price_x64,
                self.is_creator_fee_on_input(TradeDirection::ZeroForOne)?,
            )
        } else if input_vault_key == self.token_1_vault && output_vault_key == self.token_0_vault {
            let (total_output_token_amount, total_input_token_amount) =
                self.vault_amount_without_fee(output_vault_amount, input_vault_amount)?;
            let (token_0_price_x64, token_1_price_x64) =
                self.token_price_x32(output_vault_amount, input_vault_amount)?;

            (
                TradeDirection::OneForZero,
                total_input_token_amount,
                total_output_token_amount,
                token_0_price_x64,
                token_1_price_x64,
                self.is_creator_fee_on_input(TradeDirection::OneForZero)?,
            )
        } else {
            return err!(ErrorCode::InvalidVault);
        };
        Ok(SwapParams {
            trade_direction,
            total_input_token_amount,
            total_output_token_amount,
            token_0_price_x64,
            token_1_price_x64,
            is_creator_fee_on_input,
        })
    }
