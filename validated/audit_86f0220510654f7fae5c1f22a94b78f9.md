### Title
Webhook signature is verified against an organization selected from an unverified payload field, while the write path targets a different, attacker-chosen repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to check the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body. [1](#0-0) [2](#0-1)  The event handlers that actually perform the write (e.g. `PushHandler`, via `Handler#stacks`/`repository_name`) resolve the target `Repository`/`Stack` from a *different* field of the same unverified body: `repository.full_name`. [3](#0-2)  Because `webhook_secret` is documented and implemented as optional per-organization, and `verify_webhook_signature` returns `true` unconditionally when no secret is configured for the selected organization, an attacker can pick an org with no configured secret for the "authentication" field while pointing the "target" field at any other repository hosted by the same Shipit instance. [4](#0-3) [5](#0-4) 

### Finding Description
This is the same bug class as the reported `donate()` issue: a control (`_onEarnings`/signature verification) is applied to one binding (`totalSupply`/organization used for HMAC lookup) while the operation actually acts on a different, independently-controllable value (`sharesToMint`/repository actually written), so the guard silently becomes a no-op for a subset of inputs (zero `totalSupply` / blank `webhook_secret`).

Concretely:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and looks up `Shipit.github(organization: repository_owner)` to obtain the app used to verify `X-Hub-Signature`. [1](#0-0) 
2. `GitHubApp#verify_webhook_signature` explicitly treats an unconfigured `webhook_secret` as "trivially verified": `return true unless webhook_secret`. [6](#0-5)  The setup docs mark `webhook_secret` as "(optional)", so multi-organization deployments can legitimately have one org configured without a secret. [5](#0-4) [7](#0-6) 
3. Once `head(422) unless verified` is skipped (verification passed trivially), `WebhooksController#create` dispatches the entire unverified payload to `Shipit::Webhooks.for_event(event)` handlers. [8](#0-7) 
4. Handlers resolve the actual target repository not from `repository.owner.login` but from `repository.full_name` (`Handler#repository_name`), which is an independent field in the same JSON body and is never covered by the org used for verification. [3](#0-2) 
5. `PushHandler#process` uses that `Repository`/`Stack` lookup to invoke `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack/branch. [9](#0-8) 

The binding broken: **organization authenticated (`repository.owner.login` → chosen `webhook_secret`) ≠ repository that is written (`repository.full_name` → `Stack#sync_github`)**. An attacker only needs one organization in the Shipit config to lack a `webhook_secret` (an explicitly supported, documented configuration) to author an unauthenticated webhook body whose `repository.full_name` names any other org/repo tracked by the same instance, and have it processed as if it were a verified GitHub-originated event.

### Impact Explanation
This crosses the "unauthorized" boundary explicitly called out as in-scope High/Critical impact: it lets an unauthenticated requester trigger repository sync jobs, commit status updates, or other webhook-driven side effects (`GithubSyncJob`, commit statuses, PR/label handling) against a repository/stack the attacker does not control, by exploiting a mismatch between the field used for signature authentication and the field used to select the write target. In deployments using the documented multi-organization `github:` config where at least one org omits `webhook_secret`, this effectively defeats signature verification for every other org's repositories hosted on the same instance.

### Likelihood Explanation
Requires no credentials, session, or prior access - only knowledge that a multi-org Shipit deployment exists with at least one organization that has not set `webhook_secret` (an explicitly optional setting per `docs/setup.md`). This is a plausible, even encouraged, real-world configuration (e.g., an internal/test org added without bothering to set a webhook secret), and the attacker only needs to guess/observe that org's name and craft a JSON body with mismatched `repository.owner.login` vs `repository.full_name`.

### Recommendation
Verify the webhook signature using the same repository/organization identity that handlers will subsequently act on, and require that `repository.owner.login`/`organization.login` and the resolved `repository.full_name` owner are consistent before dispatching to handlers. Additionally, consider not treating a blank `webhook_secret` as automatic verification success, or restricting that fallback to single-org deployments only, so a misconfigured/secret-less organization cannot be used as a "skeleton key" for other organizations' repositories in a shared instance.

### Proof of Concept
1. Configure Shipit with two organizations in `config/secrets.yml`: `orgA` (no `webhook_secret` set) and `orgB` (real repo `orgB/victim-repo` tracked, with `webhook_secret` set), per the documented multi-app format. [7](#0-6) 
2. POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/victim-repo"
  }
}
```
with any/no `X-Hub-Signature` header.
3. `verify_signature` resolves `repository_owner` = `"orgA"`, loads `orgA`'s `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `orgA.webhook_secret` is blank. [1](#0-0) [6](#0-5) 
4. `PushHandler` resolves the target via `repository.full_name` = `"orgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: ...)` on the real, non-archived `orgB/victim-repo` stacks - an unauthorized write triggered without ever presenting a valid signature for `orgB`. [3](#0-2) [9](#0-8)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
