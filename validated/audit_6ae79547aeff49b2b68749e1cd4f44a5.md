### Title
Multi-tenant webhook signature check binds the wrong org, allowing cross-organization webhook forgery — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects the HMAC secret used to validate an incoming webhook by reading `repository.owner.login` (or `organization.login`) out of the *unauthenticated* request body itself, then verifies the signature against that same body using the secret belonging to whichever organization that field names. Every downstream webhook handler, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field from the same untrusted body: `repository.full_name`. Because nothing ties `repository.owner.login` to `repository.full_name`, an attacker who legitimately controls one organization onboarded to the shared Shipit GitHub App (and therefore knows that organization's `webhook_secret`) can sign an arbitrary payload with their own secret while setting `repository.full_name` to point at a completely different repository/stack tracked by the same Shipit instance.

### Finding Description
`verify_signature` computes the signing organization from the body before the signature is checked: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the app configuration (and its `webhook_secret`) keyed by `repository_owner`, i.e. by `params.dig('repository','owner','login')` or `params.dig('organization','login')`: [3](#0-2) 

Multiple independent GitHub organizations, each with its own `webhook_secret`, can be configured for one Shipit installation, as shown in the sample multi-org secrets file: [4](#0-3) 

Once `verify_signature` passes, `WebhooksController#create` dispatches the raw, attacker-controlled JSON to handlers: [5](#0-4) 

Every handler resolves the target repository/stack using `repository.full_name`, not `repository.owner.login`: [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that is broken is: *the organization whose secret authenticated the request* ≠ *the repository/stack that the handler actually writes to*. GitHub's real webhook delivery guarantees these two fields are consistent because GitHub itself populates the payload for the repository the hook is registered on; but Shipit's controller never re-derives or cross-checks `repository.full_name`'s owner against the organization whose secret validated the HMAC. Since the attacker fully controls the JSON body (it is only checked for a valid HMAC, not for internal consistency), they can freely decouple these two fields.

### Impact Explanation
An attacker who administers any single GitHub organization onboarded to the shared Shipit instance (and thus knows/derives that org's `webhook_secret` — a routine, non-privileged action available to anyone who can install/administer a GitHub App on their own org) can forge signed webhook events for any other repository/stack tracked by the same Shipit instance, without any credentials to that other org or repo. This reaches multiple `Shipit::Webhooks::Handlers`:
- `push_handler.rb` can trigger `sync_github` on a foreign stack.
- `status_handler.rb` can inject a fabricated commit `status` (e.g. `state: "success"`) onto commits by SHA for any tracked stack, which is exactly the signal Shipit's undeployed-commit/CI-gating logic uses to decide whether a commit is safe to deploy.
- `membership_handler.rb`, `pull_request/*` handlers can archive/unarchive review stacks or alter team membership records tied to unrelated repositories.

The most severe path (forged commit status making an arbitrary commit appear CI-green) can lead to an unauthorized deploy being permitted on a stack the attacker does not own or have legitimate access to — squarely within the "unauthorized deploy" impact bucket.

### Likelihood Explanation
This requires only that (a) the Shipit deployment is configured for multiple GitHub organizations (an explicitly documented/supported configuration, shown in `config/secrets.development.shopify.yml`), and (b) the attacker controls or can register at least one of those organizations with the shared GitHub App — which is the normal, unprivileged, self-service way an organization joins a multi-tenant Shipit instance. No access to the victim org, victim repo, GITHUB_TOKEN, or any Shipit session/ApiClient token is required. This is a design defect in the trust binding, not a probabilistic/theoretical integer-overflow scenario, so likelihood is realistic wherever multi-org configuration is used.

### Recommendation
After signature verification, re-derive the organization from the same `repository.full_name`/`organization.login` value that handlers will use to look up the `Stack`, and reject the request (422) if it does not match the organization whose secret validated the signature. Equivalently, verify the signature using the secret belonging to the organization that owns the resolved `Repository`/`Stack`, not the organization named by an attacker-controlled field taken at face value before any cross-check.

### Proof of Concept
1. Deploy Shipit with two organizations configured, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `config/secrets.development.shopify.yml`).
2. Attacker knows `attacker-org`'s `webhook_secret` (they administer that org's GitHub App installation).
3. Attacker crafts a JSON body:
   ```json
   {
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     },
     "sha": "<victim commit sha>",
     "state": "success"
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and sends it with `X-Github-Event: status` to `POST /webhooks`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `attacker-org`'s secret, and the signature validates.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)` against the global `Commit` table (not scoped to `attacker-org`) and creates a "success" status for the victim's commit, potentially unblocking a deploy on `victim-org/victim-repo` — a repository the attacker has no legitimate access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
