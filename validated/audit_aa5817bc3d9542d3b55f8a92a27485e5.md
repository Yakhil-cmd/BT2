## Title
`validate_multisig_transaction` skips payload-consistency check against on-chain stored payload when the `abort_if_multisig_payload_mismatch` feature flag is disabled, allowing an owner to substitute an unapproved payload for execution - ([File: aptos-move/framework/aptos-framework/sources/multisig_account.move])

## Summary
The multisig admission analog of the report's "missing ownership check" is a missing *payload-binding* check: `validate_multisig_transaction`, invoked by the VM prologue as the admission gate for multisig executions, only verifies the executor-supplied payload against the on-chain record in two disjoint cases — (1) `payload_hash` is set (hash-only creation path) or (2) the `abort_if_multisig_payload_mismatch` feature is enabled and a full `payload` is stored. When a transaction was created via `create_transaction` (full payload stored, no hash) and the feature flag is off, **no comparison between the executor-supplied payload and the approved on-chain payload ever happens**.

## Finding Description
`validate_multisig_transaction` in [1](#0-0)  performs quorum/timelock checks, then attempts to bind the payload the owner is about to execute to what was actually approved:

```
if (transaction.payload_hash.is_some()) { assert!(sha3_256(payload) == *payload_hash, ...) };
if (features::abort_if_multisig_payload_mismatch_enabled()
    && transaction.payload.is_some()
    && !payload.is_empty()) {
    assert!(payload == *stored_payload, ...);
}
```

For transactions created through `create_transaction` (which stores the full `payload` on-chain rather than only a hash), `transaction.payload_hash` is `None`, so the first check is skipped entirely. The second check is gated by the `abort_if_multisig_payload_mismatch_enabled()` feature flag; when this flag is off, the block is not entered regardless of whether `payload` and `stored_payload` differ. This means the value the executing owner actually supplies (`provided_payload`, constructed from the transaction's `TransactionExecutableRef` in `run_multisig_prologue`, see [2](#0-1) ) is never checked against the payload that the other owners voted to approve. The VM then executes whatever `MultisigTransactionPayload` was decoded from the caller-supplied `payload`, via `execute_multisig_payload` [3](#0-2) , not the payload that was actually voted on.

This breaks the core admission invariant documented by the module itself and its own audit checklist item #15 — "Only owners are allowed to execute a valid transaction, if the number of approvals meets the k-of-n criteria" [4](#0-3)  — which implicitly assumes the *executed* transaction is the one that was approved, not an arbitrary substitute chosen by the last executor.

## Impact Explanation
Any owner (who need not even be one of the approvers) who is entitled to execute a fully-approved pending multisig transaction (`create_transaction` path, feature flag off) can submit a different `EntryFunction`/`Script` payload than the one the quorum approved, and have it executed under the multisig account's authority with the multisig account's assets/permissions. This is a classic transaction-admission binding failure: the wrong "approval set" (an approval for payload A) is used to authorize execution of payload B. Because multisig accounts are commonly used to hold treasury funds or admin capabilities, this could allow a single malicious owner to drain funds or execute privileged calls that were never actually approved by the required quorum, while accountability records (`TransactionExecutionSucceeded` event) would misleadingly show the original stored payload rather than what was truly executed.

## Likelihood Explanation
Exploitability depends entirely on whether `abort_if_multisig_payload_mismatch_enabled()` is set on mainnet. I was not able to fully confirm the current on-chain/genesis default of this feature flag within the available indexed files (only the feature's `move` definition and Rust binding were located, not a definitive genesis/mainnet feature-set snapshot), so I cannot assert with certainty whether this is a currently-live "medium" or hypothetically-mitigated issue. If the flag is disabled (which its very name and the defensive framing "abort_if_...mismatch" suggests it was added to plug this exact gap after `create_transaction` payload-storage was introduced), the bug is directly and trivially exploitable by any authorized multisig owner acting alone, requiring no privileged access beyond normal owner status.

## Recommendation
Remove the feature-flag gating on the payload equality check so that whenever `transaction.payload.is_some()`, the supplied payload is always checked against `stored_payload` unconditionally (mirroring the unconditional hash check for the `payload_hash` path), e.g.:
```move
if (transaction.payload.is_some() && !payload.is_empty()) {
    assert!(payload == *transaction.payload.borrow(), error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH));
};
```
If the flag exists purely for staged rollout/backward compatibility, ensure it is enabled network-wide before any account relies on `create_transaction`'s full-payload storage, and treat any window where it's disabled as an active incident.

## Proof of Concept
1. Owners A, B, C control a 2-of-3 multisig account `M`.
2. Owner A calls `create_transaction(M, payload_X)` where `payload_X` transfers 10 APT to a benign address (stored fully on-chain since `create_transaction`, not `_with_hash`, was used).
3. Owner B calls `approve_transaction`, reaching the 2-of-3 threshold for `payload_X`.
4. Assuming `abort_if_multisig_payload_mismatch` feature is disabled, Owner A submits the actual on-chain multisig-wrapped transaction with `TransactionExecutableRef::EntryFunction(payload_Y)` where `payload_Y` transfers all of `M`'s funds to Owner A's own address.
5. `run_multisig_prologue` builds `provided_payload = bcs(payload_Y)` and calls `validate_multisig_transaction(A, M, payload_Y)`.
6. In `validate_multisig_transaction`: `transaction.payload_hash` is `None` (skip first check); feature flag is off (skip second check) — the function returns without error despite `payload_Y != stored payload_X`.
7. VM executes `payload_Y` via `execute_multisig_payload`, draining `M`'s funds — despite the quorum only ever approving `payload_X`.

    fun validate_multisig_transaction(
        owner: &signer, multisig_account: address, payload: vector<u8>) {
        assert_multisig_account_exists(multisig_account);
        assert_is_owner(owner, multisig_account);
        let sequence_number = last_resolved_sequence_number(multisig_account) + 1;
        assert_transaction_exists(multisig_account, sequence_number);

        if (features::multisig_v2_enhancement_feature_enabled()) {
            assert!(
                can_execute(address_of(owner), multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        }
        else {
            assert!(
                can_be_executed(multisig_account, sequence_number),
                error::invalid_argument(ENOT_ENOUGH_APPROVALS),
            );
        };

        // Count approvals, including the executing owner's implicit vote.
        let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
        if (!has_voted_for_approval(multisig_account, sequence_number, address_of(owner))) {
            num_approvals += 1;
        };
        assert!(num_approvals >= num_signatures_required(multisig_account), error::invalid_argument(ENOT_ENOUGH_APPROVALS));

        // Timelock check — separate from quorum so the error is unambiguous.
        assert!(
            can_execute_with_timelock(multisig_account, sequence_number, num_approvals),
            error::invalid_state(ETIMELOCK_NOT_EXPIRED),
        );

        // If the transaction payload is not stored on chain, verify that the provided payload matches the hashes stored
        // on chain.
        let multisig_account_resource = borrow_global<MultisigAccount>(multisig_account);
        let transaction = multisig_account_resource.transactions.borrow(sequence_number);
        if (transaction.payload_hash.is_some()) {
            let payload_hash = transaction.payload_hash.borrow();
            assert!(
                sha3_256(payload) == *payload_hash,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH_HASH),
            );
        };

        // If the transaction payload is stored on chain and there is a provided payload,
        // verify that the provided payload matches the stored payload.
        if (features::abort_if_multisig_payload_mismatch_enabled()
            && transaction.payload.is_some()
            && !payload.is_empty()
        ) {
            let stored_payload = transaction.payload.borrow();
            assert!(
                payload == *stored_payload,
                error::invalid_argument(EPAYLOAD_DOES_NOT_MATCH),
            );
        }
    }

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };
