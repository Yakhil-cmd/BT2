### Title
Cross-organization commit-status spoofing via unscoped SHA lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb](app/models/shipit/webhooks/handlers/status_handler.rb))

### Summary
`WebhooksController#verify_signature` authenticates an inbound webhook against the GitHub organization named in the payload's `repository.owner.login` field, but the event handler that then *acts* on the payload (`Handlers::StatusHandler#process`) never re-checks that the commit it mutates actually belongs to a repository owned by that authenticated organization. This breaks the binding "organization that authenticated == repository that is written."

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate the signature with, based solely on `repository_owner`, derived from the payload: [1](#0-0) [2](#0-1) 

Once the signature check for that organization passes, the controller dispatches the *entire raw payload* to every registered handler for the event, with no further binding to the authenticated organization: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up commits **only by `sha`**, globally across the whole `Commit` table (i.e. across every stack/repository configured on the instance), with no filter tying the lookup back to the payload's `repository.full_name`/owner: [4](#0-3) 

Compare this with other handlers (e.g. `PushHandler`, pull-request handlers), which correctly scope their side effects to the repository named in the payload via `Repository.from_github_repo_name(repository_name)`: [5](#0-4) [6](#0-5) 

`StatusHandler` is the one exception: it never touches `repository_name`/`stacks`, so a `status` webhook that is validly signed for **organization A** (using A's configured webhook secret from `Shipit.github(organization: ...)`) can carry any `sha` value and will match — and mutate — a `Commit` record belonging to a completely different, unrelated organization B's stack, as long as that sha happens to exist in Shipit's `commits` table (e.g. because B's repo is a fork of, or shares commit history with, A's repo — a routine occurrence on GitHub's shared object/fork network). `create_status_from_github!` then writes a new `Status` for that foreign commit and can trigger downstream effects (`stack.schedule_merges`, `Hook.emit(:deployable_status, ...)`, marking the commit `deployable?`): [7](#0-6) [8](#0-7) [9](#0-8) 

This is the exact same bug class as the reported ZetaChain issue: a value used for one accounting/authorization purpose (majority-vote tally / organization signature) is not consistently propagated to a related computation/action (total reward units / target commit's owning repository), producing an incorrect binding between what was verified and what was actually acted upon.

### Impact Explanation
An attacker who controls (or has push/status-setting rights on) **any one organization/repository** already onboarded to a shared, multi-tenant Shipit instance (as evidenced by the multi-org config support in `test/dummy/config/secrets_double_github_app.yml`) can send a legitimately-signed `status` webhook for their own org that flips the CI status of a commit belonging to a *different* tenant's stack to "success." Because `deployable?` gates on commit status and `schedule_merges`/`ContinuousDeliveryJob` are triggered off status transitions, this can make an otherwise-blocked or CI-failing commit in another organization's stack appear deployable, potentially triggering an unauthorized merge/deploy path for a repository the attacker does not control — satisfying the "unauthorized deploy" / "cross-repository writes" Critical impact bar.

### Likelihood Explanation
Requires only that the attacker administers/pushes to one repository on a multi-tenant Shipit deployment and can guess or reuse a SHA that also exists in the victim stack's commit table (realistic via GitHub's shared fork object storage, or simply if both orgs happen to import the same upstream history). No access to Shipit's `webhook_secret`, `api_clients_secret`, or any privileged Shipit account is needed — only a legitimate GitHub-signed webhook for the attacker's own, unrelated organization.

### Recommendation
Scope `StatusHandler#process` (and any other handler that performs a global lookup keyed only by `sha`) to the repository named in the payload, mirroring the pattern used by `Handler#stacks`/`repository_name`, e.g. restrict the `Commit.where(sha: params.sha)` scan to `stacks(repository_name).flat_map(&:commits)` or join through `Stack -> Repository` matching `payload.dig('repository', 'full_name')` before creating/updating any `Status`.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/webhook secret (as supported by `test/dummy/config/secrets_double_github_app.yml`).
2. Create a `Stack`/`Commit` for `OrgB/private-repo` with `sha = X` that is CI-failing/blocked.
3. As an attacker who only administers `OrgA/some-repo` (which, e.g., is a fork sharing commit `X` with `OrgB/private-repo`, or the attacker otherwise learns/reuses sha `X`), trigger GitHub to send a real `status` webhook for `OrgA/some-repo` with `sha: X, state: "success"`.
4. `WebhooksController#verify_signature` validates the signature using `Shipit.github(organization: 'OrgA')`'s webhook secret — passes.
5. `StatusHandler#process` runs `Commit.where(sha: X)`, matches the `OrgB` commit (no repository/org check), and calls `commit.create_status_from_github!`, flipping its status to success and potentially unblocking a deploy on `OrgB`'s stack — despite the attacker never authenticating as, or having any privilege on, `OrgB`.
