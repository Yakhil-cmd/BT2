This confirms the exploit chain: `GithubSyncJob#perform` fetches real commits from GitHub via `stack.github_commits` (using the stack's own `github_api`), so the actual commit data isn't attacker-controlled, but the fact that the sync/deploy pipeline is triggered at all for an unrelated org's stack is the point — and if any of the newly-fetched commits already carry passing status/checks, `schedule_continuous_delivery` can fire a real deploy via `ContinuousDeliveryJob` for a stack the attacker's org has no relationship to.

### Title
Cross-organization webhook forgery via mismatched signature-selection key and acted-upon repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-GitHub-organization deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate the HMAC against using `repository_owner`, taken from the same untrusted JSON body it is about to validate. Because the attacker fully controls the body before it is signed with their own org's secret, they can set `repository.owner.login` to their own (legitimately controlled) organization while setting `repository.full_name` to a victim organization/repo that is actually configured as a Shipit stack. The signature check passes (it's a valid signature for the attacker's own secret over the attacker's own chosen body), but the event dispatch and all downstream handlers key off `repository.full_name`, not `repository.owner.login`.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` is derived from the payload itself: [2](#0-1) .

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization when the multi-org config schema is used, as documented in [3](#0-2)  and exercised in [4](#0-3) .

After signature verification, `create` dispatches the parsed body to handlers: [5](#0-4) . `Handler#repository_name` and every handler's `stacks`/`repository` lookup use `payload.dig('repository', 'full_name')`, e.g. [6](#0-5)  and the push flow [7](#0-6) .

The binding broken: **organization that authenticated the request (`repository.owner.login`, used to pick the verifying secret) ≠ repository that is written (`repository.full_name`, used to find and mutate the `Stack`)**. Nothing enforces that `repository.owner.login` is the owner segment of `repository.full_name`, and since the whole request body is attacker-authored before signing, an attacker who legitimately administers *any* org configured in this Shipit instance (and thus knows/controls that org's `webhook_secret`) can produce a validly-signed request whose `full_name` names a different, victim organization's tracked repository.

### Impact Explanation
A forged `push` event causes `PushHandler#process` to call `stack.sync_github(expected_head_sha:)` for the victim's stack [8](#0-7) , enqueuing `GithubSyncJob` which fetches new commits from the real GitHub repo and, on new commit data, can call `schedule_continuous_delivery` on newly-appended commits [9](#0-8) , potentially triggering `ContinuousDeliveryJob#perform` → `stack.trigger_continuous_delivery` → an actual deploy [10](#0-9) , [11](#0-10) . This is an unauthorized cross-organization trigger of deploy machinery gated by a different org's credential — matching the "unauthorized deploy" / cross-repository-writes impact class.

### Likelihood Explanation
Requires the target Shipit instance to be configured with the multi-organization `github:` schema (a documented, supported configuration) and requires the attacker to control/administer at least one of the configured organizations (so they know that org's `webhook_secret`) — this is plausible for shared Shipit instances serving several orgs/teams, none of which need to be privileged relative to each other. No `ApiClient` token, session, or victim secret is needed.

### Recommendation
After verifying the signature, assert that `repository.owner.login` (or `organization.login`) used to select the verifying secret matches the owner segment of `repository.full_name` (and any other repository identifiers acted upon by handlers) before dispatching to handlers. Reject the request if they diverge.

### Proof of Concept
1. Configure Shipit with multi-org `github:` secrets for `OrgA` (attacker-controlled) and `OrgB` (victim, has a tracked `Stack` for `OrgB/victim-repo`).
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<any sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over this exact raw body.
4. POST to `/github/webhooks`. `verify_signature` looks up `Shipit.github(organization: "OrgA")` and validates successfully.
5. `create` dispatches to `PushHandler`, which resolves the repository via `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`, finds `OrgB`'s stack, and calls `sync_github`, queuing `GithubSyncJob`/`ContinuousDeliveryJob` for a stack the attacker never had legitimate signing authority over.
