### Title
Cross-repository status/commit mutation via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves commits for an incoming GitHub status webhook using a raw, repository-agnostic `Commit.where(sha: params.sha)` query, in contrast to the safe `Commit.by_sha`/`by_sha!` helpers used elsewhere in the codebase. Because git commit SHAs are content-addressed and identical across forks/mirrors of the same history, an attacker who owns any repository sharing commit history with a victim's Shipit-tracked stack can send a status webhook for their own repository and have the status applied to the victim's commit record as well.

### Finding Description
The broken binding: the intended invariant is `sha-based commit resolution in webhook handlers == sha resolution scoped to the reporting stack/repository` (i.e., `stacks.commits.where(sha:)` or equivalent, matching the pattern used by `Commit.by_sha`). `StatusHandler#process` violates this: [1](#0-0) 

This iterates over **every** `Commit` row in the entire database whose `sha` column matches `params.sha`, with no `stack_id`/repository filter and no ambiguity guard, unlike: [2](#0-1) 

`by_sha` is still not repository-scoped by itself either (it's scoped by the caller applying it on a `stack.commits` association), but critically it is *always* invoked from a stack-scoped relation elsewhere in the codebase, while `StatusHandler` calls the bare `Commit` model directly with no scoping at all.

Exploit flow: since git SHAs are content hashes, any commit pushed to an upstream repository retains the identical SHA when it appears in a fork or mirror. If both the victim's repository (tracked by a Shipit stack) and an attacker-controlled fork share a commit (e.g., a commit from the shared upstream history, or one the attacker deliberately cherry-picks/rebases to reuse), then:

1. Attacker POSTs a `status` webhook (`POST /webhooks`) whose payload declares `repository.full_name` = attacker's own repo, but `sha` = the shared/victim commit's SHA and an arbitrary `state`/`description`/`target_url`.
2. `StatusHandler#process` finds the `Commit` row by SHA only, with zero regard for which repository/stack the webhook's payload claims, and calls `commit.create_status_from_github!(params)` on it.
3. If the victim's stack has a `Commit` row with that same SHA, its status is mutated based on attacker-supplied, unauthenticated-for-that-repo content.

This bypasses `verify_signature`/webhook signature checks in effect, because those checks only validate that the webhook truly originates from *some* registered repository (the attacker's own), not that the `sha` inside the payload belongs to that repository. There is no `require_permission!`/`stacks` scoping step in `StatusHandler#process` analogous to what other handlers use, so the cross-tenant boundary is not enforced at all for this handler.

### Impact Explanation
A successful exploit lets an attacker mutate `Status` (and downstream `Hook.emit(:commit_status, ...)`/`:deployable_status`) records belonging to a victim's stack that they do not control, purely by sending webhooks from their own repository. This can flip a victim commit from pending/failing to "success," which can unblock `deployable?` and trigger `schedule_continuous_delivery`, potentially causing an unauthorized deploy of a victim's stack — this matches the listed Critical impact category "a payload for one repository mutating another's stack, commit, task or team" and, transitively, "an unauthorized deploy." The blast radius spans all stacks that happen to contain a commit with the colliding SHA, not just one victim.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control that is registered as a Shipit stack (or is otherwise able to deliver a webhook accepted by the app for *some* stack), and (b) knowledge of, and ability to reproduce, a commit SHA that also exists in a victim's tracked stack — trivially satisfied for public forks/mirrors sharing upstream history, which is common in open-source or multi-team monorepo setups. No Shipit session, API token, or GitHub secret is required beyond controlling a webhook-emitting repository, which is within the stated unprivileged attacker capability. The attack is fully repeatable and requires no race condition or timing.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stack(s) associated with `params.repository.full_name`, e.g. resolve `Repository`/`Stack` from the payload first, then query `stack.commits.where(sha: params.sha)` (or use `Commit.by_sha` against that stack-scoped relation), mirroring how other handlers (e.g. `PushHandler`) resolve their target stack before mutating any records.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` or similar, not authored here per scope but described):
1. Create two `Stack`/`Repository` fixtures, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`).
2. Create two `Commit` rows with the identical `sha` value `"a" * 40`, one belonging to `victim_stack`, one to `attacker_stack`.
3. Build a `StatusHandler` payload with `repository.full_name = "attacker/repo"`, `sha = "a" * 40`, `state = "success"`.
4. Assert, before calling `process`, that `victim_stack.commits.find_by(sha: "a"*40).statuses.count == 0`.
5. Call `StatusHandler.new(delivery).process` (or equivalent handler invocation).
6. Assert that `victim_stack.commits.find_by(sha: "a"*40).statuses.count == 1` — i.e., the victim's commit status was mutated by a webhook whose payload's `repository.full_name` never matched `victim/repo`, demonstrating the missing binding between `Commit.where(sha:)` and stack/repository scoping.
