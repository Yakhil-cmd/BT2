### Title
Cross-organization webhook confusion allows forging GitHub events for repositories belonging to a different tenant organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which per-organization webhook secret to use for HMAC verification based on `params.dig('repository','owner','login')` (or `organization.login`), but every downstream `Shipit::Webhooks::Handlers::Handler` subclass resolves the repository to act on using a *different* field of the same attacker-controlled JSON body: `payload.dig('repository','full_name')`. These two fields are never cross-checked against each other, so a payload can be crafted where the "verifying organization" and the "repository actually written to" are different tenants.

### Finding Description
Shipit supports multi-tenant GitHub App configuration, where each organization onboarded to a shared Shipit instance has its own `webhook_secret` looked up via `Shipit.github(organization: repository_owner)`: [1](#0-0) 

The webhook controller derives `repository_owner` purely from the JSON body and uses it only to pick the secret used for HMAC verification: [2](#0-1) 

Every handler, however, resolves the target repository/stacks from a *separate* field of the same body — `repository.full_name` — with no assertion that `full_name`'s owner segment matches the `repository_owner` value that selected the verification secret: [3](#0-2) 

Because the entire raw POST body is what's HMAC-signed (`request.raw_post`), and both `repository.owner.login` and `repository.full_name` are attacker-supplied fields inside that same body, anyone who legitimately knows one tenant organization's webhook secret (e.g., an org admin who set up their own GitHub App/webhook secret for their own onboarded organization) can craft a payload where `repository.owner.login` = their own org (so verification passes with their own secret) while `repository.full_name` = `"other-org/other-repo"` (a different tenant's Shipit-managed repository). The signature check succeeds because it is keyed off `repository.owner.login`, not `repository.full_name`, and Shipit never verifies that these two fields agree.

This breaks the trust binding: **organization that authenticated == repository that is written**. The verified party (Org A, via Org A's secret) is not equal to the repository actually acted upon (Org B's repo), for the pull_request/push/status/check_suite handlers that key off `full_name`: [4](#0-3) [5](#0-4) 

### Impact Explanation
This allows an attacker who administers just one tenant organization on a shared/multi-org Shipit instance to forge webhook events (`push`, `status`, `check_suite`, `pull_request`) that are attributed to a different organization's repository, without that repository owner's cooperation. Concretely this enables:
- Injecting arbitrary commit `Status` for another org's commit (`status` event), which the deploy-safety logic (`UndeployedCommit#deployable?`, `deploy_state`) relies on to gate whether a commit can be deployed — this can be used to force a commit into a "deployable"/green state that wasn't actually vetted, enabling an unauthorized deploy downstream.
- Triggering `GithubSyncJob` for another org's stack via a forged `push` event.
- Archiving/unarchiving another org's review stacks via forged `pull_request` `closed`/`reopened` events.
- Forcing `RefreshCheckRunsJob` via forged `check_suite` events.

This qualifies as a High/Critical-class impact under the rubric (cross-repository writes / unauthorized deploy path via forged commit status), since it crosses a tenant/authentication boundary that Shipit's design explicitly intends to keep separate (per-organization secrets).

### Likelihood Explanation
Requires the attacker to legitimately possess a valid webhook secret for *some* organization already onboarded onto the shared Shipit instance (a realistic scenario for any multi-tenant/shared Shipit deployment serving multiple independent GitHub orgs, as documented in `docs/setup.md` and `lib/shipit.rb`'s `github_app_config`). No Shipit session, ApiClient token, or GitHub repository write access to the *victim* repository is needed — only crafting a raw HTTP POST with a body whose `repository.owner.login`/`organization.login` differs from its `repository.full_name`, signed with the attacker's own known secret.

### Recommendation
Cross-validate that the organization used to select/verify the webhook secret matches the owner encoded in `repository.full_name` (and any other repository-identifying field used by handlers) before processing the event. Reject the payload if they don't match. Additionally, consider scoping `Repository.from_github_repo_name` lookups to only repositories confirmed to belong to the same GitHub organization/installation that produced the verified signature.

### Proof of Concept
1. Shipit instance configured for two tenant organizations, `org-a` and `org-b`, each with their own GitHub App and webhook secret (per `github_app_config`).
2. Attacker administers `org-a` and therefore knows `org-a`'s `webhook_secret`.
3. Attacker crafts a JSON body for a `status` event:
```json
{
  "sha": "<victim commit sha belonging to org-b/target-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(org-a-secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` computes `repository_owner = "org-a"`, fetches `org-a`'s `GitHubApp`, and the signature verifies successfully.
6. `Shipit::Webhooks::Handlers::StatusHandler` (via `Handler#repository_name` / `#stacks`) resolves the target using `repository.full_name = "org-b/target-repo"`, creating/updating a `Status` on `org-b`'s commit — despite the request never having been authenticated by `org-b`'s secret.

(Note: exact behavior of `status_handler.rb`/`push_handler.rb`/`check_suite_handler.rb` internals was not fully re-verified line-by-line due to iteration limits, but `handler.rb`'s shared `repository_name`/`stacks` resolution — used by all handlers — was confirmed to rely solely on `full_name`, decoupled from the signature-verifying `repository_owner`.)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
