### Title
Stack-scoped ApiClient token bypasses its stack binding in CCMenu API, allowing cross-stack read of any stack's build/deploy state - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup method that `Shipit::Api::BaseController` uses to enforce an `ApiClient`'s stack scope, so a token that is authorized only for a single stack can be used to read CCMenu status data for any stack in the installation. This breaks the equality that should hold between "the stack a token authorizes" and "the stack the token's request actually touches."

### Finding Description
`Shipit::Api::BaseController` defines the scoping used by every other API controller: an `ApiClient` bound to a specific stack (`stack_id?` true) is restricted to that stack via `Stack.where(id: current_api_client.stack_id)`, and the requested stack is resolved through that scoped relation: [1](#0-0) 

All other controllers (`TasksController`, `DeploysController`, `RollbacksController`, `LocksController`, `MergeRequestsController`, `OutputsController`, `CommitsController`, `ReleaseStatusesController`) rely on this inherited `stack` method, so a scoped token can never resolve a stack outside its assigned `stack_id`.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving the stack directly from the global `Stack` model using only the `stack_id` request parameter: [2](#0-1) 

`ApiClient#check_permissions!` only checks that the client's `permissions` list includes `read:stack`; it never checks whether the specific stack being accessed matches `current_api_client.stack_id`: [3](#0-2) 

This is exactly the "stack a token authorises versus a stack it touches" binding: for every other controller these are equal by construction (both resolved via `stacks`/`current_api_client.stack_id`), but in `CCMenuController` the token only proves possession of `read:stack`, while the stack actually touched is attacker-chosen via the `stack_id` param, independent of the client's assigned stack.

The `authenticate_api_client` override in this controller also permits authenticating via a `token` query-string parameter (not just the `Authorization` header), which increases exposure since the token can leak more easily (referrer headers, logs, browser history) — the same test file demonstrates this behavior: [4](#0-3) [5](#0-4) 

### Impact Explanation
An `ApiClient` created and scoped to a single, non-sensitive stack (e.g. `here_come_the_walrus` fixture, scoped to `shipit`) can use its `read:stack`-permission token to call `GET /api/stacks/:stack_id/ccmenu.xml` for an arbitrary other `stack_id` and receive that stack's name, lock status, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — data belonging to a stack the token was never authorized to see. This is an unauthenticated-for-that-resource / unauthorized read of stack state across the tenant boundary the `ApiClient.stack_id` scoping is meant to enforce, matching the High-impact category "escalation into authorization scope … unauthenticated read of stack state."

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token (a routine, low-privilege credential intentionally restricted to one stack) can exploit this with a single unauthenticated GET request by simply changing the `stack_id` route/query parameter — no additional privileges, timing, or race conditions are required. The bypass is deterministic and always present, not a timing/race window.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the inherited `stacks` scope) so that all stack lookups go through `stacks.from_param!(params[:stack_id])`, ensuring `ApiClient.stack_id` scoping is uniformly enforced across every API controller, including CCMenu.

### Proof of Concept
1. Create (or use an existing) `ApiClient` scoped to `stack_id: shipit_stacks(:shipit).id` with `permissions: ['read:stack']` (e.g. fixture `here_come_the_walrus`, as shown authenticating in `test/controllers/api/ccmenu_controller_test.rb`).
2. Authenticate as that client (Basic auth with its `authentication_token`, as in `ApiHelper#authenticate!`).
3. Send `GET /api/stacks/:other_stack_id/ccmenu.xml` where `:other_stack_id` refers to a stack the client's `stack_id` does **not** match (e.g. `shipit_repositories(:soc)`'s stack, or any stack created via `Stack.create!`).
4. Observe that `CCMenuController#show` renders the XML successfully (200 OK) with that other stack's `name`, `lastBuildStatus`, etc., because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the client-scoped `stacks` relation used by `BaseController#stack`, unlike the existing test at `test/controllers/api/stacks_controller_test.rb:217-223` which confirms scoped clients are normally restricted to one stack via `#index`.
