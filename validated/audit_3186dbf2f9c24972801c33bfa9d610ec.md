### Title
Webhook Signature Verification Binds to Attacker-Controlled Organization, Not the Repository the Payload Writes To - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to validate a webhook against based on an organization name parsed out of the very payload being verified, while the actual event handlers act on a completely independent `repository.full_name` field from that same payload. Nothing ties the two together, so a signature valid for one organization can be replayed to mutate state (sync commits, post commit statuses) for a stack belonging to an entirely different, unrelated repository/organization.

### Finding Description
`verify_signature` computes `repository_owner` from the untrusted JSON body and uses it to look up the secret to check the signature against: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`), i.e. attacker-supplied data contained in the same raw body whose signature is being checked.

Once the signature check passes, `WebhooksController#create` dispatches the entire payload to registered handlers with no further binding to the organization that was used for verification: [3](#0-2) 

Handlers such as `PushHandler` and the base `Handler` class resolve the affected `Repository`/`Stack` using a *different* field of the payload — `repository.full_name` — independently of `repository.owner.login`: [4](#0-3) [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the target `Repository`) are two independent, attacker-controlled strings in the same JSON body, an attacker who legitimately controls a webhook secret for **any** organization configured in Shipit (`OrgA`) can craft a payload where `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/victim-repo"`. The HMAC signature is computed over the raw body using `OrgA`'s secret (which the attacker legitimately knows), so `verify_webhook_signature` succeeds, yet the handler acts on `OrgB/victim-repo`, a stack the attacker has no legitimate relationship with.

The broken trust equality is:
`organization authenticated by verify_signature (repository.owner.login)` ⇏ `repository actually mutated by the handler (repository.full_name)`.

Before the attacker's request, these two are implicitly assumed equal by the design (a webhook is expected to originate from GitHub for the repo it describes). After the crafted request, they diverge, and the code performs no explicit equality check between them.

### Impact Explanation
This allows a party who legitimately controls a webhook secret for one configured GitHub organization/app in a multi-tenant Shipit deployment (`test/dummy/config/secrets_double_github_app.yml` shows multiple orgs configured in the same instance) to forge webhook events — pushes, commit statuses, check-suite results — against stacks belonging to a different organization/repository they do not own. This drives `PushHandler` to call `stack.sync_github`, and `StatusHandler` to create commit statuses, which are the same signals `shipit.yml`/CI-driven auto-deploy logic relies on to decide whether commits are deployable. Forging these signals can push Shipit into believing arbitrary commits are CI-green, contributing to an unauthorized deploy on a repository the attacker does not control — matching the "unauthorized deploy" High-impact category from a cross-tenant boundary the app is documented to support (multiple orgs in one instance).

### Likelihood Explanation
Requires the attacker to control a legitimate webhook secret for at least one organization/app that this Shipit instance is configured to trust — a realistic scenario in shared/multi-tenant deployments where multiple orgs' GitHub Apps point at the same Shipit instance (as reflected by the `OrgOne`/`OrgTwo` fixture config). No repository write access, session, or `ApiClient` token is needed; only a signed payload for one's own org's app, with a crafted `repository.full_name` field pointing elsewhere.

### Recommendation
After resolving the target `Repository`/`Stack` from the payload, verify that `repository.full_name`'s owner matches the `repository_owner` (and thus the GitHub App/organization) that produced a valid signature. Reject the webhook if these diverge, rather than trusting the payload's `full_name` unconditionally in `Shipit::Webhooks::Handlers::Handler#repository_name`.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker has legitimate access to `OrgA`'s webhook secret (e.g., they administer a repo under `OrgA` that is also tracked by this Shipit instance).
3. Attacker crafts a `push` webhook body:
```json
{
  "ref": "refs/heads/master",
  "after": "<sha attacker wants seen as pushed>",
  "repository": {
    "full_name": "OrgB/victim-repo",
    "owner": { "login": "OrgA" }
  }
}
```
4. Attacker signs this exact raw body with `OrgA`'s known `webhook_secret` and sends it as `X-Hub-Signature` to `POST /github/webhooks`.
5. `verify_signature` computes `repository_owner = "OrgA"`, loads `Shipit.github(organization: "OrgA")`, and `verify_webhook_signature` succeeds because the attacker signed with the correct secret for `OrgA`. [1](#0-0) 
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, unrelated to `OrgA`, and calls `stack.sync_github` for it. [5](#0-4) [4](#0-3) 

No check anywhere confirms `"OrgA" == "OrgB"` before the mutation is applied.
