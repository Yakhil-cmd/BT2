## Analysis Result

I found a directly analogous vulnerability class in `initialize_with_permission`: an unauthenticated identity value (`creator`) is trusted to set a privileged record (`pool_creator`) without any check that it corresponds to the actual permission-holder or a signer — the same "trust an attacker-supplied identity assertion without verifying it against the authenticated principal" pattern as the SillyTavern SSO header bug.

### Title
Pool creator identity spoofing via unchecked `creator` account in `initialize_with_permission` grants unauthorized creator-fee rights — (File: `programs/cp-swap/src/instructions/initialize_with_permission.rs`)

### Summary
In `initialize_with_permission`, the `permission` PDA — the account that actually proves a caller is authorized to create a gated pool — is derived from and gated on `payer.key()`: [1](#0-0) 

However, the pool's permanent `pool_creator` field (which determines who can collect creator fees forever after) is populated from a completely separate, unchecked, non-signing account, `creator`: [2](#0-1) [3](#0-2) 

There is no Anchor constraint anywhere in the `InitializeWithPermission` account struct binding `creator` to `payer`, to `permission.authority`, or requiring `creator` to be a `Signer`. Anyone permitted to build the transaction (the `payer`, who must hold a valid `permission` PDA) can pass an arbitrary `creator` pubkey — e.g., a victim's wallet, an exchange hot wallet, or an attacker-controlled address distinct from the actual permissioned party.

### Finding Description
This mirrors the SillyTavern bug class: a value that should represent a verified/authenticated identity (there, the `Remote-User` header; here, the `creator` account persisted as `pool_state.pool_creator`) is accepted without validating it against the entity that was actually authenticated for the privileged action (there, a trusted-proxy IP check; here, the `payer` signer who owns the `permission` PDA, or a `creator` signer/constraint check).

Once `pool_state.initialize(...)` runs with `ctx.accounts.creator.key()` as `pool_creator`, this value becomes permanently authoritative for the pool's lifetime and is used later, unchecked-again, to authorize fund movement: [4](#0-3) 

and to gate who receives creator fees in the permissionless variant: [5](#0-4) 

Since `creator` in `initialize_with_permission` was never validated as the actual permissioned signer, the entity that gains the standing right to `collect_creator_fee` (as `Signer` matching `pool_state.pool_creator`) is whatever address the pool-creation transaction author chose to put there — not necessarily the party that proved permission via the `permission` PDA gate. Contrast this with the non-gated `initialize.rs` path, where the creator role and the fee-payer/signer are the same account: [6](#0-5) 

### Impact Explanation
The pool creator role is the sole beneficiary of `collect_creator_fee`/`collect_creator_fee_permissionless`, which stream accumulated `creator_fees_token_0`/`creator_fees_token_1` out of the pool vaults via the `AUTH_SEED` PDA: [7](#0-6) 

If the `creator` field can be set to an address of the payer's choosing rather than being cryptographically tied to the permissioned identity, an attacker who legitimately holds a `permission` PDA can:
1. Create a pool and set `creator` to their own second wallet or an alt account they fully control, silently detaching pool ownership/fee rights from the audited/whitelisted `permission_authority` used to grant them permission in the first place (undermining the purpose of the whitelist and any off-chain compliance around it), or
2. More critically, if permission grantees are meant to be constrained 1:1 to a specific `permission_authority`/creator identity for accounting or compliance reasons, this allows creator-fee entitlement to be assigned to an unaudited identity — a permanent, unauthorized privileged effect on the pool's fee-ledger accounting for the life of the pool.

This satisfies "unauthorized privileged effect" — the `pool_creator` field is a long-lived privileged designation controlling fund flows, and it is set based on an unverified, non-signing, attacker-supplied account.

### Likelihood Explanation
High for anyone who already holds (or can obtain) a `permission` PDA under the intended gated-launch flow. The `creator` account has no `Signer` trait, no `address =` constraint, and no relation to `payer` or `permission.authority` enforced anywhere in `InitializeWithPermission`, so exploitation requires no special conditions beyond calling the already-reachable `initialize_with_permission` instruction with a chosen `creator` pubkey in the accounts list.

### Recommendation
Add an explicit binding in `InitializeWithPermission` so that `pool_creator` cannot diverge from the verified identity, e.g.:
- Constrain `creator` to be a `Signer` and require `creator.key() == permission.authority` (or `payer.key() == creator.key()`), analogous to requiring the SSO header to be validated against a trusted source rather than accepted at face value.
- Alternatively, derive `pool_creator` directly from `permission.authority` instead of from the freestanding `creator` account, eliminating the untrusted input entirely.

### Proof of Concept
1. Attacker (`payer`) obtains a `permission` PDA (via legitimate whitelisting) keyed to `payer.key()`.
2. Attacker calls `initialize_with_permission`, supplying `payer` as the signer/fee-payer but setting the `creator` account field to an arbitrary pubkey `X` (any address, not required to sign, not required to relate to `payer` or `permission.authority`).
3. `pool_state.initialize(..., ctx.accounts.creator.key(), ...)` persists `pool_creator = X` [3](#0-2) .
4. From then on, only a signer matching `X` can call `collect_creator_fee` [4](#0-3) , and `collect_creator_fee_permissionless` will always route accumulated creator fees to `X` regardless of who actually holds the vetted `permission` PDA [5](#0-4) , decoupling fee-collection rights entirely from the permission-gate the instruction was supposed to enforce.

**Note on completeness:** I was unable to fully confirm within available tool budget whether the off-chain/CLI tooling or any additional on-chain constraint (e.g., in a version of `create_pool` I did not fully inspect) enforces `creator == payer`; the account struct itself, as read, contains no such Anchor-level constraint. If deeper confirmation is needed, a Devin session with full repo/build access could compile and test this against `create_pool` and `pool_state.initialize` to verify no implicit checks exist elsewhere.
