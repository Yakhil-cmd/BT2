### Title
Malicious submodule reference in synced repo causes persistent, unrecoverable sync denial - (File: main.go)

### Summary
`git-sync` clones an untrusted upstream repository and, when submodules are enabled, unconditionally runs `git submodule update --init [--recursive]` against whatever `.gitmodules` content exists at the target commit [1](#0-0) . There is no allow-list, filter, or mechanism to skip/remove an individual problematic submodule entry — the operator can only toggle submodules globally on/off via `--submodules`. If the tracked ref's commit (fully attacker-controlled content, since git-sync's whole purpose is to sync whatever content is pushed to the repo/ref it's told to follow) references a submodule that cannot be fetched or checked out (bad/unreachable URL, disallowed protocol, huge/slow object, etc.), `configureWorktree` fails every single sync attempt for that commit, exactly mirroring the reported bug class: an item in an unconditionally-iterated/processed set cannot be excluded, so its failure blocks the whole operation.

### Finding Description
`SyncRepo` fetches the ref, creates a worktree for the new hash, and then calls `configureWorktree`, which performs a hard reset and — if submodules aren't disabled — runs `git submodule update --init --recursive` [2](#0-1) . This call has no per-submodule exception handling; if any single submodule in the current commit fails to initialize (unreachable host, blocked protocol, credential mismatch, oversized clone, etc.), the function returns an error, which propagates up through `configureWorktree`'s caller in `SyncRepo` [3](#0-2) , aborting the whole sync for that hash.

Unlike `removeDirContentsIf`, which accumulates errors and continues processing remaining items (a resilient pattern) [4](#0-3) , the submodule update step has no such per-item resilience or removal mechanism — there is no flag or code path to exclude a single named submodule while still checking out the rest of the tree. The only knob (`--submodules=off|shallow|recursive`) is a blanket, operator-only toggle set at process startup [5](#0-4) ; it cannot be applied reactively per-commit, and there's no dynamic mechanism to "remove" the bad submodule reference the way the referenced report recommends removing a bad fee recipient.

Because the outer sync loop treats this as a normal transient error (increment `failCount`, log, retry) [6](#0-5) , and because the ref will keep resolving to the same broken commit until the upstream branch/tag is moved, every retry deterministically fails in the same way — this is not a transient condition that self-heals.

### Impact Explanation
This matches the "persistent sync denial" impact category. An attacker who can push content to the tracked ref (or influence a tag/branch that git-sync follows) can add a submodule pointing to an invalid/blocked/slow-to-fail URL. From that point on:
- `git-sync` can never advance the published symlink past the last good commit for as long as the tracked ref points at (or reaches) the bad commit.
- The failure is deterministic and repeats on every poll interval, consuming fetch/exec resources indefinitely (`metricFetchCount` increments, error logs accumulate) with no automatic recovery.
- There is no operator-facing mechanism in the current code to skip just the offending submodule while still syncing the rest of the tree; the only remedies are external to git-sync (fix/remove the submodule upstream, or disable submodules entirely with `--submodules=off`, which changes behavior for the whole deployment, not just the bad entry).

This is weaker than a fully unprivileged remote DoS since it requires push/ref-influence over the synced repository content, but it squarely matches the report's underlying pattern: no mechanism to exclude one bad "recipient"/entry causes the whole aggregate operation (there: reward distribution loop; here: worktree/submodule checkout) to fail on every invocation.

### Likelihood Explanation
Requires the attacker to control (or influence) the content of the ref that git-sync is configured to follow — this is an explicitly in-scope threat surface ("untrusted repo content"). Any repository that accepts external contributions to branches/tags git-sync follows (or where an attacker can otherwise get a commit into the synced history) can trigger this without any special privilege over the git-sync deployment itself.

### Recommendation
- Add an option to tolerate/skip individual submodule failures (e.g., `git submodule update --init` per-submodule with per-entry error isolation, similar to the `multiError`/best-effort pattern already used in `removeDirContentsIf`) instead of aborting the whole worktree configuration on the first failure.
- Optionally support an allow-list/deny-list of submodule paths or URLs so a known-bad submodule can be excluded going forward without disabling submodules globally.
- Ensure sync failures caused by submodule content are clearly surfaced (distinct metric/log reason) so operators can detect "stuck on bad submodule" versus generic transient fetch errors.

### Proof of Concept
1. Deploy `git-sync` with `--submodules=recursive` following a branch in a repo where an external actor can open/merge changes (or directly if the attacker has push access to the tracked ref).
2. Attacker adds a `.gitmodules` entry pointing to an unreachable/blocked URL (e.g., `https://169.254.169.254/x` or a host that hangs) at the tip of the tracked branch, and pushes.
3. On the next poll, `SyncRepo` fetches the new hash, creates the worktree, and calls `configureWorktree`, which runs `git submodule update --init --recursive` [1](#0-0)  — this fails.
4. `SyncRepo` returns an error; the outer loop logs and retries every `--period` [6](#0-5) , but will fail identically every time because the ref still resolves to the same bad commit.
5. The published symlink never advances past the last good commit, and this persists until someone manually fixes the upstream repo or restarts git-sync with `--submodules=off` (a global behavior change, not a per-entry fix).

```go
func removeDirContentsIf(dir absPath, log *logging.Logger, fn func(fi os.FileInfo) (bool, error)) error {
	dirents, err := os.ReadDir(dir.String())
	if err != nil {
		return err
	}

	// Save errors until the end.
	var errs multiError
	for _, fi := range dirents {
		name := fi.Name()
		p := filepath.Join(dir.String(), name)
		stat, err := os.Stat(p)
		if err != nil {
			log.Error(err, "failed to stat path, skipping", "path", p)
			continue
		}
		if shouldDelete, err := fn(stat); err != nil {
			log.Error(err, "predicate function failed for path, skipping", "path", p)
			continue
		} else if !shouldDelete {
			log.V(4).Info("skipping path", "path", p)
			continue
		}
		if log != nil {
			log.V(4).Info("removing path recursively", "path", p, "isDir", fi.IsDir())
		}
		if err := os.RemoveAll(p); err != nil {
			errs = append(errs, err)
		}
	}

	if len(errs) != 0 {
		return errs
	}
	return nil
```
