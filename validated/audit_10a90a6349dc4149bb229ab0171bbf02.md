### Title
Cross-repository commit-status forgery via unscoped `StatusHandler#process` SHA lookup — `stack_id` is never validated against the webhook's own repository (`app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/commit.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` with no repository scoping, unlike other handlers that use the `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)`). Every matched `Commit` then calls `create_status_from_github!`, which hard-codes `statuses.replicate_from_github!(stack_id, github_status)` using `self.stack_id` — there is no parameter or code path by which the verified webhook's own `payload['repository']` could ever be threaded into that call.

### Finding Description
The claimed binding: `stack_id` passed to `Status.replicate_from_github!` (`app/models/shipit/status.rb:24`) should equal the `stack_id` of the stack that owns the repository named in the verified webhook payload (`payload.dig('repository', 'full_name')`). In the actual code, `create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) always supplies `self.stack_id` — i.e., whatever `Commit` row `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:21`) happened to return — with no way to substitute or check the actual owning repository. This is confirmed structural: `create_status_from_github!` accepts only `github_status` as its argument, `add_status` accepts only a block, and `Status.replicate_from_github!` accepts `(stack_id, github_status)` — none of these carry `payload['repository']`.

Other handlers (e.g. pull request handlers) route through `Handler#stacks`, which scopes to `Repository.from_github_repo_name(repository_name)&.stacks` (`app/models/shipit/webhooks/handlers/handler.rb:32-34`), so a payload for repo A cannot touch stacks belonging to repo B. `StatusHandler#process` does not use this helper at all, and instead resolves commits purely by SHA, globally across all stacks/repositories in the installation.

Because git commit SHAs are content-addressed (hash of tree + parents + author/committer + timestamps), any two repositories that share history — most commonly a fork and its upstream, or two Shipit stacks tracking the same repo under different names — will have identical SHAs for the shared commits. An attacker who owns a fork of a target repository (or any repo sharing commit history with a Shipit-tracked repo) can:
1. Install/own a webhook-emitting repository whose commits share SHAs with a target Shipit stack's commits (e.g., fork of the target repo).
2. Send (via genuine GitHub `status` API calls on their own repo, or a repo they control that GitHub will sign correctly for) a `status` event whose `sha` matches a commit also present in the victim stack.
3. `StatusHandler#process` finds the `Commit` row for that SHA regardless of which repository it "belongs to" in Shipit's `Commit.where(sha:)` query, and writes a fabricated status (e.g., `state: success`, arbitrary `context`) onto it via `statuses.replicate_from_github!(commit.stack_id, ...)`.

Existing guards do not catch this: `verify_signature`/`GitHubApp#verify_webhook_signature` only proves the webhook truly came from GitHub for the attacker's own repository/org — it says nothing about which Shipit `Commit`/`Stack` the payload is allowed to mutate. `drop_unhandled_event` only checks event type. The `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc., not repository ownership. Nothing in `StatusHandler` calls the `stacks` scoping helper that other handlers rely on.

### Impact Explanation
A forged/foreign but validly-signed webhook for a repository the attacker legitimately controls can write a fabricated commit status (`Status.replicate_from_github!`) onto a `Commit` belonging to an unrelated victim `Stack`, as long as the SHA is shared (fork/mirror scenario). This can flip `Commit#deployable?` (via `status`/`Status::Group`) and trigger `stack.schedule_merges`, `ContinuousDeliveryJob`, or otherwise unblock a deploy gate on a stack the attacker does not own — a payload for one repository mutating another's stack/commit, matching the Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy").

### Likelihood Explanation
Requires: (a) the attacker's own repository/org has the Shipit GitHub App/webhook installed and correctly signs its own status events (which is normal, unprivileged GitHub behavior for any repo the attacker administers), and (b) the target and attacker repositories share at least one commit SHA — realistically achievable via forking a public repository that Shipit tracks. No Shipit secrets, sessions, or maintainer roles are needed. This is repeatable against any commit SHA the attacker can reproduce in a repo they control.

### Recommendation
Scope `StatusHandler#process` the same way other handlers do: restrict the `Commit` lookup to commits belonging to stacks of `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` (i.e., use `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent), so a webhook can only mutate commits/statuses belonging to its own verified repository.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status event for one repository must not update commits belonging to another repository's stack" do
  victim_stack = shipit_stacks(:shipit) # repo "shopify/shipit-engine"
  attacker_repo = Shipit::Repository.create!(owner: 'attacker', name: 'fork-of-shipit')
  attacker_stack = Shipit::Stack.create!(repository: attacker_repo, environment: 'production')

  shared_sha = 'a' * 40 # same content-addressed commit exists in both repos
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared history')
  attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'shared history')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'repository' => { 'full_name' => 'attacker/fork-of-shipit' }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  # Broken binding: stack_id used is whichever Commit row matched sha=shared_sha first,
  # not scoped to attacker_repo's stack.
  assert victim_commit.statuses.reload.exists?(context: 'ci/attacker'),
    "victim stack's commit status was mutated by a webhook verified only for the attacker's repository"
end
```
This demonstrates `Commit.where(sha:)` in `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:21`) is unscoped by repository, and `create_status_from_github!`/`add_status` (`app/models/shipit/commit.rb:165-169`, `366-386`) always pass `self.stack_id` into `Status.replicate_from_github!`, with no code path validating it against the webhook's own `payload['repository']`.
