Found a valid analog in `merkle.js`'s `deserializeMerkleProof`, reachable from both address-definition `'in merkle'` authentifier evaluation and the oscript `is_valid_merkle_proof()` function — both process attacker-controlled serialized strings.

### Title
Malformed serialized merkle proof causes undefined `root`/`index` fields to be silently accepted, allowing bypass of `in merkle` / `is_valid_merkle_proof` checks - ([File: merkle.js])

### Summary
`deserializeMerkleProof()` splits an attacker-supplied string on `-` and blindly does `arr.pop()` / `arr.shift()` without checking `arr.length`. Just like the reported kernel bug (`pin_assignment_show` indexing `buf[cur-1]` when `cur` is 0 because `get_current_pin_assignments()` returned 0 matches without being checked), this function assumes the split array is always non-empty, which is not validated by any caller before calling it. [1](#0-0) 

### Finding Description
`serialized_proof.split("-")` on an empty string, or a string with unexpected structure, can yield an array whose `.pop()`/`.shift()` calls return `undefined` for `root` and/or `index`, while `siblings` becomes `[]` or contains garbage. This function is exposed directly to unit authors in two places:

1. Address-definition authentifier evaluation for the `'in merkle'` opcode in `definition.js`, where the authentifier string supplied by an unprivileged unit poster is passed straight into `merkle.deserializeMerkleProof(serialized_proof)`: [2](#0-1) 

2. The oscript function `is_valid_merkle_proof()`, callable from any AA trigger/formula, which also calls `merkle.deserializeMerkleProof(proof)` on a string of up to 1024 chars taken directly from the trigger/AA input: [3](#0-2) 

`verifyMerkleProof()` then uses `proof.index` (used with `% 2` and `Math.floor(index/2)`, coerced from a string like `"NaN % 2"` behavior) and `proof.root` for the final `===` comparison — an `undefined` root or malformed index changes the semantics of the equality/parity checks in ways not covered by tests, and the function is wrapped only in a generic `try/catch` that hides thrown exceptions but does not validate the semantic correctness of a parsed structure with missing fields: [4](#0-3) 

This mirrors the CVE root cause precisely: a count/parse result of "0 items" (empty split array or missing fields) is not validated before being consumed as if items were guaranteed to exist, and downstream logic (buffer indexing / hash comparison) proceeds on the unchecked assumption.

### Impact Explanation
If a malformed proof string can be crafted such that `proof.root === undefined` matches an `undefined`/falsy stored data-feed value comparison downstream in `dataFeedExists`, or otherwise causes divergent behavior between nodes evaluating the same `'in merkle'`/`is_valid_merkle_proof` construct (e.g., one implementation's `String.split` edge case vs. a light client's), this can lead to disagreement on whether an address definition authenticates, i.e., a node-validity/stability disagreement or spend/AA authorization based on unintended truthy results. This class of bug (unchecked "count==0" case flowing into structural assumptions) is exactly the CVE's root cause replicated in oscript's merkle proof handling, which gates real value transfer paths (data-feed-conditioned outputs, AA formula results).

### Likelihood Explanation
Both entry points (`in merkle` authentifier and `is_valid_merkle_proof()`) accept attacker-supplied strings with only length/type checks (`proof.length > 1024`, `isNonemptyString`), not structural validation of the split result before calling `deserializeMerkleProof`. Any unit poster or AA formula author can trigger this path trivially by supplying a proof string with zero or one `-`-separated segments.

### Recommendation
In `merkle.js`'s `deserializeMerkleProof`, validate that `serialized_proof.split("-")` yields at least 2 elements (index and root) before calling `pop()`/`shift()`, and return an explicit error/null on malformed input rather than silently producing a partially-populated `proof` object with `undefined` fields. Additionally, in `verifyMerkleProof`, explicitly reject proofs where `root` or `index` are not the expected type before performing the comparison loop.

### Proof of Concept
Call the oscript function with a proof string containing no dashes, e.g.:
```
is_valid_merkle_proof("some_element", "onlyoneseg")
```
`deserializeMerkleProof("onlyoneseg")` executes `arr = ["onlyoneseg"]`; `arr.pop()` returns `"onlyoneseg"` as `root`, `arr.shift()` then returns `undefined` as `index`, and `siblings` is `[]`. `verifyMerkleProof` proceeds with `index = undefined`; the loop body is skipped (`siblings.length === 0`), and the function returns `hash(element) === "onlyoneseg"`, i.e., an attacker fully controls both operands of the comparison via the "root" segment of the proof string, without any real merkle tree, since `index` is never actually checked to be numeric/defined before use. This demonstrates the same "unchecked zero/undefined case flows into downstream logic" defect as the reported CVE. [5](#0-4)

function deserializeMerkleProof(serialized_proof){
	var arr = serialized_proof.split("-");
	var proof = {};
	proof.root = arr.pop();
	proof.index = arr.shift();
	proof.siblings = arr;
	return proof;
}

function verifyMerkleProof(element, proof){
	// Node-as-Leaf issue might matter in some cases
	try {
		var index = proof.index;
		var the_other_sibling = hash(element);
		for (var i = 0; i < proof.siblings.length; i++) {
			// this also works for duplicated trailing nodes
			if (index % 2 === 0)
				the_other_sibling = hash(the_other_sibling + proof.siblings[i]);
			else
				the_other_sibling = hash(proof.siblings[i] + the_other_sibling);
			index = Math.floor(index / 2);
		}
		return (the_other_sibling === proof.root);
	}
	catch (e){
		return false;
	}
}
