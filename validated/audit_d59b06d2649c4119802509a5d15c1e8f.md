### Title
Cross-repository status-forgery merges attacker's CI signal into victim's merge queue - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` writes an incoming GitHub `status` webhook to **every** `Commit` in the entire Shipit database whose `sha` matches the payload, with no check that the commit's `stack`/`repository` corresponds to the repository that authenticated the webhook. Any commit-owning tenant with a legitimately signed webhook (their own repo/org) can therefore flip the CI state of a same-SHA commit belonging to a completely different stack, triggering `Status#schedule_continuous_delivery` and `Commit#add_status`'s `stack.schedule_merges`, which enqueues `ProcessMergeRequestsJob` for the **victim's** stack.

### Finding Description
The broken binding, stated explicitly: `repository_that_authenticated_the_webhook (params.dig('repository','owner','login') validated in WebhooksController#verify_signature) == repository_of_the_stack_owning_the_commit_being_mutated (commit.stack.repository)`. This equality is never checked, so it is violated.

Path:
1. `WebhooksController#verify_signature` [1](#0-0)  only proves that the raw payload's HMAC matches the secret configured for `repository.owner.login` **as stated in the attacker-supplied payload body**. It says nothing about which `sha` inside that same payload maps to which repository.
2. `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This is a global lookup across **all stacks/repositories** tracked by the Shipit instance — it never calls the `stacks`/`Repository.from_github_repo_name` scoping helper that other handlers use (e.g. `CheckSuiteHandler#process` explicitly scopes via `stacks.where(branch: ...)` [3](#0-2) ). `StatusHandler` has no such scoping at all, even though the base `Handler` class exposes exactly this capability via `stacks`/`repository_name` [4](#0-3) .
3. `Commit#create_status_from_github!` → `add_status` writes the `Status` for the found commit's own `stack_id` (correct model integrity), but then unconditionally schedules downstream work based on the *content* of the forged state, not on any provenance check: `stack.schedule_merges if new_status.pending? || new_status.success?` [5](#0-4) , and `Status#schedule_continuous_delivery` → `commit.schedule_continuous_delivery` [6](#0-5) , which further calls `ContinuousDeliveryJob.perform_later(stack)` [7](#0-6) . `stack.schedule_merges` enqueues `ProcessMergeRequestsJob.perform_later(self)` for `commit.stack` [8](#0-7) . This exact enqueue-on-transition-to-success behavior is asserted directly in the existing test suite: `"#add_status schedule a MergeMergeRequests job if the commit transition to \`pending\` or \`success\`"` which asserts `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [@commit.stack])` purely as a result of calling `commit.create_status_from_github!(github_status)` [9](#0-8) .

Attacker's exact action: fork `victim/repo` (public GitHub repository tracked by Shipit with `merge_queue_enabled: true`), push a branch and open a PR. The head commit SHA is byte-for-byte identical in the attacker's fork and in `victim/repo`'s PR/merge-queue view, because git SHAs are content-addressed and unaffected by which remote holds the ref. Shipit creates a `MergeRequest` for that SHA in `victim`'s stack, pending, `rejection_reason: 'ci_missing'`. The attacker then causes (or forges, depending on whether their own org's `webhook_secret` is configured) a GitHub `status` webhook event, `state: 'success'`, for that same SHA from a repository/org **they legitimately control and that legitimately authenticates against Shipit's `verify_signature`** — this is a repo/org the attacker owns, entirely separate from `victim`. Because `StatusHandler` matches on bare `sha` with no repository check, the `Status` record is created against the **victim's** `Commit`/`Stack`, and `ProcessMergeRequestsJob` is enqueued for `victim`'s stack. The subsequent job run re-evaluates `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?` against the now-forged `success` status, potentially clearing the `ci_missing` rejection and progressing the merge request toward merge — code the attacker never had CI run on in the victim's repository at all.

Existing guards do not prevent this: `verify_signature` only authenticates "this payload matches the secret for org X", it does not, and cannot, authenticate "this `sha` belongs to a commit tracked under org X's repositories" because that binding is simply never checked in `StatusHandler`. `drop_unhandled_event`, `ExplicitParameters` schema validation, and model validations on `Status`/`Commit` only validate shape/presence of fields, not cross-repository ownership of the `sha`.

### Impact Explanation
A payload correctly authenticated for one repository/tenant mutates commit/CI state and merge-request progression state that belongs to a completely different, unrelated repository/stack — this is a "payload for one repository mutating another's stack, commit ... or an unauthorized ... merge" per the Critical severity category. Blast radius is instance-wide: any tenant with any legitimately webhook-connected repository in the same Shipit deployment can influence CI status for any other tenant's commits, provided a SHA collision (trivially achievable via fork/PR since git SHAs travel unchanged across forks). This is repeatable per request and per colliding SHA; it does not require compromising any secret belonging to the victim.

### Likelihood Explanation
Requires: (1) the victim stack has `merge_queue_enabled: true` and an in-flight `MergeRequest` blocked on `rejection_reason: 'ci_missing'` for a known head SHA (both visible to any GitHub user via the public PR/merge-queue UI); (2) the attacker controls (or has legitimately connected) some repository tracked by the same Shipit instance, giving them a validly-signed webhook channel; (3) the attacker can get that repository to emit (or forge, if that org's `webhook_secret` is unset — `GithubApp#verify_webhook_signature` returns `true` when no secret is configured) a `status` event with the colliding SHA. Given that forking a public repo naturally produces SHA collisions with the upstream PR head, and that many organizations self-service-onboard many repositories/teams into a single shared Shipit instance, this is realistically achievable by an unprivileged actor without needing any of the victim's secrets.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits purely by `sha`) to the repository asserted in the payload, mirroring `CheckSuiteHandler`: resolve `stacks` via `Repository.from_github_repo_name(params.repository.full_name)` (or equivalent) and restrict `Commit.where(sha: ...)` to `stack.commits` for stacks belonging to that repository, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, rejecting/ignoring commits owned by other repositories even when the SHA matches.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status event does not update a commit belonging to a different repository even with matching sha" do
  victim_repo = shipit_repositories(:shipit) # e.g. "shopify/shipit-engine"
  attacker_repo_full_name = "attacker/unrelated-repo"

  shared_sha = "a" * 40
  victim_commit = shipit_stacks(:shipit).commits.create!(
    sha: shared_sha, message: "victim commit", author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now
  )

  params = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/attacker',
    'created_at' => Time.now.iso8601,
    'repository' => { 'full_name' => attacker_repo_full_name, 'owner' => { 'login' => 'attacker' } },
    'branches' => []
  }

  # Binding under test: repository that authenticated the webhook (attacker/unrelated-repo)
  # must equal repository owning the mutated commit (victim's stack's repository).
  assert_no_difference -> { victim_commit.statuses.count } do
    assert_no_enqueued_jobs only: ProcessMergeRequestsJob do
      Shipit::Webhooks::Handlers::StatusHandler.call(params)
    end
  end
end
```
Currently, this test fails: `StatusHandler.call(params)` creates a `Status` on `victim_commit` and enqueues `ProcessMergeRequestsJob` with `args: [victim_commit.stack]`, even though the payload's `repository.full_name` is `attacker/unrelated-repo`, demonstrating the broken binding described above.
