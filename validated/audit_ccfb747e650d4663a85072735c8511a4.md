## Title
Cross-tenant webhook forgery: signature verification org is decoupled from the repository/commit actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects *which* GitHub App's secret to HMAC-verify a webhook against using an attacker-controlled field taken from the same unverified JSON body (`repository.owner.login`, falling back to `organization.login`). Nothing then binds that selected organization to the repository, commit, or stack that the corresponding `Webhooks::Handlers` actually mutate. In a multi-tenant Shipit deployment (explicitly supported: `config/secrets.development.example.yml` and `test/dummy/config/secrets_double_github_app.yml` show multiple GitHub Apps/orgs configured on one Shipit instance), a tenant that legitimately owns its own GitHub App webhook secret can forge a payload that verifies under *its own* org but whose payload content (`repository.full_name`, or, worse, a bare commit `sha`) targets a *different* tenant's repository/commit.

### Finding Description
`WebhooksController#verify_signature` derives the verification key like this: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`repository_owner` is read straight out of the *unverified* raw JSON body — the HMAC has not been checked yet at this point. This value only selects which per-organization `webhook_secret` (`Shipit::GitHubApp#verify_webhook_signature`) is used to check the signature — it never constrains what the rest of the payload is allowed to say.

Once the signature is accepted, handlers act on other fields of the *same* body that are never cross-checked against `repository_owner`:

- `PushHandler` resolves the target `Stack`/`Repository` purely from `payload.dig('repository', 'full_name')`: [3](#0-2) [4](#0-3) 

- `StatusHandler` is even less constrained: it doesn't look at `repository` at all, only a bare commit `sha`, and writes a status to **every** `Commit` in the entire instance matching that sha, across all tenants: [5](#0-4) 

Because `repository.owner.login`/`organization.login` (used for authentication) and `repository.full_name`/`sha` (used for the write) are independent fields inside one attacker-crafted JSON body, an attacker who is a legitimate admin of Tenant B (and therefore legitimately possesses Tenant B's own `github.webhook_secret`, as configured e.g. in `test/dummy/config/secrets_double_github_app.yml`) can:

1. Set `repository.owner.login` (or `organization.login`) to `"OrgTwo"` (their own org) so `verify_signature` picks OrgTwo's `GitHubApp` and successfully verifies the HMAC with a secret they legitimately hold.
2. Set `repository.full_name` to `"OrgOne/victim-repo"` (a different tenant's repository) for a `push` event, or simply supply the `sha` of a known commit belonging to a different tenant's stack for a `status` event.
3. POST this forged, self-signed body directly to the shared `/webhooks` endpoint.

The controller accepts the request as authentic (signature checks out for OrgTwo) and the handler then performs the write against OrgOne's data — a cross-tenant / cross-repository write authorized by the wrong organization's credential. This exactly breaks the binding "an organization that authenticated versus the repository that is written."

### Impact Explanation
This crosses the explicit trust boundary the engine is supposed to enforce: each tenant's GitHub App/webhook secret should only authorize writes to that tenant's own repositories/stacks, since Shipit is designed to host multiple orgs/apps behind one endpoint (`Shipit.github(organization:)`, multi-app `secrets.yml` schema). Concretely reachable, unprivileged (relative to the victim tenant) consequences:

- **Cross-repository writes**: `PushHandler` triggers `stack.sync_github(expected_head_sha:)` on a victim tenant's stack chosen entirely by attacker-controlled `full_name`, causing `GithubSyncJob` to run against a repository the attacker has no relationship to.
- **Unauthorized deploy / CI bypass**: `StatusHandler` has no repository scoping whatsoever — it matches purely on commit `sha` (`Commit.where(sha: params.sha)`), so a forged, self-signed `status` event can inject a fabricated `success` status (with any `context`) onto a commit belonging to a completely different tenant's stack. If that context matches a `ci.require` context gating deploy, this can defeat CI-based deploy gating and enable an unauthorized deploy of that victim's stack.
- **Team/membership tampering**: `MembershipHandler` similarly trusts `organization.login`/`team` fields from the same forged body to create/modify `Team` records used for `Shipit.github_teams` authorization, without validating that the authenticating org actually owns that team.

This satisfies the "High"/"Critical" impact bar (cross-repository writes, unauthorized deploy, escalation into team-based authorization) without requiring any Shipit session, `ApiClient` token, or the victim's own `webhook_secret`/private key — only the attacker's own legitimate tenant credential, which the rules explicitly permit as an analog ("an organization that authenticated versus the repository that is written").

### Likelihood Explanation
Requires the host application to actually run a multi-organization Shipit deployment (multiple GitHub Apps configured under `github:` in `secrets.yml`, as documented and shipped in `test/dummy/config/secrets_double_github_app.yml`), and for the attacker to be an admin of at least one onboarded tenant's GitHub App (thus legitimately possessing that tenant's `webhook_secret`). Both conditions are within the engine's own documented multi-tenant design, not a misconfiguration or undocumented deployment mode, so this is not an "engine not mounted as documented" exclusion. No compromise of the victim's secrets, TLS interception, or social engineering is needed.

### Recommendation
Bind the verified organization to the object being mutated: after `verify_signature` succeeds for organization `O`, every handler must independently confirm that the `Repository`/`Stack`/`Commit` being acted upon actually belongs to organization `O` (e.g., compare `Repository#owner` to the verified `O`, and for `StatusHandler`, scope `Commit.where(sha:)` by the commit's stack's repository owner matching `O`) before performing any write, rejecting the event otherwise.

### Proof of Concept
Conceptual outline (index does not contain a runnable exploit harness; based on the code paths cited above):
1. Configure Shipit with two GitHub Apps, `OrgOne` and `OrgTwo`, each with distinct `webhook_secret` (mirrors `test/dummy/config/secrets_double_github_app.yml`). Attacker administers `OrgTwo`'s GitHub App and knows its `webhook_secret`.
2. Attacker crafts a `status` event body: `{"sha": "<sha of a commit belonging to an OrgOne-owned stack>", "state": "success", "context": "<ci.require context for that stack>"}` with no `repository`/`organization` object, so `repository_owner` in `WebhooksController` resolves to `nil` → falls back through `Shipit.github(organization: nil)`; alternatively include `organization: {"login": "OrgTwo"}` to force selection of `OrgTwo`'s app.
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(OrgTwo_webhook_secret, raw_body)`.
4. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` succeeds (secret matches `OrgTwo`). `StatusHandler#process` then executes `Commit.where(sha: params.sha)` and creates a success status on the OrgOne commit, unconstrained by which org authenticated the request.
