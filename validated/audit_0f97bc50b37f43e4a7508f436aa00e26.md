### Title
`is_valid_signed_package` in AA oscript accepts a signed package as proof of authorization from an address even after that address has changed (revoked) its signing definition - ([File: formula/evaluation.js])

### Summary

### Finding Description
Open WebUI's flaw is that a secondary authentication surface (Socket.IO / terminal WS) checked only the cryptographic validity of a JWT (signature+expiry) but not its current revocation status, while the primary HTTP path additionally consulted a live revocation store. The result: a credential that the owner had explicitly invalidated (via sign-out/back-channel logout) kept authenticating on the secondary surface.

The `oscript` function `is_valid_signed_package(signed_package, address)`, evaluated inside AA trigger processing, relies on `signed_message.validateSignedMessage()` to prove that a supplied `signed_package` object was authorized by `address`: [1](#0-0) 

`validateSignedMessage` has two authentication modes depending on whether the caller-supplied `signed_package` includes a `last_ball_unit` field (`bNetworkAware`):
- Network-aware mode looks up the address's *currently active* definition as of `last_ball_mci` from the DB (`storage.readDefinitionByAddress`), i.e., it consults the live, up-to-date state of the address, analogous to checking a live revocation/rotation record: [2](#0-1) 
- Non-network-aware mode (no `last_ball_unit`) only checks that the *inline* `definition` supplied by the caller hashes to `address`, and never consults whether that definition is still the address's active one: [3](#0-2) 

Because `address = chash160(first-ever definition)` in ocore and never changes even after the owner rotates keys via `address_definition_change`, an *old* definition (and thus an *old*, possibly-compromised or intentionally-rotated key) will always still hash to the same address. The non-network-aware branch performs exactly this check and nothing more - it is the equivalent of `decode_token()` (signature-only) in the advisory, with no analog of the Redis revocation lookup that the network-aware branch effectively performs by reading the address's current definition from storage.

This function is directly reachable by any AA trigger sender: the trigger's `data` fields (attacker-controlled) can contain an arbitrary `signed_package` object (with or without `last_ball_unit`), and the AA author's oscript can call `is_valid_signed_package(trigger.data.signed_package, some_address)` to gate fund release, permission checks, or other trust decisions on whether `some_address` "signed" the package. `formula/validation.js` only restricts this op to AA context (post-fix) but does not forbid omitting `last_ball_unit`: [4](#0-3) 

### Impact Explanation
Any AA that uses `is_valid_signed_package(...)` to authorize an action (e.g., release of AA-held funds, execution of a privileged branch, honoring an oracle/attestation-like signed statement) can be tricked by an attacker who once controlled `address`'s original keyset but has since rotated it (via `address_definition_change`) to a new keyset — e.g. after detecting a key compromise. The attacker, still possessing the old, revoked private key, can construct a `signed_package` with the OLD definition and OMIT `last_ball_unit`; `validateSignedMessage` will accept it as validly authorized by `address` because it never checks whether that definition is still current. If the AA's logic treats a valid signed package from `address` as authorization equivalent to a fresh signature by the address owner, this leads to AA fund loss/misuse and unauthorized actions being taken in the address owner's name, using a key the owner believed to be revoked — the direct oscript/ojson analog of "a revoked credential is still accepted by an authentication surface, leading to unauthorized action as the victim."

### Likelihood Explanation
Any AA author can adopt `is_valid_signed_package` as an authorization primitive (it's a documented oscript function), and any unprivileged trigger sender fully controls the `signed_package` object passed as trigger data, including whether `last_ball_unit` is present. Exploitation requires the attacker to still hold a key that was later superseded by a definition change on the target address — a realistic scenario for compromise-recovery key rotation, which is precisely the situation JWT revocation is meant to guard against.

### Recommendation
In `signed_message.js`, when validating a signed package that will be used as a trust/authorization primitive from oscript (`is_valid_signed_package`), do not allow the "no `last_ball_unit`" branch to authenticate against an address whose definition has since changed. Either require `last_ball_unit` (and thus force validation against the live/current definition via `storage.readDefinitionByAddress`) for this specific call path, or explicitly check in `validateOrReadDefinition`'s non-network-aware branch whether `address_definition_changes` contains a stable, more-recent definition_chash for `address` and reject the signature if so.

### Proof of Concept
1. Address `A` initially has definition `D1` (keypair `K1`); `chash160(D1) == A`.
2. Owner of `A` suspects `K1` compromise and issues a `address_definition_change` message changing `A`'s active definition to `D2` (keypair `K2`); this becomes stable.
3. An AA is deployed whose bounce/execution logic includes `is_valid_signed_package(trigger.data.pkg, trigger.data.addr)` to gate a privileged action for `addr == A`.
4. Attacker, still holding `K1`, crafts `pkg = { signed_message: ..., authors: [{ address: A, definition: D1, authentifiers: {...signed with K1...} }] }` with **no** `last_ball_unit` field, and sends an AA trigger with `data.pkg = pkg, data.addr = A`.
5. In `formula/evaluation.js`, `signed_message.validateSignedMessage(conn, pkg, A, mci, ...)` is invoked; since `last_ball_unit` is absent, the non-network-aware branch in `signed_message.js` lines 241-252 only checks `chash160(D1) === A`, which is still true, and the signature under `K1` verifies — the call returns `true` even though `D1`/`K1` were revoked by the owner.
6. The AA executes the privileged branch believing the current controller of `A` authorized it, though `A`'s active keyset is now `D2`/`K2`.
