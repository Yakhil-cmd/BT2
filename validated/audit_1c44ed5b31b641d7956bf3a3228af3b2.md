This confirms the vulnerability. `check_permissions!` only checks the `read:stack`/`write:stack` permission string, never comparing `current_api_client.stack_id` to the requested stack — that scoping only happens in `stacks` (`Stack.where(id: current_api_client.stack_id)`), which `CCMenuController` never calls.

### Title
Stack-scoped ApiClient token bypasses stack binding in CCMenu XML endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks` helper defined in `Shipit::Api::BaseController`, so an `ApiClient` token that is narrowly scoped to one stack (via `stack_id`) can be replayed against any other stack's `stack_id` in the CCMenu XML endpoint and still succeed, since `check_permissions!` only checks the permission string (`read:stack`) and never compares `current_api_client.stack_id` to the requested stack.

### Finding Description
The binding that should hold is: `current_api_client.stack_id? ? current_api_client.stack_id : true` must equal `stack.id` for the stack being accessed, whenever the client is scoped. This binding is enforced by `BaseController#stack`, which resolves `stacks.from_param!(params[:stack_id])` where `stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) .

`CCMenuController` overrides `stack` and bypasses this scope entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Authorization for the action is enforced only via `require_permission :read, :stack`, which calls `current_api_client.check_permissions!(:read, :stack)` [3](#0-2) . `ApiClient#check_permissions!` only checks that the permission string `read:stack` is in the client's `permissions` array; it never consults `stack_id` [4](#0-3) .

Authentication itself further weakens the binding because `authenticate_api_client` in `CCMenuController` reads the token from the query string `params[:token]`, which is documented and tested behavior (`test "can authenticate with query string token"`) [5](#0-4) [6](#0-5) .

Exploit flow: an attacker who obtains any valid `ApiClient.authentication_token` scoped to stack A (e.g., leaked via a referrer header, logs, or browser history because it's a GET query param) can call `GET /api/cc.xml?token=<tokenA>&stack_id=<stackB.to_param>` for any other stack B. `Stack.from_param!` resolves stack B unconditionally, `check_permissions!` passes because the token has `read:stack`, and the response renders stack B's deploy/build status — even though the token was only ever meant to authorize stack A.

### Impact Explanation
The attacker gains unauthenticated (relative to stack B) read access to stack B's latest deploy/rollback status, activity, and build label/time via the CC Menu XML feed, for any stack in the installation, using a token that was only issued/scoped for a different stack. This is repeatable against any stack ID and matches the High severity category "unauthenticated read of stack state ... deploy output" since the token holder has no legitimate authorization over stack B.

### Likelihood Explanation
Preconditions: the attacker needs some `ApiClient.authentication_token` scoped to a stack (any stack, even one they legitimately have limited scoped access to, or one leaked via the query-string exposure vector called out in the question). No `api_clients_secret` or other Shipit secret is needed — a legitimately-issued but narrowly scoped token suffices. Given a token, the attack is a single GET request with an attacker-chosen `stack_id`, trivially repeatable across all stack IDs.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped `stacks` method from `BaseController` instead of calling `Stack.from_param!` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id?` restricts resolution to `Stack.where(id: current_api_client.stack_id)` exactly as it does in `Shipit::Api::StacksController`.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (minitest, `ApiControllerTestCase`):
1. Create `stack_a = shipit_stacks(:shipit)` and `stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')`.
2. Create an `ApiClient` scoped to `stack_a`: `client_a = ApiClient.create!(creator: @user, name: 'scoped', stack: stack_a, permissions: ['read:stack'])`.
3. Issue request: `get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }`.
4. Assert on the binding: before fix, `assert_response :ok` and `assert_payload 'name', stack_b.to_param` succeed (bug demonstrated — token scoped to `stack_a.id` returned data for `stack_b.id`, i.e. `client_a.stack_id (stack_a.id) != stack_b.id` yet access was granted).
5. After applying the fix (`stacks.from_param!`), the same request should raise `ActiveRecord::RecordNotFound` / render `404`/`403` instead of `200`, asserting `assert_response :not_found` (or equivalent) — confirming the binding `current_api_client.stack_id == stack.id` (when scoped) is now enforced.
