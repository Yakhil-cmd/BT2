Based on the migration name `index_commits_on_stack_id_and_sha`, the uniqueness/index constraint on `commits` is scoped to `(stack_id, sha)`, not `sha` alone — confirming that the same SHA can legitimately exist as separate `Commit` rows across different stacks (and different organizations), which is exactly the scenario the question describes (a shared template repo forked into two orgs producing identical commit SHAs).

### Title
Cross-organization Status write via globally-scoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in the payload's `repository.owner.login`/`organization.login`, then dispatches to `StatusHandler#process`, which looks up commits with `Commit.where(sha: params.sha)` across the *entire* `commits` table with no repository/stack scoping. Because the `commits` table's uniqueness constraint is `(stack_id, sha)` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`) rather than `sha` alone, two stacks belonging to different organizations can hold rows with the identical SHA, and a validly-signed webhook from organization A's secret will mutate organization B's `Commit`/`Status` rows too.

### Finding Description
The binding required for isolation is: `WebhooksController#repository_owner` (the org whose `webhook_secret` verified the request, via `Shipit.github(organization: repository_owner)` at [1](#0-0)  ) must equal the org owning every `Commit` row mutated by the dispatched handler. `StatusHandler#process` never enforces this — it queries and mutates commits purely by SHA: [2](#0-1) 

Contrast with the base `Handler#stacks` helper, which properly scopes lookups through `Repository.from_github_repo_name(repository_name)&.stacks`, tying the payload's `repository.full_name` to a specific `Repository`/`Stack`: [3](#0-2) 

`StatusHandler` extends `Handler` but its `process` method never calls `stacks`/`repository_name`, so the org-scoping mechanism that other handlers (e.g. `PullRequest::OpenedHandler`) rely on is simply absent here.

Exploit flow:
1. Attacker (or any GitHub organization the attacker controls, owning org A, with its own legitimate `webhook_secret` configured in `Shipit.github`) forks a public template repository also used by victim org B; both `Stack`s end up tracking commits with identical SHAs (a realistic, attacker-inducible condition since SHAs are content-addressed and cheaply reproduced by forking/cherry-picking the same commit).
2. Attacker pushes/creates a commit status on their own org A repository for a SHA that collides with a commit in org B's stack.
3. GitHub (or the attacker, since they control org A's webhook delivery and can compute a valid HMAC with org A's own `webhook_secret`) sends a `status` webhook signed with org A's secret, with `repository.owner.login` = org A.
4. `verify_signature` validates successfully against org A's `Shipit.github(organization: 'orgA')` secret — this check only proves the payload came from someone who knows org A's secret, not that the payload only affects org A's data.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which returns *all* matching rows including org B's `Commit`, and calls `commit.create_status_from_github!(params)` on each, writing a `Status` row scoped to org B's `Stack` and triggering `Hook.emit`, `stack.schedule_merges`, and continuous-delivery scheduling (`Commit#schedule_continuous_delivery`) against org B's stack.

None of the listed guards prevent this: `verify_signature` only checks the HMAC against the org named in the payload, not against the org of every row touched; `drop_unhandled_event` and `ExplicitParameters` only validate the shape of `state`/`sha`/etc., not repository binding; there is no `force_github_authentication`/`User#authorized?`/`require_permission!` check at all in the webhook path (webhooks are unauthenticated by user identity, only by HMAC).

### Impact Explanation
An attacker who controls a legitimately-registered organization (with its own `webhook_secret`) can inject fabricated commit statuses (e.g. `state: "success"`) into another organization's `Stack` whenever a SHA collision exists, without ever possessing org B's secret. Forced `success` statuses can unblock `deployable?` and trigger `schedule_continuous_delivery`, potentially causing an unauthorized deploy of org B's stack — this is "a payload for one repository mutating another's stack, commit, task" and can escalate to "an unauthorized deploy," matching the **Critical** impact category. The write is repeatable against any stack that happens to share a commit SHA with the attacker-controlled org's stack, and blast radius spans all tenants sharing infrastructure with colliding SHAs (most plausible for shared template/scaffold repos, monorepo forks, or squash-merge coincidences, though SHA collision generally requires the same underlying commit object, not an independently crafted one).

### Likelihood Explanation
Requires: (a) the attacker to control an onboarded GitHub organization/repository already registered with Shipit and issued its own `webhook_secret` (a low bar — this is normal onboarding, not a stolen secret); (b) a real SHA collision between the attacker's stack and the victim's stack, which occurs naturally when both fork/import the same upstream commit (common for template repos, vendored dependencies, or shared submodules) — not a cryptographic SHA collision. Given those preconditions, exploitation is a single unauthenticated-relative-to-victim HTTP POST to `/webhooks` with a validly-HMAC'd payload under the attacker's own secret; no interaction with the victim org is needed. This is feasible without any additional secrets beyond what the attacker's own organization already legitimately possesses.

### Recommendation
Scope `StatusHandler#process` to only mutate commits belonging to stacks under the repository that presented in the payload and was authenticated by `verify_signature`, mirroring `Handler#stacks`: e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the mutated `Commit` rows' `Stack#repository` matches `repository_name`/`repository_owner` from the verified payload.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, no live GitHub):
1. Configure `Shipit.github` with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`.
2. Create `Repository`/`Stack` fixtures: `stack_a` under `org-a/repo-a`, `stack_b` under `org-b/repo-b`.
3. Create `Commit` fixtures sharing the same `sha` value: `commit_a` (`stack_id: stack_a.id, sha: "deadbeef..."`) and `commit_b` (`stack_id: stack_b.id, sha: "deadbeef..."`).
4. Build a `status` webhook payload with `repository.full_name = "org-a/repo-a"`, `repository.owner.login = "org-a"`, `sha: "deadbeef..."`, `state: "success"`.
5. Compute a valid `X-Hub-Signature` using `org-a`'s `webhook_secret` and POST to `/webhooks` with `X-Github-Event: status`.
6. Assert the equality before: `commit_b.statuses.count == 0` and `commit_b.stack.repository.owner_login != "org-a"`.
7. After the request, assert `commit_b.reload.statuses.count == 1` (or `commit_b.status.state == "success"`) — proving org A's signed webhook mutated org B's `Commit`/`Status`, i.e., `WebhooksController#repository_owner` ("org-a") ≠ the owning org of the mutated row ("org-b"), demonstrating the broken binding.
