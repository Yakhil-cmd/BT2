### Title
Cross-repository status forgery via `StatusHandler#process` unscoped `Commit.where(sha:)` bypasses `require_ci` deploy safety gate - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits by SHA alone, with no repository/stack scoping, unlike every other webhook handler in the same module. A validly-signed `status` webhook from *any* repository the attacker administers can therefore mutate the CI status of a `Commit` row belonging to a completely unrelated victim stack whenever the two share a commit SHA (trivial via a fork sharing history), flipping `Commit#deployable?` to `true` and silently defeating the `require_ci` safety check in `Shipit::Api::DeploysController#create`.

### Finding Description
The broken binding: `repository_that_authenticated_the_status_update == repository_whose_commit_state_is_mutated` — this fails.

- `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) only proves the webhook payload was signed for `repository_owner` (`params.dig('repository','owner','login')`), i.e. the *attacker's own* org/repo. It says nothing about which `Commit` rows may be touched.
- `Shipit::Webhooks::Handlers::Handler` (app/models/shipit/webhooks/handlers/handler.rb:32-38) provides a `stacks` helper explicitly scoped via `Repository.from_github_repo_name(repository_name)&.stacks`, and this is correctly used by every sibling handler, e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)...`) and `CheckSuiteHandler#process` (`stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }`) — both filter by the payload's own repository before touching commits.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does not use `stacks` at all:
  ```ruby
  def process
    Commit.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
  ```
  This queries the global `Commit` table by `sha` only, matching rows from any stack/repository configured in the Shipit instance.
- `Commit#create_status_from_github!` → `statuses.replicate_from_github!` writes a `Status` row with attacker-controlled `state`, `context`, `description`, `target_url` (app/models/shipit/commit.rb:165-169), which feeds `Commit#status` and ultimately `Commit#deployable?` (app/models/shipit/commit.rb:227-229: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`).
- `Shipit::Api::DeploysController#create` (app/controllers/shipit/api/deploys_controller.rb:22) trusts `commit.deployable?` as the sole basis for the `require_ci` safety gate: `param_error!(:require_ci, "Commit is not deployable") if params.require_ci && !commit.deployable?`.

Exploit flow: the attacker forks (or otherwise obtains a repository sharing commit history with) the victim's tracked repository — forking preserves identical SHA-1 commit ids for shared history, no cryptographic collision is required. The attacker administers this fork/repo and can legitimately trigger a correctly HMAC-signed GitHub `status` webhook (`POST /webhooks`) for a shared SHA with `state: "success"`. Because `StatusHandler#process` looks up `Commit.where(sha: ...)` without repository scoping, it also updates the victim's `Commit` row for that same SHA (which belongs to the victim's stack/repository), even though the attacker never authenticated against the victim's repository or organization. Once the victim's `Commit#deployable?` returns `true`, any subsequent authorized `POST /api/stacks/:id/deploys?require_ci=true` call for the victim stack no longer raises `param_error!(:require_ci, ...)`, silently bypassing the safety gate meant to guarantee CI passed on the victim's own repository.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `require_permission!`) do not prevent this because they check message authenticity/shape and stack-level authorization for the *deploy* endpoint — none of them re-validate that the `Commit` row being mutated by `StatusHandler` actually belongs to the repository that signed the webhook.

### Impact Explanation
This is a payload for one repository mutating another repository's `Commit`/CI state (matches the Critical category "a payload for one repository mutating another's stack, commit, task or team"), and it directly enables an authorization/safety-check bypass ("Commit is not deployable" gate) leading to deployment of code that never passed the victim's actual CI (`require_ci` becomes a no-op). It is repeatable against any stack/repository whose commit history intersects (via fork or shared upstream) with any repository the attacker can administer — a broad blast radius across tenants of a shared Shipit instance, since the vulnerable lookup has no tenant boundary at all.

### Likelihood Explanation
Preconditions are realistic and low-cost: the attacker only needs to legitimately administer some GitHub repository (e.g., a fork of the victim's public/shared repo) so they can generate a genuinely signed `status` webhook; sharing a SHA with the victim commit is a natural consequence of forking/shared history, not a cryptographic attack. No Shipit secrets, sessions, or API tokens are required for this leg of the attack. The subsequent `require_ci=true` deploy call is performed separately by an already-authorized caller, as stated in the question (out of scope for this finding to demonstrate, but its safety guarantee is what gets undermined).

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, consistent with every other handler, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the inherited `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) so that only commits belonging to the repository that produced the signed webhook can have their status mutated.

### Proof of Concept
Add a minitest to `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extend `test/controllers/webhooks_controller_test.rb`):

1. Create two stacks/repositories, `victim_stack` (repo `victim-org/app`) and `attacker_stack` (repo `attacker-org/app-fork`), and a `victim_commit` with `sha = "deadbeef..."` on `victim_stack` with no passing status (so `victim_commit.deployable?` is `false`).
2. Also create a `Commit` with the *same sha* belonging to `attacker_stack`.
3. Assert baseline: `refute victim_commit.deployable?`.
4. Build a `StatusHandler` payload whose `repository.full_name` is `attacker-org/app-fork` and `sha` equal to the shared sha, `state: 'success'`; invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is orthogonal and legitimately passes for the attacker's own repo).
5. Assert the bug: `assert victim_commit.reload.deployable?` — the victim's commit was flipped to deployable by a payload naming only the attacker's repository.
6. Feed this into `Shipit::Api::DeploysController#create`: `post :create, params: { stack_id: victim_stack.to_param, sha: victim_commit.sha, require_ci: true }` and assert `response.status == 202` (`:accepted`) instead of the expected `422` with `errors.require_ci == ["Commit is not deployable"]`.

Both assertions (`victim_commit.deployable?` flips to `true`, and the `require_ci` `param_error!` no longer raises) demonstrate the equality `repository_that_authenticated == repository_whose_state_changed` is violated.
