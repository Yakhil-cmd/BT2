## Title
Non-transferable assets accepted by an AA can become permanently unwithdrawable, freezing user funds - (File: validation.js, aa_composer.js)

### Summary
The reported ERC777 issue is a case of code assuming that an externally-defined token always supports a generic "send" primitive (`transfer`), when the token standard explicitly allows that primitive to be absent, leading to permanently stuck user funds with no fallback. The Obyte/ocore analog is the `is_transferrable` asset flag: an asset issuer can freely define an asset with `is_transferrable: false`, and any Autonomous Agent (AA) that generically accepts an arbitrary user-deposited asset and later tries to pay it back out via a normal `payment` message (a pattern explicitly used in the project's own oscript examples, e.g. banks/exchanges that store `var[balance_<address>_<asset>]` and later `payment` it back on withdrawal) will have that outgoing payment permanently rejected by consensus validation, locking the deposited balance inside the AA forever.

### Finding Description
`validatePaymentInputsAndOutputs` enforces that a non-transferable asset can only move between the asset's `definer_address` and the current holder — it cannot be forwarded to an arbitrary third address: [1](#0-0) 

This rule is checked unconditionally for every payment message involving that asset, including messages composed by an AA. When an AA receives a deposit of some asset (`trigger.output[[asset!=base]]`), it commonly credits an internal balance/state variable for that address+asset pair and later, on a withdraw request, emits a `payment` message sending that same asset back to `trigger.address` — exactly the pattern shown in the codebase's own oscript samples: [2](#0-1) [3](#0-2) [4](#0-3) 

None of these generic "accept any asset, withdraw by address" patterns check `is_transferrable` before accepting the deposit or before emitting the withdrawal payment. If an attacker (the asset's issuer/definer) crafts an asset with `is_transferrable: false` (fully permitted for any unprivileged asset issuer per `validateAssetDefinition`) and sends units of it to such an AA, the AA credits the deposit and updates its internal accounting normally, exactly like receiving any other divisible/transferable asset — the trigger/payment validation for the *incoming* transfer to the AA is satisfied because it can be structured as "definer sends to holder" or similar.

The problem only manifests on withdrawal: when the AA composes the outgoing `payment` message to `trigger.address` (a third party, not the asset's definer), `aa_composer.js`'s `sendUnit`/`completePaymentPayload` builds and submits the response unit, which is then validated by `validateAndSaveUnit`. Because the destination is neither the definer nor part of an allowed definer/self pattern, `validatePaymentInputsAndOutputs` rejects it with `"the asset is not transferrable"`: [5](#0-4) 

This causes `sendUnit`'s error path to invoke `bounce(err)`: [6](#0-5) 

`bounce()` discards the pending state update (the internal balance decrement is rolled back) and only refunds the *current trigger's* received amounts (subject to `bounce_fees`) — it does **not** and cannot release the previously-deposited, now-un-sendable asset balance, because that balance simply cannot be paid out to anyone except the definer address, which the AA has no logic or authorization to redirect to.

The AA's oscript logic never anticipated that a "successfully accepted" deposited asset might be permanently non-transferable outbound to the depositor, just as the Swapnet `Escrow.sol` `withdraw` function never anticipated that a "successfully accepted" ERC777 token might lack a `transfer` function.

The only way an AA author can guard against this is to explicitly inspect `asset[...].is_transferrable` (exposed via the `asset[]` oscript helper, seen in `formula/common.js`'s `objBaseAssetInfo` shape) before crediting a deposit — a check absent from the project's own canonical example contracts. [7](#0-6) 

### Impact Explanation
Any AA implementing the common "generic multi-asset deposit/withdraw ledger" pattern (banks, exchanges, escrows, DEX order books) can have arbitrary amounts of value permanently frozen: an attacker issues a worthless `is_transferrable:false` asset, deposits it into the target AA (crediting the victim's ledger entry as if it were a normal asset), and the victim's balance for that asset can never be withdrawn, since every attempted withdrawal payment will fail the transferability check and bounce. This is an AA fund-freezing condition reachable purely by an unprivileged asset issuer and AA trigger sender, without any special privileges.

### Likelihood Explanation
High. Creating a non-transferable asset is a permitted, unprivileged, one-message operation (`app: 'asset'`, `is_transferrable: false`), and depositing it into a target AA that accepts arbitrary assets is a single trigger unit. The vulnerable "accept any asset, track balance, pay back on demand" pattern is exactly what the project's own documentation/sample oscript files (bank, exchange, market-maker templates) teach developers to write, making the flaw very likely to be replicated in real-world AAs.

### Recommendation
- In AA templates/documentation and in any code review guidance, explicitly warn that `trigger.output[[asset!=base]]` may reference a non-transferable asset (`is_transferrable:false`), and require AAs that accept generic assets to check `asset[$asset].is_transferrable` (and reject/bounce the deposit) before crediting any internal balance for that asset.
- Consider exposing a clearer/cheaper oscript primitive or validation warning to detect this asset property at deposit time, similar to how `fixed_denominations` is already checked in some samples.
- Update the official example contracts (`a_bank_without_percent.oscript`, `order_book_exchange.oscript`, `sell_asset_for_bytes.oscript`, etc.) to add an `is_transferrable` guard, since these are used as reference implementations by third-party AA developers.

### Proof of Concept
1. Attacker issues asset `X` with `{is_private:false, is_transferrable:false, auto_destroy:false, fixed_denominations:false, issued_by_definer_only:true, cosigned_by_definer:false, spender_attested:false}` — validated and accepted per `validateAssetDefinition`: [8](#0-7) .
2. Attacker sends a payment of asset `X` to a target "bank" AA such as `a_bank_without_percent.oscript`, structured as definer→holder so it passes the transferability check on the way in; the AA's state handler credits `var['balance_<attacker>_X'] += amount` per: [9](#0-8) .
3. Attacker later triggers `{withdraw:true, asset:'X', amount:<n>}` to reclaim the funds; the AA composes `{app:'payment', payload:{asset:'X', outputs:[{address:trigger.address, amount:n}]}}` per: [10](#0-9) .
4. `sendUnit` composes and validates this response unit; because `trigger.address` (the withdrawal recipient) is neither `X`'s definer nor part of an allowed self/definer pattern, `validatePaymentInputsAndOutputs` rejects the unit with `"the asset is not transferrable"`: [1](#0-0) .
5. `bounce(err)` reverts the pending state update but cannot restore a sendable path for the already-deposited asset `X` balance, permanently locking it in the AA: [6](#0-5) .
