### Title
Webhook signature verification keys on `repository.owner.login` while event handlers act on `repository.full_name`, allowing cross-organization webhook forgery in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each GitHub organization has its own `GitHubApp` instance and its own `webhook_secret`, selected by `Shipit.github(organization:)` in `lib/shipit.rb`. The `WebhooksController` picks which organization's secret to verify a request against using one field of the payload (`repository.owner.login`), but the event handlers that actually mutate data pick the target repository/stack using a *different* field of the same payload (`repository.full_name`). These two fields are never cross-checked against each other.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the `webhook_secret` used for HMAC verification) using: [1](#0-0) 
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end
```
where [2](#0-1) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

After the signature is verified with the org resolved from `repository.owner.login`, `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name` resolve the target repository from a *different* field: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`lib/shipit.rb#github` resolves the `GitHubApp`/secret purely by the organization key supplied: [4](#0-3) 
```ruby
def github(organization: github_default_organization)
  if github_default_organization.nil?
    config = secrets.github
  else
    config = github_app_config(organization)
    raise GithubOrganizationUnknown, organization if config.nil?
  end
  @github ||= {}
  @github[organization] ||= GitHubApp.new(organization, config)
end
```

Because `repository.owner.login` (used for authentication) and `repository.full_name` (used to identify the write target) are two independent, attacker-controlled fields of the same raw POST body, an operator of one legitimately-configured organization ("OrgA", with their own real `webhook_secret` from their own GitHub App as documented in `docs/setup.md` and `config/secrets.development.shopify.yml`) can craft a payload where `repository.owner.login` = `"OrgA"` (so the signature validates against the secret they legitimately know) while `repository.full_name` = `"OrgB/other-repo"` (a stack belonging to a different tenant/organization hosted on the same Shipit instance). The equality that should hold — organization that authenticates the request == organization whose repository is written — is broken.

### Impact Explanation
This breaks the multi-tenant boundary the "Using Multiple Github Applications" feature is built to provide: an entity that only legitimately controls one org's GitHub App/webhook secret can forge events attributed to any other org/repo hosted on the same instance. Depending on the event type dispatched by `create` (e.g. `status`, `push`, `check_suite`, `membership`), this can inject fabricated CI `Status`es on another tenant's commits (potentially satisfying deployment checks and enabling an unauthorized deploy), trigger `GithubSyncJob`/`RefreshCheckRunsJob` against another tenant's stack, or create arbitrary `Team`/`User` records — all without any privileged Shipit session, `ApiClient` token, or access to the victim organization's own webhook secret.

### Likelihood Explanation
This requires the operator to run Shipit in the documented multi-organization configuration and for the attacker to be an administrator of at least one of the configured organizations' GitHub Apps (an unprivileged actor relative to the other tenants on the shared instance, and relative to Shipit's own privileged roles). This is a realistic and explicitly documented deployment topology, and no other credential (Shipit session, API token, GitHub push access to the victim repo) is required beyond knowledge of one's own legitimately-provisioned webhook secret.

### Recommendation
Bind signature verification and repository resolution to the same identity: derive the organization used for `Shipit.github(organization:)` from `repository.full_name`'s owner segment (or `organization.login`, but always the same field the handlers use), or after verifying the signature, explicitly assert that `repository.full_name`'s owner matches the `repository_owner` used to select the verifying `GitHubApp`, rejecting the request (422) on mismatch.

### Proof of Concept
1. Operator runs Shipit with the multi-org config shown in `docs/setup.md` ("Using Multiple Github Applications"), hosting stacks for `OrgA` and `OrgB` on one instance, each org with its own GitHub App and `webhook_secret`.
2. Attacker legitimately controls `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body with `repository.owner.login = "OrgA"` and `repository.full_name = "OrgB/victim-repo"`, computes `X-Hub-Signature` using `OrgA`'s secret over the raw body, and POSTs it to `/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` from `repository_owner` and successfully verifies the signature.
5. `Shipit::Webhooks::Handlers::StatusHandler` (via `Handler#stacks`/`#repository_name`) resolves the target repository from `full_name`, i.e., `OrgB/victim-repo`, and writes a `Status` (or triggers `GithubSyncJob`) against `OrgB`'s stack — despite the attacker never having been authenticated as, nor possessing credentials for, `OrgB`.
