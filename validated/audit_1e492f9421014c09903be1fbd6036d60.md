### Title
Unchecked `get_cell_index` return lets a pending JS TypeError be silently swallowed while the native loop continues, passing an attacker-controlled `0` cell index into `verify_cell_kzg_proof_batch`/`recover_cells_and_kzg_proofs` - (File: bindings/node.js/src/kzg.cxx)

### Summary
### Finding Description
`get_cell_index` is the only argument-validation helper in `kzg.cxx` that does **not** follow the `nullptr`-sentinel error-signalling convention used by every other helper (`get_blob`, `get_bytes32`, `get_bytes48`, `get_cell`). When the array element supplied for a cell index is not a JS number, it throws a `Napi::TypeError` but then unconditionally returns `0`: [1](#0-0) 

The author's own comment flags this: `/* TODO: how will the caller know there was an error? */`. Both call sites use the result directly without checking whether a JS exception is already pending: [2](#0-1) [3](#0-2) 

Contrast this with the `get_cell`/`get_bytes48` calls in the very same loops, whose `nullptr` result is checked and causes an immediate `goto out`. Because `get_cell_index`'s error is not checked, when `cellIndices[i]` is a non-number (e.g. a string, object, or `NaN`), the loop:
1. Silently substitutes `0` as the cell index for that position.
2. Continues iterating, potentially calling `get_cell`/`get_bytes48` on subsequent elements, all while a JS exception object is already pending on the `napi_env`.
3. Eventually calls into `verify_cell_kzg_proof_batch` or `recover_cells_and_kzg_proofs` in `src/eip7594/eip7594.c` with a `cell_indices` array containing the substituted `0` value(s) instead of aborting.

This is the same bug class as the referenced advisory: a native binding fails to validate/propagate a type-check failure correctly, so execution proceeds past the point where it should have stopped, operating on attacker-influenced data under a corrupted invariant (a pending exception + a silently defaulted numeric value).

### Impact Explanation
For `VerifyCellKzgProofBatch`, the substituted index `0` is fed straight into `verify_cell_kzg_proof_batch`, which uses `cell_indices[i]` to select the corresponding coset/root-of-unity used in the pairing check in `src/eip7594/eip7594.c`. Supplying a wrong-but-in-range index (`0` instead of the real index) causes the function to check the proof against the wrong evaluation domain point — i.e., the verification equation being evaluated no longer matches the "cell at claimed index" that the caller believes it is checking. If a caller (e.g., a client relaying on this binding's boolean result to decide whether cell data is valid for a specific index) does not itself re-validate the index-to-data mapping, this can lead to a cell being accepted as valid for the wrong index, an equality break between "verified" and "actually corresponds to claimed index." Because the JS exception is still pending when N-API returns control to the JS engine, the *thrown* TypeError will ultimately still surface to the caller (Node.js typically raises the pending exception once the native call returns undefined/null), so the practical exploitability is bounded by whatever partial native work happens before the function returns — but the core defect (validation bypass in the index path with silent default value and unchecked error propagation) matches the report's core theme of "type-check failure not properly interrupting execution."

### Likelihood Explanation
This path is reachable by any caller of the public `verifyCellKzgProofBatch` or `recoverCellsAndKzgProofs` JS APIs by supplying a `cellIndices` array containing a non-numeric element — a straightforward, single-call, low-complexity trigger requiring no privileged access, matching the "unprivileged, breaks reachable within this repo" bar.

### Recommendation
Make `get_cell_index` follow the same sentinel-and-check convention as the other `get_*` helpers: signal failure unambiguously (e.g., via an `out`-parameter `bool *ok` or by having callers check `env.IsExceptionPending()` immediately after the call) and `goto out`/return early exactly as `get_cell`/`get_bytes48` do, before any further loop iteration or native call.

### Proof of Concept
Call `verifyCellKzgProofBatch(commitments, cellIndices, cells, proofs)` where `cellIndices` is `[ "not-a-number", 1, 2, ... ]` matching the other arrays' lengths. `get_cell_index` throws a `TypeError` but returns `0`; execution proceeds into `get_cell`/`get_bytes48` for the remaining loop body and eventually calls `verify_cell_kzg_proof_batch` with `cell_indices[0] == 0` instead of aborting immediately, as shown at: [4](#0-3)
