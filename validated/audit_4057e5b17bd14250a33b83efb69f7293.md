## Title
Unauthenticated cross-repository/cross-organization write via decoupled webhook-signature-organization and webhook-target-repository fields - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback), but the event handlers that actually mutate state (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*Handler`s) resolve the target `Repository`/`Stack` from a *different* field of the same attacker-controlled JSON body: `payload.dig('repository', 'full_name')`. Because `verify_webhook_signature` unconditionally returns `true` when an organization's `webhook_secret` is unset (an explicitly optional setting per `docs/setup.md`), any organization onboarded without a configured secret becomes a skeleton key: an unauthenticated attacker can send a POST to the public `/webhooks` endpoint with `repository.owner.login` set to that unsecured org (bypassing signature verification entirely) while setting `repository.full_name` to any other real, secured repository in the same Shipit instance. The handler will then act on that unrelated repository/stack.

### Finding Description
The controller only checks that *some* known organization's signature validates (or that verification is skipped because that organization has no secret) — it never verifies that the *same* organization/repository is the one whose data is subsequently processed: [1](#0-0) [2](#0-1) [3](#0-2) 

`verify_webhook_signature` is a no-op when `webhook_secret` is blank: [4](#0-3) 

The Shipit multi-tenant secrets format explicitly supports organizations configured with `webhook_secret: # nil` (see `test/dummy/config/secrets_double_github_app.yml`'s `OrgTwo` entry), confirming this is a realistic, first-class supported deployment shape, not a hypothetical misconfiguration.

Meanwhile, every mutating handler resolves its target purely from `repository.full_name` in the same JSON payload, independent of which organization the controller used to "verify" the request: [5](#0-4) 

This is exactly the class of bug in the referenced report: two fields that are supposed to be bound together by a single trust check (the base/length pairing in `innerModExp`) are instead independently controllable, so the "verified" quantity (organization owning the secret, or lack thereof) is not the same as the quantity actually acted upon (the repository/stack the handler mutates). Concretely: `verified_org(payload.repository.owner.login) != acted_upon_repo(payload.repository.full_name)`.

### Impact Explanation
An unauthenticated external attacker (no Shipit session, no API token, no webhook secret for the target repository) can forge GitHub-style webhook payloads by choosing `repository.owner.login` to be any organization configured in the Shipit instance without a `webhook_secret` — a state explicitly permitted by Shipit's own documented setup instructions ("Webhook secret (optional)") — while setting `repository.full_name` to any other tracked repository. This yields cross-repository/cross-tenant writes: e.g. a forged `push` event will cause `Repository.from_github_repo_name` to resolve to an arbitrary victim repository/stack and enqueue a `GithubSyncJob` with an attacker-chosen `expected_head_sha`, or a forged `status`/`check_suite` event can inject fabricated CI state for a victim's commits, potentially unblocking merges or deploy gating for a stack the attacker has no relationship to. This satisfies the "Critical — cross-repository writes / unauthorized deploy" bucket, since the compromise is entirely mediated by another org's absent secret and is not gated by anything the target repository's owner controls.

### Likelihood Explanation
Exploitability depends only on the operator having at least one organization onboarded to the same Shipit instance without a `webhook_secret` — an explicitly supported, "optional" configuration per Shipit's own setup docs and test fixtures — which is a plausible real-world condition (multi-tenant Shipit instances, orgs that never set the optional secret, or orgs added ad hoc). No credentials, GitHub App keys, or session are required; the `/webhooks` endpoint is intentionally public.

### Recommendation
Bind the identity used for signature verification to the identity actually acted upon: after computing `repository_owner` for signature selection, require that the resolved target `Repository`'s `owner` matches `repository_owner` (or the verified installation) before invoking handlers, and/or make `webhook_secret` mandatory for every configured GitHub App/organization (reject requests from webhook-secret-less orgs, or scope handler processing to only the repositories owned by the exact organization whose secret validated the payload).

### Proof of Concept
1. Configure/observe a multi-tenant Shipit deployment where organization `unsecured-org` has `webhook_secret` unset (per documented optional setting) and a victim stack tracks `victim-org/victim-repo`.
2. As an anonymous attacker, POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "unsecured-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `webhook_secret` is blank for `unsecured-org`.
4. `PushHandler` (via `Handler#repository_name`) resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and enqueues `GithubSyncJob` with the attacker-supplied `expected_head_sha`, mutating state for a repository the attacker never authenticated against.

Note: I could not fully inspect `app/jobs/shipit/github_sync_job.rb` and `app/models/shipit/webhooks/handlers/push_handler.rb` contents before running out of tool iterations, so the exact downstream consequences of the forged `expected_head_sha`/sync (e.g., whether it can directly trigger a deploy versus only updating commit tracking) are inferred from the job name and are not fully confirmed line-by-line.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
