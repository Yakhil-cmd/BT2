### Title
Webhook signature verification key is selected from an unauthenticated payload field, allowing signature bypass for a different organization's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on `repository_owner`, a value read directly from the unauthenticated JSON body (`params.dig('repository', 'owner', 'login')`). The actual repository/stack a given event acts on is instead derived independently, later, from `payload.dig('repository', 'full_name')` inside each `Handler`. Because these two payload fields are never bound to each other, and because `GitHubApp#verify_webhook_signature` treats an unset `webhook_secret` as "always verified", an attacker can pick an organization key with no configured secret to trivially pass verification while targeting a completely different (secured) organization's repository in the same request.

### Finding Description
Signature verification happens in `verify_signature`: [1](#0-0) [2](#0-1) 

`repository_owner` is taken straight from the JSON payload, before any signature has been checked:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
This value selects which `GitHubApp` instance (and thus which `webhook_secret`) is used: [3](#0-2) 

Critically, `verify_webhook_signature` treats an absent secret as automatically verified: [4](#0-3) 
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```

Separately, once the request passes `verify_signature`, the actual repository/stack that a handler operates on is resolved from a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```
The same disconnect exists in the `push`, `pull_request`, `status`/commit-status, and `check_suite` handlers, all of which key off `full_name`/`repository.full_name` from the body rather than the field used for signature-key selection. [6](#0-5) 

This is analogous to the report's root cause: a management-controlled value (`dustThreshold`) with no upper bound lets a trusted operation ("set a dust threshold") be abused to defeat the safety mechanism (auctions) that is supposed to protect user funds. Here, an operator-configured value (per-organization `webhook_secret`, documented as **optional**) that is legitimately absent for one organization becomes the mechanism an attacker abuses: the "authenticating organization" (`repository_owner`, used to pick the verification key) is never bound to equal the "repository actually written" (`repository.full_name`, used by every handler to mutate state). Before the attacker's request: `organization_authenticated == repository_written` was assumed but never enforced. After: an attacker can set `organization_authenticated != repository_written` by choosing an org with a blank secret while still targeting a fully-configured, secured organization's repository.

### Impact Explanation
If a Shipit installation is configured with multiple GitHub organizations (the documented multi-org schema in `lib/shipit.rb`/README) and any one of them has no `webhook_secret` set (webhook secret is explicitly documented as optional in `docs/setup.md`), an unauthenticated attacker can:
1. Send a POST to `/webhooks` with `X-Github-Event: push` (or `status`, `pull_request`, `check_suite`, `membership`, etc.).
2. Set `repository.owner.login` to the org with no secret so `verify_webhook_signature` returns `true` unconditionally, with any or no `X-Hub-Signature` header.
3. Set `repository.full_name` to a real, secured organization's tracked repository.

Because handlers resolve the acted-upon `Stack`/`Repository` purely from `full_name`, this forges GitHub events for a repository whose organization is otherwise properly secured. Depending on event type this can:
- Forge `status` events to mark arbitrary commits as CI-green, defeating Shipit's CI safety gate that governs whether a commit is deployable — enabling an **unauthorized deploy**.
- Trigger `GithubSyncJob`/`push` handling and `pull_request`/`membership` flows for a victim org's repositories/teams without any valid credential.

This crosses the "organization that authenticated versus the repository that is written" binding explicitly called out as in-scope, and the resulting effect (bypassing CI safety checks that gate deploys) maps to the required Critical impact category of "an unauthorized deploy, rollback, or merge."

### Likelihood Explanation
Exploitability depends entirely on operator configuration: it requires a multi-organization Shipit deployment where at least one configured organization has no `webhook_secret`. Since the webhook secret is documented as optional and organizations can be added incrementally, this is a plausible, config-driven, unprivileged-attacker-reachable condition — not a "host application not mounting the engine as documented" scenario, since the multi-org schema and optional secret are both first-class, documented features of the engine itself (`lib/shipit.rb`, `docs/setup.md`). No credential, token, or session of any kind is required by the attacker; only knowledge of the org name lacking a secret (which itself is a `GithubOrganizationUnknown` fallback if not configured at all, but any *configured-without-secret* org qualifies).

### Recommendation
Bind the two fields used across signature verification and target resolution:
- Require `webhook_secret` to be mandatory for every configured organization in the multi-org schema (remove the "return true unless webhook_secret" short-circuit, or make it opt-in only for genuinely single-tenant/no-secret setups), and/or
- After signature verification, assert that `repository.owner.login` (or `organization.login`) used to select the verifying app equals the owner embedded in `repository.full_name` before dispatching to any handler, rejecting the request otherwise.

### Proof of Concept
Given a `secrets.yml` with two orgs configured, e.g.:
```yaml
github:
  attacker-org:
    app_id: ...
    installation_id: ...
    webhook_secret: # left blank/omitted
  victim-org:
    app_id: ...
    installation_id: ...
    webhook_secret: "s3cr3t"
```
An attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<commit sha of a real, pending commit in victim-org/victim-repo>",
  "state": "success",
  "branches": [{ "name": "master" }]
}
```
No `X-Hub-Signature` header (or an arbitrary one) is required because `Shipit.github(organization: "attacker-org")` resolves to a `GitHubApp` whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the signature. The `status` handler then processes the event against `victim-org/victim-repo` (matched via `repository.full_name`), creating a forged green CI status for that commit and potentially unlocking it for deploy in Shipit, despite the request never having been authenticated for `victim-org`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
