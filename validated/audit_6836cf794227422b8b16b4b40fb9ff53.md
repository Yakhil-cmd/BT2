### Title
Front-runnable signer-key authorization lets an unprivileged account steal a stacker's `stack-stx` commitment - (File: stackslib/src/chainstate/stacks/boot/pox-4.clar)

### Summary
`verify-signer-key-sig`/`consume-signer-key-authorization` in `pox-4.clar` authenticate only the *signer-key's* authorization parameters (pox-addr, reward-cycle, topic, period, max-amount, auth-id) via a signature that does not bind the tx-sender/stacker principal or the exact locked amount. Because `signer-sig` is submitted in plaintext inside the stacker's `stack-stx` transaction, any unprivileged third party who observes it in the mempool can copy it and race the original transaction into a block first, consuming the one-time `auth-id` for themselves.

### Finding Description
`stack-stx` calls `consume-signer-key-authorization pox-addr (- first-reward-cycle u1) "stack-stx" lock-period signer-sig signer-key amount-ustx max-amount auth-id` [1](#0-0) , which delegates to `verify-signer-key-sig` and then permanently marks the authorization used via `map-insert used-signer-key-authorizations { signer-key, reward-cycle, topic, period, pox-addr, auth-id, max-amount } true` [2](#0-1) .

The signed message hash covers only `{ pox-addr, reward-cycle, topic, period, auth-id, max-amount }` — it does **not** include the stacker's principal, the exact `amount-ustx` being locked, or any nonce tied to the caller [3](#0-2) . The only amount check is `(asserts! (>= max-amount amount) ...)` [4](#0-3) , so any `amount <= max-amount` is accepted, and any `tx-sender` can present the same `signer-sig`. This is functionally identical to the reported `BridgeRouter` bug class: the "identifier" the honest party expects to consume atomically for their own benefit (here, the signer's one-time authorization tuple) is not bound to the caller, so an unrelated account can win a race to consume it first — an unsigned/unauthorized-for-that-caller stacking action succeeds instead of the intended one.

Concretely:
1. Alice (a stacker) obtains a valid `signer-sig` from a signer authorizing `stack-stx` for `pox-addr`, `reward-cycle`, `period`, `max-amount`, `auth-id`, and broadcasts `stack-stx(amount-ustx, pox-addr, start-burn-ht, lock-period, signer-sig, signer-key, max-amount, auth-id)`.
2. Bob, observing this pending transaction in the mempool, extracts `signer-sig`, `signer-key`, `pox-addr`, `reward-cycle` (implied by current cycle + period), `max-amount`, and `auth-id` — all directly visible as call arguments.
3. Bob submits his own `stack-stx` call with a tiny `amount-ustx` (e.g., `u1`, satisfying `>= max-amount amount`) using the same `signer-sig`/`signer-key`/`pox-addr`/`auth-id`/`max-amount`, and gets it mined first (front-running only requires normal fee-bumping, no special privilege).
4. `verify-signer-key-sig` succeeds for Bob (all checks pass, signature validates), and `used-signer-key-authorizations` is permanently marked used for that exact tuple [5](#0-4) .
5. Bob's own STX get locked (backed by his own funds — not theft of STX itself), but he has now consumed the signer's authorization slot that was intended for Alice.
6. When Alice's original transaction lands, `map-insert` fails and `consume-signer-key-authorization` reverts with `ERR_SIGNER_AUTH_USED` [5](#0-4) , so Alice's `stack-stx` transaction fails entirely — her STX are never locked (the same PoX-Clarity call includes the balance check and lock instruction together, so failure here is atomic and she loses no principal, only the paid transaction fee), but she permanently loses the one-time signer authorization she was relying on for that reward cycle/pox-addr/auth-id combination, and must obtain a brand-new signature/auth-id from the signer to try again.

### Impact Explanation
This maps to "an unsigned stacking action" / signing-weight-abuse class: Bob's stacking action for his own `pox-addr` commitment is validated using a signer authorization that the signer never intended to spend on Bob's behalf. This is a real, reachable griefing/DoS vector against a legitimate stacker's `stack-stx` call and, more importantly, it lets an attacker consume/appropriate a signer's scarce, one-time authorization (`auth-id`) meant for someone else's locking transaction — a signer's committed capacity is diverted without their consent to a use they didn't intend, and the victim's legitimate stacking action is unilaterally blocked by an unprivileged third party. It qualifies as High: "an unsigned stacking action" succeeding for the wrong party, with permanent freezing of the victim's ability to use that specific authorization.

### Likelihood Explanation
The only requirement is visibility of a pending, unconfirmed `stack-stx` transaction (Stacks transactions and their arguments, including `signer-sig`, are visible in the mempool before confirmation) and the ability to submit a competing transaction with higher priority/fee — no special role or key is required, matching "unprivileged-account analog." This makes exploitation straightforward for any bot monitoring the mempool for `stack-stx`/`stack-extend`/`stack-increase`/`stack-aggregation-commit` calls, all of which use the same `consume-signer-key-authorization` pattern.

### Recommendation
Bind the authorization to the intended caller: include `tx-sender` (the stacker) as part of `get-signer-key-message-hash`, or require the caller/stacker's principal as an explicit argument checked by `verify-signer-key-sig`/`consume-signer-key-authorization`, so a copied signature cannot be replayed by an unrelated principal. Alternatively/additionally, key `used-signer-key-authorizations` on `(stacker, ...)` rather than solely on signer/pox-addr/cycle/topic/period/auth-id/max-amount so consumption by an unintended party cannot block the legitimate one.

### Proof of Concept
1. Signer produces `signer-sig` over `{pox-addr, reward-cycle: R, topic: "stack-stx", period: P, auth-id: A, max-amount: M}` for stacker Alice, amount `X <= M`.
2. Alice broadcasts `stack-stx(X, pox-addr, start-burn-ht, P, (some signer-sig), signer-key, M, A)`.
3. Bob copies `(signer-sig, signer-key, pox-addr, M, A)` from Alice's mempool tx and broadcasts, with higher fee, `stack-stx(u1, pox-addr, start-burn-ht, P, (some signer-sig), signer-key, M, A)` from his own account.
4. Bob's tx is mined first: `verify-signer-key-sig` passes (u1 <= M, signature recovers to `signer-key`), `used-signer-key-authorizations` entry for `{signer-key, R, "stack-stx", P, pox-addr, A, M}` is set [2](#0-1) ; Bob's own `u1` STX get locked under `pox-addr`.
5. Alice's tx is then mined: `consume-signer-key-authorization` -> `map-insert` returns false -> `(err ERR_SIGNER_AUTH_USED)` [5](#0-4)  -> entire `stack-stx` call fails, Alice's STX are never locked, and she must re-request a new signer authorization to proceed, having lost the fee for the failed transaction and the use of that authorization slot.
