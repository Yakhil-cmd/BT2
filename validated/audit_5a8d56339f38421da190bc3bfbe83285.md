### Title
`DenyReserveTransferToRelayChain` barrier is applied without recursive (nested-instruction) protection on multiple system chains, allowing a signed user to smuggle a reserve-transfer to the Relay Chain inside `SetAppendix`/`SetErrorHandler` - ([File: system-parachains/asset-hubs/asset-hub-kusama/src/xcm_config.rs], [system-parachains/asset-hubs/asset-hub-polkadot/src/xcm_config.rs], and others)

### Summary
`DenyReserveTransferToRelayChain` is used bare (not wrapped in `DenyRecursively`) in the `Barrier` type of Asset Hub Kusama/Polkadot, Bridge Hub Kusama, Collectives Polkadot, Coretime Kusama/Polkadot, People Kusama/Polkadot, and Encointer, while Bridge Hub Polkadot and Bulletin Polkadot explicitly wrap the same deny-filter in `DenyRecursively<...>`. This inconsistency indicates the bare filter only inspects the top-level instruction sequence of an XCM program and does not recurse into nested programs carried by `SetAppendix`/`SetErrorHandler`, letting a `DepositReserveAsset`/`InitiateReserveWithdraw` targeting the Relay Chain evade detection when nested inside those instructions.

The existence of `DenyRecursively` as a distinct wrapper (only added on two chains) strongly indicates that the bare `DenyReserveTransferToRelayChain` filter (from the upstream `xcm-builder` crate, not vendored in this repo) pattern-matches only the top-level instruction list of the incoming `Xcm` program, and does not descend into the nested `Xcm` programs carried inside `SetAppendix(Xcm)` / `SetErrorHandler(Xcm)`. `DenyRecursively` was introduced precisely to close that gap by re-applying the inner filter to nested appendix/error-handler programs.

Exploit flow on an affected chain (e.g. Asset Hub, which is the exact scope named by the question and where the reserve for DOT/KSM has intentionally moved off the Relay Chain per the AHM changelog entry, making reserve-transfers to the Relay Chain specifically the thing the barrier must block):
1. A signed user calls `pallet_xcm::execute` (or crafts an incoming XCM through an already-permitted route) with a program whose top-level instructions satisfy `AllowTopLevelPaidExecutionFrom<Everything>` (e.g. `WithdrawAsset`, `BuyExecution`), so the barrier's fallback tuple lets it through once `DenyThenTry`'s deny-stage returns "not denied."
2. The attacker places `SetAppendix(Xcm(vec![DepositReserveAsset { assets, reserve: Location::parent(), xcm }]))` (or the equivalent inside `SetErrorHandler`) as one of the top-level instructions.
3. `DenyReserveTransferToRelayChain::should_execute` scans only the top-level `message.0` instruction list; it does not find `DepositReserveAsset`/`InitiateReserveWithdraw` directly in that list (it is embedded as data inside `SetAppendix`'s payload), so the deny-stage of `DenyThenTry` does not trigger, and the barrier as a whole returns `Ok`.
4. The XCM executor proceeds to execute the top-level program and, per XCM semantics, unconditionally executes the appendix (or the error handler on error), which now runs the `DepositReserveAsset`/`InitiateReserveWithdraw` targeting the Relay Chain — the exact operation the barrier was supposed to prevent.

This is a genuine gap because the bare filter is a syntactic top-level pattern match, and the barrier-must-not-be-bypassed invariant is broken specifically for chains lacking the `DenyRecursively` wrapper.

### Impact Explanation
On Asset Hub, `DenyReserveTransferToRelayChain` exists specifically to stop reserve-based asset movement to the Relay Chain now that DOT/KSM's reserve location has moved to Asset Hub as part of the Asset Hub Migration (per the repository's own changelog note about disabling `reserve_asset_transfer` for DOT/KSM). Bypassing the barrier via nested `SetAppendix`/`SetErrorHandler` on the affected chains lets an unprivileged, signed user execute the exact reserve-transfer-to-Relay-Chain operation the AHM safeguard is meant to block, via the `pallet_xcm::execute` extrinsic path, independent of the extrinsic-level check added for `limited_reserve_transfer_assets`/`reserve_transfer_assets` (which only guards those two specific dispatchables, not raw `execute`). This matches the scoped impact: unauthorized reserve-asset movement to the Relay Chain outside the intended teleport-only path.

### Likelihood Explanation
Feasibility depends on details I could not verify from the indexed contents of this repository alone: (a) the exact upstream implementation of `DenyReserveTransferToRelayChain::should_execute` (defined in the external `xcm-builder`/`staging-xcm-builder` crate, not vendored here, so I cannot directly confirm it never recurses into nested instructions — this is inferred from the parallel existence of `DenyRecursively`), (b) whether `pallet_xcm::execute` is enabled/permitted for ordinary signed accounts on each affected chain (`SafeCallFilter`/`XcmExecuteFilter` configuration), and (c) whether `IsReserve`/`AssetTransactor` configuration on the Relay Chain side would actually accept and process a `ReserveAssetDeposited`/`WithdrawAsset` message from Asset Hub for DOT in a way that produces bad accounting, versus merely trapping the assets. These are runtime-wiring details not fully resolvable from the indexed snippets I retrieved.

### Recommendation
Wrap `DenyReserveTransferToRelayChain` in `DenyRecursively<...>` consistently across all affected chains' `Barrier` definitions (Asset Hub Kusama/Polkadot, Bridge Hub Kusama, Collectives Polkadot, Coretime Kusama/Polkadot, People Kusama/Polkadot, Encointer), matching the pattern already used in Bridge Hub Polkadot and Bulletin Polkadot.

### Proof of Concept
Because I could not confirm the exact upstream `should_execute` behavior of `DenyReserveTransferToRelayChain` or the `SafeCallFilter`/execute-permission wiring for each affected chain from the indexed repository content, and per the audit rules I must not speculate beyond what the code shows, I present this as a **conditional/unconfirmed finding** rather than a fully proven one. A concrete test to confirm or refute it would be an xcm-emulator test:

```rust
#[test]

    //   SetAppendix(Xcm(vec![
    //     DepositReserveAsset { assets: All.into(), reserve: Location::parent(), xcm: Xcm::default() }
    //   ])),
    // ])

    // Assert: execution result is an error / assets are NOT deposited to the Relay Chain's
    // sovereign-account-derived location; specifically assert Barrier::should_execute returns Err
    // for this program, matching behavior already asserted for the plain top-level case.
}
```

Given the uncertainty noted above, I flag this as **requiring verification against the actual `xcm-builder` implementation** (outside this repo) before treating it as a confirmed, exploitable bug rather than a configuration inconsistency that may or may not be exploitable depending on upstream filter internals.
