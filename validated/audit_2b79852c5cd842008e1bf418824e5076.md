### Title
`StatusHandler#process` applies a `status` webhook's `context`/`state` to every commit sharing a SHA, ignoring which repository authenticated the webhook - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire database and writes the incoming GitHub status to all of them, with no repository/stack scoping, even though the base `Handler` class already provides a `stacks` helper scoped to `payload['repository']['full_name']` that other handlers could use. Because `WebhooksController#verify_signature` only authenticates a webhook against the payload's `repository.owner.login` (organization-level secret), not the specific repository, an attacker who controls any repository in the same GitHub organization as a victim stack can push/fetch the exact same commit object (SHAs are content-addressed) into their own repo, set a status on it via the GitHub API, and have Shipit apply that `release/gate: failure` status to the victim stack's identical-SHA commit.

### Finding Description
Broken binding (should hold, does not):
`status.repository == commit.stack.repository` for every `Shipit::Status` record created from a webhook.

Code path:
1. `Shipit::WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e. keyed only by the organization/owner login extracted from the payload - not by the specific repository name.
2. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This queries `Commit` by bare `sha` with zero repository/stack filter, even though `Shipit::Webhooks::Handlers::Handler` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) exposes a `stacks` helper explicitly scoped by `Repository.from_github_repo_name(repository_name)` for exactly this purpose - `StatusHandler` simply doesn't use it.
3. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) then calls `add_status`, which recomputes `Status::Group` and, via `Status::Common#required?`/`#blocking?` (`app/models/shipit/status/common.rb:46-52`), can flip `commit.deployable?`/`commit.blocked?` and fire `deployable_status`/`schedule_merges` (`app/models/shipit/commit.rb:366-386`).

Exploit flow: attacker owns some repository in the same GitHub organization as the victim stack's repository (any member/owner of that org, not necessarily a maintainer of the victim's specific repo). The attacker fetches the victim's public commit (identical Git object ⇒ identical SHA-1) into their own repo, then uses the GitHub Statuses API on their own repo to post `context: "release/gate", state: "failure"` for that SHA. GitHub signs and delivers this as a genuine `status` webhook for the attacker's repository, using the org-level secret the attacker's repo shares with every other repo in that organization. `verify_signature` accepts it because it only checks the organization, and `StatusHandler#process` then applies the failure to every `Commit` row with that SHA - including the victim stack's row - regardless of which repository actually sent the webhook.

Existing guards fail because: `verify_signature` authenticates "an org member sent this", not "this specific repository sent this"; `ExplicitParameters` only validates payload shape, not repo linkage; and no model validation ties `Status#stack_id`/`commit.stack` back to `params.repository.full_name`.

### Impact Explanation
A cross-tenant write: a webhook that only proves authorship for repository A is used to mutate `Commit`/`Status` state for repository B's stack. If the victim stack requires `release/gate` (`Commit#required_statuses`, delegated to `stack`), the injected `failure` status makes `Status::Common#required?`/`#blocking?` true for that context, flipping `commit.deployable?` (`app/models/shipit/commit.rb:227-229`) and `commit.blocked?` (`app/models/shipit/commit.rb:231-237`), which can block a legitimate deploy or, on the reverse transition, unblock one via `stack.schedule_merges` (`app/models/shipit/commit.rb:383`). This is repeatable against any stack whose repository shares an organization with any repository the attacker controls, and against any commit SHA the attacker can reproduce locally (any public commit). This matches the "payload for one repository mutating another's stack/commit" and "unauthorized deploy/rollback" Critical impact categories.

### Likelihood Explanation
Preconditions: attacker needs a repository within the same GitHub organization/owner as the victim stack (a normal, unprivileged capability for org members, or trivial if the org allows public repo creation), and the victim commit must be reachable/forkable so the attacker can reproduce the identical SHA in their own repo. No Shipit secrets, sessions, or API tokens are required - `verify_signature` is satisfied by a real, GitHub-signed delivery. The attack is fully repeatable per SHA/context and requires no timing races.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, e.g. use the base `Handler#stacks` helper (`stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of the unscoped `Commit.where(sha: params.sha)`, and consider making `WebhooksController#verify_signature`/`Handler` reject payloads whose `repository.full_name` doesn't correspond to a repository actually associated with the verified organization/app installation.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status for a shared SHA leaks across repositories/stacks" do
  attacker_repo = shipit_repositories(:shipit) # repo A, same org as victim
  victim_stack  = shipit_stacks(:cyclimse)     # repo B, review_stacks_enabled: false, requires 'release/gate'
  shared_sha    = 'a' * 40

  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: 'shared', author: shipit_users(:shipit), committer: shipit_users(:shipit), authored_at: Time.now, committed_at: Time.now)
  assert_predicate victim_commit, :deployable?

  payload = {
    'sha' => shared_sha,
    'state' => 'failure',
    'context' => 'release/gate',
    'repository' => { 'full_name' => attacker_repo.github_repo_name, 'owner' => { 'login' => attacker_repo.owner } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  assert_equal 'failure', victim_commit.status.state # binding broken: attacker's repo webhook mutated victim stack's commit
  refute_predicate victim_commit, :deployable?
end
```
This demonstrates `status.repository == commit.stack.repository` is violated: a webhook payload naming `attacker_repo` still mutates `victim_stack`'s commit because `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) queries `Commit` by bare SHA with no repository/stack filter.
