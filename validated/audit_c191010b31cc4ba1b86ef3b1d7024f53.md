### Title
`ERC20Transactor` credits/debits the XCM holding register with the requested amount instead of the amount actually moved by the ERC20 contract, so fee-on-transfer or non-standard ERC20 tokens cause value mismatches - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` call an arbitrary ERC20 contract's `transfer` function and, if the call does not revert and returns `true`, unconditionally treat the *originally requested* `amount` as having moved — without ever reading the contract's balance before/after to confirm. [1](#0-0) [2](#0-1)  This is the same violated invariant as the reported bug class (amount requested is assumed to equal amount actually transferred by an external token contract), but manifesting as silent value-accounting drift rather than a hard revert, because unlike the Vyper `LimitOrders`/`Dca` contracts, this transactor doesn't even re-derive the amount for a follow-on call — it just fabricates an `AssetsInHolding` credit of the pre-call `amount`.

### Finding Description
The `ERC20Transactor` is a `TransactAsset` implementation registered in `AssetTransactors` on Asset Hub Westend, used by pallet-xcm/xcm-executor whenever an XCM program references an asset identified by an `AccountKey20` location matching `assets_common::ERC20Matcher`. [3](#0-2) 

`withdraw_asset_with_surplus`:
- Determines `(asset_id, amount)` from the XCM `Asset` via the matcher. [4](#0-3) 
- Calls `IERC20::transferCall{ to: checking_address, value: amount }` on the arbitrary contract at `asset_id` via `pallet_revive::Pallet::<T>::bare_call`. [5](#0-4) 
- If the call doesn't revert and decodes to `true`, it returns `Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))` — i.e., it credits the XCM holding register with the full requested `amount`, regardless of how many tokens actually landed in the checking account. [6](#0-5) 

`deposit_asset_with_surplus` mirrors this: it transfers `amount` from the checking account to the beneficiary via `IERC20::transferCall`, and on success (`true`, no revert) treats the deposit as fully successful with no reduction of the returned "unspent" assets, again without checking that `amount` tokens actually reached the beneficiary. [7](#0-6) 

Any account can permissionlessly deploy an arbitrary Solidity/ink! contract via `pallet-revive` (no privileged role required) implementing `transfer()` that returns `true` while moving less (fee-on-transfer) or more than `value` — this is exactly analogous to the reported bug's "fee deducted during transfer, fixed amount used downstream," except here the mismatch is silently absorbed into XCM's internal accounting instead of causing the router call to revert. Because `ERC20Matcher::matches_fungibles` derives `asset_id` directly from the `AccountKey20` in the `Asset` location (per the `ERC20Transactor` PR description: "asset ids of the form `{parents: 0, interior: X1(AccountKey20{key, network})}` will be matched... and the corresponding `transfer` function will be called in the smart contract whose address is `key`" [8](#0-7) ), an attacker fully controls which contract code executes for a given asset id — there is no allowlist enforced by the transactor itself.

Concretely, a user can:
1. Deploy a fee-on-transfer ERC20 contract (e.g., `transfer()` moves `value * 99/100` to `to` but returns `true`).
2. Submit `pallet_xcm::execute` with an XCM program that does `WithdrawAsset` for this ERC20 asset with `value = amount`, followed by `DepositAsset` to a beneficiary.
3. `withdraw_asset_with_surplus` sees the checking account received only `0.99 * amount` tokens but still credits `AssetsInHolding` with the full `amount`. On the `deposit_asset_with_surplus` leg, only `0.99 * amount` (or less, if the fee also applies here) is actually transferred to the beneficiary, but the executor's internal ledger (and any `Sent`/`Attempted`/refund logic derived from the holding register) still believes `amount` was moved.

This breaks the checked invariant "assets registered in the XCM holding register equal assets actually held/movable," producing an accounting drift between the checking-account ERC20 balance and what the XCM executor believes was withdrawn/deposited.

### Impact Explanation
This is a genuine integrity break in cross-asset accounting: the XCM executor's holding register can diverge from the real ERC20 balances held by `ERC20TransfersCheckingAccount`, for any asset that matches `ERC20Matcher` — which is any ERC20-shaped contract, deployable by anyone with no privilege. Depending on the direction of the fee (which the attacker fully controls via the fee-on-transfer contract they write), this can:
- Leave value "trapped"/lost in the checking account when withdrawing less than credited (loss for downstream steps expecting the full amount), or
- Allow crediting more XCM-internal value than actually moved out of the source account (in principle, if the contract's `transfer` moves more than requested while still returning `true`), which could be leveraged to inflate the perceived balance of assets in a multi-step XCM program relative to what backs it in the checking account.

Because the checking account is a shared, chain-wide pooling account for *all* ERC20 XCM transfers, systematically abusable discrepancies here affect the shared invariant that "checking account ERC20 balance == sum of net amounts registered via XCM," which other users' withdrawals/deposits rely on implicitly. This lands as a Medium-severity integrity/accounting issue (similar severity class to the original report), not a Critical direct theft, because: exploiting it to extract value still requires further XCM composition/timing and the attacker only controls their own contract's fee/behavior, not other users' funds directly, and a full drain scenario would need more detailed exploration of downstream refund/consumption logic that operates on the (wrong) `AssetsInHolding` amount.

### Likelihood Explanation
Likelihood is Medium-to-High for reachability: any account can deploy a contract via `pallet-revive`'s permissionless deploy path and construct an XCM `execute()` call (or `pallet_xcm::send`/`transfer_assets` targeting a destination that uses this transactor) referencing that contract as an `AccountKey20` asset — no governance, no privileged role, and no forged inputs are needed. `ERC20Transactor` is already wired into `AssetTransactors` on Asset Hub Westend today. [9](#0-8)  The actual monetary impact requires the attacker to control (or find) a fee-on-transfer/non-conforming ERC20 with the right rounding behavior, which is realistic for arbitrary user-deployed contracts but is a step beyond mere reachability, and I was not able to fully trace how the executor consumes a wrongly-sized `AssetsInHolding` credit downstream (refund/`ClearOrigin`/further hops) within the tool budget available, so the exact end-to-end loss magnitude is not fully confirmed.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the ERC20 contract's `balanceOf` for the relevant account (checking account or beneficiary) immediately before and after the `transfer` call, and use the *actual delta* — not the requested `amount` — when constructing the `AssetsInHolding` credit or determining the deposited amount. Reject (return `XcmError::FailedToTransactAsset`) if the delta is less than the requested `amount` for a withdraw, or handle any surplus explicitly, mirroring the standard fee-on-transfer mitigation the original report recommends ("check balances before and after... use the difference").

### Proof of Concept
I was not able to execute a live PoC in this environment (no filesystem/terminal access in ask-only mode). Static evidence supporting the analog:
- `ERC20Transactor` calls `IERC20::transferCall` and, on non-revert success, blindly constructs `Erc20Credit(amount)`/treats `amount` as moved without any balance-delta check: [1](#0-0) [10](#0-9) 
- This transactor is live in the Asset Hub Westend runtime's `AssetTransactors` tuple. [9](#0-8) 
- `pallet-revive` contract deployment is a normal, permissionless user entry point (confirmed via existing test fixtures using `bare_instantiate`/ERC20 fixtures in `asset-hub-westend/tests/tests.rs`), so an attacker-authored fee-on-transfer contract is reachable without any privileged role. [11](#0-10) 

A concrete integration-test PoC (deploy a fee-on-transfer ERC20 via `bare_instantiate`, run an `execute()` XCM `WithdrawAsset`/`DepositAsset` program through `ERC20Transactor`, and assert `Erc20Credit`/beneficiary balance diverges from the checking account's actual ERC20 balance change) was not run; this would need to be executed in a real Rust/FRAME test harness by a follow-up engineering task to confirm the exact magnitude of drift and whether it is exploitable for net value extraction beyond an accounting mismatch.

			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);

		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());

			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};

			Some(inner) => inner,

		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));

		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,

			);

		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);

			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");

						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)

#[test]
fn withdraw_and_deposit_erc20s() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 100_000_000_000_000_000u128;
	sp_tracing::init_for_tests();

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));
		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		let code = compile_module_with_type("MyToken", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let sender_balance_before = <Balances as fungible::Inspect<_>>::balance(&sender);

		let erc20_transfer_amount = 100u128;
		let wnd_amount_for_fees = 10_000_000_000_000u128;
		// Actual XCM to execute locally.
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.refund_surplus()
			.deposit_asset(AllCounted(1), sender.clone())
			.build();
		assert_ok!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(600_000_000_000, 15 * 1024 * 1024),
		));

		// Revive is not taking any fees.
		let sender_balance_after = <Balances as fungible::Inspect<_>>::balance(&sender);
		// Balance after is larger than the difference between balance before and transferred
		// amount because of the refund.
		assert!(sender_balance_after > sender_balance_before - wnd_amount_for_fees);

		// Beneficiary receives the ERC20.
		let beneficiary_amount =
			<Revive as fungibles::Inspect<_>>::balance(erc20_address, &beneficiary);
		assert_eq!(beneficiary_amount, erc20_transfer_amount);
	});
