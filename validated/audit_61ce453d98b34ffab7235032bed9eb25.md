### Title
Webhook signature is verified against a secret keyed by the payload-supplied organization, but downstream handlers act on a repository from the same unverified payload - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In multi-tenant configurations (`Shipit.github_organizations` > 1, e.g. `secrets.github` with several org keys), `WebhooksController#verify_signature` selects which `GitHubApp`/`webhook_secret` to verify the request against solely from `repository_owner`, a value read straight out of the untrusted, attacker-suppliable JSON body [1](#0-0) [2](#0-1) . Once the HMAC check passes, the entire raw payload is dispatched to handlers unmodified [3](#0-2) , and those handlers resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` — a field that is never cross-checked against the org used for signature verification [4](#0-3) .

### Finding Description
The binding that should hold is: **organization that authenticated the request == organization owning the repository the handler writes to**. In this engine that equality is never enforced.

- `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` (or `params.dig('organization','login')`) and fetches `Shipit.github(organization: repository_owner)`, whose `webhook_secret` is then used to validate `X-Hub-Signature` against the raw body [1](#0-0) .
- `Shipit.github(organization:)` looks up a completely independent secret per organization key in `secrets.github` [5](#0-4) .
- After verification, `create` hands the *entire* JSON body to every registered handler for the event, with no re-derivation or consistency check between the org used for verification and any other field in the body [3](#0-2) .
- `PushHandler` (and other handlers via `Handler#stacks`/`#repository_name`) resolve which `Stack`/`Repository` to act on purely from `payload.dig('repository', 'full_name')` [4](#0-3) [6](#0-5) , and `Repository.from_github_repo_name` simply splits `owner/name` from that field with no relation back to `repository_owner` used earlier [7](#0-6) .

Because `repository.owner.login` (used only to pick the verification key) and `repository.full_name` (used to pick the acted-upon repo/stack) are two independent JSON fields under full control of whoever crafts the HTTP request body, an attacker who legitimately controls a webhook for **any one** organization configured in this Shipit instance (i.e., who knows that organization's `webhook_secret`, which GitHub org/repo admins routinely see or set themselves when configuring the webhook) can:
1. Set `repository.owner.login` (or `organization.login`) to their own org, so `verify_signature` selects a `GitHubApp` whose secret they know and signs the raw body correctly with it.
2. Set `repository.full_name` (and other event fields such as `ref`, `after`) to point at a stack belonging to a **different**, victim organization/repository also hosted on the same Shipit instance.

This is the same class of bug as the referenced Frankencoin finding: a field that is *acted upon* (`repository.full_name`, driving which stack gets synced/deployed) is never *covered* by the check that is supposed to authorize the request (verification is keyed by `repository.owner.login`, a sibling field with no cryptographic or logical tie to `full_name`).

### Impact Explanation
This is a cross-repository/cross-tenant write: an attacker with legitimate control of one organization's webhook (no Shipit session, no `ApiClient` token, no privileged Shipit account) can forge `push`/`status`/`check_suite` events attributed to a completely different, victim repository configured on the same shared Shipit deployment. This can trigger `GithubSyncJob` and downstream deploy-eligibility state changes (e.g. `stack.sync_github`) for a stack the attacker does not own or have any access to, i.e., an unauthorized cross-repository action driven entirely by a forged, cross-tenant webhook payload. This matches the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires the instance to run a multi-organization Shipit configuration (multiple entries under `secrets.github`, as exercised in `test/dummy/config/secrets_double_github_app.yml` and `test/unit/shipit_test.rb`) [8](#0-7) . In that (documented, supported) topology, any org admin who can configure their own org's webhook secret meets the described "unprivileged-attacker" bar relative to the victim org — they need no credentials belonging to the victim, no Shipit account, and no GitHub App private key.

### Recommendation
After signature verification, re-derive `repository_owner` (or the full `repository.full_name`) strictly from the same value used to select the verification key, and reject the request if the handler-facing repository/organization differs from the one whose secret validated the signature. Concretely, `WebhooksController#create`/`Handler#repository_name` should assert that `payload.dig('repository','owner','login')` (already trusted for verification) matches the owner segment of `payload.dig('repository','full_name')` before dispatching to handlers, or better, pass the verified organization explicitly into handlers instead of re-reading it from the unverified body.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `attacker-org` and `victim-org`, each with its own `webhook_secret` (multi-tenant `secrets.github` as in `secrets_double_github_app.yml`).
2. Attacker legitimately owns `attacker-org` and knows its `webhook_secret` (they configured the webhook themselves).
3. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`), verifies successfully with the attacker's own known secret [1](#0-0) .
6. `create` dispatches the full payload to `PushHandler`, which resolves `stacks` from `payload.dig('repository','full_name') == "victim-org/victim-repo"` [4](#0-3)  and calls `stack.sync_github(expected_head_sha: params.after)` for `victim-org/victim-repo`'s stacks [6](#0-5)  — despite the attacker never having authenticated as, or been authorized for, `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
