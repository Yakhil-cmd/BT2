### Title
AA author can set `bounce_fees` to an unbounded value, letting the AA confiscate nearly all funds sent by a trigger sender when a bounce occurs - ([File: aa_composer.js])

### Summary
The Y2K report shows an admin who can raise `withdrawalFee` to 100% and thereby divert user funds that are already locked into the protocol. In ocore, the closest reachable analog is an Autonomous Agent (AA) author, who is only required to keep `bounce_fees.base` above a small minimum, but is otherwise free to set it as high as `constants.MAX_CAP`. Because the bounce logic subtracts the fee from whatever the trigger sender attached before refunding the remainder, a maliciously/aggressively configured AA can keep almost the entirety of a trigger sender's payment whenever the AA's business logic bounces (an event fully controlled by AA code and quite common — failed conditions, races on shared state vars, insufficient balance checks, etc.), instead of returning the funds.

### Finding Description
When validating an AA definition, `bounce_fees` is checked only for a lower bound and an absolute upper bound, with no bound relative to the amount actually sent by the trigger sender: [1](#0-0) 

```
if ('bounce_fees' in template){
    ...
    var fee = template.bounce_fees[asset];
    if (!isNonnegativeInteger(fee) || fee > constants.MAX_CAP)
        return callback("bad bounce fee: "+JSON.stringify(fee));
    ...

        return callback("too small base bounce fee: "+template.bounce_fees.base);
}
```
`constants.MAX_CAP` is an extremely large cap (near the total whitebytes supply), while `constants.MIN_BYTES_BOUNCE_FEE` is only 10000 bytes: [2](#0-1) 

At execution time, when a trigger causes the AA to bounce, `handleTrigger`'s `bounce()` function deducts `bounce_fees[asset]` from the trigger's outputs before sending any refund to the sender. If the fee equals or exceeds the amount sent, the sender receives nothing back at all and the full amount stays with the AA: [3](#0-2) 

```
if ((trigger.outputs.base || 0) < bounce_fees.base)
    return finish(null);
...
for (var asset in trigger.outputs) {
    var amount = trigger.outputs[asset];
    var fee = bounce_fees[asset] || 0;
    if (fee > amount)
        return finish(null);
    if (fee === amount)
        continue;
    var bounced_amount = amount - fee;
    messages.push({app: 'payment', payload: {asset: asset, outputs: [{address: trigger.address, amount: bounced_amount}]}});

```
An earlier check also enforces bounce-fee coverage before running the AA logic at all: [4](#0-3) 

Because `bounce_fees` has no cap proportional to typical or expected trigger amounts (only the global `MAX_CAP` ceiling and a tiny floor), an AA author can define `bounce_fees.base` (and any asset fee) to be as large as almost the entire supply, or simply set it comparable to the amounts the AA legitimately expects to receive. Whenever the AA's own logic decides to bounce (a decision entirely controlled by the AA's oscript, e.g. concurrent state-var races, unmet conditions, or deliberately crafted "trap" branches), the trigger sender's coins are absorbed by the AA rather than refunded, mirroring the way the Y2K admin diverted user funds by raising `withdrawalFee`.

### Impact Explanation
Any unprivileged user who sends bytes/assets to trigger an AA is exposed to losing that entire payment if the specific execution path bounces, because the bounce fee is not bounded relative to the trigger amount. A malicious or careless AA author can design (or subsequently exploit ambiguous corner cases in) an AA so that legitimate/expected trigger flows routinely bounce while `bounce_fees` is set high, effectively converting ordinary interactions into fund confiscation. This constitutes AA fund loss for the trigger sender, analogous to the admin using an uncapped fee parameter to steal locked user funds in the referenced report.

### Likelihood Explanation
Likelihood is moderate: deploying an AA with an inflated `bounce_fees` and business logic prone to bouncing is trivial and requires no special privilege — any address can author and publish such an AA. The main mitigating factor is that `bounce_fees` are fixed at AA-definition time and publicly visible before a user chooses to interact, unlike the Y2K case where the fee could be raised on an epoch users had already committed to. This reduces surprise-factor but does not remove the underlying protocol gap: there is no relative cap tying `bounce_fees` to actual payment sizes, so unsuspecting users interacting with an AA whose definition they haven't carefully audited (or which changes behavior under edge-case conditions after they've already sent funds within the same trigger unit) can still lose their full payment.

### Recommendation
Introduce a bound on `bounce_fees` relative to the amounts an AA can realistically expect (e.g., cap the fee as some multiple of `MIN_BYTES_BOUNCE_FEE`, or require the fee to be small relative to typical/definitional AA state), or require that `bounce_fees` cannot exceed a fraction of the trigger output rather than being validated only against the fixed, very large `MAX_CAP`. Additionally, consider surfacing bounce-fee risk more prominently to end users/wallets (e.g., displaying the max possible loss) before they send funds to an AA address.

### Proof of Concept
1. Author defines an AA with `bounce_fees: { base: constants.MAX_CAP }` (or any large multiple of the amount it expects to receive) and business logic containing at least one branch that calls `bounce(...)` under conditions reachable by ordinary triggers (e.g. a race on a shared state var, or insufficient counterpart liquidity).
2. Publish the AA (validated successfully by `aa_validation.js` since the fee is `<= constants.MAX_CAP` and `>= constants.MIN_BYTES_BOUNCE_FEE`).
3. A user sends a trigger unit with `trigger.outputs.base` amount X (X > `bounce_fees.base`) expecting normal execution.
4. Due to the deliberately crafted or naturally occurring bounce condition, `handleTrigger` invokes `bounce()`; since `fee` (== X or close to X) is subtracted from `amount`, the sender receives back `amount - fee` (potentially 0), while the full amount is retained in the AA's balance under its author's control (test harness at `aa_composer.test.js:120-155` demonstrates the exact "less than bounce fees" / retained-funds code path).

**Note on confidence:** This analog required inference because ocore does not have a literal per-epoch "withdrawal fee" concept; `bounce_fees` is the closest structurally similar unbounded-fee mechanism reachable by an unprivileged AA author. Unlike the original report, `bounce_fees` are immutable and public at AA definition time, so the "retroactive fee hike on already-locked funds" element of the original bug is not perfectly reproduced — this is the main uncertainty in applying the analog with full confidence.
