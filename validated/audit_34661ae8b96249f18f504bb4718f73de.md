### Title
Full plaintext of decrypted device messages (including private-payment blinding secrets) written to console log - (File: device.js)

### Summary
`decryptPackage()` in `device.js` logs the entire decrypted device-message body in plaintext on every inbound message, regardless of message subject or sensitivity, mirroring the ansible `no_log` bypass class of CVE-2021-20191 where secrets are disclosed via default logging.

### Finding Description
`decryptPackage()` decrypts the AES-GCM `encrypted_package` sent by any correspondent/hub-relayed device and, immediately after successful decryption, runs `console.log("decrypted: "+decrypted_message);` before even parsing the JSON [1](#0-0) . This call is unconditional — there is no allow-list of "safe" subjects, no redaction, and no `conf`-gated flag. `handleJustsaying()`'s `hub/message` case calls `decryptPackage` for every device message addressed to the node, including from already-paired correspondents and, for a whitelisted set of subjects (`pairing`, `my_xpubkey`, `wallet_fully_approved`), even non-correspondents [4](#0-3) .

Device messages of subject `"sign"` (built by `sendOfferToSign`) embed `private_payloads` — the actual private-asset payloads containing blinding factors and spend proofs needed to redeem private/indivisible outputs [2](#0-1) . Messages of subject `"private_payments"` carry full chains of private payment elements forwarded between cosigners/wallet members [3](#0-2) , and `sendMultiPayment`'s textcoin flow generates and forwards wallet-spending mnemonics through the same device-messaging channel [5](#0-4) . All of this plaintext content is dumped to `console.log` by `decryptPackage` before any business logic even inspects it.

### Impact Explanation
Any node that captures stdout/console output into a shared or persisted log (a common operational practice, e.g. via process managers, log aggregation, or crash dumps) will retain private-payment blinding factors, spend proofs, and textcoin mnemonics in plaintext. Anyone with read access to those logs — which is a much larger trust boundary than "who can decrypt the device message" — can reconstruct the ability to spend the associated private outputs or claim textcoins, i.e., unauthorized spending / theft of funds, without needing the recipient device's private key at all.

### Likelihood Explanation
The log call fires on every successfully decrypted device message with no gating, so it is triggered automatically and continuously as part of normal wallet operation whenever a paired correspondent or private-payment counterparty sends any message (payments, signing offers, textcoins). No attacker action beyond normal protocol use (sending a message to a paired device) is required to cause the sensitive data to be written to the log; the only additional requirement for exploitation is that the operator's log output is collected/retained somewhere accessible to the attacker.

### Recommendation
Remove or gate the `console.log("decrypted: "+decrypted_message)` line in `decryptPackage()` behind a debug-only flag that is disabled by default, and ensure any debug logging in this path redacts fields known to carry secrets (`private_payloads`, `chains`, `mnemonic`, blinding values) before printing.

### Proof of Concept
1. Pair two wallet instances (device A and device B) and log stdout of device B to a file, as is typical for services run under `pm2`/`systemd`/docker log drivers.
2. From device A, send a private-asset payment or textcoin to device B (`sendMultiPayment` with `asset` set to a private asset, or a textcoin output).
3. Device B's `handleJustsaying` → `decryptPackage` path executes and prints the full decrypted JSON body, including `private_payloads`/`chains`/`mnemonic`, to console/log at `device.js:466`.
4. Anyone with read access to device B's log file can extract the blinding factors/mnemonic and redeem the private output or claim the textcoin without device B's cooperation.
