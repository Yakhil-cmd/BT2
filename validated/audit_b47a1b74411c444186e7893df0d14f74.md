### Title
Asset issuer's mutable attestor-list update (`asset_attestors`) can permanently freeze an AA's holdings of a `spender_attested` asset - (File: `validation.js`)

### Summary
Analogous to EigenLayer's `thirdPartyTransfersForbidden` flag, which a strategy whitelister can toggle post-hoc to permanently break third-party withdrawal queueing for any dependent protocol (Rio), ocore assets support a `spender_attested` flag whose enforcement list (`attestors`) is **not fixed at asset creation** — the asset definer can update it at any later time via an `asset_attestors` message. If an autonomous agent (AA) holds a balance of such an asset and the definer subsequently removes the AA's own address (or all addresses the AA can output to) from the attestor list, every future attempt by the AA to transfer that asset - whether outbound to a user or even internally - will fail validation, permanently freezing those funds inside the AA with no way for the (immutable) AA code to react or route around the change.

### Finding Description
When an asset is defined with `spender_attested: true`, `payload.attestors` is set at creation time [1](#0-0) , but the attestor list is not immutable: the definer can update it at any later moment via a dedicated `asset_attestors` message, and `validateAttestorListUpdate` only checks that the sender is the asset definer and that the list is well-formed — there's no restriction preventing removal of previously-attested addresses: [2](#0-1) 

Every payment of a `spender_attested` asset is checked against the *current* attestor list at validation time, both for the issuer (on issue) and for all output addresses (on transfer): [3](#0-2) [4](#0-3) 

This is architecturally identical to the reported EigenLayer bug class: a privileged third party (there: the strategy whitelister toggling `thirdPartyTransfersForbidden`; here: the asset definer editing the attestor list) can unilaterally change a spending precondition *after* the dependent system (there: Rio's `OperatorDelegator`; here: an AA) has already taken custody of the asset, and the dependent system has no built-in mechanism to detect or adapt to that change. In Rio's case, the OperatorDelegator's calls to `queueWithdrawals` start reverting; in ocore's case, an AA's attempt to send the asset out (or even receive/react to it) as an output will fail the `"some output addresses are not attested"` check at `validatePaymentInputsAndOutputs`.

The critical difference from Rio's operator-controlled situation is that **AAs are non-upgradable smart contracts with no privileged operator who can intervene** — an AA's logic (bounce/response handling) is fixed at deployment, so if the AA's oscript response logic doesn't (and generally can't, since it doesn't know in advance which addresses will be attested in the future) special-case "attestor list revoked", the AA's balance of the asset becomes permanently stuck. This is worse than Rio's case because Rio at least has the ability to deploy new contracts/logic; an ocore AA cannot self-modify.

### Impact Explanation
Any AA that accepts or holds a `spender_attested` asset (e.g., an AA acting as a DEX, escrow, custodian, or liquidity pool involving a third-party-issued attested asset) is exposed to permanent fund freezing if the asset's definer edits the attestor list to exclude the AA's address or the addresses the AA is programmed to pay out to. Because the AA's trigger-response logic is immutable, there is no way to "migrate" the AA's held balance once this happens — the funds are effectively burned/frozen inside the AA, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
The definer of a `spender_attested` asset is by design a privileged, external, single actor who can send an `asset_attestors` message at will, with no cooldown, delay, or governance check by ocore itself. Just as in the EigenLayer report, this doesn't require any malicious protocol behavior from the core ocore system — it's a normal, legitimate feature of asset definitions being exercised in a way that the AA has no way to anticipate or defend against, exactly mirroring the "not an extreme edge case" framing of the original report.

### Recommendation
Consider one or more of the following mitigations at the ocore protocol/AA-tooling level:
- Document explicitly (in AA-authoring guidance / oscript documentation) that AAs must never rely on holding `spender_attested` assets they intend to later forward, since attestor lists are mutable and outside AA control.
- Consider adding a way for AAs to query the current attestor list via a getter (e.g., in `evaluateAssetCondition`/`readAsset` exposed to oscript) so that AA logic can defensively branch/bounce early rather than becoming stuck holding non-transferable balances after the fact — though this only allows detection, not recovery, of already-held balances.
- Evaluate whether `asset_attestors` updates should be restricted in a way that guarantees continuity for existing holders (e.g., disallow removing an address without a grace/notice period), analogous to how the EigenLayer report recommends decoupling actual custody from a mutable third-party-controlled setting.

### Proof of Concept
1. Attacker/asset-definer `D` issues an asset `X` with `spender_attested: true` and initial `attestors: [AA_address, D_address]` via the `asset` message, validated per `validateAssetDefinition` (`validation.js:2725-2827`).
2. AA is deployed and, in its trigger-response logic, receives and holds a balance of asset `X` (validated as any other `payment` message per `validatePayment`, `validation.js:2060-2124`, with attestor check at issue time `validation.js:2115-2122`).
3. Definer `D` posts an `asset_attestors` message removing `AA_address` from the attestor list; this is accepted since only `objUnit.authors[0].address !== objAsset.definer_address` is checked (`validation.js:2829-2848`), with no restriction on removing previously-listed addresses.
4. AA subsequently tries to send some of its balance of asset `X` to any output address as part of its bounce/response logic. Validation reaches `validatePaymentInputsAndOutputs`, calls `storage.filterAttestedAddresses` against the now-updated attestor list, finds the output address(es) not attested, and returns `"some output addresses are not attested"` (`validation.js:2630-2641`), causing the unit/trigger response to fail.
5. Because AA code cannot be modified after deployment and has no way to pre-empt this definer-controlled change, the AA's balance of asset `X` is permanently stuck — unauthorized freezing of AA funds with no recovery path, matching the accepted impact criteria (AA fund loss or freezing).

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
