Confirmed vulnerability. The code exactly matches the described path: `Commit.from_github` calls `User.find_or_create_author_from_github_commit`, which regex-matches attacker-controlled `commit.commit.message` for a `Merge-Requested-By: <login>` line and directly calls `find_or_create_by_login!` on that value with no verification.### Title
Author identity spoofing via forged `Merge-Requested-By:` commit trailer - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` regex-matches the fully attacker-controlled `commit.commit.message` for a `Merge-Requested-By: <login>` line and, if found, blindly assigns that GitHub login as the commit's `author` via `find_or_create_by_login!`, with zero verification that the named user actually authenticated or requested anything. Any unprivileged GitHub user who can push a commit to a branch that gets synced into a Shipit stack (their own PR branch, a fork tracked by a review stack, etc.) can attribute that commit to any existing privileged `Shipit::User` by simply writing that trailer into the commit message.

### Finding Description
The broken binding: `commit.author.login` should equal the GitHub identity that authenticated the merge/deploy request, but here `commit.author.login == regex_match_on(attacker_controlled_commit.message)`.

Code path:
- `Shipit::GithubSyncJob#append_commit` (`app/jobs/shipit/github_sync_job.rb:51-53`) calls `stack.commits.create_from_github!(gh_commit)` for every new commit fetched from GitHub during a sync (triggered by push webhooks/PR events on tracked repos/forks).
- `Commit.create_from_github! -> Commit.from_github` (`app/models/shipit/commit.rb:105-125`) calls `User.find_or_create_author_from_github_commit(commit)` and assigns the result to `author:` on the new `Commit` record.
- `User.find_or_create_author_from_github_commit` (`app/models/shipit/user.rb:34-44`) does:
```ruby
if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
  return find_or_create_by_login!(match_info[1])
```
`github_commit.commit.message` is the raw commit message from the pushed commit — entirely attacker-controlled bytes, not GitHub-authenticated metadata about who requested a merge. `MergeRequest::MERGE_REQUEST_FIELD` is just the string `'Merge-Requested-By'` (`app/models/shipit/merge_request.rb:7`), used legitimately only when Shipit itself generates the merge commit message during `MergeRequest#merge!` (`merge_message`, `app/models/shipit/merge_request.rb:262-266`). The regex has no way to distinguish a message string written by Shipit after an authenticated `request_merge!` call from one an attacker typed into their own commit before pushing.
- `find_or_create_by_login!(login)` (`app/models/shipit/user.rb:22-28`) does `find_or_create_by!(login:)`, so if `victim-login` already exists as a `Shipit::User` (e.g., logged in before as a maintainer), it is found and returned directly — no GitHub API round-trip is even needed to validate the claim beyond the login lookup.

No existing guard intercepts this: `identify_merge_request` (`app/models/shipit/commit.rb:316-328`) only overrides `author` from `merge_request.merge_requested_by` when a genuine `MergeRequest` record exists in Shipit's own DB (created via an authenticated `request_merge!` call) — but `Commit.from_github` sets `author` unconditionally *before* that, and a commit not associated with any tracked `MergeRequest` still goes through `find_or_create_author_from_github_commit` and picks up the forged attribution. Signature verification (`verify_signature`) and `drop_unhandled_event` protect against forged *webhook payloads*, not against the semantic content of a legitimately-pushed commit's message, which is exactly the attack surface here.

Attacker exploit flow: push (or open a PR from a fork tracked by a review stack) a commit whose message body contains a line `Merge-Requested-By: victim-login\n`. When `GithubSyncJob` syncs the branch, `Commit.from_github` creates a `Commit` row with `author_id` pointing to the victim's real `Shipit::User` record.

### Impact Explanation
The `Commit#author` field is used for attribution in deploy history, hooks (`identifiers_for_ping`), and any authorization or audit logic keyed off commit authorship (e.g., `stacks_contributed_to`, `repositories_contributed_to`, notification hooks). An attacker can make it falsely appear that a privileged/maintainer `Shipit::User` authored or requested a specific commit/deploy-triggering change, corrupting audit trails without ever authenticating as that user. This is a genuine identity-attribution forgery on records the engine treats as authoritative, matching the "unauthorized attribution... affecting deploy audit trails" category. It does not by itself grant additional authorization capabilities (the endpoint-level `authorized?`/team checks are untouched), so the practical blast radius is confined to commit attribution/audit-trail poisoning rather than a direct privilege escalation or RCE.

### Likelihood Explanation
Preconditions are modest: the victim login must already exist as a `Shipit::User` (common for any maintainer who has ever logged in), and the attacker needs the ability to get a commit synced into a tracked stack — achievable via a push to a branch on a repo Shipit tracks, or via a fork/PR flow for repos with review-stacks enabled. No secrets, tokens, or elevated permissions are required; this is directly reachable by "any GitHub user who can push to a fork / open a PR," matching the stated attacker model. It is fully repeatable against any stack and any known victim login.

### Recommendation
Do not derive commit authorship from free-form commit-message text supplied by the pushing party. Only set `author` from a `Merge-Requested-By` inference when it corresponds to a Shipit-tracked `MergeRequest#merge_requested_by` that was itself set via an authenticated `request_merge!` call (as `identify_merge_request` already does), and remove or gate `User.find_or_create_author_from_github_commit`'s regex-based trust of `commit.commit.message` so it no longer overrides authorship for arbitrary synced commits. If a message-trailer based signal is still desired, it must be cryptographically bound to Shipit's own generated merge commit message, not evaluated against attacker-supplied source commits.

### Proof of Concept
```ruby
# test/models/shipit/user_test.rb (or similar)
test "find_or_create_author_from_github_commit can be spoofed via forged Merge-Requested-By trailer" do
  victim = shipit_users(:walrus) # existing privileged Shipit::User fixture with a known login
  forged_message = "Some innocuous commit\n\nMerge-Requested-By: #{victim.login}\n"

  github_commit = stub(
    commit: stub(message: forged_message, author: stub(name: 'Attacker', email: 'a@a.com', date: Time.now),
                 committer: stub(name: 'Attacker', email: 'a@a.com', date: Time.now)),
    sha: 'deadbeef',
    author: stub(id: 999999, login: 'attacker'),
    committer: stub(id: 999999, login: 'attacker'),
    stats: nil,
    parents: []
  )

  commit = Shipit::Commit.from_github(github_commit)

  # Binding under test: commit.author should equal the GitHub identity that
  # actually authenticated the push (the attacker), not an arbitrary named login.
  assert_equal victim, commit.author, "commit author was forged to the victim despite no authentication as victim"
  refute_equal 'attacker', commit.author.login
end
```
This demonstrates that `Commit.from_github` -> `User.find_or_create_author_from_github_commit` attributes the commit to `victim` purely from message text, with no verification tying `victim` to the actual authenticated pusher.
