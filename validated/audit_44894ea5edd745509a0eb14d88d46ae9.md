### Title
Cross-repository `Status` write via SHA-only matching in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits purely by `Commit.where(sha: params.sha)` with no check that the webhook's repository matches the commit's stack/repository. Any GitHub user who can produce a validly-signed `status` webhook for **their own** repository (e.g., a public fork of the victim project, which shares commit SHAs with the upstream repo) can write a `Shipit::Status` row against a victim commit belonging to a stack they do not own. Whether this write also flips `Commit#state`/deployability depends on the victim stack's `ignore_ci?` flag, but the record write itself is unconditional.

### Finding Description
Broken binding (as claimed): `webhook.repository_owner/full_name == commit.stack.repository` is **not** enforced by `StatusHandler`; the actual predicate used is only `Commit.sha == params.sha`.

Code path:
1. `Shipit::WebhooksController#create` parses the JSON body and dispatches by `X-Github-Event` to `Shipit::Webhooks.for_event(event)`, which for `status` is `[Handlers::StatusHandler]`. [1](#0-0) [2](#0-1) 
2. `verify_signature` computes the expected HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight out of the attacker-controlled payload. [3](#0-2)  This only proves the payload was signed by *some* organization's webhook secret — specifically it can be the attacker's own org/repo, since GitHub lets any repo owner install the Shipit GitHub App / configure a webhook with their own secret on their own repository.
3. `StatusHandler#process` then does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [4](#0-3) 
There is no filter on `commit.stack.repository` or on the webhook's originating repo/org at all — `sha` is a global, cross-repository lookup key in the `commits` table.
4. `create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)`, which is a `find_or_create_by!` write scoped to `stack_id` — i.e., it creates a `Status` row belonging to whichever stack owns that commit, not the attacker's stack. [5](#0-4) [6](#0-5) 
5. `Status` model has `after_create :enable_ci_on_stack` (calls `commit.stack.enable_ci!`) and `after_commit :schedule_continuous_delivery`. [7](#0-6) [8](#0-7)  The `schedule_continuous_delivery` path re-evaluates the commit's deployability, which is where `ignore_ci?` becomes relevant.

Git commit SHAs are content hashes; a fork of a public repository shares identical commit SHAs with its upstream until histories diverge. An attacker who forks the victim project (a routine, unprivileged action) automatically possesses valid commit SHAs that also exist in the victim's `Commit` table. They can then trigger (or directly POST, since `/webhooks` is an unauthenticated public endpoint requiring only a correct signature for the *sending* repository/org) a `status` event referencing that shared SHA with an arbitrary `state`/`description`/`context`, and it gets signed with their own webhook secret — which they legitimately possess for their own fork.

Why guards fail:
- `verify_signature` only authenticates *which organization sent the payload*, never *which stack/repository the payload's `sha` belongs to* — so it cannot prevent cross-repo binding violations by design.
- `drop_unhandled_event` / `check_if_ping` are irrelevant to this path.
- `ExplicitParameters` (the `params do ... end` schema) only validates types/presence of `sha`, `state`, etc.; it performs no repository-ownership check. [9](#0-8) 
- No model validation on `Status` or `Commit` ties `stack_id` back to the webhook's source repository.

### Impact Explanation
The attacker can create an unauthenticated `Shipit::Status` record for a commit in a stack/repository they do not control, with attacker-chosen `state`, `description`, `target_url`, and `context`. This satisfies "a payload for one repository mutating another's stack, commit, task" (Critical). The magnitude of impact varies by target stack configuration:
- If the victim stack has `ignore_ci?` **false** (the common, CI-gated configuration), a forged `state: "success"` status can flip `Commit#state`/deployable status, potentially unblocking or triggering downstream continuous-delivery logic (`schedule_continuous_delivery`) for a commit whose real CI never passed — this is the case where the attack has direct deploy-gating impact.
- If `ignore_ci?` is **true**, the forged `Status` row is still written (junk/log pollution, potential UI confusion, `enable_ci_on_stack` side effect toggling `ignore_ci` state) but does not by itself change `deployable?`, since that stack already disregards CI status.

Repeatable against any commit SHA the attacker can reproduce via forking (or any commit whose SHA is otherwise learnable, since GitHub commit SHAs are public for public repos), for arbitrary victim stacks in the same Shipit instance.

### Likelihood Explanation
Preconditions: victim repository is trackable by Shipit (any stack), and the attacker can fork it (or otherwise learn/reproduce a valid commit SHA) and register their own webhook signed with a secret they hold for their own org/repo. No Shipit session, API token, or GitHub App secret is required — only the attacker's own repo's legitimate webhook credentials. This is low-cost and fully repeatable per target commit.

### Recommendation
In `StatusHandler#process` (and analogously in check-run/other SHA-keyed handlers), scope the `Commit` lookup to the stack(s) whose `Repository` matches the webhook's authenticated `repository_owner`/`full_name`, e.g. `commit.stack.repository.owner/name == payload repository`, rejecting or ignoring statuses whose originating repository does not match the commit's stack repository.

### Proof of Concept
Minitest plan under `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or extending `test/controllers/webhooks_controller_test.rb`):

```ruby
[true, false].each do |ignore_ci|
  test "cross-repo status write occurs even when ignore_ci?=#{ignore_ci}, but deployable? only flips when ignore_ci?=false" do
    victim_stack = shipit_stacks(:shipit) # repository: rails/rails, say
    victim_stack.update!(ignore_ci: ignore_ci)
    victim_commit = shipit_commits(:first) # belongs to victim_stack

    attacker_payload = {
      'sha' => victim_commit.sha,
      'state' => 'success',
      'context' => 'attacker-ci',
      'branches' => [{ 'name' => victim_stack.branch }],
      'repository' => { 'full_name' => 'attacker/unrelated-fork', 'owner' => { 'login' => 'attacker' } }
    }

    assert_difference -> { victim_commit.statuses.count }, 1 do
      Shipit::Webhooks::Handlers::StatusHandler.new(attacker_payload).call
    end

    if ignore_ci
      refute victim_commit.reload.deployable_by_ci_change? # no flip
    else
      assert victim_commit.reload.state.in?(%w[success]) # commit state moved due to forged status
    end
  end
end
```

Both branches must show the `Status` row created against `victim_commit`/`victim_stack` (the REPOSITORY SCOPE violation, independent of `ignore_ci?`), while the effect on `deployable?`/`commit.state` diverges based on `ignore_ci?`.
