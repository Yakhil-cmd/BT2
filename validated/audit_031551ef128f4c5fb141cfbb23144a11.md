### Title
Cross-organization team ID collision in `MembershipHandler#find_or_create_team!` lets a webhook from Org B add a member to Org A's authorization team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` looks up a `Team` purely by the numeric `github_id` from the webhook payload, with no check that the requesting organization (the one whose secret validated the payload) actually owns that team. In a multi-organization Shipit deployment, a legitimately-configured but unprivileged/attacker-administered organization can send a genuinely-signed `membership` webhook naming a `team.id` that belongs to a different, target organization's team, causing `MembershipHandler#process` to add an arbitrary user as a member of that target team.

### Finding Description
The broken binding is: `params.organization.login (org whose webhook_secret verified this request) == team.organization (org that actually owns github_id T)`.

`WebhooksController#verify_signature` resolves the app/secret to check the HMAC using `Shipit.github(organization: repository_owner)`, and for `membership` events, `repository_owner` falls back to `params.dig('organization', 'login')`: [1](#0-0) 
This only proves the payload was signed by *the org named in the payload's own `organization.login`* — it says nothing about whether the `team.id` inside the same payload actually belongs to that org.

`MembershipHandler` then does: [2](#0-1) 
`Team.find_or_create_by!(github_id: params.team.id)` is unscoped by organization. The `organization` assignment only happens inside the `do |team| ... end` block, which ActiveRecord only executes when a **new** record is being built — if a `Team` row with that `github_id` already exists (e.g., belonging to a completely different organization already tracked via `Shipit.github_teams`), the existing row is returned unchanged, and `team.organization` is never re-checked against `params.organization.login`. `process` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))`, writing a `Membership` row for that pre-existing (target-org) team.

Existing guards do not catch this:
- `verify_signature` only authenticates "this payload really came from org X's webhook", not "team T belongs to org X".
- The `ExplicitParameters` schema on `MembershipHandler` only requires `team.id`/`organization.login` to be present and of the right type; it enforces no cross-field relationship.
- `Team` has no uniqueness validation or scoped lookup tying `github_id` to `organization`.
- `User#authorized?` trusts team membership directly: `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [3](#0-2) , so any `Membership` row created this way directly affects authorization.

**Preconditions**: This requires a multi-organization Shipit deployment (per `docs/setup.md`'s "Using Multiple Github Applications" section) where the attacker administers one of the *other* configured organizations and thus legitimately knows/controls that organization's own `webhook_secret`. Given that, the attacker can freely choose an arbitrary `team.id` value in their own org's genuinely-signed `membership` webhook to match a `github_id` already present in the `shipit.teams` table for the target organization (e.g., a team enumerated via `Shipit.github_teams`, which is built from `github.oauth_teams` config and pre-populated by `Team.find_or_create_by_handle`).

**Exploit flow**: Attacker's org sends `POST /webhooks` with `X-Github-Event: membership`, `X-Hub-Signature` computed with attacker-org's real webhook secret, and body `{action:'added', team:{id:T,...}, organization:{login:'attacker-org'}, member:{login:'attacker'}}` where `T` is the target org's team's `github_id`. Signature check passes (real secret for attacker-org). `find_or_create_team!` resolves the existing target-org `Team` row by `github_id: T`. `team.add_member(...)` creates a `Membership` linking the attacker's `User` to that team.

### Impact Explanation
The attacker gains a `Membership` record binding their `User` to a `Team` that belongs to (and is scoped to authorize access for) a different organization than the one that authenticated the webhook. If that team is part of `Shipit.github_teams`, `User#authorized?` becomes true for the attacker, granting them Shipit-level authorization tied to the target organization's authorization boundary — an escalation into `Shipit.github_teams` authorization across tenants. This is repeatable against any team `github_id` the attacker can guess/enumerate (team IDs are visible via GitHub UI/API for members of the target org, or brute-forceable as small sequential integers) and is not limited to a single request. Blast radius: any Shipit instance serving multiple GitHub organizations where one tenant's compromised/malicious admin can affect another tenant's authorization set — matches the High severity category ("escalation into `Shipit.github_teams` authorization").

### Likelihood Explanation
Requires (a) a multi-org Shipit configuration (`config/secrets.yml` with multiple orgs, each with its own `webhook_secret`, as documented and tested via `test/dummy/config/secrets_double_github_app.yml`), and (b) the attacker to be a legitimate administrator of one of those *other* configured GitHub organizations (able to register/replay a webhook with that org's own real secret) but not of the target org. Given that precondition, the attack is cheap: a single crafted HTTP POST with a correctly computed HMAC using their own secret, and a guessable/enumerable team `github_id`. No GitHub API access to the target org is needed. This is a real, mechanically reachable defect in this engine's code, not a theoretical one, though it depends on operators running a shared multi-tenant instance, which is an explicitly documented, supported configuration in `docs/setup.md`.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup/creation by both `github_id` and the verified `organization` (e.g., `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`), and reject/raise (rather than silently reusing) if a `Team` with that `github_id` already exists under a *different* organization than `params.organization.login`. Additionally, consider validating uniqueness of `github_id` scoped per organization at the model level.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual, multi-org fixtures required)
test "membership webhook from one org cannot add a member to another org's pre-existing team" do
  target_team = shipit_teams(:some_target_org_team) # organization: 'target-org', github_id: 999

  @request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # or stub Shipit.github('attacker-org').verify_webhook_signature -> true

  post :create, as: :json, body: {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' }
  }.to_json

  assert_response :ok
  # Broken binding assertion: team resolved belongs to 'target-org' though request authenticated as 'attacker-org'
  assert_equal 'target-org', target_team.organization
  assert Shipit::Membership.exists?(team_id: target_team.id, user: Shipit::User.find_by(login: 'attacker'))
  assert Shipit::User.find_by(login: 'attacker').authorized? if Shipit.github_teams.map(&:id).include?(target_team.id)
end
```

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      head(422) unless verified

      Rails.logger.info([

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
