### Title
Unauthenticated public read access to live task/deploy output streams via `Pubsubstub::StreamAction` mount - (File: config/routes.rb)

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` directly as a Rack endpoint at `/events`, bypassing the `Shipit::Authentication` concern that every other controller in the engine includes via `Shipit::ShipitController`. Any unauthenticated internet client can open `GET /events?channels[]=stack.<id>` (or `task.<id>`) and receive the live SSE stream of task/deploy output and status transitions for any guessable stack/task id.

### Finding Description
The claimed binding is: `force_github_authentication executed == true` before any response carrying stack/task data is sent to a client. Tracing the routes file: [1](#0-0) 

`mount Pubsubstub::StreamAction.new, at: "/events", as: :events` registers a bare Rack endpoint (not an `ActionController` action), so it never goes through the controller filter chain. The only place `force_github_authentication` is wired in is the `Shipit::Authentication` concern's `included do; before_action :force_github_authentication; end` block, which is included solely by `Shipit::ShipitController`: [2](#0-1) [3](#0-2) 

`Pubsubstub::StreamAction` does not inherit `Shipit::ShipitController`; it's a vendored third-party Rack app the engine mounts as-is, and the engine's `lib/shipit/engine.rb` initializer only registers `OmniAuth::Builder` and `Shipit::SameSiteCookieMiddleware` as global middleware — neither performs identity/authorization checks: [4](#0-3) 

Therefore no code path enforces `current_user.authorized?` (or any check at all) before `/events` streams data. The data reaching that stream comes from `Task#write`, which appends output to a Redis key and (via Pubsubstub's channel mechanism used elsewhere in the app, e.g. stack/task channel naming in `app/models/shipit/stack.rb`) is broadcast on a channel keyed by stack/task id: [5](#0-4) 

An attacker's exact request: `GET /events?channels[]=stack.1` (or any guessed id) with no session cookie, no `ApiClient` token — the request is routed straight into `Pubsubstub::StreamAction#call`, with no `force_github_authentication`, no `require_permission!`, no `current_api_client.stack_id` check, and no repository/team ownership check anywhere in the call path. Every existing guard listed in the Validate section (`force_github_authentication`, `User#authorized?`, `require_permission!`, the `stacks` scope) only applies to controllers built on `ShipitController`; none of them wrap this Rack mount, so the divergence between "should require auth" and "does not require auth" is real and unmitigated.

### Impact Explanation
An unauthenticated attacker can subscribe to the SSE channel for any stack or task id (ids are sequential/guessable) and receive real-time deploy/task command output — which can include repository-specific data (branch/environment names, command output, potentially embedded secrets printed by build/deploy scripts) — as well as status transition events, for any tenant's stack hosted by the Shipit instance. This is repeatable against arbitrary stack/task ids with no rate limiting concern in scope, and the blast radius spans every stack managed by the instance, matching the "High - unauthenticated read of stack state, task streams or deploy output" impact category.

### Likelihood Explanation
No preconditions beyond network access to the Shipit host are required — no session, no API token, no GitHub team membership. The attacker only needs to guess or enumerate small sequential integer ids and open a long-lived HTTP GET, which is trivial and highly feasible. This is fully repeatable and requires no special Shipit or repository configuration (it exists purely because of how the route is mounted).

### Recommendation
Do not mount `Pubsubstub::StreamAction` unauthenticated. Wrap it behind an authenticated controller action (e.g., a thin `EventsController < ShipitController` action that verifies the requesting user is authorized for the specific stack referenced by the requested channel(s) before delegating to the streaming logic), or add a `before_action`/Rack middleware in front of the `/events` mount that validates `current_user.authorized?` and per-stack access for every channel name in `params[:channels]` before allowing the subscription.

### Proof of Concept
```ruby
# test/integration/unauthenticated_events_stream_test.rb
require 'test_helper'

module Shipit
  class UnauthenticatedEventsStreamTest < ActionDispatch::IntegrationTest
    test "unauthenticated client can open /events for an arbitrary stack channel" do
      # No session cookie, no ApiClient token set.
      get Shipit::Engine.routes.url_helpers.events_path(channels: ['stack.1'])

      # BINDING UNDER TEST:
      # force_github_authentication_executed == true  (expected, per stated binding)
      # vs
      # response redirected to github_authentication_path OR rendered 403 forbidden
      #
      # Observed: request is routed to Pubsubstub::StreamAction with status 200
      # and Content-Type text/event-stream, i.e. force_github_authentication
      # was never invoked.
      assert_response :success
      assert_equal 'text/event-stream', response.media_type
      refute_includes response.location.to_s, 'github_authentication'
    end
  end
end
```
This demonstrates the two sides of the binding diverge: `force_github_authentication` is not executed for `/events`, while it is executed (and enforced) for every other route serving stack/task data through `Shipit::ShipitController` subclasses.
