### Title
Independent per-recipient rounding when splitting `earned_headers_commission_share` inflates spendable headers-commission supply - (File: `headers_commission.js`)

### Summary
When a multi-authored unit wins another unit's `headers_commission`, the commission is split among `earned_headers_commission_recipients` by rounding each recipient's percentage share **independently**, exactly like the `commitToLiens`/`_handleProtocolFee` pattern where `(1 - np/dp)*T` was rounded per-leg instead of once against the fixed total `T`. Validation only guarantees the declared shares sum to exactly 100%, but never checks that the resulting *rounded byte amounts* sum to the original commission amount. Because `Math.round()` is applied to each recipient separately, the sum of rounded amounts can exceed the actual `headers_commission` collected from the paying unit, creating spendable bytes that are not backed by any real fee payment.

### Finding Description
`validateHeadersCommissionRecipients` in `validation.js` only enforces that shares sum to 100: [1](#0-0) 

The actual distribution, however, rounds each recipient's cut independently instead of using a single total-preserving allocation (e.g., largest-remainder method): [2](#0-1) [3](#0-2) 

The same "round-before-summing" behavior is documented in-line: *"note that we round _before_ summing up header commissions won from several parent units"* — an acknowledgment that per-recipient rounding, not total-preserving rounding, is used: [4](#0-3) 

The resulting `headers_commission_contributions` rows are aggregated per main-chain-index/address into `headers_commission_outputs`: [5](#0-4) 

These aggregated amounts later become spendable via a `"headers_commission"`-type input. Its value is computed by `mc_outputs.calcEarnings` (which reads straight from `headers_commission_outputs`) and is required to balance the unit's inputs/outputs: [6](#0-5) [7](#0-6) 

Nowhere in this pipeline is the sum of per-recipient rounded amounts checked against the original `punits.headers_commission` (the amount actually deducted from the fee-paying unit). If the sum of `Math.round(full_amount * share / 100.0)` over all recipients exceeds `full_amount`, extra bytes are minted into `headers_commission_outputs` that were never actually collected as fees from any payer.

### Impact Explanation
This is a base-currency (bytes) supply-inflation bug: recipients can end up with more bytes credited to `headers_commission_outputs` than were ever collected via `headers_commission` from the paying unit. Since these outputs are later spendable as ordinary transfer inputs once claimed via a `"headers_commission"` input, the excess bytes become real, spendable currency not backed by any burned/consumed value elsewhere — a direct violation of the network's currency-conservation invariant. Any attacker able to author a multi-authored unit and control `earned_headers_commission_recipients` (an ordinary unprivileged unit-composition feature) can repeatedly engineer share splits that round up for every recipient, systematically extracting fractional-byte inflation over many units.

### Likelihood Explanation
Reaching this path requires nothing privileged: any wallet author composing a multi-author unit (a normal, supported feature) sets `earned_headers_commission_recipients` with shares of their choosing, subject only to the sum-to-100 constraint that is trivially satisfiable while still causing every individual share's rounding to round up (e.g., shares whose `full_amount * share / 100` fractional parts are all ≥ 0.5). Because `headers_commission` amounts recur naturally for every unit and this can be repeated at will, the inflation is not a one-off edge case but a systematically exploitable, low-cost griefing/inflation vector.

### Recommendation
Replace independent per-recipient rounding with a total-preserving allocation algorithm (e.g., largest-remainder method): compute floor amounts for each recipient, then distribute the few leftover units (the difference between `full_amount` and the sum of floors) to the recipients with the largest fractional remainders, guaranteeing `sum(recipient_amounts) === full_amount` exactly. Apply this both in the SQL-based (`mysql`) and JS-based (`sqlite`) branches of `calcHeadersCommissions`, and consider adding an invariant check (assertion) that per-payer-unit sums equal `headers_commission` before insertion into `headers_commission_contributions`.

### Proof of Concept
1. Author a unit with 3 authors and `earned_headers_commission_recipients` shares `[33, 33, 34]` (valid: sums to 100, passes `validateHeadersCommissionRecipients`).
2. Have this unit win a parent's `headers_commission` of `full_amount = 5` bytes (a routine, unprivileged event determined by `getWinnerInfo`'s hash-based tie-break, or simply arrange headers commissions of that magnitude).
3. In `calcHeadersCommissions`, each recipient's cut is computed as:
   - `Math.round(5 * 33 / 100) = Math.round(1.65) = 2`
   - `Math.round(5 * 33 / 100) = Math.round(1.65) = 2`
   - `Math.round(5 * 34 / 100) = Math.round(1.70) = 2`
   - Total inserted into `headers_commission_contributions` = `6`, while the payer unit's actual `headers_commission` was only `5`.
4. These `6` bytes are aggregated into `headers_commission_outputs` and become spendable by the 3 recipient addresses via `"headers_commission"`-type inputs, one extra byte more than was ever collected as a fee — demonstrating supply inflation reproducible by any user controlling the recipient share list.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
