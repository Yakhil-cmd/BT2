### Title
Cross-tenant CI status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha` with `Commit.where(sha: params.sha)`, without restricting to the stacks that belong to the webhook's own repository. Because the `commits` table's unique index is `(sha, stack_id)` rather than a global unique constraint on `sha`, the same SHA can legitimately exist for multiple stacks across different repositories/organizations, and a validly-signed webhook for one repository will write a forged CI status onto commit rows owned by an unrelated stack.

### Finding Description
The broken binding is: the request is authenticated as `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` == true for `repository_owner` (attacker's own org/repo R1), which should only authorize state changes scoped to `Repository.from_github_repo_name(repository_owner/repo).stacks`, but the code that actually applies the write, `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` in `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`, applies to **all** `Commit` rows sharing that `sha` value regardless of `stack_id`/repository.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) derives `repository_owner` from `params.dig('repository', 'owner', 'login')` and validates the HMAC signature using `Shipit.github(organization: repository_owner)`'s `webhook_secret`. This only proves the request truly originated from GitHub for that organization/repo — it does not scope which DB rows may be mutated.
- The base `Handler` class exposes a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-34`) that correctly scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, intended to prevent exactly this kind of cross-tenant bleed. `StatusHandler#process` does not use it.
- `Commit` belongs to a single `Stack` (`app/models/shipit/commit.rb:11`), and the DB explicitly permits the same `sha` under multiple `stack_id`s: `add_index :commits, %i(sha stack_id), unique: true` (`db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`) — i.e., uniqueness is per-stack, not global.
- `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:24-33`) creates a `Status` row tied to that commit's own `stack_id`, and also fires `stack.schedule_merges`/hooks (`app/models/shipit/commit.rb:379-384`).

Exploit flow:
1. Attacker controls repository R1, which is registered as a Shipit stack under some organization the attacker has push access to (a normal, unprivileged prerequisite — R1 is their own tracked repo).
2. Victim's repository R2 (different organization/tenant) has an existing `Commit` row in Shipit with `sha = X` under stack S2.
3. Attacker obtains/reconstructs a git commit object with the identical `sha X` (git commit hashes are content-addressed; pushing/cherry-picking the exact same commit content, parents, author/committer identities and timestamps into R1 reproduces the same SHA — no cryptographic collision needed) and pushes/force-pushes it into R1.
4. Attacker causes GitHub to emit a real, validly-signed `status` webhook for R1/sha=X (e.g., via their own CI reporting success, or any mechanism that causes GitHub to send a status event for that commit in R1). GitHub signs this with R1's org's real `webhook_secret`, so `verify_signature` passes legitimately.
5. `StatusHandler#process` runs `Commit.where(sha: X).each { ... create_status_from_github!(params) }`, matching **both** the R1 commit row and the unrelated R2/S2 commit row, and writes a forged `success` status onto S2's commit, potentially unblocking merges/deploys there via `stack.schedule_merges`.

Existing guards (`verify_webhook_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) all check the webhook's authenticity for R1 only; none of them constrain which `Stack`/`Commit` rows the handler is allowed to touch. The `stacks` scoping helper exists in the base `Handler` class precisely for this purpose but `StatusHandler` bypasses it.

### Impact Explanation
A successfully authenticated webhook for one attacker-controlled repository can write a `Status` record (and trigger `deployable_status`/`commit_status` hooks and `schedule_merges`) against a `Commit` belonging to a completely different tenant's `Stack`, as long as a matching `sha` row exists there. This is a payload for one repository mutating another's stack/commit state — a cross-tenant record write not authenticated by the affected tenant, matching the "Critical" impact category (payload for one repository mutating another's stack/commit). It is repeatable against any `sha` value the attacker can reproduce that happens to coexist as a `Commit` row for another stack.

### Likelihood Explanation
Requires: (a) the attacker's own repository R1 already onboarded as a Shipit stack (a normal, unprivileged setup for any Shipit user who owns a tracked repo), and (b) a `sha` collision between a commit in R1 and an existing `Commit` row for a victim stack S2. Since git SHAs are deterministic content hashes, an attacker can deliberately reproduce a specific known commit (e.g., a shared upstream/public commit, a cherry-picked/format-patched commit preserving authorship and timestamps) into R1 and get it recorded as a `Commit` there via normal sync, then trigger a real signed status webhook. No secrets are needed since GitHub itself signs the webhook for R1. The chief precondition — a real collision between two independently-created stacks' commits — is opportunistic (shared history, forks, template commits, vendored commits) rather than guaranteed for arbitrary targets, but it is fully within an unprivileged attacker's control to engineer for any specific target sha they can discover (e.g., via the target's public commit history) and any repo the attacker adds to Shipit.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository's stacks, matching the pattern already provided by `Handler#stacks`, e.g.:
```ruby
def process
  stacks.joins(:commits).where(commits: { sha: params.sha }).each do |stack|
    stack.commits.find_by(sha: params.sha)&.create_status_from_github!(params)
  end
end
```
or equivalently filter `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test ":status webhook signed for repo1 must not update commit belonging to another repository's stack" do
  stack1 = shipit_stacks(:shipit)               # owned by org "shopify", repository R1
  stack2 = shipit_stacks(:cyclimse)             # different repository/org, R2 — attacker has no access
  shared_sha = "a" * 40

  commit1 = stack1.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now,
                                    committer: shipit_users(:shipit), committed_at: Time.now, message: "x")
  commit2 = stack2.commits.create!(sha: shared_sha, author: shipit_users(:shipit), authored_at: Time.now,
                                    committer: shipit_users(:shipit), committed_at: Time.now, message: "y")

  request.headers['X-Github-Event'] = 'status'
  body = { 'sha' => shared_sha, 'state' => 'success', 'branches' => [{ 'name' => stack1.branch }] }
           .merge(repository_params) # repository owner = stack1's org, validly signed
           .to_json

  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate valid GitHub-signed request for R1 only

  post :create, body:, as: :json

  assert_equal 'success', commit1.reload.state   # expected: R1's own commit updates (binding holds here)
  assert_not_equal 'success', commit2.reload.state # BROKEN: currently also flips to 'success', proving cross-tenant write
end
```
Before the fix, `commit2.reload.state` becomes `'success'` despite the webhook never being authenticated for R2/stack2, demonstrating the divergence.
