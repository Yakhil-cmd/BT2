## Analysis

This confirms the finding. `StatusHandler#process` at [1](#0-0)  looks up commits **globally by `sha` alone** (`Commit.where(sha: params.sha)`), with no relation to `repository.owner.login` at all — it isn't even scoped by the `repository.full_name` used by `Handler#stacks`. This makes the organization/repository binding gap even more consequential: any org whose webhook secret is known can inject a `status` event forging CI success for an arbitrary commit sha, which is picked up by every stack across every tenant that happens to have a commit with that sha, feeding directly into `Commit#create_status_from_github!` → `ProcessMergeRequestsJob` and merge-eligibility checks (`MergeRequest#reject_unless_mergeable!`, `StatusChecker`).

### Title
Webhook organization used for signature verification is never bound to the repository/commit actually written - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification from `repository.owner.login` (or `organization.login`) in the JSON body, but every downstream `Webhooks::Handlers::Handler` (and `StatusHandler`) resolves the target repository/stack/commit from a *different* field of the same body (`repository.full_name`, or bare `sha` for statuses) without re-checking it belongs to the organization that authenticated the request.

### Finding Description
`verify_signature` in [2](#0-1)  does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where `repository_owner` reads `params.dig('repository', 'owner', 'login')` [3](#0-2) . This selects *which organization's webhook secret* is used to validate the HMAC over the raw body.

Once verification passes, `create` dispatches the parsed body to handlers keyed only by the `X-Github-Event` header [4](#0-3) . The generic `Handler` base class resolves the actual repository/stack to operate on from a **separate** JSON field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the repository/stack that gets mutated) are two independent strings inside the same signed body — nothing enforces `full_name` starts with `owner.login`. `StatusHandler` is worse still: it ignores repository scoping entirely and matches by `sha` across the whole `Commit` table [1](#0-0) .

In Shipit's documented multi-organization configuration (`config/secrets.development.example.yml`, shown supporting several `github:` blocks each with its own `app_id`/`webhook_secret`), a party who legitimately administers **one** configured GitHub organization (Org A) — and therefore knows Org A's `webhook_secret` because they created/installed that GitHub App — can craft an arbitrary JSON body, set `repository.owner.login = "OrgA"` (so `Shipit.github(organization: "OrgA")` picks Org A's secret and `verify_webhook_signature` succeeds), while setting `repository.full_name = "OrgB/victim-repo"` (or an arbitrary `sha`) so the handler acts on Org B's stack/commit instead. The equality broken is:

`organization whose secret authenticated the HMAC (repository.owner.login)` ≠ `repository/commit that the handler subsequently mutates (repository.full_name / sha)`

### Impact Explanation
This lets a tenant authorized only for their own org's stacks forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against **any other tenant's stack** in the same Shipit installation, purely by controlling the JSON body content, since only the raw bytes — not any relationship between fields — are covered by the signature. Concretely:
- `StatusHandler` ( [6](#0-5) ) lets the attacker inject a forged `success` CI status for a commit sha belonging to another organization's stack, which feeds into `Commit#create_status_from_github!` and can flip a pull request's CI checks to "passed", influencing `MergeRequest#reject_unless_mergeable!` / `StatusChecker` and enabling an unauthorized merge on that unrelated stack.
- `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`) lets an attacker enqueue `sync_github(expected_head_sha: ...)` for an arbitrary victim stack, feeding an attacker-chosen sha into commit-tracking machinery for a repository they don't control.

This matches the "cross-repository writes"/"escalation into authorization boundaries" High-severity impact bucket, since it lets an authenticated-but-unrelated org's credential holder write into another org's stack state and CI/merge decision-making.

### Likelihood Explanation
Medium: it requires the Shipit installation to be configured for multiple GitHub organizations (a documented, supported configuration — see `config/secrets.development.example.yml` and `docs/setup.md`), and requires the attacker to be an administrator of at least one of those configured organizations (i.e., they legitimately know that organization's own `webhook_secret`). No `ApiClient` token, no OAuth session, and no access to the victim organization's GitHub App or secrets is required — only knowledge of one's own tenant's webhook secret, which the engine itself hands to org admins as part of onboarding.

### Recommendation
After signature verification succeeds, re-derive the repository/organization strictly from the field that was used to select the verifying secret, and have every handler validate that the repository/stack it is about to mutate actually belongs to that same verified organization (e.g., compare `repository.full_name.split('/').first` against `repository_owner`, and reject or ignore otherwise). `StatusHandler` additionally needs to scope its `Commit` lookup by the repository/stack resolved from the verified organization rather than a bare, globally-unique `sha` match.

### Proof of Concept
1. Shipit is configured with two orgs, e.g.:
```yaml
github:
  orga:
    app_id: 1
    webhook_secret: "secret-a"   # known to Org A's admin (attacker)
  orgb:
    app_id: 2
    webhook_secret: "secret-b"   # unknown to attacker
```
2. Attacker (Org A admin) builds a JSON body:
```json
{
  "sha": "<sha-of-a-commit-on-OrgB-stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/victim-repo" }
}
```
3. Attacker computes `sha1=` HMAC of this exact body using `secret-a` (which they legitimately know) and POSTs it to `/github/webhooks` with `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
4. `verify_signature` calls `Shipit.github(organization: 'orga')` (from `repository.owner.login`), verifies successfully against `secret-a` for the whole raw body.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `success` status on the Org B commit, unrelated to Org A entirely, potentially unblocking a merge on Org B's stack that the attacker has no legitimate access to.
