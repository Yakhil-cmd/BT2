### Title
Webhook signature is verified against `repository.owner.login` while the acted-upon target is selected from the independent, unchecked `repository.full_name` field, allowing cross-organization/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). [1](#0-0) [2](#0-1) 

Every event handler (`Shipit::Webhooks::Handlers::Handler`), however, resolves the target repository/stacks using a *different* field of the same JSON body: `payload.dig('repository', 'full_name')`. [3](#0-2) 

Both fields are entirely attacker-supplied inside the raw POST body that is HMAC-signed as a whole, but the code never checks that `full_name`'s owner segment matches `owner.login`. This breaks the intended binding: `organization authenticated == repository written`.

### Finding Description
- Signature check binds trust to `repository_owner` (`owner.login`), used only to pick the correct `webhook_secret` via `Shipit.github(organization: repository_owner)`. [1](#0-0) 
- Handlers such as `PushHandler` compute the set of `stacks` to act on purely from `Repository.from_github_repo_name(repository_name)`, where `repository_name` comes from `payload.dig('repository', 'full_name')` — a completely separate JSON key from `repository.owner.login`. [4](#0-3) [3](#0-2) 
- Because the signature only proves "this body was signed with organization X's webhook secret" and not "this body only references organization X's repositories", any organization that legitimately owns a Shipit-configured GitHub App/webhook secret (a normal, non-privileged setup step for multi-tenant Shipit deployments, per `config/secrets.development.shopify.yml` showing multiple independently-configured `github:` orgs) can craft a payload where `repository.owner.login` = their own org (so `verify_signature` succeeds using their own known secret) while `repository.full_name` = `"other-org/other-repo"` (so the handler acts on a stack that belongs to a completely different, unrelated organization/repository). [5](#0-4) 
- This crosses the exact boundary called out by the audit-analog rules: "an organization that authenticated versus the repository that is written."

### Impact Explanation
An attacker who controls (or is an authorized member of) one organization onboarded onto a shared Shipit instance can forge webhook events (e.g. `push`, `status`, `check_suite`, `membership`) that are accepted as authentic for a *different* organization's repository, because the signature check and the target-resolution logic consult different, independently-forgeable fields of the same payload. This can, for example, drive `PushHandler` to invoke `stack.sync_github(expected_head_sha: ...)` on stacks owned by another organization/repository, or manipulate `StatusHandler`/`CheckSuiteHandler` state for commits that do not belong to the attacker's own org — i.e. cross-repository writes/state manipulation not intended to be reachable by that organization's credentials. This matches the "cross-repository writes" / "unauthorized deploy" class of Critical impact defined in scope.

### Likelihood Explanation
Any organization already configured with its own GitHub App/webhook secret in the shared Shipit instance (a routine, low-privilege multi-tenant configuration, evidenced by the multi-org `github:` config format) can trivially craft this payload — no compromise of another tenant's secret, no GitHub App private key, and no `ApiClient`/session token is required. The only requirement is knowledge of one's own legitimately-configured webhook secret, which is a completely unprivileged capability from the perspective of any other tenant/repository.

### Recommendation
In `verify_signature` (or immediately in `WebhooksController#create`), enforce that `params.dig('repository', 'full_name')`'s owner segment (and/or `organization.login`) is consistent with `repository_owner` used to select the webhook secret, rejecting payloads where they diverge. More robustly, every `Handler` should re-derive the repository strictly from the same `repository_owner`/organization value that was cryptographically verified, rather than trusting `full_name` independently.

### Proof of Concept
1. Organization `attacker-org` is legitimately configured in Shipit with its own `webhook_secret` (`attacker-org` administrator knows this secret, as they configured their own GitHub App).
2. Attacker crafts a raw JSON push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact raw body.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")` (derived from `repository.owner.login`) and the signature verifies successfully. [1](#0-0) 
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, acting on stacks the attacker's organization has no relationship to. [4](#0-3) [3](#0-2)
