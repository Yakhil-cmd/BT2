### Title
Cross-organization webhook forgery via `repository.owner.login` / `repository.full_name` mismatch bypasses per-organization signature binding - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`), but the actual webhook handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`) resolve the target `Stack`/`Repository` using the independent `repository.full_name` field from the same attacker-suppliable JSON body. Because these two fields are never cross-checked, an attacker who legitimately controls one GitHub organization/App configured in a multi-tenant Shipit deployment can sign a payload with their own known `webhook_secret` while pointing the payload's `repository.full_name` at a different, victim-owned tracked repository, letting that org's credentials authorize actions against a repository it doesn't own.

### Finding Description
`verify_signature` picks the app instance/secret with:
```ruby
github_app = Shipit.github(organization: repository_owner)
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

The HMAC signature check (`verify_webhook_signature`) is only strong against tampering of the raw body relative to *whatever secret was selected*; it does not bind the verified organization to any specific repository referenced inside the payload: [2](#0-1) 

Once signature verification passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that resolve the affected `Stack` via a *different* JSON field:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

`repository.owner.login` (verified) and `repository.full_name` (acted upon) are independent keys in the same attacker-crafted JSON body — nothing enforces `full_name` starts with `owner.login/`. This is the same class of bug as the reported `NotionalV1ToNotionalV2.notionalCallback` issue: the value trusted for authorization (`sender`/`repository.owner.login`) is not the value the operation actually executes against (`account`/`repository.full_name`), and the attacker fully controls both independently while only being able to legitimately satisfy the check for one identity.

Concretely, in a Shipit installation configured for multiple GitHub organizations (`config/secrets*.yml` `github:` multi-org schema, see `lib/shipit/github_app.rb`), or in any installation where an attacker legitimately owns one tracked organization/App with a known `webhook_secret`, the attacker can:
1. Compute a valid `X-Hub-Signature` HMAC using **their own** org's `webhook_secret` over a JSON body of their choosing.
2. In that body, set `repository.owner.login` = their own org (so `Shipit.github(organization: repository_owner)` picks their own `GitHubApp`/secret, and the signature validates), while setting `repository.full_name` = `victim-org/victim-repo` (a repository tracked by a different, victim `Stack`).

`PushHandler` and `StatusHandler` then act on the victim's stack using attacker-supplied data:
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [4](#0-3) 
```ruby
def process
  Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
end
``` [5](#0-4) 

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." An attacker with legitimate control of one org/App in a multi-tenant Shipit instance can forge `push`, `status`, and `check_suite` webhooks for a repository belonging to a completely different, victim organization/team also tracked by the same Shipit instance. `StatusHandler` lets the attacker inject arbitrary CI status objects (`state`, `context`, `description`, `target_url`) onto victim commits, which can be used to defeat CI-gating conditions Shipit relies on before allowing a merge/deploy (e.g. faking a green "ci/required" status). `PushHandler` forces `GithubSyncJob`/`sync_github` against the victim stack with attacker-chosen `expected_head_sha`. Depending on the victim stack's continuous-deployment configuration, this can trigger unwanted syncs/deploy eligibility changes on a repository the attacker does not own — a cross-repository write/unauthorized-deploy-adjacent condition, satisfying the "cross-repository writes / unauthorized deploy" impact bar.

### Likelihood Explanation
Requires the attacker to control at least one organization/App entry configured in the same multi-tenant Shipit instance (a realistic scenario for shared internal deploy tooling covering several orgs/teams), and requires the victim repository to be tracked by the same Shipit instance. No privileged Shipit session, `ApiClient` token, or GitHub write access to the victim repo is needed — only the ability to send an HTTP POST to `/webhooks` with a validly-signed-for-their-own-org body. Single-organization Shipit deployments are not affected the same way (the attacker would need any org's secret, and there is only one), but the vulnerable binding logic itself is unconditional and present regardless of deployment shape.

### Recommendation
Bind the verified organization to the repository actually acted upon: after computing `repository_owner` and verifying the signature, also verify that `payload.dig('repository', 'full_name')` (and/or `payload.dig('organization', 'login')`) is consistent with `repository_owner` (e.g., `full_name.split('/').first == repository_owner`) before dispatching to handlers, or resolve the target `Stack`/`Repository` using the same `repository_owner` value that was cryptographically verified rather than a separate unverified field.

### Proof of Concept
1. Configure Shipit for two organizations (`OrgA` — attacker-controlled, `OrgB` — victim), each tracked with distinct GitHub Apps/`webhook_secret`s, as in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker (owner of `OrgA`'s App) crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` using their own known `OrgA` secret.
4. POST to `/webhooks` with header `X-Github-Event: push` and the above body/signature.
5. `verify_signature` calls `Shipit.github(organization: 'OrgA')` and successfully verifies the signature against `OrgA`'s secret [6](#0-5) .
6. `PushHandler#stacks` resolves via `Repository.from_github_repo_name('OrgB/victim-repo')` [3](#0-2) , and `stack.sync_github(expected_head_sha: params.after)` is invoked on the victim's stack, using data the attacker fully controls despite never proving control of `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
