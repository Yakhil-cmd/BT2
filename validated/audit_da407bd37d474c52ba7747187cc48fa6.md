### Title
`StatusHandler#process` applies GitHub `status` webhooks by SHA only, with no check that the reporting repository owns that commit, letting one repo's status mutate another repo's `Stack`/`Commit`/deploy decision — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits globally with `Commit.where(sha: params.sha)` and writes a `Status` for every match, without ever checking `payload['repository']['full_name']` against the commit's actual repository/stack. Every other handler in the same namespace (`CheckSuiteHandler`, the `PullRequest::*Handler`s) explicitly scopes lookups through `Repository.from_github_repo_name(...)`/`stacks`; `StatusHandler` does not, so a `status` webhook whose signature validates for organization A can still write a `success`/`failure` status onto a `Commit` belonging to a `Stack` in organization/repository B whenever the two repositories happen to share a commit SHA.

### Finding Description
The broken binding: `payload['repository']['full_name'] == commit.stack.repository.full_name` should hold for every `Status` created from a webhook, but it does not.

Code path:
1. `WebhooksController#verify_signature` only checks that the signature matches the secret configured for `repository_owner = payload.dig('repository','owner','login')` [1](#0-0) . This binds the request to an *organization*, not to a specific repository or stack.
2. `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This is a global, unscoped lookup by `sha` alone — the params schema for `StatusHandler` doesn't even require a `repository` field [3](#0-2) , and `process` never calls the `Handler#stacks`/`repository_name` helper that every sibling handler uses to scope by repository, e.g. `CheckSuiteHandler#process` uses `stacks.where(branch: ...)` before touching commits [4](#0-3) , and the `PullRequest` handlers all resolve `repository = Shipit::Repository.from_github_repo_name(params.repository.full_name)` before acting [5](#0-4) .
3. `commit.create_status_from_github!` calls `add_status` which creates the `Status` scoped to `commit.stack_id` (the victim stack, whatever it is) [6](#0-5)  and, on a `success`/`pending` transition, schedules merges and continuous delivery [7](#0-6) , and `Status#schedule_continuous_delivery` / `Status.after_commit` hooks fire deploy scheduling [8](#0-7) .
4. `Stack#next_commit_to_deploy` then re-evaluates `deployable_commits` over `commits_with_max_applied` using `Commit#deployable?`/status state [9](#0-8) . Because the earliest blocked commit in the victim's undeployed batch now has an attacker-forged `success` status attached (created via a webhook whose only binding is the *organization*, not the specific stack/repository), `find(&:deployable?)`/`deployable_commits` unblocks the batch and the pipeline advances to `trigger_continuous_delivery` → `trigger_deploy`, deploying a commit the victim's own CI never validated.

Why existing guards fail: `verify_signature` authenticates the *organization* the payload claims to be from, not the specific repository, and `StatusHandler` performs no additional repository check at all — unlike `CheckSuiteHandler` and the `PullRequest::*` handlers, which all resolve and filter by `Repository.from_github_repo_name`/`stacks` before mutating anything. `ExplicitParameters` only validates shape (`sha`, `state`, etc.), not tenancy. There is no model validation on `Status`/`Commit` that ties the status's origin repository to the commit's stack.

Exploit flow: an attacker who is any normal (non-maintainer) contributor to a repository within an organization Shipit already tracks can cause GitHub to emit — or, per the given attacker capabilities, directly send — a correctly-signed `status` webhook (signed by the org's own webhook secret, which the attacker never needs to know because GitHub computes it) reporting `state: success` for a `sha` that is shared (same commit content) between that repository and an entirely different stack's earliest undeployed commit in the target organization. Because `StatusHandler` matches purely on `sha`, the forged status attaches to the victim commit and the victim stack's `next_commit_to_deploy` selection changes.

### Impact Explanation
This lets a webhook honestly attributable to repository/stack A write a `Status` record (and trigger downstream continuous-delivery scheduling, merge processing, and deploy selection) for repository/stack B within the same organization, purely because a commit SHA coincides. The direct consequence matches the rules' Critical category "a payload for one repository mutating another's stack, commit, task or team" and can produce "an unauthorized deploy" by causing `Stack#next_commit_to_deploy` to select and ship a commit further than the victim stack's legitimate CI state would allow. It is repeatable against any pair of repositories/stacks in the same org that share, or can be made to share, a commit SHA, and blast radius is bounded to intra-organization cross-repository/cross-stack tenants (the org-level signature check does prevent cross-organization forgery).

### Likelihood Explanation
Preconditions: the victim stack must have `deploy.max_commits` (`maximum_commits_per_deploy`) set and multiple undeployed commits, and the earliest blocking commit's SHA must be reachable/reproducible by the attacker in a repository under the same Shipit-tracked organization (e.g., via shared history, cherry-pick, template/fork repos, or monorepo splits preserving SHAs) — this is a real but non-trivial precondition, explicitly given in the question rather than requiring a raw SHA-1 collision. Given that precondition, attacker cost is low: no Shipit session, API token, or secret is needed; the org-level webhook signature is computed by GitHub itself for any legitimate webhook event the attacker can trigger in a repository they can push/PR to within that org. The vulnerability is fully repeatable for as long as the shared-SHA condition holds.

### Recommendation
Scope `StatusHandler#process` to the reporting repository, the way `CheckSuiteHandler` and the `PullRequest::*Handler`s already do: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name(params.repository.full_name)`, and only create/update statuses for commits that belong to stacks under that repository (e.g. `repository.stacks.commits.where(sha: params.sha)` instead of the global `Commit.where(sha: params.sha)`).

### Proof of Concept
Minitest plan (model-level, no live GitHub needed):
1. Set up two `Repository`/`Stack` fixtures, `stack_a` (attacker-controlled) and `stack_b` (victim), each with `deploy.max_commits` configured on `stack_b`.
2. Create a `Commit` under `stack_a` and a `Commit` under `stack_b` sharing the identical `sha` value (simulating the "shared reachable sha" precondition), where `stack_b`'s commit is the earliest undeployed/blocking commit in a multi-commit batch.
3. Assert baseline: `stack_b.next_commit_to_deploy` returns the first, still-blocked commit (or `nil`) because the earliest commit has no passing status.
4. Simulate the forged webhook by invoking `Shipit::Webhooks::Handlers::StatusHandler.call(payload_for_stack_a_repo_with_shared_sha_and_state_success)` — a payload whose `repository.full_name` names `stack_a`'s repository but whose `sha` matches `stack_b`'s earliest commit.
5. Assert the divergence: `stack_b`'s earliest commit is now `deployable?` (via the newly created cross-repository `Status`), and `stack_b.next_commit_to_deploy` now returns a later commit than before step 4 — demonstrating that a webhook attributable to repository A altered repository B's deploy target with no relation between the two.
