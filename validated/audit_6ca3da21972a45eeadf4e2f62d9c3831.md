### Title
Autonomous Agents holding `spender_attested` (KYC‑gated) assets can act as permissionless proxies to move restricted funds to unattested addresses - (File: `aa_validation.js`, `definition.js`, `storage.js`)

### Summary
Obyte's `spender_attested` asset feature is the ocore analog of Coinbase's verified‑pool KYC gate described in the report: only addresses that hold a valid attestation from a whitelisted attestor are allowed to spend the restricted asset, enforced through the `attested` operator in address definitions [1](#0-0) . Just as an ERC‑4337 smart wallet can receive an attestation and later be re‑purposed (via upgradeable/delegatecall logic) into a permissionless swap proxy, an Autonomous Agent (AA) can receive a `spender_attested` asset from a legitimately attested depositor and then re‑distribute it to arbitrary, non‑attested addresses in its own response messages, because AA-authored outputs are not re‑validated against the `attested` address-definition condition the way author-signed units are.

### Finding Description
`spender_attested` assets restrict who may be an "author"/spender of a payment by requiring the spending address's definition to satisfy an `['attested', address, arrAttestors]` clause, which is checked against the `attestations` table via `storage.filterAttestedAddresses` [2](#0-1)  and consumed during authentifier validation [3](#0-2) . This check ties the validity of the attestation to the spender's *own address definition* at the moment of last definition change, so a normal wallet cannot silently re-purpose itself after being attested.

However, `aaApps` explicitly includes `asset`, `asset_attestors`, `attestation` and `payment` as valid AA message types [4](#0-3) , and AA logic can check an incoming trigger author's attestation status via the `attestation` formula function [5](#0-4) . An AA is deployed once with an immutable oscript definition, but that definition can encode arbitrary forwarding/swap logic that is gated only on the *inbound* trigger being attested, while *outbound* payment messages the AA generates in response are not subject to any further `attested`-address-definition check on the recipient — AA response units are composed and authorized by the AA execution engine itself, not by a signature satisfying the recipient's or AA's own address definition against `['attested', ...]`.

This mirrors the report's core issue exactly: a wallet/contract that legitimately holds an attestation (KYC status) can act as an intermediary that swaps or forwards value on behalf of unattested/sanctioned counterparties, because the attestation check is only enforced at the boundary (deposit), not for every subsequent hop of value inside the contract.

### Impact Explanation
An AA that accepts a `spender_attested` asset from a KYC'd/attested trigger address (satisfying the deposit-side check) can, in its `messages`/`payment` app definition, forward that same restricted asset to any address specified by the trigger, including addresses that have never been attested. This lets any user (once holding a valid attestation) act as a proxy, laundering value out of the KYC‑gated system on behalf of unattested or sanctioned counterparties. High impact: it defeats the entire purpose of `spender_attested` assets (compliance-restricted tokens), similar to unauthorized swaps bypassing sanctions/KYC in the original report.

### Likelihood Explanation
Low/Medium: it requires an attested/KYC'd user to deliberately build or use such an AA and violate the intent of the attestation-gated asset (a ToS/compliance violation rather than a protocol bug per se), and it is fully permissionless and requires no special privileges once the AA is deployed and the attested depositor makes the first hop.

### Recommendation
Consider extending the `spender_attested` enforcement so that every output of a message transferring the restricted asset — including those generated by an AA in its response — is checked against the `attested` condition for the *ultimate recipient*, not only for the address that authored the depositing unit. Alternatively, disallow `spender_attested` assets from being sent to AA addresses at all (analogous to "only allow a certain set of smart contract wallets to receive attestations"), or require that AAs that are meant to remain compliant include the `attestation` check on every payment message, and document/flag that using an AA as an unrestricted relay for spender_attested assets circumvents the asset's compliance design.

### Proof of Concept
1. Asset X is created with `spender_attested: true` and a trusted attestor list (checked via `definition.js` `attested` opcode and `storage.filterAttestedAddresses`) [1](#0-0) [2](#0-1) .
2. Address A obtains a valid attestation from the trusted attestor and legitimately receives asset X.
3. Deploy an AA whose `messages` use the `attestation` formula function to confirm `trigger.address` is attested [5](#0-4) , then unconditionally forwards any received asset X to `trigger.data.recipient` (an arbitrary, unattested address) via a `payment` message.
4. Address A sends asset X to the AA as a trigger, specifying an unattested/sanctioned address as `recipient`.
5. The AA's `payment` response message transfers asset X to the unattested address without any further `attested` check being applied to that output, completing the bypass.
