This confirms the finding. Both `PushHandler` and `CheckSuiteHandler` scope their lookups through `stacks` (which is derived from `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`) [1](#0-0)  before touching any commit or stack, but `StatusHandler#process` never uses `stacks`/`repository_name` at all — it queries `Commit.where(sha: params.sha)` globally and calls `create_status_from_github!` on every match, regardless of which repository the webhook actually came from [2](#0-1) .

### Title
Cross-repository merge-queue trigger via unscoped `Commit.where(sha:)` lookup in status webhook - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by SHA (`Commit.where(sha: params.sha)`) without ever checking that the SHA belongs to a commit in the repository named by the webhook's own `repository.full_name` field. Any GitHub org/repo the attacker controls (which passes `verify_signature`) can therefore push a status webhook for a SHA that happens to also exist as a commit on an unrelated `victim_stack`, causing `commit.create_status_from_github!` → `Commit#add_status` → `stack.schedule_merges` → `ProcessMergeRequestsJob.perform_later(victim_stack)` to fire for the victim, entirely outside any real state change on the victim's actual repository.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`. This equality is enforced by every other webhook handler via the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) [1](#0-0) , as seen in `PushHandler#process` (`stacks.not_archived.where(branch:)`) [3](#0-2)  and `CheckSuiteHandler#process` (`stacks.where(branch: ...)` then `stack.commits.where(sha: ...)`) [4](#0-3) . `StatusHandler#process`, however, does:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This never calls `stacks` or filters by `repository_name`, so any `Commit` row anywhere in the database with a matching `sha` — belonging to any stack, any repository, any tenant — is updated.

`Commit#create_status_from_github!` calls `add_status`, which, on a `pending?`/`success?` transition, unconditionally calls `stack.schedule_merges` [5](#0-4) . `Stack#schedule_merges` enqueues `ProcessMergeRequestsJob.perform_later(self)` for that commit's actual owning stack (the victim's), not the stack corresponding to the webhook's repository. `ProcessMergeRequestsJob#perform` then iterates the victim stack's pending `MergeRequest`s, calling `reject_unless_mergeable!`, `revalidate!`, `all_status_checks_passed?`, and `merge!` [6](#0-5) .

`verify_signature` only proves that the payload came from a real GitHub webhook for `repository_owner` (the org named in the *attacker's* own payload) [7](#0-6)  — it does not, and cannot, prove that the `sha` field refers to a commit that actually lives in that repository. As long as the attacker's own GitHub org/repo is registered with a valid webhook secret in Shipit (a precondition already assumed reachable per the attack model — "any GitHub user who can... emit webhooks from a repository they own"), the signature check passes trivially, and `StatusHandler` performs zero repository-binding validation afterward.

A SHA collision across repositories is not a cryptographic SHA-1 collision requirement — git commit objects are content-addressed, so any commit shared unmodified between a fork and its upstream (or between any two repositories with a common history, e.g. victim's repo and attacker's fork of it) has an identical SHA in both. An attacker who forks `victim/repo` inherits the exact SHAs of every ancestor commit. If `victim_stack`'s merge queue has a `MergeRequest` head commit that is (or shares an unmerged ancestor with) a commit also present unmodified in the attacker's fork, the attacker can set an arbitrary commit status on that SHA within their own fork via the GitHub Status API (a completely legitimate action on their own repository) and GitHub will deliver a correctly-signed webhook to Shipit naming the attacker's repo — which `StatusHandler` then misapplies to the victim's `Commit` row.

### Impact Explanation
This lets an unprivileged webhook sender force `ProcessMergeRequestsJob` to run for a stack they don't own and never authenticated against, potentially causing `MergeRequest#merge!` to execute against `victim_stack` based on a status the attacker fabricated on their own copy of the commit, rather than any state change GitHub recorded on `victim_stack`'s actual repository. This is a cross-tenant write: a payload verified only for the attacker's own repository mutates another repository's stack/commit/merge-queue state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge." It is repeatable against any stack whose tracked repository shares commit history (via fork or otherwise) with a repository the attacker controls, and the resulting job/merge behavior is not scoped to a single tenant — it can be replayed for every colliding SHA the attacker can produce.

### Likelihood Explanation
Preconditions: `victim_stack.merge_queue_enabled` must be true with a `MergeRequest` queued and waiting on the colliding commit's status, matching the question's stated scenario. The attacker needs only a GitHub repository/org of their own already registered with Shipit as a webhook source (satisfying `verify_signature`) and a forked/shared-history relationship to the victim's commit — both are within reach of an unprivileged GitHub user per the stated attacker model. No secrets, sessions, or maintainer privileges are required. The cost is low (one GitHub Status API call plus GitHub's webhook delivery) and fully repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the webhook's own verified repository, mirroring `PushHandler`/`CheckSuiteHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the update to `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`, restoring the equality between the webhook's verified repository and the commit/stack being mutated.

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?

      return false unless stack.allows_merges?

        merge_request.refresh!

          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
