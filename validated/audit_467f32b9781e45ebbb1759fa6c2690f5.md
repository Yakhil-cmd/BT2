### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, letting a stack-restricted token read any stack's build/deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the shared `stack` lookup helper and drops the tenant-scoping that `Shipit::Api::BaseController` enforces for every other API controller. This breaks the binding "the stack a token authorizes" ↔ "the stack the request actually touches," the same class of bug as the Sherlock M-6 report where an action bound to one condition (`raiseAssetTarget`'s "target met" check) was allowed to act on data (price/ratio of every component) that the check never covered.

### Finding Description
`Shipit::ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The generic `BaseController#stacks`/`#stack` helpers enforce this scope on every lookup:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

Every other API controller (e.g. `Api::StacksController`) relies on this scoped `stacks`/`stack` method, so a token created with `stack_id` set can only ever resolve a `Stack` record that matches its own `stack_id`.

`CCMenuController`, however, redefines `stack` to bypass the scope entirely and query the unscoped model directly:

```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end

private

def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller only checks the coarse-grained permission `read:stack` via `require_permission :read, :stack`, which is implemented as `current_api_client.check_permissions!(operation, scope)` — a check that merely verifies the string `"read:stack"` is present in the token's `permissions` array, with no notion of *which* stack [4](#0-3) . Nothing in `CCMenuController` re-applies the `stack_id` restriction that `stacks` would have enforced.

So the equality that should hold — `stack authorized by token == stack acted on by request` — is broken specifically in this controller: any token with `read:stack` permission (regardless of its `stack_id`) can pass an arbitrary `stack_id` param and receive that other stack's CCMenu status.

### Impact Explanation
This is an authenticated-but-unauthorized cross-stack information disclosure: a token deliberately scoped by an operator to a single stack (e.g. handed to a low-trust CI dashboard/monitor for one project) can be used to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, lock state, activity) of every other stack in the Shipit instance, including stacks and repositories the token's creator never intended to expose. It maps to the "unauthenticated/unauthorized read of stack state" High-impact class in scope: the token is authenticated, but the specific stack being read is not one it was authorized for — the exact "stack a token authorises versus a stack it touches" binding called out as in-scope.

### Likelihood Explanation
Any actor possessing a stack-scoped `ApiClient` token (which is explicitly the low-privilege, narrowly-scoped credential type this feature exists to support) can trivially exploit this by hitting the CCMenu endpoint with a different `stack_id`/`token` combination — no special conditions, races, or additional secrets are required beyond having any valid scoped token.

### Recommendation
Remove `CCMenuController`'s private `stack` override and let it inherit `BaseController#stack` (which is `stacks.from_param!(...)`), so the `stack_id` scope on `current_api_client` is enforced identically to every other Api controller endpoint.

### Proof of Concept
1. Operator creates an `ApiClient` scoped to Stack A: `ApiClient.create!(stack: stack_a, permissions: ['read:stack'], creator: user)`, and hands out its `authentication_token`.
2. Attacker (holder of that token) sends: `GET /api/stacks/:stack_b_id/ccmenu.xml?token=<stack_a_token>` where `stack_b_id` is a completely unrelated Stack B.
3. `CCMenuController#authenticate_api_client` succeeds (token is valid) [5](#0-4) ; `require_permission :read, :stack` passes because the token has `read:stack` in its permission list, with no stack check [4](#0-3) .
4. `stack` resolves via the unscoped `Stack.from_param!(params[:stack_id])` to Stack B [6](#0-5) , and the response renders Stack B's latest deploy/lock/build status — data the Stack-A-scoped token was never authorized to see.
