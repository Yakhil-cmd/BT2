### Title
Dust-output flooding can permanently block an AA's asset send-all payments and freeze AA funds - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `completePaymentPayload` builds payment messages for AA responses by iterating over **all** unspent outputs owned by the AA address for a given asset with no cap on the number of rows consumed when the payment message contains a "send-all" output. An attacker can flood the AA address with a large number of tiny-amount custom-asset outputs (analogous to the Knox report's technique of transferring many claim tokens to a victim across many epochs), forcing `iterateUnspentOutputs` to accumulate more inputs than `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128) allows, which makes every subsequent AA response that tries to `send-all` of that asset invalid/bounced.

### Finding Description
In `completePaymentPayload`, `readStableOutputs` selects unspent outputs for the AA's `address` and `asset` with **no LIMIT clause**: [1](#0-0) 

Notice that the dust-protection minimum (`amount>=FULL_TRANSFER_INPUT_SIZE`) is applied only for the base asset (`asset IS NULL`), not for custom assets — the `asset="..."` branch has no minimum-amount filter: [2](#0-1) 

`iterateUnspentOutputs` then loops through every row returned. When the trigger's payload contains a `send_all_output`, the loop does **not** break once the target amount is reached — it explicitly `continue`s so that all remaining outputs keep being consumed as inputs: [3](#0-2) 

This means `payload.inputs` (and `arrUsedOutputIds`) can grow without any bound related to `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE = 128`: [4](#0-3) 

If more than 128 unspent outputs of the asset exist at the AA's address, the resulting payment message will contain more than 128 inputs, which is rejected by unit-size/message validation, causing the AA's constructed response unit to be invalid. The existing code comment even acknowledges the general dust-attack class ("byte outputs less than 60 bytes ... are ignored to prevent dust attack: spamming the AA with very small outputs"), but this protection is not applied to non-base assets, and even where it is applied for bytes, it does not bound the input array against `MAX_INPUTS_PER_PAYMENT_MESSAGE` for the `send_all_output` case.

### Impact Explanation
An attacker (who controls or funds many addresses, or repeatedly sends many small-value custom-asset outputs to the AA address across many units/epochs, mirroring the "many claim tokens across many epochs" pattern in the original report) can inflate the count of unspent asset outputs owned by the AA far beyond 128. Once that happens, any legitimate trigger that causes the AA to send-all of that asset out (a common accounting pattern, e.g., "return remaining balance to user") will always fail to compose a valid unit, causing the AA response to bounce. Since a bounce still consumes the AA's byte balance for the bounce fee, this both denies service to legitimate users of the AA and can progressively drain/freeze the AA's byte balance, while the asset funds held by the AA become permanently unspendable via any code path that relies on send-all for that asset.

### Likelihood Explanation
Sending outputs to an arbitrary address (including an AA address) is a normal, unprivileged action available to anyone; no special permission or race condition is needed. Because the dust-amount filter (`amount>=FULL_TRANSFER_INPUT_SIZE`) only applies to base-asset outputs, generating 128+ tiny custom-asset outputs against a target AA is cheap and requires only ordinary payment transactions, making this practically achievable by any user who wants to grief a specific AA.

### Recommendation
- Apply a minimum-amount (dust) filter to non-base assets in `readStableOutputs`/`readUnstableOutputsSentByAAs` similar to the one already used for bytes.
- Add an explicit `LIMIT` to these queries (e.g., bounded by `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE`), and enforce that `iterateUnspentOutputs` stops accumulating additional inputs once the input count reaches `MAX_INPUTS_PER_PAYMENT_MESSAGE - 1` (reserving space for a change/fee input), returning an error/bounce condition gracefully instead of producing an invalid oversized payment message.
- Consider consolidating dust outputs opportunistically (e.g., via periodic "cleanup" transfers) or rejecting/merging incoming sub-threshold asset outputs to AA addresses at validation time.

### Proof of Concept
1. Deploy an AA that, upon trigger, sends all of its balance of a custom asset back to the triggering address (`{asset: X, outputs: [{address: trigger.address}]}`, i.e., a send-all output).
2. Attacker crafts 200+ separate payment units, each sending a minuscule amount (e.g., 1 unit) of asset `X` to the AA's address, from many different funding sources across many units (paralleling the "many different epochs / many addresses" technique from the original report).
3. Trigger the AA to send-all of asset `X`. In `completePaymentPayload`, `readStableOutputs` returns 200+ rows; `iterateUnspentOutputs` keeps `continue`-ing (because `send_all_output` is set) and pushes all 200+ inputs into `payload.inputs`.
4. The resulting payment message exceeds `constants.MAX_INPUTS_PER_PAYMENT_MESSAGE` (128), the AA's response unit fails validation/composition, and the trigger bounces — consuming the AA's bounce fee — while the asset remains stuck at the AA address for this and all future triggers relying on send-all of that asset.
