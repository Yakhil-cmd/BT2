No SQL injection analog exists in this codebase. I reviewed the one component that uses SQL — `substrate/frame/revive/rpc/src/receipt_provider.rs`, the off-chain eth-rpc receipt/log indexer for `pallet-revive` — and all attacker-influenced values (transaction hashes, block hashes/numbers, log addresses/topics from `Filter`) are passed exclusively through parameterized `query!` macros or `QueryBuilder::push_bind`, never concatenated into SQL text. [1](#0-0) [2](#0-1) [3](#0-2) 

The only `format!`-constructed SQL strings build placeholder lists (`"?"` repeated per chunk) for the `DELETE ... WHERE ... IN (...)` batch-pruning queries, with actual values still bound via `.bind()` rather than interpolated, so no attacker-controlled data ever reaches the query text itself. The remaining `format!` usage of table names in `sqlx::query_scalar` is confined to `#[cfg(test)]` helper code with hardcoded literals, not reachable from any user input.

More broadly, this SQL-backed store is an off-chain indexing/RPC convenience database for the Ethereum-compatibility layer, not part of consensus state transition, storage, or extrinsic dispatch — it holds no funds, mints no issuance, and has no bearing on runtime invariants. Even within that off-chain component, the SQL-injection bug class from the CVE (unsanitized user input concatenated into a SQL query in PHP) has no reachable analog here.
