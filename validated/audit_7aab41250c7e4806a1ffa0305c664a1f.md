### Title
`StatusHandler#process` writes GitHub statuses by bare `sha` with no repository scoping, letting an attacker's signed webhook mutate a victim stack's commit state - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and applies the incoming status to every match, without filtering by the repository that authenticated the webhook. Every other handler (e.g. `CheckSuiteHandler`) scopes the query through `stacks` (derived from `payload.dig('repository', 'full_name')`), but `StatusHandler` does not, so a status webhook signed for the attacker's own repository/org can be applied to any `Commit` row in the database sharing the same SHA, including one belonging to a completely different, victim stack.

### Finding Description
The broken binding: the code assumes `commit.stack_id == stack_of(repository_owner_that_signed_the_webhook)`, but the actual code only guarantees `commit.sha == params.sha`, with no constraint tying `commit.stack_id` back to `payload.dig('repository', 'full_name')`.

Path:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb) verifies the HMAC signature via `verify_signature`, which calls `Shipit.github(organization: repository_owner)` — this only proves the payload was legitimately sent by GitHub for the *attacker's own organization/app installation*; it says nothing about which repository's commits the payload is allowed to affect.
- `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler.call(params)` → `new(params).process` (app/models/shipit/webhooks/handlers/handler.rb, lines 15-17).
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb, lines 20-24):
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This never touches `repository_name`/`stacks` (the helper defined in `Handler#stacks`, app/models/shipit/webhooks/handlers/handler.rb lines 32-38) that other handlers use to scope work to the authenticated repository. Contrast with `CheckSuiteHandler#process` (app/models/shipit/webhooks/handlers/check_suite_handler.rb, lines 13-17), which explicitly restricts to `stacks.where(branch: ...)` before touching commits.
- `Commit#create_status_from_github!` → `add_status { statuses.replicate_from_github!(stack_id, github_status) }` (app/models/shipit/commit.rb, lines 165-169, 366-386) creates the new `Status` scoped to the *matched commit's own* `stack_id` — i.e., the victim stack — and then recomputes `status`, potentially flipping `deployable?`/`blocked?` and triggering `stack.schedule_merges` if the simple state changes (lines 379-384).

Exploit flow: the attacker owns/controls a GitHub repository (or organization) that is itself wired to the same Shipit instance (a normal, unprivileged tenant onboarding), and arranges for one of its commits to share a SHA with a commit already tracked in the victim's stack (e.g., by forking the victim's public repo so identical commit objects/SHAs exist in both). The attacker then sends `POST /webhooks` with `X-Github-Event: status`, a signature valid for their own org, and body `{"sha": "<shared sha>", "context": "ci/kubernetes", "state": "failure", "repository": {"owner": {"login": "<attacker-org>"}, "full_name": "<attacker>/<attacker-repo>"}}`. `verify_signature` succeeds because it only checks the attacker's own org's webhook secret. `StatusHandler#process` then finds the victim's `Commit` row (matching by bare SHA) and writes a `failure` status onto it, changing the victim stack's `required_statuses`/`blocking_statuses` evaluation and thus `deployable?`/`blocked?` — a payload for one repository mutating another repository's commit/stack state.

Existing guards do not stop this: `verify_signature` authenticates the sender's own org, not the target repository; `drop_unhandled_event` and `ExplicitParameters` schema only validate shape, not repository ownership; there is no `require_permission!`/`stacks` scoping inside `StatusHandler` at all.

### Impact Explanation
An attacker who controls any onboarded repository can, with a single crafted `status` webhook, write arbitrary CI status (`failure`/`success`/`pending`, any `context`) onto commits belonging to a different, victim stack whenever a SHA collision (shared commit) exists between their repo and the victim's. This can force a required-context failure that blocks a pending deploy/merge, or conversely fabricate a `success` status that unblocks/enables a deploy that should not have shipped. This is a cross-repository state write authored by a party that never authenticated for the victim's repository — matching the "Critical: a payload for one repository mutating another's stack/commit/task/team" category.

### Likelihood Explanation
Preconditions: the attacker must operate a repository already connected to the same Shipit instance (a normal, low-privilege onboarding step for anyone able to add a repo/app install under their own account), and a commit SHA must be shared between attacker and victim repositories — realistic in fork relationships, shared upstream/vendor commits, or monorepo-derived repos where identical commit objects propagate by construction of Git's content addressing. Given the shared-SHA precondition (as stipulated in the question), the attack is a single unauthenticated-adjacent HTTP POST, fully repeatable against any stack containing that SHA, with no rate limiting or additional privilege required.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, mirroring `CheckSuiteHandler`/other handlers: resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) from `payload.dig('repository', 'full_name')` and restrict the `Commit` lookup to `stack.commits.where(sha: params.sha)` for stacks belonging to that repository, rejecting/ignoring matches from unrelated stacks even when the bare SHA collides.

### Proof of Concept
minitest plan (no live GitHub):
1. Create `victim_stack` (`Shipit::Stack`) with `required_statuses = ['ci/kubernetes']` (or configure via `DeploySpec`), and a `Commit` `victim_commit` with `sha: "deadbeef" * 5` belonging to `victim_stack`. Assert `victim_commit.deployable?` is currently `true` (no blocking status yet) — i.e., establish the binding `victim_commit.stack_id == victim_stack.id` and `victim_commit.deployable? == true` before the attack.
2. Build a webhook payload mimicking an attacker-owned repository: `{"sha" => victim_commit.sha, "context" => "ci/kubernetes", "state" => "failure", "repository" => {"full_name" => "attacker/unrelated-repo", "owner" => {"login" => "attacker-org"}}}`, i.e., the `repository.full_name` in the payload is not the victim's repository and has no `Repository`/`Stack` record tied to `victim_stack`.
3. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing controller-level signature check, since that only proves attacker-org authenticity, not repository targeting — the point under test is `StatusHandler#process` itself).
4. Assert: `victim_commit.reload.status.state == 'failure'` and `victim_commit.deployable? == false` (or `blocked?`) even though the request's `repository.full_name` never matched `victim_stack.repository`. This demonstrates the equality `commit.stack_id == stack_of(payload.repository)` is false yet the write still occurred — confirming the cross-repository state mutation.
