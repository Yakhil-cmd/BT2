### Title
Webhook signature verified against the organization named in `repository.owner.login`, but handlers act on the unrelated `repository.full_name` in the same unauthenticated-at-verification-time payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using an attacker-supplied field (`repository.owner.login` / `organization.login`), while every handler downstream resolves the actual repository/stack to mutate using a *different* attacker-supplied field (`repository.full_name`). Nothing binds these two fields together, so a signature that is valid for organization A's secret authorizes a payload whose `repository.full_name` names a completely different, unrelated repository B.

### Finding Description
`verify_signature` derives the organization used to pick the verification secret straight from the unauthenticated JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns a `GitHubApp` instance whose `webhook_secret` is configured per-organization: [3](#0-2) 

Verification is a pure HMAC compare of the raw body against that organization's secret: [4](#0-3) 

Once verification passes, every registered handler resolves the target repository/stack from an entirely separate field of the same body, `repository.full_name`, which was never part of the binding used to select the verification secret: [5](#0-4) [6](#0-5) 

The equality the app implicitly relies on is:
`organization used to select webhook_secret (repository.owner.login / organization.login)` == `repository whose stacks/commits/PRs are mutated (repository.full_name)`

This equality is never checked. Because the attacker fully controls the raw JSON body (up to producing a valid HMAC with a secret they know), they can set `repository.owner.login`/`organization.login` to an org whose `webhook_secret` they know (e.g., their own tenant/org registered on the same Shipit instance) while setting `repository.full_name` to any other repository tracked by this Shipit instance, including one owned by a different organization/team.

### Impact Explanation
Handlers dispatched from `WebhooksController#create` operate on whatever `repository.full_name` names, e.g. archiving review stacks (`ClosedHandler#process` → `review_stack.archive!`) and, more critically, `StatusHandler`, which is registered for the `status` event and writes commit status against the resolved repository/commit: [7](#0-6) 

An attacker who only controls one organization's webhook secret can forge `status`, `pull_request`, or `check_suite` events for a repository/stack belonging to a different organization on the same instance — closing/archiving PR review stacks they don't own, or writing forged commit statuses on a victim repository's commits that can be used to satisfy Shipit's deployability checks and enable an unauthorized deploy. This is a cross-repository write and a break of the deploy-safety binding, matching the Critical bucket ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Exploitation requires only knowledge of a legitimate `webhook_secret` for *any one* organization configured on the Shipit instance (a realistic scenario for multi-tenant Shipit deployments where different teams/orgs each have their own GitHub App/webhook secret configured) plus knowledge of the target repository's `full_name` — no GitHub credentials, Shipit session, or `ApiClient` token for the victim organization are needed. This is a straightforward crafted HTTP POST to `/webhooks` with a mismatched `owner.login`/`full_name` pair and a valid HMAC computed with the known secret.

### Recommendation
After verifying the HMAC, assert that the organization resolved for signature verification matches the owner encoded in `repository.full_name` (and `organization.login` when present) before dispatching to handlers; reject the request otherwise.

### Proof of Concept
1. Instance hosts two orgs: `attacker-org` (attacker knows its `webhook_secret`) and `victim-org` (owns repo `victim-org/prod-app`, tracked as a Shipit stack).
2. Attacker crafts a `status` (or `pull_request`) webhook body with:
   - `"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/prod-app"}`
   - `"sha"`/`"state"`/PR fields referencing a real commit/PR in `victim-org/prod-app`.
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known `webhook_secret` over the raw body.
4. `verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s `GitHubApp`, and `verify_webhook_signature` succeeds (correct secret, correct body).
5. `create` dispatches to handlers, which resolve `repository_name` = `victim-org/prod-app` and mutate that stack's status/PR/review-stack state — despite the attacker never having any credential or access tied to `victim-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
