### Title
Cross-repository Status forgery via repository-agnostic `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits to attach a GitHub status to by SHA alone, with no repository/stack scoping, unlike every other webhook handler in the engine. A legitimately-signed `status` webhook for one repository can therefore mutate `Shipit::Commit` rows — and trigger continuous-delivery side effects — belonging to any other tracked repository/stack that happens to contain a `Commit` row with the same SHA.

### Finding Description
The broken binding: for a genuine one-repository-one-commit-object model, it should hold that
`Shipit::Commit` row matched by a `status` webhook == `{ repository: params.repository.full_name, sha: params.sha }` (i.e. commit scoped to the stack whose repository issued the webhook).

Instead, the actual code is: [1](#0-0) 
which resolves to `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, repository-agnostic lookup across the entire `commits` table.

Every other handler in the engine derives a `stacks`/`repository` scope from `payload.dig('repository', 'full_name')` before touching any records:
- `PushHandler` scopes via `stacks.not_archived.where(branch:)` [2](#0-1) 
- `CheckSuiteHandler` scopes via `stacks.where(branch:)` before touching `stack.commits` [3](#0-2) 
- The base `Handler#stacks` method itself is built around `Repository.from_github_repo_name(repository_name)` [4](#0-3) 

`StatusHandler` alone ignores `payload['repository']` entirely for its query, even though the `params` schema doesn't require or use it [5](#0-4) .

`WebhooksController#verify_signature` only authenticates that the payload was signed by the organization named in `repository.owner.login` — it does not, and cannot, constrain which `Commit` rows the handler is allowed to touch: [6](#0-5) 
So a legitimately-signed webhook from organization/repo B's own GitHub App installation passes `verify_signature`, then reaches `StatusHandler.process`, which fans out to every `Shipit::Commit` sharing the SHA regardless of stack or repository.

Exploit flow: an attacker who controls a repository tracked by Shipit (e.g., their own repo B, in an org where the Shipit GitHub App is installed) crafts a commit whose SHA collides with a commit SHA already present in another tenant's `Commit` table — trivially achievable since Git commit SHAs are a hash purely of tree/parent/author/committer/message/timestamp content, so an attacker fully controls all of those fields except the parent history, and any repository initialized independently with identical initial content (e.g. the canonical empty-tree initial commit many scaffolds/templates use) yields identical SHAs across unrelated repositories. The attacker pushes/commits this SHA to repo B, then a real CI/status integration on repo B (or the attacker's own status-posting integration on their own repo) emits a genuine, correctly-signed `status` event with `state: success` for that SHA. Because `StatusHandler` does `Commit.where(sha: params.sha)` with no join to `repository_id`/`stack_id` derived from `payload['repository']`, every `Shipit::Commit` row across every unrelated `Stack`/`Repository` that has that same SHA gets `create_status_from_github!` called on it.

`create_status_from_github!` → `add_status` triggers `Hook.emit(:deployable_status, ...)` and, on success/pending transitions, `stack.schedule_merges` and `schedule_continuous_delivery` [7](#0-6) , meaning a forged-context "success" status on one tenant's commit can trigger continuous deployment merge/deploy scheduling on a completely unrelated tenant's stack.

### Impact Explanation
A single legitimately-signed webhook from an attacker-controlled repository writes `Shipit::Status` rows and mutates commit state for `Shipit::Commit` records belonging to any number of unrelated repositories/stacks that share the colliding SHA. This can flip an unrelated stack's commit to `success`, unblocking `deployable?` gating and scheduling continuous delivery (`schedule_merges`, `ContinuousDeliveryJob`) on a repository the attacker never authenticated against. This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy". The blast radius is every tenant repository in the same Shipit deployment whose tracked commit history happens to include the colliding SHA — repeatable at will since the attacker fully controls their own commit content and can retry with different well-known/trivial SHAs.

### Likelihood Explanation
Preconditions: the attacker needs a repository that is tracked by Shipit and capable of emitting a genuinely GitHub-signed `status` webhook (e.g. their own repo with a CI integration, or any repo where they can push commits and something posts a commit status). No Shipit session, API token, or `webhook_secret` is needed — the signature is genuinely produced by GitHub for the attacker's own repo. The only additional requirement is SHA collision with a target commit, which is feasible using well-known trivial/empty-tree initial commits that many unrelated repositories share by construction (same author/committer/timestamp/tree), making the attack directly reproducible rather than theoretical.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: derive `stacks`/`repository` from `payload.dig('repository', 'full_name')` and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { ... })`) instead of the repository-agnostic `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (models or controller test, no live GitHub calls needed — stub `verify_signature` as existing tests do):
1. Create 3 `Shipit::Stack` fixtures/records, each belonging to a distinct `Shipit::Repository` (distinct `full_name`).
2. Create one `Shipit::Commit` per stack, all three sharing the identical `sha` value (e.g. `"4b825dc642cb6eb9a060e54bf8d69288fbee4904"`), each with initial `state`/`status` `unknown`.
3. Post a `status` webhook (`X-Github-Event: status`) with `state: "success"`, the shared `sha`, and `repository.full_name` pointing only at stack #1's repository, stubbing `GithubHook#verify_signature` (or `verify_webhook_signature`) to return true as in `test/controllers/webhooks_controller_test.rb`.
4. Assert the binding before: `commit1.reload.state == "unknown" && commit2.reload.state == "unknown" && commit3.reload.state == "unknown"`.
5. After posting, assert `commit1.reload.state == "success" && commit2.reload.state == "success" && commit3.reload.state == "success"` — proving the webhook scoped to repository #1's payload mutated `Commit` rows on stacks #2 and #3 that never received or authenticated that webhook, violating the one-physical-commit-per-repository binding.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
