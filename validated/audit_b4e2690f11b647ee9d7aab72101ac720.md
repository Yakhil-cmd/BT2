### Title
Cross-tenant CCMenu stack read via unscoped `Stack.from_param!` bypassing `current_api_client.stack_id` filter - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController#stack` overrides `Api::BaseController#stack`/`#stacks` and resolves `params[:stack_id]` directly against `Stack.from_param!`, the unscoped model class method, instead of the tenant-scoped `stacks.from_param!` used everywhere else in the base controller. Because `ApiClient#check_permissions!` only validates the permission *name* (e.g. `read:stack`) and never checks `current_api_client.stack_id` against the requested stack, a token minted for stack A can read CCMenu build-status XML for any stack B.

### Finding Description
The intended binding is: `stack resolved by CCMenuController#show ∈ Stack.where(id: current_api_client.stack_id)` (when `stack_id?` is true), mirroring `Api::BaseController#stacks` at [1](#0-0) . Instead, `CCMenuController#stack` does: [2](#0-1) 
which queries `Stack.from_param!` against the entire `Stack` table with no `stack_id` filter, breaking the binding to false.

`require_permission :read, :stack` at [3](#0-2)  only triggers `require_permission!` → `current_api_client.check_permissions!(:read, :stack)`, which merely checks that the string `"read:stack"` is present in `permissions`: [4](#0-3) 
It never compares `current_api_client.stack_id` to the resolved stack, so it provides no tenant isolation on its own — that isolation is supposed to come exclusively from the `stacks` scope in `BaseController`, which `CCMenuController` bypasses.

Attack flow: attacker is a collaborator on stack A only, obtains a legitimate CCMenu URL/token for stack A via `Shipit::CCMenuUrlController#fetch` (creates an `ApiClient` with `permissions: %w[read:stack]` and `stack_id` = stack A) at [5](#0-4) . They then send `GET /api/stacks/:stack_id/ccmenu.xml?token=<token>` substituting stack B's `to_param`. `authenticate_api_client` (overridden in `CCMenuController`) validates the token via `ApiClient.authenticate` at [6](#0-5)  successfully (token is valid, just scoped to stack A), `require_permission!` passes because the client has `read:stack` permission (regardless of which stack), and `stack` resolves stack B unscoped, rendering stack B's deploy/build status.

### Impact Explanation
Any holder of a valid CCMenu token for one stack can read CI/deploy build status (latest deploy id, running state, ended_at) of any other stack in the installation by iterating `stack_id`/`to_param` values, regardless of `current_api_client.stack_id`. This is a cross-tenant unauthorized read of stack state, matching the High severity category ("unauthenticated"/cross-scope unauthorized read of stack state"). It is repeatable against arbitrary stacks with no rate limiting concern in scope, and the blast radius spans all stacks in the Shipit instance reachable from a single legitimately-issued, narrowly-scoped token.

### Likelihood Explanation
Preconditions are modest: attacker needs to be a legitimate collaborator/authorized user on at least one stack (stack A) to obtain a CCMenu token via the normal UI flow (`CCMenuUrlController#fetch`), and needs to know or guess another stack's `to_param` (typically `repo/branch`, often discoverable/enumerable). No secrets, no session, no elevated GitHub team membership required beyond access to stack A. This is a low-cost, easily repeated exploit once a CCMenu token is obtained.

### Recommendation
Change `CCMenuController#stack` to use the tenant-scoped lookup, e.g. `stacks.from_param!(params[:stack_id])` (removing the private `stack` override entirely so it falls back to `BaseController#stack`), ensuring `current_api_client.stack_id` is enforced consistently across all API controllers.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
class Shipit::Api::CCMenuControllerTest < ActionController::TestCase
  test "a token scoped to stack A cannot read stack B's ccmenu status" do
    stack_a = shipit_stacks(:shipit)
    stack_b = shipit_stacks(:cyclimse)

    client_for_stack_a = ApiClient.create!(
      creator: shipit_users(:walrus),
      name: 'CCMenu Client',
      permissions: %w[read:stack],
      stack: stack_a,
    )

    get :show, params: {
      stack_id: stack_b.to_param,
      token: client_for_stack_a.authentication_token,
    }

    # Binding under test: resolved stack ∈ Stack.where(id: current_api_client.stack_id)
    assert_not_equal stack_a.id, stack_b.id
    assert_response :forbidden # or :not_found after fix; currently returns :ok with stack_b data
  end
end
```
Before the fix this test fails because `response.status == 200` and the rendered XML corresponds to `stack_b`, demonstrating the cross-tenant read.
