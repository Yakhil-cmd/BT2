### Title
Leftover Change From Fee-Asset Swap Is Silently Forfeited Instead Of Returned To Holding - (File: polkadot/xcm/xcm-executor/src/lib.rs)

### Summary
When the XCM executor needs to pay execution/delivery fees in an asset different from the one the user actually holds, `take_fee()` swaps the held asset for the exact fee asset via `Config::AssetExchanger::exchange_asset(..., maximal=false)`. The `SingleAssetExchangeAdapter` implementation of `exchange_asset` bundles both the swapped-out fee asset **and** any unspent "change" from the swap into a single opaque `AssetsInHolding` result. `take_fee()` then hands that entire bundle to `Config::FeeManager::handle_fee`, which either burns it or forwards it wholesale to a fee-receiver account. Any leftover change belonging to the origin is never returned to the XCM Holding Register, so it is lost — the same class of bug as the GlueX report, where excess input from an "exact-output" style swap never makes it back to its rightful owner.

### Finding Description
`take_fee` in the XCM executor withdraws an exact amount of the "wanted" asset from holding/fees register and, if it differs from the asset actually needed for fees, converts it: [1](#0-0) 

The conversion is performed with `maximal=false`, i.e. a "tokens-for-exact-tokens" swap (analogous to the report's `swapTokensForExactTokens`). Inside `SingleAssetExchangeAdapter::exchange_asset`, the `minimal` branch calls `swap_tokens_for_exact_tokens`, which returns `(credit_out, credit_change)` — the exact fee asset plus any unspent input asset: [2](#0-1) 

Both `credit_out` and `credit_change` (if any) are merged into a single `result: AssetsInHolding` and returned as one value — there is no channel back to the executor distinguishing "the fee that was needed" from "unspent input that belongs to the origin." Back in `take_fee`, this combined value (`paid`) is passed wholesale to `Config::FeeManager::handle_fee`: [3](#0-2) 

`FeeManager::handle_fee` implementations either burn everything (`()` / default) or deposit everything into a fixed `ReceiverAccount` (`SendXcmFeeToAccount`): [4](#0-3) [5](#0-4) 

Neither implementation is capable of splitting out change and returning it to `self.holding`; the trait itself only distinguishes "fee" from "context/reason," with no notion of "unspent change belonging to the origin." Contrast this with the `ExchangeAsset` XCM *instruction* handler, which correctly puts the entire `exchange_asset` result — including any leftover — back into the Holding Register for the user to reclaim: [6](#0-5) 

`take_fee`'s internal use of the same `AssetExchange` trait does not have this safety net: `paid` never returns to holding, so any part of it is unconditionally consumed as a "fee," even though a portion is actually the origin's own change.

The amount withdrawn for conversion, `asset_to_pay_for_fees`, is computed just beforehand via `calculate_asset_for_delivery_fees`, which quotes the *necessary* input using `QuotePrice::quote_price_tokens_for_exact_tokens`: [7](#0-6) 

If that quote's rounding does not exactly match the rounding performed by the actual swap execution path (`do_swap_tokens_for_exact_tokens` / `balance_path_from_amount_out` / `get_amount_in`), a non-zero `credit_change` is produced on essentially every fee-conversion swap, and that change is what gets forfeited.

`Config::AssetExchanger = SingleAssetExchangeAdapter<...>` (backed by `pallet-asset-conversion`) is wired into multiple production runtimes, e.g. Asset Hub Westend/Rococo, Penpal, Bridge Hub, Collectives, Coretime, People — confirming this is reachable in shipped configurations, not a mock-only path.

### Impact Explanation
Any unprivileged account that submits or triggers an XCM program using `PayFees`/`BuyExecution` with a fee asset different from what's actually needed (a normal, permitted flow, e.g. paying delivery fees in a non-native asset that must be converted via the on-chain AMM) can cause a small, deterministic amount of its own asset to be silently diverted to the fee burn/receiver instead of returned to holding for eventual use/refund. This is a genuine, repeatable loss-of-funds bug for the message's origin, matching the report's core invariant violation ("leftover from an exact-output-style operation is not returned to its rightful owner"), though the magnitude here is bounded by rounding/quote-vs-execution drift rather than an entire uncapped swap output — i.e., it is a dust/rounding-level loss per occurrence rather than a large one-shot theft.

### Likelihood Explanation
The vulnerable code path (`take_fee` converting via `AssetExchanger` when the "wanted" and "needed" fee assets differ) is exercised on any parachain that has `AssetExchanger` configured to a real swap adapter and processes messages using `PayFees`/`BuyExecution` with a mismatched asset — a normal and encouraged usage pattern under the newer `PayFees`/`DryRunApi` fee-payment model referenced in the migration notes. No governance, validator, or attacker-privileged capability is required; a regular signed extrinsic via `pallet_xcm::execute`/`send` (or any XCM triggering delivery-fee conversion) suffices.

### Recommendation
`take_fee` (and the `AssetExchange` trait more generally) should not treat the full result of a "minimal" exchange as fee. `SingleAssetExchangeAdapter::exchange_asset`/the `AssetExchange` trait should expose the change separately (or `take_fee` should re-derive/split it based on the known `want_amount`), and any leftover portion should be `subsume_assets`'d back into `self.holding` (mirroring what the `ExchangeAsset` instruction handler already does at polkadot/xcm/xcm-executor/src/lib.rs:1755-1771) instead of being passed to `FeeManager::handle_fee`.

### Proof of Concept
No live network or mocked-authority test was executed; this analysis is based on static code tracing only, as required. A concrete integration reproduction would involve:
1. Configuring a test runtime with `pallet-asset-conversion` + `SingleAssetExchangeAdapter` as `AssetExchanger`, and `XcmFeeManagerFromComponents` with a `HandleFee` that records what it receives (or `SendXcmFeeToAccount`).
2. Creating a pool where `quote_price_tokens_for_exact_tokens`'s rounding for the needed fee amount diverges (even by 1 unit) from the actual amount computed inside `do_swap_tokens_for_exact_tokens`.
3. Submitting an XCM via `pallet_xcm::execute` from a normal signed origin containing `WithdrawAsset` (asset A) + `PayFees`/`BuyExecution` (fee asset B, requiring on-chain conversion from A).
4. Asserting: `self.holding` after `post_process()` does not contain the expected leftover of asset A, and the recorded `handle_fee` call received more than the strict fee amount needed for B.

This was not executed against a running node/test harness in this session; the above is a proposed harness for the background engineering team to run against `polkadot/xcm/xcm-executor/src/tests` (which already has scaffolding for `PayFees`/`ExchangeAsset`/transactional rollback tests, e.g. `polkadot/xcm/xcm-executor/src/tests/transactional.rs`) to confirm the numeric leak.
