### Title
Bridge Pending-Event Queue Silently Drops High-Nonce Value-Transfer Requests When Full, Enabling Griefing DOS on Asset Transfers - (File: node/sc/bridge_manager.go)

### Summary

`BridgeInfo.AddRequestValueTransferEvents` in `node/sc/bridge_manager.go` enforces a soft cap of `maxPendingNonceDiff = 1000` on the in-memory pending request event queue. When the queue is full, any incoming event whose nonce is **greater than or equal to** the current maximum nonce in the queue is **silently discarded** via `continue`. Because bridge contract nonces are strictly sequential, this means that once the queue fills up, every subsequent legitimate value-transfer event is dropped. An attacker who floods the bridge with cheap `requestValueTransfer` calls can fill the queue with their own low-nonce events, causing all later users' events to be silently lost from the relay pipeline. The code itself acknowledges the gap with a `TODO` comment.

### Finding Description

`BridgeInfo.pendingRequestEvent` is allocated with `bridgepool.UnlimitedItemSortedMap` (no hard limit at the data-structure level):

```go
pendingRequestEvent: bridgepool.NewItemSortedMap(bridgepool.UnlimitedItemSortedMap),
``` [1](#0-0) 

The only size enforcement is inside `AddRequestValueTransferEvents`:

```go
func (bi *BridgeInfo) AddRequestValueTransferEvents(evs []IRequestValueTransferEvent) {
    for _, ev := range evs {
        if bi.pendingRequestEvent.Len() > maxPendingNonceDiff {
            flatten := bi.pendingRequestEvent.Flatten()
            maxNonce := flatten[len(flatten)-1].Nonce()
            if ev.Nonce() >= maxNonce || bi.pendingRequestEvent.Exist(ev.Nonce()) {
                continue          // ← silent drop
            }
            bi.pendingRequestEvent.Remove(maxNonce)
            ...
        }
        bi.pendingRequestEvent.Put(ev)
    }
}
``` [2](#0-1) 

`maxPendingNonceDiff` is 1000: [3](#0-2) 

The eviction condition `ev.Nonce() >= maxNonce` is always true for events arriving in normal sequential order (each new event has a nonce one higher than the previous maximum). Therefore, once the queue reaches 1001 entries, **every subsequent event is silently discarded** — no error is returned, no retry is scheduled, and no log at a level that would alert operators.

The caller `ProcessRequestEvent` in `sub_event_handler.go` contains an explicit TODO acknowledging the missing guard:

```go
// TODO-Kaia need to manage the size limitation of pending event list.
handleBridgeInfo.AddRequestValueTransferEvents([]IRequestValueTransferEvent{ev})
``` [4](#0-3) 

The recovery path (`vt_recovery.go`) can re-inject dropped events, but it is also capped at `maxPendingTxs = 1000`: [5](#0-4) 

If the attacker keeps the queue saturated, recovery events are also dropped by the same `ev.Nonce() >= maxNonce` guard, creating a persistent stall.

### Impact Explanation

Any user can call `requestValueTransfer` on the bridge contract (it is a public, permissionless function). An attacker who submits enough requests to fill the 1000-slot queue causes all subsequent legitimate value-transfer events to be silently dropped from the relay pipeline. Affected assets — KAIA, ERC-20 tokens, and ERC-721 NFTs — remain locked in the source bridge contract and are not minted/released on the counterpart chain. This is a direct impact on bridged-asset availability and matches the allowed impact category: *unauthorized … unlock … affecting KAIA, bridged assets*.

### Likelihood Explanation

The attack requires only a funded account and the ability to call the public bridge contract. `maxPendingNonceDiff = 1000` is a small threshold; at 2 × 500 TPS (the comment's own estimate), the queue can be saturated in under one second. The TODO comment confirms the developers are aware the guard is incomplete. The attack is cheap, repeatable, and requires no privileged access.

### Recommendation

1. **Hard-cap the queue at the data-structure level** by passing a finite size to `NewItemSortedMap` instead of `UnlimitedItemSortedMap`.
2. **Fix the eviction policy**: when the queue is full, drop the event with the *lowest* nonce (already processed or furthest from the current handle nonce), not the highest. This preserves forward progress.
3. **Return an error or emit a warning-level log** when an event is dropped so operators can detect the condition.
4. **Rate-limit per-sender bridge requests** at the contract level (e.g., require a minimum fee or cooldown) to raise the cost of flooding.

### Proof of Concept

```
1. Attacker calls requestValueTransfer() on the bridge contract 1001 times,
   generating events with nonces 0 … 1000.

2. SubBridge observes these events and calls ProcessRequestEvent() for each,
   which calls AddRequestValueTransferEvents().

3. After the 1001st event, pendingRequestEvent.Len() == 1001 > maxPendingNonceDiff (1000).

4. Legitimate user calls requestValueTransfer(), generating event with nonce 1001.

5. AddRequestValueTransferEvents() evaluates:
       maxNonce = 1000   (highest nonce currently in queue)
       ev.Nonce() = 1001 >= maxNonce  →  continue   // silently dropped

6. The legitimate user's KAIA/ERC-20/ERC-721 transfer is never relayed.
   The asset remains locked in the source bridge contract indefinitely
   (or until the attacker stops flooding and recovery eventually catches up).
```

// AddRequestValueTransferEvents adds events into the pendingRequestEvent.
func (bi *BridgeInfo) AddRequestValueTransferEvents(evs []IRequestValueTransferEvent) {
	for _, ev := range evs {
		if bi.pendingRequestEvent.Len() > maxPendingNonceDiff {
			flatten := bi.pendingRequestEvent.Flatten()
			maxNonce := flatten[len(flatten)-1].Nonce()
			if ev.Nonce() >= maxNonce || bi.pendingRequestEvent.Exist(ev.Nonce()) {
				continue
			}
			bi.pendingRequestEvent.Remove(maxNonce)
			vtPendingRequestEventCounter.Dec(1)
			logger.Trace("List is full but add requestValueTransfer ", "newNonce", ev.Nonce(), "removedNonce", maxNonce)
		}

		bi.SetRequestNonceFromCounterpart(ev.GetRequestNonce() + 1)
		bi.pendingRequestEvent.Put(ev)
		vtPendingRequestEventCounter.Inc(1)
	}
	logger.Trace("added pending request events to the bridge info:", "bi.pendingRequestEvent", bi.pendingRequestEvent.Len())

	select {
	case bi.newEvent <- struct{}{}:
	default:
	}
}
