### Title
Unauthenticated webhook forgery via organization/repository binding mismatch enabling forged team membership and CI status - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on an attacker-controlled field in the unverified JSON body — `repository.owner.login`/`organization.login` — while the handlers that consume the same payload act on a *different* field, `repository.full_name` or `organization.login`/`team`/`member`, taken from `Handler#repository_name` and `MembershipHandler`. If any configured organization has no `webhook_secret` set (a documented, supported configuration, see `config/secrets.development.example.yml`), signature verification for that organization is unconditionally skipped, letting an attacker submit an arbitrary unsigned payload that is dispatched to handlers referencing any other repository/organization/team in the installation.

### Finding Description
`verify_signature` computes the app to verify against purely from body content that has not yet been authenticated: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally treats the request as verified when no `webhook_secret` is configured for the resolved organization: [3](#0-2) 

This is a documented, legitimate configuration state (`webhook_secret: # nil`) for organizations in a multi-org Shipit installation: [4](#0-3) 

Once verification "passes" for the attacker-chosen (unsecured) organization, the raw body is dispatched unchanged to handlers, which key off *different* fields of the same payload than the one used for signature selection: `Handler#repository_name` reads `repository.full_name`, decoupled from `repository.owner.login` used at verification time: [5](#0-4) 

`MembershipHandler` is the most damaging consumer: it creates/uses a `Team` and a `User` purely from unauthenticated payload fields and adds the named member to that team: [6](#0-5) 

Team membership is exactly what governs application-wide authorization: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who knows (or controls) one configured GitHub organization in the installation that has no `webhook_secret` set can send an unsigned `membership` webhook naming any `team` (matching `Shipit.github_teams`) and any `member.login` (their own real GitHub login). `MembershipHandler#process` will create the team if needed and add the attacker's user as a member with no GitHub-side verification that the attacker is actually a member of that team/org. The attacker then completes the real GitHub OAuth login flow as themselves (`GithubAuthenticationController#callback` / `User.find_or_create_from_github`), and `current_user.authorized?` now returns `true` because of the forged team membership — granting full access to trigger deploys, rollbacks, and stack management across every repository configured in the Shipit instance. This is an authentication/authorization-boundary break equivalent to the "organization that authenticated versus the repository/team that is written" case explicitly called out as in-scope, and results in an unauthorized deploy path — a Critical-tier impact.

### Likelihood Explanation
Requires only that the Shipit deployment be configured with more than one GitHub organization (a supported, documented setup) and that at least one of those organizations does not have a `webhook_secret` configured — the example config ships with `webhook_secret: # nil` as the default. No privileged credentials, GitHub App private key, or repository write access are needed; the attacker only needs network access to the public webhook endpoint and knowledge of one org name using the app without a webhook secret set.

### Recommendation
Do not let the same untrusted field select the verification key and the acted-upon target. Bind verification and processing to the same authenticated organization: after choosing the `GitHubApp` config, ensure all handlers reject payloads whose `repository.full_name`/`organization.login`/`team.organization` do not belong to the same organization that was used to verify the signature. Additionally, treat a missing `webhook_secret` as a hard configuration error (fail closed) rather than an implicit bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `org-a` (no `webhook_secret`) and `org-b` (has a `webhook_secret`, hosts the real, sensitive team `Shipit.github_teams`).
2. POST to `/github/webhooks` (or whichever route mounts `WebhooksController`) with header `X-Github-Event: membership` and no valid `X-Hub-Signature`, and a JSON body:
```json
{
  "action": "added",
  "organization": { "login": "org-a" },
  "team": { "id": 123, "name": "shopify/developers", "slug": "developers", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
Because `repository_owner`/`organization.login` resolves to `org-a`, `verify_signature` looks up `Shipit.github(organization: "org-a")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the (absent) signature.
3. `MembershipHandler#process` creates/loads the team with `github_id: 123` and adds `attacker-github-login` as a member — even though `team.id` here can be crafted to collide with an existing authorized `Shipit.github_teams` team's `github_id`.
4. Attacker completes real GitHub OAuth as `attacker-github-login`; `current_user.authorized?` now returns `true`, granting full deploy/rollback access.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
