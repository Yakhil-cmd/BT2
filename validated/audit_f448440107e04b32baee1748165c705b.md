### Title
Cross-repository Commit status forgery via SHA collision in `StatusHandler#process` unscoped `Commit.where(sha:)` query - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits solely by `sha`, with no scoping to the repository/stack that the webhook signature was verified against. Because `Commit.sha` is only unique per `stack_id` (not globally), and because certain SHAs (e.g. the well-known empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, or any hash collision an attacker can engineer for a low-entropy tree/commit) are identical across unrelated git repositories, a status webhook validly signed by organization B's `webhook_secret` can cause `create_status_from_github!` to execute against a `Commit` row that belongs to stack A.

### Finding Description
The binding the system is supposed to enforce is:
`repository_owner` (used in `WebhooksController#verify_signature` at app/controllers/shipit/webhooks_controller.rb:24-49, derived from `params.dig('repository','owner','login')`) `==` the repository owning the `Commit`/`Stack` row(s) mutated by the handler.

`verify_signature` only proves that the payload was signed with the `webhook_secret` for the organization identified in the payload's own `repository.owner.login` field [1](#0-0) . It does not constrain which `Stack`/`Commit` rows the handler is allowed to touch — that decision is made later, independently, by `StatusHandler#process`:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

This query is global across the entire `commits` table and is not filtered by repository, stack, or organization. The database only enforces uniqueness of `sha` per `stack_id` (index `index_commits_on_stack_id_and_sha`, per db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb), which by construction confirms multiple stacks can hold rows with the identical `sha` value. `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` in app/models/shipit/commit.rb:165-169, writing a `Status` row scoped to whatever `commit.stack_id` happens to be, `stack.update_undeployed_commits_count`, `Hook.emit(:commit_status, ...)`, and can trigger `stack.schedule_merges` if the new status is `success` — all against stack A even though the request never proved control of stack A's repository.

Root cause: signature verification authenticates "the sender knows organization B's secret and named repository B in the payload," but the mutation performed afterward is keyed only on `sha`, an attacker-controlled/collision-able value, with no cross-check that `commit.stack.repository` (or `github_repo_name`) matches `repository_owner`/`params.dig('repository','full_name')` from the verified payload.

Attack flow:
1. Attacker owns repository B (any public/free GitHub repo) and has Shipit configured to track stack B (or simply needs *a* `Commit` row for B with a chosen SHA — this can be arranged if B is tracked by Shipit, or via any push that creates a commit fetched by Shipit's normal sync).
2. Attacker crafts/uses a commit whose SHA collides with a commit already present in victim stack A (trivially achievable with the empty-tree SHA `4b825dc642cb6eb9a060e54bf8d69288fbee4904`, which is identical in every git repository and commonly appears as a parent/merge-base commit).
3. Attacker computes a valid `X-Hub-Signature` for repository B using B's own `webhook_secret` (which the attacker legitimately possesses/controls as B's repo admin) and POSTs to `/webhooks` with `X-Github-Event: status`, `repository.owner.login` = B's org, `sha` = the colliding SHA, `state: success`.
4. `verify_signature` passes because B's own secret correctly signs the payload for B's own organization.
5. `StatusHandler#process` runs `Commit.where(sha: <colliding sha>)`, which matches both B's commit row and A's commit row, and calls `create_status_from_github!(params)` on A's row too, injecting a forged `success` status into stack A's commit and potentially triggering `stack.schedule_merges` for stack A.

Existing guards that fail to stop this: `verify_signature` verifies only the payload signature and organization named in the payload, not the target rows mutated; `drop_unhandled_event` and the `ExplicitParameters` schema (`params do ... end`) only validate payload shape, not repository ownership of the affected `Commit`; there is no `stack.github_repo_name == params.dig('repository','full_name')` check anywhere in `StatusHandler` or a shared `Handler` base before the mutation.

### Impact Explanation
An attacker who owns any GitHub repository (unprivileged relative to victim organizations) can inject forged commit statuses into another organization's `Stack`/`Commit` — a payload for one repository mutating another's stack/commit, matching the "Critical" category explicitly listed ("a payload for one repository mutating another's stack, commit, task or team"). Depending on the victim stack's configuration, a forged `success` status can make a commit `deployable?` (app/models/shipit/commit.rb:227-229) and can trigger `stack.schedule_merges` (commit.rb:383) if `continuous_deployment?` is enabled, potentially causing an unauthorized deploy/merge decision for stack A. This is repeatable against any stack whose commit history contains a SHA that also exists in a repository the attacker controls — the empty-tree SHA guarantees at least one universally-shared collision point across virtually all git repositories tracked by Shipit.

### Likelihood Explanation
Preconditions: the attacker needs (a) their own GitHub repository/organization already registered as a Shipit stack (or otherwise able to get a `Commit` row created with the chosen SHA under their own stack — this is a normal, low-privilege action for any repo owner using Shipit), and (b) a target stack A whose commit history contains a colliding SHA — trivially true for the empty-tree SHA, which appears in numerous real repositories as an ancestor/merge-base commit. No Shipit secrets, session, or `Shipit.github_teams` membership are needed — only the attacker's own repository's `webhook_secret`, which they legitimately hold as that repository's administrator. The exploit is cheap (a single signed HTTP POST) and repeatable against every stack containing a matching SHA.

### Recommendation
Scope the `StatusHandler` (and any other SHA-keyed handler) lookup to the repository that was authenticated by `verify_signature`. Concretely, add a check in `Commit.where(sha: params.sha)` that filters by `stack.github_repo_name` (or `repository`) matching `params.dig('repository','full_name')`/`repository_owner` from the verified payload, e.g. join through `stack` and require `stacks.repository_owner`/`repository_name` to equal the payload's `repository.full_name`, before calling `create_status_from_github!`.

### Proof of Concept
Minitest integration test plan (no live GitHub):
1. Create `stack_a` with `repository_owner: 'victim-org'`, `repository_name: 'repo-a'`, and a `commit` fixture with `sha: '4b825dc642cb6eb9a060e54bf8d69288fbee4904'`, `stack: stack_a`.
2. Create `stack_b` with `repository_owner: 'attacker-org'`, `repository_name: 'repo-b'`, with its own `commit` fixture using the *same* `sha`, `stack: stack_b`.
3. Configure `Shipit.github(organization: 'attacker-org')` with a known `webhook_secret` in test secrets.
4. Build a JSON payload: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/repo-b"}, "sha": "4b825dc642cb6eb9a060e54bf8d69288fbee4904", "state": "success", "context": "ci"}`.
5. Compute `X-Hub-Signature` using attacker-org's webhook secret.
6. POST to `/webhooks` with `X-Github-Event: status` and the computed signature.
7. Assert response is `200 OK` (signature accepted).
8. Reload `stack_a`'s commit and assert `commit.status.state == 'success'` (or that a new `Status` row was created with `stack_id: stack_a.id`) — proving the equality `repository_owner (attacker-org) == repository owning the mutated Commit (stack_a/victim-org)` is violated, since stack A's commit was mutated by a request authenticated only for attacker-org.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )
      head(422) unless verified

      Rails.logger.info([

    rescue Shipit::GithubOrganizationUnknown => e
