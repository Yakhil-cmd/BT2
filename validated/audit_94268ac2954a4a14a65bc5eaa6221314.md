### Title
Cross-tenant webhook forgery via no-secret organization bypasses signature verification and lets `LabeledHandler` archive/unarchive an arbitrary victim's review stack - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and thus the `webhook_secret`) using only `params.dig('repository','owner','login')`, and `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that organization's config has no `webhook_secret` configured. Because the handler that actually processes the event (`LabeledHandler` → `ReviewStackAdapter`) resolves the target repository/stack from the independent field `params.repository.full_name`, an attacker who owns a repo under any Shipit-configured, secret-less organization can set `repository.owner.login` to that org while setting `repository.full_name` to an arbitrary victim repository, bypassing signature verification entirely and mutating the victim's stack.

### Finding Description
The broken binding: the code assumes `repository_owner (used for signature verification) == owner segment of repository.full_name (used for repository resolution)`, but no code enforces this equality.

Path:
1. `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) computes `repository_owner` from `params.dig('repository','owner','login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
2. `GitHubApp#verify_webhook_signature` returns `true` immediately if the resolved org's `webhook_secret` is blank [2](#0-1) , i.e., no HMAC check is performed at all for that org.
3. `WebhooksController#create` then parses the raw body and dispatches to handlers for the event with no re-check that `repository.full_name`'s owner matches `repository_owner` [3](#0-2) .
4. `LabeledHandler#repository` resolves the actual Shipit `Repository` from `params.repository.full_name` [4](#0-3) , a field completely independent from `repository.owner.login` used for verification.
5. `LabeledHandler#handle` calls `stack.archive!` or `stack.unarchive!` on the `ReviewStackAdapter`, which looks up the review stack by `environment: "pr#{params.number}"` under `repository.review_stacks` [5](#0-4)  and, on unarchive, re-enqueues it for provisioning [6](#0-5)  or deprovisions/archives it [7](#0-6) .

Exploit flow: attacker registers/owns a GitHub org+repo that is configured in Shipit but whose entry in `Shipit.github_teams`/app config has no `webhook_secret` (e.g., a low-security or staging org onboarded without a secret). They send `POST /webhooks` with header `X-Github-Event: pull_request`, body `action: "labeled"`, `repository.owner.login` = that secret-less org, `repository.full_name` = "victim-org/victim-repo", `number` matching an existing review-stack PR number, and forged `pull_request`/`sender`/`labels` fields. `verify_webhook_signature` short-circuits to `true`, `drop_unhandled_event` passes because `pull_request`/`labeled` is a handled event, and `LabeledHandler` archives or unarchives the victim stack — a stack the attacker never authenticated against and has no ability to interact with through legitimate means.

Existing guards fail because: `verify_signature` never compares `repository_owner` against `repository.full_name`'s owner segment; `drop_unhandled_event` only checks the event type is handled, not repo identity; the `ExplicitParameters` schema in `LabeledHandler` only validates types/presence, not cross-consistency with `repository_owner`; and `Repository.from_github_repo_name` performs no ownership/ACL check tying the caller's authenticated org to the resolved repository.

### Impact Explanation
An unauthenticated, unprivileged attacker can archive or unarchive (re-provision) any Shipit review stack belonging to any repository, as long as: (a) some organization configured in Shipit lacks a `webhook_secret`, and (b) the attacker can enumerate/guess a target `repository.full_name` + PR `number`. This is a payload for one repository mutating another repository's stack — squarely a Critical-severity condition per the stated rules. Unarchiving forces `Shipit::ReviewStackProvisioningQueue.add(stack)`, causing re-provisioning/deploy activity for the victim stack; archiving deprovisions and archives it, disrupting the victim's review environment. The blast radius spans every stack/repository configured in the same Shipit instance, since the resolution of the target is entirely attacker-supplied and decoupled from the field used for authentication. Combined with an `ignore_ci: true` victim stack, subsequent deploy/merge machinery treats the stack as shippable without CI gating, amplifying the effect of the forced state transitions, though the finding is exploitable independent of that amplification.

### Likelihood Explanation
Preconditions: at least one Shipit-configured GitHub organization/app entry with a blank `webhook_secret` (a real, plausible misconfiguration this control is supposed to guard against — the code explicitly special-cases "no secret" as automatically verified rather than rejecting it), and a target victim repository with an existing review stack (`ignore_ci: true` is one such stack type, not a strict requirement for the initial forgery). Attacker cost is a single unauthenticated HTTP POST with a crafted JSON body; no GitHub credentials, Shipit session, or API token are required. It is fully repeatable against arbitrary repositories/stacks in the same Shipit deployment.

### Recommendation
In `WebhooksController#verify_signature`, require a `webhook_secret` to be configured for every organization that is expected to send webhooks (fail closed instead of "verified" when blank), and additionally validate that the owner segment of `params.repository.full_name` matches `repository_owner` before dispatching to any handler, rejecting mismatches with `head(422)`.

### Proof of Concept
minitest plan (webhooks controller test, no live GitHub):
1. Configure `Shipit.github_teams`/app config with an org `"no-secret-org"` that has no `webhook_secret`, and a separate victim org `"victim-org"` with a real secret.
2. Create `victim_repository = Shipit::Repository.create!(... , owner: "victim-org", name: "victim-repo")`, enable `review_stacks_enabled`, and create a `Shipit::ReviewStack` under it with `environment: "pr42"`, `ignore_ci: true`, not archived.
3. Assert binding before: `victim_stack.archived? == false`.
4. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body: `action: "labeled"`, `number: 42`, `repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" }`, `pull_request: { state: "open", head: {...}, labels: [{name: provisioning_label}], ... }`, `sender: { login: "attacker" }`.
5. Assert response is `200`/`head(:ok)` (i.e., signature check passed) rather than `422`.
6. Assert binding after: `victim_stack.reload.archived?` has changed (or `archive!`/`unarchive!`/`ReviewStackProvisioningQueue.add` was invoked) — demonstrating that a repository (`no-secret-org`) which never authenticated `victim-org`'s webhook was able to mutate `victim-org/victim-repo`'s stack state.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
