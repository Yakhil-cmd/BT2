### Title
Webhook signature verified against `repository.owner.login`'s org secret while handlers act on the attacker-controlled `repository.full_name` — cross-organization webhook forgery in multi-app deployments - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the HMAC signature against using `repository_owner`, itself extracted from the *attacker-supplied JSON body* (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). Once the signature check passes, every downstream `Shipit::Webhooks::Handlers::Handler` subclass resolves the target `Repository`/`Stack` using a *different* field from the same attacker-supplied body: `payload.dig('repository', 'full_name')`. Nothing enforces that these two fields refer to the same organization.

### Finding Description
The binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository the handler writes to`

In `app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` (in `lib/shipit.rb`) looks up a per-organization `GitHubApp` instance (and thus a distinct `webhook_secret`) when Shipit is configured with the documented multi-org schema (`docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`):
```ruby
def github(organization: github_default_organization)
  ...
  config = github_app_config(organization)
  raise GithubOrganizationUnknown, organization if config.nil?
  @github[organization] ||= GitHubApp.new(organization, config)
end
``` [2](#0-1) 

Every handler, however, resolves the affected `Repository`/`Stack` from a completely independent field of the same JSON body:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [3](#0-2) 

Because the whole request body is attacker-controlled prior to signature validation, nothing prevents `repository.owner.login` from naming an organization the attacker legitimately administers (and therefore knows the `webhook_secret` for, since they configured or can view/rotate that GitHub App's webhook secret as its owner), while `repository.full_name` names a stack belonging to an entirely different, victim organization also hosted on the same multi-tenant Shipit instance. The HMAC only proves "the body was signed with OrgA's secret" — it does not prove that the `full_name` field used for dispatch is `OrgA`-owned. `PushHandler`, `StatusHandler`, and the `PullRequest::*Handler`s all key off `repository.full_name` to find and mutate state (`sync_github`, `create_status_from_github!`, `archive!`/`unarchive!`/`find_or_create!`) with no additional check that `full_name`'s owner matches the organization that authenticated the request: [4](#0-3) [5](#0-4) [6](#0-5) 

Of particular concern is `StatusHandler`, which creates a `Status` on any `Commit` matching the attacker-chosen `sha`, regardless of which stack/org that commit belongs to:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [5](#0-4) 
Commit statuses feed directly into `required_statuses`/`blocking_statuses` used by `MergeRequest#all_status_checks_passed?` and `Stack#deployment_checks_passed?` to gate merges and deploys, so a forged "success" status on a victim's commit can unblock deploys/merges that should have been blocked by real, unmet CI requirements.

### Impact Explanation
On a Shipit instance configured for multiple GitHub organizations (the documented, supported multi-tenant setup), an attacker who administers one onboarded organization can forge webhook payloads whose `repository.owner.login`/`organization.login` names their own org (satisfying signature verification with a secret they legitimately know) while `repository.full_name` names a repository belonging to a different tenant. This breaks organization isolation and can be used to inject forged CI/commit statuses that gate a victim stack's merge queue and deployability checks (`Stack#deployment_checks_passed?`, `MergeRequest#all_status_checks_passed?`), enabling an unauthorized deploy or merge on infrastructure the attacker does not otherwise control — matching the required "unauthorized deploy, rollback or merge" impact class.

### Likelihood Explanation
Requires: (1) a Shipit deployment using the multi-organization GitHub App configuration schema, and (2) the attacker to legitimately administer at least one of the onboarded organizations (able to read/rotate that org's GitHub App webhook secret) while targeting a different onboarded organization's stack. This is a realistic scenario for any shared/multi-tenant Shipit deployment, which is an explicitly documented and tested configuration (`docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`, `test/unit/shipit_test.rb`).

### Recommendation
After signature verification succeeds against the organization derived from the payload, re-validate that every field the handler subsequently uses to select the target repository/stack (`repository.full_name`, or any `owner.login` embedded in it) belongs to that same verified organization before dispatching to handlers — e.g., assert `repository.full_name.split('/').first.casecmp(repository_owner) == 0` in `WebhooksController#verify_signature`, or thread the verified organization into `Handler#stacks` and filter/reject stacks whose repository owner doesn't match it.

### Proof of Concept
1. Configure Shipit with the multi-org schema, onboarding `OrgA` (attacker-administered) and `OrgB` (victim), each with its own GitHub App and `webhook_secret`.
2. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<victim_commit_sha_belonging_to_OrgB_stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using OrgA's known `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` calls `Shipit.github(organization: 'OrgA')`, which validates successfully against OrgA's secret.
5. `StatusHandler#process` runs against `Commit.where(sha: ...)`, creating a forged success `Status` on the victim's commit, unblocking OrgB's merge queue/deploy checks despite the attacker never authenticating against OrgB's GitHub App.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end
