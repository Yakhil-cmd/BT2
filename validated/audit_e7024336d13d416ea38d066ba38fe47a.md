### Title
Check-then-async-effect race in arbiter contract completion allows duplicate payment / double release of shared-address funds - (File: arbiter_contract.js)

### Summary
`complete()` in `arbiter_contract.js` mirrors the exact bug class from the reported `claimLoanNFT` reentrancy: it validates the contract's `status` field, then performs several asynchronous operations (network/HTTP calls, DB reads, wallet composition) before finally persisting the new status via `setField(...)`. Because the state (`status`) is not updated (or locked) before the async chain runs, invoking `complete()` twice in quick succession lets both invocations pass the same stale-state check and each independently compose and broadcast a payment from the shared address.

### Finding Description
`complete(hash, walletInstance, arrSigningDeviceAddresses, cb)` performs:
1. A guard check: `if (objContract.status !== "paid" && objContract.status !== "in_dispute") return cb("contract can't be completed");` [1](#0-0) 
2. Several `await`/callback-based async steps: `fillArbstoreAddresses`, `storage.readAssetInfo`, optionally `readSharedAddressDefinition`, and finally `walletInstance.sendMultiPayment(opts, ...)`. [2](#0-1) 
3. Only *after* the payment unit is composed and sent does it persist the new status: `setField(objContract.hash, "status", status, function(objContract){ cb(null, objContract, unit); });` [3](#0-2) 

There is no mutex/lock around the hash, and the in-memory `objContract` object fetched via `getByHash` at the top of the function is a snapshot that becomes stale the moment a concurrent call also fetches it before the first call's `setField` completes. Since `getByHash` re-reads from the DB independently each time (`db.query("SELECT * FROM wallet_arbiter_contracts WHERE hash=?", ...)`) [4](#0-3) , two overlapping calls to `complete()` for the same `hash` will both observe `status="paid"` (or `"in_dispute"`), both pass the guard, and both proceed to build and send a `sendMultiPayment` — this is structurally identical to the reported pattern where `bid.lender` (the guard variable) is not updated until after the external call (`lenderManager.registerLoan`), letting a second invocation slip past the same check.

The same check-then-mutate-late pattern also appears in `pay()` (checks `status !== "signed"`, then calls `sendMultiPayment`, then `setField(..., "paid", ...)`) [5](#0-4)  and `openDispute()`/`appeal()`, all of which follow: read status → do async work → `setField` at the end.

### Impact Explanation
For non-private, non-fixed-denomination assets in the "complete" (payer) branch, a successful `sendMultiPayment` spends the shared-address balance according to the `["has", ...]` output requirements baked into the shared-address definition (see `deriveSharedAddress`) [6](#0-5) . If two competing `complete()` calls both build and successfully post spending transactions before either is serialized by the DAG's normal double-spend detection, the outcome depends on network-level double-spend resolution — but the wallet-side race means the wallet composes and signs two separate payment units against the same shared-address funds without an internal mutex, which can produce duplicate signed/broadcast requests to cosigners (in multisig contracts) or duplicate `sendMultiPayment` composition attempts, each of which draws down the shared-address balance and consumes attacker/legitimate double effort, before the underlying ledger reconciles which one wins. For the private-asset path, `complete()` posts a `data_feed` message (`CONTRACT_DONE_<hash>`) from `objContract.my_address` — a second overlapping call can produce a second such data-feed post, potentially confusing the peer's `parseWinnerFromUnit`/status-tracking logic and duplicating the "contract done" signal, causing the counterparty wallet to process duplicate "completed"/"cancelled" transitions.

### Likelihood Explanation
The race requires the same wallet/device to invoke `complete()` (or `pay()`) twice for the same `hash` before the first call's terminal `setField` write lands — e.g., a double-click in the UI, an automated retry on timeout, or a paired-device message replay triggering the same completion flow concurrently. There is no `mutex.lock` guarding these functions (unlike `divisible_asset.js`/`indivisible_asset.js`, which explicitly take `mutex.lock('handleJoint')` before validating and saving) [7](#0-6) , so nothing in `arbiter_contract.js` prevents concurrent execution.

### Recommendation
- Update the contract's `status` to an intermediate "in-progress" value synchronously (or acquire a `mutex.lock([hash])`) immediately after the initial guard check in `complete()`, `pay()`, `openDispute()`, and `appeal()`, before starting any async work, and release/finalize only after `setField` completes.
- Re-check the status from a `mutex`-protected re-read immediately before calling `walletInstance.sendMultiPayment`.
- Alternatively wrap the whole body of `complete()`/`pay()` in `mutex.lock(["arbiter_contract_" + hash], fn)` similar to the `mutex.lock('handleJoint')` pattern used elsewhere in the codebase. [7](#0-6) 

### Proof of Concept
1. Establish an arbiter contract and drive it to `status = "paid"`.
2. Call `arbiter_contract.complete(hash, walletInstance, [], cb1)` and, before its callback fires (i.e., before the internal `setField(objContract.hash, "status", ..., ...)` at line 787 completes), immediately call `arbiter_contract.complete(hash, walletInstance, [], cb2)` again.
3. Both calls independently call `getByHash(hash, ...)` [8](#0-7)  and observe `status === "paid"`, both pass the guard, and both proceed to build `opts` and call `walletInstance.sendMultiPayment(opts, ...)` [9](#0-8) , resulting in two independently composed and signed payment/data-feed units for the same contract before the status is ever transitioned away from `"paid"`.
