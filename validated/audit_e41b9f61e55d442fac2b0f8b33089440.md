### Title
Stack overflow via deeply-nested JSON in oscript `json_parse()` - (File: formula/evaluation.js)

### Summary
The `json_parse` oscript operator, reachable by any AA trigger sender through `trigger.data` or by an AA author's own formula, calls the native `JSON.parse()` on an attacker-controlled string with no depth or nesting-complexity check performed *before* parsing, mirroring the hutool-json / `org.json.JSONTokener` bug class: an unbounded, recursive-descent JSON parser can be driven into a stack overflow with a deeply nested (but otherwise small) payload such as `[[[[[...]]]]]`.

### Finding Description
In the `json_parse` case of the formula evaluator: [1](#0-0) 

the input string `res` (which can originate directly from `trigger.data`, a state variable, or any other attacker-influenced formula expression) is passed straight into `JSON.parse(res)`. Only *after* a successful parse is the result checked with `isTooBigObj(json)` (size/branching/depth bound). There is no pre-parse limit on nesting depth of the string, and unlike `getSourceString`/`getJsonSourceString` in `string_utils.js`, which recurse per key/element but are only invoked on already-parsed, application-controlled object graphs, `JSON.parse` here is invoked on a raw string supplied by an untrusted trigger.

`JSON.parse` in V8 uses a recursive-descent parser: each nested `[` or `{` adds a call-stack frame. A string like `"["repeated N times + "]"repeated N times` (or the object equivalent) is very small in bytes but can drive the parser recursion deep enough to overflow the Node.js call stack when N is large enough (tens of thousands), causing an uncaught `RangeError: Maximum call stack size exceeded` (a native/fatal JS error, not a catchable application `Error` in all V8 versions — in some cases it manifests as an unrecoverable process crash) inside the `try { JSON.parse(res) } catch(e)` block. If the parser overflow is not cleanly caught (deep V8 stack overflows can also corrupt the ability to run subsequent JS, or crash the process outright in certain Node builds), the AA-processing node process can crash while formula evaluation is running inside the unit/joint validation and AA response composition pipeline (`aa_composer.js`).

This is reachable purely by:
1. Any unprivileged unit poster paying an AA whose bounce/response formula contains `json_parse(trigger.data.<field>)` (many "utility" AAs parse attacker JSON, e.g. bridges/oracles/complex logic accepting JSON payloads in `data`), or
2. An AA author deliberately embedding `json_parse` on `trigger.data` in their own AA definition to accept flexible JSON inputs from any future trigger sender.

### Impact Explanation
A successful deep-nesting payload can crash the Node.js process executing `handleTrigger`/AA formula evaluation on every full node that processes the triggering unit (this runs deterministically as part of consensus-critical AA response composition, so all validating nodes execute the same crash). This is a network-wide Denial-of-Service against nodes composing/validating AA responses: repeated posting of such triggers can prevent the network from progressing (AAs failing to respond, backlog of triggers, or full node crashes/restarts), which maps to "a network unable to confirm new units" under the report's acceptance criteria. It does not itself cause double-spend or fund loss, but the DoS is broadly and cheaply reachable by any wallet able to post a payment/trigger to a vulnerable/typical AA.

### Likelihood Explanation
Likelihood is moderate-to-high: `json_parse` is a documented, commonly used oscript built-in for AAs to parse structured data from `trigger.data`, so many deployed AAs likely call it on attacker-supplied strings. Constructing the crafted payload requires only building a small deeply-nested JSON string (no cryptographic material, no special privileges), and the payload can be delivered simply as `trigger.data` in a normal payment message consumed by any AA.

### Recommendation
Before calling `JSON.parse(res)`, validate `res` is not maliciously deeply nested — e.g., cap `res.length` to a small bound relative to `constants.MAX_AA_STRING_LENGTH` (already used elsewhere) and additionally scan/limit nesting depth (count of consecutive `[`/`{` without a corresponding value) prior to parsing, or use a hardened/iterative JSON parser with an explicit depth counter instead of `JSON.parse`. Alternatively wrap the `json_parse` evaluation (and ideally the whole formula evaluator) in a worker/child process or `vm` context with a constrained stack size so a stack overflow there cannot crash the main validating process, and treat any low-level parse failure (including uncatchable RangeErrors) as a formula evaluation failure rather than a process fault.
