### Title
Debt valuation overflow during interest accrual permanently freezes a large whale market before the index cap can engage - (File: common/src/rates/index.rs)

### Summary

`calculate_supplier_rewards` and `scaled_to_original` evaluate `borrowed * index` and `shares * index` in RAY fixed point. Every multiply-divide tries `i128` first and widens to `I256` only for the *intermediate* product — the **result** must still fit `i128`, otherwise `Ray::mul` panics with `MathOverflow` [1](#0-0) . Because accrual runs at the top of every pool verb, once `total_borrowed_shares * borrow_index` crosses `i128::MAX` the market is permanently frozen: `update_indexes`, `repay`, `withdraw`, `borrow`, `liquidate`, `clean_bad_debt` all revert. The intended `MAX_BORROW_INDEX_RAY` clamp in `update_borrow_index` never gets a chance to engage, because the panic happens while *valuing* debt at the new index, not while writing the index [2](#0-1) .

The repo's own harness test documents this exact cliff: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` shows `try_update_indexes_for`, `try_withdraw_raw` and `try_repay` all failing with `MATH_OVERFLOW`, with the borrow index still below `MAX_BORROW_INDEX_RAY` [3](#0-2) .

### Finding Description

The analog to CVE-2019-14444 (integer overflow → crash on an attacker-shaped input) is the un-guarded RAY-domain valuation `shares × index / RAY` used during accrual:

- `calculate_supplier_rewards` computes `borrowed.mul(env, new_borrow_index)` and panics if the resulting debt value exceeds `i128::MAX` (~1.7e38, i.e. ~170 billion whole tokens at RAY) [4](#0-3) .
- `update_supply_index` and `supply_index_reward_shortfall` likewise multiply `supplied` by the index before any saturation applies — the saturating helper `mul_div_floor_saturating` only protects the *division* step, not the `supplied.mul(old_index)` valuation that precedes it [5](#0-4) .
- Position unscaling (`unscale_borrow_ceil`, `unscale_supply_floor`) in `contracts/pool/src/cache/scale.rs` has the same ceiling for any single large position [6](#0-5) .

An unprivileged attacker reaches this by `supply`ing a whale-sized position (caps can be large; the test uses ~1 billion whole-token units via `lift_caps`-scale supply), `borrow`ing near the cap on a steep-curve market (e.g. the XLM curve's high-utilization segment), and then letting public `update_indexes` accrue interest until `borrowed × index > i128::MAX`. From that block onward, no one — not suppliers, not the borrower, not liquidators — can touch the market.

### Impact Explanation

Permanent freezing of all funds in the affected `(hub, token)` book: supplied principal, unclaimed yield, and the pool's claim on outstanding debt all become unreachable because every state-changing entrypoint accrues first and panics inside `scaled_to_original`/`calculate_supplier_rewards`. This matches the "permanent freezing of funds" / "contract unable to operate" impact classes.

### Likelihood Explanation

Requires whale-scale capital (the RAY value ceiling is ~170 billion whole-token units regardless of decimals [7](#0-6) ) and a market with sustained high utilization on a steep rate curve. It is not cheap, but it needs no privilege, no oracle manipulation and no cooperation — just `supply` + `borrow` + public `update_indexes`. The test demonstrates the cliff is reached well before `MAX_BORROW_INDEX_RAY`, so the designed mitigation does not save the market.

### Recommendation

Make accrual fail-safe at the value ceiling rather than panic: e.g. cap `new_borrow_index`/`new_supply_index` such that `total_shares × index` stays below `i128::MAX` (clamp the index to `i128::MAX / shares` before valuing), or saturate debt valuation and short-circuit `accrue` to a no-op past the ceiling so `repay`/`withdraw`/`liquidate` remain callable. At minimum, order the index cap check before any `shares × index` multiplication in `update_supply_index` / `calculate_supplier_rewards`.

### Proof of Concept

The repo already contains it: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs` supplies 1e9 × 10^18 units of `BIG18`, borrows 98% of it, advances time, and asserts `try_update_indexes_for`, `try_withdraw_raw` and `try_repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY` [8](#0-7) .

pub fn calculate_supplier_rewards(
    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

    let accrued_interest = new_total_debt.checked_sub(env, old_total_debt);

    let protocol_fee = params.reserve_factor.apply_to_ray(env, accrued_interest);
    let supplier_rewards = accrued_interest.checked_sub(env, protocol_fee);

    (supplier_rewards, protocol_fee)
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}

/// The cap ceiling and the balance ceiling are the same number: both are the
/// largest amount `Ray::from_asset` can upscale without overflowing `i128`.
/// See `docs/reference/formulas.md#numeric-limits`
#[test]
fn cap_ceiling_is_exactly_the_largest_representable_balance() {
    let env = Env::default();
    use crate::math::fp::Ray;

    for decimals in crate::constants::MIN_ASSET_DECIMALS..=crate::constants::MAX_ASSET_DECIMALS {
        let ceiling = max_cap_for_decimals(decimals);

        assert_eq!(
            Ray::from_asset(&env, ceiling, decimals).to_asset(&env, decimals),
            ceiling
        );

        let unit_in_ray = 10i128.pow(RAY_DECIMALS - decimals);
        assert!(
            ceiling.checked_mul(unit_in_ray).is_some(),
            "ceiling must not overflow at {decimals} decimals",
        );
        assert!(
            (ceiling + 1).checked_mul(unit_in_ray).is_none(),
            "ceiling is not tight at {decimals} decimals",
        );
    }
}
