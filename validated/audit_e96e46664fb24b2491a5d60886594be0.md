## Analog Found: Permanently frozen funds when an asset's attestor list is unilaterally changed by the definer, retroactively invalidating already-held `spender_attested` coins/tokens

### Title
Holder of a `spender_attested` asset (including AA-held balances) can permanently lose the ability to transfer previously legitimately-acquired coins when the asset definer changes the attestor list or the attestor stops attesting - (File: `validation.js`)

### Summary
The reported Sherlock bug is a "party-controlled external resource can be unilaterally destroyed by one actor, permanently breaking another actor's ability to complete a legitimate, already-in-flight operation (repay)". The closest reachable analog in ocore is the `spender_attested` asset mechanism: transfer/issue validity for such assets is re-checked against the *current* (latest) attestor list and *current* attestation status every time a coin is spent, not the status at the time the coin was received. Because the asset definer can change the attestor list at any time, and attestors can simply stop attesting, a holder (or an AA) that legitimately received `spender_attested` coins can become permanently unable to move them — an irrecoverable freeze of funds analogous to the borrower being unable to `repay()` after the lender burns the backing NFT.

### Finding Description
When an asset has `spender_attested: true`, every payment involving that asset is validated against the asset's attestor list and the current attestation status of the input owner and all output addresses: [1](#0-0) [2](#0-1) 

The attestor list itself can be updated by the asset **definer** at any time, unilaterally and without any need for the current holders' consent: [3](#0-2) 

The check for "is this address attested" uses only the *latest* attestor list and the *most recent* attestation, not what applied at the time the coins were issued or transferred to the holder: [4](#0-3) [5](#0-4) 

Consequence: a holder (a normal address or an AA) can legitimately acquire `spender_attested` coins while properly attested. Afterward:
- the attestor can simply choose not to renew/keep the attestation (no on-chain mechanism forces attestors to keep attesting), or
- the asset **definer** can publish a brand-new attestor list (`asset_attestors` message) that excludes the attestor who originally attested the holder,

and from that point on, **every future attempt by that holder to transfer the coins they already legitimately hold will fail validation** with `"owner address is not attested"`, exactly the same failure mode as the reported issue where `repay()` reverts with `"Invalid token ID"` because the lender destroyed the backing resource. There is no path in the code to recover: the holder cannot re-attest themselves, and nothing forces the definer/attestor to restore the previous attestor set.

This is especially severe when the holder is an **Autonomous Agent (AA)**: an AA that received `spender_attested` tokens as part of its normal balance (e.g., an escrow/exchange AA) will permanently bounce/fail any response message that tries to move those tokens out once the attestation is invalidated, freezing that portion of the AA's balance forever, with no emergency-withdrawal path defined by the protocol layer.

### Impact Explanation
- **AA fund loss/freezing**: an AA holding `spender_attested` balances can have those balances become permanently untransferable if the definer changes the attestor list or the attestor withdraws attestation, mirroring the reported "borrower loses liquidation bonus/position forever" impact.
- **Freezing of user funds**: any regular holder of such coins loses access to funds they legitimately own, through no fault or action of their own, purely due to a unilateral action by the asset definer/attestor — a direct analog of "lender burns NFT, borrower can't repay."
- No liquidation/emergency mechanism exists in the protocol to recover or reroute such frozen balances (there is no equivalent of "isEmergency" restoration logic that ocore's asset/validation layer provides for this case).

### Likelihood Explanation
- The `spender_attested` flag is a first-class asset feature (`validateAssetDefinition`, `validateAttestorListUpdate`) intentionally exposed to any asset definer; issuing such an asset and later changing/dropping attestors requires nothing more than a single `asset_attestors` message signed by the definer, or attestor inaction — no special privileges beyond being the asset's own definer are needed.
- Any third party can build an AA (escrow, DEX, lending, subscription, etc.) that accepts arbitrary attested assets as payment; if that asset's definer/attestor later invalidates the holder's attestation, the AA's balance in that asset becomes stuck, which is fully reachable by an ordinary AA author or a counterparty choosing which asset to send into the AA.

### Recommendation
- Consider snapshotting/pinning the attestation status (or attestor list version) that applied at the time coins were transferred to an address, rather than always re-validating against the current, mutable attestor list on every subsequent spend.
- Alternatively, provide a documented/standardized "unlock" or grace-period mechanism so that holders (especially AAs) are not permanently deprived of already-owned balances purely due to a later, unilateral change made by the asset definer or a withdrawal of attestation by an attestor.

### Proof of Concept
1. Definer issues asset X with `spender_attested: true` and attestor set `{A}`.
2. Attestor `A` attests holder `H` (`attestation` message referencing `H`).
3. `H` receives a transfer of asset X (validated fine, since `H` is in `arrAttestedAddresses` per `storage.js:1960` `filterAttestedAddresses`).
4. Definer publishes a new `asset_attestors` message for asset X with attestor set `{B}` (allowed per `validation.js:2829-2847`, single signature by definer only) — or attestor `A` simply never re-attests `H` again.
5. `H` (or an AA holding the same balance) attempts to spend/transfer the previously received coins of asset X.
6. Validation in `validation.js:2504-2507` (or `2630-2642` for outputs) finds `H` (or the AA) is no longer in the current `arrAttestedAddresses` and rejects with `"owner address is not attested"` — the funds are permanently stuck with no way for `H` to restore attestation unilaterally, mirroring the reported `repay()` reverting with `"Invalid token ID"` after the NFT was burned.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
