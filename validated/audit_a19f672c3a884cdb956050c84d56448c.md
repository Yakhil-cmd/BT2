### Title
LP-collateral price outage blocks liquidation and bad-debt cleanup - (File: contracts/price-aggregator/src/providers/aquarius.rs)

### Summary
A borrower who is also an Aquarius liquidity provider can add a dust amount of a listed Aquarius LP token as collateral, then withdraw enough of their remaining pool liquidity to push the pool below `min_pool_value_wad`. Aquarius pricing then fails closed with `InsufficientAquariusLiquidity`, which prevents valuation-dependent controller actions from resolving the account's collateral set. [1](#0-0) [2](#0-1) 

### Finding Description
`supply` accepts a new collateral leg without requiring that asset's oracle to resolve, allowing an underwater borrower to plant a dust LP position. [3](#0-2) 

During account valuation, liquidation reads all collateral legs rather than only collateral proportional to the selected repayment; an unusable price therefore aborts the entire call. [4](#0-3) 

The Aquarius provider computes total pool value as `price_wad * total_shares / share_unit` and rejects any value below the configured `min_pool_value_wad`. [5](#0-4) 

A mainnet-listed LP market uses this mechanism, for example `AQUAUSDC_LP` with a `200,000 USD` minimum pool-value floor. [6](#0-5) 

### Impact Explanation
An underwater account can temporarily block `liquidate` and `clean_bad_debt` while interest continues accruing. [7](#0-6) 

This delays loss containment and can turn an otherwise liquidatable account into protocol bad debt. The freeze is temporary because restoring Aquarius liquidity above the floor restores pricing and liquidation. [8](#0-7) 

### Likelihood Explanation
The attacker needs enough Aquarius liquidity to reduce pool value below the configured floor, or a pool already close to that floor. [1](#0-0) 

The borrower does not need to withdraw the dust LP shares deposited as lending collateral; they only need to control sufficient separate LP shares to move the pool below the floor. The issue requires no privileged role and can be executed through ordinary supply plus the attacker's own Aquarius liquidity withdrawal. [3](#0-2) 

### Recommendation
Do not let an unpriceable dust collateral leg unconditionally abort account valuation. Liquidation should exclude legs whose seizure value rounds to zero or apply an explicit bounded fallback for tiny legs, while still preventing borrowers from hiding material collateral from liquidation. At minimum, allow the owner to ignore a collateral leg whose value is below the bad-debt dust threshold and preserve the current full-valuation behavior for material legs. [3](#0-2) 

### Proof of Concept
1. A borrower opens an indebted account using ordinary liquid collateral.
2. The borrower calls controller `supply` with the listed Aquarius LP `HubAssetKey` and a positive dust amount. The LP collateral position is created even though a later outage can make its price unreadable. [3](#0-2) 
3. The borrower's other collateral loses value until the account's health factor is below one; a control account without the LP leg remains liquidatable. [9](#0-8) 
4. Holding separate LP shares, the borrower withdraws enough liquidity from the configured Aquarius pool that `pool_value_wad < min_pool_value_wad`.
5. A liquidator calls `liquidate(liquidator, account_id, offered, SeizeMode::Transfer)` or `SeizeMode::Credit(receiver_id)`. The provider returns `InsufficientAquariusLiquidity`, and the call aborts instead of liquidating the account. [5](#0-4) [10](#0-9) 
6. `clean_bad_debt` fails through the same collateral-valuation path, so the protocol cannot immediately socialize the growing deficit. [11](#0-10) 
7. When liquidity is restored above `min_pool_value_wad`, the same liquidation succeeds, confirming that the LP outage rather than insufficient collateral caused the denial. [8](#0-7)
