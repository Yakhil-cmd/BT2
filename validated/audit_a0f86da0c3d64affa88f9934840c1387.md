### Title
Webhook signature verification selects the HMAC secret from an attacker-controlled payload field, letting one tenant forge events for another tenant's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to verify the request against based on the *organization named inside the untrusted request body itself*, not based on any independently-authenticated identity. Because the same untrusted body also supplies the `repository.full_name` used by every event handler to select which stack/commit/team is mutated, an attacker who legitimately controls one org configured in a multi-org Shipit deployment can sign a payload with their own known `webhook_secret` while making the payload's `repository` block point at a completely different, unrelated org/repo tracked by the same Shipit instance. The signature check only proves "this body was signed with OrgA's secret" — it never proves "OrgA owns the repository this body claims to describe."

### Finding Description
`verify_signature` derives `repository_owner` straight from the JSON body: [1](#0-0) 

and uses that value to select which `GitHubApp`/secret to verify against: [2](#0-1) 

`Shipit.github(organization:)` looks the secret up per-org from `secrets.github`, which is how the engine documents/supports connecting multiple independent GitHub organizations to one Shipit instance: [3](#0-2) [4](#0-3) 

`verify_webhook_signature` then performs a plain HMAC-SHA1 compare of the *entire raw body* against that resolved secret: [5](#0-4) 

Once the signature check passes, every registered handler resolves the actual target purely from the same untrusted body, via `Handler#repository_name`: [6](#0-5) 

e.g. `PushHandler` triggers a `GithubSyncJob` for whatever stack matches that repo name/branch: [7](#0-6) 

and `StatusHandler` writes a `Status` (which can flip a commit's deployability and trigger merge-queue scheduling) for whatever commit SHA is supplied, independent of which repository that commit actually belongs to: [8](#0-7) [9](#0-8) 

**The binding that should hold:** `organization whose secret authenticated the request == organization that owns the repository the payload will mutate`.

**Before an attack:** `Shipit.github(organization: repository_owner)` is meant to bind the verified signer to the acted-upon repository because in a legitimate GitHub-originated webhook, `repository.owner.login` and `repository.full_name` both accurately describe the same, single repository that GitHub itself is reporting on.

**After the attack:** the attacker fully controls the raw JSON body sent to `/webhooks`, so `repository.owner.login` (used to pick the secret) and `repository.full_name` (used by the handler to pick the target stack) can be made to disagree. The attacker signs with the secret of an org they legitimately administer (OrgA, for which they can freely create a GitHub webhook and read the secret, or reuse one), but sets `repository.full_name` (and, for `status`, an arbitrary `sha`) to point at any repository tracked under any *other* org (OrgB) configured on the same shared Shipit instance. The signature check passes because it never re-checks that the resolved `repository_owner` matches the org whose secret was actually used, nor that the target repository belongs to that org.

### Impact Explanation
This breaks a cross-tenant boundary: an operator who is only supposed to control Shipit's view of their own GitHub organization can forge arbitrary GitHub webhook events for *any other org/repository* hosted on the same Shipit deployment, achieving cross-repository writes:
- Forge `status` events to mark arbitrary commits on unrelated stacks as `success`, flipping `deployable_status`/`commit_status` and triggering `stack.schedule_merges`, which can push otherwise-unqualified commits into a merge/deploy pipeline for a repository the attacker does not own.
- Forge `push` events to force `GithubSyncJob`/resync activity against arbitrary stacks.
- Forge `membership` events to create/delete `Team`/`Membership` records tied to unrelated organizations.

Per the stated impact criteria, this qualifies as "cross-repository writes" (Critical) since it lets a tenant mutate Shipit-managed state belonging to a repository/org it has no authorization over.

### Likelihood Explanation
Any operator with legitimate access to configure a webhook for one org in a multi-org Shipit deployment (a normal, low-privilege administrative action within their own org, not a Shipit session/API token/GitHub App key) can construct this payload with a standard HTTP client — no interaction with the target org or its secrets is required, only knowledge of their own org's secret and the target's public `repository.full_name`/branch/commit SHA.

### Recommendation
After resolving `repository_owner` and verifying the HMAC, independently confirm that the resolved organization actually owns the repository referenced in the payload (e.g., re-derive the owner from `Repository.from_github_repo_name(payload.dig('repository','full_name')).owner` and compare it against `repository_owner`, rejecting on mismatch) before dispatching to any handler. Alternatively, bind each configured GitHub App to an explicit allow-list of repositories/organizations it may report on, and enforce that list in `verify_signature` rather than trusting the payload's self-declared owner to pick the verification secret.

### Proof of Concept
1. Shipit is configured with `github: { OrgA: {webhook_secret: SECRET_A, ...}, OrgB: {webhook_secret: SECRET_B, ...} }` (multi-org config as documented), with `OrgB/target-repo` tracked as a stack.
2. Attacker administers `OrgA` and knows/controls `SECRET_A` (they configured the webhook themselves).
3. Attacker builds a `status` (or `push`) JSON body with:
   - `repository.owner.login = "OrgA"` (so `verify_signature` resolves and verifies against `SECRET_A`)
   - `repository.full_name = "OrgB/target-repo"`, `sha = <victim commit sha>`, `state = "success"`
4. Attacker computes `X-Hub-Signature: sha1=HMAC(SECRET_A, raw_body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` succeeds (secret matches, since it was chosen based on the attacker-supplied `OrgA` owner field).
6. `StatusHandler#process` looks up `Commit.where(sha: ...)` for `OrgB/target-repo` and calls `create_status_from_github!`, marking the commit deployable — despite the request never being signed with `OrgB`'s secret.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
