### Title
Null Pointer Dereference in AA Primary-Trigger Anti-Replay Check - (File: aa_composer.js)

### Summary
`handleTrigger()` in `aa_composer.js` dereferences `storage.assocStableUnits[trigger.unit]` without checking that the cache entry exists, unlike the otherwise-identical lookup performed a few lines later in `handlePrimaryAATrigger()`, which explicitly guards against a missing entry and throws a descriptive error instead of crashing on a raw property access.

### Finding Description
When a unit pays to an AA address, `handlePrimaryAATrigger()` builds the `trigger` object from the posted unit and calls `handleTrigger()`: [1](#0-0) 

Inside `handleTrigger()`, for a non-secondary, non-air (real) primary trigger, the code performs an anti-double-trigger check: [2](#0-1) 

`storage.assocStableUnits[trigger.unit]` is accessed and `.count_aa_responses` is read off it directly, with **no null/undefined check**. Compare this to the check performed immediately after `handleTrigger()` completes, in the very same code path, on the very same cache (`storage.assocStableUnits[unit]`), where the developers explicitly anticipated that the entry could be missing and guarded it: [3](#0-2) 

This shows the maintainers are aware that `storage.assocStableUnits` entries for a trigger's originating unit can be absent by the time AA-trigger processing runs (units are evicted from this in-memory cache once they fall behind the minimum retrievable MCI, see the `assocStableUnits` cache maintained in `storage.js`), yet the earlier access at line 1861 — which executes *before* the guarded check ever runs — has no such protection. If `trigger.unit` is not present in `storage.assocStableUnits` when this line executes, `storage.assocStableUnits[trigger.unit]` evaluates to `undefined`, and `.count_aa_responses` throws a `TypeError: Cannot read properties of undefined`.

This code path is exercised for every AA primary trigger processed as part of normal AA execution, driven from `handleAATriggers()`, which is invoked under the `mutex.lock(['aa_triggers'])` lock whenever a stable unit triggers an AA: [4](#0-3) 

No `try/catch` wraps this deep asynchronous callback chain, so an uncaught `TypeError` here is an unhandled exception in Node.js and will crash the process.

### Impact Explanation
An uncaught exception thrown while holding the `aa_triggers` mutex crashes the full node process during core AA-response generation, which is executed on every full node processing stable units that trigger AAs. Because this occurs inside AA trigger handling (a mandatory, consensus-relevant path for units posted by any unprivileged user paying an AA), a reliably reproducible trigger causes denial of service on any full node processing that AA trigger, preventing it from continuing to confirm/process further units — matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
The vulnerable branch is reached whenever `trigger.unit !== constants.GENESIS_UNIT`, `!trigger_opts.bAir` (i.e., real execution, not a dry run/estimate), and `mci >= constants.pemCurvesFixMci` — i.e. essentially all live, non-genesis primary AA triggers on current mainnet/testnet MCI. The only remaining question is whether `storage.assocStableUnits[trigger.unit]` can actually be absent at the moment `handleTrigger` runs; the presence of the explicit guard for the identical lookup a few lines later in `handlePrimaryAATrigger` (added specifically to `throw Error("...unit ${unit} not found in cache")` rather than segfault-style undefined access) is strong evidence that the ocore maintainers have already observed or anticipated this exact cache-miss condition in production, i.e., that under a backlog of pending AA triggers (many units paying into AAs faster than they are processed) combined with the storage layer's periodic eviction of old entries from `assocStableUnits` once they fall behind the minimum retrievable MCI, the entry for `trigger.unit` is not guaranteed to still be resident by the time `handleTrigger` executes.

### Recommendation
Add the same defensive check used in `handlePrimaryAATrigger` before dereferencing the cache entry in `handleTrigger`, e.g.:
```js
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir) {
    const objUnitProps = storage.assocStableUnits[trigger.unit];
    if (!objUnitProps)
        return bounce(`trigger unit ${trigger.unit} not found in cache`); // or re-fetch from DB
    if (objUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
        return bounce('a second primary trigger from the same unit is not allowed');
}
```
Alternatively, fall back to a DB read (`storage.readUnitProps`) when the in-memory cache entry is missing, rather than assuming it is always present.

### Proof of Concept
1. Post a unit that pays outputs into an AA address so it becomes a primary AA trigger recorded in `aa_triggers` (reachable by any unprivileged unit poster).
2. Cause a backlog in AA trigger processing relative to storage's memory-cache eviction of old stable units from `storage.assocStableUnits` (e.g., by generating a burst of many AA-triggering units so that `handleAATriggers`'s `async.eachSeries` processing lags while the storage layer's minimum-retrievable-MCI advances and evicts older entries from the cache — this eviction logic is in `storage.js`, exercised whenever the retrievable MCI window is advanced).
3. When `handlePrimaryAATrigger` -> `handleTrigger` finally processes the delayed trigger unit whose cache entry has since been evicted, the unguarded access `storage.assocStableUnits[trigger.unit].count_aa_responses` at `aa_composer.js:1861` throws a `TypeError`, which is uncaught and crashes the node process while it holds the `aa_triggers` mutex.

Note: Full confirmation of the exact eviction timing/race conditions in `storage.js`'s cache-purging logic could not be independently exercised in this review; the finding is grounded in the direct code inconsistency (unguarded vs. guarded identical lookup) rather than a live-triggered crash trace. A Devin session with full repo/runtime access could validate the exact eviction window under `storage.js`.
