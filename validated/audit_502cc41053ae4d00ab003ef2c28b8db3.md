### Title
Cross-repository status-webhook mutation of unrelated stacks' commit statuses via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves commits purely by `sha` with no repository scoping, unlike other webhook handlers (`push_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) which all use the `stacks` helper in `Handler#stacks` that scopes lookups to `Repository.from_github_repo_name(repository_name)`. Because `verify_signature` in `webhooks_controller.rb` only proves that the payload's claimed `repository.owner.login` (org B) owns the `webhook_secret` used to sign the request, it never proves that the `sha` inside the payload actually belongs to repository B. `StatusHandler#process` then writes a `Status` and fires `Hook.emit(:commit_status, ...)` against `commit.stack`, which can be an entirely different, victim stack A if that stack has a `Commit` row with the same `sha`.

### Finding Description
The broken binding, stated as an equality that the code should enforce but does not:

`payload.dig('repository','full_name') == commit.stack.repository.full_name`

`verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) only checks:

`HMAC(webhook_secret_of(repository_owner_from_payload), raw_post) == X-Hub-Signature`

This proves the sender controls a repo/org whose webhook is configured in Shipit (repo B), and that the payload body wasn't tampered with in transit — it says nothing about which repository's *commit* is inside the payload's `sha` field.

`StatusHandler` never consults `repository_name`/`stacks` (the scoping helper defined in `Handler#stacks`, app/models/shipit/webhooks/handlers/handler.rb:32-38) that every other handler (`push_handler.rb`, `check_suite_handler.rb`, `pull_request/*_handler.rb`) relies on. Instead: [1](#0-0) 

`Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` queries the global `commits` table across *all* stacks/repositories, matching any row with that sha regardless of which repository it was created under.

`create_status_from_github!` → `add_status` then uses `commit.stack` (the *matched* commit's own stack) to emit the hook and drive downstream logic: [2](#0-1) 

Notably `add_status` uses `stack` (delegated to `commit.stack`) for `Hook.emit(:commit_status, stack, ...)`, `Hook.emit(:deployable_status, stack, ...)`, and `stack.schedule_merges`, and the `after_commit` callback on `Status` triggers `commit.schedule_continuous_delivery` which checks `stack.continuous_deployment? && stack.deployable?` (app/models/shipit/status.rb:19,42-44; app/models/shipit/commit.rb:281-287) — all scoped to *whichever stack happens to own the matching sha*, not the stack of the authenticated repository B.

Exploit flow:
1. Attacker owns/administers repository B (any GitHub repo, e.g. a fork of the repository backing victim stack A, or any repo sharing a commit object with A — forks share git objects/SHAs for identical commits by construction).
2. Attacker sets up (or already has) B tracked in Shipit with a real GitHub webhook, so GitHub itself computes a valid `X-Hub-Signature` using B's real `webhook_secret` — the attacker never needs to know any Shipit secret.
3. Attacker pushes/labels/triggers a `status` event on repo B for a commit sha that is identical to a commit already ingested into victim stack A's `commits` table (trivial for a fork of A, or any repo that shares history with A).
4. `verify_signature` passes (correctly, for repo B). `StatusHandler#process` then finds *all* `Commit` rows with that `sha`, including the one belonging to stack A, and calls `add_status` on it using stack A's own scoping (`stack_id`, `Hook.emit(..., stack, ...)`), writing a new `Status` row tied to stack A and firing `commit_status`/`deployable_status` hooks and continuous-delivery scheduling for stack A.
5. By alternating `state` between `pending` and `success` in repeated repo-B webhooks, the attacker can toggle stack A's `blocking_statuses` state (`Commit#blocked?`, app/models/shipit/commit.rb:231-237) from blocked to unblocked, since `blocked?` checks `commits.reachable...any?(&:blocking?)` which is driven by the very `Status` rows the attacker is injecting through repo B's channel.

Existing guards do not stop this: `verify_signature` authenticates the *sender's org*, not the *sha's owning repository*; `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates the shape of the JSON, not sha ownership; `drop_unhandled_event` and `force_github_authentication` are irrelevant to this path (this is a public POST /webhooks path, not a UI/API auth path).

### Impact Explanation
An attacker who controls an arbitrary repository (with the shared-sha requirement being GitHub-fork-relative and thus easy to satisfy for fork-based or shared-history stacks) can inject `Status` records and fire `Hook.emit(:commit_status/:deployable_status, stack, ...)` for a victim stack A they never authenticated for. This can flip `Commit#blocked?`/`Commit#deployable?` on stack A, enabling `Commit#schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)` and ultimately an unauthorized deploy of stack A driven entirely by webhook traffic that was only ever authenticated against repository B's secret. This matches "Critical: a payload for one repository mutating another's stack/commit... or an unauthorized deploy" per the rubric, since the write is to a resource (`Status` belonging to stack A) that repo B's credential never proved authority over. Repeatable indefinitely and against any victim stack whose git history intersects with a repo the attacker controls (forks are the common case).

### Likelihood Explanation
Preconditions: stack A must exist in Shipit with `blocking_statuses`/`required_statuses` configured (via `shipit.yml`), and stack A must have already ingested a `Commit` with a sha that also exists in a repo (B) the attacker controls and which is registered in Shipit with a legitimate webhook (an org onboarded with its own `webhook_secret`, e.g. any public fork target the same GitHub App/organization tracks, or any repository shared under the same `Shipit.github_teams`/app installation). Given forks trivially share commit SHAs with upstream, and any GitHub user can fork a public repo and push additional commits/labels to trigger status events on their fork, the attacker cost is minimal: no Shipit secrets, no session, no API token — only ordinary GitHub repo ownership and the ability to make GitHub emit a `status` webhook (achievable via GitHub Actions/CI integrations they control on their own fork). The main constraint is that B must be a repository Shipit is already configured to receive webhooks from with a real `webhook_secret`; this is plausible in any org allowing self-service repo/stack onboarding.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve the target `stacks`/`Repository` from `payload.dig('repository','full_name')` (as `Handler#stacks` already does) and restrict the `Commit.where(sha: ...)` lookup to `commit.stack_id` values belonging to that repository's stacks (e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository.id })`), so a commit's status can only ever be mutated by a webhook whose signature was verified for the repository that actually owns that commit.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook from repository B mutates commit_status for an unrelated stack A sharing the same sha" do
  stack_a = shipit_stacks(:shipit)                     # victim stack, repository A
  commit_a = stack_a.commits.create!(sha: 'deadbeef' * 5, ...)  # ingested independently, e.g. via push to A

  # Attacker controls repository B, tracked separately in Shipit, with its own webhook_secret.
  # GitHub-signed payload for repo B references the SAME sha as commit_a (fork/shared history).
  payload = {
    'sha' => commit_a.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'full_name' => 'attacker/repo-b' }, # NOT stack_a's repository
  }

  assert_equal 'attacker/repo-b', payload['repository']['full_name']
  refute_equal payload['repository']['full_name'], stack_a.repository.full_name

  hook_fired_for = nil
  Shipit::Hook.stub(:emit, ->(event, stack, *) { hook_fired_for = stack if event == :commit_status }) do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end

  # BUG: victim stack A's hook fires as a direct result of repo B's payload.
  assert_equal stack_a, hook_fired_for
end
```
This demonstrates that `Hook.emit(:commit_status, stack_a, ...)` fires purely from a payload whose only repository reference is `attacker/repo-b`, confirming the WEBHOOK_PROVENANCE binding is broken.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end
