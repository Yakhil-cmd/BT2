### Title
Block revenue commission (`block_revenue_commission_bps`) is never applied when distributing delegator block rewards — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The vote program (SIMD-0123/SIMD-0291) lets a validator configure a `block_revenue_commission_bps` and a `block_revenue_collector` on its `VoteStateV4`, intended to let the validator keep a commission cut of the block/delegator rewards it deposits via `DepositDelegatorRewards`. However, the actual epoch-boundary distribution logic that pays out `pending_delegator_rewards` to delegators (`calculate_block_reward`) never reads or applies this commission at all — it hands 100% of `pending_delegator_rewards` to stakers, proportionally by stake, with no split analogous to the one used for `InflationRewards`.

### Finding Description
For inflation rewards, `redeem_delegation_rewards` explicitly fetches the voter's commission (`vote_state_for_commission.inflation_rewards_commission()` or the legacy `commission()`) and feeds it into `redeem_rewards` → `commission_split`/`commission_split_preserve_lamports`, which splits the reward between voter and staker according to `commission_bps`. [1](#0-0) [2](#0-1) 

By contrast, `calculate_block_reward` — the function used for SIMD-0123 block-revenue-sharing rewards — only reads `pending_delegator_rewards()` from the vote state and divides it purely by stake proportion. It never touches `block_revenue_commission_bps`/`block_revenue_commission()`, and there is no commission-holdback or commission-collector payout anywhere in this path: [3](#0-2) 

The resulting `block_reward` is added directly into `PartitionedStakeReward` for the stake account, with no corresponding `RewardCommission` entry for the block-revenue side: [4](#0-3) 

Meanwhile, the vote program fully supports configuring and updating this commission and collector:
- `block_revenue_commission_bps` / `block_revenue_collector` fields exist on `VoteStateV4` and are exposed via `vote_state_view` (`block_revenue_commission_view`, `Simd185Field::BlockRevenueCommission`). [5](#0-4) 
- CLI flags let a validator explicitly configure `--block-revenue-commission-bps` and `--block-revenue-collector`. [6](#0-5) 
- The `UpdateCommissionBps` instruction with `CommissionKind::BlockRevenue` allows on-chain updates to this commission. [7](#0-6) 
- `DepositDelegatorRewards` deposits lamports into the vote account and increments `pending_delegator_rewards`, which is exactly the pool later consumed unconditionally by `calculate_block_reward`. [8](#0-7) 

So the on-chain state fully advertises a commission mechanism for block revenue (fields, setters, CLI support, getters), but the reward-distribution code path that actually pays out that revenue pool at epoch boundaries silently ignores it, unlike the parallel and correctly-implemented `InflationRewards` commission path.

### Impact Explanation
This is the direct analog of the reported bug class: a fee/commission mechanism is defined and configurable (`block_revenue_commission_bps`, `block_revenue_collector`) but is not actually applied when the associated reward pool is distributed. The practical effect is a misattribution of lamports: 100% of `pending_delegator_rewards` (block revenue meant to be split between the validator commission collector and delegators) is instead paid entirely to stake accounts, and the configured `block_revenue_collector` never receives its share. This runs automatically for every stake delegation at every epoch boundary via `calculate_stake_rewards_and_commissions`/`redeem_delegation_rewards`, i.e., in the unprivileged, automatic epoch reward distribution path, not gated behind any validator/operator action — it silently misallocates lamports across the whole reward-distribution mechanism whenever `block_revenue_sharing` is active.

### Likelihood Explanation
`block_revenue_sharing` is an active feature-gated code path (`feature_snapshot.block_revenue_sharing`), and `calculate_block_reward` is invoked unconditionally for every stake delegation whenever that feature is enabled: [9](#0-8) 
Any validator that funds delegator rewards via `DepositDelegatorRewards` and expects its `block_revenue_commission_bps`/`block_revenue_collector` to take effect will be affected every epoch, making this a systematic, high-likelihood issue rather than a corner case.

### Recommendation
In `calculate_block_reward` (or in the caller `calculate_stake_rewards_and_commissions`), fetch `vote_state.block_revenue_commission()`/`block_revenue_commission_bps` and split the `pending_delegator_rewards` pool between the `block_revenue_collector` and the delegators using the same `commission_split`/`commission_split_preserve_lamports` machinery already used for inflation rewards, and emit a corresponding `RewardCommission` entry so the commission is actually paid out (or burned/accounted for) analogous to `redeem_delegation_rewards`.

### Proof of Concept
1. Enable `block_revenue_sharing` feature.
2. Create/configure a vote account with `block_revenue_commission_bps = 5000` (50%) and a distinct `block_revenue_collector`.
3. Call `DepositDelegatorRewards` to add, e.g., 100 SOL to `pending_delegator_rewards` (see `test_deposit_delegator_rewards`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs` test `test_calculate_block_reward_specific`).
4. Advance to the epoch boundary so `calculate_block_reward` runs for delegated stake accounts (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:173-232`).
5. Observe: all 100 SOL of `pending_delegator_rewards` is distributed to stake accounts proportionally to stake; the `block_revenue_collector` account balance is unaffected, and no `RewardCommission` referencing the block-revenue commission is produced — confirming the configured 50% commission is never collected.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}
