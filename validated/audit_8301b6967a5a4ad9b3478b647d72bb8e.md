### Title
Cross-stack read of deploy/build status via `Api::CCMenuController` bypassing API token stack scoping - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
An `ApiClient` token that is scoped to a single stack (`stack_id` set) is authorized by `ApiClient#check_permissions!` to read only that stack's data, and every other API controller enforces this scope through `BaseController#stacks`/`#stack`. `Api::CCMenuController` overrides `#stack` to look up `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table instead of the scoped relation, so a token that authorizes one stack ends up touching any stack.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the authenticated client: [1](#0-0) 

`Shipit::ApiClient#check_permissions!` only checks that the `"read:stack"` string is present in the client's `permissions` array — it never checks `stack_id`: [2](#0-1) 

The `stack_id` restriction is therefore enforced *exclusively* by the `stacks` helper method in `BaseController`, and every other API resource controller (`Api::StacksController`, and by extension the nested `deploys`, `tasks`, `commits`, `hooks`, etc. which are reached through `Stack.from_param!` scoped via `stacks`) goes through it: [3](#0-2) 

`Api::CCMenuController`, mounted at `/api/stacks/*stack_id/ccmenu`, defines its own `stack` method that bypasses this scoping and resolves any stack by param directly from the unscoped `Stack` model: [4](#0-3) [5](#0-4) 

This is exactly the class of bug the report describes: a value the deployment trusts as "authorized" (the token's `stack_id`) is checked in one place (`current_api_client.stack_id?` in `stacks`) but the field actually acted upon (`params[:stack_id]` used to fetch an arbitrary `Stack`) is never re-validated against it, so the binding `authorized stack == touched stack` is broken by this specific controller.

Scoped tokens genuinely exist in this codebase — e.g. the `here_come_the_walrus` fixture client has `stack: shipit` and permission `read:stack`: [6](#0-5) 
and the existing test suite confirms that scoping is expected to be enforced by `#index`: [7](#0-6) 

### Impact Explanation
Any holder of a stack-scoped `ApiClient` token (Basic Auth credentials, or the query-string `token` param accepted by `CCMenuController#authenticate_api_client`) with only `read:stack` permission for stack A can call `GET /api/stacks/*stack_id/ccmenu?token=...` with an arbitrary `stack_id` for stack B and receive stack B's name, activity state, and last build status/label/time — deploy/build output that they were never authorized to read. This matches the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output" achieved via privilege/scope escalation rather than a missing-authentication bug: the attacker holds a legitimately-authenticated but narrowly-scoped credential and escalates it to read state for repositories/stacks outside its authorized scope.

### Likelihood Explanation
The bug is a straightforward, deterministic code-path mismatch — no timing, race, or social-engineering conditions are needed. Any application deploying Shipit and issuing stack-scoped API tokens (a supported, documented feature via `ApiClient#stack`) is affected as soon as such a token exists, and the request is a single unauthenticated-by-CCMenu-standards GET with the victim's `stack_id` substituted in the URL.

### Recommendation
Change `Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` relation (i.e. `stacks.from_param!(params[:stack_id])`) exactly like `Api::BaseController`/`Api::StacksController` do, so a client's `stack_id` scope restriction is honored for the CCMenu endpoint as well.

### Proof of Concept
1. Create two stacks: `owner/repoA/staging` (Stack A) and `owner/repoB/production` (Stack B).
2. Create an `ApiClient` scoped to Stack A only: `ApiClient.create!(creator: user, name: 'scoped', stack: stack_a, permissions: ['read:stack'])`.
3. Using that client's Basic Auth token (or its `authentication_token` as the `token` query param), request:
   `GET /api/stacks/owner/repoB/production/ccmenu`
4. Observe the response returns HTTP 200 with Stack B's CCMenu XML (name, activity, lastBuildStatus, lastBuildLabel, lastBuildTime) even though the client is only authorized (`stack_id`) for Stack A — whereas the equivalent request to `Api::StacksController#show` (`GET /api/stacks/owner/repoB/production`) correctly 404s/`from_param!`-raises because `stacks` filters by `current_api_client.stack_id`.
