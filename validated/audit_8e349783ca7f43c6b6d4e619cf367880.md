I have enough evidence now to confirm the vulnerability. Let me lay out the exact mechanism.

Key facts confirmed:
- `WebhooksController#verify_signature` derives the org used for signature verification from the untrusted JSON body itself: `params.dig('repository', 'owner', 'login')` (fallback `organization.login`), then calls `Shipit.github(organization: repository_owner)` and verifies the signature against **that org's** `webhook_secret`. [1](#0-0) 
- Separately, `Handler#stacks`/`#repository_name` resolves the target repository/stack from a **different field of the same untrusted body**: `payload.dig('repository', 'full_name')`, via `Repository.from_github_repo_name`, which just splits on `/`. [2](#0-1) [3](#0-2) 
- Nothing cross-checks that `repository.owner.login` (the org whose secret was used to verify) actually matches the owner portion of `repository.full_name` (the org/repo actually written to). Both are attacker-supplied JSON fields.
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for that org: `return true unless webhook_secret`. [4](#0-3) 
- Shipit explicitly supports multiple GitHub Apps/orgs, each with its own independently-configured (optional) `webhook_secret`. [5](#0-4) 
- `StatusHandler#process` creates a `Status` (CI status) directly from unverified webhook fields (`state`, `description`, `context`, `target_url`) for any commit matching `sha`, with no callback to GitHub's API to confirm the status is real. [6](#0-5) [7](#0-6) 

### Title
Webhook signature is verified against `repository.owner.login`, but the write target is resolved from `repository.full_name` — an unprivileged attacker can forge CI statuses and drive deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/`webhook_secret` to check the HMAC signature against using `repository.owner.login` from the raw, unverified JSON body. But every webhook `Handler` resolves the actual repository/stack to act on using `repository.full_name` from that same body. Since these two fields are never cross-validated, and come from a body whose signature hasn't been checked yet at the point they're read, an attacker can pick an org with no (or a guessable) `webhook_secret` to pass verification, while pointing `full_name` at a completely different, protected repository/stack.

### Finding Description
The binding that should hold is: *the organization whose secret authenticated this webhook* == *the organization owning the repository the handler subsequently writes to*. In this codebase that equality is never enforced.

1. `verify_signature` computes `repository_owner` purely from the JSON payload:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
and uses it to pick the `GitHubApp` (and thus the `webhook_secret`) to verify against: `Shipit.github(organization: repository_owner)`. [1](#0-0) 

2. Every handler, however, resolves the stack(s)/repository to mutate from a *different* payload field, `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

3. `Repository.from_github_repo_name` naively splits `full_name` on `/` with no relation to `repository.owner.login`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [3](#0-2) 

4. Shipit is designed to support multiple GitHub Apps for multiple orgs, each with an *independently optional* `webhook_secret` (per `docs/setup.md` and the multi-org config shown in `config/secrets.development.shopify.yml`). If any onboarded org has no `webhook_secret` configured, `verify_webhook_signature` unconditionally returns `true`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [4](#0-3) 

Putting it together: an attacker POSTs a forged webhook to `/webhooks` with `repository.owner.login` set to an onboarded org that has no `webhook_secret` set (verification auto-passes, no secret required), and `repository.full_name` set to `"<protected-org>/<protected-repo>"`. Signature verification passes trivially (using the weak org's config), but the handler acts on the protected org's repository/stack, because the handler never re-derives or checks the owner against the field that was actually verified.

The clearest concrete abuse is `StatusHandler`, which writes a `Shipit::Status` record straight from attacker-controlled fields (`state`, `context`, `description`, `target_url`) for any commit matching the attacker-chosen `sha`, without any callback to the GitHub API to confirm the status is genuine:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [8](#0-7) 

Since `ci.require`/`ci.blocking` checks in `shipit.yml` gate whether a stack considers a commit deployable purely by looking at `Status` records tied to specific `context`s, an attacker can forge a `"success"` status for a required CI context on a commit belonging to a stack in a fully-protected organization (one that *does* have a `webhook_secret` configured), bypassing that org's authentication entirely by routing verification through an unrelated, unprotected org.

### Impact Explanation
This breaks the equality "organization that authenticated == repository that is written," matching High severity per the rules: escalation into unauthenticated write of stack/commit state, and it is a plausible path to an **unauthorized deploy** — forged CI success statuses satisfy `ci.require`, letting a continuous-deployment-enabled stack (or a human clicking Deploy who trusts the green CI status) ship an unreviewed/unapproved commit to production. It also allows unauthenticated cross-repository writes (Status records, and via `PushHandler`, spurious `GithubSyncJob` triggers) on any stack, regardless of whether that stack's own org has a webhook secret configured.

### Likelihood Explanation
Requires no credentials, no session, no GitHub App private key, and no knowledge of any org's `webhook_secret` — the attacker only needs any one onboarded org in the multi-org config to have an unset/blank `webhook_secret` (documented as optional in `docs/setup.md`), which is a realistic real-world configuration for a low-value/test org while other production orgs are protected. The attacker crafts the JSON body themselves; both `repository.owner.login` and `repository.full_name` are entirely attacker-controlled and unrelated to each other in the code.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the repository/stack strictly from the organization that was actually verified (e.g., require `repository.full_name.split('/').first.downcase == repository_owner.downcase`, or better, verify against the owner derived the same way the handler will use it), rejecting the webhook (422) on mismatch. Alternatively, always require a `webhook_secret` per configured organization in multi-org setups, and refuse to boot/serve webhooks for organizations missing one.

### Proof of Concept
1. Configure two orgs in `secrets.yml`: `weak-org` (no `webhook_secret`) and `strong-org` (protected, with `webhook_secret` set), each with a stack, e.g. `strong-org/target-repo` having `ci.require: ["ci/build"]` and continuous deployment enabled.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "weak-org" }, "full_name": "strong-org/target-repo" },
  "sha": "<sha of an undeployed commit in strong-org/target-repo>",
  "state": "success",
  "context": "ci/build",
  "description": "forged"
}
```
No `X-Hub-Signature` header needed.
3. `verify_signature` resolves `repository_owner` = `"weak-org"`, calls `Shipit.github(organization: "weak-org")`, whose `verify_webhook_signature` returns `true` because `webhook_secret` is blank.
4. `StatusHandler#process` runs against the payload, resolving the target commit purely by `sha`, and creates a `Status(state: "success", context: "ci/build")` on the commit belonging to `strong-org/target-repo`, satisfying the CI requirement and enabling deploy/continuous delivery — despite `strong-org`'s webhook secret never having been checked.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
