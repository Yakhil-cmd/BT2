### Title
Webhook organization used for signature verification is decoupled from the repository acted upon, enabling cross-repository webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) used to authenticate an incoming webhook based on `repository.owner.login` (or `organization.login`), while the downstream event handlers act on a completely different field, `repository.full_name`. Nothing ties these two fields together, so a request can be signed as belonging to one organization while being processed as an event for a repository under a different organization.

### Finding Description
`verify_signature` picks the app/secret purely from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` and is passed to `Shipit.github(organization: repository_owner)`, which resolves to a per-organization `GitHubApp` instance holding that organization's own `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check succeeds, the actual event handler (`Handler`) determines which repository/stack to act on using a *different* field of the same payload — `repository.full_name` — with no cross-check against `repository.owner.login`: [5](#0-4) 

For example, `PushHandler` looks up stacks solely from `repository_name` (i.e., `repository.full_name`) and calls `stack.sync_github(expected_head_sha: params.after)`: [6](#0-5) 

In a Shipit instance configured with the multi-organization GitHub App schema (`Shipit.github_organizations`, `github_app_config`), each organization has its own webhook secret: [7](#0-6) 

An attacker who legitimately administers "their-org"'s GitHub App integration (and thus knows/controls that org's `webhook_secret`) can send a POST directly to Shipit's `/github/webhooks` endpoint with a payload where:
- `repository.owner.login` = `"their-org"` (so `verify_signature` picks and successfully verifies against *their* org's secret), but
- `repository.full_name` = `"victim-org/victim-repo"` (so the `Handler` subclasses resolve and act on a stack belonging to a different, victim organization they do not control).

Because the HMAC signature only proves the request was signed with *some* configured organization's secret, not that the organization who signed it matches the repository the payload claims to describe, this breaks the binding: **organization authenticated == repository written**.

### Impact Explanation
Depending on the handler triggered, this can cause a legitimate Shipit instance to record/act on a forged sync for a repository/stack the attacker does not control, e.g. `PushHandler` invoking `stack.sync_github(expected_head_sha:)` on a victim stack, `CheckSuiteHandler`/`StatusHandler` altering commit deployability status, or `MembershipHandler`/pull-request handlers mutating team/PR state for repositories outside the attacker's own organization. Because `sync_github` and status changes feed directly into Shipit's deployability and continuous-delivery gating logic used elsewhere in `Stack`, this can influence unauthorized deploy/rollback decisions for a repository the attacker has no legitimate access to — a cross-repository write across an organizational trust boundary. This matches the High/Critical impact class of unauthorized/forged actions on a repository the attacker does not otherwise have access to.

### Likelihood Explanation
This requires the attacker to control at least one legitimate GitHub App/organization integration configured in the same multi-tenant Shipit instance (i.e., they must know a valid `webhook_secret` for *some* org tracked by that instance) — which is a realistic scenario in multi-tenant/shared Shipit deployments where different teams or orgs share one instance. No GitHub session, `ApiClient` token, or privileged Shipit account is required; only the ability to reach the public `/github/webhooks` endpoint and possession of one org's webhook secret.

### Recommendation
Verify that the organization used to select/validate the webhook signature (`repository.owner.login` / `organization.login`) actually matches the organization portion of `repository.full_name` before dispatching to handlers, e.g. reject the request (or refuse to process it) if `repository_owner` does not case-insensitively equal the owner segment parsed from `repository.full_name`. This closes the gap analogous to requiring `totalSupply <= maxCap` — i.e., require `repository_owner == owner_of(repository.full_name)` before trusting the payload.

### Proof of Concept
1. Configure/administer a GitHub App integration for `attacker-org` on the shared Shipit instance, obtaining `attacker-org`'s `webhook_secret`.
2. Craft a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac using attacker-org's webhook_secret>` over the raw body.
4. POST to `/github/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and successfully verifies the signature (as noted in `app/controllers/shipit/webhooks_controller.rb:24-30`).
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` (per `app/models/shipit/webhooks/handlers/handler.rb:36-38`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — an action the attacker has no legitimate authorization to trigger.

Note: I was not able to fully trace, within the available tool budget, the exact downstream code path from `sync_github`/`ContinuousDeliveryJob` to confirm whether this alone is sufficient to trigger an actual deploy execution versus only updating cached commit/head state; this final step should be verified in the engine's `Stack#sync_github` and `ContinuousDeliveryJob` implementations before finalizing severity.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
