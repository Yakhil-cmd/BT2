### Title
Attacker-controlled PR label injects arbitrary environment variables (e.g. `LD_PRELOAD`) into deploy-host command execution - (File: app/models/shipit/review_stack.rb:84-93)

### Summary
`Shipit::ReviewStack#env` merges every label name on a linked pull request, upcased, into the task/command environment with the value `"true"`, with no allow-list or key filtering. Since PR labels are attacker-controlled (any collaborator on a PR tied to a review stack can add a label), this lets an attacker inject env vars such as `LD_PRELOAD` that flow unfiltered through `TaskCommands#env` and `Command#unbundled_env` into `PTY.spawn`.

### Finding Description
The broken binding: `Command#unbundled_env`'s resulting key set is claimed to be exactly `BASE_ENV keys ∪ {PATH} ∪ Shipit.env keys ∪ deploy_spec.machine_env keys ∪ @task.env keys`, i.e. `keys(unbundled_env) == keys(BASE_ENV) ∪ {PATH} ∪ keys(Shipit.env) ∪ keys(deploy_spec.machine_env) ∪ keys(@task.env)`. This equality is false in practice, because `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) also merges `@stack.env`, and for a `Shipit::ReviewStack` that method is overridden (`app/models/shipit/review_stack.rb:84-93`) to inject `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }` — an attacker-controlled, unbounded key set derived from PR labels, not from any of the five named sources.

Path: `PullRequest::LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `pull_request.labels = params.pull_request.labels.map(&:name)` whenever a labeled/unlabeled/opened/reopened webhook event is received for a repository that has a matching, non-archived stack. `ReviewStack#env` reads `pull_request.labels`, upcases each label, and sets it to `"true"` unconditionally — no allow-list, no restriction to known/expected keys. `TaskCommands#env` merges `@stack.env` in the middle of its chain (`lib/shipit/task_commands.rb:35`), after which `Command.new(command_line, env:, ...)` stores it as `@env`, and `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) does `BASE_ENV.merge('PATH' => ...).merge(@env.stringify_keys)` — the attacker-controlled key overwrites anything already present under that name, and if it's a new key (like `LD_PRELOAD`), it's simply added. `Command#start` then calls `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` (`lib/shipit/command.rb:92`), so the injected variable is inherited by every process executed for that task.

Exploit: An attacker with permission to label a pull request that is `capture_labels?`-eligible (opened/labeled/unlabeled/reopened on an active, non-archived stack) adds a label named `ld_preload` (or `ld_library_path`, `bundle_gemfile`, `ruby_yjit_enable`, etc.) to their PR. The next legitimately-signed webhook from GitHub (signed with that repository's own `webhook_secret`, which the repo owner legitimately controls) is processed by `LabelCapturingHandler`, which writes `labels: ['ld_preload']` onto the `PullRequest` record via `capture_labels`. On the next deploy/task for that review stack, `ReviewStack#env` produces `{'LD_PRELOAD' => 'true'}`, which flows through `TaskCommands#env` and `Command#unbundled_env` unchanged into `PTY.spawn`.

Why existing guards don't stop it: webhook signature verification, `ExplicitParameters` schema validation, and `capture_labels?`'s state checks all validate *that this is a genuine webhook for this repository's own PR*, not *what label names are semantically safe to promote into the process environment*. There is no allow-list, denylist, or sanitization of label names anywhere in `ReviewStack#env`, `TaskCommands#env`, or `Command#unbundled_env`. Labels are free-form GitHub PR labels which the PR author/maintainer of their own repository controls entirely, and review stacks are explicitly designed to run commands based on a PR from a possibly-forked, less-trusted branch (that's the point of the `review_stacks_enabled` feature), so this crosses a trust boundary the label-to-env mechanism does not account for.

### Impact Explanation
This allows an unprivileged (from Shipit's perspective) actor who can label a PR against their own repository's review-stack-enabled configuration to set arbitrary environment variable names/values (name derived from label, value fixed to `"true"`) for every command run by that stack's tasks (install steps, deploy steps, etc.), executed via `PTY.spawn` on the deploy host. `LD_PRELOAD=true` itself is likely to cause the dynamic loader to fail/abort exec'd processes (a denial of that specific task), but the underlying primitive — attacker-controlled env-var *names* landing unfiltered in `PTY.spawn`'s environment — is a genuine command-execution-environment injection into the shared deploy host process, matching the "Critical - RCE on the deploy host via `Command`/`PTY.spawn`" category if any exploitable env var name (e.g., one honored by an interpreter/shell/tool in the deploy pipeline, such as `BASH_ENV`, `RUBYOPT`, `NODE_OPTIONS`, `PERL5OPT`, etc.) is used instead of `LD_PRELOAD`. Blast radius is scoped to the one stack/repository owning the PR (labels only affect that stack's own tasks), but it is repeatable on every deploy of that stack as long as the label remains attached, and any repository owner who enables `review_stacks_enabled` is exposed to this from any PR-labeling actor on their own repo (including forks, depending on collaborator permissions for labeling).

### Likelihood Explanation
Preconditions: `repository.review_stacks_enabled` must be true, and the PR must be tied to a non-archived, provisioned `ReviewStack`. Labeling a PR typically requires write/triage access to the repository (not merely opening a PR), so the realistic attacker is a maintainer/collaborator of a review-stack-enabled repo, or in configurations where GitHub Actions/bots auto-label PRs from forks. No Shipit secrets are needed — only the ability to label a PR on a repository that already has review stacks enabled and linked to Shipit, and for the webhook to be delivered (which happens automatically via the already-configured GitHub webhook). This is a low-cost, deterministic, repeatable action.

### Recommendation
Restrict `ReviewStack#env` to only project through a strict allow-list of expected/safe env var name patterns (e.g., prefix-namespaced like `PR_LABEL_<NAME>` instead of raw upcased label names), or drop the label-to-env-var feature and instead expose labels as a single opaque `PR_LABELS` string for use via explicit, safe interpolation rather than raw process environment injection. At minimum, block label names that map to loader/interpreter-sensitive variable names (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `BASH_ENV`, `RUBYOPT`, `NODE_OPTIONS`, `PERL5OPT`, `PYTHONSTARTUP`, etc.) before merging into `Command`'s environment.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_test.rb (conceptual, no live GitHub required)
test "labels injected via webhook propagate into Command#unbundled_env" do
  stack = shipit_stacks(:review_stack) # a provisioned, non-archived ReviewStack
  pull_request = stack.pull_request
  pull_request.update!(labels: ['ld_preload'])

  task_commands = Shipit::TaskCommands.new(shipit_tasks(:deploy_on_review_stack))
  assert_equal 'true', task_commands.env['LD_PRELOAD']

  command = Shipit::Command.new('true', env: task_commands.env, chdir: Dir.tmpdir)
  assert_equal 'true', command.unbundled_env['LD_PRELOAD']
end
```
This demonstrates: `stack.pull_request.labels = ['ld_preload']` (attacker-controlled via `LabelCapturingHandler#capture_labels`) → `ReviewStack#env['LD_PRELOAD'] == 'true'` → `TaskCommands#env['LD_PRELOAD'] == 'true'` → `Command#unbundled_env['LD_PRELOAD'] == 'true'`, the exact value reaching `PTY.spawn` in `Command#start`.
