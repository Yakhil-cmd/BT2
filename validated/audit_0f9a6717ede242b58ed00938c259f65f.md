### Title
Signed Message / Signed Package Authentication Lacks Network (`alt`) Binding, Enabling Cross-Network/Fork Replay of Authorizations - (File: `signed_message.js`, `object_hash.js`)

### Summary
`signMessage()`/`validateSignedMessage()` in `signed_message.js` build the hash-to-sign for off-unit signed messages (`is_valid_signed_package`, wallet "sign" requests, hub logins) via `objectHash.getSignedPackageHashToSign()`, which hashes only `signed_message`, `authors`, `last_ball_unit`, `version` — never the network identifier (`constants.alt`/`GENESIS_UNIT`). This is the same class of bug as the reported hardcoded-`chainId` `DOMAIN_SEPARATOR`: an authorization signature is not cryptographically bound to the specific chain/network instance it was produced for, so it can be replayed on a different network (mainnet/testnet/devnet, or a post-hard-fork chain sharing the same address derivation) where the signer's address still exists.

### Finding Description
In `object_hash.js`:
```
function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
``` [1](#0-0) 

Compare with `getUnitHashToSign`, used for real DAG units, which operates on the naked *unit* object that always retains the `alt` field (network fork identifier) via `getNakedUnit` (only `unit`, `headers_commission`, `payload_commission`, `oversize_fee`, `actual_tps_fee`, `main_chain_index`, and conditionally `timestamp` are stripped): [2](#0-1) [3](#0-2) 

The regular unit path is protected because `validation.js` checks `objUnit.alt !== constants.alt` and `alt` is embedded into `objNakedUnit`, so units carry a network/fork tag and can't be replayed on a different `alt`/version fork: [4](#0-3) 

But the *signed package* structure (`signMessage`/`validateSignedMessage`) never includes `alt` (or any other network tag). `signMessage` explicitly restricts the object to `{version, signed_message, authors[, last_ball_unit]}`: [5](#0-4) 

and `validateSignedMessage` only allows `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` — `alt`/network id is not even an allowed field: [6](#0-5) 

This signed-package format is consumed by AA oscript's `is_valid_signed_package`/`is_valid_sig`, which verify the signature purely against the given `address` using `signed_message.validateSignedMessage`: [7](#0-6) 

and reused by `wallet.js`'s "sign" flow for off-chain multisig/multilateral cosigning of arbitrary payloads: [8](#0-7) 

Because ocore addresses are derived purely from the definition/pubkey (`getChash160`) with no network salt, and because `alt`/`version`/network-specific constants (e.g. `GENESIS_UNIT`, `constants.alt`, devnet/testnet flags in `constants.js`) are never mixed into `getSignedPackageHashToSign`, the exact same address+definition can exist and be funded on multiple parallel ocore networks/forks (mainnet, testnet, a devnet fork, or a network after a hard fork that only bumped `constants.alt`/`version`). A signed package/authorization produced by a user for use on one such network is byte-identical in its signed content on all of them, so it validates successfully everywhere the address/definition and any referenced `last_ball_unit` happen to be reachable.

### Impact Explanation
Any AA that accepts a `signed_package`/`signed_message` as an authorization proof (e.g. off-chain order signing patterns as in `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript`) can have that authorization replayed against the AA on a sibling network/fork sharing the same address, or reused after a hard fork changes only the network tag while keeping the same address space — leading to unauthorized fund movement, double execution of an intended single-use authorization, or draining of AA/wallet funds via off-chain-signed-message replay. This maps to "unauthorized spending" / "AA fund loss" impact categories.

### Likelihood Explanation
Requires the existence of another ocore instance/fork (testnet, devnet, or a post-hard-fork chain) where the victim's address/definition is also present and funded, and an AA or wallet flow that accepts a previously-observed signed package. This is realistic in ocore's own multi-network design (mainnet/testnet/devnet share the same codebase and address derivation, differing mainly by `constants.alt`/version constants), making the scenario directly reachable by any AA author who builds a signed-message based authorization scheme, or by any hard fork event — matching the external report's "hard fork replay" scenario but reachable purely through in-scope oscript/AA and wallet signing paths.

### Recommendation
Include `constants.alt` (and ideally `constants.version`/network identity) inside the hashed/signed structure for signed packages, mirroring what `getUnitHashToSign` already does for on-chain units, so that `getSignedPackageHashToSign` binds the signature to the specific network/fork it targets. Reject signed packages during `validateSignedMessage` whose embedded network tag does not match the currently running network's `constants.alt`.

### Proof of Concept
1. On network A (e.g. mainnet, `constants.alt = '1'`), a user signs a `signed_message` payload with `signMessage()`, producing `objUnit = {version, signed_message, authors:[{address, authentifiers}], last_ball_unit?}` and hash `objectHash.getSignedPackageHashToSign(objUnit)`.
2. The same address (derivable identically on any ocore network from the same definition/pubkey) exists and is funded on network B (e.g. a testnet/devnet fork, or network A after a hard fork that only changed `constants.alt`/version).
3. The attacker submits the identical `signed_message`/`signed_package` object plus signature to an AA or wallet "sign" endpoint on network B.
4. `validateSignedMessage` (`signed_message.js`) and formula `is_valid_signed_package`/`is_valid_sig` (`formula/evaluation.js`) verify the signature purely via `ecdsaSig.verify` against `objectHash.getSignedPackageHashToSign`, which contains no network tag, so validation succeeds and the AA executes the authorized action on network B even though the signature was never intended for that network.
