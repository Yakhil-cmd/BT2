## Title
Deploy spec `machine.environment` from checked-out `shipit.yml` overwrites `GITHUB_TOKEN`/`GIT_ASKPASS` in `TaskCommands#env`, feeding attacker-controlled values into `PTY.spawn` - (`lib/shipit/task_commands.rb`)

## Summary
`TaskCommands#env` merges `deploy_spec.machine_env` — an unfiltered hash sourced directly from the repository's checked-out `shipit.yml` — after `base_env`/stack env (which sets `GITHUB_TOKEN`/`GIT_ASKPASS` from `Shipit.github(organization:).token`) and before `@task.env`. Unlike `deploy_variables`/`rollback_variables`, `machine_env` is never passed through `EnvironmentVariables#permit`, so a `shipit.yml` author can declare a `machine.environment.GITHUB_TOKEN` (or `GIT_ASKPASS`) key that silently overrides the App-issued token/askpass script used by subsequent git commands executed via `PTY.spawn`.

## Finding Description
Broken binding: `Shipit::Commands#base_env['GITHUB_TOKEN']` (set via `Shipit.github(organization:).token` at [1](#0-0) ) is expected to equal the `GITHUB_TOKEN` present in the environment that reaches `PTY.spawn` in `Command#start`/`#unbundled_env` ( [2](#0-1) ). This binding is broken by the merge order in `TaskCommands#env`:

```
super            # base_env (GITHUB_TOKEN/GIT_ASKPASS from Shipit.github) + @stack.env
  .merge(literal task hash)
  .merge(deploy_spec.machine_env)   # <-- untrusted, unfiltered
  .merge(@task.env)
``` [3](#0-2) 

`deploy_spec.machine_env` is defined as `config('machine', 'environment') || {}` with no key restriction or sanitization [4](#0-3) , in contrast to `deploy_variables`/`rollback_variables`, which are explicitly whitelisted via `filter_deploy_envs`/`filter_rollback_envs` calling `EnvironmentVariables.with(env).permit(...)` [5](#0-4) . `deploy_spec` is instantiated as `DeploySpec::FileSystem.new(@task.working_directory, @stack)` — i.e., parsed from the just-checked-out `shipit.yml` of the commit/branch being deployed [6](#0-5) . Since `@task.env` (the last merge) is populated only from deploy/rollback trigger-time variables (filtered against `deploy_variables`/`rollback_variables`), it will not contain a `GITHUB_TOKEN` key unless the deploy spec itself declared such a variable, so the malicious `machine.environment.GITHUB_TOKEN` value from `machine_env` survives to the final env hash. That hash is passed as `env:` into `Command.new`, stored in `@env`, and merged over `BASE_ENV`/`PATH` in `Command#unbundled_env`, which is what `PTY.spawn` receives [7](#0-6) , [8](#0-7) .

No code re-asserts `GITHUB_TOKEN`/`GIT_ASKPASS` after the `machine_env` merge; no guard (`verify_signature`, `force_github_authentication`, `EnvironmentVariables#permit` for `machine_env` specifically) exists to block this since `filter_deploy_envs`/`filter_rollback_envs` only apply to explicitly-declared task/deploy variables, not to `machine_env`.

**Attacker path caveat**: exploiting this requires the attacker's `shipit.yml` to actually be checked out and run as the *active* deploy spec for a stack, i.e., their branch/commit must be deployed by Shipit (either via `Stack#trigger_deploy` on a branch they can push commits that get merged/deployed, or via `ReviewStack`, which is provisioned directly from a pull request's head branch/ref per `stack_attributes` in `review_stack_adapter.rb` — `branch: params.pull_request.head.ref` [9](#0-8) ). For review stacks, the deploying commit's `shipit.yml` originates from the PR head, which an attacker who owns the PR's source branch/fork fully controls, satisfying the "unprivileged attacker who can push to a fork / open a PR" precondition.

## Impact Explanation
An attacker whose PR is deployed as a `ReviewStack` (or whose commit reaches a deployed branch) can overwrite `GITHUB_TOKEN` and `GIT_ASKPASS` for every command run in that task's environment (`git fetch`/`clone`/`checkout`, dependency installation, deploy steps), causing the real GitHub App token issued for that organization to be replaced with an attacker string for downstream git operations, or conversely enabling exfiltration if the attacker's `shipit.yml` step echoes `$GITHUB_TOKEN` to task output/logs (which are readable per the stack's task-stream visibility). This matches the Critical impact category: exfiltration of `GITHUB_TOKEN` / deploy-time secrets via an attacker-authored `shipit.yml`. The blast radius is scoped to tasks run against that specific stack/organization's token, not cross-tenant, but is fully repeatable on every deploy of the attacker-controlled branch.

## Likelihood Explanation
Precondition: the attacker's commit/branch must be executed as a deploy or review-stack task, which for `ReviewStack` happens automatically off an incoming pull request without merge or maintainer approval (per `review_stack_adapter.rb`), and for a regular `Stack` deploy requires the branch to be deployed (which may need push access to the deploy branch or PR merge, depending on Shipit configuration). No secrets, sessions, or elevated roles are required from the attacker; only the ability to author `shipit.yml` in the deployed ref. Cost is a single commit/PR.

## Recommendation
Do not allow `machine_env` (or any deploy-spec-sourced hash) to define reserved key names (`GITHUB_TOKEN`, `GIT_ASKPASS`, `GITHUB_DOMAIN`, `PATH`, etc.). Either strip these keys from `deploy_spec.machine_env` before merging, or re-apply `base_env`'s `GITHUB_TOKEN`/`GIT_ASKPASS`/`GITHUB_DOMAIN` as the final merge step in `TaskCommands#env` (and `StackCommands#env`) so they cannot be overridden by untrusted deploy-spec content, mirroring the `filter_deploy_envs`/`filter_rollback_envs` whitelist approach already used for task/deploy variables.

## Proof of Concept
```ruby
# test/unit/task_commands_env_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsEnvOverrideTest < ActiveSupport::TestCase
    setup do
      @stack = shipit_stacks(:shipit)
      @deploy = @stack.trigger_deploy(@stack.commits.last, shipit_users(:walrus))
      @commands = TaskCommands.new(@deploy)
      Shipit.github(organization: @stack.repository.owner).stubs(:token).returns('real-app-token')
    end

    test "malicious machine_env overrides the App-issued GITHUB_TOKEN" do
      @commands.deploy_spec.stubs(:machine_env).returns('GITHUB_TOKEN' => 'attacker-controlled')

      env = @commands.env

      # Binding under test, before vs after:
      assert_equal 'real-app-token', Shipit.github(organization: @stack.repository.owner).token
      refute_equal 'real-app-token', env['GITHUB_TOKEN'],
        "expected shipit.yml's machine.environment.GITHUB_TOKEN to be blocked, but it overrode the App token"
      assert_equal 'attacker-controlled', env['GITHUB_TOKEN']
    end
  end
end
```
This demonstrates that `TaskCommands#env['GITHUB_TOKEN']` diverges from the value computed in `Shipit::Commands#base_env`, with no reconciliation step, confirming the vulnerability.
