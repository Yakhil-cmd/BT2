### Title
API client scoped to a single stack can create arbitrary stacks for other repositories - ([File: app/controllers/shipit/api/stacks_controller.rb])

### Summary
The bug class described in the report is a binding break between what a credential is scoped to authorize and what it is actually allowed to touch, introduced because an "initializer"-style action (creating a new resource) is not bound to the same scoping check used everywhere else. In shipit-engine, `ApiClient` records can be scoped to a single `Stack` via `belongs_to :stack, optional: true` [1](#0-0) , and `Api::BaseController#stacks`/`#stack` correctly restrict `index`/`show`/`update`/`destroy` to that one stack when `current_api_client.stack_id?` is true [2](#0-1) . However, `Api::StacksController#create` never consults this scope — it just builds a brand-new `Stack` for whatever `repo_owner`/`repo_name` are supplied in the request, gated only by the coarse `write:stack` permission string [3](#0-2) .

### Finding Description
The binding that should hold is: `stack the token authorizes == stack the token's action touches`. For `index`, `show`, `update`, and `destroy`, this equality is enforced through `stacks.from_param!` / `stacks.where(...)`, which is scoped by `current_api_client.stack_id` when present [2](#0-1) .

`create`, however, is exempted from this scoping:
```ruby
def create
  stack = Stack.new(create_params)
  stack.repository = repository
  stack.save
  render_resource(stack)
end
``` [4](#0-3) 

`require_permission :write, :stack, only: %i[create update destroy]` only checks that the token's `permissions` array contains the literal string `write:stack` [5](#0-4) , via `ApiClient#check_permissions!`, which has no knowledge of `stack_id` at all [6](#0-5) . The `repository` used for the new stack is derived purely from client-supplied `repo_owner`/`repo_name` params, found-or-created on the fly [7](#0-6) .

The fixture data confirms stack-scoped tokens are a real, intended pattern (`here_come_the_walrus` client is scoped to the `shipit` stack with only `read:stack`) [8](#0-7) , and existing tests validate the scoping works for `index` [9](#0-8) . No equivalent test or enforcement exists for `create`, confirming the scope is not checked there.

Before: a client scoped to stack A with `write:stack` is expected to only mutate stack A.
After: the same client, hitting `POST /stacks` (or `/stacks.json` via `Api::StacksController#create`) with arbitrary `repo_owner`/`repo_name`, creates and controls an entirely new `Stack`/`Repository` unrelated to A — breaking `stack authorized == stack touched`.

### Impact Explanation
This allows an attacker holding a narrowly-scoped API token (one meant to authorize writes to a single stack) to create new stacks bound to arbitrary GitHub repositories that the token was never meant to have access to. Since stack creation also triggers webhook setup and subsequent deploy/task capabilities tied to that new stack, this is effectively a cross-repository write capability obtained from a token that should be confined to one stack — matching the "Critical: cross-repository writes" impact bucket.

### Likelihood Explanation
Any deployment that issues stack-scoped `write:stack` API tokens (a documented, intended usage pattern per the `ApiClient` model and fixtures) is affected as soon as such a token is used against the `create` endpoint. No special privilege beyond possessing that one scoped token is required, and the exploit is a single unauthenticated (from the app's perspective, just token-authenticated) API call — no timing/front-running race is even needed since the check is simply absent for this action.

### Recommendation
In `Api::StacksController#create`, when `current_api_client.stack_id?` is true, reject the request (or otherwise verify the newly created stack's identity matches the token's bound `stack_id`), mirroring the scoping already applied to `index`/`show`/`update`/`destroy` via `stacks`/`stack`. More generally, `ApiClient#check_permissions!` should be extended to consider `stack_id` scoping wherever a stack-scoped client can affect resources outside its assigned stack.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack: shipit_stack_A` with `permissions: ['write:stack']` (analogous to fixture `here_come_the_walrus`, but with `write:stack` instead of `read:stack`).
2. Authenticate as this client and call:
   ```
   POST /stacks.json
   repo_owner=some-other-org
   repo_name=some-other-repo
   environment=production
   branch=main
   ```
3. Observe that `Api::StacksController#create` succeeds and a brand-new `Stack`/`Repository` for `some-other-org/some-other-repo` is created and returned, even though the token was only ever meant to authorize actions on `shipit_stack_A` [4](#0-3) .
