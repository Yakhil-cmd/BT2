### Title
Webhook signature verified against payload's `repository.owner.login`, but write targets (`repository.full_name` for push, bare `sha` for status) are never checked against that same organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub Apps/organizations from a single instance (`docs/setup.md:182-209`). Each organization has its own `webhook_secret`. When a webhook arrives, `WebhooksController#verify_signature` picks which organization's secret to validate the HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted payload, then calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

Once the signature passes, the event handlers act on a *different* field of the same payload to decide which resource to mutate: `Handler#repository_name` (used by the push handler to select which `Repository`/`Stack` to sync) reads `payload.dig('repository', 'full_name')`, and `StatusHandler` doesn't even use the repository at all - it looks up commits globally by `sha`. [3](#0-2) [4](#0-3) 

Because the HMAC only proves "this request was signed with OrgA's secret," not "this request may only mutate OrgA's data," an operator (any GitHub org owner) who has legitimately configured their own org's GitHub App on a shared Shipit instance can forge a payload whose `repository.owner.login`/`organization.login` matches their own org (so the correct secret is picked and the signature validates) while the `repository.full_name`/`sha` field references a repository or commit belonging to a *different* organization hosted on the same instance.

### Finding Description
This is the same class of bug as the referenced Olympus finding: a value that is checked/authenticated (the organization identity behind the signature) is not the same value that the code subsequently trusts to authorize the write (the repository/commit that is mutated). The signature check binds *"which secret matches"* to `repository.owner.login`, but the actual mutation binds to `repository.full_name` (push) or nothing at all (status), so the two are never required to agree.

- `WebhooksController#verify_signature` selects the app/secret by `repository_owner` [5](#0-4) .
- `PushHandler` resolves the target stacks purely from `repository.full_name`, with no re-check that this repository belongs to the organization whose secret validated the request [6](#0-5) .
- `StatusHandler` is worse: it resolves target commits by `Commit.where(sha: params.sha)` with **no repository scoping whatsoever**, so any commit sha existing anywhere in the Shipit instance's database (across every hosted org/stack) can have a status written to it by whoever controls a validly-configured org's webhook secret [4](#0-3) .

### Impact Explanation
Commit statuses gate whether a commit is "deployable" in Shipit's UI/checks flow. By forging a `status` event that is validly signed under an org the attacker legitimately controls (e.g. their own GitHub App/org registered on the shared instance) but whose `sha` corresponds to a commit belonging to a victim organization's stack, the attacker can write a fabricated "success" status for a required CI context onto that commit, satisfying deploy-gating checks the attacker never actually passed. This lets an attacker who has no push access, no `ApiClient` token and no session on the victim's stack push a stack toward an unauthorized deploy decision - matching the "unauthorized deploy" Critical impact criterion. The push-handler variant additionally lets the attacker force a `GithubSyncJob`/resync on stacks belonging to a different organization than the one whose credentials they used, at a time of their choosing.

### Likelihood Explanation
Requires only that Shipit be configured to host more than one GitHub organization (an explicitly documented and supported configuration, `docs/setup.md:182-209`) and that the attacker controls (or has previously configured/known secrets for) at least one of those hosted organizations - they need no privileges on the victim organization/repository, no `ApiClient` token, and no authenticated Shipit session, satisfying the "unprivileged attacker" requirement.

### Recommendation
After signature verification succeeds for organization `O`, re-validate that every repository/commit referenced by the payload actually belongs to `O` before dispatching to handlers - e.g., require `repository.full_name`'s owner segment to equal `repository_owner`, and have `StatusHandler` (and any other handler that resolves records without going through `Handler#repository_name`) scope its lookup (`Commit.where(sha:)`) to commits belonging to the verified organization's repositories, not a global lookup.

### Proof of Concept
1. Shipit instance hosts two orgs, `OrgA` (attacker-controlled, own GitHub App/secret) and `OrgVictim` (unrelated, hosts the target stack), per the multi-org setup in `docs/setup.md`.
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha, known publicly via GitHub UI/API>",
     "state": "success",
     "context": "ci/required-check",
     "organization": {"login": "OrgA"}
   }
   ```
3. Attacker signs it with `HMAC-SHA1(OrgA_webhook_secret, raw_body)` and sets `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app config, and the signature validates successfully [7](#0-6) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`, writing a fabricated "success" status onto the victim's commit with no check that it belongs to `OrgA` [4](#0-3) .
6. The victim stack's commit now shows a passing required check it never actually received, which can enable/queue an unauthorized deploy decision on `OrgVictim`'s stack.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
