### Title
NULL/undefined pointer dereference on unchecked `output_index` in private payment chain processing - ([File: wallet.js])

### Summary
`emitNewPrivatePaymentReceived()` in `wallet.js` reads `payload.outputs[objHeadPrivateElement.output_index]` without checking that `output_index` is a valid, in-bounds index into `payload.outputs`. A malicious pairing/private-payment counterparty can send a private-payment chain whose head element has an `output_index` that is out of range for the accompanying `payload.outputs` array (which only needs to be a non-empty array of non-empty objects), causing `payload.outputs[output_index]` to evaluate to `undefined` and the subsequent `.amount` access to throw a TypeError, analogous to the CVE's NULL pointer dereference caused by an incomplete/malformed descriptor being dereferenced without a bounds/nullness check.

### Finding Description
The message handler `handlePrivatePaymentChains(ws, body, from_address, callbacks)` [1](#0-0)  validates incoming private-payment chains structurally but never validates that `output_index` (when present on the head element) is within the bounds of `payload.outputs`:

```
c.every(e =>
    isNonemptyObject(e) &&
    isNonemptyString(e.unit) &&
    isNonemptyObject(e.payload) &&
    isNonemptyString(e.payload.asset) &&
    isNonemptyArray(e.payload.inputs) &&
    isNonemptyArray(e.payload.outputs) &&
    e.payload.inputs.every(isNonemptyObject) &&
    e.payload.outputs.every(isNonemptyObject)
)
``` [2](#0-1) 

After the chains are individually validated (`network.handleOnlinePrivatePayment`) and accepted, `checkIfAllValidated()` is invoked, which calls `emitNewPrivatePaymentReceived(from_address, arrChains, current_message_counter)` [3](#0-2) .

Inside `emitNewPrivatePaymentReceived`, for the indivisible-asset branch, the code blindly indexes into `payload.outputs` using the attacker-supplied `output_index` from the head private element, with no bounds check against `payload.outputs.length`:

```
var output = objHeadPrivateElement.output;
if (output && output.address && arrAddresses.indexOf(output.address) >= 0){
    assocAmountsByAsset[asset] += payload.outputs[objHeadPrivateElement.output_index].amount;
    assocMyReceivingAddresses[output.address] = true;
}
``` [4](#0-3) 

If `output_index` is larger than `payload.outputs.length - 1` (or otherwise doesn't correspond to a real element, e.g. negative or huge), `payload.outputs[output_index]` is `undefined`, and `.amount` throws `TypeError: Cannot read properties of undefined`. This is the direct analog of the CVE's NULL pointer dereference from an "incomplete" descriptor field that the code assumes is always present/valid without checking.

This call path is reachable by any device that is allowed to send `private_payments` justsaying messages (a paired counterparty in a private/one-time payment interaction, not necessarily privileged), matching the "private-payment counterparty" surface explicitly permitted by the rules.

### Impact Explanation
`handleMessageFromHub` wraps `doHandle()` in a try/catch that converts thrown exceptions into an `ifError` callback for that specific message [5](#0-4) , so a directly-thrown exception during the synchronous body of `doHandle` would be caught. However, `emitNewPrivatePaymentReceived` is invoked asynchronously, inside a nested `async.eachSeries` callback chain and further inside `checkIfAllValidated`, which executes **after** `doHandle()` has already returned (from inside `network.handleOnlinePrivatePayment`'s `ifAccepted`/`ifQueued` callbacks and eventBus event handlers). An exception thrown there is not caught by the `try/catch` in `handleMessageFromHub`, and will propagate as an unhandled exception in the event loop, crashing the wallet/hub process (denial of service — the node becomes unable to process further units/messages until restarted).

### Likelihood Explanation
Likelihood is limited by the fact that the vulnerable code path only executes for private (indivisible-asset) payment chains that are addressed to one of the local wallet's own receiving addresses (`arrAddresses.indexOf(output.address) >= 0`) and only on the divisible/indivisible payment reveal path. An attacker who is a legitimate device correspondent/private-payment counterparty of the victim can craft a private-payment chain head element with a mismatched `output_index` relative to the disclosed `payload.outputs` array and send it via `private_payments` to trigger the crash once the recipient wallet processes and accepts the chain as intended for one of its own addresses.

### Recommendation
Add explicit bounds validation for `output_index` in `handlePrivatePaymentChains`'s structural validation step (or immediately before use in `emitNewPrivatePaymentReceived` and any other consumer such as `forwardPrivateChainsToOtherMembersOfOutputAddresses`), e.g. require `ValidationUtils.isNonnegativeInteger(output_index) && output_index < payload.outputs.length` whenever `output_index` is present, and defensively guard `payload.outputs[output_index]` with an existence check before dereferencing `.amount`.

### Proof of Concept
1. Attacker device is a paired correspondent of the victim (or a private-payment counterparty in a one-time address exchange).
2. Attacker sends a `private_payments` justsaying message with `body.chains = [[ { unit: <validUnit>, payload: { asset: <indivisibleAssetHash>, inputs: [...], outputs: [ {address: <victimAddress>, amount: 100} ] }, output: { address: <victimAddress> }, output_index: 5 } ]]` — i.e. `output_index` (5) is out of range for the single-element `outputs` array.
3. Provided the chain otherwise passes the structural checks in `handlePrivatePaymentChains` (isNonemptyArray/isNonemptyObject checks) and is accepted by `network.handleOnlinePrivatePayment` for the victim's own address, `checkIfAllValidated()` → `emitNewPrivatePaymentReceived()` executes `payload.outputs[5].amount`, throwing a `TypeError` outside of the `try/catch` protecting `doHandle()`, crashing the victim's wallet/hub process.

*(Note: full confirmation that `network.handleOnlinePrivatePayment`/the indivisible-asset private-payment validator does not itself bounds-check `output_index` against `payload.outputs.length` before this point could not be completed within the available search budget — the relevant validation function name was not found via `grep_search` for `validateIndivisiblePrivatePayment`, so it may live under a different name in `indivisible_asset.js` or `private_payment.js`. This should be verified in a full session before treating this as fully proven.)*
