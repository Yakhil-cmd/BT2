### Title
Missing ciphertext/sender-binding check for encrypted transactions in mempool/VM admission allows rebinding a captured ciphertext to an attacker-controlled sender - (File: `types/src/transaction/encrypted_payload.rs`, `aptos-move/aptos-vm/src/aptos_vm.rs`)

### Summary
The Rubicon report's root cause was a computation performed on one admission path (`Position._marketBuy`/`_marketSell`) that omitted a check enforced on another path (`RubiconMarket.buy`'s maker-fee logic), letting a value pass a weaker gate than the one that actually governs settlement. The Aptos-native analog found here is a binding check — `EncryptedPayload::verify()`, which cryptographically ties an encrypted-transaction ciphertext to the submitting `sender` and its `signer_auth_keys` — that is only invoked on the REST `submit_transaction` HTTP path [1](#0-0) , but is not invoked in the VM's transaction-validation/admission path that mempool actually uses to accept and gossip transactions [2](#0-1) , nor in `validate_and_add_transactions` which is the code that runs for transactions received over the shared-mempool gossip network [3](#0-2) .

### Finding Description
`EncryptedInner` bundles a `ciphertext`, `extra_config`, `payload_hash`, `encryption_epoch`, and optional `claimed_entry_fun` [4](#0-3) . The `ciphertext` is cryptographically bound at encryption time to a `PayloadAssociatedData::V1 { sender, signer_auth_keys }` via `Id::from_verifying_key_and_ad`, and `Ciphertext::verify` checks that the associated data byte-encoding still matches before accepting it [5](#0-4) . `EncryptedPayload::verify(sender, signer_auth_keys)` is the wrapper that performs this binding check [6](#0-5) , and there is an explicit unit test proving that mismatched sender/auth-key bindings are rejected by this call [7](#0-6) .

Critically, `EncryptedInner` (including the raw ciphertext bytes and `payload_hash`) is copyable, BCS-serializable data. An attacker who observes any submitted-but-not-yet-decrypted encrypted transaction on the wire can copy its entire `EncryptedInner` verbatim into a brand-new `RawTransaction` with the attacker's own `sender`, `sequence_number`, `gas_unit_price`, `expiration_timestamp_secs`, and `chain_id`, and sign it validly with the attacker's own private key. This produces a fully self-consistent, correctly signed `SignedTransaction` — signature verification succeeds because `TransactionAuthenticator::verify` only checks the signature over the (encrypted) `RawTransaction` bytes, not any relationship between the embedded ciphertext and the signing sender [8](#0-7) .

The only place in the codebase found to check that the ciphertext's associated data actually matches the transaction's claimed `sender`/`signer_auth_keys` is the REST API submission handler [1](#0-0) . The VM's `VMValidator::validate_transaction` — which is the function mempool calls for every transaction, whether locally submitted or received via inter-validator gossip — only checks feature-gating and BCS/signature well-formedness for encrypted payloads, with no call to `EncryptedPayload::verify` or any sender/AD-binding assertion [2](#0-1) . The shared-mempool ingestion path that handles gossiped transactions from peer validators also calls only this same VM validator, with no additional encrypted-payload binding check [3](#0-2) .

Because the block-level decryption pipeline only checks `payload_hash` (a hash of the plaintext) and, optionally, `claimed_entry_fun` before accepting a decryption result [9](#0-8) , and threshold decryption succeeds purely based on the ciphertext's own committed `Id` (independent of whatever `sender` the attacker later claims in the surrounding `RawTransaction`) [5](#0-4) , a rebroadcast/rebound ciphertext will decrypt correctly and then execute the victim's intended payload — but under the attacker's `sender`, sequence number, and gas payment, since the VM's executing `signer` comes from `RawTransaction.sender`, not from anything embedded in the ciphertext.

### Impact Explanation
This is a pre-validation admission mismatch: mempool/VM admission for encrypted transactions is strictly weaker than the REST-API submission gate, and the two disagree on what should be executable. A transaction whose sender/ciphertext binding is broken — which should fail admission — can instead be gossiped node-to-node, accepted into mempool, and ultimately committed and executed. This directly matches the "Pre-validation mismatch that causes a transaction which should fail admission to execute and commit" and "domain-binding failure that lets an attacker reuse or rebind a transaction" admission pivots: an attacker can capture another user's still-encrypted transaction and rebind its confidential payload to their own account context, undermining both the confidentiality guarantee of encrypted transactions and the sender-authorization invariant that the executed action's `signer` correctly represents whoever authorized the underlying intent.

### Likelihood Explanation
Encrypted transactions and the associated confidential-transaction feature are guarded by a feature flag (`ENCRYPTED_TRANSACTIONS`) and are still an emerging code path, but once enabled the only network-facing chokepoint that performs the sender/ciphertext binding check is the local REST submission handler — any transaction reaching a validator's mempool via the P2P gossip protocol from a peer (the normal path for transactions not submitted directly to that validator) bypasses this check entirely. This makes exploitation straightforward for any actor capable of observing an in-flight encrypted transaction and running/controlling a node (or an unprivileged submitter to any node in the network) to gossip a crafted rebinding.

### Recommendation
Move the `EncryptedPayload::verify(sender, signer_auth_keys)` binding check out of the REST-only submission handler and into the authoritative VM/mempool admission path — i.e., call it from `AptosVM::validate_transaction` (or the corresponding Move prologue) so that it is enforced uniformly regardless of how the transaction entered mempool (local REST submission vs. inter-validator gossip vs. any future ingress path).

### Proof of Concept
1. Enable `FeatureFlag::ENCRYPTED_TRANSACTIONS`.
2. Victim submits an encrypted transaction; observe the `EncryptedInner { ciphertext, extra_config, payload_hash, encryption_epoch, claimed_entry_fun }` on the wire before decryption occurs.
3. Attacker constructs a new `RawTransaction` with their own `sender`, `sequence_number`, `gas_unit_price`, `expiration_timestamp_secs`, `chain_id`, and the copied `EncryptedPayload::Encrypted(EncryptedInner)` (byte-for-byte identical ciphertext/payload_hash), then signs it with their own private key, producing a fully valid `SignedTransaction`.
4. Submit this transaction directly to a validator's mempool via the P2P shared-mempool protocol (not the REST `submit_transaction` endpoint) so the `api/src/transactions.rs` binding check at [1](#0-0)  is never invoked.
5. `AptosVM::validate_transaction` accepts it (no AD/sender-binding check present at [2](#0-1) ).
6. During block execution the decryption pipeline's `try_into_decrypted` succeeds because `payload_hash` matches the copied plaintext hash [9](#0-8) , and the attacker's transaction executes the victim's intended action under the attacker's own `sender`/signer context.

Note: I was not able to exhaustively trace every mempool ingestion code path (e.g., quorum-store batch validation, additional intake points) to conclusively rule out a redundant check elsewhere; this assessment is based on the `VMValidator::validate_transaction` implementation and the shared-mempool gossip-ingestion function found via search, which show no such binding check. A full audit of all mempool/consensus ingestion entry points is recommended to confirm there is no other enforcement point.

    pub fn try_into_decrypted(
        &mut self,
        eval_proof: EvalProof,
        plaintext: DecryptedPlaintext,
    ) -> Result<(), DecryptionFailureReason> {
        let Self::Encrypted(original) = self else {
            panic!("try_into_decrypted called on non-Encrypted state");
        };

        if original.payload_hash != CryptoHash::hash(&plaintext) {
            return Err(DecryptionFailureReason::PayloadHashMismatch);
        }

        if let Some(claim) = &original.claimed_entry_fun {
            let TransactionExecutable::EntryFunction(entry_fun) = plaintext.executable() else {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            };
            if *entry_fun.module() != claim.module {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
            if let Some(claimed_function_id) = &claim.function
                && entry_fun.function() != claimed_function_id.as_ident_str()
            {
                return Err(DecryptionFailureReason::ClaimedEntryFunctionMismatch);
            }
        }

        *self = Self::Decrypted {
            original: original.clone(),
            eval_proof,
            decrypted: plaintext,
        };
        Ok(())
    }

    pub fn verify(&self, associated_data: &impl AssociatedData) -> Result<()> {
        let hashed_id = Id::from_verifying_key_and_ad(&self.vk, associated_data);

        (self.associated_data_bytes == bcs::to_bytes(associated_data)?)
            .then_some(())
            .ok_or(BatchEncryptionError::CTVerifyError(
                CTVerifyError::AssociatedDataDoesNotMatch,
            ))?;

        (self.bibe_ct.id() == hashed_id).then_some(()).ok_or(
            BatchEncryptionError::CTVerifyError(CTVerifyError::IdDoesNotMatchHashedVKAndAD),
        )?;

        let to_verify = (&self.bibe_ct, &self.associated_data_bytes);

        self.vk
            .verify(&bcs::to_bytes(&to_verify)?, &self.signature)
            .map_err(|e| {
                BatchEncryptionError::CTVerifyError(CTVerifyError::SigVerificationFailed(e))
            })?;

        Ok(())
    }
