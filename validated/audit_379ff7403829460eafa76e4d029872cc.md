### Title
Webhook signature verification binds the wrong organization's secret to the wrong repository, permitting cross-organization event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC based on an organization name that is itself taken from the *unauthenticated* request body, then hands the entire body to handlers that resolve the target `Repository`/`Stack` from a *different* field of that same body (`repository.full_name`). Because Shipit supports multiple organizations, each with its own `webhook_secret` [1](#0-0) , an attacker who legitimately administers Organization A's GitHub App/webhook (and thus knows Organization A's `webhook_secret`) can craft a payload whose `repository.owner.login`/`organization.login` says "org-A" (so Shipit picks Org A's secret) but whose `repository.full_name` points at a completely unrelated repository belonging to Organization B. The signature check only verifies "this body was signed with Org A's secret" — it never verifies that the repository referenced inside the body actually belongs to Org A.

### Finding Description
`verify_signature` derives the organization used to select the verification secret directly from the untrusted payload: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` loads a per-organization config/secret map (`github_app_config`), meaning distinct organizations can have distinct `webhook_secret` values: [1](#0-0) 

The signature is verified over the *entire* raw body using the secret keyed to that self-declared `repository_owner`/`organization.login`: [4](#0-3) 

Once the signature is accepted, `create` forwards the *whole* JSON body to handlers: [5](#0-4) 

Handlers resolve the target `Stack`/`Repository` purely from `payload.dig('repository', 'full_name')`, with no cross-check against the organization that was used to authenticate the request: [6](#0-5) [7](#0-6) 

The equality that should hold is: **organization whose secret authenticated the request == organization that owns the repository being acted upon**. This binding is never enforced. `repository_owner` (used to pick the verification key) and `repository.full_name` (used to pick the acted-upon repository) are two independently attacker-controlled fields inside the same signed JSON body; nothing forces `repository.full_name`'s owner to equal `repository_owner`/`organization.login`. An attacker who controls Organization A (and therefore knows Org A's `webhook_secret`, since they can configure/replay it from their own legitimate GitHub App installation or webhook settings) can sign a payload as Org A while setting `repository.full_name` to `org-b/some-repo`, and the controller will accept and process it as a legitimate event for Org B's repository.

### Impact Explanation
This breaks the trust boundary between organizations hosted by the same Shipit instance. A forged, "validly signed" (from Shipit's point of view) webhook for a foreign repository can drive `GithubSyncJob` (importing arbitrary forged commits into a Stack's history via `stack.commits.create_from_github!`, since the sync job then fetches from GitHub using the target stack's own `github_api`, but the *decision to sync/lock/append* is triggered by attacker-controlled data), and other handlers (`push_handler.rb`, `check_suite_handler.rb`, `status_handler.rb`, `pull_request/*`) that operate on Org B's `Stack`/PR objects based purely on the forged `repository.full_name`, `sha`, `ref`, `state`, and PR fields. Depending on which handler fires, this can affect deploy-relevant state (commit statuses, PR labeling that drives review-stack provisioning, lock/unlock behavior via revert detection) for a repository/organization the attacker does not administer. This aligns with the "cross-repository writes" / "escalation into a boundary the app assumed only that organization's admins could cross" class of High/Critical impact, since the organization that cryptographically authenticated the request is not the same as the repository whose state gets mutated.

### Likelihood Explanation
Exploitation requires the attacker to be an administrator of at least one organization already configured in this Shipit instance's multi-org GitHub settings (so they legitimately know that organization's `webhook_secret`), and requires that Shipit instance to have multiple organizations configured (the multi-org schema in `github_app_config`). This is a real, supported deployment mode (not requiring any Shipit credential, `ApiClient` token or GitHub App private key), and no other authentication barrier exists between "knows one org's webhook secret" and "can forge events for any repository in the payload," making it a low-effort attack once the prerequisite (control over one onboarded organization) is met — a plausible scenario for shared/multi-tenant Shipit deployments.

### Recommendation
After verifying the HMAC, explicitly validate that the organization/owner used to select the verification secret matches the owner of `repository.full_name` (and `organization.login` if present) in the payload before dispatching to handlers — i.e., reject the webhook if `repository.full_name.split('/').first.downcase != repository_owner.downcase`. Alternatively, bind the webhook secret lookup to the resolved `Repository` record's stored organization rather than to an attacker-suppliable field in the same untrusted body.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` in `secrets.github` (multi-org schema, see `github_app_config` in `lib/shipit.rb`).
2. Attacker is an admin of `org-a` and thus knows/controls `org-a`'s `webhook_secret` (e.g., by configuring a real webhook against their own org).
3. Attacker crafts a JSON payload for the `push` event:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>"
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POSTs to `/webhooks`.
5. `WebhooksController#repository_owner` returns `"org-a"`, so `Shipit.github(organization: "org-a")` is used, and `verify_webhook_signature` succeeds because the attacker signed with Org A's real secret [2](#0-1) [4](#0-3) .
6. `create` forwards the payload to `Shipit::Webhooks.for_event('push')` handlers, which resolve the Stack via `Repository.from_github_repo_name("org-b/victim-repo")` [6](#0-5)  and enqueue a `GithubSyncJob` for Org B's stack using attacker-supplied `sha`/`ref`, despite the request never having been authenticated with anything Org B controls.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
