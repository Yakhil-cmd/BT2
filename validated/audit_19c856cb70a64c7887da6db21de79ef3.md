## Title
Cross-tenant commit status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

## Summary
`WebhooksController#verify_signature` only proves that the webhook payload was signed by the secret configured for whatever organization appears in `repository.owner.login`/`organization.login` of the payload — it does not prove that organization owns the commit being referenced. `StatusHandler#process` then looks up commits purely `Commit.where(sha: params.sha)` with zero repository/stack/organization scoping, so any org configured in `Shipit.secrets.github` (which can be an attacker's own org if the operator supports multiple GitHub orgs via `github_app_config`) can forge a status onto a commit belonging to any other stack, as long as it knows the target's SHA.

## Finding Description
The intended binding is: `organization that authenticated the payload (repository_owner in the payload) == organization owning the stack whose commit is mutated`. Tracing the code:

- `verify_signature` computes `repository_owner` from the payload itself (`params.dig('repository','owner','login')`) and calls `Shipit.github(organization: repository_owner)` to fetch that organization's `webhook_secret`/`GitHubApp`, then verifies the HMAC signature against it: [1](#0-0) [2](#0-1) 
- This design explicitly supports multi-organization deployments where `secrets.github` has one entry per org, each with its own `webhook_secret`, resolved via `github_app_config`: [3](#0-2) 
- Once signature verification passes (proving only that ATTACKER_ORG's secret was used, matching the ATTACKER_ORG value the attacker put in the payload), the request is dispatched to handlers purely by event type, with no further tie to `repository_owner`: [4](#0-3) 
- `StatusHandler#process` never re-reads `repository_owner`/`repository.full_name` from the payload at all. It resolves commits solely by SHA, globally across the whole `commits` table, and mutates every match: [5](#0-4) 
- `Commit#create_status_from_github!` then writes a `Status` record using the found commit's own `stack_id` (the victim's stack), not anything derived from the authenticated organization: [6](#0-5) 

So after tracing: the two sides of the binding are **not** equal and **not** checked to be equal anywhere in this path — `repository_owner` (attacker's org, used only for signature verification) is completely decoupled from the `stack.organization`/repository that actually owns the matched `Commit` row. No other guard (`drop_unhandled_event`, the `ExplicitParameters` schema in `StatusHandler`, `force_github_authentication`, `require_permission!`, model validations) constrains this, since those are unrelated to commit-to-organization binding; this is purely a data-authorization gap in `Commit.where(sha: ...)`.

Attack flow: attacker registers/controls ATTACKER_ORG which is a legitimate, separately-configured GitHub organization in this Shipit instance's `secrets.github` (multi-org support is a first-class feature per `github_app_config`), and knows ATTACKER_ORG's `webhook_secret` because they configured the GitHub App on their own org. They observe a victim commit's SHA (public on GitHub) belonging to VICTIM_REPO's stack. They POST to `/webhooks` a `status` event with `X-Github-Event: status`, `repository.owner.login: "ATTACKER_ORG"`, HMAC signature computed with ATTACKER_ORG's secret, and body `{"sha": "<victim_sha>", "state": "success", ...}`. `verify_signature` succeeds because it only validates against ATTACKER_ORG's own secret. `StatusHandler#process` finds the victim `Commit` by sha (global lookup) and calls `create_status_from_github!`, creating a `Shipit::Status` row on the victim commit with attacker-controlled `state`/`target_url`/`description`/`context`.

## Impact Explanation
This is a payload authenticated by one organization mutating a commit/stack belonging to a different, unrelated organization/repository — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team". A forged `success` status can make a previously blocked commit `deployable?` (since `Commit#deployable?` and `blocked?` depend on `stack.blocking_statuses`/`status` derived from `Status` rows), potentially unblocking a merge or continuous deployment (`schedule_continuous_delivery`/`stack.schedule_merges` are triggered from `add_status`). The attack is repeatable against any known SHA in the entire `commits` table and is not scoped to any relationship between attacker and victim — full cross-tenant blast radius bounded only by SHA knowledge (SHAs are public on GitHub in the vast majority of cases).

## Likelihood Explanation
Preconditions: the Shipit instance must be configured for multi-organization GitHub App webhooks (`secrets.github` has multiple named-org entries with distinct `webhook_secret`s) and the attacker must control one such registered organization (a legitimate, low-privilege setup — e.g., a public/self-serve Shipit deployment covering multiple GitHub orgs). If the instance uses the single-org legacy schema, `github_default_organization` is `nil` and every event is verified against one shared secret regardless of `repository_owner`, which is a different but related exposure not scoped by this question. Attacker cost is low: sign one HTTP request with a secret they legitimately possess, and know a target SHA (trivially obtainable from public GitHub or a fork). Fully repeatable per request against any commit.

## Recommendation
`StatusHandler#process` (and other handlers using bare `Commit.where(sha: ...)`/similar lookups) must scope commit lookup by the repository/organization derived from the verified payload, e.g. restrict to commits whose `stack.repository.owner` matches `repository_owner`/`params.dig('repository','full_name')`, or join through `Stack`/`Repository` and filter by `full_name` before applying the status. Do not rely solely on signature verification of an arbitrary attacker-supplied `repository_owner` field without binding it to the specific commit's actual repository ownership.

## Proof of Concept
Minitest plan (no live GitHub, using existing webhook test helpers):
1. Configure `Shipit.secrets.github` (or stub `Shipit.github_app_config`) with two orgs: `victim-org` and `attacker-org`, each with distinct `webhook_secret`s.
2. Create a `Stack` owned by `victim-org` with a `Commit` `victim_commit` having a known `sha`.
3. Build a `status` webhook payload: `{ "sha" => victim_commit.sha, "state" => "success", "repository" => { "owner" => { "login" => "attacker-org" } } }`.
4. Compute `X-Hub-Signature` using `attacker-org`'s `webhook_secret`.
5. POST to `/webhooks` with `X-Github-Event: status` and this signature.
6. Assert response is `200 OK` (signature accepted).
7. Assert `victim_commit.reload.statuses.last.state == "success"` — i.e., a `Shipit::Status` was created on the victim's commit despite the payload only being authenticated as `attacker-org`, proving `repository_owner (attacker-org) != stack.organization (victim-org)` yet the write succeeded.
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
