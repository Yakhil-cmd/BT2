## Title
Malicious asset definer can freeze an AA's asset balance by revoking attestation of the payout address - (File: `validation.js`, `aa_composer.js`)

### Summary
In ocore, an asset can be created with `spender_attested: true`, which requires every author and output address in a payment of that asset to be on the asset definer's attestor list, and the definer alone can update that list at any time by publishing an `asset_attestors` message. This is functionally identical to a token issuer maintaining an admin-controlled blocklist (e.g. USDC/USDT): if the definer removes an address from the attestor list, all transfers to/from that address are rejected. If an AA holds or is expected to pay out such an asset to a specific recipient, the definer can revoke that recipient's attestation, causing every AA response that tries to pay the asset to that address to bounce permanently, with the asset balance stuck in the AA.

### Finding Description
When an asset has `spender_attested=true`, `validatePayment`/`validatePaymentInputsAndOutputs` require that every author and output address of a payment message using that asset be present in the definer's latest attestor list, checked via `storage.filterAttestedAddresses` and `objAsset.arrAttestedAddresses`: [1](#0-0) [2](#0-1) 

The attestor list can only be modified by the asset definer, single-authored, at any time after the asset already exists and has been distributed: [3](#0-2) 

`aa_composer.js`'s `sendUnit`/`completePaymentPayload` logic, which composes and validates outgoing AA payments of non-base assets, does not pre-check whether the destination address is currently attested before consuming AA-owned outputs and building the unit; it relies entirely on `validateAndSaveUnit` to catch the problem after construction: [4](#0-3) [5](#0-4) 

If validation fails (e.g. "some output addresses are not attested"), the whole AA response is bounced and reverted via `bounce(err)`/`revert`, which rolls back to the savepoint and leaves the AA's balance of that asset intact but unspendable to that address: [6](#0-5) 

Because nothing in the AA composer or validation path provides a fallback (e.g. skip this recipient, refund differently, or otherwise recover), a definer who revokes attestation for a specific payout address after the AA has already accepted/committed to paying that asset can make the AA's outgoing payment fail indefinitely, exactly mirroring the reported USDC/USDT blocklist bug class where a privileged token controller can trap funds already resident in a smart contract.

### Impact Explanation
Any AA that accepts a `spender_attested` custom asset (e.g. an escrow, DEX, vault, or payout AA) is exposed: once the asset definer decides to remove a legitimate recipient address from the attestor list (whether maliciously or due to a compromised definer key), the AA can never complete the payment to that address. Because the AA transaction is bounced and rolled back rather than completed, the asset remains stranded in the AA's balance with no built-in recovery path, resulting in a permanent freeze of AA funds — squarely within the "AA fund loss or freezing" impact category.

### Likelihood Explanation
This requires the asset in question to have been created with `spender_attested: true` and for the AA design to trust and hold that asset for payout to end users, and it requires the definer to act adversarially (or be compromised) post-issuance. Since `spender_attested` and attestor-list updates are unrestricted, standard, documented features controlled solely by the definer address, this is straightforward for a malicious or compromised asset issuer to trigger, and it directly targets AAs that don't specifically vet or restrict which non-base assets they accept and pay out.

### Recommendation
AAs that plan to pay out non-base assets should validate/whitelist accepted assets and avoid unconditionally trusting `spender_attested`/`transfer_condition`-gated assets from third-party definers for critical payout logic. At the protocol layer, consider giving AA authors visibility (e.g. a getter/state variable) into whether the destination address is currently attested/eligible for a given asset before consuming outputs, and/or provide an explicit mechanism (analogous to a try/catch or skip) so an AA can detect a failed conditional transfer and take an alternate action (e.g. mark the claim as unresolved and allow a different recipient) rather than permanently reverting with the balance trapped.

### Proof of Concept
1. Asset definer `D` creates asset `A` with `spender_attested: true` and an initial attestor list including address `U`.
2. AA `P` (e.g. a payout/escrow AA) is designed to receive asset `A` and later pay it to whichever address triggers the payout, e.g. `U`.
3. `U` deposits asset `A` into `P`, and `P`'s bookkeeping records that `U` is owed a payout of asset `A`.
4. `D` publishes an `asset_attestors` message removing `U` from the attestor list (`validateAttestorListUpdate`, `validation.js:2829-2848`).
5. When `P`'s trigger logic attempts to pay `U`, `aa_composer.js`'s `sendUnit` builds the payment (`aa_composer.js:1323-1344`), but `validateAndSaveUnit` rejects it because `U` is no longer attested (`validation.js:2630-2641`), causing `bounce(err)`/`revert` (`aa_composer.js:1759-1783`).
6. `P`'s state is rolled back to before the payment attempt; the asset balance remains locked in `P` and can never be delivered to `U` as long as `D` keeps `U` off the attestor list, with no alternate recovery path in the AA logic.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");

			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
