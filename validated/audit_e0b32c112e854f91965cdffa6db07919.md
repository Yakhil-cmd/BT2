### Title
Fail-Open PreToolUse Security Hook: Any Rule-Engine Error Silently Disables All Configured Command/File Blocking - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
The Connext report describes a single point of failure where an external dependency's error propagates and breaks the entire safety-relevant code path (denial of service). The closest analog in this codebase is the inverse failure mode with a worse security consequence: in the `hookify` plugin's `PreToolUse` hook, any exception raised while loading or evaluating user-defined blocking rules is caught and the hook unconditionally allows the tool call to proceed, rather than failing safe.

### Finding Description
`plugins/hookify/hooks/pretooluse.py` is registered as a `PreToolUse` hook that is meant to block dangerous `Bash`/`Write`/`Edit`/`MultiEdit` operations based on user-authored rule files (`.claude/hookify.*.local.md`). The `main()` function wraps rule loading and evaluation in a broad `try/except Exception`, and its `finally` block always exits with code `0`: [1](#0-0) 

The comment is explicit about the design intent: "ALWAYS exit 0 - never block operations due to hook errors." This means that if `load_rules()` or `RuleEngine.evaluate_rules()` raises for any reason not otherwise caught internally, or if the two-stage rule-file parser (`extract_frontmatter` / `Rule.from_dict`) mis-parses a `conditions` block and silently produces an empty or malformed rule set, the hook emits no `hookSpecificOutput.permissionDecision: "deny"` and the tool call executes unchecked.

Supporting the failure surface: `load_rules()` and `load_rule_file()` in `plugins/hookify/core/config_loader.py` already swallow `IOError`/`OSError`/`ValueError`/`KeyError`/`AttributeError`/`TypeError`/`UnicodeDecodeError`/generic `Exception` per-file and simply skip that file with a stderr warning rather than surfacing the failure to the caller: [2](#0-1) [3](#0-2) 

The hand-rolled YAML-like frontmatter parser in `extract_frontmatter` is fragile (custom indentation/list/dict state machine) and can easily produce a `Rule` with empty `conditions`, which `RuleEngine._rule_matches` treats as "never matches": [4](#0-3) 

So there are two independent points where a rule file that fails to parse correctly (a bad indentation, unexpected character, or unicode issue in a `.claude/hookify.*.local.md` file) results in the corresponding blocking rule silently never firing, and the outer `pretooluse.py` handler additionally guarantees exit 0 (allow) on any unhandled error in the whole pipeline.

### Impact Explanation
`hookify` exists specifically to let a user define command/file guardrails (e.g., block `rm -rf`, block writes to `.env`, block credential leakage patterns) that are meant to constrain what the Claude Code agent can execute. If any error occurs anywhere in the rule-loading/evaluation pipeline — a malformed rule file (which could be introduced by any process with write access to `.claude/`, including the agent itself during a session, or corrupted during editing), an import failure, or an unhandled exception in the custom parser — the hook fails open and the dangerous `Bash`/`Write`/`Edit` operation the user believed was blocked executes anyway with no warning of the failure reaching the permission decision. Because Claude Code hooks run non-interactively and the agent (an LLM with tool-use capability) is the actor being constrained, this is a "hook bypass" of a command-approval mechanism: a single parsing bug or file corruption converts every configured guardrail into a no-op simultaneously, i.e., the single-point-of-failure pattern from the report, but manifesting as silent unauthorized action instead of DoS.

### Likelihood Explanation
This is a documented, intentional behavior (not a randomly-triggered crash), so it fires deterministically whenever the custom frontmatter parser mis-handles a rule file's YAML-like syntax or any other exception occurs in `load_rules`/`evaluate_rules`. Given the parser is a hand-written state machine (not a real YAML parser) handling nested lists/dicts with indentation-sensitive logic, malformed or unusual `conditions:` blocks are plausible in normal authoring, and the agent itself has read/write access to `.claude/` files in many workflows, making it realistic for a rule file to become malformed mid-session. However, this plugin is an opt-in, user-installed extension (not part of the core CLI permission engine), which somewhat limits blast radius to users who have adopted `hookify` for security enforcement.

### Recommendation
Change the fail-open default to fail-closed for blocking-intent rules: if `load_rules()` returns an error state (as opposed to "no files present"), or if `evaluate_rules()` raises, the `PreToolUse` hook should return a `deny`/`ask` decision (or at minimum surface a clear `systemMessage` warning that rule evaluation failed) rather than silently exiting 0. Additionally, replace the custom indentation-based frontmatter parser with a real YAML parser (e.g., `yaml.safe_load`) so malformed `conditions` blocks raise a clear, catchable parse error instead of silently producing an empty/no-op rule.

### Proof of Concept
1. Install the `hookify` plugin and add a blocking rule, e.g. `.claude/hookify.bash-block.local.md`:
```
---
name: block-rm
enabled: true
event: bash
action: block
conditions:
  - field: command
    operator: regex_match
    pattern: "rm -rf"
---
Blocked: dangerous rm command.
```
2. Introduce a subtle malformation that the hand-rolled parser mis-handles (e.g., mixing tabs/spaces in the `conditions:` list item continuation, or adding an unexpected colon inside the `pattern` value) so that `extract_frontmatter` fails to populate `conditions` correctly, or causes `Condition.from_dict`/`Rule.from_dict` to raise `AttributeError`/`TypeError`.
3. Run a `Bash` tool call containing `rm -rf /some/path`.
4. Observe: `load_rule_file` catches the exception, prints a warning to stderr, and returns `None` for that file (dropping the rule entirely) — or `pretooluse.py`'s outer `except Exception` catches any other failure — and in both cases `main()` reaches its `finally: sys.exit(0)` with no `permissionDecision: deny` emitted, so the `rm -rf` command executes without the configured block firing, contrary to the user's expectation that the guardrail is enforced. I was not able to execute this end-to-end in a live Claude Code session to confirm the exact hook-runner behavior on hook script failure versus non-matching output, since that requires the full Claude Code hook dispatcher which is not present in the indexed portion of this repository.

```python
def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
```
