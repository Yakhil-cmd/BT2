This confirms the vulnerability path: creating a `success` `Status` on a commit directly triggers continuous deployment (`test/models/commits_test.rb:233-243`), and `StatusHandler` binds a webhook-carried `state`/`sha` payload to *any* `Commit` matching that `sha`, globally, without scoping to the repository/organization that the webhook signature actually authenticated.### Title
Cross-organization Status webhook spoofing triggers unauthorized deploy on an unrelated Stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController` authenticates a webhook by HMAC-verifying the raw payload against the secret configured for the *organization named in that same payload's `repository.owner.login`* [1](#0-0) . However, `StatusHandler#process` (the code that actually writes state) never re-checks that binding: it looks up the target `Commit` purely by `sha`, across the entire `commits` table, regardless of which repository/organization the record belongs to [2](#0-1) . Every other handler (`PushHandler`, `CheckSuiteHandler`, all `PullRequest::*Handler`s) scopes its writes through `Repository.from_github_repo_name(repository_name)` first [3](#0-2) [4](#0-3) , but `StatusHandler` is the exception.

### Finding Description
The equality that should hold is: `organization that authenticated the webhook signature == organization that owns the Commit being mutated`. Concretely:

- Before: `Shipit.github(organization: repository_owner)` verifies the signature using the secret belonging to the org named in `payload['repository']['owner']['login']` [1](#0-0) .
- After: `StatusHandler#process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1)  — it never filters by `repository`/`stack`, only by `sha`.

Because Git commit SHAs are content-addressed and identical across forks/mirrors that share history, any repository (owned by an unprivileged attacker who has push/webhook-triggering rights on their own repo) that shares a commit SHA with a repository tracked by a Shipit `Stack` can send a legitimately-signed `status` event for its own repository, with `state: success` and the shared `sha`. GitHub will sign this event with the attacker's own organization's webhook secret — a signature Shipit will correctly verify (per its own organization) — yet the payload lands on the wrong `Commit` because the handler is not scoped to the authenticated repository/organization.

### Impact Explanation
`Commit#create_status_from_github!` → `add_status` creates a `Status`, and once the commit's `state` becomes `success`, `Commit#schedule_continuous_delivery` is invoked (via `after_commit` on the new `Status` and via the commit callback chain) [5](#0-4) [6](#0-5) . If the victim stack has `continuous_deployment` enabled, this enqueues `ContinuousDeliveryJob`, which — if the stack is not occupied/locked and within schedule — calls `stack.trigger_continuous_delivery` and deploys the commit [7](#0-6) [8](#0-7) . This is confirmed directly by the existing test showing that creating a `success` status on a commit triggers a real `Deploy` for a CD-enabled stack [9](#0-8) . An attacker with zero Shipit credentials and no access to the victim's GitHub repository can thus cause an **unauthorized deploy** of the victim's stack — matching the "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Requires: (1) the attacker controls (or can trigger webhooks for) a GitHub repository whose commit history shares at least one SHA with a repository tracked as a Shipit `Stack` (trivially achievable via a public fork, since forks always share ancestor commit SHAs with the upstream — and the upstream is very often exactly what's deployed via Shipit), and (2) that stack has `continuous_deployment` enabled and is not locked/occupied at the time. Both preconditions are common in real-world Shipit deployments where the tracked repository is public and forkable. No signing-secret compromise, no Shipit session, and no privileged account are required — the attacker relies entirely on their own repository's genuine, correctly-signed webhook traffic.

### Recommendation
Scope `StatusHandler` the same way every other handler does: resolve the `Repository` via `Repository.from_github_repo_name(repository_name)` (already provided by the base `Handler` class) and restrict the `Commit` lookup to `stacks`/that repository's commits (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent scoped query) instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
1. Attacker owns/forks public repo `attacker/evil`, which shares an ancestor commit `abc123...` with `victim/app` (tracked by a Shipit `Stack` with `continuous_deployment: true`).
2. Attacker pushes/triggers a GitHub `status` event on `attacker/evil` for commit `abc123...` with `state: "success"`. GitHub signs this payload with `attacker/evil`'s own configured webhook secret.
3. `WebhooksController#verify_signature` resolves `Shipit.github(organization: 'attacker')` and correctly verifies the signature against that org's secret [1](#0-0) ; the request is accepted.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `victim/app` commit `abc123...` (unrelated to the authenticated org), and calls `create_status_from_github!` on it [2](#0-1) .
5. The new `success` status flips the commit's deployable state, `schedule_continuous_delivery` fires, `ContinuousDeliveryJob` runs, and `victim/app`'s stack is deployed without any authorization from `victim`'s organization or a Shipit account.
