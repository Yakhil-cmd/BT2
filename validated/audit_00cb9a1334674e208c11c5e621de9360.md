Confirmed root cause: the webhook signature is verified using an HMAC computed with the webhook secret selected for `repository_owner` — the `login` extracted from `payload.dig('repository','owner','login')` (or `organization.login`) — while the actual repository acted on by every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `MembershipHandler`) is `payload.dig('repository', 'full_name')`, a **separate, unrelated field of the same JSON body**. Both fields sit inside the one payload that is HMAC-signed as a whole, but Shipit only cross-checks the signature against the organization derived from `owner.login`; it never asserts that `full_name`'s owner matches that same organization before dispatching to handlers. ### Title
Webhook signature is validated against `repository.owner.login`, but handlers act on the independent `repository.full_name` field — organization authenticated ≠ repository written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify the HMAC using `repository_owner`, which is read from `params.dig('repository','owner','login')` (falling back to `organization.login`). Once the signature check passes, the full raw JSON `params` are handed unmodified to every registered handler (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), and each handler's `stacks` scope is derived from `payload.dig('repository', 'full_name')` — a field that is never compared to `repository.owner.login` used for authentication.

### Finding Description
Because a single Shipit engine instance is configured (in `config/secrets.yml`) with per-organization webhook secrets (`Shipit.github(organization:)` / `github_app_config`), a member of Organization A who legitimately owns a repository/app installation there can generate a validly-signed webhook payload for that organization (or is able to trigger a push to a repo they control that they name/report as belonging to `owner.login: "org-a"`), while setting `repository.full_name` to `"org-b/private-repo"` — a repository owned by a *different* organization also configured on the same Shipit instance. `verify_signature` only checks `Shipit.github(organization: "org-a").verify_webhook_signature(sig, raw_post)`, which succeeds because it was in fact HMAC'd with org-a's secret. Nothing re-derives the secret from, or cross-validates against, `full_name`'s owner before `PushHandler`/`StatusHandler`/`CheckSuiteHandler` resolve `Repository.from_github_repo_name(repository_name)` and enqueue a `sync_github`, create a commit status, or refresh check runs for `org-b/private-repo`'s stacks — a stack the attacker was never authorized to touch. This is the same class of bug as the reported issue: a security-critical check (`afterWithdrawChecks` / here, the organization-repository binding) is scoped to only part of the data the check should cover, letting the unchecked branch (a mismatched `full_name`) slip through.

### Impact Explanation
This lets an attacker who only controls one organization's webhook (its own repos/app installation) forge push/status/check_suite events against stacks belonging to a repository under a completely different organization hosted on the same Shipit instance, causing unauthorized `sync_github` triggers, forged commit statuses, or forged check-run refreshes that can unblock or influence deploy gating for a repository the attacker never had access to — a cross-repository write into an unrelated, unauthorized stack.

### Likelihood Explanation
Requires the deployment to configure more than one GitHub organization (`github_organizations`/`github_app_config`) in a single Shipit instance and requires the attacker to control (or be able to author) a webhook delivery/app installation for at least one of those organizations — a realistic multi-tenant Shipit configuration, and no additional Shipit credentials, sessions, or tokens are needed.

### Recommendation
After `verify_signature` succeeds, re-derive the organization from `payload.dig('repository','full_name')` (or `payload.dig('repository','owner','login')` matched against `full_name`'s owner segment) and reject the webhook (`head(422)`) if they diverge, ensuring the same organization is used both to select the verification secret and to resolve the target repository/stacks.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` and `org-b`, each with its own `webhook_secret` in `secrets.yml`.
2. Attacker is a legitimate GitHub App/webhook sender for `org-a` and knows `org-a`'s webhook secret (or can trigger a real GitHub event from an `org-a` repo).
3. Attacker crafts (or triggers) a `push` payload where `repository.owner.login == "org-a"` but `repository.full_name == "org-b/private-repo"`, and signs the raw body with `org-a`'s secret.
4. `POST /github/webhooks` → `verify_signature` computes `Shipit.github(organization: "org-a").verify_webhook_signature(sig, raw_post)` → passes.
5. `PushHandler.call(params)` resolves `Repository.from_github_repo_name("org-b/private-repo")` and calls `stack.sync_github(expected_head_sha: params.after)` on stacks belonging to `org-b`, which the attacker never had legitimate write access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
