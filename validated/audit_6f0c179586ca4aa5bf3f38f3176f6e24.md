### Title
Attacker-controlled unbounded submodule recursion in `configureWorktree()` causes persistent sync denial - (File: main.go)

### Summary
`repoSync.configureWorktree()` unconditionally invokes `git submodule update --init --recursive` on every synced commit, with no limit on the number or depth of submodules being recursed into. Since the submodule tree is entirely defined by the content of the untrusted upstream repository (`.gitmodules` and nested `.gitmodules` files, which any party able to push a commit or ref that git-sync fetches controls), an attacker can craft a commit containing an unbounded/very large chain or fan-out of submodules, causing this step to consume excessive time and resources on every sync attempt.

### Finding Description
`configureWorktree` runs after every new checkout: [1](#0-0) 

The submodule initialization is driven purely by `git.submodules` (`recursive` by default) and the content pulled from `--repo`: [2](#0-1) 

There is no limit on the number of submodules, no limit on recursion depth, and no cap on total transfer size beyond `--depth` (which only bounds commit history depth, not submodule count/fan-out). This is directly analogous to the `SurplusGuildMinter.getReward()` bug: an unbounded loop (there, over all gauges; here, over all submodules recursively) whose bound is controlled by untrusted/attacker-influenced state (there, `GuildToken` gauge registrations; here, the fetched repo's `.gitmodules` tree), executed on every routine operation (`stake`/`unstake`/`getReward` there; every `SyncRepo` pass here).

`SyncRepo` calls `configureWorktree` as part of every sync pass whenever the hash changes: [3](#0-2) 

The whole pass is nominally bounded by `--sync-timeout` (default 120s), but that only turns "unbounded work" into "guaranteed failure/timeout on every attempt" rather than eliminating the DoS — it converts to a persistent inability to complete a sync (repeated timeout failures), which is one of the explicitly accepted impacts (persistent sync denial).

### Impact Explanation
If an upstream repository that git-sync is configured to follow (which need not be trusted/controlled by the git-sync operator — e.g. a shared/forked repo, a repo where the attacker has push access to a branch/PR ref being synced, or a compromised upstream dependency) contains a commit with a very large number of submodules or deeply nested submodule chains, every `git-sync` sync attempt against that ref will:
- Consume excessive CPU/network/time cloning and recursively initializing all submodules, or
- Exceed `--sync-timeout` and fail repeatedly, incrementing `max-failures` until git-sync gives up (persistent sync denial of the sidecar), or
- Consume unbounded disk space (each submodule clone stored under `.git/modules`), potentially exhausting the volume shared with the application container.

This matches the accepted impact category "persistent sync denial" from the rules.

### Likelihood Explanation
Likelihood is comparable to the original finding: it requires an attacker to control content in the synced repository (e.g., push access to a tracked branch, an accepted PR/ref, or a compromised dependency/submodule maintainer) — this is a realistic, low-privilege threat model for a CI/sidecar tool like git-sync that often syncs branches or PR refs from less-trusted contributors, unlike the ECG report where a governance quorum was needed. `--submodules` defaults to `"recursive"`, so no special configuration is required to be vulnerable; the default configuration is affected as soon as `--repo` content includes many/deep submodules.

### Recommendation
- Add explicit configuration limits, e.g. `--submodules-max-count` / `--submodules-max-depth`, and refuse or fail fast when the `.gitmodules` tree exceeds them, rather than blindly running `git submodule update --init --recursive`.
- Consider defaulting `--submodules` to a safer mode (e.g., `shallow`, non-recursive) for untrusted repos, and clearly document the DoS/resource-exhaustion risk of `recursive` mode in the README's submodules section.
- Enforce a submodule-specific timeout distinct from `--sync-timeout`, and surface clear metrics/logging distinguishing "submodule update taking too long" from generic sync timeout, so operators can detect and mitigate before disk/CPU exhaustion.
- Optionally allow filtering which submodule paths/URLs are permitted (allow-list) to prevent recursion into arbitrary attacker-added submodules.

### Proof of Concept
1. Set up an upstream repo and, in it, add hundreds/thousands of submodule entries in `.gitmodules` (or a chain of submodules each containing another submodule, nested arbitrarily deep), each pointing to a trivial repo.
2. Commit this to the branch/ref that `git-sync` is configured to follow (default `--submodules=recursive`).
3. Run `git-sync --repo=<upstream> --root=<root> --link=link` (defaults, no `--submodules=off`).
4. Observe that `configureWorktree`'s `git submodule update --init --recursive` step (main.go:1733-1747) takes an amount of time proportional to the number/depth of submodules, and with a sufficiently large tree the sync either takes excessive time on every period or exceeds `--sync-timeout` (default 120s), causing the sync to fail repeatedly and, once `--max-failures` is exhausted, causing git-sync to exit/abort — a persistent denial of synchronization. This is directly analogous to the PoC in the original report where increasing `numTerms` pushed `getReward()` past the block gas limit, causing permanent failure of an otherwise routine operation.
