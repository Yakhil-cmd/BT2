### Title
Webhook signature is verified against the organization named in `repository.owner.login`, but events are applied to whatever repository/commit the same untrusted payload names elsewhere — allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp` (and thus which HMAC secret) to validate a webhook against using the `repository.owner.login` (or `organization.login`) field taken from the same, still-unauthenticated JSON body. Every downstream event handler, however, resolves the repository/commit it acts on from a *different* field in that body (`repository.full_name`, or in the `status` handler, no repository at all — only a bare `sha`). Nothing enforces that the organization used to select/verify the signature matches the repository the handler subsequently mutates. In a multi-organization Shipit deployment this breaks the equality `organization that authenticated == repository that is written`.

### Finding Description
`verify_signature` in [1](#0-0)  does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
```
where `repository_owner` is read straight from the attacker-controlled JSON body: [2](#0-1) .

`Shipit.github(organization:)` looks up a per-organization `GitHubApp` from `secrets.github`, which the documentation explicitly supports configuring with multiple independent organizations, each with its own (optional) `webhook_secret`: [3](#0-2) . Critically, `GitHubApp#verify_webhook_signature` **returns `true` unconditionally when no `webhook_secret` is configured** for that organization: [4](#0-3) .

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire, still-attacker-controlled* payload to the registered handlers: [5](#0-4) . Handlers resolve the target repository from `payload.dig('repository', 'full_name')` — a field completely independent from `repository.owner.login` used for signature selection: [6](#0-5) . `PushHandler` uses this to find and sync arbitrary stacks: [7](#0-6) . Worse, `StatusHandler` doesn't scope by repository at all — it matches `Commit.where(sha: params.sha)` across the **entire installation** and writes a status for every matching commit, regardless of which org/repo it belongs to: [8](#0-7) .

Because `repository.owner.login` (used to pick/verify the signing secret) and `repository.full_name` / bare `sha` (used by the handlers to decide what to mutate) are two independent fields inside the same unauthenticated body, an attacker who can produce a valid signature for *any one* configured organization — trivially possible if that organization has no `webhook_secret` set, per the fallback shown above, or if the attacker legitimately controls a low-security/test org that is configured alongside a victim org, as the docs' multi-org example illustrates: [9](#0-8)  — can forge events that are executed against a completely different, secured organization's repositories and commits.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in scope. Concretely:
- Forging a `status` webhook lets an unprivileged attacker mark **any commit sha in the entire Shipit instance** (belonging to any stack/repository, not just the attacker's own) with `state: "success"` and an arbitrary `context`, via `commit.create_status_from_github!(params)`. Since deploy/merge gating in Shipit relies on required CI contexts (`ci.require` in `shipit.yml`), this can satisfy CI requirements for a victim stack the attacker has no access to, enabling an **unauthorized deploy**.
- Forging a `push` webhook lets an attacker trigger `GithubSyncJob`/`stack.sync_github` for a victim stack even though the signature was verified against an unrelated organization's (possibly secret-less) app.

This matches the "High"/"Critical" impact classes: escalation into deploy/merge gating and an unauthorized deploy, achieved purely through crafting a webhook payload with mismatched `repository.owner.login` vs `repository.full_name`/`sha` — no session, `ApiClient` token, or repository write access required.

### Likelihood Explanation
Any Shipit deployment configured with multiple GitHub organizations (a documented, supported configuration) is affected as soon as at least one configured organization has no `webhook_secret` set (also a documented/default state — the example config ships with `webhook_secret: # nil`). Even without a secret-less org, an attacker who has legitimate access to any one configured org's `webhook_secret` (e.g., a low-trust org onboarded to the same Shipit instance) can forge events for every other org on that instance. No additional authentication, session, or GitHub write access is required — only the ability to POST to the public `/webhooks` endpoint.

### Recommendation
Bind the verified signer identity to the entity being mutated:
- After signature verification, re-derive `repository_owner`/organization strictly from the same field used to select the verifying `GitHubApp`, and reject the request if `repository.full_name`'s owner segment (or the commit's actual repository, resolved server-side) does not match the organization that produced a valid signature.
- For `StatusHandler`, scope commit lookup to stacks belonging to the verified organization instead of a bare, cross-tenant `Commit.where(sha:)`.
- Do not allow `verify_webhook_signature` to silently return `true` for organizations with no configured secret in a multi-org setup, or require an explicit opt-in flag acknowledging the tenant is intentionally unauthenticated.

### Proof of Concept
Assume a Shipit instance configured with two orgs, per the documented multi-app schema: `victim-org` (has a `webhook_secret`) and `low-security-org` (has `webhook_secret: nil`, e.g. a sandbox/test org onboarded by anyone with less scrutiny).

1. Attacker crafts a `status` webhook body:
```json
{
  "sha": "<sha of a commit in victim-org/victim-repo required for deploy gating>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "low-security-org" }, "full_name": "low-security-org/whatever" }
}
```
2. Attacker sends `POST /webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature` (or any signature, since `low-security-org` has no secret).
3. `verify_signature` computes `Shipit.github(organization: "low-security-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) — request passes.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and applies a `success` status to the matching commit(s) in `victim-org/victim-repo`, regardless of the fact that the signature was verified for `low-security-org`, satisfying that stack's CI gating and enabling deploy/merge.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
