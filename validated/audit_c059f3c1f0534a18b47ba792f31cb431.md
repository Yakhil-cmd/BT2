### Title
Missing minimum-amount enforcement in `verify-l1-lockups`/`validate-l1-lockup` allows crediting sBTC bond registration with insufficient locked value - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`validate-l1-lockup` (used by `verify-l1-lockups`) validates that each supplied Bitcoin UTXO belongs to the correct timelock script, has not been double-counted, and is confirmed via a valid Merkle proof and block header [1](#0-0) . However, nowhere in this fold function, nor in `verify-l1-lockups` itself, is the summed `sats` amount checked against any required minimum for the bond/staker before it is accepted and returned as the credited amount [2](#0-1) . This is directly analogous to the SyncSwapper report: just as the swap accepted any `amountOutMin` (including zero) without protecting against value degradation, this function accepts any positive-or-zero `sum` of validated L1 lockups without asserting it meets the bond's `allowlist`/`maxSats` or any minimum stx-value ratio requirement inside this path itself.

### Finding Description
`verify-l1-lockups` walks the caller-supplied list of Bitcoin outputs, verifies each is a legitimately confirmed, correctly-scripted, non-duplicate lockup UTXO, and returns the `sum` of the `amount` fields as the credited sats [3](#0-2) . The per-output checks in `validate-l1-lockup` cover unlock height, script correctness, amount-matches-output, duplicate outpoints, block header validity, and Merkle proof [1](#0-0) . None of these assertions bound the *aggregate* `sum` from below — a staker could supply lockups totalling an arbitrarily small (even zero, with an empty `outputs` list) amount of sats and still receive a successful `(ok sum)` result from this function, since the fold starts from `sum: u0` and there is no final `asserts!` comparing `sum` to a required minimum [4](#0-3) .

I was unable to fully trace the caller (`register-for-bond`) within the given tool budget — the tool call for `register-for-bond` in `pox-5.clar` did not return content before the session ended, so I cannot confirm with certainty whether the caller of `verify-l1-lockups` re-validates the returned `sum` against `allowlist`'s `maxSats` or the bond's `minUstxRatio` elsewhere in the contract. The tests I did find (`pox-5.test.ts`) show `allowlist: [{ maxSats: ..., staker: ... }]` being configured per bond and used in flows alongside `registerForBond`, suggesting a cap-check may exist upstream, but I found no explicit lower-bound (minimum sats) check anywhere in the `verify-l1-lockups`/`validate-l1-lockup` path itself [3](#0-2) .

### Impact Explanation
If the aggregate minimum is not enforced downstream either, a staker could register for a bond and receive signer/reward shares proportional to a `sum` far below what the bond's economics assume (e.g., far below `minUstxRatio` sats-backing), diluting or double-counting reward-share accounting relative to actually-locked BTC value — a variant of "sats credited by an L1 proof that were never sufficiently locked on Bitcoin" per the rules' impact categories. If such a downstream minimum check does exist, this specific function would not itself be exploitable, and this finding would only apply if that check is missing or bypassable.

### Likelihood Explanation
Likelihood depends entirely on whether a minimum-sats/ratio check exists in the caller (`register-for-bond`) and is applied to the value returned by `verify-l1-lockups`. Because I could not retrieve that caller's code in this session, I cannot assert with confidence that this is exploitable end-to-end — this is a **gap in my verification** rather than a confirmed unprotected path.

### Recommendation
Add an explicit minimum-sats assertion inside `verify-l1-lockups` (or immediately after its call site) requiring `(>= sum required-minimum-sats)`, mirroring the "introduce a dedicated minimum acceptable value" recommendation from the analogous SyncSwap report, so the credited L1-locked amount can never fall below what the bond configuration expects regardless of how many/few outputs the caller supplies.

### Proof of Concept
Not fully constructible without confirming `register-for-bond`'s downstream checks; a Devin session with full file access to `pox-5.clar`'s `register-for-bond` function (and any `pox-5-auth-proxy.clar` logic) is recommended to confirm whether `sum` returned by `verify-l1-lockups` is bound-checked, and if not, to build a PoC registering a bond with an `outputs` list summing to `u0` or a trivially small amount.

;; Verify l1 lockup information for a staker. This asserts that each lockup
;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)
