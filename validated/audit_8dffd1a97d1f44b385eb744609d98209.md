### Title
Global `removeAllListeners(key)` corrupts other pending private-payment waiters' state, stalling private-payment confirmation for a paired device / counterparty - ([File: wallet.js])

### Summary
The ALSA bug is a wait-list corruption caused by improperly scoped removal of a waiter's entry from a shared list under concurrency: one waiter's cleanup path can remove/orphan another (unrelated) waiter's entry from the shared queue, corrupting state for both. The analogous pattern in ocore is `handlePrivatePaymentChains()` in `wallet.js`, which registers per-chain `eventBus.once(key, ...)` "waiters" keyed only by the deterministic content hash of the private payment (`private_payment_validated-<unit>-<payload_hash>-<output_index>`), and on error calls `eventBus.removeAllListeners(key)` — a **global, unscoped removal** that deletes every listener registered for that key, not just the caller's own listener.

### Finding Description
In `wallet.js`, `handlePrivatePaymentChains()` builds a per-invocation map `assocValidatedByKey` and for every chain whose underlying unit content is not yet locally known, registers a waiter: [1](#0-0) 
```
ifQueued: function(){
    eventBus.once(key, function(bValid){
        if (!bValid)
            return cancelAllKeys();
        assocValidatedByKey[key] = true;
        ...
    });
    cb();
}
```
`cancelAllKeys()` is defined as: [2](#0-1) 
```
var cancelAllKeys = function(){
    for (var key in assocValidatedByKey)
        eventBus.removeAllListeners(key);
};
```
`key` is derived only from `objHeadPrivateElement.unit`, the hash of the payload, and `output_index` — i.e., it is *content-addressed*, not scoped to the particular `handlePrivatePaymentChains()` invocation or sender. The same underlying private payment chain can legitimately be delivered/processed concurrently more than once before the de-dup cache (`handledChainsCache`, keyed by the hash of the *entire* `arrChains` array) is populated — e.g. sent twice in quick succession by a paired device/counterparty, or received both directly and via forwarding (`forwardPrivateChainsToOtherMembersOfOutputAddresses` / `forwardPrivateChainsToOtherMembersOfSharedAddresses` in `arbiter_contract.js`/`wallet.js`), each spawning its own `assocValidatedByKey`/listener set on the exact same `key`.

When two concurrent invocations both register `eventBus.once(key, ...)` for the same content, and *one* of them encounters an unrelated validation error elsewhere in its own `arrChains` array, its `cancelAllKeys()` calls `eventBus.removeAllListeners(key)` for every key it tracked — including the key shared with the other, still-legitimate, concurrent invocation. This is the direct structural analog of the kernel bug: a waiter cleanup routine, operating on a shared/global list keyed only by content rather than by the specific waiter instance, removes an entry that does not belong to it, corrupting the wait state for the other party.

The corresponding notifier side lives in `network.js`, which emits this exact key once validation completes: [3](#0-2) 

### Impact Explanation
The unrelated, legitimate invocation's `eventBus.once(key, ...)` listener is silently removed. When the real validation result is later emitted on that `key` (`network.js` line ~2488/2496), that invocation never receives it: `assocValidatedByKey[key]` for it stays `false` forever, so `checkIfAllValidated()` never completes and `'all_private_payments_handled'` / `'all_private_payments_handled-<unit>'` are never emitted for that call. Any caller awaiting that event (e.g. `handlePrivatePaymentFile` in `wallet.js`, used for textcoin/file-based private payment claims) hangs indefinitely, and the private payment can be left stuck in `unhandled_private_payments`/never surfaces to the recipient wallet, i.e. an availability/fund-visibility issue reachable by an ordinary private-payment counterparty or paired device, without needing a malicious hub, peer, or node.

### Likelihood Explanation
Triggering the race requires only that the same private-payment chain content be submitted to `handlePrivatePaymentChains()` twice concurrently (duplicate device message, retried send, or dual delivery via direct + forwarded paths) while at least one of the two batches also contains another chain that fails validation, causing that batch's `cancelAllKeys()` to fire before the de-dup cache is populated. This is plausible under normal but imperfect network/device conditions (retransmission, near-simultaneous forwarding) and does not require any privileged or malicious actor — a legitimate paired device or private-payment counterparty resending a message is sufficient.

### Recommendation
Scope waiter registration/removal to the specific invocation instead of operating on the shared `eventBus` key globally: e.g., track the specific listener function reference returned/created per call and use `eventBus.removeListener(key, thisListenerFn)` instead of `eventBus.removeAllListeners(key)`, or namespace the `once` key per invocation (e.g., include a per-call nonce) while still allowing the emitter to broadcast a shared completion event to all waiters.

### Proof of Concept
1. Device A sends the same `private_payment` chains payload (`body.chains`) to the hub/local wallet twice in rapid succession (e.g. due to a retry on a slow ACK), invoking `handlePrivatePaymentChains()` twice before `handledChainsCache[cache_key]` is set.
2. Suppose invocation #1's `arrChains` batch contains an additional (unrelated) chain that fails validation via `ifValidationError`/`ifError`; `async.eachSeries`'s final callback runs `cancelAllKeys()`, which iterates invocation #1's own `assocValidatedByKey` and calls `eventBus.removeAllListeners(key)` for the shared content key.
3. Because `key` is content-addressed (not scoped to invocation #2), invocation #2's `eventBus.once(key, ...)` listener registered at `wallet.js:1052` is also destroyed.
4. When `network.js` later emits that `key` on successful/failed validation of the underlying payment (`network.js:2488`/`2496`), invocation #2 never gets notified; its `checkIfAllValidated()` never completes and any caller awaiting `'all_private_payments_handled-<unit>'` (e.g. `handlePrivatePaymentFile`) hangs indefinitely, and `callbacks.ifOk()`/completion notification for that legitimate private payment is lost.
