### Title
Attacker-controlled repository content can force `os.Exit(1)` via killed git subprocess during `--sync-timeout`, causing persistent sync denial - (File: main.go, pkg/cmd/cmd.go)

### Summary
`git-sync` fetches and materializes an attacker-influenced remote repository (including submodules) inside a bounded `context.WithTimeout(ctx, *flSyncTimeout)` window [1](#0-0) . Every git invocation for that sync attempt, including `worktree add` and `submodule update --init [--recursive]`, runs via `exec.CommandContext(ctx, ...)` [2](#0-1)  which SIGKILLs the child process the instant the shared deadline expires, regardless of which git operation is mid-flight [3](#0-2) [4](#0-3) . If the attacker controls repository content (e.g., a large/slow submodule tree), they can calibrate the work required so it reliably exceeds `--sync-timeout`, producing a deterministic failure. Because the default `--max-failures` is `0` ("any sync failure will terminate git-sync") [5](#0-4) , this single, attacker-triggered failure causes `os.Exit(1)` in the main sync loop [6](#0-5) , which is directly analogous to the Nouns Builder bug where an external, resource-bounded call (`token.mint()`) is deliberately driven to fail so that the surrounding catch-handler triggers an unintended, persistent halt (`_pause()`).

### Finding Description
The main sync loop wraps `git.SyncRepo` in a per-iteration timeout and treats any error as a "failure," incrementing `failCount` and exiting the process once `failCount >= maxFails` [7](#0-6) . `SyncRepo` performs several git subprocess calls sequentially — fetch, `worktree add` [8](#0-7) , and `configureWorktree`'s `reset --hard` and `submodule update --init [--recursive]` [9](#0-8)  — all sharing the same `ctx` deadline. `runWithStdin` uses `exec.CommandContext`, which kills the underlying process (default via `os/exec`'s `cmd.Cancel`/SIGKILL semantics) as soon as the context is done, and explicitly surfaces this as an error when `ctx.Err() == context.DeadlineExceeded` [10](#0-9) . Because the repository content being fetched/checked out is fully attacker-controlled (an attacker with push access to the synced remote, or one who can get git-sync pointed at a malicious ref), the attacker can size a submodule tree, blob, or deep history precisely so that a specific step in `configureWorktree` or `createWorktree` exceeds the remainder of `--sync-timeout`. This is the direct analog of the Solidity finding: an untrusted, resource-bounded external operation (`token.mint()` / `git submodule update`) is deliberately driven into a failure path whose only intended purpose was to handle *transient* failures, but whose real effect — combined with the default policy (`_pause()` / `os.Exit(1)`) — is an attacker-triggered halt.

### Impact Explanation
With the documented default of `--max-failures=0`, a single successfully-induced timeout is sufficient to terminate the git-sync process (`os.Exit(1)`) [11](#0-10) . In a Kubernetes sidecar deployment this manifests as a crash/restart loop of the git-sync container as long as the malicious content (or the ref pointing to it) remains reachable, which is a persistent sync denial matching the "impact" bar in the Validate section (persistent sync denial). Because worktree creation and removal are not atomic with respect to SIGKILL (`createWorktree` even has a documented comment about "wedge cases where the worktree was created but this function error'd without cleaning up") [12](#0-11) , a killed subprocess can also leave partially-initialized worktree/lock state that fails `sanityCheckRepo`'s lock-file check on the next attempt [13](#0-12) , compounding the denial across restarts.

### Likelihood Explanation
This requires: (1) the attacker to control or influence the content being synced (push access to the tracked branch/tag, or a submodule under attacker control), and (2) `--sync-timeout` to be tight enough relative to achievable operation cost (analogous to the "20 tokens minted" precondition in the original report — non-trivial but demonstrably achievable, since submodule/checkout cost scales with attacker-chosen repository size). Given the default `--max-failures=0`, no repeated/precise calibration across multiple attempts is even needed — a single sync that exceeds `--sync-timeout` is sufficient. This mirrors the judge's assessment in the original report: the precondition is non-trivial but the mechanism and impact (denial-of-service) are real and deterministic once achieved.

### Recommendation
- Do not treat a single `context.DeadlineExceeded` on a slow-but-legitimate operation (fetch, submodule update, worktree add) the same as a hard content/auth error for the purposes of the failure counter, or bound per-subcommand timeouts independently rather than sharing one deadline across the entire multi-step `SyncRepo` sequence.
- Avoid defaulting `--max-failures` to `0`; require an explicit opt-in to "fail fast on any single error," or treat timeout-class errors specially with their own retry budget.
- Ensure any subprocess killed by context cancellation triggers deterministic cleanup (remove partial worktrees/lock files) before the next sanity check, so a single killed operation cannot permanently wedge the repo state.

### Proof of Concept
1. Attacker with push access adds a very large/slow git submodule (or deeply nested recursive submodules) to the tracked branch that git-sync follows.
2. Operator runs git-sync with default `--max-failures=0` and a `--sync-timeout` sized for normal operation (e.g., the documented default of `10s`/typical values) and `--submodules=recursive`.
3. On the next poll, `SyncRepo` detects the change and calls `createWorktree` then `configureWorktree`, which runs `git submodule update --init --recursive` [4](#0-3) ; because the submodule content is attacker-sized to exceed the remaining context deadline, `exec.CommandContext` kills the subprocess and `runWithStdin` returns a `context.DeadlineExceeded`-wrapped error [10](#0-9) .
4. Back in the main loop, `failCount` becomes `1`, which is `>= maxFails (0)`, so `os.Exit(1)` is called [6](#0-5) , terminating git-sync (and, in Kubernetes, restarting the container, which repeats the same failure indefinitely as long as the malicious ref is targeted).

func hasGitLockFile(gitRoot absPath) (string, error) {
	gitLockFiles := []string{"shallow.lock"}
	for _, lockFile := range gitLockFiles {
		lockFilePath := gitRoot.Join(".git", lockFile).String()
		_, err := os.Stat(lockFilePath)
		if err == nil {
			return lockFilePath, nil
		} else if !errors.Is(err, os.ErrNotExist) {
			return lockFilePath, err
		}
	}
	return "", nil
}

// sanityCheckRepo tries to make sure that the repo dir is a valid git repository.
func (git *repoSync) sanityCheckRepo(ctx context.Context) bool {
	git.log.V(3).Info("sanity-checking git repo", "repo", git.root)
	// If it is empty, we are done.
	if empty, err := dirIsEmpty(git.root); err != nil {
		git.log.Error(err, "can't list repo directory", "path", git.root)
		return false
	} else if empty {
		git.log.V(3).Info("repo directory is empty", "path", git.root)
		return false
	}

	// Check that this is actually the root of the repo.
	if root, _, err := git.Run(ctx, git.root, "rev-parse", "--show-toplevel"); err != nil {
		git.log.Error(err, "can't get repo toplevel", "path", git.root)
		return false
	} else {
		root = strings.TrimSpace(root)
		if root != git.root.String() {
			git.log.Error(nil, "repo directory is under another repo", "path", git.root, "parent", root)
			return false
		}
	}

	// Consistency-check the repo.  Don't use --verbose because it can be
	// REALLY verbose.
	if _, _, err := git.Run(ctx, git.root, "fsck", "--no-progress", "--connectivity-only"); err != nil {
		git.log.Error(err, "repo fsck failed", "path", git.root)
		return false
	}

	// Check if the repository contains an unreleased lock file. This can happen if
	// a previous git invocation crashed.
	if lockFile, err := hasGitLockFile(git.root); err != nil {
		git.log.Error(err, "error calling stat on file", "path", lockFile)
		return false
	} else if len(lockFile) > 0 {
		git.log.Error(nil, "repo contains lock file", "path", lockFile)
		return false
	}

	return true
}

func runWithStdin(ctx context.Context, log logintf, cwd string, env []string, stdin, command string, args ...string) (string, string, error) {
	cmdStr := cmdForLog(command, args...)
	log.V(5).Info("running command", "cwd", cwd, "cmd", cmdStr)

	cmd := exec.CommandContext(ctx, command, args...)
	if cwd != "" {
		cmd.Dir = cwd
	}
	if len(env) != 0 {
		cmd.Env = env
	}
	outbuf := bytes.NewBuffer(nil)
	errbuf := bytes.NewBuffer(nil)
	cmd.Stdout = outbuf
	cmd.Stderr = errbuf
	cmd.Stdin = bytes.NewBufferString(stdin)

	start := time.Now()
	err := cmd.Run()
	wallTime := time.Since(start)
	stdout := strings.TrimSpace(outbuf.String())
	stderr := strings.TrimSpace(errbuf.String())
	if ctx.Err() == context.DeadlineExceeded {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, ctx.Err(), stdout, stderr)
	}
	if err != nil {
		return stdout, stderr, fmt.Errorf("Run(%s): %w: { stdout: %q, stderr: %q }", cmdStr, err, stdout, stderr)
	}
