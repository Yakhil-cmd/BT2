### Title
Interest accrual integer overflow permanently bricks a saturated market - (File: common/src/rates/index.rs)

### Summary
A user can open a debt position whose scaled RAY balance is close to `i128::MAX`. On the next accrual, `calculate_supplier_rewards` multiplies that balance by an increased `borrow_index`; the result no longer fits in `i128`, so the market panics before committing a new timestamp. Because every state-changing pool leg accrues first, the same panic blocks repayment, withdrawal, liquidation, further borrowing, supply, cleanup, and `update_indexes` for that `(hub_id, asset)` market. [1](#0-0) [2](#0-1) 

### Finding Description
The controller exposes permissionless, authenticated `borrow` and `update_indexes` paths. Borrowing calls `pool_borrow_call`, which reaches `borrow::mint_debt`; debt shares are minted as `Ray::from_asset(amount).div_ceil(borrow_index)` and added to market `borrowed`. [3](#0-2) [4](#0-3) [5](#0-4) 

On the next market operation, `ops::load_leg` calls `synced_market`, which calls `interest::global_sync`. `global_sync` invokes `accrue_step`, which first updates `borrow_index` and then computes `new_total_debt = borrowed.mul(new_borrow_index)`. `Ray::mul` uses checked fixed-point multiplication and panics with `MathOverflow` if the resulting RAY value exceeds `i128`. [6](#0-5) [7](#0-6) [8](#0-7) 

The borrow index cap does not prevent this condition: `update_borrow_index` caps the index at `10^36` RAY, but it does not ensure that `borrowed * borrow_index` remains representable. The panic occurs before `cache.mark_accrued()` or `cache.commit()`, so `last_timestamp` remains in the past and every subsequent operation repeats the overflowing accrual. [9](#0-8) [10](#0-9) 

### Impact Explanation
This is a permanent freezing-of-funds condition for the affected market. Normal withdrawals call `pool_withdraw_call`, repayments call `pool_repay_call`, liquidation withdrawals and bad-debt settlement call the same synced pool paths, and every one loads an interest-synced cache before mutating. Once `borrowed * new_borrow_index` overflows, none of those calls can commit state, including calls intended to reduce the oversized debt. [11](#0-10) [12](#0-11) [13](#0-12) [14](#0-13) 

Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot retire the bad position, and keepers cannot advance the market indexes. The attacker also cannot recover their position, but the market and other users' funds are frozen permanently.

### Likelihood Explanation
Likelihood is bounded by capital and market configuration, but it does not require privileged access or an invalid parameter. A market can admit exposure up to the protocol's asset-to-RAY domain, approximately `i128::MAX / 10^(27 - decimals)` base units. A borrower who can provide sufficient collateral and liquidity can mint scaled debt near `i128::MAX` while `borrow_index` is still near `RAY`; even minimal later index growth makes `borrowed * borrow_index` exceed `i128`. [5](#0-4) [4](#0-3) 

This is best rated Medium: the impact is a permanent market shutdown and freezing of user funds, but reaching the numerical boundary requires a very large position and sufficient configured caps, collateral, and pool liquidity.

### Recommendation
Enforce a stricter representability bound on every debt and supply share total: require `scaled_amount * MAX_BORROW_INDEX_RAY <= i128::MAX` for debt and `supplied * MAX_SUPPLY_INDEX_RAY <= i128::MAX` for supply, rather than only checking that the initial asset-to-RAY conversion fits. The cap checks should use saturating or widened intermediate arithmetic and reject entries that can overflow under the maximum index.

For defense in depth, accrual should also handle the saturated-value state deterministically—for example by clamping index growth before the overflowing product or using widened arithmetic for market totals—so a boundary position cannot poison `global_sync` and block repayment or cleanup.

### Proof of Concept
```rust
// Assumptions:
// - debt_asset market has nonzero utilization and its configured borrow cap
//   admits amount_near_ray_domain_max.
// - Attacker supplies enough collateral to satisfy health checks.

let debt = HubAssetKey {
    hub_id,
    asset: debt_asset.clone(),
};

// 1. Open a maximal admitted debt position.
controller.borrow(
    attacker,
    account_id,
    vec![&env, (debt.clone(), amount_near_ray_domain_max)],
    None,
);

// 2. Wait until the ledger timestamp advances by at least 1 ms.
// 3. Anyone can trigger the overflow through the permissionless keeper path.
controller.update_indexes(
    keeper,
    vec![&env, debt.clone()],
);
// Reverts with MathOverflow inside:
// calculate_supplier_rewards -> borrowed.mul(new_borrow_index).

// 4. Recovery attempts all hit the same accrual before repayment:
controller.repay(payer, account_id, vec![&env, (debt.clone(), i128::MAX)]);
controller.update_indexes(keeper, vec![&env, debt]);
// Both revert before `last_timestamp` or `borrowed` can be changed.
```

The poisoned state is permanent because the accrual panic precedes both `cache.mark_accrued()` and `cache.commit()`. [2](#0-1) [10](#0-9)

    env: &Env,
    params: &MarketParams,
    borrowed: Ray,
    new_borrow_index: Ray,
    old_borrow_index: Ray,
) -> (Ray, Ray) {
    let old_total_debt = borrowed.mul(env, old_borrow_index);
    let new_total_debt = borrowed.mul(env, new_borrow_index);

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

    cache.credit_cash(net_repay);
