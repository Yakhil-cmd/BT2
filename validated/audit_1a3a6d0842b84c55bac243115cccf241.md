### Title
Webhook signature is verified against an organization chosen from unauthenticated payload fields, not the repository the event actually writes to - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App / `webhook_secret` to validate the incoming HMAC against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, then checks the signature of the *entire* raw body against that secret. [1](#0-0)  The signature only proves "whoever sent this owns the secret for the organization named in the payload" — it never proves that every other repository/commit field inside that same payload actually belongs to that organization. Downstream event handlers (e.g. the `status` handler) trust those other fields directly to create/update `Status` records on arbitrary stacks. [2](#0-1) 

### Finding Description
Shipit supports hosting multiple GitHub organizations/Apps in one deployment, each with its own independent `webhook_secret`. [3](#0-2)  `verify_webhook_signature` is a pure HMAC-over-raw-body check that says nothing about which repository the payload describes — it only proves the sender knows the secret configured for whichever org `repository_owner` resolves to:
```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [4](#0-3) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  ...
``` [5](#0-4) 
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [6](#0-5) 

The intended binding is:
`organization_whose_secret_signed_the_request == organization_that_owns_the_repository_the_event_mutates`

But the check only enforces:
`organization_named_in_payload.owner.login == organization_whose_secret_signed_the_request`

Nothing ties the `repository.owner.login`/`organization.login` field used for secret *selection* to the repository/commit fields the handler actually acts on further down in the same body (e.g. `repository.full_name`, `sha`, `state`, `context`, `target_url` used by the `status` handler to create a `Status`). Because these are all attacker-controlled fields inside a single JSON body that the attacker signs themselves (with their own legitimate, low-privilege org's secret), the attacker can put one org's login in `repository.owner.login`/`organization.login` (to pass signature selection) while pointing the rest of the payload at a completely different, victim organization's repository/stack.

This is the analog of the audit's root cause: fields that are read and acted upon are not the same fields that are actually covered/verified by the authenticating check — here it's "organization authenticated" vs. "repository that gets written," exactly the pattern the rules flag as valid.

### Impact Explanation
An attacker who controls (or is a member of) their own organization/GitHub App installation registered in the same multi-tenant Shipit instance possesses that org's genuine `webhook_secret` and can produce a validly-signed webhook body. By setting the commit/repository identifiers in the body to reference a *different, victim* organization's stack, they can, for example, forge a `status` webhook that creates a `Status` (state, context, target_url, description) attached to an arbitrary commit in the victim's repository/stack. [2](#0-1)  Forged "success" statuses can satisfy required/blocking statuses used by Shipit's merge queue and deploy gating, resulting in an unauthorized deploy or merge on a repository the attacker has no legitimate access to — a cross-organization/cross-repository write and an unauthorized deploy.

### Likelihood Explanation
This requires only that the Shipit instance is configured for more than one GitHub organization (a documented, supported configuration) and that the attacker legitimately controls one of those low-privileged orgs (e.g. via their own GitHub App installation and its webhook secret). No repository write access, GitHub token, or Shipit session on the victim org is required — only knowledge of one's own org's webhook secret, which any org admin possesses. The only gate is `verify_signature`, and it never cross-checks that the org used for signature selection matches the repository being mutated inside the same payload.

### Recommendation
After signature verification succeeds for `repository_owner`, re-validate that every repository/commit-owning field the specific handler will act on (`repository.full_name`, `organization.login`, etc.) belongs to that same verified organization before dispatching to `Shipit::Webhooks.for_event`. Reject the event (422) if there is any mismatch between the organization whose secret validated the signature and the organization that owns the repository referenced elsewhere in the payload.

### Proof of Concept
1. Attacker administers `attacker-org`, a GitHub organization/App installed on the shared Shipit instance, and thus knows `attacker-org`'s `webhook_secret`.
2. Attacker crafts a JSON body for the `status` event:
```json
{
  "sha": "<victim-org/private-repo commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://ci.example.com/fake",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/private-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` resolves `repository_owner` to `attacker-org` from `repository.owner.login`, fetches `attacker-org`'s `GithubApp`, and the HMAC validates successfully because it's the attacker's own valid secret over their own crafted body. [1](#0-0) 
5. The `status` handler proceeds to create/update a `Status` record for the commit in `victim-org/private-repo`, exactly as shown in the existing test that demonstrates a `Status` being created purely from payload fields merged with `repository_params`. [2](#0-1) 
6. If this forged status is one of the stack's required/blocking statuses, it can unblock deploys or the merge queue for `victim-org/private-repo`, an organization the attacker never authenticated against.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

      )

      Rails.logger.info([
