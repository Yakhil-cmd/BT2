### Title
Unbounded storage of unvalidated private-payment chains sent by a paired device leads to Denial of Service via `unhandled_private_payments` flooding - (File: `network.js`, `wallet.js`)

### Summary
The reported SignalK bug is a classic "attacker-controlled queue with no size/rate limits, pruned too infrequently" DoS: unauthenticated POSTs are pushed into an in-memory `requests` object with no cap, and pruning happens only once every 15 minutes. The closest reachable analog in `ocore` is the private-payment-chain relay path: any **paired device** (or a private-payment counterparty communicating over the wallet chat/hub channel) can send arbitrarily many `private_payments` chat messages, each containing multiple, arbitrarily long private-payment "chains", which are persisted verbatim to the `unhandled_private_payments` table with no limit on count, chain length, or aggregate size, and are only garbage-collected once a day (and only on full nodes, not light nodes).

### Finding Description
`wallet.js:handlePrivatePaymentChains()` accepts `body.chains` from a message received through `handleMessageFromHub()` [1](#0-0) . The only validation performed is structural (non-empty arrays/objects, required string/array fields) — there is no cap on:
- the number of chains in `arrChains`,
- the length of each chain (`c.length`),
- the size of `inputs`/`outputs` arrays inside each chain element.

The message envelope itself is checked with `isTooDeeplyNestedOrHasTooManyNodes(json, 20, 100000)` [2](#0-1) , which bounds a *single* message to 100000 nodes, but nothing bounds how many such messages an attacker can send, nor how quickly.

Each chain is handed to `network.handleOnlinePrivatePayment()`, which — for private elements that are not immediately known/validatable (the common outcome for light clients, or any element still waiting on its parent chain) — calls `savePrivatePayment()`, which `JSON.stringify()`s the entire (attacker-supplied) `arrPrivateElements` array and `INSERT`s it as a `LONGTEXT`/`TEXT` blob into `unhandled_private_payments`, keyed only by `(unit, message_index, output_index)` [3](#0-2) . This mirrors the SignalK flaw almost exactly: attacker-controlled JSON blobs are stored unconditionally, with no size limit and no count limit per sender.

Cleanup of this table is extremely infrequent and narrow in scope: `cleanBadSavedPrivatePayments()` only deletes rows whose referenced `unit` never showed up in the `units` table **after 1 day**, and it only runs for full nodes (`if (conf.bLight || bCatchingUp) return;`) [4](#0-3) . This is analogous to SignalK's 15-minute `pruneRequests` interval being "too infrequent" — except here it is a full day, and light-node hubs/wallets never prune at all. An attacker only needs to reference plausible-looking but never-broadcast unit hashes (`unit` is only checked for being a 44-byte base64 string, not that it actually exists yet — `ifNew` and `ifKnownUnverified` paths both call `savePrivatePayment`) [5](#0-4) .

Additionally, `wallet.js` keeps its own dedup cache `handledChainsCache`, keyed by a hash of the entire `arrChains` payload, which only grows (cleared hourly by `setInterval`) and does not deduplicate across different attacker-chosen `arrChains` values, so it provides no real protection against a flooding attacker who varies the payload slightly each time [6](#0-5) .

### Impact Explanation
A single paired device (an actor explicitly reachable per this analysis' scope — pairing only requires knowledge of a pairing code/QR, which many wallets/bots hand out to arbitrary users) can repeatedly send `private_payments` messages with large `chains` arrays containing bogus/never-to-be-broadcast unit references. Each such message:
1. Bypasses meaningful validation (only structural checks),
2. Is fully JSON-stringified and stored to disk in `unhandled_private_payments` (and briefly held as parsed JS objects in memory during processing/forwarding, e.g., `_.cloneDeep(arrPrivateElements)`, `arrRecipientChains`, `arrCosignerChains`),
3. Persists for up to 24 hours (full node) or forever (light node — `cleanBadSavedPrivatePayments` is `full only`), because the referenced units never appear.

Sustained flooding can grow the `unhandled_private_payments` table (and associated JSON parsing/serialization work on every `handleSavedPrivatePayments` sweep, which does a `CROSS JOIN units` and re-parses every row's JSON) without bound, degrading or crashing the hub/wallet process — a "network unable to confirm new units" condition for that node, consistent with the CWE-400/CWE-770 resource-exhaustion class in the source report.

### Likelihood Explanation
Medium. It requires the attacker to be paired with the victim's wallet or connected as a hub client relaying `private_payments` on behalf of a paired device, which is a lower bar than compromising a witness/full node, and is exactly the "paired device" / "private-payment counterparty" actor this analysis is scoped to accept. No signature or proof-of-funds is required before the payload is persisted (validation happens asynchronously and only after the DB write in the common "waiting for chain" light-client scenario).

### Recommendation
- Enforce hard caps on `arrChains.length`, chain length (`c.length`), and the size of `inputs`/`outputs` arrays in `wallet.js:handlePrivatePaymentChains()` before processing, in addition to the existing node/depth check.
- Enforce a maximum number of outstanding `unhandled_private_payments` rows per sending device/peer, and reject (rather than silently queue) further payments once the cap is hit.
- Shorten and generalize the pruning of `unhandled_private_payments` (run it on light nodes too, and prune much sooner than 24 hours for entries whose referenced unit is implausible/never requested successfully).
- Rate-limit `private_payments`/`private_payment` messages per device address at the wallet/hub layer.

### Proof of Concept
A paired device (or a hub relaying on its behalf) sends repeated `pairing`-authenticated chat messages of the form:
```json
{
  "subject": "private_payments",
  "body": {
    "chains": [ /* N large synthetic chains, each with a fabricated head "unit" (valid-looking base64 hash that will never be broadcast), long inputs/outputs arrays */ ]
  }
}
```
via `handleMessageFromHub()` → `handlePrivatePaymentChains()` → `network.handleOnlinePrivatePayment()` → `savePrivatePayment()`. Each call inserts the full serialized chain into `unhandled_private_payments`; repeating this with fresh fabricated `unit` values on every message causes unbounded growth of the table (and repeated JSON parse/stringify overhead on every subsequent `handleSavedPrivatePayments()` sweep), since the referenced units will never appear and the daily cleanup does not run for light nodes and is a full day away for full nodes.

**Note on confidence:** I was not able to execute this PoC in a live ocore instance from this environment, so the concrete memory/CPU exhaustion magnitude is inferred from the code paths shown above rather than measured; the structural absence of size/count caps on this attacker-reachable path is directly confirmed by the cited code.

function handlePrivatePaymentChains(ws, body, from_address, callbacks){
	var arrChains = body.chains;
	if (!ValidationUtils.isNonemptyArray(arrChains))
		return callbacks.ifError("no chains found");
	if (!arrChains.every(c =>
		isNonemptyArray(c) &&
		c.every(e =>
			isNonemptyObject(e) &&
			isNonemptyString(e.unit) &&
			isNonemptyObject(e.payload) &&
			isNonemptyString(e.payload.asset) &&
			isNonemptyArray(e.payload.inputs) &&
			isNonemptyArray(e.payload.outputs) &&
			e.payload.inputs.every(isNonemptyObject) &&
			e.payload.outputs.every(isNonemptyObject)
		)
	))
		return callbacks.ifError("malformed private chain");

function cleanBadSavedPrivatePayments(){
	if (conf.bLight || bCatchingUp)
		return;
	db.query(
		"SELECT DISTINCT unhandled_private_payments.unit FROM unhandled_private_payments LEFT JOIN units USING(unit) \n\
		WHERE units.unit IS NULL AND unhandled_private_payments.creation_date<"+db.addTime('-1 DAY'),
		function(rows){
			rows.forEach(function(row){
				breadcrumbs.add('deleting bad saved private payment '+row.unit);
				db.query("DELETE FROM unhandled_private_payments WHERE unit=?", [row.unit]);
			});
		}
	);
	
}
