### Title
Cross-repo forged commit status bypasses CD gating regardless of stack lock state - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit(s) for an incoming GitHub `status` webhook using `Commit.where(sha: params.sha)` with no repository scoping, so a `success` status forged by an attacker's own repository can be attached to any `Commit` row sharing that SHA in any stack. Because `Stack#deployable?` and `Commit#deployable?` are two independent, unrelated gates, an unlocked `victim` stack (`lock_reason` nil) offers zero protection against this: the attacker only needs to satisfy the commit-half of the gate, which they can do without any operator action, while the stack-half was already permissive throughout.

### Finding Description
The binding that should hold is: `params.dig('repository','full_name')` (the repository that authenticated/authored the webhook) **==** `commit.stack.repository.full_name` (the repository whose commit is being marked). This equality is never checked.

Path:
- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e. it authenticates that the payload came from *some* app installation for that *organization* — it never checks that the specific `repository.full_name` in the payload matches the repository owning any particular `Commit`/`Stack`.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
No `stack_id`, `repository_id`, or `full_name` filter is applied — any `Commit` row with a matching SHA across the entire Shipit instance, belonging to any stack/repository, will receive the forged status.
- `Commit#create_status_from_github!` → `Status.replicate_from_github!` (app/models/shipit/status.rb:24-33) persists a `success` `Status` row for `victim`'s commit.
- `Commit#deployable?` (app/models/shipit/commit.rb:227-229): `!locked? && (stack.ignore_ci? || (success? && !blocked?))`. Once the forged `success` status is attached, `success?` (delegated to `status`, computed from the injected `Status` rows) becomes true, making `deployable?` true — with zero interaction with `Stack#deployable?`.
- `Commit#schedule_continuous_delivery` (app/models/shipit/commit.rb:281-287): `return unless deployable? && stack.continuous_deployment? && stack.deployable?`. `Stack#deployable?` (app/models/shipit/stack.rb:376-378) only checks `!locked? && !active_task? && !awaiting_provision? && deployment_checks_passed?` — none of these conditions are influenced by, or protective against, a forged commit status. If `victim` stack is simply unlocked/idle (a totally ordinary, common state), this second half of the AND is already `true` before and after the attack, and the lock mechanism never engages.

Existing guards checked and found insufficient: `verify_signature` authenticates the org, not the specific repo/commit binding; `drop_unhandled_event` only filters unregistered event types (status is registered); `ExplicitParameters` schema in `StatusHandler` validates shape (`sha`, `state`, etc.) but not repository ownership; `Stack#locked?`/`lock_reason` is an orthogonal control over deploy scheduling, unrelated to which repository is allowed to post a status for a given SHA.

### Impact Explanation
An attacker who owns/controls any GitHub repository (their own fork or unrelated repo) that shares a commit SHA with a `victim` Shipit stack (e.g., via a shared history, cherry-pick, or an intentionally crafted commit with identical tree/parent/timestamps to produce a SHA collision-adjacent scenario, or more simply any commit the attacker can reference by SHA that also exists in `victim`'s stack — such as a shared base commit merged into both repos) can send a webhook `status` event asserting `state: success` for that SHA. This flips `commit.deployable?` to `true` for `victim`'s commit, and — since ordinary unlocked stacks pass `stack.deployable?` by default — triggers `schedule_continuous_delivery` → `ContinuousDeliveryJob`, which can lead to `victim`'s stack deploying that commit. This is an unauthorized deploy triggered by a payload from a repository that did not authenticate control over `victim`'s repository, matching the Critical category "a payload for one repository mutating another's stack/commit ... or an unauthorized deploy." The `Stack#lock_reason` mechanism provides no compensating control since it is never consulted as part of the commit-status write path, only as part of the (already-passing) deploy-scheduling half.

### Likelihood Explanation
Preconditions: `victim` stack must be unlocked (`lock_reason` nil) and not mid-deploy/awaiting-provision — the ordinary, default operating state of most stacks. The attacker needs no Shipit credentials, session, or GitHub App secret; they only need to know or produce a SHA that is `Commit`-tracked in `victim`'s stack (commonly true for shared base/release commits, cherry-picks, or commits from a common upstream) and be able to trigger a `status` webhook from their own installation (any repo they control, or any public event to which they have publish rights). This is directly repeatable per target SHA and requires no privileged role.

### Recommendation
Scope `StatusHandler#process` (and `CheckRunHandler`, if similarly structured) to commits belonging to the stack(s) whose repository matches the webhook payload's `repository.full_name`/`id`, e.g. filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: repository_from_payload.id })` instead of unscoped `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
test "forged status is applied to victim's commit even though victim stack is unlocked and deployable" do
  victim_stack = shipit_stacks(:shipit)
  victim_stack.update!(lock_reason: nil) # unlocked
  assert victim_stack.deployable?, "victim stack should already be deployable before the attack"

  shared_sha = "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared base commit")
  refute victim_commit.deployable?, "commit starts non-deployable (no success status)"

  # Attacker-controlled webhook payload, authenticated only for the ATTACKER's own org/repo,
  # referencing the shared SHA -- StatusHandler never checks payload['repository']['full_name']
  # against victim_commit.stack.repository.full_name.
  forged_params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: shared_sha, state: "success", context: "ci/attacker"
  )
  Shipit::Webhooks::Handlers::StatusHandler.new(forged_params).process

  victim_commit.reload
  assert victim_commit.deployable?, "victim commit became deployable via forged cross-repo status"
  assert victim_stack.deployable?, "victim stack lock state never changed / was never involved"
end
```
