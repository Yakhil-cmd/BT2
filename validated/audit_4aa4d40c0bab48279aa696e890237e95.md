## Analog Found

### Title
Webhook signature verification binds the wrong organization to the resource being mutated, allowing cross-repository status/stack forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The reported bug is a class of "verified-field vs. acted-upon-field" mismatch: `StabilityPool` verifies/tracks one quantity (`raacToken.balanceOf`) but distributes rewards based on a different, uncontrolled quantity that includes unrelated deposits. The same pattern exists in Shipit's webhook trust chain: the HMAC signature is checked against the GitHub App/organization selected via `repository.owner.login` (or `organization.login`), but the handlers that mutate state select the *target repository/stack* using a **different field of the same untrusted JSON body** — `repository.full_name` — which is never covered by the equality that the signature actually proves.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App config (and therefore which `webhook_secret`) to verify against based on `repository_owner`: [1](#0-0) [2](#0-1) 

This only proves "whoever holds the `webhook_secret` configured for organization X sent this exact byte stream." Shipit explicitly supports **multiple GitHub organizations, each with its own independent `webhook_secret`**: [3](#0-2) [4](#0-3) 

Once the signature passes, every handler resolves the target `Repository`/`Stack` from a **separate, unchecked field of the same payload** — `repository.full_name` — with no assertion that it is consistent with the `repository.owner.login` used for signature selection: [5](#0-4) 

`PushHandler` uses this to sync a stack: [6](#0-5) 

`StatusHandler` is even more directly exploitable: it doesn't consult `repository` at all, it applies a forged CI status to **any** `Commit` matching the attacker-chosen `sha`, globally, regardless of which repository it belongs to: [7](#0-6) 

Because an organization operator with a legitimate (but different) GitHub App installation controls the entire raw request body they sign with their own `webhook_secret`, they can set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` succeeds using their own secret) while setting `repository.full_name` (for push/pull_request handlers) or `sha` (for the status handler) to values belonging to a victim organization's stack. The signature only asserts "signed by org A's secret"; the code then acts as if it was authorized for org B's repository.

### Impact Explanation
This breaks the binding: `organization that authenticated == repository that is written`, which is explicitly the accepted vulnerability class for this engine. Concretely:
- `StatusHandler` lets an attacker (who legitimately controls a webhook secret for *any* configured organization) inject a forged "success" commit status for a victim's commit shared across `Shipit::Commit` records, which feeds `CommitChecks`/deployability gating used to allow a deploy to proceed — an escalation path toward an unauthorized ship.
- `PushHandler`/pull-request handlers let the same attacker trigger `stack.sync_github`, archive/unarchive review stacks, or otherwise mutate a victim organization's `Stack` records that they have no legitimate relationship to, purely by pointing `repository.full_name` at the victim.

This is High severity per the rubric: "escalation into `Shipit.github_teams` authorization" / gating-bypass toward "an unauthorized deploy."

### Likelihood Explanation
Requires only that the deployment configures **more than one GitHub organization** (a documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications"), and that the attacker legitimately controls the webhook secret/App installation for at least one of those organizations (e.g., they are an admin of their own org that is also configured in the same Shipit instance). No GitHub App private key, `api_clients_secret`, or Shipit session is needed — only the ability to sign an arbitrary payload with their own org's `webhook_secret`, which is precisely the credential the multi-tenant design hands out to each org owner.

### Recommendation
After signature verification succeeds for organization `O`, assert that every resource identifier the handler will act on (`repository.full_name`, `repository.owner.login` used inside handlers, and any `sha`/stack lookup) actually belongs to organization `O` before performing any mutation — i.e., verify `Repository#owner`/`full_name` prefix matches `O`, and scope `StatusHandler`'s `Commit.where(sha:)` lookup to commits whose stack's repository belongs to the verified organization.

### Proof of Concept
Conceptual sequence (Shipit configured with `OrgOne` and `OrgTwo`, attacker controls `OrgOne`'s app/webhook secret, `OrgTwo/victim-repo` is a real stack):
1. Attacker builds a JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "full_name": "OrgTwo/victim-repo", "owner": { "login": "OrgOne" } }
}
```
2. Attacker signs it with `OrgOne`'s `webhook_secret` and POSTs to `/github/webhooks` with `X-Github-Event: status`.
3. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and succeeds, because the signature is valid for `OrgOne`'s secret over this exact body.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit in `OrgTwo/victim-repo` — and calls `create_status_from_github!`, forging a green check for a repository the attacker never had signing rights over.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
