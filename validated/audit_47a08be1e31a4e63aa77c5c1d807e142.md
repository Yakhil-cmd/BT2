### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` writes a GitHub commit status to every `Commit` record in the entire database that matches the raw `sha` string from the webhook payload, without ever checking that the commit belongs to the repository whose signature was verified in `WebhooksController#verify_signature`. Because `Commit#stack_id` is set at commit-creation time and is completely independent of which repository sent the current webhook, a `security/scan` `success` status authenticated only for the attacker's own repository can be written onto a `Commit` row that belongs to an unrelated victim `Stack`, feeding `add_status` → `stack.schedule_merges` and `Commit#deployable?`.

### Finding Description
The broken binding is: **`commit.stack.repository` (the repository that must have authenticated this webhook) should equal `repository_owner`/`params['repository']` (the repository whose signature `verify_signature` actually validated)**. In the code, this equality is never checked.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-49) validates the HMAC signature using `Shipit.github(organization: repository_owner)`, i.e. it authenticates that *a* payload came from a specific GitHub organization/repo — it does not scope anything about which `Commit`/`Stack` rows may be touched.
- `StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24) then does:
  ```ruby
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
  ```
  This is a bare, global lookup by `sha` across the whole `commits` table — it never filters by `stack.repository` or by `params['repository']['full_name']`.
- `Commit#create_status_from_github!` → `add_status` (app/models/shipit/commit.rb:165-169, 366-386) writes the new status into `commit.statuses` (scoped to `commit.stack_id`, i.e. the **victim's** stack) and, if the simple state transitions, calls `stack.schedule_merges` when `new_status.success?`, and can flip `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`, commit.rb:227-229).

Exploit flow: an attacker who legitimately controls a repository connected to Shipit (any repo they own that has the Shipit GitHub App/webhook configured — explicitly granted by the threat model as "emit webhooks from a repository they own") can produce a valid, correctly-signed `status` webhook for their own repository. If any `Commit` row in the database — belonging to a *different*, victim `Stack` — happens to have the same `sha` (e.g. a shared ancestor commit from a fork/mirror relationship, or any two repositories that happen to contain an identical git object), `StatusHandler` will apply the attacker's forged `security/scan`/`success` status to the victim's commit. If the victim stack has `merge_queue_enabled` true and requires `security/scan` as part of its deploy spec, this state flip is picked up by `add_status`'s call to `stack.schedule_merges`, which can advance the merge queue and trigger `merge!`/deploy of a commit the victim's own CI/security process never actually approved.

None of the listed guards prevent this: `verify_signature` only authenticates the sender's own organization, not the target of the write; there is no `ExplicitParameters` repository field required or checked; `drop_unhandled_event` only filters by event type; there is no `Repository`/`Stack` scoping, model validation, or `subset`/`url` validator anywhere in this path that ties `Commit.where(sha:)` back to the authenticated repository.

### Impact Explanation
A payload from repository A can mutate `Commit`/`CommitStatus` state belonging to Stack/repository B — exactly the "payload for one repository mutating another's stack, commit, task or team" Critical category. On a `merge_queue_enabled` stack, this can force `stack.schedule_merges`/`merge!` to proceed on a commit whose real CI/security gate was never satisfied by the victim's own repository, resulting in an unauthorized merge/deploy. The blast radius is bounded by SHA coincidence: it requires that a commit object with an identical SHA exist in both the attacker-controlled repo and the victim's Shipit-tracked repo (e.g., fork/mirror/shared-history relationships), which is common in real-world Shipit deployments that track multiple stacks/forks of the same upstream project, but not universal across arbitrary unrelated repositories.

### Likelihood Explanation
Preconditions: (1) attacker owns/controls a repository that is wired into the same Shipit instance and can produce a validly-signed `status` webhook (explicitly granted attacker capability), (2) a target `Stack` exists whose `Commit` table contains a row with the same `sha` as a commit the attacker controls status on (realistic for forks/mirrors of the same codebase, less so for arbitrary unrelated repos), (3) the victim stack has `merge_queue_enabled: true` and requires `security/scan` in its deploy spec. Given those, the attack is a single unauthenticated-relative-to-victim HTTP webhook, fully repeatable against any commit sharing that SHA, at zero cost beyond owning a connected repo.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalently in any other SHA-keyed handler) to commits whose `stack.repository` matches the repository that authenticated the webhook (`params['repository']['full_name']` / `repository_owner`), e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { ... matching owner/name ... })`, rather than a bare global `Commit.where(sha:)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "success status from repository A must not affect stack scoped to repository B" do
  victim_stack = shipit_stacks(:shipit) # merge_queue_enabled: true, requires security/scan
  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)

  before_deployable = victim_commit.deployable?
  before_merge_scheduled = victim_stack.masters_status # or spy on schedule_merges

  # Attacker's repository payload, sha collides with victim_commit.sha,
  # but params['repository'] does NOT match victim_stack.repository
  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'context' => 'security/scan',
    'repository' => { 'full_name' => 'attacker/other-repo', 'owner' => { 'login' => 'attacker' } }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)

  victim_commit.reload
  assert_equal before_deployable, victim_commit.deployable?, "victim commit's deployability must not change from an unrelated repository's webhook"
  # assert stack.schedule_merges was NOT invoked for victim_stack
end
```
Both sides of the binding (`commit.stack.repository` vs the authenticated `params['repository']`) diverge in the current code — the handler applies the status regardless — confirming the vulnerability.
