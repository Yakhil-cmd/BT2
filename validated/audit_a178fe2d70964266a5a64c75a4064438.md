### Title
AA `bounce()` handler discards refunds of all other assets (including NFTs) when just one asset's amount is insufficient for its configured bounce fee - (File: `aa_composer.js`)

### Summary
This bug class mirrors the Connext `Executor.sol` finding: a failure/recovery path that is supposed to safely return sent funds instead silently swallows valuable, unrelated assets because the recovery logic aborts wholesale instead of degrading gracefully per-asset.

### Finding Description
When an AA trigger bounces (fails), `handleTrigger`'s `bounce()` function is responsible for returning the sender's funds, asset by asset, minus any configured `bounce_fees` [2](#0-1) . The function iterates `trigger.outputs` and, for each asset, computes `fee = bounce_fees[asset] || 0`. If `fee > amount` for that asset, it calls `return finish(null)` immediately [3](#0-2) . This aborts the *entire* refund unconditionally — including the `messages` array already built for the base asset and for any other, unrelated assets (e.g., an indivisible/fixed-denomination "NFT-like" asset or a valuable custom token) that had already passed their own fee checks and were queued for a full refund.

The same defect is reachable earlier: before `evaluateAA` even runs, `handleTrigger` iterates `trigger.outputs` and if any single asset's amount is below its configured `bounce_fees[asset]`, it calls `bounce(...)`, whose in-function comment claims the intent is to "ignore silently" the under-funded asset only [4](#0-3) . In practice, calling `bounce()` re-triggers the exact same `fee > amount` branch for that asset inside `bounce()`, which wipes out the whole refund, not just that one asset's portion.

Because `bounce_fees` per non-base asset can be set to any value up to `MAX_CAP` with no sanity bound relative to typical trigger amounts [1](#0-0) , an AA author (intentionally or by misconfiguration) can define a bounce fee for some asset X that is trivially exceeded (e.g., set higher than any single output, or simply configured for an asset the sender didn't intend to interact with at all in that trigger but which was bundled in the same unit as other outputs to the AA address). Any user who, in the same trigger unit, sends both a valuable asset (fully refundable on its own) and any output of asset X below its bounce fee will have the *entire* trigger — including the valuable asset — permanently absorbed into the AA's balance with no refund message and no way to reclaim it, since `updateInitialAABalances` already credited all trigger outputs to the AA's balance before evaluation [5](#0-4) , and once `bounce()` produces zero messages via `finish(null)`, those balances are never sent back.

### Impact Explanation
This results in permanent AA fund loss/freezing for an unprivileged trigger sender: any asset (including private/indivisible/NFT-like assets built on top of `fixed_denominations` assets) sent as part of a trigger unit that also happens to include (even unintentionally, e.g. leftover dust from wallet composition or a bundled data/payment message) an output for any asset whose bounce fee exceeds the sent amount, is trapped irrecoverably in the target AA's balance. There is no mechanism analogous to a per-asset skip; the recovery path is all-or-nothing.

### Likelihood Explanation
The precondition (an AA definition with a `bounce_fees` entry for a non-base asset set higher than realistic trigger amounts, or simply higher than what the sender happens to include) is fully within reach of any AA author and does not require malicious intent from the sender — a legitimate user composing a multi-output trigger, or interacting with an AA the sender doesn't fully understand, can trigger this unintentionally. The base-asset case (line 928 in `bounce()`, mirrored by the pre-check at 1852) is even more directly reachable: if the trigger fails for any unrelated reason (formula bug, business-logic revert) after the sender already provided adequate `bounce_fees.base`, that part still refunds correctly; but the presence of a second asset with `fee > amount` for that asset alone silently voids the whole refund path, an easy-to-hit edge case in composite triggers (e.g., swap/bridge-style AAs receiving both an NFT-like asset and bytes in one unit).

### Recommendation
Change `bounce()` so that failing to meet the bounce fee for one asset only excludes that asset's refund message, rather than discarding the whole `messages` array via `finish(null)`. I.e., inside the `for (var asset in trigger.outputs)` loop, replace `if (fee > amount) return finish(null);` with `if (fee > amount) continue;` (skip only that asset, keep — and eat/lose only — the deficient one), and after the loop, proceed to `sendUnit(messages)` with whatever refundable outputs remain, so unrelated valuable assets sent alongside are not caught in the blast radius of one under-funded asset.

### Proof of Concept
1. An AA author publishes an AA with `bounce_fees: { base: 10000, "<asset_hash_of_X>": 1000000 }` where asset X is some arbitrary/custom asset unrelated to the AA's core logic (or even one the AA never expects), e.g. simply copying a template without realizing the implication, or deliberately to exploit unaware users.
2. A user builds a trigger unit sending: (a) an indivisible/fixed-denomination NFT-like asset Y (amount fully refundable, no bounce fee configured for Y) intended for a legitimate purpose (e.g., depositing into the AA for later use), and (b) a small incidental output of asset X (e.g., dust of amount 1) to the AA address in the same unit — this can happen naturally if the wallet coalesces multiple payment messages, or the sender interacts with an AA whose usage instructions include sending a secondary token they underestimate the required amount for.
3. The AA's business logic fails for any reason relevant to the trigger (formula error, insufficient balance check, `if` condition failing another output/state message), causing `bounce(err)` to be invoked [6](#0-5) .
4. Inside `bounce()`, iterating `trigger.outputs`, when the loop reaches asset X: `fee (1000000) > amount (1)` is true, so `return finish(null)` executes immediately — discarding the messages array that (depending on iteration order) may already contain, or would have contained, the refund of asset Y and the base bytes.
5. Result: asset Y (the valuable NFT-like asset) and the base bytes remain permanently credited to the AA's internal balance (`aa_balances`) with no refund unit ever produced, and no mechanism for the sender to reclaim it — a direct AA fund loss/freezing outcome, analogous to the NFT permanently locked in `Executor.sol`'s failure path.
