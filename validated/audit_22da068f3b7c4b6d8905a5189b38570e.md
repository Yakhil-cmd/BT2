### Title
Unauthenticated arbiter address in `arbiter_contract_offer` allows a malicious counterparty to self-appoint as escrow arbiter and drain the multisig deposit - (File: wallet.js)

### Summary
`ocore`'s arbiter-contract escrow feature (`wallet.js` handling of `arbiter_contract_offer`, and `arbiter_contract.js`'s `deriveSharedAddress`) accepts an `arbiter_address` supplied by the remote counterparty with only address-format validation, and never verifies that this address belongs to a genuine, mutually-trusted ArbStore-registered arbitrator before it is baked into the multisig (shared address) definition that will hold the trade funds. This mirrors the RetoSwap incident, where the attacker impersonated the trusted arbitrator to get their own address accepted as the trade's dispute authority, letting them unilaterally release escrowed funds to themselves.

### Finding Description
When a peer sends an `arbiter_contract_offer` device message, `wallet.js` validates only structural/type properties of `arbiter_address`: [1](#0-0) 

There is no check that `body.arbiter_address` corresponds to a real, previously known/registered arbiter (e.g. cross-checked with `wallet_arbiters` / `arbiters.getInfo`, which fetches `device_pub_key`/`real_name` from an ArbStore). The offeree's client stores the contract and, upon acceptance, derives the shared (multisig) address using exactly this attacker-supplied `arbiter_address`: [2](#0-1) 

The resulting address definition contains an `"in data feed"` branch that lets whoever controls `arbiter_address`'s private key post a data feed unit (`CONTRACT_<hash> = <address>`) that unilaterally authorizes release of the escrowed funds to the named party: [3](#0-2) 

`arbiters.getArbstoreInfo` and `arbiters.getInfo` only fetch cut/fee and display metadata for whatever address is given — they do not perform any authentication of the arbiter's legitimacy or bind it to a directory the victim actually trusts: [4](#0-3) [5](#0-4) 

Because the offeror fully controls the `arbiter_address` field of the contract (and the derived multisig definition is deterministic from it), a malicious counterparty can specify an address they control as "arbiter." The victim's client — like RetoSwap's client trusting a spoofed arbitrator identity before deposit — has no independent verification step that the arbitrator is the intended neutral third party, only that the address is syntactically valid.

### Impact Explanation
If the victim proceeds to fund the shared/multisig address (`createSharedAddressAndPostUnit`), the attacker (posing as their own "arbiter") can post a data feed unit at any time naming themselves as the contract winner, satisfying the `"in data feed"` definition branch and unilaterally spending the escrowed funds without genuine dispute resolution or the counterparty's cooperation. This is direct unauthorized draining of AA/multisig-escrowed funds — concrete unauthorized spending analogous to the ~$2.7M XMR loss in the RetoSwap incident, where a fake arbitrator address let the attacker create a compromised multisig before the victim deposited funds.

### Likelihood Explanation
The attack requires only that the attacker be the offeror in an arbiter-mediated trade (or convince a victim to accept an offer with a spoofed `arbiter_address`) — a normal, unprivileged usage of the P2P trade-offer feature. No hub/network/relay compromise is needed; a single crafted `arbiter_contract_offer` device message suffices, and the receiving wallet has no built-in step forcing confirmation that the arbiter is a recognized ArbStore entity before it becomes cryptographically load-bearing in the funds-holding definition.

### Recommendation
Before accepting an `arbiter_contract_offer` (and definitely before deriving/funding the shared address), require the client to resolve `arbiter_address` against a trusted arbiter directory (e.g. via `arbiters.getInfo`/ArbStore lookup) and surface the arbiter's verified identity/name to the user for explicit confirmation, rejecting offers whose `arbiter_address` cannot be resolved to a known, previously vetted arbiter. Consider also allowing the accepting party to specify/require a particular arbiter rather than blindly accepting whatever the offeror proposes.

### Proof of Concept
1. Attacker generates a fresh address `A` that they control the private key for.
2. Attacker sends an `arbiter_contract_offer` device message to the victim with `arbiter_address = A`, otherwise well-formed (valid `my_address`, `peer_address`, correct `hash`, etc.), per the checks in `wallet.js:617-627`.
3. Victim's client accepts the offer (`arbiter_contract.store` in `wallet.js:650`), later calls `respond`/`createSharedAddressAndPostUnit`, which derives the multisig address embedding `arbiter_address = A` via `deriveSharedAddress` (`arbiter_contract.js:461-481`).
4. Victim deposits/funds the shared multisig address as part of the trade.
5. Attacker, controlling `A`, posts a `data_feed` unit `{"CONTRACT_<hash>": "<attacker_address>"}` from address `A`, satisfying the `"in data feed"` branch in the multisig definition (`arbiter_contract.js:798-814`), and spends the funds to themselves — without any real dispute or the victim's cooperation.

```javascript
function parseWinnerFromUnit(contract, objUnit) {
	if (objUnit.authors[0].address !== contract.arbiter_address) {
		return;
	}
	var key = "CONTRACT_" + contract.hash;
	var winner;
	objUnit.messages.forEach(function(message){
		if (message.app !== "data_feed" || !message.payload || !message.payload[key]) {
			return;
		}
		winner = message.payload[key];
	});
	if (!winner || (winner !== contract.my_address && winner !== contract.peer_address)) {
		return;
	}
	return winner;
}
```

```javascript
function getArbstoreInfo(arbiter_address, cb) {
	if (!cb)
		return new Promise(function(resolve, reject){
			getArbstoreInfo(arbiter_address, function(err, info){
				if (err) return reject(err);
				resolve(info);
			});
		});
	if (arbStoreInfos[arbiter_address]) return cb(null, arbStoreInfos[arbiter_address]);
	device.requestFromHub("hub/get_arbstore_url", arbiter_address, function(err, url){
		if (err) {
			return cb(err);
		}
		if (!validationUtils.isNonemptyString(url))
			return cb("invalid url received from hub");
		requestInfoFromArbStore(url+'/api/get_info', function(err, info){
			if (err)
				return cb(err);
			if (!validationUtils.isNonemptyObject(info))
				return cb("invalid info received from arbstore");
			const cut = parseFloat(info.cut);
			if (!info.address || !validationUtils.isValidAddress(info.address) || isNaN(cut) || cut < 0 || cut >= 1) {
				return cb("malformed info received from ArbStore");
			}
			info.url = url;
			arbStoreInfos[arbiter_address] = info;
			cb(null, info);
		});
	});
}
```
