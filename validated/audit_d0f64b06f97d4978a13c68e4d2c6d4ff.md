### Title
Cross-tenant forged commit status write via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload against the GitHub App/org resolved from `repository_owner` [1](#0-0) , but `StatusHandler#process` never checks that the authenticated org actually owns the commit it mutates — it looks the commit up by raw `sha` alone across the entire database [2](#0-1) . Any org onboarded into Shipit (with its own valid webhook secret) can send a validly-signed `status` event naming a victim commit's SHA belonging to an unrelated org's stack, and `create_status_from_github!` will write a forged status onto that victim `Commit`.

### Finding Description
Binding claimed by the equality: `org(repository_owner)` used in `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:25`) `==` `org(commit.stack)` for every `Commit` matched and mutated by `StatusHandler#process`. Tracing the code shows this equality is **never established or enforced anywhere**:

- `verify_signature` resolves `github_app = Shipit.github(organization: repository_owner)` and only checks that the HMAC of `request.raw_post` matches that org's `webhook_secret`; it proves the *request* was signed by *some* known org, not that the request's *content* (the `sha`) belongs to that org [1](#0-0) .
- `repository_owner` reads `params.dig('repository','owner','login') || params.dig('organization','login')` from the same JSON body used for the HMAC check, so both are attacker-controlled fields of a single, fully attacker-authored payload [3](#0-2) . Since these fields never disagree "by surprise" (the attacker sets them deliberately), the disagreement isn't the actual root cause — the real gap is downstream.
- `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with **no filter by repository, org, or stack** [2](#0-1) . `params.sha` is a free-text string from the schema (`requires :sha, String`) [4](#0-3) , entirely attacker-supplied, and is matched against every `Commit` row in the whole installation regardless of which org's secret signed the request.
- `Commit#create_status_from_github!` unconditionally creates the status via `add_status`/`statuses.replicate_from_github!` for whatever commit was matched [5](#0-4) , which can flip `deployable?` gating for that commit's actual stack [6](#0-5) .

Exploit flow: attacker legitimately owns/administers "Org-A", which is onboarded into the shared Shipit instance with its own valid `webhook_secret` (this is normal SaaS multi-tenancy — the attacker only ever knows Org-A's secret, never a victim's). Attacker crafts a `status` event body with `repository.owner.login` (or `organization.login`) = `"Org-A"` and `sha` = a known/guessable commit SHA belonging to a victim "Org-B" stack (obtainable e.g. from a public repo's commit history), signs it with Org-A's secret, and POSTs to `/webhooks`. `verify_signature` passes (Org-A's secret is valid for Org-A), and `StatusHandler#process` then writes a forged status onto Org-B's commit because the lookup is SHA-only. No guard in the chain — `drop_unhandled_event`, `check_if_ping`, the `ExplicitParameters` schema, or `verify_signature` — checks that the matched `Commit`'s `stack`/repository corresponds to the org that authenticated the request.

### Impact Explanation
A tenant that legitimately controls one org/repo in a multi-tenant Shipit deployment can inject arbitrary CI/CD status records (`success`, `failure`, etc., with attacker-chosen `description`/`target_url`/`context`) onto any commit in any other tenant's stack, as long as they can name that commit's SHA. This directly manipulates `Commit#deployable?`/merge gating for the victim stack [6](#0-5) , satisfying the "payload for one repository mutating another's stack/commit" Critical category. The attack is repeatable against any commit SHA and any number of victim stacks sharing the same Shipit installation.

### Likelihood Explanation
Precondition: the attacker must control at least one org/repo that is legitimately onboarded into the same Shipit instance with its own valid webhook secret (a realistic multi-tenant scenario, not a purely unprivileged internet attacker with zero Shipit relationship). Additionally the attacker needs the target commit's SHA, which is often discoverable via the victim's public GitHub repo. No GitHub App keys, session, or API tokens are needed. Cost is a single crafted, self-signed HTTP POST per forged status, fully repeatable and scriptable.

### Recommendation
In `StatusHandler#process` (and any other webhook handler that mutates `Commit`/`Stack` state by looking up records independent of the authenticated org), scope the lookup by the same repository/org that was used to authenticate the webhook — e.g. join through `Stack` on `repo_owner`/`repo_name` derived from the verified `repository_owner`/`repository.full_name`, instead of a bare `Commit.where(sha: ...)`. Reject or ignore any status/commit update whose owning stack's repository does not match the payload's authenticated repository.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual, no live GitHub)
test "status webhook from Org-A cannot forge a status on a commit belonging to Org-B's stack" do
  org_a_stack = shipit_stacks(:shipit)              # authenticated org for this request
  victim_commit = shipit_commits(:from_other_org)   # belongs to a different repository/stack

  refute_equal org_a_stack, victim_commit.stack      # sanity: distinct tenants

  payload = {
    sha: victim_commit.sha,
    state: 'success',
    context: 'forged',
    repository: { owner: { login: 'org-a' }, full_name: 'org-a/repo' }
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(
      ActiveSupport::HashWithIndifferentAccess.new(payload)
    )
  end
end
```
This test currently fails (the status IS created) because `StatusHandler#process` matches `victim_commit` purely by `sha` without checking it belongs to the org authenticated by `verify_signature`, demonstrating the equality `org(repository_owner) == org(commit.stack)` does not hold and is never enforced.
