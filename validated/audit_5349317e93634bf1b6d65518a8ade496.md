### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login` while the handler dispatches on a different attacker-controlled `repository.full_name`, allowing cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, which is read straight out of the untrusted request body (`params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')`). The actual repository/stack that receives the event is resolved independently, later, from a different field of the same untrusted body (`payload.dig('repository', 'full_name')` in `Handler#repository_name`). Because these two "identity" fields are never bound together or cross-checked, an attacker who legitimately controls one organization in a multi-tenant Shipit deployment (and therefore legitimately knows that organization's `webhook_secret`) can sign a payload as their own org while pointing the payload's `repository.full_name` at a completely different, victim repository/stack.

### Finding Description
Signature verification and event dispatch use two different untrusted fields of the same JSON body, with no cryptographic binding between them:

- Verification looks up the app/secret to check against via `repository_owner`, computed from the payload itself: [1](#0-0) [2](#0-1) 

- `Shipit.github(organization:)` resolves per-organization config/secrets (multi-tenant setups configure a distinct `webhook_secret` per organization, as shown in the fixture): [3](#0-2) 

- Once the signature check passes (because it was checked against the attacker's *own* org's secret, which the attacker legitimately knows), every handler determines which `Stack`/repository to act on from a *different, independently-controlled* field of the same payload: [4](#0-3) 

Nothing ties `repository.owner.login` (used for authentication) to `repository.full_name` (used for the write target). An attacker who owns/administers their own GitHub organization configured in this Shipit instance can craft a raw POST body where `repository.owner.login` = their own org (so the HMAC they compute with their own known `webhook_secret` verifies), but `repository.full_name` = `victim-org/victim-repo`. `verify_signature` accepts it, and the handler then processes the event as if it came from the victim repository — breaking the trust binding "organization that authenticated == repository that is written."

### Impact Explanation
This lets an unprivileged-relative-to-the-victim attacker forge GitHub webhook events for any repository/stack hosted on the same Shipit instance, without ever having credentials, membership, or write access to that victim repository. Concretely:
- Forged `push` events can enqueue `GithubSyncJob` for the victim stack.
- Forged `status`/`check_suite` events can create passing CI statuses/check-runs on arbitrary commits of the victim stack (as exercised in `test/controllers/webhooks_controller_test.rb`'s `:state` and `:check_suite` tests), which feeds directly into `Commit#deployable?` and `Stack#branch_status`/`merge_status`: [5](#0-4) 
- Marking a commit as CI-green can enable an unauthorized deploy/merge of that commit on the victim stack, or corrupt the victim's deploy pipeline state. This constitutes a cross-repository write / unauthorized deploy path, matching the Critical impact bar in scope.

### Likelihood Explanation
Requires only that the attacker administers one organization/repository already configured in the multi-tenant Shipit deployment (a low, "unprivileged relative to the victim" bar — they need no access to the victim's repo, team, or Shipit account) and can craft a raw HTTP POST with a custom body/signature to the shared `/webhooks` endpoint. No GitHub API access, private key, or victim credentials are needed.

### Recommendation
Bind the organization used for signature verification to the same repository identity used for dispatch: derive both from `repository.full_name` (or require they match, rejecting mismatches), and/or resolve the organization from a trusted, non-payload source (e.g., the installation ID from the GitHub webhook headers or a per-installation URL segment) rather than from attacker-supplied JSON fields.

### Proof of Concept
1. Attacker legitimately configures/owns organization `AttackerOrg` in the multi-tenant Shipit config and knows its `webhook_secret`.
2. Attacker crafts a `status` (or `push`/`check_suite`) webhook JSON body:
```json
{
  "repository": { "owner": { "login": "AttackerOrg" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  ...
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(AttackerOrg_webhook_secret, raw_body)` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and validates successfully against the attacker's own secret [6](#0-5) .
5. `Shipit::Webhooks.for_event('status').each { |h| h.call(params) }` processes the payload; the handler resolves the target stack via `repository.full_name` = `victim-org/victim-repo` [7](#0-6)  and creates/updates a passing status on the victim's commit, despite the attacker having no access to `victim-org`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
