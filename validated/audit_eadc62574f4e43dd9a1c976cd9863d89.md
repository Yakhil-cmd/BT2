### Title
`Api::CCMenuController#stack` resolves the target stack from `params[:stack_id]` without scoping to `current_api_client.stack_id`, allowing cross-stack CCXML disclosure - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of using the `stacks` scope defined in `Api::BaseController`, which restricts lookups to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. Because the permission check (`ApiClient#check_permissions!`) only validates that the token carries the `read:stack` string permission and never compares the requested stack's id to `current_api_client.stack_id`, a token minted for stack A can fetch the CCXML deploy status of any other stack B.

### Finding Description
The binding that should hold is: `stack_shown_to_client.id == current_api_client.stack_id` whenever `current_api_client.stack_id?` is true.

- `Api::BaseController#stacks` enforces this binding: [1](#0-0) 
- `Api::CCMenuController#stack` overrides this entirely and never consults `current_api_client.stack_id`: [2](#0-1) 
- The only authorization gate on the action is `require_permission :read, :stack`, which resolves to `ApiClient#check_permissions!("read", "stack")` — a check of the string `"read:stack"` against the client's `permissions` array, with no reference to any particular stack id: [3](#0-2) [4](#0-3) 
- `authenticate_api_client` in `CCMenuController` sets `@current_api_client` from `params[:token]` (any valid client token), then `show` calls `stack.deploys_and_rollbacks.last` and renders the CCXML feed using whatever stack was resolved: [5](#0-4) 

Exploit flow: attacker holds a `token` for an `ApiClient` with `stack_id: A.id` and `permissions: ["read:stack"]`. They issue `GET /api/1/stacks/:B_id/cc.xml?token=<token>`. `authenticate_api_client` finds the client (valid, since the token itself is legitimate for stack A). `require_permission!(:read, :stack)` passes because the client does have `read:stack` in its permission list — this check is scope-name-based, not target-instance-based. `stack` then resolves `Stack.from_param!(params[:stack_id])`, i.e. stack B, unscoped. The CCXML for stack B (branch, latest deploy/rollback status) is rendered and returned to the attacker, who has no legitimate access to stack B.

This differs from every other API resource controller (e.g., `Api::StacksController` and others inheriting `BaseController#stack`), which properly scope through `stacks.from_param!`.

### Impact Explanation
An attacker holding a token scoped to one stack can read the CI/CD status (CCXML: build/deploy state, last deploy outcome, running status) of any other stack in the same Shipit instance, including stacks belonging to different repositories/tenants they have no authorization for. This is repeatable against arbitrary stack ids by simply changing `params[:stack_id]` in the URL, with no rate limiting. This matches the "High - unauthenticated/cross-scope read of stack state" impact category (deploy/task state disclosure across tenant boundaries via a token that should be confined to a single stack).

### Likelihood Explanation
Preconditions: attacker must already possess one valid `ApiClient` token scoped to some stack (`stack_id: A.id`) — this is not a "no credentials" attacker per the strict definition (they need an API token), but critically that token is legitimately scoped only to stack A and grants no rights whatsoever over stack B. No GitHub secrets, session, or elevated privilege is required; only knowledge/possession of one low-privilege scoped token and the target stack's id (guessable/enumerable via `Stack.from_param!`, which typically accepts a numeric id or the repository slug). Cost is a single HTTP GET; fully repeatable.

### Recommendation
Change `Api::CCMenuController#stack` to use the tenant-scoped lookup, mirroring `Api::BaseController#stack`:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This reuses `Api::BaseController#stacks`, which already limits resolution to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped, restoring the intended binding.

### Proof of Concept
Add a minitest to `test/controllers/api/ccmenu_controller_test.rb` (existing file):

```ruby
test "#show does not leak another stack's CCXML to a token scoped to a different stack" do
  stack_a = shipit_stacks(:shipit)          # or any fixture stack A
  stack_b = shipit_stacks(:other)           # a distinct stack B

  scoped_client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-to-a',
    stack_id: stack_a.id,
    permissions: ['read:stack']
  )

  get "/api/1/stacks/#{stack_b.to_param}/cc.xml", params: { token: scoped_client.authentication_token }

  # Binding under test: stack shown to client (from response body) must equal current_api_client.stack_id (stack_a.id)
  # Before fix: request succeeds (200) and body contains stack_b's project name/state -> binding violated.
  assert_response :not_found # or :forbidden, once fixed via `stacks.from_param!`
  assert_no_match(stack_b.to_param, response.body)
end
```

Before the fix, this request returns `200 OK` with stack B's CCXML payload despite the token being scoped to stack A, proving the cross-tenant read. After applying the recommended fix, `stacks.from_param!` raises `ActiveRecord::RecordNotFound` (rendered as 404) because stack B is outside `current_api_client.stack_id`'s scope.
