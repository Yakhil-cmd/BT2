No vulnerability found for this question.

**Rationale:**

The claimed exploit does not hold up. `object::create_named_object` derives the object address deterministically from `(creator_address, seed)` and delegates to `create_object_internal`, which unconditionally asserts `!exists<ObjectCore>(object)` before doing any state mutation via `move_to`: [1](#0-0) . This assertion aborts with `EOBJECT_EXISTS` (`error::already_exists`) whenever a second creation attempt targets an address that already has an `ObjectCore`, with no code path that skips this check. [2](#0-1) 

This is already verified by an existing test in the framework itself, `test_duplicate_collection`, which creates the same collection twice and asserts the second call aborts with `abort_code = 0x80001` at `aptos_framework::object` — exactly the object-already-exists condition the question asks to prove: [3](#0-2) . The formal spec for `create_named_object` also encodes this as an invariant (`aborts_if exists<ObjectCore>(obj_addr)`), reinforcing that duplicate creation at the same derived address is a hard, unconditional abort, not a race or bypassable condition: [4](#0-3) .

Additionally, this scenario is out of scope for the review's admission boundary. The premise of "replaying an already-executed transaction after a chain reorg or resubmission" is a transaction-replay concern that is handled at the mempool/VM sequence-number, chain-id, and expiry validation layer — not at the Move-module object-creation layer. Even if such a replay were attempted, standard sequence-number-based replay protection in the VM/mempool would reject a resubmission of an already-committed transaction before its Move logic ever executes a second time. The `object.move` duplicate-object guard is a defense-in-depth invariant inside application logic, not an admission-boundary component (authenticator, mempool, or vm-validator), so it falls outside the boundary conditions specified for this review (which require the path to start from unprivileged transaction/authenticator/API/proof input impacting sender, signer, sequence, or domain-binding guarantees at admission).

    spec create_named_object(creator: &signer, seed: vector<u8>): ConstructorRef {
        let creator_address = signer::address_of(creator);
        let obj_addr = spec_create_object_address(creator_address, seed);
        aborts_if exists<ObjectCore>(obj_addr);

        ensures exists<ObjectCore>(obj_addr);
        ensures global<ObjectCore>(obj_addr) == ObjectCore {
            guid_creation_num: INIT_GUID_CREATION_NUM + 1,
            owner: creator_address,
            allow_ungated_transfer: true,
            transfer_events: event::EventHandle {
                counter: 0,
                guid: guid::GUID {
                    id: guid::ID {
                        creation_num: INIT_GUID_CREATION_NUM,
                        addr: obj_addr,
                    }
                }
            }
        };
        ensures result == ConstructorRef { self: obj_addr, can_delete: false };
    }
