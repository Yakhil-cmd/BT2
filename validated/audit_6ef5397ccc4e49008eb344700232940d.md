### Title
Webhook signature verification is bound to `repository.owner.login`/`organization.login` while all event handlers act on the independently attacker-controlled `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the `X-Hub-Signature` against using `repository_owner`, which is read straight from the untrusted JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up the corresponding `GitHubApp` (and its `webhook_secret`) for that organization name, and Shipit explicitly supports multiple independent GitHub Apps/organizations sharing the same engine instance: [3](#0-2) 

However, once the signature check passes, `Shipit::Webhooks.for_event(event)` dispatches the *entire raw payload* to handler classes that resolve the actual `Repository`/`Stack` to act on using a completely different field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

The binding that should hold is: `organization authenticated by HMAC == organization owning the repository acted upon`. Because both `repository.owner.login`/`organization.login` (used only for picking the verification secret) and `repository.full_name` (used to find the `Repository`/`Stack` to mutate) are independent, attacker-controlled keys inside the same signed JSON body, an attacker who legitimately knows the `webhook_secret` for **one** configured organization (e.g., an org they administer, in a multi-org Shipit deployment as documented in `docs/setup.md`) can forge a signature that is valid for *that* org while pointing `repository.full_name` at a *different* org's repository/stack.

Concretely, `PushHandler#process` (and, by the same `Handler#repository_name` mechanism, `StatusHandler`/`CheckSuiteHandler`) look up stacks via `Repository.from_github_repo_name(repository_name)` where `repository_name = payload.dig('repository', 'full_name')`, then trigger `stack.sync_github(expected_head_sha: params.after)` / commit-status/check-run mutations against that stack — all keyed off a field never covered by the org used to compute the signature.

### Impact Explanation
Once past `verify_signature` (using a secret the attacker legitimately possesses for their own org), the attacker fully controls the JSON body, including `repository.full_name`. This lets them:
- Trigger `GithubSyncJob` for an arbitrary victim `Stack` with an attacker-chosen `expected_head_sha`, forcing the engine to fetch and append commits reachable from that SHA on the *victim's real* GitHub repo via the victim's real `github_api` credentials (`PushHandler` → `Handler#stacks` → `stack.sync_github`).
- Forge `status`/`check_suite` events for the victim repository/commit (same `repository.full_name`-based lookup pattern shared by all `Handler` subclasses), which can flip commit deployability state used to gate deploys/continuous delivery.

This breaks the "organization that authenticated == repository that is written" binding and can escalate to state changes (unauthorized commit ingestion, forged CI/check status, and potentially enabling an unauthorized deploy through continuous delivery relying on forged deployable status) on a repository/organization the attacker does not control — matching the High-impact class ("escalation into authorization boundaries" / "unauthorized deploy").

### Likelihood Explanation
Requires the attacker to legitimately possess a `webhook_secret` for any single organization configured in this Shipit instance (e.g., their own org, in the documented multi-org configuration, `docs/setup.md` "Using Multiple Github Applications"). No access to the victim org, its secret, or any Shipit session/API token is needed. Likelihood is higher in the common single-org deployments too, since `webhook_secret` is documented as optional (`nil` by default in `config/secrets.development.example.yml`), in which case `verify_webhook_signature` returns `true` unconditionally regardless of the body.

### Recommendation
Bind the verified organization to the repository actually processed: derive `repository_name`/the org used by handlers from the same value validated during signature verification (or, at minimum, verify that `repository.full_name`'s owner segment equals the `repository_owner`/`organization.login` used to select the `webhook_secret`) before dispatching to handlers. Reject payloads where these disagree.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/orgs, `AttackerOrg` (attacker-administered, with `webhook_secret: S`) and `VictimOrg` (hosting stack `VictimOrg/victim-repo`), per `docs/setup.md`'s multi-org schema.
2. Attacker crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "full_name": "VictimOrg/victim-repo", "owner": { "login": "AttackerOrg" } }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, body)>` using their own known `webhook_secret` `S` for `AttackerOrg`, and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'AttackerOrg')` and validates successfully against `S` (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, which resolves `repository_name = 'VictimOrg/victim-repo'` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and enqueues `GithubSyncJob` against the real victim stack (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`), despite the signature only ever having been checked against `AttackerOrg`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
