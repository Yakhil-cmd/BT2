### Title
Webhook signature verification is keyed to an attacker-controlled `repository.owner.login`/`organization.login` field, while events are dispatched based on the independent `repository.full_name` field — an unsigned/misconfigured organization can forge events for any other organization's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the request signature against using a field taken directly from the unauthenticated request body (`repository.owner.login`, falling back to `organization.login`), but the handlers that actually act on the payload (e.g. `PushHandler`, `StatusHandler` via `Handler#repository_name`) resolve the target `Stack`/`Commit` using a *different* field from the same body, `repository.full_name`. These two fields are never checked against each other, so the organization whose secret "authenticates" the request is not bound to the repository that is actually written to.

### Finding Description
- The signature check picks the verifying organization from attacker-supplied JSON: [1](#0-0) [2](#0-1) 

- `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [3](#0-2) 

  Shipit explicitly documents/ships configurations where `webhook_secret` can be left blank, and supports multiple independently configured GitHub organizations in a single install: [4](#0-3) [5](#0-4) 

- Once `verify_signature` passes (either because the named org's secret is blank, or otherwise), the actual event handlers determine which repository/stack to act on using an entirely separate field of the same JSON body, `repository.full_name`, with no cross-check against `repository.owner.login`/`organization.login` used above: [6](#0-5) [7](#0-6) [8](#0-7) 

This is structurally the same class of bug as `TRST-H-1`: a field that is supposed to gate/scope an action (the organization the signature is checked against) is disjoint from the field that the privileged action actually operates on (the repository written), so the "authenticated" identity and the "acted-upon" resource can diverge, exactly the binding called out in scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
If any organization configured in Shipit's `secrets.yml` has `webhook_secret` left blank (a documented, supported configuration), an unauthenticated network attacker can:
1. POST to `/github/webhooks` with `X-Github-Event: push` (or `status`, `pull_request`, etc.).
2. Set `repository.owner.login`/`organization.login` to the name of the org with no `webhook_secret` — signature verification passes unconditionally (`return true unless webhook_secret`).
3. Set `repository.full_name` to `<other-org>/<real-repo>`, targeting a completely different, "protected" organization's stack.
4. The dispatched handler (`PushHandler`, `StatusHandler`, etc.) resolves the `Stack`/`Commit` purely from `repository.full_name` and performs privileged actions: e.g. `PushHandler` forces `stack.sync_github(expected_head_sha:)`, and `StatusHandler` forges a `Commit#create_status_from_github!`, which can flip commit-status gates used by the merge queue/continuous-deployment logic in `Stack`.

This crosses an organization/repository authorization boundary without any credentials, satisfying the "cross-repository writes"/"unauthorized deploy" bar in scope, because a status forged for a commit can unblock automatic deploy/merge decisions that are otherwise gated on real GitHub CI status.

### Likelihood Explanation
Requires only: (a) the target Shipit instance is configured with at least two GitHub organizations (a documented, supported multi-org setup) and (b) at least one of them has no `webhook_secret` set (also a documented/example configuration, and the natural state before an operator finishes setup). No credentials, sessions, or tokens are required — only knowledge of the org name lacking a secret and the target repo's `full_name`, both of which are typically public knowledge (GitHub org/repo names).

### Recommendation
Bind the two identity fields together instead of trusting them independently: the handler must verify that the resolved `Stack`'s `Repository` actually belongs to the same GitHub organization that was used to validate the webhook signature (i.e., compare `repository_owner` from `verify_signature` against the owner segment of `repository.full_name` used by `Handler#repository_name`, and reject on mismatch). Additionally, treat a missing `webhook_secret` as "verification not configured" rather than "verification passes," and require operators to configure secrets for every organization before webhook events are accepted, or scope handler lookups to only stacks belonging to the verified organization.

### Proof of Concept
Assume `secrets.yml` configures two orgs, `unsecured-org` (no `webhook_secret`) and `victim-org` (has a stack tracking `victim-org/app`):

```http
POST /github/webhooks HTTP/1.1
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "victim-org/app" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
- `WebhooksController#verify_signature` calls `Shipit.github(organization: "unsecured-org")` and `verify_webhook_signature` returns `true` immediately because `unsecured-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-83`).
- `Shipit::Webhooks::Handlers::StatusHandler#process` then finds `Commit` by `sha` (any commit tracked by any stack, including `victim-org/app`) and calls `create_status_from_github!`, forging a passing CI status for a commit the attacker does not control, with zero GitHub credentials involved.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
```
