### Title
Cross-repository commit-status forgery via unscoped global `sha` lookup - (`app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up `Commit.where(sha: params.sha)` with no repository/stack scoping and calls `commit.create_status_from_github!(params)` on every match. Every other webhook handler (`push_handler.rb`, `check_suite_handler.rb`, the `pull_request/*` handlers) resolves records through `Handler#stacks`, which scopes to `Repository.from_github_repo_name(repository_name)` derived from the payload's `repository.full_name` — `StatusHandler` is the outlier that skips this scoping entirely.

### Finding Description
The binding that should hold is: `repository_owner`/`repository.full_name` from the verified webhook payload == the repository that owns the `Commit` row being mutated. `WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App installation for `repository_owner` [1](#0-0) . It does not restrict which `Commit` rows the resulting handler is allowed to touch.

`StatusHandler#process` never calls `stacks` (the helper defined in `Handler` that scopes to `Repository.from_github_repo_name(repository_name)` [2](#0-1) ) and instead does a bare global lookup: [3](#0-2) 

The `commits` table only enforces uniqueness of `sha` per `stack_id` (`add_index :commits, %i(sha stack_id), unique: true`), i.e., the schema explicitly permits the same `sha` to exist under multiple stacks/repositories simultaneously [4](#0-3) . `Commit#create_status_from_github!` writes attacker-controlled `state`/`description`/`target_url` via `statuses.replicate_from_github!` and this feeds `Commit#status`, `#deployable?`, and `#blocked?` [5](#0-4) [6](#0-5) .

Exploit flow: attacker forks or otherwise controls a repository under an org where a Shipit GitHub App installation exists (so `Shipit.github(organization: repository_owner)` succeeds and signature verification passes). If that repository shares any commit sha with a victim's tracked stack (trivial for a fork sharing history, or any commit whose sha the attacker learns and can reproduce byte-for-byte, e.g. by fetching and re-pushing/mirroring the exact commit object into their own repo — sha is content-addressed, not repo-bound, so pushing the identical commit object to any repo they control reproduces the identical sha), the attacker creates a commit status on that sha in their own repository via the normal GitHub status API (which they have write access to). GitHub delivers a validly-signed `status` webhook naming that sha. `StatusHandler` finds every `Commit` row across all stacks/orgs with that sha — including the victim's — and writes the attacker's `state`/`description`/`target_url` onto it, flipping `deployable?` and CI gating for the victim stack.

Existing guards do not catch this: `verify_signature` only authenticates the org the payload claims to be from, not which `Commit` rows may be touched; `drop_unhandled_event` and the `ExplicitParameters` schema only validate/allow-list the payload shape, not scope; there is no `stacks`/`Repository.from_github_repo_name` check in `StatusHandler` unlike its siblings.

### Impact Explanation
A payload validly signed for repository/org A can write a commit status onto a `Commit` row belonging to a completely different stack/org B, as long as a `Commit` with the same `sha` exists there. This directly matches the "payload for one repository mutating another's stack/commit" Critical category: it can flip `deployable?` (via `success?`/`blocked?`) and thus influence deploy/CI gating decisions for a victim stack the attacker never authenticated against. The attack is repeatable against any sha collision the attacker can arrange (most practically via forks sharing history, or by reproducing identical commit objects), across arbitrary tenant stacks that track the same commit sha.

### Likelihood Explanation
Preconditions: attacker must control a GitHub repository/org for which a Shipit GitHub App/webhook secret is already configured (a normal precondition of using Shipit's public GitHub App), and must find or manufacture a commit sha collision with a victim's tracked commit — realistically via forking a victim's public repo (shared ancestry naturally produces identical shas for shared commits) or by pushing an identical commit object to a repo they control. No Shipit credentials, sessions, or admin roles are required beyond what's stipulated in the question (a validly-signed webhook from the attacker's own org). This is feasible without brute-forcing SHA-1 collisions in the common fork scenario.

### Recommendation
Scope `StatusHandler#process` to the repository asserted in the payload, mirroring the other handlers: resolve the target stack(s) via `stacks` (`Repository.from_github_repo_name(repository_name)`) and restrict the `Commit` lookup to `stacks.commits.where(sha: params.sha)` (or equivalently join through `stack_id`) instead of a bare global `Commit.where(sha: ...)`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new or existing file under `test/`):
1. Create `repo_a = Repository.create!(...)`, `stack_a = Stack.create!(repository: repo_a, ...)`, `commit_a = Commit.create!(stack: stack_a, sha: 'deadbeef' * 5, ...)`.
2. Create `repo_b = Repository.create!(...)` (different `github_id`/owner), `stack_b = Stack.create!(repository: repo_b, ...)`, `commit_b = Commit.create!(stack: stack_b, sha: commit_a.sha, ...)`.
3. Build a `status` payload where `payload['repository']['full_name'] == repo_a.full_name` and `sha == commit_a.sha`, `state: 'success'`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature verification, which is out of scope for the handler-level bug).
5. Assert `commit_b.reload.status.state == 'success'` even though the payload's `repository.full_name` equals `repo_a.full_name`, i.e. assert `commit_b.stack.repository.full_name != payload['repository']['full_name']` while `commit_b.status.state` changed — proving the binding `payload.repository == commit.stack.repository` is violated.
6. Contrast with the fixed behavior: after scoping the handler via `stacks`, assert `commit_b.reload.status.state` remains unchanged (`unknown`/previous state) and only `commit_a.status.state` is updated.
