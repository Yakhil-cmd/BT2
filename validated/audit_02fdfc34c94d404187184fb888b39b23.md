## Finding: Attestation-gated assets can permanently freeze a holder's coins with no self-service escape

### Title
Spender-attested assets can trap a holder's coins indefinitely with no way to force a transfer - (File: `validation.js`)

### Summary
Obyte lets an asset definer create an asset with `spender_attested: true`. Every payment (public or private, divisible or indivisible) that spends or sends coins of that asset requires the input owner's address (and, for issues, the issuer's address) to currently appear in the asset's attestor-approved list. The attestor list itself can only be changed by the asset definer, and individual address attestations can only be published by the attestor. A coin holder has no mechanism of their own to move or reclaim their coins if the attestor stops attesting them (or never attests them, or the attestation is invalidated by an unrelated address-definition change) — exactly the "must wait for a third party to act before I can close/move my position" pattern described in the report.

### Finding Description
When an asset is defined with `spender_attested: true`, `validateAssetDefinition` requires an initial attestor list [1](#0-0) , and that list can subsequently be updated only by the asset's definer via an `asset_attestors` message: [2](#0-1) 

Every payment of such an asset is checked against the *current* attestor-approved list of addresses, not against a one-time approval:
- For divisible/base payments, both the issuer and payment authors must be attested: [3](#0-2) 
- For private indivisible coin transfers, the owner address of every spent coin must be attested at spend time: [4](#0-3) 

The set of "attested addresses" is computed dynamically by `filterAttestedAddresses`, which requires an `attestation` row from one of the *asset's currently-registered* attestors, and — critically — that attestation must be newer than the address's *last definition change*: [5](#0-4) 

This means a holder's ability to spend depends on:
1. The definer keeping/adding the right attestor in `asset_attestors` (definer-only, `validation.js:2841-2842`), and
2. That attestor continuing to publish a fresh `attestation` for the holder's address after any definition change.

If either party stops cooperating — attestor removed from the list, attestor goes offline, attestor simply declines to re-attest, or the holder rotates their address definition (a normal user action) after which the old attestation no longer counts — the holder's coins of that asset become permanently unspendable. There is no `force`/override input type, no timeout-based fallback, and no way for the holder alone to satisfy the condition, unlike ordinary address-definition-based spending conditions where the owner can always satisfy their own signature requirement.

### Impact Explanation
Funds denominated in a `spender_attested` asset can become permanently frozen for legitimate holders whenever the definer or attestor becomes unresponsive, malicious, or simply changes policy (e.g., de-lists an attestor, or an attestor refuses to renew attestation after a routine address key rotation). This is a fund-freezing condition reachable purely through normal asset/attestation/definition-change message flows already supported by the protocol — no p2p or node-level compromise is needed. The severity depends on how much value is denominated in such assets (which include private, indivisible, KYC-style assets), but the freezing is total and indefinite for the affected holder(s).

### Likelihood Explanation
Any asset definer can create a `spender_attested` asset (a first-class, documented protocol feature), and any of these conditions can arise from ordinary usage: the definer updating the attestor list for business reasons, an attestor discontinuing service, or a holder rotating their address definition (a supported, common action in `has_definition_change`/`seen definition change` conditions, cf. `definition.js:352-368`) which invalidates prior attestations per the `filterAttestedAddresses` join condition. No adversarial network behavior is required — only ordinary administrative/business actions by the definer/attestor, which are explicitly outside the holder's control.

### Recommendation
Provide holders of `spender_attested` assets a self-service escape hatch analogous to a "force repay" — e.g., allow spending to a fixed set of addresses (such as back to the definer, or to a "burn"/exit path) without requiring current attestation, or add a grace/expiry mechanism so that once-attested coins can still be moved for some fallback purpose even if the attestor list changes later. Alternatively, document explicitly that `spender_attested` assets carry indefinite freezing risk and that holders must trust the definer/attestor to keep cooperating, since currently there is no way for holders to force a transfer independent of attestor cooperation.

### Proof of Concept
1. Definer issues asset A with `spender_attested: true` and attestor set `{X}` (`validation.js:2725-2827`, `validateAttestorListUpdate`).
2. Attestor X attests holder H's address; H receives/holds coins of asset A.
3. Definer publishes a new `asset_attestors` message removing X (or replacing with Y) — allowed unilaterally by the definer per `validateAttestorListUpdate` (`validation.js:2829-2848`).
4. H's earlier attestation from X no longer satisfies `filterAttestedAddresses` because X is no longer in `objAsset.arrAttestorAddresses` (`storage.js:1959-1974`).
5. Any subsequent payment by H spending asset A fails validation at `validation.js:2115-2122` (divisible) or `validation.js:2430-2433` (private/indivisible) with "none of the authors is attested" / "owner address is not attested".
6. H has no way to construct a valid payment moving these coins anywhere — including back to the definer — until/unless the definer/attestor cooperate again, mirroring the reported "must wait for someone else to act, no force option" bug class.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
			handleAttestedAddresses(arrAttestedAddresses);
		}
	);
}
