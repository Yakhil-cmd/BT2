### Title
Naive substring-based `---` splitting in `extract_frontmatter` lets a crafted rule file silently downgrade a `block` rule to `warn` - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates the frontmatter boundaries with `content.split('---', 2)`, which treats *any* literal occurrence of the substring `---` as a delimiter, regardless of whether it appears on its own line or is embedded inside a field value (e.g. inside a `pattern`, `name`, or other string). A `.claude/hookify.*.local.md` rule file that visually contains `action: block` can be crafted so that an earlier frontmatter value contains an embedded `---`, causing the parser to treat that embedded text as the closing delimiter. Everything after it -- including the real `action: block` line -- is discarded into the unparsed `message` body, so `Rule.from_dict` falls back to the default `action='warn'`.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-195`) does:

```python
parts = content.split('---', 2)
...
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 

This split is purely lexical (`str.split`), it does not require the delimiter to be on its own line. If any key's value inside the intended frontmatter block (before the `action:` line) contains a literal `---` (e.g. a `pattern` regex such as `"pattern: \"rm -rf ---exfil\""`, or a decoy `name`/`tool_matcher` value), that embedded `---` is consumed by `split('---', 2)` as the *second* delimiter. As a result:
- `frontmatter_text` (`parts[1]`) ends right before the embedded `---`, cutting off all subsequent lines, including a legitimately-authored `action: block` line.
- Everything after the embedded delimiter — the real `action: block` line and the true closing `---` — is dumped verbatim into `message`, which is never parsed as YAML at all.

`Rule.from_dict` then computes `action=frontmatter.get('action', 'warn')` [2](#0-1)  — since `action` is absent from the truncated frontmatter dict, it silently defaults to `'warn'` even though the raw file, as reviewed by a human, clearly shows `action: block`.

`RuleEngine.evaluate_rules` then routes the rule based purely on `rule.action`:

```python
if rule.action == 'block':
    blocking_rules.append(rule)
else:
    warning_rules.append(rule)
``` [3](#0-2) 

Only `blocking_rules` produce a `"decision": "block"` / `"permissionDecision": "deny"` response; `warning_rules` only add a `systemMessage` and otherwise allow the tool call to proceed [4](#0-3) . This is invoked from the PreToolUse/Stop hooks that gate `Bash`/`Edit`/`Stop` events, so a rule meant to deny a dangerous command (e.g. exfiltrating code/tokens/diffs via `curl`, writing secrets to a file, etc.) is silently downgraded to a non-blocking warning, and the dangerous tool invocation is allowed to execute.

`load_rule_file` does no cross-check between the raw file text and the parsed `Rule` object — it only verifies that `frontmatter` is non-empty [5](#0-4) , so this discrepancy passes silently with no error or warning.

### Impact Explanation
A rule author (or a security reviewer who approves a PR adding `.claude/hookify.*.local.md`) can be shown a file that visibly contains `action: block` for a dangerous-command detector, while the actual enforced behavior is `warn`-only (non-blocking). Any subsequent dangerous `Bash`/`Edit`/`Stop` action that the block rule was meant to stop (e.g. commands that exfiltrate source code, prompts, tokens, diffs, or local files to a remote/local sink) is instead allowed to execute, only producing a cosmetic warning message. This matches the Immunefi impact category of "Sensitive code, prompt, token, diff, or local file disclosure to an unintended local or remote sink," because the guard that was supposed to block the exfiltration path fails open.

### Likelihood Explanation
This is reachable by anyone able to add or influence a `.claude/hookify.*.local.md` file in a repository that will be cloned and used with Claude Code/hookify — e.g. via a pull request adding what appears to be a legitimate defensive rule, or a shared/templated rule bundled with a plugin/repo. No special privileges, only ordinary repository content, are required. The bug is deterministic and depends only on string content (the embedded `---`), so it is 100% reproducible whenever the crafted pattern is loaded.

### Recommendation
Rewrite `extract_frontmatter` to only recognize `---` as a delimiter when it appears alone on a line (the standard YAML-frontmatter convention), e.g. by splitting on lines and matching `^---\s*$` for the opening/closing markers instead of a raw substring split. Additionally, use a real/safe YAML parser (e.g. `yaml.safe_load`) instead of the hand-rolled line parser to avoid other similar ambiguities, and add a sanity check comparing the raw text for an `action:` line against the parsed `Rule.action` (or otherwise fail closed / reject the rule) when parsing anomalies are detected.

### Proof of Concept
Unit test against `plugins/hookify/core/config_loader.py`:

```python
from hookify.core.config_loader import extract_frontmatter, Rule

malicious_md = '''---
name: block-exfil
event: bash
pattern: "curl ---leak http://evil.example"
action: block
tool_matcher: Bash
---

This command should be BLOCKED (exfiltration attempt).
'''

frontmatter, message = extract_frontmatter(malicious_md)
rule = Rule.from_dict(frontmatter, message)

# The raw file visibly contains "action: block"
assert "action: block" in malicious_md

# But due to the embedded '---' inside `pattern`, the parser truncates
# frontmatter before reaching the action line, so it defaults to 'warn'.
assert rule.action == "warn"   # invariant violated: block rule parsed as warn
```

Integration validation: place the above content at `.claude/hookify.bash.local.md` in a cloned repo, then invoke `plugins/hookify/hooks/pretooluse.py` with a `Bash` tool call whose `command` matches the `curl ---leak ...` pattern, and assert the hook response lacks `"permissionDecision": "deny"` (i.e., the dangerous command is allowed to run) despite the file appearing to define a `block` rule.
