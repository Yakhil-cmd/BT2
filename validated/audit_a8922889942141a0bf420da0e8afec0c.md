### Title
Webhook signature verification is bypassed entirely when `webhook_secret` is blank, allowing unauthenticated forgery of GitHub events including team membership escalation - (File: `lib/shipit/github_app.rb`, `app/controllers/shipit/webhooks_controller.rb`)

### Summary
The Sherlock report describes a binding failure: the price a liquidator *approves* is not the price that is actually *charged*, because nothing ties the executed transaction to the value the user committed to. The analogous binding in `shipit-engine` is between the GitHub organization that is supposed to *authenticate* an inbound webhook and the repository/team data that is actually *written* as a result of processing it. `WebhooksController` derives the signing key from an attacker-controlled field of the very payload it's about to verify, and `GitHubApp#verify_webhook_signature` silently accepts *any* request, unsigned or not, whenever `webhook_secret` is unset for that organization — a configuration explicitly documented as "optional".

### Finding Description
`WebhooksController#verify_signature` picks which secret to check the HMAC against using an untrusted field pulled straight out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

The actual verification is delegated to `GitHubApp#verify_webhook_signature`: [3](#0-2) 

`return true unless webhook_secret` means that for any organization configured in Shipit without a `webhook_secret` — a state the setup docs present as a normal, optional choice — **all signature checking is skipped**, and the request is treated as authentic regardless of who sent it: [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, `WebhooksController#create` parses the raw body and dispatches it, unmodified and fully attacker-controlled, to the registered handlers for whatever `X-Github-Event` header was supplied: [6](#0-5) 

One of these handlers is the membership handler, which mutates `Shipit::Membership`/`Shipit::Team` records directly from the payload's `team`, `member`, and `action` fields — confirmed by the controller test asserting it creates teams and appends/removes memberships purely from webhook parameters: [7](#0-6) 

Authorization to use Shipit at all is gated by exactly this membership data: [8](#0-7) 

So the equality that should hold — "the organization whose credentials authenticated this request" == "the organization/repository/team whose state this request is permitted to write" — is broken in two independent ways: (1) `repository_owner` (used only to pick the signing key) is never checked against the `repository.full_name`/`team`/`member` fields the handlers act on, and (2) when `webhook_secret` is blank, there is no authentication step at all, so *no* organization is actually authenticated, yet the payload is still trusted to create/delete team memberships that feed straight into `Shipit.github_teams` authorization.

### Impact Explanation
An unauthenticated network attacker who can reach `/webhooks` on a Shipit instance configured with an organization that has no `webhook_secret` set can:
- Add arbitrary GitHub logins to arbitrary team IDs that match `Shipit.github_teams`, causing `User#authorized?` to return `true` for those logins — i.e., escalation into `Shipit.github_teams` authorization, one of the explicitly qualifying High-severity impacts.
- Forge `push`/`status`/`check_suite` events for any tracked stack, enqueuing sync jobs and fabricating commit statuses that downstream automation (merge queue, auto-deploy) may rely on.

This is a direct instance of the "verified vs. executed" binding failure the report describes, but manifesting as an authorization/data-integrity bypass rather than a pricing bypass.

### Likelihood Explanation
Likelihood depends on the operator leaving `webhook_secret` blank for at least one configured organization. The setup docs and example secrets file present this as a normal, optional setting with no warning that omitting it disables all authentication on the endpoint, making misconfiguration plausible in real deployments, especially multi-organization ones where a "less important" org's entry might be added without a secret.

### Recommendation
- Make `webhook_secret` mandatory (fail closed) rather than optional; refuse to boot, or refuse to process events for, any organization without a configured secret.
- Cross-validate the payload's `repository.owner.login` (or `organization.login`) used to select the verification key against the same field(s) later used by handlers (`repository.full_name`, `team`, `member`) so a signed request for org A cannot be used to mutate state belonging to org B.
- Do not let webhook-sourced `membership` events directly grant `Shipit.github_teams` authorization without an additional server-side re-verification (e.g., a follow-up API call against GitHub) of the claimed membership change.

### Proof of Concept
1. Configure Shipit with an organization entry (e.g. `shopify`) that has `webhook_secret: nil` (a supported configuration per `docs/setup.md`).
2. As an unauthenticated attacker, `POST /webhooks` with header `X-Github-Event: membership` and a body:
```json
{
  "action": "added",
  "organization": { "login": "shopify" },
  "repository": { "owner": { "login": "shopify" } },
  "team": { "id": <id of a Shipit.github_teams entry>, "slug": "developers", "name": "Developers", "url": "http://example.com" },
  "member": { "login": "attacker-handle" }
}
```
3. `verify_signature` calls `verify_webhook_signature(nil, raw_body)` on the `shopify` `GitHubApp`, which returns `true` immediately because `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`).
4. The membership handler creates a `Shipit::Membership` linking `attacker-handle` to the targeted team (behavior demonstrated by `test/controllers/webhooks_controller_test.rb:159-165`), after which `User#authorized?` returns `true` for that login, granting it full Shipit access without ever having authenticated through GitHub OAuth.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
