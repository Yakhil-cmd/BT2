### Title
User-controlled swap route executes arbitrary venue code under the caller’s authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
Controller strategies pass attacker-controlled route bytes to the configured router after authorizing only the routed input transfer. Because route hops are not restricted to governance-approved pool contracts, a malicious pool can run during the strategy and request additional authorization from the original caller. Soroban records that request beneath the caller’s `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, or equivalent root authorization. If the wallet signs the simulated tree, the pool can transfer unrelated wallet assets to an attacker while still returning a valid swap output.

### Finding Description
`swap_collateral` accepts arbitrary `swap` bytes and forwards them into the strategy implementation. [1](#0-0)  `swap_tokens` snapshots input/output balances, authorizes only `token_in.transfer(controller, router, amount_in)`, and invokes `router.execute_strategy(controller, amount_in, swap)`. [2](#0-1)  The controller then checks only that measured input spending does not exceed `amount_in` and that measured output is positive; it does not constrain which contract addresses the route invokes. [3](#0-2) 

The router treats the payload as an executable program: it authenticates `sender`, decodes caller-supplied asset and instruction registries, and executes each hop. [4](#0-3)  A swap hop resolves its `pool`, `token_in`, and `token_out` entirely from the payload’s `assets` registry and dispatches to the selected venue adapter. [5](#0-4)  There is no pool allowlist in dispatch; the venue selector chooses the ABI, while the payload chooses the contract address. [6](#0-5) 

For example, the Soroswap adapter calls payload-controlled `pool.get_reserves()` and then `pool.swap(...)`. [7](#0-6)  The Phoenix and Sushi adapters likewise invoke a payload-controlled pool’s `swap` function. [8](#0-7) [9](#0-8) 

The repository’s adversarial test demonstrates the authorization consequence: a rogue hop pool invoked beneath the controller calls `token.transfer(victim, attacker, amount)`. [10](#0-9)  Simulation attaches that unrelated transfer as a child of the victim’s `swap_collateral` authorization. [11](#0-10)  In enforcing mode, the same transfer succeeds only when the signed authorization tree contains it. [12](#0-11) 

### Impact Explanation
This is theft of user funds beyond the routed amount. A malicious pool can target any token for which it can induce the victim to authorize a nested `transfer`, including assets not listed by XOXNO Lending. The demonstrated PoC transfers an unrelated wallet token balance to the attacker while preserving the expected lending-side swap result. [13](#0-12) 

The attacker can also satisfy route settlement honestly: return a positive `token_out` delta, consume exactly `amount_in`, and preserve the victim’s final account health. Consequently, the controller’s balance-delta checks and risk gates do not bound the loss to the routed input. [14](#0-13)  This crosses the intended authorization boundary: one lending-strategy signature becomes authorization for unrelated token movement requested by arbitrary route-selected code.

### Likelihood Explanation
Likelihood is Medium. Exploitation requires a victim to submit a poisoned route and sign an authorization tree containing the malicious transfer, so it is not a purely permissionless theft from an arbitrary account. However, routes are opaque XDR payloads supplied to normal strategy entrypoints, venue contracts are selected by the payload, and an honest simulation records the rogue transfer beneath the expected strategy root rather than as a separate top-level operation. [15](#0-14)  A malicious quote provider, compromised frontend, or phishing flow can therefore present a valid-looking strategy while embedding an unrelated wallet transfer.

### Recommendation
Do not let route bytes select arbitrary venue contract addresses during lending strategies.

- Maintain a governance-approved venue/pool registry and reject any payload naming an unregistered address.
- Prefer registry IDs over raw contract addresses in the packed route format.
- Include the decoded venue addresses and all required authorization children in wallet-visible route verification.
- Treat any authorization child other than the expected strategy input flow as fatal by default.
- Consider routing through venue adapter contracts that call only immutable approved pool addresses, rather than accepting pool addresses from user-controlled XDR.

### Proof of Concept
1. The attacker deploys `RoguePool`, implementing the expected venue ABI.
2. The victim supplies collateral to XOXNO Lending and holds an unrelated wallet token `T`.
3. The attacker constructs `swap` XDR whose `assets` registry names `RoguePool`, normal `token_in`, and normal `token_out`, with a valid `min_out`.
4. The victim calls:

   `controller.swap_collateral(victim, account_id, current_asset, amount, new_asset, swap)`

   `swap_collateral` accepts the route and forwards it through the strategy path. [1](#0-0) 
5. `swap_tokens` authorizes only the expected controller-to-router input transfer and invokes the router. [16](#0-15) 
6. During `RoguePool.swap`, the pool executes:

   ```rust
   token::Client::new(&env, &wallet_token).transfer(
       &victim,
       &attacker,
       &wallet_balance,
   );
   ```

   The equivalent malicious pool is implemented in the repository test. [17](#0-16) 
7. `RoguePool` also returns enough `token_out` to satisfy positive-output and `min_out` checks, so the lending strategy completes normally.
8. The poisoned simulated authorization tree contains the unrelated `wallet_token.transfer(victim, attacker, wallet_balance)` beneath the victim’s `swap_collateral` authorization. [18](#0-17) 
9. If the victim signs that tree, `T` moves to the attacker while the route still reports valid output. The repository test demonstrates Alice’s full unrelated wallet balance becoming zero and the attacker receiving it. [19](#0-18)

pub(crate) fn swap(ctx: &HopContext<'_>) {
    let token_in_is_0 = ctx.hop.token_in < ctx.hop.token_out;

    let no_args: Vec<Val> = vec![ctx.env];
    let (reserve_0, reserve_1): (i128, i128) = ctx.env.invoke_contract(
        &ctx.hop.pool,
        &Symbol::new(ctx.env, "get_reserves"),
        no_args,
    );
    let (reserve_in, reserve_out) = if token_in_is_0 {
        (reserve_0, reserve_1)
    } else {
        (reserve_1, reserve_0)
    };

    let requested_out = soroswap_amount_out(ctx.env, ctx.amount_in, reserve_in, reserve_out);
    if requested_out <= 0 {
        panic_with_error!(ctx.env, Error::ZeroOutput);
    }

    let token_client = token::Client::new(ctx.env, &ctx.hop.token_in);
    token_client.transfer(ctx.router, &ctx.hop.pool, &ctx.amount_in);

    let (amount_0_out, amount_1_out) = if token_in_is_0 {
        (0_i128, requested_out)
    } else {
        (requested_out, 0_i128)
    };
    let args: Vec<Val> = vec![
        ctx.env,
        amount_0_out.into_val(ctx.env),
        amount_1_out.into_val(ctx.env),
        ctx.router.into_val(ctx.env),
    ];
    let _: () = ctx
        .env
        .invoke_contract(&ctx.hop.pool, &symbol_short!("swap"), args);
}

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
