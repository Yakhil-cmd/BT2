### Title
Rounding of headers commission shares among multiple recipients allows byte (base-currency) supply inflation - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a unit's earned `headers_commission` (a fixed integer amount, `full_amount`, actually paid by the payer unit) among several `earned_headers_commission_recipients` using independently rounded percentage shares: `Math.round(full_amount * share / 100.0)`. Because each recipient's share is rounded separately, the sum of the individually rounded amounts is not guaranteed to equal `full_amount`. No invariant check re-validates that the sum of distributed shares matches the original fee, so the total amount credited to `headers_commission_contributions`/`headers_commission_outputs` can exceed the amount actually paid, minting extra spendable bytes.

### Finding Description
When a stable child unit wins headers commission from a parent, and that child has multiple authors, the earning is split according to `earned_headers_commission_recipients` (validated only to have integer `earned_headers_commission_share` values summing to exactly 100, see `validateHeadersCommissionRecipients` in [1](#0-0)  and stored per-unit in [2](#0-1) ).

The actual byte amounts are computed per recipient independently with rounding, both in the SQL path and the in-RAM/JS path: [3](#0-2) [4](#0-3) 

Because `Math.round()` (or MySQL `ROUND()`) is applied to each `full_amount * share / 100.0` term independently, the sum of the results is not constrained to equal `full_amount`. There is no post-loop assertion (analogous to the reported `require(totalPaid == purchaseCost)`) that checks the sum of the per-recipient amounts against `full_amount`; the values are simply inserted into `headers_commission_contributions` and later aggregated into `headers_commission_outputs`, which are real spendable base-asset outputs.

An attacker fully controls this split: they can author a multi-author unit, freely choose which of their own addresses are co-authors, and set the `earned_headers_commission_share` percentages (only constrained to sum to 100 and be positive integers). By choosing shares that individually round up (e.g., 34/33/33) against a small `full_amount`, the attacker can make the sum of rounded amounts exceed `full_amount`, effectively minting extra bytes with each win.

### Impact Explanation
This is a supply-inflation bug in the base currency (bytes): outputs recorded in `headers_commission_outputs` are spendable exactly like ordinary payment outputs, but here they can be created in an amount exceeding what the payer unit actually paid as `headers_commission`. Repeated systematically (attacker posts cheap, small-fee units authored by several attacker-controlled addresses with rounding-favorable percentage splits, and wins the headers-commission race for a parent), this results in unauthorized creation of base-currency supply, i.e., value not backed by any input, harming the integrity of the DAG's monetary supply.

### Likelihood Explanation
Any regular (non-privileged) node can author a multi-authored unit and set `earned_headers_commission_recipients`; no special role (witness, hub, arbitrator) is required. The only extra requirement is winning headers commission on a chain, which is a routine, expected outcome of normal DAG operation, not a rare edge case, and the exact `full_amount` value on a given branch can be influenced by choosing which/how many units to author. This makes the rounding-based gain reproducible with modest effort.

### Recommendation
Do not round each recipient's share independently and drop the remainder. Either:
- Compute all recipients' shares with integer arithmetic that keeps a running remainder and assigns any leftover/deficit to a single designated recipient (e.g., the largest-share or first-address recipient) so the sum always exactly equals `full_amount`, or
- After computing rounded amounts, add an explicit invariant check that `sum(amounts) === full_amount` and correct the last recipient's amount to force equality before inserting into `headers_commission_contributions`.
Apply the same fix pattern to the analogous witnessing payout rounding (`Math.round(objUnit.payload_commission / countPaidWitnesses[...])` in `paid_witnessing.js`) if it is subject to the same drift.

### Proof of Concept
1. Attacker controls addresses `A1 < A2 < A3` (sorted, as required).
2. Attacker crafts a unit `U`, authored by `A1, A2, A3`, with `earned_headers_commission_recipients = [{A1,34},{A2,33},{A3,33}]` (validated: sum=100, all positive integers — passes `validateHeadersCommissionRecipients`).
3. Attacker arranges for `U` to be the winning child unit for a parent unit `P` whose `headers_commission` (`full_amount`) is small, e.g., `2` bytes (winner selection is via SHA1 hash tie-break in `getWinnerInfo`, `headers_commission.js:249-259` — attacker can try many candidate units/timings to land a favorable `full_amount`, or simply repeat over many small-fee parent units until a favorable value occurs).
4. `calcHeadersCommissions` computes, per `headers_commission.js:180-188`/`192-206`:
   - `Math.round(2*34/100)=Math.round(0.68)=1`
   - `Math.round(2*33/100)=Math.round(0.66)=1`
   - `Math.round(2*33/100)=1`
   - Total credited = 3, while the payer unit `P` only actually paid `full_amount = 2`.
5. The extra `1` byte is inserted into `headers_commission_contributions` and aggregated into `headers_commission_outputs` (`headers_commission.js:222-227`), becoming spendable by attacker-controlled `A1/A2/A3`, with no compensating check anywhere in `validation.js` or `writer.js` that the recipients' amounts sum back to `full_amount`.
6. Repeating this over many low-value parent units yields systematic, unbacked byte creation.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
