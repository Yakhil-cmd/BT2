### Title
`provision?` operator-precedence bug lets `allow_with_label`/`prevent_with_label` create stacks while `review_stacks_enabled` is `false` - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`PullRequest::OpenedHandler#provision?` combines `review_stacks_enabled` and `provisioning_behavior_*` predicates with `&&`/`||` without parentheses, so Ruby's operator precedence makes `review_stacks_enabled` bind only to the `allow_all?` branch. The `allow_with_label?` and `prevent_with_label?` branches are evaluated completely independently of `review_stacks_enabled`, so an operator who sets `provisioning_behavior` to `allow_with_label` (or `prevent_with_label`) via the documented settings form, while leaving the separate "Dynamically provision stacks for Pull Requests?" checkbox unchecked, will still get Review Stacks created/destroyed from an attacker-controlled PR label.

### Finding Description
The intended binding an operator believes holds is: `review_stacks_enabled == false` implies `provision? == false` for every `provisioning_behavior` value. The actual code is: [1](#0-0) 

```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

In Ruby, `&&` has higher precedence than `||`, so this parses as:

```ruby
(repository.review_stacks_enabled && repository.provisioning_behavior_allow_all?) ||
(repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
(repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
```

`review_stacks_enabled` is only ANDed into the first disjunct. The second and third disjuncts (`allow_with_label` / `prevent_with_label`) evaluate to `true` purely from `provisioning_behavior` and the PR's labels, with no dependency on `review_stacks_enabled` at all.

The settings form exposes `review_stacks_enabled` and `provisioning_behavior` as two independent fields: [2](#0-1) 

The migration confirms `review_stacks_enabled` defaults to `false` and `provisioning_behavior` defaults to `allow_all`: [3](#0-2) 

Documentation (`docs/review_stacks.md`) instructs operators to check the checkbox AND pick a behavior, implying both fields jointly gate provisioning — but the code does not enforce that for two of the three behavior modes.

**Attack/misconfiguration flow:** An operator, following the settings UI, changes `provisioning_behavior` to `allow_with_label` (or `prevent_with_label`) but does not check "Dynamically provision stacks for Pull Requests?" (leaving `review_stacks_enabled` at its default `false`). Any unprivileged GitHub user who can open a PR against that repository and add/omit the configured provisioning label can then trigger `respond_to_pull_request_opened?` → `provision?` → `true`, causing `ReviewStackAdapter#find_or_create!` to create a Review Stack, entirely bypassing the operator's belief that review stacks are disabled. [4](#0-3) 

No guard elsewhere (`verify_signature`, `ExplicitParameters` schema, model validations) checks or restores this binding — those guards validate payload shape and authenticity, not the `review_stacks_enabled`/`provisioning_behavior` interaction. The existing test suite's `configure_provisioning_behavior` helper defaults `provisioning_enabled: true` for the `allow_with_label`/`prevent_with_label` tests, so the existing tests never exercise (and thus never catch) the `review_stacks_enabled: false` + `allow_with_label`/`prevent_with_label` combination.

### Impact Explanation
This causes unauthorized creation (and subsequent deploy/rollback lifecycle via `ReviewStack`) of a Shipit stack for a repository whose operator explicitly believed review-stack provisioning was disabled, triggered purely by an attacker's PR label choice. This is a record being written (a `Stack`/`ReviewStack` row, provisioning queue entry, and potential downstream deploy actions) for a repository based on state the operator did not authorize, matching the "unauthorized deploy... or a payload... mutating another's stack" class of impact. It is repeatable on every `opened`/`reopened`/`labeled`/`unlabeled` webhook for any repository misconfigured this way, and is not scoped to a single PR — any PR against that repo is affected.

### Likelihood Explanation
Requires no attacker privilege beyond opening a PR and applying a label they control on their own PR/fork — exactly the documented, low-cost attacker capability. It requires a specific but realistic operator misconfiguration: setting `provisioning_behavior` to `allow_with_label`/`prevent_with_label` without also checking the `review_stacks_enabled` checkbox — a very plausible mistake since the two fields are visually and semantically presented as independent controls in `settings.html.erb`, and the docs conflate them as a single "enable review stacks" step. No secrets, tokens, or elevated GitHub roles are needed.

### Recommendation
Add explicit parentheses so `review_stacks_enabled` gates all three behavior branches:

```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```
Apply the identical fix to the other handlers with the same duplicated logic (`labeled_handler.rb`, `unlabeled_handler.rb`, `reopened_handler.rb`).

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:

```ruby
test "does NOT create a stack for allow_with_label when review_stacks_enabled is false (operator left checkbox unchecked)" do
  repository = shipit_repositories(:shipit)
  repository.review_stacks_enabled = false # DB default, operator never checked the box
  repository.provisioning_behavior = :allow_with_label
  repository.provisioning_label_name = "pull-requests-label"
  repository.save!

  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] << { "name" => "pull-requests-label" }

  assert_equal false, repository.review_stacks_enabled
  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```

Running this against current code fails: `Shipit::Stack.count` increases by 1 despite `repository.review_stacks_enabled == false`, proving `provision?` returns `true` when it should be gated to `false`, confirming the precedence bug.
