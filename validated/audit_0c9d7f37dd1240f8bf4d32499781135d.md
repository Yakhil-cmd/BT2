## Title
Webhook signature is verified against an attacker-selected organization while write-handlers act on repository/commit data outside that organization's control - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on an unauthenticated field taken straight out of the request body, then, once *any* configured organization's secret validates the signature, downstream `Shipit::Webhooks::Handlers` act on other fields of that same attacker-supplied body (`repository.full_name`, or in `StatusHandler`'s case, just a bare `sha`) with no re-check that those fields belong to the organization whose secret actually verified the request. This breaks the intended binding `organization whose secret verified the signature == organization owning the resource being written`, mirroring the reported class of bug where a value used for one authorization decision (approval) is disconnected from the value the acted-upon logic (route/settle) actually consumes.

### Finding Description
`verify_signature` picks the verification key like this: [1](#0-0) 

`repository_owner` is read straight from the unauthenticated JSON body: [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config/secrets from `secrets.github` (multi-tenant orgs are supported, each with its own `webhook_secret`): [3](#0-2) 

Once `verify_webhook_signature` returns true for whichever organization's secret was selected by `repository_owner`, `create` dispatches the *entire, attacker-crafted raw body* to the registered handlers for the event type: [4](#0-3) 

Handlers, however, do not re-derive the acted-upon resource from `repository_owner` (the value that was actually cryptographically verified). Most look up the target stack via `repository.full_name`: [5](#0-4) 

and `StatusHandler` goes further and doesn't even consult the repository field — it matches purely on a bare `sha` against every `Commit` in the database, i.e. across every stack/organization tracked by the Shipit instance: [6](#0-5) 

So the equality that should hold — "the organization that authenticated the request equals the organization owning the repository/commit being written" — is never enforced. `repository.owner.login` (used to pick the verification secret) and `repository.full_name`/`sha` (used to select what gets mutated) are independent fields inside the same attacker-controlled JSON body; nothing ties them together besides an honest GitHub server. Any tenant that legitimately knows one organization's `webhook_secret` (i.e., any org admin in a multi-org Shipit deployment, or anyone who can send a request with a valid signature for at least one configured org) can craft a payload that is signed correctly for their own org but whose `repository.full_name`/`sha` targets a completely different org's stack or commit.

### Impact Explanation
This allows cross-repository/cross-organization writes:
- `StatusHandler` lets a request validly signed with *any one* configured organization's `webhook_secret` create/forge a commit `Status` (`create_status_from_github!`) for **any** commit `sha` tracked anywhere in the Shipit instance, regardless of which org/repo it belongs to. Forged "success" statuses can satisfy `ci.require` checks that gate deploys and the merge queue, leading to an unauthorized deploy or merge of unreviewed code — matching the report's Critical/High bucket ("unauthorized deploy, rollback or merge", "cross-repository writes").
- `PushHandler`/`PullRequest` handlers resolve the target stack from `repository.full_name`, which is likewise not checked against the org that actually verified the signature, allowing a tenant of org A to trigger `GithubSyncJob`, archive/unarchive review stacks, or otherwise mutate stacks belonging to org B as long as the payload passes org A's signature check.

### Likelihood Explanation
Exploitability requires only that the attacker legitimately controls (or knows) the `webhook_secret` for at least one organization configured in the shared Shipit instance's `config/secrets.yml` (a normal, low-privilege tenant in the documented multi-org setup), and no other credential (no `ApiClient` token, no session, no GitHub App private key) is needed to hit `POST /webhooks`. This satisfies the "unprivileged attacker" bar for the analog scan since a tenant org admin is not a Shipit-privileged account and has no cross-org authorization.

### Recommendation
Bind the acted-upon resource to the organization that verified the signature: after `verify_signature` succeeds, pass the verified organization through to `Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization:) }`, and have `Handler#stacks` / `StatusHandler#process` filter by `stack.repository.owner == verified_organization` (or equivalent) before performing any lookup or mutation, rather than trusting `repository.full_name`/`sha` alone.

### Proof of Concept
1. Deploy Shipit configured for two GitHub organizations, `orgA` and `orgB`, each with distinct `webhook_secret`s (per `docs/setup.md`'s "Using Multiple Github Applications"), each tracking their own stacks/commits.
2. As the (low-privileged, tenant) admin of `orgA`, who legitimately knows `orgA`'s `webhook_secret`, craft a `status` event payload:
```json
{
  "sha": "<commit-sha-belonging-to-orgB-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, body)>` and POST it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` looks up `repository_owner` = `"orgA"`, fetches `orgA`'s `webhook_secret`, and the signature check passes (it was genuinely signed with `orgA`'s secret).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the `orgB` commit by SHA alone — and calls `create_status_from_github!`, forging a green CI status on an `orgB` commit that `orgA` has no legitimate authority over, potentially unblocking a deploy/merge in `orgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
