### Title
CCMenu API endpoint lets a stack-scoped ApiClient token read the state of any other stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` fetches the target `Stack` directly by param, bypassing the stack-scoping enforcement that every other `Api::BaseController` subclass relies on. This breaks the binding "the stack a token authorizes == the stack the endpoint touches": an `ApiClient` created with a `stack_id` restriction (via `Shipit::CCMenuUrlController` or an operator-restricted token) can be replayed with an arbitrary `stack_id` to read any stack's build/deploy status.

### Finding Description
In `Shipit::Api::BaseController`, stack access is meant to be constrained to the stacks an `ApiClient` is authorized for: [1](#0-0) 

`stacks` restricts the queryable set to `current_api_client.stack_id` when the client is scoped to a specific stack, and `stack` looks up the requested `stack_id` param only within that restricted scope, i.e. `stack ∈ authorized_stacks(token)`.

`Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly on the `Stack` model, with no reference to `current_api_client.stack_id`. The only check performed is a permission-name check (`require_permission :read, :stack`), which validates that the token holds the *permission string* `read:stack`, but never validates *which* stack the token is scoped to: [3](#0-2) 

So the equality that should hold — `stack_id` param ∈ `{token.stack_id}` when the token is stack-scoped — is broken; any `stack_id` value is accepted as long as it's a syntactically valid stack.

This is exactly analogous to the report's bug class: a value that is verified/authorized in one dimension (the client has the `read:stack` permission) is silently substituted with unchecked data from another source (an arbitrary `stack_id` param) when the privileged action (rendering CI status) is actually performed — mirroring how the rollover fee is correctly *calculated* but never actually routed to the vault that is supposed to gate its use.

`CCMenuUrlController` demonstrates the intended, narrower scope of such tokens — creating an `ApiClient` scoped to a single stack for exactly this XML feed: [4](#0-3) 

That scoping is meaningless because `CCMenuController#stack` doesn't honor it.

### Impact Explanation
Any holder of a `read:stack`-scoped `ApiClient` token — even one that was created/intended to be restricted to a single stack via `stack: id` — can query `GET /api/stacks/:stack_id/ccmenu.xml` for any other stack in the Shipit instance and obtain: stack `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl`, as shown by the rendered attributes in the controller test: [5](#0-4) 

This is an unauthenticated-for-that-resource read of stack state (deploy/lock status, latest build info) for stacks the token was never authorized to see — matching the in-scope High-impact category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
High. Exploitation requires only possession of any valid `ApiClient` token carrying the `read:stack` permission (even one deliberately scoped to a single stack, e.g. via the CCMenu widget URL feature), and knowledge/guessing of another stack's `owner/name` param — stack names are often predictable or discoverable (e.g. via the public UI, `Stack#to_param` = `owner/repo/environment`). No signature, secret, or elevated privilege is needed beyond having one legitimately-issued, narrowly-scoped token.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup from `BaseController` instead of querying `Stack` directly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This restores the invariant that a stack-scoped `ApiClient` can only ever resolve `stacks` within its authorized scope, consistent with every other API controller.

### Proof of Concept
1. Create (or obtain) an `ApiClient` scoped to a single stack, e.g. via `CCMenuUrlController#fetch` for `stack_a` (`permissions: ['read:stack']`, `stack_id: stack_a.id`), yielding `token`.
2. As this token holder, issue: `GET /api/stacks/<owner>/<stack_b_repo>/<env>/ccmenu.xml?token=<token>` where `stack_b` is a different, unauthorized stack.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unconditionally, the request succeeds (`200 OK`) and returns `stack_b`'s `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl`, even though the token was only ever authorized for `stack_a`.

Note: I was unable to execute this against a running instance (no filesystem/terminal access in this mode); the analysis is based on static review of the cited controller, model, and test code, which confirms the missing scoping check.
