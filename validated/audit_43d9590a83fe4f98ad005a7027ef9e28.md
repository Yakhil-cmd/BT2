### Title
Whale-scale market state drives a permanent `i128` overflow panic in accrual, freezing all funds in the market - (File: common/src/rates/simulate.rs)

### Summary
The CVE class is "crafted input triggers memory corruption / crash". On Soroban there is no raw memory corruption, but the equivalent data-space corruption primitive exists: a single unprivileged whale can drive a market into a state where the unscaling multiplication `scaled * index` can no longer be represented in `i128`. Every state-mutating entrypoint accrues first, and accrual panics with `GenericError::MathOverflow` inside `scaled_to_original`, so the panic is permanent and unrecoverable. The index cap (`MAX_BORROW_INDEX_RAY` / `MAX_SUPPLY_INDEX_RAY` = 10³⁶) never engages because the value product overflows at ~170× the index while the cap sits at 10⁹×.

### Finding Description
`accrue_step` in `common/src/rates/simulate.rs:60-61` computes `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)` on every accrual step. `scaled_to_original` (`common/src/rates/scaling.rs:14`) is `Ray::mul`, which panics with `MathOverflow` when `scaled * index / RAY` exceeds `i128` (`common/src/math/fp.rs:12-25`, `common/src/math/fp_core.rs:108-118`). `update_borrow_index` only caps the index at `MAX_BORROW_INDEX_RAY = 10³⁶` (`common/src/rates/index.rs:13-19`), i.e. index ≤ 10⁹·RAY, while the i128 ceiling (~1.7e38) is crossed when `scaled · index / RAY > 1.7e38`. For `scaled = 10³⁶` raw ray (1 billion whole tokens at 18 decimals) the cliff is index ≈ 170×, versus a cap of 10⁹× — the cap cannot prevent the overflow.

`global_sync` (`contracts/pool/src/interest.rs:20-33`) runs `accrue_chunk` → `accrue_step` at the head of every pool verb, so once `borrowed · borrow_index` exceeds `i128` there is no entrypoint that bypasses accrual: `withdraw`, `repay`, `borrow`, `liquidate`, `clean_bad_debt`, `update_indexes` all trap. The borrow index is monotone (`update_borrow_index` never decreases it) and `borrowed` (debt shares) cannot be burned without a repay — which itself panics. The freeze is therefore permanent, confirmed by the in-repo test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`), which asserts `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`.

An unprivileged attacker reaches the state by calling `supply`/`borrow` on a steep-curve market at high utilization and waiting: debt compounds faster than supply (`update_borrow_index` grows the debt value while `update_supply_index` growth saturates at the same 10³⁶ cap but stays below it in practice), so the debt-value product climbs superlinearly. On the in-repo XLM stress curve (175% max rate, optimal 75%) the index grows ~170× in a few years at 98% utilization, and a smaller position (e.g. 10⁶ whole tokens at 18 decimals = 10³³ raw ray) still crosses at index ≈ 1.7e5× — far below the 10⁹× cap. Caps are the only throttle: with `borrow_cap`/`supply_cap` near `max_cap_for_decimals` the attacker alone can hold utilization pinned.

### Impact Explanation
Permanent freezing of funds and protocol insolvency for the affected market book: all supplier deposits and all borrower collateral backing that debt become permanently unrecoverable, and bad debt can never be cleaned (`clean_bad_debt` accrues first and panics). Impact persists across the protocol because the hub book is poisoned, not just one position.

### Likelihood Explanation
Requires a whale-scale position (large absolute token amount at high decimals) and sustained high utilization over a multi-year compounding horizon, plus admin-set caps high enough to admit the position. No privileged call, leaked key, or oracle manipulation is needed — only `supply`, `borrow`, and time via `update_indexes`. Likelihood is therefore moderate-to-low but nonzero on any market whose caps and rate curve admit it; Medium severity overall.

### Recommendation
Bound the value product, not just the index: enforce `scaled · index ≤ i128::MAX` as an accounting invariant (e.g. cap `supplied`/`borrowed` share totals as a function of the current index in `pool::cache`, or clamp market caps to `i128::MAX / index` when `update_account_threshold`/listing restamps config). Alternatively, make `scaled_to_original` saturate (as `mul_div_floor_saturating` already does for `calculate_scaled_cap`) so accrual freezes index growth rather than trapping every verb.

### Proof of Concept
Reproduced by the existing harness test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361`: supply `10⁹ × 10¹⁸` base units of an 18-decimal asset, borrow 98% of it against collateral in a second market, advance the ledger in yearly steps calling `update_indexes`; after the borrow index passes ~170×, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all return `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`, demonstrating the cap cannot rescue the frozen book.
