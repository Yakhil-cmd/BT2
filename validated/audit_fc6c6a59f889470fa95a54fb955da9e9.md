## Analog Vulnerability Found

### Title
Webhook signature is verified against `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field, letting an authenticated organization forge writes against a repository/stack it does not own - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of H-05: the field that is checked at the validation boundary (`repository.owner.login`, used to pick which organization's `webhook_secret` verifies the HMAC) is different from the field that is actually trusted downstream to select the target of the write (`repository.full_name`). Nothing enforces that these two fields inside the same signed payload refer to the same repository the sender is authorized to speak for from Shipit's perspective, when multiple organizations are configured with independent secrets.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization config (and therefore which `webhook_secret`) to use for HMAC verification purely from `repository.owner.login` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

Shipit supports multiple GitHub organizations, each with its own independently configured `webhook_secret`: [3](#0-2) 

Once the signature check passes (i.e., the request was signed with *some* organization's configured secret), the request is dispatched to handlers that determine which `Repository`/`Stack` to mutate using a *different* payload field: `repository.full_name` (or `params.dig('repository','full_name')`), not `repository.owner.login`: [4](#0-3) [5](#0-4) 

The binding that should hold is:
`organization whose secret authenticated the request == owner segment of the repository the handler mutates`

But the code never checks this equality — `repository_owner` (used only to select the HMAC key) and `repository.full_name` (used to select the target `Repository`/`Stack`) are two independent fields inside the same JSON body, and only the second one drives what gets written.

Concretely: if Shipit is configured for multiple organizations `org-a` and `org-b` (each with its own `github.<org>.webhook_secret`, as shown in `Shipit.github_app_config`), and an attacker who controls (or has compromised) the GitHub App/webhook secret for `org-a`'s installation sends a POST to `/webhooks` with:
- `repository.owner.login = "org-a"` (so `verify_signature` picks `org-a`'s secret, and the attacker signs the raw body correctly with that known secret)
- `repository.full_name = "org-b/victim-repo"` (crafted to point at a stack belonging to a completely different, unrelated organization)

`verify_signature` succeeds because the HMAC matches `org-a`'s secret over the (attacker-fully-controlled) raw body. The handler layer then looks up `Repository.from_github_repo_name("org-b/victim-repo")` and processes the event against that stack — e.g. `PushHandler` triggers `stack.sync_github`, or `PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` create/archive/unarchive review stacks, or `StatusHandler` writes a commit status — none of which re-validate that `org-b` is the organization whose secret actually authenticated the request.

### Impact Explanation
This breaks the trust boundary between "GitHub App installation that signed this webhook" and "repository/stack the event is applied to." An attacker who only controls one organization's webhook secret (e.g. through leakage of a single org's secret, or by being a legitimate admin of `org-a` that is also onboarded onto the same Shipit instance) can forge state changes — archiving/unarchiving review stacks, injecting arbitrary commit statuses via `StatusHandler`/`Commit#create_status_from_github!`, or triggering `sync_github`/deploy-adjacent side effects — against stacks belonging to `org-b`, which they have no legitimate access to. This is a cross-repository write achieved purely by exploiting the mismatch between the field used for authentication and the field used for authorization of the target resource, matching the Critical "cross-repository writes" impact category.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (documented, supported configuration via `github.<org>.webhook_secret`) and possession of a valid webhook secret for at least one onboarded organization — no repository write access, no Shipit session, and no privileged Shipit account are needed. Given that Shipit is explicitly designed to host many organizations/repositories behind a single instance, and each org's secret is independently distributed to that org's GitHub App configuration, the likelihood that an org's secret is available to a party that is not authorized to affect other orgs' stacks is realistic.

### Recommendation
After `verify_signature` succeeds, re-derive the organization actually authorized to speak for the target repository from `repository.full_name`'s owner segment (or from the resolved `Repository#owner`) and assert it equals the organization whose secret verified the signature (`repository_owner`). Reject the webhook if they differ, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) and return unless verified

  target_owner = params.dig('repository', 'full_name')&.split('/')&.first
  head(422) if target_owner.present? && target_owner.casecmp(repository_owner).nonzero?
end
```

### Proof of Concept
1. Configure Shipit with two organizations, each with its own `github.<org>.webhook_secret` (per `docs/setup.md` / `Shipit.github_app_config`).
2. Onboard `org-a/repo-a` and `org-b/victim-repo` as stacks.
3. As holder of `org-a`'s webhook secret, POST to `/webhooks` with header `X-Github-Event: pull_request` (or `push`, `status`) and a JSON body where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"`, correctly HMAC-signed with `org-a`'s secret.
4. `WebhooksController#verify_signature` succeeds (it only checked `org-a`'s secret against `org-a`'s claimed owner).
5. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler` (or `PushHandler`/`StatusHandler`) resolves `Repository.from_github_repo_name("org-b/victim-repo")` and mutates `org-b`'s stack — a write the `org-a` secret holder should never be able to trigger.

*Note: I was not able to execute this against a running multi-org Shipit instance to observe the live HTTP response; the analysis is based on tracing the exact code paths in `webhooks_controller.rb`, `handler.rb`, and the individual handler classes cited above.*

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
