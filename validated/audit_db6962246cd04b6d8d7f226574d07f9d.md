### Title
Cross-repository webhook forgery via unbound `Repository.from_github_repo_name` lookup - ([File: app/models/shipit/repository.rb])

### Summary
`Repository.from_github_repo_name` resolves a `Repository` purely from the unsigned-relative-to-owner `repository.full_name` string in the webhook JSON body, with no check that its `owner` matches the `repository_owner` (`repository.owner.login` / `organization.login`) that was actually used to verify the HMAC signature in `WebhooksController#verify_signature`. Any attacker who legitimately controls one GitHub organization/repo onboarded onto the Shipit instance can sign an arbitrary payload with their own webhook secret while setting `repository.full_name` to a victim organization's repo, causing pull-request handlers to create/archive review stacks and mutate state for a repository they do not own.

### Finding Description
Broken binding (should hold, does not):
`Repository.from_github_repo_name(payload['repository']['full_name']).owner == repository_owner` (the value verified against the correct webhook secret in `verify_signature`).

Code path:
- `WebhooksController#verify_signature` selects the GitHub App/secret solely from `repository_owner`, derived from `params.dig('repository','owner','login')` (fallback `organization.login`), and validates `X-Hub-Signature` against that org's `webhook_secret`: [1](#0-0)  and the owner extraction: [2](#0-1) .
- `repository.owner.login` and `repository.full_name` are two independent JSON fields in the same attacker-controlled body — nothing forces them to be consistent once the request is crafted by hand rather than emitted by GitHub itself.
- Handlers (e.g. `OpenedHandler`, `ClosedHandler`, `LabelCapturingHandler`) resolve the `Repository` exclusively from `params.repository.full_name` via `Shipit::Repository.from_github_repo_name`, e.g. [3](#0-2)  and [4](#0-3) , and the generic base handler helper does the same: [5](#0-4) .
- `Repository.from_github_repo_name` performs a plain, case-normalized `find_by(owner:, name:)` with no cross-check against any verified identity: [6](#0-5) .

Root cause: signature verification authenticates "this body was sent using organization X's secret," but nothing ties the *content* of `repository.full_name` used for the DB lookup to organization X. An attacker who legitimately installs/configures the Shipit GitHub App on their own organization (a normal, permitted action for any org admin in a multi-tenant Shipit deployment) knows that organization's `webhook_secret` (`GitHubApp#verify_webhook_signature`, `@webhook_secret = @config[:webhook_secret]`, see [7](#0-6) ). They can then POST directly to `/webhooks` with a hand-crafted JSON body where `repository.owner.login = "attacker-org"` (so `verify_signature` picks their own, known secret and succeeds) but `repository.full_name = "victim-org/victim-repo"` (so the handler resolves and mutates the victim's `Repository`/`stacks`/`review_stacks`).

Exploit flow example (pull_request `opened`):
1. Attacker computes `sha1=HMAC(attacker_org_webhook_secret, body)`.
2. Body: `{"action":"opened","repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"}, "pull_request": {...}, "sender": {...}}`.
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and the signature checks out — request passes.
4. `OpenedHandler#repository` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` → the real victim `Repository` row, and `ReviewStackAdapter.find_or_create!` provisions/mutates a review stack scoped to the victim repo, entirely under attacker control of PR number/branch/labels.

Existing guards fail to close this because: `drop_unhandled_event` only filters on `X-Github-Event` header, `ExplicitParameters` only validates shape/types of fields (not cross-field consistency), and `verify_signature` validates the signature against the org named in the payload rather than the org actually referenced by `full_name`.

### Impact Explanation
An attacker who controls one onboarded organization can forge webhook events attributed to a different tenant's repository, causing Shipit to create, label-track, or archive review stacks for repositories/stacks they never authenticated against. This is a payload for one repository mutating another's stack/task/review state — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The attack is repeatable against any repository already registered in Shipit (`Repository` row with known owner/name), and the blast radius spans all tenants sharing the same Shipit instance, since `Repository` records are global and not scoped to the verifying organization.

### Likelihood Explanation
Preconditions: the attacker must control (or have webhook credentials for) at least one organization/repo that is configured in Shipit's github app config (so `Shipit.github(organization: repository_owner)` resolves without raising `GithubOrganizationUnknown`), and the target victim repository must already exist as a `Repository` row in Shipit with a known lowercase `owner/name`. In any multi-tenant Shipit deployment (the architecture explicitly supports multiple organizations via `Shipit.github(organization:)`), this is a realistic scenario — any legitimately onboarded team/org is effectively "trusted" to guess/target any other team's repo names, which are typically public/well-known. Attacker cost is a single crafted HTTP POST with a correctly computed HMAC using their own known secret; no privileged credentials or secret material belonging to the victim are required.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), enforce that the owner embedded in `payload.dig('repository','full_name')` matches `repository_owner` (case-insensitively) before dispatching to handlers, rejecting (422) any mismatch. Additionally/alternatively, change `Repository.from_github_repo_name`-based resolution in handlers to accept and validate the verified `repository_owner` alongside `full_name`, and scope the `find_by` to that owner explicitly rather than trusting the free-form `full_name` field alone.

### Proof of Concept
Minitest plan (`test/models/shipit/repository_test.rb` and `test/controllers/webhooks_controller_test.rb`):
1. Create `Repository` `owner: "victim-org", name: "victim-repo"`.
2. Configure two orgs in `Shipit.github_apps`/test config: `attacker-org` (webhook secret `S_a`) and `victim-org` (webhook secret `S_v`), `S_a != S_v`.
3. Build a webhook body: `repository.owner.login = "attacker-org"`, `repository.full_name = "victim-org/victim-repo"`, valid `pull_request` fields, `action: "opened"`.
4. Compute `X-Hub-Signature = "sha1=" + HMAC-SHA1(S_a, body)`.
5. POST to `/webhooks` with header `X-Github-Event: pull_request`.
6. Assert response is `200 OK` (i.e., `verify_signature` passed using `attacker-org`'s secret) — asserting the left side of the binding: `repository_owner == "attacker-org"`.
7. Assert `Repository.from_github_repo_name("victim-org/victim-repo").owner == "victim-org"` was the record acted upon (e.g., assert a `ReviewStack` was created/archived scoped to the `victim-org/victim-repo` `Repository`), demonstrating `resolved_repository.owner ("victim-org") != repository_owner ("attacker-org")` — proving the binding is currently violated.
8. Unit-level companion test on `Repository.from_github_repo_name` with crafted `full_name` variants (extra slashes, mixed case, whitespace) confirming normalization behavior, paired with an assertion that no caller cross-checks the returned `owner` against any verified identity.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
