### Title
`pox_lock_update_v5` never rejects a `stake-update` response whose `unlock-burn-height` rolls the lock's unlock schedule backward, unlike `pox_rollover_v5` - ([File: pox-locking/src/pox_5.rs])

### Summary
`pox_lock_update_v5` (handling pox-5's `stake-update`) calls `snapshot.update_unlock_v5(unlock_burn_height)` and only validates `total_amount < new_total_locked` and `bal.amount_locked() > new_total_locked` afterward — it never checks that `unlock_burn_height` is strictly greater than the account's current `bal.unlock_height()`. Its sibling function `pox_rollover_v5`, which handles the analogous `stake`/`register-for-bond` roll-over case, explicitly enforces `unlock_burn_height <= bal.unlock_height() => Err(PoxInvalidUnlockHeight)`. This asymmetry means any legitimate `stake-update` call whose contract-computed `unlock-burn-height` happens to be lower than the account's existing (already extended/committed) unlock height will silently roll the unlock schedule backward instead of being rejected.

### Finding Description
The broken invariant is: **`new_unlock_height` (as passed to `pox_lock_update_v5`) must be `>= bal.unlock_height()` before the call**, exactly as `pox_rollover_v5` enforces for the roll-over path. In `pox_lock_update_v5`: [1](#0-0) 

`snapshot.update_unlock_v5(unlock_burn_height)` is applied unconditionally before any comparison against the account's prior unlock height, and no code path anywhere in this function checks `unlock_burn_height` against `bal.unlock_height()`. Contrast with `pox_rollover_v5`: [2](#0-1) 

which explicitly guards `unlock_burn_height <= bal.unlock_height()` with `PoxInvalidUnlockHeight` before calling `set_lock_v5`.

`handle_stake_lockup_update_pox_v5` is the dispatch point that funnels `stake-update`'s Clarity response straight into `pox_lock_update_v5` with the `unlock-burn-height` value taken verbatim from the parsed tuple, with no additional Rust-side monotonicity check: [3](#0-2) 

The Rust locking layer is documented as trusting the pox-5 contract's gating ("the contract is responsible for gating the roll-over ... if the contract returns ok, this handler trusts the call is legitimate" — comment above `handle_lockup_pox_v5`), but for `stake-update` specifically there is no equivalent monotonicity enforcement even as a defense-in-depth invariant check, unlike the parallel `pox_rollover_v5` path.

I was not able to fully trace pox-5.clar's `stake-update` implementation within the available tool budget to confirm definitively whether the Clarity contract itself can ever compute (and thus echo back through this response tuple) an `unlock-burn-height` lower than the staker's current locked `unlock-burn-height` (e.g., if `stake-update`/extend semantics allow requesting a smaller number of additional cycles than were already committed by a prior `stake`/`stake-update` call). If that Clarity-side computation is possible under any code path — buggy or otherwise — this Rust function provides no backstop and will apply it.

### Impact Explanation
If reachable, the impact is a self-inflicted (or signer-manager-triggered) early unlock of the staker's own already-locked STX relative to the height originally committed by an earlier `stake`/`stake-update` call. Because reward-cycle signer weight and reward slots for later cycles are provisioned assuming the STX remains locked until the previously committed (later) height, an early rollback of the unlock height lets the staker withdraw funds while signing weight/reward-slot allocations for those future cycles are still outstanding — matching "signing weight or reward slots exceeding locked value" (High) or, if it also lets funds be withdrawn ahead of a cycle-boundary commitment that other protocol accounting depends on, "unlocking value never locked" relative to the committed schedule (Critical). This is repeatable per call to `stake-update` for as long as the contract-side condition producing the lower height can be triggered.

### Likelihood Explanation
Likelihood depends entirely on whether pox-5.clar's `stake-update` entry point can ever compute/return an `unlock-burn-height` less than the caller's existing `bal.unlock_height()`. I could not confirm this from the Clarity source within the available investigation. The Rust-level guard that would make this moot regardless of contract behavior (the same check present in `pox_rollover_v5`) is absent from `pox_lock_update_v5`, so this is a defense-in-depth gap: it does not by itself prove exploitability, only that the safety net `pox_rollover_v5` has is missing from `pox_lock_update_v5`.

### Recommendation
Add the same monotonicity guard to `pox_lock_update_v5` that already exists in `pox_rollover_v5`: before (or immediately after) calling `snapshot.update_unlock_v5(unlock_burn_height)`, compare `unlock_burn_height` against the account's current `bal.unlock_height()` (captured before the update) and return `LockingError::PoxInvalidUnlockHeight` if `unlock_burn_height <= previous_unlock_height`. This makes the Rust-level invariant hold independent of pox-5.clar's contract logic, matching the existing defense-in-depth pattern in `pox_rollover_v5`.

### Proof of Concept
Rust test in `pox-locking/src/pox_5.rs` test module:
1. Fund an account, call `pox_lock_v5` with `unlock_burn_height = 20_000`.
2. Call `pox_lock_update_v5(db, &staker, unlock_burn_height = 15_000, new_total_locked = <same or higher amount>)`.
3. Assert equality before: `snapshot.canonical_balance_repr()?.unlock_height() == 20_000`.
4. Current behavior: the call succeeds and returns `Ok(balance)` with `unlock_height() == 15_000` — assert this to demonstrate the rollback occurs (`assert_eq!(out_balance.unlock_height(), 15_000)`), and note this contradicts the equality asserted in step 3 (unlock height decreased instead of `Err(PoxInvalidUnlockHeight)` as `pox_rollover_v5` would produce for the identical scenario — write the same test calling `pox_rollover_v5` with `unlock_burn_height = 15_000 <= bal.unlock_height() = 20_000` and confirm it returns `Err(LockingError::PoxInvalidUnlockHeight)`, showing the asymmetry directly in a single test file).

Further Clarity-side verification of whether `stake-update` in `pox-5.clar` can produce such an inverted `unlock-burn-height` was not completed and would be required to fully confirm end-to-end reachability from an unprivileged caller.
