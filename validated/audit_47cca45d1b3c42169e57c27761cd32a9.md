### Title
Cross-tenant Stack sync trigger via decoupled webhook signature org and payload `repository.full_name` - (`app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`)

### Summary
In multi-org Shipit deployments (`config/secrets.yml` `github:` keyed by organization, e.g. `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects the HMAC secret solely from `params.dig('repository','owner','login')` while `Handler#stacks`/`PushHandler#process` resolve the affected `Stack` solely from `payload.dig('repository','full_name')`. Nothing binds these two values together, so a payload signed with org A's webhook secret can name org B's repository in `repository.full_name` and still pass verification, causing `GithubSyncJob` to be enqueued for org B's `Stack`.

### Finding Description
The claimed binding is: `repository_owner` (used in `Shipit.github(organization: repository_owner)` at `app/controllers/shipit/webhooks_controller.rb:25`, where `repository_owner` = `params.dig('repository','owner','login')`, line 61) **==** the owner encoded in `payload.dig('repository','full_name')` (used at `app/models/shipit/webhooks/handlers/handler.rb:33-37` via `Repository.from_github_repo_name(repository_name)`).

Tracing the code confirms these two reads are independent JSON keys with no cross-validation:
- `verify_signature` picks the `GitHubApp` (and thus `webhook_secret`) using `repository.owner.login` only [1](#0-0) , with `repository_owner` defined at [2](#0-1) .
- `Shipit.github(organization:)` in multi-org mode looks up the config bucket keyed by that organization name [3](#0-2) , confirmed as legitimate multi-tenant deployment pattern (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md:182-209`).
- `PushHandler#process` calls `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(...) }` [4](#0-3) , where `stacks` is resolved from `payload.dig('repository','full_name')` via `Repository.from_github_repo_name` — a completely separate JSON field from the one used for signature-secret selection [5](#0-4) .

Root cause: the signature-verification step authenticates "this payload was signed by whoever holds org X's webhook secret," but the handler layer trusts a completely different, attacker-supplied field (`repository.full_name`) to decide which `Stack`/`Repository` row to mutate. There is no assertion anywhere that `repository.full_name`'s owner segment equals `repository.owner.login`.

Exploit flow: an operator/holder of organization "attacker-org"'s legitimately configured webhook secret (a valid multi-tenant participant on the same Shipit instance) crafts a raw JSON push payload with `repository.owner.login = "attacker-org"` (so the correct, known secret is selected and HMAC passes) but `repository.full_name = "victim-org/app"` and `ref = "refs/heads/master"`, `after = <attacker-chosen sha>`. `verify_signature` passes because the HMAC is computed over the attacker-controlled raw body with the attacker's own known secret. `PushHandler#process` then resolves `victim-org/app`'s `Repository`/`Stack` and enqueues `GithubSyncJob` for it with the attacker-chosen `expected_head_sha`.

Existing guards do not stop this: `verify_signature` never re-checks `repository.full_name` against `repository.owner.login`; `drop_unhandled_event` only filters by event type; `ExplicitParameters` schema for `PushHandler` only requires `ref` and `after` present, not any repository/owner constraint [6](#0-5) ; and `Repository.from_github_repo_name` performs no ownership cross-check with the signing org [7](#0-6) .

### Impact Explanation
The immediate effect is enqueuing `GithubSyncJob` for a repository/stack that did not authenticate the request — the victim's `Stack` id is written into a job queue by a payload authenticated only by org A's secret [8](#0-7) . When the job runs, it uses the **victim stack's own** `github_api`/credentials (`stack.github_commits`, `stack&.github_api` inside `GithubSyncJob`) to fetch commits from the victim's real GitHub repo [9](#0-8) , so no victim secret is exfiltrated and no forged commit content is injected — the job just performs a legitimate resync using the victim's actual GitHub state, but it is triggered by an unauthenticated (with respect to the victim) actor. This matches "a payload for one repository mutating another's stack" (Critical bucket), though the concrete write is a forced resync job, not data exfiltration or command execution; the practical blast radius is a forced-refresh / minor DoS-adjacent nuisance against an arbitrary victim stack anywhere on the same multi-tenant Shipit instance, repeatable at will by any tenant sharing the instance.

### Likelihood Explanation
This only applies to **multi-org** Shipit deployments (`github:` keyed by organization names, as documented in `docs/setup.md:182-209` and exercised in `test/dummy/config/secrets_double_github_app.yml`). It requires the attacker to be a legitimate tenant on that same instance holding a valid webhook secret for their own org bucket — not a fully external, secret-less attacker. In the common single-org schema (`github_default_organization` nil), `Shipit.github(organization: repository_owner)` ignores the passed organization entirely and always uses the single global secret [10](#0-9) , so the attack does not apply there because there is only one secret and only one org's repos are trackable anyway. Given a multi-org setup, the attack is trivial and repeatable: one HTTP POST to `/webhooks` per target stack, cost is one HMAC computation with a secret the attacker already legitimately possesses.

### Recommendation
In `Handler#stacks` (or `PushHandler#process`), verify that the resolved `Repository`'s `owner` matches the organization whose secret verified the webhook signature (e.g., pass the verified `repository_owner`/organization through to the handler and assert `repository_name.downcase.split('/').first == verified_organization.downcase`), rejecting/no-oping the event otherwise. Alternatively, derive the signature-verification organization from the same `repository.full_name` field used by the handlers instead of `repository.owner.login`, so both reads are guaranteed to agree.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":push signed by attacker-org but targeting victim-org repo enqueues victim's stack" do
  # multi-org secrets fixture: attacker-org and victim-org each with distinct webhook_secret
  # (mirrors test/dummy/config/secrets_double_github_app.yml)
  victim_stack = shipit_stacks(:shipit) # repository.full_name == "victim-org/app", branch "master"

  request.headers['X-Github-Event'] = 'push'
  payload = JSON.parse(webhooks_payload(:push_master))
  payload['repository']['owner']['login'] = 'attacker-org'       # selects attacker-org's secret
  payload['repository']['full_name']      = 'victim-org/app'     # targets victim stack
  payload['ref'] = 'refs/heads/master'
  body = payload.to_json
  signature = sign_with_secret(body, attacker_org_webhook_secret) # attacker knows their own secret

  request.headers['X-Hub-Signature'] = signature

  # Equality under test:
  #   verified_org  = params.dig('repository','owner','login')       => "attacker-org"
  #   targeted_repo_owner = params.dig('repository','full_name').split('/').first => "victim-org"
  # BEFORE fix: verified_org != targeted_repo_owner, yet job is enqueued for victim stack.
  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: payload['after']]) do
    post :create, body:, as: :json
  end
  # AFTER fix: expect no job enqueued (or 422/dropped) when verified_org != targeted_repo_owner.
end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end

    def append_commit(gh_commit)
      stack.commits.create_from_github!(gh_commit)
    end

    def fetch_missing_commits(&block)
      commits = []
      github_api = stack&.github_api
      iterator = Shipit::FirstParentCommitsIterator.new(github_api:, &block)
