### Title
Signature verification keyed on `repository.owner.login` while stack resolution keyed on `repository.full_name` allows cross-repository stack mutation - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates the inbound webhook against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from `params.dig('repository','owner','login')`. `Handler#stacks`/`#repository_name`, used by every handler including `PushHandler`, instead resolve the target repository from the independent field `payload.dig('repository','full_name')`. Because these two fields are never cross-checked, an attacker who controls a GitHub org/repo can register that org's webhook secret with Shipit, forge a payload where `repository.owner.login` matches their own org (so signature verification passes) but `repository.full_name` names a victim's repo, and cause `PushHandler#process` to enqueue `stack.sync_github` against the victim's real `Stack`.

### Finding Description
The broken binding is: `repository_owner` (verified identity) = `params.dig('repository','owner','login')` MUST equal `repository_name.split('/').first` (mutation target owner) = `payload.dig('repository','full_name').split('/').first`, but the code never enforces this equality.

Path:
1. `WebhooksController#verify_signature` [1](#0-0)  computes `repository_owner` via [2](#0-1)  and calls `Shipit.github(organization: repository_owner)` to verify `X-Hub-Signature` using that organization's own `webhook_secret`.
2. If the attacker owns `attacker-org` in Shipit (a legitimate, unprivileged GitHub organization/app installation configured with its own webhook secret), a payload with `repository.owner.login = "attacker-org"` verifies successfully using the attacker's own secret — no victim secret is needed.
3. `WebhooksController#create` then dispatches to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [3](#0-2) .
4. `Handler#repository_name` reads `payload.dig('repository', 'full_name')` [4](#0-3)  — a separate field from `repository.owner.login`, and `#stacks` resolves `Repository.from_github_repo_name(repository_name)` [5](#0-4) .
5. `Repository.from_github_repo_name` splits `full_name` on `/` and does a plain DB lookup with no relation to the verified org [6](#0-5) .
6. `PushHandler#process` then runs `stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }` [7](#0-6)  against the victim's actual `Stack` record (owned by `victim-org/victim-repo`), not anything belonging to the attacker.

No existing guard closes this gap: `ExplicitParameters` schema on `PushHandler` only requires `ref`/`after` presence and does not validate `repository.full_name` against `repository.owner.login`; `drop_unhandled_event` only checks event type presence; `Repository` model validations constrain `owner`/`name` format but do not tie a repository record's ownership to the webhook's verified signer at request time. The two fields (`repository.owner.login` and `repository.full_name`) are genuinely independent JSON keys in a single GitHub webhook payload and both are fully attacker-controlled in the raw POST body (the attacker doesn't need real GitHub cooperation — they craft the POST directly). This matches the impact category "a payload for one repository mutating another's stack, commit, task or team."

### Impact Explanation
An attacker who has a Shipit-registered GitHub org (their own, with its own `webhook_secret`) can send arbitrary `POST /webhooks` push events that pass signature verification under their own org, but whose `repository.full_name` names any other Shipit-tracked repository/stack. This lets them enqueue `GithubSyncJob`/`stack.sync_github` (and by the same mechanism, any other handler keyed off `Handler#stacks`/`repository_name` — e.g. `pull_request` label/closed/opened handlers) against a victim stack they do not own. This is repeatable against any repository tracked by the Shipit instance, for any branch name, at will, and constitutes cross-tenant/cross-repository state mutation without the victim's authorization — Critical severity per the stated impact categories.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be a legitimate (even unprivileged) Shipit-registered GitHub organization/app owner able to receive a `webhook_secret` for their own org — a standard, self-service Shipit/GitHub-app installation, not a compromise of victim or platform secrets. They craft the raw JSON POST body themselves (no live GitHub interaction required), setting `repository.owner.login` to their own org login and `repository.full_name` to `"victim-org/victim-repo"`. The signature is computed with their own known secret. This is fully reproducible and low-cost.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), enforce that the owner segment of `repository.full_name` matches `repository.owner.login` (or organization.login) before dispatching to handlers, rejecting the request (e.g., `head(422)`) on mismatch. Alternatively, derive `repository_owner` from `repository.full_name`'s owner segment consistently in both the controller and `Handler`, so the same field is used for both authentication and stack resolution.

### Proof of Concept
Minitest plan (controller/integration test, no live GitHub):
```ruby
test "push webhook with mismatched owner.login and full_name mutates a different org's stack" do
  attacker_org = "attacker-org"
  victim_stack = shipit_stacks(:shipit) # some stack owned by repo "victim-org/victim-repo"
  Shipit.stubs(:github).with(organization: attacker_org).returns(
    stub(verify_webhook_signature: true)
  )

  payload = {
    ref: "refs/heads/#{victim_stack.branch}",
    after: "deadbeef",
    repository: {
      full_name: "victim-org/victim-repo",   # mutation target
      owner: { login: attacker_org }          # verified identity - MISMATCH
    }
  }

  assert_enqueued_with(job: GithubSyncJob, args: [victim_stack]) do
    post shipit.webhooks_path,
      params: payload.to_json,
      headers: { 'X-Github-Event' => 'push', 'X-Hub-Signature' => 'sha1=whatever', 'Content-Type' => 'application/json' }
  end

  assert_response :ok
end
```
Assert both sides of the binding explicitly: `payload.dig('repository','owner','login')` (`attacker-org`) is used for `Shipit.github(organization:)` in `verify_signature`, while `payload.dig('repository','full_name')` (`victim-org/victim-repo`) is used in `Handler#repository_name`/`#stacks` — showing they differ and that no code path rejects the mismatch, resulting in `GithubSyncJob` enqueued for the victim's stack.
