### Title
Stack-Scoped ApiClient Token Bypasses Stack Authorization in CCMenu API - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` accessor with an unscoped lookup, so an `ApiClient` token that is restricted to a single stack can nonetheless read the CCMenu build/deploy status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` implements stack authorization by scoping the queryable stacks to the calling `ApiClient`'s `stack_id` when the client is stack-scoped: [1](#0-0) 

Every other API controller (`StacksController`, `TasksController`, etc.) relies on this `stacks`/`stack` helper, so a token created with `stack: X` can only resolve stacks equal to `X`, enforcing the intended binding: *"the stack a token authorizes" == "the stack the request touches"*.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(...)`, so it resolves **any** stack in the database regardless of `current_api_client.stack_id`. Only the `read:stack` permission bit is checked via `require_permission :read, :stack` (`app/controllers/shipit/api/ccmenu_controller.rb:6`), which every stack-scoped client also carries by design (e.g., the `here_come_the_walrus` fixture, scoped to the `shipit` stack, has only `read:stack`: [3](#0-2)  ). Because `check_permissions!` only checks the operation/scope string and never compares against `stack_id`, this authorization decision is disconnected from the actual stack being fetched — this is the same class of bug as the Solidity report's ownership-parameter mismatch: the authorization check validates one identity/scope (`operation:scope` on the token) while the action is performed against a different, unchecked target (`params[:stack_id]`) that was never bound by the check.

### Impact Explanation
A stack-scoped, read-only `ApiClient` token — created for example via the CCMenu URL feature (`Shipit::CcmenuUrlController#client`, which creates tokens with only `read:stack` and no stack restriction shown to the end user) — can be replayed against `GET /api/*any_other_stack*/ccmenu.xml` to read the build/deploy status (last build status, last build label, last build time, activity, web URL) of stacks the token was never meant to access. This is an unauthenticated-for-other-stacks read of stack/deploy state, matching the High-impact category "unauthenticated read of stack state, task streams or deploy output" once any read-scoped credential for one stack is obtained, since the intended per-stack sandboxing is completely bypassed.

### Likelihood Explanation
Any stack-scoped `ApiClient` token normally used only for its own stack's CCMenu widget (a common, low-privilege, non-sensitive credential handed out for CI status dashboards) can trivially be pointed at a different `stack_id` in the URL; there is no additional check to prevent it. Exploitation only requires changing the `stack_id` path segment.

### Recommendation
Have `CCMenuController#stack` use the same client-scoped lookup as `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the stack resolved is always constrained by `current_api_client.stack_id?`, restoring the binding between the permission scope and the actual stack acted upon.

### Proof of Concept
1. Obtain (or generate via the CCMenu widget flow) an `ApiClient` token scoped to stack `A` with `read:stack` permission (e.g., fixture `here_come_the_walrus`, scoped to stack `shipit`). [3](#0-2) 
2. Call `GET /api/<stack_B_owner>/<stack_B_name>/<env>/ccmenu.xml?token=<token>` for a different stack `B` that the token was never scoped to.
3. `authenticate_api_client` accepts the token, `require_permission :read, :stack` passes because the token has `read:stack`, and `stack` resolves `B` via unscoped `Stack.from_param!` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`), returning `B`'s deploy status instead of a 404/403.
