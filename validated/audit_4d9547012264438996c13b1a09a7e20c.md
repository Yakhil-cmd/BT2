### Title
Global, repository-unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status webhook from any repository mutate commit status on unrelated stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
Every other webhook handler (`PushHandler`, `PullRequestHandler`, `CheckSuiteHandler`, `MembershipHandler`) scopes its mutations through `Handler#stacks`, which resolves `Repository.from_github_repo_name(payload.dig('repository','full_name'))`. `StatusHandler#process` never calls `stacks`/`repository_name` at all; it looks up commits by `Commit.where(sha: params.sha)` across the entire `commits` table, keyed only on `sha` and unique per `(stack_id, sha)` (see the `index_commits_on_stack_id_and_sha` migration), not per repository. Since a git SHA is only unique to the content+history that produced it, two different repositories (e.g. a fork) can legitimately contain a commit with the identical SHA, letting a validly-signed webhook for one repository update commit status for a stack belonging to a completely different, unrelated repository.

### Finding Description
The binding that should hold is:
`Handler#stacks` (i.e. `Repository.from_github_repo_name(payload['repository']['full_name']).stacks`) == the set of stacks whose data is mutated by `#process`.

For `PushHandler#process` this holds: [1](#0-0)  it only touches `stacks.not_archived.where(branch:)`.

For `StatusHandler#process` it does not hold: [2](#0-1)  the handler calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no reference to `repository_name` or `stacks` at all, unlike the base class helper it inherits: [3](#0-2) .

`Commit#create_status_from_github!` writes a `Status` row scoped to `commit.stack_id`/`commit.stack`, and then triggers side effects via `add_status`, including `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` when the new status is pending/successful: [4](#0-3) [5](#0-4) .

Exploit flow: the attacker owns/forks a public repository (`attacker/repoA`) that shares a commit (identical SHA1) with `victim/repoB` — trivial via a normal GitHub fork, or by cherry-picking/pushing the same tree+parent+author+timestamp commit. If the attacker's own repository has any Shipit-recognized commit with that SHA and the attacker triggers (or GitHub sends, e.g. via a connected CI service on their own repo, or by using the GitHub Statuses API on their own repository, which they legitimately control) a `status` event, GitHub signs and delivers this webhook with `payload['repository']['full_name'] == 'attacker/repoA'`. `StatusController`/`GithubApp#verify_webhook_signature` only checks that the payload was signed by Shipit's configured webhook secret; it does not, and cannot, validate that the `sha` referenced belongs to the repository named in the payload. Because `StatusHandler#process` ignores `repository_name`/`stacks` and queries `Commit.where(sha: params.sha)` globally, every commit row across every tenant/stack sharing that SHA gets its status updated, including `victim/repoB`'s. If that stack has `continuous_deployment?` enabled and the injected state marks the commit deployable (`success`), `add_status` invokes `stack.schedule_merges`, and separately `Commit#schedule_continuous_delivery` (invoked on original creation, but the changed status now satisfies `deployable?`) — on next evaluation of continuous delivery for that stack the forged status is what CI-gates the deploy decision, allowing an attacker to unblock/trigger a deploy on a stack they have no relationship with.

None of the existing guards prevent this: `verify_signature`/`GitHubApp#verify_webhook_signature` proves message integrity/origin from GitHub but not that the named repository "owns" the SHA; `drop_unhandled_event` and the `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) only validate shape; there is no `subset`/repository-ownership validator on `Commit#sha` at write time in this path.

### Impact Explanation
A payload naming `attacker/repoA` mutates status/state data belonging to `victim/repoB`'s commit and stack — this is a cross-tenant write that the attacker never authenticated for `repoB`, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Because continuous deployment gating relies on commit status/state (`deployable?`, `schedule_continuous_delivery`, `stack.schedule_merges`), the attacker can influence deploy readiness signals for a victim stack, which can result in an unauthorized deploy. This is repeatable against any repository/stack pair that happens to share a commit SHA (forks are the most common and cheap way to guarantee a shared SHA) and requires no privilege beyond controlling a repository that can emit a legitimately-signed webhook to the Shipit host.

### Likelihood Explanation
Preconditions: (1) `victim/repoB` has an existing `Commit` row with a SHA the attacker can also produce/control in their own repo (fork gives this for free), (2) the Shipit installation is subscribed to `status` events for the attacker's repository (standard for any GitHub App/webhook-integrated org where public forks/installs can emit events), (3) no privileged Shipit role, session, or secret is required by the attacker — they only need to control a repository capable of emitting a signed status event. Attacker cost is low: fork a public repo tracked by Shipit and trigger/receive a status event for the shared commit. It is fully repeatable against any stack sharing commit history with an attacker-controlled repository.

### Recommendation
Scope `StatusHandler#process` by repository the same way other handlers do: resolve `stacks` from `payload['repository']['full_name']` and restrict the `Commit` lookup to `stacks.commits` (i.e., join `Commit` to `Stack`/`Repository` via `stack_id`) rather than a bare `Commit.where(sha: params.sha)` across all stacks. For example, replace the global scan with something scoped like `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or a scoped query `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`, mirroring the `Handler#stacks` binding used elsewhere.

### Proof of Concept
Minitest plan (no live GitHub, using existing fixtures/factories):
1. Create `victim_repo` (`Shipit::Repository`, e.g. `victim/repoB`) with a `Stack` that has `continuous_deployment` enabled, and a `Commit` with `sha: 'deadbeef...'`.
2. Create `attacker_repo` (`Shipit::Repository`, e.g. `attacker/repoA`) with its own `Stack` (no relation to victim) and no commit with that SHA (simulate the shared-SHA fork scenario by simply asserting on the `Commit.where(sha:)` behavior directly against the existing victim commit).
3. Build a `payload` hash: `{ 'repository' => { 'full_name' => 'attacker/repoA' }, 'sha' => 'deadbeef...', 'state' => 'success', 'context' => 'ci/attacker' }`.
4. Instantiate `handler = Shipit::Webhooks::Handlers::StatusHandler.new(payload)`.
5. Assert the binding is broken:
   - `assert_equal Shipit::Stack.none.to_a, handler.send(:stacks).to_a` (or assert it excludes victim's stack) — i.e., `refute_includes handler.send(:stacks), victim_stack`.
   - Call `handler.process`.
   - `victim_commit.reload` and assert `victim_commit.statuses.last.context == 'ci/attacker'` (or state changed), proving `victim_commit`'s stack (not present in `handler.send(:stacks)`) was mutated by a payload that never referenced `victim/repoB`.
6. This demonstrates `handler.send(:stacks)` (scoped to `attacker/repoA`, excluding `victim_stack`) diverges from the actual set of stacks/commits mutated by `#process` (which includes `victim_stack`'s commit), proving the binding violation.

      already_deployed = deployed?

      reload # to get the statuses into the right order (since sorted :desc)

        payload = { commit: self, stack:, status: new_status.state }
