### Title
Arbitrary command execution via unrestricted git submodule URL protocol (`ext::`) during recursive submodule update - (File: main.go)

### Summary
The external report describes an RCE analog where attacker-controlled data (a URI) is handed to a powerful, protocol-unrestricted function (`shell.openExternal`) without validating or whitelisting the scheme, allowing `file://`/`smb://` to trigger code execution. The closest reachable analog in `git-sync` is `configureWorktree`'s submodule update step, which invokes `git submodule update --init [--recursive]` against content that comes entirely from the synced (attacker-controllable) upstream repository, without restricting which git transport/protocol submodule URLs may use.

### Finding Description
When `--submodules` is not `off`, `configureWorktree` runs: [1](#0-0) 

This composes `git submodule update --init` (optionally `--recursive`, `--depth N`) and executes it via `git.Run`, which shells out to the real `git` binary with the given argv: [2](#0-1) 

The `.gitmodules` file that defines submodule URLs is part of the tree that was just checked out from the fetched hash (`reset --hard hash` immediately precedes this): [3](#0-2) 

That means the submodule URL values are fully attacker-controlled content — anyone who can push a commit to the synced ref (the exact "attacker-pushed commit" threat model called out in the task) can set a submodule URL to a dangerous git transport helper form such as `ext::sh -c "id > /pwned; exit 1" foo` or similar `ext::<cmd>` remote helper syntax. Historically, git itself blocked this class of attack (CVE-2017-1000117 / CVE-2018-11235) at the `git submodule` layer by default-disabling `ext::` and similar protocols unless `protocol.ext.allow` (or `GIT_ALLOW_PROTOCOL`) is explicitly set. Nowhere in `main.go` does `git-sync` set `GIT_ALLOW_PROTOCOL` or `protocol.*.allow` to lock down the transports; it relies entirely on whatever git's compiled-in defaults are, and never adds a defense-in-depth restriction. Searching the codebase for `GIT_ALLOW_PROTOCOL`, `protocol.allow`, and `ext::` handling in `main.go` returns no matches, confirming no explicit allow-listing is performed by `git-sync` itself. `main.go` also passes the environment through untouched in most exec paths (e.g., `GIT_SSH_COMMAND` is the only env var explicitly set, in `SetupGitSSH`): [4](#0-3)  — there is no equivalent hardening for submodule protocol restriction.

This mirrors the report's root cause exactly: a function with unrestrained protocol/scheme reach (`shell.openExternal` there, `git submodule update` / general git transport here) is fed attacker-influenced data (a URI there, a `.gitmodules` submodule URL here) without any application-level validation or whitelist, even though the underlying tool (Electron / git) is documented to support dangerous non-http(s) schemes for exactly this operation.

### Impact Explanation
If exploited on a git version/configuration where `ext::` or other command-executing submodule protocols are not blocked by git's own defaults, an attacker who can commit to the tracked branch/ref (or supply a malicious ref that gets fetched, e.g. via an unauthenticated `--repo` source, a compromised upstream, or a permissive CI push) obtains arbitrary command execution in the git-sync container/process, running as whatever UID git-sync runs as. This is full code execution outside `--root`, capable of exfiltrating credentials configured for git-sync (SSH keys, cookie files, askpass tokens) and tampering with or deleting arbitrary files reachable by that UID — squarely within the "Accept" criteria (code execution, credential/token disclosure, file write/delete outside `--root`).

### Likelihood Explanation
Likelihood depends on the git binary's own protocol allow-list defaults remaining unmodified/downgraded and requires `--submodules` not set to `off` (which is not the default — the default is `recursive`, per the flag docs): [5](#0-4) . It also requires that an attacker can get a malicious `.gitmodules` commit onto the tracked ref of the synced repo — this is realistic in common git-sync use cases where it syncs a repo/branch that accepts external contributions, PR merges, or is otherwise not fully trusted-write. Because modern git already blocks `ext::`/`file://` by default in most stock installations, likelihood is reduced to scenarios with an older/misconfigured git or an explicitly (mis)configured `protocol.allow`/`GIT_ALLOW_PROTOCOL` environment — but `git-sync` performs no independent mitigation of its own, so it inherits whatever risk the underlying git binary/environment carries, with zero defense-in-depth.

### Recommendation
- Short term: Before running `git submodule update`, explicitly set `GIT_ALLOW_PROTOCOL=file:git:https` (or narrower, matching only the schemes actually needed) in the environment used for the `git.Run` call in `configureWorktree`, so `ext::`, `ssh` (if unneeded), and other command-capable helpers are denied regardless of the host git's compiled defaults.
- Also consider passing `-c protocol.ext.allow=never` (and similarly for any other unneeded transport) as explicit `git` config flags on the submodule-update invocation, rather than relying on ambient environment/global config.
- Long term, treat all content originating from the synced repository (including `.gitmodules`) as untrusted input to the shell-executing `git` subprocess, and apply the same "validate/whitelist before executing" principle recommended in the source report for `shell.openExternal`.

### Proof of Concept
1. Configure `git-sync --repo=<attacker-writable-or-compromised-repo> --ref=<branch> --submodules=recursive` (the default).
2. In the attacker-controlled branch, commit a `.gitmodules` file:
   ```
   [submodule "x"]
       path = x
       url = ext::sh -c "touch /tmp/pwned; exit 1" 
   ```
3. When git-sync's `SyncRepo` detects the new hash, it calls `configureWorktree`, which runs `reset --hard <hash>` then `git submodule update --init --recursive` against the checked-out `.gitmodules`: [6](#0-5) 
4. On a git installation/environment where `ext::` is not blocked, the `sh -c "touch /tmp/pwned"` command executes inside the git-sync container as the git-sync process's user.

func (git *repoSync) SetupGitSSH(setupKnownHosts bool, pathsToSSHSecrets []string, pathToSSHKnownHosts string) error {
	git.log.V(1).Info("setting up git SSH credentials")

	// If the user sets GIT_SSH_COMMAND we try to respect it.
	sshCmd := os.Getenv("GIT_SSH_COMMAND")
	if sshCmd == "" {
		sshCmd = "ssh"
	}

	// We can't pre-verify that key-files exist because we call this path
	// without knowing whether we actually need SSH or not, in which case the
	// files may not exist and that is OK.  But we can make SSH report more.
	switch {
	case git.log.V(9).Enabled():
		sshCmd += " -vvv"
	case git.log.V(7).Enabled():
		sshCmd += " -vv"
	case git.log.V(5).Enabled():
		sshCmd += " -v"
	}

	for _, p := range pathsToSSHSecrets {
		sshCmd += fmt.Sprintf(" -i %s", p)
	}

	if setupKnownHosts {
		sshCmd += fmt.Sprintf(" -o StrictHostKeyChecking=yes -o UserKnownHostsFile=%s", pathToSSHKnownHosts)
	} else {
		sshCmd += " -o StrictHostKeyChecking=no"
	}

	git.log.V(9).Info("setting $GIT_SSH_COMMAND", "value", sshCmd)
	if err := os.Setenv("GIT_SSH_COMMAND", sshCmd); err != nil {
		return fmt.Errorf("can't set $GIT_SSH_COMMAND: %w", err)
	}
