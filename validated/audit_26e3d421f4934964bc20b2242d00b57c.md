### Title
CCMenu API Token Stack-Scope Bypass — Token Restricted to One Stack Can Read Any Stack's Build Status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` resolver used for permission-scoped queries, breaking the binding between the stack an `ApiClient` token is authorized for and the stack whose CI/build state is actually returned.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, scope-respecting accessors: [1](#0-0) 

`stacks` is deliberately restricted to the `ApiClient`'s bound stack when the client is stack-scoped (`current_api_client.stack_id?`), and `stack` is derived from that restricted relation. This is the mechanism that enforces "the stack a token authorizes" for stack-scoped clients such as the `here_come_the_walrus` fixture, which carries a `stack_id` and only `read:stack` permission: [2](#0-1) 

`CCMenuController`, however, does not reuse `stacks`/`stack` from the base controller for resource resolution. It re-defines `stack` to fetch directly by parameter, independent of `current_api_client.stack_id`: [3](#0-2) 

The controller's only authorization gate is the generic permission check `require_permission :read, :stack`, which merely verifies the string `"read:stack"` is present in `current_api_client.permissions` — it carries no per-stack identity: [4](#0-3) 

Meanwhile, `CCMenuUrlController` is the legitimate issuer of exactly this kind of stack-scoped credential — it mints an `ApiClient` intended to be embedded in a plain, unauthenticated CCMenu URL (query-string token) for a specific stack: [5](#0-4) 

The binding that should hold is:
`current_api_client.stack_id == stack.id` (the stack the token authorizes == the stack whose state is served)

`CCMenuController#stack` breaks this equality: it resolves `stack` purely from `params[:stack_id]` via `Stack.from_param!`, never intersecting with `current_api_client.stack_id`. `check_permissions!` only checks the operation/scope string, not which stack it applies to.

### Impact Explanation
Any holder of a stack-scoped, `read:stack`-only `ApiClient` token — the exact credential shape produced for CCMenu integrations and routinely embedded as a plain URL query parameter (`?token=...`), which is designed to leak into browser history, dashboards, and referrer headers as an unauthenticated bearer credential — can supply an arbitrary `stack_id` and read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state, etc.) of any other stack in the Shipit instance, not just the one the token was minted for. This is an authorization-scope escalation: unauthenticated read of stack state for stacks the token holder was never granted access to, matching the High-severity category "unauthenticated read of stack state."

### Likelihood Explanation
High. No special privilege is needed beyond possessing any valid `read:stack` token (including a legitimately-scoped, low-privilege CCMenu token designed for public/unauthenticated embedding). The attacker only needs to change the `stack_id` request parameter; `authenticate!`/`BasicAuth` still succeeds since the token itself is valid, and `require_permission` passes because it never inspects `stack_id`.

### Recommendation
Make `CCMenuController#stack` resolve through the scope-aware `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so that a stack-scoped `ApiClient`'s `stack_id` binding is enforced identically to every other API controller.

### Proof of Concept
1. Admin creates (or a user obtains via `CCMenuUrlController#fetch`) a CCMenu token scoped to `stack: shipit` with permissions `['read:stack']` (as in fixture `here_come_the_walrus`, `test/fixtures/shipit/api_clients.yml:12-17`).
2. Attacker who obtains this token (e.g., from a leaked CCMenu badge URL) issues:
   `GET /api/stacks/OTHER_OWNER/OTHER_STACK/ccmenu.xml?token=<the_scoped_token>`
3. `authenticate_api_client` in `CCMenuController` (`app/controllers/shipit/api/ccmenu_controller.rb:33-36`) authenticates the token successfully.
4. `require_permission :read, :stack` passes because the token has `read:stack` permission (`app/models/shipit/api_client.rb:38-45`), with no stack-identity check.
5. `stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) resolves `OTHER_STACK` directly via `Stack.from_param!`, bypassing the `current_api_client.stack_id` restriction that `BaseController#stacks` would have enforced.
6. The response discloses `OTHER_STACK`'s build/deploy status, even though the token was only ever authorized for `shipit`.
