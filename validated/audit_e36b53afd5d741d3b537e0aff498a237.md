### Title
Webhook signature verification uses `repository.owner.login` to select the trust key while event handlers act on `repository.full_name` - authenticated organization ≠ repository being written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate a webhook's HMAC signature against based on `repository.owner.login` (or `organization.login`) taken directly from the *unverified* JSON body. Once the signature check passes, the raw, unvalidated payload is handed to event handlers, which independently derive the target `Repository`/`Stack` from a *different* field of the same payload: `repository.full_name`. Because the field used to pick the verification key (`owner.login`) and the field used to pick the acted-upon repository (`full_name`) are never checked for consistency, an attacker who legitimately controls one GitHub organization configured on a shared Shipit instance (and therefore knows that organization's own `webhook_secret`) can sign a payload that claims ownership under their org while pointing `repository.full_name` at a stack belonging to a completely different, victim organization.

### Finding Description
The binding that should hold is:
`organization whose webhook_secret authenticated the signature == organization that owns the repository the handler acts on`

In `verify_signature`, the organization used to look up the `GithubApp`/secret comes straight from the untrusted body: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

Signature verification itself only compares the HMAC of `request.raw_post` against the secret configured for that org — it never checks that the signed org matches the repo that will actually be processed: [3](#0-2) 

After the (correctly computed, but org-scoped) signature check passes, `create` dispatches the same raw JSON to registered handlers unmodified: [4](#0-3) 

The base `Handler` (and `PushHandler`) resolve the target `Repository`/`Stack` using `repository.full_name`, a completely separate field from the one used for signature-org selection: [5](#0-4) [6](#0-5) 

Because `Shipit` supports multiple GitHub organizations configured on one instance, each with its own `webhook_secret` (documented and shown in `config/secrets.development.shopify.yml` with `somegithuborg` / `someothergithuborg`), an administrator of any one of those organizations knows only their own org's `webhook_secret`, yet can produce a validly-signed payload whose `repository.full_name` names a repository/stack belonging to an entirely different org on the same instance.

### Impact Explanation
An attacker who administers (or otherwise obtains the webhook secret for) any one GitHub organization configured on a shared Shipit instance can forge a `push` webhook that:
- Is signed with their own org's `webhook_secret` (so `verify_signature` accepts it, since it resolves `Shipit.github(organization: repository_owner)` using their org name), and
- Sets `repository.full_name` to a victim stack belonging to a different organization on the same instance.

`PushHandler#process` then locates the victim `Stack` via `Repository.from_github_repo_name(repository_name)` and calls `stack.sync_github(expected_head_sha: params.after)` with an attacker-chosen `after` SHA, forcing the victim stack to sync against a commit of the attacker's choosing. Depending on downstream auto-deploy/continuous-deployment configuration, this can drive an unauthorized deploy pipeline event for a repository the attacker does not own or have write access to — a cross-repository/cross-organization boundary violation triggered purely by an authenticated-but-mismatched org identity.

### Likelihood Explanation
This requires the deployment to host more than one GitHub organization behind the same Shipit instance (a supported, documented configuration) and requires the attacker to control (or have obtained) the `webhook_secret` for at least one of those orgs — something any admin of that org legitimately has, since they configure it themselves when creating their GitHub App. No `ApiClient` token, session, or privileged Shipit account is needed; only knowledge of one org's own webhook secret, which is an expected credential for org admins, not a Shipit-privileged secret. This makes the analog reachable by an "unprivileged" (relative to the victim org) party in a realistic multi-tenant Shipit setup.

### Recommendation
Bind the two payload fields together before trusting either: after `verify_webhook_signature` succeeds using `repository_owner`, additionally verify that `repository.full_name`'s owner segment matches `repository_owner` (and that `organization.login`, if present, is consistent), rejecting the request with 422 otherwise. Alternatively, resolve the target `Repository`/`Stack` in the handler and re-derive/re-check the organization from that resolved repository record (not from user-supplied payload fields) before allowing any stack-mutating action such as `sync_github`.

### Proof of Concept
Given a shared Shipit instance configured with two orgs, `org-attacker` (attacker is admin, knows `webhook_secret_A`) and `org-victim` (has a Stack tracking `org-victim/app`):

1. Attacker builds payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker_chosen_sha>",
  "repository": {
    "owner": { "login": "org-attacker" },
    "full_name": "org-victim/app"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_A, raw_body)>` and sends it with `X-Github-Event: push` to `POST /webhooks`.
3. `WebhooksController#verify_signature` computes `repository_owner == "org-attacker"`, loads `Shipit.github(organization: "org-attacker")`, and successfully verifies the signature against `webhook_secret_A` — see `app/controllers/shipit/webhooks_controller.rb:24-38` and `lib/shipit/github_app.rb:76-83`.
4. `create` dispatches the same payload to `Handlers::PushHandler`, which resolves `repository_name = "org-victim/app"` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and finds `org-victim`'s stacks, invoking `stack.sync_github(expected_head_sha: "<attacker_chosen_sha>")` for a branch/repo the attacker never authenticated for.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
