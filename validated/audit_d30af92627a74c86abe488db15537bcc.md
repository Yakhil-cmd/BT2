### Title
CCMenuController#stack bypasses per-client stack scoping, allowing cross-tenant enumeration of deploy state via one token - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of using `BaseController#stacks`, which is the method responsible for intersecting the requested stack with `current_api_client.stack_id`. Any holder of a valid `read:stack` API token — even one issued for a single specific stack — can enumerate arbitrary `stack_id` values and read every other tenant's CCMenu deploy state.

### Finding Description
The binding that must hold for tenant isolation is:
`Stack.find(params[:stack_id]) ∈ Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true.

`BaseController` implements this correctly for other API controllers: [1](#0-0) 
`stacks` filters by `current_api_client.stack_id` when the client is scoped to one stack, and the default `stack` method resolves through that scoped relation.

`CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!` on the unscoped `Stack` model, so `params[:stack_id]` is resolved globally rather than through `Stack.where(id: current_api_client.stack_id)`.

Permission enforcement (`require_permission :read, :stack`) only checks that the string `"read:stack"` is present in the token's `permissions` array — it has no notion of which stack the token is bound to: [3](#0-2) 
So `require_permission!` passes identically regardless of the requested `stack_id`, and nothing else in the request path checks `current_api_client.stack_id` against the resolved stack.

Attack: an attacker legitimately obtains (or is issued) an `ApiClient` token scoped to their own single stack (`stack_id` set, `read:stack` permission). They then issue:
```
GET /api/stacks/1/cc_menu.xml?token=<own-token>
GET /api/stacks/2/cc_menu.xml?token=<own-token>
...
```
incrementing the numeric `stack_id`. For every value, `CCMenuController#stack` resolves the target stack unconditionally via `Stack.from_param!`, `require_permission!(:read, :stack)` passes because the permission array matches regardless of stack, and `#show` renders `stack.deploys_and_rollbacks.last` (branch, last deploy SHA/label, running/lock status) for a stack the token was never scoped to: [4](#0-3) 

No other guard intervenes: `authenticate_api_client` here only verifies the token signature via query-string param, not stack ownership: [5](#0-4) 
There is no `ExplicitParameters` schema, model validation, or additional before_action that re-applies the `stacks` scope for this controller.

### Impact Explanation
Each request discloses another tenant's stack name, branch, activity/lock status, and last build/deploy label/status/time — this is unauthenticated (relative to that stack) read of deploy state, matching the High severity category "unauthenticated read of stack state ... deploy output" for any stack whose numeric id the attacker guesses (trivial, since ids are sequential). The exploit is fully repeatable across every stack in the instance using a single legitimately-issued token, giving full enumeration of all tenants' deploy state.

### Likelihood Explanation
Preconditions are minimal and realistic: the attacker only needs one legitimately issued `ApiClient` token scoped to their own stack with `read:stack` permission — no elevated privileges, no secrets, no session. Stack ids being sequential integers (standard AR auto-increment) makes enumeration trivial and cheap (a simple loop over `1..N`). No Shipit or repository-side configuration prevents this; it is a pure engine bug in `CCMenuController`.

### Recommendation
Remove the overriding `stack` method in `CCMenuController` (or have it delegate to `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`) so that the same `current_api_client.stack_id` scoping enforced by `BaseController#stacks` applies here as it does elsewhere.

### Proof of Concept
Minitest under `test/controllers/api/ccmenu_controller_test.rb` (existing file):
```ruby
test "a token scoped to one stack cannot read another stack's cc_menu" do
  other_stack = shipit_stacks(:cyclimse) # a stack fixture different from @stack
  @client.update!(stack_id: @stack.id, permissions: ['read:stack'])

  get :show, params: { stack_id: other_stack.to_param, token: @client.authentication_token }

  # Binding under test:
  # Stack.find(other_stack.id) ∈ Stack.where(id: @client.stack_id) must be false
  assert_not Stack.where(id: @client.stack_id).exists?(other_stack.id)
  # Yet the controller currently returns 200 with the other stack's data:
  assert_response :ok
  assert_payload 'name', other_stack.to_param  # demonstrates leakage; should instead be :forbidden/:not_found
end
```
This demonstrates that `other_stack.id` is outside `Stack.where(id: @client.stack_id)` yet `CCMenuController#show` still renders it successfully, confirming the broken binding.
