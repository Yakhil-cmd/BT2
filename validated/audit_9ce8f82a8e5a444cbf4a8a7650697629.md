### Title
Unbounded in-memory cache of full (up-to-5MB) pruned/voided joints allows attacker-triggered OOM - (File: archiving.js)

### Summary
`archiving.js` maintains an in-memory cache, `assocCachedPrunedJoints`, of the **full content** of every joint that gets voided/stripped as `final-bad`, keyed only by unit hash and evicted purely by a fixed 1-hour TTL, with no bound on the number of entries or total bytes cached. [1](#0-0)  Any unit that becomes `final-bad` (e.g. a detected double-spend/invalid unit that nevertheless gets included and stabilized in the DAG) is pushed into this cache via `cachePrunedJoint()`, called from `storage.updateMinRetrievableMciAfterStabilizingMci()` right before the unit's content is stripped from the DB. [2](#0-1)  Because units may be up to `MAX_UNIT_LENGTH` (5 MB) in size, [3](#0-2)  and the cache size/count is otherwise unbounded, an attacker who can get a stream of large, invalid ("final-bad") units accepted and stabilized can force the node to retain many megabytes of joint JSON in memory simultaneously, for up to an hour, with no upper cap — the same "buffer leak via repeated large POST data" pattern described in CVE-2024-6875 for Infinispan's REST compare API.

### Finding Description
`cachePrunedJoint(objJoint)` unconditionally stores `{ objJoint, expiry_ts }` in the plain object `assocCachedPrunedJoints`, and the only cleanup mechanism is `purgeExpiredCachedPrunedJoints()`, which runs once per hour and only deletes entries whose `expiry_ts` has passed. [4](#0-3)  There is no limit analogous to `MAX_ITEMS_IN_CACHE` used elsewhere in `storage.js` for other in-memory caches, [5](#0-4)  and unlike `network.js`'s deliberate design of keeping only small pointers for withheld joints specifically to prevent a peer from exhausting memory with large/many joints, [6](#0-5)  `assocCachedPrunedJoints` stores the entire joint object, including all messages/payloads, for every voided unit.

The cache is populated during the normal stabilization pruning path: as MCIs stabilize and `min_retrievable_mci` advances, `final-bad` units within the newly-covered MCI range are read in full via `readJoint`, stripped in the DB, and their full content is retained via `archiving.cachePrunedJoint(objJoint)` "to keep the full content around for a while in case somebody still needs it." [7](#0-6)  This path runs for every unit that ends up with `sequence='final-bad'` once it becomes covered by a stable ball — it does not require any special privilege, only that the attacker's unit(s) get included in the DAG and are later found invalid/conflicting (e.g., a double-spend), which is a routine outcome reachable by any unprivileged unit poster.

### Impact Explanation
Each cached entry can be close to `MAX_UNIT_LENGTH` (5 MB) of JSON data, and the cache has no ceiling on the number of concurrent entries — only a 60-minute time-based expiry. [8](#0-7)  An attacker who repeatedly posts large, ultimately-invalid units that become `final-bad` and get pruned can cause the node's process memory to grow essentially unboundedly during that hour window (limited only by how many large `final-bad` units they can get accepted/stabilized per unit time), leading to process-level out-of-memory and a crash/DoS of the full node — the same "unbounded memory growth via repeated large payload submissions" impact class as the Infinispan advisory.

### Likelihood Explanation
Reaching this path requires only that an unprivileged unit poster author units that: (1) pass initial joint/unit-level structural validation (so they are accepted into the DAG and can grow toward `MAX_UNIT_LENGTH`), and (2) are ultimately judged `final-bad` (e.g., losing units in a double-spend, or any other final-bad condition enumerated in `main_chain.js`) once witnessed/stabilized. This is a normal, well-documented outcome of the DAG's conflict-resolution rules and does not require compromising any node, witness, or hub — it is achievable purely from the unprivileged unit-posting side, satisfying the scope constraints (single posted unit reaching a core validation/pruning path).

### Recommendation
Bound `assocCachedPrunedJoints` similarly to the other in-memory caches in `storage.js` (e.g., cap total entry count via a `MAX_ITEMS_IN_CACHE`-style limit and/or track and cap the aggregate byte size of cached joints), evicting the oldest/largest entries first when the limit is exceeded, in addition to the existing TTL-based expiry. Alternatively, follow the pattern already used in `network.js` for `assocUnitsWaitingForPrunedContent` — store only small pointers in memory and keep the full (possibly large) joint body in the KV store, fetching it on demand instead of holding every voided joint's full content in the process heap.

### Proof of Concept
1. An attacker crafts and posts a sequence of large units (each approaching `MAX_UNIT_LENGTH`, i.e. up to ~5 MB) that are structurally valid but designed to conflict with each other (e.g., double-spending the same input across multiple units from the same address), so that most of them will ultimately be marked `sequence='final-bad'`.
2. As main-chain stabilization progresses and these units become covered (`updateMinRetrievableMciAfterStabilizingMci` runs), each `final-bad` unit's full joint is read via `readJoint`, stripped from the DB, and cached in full via `archiving.cachePrunedJoint(objJoint)`. [7](#0-6) 
3. Repeating step 1 continuously (posting new large conflicting units) keeps feeding `assocCachedPrunedJoints` faster than the 1-hour TTL can clear entries, since there is no count/size cap — only elapsed-time-based eviction. [9](#0-8) 
4. Sustained posting drives the node's process memory usage up in proportion to `(number of large final-bad units accepted per hour) × (unit size)`, eventually exhausting available memory and crashing/degrading the node — an out-of-memory denial of service triggerable entirely by an unprivileged unit poster.

// in-memory holdover of joints we just voided (stripped final-bad units), so that for a while after pruning
// we can still serve their full content to peers and recover from spends that raced the pruning locally
const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}

// looks up a specific output within a cached pruned joint, in the same shape as the outputs table columns we lost to stripping
function getCachedOutput(unit, message_index, output_index){
	const objJoint = getCachedPrunedJoint(unit);
	if (!objJoint)
		return null;
	const message = objJoint.unit.messages && objJoint.unit.messages[message_index];
	if (!message || message.app !== 'payment' || !message.payload)
		return null;
	const output = message.payload.outputs && message.payload.outputs[output_index];
	if (!output)
		return null;
	return {
		address: output.address,
		amount: output.amount,
		denomination: message.payload.denomination || 1,
		asset: message.payload.asset || null
	};
}

function purgeExpiredCachedPrunedJoints(){
	const now = Date.now();
	for (let unit in assocCachedPrunedJoints)
		if (assocCachedPrunedJoints[unit].expiry_ts < now)
			delete assocCachedPrunedJoints[unit];
}
setInterval(purgeExpiredCachedPrunedJoints, PRUNED_JOINT_CACHE_TTL_ms);
