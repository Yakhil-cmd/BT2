### Title
`StatusHandler` binds GitHub `status` webhooks to commits by SHA only, letting a same-SHA commit in an attacker's repo mutate another Stack's status - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/commit.rb`)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` without ever checking the webhook payload's `repository.full_name` against `commit.stack.repository.full_name`. `Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` using `commit.stack_id` unconditionally, so the recorded status is always attributed to whichever Stack happens to own a `Commit` row with that SHA, not to the Stack corresponding to the webhook's actual source repository.

### Finding Description
The binding that must hold is: `stack derived from payload['repository']['full_name'] == commit.stack_id used in replicate_from_github!`. Tracing the code shows this is false.

`WebhooksController#create` dispatches the parsed JSON payload to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` after `verify_signature`, which only checks that the payload was signed by the GitHub App belonging to `repository_owner` (`params.dig('repository','owner','login')`) — i.e., it proves the webhook came from *some* repo owned by that org, not that the referenced commit belongs to that repo: [1](#0-0) 

`Handler` exposes a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)` (derived from `payload.dig('repository','full_name')`) precisely for this purpose: [2](#0-1) 

`StatusHandler#process` ignores that helper entirely and queries commits globally by SHA: [3](#0-2) 

`Commit#create_status_from_github!` then writes the status using `stack_id`, the owning Stack of that Commit row, with no comparison to the payload's repository: [4](#0-3) 

**Exploit flow**: A victim Stack has a Commit with SHA `S` (visible publicly via GitHub UI/API, including its exact tree, parent, author, committer, and timestamps). Since a git commit's SHA-1 is a deterministic hash of that metadata and is not tied to which repository stores it, an attacker can construct an identical commit object (e.g., a fixed-metadata commit) in a repository they own and push it there, reproducing SHA `S`. The attacker then generates a legitimate `status` event on their own repo for SHA `S` (e.g., via GitHub's status API, which they control as repo owner), which GitHub delivers as a webhook signed with that repo owner's real webhook secret. `verify_signature` passes because the signature is genuinely valid for the attacker's own org/repo. `StatusHandler` finds the victim's `Commit` row by SHA match and updates its status, attributing it to the victim Stack (`commit.stack_id`), even though the payload's `repository.full_name` is the attacker's repo, not the victim's.

None of the existing guards catch this: `verify_signature` authenticates the sender's org, not the commit-to-repo relationship; the `ExplicitParameters` schema in `StatusHandler` only validates field types/presence (`sha`, `state`, etc.), not repository correspondence; and the `stacks` scoping helper in the base `Handler` class exists but is unused by `StatusHandler`.

### Impact Explanation
A forged status write on a locked/awaiting-deploy commit in a victim Stack can satisfy CI/status gating used by deploy-readiness checks (`CommitChecks`, `refresh_statuses!` consumers), potentially unblocking an unauthorized deploy/merge path for a repository the attacker does not control or authenticate against. This is a cross-repository state mutation triggered entirely by an unprivileged GitHub repo owner, repeatable against any Stack whose commit SHA the attacker can reproduce (feasible for any public commit, since git object hashing is deterministic and repo-independent). This matches "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge" — Critical.

### Likelihood Explanation
Preconditions: attacker needs only (1) a GitHub account and their own repository (or fork) with a valid webhook/App installation delivering `status` events to the Shipit host — standard prerequisite for any Shipit-integrated org, and (2) knowledge of the victim commit's SHA and its exact author/committer/tree/parent/timestamp metadata, all of which are public via the GitHub UI/API for any visible commit. No Shipit secrets, session, or API token are required; `verify_signature` is satisfied legitimately for the attacker's own repo. This is a self-contained, repeatable, low-cost attack requiring no privileged role.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the Stack(s) resolved from the payload's own repository (using the existing `stacks` helper from `Handler`) instead of a global `Commit.where(sha: ...)`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Repository.from_github_repo_name(repository_name)`. Additionally, `Commit#create_status_from_github!`/`refresh_statuses!` should assert `commit.stack.repository.full_name == expected_repository_name` before calling `replicate_from_github!`, defensively rejecting any status update whose source repository does not match the commit's owning Stack.

### Proof of Concept
```ruby
# test/models/commits_test.rb (conceptual, illustrating the missing binding check)
test "create_status_from_github! attributes status to commit.stack_id regardless of payload repository" do
  victim_stack = shipit_stacks(:shipit)
  commit = victim_stack.commits.last

  forged_status = OpenStruct.new(
    state: 'success',
    context: 'ci/attacker',
    description: 'forged',
    target_url: 'http://evil.example/status',
    # simulate payload claiming a different repository than victim_stack.repository.full_name
    repository: OpenStruct.new(full_name: 'attacker/evil-repo')
  )

  status = commit.create_status_from_github!(forged_status)

  # Binding under test: stack_id used == stack derived from payload repository
  assert_equal commit.stack_id, status.stack_id
  refute_equal 'attacker/evil-repo', commit.stack.repository.full_name
  # demonstrates status.stack_id was set from commit.stack_id, not from forged_status.repository.full_name
end
```
This confirms `create_status_from_github!` never consults or compares the payload's repository field to `commit.stack.repository.full_name` before writing the status against `commit.stack_id`.
