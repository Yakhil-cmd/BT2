Confirmed: `Shipit.github(organization:)` supports a per-organization config keyed by `TOP_LEVEL_GH_KEYS`, each with its own `webhook_secret`, so a multi-org Shipit deployment can have distinct secrets per GitHub organization.### Title
Webhook signature verification selects the signing secret from an attacker-controlled `repository.owner.login`/`organization.login` field that is disjoint from the `repository.full_name` actually acted upon by handlers - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App / webhook secret to HMAC-verify the raw request body against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON payload, via `Shipit.github(organization: repository_owner)`. Once verification succeeds, the same payload is handed unmodified to `Shipit::Webhooks.for_event(event)` handlers, which instead key their side effects off `repository.full_name` (`Handler#repository_name`, used by `Repository.from_github_repo_name`). Because the field used to choose the verification secret (`repository.owner.login`) is never checked for consistency with the field used to select the target repository/stack (`repository.full_name`), an attacker who legitimately controls one organization's webhook secret in a multi-org Shipit deployment can forge a valid signature for a payload whose acted-upon repository belongs to a different organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`Shipit.github(organization:)` in `lib/shipit.rb` looks up a per-organization config (`github_app_config`) that can carry an independent `webhook_secret` per organization (`TOP_LEVEL_GH_KEYS` includes `:webhook_secret`), i.e. a multi-tenant Shipit install can have organization `A`'s secret differ from organization `B`'s secret.

Once `verify_signature` passes, `create` dispatches the *same raw, attacker-supplied* payload to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
Handlers such as `PushHandler`, `CheckSuiteHandler`, `StatusHandler`, etc. resolve the target `Stack`/`Repository` using `Handler#repository_name`:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
```
`app/models/shipit/repository.rb#from_github_repo_name` then does `find_by(owner: repo_owner, name: repo_name)` from that same `full_name`.

The two lookups — `repository.owner.login` (used to pick the verification secret) and `repository.full_name` (used to pick the acted-upon repository/stack) — are independent JSON fields inside the same unsigned/unverified payload, and nothing enforces that `repository.owner.login == repository.full_name.split('/').first`. This is exactly the "organization authenticated versus the repository that is written" binding break: the HMAC only proves the raw bytes were signed by *some* configured secret, and the secret is chosen using a field the attacker also controls, decoupled from the field that determines which stack's automation actually fires.

### Impact Explanation
In a multi-org Shipit deployment (multiple entries under `secrets.github`, each with its own `webhook_secret`), an attacker who has legitimate control of organization `A`'s webhook configuration (e.g., they administer their own GitHub org/app that Shipit is configured to trust) knows/can compute a valid signature for organization `A`'s secret. They can craft a payload where `repository.owner.login` (or `organization.login`) = `A` (so `verify_signature` selects `A`'s known secret and the HMAC check passes) while `repository.full_name` = `victim-org/victim-repo`. The forged, validly-signed request then reaches `PushHandler`, `StatusHandler`, or `CheckSuiteHandler`, which act on `victim-org/victim-repo`'s stacks/commits — e.g. `PushHandler#process` enqueues `GithubSyncJob` against the victim stack, and `StatusHandler` injects commit statuses (`commit.create_status_from_github!`) for arbitrary commit SHAs in the victim stack, with attacker-controlled `state`/`description`/`context`/`target_url`. Forged commit statuses can flip a commit from "not deployable" to "deployable" in the merge/deploy pipeline, enabling an unauthorized deploy of attacker-influenced state — this maps to the report's "authenticated organization vs. repository actually acted on" binding class and the required Critical impact ("unauthorized deploy").

### Likelihood Explanation
Exploitability requires the specific precondition that the Shipit instance is configured for more than one GitHub organization with distinct webhook secrets (multi-tenant `secrets.github` config) and that the attacker legitimately controls one such organization's webhook delivery (e.g. as an org owner who configured Shipit's GitHub App against their own org). This is a real but non-default configuration; single-organization Shipit deployments (the common case, using the top-level `secrets.github` without per-org keys) are not affected because there is only one secret/one trusted owner to begin with.

### Recommendation
After successful signature verification, re-derive the organization strictly from `repository.full_name.split('/').first` (or `repository.owner.login`) and cross-check it equals the organization whose secret validated the signature before dispatching to handlers; reject the request (422) on mismatch. Alternatively, key `Shipit.github(organization:)` lookups exclusively off the same field used for repository resolution (`repository.full_name`), never off a separately-trusted `organization.login`/`repository.owner.login` value.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.github`, `attacker-org` and `victim-org`, each with a distinct `webhook_secret`, and a `victim-org/victim-repo` stack tracked in Shipit.
2. As the owner of `attacker-org` (who legitimately knows/controls `attacker-org`'s webhook secret because they administer that org's GitHub App installation), craft a JSON body:
```json
{
  "organization": { "login": "attacker-org" },
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, body)>` and POST to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` to `attacker-org`, fetches `attacker-org`'s `webhook_secret`, and the HMAC check passes.
5. `StatusHandler#process` then reads `repository.full_name` = `victim-org/victim-repo` is not directly used by `StatusHandler` (it matches by `sha` globally across `Commit`), so the forged status is attached to the victim commit, potentially satisfying deploy-blocking status checks it should never have satisfied.   def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
