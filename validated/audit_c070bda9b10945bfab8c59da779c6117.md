### Title
Status webhooks write attacker-controlled `target_url`/`description` into any stack sharing a commit SHA - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)`, with no check that the commit's owning `Stack`/`Repository` matches the repository that actually authenticated the webhook. Because GitHub commit SHAs are content-addressable and identical across forks/copied history, an attacker who can trigger a legitimately GitHub-signed `status` webhook for their own repository can write attacker-controlled `state`, `description`, `target_url`, and `context` into any other stack's `Status` row that happens to reference the same SHA.

### Finding Description
The broken binding: `stack_id used to create the Status == the Stack whose Repository produced the webhook payload's "repository" field` is assumed true but is never enforced.

Code path:
- `WebhooksController#verify_signature` only checks that the payload was HMAC-signed with the webhook secret for `repository_owner` (the organization/owner named in the payload) via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) . This proves the event came from GitHub for *some repository under that organization*, not that it came from any specific tracked `Repository`/`Stack`.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) . This query is global across the `commits` table (indexed on `stack_id, sha`, not unique on `sha` alone — see `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), so it matches every `Commit` row in every `Stack` that shares that SHA, regardless of which repository the row belongs to.
- `Commit#create_status_from_github!` and `Status.replicate_from_github!` write the payload's `state`, `description`, `target_url`, `context` verbatim against `stack_id`/`commit_id` with no repository cross-check [3](#0-2) [4](#0-3) .

Exploit flow: an attacker clones a victim's (public) repository history into a repository they control (fork or plain copy-push), which reproduces bit-identical commit SHAs since Git objects are content-addressed. If that attacker-owned repository is covered by the same Shipit-configured GitHub App/organization webhook secret (e.g., an "All repositories" GitHub App install on an org that allows members to create repos, or the attacker forks a repo already tracked by Shipit's installed org), the attacker sets a real GitHub Commit Status (via GitHub UI/API/Actions) on their copy of the shared commit with attacker-chosen `target_url`/`description`/`context` matching a victim stack's monitored context. GitHub emits a genuinely signed `status` webhook to Shipit. `verify_signature` passes (real signature, real org). `StatusHandler#process` then finds the victim stack's `Commit` row (same SHA, different repository) and writes the attacker's payload into it via `Status.replicate_from_github!`.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `StatusHandler`) only validate structure and organization-level signature; none of them check that `params.dig('repository','full_name')` matches the `Repository` backing the `Stack` that owns the matched `Commit`.

### Impact Explanation
This is a cross-repository/cross-tenant write: a `Status` row belonging to a victim `Stack` is populated with attacker-chosen `target_url`, `description`, `context`, and `state`, without that stack's own `Repository` ever authenticating the payload. This matches the "payload for one repository mutating another's stack/commit" Critical category — the write is repeatable against any stack that shares a SHA with an attacker-controlled repository under the same GitHub App/org installation, and blast radius scales with how many stacks/orgs share the GitHub App webhook secret.

### Likelihood Explanation
Requires: (1) the attacker's own repository be covered by a Shipit-configured GitHub App installation (realistic in "All repositories" org installs or forks of an already-tracked repo), (2) a shared commit SHA with the victim stack (trivial via cloning/forking, not a cryptographic collision), (3) ability to set a commit status on the attacker's own repo (trivially available to any repo owner/collaborator via GitHub UI, API, or Actions). No Shipit secrets, sessions, or privileged roles are needed — only a legitimate, GitHub-signed webhook for the attacker's own repository. This is reasonably feasible in common multi-repo/org Shipit deployments.

### Recommendation
In `StatusHandler#process`, scope commit lookup to stacks whose `Repository` matches the payload's `repository.full_name` (and owner/domain), e.g. join `Commit` to `Stack`/`Repository` and filter by the webhook's repository identity before calling `create_status_from_github!`, rather than matching on `sha` alone across the entire `commits` table.

### Proof of Concept
minitest plan (no live GitHub):
1. Create two `Stack`/`Repository` fixtures: `stack_a` (repo `victim/repo`) and `stack_b` (repo `attacker/repo`), each with a `Commit` sharing the identical `sha` value (simulating forked/copied history).
2. Stub `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (as existing tests do) to simulate a legitimately-signed webhook from `attacker/repo`.
3. POST a `status` webhook body with `repository.full_name == "attacker/repo"`, `sha` equal to the shared SHA, and attacker-controlled `target_url`/`description`/`context` matching `stack_a`'s monitored context.
4. Assert: `stack_a.commits.find_by(sha: shared_sha).statuses.last.target_url == attacker_target_url` even though the webhook's `repository.full_name` was `"attacker/repo"`, i.e. `Status#stack_id == stack_a.id` while `payload['repository']['full_name'] != stack_a.repository.full_name` — proving the cross-repository write.
