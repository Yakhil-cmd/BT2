### Title
Webhook organization used for signature verification is decoupled from the repository the event acts on, enabling cross-tenant forged deploy-status/push events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read straight from the untrusted JSON payload (`repository.owner.login` / `organization.login`). Once the signature is accepted, the actual event handlers (`app/models/shipit/webhooks/handlers/*`) resolve the object to mutate using a *different*, independently-controlled field of the same payload — `repository.full_name` (or, for status events, no repository binding at all). Nothing ties the organization whose secret authenticated the request to the repository/commit that gets written.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`Shipit.github(organization:)` returns the `GitHubApp` configured for that org in `config/secrets*.yml`, with its own `webhook_secret` per `lib/shipit/github_app.rb#initialize` [2](#0-1)  and `#verify_webhook_signature` [3](#0-2) . Because a Shipit instance can host multiple organizations (as shown in `config/secrets.development.shopify.yml`, which lists two independent orgs each with their own `webhook_secret`), an attacker who controls (or is an authorized member of) one onboarded organization — say `attacker-org` — knows that org's own `webhook_secret` and can compute a valid signature for `attacker-org`.

The `create` action then dispatches the *same, single* payload to handlers using an entirely different field:
```ruby
def repository_name
  payload.dig('repository', 'full_name')
end
``` [4](#0-3) 

There is no check anywhere that `repository.owner.login` (used for auth) matches the owner segment of `repository.full_name` (used for the write). An attacker can therefore submit:
- `X-Hub-Signature`: valid HMAC computed with `attacker-org`'s own webhook secret
- payload body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo"}, ...}`

`verify_signature` passes because it looks up `attacker-org`'s secret and the attacker legitimately knows it. The event is then routed to a handler that resolves the target repository/stack via `full_name = "victim-org/victim-repo"`, e.g. `PushHandler#process` calling `Repository.from_github_repo_name(repository_name)` [5](#0-4)  and `Repository.from_github_repo_name` [6](#0-5) .

The worst case is `StatusHandler`, which doesn't even use `repository.full_name` — it updates commit status purely by SHA, globally, across the entire multi-tenant install:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [7](#0-6) 

Since commit statuses gate mergeability/deployability (`merge_status`, deployable checks referenced in `test/models/shipit/stack_test.rb`), an attacker authenticated only as `attacker-org` can forge a `status` webhook (signed with their own secret) for any commit SHA belonging to `victim-org`'s repository, injecting a fabricated `success` status.

This is the same class of bug as the reported `DeleteEncodingRequest()` issue: a value is verified/gated under one assumption (a lock covering `e.requested`; here, "the org authorizing this signature") while a different, unguarded value is what actually gets mutated (`e.requested` deleted without exclusive lock; here, the repository/commit acted upon), breaking the intended binding between the verified entity and the entity affected.

### Impact Explanation
This breaks the binding "organization authenticated == repository/commit written," letting any onboarded-but-untrusted-relative-to-other-tenants organization forge:
- `push` events to trigger `GithubSyncJob`/`sync_github` against another org's stack, or
- `status`/`check_suite` events to mark another org's commit as CI-passing, directly enabling that commit's **unauthorized deploy** (Critical impact bucket: "unauthorized deploy, rollback or merge") since Shipit deploy eligibility relies on commit status.

This qualifies as Critical under the given impact list.

### Likelihood Explanation
Requires the attacker to control (or have webhook access to) at least one organization that is legitimately configured in the same multi-tenant Shipit instance — no privileged Shipit account, API token, or the victim org's secret is needed. Any Shipit deployment onboarding multiple orgs/tenants (a documented, supported configuration, per `config/secrets.development.shopify.yml`) is exposed. This is a realistic, low-effort attack path for an "unprivileged attacker" relative to the victim organization.

### Recommendation
Bind signature verification to the same field used for the write: require that `repository.owner.login` (used to pick the `webhook_secret`) equals the owner segment parsed from `repository.full_name` before dispatching to handlers, or better, resolve the target `Repository`/`Stack` first and verify the signature using that resolved repository's own organization's secret rather than trusting attacker-supplied `owner.login` in isolation. Reject the webhook if the two disagree.

### Proof of Concept
1. Attacker is a member of `attacker-org`, which is configured in Shipit alongside `victim-org` (multi-tenant instance), and knows/controls `attacker-org`'s `webhook_secret`.
2. Attacker crafts a `status` (or `push`) webhook payload:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(attacker-org secret, raw_body)>` and POSTs to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, validates the signature successfully (attacker knows this secret).
5. `Shipit::Webhooks.for_event('status').each { |h| h.call(params) }` → `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `success` status on the victim's commit, with no relation whatsoever to `attacker-org`, enabling that commit to satisfy deploy-status checks in `victim-org`'s stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
