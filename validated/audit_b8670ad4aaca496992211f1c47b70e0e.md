### Title
Fee-on-Transfer Token Deposits Inflate `RequestValueTransfer` Event Value, Draining Bridge Liquidity — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20.requestERC20Transfer` and the 1-step `onERC20Received` path both emit `RequestValueTransfer` with the caller-supplied `_value` rather than the actual tokens received by the bridge. For fee-on-transfer ERC20 tokens, the bridge receives fewer tokens than `_value + _feeLimit`, yet the event records the full `_value`. Bridge operators faithfully relay that event value to the counterpart chain, which mints or transfers the full `_value` to the recipient. The result is that the counterpart chain releases more tokens than the source chain ever locked, progressively draining the bridge's liquidity.

---

### Finding Description

**2-step path (`requestERC20Transfer`):**

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The `safeTransferFrom` call pulls `_value + _feeLimit` from the user. For a fee-on-transfer token, the bridge receives `(_value + _feeLimit) × (1 - feeRate)` — less than requested. `_requestERC20Transfer` is then called with the original `_value`, which is emitted verbatim in the `RequestValueTransfer` event:

```solidity
// BridgeTransferERC20.sol lines 97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // ← user-supplied, not actual received amount
    requestNonce,
    fee,
    _extraData
);
``` [1](#0-0) [2](#0-1) 

**1-step path (`onERC20Received` via `ERC20ServiceChain.requestValueTransfer`):**

```solidity
// ERC20ServiceChain.sol line 45-46
require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
```

The token contract transfers `_amount + _feeLimit` to the bridge (fee-on-transfer reduces what arrives), then calls `onERC20Received` with the original `_amount`. The bridge again emits `_amount` as the bridged value without checking actual receipt. [3](#0-2) [4](#0-3) 

**Relay path (bridge operator → counterpart chain):**

The Go bridge operator reads `valueOrTokenId` directly from the event and passes it unchanged to `HandleERC20Transfer` on the counterpart bridge:

```go
// node/sc/bridge_manager.go lines 338-343

    handleTx, err = bi.bridge.HandleERC20Transfer(
        auth, txHash, from, to, ctpartTokenAddr,
        valueOrTokenId,   // ← taken verbatim from RequestValueTransfer event
        requestNonce, blkNumber, extraData)
``` [5](#0-4) 

The counterpart bridge then mints or transfers exactly `_value` tokens to the recipient:

```solidity
// BridgeTransferERC20.sol lines 68-72

    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [6](#0-5) 

No balance-before/balance-after check exists anywhere in the deposit path to reconcile the actual received amount against the emitted value.

---

### Impact Explanation

**Lock/unlock mode (`modeMintBurn = false`):** Each deposit with a fee-on-transfer token locks fewer tokens on the source bridge than the counterpart releases. The discrepancy equals `(_value + _feeLimit) × feeRate` per transfer. Repeated transfers drain the bridge's ERC20 reserve until it cannot fulfill legitimate withdrawals — an unauthorized transfer of bridged assets.

**Mint/burn mode (`modeMintBurn = true`):** `_requestERC20Transfer` first calls `_payERC20FeeAndRefundChange` (which transfers `_feeLimit` worth of tokens out of the bridge), then calls `burn(_value)`. Because the bridge received only `(_value + _feeLimit)(1 - feeRate)` tokens, the combined outflow (`_feeLimit + _value`) exceeds the actual balance, causing a revert. The bridge becomes non-functional for that token, but no direct drain occurs in this mode.

The lock/unlock mode impact is the critical one: it constitutes an unauthorized transfer of bridged ERC20 assets from the bridge's reserve to recipients on the counterpart chain.

---

### Likelihood Explanation

Any ERC20 token with a transfer fee that is registered with the bridge triggers this. The bridge owner controls token registration, but the bridge is designed to support arbitrary ERC20 tokens. Any user (no special privilege required) who calls `requestERC20Transfer` or `requestValueTransfer` on a fee-on-transfer token registered with the bridge will trigger the discrepancy. The loss accumulates with every transfer.

---

### Recommendation

Record the bridge's token balance before and after the `safeTransferFrom` call, and use the difference as the actual bridged value in the event:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    // derive actual _value from actualReceived minus feeLimit portion
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, actualReceived.sub(_feeLimit), _feeLimit, _extraData);
}
```

Apply the same fix to `onERC20Received` by computing the actual received amount from the balance delta rather than trusting the caller-supplied `_value`. Additionally, document clearly which token types are supported and consider restricting token registration to non-rebasing, non-fee-on-transfer tokens.

---

### Proof of Concept

Assume a fee-on-transfer ERC20 token with a 2% transfer fee is registered with the bridge in lock/unlock mode.

1. Alice calls `requestERC20Transfer(tokenAddr, bob, 1000, 50)`.
2. `safeTransferFrom` pulls 1050 tokens from Alice; bridge receives `1050 × 0.98 = 1029` tokens.
3. `_payERC20FeeAndRefundChange` pays the bridge fee (say 30 tokens) to `feeReceiver` and refunds 20 tokens to Alice. Bridge now holds `1029 - 50 = 979` tokens.
4. `RequestValueTransfer` is emitted with `valueOrTokenId = 1000`.
5. Bridge operator observes the event and calls `handleERC20Transfer(..., 1000, ...)` on the counterpart bridge.
6. Counterpart bridge transfers 1000 tokens to Bob.
7. **Net discrepancy: 1000 released vs 979 locked = 21 tokens drained per transfer.**

Repeating this 48 times with the same parameters drains the entire 1000-token initial bridge reserve, leaving legitimate withdrawers unable to redeem their assets. [7](#0-6) [8](#0-7) [9](#0-8)

func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
