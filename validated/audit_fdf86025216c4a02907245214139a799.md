### Title
Oscript `data_feed[[...]]` provides no built-in staleness/timestamp check, allowing AAs to consume stale oracle data feeds indefinitely - (File: `formula/evaluation.js`)

### Summary
The oscript `data_feed` and `in_data_feed` primitives, used by AAs to consume oracle-posted price data (as in `test/samples/futures_contract.oscript` and `test/samples/option_contract.oscript`), only support filtering by `min_mci` (a lower bound on when the value was posted) and return either the raw `value` or the `unit` hash — never a timestamp or "age" of the datapoint. This mirrors exactly the Chainlink issue cited in the report: the consumer has no way to detect that an oracle has stopped updating and is unknowingly relying on stale data.

### Finding Description
`getDataFeed` in `formula/evaluation.js` resolves `data_feed[[oracles=..., feed_name=..., min_mci=..., ifseveral=..., what=..., type=..., ifnone=...]]` by calling `dataFeeds.readDataFeedValue(...)`. The only recency-related parameter exposed to the AA author is `min_mci`, a *lower* bound: [1](#0-0) 

The `what` parameter can only be `'value'` or `'unit'` — there is no `'timestamp'` or `'mci'` option that would let the AA author retrieve *when* the value was posted so they can enforce an upper bound (i.e., reject data older than N seconds/blocks): [2](#0-1) 

`readDataFeedValue` in `data_feeds.js` picks the latest matching value up to `max_mci` (the current `last_ball_mci`) with no upper-bound freshness check at all — it will happily return a value posted arbitrarily long ago as long as it is `>= min_mci`: [3](#0-2) 

Because `min_mci` only guards the past (data must be *newer than* a fixed floor), and there is no complementary mechanism to require data to be *newer than "now" minus some tolerance*, an AA cannot express "reject if the oracle hasn't posted in the last X units/time" the way Chainlink consumers are advised to check `updatedAt` in `latestRoundData()`.

### Impact Explanation
Any AA that uses `data_feed[[...]]` to price assets, settle options/futures, trigger liquidations, or gate payouts — exactly the pattern shown in `test/samples/option_contract.oscript` and `test/samples/futures_contract.oscript`, which both consult `data_feed[[oracles='X55IWSNMHNDUIYKICDW3EOYAWHRUKANP', feed_name='GBYTE_USD...']]` for settlement — will use the last known price/value even if the oracle address has stopped posting updates entirely. If the real-world price has since diverged (crashed or spiked), any user can trigger the AA with the stale, favorable price to redeem more funds/assets than they are entitled to, or to force an incorrect settlement (e.g., claiming the "yes" outcome once `GBYTE_USD > 60` becomes true only because of a stale positive value), causing fund loss to the AA or to counterparties. This is the same "Blizz Finance"-style class of loss described in the source report, ported to Obyte's AA data-feed primitive.

### Likelihood Explanation
Likelihood is contingent on real-world AA design (an unprivileged AA trigger sender only needs to know the oracle stopped posting/lagging and then send a normal trigger unit), not on any privileged actor. Since `min_mci` is the only guard oscript exposes and it is optional and only a floor, any AA author who doesn't build custom freshness-detection logic on top of `unit`/state variables is exposed by default; the primitive itself gives no native protection or warning. This matches Medium severity: it is a design gap in the oscript feature surface rather than a memory-safety/consensus bug, but it can lead to concrete fund loss in commonly-written oracle-consuming AAs.

### Recommendation
- Extend `data_feed[[...]]` with a native `what='mci'` or `what='timestamp'` option (and/or a `max_age`/`max_mci_age` parameter) so AA authors can directly enforce recency without needing an extra round-trip lookup.
- Document prominently that `min_mci` is a lower bound only and does **not** guarantee freshness; recommend AA authors combine `data_feed[[what='unit']]` with an explicit unit-timestamp lookup and `bounce()` if the datapoint is older than an acceptable threshold.
- Consider adding this validation to the reference oscript samples (`futures_contract.oscript`, `option_contract.oscript`) so developers copying these patterns don't inherit the staleness gap.

### Proof of Concept
1. An AA is deployed with settlement logic analogous to `option_contract.oscript`, where the "yes" outcome pays out when `data_feed[[oracles='ORACLE', feed_name='GBYTE_USD']] > 60`.
2. Oracle `ORACLE` posts `GBYTE_USD = 65` at some MCI, then stops posting entirely (goes offline or is compromised) while the real price crashes far below 60.
3. Any user sends a normal trigger unit to the AA with `trigger.data.winner = 'yes'`.
4. `getDataFeed` (`formula/evaluation.js:600-664`) resolves `data_feed[[...]]` via `dataFeeds.readDataFeedValue` (`data_feeds.js:205-285`), which returns the last stale value of `65` because it only checks `min_mci <= mci <= max_mci`, with no upper bound relative to current time/mci.
5. The AA records `var['winner'] = 'yes'` and pays out the losing/incorrect asset side, resulting in unauthorized/incorrect fund distribution based on stale oracle data — with no built-in mechanism in oscript to have prevented it.
