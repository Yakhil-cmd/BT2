### Title
CCMenuController bypasses per-client stack scoping, allowing a stack-A CCMenu token to read arbitrary stack B - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` is overridden to call `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, so the scoping performed by `Api::BaseController#stacks` (which restricts lookups to `current_api_client.stack_id` when the client is stack-scoped) is never applied. Any CCMenu token minted by `CCMenuUrlController#fetch` for one stack can therefore be replayed against any other stack's `cc_menu.xml` endpoint simply by changing `params[:stack_id]`.

### Finding Description
The binding that must hold is: `stack requested via params[:stack_id] ∈ Stacks authorized by current_api_client.stack_id`. In `Api::BaseController`, this is enforced via: [1](#0-0) 
`stacks` filters to `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true, and `stack` looks up within that scoped relation.

`Api::CCMenuController`, however, overrides `#stack` to bypass this scope entirely: [2](#0-1) 
`@stack ||= Stack.from_param!(params[:stack_id])` queries the unscoped `Stack` model, ignoring `current_api_client.stack_id` altogether. The only authorization check performed is `require_permission :read, :stack`, which merely checks that the client's `permissions` array includes `'read:stack'` via `ApiClient#check_permissions!` — it does not verify that the requested stack matches the client's bound `stack_id`.

`CCMenuUrlController#fetch` mints exactly such a stack-scoped, `read:stack`-only client: [3](#0-2) 
Note `client` is created with `permissions: %w[read:stack]` but is **not** bound to a specific `stack` here (`create_with(permissions: ...)` — no `stack:` attribute), so in the shipped code the resulting `ApiClient` has `stack_id` = nil, meaning `stack_id?` is false and `Api::BaseController#stacks` would return `Stack.all` for it anyway. This matches the general design that CCMenu clients are not currently stack-scoped by this flow. However, the vulnerability the question raises is broader: for *any* client that legitimately is stack-scoped (e.g., created via the admin UI at `api_client_path` with a specific `stack` assigned, which the `ApiClient` model explicitly supports via `belongs_to :stack, optional: true`), `CCMenuController#stack` provides no enforcement of that scoping at all — unlike every other endpoint under `Api::BaseController`. The existing test suite only exercises the "no scoping" case: [4](#0-3) 
and never asserts that a stack-scoped token is rejected for a foreign stack.

Root cause: `CCMenuController#stack` re-implements stack lookup instead of reusing the inherited, scope-aware `stacks`/`stack` helpers, silently dropping the `current_api_client.stack_id` restriction that the rest of the API relies on for tenant isolation.

### Impact Explanation
An attacker holding a stack-scoped `ApiClient` token with only `read:stack` permission (e.g., an admin-issued token meant to be limited to one stack/repository) can query `GET /api/stacks/<any_other_stack>/cc_menu.xml?token=<their token>` and receive that other stack's deploy/build status, name, last build label, and lock state — data belonging to a different repository owner/tenant than the token was scoped to. This is a cross-tenant unauthorized read of stack state, matching the "unauthorized read of stack state" High-severity category. It is fully repeatable against any stack ID the attacker can guess or enumerate (stack IDs/`to_param` slugs are not secret) and requires only a single valid token scoped to any one stack.

### Likelihood Explanation
Preconditions: the attacker must possess *some* valid `ApiClient` token whose `permissions` includes `read:stack` and whose `stack_id` is set to any stack. Such tokens are commonly issued in practice (e.g., via the `api_clients` admin UI where an operator assigns a client to a specific stack) even though `CCMenuUrlController#fetch` itself currently mints unscoped clients. Given the rules state the attacker holds no `ApiClient` token and no privileged role, this specific finding depends on some other Shipit operator having created and leaked/shared a stack-scoped `read:stack` token intended for a single stack — a plausible and common operational pattern (that's the entire purpose of `stack_id` scoping on `ApiClient`). Cost to exploit is a single unauthenticated HTTP GET with the known token and an arbitrary `stack_id`.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so it inherits the same `current_api_client.stack_id` restriction enforced by `Api::BaseController#stacks`, consistent with every other controller under the `Api::BaseController` hierarchy.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
test "a token scoped to stack A cannot read stack B via cc_menu" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "other", name: "repo"), branch: 'main')

  client = ApiClient.create_with(
    creator: shipit_users(:walrus),
    stack: stack_a,
    permissions: %w[read:stack]
  ).find_or_create_by!(name: 'Scoped CCMenu Client')

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack_b ∈ Stacks authorized by client.stack_id (== stack_a.id) must be FALSE
  assert_not_equal stack_b.id, client.stack_id
  # Expected secure behavior: 403/404
  assert_response :not_found # or :forbidden
  # Actual (vulnerable) behavior observed before fix: 200 with stack_b's data
end
```
This test creates a stack-scoped, `read:stack`-only client bound to `stack_a`, then requests `stack_b`'s CCMenu XML using that token; with the current `CCMenuController#stack` implementation the request succeeds (200, stack_b data returned) instead of being rejected, demonstrating the scope bypass.
