## Membership webhook confusion enables silent escalation into `Shipit.github_teams` authorization

### Title
Cross-organization webhook signature confusion allows an onboarded org to grant users membership in another org's authorization team - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the `github_app` (and thus the HMAC secret) used to authenticate an incoming webhook from a field that is independent of, and can diverge from, the field the event `Handler` actually trusts to decide *which* organization/team a `membership` event applies to. An attacker who legitimately controls one onboarded GitHub organization (and therefore knows that org's `webhook_secret`) can forge a `membership` webhook whose HMAC is verified against their own org, while the payload's `organization.login` (the field `MembershipHandler` uses to create/target a `Team`) points at a different, victim organization/team that is part of `Shipit.github_teams`.

### Finding Description
`repository_owner`, used to pick the GitHub App/secret for signature verification, is derived as: [1](#0-0) 
i.e. it prefers `repository.owner.login` and only falls back to `organization.login` when no `repository` key is present at all.

`verify_signature` then does: [2](#0-1) 
so the HMAC is checked against `Shipit.github(organization: repository_owner)`'s `webhook_secret`.

`MembershipHandler`, however, never looks at `repository_owner`/`repository.owner.login` — it exclusively trusts `params.organization.login` to find-or-create the `Team` and add/remove the member: [3](#0-2) 

Because `dig('repository', 'owner', 'login')` and `dig('organization', 'login')` are two independent, attacker-controlled JSON paths in the same raw body, an attacker who is a legitimate admin of an onboarded organization (call it `AttackerOrg`, which per the documented multi-org setup has its own `webhook_secret` known to whoever set up its GitHub App) can craft a body containing:
- `repository.owner.login = "AttackerOrg"` (used only for signature-app selection)
- `organization.login = "VictimOrg"` (the organization/team actually mutated)
- `team`, `member` fields identifying an arbitrary team/member

Since the HMAC covers the raw body itself (not a specific field), and the attacker legitimately knows `AttackerOrg`'s secret, `verify_webhook_signature` succeeds: [4](#0-3) 

`Shipit::Webhooks.for_event('membership')` then dispatches to `MembershipHandler`, which trusts `params.organization.login` unconditionally to create/find the `Team` and add the attacker-chosen `member` to it: [5](#0-4) 

The broken binding is: **organization that authenticated the request (`repository_owner` used for `verify_webhook_signature`) ≠ organization/team whose membership is actually written (`params.organization.login`)**. Team membership feeds directly into `User#authorized?`, which gates access based on `Shipit.github_teams`: [6](#0-5) 

### Impact Explanation
If any of the teams configured in `Shipit.github_teams` (used to gate authorization/login) belongs to `VictimOrg`, an attacker who only controls a *different*, unrelated onboarded organization can add an arbitrary GitHub login (including their own) to that authorization team record inside Shipit's database, without ever having real GitHub membership in `VictimOrg`. Combined with `User#authorized?`'s check (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`), this is a path to escalate into `Shipit.github_teams` authorization — one of the explicitly listed High-impact outcomes.

### Likelihood Explanation
This requires the deployment to onboard more than one GitHub organization (a documented, supported configuration — "Using Multiple Github Applications") and for the attacker to control the webhook secret of one of those organizations while a *different* onboarded organization's team is used for `Shipit.github_teams` authorization. This is a plausible configuration for any Shipit instance serving multiple business units/orgs from one deployment, but does not apply to single-organization deployments.

### Recommendation
`MembershipHandler` (and any other handler that trusts an org/repo identifier from the payload for authorization-relevant writes) must be bound to the same organization that was cryptographically verified in `WebhooksController#verify_signature`, not re-derived independently from a different JSON path. Concretely, pass the verified `repository_owner` (or the specific GitHub App/organization context that succeeded signature verification) into the handler dispatch, and have `MembershipHandler` assert `params.organization.login == verified_organization` before creating/mutating any `Team`/`Membership` record, rejecting the event otherwise.

### Proof of Concept
1. Onboard `AttackerOrg` as a second organization in `config/secrets.yml` (documented multi-org setup); attacker knows its `webhook_secret`.
2. Ensure `VictimOrg`'s team is included in `Shipit.github_teams`.
3. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "victim-team", "slug": "victim-team", "url": "https://api.github.com/teams/999" },
  "organization": { "login": "VictimOrg" },
  "member": { "login": "attacker-account" },
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
4. Set `X-Hub-Signature: sha1=<HMAC-SHA1(AttackerOrg_webhook_secret, raw_body)>`.
5. `verify_signature` resolves `repository_owner = "AttackerOrg"`, verifies successfully with `AttackerOrg`'s secret.
6. `MembershipHandler` creates/finds Team `github_id: 999` with `organization: "VictimOrg"` and adds `attacker-account` as a member, regardless of the fact that only `AttackerOrg`'s credentials were verified.
7. If `Team#id` is in `Shipit.github_teams`, `attacker-account`'s `User#authorized?` now returns `true`.

**Note:** I could not fully trace whether `Shipit.github_teams` is typically configured to a team belonging to a *specific single* organization versus validated app-wide across all onboarded orgs in a real deployment — that operational detail affects real-world exploitability and would benefit from further review in `lib/shipit.rb`'s `github_teams` configuration handling, which was not fully inspected in this pass.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
