This confirms the binding: `Shipit.github(organization:)` selects a `GitHubApp` config (and its `webhook_secret`) keyed by organization login only, per `github_app_config` and `TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`. The webhook signature check in `WebhooksController#verify_signature` also selects the secret solely by `repository_owner` (the organization login from the payload), not by the specific repository being written.### Title
Webhook signature verification is scoped to the organization login, not the target repository, allowing forged writes to any repository under a shared org-level webhook secret - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret used to validate an inbound GitHub webhook solely from `repository_owner` (the organization login taken from the payload), via `Shipit.github(organization: repository_owner)` → `Shipit::GithubApp` config. The event handlers that actually mutate state (create/archive/unarchive review stacks, update pull requests, sync repositories) key their target off a different, independently-controlled field of the same payload: `params.repository.full_name` / `payload.dig('repository', 'full_name')`. Because the secret lookup binds to "organization authenticated" while the mutation binds to "repository written," a webhook secret configured at the organization level authenticates payloads for *any* repository name claimed inside that same organization, not just the repository the secret was provisioned for.

### Finding Description
`verify_signature` resolves the app/secret purely by organization: [1](#0-0) 

`repository_owner` is read from the untrusted, attacker-supplied payload: [2](#0-1) 

The secret itself is configured and looked up strictly by organization key, with no per-repository scoping: [3](#0-2) 

`GitHubApp#verify_webhook_signature` then just HMAC-verifies the raw body against that organization-scoped secret: [4](#0-3) 

However, all the handlers that perform actual writes (create, archive, unarchive review stacks; update pull request state; find target stacks) resolve their target repository from `params.repository.full_name`, a field whose only tie back to the authenticated organization is that GitHub's real webhook sender would set it consistently — but nothing in the verification path enforces that the `repository.full_name`'s owner segment actually equals `repository_owner`/the organization used for the secret lookup: [5](#0-4) [6](#0-5) [7](#0-6) 

This is the direct analog of the reported bug class: a security-critical check (`sessionCounter == 0` in the report; here, "this payload really originates for repository X") is enforced against one identifier (`msg.sender`/module state in the report; here, the organization login used to pick the secret), while the state-mutating action that follows is keyed to a different, unchecked identifier (module removal proceeding regardless of `disable()`'s success; here, `repository.full_name` used for the actual write regardless of whether it matches the organization whose secret validated the signature). In both cases a binding that should be enforced end-to-end (module state vs. removal completion; organization authenticated vs. repository written) is broken because the code checks one side and acts on the other without cross-validating them.

Concretely: any two repositories `orgX/RepoA` and `orgX/RepoB` that share the same Shipit organization (and hence the same `webhook_secret` under `github_app_config`) are cross-authenticated. A webhook correctly signed for `RepoA` (i.e., an attacker who has, or can obtain, delivery access/secret knowledge scoped to `orgX`) can be replayed/crafted with `repository.full_name` rewritten to `orgX/RepoB`, and `verify_signature` will still accept it because the signature check never inspects `repository.full_name` — only `repository_owner`.

### Impact Explanation
This crosses the "cross-repository writes" impact bucket explicitly called out as Critical: a payload accepted for one repository's webhook trust can be used to trigger state mutations (review stack archive/unarchive/creation, pull-request state updates, sync jobs) against a different repository within the same Shipit-configured organization. This is exactly the deployment-trust binding break the task calls out ("an organization that authenticated versus the repository that is written").

### Likelihood Explanation
Medium: it requires knowledge of an organization-scoped `webhook_secret` (attacker needs to control or observe a legitimately signed delivery for at least one repository in that org — e.g., via a repository under the same org that they have delivery/webhook configuration visibility for), and it requires the target repository to already exist as a `Shipit::Repository`/`Stack` under Shipit for the handler to act on it. This is not a zero-precondition bug but does not require any Shipit application credentials (`ApiClient` token, session, GitHub App private key) — only knowledge of the shared org-level webhook secret used purely for HMAC signing.

### Recommendation
Bind the signature-selection organization to the repository actually being acted upon: after resolving `repository_owner`/the matched `Shipit::GithubApp`, verify that `payload.dig('repository', 'full_name')`'s owner segment matches `repository_owner` (and reject if not), or better, resolve the target `Shipit::Repository`/`Stack` first and use *its* owner/organization to select the verification secret rather than trusting the payload-level `owner.login` field independently from the `full_name` field used downstream.

### Proof of Concept
1. Configure Shipit with a single organization `orgX` containing two repositories `orgX/RepoA` (Shipit-tracked, has webhook configured with secret `S`) and `orgX/RepoB` (also Shipit-tracked).
2. Obtain a validly-signed webhook payload for `orgX/RepoA` (signature computed with `S` over a `pull_request` event body).
3. Modify the JSON body's `repository.full_name` (and `pull_request`/`number` fields as needed) to target `orgX/RepoB`, leaving the raw signature unchanged is insufficient (HMAC covers the raw body) — but since `S` is known/derivable to the attacker via legitimate access to RepoA's webhook configuration, recompute the HMAC over the modified body using the same organization secret `S`.
4. POST to `/webhooks` with `X-Hub-Signature` set to the recomputed HMAC.
5. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` passes because it only checks the organization-scoped secret via `repository_owner` (`orgX`), not `repository.full_name`.
6. The dispatched handler (e.g., `PullRequest::OpenedHandler` / `ReviewStackAdapter#create!`) then archives/unarchives/creates a review stack, or performs other state mutation, on `orgX/RepoB` — a repository the attacker was not otherwise authorized to affect via `RepoA`'s webhook trust.

  end
