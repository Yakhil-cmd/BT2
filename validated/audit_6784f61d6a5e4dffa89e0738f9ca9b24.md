### Title
CCMenu API endpoint bypasses per-stack token scoping, letting a stack-scoped `ApiClient` read the state of any stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds every request to the stack(s) an `ApiClient` is authorized for: `stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a single stack, and `stack` resolves `params[:stack_id]` through that scoped relation. [1](#0-0)  `Shipit::Api::CCMenuController` overrides `stack` to resolve directly against the global `Stack` model instead of the scoped `stacks` relation, breaking the binding between "the stack a token authorizes" (`ApiClient#stack_id`) and "the stack the request actually touches" (`params[:stack_id]`). [2](#0-1) 

### Finding Description
`ApiClient` supports scoping a token to a single stack via `belongs_to :stack, optional: true`; `BaseController#stacks` enforces that scope: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `BaseController#stack` resolves the URL parameter through that scoped relation via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`CCMenuController` only checks the generic permission bit (`require_permission :read, :stack`, i.e. `ApiClient#check_permissions!` which merely checks that `"read:stack"` is in the client's `permissions` array, with no per-stack awareness) [3](#0-2)  and then re-implements `stack` to bypass the scoped lookup entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the same class of bug as the external report: a piece of state that is supposed to gate what is authorized (`epoch[_tigAsset]` in the report; `current_api_client.stack_id` here) is silently skipped on a certain code path (`totalShares == 0` short-circuit in the report; the overridden `stack` method here), so the object actually acted upon (`bond`'s mint epoch / `stack`) no longer matches what the authorization step intended to bind.

### Impact Explanation
Any `ApiClient` token that has been deliberately scoped to a single stack (e.g. handed to a third-party integration that should only see one repository/environment) and holds `read:stack` permission can be replayed against the `GET /api/stacks/*stack_id/ccmenu` route for **any other stack** in the Shipit instance simply by changing `stack_id` in the URL, since `CCMenuController#stack` never consults `current_api_client.stack_id`. The response leaks that stack's `merge_status`, lock state, latest deploy id, and build activity — cross-stack disclosure of deploy/build state that the token was never authorized to see. This matches the High-severity bucket for "escalation into authorization scope / unauthenticated read of stack state or deploy output."

### Likelihood Explanation
Exploitation requires only possession of any valid `ApiClient` token with `read:stack` permission (even one intentionally scoped to a single, low-sensitivity stack) — a routine, low-privilege credential many integrations hold — and knowledge of another stack's `owner/repo/environment` identifier, which is often guessable/public (GitHub org/repo names). No additional GitHub or session credentials are needed, and the endpoint also supports authenticating via a `token` query-string parameter, further easing automated abuse. [4](#0-3) 

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it using the scoped `stacks` relation, mirroring `BaseController#stack`) so that stack-scoped tokens can only resolve stacks within their authorized scope:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Add a regression test asserting that a client scoped to stack A receives a 404/403 (not the CCMenu XML) when requesting stack B's `ccmenu` endpoint.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack: shipit` with permission `read:stack` (mirrors fixture `here_come_the_walrus`). [5](#0-4) 
2. Authenticate as that client and request the CCMenu endpoint for a *different* stack, e.g. `GET /api/stacks/other-owner/other-repo/environment/ccmenu?token=<token>`.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unconditionally instead of `stacks.from_param!`, the request succeeds and returns that other stack's build/merge status XML, even though the token's `stack_id` is set to the `shipit` stack only — demonstrated by the existing test helper pattern in `test/controllers/api/ccmenu_controller_test.rb` (`get :show, params: { stack_id: @stack.to_param }` succeeding for the authenticated client regardless of `@client.stack`). [6](#0-5)
