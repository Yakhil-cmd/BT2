### Title
Cross-organization webhook forgery via organization/repository binding mismatch in signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC `webhook_secret`) used to authenticate an inbound webhook based on `repository_owner`, which is read from the *same untrusted JSON body* (`repository.owner.login`, falling back to `organization.login`) that later drives which `Repository`/`Stack` the webhook handlers act on. In Shipit's supported multi-tenant configuration (multiple GitHub Apps per organization, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), nothing binds the organization whose secret validated the signature to the repository named in `repository.full_name` that the handlers subsequently mutate.

### Finding Description [1](#0-0) 

`verify_signature` computes `repository_owner` from the JSON body and fetches the corresponding `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`: [2](#0-1) 

The whole raw body is what's HMAC-verified [3](#0-2) , but crucially the *value* used to select which secret to check against (`repository.owner.login` / `organization.login`) is independent of the *value* used afterwards by the handler to decide which repository/stack the payload affects (`repository.full_name`): [4](#0-3) 

`Repository.from_github_repo_name` looks up the target `Repository` purely from `full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

On a Shipit instance configured with multiple GitHub Apps (one per tenant organization, as documented and tested), an attacker who legitimately administers "OrgOne" (and therefore knows OrgOne's `webhook_secret`, since they configured that GitHub App themselves) can:
1. Craft a webhook JSON body with `repository.owner.login = "OrgOne"` (so `verify_signature` selects and validates against OrgOne's known secret) but `repository.full_name = "OrgTwo/victim-repo"` (a different tenant's tracked repository).
2. Compute a valid `X-Hub-Signature` over that body using OrgOne's `webhook_secret`.
3. POST it to `/webhooks`.

`verify_signature` passes (correct secret for the claimed `repository_owner`), and `create` dispatches the forged payload to the real handlers, which resolve the affected `Stack` using `repository.full_name = "OrgTwo/victim-repo"` — completely bypassing the intended per-organization isolation of webhook trust.

This is directly analogous to the reported `FCNProduct.sol` bug: the value that is cryptographically checked (`repository_owner` used for signature selection) is not the same value that is subsequently acted upon (`repository.full_name` used for the actual write), and the binding between the two is never enforced.

### Impact Explanation
Exploiting this allows an attacker who only controls one tenant organization on a multi-org Shipit deployment to forge trusted webhooks against a *different* tenant's repositories/stacks:
- `push` events → `PushHandler` calls `stack.sync_github`, enqueuing `GithubSyncJob` for OrgTwo's stack with an attacker-chosen `expected_head_sha`, pulling and appending real commits from GitHub for the victim repo. [6](#0-5) [7](#0-6) 
- `status` events → `StatusHandler` writes fabricated CI statuses onto OrgTwo's commits based only on `sha` matching, with no repository/owner cross-check: [8](#0-7) . Since deployability/continuous-delivery gating relies on commit statuses (`checks?`), forging a green status can unblock or trigger an unauthorized deploy via `trigger_continuous_delivery`. [9](#0-8) 
- `pull_request`/`check_suite` handlers similarly key off `repository.full_name` for provisioning/deprovisioning review stacks belonging to another tenant.

This meets the "Critical: unauthorized deploy / cross-repository writes" bar defined in scope, since a low-privilege attacker (owner of one tenant org's GitHub App) can force state changes, commit ingestion, and deploy triggers on a different, victim tenant's repository — without ever needing the victim's secrets, session, or API tokens.

### Likelihood Explanation
Requires: (a) the Shipit instance to be configured for multiple GitHub organizations (an explicitly documented and supported configuration), and (b) the attacker to control at least one of those tenant orgs' GitHub App / webhook secret (a normal, unprivileged act of being an org owner elsewhere — not a Shipit credential). Given multi-org support exists specifically to let independent orgs share one Shipit instance, this is a realistic deployment and a directly reachable, credential-light attack.

### Recommendation
After resolving the target repository/stack from the payload (`repository.full_name`), verify that its owner matches the `repository_owner` (or `organization.login`) used to select the verifying GitHub App/secret, and reject the webhook otherwise. Alternatively, derive the verification organization from `repository.full_name`'s owner component only (not a separately-trusted `repository.owner.login`/`organization.login` field), ensuring the same value drives both authentication and the write target.

### Proof of Concept
1. Configure Shipit with two tenant orgs, `OrgOne` and `OrgTwo`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md`'s multi-org setup), each tracking their respective repositories/stacks.
2. As the administrator of `OrgOne`'s GitHub App (attacker), build a `status` webhook payload:
```json
{
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "sha": "<known commit sha of OrgTwo/victim-repo>",
  "state": "success",
  "context": "ci/forged"
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, body)`.
4. `POST /webhooks` with header `X-Github-Event: status` and the above body/signature.
5. `verify_signature` resolves `repository_owner = "OrgOne"`, fetches OrgOne's app, and the signature validates successfully.
6. `StatusHandler` then creates a `success` status on `OrgTwo`'s commit (matched only by `sha`), potentially unblocking/triggering continuous delivery for `OrgTwo`'s stack — despite the attacker having no relationship to `OrgTwo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
