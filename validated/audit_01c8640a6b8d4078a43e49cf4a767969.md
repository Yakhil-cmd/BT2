### Title
GCM Authentication Tag Length Not Validated Before `setAuthTag()` in Device Message Decryption - (File: device.js)

### Summary
`decryptPackage()` in `device.js` decrypts device-to-device messages (chat, private payment chains, signing requests) using AES-GCM. It decodes the attacker-controllable `authtag` field straight from the wire into a `Buffer` and passes it to `decipher.setAuthTag()` without ever validating that its length matches the expected 16-byte (128-bit) GCM tag size, mirroring the root cause of CVE-2018-10903/GHSA-fcf9-3qw3-gxmj (`finalize_with_tag` not enforcing a minimum tag length, leaving it to the caller).

### Finding Description
In `decryptPackage()`, the only validation performed on the incoming encrypted package is a `typeof` check: [1](#0-0) 

No length check is applied to `objEncryptedPackage.authtag` before it is base64-decoded and handed to `setAuthTag`: [2](#0-1) 

The correct/expected tag length is 16 bytes, as produced by `createEncryptedPackage()`, which calls `cipher.getAuthTag()` on `aes-128-gcm`: [3](#0-2) 

Because `decryptPackage()` never checks `authtag.length` (e.g., rejecting anything shorter than 16 bytes) before calling `setAuthTag()`, the code relies entirely on the underlying crypto implementation to reject short/forged tags. This is exactly the failure mode described in the advisory: the application layer must validate tag length itself because the crypto primitive is not guaranteed to enforce it — ocore ships and runs on multiple crypto backends (the code contains explicit browserify/Cordova workarounds around this same decryption path), where AES-GCM tag-length enforcement has historically been inconsistent, permitting truncated tags to pass with a small but non-negligible probability (as low as 1/256 for a 1-byte tag).

The attack surface is reachable by any device correspondent or a hub relaying `hub/deliver` messages: the hub-side validation of `hub/deliver` only checks presence of the fields, not their lengths: [4](#0-3) 

An attacker who can guess or brute-force even a short tag (particularly on a weakly-enforcing GCM backend) can forge the authenticated ciphertext content, causing `decryptPackage()` to accept attacker-controlled plaintext as if it came from the legitimate correspondent, e.g. `private_payments`, `signature`, or `payment_notification` message bodies processed in `wallet.js`.

### Impact Explanation
Successful tag forgery breaks the confidentiality/integrity guarantee of the encrypted device-messaging channel used for private payment chains and multisig co-signing. A forged/injected message could be used to spoof a `private_payments` or `signature` message to a wallet or AA-cosigning device, potentially misleading it about incoming private payments or supplying manipulated signing prompts — undermining node/wallet agreement on the validity of private-payment data received via this channel. This falls under the allowed "private payment chains" / "wallet and contract message handling" categories.

### Likelihood Explanation
Exploitability is probabilistic and depends on whether the runtime's AES-GCM implementation actually enforces a minimum/exact tag length (Node's native `crypto` binding on server-side is largely hardened today, but ocore explicitly supports Cordova/browserify environments with different crypto backends, as shown by the chunking workarounds around this very code path). Where enforcement is weak, an attacker gets a low but non-zero (as high as 1-in-256 for extreme truncation) chance per attempt to forge a valid tag, and the operation is repeatable at negligible cost, making it a genuine — though probabilistic and backend-dependent — risk rather than a guaranteed break.

### Recommendation
Add an explicit length check on `objEncryptedPackage.authtag` (require it to decode to exactly 16 bytes) before calling `decipher.setAuthTag()` in `decryptPackage()`, independent of what the underlying crypto library enforces, matching the defense-in-depth fix applied upstream for CVE-2018-10903.

### Proof of Concept
1. Attacker crafts an `encrypted_package` with a valid `iv`, `dh` fields, and a truncated `authtag` (e.g., 1 byte instead of 16), together with attacker-chosen ciphertext bytes.
2. Attacker sends this via `hub/deliver` (validated only for field presence, not length) to the target device, or embeds it in a `private_payments`/`signature` payload.
3. On a receiving runtime where the GCM tag length isn't strictly enforced by the crypto backend, `decipher.setAuthTag(authtag)` followed by `decipher.final()` in `decryptPackage()` (`device.js:444-462`) may succeed with a non-negligible probability, allowing the forged plaintext JSON to be accepted and processed by `wallet.js`'s `handleMessageFromHub`.
