Found the analog. `Shipit::Api::CCMenuController` binds the token to the requesting stack ID *without checking that the ApiClient's own `stack_id` matches the URL's `stack_id`*.

### Title
Unscoped `stack_id` param allows a CCMenu token minted for one stack to read any other stack - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` resolves `params[:stack_id]` directly via `Stack.from_param!`, bypassing the `stacks` scoping helper defined in `Api::BaseController` that restricts a scoped `ApiClient` to `Stack.where(id: current_api_client.stack_id)`.

### Finding Description
`Api::BaseController#stacks` and `#stack` are the standard mechanisms that enforce "a stack a token authorizes == a stack it touches": [1](#0-0) 
`CCMenuController` overrides `#stack` and never calls the scoped `stacks` helper, instead resolving the stack directly from the raw `params[:stack_id]`: [2](#0-1) 
`CCMenuUrlController#fetch` mints a per-user, stack-scoped `read:stack` `ApiClient` (`stack` is not set on the created client at all — only `permissions` and `creator`), and hands the resulting token to the browser: [3](#0-2) 
`ApiClient#check_permissions!` only checks the `permissions` array, never `stack_id`: [4](#0-3) 
Because the token created by `CCMenuUrlController` has no `stack` attribute set (`stack_id` is `nil`), and `CCMenuController#authenticate_api_client` accepts any token via `ApiClient.authenticate(params[:token])` and then resolves `stack` independently from `params[:stack_id]` (not from `current_api_client.stack_id`), the token is not actually bound to the stack it was minted for. The equality that should hold — `token.stack_id == requested_stack_id` — is never checked in this controller; only `token.permissions.include?('read:stack')` is checked. Any holder of a `read:stack` token (e.g. one leaked from a CCMenu URL for stack A) can supply a different `stack_id` in the URL and read task/deploy status for stack B.

### Impact Explanation
This is an unauthenticated read of stack/task state for stacks the token was never issued for, matching the "unauthenticated read of stack state, task streams or deploy output" High-impact class in this analysis. Because `Api::CCMenuController` bypasses the `stacks` scoping defined in `BaseController`, a token that was intended to be single-stack scoped instead grants global read access to every stack's build status, similarly to how the `COLLATERAL_MINTER_ROLE` bug let a role holder mint against tokenIds far beyond what should have been possible.

### Likelihood Explanation
Any `read:stack` scoped client (in practice: any CCMenu URL a legitimate user requested for a stack they have access to) is sufficient — no privileged Shipit session, GitHub identity, or webhook secret is needed. Since CCMenu tokens are embedded in plaintext URLs meant to be pasted into third-party CI dashboard tools, exposure of the token by design is common, amplifying the impact of the missing stack binding.

### Recommendation
In `Api::CCMenuController#stack`, use the inherited `stacks` scope (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])` so tokens are restricted the same way other API controllers are. Additionally, `CCMenuUrlController#client` should set `stack:` on the created `ApiClient` so a `stack_id` is actually recorded and enforceable.

### Proof of Concept
1. User A visits `/repo/stack-a/ccmenu_url` (or equivalent path served by `CCMenuUrlController#fetch`) and receives a URL containing `token=<TOKEN_A>` for `stack-a`.
2. Attacker obtains `TOKEN_A` (e.g., via a shared CI dashboard configuration, log, or referrer leakage — no special privilege required beyond having seen the URL).
3. Attacker requests `GET /api/stack-b/ccmenu.xml?token=<TOKEN_A>`.
4. `authenticate_api_client` in `Api::CCMenuController` accepts `TOKEN_A` via `ApiClient.authenticate`, `require_permission :read, :stack` passes because `TOKEN_A` has `read:stack` in `permissions`, and `#stack` resolves `stack-b` directly from `params[:stack_id]`, unrelated to the token's origin.
5. Attacker receives `stack-b`'s build/deploy status, despite `TOKEN_A` never being authorized for `stack-b`.
