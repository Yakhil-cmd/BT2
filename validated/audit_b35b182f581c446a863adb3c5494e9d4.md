### Title
`load_rules()` resolves `.claude/hookify.*.local.md` via process-relative glob instead of a bound workspace root, allowing cwd drift to load untrusted rule files - ([File: plugins/hookify/core/config_loader.py])

### Finding Description
`load_rules()` builds its glob pattern with `os.path.join('.claude', 'hookify.*.local.md')` and calls `glob.glob(pattern)`, which resolves purely against the Python process's current working directory at the moment each hook script runs. [1](#0-0) 
There is no explicit repository/workspace root resolution (no use of `CLAUDE_PROJECT_DIR`, no `os.getcwd()` anchoring to a git root, no path passed in from `input_data`). Every hook entrypoint (`userpromptsubmit.py`, `pretooluse.py`, `posttooluse.py`, `stop.py`) calls `load_rules()` with no cwd argument, relying entirely on ambient process cwd. [2](#0-1) [3](#0-2) 

The plugin's own documentation confirms rules are expected to be written and read relative to "the current working directory (where Claude Code was started)" and explicitly does not describe any repo-root pinning mechanism. [4](#0-3) 

I was unable to find, within this repository's index, the code that spawns these hook subprocesses (that logic lives in the Claude Code CLI/harness itself, not in this plugin repo), so I could not directly confirm from this codebase whether Claude Code's harness always launches hook subprocesses with `cwd` pinned to the original workspace root regardless of `cd` commands executed during a session, or whether it re-derives cwd per invocation in a way that could drift into a nested/submodule directory. This is a genuine limitation of what's verifiable from the plugin code alone — the actual trust boundary (whether cwd can drift) is enforced/controlled outside this repo's indexed files.

### Impact Explanation
If the Claude Code harness's hook-invocation cwd can ever differ from the top-level trusted project root (e.g., due to a nested submodule, monorepo package directory, or a Bash `cd` prior to a tool call within a session), `load_rules()` would silently pick up `.claude/hookify.*.local.md` files from whatever directory happens to be the process cwd at hook-execution time. That means:
- An attacker-controlled subdirectory's `hookify.*.local.md` rules (with `action: warn`/`block` and injected `message` text delivered to Claude via the hook's `systemMessage`/output) could be evaluated and injected as if they were the trusted top-level project's guardrails.
- Conversely, the trusted top-level project's real guardrail rules (e.g., "block `rm -rf`", "block writing secrets to `.env`") would silently not be loaded/enforced when cwd has drifted into a subdirectory, defeating the security guard without any error or warning to the user (errors are swallowed via broad `except Exception` blocks that just print to stderr and continue). [5](#0-4) 

This matches a trust-boundary/workspace-scoping bypass class of impact: content from a lower-privilege directory can impersonate/override the higher-privilege project's enforced hook configuration, or a real guard can be silently bypassed.

### Likelihood Explanation
Exploitability is entirely contingent on whether Claude Code's harness ever invokes these hook scripts with a cwd other than the fixed workspace root it started in. Within the plugin code itself there is no protection against this — `load_rules()` never validates or anchors the directory it globs against a known-trusted root, and no test in this repo exercises cwd drift. Since I could not verify the harness-side cwd-binding behavior from the indexed files, I cannot confirm this is exploitable end-to-end without further investigation into the Claude Code CLI internals (outside this plugin repository).

### Recommendation
Anchor rule discovery to an explicitly resolved, trusted workspace root rather than ambient `cwd`:
- Accept an explicit `project_root` (e.g., from `CLAUDE_PROJECT_DIR` env var, if the harness sets one, or a value passed via hook `input_data`) into `load_rules()`/`load_rule_file()` instead of implicit relative globbing.
- If no explicit root is available, resolve and pin the root once (e.g., first hook invocation in a session) and reuse that resolved path for all subsequent hook calls in the same session, rather than re-deriving via `os.path.join('.claude', ...)` + `glob.glob()` against whatever cwd is active per-call.
- Add an integration test that invokes `load_rules()` with varying `cwd` values (top-level vs. nested subdirectory) to assert the rule set does not change based on process cwd.

### Proof of Concept
Integration test plan (pseudocode):
1. Create `top_level/.claude/hookify.trusted.local.md` with a `block` rule for `rm -rf`.
2. Create `top_level/subdir/.claude/hookify.attacker.local.md` with a permissive/injected rule (or no rules at all, to simulate omission).
3. Call `config_loader.load_rules(event='bash')` twice: once with `os.chdir('top_level')` and once with `os.chdir('top_level/subdir')`.
4. Assert: expected behavior is identical rule set (bound to `top_level`) in both cases; actual observed behavior (per current code) is that the loaded `Rule` list differs based on cwd — demonstrating the trusted top-level rule is silently dropped when cwd is `subdir`, and/or the attacker's `subdir` rule is loaded in its place.

Because I could not confirm from this repo whether the Claude Code harness actually allows hook-invocation cwd to drift from the workspace root in practice, this finding is reported with that caveat: the code-level weakness (missing explicit root binding) is real and demonstrable via the PoC above, but full exploitability depends on harness behavior not present in this repository's indexed contents.
