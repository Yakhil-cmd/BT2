### Title
Reward harvesting in `pallet-asset-rewards` permanently freezes accrued rewards for any staker blocked by the underlying reward asset - ([File: substrate/frame/asset-rewards/src/lib.rs])

### Summary
`pallet-asset-rewards::harvest_rewards` (and its internal transfer) always sends the accrued reward directly to the fixed `staker` account with no way to redirect payment to an alternate beneficiary. If the reward asset is a `pallet-assets` asset whose Freezer/Admin later `block()`s that staker's account (a normal, permissioned, non‑attacker action available on any `pallet-assets` asset, analogous to a stablecoin issuer blacklisting an address), every subsequent `harvest_rewards` call for that staker fails with `TokenError::Blocked`, and because the failing transfer uses `?` before the staker's reward counter is reset, the pending reward amount remains stuck in `PoolStakers` forever, unclaimable by anyone, exactly mirroring the reported Derby `MainVault::withdrawRewards()` issue where a `vaultCurrency` blacklist permanently locks a user's rewards because no `recipient` argument exists.

### Finding Description
`harvest_rewards` is a permissionless, non-privileged extrinsic: [1](#0-0) 
The function computes `pending_rewards` for `staker` and pays them out with:
```
T::Assets::transfer(
    pool_info.reward_asset_id,
    &pool_info.account,
    &staker,
    staker_info.rewards,
    Preservation::Expendable,
)?;
```
There is no `beneficiary`/`recipient` parameter — the destination account is hard-coded to `staker` (either the caller or, after pool expiry, any account specified by a third caller, but the transfer destination is still that fixed `staker`).

`pallet-assets` (a typical `T::Assets` fungibles implementation) supports blocking any account for a specific asset via a signed call from that asset's `freezer` role: [2](#0-1) 
`AccountStatus::Blocked` is defined so that a blocked account can neither send nor receive assets: [3](#0-2) 
This is confirmed by the existing pallet-assets test showing a deposit attempt into a blocked account fails with `TokenError::Blocked`: [4](#0-3) 

Because `harvest_rewards` uses `?` on the transfer, if the transfer fails (e.g., `TokenError::Blocked`), the function returns the error before it reaches the code that would reset `staker_info.rewards = 0` and update `PoolStakers`: [5](#0-4) 
So the reward entitlement (`staker_info.rewards`) is preserved in storage, but there is no protocol-level mechanism in `pallet-asset-rewards` to redirect the payout to a different, unblocked account — unlike `pallet-bridge-relayers`, which explicitly supports paying rewards "to the alternative beneficiary" via `claim_rewards_to`: [6](#0-5) 

This is the direct structural analog of the reported Solidity bug: `MainVault.withdrawRewards()` sends collateral only to `msg.sender` with no `recipient` argument, so a `vaultCurrency` blacklist permanently freezes the reward. In `pallet-asset-rewards`, the equivalent is `harvest_rewards` sending the reward asset only to `staker` with no beneficiary argument, so a `pallet-assets` `block()` on that account (a legitimate action of the reward-asset's own freezer role, outside the staking-rewards pallet's control, just like an ERC-20 issuer's blacklist) permanently locks that staker's already-accrued rewards.

### Impact Explanation
Once a staker is blocked by the freezer of the configured `reward_asset_id`, their entire accumulated, already-earned reward balance for that pool becomes permanently unclaimable through any pallet-provided extrinsic — there is no `harvest_rewards_to`/beneficiary override, and no other pallet call transfers `PoolStakers` rewards anywhere else. The funds remain locked in the pool's reward account indefinitely (from the pallet's perspective), degrading to the pool operator having to manually intervene outside of the protocol (e.g. asking the freezer to `thaw()`) — which may not be possible if the asset admin is unresponsive or malicious. This matches a Medium-severity "frozen funds for a legitimately blacklisted user" class of finding, same as the original report.

### Likelihood Explanation
Likelihood depends on the runtime wiring: `T::Assets` must be backed by an asset type that supports blocking (e.g. `pallet-assets`), and the reward asset's freezer must actually block the account. This requires no privileged action or compromise by the staker/attacker — it is triggered purely by the asset issuer/freezer exercising an ordinary, intended `pallet-assets` capability (`block`), which is a realistic, foreseeable operational event for any asset that models real-world compliance/blacklist requirements (similar to how stablecoin issuers commonly blacklist addresses). Any production configuration using `pallet-assets` as the reward asset for `pallet-asset-rewards` is exposed.

### Recommendation
Add a `beneficiary`/`recipient` parameter to `harvest_rewards` (mirroring `pallet-bridge-relayers::claim_rewards_to`) so a staker (or someone acting on their claim permission) can redirect the reward payout to an account that is not blocked by the underlying asset, while still requiring signer authorization for the `staker`'s claim. Alternatively, on transfer failure due to `Blocked`, allow accrual to persist and expose an explicit "reroute" call so accrued-but-unclaimable rewards are not effectively permanently orphaned from the staker.

### Proof of Concept
This finding is derived from static code analysis and existing test evidence rather than a newly executed local reproduction:
- The blocked-account transfer failure mode is proven by the existing pallet-assets unit test `transferring_to_blocked_account_should_not_work`, which asserts `Assets::transfer(..., blocked_account, ...)` returns `TokenError::Blocked`: [4](#0-3) .
- The absence of any recipient/beneficiary parameter and the direct `?`-propagation before state reset in `harvest_rewards` is shown at [7](#0-6) .
- A full integration reproduction (constructing a `pallet-asset-rewards` mock runtime with `pallet-assets` as `T::Assets`, staking, accruing rewards, calling `Assets::block` on the staker, then asserting `harvest_rewards` fails with `TokenError::Blocked` while `PoolStakers` reward balance is unchanged) was not executed in this session due to lack of code-execution tooling; this should be run in a Devin session with `cargo test -p pallet-asset-rewards` using a custom mock wiring `T::Assets` to `pallet-assets` before treating this as a fully confirmed, executable PoC.

		/// Harvest unclaimed pool rewards.
		///
		/// Parameters:
		/// - origin: must be the `staker` if the pool is still active. Otherwise, any account.
		/// - pool_id: the pool to harvest from.
		/// - staker: the account for which to harvest rewards. If `None`, the caller is used.
		#[pallet::call_index(3)]
		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())

		/// Emits `Blocked`.
		///
		/// Weight: `O(1)`
		#[pallet::call_index(31)]
		pub fn block(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Blocked;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Blocked { asset_id: id, who });
			Ok(())
		}

/// The status of an asset account.
#[derive(Clone, Encode, Decode, Eq, PartialEq, Debug, MaxEncodedLen, TypeInfo)]
pub enum AccountStatus {
	/// Asset account can receive and transfer the assets.
	Liquid,
	/// Asset account cannot transfer the assets.
	Frozen,
	/// Asset account cannot receive and transfer the assets.
	Blocked,
}
impl AccountStatus {
	/// Returns `true` if frozen or blocked.
	pub fn is_frozen(&self) -> bool {
		matches!(self, AccountStatus::Frozen | AccountStatus::Blocked)
	}
	/// Returns `true` if blocked.
	pub fn is_blocked(&self) -> bool {
		matches!(self, AccountStatus::Blocked)
	}
}
