### Title
Missing `return` after error path in `handleSavedPrivatePayments()` causes the `async.each` callback to fire twice on a malformed private-payment chain, corrupting the parallel-handling loop over private payment chains - (File: network.js)

### Summary
In `network.js`, `handleSavedPrivatePayments()` processes private-payment chains received from a paired device or hub with `async.each`, where each chain's completion is signalled by invoking a per-row callback `cb`. In the inner `validateAndSave` function, a `try/catch` around `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` inside the `catch` block, but does not `return` afterwards. Execution therefore falls through to `privatePayment.validateAndSavePrivatePaymentChain(...)`, whose `ifOk`/`ifError`/`ifWaitingForChain` callbacks each also call `cb()` (via `deleteHandledPrivateChain(...,cb)` or directly). This results in the same `cb` for the same row being invoked twice for a single crafted payload.

### Finding Description [1](#0-0) 

The relevant code:
```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb); ... },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
``` [2](#0-1) 

`arrPrivateElements` is JSON parsed from `row.json`, which was originally stored from a private-payment message sent by a paired device / hub relay (`unhandled_private_payments`). If the head element's `payload` is structured such that `objectHash.getBase64Hash()` throws (e.g. it contains a value type that the hashing/serialization routine cannot canonicalize — such as a non-plain object, `undefined`, or a structure that fails `getSourceString`/`getJsonSourceString`), the `catch` block runs `deleteHandledPrivateChain(..., cb)` (which itself will eventually invoke `cb` again after its own async work) and then, without returning, the same closure continues to call `privatePayment.validateAndSavePrivatePaymentChain(...)`, which independently reaches one of `ifOk`/`ifError`/`ifWaitingForChain` and calls `cb` (or `deleteHandledPrivateChain(...,cb)`, itself invoking `cb`) a second time.

Calling the per-item `async.each` callback twice for a single item is the Node.js/async-library analogue of the GIMP `read_layer_block()` double-free: a resource-completion handle ("this item is done") is released/finalized twice. In `async.each`, invoking the iteratee callback more than once causes the internal completion counter to be decremented twice and the final callback (`function(){ unlock(); ... eventBus.emit("new_my_transactions", ...); }`) to be triggered prematurely/twice, releasing the `["saved_private"]` mutex lock while other rows in the same batch are still being processed, and/or firing `new_my_transactions` more than once for the same unit. It can also cause double execution of `deleteHandledPrivateChain`, which itself performs a DB delete/callback sequence not designed to be invoked twice for the same row concurrently.

### Impact Explanation
The double-callback releases the `saved_private` mutex prematurely (or emits completion events prematurely) while other private-payment rows are still mid-processing under the same lock, breaking the intended serialization guarantee for handling saved private payments. This can lead to concurrent double-processing of another private-payment chain that's still in flight under the same "lock", allowing a race where a private-payment chain and its concomitant local caching state (`assocNewUnits`, `new_my_transactions`, `private_payment_validated-*` event) can be observed/emitted inconsistently, and `deleteHandledPrivateChain` (a DB delete operation with its own callback) being kicked off twice concurrently for the same row, which risks corrupting the `unhandled_private_payments` bookkeeping and the wallet's understanding of which private chains have been finalized. In the worst case this undermines the integrity of private-payment chain finalization tracked per-address, affecting a private-payment counterparty's local ledger state for hidden-value outputs.

### Likelihood Explanation
This is triggered purely by a private-payment counterparty (or a peer relaying via the hub) sending a private-payment chain whose head element's `payload` cannot be canonically hashed by `objectHash.getBase64Hash`. Since `arrPrivateElements` originates from attacker-controlled JSON stored in `unhandled_private_payments` (received directly from a device or via the hub), an attacker who can pair with or send a private payment to a victim wallet can attempt to craft such a payload. Exploitability depends on finding an input for which `getBase64Hash`/`getSourceString` throws (this needs confirmation against `object_hash.js`/`string_utils.js`, which I was not able to fully verify with certainty before running out of tool calls) — I have not confirmed a concrete throwing payload with 100% certainty, so likelihood should be treated as plausible but requiring further validation of the exact hashing throw condition.

### Recommendation
Add a `return` statement immediately after the `catch` block's `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);` call in `network.js`'s `handleSavedPrivatePayments()` `validateAndSave` function, so that on a hashing failure the function does not fall through into calling `privatePayment.validateAndSavePrivatePaymentChain(...)` a second time for the same row/callback. Additionally, audit `deleteHandledPrivateChain` to ensure it is idempotent/guarded against being invoked twice concurrently for the same `(unit, message_index, output_index)` key.

### Proof of Concept
1. As a paired device or via the hub, send (or arrange for) a private-payment chain whose head element (`arrPrivateElements[0]`) has a `payload` object that causes `objectHash.getBase64Hash(payload, true)` to throw (exact malformed-payload shape needs confirmation against `object_hash.js`'s canonicalization logic).
2. This message gets stored to `unhandled_private_payments` and later processed by `handleSavedPrivatePayments()`.
3. In `validateAndSave()`, the `try` block throws; the `catch` block sends an error result and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — scheduling one invocation of `cb`.
4. Execution falls through (no `return`) to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which — operating on the same malformed/incomplete data — will reach `ifError`/`ifOk`/`ifWaitingForChain` and invoke `cb` again (directly, or via a second `deleteHandledPrivateChain` call).
5. `cb` for the same `async.each` item fires twice, prematurely completing/duplicating the `async.each` bookkeeping for the `["saved_private"]`-locked batch, releasing the mutex early and/or double-triggering `deleteHandledPrivateChain`'s side effects while sibling rows in the batch may still be in-flight.
