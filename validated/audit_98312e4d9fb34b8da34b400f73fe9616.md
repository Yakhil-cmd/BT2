### Title
Cross-organization webhook forgery via `repository_owner`/`repository.full_name` decoupling lets an unsigned org overwrite a victim's `PullRequest` record - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which HMAC secret to check against using `params.dig('repository','owner','login')`, while `AssignedHandler#repository` (and the sibling PR handlers) resolves the target `Shipit::Repository` from the independent `params.repository.full_name` field of the same raw JSON body. An attacker who controls the entire raw POST body can set these two fields inconsistently, so a request "verified" under their own, secret-less organization is processed as if it came from a victim organization, allowing them to overwrite the victim's `PullRequest#github_pull_request` (including assignees) with attacker-chosen data.

### Finding Description
The broken binding: `organization used to verify signature (params.dig('repository','owner','login'))` MUST equal `organization owning the repository mutated (owner segment of params.repository.full_name)`. Nothing in the code enforces this equality.

- `WebhooksController#verify_signature` derives the signing org solely from `repository_owner`, then calls `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature(signature, raw_post)`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 
- `AssignedHandler#process` then resolves the target repository from a *different* JSON path, `params.repository.full_name`, and mutates the matching `PullRequest` with attacker-supplied assignee data: [4](#0-3) 

Because the raw JSON body is entirely attacker-controlled (this is a direct `POST /webhooks` to the Shipit host, not a relayed authentic GitHub delivery), the attacker can set `repository.owner.login` to their own (registered-but-secret-less) organization login while setting `repository.full_name` to the victim's `"victim_org/victim_repo"`. `verify_signature` looks up the attacker's own org config (which the attacker legitimately owns/onboarded, e.g., a "public" org added to a multi-tenant Shipit instance without a `webhook_secret`), finds no secret, and short-circuits to `true` — no HMAC signature is checked at all. The handler then finds the real victim `PullRequest` via `full_name` and calls `pull_request.update(github_pull_request: params.pull_request)`, writing the attacker's own login into `assignees` on the victim's PR record.

None of the existing guards catch this: `drop_unhandled_event` only checks the event type exists; `ExplicitParameters` only validates JSON shape, not cross-field consistency between `repository.owner.login` and `repository.full_name`; `verify_signature` never compares the two; and `Repository.from_github_repo_name` performs no ownership check against the org that was verified.

### Impact Explanation
This is a cross-tenant write: a payload verified under organization A (attacker's own, secret-less org) mutates a `PullRequest` record belonging to organization B's (victim's) stack — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." At minimum, attacker-controlled data (assignee logins, labels, PR title/state, head SHA/ref echoed from the forged payload) is written into the victim's `PullRequest#github_pull_request`. If any downstream logic (e.g., review-stack gating or `deployable?`-style checks) consults PR assignees/labels sourced from this field, this becomes a path to unauthorized deploy state manipulation on the victim's stack; independent of that, it is at minimum unauthorized write access into another tenant's PR metadata. It is repeatable against any victim repository whose `full_name` the attacker knows, for every event handled by handlers that resolve their target `Repository` via `full_name` (e.g., `ClosedHandler`, `LabeledHandler`, `OpenedHandler`, `ReopenedHandler`, `UnlabeledHandler`, `EditedHandler` share the same pattern per the earlier grep), so the blast radius extends across all PR-related webhook handlers, not just `AssignedHandler`.

### Likelihood Explanation
The precondition is that Shipit is configured for multiple organizations and at least one organization the attacker controls (or can get onboarded, e.g. their own public/personal org) has no `webhook_secret` configured — this is a plausible and not unusual operator configuration for a multi-tenant Shipit deployment, and it requires no secret, session, token, or privileged role from the attacker. The attacker's cost is a single crafted HTTP POST to `/webhooks` with correct headers (`X-Github-Event: pull_request`) and a JSON body they fully author; the request is fully repeatable against arbitrary victim repositories known to the attacker by name.

### Recommendation
Do not let `repository.owner.login` diverge from the organization implied by `repository.full_name`. Either (a) derive `repository_owner` for signature verification from the same `full_name` field the handlers use to resolve the `Repository`, and reject if they disagree, or (b) after successfully resolving the target `Shipit::Repository`/`Stack` in each handler, assert that the verified signing organization equals `repository.github_repo_name`'s owner segment before performing any mutation. Additionally, treat organizations without a configured `webhook_secret` as unverifiable (reject webhooks) rather than auto-passing signature verification.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in `Shipit.github_apps` test fixtures: `"victim_org"` with a `webhook_secret`, and `"attacker_org"` with no `webhook_secret`.
2. Create a victim `Stack`/`Repository` with `full_name = "victim_org/victim_repo"` and an existing `Shipit::PullRequest` (e.g. `shipit_pull_requests(:review_stack_review)`) with `number: 42` and empty `assignees`.
3. POST to `/webhooks` with header `X-Github-Event: pull_request` and no valid `X-Hub-Signature` for `victim_org`'s secret, and a JSON body:
   ```json
   {
     "action": "assigned",
     "number": 42,
     "pull_request": { ..., "assignees": [{"login": "attacker"}], ... },
     "repository": { "owner": {"login": "attacker_org"}, "full_name": "victim_org/victim_repo" },
     "sender": {"login": "attacker"}
   }
   ```
4. Assert both sides of the binding: `repository_owner` resolved by the controller equals `"attacker_org"` (verified, secret-less), while the record mutated belongs to `"victim_org/victim_repo"` — i.e. `response.status == 200` (not `422`) AND `pull_request.reload.github_pull_request["assignees"]` now contains `"attacker"`, proving the write succeeded despite no valid signature for the victim's organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
