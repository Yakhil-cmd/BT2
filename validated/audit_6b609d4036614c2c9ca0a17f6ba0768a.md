### Title
Stack-scoped API token can read build status of any stack via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Api::CCMenuController#stack` bypasses the stack-scoping enforced by `Api::BaseController#stacks`, allowing an `ApiClient` token that was issued with `stack_id` restricted to a single stack to read the CCMenu build status of *any* stack in the installation, not just the one it was authorized for.

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column [1](#0-0) . `Api::BaseController` is supposed to enforce this scope for every API resource by restricting the queryable set of stacks to the client's assigned `stack_id`: [2](#0-1) 

Every other controller that needs a `stack` (e.g. `Api::TasksController`, `Api::StacksController`) relies on this scoped `stacks`/`stack` helper, so a token bound to stack A can never resolve a `Stack.from_param!` lookup for stack B.

`Api::CCMenuController`, however, overrides `stack` and resolves it directly against the full `Stack` table, ignoring the client's `stack_id` scope entirely: [3](#0-2) 

The only authorization check performed is `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [4](#0-3) 

This method only checks that the string `"read:stack"` is present in the token's `permissions` array — it never compares `current_api_client.stack_id` to the requested `stack_id`. Because `CCMenuController#stack` does not go through the scoped `stacks` helper, the `stack_id` restriction that is supposed to bind "the stack a token authorizes" to "the stack it touches" is never evaluated for this endpoint.

### Impact Explanation
Any holder of a valid `ApiClient` authentication token that was deliberately scoped to a single stack (e.g. distributed as a CCMenu URL for a specific, possibly less-sensitive stack) can use that same token to query `GET /api/stacks/*stack_id/ccmenu` for a *different, arbitrary* stack and obtain its build/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) — including for stacks the token was never meant to access. This is an authorization-scope escalation: an unprivileged, narrowly-scoped credential gains read access to stack state outside its authorized boundary, matching the "stack a token authorises versus a stack it touches" binding break called out in scope.

### Likelihood Explanation
Exploitation only requires possession of any valid `ApiClient` token with `read:stack` permission (regardless of its intended `stack_id` scope) and the target stack's identifier (`owner/repo/environment`), which is often predictable/enumerable from repository names. No additional secrets, GitHub credentials, or elevated privileges are needed beyond the token itself, and the request is a single unauthenticated-relative-to-scope `GET`.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` helper from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so that a token restricted via `ApiClient#stack_id` cannot resolve stacks outside its assigned scope. Additionally, consider having `check_permissions!`/`require_permission` explicitly assert `current_api_client.stack_id.nil? || current_api_client.stack_id == stack.id` for defense in depth.

### Proof of Concept
1. As an admin, create two stacks, `org/repo-a/production` and `org/repo-b/production`.
2. Create an `ApiClient` scoped to `repo-a` only: `ApiClient.create!(name: 'scoped', creator: user, permissions: ['read:stack'], stack_id: repo_a_stack.id)`, and obtain its `authentication_token`.
3. Send `GET /api/stacks/org/repo-b/production/ccmenu?token=<repo-a-scoped-token>`.
4. Observe a `200 OK` response containing `repo-b`'s build status XML, even though the token's `stack_id` only authorizes `repo-a` — confirmed by the fact that `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) calls `Stack.from_param!` unscoped, unlike every other API controller which uses the `stack_id`-filtered `stacks` helper in `app/controllers/shipit/api/base_controller.rb:74-80`.
