### Title
Webhook signature verification is scoped to the claimed `repository.owner.login`, but handlers act on data scoped by a different (or no) field, letting a low-trust GitHub organization forge webhooks that write into a higher-trust organization's stacks - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate a webhook against based on `params.dig('repository','owner','login')` (or `organization.login`) taken straight from the untrusted request body [1](#0-0) [2](#0-1) . Shipit explicitly supports hosting multiple, independently-trusted GitHub organizations, each with its own `app_id`/`installation_id`/`webhook_secret`, resolved through `Shipit.github(organization:)` [3](#0-2)  and documented in `docs/setup.md`'s "Using Multiple Github Applications" section. Nothing after signature verification re-checks that the *actual* target of the webhook (the commit/repository being mutated) belongs to the same organization whose secret was used to authenticate the request.

### Finding Description
The equality the system implicitly relies on is:

`organization used to select/verify webhook_secret == organization owning the resource the handler mutates`

but this is never enforced.

- The controller computes `repository_owner` purely from the JSON body and uses it only to pick which app's secret to HMAC-verify against [1](#0-0) .
- Most handlers scope their target by `payload.dig('repository', 'full_name')` via `Handler#repository_name`/`#stacks` [4](#0-3) . Since `full_name` and `owner.login` are independent JSON fields in the same unstructured hash, an attacker who legitimately controls their own low-trust org's GitHub App (and therefore knows/controls that org's `webhook_secret`) can produce a validly-signed request where `repository.owner.login` = their own org (so the signature check passes) while `repository.full_name` = `"other-org/private-repo"` belonging to a different, more trusted org also hosted on the same Shipit instance.
- `StatusHandler`, used for the `status` GitHub event, is worse: it doesn't even scope by repository at all. It looks up target commits with a global, unscoped query: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! }` [5](#0-4) . As long as a signature validates for *some* configured organization, an attacker can inject a forged "success"/"failure" commit status for any commit `sha` in the entire Shipit database, including commits belonging to other organizations' stacks, since `sha` alone (not repository) determines the write target.

This is the direct structural analog of the reported bug class: the field trusted for one purpose (selecting/validating against the organization's secret) is decoupled from the field that actually drives what gets written/mutated downstream, letting an attacker "shift" control from the verified field to an unverified one that is processed afterward.

### Impact Explanation
Commit statuses gate `ci.require`/`deployable_status` checks that determine whether continuous delivery treats a commit as deployable (`Shipit::Commit`/`Stack` continuous-delivery logic reads `Status` records created here). By forging a `status` webhook using credentials from any onboarded low-trust organization, an attacker can mark a real, existing commit sha belonging to a different, higher-trust organization's repository as CI-green, potentially unblocking an automatic/continuous deploy for that stack, an unauthorized deploy triggered without ever having credentials or write access to the victim organization or repository. This satisfies the Critical impact bar ("an unauthorized deploy... "). Because Shipit is explicitly designed to multi-tenant several GitHub orgs off one instance with independent per-org secrets, this crosses a real trust boundary the application itself defines.

### Likelihood Explanation
Exploitation requires the attacker to control (or have been issued) the `webhook_secret`/App credentials for at least one org configured in the same Shipit instance — a realistic scenario for any shared/multi-tenant Shipit deployment onboarding multiple orgs with differing trust levels (e.g., a vendor org and an internal org). No compromise of the victim org, no `ApiClient` token, and no privileged Shipit account are required, matching the rules' "unprivileged attacker" bar. The forgery itself is a simple crafted JSON POST with a correctly computed HMAC using the attacker's own known secret.

### Recommendation
- In `WebhooksController`, after determining `repository_owner` and verifying the signature, also verify that every repository/organization field referenced deeper in the payload (`repository.full_name`, `organization.login` used by handlers) is consistent with the authenticated `repository_owner`/organization, rejecting mismatches.
- In `Shipit::Webhooks::Handlers::StatusHandler` (and any other handler not scoping by repository), restrict the `Commit` lookup to commits belonging to stacks/repositories owned by the authenticated organization, e.g. join through `Stack -> Repository` and filter by the verified organization instead of a global `Commit.where(sha:)`.
- Generally, ensure every handler's "what gets mutated" query is scoped by the same organization identity that was used to select/verify the webhook secret.

### Proof of Concept
1. Shipit is configured with two orgs, e.g. `OrgLow` (attacker-controlled GitHub App/secret) and `OrgHigh` (victim), per the multi-org config format in `docs/setup.md`.
2. Attacker learns the sha of a real, existing commit in an `OrgHigh` stack (public info via GitHub UI/API).
3. Attacker POSTs to `/github/webhooks` with header `X-Github-Event: status`, body:
   ```json
   { "sha": "<OrgHigh commit sha>", "state": "success", "repository": {"owner": {"login": "OrgLow"}}, "organization": {"login": "OrgLow"}}
   ```
   signed with `X-Hub-Signature: sha1=<HMAC using OrgLow's webhook_secret>`.
4. `verify_signature` resolves `repository_owner` = `"OrgLow"`, fetches `Shipit.github(organization: "OrgLow")`, and the signature validates successfully [1](#0-0) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a `Status` on the `OrgHigh` commit regardless of the authenticated organization [5](#0-4) , potentially unblocking continuous delivery on `OrgHigh`'s stack.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
