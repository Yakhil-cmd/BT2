### Title
Webhook signature is verified against the wrong organization's secret because the org used for key-selection is read from the same untrusted, not-yet-verified payload as the repository that gets acted upon - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* organization's HMAC secret to check the signature against by reading `repository.owner.login` (or `organization.login`) straight out of the unauthenticated JSON body, before the signature has been validated. The event handlers, however, resolve *which repository/stack to act on* from a different field of that same unauthenticated body: `repository.full_name` [1](#0-0) . Nothing ties the two together, so the "authenticated organization" and the "repository actually written to" are two independent, attacker-controlled values extracted from the one unverified request.

### Finding Description
`verify_signature` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) from `secrets.github`, keyed by the org name supplied — again taken from the unauthenticated body [3](#0-2) . `GitHubApp#verify_webhook_signature` additionally returns `true` unconditionally when that organization's `webhook_secret` is blank/not configured [4](#0-3) .

Once the `422`/pass decision is made, `Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to handlers that resolve the target repository independently, via `payload.dig('repository', 'full_name')` and `Repository.from_github_repo_name` [1](#0-0)  and [5](#0-4) .

Because `repository.owner.login` (used to select the verification secret) and `repository.full_name` (used to select the acted-upon repository/stack) are two separate keys in the same forged JSON body, an attacker can:
1. Set `repository.owner.login` (or `organization.login`) to an organization configured in Shipit's `secrets.github` that has **no `webhook_secret` set**, or whose secret the attacker already knows (e.g. an org the attacker administers and had onboarded into the same multi-tenant Shipit instance). This makes `verify_webhook_signature` return `true` (blank-secret bypass) or pass with a secret the attacker controls.
2. Set `repository.full_name` to `victim-org/victim-repo` — any *other* repository actually tracked by Shipit, unrelated to the organization used in step 1.

The signature check never re-validates that the org used for key selection actually matches the repository the handler will operate on, so the handler processes an event as if it legitimately originated from `victim-org/victim-repo`'s GitHub App, while it was never signed by that organization's secret at all.

This breaks the trust equality: **organization whose secret authenticated the request == organization that owns the repository being written to**.

### Impact Explanation
Handlers act on the spoofed `repository.full_name` with full trust, e.g.:
- `PushHandler` triggers `stack.sync_github(expected_head_sha:)` for every non-archived stack of the victim repository matching the pushed branch [6](#0-5) , letting an attacker force a sync of arbitrary victim stacks to an attacker-chosen SHA/ref without ever having write access or a valid signature for that repository/org.
- Other registered handlers (status, check_suite, membership, pull_request, merge) similarly key off attacker-controlled payload fields and can be aimed at any repository tracked in the same Shipit instance, independent of which organization's secret actually signed the request.

This is a cross-tenant / cross-repository write achieved purely by forging an HTTP POST to the public `WebhooksController#create` endpoint — no GitHub credentials, API token, or session are required — satisfying the "unauthorized deploy/cross-repository writes via authentication bypass" bar.

### Likelihood Explanation
Requires a Shipit deployment configured for multiple GitHub organizations/installations (the multi-org `secrets.github` schema that `github_app_config`/`github_default_organization` supports [7](#0-6) ), and at least one organization entry with a missing/blank `webhook_secret`, or an organization the attacker controls (installed the Shipit GitHub App there themselves) whose secret they legitimately know. Both configurations are realistic in shared/multi-tenant Shipit deployments and are not flagged as invalid by the engine.

### Recommendation
- After verifying the signature, cross-check that the organization/owner used to select the verifying secret matches the `repository.owner.login` / `organization.login` actually referenced by the handler's `repository.full_name`, rejecting mismatches.
- Do not treat a blank `webhook_secret` as an automatic pass in `GitHubApp#verify_webhook_signature`; require an explicit "no verification" flag instead of defaulting to `true`.
- Bind the resolved `Repository`/`Stack` lookup to the same organization whose secret validated the request, not to an independently-parsed field of the same untrusted payload.

### Proof of Concept
1. Configure Shipit (per `secrets.github`) with two organizations: `attacker-org` (no `webhook_secret`, or a secret known to the attacker because they administer that org/app installation) and `victim-org` (has `victim-org/victim-repo` tracked as a Shipit stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and a body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")`; since that org's `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (even absent) `X-Hub-Signature` header [4](#0-3) .
4. The request proceeds to `PushHandler`, which resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers `sync_github(expected_head_sha: "<attacker-chosen sha>")` on all matching victim stacks [6](#0-5)  — an unauthenticated write against a repository the attacker never proved control of.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
