### Title
Permissionless `DepositDelegatorRewards` lets any user force zero-value block-reward entries onto every delegator of an arbitrary vote account, inflating epoch-reward distribution cost - ([File: programs/vote/src/vote_state/mod.rs])

### Summary
`VoteInstruction::DepositDelegatorRewards` (SIMD-0123) allows *any* unprivileged signer to top up `pending_delegator_rewards` on an arbitrary V4 vote account with no minimum amount check. [1](#0-0)  This mirrors the reported "claimer fee exploitation" pattern: an attacker makes a trivial, low-cost "deposit" against a third party's account, forcing that party's (and its delegators') reward-processing path to treat every associated entry as non-trivial, even though the added value is economically negligible.

### Finding Description
`deposit_delegator_rewards` only requires the source account to sign and to have enough lamports for the transfer; there is no minimum-deposit enforcement, and the deposit is added unconditionally via `add_pending_delegator_rewards`. [2](#0-1) 

During epoch-reward calculation, `calculate_block_reward` derives a per-stake-delegation block reward proportional to `pending_delegator_rewards * stake / total_active_stake` for every stake account delegated to that vote account. [3](#0-2)  In `calculate_stake_rewards_and_commissions`, if `block_reward` is nonzero but the stake's inflation reward is `None` (e.g., the stake earned no inflation credits), the code still fabricates a `PartitionedStakeReward` "zero entry" for that delegation, purely to carry the block reward through partitioning/distribution. [4](#0-3)  Without an attacker-supplied deposit, such stakes would instead be skipped entirely via the `(0, None) => (None, None)` branch, adding zero cost to distribution. [5](#0-4) 

The number of partitioned-reward blocks required to fully distribute rewards is directly proportional to the total count of these entries: `get_reward_distribution_num_blocks` computes `num_chunks = total_stake_accounts.div_ceil(stake_account_stores_per_block)`, capped at 10% of the epoch's slots. [6](#0-5)  By depositing a minimal amount (even 1 lamport, since there is no floor) into a vote account with many delegators, an attacker forces the creation of extra reward/storage entries for every one of that validator's stake accounts that would otherwise have been skipped, at the cost of only a single small, permanently-locked deposit. `store_stake_accounts_in_partition` then must load, mutate, and re-store each of these stake accounts even though credits/inflation reward is zero, explicitly documented as intentional ("even if staker's reward is 0, the stake account still needs to be stored"). [7](#0-6) 

Additionally, the deposited amount becomes locked: `withdraw` will not permit a vote account to be fully closed while `pending_delegator_rewards > 0`, and partial withdrawals must always leave at least `min_rent_exempt_balance + pending_delegator_rewards` behind. [8](#0-7)  Since there is no bound on how many times `DepositDelegatorRewards` can be called or by whom, an attacker can repeatedly deposit dust into any number of validators' vote accounts to broadly force extra reward-distribution entries and processing across the network at each epoch boundary, at a cost proportional only to the (unbounded-low) minimum deposit and transaction fees.

### Impact Explanation
This does not cause direct lamport theft or misattribution — the block reward computed and paid is arithmetically correct and proportional. The practical effect is increased per-epoch reward-calculation/distribution work (extra `PartitionedStakeReward` entries, extra account stores, and potentially more distribution blocks) imposed on the network and on the targeted validator's delegators, at negligible cost to the attacker, repeatable against arbitrary vote accounts with no minimum-deposit guard. This is a resource-amplification/griefing vector analogous to the reported bug class (forcing processing of otherwise-skippable zero-value entries), but it manifests as increased computation/storage cost rather than a bounded, capped resource (partition count is capped at 10% of epoch slots) rather than an unconditional halt.

### Likelihood Explanation
Low barrier to trigger: `DepositDelegatorRewards` requires only a signer and a system-program CPI transfer, no special permissions, and no minimum-deposit validation, so it can be invoked cheaply and repeatedly against any V4 vote account with `block_revenue_sharing`, `commission_rate_in_basis_points`, and `custom_commission_collector` features active. [1](#0-0) 

### Recommendation
Enforce a sensible minimum for `DepositDelegatorRewards` deposits (or a minimum non-zero `pending_delegator_rewards` threshold before it contributes to `calculate_block_reward`) so that dust deposits cannot force generation of "zero-value" partitioned stake-reward entries for delegations that would otherwise be skipped, mirroring the recommended fix in the referenced report (minimum purchase amount to ensure entries are substantial enough to warrant processing).

### Proof of Concept
Not independently reproducible via harness in this ask-only investigation; the mechanism is demonstrated by the existing unit tests exercising `DepositDelegatorRewards` with a "zero-lamport deposit" success case (showing no floor is enforced) and `calculate_block_reward`'s proportional payout logic. [9](#0-8) [10](#0-9)  A concrete PoC would require constructing a validator vote account with many delegated stake accounts (some with stale/zero inflation credits), invoking `DepositDelegatorRewards` with a minimal deposit, and measuring the resulting increase in `PartitionedStakeReward` entry count and `get_reward_distribution_num_blocks` versus the baseline without the deposit — this was not run in this investigation and should be validated in a live/test-validator environment.

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
