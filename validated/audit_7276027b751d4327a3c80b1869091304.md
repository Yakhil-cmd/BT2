### Title
Missing `return` after exception handling causes double-invocation of the private-payment completion callback and a fatal double-unlock crash - ([File: network.js])

### Finding Description
`handleSavedPrivatePayments()` processes private payment chains that were previously queued by an unprivileged private-payment counterparty via `handleOnlinePrivatePayment()` / `unhandled_private_payments`. Inside the `validateAndSave` closure: [1](#0-0) 

```
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, { ... cb ... });
```

The `catch` block already resolves the per-item `async.each` iteratee callback `cb` via `deleteHandledPrivateChain(..., cb)`, but there is no `return` statement after the `catch`. Execution falls through and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, whose `ifOk`/`ifError`/`ifWaitingForChain` handlers each also invoke `cb` a second time [2](#0-1) .

This is the same root-cause class as CVE-2022-36879: an error path fails to short-circuit, so a resource-completion/reference-release primitive (`cb`, tracked by `async.each`, ultimately gating `unlock()` for the `["saved_private"]` mutex) is released/consumed twice for the same logical unit of work.

`mutex.js`'s `exec()` explicitly guards against double release and throws when it happens: [3](#0-2) 

```
proc(function unlock(unlock_msg) {
    if (!bLocked)
        throw Error("double unlock?");
    ...
```

`async.each`'s completion callback runs once per completed item and fires the final callback (`unlock()` at network.js:2513) when the completion count reaches the total; an extra `cb()` invocation for the same item causes the final callback to be invoked again once the (already exhausted) counter is met, calling `unlock()` a second time and throwing `"double unlock?"`.

This uncaught exception propagates to the global handler, which deliberately crashes the process: [4](#0-3) 

### Impact Explanation
A private-payment counterparty (a normal, unprivileged actor that can send private payment chains to a wallet/hub, per `handleOnlinePrivatePayment`) can craft a private-payment payload whose head element cannot be canonically hashed by `objectHash.getBase64Hash` (e.g. a payload value unsupported by `getJsonSourceString`/`getSourceString`), forcing the `catch` branch to execute. The subsequent unconditional fall-through causes a second completion of the same `async.each` item, which manifests as a double `mutex.unlock()` call and an uncaught `"double unlock?"` exception. Because `process.on('uncaughtException')` intentionally re-throws to crash the process "to avoid ending up in an inconsistent state," the victim's node (wallet/hub) is forced to crash while handling an otherwise low-privilege message, denying it the ability to process or confirm any further units until manually restarted.

### Likelihood Explanation
High for any node/wallet that accepts private payments from outside contacts (textcoins, private asset transfers, hub-relayed private chains): the trigger only requires sending a private-payment chain whose head payload cannot be JSON-canonicalized/hashed, which is entirely attacker controlled and requires no special permission, key compromise, or timing race.

### Recommendation
Add a `return` immediately after the `deleteHandledPrivateChain(...)` call inside the `catch` block in `handleSavedPrivatePayments`'s `validateAndSave` function so `cb` is invoked exactly once and the subsequent `privatePayment.validateAndSavePrivatePaymentChain(...)` call is never reached when hashing fails. Additionally, consider validating the private-payment payload shape before hashing so malformed payloads are rejected earlier and deterministically.

### Proof of Concept
1. As a private-payment counterparty (or a peer relaying on their behalf), send a private payment chain via `handleOnlinePrivatePayment` whose head element's `payload` contains a value that `objectHash.getBase64Hash(payload, true)` cannot serialize (causing `getJsonSourceString`/`getSourceString` to throw), and let it be queued into `unhandled_private_payments`.
2. When `handleSavedPrivatePayments` later processes this row, `getBase64Hash` throws, entering the `catch` block, which calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` (consuming `cb` once).
3. Execution falls through (no `return`) to `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})`, which will call `cb` again through one of its `ifOk`/`ifError`/`ifWaitingForChain` handlers.
4. `async.each`'s internal completion tracking fires its final callback for the same task twice, invoking `unlock()` on the `["saved_private"]` mutex twice.
5. `mutex.js`'s `exec()` throws `Error("double unlock?")` on the second call, which is uncaught and crashes the process via the `uncaughtException` handler in `network.js`.
