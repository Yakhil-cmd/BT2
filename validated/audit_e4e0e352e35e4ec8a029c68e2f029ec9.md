### Title
Unbounded/uncharged loop over `attestors` array in address-definition validation enables cheap CPU-amplification DoS - (File: definition.js)

### Summary
`validateDefinition()`'s `evaluate()` function in `definition.js` enforces `MAX_COMPLEXITY`/`MAX_OPS` limits per recursive evaluation step, but the `attested` opcode's inner loop over the attacker-supplied `arrAttestors` array is never charged any complexity/op cost for its size, unlike the sibling `in data feed` and `in merkle` opcodes which at least add `complexity += arrAddresses.length-1` (after the fact). Any user who posts a unit that defines an address (or asset spending condition) using the `attested` operator can therefore embed an arbitrarily large `arrAttestors` array (bounded only by the overall unit/payload size limit, which still permits many thousands of 32-byte addresses) and force every validating node to run an unmetered `isValidAddress()` loop of that size, with zero contribution to the complexity/op budget that is supposed to bound validation cost.

### Finding Description
`evaluate()` increments `complexity`/`count_ops` once per recursive call and checks them against `constants.MAX_COMPLEXITY`/`constants.MAX_OPS` at the top of the function: [1](#0-0) 

For `in data feed` and `in merkle`, the loop over the oracle address array is followed by an explicit complexity charge proportional to its length: [2](#0-1) [3](#0-2) 

However, the `attested` case performs the equivalent loop over `arrAttestors` with **no size cap and no complexity/op charge at all** for the iteration: [4](#0-3) 

Since this single call to `evaluate()` still only costs `complexity++`/`count_ops++` (one unit total, from the top of the function) regardless of how many attestor addresses are inside, an attacker can nest many `attested` clauses (each incurring the normal 1-point cost against `MAX_COMPLEXITY`) while each one internally loops over a very large `arrAttestors` array, multiplying the real CPU cost far beyond what the complexity/op accounting is meant to bound. This directly matches the reported bug class (unbounded loop over an attacker-controlled array without an enforced maximum), but here it is worse than a typical "unbounded loop" because there is no accounting mechanism guarding it at all, whereas neighboring opcodes at least partially account for it.

### Impact Explanation
Address and asset-condition definitions are validated by every full node that processes the unit defining them, and (depending on how `attested` is re-checked when the address later signs/spends) potentially on every subsequent spend from that address. A crafted definition with a very large `attestors` set lets a single unposted unit disproportionately inflate the CPU work required by all validating nodes relative to the complexity budget the protocol assumes it is enforcing, degrading validation throughput for legitimately-sized units and increasing the risk of delayed confirmation/stability calculation network-wide when repeated or combined with other definitions. This is a Medium-severity resource-exhaustion vector reachable by any unprivileged unit poster defining an address, not a privileged/node-operator-only issue.

### Likelihood Explanation
Likelihood is Medium: constructing such a unit requires only knowledge of the `attested` definition operator and posting a definition with an oversized `attestors` array, something any wallet author could do without special privileges, and the resulting cost is triggered automatically for all validators of that unit (and potentially of dependent spends).

### Recommendation
Charge complexity/op cost proportional to `arrAttestors.length` (mirroring the `in data feed`/`in merkle` treatment) inside the `attested` case in `definition.js`, and additionally consider adding an explicit maximum bound on the `attestors` array length (and on `arrAddresses` in `in data feed`/`in merkle`) that is enforced before the loop executes, so that CPU cost for a single `evaluate()` call cannot exceed what `MAX_COMPLEXITY`/`MAX_OPS` are meant to guarantee.

### Proof of Concept
1. Craft an address definition unit of the form `['attested', ['this address', [addr1, addr2, ..., addrN]]]` (or as an asset `transfer_condition`/`issue_condition`) with `N` set to the maximum number of valid-looking base32 addresses that fit under the unit payload size limit (tens of thousands).
2. Post the unit defining this address (or an asset using this condition).
3. Every full node validating this unit executes the `for (var i=0; i<arrAttestors.length; i++) isValidAddress(arrAttestors[i])` loop in full, at a real CPU cost proportional to `N`, while `evaluate()`'s complexity/op accounting only registers this as a single-point operation.
4. Nesting several such `attested` clauses inside `and`/`or` combinators (each legitimately costing 1 complexity point) multiplies this effect while staying under `MAX_COMPLEXITY`/`MAX_OPS`, amplifying the validation cost imposed on the network relative to the intended per-unit complexity budget.
