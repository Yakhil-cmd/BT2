### Title
Prioritization fee always rounds up to a whole lamport, causing users to systematically overpay - (File: compute-budget/src/compute_budget_limits.rs)

### Summary
The BetaFinance report describes a rounding-direction bug: the protocol always rounds a fee/share calculation in the direction that favors the protocol/reserve, so lenders pay slightly more than the economically correct amount. The Agave analog is `get_prioritization_fee()` in `compute-budget/src/compute_budget_limits.rs`, which converts a transaction's micro-lamport priority fee (`compute_unit_price * compute_unit_limit`) into lamports using a ceiling-division instead of a floor/exact conversion, so a fee payer is charged up to one extra lamport whenever the product is not an exact multiple of `1_000_000` micro-lamports.

### Finding Description
`get_prioritization_fee` computes the fee to be deducted from the transaction's fee payer: [1](#0-0) 

It adds `MICRO_LAMPORTS_PER_LAMPORT - 1` before dividing — an explicit ceiling ("round up") operation — rather than truncating (floor) to the exact lamport value the user actually requested via `ComputeBudgetInstruction::set_compute_unit_price`. The accompanying unit tests explicitly confirm and expect this rounding-up behavior: [2](#0-1) 

This computed fee (`get_prioritization_fee`) flows directly into `FeeDetails` and is charged from the transaction's fee payer via `solana_fee::calculate_fee`/`calculate_fee_details`, both at fee-checking time and at actual execution/settlement time: [3](#0-2) [4](#0-3) 

Because this deduction is deterministic and applies to essentially every transaction that sets a `compute_unit_price` whose product with `compute_unit_limit` isn't an exact multiple of one million micro-lamports, every unprivileged user submitting a prioritized transaction is systematically charged up to 1 extra lamport more than the fee they mathematically specified. This is directly analogous to the reported bug class: the code always rounds in the direction that extracts more value from the ordinary user than intended, instead of computing the mathematically exact (or symmetric) amount.

Notably, the codebase itself acknowledges this is unwanted: the feature `remove_rounding_in_fee_calculation` is explicitly described as "Removing unwanted rounding in fee calculation": [5](#0-4) 

However, this feature is only present as an entry in the feature list; the actual fee-computation path (`compute_budget_limits.rs`, `fee/src/lib.rs`) does not consult this or any other feature flag to change behavior — `FeeFeatures` is an empty struct: [6](#0-5) 

So the rounding-up overcharge is currently unconditional in this codebase, i.e., the acknowledged fix has not (yet) been wired into the calculation, and the bug is live on every path that computes the prioritization fee for real deduction from the fee payer.

### Impact Explanation
Each affected transaction can only be overcharged up to 1 lamport (bounded by the ceiling operation), so the fund-loss magnitude per transaction is small and not directly comparable to fund-draining or consensus-halting vulnerabilities. However, it is a network-wide, transaction-sender-reachable, deterministic overcharge affecting essentially all prioritized transactions cluster-wide, and it constitutes unsigned/unintended movement of lamports beyond what the user authorized via their `ComputeBudgetInstruction` (the collector/validator receives value the fee payer never explicitly signed for beyond the rounding artifact). This matches the "users pay higher fee than intended" bug class from the report, scaled down to Solana's fee-accounting domain.

### Likelihood Explanation
This triggers automatically and deterministically for any transaction that includes a `set_compute_unit_price` instruction where `compute_unit_price * compute_unit_limit` is not a multiple of `1_000_000`, which is the overwhelming majority of real-world prioritized transactions (arbitrary micro-lamport prices are extremely common). No special conditions, ordering, or malicious leader/validator behavior are required — an ordinary unprivileged fee payer building any typical prioritized transaction hits this path every time.

### Recommendation
Compute the prioritization fee using exact/floor conversion (or otherwise ensure the fee charged never exceeds what the user's `compute_unit_price * compute_unit_limit` mathematically implies), consistent with the stated intent of `remove_rounding_in_fee_calculation`, and finish wiring that feature (or equivalent logic) into `get_prioritization_fee`/`calculate_fee_details` so the rounding-up behavior is actually eliminated in the live fee-deduction path rather than only tracked as an unused feature-set entry.

### Proof of Concept
Using the existing unit test as a demonstration of overcharge: [2](#0-1) 
For `compute_unit_price = MICRO_LAMPORTS_PER_LAMPORT - 1` and `compute_unit_limit = 1`, the user's requested spend is `(1_000_000 - 1)` micro-lamports = `0.999999` lamports, yet `get_prioritization_fee` returns `1` lamport — an exact 1-lamport overcharge relative to the mathematically implied fee, deducted from the fee payer at both fee-check and execution time via `calculate_fee_details`/`calculate_fee`.

```rust
fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}
```
