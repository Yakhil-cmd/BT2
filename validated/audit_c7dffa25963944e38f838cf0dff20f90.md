### Title
Windows reserved-device filename check can be bypassed with trailing whitespace, allowing release assets to be written to a Windows device (NUL/COM1/etc.) instead of a real file - (File: pkg/cmd/release/download/download.go)

### Summary
`isWindowsReservedFilename` normalizes an asset name only by upper-casing the substring before the *first* `.`, and matches it against an exact reserved-name list. It does not strip trailing whitespace, while Win32's `CreateFile` (used transitively by Go's `os.OpenFile`) strips trailing spaces/periods from a path component before resolving DOS device names. An attacker-controlled release asset named e.g. `"NUL "` (reserved word + trailing space, no extension) is *not* detected by the check but is still resolved by Windows to the `NUL`/`COM1`/etc. device file.

### Finding Description
The check lives in `pkg/cmd/release/download/download.go`: [1](#0-0) 

It is invoked in `downloadRun` for every asset name pulled straight from the GitHub API response (`release.Assets[].Name`), which is fully attacker-controlled by whoever publishes the release: [2](#0-1) 

Normalization is `strings.ToUpper(strings.Split(filename, ".")[0])`, then an exact `slices.Contains` match. This correctly catches variants like `NUL`, `NUL.tar.gz`, `NuL` (case folding) as covered by the existing unit tests, but it never trims trailing whitespace. Windows' `CreateFileW` (which Go's `os.OpenFile` calls under the hood on windows) strips trailing spaces and periods from the final path component before resolving reserved DOS device names, so a filename such as `"NUL "`, `"COM1 "`, or `"AUX  "` (reserved token + trailing space, no dot at all) is treated by Windows as the literal device, even though `strings.Split(filename, ".")[0]` returns `"NUL "` (with the space) which does not match `"NUL"` in the list and the function returns `false`.

Because the check passes, `downloadRun` adds the asset to `toDownload`, and `destinationWriter.Copy` proceeds to `os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)` on a path built from the untrusted name: [3](#0-2) 

On a real Windows machine, this will open the device instead of creating a normal file.

### Impact Explanation
Attacker-published release asset names bypass the intended Windows-reserved-device protection. Depending on the device targeted:
- `NUL` silently discards the downloaded bytes while `gh release download` reports success, defeating integrity expectations of the download and potentially masking tampering/verification workflows that rely on the file actually being written.
- `COM1`/`LPT1`/etc. can cause the process to block indefinitely or write bytes to a physical serial/parallel port if present, a denial-of-service against the CLI on the victim's machine.

This matches the "file write outside the intended path / unexpected behavior from attacker-controlled input" impact class the check itself was added to prevent (`isWindowsReservedFilename` was introduced specifically to stop this exploit vector, per its own comment).

### Likelihood Explanation
Preconditions: victim runs `gh release download` on Windows against a release published by the attacker (or a fork/PR whose release the victim is instructed to download) that contains an asset named with a reserved device token plus trailing whitespace and no extension. Asset display names are freely settable via the GitHub API/UI when uploading release assets, requiring no special privilege beyond being able to publish a release (an unprivileged repo owner/forker action). The bypass is deterministic and repeatable — no timing or race conditions involved.

### Recommendation
Harden `isWindowsReservedFilename` to mirror Windows' actual name-resolution rules:
1. Trim trailing spaces and periods from the filename before splitting off the extension (loop-trim, since multiple trailing dots/spaces are possible).
2. Split on the first `.` only after trimming, and also consider trimming trailing dots/spaces from that base segment.
3. Optionally, block outright any filename containing trailing dots/spaces, matching Windows' own restriction against such names, rather than only checking for device-name collision.

### Proof of Concept

```go
func TestIsWindowsReservedFilename_TrailingSpaceBypass(t *testing.T) {
	// Reserved device name with a trailing space and no extension.
	// Windows' CreateFile strips the trailing space and resolves this
	// to the NUL device, but the current check does not detect it.
	got := isWindowsReservedFilename("NUL ")
	assert.True(t, got, "expected \"NUL \" (trailing space) to be detected as a reserved Windows filename, but check returned false")
}
```
Expected today: `isWindowsReservedFilename("NUL ")` returns `false` (bug), while on real Windows a file created with that name resolves to the `NUL` device. A full integration PoC can reuse `Test_downloadRun_windowsReservedFilename` in `pkg/cmd/release/download/download_test.go`, substituting the asset name `"CON.tgz"` with `"NUL "` (or `"COM1 "`) and asserting that `downloadRun` does NOT return the `unable to download release due to asset with reserved filename` error, demonstrating the asset proceeds to `destinationWriter.Copy`/`os.OpenFile`.

```go
func isWindowsReservedFilename(filename string) bool {
	// Windows terminals should prevent the creation of these files
	// but that behavior is not enforced across terminals. Prevent
	// the user from downloading files with these reserved names as
	// they represent an exploit vector for bad actors.
	// Reserved filenames defined at:
	// https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file#win32-file-namespaces
	reservedFilenames := []string{"CON", "PRN", "AUX", "NUL", "COM0",
		"COM1", "COM2", "COM3", "COM4", "COM5",
		"COM6", "COM7", "COM8", "COM9", "COM¹",
		"COM²", "COM³", "LPT0", "LPT1", "LPT2",
		"LPT3", "LPT4", "LPT5", "LPT6", "LPT7",
		"LPT8", "LPT9", "LPT¹", "LPT²", "LPT³"}

	// Normalize type case and remove file type extension from filename.
	filename = strings.ToUpper(strings.Split(filename, ".")[0])

	return slices.Contains(reservedFilenames, filename)
}
```
