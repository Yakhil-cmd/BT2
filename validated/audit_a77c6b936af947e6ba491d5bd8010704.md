### Title
Webhook signature is verified against `repository.owner.login`, but every handler routes and mutates state by `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/webhook secret to validate a webhook against using `repository.owner.login` from the (unauthenticated at that point) JSON body, while every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest::*Handlers`) looks up the target `Stack`/`Repository`/`Commit` using the unrelated `repository.full_name` field. Nothing ties these two fields together, so a payload that is validly signed for organization A can still act on a repository/stack belonging to organization B, purely by making `full_name` point elsewhere while `owner.login` (and the rest of the payload consistent with A) is used to pick the verifying secret.

### Finding Description
In `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`verify_signature` derives `repository_owner` from the payload (`params.dig('repository', 'owner', 'login')`) and uses it solely to select which `GitHubApp`/`webhook_secret` to check the `X-Hub-Signature` against: [2](#0-1) 

Meanwhile, every handler in `app/models/shipit/webhooks/handlers/` resolves the affected `Repository`/`Stack` by `repository.full_name`, not by `repository.owner.login`: [3](#0-2) [4](#0-3) [5](#0-4) 

The security invariant that is implicitly assumed but never enforced is: `payload['repository']['owner']['login'] == payload['repository']['full_name'].split('/').first`. In a genuine GitHub webhook this always holds because GitHub itself fills in both fields for the same repository object and signs the whole payload with the secret configured for that specific repository/installation. But Shipit's multi-org verification (`lib/shipit/github_app.rb`'s `verify_webhook_signature`, invoked via `Shipit.github(organization: repository_owner)` in `lib/shipit.rb`) only proves that *whoever configured/knows the webhook secret for the organization named in `owner.login`* produced this exact byte string — it proves nothing about `full_name`. Anyone who administers a GitHub App/organization onboarded into this Shipit instance (i.e., anyone who legitimately knows their own org's `webhook_secret`, which is routinely visible to org admins/GitHub App owners) can craft an arbitrary JSON body, set `repository.owner.login` to their own org (so the correct secret is used for HMAC/signature verification) and set `repository.full_name` (and other event-specific fields such as `sha`, `state`, `check_suite.head_sha`, etc.) to reference a stack/repository/commit that belongs to a *different* organization entirely, then sign it with their own valid secret.

This directly breaks the binding this scan is meant to catch: *"an organization that authenticated versus the repository that is written."* The organization whose secret authenticated the webhook (`owner.login`) is not the same as the repository that ends up mutated (`full_name`).

### Impact Explanation
Depending on event type, this allows an attacker who controls one legitimately onboarded GitHub organization/webhook secret to inject state for stacks belonging to a completely different, unrelated organization onboarded on the same Shipit instance:
- `StatusHandler` (`status` event) directly writes attacker-controlled `state`, `description`, `target_url`, and `context` onto any `Commit` matching an attacker-guessed/known `sha`, regardless of which repository that commit belongs to — this can flip CI/deployability status (`commit.create_status_from_github!`) used to gate `ignore_ci`/merge/deploy decisions on someone else's stack. [6](#0-5) 
- `CheckSuiteHandler` and `PushHandler` can trigger check-run refreshes / GitHub sync jobs against a victim stack of another org. [7](#0-6) 
- `PullRequest::*Handlers` can mutate `PullRequest`/`ReviewStack` state (labels, assignment, open/close, provisioning of review stacks) for a repository not owned by the authenticating org. [8](#0-7) 

Given the rules of this analysis, only the `status` handler's ability to falsify commit-status/CI state feeding into merge/deploy decisions for a cross-organization stack rises to a concrete, credential-boundary-crossing impact (falsified deployability/merge gating state on a repository the attacker does not control) — this is the closest match to "escalation into `Shipit.github_teams` authorization" / an unauthorized deploy path, since deploy/merge gating relies on commit status.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple GitHub organizations (the `github: {org: {...}}` multi-app schema shown in `docs/setup.md`), and requires the attacker to control at least one of those onboarded organizations/webhook secrets (i.e., they are a legitimate GitHub App owner/admin for one org served by this Shipit instance, but not for the victim org). This is a realistic operator model for shared/multi-tenant Shipit deployments, but is not exploitable by a fully anonymous internet attacker with no relationship to the instance at all — it requires being a legitimate operator of one of the onboarded orgs. `repository.full_name` and commit SHAs for the victim repo are typically public/guessable (public GitHub repos), lowering the bar further.

### Recommendation
In `WebhooksController#verify_signature` / in `Handler#repository_name`, enforce that `repository.owner.login` (the field used to select the verifying secret) matches the owner segment of `repository.full_name` before dispatching to handlers, e.g.:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  return head(422) unless repository_owner_matches_full_name?
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner_matches_full_name?
  full_name = params.dig('repository', 'full_name')
  return true if full_name.blank? || repository_owner.blank?
  full_name.split('/').first&.casecmp?(repository_owner)
end
```
Alternatively, resolve the target repository/stack using `owner.login` + repo name consistently everywhere, instead of trusting `full_name` alone, so the same payload field used for authentication is the one used for authorization/dispatch.

### Proof of Concept
Conceptual (cannot be executed without live multi-org secrets, but demonstrates the code path):
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (per `docs/setup.md`'s multi-org schema).
2. Attacker, who legitimately administers `attacker-org`'s GitHub App, crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over this exact JSON body and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` computes `repository_owner = "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and successfully verifies the signature (it is genuinely signed with that org's secret).
5. `StatusHandler#process` runs, looks up `Commit.where(sha: params.sha)` for the victim's commit (unrelated to `attacker-org`) and calls `create_status_from_github!`, writing an attacker-controlled CI status onto `victim-org`'s commit — despite the request never being authenticated by anything belonging to `victim-org`.
