### Title
Non-constant-time pure-JS `secp256k1/elliptic` fallback in device ECDH/ECDSA permits private-key recovery via timing side channel - (File: package.json, device.js)

### Summary
When ocore is bundled for browser environments (light wallets / GUI wallets), the `browser` field in `package.json` aliases the native `secp256k1` binding to `secp256k1/elliptic`, a pure-JS implementation, for every signing and ECDH operation in the codebase, including the repeated Diffie-Hellman key agreement performed on the long-lived permanent device key in `device.js`.

### Finding Description
`package.json` declares:
```
"browser": {
  "request": "browser-request",
  "secp256k1": "secp256k1/elliptic"
}
``` [1](#0-0) 

This substitution silently swaps the native, side-channel-hardened `secp256k1` addon for the pure-JS `elliptic`-based scalar-multiplication implementation whenever ocore is built for a browser target, mirroring exactly the bug class in the phpseclib report: a pure-language EC implementation performing data-dependent conditional operations during scalar multiplication, with no native-engine check gating its use.

The riskiest reachable call site is `deriveSharedSecret()` in `device.js`, which performs ECDH using whichever key applies — critically, the **permanent** device private key (`objMyPermanentDeviceKey.priv`) is used as a fallback whenever the ephemeral/temp key can't be matched: [2](#0-1) [3](#0-2) 

This permanent key is also the key used to sign every device message and login challenge via `ecdsaSig.sign` in `signature.js`, which likewise routes through `secp256k1`/`secp256k1-elliptic`: [4](#0-3) [5](#0-4) 

Because the permanent device key is reused indefinitely (never rotated, unlike the temp key which is rotated on a schedule via `rotateTempDeviceKey()` [6](#0-5) ), a browser-bundled client (paired device / hub client) that repeatedly performs ECDH against this key with attacker-controlled ephemeral pubkeys, or repeatedly signs with it, exposes many ladder/nonce-multiplication executions of the same secret scalar to a local timing observer — exactly the precondition the report calls out ("reused or long-lived key … execution of the pure-... path … local observer capable of resolving individual ladder steps").

### Impact Explanation
Recovery of the permanent device private key allows an attacker to forge `ecdsaSig.sign` signatures under `objMyPermanentDeviceKey`, impersonate the victim device to its hub and paired correspondents (login, message signing, temp-pubkey signing), and decrypt all device-to-device traffic encrypted to that permanent key (private payment chains, AA triggers, and payment notifications routed via `device.js`/`wallet.js`). Where a device's identity key doubles as (or cosigns) a payment address signing path — e.g. multi-device/multisig wallets that rely on device-address identity for signing offers — this enables unauthorized spending and forged AA triggers.

### Likelihood Explanation
Exploitation requires: (1) the ocore browser bundle actually being used (light/GUI wallets built with the declared `browser` field), (2) the permanent device key being exercised repeatedly (login, message signing, ECDH with attacker-supplied ephemeral pubkeys — trivially triggerable by any correspondent/paired device sending repeated encrypted messages), and (3) a local timing observer (e.g., a malicious script/extension co-resident in the browser, or a malicious correspondent measuring round-trip response timing to a locally-observable degree). This is analogous to, but weaker in practical local-observer availability than, the original phpseclib report; it still satisfies the medium-severity local-timing-observer threat model since any paired device or asset/AA counterparty can trigger unlimited ECDH/signing operations against the target's stable permanent key merely by sending messages.

### Recommendation
Remove the `secp256k1` → `secp256k1/elliptic` browser alias, or ensure the pure-JS fallback is never used for operations on long-lived keys (permanent device key). At minimum, gate any pure-JS EC path behind explicit warnings, and consider rotating/deriving ephemeral-only keys for all ECDH in `deriveSharedSecret`, eliminating fallback to the permanent key in `decryptPackage`.

### Proof of Concept
1. Build/run ocore for a browser target (per the `browser` field in `package.json`), which loads `secp256k1/elliptic` instead of the native addon.
2. As a correspondent/paired device, repeatedly send encrypted `hub/deliver` messages to the victim's permanent device pubkey (bypassing the temp key by using `objMyPermanentDeviceKey.pub_b64` as `recipient_ephemeral_pubkey`), forcing `decryptPackage` → `deriveSharedSecret` → `ecdsa.ecdh(pubkey, priv_key, …)` on the same fixed permanent private key many times (`device.js` lines 397-402, 425-428).
3. Measure per-call timing/call patterns from a co-resident local observer during the pure-JS `elliptic` scalar multiplication to recover bits of the permanent scalar, as described in the report's Montgomery-ladder analog.
4. Use the recovered private key to forge `ecdsaSig.sign` signatures and impersonate the device / decrypt its traffic.

function deriveSharedSecret(peer_b64_pubkey, privKey){
	var pubkey = new Buffer(peer_b64_pubkey, 'base64');
	var shared_secret_src = Buffer.from(ecdsa.ecdh(pubkey, privKey, {hashfn: (x, y) => x}, Buffer.alloc(32)));
