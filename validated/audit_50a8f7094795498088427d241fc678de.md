### Title
Zero-balance "initial deposit" branch in the shipped AMM-style AA template lets a griefing trigger sender fix an extreme price/ratio before the real first depositor arrives - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The bundled reference AA `uniswap_like_market_maker.oscript` (parsed and covered by `test/ojson.test.js`) determines whether an incoming deposit is the *first* ("initial") deposit into the pool purely by checking whether the AA's pre-trigger balances of the two assets are zero:

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
``` [1](#0-0) 

This is functionally the same bug class as the Y2K `ControllerPeggedAssetV2` report: a decision branch (there, "resolve as null epoch"; here, "this is the initial deposit that fixes the price") is gated solely on a **zero total balance** check that any unprivileged trigger sender can influence by posting a minimal-value unit before the intended/legitimate participant.

### Finding Description
The AA is defined with `init` creating `$mm_asset` on the first `{define:1}` trigger, and any subsequent trigger sender can immediately follow up with a trivially small deposit (e.g. slightly over `1e5` bytes plus `1` unit of `$asset`, matching the `if` condition on the "invest in MM" case) while the AA's balances are still zero. Because `balance[$asset]` and `balance[base]` are read only from on-chain AA balances at the time of the trigger, `$asset_balance` and `$bytes_balance` both evaluate to `0`, forcing execution into the `// initial deposit` branch. That branch mints MM shares (`$issue_amount = balance[base]`) without validating any ratio, and unconditionally establishes `var['mm_asset_outstanding']` from this attacker-chosen combination of amounts.

Any subsequent depositor — including the intended legitimate first depositor — is now forced through the ratio-check branch, where the price (`$current_ratio = $asset_balance / $bytes_balance`) is dictated by the attacker's arbitrary initial numbers. As in the reported issue, a malicious/opportunistic actor watching the AA can win the race to be the party whose deposit satisfies the `== 0` check, gaining outsized control over the share-issuance ratio and imposing an unfavorable or unusable ratio on everyone else, exactly mirroring "triggering null epoch can be prevented/exploited by a malicious user who deposits a small amount while the other side is zero." [2](#0-1) 

### Impact Explanation
Because MM-share issuance and the exchange ratio for all future deposits/exchanges are derived from whichever balances happen to be non-zero at the moment the zero-check is evaluated, an attacker who wins this race can:
- Set an extreme price ratio (e.g., depositing 1 unit of `$asset` against the minimum required `>1e5` bytes), causing legitimate depositors' matching-ratio checks (`bounce('wrong ratio of amounts...')`) to fail or to require economically absurd deposits, effectively freezing the pool to genuine liquidity ("AA fund loss or freezing").
- Alternatively mint themselves a disproportionate share of `mm_asset_outstanding` relative to negligible capital contributed, diluting/extracting value from subsequent honest depositors when they divest.

This matches the accepted impact categories (AA fund loss or freezing via unauthorized/disproportionate control of a shared pool).

### Likelihood Explanation
The AA only requires an unprivileged trigger sender able to post a unit with the minimal qualifying outputs (`trigger.output[[asset=base]] > 1e5` and `trigger.output[[asset=$asset]] > 0`) before the legitimate depositor's unit becomes the one observed with zero prior balance. Since posting a trigger unit is available to any network participant and the check depends only on the AA's balance state at trigger time (not on any identity or authorization), this is trivially and cheaply reachable — the same "wait for a favorable window, then act with a tiny amount" pattern described in the original report.

### Recommendation
Do not use a bare `balance == 0` check to gate privileged/no-ratio-validation code paths. Require an explicit, authenticated initialization step (e.g., only the AA definer/owner address, or a dedicated `init` trigger recorded in state) to set the initial ratio, or enforce a minimum bootstrap liquidity deposited atomically with asset creation so no window exists where an arbitrary small deposit can be mistaken for the authoritative "first" deposit.

### Proof of Concept
1. Deploy the AA; anyone sends `{define: 1}` to create `mm_asset` (open to all, no ratio set yet).
2. Immediately after (same or next unit), attacker sends a unit with `trigger.output[[asset=base]] = 100001` and `trigger.output[[asset=$asset]] = 1` to the AA.
3. At evaluation time `balance[$asset]` and `balance[base]` are still `0` (no prior deposits), so `$asset_balance == 0` and `$bytes_balance == 0` — the `// initial deposit` branch fires, minting `mm_asset` = 100001 to the attacker and fixing `var['mm_asset_outstanding']` from this extreme 1:100001 ratio.
4. A legitimate depositor later tries to add proportional liquidity but must match `$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]])` using the attacker-fixed ratio, causing their deposit to bounce (`'wrong ratio of amounts...'`) or to require an economically infeasible amount of `$asset`, freezing genuine participation in the pool.
