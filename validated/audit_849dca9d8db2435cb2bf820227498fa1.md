### Title
Cross-stack, unauthenticated status forgery bypasses `Shipit::Commit#blocked?` via `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target commit purely by `sha`, with no check that the webhook's repository matches the commit's stack repository, so any commit sharing that sha in *any* stack receives the forged `Status` row. Because `Status::Common#blocking?` treats a `state: success` status as never blocking regardless of `context`, an attacker who can get a real signed status webhook fired for a colliding sha can neutralize a victim stack's `blocking_statuses` gate and flip `Commit#blocked?` from `true` to `false`, enabling an unauthorized deploy.

### Finding Description
The broken binding: `stack.blocking_statuses.include?(context) == context reported by the stack's own configured CI integration for that stack's repository`. In reality the equality is `stack.blocking_statuses.include?(context) == context supplied verbatim in any status webhook whose sha happens to match a commit row belonging to that stack`, with no repository binding at all.

`StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [1](#0-0) 
This query is global across the `commits` table — it is not scoped to a stack, repository, or the `repository`/`organization` fields used only in `WebhooksController#verify_signature`. `create_status_from_github!` then persists the row using the *found commit's own* `stack_id`: [2](#0-1) 
and `Status.replicate_from_github!` writes `context`/`state` verbatim from the payload with no server-side validation against what that stack's real CI ever reported: [3](#0-2) 

`Commit#blocked?` and `Status::Common#blocking?` are:
```ruby
def blocked?
  return false if stack.blocking_statuses.empty?
  stack.commits.reachable.newer_than(stack.last_deployed_commit).older_than(self).any?(&:blocking?)
end
``` [4](#0-3) 
```ruby
def blocking?
  !success? && commit.blocking_statuses.include?(context)
end
``` [5](#0-4) 
and `deployable?`: [6](#0-5) 

Exploit flow: an attacker with write access to their own repository connected to Shipit (own org/repo, own GitHub App installation and thus a validly signed webhook) creates a commit whose sha collides with a commit that already exists in a victim stack's `commits` table (e.g., shared ancestor history from a fork, or identical content). The attacker then uses the GitHub Statuses API on their own repo/sha to set an arbitrary `context` (matching the victim stack's `ci.blocking` context, e.g. `ci/tests`) with `state: success`. GitHub delivers a genuinely signed `status` webhook to Shipit. `WebhooksController#verify_signature` only checks that the signature matches the secret for `repository_owner` (the attacker's own org) — it never checks that the `sha`/commit actually belongs to that repository. `drop_unhandled_event`, `check_if_ping`, and the `ExplicitParameters` schema in `StatusHandler` (`requires :sha`, `accepts :context`) impose no cross-repository binding either. The handler then finds the victim's `Commit` row by raw sha match and writes a `Status` with attacker-chosen `context`/`state` into the victim's stack. Because the forged status has `state: success`, `Status::Common#blocking?` evaluates to `false` for that status (the `!success?` guard) even though `context` matches `stack.blocking_statuses`, so the previously-blocking commit no longer appears in `stack.commits.reachable...any?(&:blocking?)`, `blocked?` flips to `false`, and `deployable?` becomes `true` for later commits in the victim stack.

### Impact Explanation
This allows an unprivileged attacker to write an arbitrary `Status` row into a victim stack they do not own or control, and specifically to defeat the `ci.blocking` gate (`Stack#blocking_statuses`) that operators rely on for cross-cutting compliance/safety gates (e.g., `soc/compliance`), enabling an unauthorized deploy in a tenant the attacker never authenticated against. This is a payload from one repository mutating another repository's commit/stack state and enabling an unauthorized deploy — matching the Critical impact category. It is repeatable against any stack whose commit history shares a sha with a repository the attacker controls (most straightforwardly via forks, which are common and cheap to create), and the blast radius spans every stack/tenant on the Shipit instance since the `Commit.where(sha:)` lookup is global and unscoped.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository connected to a Shipit-recognized GitHub App/organization capable of producing a validly signed webhook (i.e., their own onboarded org/repo), and (b) a sha collision with a commit already tracked in the victim's stack — most practically achieved by forking the victim's repository or otherwise sharing git history, since git commit hashes are content-addressed and identical content on both sides yields identical shas without any cryptographic collision. The victim stack must have `ignore_ci?` false and a non-empty `blocking_statuses` list, and the colliding commit must be within the "reachable, newer than last-deployed, older than target" range that `blocked?` scans. These are realistic, low-cost preconditions for a public-repo fork scenario, making the attack feasible and repeatable per victim stack.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other sha-keyed handlers) to only update commits belonging to a stack whose repository matches the webhook's `repository.full_name`/`repository_id`, e.g. filter `Commit.joins(:stack).where(sha: params.sha, stack: { repository: repo_from_payload })` instead of a bare global `Commit.where(sha:)`. Additionally, consider not letting `state: success` unconditionally exempt a status from `blocking?` scoring when `context` matches `blocking_statuses`; blocking status semantics should be derived from statuses genuinely reported by the configured CI for that stack's own repository.

### Proof of Concept
```ruby
# test/models/commits_test.rb (or webhooks_controller_test.rb) — conceptual proof, no live GitHub
test "cross-stack status forgery bypasses blocking_statuses gate" do
  victim_stack = shipit_stacks(:soc) # stack with ci.blocking => ['soc/compliance']
  blocking_commit = shipit_commits(:soc_second)
  blocking_commit.statuses.delete_all
  target_commit = shipit_commits(:soc_third)

  refute victim_stack.ignore_ci?
  assert_predicate blocking_commit, :blocking? # missing required blocking status -> blocking
  refute_predicate target_commit, :deployable? # blocked

  # Attacker-controlled repo emits a validly signed webhook whose sha collides
  # with blocking_commit.sha (e.g. via fork), with attacker-chosen context/state.
  forged_status = OpenStruct.new(
    state: 'success',
    context: 'soc/compliance', # matches victim's blocking_statuses, attacker-supplied
    description: 'forged',
    target_url: nil,
    created_at: Time.current.to_formatted_s(:db)
  )

  # Simulates StatusHandler#process's unscoped lookup:
  Shipit::Commit.where(sha: blocking_commit.sha).each do |commit|
    commit.create_status_from_github!(forged_status)
  end

  refute_predicate blocking_commit.reload, :blocking?      # BEFORE would be true, now false
  assert_not target_commit.reload.blocked?                  # blocked? flips false
  assert_predicate target_commit, :deployable?               # unauthorized deploy enabled
end
```
