### Title
Cross-repository SHA collision in `StatusHandler#process` lets any GitHub-App-verified repository forge `:deployable_status`/`:commit_status` hooks for an unrelated stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits to update purely `Commit.where(sha: params.sha)`, with no join or check against the repository that actually sent the webhook. `verify_signature` in `WebhooksController` only proves the payload was signed by the GitHub App installation for `repository_owner` from the payload - it never proves that the `sha` in the payload belongs to that same repository. Any repository whose owner has a recognized GitHub App installation (attacker-controlled repo B) can send a genuinely-signed `status` webhook for a sha that also exists in victim stack A's git history (e.g. a fork, shared ancestor commit, or otherwise duplicated commit object), causing Shipit to write a new `Status` on stack A's commit and emit `Hook.emit(:deployable_status, stack_A, ...)`.

### Finding Description
The broken binding, stated as an equality that is assumed but never checked:
`commit.stack.github_repo_name == repository_owner_from(payload) + "/" + payload.dig('repository','name')`

Actual code path:
1. `Shipit::WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-30) validates only that the request signature matches `Shipit.github(organization: repository_owner)` - i.e. that *some* recognized GitHub App installation (repo B, which the attacker owns/controls) sent it. It does not check which repository's commits may be touched by the payload body. [1](#0-0) 
2. `StatusHandler#process` then resolves affected commits solely by SHA, globally across the whole `commits` table, with no repository/stack filter: [2](#0-1) 
3. For every matching commit (which may belong to stack A, a completely different repository/tenant than the one that sent the webhook), `Commit#create_status_from_github!` → `#add_status` is invoked: [3](#0-2) 
4. `#add_status` compares the previous and new simple_state and, on a qualifying transition, emits the hook scoped to `stack` (stack A), using attacker-supplied `state`/`description`/`context` fields as the new status: [4](#0-3) 

Root cause: git SHAs are content-addressed and can be identical across independent repositories that share commit history (forks, mirrors, monorepo splits, cherry-picked/rebased commits with identical author/committer/timestamp/tree). Shipit's webhook signature only authenticates "this repo's GitHub App installation sent this", not "this SHA belongs to this repo". `Commit.where(sha: params.sha)` has no `stack_id`/repository scoping, so a signed-but-unrelated payload from repo B is applied to any and all commits sharing that SHA, including stack A's.

None of the existing guards close this gap: `verify_signature` authenticates the sender but not the SHA-to-repository binding; `drop_unhandled_event` only filters on event type; the `ExplicitParameters` schema in `StatusHandler` only validates field types/presence, not ownership; there is no `require_permission!`/`stacks` scope check in this webhook path (webhooks are unauthenticated-by-session by design, relying entirely on signature + payload semantics).

### Impact Explanation
An attacker who controls repo B (any GitHub account they can register with Shipit's GitHub App) can cause Shipit to write a forged `Status` record against a commit belonging to victim stack A, changing that commit's computed `deployable?`/`state`, and can trigger:
- `Hook.emit(:commit_status, stack_A, ...)` and `Hook.emit(:deployable_status, stack_A, ...)`, propagating false state to any external system subscribed to stack A's hooks (e.g. `Shipit::GithubHook` posting a status back to GitHub for stack A's repo, or other custom webhook subscribers).
- `stack.schedule_merges` when the forged state is `pending`/`success`, potentially advancing `ContinuousDeliveryJob`/merge-request processing for stack A based on entirely attacker-controlled input.

This is a genuine cross-tenant write: a payload authenticated for repository B mutates data (`Status` rows) belonging to stack A and fires side effects scoped to A. This matches the Critical category ("a payload for one repository mutating another's stack/commit"), repeatable for any sha that happens to be shared between an attacker-controlled repo and a victim stack's commit history (most plausible via forks/mirrors of the victim's own public repository).

### Likelihood Explanation
Preconditions: the attacker must have (a) any GitHub account/org onto which Shipit's GitHub App can be installed (i.e., `Shipit.github(organization: repository_owner)` resolves, a low bar in multi-tenant/public-app Shipit deployments), and (b) a commit SHA that is present both in their own repo and in the victim stack A's tracked commit history. The latter is realistic when B is a fork or mirror of A's repository (shared ancestor commits share identical SHAs), which is common and requires no cryptographic collision - just normal git object identity. Attacker cost is low: fork or push to their own repo, then call GitHub's Statuses API on their own repo for a shared-history SHA, which GitHub will deliver as a properly signed webhook. This is repeatable against any stack whose repository has been forked/mirrored elsewhere.

### Recommendation
In `StatusHandler#process` (and analogous handlers that resolve records purely by `sha`), scope the `Commit` lookup to commits whose `stack.github_repo_name` (or `repository.full_name`) matches the repository named in the incoming payload (`payload.dig('repository','full_name')`), not just the sha:
```ruby
def process
  repo_full_name = params.dig(:repository, :full_name) # add to ExplicitParameters schema
  Commit.where(sha: params.sha).select { |c| c.github_repo_name == repo_full_name }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
Apply the same repository-scoping fix to any other webhook handler that queries by `sha` alone (e.g. check-run/check-suite handlers) to close the general class of cross-repository SHA-collision issues.

### Proof of Concept
minitest plan (model-level, no live GitHub, per rules):
```ruby
test "cross-repo sha collision forges deployable_status hook for unrelated stack" do
  stack_a = shipit_stacks(:shipit)
  commit_a = stack_a.commits.create!(sha: 'deadbeef' * 5, ...) # shared sha, unknown state

  # Simulate payload signed for/originating from an unrelated repo B, same sha as commit_a
  forged_params = Shipit::Webhooks::Handlers::StatusHandler::Params.new(
    sha: commit_a.sha, state: 'success', context: 'ci/forged', description: 'forged'
  )

  Shipit::Hook.expects(:emit).with(:deployable_status, stack_a, has_entries(deployable_status: instance_of(Shipit::Status)))

  Shipit::Webhooks::Handlers::StatusHandler.new.process # invoked with forged_params, no reference to stack_a's repo
end
```
Assert both sides of the equality: before the fix, `commit.stack.github_repo_name` ("owner/repoA") is never compared to the payload's `repository.full_name` ("attacker/repoB"), so the hook fires for stack A despite `payload.repository.full_name != stack_a.github_repo_name`. After the fix, the handler must skip commit_a when the repo names diverge, and `Hook.emit` must not be called for stack_a.
