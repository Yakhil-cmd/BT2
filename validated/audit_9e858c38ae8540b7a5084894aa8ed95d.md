## Finding: Webhook signature verification authenticates a different organization than the one whose data is acted upon

### Title
GitHub webhook signature verifies the org named in `repository.owner.login`, but handlers act on the unrelated `repository.full_name`/`sha` fields from the same untrusted payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the HMAC secret to check against based on an attacker-controlled field of the very payload it is validating, then hands the *entire* unvalidated payload to handlers that key off a *different* field of that payload to decide which repository/commit to mutate. The signature therefore proves "whoever holds org X's `webhook_secret` produced these bytes," but never proves "the `repository.full_name`/`sha` referenced inside these bytes belongs to org X." This breaks the intended binding: `organization that authenticated == repository that is written`.

### Finding Description
`verify_signature` derives the organization used to fetch the GitHub App/secret straight from the JSON body being verified: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — fields fully controlled by whoever is sending the HTTP request, before any cryptographic check has happened. `Shipit.github(organization: repository_owner)` then loads that organization's `webhook_secret` and verifies the signature against `request.raw_post`: [3](#0-2) 

Note also `return true unless webhook_secret` — for any org configured without a webhook secret (documented as optional in `docs/setup.md`), verification is a no-op regardless of the header supplied.

Once "verified," the full `params` object — including any field the attacker chose — is dispatched unchanged to handlers: [4](#0-3) 

Handlers resolve the target repository/stack from `payload.dig('repository', 'full_name')`, a completely independent field from the one used for signature routing: [5](#0-4) 

`PushHandler` triggers a GitHub sync with an attacker-chosen `expected_head_sha` for whichever repository/branch `full_name` points to: [6](#0-5) 

`StatusHandler` is even less scoped — it doesn't reference `repository` at all, and updates the CI status of any `Commit` row matching an attacker-supplied `sha`, across every stack/repository the Shipit instance tracks: [7](#0-6) 

`PullRequest::ClosedHandler` resolves an arbitrary repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and archives its review stack: [8](#0-7) 

### Impact Explanation
On a multi-organization Shipit install (explicitly supported per `docs/setup.md`'s "Using Multiple Github Applications" section, where each org has its own `app_id`/`webhook_secret`), an attacker who controls the webhook secret for *one* onboarded organization (or targets an organization deliberately left without a secret, which `verify_webhook_signature` treats as always-valid) can forge a payload that:
- passes signature verification as "org B" (`repository.owner.login: "org-b"`), while
- carries `repository.full_name: "org-a/private-repo"` and a known commit `sha` belonging to org A's tracked stack.

This lets the attacker: inject fabricated commit statuses (`state: success`, arbitrary `target_url`/`description`) onto commits in a repository they never authenticated for — potentially satisfying deploy-readiness checks and enabling an unauthorized deploy; force `GithubSyncJob` runs against arbitrary tracked repos with attacker-chosen `expected_head_sha`; or archive/mutate review stacks belonging to unrelated organizations via `pull_request` events. This crosses the "unauthorized deploy" and "escalation across repository boundary" impact classes.

### Likelihood Explanation
Requires only that the attacker control (or exploit the absence of) a `webhook_secret` for any single organization configured on the shared Shipit instance — no repository write access, `ApiClient` token, or session is needed, and the multi-tenant configuration pattern is the one documented by the project itself.

### Recommendation
Bind the signature-verification identity to the same field the handlers act on: verify the signature using the organization/secret associated with `repository.full_name` (or the `Repository`/`Stack` actually resolved), not a separate, attacker-suppliable `repository.owner.login`/`organization.login` field. Additionally, after signature verification, re-derive the authorized organization and assert it matches the owner encoded in `repository.full_name` before any handler runs, and require `webhook_secret` to be mandatory (reject unsigned webhooks) rather than defaulting to `true` when unset.

### Proof of Concept
1. Configure/compromise Organization B's webhook secret on a shared Shipit instance that also tracks Organization A's repository (per documented multi-org setup).
2. Send `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<known commit sha tracked under org-a/private-repo>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "org-b" } }
}
```
Sign the raw body with Organization B's `webhook_secret` and set `X-Hub-Signature` accordingly.
3. `verify_signature` resolves `repository_owner` as `"org-b"`, fetches org B's secret, and the signature checks out.
4. `StatusHandler#process` runs against `Commit.where(sha: params.sha)` and writes a forged status for the commit in org A's repository — despite the attacker never possessing org A's webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
