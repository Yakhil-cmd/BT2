### Title
Index cache in `market.clar` is primed from whichever caller accrues first in a block and is trusted by every other user's operations in that block - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`market.clar` caches vault liquidity/borrow indexes in the shared map `index-cache`, keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0)  . The cache is populated once per block by `accrue-and-cache`, and every subsequent `borrow`, `collateral-add`, `collateral-remove`, `liquidate`, or price-resolution call in the *same block*, from *any* caller, reads that cached value directly instead of re-deriving it, via `get-cached-indexes`/`resolve-ztoken` [2](#0-1)  and `accrue-and-cache` [3](#0-2)  .

### Finding Description
The vault index (`index`/`lindex`) is not a fixed, externally-verified value like a Pyth VAA-signed price; it is derived at call time from the *current* on-chain utilization of the vault (`interest-rate` → `utilization` → `calc-utilization` based on `get-available-assets`/`total-debt`) [4](#0-3)  . Because `accrue-and-cache` is a cache-or-compute pattern keyed only by `(timestamp, aid)` and not by caller or by the exact state that produced it, whichever transaction in a given block happens to call `accrue-and-cache aid` first "bakes in" the index for that (asset, second) for every other transaction that touches the same asset later in the block:

```
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))
    (match cached?
      cached-indexes (ok cached-indexes)          ;; cache HIT — reused for everyone else
      (let ((indexes (try! (vault-accrue aid))))  ;; cache MISS — computed by first caller
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
``` [3](#0-2) 

This is analogous to the reported bug class: a piece of unverified, caller-influenced data (the coinbase height in the Zebra report; here, the index computed off whatever utilization exists at the moment of the first caller's transaction) is accepted into a shared cache/state without being pinned to a canonical, re-derivable value, and is then trusted by a second, unrelated party (any other user whose `borrow`/`collateral-add`/`collateral-remove`/liquidation in the same block reads `get-cached-indexes`) without independent re-validation.

Concretely: attacker A can, within the same block, first perform a large borrow/repay against a vault to transiently move `utilization()` to a favorable point on the interest curve, call any market entrypoint that triggers `accrue-and-cache` for that `aid` (e.g. `collateral-add`, `borrow`), causing the resulting `index`/`lindex` for `{timestamp: T, aid}` to be cached. Any other user B whose transaction in the *same block* touches the same asset (e.g., pledges the same ztoken as collateral, borrows the same debt asset, or is evaluated for liquidation) will transparently reuse A's cached index via `resolve-ztoken`/`get-cached-indexes` instead of a value computed from the state at their own transaction [2](#0-1)  . Whether the deviation is large enough to matter depends on how much A can move `utilization()` within one block/transaction versus how narrow the interest-rate curve segments are, but the shared-state read path unconditionally trusts the first observation.

### Impact Explanation
This falls into the "shared index or cache primed by one caller and consumed by another" analog class explicitly named in scope. Because the ztoken price used in collateral valuation and health checks (`resolve-ztoken`) as well as debt/liquidity index used for scaled-debt accounting come straight from this cache, a manipulated first-write can distort another user's collateral valuation, LTV/health computation, or liquidation trigger within that block — i.e., temporary freezing/misvaluation of another user's position for the duration of that block, without any validation tying the cached index back to the state at the second user's own transaction.

### Likelihood Explanation
Requires the attacker to be able to (a) move a vault's `utilization()` meaningfully within one Stacks block via ordinary borrow/repay operations (not flashloan-fee-restricted — plain deposits/borrows suffice) and (b) be first (or control ordering, e.g., via priority fees) to call an entrypoint that triggers `accrue-and-cache` for the targeted asset before the victim's transaction in the same block. This is easier on Stacks where block production and fee-based ordering exist, but requires precise timing and is dependent on how much utilization can move with realistically available capital. This is a design pattern used across every vault (`vault-stx`, `vault-sbtc`, `vault-ststx`, `vault-usdc`, `vault-usdh`, `vault-ststxbtc`) and every market entrypoint that calls `accrue-and-cache`, so the attack surface is broad, but successfully causing enough index drift to flip a victim's health check requires favorable interest-curve steepness and capital.

### Recommendation
Do not key the cache purely on `(timestamp, aid)` shared across all callers. Either (a) recompute `vault-accrue`/`next-index`/`next-liquidity-index` per top-level transaction rather than caching across transactions within a block, or (b) validate that the cached index used by a transaction corresponds to the utilization state visible to that transaction (e.g., bound the maximum permissible index drift per block, or invalidate the cache when utilization changes materially between the cache-write and cache-read).

### Proof of Concept
1. Attacker A observes vault V (e.g. `vault-usdc`) sitting at a utilization that yields a low index growth rate.
2. In block N, A submits tx1: a large `borrow`/`repay` sequence against V that transiently shifts `utilization()` to a point on the interest curve favorable to A (e.g., lower borrow rate segment via `interpolate-rate`), then within the same tx calls an operation that invokes `accrue-and-cache USDC`, writing `{timestamp: T, aid: USDC} -> {index, lindex}` computed from this manipulated utilization [5](#0-4)  .
3. Victim B, in the same block N, submits tx2 calling `collateral-add`/`borrow` involving zUSDC or USDC debt; B's transaction calls `get-cached-indexes USDC`, which hits the cache written by A and returns A's manipulated `lindex`/`index` instead of a value reflecting B's own transaction state [2](#0-1)  .
4. B's collateral valuation / debt accrual / health check is computed against this skewed index, producing a result different from what B's own transaction state alone would produce.

Note: I could not fully verify the exact magnitude of achievable utilization swing within a single block/transaction (would require modeling vault liquidity depth and the interest-rate curve breakpoints), so the concrete quantitative severity of the index skew is unconfirmed and would need empirical/PoC testing against a specific vault's configured `points-ir`.
