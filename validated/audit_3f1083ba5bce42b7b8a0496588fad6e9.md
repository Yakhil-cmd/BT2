### Title
Textcoin claiming logic assumes all assets on a claimed address share the same privacy/divisibility type, risking miscomposed payments and frozen funds - (File: wallet.js)

### Summary
`receiveTextCoin()`'s `checkStability()` handler reads every distinct asset held at a textcoin address and, instead of validating each asset's actual `is_private`/`fixed_denominations` properties individually, uses only the properties of the *first* asset returned to decide how to build and dispatch the payment for *all* assets on that address. This is the same class of bug as the reported NFTX issue: the code assumes a single type applies uniformly across multiple distinct assets, and the divergent ones are pushed down an incorrect code path instead of being rejected up front.

### Finding Description
In `checkStability()`:
```
const objAsset = asset_infos[0]; // assuming all other assets have the same privacy and divisibility
...
let outputs_by_asset = { };
for (let { asset, amount } of rows)
    if (asset)
        outputs_by_asset[asset] = [{ amount, address: addressTo }];
outputs_by_asset.base = [{ amount: 0, address: addressTo }];
opts.outputs_by_asset = outputs_by_asset;
...
if (objAsset.fixed_denominations) { // indivisible
    indivisibleAsset.composeAndSaveIndivisibleAssetPaymentJoint(opts);
}
else { // divisible
    divisibleAsset.composeAndSaveDivisibleAssetPaymentJoint(opts);
}
``` [1](#0-0) 

The dispatch decision (`indivisibleAsset` vs `divisibleAsset`) is made purely on `asset_infos[0]`'s `fixed_denominations`/`is_private` flags, yet `opts.outputs_by_asset` may contain other assets (`rows` grouped `GROUP BY asset`) that have different `is_private`/`fixed_denominations` values, since nothing constrains a single address from receiving outputs of multiple, differently-typed assets. [2](#0-1) 

By contrast, the sibling function `sendMultiPayment()` explicitly guards against this exact scenario when it reads a representative asset (`nonbaseAsset`) for a multi-asset `outputs_by_asset` request: it checks `objAsset.is_private || objAsset.fixed_denominations` and throws if `outputs_by_asset` contains any other asset, precisely because "outputs_by_asset with multiple assets cannot be used for private payments and indivisible assets":
```
if (outputs_by_asset && (objAsset.is_private || objAsset.fixed_denominations)) {
    if (Object.keys(outputs_by_asset).filter(a => a !== 'base' && a !== nonbaseAsset).length > 0)
        throw Error("outputs_by_asset with multiple assets cannot be used for private payments and indivisible assets");
    ...
}
``` [3](#0-2) 

`receiveTextCoin()`'s `checkStability()` path calls `indivisibleAsset.composeAndSaveIndivisibleAssetPaymentJoint()` / `divisibleAsset.composeAndSaveDivisibleAssetPaymentJoint()` directly, never routing through `sendMultiPayment()`, so this protective check is never applied to the textcoin-claim flow. If the textcoin address holds a mix of assets — e.g., a public divisible asset (returned first, alphabetically largest by the `ORDER BY asset DESC` clause) and a private and/or fixed-denomination asset — the divisible/indivisible composer is invoked with an `outputs_by_asset` map containing an asset whose true type does not match the composer being used.

`validatePaymentInputsAndOutputs()` in `validation.js` (lines 2089-2096, 2142-2143, 2161-2178) enforces strict per-asset invariants (denomination presence, output_hash/blinding fields, single-input rule for fixed-denomination assets, etc.) based on the asset's actual stored properties, so a mismatched payment message would ultimately be rejected at validation. [4](#0-3) [5](#0-4) 

The practical consequence is not that the network accepts an invalid unit, but that the claim transaction as a whole fails to validate/compose correctly for the mismatched asset, while the underlying UTXOs for that asset remain locked to the (now-disclosed) textcoin address — the private key/mnemonic for that address is only intended to be usable once via the claiming flow, and a partial/failed multi-asset claim can leave the mismatched asset's outputs practically unclaimable through the normal claim UI/API path, since the code never separates them out into their own compliant payment message the way `sendMultiPayment()` would.

### Impact Explanation
A textcoin address holding a mix of asset types (something the sender fully controls when creating/funding the textcoin, or that can occur if multiple distinct assets end up credited to the same one-time address) can trigger `receiveTextCoin()` to build a payment message set that violates the type-specific validation rules of one of the assets. This can cause the claim to fail without a code path to properly separate/represent the divergent asset, effectively freezing that asset's balance at the throwaway textcoin address (which is not intended for storage, only for a one-shot claim). Given the low likelihood (specific asset-mixing setup) combined with the high impact of permanent inaccessibility of funds, this aligns with a medium severity classification consistent with the reported analog.

### Likelihood Explanation
Exploitation requires an attacker or careless sender to fund a single textcoin address with outputs from two or more assets of differing `is_private`/`fixed_denominations` properties (or a malicious counterparty could deliberately do this to grief a recipient's claim). This is a normal, unprivileged wallet operation (any user composing/funding a textcoin), matching the "posted unit"/"private-payment counterparty" reachability required by scope rules, but the precondition (asset-type mixing on one throwaway address) is not the default UX, making likelihood low-to-moderate.

### Recommendation
In `checkStability()`, do not select a single representative asset via `asset_infos[0]` for multi-asset dispatch decisions. Instead, apply the same guard used in `sendMultiPayment()`: when `outputs_by_asset` covers more than one non-base asset, verify none of them is private or has `fixed_denominations`, or otherwise split the claim into one payment per asset dispatched through the correct composer (`indivisibleAsset` vs `divisibleAsset`) based on that specific asset's own properties, rejecting/handling mixed-type claims explicitly instead of assuming uniformity.

### Proof of Concept
1. Create a textcoin address (via `expandMnemonic`) and fund it, in two separate transactions, with outputs of Asset A (public, divisible, `fixed_denominations=false`) and Asset B (private and/or `fixed_denominations=true`).
2. Call `receiveTextCoin(mnemonic, addressTo, ...)`.
3. In `checkStability()`, `rows` returns both assets (`ORDER BY asset DESC`), `asset_infos[0]` reflects only one of them (e.g., Asset A, public/divisible), and `outputs_by_asset` is populated with entries for both Asset A and Asset B keyed uniformly. [6](#0-5) 
4. `divisibleAsset.composeAndSaveDivisibleAssetPaymentJoint(opts)` is invoked (because `objAsset.fixed_denominations` is false for Asset A), but `opts.outputs_by_asset` also carries Asset B's output, whose true type requires the indivisible/private handling path (denomination, output_hash, single-input constraints) enforced in `validatePaymentInputsAndOutputs()`. [7](#0-6) 
5. The resulting composed payment either fails validation for Asset B's message (unit rejected, claim fails) or is malformed, leaving Asset B's balance stuck at the one-time textcoin address without going through the compliant multi-asset separation logic present in `sendMultiPayment()`.
