Based on my investigation, I found a genuine structural analog in `pox-5.clar`'s `unstake` mechanism.

### Title
Unauthorised self-unstake in pox-5 nullifies an already-committed reward-cycle slot without updating signer weight / reward-set totals - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar, pox-locking/src/pox_5.rs)

### Summary
pox-5 introduces a `stake`/`unstake` API where a staker can call `unstake` themselves to reschedule their own already-locked STX to unlock at the start of the next reward cycle, similar in spirit to the McDex "appliedBalance"/"cancel order" bug, where a party unilaterally nullifies a commitment that other participants (signers, reward-set totals) already relied upon.

### Finding Description
The `handle_unstake_pox_v5` handler in `pox-locking/src/pox_5.rs` explicitly documents that it "reschedules the already-locked STX to unlock at the start of the next reward cycle" while leaving the locked amount unchanged: [1](#0-0) 

The accompanying unit test confirms the STX balance's `unlock_height` moves earlier while `amount_locked` stays the same: [2](#0-1) 

This is called directly from `handle_contract_call` for the `unstake` function, gated only by being a tx-sender-initiated PoX action: [3](#0-2) 

In the older PoX-2/3/4 contracts, an early unlock (`handle-unlock`) is only ever invoked by the block processor itself for "missed reward slots" and explicitly removes the stacker from every `reward-cycle-pox-address-list` entry and decrements `reward-cycle-total-stacked` for every affected cycle, keeping the committed reward-set totals consistent with actual locked STX: [4](#0-3) [5](#0-4) 

By contrast, in pox-5 a staker-initiated `unstake` moves up the unlock height on the STX balance but the handler comment says nothing about the reward-cycle/signer-set bookkeeping being reconciled the same way the block-processor-only `handle-unlock` does in pox-2/3/4. If the pox-5 Clarity contract's reward-set / signer-weight state (analogous to `reward-cycle-pox-address-list`, `reward-cycle-total-stacked`) is not synchronously purged for the cycles the staker is unstaking from, this breaks the equality: `sum(reward-set commitments for cycle) == sum(actually-locked STX for cycle)`. This is precisely the McDex-report bug class — a party can unilaterally nullify a commitment (their own stake, previously counted in a reward slot/signer weight already relied on by the signer set and other stackers in that reward cycle) via a call the protocol treats as fully self-authorised but that was not "timelocked" or synchronized against downstream state that already consumed the commitment.

### Impact Explanation
If `unstake` allows a staker to early-unlock STX that has already been counted into a reward cycle's total stacked amount / signer weight (used to compute signer thresholds and reward-set slots for the *upcoming* cycle), then signer voting weight or reward-set totals would exceed the STX actually still locked — a "signing weight or reward slots exceeding locked value" condition explicitly listed as a High-impact class. It could also cause temporary freezing/inconsistency for other stackers in the same aggregate pox-addr entry if `unstake` decrements only the individual's own account rather than the shared `reward-cycle-pox-address-list`/`reward-cycle-total-stacked` entries.

### Likelihood Explanation
This requires no privileged access — any solo staker (or pool participant) who called `stake` can call `unstake` on their own principal. The only gating shown in the code is a generic PoX-action bookkeeping call in `handle_contract_call`, not a check that no reward-cycle commitment already depends on the amount being unlocked. This makes it a directly reachable, unprivileged action.

### Recommendation
Verify (in the Clarity `pox-5.clar` `unstake` function and its interaction with `pox-locking/src/pox_5.rs::handle_unstake_pox_v5`) that early-unstaking synchronously and atomically removes the staker's contribution from every future/current reward-cycle's committed totals and signer-weight calculations it was counted toward — mirroring the block-processor-only `handle-unlock` cleanup performed in pox-2/3/4 (`stackslib/src/chainstate/stacks/boot/pox-2.clar:362-373`) — rather than leaving those totals stale once the backing STX has been unlocked.

### Proof of Concept
1. Staker locks `amount_ustx` via pox-5 `stake` for a future reward cycle, and the amount is added to that cycle's aggregate reward-set/signer-weight totals.
2. Signers observe the (now-increased) aggregate weight for that reward cycle and configure their commitments/thresholds accordingly.
3. Staker calls `unstake`; `handle_unstake_pox_v5` (pox-locking/src/pox_5.rs:501-529) moves `unlock_height` forward immediately while keeping `locked_amount` in the STX event unchanged, per the unit test at lines 1893-1915.
4. If the corresponding reward-cycle/signer-weight state in `pox-5.clar` is not decremented in the same transaction, the staker has withdrawn locked STX that reward-set totals/signer weight still count — breaking the equality between committed stake and actually-locked STX for that cycle.

**Note:** I was unable to view the actual `unstake` public function body inside `pox-5.clar` (the `grep_search` located the definitions but the tool budget was exhausted before I could read the Clarity source directly to confirm whether it does or does not perform the reward-set cleanup). This finding should be validated by reading `stackslib/src/chainstate/stacks/boot/pox-5.clar`'s `unstake` function definition directly — a Devin session with full file access would be needed to confirm whether the reward-cycle bookkeeping is actually reconciled or left stale.

```rust
/// Handle the response from `unstake` in pox-5 — reschedules the
/// already-locked STX to unlock at the start of the next reward cycle.
fn handle_unstake_pox_v5(
    global_context: &mut GlobalContext,
    function_name: &str,
    value: &Value,
) -> Result<Option<StacksTransactionEvent>, VmExecutionError> {
    debug!(
        "Handle special-case contract-call to {:?} {function_name} (which returned {value:?})",
        boot_code_id(POX_5_NAME, global_context.mainnet),
    );

    runtime_cost(
        ClarityCostFunction::StxTransfer,
        &mut global_context.cost_track,
        1,
    )?;

    let parsed = parse_pox_stake_result(value).map_err(|e| {
        locking_error_to_vm_error(e, &format!("pox-5 {function_name}: bad response"))
    })?;
    let (staker, locked_amount, unlock_height) = match parsed {
        ParsedStakeResult::Ok {
            staker,
            amount_ustx,
            unlock_burn_height,
        } => (staker, amount_ustx, unlock_burn_height),
        ParsedStakeResult::ContractErr => return Ok(None),
    };
```

```text
;; This method is called by the Stacks block processor directly in order to handle the contract state mutations
;;  associated with an early unlock. This can only be invoked by the block processor: it is private, and no methods
;;  from this contract invoke it.
(define-private (handle-unlock (user principal) (amount-locked uint) (cycle-to-unlock uint))
    (let ((user-stacking-state (unwrap-panic (map-get? stacking-state { stacker: user })))
          (first-cycle-locked (get first-reward-cycle user-stacking-state))
          (reward-set-indexes (get reward-set-indexes user-stacking-state)))
        ;; iterate over each reward set the user is a member of, and remove them from the sets. only apply to reward sets after cycle-to-unlock.
        (try! (fold fold-unlock-reward-cycle reward-set-indexes (ok { cycle: first-cycle-locked, first-unlocked-cycle: cycle-to-unlock, stacker: user })))
        ;; Now that we've cleaned up all the reward set entries for the user, delete the user's stacking-state
        (map-delete stacking-state { stacker: user })
        (ok true)))
```
