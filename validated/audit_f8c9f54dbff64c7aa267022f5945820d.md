## Finding: `CCMenuController` bypasses per-stack ApiClient scoping, letting a stack-scoped token read any stack's build state

### Title
Stack-scoped `ApiClient` tokens can read CCMenu status for every stack, not just the authorized one — (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Shipit lets an `ApiClient` be bound to a single `Stack` (`belongs_to :stack, optional: true`) so that a token minted for one stack cannot see or act on others. [1](#0-0)  This scope is enforced centrally in `Shipit::Api::BaseController#stacks`, which restricts the `Stack` relation to `current_api_client.stack_id` whenever the client is scoped. [2](#0-1)  `Shipit::Api::StacksController` correctly resolves its target stack through this scoped relation (`stacks.from_param!`). [3](#0-2) 

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that looks the stack up directly from the global `Stack` model instead of the scoped `stacks` relation: [4](#0-3) 

`require_permission :read, :stack` only checks that the token's `permissions` array contains the string `read:stack`; `ApiClient#check_permissions!` never compares the requested stack against `current_api_client.stack_id`. [5](#0-4)  The stack-identity check exists only inside the `stacks` scoping helper, which `CCMenuController` never calls.

### Finding Description
This is the same bug class as the report: a security-relevant piece of state (which stack a token is allowed to touch) is checked/updated in one code path (`BaseController#stacks`) but a sibling code path (`CCMenuController#stack`) acts on the resource while skipping that check — the equality that should hold, `token.authorized_stack == stack_acted_on`, is broken.

Concretely:
- `BaseController#authenticate_api_client` accepts any valid, unexpired `ApiClient` token via `ApiClient.authenticate`. [6](#0-5) 
- `CCMenuController` only requires `read:stack` permission (`require_permission :read, :stack`), which every scoped or unscoped client can trivially have. [7](#0-6) 
- The actual stack object served by `#show` comes from `Stack.from_param!(params[:stack_id])` — the full, unscoped table — not `stacks.from_param!`, so `params[:stack_id]` can name a completely different stack than the one the token is bound to. [8](#0-7) 

The engine's own test suite documents the intended invariant elsewhere ("an api client scoped to a stack will only see that one stack"), [9](#0-8)  confirming this is a deliberate authorization boundary that `CCMenuController` fails to respect.

### Impact Explanation
An attacker who holds a legitimately-issued, single-stack-scoped `ApiClient` token (the low-privilege credential this feature exists to create) can enumerate/query `GET /:stack_id/ccmenu.xml?token=...` for any `stack_id` in the installation and read that stack's build/deploy state (`lastBuildStatus`, `lastBuildLabel`, activity, lock state, etc.) — data the token was never authorized to see. This is an authorization-scope escalation: escalating a stack-scoped credential into a read of arbitrary stacks' deploy/task state, matching the in-scope "High" impact category (unauthenticated/unauthorized read of stack state).

### Likelihood Explanation
Any holder of a valid, stack-scoped `ApiClient` token (a routine, low-privilege credential explicitly supported by the engine) can exploit this with a single unauthenticated-scope HTTP GET by simply changing the `stack_id` path/query parameter — no additional privileges, races, or timing are required.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` relation (i.e. `stacks.from_param!(params[:stack_id])`, inherited from `BaseController`) instead of querying `Stack` directly, so stack-scoped tokens can only reach the stack they were issued for.

### Proof of Concept
1. Admin creates an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (standard supported configuration, as tested in `test/controllers/api/stacks_controller_test.rb:217`).
2. Attacker (holder of that token) sends: `GET /A/ccmenu.xml?token=<token>` — succeeds as expected.
3. Attacker sends: `GET /B/ccmenu.xml?token=<token>` where `B` is a different, unauthorized stack.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` rather than `stacks.from_param!`, the request succeeds and returns stack `B`'s build status/lock state, even though the token's `stack_id` is `A`.
