### Title
Prototype Pollution via `__proto__` Data-Feed Name in `readJointDirectly()` Causes Unit Hash Verification Failure / Node Crash - (File: storage.js)

### Summary
`ocore` validates `data_feed` message payloads only for length and absence of `\n` in the feed name, never blocking dangerous keys such as `__proto__`, `constructor`, or `prototype` [1](#0-0) . When such a unit is later reconstructed from SQL storage in `storage.js`'s `readJointDirectly()`, the `data_feed` case rebuilds the payload object using plain bracket-notation assignment (`objMessage.payload[df_row.feed_name] = ...`), which — unlike `JSON.parse` — invokes the `__proto__` setter instead of creating an own property [2](#0-1) . This is the exact bug class described in the Locutus advisory: a deserializer builds a plain object and assigns attacker-controlled keys via bracket notation without filtering `__proto__`.

### Finding Description
`aa_validation.js` and `validation.js` both accept a `data_feed` feed name of `"__proto__"` as long as it is ≤64 chars and contains no newline — there is no denylist for prototype-polluting keys [3](#0-2) [4](#0-3) . A unit containing `{"app":"data_feed","payload":{"__proto__": "x"}}` therefore passes validation and is persisted to the `data_feeds` SQL table with `feed_name='__proto__'`.

The codebase is otherwise clearly aware of `__proto__` hazards: `formula/common.js`'s `assignField()` uses `Object.defineProperty` specifically to avoid the setter [5](#0-4) , and `string_utils.js`'s `cloneDeep()` special-cases `__proto__` for the same reason [6](#0-5) . Tests even explicitly assert that a JSON-parsed `__proto__` key stays a literal own property and doesn't pollute the object's real prototype [7](#0-6) .

However, `readJointDirectly()`'s `data_feed` branch was missed: it rebuilds the payload object with unmitigated bracket assignment from SQL rows, so `feed_name === '__proto__'` replaces `objMessage.payload`'s prototype instead of creating the literal key that existed in the originally validated/hashed unit [8](#0-7) .

### Impact Explanation
Because the unit's canonical JSON form (as authored and originally hashed via `JSON.parse`, which does create an own `__proto__` property rather than invoke the setter) differs from the SQL-reconstructed object (which loses `__proto__` as an own key due to the setter being triggered), `isCorrectHash()` will fail for this reconstructed joint [9](#0-8) . On failure, `readJointDirectly` retries once and then executes an unguarded `throw Error("unit hash verification failed...")` inside an async callback [10](#0-9) , which is uncaught and crashes the node process reading that unit. Any code path that reconstructs a joint from SQL (bypassing the cached KV/joints JSON) for a unit containing such a `data_feed` message becomes permanently unreadable and fatal to the reading node, i.e. the network becomes unable to confirm/serve that unit — a concrete availability/consensus-disagreement impact.

### Likelihood Explanation
Any unprivileged unit poster can attach a `data_feed` message with a `__proto__` key; this passes all current validation checks (length ≤64, no `\n`) in both plain-unit and AA-payload validators. Exploitation only requires the network to eventually reconstruct that joint via the SQL path rather than the cached JSON path (e.g., when `conf.bSaveJointJson` is false, when the joints-JSON cache row for the unit is absent, or upon `readJointDirectly` re-derivation) — a state that will legitimately occur in normal node operation over time.

### Recommendation
Harden `readJointDirectly()`'s `data_feed` reconstruction in `storage.js` to avoid the `__proto__`/`constructor`/`prototype` setter trap, e.g. by using `Object.defineProperty` (mirroring `assignField()` in `formula/common.js`) or by building the payload with `Object.create(null)`. Additionally, add an explicit denylist for `__proto__`, `constructor`, and `prototype` feed names in `validation.js` and `aa_validation.js`'s `data_feed` validation so such units are rejected outright rather than merely mitigated downstream.

### Proof of Concept
1. Post a unit with a message `{"app":"data_feed","payload":{"__proto__":"x"}}`. It passes `validateInlinePayload`'s `data_feed` checks (only length/`\n` checked) [4](#0-3) , gets written to the `data_feeds` table with `feed_name='__proto__'`.
2. Trigger a reconstruction of this joint via the SQL path (`readJoint(conn, unit, callbacks, true)` / cache-miss scenario), hitting the `data_feed` case in `readJointDirectly` [2](#0-1) .
3. `objMessage.payload['__proto__'] = value` replaces the prototype of `objMessage.payload` instead of creating the own key that existed at authoring time.
4. `isCorrectHash(objUnit, unit)` returns `false` because the reconstructed unit JSON no longer contains the original `__proto__` own property; after one retry, `readJointDirectly` throws an uncaught `Error("unit hash verification failed...")`, crashing/blocking the node's ability to serve or confirm that unit [10](#0-9) .
