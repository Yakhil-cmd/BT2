### Title
`StatusHandler#process` updates commit status by SHA alone, with no repository/stack scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` looks up commits via `Commit.where(sha: params.sha)` and calls `create_status_from_github!` on every match, without filtering by the webhook's `repository.full_name`. Because SHAs are plain strings with no repository-scoped uniqueness constraint, a webhook from one repository can mutate the commit status of a `Commit` row that belongs to a completely different stack/repository.

### Finding Description
The binding that should hold for every commit mutated by this handler is:
`payload.dig('repository', 'full_name') == commit.stack.repository.full_name`

This does not hold. `StatusHandler#process` is: [1](#0-0) 

It queries `Commit.where(sha: params.sha)` globally across the entire `commits` table — no `.joins(:stack)`, no `stacks.find_by!`, no use of the base class's `stacks`/`repository_name` helpers at all. Compare this to the base `Handler` class, which provides exactly the scoping mechanism this handler ignores: [2](#0-1) 

and to `PullRequest::ClosedHandler`, which correctly scopes lookups through `Repository.from_github_repo_name(params.repository.full_name)`: [3](#0-2) 

`create_status_from_github!` directly mutates commit state and fires hooks/continuous-delivery scheduling for whichever stack the matched commit belongs to: [4](#0-3) [5](#0-4) 

The `Commit.sha` column has no cross-table uniqueness/repository-binding validation visible in `app/models/shipit/commit.rb`; two stacks (for two different `Repository` rows) can each have a `Commit` row with the identical `sha` string — either through legitimately sharing a common ancestor commit, or trivially, an attacker simply pushing/forcing a commit whose SHA collides with an already-known SHA belonging to another tracked repository (the attacker fully controls the content of their own repo's commits, and the `sha` field itself is not validated against the actual repository).

Exploit flow:
1. Attacker owns/controls Repository A, which is registered as a Shipit stack.
2. Repository B (unrelated, victim's) is also a Shipit stack and has a `Commit` row with `sha = X` (e.g., a shared base commit, or coincidentally identical hash).
3. Attacker's Repository A also has (or is made to have, since they push whatever commits they like into their own repo) a commit with `sha = X`.
4. Attacker's GitHub sends (or attacker manually POSTs, matching signature since it's a legitimate webhook from their own repo A with a valid secret for that org) a `status` webhook event with `sha: X`, `state: "success"` (or `"failure"`), naming `repository.full_name` = A.
5. `verify_signature` passes — the webhook is legitimately signed for org/repo A, which the attacker fully controls.
6. `StatusHandler#process` runs `Commit.where(sha: X)`, which returns **both** stack A's commit and stack B's commit.
7. `create_status_from_github!` is invoked on both, changing Stack B's commit status/state despite the incoming webhook's `repository.full_name` naming only A.

Existing guards do not prevent this: `verify_signature` only proves the webhook genuinely originates from the org/repo the attacker controls (A) — it says nothing about which `Commit` rows the handler is allowed to touch. `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape, not repository scoping. There is no `require_permission!`/`stacks` filter anywhere in `StatusHandler`.

### Impact Explanation
A payload authenticated for repository A can mutate a `Commit#status` belonging to stack/repository B. `Commit#status` drives `deployable?`, `blocked?`, continuous-delivery scheduling (`schedule_continuous_delivery` → `ContinuousDeliveryJob`), and `Hook.emit(:deployable_status, ...)`. Forcing a victim stack's commit into a false "success" state can unblock/trigger an unauthorized deploy via continuous delivery, or force a false "failure" that blocks legitimate deploys — this is a cross-repository state-corruption impact matching the Critical category ("a payload for one repository mutating another's stack, commit ... task"). This is repeatable against any repository pair that shares (or is made to share) a SHA, and blast radius spans the whole multi-tenant Shipit instance since any onboarded repository can be used as the attack vector.

### Likelihood Explanation
The attacker only needs a repository already registered with the target Shipit instance (any unprivileged GitHub user who owns a repo that has been onboarded as a stack, or who can get a webhook fired from any onboarded repo) and knowledge of a target commit SHA in another stack (visible in Shipit's own UI/API for public/shared stacks, or via a shared base/fork commit which is common). No secrets, sessions, or elevated GitHub roles are required — the webhook signature check only validates against the attacker's own repo/org secret. This is straightforward and repeatable.

### Recommendation
Scope the lookup by the webhook's own repository, mirroring other handlers:
```ruby
def process
  stacks.joins(:commits).merge(Commit.where(sha: params.sha)).find_each do |stack|
    ...
  end
end
```
or more directly:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the base class's `stacks` (derived from `repository_name`/`payload.dig('repository','full_name')`) so only commits under stacks for the reporting repository are mutated.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create `stack_a` for `Repository` "attacker/repo", and `stack_b` for `Repository` "victim/repo".
2. Create `commit_a = stack_a.commits.create!(sha: "deadbeef" * 5, ...)` and `commit_b = stack_b.commits.create!(sha: "deadbeef" * 5, ...)` (identical `sha`, different stacks).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha = "deadbeef"*5`, `state = "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly.
5. Assert `commit_a.reload.statuses.any?` is true (expected/legit).
6. Assert `commit_b.reload.statuses.any?` is **also** true, and `commit_b.stack_id == stack_b.id` (asserting cross-stack mutation occurred) — even though the payload's `repository.full_name` ("attacker/repo") never equals `commit_b.stack.repository.full_name` ("victim/repo"), violating the required binding.
