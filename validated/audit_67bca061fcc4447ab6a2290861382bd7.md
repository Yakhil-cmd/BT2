### Title
Webhook signature is verified against `repository.owner.login`, but the acted-upon repository is taken from `repository.full_name`, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App secret to validate the inbound HMAC against using `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. However, every event handler (`PushHandler`, `StatusHandler`, `Handler#stacks`, etc.) determines which repository/stack to act on using a *different* field from that same body: `repository.full_name`. Because the signature only proves "this payload was signed with organization X's webhook secret", not "this payload's `repository.full_name` belongs to organization X", an attacker who owns a GitHub App installed on their own organization can forge a webhook whose `owner.login` matches their own org (so the signature check passes with their own secret) while `repository.full_name` names a victim repository/stack.

### Finding Description
The binding that should hold is: **organization that authenticated == repository that is written**. In this codebase it does not.

1. `verify_signature` extracts the organization for secret selection purely from the payload: [1](#0-0) [2](#0-1) 

2. The HMAC check itself only proves the payload bytes were signed by whichever org's secret was selected in step 1 — it says nothing about the content of `repository.full_name`: [3](#0-2) 

3. Every handler resolves the target `Stack`/`Repository`/`Commit` from `repository.full_name`, a completely separate field of the same untrusted body: [4](#0-3) [5](#0-4) 

4. `PushHandler` and `StatusHandler` then perform state-changing operations on whatever stack/commit that (attacker-chosen) `full_name`/`sha` resolves to: [6](#0-5) [7](#0-6) 

**Root cause equality broken:** `verify_signature` binds trust to `params.dig('repository','owner','login')`, while `Handler#repository_name`/`#stacks` binds action to `payload.dig('repository','full_name')`. These two fields are never checked against each other, and both come from the same unauthenticated request body received before any cryptographic check is applied. An attacker who legitimately owns any GitHub organization/App integrated with this Shipit instance (i.e. knows their own `webhook_secret`) can set `repository.owner.login` to their own org login and `repository.full_name` to `victim-org/victim-repo`. `Shipit.github(organization: 'attacker-org')` returns the attacker's own app config, `verify_webhook_signature` succeeds because it's validated against the attacker's own known secret, and the event is then dispatched using the victim's `full_name`, letting the handler mutate victim stacks (`sync_github`, commit statuses, team membership, etc.).

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. Concretely reachable actions with a forged, cross-org payload include:
- Forcing `Stack#sync_github` on an arbitrary victim stack via a forged `push` event (`PushHandler`), which can trigger deploy-affecting github sync operations on a repository the attacker does not control.
- Injecting arbitrary commit statuses on a victim's commits (`StatusHandler` → `Commit#create_status_from_github!`), which can be used to satisfy/bypass CI gating (`ci.require`) that Shipit consults before allowing deploys — an unauthorized-deploy enabler.
- Creating/deleting `Team`/`Membership` records for arbitrary organizations via `MembershipHandler`, potentially escalating into `Shipit.github_teams` authorization checks used by `Authentication#force_github_authentication`.

This satisfies the High-impact category ("escalation into `Shipit.github_teams` authorization") and materially assists the Critical category ("unauthorized deploy") by forging CI status on victim commits.

### Likelihood Explanation
Requires only that the attacker control (or be able to install) a GitHub App/organization already configured in this Shipit instance's `Shipit.github` multi-org config (a normal, low-privilege scenario for any multi-tenant Shipit deployment serving several orgs, as documented in `docs/setup.md`'s "Using Multiple Github Applications" section). No `ApiClient` token, `webhook_secret` of the victim, GitHub App private key, or repository write access to the victim repo is needed — only the attacker's own already-known webhook secret for their own org's app. The endpoint is public (`WebhooksController` has no session/authentication requirement beyond the signature check itself).

### Recommendation
After a signature is verified against organization X, validate that `repository.full_name` (and `organization.login`, if present) actually belongs to organization X before dispatching to handlers — e.g., compare `repository_owner` to the owner segment of `repository.full_name` and reject on mismatch, or resolve the target `Repository`/`Stack` and assert its `owner` equals the verified organization before calling any handler.

### Proof of Concept
1. Attacker owns/administers `attacker-org`, which has a configured GitHub App entry (`webhook_secret: S_attacker`) in this Shipit instance's `Shipit.github` config, alongside `victim-org` (also configured, unrelated secret).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(S_attacker, body)` (known secret) and sends `POST /github/webhooks` (or the mounted webhook path) with `X-Github-Event: push`.
4. `WebhooksController#repository_owner` returns `"attacker-org"`; `Shipit.github(organization: "attacker-org")` returns the attacker's own app config; `verify_webhook_signature` succeeds because the signature matches `S_attacker`.
5. `PushHandler.call(params)` runs `Handler#repository_name` → `"victim-org/victim-repo"`, resolves the actual victim `Stack`, and calls `stack.sync_github(expected_head_sha: ...)` — a state-changing operation on a repository/org the attacker never proved control over.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
