### Title
Webhook signature is validated against the payload's `repository.owner.login`/`organization.login`, but event handlers act on the unrelated `repository.full_name`/global `sha`, letting a holder of any one org's `webhook_secret` forge status/push events for any other org's stacks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, computed from the attacker-supplied JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw JSON body is dispatched unchanged to the registered handlers, which pick which `Stack`/`Repository`/`Commit` to mutate from *other, independent* fields of the same attacker-supplied body (`repository.full_name`, or in the status handler's case, a completely global `sha` lookup with no repository scoping at all). [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

### Finding Description
This is a Shipit-engine analog of the reported bug class: a value the code treats as authoritative/verified (`repository.owner.login`, used to pick the `webhook_secret` for HMAC verification) is never actually bound to the value the code uses to decide what state to mutate (`repository.full_name` for push/pull_request handlers, or bare `sha` for status events). The equality the code implicitly assumes but never enforces is:

`organization used to select the verifying webhook_secret == organization that owns the repository/commit being mutated`

Because Shipit is designed to be multi-tenant (`config/secrets.*.yml` shows multiple orgs, each with its own `webhook_secret`/GitHub App), any principal who legitimately controls the webhook secret for *one* configured organization (e.g., they administer their own small GitHub org that has been onboarded to this Shipit instance) can compute a valid `X-Hub-Signature` for a `POST /webhooks` body of their own choosing, since the signature only covers the raw bytes, not any claim tying the signed org to the repository fields inside it. They can then set:
- `repository.owner.login` (or `organization.login`) = the org they control (so `verify_signature` picks that org's secret and passes) 
- `repository.full_name` = a victim organization's repository that has stacks configured on the same Shipit instance

The `PushHandler` and PR handlers resolve the target `Stack`/`Repository` purely via `Repository.from_github_repo_name(repository_name)`, using `repository.full_name`, with no re-check that this repository belongs to the org whose secret validated the request: [4](#0-3) [7](#0-6) 

`StatusHandler` is worse: it does not scope by repository at all. It looks up `Commit.where(sha: params.sha)` across the *entire* database and calls `create_status_from_github!` on every match: [6](#0-5) 

This means a forged, validly-signed (for the attacker's own org) `status` event naming any commit SHA that happens to exist in *any* stack tracked by the Shipit instance will inject a fabricated commit status (e.g., `state: "success"`) for that commit, regardless of which repository/org the commit actually belongs to.

Additionally, when an organization has no `webhook_secret` configured at all (a documented, supported, "optional" configuration, as shown in `docs/setup.md` and `config/secrets.development.shopify.yml`), `verify_webhook_signature` trivially returns `true`: [8](#0-7) 
which means an unauthenticated internet attacker who merely knows the login of any such unprotected org configured on the instance can skip forging a signature entirely and still reach the same unscoped handlers.

### Impact Explanation
Commit statuses drive Shipit's CI-gating logic for deploys and the merge queue (`DeploySpec#required_statuses`, `MergeRequest::StatusChecker`). By injecting a forged `success` status for a victim's commit SHA via a signature verified only against an unrelated org's secret, an attacker can:
- Mark a victim repository's blocking/required CI check as passing, unblocking automated/continuous deployment or merge-queue merges that should have been gated on real CI results — an **unauthorized deploy/merge**, matching the report's "Critical" impact bucket (unauthorized deploy or merge).
- Trigger `sync_github`/PR provisioning flows against a victim org's `Stack`/`Repository` records via the push and pull_request handlers, causing **cross-repository writes** on state the attacker has no GitHub permissions over.

This mirrors the underlying Celo report's bug class: a binding the system implicitly relies on for security (which entity is authenticated) is decoupled from the binding actually used to act (which resource is mutated), letting one authorized identity's credentials reach resources belonging to another.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization (explicitly documented/supported multi-tenant configuration) and that the attacker legitimately controls the webhook secret/app for at least one of those orgs, or that any one configured org has no `webhook_secret` set (also an explicitly supported/documented configuration). No GitHub write access to the victim repository, no Shipit session, and no `ApiClient` token is required — only network access to `POST /webhooks` and knowledge of one org's own webhook secret (which the attacker themselves configured) or the existence of an unsecured org. This is a realistic configuration for any Shipit deployment onboarding multiple orgs/teams, which the docs actively encourage.

### Recommendation
- In `Shipit::WebhooksController`, after verifying the signature for `repository_owner`, re-derive `repository.full_name`'s owner and require it to match `repository_owner` (or the org actually associated with the resolved `Stack`/`Repository`) before dispatching to handlers.
- In `Shipit::Webhooks::Handlers::StatusHandler`, scope the `Commit` lookup by the repository identified in the payload (via `stacks`/`Repository.from_github_repo_name`) instead of a bare, instance-wide `Commit.where(sha: ...)`.
- Consider making `webhook_secret` mandatory (reject requests, rather than accept them, when unset) for any organization with configured stacks, closing the "no secret configured" bypass path.

### Proof of Concept
1. Shipit instance is configured with two GitHub orgs in `Shipit.github` config: `attacker-org` (attacker administers this org's GitHub App, so knows its `webhook_secret`) and `victim-org` (has a stack with `continuous_deployment: true` and a required CI status context `ci/tests`).
2. Attacker crafts a `status` webhook JSON body:
   ```json
   {
     "sha": "<victim commit sha, known from public GitHub history>",
     "state": "success",
     "context": "ci/tests",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(attacker-org_webhook_secret, body)` themselves (no GitHub relay needed) and sends `POST /webhooks` with header `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches that org's `GitHubApp`, and the HMAC check passes because the attacker used the correct secret for that org. [9](#0-8) 
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which finds the victim's `Commit` purely by `sha` (no ownership check) and calls `create_status_from_github!`, injecting a fabricated "success" status. [6](#0-5) 
6. If `victim-org`'s stack has `continuous_deployment` enabled and this was the last missing required status, the next `ContinuousDeliveryJob` tick deploys the victim's commit without any legitimate CI signal ever being produced by GitHub — an unauthorized deploy caused entirely by an attacker who only controlled a different organization's webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
