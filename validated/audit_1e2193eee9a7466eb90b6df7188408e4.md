### Title
Webhook signature verified against an attacker-chosen organization, but events are processed for a repository/commit read from the same unverified payload - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App configuration (and therefore which `webhook_secret`) to validate the `X-Hub-Signature` against based on a field taken from the still-unverified JSON body. The event handlers that subsequently act on that same body identify the target repository/commit using a *different* field of the same unverified body (or, in the `status` handler, no repository field at all). Nothing cross-checks that the "authenticating organization" and the "repository/commit being written to" are the same entity.

### Finding Description
`verify_signature` derives the signing organization purely from the request body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up that organization's own App config/`webhook_secret` and `GithubApp#verify_webhook_signature` is used to validate the raw signature against it: [3](#0-2) 

Once verification passes, `create` dispatches the very same untrusted `params` hash to the registered handlers: [4](#0-3) 

The base `Handler` class (used by push/pull_request handlers) determines the target repository from `payload.dig('repository', 'full_name')` — a field completely independent of `repository.owner.login`/`organization.login` used for signature verification; nothing enforces that `full_name`'s owner matches `owner.login`: [5](#0-4) 

Worse, `StatusHandler` doesn't even scope to a repository — it looks up commits globally by SHA across every stack/repository configured in the Shipit instance and writes a forged CI status to them: [6](#0-5) 

Shipit explicitly supports (and documents) a multi-organization GitHub App configuration where each org has its own independent `webhook_secret`, and documents the webhook secret itself as *optional*: [7](#0-6) [8](#0-7) 

And `verify_webhook_signature` unconditionally returns `true` when no secret is configured for the resolved organization: [9](#0-8) 

Putting this together: if a Shipit instance is configured for multiple GitHub organizations (a supported, documented setup) and at least one of them has no/blank/weaker `webhook_secret`, an attacker who knows that org's name (and secret, if any) can:
1. Set `repository.owner.login` (or `organization.login`) in the JSON body to the weak/known org so `verify_signature` authenticates against that org's secret.
2. Set the actually-processed identifying fields — `repository.full_name` for push/pull_request handlers, or simply `sha` for `status` (which does no repository check whatsoever) — to target a repository/commit belonging to a completely different, strongly-secured organization tracked by the same Shipit instance.

The equality this breaks: **organization that authenticated == repository/commit that is written**. The controller checks the former; the handlers write to the latter; they are read from two independent, both attacker-controlled fields of the same unsigned-until-verified JSON, with no cross-validation.

### Impact Explanation
The strongest exploitation path is the `status` webhook: `StatusHandler` performs `Commit.where(sha: params.sha)` with zero organization/repository binding, so a successfully "signed" (via the weak org) forged `status` event can mark *any* tracked commit, in *any* stack of *any* configured organization, as `state: "success"`. Shipit's continuous delivery / merge-queue gating relies on such commit statuses (CI checks) to allow deploys/merges to proceed. Forging a green CI status on a malicious commit in a strictly-configured, high-value repository can result in an unauthorized deploy or merge of attacker-controlled code — matching the Critical "unauthorized deploy, rollback or merge" impact criterion. Push/pull_request handlers offer a related but weaker cross-repo confusion vector (repository sync/review-stack creation for a repo whose owner doesn't match the authenticating org).

### Likelihood Explanation
Requires the host application to configure Shipit with more than one GitHub organization (an explicitly documented, supported configuration) where at least one organization has a blank/weak/known `webhook_secret`. Given `webhook_secret` is documented as optional and typical multi-tenant Shipit deployments (multiple orgs sharing one instance) are a real, encouraged use case, this is a realistic configuration to encounter, but it is conditional on that specific setup rather than universal to every Shipit deployment.

### Recommendation
- After signature verification, re-derive and enforce that the organization used to verify the signature matches the organization embedded in the fields the handlers actually act on (e.g., require `repository.full_name`'s owner == verified `repository_owner`).
- Have `StatusHandler` (and any other handler) scope lookups by repository/organization, not merely by SHA, e.g. join through `Repository`/`Stack` derived from a verified organization rather than an unscoped `Commit.where(sha:)`.
- Consider disallowing/requiring `webhook_secret` for all configured organizations when multi-org config is used, since a blank secret on any single org undermines verification guarantees for the whole shared instance.

### Proof of Concept
1. Configure Shipit for two GitHub orgs: `weak-org` (webhook_secret blank/known) and `victim-org` (strict, unknown secret), each with repos/stacks tracked by the same Shipit instance.
2. Attacker sends:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<hmac-with-weak-org-secret-or-anything-if-blank>
{
  "organization": {"login": "weak-org"},
  "sha": "<victim-org commit sha under continuous deployment>",
  "state": "success",
  "context": "ci/build",
  "description": "forged",
  "target_url": "https://example.com"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "weak-org")` and passes verification (blank/known secret).
4. `StatusHandler#process` executes `Commit.where(sha: params.sha)` with no organization check, creating a fabricated successful CI status on the victim-org commit, which can enable Shipit's continuous-deployment to proceed to deploy that commit.

    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
