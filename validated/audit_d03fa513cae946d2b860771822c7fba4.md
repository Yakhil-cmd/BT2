### Title
CCMenuController bypasses stack-scoped ApiClient authorization, allowing cross-tenant CCTray XML disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stacks` scopes stack lookups to `current_api_client.stack_id` when the client is stack-restricted, but `Shipit::Api::CCMenuController#stack` overrides this by calling `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model. `require_permission!(:read, :stack)` only checks the string permission `read:stack` in `ApiClient#check_permissions!`; it never checks whether the requested stack matches the token's `stack_id`. As a result, any token scoped to `read:stack` for stack A can read the CCTray XML of any other stack B by simply changing `params[:stack_id]` in the request.

### Finding Description
The intended binding is: `requested_stack ∈ Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true — i.e., a stack-scoped token should only ever resolve stacks belonging to its own `stack_id`.

Code path:
- `Shipit::Api::BaseController#stacks` (app/controllers/shipit/api/base_controller.rb:74-76) implements the correct scoping: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`.
- `Shipit::Api::BaseController#stack` (app/controllers/shipit/api/base_controller.rb:78-80) is the generic, correctly-scoped resolver: `stacks.from_param!(params[:stack_id])`.
- `Shipit::Api::CCMenuController#stack` (app/controllers/shipit/api/ccmenu_controller.rb:29-31) **overrides** this method with `Stack.from_param!(params[:stack_id])`, calling the unscoped `Stack` model class method directly instead of the scoped `stacks` helper.
- `Shipit::Api::CCMenuController` declares `require_permission :read, :stack` (ccmenu_controller.rb:6), which only invokes `ApiClient#check_permissions!` (app/models/shipit/api_client.rb:38-45). That method merely checks `permissions.include?("read:stack")` — a boolean flag unrelated to which specific stack the client is bound to.
- `authenticate_api_client` in `CCMenuController` (ccmenu_controller.rb:33-36) authenticates via `ApiClient.authenticate(params[:token])`, which sets `@current_api_client` to the token owner, whose `stack_id` legitimately points to the attacker's own stack.

Exploit flow: an attacker who legitimately holds a `read:stack` token scoped to their own stack A (e.g., obtained from the stack settings page they administer) sends `GET /api/stacks/:victim_stack/cc_menu.xml?token=<token>`. `authenticate_api_client` succeeds and binds `@current_api_client.stack_id = A`. `require_permission!(:read, :stack)` passes because the token has the `read:stack` permission string, irrespective of scope. `#stack` then resolves `victim_stack` via unscoped `Stack.from_param!`, completely ignoring `current_api_client.stack_id`. The controller renders the victim stack's CCTray XML (deploy status, build state, lock state) to the attacker.

This is directly demonstrated by the existing test suite: in `test/controllers/api/ccmenu_controller_test.rb`, `setup` authenticates `@client` scoped to `shipit_stacks(:shipit)`, yet the test `"stacks with no deploys render correctly"` (lines 47-51) creates an entirely unrelated `Stack` (`Repository.new(owner: "foo", name: "bar")`) never bound to `@client.stack_id`, and asserts `assert_response :ok` with correct payload — proving the divergence exists and is currently accepted as expected behavior rather than caught as a violation. `check_permissions!`, `require_permission!`, and `authenticate_api_client` all execute without objection because none of them re-validate `stack.id == current_api_client.stack_id`.

### Impact Explanation
Any repository/stack owner who can legitimately mint a `read:stack`-scoped CCMenu token for their own stack can use that same token to read CCTray XML (project name, last build status/label/time, web URL, lock status) for **any other stack on the same Shipit instance**, including stacks belonging to unrelated repositories/organizations they have no access to. This is a cross-tenant unauthorized read of stack/deploy state — matching the "High: unauthenticated/unauthorized read of stack state, task streams or deploy output" impact category. It is fully repeatable against arbitrary victim stacks by varying `params[:stack_id]`, requiring only one request per victim stack and no interaction with the victim.

### Likelihood Explanation
Preconditions are minimal and within the stated attacker capability: the attacker only needs a legitimately-issued `read:stack` API token scoped to a stack they administer (a normal, expected credential any repo admin can generate via Shipit's UI/API), and knowledge/guessability of the victim's `stack_id` (repo owner/name/branch), which is often discoverable (e.g., via public repo names). No secrets, no privileged role, and no GitHub-side action are required — only an HTTP GET request with a query-string token, which the controller explicitly supports (`authenticate_api_client` calls `ApiClient.authenticate(params[:token])` directly, and there's a dedicated test "can authenticate with query string token"). This makes the attack cheap, deterministic, and repeatable against any number of victim stacks.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to use the scoped `stacks` helper from `BaseController` instead of calling `Stack.from_param!` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
This ensures `current_api_client.stack_id` scoping (already implemented in `BaseController#stacks`) is enforced for CCMenu requests just as it is for the rest of the API, so `Stack.where(id: current_api_client.stack_id).from_param!(...)` will raise `RecordNotFound`/404 for any stack outside the token's scope.

### Proof of Concept
Minitest plan (extends `test/controllers/api/ccmenu_controller_test.rb`):
```ruby
test "a stack-scoped token cannot read another stack's cc_menu xml" do
  # @client authenticated in setup is scoped to @stack (shipit_stacks(:shipit))
  assert_equal @stack.id, @client.stack_id
  victim_stack = Stack.create!(repository: Repository.new(owner: "victim-org", name: "victim-repo"), branch: 'main')

  # Explicit binding check BEFORE tracing: victim_stack must NOT be in the client's authorized scope
  assert_not_includes Stack.where(id: @client.stack_id), victim_stack

  get :show, params: { stack_id: victim_stack.to_param, token: @client.authentication_token }

  # Correct behavior should reject; current behavior renders 200 with victim data
  assert_response :not_found  # currently fails: actual response is :ok, proving the leak
end
```
Running this against the current code shows `response.status == 200` with the victim stack's CCTray XML returned, despite `victim_stack` being provably excluded from `Stack.where(id: @client.stack_id)` — confirming the broken binding.
