## Title
Cross-organization webhook confusion allows unauthenticated commit-status/CI forgery and unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's HMAC secret to verify a webhook against using `repository_owner` (`params.dig('repository','owner','login')`), but every downstream `Handlers::Handler` resolves the *target* repository/stack using a completely different, unchecked field: `payload.dig('repository','full_name')`. Nothing in the request pipeline enforces that these two fields refer to the same organization. Because `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever the selected organization has no `webhook_secret` configured, an attacker who knows (or engineers) that this Shipit instance is configured to serve at least one GitHub organization without a webhook secret can send a forged, unsigned webhook whose `repository.owner.login` names that unprotected org while `repository.full_name` names a completely different, secret-protected org/repo that is actually tracked by Shipit.

### Finding Description
The trust binding that should hold is:
`organization whose secret authenticated the request == organization owning the repository whose Stack state is mutated`

The code breaks this equality in two independent places:

1. **Verification uses the wrong/attacker-chosen key.** `repository_owner` is taken directly from the unauthenticated JSON body: [1](#0-0) 
This value selects which `Shipit.github(organization:)` app config (and thus which `webhook_secret`) is used to verify `X-Hub-Signature`: [2](#0-1) 

2. **`webhook_secret` is optional and, when absent, verification is a no-op.** [3](#0-2) 
`return true unless webhook_secret` means any organization configured without a secret (a documented, supported configuration — see `config/secrets.development.shopify.yml` and `docs/setup.md`, where `webhook_secret` is explicitly optional/`nil`) accepts **any** payload, signed or not.

3. **Handlers act on a different field than the one used for authentication.** Every handler resolves the target `Stack`/`Repository` via `repository.full_name`, not `repository.owner.login`: [4](#0-3) 

Because (1) is attacker-controlled and (2) allows trivially satisfying verification for any org lacking a secret, an attacker can submit `{"repository": {"owner": {"login": "OrgWithoutSecret"}, "full_name": "OrgWithSecret/target-repo"}, ...}` and pass `verify_signature` while acting on `OrgWithSecret/target-repo`, a repository the attacker has no legitimate access to and no valid secret for.

This is a direct analog of the report's bug class: a value used for one purpose (authorization/attestation — `ConsensusVersion`/here, org used to authenticate) diverges from the value actually acted upon (module state migrated/here, the repository actually mutated), because nothing binds them together.

### Impact Explanation
Once the forged webhook is accepted, several handlers mutate state for the impersonated repository/stack without any real GitHub-originated authorization:
- `Handlers::StatusHandler#process` creates a `Status`/commit-status record directly from attacker-supplied `state`/`context`/`sha` for any existing commit matching the given `sha` in the target repo's stacks: [5](#0-4) 
Since deploy eligibility is gated by commit status (`Commit#deployable?`), forging a `success` status for a commit that never passed real CI can enable an **unauthorized deploy** of unreviewed/malicious code — one of the explicitly listed Critical impacts.
- `Handlers::PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` for arbitrary stacks matching the (spoofed) branch, causing Shipit to sync from GitHub using its own credentials against the real repository — a controlled but real side effect that can also be used to trigger noise/DoS-adjacent GitHub API calls (out of scope on its own, but demonstrates write-adjacent reach).
- Other handlers (`membership`, `pull_request`) can create teams/users or manipulate merge-request-adjacent records tied to the spoofed repository's stacks.

This satisfies the "unauthorized deploy" / cross-repository-write impact bar required for a valid Critical finding.

### Likelihood Explanation
Exploitability depends entirely on this Shipit instance hosting at least one configured GitHub organization without a `webhook_secret` (or one whose secret the attacker can obtain/guess) alongside at least one other, security-sensitive org/repo it also tracks. This is an explicitly supported, documented configuration (`docs/setup.md`'s `webhook_secret` field is optional; the shipped `secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml` samples ship with `webhook_secret: # nil`), so the precondition is realistic for multi-tenant Shipit deployments where some orgs skip webhook-secret setup. No authentication, session, `ApiClient` token, or GitHub credentials are required by the attacker — only an HTTP POST to the public `/webhooks` endpoint (`config/routes.rb` mounts `WebhooksController` unauthenticated aside from `verify_signature`), matching the "unprivileged attacker" scope of this review.

### Recommendation
- Bind verification and action to the same field: use `repository.full_name`'s owner (not a separate `organization`/`repository.owner.login` field) consistently for both signature-org selection and stack resolution, and reject the request if they disagree.
- Do not silently pass verification when `webhook_secret` is blank; instead, require operators to set a secret for every configured organization (fail closed), or explicitly log/alert and restrict such orgs to a strict allow-list of repositories they may report on.
- In `Handlers::Handler`, cross-check that the resolved `Repository`'s stored owner/org matches the organization whose secret verified the request before processing any handler.

### Proof of Concept
Assume a Shipit instance configured with two GitHub orgs as in `test/dummy/config/secrets_double_github_app.yml`-style config, where `OrgWithoutSecret` has `webhook_secret: nil` and `OrgWithSecret/target-repo` is an actively tracked, security-sensitive stack.

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/invalid)
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "OrgWithoutSecret" },
    "full_name": "OrgWithSecret/target-repo"
  },
  "sha": "<sha of an undeployed commit on target-repo>",
  "state": "success",
  "context": "ci/forged",
  "target_url": "https://example.com"
}
```

- `repository_owner` resolves to `OrgWithoutSecret`.
- `Shipit.github(organization: 'OrgWithoutSecret').verify_webhook_signature(...)` returns `true` immediately because `webhook_secret` is blank — the bogus `X-Hub-Signature` is never actually checked.
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, whose `repository_name` reads `payload.dig('repository','full_name')` → `"OrgWithSecret/target-repo"`, resolving the real, protected stack.
- `commit.create_status_from_github!(params)` records a fabricated `success` status for that commit, potentially satisfying `Commit#deployable?` and enabling continuous delivery / manual deploy of an unreviewed commit on `OrgWithSecret/target-repo` — all without ever presenting a valid signature for `OrgWithSecret`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
