### Title
Unauthenticated `new_shared_address` message lets a paired device inject an attacker-controlled spending branch into another wallet's "shared address" definition - (File: `ocore--001/wallet_defined_by_addresses.js`)

### Summary
The Apollo advisory describes a sync/config-update endpoint that fails to properly re-verify permission on the object being modified, letting an attacker with limited (but not zero) trust craft a request that mutates a resource (a namespace) they don't own. The closest reachable analog in ocore is the `new_shared_address` P2P wallet message handled in `wallet.js` and processed by `walletDefinedByAddresses.handleNewSharedAddress()` in `wallet_defined_by_addresses.js`. Any already-paired device can send this message with an arbitrary address-definition tree; the receiver only checks that its *own* address appears somewhere in the tree and that the tree is structurally valid — it never verifies that the definition actually corresponds to the multisig/threshold policy that was previously negotiated through the `create_new_shared_address` / `approve_new_shared_address` flow. This allows an attacker to register a "shared address" in the victim's wallet whose real spending condition is `["or", [victim_branch, attacker_branch]]`, i.e., unilaterally spendable by the attacker, while the victim's UI/DB treats it as a legitimate joint address.

### Finding Description
`wallet.js` routes the P2P message directly to the handler without any check that the shared address was actually agreed upon by all parties beforehand: [1](#0-0) 

`handleNewSharedAddress` performs only structural/consistency checks:
- that `body.definition` is a 2-element array,
- that `body.address` equals `hash(body.definition)`,
- that every "address" leaf referenced in `body.signers` matches the corresponding `address` leaf in the definition,
- that the *recipient's own* device or address is referenced somewhere in the tree (via `determineIfIncludesMeAndRewriteDeviceAddress`),
- and that the tree passes generic `Definition.validateDefinition` (syntax/complexity only — it does not enforce any particular threshold policy). [2](#0-1) 

Crucially, there is no verification that:
1. `from_address` (the actual, cryptographically-verified sender) is a party that was ever invited to the multisig via the earlier `create_new_shared_address`/`pending_shared_addresses` negotiation, and
2. The received `arrDefinition` actually matches the *template* that was negotiated (`pending_shared_addresses.definition_template`) — `handleNewSharedAddress` never looks up or cross-checks against `pending_shared_addresses` at all.

Once the checks pass, `addNewSharedAddress` blindly persists the attacker-supplied definition as an on-record shared address and inserts a `shared_address_signing_paths` row for every signer entry, including the attacker's own address/device, exactly as supplied: [3](#0-2) 

Because `Definition.validateDefinition` only validates syntax (each branch must contain a signature, complexity limits, etc.) and does not enforce that the definition matches any pre-agreed threshold, an attacker can submit e.g. `["or", [["address", victim_addr], ["address", attacker_addr]]]` — a structurally valid definition containing the victim's real address (satisfying the "my address is referenced" check) but whose actual spending rule allows either party to sign alone.

### Impact Explanation
Any device that has previously paired with the victim (a low-privilege, non-owner correspondent — analogous to Apollo's "user without necessary permission") can push a forged "shared address" record into the victim wallet's database. If the victim (or any counterparty who is shown/uses this address, e.g. as a payment destination believing it to be a secured joint/multisig address) sends funds to that address, the attacker can spend them unilaterally because the persisted definition's real boolean logic is an `or`, not the multisig `and`/`r of set` structure the victim believes was negotiated. This is a direct "unauthorized modification of a namespace/definition without permission" leading to concrete unauthorized spending of any funds sent to the compromised shared address — matching the CWE-284 class of the reference advisory (crafted request bypasses a permission/consistency check to mutate a protected resource).

### Likelihood Explanation
The precondition is only that the attacker is an existing paired correspondent device of the victim (a normal, low-privilege relationship established through the standard pairing flow, not an "owner"/multisig-approved participant of this specific address). No cryptographic break, no privileged key, and no race condition is required — the attacker simply sends a single crafted `new_shared_address` hub message. The handler performs no cross-check against the negotiated `pending_shared_addresses` template, making exploitation deterministic.

### Recommendation
- In `handleNewSharedAddress`, require that the received `arrDefinition` (after substituting the sender/members) exactly reduce to a previously stored `pending_shared_addresses.definition_template` for that set of participants, rather than accepting any well-formed definition merely because the recipient's own address is present in it.
- Verify that `from_address` corresponds to one of the addresses/paths in the definition that was already approved by this device during the `create_new_shared_address`/`approve_new_shared_address` handshake, and reject unsolicited `new_shared_address` messages that don't correlate to an existing pending record.
- Consider enforcing that `validateAddressDefinition`/`Definition.validateDefinition` (or an additional policy check) confirms the presence of the expected M-of-N/`and` structure agreed to during negotiation, rather than accepting arbitrary `or` relaxations.

### Proof of Concept
1. Attacker device `D_a` is a normal paired correspondent of victim device `D_v` (no special role/owner rights on any shared address).
2. `D_a` sends hub message:
   ```
   subject: "new_shared_address"
   body: {
     address: hash(["or", [["address","VICTIM_ADDR"], ["address","ATTACKER_ADDR"]]]),
     definition: ["or", [["address","VICTIM_ADDR"], ["address","ATTACKER_ADDR"]]],
     signers: {
       "r.0": { address: "VICTIM_ADDR" },
       "r.1": { address: "ATTACKER_ADDR", device_address: D_a }
     }
   }
   ```
3. `handleNewSharedAddress` on `D_v`: hash matches, structural validation passes, `VICTIM_ADDR` is present so `determineIfIncludesMeAndRewriteDeviceAddress` succeeds, `Definition.validateDefinition` accepts the `or` (each branch has a signature).
4. `addNewSharedAddress` inserts the address into `D_v`'s `shared_addresses`/`shared_address_signing_paths` tables as a "shared" (jointly-controlled) address.
5. If funds are later sent to this address (by `D_v` or any third party who trusts it as a joint address), `D_a` can spend them alone by satisfying only the `["address","ATTACKER_ADDR"]` branch — no cooperation from `D_v` required.

Note: I could not fully trace, within the remaining exploration budget, how deeply this forged record propagates into UI trust indicators (e.g., whether wallet UIs distinctly warn about single-signature "or" branches for addresses labeled "shared"); this would benefit from a follow-up session with runtime/UI access to confirm end-to-end user-facing impact.

// {address: "BASE32", definition: [...], signers: {...}}
function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
