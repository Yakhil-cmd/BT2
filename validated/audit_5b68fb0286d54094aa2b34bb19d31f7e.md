### Title
Session fixation on GitHub OAuth callback — session ID is never rotated on login - ([File: app/controllers/shipit/github_authentication_controller.rb])

### Summary
The bug class in the report is a broken invariant where a value that should gate/scope an operation (the APR cap) is silently defeated by a code path that never actually re-validates the binding it's supposed to enforce (target growth rate silently becomes "no cap" due to an unchecked edge case). The structural analog in shipit-engine is `GithubAuthenticationController#callback`, which is supposed to bind a freshly-authenticated GitHub identity to a *new* session, but never rotates the session id, so a pre-existing (attacker-supplied) session can be silently upgraded to an authenticated session for the victim.

### Finding Description
`GithubAuthenticationController#callback` completes the OmniAuth flow and authenticates the browser by writing directly into the existing session: [1](#0-0) 

```ruby
def callback
  return_url = request.env['omniauth.origin'] || root_path
  auth = request.env['omniauth.auth']

  return render('failed', layout: false) if auth.blank?

  session[:user_id] = sign_in_github(auth)
  session[:authenticated] = true
  redirect_to(return_url)
end
```

Unlike `logout`, which calls `reset_session`, and unlike `force_github_authentication`, which calls `reset_session` when a stale login is detected, `callback` never calls `reset_session` before assigning `session[:user_id]`: [2](#0-1) [3](#0-2) 

The identity binding that should hold is: `session_id before OAuth completion` must differ from `session_id after OAuth completion` (i.e., the session must be regenerated on privilege elevation). Because the session cookie/id is reused verbatim and only its payload (`session[:user_id]`) is mutated, an attacker who can plant a known session identifier in a victim's browser (classic session-fixation delivery, e.g. via a subdomain cookie, a response-splitting bug elsewhere, or simply sharing a public/kiosk browser) will find that session becomes fully authenticated as the victim as soon as the victim completes the GitHub OAuth login — the attacker, holding the same session id/cookie, is now logged in as the victim without ever knowing the victim's GitHub credentials.

This mirrors the report's root cause pattern: a security-relevant recomputation (cap growth rate / session identity) that is supposed to be freshly derived and validated at a trust boundary, but is instead left stale/unrotated, silently defeating the intended protection.

### Impact Explanation
This directly matches the "session fixation / forced OAuth completion" High-impact category. An attacker who fixes a victim's session id and later observes/uses the same cookie gains an authenticated `Shipit::User` session — full access to whatever the victim can do in Shipit (deploying, rolling back, managing API clients, viewing/streaming task output for stacks the victim can access), i.e., escalation into the victim's authorization without ever compromising GitHub credentials.

### Likelihood Explanation
Exploitability depends on the attacker's ability to fix a victim's session cookie value before the OAuth login completes (a well-known technique with cookie-scoping/shared-host tricks or an existing session obtained by other means, e.g. a public terminal). No `ApiClient` token, `webhook_secret`, GitHub App key, or repository write access is required — only browser-level session-cookie control, which is consistent with the "unprivileged attacker" scope of this review. Given Rails' cookie-based session store does not automatically rotate the session id on writes, the vulnerability is present by default unless `reset_session` is invoked, which it is not in `callback`.

### Recommendation
Call `reset_session` (or otherwise rotate/regenerate the session identifier) at the start of `GithubAuthenticationController#callback`, before writing `session[:user_id]` and `session[:authenticated]`, mirroring the pattern already used in `logout` and in `force_github_authentication`'s stale-login handling.

### Proof of Concept
1. Attacker obtains/sets a session cookie value `S` in the victim's browser (session fixation delivery is out of scope for engine code, but any means of getting the victim to carry a known `_session_id=S` works, e.g., a shared kiosk browser or a fixation vector on a related subdomain).
2. Victim, still carrying cookie `S`, navigates to Shipit and completes the GitHub OAuth flow: `GET /github/auth/github/callback`.
3. `GithubAuthenticationController#callback` sets `session[:user_id] = victim.id` on the *same* session `S` — no `reset_session` occurs.
4. Attacker, who already knows/holds session `S`, sends the same cookie to Shipit and is now recognized as the authenticated victim by `Shipit::Authentication#find_current_user` (`session[:user_id].present? && User.find_by(id: session[:user_id])`), gaining the victim's full application access.
