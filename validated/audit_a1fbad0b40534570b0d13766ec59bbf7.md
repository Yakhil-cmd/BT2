### Title
Webhook signature verification keyed on `repository.owner.login` while stack lookup and mutation is keyed on the unrelated `repository.full_name` field, enabling cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository.owner.login` (or `organization.login`) taken from the *unverified* JSON body. Once the signature check passes, the same unverified body is handed to the event handlers, which resolve the target `Repository`/`Stack` using a *different* field, `repository.full_name` [1](#0-0) . Nothing ties `repository.owner.login` to the owner segment embedded in `repository.full_name`, so an attacker who controls (or knows the `webhook_secret` of) any one GitHub organization configured on a shared Shipit instance can sign a payload as that organization while making `full_name` point at an entirely different organization/repository also hosted on the same Shipit install.

### Finding Description
The signature check is:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up per-organization config (including `webhook_secret`) as configured in `config/secrets.yml`, e.g. multiple orgs can be registered on one Shipit instance [3](#0-2) . The HMAC is computed over the entire raw payload using the secret belonging to `repository.owner.login`. Nothing about this check constrains what the *rest* of the payload says.

After verification, `create` dispatches the same raw payload to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler resolves the acted-upon `Repository`/`Stack` from `repository.full_name`, not from `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [1](#0-0) 
and `Repository.from_github_repo_name` simply splits the string on `/`:
```ruby
def self.from_github_repo_name(github_repo_name)
  repo_owner, repo_name = github_repo_name.downcase.split('/')
  find_by(owner: repo_owner, name: repo_name)
end
``` [5](#0-4) 

The binding that should hold is:
`organization authenticated by signature (repository.owner.login) == organization of the repository actually written to (owner segment of repository.full_name)`

This binding is never checked. An attacker who is a legitimate GitHub user/admin for "org-A" (one org integrated with this shared Shipit instance) can trigger/replay/craft a webhook whose `X-Hub-Signature` is valid for org-A's `webhook_secret` (since GitHub will actually deliver such HMACs for real events on org-A's repos, and the attacker also fully controls the JSON body being delivered when using something like a generic webhook they add themselves to a repo under org-A) while setting `repository.full_name` (and any other handler-facing fields, e.g. `pull_request`, `sender.login`) to name a repository under an unrelated "org-B" also configured on the same Shipit instance. This is analogous to the reported bug class: a field that participates in the write path (`full_name`-derived stack) is disjoint from the field the security check actually covers/derives its trust from (`owner.login`-derived secret), exactly mirroring "an organization that authenticated versus the repository that is written."

### Impact Explanation
This crosses the "escalation into `Shipit.github_teams` authorization" / unauthorized write threshold because:
- `PushHandler` will call `stack.sync_github(expected_head_sha:)` for any stack under the forged `full_name`, and continuous-deployment-enabled stacks can subsequently deploy based on attacker-forged sync state [6](#0-5) .
- Pull-request handlers (`OpenedHandler`, `LabeledHandler`, `ReopenedHandler`, `LabelCapturingHandler`, etc.) archive/unarchive review stacks and create `User`/`Membership` records attributed to an attacker-chosen `sender.login`, for a target repository the attacker does not actually control [7](#0-6) [8](#0-7) .
- This is a cross-organization/cross-repository confused-deputy: state belonging to org-B is mutated using authority (signature) that was only ever proven for org-A.

This requires a shared/multi-tenant Shipit deployment with more than one GitHub org configured (which the codebase explicitly supports, as seen in `config/secrets.development.shopify.yml`). No `ApiClient` token, session, or GitHub App private key of the victim org is needed — only knowledge of / control over one configured org's own webhook delivery.

### Likelihood Explanation
Medium: it requires (a) a Shipit instance configured with multiple GitHub organizations sharing the same `/webhooks` endpoint, and (b) attacker control of a repository/webhook under one of those configured orgs (achievable by any org admin, or if a Shipit operator lets outside collaborators manage webhook settings on any covered repo). Given Shipit is designed for multi-org setups (see `TOP_LEVEL_GH_KEYS`/per-org config loading in `lib/shipit.rb` and `lib/shipit/github_app.rb`), this is a realistic operational configuration, not a purely theoretical one.

### Recommendation
After verifying the signature, cross-check that the organization used to select the `webhook_secret` (`repository.owner.login` / `organization.login`) matches the owner segment actually used by the handlers to resolve `full_name`, e.g.:
```ruby
def verify_signature
  ...
  owner_from_full_name = params.dig('repository', 'full_name')&.split('/', 2)&.first
  head(422) and return if owner_from_full_name && owner_from_full_name.casecmp(repository_owner).nonzero?
  ...
end
```
More robustly, compute the repository/organization used for secret selection and the repository/stack lookup from a single canonical source, or additionally verify (server-side, via the GitHub API/installation) that the named repository actually belongs to the installation associated with `repository_owner` before dispatching to handlers.

### Proof of Concept
1. Configure Shipit (as supported) with two organizations, `org-A` and `org-B`, each with its own `webhook_secret` (`config/secrets.yml`), both hosting stacks tracked by the same Shipit instance.
2. As an attacker with admin rights on a repository in `org-A`, register a custom webhook (or otherwise obtain a validly-signed delivery) to observe/produce a valid `sha1=` HMAC for org-A's secret over an attacker-chosen JSON body (GitHub signs exactly the raw body you configure/receive for that org's webhook).
3. Craft a `push` (or `pull_request`) JSON payload where:
   - `repository.owner.login = "org-A"` (so `repository_owner` resolves to org-A and its `webhook_secret` is used for verification),
   - `repository.full_name = "org-B/victim-repo"` (so the handler's `Repository.from_github_repo_name` resolves the actual victim stack).
4. Sign the crafted body with org-A's `webhook_secret` and POST it to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` passes (org-A's secret matches), but `PushHandler` acts on `org-B/victim-repo`'s stacks — e.g., invoking `sync_github(expected_head_sha:)` with an attacker-chosen `after` SHA for a repository the attacker never controlled, as shown by the handler resolving `stacks` purely from `full_name` [6](#0-5) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event

    end
