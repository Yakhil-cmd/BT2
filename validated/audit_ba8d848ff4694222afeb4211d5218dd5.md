### Title
Cross-tenant Status forgery via `StatusHandler#process` global `Commit.where(sha:)` lookup with no repository/stack scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves the target commit by an unscoped, global `Commit.where(sha: params.sha)` query, unlike every other webhook handler (`PushHandler`, the `PullRequest::*` handlers, `CheckSuiteHandler`) which restrict work to `stacks` derived from `Repository.from_github_repo_name(repository_name)`. Because `verify_signature` only authenticates that the HMAC matches the secret of the organization named in the *attacker's own payload* (`repository.owner.login`), an attacker who controls any org/repo with a valid `webhook_secret` can send a `status` event whose `sha` matches a commit that also exists in a victim's stack (e.g. by forking a public repository whose commit sha is preserved), causing a forged `Status` row (`state`/`description`/`target_url`, all attacker-controlled) to be written against the victim's commit/stack.

### Finding Description
The broken binding: `repository.full_name` (or `repository.owner.login`) in a `status` webhook payload is supposed to bind the write target to the same organization that signed the request, i.e. `verify_signature`'s authenticated org == the org owning the `Commit`/`Stack` mutated by the handler. Tracing the code shows this binding does not exist for `StatusHandler`:

- `WebhooksController#verify_signature` selects the GitHub App/secret using `repository_owner`, which is read straight from the attacker-controlled payload (`params.dig('repository', 'owner', 'login')`), and only checks the HMAC against that secret: [1](#0-0) [2](#0-1) 
- `StatusHandler#process` never touches `repository_name`/`stacks` at all - it queries commits globally by exact `sha` equality across the entire `commits` table and writes a status to every match: [3](#0-2) 
- Contrast with the base `Handler` class, which provides a `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that other handlers use to scope their side effects to the org that actually owns the payload's repository: [4](#0-3) 
- `Commit#create_status_from_github!` writes the status verbatim from the handler's params (state/description/target_url/context) onto whatever commit was matched: [5](#0-4) 

Exploit flow: attacker owns org `evil-corp` and repo `evil-corp/anything`, configured in Shipit with a legitimate `webhook_secret` for `evil-corp`. Attacker forks (or otherwise reproduces) a commit that is already tracked in a victim stack `victim-corp/app` — git commit shas are deterministic hashes of content+parents, so forking preserves the sha exactly. Attacker sends `POST /webhooks` with header `X-Github-Event: status`, payload `{"repository": {"owner": {"login": "evil-corp"}, "full_name": "evil-corp/anything"}, "sha": "<victim's commit sha>", "state": "success", "description": "forged", "target_url": "https://evil.example/phish"}`, HMAC-signed with `evil-corp`'s own secret. `verify_signature` passes because it only checks the signature against `evil-corp`'s secret, which matches. `StatusHandler#process` then runs `Commit.where(sha: params.sha)`, which matches the victim's `Commit` row (belonging to `victim-corp`'s stack) regardless of the attacker's declared repository, and writes a forged `Status` to it via `create_status_from_github!`.

No existing guard prevents this: `verify_signature` only authenticates HMAC-vs-org, not org-vs-commit-target; `ExplicitParameters` schema only validates types/presence of `sha`/`state`/etc, not ownership; there is no `stacks`/`repository_name` check inside `StatusHandler` at all.

### Impact Explanation
A successful request lets an attacker who controls any org onboarded to the Shipit instance write an arbitrary CI `Status` (`state`, `description`, `target_url`, `context`) onto a `Commit` belonging to a completely different tenant's `Stack`, without ever authenticating against that tenant's secret. Since `Commit#deployable?`/`Commit#blocked?`/`Stack#continuous_deployment?` and merge-queue logic (`ci.require`/`schedule_merges`) consume `Status`/`status.state`, a forged "success" status can mark a commit as deployable/mergeable prematurely, or a forged "failure"/malicious `target_url` can be used for CI-status spoofing/phishing against the victim's engineers. This is a cross-tenant write (one repository's payload mutating another repository's commit/stack), matching the Critical severity category explicitly listed in the rules.

### Likelihood Explanation
Preconditions: attacker needs any Shipit-onboarded org with a valid `webhook_secret` (their own, e.g. a self-registered/free-tier org) — no privileged access to the victim's org, session, or API token is required. The only added cost is obtaining a commit sha that also exists in the victim's tracked stack; this is trivially achievable when the victim tracks a public repository (fork it — sha is byte-identical) or when the attacker otherwise has visibility into the victim's commit history (e.g. via a shared upstream/dependency repo, or a previously observed sha from a public PR/commit page). Once achieved, the attack is repeatable indefinitely and can be pointed at any commit sha the attacker can reproduce, across any stack on the host.

### Recommendation
Scope `StatusHandler#process` the same way as the other handlers: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` (using the payload's `repository.full_name`, the same field validated during signature verification) and restrict the `Commit` lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`) instead of a global, unscoped `Commit.where(sha:)`. This ensures a status webhook can only mutate commits belonging to a stack whose repository matches the organization that authenticated the request.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual addition)
test "#process does not create a Status for a commit belonging to a different repository/stack" do
  victim_stack = shipit_stacks(:shipit) # e.g. repository "shopify/shipit-engine"
  attacker_owned_repo_full_name = "evil-corp/anything"

  colliding_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: "victim commit")

  payload = {
    "repository" => { "full_name" => attacker_owned_repo_full_name, "owner" => { "login" => "evil-corp" } },
    "sha" => colliding_sha,
    "state" => "success",
    "description" => "forged",
    "target_url" => "https://evil.example/phish",
  }

  assert_no_difference -> { victim_commit.statuses.count } do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
Before the fix, `Commit.where(sha: params.sha)` matches `victim_commit` regardless of `payload["repository"]["full_name"]`, so the assertion fails (a `Status` is created) — demonstrating the equality `payload.repository.full_name == stack.repository.full_name` is never checked for `StatusHandler`, unlike other handlers that filter via `Repository.from_github_repo_name(repository_name)&.stacks`.
