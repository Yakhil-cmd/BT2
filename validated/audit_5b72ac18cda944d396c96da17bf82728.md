### Title
`StatusHandler#process` binds forged `Status` rows by SHA only, not by webhook `repository_owner`, enabling cross-repo status forgery that triggers unauthorized deploys via `Stack#trigger_continuous_delivery` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves target commits with `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` without ever checking that the payload's `repository_owner`/`repository.full_name` matches the `stack.github_repo_name` that owns that `Commit` row. Because `Status.stack_id` comes from the found `Commit#stack_id` (not from the webhook payload), an attacker who controls a repo A whose commits share SHAs with a tracked stack B (e.g. via a public fork) can send a validly-signed webhook for A and cause a `Status` to be written against B's commit, feeding `Commit#deployable?` → `Stack#next_commit_to_deploy` → `Stack#trigger_continuous_delivery`.

### Finding Description
Binding claimed: `Stack#github_repo_name == repository_name` (from the webhook payload that created the qualifying `Status`). Tracing the code shows this binding is never checked:

- `app/controllers/shipit/webhooks_controller.rb:24-30` verifies the signature using `Shipit.github(organization: repository_owner)` where `repository_owner` is read straight from the attacker-controlled payload (`repository_owner` at line 59-61). This only proves the payload was signed with the secret belonging to whatever org the payload itself claims to be from — an attacker who owns repo/org A and configures its own webhook secret can produce a payload that is "validly signed for A" while making the `sha` field point at any commit SHA of their choosing.
- `Shipit::Webhooks::Handlers::StatusHandler#process` (app/models/shipit/webhooks/handlers/status_handler.rb:20-24):
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
This looks up commits **globally by SHA**, with no `stack_id`/`repository` filter tying the lookup back to the org that was authenticated by `verify_signature`. [1](#0-0) 
- `Commit#create_status_from_github!` → `add_status` → `statuses.replicate_from_github!(stack_id, github_status)` uses `self.stack_id`, i.e. the stack of the *found* commit row, never the repository named in the webhook payload. [2](#0-1) [3](#0-2) 
- The DB index on `commits` is `(stack_id, sha)`, not a global unique constraint on `sha` alone (per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming the schema allows the same SHA to legitimately exist under multiple different stacks (e.g. tracked forks/mirrors of the same upstream repo, or any stack whose commit history overlaps another's).
- `Status#schedule_continuous_delivery` (after_commit) calls `commit.schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` for `stack` — the victim's stack B, not the attacker's repo A. [4](#0-3) [5](#0-4) 
- `Stack#trigger_continuous_delivery` then calls `next_commit_to_deploy` → `deployable_commits`, which relies solely on `Commit#deployable?` (backed by `Status` rows), with no re-check of which webhook/organization produced those `Status` rows. [6](#0-5) [7](#0-6) 

**Attacker request**: Attacker owns/controls GitHub org/repo "attacker-org/A" (a public fork of the victim's tracked repo, or any repo whose history shares a commit SHA with a commit already present in the victim stack B's `commits` table — e.g. a shared upstream commit, a cherry-picked/rebased-preserving commit, or a fork relationship). Attacker configures a webhook on A with a secret they control, then POSTs to `/webhooks` with `X-Github-Event: status`, a validly computed `X-Hub-Signature` for A's secret, and a body `{"sha": "<shared-sha>", "state": "success", "context": "<required-context>", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/A"}}`.

**Why guards fail**: `verify_signature` only checks that the signature matches the secret for the org named *in the payload itself* — it never cross-checks that org against the repo that owns the target `Commit`/`Stack`. `drop_unhandled_event`, `ExplicitParameters` schema (`requires :sha`, `:state`, etc. in `StatusHandler`) and model validations (`Status` state inclusion) all pass, because nothing in the schema or validations constrains `sha` to belong to the authenticated repository.

### Impact Explanation
An attacker who never touches victim stack B, its GitHub org, its webhook secret, or its Shipit session can cause a `Shipit::Status` row to be written under B's `Stack`, satisfying `Commit#deployable?` for B and driving `Stack#trigger_continuous_delivery` to enqueue and run an unauthorized `Deploy` (`Task::PerformTaskJob` → `Command`/`PTY.spawn` on the deploy host) for stack B. This is a payload for one repository (A) mutating another repository's stack/commit/deploy state (B) — matching the Critical impact category "a payload for one repository mutating another's stack, commit, task or team" and "an unauthorized deploy". The blast radius spans any tenant stack whose commit history can overlap with an attacker-controlled repo (most plausible via public forks, which are common in OSS Shipit deployments), and the attack is repeatable per target commit/stack.

### Likelihood Explanation
Preconditions: attacker needs (1) their own GitHub repo/org with its own webhook configured to point at the shared Shipit host's `/webhooks` endpoint (fully attacker-controlled, no victim secret needed), and (2) a commit SHA that is shared between their repo and a `Commit` row already tracked for victim stack B — trivially achievable by forking a public repo that Shipit tracks, since forks share commit SHAs with upstream. No Shipit credentials, GitHub App keys, or org membership on B's side are required. Cost is minimal (fork + configure webhook + one HTTP POST); it is fully repeatable against any publicly-forkable tracked repository.

### Recommendation
In `StatusHandler#process` (and analogously in `CheckSuiteHandler`/other handlers that key off SHA alone), scope the `Commit` lookup to the authenticated repository: pass the verified `repository_owner`/`repository.full_name` from the controller into the handler and filter `Commit.joins(:stack).where(sha: params.sha, stacks: { repository_owner: ..., repository_name: ... })` (or equivalent) before calling `create_status_from_github!`, so a `Status` can only ever be attributed to the `Stack` whose GitHub repo matches the one that authenticated the webhook signature.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "status webhook signed for repo A cannot create a Status/trigger deploy for stack B tracking a different repo" do
  stack_b = shipit_stacks(:shipit) # tracks "shopify/shipit-engine"
  commit_b = stack_b.commits.create!(sha: 'sharedsha1234567890', message: 'x',
                                      author: shipit_users(:walrus), committer: shipit_users(:walrus),
                                      authored_at: Time.now, committed_at: Time.now)

  # Simulate a signature valid ONLY for attacker's own org/secret "attacker-org"
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature is genuinely valid for attacker-org

  request.headers['X-Github-Event'] = 'status'
  payload = {
    'sha' => commit_b.sha,
    'state' => 'success',
    'context' => 'ci/travis',
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker-org/A' }
  }.to_json

  Shipit::Stack.any_instance.expects(:trigger_continuous_delivery) # asserts B's deploy path fires

  assert_difference 'commit_b.statuses.count', 1 do
    post :create, body: payload, as: :json
  end

  # Equality that should hold but doesn't:
  # stack_b.github_repo_name ("shopify/shipit-engine") == payload["repository"]["full_name"] ("attacker-org/A")
  refute_equal stack_b.github_repo_name, 'attacker-org/A'
  assert commit_b.reload.deployable? # Status was written despite repository mismatch
end
```
This demonstrates the binding `Stack#github_repo_name == repository_name` is false yet the `Status` (and downstream `trigger_continuous_delivery`) still fires for stack B.
