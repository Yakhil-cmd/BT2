### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while the write target is selected from the unbound `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/organization secret to validate the HMAC signature against using `repository_owner` (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), but every webhook handler (`PushHandler`, `LabelCapturingHandler`, etc.) determines *which* `Repository`/`Stack` to mutate using a completely different, unauthenticated field: `payload.dig('repository','full_name')`. Nothing binds the org used for authentication to the repo that actually gets written. In a multi-organization Shipit install where one configured organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true`, letting anyone post an unsigned/arbitrary-signed payload that authenticates as that secret-less org while `repository.full_name` names a stack belonging to a different, properly secured organization.

### Finding Description
`verify_signature` in [1](#0-0)  resolves the app config solely from `repository_owner`: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically verified: [3](#0-2) 

This is not a hypothetical: the shipped sample multi-org config explicitly allows `webhook_secret` to be `nil` per organization: [4](#0-3) 

Once `verify_signature` passes (because the "authenticating" org has no secret configured), the controller dispatches the raw JSON body to handlers, and `head(422)` is called as a *side effect* rather than as a `render`/`throw` that halts the filter chain — i.e., after calling `verify_webhook_signature` unsuccessfully, `head(422)` executes but processing continues: [5](#0-4) 

All handlers derive the mutated `Stack`/`Repository` purely from `repository.full_name`, e.g.: [6](#0-5) [7](#0-6) 

So the equality that should hold — *organization whose signature authenticated the request* == *organization owning the repository that gets written* — is never enforced. An attacker can set `repository.owner.login` (or `organization.login`) to an org configured with a blank `webhook_secret` (satisfying `verify_signature`), while setting `repository.full_name` to `"other-org/some-repo"`, a completely different, unrelated, and properly-secured stack tracked by the same Shipit instance. `PushHandler` will then call `stack.sync_github(expected_head_sha: params.after)` for that other org's stack based on attacker-supplied `ref`/`after` values, without the request ever having been validated by that other org's actual webhook secret.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary explicitly called out as in-scope. The practical effect is an unauthenticated, cross-organization write: an attacker with no GitHub credentials, no Shipit session, and no knowledge of any real webhook secret can force `sync_github` (and other webhook-driven mutations, e.g., archiving/unarchiving review stacks, capturing labels, updating pull request state) on a stack belonging to an organization they have no relationship with, purely by exploiting a secret-less sibling organization entry in the same Shipit deployment's secrets. Depending on which handler is triggered and what commits already exist upstream on GitHub, this can result in unintended deploy triggers or state changes on repositories outside the attacker's control, satisfying the "unauthorized deploy" / cross-repository-write impact bar.

### Likelihood Explanation
Requires: (1) a multi-organization Shipit deployment, and (2) at least one configured organization without a `webhook_secret`. Both conditions are explicitly supported and even shown as valid/sample configuration in this engine (`config/secrets.development.shopify.yml`, `lib/shipit.rb#github_app_config`), so this is not a contrived or unsupported deployment — it is the documented multi-org configuration schema. No credential, session, or webhook secret is required by the attacker; they only need to know the (already-guessable/public) name of a Shipit-installed org lacking a secret and the `full_name` of the target stack's repository (both are non-secret, discoverable strings).

### Recommendation
Bind the org used for signature verification to the org that owns the repository actually referenced by the payload before dispatching to handlers — i.e., resolve `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, derive its actual owning organization, and require that this match (and successfully verify against) the same organization used in `verify_signature`. Additionally, do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a *configured* organization in a multi-org setup; either require a secret for all secondary orgs or reject events whose `repository_owner` doesn't match the actual repository owner recorded in Shipit's database. Also fix `verify_signature`/`check_if_ping` to actually halt the filter chain (`render`/`throw(:abort)`) instead of relying on `head` calls that don't stop `create` from being invoked.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `orgA` (no `webhook_secret`) and `orgB` (has `webhook_secret: real-secret`), each with at least one tracked stack, e.g. `orgB/prod-app`.
2. Attacker sends `POST /github/webhooks` with header `X-Github-Event: push` and no/garbage `X-Hub-Signature`, and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha that exists upstream>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/prod-app" }
}
```
3. `repository_owner` resolves to `"orgA"`; `Shipit.github(organization: "orgA")` is used; `verify_webhook_signature` returns `true` because `orgA.webhook_secret` is blank — no valid signature was needed.
4. `PushHandler` resolves the target `Stack` from `repository.full_name = "orgB/prod-app"`, unrelated to `orgA`, and calls `stack.sync_github(expected_head_sha: <attacker-controlled sha>)`, causing `orgB`'s stack (secured with a real, unknown-to-attacker secret) to sync/deploy based on an unauthenticated request.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
```
