### Title
Front-runnable griefing of `SystemInstruction::CreateAccountWithSeed` via pre-funding the derived address to force `AccountAlreadyInUse` - (File: programs/system/src/system_processor.rs)

### Summary
`create_account()` in the System program rejects account creation if the target account already has a positive lamport balance. For `CreateAccountWithSeed`, the target ("to") address is a publicly-derivable `Pubkey::create_with_seed(base, seed, owner)` value and does **not** need to be a transaction signer — only the `base` key must sign. Any unprivileged party who observes a pending `CreateAccountWithSeed` transaction can compute the same derived address and submit a trivial `Transfer` instruction sending it 1 lamport before the legitimate transaction lands, permanently causing the legitimate transaction to fail with `SystemError::AccountAlreadyInUse`. This mirrors the reported `DKIMRecoverySigValidator` front-running class: an idempotency/"already done" check keyed on data that is derivable/observable by anyone rather than gated by the intended actor's authorization, letting an attacker with no special privilege front-run and permanently block a legitimate operation.

### Finding Description
In `create_account()`:
```rust
// programs/system/src/system_processor.rs:160-171
{
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    if to.get_lamports() > 0 {
        ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
        return Err(SystemError::AccountAlreadyInUse.into());
    }
    allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
}
``` [1](#0-0) 

The signer requirement for the `to` account is derived from `Address::is_signer`, which for a seeded address only requires the `base` key to be a signer, not the derived `to` address itself:
```rust
// programs/system/src/system_processor.rs:36-42
fn is_signer(&self, signers: &HashSet<Pubkey>) -> bool {
    if let Some(base) = self.base {
        signers.contains(&base)
    } else {
        signers.contains(&self.address)
    }
}
``` [2](#0-1) 

This is confirmed by the existing unit test showing the `to` `AccountMeta` is `is_signer: false` when a separate `base` account is provided: [3](#0-2) 

Because the derived `to` address is fully computable from public data (`base`, `seed`, `owner`) contained in the transaction itself, and does not require its own signature, an attacker monitoring the network for a pending `CreateAccountWithSeed` transaction can:
1. Recompute the same `to = Pubkey::create_with_seed(base, seed, owner)`.
2. Submit an ordinary `SystemInstruction::Transfer` sending any nonzero lamport amount to `to`, using their own funds and their own signature (fully unprivileged, no special access needed).
3. If this transfer lands first, `to.get_lamports() > 0` becomes true, and the legitimate `CreateAccountWithSeed` transaction will subsequently fail with `SystemError::AccountAlreadyInUse` every time it is retried with the same `seed`, exactly as the `recoveries[identifier] == true` check permanently blocks the legitimate `DKIMRecoverySigValidator::validateSig` call in the reported bug.

### Impact Explanation
This lets an unprivileged attacker permanently deny another party's account creation for a specific `(base, seed, owner)` triple, forcing them to choose a new seed (if their calling code even allows this) or otherwise blocking downstream logic that depends on creating that specific deterministic address (e.g., program-derived account setup flows, nonce-account-with-seed creation, stake-account-with-seed creation, or any client library / dApp workflow relying on `create_account_with_seed`). This matches the reachable classes: account loading and lamport conservation checks reachable via a single unprivileged transaction.

### Likelihood Explanation
High. No preconditions are required beyond observing the pending transaction's public instruction data (base, seed, owner are always included in the instruction) before it lands, and submitting a plain, cheap `Transfer` instruction. This is trivially automatable and requires no elevated privileges, no special account ownership, and only nominal fees/lamports.

### Recommendation
Do not gate the "already in use" rejection purely on `lamports > 0` when the destination account was never expected to hold funds prior to creation from an authorized party. Consider allowing `CreateAccountWithSeed` (and `CreateAccount`) to proceed by transferring/topping-up rather than failing when the account has only been pre-funded with lamports and still has zero data length and system-program ownership (similar to the existing `create_account_allow_prefund` path), or require the derived address itself to also be represented as a signer-checked identity bound to the seed/base pairing at a level that cannot be spoofed by a bystander transfer. At minimum, document and mitigate the front-running risk for `CreateAccountWithSeed` consumers, since the current check conflates "has lamports" with "is in use."

### Proof of Concept
1. Legitimate user Alice builds and broadcasts (or has cached for later submission) a `CreateAccountWithSeed { base: Alice, seed: "s", owner: SystemProgram, lamports, space }` transaction targeting `to = Pubkey::create_with_seed(&Alice, "s", &SystemProgram)`.
2. Attacker Bob observes this transaction (e.g., in gossip/mempool prior to inclusion), computes the same `to` address using the public `base`/`seed`/`owner`.
3. Bob submits `SystemInstruction::Transfer { lamports: 1 }` from his own funded account to `to`, and it lands in an earlier slot/ahead of Alice's transaction.
4. Alice's `CreateAccountWithSeed` transaction now fails deterministically:
```rust
// programs/system/src/system_processor.rs:963-998 (existing unit test demonstrating the exact rejection path)
let owned_account = AccountSharedData::new(1, 0, &Pubkey::default());
...
Err(SystemError::AccountAlreadyInUse.into()),
``` [4](#0-3) 
This is the same rejection Alice's real transaction hits once Bob's front-run transfer has landed, permanently blocking account creation for that `seed` until a different seed is chosen.
