### Title
Cross-repository forged commit status via unscoped `StatusHandler` webhook lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The `status` webhook is authenticated per-organization (the signature is checked against `Shipit.github(organization: repository_owner)`, where `repository_owner` is read straight from the payload's `repository.owner.login`), but `Shipit::Webhooks::Handlers::StatusHandler` never re-validates that the commit it mutates actually belongs to that same repository. It looks the commit up globally by SHA across the entire `commits` table and writes a `Status` on whatever it finds.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization solely from the untrusted JSON body (`params.dig('repository', 'owner', 'login')`) and validates the HMAC against that organization's configured `webhook_secret`: [1](#0-0) [2](#0-1) 

For the other handlers, authorization is completed by additionally scoping to `stacks`, which is itself derived from the same `repository.full_name` field: [3](#0-2) 
`PushHandler` and `CheckSuiteHandler` both filter through this `stacks`/repository-derived relation before touching any commit: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores the `repository` field entirely and queries `Commit` globally by `sha`: [6](#0-5) 

Because a Git SHA is a content hash and not a repository-scoped identifier, the exact same SHA can legitimately exist in multiple independent `Repository`/`Stack` rows tracked by Shipit (mirrors, forks, repositories split from a shared history, or any repository that happens to contain an identical commit object). The signature check only proves the request was signed with *some* organization's `webhook_secret` matching the `repository.owner.login` claimed in the body; it proves nothing about which `Commit` rows that organization is entitled to update. `StatusHandler#process` therefore breaks the binding: *the organization that authenticated the webhook* ≠ *the repository/stack whose commit status is actually written*.

### Impact Explanation
Shipit's commit statuses drive CI-gating logic used for deploys and merges (`Status`, `Status::Group`, `MergeRequest` safety checks). An attacker who controls a repository with a configured Shipit webhook (i.e., can send legitimately-signed `status` events for *their own* repository/organization) can forge a `state: "success"` status for any commit SHA — including one that coincides with a commit tracked by a completely different, unrelated stack — and have that status attached to the victim's commit. If Shipit's deploy/merge safety checks rely on that forged status being green, this can help bypass CI gating for an unauthorized deploy or merge on a stack the attacker has no access to, without ever touching the victim organization's `webhook_secret`.

### Likelihood Explanation
Exploitation requires: (1) the attacker legitimately owns/administers a repository already onboarded to Shipit (so they can trigger genuinely-signed `status` webhooks), and (2) a commit SHA collision with a targeted victim stack's tracked commit — realistic for forked repos, mirrored/vendored repositories, or monorepo splits that share commit history across multiple Shipit-tracked stacks, which is a common real-world Shipit deployment pattern (multiple stacks/environments per shared codebase). No Shipit session, API token, or the victim's webhook secret is required.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup the same way `PushHandler`/`CheckSuiteHandler` do — via `stacks` (derived from the authenticated `repository.full_name`) — e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)`, instead of querying `Commit` unscoped.

### Proof of Concept
1. Onboard `attacker/repo` to Shipit with its own valid GitHub App webhook secret (legitimate self-service action).
2. Identify a commit SHA that also exists in a victim stack tracking a different repository (e.g., a shared upstream commit present in both a fork and the original, both onboarded to Shipit).
3. Send a `status` event, correctly signed with `attacker/repo`'s own webhook secret, containing that shared `sha` and `state: "success"`:
```
POST /webhooks
X-Github-Event: status
X-Hub-Signature: sha1=<valid signature for attacker/repo>
{"repository":{"owner":{"login":"attacker-org"},"full_name":"attacker/repo"},
 "sha":"<shared-sha>","state":"success", ...}
```
4. `StatusHandler#process` finds `Commit.where(sha: params.sha)` — matching the commit in the *victim's* stack — and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled "success" status onto a commit the attacker's authenticated organization does not own. [7](#0-6)

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
