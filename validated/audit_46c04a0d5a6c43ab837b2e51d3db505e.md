### Title
Epoch-reward recalculation on snapshot restore uses live stake delegations instead of the frozen epoch-boundary snapshot, misattributing rewards and causing cross-node divergence - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
On the normal (no-restart) code path, per-stake reward inputs (`stake_delegations`) are captured once at the epoch boundary, before any transaction of the new epoch runs, and cached for the whole distribution window [1](#0-0) [2](#0-1) . However, when a validator restarts from a snapshot while reward distribution for the previous epoch is still active, `recalculate_stake_rewards` recomputes those same rewards using `self.stakes_cache.stakes()` — i.e., the *current, live* stake state as of the restart slot — rather than the original epoch-boundary snapshot [3](#0-2) . Any ordinary staker (unprivileged) can submit stake-mutating instructions (delegate more, split, merge, deactivate/withdraw) in the blocks between the epoch boundary and a validator's later restart, changing the "input" that feeds a still-in-flight reward computation for the *previous* epoch — precisely the VRF-docs anti-pattern of "accepting input after the outcome-determining request has been made."

### Finding Description
`compute_new_epoch_caches_and_rewards` snapshots `stake_delegations` from `stakes_cache.stakes()` at the epoch boundary, before the new epoch's transactions execute, and this snapshot (together with `reward_epoch_delegated_stakes`) is fed into `calculate_rewards`, which caches the result per parent hash so it is not recomputed as later blocks execute [4](#0-3) [5](#0-4) .

`recalculate_stake_rewards`, invoked only via `initialize_after_snapshot_restore` (and the test helper `new_for_block_tests`) when `EpochRewards` sysvar is still active, instead pulls `stake_delegations` from the bank's *current* `StakesCache` at the restart slot via `get_epoch_params_for_recalculation` [3](#0-2) [6](#0-5)  and calls `initialize_after_snapshot_restore` -> `recalculate_partitioned_rewards_if_active` [7](#0-6) [8](#0-7) .

While the fix at `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` specifically pins the *denominator* (`RewardEpochDelegatedStakes`) to the original epoch-boundary value [9](#0-8) , the per-account `stake_delegations` vector used as the *numerator* input to `calculate_stake_points_and_credits`/`redeem_delegation_rewards` is not similarly pinned — it is whatever the live `StakesCache` contains at restart time [10](#0-9) [11](#0-10) . Because `Stake.delegation.stake` and account presence/absence in `stake_delegations_vec()` are mutated by ordinary, unprivileged stake instructions (`Delegate`, `Split`, `Merge`, `Deactivate`/`Withdraw`), any staker can change their own or another account's stake amount — or make the account disappear entirely — between the epoch boundary and the moment a validator happens to restart from a snapshot mid-distribution.

### Impact Explanation
Because the recalculation path only triggers on restart, two honest validators processing the identical block history can diverge in the reward lamports they compute and distribute for the same rewarded epoch/account depending solely on whether/when they restarted from a snapshot, given the same intervening stake-modifying transactions:
- A staker who withdraws/closes their stake account after the epoch boundary but before an unpaid partition is distributed causes that account to drop out of `stake_delegations_vec()`, so its already-earned inflation reward for the previous epoch is silently never paid — this breaks the invariant that `distributed_rewards + remaining stake rewards == total_rewards`, effectively burning owed lamports (a variant of "duplicated/misattributed rewards").
- A staker who increases stake (via `Delegate`/`Merge`) after the boundary but before restart gets a larger reward for the previous epoch than they should have earned during that epoch, and the reverse for reducing stake.
- Because this materializes on the deterministic-consensus bank-hash path (`store_accounts` in `distribute_partitioned_epoch_rewards` uses these amounts), nodes that restart mid-distribution vs. nodes that stay up produce different lamport amounts for the same stake accounts in the same slot — i.e. cross-node state divergence / bank-hash mismatch.

### Likelihood Explanation
Medium: it requires (a) an ordinary stake instruction from any unprivileged staker executed during the multi-block distribution window following an epoch boundary, and (b) a validator taking the `initialize_after_snapshot_restore` path (a routine event for any validator that restarts, e.g. after an upgrade, crash, or fast-restart from a local snapshot) while that epoch's `EpochRewards` sysvar is still active. Both conditions are common in normal cluster operation and require no special privilege — only ordinary `StakeInstruction` transactions from the staker.

### Recommendation
Persist the epoch-boundary `stake_delegations` snapshot (or an equivalent immutable per-epoch record of each account's effective stake, analogous to what was already done for `RewardEpochDelegatedStakes`) so that `recalculate_stake_rewards` reconstructs rewards strictly from state as of the rewarded epoch's boundary, not from the live `StakesCache` at restart time. Alternatively, stop accepting/erase the effect of stake-mutating instructions on already-committed-but-undistributed reward calculations by keying the recalculation off a stored, epoch-boundary-frozen delegation snapshot rather than `self.stakes_cache.stakes()`.

### Proof of Concept
1. At epoch `N` boundary, `compute_new_epoch_caches_and_rewards` computes and caches `PartitionedRewardsCalculation` for staker `S` with stake amount `X` for rewarded epoch `N-1`, spread across multiple distribution partitions across several blocks.
2. In the first distribution block of epoch `N`, staker `S` submits an ordinary `StakeInstruction::Withdraw`/`Split`/`Merge` transaction, changing (or removing) their stake delegation.
3. Before `S`'s unpaid partition is distributed, the validator restarts from a snapshot taken at that slot; `initialize_after_snapshot_restore` calls `recalculate_partitioned_rewards_if_active` → `recalculate_stake_rewards`, which reads `self.stakes_cache.stakes()` reflecting `S`'s post-step-2 stake, not the original `X` used at the epoch boundary [3](#0-2) .
4. `S`'s recalculated reward for epoch `N-1` differs from (or vanishes relative to) the value originally cached in step 1, while a validator that never restarted continues distributing based on the original snapshot — producing different final lamport balances for `S` across validators for the same slot.

    pub(in crate::bank) fn calculate_rewards(
        &self,
        stake_history: &StakeHistory,
        stake_delegations: Vec<(&Pubkey, &StakeAccount<Delegation>)>,
        cached_vote_accounts: CachedVoteAccounts<'_>,
        rewarded_epoch: Epoch,
        reward_epoch_delegated_stakes: RewardEpochDelegatedStakes,
        reward_calc_tracer: Option<impl Fn(&RewardCalculationEvent) + Send + Sync>,
        thread_pool: &ThreadPool,
        metrics: &mut RewardsMetrics,
    ) -> Arc<PartitionedRewardsCalculation> {
        // We hold the lock here for the epoch rewards calculation cache to prevent
        // rewards computation across multiple forks simultaneously. This aligns with
        // how banks are currently created- all banks are created sequentially.
        // As such, this lock does not actually introduce contention because bank
        // creation (and therefore reward calculation) is always done sequentially.
        //
        // However, if we plan to support creating banks in parallel in the future, this logic
        // would need to change to allow rewards computation on multiple forks concurrently.
        // That said, there's still a compelling reason to keep this lock even in a parallel
        // bank creation model: we want to avoid calculating rewards multiple times for the same
        // parent bank hash. This lock ensures that.
        //
        // Creating bank for multiple forks in parallel would also introduce contention for compute resources,
        // potentially slowing down the performance of both forks. This, in turn, could delay
        // vote propagation and consensus for the leading fork—the one most likely to become rooted.
        //
        // Therefore, it seems beneficial to continue processing forks sequentially at epoch
        // boundaries: acquire the lock for the first fork, compute rewards, and let other forks
        // wait until the computation is complete.
        let mut epoch_rewards_calculation_cache =
            self.epoch_rewards_calculation_cache.lock().unwrap();
        let rewards_calculation = epoch_rewards_calculation_cache
            .entry(self.parent_hash)
            .or_insert_with(|| {
                Arc::new(self.calculate_rewards_for_partitioning(
                    stake_history,
                    stake_delegations,
                    cached_vote_accounts,
                    rewarded_epoch,
                    reward_epoch_delegated_stakes,
                    reward_calc_tracer,
                    thread_pool,
                    metrics,
                ))
            })
            .clone();
        drop(epoch_rewards_calculation_cache);
