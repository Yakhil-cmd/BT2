### Title
Cross-repository status forgery via un-scoped SHA lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target `Commit` purely by `Commit.where(sha: params.sha)`, with no check that the reporting `payload['repository']['full_name']` actually owns that commit. A `status` webhook that is validly signed for the attacker's own repository (or any repository/org configured in Shipit with a GitHub App) can therefore write a `Status` onto a commit belonging to an entirely different stack, and that write fires `Hook.emit(:commit_status, ...)`/`:deployable_status` for the *victim's* stack with attacker-chosen `target_url`/`description`.

### Finding Description
The broken binding is:
`payload['repository']['full_name'] (the repo the signature/org authenticates) == commit.stack.repository.full_name (the repo whose Hooks/Status get mutated)`
This never holds in `StatusHandler`.

- `WebhooksController#verify_signature` only checks that the payload was signed by the GitHub App/org identified by `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:24-49`), i.e. it authenticates *which org sent the request*, not *which commit/stack the payload is allowed to affect*.
- Every other handler scopes its side effects through `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)` from the same payload (`app/models/shipit/webhooks/handlers/handler.rb:32-38`).
- `StatusHandler`, uniquely, bypasses this and does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
There is no filter on `commit.stack.repository`, so any commit anywhere in the database sharing that `sha` is updated, regardless of which repository's webhook_secret validated the request.
- `commit.create_status_from_github!` → `add_status` (`app/models/shipit/commit.rb:366-386`) computes the state transition and, on a meaningful transition, calls `Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status))` / `Hook.emit(:deployable_status, ...)` using `self.stack` — i.e. the stack that owns the matched commit, not the stack tied to the requester's repository. [2](#0-1) 
- `Hook.emit` schedules delivery to every `Hook` scoped to that stack (or global hooks) via `EmitEventJob`/`Hook.deliver` (`app/models/shipit/hook.rb:98-119`), sending attacker-controlled `state`, `description`, `target_url`, `context` (all accepted, unvalidated strings per the `StatusHandler` params schema) to the victim's configured `delivery_url` (e.g. Slack). [3](#0-2) 

**Attack flow:** An attacker who owns/pushes to any repository that has a Shipit-side GitHub App/webhook configured (satisfying `verify_signature` legitimately, using GitHub's own signing with that org's real secret — the attacker never needs to know the secret because GitHub computes it) creates a commit whose SHA is shared with a commit already tracked in a victim's unrelated stack (e.g. a forked/mirrored public repository sharing history, or any deliberately engineered SHA collision scenario across tracked repos). The attacker then sets a custom commit status (via `git commit --allow-empty` + `POST /repos/:owner/:repo/statuses/:sha` on their own repo, using their own GitHub token) with a crafted `description`/`target_url`. GitHub delivers the `status` webhook to Shipit, correctly signed for the attacker's org. `StatusHandler` matches the shared SHA against the victim's `Commit` row and applies the status, firing `commit_status`/`deployable_status` hooks that leak attacker content into the victim's external notification channel.

Existing guards do not close this: `verify_signature` only guarantees *origin authenticity of the org*, not *authorization to touch a specific commit/stack*; there is no per-handler repository/stack cross-check for the `status` event, unlike `push`/`pull_request`/`check_suite` handlers which all route through `Handler#stacks`.

### Impact Explanation
Attacker-controlled data (`state`, `description`, `target_url`, `context`) is written to a `Status` record belonging to a stack the attacker does not control, and this triggers that victim stack's outbound `Hook` deliveries (`commit_status`/`deployable_status`), injecting attacker-chosen content into the victim's Slack/webhook integrations and potentially influencing merge-queue logic (`stack.schedule_merges` in `add_status`). This is a cross-tenant write ("a payload for one repository mutating another's stack, commit ... " — Critical per the rubric), repeatable against any commit whose SHA the attacker can predict/reproduce and any number of stacks tracking that SHA.

### Likelihood Explanation
Requires: (1) the attacker controls at least one repository/org already wired into Shipit with a working GitHub App/webhook (a normal, low-privilege precondition for anyone onboarded to a multi-tenant Shipit instance, or achievable by forking a repo whose org already has the App installed), and (2) a SHA collision/sharing between the attacker's repo and a victim's tracked commit (trivially achievable for forks/mirrors of the same public repository, which share full commit history and thus identical SHAs). No Shipit secrets, sessions, or API tokens are needed — GitHub itself signs the forged payload legitimately for the attacker's own repo.

### Recommendation
In `StatusHandler#process`, restrict the commit lookup to commits whose stack's repository matches `payload.dig('repository', 'full_name')` (mirroring `Handler#stacks`), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or an explicit join filtering `Commit#stack_id` against `Repository.from_github_repo_name(repository_name).stacks`, before calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (illustrative)
test "status webhook cannot mutate a commit belonging to a different repository's stack" do
  victim_stack = shipit_stacks(:cyclimse) # tracks repo "cyclimse/cyclimse"
  victim_commit = shipit_commits(:cyclimse_first)
  # Attacker's payload claims a *different* repository but references the victim's sha
  forged_payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'description' => 'attacker-controlled',
    'target_url' => 'https://evil.example.com/leak',
    'repository' => { 'full_name' => 'attacker/attacker-repo', 'owner' => { 'login' => 'attacker' } }
  }

  expect_no_hook(:commit_status) do
    Shipit::Webhooks::Handlers::StatusHandler.call(forged_payload)
  end

  victim_commit.reload
  refute_equal 'attacker-controlled', victim_commit.status.description
end
```
This asserts the binding `payload['repository']['full_name'] == commit.stack.repository.full_name` is enforced before any `Status` write or `Hook.emit(:commit_status, victim_stack, ...)` occurs.
