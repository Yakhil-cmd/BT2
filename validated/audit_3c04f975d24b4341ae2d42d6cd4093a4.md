### Title
Unprivileged `Split` on a stake account between epoch-reward calculation and partitioned distribution can panic `build_updated_stake_reward`'s `assert_eq!`, halting block processing - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` computes an `expected_delegation` from the *live* `StakesCache` entry for a stake pubkey and compares it via `assert_eq!` against the `new_stake.delegation.stake` that was baked into the immutable `PartitionedStakeReward` at epoch-reward calculation time. Because `stakes_cache_accounts` is re-fetched fresh on every distribution block (not a snapshot pinned at calculation time), any legitimate transaction that changes the stake account's `delegation.stake` between calculation and its scheduled distribution partition — such as the stake authority's own `Split` instruction — desynchronizes the two values and can trip the assertion.

### Finding Description
`store_stake_accounts_in_partition` reads the *current* stakes cache on each distribution block: [1](#0-0) 

For each stake pubkey scheduled in that block's partition, `build_updated_stake_reward` fetches the live entry and, when `adjust_delegations_for_rent` is *not* active, asserts that `stake.delegation.stake` (current, live) plus the previously-computed `inflation.stake_reward` equals `new_stake.delegation.stake` (the value baked into the immutable `PartitionedStakeReward` at calculation time): [2](#0-1) 

`PartitionedStakeReward` entries are computed once during the epoch-boundary calculation phase from a stakes-cache snapshot at that time, and are then held immutable (`Arc<PartitionedStakeRewards>`) for use across the whole (potentially multi-block) distribution window: [3](#0-2) 

If, between the calculation block and the block that processes that account's assigned partition index, the stake authority submits a `Split` instruction against their own stake account, the stake program mutates the source account's `Delegation::stake` (reducing it by the split amount) as part of normal, entirely unprivileged operation — the stake program has no knowledge of, or restriction tied to, an in-flight `PartitionedStakeReward`. This mutation is reflected immediately in the live `StakesCache`. When the account's distribution partition is later processed, `expected_delegation` (current reduced stake + stake_reward) will differ from `new_stake.delegation.stake` (stale pre-split stake + stake_reward) by exactly the split amount, causing the `assert_eq!` to panic. The code comment at `distribution.rs:330-332` ("further state mutation prevents by stake-program restrictions, there should never be rewards burned") indicates the developers assumed such mutation is impossible, but no code path found in this repository actually blocks `Split` (or other delegation-mutating stake instructions) from executing against a stake account with a pending partitioned reward, nor does the calculation phase re-validate/re-freeze per-account delegation state before each distribution block.

The panic occurs inside `distribute_partitioned_epoch_rewards`, which is invoked as part of ordinary bank/block processing for every node replaying or producing that slot, meaning the crash is deterministic and would occur across the whole network processing that block — a consensus-halting condition, not an isolated per-transaction failure.

When `adjust_delegations_for_rent` (feature `relax_post_exec_min_balance_check`) is active, the code instead calls `adjust_delegation_for_rent`, which clamps the delegation using `account.lamports()` rather than asserting equality; this branch avoids the panic but was designed for rent-related adjustments, not for reconciling a mid-window `Split`, so its lamport-conservation properties versus a concurrent `Split` were not independently verified here.

### Impact Explanation
If reached, this triggers a `assert_eq!`-induced Rust panic inside core bank block-processing logic, which aborts the validator process for every node processing the affected slot — this is a scoped **consensus/liveness halt** (all validators panicking deterministically at the same block), the most severe category in the Agave bounty program for accounting-logic bugs. This does not require staked/leader/gossip control: only an unprivileged stake-authority signature on a `Split` instruction against the attacker's own stake account.

### Likelihood Explanation
Preconditions:
- The stake account must have a pending inflation reward (any non-zero delegation participates in the epoch's `PartitionedStakeReward` set).
- The reward-distribution window must span more than one block (true whenever `num_partitions > 1`, which is common for any moderately large validator set — `get_reward_distribution_num_blocks` produces multiple partitions once the number of stake accounts exceeds `partitioned_rewards_stake_account_stores_per_block`).
- `relax_post_exec_min_balance_check` feature must be inactive for the direct panic path (older/legacy feature-set state); if active, the impact shifts from panic to a different code path with its own conservation properties, not verified here as impact-shifting to lamport creation.
- The attacker needs only to submit a normal `Split` instruction using their own stake/withdraw authority, timed to land in a block after epoch-reward calculation but before their own partition index's scheduled distribution block — timing is derivable in advance since the partition-to-block mapping is deterministic from the parent blockhash and each account's partition index (`hash_rewards_into_partitions`), all public block data.

This makes the bug reliably and repeatably triggerable by any user controlling a delegated stake account, with no elevated privileges.

### Recommendation
Do not compare the live `StakesCache` state against the values frozen at calculation time via a hard `assert_eq!`. Instead:
- Re-derive `expected_delegation` from the account's actual current `delegation.stake` observed at distribution time (treating the reward as additive to whatever the current live value is, rather than requiring bit-for-bit reproduction of a stale calculated value), or
- Detect the divergence explicitly and route it through the same conservation-safe reconciliation path used for `adjust_delegations_for_rent` (or a dedicated code path) instead of panicking, ensuring lamport accounting still balances against the split remainder.
- Alternatively, enforce that stake-mutating instructions (`Split`, `Merge`, `Withdraw`, `Deactivate`) are rejected by the stake program (or by bank-level guard) for any account that still has an un-distributed `PartitionedStakeReward` pending, closing the underlying TOCTOU window entirely.

impl Bank {
    /// Process reward distribution for the block if it is inside reward interval.
    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }
