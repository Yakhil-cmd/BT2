### Title
Missing State/Session Binding in `new_shared_address` Device-Message Handler Allows Unsolicited Multisig Address Injection - ([File: wallet_defined_by_addresses.js])

### Summary
The multi-device shared (multisig) address creation protocol in `wallet_defined_by_addresses.js` binds intermediate steps (`approve_new_shared_address`) to the sending device via `WHERE definition_template_chash=? AND device_address=?` [1](#0-0) , but the terminating message, `new_shared_address`, is accepted and committed with no equivalent check that the sender ever participated in, or was authorized to complete, the negotiation it claims to finish. This mirrors the Authlib "state not bound to session" defect: a value that is supposed to correlate a multi-step protocol to its originator (here, the shared-address creation/approval flow) is instead trusted purely on its own internal consistency (hash matches definition, signer paths match definition), letting any paired correspondent complete/fabricate the flow unilaterally.

### Finding Description
`wallet.js` dispatches the `new_shared_address` device message straight into `walletDefinedByAddresses.handleNewSharedAddress(body, ...)` without ever passing `from_address` to it: [2](#0-1) 

`handleNewSharedAddress` only checks that:
- `body.definition` hashes to `body.address` (structural self-consistency)
- `body.signers` entries match the addresses referenced in `body.definition`
- via `determineIfIncludesMeAndRewriteDeviceAddress`, that one of the referenced member addresses is one of *my* own local addresses (or a known shared address) [3](#0-2) 

None of these checks verify that the actual sending device (`from_address`, already authenticated by device-message signature verification in `device.js`) is one of the participants recorded in `body.signers`, nor that this message corresponds to any locally-tracked `pending_shared_addresses` / `pending_shared_address_signing_paths` entry that the local wallet itself initiated via `create_new_shared_address`. Contrast this with the intermediate `create_new_shared_address` step, which requires an explicit user-confirmation dialog before any state is persisted [4](#0-3) ; the final `new_shared_address` step has no such gate and calls `addNewSharedAddress` directly, persisting the address and its signer table: [5](#0-4) 

Because the "state" correlating this final step to a specific negotiation (`address_definition_template_chash`) is never checked against anything the receiving device itself started or approved, any already-paired correspondent device can independently send a `new_shared_address` message naming the victim's own address as one signer and arbitrary attacker-controlled definitions/other signers, and it will be silently written into `shared_addresses` / `shared_address_signing_paths` — exactly the "no session binding on the value that completes the flow" defect described in the advisory.

### Impact Explanation
Once injected, the spoofed shared address is persisted as if it were a genuine multisig address the victim co-owns, and the victim's device will subsequently act on it as trusted (e.g., forwarding private payment chains to signer devices listed in the spoofed row via `forwardPrivateChainsToOtherMembersOfAddresses`, which sends payments/private-payload data to whatever `device_address` was recorded in `shared_address_signing_paths` for that address [6](#0-5) ). This can result in the victim's private payment chains/proofs being forwarded to an attacker device, and — depending on the crafted definition (e.g., an `or` branch giving the attacker unilateral spending rights) — funds sent to the address by the victim (who believes it requires cosigning with a legitimate, jointly-negotiated party) can be spent solely by the attacker, i.e., unauthorized spending / AA-style fund loss stemming from a definition the victim never actually negotiated or approved end-to-end.

### Likelihood Explanation
The attacker only needs to already be a paired correspondent of the victim (a routine, low-privilege relationship established via normal pairing, similar to a "private-payment counterparty"), and needs to know one of the victim's addresses (trivially obtainable, as addresses are meant to be shared for payments). No compromise of the hub, network, or victim device is required — a single crafted device message suffices, matching the "1-click" nature of the reported CSRF-class defect.

### Recommendation
Bind the completion message to the negotiation state it claims to finish: require `handleNewSharedAddress`/`new_shared_address` processing to check that `from_address` is one of the `device_address` values referenced in `body.signers`, and/or require that a corresponding `pending_shared_addresses`/`pending_shared_address_signing_paths` row (created by a local `create_new_shared_address`/`createNewSharedAddressByTemplate` call) already exists for the definition hash before persisting the address unconditionally. At minimum, gate `addNewSharedAddress` for unsolicited `new_shared_address` messages behind an explicit user-confirmation step, as is already done for `create_new_shared_address`.

### Proof of Concept
1. Attacker (D_A) is already paired with victim (D_V) as a normal chat/wallet correspondent, and knows one of the victim's public addresses `Addr_V`.
2. Without any prior `create_new_shared_address` exchange, D_A sends `D_V` a `new_shared_address` device message: `{address: chash160(def), definition: def, signers: {...}}` where `def` is `["and",[["address","Addr_V"],["address","Addr_A"]]]` (or a definition with an `or` branch letting D_A spend unilaterally), and `signers` map each path to `Addr_V`/`Addr_A` with `device_address` pointing at D_A for the attacker path.
3. `wallet.js`'s `new_shared_address` handler forwards straight to `handleNewSharedAddress`, which validates only structural consistency and that `Addr_V` belongs to the victim, then calls `addNewSharedAddress`, persisting the address with no confirmation dialog and no check that D_A is an authorized party to complete any pending negotiation.
4. The victim's wallet now shows/treats the attacker-crafted address as a legitimate shared address; future funds or private-payment chains associated with it are exposed to/controlled by the attacker per the crafted definition.

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}
	determineIfIncludesMeAndRewriteDeviceAddress(body.signers, function(err){
		if (err)
			return callbacks.ifError(err);
		validateAddressDefinition(body.definition, function(err){
			if (err)
				return callbacks.ifError(err);
			addNewSharedAddress(body.address, body.definition, body.signers, body.forwarded, callbacks.ifOk);
		});
	});
}
