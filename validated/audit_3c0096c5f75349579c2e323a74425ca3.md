### Title
Cross-organization webhook confusion: signature verified against `repository.owner.login`'s secret, but stack lookup keyed on unvalidated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate the inbound signature against using `params.dig('repository', 'owner', 'login')`, while the actual handlers (`Shipit::Webhooks::Handlers::Handler#repository_name`, used by `PushHandler`, `StatusHandler`, and all `PullRequest::*Handler`s) resolve the target `Repository`/`Stack` using the separate `repository.full_name` field of the same JSON body. Nothing ties these two fields together, so a payload signed with one organization's webhook secret can act on a Stack belonging to a completely different, unrelated organization configured on the same Shipit instance.

### Finding Description
`Shipit` supports hosting multiple GitHub organizations from a single instance, each with its own `app_id`/`webhook_secret` (documented in `docs/setup.md` "Using Multiple Github Applications", and reflected in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`).

The webhook signature check is: [1](#0-0) 

`repository_owner` is derived purely from the payload: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the org-specific `GitHubApp`/secret via `github_app_config`: [3](#0-2) 

Once the signature is verified using *that* organization's secret, the raw payload is handed unmodified to the registered handlers: [4](#0-3) 

But every handler resolves the target repository/stack using a *different* field of the same payload — `repository.full_name` — with no cross-check that it is consistent with `repository.owner.login`: [5](#0-4) 

This is used directly by, e.g., `PushHandler` (drives `stack.sync_github`) and `StatusHandler` (drives `commit.create_status_from_github!`, which feeds deployability checks): [6](#0-5) [7](#0-6) 

and by the pull-request handlers via `Repository.from_github_repo_name(params.repository.full_name)`: [8](#0-7) 

**Binding broken:** `github organization whose webhook secret authenticated the request` ≠ `repository (and its Stacks) whose state the handler mutates`. An attacker who controls a GitHub organization that has legitimately installed the same shared Shipit GitHub App instance (and therefore possesses that org's genuine `webhook_secret`, delivered to them by GitHub's own webhook mechanism for their own installation) can sign an arbitrary payload with `repository.owner.login` = their own org, but set `repository.full_name` = `"victim-org/victim-repo"`. `verify_signature` passes because it only checks the signature against the attacker's own org's secret; the handler then acts on the victim org's Stack.

### Impact Explanation
This breaks the isolation that multi-organization Shipit deployments rely on: one tenant organization's app credentials should only be able to affect that tenant's repositories. With this flaw, a tenant with a legitimately installed low-trust app installation can:
- Forge `push` events to trigger `Stack#sync_github` against another org's Stack with an attacker-chosen `after` SHA.
- Forge `status` events (`StatusHandler`) to fabricate commit statuses on another org's commits, influencing deployability/CI-gating checks that gate deploys and the merge queue.
- Forge `pull_request` events to open/close/label review stacks belonging to another org's repository.

This maps to "escalation into `Shipit.github_teams` authorization" / "unauthorized deploy" class impact because forged commit statuses can make an otherwise non-deployable commit appear deployable, and forged push/PR events can manipulate another tenant's stack state without ever holding that tenant's own webhook secret or repository write access.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple organizations (an explicitly supported and documented configuration) and requires the attacker to control one of those configured (but otherwise unrelated/lower-trust) organizations — which is a normal, unprivileged position for a "tenant" in a multi-org Shipit setup, not a privileged Shipit account, `ApiClient` token, or the victim org's own secret. This is a realistic misconfiguration-adjacent trust break rather than a purely theoretical one, given the feature is explicitly documented and shipped.

### Recommendation
After signature verification, validate that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the webhook (422) on mismatch. Alternatively, resolve the target repository/stack using the same organization identity that was used to select the verifying secret, rather than trusting `repository.full_name` independently.

### Proof of Concept
1. Configure Shipit with two organizations, `orgA` (attacker-controlled, legitimately installed) and `orgB` (victim, has a Stack for `orgB/app`), each with distinct `webhook_secret`s, per `docs/setup.md`'s multi-org schema.
2. As the owner of `orgA`, obtain `orgA`'s genuine `webhook_secret` (delivered to them via their own GitHub App installation settings, no privileged Shipit access required).
3. Craft a `status` event payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": {"login": "orgA"}, "full_name": "orgB/app" }
}
```
4. Sign the raw body with `orgA`'s `webhook_secret` using HMAC-SHA1 and send it as `X-Hub-Signature` to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "orgA")` and successfully verifies the signature against `orgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a forged status on the victim commit belonging to `orgB/app`, which the attacker never controls.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
