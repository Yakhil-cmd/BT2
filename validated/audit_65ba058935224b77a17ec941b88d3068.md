### Title
Fixed 8000-character diff truncation in `build_refute_prompt` lets attacker-controlled diff padding push dangerous hunks out of the adversarial-refute view, causing legitimate findings to be self-refuted as "not in diff" - (File: `plugins/security-guidance/hooks/review_api.py`)

### Summary
`build_refute_prompt` truncates the diff shown to the self-refute (adversarial-verification) pass to `diff_text[:8000]` characters [1](#0-0) , while the earlier investigate stage that originally found the vulnerability sees the full diff (capped only at `DIFF_PER_FILE_BYTES`/`DIFF_TOTAL_BYTES`, up to 400,000 bytes) [2](#0-1) . An attacker who controls the diff (e.g. a PR author) can pad or order the diff so that the genuinely dangerous hunk lands past byte 8000 in the refute-stage view, causing the refute prompt's own explicit "PRE-EXISTING … does NOT appear on any + line in the DIFF block above" rule to instruct the model to refute a real, newly-introduced vulnerability.

### Finding Description
`agentic_review`'s self-refute stage (both the standalone `review_api.build_refute_prompt` and its inline duplicate in `llm.py`) re-embeds the diff as raw text truncated to only the first 8000 characters: `"\n\nDIFF:\n" + diff_text[:8000]` [1](#0-0) . The refute prompt then instructs the model that a candidate should be refuted as "PRE-EXISTING" whenever "the cited vulnerableCode does NOT appear on any + line in the DIFF block above" [3](#0-2) .

Because `diff_text` at this point can be up to the investigate stage's cap of 400,000 bytes (`DIFF_TOTAL_BYTES`) [2](#0-1)  — built by concatenating every touched file's diff via `_cap_files_for_prompt`/`cap_diff_for_prompt` in file order [4](#0-3)  — an attacker fully controls both the diff content and the ordering/size of files in the changeset. By committing large, benign-looking changes (or padding a file that sorts earlier) ahead of the actually dangerous file, the attacker can push the dangerous `+` lines beyond the 8000-character cutoff used only in the refute stage. The candidate produced by the earlier investigate pass (which saw the full, untruncated diff and correctly flagged the vulnerability) is then handed to the refute pass together with a DIFF block that no longer contains the incriminating lines. Following its own explicit criterion, the model has textual justification to mark the finding "PRE-EXISTING"/not-in-diff and refute it — even though `SURVIVED_SCHEMA`'s fail-open behavior only protects against schema/parse failures [5](#0-4) , not against a model correctly following its own (truncation-corrupted) instructions.

This differs from ordinary "LLM might be wrong" risk because it is deterministic and code-driven: the truncation boundary is a fixed literal (`[:8000]`), independent of where meaningful content lives, and the refute prompt's own rubric turns "absent from the truncated view" into an instruction to suppress the finding.

### Impact Explanation
This lets an unprivileged repository contributor craft a diff that reaches the LLM investigate stage (so a real vulnerability is discovered) but is dropped in the adversarial self-refute stage purely due to truncation, silently disabling the security review's blocking/warning behavior for that specific commit — a security-control bypass matching "Security-control bypass that silently disables or routes around blocking, review, or permission boundaries." The dangerous code proceeds without the Stop-hook warning/blocking that `analyze_code_security`/`agentic_review` is meant to enforce.

### Likelihood Explanation
Preconditions: attacker only needs normal commit/PR authorship (no elevated privilege) and control over diff size/ordering, both of which are ordinary repository-contributor capabilities. The self-refute path with diff-anchor tagging is the validated default (`filter_mode == "self_refute"`) [6](#0-5) , and the 8000-char cap is a fixed constant with no relation to `DIFF_TOTAL_BYTES`, so any multi-file or moderately large diff (well within the 400KB total cap) can trivially exceed it. This is repeatable and deterministic, not probabilistic prompt-injection guesswork.

### Recommendation
Do not use a fixed global character truncation of the full diff for the refute stage. Instead, either (a) include only the diff excerpt(s) relevant to each candidate's `filePath`/`vulnerableCode` (bounded per-candidate, not globally truncated), or (b) raise the refute-stage diff budget to match the investigate-stage cap (`DIFF_TOTAL_BYTES`) so both stages see the same view, and/or (c) when truncating, guarantee that every candidate's cited file/hunk is preserved in the truncated window (e.g., prioritize including diff regions referenced by `candidates[*].filePath`/`vulnerableCode` before filling remaining budget with other content).

### Proof of Concept
Unit test plan for `plugins/security-guidance/hooks/review_api.py::build_refute_prompt`:
1. Construct a synthetic `diff_text` consisting of ~9000 characters of benign filler diff for `filler.py` followed by a small dangerous diff hunk for `danger.py` containing a marker string, e.g. `+ os.system(user_input)`.
2. Construct `candidates = [{"filePath": "danger.py", "category": "Command Injection", "vulnerableCode": "os.system(user_input)"}]`.
3. Call `prompt = build_refute_prompt(candidates, diff_text)`.
4. Assert that the dangerous marker line (`os.system(user_input)`) is present in the `"DIFF:\n" + diff_text[:8000]` portion of `prompt`. Expected (failing) result: assertion fails because the marker is truncated out, demonstrating that the refute-stage prompt does not anchor the diff content relevant to the candidate being adjudicated — confirming the truncation/anchoring defect described above.
5. As a regression guard for the fix, re-run after implementing per-candidate excerpting or full-budget parity and assert the marker line is always present regardless of its offset in the full diff.
