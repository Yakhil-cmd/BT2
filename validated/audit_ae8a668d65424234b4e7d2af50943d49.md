### Title
Accrual overflow permanently freezes large high-utilization markets - (`File: common/src/rates/scaling.rs`)

### Summary

The pool represents market totals as RAY-scaled share counts and converts them to underlying value with `scaled * index / RAY`. `scaled_to_original` uses the checked `Ray::mul`, so an unrepresentable result panics with `MathOverflow`. Because every market operation calls `interest::global_sync` before mutating state, once this conversion overflows the affected market permanently rejects `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, `recapitalize`, and even permissionless `update_indexes`.

The documented and tested boundary is reachable before the `MAX_BORROW_INDEX_RAY` cap: a market with roughly `1e36` scaled shares overflows when its borrow index approaches about `170 * RAY`. The harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates that an 18-decimal market holding one billion tokens at 98% utilization reaches this state and then rejects both withdrawal and repayment.

### Finding Description

`controller::update_indexes(caller, assets)` is callable by any authorized caller and forwards each selected `HubAssetKey` to `pool_update_indexes_call` in `contracts/controller/src/markets.rs`. In the pool, `ops::market::accrue` loads each market and invokes `interest::global_sync`.

`global_sync` executes `accrue_step` for each elapsed chunk. `accrue_step` immediately computes:

- `scaled_to_original(borrowed, borrow_index)`
- `scaled_to_original(supplied, supply_index)`

Both functions are thin wrappers around `Ray::mul`, whose fixed-point multiplication rejects results outside `i128`. The overflow site is `common/src/rates/scaling.rs::scaled_to_original`.

This failure is not contained to the maintenance endpoint. `contracts/pool/src/ops/mod.rs::synced_market` calls `Cache::load` followed by `interest::global_sync`, and the ordinary market operations use `synced_market` or `renewed_market`. Therefore, after the threshold is crossed, every later operation that needs the market panics before its mutation can execute.

The index ceiling does not prevent this condition. `update_borrow_index` clamps the index to `MAX_BORROW_INDEX_RAY = 10^36`, but the value `borrowed * borrow_index / RAY` can exceed `i128::MAX` long before that cap when `borrowed` is sufficiently large.

### Impact Explanation

Permanent freezing of funds and protocol insolvency risk.

Once either total borrow value or total supply value can no longer fit in a RAY `i128`, the market's accrual precondition fails for all subsequent calls:

- suppliers cannot withdraw;
- borrowers cannot repay;
- liquidators cannot liquidate;
- bad debt cannot be cleaned;
- flash loans cannot be processed;
- recapitalization cannot proceed;
- `update_indexes` itself cannot move `last_timestamp` forward.

Since the panic occurs before any state mutation, there is no self-recovery path through the affected market's public flow. User deposits remain locked, outstanding debt cannot be serviced, and collateral supporting positions in that market cannot be accessed through the normal lifecycle.

The repository's own regression test proves the final state by asserting `MATH_OVERFLOW` for `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`.

### Likelihood Explanation

Likelihood is constrained by market size, utilization, and elapsed accrual, but it is permissionless once such a market exists.

An attacker does not need an overflow-capable input field, privileged parameter, malformed oracle, or unauthorized call. The attack path uses ordinary calls:

1. `controller::supply` creates a very large supply position in a listed high-decimals asset.
2. `controller::borrow` leaves the market at sustained high utilization.
3. `controller::update_indexes` is called over time by anyone.
4. Eventually `scaled_to_original` overflows, after which all market operations fail.

The practical barrier is capital: the demonstrated configuration uses one billion whole units of an 18-decimal token and sustained 98% utilization. This makes the issue most relevant to highly liquid tokens, bridged assets with large supplies, or markets whose caps are raised. The bug is also not dependent on malicious timing: an organically large and highly utilized market can cross the boundary without a deliberate attacker.

### Recommendation

Prevent fixed-point value conversion from becoming a permanent transaction-wide panic.

A robust remediation should introduce a bounded market-value policy before accrual, for example:

- add an explicit `scaled * index` representability limit below `i128::MAX`;
- reject new `supply` or `borrow` when the projected post-operation market value would exceed that safe bound;
- make `update_indexes` degrade safely at the bound instead of repeatedly panicking;
- preserve a recovery path that can process repayment, withdrawal, liquidation, or bad-debt cleanup without requiring the same overflowing aggregate conversion;
- if an exact `I256` value cannot be stored, use saturating aggregate valuation only for utilization/rate derivation while retaining exact share-level accounting for settlement.

At minimum, entry-side caps must be enforced against both `scaled` amount and expected index growth, not merely against the current token amount. The existing `calculate_scaled_cap` saturation does not solve this later aggregate-value overflow.

### Proof of Concept

The existing test establishes the complete sequence:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs

let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.borrow_raw(ALICE, "BIG18", debt);

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break e;
    }
}

assert_contract_error(failed, errors::MATH_OVERFLOW);
assert_contract_error(
    t.try_withdraw_raw(BOB, "BIG18", 1),
    errors::MATH_OVERFLOW
);
assert_contract_error(
    t.try_repay(ALICE, "BIG18", 1.0),
    errors::MATH_OVERFLOW
);
```

The overflow occurs in `scaled_to_original`:

```rust
// common/src/rates/scaling.rs

pub fn scaled_to_original(env: &Env, scaled: Ray, index: Ray) -> Ray {
    scaled.mul(env, index)
}
```

and is reached by every accrual step:

```rust
// common/src/rates/simulate.rs

let borrowed_original = scaled_to_original(env, borrowed, borrow_index);
let supplied_original = scaled_to_original(env, supplied, supply_index);
```

All normal market mutations route through the same accrual call before they can modify state:

```rust
// contracts/pool/src/ops/mod.rs

let mut cache = Cache::load(env, hub_asset);
interest::global_sync(env, &mut cache);
```
