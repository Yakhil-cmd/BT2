### Title
`Api::CCMenuController` bypasses per-token stack scoping, allowing a stack-scoped ApiClient to read any stack's deploy status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` binds the set of stacks an `ApiClient` may act on to that client's `stack_id` column, but `Api::CCMenuController` re-implements stack lookup without using that binding, so a token scoped to a single stack can read the CCMenu status of *any* stack.

### Finding Description
`Api::BaseController` defines the authorization boundary that every other API controller relies on: an `ApiClient` scoped to a stack (`stack_id` set) can only see that stack, everything else sees all stacks. [1](#0-0) 

This is exactly the mechanism validated by the test `"an api client scoped to a stack will only see that one stack"`, which confirms scoped clients are intended to be restricted to their bound stack. [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` and declares `require_permission :read, :stack`, but it overrides the `stack` resolver to look the stack up directly by parameter, completely bypassing the `stacks`/`stack_id` scoping used everywhere else: [3](#0-2) 

`require_permission :read, :stack` only checks that the token carries the `read:stack` permission string via `ApiClient#check_permissions!`; it never checks which stack the permission applies to. [4](#0-3) 

So the binding that should hold is:
`stack authorized by ApiClient#stack_id == stack acted on by Api::CCMenuController#show`

But because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])` (the scoped helper used by every sibling controller, e.g. `Api::StacksController`), the equality is broken: any token with `read:stack` — including one whose `stack_id` restricts it to stack A — can pass an arbitrary `stack_id` in the URL and read stack B's, C's, etc. CCMenu XML (deploy/rollback status, latest task id, running state).

### Impact Explanation
This breaks the API's per-token authorization scoping and allows escalation into reading stack state that the token was never granted — matching the "escalation into `Shipit.github_teams` authorization ... unauthenticated read of stack state, task streams or deploy output" class of High-severity impact. A token deliberately provisioned with narrow scope (e.g. the `here_come_the_walrus`-style stack-scoped client, or the auto-created "CCMenu Client" for a specific stack) becomes effectively unscoped for this one endpoint, disclosing deploy status of stacks the token holder should have no visibility into.

### Likelihood Explanation
Any holder of a valid `read:stack` `ApiClient` token — regardless of whether that token is stack-scoped — can trivially exploit this by substituting a different `stack_id` in the CCMenu request path; no additional privilege or interaction is required beyond having one valid, low-privilege token.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup already provided by `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so the stack resolved for CCMenu output is constrained the same way as in `Api::StacksController` and other controllers, restoring the `ApiClient#stack_id` == acted-upon-stack binding.

### Proof of Concept
1. Provision (or obtain) an `ApiClient` scoped to `stack_id: A` with permission `read:stack` (e.g., via the "CCMenu Client" auto-created by `CCMenuUrlController#client`, or any stack-scoped client such as the `here_come_the_walrus` fixture pattern). [5](#0-4) 
2. Using that token, request `GET /api/stacks/<owner>/<other-repo>/<other-env>/ccmenu?token=<token>` where `<other-repo>/<other-env>` belongs to a different, unauthorized stack B.
3. `Api::CCMenuController#authenticate_api_client` accepts the token; `require_permission :read, :stack` only checks the permission string, not the stack; `stack` resolves stack B directly via `Stack.from_param!`, bypassing the `stack_id` restriction. [6](#0-5) 
4. The response renders stack B's latest deploy/rollback status (`shipit/ccmenu/project`), disclosing deploy state the token was never authorized to see.
