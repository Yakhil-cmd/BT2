Based on my research, I found a genuine analog: the `uniswap_like_market_maker.oscript` AA template ships in ocore's own examples/tests and demonstrates a documented AA pattern where the "initial deposit" state is inferred from an unauthenticated on-chain balance check (`balance[$asset] - trigger.output[[asset=$asset]] == 0`) rather than from any authenticated proof that a genuine first investor triggered the AA. This exactly mirrors the root cause of the Solidex bug: trusting an externally-observable/manipulable state signal as "proof" of the legitimate first deposit, before any real initial investment has been recorded, permanently distorting the share-issuance ratio for all subsequent users.

### Title
Unauthenticated "initial deposit" balance check in AA market-maker template allows first-depositor share-price manipulation (donation/inflation attack) - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The bundled Uniswap-like market-maker AA template determines whether an "invest" trigger is the genuine initial deposit purely by checking whether the AA's current asset/base balances (net of the incoming trigger outputs) are zero. Any unprivileged unit poster can send a bare payment of the tracked asset directly to the AA address (bypassing the "invest" message logic entirely, since a plain payment to the AA is always accepted and silently added to `balance[$asset]`), corrupting this "initial deposit" precondition before the legitimate first investor’s trigger executes.

### Finding Description
In `test/samples/uniswap_like_market_maker.oscript` the "invest in MM" branch computes:
```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
``` [1](#0-0) 
The AA treats a zero pre-trigger balance as reliable evidence that the current trigger is the "first" investment, and on that basis issues `$mm_asset` 1:1 with the deposited bytes, skipping the proportional ratio check used for all subsequent deposits. This is directly analogous to the Solidex root cause: an unauthenticated/unverified signal (here, the AA's raw on-chain balance, spoofable by simply sending assets to the AA's address outside of the "invest" flow) is trusted as proof that a specific privileged state transition (the genuine initial deposit) has legitimately occurred. Because ocore's AA engine unconditionally credits any tokens/bytes sent to an AA address to `balance[...]` regardless of the message that carried them [2](#0-1) , an attacker can pre-fund the AA with a negligible amount of `$asset` (or bytes) via a plain payment before the intended first investor's trigger fires, corrupting the `$asset_balance == 0` check and forcing the subsequent legitimate deposit down the wrong code path (or vice versa), permanently skewing the `mm_asset_outstanding` share accounting for every future investor.

### Impact Explanation
This falls under "AA fund loss or freezing": once the share-issuance ratio baseline is corrupted at the "initial deposit" stage, all later investors receive incorrect proportions of `$mm_asset`/`base`/`$asset` relative to their contribution, and the imbalance cannot be corrected without redeploying the AA (AAs are immutable), matching the same permanence noted in the original report ("a contract malfunction cannot be fixed without a contract replacement"). Since the AA holds pooled bytes and asset tokens, this can result in the attacker (or subsequent depositors) extracting a disproportionate share of the pooled funds relative to what they contributed.

### Likelihood Explanation
Any unprivileged unit poster can send a trivial payment to a known AA address before its first legitimate "invest" trigger — this requires no special privileges, only knowledge of the AA's address and timing (front-running the AA's first real investor), making the precondition trivially reachable by any network participant.

### Recommendation
AA templates relying on "first deposit" detection should not rely solely on the AA's raw balance; they should track a dedicated persistent state variable (e.g., `var['initialized']`) that is set exactly once by the AA's own logic upon the first successful investment, and check that flag rather than inferring "zero balance" from `balance[...]`. This pattern should also be documented as a required best-practice warning in `test/samples/uniswap_like_market_maker.oscript` and any other bundled templates using the same idiom, since developers copy these samples as the basis for real deployed AAs.

### Proof of Concept
1. Deploy the `uniswap_like_market_maker.oscript` AA and call the "define share asset" case to create `$mm_asset`.
2. Before any legitimate investor calls "invest in MM", the attacker sends a plain payment of `1` unit of `$asset` directly to the AA address (a normal payment message, not an "invest" trigger) — this is silently accepted and added to `balance[$asset]` per the AA's default balance accounting [2](#0-1) .
3. The legitimate first investor now sends their intended "invest" trigger with a large amount of bytes and asset. Since `$asset_balance = balance[$asset] - trigger.output[[asset=$asset]]` is now non-zero (it includes the attacker's pre-funded 1 unit), the AA takes the "not initial deposit" branch and applies the ratio check `$expected_asset_amount = round($current_ratio * trigger.output[[asset=base]])`, computed against the attacker-skewed `$current_ratio = $asset_balance / $bytes_balance`, causing the legitimate investor's deposit to bounce or be issued shares at a corrupted ratio.
4. This permanently distorts `var['mm_asset_outstanding']` accounting for all future investors, matching the report's described impact of "incorrect calculation of rewards" that "cannot be fixed without a contract replacement."
