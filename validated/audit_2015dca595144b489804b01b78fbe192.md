### Title
Signature verification uses the payload's own `organization.login`/`repository.owner.login`, decoupled from the `repository.full_name` used to select the mutated Stack, enabling cross-organization forged `push` webhooks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App (and thus which HMAC secret) to verify a webhook against using `repository_owner`, a value taken directly from the untrusted request body (`repository.owner.login`, falling back to `organization.login`). `PushHandler`, via `Handler#stacks`, instead resolves the target `Stack` using `payload.dig('repository', 'full_name')`. These two org/repo identifiers are never cross-checked, so an attacker can pick which configured organization "verifies" the request while pointing the actual mutation at a different, victim repository/stack.

### Finding Description
The binding that should hold is: **verifying organization** (`repository_owner`, used to pick `Shipit.github(organization: repository_owner)` in `verify_signature`) **== owning organization of the mutated Stack** (the owner in `repository.full_name`, used in `PushHandler#process` via `Handler#stacks` → `Repository.from_github_repo_name`).

Code path:
- `Shipit::WebhooksController#repository_owner` [1](#0-0)  reads `params.dig('repository','owner','login')` and falls back to `params.dig('organization','login')` if the former is absent — both attacker-controlled fields in the raw JSON body.
- `verify_signature` uses that value to select the GitHub App/secret: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that organization: `return true unless webhook_secret` [3](#0-2) .
- On success, `create` dispatches the *entire raw payload* to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `Handler#stacks` resolves the target repository independently, from `payload.dig('repository','full_name')`, with no reference to `repository_owner`: [5](#0-4) .
- `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch: [6](#0-5) .

Exploit request: attacker (no Shipit credentials, no GitHub App secret) sends `POST /webhooks` with `X-Github-Event: push` and body:
```json
{
  "repository": { "full_name": "victim-org/victim-repo" },
  "organization": { "login": "org-with-no-secret" },
  "ref": "refs/heads/master",
  "after": "attacker-chosen-sha"
}
```
`repository.owner.login` is omitted, so `repository_owner` falls back to `organization.login` = `org-with-no-secret`. `verify_signature` looks up that org's `GitHubApp`; because it has no `webhook_secret` configured, `verify_webhook_signature` returns `true` regardless of the (absent or bogus) `X-Hub-Signature` header — no cryptographic check occurs at all. The request passes verification entirely on the basis of an org that has nothing to do with the target repository. `PushHandler` then resolves `victim-org/victim-repo` from `repository.full_name` and calls `stack.sync_github(expected_head_sha: "attacker-chosen-sha")` on a stack the attacker never authenticated against.

None of the listed guards intervene: `drop_unhandled_event` only checks the event type is registered; `ExplicitParameters` (`PushHandler.params`) only requires `ref` and `after` to be present, it does not constrain `repository.full_name` vs `repository.owner.login`; `Repository.from_github_repo_name` performs no relation to the verifying org; `Stack#sync_github` has no caller-identity check.

### Impact Explanation
A forged webhook against one organization's (misconfigured, secret-less) GitHub App configuration can force `sync_github` with an attacker-chosen `expected_head_sha` on a stack belonging to an entirely different organization/repository. This is a cross-tenant write: a request that only "authenticates" as `org-with-no-secret` mutates state owned by `victim-org`. This matches the Critical category "a payload for one repository mutating another's stack." The blast radius extends to **every** repository/stack tracked by Shipit as long as at least one configured GitHub organization anywhere in the installation lacks a `webhook_secret` — that single weak link neutralizes verification for the entire multi-tenant webhook endpoint, since `repository_owner` is fully attacker-selectable per request.

### Likelihood Explanation
Preconditions: (1) Shipit must be configured with at least one organization (`org-with-no-secret`) that has no `webhook_secret` set — a realistic, non-exotic misconfiguration, especially in multi-org Shipit deployments where operators may forget to set a secret on a legacy or low-traffic org entry; (2) the target `victim-org/victim-repo` Stack must already exist and be tracked in Shipit with a matching branch. No GitHub access, Shipit session, or API token is needed — the endpoint is unauthenticated by design (webhooks) and relies solely on signature verification, which is bypassed here. Attack cost is a single crafted HTTP POST, fully repeatable against any tracked stack.

### Recommendation
Verify the webhook signature using the secret associated with the *same* organization/repository that will actually be acted upon (i.e., derive both `repository_owner` for verification and the repository used for `Repository.from_github_repo_name` from the same, single trusted field — `repository.full_name`'s owner segment — and reject the request if `repository.owner.login` is missing or does not match). Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when no `webhook_secret` is configured; a missing secret should be treated as a hard misconfiguration that fails closed (reject the webhook) rather than fail open.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Configure two orgs in test secrets: `org-with-no-secret` (no `webhook_secret` key) and `victim-org` (has a `webhook_secret`, or simply exists as a tracked `Shipit::Stack` owner).
2. Create `shipit_repository(owner: 'victim-org', name: 'victim-repo')` with a `Stack` on branch `master`.
3. `stack.expects(:sync_github).never` (or `.with(expected_head_sha: anything)` set to never fire) as a mock expectation set up before the request.
4. `request.headers['X-Github-Event'] = 'push'`; POST body:
```ruby
{
  repository: { full_name: 'victim-org/victim-repo' },
  organization: { login: 'org-with-no-secret' },
  ref: 'refs/heads/master',
  after: 'deadbeef' * 5
}.to_json
```
   with no valid `X-Hub-Signature` header (or a garbage one).
5. Assert the equality-before-mutation invariant: `repository_owner` resolved by the controller (`org-with-no-secret`) must equal the owning org of the stack acted upon (`victim-org`) — assert they differ, then assert `stack.sync_github` was never called and/or `assert_response :unprocessable_entity` is NOT what happens (currently it returns `:ok` because verification passes), demonstrating the broken binding: verification succeeds (`head(:ok)`) while `sync_github` still fires on `victim-org`'s stack despite the two identifiers diverging.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
