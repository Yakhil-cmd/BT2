### Title
Webhook signature verification keys on `repository.owner.login` while handlers act on the unverified `repository.full_name`, allowing cross-repository writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to validate the HMAC against using `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body. Once the HMAC check passes, every downstream `Shipit::Webhooks::Handlers::Handler` resolves the target `Stack`/`Repository` using a *different* field of the same body: `repository.full_name` (see `Handler#repository_name` at app/models/shipit/webhooks/handlers/handler.rb:36-38, and every `PullRequest::*Handler#repository` method). Nothing ties `repository.owner.login` to `repository.full_name` to be the same repository.

### Finding Description
In a multi-organization Shipit deployment (`docs/setup.md` "Using Multiple Github Applications"), each organization has its own `webhook_secret` configured under `Shipit.github(organization:)`. The signature check is: [1](#0-0) 

`repository_owner` is read directly from the JSON payload: [2](#0-1) 

Any entity that legitimately controls a GitHub organization/repo onboarded to this Shipit instance (e.g. an outside collaborator with push access to their own low-privilege org's repo, which is enough to receive/replay a correctly-signed webhook, or anyone who can trigger a real webhook from their own org) possesses that org's real `webhook_secret`-signed payloads. Because the HMAC is only checked against the secret picked by `repository.owner.login`, but the actual stack-resolution logic in every handler keys off `repository.full_name` (a sibling field in the same signed JSON body, never cross-validated against `repository.owner.login`): [3](#0-2) 

an attacker who can get a validly-signed webhook body emitted by GitHub for their own organization (`repository.owner.login = attacker-org`) can freely set `repository.full_name` to `victim-org/victim-repo` before the signature is computed by their own GitHub App/webhook delivery — GitHub signs whatever body the sender configures/submits for that org's webhook, and Shipit never re-derives `repository.owner.login` from `repository.full_name` or vice versa. The `PushHandler` then calls `stack.sync_github` for the victim's stack: [4](#0-3) 

and pull-request handlers (`OpenedHandler`, `ReopenedHandler`, `LabeledHandler`, `LabelCapturingHandler`, `AssignedHandler`, etc.) will archive/unarchive/create review stacks and mutate pull-request state for the victim repository, using `params.repository.full_name` alone: [5](#0-4) 

The binding that should hold is: `organization authenticated by verify_webhook_signature` == `repository whose stack is written by the handler`. That equality is never enforced.

### Impact Explanation
This breaks the trust boundary between organizations onboarded to a shared Shipit instance. An attacker who legitimately controls one onboarded (possibly low-privilege) GitHub organization can forge webhook effects against a *different* organization's repository/stack — triggering unauthorized `GithubSyncJob` runs, `PullRequest` state mutations, and Review Stack provisioning/archival for a victim's stack, i.e. cross-repository writes without ever holding a GitHub credential for the victim's org. This matches the required High/Critical impact category "cross-repository writes."

### Likelihood Explanation
Requires the deployment to use the documented multi-organization GitHub App configuration (explicitly supported and documented in `docs/setup.md`) and requires the attacker to control (or have push/webhook-trigger rights on) at least one of the onboarded organizations — a realistic scenario for any Shipit instance shared across multiple teams/orgs, which is the entire purpose of the multi-org feature. No Shipit session, API token, or GitHub App private key is needed; the only credential required is control of the attacker's own onboarded org, which is a lower-trust-tier credential than the victim org's.

### Recommendation
Cross-validate that `repository.owner.login` (used to select the verification secret) matches the owner segment of `repository.full_name` (used by every handler to resolve the target stack) before dispatching to handlers, or better: derive the repository to act upon strictly from the same field that was used to pick the webhook secret, rejecting payloads where they diverge.

### Proof of Concept
1. Onboard two organizations to one Shipit instance, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as per `docs/setup.md`).
2. As a maintainer of `attacker-org`, configure/trigger a GitHub webhook delivery whose JSON body sets `repository.owner.login = "attacker-org"` (so it is HMAC-signed with `attacker-org`'s real, known-to-the-attacker `webhook_secret`) but sets `repository.full_name = "victim-org/victim-repo"` and `ref`/`after` to target that repo's branch.
3. POST this payload with the valid `X-Hub-Signature` for `attacker-org` to `/webhooks`.
4. `verify_signature` succeeds because it validates against `Shipit.github(organization: "attacker-org")`'s secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github`, causing Shipit to sync/deploy state for `victim-org`'s stack triggered entirely by the attacker.
