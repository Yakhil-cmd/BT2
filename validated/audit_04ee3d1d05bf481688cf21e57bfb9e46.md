### Title
Webhook signature verification is keyed by an attacker-controlled `repository_owner` field that is decoupled from the repository/stack actually mutated by the event handlers - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization secret to validate the `X-Hub-Signature` against using `repository_owner`, a value read directly out of the unauthenticated JSON body. Once verification passes (or is skipped because that organization has no `webhook_secret` configured), the `create` action dispatches the very same untrusted payload to handlers (e.g. `PushHandler`) that resolve target stacks from a *different* payload field (`repository.full_name` / `ref`). Nothing binds the organization whose credential gated the request to the repository whose stacks get mutated.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  head(422) unless verified
...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) [2](#0-1) 

`repository_owner` is taken from the raw request body before any authenticity check is performed, so it is fully attacker controlled. It is used only to pick which `GithubApp`/secret to validate against: [3](#0-2) 
Note the fallback: `return true unless webhook_secret` — if the organization resolved from the attacker-supplied `repository_owner` happens to be configured without a `webhook_secret`, signature verification is bypassed entirely and `verified` is `true` for any payload/signature pair.

After this gate, `create` forwards the *whole, still-unauthenticated* JSON body to the registered handlers: [4](#0-3) 
Handlers such as `PushHandler` act on a completely different field of the same body — `ref`/`after` — and resolve target stacks independently of `repository_owner`: [5](#0-4) 

Because the field used to select the *verifying* credential (`repository.owner.login`) and the field(s) used to select the *acted-upon* stack (`repository.full_name`, `branch`, `sha`) are independent, attacker-controlled JSON keys, the signature (or its absence for an org missing a secret) never actually authenticates the repository that ends up being mutated. The equality the code implicitly relies on — "organization whose secret verified this request" == "organization owning the repository/stack the handler updates" — is never checked and is not enforced by the HMAC, because the HMAC covers the raw body, not a specific claim that `repository_owner` matches the object the handlers operate on.

### Impact Explanation
For any Shipit organization onboarded without a `webhook_secret` (an explicitly optional config key per `GithubApp#initialize`, `@webhook_secret = @config[:webhook_secret].presence`), an unauthenticated attacker can submit a forged `push`/`status`/`check_suite` webhook naming that organization as `repository.owner.login` (to sail through/skip signature verification) while setting `repository.full_name` to point at a stack under a *different, unrelated* organization. Handlers like `PushHandler` will then act on that unrelated stack (`stack.sync_github(expected_head_sha: params.after)`), forcing resynchronization against an attacker-chosen `after` SHA and branch state without any legitimate GitHub-originated event. This can trigger downstream stack state changes and continuous-delivery job scheduling for repositories the attacker has no privileges over.

### Likelihood Explanation
The main precondition is a single onboarded organization lacking `webhook_secret` — an allowed/likely misconfiguration since the field is optional rather than enforced as mandatory across all configured GitHub Apps. No credentials, session, or GitHub write access are required by the attacker; the endpoint is public per `skip_before_action :verify_authenticity_token`.

### Recommendation
Bind the identity used for signature verification to the identity of the object being mutated: verify the signature using the secret for the *actual* repository owner that handlers will act on, and additionally assert inside each handler that `params.dig('repository','owner','login')` matches the resolved stack's repository owner before mutating any state. Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is unset for a resolvable organization; require a `webhook_secret` for every configured GitHub App, or reject the request instead of treating missing configuration as "verified."

### Proof of Concept
1. Identify (or assume) that Shipit is configured with at least one organization `org-no-secret` that has no `webhook_secret` set, and a victim stack `victim-org/victim-repo`.
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": { "owner": { "login": "org-no-secret" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-no-secret")`, whose `verify_webhook_signature` short-circuits to `true` because `webhook_secret` is blank — no valid `X-Hub-Signature` header is needed.
4. `create` dispatches the payload to `PushHandler`, which looks up stacks for `victim-org/victim-repo`'s branch `main` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, mutating a stack the attacker never authenticated against.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
