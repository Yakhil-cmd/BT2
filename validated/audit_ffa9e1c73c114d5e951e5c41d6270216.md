Based on my investigation, I found a genuine analog of this bug class in `network.js`'s light-vendor request handlers.

### Title
Missing per-connection throttle on `light/get_aa_response_chain` allows unbounded recursive DB traversal despite an identical protection existing for `light/get_history` - (File: `network.js`)

### Summary
The fix pattern in the CVE is: one expensive endpoint (`/fork`) received a rate limiter while a sibling endpoint (`/duplicate`) performing the same class of expensive operation did not. The ocore analog is the `light/get_history` handler, which was hardened with a `largeHistoryTags` memoization guard to stop a peer from repeatedly triggering the same expensive proof-building work, while the structurally similar `light/get_aa_response_chain` handler — which does its own unbounded, recursive DB-driven traversal — has no equivalent protection.

### Finding Description
`light/get_history` in `network.js` wraps `light.prepareHistory` with a guard: if a request previously came back as "too large", the same `tag` is remembered in `largeHistoryTags` and immediately rejected without re-doing the expensive work: [1](#0-0) 

`light.prepareHistory` itself is bounded by `MAX_HISTORY_ITEMS` and mutex-serialized: [2](#0-1) [3](#0-2) 

By contrast, `light/get_aa_response_chain` walks a chain of `aa_responses` recursively via `addAAResponse`, issuing one DB query per hop with no upper bound on chain depth/length and no `largeHistoryTags`-style memoization to stop a client from re-issuing the same expensive chain-walk request repeatedly: [4](#0-3) 

An unprivileged light client (an "authenticated user" analog — any peer allowed to send light requests) can pick a `trigger_unit` belonging to a long AA response chain (which regularly occurs with chained/bouncing AA calls) and send `light/get_aa_response_chain` requests for it repeatedly and in parallel, forcing the node to redo the full recursive traversal each time, with no rate limiter or cached-result short-circuit comparable to the one added for `light/get_history`.

### Impact Explanation
Repeated, parallel invocation of this unbounded recursive query against long-lived AA response chains consumes CPU/DB connection resources on the serving full node. Because there is no per-tag/per-connection memoization or limiter analogous to `largeHistoryTags`, a single peer can force the same expensive traversal to be repeated indefinitely, degrading the node's ability to serve other light clients and process new units — the same "resource exhaustion via missing rate limiter on an already-known-expensive sibling endpoint" pattern as the original CVE.

### Likelihood Explanation
Any peer capable of sending light-vendor requests (the normal operating mode for light wallets) can trigger this without special privileges; AA response chains of meaningful length are common in production usage of chained/bouncing AAs, making the precondition easy to satisfy.

### Recommendation
Apply the same style of protection used for `light/get_history` to `light/get_aa_response_chain` (and any other unbounded chain-following light handlers): cap the maximum chain depth/number of DB queries per request, and add a per-tag/per-peer memoization or rate limiter so that a request already known to be large/expensive is rejected immediately on repeat instead of being fully re-executed.

### Proof of Concept
1. As a light client, submit an AA trigger that starts a long response chain (e.g., chained AA-to-AA payments causing multiple bounces/responses), or locate an existing long chain's `trigger_unit`.
2. Send repeated/parallel `light/get_aa_response_chain` requests to the same full node with that `trigger_unit`, exploiting `addAAResponse`'s per-hop DB query with no depth limit and no repeat-request memoization (contrast with the `largeHistoryTags` check gating `light/get_history` at `network.js:3641`).
3. Observe that unlike `light/get_history`, subsequent identical requests are not short-circuited, forcing the node to redo the full chain traversal each time, consuming CPU/DB resources disproportionate to the request cost.

Note: I was unable to fully confirm the real-world maximum length of AA response chains that occur in practice (this depends on runtime AA usage patterns not visible in static code), so the severity estimate assumes chains of non-trivial length are achievable, consistent with the chained/bouncing AA feature this endpoint exists to serve.
