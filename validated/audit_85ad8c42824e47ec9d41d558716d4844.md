## Title
Dust-Triggered Drain of Accumulated AA Balance via Unrestricted "Send-All" Payment Output - (File: `aa_composer.js`)

## Summary
Same bug class as the Gladius Reactor issue: a contract/AA refunds its *entire* leftover balance to whoever currently interacts with it, without distinguishing funds that belong to the current caller from funds accumulated from unrelated prior senders. In ocore, an Autonomous Agent (AA) response can contain a "send-all" output (`{address: ..., amount: undefined}`), which the core AA composer fills in with the AA's *entire* spendable balance at response time, not merely the amount attributable to the triggering unit. If an AA author gates this send-all output behind a weak/dust-satisfiable condition (a pattern the ocore repo itself ships as a reference template), any unprivileged trigger sender who barely satisfies that condition can trigger the AA and walk away with all bytes/asset balance the AA has accumulated from other, unrelated senders.

## Finding Description
The send-all mechanism is implemented in `completePaymentPayload()` inside `aa_composer.js`'s `sendUnit()`. When a payment message contains an output with `amount === undefined`, the composer treats it specially: [1](#0-0) 

The composer then iterates over ALL unspent outputs currently sitting at the AA's address — both confirmed and unconfirmed — regardless of which trigger unit originally deposited them, and assigns the full leftover `change_amount` to the send-all output: [2](#0-1) [3](#0-2) 

This is architecturally identical to `BaseGladiusReactor.sol`'s refund logic: "if `address(this).balance > 0`, send it all to `msg.sender`" — the ocore analog sends the AA's *entire remaining spendable balance* (built from the sum of every prior sender's leftover output at that address) to whichever `trigger.address` satisfies the AA's `if` condition for that response.

The AA definition language explicitly allows and validates this send-all output form (`amount` omitted) as a first-class feature: [4](#0-3) 

Crucially, nothing in the core protocol requires the AA's `if` condition gating a send-all output to be proportional to, or derived from, the current trigger's own contribution. The ocore project ships exactly this footgun pattern as an official example template, `test/samples/send_all.oscript`: [5](#0-4) 

Here the condition is only `trigger.output[[asset=base]] >= 1e6` — a fixed, dust-sized threshold unrelated to the AA's accumulated balance. Any address that sends the minimum `1e6` bytes triggers a response that hands over the AA's *entire* current byte balance (whatever it has accumulated from previous unrelated triggers/deposits/change outputs), not just the sender's own `1e6`. This mirrors the Gladius PoC precisely: pay a small, fixed amount to satisfy a superficial check, and receive the pool of funds that rightfully belongs to other parties.

The related `test/samples/bounce_half_of_balance.oscript` sample shows the same balance-based (not trigger-based) computation pattern is officially encouraged (`round(balance[base]/2)`), reinforcing that "pay whoever triggers next based on `balance[...]`/send-all rather than on their own contribution" is a first-party, documented idiom in this codebase rather than a one-off scripting mistake: [6](#0-5) 

## Impact Explanation
Any AA that uses this documented send-all/balance-based idiom — gating the payout on a fixed, easily-satisfied trigger condition instead of tracking per-sender entitlements in state variables — allows an unprivileged trigger sender to drain funds accumulated from unrelated previous senders by paying only the minimal qualifying amount. This is a direct "AA fund loss" for the legitimate depositors whose bytes/asset ended up sitting in the AA's balance (e.g., overpayments, dust change left behind by earlier responses, or funds sent by other users awaiting a later payout), exactly as legitimate fillers lost their expected ETH refund in the Gladius Reactor case.

## Likelihood Explanation
Likelihood is high for any AA deployed using the pattern the ocore repo itself documents and tests (`send_all.oscript`, `bounce_half_of_balance.oscript`). Triggering it requires only posting a single unit with the minimal qualifying `trigger.output[[asset=base]]` amount — something any unprivileged unit poster can do. No special privilege, timing, or race condition is needed; the composer's send-all logic unconditionally sweeps the AA's whole current balance into the output whenever the guarding `if` condition is satisfied.

## Recommendation
- In `aa_composer.js`, when constructing a send-all output, consider warning/flagging (at validation time via `aa_validation.js`) AA definitions whose send-all output's containing case condition does not reference variables that track per-sender/per-trigger entitlement (e.g., recommend requiring conditions based on stored state rather than only on the current trigger's own output amount).
- Document explicitly, alongside `send_all.oscript` and `bounce_half_of_balance.oscript`, that gating a send-all/balance-based payout on a low, fixed threshold is unsafe if the AA's balance can include funds belonging to parties other than the current trigger sender; AA authors should track individual balances via state vars (`var[...]`) and pay out only the amount attributable to `trigger.address`, mirroring how `fundraising_proxy.oscript`'s refund case computes `amount` strictly from `trigger.output[[asset=$asset]]` rather than from `balance[...]`.

## Proof of Concept
1. Deploy the reference AA definition from `test/samples/send_all.oscript` (or any AA following the same idiom):
   ```
   {
       messages: { cases: [
           { if: `{trigger.output[[asset=base]] >= 1e6}`,
             messages: [{ app:'payment', payload:{ asset:'base', outputs:[{address:'{trigger.address}'}] } }] },
           { messages: [...] }
       ]}
   }
   ```
2. Multiple unrelated users interact with the AA over time (e.g., via the second case, or via overpayment/rounding), each leaving small leftover byte outputs at the AA's address that accumulate in its spendable balance.
3. An unprivileged attacker sends a single unit with exactly `1e6` bytes to the AA (the minimal amount satisfying the first case's condition).
4. `aa_composer.js`'s `sendUnit()` → `completePaymentPayload()` builds the response's send-all output using `readStableOutputs`/`readUnstableOutputsSentByAAs`, which pulls in *every* unspent output at the AA address (not just the attacker's `1e6`), and assigns the full `change_amount` — the AA's entire accumulated balance — to the attacker's `trigger.address` output.
5. The attacker receives far more than the `1e6` bytes they contributed; the difference is drained from balances left behind by unrelated prior senders, analogous to the swapper draining the Gladius Reactor's leftover ETH with a dust-amount same-token swap.
