Confirmed root-cause path: `WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to verify against based on `repository_owner`, which is read directly from the unauthenticated JSON body (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), before any signature check occurs. [1](#0-0) [2](#0-1) 

However, the field actually used afterward by the event handlers to resolve which `Stack`/`Repository` the event acts on is `repository.full_name`, a *different* field from the one used to pick the verification secret (`repository.owner.login`). [3](#0-2) [4](#0-3) 

`GitHubApp#verify_webhook_signature` unconditionally returns `true` whenever `webhook_secret` is blank for the selected org config, and per-organization config (multi-org `github:` block) explicitly supports independently blank `webhook_secret` per org, as shown in the docs/fixtures. [5](#0-4) [6](#0-5) 

This is the exact "GitHub App organization authenticated vs. repository actually written" trust binding named in the rules. In a multi-org deployment, if any one configured organization has a blank/unset `webhook_secret` (a supported, documented configuration — see `docs/setup.md` and `template.rb` where `webhook_secret` defaults to empty), an unauthenticated attacker can craft a webhook body where `repository.owner.login`/`organization.login` names the org with the blank secret (satisfying `verify_signature`, which always returns `true` for that org) while `repository.full_name` names a *different* repository belonging to a different, properly-secreted organization whose stacks are tracked in Shipit. Because `verify_signature` never checks that `repository.owner.login` is consistent with `repository.full_name`, and the handler layer (`Handler#repository_name`, `PushHandler#process`) trusts `full_name` independently, the forged payload passes signature verification under the blank-secret org's identity but is then dispatched against the victim org's stack.

This breaks the binding: `organization authenticated (repository.owner.login) == repository actually written (repository.full_name)`. Concretely, for the `push` event this lets an attacker enqueue `GithubSyncJob`/`stack.sync_github` for an arbitrary tracked stack with an attacker-chosen `expected_head_sha`/ref update by simply naming that stack's `full_name` in the forged body, without ever knowing the victim org's real webhook secret — provided the deployment has at least one org configured with a blank webhook secret (a state the codebase itself documents/ships as default, e.g., `template.rb` lines 68-74 and `docs/setup.md` webhook_secret optionality).

I could not fully verify from static reading alone whether every event handler consistently derives its target purely from `full_name` (some may cross-reference `organization.login` as well), so the severity depends on which handler is invoked; `push` and other handlers extending `Handler#stacks`/`repository_name` are confirmed to only use `full_name`.

### Title
Webhook signature check keyed on unverified `repository.owner.login`, decoupled from the `repository.full_name` actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App/org config (and its `webhook_secret`) using an attacker-supplied, pre-signature-check field (`repository.owner.login` / `organization.login`), while the event handlers act on a different field, `repository.full_name`. Combined with `GitHubApp#verify_webhook_signature` treating a blank `webhook_secret` as always-valid, this lets an attacker forge events against any tracked stack as long as one configured org in a multi-org deployment has no webhook secret set.

### Finding Description
`verify_signature` computes `repository_owner` from the raw, unauthenticated JSON body and uses it to select which org's `webhook_secret` to verify the `X-Hub-Signature` against. [7](#0-6) 
`GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank. [5](#0-4) 
Downstream, `Handler#repository_name`/`#stacks` and handlers such as `PushHandler#process` resolve the target `Stack` purely from `repository.full_name`, never cross-checking it against `repository.owner.login`. [3](#0-2) [8](#0-7) 
Thus the value that is "authenticated" (the owner login tied to a specific org's secret) is not the value that is actually acted upon (`full_name`), breaking the equality `organization authenticated == repository written`.

### Impact Explanation
If any org in a multi-org `secrets.github` config has a blank `webhook_secret` (a supported/documented state), an unauthenticated attacker can send a forged `push` (or other) webhook naming that blank-secret org in `repository.owner.login` but naming a fully different, victim-org repository in `repository.full_name`. This passes `verify_signature` and results in an unauthorized `GithubSyncJob`/stack sync being enqueued for the victim's stack — an unauthorized action on a tracked repository without any valid credential for that repository's org, matching the "unauthorized deploy/rollback" class of High/Critical impact.

### Likelihood Explanation
Requires a Shipit deployment configured with more than one GitHub organization where at least one has no `webhook_secret` set — a state the project's own setup docs and generator template present as a normal/default configuration, so this is plausible in real deployments rather than purely theoretical.

### Recommendation
Bind signature verification to the same field the handlers act on: verify using the org derived from `repository.full_name`'s owner segment (or equivalently, reject the request if `repository.owner.login` and the owner segment of `full_name` disagree). Additionally, consider requiring `webhook_secret` to be present for all configured organizations, or refusing verification (rather than defaulting to `true`) when it is blank.

### Proof of Concept
1. Configure Shipit with two orgs: `OrgA` (blank `webhook_secret`) and `OrgB` (secret set, has a tracked stack `OrgB/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` needed, and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. `repository_owner` resolves to `"OrgA"`; `verify_webhook_signature` for `OrgA` returns `true` unconditionally (blank secret).
4. `PushHandler` resolves `stacks` via `repository.full_name = "OrgB/victim-repo"` and enqueues `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` for `OrgB`'s stack, without any credential for `OrgB`.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
