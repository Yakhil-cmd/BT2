### Title
`TransferStxOp` binds `sender` to an attacker-chosen `PreStxOp.output` field with no cryptographic proof of ownership - ([File: stackslib/src/chainstate/burn/operations/transfer_stx.rs])

### Summary
`TransferStxOp::check()` at lines 217-227 only rejects `self.sender == self.recipient` and a zero-value transfer, but the `sender` field itself is never cryptographically bound to any Stacks-level signature or to the Bitcoin key that authorizes the accompanying burnchain transaction. An attacker can craft their own `PreStxOp` + `TransferStxOp` pair, entirely from Bitcoin inputs they own, naming an arbitrary victim `StacksAddress` as `sender`, and drain that victim's STX balance to an address they control.

### Finding Description
The broken equality is: *STX debited from `sender` in `stx_transfer_consolidated`* should equal *STX owned by the entity that cryptographically authorized this specific transfer*. This equality is violated because `sender` is populated purely from `PreStxOp.output`, which is decoded from an arbitrary Bitcoin output address chosen by whoever crafts the `PreStxOp` transaction: [1](#0-0) 

There is no check anywhere that this `output` address corresponds to the hash160 of the public key that signs the `PreStxOp`'s own inputs. The follow-on `TransferStxOp` only requires that its first input spend `vout=1` of the referenced `PreStxOp` transaction: [2](#0-1) 

and the burnchain classifier simply forwards `pre_stx.output` as the `sender` for the resulting `TransferStxOp`, with no additional validation: [3](#0-2) 

`TransferStxOp::check()` performs only trivial checks (non-zero amount, sender != recipient): [4](#0-3) 

The op is then applied unconditionally via `run_stx_transfer(sender, recipient, transfered_ustx, ...)` in block processing, which directly debits `sender`'s balance with no Stacks-level signature check (these are "system" burn-chain-sourced STX transfers, not ordinary signed Stacks transactions): [5](#0-4) 

**Attacker's exact call:** Using only their own Bitcoin UTXOs, the attacker (an "unprivileged" party per the threat model, which explicitly permits "craft burnchain stacking ops from their own Bitcoin inputs") constructs:
1. A `PreStxOp` Bitcoin transaction whose output[0] address decodes to the *victim's* `StacksAddress` (the attacker only needs the victim's known public address/hash160, not their private key), and output[1] paying back to an address the attacker controls.
2. A `TransferStxOp` Bitcoin transaction whose first input spends output[1] of the crafted `PreStxOp` (signed with the attacker's own key, since they control that output), naming their own address as `recipient` and specifying `transfered_ustx` up to the victim's full balance.

Since `TransferStxOp::check()` never verifies that `sender` corresponds to any signature or private key the transaction submitter controls, and `run_stx_transfer` performs the debit unconditionally, the victim's STX balance is transferred to the attacker with no authorization from the victim.

Existing guards do not prevent this: `check()` only guards against self-send and zero amounts; the burnchain classifier (`classify_transaction`) only verifies the UTXO-spend linkage (`vout == 1`) between `PreStxOp` and `TransferStxOp`, not the semantic content of `PreStxOp.output`; and Clarity's normal `stx_transfer_consolidated` sender-authentication (`Some(from) != invoke_ctx.sender.as_ref()`) is bypassed for these system-level burn ops since `invoke_ctx.sender` is set directly to the op's `sender` field by the calling code, not derived from any actual signer.

### Impact Explanation
Any Stacks account's unlocked STX balance can be stolen by an unprivileged attacker who only needs to know the victim's `StacksAddress` and control their own Bitcoin funds to pay for the two-transaction sequence. This is theft of the victim's free/unlocked STX balance, matching the Critical severity category ("theft ... of locked STX"). It is fully repeatable against any address with a nonzero balance, for the cost of two low-value Bitcoin transactions.

### Likelihood Explanation
No special chain state, cycle phase, or membership status is required — this works at any burn height where `TransferStx` ops are accepted (Epoch 2.05+). The attacker's only cost is Bitcoin transaction fees for two small transactions; they do not need to compromise the victim's Stacks or Bitcoin private key. The attack is fully attacker-initiated, deterministic, and repeatable against any target address with nonzero unlocked STX.

### Recommendation
Bind `PreStxOp.output` (and therefore the resulting op's `sender`) cryptographically to the Bitcoin public key(s) that sign the `PreStxOp`'s own inputs (e.g., require `output`'s hash160 to equal the hash160 derived from the signing key of input 0), so that only the party who actually controls the corresponding Stacks/Bitcoin key can name themselves as `sender` in a `TransferStxOp`, `StackStxOp`, `DelegateStxOp`, or `VoteForAggregateKeyOp`.

### Proof of Concept
Rust integration test plan (mirroring `stx_transfer_btc_integration_test` in `stacks-node/src/tests/neon_integrations.rs`):
1. Fund `victim_addr` (a `StacksAddress` whose private key the test/attacker does NOT possess) with an initial balance via `conf.initial_balances`.
2. As the attacker, using only attacker-controlled Bitcoin UTXOs and `attacker_sk`, submit a `PreStxOp` with `output: victim_addr.clone()`.
3. Using `attacker_sk` (not any key related to `victim_addr`), submit a `TransferStxOp` spending `vout=1` of the crafted `PreStxOp`, with `recipient: attacker_addr`, `transfered_ustx: victim_full_balance`.
4. Mine blocks until the ops are processed.
5. Assert `get_balance(&http_origin, &victim_addr) == 0` (or reduced) and `get_balance(&http_origin, &attacker_addr) == victim_full_balance + attacker's own balance`, proving STX moved out of `victim_addr` with no signature ever produced by `victim_addr`'s private key — the equality "STX debited from `sender`" == "STX owned by the party that authorized this transfer" fails before vs. after: before, victim owns the balance and never signed anything; after, attacker holds it.

        if self.transfered_ustx == 0 {

            return Err(op_error::TransferStxMustBePositive);
        }
        if self.sender == self.recipient {

            return Err(op_error::TransferStxSelfSend);
