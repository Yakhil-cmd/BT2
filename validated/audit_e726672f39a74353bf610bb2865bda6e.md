## Finding: Confirmed Critical Vulnerability

### Title
Any signed AssetHub Polkadot user can forge the trusted "AssetHub root" XCM origin on Bulletin and alias into any location via `AliasOrigin` - (File: system-parachains/bulletin/bulletin-polkadot/src/xcm_config.rs)

### Summary
`TrustedAliasers` on Bulletin includes `AliasOriginRootUsingFilter<AssetHubLocation, Everything>`, which grants unconditional aliasing power to *any* target location whenever the incoming XCM origin equals the bare `AssetHubLocation` (`Location::new(1, X1(Parachain(1000)))`). This origin is not privilege-checked on the receiving side beyond the sending-parachain identity: it is derived purely from the HRMP/XCMP channel the message arrived on, not from whatever internal origin (root, governance, or ordinary signed user) triggered the send on Asset Hub.

### Finding Description
Bulletin's alias rules are defined at [1](#0-0) , where `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` allows the exact origin `AssetHubLocation` to alias into *any* target — confirmed by the emulated test that shows this origin aliasing into arbitrary parachains, AccountId32 locations, pallet instances, and even global-consensus locations: [2](#0-1) .

The `Barrier` on Bulletin permits any top-level paid execution regardless of origin via `AllowTopLevelPaidExecutionFrom<Everything>` [3](#0-2) , so a message merely needs to pay its own execution fee to reach the `AliasOrigin` instruction; there's no additional origin-based gating that would stop a non-governance sender.

Critically, on Asset Hub Polkadot, `pallet_xcm::send` is permissioned via `SendXcmOrigin = EnsureXcmOrigin<RuntimeOrigin, LocalPalletOrSignedOriginToLocation>` [4](#0-3) , and `LocalPalletOrSignedOriginToLocation` includes `SignedToAccountId32<RuntimeOrigin, AccountId, RelayNetwork>` as a fallback converter [5](#0-4) . This means **any ordinary signed account** on Asset Hub Polkadot can call `pallet_xcm::send(dest=Bulletin, message=<arbitrary raw XCM>)`. `pallet_xcm::send` forwards the user-supplied program unmodified through the `XcmRouter`/`XcmpQueue` to the destination — it does not prepend any origin descriptor reflecting the caller's on-chain privilege.

On the receiving side (Bulletin), the message is processed via `cumulus_pallet_xcmp_queue`/`pallet_message_queue`, and the executor origin for any inbound HRMP message from a sibling parachain is always derived purely from the channel/para-id — i.e., exactly `Location::new(1, X1(Parachain(1000)))`, regardless of whether the sender on Asset Hub was root, a governance body, or a plain signed account. This is fundamental to how sibling-to-sibling XCMP messaging assigns origins; there is no mechanism carrying the AssetHub-internal privilege level of the sender into the receiving chain's origin.

Consequently, an attacker with a signed AssetHub account can submit an XCM program (paying its own fees) containing an `AliasOrigin(target)` instruction where `target` is, e.g., a victim's account or the Bulletin treasury account. Since the executor sees origin == `AssetHubLocation` and `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` unconditionally allows any target, the `Aliasers::contains` check passes, and subsequent instructions in the same program execute with the origin aliased to the victim/treasury location — enabling asset withdrawal/transfer as that account.

### Impact Explanation
Full privilege escalation on Bulletin: an unprivileged Asset Hub user can alias into any account (including the Treasury account derived from `TREASURY_PALLET_ID`, and any user's account) and then issue further instructions (e.g. `WithdrawAsset`/`TransferAsset`/`Transact`) acting as that account, resulting in theft of funds or arbitrary state manipulation.

### Likelihood Explanation
Fully feasible with only a signed extrinsic and enough DOT to cover Bulletin execution fees. No governance, no special key, no bug in message-passing infrastructure required — this exploits the intended `pallet_xcm::send` capability that every ordinary signed AssetHub account already has, combined with the design assumption (embedded across Bulletin, Collectives, Coretime, People, Encointer via the same `AliasOriginRootUsingFilter<AssetHubLocation, Everything>` pattern) that "origin == AssetHubLocation" implies AssetHub-root-level trust.

### Recommendation
Do not treat the bare sibling-chain location as equivalent to that chain's root/governance for aliasing purposes. Either: (1) replace `Everything` with a narrow, explicit filter of pre-approved target locations for the `AssetHubLocation` aliaser (mirroring the narrow, rank-gated `FellowshipArchitectsAliases` pattern used elsewhere), or (2) require that messages relied upon for this alias trust arrive via a channel/mechanism that actually encodes AssetHub's internal governance origin (e.g., a dedicated `Transact`-only governance path, `UniversalOrigin`, or a pallet-level authorization list) instead of the raw sending-parachain location.

### Proof of Concept
xcm-emulator test plan (Bulletin + AssetHubPolkadot):
1. In `AssetHubPolkadot::execute_with`, submit `PolkadotXcm::send(RawOrigin::Signed(attacker), dest=Bulletin_location, message=Xcm(vec![WithdrawAsset(fee), BuyExecution{..}, AliasOrigin(victim_or_treasury_location), WithdrawAsset(victim_assets), DepositAsset{beneficiary: attacker_location}]))` from a plain, non-root, non-governance `attacker` account.
2. Process the message on `BulletinPolkadot::execute_with`.
3. Assert: attacker's balance on Bulletin increases by the victim/treasury's withdrawn amount, and/or assert `<XcmConfig as xcm_executor::Config>::Aliasers::contains(&AssetHubLocation, &victim_location)` returns `true` even though the triggering extrinsic was `Signed(attacker)`, not `Root`.
4. Contrast with a second assertion that a signed extrinsic on Asset Hub Polkadot can never be blocked from producing this exact derived origin at Bulletin (i.e., there's no barrier/origin-converter step preventing it), disproving the assumed invariant "only genuine AH pallet/root dispatch can hit AssetHubLocation as origin."
