### Title
Address-definition `timestamp` op is evaluated against attacker-chosen stale `last_ball_timestamp`, not real wall-clock time - ([File: definition.js])

### Summary
The `timestamp` operator usable in address definitions is not evaluated against the actual time a spending unit is posted/stabilized. Instead it is evaluated against `objValidationState.last_ball_timestamp`, i.e. the timestamp of whatever `last_ball_unit` the *unit's own author* chose to reference when composing the unit. Because the protocol only forbids the referenced `last_ball_mci` from *retreating* relative to what the unit's parents already reference, an author is free to keep referencing an old, already-stable ball far in the past while delaying the actual broadcast/inclusion of the spending unit. This is the same "back-dating" bug class as the reported L2/L1 upgrade-timing issue: a time-based commitment (deadline/expiry condition) is enforced using a timestamp value that the party controlling inclusion timing can choose from the past, decoupling it from the real time the unit takes effect.

### Finding Description
The `timestamp` oscript condition is defined and validated in `definition.js`: [1](#0-0) 

and evaluated at authentication time strictly against `objValidationState.last_ball_timestamp`: [2](#0-1) 

`last_ball_timestamp` is populated in `validateParents` from the timestamp of the unit's own `last_ball_unit` field — a value chosen by whoever composes the unit, not derived from the current wall-clock time of validation/broadcast: [3](#0-2) 

The only constraint on how "old" this `last_ball` can be is that the resulting `last_ball_mci` must not be lower than the max `last_ball_mci` already referenced by the chosen `parent_units`: [4](#0-3) 

This is a monotonic *floor*, not a freshness requirement — nothing forces `last_ball` to be the most recently stabilized ball. The unit's own `timestamp` field is only checked to be ≥ its parents' timestamp and not more than a few seconds in the future: [5](#0-4) [6](#0-5) 

but there is no corresponding lower-bound/freshness check tying `last_ball_timestamp` to real time. An author can therefore construct (and hold, or repeatedly reuse via low-traffic parent chains) a unit whose `last_ball_unit` is an old, already-stable ball with an old timestamp, while broadcasting the unit much later — exactly the "operator can postpone posting, and thereby retroactively apply an earlier reference time" scenario described in the report, except here it is any unit poster/AA-trigger author controlling their own spending condition, not an L1/L2 relationship.

### Impact Explanation
Address definitions can use `['timestamp', ['<', X]]` or `['timestamp', ['>=', X]]` as spending/authorization conditions — e.g., to implement expiry ("refundable only before deadline X") or unlock ("spendable only after X") logic for shared/multisig or vesting addresses. Because the condition is checked against a self-selected `last_ball_timestamp` rather than the real current time, a co-signer/attacker who is one of the required authors can effectively defeat a deadline-based condition:
- Bypass an "only before X" (expiry) condition well after real wall-clock time has passed X, by continuing to reference an old, pre-X stable ball as `last_ball_unit`.
- More generally, decouple any time-gated authorization logic from real time, leading to unauthorized spending outside the intended time window — a concrete "unauthorized spending" / fund-freezing-bypass impact as required by the validation rules.

### Likelihood Explanation
Any unit poster who is an author of an address using a `timestamp` condition can exploit this unilaterally — no special network position, operator privilege, or hub cooperation is required. The only requirement is choosing `parent_units`/`last_ball_unit` such that `last_ball_mci` does not retreat below what parents already commit to, which is easily satisfiable by an author controlling their own low-traffic address/chain (e.g., a light or isolated wallet address) that hasn't been advancing quickly. This makes exploitation practical for any address whose definition relies on `timestamp` for time-locking.

### Recommendation
Do not use the freely chosen `last_ball_timestamp` as the semantic "current time" for the `timestamp` op. Instead:
- Require that `last_ball` used for `timestamp`-op evaluation be within a bounded tolerance of the actual current/broadcast time (mirroring the report's suggestion of "a minimal tolerance of several minutes"), or
- Enforce that `last_ball_mci`/`last_ball_timestamp` cannot lag behind the globally known stable MC tip by more than a small, fixed margin when a unit's definition (or any ancestor definition in the authentication path) contains a `timestamp` op, or
- Bind the `timestamp` op to the unit's own `objUnit.timestamp` (which is bounded against the future and against its parents) instead of the author-selected `last_ball_timestamp`, so the value reflects the actual time of unit creation rather than an arbitrarily old reference.

### Proof of Concept
1. Alice and Bob co-own address A with definition `['and', [['sig', ...Bob...], ['timestamp', ['<', DEADLINE]]]]`, intended to let Bob refund funds only before `DEADLINE`.
2. Bob prepares (but does not broadcast) a spending unit from A while stable MC time is still before `DEADLINE`, setting `last_ball_unit` to a ball whose `timestamp` is safely `< DEADLINE`.
3. Bob keeps his address's chain "cold" (does not post further units that would force referencing a fresher, later `last_ball`), satisfying the "last ball mci must not retreat" check trivially since no newer reference exists for his address's parent chain (`validation.js` lines 668-674).
4. Long after real time has passed `DEADLINE`, Bob broadcasts the pre-signed unit. `validateParents` accepts the old `last_ball_unit`/`last_ball_timestamp` as long as it does not retreat relative to the chosen parents, and `definition.js`'s `timestamp` evaluation (lines 1036-1048) checks `last_ball_timestamp < DEADLINE`, which is still true.
5. The refund unit is accepted and stabilizes despite `DEADLINE` having passed in real wall-clock time, defeating the intended time-lock.
