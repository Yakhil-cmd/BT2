### Title
Cross-tenant webhook signature/repository binding break allows one organization's signed webhook to mutate another organization's commit status - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to verify against using `repository_owner`, which reads only `payload.dig('repository','owner','login')`, while `Handler#repository_name` (used by `StatusHandler#process` via `stacks`/`Repository.from_github_repo_name`) reads the independent field `payload.dig('repository','full_name')`. Nothing enforces that these two fields agree, so a payload can be signed with `attacker-org`'s legitimately configured `webhook_secret` while claiming a `full_name` that belongs to `victim-org`, causing the `status` handler to write a `Status` record onto a commit that belongs to `victim-org`'s repository.

### Finding Description
Binding claimed: the org whose secret verified the request bytes (`repository_owner` = `attacker-org`) should equal the org owning the repository the handler mutates (`Handler#repository_name`'s owner segment). Tracing the code:

- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` calls `Shipit.github(organization: repository_owner)` and then `github_app.verify_webhook_signature(signature, raw_post)`, where `repository_owner` at `app/controllers/shipit/webhooks_controller.rb:59-62` is `params.dig('repository', 'owner', 'login')`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb:76-83`) simply HMAC-SHA1-verifies the raw body bytes against the `webhook_secret` configured for whatever organization name was passed in — it performs no check that the body's `repository.full_name` matches that organization.
- After signature verification, `WebhooksController#create` dispatches the full raw JSON to handlers (`app/controllers/shipit/webhooks_controller.rb:10-15`).
- `Handler#stacks`/`#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) resolves the target `Repository` via `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, an entirely separate JSON field from `repository.owner.login`.
- `Repository.from_github_repo_name` (`app/models/shipit/repository.rb:53-56`) splits `full_name` on `/` and looks up the pre-existing `Repository` row by `owner`/`name` — this row is a legitimate, independently-synced record for `victim-org/target-repo`, unrelated to the payload's `repository.owner.login`.
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) does `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` with no repository-ownership check on the commit at all — any commit with a matching `sha` anywhere in the Shipit instance is mutated.

Exploit: an attacker controls `attacker-org`, which is a legitimately onboarded organization in this Shipit instance (i.e., an operator has configured a `webhook_secret` for it, as multi-org configs like `test/dummy/config/secrets_double_github_app.yml` demonstrate are supported). The attacker computes `OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)` over a JSON body where `repository.owner.login == "attacker-org"` (to select their own secret) but `repository.full_name == "victim-org/target-repo"`. POSTing this to `/webhooks` with `X-Github-Event: status` and a `sha` matching a real commit in `victim-org/target-repo` passes `verify_signature` (correct secret for the *stated* owner) and then `StatusHandler` writes a forged status onto `victim-org`'s commit.

No existing guard closes this gap: `drop_unhandled_event` only filters by event type; `ExplicitParameters` (`StatusHandler.params`) validates field types/presence, not cross-field/owner consistency; there is no `force_github_authentication`/session check on this controller (it's webhook-authenticated, not user-authenticated); and `Repository`/`Stack` validations only constrain format of stored records, not the relationship between the two independent payload fields at verification time.

### Impact Explanation
An attacker with control of one legitimately-configured organization (`attacker-org`) in a multi-tenant Shipit deployment can forge and inject `Status`/commit-state webhook events (and other events resolved by `full_name`, e.g. `push`, `check_run`, `check_suite`, `pull_request` review-stack handlers) against any other organization's repository whose commit SHAs they can predict/observe (e.g., via public GitHub pushes). This is a cross-tenant authentication-boundary violation: a payload "signed" for one repository mutates another repository's stack/commit/task state, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." It is fully repeatable for any commit SHA/organization pair as long as the attacker controls at least one org with a configured secret.

### Likelihood Explanation
Requires the Shipit deployment to support more than one GitHub organization (each with its own `webhook_secret`) and the attacker to control one of them — a realistic configuration for shared/multi-tenant Shipit instances. Given that precondition, the attack costs nothing beyond knowing their own org's secret (which they legitimately possess as the org's webhook configurator) and a target commit SHA, both attacker-obtainable without any Shipit credentials.

### Recommendation
In `WebhooksController#verify_signature`/`create`, after computing `repository_owner`, also parse `params.dig('repository','full_name')` and reject the request (HTTP 422) unless its owner segment matches `repository_owner` exactly. Alternatively, have `Handler`/`Repository.from_github_repo_name` re-derive the target repository strictly from the verified organization rather than trusting `full_name` independently.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (new test)
test 'a status webhook signed for attacker-org cannot mutate victim-org commits' do
  attacker_secret = 'attacker-secret'
  Shipit.stubs(:github).with(organization: 'attacker-org').returns(
    Shipit::GitHubApp.new('attacker-org', webhook_secret: attacker_secret)
  )

  victim_repo = shipit_repositories(:shipit) # owner: 'victim-org' (adjust to fixture), name: 'target-repo'
  commit = shipit_commits(:first) # belongs to a stack of victim_repo, known sha

  body = {
    repository: { owner: { login: 'attacker-org' }, full_name: "#{victim_repo.owner}/#{victim_repo.name}" },
    sha: commit.sha,
    state: 'success',
    context: 'ci/forged'
  }.to_json

  signature = 'sha1=' + OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)

  post '/webhooks', params: body, headers: {
    'X-Github-Event' => 'status',
    'X-Hub-Signature' => signature,
    'Content-Type' => 'application/json'
  }

  assert_response :ok
  assert commit.reload.statuses.exists?(context: 'ci/forged'),
    "attacker-org's signature should not have been able to write a status onto victim-org's commit, but it did"
end
```
This demonstrates: (1) `verify_signature` accepts the request because the HMAC matches `attacker-org`'s secret over the exact bytes sent; (2) `Handler#repository_name`/`Repository.from_github_repo_name` resolves `victim-org/target-repo` from `full_name`, independent of the verified owner; (3) `StatusHandler#process` calls `create_status_from_github!` on `victim-org`'s commit — proving the binding "verifying org == mutated repo's org" is broken.
