### Title
`Handler#call` enforces no repository-scoping contract, letting `StatusHandler#process` write commit statuses cross-tenant via `Commit.where(sha:)` - (File: app/models/shipit/webhooks/handlers/handler.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::Handler.call` unconditionally invokes `new(params).process` for any handler subclass, without any shared guard requiring `process` to filter by `stacks` or `repository_name`. `StatusHandler#process` does not use these helpers and instead runs `Commit.where(sha: params.sha)` globally, so a `status` webhook whose payload names any repository but contains a `sha` value colliding with a commit belonging to a *different* stack will write a status onto that unrelated commit.

### Finding Description
The broken binding, stated as an equality that should hold but does not: `StatusHandler#process`'s write scope == `Handler#stacks`/`repository_name`-filtered scope. In practice `StatusHandler#process` performs [1](#0-0)  which is `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no reference to `repository_name` or `stacks` at all.

`Handler.call` is the single dispatch entry point used for every webhook type: [2](#0-1) . It has no post-condition, no template-method hook, and no assertion that `process` must consult `stacks`(`Repository.from_github_repo_name(repository_name)&.stacks`, defined at [3](#0-2) ) before mutating state. `stacks`/`repository_name` exist as private helper methods available to subclasses, but nothing forces their use — they are opt-in, not enforced.

Attack flow: `sha` values are not globally unique across independent repositories in Shipit's schema (each `Commit` merely `belongs_to :stack`; there is no cross-repository uniqueness constraint on `sha`) — see [4](#0-3) . An attacker who owns Repository A (already known to Shipit, e.g. by opening a PR/pushing to a stack they control) can observe or engineer a commit sha that also exists as a `Commit` row for a *different*, victim-owned Repository B (e.g. by forcing a matching short/full sha through a benign coincidence, a rebase/cherry-pick of a public commit, or by directly pushing an identical tree to their own fork/branch whose SHA is computed from tree+parent+commit metadata they don't fully control but which is knowable/searchable in cases of forked/cherry-picked commits). They then trigger a GitHub `status` webhook (attacker owns/controls repo A, so they can freely configure/fire this event) with `sha` equal to the colliding value. Because `StatusHandler` never restricts the query to commits under `stacks` for the repository named in the payload, `Commit.where(sha: params.sha)` matches the victim's `Commit` row in Stack B and calls `commit.create_status_from_github!(params)`, writing an attacker-controlled `state`/`description`/`target_url`/`context` status onto the victim's commit — directly affecting the victim's CI-gating status and thus deployability signal in stack B, without any authentication tied to stack B.

Existing guards do not close this gap: `verify_signature`/webhook signature checks validate that the payload came from *some* registered GitHub repo/app installation, not that the `sha` inside the payload belongs to that repo's stacks; `ExplicitParameters` only validates types/presence of `sha`/`state`/etc., not cross-repository ownership; `drop_unhandled_event` only filters unknown event types. None of these enforce the `repository_name`/`stacks` binding that `Handler` fails to require.

### Impact Explanation
A payload from repository A can mutate `Commit`/`Status` records belonging to a different stack/repository B, injecting arbitrary CI status (success/failure/pending, description, target_url) onto a victim's commit. This can flip `deployable?`/`blocked?` signals (see `Commit#deployable?`, `#blocked?`) and influence continuous delivery scheduling (`schedule_continuous_delivery`) for a stack the attacker does not own or authenticate against — a cross-tenant write matching the "payload for one repository mutating another's stack/commit" Critical category. It is repeatable against any commit whose sha the attacker can predict/collide with across tenants.

### Likelihood Explanation
Preconditions: the attacker needs a webhook-triggering event from a repository already connected to Shipit (owning a repo/PR is explicitly an unprivileged attacker capability per the rules) and a `sha` value that also identifies a commit in the victim stack. Exploiting exact sha collisions across unrelated commits is infeasible by brute force, but is realistic when commits are shared: forks, cherry-picks, or rebases of the same commit across multiple Shipit-tracked repositories/stacks naturally produce identical SHAs referenced by multiple `Stack`s' `Commit` rows. In such (common) cases, no cryptographic collision is needed — the same sha legitimately exists in two stacks' commit tables, and the structural bug is that `StatusHandler` doesn't scope by the reporting repository, so any `status` event for repo A about that shared sha also mutates repo B's copy.

### Recommendation
Enforce the scoping binding in `StatusHandler#process` (and audit other handlers) by filtering through `stacks`: e.g. `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }`, ensuring only commits belonging to stacks under `repository_name` are updated. Additionally, add a structural safeguard in `Handler` (e.g. a required override or a base `process` that asserts `stacks`/`repository_name` were invoked) so future handler subclasses cannot silently omit repository scoping.

### Proof of Concept
Minitest plan under `test/models/shipit/webhooks/handlers/status_handler_test.rb`:
1. Create `stack_a` for `repository_name` "org/repo-a" and `stack_b` for "org/repo-b".
2. Create `commit = Commit.create!(stack: stack_b, sha: "deadbeef...")`.
3. Build `payload` with `repository.full_name = "org/repo-a"` and `sha: commit.sha`, `state: "failure"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert `commit.reload.status.state == "failure"` even though the payload's `repository_name` ("org/repo-a") does not match `commit.stack.repository.full_name` ("org/repo-b") — proving the write crossed repository boundaries.
6. Contrast test: reimplement `process` using `Commit.where(sha: params.sha, stack: stacks)` and assert the same payload leaves `commit.reload.status` unchanged, demonstrating the fix would have blocked the cross-tenant write and confirming `Handler#call`/`Handler` base class provides no such guard on its own (a direct subclass whose `process` ignores `stacks`/`repository_name` is accepted without error by `Handler.call`).
