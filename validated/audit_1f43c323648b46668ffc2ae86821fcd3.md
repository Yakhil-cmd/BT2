### Title
Unset shipit.yml step variables fall back to Shipit's real process ENV, leaking secrets like `GITHUB_TOKEN` - (File: lib/shipit/environment_variables.rb)

### Summary
`EnvironmentVariables#interpolate` substitutes `$VARNAME` tokens in task step commands by looking them up in the task's own env hash, but falls back to the Shipit process's own `ENV[variable]` when the name is absent. Since a repository's `shipit.yml` custom task steps can reference *any* variable name, an attacker-controlled step like `echo $GITHUB_TOKEN` will be interpolated with the value of `ENV['GITHUB_TOKEN']` from Shipit's own process environment, not blank/absent as the whitelist mechanism (`EnvironmentVariables#permit`) intends.

### Finding Description
The broken binding: the intended invariant is `interpolated_value($VAR) == @task.env[VAR] (or nil/empty if VAR ∉ whitelist)`. Instead the actual binding is `interpolated_value($VAR) == Shipit's process ENV[VAR]` whenever `VAR` is not a key of the env hash passed to `Command`.

Code path:
- `Shipit::Stack#trigger_task` discovers custom tasks via `DeploySpec::FileSystem#task_definitions`, producing a `TaskDefinition` whose `steps` array (`app/models/shipit/task_definition.rb:29`) comes directly from the repo's `shipit.yml`, fully attacker-controlled on their own branch/PR.
- `TaskDefinition#filter_envs` (`app/models/shipit/task_definition.rb:63-65`) only whitelists *user-supplied task input variables* via `EnvironmentVariables#permit`, which whitelists by name against `variables` declared in `shipit.yml` — it does not, and cannot, restrict which variable *names* may appear inside `steps` strings.
- `TaskCommands#perform` (`lib/shipit/task_commands.rb:23-27`) builds each `Command.new(command_line, env:, chdir: steps_directory)` where `env` is the merged hash from `TaskCommands#env` (`lib/shipit/task_commands.rb:33-48`) — this hash contains only stack env, fixed Shipit-injected vars, `deploy_spec.machine_env`, and `@task.env`. It does **not** contain arbitrary host secrets like `GITHUB_TOKEN` unless explicitly set there.
- At execution, `Command#interpolated_arguments` calls `interpolate_environment_variables` (`lib/shipit/command.rb:51-55`), which calls `EnvironmentVariables.with(env).interpolate(argument)`.
- `EnvironmentVariables#interpolate` (`lib/shipit/environment_variables.rb:20-27`) does:
```ruby
argument.gsub(/(\$\w+)/) do |variable|
  variable.sub!('$', '')
  Shellwords.escape(@env.fetch(variable) { ENV[variable] })
end
```
Because `@env` (the task's Command env) has no `GITHUB_TOKEN` key, `fetch` falls to the block `ENV[variable]`, which reads Shipit's actual process environment — populated by `Command::BASE_ENV` construction (`lib/shipit/command.rb:17-18`) from `Bundler.unbundled_env`/`ENV`, which in real deployments plausibly contains `GITHUB_TOKEN` (e.g., set for `Shipit.github_api` credentials or CI bootstrap).
- The interpolated value is inserted into the shell command line and executed via `PTY.spawn(unbundled_env, *interpolated_arguments, ...)` (`lib/shipit/command.rb:92`), and the resulting stdout is captured into `Shipit::Task#output`, visible to any user (including the PR author) who can view the task page.

Existing guards do not prevent this: `EnvironmentVariables#permit` only filters `@task.env` (user-provided task inputs) against declared `variables`, it never inspects or restricts the literal `steps` strings from `shipit.yml`, and `interpolate` is a *separate* code path invoked at execution time with a completely different fallback (`ENV[variable]`) that bypasses the whitelist's intent entirely.

### Impact Explanation
An attacker who can get a `shipit.yml` with custom task `steps` merged/reviewed onto a deployed branch (this requires the task to actually run, typically requiring some level of merge/dispatch capability by a maintainer or Shipit configuration allowing this task to be triggered) causes the deploy host's own process environment variables — potentially including `GITHUB_TOKEN` or other deploy-time secrets set in Shipit's environment — to be printed into the task's stdout, which is stored in `Shipit::Task#output` and rendered to viewers of that task/stack. This matches the "exfiltration of `GITHUB_TOKEN` ... or deploy-time secrets" Critical impact category. It's repeatable for every custom task run and for any stack whose `shipit.yml` is under attacker control.

### Likelihood Explanation
Requires: (1) a stack configured to discover custom tasks from `shipit.yml` (`DeploySpec::FileSystem#task_definitions`), (2) the custom task actually being triggered on the deployed branch, and (3) Shipit's own process `ENV` containing a sensitive value under a plausible name. Note that triggering a task generally requires it to be merged to the deployed branch and invoked through the UI/API by an authenticated operator — this is not a fully unauthenticated attacker path by itself, but the underlying interpolation bug is a genuine flaw: it silently defeats the environment-variable whitelist's security intent by falling back to the real host `ENV` instead of `nil`/empty, and any variable name (not just ones an attacker predicts) that happens to exist in the host process env will leak.

### Recommendation
In `lib/shipit/environment_variables.rb#interpolate`, remove the `ENV[variable]` fallback; missing variables should resolve to an empty string (or raise) rather than reading the host process's real environment:
```ruby
Shellwords.escape(@env.fetch(variable, ''))
```

### Proof of Concept
In a new/existing test under `test/lib/shipit/environment_variables_test.rb` (or `command_test.rb`):
```ruby
test "interpolate does not leak process ENV for variables absent from task env" do
  ENV['GITHUB_TOKEN'] = 'super-secret-token'
  env_vars = Shipit::EnvironmentVariables.with({}) # no GITHUB_TOKEN in task env
  result = env_vars.interpolate('echo $GITHUB_TOKEN')
  assert_equal 'echo ', result # expected: empty/blank
  refute_includes result, 'super-secret-token' # actual (current code): fails, leaks token
ensure
  ENV.delete('GITHUB_TOKEN')
end
```
Assert both sides of the binding: expected `interpolated_value('$GITHUB_TOKEN') == ''` (or task's own env value) vs. actual current behavior `interpolated_value('$GITHUB_TOKEN') == ENV['GITHUB_TOKEN']`, demonstrating the divergence.
