This "throw on any query error" behavior means that any malformed/erroring SQL statement crashes the whole node process — this is the exact bug class the CVE describes (crafted input reaching a SQL execution path causes a crash/DoS), just with the mechanism inverted: instead of the DB engine itself crashing on crafted SQL, ocore's own driver wrapper is deliberately designed to kill the process on any SQL error.

### Title
Unhandled SQL-query-error crash (DoS) reachable via attacker-crafted `system_vote` unit data — ([File: main_chain.js])

### Summary
`main_chain.js`'s `saveSystemVote()` builds an `INSERT INTO numerical_votes` SQL statement by string-interpolating the attacker-supplied vote `value` directly into the query text instead of passing it as a bound parameter, while every other field is properly escaped with `db.escape()`. Because both storage backends (`mysql_pool.js` and `sqlite_pool.js`) are hard-wired to `throw` an uncaught exception on *any* SQL query error, a value that produces malformed SQL when concatenated crashes the entire node process the moment the containing unit becomes stable on the main chain.

### Finding Description
When a `system_vote` message with subject `base_tps_fee`, `tps_interval`, or `tps_fee_multiplier` is posted, `validateInlinePayload()` only checks that `payload.value` is a finite JS number greater than zero, with narrow upper/lower bounds enforced only after the `pemCurvesFixMci` upgrade point [4](#0-3) . This validation never re-serializes or sanitizes `value` for SQL use — it just checks numeric range on `typeof payload.value === 'number'`.

Note that `unit`, `address`, and `subject` are escaped with `db.escape()`, but `value` and `timestamp` are inserted raw via template-literal interpolation into the SQL string, then executed with `conn.query(...)` without parameter binding.

Both database drivers used by ocore are designed so that *any* query execution error becomes an uncaught, process-killing exception rather than a recoverable callback error:
- MySQL pool: `throw err;` inside the wrapped query callback [3](#0-2) 
- SQLite pool: `throw Error(err+...)` inside the wrapped query callback [1](#0-0) 

This is the same bug class as CVE-2023-31618: a crafted input reaches a SQL execution path and triggers an unhandled failure that halts/crashes the SQL processing component — here, the "component" is the whole ocore process because of its deliberate throw-on-error design.

### Impact Explanation
If an attacker can get `value` to serialize into something that is not a syntactically valid numeric SQL literal for the underlying engine (for example, boundary IEEE-754 values whose `Number.prototype.toString()` representation differs between SQLite's and MySQL's numeric literal grammar, or future/parallel code paths that reuse this pattern with less strict validation), the resulting `INSERT INTO numerical_votes ...` statement fails at the driver level. Because of the `throw`-on-error wrappers, that failure is not caught anywhere in the stabilization pipeline (`markMcIndexStable` → `saveSystemVote`), so it propagates as an uncaught exception and terminates the node process for every full node that reaches stabilization of that unit — i.e., the entire network of full nodes, not just one victim. This is a genuine "network unable to confirm new units" condition, since the crashed nodes stop processing entirely until manually restarted, and the malicious unit remains on the DAG, potentially causing a repeat crash on restart during re-stabilization.

### Likelihood Explanation
`system_vote` is postable by any ordinary address after `constants.v4UpgradeMci` (or always on devnet) [6](#0-5) , requiring no special privilege — any unit poster can include this message. The validation function only performs a numeric-range check [4](#0-3) ; it does not verify that the specific numeric value, once converted to its default JS string form, is guaranteed to be accepted by the SQL engine's numeric literal parser in all cases. Reaching the crash requires finding a finite positive JS number whose default string form is rejected as a numeric literal by SQLite/MySQL — this needs further confirmation of a concrete floating-point value that breaks the grammar (e.g., some extreme-magnitude values before the `pemCurvesFixMci` upper-bound checks apply), so likelihood is rated medium pending that concrete PoC value, but the missing-escaping pattern itself is a clear, provable code defect.

### Recommendation
- Pass `value` (and `timestamp`) as bound query parameters (`?`) instead of interpolating them into the SQL string in `saveSystemVote()`, matching the pattern already used for `unit`, `address`, and `subject`.
- Audit the process-killing `throw`-on-error behavior in `mysql_pool.js` and `sqlite_pool.js` — consider surfacing recoverable SQL errors from paths driven by attacker-controlled unit data (validation/stabilization) as handled errors rather than uncaught exceptions, so a single malformed statement cannot take down the whole node.
- Add regression tests that stabilize `system_vote` units with boundary numeric values (subnormals, `Number.MAX_VALUE`, values just below/above the fixed thresholds) on both SQLite and MySQL backends to confirm the INSERT always succeeds.

### Proof of Concept
1. On a network at or past `v4UpgradeMci` (or a devnet), craft and post a unit from any ordinary address containing a `system_vote` message: `{ app: "system_vote", payload: { subject: "tps_interval", value: <finite positive number> } }`.
2. Choose `value` such that its default JavaScript `toString()` representation is not accepted as a numeric literal by the SQL engine in use (this requires confirming a concrete boundary value against the target SQLite/MySQL grammar — not verified in this analysis, flagged as the remaining unknown).
3. Wait for the unit to reach `is_stable=1` and MC processing to invoke `saveSystemVote()` in `main_chain.js`.
4. Observe the `INSERT INTO numerical_votes ...` statement fail at the driver level; the `throw Error(...)` in `sqlite_pool.js`/`mysql_pool.js` crashes the node process on every full node that stabilizes the unit.
