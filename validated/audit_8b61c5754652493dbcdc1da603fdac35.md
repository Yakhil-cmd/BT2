### Title
`OpenedHandler#provision?` ignores `review_stacks_enabled` for label-gated provisioning behaviors, provisioning stacks on opted-out repositories - (File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb)

### Summary
`OpenedHandler#provision?` is written as `repository.review_stacks_enabled && repository.provisioning_behavior_allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. Because `&&` has higher precedence than `||` in Ruby, `review_stacks_enabled` only scopes the first disjunct (`allow_all`), not the other two. Any repository configured with `provisioning_behavior = allow_with_label` (or `prevent_with_label`) will have PR-opened webhooks create and provision review stacks regardless of `review_stacks_enabled`.

### Finding Description
The broken binding: the intended invariant is `repository.review_stacks_enabled == true` is required for `provision?` to ever be true. Actual code:
```ruby
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 
Due to operator precedence, this parses as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`. When `review_stacks_enabled == false` and `provisioning_behavior == 'allow_with_label'`, the second disjunct alone can be true if the PR carries the configured `provisioning_label_name`, making `provision?` true even though the repository opted out of review stacks.

`process` then unconditionally calls `ReviewStackAdapter#find_or_create!`, which creates a `ReviewStack`, a `PullRequest` record, and immediately enqueues provisioning: [2](#0-1) [3](#0-2) 

Attacker's exact action: open a PR from their own fork against a repository that has `review_stacks_enabled=false` and `provisioning_behavior='allow_with_label'`, and label the PR with the exact `provisioning_label_name` string configured on that repository (label names are typically public/discoverable via the repo settings UI or by observing other public PRs/labels). No Shipit credentials are required — this is purely a GitHub PR action, and Shipit's `OpenedHandler` is invoked by the standard webhook delivery pipeline.

Existing guards do not catch this: `verify_signature`/webhook auth only validates the webhook came from GitHub for that repo — it does not enforce `review_stacks_enabled` semantics; the `ExplicitParameters` schema only validates payload shape; and `NullRepository` correctly returns `false` for all provisioning predicates only for untracked repos, not for tracked repos with `review_stacks_enabled=false`. There is no model-level or controller-level check preventing stack creation for repos with `review_stacks_enabled=false` when `provisioning_behavior` is label-gated. Compare with `LabeledHandler`/`UnlabeledHandler`, which explicitly AND `repository.review_stacks_enabled` as a separate top-level condition in `respond_to_label_change?` [4](#0-3)  — showing the intended pattern that `OpenedHandler#provision?` fails to replicate for its own combined boolean expression.

### Impact Explanation
A `ReviewStack` is created and queued for provisioning (`ReviewStackProvisioningQueue.add(stack)` → eventually `ProvisioningHandler::Base#up`) for a repository whose maintainers explicitly disabled dynamic review-stack provisioning. This is an unauthorized write/resource creation triggered by an untrusted PR author, and provisioning runs infra-provisioning logic against a repository that opted out — a cross-boundary side effect that maintainers did not consent to. This matches "a payload for one repository mutating another's stack" in spirit (mutating repository state against its own configured policy) and can consume infra resources / run arbitrary provisioning-stage commands controlled by attacker-supplied branch/environment naming (`pr#{number}`, `branch: head.ref`) feeding into the provisioning task pipeline.

### Likelihood Explanation
Preconditions are narrow but realistic: the target repository must have `review_stacks_enabled=false` and `provisioning_behavior='allow_with_label'` (a valid, documented, non-default configuration combination) [5](#0-4) . The attacker only needs to know or guess the `provisioning_label_name` string and apply it to their own PR — both achievable by any GitHub user with fork/PR access to a public repo. No secrets, sessions, or elevated GitHub permissions are required. The bug is fully deterministic and repeatable for any repository in this exact configuration.

### Recommendation
Fix operator grouping in `provision?` to require `review_stacks_enabled` for all branches:
```ruby
def provision?
  repository.review_stacks_enabled && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb` add:
```ruby
test "does not provision when review_stacks_enabled is false, even with allow_with_label and matching label" do
  repository = shipit_repositories(:shipit)
  repository.update!(
    review_stacks_enabled: false,
    provisioning_behavior: :allow_with_label,
    provisioning_label_name: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = [{ "name" => "pull-requests-label" }]

  assert_no_difference -> { Shipit::Stack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Assert both sides of the binding: before, `repository.review_stacks_enabled` is `false`; after processing, `Shipit::ReviewStackProvisioningQueue.queued_stacks` should NOT include a new stack for this repository — currently it does, demonstrating the divergence.
