### Title
Attacker-controlled PR label overrides `PATH` env var in Command#unbundled_env, enabling arbitrary binary resolution during deploy/task execution - (File: app/models/shipit/review_stack.rb, lib/shipit/command.rb)

### Summary
`ReviewStack#env` merges every GitHub PR label name (upcased) into the stack's environment hash as `LABEL_NAME => "true"` with no key filtering, so a PR labeled `path` yields `{"PATH" => "true"}`. This hash flows unfiltered into `Command#unbundled_env`, where `@env.stringify_keys` is merged *last* and therefore overrides the computed `Shipit.shell_paths`/`ENV['PATH']` value used by `PTY.spawn` to resolve `git`, `cap`, and task-step binaries.

### Finding Description
The broken binding: `Command#unbundled_env`'s `PATH` key (lib/shipit/command.rb:104: `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)`) is claimed to always equal Shipit's computed shell path, but because `.merge(@env.stringify_keys)` is applied *after* the `'PATH' => ...` assignment, any `PATH` key present in `@env` silently wins.

Path: an attacker opens a PR against a repository with `review_stacks_enabled` and adds a label literally named `path` (case-insensitive since `.upcase` is applied) via a normal GitHub UI/API action. GitHub sends `pull_request` `labeled`/`opened` webhooks; `Shipit::Webhooks::Handlers::PullRequest::LabelCapturingHandler#capture_labels` (app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102) writes `pull_request.update!(labels: params.pull_request.labels.map(&:name))` directly from webhook payload label names — this is confirmed reachable with only PR-labeling privileges the attacker has on their own PR/fork, no signature bypass needed (webhook signature verification is a separate, already-required gate, not something this path needs to defeat since the attacker is a legitimate GitHub actor triggering a legitimate signed webhook for their own repo/PR).

`ReviewStack#env` (app/models/shipit/review_stack.rb:84-93) then does:
```ruby
super.merge(pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" })
```
producing `{"PATH" => "true", ...other stack env...}` with no denylist for reserved keys like `PATH`, `GITHUB_TOKEN`, `BUNDLE_PATH`, etc.

This `env` is consumed by `TaskCommands#env` (lib/shipit/task_commands.rb:33-48, `.merge(@stack.env)`) and `StackCommands#env` (lib/shipit/stack_commands.rb:13-15), which build the `env:` hash passed into `Command.new(..., env:, ...)` for `git` operations, dependency installation, and deploy/task steps. `Command#start` (lib/shipit/command.rb:85-101) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)`, and `unbundled_env` (lib/shipit/command.rb:103-105) merges `@env` (containing the attacker's `PATH => "true"`) over the legitimate computed PATH. The result: `PTY.spawn` executes with `PATH=true`, so any relative binary name (`git`, `cap`, custom step scripts) resolves against a directory literally named `true` in the working/current directory context, which the attacker can plant via files committed in their own PR/branch (since the working directory is the checked-out repo for that stack/task).

Existing guards do not stop this: `verify_signature`/`GitHubApp#verify_webhook_signature` only ensure the webhook truly came from GitHub for a PR the attacker controls — they don't validate label *content*. `ExplicitParameters` schema for `LabelCapturingHandler` only requires `labels[].name: String`, imposing no denylist. `EnvironmentVariables#permit` is not invoked between `ReviewStack#env` and `Command#unbundled_env` for this path. No model validation on `PullRequest#labels` restricts reserved words. `Command#unbundled_env` unconditionally trusts `@env` to override `PATH`.

### Impact Explanation
An attacker with only the ability to open a PR and add a label on their own fork against a `review_stacks_enabled` repository can corrupt the `PATH` used for every git/task/deploy command executed for that review stack, enabling resolution of attacker-supplied binaries checked into the PR branch (e.g., a file named `true/git` or `true/cap` in the working directory) in place of legitimate system binaries — this is Remote Code Execution on the deploy host, scoped to the stack/tenant owning that PR, matching the Critical category ("RCE on the deploy host via `Command`/`PTY.spawn`"). It is repeatable on every subsequent command run for that review stack (fetch, checkout, dependency install, deploy steps) as long as the label remains applied, and confined to review stacks the attacker's PR is associated with — it does not directly cross into other repositories' stacks, but every review stack is attacker-reachable if `review_stacks_enabled` and repository/PR access are attacker-controlled (e.g., open source repos accepting PRs).

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled`, and Shipit's review stack automation must create/update a `Shipit::ReviewStack` + `Shipit::PullRequest` from the attacker's PR (standard flow via `ReviewStackAdapter`/`LabelCapturingHandler`). The attacker needs no Shipit credentials — only the ability to open a PR and add a label, both of which are ordinary unprivileged GitHub actions on a fork. Cost is effectively one PR + one label + a malicious file in the branch. The webhook is a real, correctly-signed GitHub webhook, so no forgery is required. This makes the attack highly feasible and repeatable for any public repository using Shipit review stacks.

### Recommendation
In `ReviewStack#env`, exclude reserved/dangerous environment variable names (at minimum `PATH`, and ideally any variable already defined by `Stack#env`, `Commands#env`, or an explicit denylist such as `GITHUB_TOKEN`, `GITHUB_DOMAIN`, `BUNDLE_PATH`, `GIT_ASKPASS`) from the label-derived hash before merging, e.g. filter `label_name.upcase` against a `RESERVED_ENV_KEYS` constant. Additionally/alternatively, fix `Command#unbundled_env` so `PATH` cannot be overridden by caller-supplied `@env` — merge order should ensure the computed `PATH` (or a safe subset) always wins, or explicitly strip `PATH` from `@env` before merging.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_path_override_test.rb
require 'test_helper'

module Shipit
  class ReviewStackEnvPathOverrideTest < ActiveSupport::TestCase
    test "PR label named PATH overrides computed PATH in Command#unbundled_env" do
      stack = shipit_stacks(:cyclimse) # or a review stack fixture
      review_stack = ReviewStack.new(stack.attributes.except("id"))
      pull_request = PullRequest.new(labels: ["path"]) # attacker-controlled label name
      review_stack.stubs(:pull_request).returns(pull_request)

      env = review_stack.env

      # Binding under test: PATH should remain Shipit-computed, not attacker-controlled
      refute_equal "true", env["PATH"],
        "PR label should not be able to set the PATH environment variable"

      command = Command.new("echo", "hi", chdir: Dir.tmpdir, env: env)
      resolved_path = command.unbundled_env["PATH"]

      expected_path = "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"
      assert_equal expected_path, resolved_path,
        "Command#unbundled_env's PATH must equal Shipit.shell_paths-derived PATH, " \
        "not the attacker-supplied label value"
    end
  end
end
```
This test currently fails against the existing code (`env["PATH"]` is `"true"` and `unbundled_env["PATH"]` is `"true"` instead of the Shipit-computed path), demonstrating the vulnerability.
