This confirms the key mechanism: AA triggers are only executed once their triggering unit's MCI becomes stable, ordered deterministically by `ORDER BY units.level, units.unit, address` [1](#0-0)  and processed in `handleAATriggers()`/`handlePrimaryAATrigger()` by MCI/level/unit order [2](#0-1) . Execution order is therefore determined by DAG/MC position, not by arrival order, and a state variable such as an exchange rate is read live at execution time from `var[...]` rather than being locked in when the user's payment was broadcast.

### Title
Privileged AA control address can front-run a public exchange trigger by racing a price/rate update, extracting user funds at an unfair rate - (File: `test/samples/sell_asset_for_bytes.oscript`)

### Summary
The bundled reference AA `sell_asset_for_bytes.oscript` implements a two-tier trigger pattern common to many Obyte AAs: a privileged `$my_address` can update `var['rate']` at will via one trigger case, while any unprivileged sender can send bytes and receive `round(bytes * var['rate'])` of an asset via a separate, always-open case in the same `cases` list [3](#0-2) . Because AA triggers are executed strictly in the order their triggering units become part of a stable MCI (ordered by `level`, `unit`, `address`, not by broadcast time) [4](#0-3) [5](#0-4) , and `var['rate']` is read live at execution time rather than being pinned to the value seen when the user composed/broadcast their payment, the privileged address can observe a pending "exchange" unit in the network and race to get its own "update exchange rate" unit stabilized first (e.g. by choosing better/more favorable parents or simply because MC/witness-level selection is not FCFS). This lets the privileged address extract nearly all value from an incoming payment by momentarily setting an extreme rate, exactly mirroring the `setTokenOutPrice()` front-running described in the external report.

### Finding Description
The AA has no mechanism to bind the exchange rate the user intended to pay/receive to the trigger they send; the rate is a mutable, globally-shared, unprivileged-read state variable `var['rate']` that:
1. Can be changed unilaterally and instantly by `$my_address` via `{trigger.data.exchange_rate AND trigger.address == $my_address}` [6](#0-5) .
2. Is consumed by the very next case matched for ordinary users: `{trigger.output[[asset=base]] > 100000}` computing `$asset_amount = round($bytes_amount * var['rate'])` [7](#0-6) .

Execution order of AA triggers is governed purely by DAG stabilization order (MCI, level, unit hash) as implemented in `handleAATriggers` in `main_chain.js` and `aa_composer.js`, not by when a unit was first broadcast to the network [4](#0-3) [2](#0-1) . A privileged address that sees a pending user payment can post a rate-change unit and, by controlling its own parent selection, obtain an earlier or otherwise favorable ordering so that its rate change is stabilized and executed before the victim's exchange trigger, analogous to a miner/owner front-running a mempool transaction in an EVM chain.

### Impact Explanation
The unprivileged trigger sender's payment is processed against an unfavorable, attacker-manipulated rate (potentially near zero for the returned asset), so the privileged address effectively consumes the sender's bytes while returning little or nothing of value — a direct unauthorized-spending/value-extraction outcome for the sender, matching Medium severity under "AA fund loss" for the party sending the trigger.

### Likelihood Explanation
Any AA author who follows this common, and codebase-endorsed (bundled sample), pattern of an admin-updatable price/rate variable consumed in the same or a lower-priority case is exposed. Because DAG unit ordering can be influenced by the party constructing/broadcasting a unit (choice of parents, low-latency infrastructure), and because the vulnerable pattern requires no special conditions beyond normal AA usage, exploitation only requires the privileged address to be economically motivated and monitoring incoming payments to itself.

### Recommendation
Any AA design (and, more generally, guidance/samples shipped with ocore) that lets a privileged trigger update a rate/price consumed by unprivileged users in the same processing pass should require the rate to be supplied and locked-in by the paying trigger itself (e.g., `trigger.data.min_rate` with a bounce if `var['rate']` is worse) or should time-lock rate changes (e.g., effective only after N MCIs) so that in-flight user payments cannot be retroactively repriced. The reference sample `sell_asset_for_bytes.oscript` should not be treated as a safe pattern to copy for asset-for-bytes exchanges without such protections.

### Proof of Concept
1. AA `sell_asset_for_bytes` has `var['rate']` initialized to some value R and `$my_address` set to the privileged owner.
2. Alice broadcasts a payment of 1,000,000 bytes to the AA, expecting `round(1000000 * R)` tokens back per the current rate.
3. Before Alice's unit stabilizes, the owner broadcasts its own trigger `{exchange_rate: 0.0000001}` from `$my_address`, arranging (via parent selection / low latency) for this unit to stabilize with an earlier MCI/level than Alice's payment unit.
4. `handleAATriggers`/`handlePrimaryAATrigger` execute the owner's rate-update trigger first because trigger execution order follows `ORDER BY units.level, units.unit, address` at stabilization, not broadcast time [4](#0-3) .
5. When Alice's trigger executes next, `var['rate']` is now 0.0000001, so `$asset_amount = round(1000000 * 0.0000001)` yields effectively zero tokens for Alice's 1,000,000 bytes, which the AA (and ultimately the owner, who can later withdraw via the `withdraw` case) retains [8](#0-7) .
