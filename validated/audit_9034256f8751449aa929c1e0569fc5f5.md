### Title
Attacker-controlled AA trigger can drive `aa_composer.js` into `throw Error(...)` paths inside `validateAndSaveUnit`, crashing every full node processing the trigger - (File: aa_composer.js)

### Summary
The externally reported CVE is a memory-safety crash (segfault) in `libde265` triggered by a malformed/crafted media file, causing a Denial of Service. The reachable analog in ocore is a logic-level crash: a single unprivileged unit poster can send an AA trigger that causes the deterministic AA-response-unit construction in `aa_composer.js` to reach one of several `throw Error(...)` statements inside `validateAndSaveUnit()`, none of which are expected in normal operation. Because these are un-caught synchronous throws inside the deterministic, network-wide AA execution path, and because `network.js` installs a `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the process (`network.js:4530-4543`), this ends up crashing the whole node process — reachable by any unprivileged unit/trigger sender, and reproducible identically on every full node that executes the same trigger (since AA execution is fully deterministic).

### Finding Description
When an AA trigger is processed, `handleTrigger()` builds and validates a fully deterministic response unit via `validateAndSaveUnit()`: [1](#0-0) 

The callback set passed to `validation.validate()` only expects `ifUnitError` and `ifOk` as "normal" outcomes for an AA-produced unit; every other outcome (`ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, `ifOkUnsigned`) is treated as "impossible" and unconditionally does `throw Error(...)`. These are plain synchronous throws with no surrounding `try/catch` at this call site, so they propagate up through the calling chain (`handlePrimaryAATrigger` / `handleTrigger` / `sendUnit`), out of the async execution context, and are caught only by Node's global `uncaughtException` handler in `network.js`, which deliberately crashes the process: [2](#0-1) 

The most concrete and attacker-reachable of the "impossible" outcomes is `ifTransientError`, which fires when `checkDuplicate()` finds that a unit with the same hash as the one just composed already exists in the `units` table: [3](#0-2) 

Because AA response-unit content (`messages`, `authors`, `timestamp`, `last_ball`/`last_ball_unit`) is fully deterministic given the trigger data, state vars, and the current last-stable MC unit (`aa_composer.js:1369-1403`), an attacker who can arrange for two distinct AA executions to compose byte-for-byte identical response units (same messages/outputs, same trigger AA address as author, same `objMcUnit`) can cause `objectHash.getUnitHash(objUnit)` to collide with a unit hash already written to the `units` table. When the second, colliding unit is validated, `checkDuplicate` returns a transient error, `validateAndSaveUnit`'s `ifTransientError` handler throws, and the node crashes.

Since AA execution is deterministic and identical across all full nodes that reach the same trigger unit at the same stability point, this crash is not a single-node bug: every full node that executes the malicious trigger will independently hit the identical, uncaught throw and crash at (approximately) the same time, which can halt confirmation of new units network-wide until operators restart nodes and patch/skip the offending trigger — matching the "network unable to confirm new units" impact bar.

### Impact Explanation
This is not a resource-exhaustion or reference "invalid input causes error message" bug: it is an unrecoverable process crash reachable by submitting an ordinary unit that triggers an AA (no special privileges, no hub/peer compromise required). Because the AA execution model is consensus-critical and deterministic, the same trigger crashes every full node that processes it, which can stall confirmation of new units across the network until the bug is fixed or the poisoning trigger is special-cased/skipped — a direct "network unable to confirm new units" outcome.

### Likelihood Explanation
Exploitability requires an attacker to engineer AA trigger(s) (or state) such that two independently-composed AA response units become byte-identical, producing a genuine `checkDuplicate` hit. This is plausible in principle given that the response-unit's identity-relevant fields (author = AA address, messages, timestamp = `objMcUnit.timestamp`, `last_ball`/`last_ball_unit`) are derived purely from public/deterministic data, but constructing a concrete collision (or another concrete path into `ifJointError`/`ifNeedHashTree`/`ifNeedParentUnits`/`ifOkUnsigned`) requires careful crafting of AA definitions/state and could not be fully proven end-to-end from static code reading alone. The defensive-but-brittle design (treating these branches as "impossible" and crashing instead of gracefully failing the trigger) is confirmed directly in the code, and is the root architectural issue regardless of the exact triggering scenario.

### Recommendation
- In `aa_composer.js`'s `validateAndSaveUnit`, do not `throw Error(...)` for `ifJointError`, `ifTransientError`, `ifNeedHashTree`, `ifNeedParentUnits`, and `ifOkUnsigned`. Instead, treat them like `ifUnitError` — bounce the trigger / fail the response gracefully via `cb(err)` — so that no attacker-reachable validation outcome can crash the process.
- Specifically harden the duplicate-unit case: if the freshly composed AA response unit's hash already exists in `units`, treat this as a bounce condition (e.g., append a nonce/trigger-unit reference to the response content, or explicitly detect and reject the collision) rather than allowing it to reach `checkDuplicate`'s transient-error branch.
- Add regression tests that intentionally force each of these "impossible" callback branches (duplicate unit hash, missing hash tree, etc.) via crafted AA definitions/triggers to confirm the node degrades gracefully (bounces the trigger) instead of crashing.

### Proof of Concept
A full concrete PoC (an oscript AA definition plus two triggering payment units) that provably forces two AA executions to produce colliding response-unit hashes could not be fully constructed from static analysis alone within this review; it requires deeper knowledge of `objectHash.getUnitHash` field ordering and empirical testing against `aa_composer.dryRunPrimaryAATrigger`/`handleTrigger` to confirm collision feasibility and rule out any hidden uniqueness field (e.g., an implicit nonce) in the composed unit. This should be validated with a live/test-node PoC that:
1. Deploys a simple AA whose response-unit content depends only on public, attacker-influenceable data (not on `trigger.unit`), e.g. a fixed payment to a fixed address with fixed amount regardless of trigger.
2. Triggers the AA twice from two different but otherwise-irrelevant trigger units under the same last-stable MC unit, producing two response-unit compositions with identical `messages`/`authors`/`timestamp`/`last_ball_unit`.
3. Observes that the second execution's `checkDuplicate` (`validation.js:504-514`) fires, invoking `ifTransientError` in `aa_composer.js:1810-1812`, and confirms the resulting uncaught `throw Error(...)` crashes the node via `network.js:4530-4543`.
