### Title
Composing-address mutex is held indefinitely across an unbounded external signing wait, freezing all further spends from that address - ([File: composer.js])

### Summary
The libvirt CVE describes a monitor "job" (lock) that is acquired for an operation and then held across a blocking query to an external component (the guest agent), so that any other operation contending for the same job is stalled — an API blockage / DoS. `composer.js`'s `composeJoint()` has the same structural pattern: it takes an exclusive mutex on the spending address(es) and deliberately keeps that lock held across a signing step that can wait indefinitely on a response from an external, potentially unresponsive party (a remote co-signing device), only releasing the lock when the signing callback eventually fires.

### Finding Description
`composeJoint()` acquires a per-address mutex, `'c-'+from_address`, at the very start of composition and stores the unlock function in `unlock_callback`: [1](#0-0) . The code intentionally closes the DB transaction and releases the DB connection before signing, but explicitly keeps the address lock held through the entire signing phase: "we close the transaction and release the connection before signing as multisig signing may take very very long however we still keep c-ADDRESS lock to avoid creating accidental doublespends" [2](#0-1) .

The signing phase iterates over authors and, for multisig/shared addresses, calls `signer.sign(objUnit, assocPrivatePayloads, address, path, function(err, signature){...})` for each signing path, in parallel via `async.each`, and only proceeds to `callbacks.ifOk(objJoint, assocPrivatePayloads, unlock_callback)` once every `cb3`/`cb2` callback has fired [3](#0-2) . For a shared/multisig address whose other co-signer lives on a paired device, the actual signature is obtained asynchronously through the device-messaging layer (a `signing_request` event is emitted to the wallet UI, and the response ultimately flows back as a `sign` event to the pending `signer.sign` callback in `wallet.js`, e.g. [4](#0-3)  and [5](#0-4) ). There is no timeout on this wait in `composer.js`: if the paired device never sends a signature (device offline, malicious/uncooperative co-signer, or a user who never confirms), the `async.each` callback for that author's paths never fires, `callbacks.ifOk`/`unlock_callback` is never invoked, and the `'c-'+address` mutex is never released.

Because `mutex.lock` queues subsequent jobs requesting the same key rather than failing them (`mutex.js`, `isAnyOfKeysLocked` / `arrQueuedJobs`) [6](#0-5) , every later call to `composeJoint`/`composePaymentJoint`/`composeDivisibleAssetPaymentJoint`/`composeMinimalJoint` that references the same address queues forever behind the stuck lock, exactly mirroring the CVE's "monitor job held during a query to a guest agent" blocking further API calls on the same resource.

### Impact Explanation
Any shared/multisig address for which this node is a co-signer can be permanently frozen for further spending by the node itself: as soon as one composition of a joint from that address begins and the counterpart co-signer (a paired device, which is in the explicitly in-scope actor set) withholds or never returns a signature, the `'c-'+address` lock is held forever. All subsequent spend attempts from that address (including automated wallet/AA flows that pay from it) queue indefinitely and never execute, which is a concrete fund/composition freeze rather than a mere resource-exhaustion nuisance. This matches the accepted impact category of "AA fund loss or freezing" / spend-capability freezing for a legitimate on-chain address.

### Likelihood Explanation
No special privilege is needed beyond being a legitimate co-signer on a shared address (a "paired device" actor explicitly listed as reachable in scope). Simply not answering (or indefinitely delaying) a signing request that the victim node itself initiates is sufficient to trigger and perpetuate the lock; the victim node initiates composition through completely normal wallet operation, so the attacker does not need to send any malformed unit or exploit low-level parsing — only withhold a response the code assumes will eventually arrive. The developers' own comment shows they anticipated slow signing but did not add any timeout/expiry to bound how long the mutex may be held.

### Recommendation
Bound the time the `'c-'+address` composing lock may be held while waiting on external signatures (e.g., a configurable signing timeout that releases the lock and calls `handleError`/`ifError` if signatures are not collected in time), and/or allow queued composers for the same address to fail fast with a clear "composition in progress / previous signing request pending" error rather than queuing indefinitely. Consider tracking per-lock acquisition timestamps in `mutex.js` and exposing a mechanism to detect and break stale locks that have exceeded a sane signing deadline.

### Proof of Concept
1. Create/own a shared (multisig) address where the wallet is a co-signer alongside a remote paired device controlled by the "attacker" (or where the attacker's device is simply offline/unresponsive).
2. Call `composeJoint`/`composePaymentJoint` (e.g., via normal wallet "send" flow) to spend from that shared address. `composeJoint` acquires the `'c-'+address` mutex [1](#0-0)  and proceeds to the signing phase, sending a signing request to the co-signing device.
3. Have the co-signer device never respond (simulate an unreachable/malicious paired device). The `signer.sign` callback in the `async.each` over `authors_for_signing` never fires [3](#0-2) , so `unlock_callback` is never invoked.
4. Attempt a second `composeJoint` call for the same address (e.g., another transfer, or an AA-driven payout from that address). Observe it queues in `mutex.js`'s `arrQueuedJobs` and never executes, confirming the address is now permanently unable to spend until process restart.
