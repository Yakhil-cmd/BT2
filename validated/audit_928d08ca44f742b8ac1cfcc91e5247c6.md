### Title
Webhook signature verified against `repository.owner.login`, but handlers act on unchecked `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the HMAC using `repository_owner`, derived from `params.dig('repository','owner','login')` or `params.dig('organization','login')`. [1](#0-0) [2](#0-1)  Every configured organization's secret is looked up solely by that owner login, and if that HMAC matches, the entire raw payload is treated as trusted and dispatched unchanged to handlers. [3](#0-2)  Handlers, however, resolve the actual repository to act on via `repository.full_name`, e.g. `Handler#repository_name` (`payload.dig('repository','full_name')`) used to load `Repository.from_github_repo_name` and its stacks. [4](#0-3)  The `PullRequest::OpenedHandler` follows the same pattern, resolving `Shipit::Repository.from_github_repo_name(params.repository.full_name)` to find or create a review stack. [5](#0-4) 

### Finding Description
This is exactly the SushiSwap `RouteProcessor2` bug class: a signer/validator checks one field of attacker-controlled input (the swap route's stated pool/token) while downstream execution trusts a *different* field of the same payload without cross-checking consistency. Here, the equality that should hold but isn't enforced is:

`organization/app that signed the webhook == owner of the repository the handler actually mutates`

Concretely: if organization `A` and organization `B` are both configured Shipit GitHub Apps (multi-org config is supported per `config/secrets.development.example.yml`), and both share the *same* `webhook_secret` (a real-world common misconfiguration/default, or an attacker who has leaked/guessed one org's secret), then a webhook payload can declare `repository.owner.login = A` (used only for signature app-lookup) while `repository.full_name = B/some-repo` (used by every handler to resolve `Repository` and `Stack`). `verify_signature` only ever inspects `repository.owner.login`/`organization.login` to select which app's secret to check against — it never re-derives or compares that owner to the owner embedded in `repository.full_name`, and no handler re-validates that `repository.full_name`'s owner matches the verified `repository_owner`. [6](#0-5) 

Because `Repository.from_github_repo_name` keys purely off `full_name`, an attacker who can produce a validly-signed payload for org A's secret can direct writes (creating repositories/teams/users, driving `commit_status`, `pull_request`, `push`-triggered sync jobs, review-stack provisioning) against any other repository/org tracked by the same Shipit instance, as long as `full_name` names it. This breaks the "organization authenticated versus the repository that is written" binding called out as in-scope.

### Impact Explanation
Worst case is cross-repository/cross-organization state manipulation without the attacker ever possessing that target organization's real webhook secret — e.g. spoofing `pull_request opened` events to force-provision a review stack for a victim repository, or `push` events to enqueue `GithubSyncJob` for an arbitrary tracked stack. This does not by itself achieve RCE or token exfiltration, and it critically depends on two Shipit-configured GitHub Apps sharing (or an attacker otherwise obtaining) a webhook secret used to satisfy `verify_signature` — a real but non-trivial precondition. Absent that shared/duplicated-secret condition, `verify_signature` does bind the signature to *an* app secret, just not to the specific target repository named in the payload.

### Likelihood Explanation
Low-to-moderate. It requires either (a) multiple orgs behind one Shipit instance configured with an identical `webhook_secret` (an operator error, but one the docs' multi-org example do not explicitly warn against), or (b) an attacker who already has one org's webhook secret trying to pivot to write against a different tracked repository. Single-org deployments (the common case, one `Shipit.github` config) are not affected, since `repository_owner` and `full_name`'s owner will always coincide honestly and there is nothing to substitute.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), assert that the owner segment of `payload.dig('repository','full_name')` matches the verified `repository_owner`/`organization.login` used to select the signing secret, and reject (422) on mismatch. Alternatively, avoid organization-secret sharing entirely by deriving the GitHub App identity from the `installation_id` in the payload rather than from an untrusted `login` string, and cross-check it before trusting `full_name`.

### Proof of Concept
1. Configure two organizations in `config/secrets.yml` (`github: orgA: ..., orgB: ...`) that (by misconfiguration) share the same `webhook_secret`.
2. Craft a `push` webhook payload: `{"repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}, "after": "<attacker sha>", ...}`, sign it with the shared secret.
3. `POST /webhooks` with header `X-Hub-Signature` computed from the shared secret and `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: 'orgA')` and passes since the shared secret matches. [1](#0-0) 
5. The `push` handler resolves the target stack via `full_name = "orgB/victim-repo"`, enqueuing `GithubSyncJob` for `orgB`'s tracked stack, even though only `orgA`'s secret was actually verified.

Note: I could not fully trace the `push` handler implementation itself (its file was not returned by search) to confirm it uses `Handler#repository_name`/`stacks` exactly as the base `Handler` class does; this is inferred from the shared `Handler` base class contract and the `OpenedHandler` example, both of which key exclusively off `full_name`. If a Devin session is available, this should be verified directly against `app/models/shipit/webhooks/handlers/push_handler.rb` (or equivalent) for full certainty.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

      ].join(' '))
    end
