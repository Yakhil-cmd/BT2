Confirmed: `here_come_the_walrus` fixture is an `ApiClient` scoped to `stack: shipit` with only `read:stack` permission, demonstrating that stack-scoped API tokens are a real, supported feature enforced elsewhere via `Api::BaseController#stacks`/`#stack`. `Api::CCMenuController`, however, overrides `#stack` to bypass that scoping.

### Title
Stack-scoped API tokens can read CCMenu deploy status of any stack, not just the stack they authorize - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController#stack` resolves the target stack directly from the `stack_id` request parameter via `Stack.from_param!(params[:stack_id])`, ignoring the `ApiClient#stack_id` scoping that every other API controller relies on. This breaks the binding "stack a token authorizes == stack the token can act on/read," letting a stack-scoped `read:stack` token disclose deploy/rollback status for arbitrary other stacks.

### Finding Description
Shipit supports scoping an `ApiClient` to a single stack: `ApiClient` has an optional `belongs_to :stack` [1](#0-0) , and `Api::BaseController` enforces this scope for every normal API controller through the `stacks`/`stack` helper methods: [2](#0-1) 

`require_permission` only checks that the client's `permissions` array contains the operation:scope string [3](#0-2)  — it never checks *which* stack the client is scoped to. That check is entirely delegated to `stacks`/`stack` in `BaseController`, which filters `Stack.where(id: current_api_client.stack_id)` when the client has a `stack_id`.

`Api::CCMenuController` inherits `require_permission :read, :stack` [4](#0-3)  but overrides `#stack` to bypass the scoping entirely: [5](#0-4) 

Because `#stack` calls `Stack.from_param!(params[:stack_id])` directly instead of going through `stacks.from_param!`, `current_api_client.stack_id` is never consulted. Any valid `read:stack` token — even one deliberately scoped to a single stack such as the `here_come_the_walrus` fixture (`stack: shipit`, permissions `['read:stack']`) [6](#0-5)  — can be replayed against `/api/stacks/:owner/:repo/:env/cc.xml` for any other stack simply by changing `stack_id`, disclosing that stack's latest deploy/rollback status.

This mirrors the reported bug class: a security-relevant equality (`stack authorized by token == stack acted upon`) that holds under one code path (`BaseController#stack`) but is silently violated under another path (`CCMenuController#stack`) for the same authenticated principal.

### Impact Explanation
This grants **unauthenticated read of stack state/task output** across the "scope" boundary: a client meant to see one stack's CI/CD status can read deploy status for any stack in the Shipit instance. This matches the High-severity category "unauthenticated read of stack state, task streams or deploy output" since it crosses a token's declared authorization boundary — it is not merely a design choice, because the very same `ApiClient` model, `require_permission` mechanism, and `BaseController` scoping exist specifically to prevent this, and `CCMenuController` opts out of it in an inconsistent way.

### Likelihood Explanation
Exploitation only requires possession of any valid `read:stack` API token (even one intentionally minted to be single-stack scoped, e.g. via `CCMenuUrlController`, which is exposed to any authenticated Shipit user through the UI) and knowledge/guessing of another stack's `owner/repo/environment` path — all of which are low-privilege, easily obtainable pieces of information in a typical Shipit deployment with multiple stacks.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoping as the rest of the API:
```diff
 def stack
-  @stack ||= Stack.from_param!(params[:stack_id])
+  @stack ||= stacks.from_param!(params[:stack_id])
 end
```
so that `current_api_client.stack_id` (when present) restricts the CCMenu endpoint the same way it restricts `Api::BaseController#stack`.

### Proof of Concept
1. As an authenticated Shipit user, visit `/stacks/:owner/:repo/:env/cc_menu` (or call `CCMenuUrlController#fetch`) to obtain a CCMenu URL containing a `token` for an `ApiClient` scoped only to stack `A` (permissions `['read:stack']`, `stack_id = A.id`), as created in `CCMenuUrlController#client` [7](#0-6) .
2. Take that `token` and issue: `GET /api/stacks/<other_owner>/<other_repo>/<other_env>/cc.xml?token=<token>` where the path now points to a different stack `B` that the client is not scoped to.
3. Observe that `Api::CCMenuController#show` renders `stack.deploys_and_rollbacks.last` for stack `B` [8](#0-7)  — the request succeeds and discloses stack `B`'s latest deploy status, even though the token was only ever intended/scoped for stack `A`.
