### Title
Same L1 BTC lockup outpoint can be double-counted across multiple bond registrations, inflating locked-sats accounting without additional collateral - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path (`verify-l1-lockups` / `validate-l1-lockup`) only deduplicates Bitcoin outpoints *within a single call* via a transient `seen-outpoints` accumulator that is discarded once the call returns. There is no contract-level (persisted) registry of BTC outpoints that have already been credited to a bond. This mirrors the HyperCore report's bug class: a guard/uniqueness check that is evaluated over a narrower, transient scope than the value it is meant to protect, allowing the same underlying collateral to be "read" and counted more than once.

### Finding Description
`validate-l1-lockup` builds up a `sum` and a `seen-outpoints` list purely as fold accumulators local to one `verify-l1-lockups` call: [1](#0-0) 
The per-output dedup check only compares against outpoints already seen *in the same list*: [2](#0-1) 

No `define-map` exists anywhere in `pox-5.clar` that records previously-consumed `(txid, output-index)` pairs across separate `register-for-bond` invocations (confirmed by grepping for `define-map`/`define-data-var` in the file — none track outpoint usage). The only cross-call protections are:
- `bond-overlaps-new-position?`, which rejects a *new* bond position only if the staker's own current membership record's cycles overlap the new bond's first cycle: [3](#0-2) 
- `verify-l1-lockups`/`validate-l1-lockup`'s script/amount/merkle checks, which only confirm the proof is a valid Bitcoin timelock output for that staker's address with a sufficiently high `unlock-burn-height` (checked via `>=`, not exact equality) against the *target bond's* minimum: [4](#0-3) 

Because the minimum-unlock-height check is `>=` rather than an exact match, a single Bitcoin lockup with a sufficiently distant unlock height satisfies the minimum-unlock-height requirement of *multiple* non-overlapping bond periods. Since `bond-overlaps-new-position?` only checks the staker's *own bookkeeping* (whether their current bond membership's cycles overlap the new bond), and not whether the specific BTC outpoint was already credited elsewhere, a staker can:
1. Register for bond A with lockup proof `P` (a real, valid on-chain BTC timelock output). This sets `protocol-bonds-total-staked` for bond A and the staker's membership/signer-cycle shares based on `sats-total` derived from `P`.
2. Once bond A's membership record no longer overlaps a later bond B (e.g., after a roll-over/expiry per pox-5's own cycle bookkeeping — which is a purely Clarity-side notion, independent of whether the actual BTC output is still locked or has even been spent), submit **the exact same lockup proof `P`** again for bond B via `register-for-bond`.
3. `validate-l1-lockup` re-verifies the same Bitcoin transaction/output/merkle proof — which is still true (the transaction did happen on Bitcoin) — and credits the *same* sats amount to bond B's `protocol-bonds-total-staked`, `add-staker-to-bond-cycles`, and `add-staker-to-signer-cycles`, all without any new BTC ever being locked.

The equality broken is: `sum of protocol-bonds-total-staked / signer shares across bonds == real BTC locked by stakers`. After the second registration, this equality is violated — the same locked BTC now backs two separate bond commitments (double-counting), inflating the staker's/signer's reward-earning shares and voting/collateral weight recorded on-chain relative to the actual BTC collateral that exists.

### Impact Explanation
This is a double-counting of a commitment: a single real BTC lockup is credited as collateral to more than one bond position's `protocol-bonds-total-staked` and reward-share accounting. This directly inflates reward entitlement (`calculate-bond-rewards`/`get-earned`) and signer-set weighting derived from `sats-total`, without a corresponding increase in real backing BTC. This matches the "Critical — double-counting a commitment or reward" category.

### Likelihood Explanation
Medium-to-High: the attacker needs no privileged role — only tx-sender control over a normal `register-for-bond` call and a real BTC lockup transaction they control (their own address is committed into the P2WSH script). The scenario requires the staker to structure their BTC lockup's `unlock-burn-height` to satisfy the minimum unlock height of more than one bond period, which is straightforward since the check is `>=` and future bonds typically require increasingly larger minimum unlock heights that a single sufficiently-far-future lockup would satisfy for several bonds. The main constraint is that `bond-overlaps-new-position?` must not flag the two bonds as overlapping (i.e., the first bond membership must be cleared or its term must have elapsed per pox-5's internal cycle math) — achievable by waiting for bond A's cycle term to lapse (a normal roll-over/expiry event) while the underlying BTC output need not actually be spent, moved, or unlocked in reality.

### Recommendation
Persist a permanent, contract-level map (e.g., `used-l1-outpoints: {txid, output-index} -> bool`) and check/insert into it inside `validate-l1-lockup`, replacing (or in addition to) the per-call `seen-outpoints` accumulator, so that any given Bitcoin outpoint can only ever be credited to a single bond registration for the lifetime of the contract, not just within one transaction's fold.

### Proof of Concept
1. Staker constructs a real P2WSH Bitcoin output locking `N` sats to `construct-lockup-output-script(staker, U, ...)` with a distant unlock height `U` that satisfies the minimum unlock height for both bond period A and a later bond period B.
2. Staker calls `register-for-bond(bond-index=A, ..., btc-lockup=(ok {outputs: [proof-of-tx], ...}))`. `verify-l1-lockups` validates the proof and credits `N` sats to bond A's `protocol-bonds-total-staked` and the staker's `protocol-bond-memberships`/signer-cycle shares. [5](#0-4) 
3. Bond A's term lapses per pox-5's cycle bookkeeping (or the staker rolls over to an STX-only stake, clearing `protocol-bond-memberships`), so `bond-overlaps-new-position?` no longer blocks a new registration. [6](#0-5) 
4. Staker calls `register-for-bond(bond-index=B, ..., btc-lockup=(ok {outputs: [SAME proof-of-tx], ...}))`. Since `seen-outpoints` is reset per call and no persisted registry exists, `validate-l1-lockup` re-validates the identical outpoint successfully and credits `N` sats again to bond B's `protocol-bonds-total-staked` and signer shares — from the same real BTC lockup already counted for bond A.

I was unable to run this scenario end-to-end in a live simnet/testnet environment (no execution tools available in this session), so this is a static-analysis-based finding; a Devin session with repo/tooling access would be needed to write a concrete fast-check/property test or an integration test (similar to `stacks-node/src/tests/pox_5_integrations.rs`'s existing `ERR_DUPLICATE_LOCKUP_OUTPOINT` test) to empirically confirm the double-credit across two separate `register-for-bond` transactions.
