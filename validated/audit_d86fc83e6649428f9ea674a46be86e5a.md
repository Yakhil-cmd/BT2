Based on my analysis, I've identified the analog vulnerability in ocore's AA (Autonomous Agent) system, which is functionally similar to the reported NFT-freezing issue: assets received by an entity are permanently unrecoverable because the recipient's own outbound logic explicitly refuses to handle that asset type.

### Title
AA responses cannot pay out `fixed_denominations` or `is_private` assets, so any such asset accidentally or deliberately sent to an AA address is frozen forever - (File: aa_composer.js)

### Summary
When any unit pays a `fixed_denominations` (indivisible) or `is_private` asset to an Autonomous Agent (AA) address, the AA's own response-composition logic in `sendUnit()` explicitly skips or rejects those payment types when trying to send the funds back out, exactly mirroring the reported bug class: a smart-contract-like entity can receive an asset type it structurally cannot re-transfer, and no recovery mechanism exists.

### Finding Description
In `aa_composer.js`, `handleTrigger()`'s `sendUnit()` function processes any `payment` message the AA definition wants to send in response to a trigger. When iterating outgoing payment messages, it loads asset info and explicitly special-cases two asset types: [1](#0-0) 
```
storage.loadAssetWithListOfAttestedAuthors(conn, asset, mci, [address], true, function (err, objAsset) {
    if (err)
        return cb(err);
    assetInfos[asset] = objAsset;
    if (objAsset.fixed_denominations) // will skip it later
        return cb();
    if (objAsset.is_private) // it'll fail validation anyway due to lack of spend_proofs
        return cb("sending private asset from AA");
    ...
```
- If the asset is `fixed_denominations` (indivisible), the outgoing payment message for it is silently dropped later: [2](#0-1) 
```
messages = messages.filter(function (message) { return (message.app !== 'payment' || !message.payload.asset || !assetInfos[message.payload.asset].fixed_denominations); });
if (messages.length === 0) {
    error_message = 'no messages after removing fixed denominations';
    console.log(error_message);
    return handleSuccessfulEmptyResponseUnit(null);
}
```
- If the asset is `is_private`, any attempt by the AA to send it out is bounced entirely with `"sending private asset from AA"`, because the AA (having no private key / spend-proof workflow) structurally cannot produce the `spend_proofs` a private payment message requires.

Crucially, an AA *can* receive such assets: nothing in `validateAATriggerObject` (`aa_composer.js:224-270`) or in `getTrigger()` (`aa_composer.js:375-397`) prevents a `fixed_denominations` or `is_private` asset from being paid to an AA address — the trigger simply records the amount received in `trigger.outputs[asset]`. Once received, the AA's balance bookkeeping (`updateInitialAABalances`) even credits the AA with this balance for public fixed-denomination assets: [3](#0-2) 
```
for (var asset in trigger.outputs) {
    trigger_opts.assocBalances[address][asset] = (trigger_opts.assocBalances[address][asset] || 0) + trigger.outputs[asset];
    ...
```
But there is no oscript/AA-author-accessible mechanism to ever pay these out again: every response payment message for such an asset is dropped (`fixed_denominations`) or bounced (`is_private`) unconditionally in the composer, regardless of what the AA definition author intended. This is not a matter of an AA author forgetting to add a "return the coins" case (which oscript authors can always add for base/divisible assets, as shown in the "silently accept coins" pattern used throughout `test/samples/*.oscript`) — for indivisible/private assets, the ocore engine itself refuses to construct any valid outgoing payment, no matter what the definition specifies.

### Impact Explanation
Any indivisible (`fixed_denominations: true`) or private (`is_private: true`) asset sent to an AA address is permanently and irrecoverably locked at that address. There is no code path, oscript construct, or protocol-level recovery mechanism that lets the AA move these funds elsewhere. This is a permanent, unauthorized-in-effect fund freeze at the protocol level — funds simply vanish from the liquid supply as far as the sender/anyone else is concerned, analogous to an NFT stuck forever in a contract with no rescue function.

### Likelihood Explanation
This is trivially reachable by any unpriviledged unit poster: any user can construct a payment message sending a `fixed_denominations` or `is_private` asset to any AA address, whether by mistake (e.g., a wallet UI allowing arbitrary asset selection) or as a probe/attack. No cooperation from the AA operator is needed, and the loss is deterministic and 100% of the amount sent — it will happen every single time such a payment is made, since the restriction is unconditional in `sendUnit()`.

### Recommendation
- At validation time (`validateAATriggerObject` in `aa_composer.js`), reject triggers whose `trigger.outputs` include a `fixed_denominations` or `is_private` asset, so the payment can never be committed to the DAG in the first place, or
- Allow AAs to at least bounce these specific asset payments back to the sender at the protocol level (bypassing the oscript response mechanism entirely, similar to how base-asset bounce fees work), since the AA definition author has no means to author correct handling code for this today.

### Proof of Concept
1. Define any AA with a simple response (e.g., the `just_a_bouncer.oscript` pattern) and post its address on-chain.
2. Issue a `fixed_denominations` (indivisible) asset, or a private asset, and send a payment of that asset to the AA's address as a trigger.
3. Observe: in `sendUnit()`, if the AA's definition tries to pay this asset back out (`app: 'payment', payload: { asset: <that asset> }`), the message is silently filtered out (`aa_composer.js:1356`) or the whole response bounces (`aa_composer.js:1330`).
4. There is no other message type, getter, or built-in oscript mechanism to move this balance out of the AA address — the funds are permanently stuck. [4](#0-3) [2](#0-1)
