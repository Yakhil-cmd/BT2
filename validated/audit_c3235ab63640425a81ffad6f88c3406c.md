### Title
`get-rewards` computes sBTC yield from the raw current token balance rather than a tracked ledger, letting anyone inflate distributed rewards - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`get-rewards`/`get-new-rewards`/`calculate-rewards` in `pox-5.clar` mirror the reported bug class: instead of relying on an internally accounted ledger of "rewards received," the contract derives the reward amount by reading the *current* live balance of `sbtc-token` held by the contract and subtracting internally tracked counters: [1](#0-0) 

`calculate-rewards` is a public, permissionless function that anyone can call once `calculation-height > last-calc`, and it bakes `gross-accrued-rewards = get-new-rewards()` (the raw balance-derived value) directly into `rewards-per-token-for-cycle`, `last-accounted-rewards-only`, and `reserve-balance`: [2](#0-1) 

This is structurally the same shape as the Balancer report: a "spot" quantity read directly from an external balance (`sbtc-token get-balance`) is treated as ground truth, and a permissionless "update" call (`calculate-rewards`, analogous to `updatePrice()`) permanently commits that spot value into distribution state (`cumulative-rewards-per-ustx`, `rewards-per-token-for-cycle`) that stakers subsequently draw real sBTC against via `get-earned`/`get-earned-staker-rewards`: [3](#0-2) 

### Finding Description
`get-rewards` assumes that `current-balance - total-staked-sbtc - cur-reserve` always equals legitimate, yield-only sBTC. That equality only holds if every sBTC unit that ever lands in the contract's balance for a reason *other* than yield (e.g., new stake deposits recorded via the L1 lockup/bond-registration path) is synchronously reflected in `total-staked-sbtc` before `calculate-rewards` can observe it. Because `calculate-rewards` is callable by any unprivileged principal at any block once `calculation-height > last-calc`, an attacker who can create *any* window where sBTC sits in the contract's balance but is not yet counted in `total-staked-sbtc`/`reserve-balance` can trigger `calculate-rewards` in that window, causing that un-accounted sBTC to be misclassified as "gross-accrued-rewards" and permanently distributed pro-rata to bonds/stakers via `cumulative-rewards-per-ustx` and `rewards-per-token-for-cycle`, i.e., real principal (not yield) is converted into claimable "rewards" for arbitrary other stakers.

This breaks the same equality the Balancer report calls out: the oracle/accounting value ("rewards" here) is read from a spot, externally influenceable balance rather than from a source that provably corresponds only to yield, and a permissionless function commits that value into a durable ledger that other principals can withdraw against.

### Impact Explanation
If this misclassification window can be triggered (I was unable to fully verify — within available context and iteration budget — the exact synchronization point between the L1-lockup/bond-registration deposit path and the `total-staked-sbtc` counter update in `pox-5.clar`), the impact is theft/double-counting of sBTC: a depositing staker's own principal could be paid out to other stakers as "rewards," or protocol reserve accounting could be permanently corrupted, i.e., "sBTC rewards paid that were not earned or counted twice" per the impact criteria (Critical/High).

### Likelihood Explanation
Likelihood depends entirely on whether such a desynchronization window between the token balance and `total-staked-sbtc` actually exists and is reachable by an unprivileged staker (e.g., front-running one's own `stack-aggregation`/bond-registration transaction with a `calculate-rewards` call, or a deposit path that transfers sBTC before updating the counter). I could not locate and confirm the deposit/registration code path that updates `total-staked-sbtc` in the indexed portion of `pox-5.clar` within this session, so I cannot confirm the exploit is concretely reachable — this is a plausible-but-unconfirmed structural analog, not a proven vulnerability.

### Recommendation
Do not derive `gross-accrued-rewards` from a live external balance snapshot. Track sBTC rewards through an explicit, atomically-updated ledger (increment a `total-rewards-received` variable only inside the specific code path that receives yield, never inferred as "whatever balance is left over"), so that `calculate-rewards` cannot be steered by balance timing regardless of who calls it or when.

### Proof of Concept
Not independently verified in this session; concrete PoC requires confirming the exact ordering/atomicity of the deposit path that updates `total-staked-sbtc` relative to sBTC transfer into the pox-5 contract, which was not fully located in the available context.
