### Title
CCMenu API endpoint bypasses ApiClient stack-scoping, allowing a stack-scoped token to read any stack's build status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the base controller's `stack` lookup to bypass the stack-scoping enforced for all other API endpoints, letting an `ApiClient` token authorized for one stack read the deploy/build status of any other stack.

### Finding Description
`Shipit::Api::BaseController` scopes stack lookups to the stacks an `ApiClient` is permitted to touch: `stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped to a specific stack, and `stack` resolves `params[:stack_id]` through that scoped relation via `stacks.from_param!(params[:stack_id])`. [1](#0-0) 

`ApiClient` supports this scoping via an optional `belongs_to :stack`, and fixtures confirm real clients are created scoped to a single stack (e.g. `here_come_the_walrus` is scoped to stack `shipit`). [2](#0-1) [3](#0-2) 

`CCMenuController`, however, defines its own private `stack` method that resolves `params[:stack_id]` directly against `Stack.from_param!`, entirely bypassing the `current_api_client.stack_id` scoping used by every other API controller: [4](#0-3) 

The controller only enforces the permission scope check (`require_permission :read, :stack`), which validates that `"read:stack"` is in `current_api_client.permissions`, but never validates that the requested `stack_id` matches the stack the token is bound to: [5](#0-4) [6](#0-5) 

The binding broken is: the stack a token authorizes (`ApiClient#stack_id`, enforced everywhere else through `BaseController#stacks`) versus the stack the CCMenu action actually touches (`Stack.from_param!(params[:stack_id])`, unscoped). Before the divergence, a token scoped to stack A can only resolve stack A via any API controller inheriting the standard `stack` method; after hitting `CCMenuController#show`, the same token can resolve and read status for any stack B simply by passing a different `stack_id` in the URL.

### Impact Explanation
This is an unauthenticated (relative to the target stack) read of stack build/deploy state through a token that was only ever authorized for a different, unrelated stack. It matches the High-severity criterion "unauthenticated read of stack state, task streams or deploy output," since the last deploy/rollback status (`stack.deploys_and_rollbacks.last`) of any stack in the installation becomes readable by a token that was scoped and issued for a completely different stack.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission (the common minimal permission, e.g. auto-created "CCMenu Client" tokens via `CCMenuUrlController`) can trivially exploit this by changing the `stack_id` path segment of the CCMenu XML endpoint URL - no additional secrets, elevated privileges, or special conditions are required.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController` and use the inherited, scoped `stack` method from `Shipit::Api::BaseController` (i.e., resolve via `stacks.from_param!(params[:stack_id])`) so CCMenu status lookups respect the `ApiClient#stack_id` binding like every other API endpoint.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to `stack_id` = A with `read:stack` permission (e.g. `here_come_the_walrus` fixture, scoped to stack `shipit`).
2. Authenticate as that client via HTTP Basic Auth (or `?token=`) against `GET /api/:stack_b_id/ccmenu.xml`, substituting a different stack B's identifier for `stack_id`.
3. Observe that `CCMenuController#stack` resolves stack B via `Stack.from_param!(params[:stack_id])` (bypassing the `current_api_client.stack_id`-scoped `stacks` relation), and the XML response for stack B's latest deploy/build status is returned, even though the token was never authorized for stack B. [7](#0-6)
