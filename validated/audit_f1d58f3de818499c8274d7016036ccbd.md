## Title
Multisig prologue skips payload-binding check when full payload is stored on-chain, letting an owner with enough approvals execute an unapproved payload - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
`multisig_account::create_transaction()` stores the full transaction payload on-chain and sets `payload_hash = None`. `validate_multisig_transaction()`, invoked by the VM prologue, only checks `sha3_256(payload) == payload_hash` when `payload_hash.is_some()`, and only checks `payload == stored_payload` when the feature flag `abort_if_multisig_payload_mismatch_enabled` is turned on. When that feature is disabled (its default/rollout state cannot be confirmed from the index), and a transaction was created via `create_transaction` (full payload path), neither check runs, so the prologue never verifies that the payload an executor submits matches what the owners actually approved. Execution then independently reconstructs the payload to run from the submitted transaction's `executable` field (in `aptos-vm/src/aptos_vm.rs::execute_multisig_transaction`), not from the on-chain `transaction.payload`. This mirrors the report's bug class: a validation hook that is supposed to bind execution to an approved/intended input, but structurally never enforces that binding under a reachable code path.

### Finding Description
`create_transaction` stores the approved payload directly, with no hash gate: [1](#0-0) 

`validate_multisig_transaction` (called from the VM prologue via `run_multisig_prologue`) gates the payload-match assertion behind quorum/timelock checks that don't verify content, then only checks the hash if `payload_hash.is_some()` and only checks full-payload equality if the feature flag is on: [2](#0-1) 

The prologue-side wiring in the VM computes `provided_payload` purely from the submitted transaction's executable (attacker/executor controlled), and forwards it as the `payload` argument to `validate_multisig_transaction`: [3](#0-2) 

Separately, actual execution (`execute_multisig_transaction`) reconstructs the payload to run again from the same submitted `executable`, not from the `MultisigAccount.transactions[seq].payload` resource: [4](#0-3) [5](#0-4) 

Because `create_transaction` (full-payload path) leaves `payload_hash = None`, the hash-based assertion is unconditionally skipped for these transactions: [6](#0-5) 

And the only remaining check that ties execution to the approved payload is itself feature-gated: [7](#0-6) 

If `abort_if_multisig_payload_mismatch_enabled` is not active on a given network/version, an owner holding sufficient approvals for sequence number N (quorum reached on the *originally proposed* payload) can submit the execution transaction with a **different** entry-function/script executable of their choosing, and the VM will both admit (pass prologue) and execute it, because the admission function never actually compares the executed payload against the one the other owners voted on.

### Impact Explanation
This breaks the core multisig invariant that execution requires owner-approved content, not just an owner-approved sequence slot. An owner (not necessarily the majority) could get a transaction proposed and approved (e.g. "transfer 1 APT to Alice"), then execute the multisig with an entirely different payload (e.g. "transfer entire treasury to attacker", or "add attacker as new owner", or "publish arbitrary malicious module under multisig account authority") once quorum is met for that sequence number, since the payload itself is never bound at the prologue level for the full-payload creation path when the mismatch-abort feature is disabled. This is unauthorized execution under the multisig account's authority — a direct admission-boundary violation with high potential impact (fund loss, governance/ownership takeover of the multisig account).

### Likelihood Explanation
Requires (a) the `abort_if_multisig_payload_mismatch_enabled` feature to be inactive for the relevant transaction, and (b) the executing owner to have legitimately obtained enough approvals for a given sequence number (which for k-of-n where the attacker is one of the k signers, or the attacker being the sole executor when threshold is 1, is a normal condition). I could not verify from the indexed code whether this feature flag is currently enabled by default on Aptos mainnet/testnet genesis — the flag's default state (`aptos_features.rs`, `vm-genesis`) was not fully retrievable within the available searches, so likelihood is uncertain and depends on external, unverified configuration state.

### Recommendation
- Make the payload-binding check unconditional (not feature-gated) whenever `transaction.payload.is_some()`.
- For `create_transaction_with_hash`, this is already always enforced via `payload_hash`; extend equivalent unconditional enforcement to the full-payload path in `validate_multisig_transaction`.
- Ensure `execute_multisig_transaction` derives what it executes from the same validated/stored payload rather than re-deriving independently from the submitted executable, or ensure the two are provably identical at prologue time for every code path, not just when a feature flag happens to be on.

### Proof of Concept
Conceptual sequence (not independently executed against a live node; based on static code tracing):
1. Owner A calls `create_transaction(owner_A, multisig_addr, payload_transfer_1_apt_to_bob)` → stores `payload = Some(transfer_1_apt_to_bob)`, `payload_hash = None`.
2. Owners B and C call `approve_transaction` to reach quorum (e.g., 2-of-3).
3. Owner A (or any owner with sufficient approvals) submits the actual multisig execution transaction with `executable = EntryFunction(transfer_all_funds_to_attacker)` instead of the approved payload.
4. `run_multisig_prologue` computes `provided_payload` from this attacker-chosen executable and calls `validate_multisig_transaction`; since `payload_hash` is `None`, the hash check is skipped, and (assuming `abort_if_multisig_payload_mismatch_enabled` is off) the payload-equality check is also skipped — prologue passes.
5. `execute_multisig_transaction` reconstructs the same attacker-chosen payload from the executable and runs it as the multisig account signer, transferring all funds to the attacker despite only the original 1-APT-to-Bob transfer having been approved. [1](#0-0) [2](#0-1) [4](#0-3)

pub(crate) fn run_multisig_prologue(
    session: &mut SessionExt<impl AptosMoveResolver>,
    module_storage: &impl ModuleStorage,
    txn_data: &TransactionMetadata,
    executable: TransactionExecutableRef,
    multisig_address: AccountAddress,
    features: &Features,
    log_context: &AdapterLogSchema,
    traversal_context: &mut TraversalContext,
) -> Result<(), VMStatus> {
    let unreachable_error = VMStatus::error(StatusCode::UNREACHABLE, None);
    // Note[Orderless]: Earlier the `provided_payload` was being calculated as bcs::to_bytes(MultisigTransactionPayload::EntryFunction(entry_function)).
    // So, converting the executable to this format.
    let provided_payload = match executable {
        TransactionExecutableRef::EntryFunction(entry_function) => bcs::to_bytes(
            &MultisigTransactionPayload::EntryFunction(entry_function.clone()),
        )
        .map_err(|_| unreachable_error.clone())?,
        TransactionExecutableRef::Empty => {
            if features.is_abort_if_multisig_payload_mismatch_enabled() {
                vec![]
            } else {
                bcs::to_bytes::<Vec<u8>>(&vec![]).map_err(|_| unreachable_error.clone())?
            }
        },
        TransactionExecutableRef::Script(script) => {
            if !features.is_multisig_script_enabled() {
                return Err(VMStatus::error(
                    StatusCode::FEATURE_UNDER_GATING,
                    Some("Multisig script payload is not enabled".to_string()),
                ));
            }
            bcs::to_bytes(&MultisigTransactionPayload::Script(script.clone()))
                .map_err(|_| unreachable_error.clone())?
        },
        TransactionExecutableRef::Encrypted => {
            return Err(VMStatus::error(
                StatusCode::FEATURE_UNDER_GATING,
                Some("Encrypted payload not supported for multisig transactions".to_string()),
            ));
        },
    };

    fn execute_multisig_payload(
        &self,
        resolver: &impl AptosMoveResolver,
        code_storage: &impl AptosCodeStorage,
        mut session: UserSession,
        gas_meter: &mut impl AptosGasMeter,
        traversal_context: &mut TraversalContext,
        multisig_address: AccountAddress,
        payload: &MultisigTransactionPayload,
        change_set_configs: &ChangeSetConfigs,
        trace_recorder: &mut impl TraceRecorder,
    ) -> Result<UserSessionChangeSet, VMStatus> {
        let serialized_signers =
            SerializedSigners::new(vec![serialized_signer(&multisig_address)], None);

        // If txn args are not valid, we'd still consider the transaction as executed but
        // failed. This is primarily because it's unrecoverable at this point.
        session.execute(|session| match payload {
            MultisigTransactionPayload::EntryFunction(entry_function) => self
                .validate_and_execute_entry_function(
                    code_storage,
                    session,
                    &serialized_signers,
                    gas_meter,
                    traversal_context,
                    entry_function,
                    trace_recorder,
                ),
            MultisigTransactionPayload::Script(script) => self.validate_and_execute_script(
                session,
                &serialized_signers,
                code_storage,
                gas_meter,
                traversal_context,
                script,
                trace_recorder,
            ),
        })?;
