### Title
Cross-repository forged CI status via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no check that the webhook's `repository.full_name` matches the repository owning that commit's stack. Any sender able to pass `verify_signature` for *some* organization configured in Shipit (e.g. their own onboarded org/repo) can attach a forged `success` `Status` to a `Commit` row belonging to an entirely different stack/repository, as long as the `sha` value matches — which is exactly what a SHA collision buys the attacker.

### Finding Description
The broken binding is:

`commit.stack.repository.full_name == payload['repository']['full_name']`

This should hold for every `Status` created from a webhook, but it is never checked. Compare the two webhook handlers:

- `PushHandler#process` resolves stacks via the base `Handler#stacks` helper, which scopes strictly to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) [2](#0-1) 
- `StatusHandler#process`, by contrast, never uses `stacks`/`repository_name` at all. It does a global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) 

`verify_signature` in `WebhooksController` only proves the request was signed with the webhook secret configured for `repository_owner` as declared in the JSON body [4](#0-3) ; it does not, and cannot, prove that the `sha` inside the payload actually originates from that repository's git history. Shipit explicitly supports multiple GitHub organizations configured with independent webhook secrets (per CHANGELOG "Support multiple GitHub organisations. (#1151)"), so an attacker who legitimately owns/administers one onboarded org/repository (their own tenant) can generate a validly-signed `status` event for their own repository, but set `sha` to a value that collides with the victim's stack HEAD commit sha.

Once that forged `Status` is created against the victim's `Commit` record, the normal side effects fire regardless of which repository actually sent the webhook: `Status#after_create :enable_ci_on_stack` and `after_commit :schedule_continuous_delivery` [5](#0-4) , which calls `commit.schedule_continuous_delivery`, ultimately queuing `ContinuousDeliveryJob`, which — given `stack.continuous_deployment?` true and the stack not occupied — calls `stack.trigger_continuous_delivery` [6](#0-5) . This selects and deploys commits up to the now-"green" HEAD using the victim's real GitHub credentials/checkout, entirely because of a status forged from a different repository.

None of the listed guards close this gap: `verify_signature` authenticates *an* org's webhook, not *the* org owning the target commit; `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler` only validate shape (`sha`, `state`, etc.), not repository identity; `Repository`/`Stack` model validators don't apply here because no `Repository` or `Stack` record is looked up at all in this handler.

### Impact Explanation
This is a cross-tenant integrity break: a webhook payload from repository A can create a `Status` record — and cascade into a real deploy — against a `Commit`/`Stack` belonging to unrelated repository B, using B's own deploy credentials (`GITHUB_TOKEN`) and infrastructure. This matches the explicitly listed Critical category "a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy." It is repeatable against any stack whose HEAD commit sha the attacker can collide with, and scales across every tenant hosted on the same Shipit instance, since the flaw is in the shared `StatusHandler`, not per-repository configuration.

### Likelihood Explanation
Preconditions are non-trivial but realistic given the multi-org threat model rules explicitly invoke: the attacker needs (a) legitimate onboarding of at least one repository/org on the target Shipit instance (to obtain validly signed webhook delivery for *some* org), (b) a `continuous_deployment: true` victim stack, and (c) the ability to produce a SHA collision with the victim's real HEAD commit (a known-hard but demonstrated class of attack, e.g. SHAttered-style). Given those, the attacker cost per exploitation attempt is just crafting one JSON POST to `/webhooks` with a colliding `sha` — no victim credentials, sessions, or secrets are required, and the same technique is repeatable against any stack/commit sha the attacker can collide.

### Recommendation
Scope `StatusHandler#process` (and any other sha/context-keyed handler) to the repository declared in the webhook payload, mirroring `PushHandler`/`Handler#stacks`: resolve `Repository.from_github_repo_name(repository_name)`, then only update `Commit` rows whose `stack.repository_id` matches that repository (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently join through `Stack` scoped by the resolved repository) before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, hypothetical — do not create under `test/` if out of scope for delivery, but conceptually):
1. Create `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`, `continuous_deployment: true`).
2. Create `commit_b` under `stack_b` with `sha: "deadbeef..."` and no blocking statuses.
3. POST a `status` webhook payload with `repository.full_name = "attacker/repo"` and `sha: "deadbeef..."` (matching `commit_b`), signed with `attacker`'s org secret (stub `verify_webhook_signature` to return true for that org only).
4. Assert: `commit_b.statuses.count` increased by 1 (`assert_difference 'commit_b.statuses.count', 1`), proving cross-repository status creation.
5. Assert: `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b])` after the post, proving the forged status from `attacker/repo` triggered deploy scheduling on `stack_b`.
6. Stub `Command.expects(:start)` / task creation at the `Deploy`/`Task` layer to show a deploy would actually be dispatched for `stack_b`'s real HEAD, purely from the forged cross-repo webhook.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
