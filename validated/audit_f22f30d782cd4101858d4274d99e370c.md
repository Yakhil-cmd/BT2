This confirms the vulnerability chain: the `StatusHandler` blindly trusts the payload's `sha`, `state`, and `description` fields to create a `Status` record for any matching commit found across the entire database (`Commit.where(sha: params.sha)`, not scoped to a repository/organization). This `Status` record directly influences `Commit#deployable?` and `MergeRequest#all_status_checks_passed?`, which gate deploys and PR merges.

### Title
Webhook organization used for signature verification is not bound to the repository/commit acted upon, allowing cross-organization CI status forgery - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the request body. However, the event handlers invoked afterwards (e.g. `Shipit::Webhooks::Handlers::StatusHandler`) act on data derived from *other, independent* fields of the same payload (`sha`, `state`, etc.) that are never cross-checked against the organization used to authenticate the request. This breaks the equality: `organization authenticated == organization whose data is written`.

### Finding Description
`verify_signature` computes `repository_owner` purely from attacker-controlled JSON fields and looks up the GitHub App config for that value: [1](#0-0) [2](#0-1) 

Shipit supports per-organization GitHub Apps, each with its own optional `webhook_secret`: [3](#0-2) 

Signature verification is a no-op if the resolved organization has no `webhook_secret` configured: [4](#0-3) 

Once verification passes (either because the org's secret is empty, or because the attacker legitimately controls webhooks for that org), `WebhooksController#create` dispatches the full, untouched JSON payload to the registered handlers: [5](#0-4) 

`StatusHandler` never re-validates which organization/repository the `sha` belongs to — it looks up **any** `Commit` row across the whole installation matching the attacker-supplied `sha` and writes a `Status` from fully attacker-controlled `state`/`description`/`context`/`target_url`: [6](#0-5) 

That `Status` record directly feeds `Commit#deployable?` and `MergeRequest#all_status_checks_passed?` / `any_status_checks_missing?`, which gate whether a commit can be deployed or a PR merged: [7](#0-6) [8](#0-7) 

So the binding that should hold — "the organization whose webhook secret authenticated this request" == "the organization/repository whose commit CI status is being written" — is never enforced. `repository_owner` (used only for auth) and the commit `sha` (used to select which `Status` rows get created) are independent, unrelated fields of the same JSON body.

### Impact Explanation
In a multi-organization Shipit deployment (the documented "Using Multiple GitHub Applications" setup), an attacker who can produce a validly-signed (or unsigned, if that org's `webhook_secret` is blank) webhook for **any one** configured organization can forge a `status` event whose `repository.owner.login` matches that org (satisfying signature verification) while the `sha` field is set to the SHA of a commit belonging to a **different**, more sensitive organization/stack managed by the same Shipit instance. Because `StatusHandler` resolves commits globally by `sha` with no repository/organization scoping, this can mark an arbitrary commit as `success`, satisfying CI requirements and unblocking an unauthorized deploy or merge-queue merge (`MergeRequest#reject_unless_mergeable!`) — this maps to the "unauthorized deploy, rollback, or merge" Critical impact bucket.

### Likelihood Explanation
Likelihood is High for any Shipit instance configured with multiple GitHub organizations (a documented, supported configuration) where at least one organization either has no `webhook_secret` set (explicitly optional in setup docs) or where the attacker has legitimate webhook-delivery capability for one org (e.g. controls a repo in a low-trust org hosted on the same Shipit instance) but not the other. No privileged Shipit account, session, or API token is required — only the ability to deliver a webhook request that satisfies signature verification for *some* configured organization.

### Recommendation
Scope commit/stack lookups in every webhook handler (especially `StatusHandler`, `PushHandler`, `CheckSuiteHandler`) to the repository identified in the payload's `repository.full_name`, and additionally verify that this repository actually belongs to the organization (`repository_owner`) whose secret validated the signature, rejecting the event otherwise. This closes the gap between "organization that authenticated" and "repository/commit whose data is written."

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `OrgA` (attacker-influenced, `webhook_secret` blank) and `OrgB` (victim, has a stack with `sha` `abc123` pending CI).
2. POST to `/webhooks` with header `X-Github-Event: status`, body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" },
  "sha": "abc123",
  "state": "success",
  "context": "ci/required"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally regardless of signature header.
4. `StatusHandler#process` runs `Commit.where(sha: "abc123")`, finds the `OrgB` commit, and creates a `success` `Status` for it, even though the request was never authenticated for `OrgB`.
5. The `OrgB` commit is now `deployable?`/mergeable despite no legitimate CI signal from `OrgB`.
