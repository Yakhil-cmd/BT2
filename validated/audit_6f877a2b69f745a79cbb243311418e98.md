### Title
Cross-repository forged commit statuses via unscoped `StatusHandler` lookup - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler` resolves commits to update **only by `sha`**, with no scoping to the repository/organization that the incoming webhook was authenticated for. Because Shipit indexes commits by `(stack_id, sha)` and the same commit sha commonly exists in more than one tracked `Stack` (forks, mirrors, or any two stacks that happen to share history), a webhook that is legitimately signed by the organization that owns one repository can be used to write a forged commit status onto the `Commit` row of a *different* stack/repository/organization that shares that sha.

### Finding Description
`WebhooksController#verify_signature` selects the `GitHubApp`/webhook secret to verify against using `repository_owner`, derived from the payload itself (`params.dig('repository','owner','login')` or `organization.login`): [1](#0-0) [2](#0-1) 

This means Shipit supports multiple GitHub organizations, each with its own `webhook_secret` (`lib/shipit.rb#github_app_config`, `config/secrets.development.example.yml`). A signature check only proves the payload was legitimately signed by **the GitHub App installed on the organization named in the payload** — nothing more.

Once verified, the raw `params` are dispatched to registered handlers for the event type: [3](#0-2) 

For the `status` event, `StatusHandler#process` does this:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

Note the `params` schema for this handler requires only `sha`, `state`, and optional description/URL/context fields — **it never requires or checks a `repository` field**, unlike `PushHandler` (which filters `stacks` by branch under an implicit stack scope) or `PullRequest::LabeledHandler` (which explicitly resolves `Shipit::Repository.from_github_repo_name(params.repository.full_name)`): [5](#0-4) [6](#0-5) 

`Commit.where(sha: params.sha)` is a **global**, cross-stack query: the schema indexes commits on `(stack_id, sha)` rather than enforcing uniqueness on `sha` alone, and the changelog explicitly documents the "PRs merged by another Shipit stacks" case where the same sha is expected to exist as separate `Commit` rows belonging to different stacks: [7](#0-6) [8](#0-7) 

**Binding broken:** *the organization that authenticated the webhook* ≠ *the repository/stack whose commit-status record is written*. Verification is scoped to organization A (the repository named in the signed payload), but `StatusHandler` writes to every `Commit` row across every tracked `Stack` whose sha matches — including stacks tracking repositories owned by unrelated organizations.

### Impact Explanation
Git commit shas are content-addressed and repo-agnostic: the same sha commonly appears in a fork of a tracked repository, or in any second Shipit `Stack` that happens to track the same upstream history (a very normal and encouraged configuration — Shipit explicitly supports "multiple GitHub organisations", per `CHANGELOG.md`). An attacker who legitimately controls their own organization/repository (and thus its own, correctly-configured, real GitHub App/webhook secret) can:
1. Fork or otherwise obtain a repository that shares commit history/shas with a victim's tracked `Stack`.
2. Trigger (or simply replay) a genuine, validly-signed `status` webhook from their own org for a sha that also exists in the victim's stack.
3. `StatusHandler` finds *all* `Commit` rows with that sha, including the victim stack's row, and calls `create_status_from_github!` on it, injecting an attacker-controlled `state`/`context`/`target_url`.

If the victim stack's `ci.require`/`ci.blocking` configuration relies on that status context to gate deploys or the merge queue (`MergeRequest::StatusChecker`, `deploy_spec.rb`), an attacker with no access whatsoever to the victim's repository or Shipit installation can forge a passing CI status and help unblock/trigger an unauthorized deploy or merge — matching the "unauthorized deploy, rollback, or merge" High/Critical impact bucket.

### Likelihood Explanation
Requires no privileged Shipit credential, no `ApiClient` token, and no compromise of the victim's GitHub org — only a legitimate webhook from an org the attacker actually controls, plus a shared commit sha with the victim (readily achievable via a fork, a shared upstream, or manually recreating an identical commit object with the same tree/parents/committer metadata, which yields an identical sha). This is a realistic, medium-likelihood scenario in any multi-organization or forked-repository Shipit deployment.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up `Commit`/`Stack` purely by `sha`) to the repository the webhook was authenticated for. Require and validate `params.repository` (owner/name) exactly as `PullRequest::LabeledHandler` does, and join through `Stack`/`Repository` before applying `Commit.where(sha:)`, e.g. `stack.commits.where(sha: params.sha)` restricted to stacks belonging to the authenticated repository/organization.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `org-victim` and `org-attacker`, each with its own `webhook_secret` (as supported in `config/secrets.development.example.yml`).
2. `org-victim` has a tracked `Stack` for `org-victim/app` requiring CI context `ci/required-check` before deploy/merge.
3. `org-attacker` forks `org-victim/app` into `org-attacker/app` (sharing the same commit sha `abc123...` for the commit under test) and also has this fork tracked as a Shipit `Stack`, or the attacker otherwise ensures identical commit sha exists in a repo they legitimately control.
4. From `org-attacker/app`, the attacker's GitHub App sends a real `status` webhook for sha `abc123...` with `state: success`, `context: ci/required-check` — validly signed with `org-attacker`'s own `webhook_secret`.
5. `WebhooksController#verify_signature` verifies successfully (correct secret for `org-attacker`).
6. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which returns **both** the `org-attacker/app` commit row and the `org-victim/app` commit row (same sha, different `stack_id`), and creates a forged "success" status on the victim's commit.
7. `org-victim`'s merge queue/deploy pipeline now sees `ci/required-check` as passed for that commit, even though no legitimate CI system for `org-victim/app` ever reported it — enabling deploy/merge despite failing or missing real CI on the victim's repository.

          requires :ref
