### Title
Membership webhook `organization.login` is trusted independently of the org whose secret authenticated the request, allowing genuine-signature cross-org team mutation - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which org's `webhook_secret` to HMAC-verify against using `repository_owner`, which prefers `params.dig('repository','owner','login')` over `params.dig('organization','login')`. `MembershipHandler#process` never checks `repository_owner`; it persists `params.organization.login` verbatim as the `Team#organization`. An attacker who owns a real Shipit-connected org can compute a fully genuine HMAC with their own real secret over a body they authored themselves, including a synthetic `repository.owner.login` (a key membership payloads don't normally carry) pointing at their own org while setting `organization.login` to a victim org, causing the signature check to pass against the attacker's own secret while the persisted `Team.organization` is the victim's.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't:
`Shipit.github(organization: repository_owner).webhook_secret` (the secret used in `verify_webhook_signature`) is assumed to correspond to `params.organization.login` (the value trusted by `MembershipHandler` for persistence), i.e. `repository_owner == params.organization.login` is assumed true for every accepted request but is not enforced anywhere.

Code path:
- `app/controllers/shipit/webhooks_controller.rb:59-62` — `repository_owner` returns `params.dig('repository','owner','login') || params.dig('organization','login')`, generically for all event types, with no schema restriction per event. [1](#0-0) 
- `app/controllers/shipit/webhooks_controller.rb:24-30` — `verify_signature` looks up the `GitHubApp` (and thus the secret) purely by `repository_owner`, then does a constant-time HMAC comparison against the raw body with no timestamp/nonce check. [2](#0-1) 
- `app/models/shipit/webhooks/handlers/membership_handler.rb:38-43` — `find_or_create_team!` sets `team.organization = params.organization.login` with no cross-check against `repository_owner` or the secret's owning org. [3](#0-2) 

Genuine GitHub `membership` events do not carry a `repository` key (they are org-scoped, not repo-scoped), but nothing in this engine validates that. An attacker fully controls the HTTP body they send to `POST /webhooks`, so they can add an arbitrary `repository.owner.login` equal to their own org. Exploit flow:
1. Attacker owns `attacker-org`, which is a legitimately configured Shipit GitHub App org with a real (attacker-known) `webhook_secret`.
2. Attacker crafts a body: `{action:'added', team:{id: <attacker's real team id>, name:'x', slug:'developers', url:'x'}, organization:{login:'victim-org'}, member:{login:'attacker-login'}, repository:{owner:{login:'attacker-org'}}}`.
3. Attacker computes `sha1=HMAC-SHA1(attacker-org's real secret, raw_body)` — no forgery or guessing required.
4. `verify_signature` computes `repository_owner = 'attacker-org'` (repository key present, takes priority), fetches `Shipit.github(organization:'attacker-org')`, and the HMAC matches — request accepted.
5. `MembershipHandler#process` creates/updates a `Team` keyed by `github_id` (attacker's own real team id) but sets `organization = 'victim-org'`, and adds the attacker's member to it.

None of the existing guards prevent this: `verify_signature` only checks the HMAC against whichever org `repository_owner` names, `drop_unhandled_event` and the `ExplicitParameters` schema for `MembershipHandler` don't require/forbid a `repository` key or cross-validate it against `organization.login`, and there is no `require_permission!`/`authorized?` check on inbound webhooks (webhooks are pre-authentication, org-scoped only through the signature).

### Impact Explanation
The attacker mutates a `Team` record tagged with `organization = 'victim-org'` and adds an arbitrary member to it, using only their own org's real webhook secret — a payload rooted in the attacker's own org mutates a different org's team record, matching the "payload for one repository/org mutating another's stack/commit/task/team" Critical category. If the forged team's `slug` is chosen to collide with an entry in `Shipit.github_teams` (statically resolved from `github.oauth.teams` config via `Team.find_or_create_by_handle`, which looks records up by `organization`+`slug`), [4](#0-3)  the forged row can be returned instead of the real victim team on a later lookup, and `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) [5](#0-4)  would then grant the attacker Shipit application access — escalating to High as well ("escalation into `Shipit.github_teams` authorization"). This is repeatable against any victim org whose login the attacker chooses, without needing that org's secret, and does not require any Shipit session or API token.

### Likelihood Explanation
Preconditions: the attacker must own/control at least one org that is genuinely configured in Shipit with its own `webhook_secret` (satisfied by the threat model — attacker-visible deliveries are limited to their own org, but the attacker fully authors the body from scratch, so this is sufficient). No secret compromise, no TLS interception, no privileged role is required — only crafting an HTTP POST with a body containing a non-standard `repository` sub-object and a genuinely-computed HMAC. This is trivially reproducible and repeatable per request.

### Recommendation
In `WebhooksController#verify_signature`, and in each event handler, derive the trusted organization from a single canonical, event-appropriate field and reject payloads containing unexpected top-level keys for that event type (e.g. `membership` events should never carry `repository`). Additionally, `MembershipHandler` should assert that `params.organization.login` (or `params.dig('repository','owner','login')` if present) equals the `repository_owner`/org used for signature verification before creating or mutating any `Team`, rejecting the request otherwise.

### Proof of Concept
```ruby
test "membership webhook with genuine HMAC from attacker-org mutates victim-org's team" do
  attacker_secret = Shipit.github(organization: 'attacker-org').send(:webhook_secret) # attacker's own, known secret
  body = {
    action: 'added',
    team: { id: 999_001, name: 'Devs', slug: 'developers', url: 'https://example.com' },
    organization: { login: 'victim-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', attacker_secret, body)}"

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { Shipit::Team.where(organization: 'victim-org').count }, 1 do
    post :create, body: body, as: :json
    assert_response :ok
  end

  team = Shipit::Team.find_by(github_id: 999_001)
  assert_equal 'victim-org', team.organization
  assert_includes team.members.map(&:login), 'attacker-login'
end
```
This asserts both sides of the broken binding: the request is accepted using only `attacker-org`'s real secret (`repository_owner == 'attacker-org'`), yet the persisted `Team#organization` ends up as `'victim-org'` — confirming `repository_owner != params.organization.login` is possible and unguarded.
