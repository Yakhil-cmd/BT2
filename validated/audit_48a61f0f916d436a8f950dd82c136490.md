### Title
Unbounded numeric `data_feed` values pass validation and propagate into AA payment/state arithmetic - ([File: validation.js])

### Summary
Any address can post a `data_feed` message with a numeric value that is only checked with `isInteger()` — a bare finiteness/integrality check with no upper-bound (unlike payment `amount` fields, which are always bounded by `constants.MAX_CAP`). This mirrors the libnbd flaw: a size/quantity field is validated as "a number of the right shape" but not range-checked against what downstream logic can safely handle, letting an out-of-range but nominally valid value reach consensus-critical code.

### Finding Description
When a unit posts a `data_feed` message, core validates each numeric feed value with: [1](#0-0) 

which only calls `isInteger(value)`: [2](#0-1) 

`isInteger` merely checks `typeof value === 'number' && isFinite(value) && Math.floor(value) === value`. For very large finite doubles (e.g. `1e300`), `Math.floor(value) === value` is trivially true (there is no fractional part representable at that magnitude), so the check passes even though the value is astronomically larger than any legitimate quantity used elsewhere in the protocol. Unlike output amounts, issue amounts, or asset caps — all of which are explicitly bounded via `constants.MAX_CAP`: [3](#0-2) [4](#0-3) 

...there is no equivalent ceiling for `data_feed` numeric values, either in the on-chain unit validator (`validation.js`) or in the AA-definition validator (`aa_validation.js`): [5](#0-4) 

These unbounded values are persisted (`main_chain.js`, `encodeDoubleInLexicograpicOrder`) and later read back by AAs via the `data_feed()` oscript operator, which converts the raw value into a `Decimal` and hands it straight to formula arithmetic: [6](#0-5) 

AA definitions commonly use such values directly to compute payment output amounts or state variables (e.g. exchange rates, shares, balances) without re-imposing an upper bound, as seen in the market-maker/oracle-driven sample AAs: [7](#0-6) [8](#0-7) 

`toDoubleRange`/`createDecimal` in `formula/common.js` only guard against underflow to zero and non-finiteness, not against implausibly large magnitudes: [9](#0-8) 

### Impact Explanation
Because a data-feed-driven number can be many orders of magnitude larger than any value the AA author anticipated (and larger than `MAX_CAP`), arithmetic built on it (rates, shares, balance ratios) can produce nonsensical results: a legitimate final `payment` output amount is still bounds-checked at unit-validation time (`isPositiveInteger` + `MAX_CAP`), so the unit itself would bounce — but intermediate `state`/`var[...]` computations derived from the oversized feed value (balances, outstanding shares, price ratios) are not bounds-checked at all. This can permanently corrupt an AA's internal accounting state (e.g., division by or multiplication with the oversized value skews `var['mm_asset_outstanding']`, `var['rate']`, etc.), leading to AA fund loss or freezing for future triggers that rely on that corrupted state — a concrete, reachable impact within the allowed impact classes.

### Likelihood Explanation
Any unprivileged address can include a `data_feed` app message in a unit they post; no special privilege, hub cooperation, or protocol upgrade is required. The only requirement is that some AA in production trusts that address as an "oracle" and consumes the feed value in unguarded arithmetic — a pattern already present in shipped sample AAs bundled with this repo. This is a core-validation gap (missing bound), not merely an application bug, since `validation.js`/`aa_validation.js` accept the value at consensus level.

### Recommendation
Add an explicit magnitude bound for numeric `data_feed` values in both `validateInlinePayload` (`validation.js`) and `validateAADefinition`'s payload validator (`aa_validation.js`), analogous to `constants.MAX_CAP` for amounts (e.g., reject `|value| > constants.MAX_CAP` or another protocol-defined ceiling), and/or clamp/reject such magnitudes in `formula/common.js`'s `toDoubleRange`/`isFiniteDecimal` before they enter oscript arithmetic.

### Proof of Concept
1. Attacker (any address) posts a unit with a `data_feed` message: `{ "price": 1e300 }`. `isInteger(1e300)` returns `true` (finite, `Math.floor` no-op at that magnitude, no `MAX_CAP`-style ceiling), so the unit passes `validateInlinePayload`.
2. An AA that reads this oracle (e.g. a market-maker AA like `test/samples/uniswap_like_market_maker.oscript`) evaluates `data_feed(...)` and uses the value in a formula such as `$p = $asset_balance * $bytes_balance` or a rate multiplication.
3. The resulting `Decimal` arithmetic produces a state variable or intermediate amount vastly out of the AA's intended range, corrupting `var[...]` balances used by subsequent triggers, even though any single output amount derived from it would still be capped/rejected at final payment validation — leaving the AA's stored state permanently skewed for future interactions.

function isFiniteDecimal(val) {
	return (Decimal.isDecimal(val) && val.isFinite() && isFinite(val.toNumber()));
}

function toDoubleRange(val) {
	// check for underflow
	return (val.toNumber() === 0) ? new Decimal(0) : val;
}

function createDecimal(val) {
	return toDoubleRange(new Decimal(val).times(1));
}
