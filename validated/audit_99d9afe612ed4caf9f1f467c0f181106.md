### Title
Cross-repository forged CI status via unscoped SHA lookup in `StatusHandler#process` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)` [1](#0-0)  instead of scoping through the `stacks` helper (derived from `Repository.from_github_repo_name(repository_name)`) that every other handler (`PushHandler`, `CheckSuiteHandler`) uses [2](#0-1) [3](#0-2) . Because git commit SHAs are content-addressed, an attacker's own repository sharing history with `victim/prod` (e.g. a GitHub fork) will contain identical SHAs, letting the attacker emit a validly-signed `status` webhook from their own repo that writes a forged `success` `Status` row against `victim/prod`'s `Commit`/`stack_id`, triggering continuous delivery.

### Finding Description
The broken binding: `Status.stack_id` should equal `Repository.from_github_repo_name(payload.repository.full_name).stacks` (the webhook's authorizing repository) for every `Status` created by a webhook. `StatusHandler#process` never enforces this:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

This queries `Commit` globally by `sha` with no join/filter on `stack`/`repository`, unlike `PushHandler` (`stacks.not_archived.where(branch:)`) [3](#0-2)  and `CheckSuiteHandler` (`stacks.where(branch: ...)`) [4](#0-3) , both of which correctly scope through `stacks`, itself derived from the payload's own `repository.full_name` [5](#0-4) .

`create_status_from_github!` writes a `Status` row bound to `commit.stack_id` (i.e., whatever stack the matched `Commit` belongs to, not the webhook's own repository) [6](#0-5) , and `Status#replicate_from_github!`/`create!` persist it with that `stack_id` [7](#0-6) . On create, `Status` triggers `schedule_continuous_delivery` -> `commit.schedule_continuous_delivery`, which (per `add_status`'s success path) schedules `ProcessMergeRequestsJob`/continuous delivery when the new state is `success`/`pending` [8](#0-7) [9](#0-8) . `ContinuousDeliveryJob#perform` then triggers a real deploy on the stack if `continuous_deployment?` is enabled and the stack isn't occupied/locked [10](#0-9) .

**Exploit flow**: Attacker forks `victim/prod` on GitHub into `attacker/prod-fork` (both share commit SHAs by construction of git). Attacker then triggers (or directly sends, since the "status" event webhook can be fired for any repo they administer) a `status` event for `attacker/prod-fork` with `state: "success"` and the shared `sha`. `WebhooksController#verify_signature` validates the signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is taken from the payload's own `repository.owner.login` — i.e. the attacker's own org/account, which they legitimately own and for which the signature is genuinely valid [11](#0-10) [12](#0-11) . This passes signature verification without any secret belonging to `victim/prod`'s organization. `StatusHandler#process` then matches the shared SHA against the `Commit` row belonging to `victim/prod`'s stack (already present in Shipit's DB from prior sync of that commit) and writes a forged `success` `Status` scoped to `victim/prod`'s `stack_id`.

**Why guards fail**: `verify_signature` only proves the payload came from *some* GitHub-recognized organization/repo that the attacker controls — it says nothing about which `Commit`/`Stack` the payload's contained `sha` is allowed to affect. `drop_unhandled_event` and the `ExplicitParameters` schema only validate shape (`sha`, `state`, `branches`), not repository ownership of the SHA. No other guard (`force_github_authentication`, `require_permission!`, model validations) applies to webhook-triggered writes.

### Impact Explanation
An unprivileged attacker who owns/administers any GitHub repository sharing commit history (e.g., a public fork) with a Shipit-tracked repository can inject an arbitrary CI `Status` (including `success`) for a commit on that tracked repository's stack, without ever authenticating to Shipit or possessing the target repository's/organization's webhook secret. If `continuous_deployment` is enabled on the victim stack, this deterministically triggers an unauthorized deploy of `victim/prod` — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." The attack is repeatable against any stack/repository pair sharing a commit SHA with an attacker-controlled repo (forks, mirrors, or any repo containing the same commit objects), and is fully deterministic (no race required, contrary to what a naive analysis of `Commit#status` memoization might suggest — the actual root cause is the missing repository scope in the SQL query, not a memoization/race issue).

### Likelihood Explanation
Preconditions: (1) the attacker can create/administer a GitHub repository that shares at least one commit SHA with the victim stack's tracked repository — trivially achieved by forking a public repo, or by an insider with any repo access; (2) that attacker-owned repository must have a webhook configured to Shipit and belong to an organization/owner that Shipit's `Shipit.github(organization:)` resolves to a known, configured GitHub App/organization (otherwise `GithubOrganizationUnknown` causes a 422) [13](#0-12) ; (3) the victim commit must already exist as a `Commit` row in Shipit's database (i.e., previously synced from `victim/prod`). Cost is low: no secrets, tokens, or privileged roles are required beyond ordinary GitHub repository ownership/administration within a recognized organization boundary.

### Recommendation
Scope `StatusHandler#process` through `stacks` (the handler's own repository-derived scope) exactly as `PushHandler`/`CheckSuiteHandler` do, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a forged `Status` can only ever be attached to a `Commit` belonging to the same repository that authenticated the webhook.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` or similar — outside the scope restriction is only for informational reference; actual test file goes under `test/`):

```ruby
test "status webhook cannot forge status onto a commit belonging to a different repository" do
  victim_repo  = shipit_repositories(:shipit) # e.g. "shopify/shipit-engine"
  victim_stack = victim_repo.stacks.first
  shared_sha   = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared", author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  attacker_payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "ci/attacker",
    "branches" => [{ "name" => "master" }],
    "repository" => { "full_name" => "attacker/prod-fork", "owner" => { "login" => "attacker" } }
  }

  # binding under test, BEFORE:
  assert_equal 0, victim_commit.statuses.where(context: "ci/attacker").count

  Shipit::Webhooks::Handlers::StatusHandler.call(attacker_payload)

  # binding under test, AFTER: forged status must NOT be attached to victim_commit/victim_stack
  assert_equal 0, victim_commit.reload.statuses.where(context: "ci/attacker").count
  refute_includes victim_stack.next_commit_to_deploy&.statuses.to_a, victim_commit.statuses.where(context: "ci/attacker").first
end
```
With the current implementation this test fails (the forged status is attached to `victim_commit`); after applying the recommended fix (scoping via `stacks`), it passes.

      yield
      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
