### Title
AA trigger execution order is determined by DAG `level` (not by unbiased FIFO), letting a trigger sender front-run a pending "loss" trigger to withdraw a shared-pool AA's funds before their share of the loss is applied - (File: aa_composer.js, main_chain.js)

### Summary
Autonomous Agents (AAs) that manage a shared pool of funds (e.g. the sample `divest MM shares` case in `uniswap_like_market_maker.oscript`, or any AA that pays users a *pro-rata share of `balance[...]`*) compute each user's payout based on the AA's current on-chain balance at the moment their trigger is executed. Because trigger *execution order* — not merely arrival time — decides which balance snapshot a user sees, an unprivileged trigger sender who is aware of a pending "loss-realizing" unit (analogous to `seizeBadDebt`/`settleBadDebt` in the Hubble report) can try to get their own withdrawal/divest trigger executed **before** that loss-realizing trigger, extracting a payout computed on the pre-loss balance and thereby escaping their pro-rata share of the loss.

### Finding Description
Primary AA triggers are not executed strictly in the order units were broadcast/received. When an MCI stabilizes, all payment triggers addressed to AAs in that MCI are collected and queued with: [1](#0-0) 

```
ORDER BY units.level, units.unit, address
```

and later dequeued/executed with the same tie-break rule: [2](#0-1) 

`level` is a purely structural DAG property (max level of the unit's parents + 1) that the unit's own author chooses by selecting which parent units to build on — it is *not* a fee, priority, or arrival-time value enforced by consensus in the same way an EVM mempool gas auction is, but it is nonetheless attacker-influenceable: a user who deliberately avoids referencing (as an ancestor) the unit that carries the pending "loss" trigger can keep their own unit's `level` lower than that unit's level. If both units end up stabilizing within the same MCI batch (a realistic scenario since MCI stabilization only requires ~1 witness-level confirmation window), the attacker's lower-`level` unit's AA trigger will be executed **before** the loss-realizing trigger, per the `ORDER BY units.level, ...` rule shown above.

This mirrors the C4 Hubble finding precisely: there, `withdraw()` could be raced ahead of `seizeBadDebt()`'s state change by paying more gas to get included first in the same block; here, a trigger sender can race a pool-divesting/withdrawal trigger ahead of a balance-reducing trigger by keeping the unit's DAG `level` lower, so it is executed first within the same batch of triggers processed at MCI stabilization.

Any AA that computes a payout from `balance[...]` (bytes or an asset) at the time the trigger executes — the pattern used throughout the codebase's own AA examples, e.g. the “divest MM shares” case: [3](#0-2) 

and the "pay out the winnings" case, which distributes `var['total']` in proportion to contributions computed against balance at trigger time: [4](#0-3) 

is exposed to the same ordering-manipulation risk if a "loss"-type trigger (e.g. a penalty payout, bad-debt-like write-off, or any AA-to-AA call that reduces the pool's balance) can be pending in the unstable DAG at the same time as a user's own withdrawal trigger.

### Impact Explanation
A user who can predict/observe an upcoming balance-reducing AA trigger can craft their own trigger unit referencing parents that exclude the loss-causing unit, keeping their `level` artificially low, and get their withdrawal/divest trigger processed first when the MCI containing both units stabilizes. This lets them extract their share of the pool's funds computed on the pre-loss balance, shifting the loss entirely onto the remaining participants — an AA fund-loss/socialized-loss scenario equivalent to unauthorized value extraction from other shareholders of the pool.

### Likelihood Explanation
Exploitation requires the attacker to notice the pending loss-causing unit while it is still unstable (visible in the DAG before MCI stabilization) and to compose a competing unit with parents chosen to avoid referencing it, which is straightforward for any node running its own witness/composer logic. Because MCI stabilization windows are short but non-instant, and multiple triggers addressed to the AA within the same MCI are ordered purely by `level`/`unit` hash rather than by submission time, the race is winnable with modest DAG-parent-selection effort rather than requiring any privileged access. Likelihood is Medium: it depends on the AA's application logic actually computing shares from `balance[...]` at trigger time (a common but not universal AA pattern) and on the attacker being able to observe the loss-trigger before it stabilizes.

### Recommendation
- AA authors implementing shared pools/pro-rata payouts should avoid basing payouts purely on `balance[...]` snapshotted at arbitrary trigger time; e.g., use a two-step withdraw pattern (request now, settle after a further-delay/mci-gated step) or snapshot balances at fixed epochs rather than "current" balance.
- At the protocol level, consider whether AA trigger execution order within the same MCI should be made harder to game via `level` selection (e.g., ordering by trigger unit's `main_chain_index` position derived independently of author-chosen parents, or requiring last-ball inclusion of all currently-known pending triggers to that AA before finalizing order).
- Document this ordering-manipulation risk clearly for AA authors so pool-style AAs are designed defensively (e.g. lock-step "commit balance, then distribute" patterns).

### Proof of Concept
1. AA `P` holds a shared pool and pays out `share = trigger_amount / total_outstanding_shares * balance[asset]` on divestment (pattern shown in `uniswap_like_market_maker.oscript`'s "divest MM shares" case).
2. A large loss-realizing operation (e.g., another AA-to-AA call, or a bounced/negative-balance-absorbing trigger) is posted as unit `L`, referencing recent tips, and is still unstable/unconfirmed.
3. Attacker `A` composes a divest trigger unit `W` that deliberately selects parent units that do not descend from `L`, keeping `level(W) < level(L)`.
4. Both `W` and `L` become part of the same MCI when it stabilizes. Per `main_chain.js`'s `ORDER BY units.level, units.unit, address` (mirrored in `aa_composer.js`'s dequeue order), `W`'s trigger executes first because `level(W) < level(L)`.
5. `A`'s divest trigger computes its payout using `balance[asset]` **before** `L`'s loss is applied, letting `A` withdraw a payout inflated relative to what they would have received had `L` executed first — effectively shifting `L`'s loss onto the remaining pool participants.
