### Title
Stale calculation-phase stake amount vs. current stake can panic the validator during partitioned epoch reward distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`build_updated_stake_reward` asserts that a delegation's stake, freshly re-computed from the *current* on-chain stake account state plus its previously calculated reward, exactly matches the reward's precomputed "new stake" value from the calculation phase. A stake account's `delegation.stake` can legitimately change between the epoch reward *calculation* phase and the (multi-block) *distribution* phase via ordinary, permissionless stake-program instructions (e.g. `Split`), which breaks this invariant and triggers a hard `assert_eq!` panic deterministically on every validator.

### Finding Description
Epoch rewards are computed once at the epoch boundary (`calculation.rs`) and then distributed over many subsequent blocks, one partition per block, via `distribute_partitioned_epoch_rewards` → `distribute_epoch_rewards_in_partition` → `store_stake_accounts_in_partition` [1](#0-0) . For each partition/block, `store_stake_accounts_in_partition` re-reads the *live* stakes cache (`self.stakes_cache.stakes()`), i.e., the actual current stake account state at distribution time, not a frozen calculation-time snapshot [2](#0-1) .

Inside `build_updated_stake_reward`, when the rent-adjustment feature is inactive (`adjust_delegations_for_rent == false`, i.e. pre‑SIMD‑0392), the code computes:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, ...);
```
where `stake` is the *current* (freshly loaded) stake state and `new_stake` is the stake state as computed during the earlier calculation phase, assuming `stake.delegation.stake` has not changed in the interim [3](#0-2) .

This assumption is false in general: a stake authority can permissionlessly submit ordinary stake-program instructions such as `Split` that reduce (or otherwise alter) `delegation.stake` on their own already-delegated stake account at any point between the calculation block and the block in which that account's partition is processed. There is no gating in the bank/transaction processing path (`epoch_reward_status`/`EpochRewardStatus::Active`) that blocks stake instructions from mutating stake accounts while epoch reward distribution is in progress — the searches for such gating (`epoch_reward_status`/`is_in_reward_interval` checks in `bank.rs` or the stake program) found no such restriction. When the mismatch occurs, `expected_delegation != new_stake.delegation.stake`, and the `assert_eq!` panics.

Because reward distribution is executed identically as part of deterministic bank processing by every validator replaying the same block, the panic is not local to one node — it happens on all validators processing that slot, i.e., a transaction-triggered, network-wide crash/halt rather than a graceful, recoverable error (contrast with the `Err(...)` paths elsewhere in the same function which are handled gracefully by `store_stake_accounts_in_partition`'s `match` and simply burn the reward instead of panicking) [4](#0-3) .

This mirrors the reported OpenQ bug-class exactly: a permissionless, attacker/user-controlled mutation to shared state (a deposited token / here a stake account) that is later consumed in a batch/loop operation (`payout` / here `store_stake_accounts_in_partition`) whose code assumes the mutated state is unchanged, causing the whole batch operation to abort — except here the "abort" is a hard Rust panic in consensus-critical bank code instead of a Solidity `revert`, making the impact categorically worse (validator crash / consensus halt vs. locked funds).

### Impact Explanation
A validator process panic triggered deterministically during normal block replay by an ordinary user transaction (`Split`, or any other instruction that changes `delegation.stake` on a delegated stake account) is a cluster-wide liveness/consensus-halting bug: every conforming validator that processes the block containing the distribution partition for the affected stake account, plus every validator that later processes the same historical block during replay, panics. This is one of the most severe possible categories of Solana bugs, causing a network-wide halt reachable by a single unprivileged transaction.

### Likelihood Explanation
Reaching this requires: (1) having a delegated stake account whose reward is calculated and scheduled for distribution in a later block, and (2) submitting a normal `Split` (or similarly delegation-stake-altering) instruction on that same stake account before its distribution partition/block is processed, and (3) the `relax_post_exec_min_balance_check` feature (which gates `adjust_delegations_for_rent`) being inactive, since the vulnerable `assert_eq!` branch is only reached in the `else` arm. All three preconditions are attacker-controllable or environment-dependent but not privileged: any staker can time a `Split` transaction within the distribution window of their own account. The likelihood is high if the feature gate is off on the target cluster; it should be explicitly verified whether `relax_post_exec_min_balance_check`/SIMD-0392 is active on mainnet, since that determines whether the vulnerable code path is currently live.

### Recommendation
- Remove the hard `assert_eq!` panic path and replace it with a graceful `DistributionError` return (as already done for `ArithmeticOverflow`/`UnableToSetState`) so a mismatch burns/skips that individual reward instead of crashing the validator.
- More fundamentally, do not assume `delegation.stake` is immutable between calculation and distribution phases; recompute the expected post-reward state solely from data captured at calculation time, or explicitly detect and handle (not panic on) any state drift caused by intervening stake instructions (splits, merges, deactivations) during the distribution window.
- Consider restricting delegation-mutating stake instructions on accounts that have a reward still pending distribution, or apply the SIMD-0392 rent-adjustment logic (which already tolerates the live account state) unconditionally instead of gating it behind a feature that leaves the panicking legacy path reachable.

### Proof of Concept
1. Wait for/observe an epoch boundary where `distribute_partitioned_epoch_rewards` calculates rewards for delegated stake accounts and schedules multi-block distribution (`EpochRewardPhase::Distribution`).
2. Identify a stake account you control that has a nonzero calculated reward whose partition/block index is scheduled some blocks after calculation (`distribution_starting_block_height + partition_index`).
3. Before that block is reached, submit an ordinary `Split` (stake program) instruction from that stake account's authority to reduce its `delegation.stake` (a fully permissionless, single-signature transaction).
4. When the bank processes the scheduled distribution block, `store_stake_accounts_in_partition` re-reads the now-reduced stake from the live `stakes_cache`, computes `expected_delegation = reduced_stake + stake_reward`, compares it against `new_stake.delegation.stake` (computed at calculation time from the pre-split stake), finds a mismatch, and hits:
```
assert_eq!(expected_delegation, new_stake.delegation.stake, "stake reward delegation must be consistent with the updated stake account lamport balance");
```
causing the validator to panic while replaying/producing that block — reproducible deterministically on every validator, i.e., a network-wide halt triggered by a single user transaction (contingent on the `relax_post_exec_min_balance_check` feature being inactive on the target cluster).

impl Bank {
    /// Process reward distribution for the block if it is inside reward interval.
    pub(in crate::bank) fn distribute_partitioned_epoch_rewards(&mut self) {
        let EpochRewardStatus::Active(status) = &self.epoch_reward_status else {
            return;
        };

        let distribution_starting_block_height = match &status {
            EpochRewardPhase::Calculation(status) => status.distribution_starting_block_height,
            EpochRewardPhase::Distribution(status) => status.distribution_starting_block_height,
        };

        let height = self.block_height();
        if height < distribution_starting_block_height {
            return;
        }

        if let EpochRewardPhase::Calculation(status) = &status {
            // epoch rewards have not been partitioned yet, so partition them now
            // This should happen only once immediately on the first rewards distribution block, after reward calculation block.
            let epoch_rewards_sysvar = self.get_epoch_rewards_sysvar();
            let (partition_indices, partition_us) = measure_us!({
                epoch_rewards_hasher::hash_rewards_into_partitions(
                    &status.all_stake_rewards,
                    &epoch_rewards_sysvar.parent_blockhash,
                    epoch_rewards_sysvar.num_partitions as usize,
                )
            });

            // update epoch reward status to distribution phase
            self.set_epoch_reward_status_distribution(
                distribution_starting_block_height,
                Arc::clone(&status.all_stake_rewards),
                partition_indices,
            );

            datapoint_info!(
                "epoch-rewards-status-update",
                ("slot", self.slot(), i64),
                ("block_height", height, i64),
                ("partition_us", partition_us, i64),
                (
                    "distribution_starting_block_height",
                    distribution_starting_block_height,
                    i64
                ),
            );
        }

        let EpochRewardStatus::Active(EpochRewardPhase::Distribution(partition_rewards)) =
            &self.epoch_reward_status
        else {
            // We should never get here.
            unreachable!(
                "epoch rewards status is not in distribution phase, but we are trying to \
                 distribute rewards"
            );
        };

        let distribution_end_exclusive =
            distribution_starting_block_height + partition_rewards.partition_indices.len() as u64;

        assert!(
            self.epoch_schedule.get_slots_in_epoch(self.epoch)
                > partition_rewards.partition_indices.len() as u64
        );

        if height >= distribution_starting_block_height && height < distribution_end_exclusive {
            let partition_index = height - distribution_starting_block_height;

            self.distribute_epoch_rewards_in_partition(partition_rewards, partition_index);
        }
