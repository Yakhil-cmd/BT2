### Title
Signature verification is bound to `repository.owner.login`/`organization.login`, but effectful webhook handlers act on the independently-controlled `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to verify the HMAC signature against using `repository_owner`, computed from `params.dig('repository','owner','login')` (or `organization.login`) inside the *unverified* JSON body itself. [1](#0-0) [2](#0-1)  Once the signature check passes, the actual side-effecting handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) determine which repository/stacks to mutate using a *different* field of the same payload: `repository.full_name`, via `Handler#repository_name`. [3](#0-2) 

### Finding Description
This is the direct analog of the reported bug class: "an organization that authenticated versus the repository that is written." The binding that should hold is:

`organization whose secret produced a valid HMAC == organization that owns the repository being acted upon`

but the code only enforces:

`organization used to look up the HMAC secret == repository.owner.login (attacker-supplied field in the same unverified body)`

and separately, independently:

`repository acted upon == repository.full_name (also attacker-supplied, in the same unverified body)`

Because `repository.owner.login` and `repository.full_name` are two unrelated JSON fields that the attacker fully controls in the raw request body they are signing, an attacker who has a valid webhook secret for *any* organization/app installation registered in this Shipit instance (e.g., their own GitHub org, which they legitimately administer and for which they can legitimately obtain a correctly-signed webhook) can:

1. Craft a JSON payload with `repository.owner.login` (or `organization.login`) set to their own org - so `Shipit.github(organization: repository_owner)` resolves to the app config whose `webhook_secret` they know, and `verify_webhook_signature` succeeds. [4](#0-3) 
2. Set `repository.full_name` in the very same payload to point at a **different** organization's repository that is also configured on this same Shipit instance.
3. Sign the whole body with their own secret and POST it to `/webhooks`.

`verify_signature` passes (their org's secret matches their org's signature), and `create` dispatches the payload to the handlers registered for the event, which resolve the target `Repository`/`Stack` purely from `repository.full_name`: [5](#0-4) [6](#0-5) 

This lets the attacker inject fully-attacker-controlled webhook events (push, status, check_suite, pull_request/*) against any stack belonging to a victim organization also hosted on the same Shipit instance, without ever possessing that victim organization's webhook secret.

### Impact Explanation
Depending on which event/handler is targeted, this crosses a real trust boundary between organizations sharing one Shipit deployment:
- `PushHandler` calls `stack.sync_github(expected_head_sha:)` for stacks matching the forged branch, letting the attacker force a specific commit SHA to be treated as the new head to sync/deploy for a victim's stack. [7](#0-6) 
- `StatusHandler` injects arbitrary/forged CI status entries onto a victim's commits, which can influence deploy-gating logic (`create_status_from_github!`). [8](#0-7) 
- `CheckSuiteHandler` schedules check-run refreshes for a victim's commits. [9](#0-8) 
- `PullRequest::*Handler`s (opened/closed/labeled/etc.) can affect review-stack provisioning and pull-request state tracking on a victim repository via `Repository.from_github_repo_name(params.repository.full_name)`. [10](#0-9) 

This is a cross-repository/cross-organization write achieved by an unprivileged attacker who only controls one tenant's own webhook secret - matching the "cross-repository writes" / escalation-of-authorization-boundary impact class. It does not directly leak `GITHUB_TOKEN` or achieve RCE, but it does let one tenant's credentials act on another tenant's repository state, which is the core boundary this engine is supposed to enforce per-organization via `Shipit.github(organization:)` app configs.

### Likelihood Explanation
Requires only that the Shipit instance is configured with more than one organization/app entry in `Shipit.github` config (multi-tenant deployment, the documented normal configuration) and that the attacker has legitimate access to one org's `webhook_secret` (e.g., they administer that GitHub App installation or repo, which is the expected trust level for triggering webhooks for their own org). No privileged Shipit account, API token, or the victim's secret is required - only a valid signature over an attacker-authored payload. This is straightforward for anyone controlling one tenant to exploit against another tenant's stacks on the same instance.

### Recommendation
Bind the signature-verification identity to the same field used for repository resolution. Concretely, `WebhooksController#repository_owner` (used to select the verifying `webhook_secret`) must be reconciled with `repository.full_name`'s owner before dispatching: reject the payload if `repository.full_name`'s owner segment does not case-insensitively match `repository_owner`, or better, resolve the target `Repository` first via `Repository.from_github_repo_name(payload full_name)` and verify the signature using the `webhook_secret` associated with that specific repository's stored organization, not a value taken directly from the unverified body.

### Proof of Concept
1. Attacker administers `github.attacker-org` app in Shipit's config with known `webhook_secret_A`.
2. Victim's `github.victim-org` app also configured, `webhook_secret_B` unknown to attacker; victim owns stack for `victim-org/prod-app`.
3. Attacker builds payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/prod-app"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(webhook_secret_A, body)` and sets `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` → `"attacker-org"` → `Shipit.github(organization: "attacker-org")` → verifies successfully with `webhook_secret_A`. [1](#0-0) 
6. `create` dispatches to `PushHandler`, which resolves `stacks` via `Repository.from_github_repo_name("victim-org/prod-app")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim's stack. [7](#0-6) [3](#0-2)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
