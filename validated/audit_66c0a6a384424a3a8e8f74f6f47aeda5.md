### Title
`OpenedHandler#provision?` operator-precedence bug bypasses `review_stacks_enabled` for `prevent_with_label` and `allow_with_label` repositories - ([File: app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb])

### Summary
`OpenedHandler#provision?` intends `repository.review_stacks_enabled` to gate *all* provisioning behaviors, as documented in `docs/review_stacks.md` ("Check 'Dynamically provision stacks for Pull Requests?'" is step 1 before selecting any behavior). Because Ruby's `&&` binds tighter than `||`, the flag only actually gates the `allow_all` branch, letting any PR author create a `Shipit::ReviewStack` on a repository with `review_stacks_enabled: false` as long as `provisioning_behavior` is `prevent_with_label` (by omitting the label) or `allow_with_label` (by adding the label).

### Finding Description
The broken binding: `repository.review_stacks_enabled` (as configured by the repo owner to mean "no review-stack behavior of any kind") **should equal** the boolean actually consulted before `ReviewStack.create!` runs for every behavior branch. It does not.

Code:
```ruby
# app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:65-70
def provision?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Ruby precedence parses this as:
```
(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)
```
`review_stacks_enabled` is not distributed across the `||` terms, so it only constrains the first disjunct. For a repository with `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, opening a PR with **no label** makes the third disjunct `true && true == true`, so `provision?` returns `true` regardless of `review_stacks_enabled`.

Call path: an unprivileged GitHub user opens a PR on a repository owned by someone else but registered in Shipit → GitHub sends the `pull_request` `opened` webhook → `OpenedHandler#process` calls `respond_to_pull_request_opened?` → `provision?` returns `true` → `ReviewStackAdapter.new(params, scope: repository.review_stacks).find_or_create!` → `create!` builds a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` (attacker-controlled) and immediately calls `Shipit::ReviewStackProvisioningQueue.add(stack)`, queuing infrastructure provisioning. [2](#0-1) [3](#0-2) 

None of the standard guards prevent this: webhook signature verification and `drop_unhandled_event` only authenticate that the payload genuinely came from GitHub for a tracked repo — they don't validate the *business logic* choice of whether review stacks should be created. `ExplicitParameters` validates the payload shape, not the provisioning decision. `Repository#review_stacks_enabled` itself has no validation tying it to `provisioning_behavior`. The existing test suite's "create stacks for repos what prevent_with_label when label is absent" test (`test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb:159-172`) uses `configure_provisioning_behavior`'s default `provisioning_enabled: true`, so it never exercises the `review_stacks_enabled: false` case and doesn't catch this divergence. [4](#0-3) 

### Impact Explanation
Any unprivileged contributor who can open a pull request against a repository tracked by Shipit — one that has explicitly disabled review-stack auto-provisioning (`review_stacks_enabled: false`) but happens to have `provisioning_behavior: prevent_with_label` (or `allow_with_label` with the label present) — can force creation of a `Shipit::Stack`/`ReviewStack` row and enqueue it for provisioning, with `branch` set to the attacker's own `head.ref`. This is a cross-boundary write: infrastructure gets provisioned for a repository/environment that never opted in, using attacker-controlled branch data, without any Shipit session or credential. Depending on the host application's registered `ProvisioningHandler`, this can result in real resource allocation/deployment against attacker-chosen code. This is repeatable against any repository configured this way and is not scoped to a single PR.

### Likelihood Explanation
Preconditions are narrow but realistic: the repository must have `provisioning_behavior` set to `prevent_with_label` (or `allow_with_label`) while `review_stacks_enabled` is `false` — a plausible misconfiguration/legacy state, since the UI historically toggled these together but the code does not enforce the coupling. Attacker cost is trivial: open a PR (optionally without any label, or with the label for the `allow_with_label` case). No secrets, sessions, or privileged roles are required, and the action is fully repeatable.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates every branch, e.g.:
```ruby
def provision?
  repository.review_stacks_enabled? && (
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
  )
end
```

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/opened_handler_test.rb`, add:
```ruby
test "does not create stacks for prevent_with_label repos when review_stacks_enabled is false" do
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,   # repository.review_stacks_enabled == false
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_opened)
  payload["pull_request"]["labels"] = []  # no label -> prevent_with_label branch fires

  assert_no_difference -> { Shipit::ReviewStack.count } do
    OpenedHandler.new(payload).process
  end
end
```
Before the fix: `Shipit::ReviewStack.count` increments (the assertion fails), demonstrating `provision?` returns `true` even though `repository.review_stacks_enabled == false`. After applying the recommended fix, the count stays unchanged, restoring the equality between the configured `review_stacks_enabled` flag and the value actually consulted.
