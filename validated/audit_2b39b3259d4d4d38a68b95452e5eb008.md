### Title
Cross-tenant Status forgery via unscoped SHA lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits with `Commit.where(sha: params.sha)` across the *entire* `commits` table with no filter on `stack_id` or repository, then calls `create_status_from_github!` on every match. Because a `sha` is only unique within the context of a single git repository, but Shipit's `Commit` table has no cross-stack uniqueness or repository-scoping guarantee on `sha`, a legitimately signed webhook for one stack/repository can write a forged `Status` onto a `Commit` row belonging to a completely unrelated stack that happens to share the same sha (e.g. a common ancestor commit, or the well-known empty-tree sha `4b825dc642cb6eb9a060e54bf8d69288fbee4904`).

### Finding Description
The broken binding is: **sha equality between `Commit` row X in stack A and `Commit` row Y in stack B implies repository/stack equality** — this is false in general (shared history, forks, or a trivially mintable sha like the empty tree).

Code path:
- `Shipit::WebhooksController#create` parses the raw JSON payload and dispatches to handlers for the event type after `verify_signature`, which only checks that the HMAC signature matches the GitHub App secret for `repository_owner` (`params.dig('repository','owner','login')`) — it does **not** bind the payload to any specific `Stack` row. [1](#0-0) 
- `StatusHandler#process` then resolves target commits purely by `sha`, with no stack/repository filter: [2](#0-1) 
- `Commit#create_status_from_github!` unconditionally writes the status to whichever `Commit` row was matched, using that row's own `stack_id`: [3](#0-2) 

Exploit flow: an attacker owns repository A, which is tracked by Shipit as stack A (attacker can push/PR/create branches there without any special Shipit privilege). Attacker crafts or naturally has a commit in repo A whose sha collides with a `Commit` row already synced into victim stack B — this can occur legitimately via a shared merge-base/common ancestor between forks, or deterministically via the universal empty-tree sha, which any git repository can contain (e.g., as a parent of an orphan/squash commit) and is often present in real repo histories. GitHub sends a real, correctly signed `status` webhook for repo A's commit (signature validated correctly for org A — the attacker needs no secrets, GitHub signs it for them). `StatusHandler#process` ignores which repository/stack the webhook came from and matches by sha alone, so if stack B also has a `Commit` row with that sha, `create_status_from_github!` is invoked on B's row, writing a new `Shipit::Status` (arbitrary `state`, `description`, `target_url`, `context`) into victim stack B. Since `Status#success?`/CI gating drives `deployable?` and `schedule_continuous_delivery`, this can flip a victim commit to "deployable" and trigger continuous deployment.

Existing guards do not stop this: `verify_signature` only proves the payload's origin organization owns a valid webhook secret for *that* org/repo — it says nothing about which `Commit`/`Stack` rows the payload may mutate. There is no `stack_id` or repository check anywhere in `StatusHandler#process` or `Commit.create_status_from_github!`.

### Impact Explanation
A payload legitimately signed for attacker-controlled repository A results in a `Status` row being written against a `Commit` belonging to victim stack B — a payload for one repository mutating another's commit/stack state, matching the **Critical** category ("a payload for one repository mutating another's stack, commit, task or team"). Repeatable against any pair of stacks whose commit tables intersect on a sha (trivially achievable via the empty-tree sha, common fork ancestry, or synced upstream commits). Blast radius spans all tenants sharing the Shipit instance since the query has no repository scoping at all.

### Likelihood Explanation
Preconditions: the victim stack B must have a `Commit` row with a sha that also exists in the attacker's own repo A (empty-tree sha is the simplest, most reliable trigger since it's mintable in any repo and often already present in synced history of merge-heavy repos). No Shipit session, API token, or GitHub secret is required — GitHub itself signs the webhook when the attacker acts within their own repository. Attacker cost is low: create/observe a commit whose sha collides, wait for or trigger a `status` event from CI/any integration on repo A. Fully repeatable and scriptable.

### Recommendation
Scope the lookup by the reporting repository, not sha alone: resolve the `Stack`(s) matching `params.dig('repository','full_name')` (or `id`) from the payload, then filter `Commit.where(sha: params.sha, stack_id: matching_stack_ids)` before calling `create_status_from_github!`. Alternatively, join through `stack.repository` to assert `commit.stack.repository.full_name == payload_repository_full_name` for every candidate before writing.

### Proof of Concept
Minitest (`test/models/webhooks/handlers/status_handler_test.rb`-style, no live GitHub):
1. Create `stack_a` (repository `attacker/repo`) and `stack_b` (repository `victim/repo`).
2. Create `commit_a = shipit_commits(:stack_a) ` with `sha: "4b825dc642cb6eb9a060e54bf8d69288fbee4904"`, `stack: stack_a`.
3. Create `commit_b` with the **same sha**, `stack: stack_b` (simulating a shared ancestor/empty-tree commit synced into victim stack).
4. Build a signed `status` webhook payload for `attacker/repo` with `sha` = that value, `state: "success"`.
5. POST to `/webhooks` with a signature computed using stack A's GitHub App secret (a valid, "attacker-affordable" signature since GitHub would sign it for real in production).
6. Assert: `commit_b.reload.statuses.count == 1` and `commit_b.status.success?` — i.e., the victim stack B's commit received a status forged via a payload that only ever authenticated repository A.
7. Equality check before: `commit_a.sha == commit_b.sha` (true) but `commit_a.stack_id != commit_b.stack_id` (true) — the vulnerability is that `StatusHandler#process` treats sha equality as authorization to write, violating this inequality.
