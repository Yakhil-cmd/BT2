### Title
Webhook signature verified against attacker-controlled organization, but payload processed against a different organization's repository - Cross-tenant unauthorized deploy sync (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The `WebhooksController#verify_signature` method selects which organization's `webhook_secret` to use for HMAC verification based on a value read directly out of the *unverified* JSON body (`params.dig('repository', 'owner', 'login')`), rather than from any value tied to the actual repository record the event will act on. Every webhook handler, however, resolves the target `Repository`/`Stack` from a different field in that same unverified body: `payload.dig('repository', 'full_name')`. These two fields are never checked against each other, so a signature that is valid for organization A's secret can be replayed with a payload whose `repository.full_name` names a repository belonging to organization B, causing Shipit to act on organization B's stack under a signature that only proves knowledge of organization A's secret.

### Finding Description
`verify_signature` derives the signing organization purely from body content and picks the matching `GithubApp`/secret: [1](#0-0) [2](#0-1) 

It then verifies the HMAC of the *entire raw body* using that organization's `webhook_secret`: [3](#0-2) 

This proves only "whoever crafted this exact JSON body knows organization X's secret" — it does not prove that organization X actually owns the repository referenced elsewhere in the same body. After the signature check passes, the raw, attacker-supplied `params` are handed unmodified to the event handlers: [4](#0-3) 

Every handler resolves the target repository/stack from `payload.dig('repository', 'full_name')`, a field independent of the one used to pick the verification secret: [5](#0-4) [6](#0-5) 

For example, `PushHandler` uses this to look up the stacks and immediately triggers a GitHub sync to an attacker-chosen `after` SHA: [7](#0-6) 

`CheckSuiteHandler` similarly schedules check-run refreshes for commits on a stack resolved the same way: [8](#0-7) 

Shipit is explicitly designed to be configured with multiple independent organizations/apps, each with its own `webhook_secret`, as shown in the sample multi-org config: [9](#0-8) 

This creates the exact binding break the report's pattern describes: the entity that authenticates (organization X, via its own `webhook_secret`) is not the entity that gets written to (repository/stack under organization B, resolved from `repository.full_name`). Before the attack: only organization X's own GitHub App can produce webhooks that act on organization X's repositories. After the attack: an attacker who legitimately administers organization X's GitHub App (and therefore knows X's `webhook_secret`, e.g. by configuring it themselves) can forge a POST to `/webhooks` with `repository.owner.login: "X"` (to pass signature verification with X's known secret) but `repository.full_name: "B/victim-repo"`, causing Shipit to sync/act on organization B's stack — a repository the attacker has no legitimate relationship with.

### Impact Explanation
This breaks the equality `organization authenticated == organization/repository written`. On a multi-tenant Shipit install (multiple orgs configured under `github:`), any org admin who can obtain/set a `webhook_secret` for their own org's app can forge signed events that make Shipit sync arbitrary other tracked stacks to an attacker-chosen commit SHA (`PushHandler`) or trigger check-run refresh / status processing for commits on stacks they do not control. Depending on downstream automation (auto-deploy on sync, merge-queue behavior tied to check runs/statuses), this can escalate into an unauthorized deploy or merge action against a repository/organization the attacker does not own — satisfying the "unauthorized deploy" bar without any Shipit session, `ApiClient` token, or GitHub write access to the victim repository.

### Likelihood Explanation
Requires the attacker to control a GitHub App/organization that is one of the (possibly many) organizations configured on the same shared Shipit instance — i.e., administrative control of their *own* onboarded org's webhook secret, not any privileged access to the victim org or a Shipit account. This matches the "unprivileged attacker crossing a deployment-trust binding" class the scan is scoped to. It does not depend on rate limiting, DoS, or any out-of-scope mechanism.

### Recommendation
Bind signature verification to the same identity used for downstream repository resolution: verify the signature using the secret associated with the `Repository` actually resolved from `repository.full_name` (or, conversely, resolve the repository/stack only from an organization value that was itself authenticated), and reject the webhook if `repository.owner.login` does not match the owner portion of `repository.full_name`.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (per `config/secrets.*.yml` multi-org pattern).
2. Attacker, as admin of `attacker-org`'s GitHub App, knows `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `push` payload body:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": {
       "owner": { "login": "attacker-org" },
       "full_name": "victim-org/victim-repo"
     }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=<hmac>` using `attacker-org`'s known secret over the raw body, per `DeliverySigner`/`verify_webhook_signature` logic [3](#0-2) .
5. POSTs to `/webhooks` with header `X-Github-Event: push`. `verify_signature` picks `attacker-org`'s secret (from `repository.owner.login`) and the HMAC matches, so the request passes [1](#0-0) .
6. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` [7](#0-6)  — acting on `victim-org`'s stack despite the signature only proving knowledge of `attacker-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
