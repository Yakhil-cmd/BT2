### Title
`StatusHandler#process` writes GitHub commit statuses to every `Commit` row sharing a `sha` across all repositories, with no repository binding - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `Commit.where(sha: params.sha)` and mutates every match, without ever comparing the payload's `repository.full_name` to the matched commit's stack/repository. This is inconsistent with sibling handlers (e.g. `PushHandler`, `CheckSuiteHandler`, and the PR handlers) which all filter through the `Handler#stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)`.

### Finding Description
Binding that should hold for every mutated row: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')`. This equality is never evaluated in `status_handler.rb`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) only proves that the signature is valid for `repository_owner` (`params.dig('repository','owner','login')`) — i.e., that the sender legitimately controls a GitHub App/webhook for *some* repository owned by that account/org. It never checks that the sha embedded in the payload actually belongs to that repository.
- `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler.call(params)` (`app/controllers/shipit/webhooks_controller.rb:12`).
- `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped lookup across the entire `commits` table.
- The base `Handler` class defines a `stacks` helper (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) that resolves `Repository.from_github_repo_name(repository_name)&.stacks`, and this is used by `PushHandler`, `CheckSuiteHandler`, and all `PullRequest::*Handler` classes to scope their queries to the repository named in the payload. `StatusHandler` is the outlier that skips this scoping entirely.

Because git commit SHAs are content-addressed, the same SHA legitimately exists in multiple independent repositories whenever they share history — most commonly via forks, but also via cherry-picks, branch merges across separate GitHub repos, or repositories that were imported/duplicated. Any GitHub user who owns a fork of a repository tracked by Shipit (or any repository whose GitHub App installation is authorized to send status webhooks) can trigger a `status` event carrying a SHA that also exists in an unrelated victim repository's Shipit stack. The victim's `Commit` row will receive the attacker's status update even though the victim repository never authenticated or was party to that webhook. `verify_signature` cannot prevent this because it validates *who sent* the payload, not *which commit/repository the sha belongs to*; there is no application-level equality check tying the two together.

### Impact Explanation
An attacker who controls (or forks) any repository can cause an arbitrary `Status` record to be created on a `Commit` belonging to a completely different tenant/repository/stack, as long as a SHA collision exists (trivially achievable via forking). Since Shipit deploy gating (`Stack#calculate_undeployed_commits`, statuses used for `Task`/`Deploy` checks, CI required-status gates) relies on `Commit` statuses, this can be used to spoof a passing/failing check on another tenant's commit, potentially unblocking or blocking deploys for a stack the attacker never authenticated against. This is a cross-tenant record mutation — matching the "payload for one repository mutating another's stack, commit, task or team" Critical category.

### Likelihood Explanation
Preconditions: the attacker needs a GitHub repository (e.g., a public fork of the victim's repo) with the Shipit GitHub App/webhook installed, which any GitHub user can typically do for their own fork of a public open-source project without any special privilege. Fork commits from before divergence share identical SHAs with upstream by construction, so the SHA collision precondition is met automatically and requires no brute force. Sending a crafted `status` webhook from the attacker's own repo is a normal, unprivileged webhook delivery. This is fully repeatable against any SHA the attacker knows is shared with a victim stack.

### Recommendation
Scope the lookup in `StatusHandler#process` to the repository named in the payload, mirroring the pattern used elsewhere, e.g.:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
using the existing `Handler#stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) so that only commits belonging to stacks of the repository that authenticated the webhook are mutated.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create three `Repository`/`Stack` records for three distinct `full_name`s (e.g. `"acme/one"`, `"acme/two"`, `"acme/three"`).
2. Create a `Commit` under each stack, all sharing the identical `sha` value `"deadbeef"`.
3. Build a status payload: `{ 'sha' => 'deadbeef', 'state' => 'success', 'repository' => { 'full_name' => 'acme/one' } }`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `commit_one.statuses.reload.count == 1` (expected, correctly scoped) — but also assert `commit_two.statuses.reload.count == 1` and `commit_three.statuses.reload.count == 1`, i.e. `commit.stack.repository.full_name == payload.dig('repository','full_name')` is **false** for `commit_two`/`commit_three` yet a status was still written, proving the binding is not enforced. After the fix, only `commit_one` should have a status.
