### Title
Reward precision loss from division-before-multiplication during Alpenglow migration epoch reward calculation - (File: `runtime/src/inflation_rewards/mod.rs`)

### Summary
`calculate_stake_rewards` computes tower-epoch rewards during the one-time Tower→Alpenglow migration epoch by performing two sequential "multiply-then-divide" operations instead of accumulating all multiplications before a single final division. This is the same anti-pattern flagged in the referenced Ajna report ("division before multiplication"), and it causes avoidable precision loss (and can zero out) legitimately earned staking rewards.

### Finding Description
In the `AlpenglowEpochType::MigrationEpoch` branch of `calculate_stake_rewards`, `tower_points` is first scaled to lamports and then re-scaled by the fraction of the epoch spent under Tower consensus: [1](#0-0) 

```rust
AlpenglowEpochType::MigrationEpoch {
    num_tower_slots,
    num_ag_slots,
    ..
} => {
    ...
    let total_slots = (num_tower_slots + num_ag_slots) as u128;
    let tower_points = tower_points
        .checked_mul(u128::from(point_value.rewards))
        .expect("Rewards intermediate calculation should fit within u128")
        .checked_div(point_value.points)
        .unwrap()
        .checked_mul(*num_tower_slots as u128)
        .unwrap()
        .checked_div(total_slots)
        .unwrap();
    tower_points + ag_points
}
```

The mathematically correct computation is:
```
reward = tower_points * point_value.rewards * num_tower_slots / (point_value.points * total_slots)
```
i.e. all multiplications should be performed before the single division. Instead, the code divides by `point_value.points` first (`checked_div(point_value.points)`), truncating to an intermediate integer, and only then multiplies by `num_tower_slots` and divides again by `total_slots`. Each `checked_div` truncates independently, so the two sequential truncations compound and can discard more precision than a single combined division would — in the worst case reducing a staker's or voter's migration-epoch reward to 0 even though a non-zero reward is mathematically owed.

This mirrors exactly the flagged Ajna pattern: `Maths.wmul(REWARD_FACTOR, Maths.wdiv(Maths.wmul(interestEarned_, totalBurnedInPeriod), totalInterestEarnedInPeriod))`, where the final multiplication happens after (not before) the division.

By contrast, the analogous Alpenglow-only points computation in `calculate_alpenglow_points` correctly performs all multiplication before the single division: [2](#0-1) 

which does not exhibit this bug, confirming the migration-epoch branch is the outlier.

### Impact Explanation
This function computes `stake_reward`/`voter_reward` payouts that are directly credited to stake and vote accounts as part of epoch-boundary reward distribution (`redeem_delegation_rewards` → `redeem_rewards` → `calculate_stake_rewards`), i.e. it is a "stake and reward accounting" code path. The double-truncation causes systematic under-payment of rewards during the migration epoch, and for small enough `tower_points`/`num_tower_slots` ratios it can round a nonzero deserved reward down to exactly zero, permanently forfeiting that staker's/voter's rewards for the migration epoch (rewards are not retried or made up later). This constitutes stake/reward corruption (silent underpayment) rather than a fund-safety break, and it is confined to the single, one-time Tower→Alpenglow migration epoch, limiting its overall blast radius.

### Likelihood Explanation
The migration epoch occurs exactly once per cluster (the Tower-to-Alpenglow consensus switch), so the affected code path executes deterministically for every stake account during that one epoch. Any staker/voter whose combination of `tower_points`, `point_value.rewards`, `point_value.points`, `num_tower_slots`, and `total_slots` produces a small intermediate quotient will be under-rewarded; this is a function of naturally varying real-world stake/credit distributions rather than an attacker needing special privileges, so the condition is likely to be triggered for at least some low-stake or short-participation accounts during migration.

### Recommendation
Restructure the migration-epoch reward computation to perform all multiplications before the single division, using `u128`/wider intermediate arithmetic to avoid overflow, e.g.:
```rust
let tower_points = tower_points
    .checked_mul(u128::from(point_value.rewards))
    .and_then(|v| v.checked_mul(*num_tower_slots as u128))
    .expect("...")
    .checked_div(point_value.points.checked_mul(total_slots).expect("..."))
    .unwrap();
```
This collapses the two independent truncations into a single final division, minimizing precision loss and avoiding erroneous zero-reward outcomes.

### Proof of Concept
Given (illustrative, integer arithmetic):
- `tower_points = 3`
- `point_value.rewards = 5`
- `point_value.points = 10`
- `num_tower_slots = 1`
- `total_slots = 3`

Correct order: `3 * 5 * 1 / (10 * 3) = 15 / 30 = 0` (in this particular case both orders round to 0, but consider):
- `tower_points = 7`
- `point_value.rewards = 5`
- `point_value.points = 10`
- `num_tower_slots = 2`
- `total_slots = 3`

Correct combined order: `7*5*2 / (10*3) = 70/30 = 2`
Current code's order: `(7*5/10) * 2 / 3 = (35/10=3) * 2 / 3 = 6/3 = 2` — matches here, but with different magnitudes (e.g. `tower_points=1, rewards=1, points=2, num_tower_slots=1, total_slots=2`): correct = `1*1*1/(2*2) = 1/4 = 0`; current code = `(1*1/2=0) *1/2 = 0` — equal again. The divergence manifests when the first division truncates a value that would not have truncated to 0 after full-numerator division, e.g. `tower_points=3, rewards=1, points=4, num_tower_slots=3, total_slots=2`: correct = `3*1*3/(4*2)=9/8=1`; current code = `(3*1/4=0)*3/2=0`, producing 0 instead of the deserved 1 — demonstrating the reward-loss-to-zero behavior described.
