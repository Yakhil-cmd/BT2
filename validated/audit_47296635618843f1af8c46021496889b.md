### Title
Cross-repository commit status forgery via unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's `status` webhook handler updates a `Commit`'s CI status by looking it up **only by SHA**, without checking that the SHA belongs to the repository the incoming webhook actually claims to originate from. Since git commit SHAs are content-addressed and public, and the handler never scopes the query to the sending repository/organization, an attacker with legitimate push/status access to any repository registered on the same (or another) Shipit-connected GitHub App installation can forge a `status` event whose payload SHA matches a commit that actually belongs to a completely different, higher-trust stack. This lets them inject arbitrary CI status (e.g. `success`) onto that unrelated commit, breaking the binding between "the organization/repository that authenticated the webhook" and "the commit that gets written."

### Finding Description
Webhook authenticity in Shipit is established purely at the HTTP layer: `WebhooksController#verify_signature` picks a `GitHubApp` config using `repository_owner` from the payload and validates the HMAC signature [1](#0-0) . Once that check passes, the raw payload is handed to the matching event handler with no further repository-ownership validation performed by the controller [2](#0-1) .

The base `Handler` class provides a `stacks` helper explicitly meant to scope any subsequent lookups to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) . Handlers like `PushHandler` and `CheckSuiteHandler` correctly use this scoping before touching any records [4](#0-3) [5](#0-4) .

`StatusHandler`, however, never calls `stacks` or checks `repository_name` at all. It resolves the target purely from `params.sha` across the **entire** `Commit` table and mutates whatever it finds:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 

Because git commit SHAs are computed only from commit content (tree, parent, author/committer, message/timestamps) and are not scoped to a specific GitHub repository, an attacker can reproduce an identical SHA in a repository they control by pushing a commit object with the same tree/parent/metadata as a target commit in a completely different (higher-trust) stack — all of that metadata is public via the GitHub API/`git clone`. They can then set a commit status via the GitHub Status API on their own repository for that SHA. GitHub will deliver a legitimately-signed `status` webhook (signed by their own organization's App installation secret, or any org onboarded to the same Shipit instance), which passes `verify_signature` because signature validity only proves *who sent it*, not *which commit/stack it is entitled to affect*.

**Binding broken:** the organization/repository that authenticated the webhook (attacker's own low-privilege repo/org) ≠ the repository/stack whose commit status actually gets written (an unrelated, possibly higher-trust stack), because `StatusHandler` never re-derives or checks `repository_name`/`stacks` before mutating the `Commit`.

### Impact Explanation
Commit statuses gate both the merge queue and deploy readiness in Shipit (`MergeRequest::StatusChecker`, `all_status_checks_passed?`, required/blocking statuses defined via `shipit.yml`) [7](#0-6) . By forging a `success` status on a commit belonging to a repository/stack the attacker does not control, they can satisfy CI requirements that gate an **unauthorized deploy or an unauthorized pull-request merge** on that stack — this matches the "High" impact bucket (escalation enabling unauthorized deploy/merge) defined in scope.

### Likelihood Explanation
Exploitation requires: (1) push/status-setting access to at least one repository connected to a Shipit-managed GitHub App installation (a low bar — any onboarded, less-trusted repo/org qualifies as an "unprivileged" foothold relative to the target stack), and (2) the ability to reproduce a target commit's SHA, which is achievable because all inputs to a git commit hash (tree, parents, author/committer, timestamps, message) are public for any commit visible on GitHub. This is a deterministic, non-probabilistic operation (no hash collision needed — the attacker constructs a byte-identical commit object), making likelihood high once repository access is obtained.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the stacks derived from the webhook's own `repository_name` (as `PushHandler`/`CheckSuiteHandler` already do), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or filter by `commit.stack.repository == Repository.from_github_repo_name(repository_name)`, and reject/ignore statuses whose payload repository does not match the commit's owning repository.

### Proof of Concept
1. Attacker is a legitimate, low-privilege contributor with push/status access to `attacker-org/decoy-repo`, which is registered as a Shipit stack (any org with a configured GitHub App entry works, per `docs/setup.md` multi-org config [8](#0-7) ).
2. Attacker identifies a target commit `sha` on `victim-org/critical-repo` that a Shipit merge queue or continuous-deployment stack is waiting on a required CI context for.
3. Attacker reconstructs an identical git commit object (same tree, parent, author/committer/timestamps/message) inside `decoy-repo`, producing the same SHA, and pushes it.
4. Attacker calls the GitHub Statuses API (`POST /repos/attacker-org/decoy-repo/statuses/:sha`) with `state=success`, `context=<the required context>`.
5. GitHub delivers a validly-signed `status` webhook for `attacker-org` to Shipit's `/webhooks` endpoint; `verify_signature` passes because the signature is valid for `attacker-org`'s own webhook secret [1](#0-0) .
6. `StatusHandler#process` finds the `Commit` row with matching `sha` — which actually belongs to `victim-org/critical-repo` — and calls `create_status_from_github!`, marking it `success` [6](#0-5) .
7. The victim stack's merge queue or continuous-deployment job now sees the required status as passing and proceeds to merge/deploy without legitimate CI having run.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
