### Title
RAY debt valuation overflows before the borrow-index cap and permanently freezes a market - ([File: common/src/rates/index.rs])

### Summary
An unprivileged borrower can place a sufficiently large, high-utilization debt position in an uncapped or high-cap market and keep it outstanding until routine accrual overflows `i128` inside `scaled_to_original` / `Ray::mul`. The configured `MAX_BORROW_INDEX_RAY` cap does not protect the market because debt valuation overflows before the capped index is reached. After that point, every operation that first synchronizes the market—including `repay`, `withdraw`, `liquidate`, `clean_bad_debt`, and `update_indexes`—reverts with `MathOverflow`, permanently locking the market's supplied funds and outstanding debt.

### Finding Description
`accrue_step` unconditionally unscales the total borrowed and supplied RAY values before computing utilization and the next indexes: `scaled_to_original(borrowed, borrow_index)` and `scaled_to_original(supplied, supply_index)`. [1](#0-0)  `scaled_to_original` performs a checked fixed-point multiplication and therefore panics once `scaled * borrow_index` exceeds the representable RAY domain. [2](#0-1) 

Although `update_borrow_index` caps the newly calculated index at `MAX_BORROW_INDEX_RAY`, that cap is applied only after the current debt value has already been unscalescaled. [3](#0-2)  The same unchecked-by-design value conversion also appears when supplier rewards compare old and new total debt. [4](#0-3) 

The pool's mutating synchronization runs `accrue_step` for every elapsed chunk and records the resulting indexes. [5](#0-4)  Repayment and withdrawal each load the market leg, which performs this synchronization before resolving or burning shares. [6](#0-5) [7](#0-6)  Because the stale `last_timestamp` is not committed when the overflow panics, every later call repeats the same failing accrual.

The repository's long-horizon harness demonstrates the exact condition: it creates a very large 18-decimal market, borrows 98% of it, repeatedly advances ledger time, receives `MATH_OVERFLOW` below `MAX_BORROW_INDEX_RAY`, and then confirms that both withdrawal and repayment fail. [8](#0-7) 

### Impact Explanation
This is a market-wide permanent freeze of user funds. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and permissionless bad-debt cleanup cannot progress because these paths require the pool market to synchronize first. The failure is permanent rather than temporary: ledger timestamps never decrease, so the next accrual always attempts the same overflowing multiplication and panics before any state update is persisted. Once crossed, the market cannot recover through the exposed user-facing entrypoints, leaving supplied liquidity inaccessible and protocol debt accounting unresolvable.

### Likelihood Explanation
The exploit requires an admitted market whose decimal scale and configured supply/borrow caps allow enough scaled exposure that a later borrow index pushes `scaled * index` past `i128::MAX`. It also requires the attacker or attacker-controlled accounts to fund the collateral needed to maintain very high utilization. Those are substantial economic and configuration prerequisites, but no privileged runtime action is required after the market configuration exists: the attacker uses ordinary `supply` and `borrow`, and any public `update_indexes` or market operation can trigger the cliff after sufficient accrual. The production documentation explicitly recognizes that finite RAY value capacity can be exhausted before the index ceiling and that synchronization of an overlarge book can then fail. [9](#0-8) 

### Recommendation
Bound the total stored scaled debt and supply conservatively at market admission and at every public mint so that `scaled * MAX_BORROW_INDEX_RAY` and `scaled * MAX_SUPPLY_INDEX_RAY` cannot exceed the arithmetic domain. In addition, make `accrue_step` use a saturating or pre-clamped debt valuation path before multiplying by the live index, or clamp `borrowed`/`supplied` to a protocol-safe maximum before unscale. Add regression coverage that attempts `update_indexes`, `withdraw`, `repay`, `liquidate`, and `clean_bad_debt` after the boundary and verifies that risk-reducing and exit paths remain executable.

### Proof of Concept
The repository already contains a working reproduction in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`. Its sequence is:

1. Create an 18-decimal market and collateral market, then remove utilization limits and raise the market caps in the fixture.
2. Have an unprivileged supplier call the normal `supply` path with `1_000_000_000 * 10^18` asset units.
3. Have an unprivileged borrower supply sufficient collateral and call `borrow` for 98% of that market.
4. Advance the ledger and call `update_indexes` until `scaled_to_original` overflows with `MATH_OVERFLOW`.
5. Call `withdraw` and `repay`; both revert with `MATH_OVERFLOW` because they synchronize the same market before applying the requested operation.

The test asserts that the last stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the arithmetic cliff occurs before the intended index cap can protect the market. [10](#0-9)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
