### Title
Any AA-controlled recipient can force a full revert of a multi-party payout AA by making its own trigger bounce, freezing distribution logic - ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) that distribute funds to multiple parties in a single response (e.g., an escrow/split AA paying buyer, seller, and marketplace) are vulnerable to a "push"-style denial-of-service. If any payout address belongs to another AA, the payment message causes that recipient AA to be invoked as a "secondary trigger." If the recipient AA's own logic bounces (which its author fully controls), the failure propagates up and causes the entire primary AA's response — including payments to all other, unrelated parties and any state updates — to be rolled back and bounced, exactly mirroring the reported "any party can reject receiving funds to prevent settling" bug class.

### Finding Description
When a primary AA sends payment outputs to an address, `sendUnit()` collects the set of unique output addresses (`arrOutputAddresses`) and, after the unit is saved, calls `handleSecondaryTriggers(objUnit, arrOutputAddresses)`. [1](#0-0) 

`handleSecondaryTriggers` looks up which of those output addresses are themselves AA addresses and invokes `handleTrigger` recursively for each one as a secondary trigger: [2](#0-1) 

Crucially, if the secondary AA's `handleTrigger` call bounces (`bounce_message` is truthy), the `async.eachSeries` callback receives an error, and — because the outer AA is not itself secondary — `revert()` is invoked on the entire primary AA execution: [3](#0-2) 

`revert()` rolls the whole primary trigger's state changes and responses back to the initial savepoint and re-bounces the primary trigger: [4](#0-3) 

This means a single hostile recipient AA — trivially deployable and controlled by any unprivileged party who is one of the intended payees (e.g., the "seller" in the reported escrow scenario) — can make its own AA logic bounce unconditionally (or conditionally on unfavorable data/amounts), which forces the *entire* primary distribution AA's response to be discarded every single time it tries to pay out. This is a direct analog of the reported "push over pull" vulnerability: any party who controls a receiving AA address can refuse to "receive" the payment (by bouncing) and thereby block settlement for all other parties, not just themselves.

Sample multi-party payout AAs in the codebase, such as the arbiter/escrow-style split payments in `test/samples/payment_channels.oscript` (paying `$addressA` and `$addressB` in one settlement message) and `ico_with_milestones.oscript`, demonstrate the general multi-recipient payment pattern that is exposed to this issue whenever a recipient address can be an AA: [5](#0-4) 

### Impact Explanation
An AA implementing dispute resolution, escrow splitting, or any batched multi-party payout is vulnerable to permanent freezing of funds and state: as long as one of the recipient addresses is a hostile AA programmed to bounce, every attempt by the primary AA to execute its distribution (and any associated state transition, such as marking a dispute as "resolved") is reverted. This denies settlement to all legitimate parties, not just the malicious one, and can permanently freeze the AA's balance since the state change that would allow retrying with a different logic path (if any) never commits either. This matches the "AA fund loss or freezing" impact category.

### Likelihood Explanation
Likelihood is high: any address holder can trivially post an AA definition, at zero extra privilege, that bounces unconditionally or bounces upon receiving splits it dislikes; they only need to be included in advance as a legitimate recipient (buyer/seller/marketplace-style party) in a payout AA's flow. No special network position, timing, or race condition is required — a single crafted AA definition and a single trigger payment reproduce the failure deterministically.

### Recommendation
Payout AAs that must guarantee finality of multi-party distributions should not rely on a single response unit's secondary-trigger success for all recipients. Consider: (1) sending payouts via independent transactions/response units per recipient so that one recipient's AA bouncing doesn't roll back payments already made to others, and/or (2) using a pull-based design where funds are credited to a per-recipient balance/state variable that the recipient (or their AA) must separately claim via a follow-up trigger, so a bounce during the claim only affects that recipient and does not revert the AA's other state changes. At the engine level, consider decoupling failures in secondary triggers spawned by output payments from the primary trigger's atomic success (e.g., not rolling back the *entire* primary response when only a downstream secondary AA bounces).

### Proof of Concept
1. Deploy AA `payer_aa` whose logic, on a trigger, sends outputs to two recipients: `victim` (an ordinary address) and `hostile_aa` (an AA address), mirroring the escrow split pattern (e.g. `test/samples/payment_channels.oscript` lines 76-88).
2. Deploy `hostile_aa` with a definition whose `messages`/`state` unconditionally calls `bounce(...)`, e.g. `{ messages: [{ app: 'state', state: "{ bounce('nope'); }" }] }`.
3. Fund `payer_aa` and post a trigger unit that causes `payer_aa` to execute its payout logic, sending funds to both `victim` and `hostile_aa`.
4. Observe in `aa_composer.js` that `handleSecondaryTriggers` invokes `hostile_aa`'s logic, which bounces; the `async.eachSeries` final callback in `handleSecondaryTriggers` (aa_composer.js:1743-1749) receives the bounce error and calls `revert()`, which rolls back `payer_aa`'s entire response — meaning `victim` never receives their intended share either, and `payer_aa`'s state update (e.g., marking the dispute/settlement as resolved) never commits.
5. Repeat the trigger: `payer_aa` bounces every time, permanently blocking distribution as long as `hostile_aa` remains a designated recipient.
