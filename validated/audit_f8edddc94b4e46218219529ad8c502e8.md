### Title
Webhook signature validated against `repository.owner.login`/`organization.login` while every event handler acts on the unvalidated `repository.full_name` field, enabling cross-organization stack manipulation in multi-org installs - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a payload against using `repository.owner.login` (falling back to `organization.login`), but every event handler (`Shipit::Webhooks::Handlers::Handler#repository_name` and its callers) resolves the target `Repository`/`Stack` to act on using the sibling field `repository.full_name` from the very same unvalidated JSON body. These two fields are never cross-checked against each other.

### Finding Description
In a multi-organization Shipit deployment (the documented and supported configuration, see `docs/setup.md` "Using Multiple Github Applications" and `test/dummy/config/secrets_double_github_app.yml`), each GitHub organization has its own GitHub App and its own `webhook_secret`.

`verify_signature` picks the app/secret to validate the HMAC with, based solely on: [1](#0-0) [2](#0-1) 

Once the signature check passes, the raw, fully-attacker-controlled JSON body is dispatched unmodified to handlers: [3](#0-2) 

Handlers determine what `Repository`/`Stack` to act on using a *different* field in the same body, `repository.full_name`: [4](#0-3) 

For example `PushHandler` triggers a git sync for any stack matching that repository/branch: [5](#0-4) 

and `PullRequest::OpenedHandler` looks up the repository the same way to auto-provision review stacks: [6](#0-5) 

There is no assertion anywhere that `repository.owner.login` (the field trusted to select the signing secret) equals the owner portion of `repository.full_name` (the field trusted to select the repository acted upon). The binding that should hold is:

`organization authenticated by verify_signature == owner(repository.full_name) acted on by the handler`

This binding is broken: an attacker who controls (or has compromised) the webhook secret for **one** organization configured in Shipit (e.g. `OrgOne`) can craft a payload where `repository.owner.login = "OrgOne"` (so the HMAC validates against `OrgOne`'s secret) but `repository.full_name = "OrgTwo/some-repo"`. The signature check passes because it only inspects `owner.login`, and the handler then acts on `OrgTwo`'s stack because it only inspects `full_name`.

### Impact Explanation
This allows an unprivileged-relative-to-`OrgTwo` attacker (who only administers `OrgOne`'s GitHub App/webhook secret) to inject forged, "authenticated" webhook events against a completely different organization's stacks:
- `push` events can force `Stack#sync_github` to run for `OrgTwo` stacks with an attacker-chosen `expected_head_sha`, potentially triggering downstream sync/deploy logic (`PushHandler`) against a repository the attacker has no legitimate GitHub access to.
- `pull_request` `opened`/`labeled`/`closed` events can create/merge/close review stacks (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`) for `OrgTwo`'s repositories.
- `membership`/`status`/`check_suite` events can create teams/users or affect commit status/check state for `OrgTwo`'s stacks.

This is a cross-repository/cross-organization write achieved purely by exploiting a mismatch between the field used for authentication and the field used to select the write target, satisfying the "cross-repository writes" / "unauthorized deploy" high-impact bar defined in the rules.

### Likelihood Explanation
Exploitation requires the attacker to possess a valid webhook secret for at least one organization configured in the same Shipit instance — this is realistic in any legitimate multi-tenant Shipit deployment where multiple, mutually-untrusting organizations/teams each administer their own GitHub App but share one Shipit instance (this is the exact scenario the engine documents and ships fixtures/tests for: `test/dummy/config/secrets_double_github_app.yml`, `test/unit/shipit_test.rb`). No GitHub write access, Shipit session, or `ApiClient` token is required — only the ability to sign an arbitrary payload with one org's webhook secret and POST it to the shared `/webhooks` endpoint.

### Recommendation
In `WebhooksController#verify_signature` (or immediately after, before dispatching to handlers), assert that the organization used to select/validate the signing secret matches the owner segment of `repository.full_name` (and of `organization.login` when present) before calling `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. Reject the request (e.g. `head(422)`) on mismatch.

### Proof of Concept
1. Deploy Shipit with the multi-org config shown in `docs/setup.md`/`test/dummy/config/secrets_double_github_app.yml`, with `OrgOne` and `OrgTwo` each having distinct `webhook_secret`s and each having a stack registered in Shipit.
2. As an attacker who only knows `OrgOne`'s `webhook_secret` (e.g., because they administer `OrgOne`'s GitHub App), craft a `push` payload:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgOne" },
    "full_name": "OrgTwo/victim-repo"
  }
}
```
3. Compute `X-Hub-Signature` as `sha1=` + HMAC-SHA1(`OrgOne`'s webhook secret, raw body).
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner` = `"OrgOne"`, loads `Shipit.github(organization: "OrgOne")`, and the signature validates successfully.
6. `PushHandler#process` resolves the target repository via `payload.dig('repository', 'full_name')` = `"OrgTwo/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` on `OrgTwo`'s stack — an action the attacker was never authorized to trigger.
