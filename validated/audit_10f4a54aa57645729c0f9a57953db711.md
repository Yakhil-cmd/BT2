### Title
Cross-stack read via unscoped `Stack.from_param!` in `Api::CCMenuController#stack` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` deliberately scopes stack lookups to `current_api_client.stack_id` via its private `stacks`/`stack` methods, so a token created with a `stack_id` binding can only ever resolve to that one stack. `Api::CCMenuController` overrides `stack` with a bare `Stack.from_param!(params[:stack_id])`, discarding that scoping entirely, so any valid `read:stack`-permissioned token can be replayed against an arbitrary `stack_id` in the URL to read another stack's deploy/rollback history.

### Finding Description
The intended binding is: for a stack-scoped `ApiClient`, `current_api_client.stack_id == resolved_stack.id` for every request that reaches `#show`.

In `Api::BaseController`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [1](#0-0) 

This scopes lookups so a stack-bound `ApiClient` can only resolve to its own stack; requesting any other `stack_id` 404s (`from_param!` raises against the scoped `.where(id: ...)` relation).

`Api::CCMenuController` overrides this method:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This calls `Stack.from_param!` directly on the unscoped class, ignoring `current_api_client.stack_id`. The only permission gate is `require_permission :read, :stack`, which delegates to `ApiClient#check_permissions!`:
```ruby
def check_permissions!(operation, scope)
  required_permission = "#{operation}:#{scope}"
  unless permissions.include?(required_permission)
    raise InsufficientPermission, ...
  end
  true
end
``` [3](#0-2) 

This only checks that the string `"read:stack"` is present in the client's `permissions` array — it never compares `stack_id` to the requested stack. So for a token whose `ApiClient` record has `stack_id = A.id` and `permissions = ["read:stack"]`, a request `GET /api/stacks/B/ccmenu.xml?token=<A's token>` passes `require_permission!` (permission string matches) and then `stack` resolves to stack B unconditionally, because `CCMenuController#stack` never consults `current_api_client.stack_id`.

`#show` then renders B's data with no further check:
```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end
``` [4](#0-3) 

`authenticate_api_client` is also overridden to accept the token via `params[:token]` instead of Basic Auth (needed for CCMenu XML clients), but this is orthogonal — it still calls the same `ApiClient.authenticate`, so the token itself is legitimately verified; the divergence is purely in the missing stack scoping in `#stack`.

### Impact Explanation
A holder of any legitimate stack-scoped CCMenu/API token with `read:stack` permission can enumerate/target arbitrary `stack_id` values and read another repository's/stack's deploy and rollback history, lock status, and last build status/label — data that should be restricted to the stack the token was issued for. This is an unauthorized cross-tenant read of stack state (deploy/rollback history, lock status), matching the High-severity category "unauthenticated/[cross-tenant] read of stack state" via a scoping bypass — here it is more precisely a scope-escalation read since the attacker does hold *a* valid token, just not one authorized for the target stack. It is repeatable against any stack in the installation and requires only one legitimately-obtained token (e.g., shared by a teammate, or self-issued for a stack they're permitted to view via `CCMenuUrlController`).

### Likelihood Explanation
Preconditions: the attacker must possess one valid CCMenu API token bound to some stack (easily obtained legitimately for any stack they have UI access to, via `CCMenuUrlController#fetch`, or leaked/shared). No GitHub secrets, session, or elevated role is needed. The attack is a single unauthenticated-cost GET request with a known/guessable `stack_id` (stack `to_param` is typically `owner/name/branch`, often discoverable). This is trivially repeatable and requires no special server configuration.

### Recommendation
Make `Api::CCMenuController#stack` reuse the scoped `stacks`/`stack` lookup from `Api::BaseController` instead of calling `Stack.from_param!` directly, e.g. remove the override so it inherits `BaseController#stack`, or scope it explicitly:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a stack-bound `current_api_client.stack_id` restricts resolution the same way it does for every other API controller.

### Proof of Concept
Minitest controller test (extends the existing `test/controllers/api/ccmenu_controller_test.rb` pattern):
```ruby
test "a token scoped to stack A cannot read stack B via ccmenu#show" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.create!(owner: "other", name: "repo"), branch: "main")
  Task.create!(stack: stack_b, ... ) # give stack_b a distinguishing deploy record

  client_a = ApiClient.create!(creator: @user, name: "Client A", stack: stack_a, permissions: %w[read:stack])

  get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }

  # Binding under test: current_api_client.stack_id (== stack_a.id) must equal resolved stack.id
  assert_not_equal client_a.stack_id, stack_b.id, "sanity: tokens are for different stacks"
  assert_response :not_found  # expected secure behavior
  refute_includes response.body, stack_b.to_param  # B's data must never leak
end
```
This demonstrates that, prior to the fix, the request returns `200 OK` with stack B's XML payload despite `client_a.stack_id == stack_a.id`, violating the intended binding.
