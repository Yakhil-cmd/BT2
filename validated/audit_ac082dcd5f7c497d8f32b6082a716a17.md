### Title
Device-flow one-time code printed to terminal without escape-sequence sanitization, unlike other untrusted-content paths - ([File: internal/authflow/flow.go])

### Summary
`AuthFlow`'s `DisplayCode` closure prints the OAuth device-flow `code` value directly with `fmt.Fprintf(w, ..., cs.Bold(code))` (and copies it to the clipboard), with no sanitization, while other parts of this codebase route externally-sourced/untrusted text through `iostreams.Untrusted` or `asciisanitizer` before it reaches a terminal writer. When `--hostname` points at an attacker-controlled/spoofed enterprise host, that host's device-flow response supplies the `code` value that ends up in this unsanitized print path.

### Finding Description
`DisplayCode` is invoked by `oauth.Flow.DetectFlow()` (external `github.com/cli/oauth` dependency, not vendored in this repo) with `code` derived from the device-flow HTTP response `user_code` field returned by the host at `oauthHost`. In `internal/authflow/flow.go`: [1](#0-0) 

the closure writes `code` straight into `fmt.Fprintf` with `%s`/`cs.Bold(code)`, and separately into `clipboard.WriteAll(code)`, with no filtering of control/escape bytes. This is inconsistent with the pattern used elsewhere in the codebase for content that originates outside the CLI: `pkg/iostreams/untrusted.go` defines `Untrusted`, whose `String()` method runs the value through `asciisanitizer.Sanitizer` specifically so that "any fmt print path... renders the content with ANSI escape sequences neutralized" [2](#0-1) , and commands like `gist view` and `pr diff` explicitly wrap remote/API-derived content in `Untrusted` or check `iostreams.ContainsEscapeSequence` before printing [3](#0-2) [4](#0-3) . `flow.go`'s `DisplayCode` does not apply any equivalent sanitization to `code` before writing it to `w` (`IO.ErrOut`).

However, exploitability is limited: the `BrowseURL` closure in the same flow does perform a scheme check (`http`/`https` only) on `authURL` before use [5](#0-4) , but that check does not apply to `code`, which is opaque text with no format validation at all. The actual generation/parsing of the device-flow response (and thus the exact bytes that land in `code`) happens inside the external `github.com/cli/oauth` module, which is not part of this repository, so the precise field-length/charset constraints imposed by that library (if any) could not be verified from this codebase alone.

### Impact Explanation
If a victim runs `gh auth login --hostname <attacker-host>` and that host returns a crafted `user_code` string embedding ANSI/terminal escape sequences (e.g., cursor movement, line-clear, or fake text) instead of a normal short alphanumeric code, the sequence would be written verbatim to `IO.ErrOut`. This falls into the terminal UI/output spoofing impact class: it could visually overwrite or fabricate lines in the CLI's own trusted output (e.g., simulate a `Press Enter` prompt or hide/alter the real verification URL context), potentially misleading the victim about what they are approving. It does not by itself achieve code execution, credential exfiltration, or file write outside the intended path — the impact is scoped to terminal-rendering deception during an already-adversarial `--hostname` scenario.

### Likelihood Explanation
Requires the victim to explicitly point `gh auth login` at an attacker-controlled or spoofed hostname (a precondition acknowledged in the question and consistent with the enterprise device-flow scenario). Given that precondition, forging the response and injecting escape sequences into the `user_code` field is fully within the attacker's control and trivially repeatable — no other victim action is needed beyond initiating login against that host.

### Recommendation
Sanitize `code` the same way other untrusted external content is handled in this codebase: wrap it with `iostreams.NewUntrusted(code)` (or run it through `asciisanitizer.Sanitizer` / `iostreams.ContainsEscapeSequence` and reject/strip) before passing it to `fmt.Fprintf` in the `DisplayCode` closure, and consider validating that the code matches an expected format (e.g., short alphanumeric with dashes) before displaying or copying it to the clipboard.

    cs := ios.ColorScheme()
