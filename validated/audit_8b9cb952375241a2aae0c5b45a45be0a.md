### Title
Cross-repository CI status forgery via unscoped `Commit` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook by looking up the `GithubApp`/`webhook_secret` for the *organization* named in the payload (`repository.owner.login` or `organization.login`) and verifying the HMAC signature against that org's secret. [1](#0-0)  That check only proves the payload was signed by *some* organization onboarded to this Shipit instance — it does not prove the payload's contents are scoped to the repository owned by that organization. `Webhooks::Handlers::StatusHandler#process`, which runs after signature verification, ignores the payload's `repository` field entirely and instead updates **any** commit in the database whose `sha` matches the payload, across all stacks/repositories:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

Contrast this with the base `Handler` class, which does define a `repository_name`/`stacks` helper scoped to `payload.dig('repository', 'full_name')` [3](#0-2)  — a helper `StatusHandler` deliberately does not use, unlike `PushHandler` which correctly scopes to `stacks` derived from the payload's repository. [4](#0-3) 

### Finding Description
The binding that should hold is: **organization that authenticated the webhook == repository whose commits are written by the handler**. `verify_signature` establishes trust only for the org named in the payload's `repository.owner.login`, [5](#0-4)  but `StatusHandler` never re-checks that the `sha` being updated actually belongs to a commit within *that* repository. It performs a global `Commit.where(sha: ...)` across the whole Shipit installation. [2](#0-1) 

Git commit SHAs are content-addressed and are frequently shared across repositories — most commonly between a repository and any of its forks (all commits up to the fork point have identical SHAs), or between repositories that share history via merges/cherry-picks with identical trees/parents/messages. An attacker who controls (or has push access to) any GitHub organization/repository onboarded to the same multi-tenant Shipit instance (a legitimate, documented deployment mode — see the "multiple Github applications for different Github organizations" config in `config/secrets.development.example.yml`) [6](#0-5)  can send a `status` webhook that is correctly signed with *their own* org's `webhook_secret` (satisfying `verify_signature`), while naming a `sha` that also exists as a tracked commit in a victim stack belonging to a different organization/repository they do not control. Because `StatusHandler` never filters by repository, the forged status (`state`, `description`, `target_url`, `context`) is written onto the victim's commit via `commit.create_status_from_github!(params)`.

### Impact Explanation
Commit statuses drive Shipit's `StatusChecker`, which governs whether CI/required checks pass for both deploys and the merge queue (`Stack#required_statuses`, `MergeRequest#reject_unless_mergeable!`, `all_status_checks_passed?`). [7](#0-6)  An attacker who forges a `success` status for a required context (e.g., `ci/circleci`) on a victim commit can satisfy `required_statuses`/`blocking_statuses` checks it does not actually meet, potentially triggering an unauthorized deploy or an automatic merge via the merge queue for a repository the attacker has no legitimate write access to — a cross-repository, unauthorized-ship condition.

### Likelihood Explanation
Requires the attacker to control an org/repo already onboarded to the same Shipit instance (no Shipit session, API token, or org secret for the *victim* org is needed — only their own org's `webhook_secret`, which they legitimately possess as the owner of their own GitHub App installation). They further need a `sha` collision with a commit tracked by the victim stack, which is trivially achievable by forking the victim's public repository (shared history == identical SHAs for all pre-fork commits) or by replaying a previously observed `sha`/status pair. This is a realistic, low-effort path in any Shipit deployment serving multiple organizations or forks of the same codebase.

### Recommendation
Scope `StatusHandler#process` (and any other handler that looks up records purely by content hash) to the repository named in the payload, mirroring the pattern already used in `Handler#stacks`/`PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This re-establishes the binding between the org that signed the payload and the repository whose commit is mutated.

### Proof of Concept
1. Attacker owns `attacker-org/victim-repo-fork`, a public fork of `victim-org/victim-repo`, and has configured their own GitHub App/webhook integration pointed at the shared Shipit instance (a supported multi-org configuration). [6](#0-5) 
2. Attacker identifies a commit `sha` that is shared between the fork and `victim-org/victim-repo` (any pre-fork commit), which Shipit already tracks as part of a victim `Stack`.
3. Attacker sends a `status` event to `POST /webhooks` with `repository.owner.login = "attacker-org"`, `sha = <shared sha>`, `state = "success"`, `context = "<victim's required CI context>"`, signed with `attacker-org`'s own `webhook_secret` using `X-Hub-Signature`.
4. `verify_signature` looks up `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against the attacker's own secret. [5](#0-4) 
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` with no repository filter, finds the victim's commit record, and calls `create_status_from_github!`, writing a forged "success" status onto it. [2](#0-1) 
6. The forged status can satisfy `Stack#required_statuses`/merge-queue checks for the victim stack, enabling an unauthorized deploy or merge.

    def reject_unless_mergeable!
      return reject!('merge_conflict') if merge_conflict?
      return reject!('ci_missing') if any_status_checks_missing?
      return reject!('ci_failing') if any_status_checks_failed?
      return reject!('requires_rebase') if stale?

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end

    def all_status_checks_passed?
      return false unless head

      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).success?
    end

    def any_status_checks_failed?
      status = StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec)
      status.failure? || status.error?
    end

    def any_status_checks_missing?
      StatusChecker.new(head, head.statuses_and_check_runs, stack.cached_deploy_spec).missing?
    end
