### Title
`ERC20Transactor::withdraw_asset_with_surplus` credits XCM holding with the requested amount instead of the amount actually received by the checking account - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
The `ERC20Transactor` used to bridge/transact ERC-20 tokens deployed on `pallet-revive` via XCM credits the XCM holding register with the *nominal* `amount` requested in a `WithdrawAsset`/`TransferAsset` instruction, without verifying that the `TransfersCheckingAccount` actually received that exact amount from the `IERC20::transfer` call. This is the same root-cause pattern as the Sherlock finding: trusting the transfer-call input parameter as ground truth for accounting instead of measuring the actual balance delta of the receiving account.

### Finding Description
`withdraw_asset_with_surplus` moves ERC-20 tokens from a user to a shared `TransfersCheckingAccount` by invoking the contract's `transfer(to, value)` function via `pallet_revive::Pallet::<T>::bare_call`: [1](#0-0) 

After the call, the code only checks whether the contract call reverted and whether the ABI-decoded boolean return value is `true`. It does not compare the checking account's ERC-20 balance before and after the call: [2](#0-1) 

If the return value is `true`, the function unconditionally credits the XCM holding register with `Erc20Credit(amount)` — the *requested* amount, not the amount that actually landed in `TransfersCheckingAccount`: [3](#0-2) 

The symmetric `deposit_asset_with_surplus` function has the identical pattern: it calls `transfer(beneficiary, amount)` from the checking account and, on success, simply drops the `amount` from holding without verifying the beneficiary actually received `amount`: [4](#0-3) 

Because `Matcher: MatchesFungibles<H160, u128>` allows any deployed contract address to be treated as a fungible XCM asset (matched generically by `assets_common::ERC20Matcher`, not gated by a privileged registry entry in this transactor), an unprivileged, signed user can deploy an arbitrary `pallet-revive` contract implementing the standard `IERC20` interface with a `transfer` function whose actual balance effects diverge from the `value` parameter (e.g. a fee-on-transfer, deflationary, or otherwise non-standard token), analogous to a fee-on-transfer USDC. They can then invoke `pallet_xcm::execute` (available to any signed origin, gated only by `XcmExecuteFilter`, which permits program execution of ordinary `WithdrawAsset`/`DepositAsset` instructions) to run a local XCM program that withdraws that asset. The XCM executor's holding register will contain the full nominal `amount` even though `TransfersCheckingAccount`'s real on-chain balance in that ERC-20 contract increased by less (or a different amount) than `amount`.

This exactly mirrors the CrabNetting bug: the contract call's declared "amount" parameter is used as the source of truth for crediting an internal ledger (here, the XCM `AssetsInHolding` register) instead of measuring the actual balance delta caused by the token transfer.

### Impact Explanation
Once the XCM holding register believes it holds more (or a different amount of) the ERC-20 asset than the checking account actually possesses, any subsequent instruction in the same or a later XCM program that tries to deposit/forward that "phantom" balance (e.g. `DepositAsset` to a beneficiary, or forwarding the asset cross-chain through a reserve/teleport) will attempt a `transfer` call for the full credited `amount` from an account that does not actually hold that much of the underlying ERC-20 token. This produces either:
- Deterministic failure of subsequent, unrelated ERC-20-based XCM operations that rely on the same `TransfersCheckingAccount` (denial-of-service-like state divergence between the runtime's XCM accounting and the ERC-20 contract's real state), directly analogous to the report's stated impact ("outgoing transfers will potentially revert due to insufficient balance"); or
- Under other constructions of the malicious ERC-20 (e.g. one that debits its own accounting less than declared but returns `true`), inflated/duplicated holding credits that could be used to attempt withdrawing more value than was actually escrowed in `TransfersCheckingAccount` for that asset, though real economic damage is limited to whatever value is deposited/associated with the attacker's own contract-controlled token (the ERC-20 contract logic itself is attacker-controlled, so the "asset" has no independent backing unless it is later treated as fungible with an external reserve, e.g. through registration/liquidity elsewhere).

Given the loss is confined to accounting-state divergence on a mechanism whose "asset" identity is entirely attacker-controlled (a self-deployed contract), and does not, by itself, let an attacker drain funds belonging to other users or a chain-backed reserve, this is a Medium-severity accounting-invariant violation rather than a direct theft-of-funds Critical/High.

### Likelihood Explanation
The path is reachable by any signed, unprivileged account: deploying a `pallet-revive` contract is a normal permitted action, and invoking `pallet_xcm::execute` with a locally-executed `WithdrawAsset`/`DepositAsset` program referencing that contract as an `AccountKey20` asset is also a standard, unprivileged capability (subject only to the generic `SafeCallFilter`/`XcmExecuteFilter`, which does not vet ERC-20 semantics). No governance, validator, or relayer collusion is required — the attacker only needs to author a non-conforming ERC-20 contract, which is fully within their control.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of the receiving account (`TransfersCheckingAccount` on withdraw, the beneficiary on deposit) before and after the `bare_call`, and credit/debit the XCM holding register with that measured delta instead of trusting the `amount`/`value` parameter and the boolean return value alone.

### Proof of Concept
I was not able to complete a full, executed local Rust/FRAME integration reproduction within this session (no code-execution/terminal access is available in this ask-only investigation, and the guidance forbids claiming a test ran without results). The finding is derived from static analysis of the exact control flow in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, showing the only guard against a non-conforming `transfer` implementation is the ABI-decoded boolean success flag — there is no balance-delta check — which structurally reproduces the CrabNetting root cause (trusting the transfer's declared amount instead of verifying actually-received funds) in a place reachable by any signed user via `pallet_xcm::execute` combined with a self-deployed `pallet-revive` ERC-20 contract. A concrete PoC would deploy a minimal `pallet-revive`/`resolc`-compiled ERC-20 contract whose `transfer` function moves less than `value` to the recipient while still returning `true`, then execute an XCM `WithdrawAsset` for that token via `pallet_xcm::execute` and assert `AssetsInHolding` reports the full requested `amount` while `IERC20::balanceOf(TransfersCheckingAccount)` increased by a smaller amount — this was not executed in this session and should be validated in a live Devin session with test-harness access (e.g. building on the existing `withdraw_and_deposit_erc20s` test in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs`).
