## Title
Cross-organization webhook authentication bypass via `repository.owner.login` / `repository.full_name` divergence - (File: app/controllers/shipit/webhooks_controller.rb)

## Summary
`WebhooksController#verify_signature` selects the `GitHubApp` used for HMAC verification strictly from `repository.owner.login` (or `organization.login`) in the *unsigned* JSON body, while every handler (`CheckSuiteHandler`, `StatusHandler`, and `Handler#stacks`) resolves the target `Repository`/`Stack`/`Commit` strictly from `repository.full_name`. Nothing in the request enforces that these two fields refer to the same organization, so an attacker can pick an org with no `webhook_secret` configured for the signature check while pointing `full_name` at a different, secret-protected org's repository, causing signature verification to be skipped entirely while the payload still mutates records belonging to the secret-protected org.

## Finding Description
Broken binding: `organization_used_for_hmac_check := params.dig('repository','owner','login')` MUST equal `organization_that_actually_owns_the_mutated_stack := Repository.from_github_repo_name(params.dig('repository','full_name')).owner`. These are read from two independent, attacker-controlled JSON fields in an unauthenticated POST, and no code enforces their equality.

Path:
1. `verify_signature` computes `github_app = Shipit.github(organization: repository_owner)` where `repository_owner` comes from `params.dig('repository','owner','login')` [1](#0-0)  and `repository_owner` is defined solely from the unsigned body [2](#0-1) .
2. `GitHubApp#verify_webhook_signature` has `return true unless webhook_secret` before ever inspecting the header or the algorithm [3](#0-2) . If the org resolved in step 1 has no `webhook_secret` configured in `secrets.github`, verification is unconditionally `true`, regardless of a missing `X-Hub-Signature` header.
3. `Handler#stacks` / `Handler#repository_name` resolve the target `Repository` using `payload.dig('repository', 'full_name')`, completely independent of `repository.owner.login` [4](#0-3) . `CheckSuiteHandler#process` and `StatusHandler#process` then mutate `Commit`/`Stack` records found via that lookup [5](#0-4) [6](#0-5) .

Attacker request: POST `/webhooks` with header `X-Github-Event: check_suite` (or `status`), no `X-Hub-Signature` header, and a JSON body such as:
```json
{"repository": {"owner": {"login": "org-without-secret"}, "full_name": "org-with-secret/protected-repo"}, "check_suite": {"head_sha": "...", "head_branch": "..."}}
```
This requires a multi-org `secrets.github` configuration where at least one configured org key has no `webhook_secret` set (this is the "org with existence known but no secret" precondition from the question) and at least one other configured org has a real repository/stack in the system with a `webhook_secret`.

`drop_unhandled_event`, `check_if_ping`, and `ExplicitParameters` schemas do not check this binding — they only gate on event type and payload shape, not on owner/full_name consistency. `require_permission!`, `force_github_authentication`, and `User#authorized?` are irrelevant here since this is an unauthenticated webhook endpoint by design (GitHub webhooks are meant to be verified by HMAC, not session auth).

## Impact Explanation
An attacker who can identify (not compromise) any org configured in `secrets.github` without a `webhook_secret` can forge unsigned webhooks that are accepted (`head(422)` never rendered) and then mutate `Commit` (`create_status_from_github!`) or trigger `schedule_refresh_check_runs!` on `Stack`/`Commit` records that belong to an entirely different, secret-protected org, purely by setting `full_name` to point at that org's repo. This is a cross-tenant authentication bypass: the secret protecting org B is bypassed by authenticating as org A. This matches the Critical category "a payload for one repository mutating another's stack/commit" and "authentication bypass (forged webhook accepted)". It is repeatable per request and scoped to any repository whose owning org key lacks `webhook_secret` in the deployment's Shipit configuration.

## Likelihood Explanation
This requires a specific server-side configuration: the multi-org github secrets schema (`secrets.github` keyed by organization) with at least one org entry missing `webhook_secret`. If Shipit uses the single-app/legacy config (`github_default_organization` nil, one global `secrets.github`), the bypass reduces to the classic "no secret configured means all webhooks unsigned" case rather than a cross-org bypass, and there is no secret-protected org to attack. Given the stated attacker capability (arbitrary unauthenticated POST to `/webhooks`) and no rate limiting relevant here, cost is a single crafted HTTP request; the only real precondition is the operator-side misconfiguration (an org without a secret) coexisting with a protected org, which is plausible in setups onboarding new organizations incrementally.

## Recommendation
In `WebhooksController#verify_signature`, derive the organization used for signature verification the same way handlers derive the target repository — from `repository.full_name`'s owner segment — and reject the request outright (do not fall back to "verified" when `webhook_secret` is blank on a per-org basis unless the org is explicitly configured as intentionally unsigned). Additionally, `GitHubApp#verify_webhook_signature`'s `return true unless webhook_secret` should not implicitly authorize processing when other orgs in the same deployment do have secrets configured; consider requiring every configured org to have a `webhook_secret` or explicitly refusing to process any repository whose owning org has no secret when any org in `secrets.github` does.

## Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (existing test infra using `test/dummy/config/secrets_double_github_app.yml`, which configures multiple orgs, one of which should be adjusted to omit `webhook_secret`):

```ruby
test "a check_suite webhook with owner=unsecured-org and full_name=secured-org/repo bypasses signature check and mutates the secured org's commit" do
  secured_stack = shipit_stacks(:shipit) # owned by an org with webhook_secret configured
  commit = secured_stack.commits.create!(sha: "a" * 40, branch: secured_stack.branch)

  post :create,
    body: {
      repository: {
        owner: { login: "unsecured-org" }, # org with NO webhook_secret configured
        full_name: secured_stack.repository.full_name # points at the secured org's real repo
      },
      check_suite: { head_sha: commit.sha, head_branch: secured_stack.branch }
    }.to_json,
    params: {},
    headers: { "X-Github-Event" => "check_suite" } # deliberately omit X-Hub-Signature

  assert_response :ok
  refute_equal 422, response.status
  # assert that commit.schedule_refresh_check_runs! was actually invoked / enqueued
  # for a commit belonging to the *secured* org's stack despite an unsigned request
end
```

The assertion set validates both sides of the equality: `repository_owner` used for `Shipit.github(organization:)` (`"unsecured-org"`) differs from the actual owner of the mutated `Stack`/`Commit` (the secured org derived from `full_name`), and the response is not `422` despite no `X-Hub-Signature` header — demonstrating the two organizations diverge and the guard is bypassed.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
