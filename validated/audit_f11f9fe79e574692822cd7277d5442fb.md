### Title
Webhook signature verification selects its GitHub App/secret using an unauthenticated payload field, letting one onboarded organization forge events for another organization's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App (and therefore which HMAC webhook secret) to verify the request against by reading `repository.owner.login` (or `organization.login`) straight out of the untrusted, unauthenticated JSON body, before any signature has been checked. Every other part of the pipeline (event routing, `Repository.from_github_repo_name`, stack lookup) keys off a different field, `repository.full_name`. Because the field used to select the verification secret is not the field that ends up being acted upon, and neither is bound to the actual `X-Hub-Signature` cryptographic proof, the two can be made to disagree.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

`repository_owner` is derived purely from the request body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` resolves to a per-organization `GitHubApp` instance (`lib/shipit/github_app.rb`), each with its own independently configured `webhook_secret`: [3](#0-2) [4](#0-3) 

The verification is: `HMAC-SHA1(webhook_secret_for(payload["repository"]["owner"]["login"]), raw_body) == X-Hub-Signature`.

Once verification succeeds, the actual event handlers resolve the target repository/stack from a *different* field in the same body, `repository.full_name`: [5](#0-4) 
and, e.g., in the pull-request handlers: [6](#0-5) 

This breaks the intended binding: `organization authenticated by X-Hub-Signature == organization owning the repository the handler writes to`. An attacker who legitimately controls an organization/GitHub App entry that Shipit already trusts (i.e., knows that org's own configured `webhook_secret`, which is a normal, low-privilege capability for any org admin who is allowed to configure their own GitHub App integration in Shipit, not the victim org's secret) can:
1. Compute a valid `X-Hub-Signature` over an arbitrary raw body using their own org's `webhook_secret`.
2. Set `repository.owner.login` (or `organization.login`) in that body to their own org name, so `verify_signature` selects their own `GitHubApp` and the signature checks out.
3. Set `repository.full_name` in the same body to `victim-org/victim-repo`, which is what the handlers (`PushHandler`, `StatusHandler`, `PullRequest::*Handler`, `MembershipHandler`, `CheckSuiteHandler`) actually use to look up `Repository`/`Stack` and mutate state (create commits, change PR/merge state, add/remove `Membership`s and `Team`s, post commit statuses that gate CI-based merges/deploys).

Because the two "owner" fields are never cross-checked against each other, and the field driving the write is not the field bound to the signature, an attacker never needs the victim organization's own webhook secret to forge webhook traffic for that organization's repositories in Shipit.

### Impact Explanation
This allows cross-repository/cross-organization writes: forged `push` events can trigger `GithubSyncJob` against a victim stack, forged `status`/`check_suite` events can fabricate green CI status used to gate merges and continuous deployment, forged `pull_request` events can archive or manipulate review stacks, and forged `membership` events can create/delete `Team`/`Membership` records tied to `Shipit.github_teams` authorization. Depending on which handler is targeted, this can escalate into unauthorized deploys/merges (rated Critical per the impact criteria) or unauthenticated manipulation of team/stack authorization state (High).

### Likelihood Explanation
The precondition is only that the attacker be able to onboard (or already control) at least one organization/GitHub App entry known to `Shipit.github`, i.e., knowledge of *some* legitimate `webhook_secret` configured in the Shipit instance - not the victim's. In any Shipit deployment supporting multiple organizations (the multi-app `Shipit.github(organization:)` lookup exists specifically to support this), this is a realistic, unprivileged-relative-to-the-victim attack path requiring only a normal webhook POST to the public `webhooks` endpoint.

### Recommendation
Verify the webhook signature using the `webhook_secret` associated with the organization actually referenced by `repository.full_name` (the field the handlers use), not a separately-read `repository.owner.login`/`organization.login` field. Alternatively, after selecting the app used for verification, assert that `repository.owner.login` (or `organization.login`) equals the owner segment of `repository.full_name` before dispatching to any handler, and reject the request otherwise.

### Proof of Concept
1. Attacker registers/administers an org `attacker-org` that has a legitimate GitHub App entry in Shipit with webhook secret `S`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(S, raw_body)>` and sets `X-Github-Event: push`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is `S`; the HMAC checks out and the request is accepted.
5. `Webhooks::Handlers::PushHandler#process` (via `Handler#repository_name` → `payload.dig('repository','full_name')`) resolves `victim-org/victim-repo` and enqueues `GithubSyncJob` for that stack - despite the request never having been signed with `victim-org`'s webhook secret.       github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
