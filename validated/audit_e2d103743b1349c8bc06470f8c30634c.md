## Title
CCMenu API scoped tokens authorize any stack, not just the stack they were issued for - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` implements stack scoping for API clients so that a token created for one stack cannot be used against another: `stacks` returns `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` has a `stack_id`, and the shared `stack` helper resolves through that scoped relation. [1](#0-0) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to resolve directly against the global `Stack` collection, bypassing the scoping entirely: [2](#0-1) 

### Finding Description
The intended binding is: `ApiClient#stack_id` (the stack a token authorizes) == the stack whose data is returned by the request. This binding is enforced in `BaseController#stacks`/`#stack` for every other API endpoint (stacks, tasks, deploys, hooks, merge_requests, lock, etc.), all of which inherit `stack` from `BaseController`. [1](#0-0) 

`CCMenuController` defines its own `stack` method that ignores `current_api_client.stack_id` and simply loads `Stack.from_param!(params[:stack_id])` — i.e. whatever stack the caller names in the URL: [3](#0-2) 

`CCMenuController` only checks the generic `read:stack` permission via `require_permission :read, :stack`, which validates the permission list on the `ApiClient` record but never compares `stack_id` to the requested stack: [4](#0-3) [5](#0-4) 

The tokens that reach this controller are specifically stack-scoped by design. `CCMenuUrlController#client` creates (or reuses) an `ApiClient` with `permissions: %w[read:stack]` tied to the requesting user, and the generated CCMenu URL embeds that token together with a specific `stack_id`: [6](#0-5) 

Because the `ApiClient` created here has no explicit `stack:` association set at creation in this flow, and more importantly because `CCMenuController#stack` never consults `current_api_client.stack_id` at all, any valid `read:stack`-permissioned token (scoped or not) can be replayed against `/api/stacks/:stack_id/ccmenu` for an arbitrary `stack_id`, including stacks the token's creator has no relationship to. The token, once obtained (e.g. shared in a CI badge URL, leaked in logs, or an already-revoked/narrow-purpose CCMenu token issued for stack A by its author), lets the holder read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock status) for stack B by simply changing the URL's stack_id — a cross-stack authorization boundary that every other API endpoint enforces correctly.

### Impact Explanation
This is an authorization escalation: a token whose intended scope was "read the CI status of stack A" can be used to read the CI/deploy status of any other stack in the Shipit instance (`Stack.from_param!` has no client-based `where` filter). This matches the "High" bucket criterion of "unauthenticated/unauthorized read of stack state" via a token confusion — the equality broken is `ApiClient#stack_id` (the stack a token authorizes) != stack actually touched (`params[:stack_id]`).

### Likelihood Explanation
Exploitation requires only possession of any `read:stack`-permissioned CCMenu-style token (which are trivially created by any authenticated user via `CCMenuUrlController#fetch`, and are designed to be embedded in third-party CI-status tools/URLs that are often not treated as highly secret). No repository write access, GitHub credentials, or admin privileges are needed — only a valid token and knowledge of a target `stack_id` (stack identifiers are `owner/name/environment` strings, often discoverable/public). This makes likelihood high relative to the required "no privileged account" bar.

### Recommendation
Have `Shipit::Api::CCMenuController#stack` resolve through the same client-scoped `stacks` relation as `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so `current_api_client.stack_id` is enforced consistently for the CCMenu endpoint as it is for every other API resource.

### Proof of Concept
1. As User X, visit `/ccmenu/OwnerA/repoA/production` to obtain a CCMenu URL/token via `CCMenuUrlController#fetch` (only `read:stack` permission is granted). [6](#0-5) 
2. Take the returned `token` query parameter.
3. Request `GET /api/stacks/OwnerB/repoB/production/ccmenu?token=<token>` for an unrelated stack B that User X has no access to.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` without filtering by `current_api_client.stack_id`, and `require_permission :read, :stack` only checks that the `read:stack` permission string is present on the token, the request succeeds and returns stack B's build status/lock state. [7](#0-6)
