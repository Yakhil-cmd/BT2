### Title
SSRF via attacker-controlled `device_hub` in pairing messages enables outbound connections to arbitrary hosts - (File: device.js)

### Summary
An unpaired, unauthenticated remote device can send a `pairing` message through a hub and force the receiving node/wallet to open an outbound WebSocket connection to a host of the attacker's choosing, via the `json.device_hub` field and the reverse-pairing flow in `handlePairingMessage`. This mirrors the Nexus SSRF bug class (CVE-2021-43293): a low-privilege caller supplies a server-side target and the node performs outbound network requests to it, allowing network/host enumeration of the victim node's internal network.

### Finding Description
`handlePairingMessage` is reachable from any device, even ones that have never paired with the recipient, because `pairing` is in `arrSubjectsAllowedFromNoncorrespondents` in `device.js` (`handleJustsaying`'s hub/message handling checks correspondent, and falls back to allow "pairing", "my_xpubkey", "wallet_fully_approved" from unknown senders). [1](#0-0) 

The pairing message body carries `device_hub`, the sender's claimed "home hub" host name, which is only checked for being a non-empty string, under 200 chars, and passing `network.isValidWsUrl(conf.WS_PROTOCOL + json.device_hub)` — a syntactic/protocol check, not an SSRF-relevant allow-list (no restriction against internal/private IP ranges, localhost, link-local addresses, cloud metadata endpoints, etc.): [2](#0-1) 

If the incoming pairing body includes a `reverse_pairing_secret`, the code calls `sendPairingMessage(json.device_hub, device_pubkey, body.reverse_pairing_secret, null)`, which in turn calls `sendMessageToHub(hub_host, ...)`: [3](#0-2) [4](#0-3) 

`sendMessageToHub`, when given a hostname string (as here) rather than a websocket, calls `reliablySendPreparedMessageToHub(hub_host, ...)` → `sendPreparedMessageToHub`, which treats the string as a hub host and opens an outbound connection with `network.findOutboundPeerOrConnect(conf.WS_PROTOCOL+hub_host, ...)`: [5](#0-4) 

This causes the victim's node process to initiate an outbound WebSocket/TCP handshake to any host string the attacker supplies (subject only to the loose `isValidWsUrl` format check), including hosts on internal/private networks that are otherwise unreachable from the public internet. The pairing flow, additionally, also stores this attacker-supplied hub value into `correspondent_devices.hub` for confirmed correspondents (see `handlePairingMessage`'s INSERT), meaning the SSRF target also persists and can be triggered repeatedly on later message deliveries (`sendMessageToDevice` → `sendMessageToHub(rows[0].hub, ...)`). [6](#0-5) 

This is the same bug class as CVE-2021-43293: a party with minimal privilege (here, anyone who can send a device pairing message through a shared hub — no wallet funds, no prior trust relationship needed) supplies a URL/host that is fetched/connected-to server-side, enabling network enumeration of hosts/ports reachable from the victim node (SSRF).

### Impact Explanation
An attacker can use the victim wallet/node as a network scanning proxy: by sending crafted pairing offers with `device_hub` set to internal IPs/ports (e.g., `127.0.0.1:6379`, `10.0.0.5:22`, internal admin panels, cloud metadata services), and observing side channels (timing, error messages, retry/backoff behavior, or subsequent recognizable behavior), the attacker can infer open ports and reachable internal hosts from the victim's network position. Because the value is also persisted into `correspondent_devices`, later `sendMessageToDevice` calls repeat the outbound connection attempt automatically, giving the attacker a repeatable "probe" primitive. This is a within-scope wallet/contract message handling issue since it is reachable purely by a paired device/pairing-message sender interacting with the target's device/hub messaging layer — no p2p/catchup/sync path, no hub-operator privilege and no malicious-node assumption is required.

### Likelihood Explanation
Likelihood is real but bounded: exploitation requires the attacker to be able to route a `pairing` justsaying/hub message to the target (via a shared hub, which is a normal, low-barrier interaction — pairing QR codes/links are routinely exchanged), and it only yields information through side channels (SSRF here does not return response bodies to the attacker directly, unlike the Nexus SSRF which could return proxied HTTP responses). The attacker does not directly receive the connection result, limiting the enumeration to timing/behavioral inference rather than full response disclosure.

### Recommendation
- Apply strict SSRF hardening to `device_hub`/hub host values accepted from remote parties (pairing messages and `my_url`/`hub/message` device_hub updates): reject private/loopback/link-local/multicast IP ranges and non-standard ports unless explicitly configured for testing, and require the resolved DNS target to also not fall into private ranges (to prevent DNS-rebinding bypass).
- Do not automatically dial `device_hub` values supplied in unauthenticated/`pairing`-flow reverse-pairing sends before the human user approves the correspondent; defer the reverse-pairing hub connection until after explicit user confirmation of the new correspondent.
- Consider rate-limiting/backing off outbound connection attempts triggered by remote-supplied hub hosts to reduce the enumeration signal available via timing side channels.

### Proof of Concept
1. Attacker device (unpaired, unknown to victim) sends, via a shared hub, a `hub/message` justsaying whose decrypted `json` is `{ from: attacker_addr, device_hub: attacker_hub, subject: "pairing", body: { pairing_secret: "<valid or wildcard *>", device_name: "x", reverse_pairing_secret: "probe-secret" } }`, where `device_hub` is set to an internal target such as `"127.0.0.1:6379"` or `"169.254.169.254:80"` (any string that passes `isValidWsUrl`'s format check).
2. `handlePairingMessage` in `device.js` validates the pairing secret against the target's `pairing_secrets` table (a wildcard `'*'` permanent secret is a common configuration for hubs / auto-pairing bots) and, on match, calls `sendPairingMessage(json.device_hub, device_pubkey, "probe-secret", null)`.
3. This triggers `sendMessageToHub` → `findOutboundPeerOrConnect(conf.WS_PROTOCOL + "127.0.0.1:6379", ...)`, causing the victim node to open a TCP/WS connection attempt to the internal host/port chosen by the attacker.
4. Repeating this with different internal hosts/ports and observing differences in error timing/behavior (immediate refusal vs. connection timeout vs. protocol-level WS handshake failure) allows the attacker to fingerprint which internal hosts/ports are reachable from the victim node — i.e., SSRF-based network enumeration, analogous to CVE-2021-43293.
