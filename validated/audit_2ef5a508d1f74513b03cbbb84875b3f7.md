### Title
Signature verification keyed on `repository.owner.login` while stack resolution is keyed on `repository.full_name` allows cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/secret to validate an inbound webhook against using `repository_owner`, computed as `params.dig('repository', 'owner', 'login')`. Every event handler, however, resolves the target `Stack`/`Repository` to act on using a *different* field of the same payload: `repository.full_name`, via `Handlers::Handler#repository_name`/`#stacks`. Nothing enforces that these two fields agree, so an attacker who legitimately controls (or has a valid, unauthenticated path to) one organization's webhook endpoint can forge a payload whose `repository.owner.login` matches an org that authenticates cleanly (or has no secret configured), while `repository.full_name` points at a completely different, victim-owned repository/stack.

### Finding Description
`verify_signature` picks the GitHub App config with `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly no-ops when the resolved organization has no `webhook_secret` configured, which the setup docs describe as *optional*: [3](#0-2) [4](#0-3) 

Once past `verify_signature`, the raw JSON `params` are dispatched unchanged to the registered handler for the event: [5](#0-4) 

Every handler resolves the affected repository/stack from `repository.full_name` in that same payload, completely independent of `repository.owner.login`: [6](#0-5) 

`PushHandler`, for example, then triggers `sync_github` on every matching, non-archived stack for that repository/branch: [7](#0-6) 

The equality the system is supposed to preserve is:
`organization authenticated by verify_signature (repository.owner.login)` == `organization/repository actually acted upon (repository.full_name)`.

Before the attack, in a legitimate webhook, GitHub itself constructs the payload so `repository.owner.login` and the owner segment of `repository.full_name` always agree, and the signature covers the whole payload, so nothing can be tampered with in transit. But the `/webhooks` endpoint is a plain HTTP endpoint reachable by anyone who can build a POST request - it does not require it to actually originate from GitHub. If Shipit is configured for multiple organizations (as documented in `docs/setup.md`) and any one of them omits `webhook_secret` (allowed, "optional"), then for that org name, `verify_webhook_signature` always returns `true` regardless of body or signature header. An attacker (no credentials required) can then submit a crafted JSON body where:
- `repository.owner.login` = the org name that has no configured secret (so `verify_signature` passes unconditionally), and
- `repository.full_name` = `"victim-org/victim-repo"` (any org/repo actually registered as a Shipit `Stack`).

`repository_owner` resolves to the no-secret org, verification is skipped, and the handler still processes the payload against the victim repository's stack because `stacks` is keyed only on `full_name`. This breaks the intended binding between "the organization that authenticated the request" and "the repository that is written to."

### Impact Explanation
This allows an unauthenticated party to trigger stateful side effects against any repository/stack registered in the target Shipit instance without ever authenticating against that repository's own organization credentials. Depending on which event/handler is exercised, this can force `Stack#sync_github` (unwanted resync/state churn), or drive `pull_request` handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) which mutate `PullRequest`/`MergeRequest` state used by the merge queue, or the `membership` handler which creates/deletes `Team`/`Membership` records for an arbitrary organization login supplied in the payload. This is effectively an authentication-boundary break for a webhook consumer: cross-organization interference with another team's stack state and merge-queue bookkeeping, which the Rules classify as within the High/Critical impact bucket (cross-repository writes / authorization bypass in the trust boundary between "authenticated org" and "acted-upon repository").

### Likelihood Explanation
Exploitability is conditional on the deployment's multi-organization GitHub config having at least one organization entry without a configured `webhook_secret` — explicitly documented as an optional field, so this is a realistic, supported configuration rather than a misconfiguration outside the documented setup. Given that condition, exploitation requires no credentials, no repository access, and no GitHub App private key — only knowledge of the no-secret org's name and any target repository's `full_name` that is registered as a Shipit `Repository`/`Stack`, both of which are non-secret, discoverable values. The single-organization deployment case (only one `github:` key, no per-org secrets) is not exploitable this way since there's only one org to authenticate against and it would need to also lack a secret, in which case *any* payload would already be fully trusted regardless of this specific owner/full_name mismatch — the multi-org case is the one that introduces the actual cross-organization binding break.

### Recommendation
After signature verification, re-derive and enforce that `repository.full_name`'s owner segment matches the authenticated `repository_owner`/organization before dispatching to handlers, or better, resolve the target `Repository`/`Stack` using the same authenticated organization context rather than trusting `full_name` alone in `Handlers::Handler#repository_name`. Additionally, consider requiring `webhook_secret` to be mandatory for all configured organizations (removing the "optional" no-secret bypass in `GitHubApp#verify_webhook_signature`), since any org without a secret currently accepts arbitrary, unauthenticated payloads.

### Proof of Concept
Given a `config/secrets.yml` configured for two organizations as documented in `docs/setup.md` (multi-org format), where `org-no-secret` has no `webhook_secret` set and `victim-org` owns a real Shipit stack for `victim-org/victim-repo`:

1. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=deadbeef   (arbitrary/invalid)

{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "org-no-secret" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. `WebhooksController#verify_signature` computes `repository_owner = "org-no-secret"`, loads that org's `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank for `org-no-secret` (`lib/shipit/github_app.rb:76-77`).
3. `Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves `stacks` via `repository.full_name = "victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and calls `sync_github(expected_head_sha: ...)` on every matching stack — fully bypassing any credential belonging to `victim-org`.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
