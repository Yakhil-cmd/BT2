## Title
Webhook signature is verified against the wrong GitHub organization's secret, decoupling authentication from the repository actually acted upon - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In multi-organization deployments, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC signature against using `repository_owner`, a value read from the *unverified* JSON body (`repository.owner.login` / `organization.login`). The value that downstream handlers actually act on — `repository.full_name`, used everywhere via `Repository.from_github_repo_name` — is an independent field in the same unverified body and is never forced to be consistent with `repository_owner`. This is the same class of bug as the reported CDP issue: the code authenticates against one entity (the organization implied by `repository.owner.login`) while acting on a different entity (the repository named in `repository.full_name`), breaking the equality `organization authenticated == repository written`.

### Finding Description
`verify_signature` picks the `GitHubApp` (and thus the HMAC secret) using a value taken from the raw, not-yet-verified request body: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github` resolves the per-organization config in the multi-org secrets schema: [3](#0-2) 

And `verify_webhook_signature` unconditionally passes when the resolved organization has no `webhook_secret` configured — which is an explicitly supported/documented configuration (`webhook_secret: # nil`): [4](#0-3) [5](#0-4) 

Once `verify_signature` passes, every handler dispatches purely on `repository.full_name` from the same JSON body, not on `repository_owner`: [6](#0-5) 

There is no code path that checks `repository.full_name`'s owner segment matches the `repository_owner`/organization whose secret validated the signature. Consequently, an attacker who controls (or who exploits the absence of) a webhook secret for *any one* configured organization in a multi-org Shipit instance can craft a payload where:
- `repository.owner.login` = the organization with a weak/absent secret (used only to select the verification key),
- `repository.full_name` = `"victim-org/target-repo"` (used by every handler to locate the real `Stack`/`Repository`).

The signature check succeeds (trivially, if `webhook_secret` is nil for that org, or with a known/leaked secret for that org), while the actual mutation targets a repository belonging to a completely different, unrelated organization whose secret was never checked.

### Impact Explanation
This is a cross-repository write: with a forged `push` event, the attacker can force `PushHandler#process` to invoke `stack.sync_github(expected_head_sha: ...)` on any `not_archived` stack matching the branch of the victim's `full_name`: [7](#0-6) 

With a forged `status` event, the attacker can inject/forge CI status entries on arbitrary commits via `Commit#create_status_from_github!`, which can bypass `ci.require` gating and enable an unauthorized deploy for a victim stack that has continuous delivery enabled: [8](#0-7) 

With forged `pull_request` `labeled`/`unlabeled`/`closed`/`reopened` events, the attacker can archive/unarchive review stacks belonging to a victim repository: [9](#0-8) 

These are writes to stack/commit/PR state for a repository the attacker was never authenticated against, satisfying the "cross-repository writes" / "unauthorized deploy" impact bar.

### Likelihood Explanation
Exploitability requires:
1. A Shipit instance configured with the multi-organization `github:` secrets schema (documented and supported — see `docs/setup.md` and `config/secrets.development.example.yml`).
2. At least one configured organization with no `webhook_secret` set (explicitly allowed — `webhook_secret: # nil`) or one whose secret has otherwise been obtained by the attacker for a low-value/less-monitored org.
3ॉ. A "victim" stack for another configured organization in the same instance.

Given `webhook_secret` is documented as optional and organizations are commonly onboarded incrementally, condition (2) is realistic in real deployments running several orgs behind one Shipit install. No privileged Shipit session, API token, or GitHub write access is required — only knowledge that some org in the instance has no/weak webhook secret, which is discoverable via the very same 422 vs 200 response behavior exposed by `verify_signature`'s logging/response codes.

### Recommendation
After computing `repository_owner` and resolving `github_app`, additionally verify that the actual acted-upon entity (`repository.full_name`'s owner segment, or `organization.login` for org-level events) matches `repository_owner`/the resolved organization before dispatching to handlers. Alternatively, resolve the signing organization strictly from `Repository.from_github_repo_name(params.dig('repository','full_name'))&.owner` (i.e., derive both the signature-checking key and the target repository from the same canonical field), and reject events whose `repository.owner.login` does not match. Also consider making `webhook_secret` mandatory (removing the "return true unless webhook_secret" bypass) to eliminate the trivially-forgeable-signature avenue entirely.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`:
   ```yaml
   github:
     weak-org:
       app_id: ...
       webhook_secret: # nil, intentionally left unset
       ...
     victim-org:
       app_id: ...
       webhook_secret: "s3cr3t"
       ...
   ```
2. Attacker (no credentials) sends:
   ```
   POST /webhooks
   X-Github-Event: push
   X-Hub-Signature: sha1=0000000000000000000000000000000000000000
   {
     "ref": "refs/heads/main",
     "after": "<attacker chosen sha>",
     "repository": {
       "owner": { "login": "weak-org" },
       "full_name": "victim-org/target-repo"
     }
   }
   ```
3. `repository_owner` resolves to `"weak-org"`; `Shipit.github(organization: "weak-org").verify_webhook_signature` returns `true` immediately because `webhook_secret` is blank for `weak-org` — the bogus signature is never actually checked against `victim-org`'s secret.
4. `PushHandler#process` (or any other handler) uses `params.dig('repository','full_name') == "victim-org/target-repo"` to locate and mutate the victim's real `Stack`, e.g. triggering `stack.sync_github`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
