### Title
Webhook forgery via organization/repository binding mismatch when a configured GitHub App has no `webhook_secret` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken from the untrusted request body, while the webhook handlers that actually act on the payload look up the target `Stack`/`Repository` using a completely different field of that same body: `repository.full_name`. Because these two fields are never cross-validated against each other, and because `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for the resolved organization, an attacker who can address a webhook to an organization/app with a blank `webhook_secret` can forge a signature-free request whose `repository.full_name` names an entirely different (victim) organization's repository/stack, and have it processed as if genuinely delivered by GitHub for that victim stack.

### Finding Description
`verify_signature` resolves the GitHub App config purely from the payload: [1](#0-0) 

`repository_owner` is read straight from the JSON body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` treats an absent `webhook_secret` as automatic success: [3](#0-2) 

Meanwhile, every webhook handler (push, pull_request, membership, etc.) resolves the actual `Stack`/`Repository` to mutate using a *different* field of the same JSON body — `repository.full_name` — with no comparison back to the organization that was used to select/verify the signature: [4](#0-3) [5](#0-4) 

In a single-org deployment this is not exploitable, since there is only one `webhook_secret` and it necessarily matches every stack. But the engine explicitly supports and documents multi-org configurations, where each organization has its own independent GitHub App entry (and independently optional `webhook_secret`): [6](#0-5) 

If any configured organization's `webhook_secret` is left blank (the docs even show it as optional/commented-out in several examples), that organization becomes a "skeleton key": any request whose `repository.owner.login`/`organization.login` names that org passes `verify_signature` unconditionally, regardless of the `X-Hub-Signature` header supplied. The attacker then sets `repository.full_name` (and other event-specific fields such as `ref`, `after`, `team`, `member.login`, etc.) to target a stack that actually belongs to a different, properly-secured organization, and the handler processes it as a legitimate event for that victim stack.

### Impact Explanation
This breaks the binding "organization that authenticated == repository that is written." An unprivileged attacker with network access to `/webhooks` (no Shipit session, `ApiClient` token, or repository write access required) can, provided any org in the multi-org config has a blank `webhook_secret`:
- Trigger unauthorized deploys/syncs on a victim stack via a forged `push` event (`PushHandler` enqueues `GithubSyncJob`/deploy sync based on attacker-controlled `ref`/`after`).
- Manipulate `membership` events to add/remove arbitrary users from `Team`s that gate `Shipit.github_teams` authorization, escalating into application-wide access control.
- Manipulate pull-request/review-stack handlers to archive/unarchive or provision review stacks for a repository the attacker does not own.

This lands squarely in the High-impact bucket: escalation into `Shipit.github_teams` authorization and/or an unauthorized deploy/sync of a stack the attacker does not control.

### Likelihood Explanation
Likelihood depends entirely on operational configuration: it requires a multi-organization Shipit deployment where at least one configured GitHub App entry has no `webhook_secret` set. The setup docs present `webhook_secret` as optional/commented in more than one example, making this a realistic misconfiguration rather than a purely theoretical one, and the code contains no defense-in-depth check (e.g., verifying `repository.owner.login` equals the owner implied by `repository.full_name`, or requiring `webhook_secret` to be mandatory) to catch the case even when it occurs.

### Recommendation
- Make `webhook_secret` mandatory for every configured GitHub App/organization (fail closed instead of `return true unless webhook_secret` in `GitHubApp#verify_webhook_signature`).
- After signature verification, assert that the organization implied by `repository.full_name` (or `organization.login`) matches the `repository_owner` that was used to select the verifying GitHub App, rejecting the request otherwise.

### Proof of Concept
1. Configure Shipit with two GitHub Apps: `victim-org` (has a stack, `webhook_secret` set) and `attacker-org` (installed by the attacker, `webhook_secret` left blank).
2. POST to `/webhooks` with header `X-Github-Event: push`, no valid `X-Hub-Signature` (or any arbitrary value), and body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of signature.
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and triggers a sync for the victim's stack — despite the request never being authenticated for that organization.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```
