### Title
Interest accrual overflows total RAY value and permanently freezes a market - ([File: contracts/pool/src/interest.rs])

### Summary
An unprivileged market participant can create a very large, heavily utilized position whose scaled `borrowed × borrow_index` or `supplied × supply_index` later exceeds `i128::MAX` during routine accrual, even though both indexes remain below their configured `10^36` ceilings. [1](#0-0)  Because every pool mutation synchronizes the market before performing the requested operation, the resulting `MathOverflow` blocks repayment, withdrawal, liquidation, and further index updates for that market. [2](#0-1) 

### Finding Description
`global_sync` runs `accrue_step` for each elapsed compounding window before any market mutation proceeds. [3](#0-2)  `accrue_step` reconstructs the complete borrowed and supplied values with `scaled_to_original`, which multiplies scaled shares by the current RAY index. [4](#0-3)  `scaled_to_original` delegates to checked RAY multiplication rather than bounding the reconstructed value to the index ceiling. [5](#0-4) 

The index bounds therefore do not bound the reconstructed market values: documentation states that valid caps and bounded indexes do not guarantee future accrual fits, and that value overflow can occur before the index ceiling and block repayment or withdrawal. [6](#0-5)  The protocol’s own regression test demonstrates a one-billion-token, 98%-utilized market reaching `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`. [7](#0-6) 

The crash is persistent because `last_timestamp` remains behind ledger time when the accrual panics, so the next call retries the same overflowing calculation. [8](#0-7)  Every batched market operation loads a synced cache through `synced_market`, placing this panic ahead of supply, borrow, withdraw, repay, settlement, seizure, flash-loan, recapitalization, and revenue operations. [2](#0-1) 

### Impact Explanation
All funds associated with the affected market become permanently unreachable through the normal protocol paths. [9](#0-8)  Suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot unwind positions because the mandatory pre-operation accrual fails before any mutation executes. [10](#0-9) 

This is market-wide freezing rather than a self-inflicted transaction failure because the stored `borrowed`, `supplied`, and indexes are shared across all accounts using that `(hub_id, asset)` market. [11](#0-10)  The overflow also prevents the protocol from reaching the intended borrow-index cap behavior, which would otherwise stop additional borrower interest accrual without blocking operations. [12](#0-11) 

### Likelihood Explanation
The attacker path is unprivileged: supply enough of an 18-decimal asset to create approximately `1e36` RAY of principal, borrow near the market’s allowed utilization using sufficient collateral, then wait for the high-rate curve to compound the index. [13](#0-12)  Once the reconstructed value exceeds `i128::MAX`, any caller can trigger the persistent failure through the permissionless index-update path, and ordinary user operations trigger it independently. [14](#0-13) 

The exploit requires very large token balances or an equivalent combination of scaled principal and index growth, so practical likelihood depends on market asset supply, listing caps, collateral backing, and the configured rate curve. [15](#0-14)  The checked-in test uses protocol-admitted caps and reachable borrow/supply operations rather than forged state, malformed input, privileged calls, or oracle misbehavior. [16](#0-15) 

### Recommendation
Bound reconstructed RAY values, not just indexes and admission caps. [17](#0-16)  In particular, accrual should detect that `borrowed × borrow_index` or `supplied × supply_index` cannot fit `i128` before utilization is calculated and enter a well-defined capped or recovery state instead of panicking forever. [18](#0-17) 

A safer design would cap the borrow index and derived debt accounting before the RAY product exceeds the integer domain, while preserving a non-accruing withdrawal/repayment path for existing balances. [12](#0-11)  Position-limit and market-cap checks should also account for worst-case future index multiplication, because an amount admitted at index `RAY` can later become unrepresentable at a still-valid index. [19](#0-18) 

### Proof of Concept
The protocol’s test demonstrates the full state transition using `BIG18` and collateral markets:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);

let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
```

This creates one billion whole `BIG18` tokens supplied and approximately 98% utilization. [20](#0-19) 

Repeatedly advancing ledger time and calling `update_indexes` eventually returns `MathOverflow` before `MAX_BORROW_INDEX_RAY` is reached. [21](#0-20) 

The same persisted market state then causes both a one-unit supplier withdrawal and a repayment attempt to fail with `MathOverflow`, proving the freeze affects ordinary user exits and not just the explicit index-update call. [10](#0-9)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.
///
/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.
fn accrue_chunk(env: &Env, cache: &mut Cache, delta_ms: u64) {
    let step = accrue_step(
        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

    cache.set_borrow_index(step.borrow_index);
    cache.set_supply_index(step.supply_index);
    cache.accrue_revenue(step.revenue_shares);
```

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
```
