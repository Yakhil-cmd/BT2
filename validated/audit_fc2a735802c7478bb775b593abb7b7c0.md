## Title
Webhook authentication binds trust to `repository.owner.login`, but write handlers act on the independent `repository.full_name` field, allowing cross-organization stack manipulation when any configured GitHub App has no `webhook_secret` — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and therefore which HMAC secret) to validate the request against using `repository_owner`, a value read straight from the untrusted JSON body (`repository.owner.login` or `organization.login`). Every event handler, however, resolves *which stack to mutate* using a completely different field from the same body — `repository.full_name` — that is never covered by, or tied to, the value used for signature verification. Because `webhook_secret` is documented as optional per-organization, any organization configured without one causes `verify_webhook_signature` to unconditionally return `true`, letting an attacker submit an arbitrary, unsigned JSON body whose `repository.owner.login` matches the secret-less org while `repository.full_name` names a stack belonging to a totally different (properly secured) organization.

### Finding Description
The controller authenticates the webhook this way: [1](#0-0) 

`repository_owner` is derived purely from attacker-supplied JSON: [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-org `GithubApp`/`GithubHook` config, and signature checking is a no-op whenever that org has no secret configured: [3](#0-2) 

This "optional secret" configuration is explicitly documented and supported for multi-organization deployments: [4](#0-3) [5](#0-4) 

Once the request clears `verify_signature`, every registered handler resolves the target repository/stack using an entirely separate field, `repository.full_name`, with no cross-check back to `repository_owner`: [6](#0-5) 

For example, `PushHandler` uses `stacks` (bound to `full_name`) to enqueue a GitHub sync for matching stacks: [7](#0-6) 

The pull-request handlers exhibit the same pattern — they resolve `repository` from `params.repository.full_name` alone, independent of whatever value gated the signature check, and use it to archive/unarchive review stacks or update pull request records: [8](#0-7) [9](#0-8) 

**Binding broken:** `authenticated_org(repository.owner.login) == acted_upon_repo_org(repository.full_name)` is assumed but never enforced. The signature verification authenticates one field of the payload; every downstream handler acts on a disjoint field of the same payload.

### Impact Explanation
If a Shipit deployment configures multiple GitHub organizations (a supported, documented setup) and at least one of them has no `webhook_secret` (also documented as "optional"), an unprivileged attacker can POST an unsigned, fully-crafted JSON body to `/webhooks` with:
- `repository.owner.login` (or `organization.login`) set to the secret-less organization — this satisfies `verify_signature` trivially since `verify_webhook_signature` short-circuits to `true`.
- `repository.full_name` set to `<victim-org>/<victim-repo>` — an org that does have a properly configured secret.

Because handlers resolve the repository/stack strictly from `full_name`, this forges legitimate-looking events (`push`, `pull_request` labeled/opened/closed, etc.) against the victim organization's stacks without ever possessing the victim's `webhook_secret`. This can trigger `GithubSyncJob`s, archive/unarchive review stacks, and mutate pull request state on stacks belonging to an organization the attacker never authenticated against — a cross-repository/cross-organization write achieved purely by exploiting the mismatch between the field that gates authentication and the field that drives the write.

### Likelihood Explanation
Requires a deployment with at least two configured GitHub organizations where one has no `webhook_secret` set — an explicitly supported and documented configuration (`docs/setup.md`, `config/secrets.development.shopify.yml`). No GitHub credentials, session, `ApiClient` token, or knowledge of any secret is required; the attacker only needs to know the (public) login of the secret-less org and the (public) `owner/repo` full name of the target stack.

### Recommendation
Bind the authenticated identity to the field actually acted upon: after `verify_signature` succeeds, require that `repository.full_name`'s owner matches the `repository_owner`/organization that was used to authenticate the request (or, better, derive `repository_owner` from `repository.full_name` itself instead of a separately attacker-controlled field). Additionally, consider making `webhook_secret` mandatory for any organization to be accepted by `verify_webhook_signature`, rather than silently treating an absent secret as "always valid."

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `secretless-org` (no `webhook_secret`) and `victim-org` (properly configured with a webhook secret and an existing stack, e.g. `victim-org/prod-app`).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature` (or any garbage value), body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "full_name": "victim-org/prod-app",
    "owner": { "login": "secretless-org" }
  }
}
```
3. `verify_signature` calls `Shipit.github(organization: "secretless-org")`, whose `verify_webhook_signature` returns `true` unconditionally (no secret configured) — request passes. [10](#0-9) 
4. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/prod-app")` and enqueues `sync_github(expected_head_sha: "<attacker-chosen-sha>")` for `victim-org`'s stack, despite the request never being authenticated against `victim-org`'s secret. [11](#0-10)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
