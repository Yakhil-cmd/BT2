### Title
Path-prefix boundary confusion in mutual-signing check allows dispute-request forgery with a single real signer - ([File: wallet.js])

### Summary
CVE-2024-0753 is an HSTS "subdomain" bypass caused by a security check that matched a hostname as a prefix/suffix of another without enforcing a proper boundary (e.g., `evil-example.com` being wrongly treated as belonging to `example.com`). The `ocore` codebase contains the same bug class: signing-path strings such as `"r.0.0"`, `"r.0.1"`, `"r.0.10"`, `"r.0.11"` are checked with `Array.prototype.startsWith`/`substr` prefix matching without verifying that the next character is a path separator (`.`) or end-of-string. Because sibling indices like `10`, `11`, … share a textual prefix with `1`, a path such as `"r.0.10"` is wrongly accepted as evidence that `"r.0.1"` was signed.

### Finding Description
In `wallet.js`, the handler for `arbiter_dispute_request` verifies that a dispute-triggering unit was actually signed by both parties of an arbiter contract (offeror at signing sub-path `r.0.0`, acceptor at `r.0.1`) before accepting/storing the dispute: [1](#0-0) 

```js
const signing_paths = Object.keys(author.authentifiers);
const isMutuallySigned = signing_paths.find(p => p.startsWith('r.0.0')) && signing_paths.find(p => p.startsWith('r.0.1'));
if (!isMutuallySigned)
    return callbacks.ifError(...);
```

This is a pure string-prefix test, not a path-boundary test. Signing paths are dot-delimited (`r.0.0`, `r.0.1`, `r.0.10`, `r.0.11`, …), the same structural pattern used throughout the definition/authentifier engine (see the identical, previously-fixed hazard in `definition.js`'s `pathIncludesOneOfAuthentifiers`, which iterates authentifier paths with `authentifier_path.substr(0, path.length) === path`): [2](#0-1) 

The difference is that in `definition.js` this prefix test only gates an *optimization* — the real per-op signature/hash check still requires an exact match at the leaf (`assocAuthentifiers[path]`) in `evaluate()`: [3](#0-2) 
so a false-positive prefix match there cannot forge a signature.

In `wallet.js`, however, the `startsWith('r.0.0')` / `startsWith('r.0.1')` result is used *directly* as the security decision with no further exact-path verification. `author.authentifiers` comes straight from `objUnit` — an already-signed unit that is looked up by hash and can be produced/posted by any peer participating in an arbiter contract (an "unprivileged unit poster" in this flow, since the wallet only later checks that the contract hash/contacts-hash/arbiter matches, not that the paths are structurally exact): [4](#0-3) 

Because sibling paths of the offeror/acceptor branch (e.g. `r.0.10`, `r.0.100`, `r.0.1x…` if the mutual-signing 'or'/'and' structure has more than 10 sub-branches, or if the contract-defined address contains any nested branch whose serialized path textually begins with `r.0.0` or `r.0.1`) will satisfy `startsWith`, the check `isMutuallySigned` can be satisfied by authentifier paths that do not correspond to the real offeror (`r.0.0`) or real acceptor (`r.0.1`) branch at all — including a path that is only nested one level under a branch (e.g. `r.0.10.0`) that never signs anything real for `r.0.1`.

### Impact Explanation
`isMutuallySigned` gates whether the wallet stores/accepts an arbiter dispute request tied to a shared/contract address. If the boundary check can be satisfied without a genuine signature from both parties (offeror and acceptor), a single party (or a colluding party controlling only one side of the contract) could craft/forge a signing unit whose `authentifiers` include paths that merely share a textual prefix with `r.0.0`/`r.0.1` (e.g., paths belonging to an unrelated deeper branch of the same address's definition, or additional "or"/"r of set" alternatives numbered ≥10), causing the wallet arbstore to treat a one-sided signing as mutually agreed. This can lead to unauthorized dispute initiation/processing for a contract that only one party actually agreed to, i.e., loss of funds/agreement integrity in the arbiter/contract payment flow (asset issuance and transfer conditions / private-payment counterparty class explicitly in scope).

### Likelihood Explanation
Exploitability depends on the exact shared-address definition template used for arbiter contracts having (or being craftable to have) more than 10 numbered branches at the same nesting depth, or an attacker being able to influence/choose a definition/unit structure whose authentifier path set contains a sibling that textually collides with `r.0.0`/`r.0.1`. This requires control over the shared-address definition and the signing unit submitted as `body.unit`, both of which are attacker-influenced inputs in the `arbiter_dispute_request` message flow reachable by any correspondent device (an unprivileged peer in the dispute exchange), making this Medium likelihood — comparable to the reachability bar of the referenced CVE (requires a specific configuration, i.e., a specific branch/path structure, to trigger).

### Recommendation
Replace the prefix `startsWith`/`substr` comparisons on signing paths with boundary-aware comparisons, e.g. require `p === 'r.0.0' || p.startsWith('r.0.0.')` (and analogously for `r.0.1`), matching the same pattern that should also be hardened in `pathIncludesOneOfAuthentifiers` in `definition.js` for defense in depth. Apply this fix to every location in the codebase using `.startsWith('r.…')`/`.substr(0, prefix.length)` on dot-delimited signing/definition paths (`wallet.js`, `arbiter_contract.js`).

### Proof of Concept
1. Construct a shared/contract address whose definition contains, at path `r.0`, an `or`/`r of set` structure with at least 11 alternatives (`0`..`10`), so that a valid signing path for alternative 10 is `r.0.10`.
2. Have only the offeror side (branch `r.0.10`, unrelated to the real acceptor branch `r.0.1`) actually sign a unit; do not obtain the acceptor's signature at `r.0.1`.
3. Submit this unit as `body.unit` in an `arbiter_dispute_request` device message.
4. In `wallet.js`, `signing_paths.find(p => p.startsWith('r.0.1'))` matches `r.0.10`, and combined with a genuine `r.0.0` signature, `isMutuallySigned` evaluates to `true` even though the acceptor at `r.0.1` never signed — the dispute request is accepted as mutually signed. [1](#0-0)
