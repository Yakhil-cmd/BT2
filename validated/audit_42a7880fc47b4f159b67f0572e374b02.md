### Title
Cross-repository sha collision in `StatusHandler#process` flips `deployable?` on an unrelated victim Stack - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits with a bare `Commit.where(sha: params.sha)`, with no scoping to the repository named in the incoming webhook payload, unlike every other webhook handler in the engine. A `state: success` status webhook that is legitimately signed and delivered for one repository/organization will be applied to *every* `Commit` row across the whole install that happens to share that sha, including commits belonging to a completely unrelated Stack in a different repository.

### Finding Description
The binding that should hold is: *the Stack described by the incoming status webhook's `repository.full_name` == the Stack whose `Commit#deployable?` gets flipped*. The code breaks this binding.

`Handler#stacks` exists precisely to enforce repository scoping and is used by every other handler: [1](#0-0) 

`StatusHandler#process`, however, ignores `payload['repository']` entirely and queries `Commit` globally by `sha` only: [2](#0-1) 

For every matching `Commit` row (regardless of which `Stack`/`Repository` it belongs to), `create_status_from_github!` is invoked, which creates a `Status` scoped to `commit.stack_id` (the *victim's* real stack) and, on a `pending`/`success` transition, calls `stack.schedule_merges`: [3](#0-2) [4](#0-3) 

`Commit#deployable?` then evaluates `success? && !blocked?` using this forged status, becoming true with no real CI having run against the victim stack: [5](#0-4) 

Signature verification does not close this gap. `verify_signature` selects the HMAC key by `repository_owner`, which is read straight out of attacker-controlled payload fields (`repository.owner.login` / `organization.login`): [6](#0-5) 
And in the common single-app configuration (the default, documented setup), `Shipit.github(organization:)` ignores the `organization` argument altogether and always returns the one globally configured `GitHubApp`/`webhook_secret`: [7](#0-6) 
So signature verification only proves the request came from *some* repository covered by the (single, shared) GitHub App installation — it proves nothing about which `sha`/commit the status is entitled to describe, and `StatusHandler` never checks that either.

**Exploit flow:** the attacker needs write/push access to any one repository (Repo A) that is inside the scope of the same GitHub App/webhook installation Shipit is configured with (this can be a low-trust, unrelated repo in the same org, or, in a single global-secret setup, effectively any repo the operator's App is installed on). Because git commit SHAs are content-addressed, if Repo B (containing victim Stack S) is/was public, the attacker can fork it; any commit they didn't modify keeps the *exact same sha* as in Repo B. The attacker pushes that fork to Repo A and sets (via their own CI or the GitHub Statuses API, which they can call themselves with write access) `state: success` for that sha. GitHub delivers a validly signed `status` webhook to `/webhooks`. `verify_signature` passes (real signature, real delivery). `StatusHandler#process` finds the `Commit` row belonging to victim Stack S (because the sha is identical) and creates a `success` `Status` on it, flipping `deployable?` and triggering `stack.schedule_merges` on Stack S — a stack the attacker never authenticated against and has no legitimate relationship to.

### Impact Explanation
This is a payload for one repository mutating another tenant's `Commit`/`Stack` state, and can trigger an unauthorized deploy/merge trailhead (`stack.schedule_merges`) on a victim stack with no real CI signal — matching the "Critical: payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge" category. It is repeatable against any sha collision the attacker can arrange and is not limited to a single victim stack: any `Commit` row anywhere in the install sharing that sha is affected simultaneously.

### Likelihood Explanation
Preconditions: (1) attacker has write access to at least one repository within the scope of the GitHub App/webhook installation used by the target Shipit instance (or, in single global-secret deployments, any signed delivery suffices since the secret isn't organization-bound); (2) the victim commit's sha is knowable/reproducible by the attacker (trivial for any commit reachable from a public fork, since git hashes are deterministic over content); (3) Stack S has `ignore_ci?` false, is unblocked, and has no prior conflicting real status (as stated in preconditions). Given these, the attacker cost is low — forking a public repo and pushing it to a repo they control, then setting a status via the GitHub API is ordinary, unprivileged GitHub activity requiring no Shipit credentials, session, or secret. This is realistic wherever a single GitHub App/installation covers multiple repositories/stacks of differing trust levels, which is the documented default configuration.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository named in the payload, mirroring `Handler#stacks`/`repository_name`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status can only ever affect commits belonging to stacks whose repository matches `payload['repository']['full_name']`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` or `test/models/webhooks/handlers/status_handler_test.rb`):
1. Create `stack_a` for `repo-a/repo` and `stack_b` for `repo-b/repo` (two `Repository`/`Stack` fixtures/records).
2. Create `commit_a` under `stack_a` and `commit_b` under `stack_b` both with `sha: "deadbeef" * 5` (identical sha), `commit_b` with no prior status (`commit_b.state == 'unknown'`).
3. POST a `status` webhook payload with `sha` equal to that shared sha, `state: 'success'`, and `repository.full_name` set to `"repo-a/repo"` only (mirroring the real attacker request, i.e. it never names `repo-b/repo`).
4. Assert on both sides of the binding:
   - `assert commit_a.reload.success?` (expected legitimate effect)
   - `assert commit_b.reload.success?` (proves the cross-tenant leak — this commit belongs to `stack_b`, which was never named in the payload)
   - `assert commit_b.reload.deployable?` if `stack_b` has `ignore_ci?` false/`blocked?` false, showing the deploy-gate flip.
   - `assert_enqueued_with(job: ProcessMergeRequestsJob, args: [stack_b])` to show `stack.schedule_merges` fired for the uninvolved stack.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
