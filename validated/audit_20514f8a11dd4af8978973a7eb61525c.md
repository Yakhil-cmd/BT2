### Title
StatusHandler#process resolves commits by bare `sha` with no repository scoping, allowing a webhook from one (attacker-controlled) repository to write a Status onto a commit belonging to a different stack - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`'s `params` block only requires `:sha` and `:state`, never `:repository`, and — critically — `#process` never uses the `repository`/`stacks` scoping helper (`Handler#stacks`) that other handlers rely on. It looks up commits globally with `Commit.where(sha: params.sha)` and creates a `Status` on every match, regardless of which repository/organization authenticated the webhook.

### Finding Description
Binding claimed broken: `repository.full_name` (validated, attacker-unforgeable per-tenant identifier) == the scope used to select which `Commit`/`Stack` rows `StatusHandler#process` mutates.

Trace:
- `StatusHandler` params: [1](#0-0) 
- `#process` performs a global, unscoped lookup and write: [2](#0-1) 
- Contrast with every other handler (`PullRequest::OpenedHandler`, `ClosedHandler`, `UnlabeledHandler`, `AssignedHandler`, `LabelCapturingHandler`), which all `requires :repository { requires :full_name, String }` and resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any stack-scoped record, e.g. [3](#0-2) 
- The base `Handler` class even provides a `stacks` helper precisely for this scoping, which `StatusHandler` never calls: [4](#0-3) 
- `WebhooksController#verify_signature` only uses `repository.owner.login` (or `organization.login`) to select which `GitHubApp`/secret to verify against; it does not bind the signature to a specific repository's commits, and this secret (`webhook_secret`) is a single value shared by *every* repository configured under that GitHub organization/App: [5](#0-4) [6](#0-5) 

Exploit flow: an attacker who owns/administers any repository hooked into the same Shipit-configured GitHub organization (a normal, unprivileged position — e.g. they can push commits/tags, or trigger their own CI to POST arbitrary commit statuses via the GitHub Statuses API on their own repo) can produce a real, validly-signed `status` webhook event whose `sha` is set to a commit hash that also exists in a victim stack's repository (trivial when repos share git history via forking, or when the same commit is intentionally cherry-picked/pushed to multiple repos). Because `StatusHandler#process` does `Commit.where(sha: params.sha)` with no repository filter, GitHub delivers the event (signed with the shared org-level `webhook_secret`), and Shipit creates a `Status` row (e.g. `state: "success"`) against the *victim's* `Commit`, in the *victim's* `Stack`, even though the payload never had to name — let alone prove ownership of — that repository.

Existing guards do not close this gap: `verify_signature` authenticates "some repository under organization O", not "this specific repository"; `ExplicitParameters` never validates repository at all for this handler; and there is no model-level check that the `Commit` found belongs to the repository that signed the request.

### Impact Explanation
A forged/uncontrolled Status write lands on an arbitrary victim stack's commit as long as the attacker's own (legitimately webhook-connected) repository shares the org-level webhook secret and a matching commit sha exists. This can fake CI success (`state: success`) on a commit that has not actually passed CI, influencing `Commit#status`, `Stack#schedule_merges`, and deployability checks (`add_status` in `app/models/shipit/commit.rb`), i.e., "a payload for one repository mutating another's stack, commit" — matching the **Critical** impact category. It is repeatable against any commit sha the attacker can reproduce in a repo they control under the same organization.

### Likelihood Explanation
Requires: (1) the Shipit installation groups multiple repositories under one GitHub organization/App config sharing one `webhook_secret` (the common multi-repo Shipit deployment model), and (2) attacker owns/administers at least one repository in that org and can trigger a `status` event on a commit whose sha also exists in the target stack (achievable via forking/shared history). No Shipit secrets, sessions, or maintainer roles are needed — only ordinary repository-owner capabilities on a repo the attacker legitimately controls within the org. This is feasible and repeatable without live GitHub interaction in tests, since signature verification is stubbed/mocked in the existing test suite pattern.

### Recommendation
Add `requires :repository { requires :full_name, String }` to `StatusHandler.params`, and scope the commit lookup through the resolved `Repository`/`stacks` (e.g. `stacks.joins(:commits).where(commits: { sha: params.sha })` or filtering `Commit.where(sha: params.sha, stack: stacks)`) so a `Status` can only be created on commits that belong to the stack(s) tied to the authenticated `repository.full_name`, matching the pattern used by `PullRequest::OpenedHandler`/`ClosedHandler`.

### Proof of Concept
minitest plan (controller-level, matching existing `WebhooksControllerTest` conventions, stub `verify_signature`):
1. Create two stacks/repositories, `victim_repo` (stack `victim`) and `attacker_repo` (different stack), each with a `Commit` sharing the identical `sha` value (simulate shared git history).
2. `GithubHook.any_instance.stubs(:verify_signature).returns(true)` (or stub `verify_webhook_signature` to isolate the scoping bug from signature mechanics).
3. POST a `status` event body containing only `{ "sha" => shared_sha, "state" => "success" }` — **omit the `repository` key entirely**.
4. Assert `assert_nothing_raised { post :create, body: body, as: :json }` — confirms `ExplicitParameters` does not raise despite no `repository`.
5. Assert `assert_difference('victim_commit.statuses.count', 1)` around the post — confirms a `Status` was written to the victim stack's commit even though the payload carried no repository identity binding it to `victim_repo`.
6. Assert the created `Status.state == "success"` on `victim_commit`, demonstrating the cross-tenant mutation.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
