Based on my analysis, I found a genuine analog in the pending transaction queue's session-local optimistic accounting, which is explicitly documented as a known accepted limitation rather than a security bug.

### Title
Rejected transactions leave stale P_MAX/deploy-exclusivity slot reservations in `PendingTxSession` for the remainder of a chunk-production session - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
`PendingTxSession::check_pending` optimistically increments `session_access_key_tx_counts`, `session_deploy_tx_counts`, and `session_gas_key_withdrawals` for a transaction *before* the runtime has actually validated/applied it. If the runtime subsequently rejects the transaction (e.g., insufficient balance), these session-local counters are never rolled back [1](#0-0) . This mirrors the reported pattern in the external report: a party's contribution (`amountDeposited` / here, a reserved P_MAX or gas-key-withdrawal slot) is recorded, the underlying action is later rejected, but the recorded contribution is never cleared, leaving stale accounting that affects subsequent decisions.

### Finding Description
`check_pending` is called during chunk production to decide whether to admit a transaction into the chunk, based on aggregate constraints (`P_MAX` pending access-key tx count for contract accounts, deploy exclusivity, and gas-key withdrawal amounts) [2](#0-1) . The code comment itself acknowledges the issue: "If the runtime subsequently rejects the tx (e.g. insufficient balance), these counts are not rolled back and the tx is discarded (not reintroduced to the pool)" [3](#0-2) . Unlike the certified/pending-transaction-queue level accounting, which correctly reverses contributions per chunk via `PendingAccount::subtract` in `remove_certified_chunk_by_block_hash` [4](#0-3) [5](#0-4) , the `PendingTxSession`'s local, session-scoped counters (`session_access_key_tx_counts`, `session_deploy_tx_counts`, `session_gas_key_withdrawals`) have no corresponding decrement path if the runtime later rejects the transaction during actual application.

### Impact Explanation
The impact is a throughput/availability degradation, not a balance-inflation or theft bug: a rejected transaction can consume an account's P_MAX slot or deploy-exclusivity slot for the remainder of the chunk-production session, causing legitimate subsequent transactions from that account to be skipped (`PendingTxCheckResult::Skip`) even though no valid transaction is actually pending [6](#0-5) . This is a soft-DoS/throughput-reduction issue confined to a single chunk-production session and does not lead to unauthorized balance changes, token inflation, or state divergence.

### Likelihood Explanation
The code comment explicitly states this is an accepted, intentional trade-off, and further explains that the risk is mitigated because `check_pending` runs only after signature verification and basic validation, so "an adversary cannot cheaply spam rejected txs to exhaust slots" [7](#0-6) . This significantly limits exploitability — an attacker would need valid signatures and would only be able to affect a single session's throughput for their own account, not siphon funds or corrupt consensus-critical balances.

### Recommendation
This behavior is already documented and accepted as a bounded, low-severity trade-off by the code authors. If tightening is desired, the runtime could report rejected/invalid transactions back to `PendingTxSession` so it can roll back the optimistic `session_access_key_tx_counts`/`session_deploy_tx_counts`/`session_gas_key_withdrawals` increments, mirroring the reversal logic already present in `PendingAccount::subtract`.

### Proof of Concept
Not applicable as a security exploit — this is a self-acknowledged, bounded throughput limitation rather than an incorrect balance/state change. No PoC demonstrating unauthorized value transfer, inflation, or state divergence can be constructed from this path, since the effect is confined to transaction admission decisions within a single chunk-production session and does not affect settled account balances or consensus state (see the `is_zero` / `subtract` reversal logic that is correctly applied at the certified-chunk level) [8](#0-7) .

    /// Check if a transaction can be admitted given pending constraints.
    /// If admitted, updates session state and returns constraints
    /// for the runtime's balance/nonce validation.
    ///
    /// Acquires the pending transaction queue lock briefly to read pending state, then releases it.
    pub fn check_pending(
        &mut self,
        tx: &SignedTransaction,
        has_contract: HasContract,
    ) -> PendingTxCheckResult {
        let signer_id = tx.transaction.signer_id();
        let public_key = tx.transaction.public_key();
        let nonce_index = tx.transaction.nonce().nonce_index();
        let is_gas_key_tx = nonce_index.is_some();

        let snapshot = {
            let guard = self.pending_transaction_queue.lock();
            match guard.get(&self.shard_uid) {
                Some(ptq) => ptq.query_pending_state(signer_id, public_key, nonce_index),
                None => PendingStateSnapshot::default(),
            }
        };

        let session_access_key_count =
            self.session_access_key_tx_counts.get(signer_id).copied().unwrap_or(0);
        let session_deploy_count =
            self.session_deploy_tx_counts.get(signer_id).copied().unwrap_or(0);
        let total_access_key_count = snapshot.access_key_tx_count + session_access_key_count;
        let total_deploy_count = snapshot.deploy_tx_count + session_deploy_count;
        let tx_has_deploy = has_deploy_action(tx.transaction.actions());

        // Deploy exclusivity: a deploy cannot coexist with any other access
        // key tx (including another deploy) in the pending window.
        if !is_gas_key_tx {
            if total_deploy_count > 0 {
                return PendingTxCheckResult::Skip;
            }
            if tx_has_deploy && total_access_key_count > 0 {
                return PendingTxCheckResult::Skip;
            }
        }

        // P_MAX for contract accounts.
        if has_contract == HasContract::Yes && !is_gas_key_tx && total_access_key_count >= P_MAX {
            return PendingTxCheckResult::Skip;
        }

        // Build constraints for runtime validation.
        let gas_key = (signer_id.clone(), public_key.clone());
        let session_gas_key_withdrawal =
            self.session_gas_key_withdrawals.get(&gas_key).copied().unwrap_or(Balance::ZERO);
        let paid_from_gas_key =
            snapshot.pending_gas_key_cost.saturating_add(session_gas_key_withdrawal);

        // Update session state optimistically (assumes tx will be accepted).
        // If the runtime subsequently rejects the tx (e.g. insufficient
        // balance), these counts are not rolled back and the tx is discarded
        // (not reintroduced to the pool). This means a rejected tx may consume
        // a P_MAX or deploy exclusivity slot for the remainder of this chunk
        // production session, reducing throughput under high contention. The
        // risk is mitigated by the fact that check_pending is called after
        // signature verification and basic validation, so only transactions
        // with valid signatures can reach this point -- an adversary cannot
        // cheaply spam rejected txs to exhaust slots.
        if !is_gas_key_tx {
            *self.session_access_key_tx_counts.entry(signer_id.clone()).or_insert(0) += 1;
        }
        if tx_has_deploy {
            *self.session_deploy_tx_counts.entry(signer_id.clone()).or_insert(0) += 1;
