### Title
Fail-open handling in `handleSavedPrivatePayments`'s `validateAndSave` allows continued processing of a private payment chain after hash computation fails - ([File: network.js])

### Summary
In `network.js`, the function `handleSavedPrivatePayments` builds a `validateAndSave` closure that computes a payload hash via `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` inside a `try/catch`. When this call throws (e.g., because a peer-supplied private payment payload is malformed in a way that breaks the hashing routine), the `catch` block logs the error, optionally sends an error result to the peer, and calls `deleteHandledPrivateChain(...)`, but it does **not** `return`. Execution falls through to build `key` from the now-`undefined` `json_payload_hash` and unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` — the exact same fail-open pattern as the free5GC UDR advisory, where an input-processing failure is handled but the handler keeps going and invokes the downstream processing routine anyway.

### Finding Description
`network.js` (`handleSavedPrivatePayments` → inner `validateAndSave`):

```js
var validateAndSave = function(){
    var objHeadPrivateElement = arrPrivateElements[0];
    try {
        var json_payload_hash = objectHash.getBase64Hash(objHeadPrivateElement.payload, true);
    }
    catch (e) {
        console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
        if (ws)
            sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
        deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
    }
    var key = 'private_payment_validated-'+objHeadPrivateElement.unit+'-'+json_payload_hash+'-'+row.output_index;
    privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {
        ifOk: function(){ ... deleteHandledPrivateChain(...); eventBus.emit(key, true); ... },
        ifError: function(error){ ... deleteHandledPrivateChain(...); eventBus.emit(key, false); },
        ifWaitingForChain: function(){ ... cb(); }
    });
};
``` [1](#0-0) 

`arrPrivateElements` is attacker-controlled data taken directly from `unhandled_private_payments.json`, which is populated from private-payment chains sent over the wire (private payments received from a peer or via the hub), i.e. exactly the "private payment chains" attack surface allowed by scope. There is no `return` after the `catch` block, so:

1. `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` is invoked — this asynchronously calls the shared `cb` (the `async.each` iteratee callback for this row) once the delete completes.
2. Immediately, without waiting, execution continues synchronously to also invoke `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same (already known malformed) `arrPrivateElements`.
3. Depending on which branch (`ifOk`/`ifError`/`ifWaitingForChain`) fires, `cb` can be invoked a **second time** for the same `async.each` item, and `deleteHandledPrivateChain` can be re-invoked concurrently with the first delete, and `eventBus.emit(key, ...)` fires with a `key` built from `json_payload_hash === undefined` (the assignment never happened because the exception occurred inside the `try`).

This is a classic fail-open bug: a fatal input-processing error (hash computation failure) is acknowledged (logged + one recovery path started) but execution does not stop there, and the same unvalidated/malformed private-payment data is handed to the full validate-and-save pipeline regardless.

### Impact Explanation
Double-invoking the `async.each` iteratee callback (`cb`) for the same row breaks the invariants `async.each` relies on to track outstanding work; it can cause the surrounding `mutex.lock(["saved_private"], ...)` critical section to unlock prematurely while `validateAndSavePrivatePaymentChain` is still asynchronously running against the malformed chain, and the final callback (`unlock(); eventBus.emit("new_my_transactions", ...)`) can fire while a private-payment validation for the very same malformed input is still in flight. `eventBus.emit(key, true/false)` also fires with an `undefined` hash component in the key, meaning any code path relying on a distinct per-chain listener name (e.g. `wallet.js`'s consumer of `private_payment_validated-...`) could match against the wrong/ambiguous key for concurrently processed malformed chains, allowing a bogus "validated" completion signal to reach code that expects it to correspond to a specific, hash-identified private payment. Combined, this creates a node-local disagreement / inconsistent state around whether a specific private chain was accepted, and opens the door to accepting or acting on a private payment chain that never passed proper hash/validation checks — i.e., unintended acceptance of private-payment state, which is squarely within "private payment chains" and "node disagreement on validity" impact categories called out in scope.

### Likelihood Explanation
The trigger requires only that a peer or hub-forwarded private-payment chain contain a payload that causes `objectHash.getBase64Hash()` to throw (e.g., a payload shape that the hashing/serialization logic cannot handle, such as unsupported types, circular-like structures after JSON round-trip, or values exceeding assumptions the hash routine makes). Any unprivileged private-payment counterparty sending a payment to a wallet can supply such a payload; the code path is reached automatically via `handleSavedPrivatePayments`, which runs whenever unhandled private payments are processed. No authentication or special network position beyond being a private-payment counterparty is required, matching the "unprivileged... private-payment counterparty" reachability requirement.

### Recommendation
Add a `return` immediately after handling the `catch` block in `validateAndSave` so that once `getBase64Hash` fails and the chain is deleted/error reported, the function does not fall through to also call `validateAndSavePrivatePaymentChain`:

```js
catch (e) {
    console.log("getBase64Hash failed for private element", objHeadPrivateElement.payload, e);
    if (ws)
        sendResult(ws, {private_payment_in_unit: row.unit, result: 'error', error: e.toString()});
    return deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb);
}
```
Additionally, guard against building `key` from an `undefined` hash value, and ensure `cb` is invoked exactly once per row regardless of which branch is taken.

### Proof of Concept
Static proof (no dynamic verification performed, consistent with the "statically confirmed" caveat in the original report):
1. A peer sends a private payment chain over the wire that ends up stored in `unhandled_private_payments` with a `payload` object that causes `objectHash.getBase64Hash(payload, true)` to throw (e.g., a payload field with a value type not supported by the hashing/serialization routine).
2. `handleSavedPrivatePayments()` picks up the row and calls `validateAndSave()`.
3. The `try` block throws; the `catch` block logs the error, optionally sends an error result, and calls `deleteHandledPrivateChain(..., cb)` — but no `return` follows.
4. Execution proceeds to build `key` with `json_payload_hash === undefined` and call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the same malformed chain, resulting in a second, concurrent path of processing (potential double `cb()` invocation and premature/duplicated event emission) for data that was already deemed invalid.
