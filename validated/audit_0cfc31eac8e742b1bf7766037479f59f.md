### Title
Unhandled exception in `isChashValid` via crafted address / chash string causes validator crash — analogous to CVE-2016-7393 (out-of-bounds parsing crash on crafted input) - (File: `chash.js`)

### Summary
`chash.js`'s `isChashValid()` decodes an attacker-supplied 32- or 48-character string with `base32.decode()` / `Buffer.from(..., 'base64')` and then unconditionally feeds the decoded buffer into `buffer2bin()` → `separateIntoCleanDataAndChecksum()`, which `throw`s a raw `Error` whenever the resulting bit-length isn't exactly 160 or 288. Only the initial decode call is wrapped in `try/catch`; the subsequent parsing path is not, so a decoded buffer with an unexpected byte length (achievable through base32/base64 padding/character tricks that still satisfy the fixed string length check) throws past the `try` and out of `isChashValid` into its caller.

### Finding Description
`isChashValid(encoded)` in `chash.js` at [1](#0-0)  only length-checks the encoded *string* (32 or 48 chars) before decoding:
```
var chash = (encoded_len === 32) ? base32.decode(encoded) : Buffer.from(encoded, 'base64');
...
var binChash = buffer2bin(chash);
var separated = separateIntoCleanDataAndChecksum(binChash);
```
The decode call is inside `try/catch`, but `buffer2bin`/`separateIntoCleanDataAndChecksum` are called *after* the `catch` block closes, so any exception they raise is not caught here.

`separateIntoCleanDataAndChecksum` at [2](#0-1)  explicitly throws `Error("bad length=...")` when the binary length is not exactly 160 or 288 bits. Because base32 (5 bits/char) and base64 (6 bits/char, with padding quirks) decoding of a fixed-length string does not strictly guarantee a fixed output byte-length in all edge cases (e.g., malformed padding, non-canonical characters accepted by the `thirty-two` decoder, or base64 strings with embedded padding characters), an attacker can craft an `encoded` string of the required character length that decodes to a buffer whose bit-length differs from 160/288, triggering the uncaught throw.

This is structurally the same bug class as CVE-2016-7393: a parser trusts a length/format invariant from crafted input without validating it before indexing/processing fixed-size structures, causing an out-of-bounds/invalid-state condition. In Node.js this manifests not as a stack smash but as an uncaught synchronous exception that can crash the process (denial of service) if it propagates through an unguarded call chain.

`isChashValid` is exported and used by `validation_utils.js`'s `isValidAddress`/chash-checking logic [3](#0-2) , which is on the hot path for validating **every unit's addresses** (authors, message outputs, definitions) — i.e., reachable by any unpermissioned unit poster.

### Impact Explanation
If the uncaught exception is not caught by an enclosing `try/catch` somewhere further up the validation call stack, a single crafted unit containing a malformed address string can crash the validating node process. Since address/chash validation runs on every unit received from the network, this would let an attacker cause repeated denial-of-service against nodes processing the crafted unit, potentially preventing the network from validating/confirming units that reference the malformed address — matching the "network unable to confirm new units" impact bar.

### Likelihood Explanation
Reaching this code only requires posting a unit (or asset/AA message) containing an address-like field of exactly 32 or 48 characters that decodes via base32/base64 to a byte length other than 20 or 36 bytes. Constructing such an input is a matter of base32/base64 encoding experimentation and does not require any privileged access — any unit poster can attempt it. Whether the decoder (`thirty-two` package) can actually be coerced into producing a non-canonical byte length from a fixed-length string needs confirmation against the specific decoder implementation, which is the main uncertainty here.

### Recommendation
Wrap the entire body of `isChashValid` (not just the initial decode) in a single `try/catch`, and/or explicitly validate `chash.length` (bit-length via `buffer2bin`) equals 160 or 288 before calling `separateIntoCleanDataAndChecksum`, returning `false` instead of throwing on mismatch. Ensure all callers of `isChashValid`/`isValidAddress` treat any exception as "invalid," never letting it propagate uncaught during unit validation.

### Proof of Concept

```js

// craft a 32-character base32 string whose decoded byte buffer length is not 20 bytes
// (e.g., by exploiting padding/case handling in `thirty-two`'s base32.decode)
const malformedAddress = "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA="; // illustrative — exact bytes must be found via experimentation with thirty-two decoder
try {
  chash.isChashValid(malformedAddress);
} catch (e) {
  console.log("Uncaught exception, would crash validator if not guarded upstream:", e.message);
}
```
Note: I could not execute this in the sandbox to confirm `thirty-two`'s decoder actually yields a non-canonical byte length for a 32-character input — this must be verified against the vendored `thirty-two` module before treating this as fully confirmed. If the decoder always yields exactly 20 bytes for any accepted 32-char string, the throw path becomes unreachable and this finding would be downgraded/invalid.
