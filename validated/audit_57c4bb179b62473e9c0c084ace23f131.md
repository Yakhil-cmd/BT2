### Title
Unhandled `throw Error` in AA trigger construction can crash consensus nodes when trigger outputs don't match expectations - (File: `aa_composer.js`)

### Summary
`aa_composer.js`'s `getTrigger()` throws a raw, uncaught `Error` whenever it cannot find any output addressed to the AA it is triggering. This function is invoked directly, with no surrounding `try/catch`, from the stability-triggered AA-execution path (`handlePrimaryAATrigger`, `handleSecondaryTriggers`) that runs on every full node as consensus data becomes stable. Because ocore intentionally re-throws uncaught exceptions to kill the node process (`network.js`'s `uncaughtException` handler), any code path that lets `getTrigger()`'s invariant be violated is a full node crash — the same class of bug as the reported TensorFlow `CHECK`-fail (an unvalidated shape/invariant assumption reachable from untrusted input that aborts the whole process instead of failing gracefully).

### Finding Description
`getTrigger()` builds the trigger object for an AA by scanning `objUnit.messages` for payment outputs addressed to `receiving_address`, and unconditionally throws if none are found: [1](#0-0) 

This function has two call sites that are on the hot consensus path and are **not guarded by any try/catch**:

- `handlePrimaryAATrigger`, invoked for every unit that stability processing determined sent funds to an AA address (`aa_triggers` table populated by `main_chain.js`'s `handleAATriggers`): [2](#0-1) [3](#0-2) 

- `handleSecondaryTriggers`, invoked for every AA-generated response unit that itself pays another AA address, using the *just-composed* `objUnit` and an address list (`arrOutputAddresses`) collected incrementally while the response messages were still being finalized/filtered: [4](#0-3) [5](#0-4) [6](#0-5) 

The developers themselves acknowledge `getTrigger()`/trigger execution can crash the process: a best-effort "dry run" was added specifically to try to trigger the crash earlier, before a submitted unit is saved — but this only covers the narrow case of `conf.bDryRunNewTriggers` being enabled for freshly-submitted, non-ball joints, and does not wrap the call in error handling either (an exception there still propagates and crashes): [7](#0-6) 

The general trigger execution at actual stability time (`handlePrimaryAATrigger`/`handleSecondaryTriggers`, run on **every full node**, not just the composing one) has no such protection at all, and any divergence between (a) the `outputs`/`aa_addresses` SQL-driven selection of which addresses are considered "triggered" for a stable unit, and (b) `getTrigger()`'s own re-derivation of matching outputs from the unit's JSON `messages` (which is influenced by asset semantics like `is_private`, `fixed_denominations`, 0-amount filtering, and send-all removal for AA-composed responses), results in an uncaught `Error` and process termination.

Unlike TensorFlow's `CHECK`-fail, which is scoped to a single RPC call, this crash occurs inside deeply-nested DB-callback chains during main-chain stabilization — code that every full node executes identically and deterministically for the same stable MCI. A trigger that reliably reproduces the mismatch would crash every full node that reaches that MCI, at the same time, with no possibility of catching or recovering.

### Impact Explanation
This matches the "network unable to confirm new units" / "node disagreement on validity or stability" impact bucket: an uncaught exception thrown during main-chain stabilization crashes the node process outright (by design, per `network.js`'s `uncaughtException` handler, which explicitly re-throws "to crash the process"). If the triggering condition is deterministic given only unit/AA content (which both `handlePrimaryAATrigger`/`handleSecondaryTriggers` process identically on every node during stabilization), this can simultaneously crash all full nodes that have advanced to the offending stable MCI, halting confirmation of new units network-wide until operators patch/restart, i.e. a network-wide denial of service triggered by a single crafted unit or AA response.

### Likelihood Explanation
High severity if reachable, but likelihood of finding a concrete zero-cost trigger is uncertain from static review alone. The `validateAATrigger()` unit-validation function (`validation.js:986`) closely cross-checks output addresses/asset counts against `aa_addresses` before a unit is even accepted, which closes off the most obvious "0 outputs" cases for **primary** triggers coming directly from user-submitted units. The more promising avenue is the **secondary-trigger** path (AA-to-AA payments), where `arrOutputAddresses` is accumulated across multiple asynchronous per-asset processing steps (including `fixed_denominations` handling, private-asset rejection, and later 2-pass output filtering) before `handleSecondaryTriggers(objUnit, arrOutputAddresses)` is called with the final `objUnit`; a mismatch between when an address is added to `arrOutputAddresses` and when its outputs are later filtered out could reproduce the crash via a carefully engineered oscript/AA definition and payment sequence (e.g., interacting with `fixed_denominations` assets, send-all outputs, or auto-destroy assets). I was not able to construct or confirm a concrete minimal repro within the available context/tools, so this should be treated as a **likely-exploitable defect requiring dynamic verification**, not a confirmed 100%-reproducible exploit.

### Recommendation
- Wrap all calls to `getTrigger()` (in `handlePrimaryAATrigger`, `estimatePrimaryAATrigger`, and `handleSecondaryTriggers`) in `try/catch`, and treat a "no outputs" condition as a soft failure (skip the trigger / log and continue) rather than an uncaught throw that kills the process.
- Audit and eliminate any divergence between the SQL-driven output/AA-address matching used to schedule primary/secondary triggers and the JS-level output matching performed inside `getTrigger()`, particularly around `fixed_denominations`, `is_private`, 0-amount filtering, and send-all output removal for AA-composed responses.
- More broadly, audit other unguarded `throw Error(...)` statements inside async DB-callback chains on the consensus-critical stabilization path (e.g. `storage.js:904-995`, `main_chain.js`, `definition.js`) for the same failure mode, since ocore's deliberate crash-on-uncaught-exception policy turns any such assumption violation into a full-node DoS.

### Proof of Concept
Not conclusively constructed. Concretely demonstrated: `getTrigger()` throws an uncaught `Error("no outputs to " + receiving_address)` whenever `trigger.outputs` ends up empty [8](#0-7) , and this call is unprotected on the stabilization path [9](#0-8) [10](#0-9) , with the developers' own comment in `network.js` confirming that trigger construction/execution "would crash" under some conditions [11](#0-10) . Reproducing the exact crafted AA/asset/payment sequence that reaches this state requires dynamic testing against a running ocore node (e.g., constructing a secondary-AA trigger involving a `fixed_denominations` or `auto_destroy` asset combined with send-all removal) which was outside the scope of what could be validated via static code search alone.

function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
