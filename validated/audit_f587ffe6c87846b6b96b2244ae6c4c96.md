This is a genuine logic bug in `OpenedHandler#provision?` caused by Ruby operator precedence (`&&` binds tighter than `||`).### Title
`OpenedHandler#provision?` bypasses `repository.review_stacks_enabled` for `allow_with_label`/`prevent_with_label` provisioning behaviors due to `&&`/`||` operator precedence - (File: `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`)

### Summary
`OpenedHandler#provision?` intends to gate all review-stack provisioning on `repository.review_stacks_enabled`, but Ruby's `&&`/`||` precedence causes `review_stacks_enabled` to only apply to the `allow_all` branch. Any repository configured with `provisioning_behavior: allow_with_label` (or `prevent_with_label`) will provision a `ReviewStack` from a labeled pull request even when `review_stacks_enabled` is `false`.

### Finding Description
The broken binding: the code intends `repository.review_stacks_enabled == true` to be required for `ReviewStack` creation in all cases, but the actual guard is: [1](#0-0) 

which parses as `(review_stacks_enabled && provisioning_behavior_allow_all?) || (provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) || (provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)`. The second and third disjuncts never reference `review_stacks_enabled`.

Path: an attacker opens a pull request (with `head.ref` under their control) on a repository already registered with Shipit whose `provisioning_behavior` is `allow_with_label` and `review_stacks_enabled` is `false`, and applies the label matching `repository.provisioning_label_name` to their own PR. GitHub sends a legitimate, correctly-signed `pull_request` `opened` webhook (no forged signature needed — `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` passes because this is a real GitHub event) [2](#0-1) . `respond_to_pull_request_opened?` calls `provision?`, which returns `true` via the label clause regardless of `review_stacks_enabled`. `process` then calls `ReviewStackAdapter#find_or_create!` which creates a `Shipit::ReviewStack` with `branch: params.pull_request.head.ref` [3](#0-2)  and enqueues it into `ReviewStackProvisioningQueue` [4](#0-3) , which subsequently provisions the stack, checking out the attacker's branch and executing its `shipit.yml` steps.

No existing guard prevents this: `ExplicitParameters` only validates payload shape, not authorization; `verify_signature` only checks the webhook signature is from the correct GitHub org, not the intent of `review_stacks_enabled`; and no model validation on `Repository`/`ReviewStack` re-checks `review_stacks_enabled` before creation.

### Impact Explanation
This results in unauthorized code execution: a repository administrator configuring `provisioning_behavior: allow_with_label` while `review_stacks_enabled: false` (e.g., during a rollout or as a safety toggle) does not actually disable provisioning — an unprivileged contributor who can open a PR and add a label can still get their `shipit.yml` executed on the deploy host via `Command#start`/`PTY.spawn`. This is repeatable against any repository in this misconfigured state and matches the Critical category (RCE on the deploy host via `Command`).

### Likelihood Explanation
Requires the repository to already be registered in Shipit with `provisioning_behavior` set to `allow_with_label` or `prevent_with_label` while `review_stacks_enabled` is `false` — a plausible operator misconfiguration (e.g., intending the flag to be an overriding kill-switch). Given that configuration, attacker cost is trivial: open a PR and add a label they control (if they have label permission) or rely on `prevent_with_label` default (no label needed at all, since `!pull_request_has_provisioning_label?` is true by default). This is fully repeatable with each new PR.

### Recommendation
Fix operator precedence so `review_stacks_enabled` gates all branches, e.g.:
```ruby
def provision?
  return false unless repository.review_stacks_enabled

  repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
```

### Proof of Concept
Minitest integration test (in the handler test file):
1. Create a `Shipit::Repository` fixture with `review_stacks_enabled: false`, `provisioning_behavior: 'allow_with_label'`, `provisioning_label_name: 'deploy-preview'`.
2. Assert binding before: `repository.review_stacks_enabled == false`.
3. Build `pull_request` `opened` params with `labels: [{name: 'deploy-preview'}]`, `head.ref: 'attacker-branch'`.
4. Call `OpenedHandler.new(params).process` (or POST through the webhook flow with a valid signature/stubbed `verify_webhook_signature`).
5. Assert `Shipit::ReviewStack.exists?(environment: "pr#{params.number}")` is `true`, and that `stack.branch == 'attacker-branch'`, demonstrating `review_stacks_enabled == false` did not prevent stack creation — i.e., the two sides of the intended binding (`review_stacks_enabled` vs. actual provisioning outcome) diverge.

# frozen_string_literal: true

module Shipit
  class ReviewStackProvisioningQueue
    def self.work
      new.work
    end

    def self.add(stack)
      stack.enqueue_for_provisioning
    end

    def self.queued_stacks
      new.queued_stacks
    end

    def work
      queued_stacks.find_each(&method(:provision))
    end

    def queued_stacks
      @queued_stacks ||= Shipit::ReviewStack
                         .with_provision_status(:deprovisioned)
                         .where(awaiting_provision: true)
    end

    private

    def provision(stack)
      if stack.provisioner.provision?
        stack.provision
      else
        Rails.logger.info(
          "Putting review ReviewStack<#{stack.id}> back into the provisioning queue - #provision? was falsey."
        )
      end
    end
  end
