### Title
Asset Display-Name Spoofing via Unenforced Registry Suffix in `asset_metadata` - ([File: wallet.js])

### Summary
Similar to the Nautilus flaw where a `.desktop` file could impersonate a `.pdf` in the UI, `ocore`'s asset metadata mechanism lets an unprivileged asset issuer make their asset display with the exact same human-readable `name` as an already-registered, trusted asset, because the "suffix" that is supposed to disambiguate colliding names is never independently verified by the client — it's simply whatever the remote registry claims.

### Finding Description
Asset metadata (the display `name` shown to wallet users) is fetched from a `data` message posted by an address that calls itself the asset's `registry_address`. Any address can play this role for an asset it defines — there is no requirement that the address be a "known"/trusted registry: `fetchAssetMetadata` only checks that the metadata unit's author equals the claimed `registry_address`, and that a `name` string is present. [1](#0-0) 

The schema comment makes explicit the intended anti-collision design: a `suffix` should be appended "only if the same name is registered by different registries for different assets, equal to registry name." [2](#0-1) 

However, nothing in the code enforces this rule. The `suffix` value is taken verbatim from the registry's own response (`response.suffix`) and stored/used as-is, with no check for whether another registry already registered the same `name` and thus a suffix is actually required: [3](#0-2) [4](#0-3) 

The hub endpoint that serves this metadata performs no additional validation either — it simply echoes back whatever was stored for the asset: [5](#0-4) 

The client-facing display logic then concatenates `name` and `suffix` (or omits the suffix entirely if the malicious registry chose not to supply one): [6](#0-5) 

Because any address can self-issue an asset and simultaneously act as its own "registry" (posting a `data` message naming its own newly-created asset), an attacker can pick a `name` identical to a well-known, already-circulating asset (e.g. a stablecoin ticker) and simply not send a `suffix`, so the wallet UI shows an indistinguishable name for two completely different underlying assets (different hash, different issuance/transfer conditions). This is directly analogous to the Nautilus bug: the UI-facing identifier (file extension / asset name) does not reliably reflect the true underlying object (`.desktop` executable / a different, potentially malicious asset), and the mechanism meant to disambiguate (`trusted` metadata confirmation / `suffix`) is not actually enforced.

### Impact Explanation
A user relying on the wallet's displayed asset name (e.g., when selecting an asset to send, confirming a private payment, or receiving a textcoin/payment) can be deceived into treating an attacker-issued worthless or malicious asset as if it were a legitimate, trusted asset with the same displayed name. This can lead to real fund loss: the victim sends genuine value (e.g., GBYTE or a genuine token) in an ostensible exchange for what they believe is the trusted asset, while receiving/holding the attacker's spoofed asset instead, or accidentally selects the wrong (spoofed) asset entry from a picker populated by `readAssetMetadata`.

### Likelihood Explanation
Any address can trivially issue an asset and post the corresponding `data` metadata message naming itself as the registry — no special privilege, whitelisting, or coordination with the real registry is required. The attack only requires timing (posting before the client fetches conflicting metadata) or simply choosing a rarely-conflicting registry to avoid the update path (`REPLACE` only occurs for `conf.updatableAssetRegistries`, otherwise `INSERT OR IGNORE` is used per row), making exploitation straightforward for any single unprivileged asset issuer.

### Recommendation
Before accepting/displaying a `name` without a `suffix`, the client should check locally (and/or query the hub) whether the same `name` is already registered under a different `registry_address`, and if so, refuse to display the new asset without a distinguishing suffix (or force one derived from the registry address itself, not from attacker-supplied data). Additionally, the wallet should visually surface the `registry_address` (or a hash of it) alongside the asset name in any selection/confirmation UI so that visually identical names do not imply identical trust.

### Proof of Concept
1. Attacker issues a brand-new asset unit `X` with arbitrary `issue_condition`/`transfer_condition`.
2. Attacker's own address (author of `X`) posts a unit with a `data` message: `{asset: X, name: "USDT", decimals: 6}` (no `suffix`), making themselves the "registry" for asset `X`.
3. A victim wallet calls `readAssetMetadata`/`fetchAssetMetadata` for asset `X` (e.g., triggered by receiving a payment or textcoin in `X`), which accepts the metadata because the author matches the declared `registry_address` and a `name` is present. [7](#0-6) 
4. The wallet UI now displays asset `X` simply as "USDT", indistinguishable from a legitimate, previously-registered "USDT" asset from a different, trusted registry — since no collision check or suffix is enforced.
5. The victim, trusting the displayed name, sends real value expecting the legitimate asset's properties/backing, but instead is dealing with the attacker's asset `X`, resulting in financial loss.
