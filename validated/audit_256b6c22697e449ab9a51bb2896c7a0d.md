### Title
Webhook signature verified against organization from `repository.owner.login`, but handlers resolve the target repository from the independent, unchecked `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to verify the HMAC signature against using `repository.owner.login` (or `organization.login`) from the untrusted JSON body, while every webhook `Handler` resolves the actual `Stack`/`Repository` to act on using the independent `repository.full_name` field. Under Shipit's documented multi-organization configuration, an attacker who legitimately controls one configured GitHub organization (and therefore knows that organization's `webhook_secret`) can forge a webhook whose `repository.owner.login` matches their own org (to pass signature verification) but whose `repository.full_name` names a repository belonging to a different, victim organization also configured in the same Shipit instance.

### Finding Description
`Shipit.github(organization: repository_owner)` picks the `GitHubApp`/`webhook_secret` to verify against, where: [1](#0-0) [2](#0-1) 

`repository_owner` is read purely from `params.dig('repository', 'owner', 'login')` (or `organization.login`). This value determines the HMAC key used to validate `X-Hub-Signature` against `request.raw_post`.

Once the signature check passes, every `Shipit::Webhooks::Handlers::Handler` (including `PushHandler`, `CheckSuiteHandler`) resolves which `Stack`/`Repository` to operate on from a *different* JSON field, `repository.full_name`, not from `repository.owner.login`: [3](#0-2) 

`PushHandler#process` uses that repository resolution to trigger `stack.sync_github`, and `CheckSuiteHandler#process` uses it to schedule check-run refreshes: [4](#0-3) [5](#0-4) 

Shipit explicitly supports configuring one GitHub App per organization, each with its own `webhook_secret`, all sharing the same public `/webhooks` endpoint: [6](#0-5) [7](#0-6) 

Both `repository.owner.login` and `repository.full_name` are independently attacker-controlled fields inside the same HMAC-signed JSON body. Nothing enforces `repository.full_name.start_with?(repository.owner.login)`. The binding that should hold is:

`organization whose secret authenticated the request == owner of the repository whose Stack is written to`

but this equality is never checked. Before the attack, this binding coincidentally holds because a real GitHub App only ever sends events for repositories it is installed on, so `owner.login` and `full_name`'s owner always match, and the request also physically originates from that org's install. An attacker who legitimately owns one of the configured orgs is not limited to that install: they can send an arbitrary raw HTTP POST to `/webhooks` with a body of their own construction, sign it with their own known `webhook_secret`, but set `full_name` to `VictimOrg/some-repo`, breaking that equality.

### Impact Explanation
This lets an attacker who administers/owns one configured GitHub organization (and thus legitimately knows its `webhook_secret`, obtained the normal way when installing their own GitHub App) forge `push` and `check_suite` events for any `Stack` belonging to any other organization configured on the same Shipit instance. `PushHandler` drives `stack.sync_github`, which updates the stack's known commits and, when the stack has `continuous_deployment` enabled, results in an unauthorized automatic deploy of attacker-chosen "new commits" being reported to a victim's stack tracking. This matches the "unauthorized deploy" bucket in the rules. It also allows spoofing/corrupting a victim org's CI/check-run and merge-queue state via `CheckSuiteHandler`, potentially influencing merge decisions.

### Likelihood Explanation
This requires the Shipit multi-org configuration feature (documented and supported) and requires the attacker to be a legitimate GitHub organization admin/owner of one org configured on the target Shipit instance (unprivileged with respect to any *other* org's resources). No Shipit session, API token, or GitHub private key is required — only the ability to send a raw HTTP request to the public `/webhooks` endpoint signed with a secret the attacker already legitimately possesses for their own org.

### Recommendation
In `Handler#stacks`/`repository_name`, verify that the resolved repository's owner matches the organization whose `webhook_secret` validated the request signature (i.e., pass `repository_owner` from the controller down to handlers and assert `Repository#owner == repository_owner` before resolving `stacks`), rather than trusting `repository.full_name` independently of the signing organization.

### Proof of Concept
1. Configure Shipit with the documented multi-org schema, e.g. `OrgAttacker` and `OrgVictim`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker owns/administers `OrgAttacker` and legitimately knows its `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/some-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgAttacker_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgAttacker")` and successfully verifies the signature against `OrgAttacker`'s secret.
6. `PushHandler#process` calls `Repository.from_github_repo_name("OrgVictim/some-repo")` and triggers `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` for a `Stack` the attacker does not own, potentially triggering an automatic deploy if continuous deployment is enabled on that victim stack.

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
