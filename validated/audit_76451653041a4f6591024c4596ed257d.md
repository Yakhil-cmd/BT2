### Title
CCMenuUrlController#client is not scoped to the requested stack, so a single ApiClient token authorizes reads on every stack the operator has ever fetched a CCMenu URL for - (File: app/controllers/shipit/ccmenu_url_controller.rb)

### Summary
`CCMenuUrlController#fetch` mints a CCMenu badge URL containing an `ApiClient` token, but the client is looked up with `find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, which ignores the requested stack entirely. Because `Shipit::Api::CCMenuController#stack` also does not check the token's `stack_id` scoping, the resulting token is stack-agnostic and any leaked CCMenu URL grants read access to every stack the same operator has fetched a badge for.

### Finding Description
The broken binding: `ApiClient` created while fetching stack A's URL must not equal `ApiClient` created while fetching stack B's URL, i.e. `client_for(A).id != client_for(B).id`. In the actual code this equality is violated: [1](#0-0) 

`find_or_create_by!` is keyed only on `(creator, name)`, with no `stack` or `stack_id` in either the lookup or the `create_with` attributes, and `ApiClient#stack` is `optional: true`: [2](#0-1) 

So for the same operator, fetching the CCMenu URL for stack A and then stack B calls `@client ||= ApiClient...find_or_create_by!(creator: current_user, name: 'CCMenu Client')` twice and returns the identical row both times, with `stack_id` left `nil`.

This alone would be only a minor design smell if the consuming endpoint enforced stack scoping from the token. It does not. `Shipit::Api::BaseController#stacks` normally scopes lookups by `current_api_client.stack_id` when present: [3](#0-2) 

But `Shipit::Api::CCMenuController` overrides `stack` directly, bypassing that scoping mechanism entirely: [4](#0-3) 

It authenticates purely via `ApiClient.authenticate(params[:token])` and then resolves `Stack.from_param!(params[:stack_id])` unconditionally - it never checks whether the client is bound to that stack: [5](#0-4) 

`ApiClient.authenticate` itself only verifies the signed id, it performs no stack check: [6](#0-5) 

Exploit flow: an operator with read access to stack A and stack B visits Shipit's UI (or calls `fetch`) for stack A, receiving a URL with `token=T`. The client row created has `permissions: ['read:stack']`, `stack_id: nil`. The operator later fetches the CCMenu URL for stack B; the same memoized/persisted `ApiClient` row is returned (same `id`, same `T` when re-derived, since `authentication_token` is a deterministic function of `id`). Because `CCMenuController#show` never validates that the client is scoped to the stack in the URL, token `T` (originally minted "for" stack A) also authenticates GET requests for stack B's CCMenu XML, and vice versa. Any downstream party holding the leaked stack-A URL (a low-sensitivity public CI badge) can enumerate other stack params with the same token to read build/deploy status of stacks the operator never intended to expose via that link.

None of the listed guards prevent this: `require_permission :read, :stack` only checks the `permissions` array (`read:stack`), not stack identity; `stacks` scoping in `BaseController` is bypassed by `CCMenuController`'s override; there is no model validation binding `ApiClient` to a specific stack for this feature; `EnvironmentVariables#permit` and webhook-related guards are unrelated.

### Impact Explanation
The attacker (or anyone possessing one leaked CCMenu URL) obtains unauthenticated-relative read access to stack state (latest deploy/rollback status, exposed via the CCMenu XML) for every other stack the URL's original operator has ever fetched a CCMenu URL for, not just the stack named in that URL. This is a cross-tenant/cross-stack authorization escalation: a credential minted "for" one stack functions as a credential for arbitrary other stacks tied to the same creator. This matches the High severity category "escalation into unauthenticated read of stack state" - the token grants stack-state read beyond its intended scope, repeatable indefinitely since the token/permissions never expire and the underlying `ApiClient` row is reused for all future CCMenu fetches by that operator.

### Likelihood Explanation
Preconditions: the attacker must obtain a CCMenu URL that some operator previously generated (these URLs are commonly embedded in build-status badges, README files, or CI dashboards - designed to be shared, often outside authenticated contexts). No Shipit session, secret, or privileged role is needed by the attacker beyond having the URL and knowing/guessing target `stack_id`/`full_name` params. The operator side requires only normal, expected usage (visiting the stack settings page and clicking "fetch CCMenu URL" for more than one stack) - no misconfiguration required. This is low-cost and highly feasible.

### Recommendation
Scope the `ApiClient` to the specific stack when created in `CCMenuUrlController#client`, e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack: stack, name: 'CCMenu Client')`, and enforce that binding in `Shipit::Api::CCMenuController#stack` by using the inherited `stacks` scope (`stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so a token bound to stack A's `stack_id` cannot resolve stack B.

### Proof of Concept
Minitest plan (in `test/controllers/ccmenu_url_controller_test.rb`, not present in the repo today):
1. Create two stacks, `stack_a` and `stack_b`, and a `current_user` with read access to both.
2. Sign in as `current_user`, `get :fetch, params: { stack_id: stack_a.to_param }`; parse `ccmenu_url` from JSON, extract `token_a`.
3. `get :fetch, params: { stack_id: stack_b.to_param }`; extract `token_b`.
4. Assert the broken binding directly: `client_a = ApiClient.authenticate(token_a); client_b = ApiClient.authenticate(token_b); assert_equal client_a.id, client_b.id` (demonstrates same underlying `ApiClient` row for two different stacks).
5. Exploit the bypass: `get :show, params: { stack_id: stack_b.to_param, token: token_a }` on `Shipit::Api::CCMenuController` and assert `response.status == 200` and the returned XML corresponds to `stack_b`, proving token minted for stack A authorizes reads on stack B.
