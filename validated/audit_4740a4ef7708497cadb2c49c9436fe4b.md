### Title
Cross-organization webhook confused deputy: `webhook_secret` scoped by attacker-controlled payload field allows commit-status/push forgery for stacks belonging to other GitHub organizations - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
Shipit supports hosting multiple independently-administered GitHub Apps/organizations behind a single `/webhooks` endpoint (see the multi-org example in `config/secrets.development.example.yml:18-38` and `test/dummy/config/secrets_double_github_app.yml`), each with its own `webhook_secret`. `WebhooksController#verify_signature` picks *which* organization's secret to verify the HMAC against by reading an untrusted field straight out of the JSON body being verified, while the downstream handlers act on a *different* untrusted field of that same body to decide what to mutate. The binding "organization whose secret authenticated the request" == "repository/commit that is written" is never enforced, so a party who legitimately controls one onboarded organization's webhook secret can forge events that are applied to another organization's stacks/commits.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization from the request body itself: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`) — both attacker-controlled fields inside the very payload whose signature is about to be checked. `Shipit.github(organization: repository_owner)` then resolves to a distinct `GithubApp` config (and distinct `webhook_secret`) per organization in multi-org deployments, as configured via `lib/shipit/github_app.rb:44-51`.

Once the signature is accepted, handlers act on a *different* field of the same JSON body to determine what gets mutated:
- `Handler#repository_name` uses `payload.dig('repository', 'full_name')` to look up the target `Stack`: [3](#0-2) 
- `PushHandler#process` triggers `stack.sync_github` for stacks matched that way: [4](#0-3) 
- `StatusHandler#process` is even less scoped — it does not use `repository_name`/`stacks` at all, and updates commit status by SHA across the *entire* instance, regardless of which repository/organization the SHA belongs to: [5](#0-4) 

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` / the globally-matched `sha` (used to decide what is mutated) are independent, attacker-controlled fields inside the same signed blob, an attacker can build a payload where:
- `repository.owner.login` = `"attacker-org"` (an org the attacker legitimately administers and for which they therefore know/control the configured `webhook_secret`)
- `repository.full_name` = `"victim-org/victim-repo"`, or for the status event, `sha` = an arbitrary commit SHA belonging to any stack on the instance

Sign the whole payload with `attacker-org`'s webhook secret. `verify_webhook_signature` only checks that the raw body matches `attacker-org`'s secret — it has no way to know the payload's `full_name`/`sha` doesn't actually belong to `attacker-org`. The signature check therefore passes even though the mutation target (`victim-org`'s stack, or an arbitrary commit anywhere in the instance) was never authorized by that organization's own secret.

This is the same bug class as the Tunnl `TunnlTwitterOffers::sendFunctionsRequest()` issue: the value the system verifies/authorizes (`creatorFeePercentageBP`/here, the organization behind the signing secret) does not match the value the system actually acts on (`advertiserFeePercentageBP`/here, the repository or commit actually mutated).

### Impact Explanation
`StatusHandler` lets a forged, cross-organization request create a fabricated commit status (`state: success`, arbitrary `context`) for any commit SHA tracked by any stack in the Shipit instance, not only the attacker's own organization's repositories. Shipit's merge queue and continuous-deployment gating rely on GitHub commit statuses (`ci.blocking`, `merge.*`, required CI contexts documented in `README.md:511-538`) to decide whether a PR is mergeable / a commit is deployable. An attacker who legitimately administers one onboarded organization (and therefore knows that organization's webhook secret) can spoof a "green" CI status on a victim organization's commit, which can cause Shipit to treat an unreviewed/failing commit as mergeable/deployable — an unauthorized merge or deploy of a cross-tenant repository. `PushHandler` similarly lets the attacker enqueue sync jobs against a victim stack by forging `repository.full_name`. This satisfies the Critical bar: "cross-repository writes ... or an unauthorized deploy, rollback or merge."

### Likelihood Explanation
This requires the deployment to use Shipit's supported multi-organization GitHub App configuration (multiple orgs sharing one Shipit instance, each configuring its own `webhook_secret`) — a documented, supported mode, not a misconfiguration. Any party who is an admin of one of the onboarded orgs (and thus can see/set that org's webhook secret when wiring up its GitHub App) can mount the attack with a single crafted HTTP POST to `/webhooks`; no Shipit session, API token, or write access to the victim repository is needed.

### Recommendation
Do not use an attacker-controlled field inside the unverified payload to select the verification secret. Instead, bind the webhook delivery to a specific organization via a non-forgeable channel (e.g., a per-organization webhook path/token established at GitHub App install time), or after verifying, cross-check that the resolved `repository.owner.login`/`full_name` used by handlers actually belongs to the same organization whose secret validated the signature, rejecting the event otherwise. `StatusHandler` should additionally scope its `Commit.where(sha:)` lookup to commits belonging to stacks/repositories owned by the verified organization.

### Proof of Concept
1. Deploy Shipit configured with two organizations, e.g. `OrgA` and `OrgB`, each with its own GitHub App and `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. As an administrator of `OrgA` (attacker), craft a `status` webhook payload:
```json
{
  "sha": "<victim-commit-sha-belonging-to-OrgB-stack>",
  "state": "success",
  "context": "<required-ci-context-for-that-stack>",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" }
}
```
3. Sign the raw body with `OrgA`'s known `webhook_secret` using `sha1=HMAC-SHA1(secret, body)`, matching `GithubApp#verify_webhook_signature` in `lib/shipit/github_app.rb:76-83`.
4. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
5. `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` resolves the org as `OrgA` (from the payload) and accepts the signature; `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) then applies the forged status to the commit in `OrgB`'s stack, which was never validated by `OrgB`'s own webhook secret.
