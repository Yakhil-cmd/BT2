### Title
CCMenu API controller bypasses stack-scoped `ApiClient` authorization, allowing a token scoped to one stack to read the build/deploy state of any stack - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` resolves the target stack directly from the request parameter instead of going through the shared `stacks`/`stack` scoping helper used by every other API controller. This breaks the binding between "the stack an `ApiClient` token is authorized for" and "the stack whose state is actually returned," letting a stack-scoped, `read:stack`-permissioned token read CI/CD status for arbitrary stacks it was never granted.

### Finding Description
`Shipit::Api::BaseController` defines the canonical, permission-respecting stack resolution: [1](#0-0) 

`current_api_client.stack_id?` restricts the visible `Stack` set to the one the client is bound to (as exercised by the test "an api client scoped to a stack will only see that one stack" in `test/controllers/api/stacks_controller_test.rb`, and by the `here_come_the_walrus` fixture which has `stack: shipit`): [2](#0-1) 

`Api::StacksController` correctly reuses this scoping: [3](#0-2) 

`Api::CCMenuController`, however, overrides `stack` to bypass the scope entirely and resolves the stack from the raw `Stack` model against the unscoped `params[:stack_id]`, never consulting `current_api_client.stack_id`: [4](#0-3) 

`require_permission :read, :stack` only checks that the token has the *permission name* `read:stack` via `ApiClient#check_permissions!`, which is a flat list of permission strings and has no concept of *which* stack: [5](#0-4) 

So the only binding meant to restrict a scoped token to a single stack is the `stacks`/`stack` helper in `BaseController`, and `CCMenuController` is the one controller that doesn't use it.

### Impact Explanation
Equality that should hold: `stack the ApiClient is authorized for == stack whose data the request returns`. `CCMenuController` breaks this: `stack the ApiClient is authorized for (current_api_client.stack_id) != stack it touches (Stack.from_param!(params[:stack_id]))`. Any holder of a stack-scoped `read:stack` token (e.g. a CCMenu URL deliberately generated for one project, per `CCMenuUrlController`, or any `ApiClient` created with a `stack_id` and `read:stack` permission) can enumerate/guess other stacks' `to_param` and retrieve their build/deploy status, lock state, and last build label/URL — data the token was never scoped to see. This matches the "unauthenticated read of stack state" high-impact category, since the token functions as unauthenticated for all stacks outside its intended scope.

### Likelihood Explanation
Trivial and fully unprivileged relative to the target stack: an attacker only needs any valid stack-scoped `ApiClient` token with `read:stack` (their own token created for their own stack) and knowledge/guess of another stack's identifier (`owner/repo/environment`), which is often predictable or discoverable. No additional credentials, GitHub access, or session are required beyond the token they already legitimately hold for a different stack.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the shared, permission-scoped helper instead of the raw model, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, mirroring `Api::StacksController#stack`, so `current_api_client.stack_id` scoping is enforced.

### Proof of Concept
1. Using `ApiClientsController`, create (or have) an `ApiClient` scoped to `stack: my_project` with permission `read:stack` (e.g. via `CCMenuUrlController#fetch`, or directly through the `api_clients` UI by selecting a stack).
2. Call `GET /api/stacks/my_project/ccmenu.xml?token=<token>` — succeeds as intended, per `test/controllers/api/ccmenu_controller_test.rb`.
3. Call `GET /api/stacks/other_teams_private_project/ccmenu.xml?token=<token>` using the same token.
4. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` (not `stacks.from_param!`), the request succeeds and returns `other_teams_private_project`'s build status, lock state, and last deploy info, even though the token's `ApiClient` record is bound only to `my_project`.
