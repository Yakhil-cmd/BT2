### Title
`Shipit::Command#start` leaks interpolated (secret-containing) command arguments in `NotFound`/`Denied` exception messages - (File: `lib/shipit/command.rb`)

### Summary
`Command#start` rescues `Errno::ENOENT`/`Errno::EACCES` from `PTY.spawn` and builds the raised exception message from `interpolated_arguments`, which is the command string *after* `$VAR` interpolation against `@env` (which includes `GITHUB_TOKEN` for deploy-related commands). If an attacker-controlled deploy/task step references a nonexistent binary whose name is itself built from `$GITHUB_TOKEN`, the escaped token value ends up in the exception message that surfaces in task output.

### Finding Description
The broken binding: `Command::NotFound#message` must never contain a value sourced from `Command#env`/`unbundled_env`, i.e. `raised_message ∩ secret_env_values == ∅`. This does not hold.

- `interpolated_arguments` calls `interpolate_environment_variables(@args)` → `EnvironmentVariables#interpolate`, which replaces `$VAR` tokens with `Shellwords.escape(@env.fetch(variable) { ENV[variable] })` [1](#0-0) [2](#0-1) .
- `Command#start` rescues `Errno::ENOENT`/`Errno::EACCES` and raises `NotFound`/`Denied` using `Shellwords.split(interpolated_arguments.first).first` — i.e., the first token of the **already-interpolated** command string, not the original uninterpolated `@args` used by `#to_s`/`#exit_message` [3](#0-2) .
- `GITHUB_TOKEN` is injected into the command's `env` for deploy-related commands, confirmed by `test "#env uses the correct Github token for a stack"` asserting `command.env["GITHUB_TOKEN"]` equals the configured token [4](#0-3) .
- If a step's command line begins with a token like `$GITHUB_TOKEN-nonexistent-binary`, `interpolated_arguments.first` becomes `<token>-nonexistent-binary`, `PTY.spawn` raises `Errno::ENOENT`, and `NotFound.new("<token>-nonexistent-binary: command not found")` is raised, embedding the secret in the exception message.
- This differs from normal execution: `#to_s`/`#exit_message` (used elsewhere for status reporting) use the **uninterpolated** `@args`, which do not contain secrets [5](#0-4) . The `NotFound`/`Denied` rescue path is the one place secret-interpolated content is placed directly into an exception message that is not otherwise redacted before being surfaced as task/deploy output.

Existing guards (`EnvironmentVariables#permit`, whitelist checks) apply only to *task* user-supplied variables via `permit`, not to the fixed secrets (`GITHUB_TOKEN`, etc.) merged in by `Commands`/`TaskCommands#env`/`DeployCommands#env`, and they do not sanitize exception messages raised from `Command#start`.

### Impact Explanation
If a step's shell command name is or begins with an env interpolation of `GITHUB_TOKEN` and resolves to a nonexistent path, the token value leaves the process boundary embedded in the task's error output, visible to anyone who can view that task/deploy stream. This matches the "exfiltration of `GITHUB_TOKEN`... via an exception message shown in task output" impact category (Critical), scoped to whichever repository/stack's `shipit.yml` the attacker can get executed with that token in its environment.

### Likelihood Explanation
Exploitability strictly requires the attacker to get a step defined this way actually executed by `Command#start` with `GITHUB_TOKEN` present in `env` — i.e., control over a `shipit.yml` `deploy`/`task` step on a branch/commit that a stack (or a provisioned review stack) will build and run. The audit prompt frames this precondition as satisfied via a "`provision?` bypass" reachable by an unprivileged PR author; I located the provisioning-related code (`app/models/shipit/review_stack_provisioning_queue.rb`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`, `Stack#provision?`) but could not fully trace, within the remaining budget, whether that path lets an arbitrary unauthenticated PR author supply their own `shipit.yml` content that gets executed with the real `GITHUB_TOKEN` in env without any additional authorization/maintainer action. That reachability chain is the load-bearing precondition for this to be attacker-triggerable and is **not fully verified** here.

### Recommendation
In `Command#start`'s rescue blocks, build the `NotFound`/`Denied` message from the **uninterpolated** `@args.first` (or a redacted/`Shellwords`-escaped-but-not-secret-substituted representation), mirroring how `#to_s`/`#exit_message` avoid leaking interpolated secrets. Alternatively, run the command name resolution against `@args` before interpolation, and only interpolate the arguments actually passed to `PTY.spawn`, never echoing interpolated content back into any exception message.

### Proof of Concept
```ruby
# test/unit/command_test.rb (conceptual, do not need live GitHub)
test "NotFound message does not leak interpolated secrets" do
  command = Command.new(
    '$GITHUB_TOKEN-nonexistent-binary',
    env: { 'GITHUB_TOKEN' => 'secretvalue' },
    chdir: '.'
  )
  error = assert_raises(Command::NotFound) { command.start }
  refute_includes error.message, 'secretvalue'
end
```
Current behavior: `error.message` is `"secretvalue-nonexistent-binary: command not found"`, so the assertion `refute_includes` fails, demonstrating the leak, per [6](#0-5) .

```ruby
    def start(&block)
      return if @started

      @control_block = block
      @out = @pid = nil
      FileUtils.mkdir_p(@chdir)
      begin
        @out, child_in, @pid = PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)
        child_in.close
      rescue Errno::ENOENT
        raise NotFound, "#{Shellwords.split(interpolated_arguments.first).first}: command not found"
      rescue Errno::EACCES
        raise Denied, "#{Shellwords.split(interpolated_arguments.first).first}: Permission denied"
      end
```

```ruby
    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end
```
