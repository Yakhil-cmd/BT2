### Title
CCMenu API token authorization bypass allows reading any stack's build status — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
The `CCMenuController` used to serve build-status XML overrides the stack-lookup method used everywhere else in the API to enforce per-`ApiClient` stack scoping, instead resolving the requested stack directly from the URL parameter. Any `ApiClient` token — including one deliberately minted and scoped to a single stack — can therefore be used to read the deploy/build status of *any* stack in the Shipit installation.

### Finding Description
Every other controller under `Shipit::Api` inherits stack resolution from `Shipit::Api::BaseController`: [1](#0-0) 

`stacks` restricts the visible set to `current_api_client.stack_id` when the authenticated client is scoped to a specific stack; `stack` then does `stacks.from_param!(...)`, so a scoped client can never resolve a stack outside its `stack_id`. This is exactly the mechanism validated by the test `"an api client scoped to a stack will only see that one stack"` in `test/controllers/api/stacks_controller_test.rb:217`.

`Shipit::Api::CCMenuController`, however, defines its own `stack` method that ignores this scoping entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

It calls `Stack.from_param!` directly on the `Stack` model instead of going through the client-scoped `stacks` relation. `require_permission :read, :stack` only checks that the `read:stack` bit is present in `ApiClient#permissions` — it never checks which stack the permission applies to: [3](#0-2) 

The scoped token is exactly the credential Shipit itself hands out to unprivileged/automated consumers for this very endpoint: `CCMenuUrlController` mints an `ApiClient` with `permissions: %w[read:stack]` and a `stack_id` fixed to one specific stack, then returns a URL containing the client's bearer token as a query-string parameter for embedding in third-party CI dashboard tools: [4](#0-3) 

`CCMenuController#authenticate_api_client` also accepts the token via `params[:token]` (no Basic-Auth header needed), confirming this endpoint is meant to be used by low-trust external tooling holding only this narrow, single-stack token: [5](#0-4) 

Because `stack` bypasses the `stacks` scoping helper, a holder of this narrow CCMenu token — authorized to read only its own stack — can simply change `stack_id` in the request to read the CCMenu XML (build status, last build label, last build time, activity/lock state) of any other stack in the instance, including stacks belonging to entirely different repositories/organizations that the token holder has no business seeing.

This is the equality binding broken: **stack a token authorizes (`current_api_client.stack_id`) ≠ stack the token actually touches (`params[:stack_id]` resolved unchecked against all stacks)**.

### Impact Explanation
This grants unauthenticated (relative to the actual target stack) read access to deploy/build status for any stack, which matches the "High" impact category explicitly listed in the review rules: "unauthenticated read of stack state, task streams or deploy output." An attacker who legitimately possesses a narrowly-scoped CCMenu token for stack A (a token that is by design meant to be embedded in low-trust external CI dashboards) can enumerate stack IDs/params and read lock state, last build status, and build timing for every stack managed by the Shipit instance, leaking information about unrelated repositories, environments, and deploy activity across the organization.

### Likelihood Explanation
High. No special conditions are required beyond possessing any valid `ApiClient` bearer token that has `read:stack` permission scoped to a single stack — which is exactly the credential Shipit generates automatically for the "CCMenu URL" feature and hands to users/dashboards. Exploitation is a single unauthenticated (aside from the token) GET request with a different `stack_id` value; `Stack.from_param!` will happily resolve any stack by its numeric id or slug.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation (as `BaseController#stack` does), e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so a stack-scoped `ApiClient` cannot resolve a stack outside its authorized `stack_id`.

### Proof of Concept
1. Create (or have Shipit create, e.g. via the "Copy CCMenu URL" feature) an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']`, and note its `authentication_token`.
2. Send `GET /api/stacks/B/ccmenu.xml?token=<token-scoped-to-A>` where `B` is an arbitrary different stack the token was never granted access to.
3. Observe the response returns `200 OK` with stack `B`'s build/deploy status XML, even though the token is only supposed to authorize reads of stack `A` (compare against `Shipit::Api::StacksController`/`CommitsController`, which correctly return no data for out-of-scope stacks for the same scoped client, per `test/controllers/api/stacks_controller_test.rb:217`).
