### Title
Cross-transaction reuse of the same Bitcoin L1 lockup outpoint credits sats to multiple bonds - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`register-for-bond`'s L1 path computes `sats-total` via `verify-l1-lockups` → `validate-l1-lockup`, which folds over the caller-supplied `outputs` list and rejects duplicate outpoints only *within that single list* using a freshly-initialized `seen-outpoints` accumulator (`(seen-outpoints: (list))` at line 2013). [3](#0-2)  Because there is no persistent map recording which `(txid, output-index)` pairs have already been consumed by a prior `register-for-bond` call, the same on-chain Bitcoin lockup output can be submitted again in a later transaction (for the same or a different `bond-index`, or after unstaking/exiting) and will pass all the per-call checks (script match, amount match, merkle proof, block header validity) a second time.

### Finding Description
`verify-l1-lockups` (lines 1984–2019) computes the sats credited for a bond purely from re-verifiable Bitcoin-side facts (a merkle proof against a supplied header, and a P2WSH script match against `construct-lockup-output-script`), and returns `sum` as the amount of sats "locked." [4](#0-3)  The intra-call dedup guard (`ERR_DUPLICATE_LOCKUP_OUTPOINT`) only prevents listing the same output twice inside one `outputs` list of one transaction; it says nothing about outpoints already used in a prior transaction. [5](#0-4)  The stacks-node integration test that documents this dedup explicitly frames it as "the per-output dedup inside `validate-l1-lockup`" and only tests reuse "three times in the L1 proof list" within one call — it does not test or assert protection against reuse across separate `register-for-bond` transactions. [6](#0-5) [7](#0-6) 

This breaks the intended equality "sats credited to bonds == sats actually locked on Bitcoin," since the same locked UTXO can be counted toward `sats-total`/`get-total-shares-staked-for-cycle` for more than one bond registration (e.g., by the same staker re-registering into a new bond after their first bond's rollover/exit, or in principle by a colluding staker reusing a still-valid timelocked output for a second bond before the timelock matures).

### Impact Explanation
If the same L1 lockup can be recognized as valid stake more than once, the contract will treat sats as locked/backing rewards that are not actually backing a second commitment — this is a double-counting of a stacking commitment, which the rules classify as Critical (double-counting a commitment). At minimum it inflates a staker's effective bonded sats and reward share without a corresponding additional Bitcoin lock, i.e., reward slots/weight exceeding the value actually locked.

### Likelihood Explanation
This requires an unprivileged staker to simply call `register-for-bond` twice (or roll over) reusing the identical `l1-lockups` payload from an earlier successful registration; no admin, miner, or other user's key is needed, and the win condition depends only on knowing/replaying data that is already public on Bitcoin and in a prior Stacks transaction.

### Recommendation
Persist consumed `(txid, output-index)` outpoints in a contract-level map (analogous to `used-signer-key-authorizations` in pox-4) and check/insert into it inside `validate-l1-lockup`/`verify-l1-lockups`, rejecting any outpoint that has ever been credited to any bond, not just ones repeated within the current call's list.

### Proof of Concept
1. Staker locks `BTC_LOCKUP_SATS` in a Bitcoin P2WSH matching `construct-lockup-output-script`.
2. Staker calls `register-for-bond` with `l1-lockups` referencing that outpoint; `verify-l1-lockups`/`validate-l1-lockup` validate it and credit `sats-total` to bond A. [8](#0-7) 
3. Before or after that bond concludes (or on a different bond-index, if allowed), the staker submits a *new* `register-for-bond` transaction with the same `l1-lockups` payload (same txid/output-index/header/merkle proof).
4. Because `seen-outpoints` is reinitialized to `(list)` per call, the identical outpoint again passes `validate-l1-lockup` and is credited a second time, since there is no cross-transaction persisted outpoint registry to reject it.

Note: I was unable to fully verify from the index whether `register-for-bond`'s outer checks (`existing-membership`, allowance state, or `verify-not-prepare-phase`) incidentally prevent re-registration with the exact same outpoint in every code path (e.g., across rollovers or after an announced early exit) — the contract is large and only partially covered by the indexed context I retrieved. Confirming the exact exploitable sequence end-to-end (e.g., whether `existing-membership`/`allowance` bookkeeping blocks a second `register-for-bond` call from the same staker with the same outpoint) would require reading the full `register-for-bond` function and the bond membership/rollover logic in `pox-5.clar`, which exceeds what could be retrieved in this session; a full Devin session with direct file access is recommended to close that gap.

;; corresponds to the right timelock script for this staker, and that the lockup
;; occurred on-chain. If everything is valid, this returns the sum of all lockups in sats.
(define-private (verify-l1-lockups
        (staker principal)
        (bond-index uint)
        (lockups {
            outputs: (list 10
                {
                    height: uint,
                    tx: (buff 100000),
                    output-index: uint,
                    header: (buff 80),
                    leaf-hashes: (list 14 (buff 32)),
                    tx-count: uint,
                    tx-index: uint,
                    amount: uint,
                    unlock-burn-height: uint,
                }
            ),
            staker-unlock-bytes: (buff 683),
        })
    )
    (let (
            (bond (unwrap! (get-protocol-bond bond-index) ERR_BOND_NOT_FOUND))
            (accumulation (try! (fold validate-l1-lockup (get outputs lockups)
                (ok {
                    sum: u0,
                    staker: staker,
                    minimum-unlock-height: (get-bond-l1-unlock-height bond-index),
                    staker-unlock-bytes: (get staker-unlock-bytes lockups),
                    early-unlock-bytes: (get early-unlock-bytes bond),
                    seen-outpoints: (list),
                })
            )))
        )
        (ok (get sum accumulation))
    )
)
