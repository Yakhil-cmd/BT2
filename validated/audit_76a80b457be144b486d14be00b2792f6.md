### Title
Denial of Service via Unreachable "Should-Never-Happen" Throw in Multi-Issuer Asset Doublespend Check - (File: `validation.js`)

### Summary
For a fixed-denomination (or capped) asset with `issued_by_definer_only=false`, the doublespend check performed on `issue` inputs during payment validation does not filter conflicting records by author address, unlike the `transfer` branch of the same function. When two different addresses legitimately issue units of the same asset and denomination (explicitly permitted by the asset's own definition), the resulting query returns a record whose address does not belong to the validating unit's authors. This triggers a `throw Error("conflicting issue spent from another address?")` that is not caught anywhere in the call stack. Because it fires from a raw DB query callback (not the `async.series`/`callback` error path), it becomes an uncaught synchronous exception that propagates to the process-level `uncaughtException` handler in `network.js`, which deliberately re-throws to crash the process.

### Finding Description
`validatePaymentInputsAndOutputs` builds `doubleSpendWhere`/`doubleSpendVars` per input type inside `checkInputDoubleSpend`: [1](#0-0) 

For `type === "issue"`, the where-clause is built as `"type='issue'"` plus a `denomination=?` condition only — no `address=?` restriction is added (unlike `transfer`, which conditionally adds `AND address=?` only `if (objAsset && !objAsset.issued_by_definer_only)` is false): [2](#0-1) 

The resulting query is executed by `checkForDoublespends`, which iterates every returned conflicting row and enforces the invariant that a conflicting record must belong to one of the current unit's authors, else it throws: [3](#0-2) 

For an asset defined with `issued_by_definer_only: false` and `fixed_denominations: true` (a valid, intentional asset-definition combination validated in `validateAssetDefinition`), any address is allowed to issue coins of that asset/denomination — this is core, documented functionality, not an edge case. When two independent addresses each issue units of the same denomination for such an asset, the second unit's validation queries for prior `issue` rows of the same `asset`+`denomination` (with no address scoping) and finds the first issuer's record, whose address is not among the second unit's authors, hitting the `throw Error("conflicting issue spent from another address?")` path. This throw occurs inside a raw `conn.query` callback, bypassing the `async.series` error-collection mechanism in `validate()` entirely, so it is never delivered to `ifUnitError`/`ifJointError`: [4](#0-3) 

Because the throw is uncaught, it propagates up through `mutex.lock`/db driver callbacks to the top of the event loop, triggering Node's `uncaughtException` event. `network.js` installs a handler that intentionally crashes the process on any uncaught exception "to avoid ending up in an inconsistent state": [5](#0-4) 

This is the same bug class as the referenced advisory: a parser/validator encounters an unexpected-but-not-actually-invalid input, throws a raw system-style error instead of routing it through the application's expected error-handling path, and the framework's blanket rethrow-on-uncaught-exception behavior turns that into a full process crash.

### Impact Explanation
Any node (full node or hub) that validates a legitimately-issued unit for a multi-issuer, fixed-denomination asset where the same denomination was already issued by a different address will crash. An attacker (or even an innocent second issuer) can trigger this on every validating node by broadcasting such a unit, since validation of the same unit happens identically on all full nodes. This can be used to force mass crashes of full nodes/witnesses processing the network, halting confirmation of new units network-wide until operators notice and patch/restart nodes — a Denial of Service consistent with "network unable to confirm new units."

### Likelihood Explanation
The trigger condition requires only: (1) defining an asset with `is_private:false` (or private, does not matter), `fixed_denominations:true`, `issued_by_definer_only:false`, and (2) two different addresses each issuing at least one unit with the same denomination for that asset — both fully permitted, unprivileged operations reachable by any unit poster via ordinary `payment` messages with `type:"issue"` inputs. No special privileges, timing, or race conditions are needed beyond posting two ordinary units.

### Recommendation
Add an `AND address=?` (or equivalent authors-based) restriction to the `issue`-type doublespend query when the asset permits multiple issuers, mirroring the restriction already applied to the `transfer` branch. Additionally, replace the `throw Error("conflicting issue spent from another address?")` in `checkForDoublespends` with a call to `cb2(err)` (returning a normal validation error) so any residual unexpected condition results in unit rejection rather than an uncaught process-crashing exception.

### Proof of Concept
1. Post unit U1 defining asset A with `{is_private:false, is_transferrable:true, fixed_denominations:true, issued_by_definer_only:false, denominations:[{denomination:1000, count_coins:null}], auto_destroy:false, cosigned_by_definer:false, spender_attested:false}`.
2. From address X, post unit U2 with a `payment` message for asset A containing an `issue` input with `denomination:1000`.
3. From a different address Y, post unit U3 with a `payment` message for asset A containing another `issue` input with `denomination:1000`.
4. When any node validates U3, `checkInputDoubleSpend` queries `inputs JOIN units` for `type='issue' AND denomination=1000 AND asset=A AND unit != U3`, returning U2's row with `address=X`.
5. Since `X` is not among U3's authors (`Y`), `checkForDoublespends` executes `throw Error("conflicting issue spent from another address?")`, which is uncaught and crashes the validating node via the `process.on('uncaughtException', ...)` handler in `network.js`.
