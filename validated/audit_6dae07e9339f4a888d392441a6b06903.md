### Title
AA Definitions Are Accepted Without Sequence/Stability Validation Applied to Regular Address Definitions - ([File: storage.js])

### Summary
`storage.readAADefinition()`, the function used to resolve an Autonomous Agent's definition when validating a trigger's author or when the `definition` oscript op fetches an AA's definition, does not apply the same `is_stable=1 AND sequence='good'` integrity checks that the sibling function `readDefinitionByAddress()` / `readDefinitionAtMci()` apply to ordinary address definitions. This is structurally the same bug class as the `tough` advisory: one metadata-resolution path enforces expiration/consistency checks (top-level definitions) while a second, delegated/derived path (AA definitions) resolves the same kind of object with a weaker query.

### Finding Description
For regular addresses, `readDefinitionAtMci` requires the defining unit to be `is_stable=1 AND sequence='good'` before trusting the definition: [1](#0-0) 

For AA addresses, `readAADefinition` only filters by `mci<=?` on the `aa_addresses` table — it does not re-check `is_stable` or `sequence='good'` on the defining unit at read time: [2](#0-1) 

This function is the sole source of truth used to resolve an AA's spending/response conditions in two security-critical call sites:
1. `validateAuthor()` uses it to fetch the definition for any unit whose author is treated as an AA (`objValidationState.bAA` branch), and treats a missing definition as a fatal internal error rather than re-validating sequence/stability of the defining unit: [3](#0-2) 
2. The oscript/AA formula evaluator's `definition` operator uses it to fetch an arbitrary address's definition for use inside AA logic (e.g. to check attached conditions of a counter-party or a referenced address), falling back to `readDefinitionByAddress` only when no AA row exists: [4](#0-3) 

Because `readAADefinition` never re-derives trust from `is_stable`/`sequence`, if the row in `aa_addresses` can ever correspond to a unit that is later marked `final-bad` (e.g., due to a resolved double-spend/fork on the defining author), any code path relying on `readAADefinition` will keep treating the (now invalid) AA definition as authoritative, unlike the equivalent code path for ordinary addresses, which always re-derives trust through `is_stable=1 AND sequence='good'` at the read site. This mirrors the TUF flaw exactly: the "top-level" resolution path (`readDefinitionByAddress`) enforces the necessary state-consistency checks, but the "delegated" resolution path (`readAADefinition`) for a structurally identical object (an address definition) omits them.

### Impact Explanation
If two nodes disagree about whether the unit that authored an AA's `aa_addresses` row is still part of the `good` sequence (post-fork resolution), one node could accept trigger/response processing under an AA definition the other node has since invalidated. Because AA definitions gate fund release conditions (`bounce_fees`, `messages`, spending conditions), this can lead to disagreement on unit validity between nodes, or allow a party to keep exploiting a definition that should have been invalidated after a conflict was resolved — a stability/consensus-disagreement class impact.

### Likelihood Explanation
Exploitation requires a scenario where the unit defining an AA address participates in a non-serial/forked situation that later resolves to `final-bad` — a narrow but reachable circumstance for any address (including AA addresses) that is not yet stable when a second, conflicting definition/spend appears. AA addresses are ordinarily expected to be immediately/permanently active once posted, which may be the intentional design rationale, but the code gives no explicit indication that sequence-badness of the defining unit is otherwise excluded from `aa_addresses`, nor is that invariant enforced at read time by `readAADefinition` the way it is for `readDefinitionByAddress`. Full confirmation would require tracing every insertion path into the `aa_addresses` table to prove whether a row can ever exist for a unit that transitions from `good` to `final-bad`; I could not fully verify this insertion invariant within the available context.

### Recommendation
Add the same `is_stable=1 AND sequence='good'` verification to `readAADefinition` (join against `units` on the AA definition's unit, or explicitly verify sequence at read time) so the two definition-resolution paths enforce identical trust guarantees, matching the fix pattern used by `tough` (applying `load_delegations`'s validation identically to the top-level path).

### Proof of Concept
Not independently reproducible without confirming the `aa_addresses` insertion invariant (whether rows can exist for units later marked `final-bad`); the analog is established at the source-code level via the asymmetry between `storage.js:772-788` (`readDefinitionByAddress`/`readDefinitionAtMci`, which enforce `is_stable=1 AND sequence='good'`) and `storage.js:798-811` (`readAADefinition`, which does not).

function readDefinitionAtMci(conn, definition_chash, max_mci, callbacks){
	var sql = "SELECT definition FROM definitions CROSS JOIN unit_authors USING(definition_chash) CROSS JOIN units USING(unit) \n\
		WHERE definition_chash=? AND is_stable=1 AND sequence='good' AND main_chain_index<=?";
	var params = [definition_chash, max_mci];
	conn.query(sql, params, function(rows){
		if (rows.length === 0)
			return callbacks.ifDefinitionNotFound(definition_chash);
		callbacks.ifFound(JSON.parse(rows[0].definition));
	});
}

function readAADefinition(conn, address, to_mci, handleDefinition) {
	if (!handleDefinition)
		return new Promise(resolve => readAADefinition(conn, address, to_mci, (arrDefinition, unit, storage_size) => resolve({ arrDefinition, unit, storage_size })));
	if (to_mci === null || to_mci === Infinity)
		to_mci = MAX_INT32;
	conn.query("SELECT definition, unit, storage_size, mci FROM aa_addresses WHERE address=? AND mci<=?", [address, to_mci], function (rows) {
		if (rows.length !== 1)
			return handleDefinition(null);
		var arrDefinition = JSON.parse(rows[0].definition);
		if (arrDefinition[0] !== 'autonomous agent')
			throw Error("non-AA definition in AA unit");
		handleDefinition(arrDefinition, rows[0].unit, rows[0].storage_size);
	});
}
