This confirms the vulnerability. `Handler` provides a `stacks` helper that scopes to the repository named in the payload via `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , and `PushHandler` correctly uses this scoped `stacks` relation before acting [2](#0-1) . `StatusHandler`, however, bypasses this scoping entirely and queries `Commit.where(sha: params.sha)` globally across every stack/repository in the database [3](#0-2) .

### Title
Repository-unscoped SHA lookup in `StatusHandler#process` lets any repo's status webhook forge CI state on another stack's commit - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, with no repository/stack filter tying the lookup to the payload's own `repository.full_name`. Any commit SHA collision across two different Shipit-tracked stacks (trivial via forks, shared initial commits, or content-identical commits) lets a webhook validly signed for repo A write a `Status` row onto repo B's commit through `commit.create_status_from_github!` -> `Status.replicate_from_github!`.

### Finding Description
The broken binding: `status.stack_id` written by `Status.replicate_from_github!` should equal `Repository.from_github_repo_name(payload['repository']['full_name']).stacks.pluck(:id)`, i.e. only stacks belonging to the repository named in the verified payload. Instead it equals `commit.stack_id` for every `Commit` row matching `params.sha`, regardless of which repository the payload names [4](#0-3) [5](#0-4) .

Path: `WebhooksController#create` parses the raw payload and dispatches by event type, verifying the signature only against the GitHub App configured for `repository_owner` (the org named in the payload) [6](#0-5) . For the `status` event it calls `StatusHandler.call(params)`, whose `process` method does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) . Unlike `PushHandler`, which restricts its side effects to `stacks` scoped via `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) [2](#0-1) , `StatusHandler` never consults `payload['repository']` at all when locating commits to mutate. `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, which does `find_or_create_by!(stack_id:, state:, description:, target_url:, context:, created_at:)` — writing directly into `commit.stack_id`'s namespace with no cross-check against the requesting repository [7](#0-6) .

Exploit flow: the attacker forks or otherwise controls a GitHub repository whose org has the Shipit GitHub App installed (satisfying "emit webhooks from a repository they own"), and that repo shares a git commit SHA with a commit tracked under `victim`'s stack (fork ancestry, an identical empty/initial commit, or any content-identical commit — SHAs are content-addressed and independent of which repo references them). The attacker triggers (or directly crafts, if they can get a validly-signed request for their own repo) a `status` event with `state: 'success', context: 'ci/travis', created_at: <future>` for that shared sha. The webhook signature check in `verify_signature` only validates against the attacker's own org's `webhook_secret` — it never checks that `params.sha` actually belongs to a commit that repository owns [8](#0-7) . `StatusHandler#process` then finds `victim`'s `Commit` row (because the query is global, not repo-scoped) and creates a forged `success` status scoped to `victim`'s `stack_id`, with a `created_at` newer than the real `failure`, which the `Status::Group`/`Commit#status` "most recent per context" hierarchy will treat as authoritative.

None of the existing guards catch this: `verify_signature` authenticates the org, not the sha-to-repo relationship; `ExplicitParameters` (`params do requires :sha ... end`) validates only the payload shape, not repository ownership [9](#0-8) ; and there is no `drop_unhandled_event`/authorization check tying `sha` to `repository.full_name`.

### Impact Explanation
An attacker who controls (or forks within) any org with the Shipit GitHub App installed can inject a fabricated `success` CI status onto a commit belonging to a completely different, victim-owned stack, masking a real `failure`/`error` status and unblocking merge-queue or continuous-deployment gating logic that relies on `Commit#status`/`Status::Group` (a payload for one repository mutating another's commit/stack state). This matches the "Critical — a payload for one repository mutating another's stack, commit, task or team" category. The write is repeatable against any victim stack whose commit history shares a SHA with an attacker-reachable repo (most commonly via forking).

### Likelihood Explanation
Requires: (1) a commit SHA shared between the attacker's repo and the victim's tracked stack — realistic via GitHub forks (shared ancestor commits) or independently identical commits; (2) the attacker's own repo must be under an org/installation for which Shipit's GitHub App is configured (a real, valid `webhook_secret`), which is plausible in shared-org/monorepo/GitHub-App-org-wide-install setups. No Shipit session, API token, or secrets are needed — the attacker uses their own legitimately signed webhook. This is a config-and-topology-dependent but code-level bug, not one requiring any secret compromise.

### Recommendation
Scope `StatusHandler#process` to the repository named in the payload, mirroring `PushHandler`: resolve `stacks` via `Repository.from_github_repo_name(repository_name)` and restrict `Commit.where(sha: params.sha)` to `commits joins(:stack).merge(stacks)` (or equivalently filter by `stack_id: stacks.select(:id)`), so a status webhook can only write `Status` rows for commits under stacks belonging to the repository that the verified payload actually names.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Seed `victim_stack` (repository `victim/repo`) with a `Commit` at `sha: "abc123"` and an existing `Status.create!(stack_id: victim_stack.id, state: 'failure', context: 'ci/travis', created_at: 2.days.ago)`.
2. Seed an unrelated `attacker_stack` (repository `attacker/repo`) with no commit at that sha (simulating the attacker's own repo/org).
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo"`, `sha: "abc123"`, `state: "success"`, `context: "ci/travis"`, `created_at: 1.day.from_now`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert `Shipit::Status.where(stack_id: victim_stack.id, context: 'ci/travis').count == 2` and `victim_commit.reload.status.state == 'success'` — proving a payload naming `attacker/repo` wrote into `victim_stack`'s namespace, i.e. `status.stack_id (victim_stack.id) != Repository.from_github_repo_name(payload["repository"]["full_name"]).stacks.pluck(:id) (attacker_stack.id)`.
