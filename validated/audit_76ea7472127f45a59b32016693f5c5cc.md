### Title
Unauthenticated reconstruction of a pruned/freed output's financial data from a peer-suppliable joint cache - (File: `archiving.js`, `validation.js`)

### Summary
CVE-2021-37970 is a Chrome File-System-API use-after-free: a freed object's memory is later read/written through a stale reference that the renderer still holds, letting an attacker who controls the freed slot's content corrupt state. The closest reachable analog in this codebase is in the pruning/archiving path for `final-bad` units: once an output's row is deleted ("freed") from the `outputs` table during pruning, its authoritative data (address/amount/asset/denomination) is no longer available in the database, so the validator falls back to an in-memory, network-refillable cache (`archiving.assocCachedPrunedJoints`) to reconstruct it. That cache can be populated from content supplied by an arbitrary connected peer, gated only by a hash check whose completeness could not be fully confirmed in this review.

### Finding Description
When a `final-bad` unit becomes older than `min_retrievable_mci`, `storage.updateMinRetrievableMciAfterStabilizingMci` strips it and calls `archiving.generateQueriesToArchiveJoint` → `generateQueriesToVoidJoint`, which executes `DELETE FROM outputs WHERE unit=?` [1](#0-0)  — i.e., the output rows that describe that unit's address/amount/asset are permanently freed from SQL storage. To keep validation possible afterwards, the same code path calls `archiving.cachePrunedJoint(objJoint)` to keep a full copy of the joint in a process-local, TTL-based map (`assocCachedPrunedJoints`, 1‑hour TTL) [2](#0-1) [3](#0-2) .

Later, when a new unit tries to spend an output of that now-pruned unit, `validatePaymentInputsAndOutputs` in `validation.js` detects the missing `outputs` row (`!src_output.address`) and, instead of treating the input as unresolved, calls `archiving.getCachedOutput(input.unit, input.message_index, input.output_index)` to reconstruct `address`, `amount`, `denomination`, and `asset` straight from the cached joint, and then uses these fields for all downstream authorization/ownership/amount checks (`owner_address`, `arrAuthorAddresses`, `total_input`) [4](#0-3) .

The cache is not exclusively populated by the trusted local pruning process. `network.js`'s `tryRecoverPrunedContentOfFinalBadUnit` also populates the very same `assocCachedPrunedJoints` map from a joint delivered by any connected peer, gated only by `validation.allHashesAreValid(objJoint)` [5](#0-4) . This recovery path is reachable by an unprivileged remote peer any time a locally-submitted or relayed unit references a pruned `final-bad` input, because `validation.js` responds with `{error_code:"unresolved_dependency", arrMissingUnits:[input.unit], bRequestPrunedContent:true}` [6](#0-5) , which `network.js` turns into an active re-request of that unit's content from peers [7](#0-6) .

This is structurally the same bug class as the Chrome UAF: authoritative data for an object is destroyed ("freed") from its canonical store, yet a stale/attacker-influenceable side channel is later trusted to resurrect that data and drive further use (here, financial validation) without being re-verified against the object's original canonical state. I was not able to obtain the body of `allHashesAreValid` in this session (only its declaration was located via search), so I cannot fully confirm whether it re-derives and compares the *exact* historical `content_hash`/payload hashes that were committed for that specific pruned unit, or only checks generic well-formedness of hashes in the freshly supplied joint. If the check is not airtight (e.g., it does not tie the recovered payload back to the specific `content_hash` value that was already persisted in the `units` table for that unit before pruning), a peer could supply a syntactically hash-consistent but semantically fabricated payment message for that unit, causing `getCachedOutput` to hand back forged `address`/`amount`/`asset` values that are then accepted as if they were genuine historical output data.

### Impact Explanation
If the hash-check gate can be satisfied with attacker-chosen output data, this allows fabrication of a spendable output's address/amount/asset for a `final-bad`, already-pruned unit — i.e., unauthorized spending or supply inflation, since `total_input`/`owner_address` derived from forged data feed directly into whether the spending unit is accepted as valid. Even absent a full hash-check bypass, relying on a mutable, TTL-bounded, peer-refillable cache as the sole source of truth for previously-deleted financial rows is a fragile trust boundary for a "spend" fast-path and represents a genuine root-cause risk matching the requested bug class (stale-data reuse after the canonical object was destroyed).

### Likelihood Explanation
Reachable by an unprivileged unit poster/peer: any node can craft a unit that references an output of some historical `final-bad` unit that has since been locally pruned, forcing the local node down the `getCachedOutput`/`tryRecoverPrunedContentOfFinalBadUnit` path. However, exploitation depends on the strength of `allHashesAreValid`, which I could not fully inspect; I am marking likelihood as uncertain/medium rather than confirmed, pending review of that function's completeness.

### Recommendation
Audit `validation.allHashesAreValid` to ensure that recovered pruned content is checked against the exact `content_hash` (and, transitively, each message's `payload_hash`) that was already durably committed for that unit before pruning — not merely against a hash computed from the just-received data. Consider additionally re-verifying the recovered output against the unit's original authors/definition and against any other locally-retained commitments (e.g., stored `content_hash` in the `units` row) before trusting `getCachedOutput()`'s values in `validatePaymentInputsAndOutputs`.

### Proof of Concept
Not constructed — this requires confirming whether `validation.allHashesAreValid` can be satisfied with attacker-fabricated output data for a specific already-pruned unit, which I could not verify in this session due to tool-call limits (only the function's declaration, not its body, was located).

const PRUNED_JOINT_CACHE_TTL_ms = 60 * 60 * 1000;
let assocCachedPrunedJoints = {};

function cachePrunedJoint(objJoint){
	assocCachedPrunedJoints[objJoint.unit.unit] = { objJoint: objJoint, expiry_ts: Date.now() + PRUNED_JOINT_CACHE_TTL_ms };
}

function getCachedPrunedJoint(unit){
	const cached = assocCachedPrunedJoints[unit];
	if (!cached)
		return null;
	return cached.objJoint;
}
