### Title
Webhook signature is verified against a GitHub App selected from an attacker-controlled `repository`/`organization` field, decoupling the org whose secret authenticates the request from the org/repository the event actually mutates - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to verify the HMAC signature against by reading `repository_owner`, itself parsed straight out of the untrusted JSON body, before the signature has been validated. The event handlers that subsequently mutate state (create teams/users, add team members, sync stacks, update pull requests) key off a *different* field of the same body — `repository.full_name` — rather than the organization that was actually used to authenticate the request. This breaks the intended binding "organization whose secret authenticated the request == repository/organization being written to," exactly analogous to the `FALLBACK_ACTIONID` report where a policy set for one action id (`address(1)`) could be invoked with attacker-chosen parameters that were never bound to that policy's intended scope.

### Finding Description
`WebhooksController` runs `verify_signature` as a `before_action`: [1](#0-0) [2](#0-1) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`repository_owner` is read from the **raw, unauthenticated request body itself**, before `verify_webhook_signature` has run. In a multi-organization deployment (`Shipit.github(organization:)` picks a per-org config, see `lib/shipit.rb`'s `github`, `github_app_config`), this value is what decides which org's `webhook_secret` is used to validate the HMAC: [4](#0-3) 

`GitHubApp#verify_webhook_signature` further weakens the guarantee: if that org has no `webhook_secret` configured (documented as *optional*), verification is skipped entirely: [5](#0-4) 

Meanwhile, every default handler (`PushHandler`, `MembershipHandler`, pull-request handlers, `Handler#repository_name`) determines the record that is actually created/mutated using a *different* field of the same body — `repository.full_name` (or, for membership, `organization.login` used to create a `Team`/`User`): [6](#0-5) [7](#0-6) [8](#0-7) 

Because the field used to select the verifying secret (`repository.owner.login`/`organization.login`) and the fields used to decide what gets written (`repository.full_name`, `team`, `member.login`) are independent, attacker-controlled keys inside the same JSON body, the equality the design implicitly relies on — "the org whose secret validated this request == the org/repository this event writes to" — is never enforced in code. This mirrors the `FALLBACK_ACTIONID` bug class: a value meant to gate one narrow, intended usage (`repository_owner` chosen only to pick the correct per-org secret for *that org's own* traffic) can instead be freely chosen by the caller to redirect trust into an unrelated target (`repository.full_name`/`team`/`member`), the same way `target == address(1)` let a caller redirect validation into the fallback policy's `ecRecover` outside its intended fallback-only path.

### Impact Explanation
In any deployment that leaves `webhook_secret` unset for at least one configured organization (explicitly supported/documented as optional in `docs/setup.md`), or in a multi-org deployment where an attacker can obtain any single org's `webhook_secret`, this allows an unauthenticated caller to:
- Forge `push` events to run `stack.sync_github` on arbitrary tracked stacks belonging to a *different* organization's repository than the one whose secret was used (High: unauthenticated write to stack state).
- Forge `membership` events to create arbitrary `Team`/`User` records and add an attacker-chosen GitHub login to any team, including teams listed in `Shipit.github_teams`, directly escalating into the application's authorization model (Critical-adjacent: escalation into `Shipit.github_teams` authorization, per the rules' High-impact bucket).
- Forge `status`/`pull_request` events to inject fake CI status or manipulate `PullRequest`/`ReviewStack` state that gates deploy eligibility.

### Likelihood Explanation
Exploitability depends entirely on deployment configuration: it requires either (a) an org configured without a `webhook_secret` (documented-optional, so plausible in real deployments), or (b) an attacker who already possesses one org's `webhook_secret` in a multi-org setup. Neither of these is a "requires a Shipit session/ApiClient token/private key" precondition excluded by the rules, but I could not verify from the available files whether any additional network-level protection (e.g., mandatory secret enforcement, IP allowlisting) is layered on top of `WebhooksController` in a typical deployment — that would need to be confirmed with a running instance or the host app's routing/middleware configuration, which is outside `app/**`/`lib/shipit/**`/`config/routes.rb`.

### Recommendation
- Do not derive `repository_owner` (used to pick the verifying secret) from the same untrusted field(s) that handlers later trust to decide what to mutate, or enforce that the two must match post-verification.
- Make `webhook_secret` mandatory (reject configs / requests lacking it) rather than silently returning `true` in `verify_webhook_signature` when unset.
- After signature verification, re-derive and cross-check that the `repository`/`organization` embedded in the payload actually belongs to the organization whose secret validated the request, rejecting mismatches explicitly (analogous to the recommended `if (target == address(1)) revert();` guard in the source report).

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` (no `webhook_secret` set, or a secret known to the attacker) and `OrgB` (secret unknown to attacker) as in `test/dummy/config/secrets_double_github_app.yml`.
2. POST to `/webhooks` with header `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": { "id": 999, "name": "Deployers", "slug": "deployers", "url": "https://github.com/x" },
  "organization": { "login": "OrgA" },
  "member": { "login": "attacker-handle" }
}
```
3. `verify_signature` computes `repository_owner` → `"OrgA"`, loads `Shipit.github(organization: "OrgA")`, and (if `OrgA` has no secret) accepts the request unconditionally per `verify_webhook_signature`'s `return true unless webhook_secret`.
4. `MembershipHandler#process` creates/finds the `Team` using `params.team.id`/`params.organization.login` and adds `attacker-handle` as a member — with no relationship whatsoever enforced to the org that actually authenticated the request, letting the attacker choose which team (potentially one in `Shipit.github_teams`) to join.       config = secrets.github
    else
      config = github_app_config(organization)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
