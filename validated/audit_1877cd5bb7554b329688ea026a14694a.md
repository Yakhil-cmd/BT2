## Title
Cross-Organization Commit Status Forgery via Webhook Signature/Repository Binding Mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` authenticates an incoming webhook against the GitHub App configuration of a single organization derived from the payload, but `StatusHandler#process` never re-checks that binding — it looks up and mutates commits **globally by SHA across every repository/stack in the Shipit instance**. This breaks the equality "the organization whose secret authenticated the payload == the repository/stack whose commit gets written," directly analogous to the reported staking bug where a value used to enforce a security invariant (shares) diverged from the value that should have been checked (rewards actually owed).

### Finding Description
Signature verification is scoped per-organization: [1](#0-0) 

`repository_owner` (the field the signature is checked against) is read from `repository.owner.login` (or `organization.login`): [2](#0-1) 

`Shipit.github(organization:)` resolves a **per-organization** webhook secret from `secrets.yml` (`github_app_config`), so in a multi-tenant setup each onboarded GitHub organization has (and knows) its own configured secret: [3](#0-2) 

Once the signature is accepted for that organization, `WebhooksController#create` dispatches the *entire raw JSON body* to the event handler with no further scoping: [4](#0-3) 

`StatusHandler#process`, however, resolves the target purely from the attacker-controlled `sha` field, with **no check that the matched commit belongs to a stack/repository owned by the organization that produced the valid signature**: [5](#0-4) 

Because `Commit.where(sha: params.sha)` is a global, unscoped lookup, any commit sha tracked anywhere in the Shipit instance (any repository, any organization, any stack) can be matched and have a forged status record written to it, as long as the *signature* on the request is valid — and the signature only needs to be valid for the attacker's *own* onboarded organization (`repository.owner.login` in the same JSON body is independent of `sha`).

### Impact Explanation
Commit statuses directly gate deploy and merge safety checks: `Commit#deployable?`, `ci.require`/`ci.blocking` checks, and `MergeRequest#all_status_checks_passed?` / `StatusChecker` all rely on the statuses stored on a commit: [6](#0-5) [7](#0-6) 

An attacker who legitimately controls one onboarded organization's GitHub App/webhook secret (an "unprivileged" party with respect to every *other* tenant/stack hosted on the same Shipit instance) can forge a validly-signed `status` webhook whose `sha` targets a commit belonging to a completely different organization's repository, injecting a fabricated `success` status. This can satisfy required-CI checks and enable an **unauthorized deploy or merge** on a stack the attacker has no legitimate access to — matching the report's Critical-tier impact category (unauthorized deploy/merge via a broken trust binding), and mirroring the original bug's core pattern: a value governed by one accounting/authorization mechanism (shares/signature) diverging from the value actually consumed by a security-critical decision (owed rewards/target repository).

### Likelihood Explanation
This requires only that the Shipit deployment host multiple GitHub organizations behind the same instance (a documented, supported configuration via `github_app_config`/multi-org `secrets.yml`), and that the attacker controls one legitimately onboarded organization's webhook secret — no repository write access, no `ApiClient` token, no Shipit session, and no privileged Shipit account are required. The only precondition is knowledge of the sha of a target commit in another tenant's repository, which is routinely observable (commits/branches are typically public or discoverable via the target repo itself).

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving records by content-derived fields such as `sha`) to the stacks/repositories that belong to the organization validated by `verify_signature`, e.g. filter via `Repository.from_github_repo_name(payload.dig('repository','full_name'))` and its associated stacks (as `Handler#stacks`/`#repository_name` already does for other handlers), rather than a global `Commit.where(sha: ...)` lookup. More generally, every handler must re-derive its target strictly from the same organization/repository identity that `verify_signature` authenticated, never from an independent field an attacker can set arbitrarily inside their own validly-signed payload.

### Proof of Concept
1. Attacker legitimately installs/owns the Shipit GitHub App for `attacker-org` (a normal, documented multi-tenant onboarding) and thus knows the webhook secret Shipit has configured for `attacker-org`.
2. Attacker learns the SHA of a commit tracked by `victim-org`'s stack (e.g., from the public victim repo).
3. Attacker crafts a `status` event JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/irrelevant-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known webhook secret and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` succeeds (it only checks `attacker-org`'s secret against `repository.owner.login = attacker-org`).
6. `StatusHandler#process` executes `Commit.where(sha: "<victim commit sha>")`, finds the victim's commit (regardless of organization), and calls `commit.create_status_from_github!`, writing a forged `success` status that can satisfy `ci.require` and unblock deploy/merge on `victim-org`'s stack.   def github(organization: github_default_organization)
```ruby
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
```
