### Title
Cross-tenant webhook signature bypass in `MembershipHandler` via `repository`/`organization` field divergence - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the secret) used to validate a webhook body using `params.dig('repository','owner','login')` with a fallback to `params.dig('organization','login')` only when `repository` is absent. `Webhooks::Handlers::MembershipHandler#find_or_create_team!` instead uses `params.organization.login` to select/mutate the `Team` record. Because both `repository` and `organization` are independent, fully attacker-controlled keys in the raw JSON POST body, an attacker can make the two diverge, causing a payload verified under one (secret-less) organization's identity to mutate another organization's `Team`/`Membership` records.

### Finding Description
The binding assumed safe is: `organization_used_for_signature_verification == organization_owning_the_mutated_team`. Concretely: `repository_owner` (`app/controllers/shipit/webhooks_controller.rb:59-62`) resolves the org passed to `Shipit.github(organization:)` in `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`), while `MembershipHandler#find_or_create_team!` resolves the mutated `Team#organization` from a completely separate key, `params.organization.login` (`app/models/shipit/webhooks/handlers/membership_handler.rb:38-43`).

Real GitHub `membership` events are organization-scoped and normally carry no `repository` object at all — this is confirmed by the test suite, which has to synthetically merge a fake `repository: {owner: {login: 'shopify'}}` onto the `membership` payload just to satisfy `repository_owner`'s primary branch (`test/controllers/webhooks_controller_test.rb:208-218`). Since the controller parses `request.raw_post` with no schema validation before `verify_signature` runs, and `drop_unhandled_event`/`check_if_ping` do not validate payload shape against the declared event type, an attacker fully controls whether a `repository` key is present and what it contains, independent of the `organization` key the handler actually acts on.

`GitHubApp#verify_webhook_signature` returns `true` unconditionally when no `webhook_secret` is configured for the selected organization (`lib/shipit/github_app.rb:76-83`: `return true unless webhook_secret`). Given a multi-org `secrets.github` config where some configured org key (e.g. `attacker-org`) has no `webhook_secret` set, `Shipit.github(organization: 'attacker-org')` succeeds (it is a *known* org, so no `GithubOrganizationUnknown` is raised — `lib/shipit.rb:170-200`) and `verify_webhook_signature` trivially returns `true` for any body/signature.

Exploit: attacker POSTs to `/webhooks` with `X-Github-Event: membership` and body:
```json
{
  "action": "added",
  "team": {"id": <shopify_team_github_id>, "name": "x", "slug": "x", "url": "http://x"},
  "organization": {"login": "shopify"},
  "member": {"login": "attacker-controlled-or-arbitrary-user"},
  "repository": {"owner": {"login": "attacker-org"}}
}
```
`verify_signature` resolves `repository_owner` → `attacker-org`, calls `Shipit.github(organization: 'attacker-org').verify_webhook_signature` which returns `true` unconditionally (no secret configured), so the request passes with `head(422)` never triggered. `Shipit::Webhooks.for_event('membership')` then dispatches to `MembershipHandler`, which uses `params.organization.login` (`shopify`) and `params.team.id` to find/create and mutate the real `shopify` `Team`, adding an attacker-chosen member.

None of the existing guards catch this: `drop_unhandled_event` only checks a handler is registered for the event name; the `ExplicitParameters` schema for `MembershipHandler` (`params do ... requires :organization do requires :login, String end ... end`) validates types/presence but never cross-checks `organization.login` against `repository.owner.login`; `force_github_authentication`/`User#authorized?`/`require_permission!` are session/API-token guards irrelevant to the unauthenticated `/webhooks` endpoint.

### Impact Explanation
An attacker who can send arbitrary HTTP requests to the Shipit host (no session, no token, no secret) can create/delete `Membership` rows for any organization's `Team` whose `github_id` they know or guess, as long as the operator has any configured GitHub organization in `secrets.github` without a `webhook_secret`. This is a cross-tenant authorization write: a payload "verified" (trivially) under one org's non-existent secret mutates a different, protected org's team membership — matching the Critical category "a payload for one repository mutating another's ... team" / forged-webhook authentication bypass. It is repeatable against any team whose `github_id` is known, and against any org pairing where the verifying org lacks a secret.

### Likelihood Explanation
Requires: (1) a multi-org `secrets.github` deployment, (2) at least one configured organization entry with `webhook_secret` unset (a plausible but avoidable misconfiguration — GitHub Apps allow webhook secrets to be optional per the code, and nothing enforces every configured org have one), and (3) knowledge of the target team's `github_id` (a small sequential integer, not secret). No GitHub App private key, `webhook_secret`, session, or API token is needed by the attacker. Given those preconditions, the attack is a single unauthenticated POST and fully repeatable.

### Recommendation
Bind signature verification to the same organization identity that handlers act on: for organization-scoped events (e.g. `membership`), derive the verifying organization exclusively from `params.dig('organization','login')` (never from an attacker-suppliable `repository` key), and for repository-scoped events derive it exclusively from `repository.owner.login`, dispatched per registered event type rather than through a single generic fallback. Additionally, require `webhook_secret` to be present for every configured organization (fail closed / raise at boot or reject verification if `webhook_secret` is blank) instead of `verify_webhook_signature` returning `true` unconditionally when absent.

### Proof of Concept
```ruby
test "membership payload with mismatched repository.owner and organization.login lets an org without a webhook_secret mutate another org's team" do
  # Simulate secrets.github containing 'attacker-org' with no webhook_secret configured.
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)
  # 'shopify' app is left completely unstubbed -- its real secret is never checked/held by the attacker.

  shopify_team = shipit_teams(:shopify_developers)

  request.headers['X-Github-Event'] = 'membership'
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # arbitrary/invalid signature

  body = {
    action: 'added',
    team: { id: shopify_team.github_id, name: shopify_team.name, slug: shopify_team.slug, url: shopify_team.api_url },
    organization: { login: 'shopify' },
    member: { login: 'evil-attacker-user' },
    repository: { owner: { login: 'attacker-org' } } # decouples verify_signature's org from the mutated org
  }.to_json

  assert_difference -> { shopify_team.memberships.count }, 1 do
    post :create, body: body, as: :json
  end

  assert_response :ok
  # Binding check: org that verified (attacker-org) != org owning mutated team (shopify)
  assert_equal 'shopify', shopify_team.organization
  assert shopify_team.members.exists?(login: 'evil-attacker-user')
end
```
