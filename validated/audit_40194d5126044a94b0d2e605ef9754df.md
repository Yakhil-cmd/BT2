## Title
Global monotonic oracle timestamp watermark lets one caller's price update freeze another borrower's rescue transaction - (File: local-testing/contracts/market/market.clar / mainnet/contracts/market/v0-4-market.clar)

## Summary
`market.clar` enforces oracle-price freshness with a *global* map keyed only by feed identity, not by caller or transaction:

```clarity
(define-map last-update { type: (buff 1), ident: (buff 32) } uint)

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time) u0 (- stacks-block-time ts))))
    (and (<= delta max-staleness) (>= ts prev))))
``` [1](#0-0) [2](#0-1) 

`price-resolve` checks this against the shared `last-update` watermark and, if the submitted timestamp is newer, advances the watermark for *everyone*:
```clarity
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
(if (> timestamp last-update-time) (map-set last-update key timestamp) false)
``` [3](#0-2) 

This is the same class of "strict/monotonic check breaks a legitimate later action" bug as Y2K's Carousel `entitledShares > queue[index].assets` rollover check: a shared, mutable piece of state (the queue index / here, the `last-update` watermark) is primed by one transaction and then used as a strict gate for a different, unrelated caller's transaction, causing that caller's otherwise-valid operation to revert.

## Finding Description
`borrow`, `repay`, `collateral-add`, `collateral-remove` and `liquidate` all optionally accept `price-feeds` and route them through `write-feeds` → `price-resolve` before performing health checks and liquidation math (see the `feeds-check (try! (write-feeds price-feeds))` calls in `liquidate` and `collateral-add`) [4](#0-3) [5](#0-4) .

Each Pyth VAA a user builds off-chain is signed and timestamped at construction time and remains valid (per Pyth's own model) for as long as it is within `max-staleness` of the current block. However, `oracle-timestamp-fresh` additionally requires `ts >= prev`, where `prev` is the single global `last-update` value for that asset identifier, shared by *every* account that ever submits a price for that feed.

Consequence: if User A (e.g., a liquidator, or simply any other market participant) submits a price update with publish-time `T2` for asset X, the global watermark for X becomes `T2`. If User B (the victim, e.g., a borrower about to be liquidated) then submits their own independently-fetched, still-fresh (within `max-staleness`) VAA with publish-time `T1 < T2` — which can legitimately happen because Pyth VAAs from different relayers/guardian sets are not delivered in strict timestamp order, and because User B may have fetched their price slightly before User A — `oracle-timestamp-fresh` returns `false` and User B's entire transaction reverts with `ERR-ORACLE-INVARIANT`, regardless of the fact that User B's price data is itself fresh and legitimate.

Victim: any borrower attempting to `repay` or `collateral-add` to rescue an about-to-be-liquidated position, or to `borrow`/`collateral-remove`.
Attacker/unwitting third party: any other account (liquidator, another borrower, keeper) that happens to submit a newer, valid feed update for the same asset in the same or an earlier block.
Shared state: the single `last-update` map entry per `{type, ident}` [6](#0-5) , which is written by every caller and consumed as a strict monotonicity gate by every other caller.

**Outcome without attacker's transaction:** Victim submits their own fresh VAA (`T1`), `T1 >= prev`, the check passes, `repay`/`collateral-add` succeeds and the position becomes healthy, preventing liquidation.

**Outcome with attacker's transaction:** Attacker (even a liquidator racing to liquidate) submits a newer VAA `T2` for the same asset first, advancing `last-update` to `T2`. Victim's rescue transaction, submitted with their own valid but numerically older `T1`, now fails `(>= ts prev)`, reverts entirely (no state changes, no health improvement), and the victim's position remains liquidatable, at which point the same attacker can call `liquidate` (this time supplying `T2` again, which passes) and seize the victim's collateral. The freeze is temporary (until the victim re-fetches/obtains a newer VAA than `T2`), but it can be re-triggered every block by racing.

This is structurally identical to the Y2K bug class: a global piece of shared bookkeeping state, mutated as a side effect of one participant's ordinary transaction, is used as a hard gate on an unrelated participant's ability to perform a state-changing, funds-affecting operation, breaking their expected control flow even though nothing is wrong with their own inputs.

## Impact Explanation
This lands in **High — temporary freezing of funds**: a legitimate borrower can be prevented from repaying/adding collateral to escape liquidation, purely due to global oracle-timestamp bookkeeping being advanced by an unrelated party's transaction, and a racing liquidator can exploit this window to force through a liquidation that would otherwise have been avoided. The victim's collateral is seized during the freeze window they could not escape — an unprivileged principal (a competing liquidator, or even just an ordinary trader updating the same feed) directly harms another unprivileged principal (the borrower being liquidated).

## Likelihood Explanation
The likelihood is non-trivial but not trivially guaranteed: it requires (a) two or more callers using price feeds for the same asset within the same staleness window, and (b) the victim's VAA timestamp being numerically older than one already recorded. Because Pyth VAA delivery/propagation across relayers is not guaranteed to preserve timestamp order between independent fetches, and because a liquidator racing to liquidate has direct incentive to submit the newest feed first to both satisfy their own liquidation and simultaneously poison the watermark against the victim's rescue attempt, this is a realistic griefing vector during exactly the moments (price volatility, active liquidation races) when it matters most.

## Recommendation
Do not use a single global cross-caller monotonic watermark to gate price acceptance. Options:
- Drop the `(>= ts prev)` requirement entirely and rely solely on the `max-staleness` freshness bound (which already prevents stale-price replay within the intended safety margin), or
- Scope any monotonicity tracking to be advisory only (e.g., used purely for caching/optimization) rather than a hard `asserts!` that reverts an otherwise fresh, valid, differently-sourced price update, or
- If monotonicity must be enforced, key it per-transaction/per-caller context rather than as a single contract-wide watermark shared across all unrelated callers.

## Proof of Concept
1. Asset X has `max-staleness = 120s` and current `last-update[X] = T0`.
2. Alice (borrower) has a position near the liquidation threshold. At block time `t`, she fetches Pyth VAA `V1` for X with `publish-time = T1` (fresh, `T1 >= T0`, within staleness) and prepares `market.repay(..., price-feeds: [V1])` or `market.collateral-add(..., price-feeds: [V1])`.
3. Before Alice's transaction lands, Bob (a liquidator, or any other unrelated user borrowing/repaying a different position) submits a transaction with a newer VAA `V2` for the same asset X, `publish-time = T2 > T1`, still within staleness of the current block. `price-resolve` accepts `V2` and executes `(map-set last-update {type, ident} T2)` per `local-testing/contracts/market/market.clar:413-415`.
4. Alice's transaction with `V1` is now processed: `oracle-timestamp-fresh(T1, T2, max-staleness)` evaluates `(>= T1 T2)` as `false` → the `asserts!` in `price-resolve` fails → `ERR-ORACLE-INVARIANT` → Alice's entire `repay`/`collateral-add` call reverts, even though `V1` was independently fresh and valid.
5. Alice's position remains at its pre-existing (liquidatable) health. Bob (or any liquidator with a feed timestamped `>= T2`) calls `market.liquidate(alice, ...)` successfully, seizing Alice's collateral, in a scenario Alice could have prevented had her rescue transaction not been blocked by Bob's unrelated write to the shared `last-update` state.

Note: I was not able to fully inspect the `write-feeds`/`write-feed` fold helper body (grep for it errored due to a regex escaping issue and I did not get a chance to retry), so the exact multi-feed aggregation logic around `price-multi-resolve`/`iter-price-multi` is confirmed, but I could not double check whether `write-feeds` has any additional per-call ordering guard that might mitigate this. Based on the `price-resolve` code shown above (present identically in both `local-testing/contracts/market/market.clar` and `mainnet/contracts/market/v0-4-market.clar`), the core monotonicity check and shared global map are confirmed as described.
