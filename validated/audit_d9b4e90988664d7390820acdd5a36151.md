### Title
Cross-organization commit status forgery via webhook signature/repository binding mismatch - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The `status` webhook handler resolves the target `Commit` purely by `sha`, with no scoping to the organization/repository that was used to select and verify the webhook's HMAC signature. Because Shipit supports multiple GitHub organizations each with its own `webhook_secret`, an attacker who legitimately controls the webhook secret for *one* organization can forge a `status` event whose `repository.owner.login` matches that organization (so signature verification succeeds), but whose `sha` belongs to a commit that is tracked under a completely different organization/repository in the same Shipit instance. The forged CI status is written to that unrelated commit.

### Finding Description
`WebhooksController#verify_signature` selects which organization's secret to verify against using only `repository_owner`, itself taken straight from the untrusted payload: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw JSON `params` (fully attacker-controlled content, only its authenticity vs. *that org's* secret was checked) is dispatched to the matching event handler: [3](#0-2) 

`StatusHandler#process` then looks up the `Commit` to update using **only** `params.sha`, with no filter on repository, organization, or stack: [4](#0-3) 

Contrast this with `Handler#stacks`, which at least scopes lookups through `repository.full_name`: [5](#0-4) 

`StatusHandler` does not use this scoping mechanism at all — it is a base-class-level lookup by `sha` across the whole `commits` table, regardless of which repository/organization the commit actually belongs to.

This breaks the binding: **organization that authenticated the webhook == organization/repository whose commit state is written**. The signature only proves "this payload was sent by someone who knows OrgA's `webhook_secret`," yet the code lets that payload mutate CI status on any commit in the system, including commits belonging to OrgB, OrgC, etc. (each configured under `Shipit.github(organization: ...)` with its own secret, as seen in `test/dummy/config/secrets_double_github_app.yml`).

### Impact Explanation
`Commit#create_status_from_github!` records CI state (`state`, `description`, `target_url`, `context`) that feeds directly into `Commit#deployable?`/blocking-status checks defined by `DeploySpec` (`required_statuses`, `blocking_statuses`, `hidden_statuses`): [6](#0-5) 

An attacker holding a valid webhook secret for one organization's app installation can therefore flip an unrelated organization's commit to a passing CI state, unblocking deploys or continuous delivery for a stack they have no access to — a cross-repository/cross-organization write that can enable an unauthorized deploy. This satisfies the Critical impact bar ("cross-repository writes, or an unauthorized deploy").

### Likelihood Explanation
Any installation that configures more than one GitHub organization (a documented, supported configuration — see `secrets_double_github_app.yml` and `Shipit.github(organization:)`) is exposed. The only requirement is possession of a valid webhook secret for *any one* configured organization (which is standard, unprivileged knowledge for that org's own GitHub App/webhook configuration) and knowledge of a target commit `sha` belonging to a different organization's tracked repository (SHAs are not secret — they're visible in commit history, PRs, CI logs, etc.). No Shipit session, API token, or GitHub write access to the victim repository is required.

### Recommendation
Scope the `Commit` lookup in `StatusHandler` (and audit other handlers for the same pattern) to the repository/organization that was authenticated for that specific webhook delivery, e.g., join through `Stack -> Repository` and filter by `repository_name`/`repository_owner` derived from the same trust boundary used in `verify_signature`, rather than a bare `Commit.where(sha: ...)` across the entire table.

### Proof of Concept
1. Attacker's own repository "attacker-org/foo" is registered in this Shipit instance under GitHub organization `attacker-org`, which has its own configured `webhook_secret` (known to the attacker, as owner of that org/app).
2. Attacker crafts a `status` webhook payload:
   ```json
   {
     "sha": "<sha-of-a-commit-belonging-to-victim-org/bar>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/foo" }
   }
   ```
3. Attacker signs this payload with `attacker-org`'s `webhook_secret` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit belonging to `victim-org/bar`, and calls `create_status_from_github!`, writing a fabricated "success" status onto it — even though the signature only proved control of `attacker-org`'s secret, not any relationship to `victim-org`.
