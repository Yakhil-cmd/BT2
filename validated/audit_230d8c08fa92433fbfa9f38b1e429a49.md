## Finding: Confirmed



### Title
Unsanitized pull request label names become process environment variables for `git` subprocesses, enabling env-injection RCE (e.g. `DYLD_INSERT_LIBRARIES`/`GIT_SSH_COMMAND`) - (File: `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull request label name (uppercased) directly into the stack's environment hash with no allowlist, and that hash flows unfiltered through `StackCommands#env` into every `git` invocation performed by `StackCommands#fetch`/`#fetch_commit`/`#git_clone`. Because `Command#unbundled_env` merges `@env` **last**, on top of `BASE_ENV` and `PATH`, an attacker-chosen label name/value pair (e.g. `DYLD_INSERT_LIBRARIES` or `GIT_SSH_COMMAND`) is passed straight into `PTY.spawn`, letting an unprivileged PR author influence the git subprocess's execution environment on the Shipit host.

### Finding Description
The broken binding: the set of keys allowed into a `git` subprocess environment should equal `EnvironmentVariables#permit`'s allowlisted variable names, but for `ReviewStack`-derived env it actually equals **any string an attacker can put in a PR label**, i.e. `allowed_git_env_keys == {}` (empty allowlist) while `actual_git_env_keys == pull_request.labels.map(&:upcase)` (attacker-controlled, unbounded).

Path:
1. `LabelCapturingHandler#capture_labels` persists label names verbatim from the webhook payload with only a `String` type check in the `params` schema (no format/charset restriction): [1](#0-0) , schema at [2](#0-1) .
2. `ReviewStack#env` merges `pull_request.labels.each_with_object({}) { |n,h| h[n.upcase]='true' }` into `Stack#env` with no key filtering: [3](#0-2) .
3. `StackCommands#env` just merges this into its own base env: [4](#0-3) .
4. `StackCommands#fetch`/`#fetch_commit`/`#git_clone` pass this `env:` straight to `git(...)`: [5](#0-4) , and `git_clone` at [6](#0-5) .
5. `Command#unbundled_env` merges `@env` **last**, so attacker-controlled keys can override even `PATH`: [7](#0-6) .
6. `Command#start` passes this hash directly to `PTY.spawn`: [8](#0-7) .

Existing guards do not stop this: `EnvironmentVariables#permit` (the allowlist mechanism used for deploy/rollback/task-triggered `env` params) is applied only to user-submitted params in controllers such as `DeploysController#deploy_params` and never to the stack's own `env`/label-derived env: [9](#0-8) . The webhook params schema only validates `labels[].name` is a `String`, imposing no restriction on content, so any Github label a PR author adds to their own PR (`prevent_with_label` still lets non-labeled/labeled PRs create/keep an active review stack whose CI still runs `fetch`/`clone`) is captured and merged into the git process environment.

### Impact Explanation
An attacker who can open a pull request against a repository with review stacks enabled, and add a label to it, can set an environment variable name/value pair of their choosing (e.g. `DYLD_INSERT_LIBRARIES=/tmp/evil.dylib` on macOS runners, `LD_PRELOAD=...` on Linux, or `GIT_SSH_COMMAND`/`GIT_ASKPASS`/`GIT_PROXY_COMMAND` to hijack git's own transport execution) that reaches the environment of a `git fetch`/`git clone` process spawned via `PTY.spawn` on the Shipit deploy host. This is Critical — Remote Code Execution on the deploy host via `Command`/`PTY.spawn`, matching the stated Immunefi RCE impact class. It is repeatable against any repository with review stacks enabled and is not scoped to the attacker's own tenant only if the deploy host is shared across repositories/stacks — it runs with the deploy host's ambient privileges.

### Likelihood Explanation
Preconditions: the target repository must have `review_stacks_enabled` and any `provisioning_behavior` that still allows the review stack to remain active and its CI to run `fetch`/`clone` (this includes `prevent_with_label` when the PR isn't labeled with the specific provisioning-prevention label, or any label added on an unarchived stack, since `LabelCapturingHandler` captures labels regardless of the label matching the configured `provisioning_label_name`). Attacker cost is trivial — open a PR from a fork and add a label with the desired malicious env var name; no Shipit credentials, GitHub App keys, or webhook secret needed since this is normal GitHub label activity that legitimately triggers webhooks. The technique is fully repeatable and deterministic.

### Recommendation
Do not let arbitrary label strings become environment variable keys. Either (a) drop label-derived env entirely, or (b) route label-derived variables through `EnvironmentVariables#permit` with an explicit, repository-configured allowlist of permitted label-derived variable names, and reject/sanitize any label name that doesn't match a safe `^[A-Z_][A-Z0-9_]*$` pattern before using it as an env key, and never allow it to override reserved keys like `PATH`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `GIT_ASKPASS`, `GIT_PROXY_COMMAND`, etc.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_injection_test.rb
require "test_helper"

module Shipit
  class ReviewStackEnvInjectionTest < ActiveSupport::TestCase
    test "a malicious PR label reaches the git subprocess env unfiltered" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.labels = ["DYLD_INSERT_LIBRARIES=/tmp/evil.dylib".upcase, "GIT_SSH_COMMAND"]
      # simulate LabelCapturingHandler persisting attacker-chosen label names verbatim
      stack.pull_request.update!(labels: ["DYLD_INSERT_LIBRARIES", "GIT_SSH_COMMAND"])

      commands = Shipit::StackCommands.new(stack)
      command = commands.fetch

      # the equality that should NOT hold (invariant broken):
      assert_equal "true", command.env["DYLD_INSERT_LIBRARIES"]
      assert_equal "true", command.env["GIT_SSH_COMMAND"]
    end
  end
end
```
This demonstrates that `StackCommands#fetch`'s resulting `Command#env` (which feeds `PTY.spawn` via `Command#unbundled_env`) contains attacker-chosen keys sourced purely from PR label names, with no allowlist filtering applied anywhere on this path.
