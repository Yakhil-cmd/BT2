### Title
ERC20Transactor credits XCM holding with the requested amount instead of the actual token delta observed on the checking account, letting a non-standard (fee-on-transfer/deflationary) ERC20 mint unbacked XCM holding value - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` moves tokens by calling the Solidity `transfer()` function of an arbitrary ERC20 contract registered as an `AccountKey20` XCM asset (per `pr_7762`, "asset ids of the form `{parents:0, interior: X1(AccountKey20{key,...})}` will be matched by this transactor and the corresponding `transfer` function will be called in the smart contract whose address is `key`"). The transactor only decodes and checks the boolean return of `IERC20::transfer`, and — exactly like the RealityCards `topupMarketBalance` bug — never verifies that the checking account's actual balance changed by the requested `amount`. It then unconditionally credits the XCM holding register with `Erc20Credit(amount)`, the *requested* amount, not the *observed* delta.

### Finding Description
In `withdraw_asset_with_surplus` (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:150-216`):
```
let data = IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
let ContractResult { result, .. } = pallet_revive::Pallet::<T>::bare_call(..., asset_id, ..., data, ...);
...
if is_success {
    Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
}
``` [1](#0-0) 

The only check performed is `return_value.did_revert()` and decoding `transferCall::abi_decode_returns_validate` into a bool `is_success`. There is no read of `balanceOf(checking_address)` before/after the call to confirm `amount` tokens actually landed in the checking account. The requested `amount` (attacker-controlled: it comes from the `Asset` value in the XCM program the user submits) is trusted blindly and stuffed into the `Erc20Credit` imbalance, which becomes part of the XCM holding register and can subsequently be deposited to any destination (local account, reserve-transferred out, teleported, swapped in asset-conversion, etc.) via ordinary XCM instructions.

This mirrors the RealityCards root cause precisely: `erc20.transferFrom(...)` is called and the code trusts a boolean/success indicator to represent "exactly `amount` was moved," while ERC20-compatible tokens are free to:
- charge a transfer fee (deflationary/fee-on-transfer tokens) and still return `true`,
- be rebasing (balance changes are not 1:1 with `value`),
- or otherwise implement `transfer()` semantics that don't preserve `value` as the exact balance delta,

yet the caller has zero enforced standard to reject such tokens — any user with `UploadOrigin`/`InstantiateOrigin` permission (per `pallet_revive::Config` in this runtime, `EnsureSigned<Self::AccountId>`; see `substrate/bin/node/runtime/src/lib.rs:1575-1576`) can deploy an arbitrary contract implementing `IERC20` and use it as the `key` in an `AccountKey20` XCM asset location — this is an ordinary, permissionless, signed-extrinsic action (contract deploy via `pallet_revive::instantiate`), not a privileged path.

`deposit_asset_with_surplus` has the mirror-image issue (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:225-306`): it transfers `amount` from the checking account to the beneficiary and, on `Ok(true)`, simply returns success without validating the beneficiary's actual received balance [2](#0-1) . So the "amount consumed from holding" and "amount actually delivered" can diverge on both sides of the transactor.

### Impact Explanation
If the underlying ERC20 contract deducts a fee/burns on transfer (a well-known, common, non-malicious pattern for many real tokens, and trivially implementable by an attacker-deployed contract), then:
1. On withdraw: the checking account receives `amount - fee` real tokens, but XCM holding is credited the full `amount`.
2. That inflated holding amount can be deposited to an arbitrary account (or teleported/reserve-transferred elsewhere in the same XCM program), meaning the user effectively "mints" extra spendable XCM-asset value that is not backed by real tokens held in the checking account.
3. Repeated execution drains the checking account's real balance faster than the recorded/credited amounts, eventually causing `deposit_asset_with_surplus` (or any other consumer relying on the checking account actually holding what was credited) to fail when it tries to move out `amount` that the checking account no longer has — an analogous "lock up" via unbalanced books, in addition to the more severe issue of unbacked value creation that other users' funds could be drained against.

This is a value-integrity ("unbacked issuance"/theft-adjacent) bug rather than a mere availability bug, since attacker-controlled `amount` inflation directly benefits the attacker in subsequent XCM instructions within the same message.

### Likelihood Explanation
- No privileged role is required: any signed account can deploy an ERC20-like contract via `pallet_revive` (`UploadOrigin`/`InstantiateOrigin = EnsureSigned<AccountId>`), and any signed account can submit XCM `WithdrawAsset`/`DepositAsset` programs referencing that contract's address as an `AccountKey20` asset id, matched by `ERC20Transactor`'s `Matcher: MatchesFungibles<H160, u128>`.
- The only friction is that the attacker must author the malicious/fee-charging ERC20 contract themselves — but this requires no chain-level privilege and no third-party cooperation, consistent with the RealityCards report's "malicious actor, no privileged role" precondition.
- Deployment of `ERC20Transactor` in a live runtime (e.g., asset-hub-westend) needs to be confirmed to fully assess reachability in a specific production runtime's `XcmConfig::AssetTransactors` tuple; grepping `asset-hub-westend/src/xcm_config.rs` showed 4 references to `ERC20Transactor`/`TransfersCheckingAccount`, and `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` contains 5 references, indicating it is wired and tested, but I was not able to fully read the exact `AssetTransactors` composition/ordering within the remaining iteration budget to prove it is on the live/default execution path for arbitrary user-registered ERC20 tokens versus only a curated allow-list of ERC20s. This gap should be closed before treating this as bounty-final: check whether asset registration for ERC20 XCM assets is gated (e.g., requiring governance/foreign-asset registration) rather than fully permissionless.

### Recommendation
1. After the `transfer()` call succeeds (returns `true` and doesn't revert), read `balanceOf` of the checking account (or beneficiary) before and after the call and use the **actual observed delta** as the credited/consumed `Erc20Credit` amount, not the requested `amount`.
2. Alternatively/additionally, maintain an allow-list of ERC20 contracts vetted to be standards-compliant (no fee-on-transfer, no rebasing) before permitting them to be used as XCM-transactable assets, mirroring the RealityCards fix recommendation of using an allow-list plus `SafeERC20`-style handling.
3. Consider rejecting registration of `AccountKey20` XCM assets pointing at contracts that don't pass a "transfer preserves exact value" runtime check at registration time.

### Proof of Concept
I was not able to execute a runtime integration test in this environment (no code execution tools available in ask-only mode). A concrete reproduction would:
1. Deploy a minimal `IERC20`-implementing `pallet_revive` contract whose `transfer(to, value)` moves `value - fee` tokens to `to` (burning `fee`) but still returns `true`.
2. Register this contract's `H160` address as an `AccountKey20` interior location and configure it to be matched by `ERC20Transactor`'s `Matcher`.
3. Submit a signed XCM program (`WithdrawAsset` referencing this asset with `amount = X`, then `DepositAsset` to a second account) through `PolkadotXcm::execute` or equivalent.
4. Assert: `IERC20::balanceOf(TransfersCheckingAccount)` increased by `X - fee` (less than `X`), while the XCM holding register (and subsequent deposit) reflects a full `X` credit — demonstrating unbacked accounting.
This was not run; the guard failure (missing actual-balance verification) is established purely from static code reading of `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, and the runtime-wiring question (whether ERC20 registration is permissionless on a live Parity-bounty-eligible chain) remains unverified within my remaining budget.
