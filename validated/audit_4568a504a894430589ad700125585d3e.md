### Title
Unscoped `status` webhook cross-repository commit poisoning marks victim commit deployable - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare `sha` with no repository/stack scoping and applies the attacker-supplied GitHub status to every matching `Commit` row across all repositories. Since git commit SHAs are content-addressed and identical commits are routinely shared across forks/mirrors, an attacker who owns any repository sharing a commit with a victim stack can drive that commit's CI state and `deployable?` status on the victim's stack.

### Finding Description
The broken binding: the handler assumes `Commit.sha == params.sha` implies `Commit.stack.repository == event.repository`, but no such check exists. [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with zero filtering by the `repository` field of the incoming GitHub payload. `create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)` and recomputes the commit's `status`, which is used directly by `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`). [2](#0-1) [3](#0-2) 

The controller-level `verify_signature` only ties the request to *an organization's* registered GitHub App secret via `repository_owner` — it never confirms the payload's `repository.full_name` matches the commit's owning stack: [4](#0-3) 

Exploit flow: an attacker who owns/controls any repository under an org where a Shipit-connected GitHub App is installed (or their own registered org) can push a commit that is byte-identical to a commit already known to a victim stack (e.g., by forking the victim's public repo and pushing the same commit unmodified, which preserves the SHA1 since it's a pure function of tree/parents/author/committer/timestamps/message). GitHub will then deliver a legitimately-signed `status` webhook for the attacker's own repository/commit. The attacker sets `context` to exactly the required status context the victim stack lists in `ci.require` and `state: "success"`. `StatusHandler#process` matches the SHA against `Commit.where(sha: ...)` with no repo constraint, finds the victim's `Commit` row (created earlier via normal sync), and applies the status — flipping `success?` to true and potentially `deployable?` to true on the victim stack, without the victim's own CI ever running or reporting anything.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema on `sha`/`state`/`context`) validate payload shape and organization-level signature authenticity, but none of them cross-check `params.dig('repository', 'full_name')` against the `Commit`'s `stack.repository`, so the divergence is real.

### Impact Explanation
This is a payload from one repository (attacker-controlled) mutating a `Commit` record belonging to another repository's stack (victim), matching the Critical category explicitly listed in scope ("a payload for one repository mutating another's stack, commit, task or team"). Once `deployable?` is true, continuous-delivery/merge automation (`schedule_continuous_delivery`, `stack.schedule_merges`) can trigger an unauthorized deploy, rollback, or merge of the victim commit. This is repeatable against any repository that shares (or can be made to share, via fork/mirror/cherry-pick preserving identical git metadata) a commit SHA with a Shipit-tracked stack.

### Likelihood Explanation
Preconditions: the attacker needs a repository under a GitHub organization for which Shipit has a registered GitHub App/webhook secret (so `verify_signature` passes with a real, GitHub-issued signature), and needs a commit whose SHA collides with a victim's tracked commit — trivially achievable by forking a public victim repository and pushing the exact same commit (unmodified) to their own repo, then emitting/waiting for a `status` event on it with attacker-chosen `context`/`state`. No Shipit credentials, session, or API token are required. This is low-cost and repeatable.

### Recommendation
Scope commit lookup in `StatusHandler#process` (and the analogous check-run/push handlers) to commits belonging to the stack(s) whose repository matches `params.dig('repository', 'full_name')`/`repository.owner`, e.g. `Commit.joins(:stack).merge(Stack.where(repository_owner:, repository_name:)).where(sha: params.sha)`, before applying `create_status_from_github!`.

### Proof of Concept
minitest plan (no live GitHub):
1. Create `stack_a` (repository `victim/repo`) and `stack_b` (repository `attacker/repo`).
2. Create `commit = Shipit::Commit.create!(stack: stack_a, sha: SAME_SHA, ...)` and also `Shipit::Commit.create!(stack: stack_b, sha: SAME_SHA, ...)` to model the shared-SHA-across-forks scenario.
3. Configure `stack_a`'s deploy spec/`ci.require` to require context `"continuous-integration/my-ci"`.
4. Build a `status` payload: `{ sha: SAME_SHA, state: "success", context: "continuous-integration/my-ci", repository: { full_name: "attacker/repo", owner: { login: "attacker" } } }`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)` (or `process` directly bypassing controller signature verification, which is out of scope for this model-level assertion).
6. Assert: BEFORE, `stack_a`'s commit `deployable?` is `false`/`success?` is `false`. AFTER processing, assert `stack_a`'s commit (`commit.reload.deployable?`) is now `true`, proving the attacker's repository payload altered `stack_a`'s (victim) commit state despite `repository.full_name == "attacker/repo" != "victim/repo"`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
