## Finding

The `WebhooksController` selects which GitHub App / webhook secret to use for signature verification based on an **unauthenticated field of the request body itself**, and at least one handler (`StatusHandler`) writes CI status data to commits with **no scoping at all** to the repository named in that same body. Combined, these two facts let an unauthenticated attacker forge CI status (and other) events for repositories/organizations they have no relationship to, as long as *any* organization configured on the Shipit instance has an unset `webhook_secret` (an explicitly supported, documented "optional" setting).

### Finding Description

`WebhooksController#verify_signature` picks the `GitHubApp` used to check the HMAC signature purely from data inside the still-unverified JSON payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from `params.dig('repository', 'owner', 'login')` (or `organization.login`), i.e. attacker-controlled body content, *before* any signature has been validated. Shipit supports per-organization GitHub App configuration, each with its own optional `webhook_secret`: [3](#0-2) 

and `GitHubApp#verify_webhook_signature` explicitly no-ops when that organization's secret is blank: [4](#0-3) 

This "optional" secret is documented as a normal supported configuration, not a misconfiguration to be rejected: [5](#0-4) [6](#0-5) 

So, if the Shipit instance onboards even one organization without a `webhook_secret` (fully valid per the docs), `verify_webhook_signature` returns `true` unconditionally for **any** payload that merely claims `repository.owner.login` equals that organization — regardless of what repository/commit the rest of the payload actually references.

The `status` handler then acts on that unauthenticated payload with **zero repository scoping**: [7](#0-6) 

Unlike other handlers, it never calls the base `Handler#stacks`/`repository_name` helpers that scope by `payload.dig('repository', 'full_name')`: [8](#0-7) 

It simply does `Commit.where(sha: params.sha)` across the **entire database**, i.e. across every stack of every organization tracked by the Shipit instance, and writes a `Status` for whatever commit(s) match: [9](#0-8) 

**Binding broken (equality that should hold but doesn't):**
`organization whose (possibly-absent) secret authenticated the request` == `organization/repository whose commit actually receives the status write`.

Before the attacker's request: this equality trivially holds because real GitHub webhooks always carry a signature computed from the actual source organization's real (non-nil) secret.

After the attacker's forged request: the attacker chooses `repository.owner.login` = `OrgWithNoSecret` (bypassing the HMAC check entirely) while `sha` targets a commit that actually belongs to `OrgVictim`'s stack — a completely unrelated organization/repository that the attacker has no GitHub credentials for.

### Impact Explanation

A forged `success` status is consumed by:
- `MergeRequest#all_status_checks_passed?` → `ProcessMergeRequestsJob#merge!`, which calls `stack.github_api.merge_pull_request(...)` and actually merges a pull request on GitHub using Shipit's real (legitimate) GitHub App credentials for the victim org: [10](#0-9) 
- `Status#schedule_continuous_delivery`, which can trigger an unwanted/unauthorized deploy for continuous-deployment-enabled stacks.

This means an attacker, with no Shipit account, no `ApiClient` token, and no GitHub credentials, can cause an **unauthorized merge** (and potentially an unauthorized deploy) in a repository/organization completely unrelated to the org whose secret they abused, purely by exploiting the fact that signature verification and repository-scoping use two different, independently-forgeable fields of the same unauthenticated payload.

### Likelihood Explanation

Requires only that one organization configured on the instance uses no `webhook_secret` (explicitly presented as a supported/optional configuration in the docs and example secrets file), and that the attacker knows a target commit SHA of the victim stack (commonly public on GitHub, or previously observed via Shipit's own UI/API). No authentication, session, or GitHub access is required — the request is a plain unauthenticated POST to `/webhooks`.

### Recommendation

- Verify the webhook signature using the secret associated with the organization that actually owns the resource being modified, not a value taken from the unverified request body, and reject events entirely once an org has no secret configured rather than silently accepting them (`return true unless webhook_secret` should instead cause the request to be rejected or logged as insecure).
- Make `StatusHandler#process` (and any handler that doesn't already do so) scope its `Commit`/`Stack` lookups by `repository_name`/`stacks` derived from the same trust-verified organization, consistent with the base `Handler` class, instead of a bare global `Commit.where(sha: ...)`.

### Proof of Concept

1. Shipit instance configured with two orgs, e.g. `OrgAttacker` (no `webhook_secret` set) and `OrgVictim` (real webhook secret, unknown to attacker), each with a tracked stack/repository.
2. Attacker finds a real commit SHA `S` that exists in `OrgVictim`'s tracked branch history (e.g., from GitHub's public commit history) and note its stack allows CI-gated merges/deploys.
3. Attacker sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=anything

{
  "repository": {"owner": {"login": "OrgAttacker"}},
  "sha": "S",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `verify_signature` calls `Shipit.github(organization: "OrgAttacker")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally — the forged signature is accepted.
5. `StatusHandler#process` runs `Commit.where(sha: "S")`, finds the commit belonging to `OrgVictim`'s stack, and creates a `success` `Status` on it.
6. If a pull request in `OrgVictim`'s merge queue was only blocked by this missing/failing check, `ProcessMergeRequestsJob` merges it via the real GitHub API on the next run — an unauthorized merge performed with no credentials belonging to `OrgVictim` or GitHub at all.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
