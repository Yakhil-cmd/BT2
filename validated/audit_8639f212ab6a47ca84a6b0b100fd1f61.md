In `indivisible_asset.js`, `validatePrivatePayment()` sets `objValidationState.src_coin` for a private, fixed-denomination-asset transfer input directly from attacker-controlled fields of a private payment element sent by a counterparty: [1](#0-0)

### Title
Reachable unguarded `throw` on malformed private-payment `src_coin` causes node crash / DoS - (File: validation.js)

### Summary
A malicious private-payment counterparty (a device that a wallet exchanges private payments with) can craft a private-payment chain for a private, fixed-denomination asset whose "previous" element's revealed output is malformed in a way that is accepted by earlier lightweight checks in `indivisible_asset.js` but fails one of the four hard invariants asserted with `throw Error(...)` in `validation.js:2416-2424` (`no src_coin`, `no src_output`, `no denomination in src coin`, `no src coin amount`). This is directly analogous to CVE-2021-23191: the receiving code assumes a value (there, a decoded JPEG pointer; here, `src_output`/`denomination`/`amount` inside `objValidationState.src_coin`) is always well-formed, and dereferences/uses it without a defensive check, producing an unhandled runtime error instead of a graceful validation failure.

### Finding Description
`validatePrivatePayment()` in `indivisible_asset.js` builds `objValidationState.src_coin` from the previous private-payment element supplied by the sending peer:
```
objValidationState.src_coin = {
    src_output: src_output,
    denomination: payload.denomination,
    amount: prev_hidden_output.amount
};
```
`src_output` comes from `objPrevPrivateElement.output` and is only checked for having a truthy `.blinding` field [3](#0-2) . `prev_hidden_output.amount` comes from `objPrevPrivateElement.payload.outputs[input.output_index]`, which is only checked for existence (`!prev_hidden_output`), not for its `amount` being a positive integer [4](#0-3) . `payload.denomination` is taken from the current element's payload with no positivity check at this point.

This same `objValidationState` object is later passed into the shared payment-validation routine `validatePaymentInputsAndOutputs()`, where the "transfer" input branch for `objAsset.is_private && objAsset.fixed_denominations` reads back `src_coin` and enforces the same invariants — but by `throw`ing bare JS `Error` objects rather than calling `cb(errorString)`:
```
if (!objValidationState.src_coin)
    throw Error("no src_coin");
var src_coin = objValidationState.src_coin;
if (!src_coin.src_output)
    throw Error("no src_output");
if (!isPositiveInteger(src_coin.denomination))
    throw Error("no denomination in src coin");
if (!isPositiveInteger(src_coin.amount))
    throw Error("no src coin amount");
```
Because this code runs inside an asynchronous callback chain (triggered from `network.js`'s handling of an incoming private payment / private chain, ultimately from `handleOnlinePrivatePayment` → `privatePayment.validateAndSavePrivatePaymentChain` → `indivisible_asset.js` → `validation.validatePayment` → `validatePaymentInputsAndOutputs`), a thrown exception here is not caught by any `try/catch` in the call chain shown in these files — unlike other error paths in the same function that are wrapped in `try { … } catch(e) { return cb(...) }` (e.g., the payload-hash and payload-commission checks in `validate()` at [5](#0-4) ). An uncaught exception thrown from inside an async callback bubbles up to Node's `process.on('uncaughtException')` handler, which in this codebase deliberately re-throws to crash the process "to avoid ending up in an inconsistent state": [6](#0-5) 

So a value that should trigger a normal, recoverable validation-error response instead crashes the entire node process — the same root-cause pattern as CVE-2021-23191 (an unchecked/absent value dereferenced deep in processing logic, causing an unhandled fault instead of controlled error handling).

### Impact Explanation
Any wallet/device that engages in private-payment exchange with an attacker (a normal, expected interaction for private-asset payments) can be sent a crafted private-payment chain that reaches this code path and crashes the receiving node process. Because the process is intentionally re-thrown to terminate on uncaught exceptions, this is a denial-of-service against the victim's wallet/full node: it stops processing/confirming any further units until manually restarted, satisfying the "network unable to confirm new units" impact bar for that node. If a hub or witness process reaches this same shared validation code while relaying/handling private payments, the crash could propagate more broadly, degrading network availability for the affected node.

### Likelihood Explanation
The reachable path requires: (1) a private, fixed-denomination asset with a multi-hop private payment chain (an ordinary usage pattern, not requiring special privileges), and (2) crafting one link's revealed output/payload so it satisfies the loose checks in `indivisible_asset.js` (non-null `output`, non-null `blinding`, existing `outputs[output_index]` element) while still leaving `denomination`/`amount` non-positive-integer or `src_output` falsy by the time `validatePaymentInputsAndOutputs()` re-checks it. This is plausible because the two functions apply different, non-identical sets of checks to the same data, and the second function's checks are written as unconditional `throw`s rather than `cb()` error returns — a clear sign these are "should never happen" assertions rather than validated-input guards. Exploitability depends on the exact interplay between the two validation layers, which I could not fully trace end-to-end (e.g., whether `payload.denomination` is independently validated to be a positive integer earlier in `validateDivisiblePrivatePayment`/`validatePrivatePayment` for all code paths) — this is a source of uncertainty in confirming an exact minimal PoC, but the two "no source*" throws immediately following an `!objValidationState.src_coin` check are asserted without any caller-side try/catch visible in these files.

### Recommendation
Replace the bare `throw Error(...)` statements at `validation.js:2416-2424` (and the similarly-styled unguarded throws at lines 2451 and 2458 for the public-payment lookup path) with calls to `cb(...)`/`callback(...)` that report a normal validation error, consistent with the rest of the function. Additionally, tighten the checks in `indivisible_asset.js`'s `validatePrivatePayment()` so that `prev_hidden_output.amount` and `payload.denomination` are validated as positive integers, and `src_output.address` is validated as a well-formed address, before they are ever placed into `objValidationState.src_coin`, so that malformed private-chain data is rejected early with a controlled error rather than deferred to an assertion-style `throw` deep in shared validation logic.

### Proof of Concept
I could not build a fully verified, minimal PoC payload within the scope of this static analysis, because doing so requires tracing every validation branch in `indivisible_asset.js`/`divisible_asset.js` that populates or checks `payload.denomination` and `prev_hidden_output.amount` prior to reaching `validation.js:2416-2424`, across multiple files, to confirm no earlier check rejects the malformed value. Conceptually, the PoC would be: as a private-payment counterparty, send a multi-link private-payment chain for a private fixed-denomination asset where the non-head element's `output.address`/`blinding` are present (passing the `indivisible_asset.js` check) but the corresponding `payload.outputs[output_index].amount` is `0` or non-integer, or `payload.denomination` is `0`/absent, then have the recipient wallet process this chain via `handlePrivatePaymentChains` → `validateAndSavePrivatePaymentChain` → `validation.validatePaymentInputsAndOutputs`, triggering the `throw Error("no denomination in src coin")` / `throw Error("no src coin amount")` and crashing the recipient's node process via the `uncaughtException` handler in `network.js`.
