### Title
Missing audience/context binding in `is_valid_signed_package()` allows cross-context replay of signed packages between AAs - ([File: formula/evaluation.js])

### Summary
CVE-2018-6873 describes Auth0 accepting a JWT without validating its `aud` (audience) claim, so a token issued for one service could be replayed against another, causing privilege escalation. The `oscript`/AA analog is `is_valid_signed_package()`, which checks only that a `signed_message` blob is cryptographically signed by a given address, but the cryptographic hash that is actually signed — `getSignedPackageHashToSign()` — never binds the package to the AA (the "audience") that will consume it. If two AAs accept structurally similar signed packages from the same signer address, a package legitimately produced for AA A can be replayed against AA B, exactly analogous to a JWT missing its `aud` check.

### Finding Description
`is_valid_signed_package(signed_package, address)` is implemented in [1](#0-0)  . It:
1. Evaluates the target `address` (the expected signer) and the `signed_package` object.
2. Validates structural/version fields and, if present, that `last_ball_unit` is stable.
3. Calls `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)`.

`validateSignedMessage` in [2](#0-1)  checks that one of the `authors` matches `address`, resolves/validates that author's address definition, and validates the authentifiers/signature against `objectHash.getSignedPackageHashToSign(objSignedMessage)` [3](#0-2) . The hash-to-sign is derived purely from the `signed_message` payload, `authors`, `last_ball_unit`, `timestamp` and `version` fields of the package itself — there is no field, parameter, or check anywhere in this call chain that binds the signature to the identity of the AA (the "audience") that is asking `is_valid_signed_package` to validate it.

Contrast this with JWT: the token has a payload (`signed_message` here) and a signature, but nothing equivalent to an `aud` claim tying the token to the specific relying party. Whether the token/package is "valid for this context" is left entirely to the *content* of the signed message (`signed_message.some_id`), which is optional application logic the AA author must manually design (e.g., typically embedding an order id derived from `sha256(...)` inside the AA's own oscript, as done in `test/samples/order_book_exchange.oscript`). Nothing in `ocore` enforces or even encourages a mandatory scoping to a specific `address` (target AA) or "purpose"; the function's own name and 2nd argument (`address`) only identify the *signer*, not the *intended recipient/consumer* of the signature.

Because `is_valid_signed_package` is a general-purpose primitive exposed to every AA author (`formula/validation.js` lines 815-826, `formula/grammars/oscript.ne` line 399), any AA whose accept-logic checks `is_valid_signed_package(trigger.data.pkg, some_address)` and then trusts the embedded `signed_message` fields as authorization for a state-changing action (transfer, withdrawal, order execution, etc.) is vulnerable to cross-context replay if two AAs (or two code paths within one AA) happen to accept semantically overlapping `signed_message` shapes signed by the same address, since the underlying signature carries no unforgeable indication of which "audience" (AA/action/purpose) it was created for.

### Impact Explanation
An attacker who obtains one valid signed package (e.g., a price-quote/order signed by a market-maker's address, or an authorization signed by a user for a specific dApp/AA) can attempt to replay that identical signed package against another AA that consumes packages with a compatible schema, potentially triggering unauthorized fund transfers, unauthorized order execution, or AA fund loss if the target AA does not itself embed a strict, application-specific scoping field. Because this is a systemic design gap in the primitive rather than a bug fixable in one AA, it is a supply-inflation/fund-loss risk category (concrete unauthorized spending / AA fund loss) reachable purely by a trigger sender who controls the `trigger.data` payload.

### Likelihood Explanation
Exploitability is contingent on how AA authors use the primitive; oscript documentation encourages developers to include disambiguating context (order ids, expiry, self-references) inside `signed_message`, so well-written AAs are not vulnerable. However, `ocore` itself provides no core-level enforcement, warning, or reserved fields (like a `subject`/`audience`/`aa_address` claim) to prevent this class of misuse, unlike, e.g., `is_valid_sig`. Given that `is_valid_signed_package` is a commonly used primitive across financial oscript contracts (exchange order books, payment channels — see `test/samples/order_book_exchange.oscript` and `test/samples/payment_channels.oscript`), the likelihood of at least one deployed AA omitting sufficiently strict scoping is non-trivial, and any single mistake yields a critical, fund-affecting bug for the affected AA.

### Recommendation
- Add an optional/mandatory "audience" concept to the signed package format validated by `getSignedPackageHashToSign`/`validateSignedMessage`, e.g. allow (and, in a future protocol version, require) an `aa_address`/`app`/`purpose` field to be included inside the hashed payload so a signature is cryptographically bound to a specific consumer AA and cannot be replayed elsewhere.
- Update `formula/evaluation.js`'s `is_valid_signed_package` handling to optionally accept and compare this audience field against `trigger.address`/the executing AA's own address (`this_address`) transparently, matching the same semantics as `aud` validation in JWT libraries.
- Document explicitly in oscript/AA developer guidance that `signed_message` MUST embed context uniquely tying it to the specific AA/action, and add lint/audit tooling flags for `is_valid_signed_package` usage lacking such binding.

### Proof of Concept
Conceptual PoC (cannot be fully executed without live AAs, but demonstrates the reachable path):
1. AA-A and AA-B both expose oscript logic:
   ```
   if (!is_valid_signed_package(trigger.data.order, trigger.data.order.signed_message.address))
       bounce("bad signature");
   // ... use trigger.data.order.signed_message.amount / asset to move funds
   ```
2. A market maker signs an order package intended only for AA-A: `{signed_message: {sell_asset:X, buy_asset:Y, amount:100, price:1}, authors:[{address: MM_ADDR, ...}]}`.
3. Attacker captures this valid signed package (it is public, since it must be posted in a unit's trigger data to be used).
4. Attacker submits the *same* signed package as `trigger.data.order` to AA-B, which has a compatible schema and independently calls `is_valid_signed_package(trigger.data.order, MM_ADDR)`.
5. `validateSignedMessage` succeeds (the signature is valid over the unchanged `signed_message`), and AA-B executes trades/transfers based on the market maker's package even though it was never intended for AA-B — the "aud" (target AA) was never part of what was verified. [1](#0-0) [4](#0-3)
