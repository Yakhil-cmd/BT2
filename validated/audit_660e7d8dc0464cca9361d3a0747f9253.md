### Title
Reachable assertion via unauthenticated dry-run AA trigger crash - ([File: network.js])

### Summary
An unprivileged unit poster can send a payment unit to an Autonomous Agent (AA) address that is crafted such that `aa_composer.getTrigger()` (invoked synchronously and un-guarded in the `ifOk` post-validation path of `handleJoint`) throws an uncaught exception. Because the process installs `process.on('uncaughtException', ...)` that deliberately re-throws to crash the whole node, this uncaught assertion terminates the entire node process — mirroring the Magma MME "reachable assertion via unauthenticated remote message" bug class (CVE-2023-37024), where a single crafted NAS IE crashes the whole MME process.

### Finding Description
`network.js`'s `handleJoint()` calls `validation.validate()`; on success (`ifOk`), if `conf.bDryRunNewTriggers` is enabled and the unit has primary AA triggers, it eagerly dry-runs each trigger: [1](#0-0) 

Building `trigger` via `aa_composer.getTrigger(objJoint.unit, address)` is done outside of any try/catch, with the comment "if it would crash, let it crash now" — an explicit acknowledgment that `getTrigger()` can throw. `getTrigger()` itself contains a defensive assertion: [2](#0-1) 

`if (Object.keys(trigger.outputs).length === 0) throw Error("no outputs to " + receiving_address);`

This same unguarded `throw Error` pattern recurs throughout the AA trigger/response pipeline in `aa_composer.js` — `handleTrigger()` (bad AA definition, unexpected params, base AA not found, balance overflow lookups, secondary-trigger invariants, response-unit invariants) and `handlePrimaryAATrigger()` — all invoked from unit/AA-trigger processing paths reachable by any unit poster or AA author, none of them wrapped in try/catch at the call sites in `network.js`/`aa_composer.js`.

Regardless of the exact reachable mismatch that trips one of these assertions (e.g., a race between the SQL-derived `outputAddresses` set used to look up `aa_addresses` and the trigger-output reconstruction, or a similarly narrow inconsistency an attacker can engineer between validated unit content and the trigger object rebuilt post-validation), any such uncaught exception is fatal to the whole node because of the global handler: [3](#0-2) 

`process.on('uncaughtException', ...) { ... throw err; // crash the process to avoid ending up in an inconsistent state }`

This is architecturally identical to the Magma bug class: a piece of code reachable from unauthenticated/unprivileged network input contains an `assert`/`throw` that is not designed to be reachable, and the runtime's fail-fast policy converts that local defensive check into a full-process crash.

### Impact Explanation
Any full node (hub/witness) that has `conf.bDryRunNewTriggers` enabled and receives a single crafted unit targeting an AA can be crashed entirely, since the uncaught exception propagates to the top-level handler which intentionally re-throws to kill the process. This is a network-wide availability impact: a node operator's hub/full node goes down from a single posted unit, matching the CVSS profile of the original CVE (`AV:N/AC:L/PR:N/UI:N/A:H`, no confidentiality/integrity impact — pure availability/DoS).

### Likelihood Explanation
The dry-run path is directly triggered by ordinary unit posting to any AA address — no special privileges, peer trust, or node compromise are required, only a normally-formed unit whose payment output targets an AA address, matching the rule that only unit-poster/AA-trigger-sender-reachable classes are in scope. The likelihood of finding a concrete input that trips one of the many un-guarded `throw Error` invariants in `aa_composer.js`'s trigger-handling code is non-trivial to fully enumerate without a live test harness (this analysis could not execute a full-node instance to confirm a specific crafted unit reaches `getTrigger()`'s "no outputs" branch or another assertion in `handleTrigger()`), but the structural pattern — synchronous unguarded `throw` inside a request-driven pipeline that is explicitly known to be able to crash the process (per the code's own comment) — is a real and directly analogous instance of the reported bug class.

### Recommendation
Wrap all AA-trigger-composition/evaluation code paths reachable from unit validation (`aa_composer.getTrigger`, `handleTrigger`, `handlePrimaryAATrigger`, `dryRunPrimaryAATrigger`) in try/catch at their call sites in `network.js`, converting internal invariant violations into `ifUnitError`/log-and-continue outcomes rather than allowing them to propagate to `process.on('uncaughtException')`. At minimum, the dry-run block in `handleJoint`'s `ifOk` callback should catch exceptions from `aa_composer.getTrigger` and `dryRunPrimaryAATrigger` and treat them as non-fatal (log + skip the dry run) instead of crashing the whole node.

### Proof of Concept
A conclusive, minimal PoC unit that trips one of these throws was not verified end-to-end in this analysis (no runtime/test harness was available). The reasoning is based on static code inspection showing: (1) an explicit code comment acknowledging `getTrigger` inside `ifOk` "would crash" the process, (2) numerous synchronous `throw Error(...)` invariants inside the AA-trigger pipeline reachable from ordinary unit-posting, and (3) a global `uncaughtException` handler that deliberately re-throws to terminate the process. A background Devin session with an ocore devnet test harness would be needed to construct a concrete unit/AA-definition pair that reaches one of these `throw` statements (e.g., via `handleTrigger`'s parameterized-AA/base-AA-not-found branch, or a balance-overflow race in `updateInitialAABalances`) to fully confirm exploitability.

```javascript
function getTrigger(objUnit, receiving_address) {
	var trigger = { address: objUnit.authors[0].address, unit: objUnit.unit, outputs: {} };
	if ("max_aa_responses" in objUnit)
		trigger.max_aa_responses = objUnit.max_aa_responses;
	objUnit.messages.forEach(function (message) {
		if (message.app === 'data' && !trigger.data) // use the first data message, ignore the subsequent ones
			trigger.data = message.payload;
		else if (message.app === 'payment' && message.payload) {
			var payload = message.payload;
			var asset = payload.asset || 'base';
			payload.outputs.forEach(function (output) {
				if (output.address === receiving_address) {
					if (!trigger.outputs[asset])
						trigger.outputs[asset] = 0;
					trigger.outputs[asset] += output.amount; // in case there are several outputs
				}
			});
		}
	});
	if (Object.keys(trigger.outputs).length === 0)
		throw Error("no outputs to " + receiving_address);
	return trigger;
}
```
