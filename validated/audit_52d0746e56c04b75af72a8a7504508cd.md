### Title
Route-selected contract can add arbitrary token transfers to the caller’s authorization tree and steal wallet assets - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy entrypoints accept caller-supplied route bytes and invoke the configured router after authorizing only one exact input-token transfer, but a malicious pool or token selected by the route can execute third-party code beneath the caller’s authorization and add transfers of unrelated wallet tokens. If the victim signs the authorization tree produced for that route, the malicious transfer is authorized and can steal assets that were never supplied to the protocol. This is the XOXNO analogue of arbitrary calldata execution: the route controls external code execution while the account owner’s authorization context remains active.

### Finding Description
`swap_collateral` accepts `caller`, `account_id`, `current`, `amount`, `new`, and arbitrary `swap` bytes, authenticates the caller, and forwards the route through `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1) 

The shared strategy helper obtains the configured router, authorizes one exact transfer from the controller to that router, executes `router.execute_strategy(controller, amount_in, swap)`, and then checks only measured router input/output deltas. [3](#0-2) 

The route payload is not an allowlisted function signature: its address registry supplies venue, pool, and token addresses used by the instruction stream. [4](#0-3) 

An Aquarius hop invokes the route-selected pool’s `swap` function, and a Soroswap hop likewise invokes the route-selected pool after reading its reported reserves. [5](#0-4) [6](#0-5) 

Because route venues and token addresses are not allowlisted, that invoked contract can call `token.transfer(victim, attacker, amount)`; Soroban records this as a child invocation beneath the victim’s strategy authorization, and the transfer succeeds if the victim signs the resulting tree. [7](#0-6) [8](#0-7) 

The regression test demonstrates this by routing a `swap_collateral` call through a malicious pool that transfers Alice’s unrelated wallet token to the attacker while still returning a valid swap output. [9](#0-8) [10](#0-9) 

### Impact Explanation
A malicious route can steal tokens from the victim’s wallet that are unrelated to the lending position, while preserving enough measured swap output for the controller strategy to pass its settlement and risk checks. [7](#0-6) 

The same arbitrary child authorization applies to every route-bearing controller operation, including `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`. [11](#0-10) 

This is direct theft of user funds rather than merely poor route execution, because the malicious child call can target an unrelated token balance held by the caller. [12](#0-11) 

### Likelihood Explanation
The attacker only needs to persuade a user or integrating client to submit a route that references attacker-controlled pool or token code; no protocol privilege, leaked key, upgrade, or special account state is required. [13](#0-12) 

The exploit does depend on the victim signing the authorization tree containing the malicious transfer, so wallets or clients that explicitly reject unexpected child invocations prevent the theft. [14](#0-13) 

Nevertheless, ordinary simulation presents the malicious transfer as part of the authorization tree for the requested strategy, and the test confirms that signing that tree executes the theft. [15](#0-14) [16](#0-15) 

### Recommendation
Restrict strategy routes to a governance-approved registry of venue, pool, router, and token contracts instead of trusting arbitrary addresses embedded in route bytes. [17](#0-16) 

Controller-side settlement should also reject any route that attempts to spend account-owner assets other than the exact configured input transfer, and clients should fail closed when a simulated authorization tree contains any child invocation beyond the expected route transfer graph. [18](#0-17) [19](#0-18) 

If arbitrary venue contracts must remain supported, surface an explicit high-risk warning and require an allowlist or capability-bound route signed by governance before using them through account-owner strategies. [7](#0-6) 

### Proof of Concept
The existing adversarial test deploys a router double and a route-selected `RogueHopPool`; the pool stores `(victim, wallet_token, attacker, amount)` and calls `wallet_token.transfer(victim, attacker, amount)` during `swap`. [20](#0-19) [8](#0-7) 

The test then calls `swap_collateral(Alice, account_id, USDC, SWAP_IN_USDC, ETH, malicious_route)`. [10](#0-9) 

In recording mode, the wallet-token transfer appears as a child under Alice’s `swap_collateral` authorization, and executing the recorded route drains `WALLET_BALANCE` to the attacker while crediting the expected ETH output. [21](#0-20) 

A minimal exploitation sequence is:

```rust
// Attacker deploys a malicious venue/pool:
fn swap(env: Env) {
    token::Client::new(&env, &victim_wallet_token)
        .transfer(&victim, &attacker, &wallet_balance);
}

// Victim calls the controller strategy with attacker-supplied route bytes:
controller.swap_collateral(
    victim,
    account_id,
    usdc_key,
    swap_in_usdc,
    eth_key,
    route_naming_malicious_pool,
);

// During execution, the router invokes:
env.invoke_contract(&malicious_pool, &symbol_short!("swap"), args);

// Simulation records a child under the victim's strategy auth:
wallet_token.transfer(victim, attacker, wallet_balance);

// If the victim signs that returned tree, the malicious transfer succeeds.
```

The enforced-auth test confirms the failure case and exploit case: an honest root-only authorization rejects the malicious child transfer, while the simulated poisoned tree authorizes it and reduces Alice’s wallet balance to zero. [22](#0-21)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
