### Title
Ambiguous (non-length-prefixed) concatenation of variable-length `title`/`text` fields in `getHash`/`getHashSrc` allows contract-hash collisions, enabling on-chain contract substitution - (File: `prosaic_contract.js`, `arbiter_contract.js`)

### Summary
`prosaic_contract.js` and `arbiter_contract.js` compute a contract's unique identifying `hash` by concatenating variable-length, attacker/user-controlled strings (`title`, `text`, `creation_date`, party names, addresses, amount, asset) and hashing the resulting string with SHA-256. Because the concatenation uses either no separator at all, or a fixed, guessable delimiter that is not excluded from the field contents, two semantically different contracts can be crafted to produce the exact same `hash`. This is the same bug class as the reported EIP-712 issue: dynamic-length values must be unambiguously encoded (e.g., by hashing each field or length-prefixing) before being combined into a single digest; naive string concatenation is not injective and permits collisions.

### Finding Description
In `prosaic_contract.js`: [1](#0-0) 
`getHash`/`getHashV1` hash `contract.title + contract.text + contract.creation_date` with **no separator whatsoever**. Any pair of `(title, text)` values whose concatenation `title||text` is identical will yield an identical hash regardless of where the boundary between title and text actually is (e.g. `title="AB", text="C"` vs `title="A", text="BC"` both produce `"ABC"`).

In `arbiter_contract.js`: [2](#0-1) 
`getHashSrc` joins the same kind of free-text fields using `exports.DELIMITER = "[|#|]"`: [3](#0-2) 
Because `title`/`text` are unrestricted natural-language strings, nothing prevents them from containing the literal delimiter sequence `[|#|]`. Consequently, the same collision technique applies: `title="A[|#|]B", text="C"` and `title="A", text="B[|#|]C"` produce the identical joined string and therefore the identical `hash`, even in the "new" (post `NEW_HASH_DATE`) hashing scheme. The legacy branch (`creation_date <= NEW_HASH_DATE`) uses no delimiter at all (`join("")`), making the collision even easier.

This `hash` is treated as an unforgeable, unique commitment to the contract's exact terms throughout the protocol:
- It is sent to the counterparty in the `*_contract_offer` message and stored as the primary key of the contract.
- It is embedded on-chain in a `data` message as `contract_text_hash`, and used to correlate the on-chain signing unit with the off-chain contract text: [4](#0-3) [5](#0-4) 
Both handlers verify `payload.contract_text_hash === contract.hash` and, on match, treat the on-chain unit as valid proof of the specific stored `title`/`text` — there is no additional check that the actual `title`/`text` strings recorded locally are the unique preimage of that hash.

### Impact Explanation
Because the hash function does not uniquely and unambiguously encode the variable-length fields, a malicious counterparty (offeror or peer) can construct two different contracts — one that looks acceptable in isolation (e.g., "pay 100 for consulting services", split at boundary X) and one with different obligations, prices, or terms (split at boundary Y) — that hash to the same value. An attacker could:
- Offer contract A, get the counterparty to review and accept/sign it (based on rendered `title`+`text`), while later presenting/storing contract B (different displayed title/text, but identical `hash`) as the "same" agreement, since every downstream check (`getByHash`, `contract_text_hash` matching, arbiter dispute resolution content) relies solely on the colliding `hash`, not on binding the exact strings.
- Because `contract.hash` is also the key used to correlate the on-chain payment/signing unit and the arbiter dispute contract content (`contract_content` sent to arbstore in `openDispute`/`appeal`), a party could dispute using different contract text than what was actually signed, changing the arbiter's read of the deal terms while the on-chain proof (`contract_text_hash`) still matches.
This results in financial/contractual ambiguity and potential fund loss/misdirection for one of the two parties to a prosaic or arbiter contract — a concrete instance of asset/fund-loss-relevant miscommitment analogous to the original EIP-712 ambiguous-encoding bug.

### Likelihood Explanation
Both `title` and `text` are attacker-controlled free text fields with no length restriction on the presence of the delimiter substring, and no field-boundary validation is performed anywhere in `createAndSend`, `store`, or `getByHash`/`getHashSrc`. Constructing a colliding pair only requires choosing two strings that concatenate identically (trivial for the no-delimiter `prosaic_contract.js` case) or embedding the delimiter substring `[|#|]` inside the `title`/`text` (also trivial) for `arbiter_contract.js`. No privileged access or race condition is needed — a single contract-offering peer can exploit this.

### Recommendation
Replace naive string concatenation with an unambiguous, collision-resistant encoding before hashing, mirroring the EIP-712 fix: hash each variable-length field independently (or length-prefix it) prior to combining, e.g.:
```js
function getHashSrc(contract) {
	...
	const parts = [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'];
	return parts.map(p => crypto.createHash("sha256").update(String(p), "utf8").digest("hex")).join('');
}
```
or use the existing `object_hash.getBase64Hash`/`getSourceString` machinery (which already length-prefixes/type-prefixes each field, see `string_utils.js` `getSourceString`) instead of manual string concatenation, for both `prosaic_contract.js`'s `getHash`/`getHashV1` and `arbiter_contract.js`'s `getHashSrc`.

### Proof of Concept
1. Party P offers a prosaic contract with `title = "Pay 100 for A"`, `text = "B"`, `creation_date = D`. `hash1 = sha256("Pay 100 for AB" + D)`.
2. Party P later claims/stores a different contract with `title = "Pay 100 for "`, `text = "AB"`, same `creation_date = D`. `hash2 = sha256("Pay 100 for AB" + D) = hash1`.
3. Both contracts pass `getByHash`/`contract_text_hash` verification since the hashes are identical, despite different displayed `title`/`text` split, allowing the counterparty to be shown one version while the on-chain/arbiter-visible record legitimately matches a differently-worded version.
4. Equivalent construction works for `arbiter_contract.js` by embedding the literal string `[|#|]` inside `title` or `text` to shift the field boundary while preserving the overall joined string and thus the `hash`.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
