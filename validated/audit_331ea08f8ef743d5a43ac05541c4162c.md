### Title
Missing `review_stacks_enabled` gate in `ReopenedHandler#unarchive?` allows unarchiving a disabled repository's review stack - ([File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb])

### Summary
`ReopenedHandler#unarchive?` has an operator-precedence bug: `review_stacks_enabled` is `&&`-bound only to the first disjunct (`provisioning_behavior_allow_all?`) instead of gating the whole expression. As a result, when a repository has `review_stacks_enabled: false` and `provisioning_behavior: prevent_with_label`, reopening a PR without the provisioning label still returns `true` from `unarchive?`, forcing the deliberately archived stack to be resurrected and re-queued for provisioning.

### Finding Description
The intended binding is: `repository.review_stacks_enabled == false` must imply `unarchive? == false` for all provisioning behaviors, i.e. an operator's decision to disable review stacks on a repository must be authoritative regardless of `provisioning_behavior` or PR labels.

The code in `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb`:

```ruby
def unarchive?
  repository.review_stacks_enabled &&
    repository.provisioning_behavior_allow_all? ||
    (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
    (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?)
end
``` [1](#0-0) 

Because `&&` has higher precedence than `||` in Ruby, this parses as:
`(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)`

`review_stacks_enabled` only gates the `allow_all?` branch. The `allow_with_label?` and `prevent_with_label?` branches evaluate independently of `review_stacks_enabled`.

`process` calls this directly with no additional gate:
```ruby
def process
  return unless respond_to_pull_request_reopened?
  stack.unarchive!
end
...
def respond_to_pull_request_reopened?
  params.action == "reopened" && unarchive?
end
``` [2](#0-1) 

This is inconsistent with the sibling handlers, which correctly require `repository.review_stacks_enabled` as a top-level `&&` term before evaluating `archive?`/`unarchive?`:
```ruby
def respond_to_label_change?
  params.action == "unlabeled" &&
    pull_request_state == "open" &&
    repository.review_stacks_enabled &&
    (archive? || unarchive?)
end
``` [3](#0-2) [4](#0-3) 

Downstream, `ReviewStackAdapter#unarchive!` performs the actual resurrection and enqueues provisioning without any additional check of `review_stacks_enabled`:
```ruby
def unarchive!(*args, &block)
  ...
  return unless stack.archived?
  stack.transaction do
    Shipit::ReviewStackProvisioningQueue.add(stack)
    stack.unarchive!(*args, &block)
  end
end
``` [5](#0-4) 

Exploit flow: with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`, an attacker (any PR author on the affected repository) simply reopens their PR (or replays the `pull_request` "reopened" webhook, which is unauthenticated in terms of session/API-token privilege — it only needs to pass signature verification, which is orthogonal to this logic bug and doesn't require attacker secrets since the webhook is genuinely emitted by GitHub when the PR is reopened) without the provisioning label attached. `unarchive?` evaluates the third disjunct `(prevent_with_label? && !has_label?)` to `true`, bypassing the operator's `review_stacks_enabled = false` setting, and the previously archived stack is unarchived and queued for re-provisioning, re-running `shipit.yml` steps for that environment.

No existing guard prevents this: `respond_to_pull_request_reopened?` only checks `unarchive?`, which contains the flawed precedence; `NullRepository` returns `false` for these predicates but is irrelevant once the `Repository` exists; there is no other check of `review_stacks_enabled` in this call path.

### Impact Explanation
This allows an attacker who controls a PR on a repository (an unprivileged role per the threat model) to force an operator-disabled review stack (`review_stacks_enabled: false`) back to life and trigger provisioning again, re-running the repository's `shipit.yml` provisioning steps for that PR's environment even though the operator explicitly turned off review-stack automation. This is a same-repository authorization bypass over an operator control (`review_stacks_enabled`), not a cross-tenant stack mutation — it does not let the attacker touch another repository's stacks. It is repeatable on any repository configured with `provisioning_behavior: prevent_with_label` and `review_stacks_enabled: false`, each time the PR is reopened.

### Likelihood Explanation
Requires: an existing archived `ReviewStack` for the PR's environment; repository configured `review_stacks_enabled: false`; `provisioning_behavior: prevent_with_label`; the PR lacking the provisioning label. All of these can be set by the repository owner (who may be the attacker if it's their own repo) or already exist as a valid, intentional configuration; the attacker's only action is reopening a PR they control. Cost is essentially zero — a normal GitHub UI action or webhook replay.

### Recommendation
Fix the operator precedence in `unarchive?` (and audit `archive?`-equivalent logic if present) in `app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb` so `review_stacks_enabled` gates the entire expression, e.g.:
```ruby
def unarchive?
  repository.review_stacks_enabled &&
    (repository.provisioning_behavior_allow_all? ||
     (repository.provisioning_behavior_allow_with_label? && pull_request_has_provisioning_label?) ||
     (repository.provisioning_behavior_prevent_with_label? && !pull_request_has_provisioning_label?))
end
```
Alternatively, move `repository.review_stacks_enabled &&` into `respond_to_pull_request_reopened?` as done in `LabeledHandler`/`UnlabeledHandler`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/pull_request/reopened_handler_test.rb`, add:
```ruby
test "does NOT unarchive stacks when review_stacks_enabled is false, even with prevent_with_label and no label" do
  stack = create_archived_stack
  repository = shipit_repositories(:shipit)
  configure_provisioning_behavior(
    repository:,
    provisioning_enabled: false,
    behavior: :prevent_with_label,
    label: "pull-requests-label"
  )
  payload = payload_parsed(:pull_request_reopened)
  payload["pull_request"]["labels"] = []

  Shipit::Webhooks::Handlers::PullRequest::ReopenedHandler.new(payload).process

  assert stack.reload.archived?, "Expected stack to remain archived because review_stacks_enabled is false"
end
```
Binding to assert before/after: `repository.review_stacks_enabled == false` must imply `stack.reload.archived? == true`. With the current code, this assertion fails (`stack.reload.archived?` becomes `false` and a `Shipit::ReviewStackProvisioningQueue` entry is created), demonstrating the bypass.
