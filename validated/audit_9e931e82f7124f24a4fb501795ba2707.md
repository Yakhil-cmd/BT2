### Title
Cross-org webhook forgery via mismatched `repository.owner.login` / `repository.full_name` fields bypasses per-org signature scoping, triggering `Stack#sync_github` with a foreign org's real `GITHUB_TOKEN` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: lib/shipit/github_app.rb])

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp` (and thus the webhook secret) to validate against using `payload['repository']['owner']['login']`, while `Handler#stacks`/`Handler#repository_name` resolves the *target* `Repository`/`Stack` using the independent, also fully attacker-controlled field `payload['repository']['full_name']`. Because these two JSON fields are never cross-checked for consistency, and `GitHubApp#verify_webhook_signature` unconditionally passes when `webhook_secret` is blank, an attacker can craft a raw POST to `/webhooks` that is "verified" against an org with no configured secret (org-A) while `full_name` names a completely different, real tenant's repository (org-B), causing org-B's real `Stack` to be synced with org-B's real `GITHUB_TOKEN`.

### Finding Description
The broken binding as an equality that the code should enforce but does not:
`payload['repository']['owner']['login']` (the org used to select the `GitHubApp`/secret for `verify_signature`) MUST equal the owner-prefix of `payload['repository']['full_name']` (the org whose `Repository`/`Stack` rows get mutated by the handler). No code enforces this equality.

- `WebhooksController#verify_signature` derives the verifying org solely from `repository_owner`, and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`: [1](#0-0) , with `repository_owner` read from the raw JSON body: [2](#0-1) .
- `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no `webhook_secret` is configured for that org, before any HMAC comparison is attempted: [3](#0-2) .
- `Handler#stacks`/`Handler#repository_name` independently reads `payload.dig('repository', 'full_name')` — a *different* key in the same attacker-supplied JSON body — to look up the actual `Repository` and its `stacks`: [4](#0-3) .
- `Repository.from_github_repo_name` finds a real, pre-existing DB row by `owner`/`name` parsed from `full_name`: [5](#0-4) , and `Repository#github_app` uses that row's own `owner` column (org-B, not the payload's `owner.login`) to fetch the token: [6](#0-5) .
- `PushHandler#process` (and the pull_request handlers) then operate on the stacks found via that mismatched `full_name`, e.g. calling `stack.sync_github`: [7](#0-6) .

Exploit flow: attacker POSTs directly to `/webhooks` (permitted per rules) with `X-Github-Event: push`, body `{"repository":{"owner":{"login":"org-a-no-secret"},"full_name":"org-b/target-repo"},"ref":"refs/heads/master","after":"<sha>"}`. `repository_owner` resolves to `org-a-no-secret`; if that org has no `webhook_secret` configured, `verify_signature` passes unconditionally regardless of signature header content. `Shipit::Webhooks.for_event('push').each { |h| h.call(params) }` then runs `PushHandler`, which resolves `stacks` via `full_name = "org-b/target-repo"`, matching org-B's real, pre-existing `Repository`/`Stack` rows, and calls `stack.sync_github`, which (per `Repository#github_app`) fetches org-B's real `GITHUB_TOKEN` via org-B's own `app_id`/`installation_id`/`private_key` and hands it to git operations. Existing guards (`drop_unhandled_event`, `ExplicitParameters` schema requiring `:ref`/`:after`, `Repository` owner/name format validators) do not check consistency between `owner.login` and `full_name`, so none of them block this divergence.

### Impact Explanation
An attacker who has never authenticated to org-B can force a real git-fetch/sync operation against org-B's actual `Stack`, using org-B's real installation-scoped `GITHUB_TOKEN`, purely by naming a different org (one lacking a configured webhook secret, or one the attacker otherwise controls signing for) in the `owner.login` field while pointing `full_name` at org-B's repo. This is a payload for one org mutating another org's stack/commits state (`sync_github` updates the stack's known commits from GitHub) and constitutes unauthorized deploy-pipeline-adjacent execution triggered by an unauthenticated cross-tenant actor — matching the Critical bucket ("a payload for one repository mutating another's stack ... or an unauthorized deploy"). It is repeatable against any registered `Repository`/`Stack` as long as an org exists somewhere in the Shipit config without a `webhook_secret` (or whose secret the attacker can otherwise satisfy), because that org name is the only thing the attacker needs to control on the "verification" side of the request.

### Likelihood Explanation
The prerequisite is that at least one configured organization in `Shipit.github_apps` config has no `webhook_secret` set (a plausible, common misconfiguration, e.g. for internal/dev orgs or orgs added without webhook security review), or that the attacker otherwise controls a valid signature for some org name (the stipulated "webhook provenance break"). Given that, the attack costs a single unauthenticated HTTP POST with no session, API token, or secret required, and is fully repeatable against any org-B repository already registered in Shipit with `full_name` known to the attacker (public repo names are trivially guessable/public).

### Recommendation
In `Handler#stacks`/`Handler#repository_name`, and in `WebhooksController#verify_signature`, require that `payload['repository']['owner']['login']` matches the owner segment of `payload['repository']['full_name']` before doing any lookup or signature check, rejecting the request (422) otherwise. Additionally, `GitHubApp#verify_webhook_signature` should not silently return `true` when `webhook_secret` is blank in production — either require a secret for every configured org or fail closed instead of open.

### Proof of Concept
Add a minitest to `test/controllers/webhooks_controller_test.rb` (no live network):
1. Configure two orgs in `Shipit.github_apps`: `org-a` with `webhook_secret: nil`, `org-b` with a real `webhook_secret` and stub/mock `GitHubApp#token` (Mocha) to return distinct sentinel tokens `"TOKEN_A"`/`"TOKEN_B"`.
2. Create a real `Shipit::Repository`/`Shipit::Stack` for `org-b/target-repo`.
3. POST to `/webhooks` with header `X-Github-Event: push`, no/garbage `X-Hub-Signature`, and body `{"repository":{"owner":{"login":"org-a"},"full_name":"org-b/target-repo"},"ref":"refs/heads/master","after":"<sha>"}`.
4. Assert the response is `200`/`:ok` (not `422`), and assert (via Mocha `expects`/`stub` on `Repository#github_app` or `GitHubApp#token`) that `Shipit.github(organization: 'org-b').token` was invoked/`sync_github` ran for the `org-b` stack — i.e. `"TOKEN_B"` was fetched — even though signature verification only ever checked against `org-a`'s (absent) secret.
5. Assert both sides of the binding: `payload['repository']['owner']['login'] ("org-a") != full_name.split('/').first ("org-b")`, proving the divergence, while the stack actually mutated/synced belongs to `org-b`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
