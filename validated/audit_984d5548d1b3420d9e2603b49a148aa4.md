### Title
Webhook trust binding mismatch: signature verified against `repository.owner.login`, but events are applied to the stack identified by `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App/webhook secret to use for HMAC verification based on an attacker-controlled field read from the *unverified* JSON body (`repository.owner.login`), while every event handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` using a *different* field from the same body: `repository.full_name`. Nothing binds the organization whose secret validated the request to the repository that is actually acted upon.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 

The organization used to select the secret comes straight from the request body before any authentication has occurred: [2](#0-1) 

The secret lookup then goes through `Shipit.github(organization:)` / `GitHubApp#verify_webhook_signature`, which silently treats a missing webhook secret as "verified": [3](#0-2) 

Meanwhile, every webhook handler determines *which repository/stack to mutate* using a completely different, equally attacker-supplied field of the same JSON body: [4](#0-3) 

For example `PushHandler` triggers a GitHub sync for the resolved stack's branch: [5](#0-4) 

and `StatusHandler` writes CI status records for the resolved commit: [6](#0-5) 

The docs confirm that Shipit is intended to be multi-tenant, with a distinct GitHub App/secret per organization, and that `webhook_secret` is explicitly **optional**: [7](#0-6) [8](#0-7) 

**The break in the trust binding:** `organization authenticated (repository.owner.login, used only to pick a secret) != repository written (repository.full_name, used by every handler to pick the Stack)`. If any organization configured in this Shipit instance has no `webhook_secret` set (an explicitly supported, documented configuration), `verify_webhook_signature` returns `true` unconditionally for a payload merely *claiming* that organization as `repository.owner.login`, regardless of the actual `repository.full_name` in the same payload. An attacker who knows the name of any such "secret-less" org (installers list, GitHub org page, `Shipit.github_organizations`, error messages, etc.) can post an unsigned/arbitrary-signed webhook body where:
- `repository.owner.login` = the secret-less organization (satisfies `verify_signature`)
- `repository.full_name` = any other, fully protected repository/stack already registered in this Shipit instance

The handler layer never re-validates that the "authenticated" organization matches the repository being acted upon, so the forged event is processed against the victim stack.

### Impact Explanation
This lets an unauthenticated attacker forge GitHub webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`, etc.) against any stack tracked by the Shipit instance, as long as one org in the multi-tenant config lacks (or is misconfigured without) a `webhook_secret`:
- `push` events force `GithubSyncJob`/`stack.sync_github` to run against arbitrary stacks.
- `status` events let the attacker fabricate arbitrary CI status records (`Commit#create_status_from_github!`) for arbitrary commits/shas on a victim stack. Since `MergeRequest#all_status_checks_passed?` and `Stack#deployable?` rely on these stored statuses for the merge queue and (where enabled) continuous deployment gating, a forged "success" status can push a commit through required-CI checks it never actually passed, contributing to an unauthorized merge or deploy.
- `check_suite` events force a refresh of check runs for arbitrary commits on arbitrary stacks.

This crosses a real authentication/authorization boundary (a GitHub identity for org B is used to unlock write actions on org A's repository/stack) and can lead to unauthorized deploy/merge, satisfying the "Critical" bucket in scope (unauthorized deploy, rollback, or merge) when combined with the merge-queue/CI-gating logic.

### Likelihood Explanation
Requires (a) the target Shipit deployment to be multi-tenant (multiple orgs configured under `github:`), and (b) at least one configured organization lacking a `webhook_secret` — both are explicitly documented as supported/optional configurations, not an operator error outside the engine's design. No GitHub App private key, `api_clients_secret`, session, or repository write access is needed by the attacker; only knowledge of the "secret-less" org's login and the victim repository's `full_name` (both are typically public information). This is a design gap in the engine's own webhook-authentication code (`WebhooksController`/`GitHubApp`), not a host-misconfiguration issue outside the engine.

### Recommendation
Bind the verified identity to the acted-upon resource:
- After computing `verified` in `verify_signature`, additionally assert that `repository_owner` (the org whose secret validated the payload) matches the owner segment of `repository.full_name` used by the handlers, rejecting the event otherwise.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for a given organization in multi-tenant mode; either require a secret for every configured org, or fail closed.
- Pass the authenticated `repository_owner` (not merely `repository.full_name`) into each `Handler` and have `Handler#stacks`/`#repository_name` verify consistency before resolving `Stack`/`Repository`.

### Proof of Concept
1. Shipit configured with two orgs: `secured-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`, per documented optional setting).
2. `secured-org/victim-repo` has an existing Stack with `continuous_deployment` or a merge queue relying on required CI statuses.
3. Attacker (no credentials) POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "open-org" }, "full_name": "secured-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "open-org")`; `verify_webhook_signature` returns `true` because `open-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-77`).
5. `StatusHandler#process` resolves the commit purely by `sha` (global lookup) and creates a fabricated "success" status for `secured-org/victim-repo`'s commit, which the merge queue / deploy gating for `secured-org` will treat as legitimate CI, regardless of the fact that the request was only ever "authenticated" as belonging to `open-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
