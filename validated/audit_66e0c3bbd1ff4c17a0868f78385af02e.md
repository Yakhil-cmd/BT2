### Title
Cross-organization webhook forgery via `repository.owner.login`/`repository.full_name` binding mismatch - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate a webhook against using `repository.owner.login` (falling back to `organization.login`) read directly from the untrusted JSON body, then verifies the HMAC signature of the *entire* raw body against that secret. Downstream webhook `Handler` subclasses (`PushHandler`, `CheckSuiteHandler`, `PullRequest::ClosedHandler`, etc.) never re-derive or check that organization — they instead resolve the target `Repository`/`Stack` purely from `repository.full_name`, a sibling field in the same attacker-authored payload. In a multi-org Shipit deployment (as documented in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`), an attacker who legitimately controls the GitHub App/webhook secret for **their own** configured organization can craft a payload with `repository.owner.login = "MyOrg"` (so it authenticates against their own known secret) but `repository.full_name = "VictimOrg/some-repo"` (so the handler acts on a stack belonging to a completely different tenant).

### Finding Description
- `verify_signature` picks the app/secret from attacker-controlled JSON before checking the signature: [1](#0-0) [2](#0-1) 

- The base `Handler` class resolves the acted-upon repository/stack from a *different* field of the same payload, with no cross-check against the organization that was used to select/verify the signing secret: [3](#0-2) 

- `PushHandler` (triggers `stack.sync_github`) and `CheckSuiteHandler` (schedules check-run refreshes) both key off this unchecked `repository_name`: [4](#0-3) [5](#0-4) 

- `PullRequest::ClosedHandler` independently re-declares its own `repository.full_name` requirement and uses it to locate the repository/review stack to archive, again with no tie-back to the organization used for signature verification: [6](#0-5) 

- `Repository.from_github_repo_name` does a simple owner/name lookup with no additional authorization check: [7](#0-6) 

The equality that should hold — but doesn't — is:
`organization used to select+verify webhook_secret (repository.owner.login / organization.login)` == `organization whose repository/stack is actually mutated (repository.full_name)`.

Because both values are attacker-supplied fields inside a single self-signed JSON body, an attacker who is a legitimate app-owner for OrgA can set `owner.login=OrgA` (to pass verification with OrgA's own secret, which the attacker legitimately possesses) and `full_name=OrgB/some-repo` (to target OrgB's stack). This is analogous to the referenced `vault-native.fc` bug: a single incoming message is trusted to carry two related-but-distinct fields (there, jetton vs native "kind"; here, "owner used for auth" vs "owner acted on"), and the code applies the action using the wrong/unverified field instead of the one that was actually authenticated.

### Impact Explanation
This breaks the multi-tenant isolation between GitHub organizations hosted on the same Shipit instance. An attacker with control of one configured organization's webhook secret can force cross-organization `sync_github` calls, check-run refresh scheduling, and PR/review-stack archival actions against stacks/repositories belonging to a different organization they do not control — i.e., unauthorized cross-repository writes/state changes, matching the "cross-repository writes" High/Critical impact category.

### Likelihood Explanation
Requires the attacker to already control (own) a GitHub App/webhook installation for at least one org configured in Shipit's multi-org `secrets.yml` — a realistic scenario for a shared/multi-tenant Shipit deployment where many teams/orgs each configure their own app entry, as shown in `config/secrets.development.shopify.yml` and `test/dummy/config/secrets_double_github_app.yml`. No Shipit session, `ApiClient` token, or GitHub App private key for the victim org is needed — only network access to POST to `/webhooks` with a body signed by the attacker's own legitimately-known secret.

### Recommendation
After verifying the HMAC signature, re-derive the organization from the same field used for signature selection (`repository.owner.login`/`organization.login`) and enforce that all repository/stack resolution in `Handler#repository_name`/subclasses is scoped to that same, already-authenticated organization (e.g., pass the verified organization into the handler and require `repository.full_name.split('/').first == verified_organization`), rejecting the webhook otherwise.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/orgs, `OrgA` (attacker-controlled) and `OrgB` (victim), each with distinct `webhook_secret`s, per the multi-org config format in `config/secrets.development.shopify.yml`.
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC(OrgA_webhook_secret, body)>` using OrgA's own known secret.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#repository_owner` returns `"OrgA"` → `verify_signature` looks up `Shipit.github(organization: "OrgA")` and successfully verifies the signature against OrgA's secret. [1](#0-0) 
6. `PushHandler#process` → `stacks` → `Handler#repository_name` returns `payload.dig('repository','full_name')` = `"OrgB/victim-repo"`, so `Repository.from_github_repo_name("OrgB/victim-repo")` resolves OrgB's real stacks, and `stack.sync_github(expected_head_sha: "deadbeef")` is invoked on OrgB's stack — an action never authorized by OrgB. [4](#0-3) [3](#0-2)
