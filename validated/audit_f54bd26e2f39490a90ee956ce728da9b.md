### Title
Cross-organization webhook forgery via mismatched authentication/action bindings when multiple GitHub Apps are configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to validate a webhook against based on `repository.owner.login` (or `organization.login`) read directly from the untrusted, not-yet-verified JSON body. The actual stack/repository that gets acted upon by the event handlers, however, is resolved independently from `repository.full_name` in the same body. These two attacker-controlled fields are never checked for consistency, so the "organization that authenticated" and the "repository that is written" are two different equality classes that this code silently assumes are always the same.

### Finding Description
`verify_signature` computes: [1](#0-0) 
`repository_owner` is derived purely from body content: [2](#0-1) 

The GitHub App used to verify the signature is looked up via `Shipit.github(organization: repository_owner)`, and `GitHubApp#verify_webhook_signature` explicitly no-ops when that organization has no configured `webhook_secret`: [3](#0-2) 
`return true unless webhook_secret` means any request — even with a missing or garbage `X-Hub-Signature` — is accepted as long as the organization picked for verification has no secret configured.

Meanwhile, every event handler resolves the target repository/stack independently, from `payload.dig('repository', 'full_name')`: [4](#0-3) 
and dispatches actions against that repository's stacks, e.g. `PushHandler`: [5](#0-4) 

In a documented multi-organization deployment (Shipit explicitly supports configuring several GitHub Apps, one per organization, each with its own `webhook_secret`), nothing prevents `repository.owner.login` (used for auth) from disagreeing with `repository.full_name` (used for the actual write). An attacker who knows that one configured organization has no `webhook_secret` set (or can otherwise defeat that organization's HMAC) can submit a webhook payload where:
- `repository.owner.login` = the organization with no/weak secret (so `verify_webhook_signature` trivially returns `true`), and
- `repository.full_name` = `"<victim-org>/<victim-repo>"` belonging to a completely different, secured organization.

The equality the code relies on but never enforces is:
`organization used to authenticate (repository.owner.login / organization.login)` == `organization whose repository/stack is actually mutated (repository.full_name)`.
This is never true by construction, and is fully attacker-controlled.

### Impact Explanation
This breaks the deployment-trust binding between "an organization that authenticated" and "the repository that is written," letting an unprivileged attacker who cannot forge the victim organization's webhook signature nonetheless inject fully-controlled webhook events against that victim's stacks:
- `push` events can trigger `GithubSyncJob`/`stack.sync_github` with an attacker-chosen `expected_head_sha`.
- `status`/`check_suite` events can fabricate commit statuses or trigger `RefreshCheckRunsJob`, influencing merge-queue and CI gating decisions used for automated merges/deploys.
- `membership` events can create/delete `Team`/`Membership` records tied to the victim organization.
This can culminate in unauthorized deploys/merges or corruption of authorization state (`Shipit.github_teams` membership), matching the High/Critical impact categories (escalation into `Shipit.github_teams` authorization, unauthorized deploy/merge).

### Likelihood Explanation
Exploitability is conditional: it requires a Shipit instance configured with multiple GitHub Apps (per `docs/setup.md` "Using Multiple GitHub Applications") where at least one organization has `webhook_secret` unset/blank, which the code accepts as valid config: [6](#0-5) 
Given that omitting `webhook_secret` is presented as an acceptable, even default-nil, configuration option (`webhook_secret: # nil` in example secrets files), this is a realistic operational state rather than a purely theoretical one. No credentials, session, or prior access are required — only knowledge that such an organization exists in the multi-org configuration, which can often be inferred from public GitHub App installation listings.

### Recommendation
Enforce that the organization used to select the verification secret matches the organization embedded in `repository.full_name` before processing, e.g. derive `repository_owner` strictly from `repository.full_name.split('/').first` and reject if it disagrees with `repository.owner.login`/`organization.login`. Additionally, do not treat an absent `webhook_secret` as automatically valid; either require a secret to be configured for every organization in a multi-org setup or explicitly fail closed (422) rather than short-circuiting to `true`.

### Proof of Concept
1. Configure Shipit with two organizations: `orgA` (no `webhook_secret` set) and `orgB` (has `webhook_secret` set, hosts a real tracked stack `orgB/victim-repo`).
2. Send a `push` webhook to `/github/webhooks` with:
   - Header `X-Github-Event: push`
   - No/garbage `X-Hub-Signature` header
   - Body: `{"ref": "refs/heads/main", "after": "<attacker-chosen-sha>", "repository": {"owner": {"login": "orgA"}, "full_name": "orgB/victim-repo"}}`
3. `verify_signature` calls `Shipit.github(organization: "orgA")`; since `orgA.webhook_secret` is blank, `verify_webhook_signature` returns `true` unconditionally — the request passes with 200/OK.
4. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("orgB/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, acting on `orgB`'s stack despite the request never being authenticated with `orgB`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
