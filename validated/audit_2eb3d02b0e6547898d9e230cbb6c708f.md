## Confirmed Analog Vulnerability

### Title
Cross-tenant commit-status forgery bypasses CI gating and triggers unauthorized deploy - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `params.dig('repository','owner','login')` (or the `organization` fallback), while the code that actually acts on the payload (`StatusHandler#process`) looks up target records using an entirely different, unrelated field (`params.sha`), with **no scoping to the organization/repository that was authenticated**. This breaks the binding: *organization that authenticated == repository/commit that gets written*.

### Finding Description
`verify_signature` in [1](#0-0)  computes `repository_owner` from the JSON body and looks up `Shipit.github(organization: repository_owner)` to obtain the webhook secret used for HMAC verification. Per-organization configuration commonly ships with `webhook_secret: # nil` (see the documented multi-org template) [2](#0-1) . When that secret is blank, `verify_webhook_signature` unconditionally returns `true`, skipping any cryptographic check entirely: [3](#0-2) .

For any org configured without a `webhook_secret`, an unauthenticated caller can `POST /webhooks` with a completely attacker-controlled JSON body and pass verification simply by setting `repository.owner.login` (or `organization.login`) to that unsecured org name — a value never checked against anything else in the payload.

The event is then dispatched purely by the `X-Github-Event` header to handlers such as `StatusHandler`, which processes `params.sha`/`params.state` against **every** `Commit` row in the database matching that SHA, with no repository/org scoping at all: [4](#0-3) . The base `Handler` class does derive a `repository_name`/`stacks` scope from `payload.dig('repository','full_name')` [5](#0-4) , but `StatusHandler` does not use `stacks` at all — it queries `Commit.where(sha: params.sha)` globally, so the `repository` field used for signature-org selection is completely disconnected from what gets mutated.

Commit SHAs are not secret (visible in any public repo, PR, or the Shipit UI itself), so an attacker only needs to know: (1) one configured GitHub org/app with a blank `webhook_secret`, and (2) the SHA of a commit belonging to a completely different, securely-configured stack.

### Impact Explanation
Forging a `status` webhook (`state: "success"`) for a victim commit fabricates a passing CI status for that commit via `Commit#create_status_from_github!` → `add_status` [6](#0-5) . This directly feeds `Commit#deployable?` (`success? && !blocked?`) [7](#0-6)  and `add_status` explicitly schedules `stack.schedule_merges` and `ContinuousDeliveryJob` when the new status is `success` [8](#0-7) . On a stack configured with `continuous_deployment?`, this forged status can trigger an **unauthorized deploy** of a commit whose real CI checks may still be failing/pending, entirely from an unprivileged, unauthenticated HTTP request — no Shipit session, `ApiClient` token, or GitHub write access to the victim repo required. This satisfies the required Critical impact category ("an unauthorized deploy").

### Likelihood Explanation
Requires only: knowledge of one organization configured in `secrets.github` without a `webhook_secret` (an explicitly documented, supported configuration pattern in this engine's own templates) and a target commit SHA (public information). No credentials, no GitHub App access, no Shipit account are needed — only a plain HTTP POST to the public `/webhooks` endpoint. Deployability requires the target stack to have continuous deployment enabled, narrowing but not eliminating real-world likelihood.

### Recommendation
- Cross-validate that the organization used to select the webhook secret matches the `repository`/`organization` actually referenced by the event's target objects (commit, PR, stack) before any handler acts on them.
- Do not allow `verify_webhook_signature` to silently return `true` when `webhook_secret` is blank for multi-org configurations; require every configured organization to have a secret, or reject events from orgs with none.
- Scope `StatusHandler` (and any other handler that queries by a cross-repo-ambiguous key like `sha`) to `stacks`/`repository_name` the same way `PushHandler` does, rather than querying `Commit` globally by SHA.

### Proof of Concept
1. Configure/observe a Shipit deployment with multiple GitHub orgs, where org `unsecured-org` has `webhook_secret: nil` and org `victim-org` is properly secured and owns a stack tracking commit SHA `abc123...` (obtained from the public repo or Shipit UI).
2. Send, without any authentication and without a valid `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": { "owner": { "login": "unsecured-org" }, "full_name": "unsecured-org/anything" },
  "sha": "abc123...",
  "state": "success",
  "context": "ci/forged"
}
```
3. `WebhooksController#verify_signature` resolves `repository_owner` = `unsecured-org`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of signature — request passes.
4. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which runs `Commit.where(sha: 'abc123...').each { |c| c.create_status_from_github!(params) }`, creating a forged "success" status on the victim's commit, independent of the `unsecured-org`/`victim-org` mismatch.
5. If the victim stack has continuous deployment enabled, `add_status` schedules `ContinuousDeliveryJob`/`schedule_merges`, potentially resulting in an unauthorized deploy of that commit.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
