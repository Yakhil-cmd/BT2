## Title
Atomic Same-Unit AA Trigger Chaining Enables Flash-Loan-Style Draining of Balance-Proportional Reward/Share Pools - (File: `aa_composer.js`, `formula/evaluation.js`)

### Summary
The reported bug is that `NFTXLPStaking` computes a staker's share of accrued rewards from the *instantaneous* deposit size, allowing an attacker to flash-borrow a huge stake, claim, and exit atomically in one transaction. The structural analog in `ocore` is that Autonomous Agents (AAs) read `balance[asset]` as a live, mutable value [1](#0-0)  that can be inflated and drained within a *single, fully atomic* unit, because a primary trigger can chain into an arbitrary number of secondary AA triggers, all of which commit or roll back together as one unit [2](#0-1) . Any AA pool that computes a depositor's redeemable share as `deposit / balance[asset]` (the exact pattern shown in the repo's own `uniswap_like_market_maker.oscript` sample) can therefore be exploited: an attacker composes one signed unit whose message cascade (1) inflates the pool's balance via a payment/secondary-trigger, (2) has the pool AA mint shares/rewards proportional to that inflated balance, and (3) immediately redeems, all before any other legitimate depositor's unit can be included — with the entire sequence being atomically reversible (cheap to retry) if it fails.

### Finding Description
`balance[asset]` (`var`/`balance` opcode) is resolved from `objValidationState.assocBalances`, which is a running, mutable ledger of each AA's balance kept in memory for the duration of the whole trigger-response cascade [1](#0-0) . This balance is updated at each step: it is credited with the amount received in the trigger's payment messages when a (primary or secondary) trigger fires [3](#0-2) , and it is debited/credited as the AA sends/receives further payment messages, including in chained secondary triggers [4](#0-3) .

Crucially, a single top-level trigger unit can cause a whole chain of secondary AA invocations to fire synchronously and atomically: `handleSecondaryTriggers` walks every AA address that received a payment from the current response and immediately re-enters `handleTrigger` for each of them in the same call stack [2](#0-1) . If any AA further down the chain bounces, the *entire* cascade is rolled back via `ROLLBACK TO SAVEPOINT initial_balances` and all balance/state changes are undone [5](#0-4) , meaning a failed attack attempt costs only the trivial `bounce_fees` (`MIN_BYTES_BOUNCE_FEE`) rather than losing the "flash-loaned" funds.

This gives an attacker the same two properties that make ERC-20 flash loans dangerous for `NFTXLPStaking`:
1. **Momentary capital inflation**: a chain of AAs (an attacker-deployed "vault" AA plus the target pool AA) can move a large amount of an asset into the target pool and back out, all inside one physical unit, so the pool's `balance[asset]` reflects the inflated amount only transiently.
2. **Atomicity/no counterparty risk**: because the whole chain reverts together on any bounce, the attacker can safely attempt the maneuver — the "loan" is either fully repaid within the same unit or the whole thing never happened.

The project's own oscript sample `uniswap_like_market_maker.oscript` demonstrates the exact vulnerable computation pattern: on "invest," share of the pool's outstanding `mm_asset` is minted as `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` where `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance` [6](#0-5) , and on "divest," the redeemed amount is `round($investor_share * balance[$asset])` [7](#0-6) . If any prior fee/reward income has accumulated in `balance[$asset]`/`balance[base]` (analogous to NFTX's accrued rewards), an attacker who can transiently balloon their share of `var['mm_asset_outstanding']` via a chained trigger before redeeming captures a disproportionate cut of that accumulated value in the very same atomic unit.

### Impact Explanation
Any AA-based staking/dividend/LP-style pool deployed on `ocore` that determines a user's share of pooled rewards/fees from the ratio of the current trigger's payment to the pool's live `balance[asset]` (rather than a time-weighted or pre-committed stake) can have its accrued rewards or fee reserves siphoned by a single attacker in one unit, at the expense of long-term legitimate depositors — a direct AA fund-loss/value-theft scenario. Because the whole multi-AA cascade triggered from one unit is atomic (all-or-nothing) and cheap to abort, this is exploitable with near-zero risk capital, mirroring the "steal nearly all accrued rewards" impact from the original report.

### Likelihood Explanation
Exploitation requires only posting a single ordinary unit that triggers a chain of AAs the attacker controls (or an existing composable AA plus the target pool) — no special privileges, node access, or protocol-level manipulation are needed; this is squarely within reach of "an unprivileged AA trigger sender." The pattern of computing share-of-pool from live `balance[]`/`trigger.output[]` is explicitly documented and encouraged by the project's own sample AAs (Uniswap-like market maker, 51%-attack game payout logic based on `balance[base]` [8](#0-7) ), so it is a realistic, foreseeable design pattern for real-world AAs built on this engine, not a contrived edge case.

### Recommendation
- Document prominently (and provide safer reference implementations) that AAs implementing pooled staking/dividend logic must not size a depositor's share purely from the instantaneous `balance[asset]`/`trigger.output[]` ratio within a single atomic trigger cascade; instead, rewards should accrue based on time-weighted stake (e.g., snapshotting balance at a stable MCI, or requiring a minimum number of stable units between deposit and reward claim).
- Consider providing a built-in oscript primitive/pattern that lets AA authors detect and reject deposits and withdrawals of the same asset occurring within the same atomic trigger chain (e.g., a "response depth" or "chain id" check per asset), so pool AAs can enforce that shares can only be minted from deposits that have already been separately stabilized.
- Since this is an application-level design footgun rather than a protocol bug per se, recommend flagging it in AA developer guidance/audits of any deployed dividend, staking, or AMM-style AA, given the confirmed atomicity semantics of secondary AA triggers.

### Proof of Concept
Conceptually (following the "chain of AAs" composability already validated by the test suite [9](#0-8) ):
1. Deploy `PoolAA` implementing the `uniswap_like_market_maker.oscript` pattern, which already holds accrued `base`/asset fees from prior activity (`var['mm_asset_outstanding']`, `balance[base]`, `balance[$asset]` are all non-trivial).
2. Attacker posts one unit whose primary trigger fires `HelperAA`, which in its response sends a large payment to `PoolAA` (secondary trigger) with `trigger.data.define`/invest semantics, causing `PoolAA` to mint `mm_asset` shares proportional to `trigger.output[[asset=base]] / $bytes_balance` computed from the momentarily-passed-through balance [6](#0-5) .
3. `PoolAA`'s response (or a further secondary trigger back to `HelperAA`/attacker address) immediately redeems those freshly minted `mm_asset` shares via the divest branch, receiving `round($investor_share * balance[$asset])` and `round($investor_share * balance[base])` [7](#0-6)  — capturing a share of `PoolAA`'s pre-existing accrued fees.
4. All of this happens inside one physically-posted unit; if any step bounces, `ROLLBACK TO SAVEPOINT initial_balances` [10](#0-9)  undoes everything at the cost of only the bounce fee, so the attacker can repeat the attempt cheaply until parameters (timing, amounts) succeed.
