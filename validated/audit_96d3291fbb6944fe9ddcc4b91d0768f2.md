### Title
`isHandledEvent` Silently Swallows RPC Errors, Causing Spurious Re-submission of Already-Handled Bridge Value Transfers — (File: `node/sc/vt_recovery.go`)

---

### Summary

`isHandledEvent` in `node/sc/vt_recovery.go` calls `HandleNoncesToBlockNums` (an on-chain view call) to decide whether a bridge value-transfer event has already been handled. Any error from that call — including transient network errors, RPC rate-limit responses, or backend unavailability — is silently discarded, and the function returns `false` ("not yet handled"). This causes the Value Transfer Recovery (VTR) mechanism to classify already-handled events as pending and re-submit them to the bridge contract, consuming the operator's nonce and gas for transactions that will revert on-chain.

---

### Finding Description

`isHandledEvent` is the sole guard inside `retrievePendingEventsFrom` that prevents the VTR from re-submitting events that the counterpart bridge has already processed:

```go
// node/sc/vt_recovery.go
func isHandledEvent(to *BridgeInfo, ev IRequestValueTransferEvent) bool {
    blk, err := to.bridge.HandleNoncesToBlockNums(nil, ev.GetRequestNonce())
    if err == nil && blk > 0 {
        logger.Trace("skip handled event", "nonce", ev.GetRequestNonce())
        return true
    }
    return false   // ← returned for BOTH "not found" AND any RPC error
}
``` [1](#0-0) 

The condition `err == nil && blk > 0` means that whenever `HandleNoncesToBlockNums` returns a non-nil error (network timeout, rate limit, backend restart, etc.), the function returns `false` — identical to the "nonce genuinely not handled" path. The error is never propagated or logged.

This function is called for every candidate event in `retrievePendingEventsFrom`:

```go
if isHandledEvent(to, RequestValueTransferEvent{reqVTevIt.Event}) {
    continue
}
// event is appended to pendingEvents for re-submission
pendingEvents = append(pendingEvents, RequestValueTransferEvent{reqVTevIt.Event})
``` [2](#0-1) 

The same pattern repeats for `RequestValueTransferEncoded` events: [3](#0-2) 

Events collected in `pendingEvents` are fed into `recoverPendingEvents` → `AddRequestValueTransferEvents` → `processingPendingRequestEvents` → `handleRequestValueTransferEvent`, which unconditionally submits a `HandleKLAYTransfer` / `HandleERC20Transfer` / `HandleERC721Transfer` transaction and increments the operator's local nonce:

```go
handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
if err != nil { return err }
...
bridgeAcc.IncNonce()
``` [4](#0-3) 

---

### Impact Explanation

**On-chain revert, nonce consumed.** When the re-submitted handle transaction reaches the bridge contract, `_voteValueTransfer` reverts with `"closed vote"` (if `closedValueTransferVotes[nonce]` is still set) or `_lowerHandleNonceCheck` reverts with `"removed vote"` (if `lowerHandleNonce` has already advanced past the nonce):

```solidity
function _voteValueTransfer(uint64 _requestNonce) internal returns(bool) {
    require(!closedValueTransferVotes[_requestNonce], "closed vote");
    ...
}
``` [5](#0-4) 

```solidity
function _lowerHandleNonceCheck(uint64 _requestedNonce) internal {
    require(lowerHandleNonce <= _requestedNonce, "removed vote");
}
``` [6](#0-5) 

The transaction is mined and reverts, consuming the operator's gas and on-chain nonce. Because `bridgeAcc.IncNonce()` is called optimistically after submission (not after mining), the local nonce counter stays in sync, but the operator's KAIA balance is reduced by the wasted gas.

**Cascading stall risk.** If the RPC error is persistent (e.g., the remote backend is degraded), every VTR cycle re-submits all events in the window `[lowerHandleNonce, requestNonce)` as if none were handled. Each cycle burns operator gas and submits reverted transactions. Under sustained degradation this can drain the operator account, preventing any further legitimate handle transactions from being submitted.

**No double-asset transfer.** The bridge contract's `closedValueTransferVotes` / `_lowerHandleNonceCheck` guards prevent actual double-minting or double-transfer of KAIA/ERC-20/ERC-721 assets. The asset-level invariant is preserved; the broken invariant is the operator's nonce/gas budget and the correctness of the recovery flow.

---

### Likelihood Explanation

The VTR loop runs on a configurable timer (`VTRecoveryInterval`). Any transient connectivity issue between the service-chain node and the counterpart chain's RPC endpoint — network blip, rate-limit response, backend restart — during a recovery cycle is sufficient to trigger the bug. No privileged access or adversarial action is required; ordinary infrastructure instability is enough.

---

### Recommendation

`isHandledEvent` must distinguish between "nonce not found" (genuinely unhandled) and "RPC error" (unknown state). The simplest fix is to change the signature to return `(bool, error)` and propagate the error to `retrievePendingEventsFrom`, which should abort the recovery cycle rather than treating the event as pending:

```go
func isHandledEvent(to *BridgeInfo, ev IRequestValueTransferEvent) (bool, error) {
    blk, err := to.bridge.HandleNoncesToBlockNums(nil, ev.GetRequestNonce())
    if err != nil {
        return false, err  // propagate; caller must not re-submit
    }
    return blk > 0, nil
}
```

In `retrievePendingEventsFrom`, callers should check the error and return early:

```go
handled, err := isHandledEvent(to, RequestValueTransferEvent{reqVTevIt.Event})
if err != nil {
    return nil, err
}
if handled {
    continue
}
```

### Proof of Concept

1. A KAIA value transfer is requested on the child chain (nonce N).
2. The bridge operator handles it on the parent chain; `HandleKLAYTransfer` is mined successfully. `closedValueTransferVotes[N] = true`.
3. The VTR timer fires. `updateRecoveryHintFromTo` reads `lowerHandleNonce` and `requestNonce` correctly; nonce N is still in the window `[lowerHandleNonce, requestNonce)`.
4. `retrievePendingEventsFrom` iterates the `RequestValueTransfer` log for nonce N and calls `isHandledEvent`.
5. `HandleNoncesToBlockNums` RPC call fails (e.g., network timeout). `err != nil`, so `isHandledEvent` returns `false`.
6. Nonce N is appended to `pendingEvents`.
7. `recoverPendingEvents` feeds nonce N into `processingPendingRequestEvents`.
8. `handleRequestValueTransferEvent` calls `bi.bridge.HandleKLAYTransfer(auth, ...)`. The transaction is submitted; `bridgeAcc.IncNonce()` is called.
9. The transaction is mined and reverts with `"closed vote"` (because `closedValueTransferVotes[N]` is still `true`).
10. The operator's KAIA balance is reduced by the gas cost; the nonce is consumed for a no-op transaction.
11. If the RPC error persists, steps 4–10 repeat every `VTRecoveryInterval` seconds, draining the operator account. [1](#0-0) [2](#0-1) [7](#0-6) [8](#0-7) [5](#0-4)
