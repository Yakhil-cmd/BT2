### Title
CCMenu XML endpoint bypasses per-token stack scoping, allowing a narrowly-scoped API token to read any stack's status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController#stack` resolves the target stack through `stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` when the token is scoped to one stack [1](#0-0) . `Api::CCMenuController` overrides `stack` to call `Stack.from_param!(params[:stack_id])` directly against the unscoped `Stack` relation, so a token narrowly scoped to stack A can retrieve CCMenu status for stack B [2](#0-1) . Authorization for this action is checked with `require_permission :read, :stack`, which only verifies the permission string `"read:stack"` is present in `permissions`, not which stack it applies to [3](#0-2) [4](#0-3) .

### Finding Description
Broken binding: for a request to `Api::CCMenuController#show`, the equality `stack == stacks.from_param!(params[:stack_id])` (i.e., the resolved stack must be a member of the caller's authorized `stacks` scope) does **not** hold, because `stack` in this controller is redefined as `Stack.from_param!(params[:stack_id])`, ignoring `current_api_client.stack_id` entirely [5](#0-4) .

Path: an attacker holding a valid `ApiClient` token whose `stack_id` is set to stack A (and which includes the `read:stack` permission) sends `GET /api/stacks/:stack_id/ccmenu.xml` with `:stack_id` set to stack B's identifier and their token (via Basic Auth or `?token=`, since `CCMenuController` also overrides `authenticate_api_client` to accept `params[:token]`) [6](#0-5) . `require_permission!` only checks `permissions.include?("read:stack")`, with no reference to which stack the token is bound to [4](#0-3) . `#show` then calls `stack.deploys_and_rollbacks.last` on stack B and renders its name, activity, last build status/label, and web URL [7](#0-6) . In every other API controller (`Api::StacksController`, etc.), the same-named `stack` helper is inherited unmodified from `BaseController`, correctly scoping to `current_api_client.stack_id` — `CCMenuController` is the sole outlier that re-implements `stack` against the unscoped `Stack` model.

### Impact Explanation
An attacker with a token scoped to one stack can read deploy/build status, activity state, lock status, and web URL for any other stack in the Shipit instance by simply changing `:stack_id` in the URL. This is a cross-tenant read of stack state via a narrowly-scoped credential, which is unauthenticated with respect to the target stack: the token was never granted access to it. This matches the "unauthenticated read of stack state" High-severity impact category. It does not permit writes/mutations (the action is read-only `GET .../ccmenu.xml`), so it does not rise to the Critical "payload for one repository mutating another's stack" category, but it is a full authorization-scope bypass, repeatable against every stack in the instance with a single valid token of any scope.

### Likelihood Explanation
Requires the attacker to already possess one valid, narrowly-scoped `ApiClient` token with `read:stack` permission (i.e., they legitimately administer or were granted access to at least one stack, or otherwise obtained a scoped token) — this is a normal, intentionally-restricted credential per Shipit's design. No GitHub secrets, session, or elevated Shipit role is required. Given such a token, exploitation is a single unauthenticated-in-scope GET request with a different `stack_id` value; there is no rate limiting or additional validation preventing repeated abuse against every stack ID in the system.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the inherited, properly scoped resolution instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
or simply remove the override entirely so the `BaseController#stack` implementation (scoped via `stacks`) is used. Also review the custom `authenticate_api_client` override that accepts `params[:token]` outside of the shared Basic Auth pathway, to ensure it doesn't introduce further inconsistency with the rest of the API surface.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_test.rb
module Shipit
  module Api
    class CCMenuControllerTest < ApiControllerTestCase
      test "a token scoped to one stack cannot read another stack's ccmenu status" do
        scoped_stack = shipit_stacks(:shipit)
        foreign_stack = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')

        @client.update!(stack_id: scoped_stack.id, permissions: ['read:stack'])

        get :show, params: { stack_id: foreign_stack.to_param, token: @client.authentication_token }

        # Binding under test: resolved `stack` must be a member of `stacks`
        # (Stack.where(id: current_api_client.stack_id)), i.e. scoped_stack only.
        assert_response :not_found, "CCMenuController#stack must be scoped like BaseController#stack " \
          "(via `stacks.from_param!`), but resolves against the unscoped Stack relation instead"
      end
    end
  end
end
```
This asserts that with a token scoped to `scoped_stack`, requesting `foreign_stack`'s CCMenu XML should be rejected (404, as `stacks.from_param!` would raise `RecordNotFound` for a stack outside the scope) — but under the current code it succeeds (`200 OK`) and leaks `foreign_stack`'s status, demonstrating the divergence between `Api::CCMenuController#stack` and `Api::BaseController#stack`.
