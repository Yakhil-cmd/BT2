### Title
Webhook signature verification is bound to `repository.owner.login`, not to the `repository.full_name` that actually determines the target Stack - forged status/push events can be injected for any repository via an unsecured organization entry - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken directly from the untrusted, not-yet-verified JSON body. Every event handler, however, resolves the actual `Stack`/`Repository` to mutate using a *different* field from the same body, `repository.full_name`. These two fields are never cross-checked against each other, so the "organization that authenticated" is not bound to the "repository that is written."

### Finding Description
`verify_signature` looks up the signing secret via: [1](#0-0) 
using `repository_owner`, computed from the raw request body before any signature check has occurred: [2](#0-1) 

The secret itself comes from `Shipit.github(organization: ...)`, and `GithubApp#verify_webhook_signature` trivially returns `true` whenever no `webhook_secret` is configured for that organization: [3](#0-2) 

Meanwhile, every concrete handler (push, status, check_suite, etc.) resolves the `Stack`/`Repository` to act on using an entirely different JSON field, `repository.full_name`, via `Handler#stacks`/`#repository_name`: [4](#0-3) 
and `Repository.from_github_repo_name` simply splits that string to find the target repository, with no relationship enforced back to the organization used for signature verification: [5](#0-4) 

Because `repository_owner` (used to pick the verification secret) and `repository.full_name` (used to pick the write target) are independent, attacker-controlled fields inside the same unsigned-until-verified body, an attacker who knows of (or can install/onboard) any organization entry in `Shipit.github` config that has no `webhook_secret` set can craft a POST to `/webhooks` where:
- `repository.owner.login` / `organization.login` = the unsecured organization (verification passes unconditionally, since `webhook_secret` is blank), and
- `repository.full_name` = any other, fully-secured repository/organization already tracked by Shipit.

The request sails through `verify_signature` and is then dispatched to the real handler, which acts on the victim repository looked up via `full_name`, e.g. `StatusHandler` creating a `Status` record for an arbitrary commit SHA, or `PushHandler` enqueuing a `GithubSyncJob` for the target stack, `CheckSuiteHandler` enqueuing `RefreshCheckRunsJob`. This is exactly the class of bug in the external report: a value used to satisfy an authorization/verification check (`repository_owner` → secret selection) is not the same value that the privileged action is performed against (`repository.full_name` → stack/repository mutation), so protection intended for one binding leaks to an unrelated one.

### Impact Explanation
An unauthenticated, unprivileged network attacker can inject forged GitHub events (push/status/check_suite/pull_request/membership) for any repository tracked by the Shipit instance, as long as any configured organization in `Shipit.github` lacks a `webhook_secret` (a supported, documented configuration — see `docs/setup.md` marking `webhook_secret` as "(optional)" and the sample `config/secrets.development.shopify.yml` shipping with `webhook_secret: # nil`). Forged `status` events write attacker-controlled `Status` rows (state/description/target_url) for arbitrary commits, which feed into Shipit's deployability/merge-status checks — enabling a commit that never actually passed CI to be marked deployable/mergeable, i.e. an unauthorized deploy/merge path. Forged `push`/`check_suite` events can trigger sync/check-run refresh jobs against arbitrary tracked stacks. This matches the required "unauthorized deploy, rollback or merge" / "cross-repository writes" impact bar.

### Likelihood Explanation
Likelihood is high wherever any organization is configured without a webhook secret (an explicitly supported and documented setup) — the attacker needs no credentials, tokens, or repository access; a single crafted HTTP POST to the public `/webhooks` endpoint suffices, and the target repository/organization can be entirely unrelated to the unsecured one used to pass verification.

### Recommendation
Bind signature verification to the exact repository/organization the payload will act on:
- Verify the signature using the secret associated with the *target* repository (the one resolved via `repository.full_name`), not a separate `repository.owner.login`/`organization.login` field.
- Alternatively, after verification, assert that `repository.owner.login` matches the owner segment of `repository.full_name` before dispatching to handlers, and reject on mismatch.
- Do not silently accept unsigned webhooks (`return true unless webhook_secret`) for organizations lacking a configured secret; require a secret for any organization capable of triggering writes on tracked repositories, or scope verification/dispatch to a single canonical secret per repository rather than per loosely-derived organization field.

### Proof of Concept
1. Configure (or find already configured) two organizations in `Shipit.github`: `org-empty` (no `webhook_secret`) and `org-victim` (has a tracked repository `org-victim/app`, with a webhook secret configured).
2. Send an unauthenticated POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": {
    "owner": { "login": "org-empty" },
    "full_name": "org-victim/app"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/build",
  "target_url": "https://attacker.example/fake",
  "branches": [{ "name": "master" }]
}
```
3. `verify_signature` resolves `repository_owner` = `org-empty`, calls `Shipit.github(organization: 'org-empty').verify_webhook_signature(...)`, which returns `true` unconditionally because `org-empty` has no `webhook_secret` — see [6](#0-5) .
4. The request proceeds to `Shipit::Webhooks.for_event('status')`, whose handler resolves the target via `payload.dig('repository', 'full_name')` = `org-victim/app` [7](#0-6)  and writes a forged `Status` for the victim repository's commit, despite the attacker never possessing `org-victim`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
