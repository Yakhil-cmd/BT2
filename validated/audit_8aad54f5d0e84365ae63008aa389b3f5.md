### Title
`Shipit::Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scoping, letting any authenticated client read another stack's CCMenu feed - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`CCMenuController` overrides `#stack` with `Stack.from_param!(params[:stack_id])`, which is unscoped by the authenticated client's `stack_id`, unlike `BaseController#stack` which resolves against `stacks` (`Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped). Because `require_permission!` only checks the `read:stack` permission string and never compares `current_api_client.stack_id` to the requested `stack.id`, any client with `read:stack` permission — even one scoped to a single stack — can read the CI status/build label of any other stack via `GET /stacks/:stack_id/ccmenu`.

### Finding Description
The binding that should hold is: `current_api_client.stack_id? ? stack.id == current_api_client.stack_id : true` (i.e., a stack-scoped client should only ever resolve `stack` to its own stack). In `BaseController`, this is enforced structurally: [1](#0-0) 
`stacks` restricts the resolvable set to the client's own stack when `current_api_client.stack_id?` is true, and `#stack` calls `stacks.from_param!`.

`CCMenuController` re-defines `#stack` to bypass this entirely: [2](#0-1) 
`Stack.from_param!` resolves against the full `Stack` table with no relation to `current_api_client.stack_id`.

`authenticate_api_client` first tries token-param auth, then falls back to `super` (Basic Auth): [3](#0-2) [4](#0-3) 
Regardless of which path succeeds, `@current_api_client` ends up bound to whichever `ApiClient` record was verified — this part is correctly scoped. The bug is downstream: `require_permission :read, :stack` only calls `check_permissions!`, which checks the permission string, not the stack identity: [5](#0-4) 

Exploit flow: attacker holds a legitimately-issued `ApiClient` credential scoped to stack A (`stack_id` = A, permission `read:stack`). They send `GET /stacks/B/ccmenu` with `Authorization: Basic <base64(A's token)>` (and can pass any garbage `token` query param, since `ApiClient.authenticate(params[:token])` returns `nil` and falls through to `super`, which authenticates via Basic Auth as A's client). `authenticate_api_client` succeeds, `require_permission!(:read, :stack)` passes because A's client has `read:stack`, and `#stack` resolves `Stack.from_param!('B')` — stack B, not A. The XML for stack B's latest deploy/rollback is rendered and returned to the attacker.

No existing guard catches this: `check_permissions!` never inspects `scope`/stack identity — the `scope` argument is a literal symbol (`:stack`), not the actual `Stack` record; `stacks`/`from_param!` scoping is only used in `BaseController#stack`, which `CCMenuController` deliberately overrides.

### Impact Explanation
Any holder of a valid stack-scoped `ApiClient` credential (Basic-Auth or token form) with `read:stack` permission can read the CI status/build label of any other stack in the same Shipit installation, regardless of that stack's tenant/repository. This is a cross-tenant unauthorized read of stack state, repeatable for every stack ID the attacker can guess or enumerate, matching the High-severity category "unauthenticated/unauthorized read of stack state" across tenants sharing one Shipit instance.

### Likelihood Explanation
Requires the attacker to already hold one valid `ApiClient` credential scoped to any single stack with `read:stack` permission (a normal, legitimately-provisioned integration credential in multi-tenant Shipit deployments). No GitHub secrets, session, or `api_clients_secret` knowledge is needed beyond the one credential the attacker legitimately possesses. Given that precondition, the attack is a single unauthenticated-parameter HTTP GET with a trivially guessable stack ID, fully repeatable against every other stack.

### Recommendation
In `CCMenuController#stack`, scope resolution through the same `stacks` scoping used in `BaseController`, e.g., replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])` (removing the private `stacks` method override in `CCMenuController`, or inheriting it), so a stack-scoped `ApiClient` can only ever resolve to its own `stack_id`.

### Proof of Concept
```ruby
# test/controllers/shipit/api/ccmenu_controller_test.rb
test "#show refuses to leak another stack's status via basic auth for a differently-scoped client" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cyclimse) # a different stack

  client_a = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: "client-a",
    permissions: ["read:stack"],
    stack: stack_a,
  )

  credentials = ActionController::HttpAuthentication::Basic.encode_credentials(client_a.authentication_token, '')
  get "/stacks/#{stack_b.to_param}/ccmenu", params: { token: "garbage" }, headers: { "Authorization" => credentials }

  # Binding under test: current_api_client.stack_id (stack_a.id) must equal the resolved stack's id
  assert_equal client_a.stack_id, stack_a.id
  refute_equal client_a.stack_id, stack_b.id

  assert_response :ok # BUG: currently returns :ok and renders stack_b's XML instead of :forbidden/:not_found
  assert_match(/#{stack_b.to_param}/, response.body)
end
```
This demonstrates that despite `current_api_client.stack_id == stack_a.id`, the response body is derived from `stack_b`, proving the binding `stack.id == current_api_client.stack_id` is violated.
