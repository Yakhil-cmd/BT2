### Title
Webhook signature is verified against `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, letting a valid webhook signer for one organization spoof events for stacks belonging to a different repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
This is the same bug-class as the analog report: a value that is checked/authorized (the organization whose secret validates the HMAC signature) is not the same value that is later trusted to decide what gets acted on (the repository the event is applied to). In `RevenueHandler.sol`, the checked balance and the balance actually spent diverge because the check re-reads a value already covered by a previous accounting pass. Here, the field the signature-verification step uses to pick which secret to check with (`repository.owner.login` / `organization.login`) and the field the handlers use to resolve the target `Stack` (`repository.full_name`) are two independent keys inside the same attacker-supplied JSON body, and nothing binds them together.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to validate the signature against using a value taken directly out of the unauthenticated request body: [1](#0-0) [2](#0-1) 

`verify_webhook_signature` only proves that the raw body bytes were HMAC-signed with the secret belonging to whichever organization `repository_owner` names - it says nothing about which repository the payload's other fields describe: [3](#0-2) 

Once the signature check passes, `create` hands the entire parsed payload to the event handlers unchanged: [4](#0-3) 

Every handler, however, resolves the `Stack`/`Repository` to act on using a *different* field of the same payload, `repository.full_name`, with no cross-check against `repository.owner.login`: [5](#0-4) 

For example the push handler resyncs whatever stacks match that repository/branch: [6](#0-5) 

Because the value used to select the verifying secret (`repository.owner.login`) and the value used to select the acted-upon repository (`repository.full_name`) are independent, attacker-controlled JSON keys, an entity that legitimately possesses the webhook secret for organization A's GitHub App (i.e. is a normal, unprivileged administrator of a repo/org A that this Shipit instance also serves) can craft and sign a payload where:
- `repository.owner.login` = `"org-a"` (or `organization.login` = `"org-a"`) so `verify_webhook_signature` succeeds using org A's secret, and
- `repository.full_name` = `"org-b/some-other-repo"`, a completely different repository/organization also tracked by this Shipit instance.

The signature check passes (it only validates org A's secret against the raw bytes), yet every handler downstream (`push`, `status`, `check_suite`, `pull_request`, `commit_status`, `merge`, etc.) resolves and mutates state belonging to org B's stacks, because they trust `repository.full_name` unconditionally. This is precisely the "organization that authenticated versus the repository that is written" binding called out as an in-scope analog class.

### Impact Explanation
An attacker with legitimate webhook credentials for one repository/org can forge webhook events (push, CI `status`, `check_suite`, `pull_request`, `merge_status`) that are applied to stacks of a completely unrelated repository/org hosted on the same Shipit instance. Since Shipit's deploy button gating and CI checks rely on `status`/`check_suite` events to mark commits deployable, this can be used to mark an arbitrary target commit "deployable" (spoofed green CI) on a repo the attacker does not control, enabling an unauthorized deploy of that commit - one of the explicitly listed Critical impacts ("an unauthorized deploy"). It can also trigger `GithubSyncJob` and other side effects on stacks the attacker has no access to.

### Likelihood Explanation
Requires only that the Shipit deployment serves more than one GitHub organization/App configuration (a documented, supported multi-org setup, cf. `GithubOrganizationUnknown` handling and per-organization `Shipit.github(organization:)` lookup) and that the attacker holds a valid webhook secret for any one of those organizations - not for the target org/repo. No repository write access, no privileged Shipit account, and no interception of TLS or other credentials belonging to the victim organization are required; the crafted JSON body is entirely under the attacker's control and legitimately signable with their own org's secret.

### Recommendation
Bind the field used to select the signing secret to the field used to resolve the target repository: after `verify_webhook_signature` succeeds, re-derive `repository_name`/stack resolution strictly from the same `repository.owner.login`/`organization.login` value that was cryptographically verified (or verify that `repository.full_name`'s owner segment matches `repository_owner`) before any handler is allowed to act on the payload.

### Proof of Concept
1. Configure Shipit to serve two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (as documented in `docs/setup.md`).
2. As an attacker who only administers org A's GitHub App (has org A's `webhook_secret`), construct a `status` (or `push`) event body:
```json
{
  "repository": {
    "owner": { "login": "org-a" },
    "full_name": "org-b/target-repo"
  },
  "organization": { "login": "org-a" },
  "sha": "<victim commit sha on org-b/target-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. Sign the raw body with `org-a`'s `webhook_secret` using HMAC-SHA1 and send it with header `X-Hub-Signature: sha1=<hmac>` and `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and the signature check passes (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. The status handler resolves the target repository via `payload.dig('repository', 'full_name')` = `"org-b/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and writes a spoofed successful CI status for `org-b`'s commit, which the attacker never had credentials for.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
