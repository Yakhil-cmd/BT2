## Title
Stack-scoped API tokens can read state of arbitrary stacks via the CCMenu endpoint - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::CCMenuController` bypasses the stack-scoping enforced by `Api::BaseController` for every other API controller, letting an `ApiClient` token authorized (`stack_id`) for one stack read the deploy/build state of any other stack in the installation.

### Finding Description
`Api::BaseController` defines the canonical way controllers must resolve a stack for a scoped `ApiClient`: [1](#0-0) 

`stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated client has a `stack_id` binding, and every other API controller (e.g. `Api::StacksController`) resolves records through this scoped relation: [2](#0-1) 

`Api::CCMenuController`, however, overrides the private `stack` method to look the stack up directly and unscoped: [3](#0-2) 

`require_permission :read, :stack` only validates that the token carries the `read:stack` *permission string*; it never checks that the specific `stack_id` matches the client's `current_api_client.stack_id`, which is the check the `stacks` scoping in `BaseController` normally performs. Because `CCMenuController#stack` calls `Stack.from_param!` directly instead of `stacks.from_param!`, this scoping check is skipped entirely for this endpoint.

The equality broken is: **the stack a token authorizes (`current_api_client.stack_id`) ≠ the stack it actually touches (`params[:stack_id]` resolved unscoped)**.

### Impact Explanation
Any valid `ApiClient` token with `read:stack` permission — even one deliberately scoped by an administrator to a single stack (e.g. fixture `here_come_the_walrus`, scoped to `shipit_stacks(:shipit)` only, as seen in `test/fixtures/shipit/api_clients.yml`) — can query `GET /api/stacks/:stack_id/cc.xml` for any other stack ID and receive that stack's name, `merge_status`-derived build status, running/idle activity, last build time/label, and web URL: [4](#0-3) 

This is an unauthorized read of stack state across the authorization boundary that `stack_id`-scoped tokens are supposed to enforce, matching the "High — unauthenticated/unauthorized read of stack state" impact category.

### Likelihood Explanation
This requires only possession of any valid, narrowly-scoped API token (no elevated permission, no organization membership, no webhook secret) — exactly the kind of restricted token an operator would issue to a low-trust integration expecting it to see only its own stack. The bypass is triggered by simply supplying a different `stack_id` in the URL; no other precondition is needed.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so stack-scoped tokens can only ever resolve their own authorized stack, consistent with every other API controller.

### Proof of Concept
1. Create an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (as `here_come_the_walrus` fixture demonstrates).
2. Using that client's `authentication_token`, request `GET /api/stacks/<other-stack-B-param>/cc.xml?token=<token>` (see `authenticate_api_client` override accepting the token via query string): [5](#0-4) 
3. The response returns stack B's build status/activity/webUrl even though the token is only authorized for stack A — confirmed by the existing test suite exercising this controller with tokens scoped differently from the target stack.
