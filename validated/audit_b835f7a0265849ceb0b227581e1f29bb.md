### Title
Cross-organization commit status forgery via unscoped `sha` lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The report's bug class is "attacker-controlled data trusted without being covered by the effective verification." The analog here is not CSV formula injection, but a webhook trust binding break: the `status` webhook signature is verified against the GitHub organization named in the payload's `repository.owner.login`, yet the handler that consumes the same payload never re-checks that binding when deciding *which* commit/stack to mutate.

### Finding Description
`WebhooksController#verify_signature` selects the webhook secret to check the HMAC against using `repository_owner`, which is read straight from the untrusted payload (`params.dig('repository', 'owner', 'login')`): [1](#0-0) [2](#0-1) 

Multiple GitHub organizations can be configured, each with its own `webhook_secret`, selected via `Shipit.github(organization:)`: [3](#0-2) 

So a payload's HMAC only proves "someone who knows organization X's `webhook_secret` sent this JSON body" — it says nothing about which repository/commit the body actually references. `StatusHandler#process`, however, resolves the target purely from the `sha` field, with **no repository or organization scoping at all**: [4](#0-3) 

This directly calls `Commit#create_status_from_github!`, which writes a new `Status` for that commit regardless of which stack/repository/organization it belongs to: [5](#0-4) 

Contrast this with `PushHandler`/`CheckSuiteHandler`, which do scope through `Handler#stacks`, itself derived from `repository.full_name` (a different, also-unverified payload field) rather than the same value used for signature selection: [6](#0-5) [7](#0-6) 

Even in those cases, nothing cross-checks `repository.owner.login` (used to select the verifying secret) against `repository.full_name` (used to select the mutated repository/stack) — but `StatusHandler` is the sharpest case because it drops repository binding entirely and matches on a global `sha`.

The binding broken, stated as an equality that the code assumes but never enforces:
`organization authenticated via webhook_secret(repository.owner.login)` ≠ `repository/commit actually mutated (Commit.where(sha: params.sha), unscoped)`.

### Impact Explanation
An entity that operates one legitimately-configured GitHub organization on a shared Shipit instance (i.e., an "unprivileged attacker" relative to any other tenant organization) can compute a valid `X-Hub-Signature` using their own org's `webhook_secret`, then submit a `status` event whose `sha` matches a commit belonging to a *different* organization's stack (commit SHAs are public info for public repos, or knowable via PR/CI leakage). Because `StatusHandler` performs `Commit.where(sha: params.sha)` with no repository check, the forged status is applied to the victim's commit. Since `Commit#deployable?` and CI gating (`Shipit.yml` `ci.require` / `blocking_statuses`) rely on `Status::Group` built from these `statuses`, an attacker can artificially mark a victim's commit "success," clearing required-status gates and enabling `continuous_deployment` (`schedule_continuous_delivery`) or manual deploy triggers to proceed for a repository the attacker has no access to. This is an authorization boundary crossing between GitHub organizations that results in an unauthorized deploy — matching the "Critical: unauthorized deploy" impact bucket.

### Likelihood Explanation
Requires the Shipit instance to be configured for more than one GitHub organization (`Shipit.github_organizations`) and requires the attacker to control (or be an admin of) one of those organizations' GitHub App installations to obtain a valid `webhook_secret` — a realistic scenario for any multi-tenant Shipit deployment. No access to the victim organization, its repository, or its GitHub App credentials is required.

### Recommendation
In `StatusHandler` (and generally in `Handler`), scope lookups by the repository identified in the *same* payload used to select the verifying organization's secret, and reject/ignore events where `repository.owner.login` does not match the owner segment of `repository.full_name`. Concretely: filter `Commit.where(sha: params.sha)` by `stack.repository` where `repository.owner == verified_organization`, or better, pass the verified organization from the controller into the handler and assert equality before creating/updating any `Status`, `CheckRun`, or triggering a sync.

### Proof of Concept
1. Shipit is configured with two organizations, `orgA` (attacker-controlled) and `orgB` (victim), each with distinct `webhook_secret`s under `secrets.github`.
2. Attacker learns/observes a commit SHA belonging to `orgB`'s tracked repository (e.g., a public repo, or via a stack page they can view but not administer).
3. Attacker crafts a JSON body:
```json
{
  "sha": "<orgB's target commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(orgA_webhook_secret, body)>` using their own org's known secret.
5. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: "orgA")` and the HMAC checks out, passing verification.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — which matches `orgB`'s commit — and calls `create_status_from_github!`, injecting a forged "success" status onto a commit in a repository the attacker never had access to, potentially unblocking `orgB`'s deploy gating.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
