### Title
Cross-repository forged status injection via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `sha`, with no scoping to the repository/stack that actually emitted the webhook, and `Status.replicate_from_github!` then writes attacker-controlled `state`/`description`/`target_url`/`context` verbatim onto every matching `Commit` record. Any attacker who owns a repository with the Shipit GitHub App/webhook installed (and therefore possesses a valid signature for their own org) can trigger a webhook whose `sha` collides with a commit tracked by a victim stack in a completely different repository, causing Shipit to write attacker-chosen `Status` data (including `target_url`, rendered as a deploy-button link) onto the victim's commit/stack.

### Finding Description
The broken binding, stated as an equality that should hold but does not:
`Status(victim_stack).target_url == GitHub-emitted status for victim_stack.repository`
In reality, after the exploit: `Status(victim_stack).target_url == attacker_supplied_string`, because the value is sourced from a webhook payload that was authenticated only against the *attacker's own* organization's webhook secret, not against the victim repository's identity.

Code path:
1. `WebhooksController#create` parses the raw JSON body and dispatches to handlers, gated by `before_action :verify_signature` [1](#0-0) [2](#0-1) 
2. `verify_signature` resolves the signing app via `Shipit.github(organization: repository_owner)`, where `repository_owner` is read directly from the attacker-controlled payload's `repository.owner.login` [3](#0-2) . This only proves the request was signed by *some* configured GitHub org's webhook secret — namely, the org the attacker controls and has installed the app on — not that the `sha` inside the payload belongs to that org's repository.
3. `StatusHandler#process` then looks up commits **globally by sha**, with no join/filter on stack, repository, or the `repository_owner` that was just verified: [4](#0-3) 
4. For every matching `Commit` (which may belong to an entirely unrelated victim `Stack`/repository), `create_status_from_github!` is invoked, passing the raw `ExplicitParameters` object straight through: [5](#0-4) 
5. `Status.replicate_from_github!` writes `state`, `description`, `target_url`, `context`, `created_at` verbatim from the attacker's payload into a `Status` row belonging to the victim's `stack_id`: [6](#0-5) 

No model validation constrains `target_url`/`description` format, scheme, or length, and no code anywhere re-derives or cross-checks that the commit's `stack.repository` matches the webhook's originating repository.

Attacker's exact request: attacker owns/controls a GitHub repository (their own fork or any repo) with the Shipit GitHub App installed on their org (a normal, unprivileged action any GitHub user can do for their own repos/orgs). They identify or engineer a commit sha that also exists in a victim stack tracked by the same Shipit instance (trivial for forks of the same upstream, mirrored repos, or repos sharing history/rebase artifacts — this is the "commit sha collision" precondition). They send `POST /webhooks` with `X-Github-Event: status`, a validly-computed `X-Hub-Signature` using their own org's webhook secret, and a JSON body containing that shared `sha` plus attacker-chosen `state`, `description`, `target_url`, `context`. Shipit verifies the signature successfully (it is valid — for the attacker's own org), then writes the forged status onto the victim stack's commit.

`verify_signature`, `drop_unhandled_event`, and the `ExplicitParameters` schema in `StatusHandler` (which only requires `sha`/`state` be `String` with no length/URL-format constraints) do not prevent this, because none of them ties the verified signing identity to the specific commit/stack being mutated.

### Impact Explanation
The attacker achieves a cross-repository/cross-tenant record write: a `Status` row is created against the victim's `Stack`, with an attacker-chosen `target_url` that gets rendered as a deploy-button/status link in the victim's Shipit UI, and an attacker-chosen `description`/`state` shown as CI status on the victim's commit. This can be used to inject arbitrary links (phishing, malware) into a trusted internal tool's UI, spoof CI state to make an unreviewed/failing commit appear to have passing status (potentially influencing merge/deploy decisions), and is repeatable against any stack in the instance sharing a colliding sha with an attacker-controlled repo. This matches the rubric's Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs (a) any GitHub repository/org with the Shipit GitHub App or webhook installed and a webhook secret they can compute a valid HMAC for (achievable simply by installing the app on their own account/org, which requires no Shipit privileges), and (b) a commit `sha` that is also tracked by a victim `Stack` in the same Shipit instance. Sha collisions across repositories under the same Shipit install are realistic in common scenarios (forks of the same upstream tracked as separate stacks, mirrored/rebased repos, monorepo splits) and require no cryptographic break — only ordinary git history overlap. No Shipit session, API token, or maintainer role is required. Given these preconditions, the attack is trivially repeatable per request.

### Recommendation
Scope the commit lookup and status write to the repository that was authenticated by `verify_signature`. Concretely, `StatusHandler#process` should filter `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository_id: <repo resolved from payload> })` (or equivalent), ensuring the webhook's own `repository.full_name`/`owner.login` matches the `Stack`'s configured repository before any `Status` is created, rather than trusting a global sha match.

### Proof of Concept
Minitest plan (`test/models/webhooks/status_handler_test.rb` or `test/models/commits_test.rb`, illustrative — exact file is out-of-scope per rules but shown for reproducibility):

```ruby
test "status webhook from one repository must not mutate a commit belonging to a different stack" do
  victim_stack = shipit_stacks(:shipit)
  attacker_owned_stack = create_stack(repository_owner: 'attacker-org', repository_name: 'attacker-repo')

  colliding_sha = 'deadbeef' * 5
  victim_commit = victim_stack.commits.create!(sha: colliding_sha, message: 'victim commit', author: users(:walrus))
  # simulate the same sha existing for the attacker's own tracked repo/stack (fork/mirror scenario)
  attacker_owned_stack.commits.create!(sha: colliding_sha, message: 'attacker commit', author: users(:walrus))

  params = Shipit::Webhooks::Handlers::StatusHandler.params_class.new(
    sha: colliding_sha,
    state: 'success',
    description: 'pwned',
    target_url: 'https://evil.example.com/phish',
    context: 'ci/attacker'
  )

  Shipit::Webhooks::Handlers::StatusHandler.new.process_for_test(params) # invokes commit.create_status_from_github! for all Commit.where(sha:)

  victim_status = victim_commit.statuses.last
  assert_not_equal 'https://evil.example.com/phish', victim_status&.target_url,
    "victim stack's commit status.target_url must not equal attacker-supplied value from an unrelated repository's webhook"
end
```

Binding asserted on both sides: before exploit, `victim_status.target_url` should equal a value emitted by GitHub for the victim's own repository (or be nil/absent); after the forged webhook, the current code makes it equal the attacker-supplied `'https://evil.example.com/phish'`, confirming the divergence.
