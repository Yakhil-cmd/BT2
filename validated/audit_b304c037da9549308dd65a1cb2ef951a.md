### Title
Cross-organization/cross-repository commit status forgery via unscoped `StatusHandler` breaks the org-that-authenticated vs. repository-that-is-written binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Webhook signature verification in `WebhooksController#verify_signature` selects which organization's `webhook_secret` to check against using a field taken from the attacker-controlled JSON body (`repository.owner.login`, falling back to `organization.login`), while the code that actually mutates state — `StatusHandler#process` — never re-checks that binding and, worse, doesn't even scope by repository at all. This lets anyone who legitimately possesses **one** organization's `webhook_secret` (e.g., an admin of their own org onboarded onto a shared/multi-tenant Shipit instance) forge a validly-signed webhook whose payload content targets a commit belonging to a completely different, unrelated repository/organization.

### Finding Description
Signature verification is performed like this: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight out of the untrusted JSON body and used only to pick *which* `GitHubApp`/`webhook_secret` to verify the raw POST against: [3](#0-2) 

The signature proves only "this exact byte string was produced by someone who knows organization X's `webhook_secret`" — it says nothing about whether the *content* of that byte string (e.g. which commit sha, which repository) actually belongs to organization X. Handlers are expected to re-derive the target repository from the same payload and scope their writes accordingly, e.g. via `Handler#repository_name`/`#stacks`: [4](#0-3) 

However, `StatusHandler` — which processes GitHub `status` events — does not use this repository-scoping mechanism at all: [5](#0-4) 

`Commit.where(sha: params.sha)` searches **every commit in the entire Shipit database**, across all stacks and repositories, regardless of which organization's secret was used to sign the request. This is the binding break: `webhook_secret(organization authenticated)` == HMAC(raw_post) is verified, but the actual write target — `Commit#create_status_from_github!` — is bound only to a `sha` value inside that same signed body, with no check that the sha's owning repository corresponds to the organization whose secret was used to authenticate.

Because commit shas are content-addressed and can be identical across forks/mirrors, or simply learned/guessed by an attacker who has read access to a public mirror of the target repo, an attacker who runs their own onboarded GitHub organization (with a legitimately-configured `webhook_secret` in this Shipit instance) can sign an arbitrary status payload with their own secret and set `sha` to a commit belonging to any other tracked stack.

### Impact Explanation
A forged `success` status for a required CI context directly affects `Commit#deployable?`: [6](#0-5) 

If continuous deployment is enabled on the target stack, a forged "success" status can make an otherwise CI-blocked/unreviewed commit `deployable?`, triggering an unauthorized deploy of another organization's repository — squarely matching the Critical impact category "unauthorized deploy, rollback or merge." `CheckSuiteHandler` is comparatively safer since it scopes lookups through `stacks` (repository-derived), but `StatusHandler`'s complete lack of repository scoping makes it the concrete exploitable path.

### Likelihood Explanation
Requires only that the attacker control (or has legitimately been issued) the `webhook_secret` for *some* organization configured in the same multi-tenant Shipit instance, plus knowledge of a target commit sha (often discoverable from a public GitHub repo/mirror or previously-observed webhook traffic). No access to the victim's repository, GitHub App, or Shipit account is needed — this is an unprivileged-attacker path relative to the victim stack.

### Recommendation
`StatusHandler` (and any other handler that doesn't already do so) must scope its `Commit`/`Stack` lookups through the same repository derived from `repository.full_name`/`repository_name`, exactly as `PushHandler` and `CheckSuiteHandler` do via `Handler#stacks`, and that repository must be cross-checked against the organization used to verify the webhook signature (`repository_owner`) before any state mutation occurs.

### Proof of Concept
1. Attacker legitimately registers/administers `attacker-org` in the Shipit instance (multi-tenant `Shipit.github(organization: ...)` configuration), obtaining its `webhook_secret`.
2. Attacker crafts a `status` event JSON body: `{"repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/whatever"}, "sha": "<victim-repo-commit-sha>", "state": "success", "context": "ci/required-context"}`.
3. Attacker computes `sha1=HMAC(attacker-org-webhook-secret, raw_body)` and sends it as `X-Hub-Signature` with `X-Github-Event: status` to `WebhooksController#create`.
4. `verify_signature` resolves `repository_owner` → `attacker-org`, fetches `attacker-org`'s `GitHubApp`, and successfully verifies the signature (it was legitimately signed with that secret) — `app/controllers/shipit/webhooks_controller.rb:24-30`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` unscoped by repository — `app/models/shipit/webhooks/handlers/status_handler.rb:20-24` — and writes a forged `success` status onto the victim's commit, potentially flipping `deployable?` and triggering continuous deployment for a repository the attacker has no access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
