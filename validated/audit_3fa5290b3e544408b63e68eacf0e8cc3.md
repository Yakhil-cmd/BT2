### Title
`MembershipHandler#process` trusts attacker-supplied `team.id` without scoping the mutated `Team` to the webhook's verified organization - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`verify_signature` in `WebhooksController` only proves the payload was signed with the `webhook_secret` of the organization named in the payload itself (`repository_owner`/`organization.login`), which for a `membership` event an attacker fully controls via their own GitHub org. `MembershipHandler#find_or_create_team!` then looks up a `Team` purely by attacker-supplied `params.team.id` (`github_id`), with no check that the found team's `organization`/`github_id` actually belongs to the verified organization, so an attacker can graft their own GitHub user onto any pre-existing `Team` row whose `github_id` they can guess.

### Finding Description
The claimed broken binding is: `organization verified by HMAC signature == organization that owns the Team row being mutated`. Tracing the code:

- `verify_signature` resolves `Shipit.github(organization: repository_owner)` where `repository_owner` for a `membership` event (no `repository` key) is `params.dig('organization', 'login')` [1](#0-0) , i.e., exactly the organization the attacker names in their own payload. This is legitimately the attacker's own org, and the HMAC is legitimately signed with the attacker's own org's `webhook_secret` by GitHub — so `verify_signature` succeeds, correctly proving "this webhook really came from GitHub for attacker-org." It proves nothing about the `team.id`/`team.organization` fields inside the body, which are attacker-supplied JSON.
- `WebhooksController#create` dispatches to `Shipit::Webhooks.for_event('membership')` → `MembershipHandler.call(params)` [2](#0-1) [3](#0-2) .
- `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id)` [4](#0-3) . If a `Team` with that `github_id` already exists (e.g., belonging to a victim org that legitimately synced a real GitHub team), the block that sets `team.organization = params.organization.login` is **not executed** (it only runs on record creation), so the existing team is fetched as-is and its `organization` is left unchanged/untouched.
- `process` then unconditionally does `team.add_member(User.find_or_create_by_login!(params.member.login))` for `action == 'added'` [5](#0-4) , adding the attacker-controlled `member.login` to that victim `Team`'s `members` association regardless of which organization the signature verification actually validated.

Root cause: the handler never checks `team.organization == params.organization.login` (or the verified `repository_owner`) before mutating team membership; it trusts an attacker-suppliable `github_id` as the sole lookup key across organizational boundaries.

Existing guards do not close this gap: `verify_signature` only authenticates "this org's own webhook," not "this org owns this team ID"; `drop_unhandled_event`/`check_if_ping` are irrelevant no-ops for `membership`; the `ExplicitParameters` schema (`params do ... end`) only validates types/presence of `action`, `team.id/name/slug/url`, `organization.login`, `member.login` — it does not constrain `team.id` to a value the requesting org actually owns [6](#0-5) . `Team` has no uniqueness/ownership validation tying `github_id` to `organization` beyond the model-level `has_many :github_hooks` scoping used for hook delivery, not membership handling [7](#0-6) .

**Impact caveat (must be validated at implementation time):** exploitation strictly requires that a `Team` row with the guessed `github_id` already exists in Shipit's database (created previously via legitimate sync, e.g. `Team.find_or_create_by_handle`, `github_teams`, or a prior legitimate `membership` webhook) *and* that this team is one of the entries referenced by `Shipit.github_teams` (the configured authorization teams) at the moment `User#authorized?` is evaluated, since `authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?` [8](#0-7) . `Shipit.github_teams` is computed from `github.oauth_teams` for the *currently configured default organization*'s GitHub App and resolved via `Team.find_or_create_by_handle` [9](#0-8) , meaning a Team eligible for authorization is very likely to already exist as a persisted row with a real `github_id`, which the attacker only needs to know or guess (GitHub team IDs are visible via the GitHub API/UI for public org teams, or brute-forceable as small sequential integers).

### Impact Explanation
If a pre-existing `Team` row backing `Shipit.github_teams` exists (which is the normal steady-state for any Shipit install using team-based authorization), an attacker with no Shipit credentials and no privileged GitHub role — only ownership of *any* GitHub organization they can enable a Shipit App/webhook config for — can add an arbitrary GitHub login (including their own) as a `member` of that victim `Team`. Combined with `User#authorized?`, this grants that user full authenticated access to the Shipit instance [8](#0-7) . This is a cross-tenant authorization escalation: one organization's legitimately-signed webhook is used to mutate state belonging to a different, unrelated organization/team. Severity matches "High - escalation into `Shipit.github_teams` authorization" per the given rubric; it could reach Critical if the compromised team also grants deploy/merge rights on stacks. The attack is repeatable for any known/guessable `team.id` and any number of `member.login` values per request.

### Likelihood Explanation
Preconditions: (1) multi-org Shipit deployment where the attacker legitimately controls at least one configured GitHub org/App with its own `webhook_secret` (satisfiable by any GitHub user who can create an org and install the Shipit GitHub App per documented setup — no Shipit secret needed); (2) a `Team` row for the victim org/team must already exist in Shipit's DB with a known/guessable `github_id`. GitHub team IDs are sequential integers and are exposed via GitHub's REST/GraphQL API and UI for teams the attacker can view (public org team pages expose numeric IDs in many contexts, or an attacker could have been a member previously). Attacker cost is low: register/own a GitHub org, configure the webhook endpoint to point at the target Shipit host (feasible since organization-level GitHub webhooks are attacker-configurable within their own org), and send one crafted `membership` payload. This is repeatable and requires no live GitHub API access to reproduce in tests, only a correctly computed `X-Hub-Signature`.

### Recommendation
In `MembershipHandler#find_or_create_team!`/`#process`, reject or ignore membership events where the found (or about-to-be-created) `Team#organization` does not equal the verified `params.organization.login` from this request — e.g., scope the lookup as `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` (or explicitly raise/no-op if an existing record's `organization` mismatches) before calling `team.add_member`/`team.members.delete`. Additionally, consider passing the already-verified `repository_owner` from the controller into the handler instead of trusting `params.organization.login` a second time, and enforce it against the persisted `Team#organization`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "membership webhook from org B cannot add members to org A's team" do
  victim_team = Shipit::Team.create!(github_id: 4242, name: 'core', slug: 'core',
                                      api_url: 'https://api.github.com/teams/4242',
                                      organization: 'victim-org')
  Shipit.stubs(:github_teams).returns([victim_team])

  attacker_login = 'attacker-user'
  payload = {
    'action' => 'added',
    'team' => { 'id' => victim_team.github_id, 'name' => 'core', 'slug' => 'core', 'url' => victim_team.api_url },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => attacker_login }
  }

  # verify_signature succeeds because it's signed with attacker-org's own webhook_secret
  Shipit::Webhooks::Handlers::MembershipHandler.call(Shipit::Webhooks::Handlers::MembershipHandler.new.send(:params_class).new(payload))

  attacker_user = Shipit::User.find_by!(login: attacker_login)
  # Binding under test: attacker-org == organization owning victim_team? -> false
  assert_not_equal 'attacker-org', victim_team.reload.organization
  # Yet membership mutation succeeded across the boundary:
  assert_includes victim_team.members.reload, attacker_user
  assert attacker_user.authorized?
end
```
This demonstrates the equality `verified_organization == team.organization` is false (`'attacker-org' != 'victim-org'`) both before and after the call, yet `team.add_member` still executes and grants `authorized?`, confirming the vulnerability.
