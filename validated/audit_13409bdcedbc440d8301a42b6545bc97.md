The reported issue is a classic "pure front-running / economic race" bug class: a permissionless funder can withdraw (`refundDeposit`) their contribution right before a claim finalizes, leaving the claimant with nothing. Per the scan methodology, this class of finding — "pure front-running/economic attacks" — is explicitly excluded (see rejection criterion 5).

I looked for a structurally analogous mechanism in the Polkadot SDK (any place where a permissionless funder/contributor can withdraw a deposit that is expected to back a payout to a third-party beneficiary, racing the payout):

- `pallet-bounties`: funds for a bounty are provisioned exclusively via Treasury spend approval, not by permissionless third-party "funders" who can request an arbitrary refund whenever they choose. Once a bounty is `Active`/`PendingPayout`, there's no path for an outside contributor to reclaim the bounty value before `claim_bounty` executes — the balance transfer in `claim_bounty` simply reads whatever balance is present in the bounty account at call time [1](#0-0) , and there is no funder-initiated "refund" call analogous to `refundDeposit`.
- `pallet-child-bounties::claim_child_bounty` has the same shape — no third-party refundable funding step exists between award and claim [2](#0-1) .
- The crowdloan pallet (`polkadot/runtime/common/src/crowdloan/mod.rs`) does have contributor-initiated `withdraw`/`refund` calls [3](#0-2) , but these are only permitted once the crowdloan has ended/failed (`ensure_crowdloan_ended`), and there is no separate "claim by a beneficiary" step racing against it — the same account that contributed is the one being refunded, so there's no analog of a claimant losing an already-owed reward to a funder's front-run withdrawal.

Since no genuine FRAME/XCM path reproduces "funder unilaterally revokes backing funds moments before a legitimately entitled claimant's payout, causing that claimant to receive nothing," and the underlying bug class is explicitly excluded as a pure economic/front-running scenario, there is no qualifying analog to report.

		/// In this case, the fund's retirement flag is set and its `end` is reset to the current

		///
		/// - `who`: The account whose contribution should be withdrawn.
		/// - `index`: The parachain to whose crowdloan the contribution was made.
		#[pallet::call_index(2)]
		#[pallet::weight(T::WeightInfo::withdraw())]
		pub fn withdraw(
			origin: OriginFor<T>,
			who: T::AccountId,
			#[pallet::compact] index: ParaId,
		) -> DispatchResult {
			ensure_signed(origin)?;

			let mut fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let now = frame_system::Pallet::<T>::block_number();
			let fund_account = Self::fund_account_id(fund.fund_index);
			Self::ensure_crowdloan_ended(now, &fund_account, &fund)?;

			let (balance, _) = Self::contribution_get(fund.fund_index, &who);
			ensure!(balance > Zero::zero(), Error::<T>::NoContributions);

			CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
			CurrencyOf::<T>::reactivate(balance);

			Self::contribution_kill(fund.fund_index, &who);
			fund.raised = fund.raised.saturating_sub(balance);

			Funds::<T>::insert(index, &fund);

			Self::deposit_event(Event::<T>::Withdrew { who, fund_index: index, amount: balance });

		}
