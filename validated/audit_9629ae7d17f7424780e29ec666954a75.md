### Title
API token stack-scope bypass in CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` restricts a stack-scoped `ApiClient` to only the stack it was assigned to via a scoped `stacks` relation, but `Shipit::Api::CCMenuController` overrides `#stack` to bypass that scope, letting any valid `ApiClient` token read CCMenu build status for stacks it was never authorized to access.

### Finding Description
`Api::BaseController` defines the authorization-scoping primitive that every other API controller in the engine relies on: [1](#0-0) 

`stacks` restricts the visible set of stacks to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to one, and `stack` resolves `params[:stack_id]` against that restricted relation. This is the binding the engine relies on: **stack a token authorizes == stack a request is allowed to touch**.

`Api::CCMenuController` breaks this binding. It overrides `#stack` to resolve directly against the unscoped `Stack` model instead of the scoped `stacks` helper: [2](#0-1) 

The controller's only authorization gate is a generic permission string check via `require_permission :read, :stack`, which only calls `current_api_client.check_permissions!(operation, scope)`: [3](#0-2) 

`check_permissions!` verifies that the `ApiClient` has the `"read:stack"` permission string in its `permissions` array — it never checks `stack_id`. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing `stacks.from_param!`), an `ApiClient` created with a restrictive `stack_id` (as shown in the fixture below) is authorized only by permission name, not by the stack it was provisioned for: [4](#0-3) 

Before the request (equality that should hold): `token.authorized_stack_id == params[:stack_id]` for every stack-scoped endpoint.
After using `CCMenuController#show`: `token.authorized_stack_id != params[:stack_id]` is accepted, because `stack` resolves through `Stack.from_param!` (global) rather than `stacks.from_param!` (scoped to `current_api_client.stack_id`).

`#show` then renders build/deploy state for whatever stack was requested: [5](#0-4) 

This directly contradicts the pattern followed everywhere else in the same namespace, e.g. `Api::StacksController`, which relies on the scoped `stack`/`stacks` helpers from `BaseController` and is correctly restricted, as exercised by its own test suite: [6](#0-5) 

### Impact Explanation
An `ApiClient` token that was deliberately scoped to a single stack (e.g. `here_come_the_walrus`, scoped to `shipit` and holding only `read:stack`) can be used against `Api::CCMenuController#show` with an arbitrary `stack_id` belonging to a different stack it was never granted access to. This yields unauthenticated (with respect to that stack)/unauthorized read of stack build state — the stack's name, last build status, last build label/time, web URL, and whether it is locked. This matches the engine's own High-impact bucket: "escalation into `Shipit.github_teams` authorization, unauthenticated read of stack state, task streams or deploy output." A supposedly least-privilege, stack-scoped credential effectively becomes a global read-access credential for this one endpoint, defeating the entire purpose of `ApiClient.stack_id` scoping.

### Likelihood Explanation
The only prerequisite is possession of any valid `ApiClient` authentication token with `read:stack` permission — this is the same class of credential the engine already expects external CI/monitoring tools (CCMenu clients) to hold, and is exactly the kind of narrowly-scoped credential operators are encouraged to issue via `stack_id`. No privileged account, session, or additional secret is required beyond the token itself, and the bypass is a single unauthenticated (from the app's perspective, unscoped) GET request with a different `stack_id` — trivial and reliable to trigger.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped resolution already provided by `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
i.e. remove the private override entirely and let it inherit `BaseController#stack`, which honors `current_api_client.stack_id` scoping. Add a regression test asserting that a stack-scoped `ApiClient` (`here_come_the_walrus`) receives a 404/`RecordNotFound` when requesting `stack_id` of a stack outside its scope via the CCMenu endpoint, mirroring the existing scoping test in `Api::StacksControllerTest`.

### Proof of Concept
1. Seed two stacks: `shipit_stacks(:shipit)` and any other stack, e.g. `shipit_stacks(:soc)` (or `Repository`/`Stack.create!` as in the existing test file).
2. Create/use the fixture `ApiClient` `here_come_the_walrus`, which is scoped to `stack: shipit` and only has `permissions: ['read:stack']`.
3. Authenticate as `here_come_the_walrus` and issue:
```ruby
get :show, params: { stack_id: shipit_stacks(:soc).to_param, token: @client.authentication_token }
```
4. Expected (secure) behavior: 404 / not found, because the token is scoped to `shipit`, not `soc`.
5. Actual behavior: `200 OK` with the `soc` stack's CCMenu XML (name, lastBuildStatus, lastBuildLabel, lastBuildTime, webUrl), because `Api::CCMenuController#stack` calls `Stack.from_param!` unscoped instead of `stacks.from_param!`, and `require_permission :read, :stack` only checks the permission string, not `stack_id`.

This can be directly confirmed against the existing test in `test/controllers/api/ccmenu_controller_test.rb`, which authenticates with the default (unscoped) `@client` and never exercises the `here_come_the_walrus` scoped fixture against a foreign `stack_id` — the missing negative test is itself evidence the scoping bypass is untested and unguarded.
