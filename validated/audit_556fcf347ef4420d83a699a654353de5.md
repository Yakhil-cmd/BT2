### Title
Webhook signature verification keys off attacker-controlled `repository.owner.login`/`organization.login` while handlers act on the independent `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-GitHub-App Shipit deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each GitHub organization has its own `webhook_secret`. `WebhooksController#verify_signature` selects *which* secret to validate the HMAC against using a field taken directly from the untrusted JSON body, while the event handlers that actually mutate state select *which repository/stack to act on* using a completely different field from the same body. Nothing binds these two fields together, so a request signed with organization A's secret can carry a payload whose "target" repository belongs to organization B.

### Finding Description
`verify_signature` computes the organization used to pick the `GitHubApp`/secret purely from request body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves this attacker-supplied string to a specific `GitHubApp` config/secret: [3](#0-2) 

`GitHubApp#verify_webhook_signature` then only proves that *some* secret configured for *some* organization named by the attacker matches the HMAC of the raw body — it does not prove anything about which repository the payload's data will be applied to: [4](#0-3) 

Meanwhile every handler (`Handler#stacks`/`#repository_name`, and concrete handlers like `PushHandler`) determines the repository/stack to write to from `repository.full_name` — a sibling field in the same payload, never cross-checked against the field used for verification: [5](#0-4) [6](#0-5) 

This is the same bug class as the DAI report: the verified/authenticated attribute (`repository.owner.login` / `organization.login`, used to select the signing secret) is not the attribute that is actually acted upon (`repository.full_name`, used to select the write target). The binding that should hold — `verified_organization(payload) == owner(target_repository_written(payload))` — is never enforced. Since the request body itself is fully attacker controlled (the endpoint accepts any raw POST as long as *a* valid signature for *the org named inside that same POST* is presented), an actor who knows/controls the webhook secret for organization A (e.g., a tenant admin in a multi-org deployment, or anyone able to author org A's GitHub App config) can craft:
```json
{ "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/victim-repo" }, "ref": "refs/heads/main", "after": "<sha>" }
```
sign it with org A's `webhook_secret`, and POST it to `/webhooks`. `verify_signature` succeeds (org A's secret matches), but `PushHandler` (or any other handler: `status`, `check_suite`, `pull_request`, `membership`, etc.) operates on `org-b/victim-repo`, which belongs to a completely different, unrelated GitHub organization/tenant tracked by the same Shipit instance.

### Impact Explanation
This breaks the repository/organization trust boundary between tenants of a single Shipit instance configured with multiple GitHub Apps. An attacker who legitimately controls only organization A's webhook credentials can:
- Force `GithubSyncJob` to run against organization B's stacks (`PushHandler`), influencing what Shipit believes is deployable/undeployed for a repo it doesn't own.
- Forge commit statuses, check-run refresh triggers, membership/team changes, or pull-request-driven review-stack archive/unarchive/merge actions for organization B's repositories, since every handler trusts `repository.full_name` from the same unverified-binding payload.
This is a cross-repository/cross-organization write achieved without any credential belonging to the victim organization, matching the "cross-repository writes" / unauthorized state-changing action impact bucket.

### Likelihood Explanation
Requires an attacker to know the webhook secret of at least one organization configured in the same multi-tenant Shipit deployment (a realistic scenario per `docs/setup.md`'s documented multi-org secrets layout, where each org's secret is a separate, independently-managed credential) and to be able to send raw HTTP POSTs to the public `/webhooks` endpoint — no `ApiClient` token, GitHub App private key, or victim-organization credential is needed. This is a plausible, unprivileged-relative-to-the-victim-org attack path given the documented multi-org feature.

### Recommendation
Bind the signature-selection field to the field the handlers actually act on: verify the signature using the organization/app derived from `repository.full_name`'s owner segment (or explicitly require and check that `repository.owner.login` equals the owner segment of `repository.full_name`) before dispatching to handlers, rejecting payloads where they diverge.

### Proof of Concept
1. Deploy Shipit with the multi-org GitHub App configuration (`secrets.github.org-a`, `secrets.github.org-b`), each with a distinct `webhook_secret`, per `docs/setup.md`.
2. As someone who knows org-a's `webhook_secret` (e.g., the person who provisioned org-a's GitHub App), craft a JSON push payload:
   ```json
   {
     "ref": "refs/heads/main",
     "after": "<attacker-chosen-sha>",
     "repository": { "owner": {"login": "org-a"}, "full_name": "org-b/victim-repo" }
   }
   ```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(org-a-webhook-secret, body)>` and POST it to `/webhooks` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"org-a"`, fetches org-a's `GitHubApp`, and the HMAC check passes (attacker knows org-a's secret) — response is not `422`.
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which loads `Repository.from_github_repo_name("org-b/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on org-b's stack — an action the attacker triggered using only org-a's credentials.

```ruby
    # Backward compatibility

    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?

    @github[organization] ||= GitHubApp.new(organization, config)
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
