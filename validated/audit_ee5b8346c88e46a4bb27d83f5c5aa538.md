### Title
Cross-repository status webhook triggers `stack.schedule_merges` on a victim's stack via unscoped SHA lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commits to update purely by `Commit.where(sha: params.sha)`, with no filter on the repository from the webhook payload. Since git commit SHAs are content-addressed, an attacker who forks a victim's public repository and pushes a status for a commit whose content is identical to the victim's PR head commit (same sha, same signature-verified attacker-owned repo) can trigger `Commit#create_status_from_github!` → `Commit#add_status` → `stack.schedule_merges` on the victim stack.

### Finding Description
The binding that should hold is: `commit.stack.repository == payload.repository` for every commit updated by `StatusHandler#process`. In the actual code: [1](#0-0) 

`process` does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — there is no join or filter against the webhook's `repository` field or `repository_owner`. This means any `Commit` row anywhere in the Shipit install sharing that sha is updated, regardless of which stack/repository it belongs to.

`verify_signature` in the controller only selects which GitHub App/HMAC secret to validate against, keyed off `repository_owner` of the payload: [2](#0-1) 

It authenticates that "a webhook genuinely came from repository X", but does not restrict which `Commit`/`Stack` records the handler is allowed to touch. So a correctly-signed webhook from an attacker's own repository (X = attacker's repo) is accepted and dispatched to `StatusHandler`, which then looks up commits by raw `sha` with no `stack_id`/`repository` scoping.

`Commit#add_status` then runs: [3](#0-2) 

`stack.schedule_merges if new_status.pending? || new_status.success?` executes on whatever stack owns the matched commit — the victim's stack — even though the webhook payload's repository was the attacker's.

Exploit flow:
1. Attacker forks (or otherwise obtains a copy of) the victim's public repository so that git object content — and therefore the commit sha — is identical between the attacker's fork and the victim's repo (this is inherent to git's content-addressed SHA-1/SHA-256 hashing, not a Shipit bug by itself).
2. Victim stack has an open, CI-pending `MergeRequest` whose head commit sha equals that shared sha.
3. Attacker triggers (or crafts) a `status` webhook from their own repository for that sha with `state: success`, correctly signed via `Shipit.github(organization: attacker_org)` since it's their own repo/org.
4. `WebhooksController#verify_signature` passes (valid signature for the attacker's own repository).
5. `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler#process`, which does `Commit.where(sha: params.sha)` — matching the victim's `Commit` row too — and calls `create_status_from_github!` on it.
6. `add_status` records the forged success status on the victim's commit and calls `stack.schedule_merges` for the victim's stack, enqueuing `ProcessMergeRequestsJob` for a stack the attacker doesn't own and never authenticated against.

None of the existing guards prevent this: `verify_signature` validates *that a repo owner signed something*, not *which records that repo may affect*; `drop_unhandled_event` only checks the event type is handled; there is no `ExplicitParameters` field or model validation tying `Commit` lookup to `params.dig('repository', 'full_name')`.

### Impact Explanation
A payload correctly authenticated for the attacker's own (unrelated) repository causes state mutation (`Status` creation) and a merge-queue processing job (`ProcessMergeRequestsJob`) to be enqueued for a victim stack/repository the attacker does not control. This matches the "payload for one repository mutating another's stack, commit, task or team" / "unauthorized merge" Critical category: it can push a stalled/pending merge request through the merge queue based on a status the attacker fabricated from their own account, without any privilege on the victim's repository, team, or Shipit instance.

### Likelihood Explanation
Preconditions: (a) the victim stack must have a pending `MergeRequest` whose head commit sha is present as a `Commit` row (normal state for any queued PR), and (b) the attacker must be able to produce a commit with an identical sha in a repository they control and can emit correctly-signed webhooks for (trivial for public repos: fork + reuse the exact same commit, or craft a commit with byte-identical content/parents/timestamps). No secrets, tokens, or team membership are required — only ownership of a fork/repo and the ability to fire a `status` webhook (e.g., via GitHub Actions or the GitHub API on their own repo). This is highly feasible and repeatable against any repository/stack in the Shipit installation as long as a matching sha can be produced.

### Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalently in `check_suite_handler.rb`/`push_handler.rb` if they have the same pattern) to the repository identified in the webhook payload, e.g. join to `Stack` and filter by `stack.repository.full_name == params.dig('repository', 'full_name')` (or the equivalent repository owner/name fields) before updating statuses or calling `create_status_from_github!`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook only updates commits belonging to the payload's repository" do
  victim_stack = shipit_stacks(:shipit)
  attacker_stack = shipit_stacks(:cyclimse) # any other repo's stack

  shared_sha = "a" * 40
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "victim PR head")
  merge_request = victim_stack.merge_requests.create!(number: 42, head_sha: shared_sha, state: 'pending')

  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci',
    'repository' => { 'full_name' => attacker_stack.github_repo_name, 'owner' => { 'login' => attacker_stack.repository.owner } }
  }

  assert_no_enqueued_jobs(only: ProcessMergeRequestsJob) do
    Shipit::Webhooks::Handlers::StatusHandler.new(nil, payload).process
  end

  assert_not victim_commit.reload.statuses.exists?(context: 'ci')
end
```
Before the fix, this assertion fails: `victim_commit` receives the forged status and `ProcessMergeRequestsJob` is enqueued for `victim_stack`, proving the binding `commit.stack.repository == payload.repository` is violated.
