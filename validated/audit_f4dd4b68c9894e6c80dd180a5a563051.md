## Title
Panic-inducing state divergence in `Stakes::sub_delegated_stake` via `expect()`-based invariant checks on cached delegated stake - ([File: runtime/src/stakes.rs])

## Summary
The reported INIT-Capital bug is caused by an accounting function that assumes an accrued value only increases and therefore performs an unchecked/unsaturated subtraction, which reverts when an unprivileged actor (via ordinary protocol actions, e.g. a partial liquidation) causes the value to change out of the expected direction. The closest analog in this repository is `Stakes::sub_delegated_stake` in `runtime/src/stakes.rs`, which encodes the same "monotonic assumption + hard failure on violation" pattern, but here the hard failure is a Rust `panic!` via `.expect(...)` inside validator-critical stake-cache bookkeeping rather than a reverted transaction.

## Finding Description
`sub_delegated_stake` is used to keep `Stakes::delegated_stakes` (the in-memory cache of "current effective stake per vote account") consistent whenever a stake delegation is removed or changed via `remove_stake_delegation` and `upsert_stake_delegation`: [1](#0-0) 

Both call sites compute an `old_stake` / `removed_stake` value via `delegation_effective_stake(...)` at "removal time" and then subtract that computed value from the cached aggregate: [2](#0-1) [3](#0-2) 

The invariant these call sites depend on is that the "effective stake" value computed for a given delegation at insert-time and the value computed again at removal/update-time are consistent with what was actually added into `delegated_stakes` previously — i.e., the accounting implicitly assumes that recomputing `delegation_effective_stake` for the *same* logical delegation yields a value that was already reflected in the cache (so the aggregate can never be exceeded, mirroring `POS_MANAGER`'s assumption that `debtShareToAmtCurrent` only rises). If any code path stores/removes a stake account and the effective-stake computation diverges between the two calls (e.g. due to a stake-history/epoch/feature-flag mismatch, warmup/cooldown math change, or any accounting update that reduces the delegated amount attributed to a voter between insertion and removal), `current_stake.checked_sub(stake)` returns `None`, and the `.expect("subtraction value exceeds delegated stake")` unconditionally panics the process. Similarly, `.expect("subtraction from missing delegated stake")` panics if the voter entry was already removed/never added, which is a related divergence pattern from the same assumption.

This is structurally identical to the INIT `POS_MANAGER` issue: an accounting field is maintained by incremental add/subtract operations that trust a recomputed value to be consistent with a previously-cached value, and the "unexpected direction" case is handled by an unconditional failure (`revert` in Solidity/`panic!` in Rust) instead of a saturating/defensive correction.

## Impact Explanation
`Stakes` is the runtime's core delegated-stake bookkeeping structure used for leader schedule, vote-account weighting, and rewards — a panic here is a node-crashing bug, not a benign error path. Because `StakesCache` updates are driven directly by ordinary, unprivileged account-update processing (`check_and_store` on stake account writes caused by user transactions such as delegate/split/merge/deactivate/withdraw), an invariant violation reachable by normal user-submitted stake instructions would cause validators to panic while replaying/executing the same block, which (depending on how widely the divergent input propagates across the cluster) risks a cross-node crash or halt condition rather than a mere logic error, since Rust `panic!`/`expect()` in bank-execution code aborts the validator process.

## Likelihood Explanation
This is a lower-confidence analog than a directly reproducible vulnerability. I could not find a concrete transaction sequence in the code available to me (given index-size limits) that provably makes `delegation_effective_stake` diverge between the "add" and "subtract" calls for the same delegation record under current logic — the two computations use the same `stake_history`/`epoch`/`use_fixed_point_stake_math` values read from the same `Stakes` snapshot, and `imbl::HashMap::insert` returns the previous value being subtracted, which appears self-consistent in the paths I reviewed. The panic conditions look like they are intended as debug/sanity invariants for developer errors (e.g., a future code change breaking the accounting), rather than an unprivileged-user-triggerable condition today. I was not able to fully trace all callers/feature-flag transition boundaries (e.g. `use_fixed_point_stake_math` flipping between snapshot load and live update, or epoch-boundary refreshes) that could plausibly desynchronize the two `delegation_effective_stake` computations for the same stake account, due to the scope and size limits of the available index.

## Recommendation
Given the uncertainty above, I am not confident enough in a concrete, reachable unprivileged-user trigger to assert this as a validated finding. Recommend that a Devin session with full repository access:
1. Audit all call sites of `upsert_stake_delegation`/`remove_stake_delegation`/`check_and_store` for any path where `stake_history`, `epoch`, or `use_fixed_point_stake_math` could differ between the moment a delegation's stake was added to `delegated_stakes` and the moment it is later subtracted (e.g., across an epoch boundary, feature activation boundary, or snapshot-load vs. live-update code paths).
2. If such a path exists and is reachable via ordinary stake-program instructions (split/merge/delegate/deactivate/withdraw) without requiring a validator/operator role, treat it as a confirmed panic-based DoS and change `sub_delegated_stake` to use `saturating_sub` (mirroring the INIT-Capital fix of updating the assumption instead of reverting) with logging/metrics on the mismatch instead of `expect()`-panicking the process.
3. If no such divergence is reachable, this should be treated as a defense-in-depth hardening item (replace developer-invariant panics with saturating arithmetic plus telemetry) rather than a security finding.

## Proof of Concept
No concrete, unprivileged-user-triggerable proof of concept was established with the available tools/index. The analysis above identifies the structurally analogous code (`sub_delegated_stake`'s `.expect()`-based subtraction on a value assumed to always match a previously cached "effective stake" quantity) but I could not confirm a call sequence, using only in-scope stake/vote instruction handlers, that forces `delegation_effective_stake` to diverge between the add and subtract computations for the same delegation record.

    fn sub_delegated_stake(&mut self, voter_pubkey: &Pubkey, stake: u64) {
        if stake == 0 {
            return;
        }
        let current_stake = self
            .delegated_stakes
            .get_mut(voter_pubkey)
            .expect("subtraction from missing delegated stake");
        *current_stake = current_stake
            .checked_sub(stake)
            .expect("subtraction value exceeds delegated stake");
        if *current_stake == 0 {
            self.delegated_stakes.remove(voter_pubkey);
        }
    }
