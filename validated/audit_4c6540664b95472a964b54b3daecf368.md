### Title
Asset definer can permanently freeze already-held funds of a `spender_attested` asset by rotating the attestor list, with no override for existing holders - (File: validation.js)

### Summary
For assets defined with `spender_attested: true`, every payment (transfer or issue) requires that the input owner and output addresses appear in the asset's *current* attestor list. The attestor list can be overwritten at any time by the asset definer via an `asset_attestors` message, and validation only ever consults the single latest such list. If the definer publishes a new list that drops an existing holder (or a holder's attesting attestor), that holder's already-issued balance becomes permanently unspendable — there is no closing/liquidation-style override, mirroring the `collateralPaused`/`collateralValid` coupling described in the H-6 report where a single admin-controlled flag blocks any exit path for existing holders of value.

### Finding Description
When an asset has `spender_attested: true`, `validatePayment` requires the issuer/authors to be attested before a payment is even considered further: [1](#0-0) 

For divisible/base-style payments, `validatePaymentInputsAndOutputs` additionally requires that the *owner address of every spent input* be in `objAsset.arrAttestedAddresses`, and that every output address be attested: [2](#0-1) [3](#0-2) 

The attestor list itself is fully controlled by the asset definer via `validateAttestorListUpdate`, which only checks that the author is the `definer_address` and that the new list is well-formed — there is no restriction preventing the definer from dropping previously valid attestors/attested addresses: [4](#0-3) 

Crucially, `storage.readAsset` resolves the "current" attestor list as the single most-recent `asset_attestors` unit (`ORDER BY level DESC LIMIT 1`), i.e., only the latest list counts — older attestations are not accumulated or grandfathered: [5](#0-4) 

`filterAttestedAddresses` then checks whether an address's attestation was issued by one of the *current* `arrAttestorAddresses`, again only against the latest attestor set: [6](#0-5) 

Consequently, an asset holder who received/held coins while attestor list A was active can be locked out entirely if the definer later publishes list B that removes the attestor who vouched for that holder (or removes the holder's address from any acceptable attestation chain). Every subsequent attempt by that holder to spend their existing balance — whether to transfer it away or send it back to the definer — will fail `"owner address is not attested"` (validation.js:2506) or `"some output addresses are not attested"` (validation.js:2637), with no bypass such as a "closeLoan"-equivalent operation. This is structurally identical to the H-6 pattern: a single privileged state change (pausing collateral / rotating the attestor list) blocks all further movement of already-committed value, with no unwind path for the affected party.

### Impact Explanation
Holders of a `spender_attested` asset can have their existing, legitimately-acquired balances permanently frozen by a single action of the asset definer (an `asset_attestors` unit), with no mechanism in the protocol to reclaim or move the frozen funds. This is a concrete freezing of user funds analogous to the "outstanding loans cannot be closed" impact in the source report — it results in real economic loss/lock-up of user funds, not merely denial of new activity. Because the entire evaluation is deterministic and consensus-level (part of unit validation), this is a protocol-level fund-freezing issue, not merely an inconvenience of one client.

### Likelihood Explanation
This requires the involvement of an asset definer who is by design privileged to update the attestor list for their own asset (this is intended asset-issuer functionality, not a compromised admin). However, since the source report is itself about a similarly "intended" governance/pause action (pausing collateral) causing an unrecoverable freeze, the same reasoning applies here: the protocol provides no safeguard or exit path once a legitimate governance-type action (attestor rotation) removes a holder's eligibility, which was reachable by design any time the definer issues an `asset_attestors` message, without needing any exceptional or malicious node behavior.

### Recommendation
Provide holders of previously-attested balances a way to exit even after the attestor list changes, for example by:
- Grandfathering attestations that were valid at the time the balance was received/attested (evaluate against the attestor list valid at issuance/last-transfer time rather than only the very latest list), or
- Adding an explicit unwind/return-to-definer path in `validatePaymentInputsAndOutputs` that does not require current attestation when the destination is the asset definer, analogous to allowing `closeLoan`/`callLiquidation` to bypass `collateralValid`.

### Proof of Concept
1. Definer creates asset `X` with `spender_attested: true` and initial attestor list `[A]`.
2. Attestor `A` attests address `H`; holder `H` receives/holds a balance of asset `X` (validated successfully per `validatePayment`/`validatePaymentInputsAndOutputs`).
3. Definer publishes an `asset_attestors` message changing the list to `[B]` (dropping `A`) — accepted by `validateAttestorListUpdate` since only definer-authorship and list well-formedness are checked (`validation.js:2829-2864`).
4. `storage.readAsset` now resolves `arrAttestorAddresses = [B]` only (`storage.js:1917-1945`), and `H`'s attestation (issued by `A`) is no longer counted by `filterAttestedAddresses` (`storage.js:1959-1974`).
5. Any subsequent payment spending `H`'s existing output of asset `X` fails validation with `"owner address is not attested"` (`validation.js:2506`), and any attempt to move it — including back to the definer — likewise fails the output-side attestation check (`validation.js:2637`), permanently freezing `H`'s balance.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],

			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });
