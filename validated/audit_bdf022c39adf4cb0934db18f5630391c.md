### Title
Cross-tenant commit-status forgery via unscoped `StatusHandler` lookup enables unauthorized merges - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` authenticates a webhook payload against the GitHub App belonging to the **organization named in the payload itself** (`repository.owner.login`), then hands the raw payload to whichever `Handler` is registered for the event. For the `status` event, `StatusHandler#process` ignores the repository entirely and updates **any** commit in the database whose `sha` matches the payload, regardless of which organization/stack that commit actually belongs to. This breaks the binding "organization that authenticated == repository that is written," letting a legitimately-configured but unrelated organization push a forged CI status onto another organization's commit and trigger an unauthorized merge/deploy.

### Finding Description
`WebhooksController#verify_signature` selects the verifying `GitHubApp` using `repository_owner`, which is read straight out of the unsigned-until-verified JSON body (`params.dig('repository','owner','login')`): [1](#0-0) [2](#0-1) 

This only proves the payload was signed by *some* organization configured in Shipit's multi-org setup (a documented, supported configuration where distinct GitHub Apps/organizations each get their own `webhook_secret`): [3](#0-2) 

Every handler is supposed to scope its side effects to the repository named in the payload. The base `Handler` class exposes exactly that helper: [4](#0-3) 

`PushHandler` and `CheckSuiteHandler` correctly use it: [5](#0-4) [6](#0-5) 

`StatusHandler`, however, looks the commit up **globally**, with no repository/stack scoping at all: [7](#0-6) 

`Commit.where(sha: params.sha)` matches by SHA alone across every stack in the whole Shipit instance. `create_status_from_github!` then updates that commit's status and, through `add_status`, can flip `simple_state` to success/failure, which schedules merges and toggles deployability for the corresponding stack: [8](#0-7) 

So the equality that should hold — *organization verified by signature == repository whose commit/stack state is mutated* — is never enforced. Only the `sha` value, an attacker-controllable field never bound to organization identity, decides which stack is affected.

### Impact Explanation
Git commit SHAs are content-addressed and identical across forks/mirrors of the same history. In a multi-organization Shipit deployment (an explicitly documented setup), an organization admin/maintainer for Org A — who legitimately holds Org A's own GitHub App webhook secret and therefore always passes `verify_signature` — can fork or mirror a public repository that another tenant, Org B, tracks in the same Shipit instance. By creating a commit status via the GitHub API on their own fork/repo for a SHA that is shared with Org B's tracked history, GitHub sends Shipit a correctly-signed `status` webhook for Org A. `StatusHandler` then finds and mutates the commit belonging to Org B's stack, potentially forcing it to `success`, which triggers `stack.schedule_merges` and unblocks/allow deploys for a commit that never actually passed Org B's CI. This is an unauthorized-merge/deploy primitive achievable without ever touching Org B's credentials, satisfying the Critical "unauthorized deploy, rollback or merge" impact bucket.

### Likelihood Explanation
Requires a Shipit instance configured for multiple GitHub organizations (a supported, documented configuration) and a shared commit history between the attacker-controlled org's repo and the victim org's tracked repo (fork/mirror of a public project). Given those preconditions the exploit needs no privileged Shipit credentials — only ordinary GitHub API access to set a status on a repo the attacker controls.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to commits belonging to `stacks` (i.e., `Repository.from_github_repo_name(payload.dig('repository','full_name'))`), and require/validate the `repository` field in `StatusHandler`'s `params` block so a status can only be applied to commits within the repository the verified webhook signature actually attests to.

### Proof of Concept
1. Configure Shipit for two organizations, `org-a` and `org-b`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`'s multi-org instructions).
2. Org B tracks `github.com/upstream/project`; Shipit has ingested commit `abc123...` into a stack for that repo.
3. The attacker (an admin of `org-a`, with no access to Org B) forks/mirrors `upstream/project` into `org-a/project`, which retains the identical commit `abc123...`.
4. Using the GitHub API against `org-a/project`, the attacker sets a `success` status on commit `abc123...`.
5. GitHub sends a `status` webhook to Shipit, signed with `org-a`'s webhook secret; `WebhooksController#verify_signature` resolves and verifies against `Shipit.github(organization: 'org-a')` and succeeds.
6. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, matches Org B's commit, and calls `create_status_from_github!`, flipping the commit to `success` and triggering `stack.schedule_merges` for Org B — despite the request never having been signed by, nor scoped to, Org B.

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
