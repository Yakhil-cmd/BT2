### Title
Webhook signature is verified against the payload's `repository.owner.login`, but event handlers act on the independently-controlled `repository.full_name` field — allowing cross-organization webhook forgery in multi-org Shipit deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the *same* JSON body it is trying to authenticate. Once the signature check passes, `WebhooksController#create` dispatches the *entire* payload to event handlers (e.g. `PushHandler`), which independently resolve the target `Repository`/`Stack` using `repository.full_name`. Nothing ties the "owner" used to pick the signing secret to the "full_name" used to pick the acted-upon repository, so in a multi-organization Shipit configuration, a valid signature computed with Org A's `webhook_secret` can be replayed with a body whose `repository.full_name` points at Org B's repository, causing Shipit to act (sync commits, potentially trigger continuous deployment) on a stack the forger has no relationship to.

### Finding Description
`Shipit.github(organization:)` supports hosting several independent GitHub Apps/organizations from one Shipit instance, each with its own `webhook_secret`, configured under distinct top-level keys in `secrets.yml`. [1](#0-0) [2](#0-1) 

`WebhooksController#verify_signature` derives the organization used to look up the verification secret purely from attacker-supplied payload fields:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

After the signature check passes, the full raw payload — including its `repository.full_name` — is forwarded unchanged to handlers:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Handlers such as `PushHandler` resolve the target `Stack`(s) not from `repository.owner.login`, but from `repository.full_name`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 
```ruby
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [6](#0-5) 

The binding that should be enforced — "the organization whose secret authenticated this webhook" == "the organization that owns the repository being acted on" — is never checked. `repository.owner.login` and `repository.full_name` are two independent fields inside the same signed JSON body; the signature only proves the body wasn't tampered with by a third party who doesn't know the secret for the org named in `owner.login`, it proves nothing about consistency between `owner.login` and `full_name`. Anyone who legitimately administers (and thus knows the `webhook_secret` of) any one of the organizations configured in this Shipit instance can craft a payload naming their own org as `repository.owner.login` (so the correct secret is picked and the HMAC validates) while setting `repository.full_name` to `victim-org/victim-repo`.

### Impact Explanation
`PushHandler` calls `stack.sync_github`, which enqueues `GithubSyncJob`; this job fetches commits via `stack.github_api` (using the *victim* stack's own configured GitHub App/token) and, once new commits are appended, enqueues `CacheDeploySpecJob`. Appended commits can subsequently drive `Stack#trigger_continuous_delivery`, which calls `trigger_deploy`, i.e., an actual unauthorized deploy on a stack/organization the forger has no rights to. [7](#0-6) [8](#0-7)  This qualifies as an unauthorized deploy trigger across organizational trust boundaries — an operator of Org A's GitHub App (unprivileged with respect to Org B) can cause Shipit to sync/deploy Org B's stacks.

### Likelihood Explanation
This requires a Shipit instance to be configured with more than one GitHub organization (the documented "Using Multiple GitHub Applications" mode), and requires the attacker to know the `webhook_secret` of at least one of the configured organizations (e.g., because they are a legitimate admin of that org's own GitHub App, which is not a privileged credential with respect to *other* orgs hosted on the same Shipit instance). In single-org deployments the issue is latent because `repository_owner` always matches the sole configured org. Given multi-tenant Shipit is an explicitly documented and supported deployment model, likelihood is credible whenever that mode is used.

### Recommendation
After signature verification, re-derive the organization from the same field used to pick the signing secret and enforce that every repository referenced by the payload (e.g., `repository.full_name`, `organization.login`) actually belongs to that verified organization before dispatching to handlers — e.g., compare `repository.full_name.split('/').first` (case-insensitively) against the organization whose secret validated the request, and reject (422) on mismatch.

### Proof of Concept
1. Configure Shipit with two orgs, `orgA` and `orgB`, each with its own `webhook_secret`, and a stack for `orgB/victim-repo`.
2. As someone who knows `orgA`'s `webhook_secret` (e.g., an admin of `orgA`'s GitHub App), craft a `push` webhook body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgB/victim-repo" }
}
```
3. Compute `X-Hub-Signature` as `sha1=HMAC-SHA1(orgA_webhook_secret, body)`.
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` resolves `repository_owner` = `orgA`, verifies successfully against `orgA`'s secret. `create` then dispatches the full body to `PushHandler`, which resolves the stack via `repository.full_name` = `orgB/victim-repo`, calling `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on the victim org's stack despite the requester having no relationship to `orgB`.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
