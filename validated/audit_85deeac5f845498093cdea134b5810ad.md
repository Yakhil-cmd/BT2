### Title
`StackStxOp::check` fails to reject `num_cycles` outside `(0, POX_MAX_NUM_CYCLES]` due to a missing `return Err` - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`StackStxOp::check` detects an out-of-bounds `num_cycles` value (`0` or `> POX_MAX_NUM_CYCLES`) and logs a `warn!`, but the branch is missing the `return Err(...)` statement, so execution falls through and the function still returns `Ok(())`. This lets an attacker submit a burnchain stacking operation with an arbitrary `num_cycles` (e.g. `255`) that is accepted by consensus-critical validation and forwarded downstream to the PoX lock-up logic unmodified.

### Finding Description
The equality that must hold is: `accepted_num_cycles == num_cycles ∈ (0, POX_MAX_NUM_CYCLES]`. The code path is: [1](#0-0) 

Specifically, the validation branch: [2](#0-1) 

only calls `warn!` and does **not** `return Err(op_error::StackStxMustBePositive)` (or an equivalent error). Execution continues past the check, reaches the signer-key validation, and returns `Ok(())` unconditionally as long as the signer key (if present) parses. This means both `num_cycles == 0` and `num_cycles > POX_MAX_NUM_CYCLES` (up to `255`, the max value of the `u8` field) are silently accepted.

`num_cycles` is parsed directly from the raw burnchain transaction payload with no other range restriction: [3](#0-2) 

An attacker crafts their own Bitcoin transaction (their own inputs, no privileged role needed) encoding a `StackStxOp` with `num_cycles = POX_MAX_NUM_CYCLES + 1` (or any value up to 255). `StackStxOp::parse_from_tx` accepts it structurally, and `StackStxOp::check` — the function that is supposed to be the consensus gate enforcing the cycle bound — returns `Ok(())` instead of rejecting it. Because the codebase's own doc-comment and error variant (`op_error::StackStxMustBePositive`) indicate the intended behavior was to reject, this is a missing-`return` regression, not an intentional relaxation.

### Impact Explanation
If downstream PoX lock-processing logic (which computes reward-cycle unlock heights from `num_cycles`) trusts that `StackStxOp::check` has already bounded the value — which is the documented contract of this function — then the attacker's own `stacked_ustx` will be locked for more reward cycles than `POX_MAX_NUM_CYCLES` permits. This is a self-inflicted freeze (the attacker locks their own funds longer than the protocol allows), which nonetheless breaks the SINGLE_UNLOCK invariant that unlock height must never exceed the bounded maximum. This is repeatable per stacking operation and requires no downstream privileged action — the flaw is squarely in this consensus validation function.

### Likelihood Explanation
The precondition is trivial: any account with access to Bitcoin inputs can submit a `StackStxOp` burnchain operation with `num_cycles` set outside the allowed range. No pause admin, bond admin, signer, or miner role is required. The cost is a normal Bitcoin transaction fee. It is fully repeatable across cycles/senders.

### Recommendation
Restore the missing `return Err(op_error::StackStxMustBePositive)` (or a dedicated `op_error::StackStxInvalidCycles`) inside the `if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES` branch in `StackStxOp::check`:
```rust
if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
    warn!(...);
    return Err(op_error::StackStxMustBePositive);
}
```

```rust
impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
```
