### Title
Webhook signature verification is keyed off an attacker-controlled organization field that is decoupled from the repository the handler actually mutates - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which `GitHubApp`/secret to use for HMAC verification from a field inside the *unverified* JSON body itself, while the handlers that actually act on the payload (e.g. `PushHandler`) resolve the target repository/stack from a *different* field of that same unverified body. If any configured organization has no `webhook_secret` set, `verify_webhook_signature` short-circuits to `true`, letting an attacker fully forge a webhook for a victim repository belonging to a different, secured organization.

### Finding Description
`verify_signature` derives the signing organization purely from the incoming, not-yet-verified payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` — both attacker-controlled fields inside the raw POST body, before any signature has been validated. This value is used to select which `GitHubApp` instance (and thus which `webhook_secret`) is used to verify the signature: [3](#0-2) 

Critically, `verify_webhook_signature` returns `true` unconditionally when the selected organization's `webhook_secret` is blank — i.e., verification is skipped entirely for organizations that have no secret configured.

Once past `verify_signature`, the actual event handler (e.g. `PushHandler`) resolves which stacks/repositories to mutate independently, using the repository data embedded in the same payload: [4](#0-3) 

There is no code that ties the organization used to select the verifying secret (`repository_owner`) to the repository that `stacks`/handlers ultimately act upon. Both are independently attacker-supplied fields of the same JSON body. This breaks the equality that should hold: *the organization whose secret authenticated the request* == *the organization/repository that the handler writes to*.

### Impact Explanation
An attacker who knows (or discovers, e.g. via error messages/fixtures/config) that some organization configured in this Shipit instance has no `webhook_secret` set can craft a payload where:
- `repository.owner.login` / `organization.login` = the org with no secret (bypasses verification, since `verify_webhook_signature` returns `true` unconditionally for it), while
- the embedded `repository.full_name` (or the `push`/`status`/`check_suite` fields the handler actually reads) points at a *different*, secured organization's repository/stack.

This lets an unauthenticated caller synthesize `push`, `status`, `check_suite`, etc. events against a real stack, e.g. triggering `stack.sync_github(expected_head_sha: ...)` via `PushHandler`, updating commit statuses, or otherwise manipulating stack state that legitimate GitHub webhook signing was meant to protect — all without holding an `ApiClient` token, GitHub App private key, or repository write access. This crosses the "unauthorized deploy/rollback/merge" and "cross-repository writes" bar because the write happens against a repository that never actually authenticated the request.

### Likelihood Explanation
Likelihood depends on operational configuration: it requires at least one organization configured in `Shipit.github_teams`/GitHub app config to have a blank `webhook_secret` while another organization/repository is properly secured. This is a realistic misconfiguration in a multi-tenant Shipit deployment (e.g., a legacy/test org added without a secret), and the engine's own code explicitly supports `webhook_secret` being optional (`@config[:webhook_secret].presence`), so this is not a hypothetical edge case outside the documented mounting/configuration surface.

### Recommendation
- Do not select the verification secret/organization from unverified payload fields; if multi-tenant orgs are supported, verify the signature against *every* configured secret (or require a strict allowlist) rather than trusting an attacker-supplied field to pick the one secret to check against.
- After signature verification succeeds, cross-check that the `repository_owner`/organization used to verify the signature actually matches the organization owning the repository the handler is about to mutate; reject the request otherwise.
- Consider making `webhook_secret` mandatory (fail closed) rather than allowing verification to be skipped when it is blank.

### Proof of Concept
1. Configure (or identify) two organizations in Shipit: `org-no-secret` (no `webhook_secret`) and `org-secured` (has `webhook_secret`, owns a real stack).
2. POST to `/webhooks` with header `X-Github-Event: push` and a body such as:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker chosen sha>",
  "repository": {
    "owner": { "login": "org-no-secret" },
    "full_name": "org-secured/victim-repo"
  }
}
```
3. `verify_signature` computes `repository_owner = "org-no-secret"`, fetches that org's `GitHubApp`, and since its `webhook_secret` is blank, `verify_webhook_signature` returns `true` regardless of the (missing/invalid) `X-Hub-Signature` header.
4. `PushHandler#process` resolves `stacks` from the repository info in the same payload (`org-secured/victim-repo`) and calls `stack.sync_github(expected_head_sha: params.after)` on the victim's real stack — fully bypassing signature verification for that organization.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
module Shipit
  module Webhooks
    module Handlers

        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end
```
