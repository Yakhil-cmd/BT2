### Title
Arbiter contract flow leaks the victim's permanent device-pairing secret to the arbstore server and to unrelated wallet cosigners, enabling device impersonation - (File: arbiter_contract.js)

### Summary
The arbiter-contract subsystem embeds a user's **permanent** device-pairing secret (`my_pairing_code`) into the `wallet_arbiter_contracts` row and then broadcasts that entire row — secret included — to parties who have no legitimate need for it: every cosigner of the user's own multisig address, and the third-party arbstore HTTP server used for disputes/appeals. Anyone who obtains this permanent secret can silently and permanently pair with the victim's device.

### Finding Description
`device.getOrGeneratePermanentPairingInfo()` creates (once) or reuses a **permanent** pairing secret, stored with `is_permanent=1` and `expiry_date='2038-01-01'`, i.e. it never expires and is reused across all future pairing events for this device: [1](#0-0) 

`handlePairingMessage()` accepts this secret as sole proof of authorization to pair: it just checks the secret exists and is unexpired, then inserts the sender as a `correspondent_devices` row with `is_confirmed=1` — no additional user confirmation is required on the victim side for permanent secrets: [2](#0-1) 

`arbiter_contract.js` builds the plaintext pairing code (`pubkey@hub#secret`) from this permanent secret and stores it as `my_pairing_code` whenever a contract is created or accepted: [3](#0-2) [4](#0-3) 

This value is then propagated to two sets of parties that are not the intended pairing counterpart:

1. **All cosigners of the user's own address** — `shareContractToCosigners()` fetches the full contract row via `SELECT *` (which includes `my_pairing_code`) and sends it unfiltered to every cosigner device address: [5](#0-4)  This is invoked after the shared address is created and after a contract is accepted: [6](#0-5) 

2. **The arbstore HTTP server** — `openDispute()` and `appeal()` place both `my_pairing_code` and `peer_pairing_code` (i.e., the permanent secrets of *both* contract parties) into a plaintext JSON body POSTed to `/api/dispute/new` / `/api/appeal/new`: [7](#0-6) [8](#0-7) 

Because the leaked secret is *permanent* rather than a one-time pairing token, a single exposure to any unintended recipient (cosigner, arbstore operator, or anyone who compromises them) grants that party a standing, reusable ability to pair with the victim device at any future time, without the victim's awareness.

### Impact Explanation
Once an attacker uses the leaked permanent secret to pair, `correspondent_devices.is_confirmed=1` is set for them, making them a trusted correspondent from the victim wallet's point of view. As a confirmed correspondent, the attacker can then send device messages that the wallet treats as coming from a legitimate contact — e.g., spoofed `text` messages, `signing_request` proxy flows, or `private_payments` — to socially engineer the victim into approving a malicious multisig transaction or into leaking further private payment chains for addresses they jointly control. This can directly translate into unauthorized spending or fund loss from shared/multisig addresses that were never meant to be exposed to the arbstore operator or an unrelated cosigner. The impact rises to High because the leaked credential is reusable indefinitely and reachable by an unprivileged actor (any counterparty to an arbiter contract, i.e., a "private-payment counterparty" equivalent).

### Likelihood Explanation
The leak is deterministic and requires no special conditions: it happens automatically whenever a user (a) has more than one cosigner on the address used in an arbiter contract, or (b) opens a dispute or files an appeal through the normal arbiter-contract UI flow. No malicious input or race condition is required — the vulnerable code paths (`shareContractToCosigners`, `openDispute`, `appeal`) are part of the standard, documented arbiter-contract feature set.

### Recommendation
Do not include `my_pairing_code`/`peer_pairing_code` in data sent to the arbstore server or to cosigners. If a pairing invitation is genuinely needed for arbitration/dispute purposes, generate a short-lived, single-use, scope-limited pairing secret via `startWaitingForPairing()` (which already exists and creates a temporary, non-permanent secret) instead of `getOrGeneratePermanentPairingInfo()`, and never place any pairing secret in fields that get relayed to non-pairing-counterpart devices (`shareContractToCosigners`) or third-party HTTP endpoints (arbstore).

### Proof of Concept
1. Victim V co-owns a multisig address with cosigner Y (e.g., in an unrelated shared wallet), and separately negotiates an arbiter contract with peer P.
2. V calls `respond(hash, "accepted", ...)`, which computes `my_pairing_code` from V's permanent pairing secret and stores/sends it to P: [4](#0-3) 
3. When the shared address for the contract is created, `shareContractToCosigners(hash)` sends the full contract row (with `my_pairing_code`) to Y, an unrelated cosigner who was never supposed to learn V's permanent pairing secret: [5](#0-4) 
4. If the contract goes to dispute, `openDispute()` additionally POSTs both `my_pairing_code` and `peer_pairing_code` in plaintext to the arbstore server: [9](#0-8) 
5. Y (or the arbstore operator) extracts the leaked `pubkey@hub#secret` string and sends a `pairing` device message using it; `handlePairingMessage` accepts it because it is `is_permanent=1` and unexpired, silently adding Y as a confirmed correspondent of V: [2](#0-1) 
6. Y now has a standing trusted-correspondent channel to V's wallet and can attempt to social-engineer V (via `text`, `signing_request`, `private_payments` messages) into approving unauthorized fund transfers.
