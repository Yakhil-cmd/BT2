### Title
Cross-organization webhook forgery via repository-owner/full_name binding mismatch in multi-app config - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
### Finding Description
When Shipit is configured with the documented "Using Multiple GitHub Applications" scheme (top-level `github` keys per organization, each with its own `webhook_secret`), the webhook signature check and the webhook processing logic authenticate two *different* JSON fields of the same attacker-suppliable payload:

- `verify_signature` picks the `GitHubApp` (and thus the `webhook_secret` used for HMAC verification) using `repository_owner`, i.e. `params.dig('repository','owner','login')` or `organization.login`. [2](#0-1) [3](#0-2) 
- `Shipit.github(organization:)` resolves the per-org config/secret from `secrets.github`, keyed by organization name. [4](#0-3) 
- Once the signature passes, every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves the target `Stack`/`Repository` using `payload.dig('repository', 'full_name')` — a completely separate field that is never checked against `repository_owner`. [1](#0-0) 

Because `verify_signature` only proves "this payload's HMAC matches the secret configured for the organization named in `repository.owner.login`," it does **not** prove that `repository.full_name` (used to locate the `Stack` to sync/mutate) actually belongs to that same organization. A holder of a valid webhook secret for `OrgA` (e.g., because they administer or were granted webhook config visibility for a repo Shipit tracks under `OrgA`) can craft and correctly sign a payload where `repository.owner.login = "OrgA"` (so signature verification succeeds using OrgA's secret) but `repository.full_name = "OrgB/victim-repo"`. The signature check passes, and `PushHandler`/`CheckSuiteHandler` then operate on the `OrgB/victim-repo` stack — triggering `stack.sync_github(...)`, which fetches commits and can advance `Stack#last_deployed_commit`-adjacent state or queue deploy-eligible commits for a repository the attacker's organization never authenticated for. [5](#0-4) 

This is exactly the "organization that authenticated versus the repository that is written" trust binding described in scope: `Shipit.github(organization: repository_owner)` == the entity whose secret proved authenticity, but `Repository.from_github_repo_name(payload.dig('repository','full_name'))` == the entity actually mutated, and these two are never asserted equal.

### Impact Explanation
This lets a webhook-secret holder for one configured GitHub organization forge events (`push`, `status`, `check_suite`, `membership`, `pull_request`, etc.) that are attributed to and acted upon a *different* organization's stacks, without holding any credential (App private key, `GITHUB_TOKEN`, `api_clients_secret`) for that second organization. Depending on the handler this can trigger unwanted commit ingestion/sync (`GithubSyncJob`) or check-run refreshes for a stack under a repository/org the attacker has no legitimate write access to — an unauthorized cross-repository interaction with the deploy pipeline of another org's stack, which is a scoped-in impact ("cross-repository writes" / unauthorized deploy-pipeline interaction) under the multi-org configuration this feature explicitly documents and ships fixtures for. [6](#0-5) 

### Likelihood Explanation
Requires the deployment to use the multi-org GitHub App configuration (explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications", and `TOP_LEVEL_GH_KEYS`/`github_app_config` logic in `lib/shipit.rb`), and requires the attacker to already know/control a valid `webhook_secret` for at least one configured organization (e.g., as an admin of a GitHub App/organization onboarded to the same Shipit instance). Given that Shipit is designed to be shared across multiple orgs precisely for this multi-tenant case, and webhook secrets are commonly known to org admins/CI configurators, this is a realistic misuse path within the engine's own trust model rather than a purely theoretical one. [4](#0-3) 

### Recommendation
After signature verification, assert that the organization used to select the `webhook_secret` (`repository_owner`) matches the owner segment of `payload.dig('repository','full_name')` (and of `organization.login` for org-scoped events) before dispatching to handlers; reject (422) on mismatch. Alternatively, have `Handler#stacks`/`repository_name` re-derive/validate the repository against the authenticated organization context rather than trusting the raw payload field independently.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with distinct `webhook_secret`s (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker (who knows `OrgA`'s `webhook_secret`, e.g. as an `OrgA` admin) crafts a `push` event JSON body:
   ```json
   { "ref": "refs/heads/main", "after": "<attacker-controlled sha>",
     "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" } }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgA_webhook_secret, body)>` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and successfully verifies the signature. [2](#0-1) 
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("OrgB/victim-repo")` and invokes `stack.sync_github(expected_head_sha: params.after)` for `OrgB`'s stack, despite the signature only proving knowledge of `OrgA`'s secret. [1](#0-0) [5](#0-4)

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
