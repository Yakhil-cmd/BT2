### Title
Hookify `file`-scoped block/warn rules never evaluate for equivalent file writes performed via the Bash tool - (File: plugins/hookify/hooks/pretooluse.py)

### Summary
Hookify's own documented threat model (`plugins/hookify/README.md:99-118`, `plugins/hookify/skills/writing-rules/SKILL.md:147-158`) is to let a user write `event: file` rules that block/warn on writes to sensitive files (`.env`, `credentials`, `.pem`) or dangerous content (`eval(`, hardcoded `API_KEY`, etc.) via the Edit/Write/MultiEdit tools. The exact same file-content change can be produced by the Bash tool (`cat > .env`, `echo "API_KEY=..." >> .env`, `sed -i`, heredocs), which is classified as `event: bash` and therefore never checked against `file` rules, regardless of the rule's `pattern`/`conditions`.

### Finding Description
`plugins/hookify/hooks/pretooluse.py:43-52` derives the event strictly from `tool_name`: [1](#0-0) 
`load_rules(event=event)` in `plugins/hookify/core/config_loader.py:198-226` then filters out any rule whose `event` isn't `all` and doesn't equal that derived value: [2](#0-1) 

Because Bash is treated only as `event: bash` (matched against the `command` field), a `file`-scoped rule such as the documented example that blocks/warns on `.env`/`credentials`/`API_KEY` content (`plugins/hookify/README.md:99-118`, `plugins/hookify/skills/writing-rules/SKILL.md:69-83`) is structurally incapable of firing when the same write is performed with `Bash`. There is no cross-check that routes Bash-driven file writes through `file`-scoped conditions (`new_text`, `old_text`, `file_path`), so the restriction that the user explicitly configured for "file writes" is trivially routed around by using a different built-in tool that produces the identical on-disk effect. This mirrors the TITN root cause precisely: the guard (`_validateTransfer`) was attached to one code path (`transfer`/`transferFrom`) while an equivalent value-moving path (`mint`/`burn` via `send`) bypassed it entirely because the developers didn't realize both paths needed the same check.

### Impact Explanation
Any project or user relying on hookify's `event: file` rules to block writing secrets to `.env`/`credentials` files, or to block dangerous patterns like `eval(`/`innerHTML=`, gets a false sense of enforcement: Claude (or a user steering Claude) can achieve the identical filesystem mutation via `Bash` and never trigger the `block` action, silently defeating the guardrail. Since hookify is explicitly marketed as a user-configurable safety/hook layer (`plugins/hookify/README.md`), this is a concrete hook-bypass in the "hook bypass" trust-boundary category: a rule the user believes is enforced ("Rules are active immediately") is not enforced on an equally-reachable tool.

### Likelihood Explanation
High. No special privileges are required — any prompt that causes Claude to write file content via `Bash` instead of `Edit`/`Write` (which Claude does routinely, e.g. `cat <<EOF > file`, `echo ... >> file`, `sed -i`) reaches the unguarded path. No race condition or timing dependency is needed; the gap is deterministic and present on every Bash-tool file write.

### Recommendation
Route Bash tool calls whose command performs a file write (redirects `>`, `>>`, `tee`, `sed -i`, heredocs, etc.) through the same `file`-scoped condition evaluation used for Edit/Write/MultiEdit, or — simpler and more robust — always evaluate `file`-scoped rules against the resulting file content/path regardless of which tool produced the write (e.g., via a `PostToolUse` content check keyed on `file_path` rather than `tool_name`), so a `file` rule cannot be bypassed merely by choosing a different tool.

### Proof of Concept
1. Create `.claude/hookify.env-guard.local.md`:
```markdown
---
name: block-env-secrets
enabled: true
event: file
action: block
conditions:
  - field: file_path
    operator: regex_match
    pattern: \.env$
---
Blocked: do not write to .env files.
```
2. Ask Claude to edit `.env` with the `Write` tool → hookify's `pretooluse.py` sets `event='file'`, the rule matches, `action: block` denies the call (`plugins/hookify/core/rule_engine.py:61-79`).
3. Ask Claude to instead run `Bash` with `echo "API_KEY=leaked" >> .env` → `pretooluse.py` sets `event='bash'` (`plugins/hookify/hooks/pretooluse.py:46-47`), `load_rules(event='bash')` excludes the `event: file` rule entirely (`plugins/hookify/core/config_loader.py:221-222`), so `evaluate_rules` returns `{}` and the write proceeds unblocked — identical end state to step 2, but the "blocking" guard never runs.
