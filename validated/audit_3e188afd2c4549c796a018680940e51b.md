### Title
Unscoped `Commit.where(sha:)` in `StatusHandler#process` lets one repo's status webhook overwrite CI state on commits belonging to other repositories/stacks - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, without any repository scoping, then writes the incoming status to every matching `Commit` record via `create_status_from_github!`. Because Shipit's `Commit` table is not unique-keyed per repository (the same SHA can legitimately exist across multiple stacks, e.g. shared history, cherry-picks, or forks), an attacker who controls a repository that produces a colliding SHA can push a signed webhook for their own repo that mutates the status/deployability of a commit belonging to an unrelated victim stack.

### Finding Description
The broken binding is: `commit.stack_id == payload.repository_id` should hold for every `Commit` mutated by a status event, but `StatusHandler#process` never checks it.

Code path:
- `Shipit::WebhooksController#create` parses the JSON payload and dispatches to handlers registered for the `status` event after `verify_signature`, which only checks that the HMAC signature matches the secret configured for `repository_owner` (`params.dig('repository', 'owner', 'login')`) — it does **not** bind the payload's `sha` to the payload's `repository` in any way that affects which `Commit` rows get updated. [1](#0-0) 
- `StatusHandler#process` runs:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
```
This iterates **every** `Commit` row across **all repositories/stacks** sharing that SHA. [2](#0-1) 
- Contrast this with the base `Handler` class, which explicitly provides a `stacks` helper scoped by `Repository.from_github_repo_name(repository_name)` for exactly this purpose — a mechanism `StatusHandler` bypasses entirely by querying `Commit` directly instead of scoping through `stacks`. [3](#0-2) 
- `Commit#create_status_from_github!` calls `add_status`, which replicates the GitHub status into `statuses`, recomputes `status` (a `Status::Group`), and can trigger `Hook.emit(:deployable_status, ...)` and `stack.schedule_merges`. [4](#0-3) [5](#0-4) 
- `Commit#deployable?` is directly derived from this status: `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, so flipping a required context (e.g. `release/gate`) to `failure` on the victim's commit row changes `deployable?` and merge eligibility for the victim stack. [6](#0-5) 

Exploit flow: attacker owns/controls repository `attacker/repo`, configures a GitHub webhook secret for it (or simply owns the org so `verify_signature` succeeds for that org), and crafts a commit whose SHA collides with a real commit already ingested into the victim's stack (e.g., via a shared upstream commit, cherry-pick, or fork history reused across stacks) — no need to break SHA-256/1 collision resistance, just reuse a real SHA that already exists in both the attacker's and the victim's stacks (a legitimately common event: shared library repos, monorepo forks, template repositories, or repos added as remotes of one another). The attacker fires `POST /webhooks` with `X-Github-Event: status` and a payload for `attacker/repo` containing `sha`, `context: release/gate`, `state: failure`. `verify_signature` passes because it validates against `attacker/repo`'s own org/webhook secret — no privilege on the victim repo is needed. `StatusHandler#process` then writes this status to **all** `Commit` rows with that SHA, including the victim's, flipping their `release/gate` context to `failure` and changing `deployable?`.

Existing guards do not prevent this: `verify_signature` only authenticates that the *event* payload came from the org/repo it claims, not that the *records mutated* belong to that repository; the `ExplicitParameters` schema for `StatusHandler` only validates value types (`sha`, `state`, `context` are `String`), not repository ownership; and `drop_unhandled_event` / `check_if_ping` are irrelevant here.

### Impact Explanation
A payload authenticated for one repository can rewrite CI status (and therefore `deployable?`, `blocked?`, and merge-queue scheduling via `stack.schedule_merges`) on a `Commit` belonging to a completely different repository/stack. This is a cross-tenant state manipulation matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." The blast radius is any stack whose commit history shares a SHA with an attacker-controlled repository, and the attack is repeatable at will (each status webhook is a fresh mutation), including flipping required-context gates to force blocked deploys/merges or, conversely, to `success` to bypass a required gate for the victim.

### Likelihood Explanation
Preconditions: the attacker needs a repository whose webhook signature they can produce (i.e., a repo they legitimately push to and configure a webhook for, or any org accepted by `Shipit.github(organization:)`), and a SHA collision with a commit already tracked by the victim's Shipit stack. SHA collisions across repos are not exotic in Shipit's data model — commits are frequently shared across forks, mirrors, subtree/cherry-pick workflows, or when multiple stacks track overlapping histories (e.g., staging/production stacks of the same repo, or repos pointing at the same upstream) — this is explicitly the scenario the question's "seed a victim stack requiring `release/gate`, share the SHA" setup exploits. No GitHub App private key, `secret_key_base`, or Shipit session is required — only ownership of one webhook-emitting repository. This is a low-cost, highly repeatable attack once such a shared-SHA condition exists.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the repository that authenticated the event, mirroring the `stacks` helper already defined in `Handler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This ensures a status event can only mutate commits belonging to stacks whose repository matches `payload.dig('repository', 'full_name')`.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb` conceptually):
1. Create `attacker_repo` (`Repository`) and `attacker_stack` (`Stack`) with a commit `sha: "abc123"`.
2. Create `victim_repo` and `victim_stack` with `cached_deploy_spec.ci.require = ['release/gate']`, and a commit with the **same** `sha: "abc123"`, with an existing `release/gate` status of `success` such that `victim_commit.deployable?` is currently `true`.
3. Assert before state: `assert_equal true, victim_commit.reload.deployable?` and `assert_equal 'success', victim_commit.status.state`.
4. Build a `status` webhook payload for `attacker_repo` (`repository.full_name = attacker_repo.full_name`) with `sha: "abc123"`, `context: "release/gate"`, `state: "failure"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` directly (bypassing signature, since the vulnerability is in `process`, not `verify_signature`).
6. Assert after state: `assert_equal false, victim_commit.reload.deployable?` and `assert_equal 'failure', victim_commit.status.state` — proving `attacker_repo`'s payload mutated `victim_stack`'s commit, violating `commit.stack_id == payload.repository_id`.
7. Additionally assert `attacker_commit.reload.status.state == 'failure'` (the legitimate write) to show the victim write was purely incidental/unauthorized.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
