### Title
Failed symlink rename in `publishSymlink` leaves an orphaned `tmp-link` that permanently blocks all future publishes - (File: main.go)

### Summary
`repoSync.publishSymlink` performs the atomic "flip" that is git-sync's core safety contract: it creates a temporary symlink named `tmp-link` and then renames it onto the real `--link` path. If the `os.Rename` call fails after the `os.Symlink` call has already succeeded, the temporary file is left on disk and is never cleaned up, causing every subsequent sync attempt to fail permanently.

### Finding Description
`publishSymlink` first creates a temporary symlink at a fixed, hard-coded path (`tmp-link`) inside the link directory, then renames it over the real link: [1](#0-0) 

These two steps are not transactional. If `os.Symlink` succeeds but the subsequent `os.Rename` fails (e.g. the target directory is on a different filesystem/mount than expected, permission changes, a directory now occupies the destination path, or any other transient filesystem error), `publishSymlink` returns an error but the `tmp-link` file remains on disk. `SyncRepo` propagates that error up without any attempt to remove the stray temp file: [2](#0-1) 

On the very next sync loop iteration, `createTmpSymlink`'s `os.Symlink(targetRelative, filepath.Join(linkDir.String(), tmplink))` call will now fail every time with `EEXIST` because `tmp-link` already exists, before the rename step is ever reached again. There is no code path in `publishSymlink`, `SyncRepo`, or elsewhere in `main.go` that detects or removes a leftover `tmp-link` before attempting to create it again — a repo-wide search for `tmp-link`/`tmplink` only turns up the three lines inside this single function. This means a single transient rename failure permanently wedges the publish mechanism: the process will never again be able to update the `--link` symlink, even though fetches and worktree creation continue to succeed.

### Impact Explanation
This causes persistent sync denial: once the failure occurs, `git-sync` can no longer publish any new commit to consumers via the `--link` symlink, which is the documented "contract" between git-sync and its consumers. The sidecar keeps running (so liveness/readiness may still look up depending on config) but silently stops delivering updates indefinitely, requiring manual intervention (deleting the stray file from the shared volume) to recover. This matches the reported bug class: a failed operation in the "publish" path leaves internal/on-disk state inconsistent with what actually succeeded, and there is no retry/recovery logic to correct it, unlike the report's recommendation to give a client "another chance" after a first failed attempt.

### Likelihood Explanation
The failure requires an `os.Rename` to fail after `os.Symlink` succeeds on the same underlying path — a rare but realistic condition on real deployments (e.g. `--link` residing on a different bind mount than expected, race with another process/container manipulating the link directory, restrictive permissions applied mid-run, or filesystem-specific rename limitations). Because `--root`/`--link` directories are frequently shared volumes mounted across sidecar/init containers in Kubernetes, such transient filesystem inconsistencies are plausible in production, though not attacker-controlled in the classic sense (no privileged/malicious actor required, just an environmental fault).

### Recommendation
Make `publishSymlink` idempotent/self-healing:
- Remove any pre-existing `tmp-link` (`os.Remove`) before creating it, ignoring `os.IsNotExist` errors.
- Or use a unique/PID-based temp name instead of the fixed `tmp-link` constant to avoid collisions with a leftover file from a previous failed attempt.
- On `os.Rename` failure, attempt to clean up the temp symlink before returning the error so the next sync attempt starts from a clean state.

### Proof of Concept
1. Start `git-sync` normally against a repo with `--link=link`.
2. During a sync cycle, after `os.Symlink` in `publishSymlink` runs but before `os.Rename` completes, force the rename to fail (e.g., simulate by making the link directory read-only momentarily, or by mounting `linkDir` such that rename across the boundary fails with `EXDEV`).
3. Observe the error surfaced from `SyncRepo` and that `$ROOT/link/tmp-link` (or the resolved link dir) now contains a leftover `tmp-link` file.
4. Restore the filesystem to a normal writable state and let git-sync retry.
5. Observe that every subsequent sync attempt fails again in `publishSymlink` with `error creating symlink: ... file exists` at [3](#0-2) , because `tmp-link` was never removed — the symlink can never be updated again without manual deletion of the stray file, matching the "persistent sync denial" impact.
