### Title
Webhook Signature Verified Against `repository.owner.login`, but `StatusHandler` Writes to Any Commit Matching `sha` Cross-Repository/Cross-Organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/`webhook_secret` used to validate the HMAC signature based on `repository_owner`, a value read straight out of the attacker-supplied JSON body (`repository.owner.login` or `organization.login`) — not out of any value bound to the actual GitHub App/organization that delivered the request. `Handlers::StatusHandler`, which processes the `status` event once the signature check passes, then updates **every** `Commit` in the datastore whose `sha` matches the payload, with no re-check that the commit's stack belongs to the same repository/organization whose secret was used to authenticate the request. This breaks the binding: "organization that authenticated" ≠ "repository (commit) that is written."

### Finding Description
`verify_signature` picks which organization's `webhook_secret` to HMAC-verify against using a field taken from the untrusted payload itself: [1](#0-0) [2](#0-1) 

So the only thing this check proves is "this request was signed with organization X's webhook secret," where X is whatever `repository.owner.login` the attacker put in the body. It does **not** prove that the rest of the payload (in particular any commit `sha` referenced later) actually belongs to a repository owned by X.

`StatusHandler#process` then acts on the payload without re-validating that the referenced `sha` belongs to a stack under the authenticated organization/repository — it queries commits globally by `sha` across the entire Shipit installation: [3](#0-2) 

Compare this to the base `Handler` class, which does define a `repository_name`/`stacks` scoping helper based on `payload.dig('repository', 'full_name')`, used by `PushHandler` and the pull-request handlers [4](#0-3) [5](#0-4)  — but `StatusHandler` does not use this scoping at all, instead matching on raw `sha`.

`Commit#create_status_from_github!` (invoked from `StatusHandler`) creates a status record that feeds directly into deployability/continuous-delivery decisions: [6](#0-5) [7](#0-6) 

`Stack.trigger_continuous_delivery`/`next_commit_to_deploy` will pick up a commit as soon as it looks "success," and if the stack has `continuous_deployment: true`, it will trigger an actual `Deploy`: [8](#0-7) 

### Impact Explanation
An attacker who legitimately controls (or is a signer for) the GitHub webhook for **any** organization/repository registered in this Shipit instance (i.e., they can produce a validly-signed `status` webhook body for their own org) can forge a `status` payload with `repository.owner.login` set to their own org (so `verify_webhook_signature` passes with their own secret) while setting `sha` to the git SHA of a commit that actually belongs to a **different** organization's/repository's stack (SHAs are public information visible on GitHub). Because `StatusHandler` matches purely on `Commit.where(sha: params.sha)` with no ownership/repository check, this forged, validly-signed-for-org-A request can inject a `state: "success"` status for a commit belonging to org B's stack. If that stack has `continuous_deployment` enabled, this directly causes an **unauthorized deploy** for a repository/organization the attacker does not control — matching the report's core pattern (an attacker-influenced input that is not actually covered by what was verified) but escalated to the "Critical: unauthorized deploy" impact bucket defined in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in any multi-tenant Shipit deployment (multiple organizations/GitHub Apps configured, which is an explicitly supported configuration per `GitHubApp`/`Shipit.github(organization:)`). The only prerequisite is that the attacker can produce a validly-signed webhook for *some* organization onboarded to the instance (which is the normal, unprivileged capability of any org that legitimately uses this Shipit instance for its own repos) and knowledge of a target commit `sha` in another org (trivially obtainable from public GitHub history). No `ApiClient` token, session, or GitHub App private key is required — this is purely a signature-scope/authorization mismatch in the webhook trust boundary.

### Recommendation
In `StatusHandler` (and any other handler that doesn't already do so), scope the query using the repository identified in the payload (`payload.dig('repository', 'full_name')`) via the existing `Handler#stacks`/`repository_name` helper, and cross-check that the resolved repository's owner matches the `repository_owner` used to select the webhook secret in `verify_signature`. Reject the request (422) if the two do not match, so a signature valid for organization X can never be used to mutate commit/status state belonging to a different organization/repository.

### Proof of Concept
1. Attacker legitimately owns organization `attacker-org`, which has a webhook configured against this Shipit instance with a known `webhook_secret` (standard setup for any onboarded org).
2. Attacker finds/knows a commit SHA `deadbeef...` belonging to `victim-org/victim-repo`, which is registered as a Shipit stack with `continuous_deployment: true` and currently blocked from deploying due to `pending`/`failure` CI status.
3. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "deadbeef...",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker signs this body with `attacker-org`'s known `webhook_secret` (`X-Hub-Signature`) and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s GitHub App, and the HMAC check passes (attacker signed it correctly) [9](#0-8) .
6. `StatusHandler#process` runs `Commit.where(sha: "deadbeef...")`, finds the commit belonging to `victim-org/victim-repo`'s stack, and calls `create_status_from_github!` with `state: "success"` [10](#0-9) .
7. The commit's `add_status` flow detects a new deployable status and, since the victim stack has continuous deployment enabled, triggers `ContinuousDeliveryJob`/`trigger_continuous_delivery`, deploying code the attacker never had rights to affect [11](#0-10) [8](#0-7) .

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
