## Finding: Valid

### Title
Unbounded environment-key injection from GitHub PR label names into `Command#unbundled_env` enables `BUNDLE_GEMFILE`-based RCE on the deploy host - (File: `app/models/shipit/review_stack.rb`, `lib/shipit/task_commands.rb`, `lib/shipit/command.rb`)

### Summary
`ReviewStack#env` turns every pull-request label name into an environment-variable *key* (`label_name.upcase => "true"`) with no allowlist, and `LabelCapturingHandler#capture_labels` writes label names straight from the webhook body with no filtering. `TaskCommands#env` merges this into the environment that `Command#unbundled_env` hands to `PTY.spawn`, so a PR author who can label their own PR can inject loader-sensitive keys such as `BUNDLE_GEMFILE` into the process actually executing dependency-install/deploy steps.

### Finding Description
The broken binding: the set of environment-variable **keys** reaching `PTY.spawn` for a review-stack task should equal the deploy spec's declared `machine_env` keys ∪ a fixed internal set (`SHIPIT_USER`, `EMAIL`, `TASK_ID`, …). In practice it equals that set **∪ every PR label name uppercased**, an attacker-controlled, unbounded set.

Code path:
1. `LabelCapturingHandler#capture_labels` persists PR labels verbatim from the webhook payload with no allowlist or character restriction: `pull_request.update!(labels: params.pull_request.labels.map(&:name))` [1](#0-0) . The test suite even documents that arbitrary Unicode label names are accepted verbatim [2](#0-1) .
2. `ReviewStack#env` turns each label into an env-hash **key** with a fixed value: `pull_request.labels.each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }`, merged over the base stack env with no key allowlist [3](#0-2) .
3. `TaskCommands#env` merges `@stack.env` into the task's environment; the fixed keys added afterward (`SHIPIT_USER`, `EMAIL`, `BUNDLE_PATH`, …) do not include `BUNDLE_GEMFILE`, so an attacker-supplied `BUNDLE_GEMFILE` key survives to the final hash [4](#0-3) .
4. `Command#unbundled_env` merges `BASE_ENV` with `PATH` and then `@env.stringify_keys` — again with no allowlist — and this exact hash is passed to `PTY.spawn` in `Command#start` [5](#0-4) [6](#0-5) .
5. `TaskCommands#install_dependencies` builds the dependency-install `Command`s (e.g. `bundle install`) using this same `env`, and `DeploySpec::BundlerDiscovery#bundler?` auto-detects a Ruby dependency step whenever a `Gemfile` is present in the checked-out working tree [7](#0-6) [8](#0-7) .

Exploit flow: an attacker opens a PR against a Shipit-managed repository with `review_stacks_enabled`/`allow_all` provisioning, adds a label whose name is `bundle_gemfile` (captured verbatim and forced to `BUNDLE_GEMFILE=true`), and adds a `Gemfile` plus a file literally named `true` (containing malicious Ruby) to their own branch content. When the review stack's dependency step (`bundle install`) runs, `BUNDLE_GEMFILE=true` redirects Bundler to load the attacker's `true` file as the Gemfile; Bundler evaluates that file as Ruby, executing attacker code on the Shipit deploy host via `PTY.spawn`.

Existing guards do not stop this: there is no signature-bypass involved (this only requires a legitimate webhook for the attacker's own PR/repo), `ExplicitParameters` only validates JSON shape/types (`String` labels), not their content or an allowlist of names, and no `EnvironmentVariables#permit`/`VariableDefinition` allowlist is applied to `ReviewStack#env` or `Command#unbundled_env`.

### Impact Explanation
Arbitrary Ruby code execution as the Shipit process user on the deploy host, in the context of whichever stack the PR belongs to — Critical, matching "RCE on the deploy host via `Command`/`PTY.spawn`." The blast radius is scoped to repositories that have review stacks enabled and a ruby/bundler-detectable dependency step, but the primitive itself (unfiltered label-name-to-env-key injection) is generic: it can also be used to inject other loader/toolchain variables (`RUBYOPT`, `NODE_OPTIONS`, `GIT_SSH_COMMAND`, `LD_PRELOAD`, etc.) depending on which dependency/deploy steps a given repository's `shipit.yml` triggers, since `Command#unbundled_env`/`TaskCommands#env` apply no key allowlist for any of these.

### Likelihood Explanation
Preconditions: the target repository must have review stacks enabled with a provisioning behavior that auto-creates stacks for new/labeled PRs (e.g. `allow_all`, as exercised by the test fixtures), and the checked-out PR content must cause a Ruby/bundler dependency step to be auto-discovered (trivially achievable by adding a `Gemfile` in the PR itself). The attacker needs only the capabilities explicitly granted by the rules of engagement (open PR, push branch content, label own PR) — no Shipit credentials or GitHub org privileges are required by the code path itself. This is repeatable per PR/label event and does not require any race condition.

### Recommendation
Do not let PR label names become environment-variable keys without allowlisting: restrict `ReviewStack#env` to a fixed, sanitized set of derived keys (e.g. prefix all label-derived keys, such as `SHIPIT_LABEL_<UPCASED>` instead of overwriting the bare name), and/or maintain an explicit allowlist/denylist of environment key names (rejecting `BUNDLE_GEMFILE`, `RUBYOPT`, `LD_PRELOAD`, `NODE_OPTIONS`, `GIT_SSH_COMMAND`, etc.) in `Command#unbundled_env` before merging `@env` over `BASE_ENV`.

### Proof of Concept
minitest plan (no live GitHub required):
```ruby
test "PR label injects BUNDLE_GEMFILE key into task command env reaching unbundled_env" do
  stack = shipit_stacks(:review_stack)
  stack.pull_request.labels = ["bundle_gemfile"]
  task = shipit_tasks(:shipit_restart)
  task.stack = stack

  env = Shipit::TaskCommands.new(task).env
  assert_equal "true", env["BUNDLE_GEMFILE"]

  command = Shipit::Command.new("bundle install", env: env, chdir: "/tmp")
  assert_equal "true", command.unbundled_env["BUNDLE_GEMFILE"]
  # command.unbundled_env is exactly the hash passed to PTY.spawn in Command#start
end
```
This demonstrates the equality violation: the key set passed to `PTY.spawn` is not restricted to `machine_env`/declared `VariableDefinition` names — it includes an attacker-chosen key (`BUNDLE_GEMFILE`) sourced solely from a PR label.
