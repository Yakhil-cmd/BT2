### Title
Unauthenticated Author-Address Lock Acquisition Before Signature Verification Enables Targeted Validation-Queue Starvation - (File: validation.js)

### Summary
`validation.js`'s `validate()` function extracts author addresses directly from the untrusted, unverified unit and immediately acquires an exclusive per-address mutex lock on them, running the entire (multi-step, DB-transacted) validation pipeline under that lock *before* the address's ownership is proven via signature/authentifier verification. This mirrors the Xen platform-op bug class: "the lock acquire will, for some operations, occur ahead of any permission checking."

### Finding Description
In `validate()`, the author addresses are pulled straight from the posted unit and only checksum-validated, not authenticated: [1](#0-0) 

The mutex is then locked on these addresses before any cryptographic proof of authorship exists: [2](#0-1) 

Everything that follows — opening a DB connection, `BEGIN` transaction, `checkDuplicate`, `validateHeadersCommissionRecipients`, `validateHashTreeBall`, `validateParentsExistAndOrdered`, `validateHashTreeParentsAndSkiplist`, `validateParents`, `validateSkiplist`, `validateWitnesses`, `validateAATrigger`, `validateTpsFee` — runs while holding the address-keyed lock, all *before* `validateAuthors`/`validateAuthor` performs the actual authentifier/signature check: [3](#0-2) 

The actual permission check (does the sender control the private key for this address?) happens inside `validateAuthor` → `Definition.validateAuthentifiers`, i.e. only near the very end of the pipeline: [4](#0-3) 

The mutex module itself is a global, single-key exclusive lock shared across the whole node (`validation.js`, `composer.js`, `divisible_asset.js`, `indivisible_asset.js`, etc. all lock on the same address keys): [5](#0-4) 

Because the address lock is granted purely on the basis of an unverified claim ("I am author X") rather than on proof of ownership, any unprivileged unit poster can name an arbitrary valid address as an author and thereby seize that address's global lock for the duration of a full validation cycle — with no requirement to possess that address's private key.

### Impact Explanation
An attacker can repeatedly craft syntactically valid (but ultimately unsigned/invalid-signature) units that name a victim address as an author, each with a unique unit hash to bypass `checkDuplicate`. Because `mutex.lock(arrAuthorAddresses, ...)` is acquired before `validateAuthors` rejects the unit for a bad signature, the victim's address lock is occupied for the full duration of the earlier pipeline stages (DB transaction, parents/hash-tree/skiplist/witness/AA-trigger/TPS-fee checks) on every such submission. Since the same address-keyed lock is used by `composer.js`/`divisible_asset.js`/`indivisible_asset.js` when the legitimate owner tries to compose or finalize a real payment, and by `validation.js` itself for any legitimate unit genuinely signed by that address, an attacker with no relationship to the victim can serialize and delay the victim's real transactions behind a continuous stream of doomed-to-fail validations. This can be used to stall confirmation/stabilization of a targeted address's units — a form of "network unable to confirm new units" for a chosen victim — and could be weaponized to win races (e.g., delay a legitimate spend long enough for a competing double-spend attempt, or to stall AA trigger processing tied to the same author address).

### Likelihood Explanation
Reaching this path requires only posting a single unit over the network with `authors: [{address: <victim>, authentifiers: {...}}]` where `address` passes the plain checksum check (`isValidAddress`) — no private key, permission, or special node role is needed. This is directly reachable by any unprivileged unit poster through the normal joint-posting path (`network.js` `handleJoint` → `validation.validate`), which is squarely in the reachable-attack-surface list (unit validation, address authentifiers).

### Recommendation
Do not acquire the exclusive per-address mutex based solely on the unverified `authors[].address` field. Either:
- Defer the address-lock acquisition until after a lightweight authenticity check (e.g., structural/authentifier-presence check) confirms the unit plausibly belongs to that address, or
- Perform the signature/authentifier verification (`validateAuthors`) before or immediately upon lock acquisition, failing fast for bad signatures without holding the lock through the rest of the pipeline, or
- Use a lock scheme where lock acquisition itself does not block on unverified identity claims (e.g., lock granted only after a cheap "author actually signed the unit hash" pre-check).

### Proof of Concept
1. Choose a victim address `X` with a known valid checksum (public information from any prior transaction).
2. Craft a unit `U` with `authors: [{address: X, authentifiers: {r: "AAAA..."}}]` (garbage signature), valid `parent_units`, and a fresh/random payload so `checkDuplicate` never triggers.
3. Repeatedly submit fresh variants of `U` to the network via the normal joint submission path.
4. Each submission causes `validation.validate` to run `mutex.lock([X], ...)` at `validation.js:357` and proceed through the full DB-transacted pipeline before failing in `validateAuthor`'s authentifier check.
5. While each submission's lock is held, any legitimate operation on `X` (e.g., the real owner posting/validating a genuine payment, or `composer.js` composing a spend from `X`) is queued in `mutex.js`'s `arrQueuedJobs` and delayed until the attacker's invalid unit finishes validating and fails.
