### Title
Prefix-based signing-path check in arbiter dispute handler can accept a non-mutually-signed unit as valid mutual signature - ([File: wallet.js])

### Summary
`wallet.js` validates that a signing unit submitted with an `arbiter_dispute_request` is "mutually signed" by both parties of a shared address by checking whether any authentifier signing path merely starts with `'r.0.0'` or `'r.0.1'`, instead of an exact/boundary-aware path match. This mirrors the CoreDNS `longestMatch` flaw: an ad-hoc string-prefix comparison is used where an exact, structurally-aware match is required, so a broader/looser match can substitute for the specific one the check intends to require.

### Finding Description
In the `arbiter_dispute_request` handler, mutual-signature verification is done as: [1](#0-0) 

`p.startsWith('r.0.0')` and `p.startsWith('r.0.1')` are plain string-prefix tests with no delimiter boundary check. Signing paths in ocore's address-definition tree are built by appending `.` + index at each nesting level (see the recursive path construction pattern used elsewhere in the codebase, e.g. `path + '.' + i`) [2](#0-1) . Because `'.'` is the only separator and indices are decimal, once a set/branch at a given level has 10 or more children, sibling path `'r.0.10'` textually begins with the substring `'r.0.1'`, and `'r.0.100'`, `'r.0.11'`, etc. all likewise satisfy `startsWith('r.0.1')` even though they are unrelated sibling branches, not the acceptor's specific branch at index 1. The same ambiguity applies to `'r.0.0'` vs. any `'r.0.0x'` branch. This is exactly the class of bug described in the CoreDNS advisory: a coarse/lexicographic-style prefix test stands in for what should be an exact-segment match, allowing a wrong, more permissive branch to satisfy a check meant to enforce a specific stricter one.

The check is only ever exercised on the `authentifiers` keys of the *shared address author actually present in the already-validated signing unit* fetched via `storage.readUnit(body.unit)` [3](#0-2) , so any exploitation would require a shared-address definition with ≥10 branches at the offending nesting level and an attacker-controlled peer able to construct/propose such a definition and a unit signed only under an unrelated 10+ branch.

### Impact Explanation
If the check is bypassed, `isMutuallySigned` incorrectly evaluates true for a signing unit that was not actually co-signed by both contract parties on the expected `r.0.0`/`r.0.1` sub-definitions. The handler then proceeds to accept the dispute (`arbiter_contract.insertDispute`) and notifies the arbiter/peer, and later arbitration/resolution flows (fund release from the shared/contract address) are gated on this dispute-validity assumption. This does not directly move funds in this snippet, but it undermines the correctness guarantee ("this unit was genuinely mutually signed by offeror and acceptor") on which the arbitration/dispute resolution and eventual payout decisions rely, i.e. it is an authorization-boundary defect in a fund-adjacent workflow (arbiter contracts hold and eventually pay out shared-address funds based on dispute outcomes).

### Likelihood Explanation
Exploitation requires a specific, unusual shared-address definition shape (10+ signing branches nested such that indices collide with the `'r.0.0'`/`'r.0.1'` prefixes) and a counterparty willing/able to construct it and get it accepted as the contract's shared address — this is a narrow, structurally-dependent precondition (data-dependent, like the CoreDNS bug), not a universally triggerable bug for ordinary two-party contracts using the standard `["and", [["sig",...],["sig",...]]]` shape where only paths `r.0.0`/`r.0.1` exist and no 10+ sibling branch can arise.

### Recommendation
Replace the substring `startsWith` checks with exact match or boundary-aware matching, e.g. compare `p === 'r.0.0' || p.startsWith('r.0.0.')` and `p === 'r.0.1' || p.startsWith('r.0.1.')` (requiring the next character after the prefix to be the `.` delimiter or end-of-string), analogous to how CoreDNS's fix requires proper suffix/label-boundary comparison instead of raw string comparison.

### Proof of Concept
Conceptual PoC (cannot run in ask-only mode):
1. Construct (or have a malicious peer propose) a shared address whose definition places 11+ alternative signing branches under position 0 of the top-level array, such that recursively generated signing paths include `r.0.0`, `r.0.1`, ..., `r.0.10`.
2. Produce and broadcast a unit where the shared-address author's `authentifiers` only contain a signature under path `r.0.10` (an unrelated branch) — no signature exists under the real acceptor path `r.0.1`.
3. Submit `arbiter_dispute_request` referencing this unit. `signing_paths.find(p => p.startsWith('r.0.1'))` matches `'r.0.10'`, so `isMutuallySigned` becomes truthy despite the acceptor never having signed under `r.0.1`, allowing the dispute request to pass this authorization check.
