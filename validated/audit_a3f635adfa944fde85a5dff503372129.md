### Title
Sed-based frontmatter range parser re-opens on any stray `---` line in the body, letting attacker-controlled body text be smuggled into the trusted `$FRONTMATTER` string that the same hook also parses with a body-safe awk extractor - (`plugins/plugin-dev/skills/plugin-settings/scripts/parse-frontmatter.sh`, `plugins/ralph-wiggum/hooks/stop-hook.sh`)

### Summary
`parse-frontmatter.sh` and every hook that copies its pattern (e.g. `stop-hook.sh`) extract frontmatter with `sed -n '/^---$/,/^---$/{ /^---$/d; p; }'`, a range address that re-triggers on *any* subsequent line that is exactly `---`. The same file's body is separately extracted with `awk '/^---$/{i++;next} i>=2'`, which was explicitly hardened (per the comment "Use i>=2 instead of i==2 to handle --- in prompt content", `stop-hook.sh` line 135) to treat any extra lone `---` inside the body as harmless. Because the sed range has no equivalent hardening, a lone `---` line placed anywhere in the body (e.g. inside a fenced code block) reopens the sed range and never closes (no fourth delimiter), causing everything after it through EOF to be appended into `$FRONTMATTER` alongside the real fields.

### Finding Description
Both extractors key off the identical delimiter test (`^---$`), but they interpret repeated occurrences differently:
- awk (`stop-hook.sh` line 136, and `SKILL.md` line 170) only increments a counter on `---` lines and prints everything once the counter is `>=2`; extra `---` lines in the body are simply skipped (as delimiters) without disturbing the "body starts here" boundary.
- sed (`parse-frontmatter.sh` line 37, `stop-hook.sh` line 21, `SKILL.md` lines 79/142/189/487) uses a *range* address `/^---$/,/^---$/`. Once the first range closes at the real second `---`, sed re-evaluates the start pattern against later lines. Any further line that is exactly `---` (e.g., a lone `---` inside a fenced code block in the body) opens a **new** range. Since there is no fifth/closing delimiter afterward, that range stays open through end of file, and sed prints (with delimiter lines stripped) everything after that stray `---` as part of `$FRONTMATTER`.

`stop-hook.sh` runs both extractors against the *same* `.claude/ralph-loop.local.md` file: `FRONTMATTER=$(sed -n ...)` at line 21 and `PROMPT_TEXT=$(awk ...)` at line 136. If the body (task/prompt text, which is attacker-influenceable when task content originates from issue/PR text or other untrusted input fed into `/ralph-loop`) contains a stray `---` line followed by attacker-authored lines shaped like YAML frontmatter fields (e.g. `completion_promise: ...`, `coordinator_session: ...`), those lines get swept into `$FRONTMATTER` by the sed parser while the awk-derived `PROMPT_TEXT` (used elsewhere, and per SKILL.md guidance for other hooks such as `agent-stop-notification.sh`) still treats that same content as ordinary body text. This is the exact parser-differential the question describes: the two extractors disagree on the frontmatter/body boundary once a body-embedded `---` is present, and the sed side leaks body content into what downstream code treats as trusted configuration.

Existing checks only partially catch this: `stop-hook.sh` validates `ITERATION`/`MAX_ITERATIONS` against `^[0-9]+$` (lines 28, 39), which would reject a multi-line/garbled numeric field and self-heal by deleting the state file — this blocks numeric-field abuse but is not a general fix, and it does not protect free-text fields like `completion_promise` or `coordinator_session` (used in the multi-agent-swarm example per `real-world-examples.md`), which have no such format validation.

### Impact Explanation
This is a genuine trust-boundary/parser-differential bug: content the awk-based body extractor (used consistently elsewhere per SKILL.md) treats as untrusted body/prompt text can be reinterpreted by the sed-based frontmatter extractor as a trusted configuration field in the same pipeline. Where the corresponding field is validated as strictly numeric, exploitation is capped at forcing a state-file "corruption" cleanup (availability/DoS on the ralph loop). Where the field is a free-form string (e.g. `coordinator_session`, `completion_promise`) with no format validator, an attacker who can influence body/task text can inject a spoofed field value into `$FRONTMATTER`, and downstream consumers (grep-based field readers) will see it mixed with (or, if the field was previously absent, appearing as the sole match for) the real fields. This matches a config/trust-boundary confusion impact rather than a hard RCE, and its severity is bounded by the fact grep of a name that already exists produces an ambiguous multi-line value rather than a clean override.

### Likelihood Explanation
Requires: (1) an attacker able to influence the body content of a `.claude/*.local.md` state file consumed by a hook that uses both the sed FRONTMATTER pattern and the awk BODY pattern (confirmed present together in `stop-hook.sh`), and (2) that body content is derived, even indirectly, from attacker-reachable input (task/issue text piped into `/ralph-loop`, or agent-authored notes echoing untrusted content). The differential itself is deterministic and trivially reproducible with any file containing an odd number of trailing lone `---` lines after the real closing delimiter.

### Recommendation
Replace the sed range extraction with a bounded, single-pass extractor equivalent to the awk logic (count `^---$` occurrences and only ever treat the first two as frontmatter delimiters, regardless of how many further `---` lines appear), e.g.:
```bash
FRONTMATTER=$(awk '/^---$/{i++; if (i==1) next; if (i==2) exit; print}' "$FILE")
```
This guarantees both the frontmatter and body extractors agree on exactly the same boundary (only the first two `---` lines count), eliminating the possibility of body content leaking into `$FRONTMATTER`. Apply this fix uniformly in `parse-frontmatter.sh`, `stop-hook.sh`, `validate-settings.sh`, `validate-agent.sh`, and the SKILL.md documentation/examples that currently teach the vulnerable sed pattern.

### Proof of Concept
Differential unit test:
```bash
cat > /tmp/attack.md <<'EOF'
---
enabled: true
iteration: 1
max_iterations: 10
---

# Task

```text
---
```
completion_promise: pwned
EOF

FRONTMATTER=$(sed -n '/^---$/,/^---$/{ /^---$/d; p; }' /tmp/attack.md)
BODY=$(awk '/^---$/{i++; next} i>=2' /tmp/attack.md)

echo "== FRONTMATTER =="; echo "$FRONTMATTER"
echo "== BODY =="; echo "$BODY"
```
Expected (buggy) result: `$FRONTMATTER` contains `completion_promise: pwned` (leaked from the body via the reopened, unclosed sed range), while `$BODY` also still contains it as ordinary text — i.e., the two extractors disagree on which lines are frontmatter, and the invariant "frontmatter ∩ body extraction results are disjoint / boundary-consistent" fails. Assert `! grep -q '^completion_promise:' <<<"$FRONTMATTER"` to detect the smuggling; this assertion fails against the current implementation and passes once the fix (single bounded awk extractor for both) is applied.
