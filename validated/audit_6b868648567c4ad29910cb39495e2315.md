### Title
Race condition in `validateAndSavePrivatePaymentChain` allows double-save of a private-asset output (analogous to the `rose_accept` TOCTOU UAF) - (File: private_payment.js)

### Summary
CVE-2023-51782 is a classic check-then-act race: `rose_ioctl`/`rose_accept` inspect and mutate shared socket state without holding the lock across the whole operation, so two concurrent code paths can observe the same "not yet consumed" state and both act on it, one of them operating on freed/stale state. The same bug class — an unprotected check‑then‑act sequence reachable from an unprivileged actor (a private-payment counterparty) — exists in `private_payment.js`.

### Finding Description
`validateAndSavePrivatePaymentChain()` in `private_payment.js` performs a duplicate check and then a save without ever taking the global `mutex` that every other unit-processing path (`validation.js:357`, `network.js:1166`, `divisible_asset.js:320`, `indivisible_asset.js:833`) uses to serialize access to unit/asset state: [1](#0-0) 

The sequence is:
1. Take a DB connection and `BEGIN` a transaction.
2. `SELECT ... FROM outputs WHERE unit=? AND asset=? AND message_index=?` to see whether this private output already exists ("duplicate" check).
3. If no matching row is found, call `assetModule.validateAndSavePrivatePaymentChain(conn, ...)` (in `indivisible_asset.js` / `divisible_asset.js`) to validate and persist the output.

This whole check-then-act sequence is **not guarded by `mutex.lock`**, unlike the analogous "check known unit, then validate, then save" flow in `network.js:handleJoint` which wraps validation+save inside `mutex.lock(['handleJoint'], ...)` at [2](#0-1)  and unlocks only after `writer.saveJoint` completes at [3](#0-2) .

Compounding this, the entry point `handleOnlinePrivatePayment()` in `network.js` has the `assocUnitsInWork[unit]` guard explicitly **commented out** for the "already known unit" branch: [4](#0-3) 

This means the same private payment chain, received twice in quick succession (e.g. once from a hub and once directly from the cosigner/payer, or replayed by a device pairing counterparty), can enter `validateAndSavePrivatePaymentChain` twice concurrently. Because separate DB connections are taken per invocation (`db.takeConnectionFromPool` at `private_payment.js:45`), the two `BEGIN...SELECT...COMMIT` transactions can interleave: both see "no existing row" at step 2, then both proceed to `assetModule.validateAndSavePrivatePaymentChain`, which independently calls `writer.saveJoint`-style logic to persist outputs for the same hidden output entry — this is the same shape of bug as `rose_accept`: two racers observe stale "not yet claimed" state and both act on it.

### Impact Explanation
If two concurrent chain-save operations both pass the duplicate check and independently mark spend proofs / outputs as consumed for the same private (hidden) asset output, this can lead to inconsistent local wallet/asset ledger state — e.g. a private asset output being recorded/spendable twice locally, or spend-proof bookkeeping getting corrupted, which can be leveraged toward double-spend of a private-asset output from the perspective of the local node's accounting. This matches the "concrete unauthorized spending / double-spend of a stable output" bar required by the validation rules.

### Likelihood Explanation
Reaching this path requires only sending (or replaying) a private-payment chain message twice to a node — something any private-payment counterparty (payer, cosigner, or paired device) can trigger without special privileges, and the guard that would normally prevent duplicate concurrent processing (`assocUnitsInWork`) is explicitly disabled for this branch at `network.js:2412-2429`. The race window is small but real, requiring near-simultaneous delivery of the duplicate message, which is achievable by an attacker controlling both the hub-relayed copy and a direct-send copy of the same private payment.

### Recommendation
Serialize `validateAndSavePrivatePaymentChain` per `(unit, message_index, output_index)` (or per `unit`) using `mutex.lock`, matching the pattern already used in `validation.js` and `network.js:handleJoint`, so the duplicate-check SELECT and the subsequent save happen atomically with respect to concurrent calls for the same private element. Re-enable (or replace with an equivalent) the `assocUnitsInWork` guard in `handleOnlinePrivatePayment`'s `ifKnown` branch in `network.js` so a unit already being processed cannot be re-entered concurrently.

### Proof of Concept
1. As a private-payment counterparty (or a hub relaying on behalf of one), send the identical `private_payment` message for a given `(unit, message_index[, output_index])` to a victim node twice in immediate succession, once directly and once forwarded through another channel, so both invocations of `handleOnlinePrivatePayment` reach the `ifKnown` branch at `network.js:2412-2429` before either has committed.
2. Each invocation independently calls `private_payment.js:validateAndSavePrivatePaymentChain`, takes its own connection, and runs the `SELECT ... FROM outputs ...` duplicate check at `private_payment.js:70-107` before the other's `COMMIT` is visible.
3. Both branches proceed to `assetModule.validateAndSavePrivatePaymentChain`, each persisting/consuming the private output independently, resulting in duplicated local bookkeeping of a single private-asset output.

Note: I was not able to fully trace the exact downstream write statements inside `indivisible_asset.js`/`divisible_asset.js`'s `validateAndSavePrivatePaymentChain` (called from `private_payment.js:105`) to confirm the precise unique-constraint behavior of the `outputs`/`spend_proofs` tables under this race, due to tool-call limits reached during this session — a full trace of the SQL schema constraints would be needed to confirm whether a DB-level UNIQUE constraint incidentally prevents the double-write (turning this into a benign error) or whether it succeeds silently for both connections.
