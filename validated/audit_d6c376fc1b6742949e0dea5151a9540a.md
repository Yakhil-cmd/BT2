Confirmed exploit path found: `WebhooksController#verify_signature` selects the GitHub App/webhook secret using `repository_owner`, which is parsed from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), while every event handler (`Handler#repository_name`, `PushHandler`, `PullRequest::*Handler`) resolves and writes to the target `Stack`/`Repository` using an entirely different field, `payload.dig('repository', 'full_name')`. These two fields are never checked against each other.

### Title
Webhook signature verification keys on `repository.owner.login`, while handlers act on the unrelated `repository.full_name` field, allowing cross-organization stack writes - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
The webhook signature-verification step and the event-processing step trust two different, independently attacker-suppliable fields of the same JSON payload without ever cross-validating them.

### Finding Description
`WebhooksController#verify_signature` picks which organization's `webhook_secret` to check the `X-Hub-Signature` against by reading `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` or `params.dig('organization', 'login')` [1](#0-0) . This chooses the `Shipit.github(organization:)` instance, and thus the secret, used by `verify_webhook_signature` [2](#0-1) , and this scoping logic exists specifically because Shipit can be configured with multiple organizations, each with its own GitHub App / `webhook_secret` [3](#0-2) .

Once the signature is accepted, `params` (the full parsed JSON body, unmodified) is dispatched to every registered handler for the event [4](#0-3) . Every handler resolves the target `Stack`/`Repository` from `payload.dig('repository', 'full_name')`, via `Handler#repository_name` / `#stacks` [5](#0-4) , and the `PushHandler`, which calls `stack.sync_github(expected_head_sha: params.after)` for every non-archived stack on the matching branch [6](#0-5) , or the pull-request handlers, which similarly resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and archive/unarchive review stacks accordingly [7](#0-6) .

Because `repository.owner.login` (used for the signature/secret lookup) and `repository.full_name` (used for the actual data write) are independent fields of the same request body, and are never checked for consistency, the binding "organization whose secret authenticated this delivery" == "repository that gets written" does not hold. In a single-organization Shipit deployment this is not exploitable since only one secret exists; the binding gap is only exposed in the documented multi-organization configuration this code path exists to support.

### Impact Explanation
An attacker who is able to produce a validly-signed delivery for *any one* organization configured on the Shipit instance (e.g., because they are a collaborator who can trigger real GitHub webhook events, or has legitimately obtained one org's `webhook_secret` through configuration mistake) can set `repository.owner.login` to that organization while setting `repository.full_name` to a repository belonging to a completely different organization managed by the same Shipit instance. The `verify_signature` check passes (correct secret for the named organization), but the handler processes the payload as if it came from the other org's repository, causing `GithubSyncJob`/`sync_github`, commit-status writes, or review-stack archive/unarchive actions to fire against a stack that has nothing to do with the authenticating organization. This is a cross-repository/cross-organization write triggered by a webhook authenticated for an unrelated org — matching the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Exploitability is gated on Shipit being configured for more than one GitHub organization (as the `Shipit.github(organization:)` lookup and per-org `webhook_secret`/App config imply) and on the attacker being able to produce a genuinely-signed delivery for at least one of those organizations. Real GitHub-originated deliveries always have `repository.owner.login` and `repository.full_name`'s owner segment consistent, so the mismatch can only be introduced by a party able to author arbitrary payload content signed with a known secret — this is a real capability boundary, not merely theoretical, if any of the configured organizations' delivery paths are reachable by a less-trusted party (e.g., a bot/app installed on a lower-trust org sharing the same Shipit instance).

### Recommendation
After selecting the organization for signature verification, cross-check that `repository.owner.login` (or `organization.login`) matches the owner segment of `repository.full_name` before dispatching to handlers, and reject the delivery (422) on mismatch. Alternatively, derive the webhook-secret lookup key from the same field the handlers use (`repository.full_name`'s owner) rather than a separate, independently-controlled field.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` and `org-b`, each with its own GitHub App/`webhook_secret` (per `lib/shipit/github_app.rb`).
2. Obtain the ability to send a validly HMAC-signed payload for `org-a` (e.g. through a legitimate low-trust integration on `org-a`).
3. Craft a `push` event body where `repository.owner.login = "org-a"` (used by `WebhooksController#repository_owner` to pick the verification secret) but `repository.full_name = "org-b/some-repo"` (used by `PushHandler#stacks`/`Handler#repository_name`).
4. Sign the payload with `org-a`'s secret and POST it to `/webhooks`. `verify_signature` succeeds because it only checks the signature against `org-a`'s secret [2](#0-1) .
5. `PushHandler#process` resolves the stack for `org-b/some-repo` and calls `sync_github(expected_head_sha: params.after)` on it [6](#0-5) , causing Shipit to act on `org-b`'s stack using a delivery that was only ever authenticated for `org-a`.
