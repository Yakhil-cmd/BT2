### Title
Cross-repository commit-status confusion via unscoped `Commit.where(sha:)` amplified by `continuous_deployment` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire `commits` table with no repository/stack scoping, so a `status` webhook that is legitimately signed for one repository (e.g. an attacker's own fork) is applied to every `Shipit::Commit` row sharing that SHA, including ones that belong to a different, victim stack. Because commit SHAs are content-addressed and identical between a repo and its forks, an attacker who owns a fork sharing history with a victim's repository can flip the `shipit/checks` status on a commit that also exists in the victim stack; if that stack has `continuous_deployment` enabled, `Commit#schedule_continuous_delivery` will queue `ContinuousDeliveryJob`, potentially shipping/blocking a deploy the attacker does not control.

### Finding Description
The broken binding is: `status.context == "shipit/checks"` for `repository.full_name == victim_repo` should equal `status.context == "shipit/checks"` for `repository.full_name == attacker_repo`; instead the handler treats them as the same fact because it never checks repository identity.

Code path:
1. `Shipit::WebhooksController#create` parses the JSON body and dispatches to handlers for the `status` event; `verify_signature` only validates that the payload's `repository.owner.login` matches a configured GitHub App/organization secret — it authenticates *which org sent the payload*, not which stack/commit rows may be touched: [1](#0-0) 
2. `StatusHandler#process` then runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — this query is global across all stacks/repositories in the Shipit instance, keyed purely on the SHA string: [2](#0-1) 
3. `Commit#create_status_from_github!` writes a new `Status` row and recomputes `status`/`deployable?` for that commit: [3](#0-2) 
4. `Commit#schedule_continuous_delivery`, invoked via `after_commit ... :schedule_continuous_delivery, on: :create` and also re-evaluated through `add_status`/`stack.schedule_merges`, enqueues `ContinuousDeliveryJob.perform_later(stack)` once the commit becomes `deployable?` and `stack.continuous_deployment?` is true: [4](#0-3) [5](#0-4) 

Because SHAs are content-addressed, a commit that is an ancestor shared between an attacker's fork and the victim's upstream repository has the *same* `sha` value in both repos' `commits` rows (Shipit creates one `Commit` row per stack when it syncs that stack's own repository, but the SHA string is identical). The attacker:
1. Forks or otherwise obtains a repository that shares commit history with the victim's tracked repository, and has a valid GitHub App/webhook installation of their own (satisfying `verify_signature`'s per-organization check for their own org).
2. Sends (or lets GitHub send) a `status` event with `context: "shipit/checks"`, `state: "success"`, and `sha` = the shared ancestor SHA.
3. `verify_signature` passes because it only validates that the *attacker's own org* signed the payload — it does not validate that the SHA or repository named in the payload actually belongs to that org's tracked stack.
4. `StatusHandler#process` matches the victim's `Commit` row purely by SHA and writes a `success` status onto it, exactly as if the victim's own CI had reported it.
5. If the victim's commit was otherwise pending on `shipit/checks` and is now `deployable?`, and the victim stack has `continuous_deployment` enabled, `ContinuousDeliveryJob` is scheduled and can trigger an unauthorized deploy of attacker-influenced history state.

No existing guard closes this gap: `verify_signature` authenticates the sender's organization, not the SHA/repository pairing in the payload; the `ExplicitParameters` schema on `StatusHandler` only validates the shape of `sha`/`state`/`context`, not repository ownership; there is no `repository.full_name` check anywhere in `StatusHandler` or `Commit.create_status_from_github!`.

### Impact Explanation
An attacker can cause a `Status` row to be written for a commit belonging to a repository/stack they do not control and did not authenticate for, satisfying "a payload for one repository mutating another's stack, commit, task or team." Combined with `continuous_deployment` enabled on the victim stack, this can force `ContinuousDeliveryJob` to run and ship (or, with a failing/error status, block) a deploy on the victim stack — an unauthorized deploy/rollback per the Critical impact category. The attack is repeatable against any stack whose tracked repository shares git history (forks, mirrors, or repos merged from a common upstream) with a repository the attacker controls or can get a signed webhook for.

### Likelihood Explanation
Preconditions: the victim stack must require/watch `shipit/checks` status (or another status context) and have `continuous_deployment` enabled; the target commit SHA must exist in both the attacker's org (so their webhook signs correctly) and the victim's stack (via shared ancestry, e.g. fork relationship). Attacker cost is low — pushing/forking is free, and status webhooks are commonly emitted automatically by CI integrations the attacker controls on their own fork. The main constraint is finding/arranging a SHA collision with the victim, which is straightforward for forked repositories sharing base history, making this practically exploitable wherever forks of the victim's repo exist.

### Recommendation
Scope `StatusHandler#process` (and equivalently `CheckRunHandler`) by repository: join/filter `Commit` through its `stack` to `Repository` and only accept statuses whose payload `repository.full_name` matches `stack.repository.full_name`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repository: repo_from_payload }).each { ... }`. Reject or ignore status events whose repository does not match the commit's own stack repository.

### Proof of Concept
minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status for shipit/checks on a shared SHA from a different repository flips victim stack CI state and triggers continuous delivery" do
  victim_stack = shipit_stacks(:shipit).tap { |s| s.update!(continuous_deployment: true) }
  # commit shares SHA with attacker-controlled repo's commit history (fork ancestor)
  shared_sha = "deadbeef" * 5
  victim_commit = victim_stack.commits.create!(sha: shared_sha, message: "shared ancestor")

  # attacker's payload is signed for their OWN org (passes verify_signature),
  # but references the shared SHA that also exists in victim_stack
  payload = {
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'shipit/checks',
  }

  assert_not_equal 'success', victim_commit.reload.state

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack]) do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(payload)
  end

  assert_equal 'success', victim_commit.reload.state
  # Equality that should have held (repo scoping) but does not:
  # attacker_repo.full_name != victim_stack.repository.full_name, yet the write succeeded.
end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
