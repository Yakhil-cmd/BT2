I searched for the analogous root cause across polkadot-sdk: a single generic signature/hash format reused interchangeably between two opposite state-changing actions, combined with a shared "used" flag, such that front-running one action's signature into the other blocks the legitimate operation.

What I found instead is that every signature-based verification path in polkadot-sdk binds the signature to the specific call/action being authorized, rather than to a generic payload shared across multiple, semantically-opposite entry points:

- `pallet-verify-signature`'s `VerifySignature` extension signs over `(extension_version, call, ...)`, i.e., the actual `RuntimeCall` is part of the signed payload, so a signature produced for one call cannot be replayed against a different call. [1](#0-0) 
- `pallet-nfts`'s pre-signed mint and pre-signed attributes flows use distinct, strongly-typed payload structs (`PreSignedMint` vs `PreSignedAttributes`) with their own `deadline`/ownership checks; there's no shared "signature used" bit that a griefer could burn from one call type to block the other. [2](#0-1) [3](#0-2) 
- `pallet-people`'s replay protection for identity/alias binds the message to `(EXTENSION_VERSION, call, other_tx_ext)` and additionally checks stored state equality before rejecting as stale, rather than a raw "signature hash used" set shared across unrelated actions. [4](#0-3) 
- The EIP-2612-style `permit` pallet ties the signature to a nonce that is part of the signed digest and atomically incremented in `use_permit`, so a consumed signature cannot be reused for a different (asset/owner/spender) action, and cross-asset replay is explicitly tested and rejected. [5](#0-4) [6](#0-5) 

In all these cases, the signed payload is scoped to the specific call/action (either by including the call itself, or via typed, purpose-specific structs and monotonic nonces), which is exactly the mitigation the Sherlock report recommends (separate typehashes/domains per action). I did not find a FRAME pallet, XCM path, or bridge component where a single generic digest/hash is verified and marked "used" across two logically-opposite, user-facing extrinsics in a way that would let an attacker front-run and consume a victim's signature to block their legitimate action. Given the extensive search across signature-verification, replay-protection, and pre-signed-approval code paths without finding this pattern, I'm reasonably confident this specific bug class doesn't have a live analog in the scoped code, though I cannot rule out its presence in areas of the codebase not indexed or not surfaced by my searches.

		/// Verify and consume a permit signature atomically.
		///
		/// This is the recommended function for production use. It:
		/// 1. Validates the deadline against the current timestamp
		/// 2. Verifies the signature matches the owner
		/// 3. Increments the nonce to prevent replay attacks
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		///
		/// After this function returns `Ok(())`, the permit cannot be used again.
		pub fn use_permit(
			verifying_contract: &H160,
			name: &[u8],
			owner: &H160,
			spender: &H160,
			value: &[u8; 32],
			deadline: &[u8; 32],
			v: u8,
			r: &[u8; 32],
			s: &[u8; 32],
		) -> Result<(), Error<T>> {
			// Verify the permit first
			Self::do_verify_permit(
				verifying_contract,
				name,
				owner,
				spender,
				value,
				deadline,
				v,
				r,
				s,
			)?;

			// Consume the permit by incrementing the nonce
			// This prevents the same permit from being used again
			Self::increment_nonce(verifying_contract, owner)?;

			Ok(())
		}
