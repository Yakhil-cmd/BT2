### Title
Cross-organization/cross-repository commit-status forgery via `StatusHandler`'s global, unscoped `sha` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to verify a webhook against based solely on the organization embedded in the same payload (`repository.owner.login` / `organization.login`), while the `status` event handler that actually mutates state performs a **global, unscoped** lookup by commit SHA across the entire `Commit` table, with no check that the SHA actually belongs to a commit whose stack/repository is owned by the authenticating organization. This breaks the "organization that authenticated" vs. "repository that is written" binding.

### Finding Description
The webhook signature check picks the org whose secret to verify against straight from the untrusted payload: [1](#0-0) [2](#0-1) 

This only proves the payload was signed with **some** organization's `webhook_secret` — the one named in `repository.owner.login`/`organization.login` inside the very payload being verified. Shipit explicitly supports hosting multiple independent GitHub organizations/apps, each with its own `webhook_secret`, in a single instance: [3](#0-2) 

Once signature verification passes, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, which resolves the target of the write purely by SHA, with **no scoping to the authenticating repository/organization at all**: [4](#0-3) 

Compare this to `Handler#stacks`, used by other handlers (e.g. `PushHandler`), which does scope to the payload's `repository.full_name`: [5](#0-4) 

`StatusHandler` bypasses this scoping entirely and instead does `Commit.where(sha: params.sha)` — a query against the whole database, matching any commit from any stack/repository/organization that happens to share that SHA value, then calls `commit.create_status_from_github!(params)` on each match: [6](#0-5) 

Because commit SHAs are 40-hex-char identifiers, an attacker cannot brute-force an arbitrary victim SHA, but they don't need to: SHAs of commits tracked by a victim stack are routinely exposed in Shipit's own public-facing UI/API (stack pages, deploy pages, `/commit/:sha/checks`, etc.), so an attacker who is only authorized on their own org/repo can read a target SHA and forge a `status` webhook (signed with their own legitimately-obtained `webhook_secret` for their own org) naming that victim SHA.

### Impact Explanation
`create_status_from_github!` writes a new `Shipit::Status` row for the commit and recomputes `Commit#status`/`Commit#deployable?`: [7](#0-6) 

`deployable?` gates whether a commit can be deployed (`success? && !blocked?`), and status changes also trigger `schedule_continuous_delivery`/`ContinuousDeliveryJob`: [8](#0-7) 

By forging a "success" status (with an attacker-chosen `context` matching one of the victim stack's `ci.require` contexts) for a victim commit, an attacker who has no access to the victim organization/repository can flip that commit from CI-pending/failing to CI-passing. If the victim stack has `continuous_deployment` enabled, this can directly trigger an unauthorized deploy via `ContinuousDeliveryJob` → `trigger_continuous_delivery`; even without continuous deployment, it removes the CI safety gate a legitimate deployer relies on before manually triggering a deploy. This is an authentication-boundary violation: possession of a valid signature for organization A is treated as authorization to mutate deploy-gating state for organization B's commits.

### Likelihood Explanation
Exploitability requires: (1) the attacker controls (or can legitimately obtain) a webhook secret for *some* organization configured on the instance — realistic in any multi-org Shipit deployment where the attacker onboards their own repository, and (2) knowledge of a target commit SHA in the victim stack — trivially obtainable since Shipit exposes commit SHAs (and often full git history) through its own read-surface. No privileged access to the victim's repository, stack, or Shipit account is required, satisfying the "unprivileged attacker" bar. The main mitigating factor is that this analog is most impactful only on multi-tenant/multi-org Shipit deployments, and only for stacks that rely on `ci.require`/`ci.blocking` gating or continuous deployment.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/organization that produced the authenticated payload (e.g., via `stacks` from `Handler#repository_name`/`payload.dig('repository','full_name')`) rather than a bare, unscoped `Commit.where(sha: ...)`, mirroring the scoping already done in `PushHandler`.

### Proof of Concept
1. Attacker legitimately installs the Shipit-integrated GitHub App on their own organization `attacker-org`, obtaining a valid `webhook_secret` for it (multi-org config, per `config/secrets.development.example.yml`).
2. Attacker reads a victim stack's public page/API to learn a pending/failing commit `sha` that is being CI-gated (`ci.require: [ci/circleci]`).
3. Attacker crafts a JSON body:
```json
{
  "sha": "<victim_commit_sha>",
  "state": "success",
  "context": "ci/circleci",
  "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker_org_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner` as `attacker-org` and verifies successfully against `attacker-org`'s own secret.
6. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the victim's commit (owned by an unrelated organization/stack), and creates a `success` status on it — regardless of the fact that the authenticated organization was `attacker-org`, not the victim's organization.
