### Title
Missing Field-Boundary Separator in Prosaic/Arbiter Contract Hash Allows Hash Collision Between Different Contract Texts - (File: `prosaic_contract.js`)

### Summary
`prosaic_contract.js` computes the identifier (`hash`) that binds a prosaic/arbiter contract's terms by naively concatenating `contract.title + contract.text + contract.creation_date` and hashing the resulting string, with no delimiter, length-prefix, or field-tagging between the components. This is the same bug class as the reported "improper domain separator" issue: the hash function fails to uniquely commit to the structured tuple `(title, text, creation_date)` — it commits only to the flattened byte string. Two different `(title, text)` pairs that "shift" characters across the title/text boundary (while `creation_date` is unchanged) produce an identical hash, exactly mirroring how using the wrong/insufficiently-specific type hash in the report collapses distinct structured inputs into colliding digests.

### Finding Description
`getHash`/`getHashV1` in `prosaic_contract.js`: [1](#0-0) 

```js
function getHash(contract) {
	return crypto.createHash("sha256").update(contract.title + contract.text + contract.creation_date, "utf8").digest("base64");
}
function getHashV1(contract) {
	return objectHash.getBase64Hash(contract.title + contract.text + contract.creation_date);
}
```

Both functions hash a plain concatenation of three fields with no separator. This is exactly the anti-pattern that `object_hash.js`/`string_utils.js` elsewhere in the codebase were carefully designed to avoid: `getSourceString` explicitly tags every field with a type marker and joins components with a `\x00` separator, and even throws if a string value itself contains the join character, precisely to prevent this kind of field-boundary ambiguity: [2](#0-1) 

`prosaic_contract.js`'s `getHash`/`getHashV1`, however, bypass this protection entirely by pre-concatenating the fields into a single string before hashing (or before calling `objectHash.getBase64Hash`, which cannot recover the original field boundaries once they are erased by string concatenation).

This hash is the authoritative binding between the on-chain evidence and the off-chain contract text: `handleReceivedSigningUnit` verifies a signing unit is bound to a specific contract only by comparing `payload.contract_text_hash` to `contract.hash`: [3](#0-2) 

and `getByHash`/`getBySharedAddress`/`setField` all key contract state by this same `hash` value: [4](#0-3) 

Because `title`, `text`, and `creation_date` are simply concatenated, an attacker who is a counterparty to a prosaic/arbiter contract negotiation (reachable via the wallet/contract message handling path, e.g. `prosaic_contract_offer` / `prosaic_contract_response` device messages processed in `wallet.js`) can construct two different `(title, text)` pairs, e.g. `title="A", text="B pays 100"` and `title="A B pays 1", text="00"`, that concatenate to the identical byte string and thus hash to the identical `contract.hash`, while displaying materially different terms to each party's own UI/storage.

### Impact Explanation
Prosaic/arbiter contracts back a shared (often multisig) address that holds real funds and are used as the basis for dispute resolution/arbitration and for the on-chain `data` message that proves acceptance (`contract_text_hash`). Because the hash does not uniquely commit to the tuple of fields, a malicious counterparty can:
- Present one version of contract text to get the counterparty's on-chain deposit/signature (bound only to the colliding hash, not to the exact text), and
- Later present or store a different `(title, text)` pair with the same hash, creating ambiguity about the actual agreed terms during dispute/arbitration, which can be leveraged to divert or freeze funds held in the shared/arbiter address, since arbitration and settlement rely on the `hash`/`contract_text_hash` binding being unique to one specific text.

This maps to the "AA/contract fund loss or freezing via node/party disagreement on validity of agreement terms" category, since it undermines the sole cryptographic binding between the shared-address funds and the human-readable, dispute-relevant terms.

### Likelihood Explanation
Constructing a colliding `(title, text)` pair is trivial (just move a character run across the title/text boundary) and requires no computational effort, unlike a true hash-preimage/collision attack — it is a structural/encoding flaw, not a cryptographic weakness of SHA-256 itself. Any party negotiating a prosaic or arbiter contract (a normal, unprivileged wallet/device-message flow) can trigger it. The main constraint is that it requires deliberate action by a dishonest contract counterparty and downstream reliance on the ambiguous text during arbitration.

### Recommendation
Compute the contract hash over a properly domain-separated / length-prefixed structure instead of raw concatenation, e.g. by using the existing `objectHash.getBase64Hash({title, text, creation_date})` (object form, not string concatenation) so that `string_utils.getSourceString`'s type-tagged, `\x00`-separated encoding is applied, or otherwise insert unambiguous length-prefixes/separators between `title`, `text`, and `creation_date` before hashing.

### Proof of Concept
```js
const prosaic_contract = require('./prosaic_contract.js');

const contractA = { title: "A", text: "B pays 100", creation_date: "2024-01-01" };
const contractB = { title: "A B pays 1", text: "00", creation_date: "2024-01-01" };

console.log(prosaic_contract.getHash(contractA));
console.log(prosaic_contract.getHash(contractB));
// Both print the identical base64 SHA-256 hash, despite materially different (title, text)
```
Both `contractA` and `contractB` concatenate to the same string (`"AB pays 1002024-01-01"`), so `getHash`/`getHashV1` produce identical digests for two contracts with different visible terms, breaking the uniqueness of the on-chain `contract_text_hash` binding used in `handleReceivedSigningUnit`.
