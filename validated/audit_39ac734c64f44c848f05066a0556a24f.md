### Title
Debug logging of private-payment blinding factors and other secret payment chain data enables theft of private/indivisible-asset outputs - (File: indivisible_asset.js)

### Summary
The Undertow CVE (GHSA-8vh8-vc28-m2hf) shows how DEBUG-level logging of sensitive material (credentials) lets anyone with log access misuse that material. ocore has an analogous pattern: when a private-payment chain is received from a counterparty and saved, the full chain — including the output's `blinding` factor — is written to the console/log with `console.log`. [1](#0-0)  The `blinding` value is a secret that, together with the amount, is required to prove ownership/spend a private (indivisible) asset output whose amount is otherwise hidden on-chain behind `output_hash`. [2](#0-1) 

### Finding Description
`validateAndSavePrivatePaymentChain()` is invoked when a node processes an incoming private-payment chain (`arrPrivateElements`) supplied by a private-payment counterparty (e.g., via `handlePrivatePaymentChains` in `wallet.js`). On success it immediately logs the entire chain as JSON:
```
console.log("saving private chain "+JSON.stringify(arrPrivateElements));
``` [3](#0-2) 

This object contains, for each element, `objPrivateElement.output.blinding` and `objPrivateElement.output.address`, which are subsequently written into the `outputs` table as the secret proof data for the spendable output: [2](#0-1) 

Because the amount of a private/indivisible-asset output is hidden on the public DAG (`output_hash` only), the `blinding` value (plus amount/address) is the only proof needed to reveal and subsequently spend that output in the next hop of the private chain — functioning like a bearer secret/credential for that specific output, analogous to the "user credentials" the Undertow advisory warns about leaking into DEBUG logs.

A related and equally reachable sink exists in device message handling: incoming/outgoing encrypted device messages (which carry the same kind of private-payment chains, wallet approvals, and other secret payloads exchanged between paired devices) are logged in cleartext after decryption: [4](#0-3) 
and before encryption when sending: [5](#0-4) 

Any node operator who captures stdout to a log file (a very common Node.js deployment pattern, exactly the "debug logging enabled" precondition in the referenced CVE) ends up persisting these secrets to disk in plaintext, where they can be exfiltrated by anyone with read access to log files (backup systems, log aggregators, shared hosting, misconfigured permissions, etc.) — mirroring the exact bug class in GHSA-8vh8-vc28-m2hf.

### Impact Explanation
If the `blinding` factor for a private/indivisible asset output leaks from logs, an attacker who also learns (or brute-forces, given the hidden amount is now known too) the associated `output_hash` structure can construct and forward a competing valid spend of that specific output before the legitimate recipient does, resulting in theft of private-asset funds / unauthorized spending of a payment that the true counterparty had not yet finalized. This is a concrete unauthorized-spending impact, not merely an information disclosure of low value, because the leaked value is functionally the redemption secret for the private output rather than public metadata.

### Likelihood Explanation
Likelihood depends on an operator running the node with logs captured/persisted (default in most process managers such as `pm2`, `systemd`, `forever`, or Docker where stdout is captured to files) and an attacker gaining access to those logs. This exactly matches the precondition of the original CVE ("if enabled" / captured). The triggering data itself (the private chain with its blinding factor) is fully attacker/counterparty-supplied and reaches the logging call on every private payment exchange, i.e., it is trivially reachable by any private-payment counterparty, making the vulnerable code path exercised in normal operation without any special conditions.

### Recommendation
Remove or redact the `console.log("saving private chain "+JSON.stringify(arrPrivateElements))` statement in `indivisible_asset.js`, and similarly redact/remove logging of decrypted/encrypted device-message payloads in `device.js` (`decryptPackage` and `reliablySendPreparedMessageToHub`). If verbose logging is needed for debugging, log only non-sensitive metadata (unit hashes, counts, message types) and strip fields such as `blinding`, private-chain contents, and full device-message bodies before logging.

### Proof of Concept
1. Node operator runs the wallet/hub with stdout redirected to a log file (common deployment practice).
2. A private-payment counterparty sends a legitimate private-asset payment chain to the node via the normal private-payments flow, reaching `wallet.handlePrivatePaymentChains` → `indivisible_asset.validateAndSavePrivatePaymentChain`.
3. The full chain, including `output.blinding`, is written to the log file via the `console.log` at [3](#0-2) .
4. Anyone who later obtains read access to that log file (log shipping service, misconfigured file permissions, shared server, etc.) recovers the `blinding` value and address for the output.
5. Using the recovered `blinding`/amount/address, the attacker constructs a rival transfer message for the same output and forwards it through the network ahead of the legitimate recipient's own spend, resulting in the private-asset funds being redirected/stolen — an unauthorized spend of the private payment.
