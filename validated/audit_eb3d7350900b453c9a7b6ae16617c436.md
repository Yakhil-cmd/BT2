### Title
Autonomous Agents can read attacker-controlled, unstabilized (unconfirmed) data-feed oracle values, enabling in-flight price/oracle manipulation before consensus finality - ([File: data_feeds.js])

### Summary
The Vesper Finance incident involved an attacker manipulating an oracle price feed within a short window to drain a lending pool before the price could be corrected. In ocore, the AA (Autonomous Agent) `data_feed[[...]]` and `in_data_feed[[...]]` oscript functions do not require the referenced oracle's data feed unit to be stable/final. When evaluated inside AA logic, `unstable_opts` is passed as `bAA` (truthy), which makes `readDataFeedValue`/`dataFeedExists` in `data_feeds.js` scan `storage.assocUnstableMessages` for **any unconfirmed AA-authored unit** matching the requested oracle address(es), and use its feed value immediately — before the unit is stable and before conflicting/competing values from the same oracle address(es) can be resolved by finality.

### Finding Description
`readDataFeedValue` in [1](#0-0)  is invoked from AA formula evaluation with `unstable_opts = bAA`: [2](#0-1) 
When `bIncludeUnstableAAs` is true, the function iterates `storage.assocUnstableMessages` — i.e., units that are **not yet stable** — and accepts any `data_feed` message from a matching, not-yet-finalized AA unit as a valid oracle reading: [3](#0-2) 
The same unstable-scan behavior exists for boolean existence checks in `dataFeedExists`: [4](#0-3) 

Because an oracle address can itself be an AA (or any address able to post `data_feed` messages) and its unit only needs to be posted — not stabilized — a single attacker who controls (or colludes with) the referenced oracle address can post a manipulated `data_feed` value in a unit, then immediately trigger a victim AA (in the same DAG round, before the oracle's unit stabilizes) that reads that value via `data_feed[[oracles=..., feed_name=...]]` to price an exchange, mint/burn, or payout decision. If the oracle's unit later fails to stabilize with the same content (e.g., it loses a race to a conflicting/competing unit, or the "good/bad sequence" outcome differs once consensus is reached), the victim AA has already made irreversible fund transfers based on a value that never became canonical, since AA state-change/payment messages, once triggered and included in a unit, cause real transfers regardless of what happens to the *unstable* oracle input afterward.

This differs from intended, documented light-wallet behavior (`unstable_opts === 'all_unstable'`), which is explicitly opt-in for wallet UX (`network.js` `light/get_data_feed`) and not meant for trust-critical AA fund logic: [5](#0-4) 
For AAs, however, the unstable-read path is unconditionally enabled any time `bAA` is true — i.e., every AA execution — with no way for the AA author to force "wait for stability" beyond using `min_mci`, which constrains freshness relative to the main chain but does **not** require the feed-posting unit itself to be stable.

### Impact Explanation
An AA that relies on `data_feed`/`in_data_feed` results to gate payments, minting, redemption ratios, or liquidation logic is exposed to values from units that have not yet achieved DAG finality. If the attacker can arrange for the oracle-address unit to ultimately be treated differently upon stabilization (invalidated as duplicate/conflicting, superseded by a later value from the same address, or excluded due to non-'good' sequence) than what the AA used when it acted, the AA's already-executed payment/state changes are irreversible, resulting in AA fund loss, incorrect pricing-based settlement, or freezing/drain of AA-held assets analogous to the $1M loss in the referenced incident. This maps directly to "concrete... AA fund loss or freezing" per the validation criteria.

### Likelihood Explanation
Likelihood is elevated because: (1) this code path executes on every single AA data-feed read, not a rare/edge configuration; (2) an unprivileged unit poster who controls or colludes with the referenced oracle address can trivially post a `data_feed` unit and, within the same unstable window, trigger the dependent AA; (3) no additional privilege beyond normal unit-posting/AA-triggering rights is required. The main constraining factor is that the *victim* AA's oscript logic must reference an oracle address the attacker controls or can race — this is a property of individual AA definitions rather than of ocore's core validation, so the severity of any concrete instance depends on which oracle addresses an AA trusts. Still, the underlying platform mechanism (`data_feeds.js`) provides no safeguard or opt-out to force AAs to only consider stabilized oracle data by default, making the exposure structural to ocore's data-feed primitive rather than to individual buggy dApp contracts.

### Recommendation
- Default AA data-feed reads (`bAA` path) to stable-only data unless the AA explicitly opts into `'all_unstable'`/unstable reads (mirroring the light-wallet opt-in model in `network.js`), so unstable/unstabilized units cannot silently influence irreversible AA financial logic.
- If unstable reads must remain the default for AA composability, expose an explicit oscript flag (e.g., `stability='stable'`) so AA authors can require finality for trust-critical price/oracle data, and document the finality risk prominently in `data_feed`/`in_data_feed` semantics.
- Consider requiring `sequence === 'good'` AND full stabilization (not just presence in `assocUnstableMessages`) before a data-feed value can be used to authorize state changes that move real value.

### Proof of Concept
1. Attacker controls address `O` (an oracle address that some victim AA `V` is configured to trust for feed `PRICE`).
2. Attacker posts unit `U1` from `O` containing `data_feed: {PRICE: 999999}` (a manipulated/extreme value). `U1` is valid but not yet stable.
3. Before `U1` stabilizes, attacker sends a trigger unit to AA `V` whose oscript logic executes `data_feed[[oracles="O", feed_name="PRICE"]]`. Because AA evaluation passes `bAA=true` as `unstable_opts`, `readDataFeedValue` finds `U1` in `storage.assocUnstableMessages` (per `data_feeds.js:211-240`) and returns `999999` even though `U1` has not stabilized.
4. AA `V` executes a payment/mint/redemption based on `999999`, transferring/issuing funds accordingly.
5. If `U1` subsequently fails to stabilize as posted (e.g., loses to a conflicting non-serial/non-good-sequence unit from `O`, or a later `data_feed` unit from `O` supersedes it before finality), the AA's transfer already happened and cannot be reversed — the fund loss/inflation is final while the oracle input that caused it was never canonical.
