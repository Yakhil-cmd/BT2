### Title
Missing cosigner-authorization check in `sign` message handler allows any paired device to trigger signing prompts for local addresses - (File: wallet.js)

### Summary
`wallet.js`'s `handleMessageFromHub()` dispatches wallet-to-wallet protocol messages received over the hub, similar in structure to free5GC's SBI route groups. For the `sign` subject, the code performs strong structural/cryptographic validation of the unsigned unit and its private payloads, but the actual authorization check — verifying that the sending device (`from_address`) is a legitimate cosigner of the target `body.address` — is explicitly commented out, unlike sibling handlers (`prosaic_contract_shared`, `arbiter_contract_shared`) that perform this exact check via `wallet_signing_paths`/`my_addresses` joins. [1](#0-0) 

### Finding Description
In the `sign` case of `handleMessageFromHub`, once the target address is resolved to be locally known (`ifLocal`), the code should verify that `from_address` (the device that sent the message) is actually one of the device cosigners for `body.address`. This check is present in analogous handlers: [2](#0-1) [3](#0-2) 

But in `sign`, the equivalent DB check is commented out:

As a result, *any* paired device (any correspondent known to the wallet — including a newly-paired, low-trust correspondent) can send a `sign` request naming any locally-controlled address it can guess or learn (e.g., from chat history, a shared invoice, or a previous transaction), including addresses the sender is not a legitimate signer/cosigner of. The handler proceeds to validate the unit structurally and then fires the `signing_request` UI event: [5](#0-4) 

This event is meant to trigger a user-facing confirmation dialog in the wallet UI. Because the sender-cosigner relationship is not verified, an untrusted correspondent can craft an arbitrary unsigned unit (with attacker-chosen outputs) naming the victim's local address as one of the multiple authors, and get the wallet to surface it as a legitimate multi-signature/multilateral signing request. If the user (who may not carefully inspect a technical signing dialog, especially in multi-device/dumb-contract flows) approves, the wallet will co-sign and can broadcast a unit that moves the user's funds to attacker-controlled outputs.

### Impact Explanation
This maps to the CWE-862 "missing authorization" root cause in the reference report: a handler that reaches sensitive business logic (composing a co-signature over a unit that spends the user's on-chain funds) without verifying that the caller (paired device) is actually entitled to request that action for the given address. Under the "Validate" acceptance criteria, this can lead to concrete unauthorized spending if a user approves the deceptive signing prompt, since the missing check is the sole gate preventing arbitrary paired devices from initiating spend-authorization workflows for addresses they don't co-own.

### Likelihood Explanation
Reachable by any device the wallet has paired/corresponded with (a legitimate but potentially malicious/compromised counterparty), which matches the allowed "paired device" actor class. No p2p/hub compromise or key leakage is required — only a pairing relationship, which is a normal, low-barrier interaction (e.g. accepting a pairing link from a merchant, dApp, or chat contact). The comment in the code ("the commented check would make multilateral signing impossible") indicates the removal was intentional to support the multilateral-signing/contract-signing use case, but it removes authorization uniformly for all uses of `sign`, including plain multisig-address co-signing where the check is meaningful and should still apply.

### Recommendation
Restore an authorization check before honoring a `sign` request against a local address: verify that `from_address` is a known cosigner/device for `body.address` (via `wallet_signing_paths`/`extended_pubkeys` for wallet-defined addresses, and via `shared_addresses`/definition device list for shared addresses) OR, if multilateral/dumb-contract signing must be supported without a pre-existing cosigner relationship, gate this exception narrowly (e.g., only when the unit's definition explicitly includes `from_address`'s counterpart address as an author, and clearly surface in the UI that the request comes from an unrelated/first-time device) rather than removing the check globally.

### Proof of Concept
1. Device A pairs with Device B (wallet) via a normal pairing code — a routine, low-privilege interaction.
2. Device A learns/guesses one of Device B's local addresses that is part of a multisig or shared-address definition (addresses are often shared during normal transacting or contract negotiation).
3. Device A crafts an unsigned unit whose `authors` array includes `body.address` (Device B's local address) alongside attacker-controlled payment outputs, and sends a `sign` message: `{address: body.address, signing_path: "r", unsigned_unit: {...attacker-controlled outputs...}}`.
4. On Device B, `handleMessageFromHub` processes `case "sign"`: structural validation passes (all attacker-supplied fields can be made internally consistent), `findAddress` resolves `ifLocal`, and since the cosigner check is commented out, `callbacks.ifOk()` fires immediately and `signing_request` is emitted to the UI for user confirmation — without ever verifying Device A is entitled to request this.
5. If the wallet user approves the resulting signing dialog (which does not indicate that the requester is not a legitimate cosigner), Device B contributes its signature, potentially completing a unit that spends funds to attacker-chosen outputs.
