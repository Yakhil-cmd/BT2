This confirms the vulnerability. `Api::CCMenuController#stack` at [1](#0-0)  overrides the base class's scoped lookup at [2](#0-1)  which restricts lookup to `stacks` (itself scoped by `current_api_client.stack_id` at [3](#0-2) ). Instead it calls `Stack.from_param!` directly against the entire `Stack` table, bypassing the per-client stack restriction entirely.

The permission check `require_permission!` only validates the operation/scope string against `ApiClient#permissions` via `check_permissions!` at [4](#0-3) , and never compares `params[:stack_id]` to `current_api_client.stack_id`. So a token scoped to stack A with `permissions=['read:stack']` passes `require_permission!(:read, :stack)` unconditionally, then `stack` resolves to whatever stack the request names, including stack B.

### Title
CCMenuController#show bypasses ApiClient stack scoping via unscoped Stack.from_param! - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::CCMenuController` overrides the base controller's `stack` helper to call `Stack.from_param!(params[:stack_id])` directly instead of the scoped `stacks.from_param!`, so a stack-scoped `ApiClient` token can view CCTray build/deploy status for any stack, not just the one it's scoped to.

### Finding Description
The claimed binding `current_api_client.stack_id == B.id` must hold before rendering stack B's data, but it does not. `Api::BaseController#stack` enforces scoping by first restricting the queryable set via `stacks`, which filters to `Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true ( [5](#0-4) ). `Api::CCMenuController` overrides `stack` to instead do `@stack ||= Stack.from_param!(params[:stack_id])` ( [1](#0-0) ), which resolves against the entire `Stack` table with no scoping by `current_api_client.stack_id`.

`require_permission :read, :stack` ( [6](#0-5)  and [7](#0-6) ) only calls `current_api_client.check_permissions!(operation, scope)`, which merely checks whether `"read:stack"` is present in the client's `permissions` array ( [4](#0-3) ). It never inspects `params[:stack_id]` or compares it against `current_api_client.stack_id`.

Attack: attacker holds a valid token for `ApiClient` scoped to stack A (`stack_id == A.id`, `permissions=['read:stack']`). They send `GET /api/stacks/:owner_b/:repo_b/:branch_b/cctray.xml?token=<A's token>` (or via Basic Auth) naming stack B. `authenticate_api_client` (overridden in this controller to accept `params[:token]`, [8](#0-7) ) authenticates as A's client. `require_permission!(:read, :stack)` passes because A has `read:stack`. `stack` resolves stack B via the unscoped `Stack.from_param!`, and `#show` renders stack B's CCTray XML ( [9](#0-8) ), leaking stack B's deploy/build status to an attacker who was only authorized for stack A.

### Impact Explanation
This is an unauthorized cross-stack read of stack B's deploy/build status (name, activity, last build status/label/time, web URL) by a token holder scoped only to stack A. This is repeatable against any stack in the installation simply by varying `params[:stack_id]`, since the lookup is completely unscoped. This matches the High severity category "unauthenticated/unauthorized read of stack state" — here more precisely an authorization-scope-bypass read of stack state across tenants (stack A's client reading stack B's build state), since scoped API clients are meant to be confined to their own stack per the multi-tenant model implied by `ApiClient#stack_id` and `Api::BaseController#stacks`.

### Likelihood Explanation
The only precondition is possession of any valid stack-scoped `ApiClient` token with `read:stack` permission — a low-privilege credential intentionally scoped to a single stack by an operator. No GitHub secrets, sessions, or elevated roles are needed. The attacker only needs to know or guess another stack's `to_param` (typically `owner/repo/branch`, often public/discoverable information), and the exploit is a single unauthenticated-relative-to-B GET request, fully repeatable against every stack in the Shipit instance.

### Recommendation
Change `Api::CCMenuController#stack` to use the scoped lookup consistent with the base controller, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, removing the override entirely so it inherits `Api::BaseController#stack`.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (`ApiControllerTestCase`):
1. Create `stack_a = Stack.create!(...)` and `stack_b = Stack.create!(...)`.
2. Create `client_a = ApiClient.create!(creator: user, name: 'a', stack: stack_a, permissions: ['read:stack'])`.
3. `get :show, params: { stack_id: stack_b.to_param, token: client_a.authentication_token }`.
4. Assert `current_api_client.stack_id == stack_a.id` (token's actual scope) while the response is `200 OK` and `assert_payload 'name', stack_b.to_param` — i.e., stack B's data is returned even though `current_api_client.stack_id != stack_b.id`, proving the binding `current_api_client.stack_id == B.id` does not hold before rendering B's data.
5. Contrast with `Api::StacksController` or other actions using `stacks.from_param!`, where the same request would raise `RecordNotFound` (404) instead of 200.
