### Title
Webhook organization used for signature verification is decoupled from the repository acted upon, allowing cross-repository event forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the webhook secret to validate an inbound GitHub webhook against based on `repository.owner.login` (or `organization.login`), but the handlers that actually mutate state key off `repository.full_name`, a separate, independently attacker-controlled field within the same JSON body. Because the two fields are never cross-checked against each other, an operator who legitimately controls the webhook secret for one organization/repository configured in Shipit can forge a payload whose `owner.login` matches their own org (so it passes signature verification with their own valid secret) while `full_name` names an entirely different repository/stack managed by the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/secret purely from the owner field: [1](#0-0) [2](#0-1) 

Once verification succeeds, the raw params are dispatched unmodified to handlers: [3](#0-2) 

Every handler resolves the target `Repository`/`Stack` from a *different* field, `repository.full_name`, via `Handler#repository_name` / `#stacks`: [4](#0-3) 

`Repository.from_github_repo_name` splits `full_name` into `owner/name` and looks up the record directly, with no requirement that it matches the `owner.login` used for signature selection: [5](#0-4) 

Concretely, `PushHandler` uses this `stacks` scope (built from `full_name`) to trigger a GitHub sync for an arbitrary stack: [6](#0-5) 

This is structurally the same class of bug as the referenced report: two related values that should be locked together (the field the security check is performed against vs. the field the effectful logic actually consumes) are computed independently, so a value that "passes" the check does not guarantee validity of the value that is later used. Here the broken binding is: `organization authenticated by the signature check == repository/stack actually written by the handler`.

### Impact Explanation
An org/repo owner who is a legitimate Shipit customer (and therefore possesses a valid webhook secret for their own org) can send a `push`, `status`, `check_suite`, or `pull_request` webhook whose `repository.owner.login` is their own org (passing `verify_signature`) but whose `repository.full_name` targets a completely different repository hosted on the same Shipit instance. Depending on handler:
- `PushHandler` forces `GithubSyncJob`/`sync_github` on a victim stack with an attacker-chosen `expected_head_sha`.
- `StatusHandler` writes fabricated commit statuses (`Commit#create_status_from_github!`) against arbitrary shas in the victim's repository, which can influence deployability/merge gating for that stack.
- `check_suite`/`pull_request` handlers can similarly manipulate merge-request state, labels, or deployable status for a stack they do not own.

This is a cross-repository write achieved purely by holding credentials scoped to a different repository/org than the one being mutated, which meets the Critical bar of "cross-repository writes" / "unauthorized deploy, rollback, or merge" depending on which handler is abused, since commit status manipulation feeds into deploy eligibility decisions elsewhere in the app.

### Likelihood Explanation
Likelihood requires the attacker to be an onboarded Shipit user/organization (holder of a valid webhook secret for at least one org configured on the instance) — this is the "unprivileged" bar relative to *other* repositories, matching the rule's allowed threat model of "an organization that authenticated versus the repository that is written." No GitHub App private key, `api_clients_secret`, or session is required — only knowledge of one's own legitimately-provisioned webhook secret and the ability to POST directly to `/webhooks` with a crafted `full_name`.

### Recommendation
Cross-validate that `repository.owner.login` (the value used to select/verify the signing secret) matches the owner segment of `repository.full_name` before dispatching to handlers, e.g. reject the payload if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. Alternatively, always derive the target repository from the same field used for signature verification, or embed/verify the full repository identity as part of the webhook secret selection so a single secret cannot authorize actions on repositories with a different owner.

### Proof of Concept
1. Attacker's Shipit instance has two orgs configured: `attacker-org` (attacker controls its GitHub App/webhook secret) and `victim-org` (unrelated, managed by the same Shipit deployment).
2. Attacker crafts a `push` event body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...attacker-chosen-sha",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using the webhook secret for `attacker-org` (which they legitimately possess) — `verify_signature` calls `Shipit.github(organization: 'attacker-org')`, verifies successfully. [1](#0-0) 
4. `Shipit::Webhooks.for_event('push')` runs `PushHandler`, which resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` — a repository the attacker has no legitimate secret for — and forces a sync using the attacker-supplied `expected_head_sha`. [6](#0-5) [5](#0-4)
