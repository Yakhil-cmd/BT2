### Title
Unchecked ERC721 `transferFrom` Return in `requestERC721Transfer` Allows Unauthorized Cross-Chain NFT Minting Without Depositing the Token — (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.requestERC721Transfer` calls `IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId)` without verifying the transfer succeeded. If a registered non-standard ERC721 token silently fails (does not revert), the bridge proceeds to emit `RequestValueTransferEncoded` and increment `requestNonce`, causing bridge operators on the counterpart chain to mint or release an NFT to the attacker — with no NFT ever deposited on the source chain.

---

### Finding Description

`BridgeTransferERC721.sol` line 129 performs a bare `transferFrom` call:

```solidity
// requestERC721Transfer — BridgeTransferERC721.sol:129
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
_requestERC721Transfer(_tokenAddress, msg.sender, _to, _tokenId, _extraData);
``` [1](#0-0) 

`_requestERC721Transfer` unconditionally emits `RequestValueTransferEncoded` and increments `requestNonce`:

```solidity
emit RequestValueTransferEncoded(..., requestNonce, ...);
requestNonce++;
``` [2](#0-1) 

The ERC20 counterpart in `BridgeTransferERC20.sol` correctly uses `safeTransferFrom` from OpenZeppelin's `SafeERC20`, which reverts on both explicit `false` returns and non-reverting failures:

```solidity
// requestERC20Transfer — BridgeTransferERC20.sol:133
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
``` [3](#0-2) 

`BridgeTransferERC721` does not import or use `SafeERC20` or any equivalent safe-transfer wrapper for ERC721. The `IERC721.transferFrom` interface declares no return value, so Solidity discards any returned data and the call is considered successful as long as it does not revert. [4](#0-3) 

A second unchecked `transferFrom` also exists in `handleERC721Transfer` (lock/unlock mode), where the bridge sends an NFT to the recipient without verifying success:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [5](#0-4) 

---

### Impact Explanation

When bridge operators observe a `RequestValueTransferEncoded` event on the source chain, `handleRequestValueTransferEvent` in `bridge_manager.go` automatically calls `HandleERC721Transfer` on the counterpart bridge: [6](#0-5) 

In `modeMintBurn`, `handleERC721Transfer` mints a new NFT to the attacker's chosen recipient:

```solidity
require(ERC721MetadataMintable(_tokenAddress).mintWithTokenURI(_to, _tokenId, _tokenURI), "mint failed");
``` [7](#0-6) 

In lock/unlock mode, it transfers an NFT from the bridge's own reserves to the attacker's recipient. In both cases, the attacker receives a bridged NFT on the destination chain without ever depositing the corresponding NFT on the source chain. This is an **unauthorized mint or transfer of a bridged asset**.

---

### Likelihood Explanation

The precondition is that a non-standard ERC721 token — one whose `transferFrom` does not revert on failure — must be registered with the bridge by the bridge owner. This is a semi-trusted trigger: the bridge owner registers tokens, but may not audit every token's failure behavior. Non-standard ERC721 tokens that return `false` or silently no-op on failed transfers exist in practice. Any user can then call `requestERC721Transfer` with such a registered token to exploit the vulnerability.

---

### Recommendation

Replace the bare `IERC721.transferFrom` call in `requestERC721Transfer` with a post-transfer ownership check, or use `safeTransferFrom` (which triggers `onERC721Received` on the bridge and can be used to verify receipt). At minimum, assert ownership after the call:

```solidity
IERC721(_tokenAddress).transferFrom(msg.sender, address(this), _tokenId);
require(IERC721(_tokenAddress).ownerOf(_tokenId) == address(this), "ERC721 transfer failed");
```

Apply the same fix to the `handleERC721Transfer` lock/unlock path (line 69). The ERC20 path's use of `SafeERC20.safeTransferFrom` is the correct pattern to follow. [8](#0-7) 

---

### Proof of Concept

1. Deploy a non-standard ERC721 token `MaliciousNFT` whose `transferFrom` does nothing and does not revert.
2. Bridge owner registers `MaliciousNFT` on the source-chain bridge (satisfies `onlyRegisteredToken`).
3. Attacker calls `requestERC721Transfer(maliciousNFT, attackerAddr, tokenId, "")`.
4. `IERC721(maliciousNFT).transferFrom(attacker, bridge, tokenId)` silently no-ops — attacker retains the NFT.
5. `_requestERC721Transfer` emits `RequestValueTransferEncoded` with `requestNonce = N` and increments `requestNonce`.
6. Bridge operators observe the event and call `handleERC721Transfer` on the counterpart chain with nonce `N`.
7. In `modeMintBurn`: `mintWithTokenURI(attackerAddr, tokenId, uri)` mints a new NFT to the attacker on the destination chain.
8. In lock/unlock mode: `transferFrom(bridge, attackerAddr, tokenId)` transfers an NFT from the bridge's reserves to the attacker.

**Result**: Attacker receives a bridged NFT on the destination chain without depositing anything on the source chain — unauthorized transfer/mint of a bridged asset. [9](#0-8) [7](#0-6)
