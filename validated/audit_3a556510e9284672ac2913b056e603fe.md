### Title
Missing dust floor for custom-asset inputs lets an attacker inflate/stall an AA's payment composition and freeze its ability to distribute or withdraw that asset - (File: aa_composer.js)

### Summary
Ocore's Autonomous Agent (AA) engine already recognizes and mitigates a "dust flooding" attack for the base asset (bytes) when an AA composes its response payment: outputs smaller than `FULL_TRANSFER_INPUT_SIZE` are excluded from the candidate-input query, explicitly to stop spammers from forcing the AA to burn its balance on fees. [1](#0-0)  This same floor is **not** applied when the asset is a custom (non-base) asset — the SQL condition only enforces the amount threshold for the base-asset branch, leaving the custom-asset branch unfiltered. [2](#0-1)  Because `iterateUnspentOutputs()` walks every returned row and keeps adding it as a payment input until the target amount is reached (or, for send-all outputs, until the whole balance is exhausted), an attacker can pre-seed an AA address's custom-asset balance with a very large number of near-zero-value outputs, forcing any later AA-composed payout of that asset to absorb all of them as inputs. [3](#0-2) 

This is directly analogous to the Ajna H-6 report: there, an attacker planted "dust" quote-token deposits in many buckets to force an iterative settlement routine (`_settlePoolDebtWithDeposit`) to walk through worthless entries, exhausting the bounded iteration budget and blocking legitimate debt write-off/fund recovery. In ocore, the equivalent iterative routine is the AA's own input-selection loop (`completePaymentPayload` → `iterateUnspentOutputs`), and the equivalent "settlement" is the AA's payout/withdraw/distribution logic that must eventually spend its full asset balance (e.g., on `send-all` responses).

### Finding Description
`sendUnit()` in `aa_composer.js` builds the AA's response payment(s) via `completePaymentPayload()`. When collecting inputs to fund an outgoing payment, it queries unspent outputs sent to the AA address:

```
WHERE address=? AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" AND is_spent=0 ...
``` [2](#0-1) 

For the base asset (`asset` falsy), the query explicitly discards any output whose `amount` is below `FULL_TRANSFER_INPUT_SIZE`, with the accompanying comment: "byte outputs less than 60 bytes (which are net negative) are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond." [4](#0-3)  The same protection is missing for a custom `asset`: any output of that asset, however small (even amount=1), is a valid candidate and is fetched unconditionally.

The identical unfiltered pattern is repeated in the secondary query that reads unstable outputs sent by other AAs. [5](#0-4) 

`iterateUnspentOutputs()` then processes every returned row in order, pushing each as an input and accumulating `total_amount`, stopping only once `total_amount` satisfies `target_amount` (or, for a "send-all" output, continuing until all rows are exhausted since the entire balance must be paid out). [3](#0-2) 

There is no per-asset dust floor, no cap on how many dust inputs a single call will accumulate, and no separate accounting for "worthless" entries versus meaningful balance — mirroring exactly the missing-dust-control root cause identified in the Ajna report for `addQuoteToken()`.

### Impact Explanation
Because arbitrary users can freely send outputs of any asset — including one they define/issue themselves, or a transferable asset already used by the AA's own logic — to any AA address at negligible cost (a single-output payment message), an attacker can pre-load an AA's tracked custom-asset balance with a huge number of dust outputs. Once the AA is later triggered to pay out that asset (a common oscript pattern is a `send-all` output on withdrawal, refund, or reward-distribution AAs), the composer must fold every one of these dust outputs into the outgoing payment's inputs to correctly account for the entire balance.

This inflates the size of the AA-generated response unit far beyond what the AA's legitimate depositors intended, which:
- increases the unit's payload/oversize fees the AA itself must pay out of its own byte balance (charged via `getOversizeFee()` in the same function) [6](#0-5) , and
- can exhaust the AA's byte balance to the point where `sendUnit()`/`bounce()` fails with "not enough balance in base", preventing the payout (and any accompanying state update) from completing at all. [7](#0-6) 

The practical effect is that a single unprivileged actor can, at low cost, freeze or indefinitely delay an AA's ability to distribute/withdraw a specific asset balance to its legitimate beneficiaries — the same class of harm as the Ajna bug: an actor cheaply stalls a fund-release/settlement mechanism that other participants depend on, to their detriment.

### Likelihood Explanation
Sending payment outputs of an arbitrary (including self-issued) asset to any known AA address requires no special privilege and is inexpensive — the only cost is standard commission per unit, which is far lower than the cumulative griefing effect on the target AA (which pays proportionally larger oversize fees for every dust input it must absorb). Any AA design that (a) tracks/pays out balances of a user-transferable or attacker-issuable custom asset, and (b) uses a `send-all` (or "pay everything received of asset X") response pattern, is directly exposed. This is a common, encouraged idiom in oscript AA templates.

### Recommendation
Apply the same dust-floor principle already used for the base asset to custom-asset input selection in `aa_composer.js`:
- Compute and enforce a minimum "economically meaningful" input amount for the relevant asset (analogous to `FULL_TRANSFER_INPUT_SIZE` for bytes) in both `readStableOutputs()` and `readUnstableOutputsSentByAAs()`. [8](#0-7) 
- Alternatively/additionally, bound the number of inputs `iterateUnspentOutputs()` will absorb per payment message (independent of the `!objValidationState.bAA` exemption from `MAX_INPUTS_PER_PAYMENT_MESSAGE` in `validation.js`), so an AA-authored unit cannot be forced into unbounded size by attacker-seeded dust.
- Consider tracking and periodically "sweeping"/merging dust outputs separately from the payout path, so legitimate distributions are not blocked by attacker-controlled entries.

### Proof of Concept
Conceptual PoC (exact constant values such as `FULL_TRANSFER_INPUT_SIZE`/oversize-fee thresholds were not independently re-verified in this pass and should be confirmed by a maintainer before treating exact numeric thresholds as final):
1. Attacker deploys/uses an asset `X` that is freely transferable (or self-issues it if allowed) at negligible cost.
2. Attacker crafts and posts many units, each containing a payment message with a single output `{address: <AA_address>, asset: X, amount: 1}` to the target AA's address, repeated a large number of times.
3. Because the candidate-input SQL query only floors amounts for the base asset (`asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE`), all of these dust outputs remain valid future inputs. [9](#0-8) 
4. When a legitimate user later triggers the AA's withdrawal/payout logic for asset `X` (e.g., a `send-all` response), `completePaymentPayload()`/`iterateUnspentOutputs()` must consume all (or a very large subset) of the attacker's dust outputs as inputs to satisfy the required amount. [3](#0-2) 
5. The resulting AA-composed unit becomes abnormally large, its oversize fee (paid from the AA's own base-asset balance) grows accordingly, and if the AA's byte balance is insufficient, the payout bounces with "not enough balance in base," blocking the intended fund distribution. [10](#0-9)
