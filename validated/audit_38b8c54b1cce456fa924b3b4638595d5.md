This is confirmed valid. The `filter_deploy_envs`/`EnvironmentVariables#permit` allowlist only sanitizes the explicit `@task.env` (user-supplied deploy params), never `stack.env`/`ReviewStack#env`, which is merged unfiltered and last-wins inside `Command#unbundled_env`.

### Title
`PATH` injection via uppercased pull-request label name overrides `Command#unbundled_env`, enabling deploy-host command hijacking - (File: `lib/shipit/command.rb`, `app/models/shipit/review_stack.rb`)

### Summary
`ReviewStack#env` merges every pull-request label name (uppercased) into the stack environment with value `"true"` and no key allowlist, and this hash flows unchanged through `TaskCommands#env`/`DeployCommands#env` into `Command#env`. `Command#unbundled_env` then computes `BASE_ENV.merge('PATH' => "#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}").merge(@env.stringify_keys)`, where `@env` (attacker-controlled) is merged *last*, so a label literally named `path` becomes the env key `PATH` and completely overwrites the safe, computed `PATH` value before `PTY.spawn` executes the `deploy.override` steps.

### Finding Description
The broken binding: `Command#unbundled_env['PATH']` is expected to always equal `"#{Shipit.shell_paths.join(':')}:#{ENV['PATH']}"`, but with an unprivileged PR label it instead equals the label-derived value, e.g. `PATH == "true"`.

Path:
1. An unprivileged fork PR author labels their own PR with a label whose name, case-insensitively, is `path` (e.g. `"path"`, `"Path"`).
2. `LabelCapturingHandler#capture_labels` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:98-102`) persists `params.pull_request.labels.map(&:name)` verbatim from the webhook body onto `PullRequest#labels` — no key allowlist or blocklist is applied.
3. `ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) does:
   ```
   super.merge(pull_request.labels.each_with_object({}) { |n,h| h[n.upcase] = "true" })
   ```
   producing `{"PATH" => "true", ...}` merged over the safe `Stack#env` base — with no allowlist, unlike `filter_deploy_envs`/`EnvironmentVariables#permit`, which is only applied to the explicit user-provided `env` param in `Stack#build_deploy`/`#trigger_task` (`app/models/shipit/stack.rb:139-172`), not to `stack.env`.
4. `TaskCommands#env`/`DeployCommands#env` (`lib/shipit/task_commands.rb:33-48`, `lib/shipit/deploy_commands.rb:9-16`) merge `@stack.env` straight through to each `Command.new(command_line, env:, chdir: steps_directory)`.
5. `Command#unbundled_env` (`lib/shipit/command.rb:103-105`) computes the default `PATH`, but `.merge(@env.stringify_keys)` is applied last, so the attacker's `PATH` key wins.
6. `Command#start` (`lib/shipit/command.rb:85-101`) calls `PTY.spawn(unbundled_env, *interpolated_arguments, chdir: @chdir)` — `@chdir` is `steps_directory`, inside `task.working_directory` (`File.join(stack.deploys_path, id.to_s)`), which is a checkout of the attacker's own fork branch. The attacker fully controls the file tree at that path (they own the fork), so they can commit a directory literally named `true` containing executables matching bare command names used in a `deploy.override` step (e.g. `bundle`, `cap`, or any custom script name). Since `deploy.override` steps run with `PATH=true` (a relative directory resolved against `@chdir`), the shell's command lookup resolves those bare command names to the attacker's malicious executables inside the checked-out repo — Remote Code Execution on the Shipit deploy host.

Existing guards do not catch this: `EnvironmentVariables#permit` is never invoked on `stack.env`/`ReviewStack#env`, only on the explicit `env` param submitted via API/controller (`filter_deploy_envs`, `TaskDefinition#filter_envs`); `verify_signature`/webhook auth only confirms the webhook came from GitHub for that repository, not that label content is safe; nothing in `Command` blocklists `PATH`, `LD_PRELOAD`, `RUBYOPT`, etc.

### Impact Explanation
An unprivileged fork PR author can execute arbitrary code on the Shipit deploy host during a `deploy.override` run for their own review stack, by naming a label `path` (case-insensitive) and placing a directory named `true` with malicious binaries in their fork branch. This is Critical — RCE on the deploy host via `Command`/`PTY.spawn`, matching the required Immunefi/HackerOne severity class. Blast radius is scoped to the review stack of the repository that has `provisioning_behavior=prevent_with_label` enabled and allows unprivileged fork PRs to create/keep review stacks, but the deploy host itself (and any secrets/credentials accessible from that host, e.g. `GITHUB_TOKEN`) is shared infrastructure, so compromise there can pivot to other stacks/tenants deployed on the same host.

### Likelihood Explanation
Preconditions: the target repository must use `provisioning_behavior: prevent_with_label` (or any review-stack-enabling behavior) with a `shipit.yml` `deploy.override` step that invokes a bare command name (not an absolute path). The attacker needs only: (1) permission to open a PR against/from a repo they control, (2) permission to add a label to their own PR (labels on one's own PR in a fork-based workflow, or via the `pull_request` webhook payload structure that `LabelCapturingHandler` trusts once signed by GitHub for that repo), and (3) the ability to place arbitrary files (`true/<binary>`) in their own branch. No Shipit secrets, session, or API tokens are required. This is fully repeatable per review stack.

### Recommendation
Apply an explicit allowlist/blocklist to `ReviewStack#env`/label-derived keys before merging into the process environment — at minimum reject or drop reserved/dangerous keys such as `PATH`, `LD_PRELOAD`, `LD_LIBRARY_PATH`, `RUBYOPT`, `BUNDLE_*`, `IFS`, etc., the same way `EnvironmentVariables#permit` sanitizes explicit deploy variables. Additionally, harden `Command#unbundled_env` to always compute `PATH` last (i.e., never let `@env` override `PATH`), so command resolution can't be redirected regardless of the source of `@env`.
