### Title
Cross-stack deploy-status disclosure via stack-scoped API token bypassing scope check - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` lookup used by `Shipit::Api::BaseController` in a way that removes the per-`ApiClient` stack scoping, letting a stack-scoped API token read the deploy state of any other stack.

### Finding Description
`Shipit::Api::BaseController` centralizes API-client stack scoping: `stacks` restricts the visible set to `Stack.where(id: current_api_client.stack_id)` whenever the authenticated `ApiClient` carries a `stack_id`, and `stack` resolves `params[:stack_id]` only within that scoped relation: [1](#0-0) 

`ApiClient` supports being bound to a single stack (`belongs_to :stack, optional: true`) and only exposes coarse, non-stack-specific permission strings like `read:stack` via `check_permissions!`: [2](#0-1) 

Enforcement of "this token may only see its own stack" therefore depends entirely on the `stacks`/`stack` scoping helpers in `BaseController`, not on the `permissions` array. `CCMenuController`, however, defines its own `stack` method that queries `Stack.from_param!(params[:stack_id])` directly against the full `Stack` table, bypassing `current_api_client.stack_id` scoping entirely, while still relying on `require_permission :read, :stack` (a scope-string check only): [3](#0-2) 

The binding that should hold is: `stack a token is authorized for == stack the endpoint actually serves`. Before the request: a token such as the `here_come_the_walrus` fixture is created with `stack: shipit` and `permissions: [read:stack]`, intended to authorize reads of only that one stack: [4](#0-3) 

and this scoping is verified elsewhere in the API surface, e.g. `Stacks#index`/`#show` tests assert a stack-scoped client sees only its own stack: [5](#0-4) 

After the request against `CCMenuController#show` with a different `stack_id` in the URL, `stack` resolves via unscoped `Stack.from_param!`, so the same token now serves deploy state for an arbitrary stack: [6](#0-5) 

The regular `Api::BaseController#authenticate_api_client` uses HTTP Basic auth, but `CCMenuController` overrides it to accept the token from a query parameter, which is how these tokens are meant to be embedded in third-party CI dashboards (e.g. CCMenu clients) — i.e., these tokens are designed to be pasted into external tools and are lower-trust by design, making the scope guarantee more important, not less: [7](#0-6) 

### Impact Explanation
This is an unauthenticated-cross-scope read: possession of a token that was only ever meant to authorize read access to one specific stack (as created and distributed by `CCMenuUrlController#client`, embedded in a URL a user may share/leak) is sufficient to read deploy/build state (`stack.deploys_and_rollbacks.last`) for every stack in the installation, including private/production stacks unrelated to the token's intended scope. This matches the "High" impact bucket: unauthenticated read of stack state / deploy output through an authorization scope that was supposed to bind the token to a single stack.

### Likelihood Explanation
No privileged access is required beyond having obtained/leaked one legitimate, narrowly-scoped CCMenu token (these tokens are explicitly designed to be embedded in a URL and shared with external CI-status tools, so leakage is a realistic, intended distribution path). Exploitation is a single GET request with a different `stack_id` query/path parameter — trivial and reliable, no timing or race conditions involved.

### Recommendation
Make `CCMenuController#stack` go through the same scoped lookup as `BaseController`, e.g. replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])` (reusing `BaseController#stacks`, which already enforces `current_api_client.stack_id` scoping), so a stack-bound `ApiClient` cannot resolve any stack outside its bound `stack_id`.

### Proof of Concept
1. As an authorized Shipit user, visit a stack's settings page and trigger `CCMenuUrlController#fetch` for stack `shipit`; this creates/reuses an `ApiClient` named "CCMenu Client" scoped only to permission `read:stack` (note: as fetched, this specific client is not stack-bound by that controller, but the same `Api::CCMenuController#stack` bypass equally affects any `ApiClient` that *is* stack-bound, such as the `here_come_the_walrus` fixture used in tests, `stack: shipit`).
2. Take that stack-bound token's `authentication_token` (e.g. `here_come_the_walrus`'s token) and call:
   `GET /api/<other_stack_owner>/<other_repo>/<other_env>/ccmenu.xml?token=<token>`
3. Observe the response returns the deploy/build XML for the *other* stack, even though the token's `ApiClient.stack_id` corresponds only to the original `shipit` stack — because `CCMenuController#stack` never checks `current_api_client.stack_id`, unlike `BaseController#stack`.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
