### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but event handlers (in particular `StatusHandler`) act on data (`Commit.where(sha:)`, `repository.full_name`) that is never cross-checked against that authenticated organization - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
This is the same class of bug as the `TokenDistributor` report: a guard is validated against one piece of state (the organization used to look up the secret and verify the HMAC), while the privileged action is performed using a *different*, unauthenticated piece of the same payload (the target commit/repository). Nothing forces the two to agree, so a value the attacker fully controls (which repository/commit the action applies to) escapes the binding that the signature check was supposed to enforce.

### Finding Description
`WebhooksController#verify_signature` selects which organization's webhook secret to validate against using:

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

and then verifies `X-Hub-Signature` against `Shipit.github(organization: repository_owner).verify_webhook_signature`. [2](#0-1) 

Shipit supports **multiple GitHub organizations, each with its own `webhook_secret`** (`config/secrets.development.shopify.yml` shows a `github:` map keyed by org, each with its own `webhook_secret`) [3](#0-2) . This means any org onboarded onto the same Shipit instance can compute a perfectly valid `X-Hub-Signature` for a payload it authors, using its *own* legitimate secret — that signature only proves "this came from someone who knows org X's secret," not "this event only concerns org X's repositories."

The downstream handlers, however, do not re-check that the content of the payload actually belongs to the organization whose secret validated it:
- `Handler#stacks` resolves the target repository from `payload.dig('repository', 'full_name')`, a field completely independent from the `repository_owner` used for signature selection [4](#0-3) .
- `StatusHandler#process` doesn't even scope to a stack/repository at all — it looks up `Commit.where(sha: params.sha)` **globally**, across every repository tracked by the entire Shipit instance, and directly writes GitHub-sourced status fields onto it: `commit.create_status_from_github!(params)` [5](#0-4) .

So the equality that should hold — "organization whose signature was verified" == "organization/repository whose data is written" — is never enforced. An attacker who controls any one org configured in Shipit's `github:` map can send a `status` event, sign it correctly with their own org's `webhook_secret`, but set `sha` to a commit belonging to a totally different (victim) repository, and Shipit will accept and persist the forged status as if it came from GitHub for that commit.

### Impact Explanation
Commit statuses are load-bearing for deploy readiness/gating in Shipit (`deployable_status` is one of the hook `EVENTS`, and stacks gate deploys on required checks/status state) [6](#0-5) . Being able to forge a "success" status on an arbitrary commit of a victim repository — without ever having credentials, access, or even a relationship to that repository — can satisfy required-status-check gating and lead to an unauthorized deploy of a commit that never actually passed CI. This crosses the "organization that authenticated versus the repository that is written" trust boundary called out in scope, and lands in the Critical impact bucket (unauthorized deploy) because it originates purely from the attacker's own legitimate-but-unrelated organization credentials with zero access to the victim's repository or Shipit account.

### Likelihood Explanation
Low-to-moderate: it requires the attacker to control (or be an admin of) at least one GitHub organization/app that is independently configured in the same Shipit instance's multi-tenant `github:` config (a legitimate, intended, unprivileged-relative-to-the-victim setup, not a stolen secret). No access to the victim's repository, Shipit session, or `ApiClient` token is required — only knowledge of the attacker's own org's webhook secret, which by design they are entitled to know.

### Recommendation
After verifying the HMAC signature, re-derive the organization owner from the same trusted source used for verification and require every organization/repository-identifying field used by the handler (`repository.full_name`, and — for `StatusHandler` — the resolved commit's repository) to match `repository_owner`. Reject the event if these disagree, e.g.:
```ruby
def verify_signature
  ...
  head(422) unless verified && payload_repository_owner_matches?(repository_owner)
end
```
For `StatusHandler`, scope the `Commit` lookup by the repository derived from the verified organization instead of a global, unscoped `Commit.where(sha:)`.

### Proof of Concept
1. Attacker controls (or is an admin of) `evil-org`, which is configured in Shipit's `github:` map with its own `webhook_secret`.
2. Attacker crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha belonging to acme-org/prod-app>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "evil-org" }, "full_name": "evil-org/throwaway" }
}
```
3. Attacker computes `X-Hub-Signature` with `evil-org`'s real `webhook_secret` over this exact payload.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `evil-org`, fetches `evil-org`'s `webhook_secret`, and the signature verifies successfully [2](#0-1) .
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit in `acme-org/prod-app` — and writes the forged "success" status onto it [5](#0-4) , with no check that `acme-org` (the commit's real owner) matches `evil-org` (the signature-verified owner).
