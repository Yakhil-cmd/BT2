### Title
Missing `return` in catch block causes double-handling of private payment chains - ([File: network.js])

### Summary
In `handleSavedPrivatePayments`, when hashing the head private payload throws, the error path fails to short-circuit before the code continues to unconditionally invoke `privatePayment.validateAndSavePrivatePaymentChain` on the same chain, leading to a double dispatch and a garbage validation key.

### Finding Description
`network.js` `validateAndSave` (used inside `handleSavedPrivatePayments`) computes a hash of the head private element's payload in a `try`/`catch`: [1](#0-0) 

If `objectHash.getBase64Hash(objHeadPrivateElement.payload, true)` throws (analogous to the report's "return value/result is never checked/handled"), the `catch` block logs the error, optionally sends an error result to the peer, and calls `deleteHandledPrivateChain(row.unit, row.message_index, row.output_index, cb)` — which removes the row from `unhandled_private_payments` and invokes the `async.each` iteration callback `cb`. Critically, there is **no `return`** after this call, so execution falls through to the next line, which still computes `key` using the now-`undefined` `json_payload_hash`, and then unconditionally calls `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` on the very same chain that was just deleted/finalized.

This means the failure path from the hashing exception is not truly handled/short-circuited — analogous to the report's core complaint that an operation's outcome (success/failure) is not properly gated before subsequent logic proceeds as if nothing failed.

Consequences of falling through:
- `cb` (the `async.each` iterator callback) can be invoked a second time — once by `deleteHandledPrivateChain` in the `catch` block, and again by whichever of `ifOk`/`ifError`/`ifWaitingForChain` fires inside `validateAndSavePrivatePaymentChain`. Calling an `async.each` callback more than once is undefined behavior in the `async` library and can corrupt iteration state (e.g., cause `handleSavedPrivatePayments`'s completion handler to run early/twice, or throw).
- `privatePayment.validateAndSavePrivatePaymentChain` proceeds to actually validate and potentially persist/credit the private payment chain even though the row bookkeeping (`unhandled_private_payments`) was already deleted, and the `eventBus` key used to notify waiters (`private_payment_validated-...-undefined-...`) is malformed because `json_payload_hash` is `undefined`.
- Any other code path awaiting the correctly-keyed event (e.g. `wallet.js`'s `handlePrivatePaymentChains` callers awaiting `'private_payment_validated-'+unit+'-'+json_payload_hash+'-'+output_index`) will never receive the notification because the emitted key differs (`undefined` instead of the real hash), leaving that flow hanging or bypassing intended completion signaling.

This is reachable by any private-payment counterparty: a peer who sends a private payment chain whose head payload triggers a hashing exception in `objectHash.getBase64Hash` (e.g. malformed/edge-case payload structure) can trigger this dual-path execution on the recipient's node.

### Impact Explanation
This is a logic/control-flow defect in private payment chain processing that can cause: double-processing of a chain the code believed was already finalized/deleted, corrupted `async.each` iteration state, and mismatched event keys that break the waiting-caller synchronization mechanism used elsewhere for private payment acceptance. Depending on downstream effects in `validateAndSavePrivatePaymentChain`'s handling of already-deleted rows, this could allow inconsistent state around private payment acceptance/crediting, which affects wallet fund accounting for private payments — a Medium-severity control-flow correctness issue.

### Likelihood Explanation
Triggering requires only that `objectHash.getBase64Hash(payload, true)` throw for a maliciously or accidentally crafted private-payment payload sent by a payment counterparty (or replayed via hub `private_payments` messages). No privileged access is required, since `handleSavedPrivatePayments` is invoked while processing normal private payment chains that any peer or hub can submit to a recipient wallet.

### Recommendation
Add a `return` statement at the end of the `catch` block in `network.js` (line 2476, right after `deleteHandledPrivateChain(...)`) so that when hashing fails, `validateAndSave` exits immediately and does not fall through to compute `key` or call `validateAndSavePrivatePaymentChain` a second time on the same chain.

### Proof of Concept
1. Craft a private payment chain whose head element's `payload` causes `objectHash.getBase64Hash(payload, true)` to throw (e.g., a payload containing a value type unsupported by the hashing routine).
2. Send this chain to a recipient device such that it is queued into `unhandled_private_payments` and processed by `handleSavedPrivatePayments`.
3. Observe: the `catch` block executes (`deleteHandledPrivateChain` deletes the row and calls `cb`), but execution continues to also call `privatePayment.validateAndSavePrivatePaymentChain(arrPrivateElements, {...})` with a malformed `key` (containing `undefined`), leading to a second `cb` invocation and mismatched event emission.
