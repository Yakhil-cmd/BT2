### Title
Membership webhook trusts `team.id`/`organization.login` independent of the signing org, letting a controlled org's webhook add arbitrary members to another org's `Team` and bypass `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` looks up `Team` solely by `github_id` and only sets `organization` on record *creation*, never re-validating it against the payload on subsequent hits. Combined with `WebhooksController#verify_signature` authenticating the request against `repository.owner.login`/`organization.login` from the same untrusted payload rather than against the resolved `team.organization`, an attacker who controls a second org onboarded into the Shipit installation (and thus legitimately knows that org's `webhook_secret`) can send a signed `membership` webhook whose `team.id` matches a real team belonging to a different, privileged org and have Shipit mutate that other org's `Team` membership.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: `Team.find_by(github_id: params['team']['id']).organization` should equal `repository_owner` (the org whose signature was verified in `WebhooksController#verify_signature`), but nothing in the code path checks this.

Code path:
- `WebhooksController#verify_signature` derives the signing org from the payload itself: `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and verifies HMAC using `Shipit.github(organization: repository_owner)` [1](#0-0) [2](#0-1) .
- `MembershipHandler.params` only enforces types (`Integer`/`String`) on `team.id`, `organization.login`, `member.login`, with no cross-field constraint tying `organization.login`/`repository.owner.login` to `team.id` [3](#0-2) .
- `find_or_create_team!` resolves the `Team` purely by `github_id`; the block that assigns `team.organization = params.organization.login` only runs when a *new* record is created by `find_or_create_by!`, so if a `Team` with that `github_id` already exists (belonging to a different, victim org), it is returned unmodified: [4](#0-3) .
- `process` then unconditionally calls `team.add_member(User.find_or_create_by_login!(params.member.login))`, adding a fully attacker-chosen GitHub login as a member of that resolved team [5](#0-4) .

Exploit flow: attacker owns/administers `attacker-org`, which is configured in Shipit's multi-org `github:` settings (as shown for multi-org deployments in `config/secrets.development.shopify.yml`) and therefore attacker legitimately knows `attacker-org`'s `webhook_secret`. Attacker sends `POST /webhooks` with `X-Github-Event: membership`, a valid HMAC signature computed with `attacker-org`'s secret, and body `{ action: 'added', team: { id: <victim_team.github_id>, name, slug, url }, organization: { login: 'attacker-org' }, member: { login: 'attacker_github_login' }, repository: { owner: { login: 'attacker-org' } } }`. `verify_signature` succeeds because it only checks that `attacker-org`'s secret matches (its own org, correctly). `find_or_create_team!` then finds the existing `Team` row keyed by `github_id` — which belongs to a completely different org — and `team.add_member` attaches `attacker_github_login`'s `User` to it.

Existing guards do not stop this: `verify_signature` validates *an* org's signature but never checks that `team.id` actually belongs to the org that signed the request; `ExplicitParameters` only checks types; `Team.find_or_create_by!` has no scoping by organization; `User#authorized?`'s access-control logic (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) trusts `Team#members` unconditionally [6](#0-5) .

### Impact Explanation
If the resolved `Team` is one of `Shipit.github_teams` (the set used to gate all Shipit controller access via `force_github_authentication` and `User#authorized?`), the attacker can add an arbitrary GitHub login as a member of that privileged team purely by controlling a different, unrelated org onboarded into the same Shipit instance. Once that `User` logs in (or is otherwise resolved), `authorized?` returns true, granting full access to stacks, deploys, tasks, and API-client management — a cross-tenant authorization escalation into `Shipit.github_teams`. This is repeatable against any `github_id` the attacker can learn or guess (team IDs are small sequential integers), and works across all orgs sharing one Shipit installation. This matches the "escalation into `Shipit.github_teams` authorization" High severity category. [7](#0-6) 

### Likelihood Explanation
Requires a multi-org Shipit deployment where the attacker legitimately administers one configured org (owns its `webhook_secret` and can point its GitHub App/webhook at the Shipit host) — a realistic and documented configuration pattern (`config/secrets.development.shopify.yml` shows two configured orgs). The attacker also needs the `github_id` of a real team in the victim org that is part of `Shipit.github_teams`; GitHub team IDs are small monotonically increasing integers and are frequently discoverable (public API responses, prior webhook traffic, UI/URL leakage), making brute-force or targeted guessing feasible. No Shipit session, API token, or victim-org secret is required at any point, satisfying the attacker capability constraints. The attack is trivially repeatable per request.

### Recommendation
In `find_or_create_team!`, scope the lookup and enforce consistency: query `Team.find_by(github_id: params.team.id)` and, if found, assert `existing_team.organization == params.organization.login` (and that `params.organization.login == repository_owner`, i.e., the org that was cryptographically verified in `WebhooksController#verify_signature`) before performing any mutation; reject/drop the event otherwise. More generally, `WebhooksController#verify_signature` should pass the verified `repository_owner` down to handlers so they can refuse to act on any payload field (`organization.login`, `team.id`) that doesn't match the org whose signature was actually checked.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative)
test ":membership from a different signed org can hijack another org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  attacker_org = 'attacker-org'

  Shipit.github(organization: attacker_org).stubs(:verify_webhook_signature).returns(true)

  payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    organization: { login: attacker_org },
    member: { login: 'attacker_login' },
    repository: { owner: { login: attacker_org } }
  }

  @request.headers['X-Github-Event'] = 'membership'
  assert_no_difference -> { Team.count } do
    post :create, body: payload.to_json, as: :json
    assert_response :ok
  end

  victim_team.reload
  # Binding under test: resolved Team's organization must equal the signing org.
  refute_equal attacker_org, victim_team.organization
  assert victim_team.members.exists?(login: 'attacker_login') # cross-org write proven
end
```
This demonstrates `find_or_create_team!` resolving and mutating (`add_member`) a `Team` whose `organization` (`'shopify'`) differs from the org whose signature was verified (`attacker-org`), confirming the broken provenance binding.
