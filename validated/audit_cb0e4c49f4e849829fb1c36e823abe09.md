### Title
Attacker-controlled swap routes can poison caller authorization and drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` and the other strategy entrypoints accept caller-supplied opaque route bytes and execute them through the configured router while the account owner’s authorization is active. A malicious route can place attacker-controlled code inside that call and have it request additional `transfer` authorization from the victim; if the victim signs the simulated authorization tree, the rogue code can transfer unrelated wallet tokens to the attacker while the swap still satisfies the controller’s balance checks. This is the on-chain analogue of a malicious package that exfiltrates wallet contents. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::swap_collateral` exposes a `swap: Bytes` argument and forwards it into `SwapCollateralParams`. [3](#0-2) 

The strategy authenticates the `caller`, verifies that the caller owns or delegates the target account, withdraws collateral into controller custody, and passes the supplied route to `withdraw_and_swap_from_supply`. [4](#0-3) 

`swap_tokens` authorizes only one exact `token_in.transfer(controller, router, amount_in)` on behalf of the controller, then invokes `router.execute_strategy(controller, amount_in, swap)`. [5](#0-4) 

After the router returns, the controller only verifies that its own input balance did not increase or overspend and that it received a positive `token_out` balance delta. [6](#0-5) 

Those checks do not limit what other contracts named by the opaque route do while the victim’s authorization is active. The regression test demonstrates a route-selected rogue hop calling `WALLET_TOKEN.transfer(victim, attacker, amount)`, which simulation records as a child of the victim’s `swap_collateral` authorization. [7](#0-6) [2](#0-1) 

### Impact Explanation
If the victim signs the poisoned authorization tree produced by simulation, the rogue venue can transfer any victim-held token amount named by the attacker, not merely the collateral being swapped. [8](#0-7) 

The swap can still return a normal output and satisfy the controller’s measured-output and final-risk checks, so the wallet theft succeeds atomically alongside an apparently valid collateral swap. [9](#0-8) [10](#0-9) 

This is theft of user funds and can target assets completely unrelated to the lending account or listed markets. [11](#0-10) 

### Likelihood Explanation
Any unprivileged user can provide non-empty `swap` bytes on `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral`; the controller does not parse or allowlist the route before forwarding it. [12](#0-11) [13](#0-12) 

The exploit requires the victim to sign the expanded authorization tree; signing only the honest root causes the host to reject the rogue transfer and roll back the call. [14](#0-13) 

The likelihood is nevertheless material because quote routes are opaque bytes and a malicious quote, interface, integration, or copied route can induce users to sign a simulated tree containing attacker-chosen transfers. [3](#0-2) [15](#0-14) 

### Recommendation
Do not forward attacker-controlled route bytes into arbitrary external code under the account owner’s authorization. Enforce a governance-approved venue/pool allowlist before execution, or decode and validate every invoked contract address against such a registry; additionally require clients to reject any `swap_collateral` or other strategy authorization tree containing children beyond the expected transfers. [5](#0-4) 

### Proof of Concept
1. Alice supplies 10,000 USDC and holds an unrelated `WALLET_TOKEN`; the attacker deploys a rogue route hop configured with `(victim=Alice, token=WALLET_TOKEN, to=attacker, amount=WALLET_BALANCE)`. [16](#0-15) 
2. The attacker causes Alice to submit `swap_collateral(caller=alice, account_id=alice_account, current=hub(USDC), amount=5_000_USDC, new=hub(ETH), swap=route_through_rogue_hop)`. [17](#0-16) 
3. During route execution, the rogue hop calls `WALLET_TOKEN.transfer(alice, attacker, WALLET_BALANCE)`. [7](#0-6) 
4. Simulation records that token transfer as a child authorization under Alice’s `swap_collateral` root. [18](#0-17) 
5. If Alice signs the returned tree, the transaction succeeds, Alice’s unrelated wallet balance becomes zero, the attacker receives `WALLET_BALANCE`, and Alice still receives the expected ETH collateral output. [9](#0-8) [8](#0-7)
