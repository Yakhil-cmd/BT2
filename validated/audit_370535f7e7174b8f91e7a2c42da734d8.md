### Title
Webhook signature verification uses an organization derived from the unsigned payload, decoupled from the repository the event actually acts on - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to validate a signature against by reading `repository.owner.login` directly out of the **unverified** JSON body. The event handlers that subsequently act on the request (e.g. `PushHandler`) resolve the target `Repository`/`Stack` from a *different* field of the same untrusted payload: `repository.full_name`. Because Shipit explicitly supports multiple independent GitHub organizations, each with its own `webhook_secret`, an attacker who legitimately controls one configured organization's webhook secret can forge a webhook whose signature validates against their own org while claiming to be an event for a repository belonging to a completely different, unrelated organization/stack.

### Finding Description
`WebhooksController#verify_signature` does: [1](#0-0) 

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [2](#0-1) 

`Shipit.github(organization:)` looks up the `GitHubApp` (and its `webhook_secret`) keyed strictly by that `organization` string, which Shipit explicitly supports as a multi-tenant configuration (top-level keys per GitHub org, each with its own `webhook_secret`): [3](#0-2) [4](#0-3) 

Once the signature check passes, the actual event payload is dispatched to handlers, and every handler (`PushHandler`, `CheckSuiteHandler`, pull-request handlers, etc.) resolves the `Stack`/`Repository` to act on via `Handler#repository_name`, which reads a **different** field, `repository.full_name`: [5](#0-4) [6](#0-5) 

There is no check anywhere that the `owner.login` used to select the verifying secret is the same organization that owns the `full_name` repository that the handler subsequently mutates. `Repository.from_github_repo_name`/`stacks` simply looks up any stack matching `full_name`, independent of which org's secret validated the request. This breaks the intended trust binding: **`organization authenticated by signature` == `repository/organization actually written to`.** Before the attacker's request, the equality holds because GitHub itself always signs with the secret belonging to the org that owns the repository in the payload. After the attacker's forged request, the two sides diverge: the signature is valid for `OrgAttacker` (the attacker's own legitimately configured org/secret), while the acted-upon repository/stack is `OrgVictim/some-repo`.

### Impact Explanation
This crosses a repository-write boundary the multi-org webhook secret is meant to enforce: an operator of one configured GitHub organization can trigger webhook-driven side effects (`GithubSyncJob`, PR label/state changes, check-run refresh, commit status writes, `stack.sync_github` and subsequently `ContinuousDeliveryJob`/`trigger_continuous_delivery` for stacks that auto-deploy) against a Stack belonging to a completely different organization/repository they do not own or have credentials for. For a stack with `continuous_deployment` enabled, a forged `push` event causes `GithubSyncJob` to re-sync commits and can lead `trigger_continuous_delivery` to fire a deploy: [7](#0-6) [8](#0-7) 

This matches the "unauthorized deploy" impact category: an entity that only controls one organization's webhook secret can cause writes/deploys against a stack scoped to a different, unrelated organization.

### Likelihood Explanation
Exploitation requires: (1) Shipit configured with multiple GitHub organizations (a documented, supported configuration — `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`), and (2) the attacker being a legitimate operator/owner of at least one of those configured orgs (i.e., they know their own org's `webhook_secret`, which is normal and not a privileged secret for the *other* orgs). No session, `ApiClient` token, or GitHub App private key for the victim org is needed — only the ability to POST an HMAC-signed request to the public `/github/webhooks` endpoint using a secret the attacker legitimately possesses for their own tenant.

### Recommendation
After signature verification succeeds, cross-validate that the organization used to select the verifying `GitHubApp`/secret (`repository.owner.login` / `organization.login`) actually matches the owner of `repository.full_name` that the handler will act upon (or, more robustly, resolve the target `Stack`/`Repository` first and use *its own* configured organization to look up the expected secret, refusing to process the event if these disagree).

### Proof of Concept
1. Configure Shipit with two organizations, `OrgAttacker` and `OrgVictim`, each with its own `webhook_secret` (as documented/supported: `docs/setup.md` "Using Multiple Github Applications", `test/dummy/config/secrets_double_github_app.yml`).
2. `OrgVictim` has a Stack tracking `OrgVictim/some-repo` with `continuous_deployment: true`.
3. Attacker (who legitimately owns/administers `OrgAttacker` and thus knows `OrgAttacker`'s `webhook_secret`) crafts a push payload:
```json
{
  "ref": "refs/heads/production",
  "after": "<a real commit sha in OrgVictim/some-repo>",
  "repository": {
    "owner": { "login": "OrgAttacker" },
    "full_name": "OrgVictim/some-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgAttacker_webhook_secret, body)` and POSTs to `/github/webhooks` with header `X-Github-Event: push`.
5. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgAttacker"`, calls `Shipit.github(organization: "OrgAttacker").verify_webhook_signature(...)`, which succeeds because the attacker signed with the correct secret for `OrgAttacker`.
6. `PushHandler#process` resolves `stacks` via `payload.dig('repository','full_name')` = `"OrgVictim/some-repo"`, finds the victim's Stack, and calls `stack.sync_github(expected_head_sha: ...)`, enqueuing `GithubSyncJob` and potentially triggering continuous delivery for `OrgVictim`'s stack — despite the attacker having no credentials for `OrgVictim` at all.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
