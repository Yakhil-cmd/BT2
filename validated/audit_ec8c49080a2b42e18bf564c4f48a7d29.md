In `validation.js`, the SQL query used to look up the source output being spent checks `arrAuthorAddresses.indexOf(owner_address) === -1` and *returns a normal callback error* (not a throw) when the owner isn't an author [1](#0-0) , so that particular path is safe. ### Title
Uncaught `throw Error()` in unit-validation input/double-spend checks crashes the node (DoS) - (File: validation.js)

### Summary
`validation.js`'s payment-input and double-spend validation logic mixes normal `cb(errorString)` returns with several `throw Error(...)` statements for conditions it treats as "should never happen." These throws are not caught anywhere along the call path from `network.handleJoint()` → `validation.validate()` → `validateMessage()` → `validatePaymentInputsAndOutputs()`. Because `network.js` installs a `process.on('uncaughtException', ...)` handler that deliberately re-throws to crash the process, any successfully triggered `throw Error(...)` inside unit validation brings the entire node process down.

### Finding Description
The unit validation pipeline (`validation.validate`) is invoked directly from the network layer for every unit received from a peer or posted by a light client, via `handleOnlineJoint`/`handlePostedJoint`/`handleJoint`, with no try/catch around the call [9](#0-8) . Deep inside the payment input/double-spend validation logic several defensive invariant checks use `throw Error(...)` instead of returning a validation error through the callback chain: e.g. `throw Error("more than 1 src output")`, `throw Error("spending a stable temp-bad output ...")`, `throw Error("src output amount is not a number")` [10](#0-9) , and the equivalent throws inside `checkForDoublespends` for conflicting spend records [5](#0-4) , plus `validateParents`'s `"last ball unit ... is stable but has no ball"` [6](#0-5) . Because none of these are wrapped in try/catch (contrast with the deliberate try/catch around unit-hash and payload-hash computation at the top of `validate()` [7](#0-6) ), any code path that reaches one of them propagates an uncaught exception up through the async callback chain. `network.js`'s global handler then does `throw err;` specifically to crash the process [8](#0-7) . This mirrors the CVE-2021-27478 pattern: a single crafted, unprivileged network message (here, a posted/relayed unit) reaching an insufficiently defensive parsing/validation branch causes an unhandled fault that terminates the service.

### Impact Explanation
If any of these "impossible" conditions can be triggered by an attacker crafting a unit (e.g., a payment input pointing at an output whose on-chain state satisfies one of the guarded conditions, or a double-spend record whose address happens to differ from the current authors), the resulting uncaught exception crashes the full node process. This is a network-wide DoS: any node that processes the malicious unit (via relay/broadcast, gossip, or direct posting) goes down, and because the code path is reached before signature/authority checks fully gate it in some branches, it could be triggered by any unprivileged unit poster. Repeated crashes across bootstrap/relay nodes could stop the network from confirming new units.

### Likelihood Explanation
Medium: the throwing branches guard states that the developers believed could not occur in a correctly-functioning network (hence "should never happen" comments like "unreachable code"), so triggering them requires finding a specific combination of prior accepted units and a crafted new unit that violates the invariant the check assumes. This is plausible given the complexity of the double-spend/serialization state machine (temp-bad/final-bad/good sequences, is_stable transitions, forked address paths), but I could not confirm within the available exploration budget an exact minimal unit sequence that flips one of these throw conditions.

### Recommendation
Replace all `throw Error(...)` calls inside the unit-validation call graph (`validation.js`, `checkForDoublespends`, `validateParents`, and similar) that are reachable from network-supplied units with graceful error returns via the existing `callback(...)`/`cb(...)` error-propagation mechanism, so malformed or unexpected states result in unit rejection instead of a process crash. Alternatively/additionally, wrap `validation.validate()` invocations in network.js with a try/catch that treats any thrown error as a joint/unit validation failure (calling `ifJointError`/`ifUnitError`) rather than allowing it to escape to the global `uncaughtException` handler which intentionally crashes the process.

### Proof of Concept
Conceptual PoC (not fully verified end-to-end):
1. As an unprivileged network participant, get two units accepted into the DAG such that an output is later spent in a way that produces a `sequence` of `'temp-bad'` and is included as `bStableInParents` (i.e., its `main_chain_index <= last_ball_mci`) for a subsequently crafted spending unit.
2. Post/broadcast a new unit whose payment input references that output as a `"transfer"` input.
3. During validation, `bStableInParents && src_output.sequence === 'temp-bad'` becomes true, hitting `throw Error("spending a stable temp-bad output " + input.unit)` at `validation.js:2457-2458`, which is not caught anywhere in the async chain and propagates to `network.js`'s `uncaughtException` handler, crashing the node process.

Confirming the exact sequence of prior units needed to reach `sequence === 'temp-bad'` while `bStableInParents` is true (rather than being rejected earlier by other checks) requires dynamic testing against the actual validation/writer state machine, which I was unable to complete within this session.
