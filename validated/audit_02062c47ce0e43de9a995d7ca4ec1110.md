### Title
Premature mutex release in `shrinkCache()` races deferred cache-deletion queries against concurrent writers, corrupting stability/best-children caches - (File: storage.js)

### Summary
`storage.js`'s `shrinkCache()` acquires the global `"write"` mutex lock, which is the same lock used by every unit-writing code path (`validation.js`, `writer.js`, `joint_storage.js`) to serialize mutation of the in-memory DAG caches (`assocKnownUnits`, `assocCachedUnits`, `assocStableUnits`, `assocBestChildren`, `assocCachedUnitAuthors`, `assocCachedUnitWitnesses`). However, it calls `unlock()` immediately after *issuing* a batch of asynchronous `db.query()` calls, not after they complete, so the lock is released while the actual cache-deletion callbacks are still pending on the event loop. This mirrors the CVE-2023-6270 pattern: a reference/lock is dropped too early while a deferred cleanup operation (queued query callback, analogous to `skbtxq`) is still outstanding and can race with a new concurrent user of the same shared object.

### Finding Description
In `shrinkCache()`: [1](#0-0) 

`mutex.lock("write")` is awaited at line 2261, then for each 500-unit chunk an async `db.query(...)` is fired whose callback (lines 2280-2290) performs the actual `delete assocKnownUnits[...]`, `delete assocCachedUnits[...]`, `delete assocBestChildren[...]`, `delete assocStableUnits[...]`, etc. Critically, `unlock()` at line 2293 sits *outside* and *after* the `for` loop that only enqueues these queries — it does not wait for the queries to resolve (no `async.series`/`Promise.all`). Once `unlock()` runs, `mutex.js`'s `handleQueue()` immediately lets any other job queued on `"write"` proceed: [2](#0-1) 

Every normal unit-processing pipeline also serializes on `"write"` (e.g. `joint_storage.purgeUncoveredNonserialJoints` at `mutex.lock(["write"], ...)`, `writer.saveJoint`, AA composition writes). Because the lock is released before shrinkCache's deferred deletes actually execute, a subsequent writer can run in between: it can freshly populate `assocCachedUnits[unit]`, `assocBestChildren[parent]`, or mark a unit stable via `assocStableUnits[unit]` for a unit that is also in shrinkCache's `arrUnits` batch. When shrinkCache's stale `db.query` callback later fires (its SELECT was based on the pre-race world), it blindly deletes those same keys — wiping out state that the interleaved writer legitimately just created, without any lock protecting that specific mutation. `assocBestChildren` and `assocStableUnits` are structures directly used by the main-chain stability/advance-stability algorithms (`fixIsFreeAfterForgettingUnit`, `forgetUnit`, and the various `determine...Stable` routines) so corrupting them mid-flight can desynchronize what the node believes is the current main-chain/stable set.

### Impact Explanation
Corruption of `assocBestChildren`/`assocStableUnits` from a lost update in this race can make a node compute stability/best-parent differently than it should (or than peers do), which the scope explicitly treats as a qualifying impact: "node disagreement on validity or stability." Divergent stability determination can, in turn, allow a node to treat a since-superseded (non-final) branch as stable, opening the door to accepting/relaying a double-spend of an output that other nodes still consider unstable or already finalized differently.

### Likelihood Explanation
`shrinkCache()` runs unconditionally every 5 minutes (`setInterval(shrinkCache, 300*1000)`) once the relevant caches exceed `MAX_ITEMS_IN_CACHE`, i.e., under normal, unprivileged network activity (any user submitting units enlarges these caches over time) — no attacker privilege or malicious peer/hub interaction is required to trigger the race window; an attacker only needs to time ordinary unit submissions to land in the window between `unlock()` and the deferred `db.query` callbacks completing, which is a realistic, externally-triggerable timing condition given normal request volume.

### Recommendation
Wrap the chunked `db.query` loop in `async.series`/`async.each`+callback (or collect promises and `await Promise.all`) so that `unlock()` is only called after all cache-deletion queries have completed and applied their `delete` mutations, ensuring the entire read-then-delete cache-shrink operation is atomic with respect to the `"write"` mutex, consistent with how the rest of the codebase treats that lock.

### Proof of Concept
1. Let the node run long enough (or synthetically populate) so `assocCachedUnits`/`assocStableUnits` exceed `MAX_ITEMS_IN_CACHE`, causing `shrinkCache()` to enter its lock-then-query-then-early-unlock path (storage.js:2261-2294).
2. At the moment `unlock()` fires (line 2293), immediately submit/process a new unit whose parent is among the units in `arrUnits` currently being SELECTed for cache purge; this new unit's write acquires the `"write"` lock and freshly rebuilds `assocBestChildren[parent]`/marks a unit in `assocStableUnits`.
3. Shortly after, shrinkCache's earlier-issued `db.query` callback resolves and unconditionally deletes `assocBestChildren[row.unit]`/`assocStableUnits[row.unit]` for any unit in the result set — including the one just freshly written in step 2 — silently reverting/losing the update performed under lock protection.
4. Subsequent stability computations that rely on `assocBestChildren`/`assocStableUnits` on this node now diverge from a node that did not experience the race, demonstrating the node-disagreement-on-stability condition.
