### Title
Webhook signature verification keys the trusted secret off `repository.owner.login`, but handlers act on the unrelated `repository.full_name` field — allowing cross-organization/cross-repository webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/webhook secret to validate an inbound webhook against based on `repository_owner`, computed as `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`, and then verifies the HMAC of the whole raw body against that org's secret: [1](#0-0) [2](#0-1) 

Shipit natively supports a multi-organization configuration where each organization has its own independent `webhook_secret`, looked up via `Shipit.github_app_config(organization)`: [3](#0-2) 

However, once signature verification passes, the actual event handlers do **not** re-use `repository.owner.login` to decide which repository/stack to act on. Instead, they derive the target repository from a *different*, independently-controlled field, `repository.full_name`: [4](#0-3) [5](#0-4) 

There is no check anywhere in the request path that `repository.full_name`'s owner segment matches `repository.owner.login` (the field used to select the signing secret). Since HMAC verification only proves "the payload bytes were signed with organization X's secret," and the attacker fully controls the JSON body it signs, an entity that knows/controls **any one** onboarded organization's webhook secret can craft a payload where:
- `repository.owner.login` (or `organization.login`) = their own organization (so the correct secret is selected and the signature validates), while
- `repository.full_name` = `"victim-org/victim-repo"` — a completely different, unrelated repository/organization tracked by the same Shipit instance.

This breaks the equality the system is supposed to enforce:
`organization authenticated by the HMAC == organization whose repository is written to by the handler`

Downstream handlers then trust the forged `full_name` to look up stacks and mutate their state:
- `PushHandler#process` looks up stacks by branch under the attacker-chosen repository and calls `stack.sync_github(expected_head_sha: params.after)`, enqueuing a `GithubSyncJob` for the victim stack: [6](#0-5) 
- `StatusHandler#process` writes fabricated commit statuses via `Commit#create_status_from_github!` for any commit matching the given `sha` (statuses are looked up purely by `sha`, entirely independent of the forged repository field, widening the blast radius further): [7](#0-6) 
- `CheckSuiteHandler#process` schedules check-run refreshes for the victim stack's commits: [8](#0-7) 

### Impact Explanation
Commit statuses (`ci.require`) are used by Shipit to gate whether a commit is eligible for deploy/merge. An attacker who legitimately controls a single organization/GitHub App integrated into a shared multi-tenant Shipit deployment can forge a valid-signature `status` webhook whose `sha` matches a commit in a **victim** organization's stack, writing an attacker-controlled state (e.g., a fabricated "success" status) into that victim's commit record. Because signature verification is keyed on the attacker's own organization's secret while the write target is taken from an unrelated, unauthenticated-relative-to-that-secret field, this crosses the trust boundary between "organization that authenticated" and "repository being written," resulting in a cross-repository write. Forged passing statuses can in turn make deploy/merge gates believe CI has passed, laying groundwork for an unauthorized deploy of code that never actually passed CI for that repository. This matches the Critical impact class of cross-repository writes / potential unauthorized deploy.

### Likelihood Explanation
This requires the attacker to control the webhook secret for at least one organization already configured in the target Shipit deployment (i.e., to be a legitimate but malicious tenant in a multi-org Shipit setup, or to have obtained one org's `webhook_secret` — not the whole app's credentials). Given that:
- Multi-org configuration is a documented, supported feature (`docs/setup.md`, `config/secrets.development.example.yml`),
- The webhook payload is fully attacker-authored JSON (webhooks are just signed HTTP POSTs, not validated for internal field consistency),
- No additional authorization step ties `repository.owner.login` to `repository.full_name`,

this is a straightforward, reliably reproducible cross-tenant forgery once one org's secret is known, i.e. plausible in any Shipit instance managing more than one organization or repository set.

### Recommendation
1. In `WebhooksController#verify_signature`, after computing `repository_owner`, also verify that `params.dig('repository', 'full_name')` (and/or any repository identifiers used by handlers) actually belongs to that same owner (e.g., `full_name.split('/').first.casecmp?(repository_owner)`), rejecting the request otherwise.
2. Preferably, resolve the target `Stack`/`Repository` in `Handler` using the same authenticated owner value that selected the signing secret, rather than trusting `repository.full_name` independently.
3. For `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup to commits belonging to stacks under the verified `repository_owner`, instead of matching `sha` globally across all repositories.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (a supported, documented configuration in `docs/setup.md`).
2. As the operator of `attacker-org`, compute `sha1=HMAC(attacker_org_webhook_secret, body)` over a `status` event payload where:
   ```json
   {
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check"
   }
   ```
3. POST this to `/webhooks` with `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `attacker-org`, fetches `attacker-org`'s secret, and the signature validates successfully.
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against the victim commit (looked up purely by `sha`, unrelated to the payload's `repository` field) and calls `create_status_from_github!`, writing a forged "success" status onto `victim-org`'s commit — despite the request never being signed by `victim-org`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
