### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status authenticated for one repository mutate commit status for any other repository/stack sharing the same commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no repository/stack scoping, unlike every other webhook handler which resolves the target `stacks` via `Repository.from_github_repo_name(repository_name)`. Because git commit SHAs are content-addressed and identical across forks/mirrors of the same code, a validly-signed status webhook from repository A can flip the state of a commit belonging to an unrelated stack B whenever both track a commit with the same SHA (e.g. a shared upstream commit, a fork, or a mirrored branch).

### Finding Description
The broken binding: the code implicitly assumes `commit.sha == params.sha ⟹ commit.stack.repository == payload.repository`, but no code enforces this equality.

Path:
- `Shipit::WebhooksController#create` (app/controllers/shipit/webhooks_controller.rb:10-15) parses the payload and dispatches to handlers after `verify_signature`, which only checks that the raw body's HMAC matches the secret for `repository_owner` derived from the payload itself [1](#0-0) . This authenticates that the payload came from GitHub for *some* org/repo the attacker legitimately controls (their own repo/org where the GitHub App/webhook is installed) — it does **not** bind the `context`/`sha`/`state` fields to that repository beyond the signature covering the raw body.
- `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
This is the only handler that does not scope its query through `stacks`/`repository_name`; compare to the base `Handler#stacks`, which resolves `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) , a pattern other handlers (push, pull_request, membership, check_suite) follow but `StatusHandler` does not.
- `Commit#create_status_from_github!` then writes the status against whatever stack owns that commit row: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) , and `add_status` recomputes `status`, potentially emitting `deployable_status`/`commit_status` hooks and calling `stack.schedule_merges` [5](#0-4) .
- Deployability (`deployable?`) and blocking (`blocked?`) are derived directly from these statuses [6](#0-5) .

Exploit flow: An attacker who owns/controls repository A (with a legitimately configured GitHub App/webhook, so they can produce a validly-signed payload for A) sends `POST /webhooks` with `X-Github-Event: status`, `repository.owner.login`/`repository.full_name` = A, `sha` = a commit SHA that also exists, byte-for-byte, in victim stack B (e.g., because B mirrors/forks the same upstream history, or a commit was cherry-picked/rebased identically), `context: buildkite/deploy`, `state: failure`. `verify_signature` passes because it only checks the signature against A's secret. `StatusHandler` then finds **every** `Commit` row across the whole Shipit installation with that SHA — including the one belonging to victim stack B — and writes a `failure` status onto it, flipping `required_statuses`/`blocking_statuses` results for B's commit regardless of what actually happened in repository A.

None of the existing guards prevent this: `verify_signature` validates payload integrity/origin for repo A only, not that the *content* of the payload (sha, context) is scoped to A; `drop_unhandled_event` only filters by event type; the `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`/`context`, not repository correspondence; there is no `stacks`/`Repository.from_github_repo_name` filter used in this handler at all.

### Impact Explanation
A payload authenticated by one repository (A) can write a status onto a `Commit` belonging to a different repository's stack (B), which is explicitly called out in the rules as Critical impact ("a payload for one repository mutating another's stack, commit, task or team"). If B is configured as `buildkite/deploy` required/blocking status and is a production environment, an attacker-forced `failure` state can flip `deployable?`/`blocked?` for that commit in B, enabling denial of legitimate deploys or unblocking a rollback path, without the attacker ever having credentials for stack B.

### Likelihood Explanation
This requires two conditions beyond attacker's basic capability: (1) the attacker must be able to send a validly GitHub-signed `status` webhook for some repository (achievable if they own a repo where a GitHub App/webhook Shipit trusts is installed, or push actual commits/statuses to their own repo), and (2) a commit with the identical SHA must exist in a distinct, victim-tracked Shipit stack. Condition (2) is the limiting factor: SHA1 is content-addressed, so this only occurs naturally via forks/mirrors/re-pushed identical commits (not spoofable at will for an arbitrary target). This is a real but conditional collision, not a free-form "any sha, any repo" attack. I could not fully verify inside `lib/shipit/github_app.rb#verify_webhook_signature` whether the secret is per-organization/per-app or shared platform-wide (time/tooling ran out before reading that file's implementation), which affects exactly how easily an attacker can obtain a valid signature for a chosen "attacker" repo — this should be confirmed before rating exploitability further.

### Recommendation
Scope `StatusHandler#process` the same way as other handlers: resolve the repository from the payload (`Repository.from_github_repo_name(repository_name)`) and restrict the `Commit` lookup to that repository's stacks (e.g., `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`), rather than querying `Commit` globally by SHA.

### Proof of Concept
minitest sketch (no live GitHub):
```ruby
test "a status webhook authenticated for repo A must not mutate a commit belonging to repo B's stack" do
  stack_a = shipit_stacks(:shipit)               # tracks repo A
  stack_b = shipit_stacks(:cyclimse)              # victim, production environment, requires buildkite/deploy
  stack_b.update!(environment: 'production')

  shared_sha = 'a' * 40
  commit_a = stack_a.commits.create!(sha: shared_sha, ...)
  commit_b = stack_b.commits.create!(sha: shared_sha, ...)

  before = commit_b.reload.deployable?

  payload = {
    'sha' => shared_sha, 'state' => 'failure', 'context' => 'buildkite/deploy',
    'repository' => { 'full_name' => stack_a.github_repo_name, 'owner' => { 'login' => stack_a.repository.owner } }
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  after = commit_b.reload.deployable?

  # Broken binding under test: commit_b.stack.repository == payload['repository']['full_name']
  assert_not_equal before, after, "commit belonging to an unrelated repo/stack was mutated by a payload authenticated for a different repo"
end
```
Assert both sides of the equality `commit.stack.repository.full_name == payload['repository']['full_name']` before/after: currently they diverge (false) yet the write still succeeds, confirming the vulnerability.
