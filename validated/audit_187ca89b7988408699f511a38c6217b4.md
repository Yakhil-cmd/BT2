### Title
Cross-organization `Shipit.github_teams` membership escalation via unchecked organization binding in `MembershipHandler#process` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`WebhooksController#verify_signature` validates the HMAC signature against the webhook_secret for the organization named in the payload itself (`repository_owner`/`params.organization.login`), not against the organization that actually owns the `Team` row being mutated. `MembershipHandler#process` and `Team.find_or_create_by!(github_id: ...)` never re-check `team.organization` against the verified requesting organization before calling `team.add_member(member)`, so a signed webhook from org A can add a member to a `Team` whose `organization` column belongs to victim org B, as long as the attacker guesses/knows the victim team's `github_id`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:
`verified_organization (params.organization.login, checked against Shipit.github(organization: repository_owner).webhook_secret)` **==** `team.organization (the organization column of the Team row mutated by team.add_member)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) , and validates the signature using `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) . For a `membership` event there is no `repository` key, so `repository_owner` resolves to `params.organization.login` — the attacker's own org, whose `webhook_secret` the attacker controls/knows.
2. `MembershipHandler#find_or_create_team!` calls `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login }` [3](#0-2) . Because `find_or_create_by!` only runs the block on *creation*, if a `Team` with that `github_id` already exists (e.g., victim's team, `github_id: 555`, `organization: 'victim-org'`), the block is skipped and `team.organization` remains `'victim-org'` — untouched by the attacker's payload.
3. `MembershipHandler#process` then unconditionally calls `team.add_member(member)` for `action == 'added'` [4](#0-3) , and `Team#add_member` performs no comparison between `team.organization` and the currently verified request organization: `members.append(member) unless members.include?(member)` [5](#0-4) .
4. If that `Team` is one of the entries returned by `Shipit.github_teams` (memoized team list derived from `github.oauth_teams`) [6](#0-5) , then `User#authorized?` — `Shipit.github_teams.empty? || teams.where(id: Shipit.github_teams.map(&:id)).exists?` [7](#0-6)  — becomes `true` for the attacker's `User` record, and `force_github_authentication` in `Authentication` grants them access to the whole Shipit application [8](#0-7) .

No existing guard closes this gap: `verify_signature` verifies provenance of *an* organization, not the organization the payload claims to be operating on relative to a pre-existing record; the `ExplicitParameters` schema on `MembershipHandler` only type-checks fields, it does not compare `params.organization.login` to `team.organization` [9](#0-8) ; and `Team.find_or_create_by!` silently no-ops the organization-setting block on an existing record, meaning any staleness/mismatch is invisible to the handler.

### Impact Explanation
An attacker who administers any organization onboarded into the same multi-tenant Shipit instance (and therefore knows their own org's `webhook_secret`, which they themselves configure on the GitHub webhook settings page) can add arbitrary GitHub logins as members of any pre-existing `Team` row by replaying a `membership` `added` event with a guessed/known victim `github_id`. If that team is part of `Shipit.github_teams`, the attacker's account gains `authorized?` == `true`, bypassing the org-membership authorization gate for the entire Shipit application — this is escalation into `Shipit.github_teams` authorization (High), and repeatable against any team ID the attacker can enumerate, across all tenants sharing the instance.

### Likelihood Explanation
Preconditions: the attacker must control an organization already configured in Shipit's `secrets.github` with a distinct `webhook_secret` (multi-org Shipit deployment), must know a target `Team`'s numeric `github_id` (team IDs are sequential/small and often discoverable), and the target org's team must already exist as a `Team` row (created previously via any handler or `Shipit.github_teams`/rake task). Cost is low: crafting one signed HTTP POST to `/webhooks` with a `membership` payload. This is realistic in any Shipit setup serving more than one GitHub organization.

### Recommendation
In `MembershipHandler#find_or_create_team!`/`#process`, verify that `params.organization.login` (the organization that produced a valid signature) matches the existing `team.organization` before performing any mutation; reject/no-op (or raise) when they diverge instead of silently proceeding to `team.add_member`/`team.members.delete`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual)
test "membership webhook signed by attacker org cannot add member to victim-owned team" do
  victim_team = Shipit::Team.create!(organization: 'victim-org', github_id: 555, name: 'Victim Team', slug: 'victim-team', api_url: 'https://api.github.com/teams/555')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 555, 'name' => 'Victim Team', 'slug' => 'victim-team', 'url' => 'https://api.github.com/teams/555' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker' }
  }

  # Simulates a webhook validly signed with attacker-org's own webhook_secret
  Shipit::Webhooks::Handlers::MembershipHandler.call(payload)

  attacker = Shipit::User.find_by(login: 'attacker')
  victim_team.reload

  assert_equal 'victim-org', victim_team.organization # organization column unchanged, still victim's
  assert_includes victim_team.members, attacker        # BUG: attacker added despite org mismatch
  # if victim_team is part of Shipit.github_teams:
  # assert attacker.authorized? # escalates attacker into authorized status for victim's org gate
end
```
