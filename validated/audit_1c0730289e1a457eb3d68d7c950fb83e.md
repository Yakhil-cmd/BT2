In multi-organization deployments (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md:182-209`), each GitHub organization has its own `webhook_secret`. `Shipit.github(organization:)` picks the app/secret keyed strictly by name [1](#0-0) , and `WebhooksController#verify_signature` selects that secret using `repository_owner`, which is read straight from the untrusted JSON body (`repository.owner.login`, falling back to `organization.login`) before the HMAC is checked [2](#0-1) . ### Title
Webhook signature verification keys off `repository.owner.login` while the push handler acts on the independent `repository.full_name` field, letting one organization's webhook secret forge events for another organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate a request against using `repository.owner.login` (or `organization.login`) taken directly from the unauthenticated JSON body. Once verified, `PushHandler` (and other handlers) locate the `Repository`/`Stack` to act on using the unrelated `repository.full_name` field from that same body. An attacker who legitimately controls (or has leaked) the webhook secret for **any one** organization configured in the instance can forge a payload whose `repository.owner.login` names their own org (so it validates against their own secret) but whose `repository.full_name` names a repository belonging to a **different**, victim organization also hosted on the same Shipit instance.

### Finding Description
- `Shipit.github(organization:)` returns a per-organization `GitHubApp` (and thus a per-organization `webhook_secret`) keyed purely by organization name, as documented for multi-org setups [1](#0-0)  and exercised in `test/unit/shipit_test.rb` and `test/dummy/config/secrets_double_github_app.yml`.
- The controller derives the organization used for verification straight from the attacker-controlled body: [5](#0-4) [6](#0-5) 
- After signature verification succeeds, `Handler#repository_name`/`#stacks` (used by `PushHandler`, and analogous logic in other handlers via `params.repository.full_name`) resolve the target repository from a **different** JSON key, `repository.full_name`, not from `repository.owner.login`: [3](#0-2) 
- `PushHandler#process` then triggers `stack.sync_github(expected_head_sha: params.after)` on whatever stacks belong to that resolved repository: [4](#0-3) 

The binding that should hold is: **organization whose secret authenticated the request == organization that owns the repository being written to**. Because the controller checks the signature against `repository.owner.login`/`organization.login` while the handler acts on `repository.full_name`, these two fields are never cross-validated, so the equality is not enforced. The signature only proves "this payload was signed by Org A's secret"; it says nothing about which repository's stacks get mutated, since that's chosen by an entirely separate, unverified field in the same forgeable JSON body.

### Impact Explanation
An entity that holds a valid webhook secret for one organization onboarded to a shared Shipit instance (a plausible, lower-trust position relative to other tenant organizations) can forge push/status/check_suite events that pass signature verification yet target stacks owned by a completely different organization. Via `PushHandler`, this can drive `GithubSyncJob`/`sync_github` with an attacker-chosen `expected_head_sha` against a victim org's stack, and other handlers (`status`, `check_suite`) that also resolve the target through `repository.full_name` are equally reachable, letting the attacker inject fabricated commit/check/status state that later factors into deploy decisions on a stack they have no legitimate rights to. This is a cross-repository/cross-tenant write achieved purely by crossing an organizational trust boundary that the signature was supposed to enforce.

### Likelihood Explanation
Requires only: (1) the target instance be configured with multiple GitHub organizations (a documented, supported configuration - `docs/setup.md`), and (2) the attacker controls the webhook secret of any one onboarded organization (e.g., a low-trust or newly-onboarded org, or a leaked secret) - no Shipit session, API token, or repository write access to the victim org is needed. The request is a simple, directly crafted HTTP POST with mismatched `owner.login`/`full_name` fields.

### Recommendation
After signature verification, re-validate that `repository.owner.login` (or `organization.login`, whichever value selected the verifying app) matches the owner segment of `repository.full_name` before dispatching to any handler; reject the request (422) on mismatch. Alternatively, derive the verifying organization exclusively from `repository.full_name`'s owner segment so a single field drives both the secret selection and the write target.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker (who administers `attacker-org` and knows its `webhook_secret`) crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, raw_body)` and POSTs to `/github/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies, since the attacker used that org's own secret [5](#0-4) .
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which resolves stacks via `payload.dig('repository', 'full_name')` = `"victim-org/victim-repo"` [3](#0-2) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s stack [4](#0-3) , despite the request never being authenticated as originating from `victim-org`.
