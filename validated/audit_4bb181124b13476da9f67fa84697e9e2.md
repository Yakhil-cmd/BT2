### Title
Cross-organization Team hijack via `membership` webhook - MembershipHandler#find_or_create_team! trusts `params.team.id` without binding it to the verified organization ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the raw request body was signed by the GitHub App belonging to `repository_owner` (here, `params.organization.login`). It does not, and cannot, prove that the `team` object embedded in that same body actually belongs to that organization. `MembershipHandler#find_or_create_team!` looks up `Shipit::Team` solely by `github_id` and silently reuses any pre-existing record, so a legitimately verified webhook from organization `O_attacker` can mutate membership of a `Team` row that actually belongs to `O_victim`.

### Finding Description
The broken binding is:

`organization_that_signed_body (repository_owner ⇒ Shipit.github(organization: params['organization']['login']))` **should equal** `organization_that_owns_the_mutated_Team (Team#organization column of the record matched by params.team.id)`.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
2. This check only validates that the HMAC matches the `webhook_secret` configured for whichever org name is present in the payload — it says nothing about the `team` sub-object inside the same payload.
3. `Shipit::Webhooks.for_event('membership')` dispatches to `MembershipHandler#process`, which calls `find_or_create_team!`: `Team.find_or_create_by!(github_id: params.team.id) do |team| team.github_team = params.team; team.organization = params.organization.login end`. [3](#0-2) 
4. The `do |team| ... end` block, which sets `team.organization`, only runs when the record is **created**. If a `Team` row with that `github_id` already exists (e.g., created earlier from a legitimate `O_victim` membership event, or seeded), `find_or_create_by!` returns the existing record untouched, and `team.add_member(member)` is called on it regardless of which organization's webhook secret verified the request. [4](#0-3) 
5. Nothing in `MembershipHandler`'s `ExplicitParameters` schema, `find_or_create_team!`, or `Team` validations asserts `team.organization == params.organization.login` before mutating membership.

Exploit flow: The attacker is an owner/admin of a real, distinct organization `O_attacker` that has been onboarded to this Shipit deployment (its own entry in `secrets.github`, its own `webhook_secret`, per `Shipit.github_app_config`). [5](#0-4)  Because the attacker controls `O_attacker`'s webhook configuration, they know `O_attacker`'s `webhook_secret` and can compute a valid `X-Hub-Signature` for an arbitrary JSON body. They POST to `/webhooks` with `X-Github-Event: membership` and a body such as:
```json
{"action":"added","organization":{"login":"O_attacker"},"team":{"id":<O_victim_team_github_id>,"name":"x","slug":"x","url":"http://x"},"member":{"login":"attacker-login"}}
```
`repository_owner` resolves to `O_attacker` (no `repository` key present), `verify_signature` succeeds because the signature really was produced with `O_attacker`'s secret. `MembershipHandler#process` then runs with `params.team.id` = the victim's real GitHub team id, finds the existing `Team` record for `O_victim`'s team, and adds `attacker-login` as a member.

Existing guards do not stop this: `drop_unhandled_event` and `check_if_ping` are irrelevant to `membership`; `ExplicitParameters` only validates types/presence, not cross-field organizational ownership; `Team` has no uniqueness/organization constraint tying `github_id` to `organization` at lookup time; there is no `require_permission!`/`current_user` check on this unauthenticated controller (`WebhooksController` inherits from `ActionController::Base`, not the authenticated base controller).

### Impact Explanation
If the victim `Team` record is one of the entries in `Shipit.github_teams` (the configured authorization teams used by `User#authorized?`), the attacker becomes a member of that team in Shipit's database and is treated as `authorized?` for the whole application, even though they have never been a real member of `O_victim`. [6](#0-5)  This is a cross-tenant authorization escalation: a payload verified for one organization (`O_attacker`) mutates state (`Team`/`Membership`) that governs authorization for a different organization (`O_victim`). This matches the High severity category "escalation into `Shipit.github_teams` authorization." The attack is repeatable against any `github_id` the attacker can learn or guess (GitHub team ids are small sequential integers, and team membership listings/URLs are often visible to broader audiences than the team itself), and against any number of victim teams already present in the Shipit database.

### Likelihood Explanation
Preconditions: a multi-organization Shipit deployment (`secrets.github` configured with more than one org, each with distinct `app_id`/`webhook_secret`), the attacker legitimately administers one such onboarded organization (`O_attacker`) and therefore knows its `webhook_secret`, and a `Team` row for the victim organization already exists with a known/guessable `github_id`. Given these (plausible in any Shipit-as-a-service / shared-instance setup), the attack costs a single unauthenticated POST to `/webhooks`, is fully repeatable, and requires no GitHub-side action beyond knowledge of the attacker's own real webhook secret.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` matches the `organization` of any pre-existing `Team` matched by `github_id` before mutating membership (e.g., raise/no-op if `team.organization.casecmp?(params.organization.login)` is false), or scope the lookup itself to `github_id` **and** `organization`. More generally, `WebhooksController#verify_signature` should ensure every organization-identifying field referenced later in a handler (here `team`, elsewhere any nested org references) is consistent with the org whose secret verified the signature.

### Proof of Concept
```ruby
test ":membership from a different org's verified webhook cannot mutate another org's team" do
  victim_team = shipit_teams(:shopify_developers) # organization == 'shopify', known github_id
  attacker_org = 'attacker-org'

  @request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # simulate attacker knowing attacker-org's real secret

  body = {
    action: 'added',
    organization: { login: attacker_org },
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: victim_team.api_url },
    member: { login: 'attacker-login' }
  }.to_json

  assert_no_difference -> { Team.where(organization: attacker_org).count } do
    post :create, body:, as: :json
  end

  assert_includes victim_team.reload.members.map(&:login), 'attacker-login',
    "attacker gained membership in shopify's team via an attacker-org-verified webhook"
end
```
Both sides of the binding — `repository_owner` resolved as `attacker_org` (the org whose secret verified the request) vs. `victim_team.organization == 'shopify'` (the org actually mutated) — remain unequal after processing, confirming the cross-organization write.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
