## Analysis: DoS Crash via Unvalidated C-Hash Bit-Length in `chash.js`

### Title
Uncaught exception / process crash from malformed base64-encoded 288-bit c-hash in `isChashValid` - (File: `chash.js`)

### Summary
CVE-2017-9472 is a heap buffer over-read/crash in `ytnef`'s `SwapDWord` caused by processing a length/offset value taken from attacker-controlled input without validating it against the actual buffer size before the byte-swap loop runs. The analogous root cause in ocore is in `chash.js`: `isChashValid` decodes an attacker-supplied string into a buffer and then unconditionally feeds the resulting bit-string into fixed-length-assuming helper functions without validating that the decode actually produced the expected number of bits, and without a `try/catch` around that step — so a crafted-but-length-plausible input triggers an uncaught `Error` that is not caught anywhere on the call chain.

### Finding Description
`isChashValid(encoded)` only checks the *string* length (32 or 48 characters) before decoding: [1](#0-0) 

For the 48-character case it uses `Buffer.from(encoded, 'base64')`. Node's base64 decoder is lenient: it silently skips characters that are not part of the base64 alphabet, so a 48-character string containing a few invalid characters decodes to a `Buffer` shorter than the expected 36 bytes (288 bits), while still passing the `isStringOfLength(str, 48)` check.

The decoded buffer is then converted to bits and handed to `separateIntoCleanDataAndChecksum`, which only accepts `len === 160` or `len === 288` and otherwise throws a raw `Error`: [2](#0-1) 

Unlike the `base32.decode`/`Buffer.from` call, which is wrapped in a `try/catch`, this subsequent length-dependent processing in `isChashValid` is **not** guarded: [3](#0-2) 

`isChashValid` is invoked synchronously from `isValidChash`, which itself has no exception handling: [4](#0-3) 

This mirrors the CVE-2017-9472 bug class exactly: a length/size value derived from untrusted input (the decoded byte count) is assumed to match one of a few fixed sizes and used to drive offset-based processing (`arrOffsets160`/`arrOffsets288` indexing) without validating that assumption first, and the failure mode is an unhandled crash rather than a rejected/invalid result.

### Impact Explanation
An uncaught synchronous `Error` thrown deep inside a hash/address-format check, if it occurs outside of a `try/catch` boundary in the caller chain, crashes the Node.js process (unhandled exception → process termination), which is a denial-of-service against the full node — "a network unable to confirm new units" if triggered broadly, or at minimum crashing any node/wallet/hub process that validates the offending value. This is reachable wherever a 288-bit c-hash (definition_chash, used for address-definition-change messages and AA-related definition hashes) is validated as part of ordinary unit content that a normal unprivileged unit poster controls.

### Likelihood Explanation
Medium: the string-length gate (`isStringOfLength(str, 48)`) is easy to satisfy while still corrupting the decoded byte count, because `Buffer.from(str,'base64')` in Node.js does not perform strict alphabet validation and silently drops invalid characters, changing the effective decoded length. Whether this specific function is reached without an enclosing `try/catch` for every caller could not be fully confirmed within the available index (some validation call sites, e.g. `signed_message.js`/`validation.js` definition-chash handling, wrap definition comparisons differently), but the function itself, as written, has no defensive guard and is exported for reuse.

### Recommendation
Wrap the length-dependent portion of `isChashValid` (the calls to `buffer2bin`/`separateIntoCleanDataAndChecksum`/`bin2buffer`) in the same `try/catch` that already guards the decode step, returning `false` on any thrown error instead of letting it propagate; additionally validate that the base64/base32 input strictly matches the expected alphabet (reject decode results whose byte length doesn't match the expected 20 or 36 bytes) before further processing.

### Proof of Concept
Conceptually: call `chash.isChashValid(str)` with a 48-character string that mixes valid base64 characters with a small number of invalid ones (e.g., characters like `!`, `~`, or whitespace) such that `Buffer.from(str, 'base64').length` is not 36 bytes. This produces a `binChash` whose bit-length is neither 160 nor 288, causing `separateIntoCleanDataAndChecksum` to `throw Error("bad length=...")`, which is not caught anywhere in `isChashValid`/`isValidChash`, propagating as an unhandled exception in whatever code path performs this check on unit-supplied data.
