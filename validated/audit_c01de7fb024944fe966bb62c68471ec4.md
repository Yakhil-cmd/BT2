### Title
Unauthenticated user impersonation via `X-Shipit-User` header breaks API credential-to-identity binding - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
The Bunni bug root cause is a mismatch between the entity that is cryptographically verified as caller and the entity actually acted upon by the privileged function (`onlyBunniHub` checked, but `BunniHook` is the real caller). The analogous binding in `shipit-engine` is: `current_user = identify(verified ApiClient credential)` should equal `current_user = User acted upon in the request`. In `Api::BaseController`, the `User` that is verified as calling (via HTTP Basic Auth token, cryptographically checked with `SimpleMessageVerifier`) is a completely different object from the `User` that ends up attributed to the resulting deploy/rollback/lock/task/merge action, because the latter is taken from an unauthenticated request header.

### Finding Description
`Api::BaseController#authenticate_api_client` verifies only the `ApiClient` bearer credential: [1](#0-0) 

This authenticates *which `ApiClient` (and its scoped permissions/stack)* is calling, via `ApiClient.authenticate`, which validates a signed token against `Shipit.api_clients_secret`: [2](#0-1) 

However, the `current_user` used throughout the API — the identity that ends up recorded as the human actor for the request — is derived separately and is **not covered by that signature at all**: [3](#0-2) 

`identify_user` simply looks up any existing `Shipit::User` by the client-supplied `X-Shipit-User` header, with no check that this claimed login corresponds to the authenticated `ApiClient`'s creator, nor any signature over the header value. This `current_user` is then used as the authoritative actor for numerous privileged, auditable, mutating actions:

- Deploys: `stack.trigger_deploy(commit, current_user, ...)` [4](#0-3) 
- Rollbacks / task aborts: `deploy.trigger_rollback(current_user, ...)`, `active_task.abort!(aborted_by: current_user, ...)` [5](#0-4) 
- Ad-hoc task triggers/aborts: `stack.trigger_task(params[:task_name], current_user, ...)`, `task.abort!(aborted_by: current_user)` [6](#0-5) 
- Stack locking: `stack.lock(params.reason, current_user)` [7](#0-6) 
- Merge requests: `MergeRequest.request_merge!(stack, params[:id], current_user)` [8](#0-7) 

The equality that is supposed to hold is: `User bound to verified ApiClient credential == User recorded as request actor`. Because `identify_user` accepts an arbitrary, attacker-controlled `X-Shipit-User` header, this equality is broken: any caller who possesses a valid `ApiClient` token — even one scoped narrowly, e.g. only `deploy:stack` permission on a single stack, as shown by the existing fixture `here_come_the_walrus` (`permissions: ['read:stack']`, scoped `stack:`) — can set `current_user` to be *any* other `Shipit::User` record in the database simply by naming their login, with no relationship required between the token and the impersonated user.

The engine's own test suite documents this as intended behavior rather than a bug being tested against: [9](#0-8) 

This confirms the header is described internally as "the claimed user" — i.e., an unauthenticated claim, not a verified identity — yet it is trusted as the actor of record for every mutating API operation.

### Impact Explanation
Because `identify_user` performs no binding check between the authenticated `ApiClient` and the claimed `User`, any party in possession of a valid, even minimally-scoped API token can force any deploy, rollback, task execution, task abort, stack lock/unlock, or merge-request action to be permanently attributed to an arbitrary victim user of their choosing (e.g., an administrator or a member of `Shipit.github_teams`). This is an authentication/identity-binding bypass: the system's authorization model presents these actions as if performed by the impersonated `User`, corrupting audit trails, `CommitDeploymentStatus` author attribution, and any downstream logic (hooks, notifications, "Merge-Requested-By" resolution in `User.find_or_create_author_from_github_commit`) that treats `current_user`/`task.user` as a trustworthy, verified identity. This falls under the "authentication bypass" / identity-spoofing class explicitly called out by the rules ("a GitHub identity versus the `User` bound to the session").

### Likelihood Explanation
Any consumer holding a legitimate `ApiClient` Basic-Auth token can exploit this with a single crafted header on any authenticated API request; no additional secrets, GitHub credentials, or elevated permissions beyond a minimally scoped token are required, and the behavior is exercised (and effectively normalized) by the project's own test suite.

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity claim. Bind the acting `User` to the authenticated `ApiClient` (e.g., use `api_client.creator` or a signed/verified mapping) rather than resolving an arbitrary attacker-supplied login header, or require that the claimed user match the `ApiClient`'s `creator`/authorized scope before allowing impersonation-style attribution.

### Proof of Concept
1. Provision (or possess) an `ApiClient` scoped only to `stack:shipit` with permission `deploy:stack` (analogous to fixture `here_come_the_walrus`).
2. Authenticate to `POST /shipit/stack/deploys` (or `/rollbacks`, `/tasks/:id/abort`, `/locks`, `/merge_requests/:id`) using this client's Basic Auth token, as in [10](#0-9) .
3. Set header `X-Shipit-User: <victim-admin-login>`.
4. The resulting `Deploy`/`Rollback`/`Task`/lock/merge action is created with `user == victim-admin`, as demonstrated by [11](#0-10)  — with zero verification that the caller's token has any relationship to `victim-admin`.

        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?

          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
