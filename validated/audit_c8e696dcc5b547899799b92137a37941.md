### Title
Missing ownership/authorization validation when registering shared-address signer→device bindings - ([File: wallet_defined_by_addresses.js])

### Summary
`handleNewSharedAddress()` accepts a `new_shared_address` wallet message from **any** paired (correspondent) device and persists the signer→device_address bindings it contains without any cryptographic proof that the sending device — or any of the devices named in the payload — actually controls the signing paths/addresses being attributed to them. This mirrors the Ajna `permit()` bug: a delegation of control (here, "which device is authorized to sign on behalf of which address in a shared/multisig address") is accepted purely on the say-so of an untrusted caller, with no ownership check.

### Finding Description
`handleNewSharedAddress(body, callbacks)` in `wallet_defined_by_addresses.js` is invoked directly from the network/device-message dispatcher in `wallet.js` (`case "new_shared_address": walletDefinedByAddresses.handleNewSharedAddress(body, ...)`), i.e. it is reachable by **any paired device** without additional gatekeeping. [1](#0-0) 

The handler performs only *structural* checks:
- that `body.definition` hashes to `body.address` (`objectHash.getChash160`),
- that each `signerInfo.address` is a syntactically valid address,
- that the `signers` map is internally consistent with the addresses referenced inside `body.definition` (via `extractAddressPathsFromDefinition`). [2](#0-1) 

None of these checks verify that the `device_address` claimed for each signing path in `body.signers` is authentic — i.e. that the device named actually possesses the private key/definition for the corresponding member address, or that it consented to be recorded as the signer for that path. The only "ownership" check performed, `determineIfIncludesMeAndRewriteDeviceAddress`, merely checks whether *my own* address appears among the member addresses; it does nothing to validate the `device_address` bindings claimed for *other* members. [3](#0-2) 

After these checks pass, `addNewSharedAddress()` blindly inserts every `(shared_address, address, signing_path, device_address)` tuple from the attacker-supplied `assocSignersByPath` into `shared_address_signing_paths`, and then re-forwards this (now persisted) mapping to the cosigners of the receiver's own member addresses (`forwardNewSharedAddressToCosignersOfMyMemberAddresses`), propagating the unverified bindings further. [4](#0-3) [5](#0-4) 

This `shared_address_signing_paths` table is precisely the routing table later used to decide **which device to send a signing request to** when a payment from the shared address needs to be composed/signed (see `readSharedAddressCosigners`/`readAllControlAddresses`, and the "sign" message dispatch logic that resolves the responsible device for a signing path). [6](#0-5) [7](#0-6) 

### Impact Explanation
Because the `device_address` bound to a given signing path is trusted without verification, a malicious paired device can send a forged `new_shared_address` message naming a real victim's address as a signer but pointing that signing path's `device_address` at the attacker's own device (or an unreachable/blackholed device). Any wallet that later needs to compose a transaction from that shared/multisig address will route the signing request to the attacker-controlled `device_address` instead of the genuine cosigner's device. The attacker cannot forge the actual signature (the on-chain address is still `chash160(definition)`, enforced cryptographically), but they can:
- **Freeze funds** sent to the shared address by silently swallowing/ignoring signing requests that should have reached the real cosigner, permanently preventing the multisig transaction from being completed.
- Poison other correspondents' local databases via the re-forwarding logic in `forwardNewSharedAddressToCosignersOfMyMemberAddresses`, spreading the false routing information across the wallet's device network.

This satisfies the "AA/contract fund loss or freezing" impact bar even though no signature is forged, because it corrupts the off-chain authorization/routing metadata that determines who is asked to co-sign, without any check that the party asserting the binding actually owns it — the direct analog of `permit()` approving a spender without checking `msg.sender == ownerOf(tokenId)`.

### Likelihood Explanation
The attack requires only that the attacker be a paired correspondent device of the victim (or of any device in the propagation chain) — no special privilege, no on-chain unit, no HUB/node compromise. Sending a `new_shared_address` wallet message is a completely normal client-to-client message; any device that has been paired (even briefly, e.g., after a demo/support/pairing-code exchange) can send this payload. The check `determineIfIncludesMeAndRewriteDeviceAddress` only blocks messages where none of the receiver's own addresses are mentioned — an attacker can always include the victim's real, already-known address to pass this check while still lying about who else is (falsely) bound to which signing path/device.

### Recommendation
- Do not persist or trust `device_address` bindings supplied in an incoming `new_shared_address` (or `approve_new_shared_address`) message unless they are independently corroborated (e.g., only accept/overwrite bindings for signing paths where the message sender is the device that owns the corresponding address, or require a signed attestation from each named device confirming it agreed to be recorded as signer for that specific path).
- When forwarding shared-address information (`forwardNewSharedAddressToCosignersOfMyMemberAddresses` / `sendSharedAddressToPeer`), forward only bindings that were verified locally, not merely relay attacker-supplied data.
- Consider requiring that `device_address` for a signing path be established only through the device that actually approved membership (as in the `approvePendingSharedAddress`/`pending_shared_address_signing_paths` flow) rather than accepted wholesale from a `new_shared_address` broadcast.

### Proof of Concept
1. Attacker device `D_a` pairs with victim device `D_v` (a normal, low-privilege pairing).
2. Victim `D_v` has known address `A_v`.
3. Attacker crafts a definition `arrDefinition` referencing `A_v` at path `r.0` and a bogus/unrelated cosigner address `A_x` at path `r.1` (e.g., `["and", [["address", A_v], ["address", A_x]]]`), and computes `shared_address = chash160(arrDefinition)`.
4. Attacker sends:
```
{
  subject: "new_shared_address",
  body: {
    address: shared_address,
    definition: arrDefinition,
    signers: {
      "r.0": { address: A_v, device_address: D_a },   // falsely claims D_a controls A_v's path
      "r.1": { address: A_x, device_address: D_a }
    }
  }
}
```
5. `handleNewSharedAddress` passes all structural checks (`chash160` matches, addresses are syntactically valid, signer paths match `extractAddressPathsFromDefinition`) and, because `A_v` is one of the receiver's `my_addresses`, `determineIfIncludesMeAndRewriteDeviceAddress` succeeds. Because `bHasMyDeviceAddress` is false (device_address for `r.0` is `D_a`, not the victim's own device), the rewrite logic corrects only the local device's own record for that specific `signing_path` if the address matches `arrMyMemberAddresses` — however other cosigners receiving the forwarded message have no such correction capability for paths not concerning their own address, so mis-bound `device_address` values for *other* members persist in the shared `shared_address_signing_paths` table.
6. `addNewSharedAddress` inserts these bindings, and once funds are later sent to `shared_address` and a spend is attempted, the composer/signing flow consults `shared_address_signing_paths` and routes the required signature request for `r.1` (or any path bound to `D_a`) to the attacker's device, which can simply never respond — freezing the multisig output.

Note: I was not able to fully trace every downstream consumer of `shared_address_signing_paths.device_address` (e.g. the exact `composer.js` code path for multi-device signing aggregation) within the available context; the wiki/code index used here does not include the full `composer.js` signing-request composition logic, so the precise mechanics of how a stalled/attacker-controlled device would block a spend could not be verified end-to-end in this session. A Devin session with full repository access would allow tracing `composer.composeAuthorsAndMciForAddresses` and the signing-collection loop to confirm the exact freezing mechanism.

function determineIfIncludesMeAndRewriteDeviceAddress(assocSignersByPath, handleResult){
	var assocMemberAddresses = {};
	var bHasMyDeviceAddress = false;
	for (var signing_path in assocSignersByPath){
		var signerInfo = assocSignersByPath[signing_path];
		if (signerInfo.device_address === device.getMyDeviceAddress())
			bHasMyDeviceAddress = true;
		if (signerInfo.address)
			assocMemberAddresses[signerInfo.address] = true;
	}
	var arrMemberAddresses = Object.keys(assocMemberAddresses);
	if (arrMemberAddresses.length === 0)
		return handleResult("no member addresses?");
	db.query(
		"SELECT address, 'my' AS type FROM my_addresses WHERE address IN(?) \n\
		UNION \n\
		SELECT shared_address AS address, 'shared' AS type FROM shared_addresses WHERE shared_address IN(?)", 
		[arrMemberAddresses, arrMemberAddresses],
		function(rows){
		//	handleResult(rows.length === arrMyMemberAddresses.length ? null : "Some of my member addresses not found");
			if (rows.length === 0)
				return handleResult("I am not a member of this shared address");
			var arrMyMemberAddresses = rows.filter(function(row){ return (row.type === 'my'); }).map(function(row){ return row.address; });
			// rewrite device address for my addresses
			if (!bHasMyDeviceAddress){
				for (var signing_path in assocSignersByPath){
					var signerInfo = assocSignersByPath[signing_path];
					if (signerInfo.address && arrMyMemberAddresses.indexOf(signerInfo.address) >= 0)
						signerInfo.device_address = device.getMyDeviceAddress();
				}
			}
			handleResult();
		}
	);
}

function handleNewSharedAddress(body, callbacks){
	if (!ValidationUtils.isArrayOfLength(body.definition, 2))
		return callbacks.ifError("invalid definition");
	if (typeof body.signers !== "object" || Object.keys(body.signers).length === 0)
		return callbacks.ifError("invalid signers");
	try {
		var addr = objectHash.getChash160(body.definition);
	}
	catch (e) {
		return callbacks.ifError("invalid definition: " + e);
	}
	if (body.address !== addr)
		return callbacks.ifError("definition doesn't match its c-hash");
	for (var signing_path in body.signers){
		var signerInfo = body.signers[signing_path];
		if (signerInfo.address && signerInfo.address !== 'secret' && !ValidationUtils.isValidAddress(signerInfo.address))
			return callbacks.ifError("invalid member address: " + JSON.stringify(signerInfo.address));
	}
	const assocDefinitionAddresses = extractAddressPathsFromDefinition(body.definition);
	for (let signing_path in body.signers) {
		const signerInfo = body.signers[signing_path];
		if (assocDefinitionAddresses[signing_path] !== signerInfo.address)
			return callbacks.ifError("signer address at path " + signing_path + " doesn't match definition");
	}
	for (let def_path in assocDefinitionAddresses) {
		if (!body.signers[def_path])
			return callbacks.ifError("no signer for definition address at path " + def_path);
	}

	conn = conn || db;

			if (rows.length === 0)

				handleLists(_.union(arrControlAddresses, arrControlAddresses2), _.union(arrControlDeviceAddresses, arrControlDeviceAddresses2));
			});
		}
	);
}
