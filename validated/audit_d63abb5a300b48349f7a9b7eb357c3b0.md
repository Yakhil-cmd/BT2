### Title
Cross-Organization Webhook Forgery via Per-Organization Optional `webhook_secret` — Unscoped Status Injection — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and thus which `webhook_secret`) to verify a request against based on an attacker-controlled field in the unverified JSON body, while the handlers that act on the payload use a *different* attacker-controlled field to decide what resource is mutated. Combined with the fact that `webhook_secret` is optional per-organization and its absence makes verification a no-op, this lets anyone who knows of (or controls) one configured GitHub organization with no webhook secret forge a signature that Shipit accepts, then use the payload to act on data belonging to a completely different, unrelated organization/repository — breaking the "organization authenticated" vs. "repository/resource written" binding called out in the rules.

### Finding Description
`verify_signature` picks the app/secret to check against using only the requester-supplied `repository.owner.login` (or `organization.login`) field: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` trivially returns `true` when no `webhook_secret` is configured for that organization: [3](#0-2) 

Shipit explicitly documents `webhook_secret` as **optional** per organization, and its multi-org config format keys an entire GitHub App configuration off an organization name taken straight from the payload: [4](#0-3) [5](#0-4) [6](#0-5) 

Meanwhile, the actual side effects executed by `create` are dispatched to handlers that key off a *separate* attacker-controlled field, `repository.full_name`, or in the case of `StatusHandler`, off no repository scoping at all: [7](#0-6) [8](#0-7) [9](#0-8) 

Because `repository.owner.login` (used to pick the secret) and `repository.full_name` (used by handlers, e.g. to locate the `Repository`/`Stack`) are independently attacker-controlled fields inside the same forged JSON body, they need not agree. `StatusHandler` is the worst case: it doesn't even consult `repository.full_name` — it matches `Commit.where(sha: params.sha)` **globally across the entire installation**, so once *any* signature check passes (via any zero-secret org), a `state`/`context` status can be injected onto a commit belonging to any other, unrelated, fully-secured repository/organization.

This is the direct structural analog of the reported bug class: the value that is cryptographically bound/verified (organization tied to the accepted `X-Hub-Signature`) is not the same value that downstream code actually consumes and acts on (repository/commit written to). In the UMA report, the reward retrieved by `LongShortPairCreator` was disconnected from the recipient actually paid by the Optimistic Oracle; here, the organization whose signature is checked is disconnected from the repository/commit whose state is mutated.

### Impact Explanation
An unprivileged attacker (no Shipit session, no GitHub write access to the target repo, no knowledge of the target org's `webhook_secret`) who is aware of any single Shipit-configured GitHub organization with no `webhook_secret` set (an explicitly supported, documented configuration) can:
- Forge a valid-looking webhook whose `repository.owner.login`/`organization.login` is that no-secret org (passing `verify_signature` trivially), and
- Set `params.sha`/`state`/`context` (StatusHandler) or `repository.full_name` (other handlers) to point at commits/repositories belonging to a completely different, secured organization.

This allows unauthenticated read/mutation of stack state that should require an authenticated GitHub webhook: injecting fake "success" CI statuses onto arbitrary commits system-wide, which Shipit uses to gate merges/deploys, can facilitate an unauthorized deploy or merge decision downstream. This falls under the High-impact category ("escalation into authorization... unauthorized deploy, rollback or merge" adjacent effects via forged trust signal), given `StatusHandler`'s complete lack of repository scoping combined with the optional-secret design.

### Likelihood Explanation
Requires only that at least one org in the deployment's `secrets.github` multi-org map has no `webhook_secret` configured — an explicitly documented, supported configuration (`docs/setup.md` marks it "optional") — and that the attacker knows the name of that organization (visible from the Shipit UI/stack list, which is unauthenticated-readable metadata in many installs). No secret, token, or repository write access is needed; a single crafted HTTP POST to the public `/webhooks` endpoint suffices.

### Recommendation
Bind the signature-verification identity to the same identity the handler actually acts upon: verify the signature using the secret for the organization/repository that will be mutated (derived from `repository.full_name`'s owner, consistently), not a separately-trusted field. Additionally, `StatusHandler` should validate that the resolved `Commit`'s stack/repository matches the organization whose signature was verified, rather than matching purely by `sha` across the whole installation. Consider also requiring `webhook_secret` to be mandatory for all configured GitHub Apps to remove the "verification always true" fallback path.

### Proof of Concept
1. Shipit is configured with `secrets.github` containing two orgs, e.g. `AttackerOrg` (no `webhook_secret`, as allowed by `docs/setup.md`) and `VictimOrg` (has a real `webhook_secret`), matching the multi-org format shown at `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-commit-sha-belonging-to-VictimOrg-repo>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "AttackerOrg" } }
}
```
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and `verify_webhook_signature` returns `true` immediately because `AttackerOrg`'s `webhook_secret` is blank (`lib/shipit/github_app.rb:76-83`), regardless of the (missing/garbage) `X-Hub-Signature`.
4. `WebhooksController#create` dispatches to `StatusHandler`, which runs `Commit.where(sha: params.sha).each { |c| c.create_status_from_github!(params) }` — matching purely by `sha`, with zero regard to `AttackerOrg` vs the commit's real owning repository (`VictimOrg`) — creating a forged "success" status on a commit the attacker never had signature-verified access to.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
