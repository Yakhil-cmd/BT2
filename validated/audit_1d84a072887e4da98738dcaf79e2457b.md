### Title
Unhandled `throw Error(...)` inside async DB callbacks during AA trigger execution crashes the entire node - ([File: aa_composer.js])

### Summary
CVE-2022-37428 describes PowerDNS Recursor crashing (DoS) because an exception thrown while processing an attacker-influenced answer/query was not properly caught/cleaned up ("Improper Cleanup upon a Thrown Exception"). The same bug class exists in `ocore`'s Autonomous Agent (AA) trigger execution path: numerous invariant checks inside `aa_composer.js` are implemented as synchronous `throw Error(...)` statements nested deep inside asynchronous DB-query callbacks, rather than being routed through the `cb`/`bounce` error-handling flow used elsewhere in the same functions. Because these throws occur inside Node.js callback frames (not the original call stack), they cannot be caught by any surrounding `try/catch`, and they propagate to the process-level `uncaughtException` handler in `network.js`, which deliberately re-throws to **crash the whole process**.

### Finding Description
`handlePrimaryAATrigger` and `handleTrigger` in `aa_composer.js` process a trigger unit that any unprivileged user can post (any payment to an AA address, or any AA-to-AA secondary trigger). Along this path there are several `throw Error(...)` calls that are reachable with attacker-influenced state/timing rather than being pure "impossible" invariants:

- [1](#0-0)  — `if (!objUnitProps) throw Error(...)` inside a DB callback after AA execution completes.
- [2](#0-1)  — `if (arrDefinition[0] !== 'autonomous agent') throw Error('bad AA definition ' + arrDefinition);` executed synchronously inside `handleTrigger`, which itself can be invoked from a DB-read callback (`storage.readAADefinition(...)` callback at line 436-443) for the `base_aa` redirection path.
- [3](#0-2)  — the "base AA not found" throw and the recursive `handleTrigger` call happen inside a `storage.readAADefinition` callback, i.e., outside the synchronous call stack of the caller.
- [4](#0-3)  — `if (rows.length === 0) throw Error("AA not found? " + address);` inside a nested `conn.query` callback in `updateInitialAABalances`.
- [5](#0-4)  — `if (!Array.isArray(args)) throw Error("args is not an array");` inside `callGetter`, itself invoked from formula evaluation triggered by an AA's oscript that calls a remote getter — reachable from a crafted AA definition combined with a crafted trigger/params.

All of these are executed while a live DB transaction/connection (`conn`) and a KV `batch` are open (`BEGIN` was issued at [6](#0-5)  and [7](#0-6) ). When the throw escapes, the transaction is never rolled back and the connection is never released — an "improper cleanup upon a thrown exception," mirroring the CVE's bug class exactly.

Any such throw is caught only by the global handler: [8](#0-7)  which logs the error and then does `throw err; // crash the process to avoid ending up in an inconsistent state`. This is a deliberate acknowledgment by the developers that thrown exceptions during unit/trigger processing leave the DB/kvstore in an inconsistent state, so the *only* safe action left is to kill the whole process.

The `network.js` dry-run mechanism at [9](#0-8)  explicitly documents this risk in its own comment: *"if it would crash, let it crash now, not when we execute the trigger for real"* — confirming that trigger execution is known to be able to crash the process, and the dry-run is only a best-effort, opt-in (`conf.bDryRunNewTriggers`) mitigation that does not eliminate the underlying issue for secondary/base-AA triggers, getter calls, or nodes that don't enable this flag.

### Impact Explanation
Any of these code paths, when hit by a crafted primary trigger, secondary (AA-to-AA) trigger, or a getter call chain, throws inside an async callback and is not caught anywhere except the global "crash the process" handler. This means a single, unprivileged unit-poster/AA-trigger sender can remotely crash an arbitrary full node (or hub) that processes their trigger — a full node-wide denial of service. Because the throw happens mid-transaction, it also leaves an open DB transaction/kvstore batch, so even if the process were restarted without crashing, the state could be left inconsistent (the crash-on-throw design is precisely there to avoid persisting that inconsistency, at the cost of full DoS). This matches "a network unable to confirm new units" if enough nodes are running with the vulnerable configuration and are targeted with the same crafted trigger.

### Likelihood Explanation
Reaching some of these specific throws (e.g., `"bad AA definition"`, `"base AA not found"`, `"AA not found?"`, `callGetter`'s `"args is not an array"`) requires a combination of a crafted AA definition (an unprivileged AA author action) plus a triggering unit designed to hit the exact edge case (e.g., racing an AA definition being redefined/removed between read and use, or a `base_aa` pointing to an address whose definition changes between the two DB reads at lines 436 and 531). This is a data race/edge-case condition rather than a trivially one-shot exploit, so likelihood is Medium rather than High — it requires careful crafting and possibly favorable timing, but is realistically triggerable by a determined AA author/trigger sender without any special privilege.

### Recommendation
Replace all `throw Error(...)` invariant checks inside asynchronous DB callbacks in `aa_composer.js` (and the analogous ones in `formula/evaluation.js`'s `callGetter`) with proper error propagation through the existing `cb`/`bounce`/`onDone(err)` callback chains, so that trigger processing failures are treated as recoverable validation/execution errors (bouncing the AA, rejecting the trigger) rather than uncaught exceptions that require killing the whole process. Where an inconsistent DB/kvstore state is truly unrecoverable, explicitly roll back the transaction and release the connection before deciding whether to crash, rather than relying solely on the global `uncaughtException` handler.

### Proof of Concept
1. Deploy an AA definition `A` with `base_aa` pointing to an address `B`.
2. Have `B`'s definition become unresolvable at the moment `handleTrigger`'s `storage.readAADefinition(conn, template.base_aa, mci, ...)` callback fires (e.g., by structuring a chain of AA redefinitions/removals so that between MCI stabilization and trigger processing, `readAADefinition` returns `null` for `B` at that specific mci) — triggers `throw Error("base AA not found: " + template.base_aa)` at [10](#0-9)  inside the DB-read callback, uncaught by any `try/catch`, propagating to `process.on('uncaughtException')` in `network.js` and crashing the node.
3. Alternatively, craft an AA whose oscript calls a remote getter (`$aa#getter(...)`) with a non-array `args` (achievable via a bug in the `fargs`/`getArgs` builder combined with a crafted `map`/`filter`/`reduce` construct feeding a non-array into `callGetter`), triggering the `throw Error("args is not an array")` in [5](#0-4) , again inside an async DB-read callback, crashing the node the same way.

*Note: exact reachability of the specific race conditions for triggering `"base AA not found"` and the `callGetter` `args` check could not be fully confirmed from static reading alone — a Devin session with full repo/test access would be needed to construct a working end-to-end unit test that reliably reproduces the crash timing.*
