### Title
Reuse of a single non-expiring "permanent" pairing secret shared with every arbiter-contract counterparty and arbstore enables unauthorized device pairing - (File: `arbiter_contract.js`, `device.js`)

### Summary
`jupyterhub-systemdspawner`'s flaw (GHSA-cg54-gpgr-4rm6) was that a credential meant to authenticate a single principal (a user's API token) was instead placed somewhere readable by every other party on the same host, letting unrelated users reuse it. The analogous defect in `ocore` is that `arbiter_contract.js` reuses the wallet's single **permanent** device-pairing secret — instead of a one-time pairing secret — and hands it out to every contract counterparty and to the arbstore HTTP endpoint, so any of those unrelated third parties can later use that same secret to pair with the victim's device at will.

### Finding Description
Normal wallet-to-wallet pairing uses a single-use secret generated by `startWaitingForPairing()` that is deleted immediately after one peer consumes it via `handlePairingMessage()`: [1](#0-0) 

By contrast, `arbiter_contract.js` obtains and reuses the same **permanent** pairing secret (`is_permanent=1`, expiry year 2038) via `getOrGeneratePermanentPairingInfo()`: [2](#0-1) 

This permanent code is transmitted, in cleartext form (`pubkey@hub#secret`), to:
- every counterparty when a contract is created: [3](#0-2) 
- every counterparty again when responding/accepting a contract: [4](#0-3) 
- the external arbstore HTTP server when opening a dispute: [5](#0-4) 
- the arbstore HTTP server again when appealing: [6](#0-5) 

Because `handlePairingMessage()` never deletes a permanent pairing-secret record (deletion is skipped when `is_permanent === 1`), it never expires from use and remains valid for **any number of future pairing attempts by any holder**, unlike a one-time secret: [7](#0-6) 

The result: the same long-lived credential that authorizes indefinite device pairing is disclosed to every past contract counterparty and every arbstore server the wallet has ever interacted with, exactly the CWE-668 pattern in the report — a secret intended to authenticate one narrow, time-boxed interaction is exposed to a broad set of unrelated principals who can reuse it far outside the original context.

### Impact Explanation
Any prior arbiter-contract counterparty or any arbstore operator who retains the leaked `my_pairing_code` can call `handlePairingMessage()` at any later time to add themselves as a confirmed correspondent device (`is_confirmed=1`) of the victim's wallet: [8](#0-7) 

Once paired as a trusted correspondent, that party can send further device messages that the wallet processes as coming from a legitimate paired peer — e.g. `text`, `object`, arbiter-contract offers, shared-address invitations, and other correspondent-trust-gated flows handled in `handleMessageFromHub()`: [9](#0-8) 

This can be leveraged for social-engineering/phishing style attacks (spoofed arbiter contracts, spoofed shared-address invitations, spoofed textcoin/private-payment chains) against a device that never intended to grant this counterparty renewed, standing pairing access. This is a Medium-severity confidentiality/authenticity issue: it doesn't directly move funds, but it expands the attack surface for follow-on social-engineering-driven fund loss (e.g. tricking the user into a fraudulent shared-address wallet or accepting a forged arbiter contract), reachable purely by any past private-payment/arbiter-contract counterparty.

### Likelihood Explanation
Likelihood is moderate: exploitation requires having been a legitimate counterparty in at least one prior arbiter contract with the victim (or being/compromising an arbstore endpoint), which is easily achievable for any unprivileged actor by simply proposing a contract via `createAndSend()`. No cryptographic break or race condition is needed — the secret is handed over voluntarily by the vulnerable code path itself.

### Recommendation
- Use a fresh, single-use pairing secret (as `startWaitingForPairing()` does) for each arbiter-contract exchange and for arbstore dispute/appeal submissions, rather than reusing the account-wide permanent pairing secret.
- If a permanent secret must be shared with arbstore/counterparties for identification purposes, do not use it as a live pairing credential — use a non-reusable, purpose-scoped token instead, and rotate/invalidate it after the contract session concludes.
- Consider adding an application-level need for prior explicit user confirmation before device-messages from a newly (re)paired correspondent are surfaced/trusted for sensitive actions (shared-address setup, arbiter contracts, private payments).

### Proof of Concept
1. Alice's wallet calls `arbiter_contract.createAndSend()` to propose a contract to Bob; the message includes `my_pairing_code = devicePubkey@hub#<permanent_secret>` (`arbiter_contract.js:26`).
2. Bob stores this code (he is not required to use it immediately, and the contract can be declined/expired/completed).
3. Months later, Bob (or anyone Bob shared the code with) sends a `pairing` message to Alice's hub using the same `pairing_secret`. Because the secret's `is_permanent` flag is `1`, `handlePairingMessage()` accepts it and adds Bob as a confirmed correspondent (`device.js:816-841`), without ever having expired or been consumed.
4. Bob can now send arbitrary device messages (e.g. a forged arbiter contract offer, a shared-address invitation) that Alice's wallet processes as coming from a re-established, trusted correspondent — enabling downstream social-engineering-based fund-loss attacks that would not otherwise be possible without an active pairing relationship.
