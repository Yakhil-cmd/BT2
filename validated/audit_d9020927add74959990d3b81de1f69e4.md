### Title
Fee-on-Transfer Token Discrepancy in `BridgeTransferERC20::requestERC20Transfer` Causes Bridge Insolvency or DoS — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

---

### Summary

`BridgeTransferERC20::requestERC20Transfer` pulls `_value + _feeLimit` tokens from the caller via `safeTransferFrom`, then immediately passes the original `_value` and `_feeLimit` to `_requestERC20Transfer` without measuring the actual amount received. For fee-on-transfer tokens, the bridge receives `_value + _feeLimit - transferFee`, but the emitted `RequestValueTransfer` event records `_value` (the full nominal amount). This causes either a permanent DoS (`modeMintBurn = true`) or bridge insolvency (`modeMintBurn = false`).

---

### Finding Description

In `requestERC20Transfer`:

```solidity
// BridgeTransferERC20.sol line 133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
``` [1](#0-0) 

The bridge pulls `_value + _feeLimit` tokens. For a fee-on-transfer token with per-transfer fee `F`, the bridge actually receives `_value + _feeLimit - F`. The original `_value` and `_feeLimit` are then forwarded unchanged to `_requestERC20Transfer`.

Inside `_requestERC20Transfer`, `_payERC20FeeAndRefundChange` is called, which itself issues additional `safeTransfer` calls to `feeReceiver` and back to `from`:

```solidity
// BridgeFee.sol lines 74, 78, 85
IERC20(_token).safeTransfer(feeReceiver, fee);
IERC20(_token).safeTransfer(from, feeRefund);
// or
IERC20(_token).safeTransfer(from, _feeLimit);
``` [2](#0-1) 

Each of these transfers also incurs the fee-on-transfer, further draining the bridge's balance. After all fee/refund transfers, the bridge holds exactly `_value - F` tokens (where `F` is the per-transfer fee).

Then, in `modeMintBurn = true` mode:

```solidity
// BridgeTransferERC20.sol line 94
ERC20Burnable(_tokenAddress).burn(_value);
``` [3](#0-2) 

The bridge attempts to burn `_value` tokens but only holds `_value - F`. This **always reverts**, permanently DoS-ing `requestERC20Transfer` for any fee-on-transfer token in mint-burn mode.

In `modeMintBurn = false` mode, the burn is skipped and the event is emitted:

```solidity
// BridgeTransferERC20.sol lines 97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from, _to, _tokenAddress,
    _value,   // <-- nominal amount, not actual received
    requestNonce, fee, _extraData
);
``` [4](#0-3) 

The counterpart chain operators observe this event and call `handleERC20Transfer` with `_value`:

```solidity
// BridgeTransferERC20.sol line 71
IERC20(_tokenAddress).safeTransfer(_to, _value);
``` [5](#0-4) 

The destination chain transfers or mints the full `_value` to the recipient, while the source chain bridge only locked `_value - F`. Each cross-chain transfer of a fee-on-transfer token creates a deficit of `F` tokens on the source chain bridge, accumulating into insolvency.

The same flaw exists in the 1-step path via `onERC20Received`, which also passes the caller-supplied `_value` directly to `_requestERC20Transfer` without measuring the actual balance delta:

```solidity
// BridgeTransferERC20.sol line 120
_requestERC20Transfer(msg.sender, _from, _to, _value, _feeLimit, _extraData);
``` [6](#0-5) 

---

### Impact Explanation

- **`modeMintBurn = true`**: Every `requestERC20Transfer` call with a fee-on-transfer token reverts at `burn(_value)` because the bridge holds `_value - F < _value`. Complete DoS for that token.
- **`modeMintBurn = false`**: The source chain bridge accumulates a deficit of `F` tokens per transfer. The destination chain mints/unlocks the full `_value` each time. Over N transfers, the source chain bridge is short `N * F` tokens. When users attempt to bridge back, the source chain bridge cannot fulfill withdrawals — unauthorized net mint of bridged assets on the destination chain.
- **Fee payment corruption**: `_payERC20FeeAndRefundChange` transfers `fee` to `feeReceiver` and `feeRefund` to the user, but each transfer incurs the fee-on-transfer, so both parties receive less than the configured amounts, and the bridge's balance is drained by more than intended.

---

### Likelihood Explanation

The bridge's `registerToken` function imposes no restriction on token type — any ERC20 can be registered. A fee-on-transfer token registered by the bridge owner (or already registered) is sufficient to trigger this. The caller of `requestERC20Transfer` is any user with a token balance and approval. No privileged access is required to trigger the insolvency path.

---

### Recommendation

Measure the actual balance delta after `safeTransferFrom` and use that as the effective deposit amount, analogous to the THORChain mitigation:

```solidity
function requestERC20Transfer(
    address _tokenAddress,
    address _to,
    uint256 _value,
    uint256 _feeLimit,
    bytes memory _extraData
) public {
    uint256 balBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balBefore);
    // Derive actual _value and _feeLimit from actualReceived, or revert if insufficient
    require(actualReceived >= _value.add(_feeLimit), "fee-on-transfer token: insufficient received");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Similarly, `_payERC20FeeAndRefundChange` should measure balance deltas for each outbound transfer if fee-on-transfer tokens are to be supported.

---

### Proof of Concept

1. Deploy a fee-on-transfer ERC20 token (1 token fee per transfer) and register it on the bridge with `modeMintBurn = false`.
2. Alice calls `requestERC20Transfer(token, bob, 100, 10, "")`.
3. `safeTransferFrom(alice, bridge, 110)` → bridge receives 109 (fee = 1).
4. `_payERC20FeeAndRefundChange` with `_feeLimit = 10`, bridge fee = 5:
   - `safeTransfer(feeReceiver, 5)` → feeReceiver gets 4, bridge loses 5.
   - `safeTransfer(alice, 5)` → alice gets 4, bridge loses 5.
   - Bridge balance: 109 - 5 - 5 = 99.
5. `emit RequestValueTransfer(..., _value=100, ...)`.
6. Counterpart chain operators call `handleERC20Transfer(..., _value=100, ...)` → recipient gets 100 tokens minted/transferred.
7. Source chain bridge holds 99 tokens but has outstanding obligation of 100. Deficit = 1 token per transfer.
8. After 100 such transfers, bridge is short 100 tokens and cannot fulfill reverse withdrawals. [7](#0-6) [2](#0-1)

    function _payERC20FeeAndRefundChange(address from, address _token, uint256 _feeLimit) internal returns(uint256) {
        uint256 fee = feeOfERC20[_token];

        if (feeReceiver != address(0) && fee > 0) {
            require(_feeLimit >= fee, "insufficient feeLimit");

            IERC20(_token).safeTransfer(feeReceiver, fee);

            uint256 feeRefund = _feeLimit.sub(fee);
            if (feeRefund > 0) {
                IERC20(_token).safeTransfer(from, feeRefund);
            }

            return fee;
        }

        if (_feeLimit > 0) {
            IERC20(_token).safeTransfer(from, _feeLimit);
        }
        return 0;
    }
