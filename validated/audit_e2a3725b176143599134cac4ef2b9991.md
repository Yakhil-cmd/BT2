### Title
Cross-repository commit-status forgery via webhook signature/organization binding bypass enabling unauthorized deploy - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check verifies that a request is signed for *one* GitHub organization, but the `status` event handler writes a commit status to *any* commit in the database by SHA alone, with no check that the commit belongs to a repository owned by the authenticated organization.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/secret to use for HMAC verification based on `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`) field: `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 

Crucially, `GitHubApp#verify_webhook_signature` unconditionally trusts the request if that organization's `webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 

The secrets templates shipped in this repo explicitly show organizations configured with `webhook_secret: # nil`, i.e. no secret at all — a documented/expected configuration. [4](#0-3) 

Once verification passes (either genuinely signed by a legitimately-configured org, or trivially bypassed via a blank-secret org), the controller dispatches the raw, attacker-controlled JSON body to all registered handlers for the event with no further binding to the authenticated organization: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`. [5](#0-4) 

`StatusHandler#process` then looks up commits **globally by SHA only** — `Commit.where(sha: params.sha)` — and writes a GitHub-reported CI status onto them, without any scoping to the organization that was authenticated for the request: [6](#0-5) 

This is the exact trust-binding break called out in the rules: "an organization that authenticated versus the repository that is written." The signature check authenticates *"this request came from org X"* (or nothing at all, if org X has no secret configured), but the mutation performed — writing a commit status — is applied to whatever commit SHA the attacker supplies, regardless of which repository/organization that commit actually belongs to. Commit SHAs are not secrets; they are public git object identifiers visible in any GitHub repository's history, PRs, or Shipit's own UI.

### Impact Explanation
Commit statuses directly gate deploy eligibility. Deploy safety checks (`deployable?` and related CI-status logic used by `deploy_steps`/lock/safety checks in `Stack`/`Commit`) rely on commit statuses reported via this exact webhook path. By forging a `status` event for a victim stack's pending commit (using an SHA copied from GitHub) while only needing to pass signature verification for *any* organization configured with a blank/no `webhook_secret` in the same Shipit instance, an attacker can mark an otherwise non-deployable commit as CI-green. This crosses into "an unauthorized deploy" — the impact category listed as Critical in the rules — because it can flip the exact status flag that determines whether continuous deployment or a human-triggered deploy is allowed to proceed for a repository/organization the attacker does not control and was never authenticated for.

### Likelihood Explanation
The `/webhooks` endpoint is unauthenticated by design (it's meant to be called by GitHub, not a logged-in user) and skips CSRF protection. The only gate is `verify_signature`, which is a no-op for any organization lacking a configured `webhook_secret` — a state explicitly present in this repo's own secrets templates. Even for organizations that do have a secret, an attacker only needs their own legitimate GitHub org (with its own genuinely-signed webhooks) hosted in the same multi-tenant Shipit instance to pass the signature gate, then supply an arbitrary victim SHA in the JSON body — the signature only covers the raw bytes for HMAC validity, it does not semantically bind the "repository" field to be internally consistent with what the handler actually reads (SHA only, no repo field checked in `StatusHandler`).

### Recommendation
Scope `StatusHandler#process` (and any handler that writes state from webhook payloads) so that the commit lookup is constrained to the repository/organization derived from the same field used for signature verification (`repository_owner`), e.g. join through `Repository`/`Stack` and reject/no-op if the commit's repository does not match the authenticated organization. Additionally, treat a missing/blank `webhook_secret` as a misconfiguration to warn against rather than a silent bypass, and ensure the "authenticated organization" field and the "target repository" field used downstream are the exact same value, never independently attacker-suppliable.

### Proof of Concept
1. Deploy Shipit configured for two organizations, e.g. `victim-org` (tracks stack `victim-org/victim-repo`) and `attacker-org` (attacker legitimately owns this org's GitHub App installation, or `attacker-org.webhook_secret` is left blank as shown in the shipped secrets template).
2. Attacker finds a real, currently-pending commit SHA in `victim-org/victim-repo` (visible on GitHub or in Shipit's own public stack page).
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim-repo-pending-sha>",
  "state": "success",
  "context": "ci/whatever",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
4. `verify_signature` resolves `repository_owner` to `attacker-org`, uses `attacker-org`'s (blank or attacker-known) secret, and passes.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit — and calls `create_status_from_github!`, marking it CI-green.
6. The victim stack's commit now reports a passing status it never legitimately received, potentially permitting an unauthorized/continuous deploy of that commit.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
