### Title
Race condition in parallel private-payment-chain processing bypasses double-spend serialization checks — ([File: network.js])

### Summary
`handleSavedPrivatePayments` in `network.js` processes multiple queued private-payment chains **in parallel** (`async.each`) rather than serially, and the resulting validate-and-save path in `private_payment.js` / `indivisible_asset.js` / `divisible_asset.js` opens an independent DB connection and transaction per chain with no cross-chain mutex keyed on the spent output or asset. The double-spend acceptance logic in `validation.js`'s `checkForDoublespends`/`checkInputDoubleSpend` relies on a SELECT-then-INSERT pattern inside each independent transaction, and for unstable private inputs the `inputs` table's uniqueness constraint is intentionally bypassed (`is_unique = bStable ? 1 : null`). Two conflicting private payment chains spending the *same* private output, submitted at nearly the same time by a private-payment counterparty, can be validated concurrently in separate connections before either commits, letting both pass the "no existing conflicting spend" check and be persisted as accepted spends of the same source output.

### Finding Description
`handleSavedPrivatePayments` explicitly comments "handle different chains in parallel": [1](#0-0) 

Each row is validated independently via `privatePayment.validateAndSavePrivatePaymentChain`, which opens its **own** connection/transaction per chain, with only a duplicate-output check against already-*stored* rows, not against other in-flight validations: [2](#0-1) 

The underlying double-spend check (`checkForDoublespends` → `checkInputDoubleSpend` in `validatePaymentInputsAndOutputs`) performs a `SELECT` for conflicting inputs and then an `INSERT`, all inside the per-chain transaction: [3](#0-2) [4](#0-3) 

Crucially, for unstable/private inputs the row is inserted with `is_unique = NULL` (via `is_unique = bStable ? 1 : null` in `indivisible_asset.js`/`divisible_asset.js`), which deliberately opts the row **out** of the `inputs` table's `UNIQUE KEY bySrcOutput` constraint (the schema comment explicitly says this key "guarantees there'll be no double spend for type=transfer" — but only when `is_unique` is non-NULL): [5](#0-4) [6](#0-5) 

Because uniqueness enforcement is disabled for unstable rows, the double-spend detection for concurrently-processed chains depends entirely on the application-level SELECT-before-INSERT check happening under mutual exclusion. Since `handleSavedPrivatePayments` runs the per-chain validation concurrently on separate DB connections/transactions (and the mutex protecting private writes, `["private_write"]`, is only acquired transiently inside `checkInputDoubleSpend`'s "accept doublespend" branch — not around the whole validate+insert sequence), two chains that each spend the same private output can both complete their SELECT (finding no conflicting row yet, since neither transaction has committed) before either INSERTs and commits. Both chains are then accepted as valid non-conflicting spends of the same source output.

### Impact Explanation
This allows a private-payment counterparty (or a malicious payer colluding with two different payees/cosigners) to get **both** conflicting spends of the same private output locally accepted by a wallet/hub as "OK", each recorded and forwarded to `eventBus` as `new_my_transactions` / `aa_response`-style confirmations to the respective recipients. This is a concrete double-spend/fund-loss risk for the counterparty who is told the payment succeeded, even though only one of the two conflicting private units can ultimately serialize as "good" once main-chain stability resolves the fork — and light wallets in particular have no DAG-graph fork-resolution capability (`if (conf.bLight) return cb2(...+"conflicting "+type)`), so they cannot correct their locally-persisted acceptance if the race already let both pass.

### Likelihood Explanation
Triggering the race requires only that the attacker (the payer, or an attacker controlling a private-payment counterparty relationship) submit two private payment chains spending the same output to two different recipients/cosigners within the same 5-second `handleSavedPrivatePayments` polling window, and rely on their processing landing in the same `async.each` batch — well within reach of a normal user of the private-payment/asset-transfer feature, no privileged access needed.

### Recommendation
Serialize private-payment chain validation and persistence per conflicting resource (e.g., mutex-lock on the source output/asset key, not just `["private_write"]` around a small sub-step) so that the SELECT-then-INSERT double-spend check and the final commit happen atomically with respect to other chains that could touch the same source output, instead of processing chains in parallel across independent connections.

### Proof of Concept
1. As a private-payment payer, construct two indivisible/divisible private-payment chains that both spend the same prior private output (`src_unit`/`src_message_index`/`src_output_index`) to two different recipient addresses.
2. Send chain A to recipient/hub 1 and chain B to recipient/hub 2 at nearly the same time so both land in `unhandled_private_payments` and are picked up together by the periodic `handleSavedPrivatePayments` timer.
3. Because `async.each` in `network.js:2459-2518` processes both rows concurrently, each opens its own connection/transaction via `private_payment.js:45`, and the `checkForDoublespends` SELECT (`validation.js:1662`) for each chain executes before the other's INSERT commits — both chains are validated as `ifOk` and both `INSERT INTO inputs ... is_unique=NULL` succeed (uniqueness not enforced for `is_unique=NULL`), so both recipients receive an "accepted" result for spending the same source output.
