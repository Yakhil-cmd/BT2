### Title
`X-Shipit-User` header lets any authenticated API client forge the `current_user` attributed to deploys, rollbacks, task triggers and locks - (File: `app/controllers/shipit/api/base_controller.rb`)

### Summary
`Shipit::Api::BaseController#identify_user` resolves `current_user` solely from the client-supplied `X-Shipit-User` header, with no binding to `current_api_client` or any session. `require_permission!` authorizes only `current_api_client`, never `current_user`, so any token holder with the operation permission (e.g. `deploy:stack`) can attribute the resulting `Deploy`, `Task`, `Rollback` or `Lock` to an arbitrary existing user login.

### Finding Description
The binding that should hold is `current_user == current_api_client.creator` (the actor recorded on a write must be the actor who actually authenticated), but the code allows `current_user == User.where('lower(login) = ?', request.headers['X-Shipit-User'])` for any arbitrary existing login, independent of `current_api_client`.

Path: `authenticate_api_client` (`app/controllers/shipit/api/base_controller.rb:48-61`) validates only the bearer token into `@current_api_client`. `current_user` (`base_controller.rb:65-67`) calls `identify_user` (`base_controller.rb:69-72`), which reads `request.headers['X-Shipit-User']` verbatim and looks up any `User` by login, with zero cross-check against `current_api_client.creator`, `current_api_client.stack_id`, or a session. `require_permission!` (`base_controller.rb:82-84`) only calls `current_api_client.check_permissions!(operation, scope)` - it never touches `current_user`.

`current_user` is then used to stamp attribution on privileged, permission-gated write endpoints:
- `Api::DeploysController#create` → `stack.trigger_deploy(commit, current_user, ...)` [1](#0-0) 
- `Api::RollbacksController#create` → `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [2](#0-1) 
- `Api::TasksController#trigger`/`#abort` → `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)` [3](#0-2) 
- `Api::LocksController#create`/`#update` → `stack.lock(params.reason, current_user)` [4](#0-3) 
- `Api::ReleaseStatusesController#create` → `deploy.report_healthy!/report_faulty!(user: current_user)` [5](#0-4) 
- `Api::MergeRequestsController#update` → `MergeRequest.request_merge!(stack, params[:id], current_user)` [6](#0-5) 

Exploit flow: attacker holds an `ApiClient` token with, e.g., the `deploy:stack` permission for their own scope (or a globally scoped token they legitimately have). They send `POST /api/stacks/:id/deploys` (or `/rollbacks`, `/tasks/:name/trigger`, `/locks`) with header `X-Shipit-User: victim-admin-login`, where a `User` row with that login exists. `require_permission!` passes because it checks only `current_api_client`; `identify_user` then resolves `current_user` to the victim's `User` record purely from the header, and the resulting `Deploy`/`Task`/`Rollback`/`Lock` row is persisted with `user_id`/`author`/`aborted_by`/`locked_by` set to the victim rather than the token owner. `verify_signature`, `GitHubApp#verify_webhook_signature`, `drop_unhandled_event`, `ExplicitParameters`, and `User#authorized?` are irrelevant here (none of these guard identify against header spoofing); `require_permission!` is the only authorization check, and it never validates `current_user`.

### Impact Explanation
Each request lets a token holder forge the identity attribution on a permission-gated, mutating write (deploy trigger, rollback trigger, task trigger, lock/unlock reason, abort, release status, merge request approval) against any repository/stack the token can reach. This is an authentication/attribution bypass: audit trails and any authorization or business logic keyed on `current_user`/`task.author`/`deploy.user` (e.g., "who locked/unlocked", "who approved the merge", notification/blame in deploy UI) is falsifiable by any client with write-level API access, not just the true actor. This matches the "authentication bypass (forged ... API token accepted)" / "unauthorized deploy, rollback" Critical bucket, since the recorded actor for a real deploy/rollback/lock is forgeable to any existing Shipit user, including admins, without their token or credentials. It is repeatable on every request against every stack the attacker's token has access to.

### Likelihood Explanation
Preconditions are low-cost for a party that already holds any API token with a matching write permission (`deploy:stack`, `lock:stack`, etc.) — the attacker does not need the victim's credentials, only the victim's login (a public GitHub username, typically discoverable). No Shipit or GitHub secret is required; the header is honored on every unauthenticated-identity API request. This is trivially and repeatably exploitable with a single crafted HTTP header on any already-permitted write call.

### Recommendation
Do not trust `X-Shipit-User` as an unauthenticated identity claim. Bind `current_user` to `current_api_client.creator` by default, and only allow the header to override identity when `current_api_client` is a trusted first-party/internal client (e.g., an explicit `trusted: true` flag on `ApiClient`), or require the header value to be cryptographically tied to the request (e.g., signed, or restricted to clients whose creator has the `sudo` / admin authorization to impersonate). At minimum, validate that the resolved user is authorized on the same scope as `current_api_client`, and reject silently-successful lookups of arbitrary logins.

### Proof of Concept
```ruby
# test/controllers/api/deploys_controller_test.rb (new test)
test "#create attributes the deploy to the token owner, not an arbitrary X-Shipit-User header" do
  attacker_client = shipit_api_clients(:cyclimse) # token scoped with deploy:stack permission only
  victim = shipit_users(:walrus) # exists, distinct from attacker's identity
  authenticate!(attacker_client)
  request.headers['X-Shipit-User'] = victim.login

  post :create, params: { stack_id: @stack.to_param, sha: @stack.commits.last.sha }

  deploy = Deploy.last
  # Broken binding demonstrated: current_user (attributed) != actual authenticated actor
  assert_equal victim.id, deploy.user_id # currently passes -> proves spoofing
  refute_equal attacker_client.creator&.id, deploy.user_id
end
```
This demonstrates that `deploy.user_id` (or `task.user_id`, `stack.lock_reason`'s associated actor, etc.) is set from the forged `X-Shipit-User` header rather than from the identity that actually authenticated via `current_api_client`, confirming the broken `current_user == current_api_client.creator` binding.
