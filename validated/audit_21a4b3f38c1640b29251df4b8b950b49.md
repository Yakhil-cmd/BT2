### Title
Cross-Organization Commit Status Forgery via Webhook Signature/Repository Binding Mismatch - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate a payload against using `repository_owner`, taken from the payload itself. That value is never re-checked against the field that actually determines *what gets written* by the event handler. For the `status` event, `StatusHandler#process` looks up commits purely by `sha` — a value that is global across every repository/stack tracked by the Shipit instance — and writes a `CommitStatus` to whatever commit matches, with no scoping to the organization/repository whose secret produced the signature.

### Finding Description
Signature verification and target-selection use two different, attacker-controlled fields from the same signed payload:

- Verification selects the app/secret by `repository_owner`: [1](#0-0) [2](#0-1) 

- Shipit supports multiple GitHub organizations, each with its own independent `webhook_secret`, looked up by the organization name: [3](#0-2) 

- The `status` event handler, however, never consults `repository_owner`, `repository.full_name`, or any org/repo scoping at all. It resolves target commits purely by SHA, which is unique per-commit but not scoped to any particular stack or repository record within Shipit's database: [4](#0-3) 

Because HMAC verification only proves "this payload was signed with organization X's webhook secret" — it says nothing about which repository's data the payload is permitted to mutate — an attacker who legitimately administers their own GitHub App installation/org (call it org A, which they are free to install on the shared Shipit instance and thus knows org A's `webhook_secret`) can craft a `status` webhook body with:
- `repository.owner.login` (and/or `organization.login`) = `"org-A"` → passes signature verification using org A's secret.
- `sha` = the SHA of a commit belonging to a completely unrelated stack/repository (`org-B/victim-repo`) that they don't own or control.

The controller verifies the signature successfully (org A's secret matches), then `StatusHandler` writes a fabricated `CommitStatus` (state, context, target_url, description all attacker-controlled) onto the victim commit, regardless of which organization actually owns that commit.

The general `Handler#repository_name`/`stacks` scoping used by other handlers (`push`, `pull_request`, etc.) at least filters by `repository.full_name`: [5](#0-4) 
but `StatusHandler` bypasses this scoping entirely, and even where `repository_name`-based scoping is used elsewhere, that field is still just another attacker-controlled part of the same signed payload that verification never binds to the authenticating organization — it only proves *a* secret matched, not *whose* repository is being targeted.

### Impact Explanation
Commit statuses drive Shipit's deployability checks (`deployable_status`) and required-check gating used to decide whether a commit is safe to deploy. By forging a `success` status with a `context` that a victim stack's deploy pipeline treats as a required CI check, an unrelated, unprivileged organization operator can make an undeployed/unvetted commit in someone else's repository appear deployable, or forge a `failure`/`error` status to block deploys — a cross-repository write with potential to enable an unauthorized deploy. This satisfies the "cross-repository writes" / "unauthorized deploy" Critical impact class.

### Likelihood Explanation
Any organization that has installed its own GitHub App on the shared Shipit instance (a normal, low-privilege, self-service action supported by Shipit's multi-tenant `github` config) can trivially compute a valid HMAC using its own `webhook_secret` and POST a payload whose `owner.login`/`organization.login` matches its own org while the `sha` field references a commit in a victim's repository. No access to the victim's secret, `GITHUB_TOKEN`, or any Shipit session/API token is required.

### Recommendation
Bind the verified organization to the actual write target instead of trusting attacker-controlled `sha`/`repository.full_name` fields in isolation:
- In `StatusHandler` (and any other handler), resolve the target commit only within stacks belonging to the repository that was cryptographically verified (i.e., join through `Repository`/`Stack` scoped by the same `repository_owner`/organization used in `verify_signature`), not by a bare `Commit.where(sha:)` lookup.
- More generally, have `WebhooksController#verify_signature` compare the verified organization against the repository/organization actually referenced by the event payload before dispatch, rejecting mismatches.

### Proof of Concept
1. Attacker registers/installs their own GitHub App for `org-A` on the shared Shipit instance and obtains `org-A`'s `webhook_secret` (this is expected/legitimate for an org that self-onboards).
2. Attacker finds the SHA of a commit belonging to `org-B/victim-repo`'s tracked stack (SHAs are public via GitHub).
3. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, a body such as:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "org-A" }, "full_name": "org-A/attacker-repo" }
}
```
signed with `org-A`'s `webhook_secret` via `X-Hub-Signature`.
4. `verify_signature` calls `Shipit.github(organization: "org-A")` and successfully verifies the signature against `org-A`'s secret.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unrelated to `org-A`), and calls `create_status_from_github!`, writing a forged status onto `org-B`'s commit.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
