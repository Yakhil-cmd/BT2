### Title
Insufficient Validation Enables AMM Price Manipulation via Repeated Rounding-Favorable Trades - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The reference constant-product market-maker AA pattern shipped in ocore computes swap outputs using `round()` on a constant-product invariant without any slippage/minimum-output check, fee, or per-trade size limit. This mirrors the FIL314 root cause: a state-changing pricing function (`hourBurn`/`getAmountOut`) that can be invoked repeatedly with no bound, letting an attacker skew the internal ratio through many self-serving calls and then extract value at the distorted price.

### Finding Description
The AA's swap branches compute the new pool balance from the constant product and take the difference as the payout, with no enforced minimum-received parameter and no fee subtracted: [1](#0-0) [2](#0-1) 

Both directions rely purely on `round($p / balance[...])` to determine the counterparty's payout, and the comment even acknowledges fees are optional ("we can deduct exchange fees here"). Because:
1. There is no minimum-output ("slippage") parameter the trigger sender must satisfy, a sender fully controls the trade size and can choose amounts that repeatedly land on favorable rounding boundaries.
2. There is no per-trigger or per-block cap on how many times the swap branches can be invoked by the same address before another market participant can react (analogous to `hourBurn` being callable 6000 times atomically in the FIL314 PoC), an attacker can chain many small round-trip trades (asset→base→asset...) in successive triggers, each time capturing a `round()`-induced rounding surplus, cumulatively draining `balance[base]`/`balance[$asset]` from the pool without ever taking a directional price risk — the same "insufficient validation → price manipulation → extraction" pattern as the FIL314 `hourBurn`/`getAmountOut` loop.
3. The "invest"/"divest" branches likewise depend on `balance[$asset]`/`balance[base]` computed from the *pre-trigger* balance and offer no protection against a single large trigger moving `$current_ratio` before the same or a colluding address issues the next trigger to divest at the now-skewed ratio.

### Impact Explanation
An attacker (an unprivileged AA trigger sender, exactly the reachable actor class in scope) can, with no special privilege, submit a sequence of ordinary payment-triggering units to progressively skew the pool's internal balance ratio and extract more base/asset tokens than they deposited, at the expense of other liquidity providers. This is a concrete AA fund-loss/drain scenario reachable purely by posting units — medium/high severity depending on pool size and rounding granularity.

### Likelihood Explanation
Likelihood is high for any AA deployed from this pattern (or a derivative) without added slippage guards or fees: the exploit requires only the ability to send arbitrary trigger units with chosen output amounts, which any address can do. No node collusion, leaked keys, or privileged role is required — matching the FIL314 attacker profile of a normal on-chain caller repeatedly invoking a public, unguarded pricing function.

### Recommendation
- Require callers to supply a minimum acceptable output (slippage bound) and bounce if `$amount` (or `$issue_amount`) falls short.
- Charge a swap fee subtracted from `$p` before computing the counter-balance so that round-trip trades are guaranteed to be loss-making, eliminating the rounding-arbitrage vector.
- Round in the direction that always favors the pool (round down for payouts, round up for required deposits) rather than using naive `round()`.
- Consider bounding how much of the pool can be swapped in a single trigger relative to reserves to limit price-impact-based manipulation.

### Proof of Concept
Not directly transferable from the Solidity PoC; the analog requires deploying an AA following this oscript pattern and observing that repeated small `trigger.output[[asset=$asset]]`/`trigger.output[[asset=base]]` round-trip triggers, chosen to land on `round()` boundaries, yield a net positive balance for the attacker across many iterations, draining `balance[base]`/`balance[$asset]` — the same mechanic as the 6000x `hourBurn()` + `getAmountOut()`/`transfer()` loop in the original FIL314 exploit.
