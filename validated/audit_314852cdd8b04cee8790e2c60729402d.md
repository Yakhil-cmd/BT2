## Analysis: Cross-organization payload forgery via mismatched `repository.owner.login` and `repository.full_name` fields

### Title
Webhook signature verifies the sending organization but handlers act on an attacker-controlled `repository.full_name`, allowing cross-repository status/push forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks the GitHub App / HMAC secret to validate against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`), and verifies `X-Hub-Signature` against the raw body with that org's `webhook_secret`. [1](#0-0)  However, once the signature check passes, the dispatched handlers (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers, etc.) never re-check `repository.owner.login`; they resolve the target repository purely from `payload.dig('repository', 'full_name')` via `Shipit::Webhooks::Handlers::Handler#repository_name`/`#stacks`. [2](#0-1) 

### Finding Description
This mirrors the reported bug class exactly: two different code paths derive/consume a value that is supposed to represent "the same thing" (here, the org/repo the webhook is about), but they read it from different fields with different trust levels — one field is cryptographically bound (`owner.login`, used to select the signing secret) and the other is not (`full_name`, used to select which `Stack`/`Commit` records are mutated).

Concretely:
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner)` to fetch that organization's configured `webhook_secret`, then does an HMAC-SHA1 compare against the *entire raw request body*. [3](#0-2)  The HMAC covers the raw bytes, so `repository.full_name` is technically "covered" by the signature — but the code that *selects which secret to trust* only inspects `owner.login`, not `full_name`. In a single/global-app configuration this equivalence holds implicitly, but in the documented multi-org configuration (`config/secrets.*.yml`, `github: { OrgOne: {...}, OrgTwo: {...} }`) each organization owns and knows its own `webhook_secret`. [4](#0-3) 
- An attacker who is an admin of *their own* legitimately-installed GitHub App/organization (e.g. `OrgOne`) knows `OrgOne`'s `webhook_secret` (it's visible to any org owner in the GitHub App settings) and can therefore self-sign an arbitrary JSON payload where `repository.owner.login = "OrgOne"` (so `verify_signature` validates against `OrgOne`'s known secret) while `repository.full_name = "victim-org/victim-repo"` (an unrelated, already-tracked stack).
- `verify_signature` passes because it only checked `OrgOne`'s ownership claim was internally consistent with `OrgOne`'s secret — it never asserts that `full_name`'s owner segment equals `repository_owner`.
- The dispatched handler then looks up `Repository.from_github_repo_name(payload.dig('repository','full_name'))` — i.e. `victim-org/victim-repo` — and acts on it: `PushHandler` calls `stack.sync_github(expected_head_sha:)`, [5](#0-4)  and `StatusHandler` calls `commit.create_status_from_github!(params)` for any `Commit` in the DB matching an attacker-chosen `sha`, `state`, and `context`. [6](#0-5) 

### Impact Explanation
`StatusHandler` writing forged commit statuses onto a victim repository's commits directly affects Shipit's CI-gating logic (`ci.require`/`ci.blocking`), which is used to decide whether a commit is deployable. An attacker who legitimately controls only their own small/throwaway GitHub org (installed with the Shipit app for `read` access to trigger webhooks) could forge a `success` status on a victim stack's commit and unlock an otherwise CI-blocked deploy of that stack — this matches the "unauthorized deploy" Critical impact category. `PushHandler`/`CheckSuiteHandler` similarly let the attacker trigger `GithubSyncJob`/check-run refresh cycles against a stack they do not own, and PR handlers (`opened_handler.rb`, `labeled_handler.rb`, etc.) can archive/unarchive review stacks belonging to a repository the attacker's org never installed the app on.

### Likelihood Explanation
Requires the attacker to control (or be a member/admin of) some GitHub organization/App installation that the Shipit deployment recognizes — i.e., the multi-tenant/multi-org `Shipit.github(organization:)` configuration must be in use, and the attacker's org must be one of the configured orgs. This is a realistic setup for shared Shipit instances serving multiple organizations, which the engine explicitly documents and supports. [4](#0-3)  No repository write access to the victim repo, no `ApiClient` token, and no `GITHUB_TOKEN` are needed — only knowledge of the attacker's own org's `webhook_secret`, which they legitimately possess.

### Recommendation
In `WebhooksController#verify_signature` (or in `Shipit::Webhooks::Handlers::Handler`), cross-validate that the owner segment of `repository.full_name` (or `organization.login`) matches `repository.owner.login`/the organization whose secret validated the signature, and reject the webhook if they diverge. Alternatively, thread the verified `repository_owner` into each handler and require handlers to only operate on repositories whose `owner` matches the verified organization.

### Proof of Concept
1. Deployment configured with two orgs, e.g. `OrgOne` (attacker-controlled) and `victim-org` (target), per `test/dummy/config/secrets_double_github_app.yml`-style config. [4](#0-3) 
2. Attacker, as an admin of `OrgOne`'s GitHub App installation, knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body with:
   - `repository.owner.login = "OrgOne"`
   - `repository.full_name = "victim-org/victim-repo"`
   - `sha` = the SHA of a real undeployed commit on the victim stack, `state = "success"`, `context` = the required CI context.
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, raw_body)>` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "OrgOne")` and successfully verifies the signature against `OrgOne`'s secret. [3](#0-2) 
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` (repository-name-agnostic at this exact line) and writes a forged success status for the victim's commit, potentially satisfying `ci.require` and unlocking deploy for a stack the attacker never controlled. [6](#0-5) 

**Note on confidence**: I was not able to fully trace `Shipit.github(organization:)`'s resolution logic or confirm end-to-end whether `Status`/CI gating in `StatusChecker` strictly requires matching `full_name` elsewhere in the deploy-gating path (e.g., extra full_name checks inside `create_status_from_github!` or `Commit` scoping by `stack`), since `commit.rb` and `lib/shipit.rb`'s multi-org resolution were not fully read within the available iterations. A Devin session with full file access should verify `Commit#create_status_from_github!` and `Shipit.github`'s organization-matching logic to close this gap before treating this as fully confirmed exploitable end-to-end.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
