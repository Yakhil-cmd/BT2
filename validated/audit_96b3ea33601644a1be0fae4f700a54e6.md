The reported issue is specific to Solidity's OpenZeppelin `safeApprove` deprecation and USDT's non-zero-to-non-zero approval revert behavior — a Solidity/EVM library pattern. Searching the codebase, the only related surface is the `IERC20`-compatible `approve`/`permit` precompiles in `substrate/frame/assets/precompiles/src/lib.rs`, which wrap `pallet-assets`' native approval storage (not an external `safeApprove` call on another contract).

Critically, this precompile already implements the "cancel then re-approve" pattern that the report recommends: when overwriting a non-zero allowance, it calls `do_cancel_approval` before `do_approve_transfer` so the new value replaces rather than accumulates with the old one [1](#0-0) . This was explicitly fixed via [2](#0-1)  to match ERC-20 set semantics, and is covered by tests exercising non-zero-to-non-zero transitions without requiring a manual zero-first step from the caller [3](#0-2) .

There is no `safeApprove`-style external call from FRAME production code to an arbitrary ERC-20 contract that could revert due to non-zero-to-non-zero approval semantics — `pallet-assets`' `approve_transfer` dispatchable is additive by design and documented as such [4](#0-3) , which is native storage manipulation, not an external token call, so it cannot revert due to USDT-style approval race protections. No analogous vulnerability exists in this codebase.

fn approve_nonzero_to_nonzero(asset_index: u16) {
	use frame_support::traits::fungibles::approvals::Inspect;

	new_test_ext().execute_with(|| {
		let asset_id = 0u32;
		let asset_addr = H160::from(set_prefix_in_address(asset_index));

		let owner = 123456789u64;
		let spender = 987654321u64;

		Balances::make_free_balance_be(&owner, 100);
		Balances::make_free_balance_be(&spender, 100);

		let spender_addr = <Test as pallet_revive::Config>::AddressMapper::to_address(&spender);

		setup_asset_for_prefix(asset_id, asset_index);
		assert_ok!(Assets::force_create(RuntimeOrigin::root(), asset_id, owner, true, 1));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(owner), asset_id, owner, 100));

		let deposit: u128 = <Test as pallet_assets::Config>::ApprovalDeposit::get();

		// Approve 100 (0 → 100).
		call_approve(owner, asset_addr, spender_addr, U256::from(100));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 100);
		assert_eq!(Balances::reserved_balance(&owner), deposit);

		// Overwrite with 50 directly (100 → 50), no zeroing in between.
		call_approve(owner, asset_addr, spender_addr, U256::from(50));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 50);
		// Deposit reserved exactly once — cancel unreserved the old one, approve re-reserved.
		assert_eq!(Balances::reserved_balance(&owner), deposit);

		// Overwrite upward (50 → 200) to confirm it works in both directions.
		call_approve(owner, asset_addr, spender_addr, U256::from(200));
		assert_eq!(Assets::allowance(asset_id, &owner, &spender), 200);
		assert_eq!(Balances::reserved_balance(&owner), deposit);
	});
}
