### Title
Webhook signature verified against `repository.owner.login`'s GitHub App while all event handlers act on the independently-controlled `repository.full_name` field, breaking the "authenticating organization = written repository" binding - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which `webhook_secret`) to verify a request against using `repository_owner`, derived from the *unverified* payload field `repository.owner.login` (falling back to `organization.login`). [1](#0-0)  Once the request passes that check, the raw payload is handed unchanged to every registered handler. [2](#0-1)  Every handler, however, determines the actual repository/stack to mutate from a *different* field in the same payload: `payload.dig('repository', 'full_name')`. [3](#0-2)  Nothing in the code enforces that `repository.owner.login` and `repository.full_name` refer to the same repository/organization.

### Finding Description
This is the direct analog of the InflationaryVest.vy bug class: a value that gates a privileged action (`self.claimed`, here "which organization's signature verifies this request") is never bound/reconciled with the value that the privileged action actually operates on (`self.claimed` used later, here `repository.full_name` used by every handler). Two independently-controlled sub-fields of one attacker-supplied JSON body are treated as if they always agree, but the code never checks that they do.

Concretely:
- `verify_signature` computes `repository_owner = params.dig('repository','owner','login') || params.dig('organization','login')` and uses it to pick `Shipit.github(organization: repository_owner)`, whose `verify_webhook_signature` checks the HMAC using **that org's** `webhook_secret`. [4](#0-3) 
- `GitHubApp#verify_webhook_signature` trivially returns `true` when that org's `webhook_secret` is blank (a documented, supported configuration - see setup docs marking the webhook secret "optional"). [5](#0-4) 
- Once verification passes, `create` dispatches the *entire unmodified payload* to `Shipit::Webhooks.for_event(event)` handlers. [2](#0-1) 
- Every handler resolves the target `Repository`/`Stack` via `payload.dig('repository', 'full_name')`, a field completely independent from the one used for signature verification. [3](#0-2)  `PushHandler`, `StatusHandler`, and the `PullRequest::*` handlers (e.g. `ClosedHandler`, which also reads `params.repository.full_name` directly) all follow this same pattern. [6](#0-5) [7](#0-6) 

An attacker who can satisfy the signature check for *any one* configured GitHub organization (e.g. one that has no `webhook_secret` set, or one whose secret has otherwise leaked/is known to the attacker) can set `repository.owner.login` to that low-trust organization while setting `repository.full_name` to `victim-org/victim-repo`, an entirely different, fully-secured organization/repository also hosted on the same Shipit instance. The request authenticates as the low-trust org, but every handler acts on state (`Stack`, `Commit`, `Repository`) belonging to the victim org. This is exactly the pattern the rules flag as in-scope: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
Reachable unprivileged-attacker impacts once this decoupling is exploited:
- `StatusHandler#process` calls `commit.create_status_from_github!(params)` for any `Commit` matching `params.sha` across the whole instance, regardless of which org "authenticated." [8](#0-7)  Shipit's merge queue evaluates CI status via commit statuses to decide whether a PR is safe to auto-merge, so an attacker can forge a "success" status for a victim repository's commit using only a signature that is valid for an unrelated, weakly-secured organization — leading to an unauthorized merge/deploy decision on the victim's stack.
- `PushHandler#process` and `ClosedHandler#process` similarly operate on victim `Stack`s/`ReviewStack`s (triggering `sync_github`, archiving review stacks) chosen via the victim's `repository.full_name`, even though the request was authenticated against a different organization's webhook secret. [6](#0-5) [9](#0-8) 

This satisfies the "cross-repository writes" / "unauthorized ship, rollback or merge" bar for High/Critical impact, because it lets an attacker whose only credential is a webhook secret for org A (or an org with no secret configured) manipulate deploy/merge state belonging to org B.

### Likelihood Explanation
Requires the attacker to be able to satisfy `verify_webhook_signature` for *some* configured organization — either because that org has no `webhook_secret` configured (a supported, documented configuration per `docs/setup.md`, "Webhook secret (optional)"), or because a low-privilege org's secret is otherwise available to them (e.g. they operate their own low-trust GitHub org connected to the same Shipit instance). Given multi-org Shipit deployments are an explicitly documented and supported topology (`docs/setup.md` "Using Multiple Github Applications"), this is a realistic deployment shape, not a theoretical one. Exploitation itself only needs one crafted HTTP POST with two independently-set JSON fields — no repository write access, GitHub App key, or session is required.

### Recommendation
In `WebhooksController`, resolve `repository_owner` and the repository/stack used by every handler from the *same* verified field, and reject requests where `repository.owner.login` does not match the owner encoded in `repository.full_name`. Equivalently, have `Handler#repository_name` cross-check against the organization the signature was actually verified for, rejecting the payload if they diverge.

### Proof of Concept
1. Configure (or discover) a Shipit multi-org install where org `attacker-org` has `webhook_secret` unset (supported per docs), and org `victim-org` hosts a real Stack with a real `webhook_secret`.
2. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` needed since `attacker-org` has no configured secret, so `verify_webhook_signature` returns `true` unconditionally. [5](#0-4) 
3. `WebhooksController#verify_signature` passes because it only checked `attacker-org`. [4](#0-3) 
4. `StatusHandler` looks up `Commit.where(sha: params.sha)` (victim's commit) and records the forged "success" status, independent of which org the request "authenticated" as. [8](#0-7)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
