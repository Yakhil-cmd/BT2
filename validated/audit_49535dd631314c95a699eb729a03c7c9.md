### Title
Borrower can temporarily drain withdrawable liquidity to sandwich a supplier withdrawal - ([File: contracts/pool/src/ops/withdraw.rs])

### Summary
An unprivileged borrower can borrow nearly all available cash in a supplied market, cause another account’s `withdraw` transaction to revert with `CollateralError::InsufficientLiquidity`, and then repay the debt in a later transaction to restore liquidity. `withdraw` maps a zero amount to the account’s full position and calls the pool withdrawal path, while the pool checks cash only when executing that withdrawal. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::borrow` accepts a batch of `(HubAssetKey, i128)` debt draws from an authorized owner or delegate and sends the proceeds to `to` or the caller. [3](#0-2)  The controller calls `pool_borrow_call`, and pool borrow accounting mints debt shares, debits market cash, commits the reduced-cash state, and transfers the tokens out. [4](#0-3) [5](#0-4)  A borrow is limited by positive cash reserves, the liquidation buffer, and maximum utilization, but it can still leave only the configured liquidation reserve in the market. [6](#0-5) [7](#0-6) 

`Controller::withdraw` then performs the withdrawal against that changed pool state. [8](#0-7)  A withdrawal amount of `0` becomes `WITHDRAW_ALL_SENTINEL`, so the victim cannot rely on a previously simulated exact balance to distinguish a full exit from a partial request. [9](#0-8)  Pool withdrawal accounting burns the supply shares and calls `gate_and_debit`, whose `require_reserves` check reverts when the requested net transfer exceeds remaining cash. [10](#0-9) [11](#0-10) 

After the victim’s transaction fails, the attacker can call permissionless `repay`; the controller transfers the repayment into the pool, pool repayment credits the net payment to cash, and any overpayment is refunded to the payer. [12](#0-11) [13](#0-12) 

### Impact Explanation
A supplier can be temporarily prevented from withdrawing collateral even though the supplier’s position and health are otherwise valid. The attacker does not receive the victim’s collateral, but can make a specifically ordered withdrawal fail by occupying the market’s withdrawable cash for the duration of the attack. [11](#0-10) [14](#0-13) 

The freeze lasts only while the attacker keeps the debt open, so the impact is temporary rather than permanent. However, the attacker can repeat the borrow when liquidity returns and can target withdrawals whose size exceeds the liquidation reserve. [7](#0-6) 

### Likelihood Explanation
The attacker needs a funded account, sufficient accepted collateral, enough borrow capacity, and transaction ordering before the victim’s withdrawal. The liquidation buffer and maximum-utilization guard prevent literal exhaustion of every market token, but they do not reserve enough cash for arbitrary supplier withdrawals. [6](#0-5) [15](#0-14) 

The attack requires the borrowed asset to be returned or the debt to remain outstanding, so its direct protocol cost is bounded by accrued interest, transaction fees, and collateral capital. No privileged role, oracle manipulation, leaked key, or control of the victim account is required. [16](#0-15) [17](#0-16) 

### Recommendation
If immediate withdrawal is intended to be protected from short-lived liquidity occupation, add an explicit withdrawal reserve or withdrawal-queue mechanism rather than relying only on the liquidation buffer. Alternatively, support a bounded partial-withdrawal result for user-facing withdrawals so a temporary liquidity shortage does not necessarily revert the entire exit, while documenting the remaining claim clearly. [11](#0-10) 

Any reserve should be sized above the liquidation buffer and accounted for in both `borrow` and `withdraw`, so borrower entry cannot consume cash already earmarked for queued withdrawals. [7](#0-6) [18](#0-17) 

### Proof of Concept
Assume market `M` has `C` cash, a liquidation reserve `R`, and victim account `V` holding a supplied position worth `W > R`.

1. The attacker creates or uses a solvent account with collateral through `supply(caller=attacker, account_id, spoke_id, assets=[(collateral_asset, collateral_amount)])`. [19](#0-18) 
2. The attacker submits `borrow(caller=attacker, account_id=attacker_id, borrows=[(M, C - R)], to=Some(attacker))`, subject to caps and solvency, reducing market cash to approximately `R`. [3](#0-2) [20](#0-19) 
3. Before the attacker repays, the victim submits `withdraw(caller=victim, account_id=V, withdrawals=[(M, 0)], to=Some(victim))`; `0` requests the full position. [1](#0-0) [21](#0-20) 
4. Because `W > R`, pool withdrawal accounting reaches `require_reserves(W)` and reverts with `CollateralError::InsufficientLiquidity`; the victim receives nothing. [11](#0-10) [2](#0-1) 
5. The attacker then submits `repay(caller=attacker, account_id=attacker_id, payments=[(M, debt_amount)])`; the measured payment credits cash and restores withdrawal liquidity. [12](#0-11) [22](#0-21)

```rust
    account_id: u64,
    borrows: &Vec<HubPayment>,
    to: Option<Address>,

    validation::require_authorized_caller(env, caller);

    let mut account = storage::get_account(env, account_id);

    let mut cache = Context::new(env);
    require_external_recipient(env, &mut cache, &recipient);
    let aggregated = payments::aggregate_positive_payments(env, borrows);

        env,
        &account,
        &aggregated,

        PositionSides::Both

        PositionSides::Debt

    finalize_position_flow(env, account_id, &account, &mut cache, sides, false);
}
```

```rust
pub(crate) fn mint_debt(env: &Env, cache: &mut Cache, position: &mut Ray, amount: i128) {
    require_positive_amount(env, amount);
    cache.require_reserves(amount);
    guards::require_liquidation_buffer(env, cache, amount);

    let minted = cache.calculate_scaled_borrow(amount);

    assert_with_error!(
        env,
        minted.raw() > 0,
        GenericError::BorrowRoundsToZeroShares
    );

    *position = position.checked_add(env, minted);
    cache.mint_debt(minted);
    guards::require_utilization_below_max(env, cache);
}
```

```rust
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
```

```rust
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```
