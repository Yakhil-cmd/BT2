### Title
Possible NULL/undefined dereference in `handleTrigger` when checking for a duplicate primary AA trigger - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `handleTrigger()` checks whether a trigger unit has already produced a primary AA response by directly dereferencing `storage.assocStableUnits[trigger.unit].count_aa_responses` without first verifying that `storage.assocStableUnits[trigger.unit]` actually exists. [1](#0-0) 

### Finding Description
The check that guards against "a second primary trigger from the same unit" is:
```
if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && storage.assocStableUnits[trigger.unit].count_aa_responses && mci >= constants.pemCurvesFixMci)
	return bounce('a second primary trigger from the same unit is not allowed');
``` [2](#0-1) 

This is the exact bug-class of the reported CVE: a pointer/lookup result (`storage.assocStableUnits[trigger.unit]`) that can be `undefined` is dereferenced (`.count_aa_responses`) without a preceding existence check, unlike other places in `storage.js` that explicitly guard the same map with `if (!objUnit) throw Error(...)` before use, e.g. `getUnconfirmedAADefinition`. [3](#0-2) 

`handleTrigger` is invoked for every primary AA trigger derived from a payment message that any unprivileged unit poster sends to an AA address; `trigger.unit` is the id of the unit that the attacker/user posted. [4](#0-3) 
If, at the time this trigger is executed (which happens during MC advancement / stabilization processing, not necessarily synchronously with the unit becoming stable, and can be delayed by chains of AA processing, and `assocStableUnits` is a bounded/pruned in-memory cache), the entry for `trigger.unit` is absent from `storage.assocStableUnits`, the property access throws a `TypeError: Cannot read properties of undefined (reading 'count_aa_responses')`.

### Impact Explanation
An unhandled exception thrown deep inside the synchronous AA trigger-processing/stabilization code path is not caught by ordinary error handling used elsewhere in `handleTrigger` (which relies on `bounce(err)` for expected errors, not on try/catch around this line). An uncaught exception here would propagate up through the main-chain advancement logic that stabilizes units and executes AA triggers, crashing the node process while it is confirming units — i.e., a network node becomes unable to continue validating/confirming new units, matching the "network unable to confirm new units" acceptance criterion.

### Likelihood Explanation
The trigger is reachable by any unprivileged user simply by sending a payment to an existing AA address (a completely normal, permissionless action). The only additional requirement is a runtime condition where `storage.assocStableUnits` no longer contains the trigger's unit id when this bounce-check code executes (e.g., due to cache eviction/pruning or delayed re-processing paths), which is a timing/cache-state precondition outside the attacker's direct control, so likelihood is not "trivial" but is plausible given the codebase's own comments about needing similar defensive `if (!objUnit)` checks elsewhere for the same cache.

### Recommendation
Add an explicit existence check before dereferencing the cache entry, mirroring the pattern already used elsewhere in `storage.js`:
```js
if (!bSecondary) {
    ...
    const objTriggerUnitProps = storage.assocStableUnits[trigger.unit];
    if (trigger.unit !== constants.GENESIS_UNIT && !trigger_opts.bAir && objTriggerUnitProps && objTriggerUnitProps.count_aa_responses && mci >= constants.pemCurvesFixMci)
        return bounce('a second primary trigger from the same unit is not allowed');
}
```
If the entry being missing is actually supposed to be impossible/a bug indicator, it should `throw Error("unit not found in assocStableUnits: " + trigger.unit)` explicitly (as done for other lookups in `storage.js`) rather than crashing with an unhandled TypeError.

### Proof of Concept
Not independently reproducible from static analysis alone — a concrete PoC requires constructing a scenario where `handleTrigger` runs for a `trigger.unit` that has already been evicted from (or not yet inserted into) `storage.assocStableUnits` at the moment this bounce-check executes (e.g., via a long/delayed chain of secondary AA triggers or node restart/cache-repopulation timing). I could not verify the exact eviction/lifecycle conditions of `assocStableUnits` from the indexed code alone; a full Devin session with access to `storage.js`'s complete cache management logic and a runnable test harness would be needed to confirm exploitability with certainty.
