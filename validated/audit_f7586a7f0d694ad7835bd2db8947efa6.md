Based on my research, I found a genuine analog to the reported bug class in nearcore's `PendingTransactionQueue`. The mechanism is used for "SPICE" pending transaction admission control, gating balance/nonce checks for transactions accepted into a chunk before certification.

### Title
Silent underflow-to-default in `PendingAccount::subtract` corrupts pending-balance accounting and can bypass pending balance/P_MAX constraints - (File: chain/client/src/pending_transaction_queue.rs)

### Summary
`PendingTransactionQueue::remove_certified_chunk_by_block_hash` reverses per-chunk aggregates (`access_key_tx_count`, `deploy_tx_count`, `paid_from_balance`) from running totals using `PendingAccount::subtract`, which relies on the `checked_sub_or_default!` macro. If the subtraction underflows, the macro logs an error/`debug_assert` but silently resets the field to `Default::default()` (zero) rather than propagating an error or leaving the state internally consistent, and the removal proceeds regardless. This mirrors the reported `BoostController.removeBoostDelegation` pattern: a conditional/guarded decrement that is skipped or defaulted on failure while the corresponding "delegation"/chunk-removal action still commits, corrupting the running totals used to gate subsequent validation. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`PendingAccount` accumulates, per account, the total pending `access_key_tx_count`, `deploy_tx_count`, and `paid_from_balance` across all not-yet-certified chunks. When a chunk becomes certified, `remove_certified_chunk_by_block_hash` subtracts that chunk's per-account contribution from the running totals via `PendingAccount::subtract`, and the same pattern is used for `pending_gas_key_costs`. [4](#0-3) 

Each subtraction goes through `checked_sub_or_default!`, which on underflow does not return an error to the caller — it simply resets the value to zero (or the type default) and continues: [5](#0-4) 

This is structurally the same defect class as the reported Solidity bug: a decrement operation that is guarded/capped instead of exact, followed by unconditional removal/finalization of the corresponding entry, leaving aggregate state inconsistent with the sum of its parts. In the Boost report, `totalBoost`/`workingSupply` remain permanently inflated after a skipped subtraction while the delegation record is deleted anyway. Here, `pending_accounts[account]` (and `pending_gas_key_costs`) can be forced to zero out even though other still-pending chunks' contributions haven't actually been reversed, while `self.chunks.remove(block_hash)` for that block always succeeds. [6](#0-5) 

The resulting `paid_from_balance`/`paid_from_gas_key`/`max_nonce` snapshot feeds directly into consensus-adjacent (though not consensus-critical) balance and nonce checks used both by the RPC handler when accepting a transaction and by chunk production when preparing transactions: `get_pending_constraints` and `query_pending_state` read straight from these maps. [7](#0-6)  These constraints are consumed in `verify_and_charge_tx_ephemeral` (`available_balance = account.amount().saturating_sub(pending.paid_from_balance)`), in the gas-key equivalent, and in the RPC path in `chain/client/src/rpc_handler.rs`. [8](#0-7) [9](#0-8) 

The intended invariant is that `pending_accounts[account]` equals the sum of all `chunk_data.accounts[account]` for chunks still tracked in `self.chunks`. `add_chunk_transactions` always adds via `saturating_add` (never fails), but `remove_certified_chunk_by_block_hash` subtracts via `checked_sub_or_default!`, which is not the true inverse operation whenever the two sides diverge (e.g., a chunk removed twice due to a reorg re-processing the same `block_hash`, race between the certified-block callback and reorg re-initialization/`clear()`, or any bookkeeping divergence between per-chunk and aggregate maps). When that happens, the aggregate is forced to zero instead of reflecting the correct residual value, and no error is surfaced to callers — only a `debug_assert!`, which is compiled out in release builds. [10](#0-9) 

### Impact Explanation
If the underflow path is hit for `paid_from_balance` (or `pending_gas_key_costs`), the running "already committed" balance for that account is incorrectly reset toward zero even while other pending, uncertified chunks still have that balance genuinely reserved. Because `paid_from_balance` is subsequently used to reduce `available_balance` before validating a new transaction, a spuriously-zeroed `paid_from_balance` makes the node believe more balance is available than actually is, allowing a chunk producer or RPC handler to admit a transaction that should have been rejected for insufficient balance under the pending (uncertified) state — i.e., an unauthorized/incorrect balance/admission decision resulting from corrupted accounting, structurally analogous to the reported inflated-boost/incorrect-reward-distribution bug. It does not directly forge on-chain balances (final settlement still goes through the authoritative trie-based runtime verification once a chunk is actually applied), so the primary risk is bypassing the pending-transaction-queue's soft admission constraints (P_MAX / deploy exclusivity / balance pre-check), not a hard consensus-state forgery.

### Likelihood Explanation
Reaching the underflow requires the per-chunk aggregate removed to exceed what remains in the running total — this should not happen under the intended single-add/single-remove-per-chunk lifecycle, but the code explicitly anticipates and handles (rather than rejects) this divergence, indicating the invariant is not proven to hold across all reorg/re-certification/duplicate-removal paths. The comment before `verify_and_charge_tx_ephemeral`'s use of `saturating_sub` explicitly acknowledges this pending-constraints path is "best-effort" and does not affect the consensus path, which limits blast radius but confirms the mechanism is reachable and not authoritative-safe.

### Recommendation
Change `checked_sub_or_default!` (or its call sites for `paid_from_balance` / `pending_gas_key_costs` / counts) to propagate a hard error (panic or `Result` bubbling to a queue-reset/`clear()`) instead of silently defaulting to zero, since a defaulted value is provably wrong (not merely "safe"), unlike a saturating/no-op default. Alternatively, guard against duplicate/overlapping chunk removal by tracking removal idempotently (e.g., verifying the block hash was actually present and its exact recorded aggregate before subtracting), and add invariant tests that simulate reorg-driven double-removal or overlapping chunk certification to ensure `pending_accounts`/`pending_gas_key_costs` never silently zero out while other chunks' contributions are still outstanding.

### Proof of Concept
Concrete reproduction requires triggering two `remove_certified_chunk_by_block_hash` calls whose combined subtracted `PendingAccount`/gas-key cost exceeds what is currently tracked for that account (e.g., via a reorg path that re-delivers a "certified block" callback for the same `block_hash` twice, or a race between epoch reorg `clear()`/reinitialization and an in-flight certified-block callback). I was not able to trace a concrete external trigger (e.g. a specific reorg callback sequence) all the way to a double-invocation of `remove_certified_chunk_by_block_hash` for the same block hash within the scope of this analysis; the existing unit tests in the same file only exercise the correct single-add/single-remove lifecycle and do not test the double-removal/underflow path, so whether it is reachable from attacker-controlled input (vs. only from an internal logic bug) is unconfirmed and would need further investigation of the reorg/certification callback wiring in `chain/client`.

/// Checked subtraction that falls back to `Default::default()` on underflow,
/// logging an error and firing a debug_assert so tests catch the invariant violation.
macro_rules! checked_sub_or_default {
    ($a:expr, $b:expr, $msg:expr) => {
        match ($a).checked_sub($b) {
            Some(v) => v,
            None => {
                debug_assert!(false, $msg);
                tracing::error!(target: "client", $msg);
                Default::default()
            }
        }
    };
}

    fn add(&mut self, other: &PendingAccount) {
        self.access_key_tx_count += other.access_key_tx_count;
        self.deploy_tx_count += other.deploy_tx_count;
        self.paid_from_balance = self.paid_from_balance.saturating_add(other.paid_from_balance);

        self.access_key_tx_count = checked_sub_or_default!(

    /// Query pending state for a single transaction. Extracts the counts and
    /// constraints needed by `PendingTxSession::check_pending`. This is called
    /// under the lock and should be fast.
    fn query_pending_state(
        &self,
        signer_id: &AccountId,
        public_key: &PublicKey,
        nonce_index: Option<NonceIndex>,
    ) -> PendingStateSnapshot {
        let pending_account = self.pending_accounts.get(signer_id);
        let access_key_tx_count = pending_account.map(|a| a.access_key_tx_count).unwrap_or(0);
        let deploy_tx_count = pending_account.map(|a| a.deploy_tx_count).unwrap_or(0);
        let paid_from_balance =
            pending_account.map(|a| a.paid_from_balance).unwrap_or(Balance::ZERO);

        let gas_key = (signer_id.clone(), public_key.clone());
        let pending_gas_key_cost =
            self.pending_gas_key_costs.get(&gas_key).copied().unwrap_or(Balance::ZERO);

        let nonce_key = (gas_key.0, gas_key.1, nonce_index);
        let max_nonce = self.pending_nonces.get(&nonce_key).map(|n| n.max_nonce()).unwrap_or(0);

        PendingStateSnapshot {
            access_key_tx_count,
            deploy_tx_count,
            paid_from_balance,
            max_nonce,
            pending_gas_key_cost,
        }
