### Title
Webhook signature verification is skipped for GitHub organizations configured without a `webhook_secret`, allowing forged `membership` events to grant unauthorized access - ([File: lib/shipit/github_app.rb])

### Summary
`Shipit::GitHubApp#verify_webhook_signature` unconditionally returns `true` when the organization's `webhook_secret` is blank, exactly mirroring the reported bug class ("0 balance causes basket mode"): a config value's *absence* (unset/nil `webhook_secret`) silently disables the very check that state is supposed to gate. Because the multi-organization config schema explicitly supports per-organization `webhook_secret: # nil` [1](#0-0) , any organization deployed with this default/omitted value accepts **completely unsigned webhook payloads**. Combined with `MembershipHandler`, which trusts the payload to add arbitrary GitHub logins to any `Team`, this becomes an authentication/authorization bypass into `Shipit.github_teams`.

### Finding Description
`WebhooksController#verify_signature` selects which `GitHubApp` (and thus which secret) to verify against using an organization value taken straight from the **unauthenticated** JSON body: [2](#0-1) 

The selected `GitHubApp#verify_webhook_signature` implementation is: [3](#0-2) 

`return true unless webhook_secret` means: if the organization picked (from the attacker-controlled `repository.owner.login` / `organization.login` field) maps to a GitHub App config whose `webhook_secret` is blank, the "verified" signature check trivially passes for *any* body and *any* (or missing) `X-Hub-Signature` header — no HMAC is ever computed. `webhook_secret` is documented and shown as an intentionally optional value (`# nil`) in both the single-org and multi-org config examples [4](#0-3) [5](#0-4) , so this is a supported, reachable deployment state, not a theoretical misconfiguration.

The equality broken: **organization that authenticated the request (via HMAC secret) == organization whose webhook handlers are executed**. When `webhook_secret` is unset for an org, this equality collapses to "any unauthenticated sender == that organization," because verification is a no-op.

The most damaging handler reachable this way is `MembershipHandler`, which acts entirely on unauthenticated payload fields: [6](#0-5) 

It creates/looks up a `Team` by `params.team.id`, creates/looks up a `User` by `params.member.login` (auto-creating the user via `User.find_or_create_by_login!`), and on `action == 'added'` calls `team.add_member(member)`: [7](#0-6) 

`User#authorized?` then grants application access based purely on team membership: [8](#0-7) 

So an attacker who knows (a) the `github_id` of a `Team` referenced in `Shipit.github_teams` (discoverable via the public GitHub API, since teams map 1:1 to real GitHub team IDs) and (b) an organization configured without `webhook_secret`, can forge a `membership` webhook `added` event naming their own GitHub login as `member`, with no valid signature required, and be granted membership in that authorizing team — bypassing GitHub OAuth entirely for future logins.

### Impact Explanation
This is an authentication/authorization bypass: escalation into `Shipit.github_teams` authorization without ever completing GitHub OAuth or being a real team member, satisfying the High severity criterion ("escalation into `Shipit.github_teams` authorization"). It also enables forging `push`/`status`/`pull_request`/`check_suite` events for the same misconfigured organization, letting an attacker fabricate CI status or trigger `stack.sync_github`, further undermining deploy integrity for that org's stacks.

### Likelihood Explanation
Exploitability requires only that one configured GitHub organization has no `webhook_secret` set — a state the shipped example configs (`config/secrets.development.example.yml`, `secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`) explicitly present as valid/default (`# nil`), and which the multi-org `Using Multiple Github Applications` docs describe without mandating the field [9](#0-8) . No credentials, session, or API token are needed — only an unauthenticated HTTP POST to the webhooks endpoint.

### Recommendation
Fail closed instead of open when `webhook_secret` is blank: reject the webhook (`head 422`) rather than treating a missing secret as "verification passed." At minimum, require a non-blank `webhook_secret` for any organization whose GitHub App config is used to process `membership`/authorization-affecting events, and validate that the organization derived from the payload actually owns the `Team`/`github_id` referenced before mutating team membership.

### Proof of Concept
1. Deploy Shipit with a GitHub App configured for organization `victim-org` using the documented pattern with `webhook_secret` omitted (as shown in the shipped example secrets files).
2. Note the `github_id` of a `Shipit::Team` that is part of `Shipit.github_teams` (matches a real GitHub team backing OAuth authorization).
3. Send, with no `X-Hub-Signature` header (or any garbage value):
```
POST /github/webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "team": {"id": <team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "victim-org"},
  "member": {"login": "attacker-github-login"},
  "repository": {"owner": {"login": "victim-org"}}
}
```
4. `verify_webhook_signature` returns `true` (blank `webhook_secret`), the request passes `verify_signature`, and `MembershipHandler` adds `attacker-github-login` as a member of the authorizing team.
5. `attacker-github-login` can now log in via GitHub OAuth and pass `User#authorized?`, gaining access to the Shipit deployment application.

      verified = github_app.verify_webhook_signature(

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
      end
    end
  end
end
