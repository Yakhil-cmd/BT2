### Title
Zip Bomb DoS via Untrusted `uncompressedSize` Metadata in Private-Payment File Import - (File: wallet.js)

### Summary
`handlePrivatePaymentFile()` in `wallet.js` unzips a private-payment backup file received from a payment counterparty and decides whether it's "too large" by reading `entry._data.uncompressedSize` from the untrusted ZIP central-directory metadata, before ever inflating the entry. This mirrors CVE-2024-10569 (Gradio's zip-bomb DoS in `dataframe.py`): a size check is performed on attacker-supplied metadata rather than on the actual decompressed byte stream, so the check can be trivially bypassed with a crafted archive whose declared size is small but whose actual inflate output is enormous. [1](#0-0) 

### Finding Description
`handlePrivatePaymentFile(fullPath, content, cb)` loads a ZIP archive (using `JSZip`) that a private-payment counterparty produces via `storePrivateAssetPayload()` and hands to the recipient out-of-band (e.g. as a "private textcoin"/private-payment backup file) [2](#0-1) . When the recipient imports this file, the code does:

```
zip.loadAsync(data).then(function(zip) {
    const entry = zip.file("private_textcoin");
    ...
    if (entry._data && entry._data.uncompressedSize > 100 * 1024 * 1024)
        return cb("private_textcoin entry is too large");
    entry.async("string").then(function(data) { ... })
``` [3](#0-2) 

`entry._data.uncompressedSize` is a value taken directly from the ZIP file's local/central directory header — a field fully controlled by whoever crafted the archive (the private-payment counterparty, or anyone who can substitute the file the recipient opens). `zip.loadAsync()` only parses this header metadata; it does not verify it against the actual compressed payload. The DEFLATE decoder invoked by `entry.async("string")` does not stop at the declared `uncompressedSize` — it decompresses the entire compressed byte stream present in the entry. An attacker can therefore set an arbitrary small `uncompressedSize` in the header (passing the `<=100MB` guard) while the actual compressed data inflates to a size limited only by the compression ratio achievable with DEFLATE (roughly 1000:1), producing gigabytes of output in memory from a very small file — the same "trust metadata, not the stream" root cause as the Gradio `pd.read_csv` zip-bomb bug.

Because `entry.async("string")` builds the fully-inflated string in memory before any subsequent validation (`JSON.parse`, chain checks, etc.) occurs, the wallet process can exhaust memory and crash.

### Impact Explanation
A malicious private-payment counterparty (or anyone able to hand the victim a crafted "private payment file") can cause the victim's wallet process to allocate unbounded memory and crash, denying the wallet's ability to receive/process payments, confirm units, or otherwise operate — a concrete node/wallet availability loss reachable purely by a private-payment counterparty sending a file for the victim to import, satisfying the "private-payment counterparty" reachable-actor criterion. This is a Medium/High impact DoS matching the CWE-475 pattern of the original advisory (uncontrolled resource consumption due to trusting compressed-file metadata).

### Likelihood Explanation
Likelihood is moderate-to-high: no cryptographic secret or special privilege is required to construct a malicious ZIP with a falsified `uncompressedSize` header; any party that can hand the victim a private-payment file (the normal flow for private/indivisible-asset payments and offline textcoin claims) can trigger this path. The only prerequisite is that the victim imports/opens the received file, which is the expected, intended workflow for private payments delivered this way.

### Recommendation
Do not rely on the ZIP's self-reported `uncompressedSize` for size enforcement. Instead:
- Stream-decompress the entry (e.g. using `entry.internalStream()` / `nodeStream()`) and enforce a hard byte-count cap while reading, aborting as soon as the cumulative inflated size exceeds the limit (e.g. 1–10 MB, since the payload is just JSON describing payment chains).
- Additionally cap the total compressed input size and the number of ZIP entries read.
- Reject archives whose actual decompressed output diverges materially from the declared header value instead of trusting the header outright.

### Proof of Concept
1. Craft a small ZIP file containing an entry named `private_textcoin`.
2. In the ZIP's local file header, set the compression method to DEFLATE and manually set `uncompressed size` field in both the local file header and central directory to a small value (e.g., 1000 bytes) while the compressed data section actually contains a full DEFLATE stream that decompresses to several hundred MB/GB (a classic highly-compressible payload, e.g. repeated bytes) — most simple ZIP libraries allow constructing such a mismatched header/data pair directly via raw byte manipulation of a legitimately generated ZIP.
3. Deliver this file to the victim as a "private payment" backup (the normal channel used by `storePrivateAssetPayload`/associated UI import flow) and have them call `handlePrivatePaymentFile(fullPath, content, cb)`.
4. `zip.loadAsync()` succeeds, `entry._data.uncompressedSize` reads the falsified small value and passes the `<=100MB` check, `entry.async("string")` then inflates the full deflate stream into memory, consuming the actual (much larger) decompressed size and causing memory exhaustion / process crash.
