### Title
Webhook signature check silently no-ops when an organization has no `webhook_secret`, letting an unprivileged attacker forge `membership` events to grant themselves `Shipit.github_teams` authorization - (File: `lib/shipit/github_app.rb`)

### Summary
`GitHubApp#verify_webhook_signature` is meant to be the trust boundary that guarantees every field in an incoming webhook payload actually originated from GitHub. However, when the configured GitHub App for an organization has no `webhook_secret` set, the method returns `true` unconditionally, without checking the signature header or the raw body at all. Any payload field acted on by a webhook handler is then "verified" without ever being covered by a real signature — including `membership` events that create local `Team`/`Membership` records used to authorize Shipit access.

### Finding Description
`WebhooksController#verify_signature` picks a GitHub App/organization purely from attacker-controlled JSON (`repository.owner.login` or `organization.login`) and delegates verification to that org's `GitHubApp`: [1](#0-0) 

The verification itself is: [2](#0-1) 

`return true unless webhook_secret` means: for any organization whose `webhook_secret` config key is blank/absent, `verify_webhook_signature` always returns `true`, regardless of the `X-Hub-Signature` header or body content. This is not a hypothetical misconfiguration — it is the documented/default shape of the config: both `docs/setup.md` and `config/secrets.development.example.yml` ship `webhook_secret: # nil` as an accepted value, and the multi-org example (`config/secrets.development.shopify.yml`) shows the same for each org.

Once verification passes, `WebhooksController#create` dispatches the raw, attacker-supplied JSON directly to registered handlers: [3](#0-2) 

The `membership` handler trusts this payload completely to mutate the authorization graph — creating a `Team` and adding/removing a `member` (a real `User` row) from it: [4](#0-3) 

Team membership is exactly what gates application access: `Authentication#force_github_authentication` calls `current_user.authorized?`, which is documented/enforced against `Shipit.github_teams` (the configured authorized teams), e.g. asserted in `test/controllers/stacks_controller_test.rb`'s "current_user must be a member of at least a Shipit.github_teams" tests: [5](#0-4) 

The broken equality is: **"organization whose payload is treated as GitHub-authenticated" == "organization whose `verify_webhook_signature` returned true because HMAC matched"**. When `webhook_secret` is blank for the targeted org, the right-hand side degenerates to "always true," so an attacker who merely knows (or guesses) a configured organization login can submit a forged `membership` `added` event naming their own Shipit login as `member.login` and any team slug/id, causing `Team.find_or_create_by!` + `team.add_member(member)` to run with no cryptographic verification whatsoever — identical in spirit to the leverage bug, where a formula/check that appears to enforce a real relationship (`_debt_value + _margin_value ≈ _position_value`, here "HMAC verified ⇒ genuinely from GitHub") in fact allows the two sides to diverge under a specific, easily reachable condition (blank secret) instead of always representing the same real-world fact.

### Impact Explanation
This is a direct escalation into `Shipit.github_teams` authorization, one of the explicitly listed High-severity impacts. An attacker who:
1. Has (or creates via normal GitHub OAuth login) a legitimate Shipit `User` account bound to their own browser session (`session[:user_id]`, `app/controllers/shipit/github_authentication_controller.rb`), and
2. Knows the organization login configured on the target Shipit instance (public information — it's the GitHub org name),

can POST a forged, unsigned `membership` webhook naming themselves as the added member of a team whose `github_id`/name they choose, without ever needing to actually be a member of that GitHub team. Since `force_github_authentication` grants full application access based on local `Membership` records, this converts into full access to stacks, deploys, rollbacks, and merges — an unauthorized deploy/merge is directly reachable downstream.

### Likelihood Explanation
Requires no credentials, no `ApiClient` token, no GitHub App private key, and no privileged access — only knowledge of the org login and that the org's `webhook_secret` is unset, which is the value shown as the default/example configuration in this engine's own docs and secrets templates. This is a config state the engine itself ships and documents as acceptable, not a deployment error outside the engine's control.

### Recommendation
Do not silently accept unsigned webhooks. `verify_webhook_signature` should fail closed when no `webhook_secret` is configured (or Shipit should refuse to boot/accept webhook traffic for an org without one), rather than treating "no secret configured" as "verification passed." At minimum, sensitive handlers (`membership`, any handler creating/mutating `Team`/`Membership`) should never be reachable without a verified signature.

### Proof of Concept
```
POST /github/webhooks
X-Github-Event: membership
Content-Type: application/json
(no X-Hub-Signature header needed if `webhook_secret` is blank for "TargetOrg")

{
  "action": "added",
  "team": { "id": 999999, "name": "Fake Team", "slug": "fake-team", "url": "http://example.com" },
  "organization": { "login": "TargetOrg" },
  "member": { "login": "attacker-shipit-login" },
  "repository": { "owner": { "login": "TargetOrg" } }
}
```
`verify_signature` calls `Shipit.github(organization: "TargetOrg").verify_webhook_signature(nil, body)`, which returns `true` immediately (`lib/shipit/github_app.rb:76-77`) because `webhook_secret` is blank for `TargetOrg`. `MembershipHandler#process` then creates the `Team` and adds `attacker-shipit-login` (the attacker's own Shipit `User`, tied to their own browser session) to it, and if `Shipit.github_teams` includes that team's org/slug, `current_user.authorized?` now returns `true` for the attacker on their next request.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
