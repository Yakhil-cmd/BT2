### Title
Unauthenticated cross-repository CI status forgery via organization/repository binding confusion in webhook signature verification - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub organization's secret to check a webhook signature against using `repository_owner` (`repository.owner.login` / `organization.login`) taken from the unauthenticated request body, then hands the *entire* payload to handlers such as `StatusHandler`, which writes a commit status keyed only on `sha` — with no re-validation that the authenticated organization actually owns that commit/repository. The binding "organization whose signature was verified" == "repository/commit that gets written" is never enforced, mirroring the ERC777 pattern where a credit is applied without checking that the code path that authorized it is the same one performing the action.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/organization used for HMAC verification purely from attacker-supplied payload fields: [1](#0-0) [2](#0-1) 

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```

`GitHubApp#verify_webhook_signature` unconditionally passes when no `webhook_secret` is configured for that organization — a state explicitly presented as a normal, supported configuration in the docs/example secrets files: [3](#0-2) [4](#0-3) 

Once `verify_signature` passes (or is bypassed), the raw body is dispatched to *all* registered handlers for the event with no further scoping by the organization that was just "verified": [5](#0-4) 

Critically, `StatusHandler` — unlike `PushHandler`/other handlers which scope through `Handler#stacks` (which does look up `Repository.from_github_repo_name(payload.dig('repository','full_name'))`) — does not use the repository at all. It matches purely on `sha` across the entire `Commit` table, i.e., across every stack/repository tracked by the Shipit instance: [6](#0-5) 

So the field that is used to select which secret authenticates the request (`repository.owner.login`) is completely decoupled from the field that determines which commit gets a status written (`sha`, with no `repository` correlation at all). The equality that should hold — *"organization whose signature is verified" == "repository/commit whose status is written"* — is never checked.

### Impact Explanation
If a webhook secret is left unset for any configured organization (a state the shipped example configs (`config/secrets.development.example.yml`, `template.rb`) present as valid), signature verification for that organization label unconditionally succeeds regardless of the `X-Hub-Signature` header. An unauthenticated caller can then send a crafted `status` event naming that organization as `repository.owner.login`, but with a `sha` belonging to a commit on a *completely different*, unrelated stack/repository hosted by the same Shipit instance, and set `state: success`. Because `StatusHandler` has no repository scoping, Shipit will record this forged status against the target commit.

This directly undermines Shipit's `ci.require`/`ci.blocking` gating (`Shipit::DeploySpec#required_statuses`/`blocking_statuses`), which continuous delivery and the merge queue rely on to decide whether a commit is deployable/mergeable. Forging a "success" status on a commit that never actually passed CI can cause `Stack#trigger_continuous_delivery` to autonomously deploy that commit — an unauthorized deploy, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitability depends on at least one organization/app configuration in the Shipit deployment having no `webhook_secret` set — a configuration explicitly shown as acceptable in the shipped example secrets files, so it is a realistic, in-scope, documented operating mode rather than a misconfiguration outside the threat model. No GitHub App key, session, `ApiClient` token, or repository write access is required — only knowledge of a target commit SHA (trivially obtainable for any public repository) and the target organization login name (also public). This is a fully unauthenticated network attacker path.

### Recommendation
- Scope `StatusHandler` (and any other handler that writes state keyed by commit/sha) to the repository/stacks resolved from `repository.full_name`, the same way `PushHandler` does via `Handler#stacks`, instead of matching `Commit.where(sha:)` globally.
- Make `verify_webhook_signature` fail closed: do not treat a blank `webhook_secret` as an automatic pass; either require a secret to be configured for every organization or explicitly document/enforce that unsecured webhooks must additionally be scoped/rejected per-repository.
- After selecting `github_app` for signature verification based on `repository_owner`, re-validate downstream that the repository/commit being mutated actually belongs to that same verified organization before applying any writes.

### Proof of Concept
Preconditions: Shipit instance configured with at least one GitHub organization entry lacking `webhook_secret` (a documented valid configuration), and hosting two unrelated stacks, e.g. `OrgA/repoA` (secretless) and `OrgB/repoB` (the actual target, with commit `deadbeef...` that has a failing/blocking required status).

```
POST /github/webhooks
X-Github-Event: status
Content-Type: application/json
(no valid X-Hub-Signature needed because OrgA has no webhook_secret)

{
  "sha": "deadbeef...",                // commit belonging to OrgB/repoB
  "state": "success",
  "context": "ci/blocking-check",
  "repository": { "owner": { "login": "OrgA" } }   // used only to select the (secretless) verifier
}
```

`verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `verify_webhook_signature` returns `true` unconditionally (blank secret). `StatusHandler#process` then executes `Commit.where(sha: "deadbeef...").each { |c| c.create_status_from_github!(params) }`, writing a forged "success" status onto OrgB's commit regardless of the fact that the "verified" organization was OrgA. If OrgB's stack has `continuous_deployment: true` and this status satisfies its `required_statuses`, the next `trigger_continuous_delivery` cycle deploys the commit. [7](#0-6)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
