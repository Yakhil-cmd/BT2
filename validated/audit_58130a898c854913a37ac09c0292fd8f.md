### Title
Webhook Signature is Verified Against the Payload's `repository.owner.login`, but Handlers Act on the Independently-Attacker-Controlled `repository.full_name` - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a request against using `repository_owner`, which is read from `repository.owner.login` (falling back to `organization.login`) in the JSON body. Once the HMAC check passes, the raw payload is dispatched to handlers that instead resolve the target repository from a *different* field of the same payload — `repository.full_name` — with no check that this field's owner matches the organization whose secret authenticated the request.

### Finding Description
`verify_signature` picks the GitHub App config to verify against based on the attacker-controlled field `repository.owner.login`/`organization.login`: [1](#0-0) [2](#0-1) 

Shipit supports multiple organizations, each with its own independently configured `webhook_secret` (`config/secrets.yml`/`lib/shipit/github_app.rb`), and this is a documented multi-tenant configuration: [3](#0-2) [4](#0-3) 

Once the signature check succeeds, `create` hands the *entire raw payload* — unmodified — to the event handlers: [5](#0-4) 

Every handler resolves which `Stack`/`Repository` to act on via `Handler#repository_name`, which reads `repository.full_name` — a field completely independent from the `repository.owner.login`/`organization.login` field used for signature-org selection: [6](#0-5) 

Concrete example — `PushHandler` uses this `repository_name` binding to locate stacks and trigger a GitHub sync on them: [7](#0-6) 

**The broken binding, stated as an equality that the code never enforces:**
`organization authenticated (repository.owner.login used to pick the webhook_secret)` == `repository actually written to (repository.full_name used by Handler#repository_name)`.

The HMAC only proves "this byte-for-byte payload was signed by the secret belonging to the organization named in `repository.owner.login`." It does **not** prove that `repository.full_name` belongs to that same organization. An attacker who legitimately installs the Shipit GitHub App on their own organization ("OrgA", with its own valid `webhook_secret`) can freely construct and correctly sign a payload where `repository.owner.login = "OrgA"` (so `verify_signature` picks and validates against OrgA's secret) while `repository.full_name = "OrgB/victim-repo"` (a completely different, unrelated repository/organization also tracked by the same Shipit instance).

### Impact Explanation
Because the two fields are never cross-checked, a webhook that is cryptographically "valid" only for OrgA is accepted and then dispatched with a forged `repository.full_name` pointing at OrgB's repository. Every handler that resolves stacks via `Handler#repository_name` (push, status, check_suite, pull_request/*, merge, deployable_status, membership, etc.) will act on OrgB's stacks as if the event genuinely originated from OrgB. This is a cross-repository write: an attacker who only controls their own org's GitHub App installation can forge commit statuses, trigger `GithubSyncJob` syncs, manipulate pull-request-driven review-stack state, or alter merge/deploy-relevant status for repositories they have no access to and whose webhook secret they never possessed — satisfying the "cross-repository writes" Critical-impact criterion.

### Likelihood Explanation
Likelihood is high in any deployment that follows the documented multi-organization configuration pattern (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`), since the attacker only needs to control (or install the app on) a single low-value organization to obtain a legitimate `webhook_secret`, then can freely target any other repository tracked by the same Shipit instance by simply changing `repository.full_name` in the otherwise-correctly-signed payload. No Shipit account, `ApiClient` token, or GitHub write access to the victim repo is required — only network access to `POST /webhooks`.

### Recommendation
After signature verification, re-derive the authenticated organization and assert that `repository.full_name`'s owner (i.e., the org segment of `full_name`) equals `repository_owner`/the org whose secret validated the request, rejecting (422) any mismatch before dispatching to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `app/controllers/shipit/webhooks_controller.rb`.

### Proof of Concept
1. Attacker installs the Shipit GitHub App on their own org "OrgA" and obtains OrgA's `webhook_secret` (legitimately configured for their org in the multi-org `config/secrets.yml`).
2. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. Attacker computes `sha1=HMAC(OrgA_webhook_secret, raw_body)` and sends `POST /webhooks` with header `X-Hub-Signature` set to that value and `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")` (from `repository.owner.login`) and validates the signature successfully — `head(422)` is never triggered. [1](#0-0) 
5. `create` passes the full payload to `PushHandler`, which resolves the target via `repository.full_name = "OrgB/victim-repo"` and calls `stack.sync_github(expected_head_sha: params.after)` for OrgB's tracked stack — a repository the attacker never had signature-verified access to.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
