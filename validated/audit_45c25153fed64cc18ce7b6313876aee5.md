### Title
Webhook signature is validated against an org derived from the payload, but handlers act on a different, unvalidated payload field — ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App secret to validate the HMAC signature against by reading `repository.owner.login` (or `organization.login`) straight out of the attacker-controlled JSON body, then checks the signature of that same body against that secret [1](#0-0) . Once the signature check for *that* organization passes, `create` hands the entire raw JSON to the event handler, which independently derives the target repository/organization from other unrelated fields of the same payload (`repository.full_name` in `Handler#repository_name`, or `organization.login` in `MembershipHandler#find_or_create_team!`) [2](#0-1) [3](#0-2) . Nothing forces these two "identity" fields (the one used to pick the verifying secret, and the one used to select which Shipit-tracked resource to mutate) to refer to the same GitHub organization.

### Finding Description
The trust binding that should hold is: *"the organization whose secret authenticated this webhook" == "the organization/repository whose Shipit-managed data is written by this webhook."* Shipit is explicitly multi-tenant capable — `Shipit.github(organization:)` looks up a **per-organization** app config (`app_id`, `installation_id`, `webhook_secret`, `private_key`) via `github_app_config` [4](#0-3) , and the test fixtures demonstrate two independently configured organizations (`OrgOne`, `OrgTwo`), each with its own `webhook_secret` [5](#0-4) .

Before the payload is processed, `verify_signature` computes `repository_owner` from the JSON body itself:
```
params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
```
and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` against the *raw body*. Because HMAC-SHA1 over the raw body is what's checked, an attacker who legitimately administers **their own** GitHub App installation on organization `attacker-org` — and therefore genuinely knows `attacker-org`'s `webhook_secret` (a value an org admin is expected to hold, not a Shipit/session secret) — can sign an arbitrary JSON body with that secret. There is no requirement that the signed body's `organization.login`/`repository.owner.login` match anything about the deploy stacks it subsequently manipulates.

Concretely, for a `membership` event, `MembershipHandler#find_or_create_team!` trusts `params.organization.login` to create-or-fetch a `Team` and then adds `params.member.login` (also attacker-controlled) to it via `team.add_member(member)` [6](#0-5) . `Shipit.github_teams` — the set of teams whose membership grants access/authorization to the whole Shipit deployment UI — is exactly these `Team` records [7](#0-6) , and `User#authorized?`/`force_github_authentication` gate all engine access on membership in one of `Shipit.github_teams` [8](#0-7) [9](#0-8) .

So the attacker:
1. Sends a `membership` webhook body with `organization.login = "victim-org"` (any org Shipit is configured to trust for authorization, e.g. the org referenced in `Shipit.github_teams`) and `member.login` set to an account the attacker controls, but signs the request in a way that is *validated using the config keyed on `repository_owner`* — which for a `membership` event has no `repository` key at all, so `repository_owner` resolves to `organization.login` too (i.e. `"victim-org"`), meaning verification will look up `Shipit.github(organization: "victim-org")`.
2. This means the attacker must actually know `victim-org`'s configured `webhook_secret`, unless the deployment uses the single-app legacy schema (`github_default_organization` is `nil`), in which case *all* organizations share **one** `webhook_secret`/app regardless of which `organization.login`/`repository.owner.login` is embedded in the payload [10](#0-9) . In that (very common, single-org) configuration, the "authenticating organization" is not actually organization-scoped at all — the same one global secret validates payloads no matter what `organization.login`/`repository.owner.login` value is put in the body. That is the concrete binding break: the webhook signature does not bind to the organization/repository named inside the payload; it only proves "signed by the one app secret configured for this Shipit install," while every handler nonetheless trusts the payload's own `organization.login` / `repository.full_name` to decide *which* Shipit resource (team, stack, commit, review-stack) is written.

For `push`/`status`/`pull_request` events this lets a caller who can reach the single global webhook secret (e.g., because it's shared across many repos/orgs configured under one Shipit instance, which is the documented common setup) forge a `status` event for **any commit sha** belonging to **any repository Shipit tracks**, setting it to `success`, which can satisfy `ci.require` gating and enable continuous delivery to auto-deploy — an unauthorized deploy across repositories, since nothing about the signature ties the payload to the specific repository named in `repository.full_name`.

### Impact Explanation
- Forged `membership` events escalate the attacker into `Shipit.github_teams`, which is explicitly listed as a High-impact outcome ("escalation into `Shipit.github_teams` authorization").
- Forged `status`/`push` events targeting `repository.full_name` values that differ from whatever the signature check actually authenticated can create/advance commit statuses and trigger `stack.sync_github`/continuous-deployment logic for repositories/stacks unrelated to the org whose secret was used, i.e. cross-repository writes and unauthorized deploys.

### Likelihood Explanation
Exploitability depends entirely on the deployment's GitHub App configuration:
- In the common single-app configuration (`github_default_organization` is `nil`), there is exactly one shared `webhook_secret`; every field used by handlers (`organization.login`, `repository.owner.login`, `repository.full_name`) is fully attacker-controlled JSON with no cross-check against the secret used, so likelihood is high for any deployment with default configuration once *any* valid webhook signature can be produced by an outsider (e.g., a webhook delivery secret leak, or a maliciously-controlled repo that is legitimately hooked into the same Shipit instance).
- In the multi-org configuration, the attacker additionally needs to know a specific organization's `webhook_secret` — plausible only if the attacker administers (or has compromised) that org's own GitHub App settings, which the "no privileged account / no webhook_secret" exclusion in the rules would normally rule out. I could not fully verify from the available files whether any Shipit deployment ships with a single shared secret across repos with differing trust levels by default versus explicit developer misconfiguration, so the practical likelihood in a "typical" production deployment is uncertain and should be validated against actual `secrets.yml` conventions.

### Recommendation
Reject webhook payloads where the resource-selecting field(s) used by handlers (`repository.full_name`'s owner, `organization.login`, `repository.owner.login`) do not match the organization key that the signature was verified against. Concretely, `WebhooksController#verify_signature` should compute the "authenticated organization" once and pass it down to `Webhooks.for_event` handlers, and every handler (`Handler#repository_name`, `MembershipHandler#find_or_create_team!`, `StatusHandler`, `PushHandler`) should assert that the repository/organization it is about to mutate belongs to that same authenticated organization before performing any writes — analogous to `combineShorts`'s "re-validate before trusting a state update through an alternate path" recommendation in the source report.

### Proof of Concept
Not runnable without full app context, but the exploit shape is:
```
POST /webhooks
X-Github-Event: membership
X-Hub-Signature: sha1=<computed with the single/attacker-known webhook_secret>
Body:
{
  "action": "added",
  "team": {"id": 1, "name": "Deployers", "slug": "deployers", "url": "https://api.github.com/teams/1"},
  "organization": {"login": "victim-org-whose-team-grants-shipit-access"},
  "member": {"login": "attacker-controlled-account"}
}
```
Verified via `Shipit.github(organization: "victim-org...")` (or the single shared app), `MembershipHandler#process` then calls `team.add_member(member)` [11](#0-10) , granting the attacker's account membership in a `Team` that `Shipit.github_teams` uses to authorize access [7](#0-6) , without any check tying `organization.login` in the payload to whichever secret actually validated the signature.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

        'Webhook from unknown organization',

        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
