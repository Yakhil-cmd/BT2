### Title
Zero-Staking Proposer with Registered CL Pool Causes Division-by-Zero Panic in Block Finalization — (`kaiax/staking/staking_info.go`)

### Summary

`consolidatedNode.Split()` divides by `totalAmount = cnAmountBig + clAmountBig` without guarding against the case where both the CNStaking amount and the CLStaking amount are zero. When a block proposer has `StakingAmount = 0` and `CLStakingInfo.CLStakingAmount = 0` (both amounts round down to zero after integer division by `params.KAIA`), the call to `big.Int.Div(..., totalAmount)` panics at block finalization, halting the chain.

### Finding Description

In `kaiax/staking/staking_info.go`, the `consolidatedNode.Split()` function splits a reward amount proportionally between a validator's CNStaking and CL pool: [1](#0-0) 

The divisor `totalAmount` is the sum of `c.StakingAmount` (CNStaking, in KAIA) and `c.CLStakingInfo.CLStakingAmount` (CL pool staking, in KAIA). Both values are `uint64` fields populated by integer division of the raw kei balance by `params.KAIA` (1e18): [2](#0-1) 

Any staking contract or CL pool holding fewer than 1 KAIA (< 1e18 kei) produces a truncated value of `0`. If both fields are zero simultaneously, `totalAmount = 0` and `clAmount.Div(clAmount, totalAmount)` panics with a Go runtime division-by-zero.

`Split()` is called unconditionally for the block proposer's reward in both `specWithProposerAndFunds` and `specWithProposerAndFundsFlex`, with no guard on `totalAmount`: [3](#0-2) [4](#0-3) 

These functions are invoked during `FinalizeState` for every block after the Prague hardfork when the proposer has a registered CL pool.

### Impact Explanation

A panic in `FinalizeState` during block finalization causes every honest node to crash when processing the block where the affected validator is the proposer. Because all nodes execute the same deterministic state transition, all nodes crash simultaneously, halting the chain. The corrupted value is the block finalization itself — the block is never committed to the canonical chain, and no rewards are distributed.

This matches the allowed impact: **invalid state transition / consensus divergence on honest nodes**.

### Likelihood Explanation

The `generateProposerListWeighted` function explicitly guarantees that a validator with zero staking still receives `weight = 1` and appears in the proposer list: [5](#0-4) 

The test suite confirms this behavior: [6](#0-5) 

A validator can reach the vulnerable state by:
1. Withdrawing all KAIA from their CNStaking contract (no governance required), causing `StakingAmount = 0` after the next staking snapshot.
2. Having a registered CL pool with < 1 KAIA (e.g., a freshly registered pool with no deposits, or one from which all KAIA has been withdrawn), causing `CLStakingAmount = 0`.
3. Being selected as a block proposer — guaranteed by `weight = 1` even with zero staking.

The existing test case `"2 nodes under minStaking have CLs"` already demonstrates a node with `StakingAmount = a0 = 0` and a non-nil `CLStakingInfo`: [7](#0-6) 

This is a single-validator action requiring no collusion.

### Recommendation

Add a zero-denominator guard in `consolidatedNode.Split()`:

```go
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    if c.CLStakingInfo == nil {
        return amount, big.NewInt(0)
    }

    var (
        cnAmountBig = big.NewInt(int64(c.StakingAmount))
        clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
        totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
    )

    // Guard: if both staking amounts are zero, all reward goes to CN.
    if totalAmount.Sign() == 0 {
        return amount, big.NewInt(0)
    }

    clAmount := new(big.Int).Mul(clAmountBig, amount)
    clAmount = clAmount.Div(clAmount, totalAmount)
    cnAmount := new(big.Int).Sub(amount, clAmount)
    return cnAmount, clAmount
}
```

Additionally, consider adding a minimum staking requirement in the CLRegistry contract to prevent registration of CL pools with zero staking, and enforce that a validator's CNStaking must remain above a minimum threshold to stay in the AddressBook.

### Proof of Concept

**Setup (Prague hardfork active, WeightedRandom proposer policy):**

1. Validator V is registered in the AddressBook with staking contract S.
2. Validator V registers CL pool P in the CLRegistry.
3. Validator V withdraws all KAIA from S → `StakingAmount = 0` in next staking snapshot.
4. CL pool P holds 0.5 KAIA (5e17 kei) → `CLStakingAmount = Div(5e17, 1e18) = 0`.

**Trigger:**

5. `generateProposerListWeighted` assigns V `weight = 1` (guaranteed minimum), so V appears in the proposer list.
6. V is selected as block proposer for block N.
7. `FinalizeState(block N)` → `getDeferredRewardFull` → `specWithProposerAndFunds` → `cn.Split(proposer)`.
8. Inside `Split`: `cnAmountBig = 0`, `clAmountBig = 0`, `totalAmount = 0`.
9. `clAmount.Div(clAmount, totalAmount)` → **Go runtime panic: integer divide by zero**.
10. All nodes crash. Chain halts at block N−1. [8](#0-7) [9](#0-8) [10](#0-9)
