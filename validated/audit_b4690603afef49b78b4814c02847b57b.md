### Title
Signature-authenticated organization does not bind to the repository/commit acted upon in `StatusHandler`, allowing cross-repository forged CI status to trigger unauthorized deploys - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) validates the inbound webhook based solely on `repository.owner.login` (or `organization.login`) taken from the attacker-supplied JSON body itself, not from any GitHub-authenticated identity outside the payload. The `StatusHandler` that processes `status` events then locates the target `Commit` **globally by `sha` only**, with no scoping to the repository or organization that was used to select the signing secret: [4](#0-3) [1](#0-0) 

In a multi-organization Shipit deployment (the documented `github: { orgA: {...}, orgB: {...} }` config style, see `docs/setup.md` "Using Multiple Github Applications" and `lib/shipit.rb#github`), each organization can have its own, independently optional `webhook_secret`: [5](#0-4) 

Because `verify_webhook_signature` returns `true` unconditionally when `webhook_secret` is blank for the selected organization, an attacker who knows (or controls) an org with no configured secret can send an arbitrary JSON body that:
1. sets `repository.owner.login` / `organization.login` to the secret-less org (so `verify_signature` picks that org's `GitHubApp` and short-circuits to `verified = true`), while
2. providing a `sha` value belonging to a commit that actually belongs to a **different**, victim stack/organization (the binding the equality check should have enforced: "organization authenticated" == "repository/commit acted on").

Since `StatusHandler#process` never checks `repository.full_name` against the commit's actual stack, it happily creates a forged `success` status on the victim's commit.

### Finding Description
`verify_signature` derives the authenticating organization entirely from body fields (`params.dig('repository','owner','login')`), then calls `Shipit.github(organization: repository_owner)` to fetch a `GitHubApp` whose `webhook_secret` is used to validate `X-Hub-Signature`: [6](#0-5) [7](#0-6) 

`GitHubApp#verify_webhook_signature` treats a blank `webhook_secret` as automatically verified: [5](#0-4) 

The multi-org configuration format explicitly allows independent, optional secrets per organization: [8](#0-7) [9](#0-8) 

`Shipit::Webhooks::Handlers::StatusHandler#process` then acts on `Commit.where(sha: params.sha)` — a **global**, unscoped lookup, not filtered by the `repository` object or by the organization the signature check selected: [10](#0-9) 

Creating a `success` `Status` on a commit calls `commit.stack.enable_ci!` and `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` if the target stack has `continuous_deployment` enabled — directly causing `Stack#trigger_continuous_delivery` to build and run a deploy once the (forged) status makes the commit `deployable?`: [2](#0-1) [3](#0-2) [11](#0-10) 

The security-relevant equality the engine should enforce is: *organization that authenticated the request == organization/repository whose state the handler mutates*. That equality is broken because (a) the authenticating org is picked from a self-reported field with an independently-optional secret, and (b) the mutation target (`Commit.where(sha: ...)`) ignores organization/repository scoping entirely, relying on `sha` collision alone across the whole Shipit instance.

### Impact Explanation
An unprivileged network attacker with no Shipit session, no `ApiClient` token, and no legitimate webhook secret can, in a multi-organization Shipit deployment where at least one configured organization omits `webhook_secret` (a documented, supported configuration), forge a `status` webhook event that:
- Impersonates GitHub CI for a victim stack belonging to a *different*, secret-protected organization, by supplying that victim's real commit `sha`.
- Marks the commit `success`, making it `deployable?`.
- If the victim stack has `continuous_deployment` enabled, triggers an actual unauthorized deploy via `ContinuousDeliveryJob` / `Stack#trigger_continuous_delivery`.

This is an unauthorized deploy triggered purely by exploiting the mismatch between the field used for signature-organization selection and the field used for target-commit selection — meeting the Critical impact bar ("an unauthorized deploy").

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with multiple GitHub organizations where at least one has no `webhook_secret` set — an explicitly documented and supported configuration, not a misconfiguration outside the engine's design; (2) knowledge of a target commit `sha` for the victim stack, which is routinely public (commit SHAs appear in GitHub UI, PRs, CI logs, and are not secret). No credentials, sessions, or webhook secrets for the victim organization are needed. Likelihood is Medium-High wherever the multi-org, mixed-secret configuration is used.

### Recommendation
Scope the `StatusHandler` (and other handlers relying on cross-cutting lookups like `sha`) to the repository/organization that was actually authenticated in `verify_signature`, e.g., require that `Commit.where(sha: params.sha)` be additionally filtered through `stacks` (which is derived from `repository.full_name`) as `Handler#stacks` already does for other handlers, rather than querying `Commit` directly and globally. Additionally, either require `webhook_secret` to be mandatory for every configured organization, or ensure that an organization with no secret cannot be used to authenticate requests that reference resources belonging to a different, secret-protected organization.

### Proof of Concept
1. Configure Shipit with two organizations in `secrets.yml`: `victim-org` (with a real `webhook_secret`) and `attacker-org` (with `webhook_secret` left blank), per the documented multi-app format.
2. Attacker POSTs to `/webhooks` with `X-Github-Event: status`, no valid `X-Hub-Signature` (or an arbitrary one), and body:
```json
{
  "sha": "<real sha of a commit belonging to victim-org's continuously-deployed stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
3. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches that org's `GitHubApp`, whose blank `webhook_secret` causes `verify_webhook_signature` to return `true` unconditionally.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim's commit (unscoped by repository), and calls `create_status_from_github!`, creating a `success` status.
5. If the victim stack has `continuous_deployment` enabled, `schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, which triggers `trigger_continuous_delivery` and deploys the commit — an unauthorized deploy achieved without any credential belonging to the victim organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
