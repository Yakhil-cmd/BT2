## Title
Webhook signature verification binds to an attacker-chosen organization while handlers act on an unverified repository field, enabling cross-tenant webhook forgery and unauthorized deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate a webhook against using a field taken directly from the *unverified* JSON body (`repository.owner.login` or `organization.login`), not from any value that is itself covered by the HMAC binding to a specific tenant. Once that check passes, the event handlers act on a *different* unverified field from the same body — `repository.full_name` — to decide which `Stack`s, `Commit`s, or `Team`s to mutate. Because Shipit supports multiple organizations each with its own `webhook_secret` [1](#0-0) , an attacker who legitimately administers one onboarded organization (and therefore knows its `webhook_secret`) can forge a signature that Shipit accepts for its own organization while pointing the payload's `repository.full_name` at a victim organization's stack.

### Finding Description
`verify_signature` derives the organization used to pick the GitHub App / secret purely from the incoming JSON, before the signature has been checked: [2](#0-1) [3](#0-2) 

`Shipit.github(organization:)` looks up a per-organization config/secret keyed by that attacker-supplied string: [1](#0-0) 

The HMAC only proves "whoever crafted this payload knows organization X's `webhook_secret`" — it says nothing about which repository the *rest* of the payload refers to. Every downstream handler, however, resolves the target `Stack`/`Repository`/`Commit`/`Team` from a *different* attacker-controlled field of the same JSON body:
- `Handler#repository_name` reads `payload.dig('repository', 'full_name')` to find stacks: [4](#0-3) 
- `PushHandler#process` triggers `stack.sync_github` for any stack matching that repository/branch: [5](#0-4) 
- `StatusHandler#process` writes a commit status onto any `Commit` matching the attacker-supplied `sha`, with no repository/stack scoping at all: [6](#0-5) 
- `MembershipHandler#process` creates/updates `Team`/`User` records from `organization.login` in the body: [7](#0-6) 

Nothing ties the `repository.owner.login`/`organization.login` used for signature selection to the `repository.full_name`/`sha`/`organization.login` values the handlers actually act on — they are independent fields inside the same JSON body an attacker fully controls. An attacker who is a legitimate owner of their own organization "OrgA" (with its own configured `webhook_secret`) can:
1. Set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` selects OrgA's `GitHubApp` and secret — which the attacker knows.
2. Compute a valid `X-Hub-Signature` over the full raw body using OrgA's secret.
3. Set `repository.full_name` to `"OrgB/victim-repo"` (or an arbitrary `sha` in the `status` event) so the handler operates on OrgB's stack/commit.

This breaks the binding **"an organization that authenticated versus the repository that is written."**

### Impact Explanation
This lets a tenant that owns one organization on a shared Shipit instance forge events for any other tenant's repository:
- Forged `push` events trigger `sync_github` against a victim's stack.
- Forged `status` events call `commit.create_status_from_github!` on an arbitrary commit by `sha` with an attacker-chosen `state` (e.g. `success`), which feeds Shipit's deployability/continuous-delivery checks — a path toward an **unauthorized deploy** if the victim stack relies on commit-status-based CI gating for continuous deployment.
- Forged `membership` events create/mutate `Team`/`User` records tied to arbitrary organizations.

This matches the required High/Critical impact categories (unauthorized deploy / cross-repository writes) because it lets an attacker who controls no more than their own organization's webhook secret write state belonging to a repository/stack they do not own.

### Likelihood Explanation
Requires only that the attacker legitimately controls (or has compromised) one organization/GitHub App installation configured on a multi-tenant Shipit deployment (i.e., `secrets.github` has multiple organization keys, as supported by `Shipit.github_organizations` / `github_app_config`) — no privileged Shipit account, `ApiClient` token, or GitHub write access to the victim repo is needed. On single-organization deployments (the common case, `github_default_organization` returning `nil`) this analog does not apply, which somewhat limits likelihood, but for any multi-tenant configuration it is directly and repeatedly exploitable.

### Recommendation
Verify the webhook signature using the organization/repository derived consistently with the identity actually authorized for that data, and cross-check that the field used for secret selection (`repository.owner.login`/`organization.login`) matches the field the handlers act on (`repository.full_name`, commit ownership, etc.) before dispatching to handlers. Reject payloads where these fields are inconsistent with the resolved GitHub App/organization.

### Proof of Concept
1. Attacker is an authorized admin of `OrgA`, one of several organizations configured in `secrets.github` on a shared Shipit instance, and knows `OrgA`'s `webhook_secret`.
2. Attacker crafts a `status` (or `push`) webhook JSON body where `repository.owner.login = "OrgA"` but `sha` matches a commit belonging to `OrgB`'s stack (or, for `push`, `repository.full_name = "OrgB/victim-repo"`).
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(body, OrgA_webhook_secret)>` and POSTs to `/github/webhooks`.
4. `WebhooksController#verify_signature` resolves `Shipit.github(organization: "OrgA")` and successfully verifies the signature — see `app/controllers/shipit/webhooks_controller.rb:24-49`.
5. `Shipit::Webhooks.for_event('status').each { |handler| handler.call(params) }` runs `StatusHandler#process`, which looks up `Commit.where(sha: params.sha)` — belonging to `OrgB` — and calls `commit.create_status_from_github!(params)` with attacker-chosen `state`, `context`, and `description`, despite the attacker never having proven any relationship to `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
