### Title
Cross-organization team-membership escalation via unvalidated `team.id` lookup in `membership` webhook handler - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` only proves that the request body's `repository.owner.login` (falling back to `organization.login`) matches the organization whose `webhook_secret` produced the HMAC — it never proves that the *other* identifying field in the same body, `team.id`, actually belongs to that signing organization. `MembershipHandler#find_or_create_team!` looks up teams purely by GitHub's numeric `github_id` and only assigns `organization`/other attributes inside the `create` block, which is skipped whenever a `Team` row with that `github_id` already exists. Any organization legitimately configured in Shipit (multi-tenant `secrets.github` config) can therefore self-sign a `membership` webhook naming its own org, but pointing `team.id` at a pre-existing `Team` belonging to a different organization (e.g., one of the teams in `Shipit.github_teams`), and add an arbitrary attacker-controlled login to that team.

### Finding Description
The broken binding, stated as an equality that the code implicitly assumes but never checks:

`Team.find_by(github_id: params.team.id).organization == params.organization.login`

This equality is **not enforced** for existing `Team` rows.

Code path:
1. `WebhooksController#verify_signature` computes `repository_owner` from the payload (`params.dig('repository','owner','login') || params.dig('organization','login')`) and fetches that organization's `GitHubApp` via `Shipit.github(organization: repository_owner)`, then checks `verify_webhook_signature(signature, raw_post)` against **that org's** `webhook_secret`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` is a plain HMAC-SHA1 comparison with no nonce, timestamp, or content binding beyond the raw bytes. [3](#0-2) 
3. Because the same `organization.login` field both selects the verifying secret and is later trusted by the handler, an attacker who legitimately controls a second organization configured in Shipit (a supported multi-tenant scenario, evidenced by `test/dummy/config/secrets_double_github_app.yml` and `config/secrets.development.shopify.yml` supporting multiple `github:` orgs) can produce a **validly signed** payload where `organization.login` / `repository.owner.login` = their own org, but `team.id` = the real GitHub team ID of a team belonging to an unrelated organization (team IDs are numeric GitHub identifiers, discoverable via the public API or a previously observed legitimate webhook, per the question's own premise).
4. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }`. If a `Team` with that `github_id` already exists (e.g., pre-seeded via `Shipit.github_teams` at boot, which calls `Team.find_or_create_by_handle` for every configured `oauth.teams` entry), the block is **skipped entirely** — the found team's real `organization` is never compared to the attacker's self-signed `organization.login`. [4](#0-3) [5](#0-4) 
5. `User.find_or_create_by_login!(params.member.login)` creates/fetches a `User` for the attacker's own GitHub login, and `team.add_member(member)` creates a `Shipit::Membership` linking the attacker to the found team — a team the attacker's signing organization has no relationship to. [6](#0-5) 

Existing guards do not stop this: `drop_unhandled_event` only checks the event name exists in the handler map, `ExplicitParameters` (`params do ... end` block) only validates types/presence of `team.id`, `organization.login`, `member.login`, not cross-field consistency, and `verify_signature` validates the wrong binding (org ↔ secret) instead of the one that matters (org ↔ team). [7](#0-6) 

### Impact Explanation
If the targeted `Team` is one of the teams listed in `Shipit.github_teams` (the authorization allow-list), the attacker becomes a member of it and `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) returns true for the attacker's account, granting them full Shipit access (viewing stacks, tasks, deploy output, and — depending on further permission checks — triggering deploys). [8](#0-7) [9](#0-8)  This is repeatable against any team whose `github_id` the attacker can learn and which already has a `Team` row in Shipit's database, across any tenant, as long as the attacker legitimately owns one configured organization in the multi-tenant `secrets.github` hash. This matches the "High — escalation into `Shipit.github_teams` authorization" impact category.

### Likelihood Explanation
Preconditions: Shipit must be configured with more than one GitHub organization (a documented, supported configuration — see `secrets_double_github_app.yml`), and the attacker must legitimately administer one of those secondary organizations (own its `webhook_secret`, which is normal for a self-service/multi-tenant Shipit deployment). The attacker also needs the numeric `github_id` of the target team, obtainable via GitHub's public team API for public teams or by observing any prior legitimate `membership` webhook payload. Given these are realistic in an intentionally multi-tenant Shipit install, the attack is low-cost and fully repeatable (one HTTP POST per exploitation attempt, no rate limiting bypass needed).

### Recommendation
In `MembershipHandler#find_or_create_team!`, validate that the found (not just newly created) `Team#organization` equals `params.organization.login` (and ideally that `repository_owner`/signing organization equals it too) before calling `team.add_member`/`team.members.delete`; reject the event (e.g., raise/log and no-op) on mismatch instead of silently trusting the pre-existing record.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (no live GitHub, real HMAC computed against a second org config):

```ruby
test ":membership from a different org can hijack an existing team's membership" do
  # Simulate a Shipit deployment with two configured orgs: "shopify" (owns shipit_teams(:shopify_developers))
  # and "attacker-org" (attacker legitimately owns this org's webhook_secret).
  Shipit.stubs(:secrets).returns(
    github: {
      shopify: { webhook_secret: 'shopify-secret' },
      'attacker-org': { webhook_secret: 'attacker-secret' }
    }
  )

  team = shipit_teams(:shopify_developers) # pre-existing Team row, real github_id, organization: 'shopify'

  forged_body = {
    action: 'added',
    team: { id: team.github_id, name: team.name, slug: team.slug, url: team.api_url },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  signature = "sha1=#{OpenSSL::HMAC.hexdigest('sha1', 'attacker-secret', forged_body)}"

  @request.headers['X-Github-Event'] = 'membership'
  @request.headers['X-Hub-Signature'] = signature

  assert_difference -> { team.reload.members.count }, 1 do
    post :create, body: forged_body, as: :json
    assert_response :ok
  end

  assert_includes team.members.map(&:login), 'attacker'
  # Equality that should have held but doesn't:
  # Team.find_by(github_id: team.github_id).organization == 'attacker-org' -> false, yet membership was still created.
end
```

This demonstrates a real (not stubbed) signature verification succeeding for `attacker-org`, while the handler still mutates a `shopify`-owned `Team`, proving the binding failure.

      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
