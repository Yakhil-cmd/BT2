### Title
Webhook signature routing key (`repository.owner.login`/`organization.login`) is never bound to the repository actually acted upon (`repository.full_name`) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` picks *which* GitHub App/organization config (and therefore which `webhook_secret`) to verify the inbound webhook against based on `repository.owner.login` (or `organization.login`) taken straight out of the unauthenticated JSON body. But the handler that actually acts on the payload (`Shipit::Webhooks::Handlers::Handler#stacks` / `#repository_name`) resolves the target `Repository`/`Stack` from an entirely different field of the same body: `repository.full_name`. Nothing ties these two fields together, so the "organization that authenticated" is never checked against the "repository that is written."

### Finding Description
`verify_signature` computes `repository_owner` and uses it purely to select the `GitHubApp` instance/secret to validate the signature with: [1](#0-0) [2](#0-1) 

Once the request passes that check, `create` dispatches the same raw JSON body to the matching event handler(s): [3](#0-2) 

Every handler resolves the affected `Stack`/`Repository` from `payload.dig('repository', 'full_name')`, a field completely independent of `repository.owner.login`: [4](#0-3) 

`PushHandler#process` then syncs any not-archived stack matching that repository/branch: [5](#0-4) 

Crucially, `verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured — a state explicitly supported and shown as the default in this engine's own setup docs and fixtures: [6](#0-5) [7](#0-6) 

This produces the exact binding break called out for this bug class: the equality that should hold — `organization that authenticated == repository/org that gets written` — never holds. An unprivileged party can craft a request where `repository.owner.login` (or `organization.login`) equals an organization whose `webhook_secret` is unset (a supported, documented configuration for self-hosted Shipit instances), and pass `verify_signature`, while `repository.full_name` names a completely unrelated repository/stack actually tracked by the Shipit instance. The handler layer only trusts `full_name`, with no cross-check against the value used for signature routing.

### Impact Explanation
Any handler keyed off `repository.full_name` (push, status, check_suite, pull_request handlers) is reachable this way for any Stack hosted on the instance, regardless of which org "owns" the webhook that was nominally verified. For `PushHandler` this forces `GithubSyncJob` to run against an arbitrary tracked stack/repository at a time of the attacker's choosing, resyncing commits and (where continuous delivery is enabled) triggering the stack's normal auto-deploy pipeline ahead of its intended schedule — an unauthorized deploy trigger crossing a repository boundary the attacker has no rights to. This satisfies the "unauthorized deploy" criterion without any Shipit session, `ApiClient` token, or GitHub write access — only knowledge of the two repository names is required, and the request succeeds precisely because the org used for signature selection is decoupled from the org/repo actually mutated.

### Likelihood Explanation
Exploitability is contingent on at least one organization configured on the Shipit instance having no `webhook_secret` set. This is not a hypothetical misconfiguration: it is the value shown by this engine's own `docs/setup.md`, `config/secrets.development.shopify.yml`, and `test/dummy/config/secrets.yml` templates (`webhook_secret: # nil`), meaning many real deployments plausibly run with signature verification effectively disabled for at least one tenant. Given that, the attack requires no secret, token, or session at all — just a raw POST to the public `/webhooks` endpoint with attacker-chosen JSON.

### Recommendation
Bind the two identities before dispatching to handlers: after (or as part of) `verify_signature`, assert that the `Repository` resolved from `repository.full_name` belongs to the same organization/owner used to select the GitHub App/secret (`repository.owner.login` / `organization.login`), and reject the webhook (422) on mismatch. Additionally, treat a missing `webhook_secret` for a configured organization as a hard misconfiguration warning (or refuse unsigned webhooks by default) rather than silently trusting the payload.

### Proof of Concept
1. Identify the Shipit instance's `/webhooks` endpoint and an organization `OrgA` configured on it without a `webhook_secret` (e.g., default/documented setup).
2. Identify the `full_name` of an unrelated, real tracked repository, `OrgB/target-repo`, hosted on the same Shipit instance.
3. Send:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything   (ignored, verify_webhook_signature returns true — no secret set for OrgA)

{
  "ref": "refs/heads/main",
  "after": "<any sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/target-repo"
  }
}
```
4. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` regardless of the header.
5. `PushHandler` resolves the target `Repository` via `repository.full_name = "OrgB/target-repo"`, enqueuing `GithubSyncJob` for `OrgB/target-repo`'s stacks even though the request was never authenticated by anything belonging to `OrgB`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
