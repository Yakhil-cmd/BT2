### Title
`X-Shipit-User` header lets any authenticated API client forge `current_user` attribution on write actions - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Shipit::Api::BaseController#identify_user` resolves `current_user` solely from the attacker-controlled `X-Shipit-User` HTTP header, looking up any existing `User` by login with no binding to the authenticated `ApiClient`. Because every write endpoint that stamps an actor (locks, deploys, rollbacks, tasks, merge requests, release statuses) uses this `current_user` rather than `current_api_client.creator`, a holder of any valid token with the relevant `write`/`deploy`/`lock` permission can attribute the resulting action to an arbitrary existing user.

### Finding Description
The claimed binding is: `current_user == current_api_client.creator` (the identity attributed to a write action should equal the identity that actually authenticated the request). This binding does not hold. `authenticate_api_client` only validates the `ApiClient` token via `BasicAuth.authenticate` / `ApiClient.authenticate(token)` [1](#0-0) . Separately, `current_user` is derived purely from the request header:

```
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
``` [2](#0-1) 

`require_permission!` only checks `current_api_client.check_permissions!`, never cross-validating `current_user` against the client's `creator`: `def require_permission!(operation, scope); current_api_client.check_permissions!(operation, scope); end` [3](#0-2) . `ApiClient#check_permissions!` only inspects the `permissions` array of the token owner, with no reference to `current_user` at all [4](#0-3) .

Multiple controllers use `current_user` for attribution on writes gated only by the token's stack-level permission:
- `LocksController#create`/`update`: `stack.lock(params.reason, current_user)` gated by `lock:stack` [5](#0-4) 
- `DeploysController#create`: `stack.trigger_deploy(commit, current_user, ...)` gated by `deploy:stack` [6](#0-5) 
- `RollbacksController#create`: `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` gated by `deploy:stack` [7](#0-6) 
- `TasksController#trigger`/`abort`: `stack.trigger_task(..., current_user, ...)` / `task.abort!(aborted_by: current_user)` gated by `deploy:stack` [8](#0-7) 
- `MergeRequestsController#update`: `MergeRequest.request_merge!(stack, params[:id], current_user)` gated by `deploy:stack` [9](#0-8) 
- `ReleaseStatusesController#create`: `deploy.report_healthy!/report_faulty!(user: current_user)` gated by `deploy:stack` [10](#0-9) 

Exploit flow: an attacker holding any `ApiClient` token that carries only the specific permission required by one of these endpoints (e.g. `deploy:stack` or `lock:stack` scoped to a stack they're allowed to touch) sends the request with header `X-Shipit-User: <victim-login>` where `<victim-login>` is any existing `User.login` (discoverable, e.g., via public GitHub org membership). The action (deploy trigger, rollback, lock, task trigger/abort, merge request request, release status) is executed and persisted with the victim's identity as the recorded actor, even though the victim never authenticated the request and the token's actual `creator` is someone else. `require_permission!` never checks that `current_user` corresponds to `current_api_client.creator`, so the forgery is not caught anywhere in the request lifecycle.

Note: the question's example of `POST /api/stacks/:id/hooks` does not map to an actual create action in `HooksController` in this codebase — hooks are read-only/webhook delivery targets and no `created_by`/`creator` write path was found there. The real, verified impact is on the write endpoints listed above (locks, deploys, rollbacks, tasks, merge requests, release statuses), which do stamp `current_user` on writes gated only by the API client's own scope, independent of `current_user`.

### Impact Explanation
This allows a spoofed-identity write against any stack the attacker's token is scoped to: deploys, rollbacks, task triggers/aborts, locks, merge request requests and release status reports can all be attributed to an arbitrary existing Shipit user rather than the actual token holder. This corrupts audit trails and actor-based authorization/attribution logic (e.g., `aborted_by`, `locked_by`, deploy/rollback initiator) and could be used to implicate an innocent admin in a malicious deploy/rollback, or to disguise the attacker's own actions. It does not itself grant permissions beyond what the attacker's token already has — the write must already be permitted by `current_api_client`'s own `permissions`/`stack_id` scope — so it is an identity-forgery / attribution-integrity issue on an already-authorized action rather than a full authentication bypass or cross-tenant escalation. This is repeatable against any stack/action combination the attacker's token is scoped for, and against any existing user login.

### Likelihood Explanation
Requires the attacker to already hold a valid `ApiClient` token with at least one of `lock:stack`, `deploy:stack`, etc. for a target stack — this is a real precondition, not "any unprivileged internet user." Given a token with such scope, forging the header costs nothing (a single extra HTTP header) and is trivially repeatable across requests, stacks, and target user logins as long as the `User` record exists.

### Recommendation
Do not trust `X-Shipit-User` as an independent identity source for privileged/write actions. Either remove header-based user identification for authenticated API write paths, or explicitly bind it: only honor `X-Shipit-User` when it matches `current_api_client.creator.login`, or require a dedicated `write:user`/impersonation permission on the `ApiClient` before allowing it to override the acting user, and always fall back to `current_api_client.creator` for attribution fields.

### Proof of Concept
Minitest plan (`test/controllers/api/locks_controller_test.rb`-style, no live GitHub):
1. Create `api_client_owner` (creator of the token) and `victim_admin` as two separate `User` fixtures.
2. Create an `ApiClient` with `creator: api_client_owner`, `permissions: ['lock:stack']`, scoped to a test `Stack`.
3. Send `POST /api/stacks/:id/lock` with valid Basic Auth token for that `ApiClient` and header `X-Shipit-User: victim_admin.login`.
4. Assert response succeeds (200/201) and that `stack.reload.lock_author` (or equivalent actor field set by `stack.lock(reason, current_user)`) equals `victim_admin`, not `api_client_owner`.
5. Assert `victim_admin` never authenticated (no session, no token) yet is recorded as the actor — demonstrating `current_user != current_api_client.creator` while both fields diverge and no guard rejects it.
