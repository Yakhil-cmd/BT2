## Analog Found

### Title
Autonomous Agents Can Never Spend Fixed-Denomination (Indivisible) Assets They Receive, Permanently Freezing Those Funds - (File: aa_composer.js)

### Summary
The external report describes tokens minted to `address(this)` in `DaosLive::finalize()` becoming permanently stuck because the contract provides no mechanism to move them out. The equivalent root cause exists in ocore's AA payment composer: any `payment` message an AA defines to spend a `fixed_denominations` (indivisible) asset is silently dropped before the response unit is built, so an AA can receive indivisible-asset coins from an unprivileged trigger sender but can never construct a valid output spending them back out. The funds sit at the AA's address indefinitely with no protocol path to release them.

### Finding Description
When an AA response is composed in `handleTrigger()` → `sendUnit()`, every payment message is inspected in `aa_composer.js`: [1](#0-0) 

For assets with `fixed_denominations`, the code explicitly comments `// will skip it later` and returns immediately without calling `completePaymentPayload`, meaning no inputs/outputs are ever assembled for that asset for this message. [2](#0-1) 

After the first pass, any payment message referencing a `fixed_denominations` asset is unconditionally filtered out of the final `messages` array. Unlike `is_private` assets, which are explicitly bounced with the error `"sending private asset from AA"` (line 1330), indivisible assets are removed with no bounce and no error — the AA simply proceeds as if that message never existed, silently swallowing the intended payout. The outputs the AA received of that asset remain in the `outputs` table, credited to the AA's address, but the composer's coin-selection helpers (`readStableOutputs` / `readUnstableOutputsSentByAAs`, used only for divisible assets in `completePaymentPayload`) are never invoked for fixed-denomination assets, and the indivisible-coin picker (`indivisible_asset.js`, used by regular wallets) is never called from the AA composer at all. [3](#0-2) 

The result: any unprivileged unit poster who sends an indivisible asset to an AA (a completely normal, protocol-permitted trigger payment) causes those coins to become permanently unspendable by that AA — there is no `finalize`-style parameter, no getter, and no code path that ever allows the AA to emit a valid indivisible-asset payment message, since every attempt is stripped before the unit is built.

### Impact Explanation
This is an AA fund-freezing bug reachable by any unprivileged trigger sender: simply sending a fixed-denomination asset to an AA address (e.g., as part of a swap/vault/exchange AA that is supposed to forward or refund such assets) permanently traps those funds at the AA address. No AA definition, however carefully written, can move fixed-denomination assets back out, because the composer strips such messages unconditionally at the protocol level (`aa_composer.js`), not due to a flaw in the specific AA's oscript logic. This mirrors the external report's core defect: value enters a contract-controlled address with an intended distribution mechanism, but the platform never actually executes a valid transfer out, so the funds are permanently locked.

### Likelihood Explanation
High likelihood: this triggers deterministically any time a trigger includes a `fixed_denominations` asset payment intended to be forwarded, refunded, or paid out by an AA, which is a documented, encouraged usage pattern (assets and AAs interacting via `payment` messages). No malicious or privileged actor is required — an ordinary user constructing a normal payment unit reaches this path.

### Recommendation
Either (a) explicitly reject/bounce AA response messages that attempt to pay out `fixed_denominations` assets (mirroring the existing `is_private` bounce at line 1330), so the AA author and trigger sender get clear, immediate feedback that the funds cannot be forwarded and should design around it, or (b) implement genuine indivisible-coin selection/composition support for AA-issued payments (reusing `indivisible_asset.js` semantics) so AAs can actually spend fixed-denomination assets they hold, closing the freezing gap.

### Proof of Concept
1. Define an asset with `fixed_denominations: true` (indivisible asset), as validated in `aa_validation.js` (`asset` message case, requiring `denominations`).
2. Define an AA whose response messages include a `payment` message with `asset` set to that fixed-denomination asset, intended to forward the received coins to `trigger.address`.
3. Send a trigger unit that includes an indivisible-asset payment output to the AA.
4. Observe in `aa_composer.js` (`sendUnit`) that the payment message for the fixed-denomination asset is skipped at line 1327-1328 and then filtered out entirely at line 1356 — the AA response unit is built successfully but never contains a payout of that asset; no bounce occurs and no error is surfaced. The received indivisible coins remain permanently credited to the AA's address with no achievable future path to spend them.
