### Title
Cross-organization CI status forgery via unscoped commit lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook against the `webhook_secret` of the organization named in the (unverified) JSON payload, but the `status` event handler that then acts on that payload never re-checks that the commit it writes to actually belongs to that same organization/repository. This breaks the binding: `organization whose webhook_secret authenticated the request` ≡ `repository/stack that the write actually targets`.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify with, using `repository_owner`, which is read straight out of the unverified request body: [1](#0-0) [2](#0-1) 

Once the HMAC signature validates for *that* organization's `webhook_secret`, the whole raw payload is dispatched unchanged to the registered handlers: [3](#0-2) 

For most events, the handler scopes further processing to stacks belonging to the repository named in `payload.dig('repository','full_name')` via `Handler#stacks`/`#repository_name`: [4](#0-3) 

However, `StatusHandler` — which handles the `status` GitHub event and creates a CI status for a commit — does **not** use `stacks` or any repository/organization scoping at all. It looks up commits globally by `sha` across the entire Shipit instance: [5](#0-4) 

Because `repository_owner` (used to pick the verifying secret) and the fields actually consumed by `StatusHandler` (`sha`, `state`, `context`, etc., with no repository field at all) are independent, unvalidated fields inside the same signed byte-string, an attacker who legitimately controls a GitHub App/organization configured in this Shipit instance (and therefore knows or can trigger requests signed with that organization's `webhook_secret`) can craft an arbitrary `status` webhook payload. As long as the raw body is HMAC-valid for their own organization's secret, they can set `sha` to any commit SHA that exists in *any other* organization's/stack's commit history, and `state`/`context`/`description` to anything they like. `StatusHandler#process` will create a matching `Status` on that foreign commit with no cross-check that it belongs to the authenticating organization/repository: [6](#0-5) 

This directly breaches the "organization that authenticated versus the repository that is written" binding called out in the rules: the signature only proves *an* organization the app trusts sent the request, not that the write happening on behalf of that request is confined to that organization's own commits/repository.

### Impact Explanation
CI/commit statuses are used by Shipit to gate deploys — `required_statuses`/`blocking_statuses` from `deploy_spec.rb` govern a commit's `deployable?` state, and CI status is exactly the "unprivileged, deployment-trust" signal a bridge/deploy flow relies on. By forging a passing status (e.g. matching a stack's `release_status_context` or a required CI check name) on a victim stack's commit, an attacker who only administers their own (separately configured, lower-trust) GitHub organization in a multi-tenant Shipit install can make an otherwise CI-failing or CI-pending commit in a completely different organization's stack appear "green"/deployable, enabling an unauthorized deploy of that commit. This satisfies the "unauthorized deploy" High/Critical impact category.

### Likelihood Explanation
Requires the attacker to control at least one organization/repository that is legitimately configured with its own `webhook_secret` in this Shipit instance (multi-org support is present via `Shipit.github_organizations`/`github_app_config`), which is a realistic scenario in shared/multi-tenant Shipit deployments where different teams or orgs each install their own GitHub App integration into the same Shipit instance. No stolen secrets, sessions, or `ApiClient` tokens are required — only the ability to fire a webhook (or replay one) that is validly signed for the attacker's own org, targeting a `sha` known to exist on a different stack (SHAs are public/discoverable via GitHub).

### Recommendation
- In `Shipit::Webhooks::Handlers::StatusHandler`, scope the commit lookup to `stacks` (i.e., verify the payload's `repository.full_name` matches a repository actually owned by/consistent with the organization used to validate the signature) instead of a bare `Commit.where(sha:)` across the whole installation.
- More generally, after `verify_signature` succeeds, assert that `payload.dig('repository','owner','login')` (or `organization.login`) used to pick the verifying secret is consistent with any repository field consumed further downstream, for every handler, not just those already calling `Handler#stacks`.

### Proof of Concept
1. Deploy sets up two GitHub orgs in `secrets.github`: `attacker-org` (attacker administers this org's GitHub App, knows its `webhook_secret`) and `victim-org` (unrelated stack, e.g. `victim-org/prod-service`).
2. Attacker finds a commit SHA on the `victim-org/prod-service` stack that is required to have a passing `ci/checks` status before deploy is allowed (public GitHub commit, or discoverable from Shipit's public UI).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/checks",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known `webhook_secret` over the raw body and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "attacker-org")` and successfully verifies the signature against `attacker-org`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (regardless of organization), and calls `commit.create_status_from_github!(params)`, creating a forged "success" status.
7. If `ci/checks` is in the victim stack's `required_statuses`, the victim commit now appears deployable, and a deploy that should have been blocked by real CI results can proceed.

module Shipit
  module Webhooks

      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
