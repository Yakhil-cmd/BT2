### Title
Commit author attribution spoofed via forged `Merge-Requested-By` commit-message trailer - (File: app/models/shipit/user.rb)

### Summary
`Shipit::User.find_or_create_author_from_github_commit` trusts a `Merge-Requested-By: <login>` line found anywhere in a raw commit message and, if the named GitHub login exists, binds it as `Commit#author` with no verification that this login actually authored, pushed, or approved the commit. Since commit messages are fully attacker-controlled (a contributor writes their own commit message and pushes it), any unprivileged user who can get a commit into a tracked repository can force Shipit to record an arbitrary real GitHub user as the author of that commit.

### Finding Description
The broken binding: the intended invariant is `commit.author.login == <GitHub identity that actually pushed/authored the commit>`. After exploitation, `commit.author.login == "admin-login"` while the actual pusher is the unprivileged attacker — the two diverge with nothing in the code path reconciling them.

Code path:
- `Commit.from_github` calls `User.find_or_create_author_from_github_commit(commit)` to populate the `author` field of a new `Commit` record. [1](#0-0) 
- `find_or_create_author_from_github_commit` regex-matches the literal string `MergeRequest::MERGE_REQUEST_FIELD` (`"Merge-Requested-By"`) against `github_commit.commit.message` and, on match, calls `find_or_create_by_login!(match_info[1])`, unconditionally trusting the captured login as the commit author. [2](#0-1) 
- `find_or_create_by_login!` fetches (or creates) the `Shipit::User` record for that login via `Shipit.github.api.user(login)` — it never checks whether the login corresponds to the person who pushed the commit, opened the PR, or has any relationship to the repository. [3](#0-2) 

The `Merge-Requested-By` trailer is *intended* to be written only by Shipit itself, inside `MergeRequest#merge_message`, when Shipit performs a merge-queue merge on behalf of a user via `stack.github_api.merge_pull_request`. [4](#0-3) [5](#0-4) 
However, `find_or_create_author_from_github_commit` is invoked for *every* commit ingested through `Commit.from_github` — including commits synced from ordinary pushes/PR heads via `GithubSyncJob`, `find_or_create_commit_from_github_by_sha!`, etc. — not just Shipit-generated merge commits. There is no check that the commit was actually produced by Shipit's own merge action (e.g. no signature, no comparison against the merge SHA that Shipit recorded, no restriction to commits whose committer is Shipit's own bot/token).

Attacker exploit flow:
1. Attacker (unprivileged, owns a fork/branch) writes a commit with message body `"exploit\n\nMerge-Requested-By: admin-login\n"` where `admin-login` is a real, privileged GitHub user.
2. Attacker pushes this commit / opens a PR; Shipit's webhook/sync path eventually calls `Commit.create_from_github!` (via `Commit.from_github`) for this SHA.
3. `find_or_create_author_from_github_commit` matches the trailer, looks up `admin-login` via the GitHub API (precondition: user exists and is fetchable), and returns/creates that `Shipit::User`.
4. The `Commit` row is persisted with `author = <admin-login's Shipit::User>`, despite `admin-login` never touching this commit.

None of the existing guards intervene: there is no webhook signature check relevant to this field (`verify_signature` only authenticates that the payload came from GitHub, not that the message content is trustworthy), no `ExplicitParameters` schema restricts commit message content, and no model validation on `Commit#author`/`message` cross-checks the trailer against actual push/authorship metadata. The regex only requires the named user to exist on GitHub — full attacker string control plus GitHub existence is sufficient.

### Impact Explanation
Any commit ingested by Shipit for any repository/stack it tracks can have its recorded `author` (and thus attribution surfaced in the UI, `SHIPIT_USER` env for deploy commands, and `Commit#lock_author`-adjacent audit trail via `identify_merge_request` which also sets `self.author = merge_request.merge_requested_by`) forged to any existing GitHub login. This is a repeatable, per-commit attribution/audit-trail forgery: an unprivileged contributor can make it appear that a trusted/privileged user authored or requested every commit they push, undermining any downstream logic or human review that relies on `commit.author` to establish trust (e.g., "who requested this deploy", audit logs, `Hook.emit` payloads carrying `commit.author`). This matches the Critical category "a payload for one repository mutating another's stack, commit, task or team" in spirit — here it's a payload mutating the identity graph itself, feeding privileged-looking attribution into deploy/audit surfaces without authentication.

### Likelihood Explanation
Preconditions are minimal and already attacker-satisfiable per the threat model: the attacker only needs push/PR access to a repository Shipit tracks (which they may own as a fork/PR source) and the named privileged login must exist on GitHub (true for any real GitHub user, including ones the attacker has never interacted with). No Shipit secrets, tokens, or team membership are required. The attack is trivially repeatable across every commit and every stack the attacker can push to.

### Recommendation
Restrict trust in the `Merge-Requested-By` trailer to commits that Shipit itself produced. Concretely: only honor the trailer when creating the *merge commit* explicitly tracked by a `Shipit::MergeRequest` (i.e., set `author` from `merge_request.merge_requested_by` as already done in `Commit#identify_merge_request`, and remove/ignore the free-text regex parsing in `find_or_create_author_from_github_commit` entirely), or verify the commit's committer identity/SHA matches the one Shipit recorded when it performed the merge (`merge_request.head.sha` / the SHA returned from `merge_pull_request`). Do not derive authorship from arbitrary, attacker-controlled commit message text.

### Proof of Concept
Minitest plan (models test, no live GitHub — stub `Shipit.github.api.user`):
```ruby
test "find_or_create_author_from_github_commit trusts forged Merge-Requested-By trailer" do
  privileged_login = "admin-login"
  Shipit.github.api.stubs(:user).with(privileged_login).returns(
    stub(id: 999, login: privileged_login, name: "Admin", email: "admin@example.com",
         avatar_url: "https://avatars.githubusercontent.com/u/999", url: "https://api.github.com/users/admin-login")
  )

  github_commit = stub(
    sha: "deadbeef",
    commit: stub(
      message: "exploit\n\nMerge-Requested-By: #{privileged_login}\n",
      author: stub(id: 1, login: "attacker"),
      committer: stub(id: 1, login: "attacker"),
      date: Time.now
    ),
    author: stub(id: 1, login: "attacker"),
    committer: stub(id: 1, login: "attacker"),
    stats: nil,
    parents: []
  )

  commit = Shipit::Commit.from_github(github_commit)

  # Broken binding demonstrated:
  refute_equal "attacker", commit.author.login
  assert_equal privileged_login, commit.author.login
end
```
This shows `commit.author.login == "admin-login"` even though `admin-login` never authenticated or interacted with the push, proving the identity binding is forgeable by an unauthenticated/unprivileged party.

    def self.find_or_create_author_from_github_commit(github_commit)
      if (match_info = github_commit.commit.message.match(/^#{MergeRequest::MERGE_REQUEST_FIELD}: ([\w\-.]+)$/))
        begin
          return find_or_create_by_login!(match_info[1])
        rescue Octokit::NotFound
          # Corner case where the merge-requested-by user cannot be found (renamed/deleted).
          # In this case we carry on and search for the commit author
        end
      end
      find_or_create_from_github(github_commit.author.presence || github_commit.commit.author.presence)
    end
