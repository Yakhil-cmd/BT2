### Title
`min-ustx-for-sats-amount` double-truncating division lets a staker register for an sBTC bond while posting less STX collateral than the bond's own floor requires - ([File: stackslib/src/chainstate/stacks/boot/pox-5.clar])

### Summary
`register-for-bond` in `pox-5.clar` gates sBTC-bond registration on an STX collateral floor computed by `min-ustx-for-sats-amount`, which performs two chained integer divisions. Analogous to the `FixedStrikeOptionTeller.create` bug (rounding `amount * strikePrice / 10**decimals` down to zero for small inputs), this Clarity function can round the required floor down to a value lower than the mathematically correct one — including all the way to `0` — whenever `stx-value-ratio * sats-amount < 100`. Because `sats-amount` (the amount of sBTC the staker chooses to custody) is staker-controlled up to their allowlisted `max-sats`, any unprivileged staker can pick a small `sats-total` to make the enforced STX floor collapse, then satisfy `(>= amount-ustx floor)` with an `amount-ustx` that is far below the intended value-backing ratio (down to `0`).

### Finding Description
`min-ustx-for-sats-amount` is defined as: [1](#0-0) 

```
(define-read-only (min-ustx-for-sats-amount
        (sats-amount uint)
        (stx-value-ratio uint)
        (min-ustx-ratio uint)
    )
    (/ (* (/ (* stx-value-ratio sats-amount) u100) min-ustx-ratio) u10000)
)
```

The inner term `(/ (* stx-value-ratio sats-amount) u100)` truncates to `0` whenever `stx-value-ratio * sats-amount < 100`. Once that inner term is `0`, the outer multiplication/division `(/ (* 0 min-ustx-ratio) u10000)` is also `0`, regardless of `min-ustx-ratio`. This mirrors exactly the reported bug class: a legitimate collateral-floor computation rounds to zero for small enough numerator, letting the caller satisfy a `>=` collateral check with `0` (or an arbitrarily small) counter-value.

This function is the sole collateral gate in `register-for-bond`: [2](#0-1) 

The staker chooses `sats-total` freely (bounded only by their per-bond `max-sats` allowlist entry set by the bond admin, checked later at `(<= sats-total allowance)`), and chooses `amount-ustx` freely as well, subject only to `>= min-ustx-for-sats-amount(...)`. Because the floor function can be driven to `0`, a staker can call `register-for-bond` with `amount-ustx: u0` (or any value below the true, non-truncated floor) and a small nonzero `sats-total`, e.g. `sats-total = 1`, whenever `stx-value-ratio < 100`. The registration then proceeds: `roll-sbtc` custodies `sats-total` sBTC from the staker, `protocol-bond-memberships` records `amount-ustx: 0` (or the artificially-low value) alongside `amount-sats: sats-total`, and the staker is added to per-cycle signer/bond delegation and reward-share accounting with the real `sats-total` (not the collateral-shrunk value): [3](#0-2) 

The invariant the protocol intends to enforce — that a bond participant's locked STX (`amount-ustx`) must be at least `stx-value-ratio`/`min-ustx-ratio` proportional to their custodied sBTC (`sats-total`) — is broken. The staker earns bond sBTC rewards proportional to `sats-total` (via `calculate-bond-rewards`'s `target-yield = total-sats * target-rate / 10000 / 50`, see `calculate-bond-rewards` in the same file) and counts toward signer delegation weight, while contributing STX collateral that can be zero.

### Impact Explanation
This is an unsigned/uncollateralized stacking action: a staker obtains bond membership, reward-earning sBTC shares, and signer-delegation weight while posting STX collateral below (down to zero) the value the bond's own `stx-value-ratio`/`min-ustx-ratio` parameters require. This falls under "signing weight or reward slots exceeding locked value" (High) per the impact criteria — the staker's `sats-total`-driven reward/signing weight is not actually backed by the `amount-ustx` STX lock the protocol design assumes. In the limiting case (`sats-total` chosen such that the floor computes to `0`), the staker locks `0` STX yet is fully counted for bond rewards and signer delegation for that `sats-total`, which is an unsigned/uncollateralized stacking commitment relative to the protocol's own accounting rules.

The magnitude of the exploitable gap depends on the bond's configured `stx-value-ratio`: whenever `stx-value-ratio < 100`, the staker can always choose a `sats-total` small enough to zero out the floor (e.g. `sats-total = 1`), and the resulting custodied sBTC is small in absolute terms for a single call. However, nothing prevents repeating the trick with multiple stakers/bond slots (subject to `allowance`/`max-sats` per staker), and the fundamental invariant break — an STX-floor check that can be forced to `0` regardless of the intended `min-ustx-ratio` — is a genuine protocol-level flaw, not merely a negligible rounding dust issue, because it decouples reward/signing weight entirely from the intended collateral requirement for any bond configured with `stx-value-ratio < 100`.

### Likelihood Explanation
High. No privileged role is required: `stx-value-ratio` and `min-ustx-ratio` are set once by the bond admin in `setup-bond`, but the staker unilaterally chooses `sats-total` and `amount-ustx` within their allowlisted `max-sats`, and the check is purely arithmetic with no additional guard against a zero/degenerate floor. Any bond configured with `stx-value-ratio < 100` (a plausible value given `stx-value-ratio` is described as "ustx per 100 sats") is immediately exploitable by any allowlisted staker on their first `register-for-bond` call.

### Recommendation
Compute `min-ustx-for-sats-amount` without the intermediate truncation, e.g. by combining the multiplications before any division: `(/ (* stx-value-ratio sats-amount min-ustx-ratio) (* u100 u10000))`, and/or explicitly reject (or round up) cases where the computed floor is `0` but `sats-amount > 0`, consistent with the recommended fix pattern from the referenced report (reject/round rather than silently truncate to zero).

### Proof of Concept
1. Bond admin calls `setup-bond` with `stx-value-ratio` set to e.g. `50` (any value `< 100`) and allowlists staker `S` for `max-sats >= 1`.
2. Staker `S` calls `register-for-bond` with `sats-total = 1` (an sBTC amount they must actually custody/transfer) and `amount-ustx = 0`.
3. `min-ustx-for-sats-amount(1, 50, min-ustx-ratio)` evaluates: inner `(/ (* 50 1) 100) = 0`; outer `(/ (* 0 min-ustx-ratio) 10000) = 0`. The check `(>= 0 0)` passes.
4. `register-for-bond` succeeds: `protocol-bond-memberships` records `amount-ustx: 0`, `amount-sats: 1`; the staker is added via `add-staker-to-bond-cycles`/`add-staker-to-signer-cycles` with the real sats value for reward and delegation accounting, all while locking `0` STX.
