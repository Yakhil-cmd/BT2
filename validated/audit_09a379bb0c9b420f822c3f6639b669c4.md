### Title
`Shipit::Api::CCMenuController#stack` resolves any stack unscoped by `current_api_client.stack_id`, leaking deploy state across stacks - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuController` overrides the base controller's stack-resolution helper with its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, instead of using `BaseController#stack`/`#stacks`, which restricts lookup to `Stack.where(id: current_api_client.stack_id)` when the client is stack-scoped. Any valid `ApiClient` token minted for one stack (e.g. via `CCMenuUrlController#fetch`) can therefore be replayed against `/api/stacks/:stack_id/ccmenu.xml` for an arbitrary other stack, and `#show` will render that unrelated stack's latest deploy/rollback state.

### Finding Description
The intended binding is: the stack resolved by the controller for a request == a stack within `current_api_client`'s authorized scope, i.e. `resolved_stack.id ∈ Stack.where(id: current_api_client.stack_id)` when `current_api_client.stack_id?` is true.

`Shipit::Api::BaseController` implements this correctly: [1](#0-0) 
`stacks` filters to `current_api_client.stack_id` when present, and the default `stack` method looks up within that scope.

However, `CCMenuController` defines its own private `stack` method that bypasses this entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` — the unscoped class method on `Stack` — rather than `stacks.from_param!(params[:stack_id])`. `require_permission :read, :stack` only checks that the authenticated `ApiClient` has the `read:stack` permission bit set (`ApiClient#check_permissions!`), it does not check which stack the permission applies to: [3](#0-2) 

`CCMenuUrlController#fetch` mints exactly this kind of token: a `read:stack`-permissioned `ApiClient` tied to the current user (not stack-scoped by design in the request path used), which is then embedded in a public-facing CCMenu URL: [4](#0-3) 

Because `CCMenuController#stack` never consults `current_api_client.stack_id`, once an attacker holds any valid token with `read:stack`, they can substitute any other stack's `to_param`/id in the URL and the controller will happily resolve and render that stack's deploy state. The existing (unintentional) test in the suite already demonstrates this behavior — a client authenticated for `@stack` successfully renders an entirely unrelated, freshly created `Stack.create!(...)`: [5](#0-4) 

No other guard intervenes: `authenticate_api_client` only validates the token signature/existence, not stack ownership, and `require_permission!` only checks the permission name, not the target scope's identity.

### Impact Explanation
Any holder of a `read:stack`-scoped CCMenu token can enumerate `stack_id`/`to_param` values and read `deploys_and_rollbacks.last` (deploy id, running/success/failure state, timestamps, lock state) for every stack in the Shipit instance, including private/internal stacks the token was never intended to cover. This is an unauthenticated-relative-to-target-stack read of deploy state, matching the High severity category "unauthenticated read of stack state, task streams or deploy output." It is fully repeatable against arbitrary stacks/tenants with no additional privilege required beyond possessing any single valid CCMenu token.

### Likelihood Explanation
Preconditions are minimal and realistic: any user who can trigger `CCMenuUrlController#fetch` for a stack they have access to (a normal, low-privilege action) obtains a signed `ApiClient` token; stack `to_param`/ids are low-entropy and easily enumerable or guessable. No secrets, GitHub credentials, or elevated roles are needed — this is exploitable by any authenticated Shipit user with access to at least one stack's CCMenu URL feature.

### Recommendation
Remove the overriding `stack` method in `Shipit::Api::CCMenuController` and use the inherited `BaseController#stack` (backed by `stacks`, which enforces `current_api_client.stack_id` scoping), or explicitly scope: `@stack ||= stacks.from_param!(params[:stack_id])`.

### Proof of Concept
Add a minitest to `test/controllers/api/ccmenu_controller_test.rb` (or a new test file) asserting the binding across two distinct stacks:
1. Create `stack_a` and `stack_b` (`Stack.create!(...)`), each with distinct deploys.
2. Mint an `ApiClient` scoped to `stack_a` (`ApiClient.create!(stack: stack_a, permissions: %w[read:stack], creator: user, name: 'x')`), analogous to what `CCMenuUrlController#fetch` produces.
3. Assert `client.stack_id == stack_a.id` (binding, left side).
4. `get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }`.
5. Assert that the response is forbidden/not found (expected binding-preserving behavior) — currently it returns `:ok` and `assert_payload 'name', stack_b.to_param` succeeds, proving `resolved_stack == stack_b ∉ Stack.where(id: client.stack_id)`, i.e. the binding is violated.
