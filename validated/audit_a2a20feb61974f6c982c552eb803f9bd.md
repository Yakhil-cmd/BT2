## Title
Stack-scoped API token grants read access to any stack via `CCMenuController#stack` bypassing token scoping - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor inherited from `BaseController` and, in doing so, drops the scoping that restricts a stack-bound `ApiClient` token to only its own stack. This breaks the equality that should hold between "the stack a token authorizes" and "the stack the CCMenu endpoint touches."

### Finding Description
`BaseController#stacks` restricts the set of stacks visible to a request based on whether the authenticated `ApiClient` is bound to a specific stack: [1](#0-0) 

`stacks` returns `Stack.where(id: current_api_client.stack_id)` when the client is scoped (`stack_id?`), otherwise `Stack.all`. `stack` then does `stacks.from_param!(params[:stack_id])`, so `from_param!` is guaranteed to raise `ActiveRecord::RecordNotFound` for any stack other than the one the token is bound to.

`CCMenuController`, however, defines its own private `stack` method that talks to `Stack` directly, completely bypassing `stacks`: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

`require_permission :read, :stack` still gates the endpoint, but this only asserts the client's permission bitmask contains `read:stack`; it says nothing about which stack the permission applies to. `ApiClient#check_permissions!` (`app/models/shipit/api_client.rb:38-45`) is scope-string based only, so a token created via `CCMenuUrlController` with `permissions: %w[read:stack]` and bound to `stack: X` (see `app/models/shipit/api_client.rb:8` `belongs_to :stack, optional: true`, and its normal creation flow in `app/controllers/shipit/ccmenu_url_controller.rb:15-18`) is able to pass `require_permission!` for any `stack_id` parameter, not just X.

The equality that should be enforced but is not:
`token.stack_id (authorized stack) == params[:stack_id] (touched stack)`

Before the attacker's request: the token is only meant to unlock CCMenu status for the stack for which it was minted.
After the request: because `CCMenuController#stack` ignores `current_api_client.stack_id`, the same token, when replayed against `/api/stacks/<other_owner>/<other_repo>/<other_env>/ccmenu`, returns build/deploy status data for a completely different stack.

### Impact Explanation
This grants "unauthenticated read of stack state" (in the sense that a token scoped to stack A is unintentionally authorized for stack B) for any stack in the Shipit installation, using only a legitimately-obtained, narrowly-scoped CCMenu token (which itself requires only a normal authenticated web session — no special privilege, no GitHub write access, no `api_clients_secret`). The token holder can enumerate/read `lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, etc. for every stack in the installation rather than only the one they were granted visibility into. This matches the "High" bucket: escalation past the intended `read:stack` authorization boundary to unauthenticated (cross-stack) read of stack/deploy state.

### Likelihood Explanation
Likelihood is high given the CCMenu token flow is a normal, documented feature: `CCMenuUrlController#client` (`app/controllers/shipit/ccmenu_url_controller.rb:15-18`) automatically mints a stack-scoped, `read:stack`-only `ApiClient` for the currently logged-in user and hands the token (embedded in a URL) to that user for consumption by third-party CI-status tools (CCMenu-compatible clients). Any holder of such a URL/token — which is explicitly meant to be low-privilege and stack-specific — can trivially substitute a different `stack_id` in the request path to read another stack's status. No signature or extra secret is required; only knowledge of another stack's identifier (owner/repo/environment), which is not itself secret in Shipit.

### Recommendation
Have `CCMenuController#stack` delegate to the same scoped `stacks` helper used by `BaseController` (i.e., call `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!(params[:stack_id])`), so that a stack-bound token can never resolve a stack other than the one it was minted for. Add a regression test asserting that a token scoped to stack A returns 404 (not 200) when queried against stack B's CCMenu endpoint.

### Proof of Concept
1. As a normal authenticated user with access to stack `acme/app-a/production`, visit the CCMenu URL flow which creates a stack-scoped `ApiClient` (permissions `read:stack`, `stack_id` = A) and returns a URL containing `token=<A_token>` (`app/controllers/shipit/ccmenu_url_controller.rb`).
2. Send `GET /api/stacks/acme/app-b/production/ccmenu?token=<A_token>` (a stack the attacker is not authorized to view/is not bound to the token).
3. Because `Shipit::Api::CCMenuController#stack` calls `Stack.from_param!` directly rather than the scoped `stacks.from_param!`, the request resolves stack B, `require_permission :read, :stack` passes (the client does have `read:stack` in its permission list), and the endpoint renders stack B's XML status (`show` action, `app/controllers/shipit/api/ccmenu_controller.rb:22-25`), leaking build/deploy information for a stack the token was never authorized to touch.
