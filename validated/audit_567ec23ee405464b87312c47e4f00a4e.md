## Analog Vulnerability Found

### Title
Cross-organization commit status forgery due to unscoped SHA lookup in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
Shipit's webhook signature verification authenticates a webhook against the *organization* whose GitHub App secret matches the signature, but the `status` event handler then applies the payload to *any* commit row in the database whose SHA matches, without checking that the commit belongs to the authenticated organization's repository. This is the same class of bug as the Zebra advisory: identity established for authentication purposes (the organization/peer) is decoupled from the entity that is ultimately acted upon (the repository/block), letting one legitimately-authenticated principal affect state that belongs to a different one.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/secret to verify against using only the `repository.owner.login` (or `organization.login`) field taken from the untrusted payload, then confirms the HMAC matches that organization's `webhook_secret`: [1](#0-0) 

This design explicitly supports multiple independent GitHub App configurations keyed by organization, as shown by `Shipit.github_app_config` and the `secrets_double_github_app.yml` fixture (`OrgOne`, `OrgTwo` each with their own `webhook_secret`): [2](#0-1) 

Once the signature check passes (proving only that *some* configured organization's secret was used correctly — an organization the attacker legitimately controls a repo/installation for), the event body is dispatched to handlers with no further authorization: `WebhooksController#create` just calls `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`: [3](#0-2) 

The base `Handler` class *does* provide a `repository_name`/`stacks` helper meant to scope processing to the repository named in the payload: [4](#0-3) 

But `StatusHandler#process` does not use it. It looks up commits purely by SHA across the entire `commits` table, with no repository/stack scoping at all: [5](#0-4) 

`Commit#create_status_from_github!` then unconditionally writes the attacker-supplied `state`/`description`/`target_url` onto that commit and fires deploy-relevant side effects (`Hook.emit(:deployable_status, ...)`, `stack.schedule_merges` on success/pending): [6](#0-5) [7](#0-6) 

**The broken binding, as an equality that must hold but doesn't:**
`organization authenticated via webhook signature` == `repository/stack whose commit row is mutated`.

Before the fix (current state): the left side is checked (signature verified against `repository_owner` derived from the payload's own claimed org), but the right side (`Commit.where(sha: params.sha)`) is resolved against the *global* commits table with no relationship back to that authenticated organization/repository. Any organization (or repo) that has a legitimately configured, correctly-signed webhook integration with this Shipit instance can forge a `status` event naming a SHA that exists in a *different* tracked stack (e.g. a shared commit history from a fork, or simply a colliding/known SHA from a public upstream repo tracked by another team on the same instance) and have Shipit apply that status to the other team's commit and stack.

### Impact Explanation
This crosses exactly the repository-write authorization boundary the rules flag as in scope ("an organization that authenticated versus the repository that is written"). A malicious or compromised organization with its own valid GitHub App webhook integration into a shared/multi-tenant Shipit instance can:
- Forge success/failure `commit_status` writes on commits belonging to other organizations' stacks it has no access to.
- Because `add_status` triggers `stack.schedule_merges` and `Hook.emit(:deployable_status, ...)` on success, and `Commit#schedule_continuous_delivery`/`deployable?` gate continuous deployment on commit status, a forged "success" status can push a targeted commit through continuous-deployment/merge gating for a stack the attacker does not own, resulting in an unauthorized deploy — one of the explicitly accepted High/Critical impacts.

### Likelihood Explanation
Requires only that the attacker legitimately controls one organization/repository whose GitHub App webhook integration is configured on the same Shipit instance (a normal, unprivileged tenant, not a Shipit session, API token, or GitHub App private key holder), and knowledge of a target SHA (trivially available for shared fork history or any public commit). No signature bypass or cryptographic break is needed — the signature check is legitimately satisfied by the attacker's own credentials; only the missing repository-scoping check enables the cross-tenant write.

### Recommendation
Scope `StatusHandler#process` (and any other handler resolving commits purely by `sha`) to the repository named in the payload, mirroring the `stacks`/`repository_name` helper already present in `Handler`, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalent, so a commit can only be updated if it belongs to a stack backed by the repository that was actually authenticated for this webhook delivery.

### Proof of Concept
1. Configure a multi-tenant Shipit instance with `OrgA` (victim, tracks `OrgA/app`) and `OrgB` (attacker-controlled, has its own legitimate GitHub App installation/webhook secret, e.g. via a fork of `OrgA/app` or any repo sharing a commit SHA with `OrgA/app`).
2. As `OrgB`, send a `status` webhook correctly signed with `OrgB`'s `webhook_secret`:
```json
{
  "repository": { "owner": { "login": "OrgB" }, "full_name": "OrgB/fork" },
  "sha": "<sha shared with a commit tracked under OrgA/app>",
  "state": "success",
  "context": "ci/tests"
}
```
3. `WebhooksController#verify_signature` verifies successfully against `Shipit.github(organization: 'OrgB')` since the signature is genuinely valid for `OrgB`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the matching commit under `OrgA`'s stack, and calls `create_status_from_github!`, writing the forged "success" status and triggering `stack.schedule_merges` / continuous-deployment evaluation for `OrgA`'s stack — despite the request never being authenticated for `OrgA`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
