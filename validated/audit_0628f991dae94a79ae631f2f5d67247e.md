### Title
StatusHandler attaches forged CI status to any tracked commit without validating it belongs to the authenticated organization/repository — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The webhook signature verification and the actual state-changing write in `WebhooksController` are bound by two different, unrelated payload fields. Signature verification is keyed off `repository.owner.login` (used to pick which `GitHubApp`/secret to check against), but the `status` event handler resolves which `Commit`/`Stack` to mutate purely from the attacker-controlled `sha` field, with no check that the commit actually belongs to the repository/organization that was authenticated. This is the same class of bug as the `RewardThrottle.setTimekeeper` finding: a field that drives authorization (`epoch` / `repository.owner.login`) can diverge from the field that drives the actual effect (`checkRewardUnderflow`'s epoch usage / `sha`-based commit lookup), letting an attacker use a weak or unconfigured trust anchor to affect state that belongs to a different, unrelated trust domain.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App config to validate the HMAC signature against using only the organization derived from the payload: [1](#0-0) [2](#0-1) 

`GitHubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as "always verified": [3](#0-2) 

The webhook secret is documented as optional per organization (`docs/setup.md`, `config/secrets.development.example.yml` "Webhook secret (optional)"), and Shipit explicitly supports configuring multiple organizations, each with its own independent secret.

Once "verified", `WebhooksController#create` dispatches the parsed JSON to the matching handler(s) without any further binding of the payload to the organization that was used for signature selection: [4](#0-3) 

`Shipit::Webhooks::Handlers::StatusHandler` then looks up the target purely by `sha`, with **no scoping to `repository_name`/`stacks`** (unlike other handlers such as `PushHandler`, which do scope through `Handler#stacks`/`repository_name`): [5](#0-4) [6](#0-5) 

Because `Commit.where(sha: params.sha)` is a global lookup across the entire Shipit instance, a payload whose signature is validated against **Organization A**'s (possibly secret-less) GitHub App config can carry a `sha` that actually belongs to a commit tracked under **Organization B**'s repository/stack. The status is written to that unrelated commit regardless of which organization authenticated the request.

Creating a `Status` record has real downstream effects: it enables CI, and schedules continuous delivery / merge processing: [7](#0-6) 

That in turn feeds `MergeRequest#all_status_checks_passed?`, and `ProcessMergeRequestsJob` will actually call `merge_request.merge!`, which performs a real GitHub write using the app's install token: [8](#0-7) [9](#0-8) [10](#0-9) 

**Binding broken (as equality):** `organization used to select/validate the webhook signature` ≠ `organization/repository that owns the commit actually mutated by the handler`. Before the attacker's request, these two are only coincidentally equal (a legitimate GitHub webhook for repo X always carries `repository.owner.login` = X's owner and `sha` belonging to X). After a crafted request, an attacker can set `repository.owner.login` to any organization Shipit tracks (in particular one with no `webhook_secret` configured, which the code accepts unconditionally) while setting `sha` to a commit that belongs to an entirely different organization/repository.

### Impact Explanation
This is a cross-repository/cross-organization write: an unauthenticated actor (no GitHub account, no Shipit session, no API client, and — if the target Shipit instance has any organization configured without a `webhook_secret`, which is an explicitly documented supported configuration — no secret at all) can inject a forged "success" CI status onto a commit belonging to a completely different, unrelated, and possibly securely configured organization/repository tracked by the same Shipit instance. This can cause `ProcessMergeRequestsJob` to consider a pull request as passing CI and call `stack.github_api.merge_pull_request`, i.e., trigger an **unauthorized merge** using the app's real GitHub credentials against the victim repository — matching the Critical-impact category ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with at least two organizations (a documented, supported multi-org configuration), (2) at least one of those organizations having no `webhook_secret` set (documented as optional), and (3) knowledge of a target commit SHA in the victim repository (commit SHAs are frequently public/observable via the target's GitHub repo, PRs, or commit-status/check UI). Given that `webhook_secret` being empty is explicitly supported and multi-org configuration is a documented feature, this is a realistic, root-caused likelihood, not a theoretical one — though it does depend on the specific optional configuration choice of "no secret for at least one org," which cannot be verified from the code alone (deployment-specific).

### Recommendation
Scope every webhook handler's state-changing lookups (not just `PushHandler`) to the repository derived from `repository_name`/the authenticated organization, and reject events whose `payload.dig('repository','owner','login')` does not match the repository actually referenced by other payload fields (e.g., in `StatusHandler`, restrict `Commit.where(sha: params.sha)` to commits belonging to `Repository.from_github_repo_name(repository_name)`). Additionally, consider requiring a non-blank `webhook_secret` for every configured organization, since an org without one effectively disables signature verification for the entire multi-tenant Shipit instance.

### Proof of Concept
1. Shipit instance is configured with two organizations: `victim-org` (secured, has `webhook_secret` set, hosts `victim-org/critical-repo` with an open, CI-pending pull request) and `attacker-org` (misconfigured or newly onboarded with `webhook_secret` left blank, per documented optional setting).
2. Find the head commit SHA of the pending PR in `victim-org/critical-repo` (visible on GitHub's PR page).
3. POST to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim PR head sha>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/whatever" }
}
```
No `X-Hub-Signature` header is required because `verify_webhook_signature` short-circuits to `true` when `attacker-org`'s `webhook_secret` is blank.
4. `WebhooksController#verify_signature` resolves and "verifies" against `attacker-org`'s (secret-less) app config and passes the request through.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the commit under `victim-org/critical-repo`, and calls `create_status_from_github!`, creating a `success` status on it — with no check that this commit belongs to `attacker-org`.
6. `Status#schedule_continuous_delivery` and the merge-queue job (`ProcessMergeRequestsJob`) subsequently see the PR's CI checks as passing and call `stack.github_api.merge_pull_request`, merging the PR in `victim-org/critical-repo` using Shipit's real GitHub credentials — an unauthorized cross-organization merge triggered entirely from `attacker-org`'s webhook endpoint.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
