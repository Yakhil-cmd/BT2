### Title
Bundling mandatory fee/output transfers to a conditionally-restricted asset address with critical AA state updates forces the whole trigger response to bounce and revert - (File: aa_composer.js)

### Summary
Obyte's AA execution model performs a single, all-or-nothing state update per trigger: if any part of the composed response unit fails final validation (`validateAndSaveUnit`), the AA calls `bounce()`, which discards *every* state change made during that trigger, including unrelated critical bookkeeping (e.g. marking a loan/position as liquidated, closing a margin position, updating internal balances) that had nothing to do with the failing transfer. This mirrors the reported Vault.vy issue, where bundling an always-attempted fee transfer with the liquidation logic causes the entire liquidation to revert whenever the fee transfer fails.

### Finding Description
When an AA composes its response, the final payment message is validated and saved via `executeStateUpdateFormula` → `validateAndSaveUnit`; any failure (including a failing asset validity condition) causes the whole trigger to `bounce`: [1](#0-0) 

`bounce()` unconditionally rolls back to the savepoint taken at the very start of trigger processing, discarding all balance/state updates accumulated so far for this trigger (and its whole cascading tree of secondary triggers), not just the message that failed: [2](#0-1) 

Failures propagate the same way even when the failing transfer is isolated into a secondary (async) trigger: a bounce anywhere in the secondary-trigger chain still forces a full `revert()` of the primary trigger's state changes, so isolating the fee-payout AA does not protect the critical operation: [3](#0-2) 

The kind of "recipient can no longer receive" condition analogous to a paused/blacklisted ERC-20 exists natively for custom assets: an asset can require `spender_attested` (recipients must hold a valid, non-revoked attestation) and/or a `transfer_condition`/`is_transferrable` restriction, both of which are enforced during the same validation pass that an AA's outgoing payment must pass: [4](#0-3) [5](#0-4) 

If a lending/margin-style AA (built analogously to the audited Vault) always includes a payout to a fixed protocol-fee address denominated in such a restricted asset as part of the *same* response that also performs the critical accounting (e.g. marking a position liquidated, releasing/seizing collateral), then the moment that fee address's attestation is revoked or the transfer condition stops being satisfied, every future attempt to run that liquidation logic will fail validation and `bounce()`, wiping out the liquidation's state changes each time. Because the underlying condition (revoked attestation) is external to the trigger sender and persists across all subsequent triggers, the liquidation can be made to *always* revert, exactly like the reported issue.

### Impact Explanation
A liquidation-style trigger that always bounces means bad positions can never be closed on-chain: collateral stays locked inside the AA, the AA's internal bookkeeping (debt tracking) is never updated, and the protocol accrues unrecoverable bad debt — this is a concrete AA fund-freezing / stuck-funds scenario, matching the "AA fund loss or freezing" acceptance criterion.

### Likelihood Explanation
This requires an application built on top of ocore (an oscript AA implementing a margin/lending protocol) to route a mandatory fee payment in a `spender_attested`/`transfer_condition`-restricted asset to a fixed address within the same trigger response as its liquidation logic, and for that address's eligibility to later be revoked (analogous to a blacklist/pause event). This is not attacker-triggerable in the base protocol itself, but is a plausible, externally-triggered event exactly as characterized in the original report (rated Medium there for the same reason), so likelihood here is similarly Medium.

### Recommendation
- In the AA/oscript language documentation, warn developers that any payment to a conditionally-restricted asset destination (spender_attested, transfer_condition, is_transferrable) should not be bundled with essential/critical state-changing logic (e.g., liquidation bookkeeping) in the same trigger, since a bounce reverts the *entire* trigger tree, not just the failing message.
- Encourage decoupling: perform critical state changes (mark as liquidated) unconditionally, and route any fee payouts to restricted-asset destinations through a separate, retryable secondary trigger/withdrawal path whose failure does not roll back the primary liquidation bookkeeping, or accrue fees in a state variable and let recipients pull them independently rather than pushing them atomically with the critical operation.

### Proof of Concept
1. Define asset `FEE_ASSET` with `spender_attested: true`, attested by attestor `ATT`.
2. Deploy a margin-style AA whose response to a "liquidate" trigger sends: (a) collateral back to the liquidator, (b) a small trading fee in `FEE_ASSET` to a fixed `protocol_fee_address`, and (c) a `state` message marking the position as liquidated.
3. `ATT` revokes `protocol_fee_address`'s attestation for `FEE_ASSET` (or the asset's `transfer_condition` stops being satisfied for that address).
4. Post a valid "liquidate" trigger unit for an undercollateralized position.
5. During response composition, `validateAndSaveUnit` fails at the `spender_attested`/`transfer_condition` check for the fee output (`validation.js:2630-2659`), `sendUnit` calls `bounce(err)` (`aa_composer.js:1405-1411`), and `revert()` rolls back all state changes made during the trigger, including the "position liquidated" state update (`aa_composer.js:1759-1783`).
6. The undercollateralized position remains open and unliquidatable for as long as the fee address stays ineligible, accruing bad debt.
