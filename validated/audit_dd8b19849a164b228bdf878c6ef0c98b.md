This confirms the vulnerability path. Let me lay out the finding.

**Root cause chain:**

1. `WebhooksController#verify_signature` selects *which organization's secret* to verify against using `repository_owner`, extracted directly from the unauthenticated JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) .

2. That name is used to fetch the `GitHubApp` config for that org and validate the HMAC: `github_app = Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .

3. Critically, `verify_webhook_signature` **short-circuits to `true` if no `webhook_secret` is configured for that org**: `return true unless webhook_secret` [3](#0-2) . This is a documented, normal configuration state — every setup template ships with `webhook_secret: # nil` [4](#0-3) [5](#0-4) .

4. Once `verify_signature` passes (trivially, by naming any org with a blank secret), `WebhooksController#create` dispatches the **entire attacker-controlled body** to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [6](#0-5) .

5. Handlers resolve the target repository/stack from a **different field** of that same body — `repository.full_name` — completely independent of the `repository.owner.login`/`organization.login` field that was used for signature-org selection: `Repository.from_github_repo_name(payload.dig('repository','full_name'))` in the base `Handler` [7](#0-6) , and identically in `PushHandler` [8](#0-7)  and every `PullRequest::*Handler` (`opened_handler.rb`, `closed_handler.rb`, `edited_handler.rb`, etc.).

This is exactly the "organization that authenticated versus the repository that is written" binding break named in the rules: nothing forces `repository.full_name` (used to select the Stack to act on) to belong to the same organization as `repository.owner.login`/`organization.login` (used to select whose secret validates the request).

### Title
Cross-Tenant Webhook Forgery via Organization/Repository Binding Mismatch in Signature Verification - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
In a multi-organization Shipit deployment (`secrets.yml` with several `github:` orgs, as documented and templated), `WebhooksController#verify_signature` picks which org's `webhook_secret` to validate a webhook against by reading `repository.owner.login`/`organization.login` straight out of the unauthenticated request body. If *any* configured org has no `webhook_secret` set (the default template value, and a valid/likely configuration for orgs added later or configured without webhooks), `GitHubApp#verify_webhook_signature` returns `true` unconditionally. An attacker can therefore send an arbitrary unsigned POST to `/webhooks` naming that unsecured org in `repository.owner.login`/`organization.login`, while putting a **different, fully protected** organization/repository's `full_name` in the `repository` object that the handlers actually act on.

### Finding Description
The verification step and the action-taking step key off two different, independently attacker-controlled fields of the same JSON body:
- Verification key selection: `repository_owner` = `params.dig('repository','owner','login') || params.dig('organization','login')` [1](#0-0) 
- Action target selection: `payload.dig('repository','full_name')` [9](#0-8) 

These two are never checked for consistency. Combined with `verify_webhook_signature`'s `return true unless webhook_secret` fallback [10](#0-9) , any org in the install without a webhook secret becomes a skeleton key: naming it in `owner.login` bypasses the HMAC check entirely, after which the handler dispatch uses the unrelated `full_name` to find and mutate a `Stack`/`Repository`/`PullRequest`/`Team`/`Membership` belonging to a completely different, properly-secured organization.

### Impact Explanation
Depending on handler, this allows an unauthenticated network attacker to:
- Force `PushHandler` to enqueue `GithubSyncJob`/spec re-caching against an arbitrary tracked stack [11](#0-10) , corrupting cached deploy specs or triggering unwanted syncs.
- Drive `MembershipHandler` to create/delete `Team`/`Membership`/`User` records (per `test/controllers/webhooks_controller_test.rb` membership tests), affecting `Shipit.github_teams` authorization state used by `Authentication#force_github_authentication` [12](#0-11) .
- Manipulate PR-driven review-stack lifecycle handlers (`opened_handler.rb`, `closed_handler.rb`) for repositories under an unrelated, secured org.

This lands in the "High - escalation into `Shipit.github_teams` authorization" and potentially "unauthorized...deploy" bucket depending on which handler is abused, since it is a genuine authentication-bypass primitive on the webhook ingestion path.

### Likelihood Explanation
Requires only network access to the public `/webhooks` endpoint — no session, no GitHub credentials, no repository access. The only precondition is that the Shipit deployment has ≥2 configured GitHub orgs where at least one lacks a `webhook_secret` — a state explicitly present in shipped configuration templates (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets.yml`) and plausible for real multi-org installs that provision orgs before wiring up their GitHub App webhook secret.

### Recommendation
Bind verification and action to the same identity: after selecting `github_app` via `repository_owner`, require that `payload.dig('repository','full_name')` (and `organization.login` for org-level events) actually belongs to the same organization used for verification before dispatching to handlers. Additionally, treat a missing/blank `webhook_secret` as "reject all webhooks for this org" rather than "accept all", or require `webhook_secret` to be present for any org configured, failing fast at boot otherwise.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `OrgWithoutSecret` (no `webhook_secret`) and `OrgSecured` (a real `webhook_secret`, hosting the target stack, e.g. `OrgSecured/target-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": { "owner": { "login": "OrgWithoutSecret" }, "full_name": "OrgSecured/target-repo" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgWithoutSecret")`, whose `verify_webhook_secret` returns `true` regardless of signature [3](#0-2) .
4. `PushHandler.call(params)` resolves the stack via `full_name = "OrgSecured/target-repo"` [8](#0-7)  and enqueues `GithubSyncJob` for that stack, despite the request never being validated against `OrgSecured`'s secret.
