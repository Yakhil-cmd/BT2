### Title
Cross-organization forged commit status leads to unauthorized continuous deployment - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
The `M-05` bug class describes a value-transition failure where an entity's action (dropping a boost) is bound to an old owner via an unverified side condition, letting authority "leak" across an ownership boundary. The analogous binding here is: the *organization whose webhook signature was verified* must equal *the organization whose repository/commit state is mutated*. In `WebhooksController`, `verify_signature` derives the signing organization from the same untrusted JSON body it is about to authenticate, but `StatusHandler#process` — one of the handlers invoked after that check passes — mutates commit state by SHA only, with **no scoping to the repository/organization that was actually authenticated**.

### Finding Description
`WebhooksController#verify_signature` picks which GitHub App/organization secret to validate the HMAC signature against by reading the payload itself: [1](#0-0) [2](#0-1) 

```
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`Shipit.github(organization: repository_owner)` looks up a **per-organization** secret when multiple GitHub Apps are configured, exactly as documented in the "Using Multiple GitHub Applications" section of the setup docs: each organization onboarded to the Shipit instance gets its own `app_id`/`webhook_secret` entry in `secrets.yml`. [3](#0-2) , [4](#0-3) 

Once `verify_signature` succeeds (i.e. the HMAC matches the secret belonging to *organization A*, which owns/controls its own GitHub App and therefore its own `webhook_secret`), `WebhooksController#create` dispatches the parsed body to the registered handler for the event type without any further check that the payload's content actually belongs to organization A: [5](#0-4) 

For the `status` event, `StatusHandler#process` resolves the affected commit **purely by SHA, globally across the entire Shipit instance**, with no filter on repository or stack ownership: [6](#0-5) 

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```

`Commit#create_status_from_github!` writes a new `Status` for the matched commit and, through `add_status`, recomputes `Commit#status` / `deployable?`, and may trigger `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` if the stack has `continuous_deployment?` enabled and the commit is `deployable?`: [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

**The broken binding, stated as an equality:**
`organization(secret used to verify signature)` should equal `organization(repository/commit actually mutated by the handler)`.
Before the attacker's request: only organization A's own repositories/commits can be affected by organization A's signed webhooks (implicit assumption). After the attacker's request: organization A's valid signature is used to authenticate a payload whose `sha` field references a commit that belongs to organization B's stack — because `Commit.where(sha:)` has no organization/repository scoping, the binding is broken and organization A can write status for organization B's commit.

### Impact Explanation
An unprivileged-with-respect-to-victim actor — anyone who legitimately administers *any one* organization onboarded to a multi-org Shipit deployment (and therefore knows their own org's `webhook_secret`, since they set up their own GitHub App per the documented multi-org workflow) — can forge a `status` webhook event, sign it with their own secret, and have it accepted by `verify_signature` (which only checks that the signature matches *some* configured organization, the one named in the attacker-controlled `repository.owner.login`/`organization.login` field of the very payload being verified). The `StatusHandler` then applies the forged status to *any* commit in the system that happens to share the given SHA, regardless of which stack/repository/organization it actually belongs to. If the victim stack has `continuous_deployment` enabled and the forged status satisfies `ci.require`, this can automatically enqueue and run `ContinuousDeliveryJob`, resulting in an **unauthorized deploy** of the victim's stack — matching the Critical impact criterion "an unauthorized deploy" listed in scope.

### Likelihood Explanation
Medium-to-high within the allowed threat model: it requires the attacker to control a legitimately configured organization on the same multi-tenant Shipit instance (a scenario explicitly documented and supported by the engine), plus a SHA collision or a scenario where the same commit SHA is shared/known across stacks (e.g., forked repositories, mirrored repos, or an attacker pushing an identical commit to their own controlled repo to obtain a matching SHA, then submitting the forged status for that SHA against the victim's stack). No GitHub App private key, `GITHUB_TOKEN`, Shipit session, or `ApiClient` token is needed — only knowledge of one's own legitimately-provisioned webhook secret.

### Recommendation
- Scope handler queries by the authenticated organization/repository, not solely by payload-supplied identifiers. In particular, `StatusHandler#process` should restrict `Commit.where(sha:)` to commits whose `stack.repository` matches the repository resolved from the *verified* webhook context (repository name plus the organization that successfully signed the request), mirroring what `Handler#repository_name`/`Handler#stacks` already does for other handlers.
- In `WebhooksController#verify_signature`, after signature verification, re-derive `repository_owner`/`repository_name` from the verified payload and enforce that this owner matches the organization key used to select the webhook secret, rejecting the request if the resolved repository does not belong to the authenticated organization.
- Consider adding a uniqueness constraint or explicit stack scoping when creating statuses from GitHub payloads instead of relying on global SHA matching.

### Proof of Concept
1. Shipit is configured with two GitHub Apps/organizations per the documented multi-org setup: `orgA` (attacker-administered) and `orgB` (victim), each with its own `webhook_secret` in `secrets.yml`.
2. Attacker identifies a commit SHA present in `orgB`'s stack (e.g., by mirroring/forking the victim's repository so an identical commit exists in `orgA`'s own repo, giving them a matching SHA they legitimately know).
3. Attacker crafts a JSON body for the `status` event:
   ```json
   {
     "sha": "<victim commit sha>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/attacker-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(orgA_webhook_secret, body)` using their own known secret for `orgA`.
5. POST to `/webhooks` with header `X-Github-Event: status`. `verify_signature` resolves `repository_owner` → `"orgA"`, fetches `orgA`'s `GitHubApp`, and successfully verifies the signature.
6. `StatusHandler#process` runs `Commit.where(sha: "<victim commit sha>")`, finds the commit belonging to `orgB`'s stack, and calls `create_status_from_github!`, writing a successful status for it.
7. If `orgB`'s stack has `continuous_deployment: true` and this status satisfies `ci.require`, `Commit#schedule_continuous_delivery` enqueues `ContinuousDeliveryJob`, resulting in an unauthorized deploy of `orgB`'s stack triggered entirely by `orgA`'s forged, but validly-signed, webhook.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
```
