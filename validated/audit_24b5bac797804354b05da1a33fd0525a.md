### Title
StatusHandler applies GitHub `status` webhooks to commits matched globally by SHA, without verifying the target commit belongs to the organization whose webhook signature was authenticated - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` writes a GitHub commit status onto `Commit.where(sha: params.sha)` without any scoping to the repository/organization that signed the webhook. The `WebhooksController#verify_signature` only proves that *someone with the secret configured for `repository.owner.login`* sent the request; it never re-checks that the `sha` (or any other payload field acted on later) actually belongs to a commit that lives under that same organization. This is the same "field acted on ≠ field covered by the verification" pattern as the reported Morpho bug (verified pair ordering vs. actual pair ordering).

### Finding Description
Signature verification in `WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`): [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw JSON is handed unmodified to every registered handler for the event: [3](#0-2) 

For the `status` event, `StatusHandler#process` looks up the commit purely by `sha`, globally across the entire `commits` table, with no filter on `repository`, `stack`, or organization: [4](#0-3) 

Contrast this with the base `Handler` class, which does define a `repository_name`/`stacks` scoping helper used by other handlers (`push`, `pull_request`, `check_suite`), but `StatusHandler` does not use it at all: [5](#0-4) 

The binding that should hold is:
`organization that authenticated the webhook (repository.owner.login used in verify_signature)` == `organization owning the commit that gets mutated (sha lookup in StatusHandler)`

Before the fix, this binding is never enforced: any org with a Shipit-configured GitHub App and a webhook secret can send a `status` event whose `repository.owner.login` matches *their own* org (so `verify_signature` passes with their own secret) while the `sha` field is set to a commit SHA belonging to an entirely different stack/organization tracked by the same Shipit instance. Since commit SHAs are public (visible on GitHub, PRs, and in the Shipit UI itself), an attacker can trivially obtain the target SHA of a victim stack.

`create_status_from_github!` writes a new `Status` for that (unrelated) commit and can flip its computed `state`, which directly feeds `Commit#deployable?` and the merge queue: [6](#0-5) [7](#0-6) 

`stack.schedule_merges` is triggered whenever a new status becomes `success`, meaning a forged success status on a victim's commit can push it into the merge queue / mark it deployable, i.e., a cross-organization write that changes deploy/merge eligibility for a repository the attacker does not control.

### Impact Explanation
This crosses the organization boundary that the signature check is supposed to enforce: it lets an attacker who legitimately controls one Shipit-tracked GitHub organization (with a known/self-configured webhook secret) forge a commit status for a completely unrelated organization's commit. Because `Commit#deployable?` and `Stack#schedule_merges` depend on status state, this can be used to make an otherwise-failing or CI-pending commit in a *victim's repository* appear `success`, unblocking deploys and merge-queue processing for that commit — i.e., contributing to an unauthorized deploy/merge decision on a repository outside the attacker's authorization scope. This matches the "escalation into authorization boundaries" / "unauthorized deploy or merge" impact class.

### Likelihood Explanation
Likelihood is high for any deployment where more than one GitHub organization/app is configured in Shipit (multi-tenant style, as shown by `config/secrets.development.shopify.yml` supporting multiple orgs), since any one of those organizations' operators (who legitimately know or set their own `webhook_secret`) can send a crafted `status` payload naming any SHA. No privileged Shipit account, API token, or session is required — only knowledge of one org's webhook secret (which the attacker owns) and the target's public commit SHA.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope through `Handler#stacks`) should verify that the resolved commit's stack/repository owner matches the authenticated `repository_owner` used during signature verification, e.g., by requiring and validating `repository.full_name`/`repository.owner.login` in the handler params and filtering `Commit.where(sha: params.sha, stack: { repository: matching_repo })` rather than a bare global SHA lookup. More generally, `WebhooksController` should pass the verified organization down to handlers and have the base `Handler` enforce that every payload's `repository` field is consistent with it, closing the general class of "authenticated org vs. acted-upon repository" mismatches across all handlers.

### Proof of Concept
1. Attacker controls (or creates) a GitHub organization `attacker-org` that has been configured in Shipit with its own `webhook_secret` (`Shipit.github(organization: 'attacker-org')`), which is normal, legitimate self-service setup.
2. Attacker obtains the SHA of a commit in `victim-org/victim-repo` (public info, e.g. from GitHub or the Shipit UI) that is currently blocked/pending/failing.
3. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "attacker-org" } }
}
```
4. Attacker signs the raw body with `attacker-org`'s known `webhook_secret` and sets `X-Hub-Signature` accordingly.
5. `WebhooksController#verify_signature` looks up `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature (using attacker's own secret) per [1](#0-0) .
6. `StatusHandler#process` finds the matching `Commit` purely `by sha`, ignoring that it belongs to `victim-org`, and creates a `success` status on it per [4](#0-3) .
7. `Commit#add_status` observes the state transition and calls `stack.schedule_merges` per [7](#0-6) , potentially advancing the victim's merge queue / marking the commit deployable.

Note: I was not able to fully trace `stack.schedule_merges`/merge-queue merge execution path within the given tool budget to confirm it results in an actual GitHub merge API call versus only internal queue-state changes; this would need to be verified in a live session, but the write to a cross-organization commit's deploy-gating status is confirmed directly from the code shown above.
