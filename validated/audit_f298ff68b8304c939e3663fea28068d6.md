## Title
Retroactive `base_tps_fee`/`tps_interval` rate change lets committed TPS-fee liabilities diverge from what was actually paid - (File: `storage.js`)

### Summary
`getFinalTpsFee()` recomputes the "real" TPS fee owed by a unit using the system-var values effective *at the unit's own `main_chain_index`*, while the unit paid its TPS fee at composition time using the system-var values effective at its `last_ball_mci` (a strictly earlier point). Because `base_tps_fee`, `tps_interval` and `tps_fee_multiplier` are mutable governance values that can change between those two MCIs (via a `system_vote`/`system_vote_count` unit that any balance-holder can post), the retroactively computed liability can differ from what the payer actually locked in when composing the unit — exactly the same "rate changed after the fact, accrued value not settled at the old rate" pattern as the `VirtualStakingRewards::notifyRewardAmount` bug.

### Finding Description
- At composition/validation time, the fee a unit must pay is computed from system vars evaluated at `last_ball_mci`: [1](#0-0) 
`getLocalTpsFee()` reads `base_tps_fee`, `tps_interval`, `tps_fee_multiplier` via `getSystemVar(subject, last_ball_mci)` — i.e., the vars that were in force when the unit's last ball was stable. `validateTpsFee` uses the same `last_ball_mci`-based values to check that the posted `tps_fee` is sufficient: [2](#0-1) 

- After the unit itself becomes stable (which can happen at a materially later MCI than `last_ball_mci`, since `last_ball_mci` only has to be *some* earlier stable point), the "final"/actual fee owed is recomputed with a different MCI reference — the unit's own `main_chain_index`, not `last_ball_mci`: [3](#0-2) 
The inline comment `// not at last_ball_mci` explicitly flags this discrepancy in the source.

- This final value is then diffed against what was actually paid (`objUnitProps.tps_fee`, locked in at composition using the old rate) and the delta is applied to each recipient's running `tps_fees_balance`: [4](#0-3) 

- The rate inputs (`base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) are not fixed protocol constants; they are voted on via `system_vote` messages that any unit author can post and that are tallied by balance-weighted majority in `countVotes`: [5](#0-4) [6](#0-5) 
Once counted, the new value is pushed onto `storage.systemVars[subject]` and becomes effective for all MCIs from the vote-count MCI onward: [7](#0-6) 

- Consequently, an address that composed and posted a unit paying `tps_fee` computed under the *old* rate can have its `main_chain_index` fall after a vote-count MCI that changes the rate, so `getFinalTpsFee` recomputes its true liability under the *new* rate. If the rate went up, `total_tps_fees_delta` becomes negative and the payer's `tps_fees_balance` is driven down (into deficit) even though the payer fully satisfied the requirement that was in force when they built and signed the unit. This is structurally identical to `notifyRewardAmount` reducing `rewardRate` without calling `_updateRewardForAll()`/settling previously-accrued `rewards[user]` at the old rate before applying the new one.

### Impact Explanation
A negative/growing deficit in `tps_fees_balance` for an address is not merely cosmetic: `validateTpsFee` requires the running balance plus newly attached `tps_fee` to cover `min_tps_fee` and the minimum acceptable multiplier before any further unit from that address can be accepted: [8](#0-7) 
This means honest users whose committed fee becomes "insufficient" purely due to a post-hoc, majority-vote-driven rate change are forced to overpay on subsequent units to clear a deficit they did not agree to when they posted their earlier unit, effectively causing them to lose funds/value relative to what they legitimately committed to — an economic loss enforced network-wide, not limited to a single operator. In the opposite direction (rate decreases), other addresses gain unearned credit at the expense of the fee pool's intended balance, distorting the anti-spam fee economics for everyone.

### Likelihood Explanation
Reachable by ordinary, unprivileged actors: posting a `system_vote` unit is available to any address (`app: 'system_vote'`), and votes are tallied by held balance rather than any special operator role, so a sufficiently coordinated set of unprivileged holders (or a single large holder) can shift `base_tps_fee`/`tps_interval`/`tps_fee_multiplier` between when a victim's last-ball MCI and the victim's own unit's MCI become stable — a window that is normal and unavoidable in DAG finalization, not an edge case requiring adversarial timing beyond posting a vote around the time other units are in flight.

### Recommendation
Compute the "final"/authoritative TPS fee owed using the same reference point (`last_ball_mci`) that was used to validate and let the payer lock in the fee at composition time, i.e. change `getFinalTpsFee()` to call `getSystemVar('base_tps_fee', <the unit's last_ball_mci>)` / `getSystemVar('tps_interval', <last_ball_mci>)` instead of the unit's own `main_chain_index`, so that a rate change that becomes effective after a unit's `last_ball_mci` cannot retroactively alter the liability that the unit's author already satisfied under the rules in force at composition time.

### Proof of Concept
Conceptual sequence (protocol-level, no code execution available in this environment):
1. Address A composes and posts unit U with `last_ball_mci = M0`. At `M0`, `base_tps_fee = R0`. A's client (per `getLocalTpsFee`/`validateTpsFee`) computes and pays `tps_fee` sufficient under `R0`.
2. Before U itself stabilizes (U's own `main_chain_index = M1 > M0`), a balance-weighted majority posts and stabilizes `system_vote`/`system_vote_count` units raising `base_tps_fee` to `R1 > R0`, effective starting at some MCI ≤ M1.
3. When U stabilizes, `main_chain.js` calls `storage.updateTpsFees(conn, [M1])`, which calls `getFinalTpsFee(U)`; this reads `base_tps_fee` at `mci = M1` (now `R1`), producing a higher `tps_fee` than U actually paid.
4. `total_tps_fees_delta = U.tps_fee(paid under R0) - tps_fee(recomputed under R1) < 0`, and this negative delta is subtracted from A's `tps_fees_balance` in `tps_fees_balances`.
5. A's next unit is now validated against a `tps_fees_balance` deficit it never agreed to, per `validateTpsFee`'s check `tps_fees_balance + objUnit.tps_fee * share < min_tps_fee * share`, forcing A to overpay to compensate for a rate hike it settled correctly at the time of posting U.

function getFinalTpsFee(objUnitProps) {
	const mci = objUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', mci); // not at last_ball_mci
	const tps_interval = getSystemVar('tps_interval', mci);

	console.log(`final tps at ${objUnitProps.unit} ${tps}`);
	return Math.round(base_tps_fee * (exp(tps / tps_interval) - 1));
}

async function getLocalTpsFee(conn, objUnitProps, count_units = 1) {
	const objLastBallUnitProps = await readUnitProps(conn, objUnitProps.last_ball_unit);
	const last_ball_mci = objLastBallUnitProps.main_chain_index;
	const base_tps_fee = getSystemVar('base_tps_fee', last_ball_mci); // unit's mci is not known yet
	const tps_interval = getSystemVar('tps_interval', last_ball_mci);
	const tps_fee_multiplier = getSystemVar('tps_fee_multiplier', last_ball_mci);
	const tps = await getLocalTps(conn, objUnitProps, count_units);
	console.log(`local tps at ${objUnitProps.unit} ${tps}`);
	const tps_fee_per_unit = Math.round(tps_fee_multiplier * base_tps_fee * (exp(tps / tps_interval) - 1));
	return count_units * tps_fee_per_unit;
}
