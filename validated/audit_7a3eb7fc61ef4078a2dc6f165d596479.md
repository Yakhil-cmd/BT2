## Analysis: Missing sequence validation in `dataFeedExists()` allows unstable/invalid units to satisfy data-feed conditions

The Stake DAO incident hinged on a peripheral component (`L1BlockOracleUpdater`) accepting unverified/forged data through a bridge and treating it as trusted oracle state, which downstream vote-proof logic relied on for authorization. The closest analog in `ocore` is the data-feed oracle mechanism used by `in data feed` (address definitions/authentifiers) and `in_data_feed` (AA oscript), both of which resolve to `dataFeeds.dataFeedExists()`.

### Root cause

`dataFeedExists()` has a fast-path that scans `storage.assocUnstableMessages` (units not yet stabilized) when called from AA context (`bAA=true`): [1](#0-0) 

This loop filters candidate units only by `objUnit.bAA` (must be an AA), MCI range, and author address intersection — it never checks `objUnit.sequence`.

Compare this to the sibling function `readDataFeedValue()`, which performs the analogous unstable-message scan but explicitly excludes non-good-sequence units: [2](#0-1) 

The line `if (objUnit.sequence !== 'good') continue;` present in `readDataFeedValue` (line 219) has no counterpart in `dataFeedExists` (lines 34-43). "Sequence" marks whether a unit is a winner or loser of a double-spend race — a unit with `sequence` other than `'good'` (`'temp-bad'`/`'final-bad'`) will never contribute valid state once stable.

### Reachability

`dataFeedExists` backs:
- `in_data_feed` in AA oscript formulas: [3](#0-2) 
- `in data feed` in address definitions/authentifiers, evaluated at `objValidationState.last_ball_mci`: [4](#0-3) 

An attacker who is also an AA author (or controls an AA address usable as an "oracle" reference) can post a `data_feed` message inside a unit that is designed to double-spend (conflict with another of the attacker's own units), making its `sequence` temporarily `'good'` while unstable but destined to become `'final-bad'` once stabilized. Any other AA that queries `in_data_feed[[oracles=<attacker AA address>, feed_name=..., feed_value=...]]` during this unstable window will find the condition satisfied via the buggy unstable-scan path in `dataFeedExists`, since it does not check sequence.

### Impact

An AA (or address definition) that gates a payment/authorization on `in_data_feed`/`in data feed` referencing another AA as "oracle" can be tricked into releasing funds based on a data-feed message carried by a unit that is provably going to be excluded from the final ledger (losing sequence). This is a fund-loss/incorrect-authorization vector analogous to the external report's "poisoned oracle -> forged proof -> drained funds" pattern, and can also cause node disagreement if different nodes evaluate the trigger at different DAG-stability snapshots.

### Recommendation
Add the same `if (objUnit.sequence !== 'good') continue;` guard to the unstable-message loop in `dataFeedExists()` (mirroring `readDataFeedValue()`), so `in_data_feed`/`in data feed` cannot be satisfied by messages carried in units that are not (or will not be) part of the `'good'` sequence.

### Title
Data-feed existence check omits sequence validation, allowing doomed/bad-sequence units to satisfy `in_data_feed`/`in data feed` oracle conditions - (File: data_feeds.js)

### Summary
`dataFeedExists()`, which backs the `in_data_feed` oscript function and the `in data feed` address-definition/authentifier operator, scans unstable units for a matching data-feed message but — unlike its sibling `readDataFeedValue()` — never checks `objUnit.sequence`. This lets a data-feed message from a unit destined to become `sequence='final-bad'` (a double-spend loser) satisfy oracle-based spending/authorization conditions while still unstable.

### Finding Description
`dataFeedExists()`'s `bAA` branch iterates `storage.assocUnstableMessages`, filtering only on `objUnit.bAA`, MCI range, and author address [5](#0-4) . It omits the sequence check that the equivalent code path in `readDataFeedValue()` applies [6](#0-5) . Consequently a `data_feed` message posted by a unit that is (or will become) a double-spend loser can still be treated as an existing/matching data feed by any consumer of `dataFeedExists`, i.e. `in_data_feed` in AA formulas [7](#0-6)  and `in data feed` in address definitions/authentifiers [8](#0-7)  and [4](#0-3) .

### Impact Explanation
AAs and shared addresses that use an oracle address (which can itself be another AA, or attacker-influenced in more complex compositions) to gate payments via `in_data_feed`/`in data feed` can act on a data-feed value that is guaranteed to disappear from the final, stable ledger once the posting unit's sequence resolves to bad. This can cause an AA to release funds (or an address definition to authorize a spend) based on state that never becomes canonical — a fund-loss/incorrect-authorization condition, and a source of node disagreement since sequence resolution timing can vary across the DAG's stabilization process.

### Likelihood Explanation
Exploitation requires the attacker to control (or otherwise convince) both the "oracle" unit poster and to be able to conflict/double-spend that same unit, and requires a target AA/address that references this oracle for authorization within the vulnerable unstable window — a moderate-complexity but fully self-contained, permissionless setup requiring no privileged network position, matching the "unprivileged AA/unit poster" reachability constraint.

### Recommendation
Add `if (objUnit.sequence !== 'good') continue;` to the unstable-unit loop in `dataFeedExists()` in `data_feeds.js`, mirroring the check already present in `readDataFeedValue()`, so that only `'good'`-sequence units can satisfy `in_data_feed`/`in data feed` conditions.

### Proof of Concept
1. Attacker deploys AA `X` with a `data_feed` message that is trivially controllable/attacker-triggerable.
2. Attacker triggers AA `X` twice with conflicting inputs (creating a double-spend), so one of the two resulting response units carrying the `data_feed` message ends up transiently `sequence='good'` while unstable, but is mathematically destined to resolve to `'final-bad'` once MC-stabilized.
3. Before stabilization, attacker triggers victim AA `Y`, whose oscript contains `in_data_feed[[oracles=X, feed_name=..., feed_value=...]]` (or a shared address using `['in data feed', [X], ...]`).
4. `dataFeedExists()` scans `storage.assocUnstableMessages`, finds AA `X`'s message without checking `sequence`, and returns `true`, allowing AA `Y` to execute its fund-releasing branch.
5. Once MC advances and stabilizes, AA `X`'s conflicting unit becomes `sequence='final-bad'`, meaning the data feed that authorized AA `Y`'s payout never should have existed in the canonical ledger.
