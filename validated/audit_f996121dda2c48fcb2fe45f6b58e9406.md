### Title
Accrual overflow in scaled RAY valuation permanently freezes a market before the index cap engages - (File: contracts/pool/src/cache/scale.rs)

### Summary
Bug class from the report: arithmetic/buffer overflow leading to denial of service of a core state transition. The analog: every controller verb accrues interest first, and accrual computes total debt/supply value as `scaled_shares * index` in RAY via `scaled_to_original` / `Ray::mul`. When scaled shares are very large, this product overflows `i128` and panics with `MathOverflow` while the borrow index is still below `MAX_BORROW_INDEX_RAY`, so the intended cap never engages and the market is permanently frozen: no repay, withdraw, liquidation, or `update_indexes` ever succeeds again. All supplier and borrower funds in that market are permanently locked and the debt can never be settled — protocol insolvency for that book.

### Finding Description
`update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY` in `common/src/rates/index.rs:13-19`, and `update_supply_index` saturates its distribution at `MAX_SUPPLY_INDEX_RAY` (`common/src/rates/index.rs:29-45`). However, the actual overflow happens earlier, in the value multiplication: `calculate_utilization` calls `scaled_to_original(env, borrowed, borrow_index)` and `scaled_to_original(env, supplied, supply_index)` (`contracts/pool/src/cache/scale.rs:23-24`), and `calculate_supplier_rewards` computes `borrowed.mul(new_index)` (`common/src/rates/index.rs:80-81`). `Ray::mul` widens to `I256` but the result must still fit `i128` (`common/src/math/fp_core.rs:108-118`); once `scaled * index / RAY > i128::MAX` the call panics with `GenericError::MathOverflow`.

Scaled shares are RAY-denominated (`amount * 10^(27-d) * RAY / index`), so the ceiling is hit when the token-denominated total debt approaches `i128::MAX` base units — roughly 1.7e20 tokens for an 18-decimal asset — times the index growth. At sustained high utilization on a steep rate curve, the index multiplier brings that horizon in dramatically, and there is no supply cap or guard preventing an unprivileged user from creating that scaled-share mass. The repository's own regression test demonstrates this: `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361` shows `update_indexes` failing with `MATH_OVERFLOW`, `borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `withdraw`/`repay` also panicking.

Because every state-changing pool op accrues before acting, the panic is unrecoverable: index accrual is monotone in time, so no wait, repay, or recapitalize can unwind it. `clean_bad_debt`/`recapitalize` also flow through the cache and hit the same panic.

### Impact Explanation
Permanent freezing of funds: all supplied tokens in the frozen market can never be withdrawn, all debt positions can never be repaid or liquidated, and liquidators cannot act — which also makes the protocol's bad debt in that book insolvent since collateral seized elsewhere cannot offset it. A single unprivileged address can create the condition (supply + borrow at scale), and once the ceiling is crossed, no role can recover the market.

### Likelihood Explanation
Medium. It requires a whale-scale position (on the order of 10^18+ base units of scaled shares) and sustained high utilization so the borrow index compounds meaningfully — capital-intensive but not privileged, and borrowable capital can be flash-amplified or built from the attacker's own funds. No admin action, oracle manipulation, or third-party cooperation is needed: `supply`, `borrow`, and `update_indexes` are all unprivileged entrypoints. Once the threshold state exists, the freeze is deterministic and permanent rather than probabilistic.

### Recommendation
Make index accrual saturate rather than panic at the RAY value ceiling:
- Clamp `borrowed`/`supplied` scaled-share mass or detect overflow in `scaled_to_original`/`calculate_supplier_rewards` and saturate the accrued value at `i128::MAX` instead of panicking, so accrual completes and markets remain operable (debt simply stops growing in value terms beyond the representable bound).
- Alternatively, enforce a protocol-level cap on total scaled supply/debt per market (or on `scaled * index` headroom) at `supply`/`borrow` time so the product can never overflow — this makes the invariant explicit rather than relying on the index cap, which currently cannot engage before the value product overflows.
- Add a recovery path (e.g., admin-free `recapitalize`/write-down that skips accrual) so a market at the ceiling is not permanently bricked.

### Proof of Concept
`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360` already demonstrates the end state:

1. Attacker supplies `10^9 * 10^18` units of an 18-decimal asset and borrows ~98% of it (caps lifted only because the test uses helper markets; equivalent mass is achievable via repeated `supply`/`borrow` and flash-loan-amplified liquidity).
2. Time advances at high utilization; `update_indexes` eventually returns `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY` — the index cap never engages (`large_positions_and_long_horizons.rs:343-352`).
3. Every subsequent `withdraw` and `repay` panics with `MathOverflow` because accrual runs first (`large_positions_and_long_horizons.rs:354-356`); the market, and all user funds in it, are permanently frozen.

The root cause is the missing saturation/cap on the `scaled * index` product in `scaled_to_original`/`calculate_supplier_rewards` (`common/src/rates/index.rs:80-81`, `contracts/pool/src/cache/scale.rs:23-24`), reachable purely through the unprivileged `supply`/`borrow`/`update_indexes` entrypoints.
