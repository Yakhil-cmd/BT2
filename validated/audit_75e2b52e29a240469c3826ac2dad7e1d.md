### Title
Cross-repository commit-status spoofing via `StatusHandler` breaks the "authenticated organization = repository being written" binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler` updates commit status for **any** commit in the entire database matching the payload's `sha`, without ever checking that the commit's stack/repository corresponds to the `repository` the webhook was actually delivered for. This breaks exactly the trust binding described in the report's bug class: the GitHub organization/repository whose HMAC secret validated the incoming webhook is not the same repository whose data ends up being mutated.

### Finding Description
`WebhooksController#verify_signature` looks up the GitHub App config (and thus the HMAC secret) using `repository_owner`, derived from the payload's `repository.owner.login` (or `organization.login`), and validates the raw body signature against that organization's secret: [1](#0-0) 

This only proves the request came from *some org configured in Shipit* that legitimately owns the repository named in the payload — it says nothing about which `Commit`/`Stack` records may be touched.

`Shipit::Webhooks::Handlers::Handler` provides a `stacks` helper that scopes any handler's effects to the repository named in the payload: [2](#0-1) 

Other handlers, e.g. `PushHandler` and `CheckSuiteHandler`, correctly use this `stacks` scope before touching any records: [3](#0-2) [4](#0-3) 

However `StatusHandler` never calls `stacks`/`repository_name` at all. It declares no `repository` field in its parameter contract and queries `Commit` globally by `sha`: [5](#0-4) 

Because `Commit.sha` is not guaranteed unique per organization (identical SHAs commonly occur across forks, mirrors, shared initial/base commits, cherry-picks, or squash-merges that reproduce an existing tree/commit), an org whose own webhook signature validates successfully can submit a `status` event carrying a `sha` that happens to also exist in a stack belonging to a **completely different repository/organization** configured in the same Shipit instance. `StatusHandler#process` will then call `commit.create_status_from_github!` on that unrelated commit: [6](#0-5) 

`create_status_from_github!` feeds into `add_status`, which can transition the commit's aggregated CI state and fires the `deployable_status` hook, and each new `Commit` record schedules continuous delivery on creation: [7](#0-6) 

For a stack with `continuous_deployment` enabled, flipping a commit's status to `success` can be enough to make it eligible for automatic deployment, and for merge-queue stacks it can satisfy `ci.require` gating used by `MergeRequest` processing — i.e., the boundary broken is: **organization A authenticated (signature verified) ≠ repository/stack B whose deploy-readiness state is written**.

### Impact Explanation
This lets any organization that has legitimately onboarded a repository into this Shipit instance (and therefore controls a valid webhook secret) forge CI status for commits belonging to a different, unrelated stack, as long as it can produce/guess a matching SHA. Depending on gating configuration (`continuous_deployment`, `ci.require`, merge-queue `ci.require`), this can lead to an **unauthorized deploy** of a commit whose CI checks were never actually run by that repository's real CI, satisfying the "High/Critical" impact bar (escalation into deploy authorization state; unauthorized deploy) defined in scope.

### Likelihood Explanation
Exploitation requires: (1) attacker organization already has a Shipit-configured GitHub App/webhook (i.e., legitimately onboarded — not a stranger to the system, but crucially not privileged with respect to the *victim* repository), and (2) a SHA collision with a commit tracked in the victim stack. SHA collisions are not cryptographically forced by an attacker (SHA-1 collision) but are realistic in practice: forks sharing history, template/scaffold repos with identical initial commits, vendored/mirrored repos, or shared upstream commits merged into multiple downstream repos all produce identical SHAs across repository boundaries in Shipit's `Commit` table (which has no compound uniqueness on `(stack_id, sha)` enforced against cross-repo reuse of the underlying git object). Given this, likelihood is low-to-moderate but the described binding violation is unambiguous and directly analogous to the report's "push funds to any account it name-checks, without validating the true recipient" issue: the code writes to *any* row matching an attacker-suppliable key not covered by the authorization check.

### Recommendation
Scope `StatusHandler` (and any other handler that queries `Commit`/`Stack` by attacker-controlled identifiers) through the shared `stacks` helper, joining on `repository_name` from the payload, exactly as `PushHandler`/`CheckSuiteHandler` already do:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
Additionally require `repository.full_name` in the `StatusHandler` parameter contract so the binding is validated (payload must always declare which repository the status belongs to, and the handler must enforce it matches the record being mutated).

### Proof of Concept
1. Org "attacker-org" legitimately configures a GitHub App/webhook secret in this Shipit instance for `attacker-org/attacker-repo` and has a stack tracking that repo.
2. Org "victim-org" has a completely separate stack `victim-org/victim-repo` with `continuous_deployment: true`, tracking a commit whose SHA happens to equal (via fork/shared-history/template reuse) a commit that also exists in `attacker-org/attacker-repo`'s history.
3. Attacker sends a `status` webhook, correctly signed with `attacker-org`'s own webhook secret (a request they can legitimately produce, e.g. from their own CI or by replaying/crafting a signed payload since they know their own secret), setting `sha` to the shared commit and `state: success`.
4. `WebhooksController#verify_signature` validates successfully because the signature is checked against `attacker-org`'s (correct) secret for the `repository.owner.login` claimed in the payload: [1](#0-0) 
5. `StatusHandler#process` finds `Commit.where(sha: params.sha)` across the whole database — including the row belonging to `victim-org`'s stack — and calls `create_status_from_github!` on it: [6](#0-5) 
6. The victim's commit is marked deployable/successful despite never being validated by `victim-org`'s CI, potentially triggering an automatic (unauthorized) deploy via `schedule_continuous_delivery`.
