### Title
Webhook signature verification binds to the wrong organization, letting one tenant's GitHub App forge events for another tenant's repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports hosting multiple GitHub Apps/organizations from a single instance (see `config/secrets.development.shopify.yml`/`test/dummy/config/secrets_double_github_app.yml`, which configure `OrgOne` and `OrgTwo` each with their own `webhook_secret`). The `/webhooks` endpoint verifies the HMAC signature using the GitHub App selected by `repository.owner.login` (or `organization.login`), but every webhook handler resolves the `Stack`/`Repository` to act on using a different, unvalidated field of the very same payload: `repository.full_name`. Because these two fields are never cross-checked, an attacker who holds a valid `webhook_secret` for *any* org configured on the instance can forge a signature that passes verification while pointing `repository.full_name` at a completely different org/repo, causing Shipit to act on a stack it was never authorized to touch by that signer.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App configuration solely from `repository_owner`: [1](#0-0) [2](#0-1) 

`repository_owner` is read from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`). The chosen app's `webhook_secret` is then used to verify the HMAC over the raw request body via `GitHubApp#verify_webhook_signature`: [3](#0-2) 

Once the signature is accepted, `Shipit::Webhooks.for_event(event)` dispatches the parsed `params` to handlers, all of which inherit from `Handler` and resolve the target repository from a *different* JSON key — `repository.full_name` — with no comparison back to `repository_owner`: [4](#0-3) 

This pattern repeats in every concrete handler that touches a repository/stack, e.g. `PushHandler` (`stacks` lookup drives `sync_github`) and the pull-request handlers that create/archive review stacks: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon `Repository`/`Stack`) are two independent, attacker-supplied fields inside the same JSON body, and Shipit's signature check only proves "this body was signed with Org X's secret" — not "this body's target repository belongs to Org X" — the binding `authenticated_org == repository_being_written` is never enforced. An operator running one Shipit instance for multiple GitHub organizations (explicitly supported, per the multi-org secrets fixtures) is exposed: whoever controls the webhook secret for *one* tenant org can forge a signature for that org while making the payload's `repository.full_name` point at a stack owned by a different, unrelated org on the same instance.

### Impact Explanation
This crosses a tenant/repository boundary in a way the platform's core trust model assumes is impossible (signature verification is supposed to scope the attacker's authority to their own org's repositories). Exploiting it via `pull_request` `opened`/`labeled` events lets the attacker drive `ReviewStackAdapter#find_or_create!`/`archive!`/`unarchive!` on another org's `ReviewStack`, which enqueues provisioning/deprovisioning and ultimately deploy-script execution against that victim stack's infrastructure using Shipit's own GitHub credentials — an unauthorized deploy/provisioning action against a repository the attacker's org has no legitimate relationship to. Via `PushHandler`, the attacker can also force `Stack#sync_github` with an attacker-chosen `expected_head_sha` on an unrelated stack. This matches the "unauthorized deploy" / cross-tenant write impact category.

### Likelihood Explanation
Exploitation requires the attacker to legitimately control a `webhook_secret` for *some* GitHub App/org configured on the target Shipit instance — plausible in any multi-tenant deployment (the exact configuration shape shown in `test/dummy/config/secrets_double_github_app.yml`) where separate teams/orgs each manage their own GitHub App but share one Shipit installation. No repository write access, session, `ApiClient` token, or GitHub App private key for the *victim* org is needed — only knowledge of one's own (unrelated) org's webhook secret, which is a normal, low-privilege credential every onboarded tenant already possesses.

### Recommendation
After signature verification, validate that `repository.owner.login` (the org whose secret verified the request) matches the owner segment of `repository.full_name` used by the handlers before any handler acts on it — i.e., enforce the equality `repository_owner == full_name.split('/').first` in `WebhooksController` (or centrally in `Handler#initialize`) and reject/`422` the request otherwise.

### Proof of Concept
1. Instance is configured with two orgs, `OrgA` (victim, has a Stack/ReviewStack-enabled repo `OrgA/app`) and `OrgB` (attacker's own org), each with its own `webhook_secret`, per the pattern in `test/dummy/config/secrets_double_github_app.yml`.
2. Attacker, who legitimately knows `OrgB`'s `webhook_secret`, crafts a `pull_request` `opened` JSON body where `repository.owner.login = "OrgB"` (so `WebhooksController#repository_owner` selects `OrgB`'s app/secret) but `repository.full_name = "OrgA/app"`.
3. Attacker computes `X-Hub-Signature` over this raw body using `OrgB`'s `webhook_secret` and POSTs it to `/webhooks` with `X-Github-Event: pull_request`.
4. `verify_signature` succeeds (verified against `OrgB`'s secret for the whole raw body).
5. `Shipit::Webhooks::Handlers::PullRequest::OpenedHandler#process` resolves `repository` via `Repository.from_github_repo_name(params.repository.full_name)` = `OrgA/app`, and — if provisioning conditions are met — calls `ReviewStackAdapter#find_or_create!`, creating/provisioning a review stack on `OrgA`'s repository triggered entirely by a payload authenticated only against `OrgB`'s credentials.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
