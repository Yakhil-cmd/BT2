### Title
`Api::CCMenuController#stack` bypasses the `stacks` scope enforced by `Api::BaseController`, allowing a stack-scoped API token to read any stack's build state - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController#stack` resolves stacks through `stacks.from_param!`, which restricts lookups to `current_api_client.stack_id` when the client is scoped [1](#0-0) . `Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping that scoping entirely [2](#0-1) . A stack-scoped `ApiClient` with only `read:stack` permission can therefore fetch CCMenu build status/activity for any stack in the system, not just the one it was issued for.

### Finding Description
Binding claimed: `stack` resolved in `CCMenuController#show` for token `T` and `stack_id` `S` == `stack` resolved in `Api::StacksController#show` for the same token `T` and `stack_id` `S`. They diverge.

- `Api::StacksController#stack` (inherited scoping pattern used by other subclasses like `MergeRequestsController`, `CommitsController`) calls `stacks.from_param!(params[:id])`, where `#stacks` is `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` [1](#0-0) [3](#0-2) . For an out-of-scope `stack_id`, `Stack.where(id: current_api_client.stack_id).from_param!(...)` raises `ActiveRecord::RecordNotFound`, yielding 404.
- `Api::CCMenuController#stack` instead calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation [2](#0-1) , completely bypassing the `current_api_client.stack_id` restriction that `#stacks` would have applied.
- `ApiClient#check_permissions!` only validates the `operation:scope` permission string (e.g. `read:stack`); it has no awareness of `stack_id` at all [4](#0-3) . The only enforcement of per-stack scoping in this engine is the controller-level `#stacks` method, and `CCMenuController` opts out of it.

Attacker request: any holder of a legitimately-issued, stack-scoped `ApiClient` token (e.g. the one created for the CCMenu URL feature via `Shipit::CCMenuUrlController#client`, which is created with only `permissions: %w[read:stack]` and no `stack_id` restriction is enforced against the requested stack) sends `GET /api/stacks/:other_owner/:other_repo/:other_env/ccmenu?token=<their_token>`. Because `#stack` in `CCMenuController` never consults `stacks`, any `stack_id` resolves successfully regardless of the token's assigned stack, and the response leaks that other stack's `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`.

No existing guard prevents this: `require_permission :read, :stack` only checks the permission string, not the stack identity [5](#0-4) ; `authenticate_api_client` is overridden only to add the `?token=` query-string auth path and still calls `super`, but this has no bearing on stack scoping [6](#0-5) .

### Impact Explanation
An attacker holding any stack-scoped `ApiClient` token with `read:stack` permission (such tokens are routinely minted per-stack, e.g. by `CCMenuUrlController`) can enumerate and read build/deploy status metadata (name, activity, last build status/label/time, web URL) for every stack in the Shipit instance, not just the stack the token was scoped to. This is a cross-tenant read of stack state that the sibling `Api::StacksController#show` correctly denies for the same token, demonstrating the divergence is a genuine authorization bypass rather than intended behavior. This matches the High severity category "unauthenticated/unauthorized escalation into reading stack state" — it is repeatable against arbitrary stacks and stack IDs are guessable/discoverable (owner/repo/env triplets).

### Likelihood Explanation
Preconditions: the attacker must possess a valid, currently-issued stack-scoped `ApiClient` token with `read:stack` permission — no Shipit secrets, sessions, or elevated roles are required. Such tokens are created and handed out as part of normal CCMenu integration (`CCMenuUrlController#client`) or via the `Api::ApiClientsController`. Given any such token, exploitation is a single unauthenticated GET request with a different `stack_id` path segment; no timing or race conditions are needed, and it is trivially repeatable across all stacks.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped lookup like other subclasses, e.g. replace `Stack.from_param!(params[:stack_id])` with `stacks.from_param!(params[:stack_id])`, removing the private override entirely so it falls back to `Api::BaseController#stack`.

### Proof of Concept
minitest plan (in `test/controllers/api/ccmenu_controller_test.rb` style, using existing `ApiControllerTestCase` helpers):
1. Create two stacks, `@scoped_stack` and `@other_stack`.
2. Create an `ApiClient` `@client` with `permissions: %w[read:stack]` and `stack_id: @scoped_stack.id`.
3. `get :show, params: { stack_id: @other_stack.to_param, token: @client.authentication_token }` on `Api::StacksController#show` → assert `response.status == 404`.
4. `get :show, params: { stack_id: @other_stack.to_param, token: @client.authentication_token }` on `Api::CCMenuController#show` → assert `response.status == 200` and body contains `@other_stack.to_param` as the `name` attribute.
5. Assert the divergence: same token, same out-of-scope `stack_id`, one controller returns 404, the other returns 200 with leaked stack data.
