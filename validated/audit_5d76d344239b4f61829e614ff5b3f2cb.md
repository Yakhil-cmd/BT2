### Title
`ProxyType::NonTransfer` deny-list fails open on Asset Hub Rococo, letting a non-transfer proxy move the delegator's funds and assets - (File: cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs)

### Summary
`ProxyType::NonTransfer` on Asset Hub Rococo is documented as "can execute any call that does not transfer funds or assets," but is implemented as a deny-list that only blocks `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques`. The identical bug class was found and fixed on Asset Hub Westend (fail-open deny-list, GH issue #12466, patched by PR #12771) and partially on the staking-async parachain runtime (PR #12922), but Asset Hub Rococo was never updated and still ships the pre-fix deny-list.

### Finding Description
`InstanceFilter<RuntimeCall> for ProxyType::filter` on Asset Hub Rococo denies only five call families: [1](#0-0) 

Compare this with the already-remediated Asset Hub Westend filter, which additionally denies `ForeignAssets`, `PoolAssets`, `AssetConversion`, `Psm`, `PolkadotXcm`, `Revive`, `Vesting::vested_transfer`, and `Indices::transfer`/`force_transfer`: [2](#0-1) 

The prdoc that shipped the Westend fix confirms this exact bug class and root cause ("deny-list, so it fails open: any pallet added to the runtime is reachable ... unless it is listed here"): [3](#0-2) 

A regression test exists for Asset Hub Westend enumerating the value-moving calls a `NonTransfer` proxy must reject: [4](#0-3) 

No equivalent fix or test exists in `asset-hub-rococo`. Since Rococo Asset Hub includes `ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, and (depending on config) `Revive`/contracts pallets in its `RuntimeCall`, and its `NonTransfer` filter does not list any of them, a delegate holding only a `NonTransfer` proxy can move the delegator's funds through these pallets — exactly the invariant violation targeted by the referenced CVE's "fail open due to non-exhaustive denylist" bug class, mapped here from file-extension blocking to call-family blocking.

### Impact Explanation
An account holder grants a `NonTransfer` proxy under the explicit expectation (per the enum doc comment: "Can execute any call that does not transfer funds or assets") that the delegate cannot move value. Because the filter is an incomplete deny-list, the delegate can:
- Transfer `ForeignAssets`/`PoolAssets` directly.
- Perform `AssetConversion` swaps/liquidity withdrawals that move the delegator's assets to another account.
- Send `PolkadotXcm::transfer_assets`/`teleport_assets`/`send`/`execute`, moving assets off-chain.
- Repatriate `Indices` deposits via `transfer`/`force_transfer`.
- Execute contract calls carrying a `value` via `Revive`, if included in the runtime call set.

This breaks the documented authorization boundary between `Any` and `NonTransfer` proxies — a proxy explicitly scoped to be non-value-moving can drain the delegator's account. This is a theft/unauthorized-dispatch class issue against a real, user-facing FRAME primitive (`pallet-proxy`), matching the "unauthorized dispatch" and "theft" preference in the report's method rather than an EVM-style file-upload issue.

### Likelihood Explanation
No privileged role is required: the delegator only needs to have granted a `NonTransfer` proxy (a normal, permissionless `pallet_proxy::add_proxy` call), and the proxy delegate simply calls `Proxy::proxy` with one of the unblocked calls. This requires no governance, no stolen keys, and no malicious external actor — only the ordinary trust model of a `NonTransfer` proxy being violated. The same class of bug was already confirmed real and exploitable on sibling runtimes (Asset Hub Westend, staking-async parachain) and fixed there, which strongly supports that the unfixed Rococo instance is equally reachable and non-theoretical.

### Recommendation
Bring `asset-hub-rococo`'s `ProxyType::NonTransfer` filter in line with the fix applied to `asset-hub-westend` (PR #12771): explicitly deny `ForeignAssets`, `PoolAssets`, `AssetConversion`, `PolkadotXcm`, `Revive` (if present), `Vesting::vested_transfer`, and `Indices::transfer`/`force_transfer`, and any other pallet whose calls can move the delegator's funds/assets. Longer term, replace the deny-list pattern with an allow-list (fail-closed) so newly added pallets are excluded from `NonTransfer` by default, and add a regression test mirroring `non_transfer_proxy_rejects_value_moving_calls` from Asset Hub Westend to `asset-hub-rococo`'s test suite to prevent recurrence.

### Proof of Concept
No PoC was executed in this session (ask-only mode, no local Rust/FRAME test harness run). The finding is derived from direct comparison of production match-arms across `asset-hub-rococo/src/lib.rs` (unfixed) versus `asset-hub-westend/src/lib.rs` (fixed) and the corresponding prdoc changelog describing the exact same fail-open deny-list defect. To confirm exploitability, a Devin session with repository access could instantiate Asset Hub Rococo's runtime test mock, grant a `NonTransfer` proxy, and assert (mirroring `non_transfer_proxy_rejects_value_moving_calls`) that calls such as `ForeignAssets::transfer`, `AssetConversion::swap_exact_tokens_for_tokens`, or `PolkadotXcm::transfer_assets` are wrongly permitted through `ProxyType::NonTransfer.filter(&call)`.

**Uncertainty note:** I could not verify from the index alone whether `pallet_revive`/contracts-with-value or the exact set of `RuntimeCall` variants (e.g., whether `Revive`, `Psm`) are compiled into the `asset-hub-rococo` runtime specifically, since the full `construct_runtime!` pallet list for that file was not retrieved. The `ForeignAssets`, `PoolAssets`, `AssetConversion`, and `PolkadotXcm` variants are confirmed reachable calls (they appear as valid `RuntimeCall` variants used elsewhere, and are structurally identical to Asset Hub Westend, which shares the same base runtime template). I recommend a Devin session confirm the exact pallet list in `asset-hub-rococo`'s `construct_runtime!` and run the suggested regression test to get concrete pass/fail evidence before filing this against the live bounty program.

impl InstanceFilter<RuntimeCall> for ProxyType {
	fn filter(&self, c: &RuntimeCall) -> bool {
		match self {
			ProxyType::Any => true,
			ProxyType::OldSudoBalances |
			ProxyType::OldIdentityJudgement |
			ProxyType::OldAuction |
			ProxyType::OldParaRegistration => false,
			// NOTE: This is a deny-list, so it fails open: a pallet added to the runtime is
			// reachable by a `NonTransfer` proxy unless it is listed here. Every call family that
			// can move the delegator's funds or assets must therefore be denied explicitly.
			ProxyType::NonTransfer => !matches!(
				c,
				RuntimeCall::Balances { .. } |
					RuntimeCall::Assets { .. } |
					// The other `pallet-assets` instances transfer value just like `Assets` does.
					RuntimeCall::ForeignAssets { .. } |
					RuntimeCall::PoolAssets { .. } |
					RuntimeCall::NftFractionalization { .. } |
					RuntimeCall::Nfts { .. } |
					RuntimeCall::Uniques { .. } |
					RuntimeCall::Scheduler(..) |
					RuntimeCall::Treasury(..) |
					// Swaps and liquidity provision move the caller's assets.
					RuntimeCall::AssetConversion(..) |
					// Minting and redeeming swap the caller's stablecoins.
					RuntimeCall::Psm(..) |
					// `transfer_assets`, `teleport_assets` and friends move assets to another
					// chain, and `send`/`execute` can express the same thing as raw XCM.
					RuntimeCall::PolkadotXcm(..) |
					// Contract calls and instantiations carry a `value` to transfer.
					RuntimeCall::Revive(..) |
					// We allow calling `vest` and merging vesting schedules, but obviously not
					// vested transfers.
					RuntimeCall::Vesting(pallet_vesting::Call::vested_transfer { .. }) |
					// Transferring an index repatriates its reserved deposit to the new owner.
					// Claiming, freeing and freezing an index are still allowed.
					RuntimeCall::Indices(pallet_indices::Call::transfer { .. }) |
					RuntimeCall::Indices(pallet_indices::Call::force_transfer { .. }) |
					RuntimeCall::ConvictionVoting(..) |
					RuntimeCall::Referenda(..) |

/// Regression test for <https://github.com/paritytech/polkadot-sdk/issues/12466>.
///
/// `ProxyType::NonTransfer` is documented as permitting "any call that does not transfer funds or
/// assets", but it is implemented as a deny-list and so fails open. `ForeignAssets` and
/// `PoolAssets` transfers were reachable, as were swaps, XCM transfers, contract calls carrying a
/// value, and index transfers (which repatriate the reserved deposit).
#[test]
fn non_transfer_proxy_rejects_value_moving_calls() {
	use asset_hub_westend_runtime::ProxyType;
	use frame_support::traits::InstanceFilter;

	// Collected rather than asserted one by one, so a regression reports every call that slipped
	// through instead of only the first.
	let mut leaked = Vec::new();
	for (name, call) in value_moving_calls() {
		if ProxyType::NonTransfer.filter(&call) {
			leaked.push(name);
		}
		// The call is otherwise well-formed and reachable by a fully permissioned proxy.
		assert!(ProxyType::Any.filter(&call), "Any must permit {name}");
	}

	assert!(
		leaked.is_empty(),
		"NonTransfer must reject calls that move funds or assets, but permitted: {leaked:?}",
	);
}
