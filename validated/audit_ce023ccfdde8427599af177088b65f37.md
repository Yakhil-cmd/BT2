### Title
Stack-scoped `ApiClient` tokens bypass their stack authorization in the CCMenu API - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The report's underlying bug class is a binding break between the entity a credential is *authorized for* and the entity the code actually *acts on*. The same class of flaw exists in Shipit's `Api::CCMenuController`: an `ApiClient` token that is scoped to a single stack (`current_api_client.stack_id`) is meant to only ever see that one stack, but `CCMenuController#stack` resolves the target stack directly from the request parameter instead of through the scoped `stacks` collection, letting the token read the CCMenu/deploy status of any stack in the Shipit instance.

### Finding Description
`Api::BaseController` implements the intended binding: a stack-scoped client is restricted to its own stack via the `stacks` helper, and `stack` is derived from that scoped collection: [1](#0-0) 

This is exercised and enforced elsewhere in the codebase — e.g. the stacks index endpoint explicitly tests that "an api client scoped to a stack will only see that one stack": [2](#0-1) 

However `Api::CCMenuController` overrides both `authenticate_api_client` and `stack`, and its `stack` method never routes through the scoped `stacks` collection — it resolves the stack directly from the raw `params[:stack_id]`: [3](#0-2) 

The only authorization check performed is `require_permission :read, :stack`, which merely checks that `"read:stack"` is present in `ApiClient#permissions` via `check_permissions!`: [4](#0-3) 

That check says nothing about *which* stack the token is scoped to. The stack-identity restriction only exists in `BaseController#stacks`/`#stack`, which `CCMenuController` bypasses entirely. The equality that should hold is:

`stack the token authorizes (current_api_client.stack_id) == stack CCMenuController#show actually queries (params[:stack_id])`

Before the attacker's request: for a stack-scoped client, `current_api_client.stack_id` is set to stack A, and `Stack.where(id: current_api_client.stack_id)` would restrict access to stack A only. After the request: `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unconditionally, so passing stack B's `stack_id` param returns stack B regardless of the token's `stack_id`. The equality is broken — the token authorizes stack A but the controller acts on stack B.

### Impact Explanation
This yields unauthenticated-for-that-resource read of stack state, matching the High-severity category "unauthenticated read of stack state, task streams or deploy output": a caller holding only a narrowly-scoped, single-stack `read:stack` `ApiClient` token (e.g., the "CCMenu Client" pattern used by `CcmenuUrlController`, which issues per-stack tokens intended to expose CI status to third parties) can enumerate/read the latest deploy/rollback status, running state, and lock state of every other stack in the instance, including stacks it was never granted access to — including private or sensitive stacks whose owners never intended to share their deploy status with the token holder.

### Likelihood Explanation
Likelihood is moderate-to-high in any Shipit deployment that issues stack-scoped API tokens (the documented/tested mechanism, e.g. via `CcmenuUrlController#client` or any admin-issued token with a `stack_id`). Exploitation requires only a single unauthenticated-for-other-stacks HTTP GET with a different `stack_id`/`id` path segment and the token in Basic Auth or query string — no privilege escalation, no signature forgery, and no additional secrets beyond the token the caller already legitimately possesses for its own stack.

### Recommendation
Make `CCMenuController#stack` route through the same `stacks` scoping used by `BaseController`, e.g. `@stack ||= stacks.from_param!(params[:stack_id])`, so that stack-scoped tokens are restricted to their authorized stack exactly as they are elsewhere in the API.

### Proof of Concept
1. As a Shipit admin, create (or use the existing `CcmenuUrlController` flow to create) an `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A's id (mirrors the `here_come_the_walrus` fixture used in `test/controllers/api/stacks_controller_test.rb`).
2. Confirm the scoping works for the general API: `GET /api/stacks` with this token returns only Stack A (as asserted in `stacks_controller_test.rb` line 217-223).
3. Call the CCMenu endpoint for Stack B (a different, unrelated stack) using the same token:
   `GET /api/stacks/<StackB-id>/ccmenu.xml` with `Authorization: Basic <base64(token)>` or `?token=<token>`.
4. Observe a `200 OK` response containing Stack B's `Project` XML (`name`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, activity/lock state) — as rendered by `CCMenuController#show` — even though the token is only authorized (`stack_id`) for Stack A. This confirms `Api::CCMenuController#stack`'s use of unscoped `Stack.from_param!` discloses deploy state for a stack the token does not authorize.
