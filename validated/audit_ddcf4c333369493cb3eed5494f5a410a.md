### Title
`StatusHandler#process` writes a `Status` row without confirming the target `Commit`'s stack belongs to the webhook's signing repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits with a bare, cross-tenant `Commit.where(sha: params.sha)` and applies the incoming (signature-verified) GitHub status to *every* matching row, regardless of which stack/repository that row belongs to. Unlike `CheckSuiteHandler`, which scopes lookups through `stacks` (derived from the webhook's own `repository.full_name`), `StatusHandler` never checks that `commit.stack.repository == payload's repository`. This lets a validly-signed webhook from one repository write a `Status` (and thus flip `MergeRequest#all_status_checks_passed?`) for a `Commit` row that actually belongs to a completely different, victim-owned stack, as long as the two rows share the same git SHA (which trivially happens when the attacker's PR head commit is bit-identical to a commit they push/report status against in a repository they control).

### Finding Description
Binding that should hold but doesn't: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` for every `Commit` row mutated by a `status` webhook.

Code path:
1. `WebhooksController#create` verifies the HMAC signature against the org derived from the payload's `repository.owner.login` via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) . This only proves the payload was genuinely signed *for that org*, it says nothing about which `Commit`/`Stack` rows the handler is allowed to touch.
2. `StatusHandler#process` then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 
`Commit.where(sha:)` is a global, unscoped query across the entire `commits` table (not `stacks.commits`, not filtered by `payload['repository']`). Contrast this with `CheckSuiteHandler`, which correctly restricts to the repository the webhook was signed for:
```ruby
def process
  stacks.where(branch: params.check_suite.head_branch).each do |stack|
    stack.commits.where(sha: params.check_suite.head_sha).each(&:schedule_refresh_check_runs!)
  end
end
``` [3](#0-2) 
where `stacks` is defined as `Repository.from_github_repo_name(repository_name)&.stacks`, i.e. explicitly scoped to the signing repository [4](#0-3) .
3. `commit.create_status_from_github!(params)` calls `add_status { statuses.replicate_from_github!(stack_id, github_status) }`, using the target commit's *own* `stack_id` [5](#0-4) , and, on a state transition, calls `stack.schedule_merges` which enqueues `ProcessMergeRequestsJob` [6](#0-5) .
4. `MergeRequest#all_status_checks_passed?` / `#reject_unless_mergeable!` read `head.statuses_and_check_runs` (`statuses + check_runs`) without any re-check of which webhook/org wrote each `Status` [7](#0-6) , and `Commit#statuses_and_check_runs` is a plain concatenation with no org filter [8](#0-7) .

Exploit flow: attacker opens a legitimate PR against a victim-tracked repo B; Shipit creates a `Commit` row scoped to stack B for the PR head sha (`PullRequest#find_or_create_commit_from_github_by_sha!` via `stack.commits.by_sha`/`create_from_github!`) [9](#0-8) . Because the attacker authored that exact commit, they can reproduce the byte-identical commit (same tree/parents/messages/timestamps ⇒ identical SHA) in/against a repository they own and that is already onboarded to Shipit with a genuine signing secret (e.g., their own tracked stack, or by causing GitHub/their own CI to legitimately deliver a `status` event for that SHA on their own repo). GitHub signs that webhook with the real secret for the attacker's own org, `verify_signature` passes (it only checks the payload's own claimed `repository_owner`), and `StatusHandler#process`'s unscoped `Commit.where(sha:)` matches and mutates the victim stack's `Commit` row too, flipping its status to `success` and unblocking the merge queue for a PR that never had a validly-associated status check from the victim's own CI/org.

Existing guards fail because: `verify_signature` only authenticates "this payload really came from org X," never "org X is authorized to write to commit/stack Y"; `StatusHandler` is the only status-consuming handler that omits the `stacks`/repository scoping that `CheckSuiteHandler` correctly applies.

### Impact Explanation
A payload genuinely signed for repository/org X can write a `Status` row, and thereby unblock a pending merge, on a `Commit` belonging to an unrelated victim stack Y, purely because the two commits share the same SHA. This directly matches the "payload for one repository mutating another's stack/commit ... an unauthorized merge" Critical category: the attacker's PR can be pushed past `ci_missing`/`ci_failing` rejection and merged by Shipit's automatic merge queue without ever passing the victim repository's actual required CI checks. The blast radius spans every Shipit-tracked repository sharing the database, since the lookup is entirely unscoped by repository/stack.

### Likelihood Explanation
Requires: (1) the attacker's PR is queued in the merge queue awaiting CI (a normal, unprivileged action any contributor can trigger), and (2) the attacker be able to get a genuinely, independently-signed `status` webhook delivered for the identical SHA from some other repository/org context that Shipit's `Shipit.github(organization:)` recognizes (e.g. their own onboarded repo/stack, or any org whose signing secret they can legitimately obtain through normal GitHub self-service, such as installing the app on a repo they own or having their own CI post a status on their own commit). No Shipit session, API token, or Shipit/GitHub secret is required to be *known* by the attacker — GitHub performs the signing on their behalf for events on repositories they control. This is repeatable against any tracked stack and any PR.

### Recommendation
Scope `StatusHandler#process` the same way `CheckSuiteHandler` does: resolve `stacks` (or `Repository.from_github_repo_name(repository_name)`) from the webhook payload's own `repository.full_name`, and only update `Commit` rows that belong to stacks under that resolved repository (e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or add an explicit check `next unless commit.stack.repository.full_name == repository_name` before calling `create_status_from_github!`).

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
```ruby
test "status webhook for repository A does not update a commit belonging to stack B with the same sha" do
  stack_a = shipit_stacks(:shipit)          # repository A, attacker-controlled/onboarded
  stack_b = shipit_stacks(:cyclimse)        # repository B, victim-owned, unrelated

  shared_sha = "deadbeef" * 5
  commit_a = stack_a.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")
  commit_b = stack_b.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "shared")

  payload = { "sha" => shared_sha, "state" => "success", "repository" => { "full_name" => stack_a.github_repo_name, "owner" => { "login" => stack_a.repository.owner } } }

  # binding under test: commit_b.stack.repository.full_name != payload["repository"]["full_name"]
  assert_not_equal commit_b.stack.repository.full_name, payload["repository"]["full_name"]

  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  assert_predicate commit_a.reload, :success? # expected: legit write to A
  refute_predicate commit_b.reload, :success? # currently FAILS: commit_b is also flipped to success
end
```
This demonstrates the divergence: today `commit_b` (unrelated victim stack) is also updated by a webhook signed only for repository A's org, which would subsequently let a queued `MergeRequest` on stack B pass `all_status_checks_passed?` and merge.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
