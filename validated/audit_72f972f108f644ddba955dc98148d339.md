### Title
Forged `status` webhook creates statuses / triggers continuous deployment on ANY stack sharing a commit sha, without checking the webhook's repository - (File: app/models/shipit/webhooks/handlers/status_handler.rb, app/models/shipit/commit.rb)

### Summary
`StatusHandler#process` resolves target commits via a global, repository-unscoped `Commit.where(sha: params.sha)` query instead of the repository-scoped `stacks` helper that every other handler (`PushHandler`, `CheckSuiteHandler`, `PullRequest::*Handler`) uses. `Commit#schedule_continuous_delivery` then only checks `stack.continuous_deployment? && stack.deployable?`, with no cross-check that the stack's `repository` matches the webhook payload's `repository.full_name`. A validly-signed `status` webhook for one repository can therefore create `Status` rows and enqueue `ContinuousDeliveryJob` for every stack in the instance whose commits happen to share the sha.

### Finding Description
Binding as claimed: `set_of_stacks_authorized_by_this_webhook` (should be `<= 1`, scoped to the payload's `repository.full_name`) must equal `set_of_stacks_actually_reachable` by the handler's write path. Tracing the code shows this is false.

- `WebhooksController#verify_signature` (app/controllers/shipit/webhooks_controller.rb:24-38) only verifies the HMAC signature against the *organization* derived from `params.dig('repository','owner','login')`. It authenticates "this request came from GitHub for org X," not "this request may only touch repository X/Y." [1](#0-0) 
- `Webhooks::Handlers::Handler` provides a `stacks` helper explicitly scoped to the payload's repository: `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none`, and `repository_name` is read from `payload.dig('repository','full_name')`. [2](#0-1) 
- Every other handler (`CheckSuiteHandler`, `PushHandler`, pull-request handlers) uses this `stacks` scope before touching commits, e.g. `stacks.where(branch: ...)`. [3](#0-2) 
- `StatusHandler#process`, however, bypasses `stacks` entirely and queries `Commit` globally by `sha` alone: [4](#0-3) 
- Each matched `Commit#create_status_from_github!` creates a `Status`, whose `after_commit` callback calls `commit.schedule_continuous_delivery` (app/models/shipit/status.rb:19,42-44), which in turn checks only `deployable? && stack.continuous_deployment? && stack.deployable?` (app/models/shipit/commit.rb:281-282) — no comparison against the webhook's `repository.full_name` or the requesting organization. [5](#0-4) [6](#0-5) 

Root cause: `StatusHandler` is the only handler that resolves affected records purely by content-addressed `sha` instead of by the repository-scoped `stacks` relation, and the downstream `schedule_continuous_delivery` guard never re-validates the stack's repository against the webhook's claimed repository. Because git commit shas are deterministic hashes of tree+metadata, any stack tracking the same (or a forked/mirrored) upstream history will contain `Commit` rows with identical sha values across repositories. A validly-signed status webhook from one repository under an org already onboarded to Shipit will match and act on all of them.

Existing guards checked and found insufficient:
- `verify_signature` authenticates by organization only, not repository [7](#0-6) .
- `drop_unhandled_event`/`check_if_ping` are unrelated to this path.
- `ExplicitParameters` schema for `StatusHandler` validates presence/type of `sha`/`state`, not repository scope [8](#0-7) .
- The `stacks` scoping helper exists but is simply not used by `StatusHandler` [2](#0-1) .

### Impact Explanation
A forged/legitimately-delivered `status` event for a commit sha shared across repositories causes `ContinuousDeliveryJob.perform_later(stack)` to be enqueued for every continuous-deployment-enabled stack that has a matching `Commit` row, not just stacks belonging to the webhook's own repository. This is an unauthorized-deploy class issue: a status event scoped to repository A can trigger a deploy on stack B/C/etc. belonging to unrelated repositories, i.e., "a payload for one repository mutating another's stack/commit/task," matching the Critical severity category. Blast radius scales with the number of continuous-deployment-enabled stacks in the instance that happen to share commit history (mirrors, forks, multi-environment stacks of the same upstream repo).

### Likelihood Explanation
Requires: (1) the attacker's repository/org already recognized by Shipit's webhook signature verification (i.e., onboarded to receive signed webhooks — consistent with the stated threat model's "emit webhooks from a repository they own"), and (2) at least one other stack in the instance whose `Commit` table contains the same sha, which naturally occurs whenever multiple stacks track the same upstream repository (common: staging/production stacks of one repo, or forks/mirrors sharing history). No secrets, sessions, or elevated GitHub permissions are needed beyond what's already assumed reachable in the threat model. The attack is repeatable per sha/stack pair.

### Recommendation
In `StatusHandler#process`, scope the commit lookup through the repository-scoped `stacks` association (as `CheckSuiteHandler` and others do), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or equivalently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a status event can only affect commits/stacks belonging to the webhook's own `repository.full_name`.

### Proof of Concept
```ruby
test "status webhook only affects stacks of the payload's own repository" do
  repo_a = shipit_repositories(:shipit) # or create Repository owner/a
  repo_b = create_repository(name: 'repo-b')
  repo_c = create_repository(name: 'repo-c')

  stack_a = create_stack(repository: repo_a, continuous_deployment: true)
  stack_b = create_stack(repository: repo_b, continuous_deployment: true)
  stack_c = create_stack(repository: repo_c, continuous_deployment: true)

  shared_sha = 'deadbeef' * 5
  commit_a = stack_a.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  commit_b = stack_b.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)
  commit_c = stack_c.commits.create!(sha: shared_sha, message: 'x', author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now)

  # binding under test:
  # authorized_stacks (scoped to repo_a) == [stack_a]
  # reachable_stacks (actual)            == [stack_a, stack_b, stack_c]
  request.headers['X-Github-Event'] = 'status'
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  body = { sha: shared_sha, state: 'success', repository: { full_name: repo_a.full_name } }.to_json

  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_a]) do
    post :create, body:, as: :json
  end
  # Bug: also enqueued for stack_b and stack_c even though the payload only named repo_a
  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b]) { }
  assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_c]) { }
end
```
