### Title
Webhook Signature Verified Against a Different Organization Than the Repository the Payload Actually Targets — Cross-Tenant Forged GitHub Events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit's `/webhooks` endpoint picks the HMAC secret used to verify a webhook's signature from `repository.owner.login` in the JSON body, but the code that actually *acts* on the payload (stack lookup, commit status writes, review-stack provisioning, sync/deploy triggers) keys off a *different* field, `repository.full_name`. Nothing ties these two fields together, so on a Shipit instance configured for multiple GitHub organizations, a user who legitimately controls one organization's webhook secret can forge events for a repository belonging to a completely different organization.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to select the verifying `GitHubApp`/secret purely from the payload itself: [1](#0-0) [2](#0-1) 

The signature check only proves that the raw request body was signed with the webhook secret associated with `repository.owner.login`; it does not verify that `repository.owner.login` corresponds to the organization that actually owns `repository.full_name`: [3](#0-2) 

Once the signature passes, `Webhooks.for_event(event)` dispatches the parsed payload to handlers, and the base `Handler` class resolves the target repository/stacks using a *different* field, `repository.full_name`: [4](#0-3) 

For example, `PushHandler` looks up stacks via that repository name and triggers a sync against an attacker-chosen `after` SHA: [5](#0-4) 

Similarly, all pull-request handlers (open/close/label/reopen) and the review-stack adapter resolve the acted-upon repository from `params.repository.full_name`, independent of whichever organization's secret was used to authenticate the request: [6](#0-5) [7](#0-6) 

Shipit officially supports multiple GitHub organizations sharing one instance, each with its own webhook secret, as shown by the dummy multi-org secrets fixture: [8](#0-7) 

**Binding that should hold, but is broken:**
`organization whose webhook_secret authenticated the request == organization that owns repository.full_name acted upon by the handler`

Before an attacker's forged request: for legitimate GitHub-originated webhooks, both fields are populated consistently by GitHub itself, so the binding holds implicitly.
After the attacker's request: the attacker (an admin of Org B, one tenant on the shared Shipit instance) crafts a JSON body where `repository.owner.login = "OrgB"` (used only to pick the verifying secret, which the attacker legitimately possesses for their own org) while `repository.full_name = "OrgA/victim-repo"` (a different tenant's repository, used by handlers to find/act on stacks). The equality above no longer holds, yet the request is accepted as validly signed.

### Impact Explanation
This lets an unprivileged-relative-to-OrgA attacker (who only has legitimate access to their own, separately configured organization/app on the same Shipit instance) inject arbitrary forged GitHub events for a victim organization's repositories:
- Forged `push` events can trigger `stack.sync_github(expected_head_sha: ...)` for the victim stack, and for stacks with `continuous_deployment: true` (a supported, common configuration, see `test/fixtures/shipit/stacks.yml`) this can advance the deployable head and kick off an **unauthorized deploy** — matching the Critical bucket ("an unauthorized deploy").
- Forged `status` events let the attacker fabricate CI status on the victim's commits, undermining the CI gating (`ignore_ci`, required/blocking statuses) that is meant to control what can be deployed.
- Forged `pull_request`/`check_suite`/`membership` events can create, archive, or mutate review stacks and team membership records tied to the victim's repository.

### Likelihood Explanation
Exploitability strictly requires the deployment to run in the documented multi-organization mode (one Shipit instance serving several GitHub orgs/apps, each with its own `webhook_secret`), as shown by the shipped `secrets_double_github_app.yml` fixture. Given that configuration, exploitation requires only the ability to POST an HTTP request with a correctly computed HMAC using a secret the attacker legitimately owns (their own org's webhook secret) — no access to the victim org, its repo, or GitHub credentials is needed. This is a straightforward, repeatable HTTP-only attack once multi-org hosting is in place.

### Recommendation
After signature verification, additionally verify that the organization used to select the webhook secret (`repository.owner.login`, or `organization.login`) matches the organization/namespace segment of `repository.full_name` (and/or that the resolved `Shipit::Repository`/`Stack` is actually associated with that verified organization) before dispatching to any handler. Reject the webhook (422) if they diverge.

### Proof of Concept
Given a Shipit instance configured for two orgs, `OrgA` (victim) and `OrgB` (attacker-controlled), each with distinct `github.webhook_secret` values (per `test/dummy/config/secrets_double_github_app.yml`):

1. Attacker crafts a push payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<existing sha in OrgA/victim-repo's mirror>",
  "repository": { "full_name": "OrgA/victim-repo", "owner": { "login": "OrgB" } }
}
```
2. Attacker computes `sha1=HMAC-SHA1(OrgB_webhook_secret, raw_body)` (they legitimately know OrgB's secret) and sets it as `X-Hub-Signature`, with `X-Github-Event: push`.
3. POST to `https://shipit-instance/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgB")` and succeeds, since the signature matches OrgB's secret. [1](#0-0) 
5. `PushHandler` resolves `stacks` via `Repository.from_github_repo_name("OrgA/victim-repo")` and calls `sync_github(expected_head_sha: ...)` on OrgA's stack, without ever validating the request against OrgA's own webhook secret. [5](#0-4) 

Note: I was unable to view the full implementation of `Shipit.github(organization:)` in `lib/shipit.rb` in this session due to tool limits, so the exact mechanics of per-organization `GitHubApp` selection (and whether `GithubOrganizationUnknown` is the only additional guard) could not be fully confirmed; a Devin session with full file access should verify this method to confirm there is no additional consistency check between `organization` and the acted-upon repository before treating this as fully validated.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
