### Title
Cross-organization team-membership authorization bypass via `github_id`-only lookup in `MembershipHandler` - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` grants/revokes `Team` membership using a `Team` record looked up **only** by the numeric `params.team.id`, without verifying that the `organization` in the same webhook payload matches the organization already recorded on that `Team`. The webhook signature check that gates this handler (`WebhooksController#verify_signature`) selects the verification key using `params.dig('organization','login')` (for membership events, since there is no `repository` key), but nothing binds that authenticated organization to the `Team#organization` that actually gets mutated. This mirrors the H-10 pattern: one field (`organization.login`, used to pick the signing secret) is verified, while a different, unguarded field (`team.id`) drives the actual state change (which `Team` — and therefore which `Shipit.github_teams` authorization group — is modified).

### Finding Description
- `WebhooksController#verify_signature` picks the HMAC verification key with `Shipit.github(organization: repository_owner)`, where `repository_owner` for a `membership` event resolves to `params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 
- This only proves the payload was signed with the secret configured for *that* organization (`org-A`, an organization the attacker legitimately administers/owns and has already connected to this Shipit instance, per the documented "Using Multiple GitHub Applications" multi-org setup). Nothing else in the payload is checked against `org-A`.
- The `MembershipHandler#process` then does:
```
team = find_or_create_team!
member = User.find_or_create_by_login!(params.member.login)
case params.action
when 'added'
  team.add_member(member)
...
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [3](#0-2) 
  The `find_or_create_by!(github_id: params.team.id)` block only runs on **creation**. If a `Team` row with that `github_id` already exists (created earlier from a legitimate `org-B` membership event), the lookup returns the existing `org-B` team unchanged — `team.organization` is never re-validated against `params.organization.login`.
- `Team#add_member` unconditionally appends the resolved `User`: [4](#0-3) 
- Authorization to use Shipit at all is granted purely by membership in one of `Shipit.github_teams`: [5](#0-4) [6](#0-5) 

**Binding broken (as an equality):** `organization authenticated by webhook signature (org-A)` must equal `Team#organization actually written to / whose membership is mutated (team.github_id lookup, could resolve to org-B's team)`. The handler enforces the former only for the *creation* path and never re-checks it for the (attacker-controllable) *lookup-hit* path.

### Impact Explanation
If an attacker administers (or self-onboards) any GitHub organization configured in this Shipit instance's multi-org `github:` config (a normal, low-privilege "org admin of my own tenant" position under the documented multi-org setup, not requiring access to another organization's secrets or GitHub App), they know that organization's `webhook_secret` and can freely craft and HMAC-sign **arbitrary JSON bodies** — not just real GitHub events — and POST them directly to `/webhooks`. By setting `team.id` to the `github_id` of an already-tracked `Team` belonging to a *different*, more-privileged organization (e.g., one listed in `Shipit.github_teams`, which gates login/authorization for the whole Shipit instance) and `action: "added"`, `member.login: <attacker's own Shipit login>`, the attacker adds themselves to that privileged team, satisfying `User#authorized?` and gaining full authenticated access to Shipit (deploys, rollbacks, merges) without ever being an actual member of the target organization/team on GitHub. This crosses the "escalation into `Shipit.github_teams` authorization" impact bar (High), and depending on which teams/stacks are gated, can escalate to unauthorized deploys/rollbacks/merges (Critical-adjacent).

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (an explicitly documented, supported configuration — `docs/setup.md` "Using Multiple Github Applications"), (2) attacker control of one such onboarded, lower-trust organization (their own tenant), and (3) knowledge of a victim `Team`'s numeric GitHub `github_id` (team IDs are visible via GitHub's public/authenticated team APIs, or discoverable/enumerable, and not treated as secret). No `ApiClient` token, `webhook_secret` of the victim org, GitHub App private key, or repository write access on the victim org is needed. This is a realistic, unprivileged-relative-to-the-victim-org attack path within the engine's own signature-verification/handler logic.

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` **and** `organization`, and reject (rather than silently reuse) any pre-existing `Team` whose `organization` does not match `params.organization.login`:
```ruby
def find_or_create_team!
  team = Team.find_by(github_id: params.team.id)
  raise ArgumentError, "Team/organization mismatch" if team && team.organization != params.organization.login

  Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
end
```
More generally, `WebhooksController#verify_signature` should ensure the organization used to select the signing key is cross-checked against every organization-scoped identifier acted upon by the corresponding handler, not just used opportunistically for key selection.

### Proof of Concept
1. Configure Shipit for two organizations, `org-a` and `org-b` (per multi-org `secrets.yml` setup), each with its own `webhook_secret`. Attacker administers `org-a` and knows `org-a`'s `webhook_secret`.
2. `org-b`'s team `Shopify/developers` (used in `Shipit.github_teams`) is already tracked in Shipit's `teams` table with `github_id: 100` (created from a legitimate prior `org-b` membership webhook).
3. Attacker crafts:
```json
{
  "action": "added",
  "team": { "id": 100, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/100" },
  "organization": { "login": "org-a" },
  "member": { "login": "attacker-shipit-login" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: membership`.
5. `verify_signature` resolves `repository_owner` = `"org-a"`, verifies successfully against `org-a`'s secret.
6. `MembershipHandler#process` runs `Team.find_or_create_by!(github_id: 100)`, finds the existing `org-b`/`Shopify/developers` team (organization mismatch never checked), and calls `team.add_member(attacker_user)`.
7. Attacker is now a member of `Shopify/developers`; `User#authorized?` returns true, granting full Shipit access.

*Note: this PoC path is derived from static code review; I was not able to execute it against a running instance, so the exact HTTP/webhook plumbing (e.g., any additional Rails-level request validation) should be confirmed by a maintainer before treating this as fully verified.*
