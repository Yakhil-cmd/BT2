## Analysis

I found a genuine analog of the H-2 bug class in `Shipit::WebhooksController`. The root cause is that the field used to **select the authentication key** and the field used to **select the write target** are two independent, uncorrelated values inside the same attacker-supplied JSON body, and neither is cross-checked against the other after signature verification succeeds. [1](#0-0) [2](#0-1) [3](#0-2) 

### Title
Webhook authentication org/secret selection is decoupled from the repository the event acts on, allowing cross-repository writes when any configured GitHub App has no `webhook_secret` — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* HMAC secret to validate a webhook against based on `repository.owner.login` (or `organization.login`) taken from the **unverified** JSON body, before any authentication has occurred: `Shipit.github(organization: repository_owner)`. Once verification passes, `Webhooks::Handlers::Handler#stacks` resolves the actual `Repository`/`Stack` to act on using a **different** field of the same body, `repository.full_name`. These two fields are never checked for consistency.

### Finding Description
`verify_signature` computes the org used for the secret lookup from attacker-controlled JSON before the signature is checked: [4](#0-3) [5](#0-4) 

`GithubApp#verify_webhook_signature` explicitly treats an unconfigured secret as "always verified": [3](#0-2) 

Every downstream handler (`PushHandler`, `StatusHandler`'s `Commit.where(sha:)` lookup is even weaker — it doesn't check repository at all, `PullRequest::*Handler`, etc.) resolves the target purely from `repository.full_name`, which is an entirely separate field from the one used to select the verification secret: [2](#0-1) [6](#0-5) [7](#0-6) 

The bound equality that should hold but does not is:
`organization whose secret authenticated the request == organization that owns the repository being written to`.

Concretely: in a Shipit instance configured for multiple GitHub organizations (the documented multi-org `secrets.yml` schema shown in `docs/setup.md`), if **any** one configured org is left with `webhook_secret: # nil` (shown as the default/optional value in `config/secrets.development.example.yml` and `docs/setup.md`), then a request whose body claims `repository.owner.login` = that unsecured org will always pass `verify_signature` (`return true unless webhook_secret`) regardless of the `X-Hub-Signature` header supplied — with **zero credentials needed**. The same body can independently set `repository.full_name` to `"victim-org/victim-repo"`, a completely different, properly-secured org/repo tracked by the same Shipit instance. The `StatusHandler` in particular does not even key off `repository` at all — it matches purely on `sha` across the whole `Commit` table: [8](#0-7) 

This lets the attacker forge a "status" event with any `sha`, `state: "success"`, and `context` for a commit belonging to any tracked stack (including the victim's), regardless of which org the (bypassed) signature check thought it belonged to.

### Impact Explanation
Forged/attributed statuses feed directly into merge-queue and continuous-delivery gating logic: [9](#0-8) [10](#0-9) [11](#0-10) 

An unauthenticated attacker can inject a fabricated `success` status for a required CI context on a specific commit SHA of a stack they don't control. `Status#schedule_continuous_delivery` and `ProcessMergeRequestsJob` will then treat that commit as CI-green, causing `MergeRequest#merge!` (`stack.github_api.merge_pull_request`) to fire, or `trigger_continuous_delivery` to ship, using the Shipit-configured `GITHUB_TOKEN`/App credentials for the *victim* repository — i.e., an unauthorized merge/deploy driven entirely by a forged webhook that never needed the victim org's (or any) webhook secret.

### Likelihood Explanation
Requires only: (1) a multi-org Shipit deployment (documented, supported configuration), and (2) at least one configured org left with the documented-optional `webhook_secret` unset. Both are realistic, documented states rather than "not mounting the engine as documented." No `webhook_secret`, `ApiClient` token, GitHub App private key, repository write access, privileged account, or session is required from the attacker — a bare unauthenticated `POST /webhooks` suffices.

### Recommendation
Cross-validate the org/repo used for HMAC-secret selection against the org/repo the handler actually writes to before dispatching (e.g., re-derive the target repository from the same `repository.owner.login`/`organization.login` used for authentication, and reject if it disagrees with `repository.full_name`); additionally, make `webhook_secret` mandatory for every configured organization and refuse to boot/dispatch webhooks for an org without one, and have `StatusHandler` scope its `Commit` lookup by the authenticated repository rather than by bare `sha` across all stacks.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.github`: `org-a` (no `webhook_secret` set) and `org-b` (properly configured, tracking `org-b/victim-repo`).
2. Send, without any signature or with a garbage `X-Hub-Signature`:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": {"owner": {"login": "org-a"}, "full_name": "org-b/victim-repo"},
  "sha": "<sha of pending PR head in org-b/victim-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "org-a")`, whose `webhook_secret` is nil, so `verify_webhook_signature` returns `true` unconditionally.
4. `StatusHandler#process` creates a `success` `Status` on the matching `Commit` (looked up purely by `sha`), which is part of `org-b/victim-repo`'s stack.
5. `Status#schedule_continuous_delivery` / `ProcessMergeRequestsJob` treat the commit as CI-passing, triggering an unauthorized merge or deploy for `org-b/victim-repo`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  class ProcessMergeRequestsJob < BackgroundJob
    include BackgroundJob::Unique
    on_duplicate :drop

    queue_as :default

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
  end
end
