### Title
Silent Correspondent Hub Reassignment Without User Notification - (File: device.js)

### Summary
When ocore receives a `hub/message` from an already-paired correspondent, it silently updates that correspondent's stored home hub (`correspondent_devices.hub`) whenever the message's `device_hub` field differs from the value on record — with no user confirmation, no notification event, and no record of the previous hub. This mirrors the GitLab CVE-2018-19580 pattern: a security-relevant identity/routing attribute (there: email; here: the hub used to reach a correspondent) is changed without any notice being sent that would let the legitimate owner detect and react to the change.

### Finding Description
In the justsaying handler for `hub/message`, after the sender is authenticated as a known correspondent, the code compares the `device_hub` carried inside the message body to the hub stored in `correspondent_devices` and updates it automatically if different, before processing the message: [1](#0-0) 

```
db.query("SELECT hub, is_indirect FROM correspondent_devices WHERE device_address=?", [from_address], function(rows){
    if (rows.length > 0){
        if (json.device_hub && ... && json.device_hub !== rows[0].hub) // update correspondent's home address if necessary
            db.query("UPDATE correspondent_devices SET hub=? WHERE device_address=?", [json.device_hub, from_address], ...);
        ...
```

Unlike the deliberate, user-initiated `updateCorrespondentProps` path [2](#0-1)  which requires explicit user action to change a correspondent's `hub`/`name`/preferences, this automatic path fires on every inbound message and never emits an event or otherwise alerts the wallet UI/user that the routing destination for future messages to that correspondent has changed. All subsequent outbound traffic to that correspondent — payment notifications, private payment chain forwarding, signing requests, arbiter/prosaic contract messages — is looked up from this same `hub` column and sent via `sendMessageToHub`/`sendMessageToDevice`: [3](#0-2) .

Because the update happens silently and persists indefinitely, if a correspondent's device key is ever transiently compromised, spoofed, or misused (e.g., a stolen temporary device key before rotation, or a malicious actor who briefly controls the correspondent's session), a single crafted message can permanently redirect the victim's future communications with that correspondent to an attacker-controlled hub — with no notification analogous to what CVE-2018-19580 flags as missing (an alert to the previously trusted channel/owner about the change).

### Impact Explanation
Redirecting a correspondent's home hub silently means the victim's node will continue routing sensitive device-level traffic (private payment chain elements, payment notifications, signing offers, AA/contract negotiation messages) through a hub the attacker controls, without any UI warning that this occurred. This can facilitate interception or manipulation of private payment chains and multi-device signing flows relevant to fund custody, since the victim has no visibility that the destination changed. This qualifies as node disagreement/exposure risk for private payment and signing workflows reachable purely from a paired-device message.

### Likelihood Explanation
The change requires no privileged access beyond already being a "known correspondent" (paired device) — a role explicitly in scope. It triggers automatically and silently on ordinary message traffic whenever the `device_hub` field differs, requiring no additional user interaction or confirmation, making it straightforward to trigger for anyone able to send even one authenticated message as that correspondent.

### Recommendation
Do not auto-update `correspondent_devices.hub` silently. At minimum, emit an `eventBus` event (e.g., `correspondent_hub_changed`) so wallet UIs can notify the user, and/or require explicit user confirmation before persisting a new hub for an existing correspondent, mirroring the deliberate confirmation flow already used in `updateCorrespondentProps`.

### Proof of Concept
1. Pair with a victim node as a normal correspondent device.
2. Send any legitimate message (e.g., `text`) to the victim with `json.device_hub` set to an attacker-controlled hub domain instead of the correspondent's real hub.
3. Observe in `device.js` (lines 204-211) that the victim's `correspondent_devices.hub` row is updated to the attacker's hub with no event emitted and no user-visible confirmation.
4. All subsequent messages the victim sends to this correspondent (via `sendMessageToDevice`/`sendMessageToHub`, `device.js` lines 733-750) are now routed to the attacker-controlled hub, with the victim unaware of the change.

function sendMessageToDevice(device_address, subject, body, callbacks, conn){
	if (!device_address)
		throw Error("empty device address");
	conn = conn || db;
	conn.query("SELECT hub, pubkey, is_blackhole FROM correspondent_devices WHERE device_address=?", [device_address], function(rows){
		if (rows.length !== 1 && !conf.bIgnoreMissingCorrespondents)
			throw Error("correspondent not found");
		if (rows.length === 0 && conf.bIgnoreMissingCorrespondents || rows[0].is_blackhole){
			console.log(rows.length === 0 ? "ignoring missing correspondent " + device_address : "not sending to " + device_address + " which is set as blackhole");
			if (callbacks && callbacks.onSaved)
				callbacks.onSaved();
			if (callbacks && callbacks.ifOk)
				callbacks.ifOk();
			return;
		}
		sendMessageToHub(rows[0].hub, rows[0].pubkey, subject, body, callbacks, conn);
	});
}
