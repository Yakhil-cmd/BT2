### Title
Unauthorized locking of a victim's STX via forged `PreStxOp.output` / `StackStxOp.sender` - (File: `stackslib/src/chainstate/burn/operations/stack_stx.rs`)

### Summary
`PreStxOp::parse_from_tx` derives the future `StackStxOp.sender` solely from `outputs[0]` of a Bitcoin transaction, which requires no signature or key-ownership proof from the address it encodes. Since Bitcoin lets anyone send funds to any address, an attacker can set `outputs[0]` to a victim's `StacksAddress` while only needing to control the key that later spends `outputs[1]` (checked via `StackStxOp::get_sender_txid`) to emit the actual `StackStxOp`.

### Finding Description
Broken equality: **the Stacks account whose `STXBalance` is checked and locked by `stack-stx`** should equal **the Stacks account that authorized the transaction with its own key**. This breaks because `sender` (a.k.a. `tx-sender` inside the pox-4 contract call) is taken from `PreStxOp.output`, an unauthenticated Bitcoin output address:

- `PreStxOp::parse_from_tx` builds `output` purely from `outputs.get(0)...address...try_into_stacks_address()`, with no check that the broadcaster controls the corresponding private key [1](#0-0) .
- `Burnchain::classify_transaction` resolves `let sender = &pre_stack_stx.output;` and feeds it straight into `StackStxOp::from_tx` as the op's `sender` [2](#0-1) .
- `StackStxOp::parse_from_tx` simply stores `sender: sender.clone()` without any further validation of provenance [3](#0-2) .
- `process_stacking_ops` then executes the Clarity call `tx.run_contract_call(&sender.clone().into(), None, ..., "stack-stx", &args, ...)`, i.e. it invokes pox-4's `stack-stx` **as if `tx-sender` were the victim** [4](#0-3) .
- Inside `stack-stx`, all checks and state writes key off `tx-sender`: `(stx-get-balance tx-sender)`, `(map-set stacking-state { stacker: tx-sender } ...)`, and the returned lock-up tuple `{ stacker: tx-sender, lock-amount: amount-ustx, ... }` [5](#0-4) .
- `handle_stack_lockup_pox_v4` then calls `pox_lock_v4(..., &stacker, locked_amount, ...)` and emits `STXLockEventData { locked_address: stacker, ... }`, locking the victim's actual balance [6](#0-5) .

The `signer-key`/`signer-sig` authorization mechanism (`verify-signer-key-sig`, `consume-signer-key-authorization`) only proves the attacker controls the *signer key* used for reward-slot bookkeeping; it does not authenticate `tx-sender` (the address whose STX is locked) in any way [7](#0-6) . Thus none of the existing guards (`check-caller-allowed`, `is-none (get-stacker-info tx-sender)`, signer-key verification) validate that the `tx-sender` (victim) actually signed anything — they only prevent double-stacking and confirm the reward/signer key, both attacker-controlled.

Attacker flow: broadcast a PreStxOp with `outputs[0] = victim_stacks_address` (attacker needs only to pay the Bitcoin fee/burn amount from their own inputs — no victim key needed to construct this output), then broadcast a StackStxOp spending `outputs[1]` with the attacker's own BTC key and their own chosen `reward_addr`/`signer_key`/`stacked_ustx` (up to victim's real balance). `Burnchain::classify_transaction` resolves `sender = victim_stacks_address` and pox-4 locks the victim's own STX, crediting PoX BTC rewards to the attacker's chosen reward address.

### Impact Explanation
- The victim's real, unlocked STX gets forcibly locked into a pox-4 stacking commitment for `num_cycles` reward cycles, without the victim ever creating or signing a Stacks transaction.
- PoX Bitcoin rewards for that locked stake accrue to the attacker's chosen `reward_addr`/`signer_key`, i.e. the attacker earns stacking rewards backed by STX they neither own nor control — theft of PoX rewards funded by the victim's involuntarily-locked collateral.
- This is repeatable against any account whose balance is public and sufficiently large, once per available balance/lock-window, each time freezing the victim's funds for the chosen `num_cycles` (up to `POX_MAX_NUM_CYCLES`) and diverting the associated stacking rewards to the attacker.
- This matches at minimum "temporary freezing of staked STX" and, given reward diversion, effectively "theft of stacking rewards" funded by an unsigned stacking action — Critical/High per the stated rubric.

### Likelihood Explanation
No privileged role is required. The attacker only needs: (1) to know a target victim's `StacksAddress` (public information), (2) enough BTC to cover fees/dust for two burnchain transactions, and (3) the ability to order the PreStxOp before the StackStxOp in the same or later burn block, exactly as the existing test harness (`test_parse_pre_stack_stx`, `stackslib/src/burnchains/tests/db.rs`) already demonstrates the parse/propagation mechanics for non-adversarial cases. There's no rate limit, cost, or key-ownership check preventing an attacker from doing this at will against any address; the only true cost is the attacker's own BTC transaction fees.

### Recommendation
Require that the `sender` bound to a `StackStxOp` (i.e., the address whose STX will be locked) be cryptographically tied to the same Bitcoin key(s) that authorize the operation — e.g., derive `sender` from the same input(s)/key(s) used to spend the "authorizing" output (as is done for `reward_addr`/signer verification), or require an explicit on-chain Stacks-signed authorization (a Stacks transaction or SIP-018 message signed by the `sender`'s Stacks key) binding the burnchain op to that specific `tx-sender` before `process_stacking_ops` is allowed to call `stack-stx` on that principal's behalf.

### Proof of Concept
Rust integration test in `stackslib/src/burnchains/tests/db.rs` style:
1. Construct a two-output Bitcoin `PreStxOp` transaction: `outputs[0] = victim_addr` (arbitrary `StacksAddress` encoding, no victim key involved), `outputs[1] = attacker_change_addr` (attacker-controlled).
2. Mine it; assert `PreStxOp::parse_from_tx(...).output == victim_addr` (equality #1: unauthenticated address accepted as "sender").
3. Construct and mine a `StackStxOp` Bitcoin transaction whose input spends `outputs[1]` (signed only by the attacker's key), with attacker-chosen `reward_addr`, `signer_key`, and `stacked_ustx == victim_balance`.
4. Assert `Burnchain::classify_transaction(...)` (or the emitted `BlockstackOperationType::StackStx(op)`) yields `op.sender == victim_addr`.
5. Process the block through `StacksChainState::process_stacking_ops`, then query pox-4's `stx-account`/`get-stacker-info` for `victim_addr` and assert the victim's `STXBalance` is now locked for `num_cycles`, and that `STXLockEventData.locked_address == victim_addr` — asserting the broken equality: `locked_address (victim_addr) != authorizing_key_owner (attacker)`.
