## Analysis

The TangleStaking bug pattern — an unbounded loop over a user-influenced collection that is walked on every operation, with cost proportional to the size of that collection — has a close analog in `data_feeds.js`.

### Title
Unbounded scan of `storage.assocUnstableMessages` in `in_data_feed` lookups causes AA/validation-time DoS scaling with network-wide unstable messages - (File: `data_feeds.js`)

### Summary
`dataFeedExists()` in `data_feeds.js`, when invoked in the AA context (`bAA === true`), iterates over **every** currently unstable unit in `storage.assocUnstableMessages`, and for each one iterates over all of that unit's messages, to search for a matching `data_feed` payload: [1](#0-0) 

This loop has no bound related to the querying address or feed name — it scans the entire in-memory set of unstable messages for the whole network on every call, breaking early only if a match is found: [2](#0-1) 

### Finding Description
This is structurally the same defect as the TangleStaking `_unstake` loop: a piece of logic that must be executed per-call is written as an O(n) (or worse, considering the nested `.forEach`) scan over a collection whose size is controlled by unprivileged actors. In `TangleStaking.sol`, the attacker-controlled dimension was "number of tokens staked by one investor"; here it is "number of currently-unstable units/messages across the whole network," which any unprivileged unit poster can inflate simply by posting many units (e.g., payments plus `data_feed` messages) that stay unstable for a while (`storage.assocUnstableMessages` is populated for every unstable unit, not filtered by author) — see the population/removal sites in `writer.js`/`main_chain.js` that key entries by `unit`. Any AA that uses this "in data feed among unstable units" check will pay a cost proportional to the size of this global structure every time it is triggered, rather than a cost bounded by its own inputs.

### Impact Explanation
Because the loop runs synchronously inside AA/oscript evaluation triggered by a posted unit, a caller who first inflates `assocUnstableMessages` (by posting many not-yet-stable units) and then sends a trigger to an AA using this construct forces that AA's execution — and hence the validating/executing nodes' processing of that trigger unit — to do work proportional to total network unstable-message volume rather than to any value under the AA's own control. This can significantly degrade node performance for any AA relying on `in_data_feed`, and in the worst case can make triggers/executions unacceptably slow or resource intensive for all nodes processing that AA, which maps to the "AA fund loss or freezing" / "network struggling to confirm new units" impact classes named in the validation rules, since users interacting with the affected AA cannot get their trigger processed promptly and other legitimate work competes with the artificially expanded scan.

### Likelihood Explanation
Likelihood is moderate-to-high: any unprivileged actor can inflate `assocUnstableMessages` simply by posting ordinary units (no privileged AA definer role needed, no cryptographic difficulty), and any AA author who uses the `in_data_feed`-style check (a documented oscript primitive) becomes reachable to this cost amplification by any trigger sender. The severity is bounded by how many unstable units the attacker can realistically keep in memory before stabilization (limited by fees/tps but not by this check itself).

### Recommendation
Bound the bAA scan by the same query-relevant filters used in the on-disk (`kvstore`) path — e.g., index unstable data-feed messages by `feed_name`/oracle address instead of iterating the entire `assocUnstableMessages` map, or cap/short-circuit the number of unstable units scanned per call, mirroring the `MAX_COMPLEXITY`/`MAX_OPS` bounding pattern already used elsewhere in `definition.js` and `formula/validation.js` for AA-reachable operations.

### Proof of Concept
1. Post many ordinary units (any unprivileged unit poster) so that `storage.assocUnstableMessages` accumulates a large number of pending units before stabilization.
2. Deploy or use an existing AA whose oscript uses the "in data feed" primitive against unstable data (bAA path), and send it a trigger.
3. Observe that `dataFeedExists` walks the full `assocUnstableMessages` map (`data_feeds.js` lines 34-97) regardless of whether the search will ever match, with cost scaling with the attacker-inflated map size rather than with the AA's own state.

**Uncertainty note:** I was not able to retrieve the exact oscript call site in `formula/evaluation.js` that invokes `dataFeeds.dataFeedExists` with `bAA=true` within the tool budget available (grep confirmed matches exist in that file, but I could not view the surrounding lines to confirm the exact triggering oscript function name/reachability details before running out of iterations). The core defect — the unbounded, unfiltered loop in `data_feeds.js` itself — is confirmed directly from source.
