### Title
Delegated caller can drain account collateral through `swap_collateral` with a self-dealing route and no minimum-output enforcement - (File: contracts/controller/src/strategies/swap_collateral.rs)

### Summary
`swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` all accept fully caller-supplied `swap: Bytes` (a packed router program, `StrategySwap`) and are callable by any address satisfying `require_owner_or_delegate`. The controller never validates a minimum output on the swap leg: `swap_tokens` in `strategies/swap.rs` only asserts the router did not overspend the input (`RouterOverspend`) and that the output balance delta is positive (`NoSwapOutput` at `received > 0`). The only slippage floor is `amounts[min_out]` encoded inside the attacker-controlled `routeXdr`, which the router checks merely for `> 0`. A delegate of an account can therefore swap the victim's collateral through a route ending at the delegate's own liquidity/trade on Aquarius or Soroswap with `min_out = 1`, extracting nearly all value while leaving dust behind.

### Finding Description
`process_swap_collateral` authorizes `caller` via `account::require_owner_or_delegate(env, account_id, caller, &account.owner)` (`contracts/controller/src/strategies/swap_collateral.rs:47`), then calls `withdraw_and_swap_from_supply`, which routes through `swap_tokens_or_passthrough` → `swap_tokens` (`contracts/controller/src/strategies/swap.rs:13-55`). `swap_tokens` authorizes exactly one input transfer to the router, ignores `execute_strategy`'s return value, and validates only `in_after <= in_before` and `received > 0` (`swap.rs:37-82`). No oracle-derived floor on the output exists anywhere in the path; `strategy_finalize` (`strategies/mod.rs:48-56`) runs `enforce_post_pool_solvency`, which gates on LTV-weighted collateral covering debt and HF ≥ 1 — a check that is vacuous for a debt-free account and that still permits draining collateral down to the solvency boundary for an indebted one. The same structure applies to `swap_debt` (`swap_debt.rs:65-72`, output used to repay, so a bad fill leaves the victim's debt under-repaid) and `repay_debt_with_collateral` (withdrawn collateral swapped at a manipulated rate leaves debt outstanding while collateral is gone). Because route bytes are opaque `Bytes` forwarded verbatim to the router, venues are unallowlisted, so the delegate can point hops at pools where it is the counterparty.

### Impact Explanation
Theft of user funds. The delegate converts the victim's supplied collateral into a near-worthless output and captures the difference on its own trade leg — economically identical to the MarginDex `swap_margin` drain. For a debt-free account the entire swapped position can be siphoned; for an indebted account the drain is bounded only by the post-solvency check, and `repay_debt_with_collateral`/`swap_debt` variants can additionally strand the victim with unrepaid debt.

### Likelihood Explanation
Requires the victim to have called `add_delegate` on the attacker (delegates must be active approved managers per `docs/reference/endpoints.md:42-43`), matching the original report's trust model exactly — the vulnerability is that delegation scope implicitly includes unrestricted trade routing of the victim's funds. Once delegated, a single `swap_collateral` call executes the drain atomically.

### Recommendation
Enforce a protocol-side minimum output on strategy swap legs: either accept an explicit `min_amount_out` parameter on `swap_collateral`, `swap_debt`, and `repay_debt_with_collateral`, or validate the measured output against a Context-cached strict-price valuation (with a bounded deviation) inside `strategy_finalize`/`swap_tokens`, rather than accepting any positive balance delta.

### Proof of Concept
1. Victim supplies `X` of asset A (debt-free account) and calls `add_delegate(victim_account_id, attacker)`, where attacker is an approved manager.
2. Attacker seeds/counterparties liquidity on an Aquarius or Soroswap pool for the A→B pair and builds a `routeXdr` with `amounts[min_out] = 1` routing A→B through that pool at a manipulated price.
3. Attacker calls `controller.swap_collateral(attacker, victim_account_id, A_key, X, B_key, routeXdr)`.
4. `require_owner_or_delegate` passes; `withdraw_and_swap_from_supply` pulls `X` of A; the router pays a dust amount of B; `verify_router_output` passes since `received > 0`; `supply::process_deposit` books the dust; `strategy_finalize` passes because the account has no debt.
5. Attacker's pool position holds ~`X` of A purchased for dust; the victim's collateral is drained.
