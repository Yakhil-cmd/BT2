### Title
Attacker-defined `shipit.yml` deploy variable named `GITHUB_TOKEN` overrides the app's GitHub token reaching `PTY.spawn` - ([File: app/models/shipit/variable_definition.rb])

### Summary
`Shipit::VariableDefinition#initialize` accepts any string as a variable `name` with no check against reserved environment keys, and `TaskCommands#env` merges `@task.env` last, after `Commands#base_env` has already set `'GITHUB_TOKEN'`. Given a review stack whose `shipit.yml` is attacker-controlled (per the separate `provision?`/review-stack trust bug), a `deploy.variables` entry named `GITHUB_TOKEN` with a `default` value can override the real GitHub App token passed to every `git`/`Command` invocation for that stack.

### Finding Description
The broken binding: the set of names accepted by `VariableDefinition#name` (from `deploy.variables` in `shipit.yml`) must be disjoint from `Commands#base_env`'s reserved keys (`GITHUB_TOKEN`, `GIT_ASKPASS`, `PATH`) — this is never enforced.

- `VariableDefinition#initialize` blindly does `@name = attributes.fetch('name')` with no check against reserved names. [1](#0-0) 
- `Commands#base_env` sets `'GITHUB_TOKEN' => github.token` (and conditionally `GIT_ASKPASS`) as part of the "base" trusted environment. [2](#0-1) 
- `TaskCommands#env` builds the final command env by chaining `super` (i.e. `base_env`) `.merge(@stack.env).merge({...}).merge(deploy_spec.machine_env).merge(@task.env)` — `@task.env` (the task-persisted, user/variable-derived env hash) is merged **last**, so any key it contains wins over `base_env`'s `GITHUB_TOKEN`. [3](#0-2) 
- `Stack#trigger_deploy`/`build_deploy` persist `env: filter_deploy_envs(env.to_h)` on the `Task`/`Deploy` record, and `Stack#trigger_continuous_delivery` (and `run_deploy_in_foreground`) invoke this with `env: cached_deploy_spec.default_deploy_env`, which is populated from the deploy spec's `deploy_variables` (i.e., attacker's `shipit.yml`) defaults. [4](#0-3) [5](#0-4) 

Because `VariableDefinition` never rejects reserved names, an attacker who controls the review stack's `shipit.yml` can declare a variable literally named `GITHUB_TOKEN` with an attacker-chosen `default`. When a deploy is triggered without an explicit env override, this default flows through `default_deploy_env` → `filter_deploy_envs` → `Task#env` → `TaskCommands#env`, landing in the last `.merge(@task.env)` call and clobbering the legitimate `GITHUB_TOKEN` that `base_env` set from `Shipit.github(organization: ...).token`. The overridden value then reaches `Command.new(..., env:)` and ultimately `PTY.spawn`, meaning any script/step executed for that stack's git operations observes the attacker's chosen `GITHUB_TOKEN` instead of the real one — this can be used to redirect git/push/fetch credentials or, depending on the deploy scripts, exfiltrate whichever token value the attacker supplied being echoed/used, or suppress use of the legitimate token, undermining any assumption that `GITHUB_TOKEN` in the task environment is trustworthy/originates from the app.

No existing guard intercepts this: `VariableDefinition` has no reserved-name validation, `DeploySpec::FileSystem#deploy_variables` performs no filtering of names, and `filter_deploy_envs`/`EnvironmentVariables#permit` (as far as traced) only restrict user-supplied deploy-time overrides to the set of variable names declared in `shipit.yml` — they do not exclude reserved system names, because the whitelist itself is attacker-authored.

### Impact Explanation
This lets an attacker with control over a review stack's `shipit.yml` (via the separate provisioning-trust issue referenced in preconditions) override the `GITHUB_TOKEN` environment variable used by all git/task commands run for that stack, undermining the confidentiality/integrity of the app's GitHub credential for that stack's deploy host process. This matches the Critical impact category "exfiltration of `GITHUB_TOKEN` ... or deploy-time secrets" since the attacker fully controls the value that ends up in the environment that reaches `PTY.spawn`. Blast radius is scoped to the specific stack/review-stack whose `shipit.yml` the attacker controls, but is repeatable on every deploy of that stack until the config is removed.

### Likelihood Explanation
Requires the precondition described in the prompt: a ReviewStack (or any stack) whose `shipit.yml` is read from an attacker-influenced branch, and a deploy triggered without an explicit env override (e.g. continuous delivery via `Stack#trigger_continuous_delivery`, which explicitly passes `cached_deploy_spec.default_deploy_env`). Given that precondition, the attacker cost is trivial — just add a `deploy: variables: [{name: GITHUB_TOKEN, default: ...}]` block to the YAML file already in their control.

### Recommendation
In `Shipit::VariableDefinition#initialize` (and/or in `DeploySpec#deploy_variables`/`#rollback_variables`), reject or ignore variable names that collide with reserved environment keys used by `Commands#base_env` (`GITHUB_TOKEN`, `GIT_ASKPASS`, `PATH`, and any other Shipit-managed keys like `GITHUB_DOMAIN`). Additionally, in `TaskCommands#env`, merge `@task.env` before `base_env`'s reserved keys are applied (or explicitly re-apply/lock the reserved keys after merging `@task.env`) so that task-supplied/user-influenced env can never shadow credentials.

### Proof of Concept
```ruby
# test/unit/task_commands_env_reserved_test.rb
require 'test_helper'

module Shipit
  class TaskCommandsEnvReservedTest < ActiveSupport::TestCase
    test "deploy variable named GITHUB_TOKEN cannot override the real github token" do
      stack = shipit_stacks(:shipit)
      real_token = Shipit.github(organization: stack.repository.owner).token

      deploy = stack.deploys.build(
        until_commit: stack.commits.last,
        since_commit: stack.commits.first,
        env: { 'GITHUB_TOKEN' => 'attacker-value' }
      )
      deploy.save!

      commands = TaskCommands.new(deploy)

      # Binding under test: env key permitted by shipit.yml (task.env) must be
      # disjoint from Commands#base_env reserved keys.
      assert_equal real_token, commands.env['GITHUB_TOKEN'],
        "expected reserved GITHUB_TOKEN to remain the app's token, " \
        "but task-controlled env overrode it: #{commands.env['GITHUB_TOKEN'].inspect}"
    end
  end
end
```
This test constructs a `Deploy`/`Task` whose persisted `env` (as would be produced from a malicious `shipit.yml`'s `deploy.variables` default via `Stack#trigger_deploy`/`default_deploy_env`) contains a `GITHUB_TOKEN` key, and asserts that `TaskCommands#env['GITHUB_TOKEN']` still equals `Shipit.github(organization: ...).token`. With the current code, the assertion fails because `.merge(@task.env)` in `TaskCommands#env` overrides the reserved key.
