## Title
`signed_message` packages lack any network/chain-binding field, enabling cross-network signature replay - (File: `signed_message.js`, `object_hash.js`)

### Summary
`validateSignedMessage`/`is_valid_signed_package` verify a signature over a `signed_message` package hash that never incorporates a network-identifying value (no `alt`, no genesis unit, no chain id equivalent). Because address `chash` values are derived only from the definition/pubkey (independent of `alt`/testnet-vs-mainnet), the exact same signed package + signature can be replayed against an identical AA/address deployed on a different Obyte-based network (mainnet, testnet, devnet, or any private fork of the same codebase), analogous to the reported EVM issue where a missing `chainId` in the signed payload allowed replay of `deploy`/`call` signatures across chains.

### Finding Description
`getSignedPackageHashToSign` in [1](#0-0)  hashes only the fields present in the `signedPackage` object (`signed_message`, `authors`, optionally `last_ball_unit`, `timestamp`, `version`). It contains no constant tying the hash to a specific network (`constants.alt`, `constants.GENESIS_UNIT`, etc.).

In `validateSignedMessage` ( [2](#0-1) ), the `version` field is optional — if omitted, the `supported_versions` check that would otherwise enforce a network-specific version string (`'2.0'` on mainnet vs `'2.0t'` on testnet, see `constants.js` line 27) is skipped entirely: [3](#0-2) 

Additionally, when `last_ball_unit` is absent (`bNetworkAware = false`), the package is validated purely from the inline `author.definition`/`author.address` with no reference to any unit on any particular DAG: [4](#0-3) 

Since address `chash` (via `objectHash.getChash160`) does not depend on `alt`/network, the same keypair produces the same address on mainnet, testnet, and devnet. A signed package built this way (no `version`, no `last_ball_unit`) is therefore a self-contained, network-agnostic message: identical bytes and signature verify successfully wherever the same definition/address exists.

This primitive is consumed directly by oscript in AAs via `is_valid_signed_package` ( [5](#0-4) ), and is used in production-style AA logic such as payment-channel closing, where a peer's off-chain signed balance update is checked with `is_valid_signed_package`: [6](#0-5) . The same mechanism backs wallet-level flows (`arbiter_contract_response`, `prosaic_contract_response`) that call `signed_message.validateSignedMessage` directly: [7](#0-6) .

### Impact Explanation
If the same address/definition and equivalent AA logic are instantiated on more than one Obyte-based network (a common practice: mainnet + testnet + devnet forks, or independent private deployments of the same AA template), a `signed_message`/`is_valid_signed_package` payload created for one network can be replayed verbatim as AA trigger data on another network sharing the same signer address. This can drive unintended AA state transitions (e.g., a payment-channel "close" signed message intended for one deployment being replayed to force a close/payout on another deployment with the same channel parties and definition), resulting in AA fund loss or unauthorized state changes without requiring a fresh signature from the counterparty.

### Likelihood Explanation
Exploitation requires the attacker to possess a validly-signed package (obtained from a legitimate off-chain exchange, e.g. a payment-channel partner message) and a target AA/address pair replicated with the same definition on another network instance — a realistic scenario for template AAs deployed identically across mainnet/testnet/devnet or forked networks. No privileged access is needed; any holder of a captured signed package can post it as ordinary AA trigger data.

### Recommendation
Bind `signed_message` payloads to the network by making `version`/network-context mandatory (not optional) in `getSignedPackageHashToSign` and `validateSignedMessage`, or explicitly include `constants.alt` (or `constants.GENESIS_UNIT`) as a required field that is hashed and checked, so a package signed for one network's `alt`/genesis cannot validate on another.

### Proof of Concept
1. On Network A (e.g. mainnet) and Network B (e.g. a devnet/testnet fork running the same AA template such as `test/samples/payment_channels.oscript`), deploy the identical AA and have the same two parties (same keypairs ⇒ identical chash addresses on both networks) open channels with matching `period`/state.
2. Party A signs a `signed_message` package without a `version` field and without `last_ball_unit` (or with a `version` value not enforced per-network), e.g. `{signed_message: {channel: addr, period: 1, amount_spent: X}, authors: [{address, definition, authentifiers}]}`, per `signed_message.js` lines 241-253.
3. Party B submits this exact package as `trigger.data.sentByPeer` to Network A's AA to legitimately close the channel, per `test/samples/payment_channels.oscript` lines 40-49.
4. Party B (or an observer who captured the message from the network) resubmits the identical package as trigger data to the corresponding AA instance on Network B; `is_valid_signed_package`/`validateSignedMessage` re-verifies successfully because the hash (`object_hash.js` lines 97-103) and signature never encoded any network-specific data, letting the same signature force the analogous state change/fund payout on Network B without Party A's consent for that network.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
