### Title
Private-payment chains are forwarded in full to any co-signer/multisig peer holding *any* one output address, leaking other parties' private outputs — ([File: wallet.js])

### Summary
The Mattermost advisory describes leaking the contents of a post to a user who is not a member of the channel it belongs to, because metadata sanitization didn't correctly scope access. `ocore`'s private-asset payment protocol has an analogous access-control gap: when a device receives (or originates) a batch of private-payment chains covering multiple outputs/recipients in one unit, it computes the union of *all* output addresses across *all* chains and then forwards the **entire, unfiltered `arrChains` array** to every wallet/device that controls *any one* of those addresses — including cosigners of unrelated shared addresses that are not parties to the other outputs in the batch.

### Finding Description
`forwardPrivateChainsToOtherMembersOfOutputAddresses` in `wallet.js` collects addresses from every chain in the batch into one set, then forwards the whole `arrChains` (not just the chains belonging to that address) to whoever controls those addresses: [1](#0-0) 

This is invoked directly after successfully validating a hub-forwarded batch of private-payment chains, using the full unfiltered chain list: [2](#0-1) 

It's also used when private chains are produced locally in `sendMultiPayment`, and separately, cosigner-forwarding paths (`forwardPrivateChainsToOtherMembersOfSharedAddresses`) forward `arrChainsOfCosignerPrivateElements`/`arrChainsOfCosignerPrivateElements` to *all* control addresses of the paying addresses, again as one combined batch: [3](#0-2) [4](#0-3) 

The downstream helpers `wallet_defined_by_keys.forwardPrivateChainsToOtherMembersOfWallets` and `wallet_defined_by_addresses.forwardPrivateChainsToOtherMembersOfAddresses` do not filter the chain list per recipient — `forwardPrivateChainsToOtherMembersOfAddresses` just resolves device addresses controlling the given shared addresses and forwards the same `arrChains` blob to them verbatim: [5](#0-4) 

Each `objHeadPrivateElement.payload` in a chain element contains the full payment payload with all sibling outputs' addresses/blinding factors when derived from `buildPrivateElementsChain`/`indivisibleAsset`/`divisibleAsset` composer flows, and `emitNewPrivatePaymentReceived`/`handlePrivatePaymentChains` operate on the batch as a whole rather than isolating which chain element is destined for which recipient: [6](#0-5) 

Consequently, a device that is a cosigner or member of only one of the output addresses referenced anywhere in the multi-output batch (e.g., the "change" address of a *different* payment participant, or an unrelated shared address that happens to appear in the same composed unit) receives the complete set of private chains, including the payload (asset, amount, address, blinding) for outputs it has no right to see. This mirrors the Mattermost flaw: content scoped to one recipient/channel leaks to a party who is only tangentially related (a member of some other address in the same unit), because the forwarding logic does not sanitize/scope the payload set to the specific recipient before sending.

### Impact Explanation
This breaks the confidentiality guarantee of private (blinded) assets: a party who legitimately controls one output address in a composed transaction (e.g., a cosigner on a shared/multisig address used as change, or as one of several destinations in the same unit) can obtain the private payloads — amounts, addresses, and blinding factors — for outputs belonging to unrelated recipients in the same unit. This is a confidentiality/access-control violation (CWE-284 analog) rather than a spending or consensus bug: it does not directly enable double-spending or fund loss, but it discloses private transaction details (amounts and addresses) to parties who are not the intended recipients, undermining the entire purpose of the "private asset" feature.

### Likelihood Explanation
This requires a private (`is_private`) asset payment composed with multiple outputs whose addresses are controlled by different, mutually-untrusted device owners (a common real-world scenario: a multi-output private payment with a shared/multisig change address, or multiple recipients in one message). No malicious peer/hub/node behavior is needed — the forwarding logic itself, run by honest software on an honest device, aggregates and blindly forwards the whole batch. The bug is triggered purely by normal wallet/device message handling for private payment chains reachable by any user composing or receiving such a payment.

### Recommendation
Scope the private-payment forwarding strictly per recipient: when calling `forwardPrivateChainsToOtherMembersOfWallets`/`forwardPrivateChainsToOtherMembersOfAddresses`, filter `arrChains` down to only the chain(s) whose head output actually belongs to the specific address (or its shared-address ancestry) being notified, instead of computing a global address set from the whole batch and forwarding the entire unfiltered `arrChains`. Apply the same per-recipient filtering in `forwardPrivateChainsToOtherMembersOfSharedAddresses` and in the `sendMultiPayment` cosigner-forwarding path so that cosigners only receive the private elements relevant to addresses they actually control.

### Proof of Concept
1. Alice composes a private-asset payment unit with two outputs in the same message: one to Bob's ordinary address, and one "change" output to a shared/multisig address `S` that Alice shares with Carol (unrelated cosigner, not a party to Bob's payment).
2. `composeIndivisibleAssetPaymentJoint`/`composeDivisibleAssetPaymentJoint` builds `assocPrivatePayloads` covering both outputs; `getSavingCallbacks`'s `preCommitCallback` builds `arrRecipientChains` (for Bob) and `arrCosignerChains` (for all outputs, including the change to `S`) via `buildPrivateElementsChain`. [7](#0-6) 
3. After saving, `sendMultiPayment`'s `preCommitCb` calls `forwardPrivateChainsToOtherMembersOfSharedAddresses(arrChainsOfCosignerPrivateElements, arrPayingAddresses, ...)`, which resolves all control device addresses of `arrPayingAddresses` (including Carol, as cosigner of `S`) and forwards the same `arrChainsOfCosignerPrivateElements` batch — which includes chains for outputs unrelated to `S` — to Carol's device. [3](#0-2) [4](#0-3) 
4. Carol's device processes the received `private_payments` message via `handlePrivatePaymentChains`, which validates and saves every chain in the batch and stores/exposes the full payloads (amounts, addresses, blinding factors) for Bob's payment as well, even though Carol was never a party to that output. [8](#0-7)

function forwardPrivateChainsToOtherMembersOfSharedAddresses(arrChainsOfCosignerPrivateElements, arrPayingAddresses, excluded_device_address, bForwarded, conn, onDone){
	walletDefinedByAddresses.readAllControlAddresses(conn, arrPayingAddresses, function(arrControlAddresses, arrControlDeviceAddresses){
		arrControlDeviceAddresses = arrControlDeviceAddresses.filter(function(device_address) {
			return (device_address !== device.getMyDeviceAddress() && device_address !== excluded_device_address);
		});
		walletDefinedByKeys.readDeviceAddressesControllingPaymentAddresses(conn, arrControlAddresses, function(arrMultisigDeviceAddresses){
			arrMultisigDeviceAddresses = _.difference(arrMultisigDeviceAddresses, arrControlDeviceAddresses);
			// counterparties on shared addresses must forward further, that's why bForwarded=false
			walletGeneral.forwardPrivateChainsToDevices(arrControlDeviceAddresses, arrChainsOfCosignerPrivateElements, bForwarded, conn, function(){
				walletGeneral.forwardPrivateChainsToDevices(arrMultisigDeviceAddresses, arrChainsOfCosignerPrivateElements, true, conn, onDone);
			});
		});
	});
}
