## Confirmed vulnerability

Comparing `PushHandler#process` and `CheckSuiteHandler#process` (both scope their queries to `stacks.where(branch: ...)` before touching commits) against `StatusHandler#process`, only the latter fails to filter by repository/stack: [1](#0-0) 

The equality the code implicitly assumes is: `commit.stack.repository == webhook.payload.repository`. This is never checked. `StatusHandler#process` does `Commit.where(sha: params.sha)`, a global, cross-stack, cross-repository lookup keyed only on the SHA string, then calls `commit.create_status_from_github!(params)` on every match, regardless of which repository/organization actually sent the webhook: [2](#0-1) 

This writes into `Status` via `statuses.replicate_from_github!(stack_id, github_status)` using the **victim commit's own `stack_id`**, not any value derived from the webhook payload's repository: [3](#0-2) 

`Commit#blocked?` and `Status::Common#blocking?` then consume this attacker-controlled `state`: [4](#0-3) [5](#0-4) 

and `Status#schedule_continuous_delivery` fires unconditionally `after_commit :create`, cascading into `Commit#deployable?` → `ContinuousDeliveryJob`: [6](#0-5) [7](#0-6) 

**Why signature verification does not stop this**: `verify_signature` in `WebhooksController` only checks that the payload is signed with the webhook secret for `repository_owner` (`params.dig('repository','owner','login')`), i.e. it authenticates *which org/app installation* sent the request — it says nothing about whether the `sha` inside the payload actually belongs to that org's repository: [8](#0-7) 

So a validly-signed webhook from **any** repository the attacker controls (their own fork, or any other repo they can push a commit status to) that happens to reference a SHA that also exists as a `Commit` row belonging to a *different* stack/repository will silently overwrite that other stack's status for that commit. Because Git SHAs are content-addressed, this is trivially reachable in the extremely common case of a fork: if the attacker forks the victim's public repository, every unmodified commit in the fork has the byte-identical SHA as in upstream. The attacker can push/tag a commit status on their own fork (an action they fully control on a repo they own) with `context` set to the victim's configured `ci.blocking` context and `state: success`, causing GitHub to emit a validly-signed `status` webhook (signed by whatever org config governs the attacker's own repo/installation) with that SHA. `StatusHandler` then finds the pre-existing `Commit` record for that SHA in the **victim's** stack and applies the forged status to it.

## Assessment

This matches the reported bug precisely: `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) resolves commits purely by `sha`, with no join/check against `stack.repository` or the payload's `repository.full_name`, allowing a payload legitimately signed for one repository to mutate `Status`/`Commit` state belonging to a completely different stack. This clears the blocking-status check in `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) for a later commit and can trigger `schedule_continuous_delivery`, i.e. an unauthorized deploy — matching the Critical impact category ("a payload for one repository mutating another's stack, commit ... or an unauthorized deploy").

### Title
Cross-repository commit-status forgery via SHA-only lookup bypasses `Commit#blocked?` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits solely by `Commit.where(sha: params.sha)` with no verification that the webhook's originating repository matches `commit.stack.repository`. Any repository (e.g. an attacker-owned fork sharing SHAs with the victim's public repo history) can emit a validly-signed `status` webhook that overwrites a `Status` row belonging to an unrelated stack, clearing `Commit#blocked?` for the victim stack and triggering an unauthorized continuous deployment.

### Finding Description
The broken binding: `commit.stack.repository == webhook.payload.repository.full_name` is assumed but never checked — the real check performed is only `commit.sha == payload.sha`. `WebhooksController#verify_signature` authenticates the sending GitHub App installation/organization (`repository_owner`) but does not bind that identity to the `sha`/commit being mutated (`app/controllers/shipit/webhooks_controller.rb:24-49`). `StatusHandler#process` then does a global `Commit.where(sha: params.sha)` scan across all stacks (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`), unlike `PushHandler` and `CheckSuiteHandler`, which both scope through `stacks.where(branch: ...)` first before touching any `Commit`. `Commit#create_status_from_github!` writes the forged state via `statuses.replicate_from_github!(stack_id, github_status)` using the victim commit's own `stack_id` (`app/models/shipit/commit.rb:165-169`, `app/models/shipit/status.rb:23-33`). Attack flow: attacker forks the victim's public repo (identical SHAs by construction of Git's content addressing), sets a commit status with `context` equal to one of the victim stack's `ci.blocking` contexts and `state: success` on a commit that (in the victim's history) currently has a blocking failure between `last_deployed_commit` and a later target commit. GitHub emits a `status` webhook, signed for the attacker's own org/installation, which passes `verify_signature` (it only checks against the attacker's own repository owner) and is delivered to Shipit. `StatusHandler` matches the SHA against the victim's `Commit` row and writes a `success` `Status` to it, flipping `Status::Common#blocking?` (`app/models/shipit/status/common.rb:46-48`) to false, so `Commit#blocked?` (`app/models/shipit/commit.rb:231-237`) on the later target commit now returns `false`, `Commit#deployable?` (`app/models/shipit/commit.rb:227-229`) becomes `true`, and `Status#schedule_continuous_delivery` (`app/models/shipit/status.rb:42-44`, fired via `after_commit ... on: :create`) schedules `ContinuousDeliveryJob` for the victim stack.

### Impact Explanation
An unprivileged GitHub user who owns any repository sharing commit SHAs with a victim's public repo (trivially true for forks) can forge blocking-CI-status success on the victim's tracked commit, defeating `ci.blocking` protections and triggering an unauthorized deploy for a stack they do not own or maintain. This is repeatable against any Shipit-tracked stack whose repository is public and forkable, and the blast radius spans all stacks that happen to share commit history (forks, mirrors, monorepo splits) with any repository the attacker can push a status to — matching "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy" (Critical).

### Likelihood Explanation
Preconditions: victim stack configures `ci.blocking` in `shipit.yml`; a commit between `last_deployed_commit` and a later commit currently carries a failing/missing blocking status; the victim repository is public (or otherwise forkable/duplicable) so the attacker can obtain a repo sharing the exact commit SHA; the attacker's own repository/org must have a GitHub App installation whose webhooks reach the same Shipit instance (true whenever the same GitHub App is installed on the attacker's account/repo, or the attacker's org is one Shipit is already configured for). Cost to the attacker is low — fork, set a commit status via the GitHub API on their own repo — and it is fully repeatable against any commit/stack pair that shares SHAs.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to stacks whose `repository` matches the webhook payload's `repository.full_name`/`id` (mirroring the `stacks.where(branch: ...)` pattern already used by `PushHandler`/`CheckSuiteHandler`), e.g. resolve `stacks.where(repository: repo_from_payload).commits.where(sha: params.sha)` instead of the global `Commit.where(sha: ...)`, so a status is only applied to commits belonging to the stack whose repository actually authenticated the webhook.

### Proof of Concept
minitest plan (no live GitHub, using existing fixtures/handler directly, analogous to `test/models/commits_test.rb` blocking tests):
1. Create two `Stack` fixtures/records, `victim_stack` (repository `victim/repo`, `blocking_statuses` including `soc/compliance`) and `attacker_stack` (repository `attacker/repo-fork`).
2. Create a `Commit` with `sha: 'deadbeef...'` under `victim_stack` with a failing status whose `context` is in `victim_stack.blocking_statuses`; create a later `Commit` on `victim_stack`.
3. Assert baseline: `assert commit.blocking?` and `assert later_commit.blocked?`.
4. Also create a `Commit` fixture with the **same sha** under `attacker_stack` (simulating the shared fork history).
5. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new(status_params_with_matching_sha_and_context_and_state_success).call` (or POST through `WebhooksController` with signature stubbed to true) using a payload whose `repository.full_name == 'attacker/repo-fork'`.
6. Assert: `refute victim_commit.reload.blocking?` and `refute later_commit.reload.blocked?` — demonstrating the victim's `Status` was mutated by a payload provenanced to `attacker/repo-fork`, i.e. `commit.stack.repository != payload.repository` yet the write succeeded.
7. Assert `ContinuousDeliveryJob` was enqueued for `victim_stack` (`assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])`) to demonstrate the resulting unauthorized deploy scheduling.
