### Title
Unsafe `transferFrom` in `handleERC721Transfer()` Permanently Locks Bridged ERC721 Tokens in Non-Receiver Contracts — (File: `contracts/service_chain/bridge/BridgeTransferERC721.sol`)

---

### Summary

`BridgeTransferERC721.handleERC721Transfer()` uses `IERC721.transferFrom()` instead of `safeTransferFrom()` when releasing ERC721 tokens to the recipient `_to` in lock/unlock mode. If `_to` is a contract that does not implement `onERC721Received`, the token is permanently locked in that contract with no recovery path, because the handle nonce is consumed before the transfer executes.

---

### Finding Description

In `contracts/service_chain/bridge/BridgeTransferERC721.sol`, the `handleERC721Transfer()` function handles the destination-side release of bridged ERC721 tokens. When `modeMintBurn == false` (lock/unlock mode), the bridge holds the token and releases it to `_to` via:

```solidity
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);
``` [1](#0-0) 

The `IERC721` interface used by the bridge explicitly exposes `safeTransferFrom(address,address,uint256)` alongside `transferFrom`, but the unsafe variant is chosen: [2](#0-1) 

Critically, the handle nonce is fully consumed and state is committed **before** the transfer call: [3](#0-2) 

`_setHandledRequestTxHash`, `handleNoncesToBlockNums[_requestedNonce]`, and `_updateHandleNonce` are all finalized before line 69. The `HandleValueTransfer` event is also emitted before the transfer. Once the nonce is consumed, the bridge will reject any retry of the same request (`_lowerHandleNonceCheck` enforces this): [4](#0-3) 

`transferFrom` does not call `onERC721Received` on the recipient. If `_to` is a contract without that hook, the ERC721 token is transferred to it successfully at the EVM level (ownership changes), but the contract cannot interact with or forward the token — it is permanently locked.

---

### Impact Explanation

- **Asset loss**: A bridged ERC721 token is permanently locked in the recipient contract. The token's ownership record in the ERC721 contract points to `_to`, but `_to` has no mechanism to move it.
- **No recovery**: The bridge nonce is consumed before the transfer, so the bridge operators cannot re-execute the handle for the same cross-chain request. The source-chain lock is also already committed.
- **Scope**: Affects all deployments of `BridgeTransferERC721` operating in lock/unlock mode (`modeMintBurn == false`).

---

### Likelihood Explanation

The `_to` address is fully user-controlled: it is set by the originating user on the source chain in `requestERC721Transfer` or `onERC721Received`, and is passed through the bridge event without modification: [5](#0-4) 

Any user who specifies a contract address (e.g., a multisig, a DeFi protocol, a custom contract) as `_to` on the destination chain triggers this path. This is a realistic and common use case (bridging NFTs to a contract wallet or protocol). No special privilege is required.

---

### Recommendation

Replace `transferFrom` with `safeTransferFrom` on line 69 of `BridgeTransferERC721.sol`:

```solidity
// Before
IERC721(_tokenAddress).transferFrom(address(this), _to, _tokenId);

// After
IERC721(_tokenAddress).safeTransferFrom(address(this), _to, _tokenId);
```

`safeTransferFrom` is already declared in the `IERC721` interface used by the bridge, so no import changes are needed. The call will revert if `_to` does not implement `onERC721Received`, preventing nonce consumption and asset loss. Note that this introduces a reentrancy surface; the function should be reviewed against reentrancy guards (the ERC20 path already uses `safeTransfer` from OpenZeppelin's `SafeERC20`, which is consistent with this fix): [6](#0-5) 

---

### Proof of Concept

1. Alice owns ERC721 token ID `42` on the source chain.
2. Alice calls `requestERC721Transfer(tokenAddress, contractWithoutReceiver, 42, "")` on the source bridge, specifying a contract address that does not implement `onERC721Received` as `_to`.
3. The source bridge emits `RequestValueTransferEncoded` and locks token `42`.
4. Bridge operators observe the event and call `handleERC721Transfer(..., contractWithoutReceiver, tokenAddress, 42, nonce, ...)` on the destination bridge.
5. The bridge executes:
   - `_setHandledRequestTxHash(txHash)` — nonce marked as handled
   - `handleNoncesToBlockNums[nonce] = blockNumber` — nonce state committed
   - `_updateHandleNonce(nonce)` — `lowerHandleNonce` advanced
   - `emit HandleValueTransfer(...)` — event emitted
   - `IERC721(tokenAddress).transferFrom(bridge, contractWithoutReceiver, 42)` — **succeeds silently**
6. Token `42` is now owned by `contractWithoutReceiver`, which has no `onERC721Received` and no way to transfer it out.
7. Any retry of the same nonce is rejected by `_lowerHandleNonceCheck` with `"removed vote"`.
8. Token `42` is permanently locked. Alice's asset is lost with no recourse.
