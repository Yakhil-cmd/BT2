### Title
Webhook signature verification keyed off attacker-controlled `repository.owner.login` allows cross-organization forgery in multi-org deployments - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify the incoming payload against by reading `repository.owner.login` (or `organization.login`) directly out of the unauthenticated request body, before any signature has been checked [1](#0-0) [2](#0-1) . `GitHubApp#verify_webhook_signature` then trivially returns `true` whenever the resolved organization has no `webhook_secret` configured: `return true unless webhook_secret` [3](#0-2) .

### Finding Description
The binding that should hold is: *the organization whose secret authenticated the request* == *the repository/organization the request is allowed to mutate*. In a multi-organization Shipit deployment (documented in `config/secrets.development.example.yml`, which explicitly supports per-org `github:` blocks, each with an optional `webhook_secret`) [4](#0-3) , the engine picks the `GitHubApp` instance to verify against using an attacker-controlled field of the very payload being verified:

```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(...)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [5](#0-4) 

If any configured organization has `webhook_secret: nil` (an explicitly supported, "optional" configuration per the setup docs) [6](#0-5) , then for that organization `verify_webhook_signature` short-circuits to `true` regardless of the actual `X-Hub-Signature` header [3](#0-2) . An attacker who knows (or guesses) that one org in a multi-org install has no webhook secret configured can craft a JSON body claiming `repository.owner.login` = that unsecured org, while the `repository.full_name`/`sha`/`branches` etc. fields inside the same payload reference a completely different, secured organization's repository. The signature check passes (because it was evaluated against the unsecured org's — non-existent — secret), and the payload is then dispatched unmodified to the real handlers (`PushHandler`, `StatusHandler`, `MembershipHandler`, `CheckSuiteHandler`, etc.), which act on whatever repository/organization/commit the body actually names, not on the org used to authenticate.

This is exactly the "organization authenticated vs. repository written" trust binding: the security check is bound to one payload field while the mutating logic is bound to different, independently-controlled fields of the same forged payload.

### Impact Explanation
An attacker able to trigger this can forge GitHub webhook events for repositories belonging to a fully-secured organization: fake `push` events causing `GithubSyncJob` to run against arbitrary SHAs, fake `status`/`check_suite` events flipping commit statuses used to gate deploys, and `membership` events that auto-create arbitrary GitHub `Team`/`User` records tied into `Shipit.github_teams` authorization [7](#0-6) . Since Shipit's own authorization model gates access based on GitHub team membership synced via these webhooks, forged `membership` events can be used to escalate into `Shipit.github_teams` authorization — matching the High-severity impact class defined in scope.

### Likelihood Explanation
This requires a specific but realistic deployment condition: a multi-organization Shipit install (a documented, supported configuration) where at least one organization omits `webhook_secret` (also documented as "optional"). Under that condition, the bypass requires no credentials, no session, and no privileged access — only an internet-reachable POST to `/webhooks` with a crafted JSON body and matching `X-Github-Event` header, which is fully unauthenticated by design. The likelihood is moderate-to-high specifically for multi-org deployments that leave any one org's webhook secret unset (e.g. for local/testing orgs left in a shared production config), and zero for single-org deployments that always configure a secret.

### Recommendation
Do not let payload-supplied identity fields select the verification key. Options:
1. Require every configured `github` organization entry to have a non-blank `webhook_secret` (fail closed / raise a startup error if any org lacks one), removing the "return true unless webhook_secret" bypass entirely.
2. After signature verification succeeds under organization X, additionally assert that every repository/organization field acted upon in the payload (`repository.owner.login`, `repository.full_name`) actually belongs to organization X before dispatching to handlers.
3. Alternatively, verify the payload's HMAC against the secrets of all configured organizations and only proceed if a *non-blank* secret matched, never accepting a "no secret configured" org as a valid verification outcome for events referencing other repositories.

### Proof of Concept
1. Deploy Shipit configured with two GitHub orgs: `secured-org` (has `webhook_secret: "s3cr3t"`, and a tracked stack for `secured-org/app`) and `unsecured-org` (installed but `webhook_secret: nil`).
2. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything

{
  "repository": {"full_name": "secured-org/app", "owner": {"login": "unsecured-org"}},
  "after": "<attacker-chosen-sha>",
  "ref": "refs/heads/master"
}
```
3. `repository_owner` resolves to `"unsecured-org"` [2](#0-1) ; `Shipit.github(organization: "unsecured-org").verify_webhook_signature(...)` returns `true` immediately because that org's `webhook_secret` is blank [3](#0-2) .
4. `create` re-parses the same body and dispatches it to `Shipit::Webhooks.for_event('push')` handlers, which act on `repository.full_name = "secured-org/app"`, enqueuing a `GithubSyncJob` for the secured stack despite the request never being signed by `secured-org`'s real webhook secret.

      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
