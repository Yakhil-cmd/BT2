### Title
Coarse `(filePath, category)` dedup key lets a new dangerous finding be silently suppressed by a prior weaker finding at the same location - (File: `plugins/security-guidance/hooks/security_reminder_hook.py`)

### Summary
`handle_commit_review_posttooluse` (and the equivalent Stop-hook path) records previously-surfaced LLM findings keyed only by `(filePath, category)`, not by the actual vulnerable code. Once any finding of a given category has been reported for a file, `_dedup_against_state`/`_record_findings` will suppress every subsequent finding of the same category in that same file for the remainder of the TTL window, even if the new code is a substantially different and more dangerous instance of that vulnerability class.

### Finding Description
In `handle_commit_review_posttooluse`, after a commit is reviewed and vulnerabilities are found, new findings are recorded into shared session state keyed as: [1](#0-0) 
```
key = (f["filePath"], f["category"])
```
This is explicitly acknowledged in the code comment as a deliberate coarsening: `vulnerableCode` bytes are not used because they "drift between fires," so matching on `(filePath, category)` was chosen instead. The same shared `previous_findings` state is consumed by `_dedup_against_state` (via `_finding_keys`) in both the commit-review path and the Stop-hook diff review path, and is fed forward turn-to-turn within `PREVIOUS_FINDINGS_TTL_SEC` (default 3600s).

Because the key omits any content signal, an attacker who fully controls the diff across ordinary edits/commits (the stated threat model) can:
1. Introduce a low-severity/benign instance of a vulnerability category (e.g. `category: "SQL Injection"`) in `foo.py`, triggering one review cycle that records `("foo.py", "SQL Injection")` into `previous_findings`.
2. In a subsequent edit/commit/amend/push within the TTL window, replace that code with a genuinely dangerous instance of the same category in the same file (e.g. a real unauthenticated RCE-grade SQL injection). Because the `(filePath, category)` key already exists in `previous_findings`, `_dedup_against_state` treats the new LLM finding as already-known and drops it before any warning is emitted or exit(2) rewake occurs.
3. Both the commit-review and push-sweep code paths (`handle_commit_review_posttooluse`, `handle_push_sweep_posttooluse`) rely on the same shared state, so the dangerous change can survive amends and pushes without ever being flagged as new.

### Impact Explanation
This breaks the stated invariant that "dangerous edits and commands must stay reviewable and blockable even across retries, amends, and pushes." A new, more severe vulnerability can piggyback on a previously-seen, less severe finding in the same file/category and never trigger the exit(2) guard/rewake or the human-visible warning — a logic-level bypass of the security-guidance review gate.

### Likelihood Explanation
The attack requires only ordinary repository write access (editing/committing files), matching the "unprivileged attacker, no leaked credentials" model. It is fully deterministic — no timing race or credential leak is needed, only two edits to the same file/category within the 1-hour `PREVIOUS_FINDINGS_TTL_SEC` window (or shorter `STOP_LOOP_STATE_TTL_SEC`/session window for the Stop-hook path). The behavior is reproducible on every run because the dedup key computation is deterministic.

### Recommendation
Include a content-derived signal in the dedup key (e.g., a normalized hash of `vulnerableCode`, or at least severity-aware suppression that only dedups findings of severity ≤ the previously recorded finding for that `(filePath, category)`). At minimum, do not suppress a new finding whose `severity` is higher than any previously recorded finding for the same key.
