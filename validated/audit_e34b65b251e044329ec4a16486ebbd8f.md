### Title
Attacker-controlled route venue can join the caller's authorization tree and drain tokens beyond the routed amount - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller's router strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`) pass user-supplied route XDR to the swap router, which invokes whatever pool/token contract addresses the payload names — there is no venue/pool allowlist. Because the router call executes below the caller's `require_auth` entry, a malicious contract placed on a hop can perform `token.transfer(victim, attacker, X)` on any token the victim holds; the Soroban host records that call as a child of the victim's signed authorization tree, so it executes if the victim signs the simulated tree. This is the contract-level analog of SSRF: the protocol makes an external call to an attacker-chosen endpoint inside the victim's privilege context.

### Finding Description
`swap_tokens` authorizes exactly one input-token transfer to the router and then calls `router.execute_strategy(controller, amount_in, swap)` with `swap` fully attacker-influenced (route bytes chosen by the caller) [1](#0-0) . The controller only measures its own `token_in`/`token_out` deltas afterward (`RouterOverspend`, `NoSwapOutput`) [2](#0-1)  — those checks bound the routed amount but not what route-named code does under the caller's auth tree.

The router keeps no allowlist of pools or tokens; each hop dispatches to `ctx.hop.pool`, an address decoded from the payload [3](#0-2) . Venue adapters invoke the named pool contract directly [4](#0-3) . The threat model confirms the consequence: "a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded by an honest simulation as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount" [5](#0-4) .

The dedicated harness test proves it end-to-end: a `RogueHopPool` placed as a hop calls `token.transfer(alice, attacker, WALLET_BALANCE)` during `swap_collateral`, simulation records the theft as a child of Alice's `swap_collateral` auth entry, and in enforcing mode the signed poisoned tree moves her full wallet balance while the swap itself returns a fair output and passes all controller checks [6](#0-5) [7](#0-6) [8](#0-7) .

### Impact Explanation
Theft of user funds. The loss is not bounded by `amount_in`, `min_out`, or the final risk gate: the rogue contract can transfer any token the victim owns (not just protocol-listed assets) up to the signed amount, e.g. her entire 77.77-unit wallet balance in the test. The same exposure exists for direct `execute_strategy` callers.

### Likelihood Explanation
An unprivileged attacker crafts a route embedding a malicious hop pool and convinces a victim to execute a controller strategy through it (e.g. via a malicious frontend or phishing route). The theft only succeeds if the victim signs the simulated auth tree without inspecting child invocations — the tree visibly contains the rogue transfer, and the threat model assigns decode-and-refuse responsibility to the client. That signing dependency, plus it being a documented design exposure, caps this at Medium rather than High.

### Recommendation
- Enforce a venue/pool allowlist (or hash-pinned pool set) in the router so route bytes cannot name arbitrary contracts.
- Alternatively/additionally, have the controller invoke the router through a dedicated intermediary or restricted auth shape so hop code cannot attach sub-invocations to the user's root entry.
- Wallets and the reference client must diff the simulated auth tree and reject any `swap_*`/`multiply`/`repay_debt_with_collateral` authorization containing child invocations other than the single expected input `transfer`.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates it: Alice supplies 10,000 USDC and holds an unrelated `wallet_token`. The attacker deploys `RogueHopPool` whose `swap()` calls `token.transfer(alice, attacker, WALLET_BALANCE)`, embeds it as the hop pool in the `swap_collateral` route, and the honest router pays a fair ETH output. Simulation records the stolen transfer under Alice's `swap_collateral` entry; with the poisoned signed tree, `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` while `supply_balance_raw(ALICE, "ETH") == FAIR_OUT_ETH` — the swap looks completely normal on-chain.
