### Title
Webhook signature verification is bound to the payload's organization, but status/commit writes are resolved by a globally-unscoped SHA lookup - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
This is the same class of bug as the external report: a signature (or, in `MinimalForwarder`'s case, msg.sender) is verified against one identity, while a *different* field in the same payload is what actually gets acted upon, with no cross-check that the two agree. `WebhooksController#verify_signature` authenticates a webhook against the GitHub organization derived from `repository.owner.login` [1](#0-0) [2](#0-1) , but `StatusHandler#process` resolves which database rows to mutate using only `params.sha`, with no scoping to the repository/organization that was authenticated: [3](#0-2) .

### Finding Description
`commits` are indexed on `(stack_id, sha)`, not on `sha` alone, per `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`, confirming the same SHA-1 value is expected to legitimately exist across multiple distinct `Stack`/`Repository` rows in one Shipit instance. `StatusHandler#process` does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [3](#0-2) 

This query is global across every stack Shipit tracks — it is never filtered by the `repository` sub-object of the payload. Compare this with the base `Handler#stacks` helper, which *is* correctly scoped by `repository.full_name` [4](#0-3) ; `StatusHandler` bypasses that helper entirely.

Meanwhile, the only authentication performed before any handler runs is `WebhooksController#verify_signature`, which selects the `GitHubApp`/secret to check against using `repository_owner` (`repository.owner.login`, falling back to `organization.login`) [2](#0-1) , and verifies the HMAC using that organization's `webhook_secret` [5](#0-4) . The equality that should hold — "the organization whose secret validated this signature" == "the repository/commits whose data gets written" — is never enforced, because the actual write path (`Commit.where(sha:)`) has no notion of organization or repository at all.

Because SHA-1 git commit hashes are a deterministic function of tree, parents, author, committer, and timestamps (not of the destination repository), an attacker with ordinary, unprivileged push access to *any one* GitHub repository tracked by the same multi-tenant Shipit instance can:
1. Observe a target commit's SHA in a different, unrelated tracked repository (trivial for public repos, or for any repo whose commit history the attacker can otherwise see).
2. Reconstruct an identical commit (same tree, parents, author/committer identities and timestamps) in their own, legitimately-owned repository, producing the identical SHA-1.
3. Push it and let GitHub deliver a real, correctly-signed `status` webhook for their own organization/repository.
4. Shipit's `WebhooksController` validates the signature against the attacker's own organization successfully (as designed), then `StatusHandler` writes a `Status` for that SHA onto **every** commit in Shipit sharing that SHA — including the victim's commit in a completely different stack.

This effect propagates: `Commit#add_status` (via `create_status_from_github!`) calls `stack.schedule_merges` when the new status is `pending` or `success` [6](#0-5) , which enqueues `ProcessMergeRequestsJob`. That job checks `all_status_checks_passed?` and, if satisfied, calls `merge_request.merge!`, which performs a real GitHub merge using Shipit's own GitHub API credentials for the *victim* repository [7](#0-6) [8](#0-7) .

### Impact Explanation
An attacker who only controls one, unrelated, low-privilege repository/organization tracked by the same Shipit instance can forge CI success/status data for a commit belonging to an entirely different tenant's repository, and drive that tenant's merge queue to auto-merge a pull request using Shipit's own GitHub credentials. This is a cross-repository, cross-organization write and an unauthorized merge/deploy trigger — matching the report's Critical bar ("cross-repository writes, or an unauthorized deploy, rollback or merge"). The attacker never needs a Shipit session, `ApiClient` token, `webhook_secret` of the victim's organization, or any privileged account — only ordinary write access to a repository they legitimately control, which they use to obtain a validly-signed webhook for themselves.

### Likelihood Explanation
Requires the attacker to craft a colliding commit (feasible via GitHub's tree/commit APIs by copying tree, parent, author/committer, and timestamps — all public, non-secret metadata) and to know/target a specific SHA in the victim stack, which is typically public information. It also requires the victim stack to actually have merges pending in queue or blocking-status logic depending on that SHA. This raises the bar somewhat compared to a trivial exploit, but it requires no privileged credentials at all, only a legitimately owned, unprivileged GitHub repository — making it a realistic multi-tenant risk wherever one Shipit instance serves multiple orgs/repos.

### Recommendation
Scope every write path in webhook handlers (`StatusHandler`, and any other handler using bare `Commit.where(sha:)`, `CheckSuiteHandler`, etc.) to the repository identified in the payload, mirroring `Handler#stacks`/`Handler#repository_name`, e.g.:
```ruby
Commit.joins(:stack).merge(stacks).where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }
```
so that the organization/repository that produced a validly-signed webhook is provably the same organization/repository whose data gets mutated.

### Proof of Concept
1. Attacker controls (has push access to) `attacker-org/decoy-repo`, tracked as a Shipit stack, with a properly configured GitHub App and `webhook_secret`.
2. Attacker inspects `victim-org/victim-repo` (also tracked by the same Shipit instance) and picks a pending commit SHA `abc123...` that is awaiting CI/merge.
3. Attacker reconstructs an identical commit (same tree, parent, author, committer, timestamps) in `decoy-repo`, producing the same SHA `abc123...`, and pushes/tags it so GitHub fires a `status` event, e.g. via the Statuses API, with `state: success`, `sha: abc123...`.
4. GitHub signs and delivers this webhook using `attacker-org`'s real webhook secret; `WebhooksController#verify_signature` validates it successfully against `attacker-org`.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, which matches the commit in `victim-org/victim-repo` as well as the decoy commit, and creates a `success` `Status` on both.
6. `stack.schedule_merges` fires for the victim stack; `ProcessMergeRequestsJob` finds the corresponding pending PR's status checks now passing and calls `merge_request.merge!`, causing Shipit to merge the victim's PR using its own GitHub credentials — without any authorization from `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
