I have enough evidence to confirm the vulnerability chain: `StatusHandler#process` at [1](#0-0)  looks up commits purely `by sha` (globally, across all stacks/repos) with no repository/organization scoping, and calls `commit.create_status_from_github!(params)` which creates a `Status` that feeds directly into deployability and merge-queue gating logic such as `Commit#deployable?`, `Stack#allows_merges?`, and `MergeRequest#reject_unless_mergeable!` as shown in [2](#0-1) -style checks and `Stack#next_commit_to_deploy`/`deployable_commits` gating in [3](#0-2) .

### Title
Signature verification binds to the wrong organization, allowing cross-organization forgery of commit statuses that gate deploys and merges - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to check the HMAC signature against using `repository_owner`, a value taken from the same untrusted JSON body it is about to validate (`params.dig('repository','owner','login')` or `params.dig('organization','login')`). Once the signature check passes for that org, the entire raw payload — including a *different* field, `repository.full_name`, used by every webhook `Handler` to select the target `Repository`/`Commit`/`Stack` — is trusted and processed. In a Shipit instance configured with multiple GitHub Apps/organizations (a documented and supported configuration), these two fields are never cross-validated against each other.

### Finding Description
`verify_signature` derives the signing organization purely from attacker-controlled JSON content: [4](#0-3) 

Multiple GitHub Apps/organizations, each with its own independent `webhook_secret`, are a first-class supported configuration: [5](#0-4) [6](#0-5) 

Every webhook `Handler`, however, resolves the target repository/commit from a *separate* field, `repository.full_name` (or in `StatusHandler`'s case, a bare `sha` lookup with no repository scoping at all): [7](#0-6) [8](#0-7) 

Because the HMAC signature only proves "this exact byte sequence was signed with organization X's webhook_secret" — not "the `repository.full_name` embedded inside it actually belongs to organization X" — an actor who legitimately owns/administers one configured organization's GitHub App (and therefore knows that org's own `webhook_secret`, which they created and handed to the Shipit operator, per `docs/setup.md`'s "Using Multiple Github Applications" instructions) can freely craft a payload whose `repository.owner.login`/`organization.login` says "my org" (so it passes `verify_signature` against my own known secret) while `repository.full_name`/`sha` references any other tenant's repository or commit. This breaks the binding: *the organization whose secret authenticated the request* ≠ *the repository actually written to*.

The most damaging exploitation path is `StatusHandler`, which doesn't even use the (separately-signed) repository field — it looks up commits globally `Commit.where(sha: params.sha)` and writes an attacker-fully-controlled `state`/`context`/`description` `Status`: [1](#0-0) 

### Impact Explanation
Forged `Status` records feed directly into deploy-gating and merge-queue logic that other tenants rely on for safety: `Commit#deployable?`/required & blocking statuses (`README.md`'s `ci.require`/`ci.blocking`), `Stack#allows_merges?`, `MergeRequest#reject_unless_mergeable!`, and `Stack#next_commit_to_deploy`/continuous delivery. An attacker who only controls their own organization's GitHub App secret can inject a fake `"success"` status onto a specific commit SHA belonging to a completely different, unrelated organization's stack hosted on the same Shipit instance, unblocking that commit for automatic merge and/or continuous deployment — an unauthorized deploy/merge triggered from outside that organization's authentication boundary. This matches the report's high-severity theme (a calculation/authorization decision built from the wrong/unverified input) but manifests here as an authentication-binding confusion rather than an arithmetic error.

### Likelihood Explanation
Exploitability requires only that the Shipit deployment host more than one GitHub organization/App (an explicitly documented, supported configuration) and that the attacker administers (or otherwise knows the `webhook_secret` of) at least one of those configured orgs — which is the normal, expected level of trust/knowledge such an org owner has for their own App, without needing any access to other organizations, to `Shipit.github_teams`, or to any Shipit session/API token. No interaction with the victim organization is required; the attacker directly POSTs to `/webhooks` with a self-signed payload.

### Recommendation
Do not select the verification secret from attacker-supplied payload content. Instead:
1. Bind webhook signature verification to a fixed identity known independently of the payload (e.g. route-level per-org endpoint, or verify against *all* configured `webhook_secret`s and only accept if exactly one matches).
2. After verification, re-validate that the `organization`/`repository.owner.login` used to select the secret is the *same* organization that owns the `repository.full_name` (or `sha`'s owning stack) the handler is about to mutate — reject if they differ.
3. In `StatusHandler`, scope the `Commit.where(sha: params.sha)` lookup by the verified organization's repositories instead of searching globally across all stacks.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgA` and `OrgB`, each with its own GitHub App (`docs/setup.md` "Using Multiple Github Applications"). `OrgA`'s admin created their own App and therefore knows `OrgA`'s `webhook_secret`.
2. `OrgA`'s admin computes `sha1=HMAC(OrgA_webhook_secret, body)` for the following body, where `<victim_sha>` is a real commit SHA in `OrgB`'s stack that they want unblocked:
```json
{
  "sha": "<victim_sha>",
  "state": "success",
  "context": "ci/required-check",
  "organization": { "login": "OrgA" }
}
```
3. POST this body to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` computes `repository_owner` = `"OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check succeeds (it is genuinely signed with `OrgA`'s own secret).
5. `Shipit::Webhooks.for_event('status')` invokes `StatusHandler.call(params)`, which runs `Commit.where(sha: params.sha)` — matching the `OrgB` commit — and calls `create_status_from_github!`, creating a forged `"success"` status on `OrgB`'s commit, potentially unblocking it for merge/deploy in `OrgB`'s stack, despite the attacker never having authenticated as or been granted any access to `OrgB`.

      verified = github_app.verify_webhook_signature(

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
