### Title
CLStakingInfo Tracked Per RewardAddr Instead of Per (RewardAddr, NodeId) Pair Causes Silent CL Staking Amount Loss and Incorrect KAIA Reward Distribution — (`kaiax/staking/staking_info.go`)

---

### Summary

`consolidateNodes()` assigns each consolidated node's `CLStakingInfo` using `RewardAddr` as the sole map key. When two validators share the same `RewardAddr` (an explicitly supported AddressBook pattern) and both have registered in CLRegistry, the second `CLStakingInfo` silently overwrites the first. The lost CL staking amount is then excluded from every downstream reward calculation, causing incorrect KAIA distribution every block after the Prague hardfork.

---

### Finding Description

In `kaiax/staking/staking_info.go`, `consolidateNodes()` builds a `cmap` keyed by `RewardAddr`. The AddressBook explicitly allows multiple `NodeId`s to share one `RewardAddr` — that is the entire purpose of consolidation (see the struct comment at lines 68–85). After merging the AddressBook entries, the function iterates over `si.CLStakingInfos` and assigns each entry to the consolidated node via:

```go
// kaiax/staking/staking_info.go lines 152–158
for _, clsi := range si.CLStakingInfos {
    if r, ok := nToR[clsi.CLNodeId]; ok {
        // One CLStakingInfo per validator is guaranteed by CLRegistry.
        cmap[r].CLStakingInfo = clsi   // ← single-slot assignment, keyed only by RewardAddr
    }
}
```

`cmap[r]` is the consolidated node for `RewardAddr r`. If `N1` and `N2` both map to `r` (i.e., `nToR[N1] == nToR[N2] == r`) and both appear in `si.CLStakingInfos`, the loop first writes `cmap[r].CLStakingInfo = clsi_N1`, then immediately overwrites it with `cmap[r].CLStakingInfo = clsi_N2`. `clsi_N1`'s `CLStakingAmount` and `CLPoolAddr` are permanently lost for this block's reward computation.

The `consolidatedNode` struct confirms the single-slot design:

```go
// kaiax/staking/staking_info.go lines 86–93
type consolidatedNode struct {
    NodeIds          []common.Address
    StakingContracts []common.Address
    RewardAddr       common.Address
    StakingAmount    uint64
    CLStakingInfo *CLStakingInfo   // single pointer, not a slice
}
```

---

### Impact Explanation

Every block reward path that runs after the Prague hardfork reads `cn.CLStakingInfo` from the consolidated node:

**`assignStakingRewardsFlex`** (`kaiax/reward/impl/getter.go` lines 442–444):
```go
amount := cn.StakingAmount
if isPrague && cn.CLStakingInfo != nil {
    amount += cn.CLStakingInfo.CLStakingAmount   // only clsi_N2 counted; clsi_N1 dropped
}
```

**`assignStakingRewards`** (`kaiax/reward/impl/getter.go` lines 500–503):
```go
cnTotalStakingAmount := cn.StakingAmount
if isPrague && cn.CLStakingInfo != nil {
    cnTotalStakingAmount += cn.CLStakingInfo.CLStakingAmount  // same undercount
}
```

**`Split`** (`kaiax/staking/staking_info.go` lines 169–187) uses `cn.CLStakingInfo.CLStakingAmount` to split the reward between the CN reward address and the CL pool address. With `clsi_N1` gone, `clsi_N1.CLPoolAddr` receives zero KAIA for the block, and the total excess stake used to proportion rewards across all validators is understated, so every other validator receives a slightly inflated share.

The corrupted value is the per-block KAIA reward amount credited to `clsi_N1.CLPoolAddr` (zero instead of its correct proportional share) and the reward amounts credited to all other validators (inflated by the missing denominator contribution).

---

### Likelihood Explanation

The trigger requires two conditions that are both explicitly supported by the protocol:

1. **Two NodeIds share one RewardAddr in AddressBook.** The `consolidateNodes` doc comment and example (lines 68–83) show this is a first-class design feature, not an edge case.
2. **Both NodeIds register a CL pool in CLRegistry.** CLRegistry is keyed by `NodeId`, so each of the two NodeIds can independently register. No on-chain constraint prevents both from doing so.

No privileged action beyond normal validator operation is required. Any GC member operating two staking contracts under one reward address who also participates in consensus liquidity for both contracts will silently trigger this condition every block.

---

### Recommendation

Change `consolidatedNode.CLStakingInfo` from a single pointer to a slice, and accumulate all matching entries:

```go
// staking_info.go
type consolidatedNode struct {
    ...
    CLStakingInfos []*CLStakingInfo  // was: CLStakingInfo *CLStakingInfo
}

// in consolidateNodes():
if r, ok := nToR[clsi.CLNodeId]; ok {
    cmap[r].CLStakingInfos = append(cmap[r].CLStakingInfos, clsi)
}
```

Update `Split` and all reward functions to sum `CLStakingAmount` across the slice before computing proportions, and to distribute the CL portion to each `CLPoolAddr` individually.

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}
