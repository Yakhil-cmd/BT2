### Title
Deleting the protocol treasury account via a normal `DeleteAccount` action can crash validator/treasury reward distribution at epoch boundary - (File: `runtime/runtime/src/lib.rs`)

### Summary
The external report describes a fund-lock/DoS caused by an operator-controlled recipient address (`feeRecipient`) becoming invalid (zero address), which makes a downstream token transfer revert and permanently blocks reward distribution for unprivileged stakers. The closest reachable analog in nearcore is the `protocol_treasury_account`: it is an ordinary account (no special "cannot delete" protection like validators have), and any holder of that account's keys can submit a normal, unprivileged `DeleteAccount` transaction that removes it from state. If this happens, the epoch-boundary reward-distribution logic in `update_validator_accounts` (`runtime/runtime/src/lib.rs`) unconditionally expects the treasury account to exist and returns a `StorageError::StorageInconsistentState` if it does not.

### Finding Description
`update_validator_accounts` looks up the treasury account and treats its absence as an unrecoverable, "should never happen" invariant violation: [1](#0-0) 

```
if let Some(account_id) = &validator_accounts_update.protocol_treasury_account_id {
    if !validator_accounts_update.stake_info.contains_key(account_id) {
        let mut account = get_account(state_update, account_id)?.ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Protocol treasury account {} is not found",
                account_id
            ))
        })?;
        ...
```

Unlike validator accounts, which are protected from deletion while staking (`DeleteAccountStaking` error), the protocol treasury account has no equivalent protection in `action_delete_account`: [2](#0-1) 

A holder of the treasury account keys can therefore submit an ordinary `DeleteAccount { beneficiary_id }` transaction, an unprivileged action available to any account owner, exactly analogous to the vault-creator abusing his own privileged-but-unprotected configuration in the original report. Once the treasury account no longer exists, the very next epoch boundary triggers `update_validator_accounts` (called from chunk application, see `chain/chain/src/runtime/mod.rs`, which builds `ValidatorAccountsUpdate.protocol_treasury_account_id` from `genesis_config.protocol_treasury_account` every epoch start): [3](#0-2) 

This returns `Err(StorageError::StorageInconsistentState(...))` from `update_validator_accounts`, which propagates as a `RuntimeError`/`Error` out of chunk application. `StorageInconsistentState` in nearcore is reserved for state-corruption invariants that the runtime does not know how to recover from; it is not routed through the normal `ActionError`/`TxExecutionError` transaction-failure path that would simply fail one transaction. Practically this means the failure occurs outside of any single transaction's execution and blocks chunk application for the shard hosting the treasury account at every subsequent epoch boundary (rewards are dispensed at the start of every epoch, per `docs/RuntimeSpec/ApplyingChunk.md`): [4](#0-3) 

### Impact Explanation
If the treasury account is deleted, all subsequent epoch-boundary chunk applications on its shard fail with a fatal storage-inconsistency error instead of a benign, contained transaction failure. This blocks the runtime from completing epoch-transition processing (validator stake return, reward minting to validators, and treasury reward crediting all happen in the same function/state-update path), which can stall block/chunk production for the shard and, transitively, halt the chain. This is a strictly worse outcome than the original finding's per-user fund lock, because it is a protocol-level fatal condition rather than an isolated reverted transaction.

### Likelihood Explanation
Likelihood depends entirely on whether the treasury account's key holder ever issues a self-`DeleteAccount`. This is not something an attacker without the treasury keys can trigger; only the owner/operator of the treasury account (an "unprivileged" account from the runtime's perspective, but a special-purpose one) can send this transaction, and there is no explicit protocol-level protection preventing them from doing so, unlike for staking validators. Given the report's actor model (a vault/config owner who abuses their own configuration knob), this is a comparable actor: the treasury key holder abusing the fact that its account can be deleted like any other. I could not fully trace within this session whether the caller of `apply()` treats `RuntimeError` differently (e.g., as always fatal/panic) versus something more gracefully recoverable — this should be confirmed by inspecting all call sites of `apply_chunk`/`update_validator_accounts` error propagation before treating this as a confirmed crash path.

### Recommendation
- Add protocol-level protection preventing the protocol treasury account from being deleted via `DeleteAccount`, analogous to the `DeleteAccountStaking` check.
- Alternatively, make `update_validator_accounts` handle a missing treasury account gracefully (e.g., skip crediting reward, log, and continue) instead of returning a fatal `StorageInconsistentState` error, so an operator/owner action can never induce a chain-halting condition.

### Proof of Concept
1. At genesis, `protocol_treasury_account` is a normal account with a keypair controlled by its owner (`chain/epoch-manager/src/reward_calculator.rs` / `core/chain-configs/src/test_genesis.rs` show it is just a configured `AccountId`, no special deletion guard). [5](#0-4) 
2. The treasury-account owner submits `SignedTransaction { actions: [DeleteAccount { beneficiary_id: <any account> }] }` signed with the treasury account's own key — an ordinary, unprivileged self-delete, matching the pattern already exercised in `runtime/runtime/src/actions.rs` tests (`test_delete_account_over_limit_leaves_account_unchanged`) and `integration-tests/src/tests/features/delegate_action.rs::meta_tx_delete_account`.
3. At the next epoch boundary, `chain/chain/src/runtime/mod.rs` builds a `ValidatorAccountsUpdate` with `protocol_treasury_account_id = Some(self.genesis_config.protocol_treasury_account.clone())`. [3](#0-2) 
4. `update_validator_accounts` calls `get_account(state_update, account_id)?.ok_or_else(...)` on the now-nonexistent account and returns `Err(StorageError::StorageInconsistentState(...))`, aborting normal chunk-apply processing for that shard. [1](#0-0)

    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }

        return Ok(());
    }

    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {

            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,

        .into());
        return Ok(());
