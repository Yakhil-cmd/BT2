### Title
Webhook Signature Verification Uses Attacker-Controlled Organization Selection, Allowing Unsigned Forged `membership` Events to Escalate Into `Shipit.github_teams` Authorization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The `/webhooks` endpoint selects which organization's `webhook_secret` to verify a request against using fields taken directly from the unauthenticated request body, and `GitHubApp#verify_webhook_signature` trivially returns `true` when that organization has no configured `webhook_secret`. Combined with `MembershipHandler` not tying the `team` it mutates to the organization that (allegedly) authenticated the request, an attacker with no Shipit credentials can forge a `membership` webhook that adds an arbitrary GitHub login to any `Team` tracked by Shipit, including a team listed in `Shipit.github_teams` — the authorization gate for the entire application.

### Finding Description
`WebhooksController#verify_signature` picks the signing key like this: [1](#0-0) 

`repository_owner` is read straight from the JSON body, before any cryptographic check occurs: [2](#0-1) 

`GitHubApp#verify_webhook_signature` unconditionally accepts the request when the selected organization's secret is blank: [3](#0-2) 

Shipit explicitly supports (and templates/docs generate) organizations configured with `webhook_secret: nil`: [4](#0-3) [5](#0-4) 

Because `Shipit.github(organization:)` looks the config up per-organization key from `secrets.github` (multi-org support), and because the org name used to pick that config comes from the attacker-supplied body, an attacker can freely choose *any* configured organization key that has a blank secret to make `verify_signature` pass unconditionally, regardless of the `X-Hub-Signature` header contents: [6](#0-5) 

Once past `verify_signature`, the `membership` event is dispatched to `MembershipHandler`, which resolves the `Team` purely by the payload's `team.id` and does not check that `params.organization.login` corresponds to the organization that was (or wasn't) actually verified, nor that the requester has any relationship to that team's real organization: [7](#0-6) 

`Team` membership feeds directly into the application-wide authorization boundary: [8](#0-7) [9](#0-8) 

**The broken binding, stated as an equality that fails:**
`organization whose webhook_secret cryptographically authenticated this delivery` ≠ `organization/team that the `membership` payload claims to modify and that `MembershipHandler` actually mutates`.

Before the attack: only genuine GitHub webhook deliveries (signed with the correct org secret) can add/remove `Membership` rows for a `Team`.
After the attack: any unauthenticated POST to `/webhooks` naming an organization with a blank `webhook_secret` (a supported, documented default) is treated as verified, and the `team.id` it operates on is not required to belong to that (or any) verified organization — so the attacker's own GitHub login can be inserted as a member of a privileged team.

### Impact Explanation
This escalates into `Shipit.github_teams` authorization exactly as listed in scope's High-impact criteria: once an attacker-controlled GitHub login is added as a member of a `Team` referenced by `Shipit.github_teams` (via `oauth.teams`), that attacker can complete the normal GitHub OAuth login flow (`GithubAuthenticationController#callback`) and `current_user.authorized?` will return `true`, granting them full authenticated access to the Shipit UI/API — including triggering deploys, rollbacks, and stack management — without ever needing a Shipit session, an `ApiClient` token, or the GitHub App's private key.

### Likelihood Explanation
Likelihood is high for any Shipit deployment that (a) has any organization configured without a `webhook_secret` — which is the default in the generated `secrets.yml`/`secrets.example.yml` templates and explicitly documented as optional — or (b) runs multiple organizations where at least one has no secret. The `/webhooks` endpoint is unauthenticated by design (it must accept GitHub deliveries), so the only barrier is the signature check that this flaw bypasses.

### Recommendation
- Do not derive the verification key from unauthenticated body content combined with a "verification trivially succeeds on blank secret" fallback. Require a non-blank `webhook_secret` for every configured organization, or fail closed (reject) instead of returning `true` when no secret is configured for GitHub Apps that receive privileged event types like `membership`.
- In `MembershipHandler` (and other org-scoped handlers), verify that `params.organization.login` matches the organization actually used to verify the signature (pass the verified organization down into the handler context) before mutating `Team`/`Membership` records.
- Consider treating `membership` events specially: only trust them for teams whose `organization` matches a securely configured GitHub App with a mandatory webhook secret.

### Proof of Concept
Given a Shipit deployment configured with (at minimum) one organization `orgB` that has `webhook_secret: nil` (default/documented configuration) and a `Team` record whose `github_id` matches a team referenced by `Shipit.github_teams` for a *different*, properly secured organization:

```
POST /webhooks HTTP/1.1
Host: shipit.example.com
Content-Type: application/json
X-Github-Event: membership
X-Hub-Signature: sha1=0000000000000000000000000000000000000000

{
  "action": "added",
  "organization": { "login": "orgB" },
  "team": { "id": <privileged_team_github_id>, "name": "Developers", "slug": "developers", "url": "https://api.github.com/teams/1" },
  "member": { "login": "attacker-controlled-real-github-login" },
  "repository": { "owner": { "login": "orgB" } }
}
```

- `verify_signature` selects `Shipit.github(organization: "orgB")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature` header.
- `MembershipHandler#process` runs unimpeded, resolving/creating the `Team` by `team.id` (the privileged team) and calling `team.add_member(member)`, adding the attacker's real GitHub account as a member.
- The attacker then logs into Shipit via the normal `/github/auth/github` OAuth flow with that GitHub account; `User#authorized?` returns `true` because the user is now a member of a team in `Shipit.github_teams`, granting full authenticated access to the application.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
