### Title
`Api::CCMenuController#stack` bypasses stack-scoped ApiClient authorization, allowing cross-stack read - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` scopes stack lookup to the authenticated `ApiClient`'s `stack_id` via the `stacks` method, but `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, skipping that scope entirely. A token issued for one stack can therefore be used to read CCTray/CCMenu status (deploy state, build label) of any other stack.

### Finding Description
The intended binding is: for any API request authenticated by an `ApiClient` with `stack_id` set, the touched stack must satisfy `stack ∈ Stack.where(id: current_api_client.stack_id)`. This is implemented in `app/controllers/shipit/api/base_controller.rb`: [1](#0-0) 

`stacks` filters by `current_api_client.stack_id` when present, and `#stack` resolves through that scoped relation. `CCMenuController` inherits from `BaseController` but redefines `#stack` to bypass `stacks` entirely: [2](#0-1) 

`check_permissions!` in `ApiClient` only validates that the required permission string (e.g. `read:stack`) is present in the `permissions` array — it never checks `stack_id`: [3](#0-2) 

So the only place stack-scoping is enforced is the `stacks` method, and `CCMenuController#stack` never calls it. Attack flow: an operator issues an `ApiClient` scoped to stack A with `read:stack` permission (a legitimate, intended-to-be-restricted token). The attacker, holding that token (e.g. as a collaborator on stack A who was given this scoped token), sends `GET /api/:stack_id/ccmenu.xml` with `stack_id` = stack B's identifier and `token=<stack-A token>`. `authenticate_api_client` in `CCMenuController` succeeds via `ApiClient.authenticate(params[:token])`, then `show` calls `stack`, which resolves stack B unconditionally through `Stack.from_param!`. The response renders stack B's deploy status and build label, an unauthorized cross-stack read.

### Impact Explanation
This is an unauthenticated-for-that-resource read of another tenant's stack state (deploy status, running/succeeded state, build label) — matching the High severity category "unauthenticated read of stack state, task streams or deploy output" since the token holder is not authorized for stack B at all. It is fully repeatable against any stack in the installation merely by varying `stack_id` in the URL, using a single legitimately-issued, narrowly-scoped token. The blast radius spans all stacks hosted by the Shipit instance, not just the one the token was scoped to.

### Likelihood Explanation
Preconditions are minimal and realistic: an operator issuing per-stack API tokens (a documented, supported feature via `ApiClient` with `stack_id`) is standard practice for restricting third-party integrations (e.g. CI dashboards) to one stack. Any holder of such a token — who is by design *not* supposed to have access to other stacks — can trivially exploit this by changing one URL segment. No secrets, sessions, or elevated privileges are needed beyond the token itself, which is exactly the credential this scoping mechanism is meant to constrain.

### Recommendation
Remove the override in `Shipit::Api::CCMenuController` (or reimplement it to use the inherited scoped lookup), e.g. delete the private `stack` method from `app/controllers/shipit/api/ccmenu_controller.rb` so it inherits `BaseController#stack`, which resolves via `stacks.from_param!(params[:stack_id])`.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (existing test file):
```ruby
test "cannot read another stack's status with a stack-scoped token" do
  stack_a = shipit_stacks(:shipit)
  stack_b = shipit_stacks(:cocaine) # a different stack
  client = ApiClient.create!(
    creator: shipit_users(:walrus),
    name: 'scoped-client',
    stack: stack_a,
    permissions: %w[read:stack],
  )

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  # Binding under test: stack_b must NOT be in Stack.where(id: client.stack_id)
  assert_not Stack.where(id: client.stack_id).exists?(id: stack_b.id)
  # But the controller currently returns it anyway:
  assert_response :ok
  assert_includes response.body, stack_b.to_param # leaks stack B data via a stack-A token
end
```
This demonstrates that `Stack.where(id: current_api_client.stack_id)` (the intended scope) excludes stack B, yet `CCMenuController#stack` still resolves and returns stack B's data, proving the divergence.
