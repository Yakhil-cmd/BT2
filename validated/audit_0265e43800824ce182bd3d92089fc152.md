### Title
Webhook signature bound to `repository.owner.login`, not to `repository.full_name` used by handlers, allowing cross-repository forgery when multiple GitHub Apps/organizations are configured - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the HMAC secret to check by reading `repository.owner.login` (falling back to `organization.login`) out of the untrusted JSON body, then verifies the *entire* raw body against that org's `webhook_secret`. Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#stacks` looks up the target `Stack` using an entirely different field from the same body — `repository.full_name` — with no cross-check that this repository actually belongs to the organization whose secret validated the request.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

Signature verification is only *cryptographically sound with respect to the secret used*; it does not enforce which repository/stack the payload is permitted to act on — HMAC-SHA1 over the raw body only proves "this body was signed by the holder of org X's webhook secret," not "this body's repository field belongs to org X." Shipit deliberately supports multiple GitHub Apps/organizations, each with its own `webhook_secret` (`lib/shipit.rb#github_app_config`, `docs/setup.md` "Using Multiple Github Applications"). Each org's webhook secret is a distinct, independently-held credential — an org admin of OrgA has no expectation of trust over data destined for OrgB.

Every actual side effect, however, is dispatched based on `repository.full_name`, read by `Handler#repository_name`/`#stacks`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every stack matching that `full_name`: [3](#0-2) 
and `StatusHandler#process` writes a commit status for any commit matching `params.sha` regardless of which stack/org it belongs to: [4](#0-3) 

This is structurally identical to the reported bug class: the "index" that is checked (`repository.owner.login` against the HMAC) is not the "index" that is actually dereferenced (`repository.full_name` against the `Stack`/`Commit` records) — exactly like `JumpyFallback.Info.tree` being sized for the checked index but read at a different, unchecked index. Here, the binding that should hold is:
```
organization whose secret verified the signature == organization owning the repository the handlers act on
```
No code enforces this equality.

### Impact Explanation
In a single-org deployment (the common case) this is not exploitable because there is only one webhook secret and `Repository.from_github_repo_name` is scoped to repositories already registered under that org. But per the engine's own documented multi-tenant configuration (`docs/setup.md`, `lib/shipit.rb#github_app_config`, `test/dummy/config/secrets_double_github_app.yml`), a single Shipit instance can host several independent organizations, each with a different GitHub App and a different `webhook_secret`. In that configuration, anyone who can produce a validly-signed webhook for *any one* of the configured organizations (e.g. an admin of that org's GitHub App, or anyone who can trigger real GitHub events for that org — which is by design a much weaker trust level than "can write to every other org hosted on this Shipit instance") can set `repository.full_name`, `sha`, `ref`/`after`, `state`, `target_url`, etc. to target a `Stack`/`Repository`/`Commit` belonging to a *different, unrelated organization* also hosted on the same instance. This lets that party:
- Forge commit statuses (`StatusHandler`) on another org's commits, which feeds directly into `MergeRequest#all_status_checks_passed?` / `reject_unless_mergeable!`, potentially causing an unauthorized merge or unblocking an otherwise-blocked deploy for a repository they do not own — matching the "unauthorized deploy, rollback, or merge" Critical impact category.
- Trigger `GithubSyncJob`/deploy-spec resync (`PushHandler`) against another organization's stack.

### Likelihood Explanation
Requires a multi-organization Shipit deployment (explicitly documented and supported) and requires the attacker to control one organization's GitHub App webhook secret/events but not the target organization's. This is a realistic operating model for a shared Shipit instance serving multiple, mutually-untrusting teams/orgs — the whole point of per-org `webhook_secret` isolation is to prevent one org from affecting another's stacks, and that isolation is bypassed because the field validated by the signature and the field acted upon are different.

### Recommendation
After signature verification succeeds, verify that `repository.full_name`'s owner matches the `repository_owner`/`organization` value that selected the verifying secret (i.e., assert `repository.full_name.split('/').first == repository_owner`, case-insensitively) before dispatching to any handler. Alternatively, scope `Repository.from_github_repo_name` lookups (and all handler-side effects) to repositories belonging to the organization that was authenticated, rather than trusting `full_name` unconditionally.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` (webhook_secret `secretA`) and `OrgB` (webhook_secret `secretB`), each hosting stacks for their own repos:

1. Attacker (an OrgA GitHub App admin, or anyone able to produce a validly HMAC-signed OrgA webhook) crafts:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/target-repo" },
  "sha": "<commit sha belonging to OrgB/target-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
2. Computes `X-Hub-Signature: sha1=<hmac-sha1(secretA, body)>` and sends it with `X-Github-Event: status`.
3. `verify_signature` reads `repository.owner.login == "OrgA"`, looks up `Shipit.github(organization: "OrgA")`, and successfully verifies the signature against `secretA`.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching a commit that belongs to `OrgB/target-repo` — and creates a forged "success" status on it, even though the request was never signed by OrgB's secret.
