### Title
Unprivileged parameter restamping / governance execution can front-run `liquidate`, shrinking the bonus a liquidator was quoted - (File: contracts/controller/src/risk/params.rs)

### Summary
`liquidate` computes the seized collateral from (a) the per-position stored liquidation tuple (`liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`) and (b) the spoke-level liquidation curve (`liquidation_target_hf_wad`, `hf_for_max_bonus_wad`, `liquidation_bonus_factor_bps`), which is read live from spoke config on every call. Neither is pinned by the liquidator, and `liquidate` takes no "expected bonus / minimum seized" argument. Two unprivileged paths can worsen these parameters between a liquidator's simulation and execution: (1) any third party may supply dust to an existing supply leg of a victim account, which unconditionally restamps a *worse* liquidation tuple at any health factor, and (2) anyone may execute a ready governance `SetSpokeLiquidationCurve` operation, which instantly rewrites the live bonus curve for the entire spoke. The front-runner can therefore make the liquidator repay debt while seizing less collateral than `get_liquidation_estimate` quoted.

### Finding Description
Each supply position snapshots the listing's liquidation tuple when created, and `apply_gated_liquidation_params` in `contracts/controller/src/risk/params.rs:68-93` refreshes it. The HF >= 1.05 gate (`clears_min_hf`, `THRESHOLD_UPDATE_MIN_HF_RAW`) only applies when the new tuple *favors* the liquidator (`favors_liquidator`, params.rs:96-100: lower LT, higher bonus, or lower fee). A governance `editAssetInSpoke` that lowers `liquidation_bonus` or raises `liquidation_fees` is *not* gated: `apply_gated_liquidation_params` writes the worse tuple unconditionally, at any account health factor, and the supply path never checks post-refresh HF.

The refresh is reachable by anyone. `process_supply` (`contracts/controller/src/positions/supply.rs:40`) permits a third party to top up an already-existing supply leg of any account — `require_third_party_existing_supply` (supply.rs:78-97) only asserts the leg exists. `merge_supply_leg` (supply.rs:275-296) then calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, restamping the tuple. So a dust supply to the victim's collateral leg applies any newly-listed worse bonus/fee immediately.

Separately, the bonus curve is never snapshotted: `LiquidationCurve::from_config` (`contracts/controller/src/positions/liquidation/curve.rs:36-41`) reads `SpokeConfig` fields that `set_spoke_liquidation_curve` (`contracts/controller/src/config/spoke.rs:52-70`) mutates via the `SetSpokeLiquidationCurve` governance op. Executing a matured operation is permissionless, so a front-runner can trigger a queued curve change (e.g., raising `hf_for_max_bonus_wad` or lowering `liquidation_bonus_factor_bps`) inside the same ledger sequence as a pending `liquidate`.

Because `estimate_liquidation_amount` (curve.rs:102-137) derives the bonus at execution time, a liquidator that simulated `get_liquidation_estimate` and signed transfer authorizations for the quoted amounts has no way to bound the bonus actually applied — there is no `min_bonus`/`max_seized` parameter on `liquidate`.

### Impact Explanation
The liquidator's signed payment is pulled per its authorization while the seized amount is recomputed with the degraded parameters. A lowered `liquidation_bonus` or worse curve directly reduces the collateral seized for the same repayment, turning a profitable liquidation into a loss of real token value — theft of user funds bounded by the governance-applied parameter delta. With a deeper change (e.g., bonus factor cut toward zero on a spoke), nearly the whole expected bonus can be stripped from in-flight liquidations across every account in the spoke in a single transaction.

### Likelihood Explanation
The attack needs a governance change that worsens liquidation terms to be executable — either a matured `EditAssetInSpoke` (bonus/fee) or `SetSpokeLiquidationCurve`. Such operations are routine administrative actions (the docs describe exactly the "lower the base bonus" listing change as a contemplated option), and their execution is permissionless, so a bot can watch for a ready op plus pending `liquidate` transactions and sandwich them: `execute` (if needed) + dust `supply` to the target leg in the same transaction bundle. Cost is only a dust deposit, which is credited back as supply shares. No privileged role or timing assumption beyond the existence of a queued config change is required. This makes it a conditional but realistic Medium rather than a hypothetical.

### Recommendation
- Let the liquidator pin expected terms: add a `min_bonus_bps` (or expected `SpokeConfig`/`AssetConfig` tuple) argument to `liquidate` and revert if the effective bonus would be lower — the same fix the source report recommends.
- Alternatively, apply the HF gate symmetrically: in `apply_gated_liquidation_params`, also defer restamps that *worsen* the tuple for indebted accounts near liquidation (e.g., only apply when post-update HF >= `THRESHOLD_UPDATE_MIN_HF_RAW`), mirroring how liquidation itself never restamps (`leg_may_restamp_risk_params` excludes `WithdrawKind::Liquidation`, supply.rs:379-391).
- Snapshot the liquidation curve per position (or per liquidation plan) instead of reading `SpokeConfig` live, so `SetSpokeLiquidationCurve` cannot retroactively alter in-flight quotes.

### Proof of Concept
1. Governance schedules `EditAssetInSpoke` lowering `liquidation_bonus` for market M (or `SetSpokeLiquidationCurve` lowering `liquidation_bonus_factor_bps` for the spoke); the delay matures.
2. Liquidator simulates `get_liquidation_estimate` for victim account A, sees bonus B0, signs `transfer` authorizations and submits `liquidate`.
3. Attacker (any address) submits in one bundle before it: `governance.execute(op_id)` if not yet executed, then `controller.supply(account_id = A, assets = [(M.hub_asset, dust)])`. `require_third_party_existing_supply` passes since A's leg exists; `merge_supply_leg` → `refresh_supply_risk_params(FullTuple)` → `apply_gated_liquidation_params` writes the lower bonus unconditionally (worsening changes bypass `clears_min_hf`).
4. `liquidate` executes: `estimate_liquidation_amount` uses the restamped `liquidation_bonus` (and/or new curve), so A's seized legs pay the liquidator `R * (1 + B1)` with `B1 < B0` while pulling the authorized repayment — the liquidator realizes less collateral than quoted, the difference accruing to the borrower's residual position.
