### Title
Scoped `ApiClient` Stack Authorization Bypass in CCMenu Endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides the `stack` accessor to resolve directly against the unscoped `Stack` model instead of the tenant-scoped relation used everywhere else in the API, allowing an `ApiClient` token that is authorized for exactly one stack to read the CI status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the binding between a token's authorization and the stacks it may touch: [1](#0-0) 

`stacks` is scoped to `current_api_client.stack_id` when the client is bound to a single stack, and `stack` (used by every other API controller, e.g. `DeploysController`, `TasksController`) resolves `params[:stack_id]` only within that scoped relation. Permission checks such as `require_permission :read, :stack` only verify the operation/scope string via `ApiClient#check_permissions!`: [2](#0-1) 

They never verify which specific stack the request targets — that job is delegated entirely to `BaseController#stack`/`#stacks`.

`Api::CCMenuController`, however, redefines `stack` to bypass this scoping entirely: [3](#0-2) 

It calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` model, rather than `stacks.from_param!(...)`. Because `require_permission :read, :stack` only checks that the token has the `read:stack` permission string (not that it is entitled to *this* stack), any `ApiClient` with `read:stack` permission — including one deliberately scoped to a single stack via `ApiClient#stack_id` — can supply an arbitrary `stack_id` and receive that other stack's build/CI status.

This is exactly the "stack a token authorizes vs. stack it touches" binding: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all` (the authorized side) versus `Stack.from_param!(params[:stack_id])` (the touched side) in `CCMenuController#stack`.

### Impact Explanation
This grants an unauthenticated-relative-to-other-stacks read of stack state: an `ApiClient` legitimately provisioned and scoped to a single stack (e.g. via `CCMenuUrlController#client`, which creates clients scoped with `permissions: %w[read:stack]` and tied to one stack) can read build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, `webUrl`, etc., as rendered in `app/views/shipit/ccmenu/project...`) for every other stack managed by the Shipit instance, not just the one it was authorized for. This matches the High-severity category "unauthenticated read of stack state, task streams or deploy output" per the given impact criteria, since the scoping guarantee that other controllers enforce is broken specifically in this endpoint.

### Likelihood Explanation
Any holder of a stack-scoped `ApiClient` token (a normal, low-privilege credential type intentionally issued to give narrow read access to one stack, e.g. via the CCMenu integration flow) can trivially exploit this by changing the `stack_id` route/query parameter on a GET request — no additional secrets, elevated roles, or session are required beyond the token they already legitimately hold.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve through the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` on the unscoped model, so that stack-scoped clients cannot access stacks outside their authorized scope.

### Proof of Concept
1. As an authorized Shipit user, use `CCMenuUrlController#fetch` (or the "Create CI status URL" UI flow) to provision an `ApiClient` scoped to Stack A: `ApiClient.create!(permissions: %w[read:stack], stack: stack_a, creator: user)`, and obtain its `authentication_token`.
2. Call `GET /api/ccmenu/:stack_id_of_B?token=<token-scoped-to-A>` (or via `Authorization: Basic` with the token), substituting Stack B's `stack_id` instead of Stack A's.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` directly (bypassing the `current_api_client.stack_id` scoping), the request succeeds and returns Stack B's build status/CI XML, despite the token only being authorized for Stack A.
