### Title
Webhook Signature Verification Uses Query-String-Controlled Organization Lookup Instead of the Signed Request Body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to verify a webhook against using `repository_owner`, which is read from the Rails-merged `params` hash. `params` in Rails combines query-string parameters with the parsed request body, and for identical top-level keys the query string overrides the body-derived value. The actual HMAC check, however, is performed over `request.raw_post` — the untouched signed body — and the subsequent `create` action re-parses `request.raw_post` independently to dispatch webhook handlers. This decouples "which organization's secret is used to verify the signature" from "what payload is actually verified and processed," exactly mirroring the reported bug class: a value used for validation (`assetReceiptAddresses.length` / here, `repository_owner`) is not bound to the value that is actually acted upon (`notionalReceived` / here, the signed `raw_post` content processed by handlers).

### Finding Description
`verify_signature` resolves the GitHub App/secret like this: [1](#0-0) [2](#0-1) 

`repository_owner` is derived from `params`, not from the raw signed body: [3](#0-2) 

In a Rails controller, `params` is the union of query-string parameters and parsed body parameters; for the same top-level key, the query-string value takes precedence over the body value (shallow merge, not a deep merge). This means an attacker can freely control `repository_owner` via the URL query string (e.g. `/webhooks?repository[owner][login]=SomeOrg`) independent of what is actually inside the HMAC-signed JSON body.

`Shipit.github(organization:)` looks up per-organization config, and `GitHubApp#verify_webhook_signature` treats a missing `webhook_secret` as automatically valid: [4](#0-3) [5](#0-4) 

Multi-organization deployments are an explicitly documented and supported configuration shape, and `webhook_secret` is documented/shown as optional per organization: [6](#0-5) [7](#0-6) 

Meanwhile, the actual webhook body that drives handler dispatch is taken straight from `request.raw_post`, completely independent from the (attacker-influenced) `params` used for org/secret selection: [8](#0-7) 

**Equality broken:** `organization used to select the verification secret (params, query-string controllable)` != `organization/repository whose signed content is actually processed (request.raw_post, the truly signed payload)`.

### Impact Explanation
If a Shipit deployment is configured with multiple GitHub organizations (a documented, supported configuration) and any one of them has no `webhook_secret` configured (also documented as valid/optional), an attacker can:
1. Send a POST to `/webhooks` with query string `?repository[owner][login]=<org-without-secret>` (or `?organization[login]=<org-without-secret>`).
2. Include any crafted JSON body (no valid signature required) naming a victim repository/stack managed by the *other*, properly-secured organization.
3. `verify_signature` resolves `repository_owner` to the attacker-chosen, secret-less organization, and `verify_webhook_signature` returns `true` unconditionally (`return true unless webhook_secret`), completely bypassing signature verification.
4. `create` then re-parses the real `raw_post` body and dispatches it to `Shipit::Webhooks.for_event(event)` handlers as if it were a legitimate, verified GitHub webhook for the victim's repository/stack.

This allows unauthenticated forgery of GitHub webhook events (`push`, `status`, `check_suite`, `membership`, etc.) against any stack/repository the Shipit instance manages, without repository write access or any secret — an authentication bypass on a security-critical trust boundary (the webhook signature is the only control preventing arbitrary unauthenticated event injection). Depending on which handlers are wired up, this can affect deploy safety checks (forged CI status), or `Shipit::Membership`/`Shipit::Team` state (forged `membership` events add/remove users from teams used by `Shipit.github_teams` authorization), which crosses into the "escalation into `Shipit.github_teams` authorization" High-impact category.

### Likelihood Explanation
Requires no credentials, no session, no `ApiClient` token, and no repository write access — only network access to the public `/webhooks` endpoint and knowledge that the multi-org "Using Multiple Github Applications" feature is enabled with at least one organization lacking a `webhook_secret` (both explicitly documented, supported configurations). Single-organization deployments (where `github_default_organization` is `nil`) are not affected, since in that mode `repository_owner` is ignored entirely and `secrets.github` config is used directly.

### Recommendation
- Derive `repository_owner` for signature-key selection from the parsed `request.raw_post` body exclusively (the same bytes that are HMAC-verified), never from `ActionController::Parameters`/query string.
- Reject requests where the org-selection value used for verification differs from what is present in the verified raw body.
- Consider requiring `webhook_secret` to be present for every configured organization in multi-org mode, so a missing secret can never silently short-circuit verification.

### Proof of Concept
Given a multi-org `secrets.yml` such as:
```yaml
github:
  SecureOrg:
    webhook_secret: real-secret
  LeakyOrg:
    webhook_secret: # nil, intentionally unset in some environments
```

An attacker sends:
```
POST /webhooks?repository[owner][login]=LeakyOrg HTTP/1.1
X-Github-Event: push
Content-Type: application/json
(no valid X-Hub-Signature required)

{"repository":{"owner":{"login":"SecureOrg"},"full_name":"SecureOrg/victim-repo"}, ...forged push payload...}
```
`repository_owner` resolves to `"LeakyOrg"` from the query string (overriding the body's `"SecureOrg"`), `Shipit.github(organization: "LeakyOrg")` returns a `GitHubApp` with `webhook_secret` blank, so `verify_webhook_signature` returns `true` unconditionally. `create` then processes the forged body (naming `SecureOrg/victim-repo`) as a legitimate, verified webhook.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
