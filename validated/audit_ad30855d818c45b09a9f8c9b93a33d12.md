### Title
Stack-scoped ApiClient token authorizes any stack in `Api::CCMenuController` - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Api::BaseController` enforces that an `ApiClient` scoped to a single stack (`ApiClient#stack_id`) may only access that stack, by resolving the target stack through `stacks.from_param!` where `stacks` is filtered to `Stack.where(id: current_api_client.stack_id)` when the client is scoped. `Api::CCMenuController` overrides `stack` with a direct, unscoped lookup (`Stack.from_param!(params[:stack_id])`), breaking that binding and letting a stack-scoped token read the CI/build status of any stack.

### Finding Description
`Api::BaseController` defines the authorization-scoping logic used by every other API controller (`Api::StacksController`, `Api::TasksController`, `Api::DeploysController`, `Api::HooksController`, etc.): [1](#0-0) 

`stacks` restricts the resolvable set of stacks to `current_api_client.stack_id` when the client is scoped, and `stack` resolves `params[:stack_id]`/`params[:id]` only within that restricted set. This is the binding: `token.authorized_stack == stack.acted_on`.

`Api::CCMenuController`, however, re-defines `stack` to bypass this entirely: [2](#0-1) 

It calls `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, never consulting `current_api_client.stack_id`. `require_permission :read, :stack` only checks that the permission string `"read:stack"` is present in the token's `permissions` array — it does not check which stack the permission applies to: [3](#0-2) 

Fixtures confirm real tokens are scoped to a single stack this way (`stack: shipit`) and a dedicated test enforces that scoping for other endpoints ("an api client scoped to a stack will only see that one stack"): [4](#0-3) [5](#0-4) 

So the equality that must hold — "the stack a token authorizes equals the stack it touches" — holds for `StacksController#stack`/`TasksController`/etc. (via the inherited `BaseController#stack`), but does **not** hold for `Api::CCMenuController#stack`, since it ignores `current_api_client.stack_id`.

Before the attacker's action: a stack-scoped `ApiClient` token (`stack_id = Stack A`, `permissions = ["read:stack"]`) can only fetch data for Stack A via `Api::StacksController#show`, `Api::TasksController#index`, etc. — enforced by `BaseController#stack`. After: the same token, sent to `GET /api/stacks/:stack_id/ccmenu` with `stack_id` set to an arbitrary Stack B, succeeds because `Api::CCMenuController#stack` resolves `Stack.from_param!` unscoped, and `require_permission :read, :stack` is satisfied since the permission check is stack-agnostic.

### Impact Explanation
This allows an attacker holding a legitimately-issued but narrowly-scoped `ApiClient` token (e.g., one meant for a single stack/CI dashboard integration, exposed by design via a URL query string as generated by `CCMenuUrlController#fetch`) to read the build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `activity`, lock state) of any other stack in the Shipit instance, including stacks belonging to different repositories or teams that the token holder was never authorized to see. This is an unauthenticated-for-that-resource read of stack state via a token whose authorization was scoped elsewhere, matching the "High" impact bucket (escalation into unauthorized read of stack state via a scoped token).

### Likelihood Explanation
Likelihood is high for any deployment using stack-scoped API tokens (a documented, supported feature — see the `here_come_the_walrus` fixture and `ApiClient#stack_id`). Any holder of such a token (which can leak via logs, browser history, or the CCMenu URL feature itself, which embeds the token in a plain query string) can trivially exploit this by changing the `stack_id` path segment in the request URL — no additional credentials, signature forgery, or privileged access is required beyond the already-issued limited-scope token.

### Recommendation
Remove `Api::CCMenuController`'s custom `stack` override and rely on the inherited `BaseController#stack`/`stacks` methods so the client's `stack_id` scope is enforced identically to every other API controller. If a custom lookup is required (e.g., to support the `token` query-string path), it must still filter through `current_api_client.stack_id` before calling `Stack.from_param!`.

### Proof of Concept
1. Create (or obtain) a stack-scoped `ApiClient` token authorized only for Stack A: `ApiClient.create!(creator: user, name: 'x', stack: stack_a, permissions: ['read:stack'])`, and note `client.authentication_token`.
2. As an attacker who has this token (e.g., leaked via a CCMenu URL, which embeds the token as `?token=...`), send:
   `GET /api/stacks/<stack_b_full_name>/ccmenu` using Basic Auth with the token as username (empty password), where `stack_b` is a different, unauthorized stack.
3. Observe the response returns HTTP 200 with `stack_b`'s CI/build status (`lastBuildStatus`, `activity`, etc.), even though the token's `stack_id` corresponds only to Stack A — confirming the scoping bypass in `Api::CCMenuController#stack`.
