### Title
Webhook signature verification is keyed off an unverified payload field while write targets are keyed off a different unverified payload field, enabling cross-organization/cross-repository stack mutation - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`Space.sol`'s report is about unchecked arithmetic breaking an implicit safety invariant. The reachable analog in this Ruby engine is a similar "implicit binding that isn't actually enforced": the field used to select *which* organization's secret authenticates the request is not the same field used to decide *which* repository/stack the request is allowed to mutate, and neither is cryptographically tied to the other.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization whose `webhook_secret` will be used to validate the inbound HMAC based on a field taken directly from the **unverified** JSON body: [1](#0-0) [2](#0-1) 

`repository_owner` is computed via `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` — both attacker-suppliable JSON fields, read before any signature has been checked.

Once (or if) verification passes, the actual `create` action dispatches the payload to handlers that decide *what to mutate* using a **different, independently-controlled field** of the same JSON body: [3](#0-2) 

i.e. `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))`. This is used by `PushHandler`, the `PullRequest::*` handlers (`opened`, `labeled`, `unlabeled`, `assigned`, `edited`), etc., to look up the target stack/repository and perform writes (`stack.sync_github`, `stack.archive!`, `stack.unarchive!`, `pull_request.update`): [4](#0-3) 

Because Shipit supports **multiple configured GitHub organizations**, each with its own independent `webhook_secret` (`Shipit.github_app_config(organization)`), the app selected for signature verification is per-organization: [5](#0-4) 

Additionally, `verify_webhook_signature` treats a missing/blank `webhook_secret` as automatic success rather than failing closed: [6](#0-5) 

`return true unless webhook_secret` — if the organization named in `repository.owner.login`/`organization.login` has no `webhook_secret` configured, **any** payload with **any** (or no) valid-looking `X-Hub-Signature` is accepted as "verified" for that organization.

**Binding broken (as an equality):**
`organization authenticated by verify_signature (repository_owner field)` ≠ `repository actually written by the handler (repository.full_name field)`

Before the attacker's request: the signature is meant to prove "GitHub, on behalf of organization O, is delivering this exact payload." After: the code only proves "the secret belonging to whatever `repository.owner.login` says matches (or that org has no secret at all)," while the write target is whatever `repository.full_name` independently says — a value the signature check never inspects and that has no cryptographic tie to `repository_owner`.

### Impact Explanation
An attacker who can get one authentic/valid signature accepted for *any* configured organization (e.g. an org with a blank/misconfigured `webhook_secret`, or one whose secret they legitimately hold as an org member) can set `repository.owner.login` to that organization while setting `repository.full_name` to an entirely different, unrelated organization's/repository's `owner/repo` string. The handlers act purely on `repository.full_name`, so this results in unauthorized writes against a repository/stack the attacker was never authorized to touch: triggering deploy syncs (`stack.sync_github`), archiving/unarchiving review stacks, or mutating pull-request state cross-repository — a cross-repository write with no real GitHub authorization for the targeted repository. This matches the "cross-repository writes" Critical impact category.

### Likelihood Explanation
Requires only unauthenticated HTTP access to the public `/webhooks` endpoint plus knowledge that at least one configured GitHub organization in this Shipit deployment has a blank/default `webhook_secret`, or possession of a webhook secret for some low-value/attacker-controlled organization also registered in the same Shipit instance's multi-org `github` config. No repository write access, API token, or session is needed against the targeted victim repository, satisfying the "no privileged credential for the target" requirement.

### Recommendation
- Fail closed in `GitHubApp#verify_webhook_signature`: never treat a blank `webhook_secret` as automatically verified.
- Bind the payload's `repository.full_name` (and any other field the handlers act on) into the same trust domain as the one used to select the verification secret — e.g., re-derive/validate that the organization portion of `repository.full_name` matches `repository_owner`/the app whose secret validated the signature, rejecting mismatches before dispatching to handlers.
- Consider deriving the verifying organization strictly from `repository.full_name`'s owner segment (the field actually used for the write) rather than a separately-read `repository.owner.login`/`organization.login`, so the same field is both authenticated and acted upon.

### Proof of Concept
1. Shipit is configured with two organizations in `secrets.github`: `victim-org` (properly configured `webhook_secret`) and `test-org` (misconfigured, blank `webhook_secret`), per `Shipit.github_app_config` / `TOP_LEVEL_GH_KEYS` multi-org support (`lib/shipit.rb#L170-L200`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and any/garbage `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "test-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "deadbeef"
}
```
3. `verify_signature` resolves `repository_owner` = `"test-org"` (`app/controllers/shipit/webhooks_controller.rb#L59-L62`), loads `test-org`'s `GitHubApp`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb#L76-L83`) regardless of the bogus signature.
4. `create` dispatches to `PushHandler`, which resolves the target repository/stack from `repository.full_name` = `"victim-org/victim-repo"` (`app/models/shipit/webhooks/handlers/handler.rb#L32-L38`) and calls `stack.sync_github(expected_head_sha: ...)` on `victim-org`'s stack (`app/models/shipit/webhooks/handlers/push_handler.rb#L12-L17`) — an unauthorized action against a repository the attacker never proved control of.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
