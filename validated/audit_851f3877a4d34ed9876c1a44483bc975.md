### Title
Cross-organization webhook forgery via unverified `repository.owner.login` selecting the signing key while unrelated `repository.full_name` is trusted to select the target stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` picks *which* GitHub App/webhook secret to verify against using a field read straight out of the untrusted, unverified request body (`repository.owner.login` / `organization.login`), before any signature check has happened. The value that actually determines *which stack/repository* the event mutates is a different, unrelated field of the same untrusted body — `repository.full_name`, read later inside `Shipit::Webhooks::Handlers::Handler#repository_name`. Because these two fields are never cross-checked, and because `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved app has no `webhook_secret` configured, an attacker who can trigger genuine (correctly signed) delivery for one configured GitHub organization/App can forge the `repository.full_name` field to target a stack belonging to a completely different organization.

### Finding Description
`app/controllers/shipit/webhooks_controller.rb`:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` — the value used to select *which org's app/secret* is used for verification — is taken directly from the raw JSON body (`params`), which at this point has not been authenticated at all.

`lib/shipit/github_app.rb`:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
```
If the organization resolved from `repository_owner` has no `webhook_secret` configured (a supported, documented configuration — see `config/secrets.development.example.yml` and `docs/setup.md` "Using Multiple Github Applications"), verification is bypassed entirely, and *any* POST body is accepted regardless of its actual signature.

Once past `verify_signature`, the event is dispatched to handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), and every handler determines the target repository/stack from a *different* field:

`app/models/shipit/webhooks/handlers/handler.rb`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

There is no assertion anywhere that `repository.full_name`'s owner matches `repository.owner.login`/`organization.login` used for key selection. This is the same class of bug as the veAERO report: the binding `key used to authenticate == entity acted upon` is broken — `repository.owner.login` (verification key selector) ≠ `repository.full_name` (the actually-mutated stack/repository).

Concretely, if a multi-org Shipit deployment has:
- `OrgA` configured with no `webhook_secret` (e.g., a legacy/test/staging GitHub App entry, which the docs explicitly show as a supported config: `webhook_secret: # nil`)
- `OrgB` (a real, security-sensitive org) with a real `webhook_secret`

an attacker can POST directly to `/webhooks` with:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/critical-repo" },
  "ref": "refs/heads/main",
  "after": "<attacker-controlled sha>"
}
```
with header `X-Github-Event: push`. `repository_owner` resolves to `OrgA`, whose app has no secret, so `verify_webhook_signature` returns `true` unconditionally — no signature required at all. `PushHandler` then resolves `stacks` from `repository.full_name = OrgB/critical-repo`, and calls `stack.sync_github(expected_head_sha: ...)` on `OrgB`'s real stack.

The same technique lets the attacker forge:
- `status` events (`StatusHandler` → `Commit#create_status_from_github!`), fabricating CI/commit statuses (e.g., forcing `state: success`) for commits in `OrgB`'s stacks even though the attacker has no relationship with `OrgB` at all.
- `check_suite`, `deployable_status`, `pull_request` (label capture / merge queue interactions), and `membership` events (team/member creation) for any stack, because none of these handlers re-validate the organization that was actually authenticated.

### Impact Explanation
Forged `status`/`commit_status` events can mark arbitrary commits on any stack as CI-passing/deployable. Combined with Shipit's continuous-deployment/merge-queue logic (`Shipit::Stack#deployable?` gating and `ContinuousDeliveryJob`), an attacker with no relationship to the victim organization can make Shipit believe a commit is safe to auto-deploy, resulting in an **unauthorized deploy** — this matches the Critical impact bucket ("an unauthorized deploy, rollback or merge"). It also allows spoofing `push` events to trigger `GithubSyncJob` and re-point `LAST_DEPLOYED_SHA`/ref tracking for stacks that don't belong to the attacker's organization, and to fabricate `membership`/`pull_request` webhook side effects across organizational boundaries — a cross-organization write that the signature mechanism is specifically meant to prevent.

### Likelihood Explanation
This requires: (1) a multi-organization Shipit deployment (explicitly documented and supported: `docs/setup.md` "Using Multiple Github Applications", `config/secrets.development.example.yml`), and (2) at least one configured organization without a `webhook_secret` set (also an explicitly supported/documented state — the example config ships with `webhook_secret: # nil`). Any operator who onboards a second org (or leaves any one org's secret unset, e.g., during initial setup/testing) silently creates a bypass affecting every other configured org. No credentials, session, or repository access are needed — the `/webhooks` endpoint is unauthenticated by design and reachable by anyone. This is a realistic, not merely theoretical, misconfiguration path baked into supported functionality rather than requiring the operator to violate documented deployment practices.

### Recommendation
- Do not select the verification key from unauthenticated request data. Alternatively, after verification, assert that the organization used to select the signing key equals the owner encoded in `repository.full_name` (or `organization.login`) before dispatching to handlers, and reject on mismatch.
- Treat a missing `webhook_secret` as "verification required and impossible" (fail closed) rather than "verification not required" (`return true unless webhook_secret` in `lib/shipit/github_app.rb` should not silently pass).
- Reject webhook payloads whose `repository.owner.login` does not match the derived organization for the target `repository.full_name`.

### Proof of Concept
1. Configure Shipit with two orgs in `secrets.yml`: `OrgA` (no `webhook_secret`), `OrgB` (real `webhook_secret`, has stack `OrgB/critical-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/critical-repo" }
}
```
No `X-Hub-Signature` header is required.
3. `verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` immediately.
4. `PushHandler#process` resolves stacks via `repository.full_name` = `OrgB/critical-repo`, and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on `OrgB`'s real stack, without ever having presented a valid signature for `OrgB`.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
