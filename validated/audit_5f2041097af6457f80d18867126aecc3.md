This is a genuine, reachable cross-organization write vulnerability, structurally analogous to the reported bug: a value is validated/trusted (webhook signature bound to `repository.owner.login`), while a *different*, unchecked payload field (`repository.full_name`) is what actually determines which data gets mutated.

### Title
Webhook signature is verified against `repository.owner.login`, but the repository/stack that gets mutated is selected from the unverified `repository.full_name` field, allowing cross-organization/cross-repository writes - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` determines *which* GitHub App/organization secret to use for HMAC verification from `params.dig('repository', 'owner', 'login')` (falling back to `params.dig('organization', 'login')`), and only checks that this signature is valid for that organization. [1](#0-0) [2](#0-1) 

Once the request passes this check, `create` hands the *entire* raw JSON payload to the registered handlers unchanged. [3](#0-2) 

Every handler (`PushHandler`, `StatusHandler`, PR handlers, etc.) inherits `Handler#stacks`, which resolves the target repository/stack from a **different** field of the same payload: `payload.dig('repository', 'full_name')`. [4](#0-3) 

`Repository.from_github_repo_name` splits that string on `/` and does a plain DB lookup with no ownership cross-check against the organization that was actually authenticated. [5](#0-4) 

`repository.owner.login` (used for signature/org selection) and `repository.full_name` (used to pick the target `Repository`/`Stack`) are never compared for consistency.

### Finding Description
In a multi-organization Shipit deployment (documented in `docs/setup.md`, "Using Multiple Github Applications"), each organization has its own `webhook_secret` in `secrets.yml`. [6](#0-5) 

`GitHubApp#verify_webhook_signature` only proves that the request was signed with the secret belonging to whichever organization `repository_owner` resolves to — it says nothing about the repository the payload claims to modify: [7](#0-6) 

Because `Handler#repository_name` reads `repository.full_name` instead of `repository.owner.login`, an attacker who legitimately controls (or has the webhook secret for) organization `X` can craft a raw HTTP POST directly to the shared `/webhooks` endpoint with:
- `repository.owner.login` (and/or `organization.login`) = `X` (so `Shipit.github(organization: repository_owner)` resolves and the HMAC computed with `X`'s secret validates), and
- `repository.full_name` = `Y/victim-repo`, an entirely unrelated repository/stack belonging to organization `Y`.

The signature check passes (it is valid for `X`), but every downstream handler operates on `Y/victim-repo`'s `Stack`s, e.g. `PushHandler#process` calls `stack.sync_github(expected_head_sha: ...)` on stacks under the attacker-chosen repository, and `StatusHandler#process` writes arbitrary commit statuses via `commit.create_status_from_github!(params)`. [8](#0-7) [9](#0-8) 

Additionally, `verify_webhook_signature` treats a blank `webhook_secret` as automatic success (`return true unless webhook_secret`), and the setup docs explicitly call the webhook secret "optional" — so for any organization configured without a secret, `repository_owner` only needs to name that org to pass verification entirely, while `repository.full_name` can still target any other organization's repository in the same instance. [10](#0-9) [11](#0-10) 

This breaks exactly the binding the rules describe: *an organization that authenticated* (`repository.owner.login` verified via HMAC) *versus the repository that is written* (`repository.full_name`, never checked against the verified owner).

### Impact Explanation
This allows cross-repository/cross-organization writes without any Shipit session, API token, or repository access: an attacker who only controls one tenant organization (or knows an org configured with no `webhook_secret`) in a shared Shipit instance can forge `push`/`status`/`check_suite` events against any other organization's stacks, forcing unauthorized `sync_github` calls, injecting forged commit statuses that can satisfy `ci.require` checks and unblock merges/deploys, or disrupting deployable status for repositories the attacker has no legitimate access to. This matches the "cross-repository writes" / "unauthorized deploy, rollback or merge" Critical impact category.

### Likelihood Explanation
Requires only the ability to send a raw HTTP POST to the public `/webhooks` endpoint (no session or GitHub write access needed) plus knowledge of one organization's webhook secret (attacker's own tenant) or one organization configured without a secret — a configuration explicitly presented as optional in the setup docs. No GitHub-side webhook delivery is required since Shipit trusts any POST bearing a valid `X-Hub-Signature` for the org named in the payload.

### Recommendation
Derive the organization used for stack/repository resolution from the same field used for signature verification (or vice versa), and reject the webhook if `repository.owner.login`/`organization.login` does not match the owner embedded in `repository.full_name`. Concretely, `Handler#repository_name`/`Repository.from_github_repo_name` should validate that the resolved repository's `owner` equals the `repository_owner` that was cryptographically verified in `WebhooksController#verify_signature`, and `verify_webhook_signature` should not silently succeed when `webhook_secret` is blank in multi-organization configurations.

### Proof of Concept
1. Shipit is configured with two GitHub Apps in `secrets.yml`: `attacker-org` (webhook secret known/controlled by the attacker) and `victim-org` (separate secret, hosts `victim-org/prod-app` with an active `Stack`).
2. Attacker computes `sha1=HMAC(attacker-org-secret, body)` over a crafted JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/prod-app" }
}
```
3. Attacker POSTs this body directly to `https://shipit.example.com/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates successfully since the signature matches `attacker-org`'s secret. [12](#0-11) 
5. `PushHandler` resolves stacks via `payload.dig('repository', 'full_name')` = `"victim-org/prod-app"`, and calls `sync_github(expected_head_sha: "<attacker-chosen-sha>")` on `victim-org`'s stack, even though the signature only ever proved the request came from someone in possession of `attacker-org`'s secret. [8](#0-7) [4](#0-3)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
