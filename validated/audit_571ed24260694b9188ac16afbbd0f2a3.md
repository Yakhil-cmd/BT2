This confirms the critical detail: `StatusHandler#process` at [1](#0-0)  resolves the target commit **globally by `sha` across the entire Shipit installation** (`Commit.where(sha: params.sha)`), with no scoping to the repository/organization named in the payload at all.

### Title
Webhook signature is bound to `repository.owner.login` but never to the `sha`/`repository.full_name` actually mutated, enabling forged CI-success statuses and unauthorized auto-deploys - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/`webhook_secret` to validate the HMAC against using `repository.owner.login` read out of the *unverified* JSON body [2](#0-1) . `Shipit::GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is blank/unset [3](#0-2) , and the setup docs explicitly document `webhook_secret` as **optional** [4](#0-3) . Once past this per-organization gate, event handlers act on fields that are never cross-checked against the organization that was authenticated: `StatusHandler` looks up the target `Commit` purely `by sha`, with no repository/organization scoping at all [1](#0-0) , while other handlers scope by `repository.full_name`, a field independent from `repository.owner.login` [5](#0-4) .

### Finding Description
This is the same bug class as the Sudoswap report: a security check is bound to one field of a signed message, while the code path it's supposed to protect operates on a *different* field of that same message. In `LSSVMPairERC1155.swapTokenForAnyNFTs()`, the trade-fee accounting diverged from the invariant enforced elsewhere. Here, the invariant "a webhook is only trusted if its raw body was signed with the secret of the organization the event claims to originate from" is enforced only loosely:

- The organization used to pick the verification secret is `params.dig('repository','owner','login')` [6](#0-5) .
- If that organization has no `webhook_secret` configured (a supported, documented state — "Webhook secret (optional)" [7](#0-6) ), `verify_webhook_signature` short-circuits to `true` for **any** body and **any**/missing signature header [3](#0-2) .
- Once verification passes, `StatusHandler` never re-checks that the commit it mutates belongs to the organization that was authenticated — it matches purely on `sha` across the whole installation [8](#0-7) .
- `Commit#create_status_from_github!` writes a `state` (e.g. `success`) that directly feeds `Commit#deployable?` [9](#0-8)  and `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when the stack has `continuous_deployment` enabled [10](#0-9) , ultimately calling `Stack#trigger_continuous_delivery` → `trigger_deploy` [11](#0-10) . Tests confirm a `success` status alone (no real CI check) triggers a real `Deploy` when CD is enabled [12](#0-11) .

The binding that should hold is: `organization authenticated by verify_signature == organization owning the commit/stack the handler mutates`. Before any PR: this equality is never checked. After a hypothetical PR that only "removes an unused function" (as in the Sudoswap fix) without adding cross-field validation, the gap remains, because the root cause is architectural (signature binds to `owner.login`, mutation binds to `sha`/`full_name`, and the secret gate itself is skippable).

### Impact Explanation
This crosses the "escalation into unauthorized deploy" impact bucket: an unauthenticated network attacker (no Shipit session, no API token, no GitHub App key, no repository write access) who can reach the public `/webhooks` endpoint of an installation where at least one configured organization has no `webhook_secret` (a documented, optional setting, not a deviation from how the engine is meant to be mounted) can:
1. POST a forged `status` event (`X-Github-Event: status`) with `sha` equal to the HEAD commit of *any* stack tracked anywhere in that Shipit instance and `state: success`.
2. Because `StatusHandler` resolves the commit globally by `sha` with no organization/repository check [1](#0-0) , this works even for commits belonging to a *different, properly-secured* organization than the one whose lack of a secret let the request through the `verify_signature` gate.
3. If that stack has `continuous_deployment: true`, the forged success status causes an unauthorized automatic deploy of a commit that may never have passed real CI on GitHub.

### Likelihood Explanation
Requires: (a) the target Shipit instance to have `continuous_deployment` enabled on at least one stack (a normal, documented feature), and (b) at least one configured GitHub organization without a `webhook_secret` (explicitly supported as "optional" in setup docs). No credentials, tokens, or privileged access of any kind are needed — the `/webhooks` endpoint is public by design. This is a realistic misconfiguration-adjacent but fully documented state, not a deviation from how the engine is meant to be mounted.

### Recommendation
- Reject/require `webhook_secret` to be present for every configured organization rather than silently trusting unsigned payloads (`verify_webhook_signature` should fail closed, not open, when no secret is configured).
- Scope `StatusHandler` (and any other handler resolving state by `sha` alone) to the repository/stack identified by `repository.full_name`, and verify that `repository.full_name`'s owner matches the `repository.owner.login` that was used to select the verification secret.

### Proof of Concept
1. Configure two GitHub orgs in `secrets.yml`: `OrgA` (no `webhook_secret` set) and `OrgB` (has `Stack` with `continuous_deployment: true` and a pending commit `sha=deadbeef`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status`, no valid `X-Hub-Signature`, and body:
```json
{
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" },
  "sha": "deadbeef",
  "state": "success",
  "context": "ci/fake"
}
```
3. `verify_signature` looks up `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [13](#0-12) .
4. `StatusHandler#process` matches `Commit.where(sha: "deadbeef")` — the commit belonging to `OrgB`'s stack, not `OrgA` — and records a `success` status [1](#0-0) .
5. `OrgB`'s stack (continuous deployment enabled) auto-deploys the commit via `schedule_continuous_delivery` → `ContinuousDeliveryJob` [10](#0-9) , an unauthorized deploy triggered with zero credentials.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
