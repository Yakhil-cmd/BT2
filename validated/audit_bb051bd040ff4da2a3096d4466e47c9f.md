### Title
Bond-reward division rounds to zero while the earned sBTC is still deducted, permanently freezing that sBTC - (File: `stackslib/src/chainstate/stacks/boot/pox-5.clar`)

### Summary
`calculate-bond-rewards` in `pox-5.clar` guards only against `total-sats == 0` before computing `accrued-rewards-per-sat`, but not against the case where `total-sats` is merely large enough (relative to `earned * PRECISION`) to make the division truncate to `0` even though `earned` itself is non-zero. In that case the non-zero `earned` amount is still subtracted from `available-rewards` and folded into `last-accounted-rewards-only`, but zero is added to the bond's `rewards-per-token-for-cycle` accumulator, so no staker's claimable balance ever increases by that amount. The sBTC is accounted as "already paid out" yet never transferred to anyone.

### Finding Description
`calculate-bond-rewards` computes: [1](#0-0) 

```
(target-yield (/ (/ (* total-sats (get target-rate bond)) u10000) u50))
(earned (if (>= available-rewards target-yield) target-yield available-rewards))
...
(accrued-rewards-per-sat (if (is-eq total-sats u0) u0 (/ (* earned PRECISION) total-sats)))
```
Only the `total-sats == 0` case is treated as the "divide-by-zero" guard. If `total-sats != 0` but `earned * PRECISION < total-sats`, the division floors to `0`, even though `earned > 0`. The routine then still does: [2](#0-1) 

- writes `(+ current-rewards-per-token accrued-rewards-per-sat)` — i.e. adds `0` — to `rewards-per-token-for-cycle`, and
- returns `available-rewards: (- available-rewards earned)`, consuming the full non-zero `earned` amount from the pool that would otherwise flow to stx-only stakers or the reserve.

Back in `calculate-rewards`, `total-bond-rewards` (which includes this "earned" amount) is subtracted out of `remaining-rewards`/`gross-accrued-rewards`, and the whole `gross-accrued-rewards - reserve-deposit` (which still includes this lost `earned`) is folded into `last-accounted-rewards-only`: [3](#0-2) 

Because `get-new-rewards` computes `rewards-balance - last-accounted-rewards`, once this amount is folded into `last-accounted-rewards-only` it will never again be seen as "new" sBTC to distribute: [4](#0-3) 

Meanwhile, any staker's claim is strictly `compute-earned-rewards`, which is driven purely by the `rewards-per-token-for-cycle` delta: [5](#0-4) 

Since that delta was `0` for this bond/cycle, no staker in this bond can ever claim the lost `earned` sBTC via `claim-rewards`: [6](#0-5) 

This is structurally the same bug class as the referenced audit finding: a division that legitimately can floor to `0` on non-zero operands is only guarded for the trivial zero-denominator case, so the result is silently treated as "valid" (0 credit) while the corresponding value (`earned`) has already been consumed/accounted for elsewhere, corrupting the accounting invariant that "every sBTC subtracted from `available-rewards`/added to `last-accounted-rewards-only` is claimable by exactly the stakers it was earned for."

### Impact Explanation
The affected sBTC is deducted from the reward pool and marked as accounted-for (`last-accounted-rewards-only` increases), but is never credited to any staker's `rewards-per-token-for-cycle`, and the contract's sbtc-token balance is never transferred out for it. Because `get-new-rewards` will not re-surface this balance in any future `calculate-rewards` call, the sBTC is permanently stuck in the contract, unclaimable by any principal. Per the impact rubric, permanent freezing of sBTC rewards is a Critical-severity outcome.

### Likelihood Explanation
This requires a bond with `total-sats` large enough (or `earned` small enough due to a low `target-rate`/small `gross-accrued-rewards` in a given calculation window) that `earned * PRECISION < total-sats`. `setupBond`'s `target-rate` and allowlist `maxSats` are attacker/operator controllable parameters (within contract constraints), and `earned` also depends on how much sBTC has accrued to the contract since the last calculation, which is influenceable by timing calls to `calculate-rewards` shortly after a small reward deposit. The exact `PRECISION` constant value was not confirmed in this review, so the concrete numeric window where this triggers could not be independently verified; the structural flaw (missing zero-result guard beyond the zero-denominator check) is confirmed directly from the code, but likelihood/frequency in practice depends on that unverified constant and on typical bond sizes/target rates.

### Recommendation
In `calculate-bond-rewards`, guard the `accrued-rewards-per-sat` computation against the rounding-to-zero case, not just the zero-denominator case, e.g.: only subtract `earned` from `available-rewards` (and only count it in `gross-accrued-rewards` accounting) up to the amount actually representable/credited via `accrued-rewards-per-sat`, or round `earned` down to the largest value such that `(earned * PRECISION) / total-sats >= 1` when `total-sats > 0` and `earned > 0`, deferring any un-creditable remainder to the next calculation instead of permanently accounting it away. The same pattern should be checked in the STX-staker branch (`accrued-rewards-per-ustx`) in `calculate-rewards`, which has the identical structure.

### Proof of Concept
1. `setupBond` is created with a `target-rate` and an allowlist whose stakers commit a large aggregate `total-sats` for the bond (`register-for-bond` calls) relative to `PRECISION`.
2. A small amount of sBTC (`earned`, determined by `target-yield`/`available-rewards`) accrues to the contract such that `earned * PRECISION < total-sats`.
3. `calculate-rewards` is called: `calculate-bond-rewards` computes `accrued-rewards-per-sat = (earned * PRECISION) / total-sats = 0` (integer floor), while `available-rewards` is reduced by the full non-zero `earned`.
4. `rewards-per-token-for-cycle` for that bond/cycle is unchanged (added `0`).
5. `last-accounted-rewards-only` increases by `gross-accrued-rewards - reserve-deposit`, which includes the lost `earned`.
6. No staker of that bond can call `claim-rewards` to receive the lost `earned` sBTC, since `compute-earned-rewards` yields `0` extra for them, and `get-new-rewards` will never re-surface this sBTC in a later `calculate-rewards` call — the sBTC is permanently frozen in the contract.

;; Pure math formula for computing rewards earned since the last snapshot
;;
;; `earned = (shares * (rpt - rptPaid)) / PRECISION + pending`
(define-read-only (compute-earned-rewards
        (shares uint)
        (rpt-current uint)
        (rpt-paid uint)
        (pending uint)
    )
    (+ pending (/ (* shares (- rpt-current rpt-paid)) PRECISION))
