## Title
Delimiter Injection in Arbiter Contract Hash Allows Payer/Payee Term Ambiguity via Unescaped Field Concatenation - (File: arbiter_contract.js)

### Summary
`arbiter_contract.js` derives the security-critical contract identifier (`objContract.hash`) by naively concatenating attacker-influenced string fields (`title`, `text`, party names, addresses, amount, asset) with a fixed delimiter, without escaping occurrences of that delimiter inside the fields themselves. This mirrors the CWE-113/CWE-444 root cause in the reference advisory: untrusted string content is allowed to contain the very separator used to demarcate protocol/structural boundaries, letting an attacker forge ambiguous serialization that produces identical hashes for different substantive content.

### Finding Description
`getHashSrc()` builds the source string for the contract hash as: [1](#0-0) 

using `exports.DELIMITER = "[|#|]"` [2](#0-1)  to `.join()` the array of fields: `[title, text, creation_date, payer_address, payer_name, arbiter_address, payee_address, payee_name, amount, asset]`.

None of `title`, `text`, `my_party_name`/`peer_party_name` are checked for the presence of the delimiter string `"[|#|]"` before being concatenated — the only validation performed on these fields at intake, e.g. in `wallet.js`'s `arbiter_contract_offer` handler, is `isNonemptyString` / plain `typeof === "string"` checks: [3](#0-2) 

Because `title`, `text`, and the party names are attacker-controlled (they are supplied by the contract offeror, an untrusted paired device counterparty, and echoed back through `arbiter_contract_offer`/`arbiter_contract_shared`/`arbiter_dispute_request` device messages), a malicious party can embed the exact delimiter sequence `[|#|]` inside `title` or `text`. This breaks the 1:1 mapping between "logical contract content" and "serialized hash input": two contracts with different logical field boundaries (e.g., different `title`/`text` split, or a shifted `amount`/`asset` position) can produce the same concatenated string and therefore the same SHA-256 hash returned by `getHash()`: [4](#0-3) 

This is functionally identical to the disclosed bug class: an unsanitized separator character embedded in attacker-controlled data corrupts the intended structural boundaries of a downstream security check (there: HTTP header/request boundary via CRLF; here: contract-field boundary via the `[|#|]` token used for hash binding).

This hash is treated as an integrity anchor throughout the arbiter/dispute flow:
- It is compared against a freshly recomputed hash to validate incoming `arbiter_contract_offer`/`arbiter_contract_shared` messages from a peer or cosigner before storing the contract: [5](#0-4)  and [6](#0-5) .
- It is embedded into the on-chain `data` message (`contract_text_hash`) that is mutually signed by both parties to bind the contract terms to a specific unit: [7](#0-6) .
- It is used to derive the AA-like `has data feed` / `has output` shared-address definition condition keyed as `"CONTRACT_" + contract.hash`, which gates release of the escrowed payment to the arbiter/dispute winner: [8](#0-7) .
- It is re-verified during dispute handling against a hash independently recomputed from `contractContent` decrypted from the arbstore: [9](#0-8) .

Because the hash — not the raw structured fields — is what gets bound into the signed unit and the shared-address escrow definition, an attacker able to produce a second (title, text, amount, asset, party-name) tuple that hashes identically to a previously agreed tuple could substitute contract terms after signature/escrow creation while all hash equality checks still pass.

### Impact Explanation
This falls in the "private-payment counterparty ... asset issuance and transfer conditions ... AA definitions and triggers" reachable surface: the contract hash gates a shared, escrow-style payment address definition (`arrDefinition` with `"has output"`/`"in data feed"` conditions keyed by `contract.hash`) that controls fund release between two private-payment counterparties and an arbiter. If a hash collision via delimiter injection can be engineered, a malicious counterparty could present a contract whose disclosed/agreed terms (amount, asset, party names, or contract text) differ from what the other party or the arbiter/arbstore actually reviewed and signed, while the escrow definition and mutually-signed data message still validate — because they only assert `payload.contract_text_hash === contract.hash`, not the underlying structured fields. This is a form of fund-loss/freezing or fraudulent-dispute risk local to the two contract parties and their configured arbiter, consistent with the required impact class ("AA fund loss or freezing" analog in a wallet/contract escrow scheme).

### Likelihood Explanation
Exploitation requires the attacker to find/construct two field tuples (each containing `[|#|]` at attacker-chosen positions inside `title`/`text`) whose ordered concatenation is byte-identical, and to get the counterparty to accept/sign one interpretation while a different interpretation is later relied upon (e.g., during dispute resolution when only `contractContent.title`/`text` decrypted from an encrypted package are checked against the hash). This is achievable through straightforward field-boundary shifting (e.g., moving delimiter-like content from `title` into `text` or vice versa, since both are unrestricted free-text fields) — no cryptographic collision is required, only string re-partitioning around the fixed, non-escaped delimiter. This is a purely academic/medium-confidence chain because it requires cooperation-timing between the two parties' views of the contract; I could not fully verify a complete step-by-step exploit trace across every consuming code path (e.g. exact handling in `arbstore` server code) within the available index, since the arbstore-side code is external to this repo.

### Recommendation
Escape or reject the delimiter sequence in every field ingested into `getHashSrc()` before hashing (reject `title`/`text`/party names containing `[|#|]`), or switch to a length-prefixed / unambiguous serialization (e.g., the pattern already used in `string_utils.js`'s `getSourceString`, which explicitly rejects the `STRING_JOIN_CHAR` inside strings via `if (variable.includes(STRING_JOIN_CHAR)) throw Error(...)`) rather than naive `Array.prototype.join()` with a printable delimiter that can appear in user-supplied content: [10](#0-9) .

### Proof of Concept
1. Party A crafts an `arbiter_contract_offer` where `title = "Contract"` and `text = "[|#|]" + "100" + "[|#|]" + "USD"` (embedding the literal delimiter and forging what looks like additional trailing fields inside the `text` field).
2. Party A also crafts a second, "real" tuple where `title = "Contract[|#|]" ` and `text` shifted such that `getHashSrc()`'s array-join produces the exact same concatenated string as tuple 1 (by moving characters across the `title`/`text`/`payer_name` boundary around the delimiter token).
3. Both tuples, run through `getHashSrc()` → `getHash()` in [11](#0-10) , yield the identical SHA-256/base64 hash.
4. Party A sends tuple 1 as the `arbiter_contract_offer` (passes the `body.hash !== arbiter_contract.getHash(body)` check in [12](#0-11) ) and gets it accepted/signed, binding `contract_text_hash` into the on-chain data message.
5. Later, during a dispute, Party A supplies `contractContent` corresponding to tuple 2 to the arbstore/arbiter flow; the check at [9](#0-8)  recomputes the same hash and passes, even though the substantive contract terms differ from what Party B agreed to originally.

function getHashSrc(contract) {
	const payer_name = contract.me_is_payer ? contract.my_party_name : contract.peer_party_name;
	const payee_name = contract.me_is_payer ? contract.peer_party_name : contract.my_party_name;
	const payer_address = contract.me_is_payer ? contract.my_address : contract.peer_address;
	const payee_address = contract.me_is_payer ? contract.peer_address : contract.my_address;
	const src = contract.creation_date > exports.NEW_HASH_DATE
		 ? [contract.title, contract.text, contract.creation_date, payer_address, payer_name || '', contract.arbiter_address, payee_address, payee_name || '', contract.amount, contract.asset || 'null'].join(exports.DELIMITER)
		 : [contract.title, contract.text, contract.creation_date, payer_name || '', contract.arbiter_address, payee_name || '', contract.amount, contract.asset || 'null'].join("");
	return src;
}

function getHash(contract) {
	return crypto.createHash("sha256").update(getHashSrc(contract), "utf8").digest("base64");
}
