### Title
Stale Votes from Deregistered Bridge Operators Enable Unauthorized Value Transfers — (`contracts/service_chain/bridge/BridgeOperator.sol`)

---

### Summary

`BridgeOperator.deregisterOperator()` removes an operator from the active set but does not clear that operator's outstanding votes from the `votes` mapping. A remaining active operator can subsequently cast a vote on the same nonce with the same parameters, causing the stale vote to count toward the threshold and executing a value transfer the owner intended to block.

---

### Finding Description

When an operator is registered, they gain the ability to vote on value-transfer and configuration requests. When `deregisterOperator` is called, only `operators[_operator]` is deleted and the address is removed from `operatorList`. The `votes[VoteType][nonce].voted[operator]` and `votes[VoteType][nonce].voteCounts[voteKey]` entries are never cleared. [1](#0-0) 

The `_voteCommon` function compares the accumulated `voteCounts[voteKey]` against the current `operatorThresholds`. Because the deregistered operator's vote count contribution is never decremented, a single additional vote from any remaining active operator can push the count to or past the threshold. [2](#0-1) 

The code itself acknowledges this in a comment but frames it as an operator-management concern rather than a security invariant: [3](#0-2) 

The `_voteValueTransfer` path that triggers the actual asset transfer does not re-validate that all contributing voters are still registered at execution time: [4](#0-3) 

---

### Impact Explanation

A value-transfer request (ERC-20, ERC-721, or KLAY) can be executed on the destination bridge using a vote cast by an operator who has since been deregistered. The `handleERC20Transfer` / `handleKLAYTransfer` / `handleERC721Transfer` functions in `BridgeTransferERC20`, `BridgeTransferKLAY`, and `BridgeTransferERC721` all call `_voteValueTransfer`, which will return `true` and proceed to mint or transfer bridged assets to an arbitrary `_to` address. [5](#0-4) 

This constitutes an unauthorized transfer of bridged assets (KAIA or ERC-20/ERC-721 tokens held or mintable by the bridge contract).

---

### Likelihood Explanation

The preconditions are:

1. An operator (A) casts a vote on a value-transfer nonce N before being deregistered.
2. The owner deregisters A (e.g., because A is found to be malicious or compromised).
3. Any remaining registered operator (B) calls the same `handleERC20Transfer` with the same arguments for nonce N.

Step 3 requires a semi-trusted actor (a registered operator), but the owner's explicit remediation action (deregistration) is rendered ineffective. In a two-operator setup with threshold 2, deregistering one operator leaves the stale vote permanently in place; the remaining operator alone can complete the threshold. The window is unbounded — the stale vote never expires.

---

### Recommendation

Clear the deregistered operator's vote contributions inside `deregisterOperator`. For every open nonce where the operator has voted, decrement `voteCounts` and delete the `voted` entry:

```solidity
function deregisterOperator(address _operator) external onlyOwner {
    require(operators[_operator]);
    delete operators[_operator];
    // ... remove from operatorList ...

    // NEW: revoke outstanding votes for all open value-transfer nonces
    for (uint64 n = lowerHandleNonce; n <= upperHandleNonce; n++) {
        VotesData storage vd = votes[uint8(VoteType.ValueTransfer)][n];
        bytes32 oldKey = vd.voted[_operator];
        if (oldKey != bytes32(0)) {
            vd.voteCounts[oldKey]--;
            delete vd.voted[_operator];
        }
    }
    emit OperatorDeregistered(_operator);
}
```

Alternatively, record a "deregistration epoch" and reject votes cast before that epoch when tallying.

---

### Proof of Concept

1. Deploy `Bridge` with `modeMintBurn = false`; owner is also operator (threshold = 1).
2. Register operator A and operator B; set `ValueTransfer` threshold to 2.
3. Operator A calls `handleERC20Transfer(txHash, from, attacker, token, 1000e18, nonce=5, blockNum)`.
   — `voteCounts[voteKey] = 1`, threshold not yet reached.
4. Owner calls `deregisterOperator(A)`.
   — `operators[A] = false`, but `votes[0][5].voteCounts[voteKey]` is still 1.
5. Operator B calls `handleERC20Transfer` with identical arguments for nonce 5.
   — `_voteCommon` increments `voteCounts[voteKey]` to 2 ≥ threshold 2 → returns `true`.
   — `closedValueTransferVotes[5] = true`; `IERC20(token).safeTransfer(attacker, 1000e18)` executes.
6. 1000e18 tokens are transferred to `attacker` using a vote from a deregistered operator. [6](#0-5) [2](#0-1)

    function _voteCommon(VoteType _voteType, uint64 _nonce, bytes32 _voteKey)
        private
        returns(bool)
    {
        VotesData storage vote = votes[uint8(_voteType)][_nonce];

        // If the same voter voted again, revoke previous vote.
        bytes32 oldVoteKeyOfVoter = vote.voted[msg.sender];
        if (oldVoteKeyOfVoter == bytes32(0)) {
            vote.voters.push(msg.sender);
        } else {
            vote.voteCounts[oldVoteKeyOfVoter]--;
        }

        // Either the current voter has voted before or not, update the vote data.
        vote.voted[msg.sender] = _voteKey;

        if (vote.voteCounts[_voteKey] == 0) {
            vote.voteKeys.push(_voteKey);
        }
        vote.voteCounts[_voteKey]++;

        if (vote.voteCounts[_voteKey] >= operatorThresholds[uint8(_voteType)]) {
            return true;
        }
        return false;
    }
