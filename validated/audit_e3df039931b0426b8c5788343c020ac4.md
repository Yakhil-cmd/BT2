## Title
Asset definer can unilaterally revoke attestation from existing holders, permanently freezing their already-received tokens - ([File: validation.js])

### Summary
The `spender_attested` asset feature in `ocore` lets a token issuer (asset definer) gate transfers to only "attested" addresses, and the definer can update this attestor list at any time via an `asset_attestors` message. This is functionally equivalent to an upgradable/proxy token whose issuer can change transfer eligibility after tokens have already been distributed — the exact bug class flagged in the external report (tokens whose logic can change post-distribution and lock funds). Because the attestation check is re-evaluated at spend time using the *latest* attestor list rather than the list in effect when the tokens were received, a definer (or a definer whose signing key/AA logic is compromised or simply changes policy) can retroactively freeze balances that were legitimately received under a prior, valid attestor list.

### Finding Description
When an asset is created with `spender_attested: true`, transfers require the sending address to be in `objAsset.arrAttestedAddresses`: [1](#0-0) 

The attestor list itself is not fixed at asset-creation time. The definer can publish an `asset_attestors` message that replaces/extends the list, and validation only requires that the author be the asset's `definer_address`: [2](#0-1) 

`storage.readAsset` always resolves the asset's attestor list to the *latest* `asset_attestors` unit stable before `last_ball_mci`, not the list that was valid when a particular holder received their funds: [3](#0-2) 

The same check is duplicated for private/indivisible transfer validation and for issuance eligibility: [4](#0-3) 

Consequently, once a definer removes an address from the attestor list, any balance already held by that address in the asset becomes permanently unspendable — there is no mechanism for the holder to "grandfather" their previously-attested status. This mirrors the reported bug class: a token issuer changes behavior/logic after tokens are already in circulation, and holders can no longer move funds they legitimately possess (analogous to a rebasing/fee-changing/blacklist-capable proxy token breaking downstream assumptions).

This is especially impactful in the AA context: an Autonomous Agent that receives and holds a `spender_attested` asset (e.g. as part of a DeFi/exchange AA) has no way to react to or avoid a future attestor-list change by the asset definer. If the AA's own address is later removed from the attestor list, the tokens held by the AA become permanently stuck inside the AA, since the AA cannot re-attest itself and no other actor can move those specific coins out (`validatePaymentInputsAndOutputs` will reject any transfer from the AA's address for that asset).

### Impact Explanation
- Any legitimately received balance of a `spender_attested` asset can be frozen retroactively by the definer changing the attestor list, with no way for the holder to recover.
- If an AA holds such an asset, this results in permanent AA fund freezing — funds sent to the AA (or accumulated by the AA) in that asset become permanently locked in the AA, unreachable by any trigger, matching the "AA fund loss or freezing" acceptance criterion.
- Because the check is applied to `owner_address` (the *sender*, not just receiver) using the latest, not point-in-time, attestor list, the freezing is not an intentional design safety valve against future recipients — it strips previously-granted spending rights from existing holders.

### Likelihood Explanation
- Reachable by an unprivileged flow: any user can hold a `spender_attested` asset (including sending it into an AA), and the asset's own definer — an actor explicitly in scope ("asset issuer") — can trigger the freeze simply by posting a normal `asset_attestors` message, which requires no special consensus or hub cooperation.
- No additional conditions or races are needed: the attestor-list update is a single valid message type already supported by protocol, and its effect on existing balances is immediate and automatic due to how `readAsset`/`arrAttestedAddresses` are resolved.

### Recommendation
- Evaluate attestation status for a spend based on the attestor list in effect at the time the output being spent was created (or last confirmed as spendable), rather than always using the latest attestor list, so already-distributed funds are not retroactively frozen.
- Alternatively, provide an explicit "grace"/migration mechanism (e.g., allow spending to fixed set of previously-attested addresses even after removal, or allow transfer-only-to-definer to enable graceful exit) so holders always retain some path to move funds they legitimately hold.
- For AA-held `spender_attested` assets, disallow AAs from holding such assets, or ensure AA addresses cannot be removed from an attestor list without a corresponding on-chain remediation path.

### Proof of Concept
1. Definer creates asset `A` with `spender_attested: true`, `attestors: [X]`.
2. Definer issues/transfers some amount of `A` to address `X` (validated fine, since `X` is attested) — this validation path is `validatePayment` → `validatePaymentInputsAndOutputs`, using the attestor list active at that time (see [4](#0-3) ).
3. Definer later posts an `asset_attestors` message for asset `A` with a new list that excludes `X` (allowed per [2](#0-1) , since only definer-authorship is checked, not consent of existing holders).
4. `X` (or an AA at address `X`) attempts to spend its previously-received `A` balance. `storage.readAsset` resolves `arrAttestedAddresses` to the new list (see [3](#0-2) ), which no longer contains `X`.
5. `validatePaymentInputsAndOutputs` rejects the transfer with `"owner address is not attested"` (see [1](#0-0) ), permanently freezing `X`'s (or the AA's) previously valid balance of asset `A`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
