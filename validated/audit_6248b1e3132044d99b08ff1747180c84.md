### Title
Unchecked division in `PoolState::token_price_x32` panics (denies service) when a vault balance equals the accrued fee ledger, reachable from `swap_base_input`/`swap_base_output` - (File: `programs/cp-swap/src/states/pool.rs`)

### Summary
`token_price_x32` computes `token_1_amount as u128 * Q32 as u128 / token_0_amount as u128` and the symmetric expression for the other side using raw `/` division instead of `checked_div`. `token_0_amount`/`token_1_amount` come from `vault_amount_without_fee`, which is `vault_balance - (protocol_fees + fund_fees + creator_fees)` for that token. If that subtraction result is `0` (vault balance exactly equal to accrued, unswept fees) the subsequent division panics with a divide-by-zero runtime abort, aborting the whole transaction. This mirrors the CVE-2018-18521 bug class: an unguarded division whose divisor can become attacker-influenced zero, causing a crash instead of a handled error. [1](#0-0) 

### Finding Description
`vault_amount_without_fee` only guards against underflow via `checked_sub` (returning `InsufficientVault` if fees exceed balance), but it does not reject the boundary case where the subtraction result is exactly `0`: [2](#0-1) 

`token_price_x32` then divides by these possibly-zero amounts using plain `/` operators, with no `checked_div` or zero-guard: [1](#0-0) 

This function is invoked from `get_swap_params`, which is called unconditionally on every swap (both `swap_base_input` and `swap_base_output`), using the live vault token account amounts passed in by the swapper: [3](#0-2) [4](#0-3) 

Protocol/fund/creator fees accumulate over time on every swap via `update_fees` and are only ever reduced when explicitly collected (`collect_protocol_fee`/`collect_fund_fee`/`collect_creator_fee*`). If a pool's accrued `protocol_fees_token_0 + fund_fees_token_0 + creator_fees_token_0` (or the token_1 equivalent) happens to equal the current vault balance for that token exactly — a state reachable through ordinary, permissionless swap activity over time, since fees grow every swap while the tradable (non-fee) balance can shrink toward that value through legitimate trading — the next swap that reads that vault amount will hit `token_0_amount == 0` (or `token_1_amount == 0`) and cause an unguarded division by zero in `token_price_x32`, panicking the instruction.

### Impact Explanation
A panic inside `token_price_x32` aborts the entire transaction with a runtime error rather than returning a handled `Result` error. Once the pool's tradable vault balance for one side reaches parity with its unswept fee ledger, every subsequent `swap_base_input`/`swap_base_output` call against that pool will unconditionally panic, since `get_swap_params` is called on every swap before any fee-collection or amount computation happens. This makes the pool's swap path permanently unusable (denial of service) until fees are collected to shift the balance away from the zero boundary — and even then, the pool can be driven back into the same degenerate state by additional trading, since ordinary swap activity both grows fees and can shrink the corresponding vault side. This satisfies the "permanent freezing" bar for the affected pool's swap functionality, reached purely from a single unprivileged swap transaction.

### Likelihood Explanation
The reachability requires the fee ledger for one token to exactly equal that token's vault balance minus the other outstanding fee components — a specific numeric coincidence rather than something an attacker can force in a single transaction from arbitrary starting state. It can be approached via long sequences of ordinary swaps that grow fee accumulators while draining net vault balance on one side (e.g. extremely imbalanced repeated single-direction swaps that push one side's balance down toward its accrued fee total), but precisely landing on the exact zero point is more probable in low-decimal or otherwise sparse-value token pools. Likelihood is therefore moderate-to-low, but the mishandling (panic vs. handled error) is a genuine unguarded-division defect distinct from the `Fees`/`ceil_div`/`floor_div` helpers in `curve/fees.rs`, which do check `fee_denominator == 0` before dividing. [5](#0-4) 

### Recommendation
Guard `token_price_x32` (and its call sites in `get_swap_params`) against zero divisors, mirroring the pattern already used in `curve/fees.rs`'s `ceil_div`/`floor_div`: return a handled `ErrorCode` (e.g. `ZeroTradingTokens` or a new `InsufficientVault`/`DivideByZero` variant) instead of performing raw division. Concretely, replace the raw `/` operators in `pool.rs:226-227` with `checked_div` calls that map `None` to an `err!(...)`, consistent with how `vault_amount_without_fee` already returns `Result` for the analogous zero/negative case.

### Proof of Concept
1. Create a pool and, over a sequence of ordinary swaps, drive `token_0_vault.amount` down toward `protocol_fees_token_0 + fund_fees_token_0 + creator_fees_token_0` without ever collecting fees (all reachable via permissionless `swap_base_input`/`swap_base_output` calls).
2. Once `vault_amount_without_fee` returns `token_0_amount == 0` for the given vault balances, call `swap_base_input` (or `swap_base_output`) once more.
3. `get_swap_params` calls `self.token_price_x32(input_vault_amount, output_vault_amount)` which computes `token_0_amount as u128 * Q32 as u128 / token_1_amount as u128` — with `token_0_amount == 0`, the *other* expression `token_1_amount * Q32 / token_0_amount` divides by zero and panics, aborting the transaction and reverting the pool into a state where every subsequent swap against it repeats the same panic until fees are collected.         let fees_token_0 = self
            .protocol_fees_token_0
            .checked_add(self.fund_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_0)
            .ok_or(ErrorCode::MathOverflow)?;
        let fees_token_1 = self
            .protocol_fees_token_1
            .checked_add(self.fund_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?
            .checked_add(self.creator_fees_token_1)
            .ok_or(ErrorCode::MathOverflow)?;
        Ok((
            vault_0
                .checked_sub(fees_token_0)
                .ok_or(ErrorCode::InsufficientVault)?,
            vault_1
                .checked_sub(fees_token_1)
                .ok_or(ErrorCode::InsufficientVault)?,
        ))
    }

fn ceil_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(u128::from(fee_numerator))?
        .checked_add(fee_denominator)?
        .checked_sub(1)?
        .checked_div(fee_denominator)
}

/// Helper function for calculating swap fee
pub fn floor_div(token_amount: u128, fee_numerator: u128, fee_denominator: u128) -> Option<u128> {
    if fee_denominator == 0 {
        return None;
    }
    token_amount
        .checked_mul(fee_numerator)?
        .checked_div(fee_denominator)
}
