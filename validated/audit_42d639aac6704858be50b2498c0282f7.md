### Title
CCMenu API tokens issued for one stack authenticate `GET /api/stacks/*/ccmenu` for any stack — ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#fetch` mints a global, unscoped `read:stack` `ApiClient` token (not bound to the stack it was requested for), and `CCMenuController` overrides `stack` to resolve `params[:stack_id]` directly via `Stack.from_param!` without ever checking that the authenticated `ApiClient`'s `stack_id` matches the requested stack. A single token, legitimately obtained by a user for a stack they own, therefore authenticates `cc.xml` reads for **any** stack in the installation.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` for the stack being requested (as implemented correctly in `Api::BaseController#stack`, which restricts the `stacks` relation via `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`) [1](#0-0) .

`CCMenuUrlController#fetch` creates the client with `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` — no `stack:` attribute is ever set, so the resulting `ApiClient.stack_id` is `nil` (unscoped) regardless of which `stack_id` param was used to reach `fetch`. Because lookup is keyed only on `creator` + fixed `name`, the *same* row (and thus the same token) is reused across every stack a given user calls `fetch` for [2](#0-1) .

`CCMenuController` (mounted at `GET /api/stacks/*stack_id/ccmenu`) does not inherit `BaseController#stack`; it defines its own `stack` method that resolves `params[:stack_id]` via `Stack.from_param!` with no relation to `current_api_client.stack_id` at all, and its only authorization gate is `require_permission :read, :stack`, which merely checks the string permission `"read:stack"` is present in `current_api_client.permissions` — it never compares stack identities [3](#0-2) . `require_permission!` in `BaseController` only calls `current_api_client.check_permissions!(operation, scope)`, which is a pure permission-string membership check with no stack binding [4](#0-3) [5](#0-4) .

Attack: a user who owns/administers `stack_a` visits the settings page and triggers `GET /ccmenu/*stack_a` → `CCMenuUrlController#fetch`, receiving a token `t`. That same `t` (already possessed, no brute force) is then sent as `GET /api/stacks/*stack_b/ccmenu?token=t` for an arbitrary `stack_b` the user does not own. `ApiClient.authenticate(params[:token])` in `CCMenuController#authenticate_api_client` succeeds because the token verifies against `Shipit.api_clients_secret` and resolves to the same unscoped `ApiClient` row; `require_permission :read, :stack` passes because the client has `read:stack`; `stack` resolves `stack_b` directly with no ownership check [6](#0-5) . The existing test suite only verifies same-stack behavior and never asserts cross-stack denial [7](#0-6) .

### Impact Explanation
The attacker obtains unauthenticated (from the target stack's perspective) read access to `cc.xml` for any stack in the Shipit instance — including `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`, and lock status — using a token they legitimately hold for an unrelated stack they control. This is a token intended to be scoped to one stack silently working across all stacks, repeatable at will and across every stack in the deployment. This is a read-only status disclosure (build/deploy status, lock state), matching the **High** category: "unauthenticated read of stack state". It does not by itself permit writes, deploys, or credential exfiltration.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be a logged-in Shipit user with permission to view the settings page of at least one stack (to trigger `CCMenuUrlController#fetch`), which is a normal, low-privilege action for any stack they're associated with. No `api_clients_secret`, GitHub secrets, or elevated roles are required. The exploit is a single additional GET request with a query-string `token` and a different `stack_id`; it is trivially repeatable against any stack.

### Recommendation
Bind the minted token to the specific stack: set `stack: stack` when creating/finding the `ApiClient` in `CCMenuUrlController#client` (and include `stack` in the `find_or_create_by!` lookup key so distinct stacks get distinct clients), and enforce the binding in `CCMenuController#stack` by scoping through `current_api_client.stack_id` the same way `Api::BaseController#stack` does (e.g., reuse `stacks.from_param!(params[:stack_id])` instead of `Stack.from_param!`), rejecting the request (404/403) when `current_api_client.stack_id` is present and differs from the resolved stack.

### Proof of Concept
```ruby
# test/controllers/api/ccmenu_controller_cross_stack_test.rb
require 'test_helper'

module Shipit
  module Api
    class CCMenuControllerCrossStackTest < ActionController::TestCase
      test "a ccmenu token issued for stack A grants read access to stack B" do
        user = shipit_users(:walrus)
        stack_a = shipit_stacks(:shipit)
        stack_b = Stack.create!(repository: Repository.new(owner: 'other', name: 'repo'), branch: 'main')

        # Step 1: user legitimately fetches a ccmenu token for stack_a they own.
        @controller = Shipit::CCMenuUrlController.new
        session[:user_id] = user.id
        get :fetch, params: { stack_id: stack_a.to_param }
        token = JSON.parse(response.body)['ccmenu_url'][/token=([^&]+)/, 1]
        client = ApiClient.last

        # Binding under test: client.stack_id should equal the requested stack's id,
        # and CCMenuController should refuse to serve a different stack with this token.
        assert_nil client.stack_id # token is NOT scoped to stack_a at all

        # Step 2: same token used against an unrelated stack_b.
        @controller = Shipit::Api::CCMenuController.new
        get :show, params: { stack_id: stack_b.to_param, token: token }

        # Vulnerable behavior: request succeeds and returns stack_b's data,
        # even though client.stack_id (nil) != stack_b.id.
        assert_response :ok
        assert_includes response.body, stack_b.to_param
      end
    end
  end
end
```
This demonstrates that no stack-scope check exists: the same legitimately-issued token authenticates `cc.xml` for an arbitrary `stack_id`, with `client.stack_id` never compared to the requested stack.

      require_permission :read, :stack

      class NoDeploy

          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client

      end
