### Title
Signature verified for one GitHub org while `Team`/`Membership` state is mutated for another org named in `organization.login` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#repository_owner` selects the org used for signature verification by first checking `params.dig('repository','owner','login')` and only falling back to `params.dig('organization','login')` when `repository` is absent. `MembershipHandler`, by contrast, only reads `params.organization.login` (and ignores `repository` entirely) to decide which `Team#organization` to create/mutate. An attacker who controls a GitHub org (`orgA`, with a valid `webhook_secret`) can inject an arbitrary `repository.owner.login` block into the JSON body to force `verify_signature` to authenticate against `orgA`'s secret while the payload's `organization.login` names a victim org `orgB`, whose `Team` records will be created/mutated.

### Finding Description
The claimed binding: `organization_used_for_signature_verification (repository_owner) == organization_whose_state_is_mutated (params.organization.login)`. Before tracing, this equality is assumed to hold; verification confirms it can be broken.

`WebhooksController#repository_owner` is:
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_signature` uses this value to pick the `GitHubApp` (and thus the `webhook_secret`) used to check `X-Hub-Signature`:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(...)
``` [2](#0-1) 

`create` then parses the *same* raw body and dispatches the entire hash, unmodified, to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [3](#0-2) 

`MembershipHandler` only requires/reads `organization.login`, never `repository`:
```ruby
params do
  requires :organization do
    requires :login, String
  end
  ...
end
...
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [4](#0-3) 

Because GitHub's real `membership` webhook payload never contains a `repository` key, a legitimate request always falls through to the `organization.login` branch in `repository_owner`, and both fields agree. However, nothing in `verify_signature`, the `drop_unhandled_event` filter, or the `ExplicitParameters` schema for `MembershipHandler` rejects an attacker-supplied body that includes an extra `repository` object. An attacker who owns `orgA` (and thus its `webhook_secret`) can:
1. Build a JSON body: `{"action":"added","team":{...},"organization":{"login":"orgB"},"member":{"login":"attacker-login"},"repository":{"owner":{"login":"orgA"}}}`.
2. Sign it with `orgA`'s `webhook_secret` to produce a valid `X-Hub-Signature`.
3. POST it to `/webhooks` with `X-Github-Event: membership`.

`repository_owner` returns `"orgA"` (because `repository.owner.login` takes precedence), so `verify_signature` verifies successfully against `orgA`'s secret — a secret the attacker legitimately possesses. `Shipit::Webhooks.for_event('membership')` then dispatches the parsed params to `MembershipHandler`, which reads `params.organization.login == "orgB"` and creates/updates a `Team` scoped to `orgB`, adding the attacker-chosen `member.login` to that team via `team.add_member(member)`.

This is a real divergence: the two named values (`repository_owner` used for authentication, `params.organization.login` used for mutation) are not enforced to be equal anywhere in the code path, and the attacker fully controls both independently within the same signed body.

### Impact Explanation
This grants escalation into `Shipit.github_teams`-scoped membership records without any credential belonging to `orgB`. `User#authorized?` checks `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, so if `orgB`'s team happens to be one of `Shipit.github_teams` (the org whose team membership gates login authorization), an attacker can call `team.add_member(member)` for an arbitrary `member.login` (any GitHub username, including their own alt account or a Shipit user they control), granting that account authorization in the victim org's team without ever touching `orgB`'s GitHub org or secret. [5](#0-4)  This matches the "escalation into `Shipit.github_teams` authorization" High-severity category. It is repeatable against any org name the attacker chooses to put in `organization.login`, provided that org's `Team` row's `github_id` matches (or is newly created for) a team id the attacker controls in the payload; the blast radius spans any org configured in the multi-org `secrets.github` setup.

### Likelihood Explanation
Preconditions: Shipit configured with multiple GitHub orgs per `secrets.github`/`github_app_config`, each with a distinct `webhook_secret` [6](#0-5) ; attacker owns at least one configured org (`orgA`) and therefore its `webhook_secret`, which is standard for any org admin who installs the GitHub App on their own org. Attacker cost is low: crafting a JSON body and computing an HMAC signature with a secret they legitimately hold. The request requires no Shipit session, API token, or GitHub credentials for `orgB`. This is fully repeatable and scriptable.

### Recommendation
Make `verify_signature` and `MembershipHandler` (and any other handler) agree on a single source of truth for the organization. Either:
- Change `repository_owner` to prefer `organization.login` over `repository.owner.login` for organization-scoped events like `membership`, `team`, `organization`, etc., or
- After verifying the signature against `repository_owner`, re-validate that any `organization.login` (or other org-bearing field) referenced by the payload equals `repository_owner`, rejecting the webhook (422) if they differ.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual, not to be placed in test/ per audit scope but describing the assertions)
test "membership webhook signed by orgA cannot mutate team scoped to orgB" do
  payload = {
    action: 'added',
    team: { id: 1, name: 'Team', slug: 'team', url: 'https://api.github.com/teams/1' },
    organization: { login: 'orgB' },
    member: { login: 'attacker' },
    repository: { owner: { login: 'orgA' } }
  }.to_json

  stub_github_app = stub(verify_webhook_signature: true) # simulates orgA's secret verifying
  Shipit.stubs(:github).with(organization: 'orgA').returns(stub_github_app)

  post :create, body: payload, headers: {
    'X-Github-Event' => 'membership',
    'X-Hub-Signature' => 'sha1=valid-for-orgA'
  }

  # Binding check: repository_owner ('orgA') used for auth != params.organization.login ('orgB') used for mutation
  assert_equal 'orgA', @controller.send(:repository_owner)
  refute Shipit::Team.exists?(organization: 'orgB'), "Team for orgB must not be created via orgA's signature"
end
```
This test demonstrates that a signature verified against `orgA` results in state written under `organization: 'orgB'`, confirming the divergence described.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
