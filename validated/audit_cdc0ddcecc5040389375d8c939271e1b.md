### Title
Cross-tenant forged `status` webhook triggers unauthorized deploy via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits purely by `sha` with no repository/stack scoping, while `WebhooksController#verify_signature` validates the HMAC signature only against the org named in the *attacker's own* payload. An attacker who owns any repository connected to the same Shipit instance can send a correctly-signed `status` webhook whose `sha` field names the victim's public HEAD commit, forging a `success` status on the victim's stack and triggering an unauthorized deploy.

### Finding Description
The broken binding, stated explicitly: `Shipit.github(organization: repository_owner_from_attacker_payload).verify_webhook_signature(...)` (used to authorize the request) must equal the authority to write a `Status` for `Commit#stack_id` belonging to the *target* repository — but the code never checks this. `repository_owner` in `WebhooksController#verify_signature` is read straight from the untrusted payload (`params.dig('repository','owner','login')`), so it always matches whatever org the attacker names, i.e. their own: [1](#0-0) [2](#0-1) 

`StatusHandler` requires only `sha`/`state`/etc. as free strings, with no `repository` binding required or enforced against the resolved commit: [3](#0-2) 

Critically, unlike every other handler (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, etc.) which scope work through `Repository.from_github_repo_name(params.repository.full_name)` or the base `Handler#stacks` helper, `StatusHandler#process` bypasses that scoping entirely and queries `Commit.where(sha: params.sha)` across the whole database: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker owns (or controls) a repository/org with its own GitHub App installation on the same Shipit host, giving them a legitimate `webhook_secret` for *their* org — no Shipit secret or session required.
2. Attacker observes the victim's stack's current undeployed HEAD sha (public GitHub info for a public repo, or otherwise known).
3. Attacker POSTs a `status` event to `/webhooks` with `X-Github-Event: status`, a valid `X-Hub-Signature` computed with their own webhook secret, `repository.owner.login` set to their own org (so `verify_signature` passes), and `sha` set to the victim's HEAD sha, `state: "success"`.
4. `WebhooksController#create` dispatches to `StatusHandler`, whose `process` finds the victim's actual `Commit` record (already synced via legitimate push events) purely by sha and calls `commit.create_status_from_github!(params)`.
5. `Commit#create_status_from_github!` → `add_status` → `Status.replicate_from_github!` creates a `Status` with `stack_id: commit.stack_id` (the victim's stack) and `state: 'success'`: [6](#0-5) [7](#0-6) 
6. `Status#schedule_continuous_delivery` (`after_commit` on create) calls `commit.schedule_continuous_delivery` → `ContinuousDeliveryJob.perform_later(stack)`: [8](#0-7) [9](#0-8) 
7. `ContinuousDeliveryJob#perform` calls `stack.trigger_continuous_delivery` if `continuous_deployment?` and not occupied: [10](#0-9) 
8. `Stack#trigger_continuous_delivery` computes `next_commit_to_deploy` and, since `Commit#deployable?` is now true (`success? && !blocked?`), calls `trigger_deploy`, creating and enqueuing a real `Deploy`: [11](#0-10) [12](#0-11) 

No existing guard prevents this: `verify_signature` authenticates the *sender's own org*, not the org that owns the sha being mutated; `ExplicitParameters` only type-checks fields, it doesn't bind `sha` to `repository`; and `StatusHandler` performs no `Repository`/`Stack` scoping at all, in contrast to every other handler in the codebase.

### Impact Explanation
An unprivileged attacker who merely owns/controls a separate repository connected to the same Shipit instance can forge a commit status for an arbitrary victim stack they do not control, causing an unauthorized `Deploy` to be created and run — eventually reaching `Command#start`/`PTY.spawn` with the victim stack's deploy spec and `GITHUB_TOKEN`. This is a cross-tenant authorization bypass: the identity that authenticated the webhook (attacker's org) is decoupled from the identity whose `Commit`/`Stack` state is mutated (victim's org). It is repeatable against any stack with `continuous_deployment: true` and `ignore_ci?: false`, as long as the attacker can learn the target's current undeployed HEAD sha. This matches the Critical category: "an unauthorized deploy... triggered."

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment?` true and no active/occupied task (default, common configuration); attacker needs any repository with the GitHub App installed on the same multi-tenant Shipit instance (trivial to obtain by installing the public GitHub App on an attacker-owned repo, if the app supports multiple installations/orgs, which `Shipit.github(organization:)` and the multi-org secrets config explicitly support); attacker needs the victim's current HEAD sha, which is public for public repos. Attacker cost is a single crafted, self-signed HTTP POST, fully repeatable and scriptable against many victim stacks.

### Recommendation
Scope `StatusHandler` (and its params) by `repository.full_name` exactly like every other handler: resolve `Repository.from_github_repo_name(params.repository.full_name)`, then restrict the commit lookup to `Commit.where(sha: params.sha, stack: repository.stacks)` (or equivalent), rejecting the update if the resolved commit's stack's repository does not match the authenticated payload's repository. Require `repository.full_name` in the `StatusHandler` params schema and cross-check it against `commit.stack.repository` before calling `create_status_from_github!`.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, but conceptual — not to be placed under out-of-scope paths for delivery, just to illustrate the assertion):
1. Create `victim_stack` (fixtures) with `continuous_deployment: true`, a `Commit` with sha `SHA_V` belonging to `victim_stack`, no existing successful status, `ignore_ci?` false.
2. Stub `Shipit.github(organization: 'attacker-org').verify_webhook_signature` to return true (simulating attacker's own valid webhook secret) — asserting the equality `repository_owner_in_payload ('attacker-org') != victim_stack.repository.owner`.
3. POST to `/webhooks` with header `X-Github-Event: status`, body `{ sha: SHA_V, state: 'success', repository: { full_name: 'attacker/attacker-repo', owner: { login: 'attacker-org' } } }`.
4. `perform_enqueued_jobs` around the request.
5. Assert: `victim_stack.commits.find_by(sha: SHA_V).statuses.where(state: 'success').exists?` is true (forged status attached cross-tenant), and `assert_difference('Shipit::Deploy.count', 1)` around the POST, confirming a `Deploy` was created for `victim_stack` with `until_commit.sha == SHA_V`, despite the request never being signed by, nor originating from, the victim's repository/org.
