Webhook signature verification authenticates the wrong organization field, allowing forged writes to another repository's Stack - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App / `webhook_secret` used to validate the HMAC signature by reading `repository.owner.login` (falling back to `organization.login`) from the unauthenticated JSON body, and verifies that secret over the *entire* raw request body. However, every downstream event handler resolves which `Repository`/`Stack` to act on using a *different* field from the same body: `repository.full_name`. Because these are two independent, attacker-controlled strings inside one unsigned-until-verified payload, an attacker who controls an onboarded GitHub organization with no `webhook_secret` configured can forge a webhook whose `repository.owner.login`/`organization.login` names their own unsecured org (bypassing signature verification) while `repository.full_name` names a victim repository managed under a different, secured organization.

### Finding Description
The verification step: [2](#0-1) 

selects the app config via `repository_owner`: [3](#0-2) 

and `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured: [4](#0-3) 

This "no secret configured" state is a documented, supported configuration (default in `config/secrets.development.example.yml` and in the multi-org example in `docs/setup.md`), not a hardening requirement enforced by the engine.

Once verification passes, `WebhooksController#create` dispatches to handlers using `Shipit::Webhooks.for_event(event)`, passing the *same* raw parsed body: [5](#0-4) 

Every handler resolves its target repository from a field independent of the one used for signature authentication — `payload.dig('repository', 'full_name')`: [6](#0-5) 

For example, `PushHandler` triggers a sync job against the stacks belonging to that repository: [7](#0-6) 

and PR-related handlers (`OpenedHandler`, `LabelCapturingHandler`, `LabeledHandler`, `UnlabeledHandler`, `ClosedHandler`, `AssignedHandler`, `EditedHandler`, `ReopenedHandler`) all independently look up `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive review stacks, mutate `PullRequest#github_pull_request`, or provision new review stacks, e.g.: [8](#0-7) [9](#0-8) 

The binding that should hold is: **organization authenticated == organization whose repositories are written**. Instead the code authenticates `payload["repository"]["owner"]["login"]` (or `payload["organization"]["login"]`) but writes based on `payload["repository"]["full_name"]`, which can name an entirely different owner/organization within the same JSON object, since `ExplicitParameters` handler schemas only validate presence/type of `full_name`, not that it is consistent with the owner used for authentication.

### Impact Explanation
This breaks the deployment-trust boundary between an authenticated GitHub organization and the repository whose Stack state gets mutated. An attacker controlling any onboarded org lacking a `webhook_secret` can forge `push`, `pull_request` (opened/labeled/unlabeled/closed/reopened/assigned/edited), or other webhook events against a victim repository/stack hosted under a different, properly secured organization — triggering unauthenticated writes such as `GithubSyncJob` enqueuing, review stack archival/unarchival/creation, and mutation of `PullRequest#github_pull_request` state. This matches the High-severity class "unauthenticated read/write of stack state" via a credential/authentication boundary crossed without any Shipit session, API token, or GitHub write access to the victim's actual repository.

### Likelihood Explanation
Requires: (1) the Shipit deployment to onboard more than one GitHub organization, with at least one configured without a `webhook_secret` (a documented, common configuration shown in the project's own example secrets files), and (2) the attacker to have some presence (e.g., a repo) in that unsecured organization to know its login name, or simply knowledge of any onboarded org name that has no secret set (organization names are often public). No GitHub App private key, Shipit session, or API token is needed — only crafting a raw HTTP POST to `/webhooks` with a forged `X-Github-Event` header and JSON body.

### Recommendation
Bind signature verification to the same identity that handlers use to select the target repository/stack:
- Derive `repository_owner` and the acting `Repository` from a single, consistent field (e.g., always `repository.full_name`'s owner segment), and reject events where `repository.owner.login`/`organization.login` disagree with `repository.full_name`'s owner.
- Alternatively, verify the signature using the specific `webhook_secret` associated with the `Repository` actually targeted by `repository.full_name`, not a value independently supplied elsewhere in the same unauthenticated payload.
- Consider making `webhook_secret` mandatory for all configured organizations to remove the “verification returns true when secret is blank” bypass entirely.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` (no `webhook_secret` set) and `victim-org` (secured with a `webhook_secret`), each with repositories onboarded as Stacks — matching the supported multi-org configuration in `docs/setup.md`.
2. Attacker sends:
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
3. `verify_signature` computes `repository_owner` = `"attacker-org"` and calls `Shipit.github(organization: "attacker-org").verify_webhook_signature(...)`, which returns `true` unconditionally because `attacker-org` has no `webhook_secret` (`lib/shipit/github_app.rb:76-83`) — no valid `X-Hub-Signature` is required.
4. `WebhooksController#create` dispatches to `PushHandler`, whose `stacks` method resolves `Repository.from_github_repo_name("victim-org/victim-repo")` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and enqueues `GithubSyncJob` for the victim's stack with the attacker-chosen `expected_head_sha`, entirely bypassing `victim-org`'s configured webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
