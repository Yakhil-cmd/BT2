### Title
Recipient Contract Can Permanently Block KAIA Bridge Delivery by Reverting on Native Transfer — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

`handleKLAYTransfer` in `BridgeTransferKLAY` uses a push-transfer pattern (`_to.call.value(_value)("")`) to deliver native KAIA to the recipient. If `_to` is a contract whose fallback reverts, the `require(ok, ...)` guard causes the entire transaction to revert, rolling back all nonce/state updates. Because the recipient address is fixed by the original cross-chain request, bridge operators can never successfully deliver the KAIA, permanently locking bridged assets in the destination-chain bridge contract.

### Finding Description

In `handleKLAYTransfer`, the function performs all state mutations — marking the request hash as handled, recording the block number, advancing nonces, and closing the vote — **before** attempting the native transfer:

```solidity
_setHandledRequestTxHash(_requestTxHash);          // handledRequestTx[hash] = true
handleNoncesToBlockNums[_requestedNonce] = _requestedBlockNumber;
_updateHandleNonce(_requestedNonce);               // advances lowerHandleNonce / upperHandleNonce

emit HandleValueTransfer(...);

(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");  // reverts everything above on failure
``` [1](#0-0) 

Because `require(ok, ...)` is unconditional, a revert from `_to`'s fallback rolls back every state change in the same transaction, including `closedValueTransferVotes[_requestNonce] = true` set inside `_voteValueTransfer`. [2](#0-1) 

The `_to` address is immutable — it is taken directly from the `RequestValueTransfer` event emitted on the source chain and passed verbatim to `handleKLAYTransfer` by the bridge relayer. [3](#0-2) 

### Impact Explanation

A user who bridges KAIA to a contract address that reverts on receiving native tokens (or who deploys such a contract after initiating the bridge request) causes every `handleKLAYTransfer` attempt for that nonce to revert. Because the nonce state is rolled back on each failure, the vote is never closed and the nonce is never consumed. The KAIA deposited on the source chain is matched by KAIA held in the destination bridge contract that can never be disbursed to the intended recipient. The bridged asset is permanently locked.

Additionally, `lowerHandleNonce` cannot advance past the stuck nonce, which corrupts the recovery-block-number tracking used by the off-chain `ValueTransferRecovery` module. [4](#0-3) 

### Likelihood Explanation

Any user who initiates a KAIA bridge transfer specifying a contract address as `_to` can trigger this. The contract need not exist at request time — the user can deploy a reverting contract to the target address after the request is recorded on the source chain. No privileged access is required; the attacker is the bridge user themselves.

### Recommendation

Replace the push transfer with a pull pattern: credit `_to`'s claimable balance in a mapping and let the recipient call a separate `claim()` function. This decouples nonce/state finalization from the native transfer, ensuring the bridge nonce always advances regardless of recipient behavior. Alternatively, if a push is retained, the transfer failure should be recorded (not reverted) so the nonce is consumed and the funds are held in a claimable escrow.

### Proof of Concept

1. Alice deploys a contract `RevertReceiver` on the destination chain:
   ```solidity
   contract RevertReceiver {
       function() external payable { revert("no thanks"); }
   }
   ```
2. Alice calls `requestKLAYTransfer(address(RevertReceiver), 1 ether, "")` on the source-chain bridge, sending 1 KAIA + fee.
3. Bridge operators observe the `RequestValueTransfer` event and call `handleKLAYTransfer(txHash, alice, address(RevertReceiver), 1e18, nonce, blockNum, "")` on the destination bridge.
4. The low-level call `_to.call.value(1e18)("")` invokes `RevertReceiver`'s fallback, which reverts.
5. `require(ok, ...)` reverts the entire transaction; `closedValueTransferVotes[nonce]` remains `false`, `handledRequestTx[txHash]` remains `false`, and `lowerHandleNonce` is unchanged.
6. Every subsequent retry by operators produces the same revert. The 1 KAIA is permanently locked in the destination bridge contract. [5](#0-4) [6](#0-5)
