### Title
Cross-tenant team hijack via unscoped `Team.find_or_create_by!(github_id:)` in `MembershipHandler#process` - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#process` resolves the target `Team` solely by the attacker-supplied `params.team.id`, with no check that this team actually belongs to the organization whose webhook secret produced a valid HMAC. Combined with `User.find_or_create_by_login!(params.member.login)` creating/binding an arbitrary login with no verification against GitHub-reported team membership, an operator of any Shipit-configured GitHub org (their own) can forge a `membership` webhook that injects an arbitrary user login into a `Team` belonging to a completely different organization, including a `Team` referenced in `Shipit.github_teams` used for authorization.

### Finding Description
The broken binding: `payload['organization']['login'] == Team#organization` for the `Team` row that ends up receiving the new member — this equality is **never checked**.

Code path:
1. `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-49`) computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the HMAC using `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` [1](#0-0) [2](#0-1) . This only proves the payload was signed with the secret belonging to `repository_owner` — i.e., it proves *who sent it*, not that the `team` object inside the payload actually belongs to that sender.
2. `MembershipHandler#process` then does:
```
team = find_or_create_team!          # Team.find_or_create_by!(github_id: params.team.id) { ... organization = params.organization.login }
member = User.find_or_create_by_login!(params.member.login)
team.add_member(member) if action == 'added'
``` [3](#0-2) 
`find_or_create_by!(github_id: params.team.id)` only sets `organization` on the **create** branch of the block; if a `Team` row with that `github_id` already exists (e.g., a legitimate team belonging to organization "shopify"), the existing row is returned unchanged and the attacker-supplied `organization.login` (their own org) is silently ignored. There is no assertion `team.organization == repository_owner`.
3. `User.find_or_create_by_login!` (`app/models/shipit/user.rb:22-28`) creates/finds a `User` purely by `login` string; the only external check is an API call `Shipit.github.api.user(login)` to confirm the login exists on GitHub at all — it never checks that this user is actually a member of `params.team` or of `params.organization`.

Attacker exploit flow:
- Attacker configures/owns their own GitHub org "attacker-org" registered in Shipit (their own precondition), so they legitimately know `attacker-org`'s `webhook_secret`.
- They POST `/webhooks` with header `X-Github-Event: membership`, HMAC-signed with `attacker-org`'s secret, and body:
```json
{"action":"added","team":{"id": <github_id of victim org's team>,"name":"x","slug":"x","url":"x"},
 "organization":{"login":"attacker-org"},
 "member":{"login":"attacker-controlled-login"},
 "repository":{"owner":{"login":"attacker-org"}}}
```
- `verify_signature` succeeds because it only checks that `attacker-org`'s secret matches the HMAC over this body — it has no way to know `team.id` refers to a different org's `Team` row.
- `find_or_create_team!` finds the pre-existing `Team` for the victim org (matched purely by numeric `github_id`) and `team.add_member(member)` grants "attacker-controlled-login" membership in that team.
- If that `Team` is one of `Shipit.github_teams` (configured for OAuth authorization, see `User#authorized?` at `app/models/shipit/user.rb:80-82` and `force_github_authentication` at `app/controllers/concerns/shipit/authentication.rb:20-34`), the attacker (or anyone who later registers/owns that GitHub login) gains authenticated access to the Shipit instance upon OAuth login.

Existing guards do not catch this: `verify_signature` only authenticates the sender org, not the payload's internal `team`/`organization` consistency; `ExplicitParameters` schema only validates types/presence, not cross-field integrity; there is no `require_permission!` or team-organization equality check anywhere in `MembershipHandler`.

### Impact Explanation
An attacker who legitimately controls one Shipit-configured GitHub organization's webhook secret can inject arbitrary logins into a `Team` belonging to any other organization configured in the same Shipit instance, as long as they know (or can enumerate/guess) that team's numeric GitHub `id` — team IDs are not secret and are readable via the public GitHub API for teams the attacker can see, or leak in prior webhook traffic. If the targeted `Team` is part of `Shipit.github_teams`, this is a direct escalation into Shipit's OAuth authorization boundary (High severity per the stated categories: "escalation into `Shipit.github_teams` authorization"). This is repeatable per team/org and not scoped to a single tenant — it crosses tenant boundaries between any two organizations hosted on the same Shipit instance.

### Likelihood Explanation
Requires the attacker to already have a working, Shipit-registered GitHub App/webhook for some org (their own) — a real but attainable precondition (self-service in most multi-tenant Shipit deployments per `docs/setup.md`'s multi-org config format). No knowledge of the victim org's `webhook_secret`, `secret_key_base`, or GitHub App private key is needed. The only extra information needed is the victim `Team`'s numeric `github_id`, obtainable via the GitHub REST API (`GET /orgs/{org}/teams`) if the attacker has any visibility into the org (even indirectly), or via observed webhook payloads. Cost is low, and the request is trivially repeatable.

### Recommendation
In `MembershipHandler#find_or_create_team!`, require that the found team's `organization` matches `params.organization.login` (and that `params.organization.login` matches the already-HMAC-verified `repository_owner`); reject/raise if they diverge, e.g.:
```ruby
def find_or_create_team!
  team = Team.find_or_create_by!(github_id: params.team.id) do |t|
    t.github_team = params.team
    t.organization = params.organization.login
  end
  raise SecurityError, "team/organization mismatch" unless team.organization == params.organization.login
  team
end
```
Additionally, cross-check `params.organization.login` against the value used by `WebhooksController#verify_signature`'s `repository_owner` before dispatching to handlers, so a payload can't claim a different `team`/`organization` than the one whose secret authenticated the request.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook cannot hijack a team belonging to a different organization" do
  victim_team = shipit_teams(:shopify_developers) # organization: "shopify", github_id: known

  @request.headers['X-Github-Event'] = 'membership'
  forged_payload = {
    action: 'added',
    team: { id: victim_team.github_id, name: victim_team.name, slug: victim_team.slug, url: 'http://example.com' },
    organization: { login: 'attacker-org' },
    member: { login: 'attacker-login' },
    repository: { owner: { login: 'attacker-org' } }
  }.to_json

  # Signed correctly with attacker-org's own (legitimate) webhook secret
  Shipit.github(organization: 'attacker-org').stubs(:verify_webhook_signature).returns(true)
  Shipit.github.api.stubs(:user).with('attacker-login').returns(stub(id: 999, login: 'attacker-login', name: 'x', email: 'x@x.com', avatar_url: 'http://x', url: 'http://x'))

  assert_no_difference -> { victim_team.reload.members.count } do
    post :create, body: forged_payload, as: :json
  end
  # Currently FAILS: members.count increments by 1, proving
  # organization: "shopify" (victim_team.organization) != organization.login: "attacker-org" (payload)
  # yet membership is still created — the equality is never checked.
end
```
