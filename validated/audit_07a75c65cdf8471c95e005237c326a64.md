### Title
Unauthenticated access to `/events` stream leaks task/deploy broadcast data - ([File: config/routes.rb])

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` at `/events` inside `Shipit::Engine`, but this mount is a raw Rack app, not a controller including the `Shipit::Authentication` concern, so `force_github_authentication` never runs against it. `lib/shipit/engine.rb` does not register any Rack middleware to protect this route, despite `github_authentication_controller.rb` explicitly commenting that `/events` "leverage[s] `UserRequiredMiddleware`" to recognize authenticated sessions.

### Finding Description
The broken binding is: the comment in [1](#0-0)  asserts `session[:authenticated] == true` is checked by `UserRequiredMiddleware` before `/events` is reachable, i.e. `authenticated_request(/events) == true` should imply `session[:authenticated] == true`. In reality no such middleware exists anywhere in the engine — `lib/shipit/engine.rb`'s `initializer 'shipit.config'` only configures OmniAuth and an optional `SameSiteCookieMiddleware`, with no `UserRequiredMiddleware` insertion [2](#0-1) . The route itself mounts the Pubsubstub stream endpoint directly with no `before_action` guard, since it's a Rack mount, not a controller: [3](#0-2) . All other controllers get authentication via the `Shipit::Authentication` concern's `included do before_action :force_github_authentication end` [4](#0-3) , which cannot apply to a mounted Rack endpoint. Consequently, any unauthenticated HTTP client can open `GET /events?channels=stack.<id>` (or any channel name broadcast via `Pubsubstub.publish` in `app/models/shipit/stack.rb`) and receive live SSE/long-poll broadcast events for arbitrary stacks, including task and deploy status updates, with zero session, cookie, or token required.

### Impact Explanation
This grants unauthenticated read access to live task/deploy status streams for any stack ID, across all tenants/repositories hosted by the instance, matching the "High - unauthenticated read of stack state, task streams or deploy output" category. It does not by itself grant write access, RCE, or credential exfiltration — the broadcast payloads are status/progress data, not raw secrets — so it stays at High rather than Critical. The exposure is fully repeatable and requires no interaction with any specific repository's maintainers.

### Likelihood Explanation
Feasibility is high and cost is near zero: the attacker only needs network access to the Shipit host and knowledge (or brute-forcible guessing, since stack IDs are small sequential integers or predictable `owner/repo/env` slugs) of a channel name. No GitHub account, no Shipit session, no API token, and no privileged role are needed. This matches the "unprivileged internet attacker" threat model in scope.

### Recommendation
Register a `UserRequiredMiddleware` (or equivalent Rack middleware that checks `session[:authenticated]`/`session[:user_id]` and rejects unauthenticated requests) and insert it in `lib/shipit/engine.rb` ahead of the `/events` mount, or replace the raw `mount Pubsubstub::StreamAction.new` with a controller action that includes `Shipit::Authentication` and validates that the requested channel's stack is one the current user is authorized to view.

### Proof of Concept
Add a minitest integration test under `test/` (e.g. `test/integration/events_authentication_test.rb`) that:
1. Does not sign in any user (`session[:user_id]` unset, no `session[:authenticated]`).
2. Issues `get '/events', params: { channels: "stack.#{stacks(:shipit).id}" }`.
3. Asserts the response is `200`/streaming (not `302` redirect to `github_authentication_path` and not `403`), proving no authentication guard triggered — contrasted with a `get stack_path(stacks(:shipit))` on the same unauthenticated session, which asserts a `302` redirect via `force_github_authentication`, demonstrating the divergence between the two routes' equality of "requires authenticated session."
