### Title
Webhook Signature Verification Binds `repository.owner.login`, But Handlers Act on `repository.full_name` — Cross-Organization Stack/Commit Forgery - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/handler.rb)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/HMAC secret to validate a webhook using `repository.owner.login` (or `organization.login`) from the JSON body, but every webhook `Handler` subclass resolves *which Stack/Repository to mutate* using a different field of the same body: `repository.full_name`. Nothing ties these two fields together, so a party who legitimately controls one onboarded GitHub organization's webhook secret can forge a validly-signed payload whose `full_name` points at a completely different organization's repository, causing Shipit to act on a stack it has no authorization over.

### Finding Description
`verify_signature` picks the app config purely from the owning organization login: [1](#0-0) [2](#0-1) 

That check only proves "this request was signed with the secret belonging to organization X". It does not constrain what other fields of the (also-signed, but attacker-authored-per-organization) payload contain.

Every webhook `Handler` then determines the target `Stack` via a *different* payload field, `repository.full_name`, with no cross-check against the organization used to authenticate: [3](#0-2) 

Shipit explicitly supports hosting multiple independent GitHub Apps/organizations side by side, each with its own `webhook_secret` set by that organization's own admin when they create their App: [4](#0-3) [5](#0-4) [6](#0-5) 

Because organization admins choose/know their own `webhook_secret` (it's entered by them when creating the GitHub App per `docs/setup.md`), an admin of `OrgA` — with zero privileges on `OrgB` — can craft an arbitrary JSON body, sign it with `OrgA`'s known secret, set `repository.owner.login` (or `organization.login`) to `"OrgA"` so `verify_signature` selects and validates against `OrgA`'s secret, while setting `repository.full_name` to `"OrgB/target-repo"`. `verify_signature` passes, and the handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, etc.) resolves `stacks` for `OrgB/target-repo` and acts on it.

This is confirmed by the test suite, which shows a `push` webhook enqueues `GithubSyncJob` keyed off the stack resolved from the (attacker-controlled) `full_name`/`owner.login` fields of the same JSON payload, verified only against whichever organization's secret validates: [7](#0-6) [8](#0-7) 

The equality the code implicitly (and incorrectly) assumes is:
`organization authenticated by verify_signature (repository.owner.login) == organization of the repository/stack acted upon (repository.full_name)`

There is no code anywhere enforcing this equality — the two lookups are entirely independent reads of the same untrusted, attacker-shaped JSON body.

### Impact Explanation
Handlers gated only by this broken binding include `Handlers::StatusHandler`, which writes CI `Status` records used by Shipit's merge-queue/continuous-deployment gating logic, and `Handlers::PushHandler`/`Handlers::CheckSuiteHandler`, which trigger `GithubSyncJob`/`RefreshCheckRunsJob` against the resolved stack. An admin of any one organization configured in Shipit (who legitimately knows only their own organization's `webhook_secret`) can forge signed `status` events claiming a chosen commit in a *different* organization's repository passed CI, or force sync/refresh jobs to run against a foreign stack. Since Shipit uses commit statuses to decide whether commits are eligible to merge/deploy in the merge queue, this can enable an **unauthorized deploy** of unreviewed/unauthorized code in a repository the attacker does not control — meeting the Critical impact bar ("an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires only that the attacker administers (or has captured the webhook secret of) at least one GitHub organization/App already onboarded into the same multi-tenant Shipit deployment — a scenario the codebase explicitly supports and documents (`test/dummy/config/secrets_double_github_app.yml`, `docs/setup.md`). No access to `OrgB`, no `ApiClient` token, and no privileged Shipit account is needed; only the ability to POST a crafted, self-signed JSON body to the public `/webhooks` endpoint.

### Recommendation
After `verify_signature` selects the app/secret via `repository_owner`, re-validate that every payload field the handlers rely on (`repository.full_name`'s owner, `organization.login`) is consistent with that same verified owner before dispatching to handlers; reject the webhook otherwise.

### Proof of Concept
1. Attacker is the sole admin of `OrgA`, which is configured in Shipit's `secrets.yml` under `github: OrgA: webhook_secret: <known-to-attacker>`.
2. Attacker crafts a `status` (or `push`) JSON payload with `repository.owner.login = "OrgA"` but `repository.full_name = "OrgB/target-repo"` (a stack belonging to a victim org `OrgB` also hosted on the same Shipit instance), containing a fabricated passing CI status for a target commit.
3. Attacker computes `X-Hub-Signature: sha1=HMAC(OrgA_webhook_secret, body)` and POSTs to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgA")` and validates the signature successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `Handlers::StatusHandler` resolves `stacks` via `repository.full_name = "OrgB/target-repo"` (`app/models/shipit/webhooks/handlers/handler.rb:32-38`) and records the forged passing status against `OrgB`'s commit, with no verification that `OrgA` has any right over `OrgB`.
