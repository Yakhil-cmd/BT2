### Title
Cross-organization Team hijack via `MembershipHandler#find_or_create_team!` github_id-only lookup - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` correctly rejects webhooks from an unconfigured GitHub organization with a 422 via the `GithubOrganizationUnknown` rescue, but this guard only validates that the *sender's own organization* is registered in `Shipit.github(organization:)` config — it never binds the request's `organization.login` to the specific `team.id` the payload claims to mutate. Once an attacker controls any configured organization, they can send a `membership` webhook whose `team.id` matches an existing `Team` record that actually belongs to a different (victim) organization, and `MembershipHandler#find_or_create_team!` will silently reuse that victim `Team` row because it is looked up by `github_id` alone.

### Finding Description
The broken binding is: **expected** `Team#organization == params.organization.login` for the team object returned to `MembershipHandler#process`, **actual** `Team#organization` is whatever was persisted the first time that `github_id` was seen, independent of the organization asserted in the current, successfully-authenticated request.

Path:
- `verify_signature` resolves `Shipit.github(organization: repository_owner)` [1](#0-0)  and rescues `GithubOrganizationUnknown` with a 422 when the org isn't configured [2](#0-1) . This only proves "sender's org is configured," not "sender's org owns this team."
- `MembershipHandler#find_or_create_team!` does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.organization = params.organization.login ... }` [3](#0-2) . `find_or_create_by!` only assigns `organization` inside the block, which Rails/ActiveRecord executes **only on create**. If a `Team` with that `github_id` already exists (created earlier for a different org), the existing record is returned unchanged, `organization` is never re-checked or reassigned.
- `MembershipHandler#process` then calls `team.add_member(member)` (or removes) on whatever `Team` was returned [4](#0-3) , writing a `Membership` for the attacker-controlled `member.login` against the victim org's team.
- The `ExplicitParameters` schema for `MembershipHandler` only validates types/presence (`team.id`, `organization.login`, `member.login`) [5](#0-4) ; it does not check org/team ownership consistency.

Attacker request sequence:
1. `POST /webhooks` with `X-Github-Event: membership`, `organization.login = "unconfigured-org"` → `Shipit.github` raises `GithubOrganizationUnknown`, controller returns 422, nothing is written. This matches the existing test "unknown github organization logs and returns unprocessable entity" [6](#0-5) .
2. `POST /webhooks` with `organization.login = "<attacker's own configured org>"` (a real HMAC signed with that org's own `webhook_secret`, which the attacker legitimately controls as that tenant), `action: "added"`, `member.login = "<attacker-controlled login>"`, and `team.id = <numeric github_id of a pre-existing Team belonging to the victim org>`. `verify_signature` passes because the attacker's own org is configured and correctly signed. `find_or_create_team!` finds the victim's `Team` by `github_id` and returns it as-is; `team.add_member(member)` inserts a `Membership` linking the attacker's user to the victim's `Team`.

Why existing guards fail: `verify_signature` is scoped to "is this organization configured," not "does this organization own this team id"; the `ExplicitParameters` schema and `Handler#stacks`/`repository_name` machinery are unused by `MembershipHandler` (it never resolves `Repository`/`Stack`), so there is no secondary ownership check anywhere in the call chain.

### Impact Explanation
The attacker can silently graft a `Membership` for a user they control onto a `Team` record belonging to a completely different, victim organization, using only their own organization's legitimate webhook credentials — this is a cross-tenant "payload for one repository/org mutating another's team" record. If that victim `Team` is one of the entries resolved into `Shipit.github_teams` (used by `User#authorized?` at [7](#0-6) ), the attacker-controlled user becomes authorized across the whole Shipit instance, which is an escalation into `Shipit.github_teams` authorization (High), and in a scenario where that authorization gates deploy/merge actions the resulting unauthorized access to deploy/rollback capability rises to Critical. The attack is repeatable against any `Team#github_id` the attacker can learn (team ids are visible in GitHub team URLs/APIs and are not secret), and is not limited to a single victim org — any org's team can be targeted as long as its numeric id is known.

### Likelihood Explanation
Requires: multi-org Shipit deployment (`Shipit.github_teams`/multiple orgs in `secrets.github`), the attacker legitimately controlling at least one configured organization (their own tenant, with knowledge of only their own `webhook_secret`, no victim secrets needed), a pre-existing `Team` row for the victim org (created by any prior legitimate `membership` webhook or the `teams:fetch` rake task [8](#0-7) ), and knowledge of that team's numeric GitHub id (easily obtainable, GitHub team ids are not secret). No victim secrets, sessions, or API tokens are required — cost to the attacker is low and the action is fully repeatable.

### Recommendation
Scope the team lookup by both `github_id` and `organization`, and reject (or explicitly re-parent only via an authorized path) when a `github_id` collision maps to a different `organization` than the requester's authenticated `params.organization.login`. E.g. change `find_or_create_team!` to `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)` and raise/ignore if a `Team` with that `github_id` already exists under a different organization, rather than silently reusing it.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb` (multitenant fixtures: `:shopify` org owning `shipit_teams(:shopify_developers)`, and a second configured org, e.g. `:cyclimse`, which already has a configured `GithubHook`/webhook secret per fixtures):

```ruby
test ":membership from unconfigured org is rejected with no writes" do
  @request.headers['X-Github-Event'] = 'membership'
  Shipit.stubs(:github).raises(Shipit::GithubOrganizationUnknown.new("unconfigured-org"))

  assert_no_difference -> { Membership.count } do
    post :create, body: membership_params.merge(
      organization: { login: 'unconfigured-org' }
    ).to_json, as: :json
  end
  assert_response :unprocessable_entity
end

test ":membership from a different configured org hijacks another org's Team by github_id" do
  @request.headers['X-Github-Event'] = 'membership'
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify'

  assert_difference -> { Membership.count }, 1 do
    assert_no_difference -> { Team.count } do
      post :create, body: {
        action: 'added',
        team: { id: victim_team.github_id, slug: victim_team.slug, name: victim_team.name, url: victim_team.api_url },
        organization: { login: 'cyclimse' }, # attacker's own configured org
        member: { login: 'attacker-controlled-user' },
        repository: { owner: { login: 'cyclimse' } }
      }.to_json, as: :json
    end
    assert_response :ok
  end

  victim_team.reload
  assert_equal 'shopify', victim_team.organization # unchanged: still victim's org
  assert victim_team.members.exists?(login: 'attacker-controlled-user') # attacker user injected into victim's team
end
```
This asserts the equality `Team#organization == params.organization.login` fails after the second request (`'shopify' != 'cyclimse'`), while a `Membership` was written into the victim's `Team`, proving the guard checks org registration only, not org-to-team ownership.
