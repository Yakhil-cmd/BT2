### Title
Webhook signature verification is keyed by `repository.owner.login` while pull_request handlers mutate the repository resolved from `repository.full_name`, allowing an org with no configured `webhook_secret` to forge writes against any other org's stack - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate the HMAC signature using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')`. `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler#repository` (and every other pull_request handler) instead resolves the target `Shipit::Repository` from `params.repository.full_name`. Nothing ties these two payload fields together, so a webhook "verified" (trivially, because the org has no `webhook_secret`) under `attacker-org` can carry a `repository.full_name` of `victim-org/victim-repo` and mutate that stack's `Shipit::PullRequest`.

### Finding Description
The broken binding, stated explicitly:
`Shipit.github(organization: params.dig('repository','owner','login')).webhook_secret` (the secret that authorized the request) **should equal in scope** the organization owning `Shipit::Repository.from_github_repo_name(params.dig('repository','full_name'))` (the record actually mutated) — but the code never enforces this equality; the two are read from independent, attacker-controlled JSON fields.

Path:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` and does `github_app = Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
2. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when `@webhook_secret` is blank: `return true unless webhook_secret`. [3](#0-2) 
Per `docs/setup.md`, the webhook secret is explicitly documented as optional ("Webhook secret (optional)"), so a legitimately configured org with no secret is a supported configuration, not misconfiguration.
3. `WebhooksController#create` dispatches `params` (the full raw JSON, including the attacker-chosen `repository.full_name`) to the handler without any re-check that `repository.owner.login` matches `repository.full_name`'s owner segment. [4](#0-3) 
4. `AssignedHandler#repository` resolves the repository purely from `params.repository.full_name`, and `AssignedHandler#pull_request`/`#process` then updates the resolved `Shipit::PullRequest#github_pull_request` with attacker-supplied `pull_request` data (title, head.sha, etc.). [5](#0-4) 

Existing guards do not prevent this: `check_if_ping` and `drop_unhandled_event` only gate on the event type, not payload consistency; the `ExplicitParameters` schema in `AssignedHandler` only validates types/presence, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `require_permission!`, session, or API-client check on this controller at all, since webhooks are inherently unauthenticated except for the HMAC signature — and that signature check is the only control, and it is defeated by design whenever the attacker's own organization has no `webhook_secret` configured.

### Impact Explanation
An attacker who controls (or creates) any GitHub organization/app entry in `config/secrets.yml`'s multi-org `github` map with no `webhook_secret` (a documented, supported configuration) can send a crafted `pull_request` webhook whose `repository.owner.login` is their own org (satisfying `verify_signature`) but whose `repository.full_name` names a victim org's repository. This lets them write into another tenant's `Shipit::PullRequest#github_pull_request` (title, head sha, labels, assignees, etc.) — a cross-repository/cross-tenant write triggered by a payload that never authenticated against the victim organization at all. This matches the "payload for one repository mutating another's stack/commit" Critical category. The same flaw is present identically in `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `OpenedHandler`, `ReopenedHandler`, and `EditedHandler`, all of which resolve their target repository via `Repository.from_github_repo_name(params.repository.full_name)` (or `payload.dig('repository','full_name')` in the base `Handler#stacks`) independent of the owner used for signature verification. Repeatable for every stack in every victim org, as long as the attacker's own configured org has a blank `webhook_secret`.

### Likelihood Explanation
This requires the Shipit deployment to be configured with multiple GitHub organizations (the documented "Using Multiple Github Applications" setup) where at least one organization onboarded by the operator has no `webhook_secret` set — an explicitly supported, documented option ("Webhook secret (optional)"). Given that precondition, the attack costs a single unauthenticated HTTP POST to `/webhooks` with a crafted JSON body and no valid signature required; it is trivially repeatable against any repository/stack/PR number the attacker can guess or observe.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler`/each handler), require that the resolved `Shipit::Repository`'s owner matches the same `repository_owner` value used to select the `github_app`/secret used for verification, e.g. reject payloads where `params.dig('repository','owner','login')` doesn't match the owner segment of `params.dig('repository','full_name')`. Additionally, treat a blank `webhook_secret` as "reject all webhooks from this org" (or require operators to always set one) rather than "accept unconditionally," closing the root bypass in `GitHubApp#verify_webhook_signature`.

### Proof of Concept
Minitest plan (no live GitHub, following existing patterns in `test/controllers/webhooks_controller_test.rb` and `test/models/shipit/webhooks/handlers/pull_request/assigned_handler_test.rb`):
1. Seed two GitHub app configs via `Shipit.github_configs`/secrets fixture: `attacker-org` with `webhook_secret: nil`, `victim-org` with `webhook_secret: 'real-secret'`.
2. Create `victim_repo = Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo')`, a `Stack` on it, and `pr = Shipit::PullRequest.create!(number: 42, stack: stack, github_pull_request: { title: 'original' , head: { sha: 'orig_sha' } })`.
3. POST `/webhooks` with header `X-Github-Event: pull_request`, no `X-Hub-Signature` header (or a garbage value), and body:
```json
{"action":"assigned","number":42,"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"pull_request":{"id":1,"number":42,"url":"...","title":"PWNED","state":"open","additions":1,"deletions":0,"head":{"sha":"evil_sha","ref":"evil"},"user":{"login":"attacker"},"assignees":[{"login":"attacker"}],"labels":[]},"sender":{"login":"attacker-org"}}
```
4. Assert `response.status == 200` (not 422), proving `verify_signature` accepted the request via `attacker-org`'s (secret-less) config — equality check: `repository_owner == 'attacker-org'` while resolved repository owner from `full_name` is `'victim-org'`, i.e. `'attacker-org' != 'victim-org'`.
5. Reload `pr` and assert `pr.github_pull_request['title'] == 'PWNED'` and `pr.github_pull_request['head']['sha'] == 'evil_sha'`, proving the victim org's `PullRequest` record was mutated by a request never signed with `victim-org`'s `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
