## Analysis

The `batchId`/nonce-collision report is fundamentally about a shared piece of mutable state (`nonces[0]`) that is written by one execution path (`EntryPoint`) and consumed/relied upon by another, unrelated execution path (`execTransaction`), causing unexpected behavior for the second party because the two paths do not coordinate on that shared state. The closest analog in the Zest v2 codebase (Stacks/Clarity) is the market-level index cache, which is written by whichever transaction happens to touch a vault first in a block and is blindly consumed by every other, unrelated transaction that touches the same vault later in that same block.

### Title
Cross-transaction shared vault index cache lets one user's operation lock in a stale accrual for every other user's operation in the same block - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`accrue-and-cache` caches each vault's borrow/liquidity index in the persistent map `index-cache` keyed only by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . Because `stacks-block-time` is identical for every transaction mined in the same block, and because `map-set` persists this value in contract storage (not per-transaction memory), the cache entry written by the *first* transaction that touches a given vault (`aid`) in a block is reused as-is by *every other, unrelated transaction* that touches that vault later in the same block [2](#0-1) . This is the exact "shared cache primed by one caller and consumed by another" pattern the report's `batchId`/nonce collision represents, just expressed through a timestamp-keyed accrual cache instead of a nonce slot.

### Finding Description
`accrue-and-cache` is invoked from every collateral/debt accrual path (`accrue-debt-asset`, `accrue-collateral-asset`) before health checks, borrows, repays, deposits, redemptions and liquidations [3](#0-2) . On a cache miss it calls `vault-accrue`, which updates `index`/`lindex` in the underlying vault based on `principal-scaled` (total scaled debt) and elapsed time, and mints reserve shares to the DAO treasury based on the debt delta observed at that moment [4](#0-3) . The resulting `{index, lindex}` pair is then stored under a key that has no notion of which transaction, ordering, or intervening state changes occurred — only the block timestamp and asset id [1](#0-0) .

Once that entry exists, any subsequent transaction in the same block that touches the same `aid` (a different, unrelated user's borrow, repay, deposit, redemption, or liquidation) takes the cache-HIT branch and reuses the first caller's index/lindex directly, skipping `vault-accrue` entirely [5](#0-4) . That cached `lindex` also feeds directly into ztoken price resolution (`resolve-ztoken`), which is used for collateral valuation and health checks [6](#0-5) . Consequently, whichever unrelated transaction happens to be first in a block for a given vault silently fixes the debt/liquidity index — and therefore ztoken prices — for every other user's operations against that vault for the remainder of the block, regardless of debt or supply changes those other users' own preceding actions in the block would otherwise have caused to be re-evaluated.

The project's own documentation frames this purely as a gas optimization with "no stale data risk" because the cache is invalidated by the next block's new timestamp [7](#0-6) . That reasoning only covers cross-block staleness; it does not address that the cache is shared *across unrelated transactions within the same block*, which is precisely the scenario that matters for ordering-dependent economic outcomes between two different, unprivileged users.

### Impact Explanation
Because collateral/ztoken valuation for health checks and liquidation eligibility is derived from the cached `lindex`/`index` [6](#0-5) , a victim's borrow, withdrawal, or liquidation-avoidance transaction executed later in a block can be evaluated against an index that does not reflect debt/supply state as of that victim's own transaction, but instead reflects whatever state existed when an unrelated, earlier transaction in the same block happened to prime the cache. This can push a solvent position into apparent under/over-collateralization at the point health is checked, enabling either (a) an unwarranted liquidation of a victim's collateral beyond what their true, up-to-date position would justify (theft of user funds), or (b) permitting a borrow that should have failed a health check, leaving the pool with bad debt (protocol insolvency risk). Both map to the Critical impact class.

### Likelihood Explanation
Likelihood is moderate: it requires two unrelated transactions touching the same vault (`aid`) to land in the same block, which is common for popular vaults (e.g., `USDC`, `sBTC`) under normal network activity, and does not require any privileged role or DAO compromise — any two ordinary users' transactions can trigger it.

### Recommendation
Scope the index cache to the current transaction only (e.g., re-derive `index`/`lindex` per top-level call instead of persisting them in a block-keyed map, or add a per-transaction nonce/id to the cache key so it cannot be reused across distinct transactions), and/or force `vault-accrue` to always run for the first accrual-sensitive operation of every transaction rather than trusting a cross-transaction persistent cache.

### Proof of Concept
1. Block N: User A calls `system-borrow` on the USDC vault. `accrue-and-cache(USDC)` misses, calls `vault-accrue`, and caches `{index, lindex}` computed from the pre-borrow `principal-scaled`/utilization [1](#0-0) [8](#0-7) . User A's borrow then changes `principal-scaled`/utilization for the vault.
2. Same block N: User B, unrelated to A, calls an operation that requires health-check pricing of zUSDC collateral (e.g., a borrow against zUSDC collateral). `accrue-and-cache(USDC)` hits the cache written in step 1 and returns A's pre-borrow index/lindex instead of one reflecting the state after A's borrow [5](#0-4) .
3. `resolve-ztoken` prices B's zUSDC collateral using that stale, cross-transaction cached `lindex` [6](#0-5) , so B's health check is computed against state that does not correspond to B's actual transaction-time vault state, producing a pass/fail outcome that would differ had the cache not been shared with A's unrelated transaction.

Note: I could not access the full implementation of `next-index`/`next-liquidity-index` (the interest-rate model) to quantify the exact magnitude of index divergence introduced by intervening utilization changes within one block; the finding above is based on the confirmed cache-sharing mechanism and its confirmed consumption in pricing/health-check paths, not on a numerically simulated worst-case delta.

```text
;; -- Accrual & caching ------------------------------------------------------

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
