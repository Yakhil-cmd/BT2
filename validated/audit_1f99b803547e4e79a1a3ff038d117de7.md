### Title
Uncaught `throw Error` in private-payment chain validation crashes node process - ([File: validation.js])

### Summary
`validation.js`'s divisible-payment validator (`validatePaymentInputsAndOutputs`) contains hard `throw Error(...)` invariant checks for private, fixed-denomination asset transfer inputs that assume `objValidationState.src_coin` was already populated by the caller before `validation.validate()` is invoked. When a private-payment counterparty supplies a crafted/incomplete private-elements chain, these assumptions can be violated, causing an uncaught `Error` to propagate out of the validation callback chain. Because `network.js` installs a global `uncaughtException` handler that deliberately re-throws to kill the process, any such uncaught `Error` crashes the whole node — the same "malformed/unexpected value → assertion-style throw → process death" bug class as CVE-2019-6473 in Kea DHCPv4 (an invalid option value hits an `assert()`/invariant instead of being rejected gracefully, killing the server process).

### Finding Description
In `validatePaymentInputsAndOutputs`, the "transfer" input handling for private fixed-denomination assets branches into a code path that trusts pre-populated state instead of validating input directly: [1](#0-0) 

This code is reached from a payment message whose asset is private and has `fixed_denominations`. Unlike ordinary transfers, this path does not look up the source output in the database — it instead requires `objValidationState.src_coin` to already carry a valid `src_output`, `denomination`, and `amount`. If any of these are missing when this branch executes, the code throws a raw `Error` rather than returning a normal validation error through the `cb(...)`/`callback(...)` mechanism used everywhere else in this function.

This validation is invoked by `private_payment.js` → `validateAndSavePrivatePaymentChain`, which is the entry point that a recipient (or cosigner) calls to validate a private-payment chain **received from a counterparty**: [2](#0-1) 

The `arrPrivateElements` array (and its `payload`/`output` contents) originates from the sending counterparty and is only lightly checked (`isNonemptyArray`, presence of `payload.asset`, `message_index`) before being handed to `indivisibleAsset.validateAndSavePrivatePaymentChain`, which is responsible for constructing `objValidationState.src_coin` from the chain elements and then calling `validation.validate()`. If the counterparty's chain is malformed in a way that this construction step misses (e.g., omits/garbles the linking element needed to derive `src_output`/`denomination`/`amount` for a later transfer in the chain), `objValidationState.src_coin` (or one of its fields) will be absent when `validatePaymentInputsAndOutputs` reaches the `throw Error("no src_coin")` / `"no src_output"` / `"no denomination in src coin"` / `"no src coin amount"` checks.

Any uncaught exception anywhere in the process is caught by the global handler in `network.js`, which explicitly re-throws to crash the process: [3](#0-2) 

So a validation-time `throw Error` that is not wrapped in a try/catch by the caller results in full node termination — a denial-of-service against the specific node/wallet processing that private-payment chain, directly analogous to the Kea DHCPv4 assertion failure that crashes `kea-dhcp4` on invalid attacker-supplied option data.

### Impact Explanation
A private-payment counterparty (the direct recipient/cosigner of a private indivisible/divisible asset transfer) can send a malformed private-elements chain that triggers one of the `throw Error` invariant checks in `validatePaymentInputsAndOutputs` instead of a graceful validation rejection. Because the top-level `uncaughtException` handler is configured to re-throw and crash the process, this results in denial of service to the recipient's node — a wallet or full node becomes unable to process further units until restarted, matching the "network unable to confirm new units" / node-crash impact class called out in the validation rules.

### Likelihood Explanation
Exploitability depends on precisely how `indivisibleAsset`/`divisibleAsset`'s `validateAndSavePrivatePaymentChain` constructs `objValidationState.src_coin` from the received chain elements before calling `validation.validate()` — a code path I was only able to partially trace (grep found the `src_coin` construction site referenced only once in `indivisible_asset.js`, and I ran out of iterations to fully inspect it). If the construction logic itself already fully validates and rejects malformed chains before ever reaching `validation.validate()`, the `throw Error` branches would only be reachable via genuine internal bugs/state corruption, not directly from attacker input, lowering likelihood. This should be verified by tracing `indivisible_asset.js`'s chain-building code end-to-end against attacker-controlled `arrPrivateElements` fields (`output`, `payload.denomination`, `unit`, `message_index`, `output_index`) to confirm whether a crafted chain can skip or corrupt `src_coin` population.

### Recommendation
- Replace the `throw Error("no src_coin")` / `"no src_output"` / `"no denomination in src coin"` / `"no src coin amount"` invariant checks in `validation.js` (`validatePaymentInputsAndOutputs`, private fixed-denomination transfer branch) with calls to `cb(...)`/`callback(...)` that surface a normal validation error to the caller instead of throwing.
- Audit `indivisible_asset.js` / `divisible_asset.js` chain-building code that populates `objValidationState.src_coin` from a counterparty-supplied private-elements chain, ensuring all fields are validated (existence, type, positivity) before being trusted by `validation.js`.
- Consider wrapping calls into `validation.validate()` from private-payment handling code (`private_payment.js`, `indivisible_asset.js`, `divisible_asset.js`) in a try/catch that converts thrown errors into `ifError` callbacks rather than allowing them to propagate to the global `uncaughtException` crash handler.

### Proof of Concept
1. Attacker acts as a private-payment counterparty and initiates/participates in a private indivisible or divisible asset payment with a victim node.
2. Attacker crafts the `arrPrivateElements` chain sent to the victim (via `validateAndSavePrivatePaymentChain`) such that a later "transfer" input in the chain lacks the data needed for the chain-builder to populate `objValidationState.src_coin` (or one of `src_output`/`denomination`/`amount`) before `validation.validate()` is invoked.
3. On the victim node, `validatePaymentInputsAndOutputs` reaches the private fixed-denomination transfer branch and executes `throw Error("no src_coin")` (or one of the sibling throws) at `validation.js:2416-2424`.
4. The uncaught exception is caught by `process.on('uncaughtException', ...)` in `network.js:4530`, which logs it and re-throws, terminating the victim's node process.

*(This PoC path is based on static analysis of the `throw Error` invariant checks and the crash-on-uncaught-exception handler; full confirmation requires tracing the exact chain-building logic in `indivisible_asset.js`/`divisible_asset.js` that I could not fully inspect within the available iterations.)*
