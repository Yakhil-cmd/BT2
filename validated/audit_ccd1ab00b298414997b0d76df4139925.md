### Title
Webhook signature is verified against `repository.owner.login`'s GitHub App while `LabeledHandler` mutates the stack resolved from the unrelated `repository.full_name` field, allowing cross-organization forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/labeled_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` used to check the HMAC signature by reading `repository.owner.login` from the raw, attacker-supplied JSON body, but every `pull_request` handler (including `LabeledHandler`) resolves the actual `Shipit::Repository`/`Stack` to mutate via the completely separate `repository.full_name` field from the same body. If the organization named in `repository.owner.login` has no `webhook_secret` configured (an explicitly supported, documented configuration), `GitHubApp#verify_webhook_signature` returns `true` unconditionally, letting an unauthenticated attacker submit a payload that authenticates as the no-secret org while `full_name` points at and mutates a victim org's stack.

### Finding Description
The broken binding: the code implicitly assumes `repository.owner.login == owner(repository.full_name)`, but nothing enforces this equality.

- `verify_signature` picks the app config via `repository_owner`, which is read straight from the JSON body: `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected org's config has no `webhook_secret` (documented as optional in `docs/setup.md` and `config/secrets.development.example.yml`), meaning no cryptographic check happens at all for that org. [3](#0-2) 
- Once "verified", `Shipit::WebhooksController#create` dispatches the full raw JSON body to every handler for the event, including `LabeledHandler`. [4](#0-3) 
- `LabeledHandler` resolves the repository/stack to mutate using `params.repository.full_name`, a totally different field from the one used to pick the signing secret, and calls `stack.archive!`/`stack.unarchive!` on it. [5](#0-4) 

Exploit flow: attacker sends `POST /webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=anything`, and a JSON body where `repository.owner.login` = `"no-secret-org"` (an org whose Shipit config has `webhook_secret: nil`, which the docs present as an acceptable/optional setting) and `repository.full_name` = `"victim-org/victim-repo"` (an org with a real, secret-protected app and `bot_login` configured). `verify_signature` looks up `Shipit.github(organization: "no-secret-org")`, calls `verify_webhook_signature` which returns `true` unconditionally because `webhook_secret` is blank, and the request passes with no real authentication performed. `LabeledHandler` then looks up `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and, depending on the crafted `pull_request.labels`, archives or unarchives the victim's review stack. Unarchiving re-enables `GithubSyncJob`/continuous delivery for that stack; per `Shipit::Stack#trigger_continuous_delivery`, deploys triggered this way run as `Shipit.user`, which resolves to the configured `bot_login` when the bot is configured, giving the forged action the bot's identity for any subsequent automatic deploy of attacker-influenced commits. [6](#0-5) [7](#0-6) 

None of the usual guards catch this: `drop_unhandled_event` only checks the event type exists, `ExplicitParameters` only validates shape/types of `repository.full_name`, not that it matches `repository.owner.login`, and there is no model validation tying `Stack`/`Repository` lookups back to the org that authenticated the request.

### Impact Explanation
An attacker who controls (or can register) any Shipit-configured GitHub organization lacking a `webhook_secret` can forge webhook events that mutate stacks belonging to a completely different, secret-protected organization — a payload for one repository mutating another's stack, matching the Critical impact category. Concretely, `LabeledHandler` can silently archive or unarchive a victim's review stack; unarchiving reactivates GitHub sync and continuous-delivery triggering for that stack, which can lead to unauthorized deploys running under the bot identity. This is repeatable against any stack whose repository full name the attacker can guess or discover (repo names are generally public), across every Shipit tenant/org pair where at least one configured org omits a webhook secret.

### Likelihood Explanation
The precondition — at least one configured GitHub org in a multi-org Shipit deployment without `webhook_secret` — is explicitly presented as a supported, optional configuration in `docs/setup.md` and the example secrets files, so it is a realistic operational state, not a contrived edge case. The attacker needs no Shipit credentials, no GitHub App secret, and no repository maintainer status — only knowledge of the no-secret org's login and the victim's `owner/repo` full name, both public information. The forged request is a single unauthenticated `POST /webhooks` and is trivially repeatable.

### Recommendation
Derive the organization used for signature verification from the same identifier used for resolving the mutated resource (i.e., verify against the owner parsed from `repository.full_name`, not `repository.owner.login`), or explicitly reject any webhook where `repository.owner.login` does not match the owner segment of `repository.full_name`. Additionally, consider making `webhook_secret` mandatory for every configured organization, since its absence turns `verify_webhook_signature` into a no-op authentication bypass.

### Proof of Concept
minitest plan (`test/controllers/webhooks_controller_test.rb`):
1. Configure two orgs via `secrets.github`: `"no-secret-org"` with `webhook_secret: nil`, and `"victim-org"` with a real `webhook_secret` and `bot_login` set.
2. Create a `Shipit::Repository` for `victim-org/victim-repo` with `review_stacks_enabled: true` and a non-archived review `Stack`.
3. Build a `pull_request` `action=labeled` payload: `repository.owner.login = "no-secret-org"`, `repository.full_name = "victim-org/victim-repo"`, with labels causing `archive?` to be true (per the repo's `provisioning_behavior`).
4. `POST /webhooks` with `X-Github-Event: pull_request` and an arbitrary/garbage `X-Hub-Signature`.
5. Assert response is `200 OK` (not `422`), proving `verify_signature` passed without a valid signature.
6. Assert the equality-that-should-hold is violated: `repository_owner` ("no-secret-org") != owner of `repository.full_name` ("victim-org"), yet the request was accepted.
7. Reload the `victim-org/victim-repo` stack and assert `archived?` changed as directed by the forged payload, proving cross-organization state mutation with no valid authentication for the affected org.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
