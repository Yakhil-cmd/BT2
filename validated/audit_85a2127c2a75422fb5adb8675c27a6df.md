### Title
Vote account `UpdateCommissionBps` instruction removes the anti-front-running commission update rule, allowing a vote account owner to instantly spike commission and steal stake/block rewards - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The external report describes an FERC1155 vault "controller" who can arbitrarily and instantly change a royalty/fee percentage with no cap or delay, then front-run/back-run a large transfer to steal the difference. The structural analog in Agave's vote program is the `commission` percentage on a vote account, which determines how much of stake/block rewards the validator (vote account owner, i.e. the `authorized_withdrawer`) keeps versus what is distributed to delegators. Agave already recognized this exact "front-run the reward payout by spiking commission" risk for the legacy `UpdateCommission` instruction and added a rate-limiting rule (only allow commission increases in the first half of an epoch) plus a one-epoch delay when actually applying commission to reward calculations. However, the newer basis-points commission path (`UpdateCommissionBps`, SIMD-0291/SIMD-0249) explicitly documents that it applies **no such rule**.

### Finding Description
`update_commission` (the legacy percentage path) enforces an update rule that blocks commission *increases* once past the first half of an epoch: [1](#0-0) 

By contrast, `update_commission_bps`, reachable via the `UpdateCommissionBps` instruction, contains only a signer check and explicitly states there is no timing/rate rule: [2](#0-1) 

The instruction is dispatched directly from `vote_processor.rs` once the relevant features (`commission_rate_in_basis_points`, `delay_commission_updates`, optionally `block_revenue_sharing`) are active, requiring only that the `authorized_withdrawer` sign the transaction — an ordinary, unprivileged transaction from the vote account's own owner, structurally identical to Alice being both vault owner and fee controller in the Solidity report: [3](#0-2) 

This lets the vote-account owner set `inflation_rewards_commission_bps` or `block_revenue_commission_bps` to the maximum (10000 bps = 100%) immediately before a reward/revenue distribution event and revert it immediately after — the same "set royalty to 1% to attract volume, then flip to 100% to steal the payment, then flip back" pattern from the external report, but applied to stake/block reward commission instead of NFT royalties.

### Impact Explanation
For `CommissionKind::BlockRevenue`, there is no analogous snapshot/delay mechanism visible in the reward-redemption path (that delay is only wired through `redeem_delegation_rewards` for the inflation-rewards commission using `snapshot_epoch_vote_accounts`/`rewarded_epoch_vote_accounts`, see below), so a commission spike on the block-revenue collector path could translate directly into delegators/collectors receiving far less than expected while the vote-account owner (or its designated commission collector) captures the difference — a direct, unsigned-by-victims transfer of value away from the intended reward recipients, i.e. reward/commission corruption. [4](#0-3) 

### Likelihood Explanation
Note on confidence: I was able to confirm from code comments and the instruction handler that `UpdateCommissionBps` deliberately omits the epoch-timing rule that exists for legacy `UpdateCommission`, and that it requires only the vote account's own `authorized_withdrawer` signature (an unprivileged, ordinary transaction sender in the sense that any user who created/controls a vote account can do this). I was **not able to fully verify**, due to tool failures in the final iteration, whether the `delay_commission_updates`/snapshot mechanism used for `inflation_rewards_commission_bps` also effectively neutralizes the exploit for that specific commission kind (it appears from `calculation.rs` lines 703–724 that inflation-reward commission is read from a delayed snapshot, which would blunt front-running for that path specifically). The `BlockRevenue` commission kind's consumption path (`DepositDelegatorRewards`) was not fully traced to confirm whether it reads a similarly delayed/snapshotted commission value or the live value set by `UpdateCommissionBps`. This uncertainty is material to determining actual exploitability and severity, and would need further verification (ideally in a live Devin session with full read access) before this can be treated as a confirmed, high-confidence exploit rather than a code-comment-supported structural gap.

### Recommendation
Apply the same epoch-timing "commission update rule" (or an equivalent time-lock/rate-limit) used by `update_commission` to `update_commission_bps` for both `CommissionKind::InflationRewards` and `CommissionKind::BlockRevenue`, and confirm that whichever code path consumes `block_revenue_commission_bps` for actual payouts reads a delayed/snapshotted value rather than the live, instantaneously-mutable value, so a vote account owner cannot sandwich a reward/revenue distribution event by spiking and then reverting commission within the same slot/epoch.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern:
1. Create a `VoteStateV4` account, enable `commission_rate_in_basis_points`, `delay_commission_updates`, and `block_revenue_sharing` features.
2. As the `authorized_withdrawer`, submit `VoteInstruction::UpdateCommissionBps { commission_bps: 10000, kind: CommissionKind::BlockRevenue }` immediately before a block-revenue deposit/collection event (e.g., right before `DepositDelegatorRewards` is processed for that vote account) — see dispatch at [5](#0-4) .
3. Let the block revenue distribution occur, capturing 100% commission instead of the previously advertised low rate.
4. Immediately submit another `UpdateCommissionBps` transaction reverting commission back to the original low value, exactly mirroring the `test_CanFrontrunRoyalties` sandwich pattern in the original report.

Existing unit tests such as `test_vote_update_commission` in `vote_processor.rs` confirm the legacy path's signer/value semantics but do not exercise `UpdateCommissionBps`'s lack of a timing rule: [6](#0-5) .

/// Update the vote account's commission
pub fn update_commission<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission: u8,
    signers: &HashSet<Pubkey, S>,
    epoch_schedule: &EpochSchedule,
    clock: &Clock,
    disable_commission_update_rule: bool,
) -> Result<(), InstructionError> {
    let vote_state_result = get_vote_state_handler_checked(vote_account, target_version);
    let enforce_commission_update_rule = !disable_commission_update_rule
        && match vote_state_result.as_ref() {
            Ok(decoded_vote_state) => commission > decoded_vote_state.commission(),
            Err(_) => true,
        };

    if enforce_commission_update_rule && !is_commission_update_allowed(clock.slot, epoch_schedule) {
        return Err(VoteError::CommissionUpdateTooLate.into());
    }

    let mut vote_state = vote_state_result?;

    // current authorized withdrawer must say "yay"
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    vote_state.set_commission(commission);

    vote_state.set_vote_account_state(vote_account)
}

/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
