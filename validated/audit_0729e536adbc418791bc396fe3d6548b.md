### Title
Webhook `sha` lookup is not scoped to the authenticated repository, letting a `status` webhook forge `Status` rows on any stack sharing a commit SHA - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, an unscoped, database-wide lookup that ignores the `repository` field of the webhook payload entirely. Because Git SHAs are content-addressed and identical across a fork and its upstream (or any two stacks that happen to share commit history), an attacker who owns a fork of a victim's repository can send a validly-signed `status` webhook for their own repo/org and have `Commit#create_status_from_github!` write a `Status` row against the victim's stack.

### Finding Description
The claimed binding, stated as an equality that must hold for every persisted row:

`Status.last.stack_id == Repository.from_github_repo_name(payload['repository']['full_name']).stacks.pluck(:id)` (the stack(s) actually owned by the repository whose signature was verified for this request).

Trace:
- `Shipit::WebhooksController#verify_signature` only proves that `request.raw_post` was signed with the GitHub App secret for `repository_owner` (`payload.dig('repository','owner','login')`) — [1](#0-0) . This proves the payload's `repository` field is authentic; it proves nothing about which `Commit`/`Stack` rows in the local DB should be touched.
- `Shipit::Webhooks::Handlers::Handler` even defines a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`, intended for exactly this purpose [2](#0-1) , but `StatusHandler#process` never calls it: [3](#0-2) 
- Instead it does a global, unscoped `Commit.where(sha: params.sha)` across every stack in the installation, then calls `commit.create_status_from_github!(params)` on each match, which persists `stack_id` from that commit's own (correct, but wrongly-selected) `stack_id`: `statuses.replicate_from_github!(stack_id, github_status)` [4](#0-3) .

Root cause: nothing filters the `Commit.where(sha:)` scan to commits belonging to the requester's authenticated repository/stacks. Since Git SHAs are content-addressed, a commit an attacker forked from a victim's public repository has the identical `sha` and will already exist as a `Commit` row on the victim's stack (created when Shipit ingested that push/PR). The attacker's own repository shares that ancestor commit's SHA.

Exploit flow:
1. Attacker forks victim's public repository (or any repo whose history overlaps with the victim's stack's tracked branch), obtaining a shared ancestor commit SHA `S` that already exists as a `Commit` row on the victim's stack.
2. Attacker configures/owns a GitHub App installation or repo webhook on their own fork (their own org), which lets them emit a validly-signed `status` event for `S` with `state: "success"`, `repository.full_name` = attacker's own fork.
3. `verify_signature` succeeds because it only checks the signature against `repository_owner` = attacker's own org — a check the attacker fully controls.
4. `StatusHandler#process` runs `Commit.where(sha: S)`, which returns **both** the attacker's stack's commit row and the victim's stack's commit row (same SHA, different `stack_id`).
5. For the victim's `Commit`, `create_status_from_github!` writes a new `Status` with `stack_id` = victim's stack and `state: "success"`.
6. This status now appears in `stack.commits.reachable.newer_than(...).older_than(...)` scanned by `Commit#blocked?` [5](#0-4) , potentially flipping a previously blocking/pending CI status to `success` and unblocking `deployable?` [6](#0-5)  for a deploy the attacker never had access to.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate the shape/signature of the payload relative to the attacker's own repository; none of them constrain which `Commit`/`Stack` rows the handler is allowed to mutate.

### Impact Explanation
An unprivileged attacker who merely owns a fork (or any repository sharing commit ancestry) can inject a forged `success`/`failure` CI status onto a stack they do not own, directly influencing `Commit#blocked?` / `#deployable?` and thus continuous-delivery/deploy gating on the victim's stack. This is a cross-repository write (`Status` row for one repository's payload mutating another repository's `Commit`/`Stack` state) and can enable an unauthorized deploy to proceed — matching the Critical category "a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy." It is repeatable for any SHA shared between attacker-controlled and victim repositories (trivially achievable via forking), and scales across any number of victim stacks that share that ancestor commit.

### Likelihood Explanation
Preconditions are cheap: the attacker needs (a) to fork or otherwise share commit history with a target public/monitored repository, and (b) the ability to trigger or send a `status` webhook naming their own repo (which any repo owner/installer of a GitHub App/webhook can do for their own repository — no victim secrets needed). No `Shipit.github_teams` membership, no `ApiClient` token, and no knowledge of the victim's `webhook_secret` are required, since signature verification is performed against the attacker's own organization. The main constraint is finding/creating a SHA that already exists as a `Commit` row in the victim's stack, which is straightforward for forks (shared history) or for any workflow where Shipit tracks commits also present upstream.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to only the commits belonging to the authenticated repository, e.g., use the existing `stacks` helper: `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern already available in `Handler#stacks`. Apply the same repository-scoping fix to any other unscoped `Commit.where(sha: ...)` webhook lookups (e.g., `CheckRun`-related handlers) that share this pattern.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create `victim_stack` for repository `victim/repo` and `attacker_stack` for repository `attacker/repo`.
2. Create two `Commit` rows with the **same** `sha` (`"deadbeef" * 5`), one with `stack: victim_stack`, one with `stack: attacker_stack`, simulating a shared fork ancestor.
3. Build a webhook payload whose `repository.full_name` is `"attacker/repo"` (and `repository.owner.login` = attacker org, so `verify_signature` would pass in the controller layer — bypass by calling `StatusHandler.call(payload)` directly per repo convention for handler-level tests) with `sha` = shared sha and `state: "success"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert the equality that should hold but doesn't:
   - `assert_equal attacker_stack.id, Status.last.stack_id` should be false in the buggy code because two `Status` rows are created, and `victim_stack.commits.first.reload.statuses.last.stack_id` will equal `victim_stack.id` even though `payload['repository']['full_name'] == "attacker/repo"`.
   - Explicitly: `assert_equal victim_stack.id, Status.where(commit: victim_commit).last.stack_id` succeeds (proving the victim's stack was mutated) while `Repository.from_github_repo_name(payload.dig('repository','full_name')).stacks.pluck(:id)` does **not** include `victim_stack.id`, demonstrating the broken binding.
   - Additionally assert `victim_commit.reload.blocked?` transitions from `true` (before) to `false` (after), if a prior blocking status exists, showing the deploy-unblocking impact.
