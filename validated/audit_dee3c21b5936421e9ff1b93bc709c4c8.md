### Title
Cross-repository commit-status forgery via sha-only lookup in `StatusHandler#process` defeats the `require_ci: true` deploy gate - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit(s) to attach a GitHub `status` webhook payload to using `Commit.where(sha: params.sha)`, with no filter on the repository named in the webhook payload. [1](#0-0)  Because a valid, correctly-signed webhook only proves the sender controls the *organization/app installation* it came from (`verify_signature` scopes signature verification to `repository_owner`, not to a specific target commit/repo binding), an attacker who owns any repository already onboarded to the same Shipit instance can create a `success` status on a commit sha that is shared with a victim repository (e.g. via a fork sharing history) and have that forged status attached to the victim's `Commit` row, flipping `commit.deployable?` to `true` and defeating the `require_ci: true` gate in `Shipit::Api::DeploysController#create`. [2](#0-1) 

### Finding Description
**Broken binding:** `Status.stack_id/commit_id` written by `StatusHandler#process` should equal `commit.stack.repository` == `payload.repository.full_name`; instead it only enforces `Status.commit.sha == payload.sha`, with no check that the payload's `repository` matches the stack/repo the target `Commit` belongs to.

Trace:
1. `WebhooksController#create` parses the raw JSON body and dispatches to handlers purely by `X-Github-Event` header; `verify_signature` calls `Shipit.github(organization: repository_owner)` and validates `X-Hub-Signature` against that organization's configured secret - this proves only that the sender legitimately controls the named `repository_owner`'s GitHub App installation, not that the sha in the payload "belongs" to that repository. [3](#0-2) 
2. `StatusHandler#process` then does:
   ```ruby
   Commit.where(sha: params.sha).each do |commit|
     commit.create_status_from_github!(params)
   end
   ```
   This queries every `Commit` row in the entire database with a matching `sha`, across all stacks/tenants, and writes a new `Status` for each one using the attacker's `params` (state, description, target_url, context). [1](#0-0) 
3. `Commit#create_status_from_github!` -> `Status.replicate_from_github!(stack_id, github_status)` creates the `Status` scoped to the *victim's* `stack_id` (taken from the matched `Commit`, not from the webhook payload's repository), with `state: 'success'`. [4](#0-3) [5](#0-4) 
4. `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))`, and `success?` is delegated to the aggregated `status` built from `statuses_and_check_runs`. [6](#0-5)  A forged `success` status therefore makes the victim's commit `deployable?`.
5. `Shipit::Api::DeploysController#create` only guards `require_ci` with `commit.deployable?`; once that returns `true` the gate is bypassed and `stack.trigger_deploy` runs. [2](#0-1) 

**Attacker request:** Attacker owns/controls an org+repo already onboarded to the target Shipit instance (satisfying the question's precondition of holding an ApiClient scoped to their own stack). They create a commit status (`POST /repos/{attacker}/{repo}/statuses/{sha}`) on their own repository for a `sha` that is also present in the victim's tracked repository (trivially true for any fork/mirror sharing commit history, or any sha collision the attacker can arrange, e.g. cherry-picked/rebased identical commits). GitHub emits a legitimately-signed `status` webhook to Shipit for the attacker's own repo/org — this passes `verify_signature` because the signature is checked per-organization, not per-target-commit. `StatusHandler` then blindly attaches that status to *every* `Commit` row sharing that sha, including the victim's.

**Why existing guards fail:** `verify_signature` authenticates the sender's identity/org, not the semantic claim "this status describes commit X in repository Y." `drop_unhandled_event`, `ExplicitParameters` schema (`requires :sha`, `:state`, etc.) and model validations on `Status`/`Commit` never cross-check `params.dig('repository','full_name')` against `commit.stack.repository`, so nothing in the chain enforces the missing binding.

### Impact Explanation
A forged status from an unrelated, attacker-controlled repository is written against another tenant's `Commit`, which is explicitly listed as a Critical impact category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). Concretely, it defeats the `require_ci: true` safety gate in `DeploysController#create`, allowing an unauthorized deploy of a commit that never actually passed the victim's CI, on the victim's stack. The attack is repeatable against any commit sha shared between an attacker-controlled repo and a victim's tracked repo (e.g. any public repo the attacker forks), and is not limited to a single stack/tenant.

### Likelihood Explanation
Preconditions: attacker needs an organization/repo already integrated with the target Shipit instance's GitHub App (so `verify_signature` doesn't reject with `GithubOrganizationUnknown`) — consistent with the question's stated precondition that the attacker holds normal, otherwise-authorized access via their own stack. Beyond that, the attacker needs no Shipit secrets, session, or elevated GitHub permissions — only the ability to set a commit status on a repository they own, and for that repo to share a commit sha with the victim's tracked repo (trivially achievable via forks/mirrors of open-source victim repos, which is common). This is entirely feasible with unprivileged GitHub access and is repeatable at will.

### Recommendation
In `StatusHandler#process` (and any other sha-only lookup path, e.g. `check_suite`/check-run handlers if similarly affected), scope the `Commit` lookup to the repository named in the webhook payload, not just the sha, e.g.:
```ruby
def process
  Commit.where(sha: params.sha).select { |c| c.stack.github_repo_name == repository_full_name }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
where `repository_full_name` is read from the raw webhook payload (`payload.dig('repository','full_name')`), and compared against `commit.stack.repository`'s owner/name. Apply the same repository-binding check anywhere a `Commit`/`CheckRun` is looked up solely by `sha` from webhook input.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`-style, using existing fixtures):
1. Create two stacks, `victim_stack` (repo `victim/repo`) and `attacker_stack` (repo `attacker/repo`), each with a `Commit` sharing the identical `sha` value (simulating a forked/shared history commit).
2. Assert baseline: `victim_commit.deployable?` is `false` (no statuses yet) — left side of binding: `Status.stack_id` should only be created when `payload.repository == commit.stack.repository`; right side: no such status exists.
3. Invoke `Shipit::Webhooks::Handlers::StatusHandler.new.call(params)` (or POST to `/webhooks` with a validly-signed payload for `attacker/repo`) with `sha: shared_sha, state: 'success', repository: { full_name: 'attacker/repo' }`.
4. Assert `victim_commit.reload.deployable?` becomes `true` — proving the equality is violated (status keyed only by sha, not by repository).
5. As `Shipit::Api::DeploysController` integration test: POST `/victim_stack_id/deploys` with `sha: shared_sha, require_ci: true` using an ApiClient authorized only for `victim_stack`; assert response is `202 Accepted` instead of the expected `422`/param_error "Commit is not deployable", confirming the bypass end-to-end.
