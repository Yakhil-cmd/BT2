## Title
Attacker can inflate `storage.assocUnstableMessages` with cheap units to trigger unbounded O(n) scans on every AA `data_feed`/`in_data_feed` evaluation, degrading unit validation network-wide - (File: `data_feeds.js`)

### Summary
`data_feeds.js` implements two functions, `dataFeedExists()` and `readDataFeedValue()`, that are invoked whenever an AA formula uses `data_feed[[...]]` or `in_data_feed[[...]]` while the queried oracle's units may still be unstable (`bAA`/`bIncludeUnstableAAs` path). Both functions do a full `for (var unit in storage.assocUnstableMessages)` scan over **every currently-unstable unit in the whole DAG**, regardless of the requested oracle address, before falling back to the indexed kvstore lookup. Since any unprivileged user can post many small/cheap units, they can keep this in-memory unstable set large, making every AA trigger elsewhere in the network that evaluates a `data_feed`/`in_data_feed` formula pay a cost proportional to the total number of currently unstable units, not to the specific oracle being queried.

### Finding Description
`dataFeedExists()` iterates the full `assocUnstableMessages` map for every AA-context data-feed existence check: [1](#0-0) 
and `readDataFeedValue()` does the same unconditionally when `bIncludeUnstableAAs` is set: [2](#0-1) 

Both loops iterate `for (var unit in storage.assocUnstableMessages)`, dereference `storage.assocUnstableUnits[unit] || storage.assocStableUnits[unit]`, and then `.forEach()` over every message of that unit — this is done for *every unstable unit in the whole system*, not just units authored by the oracle addresses being queried (`arrAddresses`). The oracle-address filter (`_.intersection(arrAddresses, objUnit.author_addresses)`) is only applied *after* the full-map iteration has already begun, so the cost of the scan is `O(number_of_unstable_units × messages_per_unit)` regardless of the oracle.

This function is reached from the AA formula evaluator whenever any AA in the network posts a trigger response that uses `data_feed[[...]]` or `in_data_feed[[...]]`: [3](#0-2) [4](#0-3) 

Because units can be posted cheaply (small payload, minimal byte fee), an unprivileged attacker can keep posting many trivial units continuously. As long as they remain unstable (which typically requires witnessing progress across multiple main-chain indices, not an attacker-controlled event), `storage.assocUnstableMessages` stays inflated. Every node in the network, while validating *any* unit that triggers *any* AA using `data_feed`/`in_data_feed`, then pays for a full scan over this inflated unstable set — this is analogous to the reported pattern where cheap, repeated user actions inflate an array that is later iterated in an unbounded loop on a hot path (protection purchases inflating `activeProtectionIndexes`, scanned during premium accrual/capital locking).

### Impact Explanation
This is a shared, node-wide resource: the cost is not borne only by the attacker's own units but by every AA trigger execution across the network that touches `data_feed`/`in_data_feed` while any oracle's recent posts are unstable. If the attacker sustains a high rate of cheap unit posting, the unstable set can be kept large, causing all such AA evaluations network-wide to slow down proportionally, directly consuming validation resources on every full node and creating a shared performance bottleneck during unit validation/stabilization — the closest available impact bucket to "network unable to confirm new units" in a DAG-based ledger with no gas metering.

### Likelihood Explanation
Likelihood is moderate-to-high in networks with many active AAs using data feeds: an attacker only needs to author cheap units to keep the unstable set inflated; this doesn't require any special privilege, key, or protocol bypass — it only requires paying standard byte fees for many small units, similar to the "cost of attack purely gas fees" framing in the original report.

### Recommendation
Filter `storage.assocUnstableMessages` by author address before iterating (e.g., maintain or query an index of unstable units keyed by author address so the scan is bounded by units authored by the specific oracle addresses requested), instead of scanning the entire global unstable-unit map for every data-feed lookup.

### Proof of Concept
1. Deploy/observe an AA that evaluates `data_feed[[oracles="X", feed_name="f"]]` or `in_data_feed[[...]]` in its formula (a common oracle-consuming pattern).
2. As an unprivileged actor, continuously post many small, low-cost units to the DAG (unrelated to the oracle) so that `storage.assocUnstableMessages` remains large before those units stabilize.
3. Trigger the AA (or wait for organic triggers). Each trigger evaluation of `data_feed`/`in_data_feed` executes the `for (var unit in storage.assocUnstableMessages)` loops shown in `data_feeds.js` lines 34-97 and 205-274, whose cost scales with the attacker-inflated unstable-unit count rather than with the number of relevant oracle posts.
