### Title
`StatusHandler#process` mutates commits across arbitrary stacks by matching only on `sha`, ignoring `repository`/`stack` scoping - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` queries `Commit.where(sha: params.sha)` and calls `commit.create_status_from_github!(params)` on every match without ever calling the base `Handler#stacks`/`repository_name` scoping that other handlers use. Because GitHub commit SHAs are content-addressed and are frequently shared across repositories that fork/mirror/share history, a validly GitHub-signed webhook (signed against the real `webhook_secret` of *any* onboarded org, for *any* repository the attacker owns or controls within that org's installation) can write a forged commit status onto a commit belonging to a completely unrelated stack/repository, as long as the SHA matches.

### Finding Description
The broken binding is:
`stacks reachable via repository_name (webhooks_controller/Handler#stacks, empty when Repository.from_github_repo_name(repository_name) is nil)` **should equal** `the set of commits actually mutated by StatusHandler#process`.

They do not. `Handler#stacks` computes `Repository.from_github_repo_name(repository_name)&.stacks || Stack.none` [1](#0-0) , but `StatusHandler#process` never calls it:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [2](#0-1) 

`Commit.where(sha:)` has no stack/repository predicate at all, so any commit row anywhere in the database sharing that SHA is loaded and mutated via `create_status_from_github!`, which writes into `statuses` scoped to that commit's *own* `stack_id` [3](#0-2) , and that status creation triggers `schedule_continuous_delivery` and `enable_ci_on_stack` hooks on the real victim stack [4](#0-3) .

The controller-level guard, `verify_signature`, only authenticates that the request is a real GitHub delivery signed by the org named in `payload.dig('repository','owner','login')` - it never checks that the org/repo actually owns the commit being targeted:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
``` [5](#0-4) 

Exploit flow: the attacker controls (owns, or has push access to) some repository that is covered by an onboarded org's GitHub App/webhook installation (a very common "install app on all repos" org configuration), and that repository shares a commit SHA with a commit belonging to a completely different, Shipit-tracked stack (e.g. via forking/mirroring/re-pushing identical git history - SHAs are deterministic from content+parents+metadata, so a fork or recreated history naturally reproduces the same SHA). The attacker sets a commit status on their own repo for that shared SHA (an ordinary, unprivileged repo-owner action). GitHub genuinely signs and delivers this `status` webhook using the real `webhook_secret` for the org - `verify_signature` passes because the signature is authentic for *that org*, even though the payload's `repository.full_name` has nothing to do with the victim's stack. `StatusHandler#process` then finds and mutates every `Commit` row with that SHA, regardless of stack/repository, unlike every other handler in the codebase which is scoped through `stacks`/`repository_name`.

### Impact Explanation
The attacker can inject arbitrary CI status states (`success`/`failure`/`pending`/`error`, target URLs, descriptions) onto commits belonging to any stack whose commit happens to share a SHA with a repository the attacker controls under a signed org. A forged `success` status can flip `Commit#deployable?` (`success? && !blocked?`) [6](#0-5) , triggering `schedule_continuous_delivery`/merge-request processing on a stack the attacker has no relationship to - i.e. a payload from one repository mutating another repository's stack/commit state and potentially causing an unauthorized deploy. This is repeatable against any commit SHA the attacker can reproduce/control, across every stack in the database sharing that SHA, matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy").

### Likelihood Explanation
Requires: (1) at least one onboarded GitHub org configured in `Shipit.github_apps`/`Shipit.github(organization:)` with a webhook pointed at Shipit, and (2) the attacker owning/controlling a repository under that org's installation whose commit history shares a SHA with a Shipit-tracked commit (achievable via forking or history recreation, not a SHA1 collision attack). Given many orgs install GitHub Apps org-wide ("all repositories") and forking/history-sharing across repos in the same org is routine, this is feasible without needing any Shipit secret, session, or API token - the attacker never needs `webhook_secret` itself, GitHub signs it for them.

### Recommendation
Scope `StatusHandler#process` (and any other handler bypassing `Handler#stacks`) to only mutate commits whose `stack` belongs to the repository identified in the webhook payload, e.g. filter via `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, mirroring the pattern used by other handlers that call `stacks`/`repository_name`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb (conceptual)
test "process mutates commits belonging to unrelated stacks when SHA collides" do
  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit)

  # Simulate attacker's repo being entirely unknown to Shipit
  Shipit::Repository.stubs(:from_github_repo_name).with('attacker/evil').returns(nil)

  payload = {
    'sha' => victim_commit.sha,
    'state' => 'success',
    'repository' => { 'full_name' => 'attacker/evil', 'owner' => { 'login' => 'onboarded-org' } }
  }

  assert_difference -> { victim_commit.statuses.count }, 1 do
    Shipit::Webhooks::Handlers::StatusHandler.call(payload)
  end
end
```
This demonstrates: LHS (`stacks` reachable via `repository_name` = `Stack.none`, since `Repository.from_github_repo_name('attacker/evil')` is `nil`) vs RHS (`victim_commit.statuses.count` increases) - the two sides diverge, proving `StatusHandler#process` ignores repository identity entirely.
