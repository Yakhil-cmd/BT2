### Title
Path traversal via unsanitized asset name in `filepath.Join` - (destinationWriter).Copy - (File: pkg/cmd/release/download/download.go)

### Summary
`gh release download` writes each downloaded asset to a path built by `filepath.Join(w.dir, name)` inside `makePath`, and `name` for ordinary (non-archive) assets is the attacker-controlled GitHub release asset `Name` field, used verbatim without sanitization. `filepath.Join`/`filepath.Clean` collapse `..` segments syntactically but do not confine the result to `w.dir`, so a release asset published with a name like `../../.bashrc` can write outside the destination directory.

### Finding Description
The write path is constructed in `makePath`: [1](#0-0) 
and used unchanged by `Copy`, which then `os.MkdirAll`s the parent directory and opens/creates the file at that path: [2](#0-1) 

For normal (non-archive) assets, the `name` passed into `Copy`/`Check` is `a.Name`, taken directly from the release's asset list and forwarded into `downloadTarget.name` with no validation of `..`, absolute path, or drive-letter/UNC forms: [3](#0-2) [4](#0-3) 

The only sanitization present in this file is `isWindowsReservedFilename`, which checks for reserved device names like `CON`/`PRN`, not path traversal, and `filepath.Base(serverFileName)` used only for the archive/Content-Disposition case (`len(fileName) == 0` branch), which strips path separators for that one code path but does not apply to normal asset names: [5](#0-4) 

Because the fix in the archive branch (`filepath.Base`) is not applied to the asset-name branch, an attacker who can publish a release (repo owner, or a public fork release) with an asset whose name contains `../` segments (GitHub's asset-upload API does not obviously forbid slashes in the display `name` field for this attack, and this is unverified/unconfirmed by the visible code — no upload-side allowlist was found in this codebase) can cause the resolved `fp` in `Copy` to escape the destination directory chosen with `--dir`/`-D` (which frequently defaults to `.`, the user's current working directory). `filepath.Join` and `Clean` normalize but never verify the result remains under `w.dir`.

### Impact Explanation
If exploitable, this allows arbitrary file write/overwrite outside the intended download directory when a victim runs `gh release download` against an attacker-controlled or attacker-contributed release, potentially overwriting startup files (`.bashrc`, shell profiles) or other files reachable by traversal from the current working directory, which can escalate to code execution. This matches an Immunefi "arbitrary file write" critical-severity impact class if the asset name traversal is actually accepted by the GitHub asset-upload pipeline.

### Likelihood Explanation
Preconditions: the attacker must be able to publish a release asset with a traversal-containing name, and the victim must run `gh release download` (optionally targeting `.` as the default output directory, which is common) against that release. Whether GitHub's release-asset upload API accepts and preserves `/`, `..`, or backslash-drive-letter characters in asset names could not be confirmed from this repository's code, since asset upload/naming validation is server-side (GitHub.com), not part of this client codebase. This uncertainty affects the actual exploitability and should be validated against GitHub's real asset-upload constraints before treating this as a confirmed, exploitable bug.

### Recommendation
In `makePath`/`Copy`, after computing `fp := filepath.Join(w.dir, name)`, resolve both `w.dir` and `fp` with `filepath.Abs` (and ideally `filepath.EvalSymlinks` on the existing base dir), and verify `fp` remains prefixed by the resolved base directory (using a proper prefix check with a trailing separator, not naive `strings.HasPrefix`) before proceeding to `MkdirAll`/`OpenFile`. Additionally, apply the same `filepath.Base(name)` (or explicit rejection of `..`, absolute, and drive/UNC-prefixed names) sanitization used for archive filenames to the ordinary asset-name branch, so both branches are protected consistently.

func (w destinationWriter) Copy(name string, r io.Reader) (copyErr error) {
	fp := w.makePath(name)
	if fp == "-" {
		if w.allowEscapes {
			_, copyErr = io.Copy(w.stdout, r)
			return
		}
		copyErr = iostreams.CopyGuardedContent(w.stdout, r, w.isTTY)
		if binErr, ok := errors.AsType[iostreams.BinaryTerminalError](copyErr); ok {
			copyErr = fmt.Errorf("%w; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway", binErr)
		} else if errors.Is(copyErr, iostreams.ErrEscapeSequence) {
			copyErr = errors.New("the asset contains terminal escape sequences; use `--output` to save it to a file, or pass --allow-escape-sequences to output it anyway")
		}
		return
	}
	if copyErr = w.check(fp); copyErr != nil {
		return
	}

	if dir := filepath.Dir(fp); dir != "." {
		if copyErr = os.MkdirAll(dir, 0755); copyErr != nil {
			return
		}
	}

	var f *os.File
	if f, copyErr = os.OpenFile(fp, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644); copyErr != nil {
		return
	}
