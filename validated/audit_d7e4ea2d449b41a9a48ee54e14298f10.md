### Title
Unauthenticated public access to `/events` Pubsubstub stream exposes live stack/task update broadcasts - ([File: config/routes.rb])

### Summary
`config/routes.rb` mounts `Pubsubstub::StreamAction.new` directly at `/events` as a bare Rack endpoint, bypassing the Rails controller stack entirely. Since `Shipit::Authentication#force_github_authentication` is a `before_action` only included via `Shipit::ShipitController` (and `Shipit::Api::BaseController`), it never runs for this mounted Rack app, so any unauthenticated client can subscribe to `channels[]=stack.<id>` and receive live broadcasts published via `Pubsubstub.publish` (e.g., `Stack#broadcast_update`, task/deploy status pushes).

### Finding Description
The broken binding: every other response containing stack/task data is gated by `current_user.logged_in? && current_user.authorized?` inside `force_github_authentication` [1](#0-0) , included only through `ShipitController` [2](#0-1) . However `/events` is mounted as `mount Pubsubstub::StreamAction.new, at: "/events", as: :events` [3](#0-2) , which is a plain Rack endpoint (not a subclass of `ApplicationController`), so this `before_action` never executes for requests to `/events`. There is no other `before_action`, middleware, or route constraint checked for this mount in `config/routes.rb` or `lib/shipit/engine.rb` — the engine initializer only sets `Pubsubstub.redis_url = Shipit.redis_url.to_s` [4](#0-3) , with no auth wiring for the stream endpoint.

Exploit flow: an unauthenticated attacker sends `GET /events?channels[]=stack.<id>` (or `stack.<id>.something`, matching whatever channel names `Stack`/`Deploy`/`Commit`/`Status` publish to) with no session cookie and no API token. Because the request never passes through `ShipitController`/`Authentication`, it is accepted by `Pubsubstub::StreamAction` and the attacker begins receiving any messages published to that channel via `Pubsubstub.publish`, which include live stack/task/deploy status updates. Stack ids are small sequential integers, trivially enumerable.

### Impact Explanation
An internet-wide unauthenticated attacker can subscribe to live update streams for arbitrary stacks by guessing/enumerating stack ids, exposing task status, deploy progress, and other stack-state broadcasts without any authentication or authorization check — this is an unauthenticated read of stack/task update streams, matching the "High" impact category explicitly listed in the rules (unauthenticated read of stack state, task streams or deploy output). It is repeatable against every stack in the installation since the mount is completely un-gated engine-wide, not scoped to one repository/tenant.

### Likelihood Explanation
No special configuration is required: the mount exists in `config/routes.rb` unconditionally whenever the engine is loaded, requires no secrets, tokens, or team membership, and costs the attacker only a single HTTP GET request. This makes the finding highly likely/trivial to exploit as long as the deployed instance uses the engine's default route mounting (as instructed to assume).

### Recommendation
Wrap the `/events` mount behind an authenticating Rack middleware or a controller action that enforces `force_github_authentication`/`authorized?` before delegating to `Pubsubstub::StreamAction`, and validate that the requested `channels[]` correspond to a stack/task the authenticated user is authorized to view (mirroring `require_permission!`/`stacks` scoping used elsewhere).

### Proof of Concept
```ruby
# test/integration/events_stream_authentication_test.rb
require 'test_helper'

module Shipit
  class EventsStreamAuthenticationTest < ActionDispatch::IntegrationTest
    setup do
      @stack = shipit_stacks(:shipit)
    end

    test "unauthenticated request to /events can subscribe to a stack channel without redirect" do
      # No session[:user_id] set, no API token, no team membership.
      get "/events", params: { "channels[]" => "stack.#{@stack.id}" }

      # Binding under test: response should have been redirected to github_authentication_path
      # (as every other Shipit::ShipitController action does), matching the behavior of
      # force_github_authentication for an unauthenticated user.
      refute_equal 302, response.status, "expected /events to require authentication like other routes"
      refute_includes response.headers["Location"].to_s, github_authentication_path
      # Instead the stream is accepted directly by Pubsubstub::StreamAction:
      assert_includes [200, 101], response.status
    end
  end
end
```
This demonstrates that `/events` (mounted via `Pubsubstub::StreamAction.new` in `config/routes.rb`) is reachable and accepts channel subscriptions without the `force_github_authentication` redirect that gates every other Shipit route.
