### Title
Unauthenticated `light/dry_run_aa` race condition causes crash via concurrent unlocked mutation of global unit/state caches - (File: aa_composer.js)

### Summary
The `light/dry_run_aa` network command lets **any connected peer** (no signature, no fee, no special role — analogous to an unprivileged "Viewer") invoke `aa_composer.dryRunPrimaryAATrigger()` on demand. Unlike every other code path that touches AA execution and the shared in‑memory unit/state caches, `dryRunPrimaryAATrigger()` takes **no mutex lock** at all, while it mutates the same global associative maps (`storage.assocStableUnits`, `assocUnstableUnits`, `assocBestChildren`, `assocCachedUnits`, `objValidationState.assocBalances`, etc.) that `handleAATriggers()` (protected by `mutex.lock(['aa_triggers'])`) and `writer.saveJoint()` (protected by `mutex.lock(["write"])`) also mutate. Sending concurrent `light/dry_run_aa` requests (or one such request overlapping with a real, stabilizing AA trigger) causes interleaved reads/writes/deletes on these shared maps, which can throw uncaught `Error`s in async callbacks (e.g. "AA not found?"/`objUnitProps` undefined), crashing the whole node process.

### Finding Description
`dryRunPrimaryAATrigger` is exported and reachable from the network layer without authentication: [1](#0-0) 

It runs `handleTrigger` directly against the live, process‑wide storage caches, with **no `mutex.lock` call anywhere in the function**, unlike its sibling `handleAATriggers`, which explicitly serializes execution with `mutex.lock(['aa_triggers'], ...)`: [2](#0-1) [3](#0-2) 

`handleTrigger`/`updateInitialAABalances` reads and writes `objValidationState.assocBalances[address]` and touches `storage.assocStableUnits`/`assocUnstableUnits` (confirmed by the test suite explicitly snapshotting and diffing these exact maps after every dry run, and calling `fixCache()`/`revertResponsesInCaches()` to restore them): [4](#0-3) [5](#0-4) 

Because `dryRunPrimaryAATrigger` performs several asynchronous DB round trips (`db.takeConnectionFromPool`, `conn.query("BEGIN")`, `readLastStableMcUnit`, `insertFakeOutputsIntoMcUnit`) before it ever mutates the caches, the Node.js event loop can freely interleave a second, concurrently arriving `light/dry_run_aa` request (or a real AA trigger execution via `handleAATriggers`/`writer.saveJoint`, which use a *different* mutex key and therefore do not block dry runs at all). Two interleaved executions can:
- read stale/partial `assocStableUnits`/`assocBalances` state that the other invocation is in the middle of mutating,
- have one invocation's `revertResponsesInCaches`/rollback clobber state that the other invocation still depends on,
- hit `throw Error(...)` guards that assume single-threaded, serialized access, e.g. `handlePrimaryAATrigger`'s `if (!objUnitProps) throw Error('...unit not found in cache')`.

Any such thrown error inside these async callback chains is not funneled through a `try/catch` back to the requesting websocket handler — it propagates as an uncaught exception in the Node.js event loop and terminates the process, exactly matching the reported "fatal map access error" causing full service unavailability that requires a restart.

### Impact Explanation
A crash of the full node process is a severe availability issue: it stops broadcast/relay of new units, stops AA trigger execution, and requires an operator to notice and restart the node. Because `light/dry_run_aa` is available to any connected peer with no cost (it doesn't require posting/signing a real unit), this is trivially and repeatedly triggerable, resulting in a persistent denial of service against the affected hub/full node.

### Likelihood Explanation
The command is reachable with a simple, free, unauthenticated websocket request (`light/dry_run_aa`) that only requires a syntactically valid AA address and trigger object; no signature or balance is needed. Firing multiple such requests concurrently (or timing a dry run against a heavily-used AA around real trigger execution) is straightforward for anyone able to open a websocket connection to the node, making the race easy to reproduce.

### Recommendation
Serialize `dryRunPrimaryAATrigger` (and, more generally, any code path that mutates `storage.assocStableUnits`/`assocUnstableUnits`/`assocBalances`) behind the same mutex key(s) used by `handleAATriggers`/`writer.saveJoint` (e.g. `mutex.lock(['write'])` or a dedicated `'dry_run'` lock that is mutually exclusive with `'write'`/`'aa_triggers'`), or make dry runs operate purely on cloned/copy-on-write cache snapshots so they never touch the live global caches. Additionally, wrap the `light/dry_run_aa` handler so any exception thrown deep inside `handleTrigger`/`aa_composer` internals is caught and converted into an error response instead of propagating as an uncaught exception that kills the process.

### Proof of Concept
1. Connect two websocket clients to a full node exposing `light/dry_run_aa` (no special credentials needed).
2. From both clients, simultaneously send `light/dry_run_aa` requests targeting the same (or interacting) AA address with valid trigger payloads, e.g.:
```json
["request", {"command":"light/dry_run_aa","params":{"address":"<AA_ADDRESS>","trigger":{"outputs":{"base":10000},"data":{}}}}]
```
   sent from both connections back-to-back with no delay, repeated in a loop.
3. Because `dryRunPrimaryAATrigger` takes no lock, the two calls' asynchronous DB/callback chains interleave and mutate/revert the shared `storage.assocStableUnits`/`assocBalances` caches out of order.
4. Eventually one invocation hits a state-dependent `throw Error(...)` (e.g., unit/definition lookup that assumed serialized cache state), which is not caught anywhere in the async chain, crashing the Node.js process and taking down the entire node until manually restarted.
