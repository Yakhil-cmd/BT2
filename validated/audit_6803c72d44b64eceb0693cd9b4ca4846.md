### Title
`StatusHandler#process` writes commit statuses without scoping to the webhook's repository, enabling cross-repository status forgery - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` across the entire Shipit database instead of scoping to the webhook's own repository via the `stacks`/`repository_name` helper that sibling handlers use. A webhook that passes HMAC verification for Repository A's registered secret can therefore mutate a commit belonging to Repository B simply by naming Repository B's sha in the `sha` field, since GitHub's Status API does not validate that a `sha` actually belongs to the repository the status is posted against.

### Finding Description
The broken binding: HMAC verification succeeding for Repository A's `webhook_secret` should imply authorization to mutate only Commits belonging to Repository A's Stacks (`repository.full_name == "A" → mutate only Commits where commit.stack.repository.full_name == "A"`).

`Shipit::WebhooksController#verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) solely by `repository_owner`, derived from the *unsigned* payload (`params.dig('repository','owner','login')`), and calls `github_app.verify_webhook_signature` [1](#0-0) [2](#0-1) . This only proves the request came from an entity that knows the secret for that *organization/app*; it says nothing about which specific repository's records may be touched.

`Shipit::Webhooks::Handlers::Handler` exposes a `stacks` helper that scopes to the repository named in the payload: `Repository.from_github_repo_name(repository_name)&.stacks` [3](#0-2) . Other handlers correctly use this scope, e.g. `PushHandler#process` (`stacks.not_archived.where(branch:)`) [4](#0-3)  and `CheckSuiteHandler#process` (`stacks.where(branch: ...)`) [5](#0-4) .

`StatusHandler#process`, however, ignores `stacks`/`repository_name` entirely and queries the global `Commit` table by `sha` only: [6](#0-5) 

Because commit SHAs are 40-hex-character git object ids that are public and not secret, and because GitHub's Commit Status API (`POST /repos/{owner}/{repo}/statuses/{sha}`) does not require `sha` to correspond to a commit actually present in `{owner}/{repo}`, an attacker who has push/write access to their own Repository A (a repo they legitimately own and which is legitimately onboarded to the same Shipit instance/GitHub App) can:
1. Discover a target commit sha belonging to Repository B (public repos, or any repo whose commits are visible to the attacker).
2. Call GitHub's status API against Repository A using that foreign sha.
3. GitHub fires a genuinely-signed `status` webhook to Shipit, with `repository.full_name = "attacker/repoA"` (truthful) and `sha` = the victim's sha in Repository B.
4. `verify_signature` succeeds completely legitimately (Repository A's real secret, real signature).
5. `StatusHandler#process` matches `Commit.where(sha: params.sha)` against every stack/repository in the Shipit instance, and creates/updates a `Status` on Repository B's commit via `commit.create_status_from_github!(params)` [7](#0-6) .

`Commit#add_status` (invoked transitively) emits `commit_status`/`deployable_status` hooks and, critically, calls `stack.schedule_merges if new_status.pending? || new_status.success?` [8](#0-7) , which can trigger Stack B's continuous-delivery/merge machinery based on a forged "success" status the attacker fully controls, despite never authenticating against Stack B at all.

None of the existing guards prevent this: `verify_signature` only authenticates the organization/app tied to the (truthful) `repository_owner` in the payload, not the specific repository whose records get mutated; the `ExplicitParameters` schema for `StatusHandler` only requires `sha`/`state`/etc. types, with no repository-ownership check; and there is no `stacks`/`repository_name` filter applied before the `Commit.where(sha:)` lookup.

### Impact Explanation
An attacker with only write access to a repository they legitimately control (Repository A) can inject a `Status` record onto a commit belonging to an unrelated repository/stack (Repository B) that they are not authorized to write to, purely by naming a foreign sha. This matches "a payload for one repository mutating another's ... commit" (Critical). Because `add_status` can trigger `schedule_merges`/continuous delivery job scheduling based on this forged status, the blast radius extends to influencing deploy/merge decisions for Stack B without any authorization over Stack B. The attack is repeatable against any commit sha visible to the attacker (all public repos, or private repos the attacker can otherwise learn shas for), across every stack configured on the same Shipit instance/GitHub App.

### Likelihood Explanation
Preconditions: attacker needs push/write access to at least one repository (Repository A) that is legitimately registered with a Shipit-connected GitHub App, and knowledge of a target commit sha in Repository B (trivial for public repos, or any repo whose commit history/PRs the attacker can view). No Shipit credentials, session, API token, or `webhook_secret` are ever needed — the exploit relies entirely on GitHub's own Status API design (which does not validate that `sha` belongs to the target repo) combined with Shipit's missing repository-scoping in `StatusHandler`. This is a low-cost, fully repeatable attack requiring no privileged Shipit access.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, mirroring `PushHandler`/`CheckSuiteHandler`, e.g. `stacks.each { |stack| stack.commits.where(sha: params.sha).each { |c| c.create_status_from_github!(params) } }` instead of the global `Commit.where(sha: params.sha)`.

### Proof of Concept
Minitest plan (integration-level, `test/controllers/webhooks_controller_test.rb` style, no live GitHub):
1. Create two stacks/repositories, `repo_a` (`shopify/repo-a`) and `repo_b` (`other/repo-b`), each with a `github.webhook_secret` configured for their respective (possibly same) organization app.
2. Create a `Commit` under `repo_b`'s stack with a known `sha`.
3. Build a `status` payload with `repository.full_name = "shopify/repo-a"` (truthful) and `sha` equal to `repo_b`'s commit sha.
4. Compute a genuinely valid `X-Hub-Signature` using `repo_a`'s real `webhook_secret` (not stubbed, not bypassed).
5. POST to `/webhooks` with `X-Github-Event: status` and the valid signature.
6. Assert response is `200 OK` (signature accepted).
7. Assert `repo_b`'s `Commit#statuses.count` increased by 1 and the new status matches the forged payload — demonstrating that Repository A's legitimate signature caused a write on Repository B's commit, violating `repository_owner-that-signed == repository whose Commit is mutated`.
