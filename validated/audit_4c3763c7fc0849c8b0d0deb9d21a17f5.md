### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the commits to update purely by `sha`, with no scoping to the repository/stack that authenticated the webhook. An attacker who owns any GitHub repository wired to the same Shipit instance can emit a validly-signed `status` webhook for a commit sha that they control, and `Commit.where(sha: params.sha)` will apply that status to every `Commit` row across all stacks sharing that sha, including a victim's stack. If the victim stack has `continuous_deployment: true`, this can flip `Commit#deployable?` to true and trigger an unauthorized deploy of the victim's own commit.

### Finding Description
The broken binding is: `repository that authenticated the webhook (via Shipit.github(organization: repository_owner) + X-Hub-Signature)` == `repository/stack owning the Commit row whose status is mutated`. Tracing the code shows this does **not** hold.

- `WebhooksController#verify_signature` only checks that the HMAC signature is valid for the organization named in the payload's `repository.owner.login` [1](#0-0) . It authenticates *that the sender legitimately controls repository X*, not that repository X is the repository whose commits are being mutated.
- `StatusHandler#process` then does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
This query has no `stack_id`, `repository_id`, or repository-name filter whatsoever — it matches *every* `Commit` record in the entire Shipit database that shares the given `sha`, regardless of which stack/repository it belongs to.
- `Commit#create_status_from_github!` -> `add_status` creates the `Status` record and, via the model's `after_commit`, `Commit#schedule_continuous_delivery` is invoked, which checks `deployable? && stack.continuous_deployment? && stack.deployable?` and, if true, enqueues `ContinuousDeliveryJob.perform_later(stack)` [3](#0-2) .
- `Commit#deployable?` is `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [4](#0-3) , where `success?` is delegated to `status`, which is computed from `statuses_and_check_runs` on that same commit row [5](#0-4) , [6](#0-5) .

Because the commit row is shared across the two repos' identically-shaed commits, an attacker-controlled, correctly-signed status for the attacker's own repository directly and unconditionally mutates the `success?`/`deployable?` truth value of the victim stack's commit — with no repository/stack check anywhere in the path from `StatusHandler#process` through `create_status_from_github!` to `schedule_continuous_delivery`.

None of the existing guards prevent this: `verify_signature` validates the signer owns *a* repo, not that they own *the* repo tied to the target commit; `drop_unhandled_event` only filters by event type; there is no `ExplicitParameters` constraint tying `sha` to a `repository` field for authorization purposes (the schema only requires `sha`, `state`, etc., not a repository identity check against the resolved `Commit`) [7](#0-6) .

### Impact Explanation
An attacker can force the state of a commit (and, if the victim stack is `continuous_deployment: true`, trigger an actual deploy) belonging to a repository/stack they do not control, purely by emitting a signed webhook from their own repository with a colliding sha. This is a "payload for one repository mutating another's stack/commit," and can escalate to an unauthorized deploy — matching the Critical impact category. The blast radius is any stack on the shared Shipit instance whose next undeployed commit's sha happens to collide with a sha the attacker can produce a signed status for.

### Likelihood Explanation
Requires: (1) the attacker owns/controls a GitHub repository already registered as a Shipit stack (or any repo Shipit accepts webhooks for), (2) a sha collision between a commit in the attacker's repo and the victim's next undeployed commit, and (3) the victim stack has `continuous_deployment: true`. Producing an exact sha collision against an arbitrary victim commit is not generically feasible (requires either a genuinely shared commit history/fork scenario or a targeted collision), but the code-level authorization gap itself is unconditional and repeatable: any sha collision — accidental (e.g., shared upstream history/forks) or engineered — is sufficient, and the question's stated precondition (attacker can drive a `status` webhook for a colliding sha) is taken as given.

### Recommendation
Scope the `StatusHandler#process` lookup (and the underlying commit resolution) to the repository that authenticated the webhook, e.g., by joining/filtering `Commit` through `Stack.where(repository: resolved_repository)` before matching on `sha`, so a status can only be applied to commits belonging to stacks whose repository matches the webhook's authenticated repository.

### Proof of Concept
```ruby
test "cross-repo sha collision triggers continuous deployment of victim stack" do
  attacker_stack = shipit_stacks(:attacker)  # repo owned by attacker
  victim_stack   = shipit_stacks(:cyclimse)  # continuous_deployment: true

  colliding_sha = "a" * 40
  attacker_commit = attacker_stack.commits.create!(sha: colliding_sha, message: "attacker commit")
  victim_commit    = victim_stack.commits.create!(sha: colliding_sha, message: "victim's next undeployed commit")

  payload = {
    sha: colliding_sha,
    state: "success",
    context: "ci/attacker",
    repository: { owner: { login: attacker_stack.repository.owner } }
  }

  # simulate a correctly-signed webhook from the attacker's own repo
  assert_enqueued_with(job: Shipit::ContinuousDeliveryJob, args: [victim_stack]) do
    Shipit::Webhooks::Handlers::StatusHandler.new.call(payload.stringify_keys)
  end

  victim_stack.reload
  assert victim_commit.reload.deployable?, "victim commit became deployable from attacker's own repo's status"

  assert_difference -> { victim_stack.deploys.count }, 1 do
    perform_enqueued_jobs
  end
end
```
Both sides of the binding — `repository_owner` authenticated by `verify_signature` (attacker's repo) vs. the repository owning `victim_commit`/`victim_stack` that gets mutated — differ, confirming the vulnerability.
