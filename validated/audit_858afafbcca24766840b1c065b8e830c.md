### Title
Caller-supplied swap route can attach unauthorized token transfers to the victim's signed auth tree, draining wallet funds beyond the swapped amount - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
CVE-2023-21980's class — a low-privileged attacker who needs only victim interaction to turn a routine client call into full compromise — maps directly onto the controller's strategy-swap path. `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept caller-supplied `swap`/`steps` bytes and forward them verbatim to the configured router via `router.execute_strategy(&controller, &amount_in, swap)` [1](#0-0) . The router calls whatever pool addresses the payload names with no allowlist, so a malicious route places attacker-controlled code on the call stack below the victim's `require_auth`. Any `token.transfer(victim, attacker, X)` that code performs is recorded by simulation as a sub-invocation of the victim's own authorization entry and executes if the victim signs the presented tree [2](#0-1) .

### Finding Description
`swap_tokens` grants the router one bounded invocation — `authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in)` — and then verifies only the controller's own balance deltas (`RouterOverspend`, `NoSwapOutput`) [3](#0-2) . Those checks bound the *controller's* exposure to `amount_in`, but they do nothing for the *caller's* authorization scope. The `swap` bytes are opaque to the controller: no venue allowlist, no pool-address validation, no cap on what authorized sub-invocations the victim is asked to sign. Soroban's non-root auth semantics fold a deep `require_auth` (e.g., a token `transfer` from the victim) into the victim's root auth entry for `swap_collateral`. An honest `simulateTransaction` faithfully returns that poisoned tree; a wallet or client that signs it without inspecting every child authorizes an arbitrary transfer out of the victim's wallet — unlimited in token and amount, unrelated to the routed funds. The in-repo test demonstrates this end-to-end: the recorded tree contains `wallet_token.transfer(alice → attacker, WALLET_BALANCE)` as a child of `swap_collateral`, Alice's wallet is emptied while she receives a perfectly fair swap output, and the same route executes when the poisoned tree is signed [4](#0-3) . The project's own threat model concedes "the loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [5](#0-4) .

### Impact Explanation
Theft of user funds. The stolen amount is the victim's whole balance of any token the attacker names — not the swap input, not a slippage fraction. The strategy itself settles correctly (`min_out` met, account risk gates pass, balances measured), so nothing on-chain signals the theft; the only trace is the extra child in the signed auth tree. Every caller of `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, and direct `execute_strategy` is exposed.

### Likelihood Explanation
Requires victim interaction (signing a transaction), matching the CVE's UI:R. Exploitation needs the victim to submit an attacker-influenced route — realistic when routes originate from a compromised or malicious quote source, a phishing frontend, or a tainted `routeXdr` pasted into a builder — and a wallet that signs the simulated auth tree without per-child inspection. The attacker is unprivileged: deploying a rogue "pool" contract and crafting payload bytes costs nothing. That combination puts this at Medium–High rather than purely theoretical, and the protocol already ships a regression test proving the mechanism.

### Recommendation
- Decode the `swap` payload in the controller (or router) and enforce a governance-managed allowlist of venue pool/token addresses, so third-party code cannot ride under the caller's auth — extending the INV-STRAT-03 allowlist model to swap venues.
- At minimum, bound the caller's signature: document and enforce that an honest route produces exactly zero sub-invocations under the caller's controller entrypoint (composed path) or exactly one input `transfer` (direct path), and have the SDK/wallet reject any recorded tree with additional children before signing.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` implements it: `UnlistedPoolRouter.execute_strategy` invokes `route.hop_pool` from the payload [6](#0-5) ; `RogueHopPool.swap` transfers the victim's wallet token to the attacker [7](#0-6) ; the simulation test shows the theft recorded as a child of the victim's `swap_collateral` auth with `alice` balance 0 and `attacker` balance `WALLET_BALANCE`, while her ETH supply credit is the fair output [8](#0-7) ; and the enforcing-mode test confirms the signed poisoned tree executes the transfer [9](#0-8) .

    pub fn execute_strategy(env: Env, sender: Address, total_in: i128, swap_xdr: Bytes) -> i128 {

    }

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
