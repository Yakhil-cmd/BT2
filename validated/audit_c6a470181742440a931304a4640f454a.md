## Title
Webhook signature is verified against `repository.owner.login` while the Stack that gets mutated is selected via the unrelated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and therefore the HMAC secret) used to authenticate an incoming webhook based on `repository_owner`, which is read from `payload.dig('repository', 'owner', 'login')` (or `organization.login`). But every `Handler` subclass (used by `PushHandler`, `StatusHandler`, etc.) resolves the `Stack`/`Repository` to act on from a *different* field in the same JSON body: `payload.dig('repository', 'full_name')`. These two fields are never cross-checked, so a signature that is valid for organization A can be replayed with a payload whose `repository.full_name` points at a repository belonging to organization B.

### Finding Description
`verify_signature` computes the signing organization purely from the payload: [1](#0-0) [2](#0-1) 

Once the signature is accepted, the raw payload is dispatched unchanged to the registered handlers: [3](#0-2) 

Every handler resolves the target `Stack`/`Repository` from `repository.full_name`, a sibling field of `repository.owner.login` that is completely independent of the field used for signature verification: [4](#0-3) 

`PushHandler` uses that repository-scoped `stacks` relation to trigger a GitHub sync for the matching branch: [5](#0-4) 

`Repository.from_github_repo_name` performs a straight DB lookup by owner/name parsed out of `full_name`, with no relation enforced back to `repository.owner.login`: [6](#0-5) 

This reproduces the reward-report's bug class exactly: one field of the payload (`repository.owner.login`) is what the security check (signature verification / `rewardRate` accounting) is bound to, while a *different* field (`repository.full_name`) is what actually gets acted upon (the stack that is synced / the reward recipient). The binding that should hold — "the organization whose secret authenticated this request == the repository being written to" — is broken because nothing enforces `full_name`'s owner segment to equal `owner.login`.

Under Shipit's documented multi-org support, each GitHub organization onboarded onto the instance has its own `app_id`/`installation_id`/`webhook_secret` entry in `secrets.yml`, and that organization's own admins are the ones who created the GitHub App and therefore legitimately know its `webhook_secret`: [7](#0-6) 

An admin of an org that is validly onboarded (org A) can therefore produce a valid `X-Hub-Signature` for org A, but set `repository.full_name` in the payload to `"org-B/victim-repo"`, a repository belonging to a completely different tenant hosted on the same Shipit instance. `verify_signature` passes (it checked org A's secret against org A's owner login), and `PushHandler`/`StatusHandler` then act on org B's stack.

### Impact Explanation
This crosses a repository-isolation boundary between unrelated GitHub organizations hosted on a shared Shipit instance:
- `PushHandler` can force `stack.sync_github(expected_head_sha:)` on a victim stack the attacker has no access to, using a `sha` argument that is entirely attacker-supplied.
- `StatusHandler` (`app/models/shipit/webhooks/handlers/status_handler.rb`) creates commit statuses on `Commit.where(sha: params.sha)` for *any* commit matching that sha with attacker-chosen `state`/`context`/`description`/`target_url`, which is not even scoped by `repository_name` — meaning it can forge CI status ("success"/"failure") on arbitrary commits, directly affecting Shipit's deploy-safety/merge-queue gating logic for a repository the attacker does not own.

This maps to the "cross-repository writes" / unauthorized deploy-influencing category described in the rules, since it lets a legitimately-onboarded-but-otherwise-unprivileged organization forge webhook events attributed to a different organization's repository.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate administrator of *some* GitHub organization already onboarded to the shared Shipit instance (a realistic multi-tenant deployment scenario per `docs/setup.md`'s "Using Multiple Github Applications" section). No GitHub-side spoofing is needed — the attacker computes a correct HMAC using their own known secret and simply changes the `repository.full_name` field of the JSON body before POSTing it directly to `/webhooks`.

### Recommendation
In `WebhooksController#verify_signature` / `Handler`, enforce that the repository resolved for signature-organization selection (`repository.owner.login`) matches the owner segment of `repository.full_name` used to look up the `Stack`/`Repository`, rejecting (422) any payload where they diverge. Additionally, `StatusHandler` should scope its `Commit` lookup by the resolved `repository`/`stacks`, not by a bare, repository-unscoped `sha` match.

### Proof of Concept
1. Organization A is legitimately onboarded to a shared Shipit instance; its admin knows its `webhook_secret` (`secrets.yml` entry for org A).
2. Attacker (org A admin) crafts a push payload body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(webhook_secret_org_a, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` and successfully verifies the signature against org A's secret.
5. `Shipit::Webhooks.for_event('push')` invokes `PushHandler`, whose `repository_name` resolves to `"org-b/victim-repo"` via `payload.dig('repository','full_name')`, matching and mutating org B's `Stack` (`stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`) despite the request having been authenticated solely as org A.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

      webhook_secret:
      private_key:
      oauth:
        id:

    someothergithuborg:
