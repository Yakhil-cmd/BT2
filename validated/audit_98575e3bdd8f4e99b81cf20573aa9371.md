Based on my research, I found a direct analog in the ocore codebase reference AA implementation.

### Title
Uniswap-like AA market maker swap operations execute without a user-specified minimum-return (slippage) check, enabling sandwich attacks - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The reference/sample constant-product market-maker AA in ocore computes the amount of tokens a user receives for a bytes↔asset exchange purely from the AA's current pool balances at trigger time, with no user-supplied `min_amount` (or similar slippage bound) checked against the computed output. This mirrors the reported DODORouteProxy issue where `minReturnAmount` is accepted as a parameter but never validated/enforced, exposing users to sandwich attacks.

### Finding Description
In the "exchange bytes to asset" and "exchange asset to bytes" cases, the AA reads `balance[$asset]` and `balance[base]` at execution time, computes a constant-product price, and unconditionally sends the resulting `$amount` back to the trigger sender — there is no field in `trigger.data`/`trigger.output` that lets the caller specify a minimum acceptable output, and no `bounce()` guard compares the computed amount to any user expectation: [1](#0-0) [2](#0-1) 

By contrast, the "invest in MM" case in the very same AA *does* enforce an exact-ratio check and calls `bounce()` if the actual and expected amounts diverge: [3](#0-2) 
This inconsistency shows the swap paths were not designed with the same protection, exactly analogous to how DODORouteProxy validates `minReturnAmount` in some paths (`mixSwap`, `dodoMutliSwap`) but not in `externalSwap`.

Because AA triggers are ordinary units posted to the DAG and are not atomically bundled with the AA's state read, an attacker who observes a pending swap-trigger unit (before it is stabilized/included) can post a competing trigger of their own (front-run), shifting `balance[$asset]`/`balance[base]` unfavorably, and then post a closing trigger (back-run) to capture the price difference — a classic sandwich attack — since the victim's `if`/`init` formulas re-read `balance[...]` fresh at the time their trigger is finally processed by the AA.

### Impact Explanation
A user swapping through this AA pattern can receive substantially less asset/bytes than expected, with no on-chain mechanism to reject the trade, resulting in direct fund loss to sandwich attackers. Since this is the standard reference pattern for building AMMs on top of ocore's AA engine, any AA author who follows it (as documented/tested in this repo) inherits the exact same unchecked-slippage vulnerability.

### Likelihood Explanation
Likelihood is high wherever this AA pattern (or similar AMMs lacking a `min_amount` guard) is deployed, because sandwiching only requires an attacker to observe a pending unit and post their own units with favorable timing/fees — no privileged network position or protocol bug is needed, consistent with the "AA trigger sender" threat model.

### Recommendation
Require the trigger to supply an explicit minimum acceptable output (e.g., `trigger.data.min_amount`), and `bounce()` the AA execution if the computed `$amount` (or `$issue_amount`) is below that threshold, mirroring the existing ratio-check pattern already used in the "invest in MM" case:
```
if ($amount < trigger.data.min_amount)
    bounce('slippage too high');
```

### Proof of Concept
1. Attacker monitors the network for a pending "exchange bytes to asset" trigger unit sent to the market-maker AA.
2. Attacker posts their own larger swap trigger first (front-run), which is processed by the AA before the victim's, shifting `balance[$asset]`/`balance[base]` and the resulting constant-product price: [4](#0-3) 
3. The victim's trigger is then processed against the worsened pool ratio, and because there is no minimum-amount check, the AA sends the victim a reduced `$amount` without bouncing: [5](#0-4) 
4. Attacker posts a closing trigger (back-run) to restore the pool and realize the arbitrage profit extracted from the victim.
