### Title
Cross-repository status forgery via unscoped `sha` lookup in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves the target commit purely by `Commit.where(sha: params.sha)` with no check that the webhook's `repository.full_name` matches the `stack`/repository that owns that commit [1](#0-0) . Because webhook signature verification only proves the payload came from *some* organization Shipit trusts (`repository_owner`), not that it originated from the specific repository of the commit being updated [2](#0-1) , an attacker who controls any repository tracked under a trusted organization can forge a `success` status onto a commit belonging to a completely different stack/repository, as long as the sha matches.

### Finding Description
The broken binding is: `commit.stack.github_repo_name == payload.repository.full_name` is never checked, when it should be enforced before a status is attached to `commit`.

- `WebhooksController#verify_signature` verifies the payload's HMAC using `Shipit.github(organization: repository_owner)`, where `repository_owner = params.dig('repository','owner','login')` [3](#0-2) . This only proves the request is a genuine GitHub webhook for *an* org-installed repository, it says nothing about which repository within that org the `sha` belongs to.
- `StatusHandler#process` then does a completely global lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) . There is no `stack_id`/repository filter — any `Commit` row anywhere in the database with a matching `sha` gets the forged status attached, regardless of which stack/repository actually owns it.
- `create_status_from_github!` calls `add_status` → `statuses.replicate_from_github!` and, on a state transition to `success`/`pending`, enqueues `ProcessMergeRequestsJob` [4](#0-3) , confirmed by the existing test asserting `ProcessMergeRequestsJob` is enqueued on such a transition [5](#0-4) . This job leads into `MergeRequest#reject_unless_mergeable!`/`all_status_checks_passed?`, which relies on `head.statuses_and_check_runs` (`statuses + check_runs`, with no repository check either) [6](#0-5) .

Exploit flow: attacker owns/pushes to repo X, which is under an org that has a working Shipit webhook (attacker only needs commit + status write access to *some* repo in a trusted org — not the victim's repo). Attacker crafts a commit in repo X with identical tree/parent/author/committer/timestamp metadata to the victim PR's head commit so the resulting SHA-1 is identical (feasible since git commit hashing is fully determined by that metadata, all of which is visible via the GitHub API for the target PR). Attacker posts a real GitHub Commit Status for that sha with `state: success` on repo X; GitHub emits a correctly signed webhook for the org. `WebhooksController#verify_signature` passes (correct org secret). `StatusHandler#process` finds the *victim's* `Commit` row (same sha, different stack) and attaches the forged `success` status to it, since the lookup is sha-only and repo-agnostic.

Existing guards fail because: `verify_signature` authenticates at the organization granularity only, and no code anywhere in `StatusHandler`, `Commit#create_status_from_github!`, or `Status.replicate_from_github!` cross-checks `stack.github_repo_name` against the payload's `repository.full_name`.

### Impact Explanation
A forged `success`/`failure` status can be attached to a commit belonging to a stack/repository the attacker never authenticated against, directly matching the "payload for one repository mutating another's stack, commit" Critical category. If the affected commit is a merge-queue PR head, this pollutes `MergeRequest#all_status_checks_passed?` and can trigger `ProcessMergeRequestsJob` to advance/merge a PR based on a fabricated CI result, i.e., an unauthorized merge. This is repeatable against any commit sha the attacker can reproduce, across any stack tracked by the same Shipit instance/org, not limited to one victim.

### Likelihood Explanation
Requires: (1) the attacker to have legitimate control of at least one repository within an organization that Shipit has configured with a webhook secret (a very low bar — could be their own throwaway repo in an org that allows public repo creation, or an org that installed the shared GitHub App broadly), and (2) the ability to produce a commit with an identical SHA-1 to the victim's PR head, which requires reproducing the exact tree, parents, author, committer, and timestamps — non-trivial but deterministic and achievable for any commit whose metadata is publicly visible (e.g., via GitHub API), especially open-source PRs. `merge_queue_enabled` and a pending PR are also required on the victim stack. The attack costs one crafted commit + one Status API call, and is repeatable.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the webhook's `repository.full_name` (or a resolved `stack_id`) in addition to `sha`, e.g. resolve the `Stack`/`Repository` from `params.repository` first, then only update commits belonging to that stack: `stack.commits.where(sha: params.sha)`. Apply the same repository-scoping to `CheckSuiteHandler`/`RefreshCheckRunsJob` and any other handler that resolves records purely by `sha` without validating repository ownership.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or `webhooks_controller_test.rb`):
1. Create two stacks/repos: `victim_stack` (repo `victim-org/victim-repo`) with a `Commit` fixture of sha `SHA_X`, and `attacker_stack` (repo `attacker-org/attacker-repo`) — both under the *same* trusted organization config (or stub `Shipit.github(organization: ...)` to succeed for the attacker's org) so signature verification passes.
2. Create a second `Commit` under `attacker_stack` also with sha `SHA_X` (simulating the reproduced-hash commit).
3. POST a `status` webhook payload with `sha: SHA_X`, `state: 'success'`, `repository.full_name: 'attacker-org/attacker-repo'`, with a valid signature for that org.
4. Assert (bug present): `victim_stack.commits.find_by(sha: SHA_X).statuses.last.state == 'success'` — i.e., the victim's commit received a status even though the payload's `repository` never named `victim-org/victim-repo`.
5. Assert (fix expected): after scoping the lookup by stack/repository, the victim commit's status count is unchanged (`assert_no_difference` on `victim_commit.statuses.count`), proving the forged webhook from the unrelated repo cannot mutate the victim stack's commit.
