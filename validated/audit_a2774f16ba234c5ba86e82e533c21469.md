### Title
StatusHandler mutates `Commit` rows across repositories without checking `repository_owner`/`repository_name` used for signature verification - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App to verify the HMAC using only `repository_owner` (derived from `params.dig('repository','owner','login')`), which correctly proves the payload was signed by *that* org's webhook secret. However, `StatusHandler#process` never re-uses `repository_owner`/`repository_name` (or any stack/repository scoping) when deciding which `Commit` rows to update — it queries `Commit.where(sha: params.sha)` globally across the entire database.

### Finding Description
The claimed binding is: `repository_owner` (verified in `verify_signature`) == `repository`/`stack` whose `Commit` rows `StatusHandler#process` mutates.

Tracing the code:
- `app/controllers/shipit/webhooks_controller.rb:24-30` (`verify_signature`) computes `repository_owner` from the payload and calls `Shipit.github(organization: repository_owner)` to fetch the correct app secret, then verifies `X-Hub-Signature` against `request.raw_post`. This only proves the request was signed by the named org's own webhook secret — it says nothing about which `sha` values that org is entitled to affect.
- `create` (line 10-15) then dispatches to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`, passing the parsed JSON `params` unchanged.
- `app/models/shipit/webhooks/handlers/status_handler.rb:20-24`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
There is no `repository_owner`, `repository_name`, or `stacks`/`Handler#stacks` scoping call anywhere in `StatusHandler`. Any commit row in the entire Shipit installation whose `sha` matches `params.sha` gets a `Status` created via `commit.create_status_from_github!(params)`, regardless of which `Stack`/`Repository` it belongs to.

So the two sides of the binding are **not equal**: `verify_signature` authenticates "this payload came from org A's webhook secret," but `StatusHandler#process`'s write scope is "any commit anywhere in the DB with this SHA," which is unbounded and unrelated to org A. No `require_permission!`, `stacks` scope, or repository-format validation intervenes in this handler's `process` method — those exist only for authenticated user-facing controllers, not for the webhook `Commit` mutation.

Attack: an attacker registers/owns GitHub org A with a working webhook secret configured in Shipit (`Shipit.github(organization: 'orgA')`). They POST a `status` event to `/webhooks` with a valid `X-Hub-Signature` for org A, but with `sha` set to a commit SHA that also exists in a `Stack` under `orgB/some-repo`. Since `Commit.where(sha: ...)` has no repo/owner filter, the status is written against org B's commit as well as (or instead of) any commit of org A's that happens to share the SHA.

### Impact Explanation
A successfully signed request from an attacker-controlled organization can create/mutate `Status` records on `Commit`s belonging to a completely different organization's `Stack`, provided a SHA collision (e.g., an identical commit merged/cherry-picked into both repos, which is a realistic and reproducible precondition, not a hash-collision requirement) — this is a payload-for-one-repository mutating another's commit/stack, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Because `Commit#create_status_from_github!` can affect CI/status gating that downstream deploy logic may consult, this could influence whether commits are considered deployable, and is repeatable against any repo that shares commit SHAs with the attacker's own org (forks, vendored commits, monorepo-derived history, etc.).

### Likelihood Explanation
Preconditions: attacker needs a Shipit-registered GitHub org/app with a valid webhook secret (which is achievable by any org owner who onboards their own repo to Shipit — no special privilege beyond owning a GitHub org that Shipit trusts), and a SHA that also appears in a `Commit` row of a different stack. SHA collisions across repos are not theoretical — they commonly occur via forks, cherry-picks, submodules, or shared upstream history. The attacker cost is a single signed HTTP POST; the exploit is fully repeatable and requires no interaction with the victim org.

### Recommendation
`StatusHandler#process` (and generally handlers touching `Commit`/`Stack` records) must scope commit lookups by the repository identified in `params['repository']['full_name']`, e.g. `Commit.joins(:stack).merge(Stack.where(repository: repository_from_payload)).where(sha: params.sha)`, using the same `repository_owner`/`repository_name` that `verify_signature` trusted, so that a signed payload can only mutate commits belonging to stacks under that exact repository.

### Proof of Concept
```ruby
test "status webhook from org A cannot mutate commits belonging to org B's stack" do
  stack_a = shipit_stacks(:shipit) # repository owned by org A
  stack_b = create(:stack, repository: create(:repository, owner: 'orgB', name: 'repoB'))
  shared_sha = 'deadbeefcafebabe0000000000000000000000'
  commit_a = create(:commit, stack: stack_a, sha: shared_sha)
  commit_b = create(:commit, stack: stack_b, sha: shared_sha)

  payload = {
    'repository' => { 'owner' => { 'login' => 'orgA' }, 'full_name' => 'orgA/repoA' },
    'sha' => shared_sha,
    'state' => 'success',
    'context' => 'ci/test',
  }
  signature = OpenSSL::HMAC.hexdigest('sha1', Shipit.github(organization: 'orgA').webhook_secret, payload.to_json)

  assert_difference -> { commit_b.statuses.count }, 0 do
    post '/webhooks', params: payload.to_json,
      headers: { 'X-Github-Event' => 'status', 'X-Hub-Signature' => "sha1=#{signature}", 'Content-Type' => 'application/json' }
  end
end
```
Given the current implementation, this assertion fails: `commit_b.statuses.count` increases even though the signed payload only proved authorization for org A. [1](#0-0) [2](#0-1) [3](#0-2)
