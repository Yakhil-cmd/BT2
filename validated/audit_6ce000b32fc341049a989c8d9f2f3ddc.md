### Title
Webhook signature is verified against the wrong organization's secret, allowing cross-organization stack sync forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to use for HMAC verification based on an attacker-controlled JSON field (`repository.owner.login` / `organization.login`), while the event handlers that actually act on the payload (e.g. `PushHandler`) resolve the target `Repository`/`Stack` from a *different* attacker-controlled field (`repository.full_name`). In a multi-organization Shipit deployment, this breaks the binding "organization that authenticated == repository being written to," letting an attacker who legitimately knows the `webhook_secret` for one configured organization forge a push event that is verified against that secret but targets a `Stack` belonging to a different configured organization.

### Finding Description
`Shipit.github(organization:)` supports a multi-tenant configuration keyed by GitHub organization name, each with its own `webhook_secret`: [1](#0-0) 

The webhook signature check picks the organization (and thus the secret) purely from the JSON payload: [2](#0-1) [3](#0-2) 

`verify_webhook_signature` only checks the HMAC against whatever secret corresponds to that attacker-supplied organization name: [4](#0-3) 

However, once the signature "passes," the actual event handlers never re-check that the verified organization matches the repository being mutated. They independently derive the target repository from `repository.full_name`: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used for verification) and `repository.full_name` (used to select the `Stack`) are two independent fields inside the same attacker-supplied JSON body, an attacker can set them inconsistently: sign with a secret belonging to organization A (which they legitimately administer/know), while pointing `repository.full_name` at a `Stack` that belongs to organization B, hosted on the same Shipit instance.

The resulting job, `PushHandler#process`, calls `stack.sync_github(expected_head_sha: params.after)` on the resolved stack, enqueuing `GithubSyncJob` which fetches commits from GitHub and appends them to the stack's commit history without any additional binding check against the verified organization: [7](#0-6) 

If the targeted stack has continuous deployment enabled, newly appended/reachable commits can trigger an automatic deploy, meaning the forged webhook can effectively force an unauthorized sync/deploy cycle on a stack outside of the attacker's own organization.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" binding explicitly called out as an in-scope analog class. In a multi-org Shipit installation, an actor who is fully authorized only for organization A's webhook integration (and thus legitimately possesses/knows organization A's `webhook_secret`, without any Shipit session, API token, or repository write access to organization B) can use that secret to forge events that are processed as if they came from a repository under organization B. Depending on stack configuration (`continuous_deployment`), this can lead to an unauthorized deploy on organization B's stack — matching the "Critical: unauthorized deploy" impact bucket.

### Likelihood Explanation
This requires: (1) a Shipit instance configured with more than one GitHub organization (`Shipit.github_organizations` multi-tenant mode), and (2) the attacker legitimately controlling the webhook configuration/secret for at least one of those organizations (a realistic scenario for a shared internal Shipit deployment serving multiple teams/orgs, where each org's admins configure their own GitHub App webhook secret). Given those preconditions — which do not require compromising Shipit itself, obtaining a session, or an `ApiClient` token — the attack is straightforward: craft one HTTP POST with mismatched `repository.owner.login` and `repository.full_name` fields, signed with a legitimately-known secret.

### Recommendation
After verifying the HMAC signature, cross-check that the organization used to select the secret (`repository_owner`) matches the owner embedded in `repository.full_name` (and/or `organization.login`) before dispatching to handlers. Reject the webhook if these fields are inconsistent. More generally, handlers resolving `Stack`/`Repository` objects from webhook payloads should scope their lookups to the organization that was actually used to authenticate the request, not trust arbitrary payload fields independently.

### Proof of Concept
1. Assume Shipit is configured with two organizations, `org-a` and `org-b`, each with distinct `webhook_secret`s (multi-org config via `secrets.github`).
2. Attacker knows `org-a`'s `webhook_secret` (e.g., because they administer org-a's GitHub App/webhook).
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-existing-in-org-b-repo>",
  "repository": {
    "full_name": "org-b/victim-repo",
    "owner": { "login": "org-a" }
  }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a-secret, body)>` and sends it to `POST /webhooks`.
5. `WebhooksController#verify_signature` reads `repository_owner` = `"org-a"` [3](#0-2) , fetches `org-a`'s app/secret, and verification succeeds because the signature was computed with that exact secret.
6. `PushHandler` then resolves the target stack via `repository.full_name` = `"org-b/victim-repo"` [5](#0-4) , and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, enqueuing `GithubSyncJob` against org-b's stack despite the request never having been authenticated for org-b.

Note: I was unable to fully trace `Stack#sync_github` (only referenced, not opened) and `Repository.from_github_repo_name` implementations to confirm there is no additional org-scoping check performed there; based on the code paths reviewed (`Handler#stacks`, `PushHandler#process`, `GithubSyncJob#perform`), no such cross-check exists. A background Devin session with full repo access should confirm `Stack#sync_github` and `Repository.from_github_repo_name` contain no organization-scoping guard before treating this as fully confirmed.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

module Shipit
  module Webhooks

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
