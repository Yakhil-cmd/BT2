### Title
Unbounded EventEmitter Listener Leak via Never-Resolving Private Payment Chains - ([File: wallet.js])

### Summary
`handlePrivatePaymentChains()` in `wallet.js` registers a one-time listener on the shared global `eventBus` for every private-payment element that comes back as "queued," keyed by `'private_payment_validated-'+unit+'-'+json_payload_hash+'-'+output_index` [1](#0-0) . This listener is only removed when the corresponding validation eventually resolves (`ifOk`/`ifError` in `handleSavedPrivatePayments`, which emits the key event) [2](#0-1) , or when `cancelAllKeys()` is explicitly invoked on a parsing error. If validation instead perpetually returns `ifWaitingForChain` (light-client "waiting for ancestor units/stability" path), the key event is never emitted and `cb()` is called without any cleanup [3](#0-2)  — the `eventBus.once(key, …)` listener, and the whole enclosing closure (`assocValidatedByKey`, `arrChains`, etc.), remains permanently attached to the shared `eventBus`.

### Finding Description
`network.handleOnlinePrivatePayment()` accepts private-payment elements from a paired device / hub correspondent and, for light nodes with multi-hop chains, immediately calls `savePrivatePayment()` → `callbacks.ifQueued()`, persisting the payload into `unhandled_private_payments` [4](#0-3) . `wallet.js`'s `handlePrivatePaymentChains()` treats `ifQueued` by registering a permanent-until-resolved `eventBus.once(key, …)` callback [5](#0-4) .

The periodic job `handleSavedPrivatePayments()` (run every 5 seconds via `setInterval(handleSavedPrivatePayments, 5*1000)` [6](#0-5) ) re-attempts validation of each pending row. When `privatePayment.validateAndSavePrivatePaymentChain()` reports `ifWaitingForChain` — i.e., the chain's past/ancestor units are not yet downloaded or not yet stable — the row is simply left in place and processing moves on without ever emitting the `private_payment_validated-*` event [3](#0-2) , [7](#0-6) .

A paired device (any private-payment counterparty, which is explicitly an unprivileged reachable actor per the analog rules) can craft chains whose ancestor units are deliberately withheld, malformed just enough to remain "unfinished," or repeatedly varied (each with a distinct payload hash to bypass the `handledChainsCache` de-duplication in `handlePrivatePaymentChains` [8](#0-7) ) so that they permanently sit in the `ifWaitingForChain` state. Each such submission adds one more permanent listener to the shared, globally-used `eventBus` (a single `EventEmitter` instance imported and re-used by nearly every module in the codebase) with no cap on listener count and no timeout-based eviction visible in this code path (the existing cleanup job `cleanBadSavedPrivatePayments()` that purges stale `unhandled_private_payments` rows after 1 day is explicitly gated to full nodes only — `if (conf.bLight || bCatchingUp) return;` — so it never runs for the light-wallet code path where this bug is reachable) [9](#0-8) .

This is structurally analogous to CVE-2017-9059: an operation (`unmount`/here, an incomplete private-payment validation "channel") is torn down/abandoned without releasing the registered callback/listener resource, leaking it indefinitely and letting an unprivileged party trigger unbounded resource growth.

### Impact Explanation
Each never-resolving crafted private-payment chain leaves a permanently registered listener (plus its closed-over state: `assocValidatedByKey`, `arrChains`, `cache_key`, etc.) on the process-wide `eventBus`. A counterparty able to repeatedly send novel malformed/incomplete private chains (a normal capability of any paired device or hub correspondent) can grow this listener set without bound, causing continuous memory growth and, over time, a resource-exhaustion denial of service against the node/wallet process — consistent with the CVSS 3.0 "Availability: High / Confidentiality,Integrity: None" profile of the reference CVE.

### Likelihood Explanation
Reaching `ifQueued` → `ifWaitingForChain` only requires a light-node wallet receiving multi-element private-payment chains referencing units that are not (and will deliberately never be) retrievable/stable — an easily attacker-controlled condition for any paired device sending private payments. No special privileges, node compromise, or race condition are needed beyond normal private-payment protocol usage, making this readily reachable.

### Recommendation
- In `handleSavedPrivatePayments()`, track how long a row has been stuck in `ifWaitingForChain` and, after a bounded number of retries/age, either purge the row and emit the `private_payment_validated-*` key with `false` (to trigger `cancelAllKeys()` cleanup in `wallet.js`), or otherwise explicitly clean up the associated listener.
- Extend `cleanBadSavedPrivatePayments()` (or an equivalent) to also run for light clients, purging stale `unhandled_private_payments` and firing the corresponding cleanup event.
- In `wallet.js`'s `handlePrivatePaymentChains()`, add a timeout per registered `eventBus.once(key, …)` listener so it self-removes and invalidates `assocValidatedByKey` after a bounded period, regardless of whether the underlying validation ever completes.

### Proof of Concept
1. As a paired device / private-payment counterparty, send a `private_payments` message via `wallet.js` `handleMessageFromHub` → `handlePrivatePaymentChains()` containing a multi-element private chain whose head/ancestor units reference content that is deliberately never made retrievable/stable (e.g., point to units the sender never actually broadcasts, or which never stabilize).
2. `network.handleOnlinePrivatePayment()` inserts the row into `unhandled_private_payments` and calls `ifQueued()`, causing `wallet.js` to register `eventBus.once('private_payment_validated-...', …)`.
3. `handleSavedPrivatePayments()` (ticking every 5s) repeatedly hits `ifWaitingForChain` for this row and never emits the key event.
4. Repeat step 1 with a freshly-varied payload (different hash) many times; each iteration adds a permanent listener to `eventBus` that is never removed, observable via growing `eventBus.listenerCount()` / heap growth over time.
