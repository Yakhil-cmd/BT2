### Title
Webhook signature verification keys off a different org than the one whose Stack/commit state is mutated - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App (and thus the HMAC secret) used to authenticate an inbound webhook based on `repository_owner`, i.e. `payload.dig('repository','owner','login')`. Every downstream `Webhooks::Handlers::Handler` subclass, however, resolves the actual `Repository`/`Stack` to mutate using `payload.dig('repository','full_name')` [1](#0-0) . These two payload fields are never cross-checked, so in a multi-organization Shipit deployment (the officially supported `github: { OrgOne: ..., OrgTwo: ... }` schema, see `test/dummy/config/secrets_double_github_app.yml`) an attacker who is a legitimate tenant of one organization known to the instance (and therefore knows/controls that organization's own `webhook_secret`) can forge a signature that Shipit will accept for a payload whose `repository.full_name` targets a *different* organization's tracked Stack.

### Finding Description
`verify_signature` computes the signing organization purely from `repository.owner.login` (with a fallback to `organization.login`):
```
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [2](#0-1) 

That HMAC only proves "this payload byte-for-byte was signed by whoever knows the `webhook_secret` configured for `repository_owner`." It says nothing about which *other* fields inside that same payload the attacker was allowed to control — and since the attacker legitimately owns `repository_owner`'s webhook secret (it is their own organization's registered GitHub App), they can freely set every other field of the JSON body, including `repository.full_name`, before signing it.

Every handler that actually mutates state resolves its target strictly from `repository.full_name`:
```
def repository_name
  payload.dig('repository', 'full_name')
end

def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end
``` [1](#0-0) 
`Repository.from_github_repo_name` does a raw `owner/name` lookup with no relation back to the org that produced a valid signature: [3](#0-2) .

This is exactly the "organization that authenticated versus the repository that is written" desync pattern: the equality that should hold is
`organization_whose_secret_signed(payload) == owner_of(payload.repository.full_name)`,
but Shipit never enforces it — `repository_owner` (used for verification) and `repository.full_name`'s owner segment (used for action) are read from independent, attacker-controlled JSON keys in the very same signed body.

Concretely: assume the instance hosts `OrgOne` and `OrgTwo` (each with its own `webhook_secret`, as in the supported multi-org config). An attacker who administers `OrgTwo`'s own GitHub App knows `OrgTwo`'s `webhook_secret`. They can craft a JSON payload where `repository.owner.login = "OrgTwo"` (so `verify_signature` looks up and validates against `OrgTwo`'s secret, which the attacker legitimately controls) while `repository.full_name = "OrgOne/victim-repo"` (so the handler resolves and mutates `OrgOne`'s real, unrelated `Stack`). Because the two fields are never required to match, the forged, attacker-signed webhook is accepted and dispatched against `OrgOne`'s stack.

### Impact Explanation
Depending on event type this reaches materially different handlers, all keyed off the unverified `repository.full_name`:
- `push` → `PushHandler#process` triggers `stack.sync_github(expected_head_sha: ...)` for a non-owned stack [4](#0-3) , forcing an unauthorized resync/build trigger of another organization's Stack.
- `pull_request` (`opened`/`closed`/`labeled`/etc.) handlers create/archive Review Stacks and capture labels for `Repository.from_github_repo_name(params.repository.full_name)` belonging to the victim org, e.g. [5](#0-4) .
- `status` events let the attacker set arbitrary `state`/`description`/`context` on a real commit belonging to the victim org's tracked repository (subject to `Repository.from_github_repo_name` resolving to a real `Stack`), which can influence deployability checks that gate `deployable?` and merge/deploy decisions on commit statuses.

This crosses the organization/repository trust boundary defined by Shipit's own multi-tenant GitHub App model, satisfying the "cross-repository writes" / "unauthorized deploy" bar for Critical, since it lets a tenant with no privileges on the victim's stack force Stack-state mutations (sync, review-stack lifecycle, commit status) on that stack purely by signing with their own, unrelated organization's webhook secret.

### Likelihood Explanation
Requires only that the deployment run Shipit's documented multi-organization configuration (`github: { OrgA: ..., OrgB: ... }`) with at least two independent tenant orgs, and that the attacker controls one of those orgs' own GitHub App/webhook secret — no access to the victim org, no Shipit session, and no `ApiClient` token is needed. This is a normal, supported configuration (explicitly documented and tested via `secrets_double_github_app.yml`), making the precondition realistic for any shared/multi-tenant Shipit instance.

### Recommendation
After signature verification succeeds, require that the organization used to select the webhook secret (`repository_owner`) equals the owner segment of `repository.full_name` (and of `organization.login` if present) before dispatching to handlers; reject the webhook (422) on mismatch. Equivalently, resolve the target `Repository`/`Stack` using the same trusted `repository_owner` value that was used for signature verification instead of re-reading an independent `full_name` field from the unauthenticated-until-verified JSON body.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` (victim, tracks `OrgOne/victim-repo`) and `OrgTwo` (attacker's own tenant with its own `webhook_secret`), per `test/dummy/config/secrets_double_github_app.yml`.
2. As the attacker (who legitimately knows `OrgTwo`'s webhook secret), build a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker chosen sha, must exist on victim's real github repo>",
  "repository": { "owner": { "login": "OrgTwo" }, "full_name": "OrgOne/victim-repo" }
}
```
3. Compute `X-Hub-Signature: sha1=HMAC-SHA1(OrgTwo_webhook_secret, raw_body)`.
4. `POST /webhooks` with `X-Github-Event: push`. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'OrgTwo')` (from `repository.owner.login`), verifies successfully against the attacker's own secret [6](#0-5) .
5. `PushHandler#process` resolves `Repository.from_github_repo_name('OrgOne/victim-repo')` and calls `stack.sync_github(expected_head_sha: 'attacker chosen sha')` on the victim's real Stack [1](#0-0) [4](#0-3) , without the attacker ever having any grant on `OrgOne`.

*Note: the exact real-world blast radius of the `sync_github` call (e.g., whether it can pull attacker-fabricated commits vs. only real GitHub state, since `Stack#github_api`/`Stack#github_app` re-derives credentials from `repository.owner` — see `app/models/shipit/stack.rb` lines 434-440) could not be fully traced within the available iterations; the `status` and `pull_request` handler paths, which act more directly on attacker-supplied fields without further GitHub API validation, present the clearer unauthorized-mutation path and are cited above.*

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
