### Title
Cross-Organization Webhook Confusion — Signature Verified for the Sender's Org but Applied to a Different Org's Repository - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi-organization Shipit deployments (`config/secrets.yml` keyed by organization, see `docs/setup.md:182-209`), `WebhooksController#verify_signature` selects which GitHub App secret to validate a webhook against using one field of the untrusted JSON body, while the event handlers act on a *different* field of that same body to decide which tracked repository/stack to mutate. These two fields are never cross-checked against each other, so a party who legitimately controls a webhook secret for *their own* configured organization can forge a signature that Shipit accepts, while pointing the payload's `repository.full_name` at a stack belonging to a completely different organization on the same Shipit instance.

### Finding Description
`verify_signature` picks the GitHub App/secret based on `repository_owner`, derived from the request body itself: [1](#0-0) [2](#0-1) 

This value comes from `params.dig('repository', 'owner', 'login')` (or `organization.login`) — a field fully controlled by whoever sends the POST. Once the signature is verified against the GitHub App config for that organization, `create` re-parses the same raw body and dispatches it to every registered handler unmodified: [3](#0-2) 

Every handler, however, resolves the *actual* target repository/stack using a **different** field of the same JSON body — `repository.full_name` — via the shared `Handler` base class: [4](#0-3) 
and `Repository.from_github_repo_name`: [5](#0-4) 

Nothing enforces that `repository.owner.login` (used to select/verify the signing secret) matches the owner encoded in `repository.full_name` (used to pick the Repository/Stack that is actually mutated). Since the whole HTTP body is attacker-supplied, these two fields can be set independently. A user who administers Org A's GitHub App installation on this shared Shipit instance (and thus legitimately knows/controls Org A's `webhook_secret`) can send:
```json
{ "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" }, ... }
```
signed with Org A's secret. `verify_signature` looks up and validates against Org A's `GitHubApp`, succeeds, and the request is never rejected. The handler then resolves `Repository.from_github_repo_name("org-b/victim-repo")` and operates on Org B's stacks — an organization the attacker never authenticated against.

This is the direct structural analog of the reported Node.js smuggling bug: two different parsers/consumers (here, "verification" vs. "handler dispatch") each read a different subset of the same untrusted bytes to make a security-relevant decision, and the two subsets are never reconciled, letting the attacker desynchronize "who was authenticated" from "what gets acted on."

Concrete exploitation depends on which handler is invoked. The clearest Critical-impact chain is via `StatusHandler`, which trusts `sha` alone (no repository-scoping check on the commit query) and creates a GitHub commit status directly in Shipit's database for any matching commit across the whole install: [6](#0-5) 
If Org B's stack has continuous deployment enabled, an injected "success" status for a required CI context can make an otherwise-undeployed commit `deployable?`/mergeable, and `ProcessMergeRequestsJob`/continuous-delivery scheduling will deploy or merge it: [7](#0-6) [8](#0-7) 
— i.e. an unauthorized deploy/merge triggered on a repository the attacker never had credentials for.

### Impact Explanation
This crosses the "organization that authenticated versus the repository that is written" trust boundary the engine is supposed to enforce per-tenant in multi-org mode: an actor's proven identity (their own org's webhook secret) is silently substituted for authorization over a different org's stacks. The reachable outcomes (forged CI status feeding into automatic merge/deploy decisions, forced `RefreshCheckRunsJob`/`GithubSyncJob` runs, forged `membership`/`team` records) fall squarely into "an unauthorized deploy, rollback or merge" (Critical) once continuous delivery or merge queue is enabled on the victim stack.

### Likelihood Explanation
This requires only that the attacker be a legitimate administrator of *any* GitHub organization configured on the shared multi-org Shipit instance — not a member, collaborator, or credential holder of the victim organization, and no Shipit session, API token, or webhook secret belonging to the victim is needed. Any shared/multi-tenant Shipit deployment (the pattern explicitly documented in `docs/setup.md`) is affected.

### Recommendation
In `WebhooksController#verify_signature` / `create`, after verifying the signature, re-derive the repository owner strictly from the same field used to select the verifying secret (`repository.owner.login`), and reject (422) any event whose `repository.full_name` owner segment does not match the organization the signature was verified against, before dispatching to handlers.

### Proof of Concept
1. Configure Shipit multi-org (`github.org-a`, `github.org-b`), each with its own `webhook_secret`, both tracking stacks in Shipit.
2. As the operator of `org-a` (attacker), compute `sha1=HMAC(org-a.webhook_secret, body)` for:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "<required-ci-context-for-org-b-stack>"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and the computed `X-Hub-Signature`.
4. `verify_signature` validates against `org-a`'s secret and passes; `StatusHandler` creates a `success` status on the victim commit belonging to `org-b/victim-repo`, potentially unblocking continuous deployment/merge for a stack the attacker never authenticated to.
