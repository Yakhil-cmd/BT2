### Title
Webhook signature check keyed on attacker-controlled `repository.owner.login` + unscoped `Commit.where(sha:)` lookup allows cross-repository commit-status forgery - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to use for HMAC verification based on a value read out of the *unverified* JSON body itself (`repository.owner.login`, falling back to `organization.login`). `StatusHandler`, which processes the resulting event, never re-checks that identity against anything: it looks up the target `Commit` purely by SHA, globally, across every stack in the installation. This breaks the intended binding "organization whose secret authenticated the request == repository being written to."

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` computes: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from the untrusted, not-yet-verified request body (`params.dig('repository','owner','login')`). This value is used only to pick *which* `Shipit.github(organization:)` config's `webhook_secret` verifies the signature: [3](#0-2) 

Critically, `verify_webhook_signature` short-circuits to `true` whenever that organization has no `webhook_secret` configured — a state explicitly documented as optional (`docs/setup.md`, "Webhook secret (optional)"). So any organization onboarded without a webhook secret gives an unauthenticated attacker a free pass: POST any JSON body with `repository.owner.login` set to that org's login and the signature check is bypassed entirely, with the rest of the (attacker-controlled) body forwarded unchanged to the handlers: [4](#0-3) 

`StatusHandler`, which handles `X-Github-Event: status`, does not use `repository.full_name`/`Handler#stacks` at all — it resolves its target purely by commit SHA, with no scoping to any repository or organization: [5](#0-4) [6](#0-5) 

`state`, `description`, `target_url`, and `context` are taken verbatim from the request body and persisted onto whatever `Commit` record anywhere in the installation happens to share that SHA (`commit.create_status_from_github!(params)`), with no re-fetch or cross-check against the GitHub API.

The binding broken as an equality:
- Before the attack: `organization authenticated by verify_signature == organization owning the repository/commit actually written by the handler`.
- After the attack: the attacker chooses the "authenticated" organization login (any org lacking a `webhook_secret`) independently of the target commit, which is selected solely by SHA and can belong to a completely unrelated, security-sensitive stack/organization also hosted on the same Shipit instance.

### Impact Explanation
This allows an unauthenticated, unprivileged actor (no `webhook_secret`, no `ApiClient` token, no repository write access needed) to forge arbitrary commit statuses (`state: success`, custom `context`, `description`, `target_url`) for any commit tracked by any stack in the Shipit installation, as long as at least one configured GitHub organization omits a webhook secret — a supported, documented configuration. Because Shipit uses commit statuses (`deployable_status`, required statuses) to gate deploy safety checks, this is a cross-repository/cross-organization write that can be used to fake a passing CI check on a commit belonging to a different, hardened repository, undermining deploy-safety gating. This matches the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Likelihood is high in any multi-organization Shipit deployment (explicitly supported, see `test/dummy/config/secrets_double_github_app.yml`) where at least one configured organization has not set `webhook_secret` (the documented default/optional state). No secrets, tokens, or GitHub access are required — only knowledge of that organization's login string and the SHA of a target commit already tracked by Shipit (visible in Shipit's UI/API for any tracked stack).

### Recommendation
- Bind commit/status lookups to the organization/repository that was actually cryptographically verified, not to an unrelated field pulled from the same unverified payload. `StatusHandler` (and any handler using bare SHA lookups) should scope by `stacks`/`repository_name` the same way `PushHandler`/`CheckSuiteHandler` do.
- Do not allow `verify_webhook_signature` to silently pass (`return true unless webhook_secret`) for organizations without a configured secret in multi-org setups, or require secrets to be mandatory when more than one GitHub organization is configured.
- Do not derive the "authenticated organization" from an unverified body field before the signature check has been evaluated against the correct secret; instead, verify against all configured secrets or require an explicit trusted routing mechanism (e.g., a secret-scoped URL) that is not attacker-controlled.

### Proof of Concept
1. Configure Shipit with two GitHub orgs, `orgA` (no `webhook_secret` set, as in the documented optional configuration) and `orgB` (a real org with tracked, security-sensitive stacks and a `webhook_secret`).
2. Attacker (no credentials) sends:
```
POST /webhooks
X-Github-Event: status
Content-Type: application/json

{
  "repository": {"owner": {"login": "orgA"}, "full_name": "orgA/anything"},
  "sha": "<sha of a commit belonging to an orgB-tracked stack>",
  "state": "success",
  "context": "ci/required-check",
  "description": "forged",
  "target_url": "http://attacker.example"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "orgA")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally — no `X-Hub-Signature` header is even required.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the `orgB` commit (unscoped by repository), and calls `commit.create_status_from_github!(params)`, persisting the forged "success" status onto a commit the attacker has no access to.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
