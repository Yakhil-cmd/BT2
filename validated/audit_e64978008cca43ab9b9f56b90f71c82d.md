### Title
`StatusHandler#process` writes attacker-controlled `description`/`target_url` onto Statuses of commits in unrelated stacks - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` matches commits solely by `sha` across the entire database, without checking that the webhook's `repository.full_name` matches the commit's stack repository. Any GitHub user who owns a repository with the Shipit GitHub App/webhook installed can send a legitimately-signed `status` webhook whose free-text `description`/`target_url` fields are then persisted verbatim (via `Commit#create_status_from_github!` -> `Status.replicate_from_github!`) onto every commit sharing that sha, including commits belonging to a victim stack in a completely different repository/organization.

### Finding Description
The broken binding: the code implicitly assumes
`commit.stack.repository.full_name == payload.dig('repository', 'full_name')`
for every `commit` a status is attached to. In reality `StatusHandler` never checks this: [1](#0-0) 

`process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — a global, unscoped query across all stacks/repositories, unlike the `stacks` helper (`Repository.from_github_repo_name(repository_name)&.stacks`) that the `Handler` base class exposes for exactly this purpose: [2](#0-1) 

`Commit#create_status_from_github!` then calls `statuses.replicate_from_github!(stack_id, github_status)`, which does a `find_or_create_by!` writing `state`, `description`, `target_url`, `context`, `created_at` verbatim from the attacker-controlled payload: [3](#0-2) [4](#0-3) 

`verify_signature` in `WebhooksController` only confirms the payload was legitimately sent by GitHub for the *sending* org (`Shipit.github(organization: repository_owner)`); it does not, and cannot, verify that the commit sha referenced by that payload is unique to that repository: [5](#0-4) 

Exploit flow: attacker owns repository B with the Shipit GitHub App/webhook configured (a normal, unprivileged setup any repo owner can do). Attacker crafts a commit in B whose sha collides with (or is force-pushed/cherry-picked to match) a commit sha already present in victim stack A — e.g., by cherry-picking/rebasing a commit from a public upstream that A also tracks, since git shas are content-addressed and collisions are trivial to arrange when two repos share history (forks, common base branches, vendored commits). Attacker then sets an arbitrary `description`/`target_url` via the real GitHub Status API on their own repo/commit. GitHub delivers a validly signed `status` webhook to Shipit. `StatusHandler` finds the shared-sha `Commit` row belonging to stack A and writes the attacker's `description`/`target_url` onto a new `Status` row tied to A, indistinguishable in the UI from a legitimate GitHub-origin status.

None of the existing guards catch this: `verify_signature` authenticates the sender org, not the sha-to-repo binding; `ExplicitParameters` validates field types only; there is no `repository_name`/`stacks` scoping check in `StatusHandler` (unlike other handlers that use the `stacks` helper).

### Impact Explanation
A payload legitimately originating from attacker-owned repository B mutates commit/status state belonging to victim stack A in an unrelated repository/org — this is a cross-tenant write matching the rules' Critical category ("a payload for one repository mutating another's stack, commit, task or team"). The attacker can inject arbitrary phishing URLs or fabricated failure/success descriptions attributed to "GitHub" into A's commit history/UI, potentially influencing CI-gated deploy decisions (since `Status` participates in `deployable?`/`blocked?` checks) or social-engineering A's maintainers via the UI. Repeatable against any stack that happens to track a commit sha also reachable by an attacker-controlled repository.

### Likelihood Explanation
Preconditions: the attacker needs (a) a repository they control with Shipit's GitHub App/webhook installed (achievable by installing the app on any repo they own if the Shipit GitHub App is installable by any org/user, or already installed org-wide), and (b) a commit sha collision between their repo and the victim's tracked commit — trivially achievable via forks, shared upstream history, or cherry-picks/rebases preserving the original commit sha. No Shipit credentials, session, or API token are required; only the ability to call GitHub's real Status API on their own commit, which GitHub signs and delivers to Shipit legitimately. Cost is low and the action is repeatable per matching sha.

### Recommendation
In `StatusHandler#process`, scope the commit lookup by the sending repository, e.g. restrict to commits belonging to `stacks` (the `Handler`-provided repository-scoped stack set) instead of a global `Commit.where(sha: params.sha)`, mirroring how other handlers already scope by `repository_name`.

### Proof of Concept
Minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, hypothetical):
1. Create `stack_a` under `repository_a` (`owner/repo-a`) with a commit `commit_a` having `sha: "deadbeef..."`.
2. Create `stack_b` under `repository_b` (`attacker/repo-b`) with a commit `commit_b` having the **same** `sha: "deadbeef..."`.
3. Build a `status` webhook payload with `repository.full_name = "attacker/repo-b"`, `sha: "deadbeef..."`, `description: "PHISHING: click here http://evil.example.com"`, `target_url: "http://evil.example.com"`.
4. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)`.
5. Assert: `stack_a`'s commit (`commit_a.reload.statuses.last.description`) equals the attacker string and `target_url` equals `http://evil.example.com`, even though the webhook's `repository.full_name` was `attacker/repo-b`, not `owner/repo-a`. This demonstrates `commit.stack.repository.full_name != payload['repository']['full_name']` yet the write still succeeded, proving the binding is broken.
