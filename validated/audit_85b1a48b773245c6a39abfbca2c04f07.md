## Analysis

I found a valid analog matching the "organization that authenticated versus the repository that is written" binding.

### Title
Webhook signature verification is scoped to the wrong organization, decoupling the authenticated tenant from the repository/commits actually acted upon - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to HMAC-verify the request against based on `repository.owner.login` (or `organization.login`) taken directly from the untrusted JSON payload. Once verification passes for *that* organization's tenant, every event `Handler` resolves the actual target `Stack`/`Commit`/`Repository` using a *different* payload field, `repository.full_name`, with no re-check that it belongs to the same organization that was used to authorize the request.

### Finding Description
`verify_signature` computes the organization used to pick the HMAC secret purely from payload content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves per-org config in a multi-tenant setup, and `GitHubApp#verify_webhook_signature` explicitly **skips verification entirely if that organization's `webhook_secret` is blank** (documented as optional in `config/secrets.development.example.yml`): [3](#0-2) [4](#0-3) 

Separately, every `Handler` subclass (push, status, check_suite, pull_request, membership, etc.) locates the target repository/stack using `repository.full_name` from the same payload — a field never cross-checked against `repository_owner`/the organization whose secret validated the request: [5](#0-4) 

The equality that is supposed to hold is: `organization authenticated by verify_signature == organization owning the repository the handler mutates`. Because the two are derived from two independent, attacker-controlled sub-objects of the same JSON body (`repository.owner.login` vs `repository.full_name`), an attacker can make them diverge:

1. Set `repository.owner.login` = `OrgA`, an org configured in `Shipit.github` with `webhook_secret: nil` (an explicitly supported, documented configuration — see `config/secrets.development.example.yml` lines 8-16). Verification then returns `true` unconditionally regardless of the `X-Hub-Signature` header value.
2. Set `repository.full_name` = `OrgB/victim-repo`, referencing a real `Stack`/`Repository` tracked by Shipit under a different, secured organization `OrgB`.
3. The request passes `verify_signature` (because `OrgA`'s check is a no-op) and the handler then locates and mutates `OrgB`'s actual `Stack` via `Repository.from_github_repo_name(repository_name)`, e.g.:
   - `StatusHandler#process` creates a commit status on any commit sha in `OrgB`'s stacks: [6](#0-5) 
   - `PushHandler#process` triggers `stack.sync_github(expected_head_sha:)` on `OrgB` stacks: [7](#0-6) 

The `StatusHandler` path is the most impactful: Shipit stacks gate deploys on required/blocking CI statuses (`require_ci`), and `commit.create_status_from_github!` is the exact mechanism by which CI results are recorded. An attacker who forges a `success` status for a blocked commit in `OrgB`'s repository — without ever possessing `OrgB`'s `webhook_secret`, an `ApiClient` token, or any Shipit session — can flip the deployability of that commit and enable an unauthorized deploy of it, satisfying `require_ci` checks it should never pass.

### Impact Explanation
This breaks the authentication boundary between separately configured GitHub organizations/tenants in a multi-org Shipit deployment: authenticating as (or against) one lightly-configured org (`webhook_secret: nil`) is sufficient to inject fabricated GitHub events (push, status, check_suite, membership, pull_request label/close/reopen) against any *other* org's tracked repositories. Forging commit statuses can directly enable an unauthorized deploy by satisfying CI gating (`require_ci`), which the rules classify as Critical impact.

### Likelihood Explanation
Requires: (a) a multi-org Shipit deployment (supported and documented as a standard configuration — see the "multiple GitHub applications" example in `config/secrets.development.example.yml`), and (b) at least one configured organization with `webhook_secret` unset (explicitly called out as optional). No credential, GitHub App private key, ApiClient token, or Shipit session is required — the `/webhooks` endpoint is public and unauthenticated by design pending signature verification. This is realistic in any deployment where an operator follows the documented "optional" webhook_secret guidance for even one org while tracking other, secured orgs' repositories.

### Recommendation
Bind signature verification to the specific repository being acted upon, not merely the organization name pulled out of the payload independently of the object being mutated: verify the signature using the secret associated with the *tracked* `Repository`/`Stack` matched by `repository.full_name` (or reject the request if that repository's org differs from `repository_owner`), and stop allowing any organization's webhook to be "no-op verified" purely because that org's `webhook_secret` happens to be blank when other organizations in the same instance are secured. Additionally, consider requiring `webhook_secret` to be present for every organization or refusing to process an event whose `repository.full_name` org doesn't match `repository_owner`/`organization.login`.

### Proof of Concept
1. Configure Shipit with two orgs in `Shipit.github`: `OrgA` (`webhook_secret: nil`) and `OrgB` (`webhook_secret: "s3cr3t"`), each with tracked stacks for their respective repos.
2. POST to `/webhooks` with header `X-Github-Event: status` and an arbitrary/garbage `X-Hub-Signature`, and body:
```json
{
  "sha": "<sha of a commit in OrgB/victim-repo pending on required CI>",
  "state": "success",
  "context": "required-ci-context",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
3. `verify_signature` resolves `repository_owner` = `OrgA`, calls `Shipit.github(organization: "OrgA").verify_webhook_signature(...)`, which returns `true` immediately because `OrgA`'s `webhook_secret` is blank — the bogus signature is never checked.
4. `StatusHandler#process` runs, finds the commit by `sha` (global lookup, not scoped to org) and calls `commit.create_status_from_github!(params)`, recording a fabricated `success` status on `OrgB`'s commit, potentially unblocking a deploy gated on that CI check — all without any knowledge of `OrgB`'s `webhook_secret`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

**File:** lib/shipit.rb (L170-200)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
