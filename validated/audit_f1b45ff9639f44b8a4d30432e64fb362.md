### Title
Webhook signature verified for one GitHub organization but repository resolved from a different, unbound payload field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to check the HMAC against using `repository_owner`, but the event handlers that actually act on the payload (e.g. `PushHandler`) resolve the target repository from a completely different field, `repository.full_name`. Nothing binds the two together, so a caller who knows the `webhook_secret` for *any* organization configured on a multi-tenant Shipit install can forge a signed payload whose `repository.owner.login` names their own org (to pass signature verification) while `repository.full_name` names a stack belonging to a different, unrelated organization.

### Finding Description
`verify_signature` computes which `GitHubApp`/secret to validate against solely from the organization login found in the payload: [1](#0-0) [2](#0-1) 

```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

`verify_webhook_signature` then just HMACs the *entire raw body* against that one organization's `webhook_secret`: [3](#0-2) 

Once the signature passes, the dispatched handler determines what to act on using a *different* field of the same body: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

and `PushHandler` uses that to run `sync_github` against the resolved stacks: [5](#0-4) 

Because HMAC validity only proves "whoever built this exact byte string knows the secret for the org named in `repository.owner.login`," it does not prove that `repository.full_name` belongs to that same org. This engine explicitly supports multiple, independently secreted GitHub organizations sharing one Shipit instance (a documented, supported configuration): [6](#0-5) 

An attacker who legitimately controls/administers Org B (and therefore knows Org B's `webhook_secret`, e.g. because they installed the shared Shipit app on their own repo) can POST directly to `/webhooks` with:
- `repository.owner.login = "OrgB"` (so `repository_owner` picks Org B's secret and the HMAC — computed with Org B's known secret — verifies), and
- `repository.full_name = "OrgA/victim-repo"` (a stack that actually belongs to unrelated Org A).

The broken binding, stated as an equality:
`organization whose secret authenticated the request == organization owning the repository the handler acts on`
is never enforced; the code only proves the left side and blindly trusts the right side from the same untrusted, attacker-shaped payload.

### Impact Explanation
With this mismatch, an attacker outside of Org A's control can force Shipit to run event handlers against Org A's stacks/commits using data they fully control, despite Org A's webhook secret being unknown to them. Confirmed via `PushHandler`, this forces `GithubSyncJob`/`stack.sync_github` to run against arbitrary tracked stacks across organizational boundaries the attacker has no authorization over — an unauthenticated cross-organization interaction with stack state that should require Org A's own webhook secret. The same unbound `repository_name` resolution pattern is shared by the base `Handler` class used by all other repository-scoped handlers (`status`, `check_suite`, `pull_request`), so any handler that trusts `repository.full_name` for lookups but was authorized against `repository.owner.login` is equally exposed to spoofed events (e.g. injected commit statuses) for repositories/stacks the attacker does not control.

### Likelihood Explanation
Requires only that the attacker know the `webhook_secret` of any one organization configured on a shared Shipit instance (which the documentation explicitly supports and which the attacker may legitimately possess for their own, unrelated org), and no Shipit session, `ApiClient` token, or repository write access to the victim organization. The `/webhooks` endpoint is unauthenticated aside from the HMAC check, so the attacker can POST directly without going through GitHub at all.

### Recommendation
Bind the field used to select the verification secret to the field used to resolve the acted-upon repository/organization: either verify the signature per-repository (using the secret configured for `repository.full_name`'s owner instead of `repository.owner.login`/`organization.login`), or, after selecting the app/secret, assert that `repository.full_name`'s owner matches `repository_owner` before dispatching to handlers, rejecting the event otherwise.

### Proof of Concept
1. Configure two orgs on one Shipit instance: `OrgA` (victim, tracked stack `OrgA/victim-repo`) and `OrgB` (attacker-controlled, webhook secret known to attacker).
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgB" },
    "full_name": "OrgA/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(OrgB_webhook_secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30,59-62`) resolves `repository_owner` = `"OrgB"`, fetches Org B's `GitHubApp`, and the HMAC verifies successfully since the attacker used Org B's own known secret.
5. `PushHandler#process` (`app/models/shipit/webhooks/handlers/push_handler.rb:12-17`) resolves `repository_name` from `full_name` = `"OrgA/victim-repo"` and triggers `stack.sync_github(expected_head_sha: params.after)` on Org A's stack — an action the attacker was never authorized to trigger for Org A.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.
