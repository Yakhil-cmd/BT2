### Title
Governance vote weight is measured from an instantaneous balance snapshot, allowing flash‑loan‑style manipulation of `op_list`/system parameter votes - (File: `main_chain.js`)

### Summary
The `countVotes` function in `main_chain.js` determines the weight of a `system_vote` by summing the voter's *current* stable balance at the moment vote-counting executes (once per newly-stabilized MCI), rather than requiring the balance to have been held for any minimum period before or during the vote. An attacker can therefore receive a large temporary balance, cast a vote, and move the funds away again once the balance snapshot has been taken — mirroring the M‑24 pattern where two dependent steps (allocate weight, then commit it) can be triggered back-to-back using borrowed funds that never need to be genuinely staked.

### Finding Description
`countVotes(conn, mci, subject, ...)` is invoked once per stabilized MCI, after all `system_vote`/`system_vote_count` messages for that MCI have been recorded: [1](#0-0) 

Inside `countVotes`, the voter's balance used for weighting is computed as a live query over `outputs`/`units`, counting every stable-good output that has **no stable-good spender at query time**: [2](#0-1) 

This balance is inserted into a temporary `voter_balances` table and directly used to weight `op_list` (witness list) votes and numerical system parameter votes (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`): [3](#0-2) [4](#0-3) 

Crucially, an output only stops counting toward the voter's balance once its *spending unit is itself stable and sequence='good'* (per the `NOT EXISTS` sub-query). If the spending (return) transaction has not yet stabilized at the moment `countVotes` runs for that MCI, the full, temporarily-received balance is counted in full — even though the voter no longer economically "owns" those funds for more than the brief window needed to get the credit and vote unit stable in the same MCI. The vote-count loop that decides the counting window (`since_timestamp`) only checks whether *some address* voted within a time window and the *aggregate* voted balance meets `SYSTEM_VOTE_MIN_SHARE * TOTAL_WHITEBYTES`; it does not verify that any individual voter held their balance for a sustained period: [5](#0-4) 

This is directly analogous to the M‑24 report: in Game.sol, a privileged two-step process (`pushAllocationsToController` then `pushAllocationsToVaults`) could be executed back-to-back with a flash-loaned balance to distort weight calculations. Here, the equivalent two-step process is "receive funds → have `system_vote` unit stabilize" followed by "return funds before the vote's snapshot is superseded," both of which can be arranged within the same MCI/next MCI, since the weight-determining check reads a live, unlocked balance rather than a time-locked stake.

### Impact Explanation
`op_list` directly determines the network's witness/order-provider set, and the numerical subjects (`threshold_size`, `base_tps_fee`, `tps_interval`, `tps_fee_multiplier`) control core consensus/fee parameters. An attacker who can cheaply and repeatedly borrow a large GBYTE balance for the short duration of a single MCI stabilization cycle can inflate their voting weight without genuinely locking capital, potentially:
- Electing a malicious/compromised witness set (`op_list`), enabling downstream double-spend or censorship risk once such witnesses control ordering.
- Pushing system parameters (fees, TPS thresholds) to values that benefit the attacker or destabilize network throughput/fee economics.

This matches the "node disagreement on validity/consensus parameters" and network-liveness impact classes accepted for this analysis.

### Likelihood Explanation
Exploitation requires only:
1. Access to a temporary large GBYTE balance (e.g., an exchange withdrawal briefly routed through the voting address, or a cooperative counterparty), and
2. Timing the outgoing "return" unit so it is not yet stable when `countVotes` executes for the relevant MCI.

Since MCI stabilization in Obyte typically completes within seconds to a couple of minutes, and there is no explicit minimum holding-period check on the voter's balance in `countVotes`, this is achievable by any moderately resourced actor without any protocol-level restriction preventing it. Likelihood is Medium given it requires coordinated timing and enough capital to move the `SYSTEM_VOTE_MIN_SHARE` threshold for op_list/param changes, but no code path currently prevents it.

### Recommendation
Require voting weight to be based on a balance that has been held for a minimum, enforced duration prior to the vote (e.g., balance snapshot at `min_mci`/`since_timestamp` window start rather than at count time), or require that funds backing a vote remain locked/unspent for a cooldown period after voting before they can be spent, closing the window for temporarily-borrowed balance to influence `op_list`/numerical system-parameter vote outcomes.

### Proof of Concept
1. Attacker controls address `V` used only for voting.
2. A counterparty (or the attacker's own funded address) sends a large GBYTE payment to `V` in unit `A`. `A` stabilizes.
3. Attacker sends a `system_vote` (e.g., for `op_list`) from `V` in unit `B`, referencing the boosted balance. `B` stabilizes in the same or next MCI.
4. Before `countVotes` executes for that MCI (`main_chain.js:1657-1663`), the return-transfer unit `C` moving the funds back out of `V` is composed but is deliberately kept from stabilizing until after the vote count query in `main_chain.js:1757-1773` has run.
5. Because `C` has not yet stabilized as `sequence='good'` at query time, the `NOT EXISTS` condition still counts `V`'s full (borrowed) balance in `voter_balances`, inflating `V`'s influence on the `op_list`/parameter outcome in `main_chain.js:1850-1902`.
6. Once the count is finalized, `C` stabilizes normally, and the funds are returned to their original owner — the attacker never needed to permanently hold the stake that determined their voting weight.
