### Title
`repay` refunds a self-declared "overpayment" out of pool custody on a debt-free market, draining supplier funds - (File: contracts/pool/src/ops/repay.rs)

### Summary
The pool's `repay` op resolves the declared `amount` into burned debt shares plus an `overpayment`, then transfers the overpayment back to the caller via `transfer_out` — without debiting `cash`, without checking `require_reserves`, and without verifying that any tokens were actually transferred in. On a market with zero (or less-than-declared) debt, the entire declared amount is classified as overpayment and is paid out of the pool's real token custody to an arbitrary caller. This mirrors the reported bug class — a refund computed from a self-declared figure rather than from actual settled state, letting the operation hand out funds that were never received.

### Finding Description
`ops::repay::accounting` calls `cache.resolve_repay(amount, position)` and computes `net_repay = amount - overpayment` [1](#0-0) . When the market carries no debt, `current_debt_ceil` is zero, `resolve_repay` takes the full-close branch, `burned` is zero and `overpayment == amount`. The `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, so no revert occurs [2](#0-1) . `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)` — a payout from the pool's own token balance [3](#0-2) . Because `credit_cash(net_repay)` adds zero, the cash book is untouched, so no reserve check can catch the payout; custody silently diverges from the book.

The protocol's own test suite pins this behavior: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` calls `client().repay(&payer, ...)` directly with a declared amount equal to the pool's entire token balance on a zero-debt market, and asserts the custody is drained while `actual_amount` is 0 [4](#0-3) . The same test file documents that neither `repay` nor `recapitalize` refunds debit `cash` or pass `require_reserves` [5](#0-4) . The guard spec confirms the intended invariant — "the refund handed back to the payer is bounded by the amount that payer just sent in" — which the unfunded call violates because nothing enforces the inbound leg at the pool layer [6](#0-5) .

The controller path (`settle_repay`) always transfers a measured amount in before calling the pool [7](#0-6) , so the vulnerability exists only if `pool.repay` is directly callable; the test calling it with a freshly generated `payer` (no controller, no pre-transfer) indicates it is, though I could not fully confirm the pool's auth gate on `repay` within this iteration — that is the one open precondition.

### Impact Explanation
An unprivileged address can drain the pool's token balance for any market whose outstanding debt is below the declared `amount`: call `repay` with `amount` up to the pool's token custody, receive the "overpayment" as a real token transfer, and retire no debt. Suppliers' principal (cash backing supply shares) is stolen directly. Repeated across markets and hubs sharing a physical pool balance, this is theft of user funds at full custody scale.

### Likelihood Explanation
Requires only a single `repay` call with a debt-free (or low-debt) target market and a declared amount no larger than the pool's token balance — no privileged role, no oracle manipulation, no timing dependence. Any freshly deployed market or a market whose debt was just fully repaid qualifies immediately.

### Recommendation
Make the refund provably funded. Options: (a) require `repay` (and `recapitalize`) to be invoked only through the controller, which already performs `transfer_amount_measured` of the declared amount into the pool first; (b) measure the inbound receipt inside the pool (balance delta) and cap `overpayment` at that measured amount rather than the declared `amount`; (c) gate the `net_repay == 0` branch of `RepayRoundsToZeroShares` so a zero-debt repay with positive `amount` reverts instead of refunding.

### Proof of Concept
1. Deploy pool, supply 1000 TOKEN via `supply` (custody = cash = 1000, borrowed = 0).
2. Attacker (no tokens needed) calls `repay(attacker, [(market, position=0, amount=1000)])`.
3. `resolve_repay` returns `overpayment = 1000`, `burned = 0`; `net_repay = 0` passes the assert; `transfer_out(attacker, 1000)` pays the full custody to the attacker; `cash` stays 1000 while custody drops to 0.
4. This is exactly what `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` already exercises end-to-end [8](#0-7) .

```rust
pub(crate) fn accounting(env: &Env, action: &PoolAction) -> RepayOutcome {
    let (mut cache, position) = ops::load_leg(env, action);
    let amount = action.amount;

    let (burned, overpayment) = cache.resolve_repay(amount, position);
    let net_repay = amount
        .checked_sub(overpayment)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow));
    assert_with_error!(
        env,
        net_repay == 0 || burned.raw() > 0,
        GenericError::RepayRoundsToZeroShares
    );

    let position = position.checked_sub(env, burned);
    cache.burn_debt(burned);

    cache.credit_cash(net_repay);
```

```rust
#[test]
fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {
    let t = TestSetup::new();
    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
```
