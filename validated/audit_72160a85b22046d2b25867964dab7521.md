### Title
Webhook signature verification binds the wrong scope: organization used to select `webhook_secret` is decoupled from the repository actually written - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, which is read from the untrusted, attacker-suppliable JSON body (`params.dig('repository', 'owner', 'login')`). Once the signature check passes, the event handlers (`PushHandler`, `StatusHandler`, etc.) resolve the actual `Repository`/`Stack` to mutate using a *different* field of the same body — `payload.dig('repository', 'full_name')` — via `Handler#repository_name` / `Handler#stacks`. Nothing ties the organization whose secret validated the request to the repository that is subsequently written to.

### Finding Description
`verify_signature` selects the app config like this: [1](#0-0) 
and `repository_owner` is derived purely from the request body: [2](#0-1) 

Meanwhile, every handler resolves the target stack/repository independently from another body field: [3](#0-2) 

`PushHandler#process` and `StatusHandler#process` then act on whatever `Repository.from_github_repo_name(repository_name)` / matching `Commit` resolves to, with no re-check that this repository belongs to the same organization that was authenticated for the signature: [4](#0-3) [5](#0-4) 

In a Shipit deployment configured with multiple GitHub organizations (each with its own `webhook_secret`, as `Shipit.github(organization:)` implies), an entity that legitimately knows/controls one organization's webhook secret (e.g., an org admin who configured their own GitHub App/webhook in Shipit, as documented in `lib/shipit/github_app.rb`) can craft an entirely custom raw JSON body, set `repository.owner.login` to their own org (so the signature check passes against a secret they know), while setting `repository.full_name` to point at a *different, victim* organization's repository. Because the HMAC is computed over the raw body they control and sign themselves, this is fully self-consistent and passes `verify_webhook_signature`: [6](#0-5) 

The binding that should hold — `organization that authenticated == organization owning the repository being written` — does not exist anywhere in the code path. This matches the report's underlying bug class of a validation/consistency check applied to one input while a downstream decision (`limitedBigJump`/`IsInitialCycle` in the Erigon analog) is driven by an unguarded, independently-derived value.

### Impact Explanation
This allows cross-repository writes: an attacker who legitimately controls one organization's webhook secret in a multi-tenant Shipit instance can forge `push` events (triggering `stack.sync_github` for arbitrary stacks matching the forged `full_name`/branch) or `status` events (writing fabricated commit statuses via `commit.create_status_from_github!`) against stacks/commits belonging to a completely different organization/repository that they do not control. This can pollute deploy-readiness signals (fake green CI status) or trigger syncs for repositories outside the attacker's authorization scope — a cross-repository write as defined in the scoring rules.

### Likelihood Explanation
Exploitability requires the attacker to possess a valid `webhook_secret` for at least one organization configured in the Shipit instance (e.g., because they administer that org's GitHub App/webhook themselves) — this is plausible for shared/multi-tenant Shipit deployments where many independent GitHub organizations register their own webhooks against a single Shipit installation, which is exactly the model `lib/shipit/github_app.rb` and `Shipit.github(organization:)` support. No GitHub App private key, Shipit session, or `ApiClient` token is required — only the webhook secret of the attacker's own organization, which is not a privileged Shipit credential.

### Recommendation
After signature verification, cross-check that the organization/owner used to select the webhook secret matches the owner of the repository referenced by the event payload's `repository.full_name` (or, more robustly, look up the target `Repository`/`Stack` first, verify against *that* repository's associated organization's secret rather than the attacker-supplied `repository.owner.login`).

### Proof of Concept
1. Attacker administers GitHub App/webhook for `org-attacker`, configured in Shipit with `webhook_secret = S`.
2. Attacker crafts JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": { "owner": { "login": "org-attacker" }, "full_name": "victim-org/victim-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC(S, body)` themselves (they know `S`).
4. POST to `/webhooks` with `X-Github-Event: push`. `verify_signature` calls `Shipit.github(organization: "org-attacker")` and validates successfully against `S`.
5. `PushHandler#stacks` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `sync_github` on its stacks — despite the attacker having no legitimate relationship to `victim-org`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
