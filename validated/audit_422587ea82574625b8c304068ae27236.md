### Title
Webhook signature is verified against a payload-supplied organization while handlers act on a different, unverified organization/repository field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and thus which `webhook_secret`) to use for HMAC validation based on `repository.owner.login`/`organization.login` read directly out of the unauthenticated JSON body, but the handlers that actually mutate state (`Repository.from_github_repo_name(payload.dig('repository','full_name'))`, `MembershipHandler`'s `params.organization.login`) key off a *different* field of that same body that is never cross-checked against the field used for secret selection.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 
using `repository_owner`, derived from the raw, unauthenticated body: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `GitHubApp` (and distinct `webhook_secret`) per organization when the engine is configured for multiple GitHub organizations, as documented and supported by `github_app_config`: [3](#0-2) 

Once the signature check passes (HMAC computed with the secret belonging to whichever organization `repository_owner` claims), the raw body is dispatched unmodified to handlers, which key their side effects off a *different* field, `repository.full_name` (or `organization.login` for membership events), with no comparison back to `repository_owner`: [4](#0-3) [5](#0-4) 

`Repository.from_github_repo_name` performs a plain lookup by owner/name parsed out of that unchecked `full_name` string: [6](#0-5) 

The binding that should hold is: `organization authenticated by HMAC == organization/repository whose state is mutated`. Nothing enforces this equality. `repository.owner.login` (used to pick the secret) and `repository.full_name` / `organization.login` (used to pick the target Repository/Team) are independent JSON fields inside the same signed body, and the signature only proves the *body as a whole* was produced by whoever holds the secret for the organization named in `repository.owner.login` - it says nothing about which organization's data that body claims to describe elsewhere.

### Impact Explanation
On a multi-organization Shipit deployment (explicitly supported, see `docs/setup.md` "Using Multiple Github Applications"), anyone who controls the webhook configuration for one onboarded, low-trust organization (Org A - e.g., they administer their own GitHub App/organization that was legitimately installed on this Shipit instance) can sign an arbitrary JSON body with Org A's `webhook_secret`, set `repository.owner.login`/`organization.login` to `org-a` so it passes `verify_signature`, but set `repository.full_name` (or `organization.login` for `membership` events) to point at a completely different, victim organization (Org B) also hosted on the same Shipit instance. This lets the attacker:
- Trigger `PushHandler` → `stack.sync_github` for Org B's stacks, spoofing arbitrary `ref`/`after` SHAs: [7](#0-6) 
- Archive/unarchive Org B's review stacks via the pull-request handlers that key off `params.repository.full_name`: [8](#0-7) 
- Most severely, via `MembershipHandler`, add an arbitrary GitHub login to a `Team` identified only by its numeric `github_id`, with no verification that the crafted `organization.login`/team actually belongs to the organization that authenticated the request: [9](#0-8) 
  If that `github_id` matches a `Team` referenced in `Shipit.github_teams` (the OAuth authorization gate), this is a direct escalation into `Shipit.github_teams` authorization: [10](#0-9) [11](#0-10) 

This matches the explicitly in-scope High-severity impact "escalation into `Shipit.github_teams` authorization," and the cross-repository/cross-organization mutation of stacks matches "cross-repository writes."

### Likelihood Explanation
Requires only that the Shipit instance be configured for more than one GitHub organization (documented, supported configuration) and that the attacker controls the webhook secret/App configuration for one of those onboarded organizations - no Shipit session, `ApiClient` token, or repository write access on the victim org is needed. The `verify_signature` before_action never re-validates that the organization used for secret selection matches the organization referenced deeper in the payload, so this is a straightforward, deterministic bypass of the authentication boundary once the multi-org precondition is met.

### Recommendation
After `verify_webhook_signature` succeeds, re-derive the organization from the same field(s) the handlers will use (`repository.full_name` owner segment, or `organization.login` for org-scoped events) and reject the request (422) unless it matches the organization (`repository_owner`) whose secret validated the signature. Alternatively, verify the signature using every configured organization's secret and only accept the match whose organization equals the one the payload claims to describe for the handler's Repository/Team lookup, rather than trusting `repository_owner` as an independent selector.

### Proof of Concept
1. Deploy Shipit with a multi-organization `github:` config (per `docs/setup.md`), onboarding attacker-controlled `org-a` and victim `org-b`, each with distinct `webhook_secret`s.
2. Attacker computes `sha1=HMAC(org_a_webhook_secret, body)` for a crafted JSON body where `repository.owner.login = "org-a"` but `repository.full_name = "org-b/victim-repo"` (or, for a `membership` event, `organization.login = "org-a"` while `team.id` matches a `github_id` of a `Team` in `Shipit.github_teams`, and `member.login` is the attacker's own GitHub login).
3. POST to `/webhooks` with header `X-Github-Event: push` (or `membership`) and `X-Hub-Signature: sha1=<computed>`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")`, verifies successfully with Org A's secret, and the request proceeds.
5. `PushHandler`/`MembershipHandler` acts on `org-b`'s repository/team, e.g. adding the attacker to a team gating `Shipit.github_teams` authorization, without ever holding credentials for `org-b`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
      class MembershipHandler < Handler
        params do
          requires :action, String
          requires :team do
            requires :id, Integer
            requires :name, String
            requires :slug, String
            requires :url, String
          end
          requires :organization do
            requires :login, String
          end
          requires :member do
            requires :login, String
          end
        end
        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
```
