### Title
Arbitrary victim impersonation via `PreStxOp`/`StackStxOp` output/input decoupling forces third-party STX locking with attacker-controlled reward payout - ([File: stackslib/src/chainstate/burn/operations/stack_stx.rs])

### Summary
`PreStxOp::parse_from_tx` derives the `output` field (later used as the `StackStxOp.sender`) purely from Bitcoin output 0's scriptPubKey, which requires no cooperation or signature from the address owner, while `StackStxOp::get_sender_txid` only requires that the chained transaction spend Bitcoin output 1 of the same PreStx transaction. Because outputs 0 and 1 are cryptographically independent, an attacker funding the PreStx transaction can set output 0 to a victim's address and output 1 to their own address, then later spend output 1 (which they control) to submit a valid `StackStxOp` whose `sender` is set to the victim.

### Finding Description
The broken equality: the protocol implicitly assumes `identity(output 0 of PreStxOp) == authorization(key spending output 1 of PreStxOp)`, but nothing in the code enforces this.

- `PreStxOp::parse_from_tx` sets `output` from `outputs[0].address` with no signature/ownership check [1](#0-0) .
- `StackStxOp::get_sender_txid` only validates that the chaining transaction's input spends vout=1 of the referenced PreStx txid [2](#0-1) .
- `burnchain.rs` resolves `sender` as `pre_stack_stx.output` (i.e., the attacker-chosen output-0 address) and passes it into `StackStxOp::from_tx` [3](#0-2) .
- Downstream, `StacksChainState::process_stacking_ops` executes `run_contract_call(&sender.clone().into(), None, ..., "stack-stx", &args, ...)`, i.e. it invokes the active PoX contract's `stack-stx` entry point *as if `sender` (the victim) were `tx-sender`* [4](#0-3) .
- The PoX `stack-stx` entry point only checks that `tx-sender` has sufficient unlocked balance; it performs no additional signature check binding the call to the account holder, since burnchain ops are assumed to already be authenticated by whoever created the underlying Bitcoin transaction [5](#0-4) .
- The PoX reward address (`reward_addr`) is decoded from output 0 of the *StackStxOp* transaction itself — fully attacker-controlled, independent of the victim [6](#0-5) .

Exploit flow: Attacker funds a PreStx Bitcoin transaction from their own UTXOs, sets output 0 = victim's Bitcoin address (Stacks-address-derivable) and output 1 = an address they control (any value, e.g. dust). This requires no permission from the victim, since paying to any Bitcoin address does not require the recipient's signature. In a subsequent block, attacker spends output 1 (signed with their own key) as input 0 of a `StackStxOp` transaction, setting output 0 to their own reward address and encoding `stacked_ustx`, `num_cycles`, `signer_key`, etc. Both `PreStxOp::parse_from_tx` and `StackStxOp::get_sender_txid`/`parse_from_tx` accept this as valid, and `StackStxOp.sender` is set to the victim's address.

Existing guards checked and found insufficient: `StackStxOp::check()` only validates `stacked_ustx != 0`, `num_cycles` range, and `signer_key` format — no sender/authorization check [7](#0-6) . The pox-5-specific guards named in the prompt (`verify-not-prepare-phase`, `signer-manager-call-active`, `verify-signer-key-grant`, etc.) belong to the separate `signer-manager.clar`/`pox-5.clar` bond/grant system and do not intersect this burnchain-op parsing/dispatch path at all — they cannot prevent this.

### Impact Explanation
The victim's real, unlocked STX balance gets locked for up to `POX_MAX_NUM_CYCLES` cycles without their consent, and the PoX Bitcoin reward corresponding to that locked stake is paid to a reward address chosen entirely by the attacker — this is theft of the rewards that should accrue to the locked STX, plus temporary freezing of the victim's staked STX for the lock period. This is repeatable against any Stacks address with a spendable STX balance and costs the attacker only Bitcoin transaction fees (two on-chain BTC txs, no dust required beyond minimal outputs).

### Likelihood Explanation
No privileged role is required. The attacker needs only: (1) enough BTC to pay two transaction fees, (2) knowledge of the victim's Stacks address (public information), and (3) the ability to craft raw Bitcoin OP_RETURN-tagged transactions, all of which are explicitly permitted attacker capabilities ("craft burnchain stacking ops from their own Bitcoin inputs"). This does not require compromising any node, miner, or relayer. However, this mechanism (`PreStxOp`/`StackStxOp`/`TransferStxOp`/`DelegateStxOp`) has existed unchanged since Stacks epoch 2.1 and is exercised the same way regardless of which PoX contract version (pox-2/3/4/5) is active, so if this were exploitable in the way described it would represent a protocol-wide, multi-year-old critical flaw rather than something newly introduced by pox-5. I could not find in this codebase any additional binding check (e.g., requiring output 0 and output 1 of the PreStx tx to share the same script/address, or a Stacks-level signature over the intended sender) that would close this gap, but I also could not conclusively confirm via a runnable test in the time available whether some other layer (e.g. mempool/relay-level filtering, or an undiscovered check in `SortitionHandleTx` reward-set validation) blocks this specific chain. This uncertainty should be resolved with an actual reproduction.

### Recommendation
Require that `PreStxOp.output` be provably associated with the same key that will later spend the chained UTXO, e.g., by deriving `sender` from the address that signs the input of the follow-up operation's referenced PreStx output (or by requiring both outputs 0 and 1 of the PreStx transaction to encode the same address), rather than trusting an unauthenticated Bitcoin output as an on-chain identity assertion.

### Proof of Concept
Rust integration test plan (extending `stackslib/src/burnchains/tests/db.rs` patterns):
1. Construct `pre_stack_stx_tx` with `output[0].address = victim_hash160` and `output[1].address = attacker_hash160`, inputs funded from an unrelated attacker UTXO.
2. Process this via `BurnchainDB` parsing and assert `PreStxOp.output == victim_addr` (as in existing test at `stackslib/src/burnchains/tests/db.rs:511-515`).
3. Construct `stack_stx_tx` with `inputs[0].tx_ref = (pre_stack_stx_txid, 1)` (spending attacker-controlled output 1), `output[0].address = attacker_reward_hash160`.
4. Assert `StackStxOp.sender == victim_addr` and `StackStxOp.reward_addr == attacker_reward_addr` (mirroring `stackslib/src/burnchains/tests/db.rs:517-521`).
5. Feed both ops through `StacksChainState::process_stacking_ops` with a chainstate where `victim_addr` has a known unlocked STX balance and assert, before/after: `stx_get_balance(victim_addr)` unlocked amount decreases by `stacked_ustx` and `stacking-state`/lock records show `stacker: victim_addr`, while the PoX reward-set entry's payout address is `attacker_reward_addr` — demonstrating the equality `authorized_locker(victim_addr) == entity_controlling(output_1_key)` is false yet the lock proceeds.

impl StackStxOp {
    pub fn check(&self) -> Result<(), op_error> {
        if self.stacked_ustx == 0 {
            warn!("Invalid StackStxOp, must have positive ustx");
            return Err(op_error::StackStxMustBePositive);
        }

        if self.num_cycles == 0 || self.num_cycles > POX_MAX_NUM_CYCLES {
            warn!(
                "Invalid StackStxOp, num_cycles = {}, but must be in (0, {}]",
                self.num_cycles, POX_MAX_NUM_CYCLES
            );
        }

        // Check to see if the signer key is valid if available
        if let Some(signer_key) = &self.signer_key {
            Secp256k1PublicKey::from_slice(signer_key.as_bytes())
                .map_err(|_| op_error::StackStxInvalidKey)?;
        }

        Ok(())
    }
