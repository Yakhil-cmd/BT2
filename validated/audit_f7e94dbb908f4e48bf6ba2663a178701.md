### Title
Reachable assertion (uncaught `throw Error`) via crafted payment input referencing a "stable temp-bad" output causes node crash - (File: validation.js)

### Summary
CVE-2017-13727 describes a reachable assertion abort in LibTIFF's directory-writing code that a remote attacker can trigger with a crafted file, crashing the process. The same bug class exists in `ocore`'s unit-validation logic: `validatePaymentInputsAndOutputs()` in `validation.js` contains `throw Error(...)` statements that encode invariants about internal database state rather than performing normal, recoverable validation-error handling (`return cb(...)`). If an attacker can get the DB into a state where these invariants don't hold and then post a unit that hits the check, the thrown exception propagates out of an asynchronous DB-callback with no enclosing `try/catch`, which is unhandled by Node.js and crashes the whole node process — a remote denial of service, exactly analogous to the LibTIFF assertion abort.

### Finding Description
In `validatePaymentInputsAndOutputs()`, when validating a `transfer` input, the code loads the referenced source output and asserts: [1](#0-0) 

```
if (rows.length > 1)
    throw Error("more than 1 src output");
...
if (bStableInParents) {
    if (src_output.sequence === 'temp-bad')
        throw Error("spending a stable temp-bad output " + input.unit);
    ...
}
```

This is invoked from the normal validation pipeline for every publicly posted unit that spends an output (`validateAuthors` → `validateMessages` → `validatePaymentInputsAndOutputs`), which is reachable by any unprivileged unit poster: [2](#0-1) .

The invariant being asserted is that once an output's containing unit becomes stable (`bStableInParents`), its `sequence` can only be `'good'` or `'final-bad'` — `'temp-bad'` is supposed to be resolved to one of those two values as soon as the unit stabilizes, in `markMcIndexStable()`/`handleNonserialUnits()`: [3](#0-2) . That function itself contains a similar hard assertion for a related invariant (`temp-bad and with content_hash?`): [4](#0-3) .

Both `throw Error()` calls execute deep inside `conn.query(...)` callbacks (asynchronous DB driver callbacks), not inside any `try/catch` block set up by the caller chain (`validateAuthors` → `validateMessages` → `async.series` in `validate()`). Node.js has no way to route such a synchronous throw from an async callback back into the `async.series` error-handling path; it becomes an uncaught exception. Unless the process has a global `process.on('uncaughtException')` handler that gracefully degrades (none of which was found wired into the validation code path in `network.js`/`validation.js`), the entire node process terminates.

This mirrors the LibTIFF CVE precisely: a reachable, crash-only assertion embedded in code that processes attacker-influenced/crafted data (a posted unit and its referenced output chain), rather than a graceful validation-error return.

### Impact Explanation
If the `sequence === 'temp-bad'` invariant on a stable output can be violated (e.g., through a race between the moment an output's status is momentarily `temp-bad` while its owning unit's stability/sequence-resolution has not yet fully propagated to all replicas, or through any code path that updates `sequence` inconsistently with `is_stable`), then any subsequent unit spending that output — something an ordinary, unprivileged user can craft merely by referencing the input's `unit`/`message_index`/`output_index` — will crash every full node that validates it. Because `validate()` is called by every node when it receives the joint, a single crafted unit broadcast to the network could crash a large fraction of full nodes simultaneously (network-wide denial of service, and nodes are then "unable to confirm new units," matching the report's acceptance criteria), not merely take down the attacker's own client. This is a hard process crash, not merely a validation failure, so it is unrecoverable without restarting the node and re-processing the poison unit again from the mempool/peers unless it is specifically filtered out.

### Likelihood Explanation
The bug is a defense-in-depth assertion meant to catch "impossible" states, so likelihood hinges on whether an attacker can actually create a stable output whose `sequence` remains `temp-bad` (or duplicate src-output rows). The exact database race or ordering bug that would let this state exist could not be confirmed from static analysis alone — it depends on subtle interactions between `main_chain.js`'s stabilization/`handleNonserialUnits` logic, `writer.js`'s additional-query scheduling for `sequence='temp-bad'` updates, and concurrent stabilization of multiple units. Given the complexity of the sequence-resolution state machine (conflicting units, forks, `arrAdditionalQueries`, batched writes across `kvstore`/SQL), a specific bypass path is plausible but unproven; likelihood is assessed as medium given the code explicitly anticipates this as an "impossible" case worth asserting on, indicating the developers themselves were unsure this invariant always holds.

### Recommendation
- Replace the `throw Error(...)` invariant checks in `validatePaymentInputsAndOutputs()` (validation.js:2451, 2458) and in `main_chain.js` (`handleNonserialUnits`, line 1333) with graceful `return cb(...)`/logged-and-rejected validation errors (or `nonfatal_error` event emission as used elsewhere in the code, e.g. the commented-out `eventBus.emit('nonfatal_error', ...)` pattern seen in `validateParents`), so that an unexpected state degrades to "unit rejected" rather than a full process crash.
- Audit the sequence-resolution state machine in `main_chain.js`/`writer.js` to confirm that a unit's `sequence` field can never remain `'temp-bad'` once `is_stable=1` is set, across all code paths (including partial/interrupted writes, replays, and catch-up).
- Add a global `process.on('uncaughtException')` safety net in the node entry point that logs and performs a controlled, isolated rejection of the offending unit instead of terminating the whole process, as a defense-in-depth measure against any remaining reachable assertions.

### Proof of Concept
Conceptual PoC (exact triggering DB state not fully reproducible without deeper access to the stabilization internals):
1. Attacker crafts two conflicting units spending the same address's history such that one becomes `sequence='temp-bad'` while the network is at the edge of stabilizing the MCI containing it (racing `handleNonserialUnits`/`markMcIndexStable`).
2. Attacker (or another cooperating unprivileged party) immediately broadcasts a further unit whose `payment` message contains a `transfer` input pointing at the output of the `temp-bad` unit (`input.unit`/`message_index`/`output_index`), timed so that on the recipient nodes the src output row is already flagged `is_stable`/`main_chain_index <= last_ball_mci` (i.e., `bStableInParents = true`) while `sequence` has not yet been flipped away from `'temp-bad'`.
3. When each full node calls `validation.validate()` on the new unit, it hits `validatePaymentInputsAndOutputs()` at the `if (src_output.sequence === 'temp-bad') throw Error(...)` line, causing an uncaught exception and crashing the node process.

Because the precise DB race window that produces `sequence='temp-bad'` on a stable output was not independently verified within tool access, this PoC is illustrative of the reachable code path and its lack of exception-safety rather than a fully confirmed exploit chain.
