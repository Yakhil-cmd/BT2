### Title
Cross-organization webhook confusion: HMAC signature is verified against `repository.owner.login` but events are dispatched against `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
The reported bug class (a flag/check that is verified against one piece of state but the write path actually uses a different, unvalidated piece of state) maps onto `WebhooksController#verify_signature`. The webhook HMAC is checked against the GitHub App configured for `repository.owner.login` (or `organization.login`), but every downstream `Webhooks::Handlers::Handler` resolves the target `Stack`/`Repository` from the independent `repository.full_name` field. Nothing in the code enforces that these two fields refer to the same organization.

### Finding Description
`WebhooksController#verify_signature` derives the signing organization solely from the request body: [1](#0-0) [2](#0-1) 

```
repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```

This looks up a `GitHubApp` instance keyed strictly by the organization name embedded in the payload, and validates the HMAC using that organization's own `webhook_secret`: [3](#0-2) 

Shipit supports multiple independently-configured GitHub Apps/organizations sharing the same webhook endpoint (`Shipit.github(organization:)`, `github_app_config`): [4](#0-3) 

Once the signature check passes, every event handler resolves which `Stack`/`Repository` to mutate from a *different* field of the same attacker-controlled JSON body — `repository.full_name` — with no cross-check against `repository.owner.login`/`organization.login` that was used for signature verification: [5](#0-4) [6](#0-5) 

The equality that should hold is: `organization that signed the payload == organization that owns the repository being written to`. In this engine, the code actually only checks `repository.owner.login (used to pick the verifying secret) == repository.owner.login (never revalidated)`, while the effective write target is chosen from `repository.full_name`, a sibling field of the same untrusted JSON that is never compared to the verified organization.

### Impact Explanation
An entity that is a legitimate GitHub organization administrator for **any one** organization configured in this Shipit instance's multi-org `github:` secrets block (and therefore knows/controls that organization's own `webhook_secret`, which they themselves provisioned when creating their GitHub App) can compute a valid HMAC for a completely fabricated JSON body. They can set `repository.owner.login`/`organization.login` to their own org (so `verify_signature` selects their own org's secret and passes), while setting `repository.full_name` to `"OtherOrg/other-repo"` — a repository belonging to a totally unrelated organization also tracked by the same Shipit instance. Because `Handler#stacks`/`#repository_name` only reads `full_name`, this forged, but "validly signed", request drives real state changes against a stack the attacker does not own: e.g. `PushHandler` enqueues `GithubSyncJob`/deploy-affecting syncs, `pull_request` handlers can archive/unarchive/provision review stacks, membership/status handlers can create teams or set commit statuses for repositories outside the attacker's organization. This is a cross-repository/cross-organization write achieved purely by request forgery against the engine's own webhook trust boundary, matching the "cross-repository writes" / unauthorized deploy-adjacent impact category.

### Likelihood Explanation
This requires the target Shipit deployment to use the documented multi-organization GitHub App configuration (`docs/setup.md`, "Using Multiple Github Applications") and for the attacker to control at least one of the configured organizations (i.e., have created/administered a GitHub App with a webhook pointed at this Shipit instance). This is a realistic operating mode for shared/multi-tenant Shipit deployments, and no privileged Shipit credentials (session, `ApiClient`, GitHub App private key) are needed — only the attacker's own organization's `webhook_secret`, which they legitimately possess. Likelihood is moderate: it depends on multi-org configuration and does not apply to single-org deployments where `repository_owner` can only ever resolve to the one configured organization.

### Recommendation
In `WebhooksController#verify_signature` and/or in `Shipit::Webhooks::Handlers::Handler#repository_name`, explicitly assert that the organization used to select/verify the webhook signature (`repository.owner.login` / `organization.login`) matches the organization portion of `repository.full_name` for the resolved `Repository`. Reject the request (422) if they diverge. Alternatively, resolve the target `Repository` first and verify the signature using the webhook secret associated with that repository's actual configured organization, rather than trusting the organization name embedded in the same untrusted payload used for routing.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own GitHub App/`webhook_secret` (per `docs/setup.md` multi-org schema); Shipit tracks a `Repository`/`Stack` for `OrgB/victim-repo`.
2. Attacker administers `OrgA`'s GitHub App and therefore knows `OrgA`'s `webhook_secret`.
3. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "OrgA" },
    "full_name": "OrgB/victim-repo"
  }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s known `webhook_secret` over the raw body and POSTs to `/webhooks` with `X-Github-Event: push`.
5. `verify_signature` resolves `repository_owner = "OrgA"`, fetches `Shipit.github(organization: "OrgA")`, and the HMAC check succeeds because the attacker signed with `OrgA`'s real secret.
6. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("OrgB/victim-repo")`, which is unrelated to `OrgA`, and enqueues `GithubSyncJob`/branch sync against `OrgB`'s stack — a write the attacker was never authorized to trigger.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
