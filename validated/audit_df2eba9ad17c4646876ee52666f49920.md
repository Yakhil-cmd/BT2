### Title
Cross-stack authorization bypass in CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` re-implements stack resolution instead of using the scoped helper defined in `Shipit::Api::BaseController`, so a stack-scoped `ApiClient` token can be used to read the build status of any stack in the installation, not just the stack it was authorized for.

### Finding Description
`Shipit::Api::BaseController` binds every API request to the stacks an `ApiClient` is entitled to see: [1](#0-0) 
`stacks` filters by `current_api_client.stack_id` when the client is scoped, and `stack` resolves the requested `params[:stack_id]` only within that filtered relation. This is the intended binding: "a stack a token authorises" == "a stack it touches". This scoping is a real, tested feature — a fixture-based `ApiClient` scoped to one stack ("here_come_the_walrus") is verified to only be able to list/see its own stack via the standard controllers: [2](#0-1) 

`Shipit::Api::CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [3](#0-2) 
Instead of calling the scoped `stacks.from_param!` helper, it calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` class. The controller still declares `require_permission :read, :stack`: [4](#0-3) 
but `check_permissions!` only checks that `"read:stack"` is present in the client's `permissions` array — it never checks `stack_id`: [5](#0-4) 

As a result, the equality the system is supposed to enforce — `current_api_client.stack_id == requested stack` — holds in every other API controller that uses `BaseController#stack`, but is broken specifically in `CCMenuController`, where the check degrades to "any authenticated client with `read:stack` permission may read any stack's CCMenu status," regardless of the `stack_id` the token was scoped to when it was created.

### Impact Explanation
An `ApiClient` token that was deliberately scoped to a single stack (e.g., issued to a low-trust integration for stack A) can be reused via `GET /api/stacks/:stack_id/ccmenu.xml` to read CCMenu state — `lastBuildStatus`, `lastBuildLabel` (which is the deployed commit SHA), `webUrl`, and activity — for any other stack in the Shipit instance, including stacks the token holder has no legitimate visibility into. This is an unauthorized cross-stack read of stack/deploy state, matching the High-impact category of "unauthenticated/unauthorized read of stack state, task streams or deploy output" defined by the scope of this exercise.

### Likelihood Explanation
High for any deployment that issues stack-scoped `ApiClient` tokens (a supported and tested feature of the engine). No additional secret, session, or privileged access is required beyond the already-issued, narrowly-scoped API token itself — the attacker only needs to change the `stack_id` path segment on a request they are already entitled to make with valid Basic Auth credentials.

### Recommendation
Change `Shipit::Api::CCMenuController#stack` to resolve the stack through the scoped `stacks` relation (i.e., `stacks.from_param!(params[:stack_id])`) exactly as `BaseController#stack` does, so the `current_api_client.stack_id` binding is enforced consistently across all API controllers, including CCMenu.

### Proof of Concept
1. Create (or use) an `ApiClient` scoped to Stack A with `permissions: ['read:stack']` (`stack_id = A.id`).
2. Authenticate with that client's `authentication_token` via HTTP Basic Auth.
3. Request `GET /api/stacks/B/ccmenu.xml`, where `B` is any other stack the client was never scoped to.
4. Observe the response returns `200 OK` with Stack B's `lastBuildStatus`, `lastBuildLabel` (commit SHA), and `webUrl` — because `CCMenuController#stack` calls `Stack.from_param!` on the entire `Stack` table rather than the client-scoped `stacks` relation used by every other API controller (`app/controllers/shipit/api/ccmenu_controller.rb:29-31` vs. `app/controllers/shipit/api/base_controller.rb:74-80`).
