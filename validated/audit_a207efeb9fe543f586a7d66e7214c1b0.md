## Analysis

Confirmed. `SystemInstruction::InitializeNonceAccount` is dispatched without any signer or ownership check on the target account — it only requires the account to be `Uninitialized` and writable. Combined with `withdraw_nonce_account`, which honors whoever is recorded as `data.authority`, this reproduces the exact "init lacks access control" bug class from the report: anyone can race to initialize a pre-funded, uninitialized nonce account and set themselves as the authority, then drain it.

### Title
Missing access control on `InitializeNonceAccount` allows front-running of nonce-authority assignment and fund theft - (File: `programs/system/src/system_processor.rs`)

### Summary
`SystemInstruction::InitializeNonceAccount` transitions a system-owned account from `State::Uninitialized` to `State::Initialized` and assigns an arbitrary `authorized` pubkey supplied purely from instruction data, with no requirement that the target account (or any related authority) sign the transaction.

### Finding Description
In the dispatch of `InitializeNonceAccount`, the processor only checks the instruction has 1 account and reads sysvars; it never verifies that account 0 is a signer: [1](#0-0) 

The actual state transition in `initialize_nonce_account` likewise performs no ownership/signer check — it only verifies the account is writable and currently `Uninitialized`, then unconditionally writes the caller-supplied `nonce_authority` into the account state: [2](#0-1) 

Compare this to `assign()` in the same file, which correctly requires `address.is_signer(signers)` before changing account state: [3](#0-2) 

Once a nonce account is `Initialized`, `withdraw_nonce_account` allows withdrawing all/part of its lamports as long as `signers.contains(&data.authority)` — i.e., whoever was set as `authority` during initialization fully controls the funds: [4](#0-3) 

**Exploitation path**: A nonce account must first be brought into existence with `SystemInstruction::CreateAccount`/`Allocate`/`Assign` (owned by the system program, `Uninitialized` state, funded to be rent-exempt). If this account-creation step is **not atomically bundled** in the same transaction as `InitializeNonceAccount` (e.g., separate transactions from a wallet/service, staged/multisig provisioning flows, or a batch nonce-account-creation service that funds many nonce addresses ahead of time and initializes them later), any unprivileged party who observes the funded, `Uninitialized`, system-owned account on-chain can submit their own `InitializeNonceAccount` instruction naming that address as account 0 and any pubkey they control as `authorized`. Because no signature from the account or its intended owner is required, this transaction succeeds and overwrites the account with the attacker's chosen authority before the legitimate owner's `InitializeNonceAccount` transaction lands.

### Impact Explanation
Once the attacker's `InitializeNonceAccount` transaction confirms first, the attacker becomes the sole `authority` for `AdvanceNonceAccount`, `AuthorizeNonceAccount`, and `WithdrawNonceAccount` on that account. Via `withdraw_nonce_account`, the attacker can withdraw the account's lamports (down to rent-exemption or fully, if they also drop below rent-exempt minimum) to an account they control — a concrete, unsigned/unauthorized fund transfer that meets the "concrete fund movement" bar. This is a real fund-loss vector for any protocol or wallet flow that funds nonce-account addresses before submitting the initialization instruction in a separate transaction.

### Likelihood Explanation
Likelihood depends on whether any legitimate workflow separates account creation/funding from `InitializeNonceAccount` into different transactions (rather than atomically bundling both instructions in one transaction, which is the common/safe pattern used by the CLI's nonce helpers). I was not able to fully verify, within the available tooling and iteration budget, whether all in-repo callers (CLI, SDK helper `solana_system_interface::instruction`) always bundle `CreateAccount` + `InitializeNonceAccount` atomically for every code path, or whether any exposed path (SDK, RPC-driven multisig/staged flows) allows submitting them separately. Given the missing check is unconditional in the processor itself, any external caller (dApp, custodian, exchange) constructing its own transactions without bundling both instructions atomically would be exposed regardless of what the CLI does.

### Recommendation
Require that the nonce account itself (or a designated authority passed as an additional signer account) sign the `InitializeNonceAccount` instruction, analogous to the signer check already enforced in `allocate`/`assign`. At minimum, add `if !signers.contains(account.get_key()) { return Err(InstructionError::MissingRequiredSignature); }` inside `initialize_nonce_account` before transitioning state, mirroring the `initOwner()` fix recommendation of "add access control before allowing initialization."

### Proof of Concept
1. Victim submits `SystemInstruction::CreateAccount` (or `Allocate`+`Assign`) creating `nonce_pubkey`, owned by the system program, sized as a nonce account, funded to rent-exemption — but does *not* include `InitializeNonceAccount` in the same transaction (e.g., intends to send it in a follow-up transaction).
2. This transaction confirms on-chain; `nonce_pubkey`'s account data and lamports are now publicly visible with `State::Uninitialized`.
3. Attacker submits a transaction containing `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` with account 0 = `nonce_pubkey` (no signature required for `nonce_pubkey`), plus the required `RecentBlockhashes`/`Rent` sysvar accounts — see the exact accepted shape in the existing test: [5](#0-4) 
4. This transaction lands before the victim's intended initialization, setting `authority = attacker_pubkey`.
5. Attacker submits `SystemInstruction::WithdrawNonceAccount(lamports)` signed by `attacker_pubkey`, draining the account's lamports to an attacker-controlled destination, per the logic in `withdraw_nonce_account`.

            from.get_key()

        return Err(InstructionError::InvalidArgument);

    let check_signer = |signer: &Pubkey| {
        if !signers.contains(signer) {
            ic_msg!(
                invoke_context,
                "Withdraw nonce account: Account {} must sign",
                signer
            );
            return Err(InstructionError::MissingRequiredSignature);
        }
        Ok(())

    match state.state() {
        State::Uninitialized => {
            if lamports > from.get_lamports() {
                ic_msg!(
                    invoke_context,
                    "Withdraw nonce account: insufficient lamports {}, need {}",
                    from.get_lamports(),
                    lamports,

                return Err(InstructionError::InsufficientFunds);
