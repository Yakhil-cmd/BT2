### Title
Cross-organization webhook signature bypass lets an attacker force a `github sync` on an arbitrary victim stack - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/handler.rb`, `app/models/shipit/webhooks/handlers/push_handler.rb`)

### Summary
`WebhooksController#verify_signature` resolves the HMAC secret using `repository.owner.login`, while the actual event handler (`PushHandler`/`Handler#stacks`) resolves the target stack using `repository.full_name`. `GitHubApp#verify_webhook_signature` returns `true` unconditionally when the resolved organization's config has no `webhook_secret`, so an attacker can pick a Shipit-configured org that has no secret for the `owner.login` field to trivially pass verification, while independently setting `repository.full_name` to any victim repository configured in Shipit to make `PushHandler` sync that victim's stack(s).

### Finding Description
The broken binding is the implicit equality the code assumes but never enforces:
`organization_used_for_signature_verification (params.dig('repository','owner','login')) == organization_that_owns_the_targeted_repository (params.dig('repository','full_name').split('/').first)`

Trace:
- `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository', 'owner', 'login')` [1](#0-0)  and calls `Shipit.github(organization: repository_owner)` then `github_app.verify_webhook_signature(...)` [2](#0-1) .
- `GitHubApp#verify_webhook_signature` returns `true` immediately when `webhook_secret` is blank for that org's config [3](#0-2) .
- If verification passes (whether legitimately or via the no-secret bypass), `WebhooksController#create` dispatches the same raw `params` hash to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .
- `Handler#stacks` and `Handler#repository_name` resolve the target repository from a **different** field: `payload.dig('repository', 'full_name')` [5](#0-4) .
- `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` on every non-archived stack whose branch matches, for whichever repository `full_name` resolved to [6](#0-5) .

Because `repository.owner.login` (used for secret lookup) and `repository.full_name` (used for stack targeting) are two independent, attacker-controlled JSON fields in the same forged POST body with no cross-check, the attacker can set `owner.login` to any Shipit-configured organization that happens to have no `webhook_secret` (satisfying `Shipit.github(organization: ...)` lookup and passing `verify_webhook_signature` trivially per `lib/shipit/github_app.rb:76-77`), while setting `full_name` to `victim-org/victim-repo`, an organization that *does* have a secret and that the attacker does not control. The signature check never touches `full_name`, so it never notices the mismatch.

`drop_unhandled_event`, `check_if_ping`, and the `ExplicitParameters` schema (`requires :ref`, `requires :after`) do not defend against this because they only validate presence of fields, not cross-consistency between `owner.login` and `full_name` [7](#0-6) .

### Impact Explanation
The attacker can force `Shipit::Stack#sync_github` to run for any stack backed by any repository configured in Shipit, without possessing that repository's `webhook_secret`, `github_access_token`, or any Shipit credential — this is a payload for one (attacker-controlled, secret-less) organization mutating the state of another organization's/repository's stack, matching the explicitly listed Critical impact category "a payload for one repository mutating another's stack, commit, task or team." The immediate, demonstrable effect is an unauthenticated, forced invocation of the GitHub sync pipeline for a victim stack (enqueuing `GithubSyncJob`, updating `expected_head_sha`/commit state) attributed to a repository/org that never authenticated the request via its own secret. This is repeatable against any stack whose repository is registered in Shipit, for as long as at least one other Shipit-configured organization exists with a blank `webhook_secret`.

Whether this additionally lets the attacker inject literally attacker-authored commit content (rather than just forcing a resync of the real upstream state) depends on what `Stack#sync_github`/`GithubSyncJob` fetch from the GitHub API versus what they trust from the payload — I was not able to fully verify `Stack#sync_github`'s implementation within the available context, so the "appending attacker commits" framing should be treated as unconfirmed pending review of `app/models/shipit/stack.rb` and `app/jobs/shipit/github_sync_job.rb`. The confirmed, sufficient finding is the authentication-bypass-driven forced state mutation of an arbitrary victim stack.

### Likelihood Explanation
Preconditions: (1) Shipit is configured in multi-org mode with at least two organizations, one of which has a blank/absent `webhook_secret` in its config — a configuration state that is realistic since `webhook_secret` is optional per-org in `Shipit.github_app_config` [8](#0-7) ; (2) a target repository exists in Shipit under a different organization. No Shipit session, API token, or GitHub secret is required — only knowledge (which is discoverable by trial, since `GithubOrganizationUnknown` vs `422` responses differ) of which configured org lacks a secret and the target repo's `full_name`/branch. The attacker cost is a single unauthenticated `POST /webhooks` request with a crafted `X-Github-Event: push` header and JSON body; fully repeatable.

### Recommendation
Cross-validate that the organization used to resolve/verify the webhook secret matches the organization implied by `repository.full_name` (and `organization.login`, if present) before dispatching to handlers. Alternatively, reject/require a non-blank `webhook_secret` for every configured organization (fail closed instead of `return true unless webhook_secret`), and have `Handler#repository_name`/`stacks` re-derive the owner from the same verified field used in `WebhooksController#repository_owner`, raising if they diverge.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "push event with mismatched owner.login (no-secret org) and full_name (victim org) forces sync on victim stack" do
  # Precondition: Shipit.github(organization: 'no-secret-org') config has no webhook_secret
  # Shipit.github(organization: 'victim-org') config HAS a webhook_secret the attacker does not know
  victim_stack = shipit_stacks(:shipit) # repository full_name == 'victim-org/victim-repo', branch 'master'

  payload = {
    ref: 'refs/heads/master',
    after: 'deadbeef' * 5,
    repository: {
      full_name: 'victim-org/victim-repo', # binding B: used by Handler#stacks
      owner: { login: 'no-secret-org' }     # binding A: used by verify_signature
    }
  }.to_json

  assert_equal 'no-secret-org', JSON.parse(payload).dig('repository', 'owner', 'login')
  assert_equal 'victim-org/victim-repo', JSON.parse(payload).dig('repository', 'full_name')
  # Assert A != owner_of(B) to establish the divergence before tracing

  Shipit::Stack.any_instance.expects(:sync_github).with(expected_head_sha: 'deadbeef' * 5)

  post shipit_engine.webhooks_path,
    params: payload,
    headers: {
      'X-Github-Event' => 'push',
      'X-Hub-Signature' => 'sha1=irrelevant', # accepted because no-secret-org has no webhook_secret
      'CONTENT_TYPE' => 'application/json'
    }

  assert_response :ok
  # Assert victim_stack.sync_github was invoked despite the request never being signed
  # by victim-org's secret — demonstrating state mutation attributed to an org whose
  # secret did not verify the request.
end
```
