Confirmed root cause: `StatusHandler#process` looks up commits **globally by SHA**, with no scoping to the repository/organization whose webhook secret authenticated the request. [1](#0-0) 

The status webhook's signature is verified against the GitHub App configured for `repository_owner` (`params.dig('repository','owner','login')`), as computed in `WebhooksController#verify_signature`. [2](#0-1) 

But the actual write performed by `StatusHandler` is `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — it never checks `payload['repository']['full_name']` or restricts the query to commits belonging to that repository's stack(s). Since the `commits` table has a composite unique index on `(sha, stack_id)`, not on `sha` alone, the *same* SHA can legitimately exist as separate `Commit` rows under unrelated `Stack`s/repositories tracked by the same Shipit instance. [3](#0-2) [4](#0-3) 

Contrast this with `PushHandler` and `CheckSuiteHandler`, which correctly scope through `Handler#stacks`, itself derived from `payload.dig('repository','full_name')`: [5](#0-4) [6](#0-5) 

`StatusHandler` breaks this pattern by binding directly on `Commit.where(sha:)` with no stack/repository filter.

### Title
Cross-Repository Commit Status Injection via Unscoped SHA Lookup in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
The binding that should hold is: `organization authenticated by the webhook signature == organization/repository whose data is written`. `StatusHandler#process` breaks this by looking up commits by `sha` alone across the entire `commits` table, rather than scoping to the repository named in the same payload's `repository.full_name` field (as every other stack-aware handler does). Since git commit SHAs are content-addressed and can be reproduced in any repository holding the same objects, an attacker who legitimately controls a GitHub repository/organization with its own valid Shipit webhook (its own `webhook_secret`) can push/import a commit object whose SHA matches a commit already tracked under a *different, unrelated* Shipit stack, then trigger a `status` event for it (e.g., via the Statuses API) on their own repo. The webhook is correctly signed by their own org's secret and passes `verify_signature`, but `StatusHandler` then attaches the forged CI status to the victim stack's `Commit` record.

### Finding Description
- `WebhooksController#verify_signature` selects which GitHub App/secret to validate against using `repository_owner`, derived from the payload's own `repository.owner.login` (or `organization.login`). [7](#0-6)  This ties signature validity to "the sender is a legitimate source *for that org*", not to "the sender is authorized to modify the referenced commit".
- `StatusHandler` (invoked after signature verification) ignores the `repository` field entirely for its actual mutation, and instead does a bare, table-wide `Commit.where(sha: params.sha)` lookup: [1](#0-0) 
- The `Commit` model's uniqueness constraint is `(sha, stack_id)`, confirming the schema explicitly anticipates the same `sha` existing under multiple, unrelated stacks: [3](#0-2) 
- `create_status_from_github!` then writes a `Status` record and can trigger `Hook.emit(:deployable_status, ...)`/`stack.schedule_merges` for the *victim's* stack, whose commit belongs to a repository/org the attacker never authenticated for: [8](#0-7) [9](#0-8) 

This is analogous to the Blur report's core defect: a privilege/authorization check is performed on one identity/scope (the calling org, analogous to `approvedContract`), while the actual state mutation acts on an entirely different, unchecked scope (arbitrary commit records, analogous to arbitrary token transfers) — the "approved" boundary and the "acted upon" boundary diverge.

### Impact Explanation
If a victim stack's `shipit.yml` uses `ci.require`/`ci.blocking` and `continuous_deployment: true` (documented in `README.md`), a forged successful status for a commit under that stack can move it from "blocked/pending" to "deployable", triggering `stack.schedule_merges` and continuous delivery evaluation — i.e., an **unauthorized deploy** of the victim's stack, using an attacker's own, unrelated GitHub organization credentials. This matches the required Critical-tier impact ("unauthorized deploy") in the rules.

### Likelihood Explanation
Exploitability requires: (1) the attacker legitimately controls some GitHub org/repo with a Shipit-configured webhook (a normal, unprivileged Shipit user relative to the victim stack — not a Shipit session/API token/webhook secret of the victim), and (2) the attacker can get a commit with an identical SHA to the victim's target commit into their own repository, which is feasible if the target commit is derived from a public repo/PR (fork, cherry-pick preserving parents/timestamps, or direct object import), then trigger/replay a `status` event referencing that SHA in their own repo. This is a realistic path for any semi-public/OSS-adjacent Shipit deployment tracking commits also present in forks or upstream/downstream repos.

### Recommendation
Scope `StatusHandler#process` (and any other handler using bare `Commit.where(sha:)`) through `stacks` (derived from the payload's `repository.full_name`, as `PushHandler`/`CheckSuiteHandler` already do), e.g. `stacks.flat_map(&:commits).where(sha: params.sha)`, so a status can only be applied to commits belonging to the repository that the webhook's own verified organization actually owns.

### Proof of Concept
1. Attacker owns `github.com/attacker-org/repo`, with a Shipit GitHub App installed and its own `webhook_secret`.
2. Attacker identifies a commit SHA `S` already tracked by Shipit under `victim-org/victim-repo`'s stack (e.g., a public PR commit).
3. Attacker imports the identical git object into `attacker-org/repo` (e.g. via `git fetch`/`git push` preserving the object, or by cherry-picking with identical author/committer/timestamps/parents) so it has the same SHA `S`.
4. Attacker sets a commit status on `S` in their own repo via the GitHub Statuses API (`state: success`), causing GitHub to send a `status` webhook signed with `attacker-org`'s `webhook_secret`.
5. `WebhooksController#verify_signature` succeeds (correct org, correct secret). [10](#0-9) 
6. `StatusHandler#process` runs `Commit.where(sha: 'S')`, matching the victim's `Commit` row, and calls `create_status_from_github!`, marking it `success` and potentially triggering deployment logic on the victim's stack. [1](#0-0)

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([

        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",

      ].join(' '))
    end
