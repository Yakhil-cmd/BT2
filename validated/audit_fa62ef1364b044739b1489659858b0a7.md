### Title
Pre-EIP155 Unprotected Legacy Transactions Bypass ChainId Validation, Enabling Cross-Chain Replay Attacks — (`blockchain/tx_pool.go`, `blockchain/types/transaction_signing.go`)

---

### Summary

Kaia's transaction pool and signer unconditionally accept pre-EIP155 legacy transactions (those with V = 27 or V = 28) without verifying that the transaction belongs to the Kaia chain. The `chainId` guard in `validateTx` is gated behind `tx.Protected()`, and the `EIP155Signer.Sender()` falls back to `HomesteadSigner` for unprotected transactions, which performs no chain-binding check at all. Any pre-EIP155 Ethereum transaction whose sender holds a KAIA balance can be replayed verbatim on Kaia, draining that balance.

---

### Finding Description

**Root cause 1 — tx pool chainId check is conditional (`blockchain/tx_pool.go`)** [1](#0-0) 

The guard reads:
```go
if tx.Protected() && tx.ChainId().Cmp(pool.chainconfig.ChainID) != 0 {
    return ErrInvalidChainId
}
```
When `tx.Protected()` is `false` (V = 27 or V = 28), the entire chainId comparison is skipped. The transaction proceeds to sender recovery and balance checks with no chain-binding enforcement.

**Root cause 2 — `EIP155Signer.Sender()` falls back to `HomesteadSigner` for unprotected transactions (`blockchain/types/transaction_signing.go`)** [2](#0-1) 

```go
func (s EIP155Signer) Sender(tx *Transaction) (common.Address, error) {
    ...
    if !tx.Protected() {
        return HomesteadSigner{}.Sender(tx)   // no chainId check
    }
    if tx.ChainId().Cmp(s.chainId) != 0 {    // only reached for protected txs
        return common.Address{}, ErrInvalidChainId
    }
    ...
}
```

`HomesteadSigner.Sender()` recovers the sender purely from the ECDSA signature over `(nonce, gasPrice, gas, to, value, data)` — no chain identifier is included in the signed hash. [3](#0-2) 

**`Protected()` definition — V = 27 or V = 28 means unprotected** [4](#0-3) 

**Confirmed by an existing passing test (`blockchain/tx_pool_test.go`)**

`TestHomesteadTransaction` decodes a real unprotected Homestead transaction, funds the sender, and asserts `pool.AddRemote(tx)` returns `nil` — i.e., the pool accepts it without error: [5](#0-4) 

This test is not marked as expected-to-fail; it documents and validates the permissive behavior.

---

### Impact Explanation

An attacker who finds any pre-EIP155 Ethereum transaction (V = 27 or V = 28) where the original sender also holds a KAIA balance can:

1. Copy the raw RLP-encoded transaction bytes verbatim.
2. Submit them to Kaia via `eth_sendRawTransaction`.
3. The tx pool accepts the transaction (no chainId rejection for unprotected txs).
4. `ValidateSender` → `Sender` → `HomesteadSigner.Sender` recovers the correct sender address.
5. The state transition executes: the victim's KAIA balance is debited and the `to` address (controlled by the attacker) is credited.

The victim's nonce is consumed and their KAIA is transferred without their knowledge or consent. This is a direct, unauthorized transfer of KAIA from a victim account.

---

### Likelihood Explanation

- Pre-EIP155 Ethereum transactions are publicly visible on Etherscan and other explorers. Millions exist.
- Many Ethereum addresses that sent pre-EIP155 transactions also hold KAIA (Kaia is EVM-compatible and shares the same address space).
- The attack requires no privileged access, no key material, and no on-chain setup — only the raw hex of a historical transaction.
- The attacker does not need to know the victim's private key.

---

### Recommendation

Reject unprotected (pre-EIP155) legacy transactions at the tx pool entry point. Change the guard in `validateTx` from a conditional to an unconditional rejection:

```go
// blockchain/tx_pool.go
if !tx.Protected() {
    return ErrInvalidChainId  // or a dedicated ErrUnprotectedTransaction
}
if tx.ChainId().Cmp(pool.chainconfig.ChainID) != 0 {
    return ErrInvalidChainId
}
```

Equivalently, `EIP155Signer.Sender()` should return `ErrInvalidChainId` instead of delegating to `HomesteadSigner` when `!tx.Protected()`:

```go
// blockchain/types/transaction_signing.go
if !tx.Protected() {
    return common.Address{}, ErrInvalidChainId
}
```

The existing `TestHomesteadTransaction` test in `blockchain/tx_pool_test.go` (line 531) should be updated to assert that `pool.AddRemote(tx)` returns an error after this fix.

### Proof of Concept

1. Take any pre-EIP155 Ethereum transaction. For example, the first-ever Ethereum transaction:
   ```
   0xf86780862d79883d2000825208945df9b87991262f6ba471f09758cde1c0fc1de734827a69801ca088ff6cf0fefd94db46111149ae4bfc179e9b94721fffd821d38d16464b3f71d0a045e0aff800961cfce805daef7016b9b675c137a6a41a548f7b60a3484c06a33a
   ```
   This transaction has V = 0x1c (28), so `tx.Protected()` returns `false`.

2. Fund the sender address (`0xA1E4380A3B1f749673E270229993eE55F35663b4`) with KAIA on a Kaia node.

3. Submit the raw transaction:
   ```bash
   curl http://<kaia-rpc>:8551 -X POST -H "Content-Type: application/json" \
     --data '{"jsonrpc":"2.0","method":"eth_sendRawTransaction",
              "params":["0xf86780862d79883d2000825208945df9b87991262f6ba471f09758cde1c0fc1de734827a69801ca088ff6cf0fefd94db46111149ae4bfc179e9b94721fffd821d38d16464b3f71d0a045e0aff800961cfce805daef7016b9b675c137a6a41a548f7b60a3484c06a33a"],
              "id":1}'
   ```

4. The tx pool accepts it (matching the behavior asserted in `TestHomesteadTransaction`). The state transition executes, transferring KAIA from the victim to `0x5df9b87991262f6ba471f09758cde1c0fc1de734` — without the victim's private key ever being used on Kaia.

func isProtectedV(V *big.Int) bool {
	if V.BitLen() <= 8 {
		v := V.Uint64()
		return v != 27 && v != 28 && v != 1 && v != 0
	}
	// anything not 27 or 28 is considered protected
	return true
}

// Protected says whether the transaction is replay-protected.
func (tx *Transaction) Protected() bool {
	if tx.IsLegacyTransaction() {
		v := tx.RawSignatureValues()[0].V
		return v != nil && isProtectedV(v)
	}
	return true
}
