## Title
Signed messages (`is_valid_signed_package`) omit any network/chain identifier from the signed hash, enabling cross-network and cross-context replay of otherwise valid off-chain signatures - (File: `object_hash.js`, `signed_message.js`)

### Summary
Ocore's off-chain "signed message" mechanism — used by AAs via `is_valid_signed_package()`/`is_valid_sig()` and by peer-to-peer contracts (payment channels, prosaic contracts) — hashes only a small, author-controlled whitelist of fields (`signed_message`, `authors`, `last_ball_unit`, `timestamp`, `version`) and *never* includes the `alt` field that separates mainnet from testnet, unlike ordinary unit signing. This is directly analogous to the zkSync finding where `reserved[0]==0` strips `chainId` from the signed payload of legacy transactions, permitting replay of a signature outside the context it was authorized for.

### Finding Description
For regular DAG units, `getUnitHashToSign()` hashes `getNakedUnit(objUnit)`, which retains the unit's `alt` field [1](#0-0) , and `getNakedUnit` does not strip `alt` [2](#0-1) . Because `alt` is `'1'` on mainnet and `'2'` on testnet [3](#0-2) , ordinary unit signatures are implicitly bound to one network.

However, the "signed package" object built for off-chain authorization (`signMessage()` in `signed_message.js`) is constructed with only `version`, `signed_message`, and `authors` — no `alt` at all [4](#0-3) . `validateSignedMessage()` explicitly whitelists the same restricted field set (`signed_message`, `authors`, `last_ball_unit`, `timestamp`, `version`) and rejects anything else, but it never requires or checks a network identifier [5](#0-4) . The hash that is actually signed/verified, `getSignedPackageHashToSign()`, only hashes whatever fields exist on the package (again from that restricted whitelist) — there is no code path that mixes `alt`/chain context into it [6](#0-5) .

Address derivation (`chash160` of an address definition) is likewise network-independent — the same private key/definition produces the identical address string on mainnet and testnet, since `getChash160` does not fold in `alt` [7](#0-6) . `is_valid_signed_package` in the oscript/AA formula evaluator verifies only that the package was signed by the specified `address` and (optionally, only if the author included it) that `last_ball_unit` is a stable unit — it performs no binding to network, to the AA's own address, or to any caller-supplied session/nonce unless the AA script does so itself [8](#0-7) , [9](#0-8) .

This mirrors the reported zkSync bug precisely: a protocol-level signing mechanism has an *optional* binding to network/chain context (there `reserved[0]`/`chainId`, here `alt`), and when that binding is omitted — which, for signed packages, is the *only* option, since `alt` can never be included — a signature produced for one context (e.g. testnet, or a different AA instance) validates successfully in another. The included sample contract `test/samples/payment_channels.oscript` demonstrates that AA authors are expected to manually re-implement this binding themselves (checking `signed_message.channel != this_address` and a monotonic `period` counter) [10](#0-9)  — exactly the kind of ad-hoc, developer-responsibility mitigation that the zkSync judges criticized as insufficient at the protocol layer.

### Impact Explanation
Any AA that relies on `is_valid_signed_package`/`is_valid_sig` to authorize state changes or fund releases based on an off-chain counter-signature (payment channels, prosaic/arbiter contracts, oracle-style signed data feeds) is exposed to replay if the AA author does not independently invent and enforce a nonce/context-binding field. Because the protocol itself supplies no chain/network separator and no automatic binding to the verifying AA's own address, a signature legitimately produced for one channel/AA/network can be resubmitted by an unprivileged trigger sender against a different, identically-coded AA instance (or the same AA on the other network) that a naive author deployed without manual protection, resulting in AA fund loss or freezing and unauthorized state transitions. This satisfies "AA fund loss or freezing" and "double-spend" style impact.

### Likelihood Explanation
Exploitation requires: (1) an AA/contract author using `is_valid_signed_package`/off-chain signed messages for authorization (a documented, supported ocore pattern), and (2) that author omitting explicit context binding (channel/instance identifier, nonce, network tag) inside `signed_message` — which the protocol does not mandate or automatically supply. Given that even the reference sample needed hand-rolled protection, and that `alt` is structurally excluded from every signed package regardless of author intent, this is a systemic footgun rather than a rare misconfiguration, making likelihood moderate-to-high for any nontrivial AA relying on off-chain co-signing.

### Recommendation
Make `getSignedPackageHashToSign()`/`signMessage()`/`validateSignedMessage()` mandatorily include a network/chain discriminator (e.g. `alt`) in the hashed/signed structure, analogous to how ordinary unit signing already retains `alt` via `getNakedUnit`. Additionally, consider requiring `is_valid_signed_package` callers (or the formula function itself) to bind the verified package to the evaluating AA's own address and/or a caller-supplied nonce by default, rather than leaving this entirely to oscript authors.

### Proof of Concept
1. Attacker/operator obtains a `signed_message` package (e.g. an `amount_spent` update) legitimately signed by an address on testnet, or intended for AA instance A, via `signMessage()` (which never sets `alt`) [4](#0-3) .
2. Because the same address (chash160) exists identically on mainnet (address derivation is network-agnostic) and the signed hash never contains `alt` [6](#0-5) , the attacker submits the identical `signed_message` object as `trigger.data` to a mainnet AA (or to AA instance B running the same code) that calls `is_valid_signed_package(trigger.data.pkg, addr)` without independently checking a channel/instance-specific field.
3. `validateSignedMessage()` passes because it only checks the whitelisted fields, signature validity, and (if present) `last_ball_unit` staleness — no network or instance check exists [9](#0-8) .
4. The AA processes the replayed authorization as genuine, releasing funds or mutating state it should not have, exactly mirroring the zkSync scenario where omission of `chainId` from the signed payload let a transaction/authorization validated for one context be replayed in another.

function getUnitHashToSign(objUnit) {

	for (var i=0; i<objNakedUnit.authors.length; i++)
