### Title
Unauthenticated `sender` binding in `PreStxOp`/`StackStxOp` allows locking a victim's STX without their signature - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` derives the future `StackStxOp.sender` solely from Bitcoin output[0]'s address, with no cryptographic binding to the key that later spends output[1]. An attacker can craft a `PreStxOp` whose output[0] encodes a victim's `StacksAddress` while funding/controlling output[1] themselves, then submit a `StackStxOp` spending that output[1], causing the PoX contract's `stack-stx` to run with `tx-sender` = victim while the attacker chooses `reward-addr`.

### Finding Description
The broken equality: **"the STX-locking authority == the principal whose signature authorized the lock"** — i.e. `sender` in `StackStxOp` should only ever be a principal that cryptographically authorized the corresponding Bitcoin spend, since this `sender` is fed directly into `stack-stx` as `tx-sender` without any Stacks-transaction-level signature check.

Code path:
1. `PreStxOp::parse_from_tx` ( [1](#0-0) ) takes `outputs.get(0)` — the Bitcoin address of the **first output** — and converts it directly into a `StacksAddress` with no check that this address is controlled by the same key(s) that sign the transaction's inputs.
2. `StackStxOp::get_sender_txid` ( [2](#0-1) ) only verifies that the StackStx transaction's input references `(pre_stx_txid, vout=1)` — it enforces a UTXO chain, not a key-identity chain.
3. `Burnchain::classify_transaction` resolves `pre_stx_txid`, looks up the `PreStxOp` via `pre_stx_op_map`/`find_burnchain_op`, and passes `pre_stack_stx.output` as `sender` into `StackStxOp::from_tx` ( [3](#0-2) ).
4. `StackStxOp::parse_from_tx` also independently derives `reward_addr` from the **StackStxOp transaction's own output[0]** ( [4](#0-3) ) — fully attacker-controlled.
5. `StacksChainState::process_stacking_ops` invokes `tx.run_contract_call(&sender.clone().into(), None, ..., "stack-stx", &args, ...)` ( [5](#0-4) ), directly setting `tx-sender` to the attacker-chosen victim address inside the Clarity call — bypassing the normal Stacks-transaction signature-verification path entirely (this is a burnchain-op-triggered call, not a signed Stacks transaction).
6. Inside `pox-4.clar`'s `stack-stx`, the only check on funds is `(>= (stx-get-balance tx-sender) amount-ustx)` ( [6](#0-5) ) — this only checks that the victim (now impersonated as `tx-sender`) has sufficient balance; it does not (and structurally cannot) verify that the victim authorized this specific call, since PoX-contract logic has no visibility into how `tx-sender` was set by the burnchain-op path.

No code anywhere binds the Bitcoin key used to author the `PreStxOp` (whose output[0] encodes the victim's address) to the Bitcoin key later used to spend output[1] in the `StackStxOp`. The attacker needs neither the victim's Stacks private key nor any Bitcoin key associated with the victim.

Exploit flow: Attacker (fully funding both transactions from their own UTXOs) broadcasts:
- Tx A (`PreStxOp`, opcode `PreStx`): output[0] = victim `StacksAddress`-equivalent Bitcoin address, output[1] = dust payable to an attacker-controlled key.
- Tx B (`StackStxOp`, opcode `StackStx`): input spends Tx A's output[1] (signed by attacker's key), output[0] = attacker's PoX reward address, data = desired `stacked_ustx`/`num_cycles`/`signer_key`.

Result: `stack-stx` executes with `tx-sender` = victim, locking the victim's real STX balance for `num_cycles` reward cycles, with `reward-addr` fully controlled by the attacker.

### Impact Explanation
- Victim's STX get locked (frozen from their own use) for up to `POX_MAX_NUM_CYCLES` reward cycles without their consent or signature.
- PoX/BTC rewards attributable to the locked STX are steered to an attacker-chosen `reward_addr`, i.e. theft of staking rewards that should accrue to the (unwitting) locker.
- Repeatable against any address holding sufficient unlocked STX and not already stacking/delegating, each time the attacker can afford dust-output Bitcoin fees; each successful op consumes only trivial Bitcoin transaction fees.
- Matches Critical severity: theft of locked-STX-derived (PoX/sBTC-adjacent) rewards, and an unsigned stacking action locking value the attacker never owned or was authorized to commit.

### Likelihood Explanation
- Preconditions: victim must hold ≥ stacking-minimum unlocked STX, not already stacking, not delegating, and the active PoX cycle must accept a new `stack-stx` call for that principal.
- No privileged role, node access, or victim cooperation is required — the attacker only needs to broadcast two ordinary Bitcoin OP_RETURN transactions funded from their own wallet.
- Any Stacks/Bitcoin address holder is a potential attacker; the barrier to entry is minimal (dust amounts + fees).
- Fully repeatable against distinct victim addresses; each attempt costs only Bitcoin transaction fees.

### Recommendation
Cryptographically bind the `PreStxOp.output` (the future stacker) to the Bitcoin key(s) that spend the corresponding `StackStxOp` input, e.g. by requiring that the `PreStxOp`'s designated sender address be derivable from (or explicitly co-signed by) the same key that authorizes spending of output[1], or by deprecating/removing the legacy burnchain-op stacking path (`PreStxOp`/`StackStxOp`) in favor of exclusively signed Clarity `stack-stx` calls (which already require `tx-sender`'s own signature). At minimum, require the StackStx-triggering Bitcoin input to be provably controlled by the same principal as `PreStxOp.output`.

### Proof of Concept
Rust integration test plan (mirroring existing tests in `stack_stx.rs` and `neon_integrations.rs`):
1. Set up a regtest-style chainstate with `victim_addr` holding N unlocked STX and `attacker` holding separate BTC UTXOs (attacker owns no STX commitment to `victim_addr`).
2. Construct `pre_stx_op = PreStxOp { output: victim_addr, ... }` inside a Bitcoin transaction whose output[1] is payable to `attacker_btc_key`, funded and signed entirely by `attacker`'s own UTXOs (no victim signature anywhere).
3. Submit via `btc_regtest_controller.submit_operation` as in existing tests (e.g. pattern in `nakamoto_integrations.rs` lines ~5076-5106).
4. Construct and submit `stack_stx_op` Bitcoin transaction whose sole input spends `pre_stx_op`'s output vout=1, signed by `attacker_btc_key`, with `reward_addr` = `attacker_reward_addr`, `stacked_ustx` = N.
5. Mine the blocks, run `Burnchain::classify_transaction`/`process_stacking_ops`.
6. Assert: `stack-stx` receipt is `Ok(Response{committed: true, ...})`, `(stx-account victim_addr)` shows `locked = N`, `stacking-state` for `victim_addr` records `pox-addr = attacker_reward_addr` — despite `victim_addr`'s private key never signing any transaction (Bitcoin or Stacks).
7. Compare both sides of the equality: expected `locked-stx-owner-authorization == victim_addr's signature`; actual `locked-stx-owner-authorization == attacker's Bitcoin signature only`, proving the equality is broken.
