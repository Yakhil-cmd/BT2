### Title
Unsanitized `submodule_git_url` from repo Contents API reaches victim terminal via `fmt.Errorf` in `fetchFile` - ([File: pkg/cmd/repo/read-file/http.go])

### Summary
When `gh repo read-file` resolves a path that is a git submodule, `fetchFile` builds an error message that embeds `content.SubmoduleGitURL` verbatim, even though the adjacent code comment explicitly states the intent to avoid smuggling escape sequences into output by using only the API-sanitized `content.Path`. `submodule_git_url` is derived from the `.gitmodules` file, which is fully attacker-controlled content in a repo the attacker publishes.

In `fetchFile` (pkg/cmd/repo/read-file/http.go), the `case "submodule":` branch does: [1](#0-0) 

The comment right above explicitly warns "so a crafted path cannot smuggle terminal escape sequences into our output" and the fix applied is to use `content.Path` instead of the raw user-supplied `filePath` — but this only protects the *path*, not `content.SubmoduleGitURL`, which is passed through unmodified into `fmt.Errorf`. `SubmoduleGitURL` is populated directly from the GitHub Contents API's `submodule_git_url` JSON field [2](#0-1) , which in turn reflects the submodule URL an attacker writes into `.gitmodules` in their own repository — a value they fully control and can set to contain ANSI/terminal escape sequences (e.g. `git@github.com:x/y\x1b]0;pwned\x07`).

This error is returned up through `fetchFile` → `readFileRun` → the command's `RunE` return value [3](#0-2) , where it becomes the top-level command error, ultimately printed to the victim's terminal (stderr) by the CLI's generic error-printing path in `cmd/gh` / `internal/ghcmd`. That path is separate from `opts.IO.ContentOut`, so the `iostreams.ContainsEscapeSequence` guard and `SetContentSanitization` mechanism used elsewhere in `readFileRun` for actual file *content* [4](#0-3)  do not apply to this error string at all — the sanitization design only covers `file.Content`, not diagnostic error text.

### Impact Explanation
An attacker who gets a victim to run `gh repo read-file <path> --repo attacker/repo` (or any repo where the attacker controls a `.gitmodules` entry, e.g. via a PR branch/fork the victim inspects) against a path that resolves to a submodule can inject raw ANSI/terminal escape sequences into the victim's terminal output. This matches GitHub's "terminal escape sequence injection" bounty class — potential impact includes terminal title spoofing, cursor/screen manipulation, hiding/obscuring subsequent output, or (depending on victim's terminal emulator) more severe terminal-injection attacks. It does not achieve remote code execution or credential theft by itself, so impact is scoped to terminal manipulation/output spoofing.

### Likelihood Explanation
Fully attacker-controlled and remotely reachable with no privileges beyond publishing a repository: the attacker adds a submodule entry with a crafted URL to a repo (or fork/PR) and waits for the victim to run `gh repo read-file` against that submodule path. This is a normal command usage pattern reachable purely by the victim inspecting attacker-supplied content, and reproducible every time the victim's terminal is not otherwise sanitizing escape sequences.

### Recommendation
Sanitize or strip terminal escape sequences from `content.SubmoduleGitURL` (and similarly reconsider `content.Target` in the symlink branch, which has the same issue) before interpolating into `fmt.Errorf`, consistent with the stated intent in the code comment. Use `iostreams.ContainsEscapeSequence`/existing sanitization utilities on these fields, or quote/escape non-printable bytes before including them in any error string that is written to the terminal.

### Proof of Concept
Go test using httpmock to simulate the Contents API response for a submodule with a malicious `submodule_git_url`:
```go
func TestFetchFile_SubmoduleGitURLEscapeSequence(t *testing.T) {
    reg := &httpmock.Registry{}
    reg.Register(
        httpmock.REST("GET", "repos/OWNER/REPO/contents/vendor/mod"),
        httpmock.StringResponse(`{
            "type": "submodule",
            "path": "vendor/mod",
            "sha": "deadbeef",
            "submodule_git_url": "git@github.com:x/y\u001b]0;PWNED\u0007"
        }`),
    )
    httpClient := &http.Client{Transport: reg}
    repo, _ := ghrepo.FromFullName("OWNER/REPO")

    _, err := fetchFile(httpClient, repo, "vendor/mod", "")
    require.Error(t, err)
    // Assert the raw escape byte made it into the error string unsanitized
    require.Contains(t, err.Error(), "\x1b]0;PWNED\x07")
}
```
Expected (vulnerable) result: the assertion passes, showing the raw escape sequence is present in the error text that `readFileRun` returns and that gets printed to the victim's terminal. After the fix, the escape bytes should be stripped/escaped and the assertion should fail.
