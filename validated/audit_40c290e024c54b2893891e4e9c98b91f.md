### Title
Repay overpayment refund pays declared excess out of pool custody without measuring receipt - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay::apply` refunds the "overpayment" — the declared `action.amount` minus outstanding debt — via `cache.transfer_out(payer, overpayment)` before/without verifying the pool actually received any tokens. When a market has zero debt, `resolve_repay` classifies the entire declared amount as excess, the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct, and the pool pays real custody to the payer while crediting nothing to the cash book. This is the same bug class as the SuiteCRM scanner: a safety check (measured receipt / debt-backed refund basis) is silently bypassed because the code path resets to a "nothing to credit, everything is excess" state on attacker-controlled input.

### Finding Description
In `repay::apply` (`contracts/pool/src/ops/repay.rs:25-34`), the flow is:

1. `accounting()` resolves the declared `action.amount` via `cache.resolve_repay(amount, position)` (`line 44`). With `current_debt_ceil == 0`, the full-close branch makes `overpayment == amount` and `net_repay == 0`.
2. The zero-share guard `net_repay == 0 || burned.raw() > 0` (`lines 48-52`) passes vacuously when `net_repay == 0`.
3. `cache.credit_cash(0)` leaves the book untouched; `apply` then calls `outcome.cache.transfer_out(payer, outcome.overpayment)` (`line 32`), which sends the full declared amount from the pool's token balance to `payer`.

The refund derives from a *declared* inbound amount, not from the pool's measured balance delta (`INV-ACCT-03` requires measured receipt for token-funded credit, but the refund side has no symmetric check and debits neither `cash` nor passes `require_reserves`). The repository's own test `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (`contracts/pool/tests/flows.rs:3589-3611`) pins this: a `repay` of `custody_before` against a market with no debt and no inbound transfer credits `actual_amount == 0` while draining custody to the payer. The test comment notes `ops::recapitalize::apply` shares the same refund gap for the excess over the shortfall.

### Impact Explanation
Theft of user funds / protocol insolvency. An unprivileged payer can call `repay` on any market with little or no outstanding debt, declare `amount` equal to the pool's token custody, and receive that amount back as an "overpayment refund" — without transferring anything in and without the refund touching the tracked cash book. Repeating across markets/hub books drains supplier-backed reserves; suppliers' share claims remain on the book but the underlying tokens are gone, producing insolvency and permanent loss for suppliers and remaining borrowers' collateral backing.

### Likelihood Explanation
The attack requires only: (a) a market whose outstanding debt is smaller than its token custody (a no-debt market makes the whole declared amount "excess"), and (b) the ability to reach `pool.repay` — the harness test invokes it directly with a freshly generated `payer` and no seeded auth, and the same refund path is exercised via controller repay legs where the declared action amount, not the measured receipt, sizes the refund. No privileged role, oracle manipulation, timing, or reentrancy is needed; it is a single-call arithmetic path. One residual uncertainty: whether production `pool.repay` enforces a controller-only caller gate in `lib.rs`; the indexed test evidence shows the drain succeeds via the public client call, and even if a caller check exists, the controller-driven repay path still computes refunds from declared amounts rather than measuring what the pool received, so the gap warrants verification of every caller.

### Recommendation
- Compute the refund from the measured inbound receipt: snapshot the pool's token balance before the leg, and cap `overpayment` at `min(declared excess, measured_receipt)` inside `resolve_repay`/`accounting` — never refund more than the balance increase the leg produced.
- Route the refund through the cash book (debit `cash` or call `require_reserves`) so refunds cannot pay out of untracked custody.
- Apply the same fix to `ops::recapitalize::apply`, which the codebase documents as sharing the identical declared-amount refund gap.
- Tighten `RepayRoundsToZeroShares` so a `net_repay == 0` leg with a nonzero refund cannot silently succeed as a no-op withdrawal.

### Proof of Concept
Pinned by `contracts/pool/tests/flows.rs:3589-3611`:

```rust
// Market with supply-funded custody and zero borrowed debt.
let custody_before = token.balance(&t.pool);
let before = t.state_snapshot();
assert_eq!(before.cash, custody_before);
assert_eq!(before.borrowed, 0);

// Attacker calls repay with NO inbound transfer, declaring amount = custody.
let credited = t
    .client()
    .repay(&payer, &t.ract(0, custody_before))
    .get_unchecked(0)
    .actual_amount;

assert_eq!(credited, 0);                 // no debt retired, nothing credited
assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
// payer's balance increases by custody_before; pool custody drained;
// cash book unchanged => book now overstates backing by custody_before.
```

Root cause: `contracts/pool/src/ops/repay.rs:44-57` — `resolve_repay` returns `overpayment = declared_amount - debt` from declared input, and `transfer_out(payer, overpayment)` at line 32 pays it out of real custody without a measured-receipt bound.
