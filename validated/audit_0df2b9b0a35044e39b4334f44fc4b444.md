### Title
Unbounded swap-route callbacks can join the caller’s authorization tree and steal unrelated wallet assets - ([File: `contracts/controller/src/strategies/swap.rs`])

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept caller-supplied route bytes and execute them through the configured router after granting only the controller’s own input-transfer authorization. The controller validates only the input spend and positive output receipt; it does not bound the authorization tree that payload execution attaches to the caller’s top-level authorization. A malicious route can therefore include attacker-controlled code that performs an unrelated token transfer from the caller. If the caller signs the simulated authorization tree containing that child transfer, the route can steal wallet assets unrelated to the lending operation while still satisfying the controller’s swap accounting.

### Finding Description
`process_swap_collateral` authenticates the caller, authorizes the owner or delegate for the account, withdraws collateral into controller custody, and forwards the user-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [1](#0-0)  Similarly, `process_swap_debt` borrows the new debt asset and forwards the supplied `swap` bytes to `swap_tokens_or_passthrough`. [2](#0-1) 

For distinct input and output tokens, `swap_tokens` snapshots the controller’s input and output balances, authorizes exactly one `token_in.transfer(controller, router, amount_in)` invocation with no sub-invocations, and invokes `router.execute_strategy`. [3](#0-2)  The authorization helper explicitly grants only that exact transfer and attaches no sub-invocations. [4](#0-3) 

The post-router checks reject only controller input-balance growth, input spending above `amount_in`, or non-positive measured output. [5](#0-4)  They do not inspect the caller’s Soroban authorization tree and therefore cannot reject an unrelated child `token.transfer(caller, attacker, amount)` recorded below the caller’s `swap_collateral` authorization.

The repository’s adversarial test demonstrates the reachable sequence: the attacker-controlled hop contract calls `token.transfer(victim, attacker, amount)` during route execution. [6](#0-5)  Simulation records that unrelated transfer as a child of Alice’s `swap_collateral` authorization, and the transfer succeeds when that poisoned tree is signed. [7](#0-6)  The enforcing-mode test confirms that signing the poisoned child causes Alice’s unrelated wallet token balance to reach zero and the attacker to receive the full balance. [8](#0-7) 

### Impact Explanation
This is theft of user funds beyond the routed amount. A victim may sign a strategy transaction that correctly withdraws collateral and produces positive measured output, while a malicious venue called by that route steals any unrelated token held in the victim’s wallet. The controller’s exact input authorization protects only the controller-held strategy input; it does not protect the caller from extra child authorizations introduced deeper in execution.

The loss is not limited by the swap amount, router output, final health factor, or collateral floor. It is limited only by wallet balances that malicious code can transfer through a signed child authorization.

### Likelihood Explanation
Exploitation requires the victim to submit a strategy with attacker-influenced route bytes and to sign the authorization tree generated by simulation, including the malicious transfer. Users who obtain route bytes from an untrusted quote source, route builder, web application, or pasted transaction template can satisfy those conditions.

The route itself can produce fair output, so transaction simulation may show the intended collateral conversion while also including an extra child authorization. A wallet or client that does not decode and display every child of the strategy authorization can make the transaction appear safe.

### Recommendation
Constrain route execution so arbitrary contract addresses cannot attach unrelated authorization children below a lending strategy. Prefer a venue allowlist or immutable venue registry instead of accepting arbitrary pool addresses in route payloads.

At minimum, clients and wallets must decode the complete signed authorization tree for `swap_collateral`, `swap_debt`, `multiply`, `repay_debt_with_collateral`, and direct router calls. They should reject any child authorization other than the expected strategy-specific token pulls. This client mitigation should be accompanied by route-level validation because users can still be induced to sign opaque trees.

### Proof of Concept
The harness constructs an attacker-controlled `RogueHopPool` whose `swap` function executes:

```rust
token::Client::new(&env, &wallet_token)
    .transfer(&victim, &to, &amount);
``` [9](#0-8) 

The test then invokes controller `swap_collateral` with Alice as caller, her `account_id`, `current` set to USDC, `from_amount` set to `50_000_000_000`, `new` set to ETH, and `swap` containing the malicious route. [10](#0-9) 

Simulation records the unrelated `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)` as a child of Alice’s `swap_collateral` authorization. [11](#0-10)  In enforcing mode, signing that recorded tree succeeds and leaves Alice with zero wallet tokens while crediting the attacker with `77_770_000_000`. [8](#0-7)

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
