### Title
`StatusHandler#process` resolves commits by `sha` alone across all repositories, allowing cross-repository status/CI sabotage - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely via `Commit.where(sha: params.sha)` with no comparison against `params.repository.full_name`, `params.repository.owner`, or the commit's own stack/repository. Because the webhook signature is only verified per-organization (not per-repository), any repository within the same GitHub organization can post a `status` webhook naming an arbitrary SHA and flip the state of a commit belonging to a completely different repository/stack in that org.

### Finding Description
The claimed binding is: `Status mutation authorized by an org's webhook_secret == Status confined to the repository named in that org's payload`. Tracing the code shows this binding is false.

- `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` and validates the HMAC signature against `Shipit.github(organization: repository_owner).verify_webhook_signature`, i.e., authentication is scoped to the **organization**, not the individual repository [1](#0-0) .
- Once the signature check passes, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` dispatches to `StatusHandler#process`, which does:
```ruby
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 
- There is no filter on `params.repository` at all — the `params` schema for `StatusHandler` doesn't even require a `repository` key [3](#0-2) , and the query matches any `Commit` row with that `sha`, regardless of which `stack`/`repository` it belongs to.
- `Commit#create_status_from_github!` then calls `add_status`, which updates `status`, triggers `deployable?`/`blocked?` recomputation, and can invoke `stack.schedule_merges` and `ContinuousDeliveryJob` [4](#0-3) [5](#0-4) .

Exploit flow: Attacker owns/controls Repository B in the same GitHub org as victim Repository A (both onboarded as Shipit stacks under that org). Attacker scripts their own CI/webhook delivery (or crafts an HTTP POST directly, since GitHub allows repo owners to configure webhooks and payload content freely) to send a `status` event where `repository.full_name = "org/B"` but `sha` is copied to equal a real commit SHA that exists in stack A (e.g., by cherry-picking/rebasing a commit so the SHA collides, or simply reusing a known SHA string in the payload — the handler never checks that the SHA actually belongs to repository B). Because the org's `webhook_secret` is shared across all repos in the org and `verify_signature` only checks the organization, the payload passes signature verification. `StatusHandler` then finds the `Commit` row for stack A with that `sha` and applies the attacker-controlled `state: failure`, flipping `blocked?`/`deployable?` to false for the victim's stack.

None of the listed guards prevent this: `verify_signature`/`verify_webhook_signature` only bind to the org, not the repo; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema for `StatusHandler` has no `repository` requirement to enforce; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` involved since webhooks are unauthenticated-by-signature only; and no model validation ties a `Status` to a specific repository at write time.

### Impact Explanation
A payload originating in the context of Repository B mutates state belonging to Repository A's stack/commit — this is the "payload for one repository mutating another's stack/commit" category, rated **Critical**. Concretely, the attacker can force any tracked commit in a sibling repository to appear as `failure`, flipping `Commit#deployable?` to `false` and `blocked?` semantics for downstream commits, which can block or disrupt continuous deployment (`schedule_continuous_delivery`), and conversely could also be used to force a `success` status on a commit that never actually passed CI in its real repository, potentially enabling an unauthorized deploy if the victim stack has `continuous_deployment?` enabled — since `create_status_from_github!` doesn't verify the status target_url/context is legitimately tied to the named repository. This is repeatable against arbitrary shared-org stacks/commits since the attacker only needs any commit SHA belonging to the victim (e.g., discoverable via the victim's public commit history or PR) and controls their own repo's webhook delivery/CI content fully.

### Likelihood Explanation
Preconditions: attacker needs to own or control a GitHub repository that is provisioned as a Shipit stack in the *same GitHub organization* as the victim stack (organizations map 1:1 to a `webhook_secret` in this app's config). This is a low-cost, realistic scenario in any multi-repo org where Shipit tracks many repos and webhook secrets are shared per-org (as configured in `secrets.yml`, `github_app.rb`). The attacker does not need any Shipit credentials, session, or GitHub App private key — they only need to be able to trigger a `status` webhook delivery from their own repo (trivial, e.g. via their own CI reporting a commit status, which GitHub relays using the shared org-level webhook secret configured on the App/Org, or, if repo-level webhooks are used instead of an org-level GitHub App installation, directly control the webhook payload). This is fully repeatable, at will, against any victim commit SHA in the same org.

### Recommendation
Scope the `Commit` lookup in `StatusHandler#process` to the repository named in the payload, not just the SHA — e.g., join through `stack: :repository` and filter by `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, mirroring the pattern already used in `PullRequest::EditedHandler#pull_request` at [6](#0-5) . Additionally require `:repository` in the `StatusHandler` params schema so malformed/missing repository payloads are rejected outright.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual)
test "status webhook from sibling repo in same org cannot mutate a victim stack's commit" do
  org = "acme"
  victim_repo = shipit_repositories(:shipit)  # full_name = "acme/victim"
  attacker_repo_full_name = "acme/attacker-repo"

  victim_stack = shipit_stacks(:shipit)
  victim_commit = victim_stack.commits.create!(sha: "a" * 40, message: "victim commit")

  # Binding under test, stated as equality BEFORE:
  # authorized_repo_for(sha) == params.repository.full_name
  assert_not_equal attacker_repo_full_name, victim_repo.full_name

  payload = {
    "sha" => victim_commit.sha,
    "state" => "failure",
    "context" => "ci/attacker",
    "repository" => { "full_name" => attacker_repo_full_name, "owner" => { "login" => org } }
  }

  # Signature check passes because it only verifies at org-level (mocked/stubbed here to simulate
  # a valid HMAC for org "acme", independent of which repo is named in payload).
  Shipit::Webhooks::Handlers::StatusHandler.new.call(ActionController::Parameters.new(payload))

  victim_commit.reload

  # AFTER: the victim commit was mutated despite the payload naming a different repository.
  assert_equal "failure", victim_commit.status.state
  assert_equal false, victim_commit.deployable?
end
```
This demonstrates the binding `authorized_repo_for(sha) == params.repository.full_name` does NOT hold after processing: the commit belongs to `acme/victim` but the mutating payload named `acme/attacker-repo`, confirming the cross-tenant sabotage.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
