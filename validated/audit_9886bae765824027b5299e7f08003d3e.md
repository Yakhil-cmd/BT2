### Title
Missing `isRunning` Check in `handleKLAYTransfer`/`handleERC20Transfer`/`handleERC721Transfer` Allows Bridge Operators to Complete Value Transfers After Bridge Is Stopped — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The Kaia service-chain bridge enforces `isRunning` at the **request** side of every value transfer but omits the same check on the **handle** (completion) side. When the bridge owner calls `setRunningStatus(false)` to halt the bridge — typically in response to an emergency or exploit — bridge operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` to settle any pending cross-chain requests, transferring or minting assets on the counterpart chain against the owner's explicit intent.

---

### Finding Description

`BridgeTransfer.sol` declares `isRunning = true` and exposes `setRunningStatus(bool)` (owner-only) to pause all bridge activity. [1](#0-0) 

Every **request** function enforces this flag before accepting a new cross-chain transfer:

- `BridgeTransferKLAY._requestKLAYTransfer`: [2](#0-1) 

- `BridgeTransferERC20._requestERC20Transfer`: [3](#0-2) 

- `BridgeTransferERC721._requestERC721Transfer`: [4](#0-3) 

However, the corresponding **handle** functions that complete the transfer on the counterpart chain contain **no** `isRunning` check:

- `handleKLAYTransfer` (lines 62–100): only checks `onlyOperators`, `_lowerHandleNonceCheck`, and `_voteValueTransfer`. [5](#0-4) 

- `handleERC20Transfer` (lines 32–73): same — no `isRunning` guard, proceeds to `mint` or `safeTransfer`. [6](#0-5) 

- `handleERC721Transfer` (lines 29–71): same — no `isRunning` guard, proceeds to `mintWithTokenURI` or `transferFrom`. [7](#0-6) 

A secondary, identical gap exists for the per-token `lockedTokens` flag: `_requestERC20Transfer` and `_requestERC721Transfer` enforce `onlyUnlockedToken(_tokenAddress)`, but `handleERC20Transfer` and `handleERC721Transfer` do not, so a locked token can still be minted/transferred on the handle side. [8](#0-7) 

---

### Impact Explanation

When the bridge owner stops the bridge (e.g., after detecting an exploit or a misconfiguration), the intent is to freeze **all** asset movement. Because the handle functions skip the `isRunning` check, operators — whether acting in good faith without realising the bridge was stopped, or acting maliciously after a key compromise — can still call `handleKLAYTransfer`/`handleERC20Transfer`/`handleERC721Transfer` to:

- Transfer KAIA from the bridge contract's balance to arbitrary recipients (`_to.call.value(_value)("")`).
- Mint unbounded ERC-20 tokens on the counterpart chain (`ERC20Mintable.mint`).
- Mint ERC-721 NFTs on the counterpart chain (`ERC721MetadataMintable.mintWithTokenURI`).
- Transfer ERC-20/ERC-721 tokens held in the bridge escrow (`safeTransfer` / `IERC721.transferFrom`).

This constitutes an **unauthorized transfer of bridged assets** after the protected `isRunning` flag has been set to `false` by the owner.

---

### Likelihood Explanation

The bridge owner's primary emergency lever is `setRunningStatus(false)`. Operators are semi-trusted relayers that run automated software; they will continue processing queued `RequestValueTransfer` events unless explicitly stopped at the software layer. Because the on-chain contract does not enforce the stop on the handle path, any operator that processes a queued event after the bridge is stopped will successfully complete the transfer. A single operator acting alone (threshold = 1) or a threshold-meeting subset acting in concert is sufficient.

---

### Recommendation

Add an `isRunning` guard to all three handle functions, mirroring the check already present in the request functions:

```solidity
// In handleKLAYTransfer, handleERC20Transfer, handleERC721Transfer:
require(isRunning, "stopped bridge");
```

For the token-lock gap, add `onlyUnlockedToken(_tokenAddress)` (or an equivalent inline check) to `handleERC20Transfer` and `handleERC721Transfer`, consistent with the guard already applied on the request side.

---

### Proof of Concept

1. Bridge is deployed; `isRunning = true`.
2. User calls `requestKLAYTransfer` on the child chain, emitting `RequestValueTransfer` with `requestNonce = N`. KAIA is locked in the bridge contract.
3. An exploit is detected. Bridge owner calls `setRunningStatus(false)` on the parent-chain bridge. New requests are blocked (`require(isRunning, "stopped bridge")`).
4. A bridge operator's relay daemon, still processing the event queue, calls `handleKLAYTransfer(txHash, from, to, value, N, blockNum, extraData)` on the parent-chain bridge.
5. `handleKLAYTransfer` checks only `onlyOperators` and `_lowerHandleNonceCheck` — both pass. `_voteValueTransfer` reaches threshold. The function executes `_to.call.value(_value)("")`, transferring KAIA to the recipient.
6. The bridge owner's emergency stop is bypassed; assets move despite `isRunning == false`. [9](#0-8) [10](#0-9)
