### Title
Cross-repository forged `success` status makes `Commit#deployable?` true regardless of unlocked `Stack#deployable?` state - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits to update purely by SHA (`Commit.where(sha: params.sha)`) with no check that the SHA belongs to a commit in the same repository that the webhook payload/signature was authenticated for. Because `Commit#deployable?` only checks the commit's own lock/status state and never checks which repository authored the status, a forged/cross-repo `success` status can flip a `victim` stack's commit to `deployable?` regardless of the independent `Stack#deployable?` (lock) gate.

### Finding Description
The claimed binding is: *repository that authenticated the webhook* == *repository whose stack/commit the status is applied to*. This does not hold.

- `WebhooksController#verify_signature` derives the signing organization from the payload's own `repository.owner.login` / `organization.login` field and validates the HMAC against that organization's configured `webhook_secret` [1](#0-0) . This only proves the payload was signed for *some* organization's GitHub App installation - it never ties the specific `sha` in the body to a commit that actually belongs to that repository.
- `StatusHandler#process` then fetches **every** `Commit` row matching the raw `sha` string, with no `stack_id`/`repository` filter, and applies the forged status to all of them: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [2](#0-1) .
- `Commit#deployable?` is purely local to the commit/stack CI state: `!locked? && (stack.ignore_ci? || (success? && !blocked?))` [3](#0-2) . Nothing here references which repository generated the underlying status.
- `Stack#deployable?` is a completely orthogonal predicate: `!locked? && !active_task? && !awaiting_provision? && deployment_checks_passed?` [4](#0-3) , gated only by `lock_reason`/`lock`/`unlock` [5](#0-4) . It has no relationship to `Commit#deployable?` or to the `StatusHandler` write path.
- The combined continuous-delivery/deploy-eligibility gate that developers rely on, `UndeployedCommit#deploy_disallowed?`, explicitly ANDs the two: `!deployable? || !stack.deployable?` [6](#0-5) . Since `victim.stack.lock_reason` is nil (unlocked) throughout the scenario, `stack.deployable?` is already `true` before the attack and stays `true` after - the attacker does not need to touch it at all. Only the `commit.deployable?` half is forged, which is sufficient because the gate is an AND across two independently-satisfiable halves and the attacker's write path (`StatusHandler`) never checks `stack.locked?`/`lock_reason` before writing the status; `Commit#add_status`/`create_status_from_github!` writes and fires `deployable_status`/`schedule_merges` hooks purely from the commit's own state transition [7](#0-6) .
- No existing guard closes this gap: `verify_signature` only checks organizational HMAC validity (not per-repo SHA ownership), `ExplicitParameters` on `StatusHandler` only validates payload shape (`sha`, `state`, etc., not repo linkage) [8](#0-7) , and there is no DB uniqueness constraint scoping `sha` to a repository — the only index found is `stack_id + sha`, not a global-uniqueness constraint, confirming the same SHA string can legitimately exist in multiple stacks/repos and all of them will be updated by one webhook.

### Impact Explanation
Any stack whose commit table contains a SHA that collides with a SHA from a different, unrelated repository (via shared git history, forks, cherry-picks, or subtree/vendor merges) will have that commit's CI status forged by a webhook that only needed to authenticate for the attacker's own organization/repo. This lets an attacker mark a `victim` stack's commit `deployable?` (or make it `failure`/blocking, causing DoS in the other direction) without the victim's real CI passing, and — critically for this question — without needing the victim stack to be unlocked at all; it already is, so the only remaining safety condition on the deploy path is neutralized. This matches "a payload for one repository mutating another's stack/commit" and can enable an unauthorized deploy via continuous delivery or a manually-triggered deploy of that commit. It is repeatable against any repository pair that shares a SHA and is bounded only by SHA-collision opportunities, not by any per-request cost.

### Likelihood Explanation
Preconditions: attacker needs a repository already onboarded to the Shipit host's GitHub App (so a `status` webhook they can trigger will pass HMAC verification for their own org), and a `victim` stack whose commit table contains a matching SHA (attainable via forks/shared history, or shared monorepo checkouts across multiple stacks). No Shipit session, API token, or GitHub team membership is required — consistent with the stated unprivileged threat model. Feasibility is high given `StatusHandler` is a public unauthenticated-mapping business-logic bug (SHA-only lookup), not one requiring any secret beyond what a legitimate CI/webhook already possesses for the attacker's own repo.

### Recommendation
Scope `StatusHandler#process` (and any other SHA-keyed webhook handler) to only update commits belonging to stacks whose `repository` matches the `repository` (`full_name`/owner+name) asserted in the webhook payload, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, shipit_repositories: { owner: ..., name: ... })`, rather than a bare `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/webhooks/status_handler_cross_repo_test.rb
test "forged status from unrelated repo makes victim commit deployable while victim stack lock is untouched" do
  victim_stack = shipit_stacks(:some_unlocked_stack)
  assert_nil victim_stack.lock_reason
  assert_predicate victim_stack, :deployable? # unlocked before

  victim_commit = victim_stack.commits.create!(sha: "deadbeef" * 5, ...)
  refute_predicate victim_commit, :deployable? # no status yet

  # forged payload authenticated for attacker's own (unrelated) repository
  forged_params = OpenStruct.new(sha: victim_commit.sha, state: "success", context: "ci/attacker")
  Shipit::Webhooks::Handlers::StatusHandler.new.call(forged_params.to_h)

  assert_predicate victim_commit.reload, :deployable?      # forged status accepted cross-repo
  assert_predicate victim_stack, :deployable?               # lock state never changed / never needed
end
```

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
