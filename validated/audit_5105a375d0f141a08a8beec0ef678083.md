## Finding: Reward-distribution invariant panic (`assert_eq!`) reachable via user stake operations during multi-block partitioned reward distribution

### Title
Unsanitized user stake-account mutation during partitioned epoch-reward distribution can trigger a consensus-wide validator panic - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
The external report's core theme — a state invariant (peg) that a staking system silently assumes will hold but does not actually enforce, leading to inconsistency between "recorded" and "actual" balances — maps to a concrete Agave analog in the partitioned-epoch-rewards distribution path. `build_updated_stake_reward` in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` compares a stake account's *current* on-chain delegation against a *stale* delegation snapshot taken at reward-calculation time, and hard-panics via `assert_eq!` if they diverge, instead of returning the `DistributionError` that the surrounding code is otherwise designed to handle gracefully. [1](#0-0) 

### Finding Description
Partitioned epoch rewards are computed once at the epoch boundary (`calculate_stake_rewards_and_commissions`) and then distributed to stake accounts over many subsequent blocks (`store_stake_accounts_in_partition` / `build_updated_stake_reward`), one partition at a time. [2](#0-1) [3](#0-2) 

At distribution time, `build_updated_stake_reward` re-loads the stake account's *current* state from `stakes_cache_accounts` and, when the `relax_post_exec_min_balance_check` feature (`adjust_delegations_for_rent`) is not active, asserts that this current delegation plus the pre-computed inflation reward exactly equals the delegation value snapshotted during the earlier calculation phase:
```
let expected_delegation = stake.delegation.stake.saturating_add(partitioned_stake_reward.inflation.stake_reward);
assert_eq!(expected_delegation, new_stake.delegation.stake, ...)
``` [4](#0-3) 

The surrounding function comment explicitly documents the assumption this relies on: *"Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."* [5](#0-4) 

However, I was unable to locate any actual enforcement inside the stake builtin program (or elsewhere in the transaction-processing path) that blocks ordinary stake instructions (`Split`, `Merge`, `Withdraw`, `Deactivate`, `Redelegate`, `MoveStake`) from being submitted by a stake account's own authority against an account that is currently queued in `partition_rewards.all_stake_rewards` awaiting distribution across the several blocks the reward interval spans. `grep` for reward-interval / `EpochRewards` gating logic under the stake program directory returned no matches — the only interval-tracking logic exists on the `Bank` side (`runtime/src/bank/partitioned_epoch_rewards/mod.rs`), not inside the stake program's instruction processors. This is consistent with normal Solana behavior where users can freely `Split`/`Merge`/`Withdraw` stake at any point in the epoch, including during the multi-block reward-distribution window.

Every other failure mode in this same function (account-not-found, lamport overflow, `set_state` failure) is handled by returning a `DistributionError` that the caller converts into a burned-reward accounting entry rather than crashing: [6](#0-5) 
Only the delegation-consistency check is implemented as a hard `assert_eq!`, i.e. an unrecoverable panic rather than a handled error — an inconsistency in the error-handling design that suggests this specific invariant violation was not anticipated as a real, reachable path, only asserted defensively.

### Impact Explanation
`distribute_partitioned_epoch_rewards` (and therefore `store_stake_accounts_in_partition` / `build_updated_stake_reward`) is called from deterministic bank-processing logic executed identically by every validator replaying the same block. If a stake account queued for a not-yet-processed reward partition has its `delegation.stake` altered (e.g., via a normal `Split` or `Merge` transaction submitted by its own authority) between the epoch-boundary calculation block and the specific later block in which its partition is distributed, the `assert_eq!` will fail on **every** validator processing that block, causing a synchronized panic in bank/block processing — i.e., a transaction-triggered cluster halt, which is one of the accepted high-severity impact classes for this scan.

### Likelihood Explanation
Reaching this code path requires:
1. The `relax_post_exec_min_balance_check` (SIMD-0392 related) feature to be inactive on the cluster for the `assert_eq!` branch to be taken instead of the `adjust_delegation_for_rent` branch.
2. A stake account to be a recipient of a nonzero reward in the current epoch (common — any actively delegated stake).
3. A normal stake instruction (`Split`, `Merge`, `Withdraw`, etc.) from that account's own authority landing in a block between reward calculation and that account's specific distribution partition — the reward-distribution window can span up to 10% of an epoch's slots, giving a meaningfully large window.
4. No stake-program-level restriction against mutating stake accounts during this window (I could not find one in the codebase).

I could **not confirm** the current mainnet/production activation status of `relax_post_exec_min_balance_check`, which directly gates whether this specific `assert_eq!` branch is reachable today, versus whether it has already been fully activated cluster-wide, which would make this path dead code. This is an important open question that limits confidence in current exploitability, though the code path itself, and the undocumented lack of enforcement of the stated invariant, is concretely present in the reviewed source.

### Recommendation
- Replace the `assert_eq!` in `build_updated_stake_reward` with a proper `DistributionError` return (mirroring the handling of `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState`), so that an unexpected delegation mismatch degrades to a burned/skipped reward rather than panicking the whole validator.
- Independently of the panic-vs-error question, verify and, if absent, add an explicit enforcement mechanism (either in the stake program or in transaction admission) that prevents/queues stake-mutating instructions on accounts that have an unresolved reward entry pending distribution, so the "stake-program restrictions" the code comment relies on actually exist.
- Confirm and document the current cluster-wide activation status of `relax_post_exec_min_balance_check`, since it determines whether the vulnerable branch is currently live.

### Proof of Concept
Conceptual reproduction (requires a devnet/local cluster with `relax_post_exec_min_balance_check` inactive):
1. Delegate a stake account and let it earn epoch rewards, so it will have a nonzero entry in `partitioned_stake_reward` for the next epoch's distribution.
2. At the epoch boundary, rewards are calculated and partitioned across multiple blocks (`distribute_partitioned_epoch_rewards`), so this account's payout is deferred to a later block in the distribution window.
3. Before that later block, submit a normal `Split` (or `Merge`/`Withdraw`) transaction from the stake account's own authority, altering `delegation.stake` on-chain.
4. When the bank reaches the block containing this account's assigned partition index, `build_updated_stake_reward` recomputes `expected_delegation` from the now-mutated on-chain state and compares it against the stale `partitioned_stake_reward.inflation.stake` snapshot, triggering the `assert_eq!` panic deterministically on all validators processing/replaying that block. [4](#0-3) 

**Caveat:** I could not fully verify from static code review alone (a) the live activation state of `relax_post_exec_min_balance_check` on production clusters, or (b) whether some other layer (e.g. a runtime check not indexed/found in this search) actually blocks stake mutation during the distribution window as the code comment claims. These would need to be confirmed in a running/test-validator environment (e.g. `solana-program-test`) to establish concrete exploitability rather than a code-level design gap.
