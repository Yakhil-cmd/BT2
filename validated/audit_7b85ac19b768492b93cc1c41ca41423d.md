### Title
Cross-repository status webhook forgery triggers unauthorized deploy — `StatusHandler#process` matches commits by SHA with no repository check - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha`, without verifying that the SHA belongs to the repository named in the webhook payload. Because signature verification (`verify_signature`) only proves the request came from *some* GitHub org configured on the Shipit instance — not that it originated from the specific repository owning the commit — an attacker who controls a repo/org onboarded to the same Shipit instance can forge a "success" status for a SHA belonging to a different, victim stack and trigger an unauthorized deploy.

### Finding Description
The broken binding: `commit.stack.repository.full_name == payload.dig('repository', 'full_name')` (i.e., "the status genuinely represents this repo's CI") is assumed but never checked.

- `Shipit::Webhooks::Handlers::StatusHandler#process` does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 
This queries `Commit` globally by `sha` across *all* stacks/repositories, with no filter tying the commit to the webhook's `repository` payload field.

- Contrast with the base `Handler` class, which defines a `stacks` helper scoped by `repository_name` from the payload (`Repository.from_github_repo_name(repository_name)&.stacks`), used correctly by other handlers such as `PushHandler`, but `StatusHandler` bypasses this scoping entirely. [2](#0-1) 

- `WebhooksController#verify_signature` resolves the GitHub App/webhook secret purely from `repository_owner` (the org named in the *attacker-controlled* payload) and validates the HMAC signature against that org's `webhook_secret`:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
``` [3](#0-2) 
This only proves the request genuinely came from GitHub for *that org's* own app/secret — it says nothing about whether the `sha` inside the payload actually belongs to a commit in that org's repository. Since `StatusHandler` never cross-checks `sha` against `repository_owner`/`repository.full_name`, a valid signature from Org B lets an attacker write a `Status` onto a `Commit` belonging to Org A's stack.

- `Commit#create_status_from_github!` → `#add_status` → `Hook.emit(:deployable_status, ...)` and updates `status`, feeding directly into `Commit#deployable?`:
```ruby
def deployable?
  !locked? && (stack.ignore_ci? || (success? && !blocked?))
end
``` [4](#0-3) 
and `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when `deployable? && stack.continuous_deployment? && stack.deployable?`. [5](#0-4) 
`Stack#trigger_continuous_delivery` then picks `next_commit_to_deploy` and calls `trigger_deploy`, creating and running a `Deploy`. [6](#0-5) 

Exploit flow:
1. Attacker reads the victim stack's current undeployed HEAD commit (tree, parents, author/committer, message, timestamps) from the target repo's public GitHub data.
2. Attacker reproduces the identical SHA1 via `git commit-tree` with identical inputs in their own repo (feasible since a git commit SHA is a pure hash of these fields and is not itself an authenticity proof).
3. Attacker's own repo (belonging to an org already onboarded to the same Shipit instance, so `Shipit.github(organization: attacker_org)` resolves to a real `webhook_secret`) sends a `status` webhook with `state: success` and that SHA. This produces a signature that legitimately validates against the attacker org's own `webhook_secret`.
4. `verify_signature` passes because it only checks the org named in the payload, and `StatusHandler#process` matches `Commit.where(sha: ...)` irrespective of which org/repo sent the webhook — writing a forged `Status` onto the victim's `Commit` row.
5. `Commit#deployable?` flips to true, `schedule_continuous_delivery` fires, and `Stack#trigger_continuous_delivery` deploys the victim's current HEAD.

Existing guards do not prevent this: `verify_signature` authenticates the sender's org, not the sha/repo relationship; `drop_unhandled_event` and `ExplicitParameters` (`params.sha`, `params.state`) validate payload shape only, not repository ownership of the sha; there is no `subset`/repository-match validator in this path.

### Impact Explanation
A forged webhook from an attacker-owned repository/org (already onboarded to the shared Shipit instance) can write a `Status` for, and trigger a `Deploy` on, an unrelated victim stack/repository — an unauthorized deploy of victim production infrastructure triggered by a payload signed for a different repository. This is repeatable against any stack whose current undeployed HEAD is public (or otherwise known) and configured with `continuous_deployment: true` and no `blocking_statuses`; because the primitive is "cross-tenant write via mismatched repository/sha binding," the blast radius spans all stacks hosted on a shared Shipit instance, matching the Critical category ("a payload for one repository mutating another's stack, commit, task or task ... or an unauthorized deploy").

### Likelihood Explanation
Preconditions: (1) attacker controls, or is a member of, some org/repo already configured with a `webhook_secret` on the target Shipit instance (multi-tenant precondition — not the victim's org); (2) the victim repo is public so its exact commit object fields are retrievable; (3) the victim stack has `continuous_deployment: true` and no effective `blocking_statuses`. Attacker cost is low: git object reconstruction via `commit-tree` with copied fields, then one HTTP POST to `/webhooks`. This is trivially repeatable against any stack matching the configuration precondition.

### Recommendation
In `StatusHandler#process` (and any other sha-keyed handler), scope the `Commit` lookup by the repository named in the webhook payload, mirroring `Handler#stacks`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This binds the write to `Repository.from_github_repo_name(payload_repository_name)`, restoring the equality between the org that signed the webhook and the org whose commit is being mutated.

### Proof of Concept
Add a minitest (outside `test/` restriction noted, but conceptually):
1. Create two fixtures: `stack_a` (victim, `continuous_deployment: true`, no blocking statuses) with `commit_a` (sha `S`, undeployed HEAD), and `stack_b` (attacker, arbitrary repo) with `commit_b` sharing the identical `sha: S` under `stack_b`.
2. Simulate `StatusHandler.call` with a payload whose `repository.full_name` is `stack_b`'s repo and `sha: S`, `state: 'success'`.
3. Assert: `commit_a.reload.statuses.count` increased (i.e., `Commit.where(sha: S)` matched both stacks' commits) and `assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_a])`, demonstrating `stack_a.trigger_continuous_delivery` / `Deploy.create` is invoked for the victim stack purely from a payload signed for `stack_b`'s repository — proving the equality `commit.stack.repository.full_name == payload['repository']['full_name']` is violated.
