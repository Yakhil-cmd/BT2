### Title
Prosaic contract acceptance signature is bound only to the `title` text, not the contract hash - forged/replayed acceptance across contracts with identical titles - (File: wallet.js)

### Summary
The `prosaic_contract_response` handler in `wallet.js` validates a peer's acceptance signature with `signed_message.validateSignedMessage()` but then checks the signed payload only against `objContract.title`, never against the unique contract hash (which is derived from `title + text + creation_date`). This is the same class of bug as the Discourse SNS issue: a cryptographically valid, correctly-signed message is accepted without binding it to the specific trusted context (there: the SNS TopicArn; here: the specific contract/hash) it was meant to authorize.

### Finding Description
When a peer accepts a prosaic contract, the wallet composes a `prosaic_contract_response` with `body.signed_message` being a signed package whose `signed_message` field is expected to equal the contract's `title` string (not the full contract hash). This is verified in the handler at [1](#0-0)  :

```
signed_message.validateSignedMessage(db, objSignedMessage, objContract.peer_address, function(err) {
    if (err || objSignedMessage.authors[0].address !== objContract.peer_address || objSignedMessage.signed_message != objContract.title)
        return callbacks.ifError("wrong contract signature");
    processResponse(objSignedMessage);
});
```

`signed_message.validateSignedMessage` in [2](#0-1)  only proves that `objSignedMessage.signed_message` was validly signed by `address` — it has no notion of "which contract" the signature is bound to. The binding to a specific contract is left entirely to the caller comparing `signed_message` against `objContract.title`.

The unique identifier of a contract, however, is `getHash()`, which incorporates `title + text + creation_date`, as seen at [3](#0-2) . Because the acceptance check in `wallet.js` compares only against `title` (a string fully controlled by whichever device offered the contract, per `createAndSend` at [4](#0-3) ), two contracts offered by the same attacker-controlled peer device with identical `title` but different `text`/terms produce different `hash` values but require the exact same signed message (`title`) to be "accepted."

This is structurally identical to the reported bug class: the signature check verifies authenticity (who signed) but omits verifying the binding to the specific object/context (which contract) the signer actually consented to — the contract analog of a missing "TopicArn" check.

### Impact Explanation
An attacker who is a paired-device counterparty (in-scope actor: "private-payment counterparty" / paired device) can:
1. Offer contract A (benign-looking, title "Agreement", text T1) to the victim.
2. Victim reviews and accepts A in good faith; the wallet signs `signed_message = "Agreement"` under `objContract.peer_address` and sends `prosaic_contract_response{hash: A.hash, status: "accepted", signed_message: <sig of "Agreement">}`.
3. Attacker also offers contract B to the same victim beforehand or afterward, with the same title "Agreement" but different, harmful `text` (e.g., different payment terms, cosigner obligations, or dispute conditions), producing a different `hash`.
4. Attacker replays the previously captured signed package (same address, same signed text "Agreement") in a forged `prosaic_contract_response` referencing `hash: B.hash`.
5. The handler check passes (`signed_message == objContract.title` and `authors[0].address == objContract.peer_address`), so `prosaic_contract.setField(objContract.hash, "status", "accepted")` marks contract B as accepted by the victim even though the victim never reviewed or agreed to B's actual terms at [5](#0-4) .

Since prosaic contracts can gate cosigning of shared addresses and financial obligations between the two parties (`deriveSharedAddress`, `cosigners`), a forged "accepted" status can be leveraged to make the victim's software/UI believe a materially different (and potentially adversarial) agreement was consented to, enabling fraud/financial loss disputes and undermining the non-repudiation guarantee the signature is meant to provide. This matches the accepted "AA fund loss/freezing" or "node disagreement on validity" style impact by analogy: contract-level double-binding failure causing unauthorized/forged consent to different terms than what was actually signed.

### Likelihood Explanation
The attacker only needs to be a paired device correspondent capable of sending `prosaic_contract_offer` / `prosaic_contract_response` justsaying messages — a normal, unprivileged capability for anyone the user has paired with. Crafting two offers with an identical `title` but different `text`/`creation_date` is trivial and entirely under the attacker's control since the attacker is the offeror in both cases. No cryptographic break is needed — only reuse of a validly captured signature across the two contracts sharing the same title.

### Recommendation
Bind the acceptance signature to the full unique contract identifier rather than the human-readable `title`. Specifically:
- In `respond()`/wallet UI signing flow, sign `objContract.hash` (or a message that unambiguously incorporates `title`, `text`, and `creation_date`) instead of `objContract.title`.
- In the `prosaic_contract_response` handler, verify `objSignedMessage.signed_message === objContract.hash` (or the equivalent full-binding value) rather than comparing against `objContract.title`.
- Add a regression test that offers two contracts with identical titles/different bodies and confirms that a signature captured for one cannot be replayed to accept the other.

### Proof of Concept
1. Attacker device pairs with victim device.
2. Attacker calls `prosaic_contract.createAndSend()` twice, sending:
   - Contract A: `{title: "Agreement", text: "Pay 10 GBYTE for goods", creation_date: t1}`
   - Contract B: `{title: "Agreement", text: "Pay 10 GBYTE and grant cosigning rights on shared_address X", creation_date: t2}`
   (different `hash` values due to `getHash(title+text+creation_date)`.)
3. Victim reviews and accepts Contract A via wallet UI, producing `prosaic_contract_response{hash: A.hash, status:"accepted", signed_message: <base64 signed package where signed_message = "Agreement">}`, per the `respond()` composition in `prosaic_contract.js` line 72-90.
4. Attacker (who received this response and captured the `signed_message` blob) crafts and replays a forged `prosaic_contract_response{hash: B.hash, status:"accepted", signed_message: <same captured blob>}` from the same device_address (which is `objContract.peer_device_address` for both contracts since attacker is the counterparty in both).
5. In `wallet.js`, `from_address === objContract.peer_device_address` (true, attacker device), `signed_message.validateSignedMessage` succeeds (real, valid signature by `objContract.peer_address`), and `objSignedMessage.signed_message != objContract.title` is false because both A and B share `title === "Agreement"`.
6. `prosaic_contract.setField(B.hash, "status", "accepted")` is called, marking Contract B as accepted by the victim despite the victim never reviewing/signing B's actual terms.
