### Title
Webhook signature verification binds to the payload's `repository.owner.login`/`organization.login`, but every event handler acts on the independently-controlled `repository.full_name` field, letting an attacker with a valid signature for one configured GitHub organization forge events for a stack belonging to a different repository - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App config (and thus which `webhook_secret`) to validate the HMAC signature against, using a field extracted straight from the untrusted JSON body, not from anything tied to the actual repository the handlers will operate on.

### Finding Description
`verify_signature` computes `repository_owner` and uses it to pick the app config used to check the signature: [1](#0-0) [2](#0-1) 

`repository_owner` reads `params.dig('repository', 'owner', 'login')`, falling back to the top-level `params.dig('organization', 'login')` only if the former is absent. This selects the `GitHubApp` (and its `webhook_secret`) via `Shipit.github(organization: repository_owner)`, which looks up per-organization config in `Shipit.github_app_config`: [3](#0-2) 

Once the signature is accepted, `create` dispatches the **entire raw payload** to handlers: [4](#0-3) 

Every handler, however, resolves the target `Repository`/`Stack` from a **different, independent** field — `payload.dig('repository', 'full_name')` — via the shared `Handler#repository_name`/`#stacks` helpers, or the equivalent `params.repository.full_name` lookup in the pull-request handlers: [5](#0-4) [6](#0-5) [7](#0-6) 

Nothing in `verify_signature` or in the handlers cross-checks that `repository.owner.login` (used to select the signing secret) matches the owner encoded in `repository.full_name` (used to select the stack that gets acted on). This is the same class of bug as the report: a value is authenticated ("verified owner/org") while a different value is the one actually acted upon ("repository written to"), and the two are never asserted equal.

In a deployment supporting multiple GitHub organizations (the intended, documented multi-org config schema — see `test/dummy/config/secrets_double_github_app.yml` and `Shipit.github_app_config`), each org has its own independent `webhook_secret`. Anyone who administers/owns a repository under one of the configured organizations (Org A) can freely emit legitimate signed webhook deliveries for Org A (e.g., by pushing to their own repo, since GitHub actually signs the payload with Org A's secret). They can also directly craft a payload without going through GitHub, since the controller only checks the HMAC — not the delivery's true origin. Because `repository_owner` reads `repository.owner.login` (or the fallback `organization.login`) while the handler reads the sibling but distinct `repository.full_name`, an attacker who owns/controls a webhook delivery for `OrgA/some-repo` can submit a payload where:
- `repository.owner.login` = `"OrgA"` (so `verify_signature` selects OrgA's `webhook_secret`, which the attacker legitimately possesses a signature for), and
- `repository.full_name` = `"OrgB/victim-repo"` (a stack belonging to a completely different, unrelated organization configured on the same Shipit instance).

The signature check passes (OrgA's secret matches), yet the handler acts on `OrgB/victim-repo`'s stack — e.g. `PushHandler` will call `stack.sync_github(expected_head_sha: params.after)` for the victim's stack, or `ClosedHandler`/`LabeledHandler`/etc. will archive/unarchive a review stack belonging to Org B, using solely attacker-controlled data (no ownership relationship between OrgA and OrgB is required).

### Impact Explanation
This crosses a genuine authentication/authorization boundary: the "verified organization" and the "repository actually written to" are supposed to be the same identity, but the code never enforces that equality. It allows an attacker who is entitled to sign/deliver webhooks only for their own organization's repos to inject events (push syncs, review-stack archive/unarchive, label-driven stack behavior, PR-close archival) affecting stacks belonging to a completely different, unrelated repository/organization hosted on the same multi-tenant Shipit instance. This is a cross-repository write triggered purely by a forged/replayed webhook payload with mismatched identity fields, satisfying the "cross-repository writes" Critical impact criterion — though the concrete blast radius depends on which handler is targeted (sync-triggering vs. archival actions), and does not by itself achieve RCE, token exfiltration, or an unauthorized deploy/rollback/merge.

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured with the multi-organization `github:` secrets schema (multiple orgs, each with a GitHub App/webhook secret installed on the same instance) — a supported, documented configuration. The attacker needs no privileged Shipit account, `ApiClient` token, or GitHub App private key; they only need the ability to generate one valid signed webhook for an organization they control (trivial: push to their own repo, or knowledge of that org's `webhook_secret` if they administer the GitHub App). Given the `repository_owner` fallback to `organization.login` and its independence from `repository.full_name`, forging the payload body is straightforward once a valid signature for *any* configured org is obtainable.

### Recommendation
In `WebhooksController#verify_signature`, after successfully verifying the signature, assert that the organization used to select the webhook secret is consistent with the repository owner encoded in `repository.full_name` (the field handlers actually use), rejecting the request (HTTP 422) if they diverge. More robustly, derive a single canonical "verified organization" once, and have every handler resolve `Repository` scoped to that verified organization rather than trusting `repository.full_name` outright.

### Proof of Concept
1. Configure Shipit with two GitHub organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per the documented multi-org schema, cf. `test/dummy/config/secrets_double_github_app.yml`). `OrgB` owns a repository `OrgB/victim-repo` with an existing Shipit stack.
2. As an attacker who administers `OrgA`'s GitHub App/repo (only privileged for `OrgA`), craft (or legitimately trigger) a `push` webhook payload signed with `OrgA`'s `webhook_secret`, but set:
   - `repository.owner.login` = `"OrgA"` (or omit it and set top-level `organization.login` = `"OrgA"`)
   - `repository.full_name` = `"OrgB/victim-repo"`
   - `ref`/`after` pointing at attacker-chosen values.
3. POST this payload with header `X-Hub-Signature` computed against `OrgA`'s secret to `/webhooks`.
4. `verify_signature` calls `Shipit.github(organization: "OrgA")`, resolves `OrgA`'s secret, and the HMAC check passes.
5. `PushHandler#process` resolves the target via `Repository.from_github_repo_name("OrgB/victim-repo")` and enqueues `stack.sync_github(expected_head_sha: params.after)` for `OrgB`'s stack — an action the attacker has no legitimate authority over, using only a signature they hold for `OrgA`.

```ruby
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
```

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
