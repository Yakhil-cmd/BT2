### Title
ReDoS heuristic (`_has_redos_structure`) has coverage gaps that let an attacker-committed `security-patterns.yaml` hang `check_patterns()` on every edit - ([File: plugins/security-guidance/hooks/extensibility.py])

### Summary
`_validate_pattern` only rejects a user-supplied `regex` if `_has_redos_structure` flags it, but that heuristic only recognizes two structural shapes (`_REDOS_SHAPES`) plus overlapping alternation under repetition (`_ALT_UNDER_REP`) — all of which require literal `(...)` groups combined with `+`/`*` characters. Regexes that achieve catastrophic backtracking through other well-known shapes (e.g. brace-quantified nested groups, or long chains of unparenthesized optional/greedy quantifiers) pass validation unflagged, are compiled successfully by `re.compile`, and get executed via `re.search` on every file touched by PostToolUse Edit/Write for the rest of the session.

### Finding Description
`extensibility.load_for_session()` calls `_load_user_patterns(cwd)`, which reads `.claude/security-patterns.{yaml,json}` — explicitly documented as "project, committed" and loaded without any additional sandboxing beyond the ReDoS heuristic [1](#0-0) . Each entry's `regex` is passed through `_validate_pattern`, which only skips it if `_has_redos_structure(regex)` returns `True` [2](#0-1) .

`_has_redos_structure` is a narrow structural heuristic:
```
_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")
``` [3](#0-2) 

Both `_REDOS_SHAPES` entries require a literal `+` or `*` character *inside* a parenthesized group **and** a literal `+`/`*` immediately after the closing paren. This means:
- Nested groups quantified with `{m,n}` bounds instead of `+`/`*` (e.g. `(a{1,50}){1,50}$`) are structurally identical catastrophic-backtracking shapes but contain no `+`/`*` characters at all, so neither `_REDOS_SHAPES` regex matches, and `_ALT_UNDER_REP` (which requires `|`) doesn't apply either.
- Sequences of overlapping quantifiers with no enclosing group at all (e.g. `^(\w?){0,40}\w{40}$`-style or a long chain of ungrouped optional repeats) can still hit Python's backtracking `re` engine's exponential worst case, but the heuristic only scans for the specific `(...)+`/`(...)  *` textual shapes.

Because `re.compile(regex)` succeeds for such a pattern (it's syntactically valid), `_validate_pattern` accepts it into the cached `_user_patterns` list, returned by `user_patterns()` and merged with `SECURITY_PATTERNS` for every subsequent `check_patterns()` call in `patterns.py`/`security_reminder_hook.py` (no per-rule execution timeout or resource cap exists in `patterns.py`) [4](#0-3) . Since `_user_patterns` is loaded once per hook invocation and reused for all edits in the session [5](#0-4) , a single malicious rule causes every PostToolUse Edit/Write to re-run the pathological `re.search` against the new file content, hanging or consuming excessive CPU on each edit.

### Impact Explanation
This starves the pattern-rule PostToolUse enforcement path: because `check_patterns()` is invoked synchronously per edited file and the malicious regex is now permanently part of the merged rule set for the session, every subsequent hardcoded-secret/SQLi/command-injection pattern warning is delayed or never delivered before the hook times out, effectively disabling the deny/warn signal for the remainder of the session — a logic defect that defeats an existing security control (the ReDoS heuristic cap), matching the "resource cap defeated by a code defect" category rather than plain volumetric DoS.

### Likelihood Explanation
Fully feasible and repeatable: the attacker only needs write access to a branch/PR that gets cloned and whose `.claude/security-patterns.yaml` is picked up per the plugin's own project-precedence discovery order — no admin privilege, no social engineering beyond a normal commit/PR. The `re` module is CPython's default backtracking engine, so no special environment is required to trigger worst-case blowup; only crafting a regex shape the heuristic doesn't recognize (e.g. brace-quantified nested groups) is needed.

### Recommendation
Replace or supplement the structural heuristic with an actual bounded-time probe: after `re.compile`, run `re.search` against a small set of adversarial synthetic inputs (e.g. `"a" * N` plus a non-matching suffix) under a hard wall-clock/CPU budget (e.g. via `signal.alarm`, a subprocess with a timeout, or a `re2`/`regex`-with-timeout backend), and reject the rule if it exceeds the budget — rather than relying solely on `+`/`*`-literal pattern-matching in `_has_redos_structure`. Also generalize `_REDOS_SHAPES` to recognize `{m,n}`-quantified nested groups, not just `+`/`*`.

### Proof of Concept
Fuzz/invariant test in `plugins/security-guidance/hooks/test_extensibility.py` (or new test file):
```python
import re, time
from extensibility import _has_redos_structure

CATASTROPHIC_BUT_UNCOVERED = [
    r"^(a{1,20}){1,20}$",      # brace-quantified nested group, no +/* chars
    r"^(a{0,10}){0,10}b$",
]

def test_redos_heuristic_catches_brace_quantified_nesting():
    for rx in CATASTROPHIC_BUT_UNCOVERED:
        # Confirm it actually causes pathological runtime.
        pattern = re.compile(rx)
        start = time.monotonic()
        pattern.search("a" * 30 + "!")   # non-matching tail forces backtracking
        elapsed = time.monotonic() - start
        assert elapsed > 1.0, f"{rx} did not exhibit catastrophic backtracking in this run"
        # The heuristic should have flagged it — this assertion currently FAILS,
        # demonstrating the gap.
        assert _has_redos_structure(rx), f"heuristic missed catastrophic pattern: {rx}"
```
Expected: the timing assertion passes (confirming genuine catastrophic backtracking) while `_has_redos_structure(rx)` returns `False`, proving the bypass. A follow-up integration test should load such a rule via `security-patterns.yaml` through `extensibility.load_for_session` and confirm `patterns.check_patterns()` (or equivalent) hangs beyond a reasonable PostToolUse budget on a crafted file.

_REDOS_SHAPES = [
    re.compile(r"\([^()]*[+*][^()]*\)[+*?]"),  # nested quantifier: (a+)*  (a*b)*
    re.compile(r"\(\.\*[^()]*\)[+*]"),         # wildcard group: (.*)*
]
_ALT_UNDER_REP = re.compile(r"\(([^()]*)\|([^()|]*)(?:\|[^()]*)*\)[+*]")


def _has_redos_structure(regex: str) -> bool:
    """Heuristic catastrophic-backtracking check. Not a proof. Catches:
      - nested quantifiers ((a+)*, (a*b)+)
      - wildcard groups under repetition ((.*)*)
      - alternation under repetition where one branch is a prefix of another
        ((a|aa)*, (ab|a)*) — these overlap and explode on non-matching input.
    Does NOT flag non-overlapping alternation ((a|b)*) which is safe."""
    if any(p.search(regex) for p in _REDOS_SHAPES):
        return True
    for m in _ALT_UNDER_REP.finditer(regex):
        branches = [b for b in m.group(0).strip("()*+").split("|") if b]
        for i, a in enumerate(branches):
            for b in branches[i + 1:]:
                # If one branch is a literal prefix of another, the alternation
                # overlaps and the engine backtracks combinatorially.
                if a.startswith(b) or b.startswith(a):
                    return True
    return False
```
