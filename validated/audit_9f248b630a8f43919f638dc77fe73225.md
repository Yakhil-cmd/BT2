### Title
Cross-repository status webhook injection via unscoped `Commit.where(sha:)` lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the commit to update by SHA alone, with no check that the payload's `repository` belongs to the commit's actual `stack`/`Repository`. Because webhook signature verification in `WebhooksController#verify_signature` only proves the payload was signed by *some* GitHub org configured in Shipit (chosen by `repository.owner.login` in the very same attacker-controlled payload), an attacker who administers any org onboarded to a multi-tenant Shipit instance can forge a `success` status for a `sha` belonging to a totally different org/repo/stack, and have it applied to that unrelated commit.

### Finding Description
The broken binding: `payload.repository.owner.login` (used to select the signing `GitHubApp`/secret in `WebhooksController#verify_signature`) should equal the `Repository`/org that actually owns the commit referenced by `payload.sha` before that commit's status is mutated — but no such equality is ever checked.

Code path:
1. `WebhooksController#verify_signature` derives `repository_owner` from the raw JSON payload (`params.dig('repository','owner','login')`) and verifies the signature against `Shipit.github(organization: repository_owner)` — i.e., whichever org's webhook secret the attacker names and controls: [2](#0-1) 
2. On success, `Shipit::Webhooks.for_event('status')` dispatches to `StatusHandler`, whose param schema doesn't even require a `repository` field: [3](#0-2) 
3. `StatusHandler#process` looks up commits **globally by `sha` only**, with zero scoping to the org/repo that was authenticated in step 1: [4](#0-3) 
4. `Commit#create_status_from_github!` → `#add_status` creates the `Status`, and if the state transitions to `success`/`pending`, immediately calls `stack.schedule_merges` and (via `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`) enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment? && stack.deployable?`: [5](#0-4) [6](#0-5) [7](#0-6) 

Exploit flow: Shipit supports hosting multiple independent GitHub orgs in one instance, each with its own `webhook_secret`, as documented and tested (`docs/setup.md:182-209`, `test/dummy/config/secrets_double_github_app.yml`, `Shipit.github(organization:)`) [8](#0-7) . An attacker who administers *any one* of these onboarded orgs (e.g., their own, satisfying the "org they administer" precondition) knows that org's `webhook_secret`. They:
1. Open a PR from their own fork against the target repo, so the target Shipit instance ingests a `Commit` with a SHA the attacker knows (their own commit).
2. Craft a `status` event JSON body: `{"sha": "<known target commit sha>", "state": "success", "repository": {"owner": {"login": "<attacker-org>"}}}`.
3. Compute a valid `X-Hub-Signature` using their own org's real `webhook_secret` (no secret is stolen — it's their own legitimate credential).
4. POST to `/webhooks` with `X-Github-Event: status`. `verify_signature` resolves `Shipit.github(organization: 'attacker-org')` and the signature checks out, since it's a genuinely valid signature for that org.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, which matches the target's commit purely by SHA value, irrespective of which org's key verified the signature, and applies the forged `success` status to it.

Existing guards do not stop this: `verify_signature` authenticates *an org*, not *the org owning the commit being mutated*; the `StatusHandler` params schema has no `repository` requirement and performs no repository/stack scoping (contrast with `PullRequest::ClosedHandler`, `EditedHandler`, etc., which all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` before touching any record) [9](#0-8) .

### Impact Explanation
An attacker can inject arbitrary CI status (`success`/`pending`/`failure`/`error`) onto any commit in any repository/stack hosted by the same multi-org Shipit instance, as long as they can guess or know the target commit's SHA (trivial for their own fork-originated PR commits, or for any public commit whose SHA is visible on GitHub). With `stack.continuous_deployment?` and `stack.deployable?` true on the target, injecting `success` triggers `Stack#schedule_merges` and `ContinuousDeliveryJob`, resulting in an unauthorized deploy or merge-queue progression of a commit that a maintainer of the target org never approved. This is a payload for one repository/org mutating another's stack/commit state, matching the Critical "unauthorized deploy" category. It is repeatable against any stack in the instance and any known SHA, not limited to one tenant.

### Likelihood Explanation
Requires: (a) the target Shipit deployment configured for multiple GitHub organizations (a documented, supported setup), and (b) the attacker administering at least one onboarded org (or having their own GitHub App/org onboarded, per the threat model's own precondition), which they use to legitimately sign a payload naming that org while referencing a foreign SHA. No secret theft, no session, no API token is needed — only knowledge of the target's commit SHA and control of a legitimately configured org's webhook secret. This is fully feasible and repeatable per request.

### Recommendation
In `StatusHandler#process`, scope the `Commit` lookup to the repository/org that was actually authenticated by `verify_signature` — e.g., require `repository.full_name` in the params schema, resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, and constrain `Commit.where(sha: params.sha, stack_id: repository.stacks.select(:id))` (or equivalent join), mirroring the pattern already used by `PullRequest::EditedHandler`/`ClosedHandler`. Additionally, `WebhooksController#verify_signature` should not let the payload dictate which org's secret to check against without that org later being cross-validated against the resource being mutated.

### Proof of Concept
Minitest (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or a controller test in `test/controllers/webhooks_controller_test.rb`), asserting the binding directly:

```ruby
test "status webhook signed by org A can mutate a commit belonging to org B's stack" do
  # Org A: attacker-administered, configured with its own real webhook_secret
  # Org B: victim org owning @stack (continuous_deployment: true, deployable? true)
  victim_commit = shipit_commits(:review_stack_fork_commit) # sha known to attacker (their own PR)

  payload = {
    "sha" => victim_commit.sha,
    "state" => "success",
    "repository" => { "owner" => { "login" => "attacker-org" } }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", ATTACKER_ORG_WEBHOOK_SECRET, payload)

  request.headers['X-Github-Event'] = 'status'
  request.headers['X-Hub-Signature'] = signature

  assert_enqueued_with(job: ProcessMergeRequestsJob, args: [victim_commit.stack]) do
    post :create, body: payload, as: :json
  end

  assert_equal 'success', victim_commit.reload.state
  # Binding check: attacker-org (payload.repository.owner.login) != victim_commit.stack.repository.owner
  refute_equal "attacker-org", victim_commit.stack.repo_owner
end
```

This demonstrates that a signature valid only for `attacker-org` is sufficient to flip the status—and trigger merge/deploy scheduling—of a commit that belongs to an entirely different, unauthenticated-by-that-signature repository/stack.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
