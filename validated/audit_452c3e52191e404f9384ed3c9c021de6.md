### Title
`isRunning` Emergency-Stop Flag Not Enforced in `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`)

---

### Summary

The bridge's `isRunning` flag is the designated emergency-stop mechanism. All three outbound request functions correctly gate on it, but all three inbound handle functions ignore it entirely. When the bridge owner calls `setRunningStatus(false)`, operators can still call `handleKLAYTransfer`, `handleERC20Transfer`, and `handleERC721Transfer` to complete inbound value transfers — minting or releasing KLAY/ERC20/ERC721 to recipients on the destination chain — defeating the emergency stop.

---

### Finding Description

`BridgeTransfer.sol` declares `bool public isRunning = true` and exposes `setRunningStatus(bool)` (owner-only) as the bridge's emergency stop. [1](#0-0) 

The outbound (request) path consistently enforces this flag:

- `_requestKLAYTransfer`: `require(isRunning, "stopped bridge")` [2](#0-1) 
- `_requestERC20Transfer`: `require(isRunning, "stopped bridge")` [3](#0-2) 
- `_requestERC721Transfer`: `require(isRunning, "stopped bridge")` [4](#0-3) 

The inbound (handle) path has **no such check** in any of the three functions:

- `handleKLAYTransfer` proceeds directly to `_lowerHandleNonceCheck` → `_voteValueTransfer` → KLAY transfer with no `isRunning` guard. [5](#0-4) 
- `handleERC20Transfer` proceeds directly to nonce check → vote → mint/transfer with no `isRunning` guard. [6](#0-5) 
- `handleERC721Transfer` proceeds directly to nonce check → vote → mint/transfer with no `isRunning` guard. [7](#0-6) 

This is the exact structural analog to the Astaria bug: the protected-state flag (`isRunning` / `isShutdown`) is set and readable, but the critical execution path that moves assets does not consult it.

---

### Impact Explanation

When the bridge owner stops the bridge (e.g., in response to a discovered exploit, operator key compromise, or migration), they expect **all** asset movement to halt. Because the handle functions bypass `isRunning`, operators can continue to:

- Transfer KLAY from the bridge contract to arbitrary recipients (`handleKLAYTransfer` line 98: `_to.call.value(_value)("")`). [8](#0-7) 
- Mint or release ERC20 tokens to arbitrary recipients (`handleERC20Transfer` lines 68–72). [9](#0-8) 
- Mint or transfer ERC721 tokens to arbitrary recipients (`handleERC721Transfer` lines 66–70). [10](#0-9) 

The corrupted value is the recipient's token balance / KLAY balance: it increases when it should not, draining bridge-held or bridge-mintable assets after the owner has declared the bridge stopped.

---

### Likelihood Explanation

The trigger requires an operator to call a handle function after `isRunning` is set to `false`. Operators are semi-trusted (appointed by the owner via `BridgeOperator`). The scenario is realistic precisely when the owner stops the bridge because operator keys are suspected compromised, or because a cross-chain exploit is in progress — the moment the stop is most needed, a compromised or malicious operator can still complete pending or fabricated handle calls. The `onlyOperators` restriction does not eliminate the risk; it defines the attacker class.

---

### Recommendation

Add `require(isRunning, "stopped bridge")` at the top of each handle function, mirroring the pattern already used in the request functions:

```solidity
// BridgeTransferKLAY.sol – handleKLAYTransfer
function handleKLAYTransfer(...) public onlyOperators nonReentrant {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

// BridgeTransferERC20.sol – handleERC20Transfer
function handleERC20Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}

// BridgeTransferERC721.sol – handleERC721Transfer
function handleERC721Transfer(...) public onlyOperators {
+   require(isRunning, "stopped bridge");
    _lowerHandleNonceCheck(_requestedNonce);
    ...
}
```

---

### Proof of Concept

1. Deploy the bridge in lock-step mode (`modeMintBurn = true`).
2. Owner calls `setRunningStatus(false)` — bridge is stopped.
3. Verify: `requestERC20Transfer(...)` reverts with `"stopped bridge"`. ✓
4. Operator calls `handleERC20Transfer(txHash, from, victim, token, 1e18, nonce, blockNum, "")` directly.
5. Observe: `ERC20Mintable(token).mint(victim, 1e18)` succeeds — tokens are minted to `victim` despite the bridge being stopped.
6. Repeat with `handleKLAYTransfer` (KLAY drained from bridge balance) and `handleERC721Transfer` (NFT minted/transferred).

The `isRunning` flag is read by `setRunningStatus` and the request path, but is never consulted by any handle function, so step 4 always succeeds regardless of the bridge's stopped state. [11](#0-10) [12](#0-11)
