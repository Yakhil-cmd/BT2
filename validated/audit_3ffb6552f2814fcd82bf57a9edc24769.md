### Title
Signed-Integer Truncation in `consolidatedNode.Split()` Corrupts Validator/CL Reward Distribution — (`File: kaiax/staking/staking_info.go`)

---

### Summary

`consolidatedNode.Split()` casts two `uint64` staking-amount fields to `int64` before constructing `*big.Int` values. If either field exceeds `math.MaxInt64` (≈ 9.22 × 10⁹ KAIA), the cast silently wraps to a negative integer. The resulting negative `*big.Int` is then used as the denominator and numerator in the proportional reward split between a validator's CN staking address and its Consensus-Liquidity (CL) pool address. This produces a negative `clAmount` and a `cnAmount` that exceeds the total reward, causing the CL pool to be debited (balance drained) and the CN to receive more KAIA than it is entitled to every block.

---

### Finding Description

`consolidatedNode.StakingAmount` and `CLStakingInfo.CLStakingAmount` are both declared as `uint64` (in KAIA units, not kei). [1](#0-0) 

`Split()` converts them to `int64` via `big.NewInt(int64(...))`: [2](#0-1) 

`int64` can represent at most 9,223,372,036 KAIA. Any `uint64` value above that wraps to a negative `int64`. `big.NewInt` faithfully preserves the sign, so `cnAmountBig` or `clAmountBig` becomes negative.

Downstream arithmetic:

```
totalAmount = cnAmountBig + clAmountBig   // may be negative or near-zero
clAmount    = clAmountBig * reward / totalAmount  // negative if totalAmount < 0
cnAmount    = reward - clAmount           // > reward (overflow of intended share)
```

`Split()` is called unconditionally from both reward-distribution paths: [3](#0-2) [4](#0-3) [5](#0-4) 

The corrupted `clAmount` (negative `*big.Int`) is inserted into `spec.Rewards` and applied via `state.AddBalance(clPoolAddr, negativeAmount)` in `FinalizeState`: [6](#0-5) 

A secondary unchecked `uint64` accumulation exists in both `assignStakingRewards` and `assignStakingRewardsFlex` where per-validator excess stakes are summed into `totalExcessInt` without overflow detection: [7](#0-6) [8](#0-7) 

---

### Impact Explanation

- **CL pool balance drained**: `state.AddBalance(clPoolAddr, negativeAmount)` subtracts KAIA from the CL pool every block, draining it without any corresponding transfer.
- **CN over-rewarded**: The CN validator address receives `reward - clAmount` where `clAmount` is negative, so it receives more than the full staking reward.
- **Reward accounting invariant broken**: `spec.Rewards` no longer sums to `spec.Minted + distributableFee`, breaking the conservation invariant checked by `spec.Validate()`.

This is an unauthorized reward distribution affecting KAIA and CL-pool-managed funds, matching the allowed impact gate.

---

### Likelihood Explanation

`StakingAmount` is stored in KAIA (divided by `params.KAIA = 1e18` kei) and sourced from the native-token balance of each staking contract: [9](#0-8) 

The `int64` threshold is ≈ 9.22 billion KAIA. The current total KAIA supply is approximately 5.7 billion KAIA, so no single validator can currently exceed the threshold. However:

1. No explicit cap is enforced anywhere in the staking ingestion path.
2. `consolidateNodes()` sums multiple staking contracts sharing the same reward address without overflow protection: [10](#0-9) 

3. As inflation increases total supply, the threshold becomes reachable.
4. The `uint64` accumulator overflow in `totalExcessInt` (threshold ≈ 18.4 billion KAIA) is a second, higher-threshold variant of the same class.

Likelihood is **low** under current supply but the code contains no guard and the bug class is latent.

---

### Recommendation

Replace the narrowing `int64` casts in `Split()` with safe `uint64`-to-`*big.Int` conversions:

```go
// Before (unsafe):
cnAmountBig = big.NewInt(int64(c.StakingAmount))
clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))

// After (safe):
cnAmountBig = new(big.Int).SetUint64(c.StakingAmount)
clAmountBig = new(big.Int).SetUint64(c.CLStakingInfo.CLStakingAmount)
```

Additionally, replace bare `uint64` additions in `assignStakingRewards`, `assignStakingRewardsFlex`, and `consolidateNodes` with `math.SafeAdd`-guarded additions (already available in `common/math/integer.go`): [11](#0-10) 

Return an error or clamp on overflow rather than silently wrapping.

---

### Proof of Concept

```go
package main

import (
    "fmt"
    "math"
    "math/big"
)

func main() {
    // Simulate a validator with StakingAmount just above int64 max (in KAIA units)
    cnStake  := uint64(math.MaxInt64) + 1  // 9_223_372_036_854_775_808 KAIA
    clStake  := uint64(5_000_000_000)      // 5 billion KAIA

    // Current (buggy) code path
    cnAmountBig := big.NewInt(int64(cnStake))  // wraps to -9_223_372_036_854_775_808
    clAmountBig := big.NewInt(int64(clStake))  // 5_000_000_000 (positive)
    totalAmount := new(big.Int).Add(cnAmountBig, clAmountBig)

    reward := big.NewInt(6_400_000_000_000_000_000) // 6.4 KAIA in kei

    clAmount := new(big.Int).Div(new(big.Int).Mul(clAmountBig, reward), totalAmount)
    cnAmount := new(big.Int).Sub(reward, clAmount)

    fmt.Println("totalAmount:", totalAmount)  // negative
    fmt.Println("clAmount:   ", clAmount)     // negative → CL pool drained
    fmt.Println("cnAmount:   ", cnAmount)     // > reward  → CN over-rewarded
}
```

Running this demonstrates that `clAmount` is negative and `cnAmount` exceeds the full reward, confirming the corrupted distribution that would be applied to chain state via `FinalizeState` every block.
