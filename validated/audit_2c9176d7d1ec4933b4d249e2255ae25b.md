## Analysis

The Sherlock H-10 root cause is a strict ordering invariant violation: a staker's *share balance* must never be mutated before the reward-per-token snapshot (`_updateReward`) is taken for that account, otherwise the new/increased balance gets multiplied against a reward-per-token delta that accrued before the balance changed, producing unearned reward credit.

`pox-5.clar` reimplements this exact reward-per-token accounting pattern (`compute-earned-rewards = shares * (rpt-current - rpt-paid) + pending`) and explicitly documents the invariant: [1](#0-0) 

The STX-only staking path, `add-staker-to-signer-for-cycle`, correctly honors this: it calls `settle-rewards` (and conditionally `settle-staker-rewards`) *before* mutating `signer-shares-staked-for-cycle` / `total-shares-staked-for-cycle`: [2](#0-1) 

However, the bond-staking path, `add-staker-to-bond-for-cycle`, mutates `total-shares-staked-for-cycle` and `signer-shares-staked-for-cycle` (the signer's aggregate share balance used for `settle-rewards`) directly, without first calling `settle-rewards` for the signer: [3](#0-2) 

This means when a new bond-staker is added to a signer mid-cycle, the signer's `signer-shares-staked-for-cycle` grows *before* its `signer-rewards-per-token-settled-for-cycle` checkpoint is refreshed. The next time `settle-rewards` runs for that signer (on any subsequent stake/unstake/claim), it computes `earned = new_larger_shares * (rpt-current - rpt-paid)`, applying the enlarged share count retroactively to the entire un-settled period — including the portion before the new staker joined. This inflates the signer's (and thus its stakers') claimable sBTC rewards beyond what was actually deposited/distributed, i.e., reward tokens get double-counted/over-credited, echoing the H-10 root cause.

I was not able to fully trace the caller of `add-staker-to-bond-for-cycle` (likely `register-for-bond`) within the remaining tool budget to confirm whether it can be invoked mid-cycle *after* a reward distribution has already bumped `rewards-per-token` for that cycle (as opposed to only being reachable before any distribution occurs, in which case `rpt-current == rpt-paid` and the bug would be inert). That timing precondition is the key remaining unknown for exploitability.

### Title
Bond-staker registration bumps signer share totals without settling signer rewards first, enabling reward over-crediting - (File: stackslib/src/chainstate/stacks/boot/pox-5.clar)

### Summary
`add-staker-to-bond-for-cycle` increases `signer-shares-staked-for-cycle` and `total-shares-staked-for-cycle` without first calling `settle-rewards` for the affected signer, violating the documented invariant that reward-per-token accounting requires settling before any share-count mutation.

### Finding Description
`settle-rewards` computes `earned = shares * (rewards-per-token-current - rewards-per-token-paid) + pending` [4](#0-3) , and its own doc comment states it "MUST be called before any update to `signer-shares-staked-for-cycle`" [1](#0-0) . The STX-staking code path respects this ordering [5](#0-4) , but `add-staker-to-bond-for-cycle` bumps `signer-shares-staked-for-cycle` directly with `map-set` and only afterward sets the new staker's own settled checkpoint, never re-settling/refreshing the signer's aggregate `signer-rewards-per-token-settled-for-cycle` [6](#0-5) . Any subsequent `settle-rewards` call for that signer applies the accrued `rewards-per-token` delta to the now-larger share total, crediting shares that did not exist during part of the accrual window.

### Impact Explanation
If the signer's `rewards-per-token-for-cycle` had already advanced (rewards distributed) before the new bond-staker registers in the same cycle, the signer's total earned/claimable sBTC becomes inflated relative to the sBTC actually deposited for that cycle — a double-counting of reward tokens paid to stakers of that signer, at the expense of the reward pool's backing (Critical/High per the rubric: "sBTC rewards paid that were not earned or counted twice").

### Likelihood Explanation
Requires only an unprivileged staker/delegate calling the normal bond-registration flow (`register-for-bond` → `add-staker-to-bond-for-cycle`) for an existing signer that already has accrued (but not yet settled) reward-per-token movement in the current cycle. No privileged role is needed. Confirmed feasibility depends on whether reward distribution (`rewards-per-token` bump) can occur before/interleaved with bond registration in the same cycle — this could not be fully confirmed within the available investigation.

### Recommendation
Call `settle-rewards signer reward-cycle (some bond-index)` for the signer before mutating `signer-shares-staked-for-cycle`/`total-shares-staked-for-cycle` inside `add-staker-to-bond-for-cycle`, mirroring the pattern already used in `add-staker-to-signer-for-cycle`.

### Proof of Concept
Conceptual sequence (needs confirmation against the actual `register-for-bond` reachability):
1. Signer S has existing bond shares in cycle N; sBTC rewards are distributed, bumping `rewards-per-token-for-cycle` for (N, bond-index) without S's `signer-rewards-per-token-settled-for-cycle` being refreshed yet.
2. A new staker registers for the same bond/signer via `register-for-bond`, which calls `add-staker-to-bond-for-cycle`, increasing `signer-shares-staked-for-cycle` for S without calling `settle-rewards`.
3. Any later action that triggers `settle-rewards` for S recomputes `earned = new_larger_shares * (rpt-current - rpt-paid)`, crediting S's aggregate unclaimed rewards using the post-registration share count for a period that included the pre-registration (smaller) share count, inflating claimable sBTC beyond the actual deposited amount.
