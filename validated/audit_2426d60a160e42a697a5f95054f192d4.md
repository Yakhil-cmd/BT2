I found a concrete instance of exactly the vulnerability class described: a **binding between "the stack an `ApiClient` token authorizes" and "the stack an endpoint actually reads/writes"** is broken in the CCMenu controller.This confirms the vulnerability. `Api::StacksController#index` correctly scopes results through `stacks` (which filters by `current_api_client.stack_id` in `app/controllers/shipit/api/base_controller.rb:74-76`), but `Api::CCMenuController#stack` (`app/controllers/shipit/api/ccmenu_controller.rb:29-31`) bypasses that scoping entirely by calling `Stack.from_param!(params[:stack_id])` directly, not `stacks.from_param!(...)`.

### Title
Stack-scoped API tokens can read the CI/deploy status of any stack via the CCMenu endpoint - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`ApiClient` records can be scoped to a single stack via the `stack_id` column, and `Api::BaseController#stacks`/`#stack` enforce that scoping for every controller that inherits it. `Api::Api::CCMenuController` overrides `#stack` and looks the stack up unscoped, so any valid API token — regardless of the stack it was authorized for — can fetch the CCMenu XML status for every stack in the instance.

### Finding Description
`ApiClient#check_permissions!` only checks whether the token's `permissions` array contains `"read:stack"` — it never checks which stack the operation targets [1](#0-0) . The actual per-stack restriction is enforced structurally, in `Api::BaseController#stacks`, which restricts the queryable set to `current_api_client.stack_id` when the client has one: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`, and `#stack` resolves `params[:stack_id]` against that restricted relation [2](#0-1) .

`Api::CCMenuController` however defines its own `stack` method that ignores this scoping and resolves directly against the full `Stack` table: `@stack ||= Stack.from_param!(params[:stack_id])` [3](#0-2) . The controller still declares `require_permission :read, :stack` [4](#0-3) , but that only validates the permission string, not the `stack_id` — a token created for Stack A that holds `read:stack` will also satisfy this check for a request naming Stack B.

This is the same trust-binding gap as the analog bug class: the equality the system is supposed to enforce is `token.stack_id == requested_stack.id` (when `token.stack_id` is present), but `CCMenuController#stack` breaks that equality by resolving the stack independent of the token's authorized scope.

### Impact Explanation
The CCMenu endpoint discloses stack name, activity, last build status/label/time, and web URL — internal deployment state — for the CI/deploy pipeline [5](#0-4) . A token minted for one stack (e.g. via `CCMenuUrlController`, which explicitly creates a client scoped to a single stack: `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')` bound implicitly by `stack_id`) [6](#0-5)  can be replayed with a different `stack_id` parameter to read the deploy state of any other stack in the Shipit instance, which is an unauthenticated-scope read of stack state that the token was never authorized to see.

### Likelihood Explanation
Any holder of a valid, stack-scoped `read:stack` API token (which may be distributed more widely than instance-wide tokens, e.g. embedded in a CI dashboard URL as in `CCMenuUrlController#fetch`) can trivially exploit this by changing the `stack_id` route/query parameter — no additional privilege or secret is required beyond possessing one legitimate scoped token.

### Recommendation
Change `Api::CCMenuController#stack` to use the inherited, scope-aware resolution (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!(params[:stack_id])`, so the `current_api_client.stack_id` restriction from `Api::BaseController#stacks` is honored consistently across all API controllers.

### Proof of Concept
1. As a Shipit user, request a CCMenu URL for Stack A via `CCMenuUrlController#fetch`, obtaining a token scoped to Stack A only (`stack_id` set, permissions `['read:stack']`).
2. Send `GET /api/:stack_a_id/ccmenu.xml?token=<token>` — succeeds as expected.
3. Send `GET /api/:stack_b_id/ccmenu.xml?token=<token>` for an unrelated Stack B.
4. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` unscoped, the request succeeds and returns Stack B's build/deploy status, even though the token was only ever authorized for Stack A.
