## Analysis

Notably, `StatusHandler#process` at [1](#0-0)  resolves target `Commit` objects purely by `sha` — with **no repository/organization scoping at all** — while `WebhooksController#verify_signature` authenticates the request against the GitHub App keyed by `repository_owner` (`repository.owner.login`/`organization.login`) taken from the same untrusted JSON body [2](#0-1) . In a multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications"), each org has its own optional `webhook_secret`; `GitHubApp#verify_webhook_signature` unconditionally returns `true` when no secret is configured for that organization [3](#0-2) .

### Title
Cross-organization write via mismatched "authenticating organization" vs. "acted-upon repository" fields in `WebhooksController` — (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects the `GitHubApp`/secret to validate a webhook against using `repository.owner.login` (or `organization.login`) taken from the unauthenticated request body [4](#0-3) . Once "verified," the handler dispatch (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) re-parses the same body and resolves the actual repository/stack/commit to act on using a *different* field — `repository.full_name` in `Handler#repository_name` [5](#0-4) , or, in `StatusHandler`, no repository field at all, just `sha` [1](#0-0) . Nothing cross-checks that the organization used to select/verify the signature matches the organization actually written to.

### Finding Description
In a Shipit instance configured with multiple GitHub Apps (one per organization, per `docs/setup.md` §"Using Multiple Github Applications"), each org's `GitHubApp` has its own independently configured, optional `webhook_secret` [6](#0-5) . If an org is configured without a secret (a documented, valid setup — "Webhook secret (optional)" per `docs/setup.md`), `verify_webhook_signature` trivially returns `true` for *any* payload claiming to belong to that org, without inspecting a signature header at all [3](#0-2) .

The binding broken is: **organization authenticated (`repository_owner` used to pick the `GitHubApp`/secret) ≠ repository actually written (`repository.full_name` used by `Handler#stacks`, or bare `sha` lookup in `StatusHandler`)**.

An unprivileged internet attacker (no `ApiClient` token, no GitHub session, no webhook secret needed) can:
1. POST directly to `/webhooks` with header `X-Github-Event: push`, and body: `{"repository": {"owner": {"login": "org-without-secret"}, "full_name": "victim-org/victim-repo"}, "ref": "refs/heads/main", "after": "<existing sha>"}`.
2. `verify_signature` calls `Shipit.github(organization: "org-without-secret")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally [3](#0-2) .
3. `PushHandler#process` then resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` — the org actually secured by its own (secret-protected) GitHub App — and calls `stack.sync_github(expected_head_sha: params.after)` [7](#0-6) , which enqueues `GithubSyncJob` [8](#0-7) . This job fetches real commits from `victim-org` via its own legitimately-installed App token and appends them to the stack, and — because `sync_changed_nothing` gating can be bypassed by controlling `after`/branch — can trigger continuous deployment for that stack.
4. Alternatively, `StatusHandler#process` writes a fabricated CI status onto **any** `Commit` row in the whole Shipit instance simply by matching `sha`, without any repository binding whatsoever [1](#0-0) , which can flip a PR's CI state to green and unblock the merge queue for `victim-org`.

### Impact Explanation
This allows an attacker who controls (or who is simply aware of) one organization configured in Shipit without a webhook secret to forge writes — commit syncs, fabricated CI statuses, and consequently unauthorized deploys/merges — against completely unrelated, properly-secured organizations tracked by the same Shipit instance. This is a cross-repository/cross-organization write and can lead to an unauthorized deploy or merge, matching the Critical impact bar ("cross-repository writes... an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Likelihood depends on at least one org in a multi-org Shipit deployment being configured without a `webhook_secret` — a state the project's own setup documentation presents as a normal, optional configuration choice, not a misconfiguration to avoid. Given that, the attack requires zero credentials: a bare, unauthenticated HTTP POST to the public `/webhooks` endpoint.

### Recommendation
Cross-validate that the organization used to select the verifying `GitHubApp` (`repository_owner`) matches the organization embedded in every field a handler subsequently acts on (`repository.full_name`'s owner segment, and any commit/stack lookups), rejecting mismatches. Additionally, `StatusHandler` should scope its `Commit.where(sha:)` lookup to commits belonging to the stack/repository actually named in the verified payload, rather than a bare, repository-agnostic `sha` match.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: push
Content-Type: application/json

{
  "repository": {
    "owner": { "login": "org-without-secret" },
    "full_name": "victim-org/victim-repo"
  },
  "ref": "refs/heads/main",
  "after": "<sha already present in victim-org/victim-repo>"
}
```
No `X-Hub-Signature` header is required if `org-without-secret`'s `webhook_secret` is unset; `verify_signature` passes, and `PushHandler` acts on `victim-org/victim-repo` regardless.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

    def perform(params)
      @stack = Stack.find(params[:stack_id])
      expected_head_sha = params[:expected_head_sha]
      retry_count = params[:retry_count] || 0
      head_before_sync = spec_cache_target
      appended_commits = []

      handle_github_errors do
        new_commits, shared_parent = fetch_missing_commits { stack.github_commits }

        # Retry on Github eventual consistency: webhook indicated new commits but we found none
        if expected_head_sha && new_commits.empty? && !commit_exists?(expected_head_sha) &&
           retry_count < MAX_RETRY_ATTEMPTS
          GithubSyncJob.set(wait: RETRY_DELAY * retry_count).perform_later(params.merge(retry_count: retry_count + 1))
          return
        end

        stack.transaction do
          shared_parent&.detach_children!
          appended_commits = new_commits.map do |gh_commit|
            append_commit(gh_commit)
          end
          stack.lock_reverted_commits! if appended_commits.any?(&:revert?)
        end
      end
      sync_changed_nothing = appended_commits.empty? &&
                             spec_cache_target == head_before_sync &&
                             stack.cached_deploy_spec.present?
      return if sync_changed_nothing && !params[:force_spec_cache]

      CacheDeploySpecJob.perform_later(stack)
    end
