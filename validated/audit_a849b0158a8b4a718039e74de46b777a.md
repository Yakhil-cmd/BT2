### Title
`pull_request` webhook authenticates against `repository.owner.login` but mutates the stack resolved from `repository.full_name`, letting a no-secret org's trust forge label writes onto any victim `ReviewStack` - ([File: app/controllers/shipit/webhooks_controller.rb], [File: lib/shipit/github_app.rb], [File: app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp` (and therefore the secret to validate against) using `repository.owner.login` from the JSON body, while every downstream handler—including `LabelCapturingHandler`—resolves the affected `Repository`/`Stack` using the independently-controlled `repository.full_name` field, with no cross-check that the two refer to the same tenant. [1](#0-0) [2](#0-1) [3](#0-2)  Because `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever the selected organization has no `webhook_secret` configured, an attacker who names `repository.owner.login` as any such no-secret org (their own, or any laxly configured tenant on the same Shipit instance) while setting `repository.full_name` to a fully-secured victim repo can pass verification and still have the payload processed against the victim's repository. [4](#0-3) 

### Finding Description
The broken binding: the code implicitly assumes `repository_owner == owner(repository.full_name)`, i.e. the organization used to pick the verification secret is the same tenant whose repository/stack state gets mutated. No such equality is enforced anywhere in `verify_signature`, `LabelCapturingHandler`, or `ReviewStackAdapter`.

- `verify_signature` computes `repository_owner` purely from `params.dig('repository', 'owner', 'login')` (falling back to `organization.login`) and uses it only to pick `Shipit.github(organization: repository_owner)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank/unset—the malformed-signature `split('=', 2)` path (`algorithm` = whole header, `signature` = `nil`) is never reached in that branch, exactly as the question itself notes. [4](#0-3) 
- Once past `before_action`, `create` dispatches to handlers using `Shipit::Webhooks.for_event(event)`, passing the raw parsed JSON—including the attacker-controlled `repository.full_name`. [5](#0-4) 
- `LabelCapturingHandler#repository` looks the target repository up from `params.repository.full_name` alone, with `NullRepository` fallback if not found, and never re-derives or re-checks the org whose secret authenticated the request. [6](#0-5) 
- `capture_labels?` allows `action == "reopened"` on any present, non-archived stack (`reopened_active_stack?`), and `capture_labels` persists `params.pull_request.labels.map(&:name)` onto that stack's `PullRequest` record. [7](#0-6) 
- `ReviewStack#env` merges `pull_request.labels` as uppercased `"true"` env entries into the task environment, and this is what flows into deploy/task commands (`TaskCommands#env`, `DeployCommands`), which are ultimately exec'd via `Command`/`PTY.spawn` during continuous delivery. [8](#0-7) [9](#0-8) 

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, a body where `repository.owner.login` names an organization configured in this Shipit instance with no `webhook_secret` (e.g. their own sandbox org, or any tenant an operator forgot to set a secret for), `repository.full_name` set to the victim's `owner/repo`, `action: "reopened"`, and `pull_request.labels` set to attacker-chosen label names. `X-Hub-Signature` can be anything (even absent/malformed) because the no-secret branch never evaluates it.

Why existing guards fail: `check_if_ping` and `drop_unhandled_event` only gate on event type; `verify_signature`'s only check is the per-org secret comparison, scoped to the wrong field (`owner.login`) relative to the field actually used for resource resolution (`full_name`); there is no model-level or handler-level assertion that the authenticated org matches the target repository's owner.

### Impact Explanation
An unprivileged attacker can write attacker-chosen `PullRequest#labels` onto a victim `ReviewStack` they do not control, which become uppercase environment variables merged into every subsequent deploy/task/`ContinuousDeliveryJob` run for that stack (e.g., flags like `SKIP_TESTS=true`, `FORCE=true`, or anything the victim's deploy scripts interpret from env). Because the target stack is chosen independently of the authenticating secret, this is a payload authenticated for one tenant/org mutating another repository's stack state—matching the Critical category "a payload for one repository mutating another's stack, commit, task or team." Repeatable against any victim `ReviewStack` as long as the attacker can name/find one no-secret-configured org on the same Shipit instance; blast radius spans all tenants sharing that Shipit deployment.

### Likelihood Explanation
Requires: (1) at least one organization configured in this Shipit instance without a `webhook_secret` (an operator configuration gap, but the code makes no attempt to prevent cross-org effects even when such a gap exists), (2) a target `ReviewStack` that already exists (created from a real PR) and is not archived, with `continuous_deployment` enabled to realize the auto-ship amplification. Attacker cost is a single unauthenticated HTTP POST; no GitHub, session, or API secrets are needed. Feasibility depends entirely on operator misconfiguration of at least one org's secret—this is plausible in multi-tenant Shipit installs where some low-stakes orgs are onboarded without setting `webhook_secret`.

### Recommendation
Bind the authenticated organization to the resource actually mutated: after `verify_signature` succeeds, re-derive `repository.full_name`'s owner and reject the request (422) if it doesn't match `repository_owner`/the org whose secret authenticated it. Additionally, require `webhook_secret` to be present for every configured org (fail closed instead of `return true unless webhook_secret`), and have handlers assert the resolved `Repository`'s owner matches the verified organization before performing any writes.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb`-style, no live GitHub):
1. Configure two orgs in the test `Shipit.github_apps` fixture/config: `"no-secret-org"` with `webhook_secret: nil`, and `"victim-org"` with `webhook_secret: "realsecret"`.
2. Create `victim_stack = Shipit::ReviewStack.create!(environment: "pr42", continuous_deployment: true, repository: shipit_repositories(:"victim-org/victim-repo"))` with an attached `pull_request` (`stack.build_pull_request.update!(github_pull_request: ...)`), labels empty.
3. POST to `/webhooks` with `X-Github-Event: pull_request`, no valid `X-Hub-Signature` (or malformed one), body: `{ action: "reopened", number: 42, repository: { owner: { login: "no-secret-org" }, full_name: "victim-org/victim-repo" }, pull_request: { ...head/user/assignees..., labels: [{ name: "FORCE_DEPLOY" }] }, sender: { login: "attacker" } }`.
4. Assert `response.status == 200` (not 422), proving verification was bypassed via the `no-secret-org` selection.
5. Assert `victim_stack.reload.pull_request.labels == ["FORCE_DEPLOY"]` and `victim_stack.env["FORCE_DEPLOY"] == "true"`, proving a payload "authenticated" under `no-secret-org`'s (non-)secret mutated `victim-org`'s stack state—violating the invariant "A `pull_request` event only affects the repository/stack whose secret authenticated it."

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
