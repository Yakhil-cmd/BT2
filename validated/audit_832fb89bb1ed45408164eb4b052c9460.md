### Title
Denial of Service via unbounded recursion in `replaceInTemplate` when evaluating `definition template` address/asset conditions - (File: `definition.js`)

### Summary
`replaceInTemplate()` in `definition.js` recursively walks an entire attacker-supplied JSON structure with no depth limit, no complexity counter, and no periodic call-stack interruption. This function is invoked whenever a `definition template` operator is evaluated inside an address definition or spending condition, using a template that any unprivileged user can store beforehand via a `definition_template` message, which itself is validated with only a two-element-array check and no depth/complexity bound. An attacker can therefore craft a deeply nested template and trigger a stack overflow / process crash in any node that validates a unit exercising that condition — the same recursion-based DoS bug class as the reported `smol-toml` advisory (unbounded recursion during parsing/processing of attacker input).

### Finding Description
1. Storing the template: a `definition_template` message's payload is validated only by `ValidationUtils.isArrayOfLength(payload, 2)`, both in the plain-unit path [1](#0-0)  and in the AA path [2](#0-1) . There is no restriction on the nesting depth or size of the stored `payload` structure (unlike other AA payload fields such as denominations or choices, which are explicitly length-capped).

2. Using the template: when an address definition (or asset spending condition) contains a `['definition template', [unit, params]]` node, `evaluate()` loads the stored template and calls `replaceInTemplate(arrTemplate, params)`: [3](#0-2) 

The same pattern exists in the authentifier-evaluation path: [4](#0-3) 

3. `replaceInTemplate`/`replaceInVar` recurse into every array element and object property of `arrTemplate` with **no depth counter, no `MAX_DEPTH` check, and no periodic `setImmediate`/stack-interruption trick** (unlike `evaluate()` in the same file, which increments `complexity`/`count_ops` and enforces `constants.MAX_COMPLEXITY`/`MAX_OPS`, or `aa_validation.js`'s `validate()`, which explicitly checks `depth > MAX_DEPTH` and periodically calls `setImmediate`): [5](#0-4) 

Because the stored template's nesting depth is unbounded at creation time, and `replaceInTemplate` walks it recursively without any depth cap, a template with tens of thousands of nested arrays/objects will cause `replaceInVar` to recurse to a matching depth, exceeding V8's call-stack limit (`Maximum call stack size exceeded`) and crashing the Node.js process that is validating the referencing unit — a raw JS exception uncaught by the validation flow (thrown, not passed to `cb`), analogous to the `smol-toml` PoC (`'# comment\n'.repeat(8000) + ...` causing a stack overflow via unbounded recursive comment-skipping).

### Impact Explanation
Any node (full node, hub, or light-vendor doing full validation) that processes a unit signed by an address whose definition (or an asset's spend/issue condition) contains a `definition template` operator referencing an attacker-planted deeply nested template will crash with a stack overflow while evaluating `validateDefinition`/`validateAuthentifiers`. Since address definitions and asset conditions are public and reusable, a single malicious template + one unit exercising it can be relayed/gossiped to and validated by many nodes, each independently crashing — a network-wide availability impact (CWE-674, matches the CVSS `A:L` availability-only impact of the advisory). This is reachable by a completely unprivileged unit poster: no special role, key leak, or protocol privilege is required, only the ability to post two ordinary units (one `definition_template` message, one unit using an address/condition with `definition template`).

### Likelihood Explanation
Likelihood is high for an attacker with basic protocol knowledge: both required messages (`definition_template` payload and an address definition containing `['definition template', ...]`) are standard, currently-accepted message types with no depth validation on the template payload. Building a deeply nested JSON array (e.g. `[[[[...]]]]` repeated tens of thousands of times) is trivial and well within unit size limits, since size limits alone don't restrict nesting depth. No coordination with other network participants, no compromised keys, and no timing dependencies are required.

### Recommendation
- Enforce a maximum nesting-depth (and/or total node count) limit on `definition_template` payloads at validation time, consistent with `aa_validation.js`'s `MAX_DEPTH` pattern.
- Add an explicit depth parameter/counter to `replaceInTemplate`/`replaceInVar` in `definition.js` that aborts with an error once a bound (e.g. `MAX_DEPTH`) is exceeded, mirroring the protections already present in `evaluate()` (`complexity`/`count_ops`) and `aa_validation.js`'s `validate()` (`depth > MAX_DEPTH`, periodic `setImmediate`).
- Ensure any thrown exception from `replaceInTemplate` is caught and converted into a normal validation error (`cb(err)`), not left able to crash the process, at both call sites (`definition.js` lines ~330-339 and ~813-816, the latter of which doesn't even wrap the call in try/catch).

### Proof of Concept
1. Attacker posts unit A containing message `{app: 'definition_template', payload: [<deeply nested array template>, ...]}` (e.g. depth 50,000: `'['.repeat(50000) + '1' + ']'.repeat(50000)`-like structure as the template, per the earlier existing test showing 2000-deep arrays already stress formula recursion) — accepted because validation only checks `isArrayOfLength(payload, 2)`.
2. Attacker (or victim address controller) creates/uses an address whose definition includes `['definition template', [unit_of_A, {param1: 'x'}]]`.
3. Attacker posts unit B authored/spent by that address (or referencing the asset condition), forcing any validating node to call `validateDefinition`/`validateAuthentifiers` → `evaluate()` → `replaceInTemplate(arrTemplate, params)` on the deeply nested template.
4. `replaceInVar`'s unbounded recursion exhausts the call stack, throwing `RangeError: Maximum call stack size exceeded`, which is not caught in the `definition.js:802-819` path and crashes the validating node's process.

function replaceInTemplate(arrTemplate, params){
	function replaceInVar(x){
		switch (typeof x){
			case 'number':
			case 'boolean':
				return x;
			case 'string':
				// searching for pattern "$name"
				if (x.charAt(0) !== '$')
					return x;
				var name = x.substring(1);
				if (!ValidationUtils.hasOwnProperty(params, name))
					throw new NoVarException("variable "+name+" not specified, template "+JSON.stringify(arrTemplate)+", params "+JSON.stringify(params));
				return params[name]; // may change type if params[name] is not a string
			case 'object':
				if (Array.isArray(x))
					for (var i=0; i<x.length; i++)
						x[i] = replaceInVar(x[i]);
				else
					for (var key in x)
						assignField(x, key, replaceInVar(x[key]));
				return x;
			default:
				throw Error("unknown type");
		}
	}
	return replaceInVar(_.cloneDeep(arrTemplate));
}
