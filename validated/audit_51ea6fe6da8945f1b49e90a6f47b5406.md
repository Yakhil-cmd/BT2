### Title
`reward_per_token` cumulative index overflow can permanently DoS stake/unstake/harvest and freeze staked funds in `pallet-asset-rewards` - (`substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements a Compound/Aave-style "reward-per-token" accumulator (`PoolInfo::reward_per_token_stored`) that only ever increases, computed as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`. This is structurally identical to the reported `RewardsDistributor.index` bug: an ever-growing accumulator that is inversely proportional to a pool's total staked/supplied amount, with no lower bound on that denominator and no fallback when the checked arithmetic saturates its integer width. Because the accumulator is recomputed and persisted on every `stake`, `unstake`, and `harvest_rewards` call, once it can no longer be updated, all of these extrinsics revert — including `unstake`, which permanently locks any staker's frozen tokens in the pool.

`total_tokens_staked` is user-controlled: any signed account can call `stake`/`unstake` freely, and `unstake` performs no minimum-remaining-stake check — `ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens)` is the only guard. [2](#0-1) 

This means a pool's `total_tokens_staked` can legitimately be driven down to a dust value (e.g. `1`) by ordinary unstaking, exactly the "dust total supply" precondition in the original report. With `total_tokens_staked` at dust, the per-block increment `reward_rate_per_block * blocks_elapsed * 4096 / total_tokens_staked` becomes disproportionately large, and the cumulative `reward_per_token_stored.ensure_add(...)` will eventually saturate `T::Balance`'s max value, causing `ensure_add`/`ensure_mul`/`ensure_div` (via `sp_runtime::traits::Ensure*`) to return an `ArithmeticError` instead of silently wrapping.

Every state-mutating call in the pallet begins by invoking `update_pool_and_staker_rewards` → `reward_per_token`: [3](#0-2)

- `unstake` (line 529-530)
- `harvest_rewards` (line 584-585) [4](#0-3) [5](#0-4) [6](#0-5) 

Once `reward_per_token` starts erroring, all three extrinsics propagate the error via `?` and abort before any mutation, meaning `unstake` itself becomes permanently unusable for that pool. Since staked tokens are held via `AssetsFreezer::increase_frozen` and only released inside `unstake` (which cannot complete), the remaining staker's tokens become frozen indefinitely — no admin or governance action in the pallet can reset `reward_per_token_stored` or `total_tokens_staked` to recover it (`cleanup_pool` requires zero stakers, which can no longer be reached).

### Impact Explanation
This is a genuine, no-privilege-required chain-state DoS + fund-freezing bug pattern matching the report's "index reaches type max and blocks all further updates" root cause: missing threshold/lower-bound check on the divisor (`total_tokens_staked`) combined with hard-reverting checked arithmetic on an ever-accumulating value. If triggered, it permanently disables `stake`, `unstake`, and `harvest_rewards` for the affected pool and locks the last staker(s)' frozen assets with no recovery path in the pallet logic.

### Likelihood Explanation
Lower than the original EVM report because Substrate's `T::Balance` (`Balance: BaseArithmetic + ... ` — u128 in the pallet's own mock/tests) has vastly more headroom (~3.4×10^38) than Solidity's `uint104` (~2×10^31), and `PRECISION_SCALING_FACTOR` is a small constant (4096) rather than `10**decimals`. Reaching the overflow point requires either an extremely large `reward_rate_per_block` sustained over enough blocks, or `total_tokens_staked` pinned at dust for a long time — both are attacker-influenceable (via unstaking down and simply waiting/calling periodically) but require considerably more "stars aligning" than the original 18-decimal/uint104 scenario. Additionally, it is not established from the indexed code that `pallet-asset-rewards` is wired into any live Polkadot/Kusama/Asset Hub runtime — this appears to be a newer, possibly still-staging pallet, which affects bounty-program eligibility per the scan rules even though the code path itself is real production pallet logic reachable via ordinary signed extrinsics.

### Recommendation
- Enforce a minimum non-dust threshold on `total_tokens_staked` relative to `reward_rate_per_block`/`PRECISION_SCALING_FACTOR`, or require a minimum stake amount in `stake`/disallow unstaking below a floor while other rewards are still accruing (mirroring nomination-pools' `ok_to_join`/`ok_to_be_open` `points_to_balance_ratio_floor` pattern, which this pallet lacks).
- Consider widening precision or capping `reward_per_token_stored` growth, and ensure `unstake` can always succeed to release frozen funds even if reward accrual saturates (e.g., decouple reward computation failures from the ability to withdraw principal).

### Proof of Concept
No executable PoC was run against a live network or test harness; this is a structural code-path analysis. A concrete FRAME integration test would need to: create a pool with `CreatePoolOrigin`, have a staker `stake` a small amount, have other stakers `unstake` down to leave `total_tokens_staked` at `1`, advance blocks via the mock `BlockNumberProvider`, and repeatedly call `stake`/`harvest_rewards`/`unstake` while increasing `reward_rate_per_block` (via `set_pool_reward_rate_per_block`, admin-only but not attacker-controlled) or waiting enough blocks to force `reward_per_token`'s `ensure_add`/`ensure_mul` to return `Err(ArithmeticError)`, then assert `unstake` also fails, confirming the frozen-fund lock. This was not executed; the finding is based on static code-path tracing of `reward_per_token`, `update_pool_and_staker_rewards`, `stake`, and `unstake` in `substrate/frame/asset-rewards/src/lib.rs`, cross-referenced against the report's root cause (unbounded index / dust-denominator overflow with a hard-revert guard).
