### Title
Reverting Recipient in `handleKLAYTransfer` Permanently Locks Bridged KAIA and Freezes `lowerHandleNonce` — (`File: contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

`BridgeTransferKLAY.handleKLAYTransfer` delivers KAIA to the recipient via a raw `.call.value()` to the user-controlled `_to` address. If `_to` is a contract whose fallback reverts, every operator attempt to settle that nonce reverts atomically, the nonce is never marked handled, `lowerHandleNonce` never advances past it, and the KAIA locked on the source bridge is permanently unrecoverable. Any unprivileged user can trigger this by specifying a reverting contract as `_to` when calling `requestKLAYTransfer`.

---

### Finding Description

In `BridgeTransferKLAY.sol`, `handleKLAYTransfer` follows this sequence:

```
_lowerHandleNonceCheck(_requestedNonce)          // guard
_voteValueTransfer(_requestedNonce)              // multi-sig vote; sets closedValueTransferVotes[N]=true on threshold
_setHandledRequestTxHash(_requestTxHash)         // marks tx hash
handleNoncesToBlockNums[N] = _requestedBlockNumber
_updateHandleNonce(N)                            // advances lowerHandleNonce / upperHandleNonce
emit HandleValueTransfer(...)

(bool ok, ) = _to.call.value(_value)("");        // ← external call to user-controlled address
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

Because Solidity reverts are atomic, if `_to.call` returns `false` (or the callee reverts), every state mutation in the same transaction — including `closedValueTransferVotes[N] = true`, `handleNoncesToBlockNums[N]`, and the `lowerHandleNonce` update — is rolled back. The nonce is left in a permanently unprocessable state: operators cannot skip it, and every retry reverts identically.

The `_updateHandleNonce` function advances `lowerHandleNonce` only when consecutive nonces have `handleNoncesToBlockNums[i] > 0`:

```solidity
for (i = lowerHandleNonce; i <= limit && handleNoncesToBlockNums[i] > 0; i++) { ... }
lowerHandleNonce = i;
``` [2](#0-1) 

Since nonce N is never successfully written, `lowerHandleNonce` is permanently frozen at N. The value-transfer recovery system (`vt_recovery.go`) reads `LowerHandleNonce()` from the contract as its recovery starting point: [3](#0-2) 

With `lowerHandleNonce` frozen, the recovery loop perpetually re-queues nonce N, which always fails, breaking the bridge's automated recovery for all subsequent unhandled nonces.

The attack entry point is `requestKLAYTransfer` (or the fallback) on the source bridge, which any user can call: [4](#0-3) 

The user specifies `_to` freely. Bridge operators faithfully relay the `_to` value from the `RequestValueTransfer` event into `handleKLAYTransfer`: [5](#0-4) 

---

### Impact Explanation

- **Bridged KAIA permanently locked**: The KAIA deposited into the source bridge on the source chain can never be released on the destination chain. The `handleKLAYTransfer` for that nonce always reverts; there is no skip or override mechanism.
- **`lowerHandleNonce` frozen**: Because `handleNoncesToBlockNums[N]` is never written, `lowerHandleNonce` cannot advance past N. This corrupts the bridge's nonce accounting.
- **Recovery mechanism broken**: `vt_recovery.go` uses `LowerHandleNonce()` as the floor for pending-event retrieval. A frozen `lowerHandleNonce` causes the recovery loop to perpetually retry the stuck nonce, preventing automated recovery of any subsequent unhandled transfers.

---

### Likelihood Explanation

The trigger requires only a standard `requestKLAYTransfer` call with `_to` set to a contract whose `receive`/fallback reverts. This is reachable by any unprivileged user with no special role. A malicious actor can deliberately deploy such a contract and use it as `_to`. Even non-malicious users can accidentally trigger this if `_to` is a multisig or proxy that does not accept plain KAIA transfers.

---

### Recommendation

Adopt a pull-payment pattern: instead of pushing KAIA to `_to` inside `handleKLAYTransfer`, record the pending withdrawal in a mapping and let `_to` claim it separately. Alternatively, use a try/catch pattern (Solidity ≥ 0.6) to catch the revert and emit a `TransferFailed` event without reverting the nonce-accounting state, so `lowerHandleNonce` can still advance. At minimum, remove the `require(ok, ...)` and emit a failure event, allowing operators to mark the nonce as handled even when delivery fails.

---

### Proof of Concept

1. Deploy a malicious contract `Blocker` on the destination chain:
   ```solidity
   contract Blocker {
       receive() external payable { revert("blocked"); }
   }
   ```

2. On the source chain, call:
   ```solidity
   bridge.requestKLAYTransfer{value: 1 ether}(address(blocker), 1 ether, "");
   ```
   This emits `RequestValueTransfer` with `_to = address(blocker)`, nonce = N.

3. Bridge operators observe the event and call on the destination bridge:
   ```solidity
   bridge.handleKLAYTransfer(txHash, from, address(blocker), 1 ether, N, blockNum, "");
   ```
   The call reaches line 98 (`_to.call.value(_value)("")`), `Blocker.receive()` reverts, `require(ok, ...)` reverts the entire transaction.

4. Verify:
   - `bridge.lowerHandleNonce()` remains at its pre-N value — never advances.
   - `bridge.handleNoncesToBlockNums(N)` returns 0 — nonce N was never committed.
   - Every subsequent operator retry for nonce N reverts identically.
   - The 1 KAIA deposited on the source bridge is permanently locked.
   - The recovery system (`vt_recovery.go`) loops indefinitely on nonce N.
