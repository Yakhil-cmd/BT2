## Title
Cross-repository commit-status forgery via unscoped `StatusHandler` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler` writes GitHub commit statuses purely by matching a raw `sha` string, without checking that the SHA belongs to the repository the inbound webhook was actually signed for. This breaks the trust binding between "organization/repository the webhook was authenticated for" and "repository whose data gets written," letting a webhook that is legitimately signed for one repository push a fabricated status onto a commit that belongs to a completely different stack/repository in Shipit.

### Finding Description
Shipit verifies webhooks by HMAC-signing the whole payload against the secret configured for the *organization* named in the payload's `repository.owner.login` field: [1](#0-0) [2](#0-1) 

This only proves the sender knows the secret for a given GitHub organization/app installation — it says nothing about which specific repository's data the payload should be allowed to modify. Each event handler is therefore responsible for scoping its writes to the repository named in the payload. `Handler` provides exactly that helper: [3](#0-2) 

`PushHandler` and `CheckSuiteHandler` correctly use this `stacks` scoping (filtered by `repository.full_name`) before touching any commit: [4](#0-3) [5](#0-4) 

`StatusHandler`, however, ignores the repository entirely and looks up commits globally by SHA across the whole Shipit instance: [6](#0-5) 

Because `Commit#create_status_from_github!` attaches the new status using `commit.stack_id` (the commit's own real stack), the write lands on whatever stack that SHA actually belongs to — not the stack named in the authenticated webhook payload: [7](#0-6) 

Creating that status can flip a commit's simple state to `success`, which triggers auto-merge scheduling and deployability changes: [8](#0-7) 

**Binding broken:** `{organization authenticated by webhook signature, repository named in payload}` ≠ `{repository/stack whose commit actually receives the status write}`.

GitHub's Commit Statuses API (`POST /repos/:owner/:repo/statuses/:sha`) does not require the `sha` to be an ancestor of `:repo`'s history — any caller with `repo:status`/push access to *some* repository `A` in an organization can post a status naming an arbitrary 40-character SHA (e.g., a SHA copied from a different, unrelated repository `B` in the same org, or from a public commit anywhere). GitHub relays this as a `status` webhook whose `repository` field is `A`, correctly signed with organization `A`'s webhook secret (or the shared org-level GitHub App secret if Shipit uses a single org-wide app for multiple repositories/stacks). `StatusHandler` then updates the status of whatever commit happens to match that SHA in Shipit's database — which may belong to a `Stack` for repository `B`, a repository the attacker has no access to.

### Impact Explanation
An attacker with only push/status-write access to one repository connected to Shipit can forge a passing (`success`) CI status on a commit belonging to a different repository/stack they do not control. Per `add_status`, a transition to a "success"/"pending" simple state schedules `stack.schedule_merges`, which can drive the merge queue and continuous-delivery pipeline toward merging/deploying that commit. This can result in an unauthorized merge or deploy of a stack the attacker was never authorized to touch — matching the Critical criteria of "an unauthorized deploy, rollback or merge."

### Likelihood Explanation
Any Shipit installation that manages more than one repository under the same GitHub organization (a very common configuration, since webhook verification/authentication is keyed by organization, not repository) is exposed. The attacker only needs commit-status write privileges on any one repository in that org and knowledge of a target commit's SHA (SHAs are generally public/discoverable via GitHub). No Shipit session, API token, or webhook secret is required — only ordinary collaborator access to one repository.

### Recommendation
In `StatusHandler#process`, scope the commit lookup to the repository named in the verified webhook payload (mirroring `PushHandler`/`CheckSuiteHandler`'s use of the `stacks` helper), e.g. restrict to `stacks.flat_map(&:commits).where(sha: params.sha)` or otherwise join through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` before updating any commit's status.

### Proof of Concept
1. Attacker has commit-status write access (e.g., collaborator, or a CI integration token with `repo:status`) on `org/repo-A`, which is connected to Shipit.
2. `org/repo-B` is a separate, sensitive Stack in the same GitHub organization, using the same organization-level webhook secret configured in Shipit (`Shipit.github(organization: 'org')`).
3. Attacker finds the SHA of a pending/blocked commit on `repo-B`'s deploy branch (commit SHAs are typically visible via GitHub UI/API).
4. Attacker calls GitHub's Statuses API on `repo-A` (`POST /repos/org/repo-A/statuses/<repo-B-target-sha>`) with `state: success`.
5. GitHub sends a correctly-signed `status` webhook to Shipit with `repository.full_name = "org/repo-A"` and `sha = <repo-B-target-sha>`.
6. `WebhooksController#verify_signature` validates the signature against organization `org`'s secret and passes.
7. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, finds the commit belonging to `repo-B`'s stack, and calls `create_status_from_github!`, creating a forged `success` status on that stack's commit — potentially triggering `schedule_merges`/auto-deploy for `repo-B`, despite the attacker having no access to `repo-B`.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
