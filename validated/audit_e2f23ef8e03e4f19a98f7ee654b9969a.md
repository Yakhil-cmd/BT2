### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized PR merge - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` resolves the target commit for an incoming `status` webhook purely by `sha`, with no check that the webhook's `repository.full_name` matches the `stack`/`Commit`'s actual repository. Because the same git commit sha can legitimately be reproduced by any party who possesses that commit's exact content (git hashing is deterministic — pushing an identical commit object into an unrelated repository yields the identical sha, no cryptographic break required), an attacker who controls a repo in any Shipit-trusted GitHub org can forge a `success` status for a queued merge request's head commit belonging to a completely different repository/tenant, causing `Shipit::MergeRequest#merge!` to fire.

### Finding Description
The broken binding is:

`params.repository.full_name (Repo A, attacker's org)` **should equal** `merge_request.stack.repository.full_name (Repo B, victim's org)`

but `StatusHandler#process` never checks this: [1](#0-0) 

`Commit.where(sha: params.sha)` is an unscoped, cross-stack, cross-tenant query — it iterates over *every* `Commit` record in the database sharing that sha, calling `commit.create_status_from_github!(params)` on each, which creates a `Status` bound to that commit's own `stack_id`, not to the webhook's originating repository: [2](#0-1) [3](#0-2) 

The only authentication check in front of this handler is `WebhooksController#verify_signature`, which validates the HMAC signature against the org derived from `params.repository.owner.login` — it proves the payload came from *some* GitHub org configured in Shipit, but says nothing about which repository's commit the `sha` field actually belongs to: [4](#0-3) 

Because git commit hashes are a pure function of content (tree, parent(s), author, committer, message/timestamps) and not of which repository hosts them, an attacker who can obtain the exact bytes of a target commit (e.g. because Repo B is public, or the attacker previously had read access, or common fork lineage) can push that identical commit object into a branch/PR in their own Repo A. This is a legitimate git operation, not a hash collision or preimage attack. The attacker then triggers (or GitHub automatically sends) a `status` event with `state: success` for that sha, signed correctly by Repo A's org secret.

Once this webhook is processed, `Commit.where(sha:)` matches Repo B's queued `MergeRequest#head` commit, and `create_status_from_github!` attaches a forged `success` `Status` to Repo B's stack. `ProcessMergeRequestsJob#perform` subsequently calls `merge_request.refresh!` and checks `all_status_checks_passed?`: [5](#0-4) [6](#0-5) 

`all_status_checks_passed?` builds its `StatusChecker` purely from `head.statuses_and_check_runs` (commit-scoped, not repo-scoped), so the forged status counts toward the required-checks decision: [7](#0-6) 

If this flips the check from failing/missing to passing, `merge_request.merge!` calls `stack.github_api.merge_pull_request` against **Repo B**, using Shipit's own credentials for Repo B's org — an unauthorized merge triggered entirely by a webhook that Repo B's org never sent and never signed.

### Impact Explanation
This is a payload for one repository (Repo A) mutating another tenant's stack/commit/merge-request state (Repo B), and can escalate to an unauthorized merge of a pull request in a repository the attacker never controls or authenticated a webhook for — matching the Critical category ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). The forged status persists in the `statuses` table against Repo B's stack and is repeatable for any sha the attacker can reproduce; blast radius spans every stack tracked by the Shipit instance, since `Commit.where(sha:)` is global and unscoped by stack/repository.

### Likelihood Explanation
Preconditions are non-trivial but realistic in shared/multi-tenant Shipit deployments: the attacker must (1) control a repository under a GitHub org that Shipit already trusts (has a configured `webhook_secret`/App installation) — i.e. they must be an unprivileged member/owner of *some* onboarded org, not the victim's; (2) know the exact byte-for-byte content of the victim's queued PR head commit (tree, parents, author/committer identities and timestamps, message) in order to reproduce its sha — feasible if Repo B is public, if the two repos share fork lineage, or if the attacker had prior read access; (3) the victim `MergeRequest` must be `pending` with `StatusChecker` currently blocked on a missing/pending status so the forged `success` flips the decision. This is not a SHA-1 cryptographic break (no collision search needed) but does require reproducing exact commit metadata, which constrains but does not eliminate feasibility for public/forked repos.

### Recommendation
Scope the `status`/`check_run` webhook handlers by repository, not sha alone: resolve the target `Stack`/`Repository` from `params.repository.full_name` first, then constrain `Commit.where(sha: params.sha, stack: stack)` (or equivalent join through `Stack#repository`) before calling `create_status_from_github!`. Reject or ignore statuses whose `repository.full_name` does not match the stack owning the matched commit.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, or `test/jobs/process_merge_requests_job_test.rb`):
1. Create two stacks, `stack_a` (repository `attacker/repo-a`) and `stack_b` (repository `victim/repo-b`).
2. Create a `MergeRequest` on `stack_b` in `pending` merge_status, with `head` commit sha `SHARED_SHA`, and no passing status (StatusChecker returns `missing?/pending?` true, `success?` false). Assert `merge_request.all_status_checks_passed?` is `false` and `merge_request.stack.repository.full_name == "victim/repo-b"`.
3. Also create a `Commit` with the same sha `SHARED_SHA` under `stack_a` (simulating the attacker's reproduced commit in their own repo).
4. Build a `status` webhook payload: `{ sha: SHARED_SHA, state: "success", repository: { full_name: "attacker/repo-a", owner: { login: "attacker-org" } } }`, and invoke `StatusHandler.new.call(payload)` (or POST through `WebhooksController#create` with signature stubbed for `attacker-org`).
5. Assert a `Status` with `state: "success"` was created against `stack_b`'s commit (`merge_request.head.reload.statuses`), i.e. `params.repository.full_name != merge_request.stack.repository.full_name` yet the status was recorded for `stack_b`.
6. Assert `merge_request.reload.all_status_checks_passed?` is now `true`.
7. Run `ProcessMergeRequestsJob.new.perform(stack_b)` with `Shipit.github.api.expects(:merge_pull_request)` set to expect a call for `stack_b`'s repo/number — assert it is invoked, proving `merge_request.merge!` fired for `stack_b`'s PR solely due to a status webhook signed for `stack_a`'s org.
