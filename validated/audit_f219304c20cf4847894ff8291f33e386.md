### Title
Unauthorized nonce-authority hijack via front-run of `InitializeNonceAccount` (no signer/authority check) - (File: `programs/system/src/system_instruction.rs`)

### Summary
The System Program's `InitializeNonceAccount` instruction sets the nonce account's `authority` field to an attacker-supplied pubkey without requiring any signature — not from the nonce account itself, nor from any pre-existing authority. Any unprivileged transaction sender who references a writable, `Uninitialized`, System-owned nonce-account address can call this instruction first and permanently claim control of that nonce account before its legitimate owner's own initialize instruction executes, exactly mirroring the "first caller wins, no permission check" root cause described in the reference Gitcoin/Sherlock report for `IVotingStrategy.init()` / `IPayoutStrategy.init()`.

### Finding Description
`initialize_nonce_account` in [1](#0-0)  only checks that the account is writable and that its current state is `Uninitialized`, then unconditionally writes `State::Initialized(Data::new(*nonce_authority, ...))` using the caller-supplied `nonce_authority` argument. There is no check that:
- the nonce account itself is a transaction signer, or
- the caller is the account's creator/funder, or
- any prior authority approved the operation.

This is dispatched directly from `system_processor.rs` with no additional signer validation added at the instruction-processing layer: [2](#0-1) .

This is in stark contrast to the sibling nonce operations in the same file, which *do* enforce a signer/authority check before mutating state — `advance_nonce_account` requires `signers.contains(&data.authority)` [3](#0-2) , and `withdraw_nonce_account` requires `check_signer(&data.authority)` (or the account's own signature when uninitialized) [4](#0-3) . `initialize_nonce_account` conspicuously omits any analogous check, and its signature doesn't even take a `signers: &HashSet<Pubkey>` parameter [5](#0-4) .

The CLI's normal flow avoids this hazard only by bundling `CreateAccount` and `InitializeNonceAccount` into a single atomic transaction [6](#0-5) . But the protocol itself does not enforce this atomicity: `InitializeNonceAccount` is a standalone instruction that can be submitted independently by anyone in its own transaction. This mirrors the Gitcoin `init()` bug exactly: a security-critical one-time-initialization function is reachable by any caller with no permission check, and "the first sender" wins.

Concrete race scenario (fully triggerable by an unprivileged transaction sender, requiring no special access):
1. Victim creates (via `system_instruction::create_account`) a System-owned account funded with rent-exempt lamports, sized for nonce state, intending to send a follow-up `InitializeNonceAccount(victim_authority)` in a later transaction (e.g., a wallet/service that splits account creation and nonce initialization into separate transactions, or that pre-funds nonce accounts in batch before initializing them).
2. An attacker observes the pending/confirmed `CreateAccount` (or generally any System-owned, rent-exempt, `Uninitialized`-state account not yet nonce-initialized — including accounts that returned to `Uninitialized` after a full nonce withdrawal, as shown at [7](#0-6) ), and submits their own `InitializeNonceAccount(attacker_pubkey)` transaction referencing that address as a writable, non-signing account.
3. Because no signature is required from the nonce account or any authority, the attacker's transaction succeeds first and sets `authority = attacker_pubkey`.
4. The victim's subsequent `InitializeNonceAccount` call then hits the `State::Initialized(_)` branch and fails with `InstructionError::InvalidAccountData` [8](#0-7) , permanently blocking the victim from ever initializing that account as intended — the account is now durably controlled by the attacker as nonce authority (able to `advance`/`withdraw` per the authority checks shown above), until/unless the attacker relinquishes it.

### Impact Explanation
This grants an unprivileged attacker unauthorized control (privilege takeover) over another party's nonce account and its authority field — a durable-nonce authority controls the ability to advance the nonce (enabling free "replay-resistant" transaction construction with attacker-chosen blockhash-substitute values) and to withdraw the account's lamports once it is later funded, and can permanently deny the legitimate owner the ability to initialize the account as intended (a griefing/DoS on that specific account, directly analogous to "Round will never be created" in the source report). This satisfies the "unauthorized privilege/authority takeover" and "DoS of a protocol-critical initialization path" criteria from a single, unprivileged, submitted transaction.

### Likelihood Explanation
Likelihood is real but conditional on the higher-level usage pattern: it requires that `CreateAccount` and `InitializeNonceAccount` be submitted as two separate transactions (or that the account temporarily returns to `Uninitialized` state, e.g., after a full withdraw) rather than atomically combined as the reference CLI does today. Any wallet, exchange, or program that creates nonce accounts and initializes them in decoupled steps (common in more complex account-abstraction or batch-provisioning flows) is exposed to front-running by any observer of the pending transaction/mempool, or simply by scanning on-chain for rent-exempt, `Uninitialized` System-owned accounts.

### Recommendation
Require that `InitializeNonceAccount` either (a) be signed by the account being initialized (mirroring `Allocate`/`Assign`'s `address.is_signer(signers)` check pattern used elsewhere in the same file [9](#0-8) ), or (b) be signed by the funder/creator recorded at account-creation time, so that a third party cannot claim authority over an account they did not create. At minimum, add a signer check analogous to the one already used by `advance_nonce_account` and `withdraw_nonce_account` before allowing the state transition from `Uninitialized` to `Initialized`.

### Proof of Concept
1. Victim sends `SystemInstruction::CreateAccount` funding a new pubkey `N` with `nonce::State::size()` space, owned by the System program, with rent-exempt lamports (as a standalone transaction, not bundled with initialize).
2. Before the victim's follow-up `InitializeNonceAccount` transaction lands, attacker submits their own transaction with instruction `SystemInstruction::InitializeNonceAccount(attacker_pubkey)`, listing account `N` as writable and non-signing, per the accepted account layout used in `system_processor.rs`'s dispatch (`check_number_of_instruction_accounts(1)` only) [2](#0-1) .
3. `initialize_nonce_account` sees `State::Uninitialized`, has sufficient rent-exempt balance, and unconditionally sets `authority = attacker_pubkey` [10](#0-9) .
4. Victim's later `InitializeNonceAccount(victim_authority)` on the same account now hits `State::Initialized(_)` and fails with `InstructionError::InvalidAccountData` [8](#0-7) , confirmed by the existing regression test `initialize_inx_initialized_account_fail` [11](#0-10) . The account is now permanently under the attacker's nonce authority.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
