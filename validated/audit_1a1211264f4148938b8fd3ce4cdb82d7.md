## Title
Cross-tenant status injection triggers unauthorized deploys via webhook signature/repository binding mismatch - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` authenticates a webhook only against the GitHub organization named in the payload's `repository.owner.login` (or `organization.login`) field, selecting that organization's configured `webhook_secret` [1](#0-0) . This is the correct pattern for the multi-organization deployment mode Shipit explicitly supports [2](#0-1) [3](#0-2) . However, once the signature is verified for organization A, `Shipit::Webhooks::Handlers::StatusHandler#process` never re-checks that the `sha` in the payload belongs to a commit under organization A's repositories — it matches by raw commit SHA across the *entire* database:

```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [4](#0-3) 

### Finding Description
The equality that should hold is: `organization authenticated by verify_signature == organization/stack whose data is mutated by the handler`. It does not hold for the `status` event.

- `verify_signature` derives `repository_owner` purely from the payload body (`params.dig('repository','owner','login') || params.dig('organization','login')`) and uses it only to pick which configured GitHub App's `webhook_secret` to validate the HMAC against [5](#0-4) .
- Once verified, the controller dispatches the parsed JSON to `StatusHandler`, which looks up commits solely `WHERE sha = params.sha`, with no filter on stack, repository, or organization [6](#0-5) .
- `commit.create_status_from_github!(params)` passes the attacker-controlled `state`, `description`, `target_url`, `context`, and `created_at` straight through into a new `Status` record via `Status.replicate_from_github!` [7](#0-6) [8](#0-7) .
- Creating a `Status` record fires `schedule_continuous_delivery`, which calls `commit.schedule_continuous_delivery`, which (via `ContinuousDeliveryJob` / `Stack#trigger_continuous_delivery`) can trigger a real deploy if the target stack has `continuous_deployment: true` and the injected status makes the commit `deployable?` [9](#0-8) [10](#0-9) .

Because a git commit SHA is a public, non-secret identifier obtainable from GitHub, an attacker who legitimately administers **their own** GitHub organization/App entry in Shipit's multi-org config (and therefore knows their own org's `webhook_secret` value they configured) can sign an arbitrary `status` payload with that secret while setting `sha` to a commit belonging to a **victim organization's** stack. `verify_signature` will succeed (it only validates against the attacker's own org's secret, which matches), and `StatusHandler` will happily write a forged `success` status onto the victim commit, since it never checks that the commit's stack belongs to the organization that was actually authenticated.

### Impact Explanation
This breaks the organization-authenticated vs. repository-written binding: an attacker who controls one Shipit-tracked organization (their own webhook secret) can forge required-CI-status data for a commit in a completely different organization's stack. If that stack has continuous deployment enabled and the forged `success` status satisfies `ci.require`/blocking-status checks, this leads directly to an **unauthorized deploy** of that commit — one of the explicitly listed Critical impacts. It can also be used to bypass merge/deploy safety gating (masking a real CI failure) even without continuous deployment, by polluting the commit's status history relied on by `deployable?`.

### Likelihood Explanation
Exploitability only requires: (1) knowledge of a target commit SHA on a victim stack (public information), and (2) the attacker being a legitimate, unprivileged-relative-to-the-victim owner of any organization/App entry configured in the same Shipit instance's multi-org `github` config — a supported, documented configuration [3](#0-2) . No Shipit session, API token, or victim-org credentials are needed; the attacker signs with their own legitimately-known secret. This is directly analogous to the report's root cause pattern: a value scoped to one context (organization A) is applied without re-validating it against the object it actually mutates (a commit under organization B).

### Recommendation
In `StatusHandler#process` (and analogous handlers matching by SHA/number rather than by verified repository), scope the `Commit` lookup to the repository named in `payload.dig('repository','full_name')` and require that this repository's owning organization matches the organization that was verified in `WebhooksController#verify_signature`. Consider passing the verified `repository_owner` down into the handler dispatch so handlers can assert `stack.repository.owner == verified_organization` before mutating any record.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgA` (attacker-administered) and `OrgVictim`, each with its own `webhook_secret`, per the documented multi-org config [3](#0-2) .
2. Attacker (legitimate admin of `OrgA`'s GitHub App) obtains the public SHA of an undeployed commit on a stack owned by `OrgVictim` that has `continuous_deployment: true` and a `ci.require` context.
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/circleci",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC_SHA1(OrgA_webhook_secret, body)` and POSTs to `/webhooks`.
5. `verify_signature` resolves `repository_owner` = `"OrgA"`, fetches `OrgA`'s app, and the HMAC validates successfully [11](#0-10) .
6. `StatusHandler#process` matches `Commit.where(sha: "<victim commit sha>")` — found under `OrgVictim`'s stack — and creates a forged `success` `Status`, which can trigger `OrgVictim`'s continuous delivery pipeline [4](#0-3) .

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
