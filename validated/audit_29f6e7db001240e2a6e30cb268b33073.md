### Title
Cross-organization webhook secret confusion lets an attacker forge push/status/pull_request events for any repository tracked by the Shipit instance - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App configuration (and therefore which `webhook_secret`) to validate an inbound webhook against using `repository_owner`, a field read directly from the untrusted, not-yet-verified JSON body. [1](#0-0)  The value actually used afterwards by every event handler to decide *which repository/stack is mutated* is a different field from that same untrusted body: `repository.full_name`. [2](#0-1)  These two fields are never required to agree, so the "organization whose credentials authenticated the request" and "the repository the event is applied to" are two independently attacker-controlled values inside the same payload.

### Finding Description
In a single-organization deployment this is not exploitable because there is only one `webhook_secret` to check against. However, Shipit explicitly supports hosting multiple GitHub Apps/organizations from one instance, each with its own, independently-configured `webhook_secret` (`docs/setup.md` "Using Multiple Github Applications"). [3](#0-2)  `github.webhook_secret` is explicitly documented as optional per organization. [4](#0-3) 

`GitHubApp#verify_webhook_signature` short-circuits to `true` when no `webhook_secret` is configured for that organization:
```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
``` [5](#0-4) 

`WebhooksController#verify_signature` resolves *which* `GitHubApp`/secret to check against using `repository_owner`, taken straight from the unauthenticated raw request body (`params.dig('repository', 'owner', 'login')`):
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
  ...
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [6](#0-5) 

But the handlers that actually apply the event never look at `repository_owner`/the org used for authentication — they resolve the target repository purely from `repository.full_name` in the same JSON body:
```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 
`PushHandler` uses exactly this to select stacks and trigger `sync_github`: [7](#0-6) 
`PullRequest::OpenedHandler`/`ClosedHandler`/`LabeledHandler` resolve the repository the same way, independently of the org used for signature verification. [8](#0-7) [9](#0-8) 

The binding that should hold — "the organization whose GitHub App credentials authenticated this webhook == the repository whose stacks/state the handler mutates" — is not enforced. An attacker who knows (or can probe, since failed verification yields a distinct `422`/log message versus a processed `200`/`204`) that *some* org configured on the shared Shipit instance has no `webhook_secret` set, can send an arbitrary unsigned/any-signature payload with:
- `repository.owner.login` (or `organization.login`) = the name of the org with no configured secret (used only to pick the `GitHubApp` and pass `verify_webhook_signature`, which returns `true` unconditionally for that org)
- `repository.full_name` = the full name of a *different, victim* repository/org that Shipit tracks and that does have a properly configured secret.

`verify_signature` passes (because the selected org has no secret), and the handler then acts on the victim repository, since it only reads `repository.full_name`.

### Impact Explanation
This breaks the "GitHub App / organization authenticated versus repository written" binding explicitly called out as an in-scope analog class. Concretely, an unprivileged external attacker can:
- Forge `push` events to make `PushHandler` invoke `stack.sync_github(expected_head_sha: ...)` on stacks belonging to a victim org/repo they do not control, even though the shared secret protecting that victim repo was never satisfied. [10](#0-9) 
- Forge `pull_request`/`status`/`check_suite` events against arbitrary tracked stacks, affecting merge-queue state, review-stack archival/creation, and CI status records for repositories outside the org whose credential gated the request.

This is a cross-repository/cross-organization write achieved purely by supplying two attacker-controlled JSON fields, satisfying the "cross-repository writes" / "unauthorized" impact bar defined in scope. Whether it rises to Critical depends on the deployment mix (multi-org configurations with at least one org lacking a `webhook_secret`), but it is a real authentication-binding defect independent of that pre-condition: the design allows the field used for auth-selection and the field used for authorization-of-target to diverge within a single signed payload, which is exactly the confused-deputy pattern described in the analog rules.

### Likelihood Explanation
Requires: (1) the Shipit instance to be configured for multiple GitHub organizations (a documented, supported configuration), and (2) at least one of those organizations to have `webhook_secret` left unset (also documented as optional). Both conditions are plausible in real deployments (e.g., a low-risk sandbox/test org added without a secret). No credentials, session, or repository access are required by the attacker — only knowledge of an org name configured on the instance, discoverable by observing response codes (`422` for signature failure with logged `repository_owner`, vs. `200`/`204` for accepted events) while probing candidate org logins.

### Recommendation
Do not select the verification secret from an unauthenticated field that differs from the field later used to authorize the target repository. Concretely:
- Require that `repository.owner.login`/`organization.login` and `repository.full_name`'s owner segment match before dispatching to handlers, or
- Resolve the `GitHubApp` used for verification from the same value the handler will use to select the `Stack`/`Repository` (i.e. derive it consistently from `repository.full_name`), and
- Refuse to treat a missing `webhook_secret` as an implicit "always verified" for any organization once multi-org support is enabled, or at minimum reject events whose declared repository does not belong to the organization the request was verified against.

### Proof of Concept
Preconditions: Shipit configured with multiple orgs, e.g. `sandbox-org` (no `webhook_secret` configured) and `victim-org/victim-repo` (properly configured with a secret and an active stack).

1. Attacker sends:
```
POST /webhooks
X-Github-Event: push
X-Hub-Signature: sha1=anything-or-empty

{
  "ref": "refs/heads/main",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "sandbox-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. `WebhooksController#verify_signature` calls `Shipit.github(organization: "sandbox-org")` and `verify_webhook_signature` returns `true` because `sandbox-org` has no `webhook_secret`. [5](#0-4) 
3. `PushHandler#process` resolves stacks via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "deadbeef...")` on the victim's stacks, despite the request never being authenticated against `victim-org`'s secret. [10](#0-9) 

This confirms the "authenticated organization" and "repository acted upon" are independently attacker-controlled fields in the same unauthenticated payload, and the engine never verifies they correspond.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml
production:
  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

# frozen_string_literal: true

module Shipit
  module Webhooks
    module Handlers
      class PushHandler < Handler
        params do
          requires :ref
          requires :after
        end

        def process
          stacks
            .not_archived
            .where(branch:)
            .find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
        end

        private

        def branch
          params.ref.gsub('refs/heads/', '')
        end
      end
    end
  end
end
