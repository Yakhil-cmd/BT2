## Finding

`is_valid_signed_package()` in AA oscript lets an attacker replay a signature created under an address's *original* definition even after that address has rotated its key via `address_definition_change`, because the "network-unaware" signed-message-verification path in `signed_message.js` re-derives authorization purely from `chash160(definition) === address`, which is permanently satisfied only by the address's original (possibly compromised) definition.

### Title
Revoked/old address definitions remain permanently valid for `is_valid_signed_package` when `last_ball_unit` is omitted, defeating key-rotation "revocation" - (File: `signed_message.js`, `formula/evaluation.js`)

### Summary
Obyte addresses can rotate their signing key/definition at any time by posting an `address_definition_change` message, which is the protocol's designed mechanism for revoking a compromised key while keeping the same address. However, the `is_valid_signed_package` oscript primitive used by AAs to authenticate off-chain-signed messages does not require this rotation to be honored: if the attacker-supplied `signed_package` omits the optional `last_ball_unit` field, verification falls back to a definition supplied inline by the signer, and that inline definition is accepted as long as its hash equals the address - which, by construction, is only true for the address's *original* definition. This lets anyone holding an old/compromised key keep forging validly-authenticated messages for that address forever, exactly the "no way to revoke a signature" problem described in the reference report, just realized through address-definition rotation instead of a Factory.sol nonce.

### Finding Description
`formula/evaluation.js` implements `is_valid_signed_package`: [1](#0-0) 
The check on `last_ball_unit` (and the MCI/stability constraints tied to it) is only performed `if (typeof signedPackage.last_ball_unit === 'string')`. If the attacker simply omits `last_ball_unit` from the `signed_package` they place in trigger data, the code proceeds directly to `signed_message.validateSignedMessage(conn, signedPackage, evaluated_address, mci, ...)` with no last-ball reference at all.

Inside `signed_message.js`, `bNetworkAware` is computed as `("last_ball_unit" in objSignedMessage)`: [2](#0-1) 
When `bNetworkAware` is false, `validateOrReadDefinition` takes the "no last_ball_unit" branch, which never queries the address's *current* on-chain definition. Instead it requires the caller to supply a `definition` inline and only checks that its hash equals the address: [3](#0-2) 

Because an Obyte address is permanently defined as `chash160(initial_definition)` and never changes even after `address_definition_change` updates the *active* definition used for on-chain unit signing, the only definition array that can satisfy `getChash160(definition) === address` is the address's original definition (chash collision resistance makes any other definition with a matching hash infeasible to produce). Consequently:

- A user who signs with the key in their original definition, then rotates away from that key (via `address_definition_change`) after suspecting compromise, has *not* actually revoked that key for this verification path.
- Anyone still holding the old private key can construct a `signed_message` (with an arbitrary payload), sign it with the old key, attach the original `definition` inline, omit `last_ball_unit`, and it will pass `Definition.validateAuthentifiers` exactly as it would have before rotation: [4](#0-3) 

This is functionally identical to the reported bug class: a credential (signature) that should be revocable via a protocol-provided mechanism (definition rotation) remains permanently usable through an alternate, non-network-aware verification code path that ignores the revocation.

### Impact Explanation
AAs that use `is_valid_signed_package(...)` to authorize actions on behalf of a user address (e.g., decentralized-exchange order signing, off-chain approvals for AA-held funds, voting/attestation gating) are directly exposed: any attacker who ever obtained a user's original private key (leak, old device, compromised backup) can keep forging "approved" packages for that address indefinitely, regardless of the user rotating their address definition specifically to shut the attacker out. Where such AA logic gates fund transfers or state changes on this check, this results in AA fund loss/unauthorized actions attributable to a supposedly-revoked key — matching the "AA fund loss" and "unauthorized spending" impact categories.

### Likelihood Explanation
Reachable purely by an unprivileged AA trigger sender: the `signed_package` object lives entirely in attacker-controlled trigger `data`, and omitting `last_ball_unit` is a one-field change requiring no special privilege, network position, or race condition. Any AA design that relies on `is_valid_signed_package` for authorization based on an address's signature (a documented and expected use, per the "signature verification" test in `test/formula.test.js`) is affected as soon as a historical key for the referenced address is ever compromised and the owner attempts to rotate away from it.

### Recommendation
Either (a) make `last_ball_unit` mandatory for `is_valid_signed_package` so the current on-chain definition (as of a real MCI) is always consulted, removing the non-network-aware fallback in this AA-reachable path, or (b) change the non-network-aware branch in `signed_message.js` to still resolve/verify against the address's *latest known* definition rather than accepting any inline definition whose hash simply matches the address's original chash.

### Proof of Concept
1. User creates address `A` with definition `D0 = ["sig", {pubkey: P0}]`; `A = chash160(D0)`.
2. Private key for `P0` leaks to attacker.
3. User, upon suspecting compromise, posts `address_definition_change` rotating `A`'s active definition to `D1 = ["sig", {pubkey: P1}]`.
4. An AA that gates a withdrawal/action on `is_valid_signed_package(trigger.data.signed_package, 'A')` is triggered by the attacker with:
   ```
   signed_package: {
     signed_message: { action: "withdraw", amount: 1000000 },
     authors: [{ address: 'A', definition: D0, authentifiers: { r: <sig using leaked P0 key> } }]
     // no last_ball_unit field
   }
   ```
5. `formula/evaluation.js` skips the last-ball MCI checks (no `last_ball_unit`), calls `signed_message.validateSignedMessage` with `bNetworkAware = false`.
6. `validateOrReadDefinition` accepts `D0` because `getChash160(D0) === A`, never checking that `A`'s active definition is now `D1`.
7. `Definition.validateAuthentifiers` verifies the attacker's signature against `D0`'s `pubkey: P0` and succeeds, so `is_valid_signed_package` returns `true`, and the AA executes the withdrawal despite the user having rotated the key specifically to prevent this.
