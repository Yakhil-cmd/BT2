### Title
Webhook signature verification selects the signing organization from unauthenticated payload data, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In multi–GitHub-App deployments, `WebhooksController#verify_signature` chooses which organization's `webhook_secret` to verify the request against by reading `repository.owner.login` (or `organization.login`) directly out of the **unverified** JSON body, before any signature check occurs. Because this selector is itself outside the HMAC it is supposed to validate, and because the handlers that subsequently act on the payload key off other payload fields (e.g. `repository.full_name`, `sha`) rather than re-confirming the same organization, an attacker who knows (or can trigger) a weak/absent `webhook_secret` for *any one* configured organization can forge events that are processed as if they came from a *different*, stricter organization's repository.

using: [2](#0-1) 

`repository_owner` is read straight from `params`, i.e. from the raw, not-yet-verified request body (`params = JSON.parse(request.raw_post)` happens again in `create`). `Shipit.github(organization:)` resolves a per-organization `GitHubApp` instance from `config/secrets.yml`, a configuration explicitly documented as supporting one distinct `webhook_secret` per organization: [3](#0-2) [4](#0-3) 

Critically, `GitHubApp#verify_webhook_signature` returns `true` unconditionally whenever that organization's `webhook_secret` is not configured: [5](#0-4) 

This is the exact pattern the example configs use for “no secret configured” organizations (`webhook_secret: # nil`), including the dedicated multi-org test fixture: [6](#0-5) 

The binding that should hold is: *the organization whose secret authenticated the request* == *the organization owning the repository the handler subsequently mutates*. But the controller derives the authenticating organization from the same untrusted payload the handlers later use to pick the target repository/stack — and the handlers (e.g. `StatusHandler`) locate the target purely by `sha`/`repository` fields, without re-validating that they belong to the organization that was actually verified: [7](#0-6) 

So an attacker can submit a webhook body whose `repository.owner.login` is set to an organization that has no `webhook_secret` (or one the attacker knows), which makes `verify_signature` pass trivially, while any other repository-identifying data in the payload used by the handler corresponds to a **different**, unrelated stack/repository configured under a different (properly-secured) GitHub App. Nothing in `WebhooksController` or the handlers cross-checks that the "verifying" organization matches the repository actually being written to.

### Impact Explanation
This lets an unauthenticated, unprivileged attacker forge `push`, `status`, or `check_suite` events for a stack belonging to an organization other than the one whose (weak/absent) secret was used to pass verification. Forged `status` events let an attacker mark arbitrary commits as `success`, satisfying CI requirements enforced by `MergeRequest::StatusChecker` (`all_status_checks_passed?`), and forged `push` events can trigger `GithubSyncJob`/deploy-eligibility flows on stacks the attacker has no legitimate access to. Combined with the merge queue's reliance on commit statuses to decide mergeability, this can result in an unauthorized deploy or merge on a repository/stack the attacker doesn't control — meeting the Critical bar ("unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitation requires only network access to the public `/webhooks` endpoint (unauthenticated by design) and a deployment that configures more than one GitHub App/organization (a documented, supported configuration) where at least one organization has no `webhook_secret` set or a guessable one. No GitHub credentials, Shipit session, or ApiClient token are needed.

### Recommendation
Do not let the payload dictate which secret validates the payload. Verify the signature against every configured organization's secret (or against a single instance-wide secret), and only after successful verification use the payload to resolve the target repository/stack — then confirm that resolved repository's owning organization matches the organization whose secret verified the request. Alternatively, require a `webhook_secret` to be present for every configured GitHub App and reject requests when it's absent.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgWeak` (no `webhook_secret`) and `OrgStrict` (strong `webhook_secret`), each with a Stack registered under Shipit.
2. Send a `POST /webhooks` request with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "OrgWeak" }, "full_name": "OrgStrict/protected-repo" },
  "sha": "<sha of a commit in OrgStrict/protected-repo>",
  "state": "success",
  "context": "ci/required-check"
}
```
No `X-Hub-Signature` is required to be valid, because `verify_signature` resolves `Shipit.github(organization: "OrgWeak")`, whose `verify_webhook_signature` returns `true` unconditionally (`lib/shipit/github_app.rb:76-77`).
3. `StatusHandler#process` (`app/models/shipit/webhooks/handlers/status_handler.rb:20-24`) looks up `Commit.where(sha: params.sha)` — matching the commit in `OrgStrict/protected-repo` — and records the forged `success` status, independent of which organization "verified" the request.
4. If that commit is under merge-queue review, `MergeRequest::StatusChecker` will now see the required check as passed, enabling merge/deploy despite the forged origin.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
