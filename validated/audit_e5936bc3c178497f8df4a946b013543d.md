### Title
Webhook signature is checked against the wrong tenant's secret, allowing cross-repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to validate the HMAC signature with, based on `repository.owner.login` (falling back to `organization.login`) taken from the *unauthenticated* request body itself. [1](#0-0) [2](#0-1)  Once the signature is accepted, the actual event handlers resolve *which* `Stack`/`Repository` to mutate using a **different** field of the same payload: `repository.full_name`. [3](#0-2)  Because the signature-selection key (`owner.login`) and the write-target key (`full_name`) are never cross-checked against each other, an attacker who legitimately controls one tenant/organization's webhook secret in a multi-org Shipit deployment can produce a validly-signed payload whose `full_name` points at a stack belonging to a *different* organization, causing Shipit to act on that other organization's data.

### Finding Description
Shipit supports hosting multiple GitHub organizations from a single instance, each with its own `webhook_secret`/App credentials (`somegithuborg`, `someothergithuborg`, etc.), selected via `Shipit.github(organization: ...)`. [4](#0-3) [5](#0-4) 

The verification flow is:
1. `repository_owner` is read straight from the JSON body (`repository.owner.login`, or `organization.login`). [2](#0-1) 
2. That value is used to fetch the corresponding `GitHubApp`/secret and verify `X-Hub-Signature` against `request.raw_post`. [1](#0-0) [6](#0-5) 
3. If it verifies, `Shipit::Webhooks.for_event(event)` dispatches the full raw payload to handlers. [7](#0-6) 
4. Every handler then resolves the target `Stack`/`Repository` via `payload.dig('repository', 'full_name')` → `Repository.from_github_repo_name(...)`, completely independent of the `owner.login`/`organization.login` value that was used to authenticate. [3](#0-2)  This same pattern repeats in `PullRequest::OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, etc. [8](#0-7) [9](#0-8) 

This is the same class of bug as the reported smart-contract issue: the code checks one field (`deposits`) but acts on another concept (`debt`); here the code cryptographically verifies one field (`repository.owner.login` / `organization.login`) but acts on a different, unverified field (`repository.full_name`) to decide which resource is written. The equality that should hold but doesn't is:

`organization authenticated by signature (repository.owner.login) == organization that owns the repository actually written (repository.full_name)`

Before the fix these two are only linked "by convention" because GitHub itself always produces consistent payloads; an attacker forging a raw POST is free to decouple them as long as they can produce a signature that matches *some* configured organization's secret (i.e. they only need legitimate GitHub App/webhook-secret knowledge for **one** tenant on the instance, not for the tenant whose stack they end up touching).

### Impact Explanation
Because `full_name` — not `owner.login` — drives `Repository.from_github_repo_name` in `Handler#stacks`, `PushHandler#process` (which triggers `stack.sync_github(expected_head_sha:)` and enqueues `GithubSyncJob`), and the `PullRequest::*Handler`s (which call `review_stack.archive!` / `stack.unarchive!`), an attacker who is an admin for Organization A (and thus legitimately knows Org A's webhook secret) can sign a payload whose `repository.full_name` names a stack belonging to Organization B. This causes Shipit to enqueue syncs, archive/unarchive review stacks, or otherwise mutate state for a repository the attacker does not control — a cross-repository write across a tenant boundary that the signature check was supposed to enforce. This matches the "Critical – cross-repository writes" impact category.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (a configuration explicitly supported and documented by the engine, see `config/secrets.development.shopify.yml` and `Shipit.github_organizations`), and requires the attacker to control (or have legitimately been issued) the webhook secret for at least one of the hosted organizations — not for the target organization. Within that setup, forging the mismatch is trivial: it only requires crafting a JSON body with differing `owner.login`/`organization.login` and `repository.full_name` values and computing the HMAC with the attacker's own known secret.

### Recommendation
After signature verification succeeds, re-derive the organization/owner from `repository.full_name` (or `organization.login` for org-level events) and assert it matches the organization key (`repository_owner`) that was used to select the verifying secret before dispatching to handlers. Alternatively, look up the `Repository`/`Stack` for `full_name` first and verify the signature using **that** repository's own configured owner/secret rather than trusting the unauthenticated `owner.login` field to pick the verification key.

### Proof of Concept
Given a Shipit instance configured with two organizations, `orga` and `orgb`, each with its own `webhook_secret`, and a `Stack` tracking `orgb/target-repo`:

1. Attacker, who administers `orga` (and thus knows/controls `orga`'s webhook secret), crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha, or a sha attacker wants synced>",
  "repository": {
    "owner": { "login": "orga" },
    "full_name": "orgb/target-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC(orga_webhook_secret, raw_body)` and POSTs to `/github/webhooks`.
3. `verify_signature` resolves `repository_owner` = `"orga"`, fetches `Shipit.github(organization: "orga")`, and the HMAC check succeeds because the attacker used `orga`'s real secret. [1](#0-0) 
4. `Handler#stacks` / `Handler#repository_name` resolve based on `full_name = "orgb/target-repo"`, looking up and acting on `orgb`'s stack via `Repository.from_github_repo_name`. [3](#0-2) [10](#0-9) 
5. `PushHandler#process` calls `stack.sync_github(expected_head_sha: params.after)` on `orgb`'s stack, even though the request was never signed by `orgb`.

I was unable to further verify at what stack.sync_github/GithubSyncJob ultimately uses which GitHub API credentials for the target org's API calls (that would determine whether this also produces GitHub API errors/`mark_as_inaccessible!` versus a fully successful cross-org action); confirming that end-to-end effect would need a running instance or a Devin session with test execution.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
