### Title
Withdraw and other guarded flows authorize against the stale account-cached owner instead of the live position-NFT owner, letting a prior owner drain a transferred account — ([File: contracts/controller/src/positions/supply.rs](contracts/controller/src/positions/supply.rs))

### Summary
Analogous to the FeatherPanel bug (a permission record that is never re-validated against the current authority), the controller caches `account.owner` at NFT mint time in `create_account_with` and later authorizes sensitive flows with `require_owner_or_delegate(env, account_id, caller, &account.owner)`, while other paths (`renew_account`, `set_account_delegate`) correctly resolve the *live* NFT owner via `storage::account_owner`. After a position NFT transfer, the previous owner retains full withdrawal/borrow authority over the account and can send proceeds to an arbitrary `to` address.

### Finding Description
`create_account_with` stores `owner` inside the `Account` struct at mint time (`contracts/controller/src/account.rs:64-70`). `process_withdraw` then loads the account and authorizes with the cached field:

- `require_owner_or_delegate(env, account_id, caller, &account.owner)` — `contracts/controller/src/positions/supply.rs:150`
- The payout recipient is attacker-controlled: `let recipient = to.unwrap_or_else(|| caller.clone());` with only `require_external_recipient` as a constraint (supply.rs:152-154).

By contrast, `require_account_owner` (account.rs:143-148) resolves the *current* NFT owner via `storage::account_owner` and is used by `renew_account` and `set_account_delegate` — proving the codebase recognizes NFT ownership is the live authority and that the cached `account.owner` can diverge. The guarded flows (`withdraw`, `borrow`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `multiply`, `migrate_from_blend`) all funnel through `require_owner_or_delegate`/`is_owner_or_delegate` (account.rs:115-140), which compares `caller == owner` and looks up `get_delegates(env, account_id, owner)` — both keyed to the stale stored owner.

Nothing in `create_account`/`Account` or the NFT transfer path updates `account.owner` on transfer, so after `position-nft.transfer`, the original minter still satisfies `caller == account.owner`.

### Impact Explanation
Theft of user funds. Any account whose NFT was transferred (sold, moved between wallets, used as collateral in another contract) remains fully controllable by the previous owner. The prior owner calls `withdraw` with `to` set to their own address and removes all collateral (subject to HF checks, easily satisfied by also withdrawing only unencumbered assets or repaying trivial debt), or calls `borrow` to extract debt proceeds to themselves. The new NFT owner cannot stop it: they are not `account.owner` and hold no delegate entry under the stored owner. Positions traded on secondary markets are retroactively drained.

### Likelihood Explanation
High for any affected account: the attack requires no privileged role, no flash loan, and only a single `withdraw` call reachable by any unprivileged address that once owned the NFT. The likelihood that positions get transferred is inherent — the protocol ships a position-NFT contract whose `transfer`/`approve` are in the permitted reachability set, so transfers are an expected, supported operation. The stale-owner check silently remains valid forever after transfer.

### Recommendation
Authorize every account-mutating flow against the live NFT owner: replace `account.owner` in `require_owner_or_delegate`/`is_owner_or_delegate` with `storage::account_owner(env, account_id)` (or refresh `account.owner` from the NFT on every load in `storage::get_account`). Delegate entries should likewise be keyed by the current NFT owner, or cleared/invalidated on transfer. Add a regression test that transfers the NFT and asserts the previous owner can no longer withdraw and the new owner can.

### Proof of Concept
1. Alice calls `supply(caller=alice, account_id=0, spoke_id=1, [(asset, 1000e7)])` → `create_account_with` mints NFT `id=7` to Alice and stores `account.owner = alice`.
2. Alice transfers NFT `7` to Bob via the position-NFT `transfer` entrypoint.
3. Alice calls `withdraw(caller=alice, account_id=7, [(asset, 0)], to=Some(alice))`.
4. `process_withdraw` loads the account; `require_owner_or_delegate(env, 7, alice, &account.owner)` passes because `account.owner == alice` (stale), even though `storage::account_owner(env, 7)` now returns Bob.
5. `settle_withdraw` treats `0` as `WITHDRAW_ALL_SENTINEL`, the pool pays Alice, and `cleanup_account_if_empty` burns Bob's NFT — Bob's collateral is fully stolen by a signer who holds no position ownership.

Supporting code: stale owner cached at `contracts/controller/src/account.rs:64-70`; stale authorization at `contracts/controller/src/positions/supply.rs:149-150`; attacker-chosen recipient at `supply.rs:152`; correct live-owner check (inconsistency) at `account.rs:143-148`.
