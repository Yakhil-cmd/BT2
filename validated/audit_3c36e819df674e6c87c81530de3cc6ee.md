### Title
Webhook signature verified against payload's `repository.owner`/`organization.login` but handlers act on `repository.full_name` without re-checking it belongs to the verified organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
This is a plausible analog of the reported bug class ("a field acted on but never covered by the verification binding"), but I could not fully confirm it within the available context — the handler implementations (`push_handler.rb`, `handler.rb`, `lib/shipit.rb#github`) that would prove or disprove the exploit path failed to load in my final tool calls, so the chain from "verified owner" to "written stack/repository" is not conclusively demonstrated with line-level evidence.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/organization secret to use for HMAC verification based on `repository_owner`, which is read straight from the untrusted JSON payload: [1](#0-0) [2](#0-1) 

The verification only proves that the payload was signed by whichever organization's `webhook_secret` matches `repository_owner`. It does not prove that the `repository.full_name` field later consumed by the event handlers (`Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`) actually belongs to that same organization: [3](#0-2) 

If Shipit is configured with multiple GitHub organizations/apps (each with its own `webhook_secret` per `Shipit.github(organization:)`), an attacker who controls one onboarded organization (and therefore knows/can trigger deliveries signed with that organization's secret) could theoretically craft a payload where `repository.owner.login` matches their own org (so signature verification passes) while other repository-identifying fields used by downstream handlers point at a different organization's repository — analogous to the Ammplify bug where the signed/verified quantity (`repository_owner`) and the quantity actually acted upon (`repository.full_name` used to resolve the `Stack`/`Repository` record) are not the same value and are not cross-checked.

I was unable to verify this last step conclusively: the handler code (`app/models/shipit/webhooks/handlers/push_handler.rb`, `handler.rb`) that resolves the `Stack`/`Repository` from `params['repository']['full_name']` did not load in my final read attempts, so I cannot confirm whether it independently re-derives/validates the owner from the same trusted field used for signature verification, or whether `full_name`'s owner segment is always identical to `repository.owner.login` (which would close this gap).

### Impact Explanation
If the binding gap is real, it would allow an actor who legitimately controls one GitHub organization's webhook secret to forge webhook deliveries that get accepted as authentic for a *different* organization's repository/stack, potentially triggering unintended `GithubSyncJob`, status updates, membership changes, or merge-related side effects cross-repository. That would map to the "cross-repository writes" / unauthorized-action tier in scope.

### Likelihood Explanation
Low-to-uncertain. This requires: (a) a multi-organization Shipit deployment, (b) the attacker already being a legitimate, trusted operator of at least one onboarded organization (a fairly high bar, arguably itself a privileged position), and (c) confirmation that `repository.full_name`'s owner is not re-derived from/cross-checked against the already-verified `repository_owner`. Point (c) is the crux and I could not confirm it with code evidence in this session.

### Recommendation
If not already done, `WebhooksController` should ensure the organization used to resolve the target `Stack`/`Repository` for a given event is derived from the exact same trusted field that was used to select/verify the signature (i.e., re-validate that `repository.full_name`'s owner segment equals `repository_owner` before dispatching to handlers), rather than trusting the two independently-read fields to agree.

### Proof of Concept
Not constructed — I could not obtain the handler source (`push_handler.rb`, `handler.rb`) needed to demonstrate a concrete forged payload and confirm the resolution path, so no working PoC can be provided.
