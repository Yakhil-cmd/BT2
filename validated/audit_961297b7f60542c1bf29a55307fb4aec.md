### Title
Cross-tenant CCMenu disclosure: `CCMenuController#stack` bypasses `current_api_client.stack_id` scoping - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::CCMenuController` overrides both `#authenticate_api_client` and `#stack`, and its `#stack` implementation calls `Stack.from_param!(params[:stack_id])` directly instead of using the scoped `#stacks` helper defined in `BaseController`. Any token-authenticated `ApiClient` with the `read:stack` permission can therefore request `GET /api/stacks/:stack_id/cc.xml?token=<token>` for a stack it was never scoped to, and receive full CCTray build/deploy state.

### Finding Description
The intended binding is: `current_api_client.stack_id == params[:stack_id]` (or `current_api_client.stack_id` is nil, meaning "all stacks"), enforced by `BaseController#stacks`: [1](#0-0) 
`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `#stack` (singular) is defined in terms of `stacks.from_param!`.

`CCMenuController` re-defines `#stack` to bypass this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` on the unscoped `Stack` model, and only ever authenticates via `ApiClient.authenticate(params[:token])`, never invoking the base `#authenticate_api_client`'s scoping logic (`super` is only called if authentication fails).

Authorization is then checked only via `require_permission :read, :stack`, which calls `ApiClient#check_permissions!`: [3](#0-2) 
This method checks only the string permission (e.g., `"read:stack"`) against the client's `permissions` array — it performs no comparison against `stack_id` at all. The `stack_id` scoping is enforced *exclusively* inside `BaseController#stacks`, which `CCMenuController#stack` deliberately does not use.

Attacker flow: attacker obtains (or is given, e.g. by a third party integrating with CI dashboards) a valid `ApiClient` token scoped to `stack_id = A` with `read:stack` permission. Attacker sends `GET /api/stacks/B/cc.xml?token=<token_for_A>` where `B` is any other stack. `authenticate_api_client` succeeds (token is valid), `require_permission!` passes (`read:stack` is present), and `#stack` resolves stack `B` unscoped — the controller renders `B`'s deploy/build XML.

None of the existing guards catch this: `verify_signature`/webhook signature checks are irrelevant to this API endpoint; `ExplicitParameters` is not used here; `check_permissions!` only checks the permission string, not the stack id; and the `stacks` scope that would prevent this is simply never invoked by this controller.

### Impact Explanation
Any holder of a stack-scoped `ApiClient` token with `read:stack` permission can read CCTray XML (build/deploy status, last build label, activity, web URL) for **every** stack in the Shipit instance, not just the one their token is scoped to. This is a cross-tenant unauthorized read of stack state — matching the High severity category "unauthorized read of stack state, task streams or deploy output." It is fully repeatable against arbitrary stacks with a single GET request per stack and requires no additional privilege escalation.

### Likelihood Explanation
Preconditions: at least one `ApiClient` record scoped to a `stack_id` exists with `read:stack` permission, and the attacker possesses that client's token (a normal, low-privilege API client credential meant to authorize CI status polling for one stack only). Given that `ApiClient` tokens are commonly distributed to lower-trust integrations (e.g., embedding a CCTray/CI dashboard credential in a build tool), obtaining or being handed such a scoped token is a realistic occurrence, and exploitation is a single unauthenticated-cost HTTP GET with no other secret required.

### Recommendation
Change `CCMenuController#stack` to use the scoped `stacks` helper (i.e., `stacks.from_param!(params[:stack_id])`) instead of calling `Stack.from_param!` directly, and/or have `authenticate_api_client` call `super` unconditionally so `current_api_client`'s stack scoping is consistently applied, ensuring `check_permissions!`/`stacks` enforce `current_api_client.stack_id == stack.id` when the client is scoped.

### Proof of Concept
Add to `test/controllers/api/ccmenu_controller_test.rb` (existing test class, `ApiControllerTestCase`):

```ruby
test "a client scoped to a different stack can still read another stack's cc.xml (scope bypass)" do
  other_stack = shipit_stacks(:cyclimse) # any stack with different id than @stack
  @client.update!(stack_id: other_stack.id, permissions: ['read:stack'])

  get :show, params: { stack_id: @stack.to_param, token: @client.authentication_token }

  # Binding under test: current_api_client.stack_id (other_stack.id) should equal
  # the requested stack.id (@stack.id) for access to be granted; they differ here.
  assert_not_equal other_stack.id, @stack.id
  assert_response :ok            # demonstrates the bypass: expected 403/404, got 200
  assert_payload 'name', @stack.to_param
end
```
This demonstrates that a token scoped to `other_stack` is accepted for `@stack`, proving the `stacks` scoping in `BaseController` is bypassed by `CCMenuController#stack`.
