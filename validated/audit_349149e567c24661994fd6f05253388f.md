### Title
Webhook signature check is keyed on an unverified `repository.owner.login`/`organization.login` field, letting a payload for one GitHub organization forge CI status/events for a stack belonging to a different organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects **which** organization's HMAC secret to verify the delivery against by reading `repository.owner.login` (or `organization.login`) straight out of the still-unverified JSON body, then hands the *entire* raw body off to every handler unmodified. Handlers such as `StatusHandler` never re-check that the payload's `repository` matches the org that was used to authenticate it - they match commits globally by `sha`. If any organization configured on the instance has `webhook_secret` left blank/nil (documented as optional in `docs/setup.md`), the equality "organization whose secret authenticated this payload == organization the payload's actions are applied to" breaks down completely: an attacker with no credentials can pick that unauthenticated organization's name for `repository.owner.login`/`organization.login` to sail through `verify_signature`, while writing an entirely different repository's `full_name` and any commit `sha` into the body to affect another org's stacks.

### Finding Description
`verify_signature` computes the app/secret to check against from the payload itself, before that payload has been authenticated: [2](#0-1) [3](#0-2) 

`GitHubApp#verify_webhook_signature` explicitly treats a missing `webhook_secret` as "always verified": [4](#0-3) 

Multi-organization installations are an explicitly supported, documented configuration where each org has its own `webhook_secret`, and that secret is allowed to be nil per org: [5](#0-4) [6](#0-5) 

Once `verify_signature` passes (because it looked at `repository.owner.login` = the org with no secret), the full unauthenticated JSON is dispatched to handlers unmodified: [7](#0-6) 

`StatusHandler` (registered for the `status` GitHub event) then does a **global** commit lookup with no repository check at all: [8](#0-7) 

and `Commit#create_status_from_github!` unconditionally creates a `Status` row for the commit found, which drives `commit.state` (used by required-status/merge-queue/CI gating logic) and fires webhook events: [9](#0-8) [10](#0-9) 

**Binding broken:** *organization that authenticated the webhook* == *repository/stack whose commit/state the payload is allowed to mutate*. Before the attacker's request: only GitHub, holding the per-org `webhook_secret`, can produce a valid signature for events belonging to that org's repositories, and (for orgs with a secret configured) the signature covers the whole body including `repository.full_name`. After the attacker's request: for any org configured without a secret, `verify_signature` is satisfied purely by naming that org in `repository.owner.login`, while the `sha`/`repository.full_name` fields actually acted on by `StatusHandler`/`PushHandler`/etc. are never checked against that org - they can target a commit belonging to a totally different, securely-configured organization's stack.

### Impact Explanation
This is a High-severity unauthenticated write into another organization's `Shipit::Commit#state`/`Shipit::Status`, and by extension into the merge-queue/required-status gating that many `shipit.yml` configs use to gate deploy/merge decisions - i.e. escalation into stack state without any credential for the targeted organization, satisfying "unauthenticated read/write of stack state" under the High rubric. It is reachable purely through the public `/webhooks` endpoint with no session, `ApiClient` token, or GitHub credential for the victim org.

### Likelihood Explanation
Likelihood is conditioned on the deployment choosing the documented "no webhook secret" option for at least one configured organization (explicitly supported and shown as a valid config in `docs/setup.md` and the sample secrets files), which is a legitimate, unprivileged installation choice rather than a misconfiguration outside the engine's control. Given that, exploitation requires zero credentials - just knowledge of that org's name and a target stack's commit sha (both are typically public/discoverable via the Shipit UI or GitHub itself).

### Recommendation
Do not select the verification secret from an unauthenticated field of the same payload it will be used to authenticate. Concretely:
- Route webhook deliveries per-organization (e.g. distinct URLs/paths per configured GitHub App/org) so the secret used is fixed by routing, not by payload content, or
- After a successful signature check, re-derive and enforce that every handler's `repository.full_name` / org used for stack lookups belongs to the same organization identified during `verify_signature`, rejecting mismatches, and
- Stop treating an absent `webhook_secret` as an implicit "verification always passes" for that organization; require an explicit `insecure_webhooks: true`-style opt-in and warn loudly in docs about the cross-organization exposure it creates.

### Proof of Concept
1. Instance is configured with two GitHub orgs: `victim-org` (has a real `webhook_secret`) and `open-org` (per docs, `webhook_secret:` left blank) - both map to stacks tracked by the same Shipit instance.
2. Attacker (no credentials, no `ApiClient` token) sends `POST /webhooks` with header `X-Github-Event: status` and body:
```json
{
  "sha": "<sha of a commit belonging to a victim-org/some-repo stack>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "open-org" }, "full_name": "attacker/whatever" }
}
```
Any `X-Hub-Signature` value (or none) is accepted because `verify_signature` looks up `Shipit.github(organization: "open-org")`, whose `webhook_secret` is nil, so `verify_webhook_signature` short-circuits to `true` at `lib/shipit/github_app.rb:77`.
3. `WebhooksController#create` dispatches the parsed body to `StatusHandler`, which finds the `victim-org` commit purely by `sha` and creates a `success` `Status` on it - regardless of the fact the payload claimed to come from `open-org` and never named `victim-org/some-repo`.
4. If `victim-org`'s stack requires that `ci/required-check` context to merge/deploy, the merge queue/CI gating logic now considers that commit deployable, without any `victim-org` credential ever being presented.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
