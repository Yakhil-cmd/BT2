### Title
Attestor-list replacement in `asset_attestors` can permanently freeze balances of previously‑attested holders of a `spender_attested` asset - (File: storage.js, validation.js)

### Summary
For assets with `spender_attested: true`, `ocore` determines who is allowed to hold/spend the asset by looking only at the **most recently posted** attestor list for that asset (`storage.readAsset` → `addAttestorsIfNecessary`). The asset definer can post a new `asset_attestors` message at any time, instantly and completely replacing the trusted attestor list, with no check on whether addresses that already received/hold the asset were attested only by attestors that are now removed. This is the same root-cause pattern as the Sablier `CouncilMember` issue: a privileged party unilaterally reconfigures the trust/authorization source without accounting for balances/state that depend on the *old* configuration, permanently stranding funds that were valid under the old configuration.

### Finding Description
When an asset is created with `spender_attested: true`, every payment or issue involving that asset must include only addresses that are "attested" (`validatePaymentInputsAndOutputs` calls `storage.filterAttestedAddresses`, which restricts to `objAsset.arrAttestedAddresses`).

`storage.readAsset` computes `arrAttestorAddresses` by picking the single **latest** `asset_attestors` unit for the asset: [1](#0-0) 

`filterAttestedAddresses` then only counts an address as attested if some attestor **currently in that latest list** attested it (and the attestation is newer than any subsequent key-change): [2](#0-1) 

The definer can update the attestor list at will via the `asset_attestors` message, and `validateAttestorListUpdate` performs no continuity or overlap check with the previous list, and no check of who currently holds the asset: [3](#0-2) [4](#0-3) 

Composing this update from a wallet is exposed directly via `composeAssetAttestorsJoint`: [5](#0-4) 

The check enforced on both spends and issues of the asset requires all inputs/outputs to be in the (now-latest) attested set: [6](#0-5) [7](#0-6) 

Because only the latest list matters, replacing the attestor set (e.g. `[A]` → `[B]`) instantly invalidates every address that was attested solely by `A`, even though those addresses may already be holding a `spender_attested` balance issued/received while `A`'s attestation was valid. Exactly as in the `CouncilMember` report — where updating the stream/target/ID mid-flight orphaned funds tied to the old configuration — updating the attestor list here orphans balances tied to the old attestor set, with no mechanism (comparable to the recommended "Sablier hook" / "check-before-update" pattern) to settle or migrate the old holders before the change takes effect.

### Impact Explanation
Any address holding a `spender_attested` asset can have its balance become permanently unspendable the moment the definer posts a new `asset_attestors` unit that omits the attestor who originally attested it, since:
1. It can no longer be an input address for further payments of the asset (`objAsset.arrAttestedAddresses.indexOf(owner_address) === -1`).
2. It can no longer receive change/outputs of the asset for the same reason.
The frozen balance is only recoverable if one of the *new* attestors chooses to (re)attest the affected address — something entirely outside the holder's control and with no on-chain guarantee it will ever happen. This is a genuine fund-freezing condition triggered by a normal, permitted action of the asset issuer (an allowed unprivileged-relative actor per scope), with no compensating check comparable to the "verify depleted / settle before update" mitigation recommended in the original report.

### Likelihood Explanation
The action requires only a single, ordinary, valid unit from the asset's definer (posting `asset_attestors`), which is explicitly supported functionality (used, e.g., to rotate compromised attestors). No special privileges beyond being the asset definer (an expected, reachable role) are needed, and no cooperation from witnesses or governance is required. Any definer who rotates attestors — intentionally or due to routine key rotation — without first re-attesting or migrating existing holders will trigger this freeze; the scenario mirrors the report's observation that governance/multisig updates naturally happen "after some time," during which holders can accumulate balances under the soon-to-be-invalidated configuration.

### Recommendation
- When computing `arrAttestorAddresses`/`arrAttestedAddresses`, treat an address as attested if it was attested by **any** attestor that was valid at the time of attestation (i.e., accumulate attestor lists over time, or record which attestor list version validated a given attestation), rather than only the single latest list.
- Alternatively, require that `asset_attestors` updates be strictly additive (attestors can only be added, not silently dropped), or require an explicit, asset-level migration/grace mechanism before an attestor's authority is revoked, analogous to checking/settling the "streamed" state before allowing a state update in the original report.
- Add a guard in `validateAttestorListUpdate` to prevent removing attestors that are the sole attestors of addresses currently holding non-zero balances of the asset, or emit an event so wallets can proactively re-attest before old attestors are dropped.

### Proof of Concept
1. Definer `D` creates asset `X` with `spender_attested: true`, `attestors: [A]`.
2. Attestor `A` attests holder address `H`.
3. `H` receives/holds a balance of asset `X` (valid at this point since `A` is in the current attestor list).
4. `D` posts `asset_attestors` message replacing the list with `[B]` (a different attestor), which is accepted per `validateAttestorListUpdate` with no continuity check.
5. `storage.readAsset` now reports `arrAttestorAddresses = [B]`; `filterAttestedAddresses` no longer includes `H` because `H` was only attested by `A`.
6. Any further attempt by `H` to spend or receive change of asset `X` fails validation ("some output addresses are not attested" / "issuer is not attested"), permanently freezing `H`'s existing balance unless `B` chooses to attest `H`.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
