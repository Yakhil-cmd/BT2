### Title
Unbounded strategy routes execute attacker-controlled contracts under the caller's authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The strategy entrypoints accept opaque route payloads and forward them to the configured swap router without venue validation. A malicious payload can name an attacker-controlled venue that performs token transfers using authorizations attached to the victim's submitted call tree. The controller only bounds the input transfer and requires a positive measured output, so collateral can still be deposited after the unrelated wallet transfer. [1](#0-0) [2](#0-1) 

### Finding Description
`multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` accept `swap` as raw `Bytes` and pass it through `swap_tokens` unchanged. [3](#0-2)  `swap_tokens` authorizes only the exact input transfer to the configured router and invokes `router.execute_strategy`; it does not inspect or constrain the serialized route. [4](#0-3)  It then verifies only that the controller received positive `token_out`, not that no unrelated caller-authorized invocation occurred. [5](#0-4) 

The repository's route-authorization proof demonstrates the resulting behavior: a router payload can invoke a rogue hop contract, and that contract's transfer of the caller's wallet tokens is recorded beneath the caller's `swap_collateral` authorization. [6](#0-5) [7](#0-6) 

### Impact Explanation
A victim who submits a malicious route loses wallet tokens unrelated to the strategy input while still receiving enough output collateral for the transaction to pass the controller's settlement and risk checks. [8](#0-7)  This is theft of user funds because the damage is not bounded by `amount_in` or by the strategy's collateralized position. [5](#0-4) 

### Likelihood Explanation
The victim must submit a poisoned route and authorize the expanded invocation tree produced during simulation, so this is not remotely triggerable against an arbitrary account. However, routes are supplied as opaque bytes through reachable user entrypoints, route construction is commonly delegated to a client or route provider, and the controller places no protocol-level venue boundary on the executed code. [9](#0-8) [10](#0-9) 

### Recommendation
Enforce a venue allowlist for every contract invoked by a route, or replace opaque nested calls with fixed, protocol-approved venue adapters. Reject routes containing unrecognized pool, token, or callback addresses before invoking the router. Clients should additionally display and reject authorization trees containing invocations other than the expected controller call and exact input transfer. [10](#0-9) 

### Proof of Concept
1. The victim owns a funded wallet and an account with withdrawable `current` collateral.
2. An attacker provides a `swap` payload whose route includes attacker contract `RogueVenue`, plus `min_out` high enough to satisfy the swap.
3. The victim calls `Controller::swap_collateral(caller, account_id, current, amount, new, swap)`.
4. `swap_collateral` withdraws `amount`, calls `swap_tokens`, authorizes the router to receive only `amount`, and invokes `execute_strategy`. [11](#0-10) [10](#0-9) 
5. While executing the route, `RogueVenue` calls `Token::transfer(victim, attacker, victim_balance)`.
6. Simulation records that transfer as a child invocation under the victim's `swap_collateral` authorization; if the victim signs that tree, the transfer executes.
7. The router returns positive `new` collateral to the controller, so the measured-output check succeeds and the collateral is deposited. [5](#0-4) [12](#0-11) 
8. The victim's wallet balance is stolen even though the strategy's authorized input spend remained within `amount`. [13](#0-12)
