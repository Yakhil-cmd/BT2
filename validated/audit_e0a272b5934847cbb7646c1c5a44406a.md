### Title
Non-string `new_string`/`content` values bypass type coercion in `_extract_field`, causing unhandled exceptions that fail-open through `pretooluse.py`'s broad exception handler - ([File: plugins/hookify/core/rule_engine.py])

### Summary
`RuleEngine._extract_field` coerces field values to `str` only on its generic lookup path (`if field in tool_input: ... return str(value)`), but the tool-specific branches for `Write`/`Edit`/`MultiEdit` (fields `content`, `new_text`, `old_text`, `file_path`) return raw values from `tool_input` without any coercion. If those values are non-string (list/dict), `_check_condition`'s `starts_with`/`ends_with`/`regex_match` operators call `.startswith()`/`.endswith()`/`re.search()` on them, raising `AttributeError`/`TypeError`. This exception propagates out of `RuleEngine.evaluate_rules` and is caught by `pretooluse.py`'s outer `except Exception`, which prints only a `systemMessage` (no `permissionDecision: deny`) and unconditionally `sys.exit(0)`, silently allowing the tool call and defeating any matching `block` rule for that invocation.

### Finding Description
`_extract_field` (plugins/hookify/core/rule_engine.py:182-254) documents that it returns "Field value as string, or None if not found," and the generic branch enforces this via `str(value)` coercion: [1](#0-0) 

However, for `Write`/`Edit`, the aliased fields `new_text`/`new_string`, `old_text`/`old_string`, and `content` are only reachable through the tool-specific `elif tool_name in ['Write', 'Edit']` branch when the literal key isn't already present under that exact name in `tool_input` (e.g. a condition on `new_text` never matches the generic `if field in tool_input` check, since the actual key is `new_string`), and this branch returns the raw value with no type check: [2](#0-1) 

The same applies to `MultiEdit`'s `edits` aggregation, which calls `e.get('new_string', '')` and joins values with `' '.join(...)` without validating they are strings: [3](#0-2) 

`_check_condition` then applies string-only operators directly on `field_value` without any type check: [4](#0-3) 

If `field_value` is a list/dict, `starts_with`/`ends_with` raise `AttributeError`, and `_regex_match`'s `regex.search(text)` raises `TypeError` (only `re.error` is caught inside `_regex_match`, not `TypeError`): [5](#0-4) 

This exception propagates up through `_rule_matches` and `evaluate_rules` into `pretooluse.py`'s `main()`, which catches all exceptions broadly, emits only a warning `systemMessage` with no `hookSpecificOutput`/`permissionDecision: deny`, and always exits 0: [6](#0-5) 

Because `evaluate_rules` never got to return its `"permissionDecision": "deny"` payload for the matching blocking rule (defined at plugins/hookify/core/rule_engine.py:72-79), the tool call proceeds unblocked, i.e., a rule-evaluation crash silently defeats a configured `block` rule.

### Impact Explanation
This causes a fail-open bypass of user-configured `block` rules (e.g., a rule blocking edits that introduce a secret pattern, or a dangerous file write) for the specific tool call whose `tool_input` contains a non-string value in one of the affected fields. The bypassed operation (Write/Edit/MultiEdit) still executes as originally requested — the vulnerability's impact is defeating the security guardrail (DENY_MEANS_DENY invariant), not gaining new privileges beyond what the underlying tool call itself would do. This matches a "trust-boundary/enforcement bypass" class finding rather than direct compromise, and its severity is bounded by whatever the un-blocked tool call would otherwise have done (e.g., writing a file hookify was configured to block).

### Likelihood Explanation
The precondition — a non-string value landing in `tool_input['new_string']`, `tool_input['content']`, `tool_input['old_string']`, or a non-string `edits[i]['new_string']` for the native `Write`/`Edit`/`MultiEdit` tools — depends on whether Claude Code's own tool-calling/schema-validation layer (outside this repository) already enforces these parameters as strings before invoking the `PreToolUse` hook. This repository does not contain that upstream validation code, so it cannot be confirmed here whether malformed/non-string arguments for these specific built-in tools can actually reach the hook in a real session (e.g., via a compromised/malicious MCP server response influencing the model's constructed tool call, or a buggy orchestration layer). Within the hookify plugin itself, however, the defect is fully reproducible and deterministic: any caller that invokes `RuleEngine.evaluate_rules` with such a `tool_input` will trigger the crash-to-fail-open path shown above.

### Recommendation
Coerce all extracted field values to `str` uniformly in `_extract_field`, including in the `Write`/`Edit`/`MultiEdit` tool-specific branches, mirroring the coercion already done in the generic branch (plugins/hookify/core/rule_engine.py:198-200). Additionally, harden `_check_condition`/`_regex_match` to defensively handle non-string `field_value` (e.g., wrap operator application in a try/except, or explicitly coerce/validate before use), and change `pretooluse.py`'s exception handler so that an internal rule-evaluation error does not silently produce an allow-equivalent result — e.g., surface the error distinctly so operators can detect fail-open events, or fail closed for `block`-only rule sets if configurable.

### Proof of Concept

```python
from hookify.core.config_loader import Condition, Rule
from hookify.core.rule_engine import RuleEngine

rule = Rule(
    name="block-secret-in-edit",
    enabled=True,
    event="file",
    action="block",
    conditions=[Condition(field="new_text", operator="starts_with", pattern="SECRET")],
    message="blocked",
)

engine = RuleEngine()
input_data = {
    "hook_event_name": "PreToolUse",
    "tool_name": "Edit",
    "tool_input": {
        "file_path": "/tmp/f.txt",
        "old_string": "x",
        "new_string": ["SECRET", "leaked"],  # attacker/malformed-shaped non-string value
    },
}

# Expected (buggy) behavior: raises AttributeError inside evaluate_rules
# ('list' object has no attribute 'startswith'), instead of returning
# {"hookSpecificOutput": {..., "permissionDecision": "deny"}, ...}
import pytest
with pytest.raises(AttributeError):
    engine.evaluate_rules([rule], input_data)
```

def main():
    """Main entry point for PreToolUse hook."""
    try:
        # Read input from stdin
        input_data = json.load(sys.stdin)

        # Determine event type for filtering
        # For PreToolUse, we use tool_name to determine "bash" vs "file" event
        tool_name = input_data.get('tool_name', '')

        event = None
        if tool_name == 'Bash':
            event = 'bash'
        elif tool_name in ['Edit', 'Write', 'MultiEdit']:
            event = 'file'

        # Load rules
        rules = load_rules(event=event)

        # Evaluate rules
        engine = RuleEngine()
        result = engine.evaluate_rules(rules, input_data)

        # Always output JSON (even if empty)
        print(json.dumps(result), file=sys.stdout)

    except Exception as e:
        # On any error, allow the operation and log
        error_output = {
            "systemMessage": f"Hookify error: {str(e)}"
        }
        print(json.dumps(error_output), file=sys.stdout)

    finally:
        # ALWAYS exit 0 - never block operations due to hook errors
        sys.exit(0)
