### Title
Reentrancy on hardcoded external LST token calls in vault `deposit`/`redeem` allows share-price manipulation that dilutes other depositors - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and `v0-vault-usdh.clar` hardcode the address of an external, third-party liquid-staking/stablecoin token contract (`ststx-token`, `ststxbtc-token-v2`, `usdh-token-v1`) and invoke its `transfer` function directly from `deposit`/`redeem`, exactly like the Lybra vaults that hardcoded Lido/wBETH/rETH addresses in the referenced report. As in that report, these calls are made to external code the vault cannot fully guarantee the behavior of, and the vault updates its shared accounting state (`assets` data-var, `zft` total-supply) only *after* the external call returns, with no reentrancy guard on the deposit/redeem path itself (only a flashloan-specific `in-flashloan` guard exists).

### Finding Description
In `v0-vault-ststx.clar`, `deposit` computes `inkind` (shares to mint) from `current-assets`/`total-assets-preview`/`total-supply` captured *before* the external call, then makes an external call to the hardcoded third-party token contract via `receive-underlying`, and only afterwards mints shares and commits `(var-set assets (+ current-assets amount))`: [1](#0-0) 

The external call target is a hardcoded, non-registry-checked mainnet principal exactly analogous to the Lido/RocketPool/wBETH pattern flagged in the report: [2](#0-1) 

`receive-underlying`/`send-underlying` perform the raw `contract-call?` into this hardcoded external contract: [3](#0-2) 

The only reentrancy guard present in `deposit` is scoped to flashloans (`in-flashloan`), not to deposit/redeem itself: [4](#0-3) 

`assets` and `zft`'s total supply are **shared state consumed by every depositor** through `convert-to-shares-preview`/`convert-to-assets-preview`, which determine the exchange rate between underlying and zTokens for the whole vault: [5](#0-4) 

Because Clarity's `contract-call?` is a genuine synchronous cross-contract call (unlike an EOA-only assumption), if the external, hardcoded token contract at any point in its call graph calls back into the vault's public `deposit`/`redeem` before the vault has committed `(var-set assets ...)`, the nested call will read the stale `current-assets`/`total-assets-preview` and mint shares at an exchange rate that does not reflect the first (in-flight) deposit. This lets an attacker mint disproportionately many shares for the same amount of pledged underlying, diluting the claim of every other zstSTX/zstSTXbtc/zUSDH holder — a case of one caller's action harming all other suppliers via the shared vault accounting, not merely self-harm to the caller.

### Impact Explanation
If exploited, the attack dilutes the shared `assets`↔`zft` exchange rate used by `convert-to-assets-preview`/`convert-to-shares-preview` for **all** vault depositors, letting the attacker redeem more underlying than they deposited at other users' expense. This is a direct theft of user funds at rest (Critical) affecting the socialized pool of the vault, matching the impact class in the rules ("a socialization charged to all suppliers").

### Likelihood Explanation
Likelihood is speculative and bounded by the same trust assumption noted in the source report: the hardcoded token contracts (`ststx-token`, `ststxbtc-token-v2`, `usdh-token-v1`) are real, already-deployed third-party mainnet contracts, and standard SIP-010 `transfer` implementations do not call back into callers. Exploitation requires the external token contract to contain (now or after any future upgrade by its own maintainers) logic that reenters the caller during `transfer` — the same "cannot be fully guaranteed" trust gap flagged in the report for Lido/RocketPool/wBETH. No reentrancy guard specific to `deposit`/`redeem` exists to close this gap even though the flashloan path already demonstrates the team is aware of and mitigates reentrancy elsewhere (`in-flashloan`).

### Recommendation
Add a dedicated reentrancy guard (a data-var flag, e.g. `in-op`) around `deposit`/`redeem`/`transfer` in `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and `v0-vault-usdh.clar`, set before the external `receive-underlying`/`send-underlying` calls and cleared after the state (`assets`, `zft` supply) has been committed, mirroring the existing `in-flashloan` pattern. Alternatively, move the `(var-set assets ...)` / `ft-mint?` accounting to occur strictly before the external call using a checks-effects-interactions ordering with a balance-delta verification, so any reentrant call observes already-updated, consistent shared state.

### Proof of Concept
Not independently reproducible from static review alone: exploitation depends on the internal behavior of the externally-deployed, hardcoded token contracts (`'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.ststx-token`, `ststxbtc-token-v2`, `usdh-token-v1`), whose full source was not available in this index. Conceptually:
1. Attacker calls `deposit(amount, min-out, attacker)` on `v0-vault-ststx`.
2. `current-assets`/`inkind` are computed from vault state before the external transfer.
3. During the `contract-call?` into the hardcoded external token's `transfer`, if that contract's logic re-enters the vault's `deposit` (e.g., via a callback, hook, or trait it itself calls), the nested `deposit` reads the same stale `current-assets`, minting a second batch of shares at the pre-update exchange rate.
4. Both calls succeed; `assets` is only incremented once per completed `var-set`, but total minted `zft` shares now exceed what the underlying deposited justifies, diluting all existing zstSTX holders' redeemable share of `assets`. [1](#0-0)
