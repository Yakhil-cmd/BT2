### Title
Cross-organization webhook signature confusion lets an attacker act on repositories in an organization they don't control - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In the multi-organization GitHub App configuration mode, `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on `repository_owner`, but that field is derived from the *same* attacker-controlled JSON payload that later determines the repository actually written to. Because the value used for signature-app-selection (`repository.owner.login` / `organization.login`) and the value used to select the target repository (`repository.full_name`) are read independently from the same untrusted body, and each organization is configured with its own `webhook_secret`, an attacker who legitimately controls a repository/webhook secret for **Organization A** can forge a payload whose `repository.owner.login` says `"orgA"` (so the signature validates against orgA's secret) while `repository.full_name` says `"orgB/target-repo"`, causing the handler to look up and mutate a stack belonging to `orgB` despite `orgB`'s webhook secret never being used to authenticate the request.

Because `repository.owner.login` (used to pick the verifying secret) and `repository.full_name` (used to pick the acted-upon repository) are two independently-controlled strings inside the same unsigned-until-verified JSON body, nothing forces them to refer to the same organization. The binding that should hold — "organization whose secret verified the request" == "organization whose repository is mutated" — is never enforced.

### Impact Explanation
An attacker who is a legitimate contributor/webhook holder for one configured GitHub organization (Organization A) in a multi-tenant Shipit deployment can forge webhook deliveries that pass signature verification under Organization A's secret, yet cause writes (stack syncs, review-stack creation/archival, provisioning-queue changes) against repositories belonging to Organization B, whose secret was never used. This crosses a repository/organization trust boundary and results in unauthorized state changes (deploy-relevant syncs, review-stack provisioning/deprovisioning) on repositories the attacker has no legitimate access to — a cross-repository write.

### Likelihood Explanation
Requires the deployment to run in multi-organization mode (`Shipit.github_organizations` with per-org `webhook_secret`s) and requires the attacker to hold a valid webhook secret/delivery capability for at least one configured organization (e.g., by owning a repo hooked into Shipit under Org A). Given that constraint, no other secrets, GitHub App keys, or session access are needed — only crafting the JSON body and computing the HMAC with the known Org A secret. This is realistic for any Shipit instance that shares one deployment across multiple organizations with separate GitHub Apps.

### Recommendation
After `verify_signature` selects the GitHub App/organization based on `repository.owner.login` (or `organization.login`), the same value must be cross-checked against the field the handlers actually use to resolve the target repository (`repository.full_name`'s owner segment) before dispatching to handlers — reject the request if they disagree. Alternatively, derive the authorized organization once in the controller and pass it down explicitly to `Handler#repository_name`/`stacks` so handlers cannot resolve a repository outside the organization whose secret verified the payload.

### Proof of Concept
1. Deploy Shipit configured with two organizations, `orga` and `orgb`, each with its own `webhook_secret` (per `lib/shipit.rb#github_app_config`).
2. Attacker controls a repo hooked under `orga` and knows `orga`'s `webhook_secret` (legitimately configured for their own repo's webhook delivery).
3. Attacker crafts a `push` event payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<malicious_sha>",
  "repository": { "owner": { "login": "orga" }, "full_name": "orgb/target-repo" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(orga_webhook_secret, body)>` and POSTs to `/github/webhooks`.
5. `verify_signature` calls `Shipit.github(organization: "orga")` and validates successfully against `orga`'s secret.
6. `PushHandler#process` calls `stacks` → `Handler#repository_name` returns `"orgb/target-repo"` → `Repository.from_github_repo_name("orgb/target-repo")` resolves the `orgb`-owned repository and its stacks, which are then synced (`stack.sync_github(expected_head_sha: params.after)`) — even though `orgb`'s webhook secret never verified this request.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
