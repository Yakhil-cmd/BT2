### Title
Webhook Signature Verified Against `repository.owner.login` But Handlers Act On Unrelated `repository.full_name` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret used to authenticate an inbound webhook using an **attacker-supplied, pre-verification field** (`repository.owner.login`), while every `Webhooks::Handlers::Handler` subclass subsequently resolves the repository/stack to mutate using a **separate, independently-controlled field** (`repository.full_name`). Nothing ties these two values together, so a payload can be legitimately signed for organization A while acting on organization B's tracked repository.

### Finding Description
`verify_signature` derives the signing organization from the raw JSON body before the signature has been checked, and uses it only to pick which secret to verify against: [1](#0-0) [2](#0-1) 

If the signature computed with `Shipit.github(organization: repository_owner)`'s secret matches, the whole raw payload is accepted and dispatched to handlers via `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` in `WebhooksController#create`.

Every handler, however, determines which `Repository`/`Stack` records to touch from a *different* JSON field, `repository.full_name`, not `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` performs a case-insensitive lookup purely on `owner/name` parsed out of that field, with no cross-check against the organization whose secret validated the signature: [4](#0-3) 

For a `push` event, this directly drives `GithubSyncJob` enqueue via `stack.sync_github`: [5](#0-4) 

The binding that should hold is:
`organization whose webhook secret authenticated the request == organization that owns the repository being written to`

Because `repository_owner` (used to pick the verifying secret) and `repository.full_name` (used to pick the mutated `Repository`) are two independent, attacker-controlled JSON fields with no equality check between them, this binding is not enforced. Shipit explicitly supports multiple GitHub organizations/apps with distinct webhook secrets (confirmed by the `Shipit.github(organization:)` selector and the multi-app test fixture `test/dummy/config/secrets_double_github_app.yml`), so this is a real, supported multi-tenant configuration, not a hypothetical single-org deployment.

### Impact Explanation
An attacker who administers *any* GitHub organization/repository that is legitimately onboarded to a multi-tenant Shipit instance (and therefore knows/controls that org's webhook secret, as the org owner who configured the integration) can forge a webhook body where:
- `repository.owner.login` = their own org (so `verify_signature` validates the signature with their own known secret), and
- `repository.full_name` = a victim org/repository also tracked by the same Shipit instance.

This causes Shipit to process the forged event as if it originated from the victim repository — e.g. triggering `GithubSyncJob` with an attacker-chosen `after` SHA for the victim's stack, or driving `PullRequest`/`Stack` creation and mutation handlers against the victim repository. This is a cross-repository write achieved without ever having write access, admin access, or a valid webhook secret for the victim repository — it only requires legitimate admin access to *some other* org onboarded to the same Shipit instance. This can lead to unauthorized syncing/deployment of arbitrary commits into a victim stack, satisfying the "cross-repository writes" / "unauthorized deploy" Critical impact bar.

### Likelihood Explanation
Requires: (1) a multi-organization/multi-app Shipit deployment (a supported, documented configuration), and (2) attacker admin/owner access to any one of the onboarded organizations (to know that org's webhook secret) — no access to the victim organization or repository is needed. This is a realistic, low-privilege-crossing scenario for any multi-tenant Shipit install serving more than one organization.

### Recommendation
After verifying the signature, re-derive the organization strictly from the field(s) actually used by handlers (`repository.full_name`'s owner segment, or `organization.login`) and reject the request (422) if it does not match the organization whose secret validated the signature. Alternatively, verify the signature using the secret associated with the resolved `Repository`/`Stack` rather than the raw, unverified `repository.owner.login`.

### Proof of Concept
1. Shipit instance configured with two orgs, `AttackerOrg` and `VictimOrg` (each with distinct webhook secrets via `Shipit.github`), both with repositories tracked as Shipit stacks.
2. Attacker (owner of `AttackerOrg`, knows `AttackerOrg`'s webhook secret) crafts a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "AttackerOrg" },
    "full_name": "VictimOrg/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature` using `AttackerOrg`'s known secret over this exact body and POSTs it to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "AttackerOrg")` and the signature validates successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("VictimOrg/victim-repo")` (from `repository.full_name`) and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")`, causing `GithubSyncJob` to run against `VictimOrg`'s stack despite the request being authenticated only for `AttackerOrg`.
