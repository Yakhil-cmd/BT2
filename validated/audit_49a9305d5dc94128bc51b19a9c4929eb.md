### Title
Unverified recapitalize lets any caller inflate the cash book and drain pool custody via the refund - (File: contracts/pool/src/ops/recapitalize.rs)

### Summary
The pool's `recapitalize` entrypoint credits its accounting cash from the caller-supplied `amount` and refunds the portion above the backing shortfall to `payer` — without measuring that any tokens were actually transferred in. The controller wrapper (`markets.rs::recapitalize`) prefunds the pool and passes the measured receipt, but the pool contract trusts whatever `amount` it is given. An unprivileged address can call the pool directly, credit cash it never paid, and have the "unused" amount refunded from real supplier custody. The codebase's own test, `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` in `contracts/pool/tests/flows.rs`, demonstrates exactly this: custody is drained to `payer`, the book still claims the cash, and a subsequent `withdraw` passes the pool's liquidity guard (`require_reserves` reads the book) only to fail inside the SAC transfer.

### Finding Description
The CVE analog is an unchecked receipt: like libmicrodns using an unchecked parse result, the pool consumes the caller-declared `amount` as if the tokens had arrived, instead of measuring the balance delta the way every other inbound path does (`transfer_amount_measured` in `common/src/token.rs` exists precisely for this). The controller does the right thing in `contracts/controller/src/markets.rs:154-163` — it transfers first and passes `received` — but the pool entrypoint performs no auth check tying it to the controller and no custody measurement, so the safeguard is bypassable by calling the pool contract directly:

```rust
// contracts/controller/src/markets.rs:154
let received = payments::transfer_amount_measured(env, &hub_asset.asset, &payer, &pool_addr, amount, ...);
pool_recapitalize_call(env, &pool_addr, &hub_asset, &payer, received).actual_amount
```

Because the pool never verifies receipt, `recapitalize(hub_asset, attacker, custody)` both overstates `cash` on the book and sends real tokens to the attacker as a "refund."

### Impact Explanation
Direct theft of user funds: the attacker pulls existing supplier custody out of the pool as a refund for funds never deposited. Residual impact is protocol insolvency — the cash book overstates custody, so `withdraw` clears `require_reserves` and then reverts inside the token transfer, permanently freezing suppliers' exits until the deficit is covered.

### Likelihood Explanation
A single unprivileged transaction against the pool contract: `recapitalize(hub_asset, attacker_address, pool_custody_balance)`. No timing, oracle, or governance preconditions — only that the pool holds tokens, which is the normal state.

### Recommendation
Inside `contracts/pool/src/ops/recapitalize.rs`, measure the pool's balance delta for `hub_asset.asset` across the operation (or require the call to come from the controller) and credit/refund only the measured receipt. Alternatively, pull the tokens in the pool itself via `transfer_amount_measured` from `payer` rather than trusting the declared amount.

### Proof of Concept
The pattern is already exercised by `contracts/pool/tests/flows.rs:3408` (`test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody`): after a 10_000_000_000 deposit, `pool.recapitalize(hub, payer, custody)` sets `token.balance(pool)` to 0 with `payer` receiving the funds, while `state_snapshot().cash >= deposit` — and the subsequent supplier `withdraw` fails only inside the SAC transfer (contract error 10), proving the book/custody divergence. A malicious variant simply substitutes an attacker-generated `payer` address.

Caveat: I did not have iterations left to read `contracts/pool/src/ops/recapitalize.rs` directly to confirm the absence of a controller-only auth check; the finding rests on the repo's own test, which invokes `recapitalize` through the pool client without any controller setup and succeeds.
