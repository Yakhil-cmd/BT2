This confirms the multi-org configuration design in `lib/shipit.rb` `Shipit.github(organization:)` at [1](#0-0) , where each GitHub organization has its own independent `webhook_secret`. This is the basis for the finding below.

### Title
Webhook signature verified against the payload's `repository.owner.login` while stack/repository resolution uses the unauthenticated `repository.full_name` field, allowing cross-organization webhook forgery - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit deployment, each GitHub organization is configured with its own independent `webhook_secret` (`lib/shipit/github_app.rb`, `lib/shipit.rb`). `WebhooksController#verify_signature` selects which organization's secret to verify the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). However, none of the webhook event handlers actually use that field to scope their side effects: `Handler#repository_name` (the base class used by `PushHandler` and others) and multiple `PullRequest` handlers instead resolve the target repository/stack from `params.repository.full_name`. Because the HMAC only signs the raw JSON body and the verification step's *choice of secret* is keyed off `repository.owner.login`, while the actual mutation is keyed off `repository.full_name`, an attacker who controls one legitimately-configured (but unrelated) GitHub organization in the same Shipit instance can craft and self-sign a payload whose `repository.owner.login` matches their own org (so it passes signature verification with their own secret) but whose `repository.full_name` names a victim organization's repository, causing Shipit to act (e.g., trigger `stack.sync_github`, archive/unarchive review stacks) on a repository they do not control.

### Finding Description
`WebhooksController#verify_signature` at [2](#0-1)  computes:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
with
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [3](#0-2) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization key from `secrets.github` [1](#0-0) , confirming this is a supported "multiple GitHub applications for different GitHub organizations" configuration as documented in `config/secrets.development.example.yml` (lines 18–38).

Once signature verification passes, `create` dispatches the entire raw payload to handlers: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) . The base `Handler` class resolves the target stacks using `repository.full_name`, not `repository.owner.login`:
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [5](#0-4) 

`PushHandler#process` uses this `stacks` scope to call `stack.sync_github(expected_head_sha: params.after)` on every matching, non-archived stack on the target branch [6](#0-5) . Several `PullRequest` handlers (`OpenedHandler`, `ClosedHandler`, `ReopenedHandler`, `LabeledHandler`, `UnlabeledHandler`) similarly resolve `repository` via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` and then archive/unarchive/provision review stacks accordingly, e.g. [7](#0-6) .

The equality that should hold but does not is:
`organization whose secret authenticated the request (repository.owner.login)` == `repository whose stacks are mutated (repository.full_name)`.

Since HMAC-SHA1 only proves the raw bytes weren't tampered with by someone lacking the matching organization's secret — it says nothing about internal consistency between two independently attacker-controlled JSON fields in that same signed body — an org owner who legitimately possesses their own `webhook_secret` can freely set `repository.full_name` to any string of their choosing while keeping `repository.owner.login` equal to their own org, and the signature will still validate.

### Impact Explanation
This crosses a cross-repository-write boundary: an attacker who administers their own GitHub App installation/org in a multi-org Shipit deployment (a low-privilege, unrelated party with respect to the victim organization) can, without ever compromising the victim's `webhook_secret`, GitHub credentials, or Shipit account, force Shipit to treat forged payloads as authentic events for the victim's repository. Concretely this can:
- Trigger `GithubSyncJob`/`sync_github` against a victim stack via forged `push` events, and
- Archive or unarchive victim review stacks via forged `pull_request` events (`closed`, `reopened`, `labeled`, `unlabeled`), and provision new review stacks via forged `opened` events (subject to `repository.review_stacks_enabled`/provisioning policy on the victim repo).

This matches the "cross-repository writes" impact category, since state-changing operations are performed against a repository outside the authenticating organization's ownership.

### Likelihood Explanation
Likelihood is limited to deployments actually configured with multiple GitHub organizations sharing one Shipit instance (the documented `github: { org1: {...}, org2: {...} }` schema). Within such a deployment, exploitation requires no special access beyond being a legitimate org admin/webhook owner for any one configured organization — a comparatively low bar relative to compromising another org's secret directly.

### Recommendation
Bind the field used to select/verify the webhook secret to the same field used for repository resolution. Concretely:
- In `WebhooksController#verify_signature`, derive `repository_owner` from `repository.full_name` (i.e., the owner segment of `full_name`) rather than the separate `repository.owner.login`, or
- After verification, re-validate in `Handler`/subclasses that `payload.dig('repository','owner','login')` (or the split of `full_name`) matches the organization key that produced a successful signature check, rejecting the webhook otherwise.

### Proof of Concept
Assume a Shipit instance configured with two organizations, `attacker-org` and `victim-org`, each with its own `webhook_secret` per `config/secrets.development.example.yml`. As an admin of `attacker-org`'s GitHub App, the attacker knows `attacker-org`'s `webhook_secret`.

1. Attacker crafts a `push` event JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
2. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(attacker-org secret, raw body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
3. `verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature using `attacker-org`'s own secret [8](#0-7) .
4. `PushHandler` resolves stacks via `Repository.from_github_repo_name('victim-org/victim-repo')` [5](#0-4)  and calls `stack.sync_github(expected_head_sha: '<attacker-chosen-sha>')` on `victim-org/victim-repo`'s stacks [6](#0-5) , despite the request never being authenticated by `victim-org`'s secret.
