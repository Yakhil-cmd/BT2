### Title
Webhook signature verification authenticates the wrong organization, allowing cross-tenant repository writes - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
In a multi-organization Shipit deployment (multiple GitHub Apps configured under `github:` in secrets, e.g. `OrgOne`/`OrgTwo` as shown in `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects which organization's `webhook_secret` to use for HMAC verification based on an attacker-influenced field of the very payload being verified (`repository.owner.login`), while the handlers that actually mutate state key off a *different* field of the same payload (`repository.full_name`). Because both fields live inside the same HTTP body that the attacker fully controls when crafting the signature, an operator/admin of one legitimately-onboarded (but less-trusted) organization can forge a webhook whose signature is valid for their own org while its `repository.full_name` points at a repository belonging to a different, victim organization onboarded to the same Shipit instance.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/secret to use for verification purely from the JSON body: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up the per-org config (and its `webhook_secret`) using `repository.owner.login` taken directly from the untrusted request body, not from any value bound by the signature itself. Signature verification then just checks the HMAC of the *entire* raw body against that org's secret: [3](#0-2) 

Meanwhile, every webhook `Handler` resolves the target `Repository`/`Stack` from a *different* field of the same body — `repository.full_name` — via `Repository.from_github_repo_name`: [4](#0-3) [5](#0-4) 

The security invariant the system relies on is: *"the organization whose secret validated this payload" == "the organization that owns the repository being acted upon."* That equality is never enforced. An attacker who legitimately controls (and knows the `webhook_secret` for) `OrgTwo` in a multi-org Shipit instance can build a JSON body with `repository.owner.login = "OrgTwo"` and `repository.owner.login`-derived HMAC valid for OrgTwo, but with `repository.full_name = "OrgOne/victim-repo"`. Since the attacker computes the whole HMAC themselves (they know OrgTwo's secret), the signature will pass `verify_webhook_signature`, and the handler will then act on `OrgOne/victim-repo`, a repository they do not administer.

This is the same class of bug as the reported analog: a value used to authenticate ("who signed this") differs from the value that is trusted for a privileged action ("what/whom the action targets"), and the code never checks that they are the same entity.

### Impact Explanation
Depending on webhook event/handler this enables:
- `push` (`PushHandler`) — trigger `stack.sync_github(expected_head_sha: ...)` against another organization's tracked branch, forcing the target stack to sync to an attacker-chosen SHA reference on the victim repo's branch, which can influence deploy candidate selection. [6](#0-5) 
- `status` (`StatusHandler`) — forge CI status on the victim's commits, which stacks may treat as a deployability gate (`commit.deployable?` in `build_deploy`), potentially enabling an "unauthorized deploy" of a commit that never actually passed CI on the real org. [7](#0-6) [8](#0-7) 
- `check_suite` — schedule check-run refreshes for the victim's commit. [9](#0-8) 

This crosses the "cross-repository writes" / "unauthorized deploy" impact bar defined in scope, because a party with no legitimate relationship to the victim org's repository can cause writes and influence deploy gating on it. This satisfies the required binding: "an organization that authenticated versus the repository that is written."

### Likelihood Explanation
Exploitability requires the Shipit instance to be configured for multiple GitHub organizations (the documented multi-org secrets format used in `test/dummy/config/secrets_double_github_app.yml`), and requires the attacker to be a legitimate operator of one of those onboarded (but lower-trust) organizations. It does not require an `ApiClient` token, a Shipit session, or `GITHUB_TOKEN`; the webhook endpoint is unauthenticated apart from the HMAC check. In any Shipit deployment shared across independent organizations/tenants, this is directly reachable via a normal HTTP POST to `/webhooks` (no GitHub involvement needed once the attacker knows their own org's `webhook_secret`, which they set up themselves).

### Recommendation
- Bind the value used to select the verification secret to the value used for the actual write target: verify the signature using the same `repository.full_name` (or an org derived consistently from it), not an independently-sourced `repository.owner.login`.
- Alternatively, once verification succeeds for organization `O`, assert `Repository.from_github_repo_name(payload full_name).owner == O` before dispatching to any handler, and reject/`head(422)` on mismatch.
- Consider using GitHub's `X-Github-Delivery`/App installation ID (bound to the installation, not the payload body) to select the org config instead of trusting a payload field.

### Proof of Concept
1. Configure Shipit with two orgs, `OrgOne` (victim) and `OrgTwo` (attacker-controlled), each with distinct `webhook_secret`s, as in `test/dummy/config/secrets_double_github_app.yml`.
2. As the `OrgTwo` administrator, craft a JSON body:
```json
{
  "ref": "refs/heads/main",
  "after": "deadbeef",
  "repository": {
    "owner": {"login": "OrgTwo"},
    "full_name": "OrgOne/victim-repo"
  }
}
```
3. Compute `sha1=HMAC(OrgTwo_webhook_secret, body)` and POST to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=...`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "OrgTwo")`, verifies successfully against `OrgTwo`'s own secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgone/victim-repo")` and calls `stack.sync_github` on the victim's stack — despite the request never having been signed by `OrgOne`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
