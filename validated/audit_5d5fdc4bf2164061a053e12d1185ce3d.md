### Title
Arbitrary swap-route execution can piggyback user authorization to drain unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Controller strategy entrypoints accept opaque router payload bytes and execute the configured router without constraining which contracts the route may invoke. [1](#0-0)  A malicious route can therefore place attacker-controlled code inside a victim-authorized `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` transaction. [2](#0-1)  If that code requests a token transfer from the victim, transaction simulation can add the transfer as a child of the authorization tree that the victim signs.

### Finding Description

`process_swap_collateral` requires the caller’s authorization and verifies that the caller owns or delegates the target account, but it forwards the user-supplied `swap` payload into the strategy withdrawal path without validating its embedded venues or contract addresses. [2](#0-1) 

`swap_tokens` only verifies that the payload is nonempty, authorizes the controller’s exact input transfer to the configured router, and invokes `execute_strategy`. [3](#0-2)  After execution it validates only the controller’s token-input decrease, maximum spend, and positive token-output receipt; none of these checks restricts other calls made by route-selected contracts. [4](#0-3) 

The router interface explicitly accepts `swap_xdr` as opaque bytes, so the controller has no structural opportunity to distinguish a normal venue hop from a call into an attacker-controlled contract. [5](#0-4)  Because the strategy root call requires the victim’s authorization, a nested `transfer(victim, attacker, amount)` issued by route-selected code can be authorized when the victim signs the simulated authorization tree.

### Impact Explanation

An attacker can steal tokens held in the victim’s wallet that are unrelated to the lending collateral being swapped. The stolen amount is bounded by the victim’s token balances and the unauthorized transfers included in the signed tree, not by the strategy’s `amount_in`. [6](#0-5) 

The malicious route can still return a positive `token_out` amount, allowing `verify_router_output`, collateral redeposit, and final risk checks to succeed while the separate wallet-token theft remains part of the same transaction. [7](#0-6) [8](#0-7) 

### Likelihood Explanation

Exploitation requires user interaction: the victim must use an attacker-supplied or poisoned route and sign the authorization tree produced by simulation. No privileged role, leaked key, oracle manipulation, or control of the configured router is required. [9](#0-8) 

All four router-backed strategy paths are reachable by an ordinary account owner or active delegate, and the payload is supplied as a normal strategy argument. [10](#0-9)  The likelihood is user-interaction-dependent rather than fully remote, consistent with Medium severity.

### Recommendation

Do not allow route bytes to invoke arbitrary contract addresses during controller strategies. Enforce a governance-managed venue/pool allowlist in the router before dispatching each hop, and reject any route containing an unlisted target. If unrestricted routing is required, the signing interface must decode the complete route and refuse any authorization tree containing calls beyond the expected controller-root authorization and controller input-token transfer.

### Proof of Concept

1. The victim owns a lending account with collateral in market `current` and also holds an unrelated token `T` in their wallet.
2. The attacker deploys a contract exposing the route venue interface expected by the router and gives the victim route bytes that include this contract as a hop.
3. The victim calls `swap_collateral(caller=victim, account_id=victim_account, current, amount, new, swap=malicious_route)`. [11](#0-10) 
4. The controller authorizes only its own `token_in.transfer(controller, router, amount_in)` grant, then invokes `router.execute_strategy(controller, amount_in, malicious_route)`. [1](#0-0) 
5. During route execution, the attacker contract invokes `T.transfer(victim, attacker, victim_balance)`.
6. Transaction simulation records that token transfer beneath the victim’s `swap_collateral` authorization tree. If the victim signs the displayed/generated tree, the nested transfer executes.
7. The route returns a positive `new` token amount to the controller, so the post-router spend and receipt checks pass and the swapped output is redeposited. [4](#0-3) 
8. The transaction succeeds: the victim’s lending position remains valid, but their unrelated `T` wallet balance has been transferred to the attacker.
