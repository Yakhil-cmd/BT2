### Title
Double self-issuance of a capped asset within a single AA trigger response - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit` processes an AA's outgoing `payment` messages with `async.eachSeries`, and for each message that needs a capped asset it independently calls `completePaymentPayload` → `issueAsset`. `issueAsset` decides whether to self-issue a capped asset purely by querying the already-committed `inputs` table ("already issued" check), then synchronously mutates the in-memory `payload.inputs` of that one message. Because the check is against the DB (not against issues staged in-memory for other messages of the same response unit), two payment messages in the same AA definition that both request the same capped asset can each pass the "already issued" check and each add a full `cap`-amount issue input, before any of it is written to the DB.

### Finding Description
The check-then-act pattern is in `aa_composer.js`: [1](#0-0) 

```
function issueAsset(cb2) {
    ...
    if (objAsset.cap) { // only our AA can issue, no unstable consensus-breaking issues possible
        conn.query("SELECT 1 FROM inputs WHERE type='issue' AND asset=?", [asset], function(rows){
            if (rows.length > 0) // already issued
                return cb2('already issued');
            addIssueInput(1);
        });
    }
    ...
}
```

`issueAsset` is invoked from `completePaymentPayload`, which itself is called once per payment message of a response unit, via `async.eachSeries` over `messages`: [2](#0-1) 

Each call to `completePaymentPayload`/`issueAsset` runs its own SQL `SELECT 1 FROM inputs WHERE type='issue' AND asset=?`. This query only reflects rows that already exist in the `inputs` table (i.e., previously committed/saved units). The `addIssueInput` call that follows only mutates the message's own in-memory `payload.inputs` array — it does not insert a row into the `inputs` table. The actual DB write for the whole response unit happens much later, in `validateAndSaveUnit`, after *all* messages (including a second one needing the same capped asset) have already been processed by `sendUnit`.

Consequently, if a single AA response (built from one AA definition, possibly reached via `messages: [...]`/`messages.cases` producing 2 payment messages referencing the same capped, AA-definer-issued asset, e.g. one primary payment and one secondary "change"/split payment in the same trigger evaluation) needs the same not-yet-issued capped asset twice, the "already issued" check queries the DB twice, sees no committed issue input either time, and lets `addIssueInput` run twice — creating two `type='issue'` inputs each with the full `cap` amount inside the same unit. This inflates the total issued supply of the asset beyond its declared `cap`, which validators can be tricked into accepting because both issue inputs are inside the same not-yet-persisted unit and the guard's SQL only ever looks backward at history, never at sibling issues in flight.

The referenced GitHub report's root cause is structurally identical: a one-time "already done" guard is evaluated against stale/pre-mutation state, and the actual mutation happens after the guard passes for a second time within the same logical operation, because the set of "already existing" facts used for the check does not include facts staged earlier in the very same operation.

### Impact Explanation
This breaks the "capped asset" invariant fundamental to `ocore`'s asset model (`assets.cap`): an AA-controlled capped asset could be issued for more than its `cap`, producing asset supply inflation. Any AA-issued token relying on `cap` to bound total supply (a common ocore/Oscript pattern, `app: 'asset'` with `cap: ...` + AA self-issuance as seen in `test/aa_composer.test.js` "issue recently defined asset"/"recently defined asset" tests) would have its cap violated, undermining every downstream contract, exchange, or holder that assumes `asset[...].cap` is an upper bound on issued supply. This is a concrete supply-inflation bug in the AA-driven asset issuance path, matching the "supply inflation" impact category.

### Likelihood Explanation
Reaching this requires an AA definition (attacker-authored or a legitimate AA whose trigger logic can be manipulated by an attacker's trigger data/unit) that produces, within a single trigger evaluation, two distinct `payment` messages that both need to draw on the same not-yet-issued capped asset (e.g., two separate payment messages to different addresses in the same response, both funded from the AA's own capped, self-issued token, where neither payment's inputs are otherwise satisfiable from existing balance). This is entirely reachable by any unprivileged party who can trigger the AA with a unit/trigger designed to force such a message layout — no special privileges, hub, or node cooperation are needed; it is a single-poster-controllable code path inside `sendUnit`/`completePaymentPayload`. I could not fully verify from the available snippets whether `mergeMessagesAndOutputs` (called before this loop when `mci >= constants.pemCurvesFixMci`) always merges multiple payment messages of the same asset into one, which would close this gap for messages present in the original AA definition; if merging is complete for same-asset payment messages, the practical trigger would instead need the two issuance-needing payment completions to occur via separate qualifying `if`-cases across sequential invocations that still resolve within the same `sendUnit` call (e.g., secondary/self triggers chained within one top-level trigger, similar to the "issue recently defined asset" test which chains 3 AA responses through a bouncer AA). Given the uncertainty around `mergeMessagesAndOutputs`'s exact merge scope, this should be validated with a live PoC AA before treating it as fully confirmed; however, the underlying check-then-act flaw in `issueAsset` is confirmed directly from the code.

### Recommendation
Track "issued" state for a capped asset in the same in-memory scope used across all messages of one `sendUnit` invocation (and, ideally, across chained/secondary triggers of the same top-level trigger), not solely via a DB query. For example, maintain a local `Set`/flag keyed by `asset` in `handleTrigger`'s outer scope (alongside `assetInfos`) that is set as soon as an issue input is staged for that asset in the current response, and have `issueAsset` check both the DB and this staged-issuance flag before calling `addIssueInput`. Ensure this staged state is also checked/updated when handling secondary triggers arising from the same primary trigger (`arrPreviousAAResponses`), since those units are not yet in the `inputs` table either.

### Proof of Concept
Conceptual PoC (mirrors the report's "validate() re-entrant reset" pattern, adapted to `ocore`'s AA issuance path):

1. Deploy an AA that defines an asset with `cap: N`, `issued_by_definer_only: true`, self-issuable by the AA (as in the `test/aa_composer.test.js` "issue recently defined asset" test scaffold).
2. Craft a trigger (single unit, single trigger data payload) whose evaluated `messages` produce two separate `payment` messages both needing to draw `N` units of the not-yet-issued asset — e.g., one message paying `N/2` to address X and a second message paying `N/2` to address Y from the same asset, structured so `mergeMessagesAndOutputs` (only active from `constants.pemCurvesFixMci` onward) does not coalesce them into a single payment message (or via chained secondary AA triggers within the same top-level trigger evaluation, as in the existing "issue recently defined asset" test, but arranged so two separate `sendUnit` message-processing passes each need to issue the same capped asset before either is persisted).
3. Because each message's `completePaymentPayload`/`issueAsset` call queries `SELECT 1 FROM inputs WHERE type='issue' AND asset=?` against the DB — which has no rows yet for either call since the unit hasn't been saved — both calls proceed to `addIssueInput(1)`, each adding an issue input of `cap` amount.
4. The resulting unit (or units) contain two `type='issue'` inputs summing to `2*cap` for an asset whose declared cap is `cap`, violating the asset's supply cap once the unit(s) are validated and saved via `validateAndSaveUnit`.
