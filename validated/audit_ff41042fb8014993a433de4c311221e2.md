### Title
Credentials configured for one submodule URL are not host+path-scoped and can be disclosed to a different repository on the same host - (File: main.go)

### Summary
`git-sync`'s `--credential` flag lets operators register multiple `url`/`username`/`password` triples (typically to authenticate distinct submodules) which are handed to git via `git credential approve` in `StoreCredentials`. Git's default credential-matching semantics key credentials by protocol+host only (path is ignored unless `credential.useHttpPath` is enabled), which git-sync never sets. This is analogous to the Spigot "whitelisted function not scoped to a specific revenue contract" bug: an authorization/credential record intended for one specific target (a function selector on one contract / a URL for one submodule) is not scoped tightly enough, and a different, attacker-influenced target that shares the coarse-grained key (any selector at all / any path on the same host) can consume it.

### Finding Description
`refreshCreds` in `main.go` iterates `*flCredentials` and calls: [1](#0-0) 
which calls `StoreCredentials`: [2](#0-1) 
This feeds `url=<value>\nusername=<value>\npassword=<value>` into `git credential approve` for the exact URL string configured by the operator (e.g. `https://host/subA`). Git's built-in `credential.helper cache` (configured by git-sync itself in `SetupDefaultGitConfigs`) stores and later retrieves entries keyed by protocol and host by default: [3](#0-2) 
git-sync never sets `credential.useHttpPath=true`, so the `path` component of the stored URL is not part of the lookup key that `git credential fill` uses when git later needs credentials for any fetch/clone against that host — including a submodule fetch to a different path.

README explicitly documents that `--credential` exists specifically "for specific URLs, for example when using submodules" and multiple credentials may be supplied when a repo has multiple submodules with different auth: [4](#0-3) [5](#0-4) 

Because the repository content (including `.gitmodules` and submodule URLs) is attacker-controlled content pulled from the synced upstream repo, and submodule fetching is performed automatically by `configureWorktree`/`submodule update --init` without any additional per-submodule authorization check: [6](#0-5) 
an attacker who can add or modify a submodule pointing at a new path on the same host as one of the operator's `--credential` entries can cause git to present that host-scoped credential to the attacker-controlled path — even though the operator only intended it for a specific, different repo path on that host. This mirrors the audit finding's root cause: an authorization record (whitelisted selector / stored credential) is validated only against a coarse identifier (4-byte selector / host) rather than the full intended target (contract address + selector / host + path), enabling an attacker-controlled sibling target to piggyback on it.

### Impact Explanation
If exploited, this results in credential/token disclosure: an attacker-influenced repository (via a malicious or altered submodule entry) can cause git-sync's stored credentials for one intended host+path to be sent (as HTTP Basic Auth) to a different path/repo under the attacker's control on the same host, which the attacker can log or exfiltrate. This directly maps to the allowed "credential or token disclosure" impact category. It requires the attacker to control repository content (submodule URLs) that git-sync fetches, and it requires the operator to be using `--credential` with more than one path on a shared host — a supported and documented multi-credential/submodule use case.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the operator to configure `--credential` for at least one path-scoped URL, and (b) an attacker capable of introducing or altering a submodule reference in the synced repository to point at another path on the same host (e.g., via a compromised/malicious PR or a self-hosted git server where the attacker can create arbitrary repos/paths on the same host). This is a realistic scenario for the documented "submodules with different auth" use case, but is not automatically triggered by every git-sync deployment.

### Recommendation
- Set `credential.useHttpPath=true` in `SetupDefaultGitConfigs` (or specifically for entries supplied via `--credential`) so git's credential matching honors the full path, not just protocol+host, scoping stored credentials to the exact URL the operator intended.
- Consider clearing/rotating the credential cache's scope between fetch operations for different declared URLs, or use a helper that supports exact-URL matching instead of the generic `cache` helper.
- Document clearly that `--credential` entries are host-scoped unless `useHttpPath` is set, so operators are aware of the blast radius when multiple submodules share a host.

### Proof of Concept
1. Operator configures git-sync with two submodule credentials on the same host but different paths, e.g.:
   ```
   --credential='{"url":"https://git.example.com/teamA/private-sub","username":"userA","password-file":"/creds/a"}'
   ```
   This is stored via `git.StoreCredentials` → `git credential approve` (main.go:2055-2067), and `credential.helper=cache` is the only helper configured (main.go:2276-2303), with no `useHttpPath`.
2. The upstream repo that git-sync tracks (attacker-controlled/attacker-influenced) is modified to add a new submodule at `https://git.example.com/attacker/evil-sub` (same host, different path).
3. On next sync, `configureWorktree` runs `submodule update --init [--recursive]` (main.go:1733-1747), which triggers `git credential fill` for `https://git.example.com/attacker/evil-sub`.
4. Because the credential cache matches on protocol+host only (no `useHttpPath`), git supplies the `userA` credentials intended for `teamA/private-sub` to the fetch against `attacker/evil-sub`. If `attacker/evil-sub` is a git server under attacker control (e.g., attacker owns another repo path on the shared host, or a proxy in front of `git.example.com`), the attacker's server receives and can log the Basic-Auth credentials in the fetch request, achieving credential disclosure without ever needing the original credential value.

// StoreCredentials stores a username and password for later use.
func (git *repoSync) StoreCredentials(ctx context.Context, url, username, password string) error {
	git.log.V(1).Info("storing git credential", "url", redactURL(url))
	git.log.V(9).Info("md5 of credential", "url", url, "username", md5sum(username), "password", md5sum(password))

	creds := fmt.Sprintf("url=%v\nusername=%v\npassword=%v\n", url, username, password)
	_, _, err := git.RunWithStdin(ctx, "", creds, "credential", "approve")
	if err != nil {
		return fmt.Errorf("can't configure git credentials: %w", err)
	}

	return nil
}

            prefer password-file for better security.

              --credential='{"url":"https://github.com", "username":"myname", "password-file":"/creds/mypass"}'
