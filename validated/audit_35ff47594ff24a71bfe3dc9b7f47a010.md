### Title
Webhook signature verification keys on `repository.owner.login`, but stack/commit resolution keys on `repository.full_name` / commit `sha` — allows cross-organization forgery in a multi-org Shipit deployment - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a multi-organization Shipit configuration, the HMAC signature over an inbound webhook is verified using the GitHub App config selected by `repository.owner.login` (or `organization.login`), while the actual repository/stack/commit that the payload acts upon is resolved from an entirely different, unvalidated field of the *same* attacker-supplied JSON body (`repository.full_name`, or bare `sha` for status events). Nothing cross-checks that these two fields refer to the same organization.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App/organization config used to check `X-Hub-Signature` purely from `repository_owner`: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` looks up a per-organization `webhook_secret` from `secrets.github`, one entry per organization in a multi-org deployment: [3](#0-2) 

Once the signature check passes, the actual event body is dispatched to a `Handler`, whose repository resolution reads a *different* field of the same JSON payload: [4](#0-3) 

`Repository.from_github_repo_name` blindly trusts and splits that string into owner/name to find the target `Repository`/`Stack`: [5](#0-4) 

`StatusHandler` goes even further and doesn't consult `repository` at all — it resolves target commits purely by `sha`, globally, with no organization/repository scoping whatsoever: [6](#0-5) 

Because the HMAC is computed over the raw POST body, and the body's `repository.owner.login` field (used for verification) is independent from `repository.full_name` / `sha` (used for effect), an actor who legitimately administers **their own** organization in a multi-org Shipit install — and therefore legitimately knows **their own** org's `webhook_secret`, configured by them at GitHub App creation time per `docs/setup.md` — can craft an arbitrary raw JSON body, sign it with their own secret, and set `repository.owner.login` to their own org (so `verify_signature` passes) while setting `repository.full_name` (or `sha`) to point at a victim organization's repository/stack/commit.

This breaks exactly the binding: `organization that authenticated == repository that is written`. The check authenticates side A of the payload; the handlers act on side B, with no equality enforced between them.

### Impact Explanation
- Via `PushHandler`, the attacker can trigger `GithubSyncJob` for a victim stack, forcing a foreign stack to sync to an attacker-chosen `expected_head_sha`, manipulating the victim's undeployed-commit state.
- Via `StatusHandler`, since resolution is by raw `sha` with **no organization/repository scoping at all**, the attacker can forge arbitrary commit statuses (`state`, `context`, `target_url`, `description`) for any commit SHA known to exist in *any* stack across the whole Shipit installation, including a victim org's. Since CI-required statuses (`ci.require`/`blocking` in `shipit.yml`) gate whether a commit is deployable, this can be used to make an otherwise-blocked victim commit appear "green"/deployable — i.e., a path toward an **unauthorized deploy** on a stack the attacker has no legitimate access to.
- `MembershipHandler` and the pull-request handlers are similarly reachable and act on data keyed by fields (`organization.login`, team/member logins, PR repository) not cross-validated against the signature-verifying organization, enabling cross-org team membership tampering as well.

This matches the "High"/"Critical" impact bar: escalation across a repository/organization trust boundary using only the attacker's own legitimately-known configuration secret, resulting in unauthorized state changes (and a credible path to unauthorized deploys) on a repository the attacker does not control.

### Likelihood Explanation
This is realistically reachable only in the documented multi-organization configuration (`config/secrets.development.example.yml` shows the multi-org schema), where each organization's admin sets up their own GitHub App and legitimately knows their own `webhook_secret`. No compromise of the victim's or any privileged secret is required — only knowledge of a secret the attacker validly possesses for their own tenant. This is a realistic misuse case for any shared/multi-tenant Shipit deployment, not a purely theoretical scenario.

### Recommendation
After computing `repository_owner` for signature verification, re-derive the acting repository strictly from the same trusted scope: reject the webhook (422) unless `repository.full_name`'s owner segment (or the commit's stack's repository owner, for `status` events) equals the verified `repository_owner`/organization. For `StatusHandler` specifically, scope commit lookup by repository/organization rather than by bare `sha` alone.

### Proof of Concept
1. Attacker is a legitimate admin of `attacker-org`, which is one of several organizations configured in a multi-org Shipit `secrets.github` block, and knows `attacker-org`'s `webhook_secret` (they created the GitHub App per `docs/setup.md`).
2. Attacker crafts a raw JSON body for a `push` event:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeef...",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac(attacker-org secret, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `WebhooksController#verify_signature` selects `Shipit.github(organization: "attacker-org")`, computes the HMAC with `attacker-org`'s secret, and it matches — verification passes.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")`, entirely unrelated to `attacker-org`, and enqueues `GithubSyncJob` against the victim's stack.
6. For a stronger PoC, repeat with `X-Github-Event: status` and a forged `sha` belonging to a commit in `victim-org`'s stack — `StatusHandler` updates that commit's CI status with no repository check at all, since resolution is `Commit.where(sha: params.sha)` with no organization scoping.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
