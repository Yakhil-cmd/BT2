### Title
Cross-organization webhook forgery via decoupled `repository.owner.login` (signature verification) and `repository.full_name` (mutation target) - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/org config — and thus whether a `webhook_secret` even needs to be checked — using `params.dig('repository','owner','login')`, while every webhook handler resolves the repository/stack it actually mutates using the independent field `payload.dig('repository','full_name')`. Because the attacker fully controls the raw JSON POST body to the unauthenticated `POST /webhooks` endpoint, these two fields can be set to different organizations, letting an attacker pick a configured org with no `webhook_secret` to trivially pass verification while the mutation target names a victim org's repository.

### Finding Description
Broken binding (should hold, does not): `org_used_for_verification(repository.owner.login) == org_owning_mutated_repo(repository.full_name)`.

- Verification: `verify_signature` computes `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`. [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` short-circuits to `true` when the selected org has no configured secret: `return true unless webhook_secret`. [3](#0-2) 
- Mutation target: every `Handler` (base class used by all event handlers) resolves the acted-upon repository/stacks from a completely different field of the same attacker-supplied JSON: `payload.dig('repository', 'full_name')`, then `Repository.from_github_repo_name(repository_name)&.stacks`. [4](#0-3) 

Because the controller passes the raw, unauthenticated JSON straight to handlers (`params = JSON.parse(request.raw_post); Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }`), there is no requirement that `repository.owner.login` and `repository.full_name`'s owner segment refer to the same repository object — this internal consistency only exists incidentally in genuine GitHub payloads, not enforced by any code in this engine. [5](#0-4) 

Exploit flow: attacker sends `POST /webhooks` with `X-Github-Event: push` (or any handled event) and a body where `repository.owner.login = "attacker_org"` (an org configured in Shipit with no `webhook_secret`) and `repository.full_name = "victim_org/victim_repo"` (the real target, whose org does have a `webhook_secret` — e.g. because it uses sha256-only tooling and this engine never reads `X-Hub-Signature-256`). `verify_signature` resolves `Shipit.github(organization: "attacker_org")`, whose `verify_webhook_signature` returns `true` unconditionally because `attacker_org` has no secret — the `X-Hub-Signature` header content is irrelevant. `head(422)` is never called. The handler then runs against `victim_org/victim_repo`'s stacks, e.g. enqueuing `GithubSyncJob`, creating commit `Status`, or acting on `pull_request` events for the victim's repository.

None of the listed guards prevent this: `drop_unhandled_event` only checks event type presence; the `ExplicitParameters` schemas in individual handlers parse fields but never cross-check `owner.login` against `full_name`; `force_github_authentication`/`User#authorized?`/`require_permission!` are session/API-token concerns not invoked on this unauthenticated controller at all; `Repository`/`Stack` model validations only constrain format of stored records, not consistency between two attacker-controlled JSON fields in a single request.

### Impact Explanation
An unauthenticated attacker can make Shipit act on an arbitrary victim repository/stack (enqueue sync jobs, write commit statuses, drive pull-request/label handlers, trigger review-stack provisioning, etc.) as long as they can name any Shipit-configured GitHub org that lacks a `webhook_secret`. This is a direct authentication bypass plus cross-repository/cross-tenant mutation, matching the Critical category "a payload for one repository mutating another's stack, commit, task or team" and "authentication bypass (forged webhook accepted)". Blast radius spans every stack/repository configured under any org whose webhook signature would otherwise be required, as long as at least one other configured org in the same Shipit instance has no `webhook_secret`.

### Likelihood Explanation
Preconditions: (1) the Shipit deployment must have at least one GitHub org configured without a `webhook_secret` (common in multi-org self-hosted setups, staging orgs, or orgs onboarded before secret rotation/sha256 migration) which `Shipit.github(organization: ...)` can resolve without raising `Shipit::GithubOrganizationUnknown`; (2) the victim org's repo full_name is known/guessable (public repos are trivially known). Attacker cost is a single crafted HTTP POST with no secrets, sessions, or tokens required. The attack is fully repeatable against any repository whose full name the attacker knows, for every supported webhook event type.

### Recommendation
Bind signature verification to the same repository object that handlers act on: derive both the verification org and the mutated repository from one authoritative source (e.g., always use `repository.full_name`'s owner segment for `Shipit.github(organization: ...)`, or validate `repository.owner.login == repository.full_name.split('/').first` before proceeding). Additionally, support and require `X-Hub-Signature-256` verification when a secret is configured, and treat "webhook_secret configured but no valid signature header of a supported algorithm present" as a verification failure rather than falling through.

### Proof of Concept
Add to `test/controllers/webhooks_controller_test.rb`:
```ruby
test "cross-org forgery bypasses signature check via mismatched owner/full_name" do
  victim_stack = shipit_stacks(:shipit) # belongs to org "shopify", has webhook_secret configured in test config
  Shipit.stubs(:github).with(organization: 'attacker_org').returns(
    Shipit::GitHubApp.new('attacker_org', {}) # no webhook_secret => verify_webhook_signature always true
  )

  request.headers['X-Github-Event'] = 'push'
  request.headers['X-Hub-Signature'] = 'sha1=deadbeef' # attacker-guessable/garbage

  body = JSON.parse(payload(:push_master))
  body['repository']['owner']['login'] = 'attacker_org'          # used for verification
  body['repository']['full_name'] = victim_stack.repository.github_repo_name # used for mutation

  assert_enqueued_with(job: GithubSyncJob, args: [stack_id: victim_stack.id, expected_head_sha: body['after']]) do
    post :create, body: body.to_json, as: :json
  end
  assert_response :ok  # head(422) never rendered despite bogus signature
end
```
This asserts both sides of the binding: the org used for verification (`attacker_org`, no secret) differs from the org owning the mutated stack (`shopify`/victim), yet the handler still executes against the victim's stack.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
