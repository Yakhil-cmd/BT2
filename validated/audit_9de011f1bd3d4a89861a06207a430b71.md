### Title
Webhook signature is bound to `repository.owner.login` while every handler resolves and writes state using the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` authenticates an inbound GitHub webhook by looking up the HMAC secret for the organization named in `repository_owner`, but the downstream `Handler` base class (and every concrete handler built on it) resolves *which* `Repository`/`Stack` to mutate using a different, independently-controlled field from the same JSON body: `repository.full_name`. These two fields are never cross-checked, so the "organization whose secret validated the request" and "the repository that gets written to" are not the same binding.

### Finding Description
`WebhooksController#verify_signature` computes: [1](#0-0) 
using [2](#0-1) 
i.e. it fetches `Shipit.github(organization: repository_owner)` and checks `X-Hub-Signature` against that organization's `webhook_secret`. In a multi-tenant deployment (explicitly supported and documented), each GitHub organization onboarded to Shipit has its own independent `webhook_secret`: [3](#0-2) [4](#0-3) 

Once the signature check passes, `create` dispatches the *entire raw payload* to all registered handlers: [5](#0-4) 

Every handler inherits from `Shipit::Webhooks::Handlers::Handler`, which independently derives the target repository/stacks from a *different* payload field, `repository.full_name`, with no reference back to `repository_owner`/the org that was actually authenticated: [6](#0-5) 

`Repository.from_github_repo_name` splits this attacker-controlled string on `/` and looks up any repository, regardless of which org's secret validated the request: [7](#0-6) 

Concretely, `PushHandler` and every `PullRequest::*Handler`, and `StatusHandler` all key off `params.repository.full_name` (or `repository_name`) to select the `Stack`/`Commit` to act on: [8](#0-7) [9](#0-8) 

This breaks the equality that should hold: `organization authenticated by signature == organization that owns the repository being written`. Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are two independent JSON fields in the same untrusted body, an attacker who can get a validly-signed webhook for *any one* onboarded organization (e.g. because they administer/own that org's GitHub App installation, or simply because that org's webhook secret is unset/blank — `verify_webhook_signature` returns `true` when `webhook_secret` is blank, see `lib/shipit/github_app.rb`) can set `repository.owner.login` to their own org (satisfying the signature check) while setting `repository.full_name` to point at a completely different, victim organization's repository tracked by the same Shipit instance.

`StatusHandler` is the most damaging instance: it writes a `CommitStatus` directly from unauthenticated payload fields (`state`, `description`, `target_url`, `context`) onto any `Commit` matching `params.sha` across the whole install, with no verification that the commit belongs to the org that signed the request: [10](#0-9) 
This directly feeds Shipit's CI/deployability gating for arbitrary stacks belonging to other organizations.

### Impact Explanation
This allows a webhook validly signed under Organization A's secret to forge/inject CI status ("success") or trigger sync jobs for commits/stacks belonging to Organization B, an org the attacker has no access to. Forged commit statuses can flip a commit from "not deployable" to "deployable," enabling an unauthorized deploy of a repository the attacker does not control — matching the "unauthorized deploy" High-severity criterion, since it escalates a signature valid for one tenant's data into a write on another tenant's protected state.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to already control (or have compromised) a legitimately-configured GitHub App/webhook secret for *some* organization onboarded to the same multi-tenant Shipit instance (a realistic scenario for shared internal Shipit deployments servicing many orgs, as explicitly documented as a supported configuration), or to exploit an org configured with a blank `webhook_secret` (which `verify_webhook_signature` treats as always-valid). No repository write access, `ApiClient` token, or Shipit session is needed — only the ability to send an HTTP POST to `/webhooks` with a validly-signed body for one org while spoofing the `repository.full_name` field.

### Recommendation
In `WebhooksController#verify_signature` (or in `Handler#repository_name`), validate that the repository owner encoded in `repository.full_name` matches `repository_owner` (the value the signature was actually verified against) before dispatching to handlers, e.g. reject the request if `params.dig('repository','full_name')&.split('/')&.first != repository_owner`. Handlers should not trust `repository.full_name` independently of the field used for signature verification.

### Proof of Concept
1. Deploy Shipit configured for two organizations, `OrgA` and `OrgB`, each with its own `github.webhook_secret` (per `docs/setup.md` "Using Multiple Github Applications").
2. Shipit tracks a `Stack`/`Repository` for `OrgB/victim-repo`.
3. Attacker, who knows/controls `OrgA`'s webhook secret (or exploits an org with blank `webhook_secret`), crafts a `status` event payload:
```json
{
  "sha": "<victim commit sha in OrgB/victim-repo>",
  "state": "success",
  "context": "ci/attacker-forced",
  "repository": { "full_name": "OrgB/victim-repo", "owner": { "login": "OrgA" } }
}
```
4. Attacker computes `X-Hub-Signature` using `OrgA`'s webhook secret over the raw body and POSTs to `/webhooks` with header `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: 'OrgA')` (from `repository.owner.login`) and successfully verifies the signature against `OrgA`'s secret.
6. `StatusHandler#process` looks up `Commit.where(sha: params.sha)` — which matches the commit in `OrgB/victim-repo` — and calls `commit.create_status_from_github!(params)`, writing a forged "success" status onto `OrgB`'s commit, despite the request never being signed by `OrgB`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
