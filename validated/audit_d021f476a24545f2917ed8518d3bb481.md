### Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` lookup enables unauthorized commit status/deploy trigger - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by SHA alone across the entire `commits` table, without restricting to the repository named in the signed webhook payload. Since the `commits` table is only unique on `(stack_id, sha)` and not globally, a status webhook legitimately signed for one repository/organization can attach a forged `success` state to a same-SHA `Commit` row belonging to a completely different stack, triggering that victim stack's continuous-delivery deploy path.

### Finding Description
The binding that should hold is: `payload['repository']['full_name'] (as verified by verify_signature/verify_webhook_signature) == the stack/repository whose Commit rows receive the resulting Status`.

`Shipit::WebhooksController#verify_signature` only proves that the payload was signed by the GitHub App/webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`) [1](#0-0) . It says nothing about which `Commit` rows the handler is allowed to mutate — that scoping is supposed to happen inside each `Handler`. The base `Handler` class provides a `stacks` helper for exactly this purpose, built from `Repository.from_github_repo_name(repository_name)` [2](#0-1) .

`StatusHandler#process`, however, does not use this scoping at all:
```
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This matches every `Commit` row with the given SHA regardless of which stack/repository it belongs to. The `commits` table's only SHA index is `(stack_id, sha)` (added in `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb`), confirming SHA is not globally unique and multiple stacks can legitimately hold `Commit` rows with the same SHA (e.g., shared history between a fork and its upstream). `create_status_from_github!` then creates the `Status` scoped to that commit's own `stack_id` [4](#0-3) , and `Status#replicate_from_github!` persists it under that `stack_id` unconditionally [5](#0-4) .

Once the forged `Status(state: 'success')` is created on the victim's `Commit`, `Commit#deployable?` becomes true (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [6](#0-5) . `Status` has `after_commit :schedule_continuous_delivery` which calls `commit.schedule_continuous_delivery`, enqueuing `ContinuousDeliveryJob` for the victim's stack [7](#0-6) . If `continuous_deployment: true` on the victim stack, `ContinuousDeliveryJob#perform` calls `stack.trigger_continuous_delivery` [8](#0-7) , which computes `next_commit_to_deploy` from `deployable?` commits and calls `trigger_deploy` [9](#0-8) , ultimately running the victim's deploy scripts via `Task#enqueue`/`Command`/`PTY.spawn` against a commit whose "success" status was forged by an unrelated, attacker-controlled repository's webhook.

The forged webhook is fully valid at the transport layer: it is correctly signed with the attacker's own repository's/organization's webhook secret, so `verify_signature` passes. `drop_unhandled_event` and the `ExplicitParameters` schema in `StatusHandler.params` only validate shape (`sha`, `state`, etc.), not ownership [10](#0-9) . Nothing in the call path re-checks that the commit's stack actually belongs to the repository that the signature was verified against.

### Impact Explanation
An attacker who controls any repository with a Shipit webhook installed (their own fork/org) can, by causing a `status` event to fire for a SHA that also exists as a `Commit` row in a victim's unrelated stack, inject a forged `success` `Status` into that victim stack. If the victim stack has `continuous_deployment: true`, this can cause an unauthorized deploy — code execution on the victim's deploy host via the normal `Task`/`Command`/`PTY.spawn` deploy pipeline — for a commit that never passed the victim's own CI. This is a cross-tenant "payload for one repository mutating another's stack/commit" and unauthorized-deploy scenario, matching the Critical severity bucket. Impact is repeatable against any victim stack/commit pair that shares an identical SHA with a repository the attacker controls.

### Likelihood Explanation
Preconditions: victim stack has `continuous_deployment: true`; a `Commit` row with the same SHA must already exist for both the attacker's controlled repository and the victim's stack (realistic via shared/forked git history, shared upstream commits, or identical merge-commit trees, as noted in the prompt); attacker needs no Shipit credentials, only a repository with the Shipit GitHub App/webhook installed for their own org, which they can control as an ordinary GitHub user. Cost is low: forging a status webhook for one's own repository is a completely legitimate, unprivileged action.

### Recommendation
Scope `StatusHandler#process` (and audit other handlers similarly) to only update commits belonging to stacks resolved from `repository_name` (payload `repository.full_name`), e.g. using the existing `stacks` helper: `stacks.flat_map(&:commits).where(sha: params.sha)` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, instead of a global `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
require 'test_helper'

module Shipit
  module Webhooks
    module Handlers
      class StatusHandlerCrossTenantTest < ActiveSupport::TestCase
        test "status for a SHA shared across stacks only updates the commit belonging to the webhook's repository" do
          attacker_repo = shipit_repositories(:some_other_repo) # not related to victim stack
          victim_commit = shipit_commits(:cyclimse_first)
          victim_stack = victim_commit.stack
          victim_stack.update!(continuous_deployment: true)

          # Simulate: attacker's repo happens to contain a commit with the same sha
          shared_sha = victim_commit.sha
          attacker_stack = attacker_repo.stacks.first
          attacker_commit = attacker_stack.commits.create!(sha: shared_sha, message: 'x',
            author: shipit_users(:walrus), committer: shipit_users(:walrus),
            authored_at: Time.now, committed_at: Time.now)

          payload = {
            'sha' => shared_sha,
            'state' => 'success',
            'context' => 'ci/forged',
            'repository' => { 'full_name' => attacker_repo.full_name, 'owner' => { 'login' => attacker_repo.owner } }
          }

          assert_no_difference -> { victim_commit.statuses.count } do
            StatusHandler.call(payload)
          end
          # currently FAILS: victim_commit.statuses.count increases by 1
          # because StatusHandler#process matches Commit.where(sha: shared_sha) globally,
          # proving the binding repository_name(payload) == commit.stack.repository is broken.
        end
      end
    end
  end
end
```

    def trigger_continuous_delivery
      return if cached_deploy_spec.blank?

      commit = next_commit_to_deploy

      if should_resume_continuous_delivery?(commit)
        continuous_delivery_resumed!
        return
      end

      if should_delay_continuous_delivery?(commit)
        continuous_delivery_delayed!
        return
      end

      begin
        trigger_deploy(commit, Shipit.user, env: cached_deploy_spec.default_deploy_env)
      rescue Task::ConcurrentTaskRunning
      end
    end
