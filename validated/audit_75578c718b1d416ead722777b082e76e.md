### Title
Cross-repository commit-status forgery via unscoped SHA lookup enables victim-repo `merge_pull_request` with Shipit's own credentials - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` updates commit statuses purely by matching `sha` across the entire `commits` table, with no check that the commit belongs to the repository/organization whose webhook signature was verified. A user who legitimately owns any GitHub organization/repo already onboarded to the same multi-tenant Shipit instance can send a real, correctly-signed `status` webhook for a commit SHA they control, and if that SHA happens to also exist as a `Commit` row under a different (victim) stack — e.g. because the victim's PR head commit is byte-identical to a commit in the attacker's own fork/repo, which is the normal case before any additional commits are pushed — the forged status is applied to the victim's commit. This can flip `MergeRequest#all_status_checks_passed?` to true and cause `ProcessMergeRequestsJob` to invoke `merge_request.merge!`, which calls `stack.github_api.merge_pull_request(stack.github_repo_name, ...)` using the **victim stack's own configured GitHub App credentials**, executing a real merge the attacker never had authorization to trigger on that repository.

### Finding Description
The claimed binding is: `verified_org(webhook signature) == org(commit.stack.repository)` for every `Commit` a `status` webhook is allowed to mutate.

Tracing the code:
1. `WebhooksController#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)`, where `repository_owner` is read from the *webhook payload's own* `repository.owner.login` [4](#0-3) . This only proves the payload was sent by (or forged with the secret of) the organization named in the payload itself — it says nothing about which `Commit` rows in Shipit's database the event is allowed to touch.
2. `StatusHandler` never uses the `Handler#stacks`/`repository_name` helpers (unlike `PullRequest` handlers, which correctly scope lookups via `Repository.from_github_repo_name(params.repository.full_name)` [5](#0-4) ). Instead it does a bare, cross-tenant SHA lookup: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [1](#0-0) .
3. `create_status_from_github!` → `add_status` writes the status and, on success/pending transitions, calls `stack.schedule_merges` for whichever stack owns that commit — not the stack tied to the webhook's org [2](#0-1) [6](#0-5) .
4. `ProcessMergeRequestsJob` then checks `merge_request.all_status_checks_passed?` and calls `merge_request.merge!` [7](#0-6) .
5. `MergeRequest#merge!` calls `stack.github_api.merge_pull_request(stack.github_repo_name, number, ..., sha: head.sha, ...)` using the *victim* stack's own `stack.github_api`/`stack.github_repo_name` — i.e., Shipit's legitimately configured, victim-repo-scoped GitHub App credentials [8](#0-7) .

Root cause: the equality the code implicitly relies on (verified webhook org == org of the commit being mutated) is never enforced, because `Commit` records carry no repository/org identity check at write time in `StatusHandler`; only `sha` is used as the join key, and SHAs are content-addressed and can be shared identically across unrelated repositories (most straightforwardly: attacker's own fork and the victim's PR share the same head commit SHA until any additional commit is pushed by either party).

Existing guards do not close this gap: `verify_signature` only authenticates *which organization sent the payload*, not *which commit rows it may affect*; `drop_unhandled_event` and the `ExplicitParameters` schema for `StatusHandler` only validate shape (`sha`, `state`, etc.), not ownership; there is no `require_permission!`/`stacks` scoping step in this handler as there is in the `PullRequest` handlers.

### Impact Explanation
An attacker who legitimately controls any GitHub org/repo that is already a Shipit tenant (even a low-privilege one, since they only need to be able to push a commit and post a status on their own repo) can cause **any other tenant's merge queue to complete a real merge** via `stack.github_api.merge_pull_request` scoped to the victim's repository, using Shipit's own GitHub App credentials for that repository — an unauthorized merge, matching the Critical category ("payload for one repository mutating another's stack/commit ... or an unauthorized deploy, rollback or merge"). This is repeatable against any stack/repository hosted on the same Shipit instance whenever a shared/collided SHA exists (most reliably: the moment a PR is opened from a fork, before any additional commits are added, the fork and base repo commit are byte-identical), and blast radius spans all tenants of the Shipit deployment, not just the attacker's own repository.

### Likelihood Explanation
Requires: (a) a multi-tenant Shipit deployment where the attacker's own org is validly configured with its own GitHub App/webhook secret (so they can generate a correctly-signed webhook for their own org), and (b) a SHA collision between a commit in the attacker's controlled repo and a commit tracked by the victim's stack — trivially achievable for the PR-fork case, since the head commit of a freshly opened cross-fork PR is identical between fork and base until diverged. Attacker cost is low (open a PR/fork, push a commit, post a status on their own repo/commit to trigger the real webhook); no secrets, sessions, or elevated roles are needed. Repeatable per target stack.

### Recommendation
Scope `StatusHandler#process` to the repository that sent the webhook: join through `stack: :repository` and filter by `Repository.from_github_repo_name(payload.dig('repository','full_name'))` (as the `PullRequest` handlers already do), so a status webhook can only mutate `Commit` rows belonging to stacks under the repository/org that authenticated the request, e.g. `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { id: repository.id })`.

### Proof of Concept
minitest, no live GitHub:
1. Create two `Stack`/`Repository` fixtures under different orgs, `victim/repo` and `attacker/repo`.
2. Create a `Commit` with `sha: "deadbeef..."` under `victim/repo`'s stack, and a pending `MergeRequest` for it whose only missing requirement is a passing status; stub `stack.github_api.merge_pull_request` on the victim stack via `Stack.any_instance.stubs(:github_api).returns(fake_api)` (or `Shipit.github(organization: 'victim').expects(:merge_pull_request)`).
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name` / `repository.owner.login` is `attacker/repo`, and `sha` equal to the victim commit's `sha`, `state: "success"`; stub `verify_signature` (as existing tests do via `GithubHook.any_instance.stubs(:verify_signature).returns(true)`) to isolate the authorization-scoping bug from signature mechanics.
4. Assert: `assert_difference "victim_commit.statuses.count", 1 { post :create, ... }` — proving the attacker-org-signed webhook wrote a status onto the victim's commit.
5. Run `ProcessMergeRequestsJob.perform_now(victim_stack)` and assert `fake_api.merge_pull_request` (scoped to `victim/repo`) was invoked — proving the victim-repo-scoped credential executed a merge triggered only by the attacker-org's webhook.
6. Both assertions passing demonstrates the binding "webhook org == org of mutated commit/merge" is broken.

    def add_status
      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def merge!
      raise InvalidTransition unless pending?

      raise NotReady if not_mergeable_yet?

      stack.github_api.merge_pull_request(
        stack.github_repo_name,
        number,
        merge_message,
        sha: head.sha,
        commit_message: 'Merged by Shipit',
        merge_method: stack.merge_method
      )
      begin
        if stack.github_api.pull_requests(stack.github_repo_name, base: branch).empty?
          stack.github_api.delete_branch(stack.github_repo_name, branch)
        end
      rescue Octokit::UnprocessableEntity
        # branch was already deleted somehow
      end
      complete!
      true
    rescue Octokit::MethodNotAllowed # merge conflict
      reject!('merge_conflict')
      false
    rescue Octokit::Conflict # shas didn't match, PR was updated.
      raise NotReady
    end
