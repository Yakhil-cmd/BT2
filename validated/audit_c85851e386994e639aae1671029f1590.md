### Title
Cross-organization webhook confusion — signature is verified against the org derived from `repository.owner.login`, but handlers act on the org/repo derived from `repository.full_name` in the same untrusted body - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate the HMAC based on `repository_owner`, a value read straight out of the untrusted JSON body (`params.dig('repository', 'owner', 'login')` or the `organization.login` fallback). All handlers (e.g. `PushHandler`, `StatusHandler`, `CheckSuiteHandler`, PR handlers) then resolve which `Repository`/`Stack`/`Commit` to act on using a *different* field from that same body: `payload.dig('repository', 'full_name')` in `Handler#repository_name`. Nothing ties these two fields together, so the organization whose secret authenticated the request is never checked against the organization that is actually written to.

### Finding Description
- `verify_signature` in [1](#0-0)  computes `github_app = Shipit.github(organization: repository_owner)` and validates the HMAC using that org's `webhook_secret`, where `repository_owner` comes from the request body itself: [2](#0-1) .
- The actual signature check is delegated to `GitHubApp#verify_webhook_signature`, which HMACs the raw body with the org-specific secret: [3](#0-2) .
- Every handler resolves the target `Repository`/`Stack` from a separate field in the same body, `repository.full_name`, via `Handler#repository_name` / `Handler#stacks`: [4](#0-3) , then `Repository.from_github_repo_name` looks up by `owner/name` split out of that string: [5](#0-4) .
- In a legitimate GitHub-generated webhook, `repository.owner.login` and `repository.full_name` always describe the same repository, so they can never diverge. But Shipit supports multi-tenant configuration where each organization has its own independently-configured `webhook_secret` (as shown in `config/secrets.development.shopify.yml`) [6](#0-5) . An organization owner who legitimately controls their own GitHub App/webhook configuration in this multi-tenant Shipit instance knows their own org's `webhook_secret` and can freely craft an arbitrary JSON body, sign it with that known secret, and set `repository.owner.login` = their own org (to pass `verify_signature`) while setting `repository.full_name` = `"other-org/other-repo"` (to make the handler act on a stack belonging to a different tenant whose real webhook secret they never had).

The equality that should hold but doesn't is:
`organization whose webhook_secret authenticated the request == organization owning the repository the handler writes to`

Before the attack: each org's webhook traffic can only affect that org's own repositories, because only the org that owns a stack knows the secret needed to forge events for it.
After the attack: an attacker holding secret for org A can forge webhook events (`push`, `status`, `check_suite`, PR events, etc.) that are processed as if they targeted org B's stacks, since only `repository.full_name` — not `repository.owner.login` — governs which `Stack`/`Commit` records the handler code manipulates.

### Impact Explanation
Concretely, `StatusHandler#process` [7](#0-6)  creates a commit status for any `Commit` whose `sha` matches, purely by sha, with no repository/org check at all inside `create_status_from_github!` beyond the `sha` lookup — meaning a forged status event from one org's secret can flip CI/deploy-gating statuses on another org's commits. `PushHandler#process` [8](#0-7)  can trigger `stack.sync_github` against a victim org's stack. Depending on Shipit's `continuous_delivery`/auto-deploy configuration (`app/models/shipit/stack.rb`), a forged "green" status on a victim commit could satisfy deployability checks and contribute to an unauthorized deploy being scheduled — I was not able to fully trace the continuous-deployment trigger chain in the remaining budget to confirm this end-to-end, so this specific escalation to "unauthorized deploy" is plausible but not fully proven from the code I reviewed.

### Likelihood Explanation
This requires the Shipit deployment to be configured for multiple GitHub organizations, each with an independently-set `webhook_secret` (a documented, supported configuration per `config/secrets.development.shopify.yml` and `docs/setup.md`), and requires the attacker to be a legitimate operator/owner of one such tenant organization (not a random unauthenticated internet user). This is a real trust boundary inside the same Shipit deployment, but it is a comparatively narrow scenario (multi-tenant single instance, attacker is one of the trusted-but-mutually-distrusting tenant admins).

### Recommendation
In `Handler#repository_name` / `Handler#stacks`, or in `WebhooksController#verify_signature`, enforce that the organization used to select and verify the webhook secret (`repository_owner`) is the same organization present in `repository.full_name` before processing the event; reject the request otherwise.

### Proof of Concept
1. Deploy Shipit in multi-tenant mode with two configured GitHub organizations, `org-a` (attacker-controlled, attacker knows `webhook_secret_a`) and `org-b` (victim, `webhook_secret_b` unknown to attacker), per `config/secrets.development.shopify.yml`.
2. Attacker crafts a `push` (or `status`) JSON body:
   ```json
   {
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
     "ref": "refs/heads/master",
     "after": "<attacker-chosen sha>"
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(webhook_secret_a, body)>` and POSTs to `/webhooks` with `X-Github-Event: push`.
4. `verify_signature` resolves `Shipit.github(organization: "org-a")` and successfully verifies the signature using `webhook_secret_a` [9](#0-8) .
5. `PushHandler` resolves the target stacks via `repository.full_name = "org-b/victim-repo"` [10](#0-9) , causing `org-b`'s stacks to be synced/acted on as a result of a forgery authenticated only by `org-a`'s secret.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",

      ].join(' '))
    end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
