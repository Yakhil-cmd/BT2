### Title
Cross-organization forged commit status enables unauthorized deploy trigger via webhook - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to validate a webhook against using the `repository.owner.login` (or `organization.login`) field from the untrusted request body, then dispatches the *entire* payload to event handlers [1](#0-0) [2](#0-1) . Shipit supports hosting multiple GitHub organizations, each with its own independent App credentials and `webhook_secret` [3](#0-2) [4](#0-3) . Once the signature check passes for *any* configured organization, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` runs unrestricted with the full body [5](#0-4) . Critically, `StatusHandler#process` looks up commits solely by SHA, globally, with no scoping to the repository/org whose secret produced the valid signature: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [6](#0-5) .

### Finding Description
The binding that should hold is: `organization whose secret authenticated the signature == organization owning the repository/commit being mutated`. This binding is broken.

`verify_signature` derives the org used to pick the verifying `GitHubApp`/secret entirely from attacker-controlled JSON in the payload (`repository.owner.login` or `organization.login`) [1](#0-0) [2](#0-1) . `verify_webhook_signature` only confirms the HMAC matches *that selected org's* secret over the raw body [7](#0-6) ; it never confirms that the org, whose secret produced the signature, actually owns the resource acted upon later in the payload.

For the `status` event, the handler that then executes ignores the repository field entirely and updates commit status purely by matching `sha` across the whole database: [8](#0-7) . Unlike `PushHandler`/`CheckSuiteHandler`, which scope through `Handler#stacks` (which does look up by `repository.full_name`) [9](#0-8) , `StatusHandler` performs no such scoping at all.

This means an operator that legitimately controls one configured organization (e.g., `OrgOne` in a multi-org Shipit deployment) — and thus knows/derives their own valid `webhook_secret` — can sign a payload with `repository.owner.login` set to their own org (so the signature check passes against their own secret) while setting `sha` to an arbitrary commit SHA belonging to a *different* organization's stack, along with `state: "success"`. `StatusHandler` finds and updates that commit regardless of which org it belongs to [6](#0-5) .

Updated statuses feed directly into deploy gating: `Commit#deployable?` requires `success?` (derived from the injected status) [10](#0-9) , and `Commit#schedule_continuous_delivery` schedules a `ContinuousDeliveryJob` once `deployable? && stack.continuous_deployment? && stack.deployable?` is satisfied [11](#0-10) , which in turn calls `stack.trigger_continuous_delivery` [12](#0-11) . Forging a "success" status on the latest commit of a stack with continuous deployment enabled can therefore cause an unauthorized deploy of a repository/org that the attacker's own credentials were never authorized for.

### Impact Explanation
This crosses a credential/organization boundary: possession of a legitimate webhook secret for org A is used to mutate CI/commit state belonging to org B, and that mutated state can gate an actual deploy pipeline (`ContinuousDeliveryJob` → `stack.trigger_continuous_delivery`). This matches the Critical category "unauthorized deploy" defined in the rules, since it can cause a stack to deploy code without any valid signal from the org that actually owns that stack/repository.

### Likelihood Explanation
Exploitability requires the attacker to be an operator/administrator of at least one org configured in a multi-org Shipit deployment (a supported, documented configuration [13](#0-12) ), and requires the target stack to have `continuous_deployment` enabled with the attacker guessing/knowing a valid commit SHA for the victim's stack (SHAs are often disclosed publicly via GitHub, PRs, CI logs, etc., so this is a realistic condition rather than a purely theoretical one). This is a meaningfully lower bar than compromising the victim org's own GitHub App/webhook secret.

### Recommendation
`WebhooksController#verify_signature` and each `Handler` should enforce that the organization whose secret validated the signature matches the organization that owns the repository/stack/commit being mutated. Concretely: (1) after verifying the signature for `repository_owner`, propagate that verified owner into the handler dispatch and require handlers (especially `StatusHandler` and `CheckSuiteHandler` if they don't already scope) to filter records by both the payload's `repository.full_name` (or `owner`) and the org used to validate the signature; (2) explicitly scope `StatusHandler#process` to commits belonging to a stack whose repository owner equals `repository_owner`, e.g. via `stacks` (like `PushHandler`) instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Deploy Shipit in multi-org mode with orgs `OrgOne` and `OrgVictim`, each with distinct `webhook_secret`s (per `docs/setup.md`'s "Using Multiple Github Applications" section) [13](#0-12) .
2. Attacker controls `OrgOne`'s webhook secret (e.g., is an admin of that org's GitHub App installation).
3. Attacker crafts a `status` event JSON body:
```json
{
  "sha": "<victim commit sha belonging to OrgVictim/some-repo>",
  "state": "success",
  "repository": { "owner": { "login": "OrgOne" } }
}
```
4. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(OrgOne_webhook_secret, raw_body)>` and POSTs to `/github_hook` (or engine-mounted webhook endpoint) with `X-Github-Event: status`.
5. `verify_signature` resolves `repository_owner` = `"OrgOne"`, fetches `Shipit.github(organization: "OrgOne")`, and successfully verifies the signature using `OrgOne`'s own secret [1](#0-0) .
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of org — and calls `create_status_from_github!`, setting a "success" status [6](#0-5) .
7. If the victim stack has `continuous_deployment` enabled and is otherwise unoccupied, `Commit#schedule_continuous_delivery` schedules `ContinuousDeliveryJob`, which calls `stack.trigger_continuous_delivery`, deploying the victim's stack without any authorization from `OrgVictim`.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

For example:

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
