### Title
Cross-repository Commit status write via unscoped sha lookup enables unauthorized continuous deployment - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the target `Commit` purely by `sha`, with no scoping to the repository/stack that the verified webhook actually belongs to, unlike sibling handlers such as `CheckSuiteHandler` which scope through `stacks.where(...)`. An attacker who owns an unrelated, Shipit-trusted repository can reproduce a victim's exact git commit object (same tree/parents/author/committer/message/timestamps) in their own repo, obtain the identical SHA, and have their own genuinely-authenticated CI post a `status` webhook that Shipit will apply to the victim's `Commit` row in a completely different stack, potentially triggering an unauthorized deploy.

### Finding Description
The broken binding is: **the organization/repository whose webhook secret verified the request == the repository whose `Commit` row is mutated by that request.** This holds for `PushHandler` and `CheckSuiteHandler` (both scope lookups via `Handler#stacks`, which filters by `Repository.from_github_repo_name(repository_name)` [1](#0-0) ), and for `CheckSuiteHandler` specifically, which does `stacks.where(branch: ...).each { |stack| stack.commits.where(sha: ...) }` [2](#0-1) .

`StatusHandler#process`, however, breaks this binding:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [3](#0-2) 

This queries the global `Commit` table by `sha` alone, with no `repository_name`/`stacks` scoping, even though the base `Handler` class exposes exactly that scoping helper and other handlers use it.

`WebhooksController#verify_signature` authenticates the request only against the organization named in the payload's `repository.owner.login` (or `organization.login`), via `Shipit.github(organization: repository_owner)` and `github_app.verify_webhook_signature` [4](#0-3) . This authenticates "a request signed by org X's webhook secret," not "a request describing repository Y." Because `StatusHandler#process` never re-checks that the `sha` belongs to a commit under the same repository/org that was authenticated, any org whose secret is known (including the attacker's own legitimately-onboarded org/repo) can write a `Status` onto a `Commit` belonging to an entirely different stack/repository, as long as the `sha` values collide.

Exploit flow:
1. Attacker reads the victim's public repo HEAD commit via GitHub's public API (tree, parents, author/committer, timestamps, message) - an unauthenticated read of already-public data.
2. Attacker runs `git commit-tree` with those exact identical inputs in their own repo. Since a git commit's SHA is a hash of that exact byte content, reproducing the identical inputs deterministically reproduces the identical SHA — this is not a hash collision, it is recreating an identical object, which git explicitly guarantees.
3. Attacker pushes this commit to their own repo. Their own CI (or a manual `curl`) sends a `status` webhook to Shipit's `/webhooks` endpoint, with `repository.owner.login` set to the attacker's own (Shipit-trusted) org, signed with that org's real, legitimately-known webhook secret. `verify_signature` passes — no forgery of any secret is needed.
4. `StatusHandler#process` matches `Commit.where(sha: params.sha)` and finds the victim's `Commit` row (under a completely different `Stack`/org), because the query is not scoped to the attacker's repository at all.
5. `commit.create_status_from_github!(params)` creates a `Status` on the victim's commit. Per `commits_test.rb`, successful status creation triggers `schedule_continuous_delivery` via an `after_commit` callback chain, which enqueues `ContinuousDeliveryJob` when `stack.continuous_deployment?` and `commit.deployable?` [5](#0-4) , and `Stack#trigger_continuous_delivery` then calls `trigger_deploy` -> `Deploy.create` for the victim stack [6](#0-5) .

Existing guards fail to catch this because:
- `verify_signature` authenticates the *signing org*, not the *commit's owning repository*, and this handler never cross-checks the two.
- The `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc., not that the target commit's stack matches `payload.dig('repository','full_name')`.
- The `subset` used by `Handler#stacks`/`repository_name` is defined but simply unused by this specific handler.

### Impact Explanation
An attacker who controls any repository already trusted by the Shipit instance (their own account/org, requiring no elevated privilege) can inject a fabricated CI status onto an arbitrary victim's commit in a different stack, purely by SHA collision through content duplication. If the victim stack has `continuous_deployment` enabled and no other blocking gates, this results in an unauthorized `Deploy` being created and run against the victim's production infrastructure — matching "Critical: a payload for one repository mutating another's stack, commit, task or team" / "an unauthorized deploy." The attack is repeatable against any stack/commit whose SHA the attacker can reproduce from public commit metadata, and the blast radius spans all stacks hosted on the same Shipit instance, not just the attacker's own tenant.

### Likelihood Explanation
Preconditions: (1) the attacker must control at least one repository/org already onboarded to the target Shipit instance (i.e., their own webhook secret is legitimately known to them — a normal, low-privilege situation for any user with a Shipit-integrated org/repo, or feasible if Shipit hosts many independent orgs/tenants); (2) the victim stack has `continuous_deployment` on with no `blocking_statuses`/other gates; (3) the victim's target commit's git object (tree, parents, author/committer, message, timestamps) is fully reconstructible, which is true for any public commit. Reproducing the identical SHA via `git commit-tree` costs nothing and is 100% reliable, not probabilistic. This is a low-cost, repeatable, cross-tenant exploit once the above preconditions hold.

### Recommendation
Scope `StatusHandler#process` the same way `PushHandler`/`CheckSuiteHandler` do: restrict the `Commit` lookup to commits belonging to `stacks` derived from `payload.dig('repository', 'full_name')`, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, so a webhook authenticated for organization/repo X can never mutate a `Commit` belonging to a different repository's stack.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`):
1. Create two `Stack` fixtures, `victim_stack` (repo `victim/repo`, `continuous_deployment: true`, no blocking statuses) and `attacker_stack` (repo `attacker/repo`).
2. Create two `Commit` fixtures sharing the identical `sha` value ("colliding" sha, representing the reproduced git object), one under each stack: `victim_commit` (undeployed HEAD of `victim_stack`), `attacker_commit` (under `attacker_stack`).
3. Build a `status` webhook payload with `sha: shared_sha`, `state: 'success'`, and `repository: { full_name: 'attacker/repo', owner: { login: 'attacker' } }`.
4. Stub `Shipit.github(organization: 'attacker').verify_webhook_signature` to return `true` (simulating attacker's own legitimately-known secret — no victim secret required).
5. POST to `/webhooks` with `X-Github-Event: status`.
6. Assert: **broken binding demonstrated** — `victim_commit.reload.statuses.count` increased by 1 (status written despite the request only authenticating `attacker/repo`), and `Stack#trigger_continuous_delivery`/`Deploy.create` is invoked for `victim_stack` (e.g. via `assert_enqueued_with(job: ContinuousDeliveryJob, args: [victim_stack])` and `assert_difference('victim_stack.deploys.count', 1)`), all triggered solely from a webhook signed for `attacker/repo`.
7. Assert the equality that should have held but didn't: `payload_authenticated_repository ("attacker/repo") == mutated_commit.stack.repository.full_name ("victim/repo")` is `false`, proving the cross-tenant write.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
