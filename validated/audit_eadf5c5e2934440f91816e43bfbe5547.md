### Title
Stale stored `Account.owner` lets a seller keep acting after transferring the position NFT — ([File: contracts/controller/src/account.rs])

### Summary
CVE-2018-1334 is an impersonation class: a party is accepted as another user because identity is not bound to fresh authorization. The analog lives in the split between the transferable position NFT and the `owner` field frozen into `Account` at mint time. `create_account_with` mints the NFT to `owner` and stores `owner` inside the `Account` struct (`contracts/controller/src/account.rs:62-70`). Every state-changing entrypoint — `withdraw`, `borrow`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `flash_position` on an existing account, `migrate_from_blend` — authorizes via `require_owner_or_delegate`/`is_owner_or_delegate`, which compare `caller` to that stored `account.owner`, not to `owner_of(token_id)` on the NFT (`account.rs:115-140`, `supply.rs:147-150`, `debt.rs:40-47`). Meanwhile the NFT implements the stock OZ `NonFungibleToken`/`Enumerable` interface with unrestricted `transfer`/`approve` (`position-nft/src/contract.rs:131-173`), and nothing resyncs `account.owner` on transfer.

### Finding Description
1. Alice creates an account via `supply`; the NFT is minted to Alice and `Account.owner = Alice` is persisted.
2. Alice transfers token `id` to Bob (ordinary NFT transfer — sale, gift, or escrow), which succeeds because `PositionNft` exposes the full OZ enumerable interface and burn/mint are the only controller-gated calls.
3. `Account.owner` still equals Alice. `borrow`, `withdraw`, and every strategy entrypoint continue to authorize Alice, while Bob — the `owner_of` the NFT — fails `require_owner_or_delegate` because `caller != account.owner` and he was never registered under Alice's delegate list (delegates are keyed `(account_id, owner)` in `account.rs:126`).
4. Alice calls `withdraw(caller=Alice, account_id, withdrawals, to=Some(Alice))`. `require_owner_or_delegate` passes on the stale owner, `require_external_recipient` only checks the recipient isn't a protocol contract, and the pool pays Alice (`supply.rs:140-168`). Bob, the rightful owner per the NFT contract's own invariant "the token owner is the account owner" (`contract.rs:1-3`), cannot withdraw, borrow, add/remove delegates, or liquidate-defensively — he holds a token conferring no authority while the seller retains full authority.

### Impact Explanation
Theft of user funds: any buyer of a position NFT (or recipient of an airdropped/transferred one) can have the entire collateral drained by the previous owner the moment after transfer settles, at zero cost and with no governance involvement. It also inverts the intended ownership model — documentation states the NFT *is* account ownership, so integrators and marketplaces will price/transfer positions on that assumption. Reachable by a single unprivileged address via `transfer` on the NFT plus `withdraw`/`borrow` on the controller.

### Likelihood Explanation
Deterministic whenever an NFT changes hands. No price manipulation, oracle, or timing dependency is needed: the attacker is simply the former owner exercising retained authorization. Requires a second party to value the NFT (or the attacker can buy a listed position NFT cheaply if the seller is unaware control persists — either direction of the asymmetry is exploitable).

### Recommendation
Bind controller authorization to live NFT ownership. Either query `owner_of(account_id)` in `is_owner_or_delegate`/`require_account_owner` instead of the stored `account.owner`, or disallow NFT `transfer`/`approve` entirely if positions are meant to be soulbound (the `Credit` seize path already gives liquidation-time reassignment semantics). If transfers remain supported, also migrate or re-key delegate grants on ownership change so the previous owner's managers cannot retain delegated authority.

### Proof of Concept
1. Alice: `supply(account_id=0, spoke_id=1, [(hub_asset, 1000e7)])` → account `1`, NFT `1` minted to Alice; `Account.owner = Alice`.
2. Alice: `position_nft.transfer(from=Alice, to=Bob, token_id=1)` → succeeds; `owner_of(1) = Bob`; `Account.owner` still Alice.
3. Alice: `withdraw(account_id=1, withdrawals=[(hub_asset, 0)], to=Alice)` → `require_owner_or_delegate` passes against the stale stored owner; pool pays Alice the full collateral.
4. Bob: `withdraw(account_id=1, ...)` → reverts `NotAuthorized` despite `owner_of(1) = Bob`. Bob holds a worthless token; Alice has the collateral and the sale proceeds.

Uncertainty noted: `storage::account_owner` (used by `require_account_owner` for `renew_account`/`add_delegate`) was not inspected; if it reads the NFT, the auth model is additionally inconsistent between renewal/delegation (new owner) and value-moving operations (old owner).
