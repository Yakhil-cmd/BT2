### Title
Spoofable `X-Shipit-User` header lets an API-token holder forge deploy health attestations - (File: app/controllers/shipit/api/base_controller.rb)

### Summary
`Api::BaseController#identify_user` derives `current_user` purely from the client-supplied `X-Shipit-User` header, looking up any existing `User` by login with no cryptographic or relational binding to the authenticated `ApiClient`. `Api::ReleaseStatusesController#create` uses that unverified `current_user` as the `user:` attributed to `Deploy#report_healthy!`/`report_faulty!`, so any holder of a token scoped only with `deploy:stack` can attribute a release-health verdict to an arbitrary existing Shipit user (e.g., a maintainer), even though that user never made the call.

### Finding Description
The claimed binding is: `current_api_client.check_permissions!(operation, scope)` (in `require_permission!`, `app/controllers/shipit/api/base_controller.rb:82-84`) should equal "the acting identity is authorized to perform the operation," but it only equals "the token that made the HTTP request has the `deploy:stack` permission." The acting identity, `current_user`, is derived independently and unauthenticated: [1](#0-0) 

`identify_user` does a case-insensitive `User` lookup by the raw `X-Shipit-User` header value with no signature, no membership check against `Shipit.github_teams`, and no relation to `current_api_client.creator` or `current_api_client.stack_id`.

`ReleaseStatusesController#create` then passes this attacker-controlled `current_user` straight into the model: [2](#0-1) 

`Deploy#report_healthy!` persists `user:` into the `CommitDeployment`/`ReleaseStatus` record and generates a description quoting the spoofed login (`"@#{user.login} signaled this release as healthy."`): [3](#0-2) [4](#0-3) 

`ApiClient#check_permissions!` only checks the `permissions` array stored on the `ApiClient` record itself — it never touches `current_user` at all: [5](#0-4) 

Attacker request: with a valid token scoped to stack A holding `deploy:stack` (which the attacker could legitimately hold, e.g., as a low-trust CI integration), POST `/api/stacks/A/deploys/:deploy_id/release_statuses` with body `{"status":"success"}` and header `X-Shipit-User: victim-login`. `report_healthy!` transitions the deploy to `complete!` (if pending validation) and records a `ReleaseStatus`/attestation as if `victim-login` approved it. Existing guards do not stop this: `authenticate_api_client` only validates the bearer token; `require_permission!` only checks the client's `permissions` subset; there is no `User#authorized?`/team-membership check anywhere in this call path binding `current_user` to any real authentication event.

### Impact Explanation
The attacker can attribute a fabricated `success`/`failure` release-health verdict to any existing Shipit user login of their choosing, on any stack the attacker's token is scoped to (or any stack, if using a token without `stack_id` restriction). Because `report_healthy!`/`report_faulty!` drive `complete!`/`mark_faulty!` transitions and `after_transition to: :success` callbacks (`schedule_merges`, `schedule_continuous_delivery`), this forged attestation can gate the merge queue (`allows_merges?`, `app/models/shipit/stack.rb`) and continuous-deployment logic, making it an unauthorized deploy-outcome/merge decision attributed to a forged identity — this is a Critical-severity unauthorized-deploy/merge condition. It is repeatable for every deploy and every user login the attacker chooses to spoof, within the token's stack scope.

### Likelihood Explanation
The attacker needs only a valid `ApiClient` token with `deploy:stack` permission (a normal, low-privilege scope for CI-style integrations) and knowledge of an existing victim login — both plausible/observable in typical Shipit deployments (logins are visible in stack UI/GitHub). No secrets (`api_clients_secret`, `secret_key_base`, webhook secret) are needed to spoof `X-Shipit-User`; it is a plain, unauthenticated header. This makes the attack low-cost and fully repeatable by anyone who legitimately holds such a scoped token but should not be able to impersonate other users.

### Recommendation
Do not trust `X-Shipit-User` as an identity assertion for actions that persist attribution or affect authorization/state (like release-status/health reporting). Either remove the header-based identity spoofing capability for this endpoint (always use `current_api_client.creator` or an `AnonymousUser`/service identity), or require that the API client independently prove out-of-band that the named user authorized the action (e.g., only allow `X-Shipit-User` impersonation for `ApiClient`s explicitly flagged as trusted integrations, and verify the named user is actually associated with the calling system, not merely present in the `users` table).

### Proof of Concept
```ruby
# test/controllers/shipit/api/release_statuses_controller_test.rb (conceptual)
test "an api client can forge release status attribution via X-Shipit-User" do
  attacker_client = shipit_api_clients(:cyclid) # token scoped to stack A, permissions: %w[deploy:stack]
  victim = shipit_users(:walrus) # a maintainer of stack A, never made this call

  deploy = shipit_deploys(:shipit_pending)
  refute_equal attacker_client.creator_id, victim.id

  post "/api/stacks/#{deploy.stack.to_param}/deploys/#{deploy.id}/release_statuses",
       params: { status: 'success' }.to_json,
       headers: {
         'Authorization' => "Basic #{Base64.strict_encode64(attacker_client.authentication_token + '--x')}",
         'X-Shipit-User' => victim.login,
         'Content-Type' => 'application/json'
       }

  assert_response :created
  release_status = deploy.until_commit.reload.last_release_status
  assert_equal victim.id, release_status.user_id          # forged identity persisted
  refute_equal attacker_client.creator_id, release_status.user_id  # actual caller differs
end
```
This demonstrates `Deploy#report_healthy!` records `user_id == victim.id` while the authenticated `ApiClient#creator_id` differs, confirming the identity used for authorization (the API client) is not the identity recorded as having performed the action.
