### Title
Stack-scoped API client tokens can read CI status of any stack via CCMenu, bypassing `stack_id` authorization scope - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController#stack` fetches the target stack with `Stack.from_param!(params[:stack_id])`, bypassing the tenant-scoping helper `stack`/`stacks` defined in `Shipit::Api::BaseController`, which restricts lookups to `current_api_client.stack_id` when the authenticated `ApiClient` is scoped to a single stack. [1](#0-0) [2](#0-1) 

### Finding Description
`ApiClient` records can be scoped to a single stack via the `stack_id` column (`belongs_to :stack, optional: true`), and the base API controller enforces this scope by filtering candidate stacks through `stacks` before resolving the `stack_id` param: `current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all`. [3](#0-2) [2](#0-1) 

`Api::CCMenuController` overrides `stack` to look up `Stack.from_param!(params[:stack_id])` directly on the unfiltered `Stack` relation, dropping the `stacks` scoping entirely, while still relying on `require_permission :read, :stack`, which only checks the coarse-grained permission string via `ApiClient#check_permissions!` and never validates that the requested `stack_id` matches the client's bound `stack_id`. [4](#0-3) [5](#0-4) [6](#0-5) 

This is the same class of bug as the HackerOne report: one identifier (the authenticated client's authorized `stack_id`) is verified, but a different, attacker-supplied identifier (`params[:stack_id]`) is the one actually acted upon, breaking the binding "a stack a token authorizes == a stack it touches." A test fixture (`here_come_the_walrus`) demonstrates that stack-scoped `ApiClient` tokens are a real, supported configuration used elsewhere to restrict visibility to exactly one stack. [7](#0-6) 

The CCMenu endpoint additionally accepts the token via a query-string parameter rather than only via Basic Auth, which is how such stack-scoped tokens are meant to be embedded in CI-status URLs (e.g. `CCMenuUrlController`), making them easy to obtain/observe and reuse against other stacks. [8](#0-7) [9](#0-8) 

### Impact Explanation
A holder of a stack-scoped `read:stack` `ApiClient` token — intended by design to only ever see one specific stack's build/deploy status — can instead read the CI status, last build result, deploy label and web URL of any stack in the installation by changing the `stack_id` query parameter. This is unauthenticated read of stack state beyond the token's intended scope, matching the "High: unauthenticated read of stack state" impact category, since it crosses a repository/stack authorization boundary the token was explicitly restricted to.

### Likelihood Explanation
Any party in possession of a legitimate, narrowly-scoped CCMenu token (which is routinely shared/embedded in CI dashboard URLs, per `CCMenuUrlController`) can exploit this with a single parameter change and no additional privileges — high likelihood given the token is designed to be portable and low-sensitivity from the token issuer's perspective.

### Recommendation
In `Api::CCMenuController`, remove the private `stack` override and use the inherited `stacks`/`stack` helpers from `Api::BaseController` so lookups are constrained by `current_api_client.stack_id` when the client is scoped, consistent with every other API controller (e.g. `Api::StacksController`).

### Proof of Concept
1. As an admin, create a stack-scoped `ApiClient` with `permissions: ['read:stack']` and `stack_id` set to Stack A (mirrors fixture `here_come_the_walrus`).
2. Use that client's `authentication_token` to call `GET /api/stacks/:stack_id/ccmenu.xml` (or the `token` query-string variant) with `stack_id` set to Stack B's identifier instead of Stack A.
3. Observe that `Api::CCMenuController#stack` resolves Stack B via `Stack.from_param!(params[:stack_id])` and returns Stack B's deploy/CI status, even though the client's token is only authorized for Stack A. [10](#0-9)
