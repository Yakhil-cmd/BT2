## Title
Cross-tenant status forgery via unscoped `Commit.where(sha:)` in `StatusHandler#process` — ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

## Summary
`Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits purely `Commit.where(sha: params.sha)` with no scoping to the repository/stack the webhook was authenticated for, then calls `create_status_from_github!` on every match. `Commit#sha` is only indexed/scoped per `(stack_id, sha)`, not globally unique, so a signed webhook that is legitimately authenticated for one organization's GitHub App can write a `Status` onto a `Commit` belonging to a completely different stack/repository, as long as that commit's sha happens to collide.

## Finding Description
The broken binding, stated explicitly: `Commit#stack.repository` (the repository whose merge/deploy readiness is being decided by the resulting `Status`) should equal `params.dig('repository','owner','login')` / the GitHub App organization that `WebhooksController#verify_signature` authenticated the request against. Instead, `StatusHandler#process` enforces no such equality at all: [1](#0-0) 

`verify_signature` in `WebhooksController` only proves that the raw payload was HMAC-signed with the webhook secret configured for `repository_owner` as declared in the *attacker-controlled JSON payload* — it does not constrain which `Commit` rows the handler is allowed to mutate: [2](#0-1) 

In a multi-tenant Shipit deployment (explicitly supported and documented, e.g. `test/dummy/config/secrets_double_github_app.yml`, docs/setup.md "Using Multiple Github Applications"), each onboarded GitHub organization has its own `GitHubApp` config and its own `webhook_secret`: [3](#0-2) 

An attacker who is a legitimate GitHub org owner for one tenant onboarded to the same Shipit instance (e.g. `OrgTwo`) knows their *own* org's webhook secret and can send a correctly-signed `status` event for `repository.owner.login = "OrgTwo"`. The `sha` field, however, is fully attacker-controlled and is never checked against the repository that the signature actually vouches for. Because `Commit` rows are keyed by `(stack_id, sha)` rather than by a global unique sha (confirmed by the dedicated migration/index `20170524104615_index_commits_on_stack_id_and_sha.rb` and schema), the same sha value can legitimately exist as separate `Commit` rows belonging to unrelated stacks/repositories — trivially achievable by copying a public commit from the victim's history into the attacker's own repo/fork.

`Commit#create_status_from_github!` then unconditionally records the forged status via `add_status`, which is the same path that fires `deployable_status`/`commit_status` hooks and schedules merges: [4](#0-3) [5](#0-4) 

None of the existing guards catch this: `verify_signature` validates *that a webhook is genuinely from some tenant*, not *that the sha in the payload belongs to that tenant's repository*; `ExplicitParameters` (`params do ... end` in `StatusHandler`) only validates types/presence, not sha-to-repository ownership; and `Commit.where(sha:)` performs no join against `Stack`/`Repository` to filter by the webhook's originating org.

## Impact Explanation
A tenant of a multi-tenant Shipit installation (unprivileged with respect to any *other* tenant's repository, but a legitimate owner/admin of their own onboarded org/repo) can forge a required CI status (e.g. `state: success`, `context: ci/tests`) onto another tenant's pending `Commit`, satisfying that victim stack's `required_statuses`/CI-gating check and triggering an unauthorized merge or deploy readiness state — a payload from one repository mutating another's commit/stack state, matching the Critical category explicitly listed in scope ("a payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy, rollback or merge"). This is repeatable against any stack in the instance whose pending commit sha the attacker can reproduce (trivial for any historically shared commit, e.g. a common base commit, vendored dependency commit, or a commit copied unmodified from the victim's public history into the attacker's own fork), and the blast radius spans every tenant sharing the same Shipit instance/database, not just repos the attacker has any access to.

## Likelihood Explanation
Preconditions: (1) the Shipit instance is multi-tenant (multiple GitHub orgs onboarded, each with a `webhook_secret` the operator has configured — this is a documented, supported configuration, not a misconfiguration); (2) the attacker owns/administers at least one onboarded org/repo (to legitimately sign their own webhook); (3) the attacker can produce a commit sha identical to one already present as a `Commit` row for the victim's stack (trivial — copy any historic commit from the victim's public repo, since git commit hashes are content-addressed and portable across repos). No secrets, tokens, or victim-side access are required. Given that this only requires normal, legitimate use of the attacker's own tenant credentials plus a copied sha, this is highly feasible and fully repeatable.

## Recommendation
Scope the commit lookup in `StatusHandler#process` (and equivalently in check-run/other sha-keyed webhook handlers) to only the `Stack`(s)/`Repository` that the authenticated webhook's `repository.full_name`/`repository.owner.login` actually corresponds to, e.g. join through `Stack` on `repo_owner`/`repo_name` matching the payload's `repository` object, rather than a bare `Commit.where(sha: params.sha)`. Additionally, consider making `(stack_id, sha)` the only key ever used to resolve a commit for a webhook, and reject/no-op when the payload's repository does not match the commit's owning stack's repository.

## Proof of Concept
minitest plan (functional/model level, no live GitHub, multi-tenant secrets config e.g. `test/dummy/config/secrets_double_github_app.yml`):

1. Set up two tenants, `OrgOne` (victim) and `OrgTwo` (attacker), each with its own `webhook_secret` in `Shipit.secrets.github`.
2. Create `victim_stack` under `OrgOne`, with a pending `victim_commit` (`sha: SHARED_SHA`) and a `shipit.yml`/deploy spec requiring `required_statuses: ['ci/tests']`.
3. Create `attacker_stack` under `OrgTwo` with its own `Commit` row also having `sha: SHARED_SHA` (simulating the attacker copying the victim's historical commit into their own fork).
4. Build a `status` webhook JSON body: `{ sha: SHARED_SHA, state: 'success', context: 'ci/tests', repository: { owner: { login: 'OrgTwo' } } }`, sign it with `OrgTwo`'s webhook secret (`OpenSSL::HMAC.hexdigest('sha1', org_two_secret, body)`).
5. POST to `/webhooks` with header `X-Github-Event: status` and the correct `X-Hub-Signature` for `OrgTwo`.
6. Assert response is `200 OK` (signature accepted for `OrgTwo`).
7. Assert the binding equality fails: `victim_commit.reload.statuses.where(context: 'ci/tests', state: 'success').exists?` is `true`, even though the webhook was never signed by/for `OrgOne` — i.e. `victim_stack.repository != OrgTwo` yet `victim_commit.status.success?` is now true and `required_statuses` are satisfied, demonstrating the merge/deploy-readiness check for `OrgOne`'s commit was influenced entirely by `OrgTwo`'s CI run.
