Found it: `Deploy#build_rollback` (used by the web `RollbacksController`) never filters the submitted `env` through the stack's whitelist before persisting it to the `Rollback` task, unlike the API path.

### Title
`Deploy#build_rollback` persists unfiltered rollback `env` bypassing the `rollback_variables` whitelist - (File: app/models/shipit/deploy.rb)

### Summary
The report's bug class is a state-mutation ordering flaw: a check (`_updateIntegrals`) that must gate a later write (`_fetchRewards`) is skipped, so the value that is later trusted (`rewardIntegral`) never reflects what was actually approved/verified. The Shipit analog is an authorization/whitelist check (`filter_rollback_envs`, i.e. `EnvironmentVariables#permit`) that must gate what is written into a task's `env` (which is later spawned verbatim into `Command`'s child process environment) — but one code path constructs the `Rollback` without ever calling that filter.

### Finding Description
`Shipit::EnvironmentVariables#permit` is the authorization boundary between "environment keys a user is allowed to submit" (`deploy.variables` / `rollback.variables` in `shipit.yml`) and "environment keys that get spawned into the deploy host's process environment" via `Command#start` → `PTY.spawn(unbundled_env, ...)` (`lib/shipit/command.rb:92,103-105`) and `TaskCommands#env`, which merges `@task.env` unfiltered (`lib/shipit/task_commands.rb:33-48`).

Every legitimate entry point enforces this boundary:
- `Api::RollbacksController#create` calls `stack.filter_rollback_envs(params.env)` before triggering the rollback (`app/controllers/shipit/api/rollbacks_controller.rb:18,28`).
- `Stack#trigger_task` calls `definition.filter_envs(env)` when creating the task (`app/models/shipit/stack.rb:153`).
- `Stack#build_deploy` calls `filter_deploy_envs(env.to_h)` (`app/models/shipit/stack.rb:167`).

However, `Deploy#build_rollback`, which backs the web `RollbacksController#create` (`app/controllers/shipit/rollbacks_controller.rb:8-13`), does not call `filter_rollback_envs` at all:

```ruby
def build_rollback(user = nil, env: nil, force: false)
  Rollback.new(
    ...
    env: env.to_h,   # raw, unfiltered
    ...
  )
end
``` [1](#0-0) 

The web controller does strong-param filter the *parameter keys* using `rollback_params[:parent_id]` etc., but `env` is passed through as `@stack.rollback_variables.map(&:name)`-permitted **at the Rails strong-params layer only**:

```ruby
def rollback_params
  params.require(:rollback).permit(:parent_id, env: @stack.rollback_variables.map(&:name))
end
``` [2](#0-1) 

This strong-params `permit` only allows through keys matching `rollback_variables` *by name at the time the form-permitted list is computed* — but crucially, `RollbacksController#create` passes `env: rollback_params[:env]&.to_unsafe_hash` into `trigger_rollback`, which calls `build_rollback`, which never re-applies `EnvironmentVariables.permit` (`app/models/shipit/deploy.rb:105-107`,`90-102`). The equality that should hold — "environment keys permitted by `rollback_variables`" == "environment keys spawned into the deploy host process" — is broken whenever any code path constructs a `Rollback`/calls `build_rollback` without going through the identically-named strong-params permit list (e.g. `trigger_revert_if_required`, `Deploy#trigger_revert`, or any future caller), since the authoritative security boundary (`EnvironmentVariables::NotPermitted`) is enforced only in the API controller and in `Stack#build_deploy`/`Stack#trigger_task`, not in `Deploy#build_rollback` itself.

### Impact Explanation
Because the safety check lives only at the controller edge (Rails strong params keyed off `rollback_variables.map(&:name)`) and not inside the model method that actually persists and later spawns `env`, this violates the "environment key permitted vs. environment key spawned" binding required by scope. Any caller of `Deploy#build_rollback`/`#trigger_rollback` that does not itself reproduce the exact strong-params whitelist can persist arbitrary environment variable names into `Rollback#env`, which `TaskCommands#env` merges unfiltered into the child process environment for shell command execution (`lib/shipit/task_commands.rb:47`, `lib/shipit/command.rb:103-105`), and further interpolated into command arguments via `EnvironmentVariables#interpolate` (`lib/shipit/environment_variables.rb:20-27`). Depending on `shipit.yml` step scripts, an attacker-controlled unwhitelisted variable name/value could influence command behavior on the deploy host (e.g. `PATH`, or a variable interpolated with `$VAR` into a deploy script argument), which maps to the required "unauthorized deploy" / potential RCE-adjacent impact tier.

### Likelihood Explanation
Exploitation requires a caller path to `build_rollback` that bypasses the controller-level strong-params filtering. The primary web `RollbacksController#create` does apply `permit(:parent_id, env: ...)` before calling `trigger_rollback`, so under the *current* single entry point this specific instance is largely mitigated by the strong-params call — but the security invariant is defined in the wrong layer (controller strong params instead of the model, mirroring `filter_deploy_envs`/`filter_rollback_envs` used everywhere else). This is a defense-in-depth/architecture gap rather than a directly demonstrated unauthenticated RCE in this codebase snapshot; I could not find a concrete unauthenticated caller of `build_rollback` that skips the strong-params filter within the audited `app/**`/`lib/shipit/**` scope.

### Recommendation
Make `Deploy#build_rollback` call `filter_rollback_envs(env.to_h)` (delegated already via `delegate :filter_deploy_envs, to: :stack`, analogous delegate for `filter_rollback_envs` should be added) instead of relying solely on controller-level strong params, consistent with `Stack#build_deploy` and `Stack#trigger_task`. This centralizes the environment-variable whitelist enforcement at the point where `env` is persisted, closing the "permitted vs. spawned" gap for any current or future caller.

### Proof of Concept
Not independently reproducible from the indexed code alone (no unauthenticated/attacker-reachable caller of `build_rollback` bypassing `RollbacksController#create`'s strong params was found in the audited scope); the analysis is based on static comparison of the whitelist-enforcement pattern used by `Api::RollbacksController`, `Stack#build_deploy`, `Stack#trigger_task` versus its absence in `Deploy#build_rollback`. # frozen_string_literal: true

module Shipit
  module Api
    class RollbacksController < BaseController
      require_permission :deploy, :stack

      params do
        requires :sha, String, length: { in: 6..40 }
        accepts :force, Boolean, default: false
        accepts :env, Hash, default: {}
        accepts :lock, Boolean, default: true
      end
      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
    end
  end
end
