### Title
Fixed `bounce_fees` Threshold Permanently Traps Sender Funds in an AA With No Refund or State Accounting - ([File: aa_composer.js])

### Summary
Autonomous Agents (AAs) in ocore require a payer to send at least `bounce_fees` (default `MIN_BYTES_BOUNCE_FEE`) worth of bytes/assets to the AA address so that, if the trigger fails, the AA can afford to send back a bounce message with the leftover funds. This is directly analogous to the Flat Money "keeper fee" pattern flagged in the external report: a protocol-mandated minimum fee that a caller must supply for their action to be handled safely. Just as an undercollateralized trader in Flat Money cannot pay the keeper fee and is forced into liquidation with no recourse, an unprivileged unit poster who sends an amount below the AA's `bounce_fees` threshold has those funds permanently and silently absorbed by the AA — with no bounce, no state update, and no way to ever recover them.

### Finding Description
When a trigger unit is processed, `handleTrigger()` computes `bounce_fees` from the AA's template (or `MIN_BYTES_BOUNCE_FEE` by default): [1](#0-0) 

Before evaluating the AA logic, the code enforces that the trigger's outputs must be at least the bounce fee, otherwise it calls `bounce()`: [2](#0-1) 

Inside `bounce()`, if the received bytes are less than `bounce_fees.base`, the function does not send anything back — it simply calls `finish(null)`, silently ending the trigger processing: [3](#0-2) 

Because the trigger's payment output to the AA address is already a valid, mined payment (the outputs are legitimately spent to the AA's address, as with any normal payment unit), the sent bytes become part of the AA address's on-chain balance. However, since the trigger is bounced before `evaluateAA()`/state formula execution ever runs, no `state` message runs and no state variable is updated to record or credit these funds. The result is money that is verifiably part of the AA's balance but that the AA's own oscript logic has no accounting for, and that the original sender has no way to reclaim (there is no generic "refund" or "withdraw arbitrary dust" capability in the protocol).

This exactly mirrors the reported bug class: a fee/threshold requirement that is mandatory for safe execution of an action, but whose absence turns what should be a recoverable/failed operation into an unrecoverable loss for the caller. In Flat Money it's margin vs. keeper+trade fee; in ocore it's trigger-output vs. `bounce_fees`.

There is a client-side helper, `checkAAOutputs()` in `aa_addresses.js`, that warns wallets when composing a payment below `bounce_fees`, but this is opt-in advisory logic used only by wallet UIs, not a network-enforced invariant: [4](#0-3) 

Nothing in unit or AA validation (`aa_validation.js`, `validation.js`) prevents an unprivileged unit poster (or any other AA that programmatically forwards funds, e.g., a chained AA response) from sending less than `bounce_fees` to an AA address — the network happily accepts and finalizes such a unit, and only at AA-trigger-processing time does the fund loss occur.

### Impact Explanation
This causes a concrete, protocol-level AA fund loss: any unprivileged unit poster (or intermediate AA in a call chain forwarding an insufficient amount, e.g. after its own fee deductions) who sends slightly less than the target AA's `bounce_fees` will have those funds permanently stuck at the AA address, untracked by any state variable and unrecoverable by any oscript-driven withdrawal path. This is verified directly by the test suite, where a trigger sending less than `bounce_fees` results in `bounced: true`, `response_unit: null`, `objResponseUnit: null` — i.e., total silent absorption with no refund and no record: [5](#0-4) 

Given that `bounce_fees` can be set by the AA author to any value (and `MIN_BYTES_BOUNCE_FEE` applies by default even when unset), and that this threshold is completely opaque to callers unless they independently inspect the AA's definition or rely on wallet-side heuristics (`checkAAOutputs`), ordinary and chained-AA payments routinely risk falling below the threshold, especially in composed multi-hop AA payments where amounts are computed dynamically (percentages, dynamic fees, etc.) and can accidentally round down below `bounce_fees`.

### Likelihood Explanation
Likelihood is high in practice: any user or bot interacting with an AA without perfectly matching the AA's exact `bounce_fees` requirement (which is not enforced anywhere in unit/AA validation, only advisory in wallet code) triggers this loss path. Complex or chained AAs performing internal transfers (e.g., forwarding partial change, calculated shares, or fees) are especially exposed since arithmetic (rounding, fee deduction) can easily produce an amount just under the threshold.

### Recommendation
- Enforce a network-level (or at minimum a `handleTrigger`-level) invariant that funds below `bounce_fees` are still refunded (minus an actual, dynamically-computed cost of doing so), rather than being unconditionally absorbed with `finish(null)`.
- Alternatively, when the amount is insufficient to safely bounce, credit the shortfall amount to a recoverable state variable (e.g., attributable to the sending address) so the AA (or a follow-up governance/sweep mechanism) can eventually make the sender whole, instead of a bare, permanent, and unaccounted loss.
- Make `checkAAOutputs()`-style validation mandatory (not just advisory) at the protocol/validation layer for any payment message whose sole output(s) go to a known AA address, so units that would trigger an unrecoverable "less than bounce fees" bounce cannot be composed/broadcast in the first place.

### Proof of Concept
1. Deploy an AA with `bounce_fees: { base: 10000 }` (default or explicit), similar to the sample fixtures in the repo: [6](#0-5) 
2. As an unprivileged unit poster, send a payment of `2000` bytes to the AA address (any amount `< 10000`).
3. The trigger is processed by `handleTrigger()`; since `trigger.outputs.base (2000) < bounce_fees.base (10000)`, `bounce()` is invoked and immediately calls `finish(null)` without composing or sending any bounce message: [3](#0-2) 
4. This exact scenario is reproduced by the existing unit test `'less than bounce fees'`, which asserts `bounced: true`, `response_unit: null`, `objResponseUnit: null`, `error: "received bytes are not enough to cover bounce fees"` — confirming no funds are returned and no state changes are recorded: [5](#0-4) 
5. The 2000 bytes remain permanently part of the AA address's UTXO set/balance with no oscript state variable referencing them and no path for the sender (or anyone else) to recover them.

function checkAAOutputs(arrPayments, handleResult) {
	var assocAmounts = {};
	arrPayments.forEach(function (payment) {
		var asset = payment.asset || 'base';
		payment.outputs.forEach(function (output) {
			if (!assocAmounts[output.address])
				assocAmounts[output.address] = {};
			if (!assocAmounts[output.address][asset])
				assocAmounts[output.address][asset] = 0;
			assocAmounts[output.address][asset] += output.amount;
		});
	});
	var arrAddresses = Object.keys(assocAmounts);
	readAADefinitions(arrAddresses, function (err, rows) {
		if (err)
			return handleResult(err);
		if (rows.length === 0)
			return handleResult();
		var arrMissingBounceFees = [];
		rows.forEach(function (row) {
			var arrDefinition = JSON.parse(row.definition);
			var bounce_fees = arrDefinition[1].bounce_fees;
			if (!bounce_fees)
				bounce_fees = { base: constants.MIN_BYTES_BOUNCE_FEE };
			if (!bounce_fees.base)
				bounce_fees.base = constants.MIN_BYTES_BOUNCE_FEE;
			for (var asset in bounce_fees) {
				var amount = assocAmounts[row.address][asset] || 0;
				if (amount < bounce_fees[asset])
					arrMissingBounceFees.push({ address: row.address, asset: asset, missing_amount: bounce_fees[asset] - amount, recommended_amount: bounce_fees[asset] });
			}
		});
		if (arrMissingBounceFees.length === 0)
			return handleResult();
		handleResult(new MissingBounceFeesErrorMessage({ error: "The amounts are less than bounce fees", missing_bounce_fees: arrMissingBounceFees }));
	});
