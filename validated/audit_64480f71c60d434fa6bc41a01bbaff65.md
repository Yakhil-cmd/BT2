### Title
Cross-tenant `Team`/`Membership` mutation via `github_id`-only lookup in `MembershipHandler` bypasses per-organization webhook authentication - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` correctly selects and validates the webhook signature against the GitHub App configured for the organization named in the payload (`Shipit.github(organization: repository_owner)`), but `MembershipHandler#find_or_create_team!` looks up the target `Team` solely by `github_id`, with no check that the found team's `organization` matches the verified `organization.login`. An attacker who controls one configured GitHub organization (and thus legitimately knows that organization's `webhook_secret`) can forge a `membership` webhook, signed correctly for their own org, whose `team.id` collides with the `github_id` of a `Team` row belonging to a completely different configured organization, causing `Membership` records to be created/deleted on that other tenant's team.

### Finding Description
The binding the code is expected to satisfy is:
`Shipit.github(organization: repository_owner)` selecting GitHub App X (verified by X's `webhook_secret`) `==` `Team#organization` of every `Team` row mutated while processing that request.

Trace:
1. `Shipit::WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and verifies the HMAC signature using `Shipit.github(organization: repository_owner).verify_webhook_signature`, per [2](#0-1) [3](#0-2) . This only proves the request was signed with the secret configured for whichever organization login the attacker put in the payload — it does not constrain which `Team` rows the handler is allowed to touch.
2. `MembershipHandler#process` calls `find_or_create_team!`, which does `Team.find_or_create_by!(github_id: params.team.id) { |team| team.github_team = params.team; team.organization = params.organization.login }`, per [4](#0-3) . The `organization:` assignment inside the block only runs when a **new** record is created; if a `Team` with that `github_id` already exists (belonging to any organization), it is returned as-is and mutated (`team.add_member`/`team.members.delete`) regardless of which organization is named in the current, verified payload.
3. `Team#github_id` is a plain integer column with no per-organization scoping (`t.bigint "github_id"` on the `teams` table, indexed globally), per fixtures such as [5](#0-4) .

Exploit: An attacker who administers "attacker-org" (one of the multiple organizations configured in `config/secrets.yml`, hence they legitimately know `attacker-org`'s `webhook_secret` because they configured that GitHub App's webhook themselves) sends `POST /webhooks` with header `X-Github-Event: membership`, body `{"action":"added","organization":{"login":"attacker-org"},"team":{"id":<victim_team_github_id>,"name":"x","slug":"x","url":"https://x"},"member":{"login":"attacker-or-any-login"}}`, signed with `attacker-org`'s `webhook_secret`. `verify_signature` resolves `Shipit.github(organization: "attacker-org")`, verifies successfully, and the request proceeds. `find_or_create_team!` finds the pre-existing `Team` row for the victim organization (matched purely by `github_id`) and `team.add_member(member)` inserts a `Membership` row tying an attacker-controlled user into the victim's team — a record mutation for a tenant that never authenticated this request.

None of the listed guards prevent this: `verify_signature` only authenticates the organization named in the payload, not the organization of records touched later; there is no `ExplicitParameters` cross-check between `params.organization.login` and an existing `Team#organization`; `force_github_authentication`/`User#authorized?` are downstream consumers of the corrupted data, not guards on it.

### Impact Explanation
A successful forged request causes `Shipit::Membership` creation/removal on a `Team` belonging to a different, non-consenting organization, without any credential from that organization. Since `User#authorized?` ( [1](#0-0) ) grants Shipit access based on `teams.where(id: Shipit.github_teams.map(&:id)).exists?`, an attacker able to add an arbitrary (including their own) user to a victim's `Shipit.github_teams`-configured team can escalate that user into authorized Shipit access for the victim's stacks/deploys — matching the "escalation into `Shipit.github_teams` authorization" High-severity category, and constitutes cross-tenant record mutation ("a payload for one repository/organization mutating another's team") which is Critical-severity impact. This is repeatable against any `Team#github_id` the attacker can guess or has observed (GitHub team IDs are sequential/small integers, often visible via public GitHub UI/API to org members), and is not limited to a single victim team per request.

### Likelihood Explanation
Preconditions: Shipit must be configured with multiple GitHub Apps/organizations (explicitly the scoped scenario), and the attacker must legitimately administer at least one of those organizations (so they know its `webhook_secret` — a normal, unprivileged capability for an org owner setting up their own GitHub App integration, not a Shipit secret). The attacker needs only the victim `Team`'s `github_id`, a small integer that is frequently guessable/enumerable and not treated as a secret anywhere in this codebase. No Shipit session, API token, or victim-org secret is required. The attack is a single crafted HTTP POST, fully repeatable and scriptable.

### Recommendation
Scope the `Team` lookup by both `github_id` and the verified organization: e.g. `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and additionally have `MembershipHandler` (or the controller) assert that `params.organization.login` matches the `repository_owner`/verified organization used in `verify_signature`, raising/discarding the webhook on mismatch instead of silently reusing an existing `Team` row from another tenant.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (conceptual addition)
test "membership webhook for org A cannot mutate a team belonging to org B" do
  # Org B's team already exists, created under org B's authentication
  victim_team = shipit_teams(:shopify_developers) # organization: 'shopify', github_id: 1

  # Configure two orgs (as in test/unit/shipit_test.rb multi-app setup)
  # attacker-org has its own webhook_secret, distinct from shopify's

  @request.headers['X-Github-Event'] = 'membership'
  GithubHook.any_instance.stubs(:verify_signature).returns(true) # signature legitimately verifies for attacker-org

  forged_payload = {
    action: 'added',
    organization: { login: 'attacker-org' },       # verified org == attacker-org
    team: { id: victim_team.github_id, name: 'x', slug: 'x', url: 'https://x' }, # collides with victim's github_id
    member: { login: 'attacker-controlled-user' }
  }.to_json

  assert_no_difference -> { Team.count } do
    assert_difference -> { Membership.count }, 1 do
      post :create, body: forged_payload, as: :json
      assert_response :ok
    end
  end

  # BUG: membership was added to shopify's (org B's) team even though
  # only attacker-org's webhook_secret authenticated the request.
  assert_includes victim_team.reload.members.map(&:login), 'attacker-controlled-user'
end
```
Assert on both sides of the binding: `Shipit.github(organization: 'attacker-org')` is what authenticated the request, while `victim_team.organization == 'shopify'` — the mismatch demonstrates the broken binding.
