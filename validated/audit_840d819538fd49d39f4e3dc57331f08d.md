### Title
Cross-tenant status forgery — `StatusHandler#process` writes to any commit matched by `sha` alone, with no binding to the signature-verified `repository_owner` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` only proves that the request was signed with *some* org's `webhook_secret` (`Shipit.github(organization: repository_owner)`), it does not prove that org owns the commit being mutated. `StatusHandler#process` then looks up commits by `sha` alone across the entire database and writes a status to whatever it finds, so any onboarded org can forge a `status` webhook naming its own repo but carrying a `sha` belonging to another tenant's commit, and Shipit will mutate that victim commit.

### Finding Description
The binding that must hold is: `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` succeeding ⇒ `repository_owner == owner_of(stack_of(commit_mutated))`. That binding is never checked.

Trace:
1. `WebhooksController#verify_signature` computes `repository_owner` from `params.dig('repository','owner','login')` [1](#0-0)  and verifies the raw body signature against `Shipit.github(organization: repository_owner)`'s configured `webhook_secret` [2](#0-1) . This only proves "the attacker knows `attacker_org`'s webhook secret and attests `repository.owner.login = attacker_org`" — the rest of the JSON body (including `sha`) is attacker-controlled and never cross-checked against `repository_owner`.
2. `WebhooksController#create` dispatches the full parsed payload to every handler registered for the event, with no repository/stack scoping performed at the controller layer [3](#0-2) .
3. `StatusHandler#process` takes `params.sha` from the (attacker-supplied) payload and does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3)  — the lookup is a global `Commit` query keyed only by `sha`, with no `stack_id`, no repository, and no relation whatsoever to `repository_owner` that was used for signature verification.
4. `Commit#create_status_from_github!` calls `add_status` which creates a `Status` record, updates `commit.status`, and fires `Hook.emit(:commit_status, ...)` / `Hook.emit(:deployable_status, ...)` and can trigger `stack.schedule_merges` [5](#0-4) [6](#0-5)  — i.e. it is a real state mutation with downstream effects on deployability/merging for the *victim's* stack, not the attacker's.

Exploit: attacker registers/owns `attacker_org` (any org with a `webhook_secret` configured in this Shipit instance — this can be a wholly unrelated org onboarded for unrelated reasons). Attacker signs a `status` event payload with `attacker_org`'s secret, sets `repository.owner.login = attacker_org` (so signature verification passes), but sets `sha` to a real commit sha belonging to `victim_org`'s repo (shas are public, visible on GitHub/Shipit UI). `StatusHandler` finds the `Commit` row by that sha (regardless of which stack/org it belongs to) and writes a forged status (e.g. `state: "success"`) onto it.

Existing guards do not catch this: `verify_signature` only authenticates "who signed," never "who is target of this write"; `ExplicitParameters` (`params do ... end` in `StatusHandler`) validates the *shape* of `sha`/`state`/etc. but not their relation to `repository_owner`; there is no `stacks`-scope, `Repository` model check, or handler-level assertion that the resolved `Commit#stack.repository` matches the org that authenticated the request.

### Impact Explanation
A forged/fully-controlled `status` (state, description, target_url, context) is written onto a commit belonging to an org the attacker does not control, purely because the attacker holds a valid `webhook_secret` for *some* other onboarded org. Since `Commit#deployable?`/`blocked?` and continuous-delivery scheduling (`schedule_continuous_delivery`, `stack.schedule_merges`) are driven by commit status, this can flip a victim commit to `success`, potentially unblocking or triggering a deploy/merge for a stack the attacker has no authorization over. This is a payload for one tenant's webhook mutating another tenant's commit/stack state — matching the "Critical: a payload for one repository mutating another's stack/commit/task" category, and demonstrates multi-tenancy is not enforced for the `status` event handler.

### Likelihood Explanation
Preconditions: the attacker's org must have any `webhook_secret` recognized by `Shipit.github`, i.e. the attacker's org must be onboarded to the same Shipit instance (this is explicitly framed by the audit as the only real precondition — no relationship to the victim's org is required). The attacker needs no session, no API token, no knowledge of the victim's secret, and the victim's commit sha is public (visible on GitHub). Cost is a single crafted HTTP POST to `/webhooks` with a valid HMAC computed from the attacker's own secret. This is fully repeatable against any commit whose sha the attacker knows, for any stack tracked by the same Shipit instance.

### Recommendation
In `StatusHandler#process` (and any other sha/repo-driven handler), scope the `Commit` lookup to the repository asserted in the payload and verified at the controller layer, e.g. resolve `Stack`/`Repository` from `repository.full_name` and only update commits under stacks belonging to that repository: `Commit.joins(:stack).where(sha: params.sha, stack: { repository: matched_repository }).each { ... }`. More generally, `WebhooksController` should pass the verified `repository_owner`/`repository.full_name` into the handler dispatch so every handler can assert `commit.stack.repository.owner == repository_owner` (or equivalent) before mutating any record, rather than trusting global `sha`-only lookups.

### Proof of Concept
Minitest integration test plan (under `test/controllers/webhooks_controller_test.rb`, no live GitHub):
1. Configure two orgs in `Shipit.github`/secrets fixtures: `attacker_org` with `webhook_secret: "attacker-secret"` and `victim_org` with `webhook_secret: "victim-secret"`.
2. Create a `Stack` owned by `victim_org` with a `Commit` (`sha: "deadbeef..."`, no existing status).
3. Build a `status` webhook JSON body: `{"sha": "deadbeef...", "state": "success", "repository": {"owner": {"login": "attacker_org"}, "full_name": "attacker_org/some-repo"}}`.
4. Compute `X-Hub-Signature` as `"sha1=" + HMAC-SHA1(body, "attacker-secret")` (i.e. sign only with `attacker_org`'s secret).
5. POST to `/webhooks` with header `X-Github-Event: status` and the above signature.
6. Assert response is `200 OK` (not `422`), then reload the victim `Commit` and assert `commit.status.state == "success"` (or `commit.statuses.last.state == "success"`) — proving that a payload authenticated only via `attacker_org`'s secret mutated a `victim_org` commit.
7. Contrast: assert that no equivalent authorization check exists comparing `repository.owner.login` (`attacker_org`) to the victim commit's `stack.repository` owner, demonstrating the equality `repository_owner == owner_of(stack_of(commit))` is never enforced.

      already_deployed = deployed?

      reload # to get the statuses into the right order (since sorted :desc)

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
