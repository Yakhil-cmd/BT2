### Title
Cross-organization `Team` hijack via `membership` webhook `github_id` lookup grants `Shipit.github_teams` authorization - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` purely by the numeric `params.team.id` from the webhook body, with no check that the authenticating organization (the one whose `webhook_secret` verified the request) actually owns that team. Any organization enrolled in Shipit's multi-tenant `secrets.github` config (i.e., any org with its own valid `webhook_secret`) can send a `membership` webhook naming the numeric GitHub team ID of a *different*, privileged org's team (e.g. one listed in `Shipit.github_teams`) and add an arbitrary existing `User` to it.

### Finding Description
The broken binding: `organization owning webhook_secret that verified the request == organization owning the Team row being mutated`. `WebhooksController#verify_signature` only checks the signature against `Shipit.github(organization: repository_owner)`, where `repository_owner` is `params.dig('organization', 'login')` for membership events [1](#0-0) . This proves the payload was signed by *some* organization's configured secret — the one named in `params.organization.login` — but nothing ties that identity to the `team.id` also present in the same attacker-controlled body.

`MembershipHandler#process` and `#find_or_create_team!` then resolve/create the `Team` solely by `github_id`: [2](#0-1) 

If a `Team` row with that `github_id` already exists (e.g., a team belonging to `Shopify/developers` that is part of `Shipit.github_teams`), `find_or_create_by!(github_id: params.team.id)` returns *that* existing row regardless of which organization actually signed the webhook. The handler never compares `team.organization` to `params.organization.login` (the value used to select the verifying secret). `User.find_or_create_by_login!(params.member.login)` likewise resolves/creates a global `User` by login only, with no org binding [3](#0-2) , so a `login` that matches a real Shipit user (created earlier via any unrelated org's PR/push) is fetched and mutated directly. Finally `team.add_member(member)` [4](#0-3)  persists the `Membership`.

`Shipit.github_teams` is the admin-configured authorization list built from `github.oauth_teams` (the *default* org's OAuth config) [5](#0-4) , and `User#authorized?` checks membership against exactly these `Team` ids [6](#0-5) . Since the `Team` lookup key (`github_id`) is fully attacker-supplied and not scoped to the authenticating org, any org with its own valid `webhook_secret` — a low-privilege precondition already satisfiable by an attacker who legitimately administers *some* org onboarded to a multi-tenant Shipit instance — can target a `Team` belonging to a different org, as long as they know or guess that team's real numeric GitHub `id`.

None of the existing guards prevent this: `verify_signature` validates the signer's identity but not the payload's internal cross-references; `drop_unhandled_event` only filters unknown event types; the `ExplicitParameters` schema in `MembershipHandler` (`requires :team do requires :id, Integer ... end`) validates types/presence only, not organizational ownership; there is no `require_permission!` or org-equality check anywhere in `find_or_create_team!`.

### Impact Explanation
A successful forged webhook silently adds an attacker-chosen (but pre-existing) `User` row to a `Team` that feeds `Shipit.github_teams`, causing `User#authorized?` to flip to `true` for that user — granting access to the Shipit UI/API for stacks gated by team-based authorization, without ever being a real member of the target GitHub org/team. This matches the Critical/High "escalation into `Shipit.github_teams` authorization" category. The attack is repeatable for any team/user combination the attacker can enumerate a numeric GitHub team ID for, and it works across the entire multi-tenant install (any onboarded org can target any other onboarded org's teams), so blast radius spans all tenants sharing one Shipit deployment.

### Likelihood Explanation
Requires: (1) Shipit configured for multiple GitHub organizations (`secrets.github` multi-org schema, as supported by `Shipit.github_app_config`/`github_organizations`), each with its own `webhook_secret`; (2) attacker legitimately controls at least one such onboarded org (able to generate its own webhook secret when the GitHub App was installed there) — this is a normal, non-privileged-to-Shipit precondition, not a leak of another org's secret; (3) attacker can discover/guess the target team's real numeric GitHub `id` (team IDs are visible via the GitHub API/UI for any team the attacker can view, or via prior webhook deliveries); (4) a `User` row with the target login must already exist (trivially created by any prior PR/push webhook from any org). Given these, forging the POST is a single unauthenticated HTTP request with a correctly HMAC-signed body using the attacker's own known secret — fully repeatable and low-cost.

### Recommendation
In `MembershipHandler#find_or_create_team!`, verify that `params.organization.login` (the org that signed the webhook, as used in `verify_signature`) matches the `organization` already stored on the existing `Team` record before reusing it; reject (or scope the lookup by `github_id` AND `organization`) when they diverge. Similarly, consider scoping `Team.find_or_create_by!` to `(github_id:, organization:)` instead of `github_id` alone.

### Proof of Concept
Minitest (extends existing `test/controllers/webhooks_controller_test.rb`):
```ruby
test "membership webhook from org B cannot mutate org A's privileged team" do
  # Setup: team belongs to organization "shopify" and is part of Shipit.github_teams
  privileged_team = shipit_teams(:shopify_developers) # organization: 'shopify'
  Shipit.stubs(:github_teams).returns([privileged_team])

  existing_user = shipit_users(:walrus) # created earlier via an unrelated org's PR

  @request.headers['X-Github-Event'] = 'membership'
  # Signed with orgB's own valid webhook_secret (attacker legitimately controls orgB)
  body = {
    action: 'added',
    team: { id: privileged_team.github_id, name: privileged_team.name, slug: privileged_team.slug, url: privileged_team.api_url },
    organization: { login: 'orgb' }, # attacker's own org, verified by orgb's secret
    member: { login: existing_user.login },
    repository: { owner: { login: 'orgb' } }
  }.to_json

  post :create, body:, as: :json
  assert_response :ok

  assert privileged_team.members.reload.include?(existing_user)
  assert existing_user.reload.authorized?, "user gained Shipit.github_teams authorization via a foreign org's webhook"
end
```
Assert on both sides of the binding: `signing_org = 'orgb'` vs `privileged_team.organization = 'shopify'` — they diverge, yet the write to `privileged_team.members` and the resulting `authorized?` still succeeds, proving the vulnerability.

          team = find_or_create_team!

          when 'removed'

        end
