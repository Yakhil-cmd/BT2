### Title
Deterministic validator panic via stale stake-delegation assertion in partitioned reward distribution - (File: `runtime/src/bank/partitioned_epoch_rewards/distribution.rs`)

### Summary
`Bank::build_updated_stake_reward` asserts that a stake account's *currently* cached delegation plus its calculated reward equals the delegation value that was computed during the earlier, separate reward-*calculation* phase. Because ordinary, fully-authorized stake-program instructions (e.g. `Split`, `Merge`, `Deactivate`) are not blocked from mutating a stake account's delegation between the calculation phase and the later block in which that account's partition is distributed, a stake owner can change their own delegation in that window and cause the assertion to fail, panicking every validator that processes the distribution block. This is the same bug class as the RFPSimpleStrategy bait-and-switch: state is "accepted"/computed at one point in time, held as a stale copy, and then blindly consumed later without re-validating that the underlying account has not been legitimately mutated in the interim by its (unprivileged) owner.

### Finding Description
Partitioned epoch rewards are computed in two temporally separate phases:
1. **Calculation** – `calculate_stake_rewards_and_commissions` (via `recalculate_stake_rewards`, `runtime/src/bank/partitioned_epoch_rewards/calculation.rs:1032-1089`) computes a `PartitionedStakeReward` per stake account, embedding a full `Stake` snapshot (`inflation.stake`) as it existed at calculation time.
2. **Distribution** – spread over multiple subsequent blocks (`distribute_partitioned_epoch_rewards`, `runtime/src/bank/partitioned_epoch_rewards/distribution.rs:81-172`), one partition of accounts is paid out per block via `store_stake_accounts_in_partition` → `build_updated_stake_reward`.

In `build_updated_stake_reward` (`runtime/src/bank/partitioned_epoch_rewards/distribution.rs:240-323`):
```
254: let (mut account, stake_state): (AccountSharedData, StakeStateV2) = stake_account.into();
...
284: } else {
285:     let expected_delegation = stake
286:         .delegation

289:     assert_eq!(
290:         expected_delegation, new_stake.delegation.stake,
291:         "stake reward delegation must be consistent with the updated stake account \
292:          lamport balance"
```

`stake` is the account's **current** delegation freshly fetched from `stakes_cache_accounts` at distribution time (line 249-255), while `new_stake` (`partitioned_stake_reward.inflation.stake`) is the **stale** delegation captured during the earlier calculation phase. The `else` branch (taken whenever `relax_post_exec_min_balance_check`/`adjust_delegations_for_rent` is not active) asserts these must match.

The surrounding comment at `distribution.rs:328-330` explicitly states the invariant depends on an assumption that is not actually enforced in code:
> "Because stake accounts are checked in calculation, and further state mutation prevents by stake-program restrictions, there should never be rewards burned."

A search of `programs/stake/**` found no code that blocks `Split`, `Merge`, `Deactivate`, `Withdraw`, or other authorized stake instructions from executing while `EpochRewardStatus` is `Active` (`runtime/src/bank/partitioned_epoch_rewards/mod.rs:160-177`). Reward distribution spans many blocks (one partition per block, up to `SLOTS_PER_EPOCH/10` blocks per `runtime/src/bank/partitioned_epoch_rewards/mod.rs:1208-1210`), giving a stake owner an ordinary, unprivileged window to submit a normal signed stake instruction that changes their own account's `delegation.stake` after their reward was calculated but before their specific partition block executes.

### Impact Explanation
When the mismatch occurs, `assert_eq!` panics inside `build_updated_stake_reward`, which is invoked deterministically from `store_stake_accounts_in_partition` during normal block/bank processing (not inside a `Result`-returning code path guarded against panics). Because every validator processes the same partitioned distribution logic for the same block deterministically, this panic occurs simultaneously on all validators that reach that block, producing a cluster-wide halt — a transaction-triggered denial of service with no requirement for the attacker to control any privileged component, matching the "transaction-triggered cluster halt" acceptance criterion.

### Likelihood Explanation
Likelihood is contingent on the `relax_post_exec_min_balance_check` feature flag being inactive on the cluster (feature-gated in `feature-set/src/lib.rs`), which selects the vulnerable `else` branch. On networks or test/preview clusters where this feature has not yet been activated, the exploit path requires only:
1. A stake account eligible for rewards in the current epoch.
2. A normal, unprivileged, fully-signed stake instruction (e.g., `Split`) sent by the account's own authority that alters `delegation.stake`, timed to land after reward calculation for that epoch but before the block corresponding to that account's assigned partition index (a multi-block, publicly-computable window based on `hash_rewards_into_partitions`).

No special privileges, front-running races, or leader collusion are needed — only ordinary transaction submission timed within a deterministic, several-block window.

### Recommendation
- Remove reliance on an unenforced assumption; either recompute the reward from the *current* stake state at distribution time (as is already done in the `adjust_delegations_for_rent` branch) instead of asserting equality with the stale calculation-time snapshot, or
- Explicitly detect and gracefully handle (return a recoverable `DistributionError` instead of panicking) any mismatch between current and previously-calculated delegation, or
- Enforce the assumed "stake-program restriction" by actually preventing stake-mutating instructions on accounts that have a pending, un-distributed reward (e.g., checking `EpochRewardStatus` state in the stake program), consistent with the comment's stated intent.

### Proof of Concept
1. Stand up a bank/cluster with `relax_post_exec_min_balance_check` inactive.
2. Create a delegated stake account `S` with owner-authority `A`.
3. Advance to the epoch boundary; `recalculate_stake_rewards`/`calculate_stake_rewards_and_commissions` computes and caches `PartitionedStakeReward` for `S`, embedding `S`'s delegation at that moment.
4. Before the block corresponding to `S`'s partition index is reached (reward distribution spans multiple blocks), have `A` submit an ordinary `Split` (or `Merge`/`Deactivate`) instruction against `S`, changing `delegation.stake`.
5. When the bank reaches `S`'s distribution block, `store_stake_accounts_in_partition` → `build_updated_stake_reward` fetches `S`'s now-changed delegation from `stakes_cache`, computes `expected_delegation = current_delegation + reward`, and compares it against the stale `new_stake.delegation.stake` captured in step 3; the values differ and `assert_eq!` panics deterministically on every validator processing that block.
