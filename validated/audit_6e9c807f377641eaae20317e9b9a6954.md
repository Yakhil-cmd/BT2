### Title
Webhook signature is verified against the payload's `repository.owner.login` / `organization.login`, but event handlers act on the independently-supplied `repository.full_name` — allowing a valid webhook secret for one GitHub org to authenticate forged events for a different org's repositories - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App / webhook secret to validate the HMAC signature against using `repository_owner`, which is read from the unverified JSON body (`params.dig('repository','owner','login')` or `organization.login`). Once the signature check passes, `Shipit::Webhooks::Handlers::Handler#repository_name` (used by every event handler to look up the target `Repository`/`Stack`) reads a *different* field from the very same unverified body: `payload.dig('repository', 'full_name')`. Nothing ties these two fields together, so a party that legitimately controls a webhook secret for organization A can craft a payload whose `repository.owner.login` says "A" (so it authenticates with A's secret) while `repository.full_name` says "B/some-repo" (so the handler acts on organization B's stack).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb` does: [1](#0-0) 
```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(
    request.headers['X-Hub-Signature'],
    request.raw_post
  )
  head(422) unless verified
```
and `repository_owner` is derived purely from the request body: [2](#0-1) 

`Shipit.github(organization: ...)` looks up per-organization config (including `webhook_secret`) as configured in `secrets.yml`, matching the architecture documented in `docs/setup.md` where multiple orgs each have their own `github_app` / `webhook_secret` entry, and `lib/shipit/github_app.rb#verify_webhook_signature` HMACs the *raw* body against that org's secret: [3](#0-2) 

Once `verify_signature` passes, `create` dispatches the parsed JSON to all registered handlers for the event: [4](#0-3) 

Every handler resolves the repository/stack to act on via `Handler#repository_name`, which reads `repository.full_name` — a field entirely independent of the `repository.owner.login` used for authentication: [5](#0-4) 

Concrete handlers such as `PushHandler` (`app/models/shipit/webhooks/handlers/push_handler.rb`), the pull-request handlers (`opened_handler.rb`, `labeled_handler.rb`, `reopened_handler.rb`, `assigned_handler.rb`, `label_capturing_handler.rb`) and the status handler all resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (or `stacks` from `Handler#stacks`) to decide which stack, commit, or pull request to mutate: [6](#0-5) [7](#0-6) 

The binding that should hold is: `organization authenticated by signature == organization that owns the repository being mutated`. Before the attack, for a legitimate GitHub-originated webhook these two values are always consistent because GitHub itself fills in both `repository.owner.login` and `repository.full_name` from the same real repository. After the attack (an attacker directly POSTing a forged JSON body signed with organization A's secret, which the attacker legitimately possesses e.g. as an admin who configured Shipit's GitHub App for org A), `repository.owner.login = "A"` while `repository.full_name = "B/target-repo"`. The signature check only ever inspects `repository.owner.login`/`organization.login` and the raw bytes; it never cross-checks that `full_name`'s owner segment matches. The controller has no code path enforcing that equality anywhere in `app/controllers/shipit/webhooks_controller.rb` or `app/models/shipit/webhooks/handlers/handler.rb`.

### Impact Explanation
This breaks a cross-tenant trust boundary: an entity with legitimate knowledge of a webhook secret for one org configured in a multi-organization Shipit deployment (as explicitly supported by `Shipit.github(organization:)` and documented in `docs/setup.md`'s multi-org `secrets.yml` layout) can forge arbitrary webhook events (`push`, `status`, `pull_request`, `check_suite`, `membership`, etc.) targeting a *different* organization's repositories/stacks that it has no authorization over. Depending on the event, this can:
- Trigger `GithubSyncJob`/`stack.sync_github` on another org's stack (`PushHandler`), causing unwanted syncs/continuous-deployment triggers for stacks belonging to a different, unrelated tenant.
- Inject or manipulate commit `Status` records via the status handler and `Commit#add_status`/`create_release_status!`, directly feeding into `Commit#deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) and thus the deploy gating logic used elsewhere to decide whether a commit can be shipped: [8](#0-7) 
  This can make an unreviewed/failing commit on a different organization's repository appear "deployable", bypassing that org's CI gating for deploys — an unauthorized-deploy-enabling condition.
- Create/modify Teams, Users, and Memberships (`membership` event) or open/close review-stack provisioning for pull requests belonging to another tenant.

This satisfies the escalation-into-authorization / unauthorized-deploy impact bar because the authentication check (which secret validated the request) is decoupled from the authorization decision (which repository/stack is mutated).

### Likelihood Explanation
Exploitation requires the attacker to already know a valid webhook secret configured in Shipit for at least one organization (e.g., they are a legitimate but lower-privileged admin of org A's GitHub App integration, or the secret otherwise leaked/was shared for one tenant). Given that requirement, the exploit itself is trivial: craft one HTTP POST with a custom JSON body where `repository.owner.login` (or top-level `organization.login`) is set to the org whose secret is known, while `repository.full_name` names the victim org's repo, then compute the HMAC-SHA1 over the exact raw bytes using the known secret. No other credential or GitHub access is required. This is realistic specifically in the documented multi-tenant Shipit deployment model where a single Shipit instance serves multiple GitHub organizations with independent secrets, each managed by different admins who are not supposed to have authority over each other's repositories.

### Recommendation
After verifying the HMAC signature, enforce that the identifying field(s) used for authentication and for repository lookup are the same and internally consistent:
- Have `verify_signature` and `repository_name`/`Handler#stacks` both derive the organization strictly from `repository.full_name`'s owner segment (single source of truth), or
- After choosing `github_app` by `repository_owner`, explicitly assert that `payload.dig('repository','full_name')&.split('/')&.first == repository_owner` before dispatching to handlers, rejecting (422) on mismatch.
- Additionally, associate stored webhook secrets/config with the exact repository (not just the org) where possible, so that a secret scoped to org A cannot be used to authenticate payloads referencing org B repositories at all.

### Proof of Concept
1. Assume Shipit is configured (per `docs/setup.md`) with two GitHub orgs, `org-a` (secret `SECRET_A`) and `org-b` (secret `SECRET_B`), each with repos registered as Shipit `Repository`/`Stack`s, e.g. `org-a/repo-a` and `org-b/repo-b`.
2. Attacker (who legitimately possesses `SECRET_A`, e.g., as org-a's GitHub App admin) builds a `push` payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha-that-exists-on-org-b/repo-b>",
  "repository": {
    "full_name": "org-b/repo-b",
    "owner": { "login": "org-a" }
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(SECRET_A, raw_body)>`.
4. POST to `/webhooks` with header `X-Github-Event: push`.
5. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`), which succeeds because the signature was computed with `SECRET_A`.
6. `create` dispatches to `PushHandler`, which resolves `Handler#repository_name` → `"org-b/repo-b"` and syncs/triggers behavior on `org-b`'s stack — despite the request only ever having been authenticated for `org-a`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
