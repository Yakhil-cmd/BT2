### Title
Unbounded iteration over all currently-unstable units in `data_feeds.js`/`in_data_feed` data feed lookup can degrade or deny AA trigger processing - (File: `data_feeds.js`, `formula/evaluation.js`, `definition.js`)

### Summary
`data_feeds.dataFeedExists()` and `readDataFeedValue()` iterate over every unit in `storage.assocUnstableMessages` (i.e., every currently-unstable unit known to the node network-wide) whenever the lookup is performed for an AA (`bAA=true`) context, instead of scoping the search to the oracle address(es) being queried. This code path is reachable by any unprivileged user simply by sending a trigger to (or authoring a unit that references) an AA/definition that uses `in_data_feed`, `data_feed`, or `in data feed`. As the number of concurrently unstable units grows (e.g., during high network load or slow stabilization), the per-call cost of this loop grows linearly with total network-wide unstable-unit count rather than with any bounded per-oracle quantity, mirroring the `recordMintBestAvailableTier` bug class: an in-memory synchronous loop whose size is attacker/environment-influenced and unbounded, executed on the hot path of a very commonly used feature.

### Finding Description
`dataFeedExists()` in `data_feeds.js` does: [1](#0-0) 
for every element of `storage.assocUnstableMessages`, and then, for matching units, iterates all messages of that unit. `readDataFeedValue()` performs the analogous unbounded scan: [2](#0-1) 

These two functions back the `in_data_feed` and `data_feed` formula ops used inside AA oscript, which are evaluated synchronously by any AA whose trigger is processed: [3](#0-2) [4](#0-3) 

and the `in data feed` address/asset-definition authentifier op, reachable by any unit author whose spending condition includes this clause: [5](#0-4) 

Unlike the bounded, per-oracle DB-indexed key-range scans used for the non-AA path (`dataFeedByAddressExists`/`readDataFeedByAddress`, which query a specific key prefix per oracle address), the AA path performs a full in-process `for...in` scan of the global `assocUnstableMessages` map — the set of *all* not-yet-stable units the node currently knows about, regardless of how many oracle addresses are specified in the query. The number of unstable units is not bounded by the AA author or the caller; it grows with overall network throughput and can spike during congestion or before the main chain advances.

### Impact Explanation
Because `in_data_feed`/`data_feed` are extremely common (nearly every oracle-driven AA — price feeds, lottery/game outcomes, DEX AAs — uses them), and because this scan is repeated on **every single trigger** for **every such AA**, a growing unstable-unit set directly and repeatedly increases the CPU time spent per AA execution across the whole node, not just for one "victim" AA. Since AA execution is synchronous and part of unit validation (which gates stabilization and MC advance), sustained growth in the unstable set degrades the node's ability to validate/process new units in time, which can cascade into delayed stabilization for all AAs that rely on data feeds — i.e., AA execution failures/timeouts causing legitimate payments to such AAs to bounce (fund loss to sender, net of bounce fees) and, in the aggregate, contributes to the node being unable to keep up with confirming new units, matching the "network unable to confirm new units" impact class validated for the original finding.

### Likelihood Explanation
This does not require a malicious/privileged actor: any user or AA can trigger the path just by using `in_data_feed`/`data_feed` (a documented, encouraged pattern for oracle usage), and the size of `assocUnstableMessages` is influenced by ordinary organic network activity (transaction volume, chain congestion) rather than by any single attacker artificially inflating "tiers" as in the original report — making the degradation likely to occur naturally as network usage grows, and easy to inadvertently amplify by simply generating more transaction volume (posting many low-value units) to inflate the unstable set while data-feed-consuming AAs are in active use.

### Recommendation
Scope the in-memory unstable scan to only the oracle addresses passed in `arrAddresses` (e.g., maintain a per-address index of pending/unstable data-feed messages instead of iterating the global `assocUnstableMessages` map), so the cost is proportional to the number of unstable messages from the queried oracle(s), not to the total number of unstable units network-wide. Additionally, consider capping/limiting the number of unstable units scanned per call, with a defined fallback (e.g., treat feed as "not found among unstable" beyond the cap) so worst-case AA evaluation time is bounded regardless of network congestion.

### Proof of Concept
Not independently reproducible from static review alone (requires simulating a large, sustained unstable-unit set); this assessment is based on code-path tracing: `formula/evaluation.js` `in_data_feed`/`data_feed` ops → `data_feeds.dataFeedExists`/`readDataFeedValue` → unbounded `for (var unit in storage.assocUnstableMessages)` scan, confirmed via the cited line ranges. A concrete PoC would involve generating a large backlog of unstable units on a testnet while repeatedly triggering an AA using `in_data_feed` and measuring per-trigger evaluation latency growth as the unstable set size increases.
