### Title
ERC20Transactor credits/consumes XCM holding based on the requested `amount`, not the actual ERC20 balance delta, for non-standard (fee-on-transfer/deflationary) tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` treat an ERC20 `transfer` call as fully successful (crediting/consuming exactly `amount`) whenever the call does not revert and returns `true`, without ever comparing the checking account's/beneficiary's balance before and after the call. This is the same class of bug as the reported Masset issue: the pallet's internal accounting of "how much of this asset the checking account holds" can diverge from the ERC20 contract's real balance whenever the token does not transfer the full nominal amount (fee-on-transfer, deflationary/burn-on-transfer, or otherwise non-standard ERC20 semantics), even though `transfer` returns `true`.

### Finding Description
`ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` tuple [1](#0-0) , and is the designated `TransactAsset` implementation for any ERC20 contract registered as an XCM asset of the form `AccountKey20` on Asset Hub Westend [2](#0-1) . Any signed account can trigger this path via `pallet_xcm::execute` or a reserve transfer that references an ERC20 asset in the message's `Asset` list — no privileged origin is required.

`withdraw_asset_with_surplus` calls `IERC20::transfer(checking_account, amount)` from the user's account and, if the call does not revert and decodes to `true`, unconditionally creates an `AssetsInHolding` credit of exactly `amount`: [3](#0-2) 

`deposit_asset_with_surplus` performs the mirror operation, calling `transfer(beneficiary, amount)` from the checking account and treating a `true` return as proof that `amount` was fully deposited: [4](#0-3) 

Neither function reads `balanceOf` before/after the transfer to confirm the actual balance delta equals `amount` — exactly the assumption flagged as the root cause in the Masset report ("the integration contract assumes that the amount deposited into the pool is equal to the amount received"). For ERC20 tokens that: (a) charge a transfer fee/burn a percentage on `transfer` (common "deflationary"/"reflection" tokens), or (b) are rebasing tokens whose balances change between the `transfer` call and subsequent reads, the checking account's *real* balance can end up smaller than the amount the XCM executor's internal `AssetsInHolding`/subsequent accounting believes it received. The comment in the code even acknowledges this design gap: "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [5](#0-4) .

### Impact Explanation
Because the XCM holding register now reflects a virtual `amount` that exceeds what the checking account actually possesses in the ERC20 contract, any subsequent `DepositAsset` instruction in the same (or later) program that tries to move the full nominal `amount` out of the checking account will either:
1. Fail (the ERC20 `transfer` reverts/returns `false` due to insufficient real balance), trapping the "phantom" excess amount and any assets bundled with it in the XCM `AssetTrap`, permanently or until manual claim — a fund-lock/DoS on the depositor's assets, or
2. In multi-step compositions where the "amount received" is fanned out to multiple beneficiaries or split across further XCM instructions based on the nominal `amount` rather than a verified balance, a subset of beneficiaries can be shorted while others are paid based on stale/incorrect internal bookkeeping, since none of the intermediate logic re-checks real balances.

This mirrors the "Won't Fix" classification of the source report (temporary, self-correcting divergence of negligible economic size in the original mAsset case), but here the divergence is not bounded to "1 base unit" — it is proportional to the token's fee/rebasing percentage, which is attacker- (i.e., token-issuer-) controlled and not something Asset Hub's runtime validates when the ERC20 is registered as an XCM asset. Impact is bounded by asset trapping/DoS rather than direct theft, since a failed transfer from the checking account reverts that specific instruction.

### Likelihood Explanation
Reaching this code only requires a signed extrinsic invoking `pallet_xcm::execute`/reserve-transfer referencing an ERC20 asset that is deflationary/fee-on-transfer, and no privileged role or governance action is needed to trigger the divergence — only permissionless registration of an unusual ERC20 token as an XCM-referenceable asset (which appears to be automatic based on the `AccountKey20` matcher, not curated) is needed. However, I could not verify from the indexed files whether Asset Hub Westend enforces any allow-list or standard-conformance check before an ERC20 contract can be referenced via this transactor; if such a gate exists elsewhere in the runtime it would reduce likelihood. This is left unconfirmed due to index coverage limits.

### Recommendation
Following the same fix pattern recommended in the source report ("use the balance increase ... instead of using the amount received"), `ERC20Transactor` should read `balanceOf` on the checking account/beneficiary immediately before and after the `transfer` call and use the actual observed delta (capped at `amount`) to construct the `Erc20Credit`/to determine how much was actually deposited, rather than trusting the boolean return value combined with the requested `amount`.

### Proof of Concept
No executable PoC was run; this is a static-analysis-based structural finding derived from source inspection, consistent with the constraints of this environment (read-only codebase access, no ability to deploy contracts or execute a local Rust/XCM integration test). A concrete reproduction would require:
1. Deploying a fee-on-transfer/deflationary ERC20 contract via `pallet_revive` on an Asset Hub Westend test node.
2. Registering it as an XCM asset (`AccountKey20` location) usable by `ERC20Transactor`.
3. Executing an XCM program via `pallet_xcm::execute` that does `WithdrawAsset` (nominal `amount`) followed by `DepositAsset` to a second beneficiary for the same nominal `amount`, and observing that the second `DepositAsset` either fails (trapping assets) or, in a crafted multi-step program, distributes more nominal value than the checking account actually received.
No such test was executed in this session; the above steps describe what would be needed to empirically confirm the divergence and its concrete on-chain effect (trap vs. inconsistency), which remains unverified beyond the code-level structural analysis presented above.
