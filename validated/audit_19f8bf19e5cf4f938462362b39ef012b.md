## Analysis

The reported bug class is: **a resource's spending/validation parameters can be mutated by their owner while a dependent operation is "in flight," and the validation of that operation reads the mutated parameter using the wrong reference point (a "live/latest" state) instead of the value that was fixed/committed when the dependent operation was created.** In `ocore`, the direct analog is in `storage.readAsset()`, used to fetch the attestor list of a `spender_attested` asset for validating a payment. [1](#0-0) 

For assets issued by an AA that is not yet confirmed (`bAcceptUnconfirmedAA` / the "byAA" branch), the SQL query that selects the "latest" attestor-list unit drops the `main_chain_index<=last_ball_mci AND is_stable=1` filter entirely and simply picks by `level DESC LIMIT 1` (or `rowid DESC` for light clients) among **all** `sequence='good'` `asset_attestors` records for that asset — including units that are unstable and not yet included in the payment's own `last_ball`: [2](#0-1) 

Compare this to the normal (non-AA) path, which correctly pins the attestor-list lookup to the payment's `last_ball_mci` and requires `is_stable=1`, guaranteeing every node validates against the same, deterministic snapshot: [3](#0-2) 

The attestor list for a `spender_attested` asset can only be edited by the asset's definer via the `asset_attestors` app message, validated in `validateAttestorListUpdate`: [4](#0-3) 

And this update is consumed during payment validation whenever `objAsset.spender_attested` is checked: [5](#0-4) 

### Title
Unpinned "latest" attestor-list lookup for AA-issued assets allows definer to alter spending authorization mid-flight, causing non-deterministic/disagreeing validation - (File: storage.js)

### Summary
`storage.readAsset()` normally resolves the attestor list of a `spender_attested` asset by pinning the lookup to the validated unit's `last_ball_mci` and requiring `is_stable=1`, so every node deterministically agrees on which attestor list applies. When the asset is issued by an AA and the caller accepts unconfirmed AA definitions (`bAcceptUnconfirmedAA`, used when `objValidationState.bAA` is true during AA trigger/payment processing), the code switches to the `byAA` branch, which drops both the `main_chain_index<=last_ball_mci` and `is_stable=1` conditions and instead selects the attestor-list unit with the highest `level` (or `rowid` for light nodes) among all "good" units.

### Finding Description
This is the same class of bug as the reported "auction parameters can be updated during ongoing auction": a value that should be frozen relative to the operation being validated (the attestor list as of the payment's committed reference point) is instead read as a "live/latest" value that keeps changing as new, possibly-unstable `asset_attestors` units arrive. Because the AA definer can post a new `asset_attestors` update at any time, and because the byAA lookup has no floor tied to the payment's `last_ball_mci`, the set of addresses considered "attested" for spending the asset can change between the moment a payment (or nested-AA-issued-asset payment) is composed/broadcast and the moment it is actually processed and stabilized.

### Impact Explanation
Because the query orders by `level`/`rowid` over units regardless of stability, different nodes that have received a different subset of the DAG at validation time (e.g., during AA trigger response construction, which must be deterministic across all nodes) can compute different "latest" attestor lists for the same asset and the same last-ball state, since unstable units are not guaranteed to be seen in the same order/set by all nodes before finality. This breaks the core invariant that all full nodes deterministically agree on unit/AA-response validity, which is required so witnesses/nodes converge on the same DAG and stability. A definer/AA can also weaponize this deliberately: issue a payment expecting current attestors, then push a conflicting `asset_attestors` update before the payment stabilizes, changing who is considered "attested" and therefore whether spending from/to a given address is valid — enabling unauthorized spending or unexpected freezing of a payment that was valid when constructed.

### Likelihood Explanation
Any account controlling an AA that defines a `spender_attested`, `issued_by_definer_only=false`-style asset (or the AA itself, since only the definer may post `asset_attestors`) can trigger this path simply by issuing the asset via an AA and later posting an attestor-list update while payments referencing that asset are still unstable. No special privileges beyond normal AA/asset issuance are required, and the AA definer fully controls the timing of the `asset_attestors` update relative to in-flight payments.

### Recommendation
Remove the special-cased `before_last_ball_cond = ""` for the `byAA` branch in `storage.js`'s `readAsset()`/`addAttestorsIfNecessary()`, or replace it with a condition that still pins the lookup deterministically to the validated unit's `last_ball_mci` (and to a DAG-order-consistent notion of "latest" that does not depend on unstable units not yet globally visible), matching the behavior of the non-AA branch, so that all nodes are guaranteed to select the same attestor-list unit for a given payment/trigger regardless of transient DAG visibility.

### Proof of Concept
1. An AA `A` issues asset `X` with `spender_attested: true`, `issued_by_definer_only: true`, attestors `[P1]` (validated via `aa_validation.js`'s `asset` case, requiring `attestors` and `spender_attested`). [6](#0-5) 
2. A user triggers AA `A` to issue/transfer `X` to address `U1`, which is attested by `P1`. This trigger unit is broadcast but not yet stable.
3. Before the trigger becomes stable, AA `A`'s definer (or another trigger causing `A` to emit it) posts an `asset_attestors` update for `X` removing `P1` and adding `P2`, validated by `validateAttestorListUpdate`. [4](#0-3) 
4. When the original trigger/payment is finally validated (via `loadAssetWithListOfAttestedAuthors` → `readAsset` with `bAcceptUnconfirmedAA=true`), `readAsset`'s `byAA` branch picks whichever `asset_attestors` unit has the highest `level` visible to that particular node at that moment — not the one deterministically tied to the trigger's `last_ball_mci`. [2](#0-1) 
5. Depending on which `asset_attestors` unit each node has processed/considers "latest" at validation time, nodes can reach different conclusions about whether `U1` is still an attested spender, producing divergent validation results for the same trigger/payment.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
