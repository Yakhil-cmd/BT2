### Title
Webhook signature is verified against `repository.owner.login`/`organization.login` while every event handler acts on `repository.full_name` — allows cross-organization webhook forgery in multi-app deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
In a Shipit installation configured with multiple GitHub Apps (one per organization, as documented in `docs/setup.md` and `test/dummy/config/secrets_double_github_app.yml`), `WebhooksController#verify_signature` selects which GitHub App/HMAC secret to verify the inbound webhook against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature check passes, `create` dispatches the **entire raw JSON payload** — unmodified — to the registered `Shipit::Webhooks::Handlers::*`, which independently resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')` (`app/models/shipit/webhooks/handlers/handler.rb#repository_name`/`#stacks`). Because these are two independent, attacker-controlled JSON fields inside the same payload, nothing forces `repository.owner.login` (the identity that is cryptographically authenticated) to equal the owner encoded in `repository.full_name` (the identity that is actually acted upon).

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb`: [1](#0-0) 

selects the app config strictly from `repository_owner`: [2](#0-1) 

`Shipit.github(organization:)` looks up the app config keyed by that organization name and instantiates a `GitHubApp` whose `webhook_secret` is used for HMAC verification: [3](#0-2) [4](#0-3) 

After signature verification succeeds, `create` hands the raw, still-untouched `params` hash to every registered handler for the event: [5](#0-4) 

All handlers resolve the target repository/stack from a **different** field of the same payload — `repository.full_name` — via the shared base `Handler`: [6](#0-5) 

`Repository.from_github_repo_name` simply splits `owner/name` out of that string and looks up the DB row with no comparison back to `repository_owner`/the app whose secret authenticated the request: [7](#0-6) 

Nothing ties `repository.owner.login` (used only to pick the HMAC secret) to `repository.full_name` (used to pick the DB row that gets written to). An attacker who legitimately controls the webhook secret for **any one** organization configured on the shared Shipit instance (e.g. they are an admin of their own small org, `OrgA`, that has been onboarded into the same multi-tenant Shipit deployment as a victim `OrgB`) can craft an arbitrary JSON payload, set `repository.owner.login` (or `organization.login`) to `"OrgA"`, sign it with `OrgA`'s known webhook secret, but set `repository.full_name` to `"OrgB/victim-repo"`. The signature check succeeds (it only validates against `OrgA`'s secret) and the payload is then routed to handlers that act on `OrgB`'s repository/stacks. This breaks the equality that should hold: `organization authenticated == organization acted upon`.

Concretely, with `Handlers::StatusHandler` this lets the attacker forge a `status` event for an arbitrary already-known commit SHA belonging to `OrgB`'s tracked commits, creating a fabricated CI status (`state: success`, arbitrary `context`) on that commit: [8](#0-7) 

If `OrgB`'s stack has `continuous_deployment: true` and relies on that CI status context as a required check, this forged status can satisfy `deployable?`/CI gating and trigger an unauthorized deploy of a real commit that never actually passed CI. With `Handlers::MembershipHandler`, the same trick lets the attacker forge `membership` events, creating/joining arbitrary GitHub teams and adding arbitrary users as members: [9](#0-8) 

`Shipit.github_teams` (used to gate access to the whole application, e.g. `ApiClientsController`) is built directly from `Team` records populated by this handler: [10](#0-9) 

so forged `membership` "added" events let an attacker who controls only `OrgA`'s webhook secret grant themselves (or any GitHub login) membership in a `Team` that is trusted for authorization decisions elsewhere in the app — an escalation into `Shipit.github_teams` authorization.

### Impact Explanation
- Forged `status` events on a cross-organization commit can fabricate a passing CI check that a `continuous_deployment`-enabled stack relies on, enabling an unauthorized deploy of a commit that never passed real CI — Critical impact ("unauthorized deploy").
- Forged `membership` events let the attacker add arbitrary users to `Team` records that back `Shipit.github_teams`, escalating access-control decisions gated on team membership — High impact ("escalation into `Shipit.github_teams` authorization").
- The blast radius extends across every organization/repository hosted on the shared Shipit instance, not just the organization whose secret the attacker legitimately possesses, because the verification step and the "act upon" step consult two independently-controlled payload fields.

### Likelihood Explanation
This requires a multi-organization Shipit deployment (explicitly supported and documented: `docs/setup.md`, `test/dummy/config/secrets_double_github_app.yml`) where the attacker legitimately administers at least one of the onboarded GitHub Apps/organizations and therefore knows that org's `webhook_secret`. Given that precondition — which is a normal, documented deployment mode rather than a privileged internal role — crafting the payload requires no special access beyond POSTing to the public `/github` webhook endpoint with a correctly computed HMAC for the attacker's own org.

### Recommendation
In `WebhooksController#verify_signature` / `#create`, after verifying the signature, assert that the resolved `repository_owner` used to select the signing app also matches (case-insensitively) the owner embedded in `repository.full_name` (and in `organization.login` where present) before dispatching to handlers; reject the request (422) on mismatch. Alternatively, have `Handler#stacks`/`#repository_name` receive and enforce the authenticated organization from the controller rather than re-deriving the repository identity from the untrusted payload independently.

### Proof of Concept
1. Configure Shipit with two GitHub Apps, `OrgA` and `OrgB`, per `test/dummy/config/secrets_double_github_app.yml`.
2. As an admin of `OrgA`, obtain `OrgA`'s `webhook_secret`.
3. Build a `status` webhook payload:
```json
{
  "sha": "<known sha of a commit tracked under OrgB/victim-repo>",
  "state": "success",
  "context": "required-ci-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
4. Compute `X-Hub-Signature` as `sha1=HMAC_SHA1(OrgA_webhook_secret, payload)` and POST to the Shipit `/github` endpoint with `X-Github-Event: status`.
5. `verify_signature` calls `Shipit.github(organization: "OrgA")`, which succeeds against `OrgA`'s secret.
6. `Shipit::Webhooks::Handlers::StatusHandler#process` runs `Commit.where(sha: params.sha)` and creates a status for the commit belonging to `OrgB/victim-repo`, using `repository.full_name`, not `repository.owner.login`, confirming the cross-org write.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
