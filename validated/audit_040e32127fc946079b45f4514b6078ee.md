### Title
Non-message-bound `hash` authentifier permits permanent replay bypass of the intended `sig` control in `or`-combined address definitions - ([File: definition.js])

### Summary
Address (and asset-condition) definitions can combine a cryptographic `sig` branch with a `hash` branch under an `or` combinator. Unlike `sig`, the `hash` authentifier is never bound to the unit being authorized (`unit_hash_to_sign`), so once the secret preimage is disclosed on-chain in one unit, it remains a permanently valid authenticator for that address/path. This mirrors the reported bug class: an alternate, weaker "login path" left enabled alongside the intended strong authentication (SSO/DiscourseConnect vs. local login) lets anyone bypass the stronger control forever.

### Finding Description
`Definition.validateAuthentifiers` -> `evaluate()` implements the `hash` op by simply comparing the disclosed authentifier value against a stored hash, with no binding to the unit content or timestamp: [1](#0-0) 

Contrast this with the `sig` op, which verifies the signature over `objValidationState.unit_hash_to_sign`, i.e. it is bound to the specific unit and cannot be replayed for a different spend: [2](#0-1) 

An address definition is free to combine both branches with `or`, e.g. `["or", [["sig", {...}], ["hash", {...}]]]`. `validateDefinition` accepts arbitrary nesting of `or`/`and`/`r of set` and other conditions, and `pathIncludesOneOfAuthentifiers`/`needToEvaluateNestedAddress` only optimize which branches get evaluated based on which authentifier paths were supplied — they do not restrict which branch is "the" intended default: [3](#0-2) [4](#0-3) 

`validateAuthentifiers` re-evaluates the *whole* definition tree against whatever `assocAuthentifiers` (paths => values) are supplied in the unit, and any branch of an `or` that evaluates true satisfies the whole condition: [5](#0-4) 

Because the `hash` op's success condition is `args.hash === sha256(assocAuthentifiers[path])` with no reference to `unit_hash_to_sign`, `last_ball_mci`, or any nonce, the *same* preimage value that was disclosed in one historical unit (any unit, since the DAG and all units are public) can be reused as the `authentifiers[path]` value in a brand-new, unrelated unit spending from the same address, as long as the `hash` branch of the `or` is still part of the address's current definition. This effectively creates a standing "backup login path" that never expires and is not bound to any specific transaction, unlike the intended `sig` control which is unique per unit.

This is directly analogous to the Discourse bug class: the address owner may believe the address is protected by the strong, message-bound `sig` control, while an alternate, weaker, replayable `hash` control coexists in the same `or` definition and can be used by any observer who has ever seen the preimage (e.g., leaked during an atomic swap, a bounced/failed attempt, a test unit, or a partially-executed multi-step protocol) to bypass the intended strong control indefinitely.

### Impact Explanation
Any third party who observes a disclosed `hash` preimage for an address whose definition contains a `hash` branch combined via `or` with a `sig` branch can construct and post new units on behalf of that address, authorizing arbitrary payments/AA triggers/asset transfers, without ever possessing the private key. This is unauthorized spending / authentication bypass on any live address using this common secret-reveal (swap-like) pattern, and it persists for the lifetime of the address definition, not just for a single transaction as most authors of such definitions likely assume.

### Likelihood Explanation
Definitions containing `hash` branches are a documented feature (frequently used for atomic-swap-style secret-reveal spending conditions) and are commonly combined with `sig`/timeout `or` branches so that the address can be reclaimed either by revealing a secret or (after a timeout) by the owner's signature. Because a `hash` preimage disclosed once in any historical unit remains valid forever for that path, and because the DAG is fully public, exploitation only requires the attacker to have observed any unit where the address's `hash` authentifier value was ever revealed (which is required by the swap protocol itself in order to be useful) — making exploitation straightforward once a secret has been revealed even once, with no need to compromise the private key.

### Recommendation
Bind the `hash` authentifier check to the unit being authorized (e.g., require `hash(preimage || unit_hash_to_sign)` or otherwise incorporate a per-unit nonce/hash into the comparison) so a previously disclosed preimage cannot be replayed to authorize unrelated units. Alternatively, document and enforce (at the wallet/definition-validation layer) that any address definition containing a `hash` branch must be single-use (i.e., its definition must be rotated/invalidated immediately once the preimage is disclosed), and warn users composing `or`-combined `sig`/`hash` definitions that the `hash` branch never expires and is not message-bound.

### Proof of Concept
1. Address `A` is created with definition `["or", [["sig", {pubkey: P}], ["hash", {hash: H}]]]`, intended so the owner normally spends with `sig`, and the `hash` branch is a one-time escape/swap mechanism revealing preimage `S` such that `sha256(S)=H`.
2. Owner (or a counterparty in an atomic swap) posts a unit that includes `authentifiers = {"r.1.1": S}` to satisfy the `hash` branch for one specific spend, as validated in `evaluate()`'s `hash` case (definition.js:756-772). This exposes `S` publicly in the immutable DAG.
3. Any observer extracts `S` from that historical unit's authors/authentifiers.
4. The observer later composes an entirely new unit spending further funds from address `A` (or triggering an AA, or changing the address definition, etc.), supplying `authentifiers = {"r.1.1": S}` again.
5. `Definition.validateAuthentifiers` re-evaluates the definition against this new unit (definition.js:1443-1466); the `hash` branch again returns true because the check (definition.js:762-763) is `sha256(S) === H`, with no dependency on the new unit's hash — so the `or` condition is satisfied and the new unit is treated as validly authorized by address `A`, despite the observer never having controlled the `sig` private key.
