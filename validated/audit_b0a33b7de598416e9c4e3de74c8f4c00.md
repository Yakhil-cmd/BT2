### Title
Cross-stack disclosure of deploy state via `CCMenuController` bypassing the token's `stack_id` scope - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`CCMenuUrlController#client` mints an `ApiClient` scoped to a single stack (`stack_id` set, `permissions: %w[read:stack]`) so that a low-privilege CCTray/CCMenu token can only report the build status of the stack it was issued for. [1](#0-0)  The generic `Api::BaseController` correctly enforces that scope by intersecting the requested stack with `current_api_client.stack_id` in `#stacks`/`#stack`. [2](#0-1)  However `Api::CCMenuController` overrides `#stack` to look the stack up directly by the URL `stack_id` param, completely bypassing that scoping check. [3](#0-2)  The equality the engine is supposed to enforce — *"stack authorised by token" == "stack touched by the request"* — is broken: any valid `read:stack` token, even one deliberately scoped to a single stack, can be replayed against every other stack in the installation by changing the `stack_id` path segment.

### Finding Description
`ApiClient#stack_id` and `permissions` together define the authorization envelope of a token. [4](#0-3)  The base API controller enforces the stack scope through the `stacks`/`stack` helper methods that every other controller (deploys, tasks, commits, hooks, etc.) relies on:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`Api::CCMenuController` inherits from `BaseController` and only runs `require_permission :read, :stack`, which checks the *permissions array* but never the *stack scope*: `check_permissions!` only validates that `"read:stack"` is present in `permissions`, with no reference to `stack_id`. [5](#0-4)  The controller then redefines `#stack` to resolve the stack directly from the URL, independent of `current_api_client`:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [6](#0-5) 

Because `#show` calls this overridden `#stack`, the token's `stack_id` binding (checked nowhere here) is disconnected from the stack actually rendered:

```ruby
def show
  latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
  render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
end
``` [7](#0-6) 

This is the direct engine analog of the reported bug class: a binding that is supposed to hold at authorization time (token → stack) is silently dropped at the point where the data is actually produced, letting a value in the request override the value that was meant to be pinned by the credential.

### Impact Explanation
Any holder of a scoped, read-only CCMenu token (any Shipit user can mint one for a stack they can already view via `CCMenuUrlController#fetch`, and such tokens are designed to be embedded in third-party CI dashboard tools/URLs, so their exposure surface is far broader than their intended one-stack scope) can query `api_stack_ccmenu_url` for **any** other stack in the Shipit instance and obtain that stack's `name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, and `webUrl` — deploy state that other stacks and teams may not intend to expose to holders of an unrelated stack's token. This matches the rubric's "High — unauthenticated [for that stack] read of stack state / deploy output," because the token was never authorized to read the target stack; only its issuing stack.

### Likelihood Explanation
Exploitation requires nothing beyond changing one URL segment (`stack_id`) while reusing a token already legitimately obtained for a different, low-privilege purpose (a CCTray badge). No write access, no secrets, and no privileged account are needed — the only precondition is possession of *any* stack-scoped `read:stack` CCMenu token, which is the intentionally weakest class of credential the engine issues. The bug is a straightforward method override that silently drops the scoping check present in the shared base controller, making it easy to trigger and easy to miss in review since every sibling API controller (`Api::StacksController`, `Api::DeploysController`, etc.) correctly uses the inherited `#stack`.

### Recommendation
Remove the `#stack` override in `Api::CCMenuController` and use the inherited, scope-respecting `stack`/`stacks` helpers from `Api::BaseController` instead of `Stack.from_param!(params[:stack_id])` directly. If a custom lookup is required, explicitly re-apply the `current_api_client.stack_id` constraint before resolving the `stack_id` param, mirroring `BaseController#stacks`.

### Proof of Concept
1. As a legitimate Shipit user with access to Stack A, visit `CCMenuUrlController#fetch` for Stack A to obtain a token scoped to Stack A only (`ApiClient.stack_id == A.id`, `permissions == ["read:stack"]`). [8](#0-7) 
2. Take the returned `ccmenu_url` (which encodes `token=<Stack-A-token>&stack_id=A`) and replace the `stack_id` path segment with Stack B's identifier, e.g.:
   `GET /api/<Stack-B-owner>/<Stack-B-name>/<env>/ccmenu?token=<Stack-A-token>`
3. `authenticate_api_client` in `CCMenuController` validates the token as belonging to a real `ApiClient` (Stack A's) and grants access since `require_permission :read, :stack` passes. [9](#0-8) 
4. `#show` calls the overridden `#stack`, which resolves Stack B directly from `params[:stack_id]`, ignoring that the token was only authorized for Stack A. [10](#0-9) 
5. The response renders Stack B's `name`, `lastBuildStatus`, `lastBuildLabel`, etc., disclosing deploy state the Stack‑A token was never authorized to see.
