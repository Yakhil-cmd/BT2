### Title
Missing Staking Info Content Validation in Fast Sync Allows Malicious Peer to Corrupt Proposer Selection and Reward Distribution — (`datasync/downloader/queue.go`)

### Summary
During fast sync, a malicious P2P peer can respond to `StakingInfoRequestMsg` with `P2PStakingInfo` entries whose `BlockNum`, `NodeIds`, or `StakingAmounts` are fabricated. Because `queue.DeliverStakingInfos` has a no-op validate closure, the fabricated data is written verbatim into the staking DB. After sync, the node derives its weighted-random proposer list from this corrupted DB, causing consensus divergence and incorrect block reward distribution.

### Finding Description

`handleStakingInfoMsg` in `node/cn/handler.go` receives a `StakingInfoMsg` from any connected P2P peer, decodes it, and forwards it to the downloader without any content validation: [1](#0-0) 

The downloader enqueues it via `queue.DeliverStakingInfos` in `datasync/downloader/queue.go`. The validate closure is intentionally left as a no-op: [2](#0-1) 

The generic `deliver` function calls `validate(i, header)` at line 1005, but since it always returns `nil`, the `reconstruct` closure runs unconditionally, writing the peer-supplied `stakingInfoList[index]` into `result.StakingInfo`: [3](#0-2) 

`commitFastSyncData` then persists the data using the **peer-supplied** `result.StakingInfo.BlockNum` as the DB key: [4](#0-3) 

Compare with `DeliverBodies` and `DeliverReceipts`, which verify content against the header's `TxHash` / `ReceiptHash`: [5](#0-4) 

No equivalent commitment exists for staking info in the block header, but even a `BlockNum == header.Number.Uint64()` check is absent.

### Impact Explanation

After fast sync completes, `kaiax/valset/impl/getter_proposers.go` computes the weighted-random proposer list by reading staking info from the DB for the proposer update block: [6](#0-5) 

If the DB entry for that update block was written with attacker-controlled `StakingAmounts` or `NodeIds`, the proposer list is derived from fabricated data. The affected node will:
- Select wrong proposers, causing it to reject valid blocks and accept invalid ones — **consensus divergence**.
- Compute wrong reward distributions when it processes blocks — **incorrect KAIA reward accounting**.

The `SyncStakingInfo` recovery path does check `BlockNum` against expected values (downloader.go:673), but `commitFastSyncData` — the fast sync path — has no such guard. [7](#0-6) 

### Likelihood Explanation

- **Attacker entry point**: Any permissionless P2P peer. No special privileges required.
- **Trigger condition**: The victim node must be performing fast sync (`FastSync` or `SnapSync` mode). This is the default for new nodes joining the network.
- **Attack complexity**: Low. The attacker connects as a peer, waits for a `StakingInfoRequestMsg`, and responds with a `StakingInfoMsg` containing fabricated `P2PStakingInfo` entries. No cryptographic material is needed because there is no commitment in the block header to verify against.

### Recommendation

In `queue.DeliverStakingInfos`, replace the no-op validate closure with a check that `stakingInfoList[index].BlockNum == header.Number.Uint64()`. Additionally, in `commitFastSyncData`, use `result.Header.Number.Uint64()` as the DB key rather than the peer-supplied `result.StakingInfo.BlockNum`, and validate that the two match before writing.

### Proof of Concept

1. Spin up a fast-syncing node (victim) and a malicious peer.
2. The malicious peer intercepts the `StakingInfoRequestMsg` for block hash `H` (corresponding to block number `N`, a staking update interval boundary).
3. The malicious peer responds with a `StakingInfoMsg` containing a `P2PStakingInfo` where `BlockNum = N` but `StakingAmounts` are all set to `0` (or to values that favor a specific validator).
4. After fast sync completes, query the victim node's staking DB for block `N` — it will contain the fabricated amounts.
5. Observe that the victim node's proposer list for the epoch starting at `N` differs from honest nodes, causing it to diverge from consensus. [8](#0-7) [4](#0-3)
