### Title
Webhook signature is verified against the organization named in the payload's `repository.owner.login`, but handlers act on the (unverified) `repository.full_name` field, enabling cross-organization stack writes in multi-org deployments - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate an inbound GitHub webhook against by reading an attacker-controlled field from the JSON payload (`repository.owner.login`, falling back to `organization.login`), rather than from any credential tied to the actual GitHub App/organization that delivered the request. All downstream event handlers, however, determine *which* `Stack`/`Repository` to mutate using a *different* field of the same attacker-controlled payload: `repository.full_name`. Because these two fields are never cross-checked, a party who legitimately controls the webhook secret for **one** configured organization can forge a payload whose signature validates for their own organization while its `repository.full_name` points at a stack belonging to a **different** organization, causing Shipit to act on that other organization's data.

### Finding Description
The class exhibits the same root cause as the referenced GogoPool report: two pieces of state that must stay bound together (the identity that was *authenticated* and the resource that is subsequently *acted upon*) are allowed to diverge across a single request.

`repository_owner` is computed purely from the JSON body: [1](#0-0) 

It feeds directly into secret selection: [2](#0-1) 

`Shipit.github(organization:)` looks up a distinct `webhook_secret` per organization when the installation is configured for multiple organizations: [3](#0-2) 

Once the signature check passes (using whichever organization's secret matched `repository_owner`), the raw, unauthenticated payload is dispatched to handlers as-is: [4](#0-3) 

Every handler, however, resolves the target `Stack`/`Repository` from a completely separate JSON field, `repository.full_name`, with no relation to `repository.owner.login` used for verification: [5](#0-4) [6](#0-5) [7](#0-6) 

Nothing in the request pipeline enforces the invariant `repository.owner.login == owner(repository.full_name)`. The equality that should hold is:

`organization whose webhook_secret authenticated the request == organization that owns the repository being written to`

Before an attack: for any legitimate GitHub-originated webhook, both fields naturally describe the same repository, so the invariant holds implicitly (not because it's checked, but because GitHub always fills both consistently). After an attacker crafts the request: the attacker controls both fields independently, only one of which is covered by the HMAC verification path's *choice of key*, while the signature itself covers the whole raw body — but that's irrelevant, because the attacker can compute a fully valid signature using their own legitimately-held secret over a payload of their own choosing. The verification only proves "this body was signed with organization A's secret"; it never proves "this body's payload data about a different organization's repository should be trusted."

### Impact Explanation
In any Shipit installation configured with multiple GitHub organizations (the documented multi-org secrets/config shape read by `github_app_config`), a party who is a legitimate admin/owner of *any one* configured organization's GitHub App (and thus knows that org's `webhook_secret`) can forge webhook deliveries whose `repository.full_name` names a stack belonging to a **completely different, unrelated organization**. Depending on event type this allows:
- Forcing `PushHandler` to enqueue `GithubSyncJob` against another organization's stack.
- Forcing PR handlers (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `LabelCapturingHandler`, `ReviewStackAdapter`) to create, archive, or unarchive `ReviewStack`s belonging to another organization's repository — `ReviewStack` provisioning runs deploy-time steps, i.e. this can trigger an unauthorized deploy/provisioning action on infrastructure that does not belong to the attacker's organization.

This crosses the organization/credential boundary that per-organization webhook secrets are meant to enforce, matching the Critical impact category of cross-repository writes / an unauthorized deploy.

### Likelihood Explanation
Exploitation requires no privileged Shipit account, no `ApiClient` token, and no GitHub write access to the victim repository — only knowledge of a webhook secret for *some* organization configured in the same Shipit instance (which such an organization's own administrators legitimately hold, or which could leak independently of the victim organization). The webhook endpoint (`POST /webhooks`) is public and unauthenticated aside from the HMAC check, and none of the handlers re-validate that `repository.owner.login` matches `repository.full_name`'s owner.

### Recommendation
Derive `repository_owner` used for secret selection from the same field that is subsequently trusted for routing/writes (`repository.full_name`'s owner segment, or `organization.login` consistently), and reject the webhook if `repository.owner.login` (or `organization.login`) does not match the owner segment of `repository.full_name`. Alternatively, verify the signature using the secret associated with the resolved `Repository`/`Stack` (derived from `full_name`) rather than the attacker-suppliable `owner.login`/`organization.login` fields.

### Proof of Concept
1. Assume Shipit is configured with two organizations, `attacker-org` (secret `S_A`) and `victim-org` (secret `S_V`), each with its own GitHub App per the documented multi-org `secrets.github` schema consumed by `Shipit.github_app_config`.
2. `victim-org/victim-repo` is tracked by Shipit with `review_stacks_enabled` and `provisioning_behavior_allow_all?`.
3. An administrator of `attacker-org` (who legitimately knows `S_A`) crafts a `pull_request` "opened" webhook body:
```json
{
  "action": "opened",
  "number": 1,
  "pull_request": { "id": 1, "number": 1, "url": "...", "title": "x", "state": "open",
                     "additions": 1, "deletions": 0,
                     "head": {"sha": "deadbeef", "ref": "feature"},
                     "user": {"login": "attacker"}, "assignees": [], "labels": [] },
  "repository": { "owner": {"login": "attacker-org"}, "full_name": "victim-org/victim-repo" },
  "sender": {"login": "attacker"}
}
```
4. Compute `X-Hub-Signature: sha1=<HMAC-SHA1(S_A, raw_body)>` and POST to `/webhooks` with `X-Github-Event: pull_request`.
5. `verify_signature` resolves `repository_owner` = `"attacker-org"`, fetches `S_A`, and the signature validates successfully — see: [2](#0-1) .
6. `OpenedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")`, and, if provisioning conditions are met, creates/provisions a `ReviewStack` for the victim's repository — see: [8](#0-7) . The attacker never possessed `S_V` nor any credential tied to `victim-org`.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
