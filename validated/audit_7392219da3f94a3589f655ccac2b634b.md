### Title
Webhook organization used for signature verification differs from the repository the payload is applied to, enabling cross-tenant stack manipulation - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController` selects which organization's webhook secret to verify a signature against using one payload field (`repository.owner.login` / `organization.login`), while the event handlers act on a *different* payload field (`repository.full_name`) to decide which `Repository`/`Stack` the payload's data (ref, head sha, etc.) is applied to. Because the HMAC signature only proves "this body was signed with organization X's secret," not "this body's target repository is one owned by organization X," an attacker who legitimately knows the webhook secret for their own onboarded organization can forge a payload whose `repository.full_name` points at a different (victim) organization's repository, and the request will still pass signature verification.

### Finding Description
`WebhooksController#verify_signature` derives the organization used to look up the correct GitHub App/webhook secret exclusively from: [1](#0-0) 

```ruby
def repository_owner
  # Fallback to the organization sub-object if repository isn't included in the payload
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

This value is passed to `Shipit.github(organization: repository_owner)` and the resulting `webhook_secret` is used to verify the `X-Hub-Signature` HMAC over the raw request body: [2](#0-1) 

Once verification succeeds, the entire raw JSON body is handed unmodified to the registered handler(s): [3](#0-2) 

Each `Handler` (e.g. `PushHandler`) determines the actual `Repository`/`Stack` to mutate using a *different* field, `repository.full_name`: [4](#0-3) 

```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

and `PushHandler` uses this stack set to force-sync stacks to an attacker-supplied `after` sha: [5](#0-4) 

Nothing ties `repository.owner.login` (the field that selects the signing secret) to `repository.full_name` (the field that selects which stack is mutated). This is precisely the equality that is supposed to hold but doesn't:

`organization whose secret authenticated the request == owner(repository written to by the handler)`

An attacker who is a legitimate tenant of the Shipit instance — i.e., they onboarded their own GitHub organization/App and therefore know their own `webhook_secret` — can POST directly to the public `/webhooks/github` endpoint (this is a plain HTTP endpoint, not restricted to genuine GitHub-origin traffic) with a crafted body such as:

```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>"
}
```

signed with `X-Hub-Signature` computed using the attacker's own known `webhook_secret` for `attacker-org`. `repository_owner` resolves to `"attacker-org"`, so `verify_signature` succeeds using the attacker's own secret. `PushHandler`, however, resolves the target stacks via `repository.full_name`, which is `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen-sha>")` on stacks the attacker does not own or have any relationship to.

### Impact Explanation
This allows an attacker with no privileges on the victim organization/repository to force victim `Stack`s to sync against an attacker-chosen commit SHA (`GithubSyncJob`/`sync_github`), i.e., a cross-tenant, cross-repository write into state that drives Shipit's deploy pipeline (continuous deployment, merge queue triggers, deployable status, etc.) for a repository the attacker does not control. This matches the "cross-repository writes" / "unauthorized deploy" impact tier: the trust boundary broken is exactly the "organization that authenticated versus the repository that is written" pattern called out as in-scope.

### Likelihood Explanation
Likelihood is moderate-to-high in any Shipit deployment that onboards more than one GitHub organization/tenant (a documented, supported multi-org configuration). Any tenant who has legitimately set up their own GitHub App/webhook secret in such a deployment can mount this attack with a single crafted HTTP request; no compromise of the victim's credentials, GitHub access, or Shipit account is required — only knowledge of the attacker's own (legitimately possessed) webhook secret, which is the exact "unprivileged-attacker breaks a deployment-trust binding" scenario the rules target.

### Recommendation
Bind the organization used for signature verification to the same field used to resolve the target repository. Either:
1. Verify that `repository.full_name`'s owner segment matches `repository_owner` before dispatching to handlers, rejecting mismatches, or
2. Have `Handler#repository_name` resolve strictly from the already-verified `repository_owner`/organization context rather than re-reading `repository.full_name` independently from the payload.

### Proof of Concept
1. Attacker legitimately onboards `attacker-org` into the multi-tenant Shipit instance and thus knows its `webhook_secret` (`lib/shipit/github_app.rb`, `@webhook_secret`).
2. Attacker crafts a `push` event body:
   ```json
   {"repository":{"owner":{"login":"attacker-org"},"full_name":"victim-org/victim-repo"},"ref":"refs/heads/master","after":"deadbeefcafebabe..."}
   ```
3. Attacker computes `X-Hub-Signature: sha1=<hmac>` over the raw body using `attacker-org`'s known secret and POSTs it to `/webhooks/github` with header `X-Github-Event: push`.
4. `WebhooksController#verify_signature` resolves `repository_owner` → `"attacker-org"`, fetches `attacker-org`'s secret, and the HMAC matches → request accepted.
5. `PushHandler#process` resolves stacks via `payload.dig('repository','full_name')` → `"victim-org/victim-repo"`, and calls `stack.sync_github(expected_head_sha: "deadbeefcafebabe...")` on the victim's stack, an org the attacker has no relationship with. [1](#0-0) [4](#0-3) [5](#0-4)
