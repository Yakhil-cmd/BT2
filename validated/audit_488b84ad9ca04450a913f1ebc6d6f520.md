### Title
Cross-tenant CommitStatus forgery via unscoped `Commit.where(sha:)` in StatusHandler - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` verifies the webhook signature against the GitHub App/organization identified purely by `params.dig('repository','owner','login')`, but `StatusHandler#process` then looks up commits by `Commit.where(sha: params.sha)` with no filter tying the match back to that same repository/organization. Because `Commit` rows are only unique per `(sha, stack_id)` (not globally), any actor who controls a repository whose signature verifies (attacker-org) can trigger a `CommitStatus`/`Status` write on a `Commit` row belonging to an entirely different stack/organization, as long as a commit with the same `sha` exists there.

### Finding Description
The claimed binding is: `organization verifying signature (repository.owner.login in payload, checked against Shipit.github(organization: repository_owner).verify_webhook_signature)` == `organization owning the commit(s) mutated by commit.create_status_from_github!`.

Code path:
- `app/controllers/shipit/webhooks_controller.rb#verify_signature` (lines 24-49) computes `repository_owner` from `params.dig('repository','owner','login')` [1](#0-0)  and validates the HMAC signature using `Shipit.github(organization: repository_owner).verify_webhook_signature` [2](#0-1) . This only proves the request bytes were signed with *that org's* webhook secret — it says nothing about which `Commit`/`Stack` rows in the DB the payload's `sha` should affect.
- `#create` then dispatches the parsed JSON to the registered handler for the event [3](#0-2) .
- `StatusHandler#process` performs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [4](#0-3) . This query is **global**, not scoped by `stack`, `repository`, or `repository_name` at all.
- Contrast with `PushHandler#process`, which correctly scopes to `stacks` derived from `Repository.from_github_repo_name(repository_name)` before acting [5](#0-4) , and with the base `Handler#stacks`/`#repository_name` helpers that exist precisely for this purpose [6](#0-5) . `StatusHandler` does not use `stacks`/`repository_name` at all.
- The DB schema confirms commits are only unique per `(sha, stack_id)`, not globally: `add_index :commits, %i(sha stack_id), unique: true` [7](#0-6) . Multiple stacks (belonging to different repositories/organizations) can therefore each have a `Commit` row with the same `sha` — this is expected in practice for forks, mirrors, or shared history, since git SHAs are content-addressed and identical commits copied into a different repository (e.g., via a fork) retain the same SHA in both places.

Exploit flow: Attacker owns `attacker-org/some-repo` (or a fork) which is configured as a Shipit stack (or otherwise has a `Repository`/`webhook_secret` for `attacker-org` registered in `Shipit.github`). Attacker force-pushes/creates a commit whose SHA matches a real commit already tracked by Shipit for `victim-org/repo` (trivial via forking — the SHA is identical by construction). Attacker sends `POST /webhooks` with `X-Github-Event: status`, payload `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<shared-sha>", "state": "success", ...}`, signed with `attacker-org`'s own `webhook_secret` (which the attacker controls/knows because it's their own GitHub App/org integration). `verify_signature` passes because the signature is valid for `attacker-org`. `StatusHandler#process` then finds **all** `Commit` rows across the whole database with that `sha`, including the one belonging to `victim-org`'s stack, and calls `create_status_from_github!` on it, writing a `Status` row via `Status.replicate_from_github!` [8](#0-7)  and `Commit#create_status_from_github!` [9](#0-8) .

None of the existing guards prevent this: `verify_signature` authenticates the sender's org, not the target of the mutation; the `ExplicitParameters` schema in `StatusHandler` only validates types/presence of `sha`/`state`/etc, not repository ownership [10](#0-9) ; and `drop_unhandled_event`/`check_if_ping` are unrelated to this check.

### Impact Explanation
A forged `CommitStatus` (`Status` row) is written onto a victim organization's commit without that organization's webhook secret or authorization. This is a cross-tenant write: a payload signed by `attacker-org` mutates state belonging to `victim-org`'s stack. Since `Status` affects `Commit#deployable?`/`Commit#blocked?` (CI gating) and can enable/trigger `enable_ci_on_stack`, `schedule_continuous_delivery`, `ProcessMergeRequestsJob`, etc. [11](#0-10) [12](#0-11) , an attacker can fabricate a fake "success" CI status to unblock/deploy or a fake "failure" to block a legitimate deploy on a victim's stack. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker needs any repository/org that is registered with Shipit's GitHub App config (i.e., `Shipit.github(organization: repository_owner)` resolves without raising `GithubOrganizationUnknown`), and they need a commit whose SHA coincides with a commit already tracked in a victim stack — trivially achievable by forking the victim repo or otherwise obtaining identical commit content. No Shipit session, API token, or victim secrets are required; only the attacker's own legitimate webhook signature for their own org. This is repeatable against any `sha` shared across stacks and is not rate-limited by any check in this path.

### Recommendation
Scope `StatusHandler#process` (and audit other handlers for the same pattern) to only touch commits belonging to stacks whose repository matches the payload's `repository.full_name`/owner, mirroring `PushHandler`'s use of the `stacks` helper, e.g. `stacks.flat_map(&:commits).select { |c| c.sha == params.sha }` or `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test ":status from an unrelated org must not create a status for a commit in another org's stack" do
  # victim commit lives in a different stack/repo than the payload's repository.owner
  victim_commit = shipit_commits(:first) # belongs to shipit_stacks(:shipit)

  request.headers['X-Github-Event'] = 'status'
  body = JSON.parse(payload(:status_master)).merge(
    'sha' => victim_commit.sha,
    'repository' => { 'owner' => { 'login' => 'attacker-org' }, 'full_name' => 'attacker-org/some-repo' }
  ).to_json

  # signature verification stubbed/valid for attacker-org only
  GithubHook.any_instance.stubs(:verify_signature).returns(true)

  assert_no_difference -> { victim_commit.statuses.count } do
    post :create, body:, as: :json
  end
end
```
This test demonstrates the equality `repository_owner (attacker-org, signature-verified)` != `victim_commit.stack.repository.owner (victim-org)` is not enforced, and currently fails against `StatusHandler#process` as written (asserting no difference would fail because a `Status` row IS created for the victim's commit).
