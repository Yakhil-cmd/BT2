### Title
CCMenu Controller Ignores API Client's Stack Scope, Exposing Any Stack's Deploy/Lock Status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController` overrides the base `stack` lookup so it never checks whether the authenticated `ApiClient` is scoped to a particular stack. This breaks the binding **"a stack a token authorises versus a stack it touches"**: a token created with `read:stack` permission and restricted to `stack_id: A` can be used to read status/lock/build data for **any** stack `B` on the install, simply by changing the `stack_id` request parameter.

### Finding Description
`ApiClient` supports being scoped to a single stack via `belongs_to :stack, optional: true` [1](#0-0) . The generic API base controller enforces this scope everywhere by resolving the requested stack only from within the set of stacks the client is authorized for:

```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`CCMenuController`, however, overrides `stack` and resolves it directly against the global `Stack` relation, bypassing `stacks` entirely:

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [3](#0-2) 

The controller still declares `require_permission :read, :stack` [4](#0-3) , but `check_permissions!` only tests whether the string `"read:stack"` is present in the client's `permissions` array — it has no notion of *which* stack [5](#0-4) . The actual per-stack restriction is supposed to come exclusively from the `stacks`/`stack` scoping helper in `BaseController`, which `CCMenuController` deliberately skips.

The verified/authorized side of the binding is: *token → `ApiClient#stack_id` (the one stack it was issued for)*. The acted-upon side is: *`params[:stack_id]` → any `Stack` in the database*. Nothing ties these together in `CCMenuController#show`, so the equality `token.authorized_stack == stack_acted_on` is not enforced, even though it is enforced for every other stack-scoped API endpoint that relies on `BaseController#stack`.

### Impact Explanation
Exploiting this returns cross-stack information disclosure: `deploys_and_rollbacks.last` state (running/backlogged/locked, last build time, last deploy id) for a stack the token was never meant to see [6](#0-5)  and [7](#0-6) . This qualifies as the "unauthenticated/unauthorized read of stack state" High-impact category: a legitimately-issued, narrowly-scoped credential is used to read state for repositories/environments outside its granted scope, which is exactly the escalation the `ApiClient.stack_id` scoping mechanism exists to prevent.

### Likelihood Explanation
Likelihood is high for any deployment that issues stack-scoped tokens (the schema and fixtures — e.g. `here_come_the_walrus` in `test/fixtures/shipit/api_clients.yml` — explicitly demonstrate a client scoped to a single stack with `read:stack` permission) [8](#0-7) . Any holder of such a token (an "unprivileged" client compared to other stacks) can trivially enumerate `stack_id` values to read data for stacks it was not authorized for — no additional privilege, secret, or session is required beyond the token itself, which is exactly the class of credential this endpoint is designed to accept (`params[:token]`) [9](#0-8) .

### Recommendation
Remove the `CCMenuController#stack` override, or make it consistent with `BaseController#stack`/`#stacks` so that the requested `stack_id` is resolved only from the set of stacks the authenticated `ApiClient` is scoped to:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

Delete the private `stack` method entirely (inheriting `BaseController#stack`) so the stack-scope check present everywhere else in the API is also enforced here.

### Proof of Concept
1. Admin issues an `ApiClient` with `permissions: ["read:stack"]` and `stack: <stack A>` (supported by the schema/fixtures, e.g. `here_come_the_walrus`).
2. Attacker holding this token requests:
   `GET /api/stacks/<stack_B>/cc.xml?token=<token>` where `stack_B != stack A`.
3. `authenticate_api_client` succeeds (token is valid) [9](#0-8) .
4. `require_permission :read, :stack` passes because the client has the `read:stack` string in its permission list, regardless of stack [5](#0-4) .
5. `stack` resolves `stack_B` directly via `Stack.from_param!`, bypassing the `stacks` scope that would have raised `RecordNotFound` for a client scoped to stack A [3](#0-2) .
6. The response discloses stack_B's build/lock/deploy status, which the token was never authorized to view.
