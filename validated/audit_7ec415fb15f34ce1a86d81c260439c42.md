### Title
Webhook signature is verified for the organization named in `repository.owner.login`, but the handlers act on the unrelated `repository.full_name` field, allowing cross-repository event spoofing - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App / `webhook_secret` to use for HMAC verification based on the payload's `repository.owner.login` (or `organization.login`) field, but every webhook `Handler` subsequently resolves the target `Stack` to mutate using a completely different payload field, `repository.full_name`. Because these two fields are never cross-checked against each other, an attacker who can produce a validly-signed payload for *any* one onboarded GitHub organization can forge events (pushes, statuses, check suites) that are applied to a `Stack`/`Repository` belonging to a *different* organization tracked by the same Shipit instance.

### Finding Description
The signature check binds trust to an organization derived from the payload itself: [1](#0-0) [2](#0-1) 

`repository_owner` is read straight from attacker-controlled JSON (`params.dig('repository','owner','login')` or `organization.login`), and `Shipit.github(organization: repository_owner)` is used to fetch the corresponding `webhook_secret` for HMAC comparison: [3](#0-2) 

Crucially, `verify_webhook_signature` treats a missing/optional `webhook_secret` (documented as optional in `docs/setup.md`) as "verified" (`return true unless webhook_secret`), and even when a secret is set, it only proves the payload was signed by *some* org's secret — not that the `full_name` embedded in the body actually belongs to that org.

Every handler that mutates state ignores `repository.owner.login` entirely and instead looks up the target `Stack` via `repository.full_name`: [4](#0-3) 

This value is then used by `Repository.from_github_repo_name` to find any `Stack` in the system, without validating it matches the organization used to select the verification secret: [5](#0-4) 

Handlers such as `PushHandler` (triggers `stack.sync_github`), `StatusHandler` (creates a commit `Status` from `params`), and `CheckSuiteHandler` (schedules check-run refreshes) all operate on the `stacks` looked up this way: [6](#0-5) [7](#0-6) [8](#0-7) 

**The broken binding, stated as an equality that should hold but doesn't:**
`organization used to verify the HMAC (repository.owner.login)` == `organization that actually owns the repository/stack being written (repository.full_name)`.

Before the attack: a webhook is only trusted if it is genuinely signed by the secret of the organization that owns the target repository.
After the attacker's crafted request: the webhook is signed with organization A's secret (known to the attacker, or simply unset since it's optional), while `repository.full_name` names a repository belonging to organization B — a stack the attacker has no legitimate access to — and the handler happily processes it as authentic.

### Impact Explanation
This crosses a repository/authentication boundary explicitly called out in scope: "an organization that authenticated versus the repository that is written." Concretely:
- `StatusHandler` lets an attacker inject arbitrary CI `Status` records (`state: success`, arbitrary `sha`) onto commits of a `Stack`/repository they don't own, by naming that repository's `full_name` while authenticating as a different, attacker-controlled organization.
- `PushHandler`/`CheckSuiteHandler` similarly let an attacker trigger `sync_github` or check-run refresh jobs against foreign stacks.
- Combined with continuous deployment (`continuous_deployment: true`), forged passing CI statuses on a foreign stack can lead to an unauthorized deploy being triggered by Shipit's own scheduler — matching the "unauthorized deploy" Critical/High impact bucket.

### Likelihood Explanation
Any Shipit deployment configured for more than one GitHub organization (a documented, supported configuration — see `config/secrets.development.shopify.yml`) is affected as soon as one organization's payload can be crafted/replayed with a spoofed `repository.full_name`. If any onboarded organization has no `webhook_secret` set (explicitly documented as "optional"), the attack requires no secret knowledge at all — `verify_webhook_signature` returns `true` unconditionally for that organization — making this a fully unauthenticated cross-repository write in that configuration.

### Recommendation
After signature verification, require that the organization used to select the verification secret (`repository.owner.login` / `organization.login`) matches the owner encoded in `repository.full_name` before dispatching to any handler, e.g. reject the webhook if `payload.dig('repository','full_name')&.split('/')&.first != repository_owner`.

### Proof of Concept
1. Shipit is configured with two organizations, `org-a` (attacker-controlled, `webhook_secret` known to the attacker or left blank) and `org-b` (victim, has a tracked `Stack` for `org-b/secret-repo`).
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and body:
```json
{
  "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/secret-repo" },
  "sha": "<victim-commit-sha>",
  "state": "success",
  "context": "ci/forged"
}
```
signed (or left unsigned, if `org-a` has no `webhook_secret`) using `org-a`'s secret.
3. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and verifies successfully against `org-a`'s secret/HMAC.
4. `StatusHandler#process` resolves the commit purely from `params.sha` and creates a `Status`, unaffected by which organization actually authenticated — see [7](#0-6)  — forging a passing CI status on `org-b`'s commit despite the request being authenticated only as `org-a`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
