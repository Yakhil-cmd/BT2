### Title
Webhook signature verification binds to a different payload field than the one used to select the target repository, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate against using `repository.owner.login` (falling back to `organization.login`), but the event handlers that actually act on the payload (e.g. `Shipit::Webhooks::Handlers::Handler#repository_name` / `PushHandler`) select the target `Repository`/`Stack` using the independent `repository.full_name` field. Because these are two distinct, attacker-controlled JSON fields inside the same payload, an attacker who legitimately controls a GitHub App/organization already configured on the Shipit instance (and thus knows that organization's `webhook_secret`) can forge a payload whose `repository.owner.login` matches their own org (so signature verification succeeds with their known secret) while `repository.full_name` points at a completely different, victim organization's repository.

### Finding Description
`verify_signature` in <cite repo="Ellentat/shipit-engine--017" path="app/controllers/shipit/webhooks_controller.rb" start="24,59" end="30,62" /> computes `repository_owner` from `params.dig('repository', 'owner', 'login')` (or `organization.login`) and uses it to fetch the corresponding `Shipit.github(organization: repository_owner)` app config to verify the HMAC signature. This only proves that the request was signed by *some* organization's webhook secret — the one named in `repository.owner.login`.

Downstream, `Shipit::Webhooks::Handlers::Handler#repository_name` reads `payload.dig('repository', 'full_name')` [1](#0-0)  and uses it via `Repository.from_github_repo_name(repository_name)` to look up the `stacks` that will be acted on [2](#0-1) . `PushHandler#process` then calls `stack.sync_github(expected_head_sha: params.after)` for every matching, non-archived stack [3](#0-2) .

The binding broken is: **organization authenticated (`repository.owner.login`) ≠ repository that is written (`repository.full_name`)**. The signature only proves "this payload was signed by org A's secret"; it does not prove "this payload is legitimately about a repository belonging to org A." Since these are separate JSON keys that the attacker fully controls in the raw POST body they sign themselves, an org administrator (of *any* org already onboarded to the same Shipit instance) can set `repository.full_name` to `"victim-org/victim-repo"` while keeping `repository.owner.login` equal to their own org, producing a valid signature and a payload that gets routed to a stack they do not own.

### Impact Explanation
This lets an actor who is not authorized on the victim's stack trigger `GithubSyncJob` against that stack via a forged `expected_head_sha`, causing the job to fetch commits from GitHub for the victim repository using Shipit's own GitHub App credentials and append them / mark the stack as accessible/inaccessible, effectively forcing an unscheduled sync of an unrelated tenant's stack from cross-tenant-controlled webhook traffic. Other handlers keyed the same way (status, check_suite, membership, pull_request handlers) are equally reachable with a forged `full_name` versus verified `owner.login`, extending the primitive to writing `Status`, `CheckRun`, `MergeRequest` state on stacks the attacker does not administer. This crosses a repository/authorization boundary the signature was meant to enforce, satisfying the "cross-repository writes" / "unauthorized deploy" class of impact, though it requires the attacker to already administer at least one legitimately configured GitHub App/organization on the shared instance.

### Likelihood Explanation
Requires the Shipit deployment to host multiple organizations/GitHub Apps with independently configured webhook secrets (a documented, supported multi-org configuration — see `docs/setup.md`'s "Using Multiple Github Applications" section), and requires the attacker to control one of those onboarded orgs (i.e., know its `webhook_secret`) while targeting a different, victim org/repo on the same instance. This is a realistic scenario for shared/multi-tenant Shipit deployments but not exploitable against a single-organization deployment.

### Recommendation
After signature verification, cross-check that the organization used to select/verify the webhook secret (`repository.owner.login` / `organization.login`) matches the owner embedded in `repository.full_name` (and any other org identifiers used later, e.g. in `Repository.from_github_repo_name`) before dispatching to handlers. Reject the webhook (422) if they diverge, so the field the signature is scoped to and the field acted upon by handlers refer to the same repository/organization.

### Proof of Concept
1. Configure Shipit with two organizations, `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `docs/setup.md`, "Using Multiple Github Applications").
2. As the administrator of `attacker-org`'s GitHub App, craft a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "deadbeefdeadbeefdeadbeefdeadbeefdeadbeef",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Sign the raw body with `attacker-org`'s known `webhook_secret` using the same `sha1=` HMAC scheme as `Shipit::GithubApp#verify_webhook_signature` [4](#0-3) , and send it to `POST /webhooks` with `X-Github-Event: push` and `X-Hub-Signature`.
4. `verify_signature` resolves `repository_owner` to `"attacker-org"`, fetches that org's app, and the signature validates successfully [5](#0-4) .
5. `PushHandler` resolves the target repository via `repository.full_name` = `"victim-org/victim-repo"` [1](#0-0)  and enqueues `GithubSyncJob` for `victim-org/victim-repo`'s stack, which the `attacker-org` administrator does not own [3](#0-2) .

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
