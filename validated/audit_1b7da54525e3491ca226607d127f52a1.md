### Title
Unauthenticated P2P Staking Info Delivery Poisons Reward DB During FastSync — (`datasync/downloader/queue.go`, `datasync/downloader/downloader.go`)

### Summary

During FastSync, a remote peer can deliver `P2PStakingInfo` packets with fully attacker-controlled `CouncilRewardAddrs`, `CouncilNodeAddrs`, and `CouncilStakingAmounts`. The delivery validation function is a deliberate no-op (`// TODO-Kaia-Snapsync update validation logic`), and the data is written to the staking DB via `PutStakingInfoToDB` **before** `InsertReceiptChain` verifies the corresponding block. After sync, `GetStakingInfo` trusts the DB entry unconditionally (before Kaia fork), so the poisoned entries are used for block reward distribution and validator-set selection.

### Finding Description

**Step 1 — No-op validation in `DeliverStakingInfos`** [1](#0-0) 

Receipts and bodies both validate their content against the block header hash (`DeriveReceiptsRoot`, `DeriveTransactionsRoot`). Staking info has no equivalent check — the validate callback unconditionally returns `nil`.

**Step 2 — `PutStakingInfoToDB` called before `InsertReceiptChain`** [2](#0-1) 

The staking info is persisted to the DB in the loop over `results`, then `InsertReceiptChain` is called. If `InsertReceiptChain` fails, the poisoned DB write is not rolled back. Even when it succeeds, the content was never validated against the block's state root.

**Step 3 — `GetStakingInfo` trusts the DB unconditionally (pre-Kaia)** [3](#0-2) 

Before the Kaia hardfork, if a DB entry exists for `sourceNum`, it is returned immediately without re-reading from state. A poisoned entry is never overwritten by the correct state-derived value because `WriteStakingInfo` is only called when the DB entry is absent.

**Step 4 — Poisoned `RewardAddrs` flow into `FinalizeState`** [4](#0-3) 

`GetDeferredReward` calls `GetStakingInfo`, which returns the poisoned entry. The resulting `spec.Rewards` map — keyed by attacker-controlled addresses — is applied directly to state via `state.AddBalance`.

**Step 5 — `BlockNum` in the staking info itself is used as the DB key** [5](#0-4) 

The key passed to `PutStakingInfoToDB` is `result.StakingInfo.BlockNum`, which comes from the peer's response, not from the locally-validated header. An attacker can therefore write to an arbitrary staking interval slot in the DB, not just the one that was requested.

**Step 6 — Staking info is only fetched for pre-Kaia staking-interval blocks** [6](#0-5) 

The attack surface is limited to chains that have not yet activated the Kaia hardfork, or to the pre-Kaia portion of a chain that later activates it. After the Kaia fork, `GetStakingInfo` reads from the previous block's state and ignores the DB.

### Impact Explanation

A malicious P2P peer connected during FastSync can redirect block rewards (minting + deferred fees) from legitimate validator `RewardAddrs` to attacker-controlled addresses for every block in the affected staking interval. It can also substitute `NodeIds` and `StakingAmounts` to alter the weighted-random proposer selection, causing consensus divergence between the victim and honest nodes. Both effects persist durably in the staking DB and survive node restarts.

### Likelihood Explanation

The attacker only needs to be a reachable P2P peer while the victim is in FastSync mode. No governance keys, validator majority, or cryptographic break is required. FastSync is the default mode for nodes that are significantly behind the chain head, making this a realistic attack surface on newly bootstrapped nodes.

### Recommendation

1. Implement content validation in `DeliverStakingInfos` analogous to `DeliverReceipts`: derive the expected staking info from the block's state root (or a commitment in the header) and reject deliveries that do not match.
2. Move `PutStakingInfoToDB` to after a successful `InsertReceiptChain` call, and add a rollback path if the insert fails.
3. In `commitFastSyncData`, validate that `result.StakingInfo.BlockNum` matches `result.Header.Number.Uint64()` before writing to DB.
4. In `GetStakingInfo`, consider re-deriving from state and overwriting a stale/incorrect DB entry rather than trusting it blindly.

### Proof of Concept

1. Victim node starts FastSync against an attacker-controlled peer.
2. Attacker peer responds to `RequestStakingInfo` with a `P2PStakingInfo` whose `CouncilRewardAddrs` are all set to an attacker-owned address and whose `BlockNum` matches a staking-interval block.
3. `DeliverStakingInfos` accepts the packet (no-op validate).
4. `commitFastSyncData` calls `PutStakingInfoToDB(attackerBlockNum, attackerStakingInfo)` before `InsertReceiptChain`.
5. After FastSync completes, the victim node calls `GetStakingInfo(N)` for any block `N` in the affected interval.
6. `ReadStakingInfo` returns the poisoned entry; `GetStakingInfo` returns it without re-reading state.
7. `FinalizeState` calls `state.AddBalance(attackerAddr, blockReward)` — block rewards are redirected to the attacker.
