### Title
Donation-based share-price manipulation in the sample LP AA leads to rounding victim deposits to zero shares and fund theft - ([File: test/samples/uniswap_like_market_maker.oscript])

### Summary
The Uniswap-like market-maker Autonomous Agent shipped as a reference implementation in ocore (`test/samples/uniswap_like_market_maker.oscript`, mirrored in `test/ojson.test.js`) computes LP-share issuance as `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])`, where `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance` [1](#0-0) . Because `balance[base]`/`balance[$asset]` reflect the AA's *actual* on-chain balance and can be inflated by any address sending bytes/asset directly to the AA without matching any `if` case, an attacker can donate funds that raise `$bytes_balance` (the share-price denominator) without increasing `var['mm_asset_outstanding']` (the share supply). This is the same class of bug as the reported inflation attack: a low-cost manipulation of the deposit/share ratio that causes a subsequent depositor's `round()` computation to truncate to zero minted shares while their deposited assets remain in the pool, which the attacker (holding the existing shares) can later redeem.

### Finding Description
Three properties of the AA combine to enable the attack:

1. **Initial-deposit shortcut ignores asset value.** On the very first investment, `$issue_amount = balance[base]` regardless of how much of `$asset` was actually deposited [2](#0-1) . An attacker can seed the pool with a minimal amount of `$asset` (e.g., 1 unit) alongside a modest amount of bytes, receiving `mm_asset` shares 1:1 with bytes contributed, which sets an arbitrary, attacker-controlled ratio between `mm_asset_outstanding` and `bytes_balance`.

2. **No protection against un-tracked direct transfers.** Every subsequent case requires a specific combination of `trigger.output[[asset=base]]`/`trigger.output[[asset=$asset]]` to match (`invest`: base > 1e5 AND asset > 0; `divest`: mm_asset output nonzero; `exchange bytes→asset`: base > 1e5 AND asset == 0; `exchange asset→bytes`: asset > 0) [3](#0-2) . A payment of ≤1e5 bytes with no asset output matches none of these cases, so the AA silently keeps the funds without executing any state-changing logic — `balance[base]` grows but `var['mm_asset_outstanding']` does not. Repeating this (or sending it in larger single-message batches under the threshold) lets the attacker inflate `$bytes_balance` arbitrarily relative to `mm_asset_outstanding`.

3. **Naive proportional-share rounding.** With `$bytes_balance` inflated far beyond `mm_asset_outstanding`, a legitimate investor's `$investor_share_of_prev_balance = trigger.output[[asset=base]] / $bytes_balance` becomes a very small fraction; `round($investor_share_of_prev_balance * var['mm_asset_outstanding'])` rounds to `0` for any deposit that is small relative to the inflated balance [4](#0-3) . The victim's bytes and asset outputs are nonetheless absorbed into the AA's balance (no `mm_asset` is returned to them, and no bounce occurs since `$issue_amount` of `0` is still a valid payment amount... functionally the victim receives nothing for their deposit).

### Impact Explanation
When a genuine investor's deposit rounds to `0` shares, their contributed bytes/asset become part of `balance[base]`/`balance[$asset]` but are not represented by any `mm_asset` they hold. The attacker, who holds the entire (unchanged) `mm_asset_outstanding` supply, can subsequently `divest` and receive a proportional share of the now-larger `balance[base]`/`balance[$asset]`, effectively capturing the victim's deposit. This is a direct AA fund-loss/theft scenario reachable by any address that can post a unit — no privileged access is required, matching the "unauthorized spending" / "AA fund loss" bar from the reported inflation-attack class.

### Likelihood Explanation
The attack requires only ordinary unit-posting capability: (a) become an early/initial investor to control the outstanding-share baseline, (b) send several plain payments below the 1e5-byte case threshold to inflate `balance[base]` without touching `mm_asset_outstanding`, and (c) wait for or induce a legitimate small deposit. All steps use only standard `payment` messages triggering (or intentionally not triggering) the AA's documented `if` cases — no special privileges, races with network operators, or protocol-level bugs are needed, making this a realistically triggerable, moderate-cost griefing/theft vector for any AA built on this widely-referenced sample pattern.

### Recommendation
- Track pool reserves via explicit AA state variables (e.g., `var['bytes_reserve']`, `var['asset_reserve']`) updated only inside the state logic of matched cases, rather than reading live `balance[...]` which can be inflated by un-tracked direct transfers.
- On the initial deposit, mint shares based on a value function (e.g., using both the base and asset amounts, or a `sqrt(base*asset)`-style bonding formula as in Uniswap V2) instead of `balance[base]` alone.
- Add a minimum-liquidity/dead-share mechanism and/or bounce (rather than silently accept) trigger amounts that don't match any case, so unaccounted deposits cannot be used to skew share price.
- Reject or bounce `$issue_amount == 0` on invest, so investors are never silently diluted to zero shares while still contributing funds.

### Proof of Concept
1. Attacker sends a trigger with `trigger.output[[asset=base]] = 100001`, `trigger.output[[asset=$asset]] = 1` to `invest` in a freshly-defined pool (`mm_asset_outstanding` starts at 0). Per the initial-deposit branch, `$issue_amount = balance[base] = 100001`; attacker now owns all 100001 outstanding `mm_asset` shares while having contributed only 1 unit of `$asset` [2](#0-1) .
2. Attacker repeatedly sends plain payments of ≤1e5 bytes (with no `$asset` or `mm_asset` output) to the AA. None of the `if` conditions match (`invest` needs >1e5 bytes; `exchange bytes→asset` needs >1e5 bytes; others need asset/mm_asset outputs), so `balance[base]` grows arbitrarily while `var['mm_asset_outstanding']` stays at 100001 [5](#0-4) .
3. A victim sends a legitimate `invest` trigger with a modest byte amount relative to the now-huge `$bytes_balance`. `$investor_share_of_prev_balance` computes to a tiny fraction, and `round($investor_share_of_prev_balance * 100001)` evaluates to `0` — the victim's bytes/asset are added to the AA balance but they receive `0` `mm_asset` [4](#0-3) .
4. Attacker sends a `divest` trigger with their full 100001 `mm_asset` holding, receiving `round($investor_share * balance[$asset])` and `round($investor_share * balance[base])` — since `$investor_share = 1` (they own 100% of outstanding shares), they withdraw the entire pool, including the victim's uncredited deposit [6](#0-5) .
