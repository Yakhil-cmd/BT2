### Title
Permissionless `initialize` allows front-running/blocking of `initialize_with_permission` pool creation via deterministic PDA squatting - (File: programs/cp-swap/src/instructions/initialize.rs, programs/cp-swap/src/instructions/initialize_with_permission.rs)

### Summary
`initialize` is fully permissionless ("Address paying to create the pool. Can be anyone") [3](#0-2) , while `initialize_with_permission` gates the caller with a `Permission` PDA tied to the payer [4](#0-3) . Both instructions call the identical shared `create_pool` helper, deriving `pool_state` from the exact same seeds: `[POOL_SEED, amm_config, token_0_mint, token_1_mint]` [5](#0-4) , and this same `pool_state` key is reused (via `initialize_with_permission.rs` line 3 importing `create_pool`) [6](#0-5) . Since `AmmConfig` carries no marker restricting it to permission-gated pool creation only [1](#0-0) , an unprivileged actor lacking a `Permission` account can call the fully open `initialize` with the same `amm_config`/`token_0_mint`/`token_1_mint` triple that a permission-holder intends to use for `initialize_with_permission`, occupying the deterministic `pool_state`, `lp_mint`, vault, and `observation_state` PDAs first.

### Finding Description
This mirrors the DebtToken bug pattern: a resource identifier (an issuance hash for DebtToken; a `PoolState`/`lp_mint` PDA here) that should only be claimable through an authorized path is in fact claimable through an unauthorized public entrypoint using the identical derivation seeds, letting an attacker pre-empt the authorized party. Here, `create_pool`'s PDA derivation is shared verbatim between the permissioned and permissionless initializer paths [7](#0-6) , and the only shared guard is `amm_config.disable_create_pool`, which the config owner would have to leave `false` to allow the permissioned flow to work at all — but that same flag also permits the permissionless flow for the identical config [8](#0-7) [9](#0-8) .

### Impact Explanation
An attacker who front-runs a permission-holder's intended `initialize_with_permission` call for a specific `amm_config`+token pair, by calling permissionless `initialize` first with the same triple, will succeed in creating the pool via `init` on `pool_state`/`lp_mint`/`observation_state`. The permission holder's subsequent `initialize_with_permission` call will then fail (the `init` constraints require the accounts not already exist), permanently preventing that specific permissioned pool configuration from ever being created for that `amm_config`/mint pair. This denies the intended privileged effect (permission-gated pool creation) that the protocol relies on the `Permission` PDA check to enforce.

### Likelihood Explanation
The likelihood is limited by economics: unlike the DebtToken bug (attacker mints for free with zero cost), here the attacker must supply real `init_amount_0`/`init_amount_1` liquidity and pay the config's `create_pool_fee` to execute `initialize` [10](#0-9) , receiving LP tokens for their locked liquidity in return. This is consistent with standard permissionless-AMM pool creation (as in Uniswap V2/Raydium CP-swap generally) rather than a costless griefing vector, and it is unclear whether any legitimate workflow actually relies on a specific `amm_config` being used exclusively through `initialize_with_permission` for a not-yet-created pool — if permissioned and permissionless pool creation are simply expected to use disjoint `amm_config` indices in practice, this path has no practical impact.

### Recommendation
If `initialize_with_permission` is intended to guarantee that only permission holders can ever be the first to create a pool for a given `amm_config`/token pair, add an explicit flag on `AmmConfig` (or a separate marker account) designating "permission-required" configs, and enforce in `initialize` that such configs cannot be used by the permissionless path.

### Proof of Concept
1. Admin creates `amm_config` intending it to be used only via `initialize_with_permission` for token pair (`mintA`, `mintB`).
2. Before the permission holder acts, an attacker (with no `Permission` account) calls `initialize` with the same `amm_config`, `token_0_mint = mintA`, `token_1_mint = mintB`, providing arbitrary non-zero `init_amount_0`/`init_amount_1` and paying `create_pool_fee`.
3. `create_pool` succeeds and initializes `pool_state` at the deterministic PDA `[POOL_SEED, amm_config, mintA, mintB]` [11](#0-10) .
4. The permission holder's later call to `initialize_with_permission` with the identical `amm_config`/mint pair fails because `pool_state`, `lp_mint`, and `observation_state` `init` constraints reject already-initialized accounts [12](#0-11) .

**Confidence note:** I was unable to fully verify whether the deployment/off-chain tooling always allocates disjoint `amm_config` indices for permissioned vs. permissionless flows, which would neutralize this issue in practice — the on-chain program itself contains no such separation.
