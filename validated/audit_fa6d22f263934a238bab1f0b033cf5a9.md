### Title
Cross-repository CI status forgery via unscoped `Commit.where(sha:)` lookup in `StatusHandler` - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary

### Finding Description
The webhooks pipeline verifies the inbound GitHub webhook HMAC signature using a GitHub App secret selected from the *payload's* `repository.owner.login` (or `organization.login`) field: [1](#0-0) [2](#0-1) 

This establishes the binding: *organization that authenticated* = the org whose `webhook_secret` matched the signature, derived from `repository.owner.login`. Shipit explicitly supports configuring **multiple** GitHub Apps/organizations, each with its own `webhook_secret` (see `docs/setup.md` "Using Multiple Github Applications"), so a valid, independently-verifiable signature can originate from any one of several distinct orgs/repos onboarded onto the same Shipit instance.

Once the signature is verified, the event is dispatched to `StatusHandler`, which processes the payload **without any repository scoping**: [3](#0-2) 

Note that although the base `Handler` class defines a `repository_name`/`stacks` helper scoped to `payload.dig('repository','full_name')` ( [4](#0-3) ), `StatusHandler#process` does **not** use it — it queries `Commit.where(sha: params.sha)` globally across the entire database, and calls `commit.create_status_from_github!(params)` for every match, regardless of which repository/stack that `Commit` record belongs to.

`create_status_from_github!` unconditionally records a `Status` (`state`, `context`, `target_url`, `description`) on the matched commit: [5](#0-4) [6](#0-5) 

This is precisely the "trusted pointer without validation" bug class from the report: the bank tile trusted an unchecked `bank` pointer taken from an incoming fragment and used it directly in a privileged operation; here `StatusHandler` trusts an unchecked `sha` field taken from an incoming (correctly-signed, but repository-unscoped) webhook payload and uses it to select **any** commit in the datastore for a privileged write (a CI status that gates deploys), breaking the "organization that authenticated versus the repository that is written" binding required by the rules.

### Impact Explanation
A `Status` with `state: success` directly affects `Commit#deployable?`: [7](#0-6) 

and `required_statuses`/`ci.require` gating is driven by matching `Status#context` records on the commit (`app/models/shipit/deploy_spec.rb` `required_statuses`, `app/models/shipit/merge_request.rb` `StatusChecker`). `Status` creation also triggers `enable_ci_on_stack` and `schedule_continuous_delivery` ( [8](#0-7) ), which is the mechanism that drives Shipit's continuous-delivery auto-deploy pipeline.

Because Git commit SHA-1 hashes are deterministic over commit metadata (tree, parent, author, committer, message, timestamps), an attacker who controls **any** repository under **any** GitHub org/App onboarded to the same Shipit instance (which need not have any relationship to the target stack's repository — it only needs its own `webhook_secret` configured in Shipit's multi-org setup) can:
1. Reconstruct/replicate a commit object with an identical SHA to a real, unmerged/unreviewed commit sitting in the target stack.
2. Trigger a legitimate, correctly-signed `status` webhook for that SHA from their own (unrelated, unprivileged) repository/CI integration, with `state: success` and whatever `context` value satisfies `ci.require` for the victim stack.
3. Shipit accepts the signature (valid for the attacker's own org) and, due to the unscoped `Commit.where(sha:)` lookup, writes a forged "success" `Status` onto the victim commit in the victim stack — satisfying CI-gating and potentially triggering an unauthorized/continuous deploy of that commit.

This satisfies the Critical/High bar: "unauthorized deploy" via forged CI state, achieved purely by an unprivileged attacker with no Shipit session, no `ApiClient` token, and no write access to the target repository — only the ability to control any onboarded repo/org's own signed webhook traffic.

### Likelihood Explanation
Moderate-to-High in multi-organization Shipit deployments (a documented, supported configuration). The attack requires only: (a) the target repository is tracked by a Shipit instance that also onboards at least one org/app the attacker can independently trigger status events for, and (b) the attacker can predict or reconstruct a target commit SHA (straightforward for public repos, or for commits the attacker can observe via PR/branch activity). No credential theft, session, or write access to the victim repository is required — the core defect is purely the missing repository scoping in `StatusHandler`.

### Recommendation
In `app/models/shipit/webhooks/handlers/status_handler.rb`, scope the `Commit` lookup by the webhook's own `repository.full_name` (via the existing `stacks`/`repository_name` helpers already defined in `Handler`), e.g. resolve commits only through `stacks.flat_map(&:commits).where(sha: params.sha)` (or an equivalent `Commit.joins(stack: :repository).where(sha: params.sha, repositories: { name: ... })`), so a signed webhook for org/repo A can never write a status onto a commit belonging to stack/repo B.

### Proof of Concept
1. Configure Shipit with two GitHub Apps/organizations (per `docs/setup.md` "Using Multiple Github Applications"): OrgA (victim, owns target Stack/Repo) and OrgB (attacker-controlled, e.g. attacker's personal org with its own repo and its own valid `webhook_secret`).
2. In OrgB's repo, create a commit whose SHA is identical to an existing, undeployed commit SHA in OrgA's tracked stack (achievable by replicating tree/parent/author/committer/message/timestamps).
3. From OrgB's repo/CI, POST a GitHub Status API call (`state: success`, `context: <required ci context>`) for that SHA; GitHub relays a `status` webhook to Shipit signed with OrgB's `webhook_secret`.
4. `WebhooksController#verify_signature` resolves `repository_owner` from the payload (`OrgB`) and validates against `Shipit.github(organization: 'OrgB')` — signature passes.
5. `StatusHandler#process` executes `Commit.where(sha: params.sha)`, matching the commit in OrgA's stack (not OrgB's), and calls `create_status_from_github!`, writing a forged `success` status onto it.
6. Observe the OrgA commit's `deployable?`/`required_statuses` gating flip to satisfied, and (if continuous delivery is enabled) an unauthorized deploy is scheduled for a commit the attacker never had access to.
