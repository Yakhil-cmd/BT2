No vulnerability found for this question.

The Ajna report is about `_safeMint`'s ERC721 receiver callback (`onERC721Received`) letting an attacker's contract re-enter the mint function mid-execution before state is finalized. This bug class requires a mint path that synchronously calls into arbitrary, attacker-controlled code as part of minting.

Polkadot SDK's NFT-minting analogs don't have this shape:

- `pallet-nfts::mint`/`force_mint` dispatch into `Pallet::do_mint`, which performs all state mutation inside a single `Collection::<T, I>::try_mutate` closure (existence check, supply check, deposit reserve, `Item`/`Account` storage writes) and only emits the `Issued` event after the mutation closure returns successfully. There is no external call to attacker-supplied code during this sequence — no receiver hook analogous to `onERC721Received`. [1](#0-0) [2](#0-1) 
- `pallet-uniques::do_mint` follows the identical pattern: single `try_mutate`, deposit reserve, storage insert, then event — again no synchronous external callback point. [3](#0-2) 
- Item duplication is explicitly guarded by `ensure!(!Item::<T, I>::contains_key(collection, item), Error::<T, I>::AlreadyExists)` checked before the mutation begins, so even if a hypothetical reentrant call occurred, minting the same `(collection, item)` twice is rejected at the storage-existence check rather than relying on a reentrancy lock. [4](#0-3) 

The only place in this codebase where minting genuinely triggers user-controlled code during construction is contract/account creation in `pallet-contracts` and `pallet-revive`, and both already implement explicit reentrancy protections that were specifically hardened against exactly this class of bug (recursive instantiate at the same in-construction address, `allows_reentry`/`ReentrancyProtection::Strict` frame checks, and a `ReenteredPallet` guard for the top-level pallet). [5](#0-4) [6](#0-5) [7](#0-6)  This was even the subject of a specific fix (rejecting re-entrant instantiate at an in-construction address, matching EIP-684) rather than an open gap. [8](#0-7) 

Since no FRAME NFT/asset minting path performs a synchronous external callback to attacker code comparable to `_safeMint`, and the one subsystem that does (contracts/revive instantiate) already has dedicated, tested reentrancy guards, there is no demonstrable analog to this Ajna finding in the Polkadot SDK production code.

	fn run_guarded<R, F: FnOnce() -> Result<R, ExecError>>(f: F) -> Result<R, ExecError> {
