### Title
Assertion-based panic in `Bank::build_updated_stake_reward` when a stake account's delegation is mutated (e.g. via `Split`/`Merge`) between epoch-reward calculation and distribution - ([File: runtime/src/bank/partitioned_epoch_rewards/distribution.rs])

### Summary
`Bank::build_updated_stake_reward` recomputes a stake account's post-reward delegation at *distribution* time using a value (`partitioned_stake_reward.inflation.stake`) that was pre-computed several blocks earlier during the *calculation* phase, and then asserts that this pre-computed value is consistent with the live `StakesCache` state at distribution time. When the `relax_post_exec_min_balance_check` (SIMD-0392) feature is not active, any mismatch between the two hits an `assert_eq!` that panics the validator process. Because `Split`/`Merge` stake instructions are unprivileged operations that mutate `delegation.stake` directly and are permitted on delegated/activating stake accounts, a stake authority can race the reward pipeline (which spans multiple blocks at every epoch boundary) to desynchronize these two views and trigger the assertion deterministically on every validator replaying the same block, which is precisely the class of "selection precedes validation, and the later validation enforces an invariant that isn't actually guaranteed" bug described in the report (there, `_findOptimalDepositFarm` selects a farm without validating its cap is still valid at execution time).

### Finding Description
Reward distribution for stake accounts happens over multiple blocks (`REWARD_CALCULATION_NUM_BLOCKS`+ partitions). During the calculation phase, `calculate_stake_rewards_and_commissions` snapshots the stake account state and produces a `PartitionedStakeReward` containing `inflation.stake` — the delegation the account *should* have after rewards, computed from the stake state as of the calculation block [1](#0-0) .

Several blocks later, during the distribution phase, `store_stake_accounts_in_partition` re-reads the *live* `StakesCache` entry for the same stake pubkey and calls `build_updated_stake_reward` [2](#0-1) . Inside `build_updated_stake_reward`, when the `relax_post_exec_min_balance_check` feature is inactive (`adjust_delegations_for_rent == false`), the code asserts that the *live* stake's delegation plus the pre-computed reward exactly equals the *pre-computed* `new_stake.delegation.stake`: [3](#0-2) 

This assumes the stake account's `delegation.stake` did not change between the calculation block and the (later) distribution block. However, `delegation.stake` can be mutated directly by unprivileged, permissionless stake-program instructions such as `Split` and `Merge`, which are allowed on delegated/activating stake accounts (confirmed by `stake_merge_immediately_after_activation` test showing merges of active/just-activated stakes are permitted) [4](#0-3) , and `Split` is likewise usable on an existing delegated stake account by its stake authority [5](#0-4) . Any staker can issue a `Split` or `Merge` transaction against their own stake account in the window between the epoch-boundary calculation block and the block in which their partition is actually distributed (this window widens with the number of partitions, i.e., with the number of stake accounts receiving rewards that epoch — see `get_reward_distribution_num_blocks`) [6](#0-5) .

When this happens, the live `stake.delegation.stake` no longer matches what was captured in `partitioned_stake_reward.inflation.stake`, and `expected_delegation != new_stake.delegation.stake`, causing the `assert_eq!` to panic. This code path runs inside `distribute_partitioned_epoch_rewards`, which is invoked from block processing (i.e., consensus-critical, deterministically replayed by every validator) [7](#0-6) . Because every validator processes the same block containing the same (unchanged) stake state, the panic is deterministic and would occur simultaneously across the cluster.

This mirrors the report's bug class: a "selection"/pre-computation step (farm selection in the report; reward/delegation computation here) produces a decision based on state that is not re-validated against the live state at execution time, and the execution-time enforcement (the farm's cap check; here, the `assert_eq!`) fails because the precondition silently changed in between, causing repeated/deterministic failure of a shared, critical path (all future deposits in the report; block/epoch-reward processing here).

### Impact Explanation
If triggered, `assert_eq!` panics inside `Bank::build_updated_stake_reward`, which executes during normal block processing at every epoch boundary that has a multi-block partitioned reward distribution. A deterministic panic hit by all validators replaying the block would crash validator processes simultaneously, producing a cluster-wide halt at the epoch boundary — this matches the accepted impact category of "epoch-boundary halt" in the validation criteria. This is a liveness/availability issue affecting the entire network, not merely a single transaction.

### Likelihood Explanation
The trigger requires:
1. The `relax_post_exec_min_balance_check` feature being inactive on the target cluster (this is a real, gated feature in `feature-set/src/lib.rs`, meaning any cluster that has not yet activated it — e.g. devnet/testnet or a fresh cluster during rollout — is exposed) [8](#0-7) .
2. An unprivileged stake authority issuing a `Split` or `Merge` instruction against their own delegated stake account in the window between the epoch's reward-calculation block and the block where their specific partition is distributed.

Both preconditions are attacker-controllable without any special privilege — the attacker only needs to own a stake account with any non-zero delegation and can time an ordinary `Split`/`Merge` transaction. I was not able to determine from the available index whether `relax_post_exec_min_balance_check` is already permanently activated on mainnet-beta (this would need on-chain feature-activation status, not just source code), so exploitability specifically against mainnet-beta today is uncertain; the code path itself is unconditionally present and reachable when the feature is inactive.

### Recommendation
- Re-derive the expected delegation at distribution time from the *live* `StakesCache` state (as read in `store_stake_accounts_in_partition`) rather than asserting equality against a value pre-computed at calculation time; if a discrepancy is detected, gracefully skip/recompute rather than panicking.
- Alternatively, ensure the legacy (`adjust_delegations_for_rent == false`) branch cannot panic on user-triggerable state changes: replace `assert_eq!` with a fallible check that recomputes the reward proportionally to the live state, or defers to `DistributionError`-style handling (as already used for `AccountNotFound`/`ArithmeticOverflow`/`UnableToSetState`) instead of asserting.
- If the intent is that `Split`/`Merge` should be blocked once epoch rewards begin calculation but before distribution completes, consider enforcing that at the stake-program instruction level, or track the state actually used in the calculation phase and reconcile it deterministically without an unconditional `assert_eq!`.

### Proof of Concept
Not runnable within this analysis (no code-execution/test environment access here), but the trigger conditions can be reproduced conceptually as an integration test:
1. Start a test validator/bank with `relax_post_exec_min_balance_check` deactivated and a delegated stake account with enough stake distributed across enough validators/partitions that `get_reward_distribution_num_blocks` yields more than 1 partition.
2. At the epoch boundary, allow `begin_partitioned_rewards`/reward calculation to run, capturing `partitioned_stake_reward.inflation.stake` for the target account.
3. Before the block in which that account's partition would be distributed, submit a `Split` (or `Merge`) instruction from the stake authority against that same stake account, changing its `delegation.stake` in the live `StakesCache`.
4. Advance to the block where `distribute_epoch_rewards_in_partition` processes that account's partition; observe the `assert_eq!` panic in `build_updated_stake_reward` (as reachable via `store_stake_accounts_in_partition` → `distribute_partitioned_epoch_rewards`) [3](#0-2) .

    /// Calculate the number of blocks required to distribute rewards to all stake accounts.
    pub(super) fn get_reward_distribution_num_blocks(
        &self,
        rewards: &PartitionedStakeRewards,
    ) -> u64 {
        let total_stake_accounts = rewards.num_rewards();
        if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
            1
        } else {
            const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
            let num_chunks = total_stake_accounts
                .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
                as u64;

            // Limit the reward credit interval to 10% of the total number of slots in a epoch
            num_chunks.clamp(
                1,
                (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
            )
        }
    }
