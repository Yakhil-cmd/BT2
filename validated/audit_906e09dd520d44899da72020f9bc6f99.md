## Analysis

I traced the disclosed bug class — a mutating handler validating a *weaker* condition (room membership from a `read`-level join) instead of the actual authorization required for the mutating action (`write` permission) — to `wallet.js`'s `"sign"` message handler, which is reachable by any paired correspondent device sending a device message.

### Root cause

In `wallet.js`, the `"sign"` case of `handleMessageFromHub` (`doHandle`) resolves the target address via `findAddress()` and, when the address is locally controlled (`ifLocal`), it deliberately omits verifying that the message sender (`from_address`) is an actual cosigner of the wallet that owns the address: [1](#0-0) 

The check that would enforce this authorization is explicitly commented out: [2](#0-1) 

Compare this with the `ifRemote` branch, a few lines below, which *does* verify that the sender is a legitimate party to the signing path before forwarding/proxying: [3](#0-2) 

So for the `ifLocal` case, the only checks performed are structural (`body.address` is a valid address, `body.signing_path` matches the regex, the unit has valid authors/messages) — see the top of the handler: [4](#0-3) 

None of these validate that the *sender* of the `"sign"` message (`from_address`, derived from the device's pubkey, `wallet.js:94`) is actually a cosigner of the wallet/shared address that controls `body.address`. Once `ifLocal` fires, the wallet immediately raises a `"signing_request"` event, which typically triggers a user-facing signing/confirmation dialog carrying attacker-fully-controlled unit content (payment outputs, `data`, `signed_message`, etc.): [5](#0-4) 

This mirrors the disclosed pattern exactly: a weak, membership/existence-style check (`ifLocal`: "do I hold this signing path locally?") stands in for the real authorization check (`is this sender actually one of my cosigners for this wallet?`), and only the *final* consequence (private key actually signing) sits behind a different gate (in this case, the local user's approval of the dialog) — just as the original bug's persistence was gated by a separate, correctly-checked `document_save_handler`.

### Title
Any Paired Correspondent Device Can Trigger Unauthorized Signing Requests for a User's Wallet Keys - (File: wallet.js)

### Summary
The `"sign"` device-message handler in `wallet.js` verifies only that the requested `address`/`signing_path` pair is locally held by the device (`findAddress` → `ifLocal`), but does not verify that the message's sender is actually a cosigner of the wallet/shared address in question. The authorization check that would enforce this was intentionally removed/commented out to support "multilateral signing," but this leaves the door open for **any** paired correspondent device — not just genuine wallet cosigners — to submit an attacker-crafted `unsigned_unit` and trigger a `"signing_request"` event asking the victim to sign with their own private key.

### Finding Description
`findAddress()` recursively resolves `body.address`/`body.signing_path` down through `my_addresses` → `wallet_signing_paths` → `shared_address_signing_paths`, ultimately calling `ifLocal(objAddress)` whenever the resolved signing path is one this device actually holds a private key for [6](#0-5) . This resolution answers only "do I have keys for this path?" — an existence/ownership check analogous to the disclosed bug's Socket.IO room-membership check — but says nothing about who is allowed to *request a signature* over that path.

The `"sign"` handler in `wallet.js` uses exactly this weaker check as its sole gate before raising `signing_request`: [1](#0-0) 

The stronger, correct authorization check ("is the sender a cosigner on the wallet that owns this address?") is present in the code as a comment, explicitly disabled: [7](#0-6) 

Because `body.address` and `body.signing_path` are attacker-controlled inputs (any string satisfying `ValidationUtils.isValidAddress` and the `r(\.\d+)*` regex, see [8](#0-7) ), an attacker who is merely paired as a correspondent with the victim (via normal device pairing, `device.js:handlePairingMessage`) can address a `"sign"` request at *any* address/path the victim's device happens to control — including addresses belonging to multi-device wallets the attacker has no relationship to — and supply a fully attacker-crafted `unsigned_unit` (payment outputs, amounts, `data`, or a `signed_message`).

The only remaining gate before the private key is actually used is the wallet UI's `signing_request` confirmation dialog, which is populated straight from attacker-supplied data (`objUnit`, `assocPrivatePayloads`) via the emitted event, without the UI knowing that `from_address` was never validated as a legitimate cosigner of that specific address.

### Impact Explanation
If the victim approves the resulting confirmation dialog — plausible since nothing in the protocol distinguishes a legitimate cosigner's request from an arbitrary correspondent's — the victim's device will sign the attacker-supplied unit with the victim's own key at that signing path. For multisig/shared addresses this can contribute a valid signature toward a transaction that sends the victim's funds to attacker-controlled outputs, or falsely attest a `signed_message` as coming from that address/path. This is unauthorized use of a user's signing authority (integrity impact on wallet fund control), triggered purely by network-reachable device messaging from an unprivileged paired counterparty, matching the CWE-863 "Incorrect Authorization" class of the source report.

### Likelihood Explanation
Exploitation requires only that the attacker be paired as a correspondent device with the victim (a low bar — pairing secrets are exchanged out-of-band but pairing itself does not imply trust for wallet cosigning) and that the victim's wallet UI surfaces a signing confirmation the user approves. This is analogous to the source report's requirement that a write-access user eventually "save" tampered content — here, the analogous gate is the user approving the signing dialog. No network-level or node-level compromise is needed; the flaw is purely in `ocore`'s authorization logic for a wallet message handler.

### Recommendation
Restore (and generalize) the disabled authorization check in the `ifLocal` branch of the `"sign"` handler in `wallet.js`: before emitting `signing_request`, verify that `from_address` is actually registered as a cosigner/device of the wallet or shared address that owns `body.address` (e.g., via `extended_pubkeys`/`wallet_signing_paths`/`shared_address_signing_paths`, similar to the check already performed in the `ifRemote` branch). If multilateral (non-multisig) signing of arbitrary `signed_message` content must remain supported, gate it on an explicit application-level opt-in/context (e.g., separate message type or contract-linked correlation ID) rather than silently trusting any correspondent for any locally-held signing path.

### Proof of Concept
1. Victim pairs their wallet with Attacker's device as an ordinary correspondent (no wallet/cosigning relationship established).
2. Attacker crafts and sends a device message: `{subject: "sign", body: {address: <victim's known address>, signing_path: "r", unsigned_unit: <attacker-crafted unit paying attacker's address>}}`.
3. `handleMessageFromHub` → `doHandle()` reaches the `"sign"` case; structural validation passes; `findAddress` resolves the path to `ifLocal` since the victim's device genuinely holds that key.
4. Because the cosigner check is commented out, `signing_request` fires immediately with the attacker-controlled unit, address, and `from_address` set to the attacker's device — even though the attacker is not part of that wallet.
5. If the victim's wallet UI displays/approves the resulting dialog, the victim's device signs the attacker-crafted transaction, spending the victim's coins to the attacker's address.

function findAddress(address, signing_path, callbacks, fallbackInfo){
	db.query(
		"SELECT wallet, account, is_change, address_index, full_approval_date, device_address \n\
		FROM my_addresses JOIN wallets USING(wallet) JOIN wallet_signing_paths USING(wallet) \n\
		WHERE address=? AND signing_path=?",
		[address, signing_path],
		async function(rows){
			if (rows.length > 1)
				throw Error("more than 1 address found");
			if (rows.length === 1){
				var row = rows[0];
				if (!row.full_approval_date)
					return callbacks.ifError("wallet of address "+address+" not approved");
				if (row.device_address !== device.getMyDeviceAddress()) {
					const other_rows = await db.query("SELECT DISTINCT device_address FROM wallet_signing_paths WHERE wallet=? AND device_address!=?", [row.wallet, row.device_address]);

					return callbacks.ifRemote(row.device_address, other_device_addresses);

					address: address,
					wallet: row.wallet,
					account: row.account,
					is_change: row.is_change,
					address_index: row.address_index
				};
				callbacks.ifLocal(objAddress);
				return;
