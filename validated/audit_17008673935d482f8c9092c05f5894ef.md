### Title
Autonomous Agent AMM price manipulation via unaccounted "orphan" balance from bounced triggers - (File: `test/samples/uniswap_like_market_maker.oscript`, `aa_composer.js`)

### Summary
The Uniswap-like market-maker Autonomous Agent (AA) example computes swap/issuance ratios directly from the AA's raw ledger balance (`balance[$asset]`, `balance[base]`), exactly like the Surge `Pool.sol` computed shares from `LOAN_TOKEN.balanceOf(address(this))`. In ocore, an AA's `balance[asset]` is not a value the AA tracks in its own state; it is whatever total the protocol's `aa_balances` table records for that address [1](#0-0) . Any unit that sends funds to the AA address but does not match any of the AA's `if` cases is bounced by the composer, which keeps the configured bounce fee inside the AA and refunds only the remainder — permanently and silently adding the bounce fee to `aa_balances` without the AA's own `messages.cases` logic (and hence its `mm_asset_outstanding` state var) ever running [2](#0-1) .

### Finding Description
The market-maker AA keeps its own accounting variable `var['mm_asset_outstanding']` to represent the number of "shares" issued, and it prices deposits/exchanges using the *raw* balances of the pool: [3](#0-2) [4](#0-3) 

The `cases` mechanism requires every trigger to match one of the listed `if` conditions; if none match, `handleTrigger` reports "neither case is true" and the trigger is bounced [5](#0-4) . In the sample AA, both the "invest" and "exchange bytes→asset" cases only fire when `trigger.output[[asset=base]] > 1e5`, and the other cases require asset payments. Consequently, sending only bytes in the amount range `(bounce_fees.base, 1e5]` matches none of the cases, so the trigger is bounced.

When a real (non air-gapped) trigger is bounced, `bounce()` refunds `amount - fee` to the sender and keeps `fee` (the configured `bounce_fees.base`, minimum `constants.MIN_BYTES_BOUNCE_FEE`) inside the AA: [6](#0-5) 
This retained fee is folded into `aa_balances` via `updateFinalAABalances`, which simply nets all incoming/outgoing payment deltas against the address's balance row, with no hook back into the AA's own oscript state: [7](#0-6) 

The `balance[base]` read by the AA's oscript formulas is populated straight from this same table via the `balance` opcode [1](#0-0) , so every bounced trigger silently inflates `$bytes_balance` in the invest/exchange formulas without ever touching `var['mm_asset_outstanding']`, exactly mirroring the Surge report's core defect: a balance used for pricing/share math can be inflated by funds that never went through the code path that updates the corresponding accounting variable.

### Impact Explanation
Because `$current_ratio`, `$p` (constant product), and `$expected_asset_amount` are all derived from `balance[base]`/`balance[$asset]` rather than from a self-maintained ledger reconciled with `mm_asset_outstanding`, an attacker can cheaply and repeatedly nudge the pool's implied bytes reserve upward (each bounce costs the attacker only the bounce fee, which stays inside the AA) to:
- Skew the constant-product formula (`$p = $asset_balance * $bytes_balance`) used by the "exchange asset to bytes"/"exchange bytes to asset" cases, extracting more value than a correctly priced swap would allow, or
- Distort `$current_ratio` so that legitimate depositors are forced to bounce (wrong ratio) or receive incorrectly priced `mm_asset` shares, diluting/inflating the effective share price for other participants.

This is a concrete "market prices manipulation" issue: the pool's pricing state can be moved by any unprivileged unit poster without going through the deposit/exchange accounting that is supposed to gate all balance changes.

### Likelihood Explanation
Any address can post a payment unit to the AA's address; no special privilege, hub, or peer compromise is needed — only a normal `payment` message with an amount inside the un-matched byte range. The cost per manipulation is bounded by the AA's configured bounce fee (as low as `constants.MIN_BYTES_BOUNCE_FEE`), making repeated manipulation economically feasible, especially in the run-up to a large expected swap. This is squarely reachable by a "single posted unit," which the analysis rules identify as an in-scope actor.

### Recommendation
AAs (and any oscript AMM/pool pattern) that price operations off `balance[asset]` should reconcile that balance against an explicitly tracked reserve variable (e.g., `var['bytes_reserve']`, `var['asset_reserve']`) that is incremented/decremented only inside the matched cases, and treat any surplus (`balance[asset] - var['reserve']`) as unaccounted dust rather than folding it into pricing formulas. More generally, AA authors should add a catch-all case (as done in the `a_bank_without_percent.oscript` sample, which explicitly captures "silently accept coins") so that no incoming payment can be bounced-and-partially-retained without the AA's own state-tracking logic running. Documentation/samples that use `balance[...]` directly in AMM pricing (like `uniswap_like_market_maker.oscript`) should be updated to warn against this pattern, since it is the oscript equivalent of trusting `balanceOf(this)`.

### Proof of Concept
1. AA `uniswap_like_market_maker.oscript` is initialized and has an active pool (`mm_asset_outstanding > 0`).
2. Attacker posts a unit sending only bytes to the AA address with `10000 < amount <= 100000` (i.e., above `bounce_fees.base` but below the `1e5` threshold used by the "invest" and "exchange bytes→asset" cases), and no asset output.
3. `handleTrigger` evaluates the `cases` list: "invest" fails (`asset amount == 0`), "divest" fails (no `$mm_asset` output), "exchange bytes→asset" fails (`base <= 1e5`), "exchange asset→bytes" fails (`asset amount == 0`) — none matches, so `bounce("neither case is true...")` fires [5](#0-4) .
4. `bounce()` refunds `amount - bounce_fees.base` to the attacker and keeps `bounce_fees.base` bytes inside the AA [6](#0-5) ; `updateFinalAABalances` commits this to `aa_balances` [7](#0-6) .
5. `var['mm_asset_outstanding']` is unchanged, but `balance[base]` (read via the `balance` opcode from `aa_balances`) is now `bounce_fees.base` bytes higher.
6. Repeating steps 2–5 lets the attacker inflate `$bytes_balance` in the "exchange" and "invest" formulas at will, at the fixed cost of one bounce fee per iteration, skewing `$current_ratio`/`$p` used for subsequent swaps and deposits.
