### Title
Cross-tenant CI status forgery via SHA-only commit lookup, unbound from the webhook signature's organization - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a webhook against based solely on `repository_owner`, derived from the attacker-controlled JSON body itself (`params.dig('repository','owner','login')` or `params.dig('organization','login')`), and then looks up the app via `Shipit.github(organization: repository_owner)` to call `verify_webhook_signature`. [1](#0-0) [2](#0-1) 

Shipit explicitly supports hosting multiple, independent GitHub organizations/tenants in a single instance, each with its own `webhook_secret`, configured under `github.<org>.webhook_secret`. [3](#0-2) 

For the `status` event, `StatusHandler#process` never checks repository ownership at all — it matches purely on the git SHA across the *entire* `commits` table and writes a CI status onto every match: [4](#0-3) 

`Commit.create_status_from_github!` unconditionally persists the attacker-supplied `state`/`description`/`context` as a new status record for that commit. [5](#0-4) 

The signature-selection logic in `verify_signature` only proves the payload was signed by *some* configured org's secret (whichever `repository_owner` the attacker put in the body) — it never proves that the `sha` the handler acts on actually belongs to a commit tracked under that same organization's repositories. The equality that should hold is:

`organization whose secret verified the request == organization owning the repository/stack whose commit status is mutated`

but the code only enforces the left side (signature verification keyed by the attacker-chosen `repository_owner` field) and never checks the right side, because `StatusHandler` and `Commit.where(sha:)` do not scope by repository/stack/organization at all.

### Impact Explanation
An administrator of Org A (a legitimate tenant with its own GitHub App and `webhook_secret`, configured per `docs/setup.md`'s multi-app scheme) is an unprivileged attacker with respect to Org B's stacks — they hold no Shipit session, no `ApiClient` token, no `github_access_token` for Org B, and no write access to Org B's repository. Using only their own legitimately-provisioned webhook secret for Org A, they can:

1. Set `repository.owner.login` (or `organization.login`) = `OrgA` so `verify_signature` validates the HMAC using Org A's own secret.
2. Set `sha` in the same JSON body to the SHA of any commit that Shipit is tracking for an Org B stack (SHA1 is content-addressed and is often knowable/reproducible for public or previously-observed commits), and `state: "success"`.

Because `StatusHandler` looks up `Commit.where(sha: params.sha)` with no repository/stack filter, this forges a passing CI status on Org B's commit. Since `Commit#deployable?` gates continuous delivery and manual "ready to deploy" state on `success?` (i.e., on stored `statuses`), this can unlock/trigger an unauthorized deploy of an Org B stack that should have been blocked pending real CI results — satisfying the "unauthorized deploy" cross-repository-write impact class. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
Requires only knowledge of a JSON webhook body structure (publicly documented GitHub webhook format) and a legitimately-owned webhook secret for any one tenant configured on the shared Shipit instance — no compromise of any other tenant's secrets, sessions, or tokens is needed. This is realistic wherever the documented multi-org feature is used to host mutually distrusting teams/organizations on one Shipit deployment.

### Recommendation
- In `StatusHandler`, `CheckSuiteHandler`, and any other handler that resolves records by SHA, scope the lookup through `Repository.from_github_repo_name(payload.dig('repository','full_name'))` / `stacks` (as `PushHandler` already does) rather than a bare `Commit.where(sha:)`.
- In `WebhooksController#verify_signature`, after verifying the HMAC, assert that the `repository_owner`/`organization` used to select the verifying secret matches the owner segment of `repository.full_name` in the same payload, rejecting mismatches with `422`.
- Consider requiring that `Handler#stacks`/`Handler#repository_name` be derived consistently and cross-checked against whatever the controller used to authenticate the request, closing the organization-authenticated vs. repository-written gap analogous to the `onInstall`/`onUninstall` missing-state-check pattern in the source report.

### Proof of Concept
1. Configure Shipit with two tenants per the documented multi-app scheme: `OrgA` (attacker-controlled) and `OrgB` (victim), each with its own `webhook_secret`. [8](#0-7) 
2. Identify (or reproduce, since SHA1 is content-derived) the SHA of a commit Shipit already tracks for an `OrgB` stack.
3. Craft a `status` webhook JSON body:
```json
{
  "sha": "<OrgB tracked commit sha>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" } }
}
```
4. Sign the raw body with `OrgA`'s `webhook_secret` (HMAC-SHA1) and POST it to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha1=<hmac>`.
5. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` and verifies successfully against `OrgA`'s secret. [9](#0-8) 
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and calls `create_status_from_github!`, writing a forged "success" status onto the `OrgB` commit despite the request never having been authenticated by anything belonging to `OrgB`. [4](#0-3)

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
