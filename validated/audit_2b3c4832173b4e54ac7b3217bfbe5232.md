### Title
Webhook signature verification is bypassed by an attacker-controlled organization selector, letting a forged payload write to a target org/repository never covered by any valid signature - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App / webhook secret to verify a request against using a field taken directly from the unauthenticated JSON body (`repository.owner.login` or `organization.login`), then hands the *entire* body to event handlers that act on other, independently-controlled fields of the same body (`repository.full_name`, `team`, `member`, `organization`). If the organization used to pick the verification secret has no `webhook_secret` configured, `GithubApp#verify_webhook_signature` short-circuits to `true` for the *whole request*, so none of the payload's fields — including the ones that determine which stack/team/repository is actually mutated — are ever covered by a valid signature. This is the same class of bug as the reported `TradingAccountBranch::depositMargin` issue: one value (`repository_owner`, analogous to the "verified" scaled amount) is checked, while a different, unchecked value (`repository.full_name` / `team` / `member`, analogous to the actually-transferred amount) is the one actually acted upon.

### Finding Description
`verify_signature` computes the organization used for verification purely from the incoming payload: [1](#0-0) [2](#0-1) 

That organization is used to fetch a `GithubApp` instance and call `verify_webhook_signature`: [3](#0-2) 

Note line 77: `return true unless webhook_secret`. A multi-tenant `github:` configuration where some organizations have no `webhook_secret` set is a documented, supported configuration state: [4](#0-3) 

Once `head(422)` is *not* triggered, `WebhooksController#create` parses the raw body and dispatches it, unmodified, to every registered handler for the event: [5](#0-4) 

Handlers then locate the target `Stack`/`Repository` using a *different* field of the same payload — `repository.full_name` — which was never itself tied to the organization used for the signature check: [6](#0-5) 

Push/status/check_suite handlers all key off this decoupled `repository.full_name`/`stacks` lookup, e.g.: [7](#0-6) 

For the `membership` event specifically, the existing test suite shows the handler creates/updates local `Team`/`Membership` records purely from the `team`/`member`/`organization` fields of the body, with no cross-check against a specific repository owner at all: [8](#0-7) 

These `Team`/`Membership` records are exactly what `User#authorized?` consults to gate access to the entire Shipit UI/API: [9](#0-8) 

**The broken binding, as an equality:**
`organization used to select/verify the webhook signature (repository_owner)` ⇔ `organization/repository/team actually mutated by the handler (repository.full_name, team, member, organization)`.

Before the fix these must be equal for the verification to mean anything; the code never enforces this equality, and when the selected organization has no `webhook_secret`, the "verification" step is a no-op regardless of what the rest of the payload claims.

### Impact Explanation
An unprivileged network attacker (no GitHub App private key, no `webhook_secret`, no Shipit session, no repository access) can POST a forged webhook body directly to the public `WebhooksController#create` endpoint. By setting `organization.login` (or `repository.owner.login`) to any organization configured in `Shipit.github` that lacks a `webhook_secret` — a state the project's own sample configs treat as normal/expected — the attacker causes `verify_webhook_signature` to return `true` unconditionally for the entire raw body. The rest of the body (which references a *different*, actually-secured organization's repository, stack, or `Shipit.github_teams` team) is then processed as if it were a legitimate, signed event:
- A forged `membership added` event can add an arbitrary GitHub login to a `Team` matching one of `Shipit.github_teams`, which directly satisfies `User#authorized?` — an authentication/authorization bypass into the app.
- A forged `push`/`status`/`check_suite` event can trigger `sync_github`, create commit statuses, or refresh check runs for any tracked stack, independent of which organization "authenticated" the request.

This crosses the "escalation into `Shipit.github_teams` authorization" / "unauthenticated write of stack state" bar defined as in-scope High/Critical impact.

### Likelihood Explanation
Exploitability depends entirely on the operator's multi-organization `github:` configuration containing at least one organization without a `webhook_secret`. This is shown as an accepted, non-error configuration in the shipped sample files (`config/secrets.development.shopify.yml`, `test/dummy/config/secrets.test.json`), and nothing in `GithubApp#initialize` or `WebhooksController` rejects or warns about this combination when multiple organizations are configured. Any Shipit deployment serving more than one GitHub organization and setting up the App for a low-value/staging org without a webhook secret would be immediately exposed. I was not able to fully re-verify `MembershipHandler`'s source in this session (tool budget exhausted) — the membership-team-authorization path is inferred from `test/controllers/webhooks_controller_test.rb:129-149` and `User#authorized?`, and should be double-checked by reading `app/models/shipit/webhooks/handlers/membership_handler.rb` directly before treating this as fully confirmed.

### Recommendation
Bind the organization used for signature verification to the same field(s) the handlers subsequently act on, and refuse to treat a missing `webhook_secret` as an automatic pass when the payload references a different, secured organization/repository. Concretely:
- Require every configured GitHub organization to have a non-blank `webhook_secret`, or fail closed (`head(422)`) instead of returning `true` when `webhook_secret` is blank.
- After verification, re-derive the acting organization/repository from the payload and assert it matches the organization/config used to verify the signature before invoking handlers.

### Proof of Concept
Given a Shipit deployment configured with two organizations, `secure-org` (has `webhook_secret`) and `open-org` (no `webhook_secret`):
```
POST /github/webhooks
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "organization": { "login": "open-org" },
  "team": { "id": <id of a team in Shipit.github_teams belonging to secure-org>, "slug": "developers", "name": "Developers", "url": "https://example.com" },
  "member": { "login": "attacker-controlled-login" }
}
```
`repository_owner` resolves to `"open-org"` (no `repository` key present, falls back to `organization.login`); `Shipit.github(organization: "open-org").verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank for `open-org`. `MembershipHandler` then processes the `team`/`member` fields, which belong to `secure-org`'s authorization team, creating a `Membership` for `attacker-controlled-login` without ever presenting a valid signature for `secure-org`.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
