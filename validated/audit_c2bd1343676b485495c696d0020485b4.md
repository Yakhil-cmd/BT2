### Title
Malicious Recipient in KLAY Bridge Transfer Permanently Locks All Subsequent Cross-Chain Transfers — (`node/sc/bridge_manager.go`, `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

---

### Summary

A user who bridges KAIA to a contract address that reverts on receiving native tokens can permanently block the service-chain bridge operator from processing that nonce and every subsequent nonce. The bridge event loop re-enqueues the failing event indefinitely with no skip mechanism, mirroring the H-3 pattern exactly: an unrecoverable external call failure inside a sequential loop permanently locks bridged assets.

---

### Finding Description

**Step 1 — User-controlled recipient in `requestKLAYTransfer`**

On the source chain a user calls:

```solidity
function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable
```

`_to` is fully user-controlled and is recorded in the emitted `RequestValueTransfer` event with a monotonically increasing `requestNonce`.

**Step 2 — `handleKLAYTransfer` reverts when `_to` cannot receive KLAY**

On the destination chain the bridge operator calls `handleKLAYTransfer`. After updating all nonce state it does a low-level call:

```solidity
(bool ok, ) = _to.call.value(_value)("");
require(ok, "handleKLAYTransfer: transfer failed");
``` [1](#0-0) 

If `_to` is a contract whose fallback reverts (or has no payable fallback), `ok` is `false`, the `require` fires, and the entire transaction reverts — including the earlier state writes that would have marked the nonce as handled.

**Step 3 — Go-level error causes unconditional re-enqueue of the failing event**

The Go bridge operator calls the binding `bi.bridge.HandleKLAYTransfer(auth, ...)`. Because the EVM simulation during gas estimation detects the revert, the call returns an error. `handleRequestValueTransferEvent` propagates that error to `processingPendingRequestEvents`:

```go
if err := bi.handleRequestValueTransferEvent(ev); err != nil {
    bi.AddRequestValueTransferEvents(ReadyEvent[idx:])   // re-enqueue failing event + all after it
    logger.Error("Failed handle request value transfer event", ...)
    return
}
``` [2](#0-1) 

`ReadyEvent[idx:]` includes the failing event and every event with a higher nonce. All of them are pushed back into `pendingRequestEvent`.

**Step 4 — The bridge loop retries forever**

`BridgeInfo.loop()` calls `processingPendingRequestEvents()` on every tick (every second) and on every new event:

```go
for {
    select {
    case <-bi.newEvent:
        bi.processingPendingRequestEvents()
    case <-ticker.C:
        bi.processingPendingRequestEvents()
    ...
    }
}
``` [3](#0-2) 

Because the failing nonce is always re-enqueued at the front (lowest nonce), every retry attempt hits the same permanently-reverting event first. There is no counter, no skip-after-N-failures, and no admin API to advance `lowerHandleNonce` past a stuck nonce.

**Step 5 — VT recovery makes no difference**

`valueTransferRecovery.recoverPendingEvents()` simply calls `AddRequestValueTransferEvents` again with the same events:

```go
vtr.pBridgeInfo.AddRequestValueTransferEvents(events)
``` [4](#0-3) 

The recovery path feeds the same stuck event back into the same loop.

---

### Impact Explanation

All KAIA bridge transfers with a nonce ≥ the stuck nonce are permanently undeliverable. The KAIA locked in the bridge contract for those transfers cannot be released. The `lowerHandleNonce` in the Solidity contract never advances past the stuck nonce because `_updateHandleNonce` is only reached after the `require(ok, ...)` check, which always reverts. [5](#0-4) 

This matches the "Unauthorized … lock … affecting KAIA, bridged assets" impact gate.

---

### Likelihood Explanation

The trigger requires only a standard user action: calling `requestKLAYTransfer` with `_to` set to any contract that lacks a payable fallback (e.g., a multisig, a DAO treasury, or a deliberately crafted griefing contract). No privileged access is required. The attacker does not need to control any validator or operator key.

---

### Recommendation

1. **In `processingPendingRequestEvents`**: Track a per-event retry counter. After a configurable threshold of consecutive failures for the same nonce, skip that event (log it as permanently failed) and continue processing subsequent nonces. This mirrors the fix applied in the original H-3 report (try-catch / fallback to stored creditor).

2. **In `BridgeTransferKLAY.sol`**: Replace the push-payment pattern with a pull-payment pattern. Record the owed amount in a mapping and let `_to` withdraw it, so a reverting recipient cannot block the nonce queue.

3. **Add an operator-accessible `skipNonce(uint64)` function** in the bridge contract that allows operators to mark a nonce as permanently skipped and advance `lowerHandleNonce`, providing an emergency escape hatch.

---

### Proof of Concept

1. Deploy a contract `Rejecter` with a reverting fallback on the destination chain.
2. On the source chain, call `requestKLAYTransfer(Rejecter, 1 ether, "")` — this emits `RequestValueTransfer` with nonce N.
3. Submit a second legitimate transfer to an EOA with nonce N+1.
4. Observe the bridge operator loop: every second it calls `HandleKLAYTransfer` for nonce N, the transaction reverts, and `ReadyEvent[N:]` (including nonce N+1) is re-enqueued.
5. Nonce N+1 is never processed. The KAIA for both transfers is permanently locked in the bridge contract. [6](#0-5) [7](#0-6)

// processingPendingRequestEvents handles pending request value transfer events of the bridge.
func (bi *BridgeInfo) processingPendingRequestEvents() {
	ReadyEvent := bi.GetReadyRequestValueTransferEvents()
	if ReadyEvent == nil {
		return
	}

	logger.Trace("Get ready request value transfer event", "len(readyEvent)", len(ReadyEvent), "len(pendingEvent)", bi.pendingRequestEvent.Len())

	for idx, ev := range ReadyEvent {
		if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
			logger.Trace("handled requests can be ignored", "RequestNonce", ev.GetRequestNonce(), "lowerHandleNonce", bi.lowerHandleNonce)
			continue
		}

		if err := bi.handleRequestValueTransferEvent(ev); err != nil {
			bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
			logger.Error("Failed handle request value transfer event", "err", err, "len(RePutEvent)", len(ReadyEvent[idx:]))
			return
		}
	}
