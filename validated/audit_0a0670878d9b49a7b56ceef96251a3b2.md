### Title
API-client stack scoping bypassed in `CCMenuController` — a token authorized for one stack can read any stack's build status - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
The H-24 bug class is a check that is not evaluated against the actual object being acted upon (the debt limit is checked before the new lien is included, so the check and the write diverge). In shipit-engine, the same class of bug appears as a scoping check that is bypassed by an overriding accessor: `Shipit::Api::BaseController#stack` enforces that an `ApiClient` may only touch the `Stack` it is scoped to, but `Shipit::Api::CCMenuController` redefines `stack` in a way that never applies that scoping, so the permission check and the object actually served diverge.

### Finding Description
`Shipit::Api::BaseController` scopes any stack lookup to the API client's authorization: [1](#0-0) 
```
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
Every other API controller (`DeploysController`, `TasksController`, `MergeRequestsController`, etc.) inherits `stack` unmodified, so an `ApiClient` created with a `stack_id` (i.e. scoped to a single stack) can never resolve any other stack: `stacks.from_param!` raises/404s for any `stack_id` param outside its scope.

`CCMenuController`, however, overrides `stack` directly against the unscoped model: [2](#0-1) 
```
class CCMenuController < BaseController
  require_permission :read, :stack
  ...
  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
```
`require_permission :read, :stack` only calls `ApiClient#check_permissions!`, which checks a *global* permission string list (`read:stack`, `write:stack`, …) with no notion of which stack is targeted: [3](#0-2) 
The per-stack authorization is entirely delegated to the `stacks`/`stack` accessor pattern in `BaseController`. Because `CCMenuController#stack` reimplements that accessor against `Stack.from_param!` instead of `stacks.from_param!`, the binding "the stack a token authorizes" (`current_api_client.stack_id`) is checked nowhere for this endpoint, while "the stack it touches" (`params[:stack_id]`) is fully attacker-controlled.

### Impact Explanation
This maps to the "unauthenticated/unauthorized read of stack state, task streams or deploy output" High-impact category: an `ApiClient` that was deliberately scoped to a single stack (e.g. issued to one team's CI dashboard) and holds only `read:stack` permission can query `GET /:stack_id/ccmenu.xml?token=<its token>` for any other stack ID in the Shipit instance and receive that stack's latest deploy status, build label, and activity — data the client's token was never authorized to see. This is exactly the "stack a token authorises" vs "stack it touches" binding called out in the analog rules.

### Likelihood Explanation
Trivial for anyone holding a valid, stack-scoped `ApiClient` token with `read:stack` permission (a normal, non-privileged credential by design — scoping to one stack is the whole point of `stack_id`): the attacker only needs to guess or enumerate another stack's `to_param` (name/environment) and issue a GET request with their own token; no privilege escalation on the token itself, no signing keys, and no repository write access are required.

### Recommendation
Change `CCMenuController#stack` to reuse the scoped accessor from `BaseController` (`stacks.from_param!(params[:stack_id])`) instead of the unscoped `Stack.from_param!`, so the `stack_id` authorization performed for every other API endpoint is also enforced here.

### Proof of Concept
1. Create two stacks, `stack-a` and `stack-b`.
2. Create an `ApiClient` scoped to `stack-a` (`stack_id` set) with `permissions: ['read:stack']`, and note its `authentication_token`.
3. Confirm scoping works elsewhere, e.g. `GET /api/stacks/stack-b?token=<token>` (or basic-auth with the token) returns 404/empty because `BaseController#stack` filters via `stacks`.
4. Request `GET /:stack-b_id/ccmenu.xml?token=<token>` (route mounted per `CCMenuController`). Because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` unscoped, the request succeeds and returns `stack-b`'s deploy status/activity XML, even though the token is only authorized for `stack-a`.
