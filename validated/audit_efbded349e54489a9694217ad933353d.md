### Title
Integer overflow in skill preview byte-budget check bypasses `maxTotalBytes` size limit - (File: pkg/cmd/skills/preview/preview.go)

### Summary
`renderAllFiles` in `pkg/cmd/skills/preview/preview.go` accumulates a running byte counter and compares it against a fixed cap using plain `int` addition without an overflow check, mirroring the zkSync bootloader bug where `add(refundGas, reservedGas)` was not overflow-checked before being compared with a limit.

### Finding Description
The loop that fetches "extra files" for a skill during `gh skill preview` enforces a size cap via: [1](#0-0) 
`f.Size` comes from the repository's git tree metadata returned by `discovery.ListSkillFiles`/the GitHub API — this is attacker-controlled content served by whatever repository the user points `gh skill preview` at (`opts.repo`, from `opts.RepoArg`). Since `f.Size` is read from JSON as an `int` and used directly in `totalBytes+f.Size > maxTotalBytes`, a malicious repository can declare a file's `Size` field as a very large value (e.g., close to `math.MaxInt`), causing the addition `totalBytes+f.Size` to overflow into a negative number on 64-bit platforms only for astronomically large sizes, or more practically, an attacker can chain multiple files whose declared sizes sum to just under `math.MaxInt` and then add one more large value to wrap the counter negative, defeating the `> maxTotalBytes` comparison and causing the loop to keep fetching/rendering unbounded content instead of stopping at the 512KB cap.

### Impact Explanation
This is a resource-exhaustion / cap-bypass issue reachable by an unprivileged remote attacker who merely publishes a "skill" repository that a victim previews with `gh skill preview <attacker/repo> <skill>`. This is a normal, expected `gh` workflow per the tool's own documentation (`skills/gh-skill/SKILL.md`), which explicitly recommends `gh skill preview` as a step before installing. Bypassing the byte cap can lead the CLI to fetch and buffer far more attacker-controlled content than intended, feeding much larger amounts of unsanitized/oversized content into the terminal-rendering pipeline than the size guard was designed to allow, defeating the safety limit's purpose (protecting the user's terminal/memory from large or excessive payloads during an unprivileged preview of untrusted content).

### Likelihood Explanation
Moderate-to-high: the trigger only requires publishing a public GitHub repository with a maliciously crafted git tree (fake `size` field for a blob — normal git blob metadata is attacker-controlled) and getting a user to run `gh skill preview` against it, which is an explicitly documented, expected, unprivileged usage pattern for discovering/reviewing third-party skills before install.

### Recommendation
Use overflow-safe accumulation and comparison, e.g. clamp/validate `f.Size` to a sane non-negative bound before adding, or use `math/bits` overflow-checked addition, or restructure the check as `if f.Size > maxTotalBytes-totalBytes` (still needs `totalBytes <= maxTotalBytes` invariant maintained) with an explicit guard against negative/oversized declared sizes from the API response rather than trusting `f.Size` as authoritative before the real byte count is known from `FetchBlob`.

### Proof of Concept
1. Attacker publishes a skill repository whose git tree lists an extra file with a `size` value engineered (via repeated large values or a single huge value) so that `totalBytes + f.Size` overflows `int` and produces a small/negative result at: [2](#0-1) 
2. Victim runs `gh skill preview attacker/repo <skill>`.
3. The `if totalBytes+f.Size > maxTotalBytes` check never trips due to overflow, so the loop continues fetching and rendering files (bounded only by `maxFiles = 20`, not by the intended 512KB byte budget), allowing far larger content volume to be pulled and printed than the size-limit control was designed to permit.

Note: I was unable to fully confirm within the available context whether `discovery.SkillFile.Size` is typed as `int`, `int64`, or otherwise bounds-checked upstream in `internal/skills/discovery` — the index did not surface that struct/field definition. If `Size` is validated or clamped before this point, the practical overflow window may be narrower than described; a Devin session with full repo access would be needed to confirm the exact type and any upstream validation.
