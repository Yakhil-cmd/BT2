### Title
Webhook signature verification uses `repository.owner.login` while repository/stack resolution uses `repository.full_name`, allowing cross-organization webhook forgery in multi-tenant configurations - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook against using the `repository.owner.login` field read straight from the *unverified* JSON body, while the handlers that actually act on the payload (`Shipit::Webhooks::Handlers::Handler#stacks` / `#repository_name`) resolve the target `Repository`/`Stack` using the *different* field `repository.full_name`, also from the same unverified body. Because these two fields are never cross-checked, an attacker who controls (or is a legitimate tenant admin of) one configured GitHub organization's webhook secret can forge a webhook whose signature validates against their own org, but whose `repository.full_name` points at a stack belonging to a completely different, unrelated GitHub organization also hosted on the same Shipit instance. This breaks the binding: `organization that authenticated == organization owning the repository being written`.

### Finding Description
`verify_signature` looks up the signing secret using `repository_owner`, computed exclusively from request body content: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` uses this attacker-supplied organization name to pick the `GitHubApp` config/secret to verify against: [3](#0-2) 

This is the documented "Using Multiple GitHub Applications" configuration where each organization has its own, distinct `webhook_secret` (docs/setup.md, lines 182-209, out of engine scope but explains the deployment model this code implements).

Once the signature check passes (using OrgA's secret because `repository.owner.login == "OrgA"`), `Webhooks.for_event(event)` dispatches to handlers such as `PushHandler`, which resolve the target repository/stack using a *different* payload field, `repository.full_name`, with no cross-check against `repository.owner.login`: [4](#0-3) [5](#0-4) 

Since `repository.owner.login` and `repository.full_name` are both attacker-controlled fields of the same unverified JSON body, an attacker can set them inconsistently: `repository.owner.login = "orgA"` (used only to select the verification secret) and `repository.full_name = "orgB/tracked-repo"` (used to select the actual `Stack` that gets mutated). The HMAC signature is computed over `request.raw_post`, so it does cover the full payload bytes, but it is verified against OrgA's secret — a secret the attacker legitimately possesses because they administer OrgA's GitHub App on the same multi-tenant Shipit instance. The check therefore proves "this came from someone who knows OrgA's secret," not "this came from GitHub for the repository referenced in the payload."

### Impact Explanation
This breaks the deployment-trust binding "organization that authenticated versus the repository that is written." A tenant who legitimately controls one org's webhook secret can inject forged GitHub webhook events (`push`, `status`, `check_suite`, etc.) that are processed as if they came from GitHub for a stack owned by a completely different organization. Concretely with `PushHandler`, this forces `Stack#sync_github` to run against OrgB's stack based on attacker-chosen `after` SHA, and other handlers (`status`, `check_suite`) write commit status/check data cross-organization. Because such writes can feed into continuous-delivery/auto-deploy decisions and commit state used elsewhere in Shipit, this constitutes cross-organization/cross-repository writes into stack state that the attacker has no authorization over — matching the Critical "cross-repository writes" / unauthorized deploy trigger class.

### Likelihood Explanation
Exploitability requires the attacker to be a legitimate, unprivileged operator of at least one GitHub organization configured on the same shared Shipit instance (a realistic scenario for any multi-tenant Shipit deployment using the documented multi-org `secrets.yml` layout). No GitHub App private key, `api_clients_secret`, or Shipit session is required — only knowledge of their own org's `webhook_secret`, which they are entitled to know. The only defense (`repository_owner` lookup failing with `GithubOrganizationUnknown`) only blocks completely unconfigured organizations, not mismatched-but-valid ones.

### Recommendation
After signature verification, re-derive the organization from the same field(s) used to resolve the target `Stack`/`Repository` (i.e., validate that the owner of `repository.full_name` matches the `repository_owner` used to select the webhook secret), or resolve the target stack first and use its known GitHub organization to select the verification secret, rejecting the webhook if there's a mismatch.

### Proof of Concept
1. Deploy Shipit with the documented multi-org config (`secrets.github.orgA.webhook_secret`, `secrets.github.orgB.webhook_secret`), tracking a repository `orgB/target-repo` (owned by OrgB).
2. As an attacker who legitimately administers a separate GitHub App/org `orgA` on the same Shipit instance (and thus knows `orgA`'s `webhook_secret`), craft a payload:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "orgA" },
    "full_name": "orgB/target-repo"
  }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac(orgA_webhook_secret, raw_body)>` and POST to `/webhooks` with header `X-Github-Event: push`.
4. `verify_signature` calls `Shipit.github(organization: "orgA")` and verifies successfully using OrgA's secret.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("orgB/target-repo")` and calls `stack.sync_github(expected_head_sha: ...)`, mutating OrgB's stack state despite the request never being authenticated by OrgB's GitHub App.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
