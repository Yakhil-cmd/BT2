### Title
Cross-tenant membership webhook forgery allows deleting/hijacking any `Shipit.github_teams` `Membership` via `team.id` reuse - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
The `membership` webhook handler looks up the `Team` solely by the payload's numeric `team.id` and never checks that the organization whose secret signed the request actually owns that team. Any org configured as a `GithubHook::Organization` subscriber to `membership` events can therefore forge a `removed` (or `added`) event referencing a `team.id`/`member.login` pair belonging to a completely different organization, deleting (or hijacking) a real `Shipit::Membership` row that gates `Shipit.github_teams` authorization.

### Finding Description
The binding the security model assumes is: `organization that signed the webhook == organization that owns team.id in the payload`. This binding is never enforced.

`WebhooksController#verify_signature` selects the HMAC secret to verify against using `repository_owner`, which for membership events is `params.dig('organization', 'login')` — a value taken directly from the attacker-controlled JSON body: [1](#0-0) [2](#0-1) 

This only proves the request was signed by *some* organization's registered secret (e.g. `shopify_membership` in fixtures, `event: membership`, per-org `secret`) — it says nothing about which `team.id` that organization is entitled to report on: [3](#0-2) 

`MembershipHandler#process` then resolves the team by the global numeric `github_id` alone, with no filter on `organization`: [4](#0-3) 

`find_or_create_team!` only assigns `team.organization = params.organization.login` inside the `find_or_create_by!` block, which only runs on *creation*. If the `Team` with that `github_id` already exists (belonging to the real organization), the found record's `organization` is left untouched and is never compared against the signing organization before `team.add_member(member)` / `team.members.delete(member)` executes: [5](#0-4) 

`Team#add_member` and the `members` association operate directly on the `memberships` table that backs `User#authorized?`: [6](#0-5) [7](#0-6) 

**Exploit flow (given the question's stipulated precondition that attacker controls an org legitimately configured with a `membership` webhook subscription):**
1. Attacker knows their own org's webhook secret (they set it themselves when creating the GitHub App per `docs/setup.md`'s "Webhook secret ... Fill it with some randomly generated string").
2. Attacker POSTs to `/webhooks` with `X-Github-Event: membership`, a valid `X-Hub-Signature` computed with their own org's secret, `organization.login` = their own org (so `verify_signature` passes), but `team.id` = the real `github_id` of `real-org`'s admin team, `action: 'removed'`, and `member.login` = the victim admin's login.
3. `verify_signature` succeeds because it only validates the HMAC against the attacker's own org's secret — it never checks that `team.id` belongs to that org.
4. `find_or_create_team!` finds the pre-existing `Team` row for `real-org` by `github_id` match and returns it unchanged.
5. `team.members.delete(member)` deletes the legitimate `Membership` row, and `User#authorized?` flips to `false` for that admin.
6. A follow-up forged `added` event for the same `team.id` with the attacker's own `member.login` completes a full authorization swap.

No guard (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema, `require_permission!`, model validations) checks `team.organization == repository_owner` before mutating membership.

### Impact Explanation
This is an authorization-state mutation for a party (`real-org`'s team) that did not authenticate the request — the attacker's org signed it, not `real-org`. Repeated at will, it can permanently deny a legitimate operator access to Shipit (`authorized?` becomes false), and combined with a subsequent forged `added` event, gives the attacker a full impersonation swap into `Shipit.github_teams`, matching the "escalation into `Shipit.github_teams` authorization" High-severity category. Blast radius covers any Shipit installation using the documented multi-organization webhook configuration, since any subscribed org can target any other org's team by numeric ID.

### Likelihood Explanation
Requires: (1) Shipit configured with `membership` webhook events enabled for at least one `GithubHook::Organization`, and (2) attacker controls that organization (owns/administers it and its GitHub App webhook secret) — both explicitly part of the documented multi-tenant setup (`docs/setup.md`, "Using Multiple Github Applications"). No Shipit-side secret, session, or API token is needed. `team.id` values are GitHub's numeric team IDs, which are sequential/enumerable or discoverable through other legitimate API access the attacker's own org has (e.g., listing teams via their installed app or public org APIs). Cost is a single crafted HTTP POST per action, fully repeatable.

### Recommendation
In `MembershipHandler`, verify that the signing organization (`repository_owner`/`params.organization.login`) matches the `Team#organization` of the record found by `github_id` before performing `add_member`/`delete`; reject (or no-op with a log) any mismatch. Additionally, scope `Team.find_or_create_by!` lookups by both `github_id` and `organization`, and refuse to reuse a `Team` row whose stored `organization` differs from the authenticated payload's organization.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test ":membership 'removed' from unrelated-but-subscribed org deletes membership belonging to a different org" do
  real_org_team = shipit_teams(:shopify_admins) # github_id: 999, organization: "shopify"
  admin = shipit_users(:walrus)
  Membership.create!(team: real_org_team, user: admin)
  assert admin.authorized?

  # attacker-controlled org "evilcorp" is a legitimately subscribed GithubHook::Organization
  request.headers['X-Github-Event'] = 'membership'
  body = {
    action: 'removed',
    team: { id: real_org_team.github_id, name: real_org_team.name, slug: real_org_team.slug, url: real_org_team.api_url },
    organization: { login: 'evilcorp' }, # attacker's own org, signs with its own secret
    member: { login: admin.login }
  }.to_json

  # signature computed with evilcorp's own known webhook secret
  post :create, body:, as: :json
  assert_response :ok

  assert_not Membership.exists?(team: real_org_team, user: admin)
  assert_not admin.reload.authorized?
end
```
This demonstrates the binding `signing_org == team.organization` does not hold: `evilcorp` successfully signs a request that mutates `shopify`'s team membership, deleting a legitimate admin's authorization.

        def process
          team = find_or_create_team!
          member = User.find_or_create_by_login!(params.member.login)

          case params.action
          when 'added'
            team.add_member(member)
          when 'removed'
            team.members.delete(member)
          else
            raise ArgumentError, "Don't know how to perform action: `#{action.inspect}`"
          end
        end

        private

        def find_or_create_team!
          Team.find_or_create_by!(github_id: params.team.id) do |team|
            team.github_team = params.team
            team.organization = params.organization.login
          end
        end
