### Title
CCMenu API token stack-scope bypass allows reading any stack's state - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
An `ApiClient` token can be created scoped to a single `Stack` (`api_clients.stack_id`), meaning it is meant to only authorize `read:stack`/etc operations on that one stack. `Shipit::Api::CCMenuController` breaks this binding: it authenticates the token but resolves the target stack from `params[:stack_id]` without going through the stack-scoping used everywhere else in the API.

### Finding Description
In `Shipit::Api::BaseController`, stack-scoped tokens are enforced via: [1](#0-0) 
`stacks` restricts the queryable relation to `Stack.where(id: current_api_client.stack_id)` when the client is scoped, and `stack` resolves `params[:stack_id]` through that scoped relation, raising if the id doesn't belong to the allowed set.

`CCMenuController`, however, overrides `stack` to bypass this scoping entirely: [2](#0-1) 
It calls `Stack.from_param!(params[:stack_id])` directly against the whole `Stack` table, not the caller's `stacks` scope. The class only declares `require_permission :read, :stack`, which is checked by `ApiClient#check_permissions!`: [3](#0-2) 
`check_permissions!` only checks that the string `"read:stack"` is present in the `permissions` array — it has no notion of *which* stack. The binding that should hold is: `token.stack_id == requested_stack.id` (when the token is stack-scoped) — this is enforced in `BaseController#stack`/`stacks` but not in `CCMenuController#stack`.

Additionally, `CCMenuController#authenticate_api_client` accepts `params[:token]` (URL query string) directly rather than only via `Authorization` header: [4](#0-3) 

### Impact Explanation
Any holder of a stack-scoped `read:stack` `ApiClient` token (e.g. from the CCMenu URL feature, which mints such tokens for any user who can view a stack: `Shipit::CCMenuUrlController`) can use that token against `Api::CCMenuController#show` with an arbitrary `stack_id` belonging to any other stack in the installation, and get back that unrelated stack's build/deploy status (`lastBuildStatus`, `lastBuildLabel`, lock state) via the rendered `shipit/ccmenu/project` XML. This is an unauthenticated-for-that-resource read of stack state, matching the "High" impact category for "unauthenticated read of stack state."

### Likelihood Explanation
Any user who can view a stack in the UI can mint a CCMenu token scoped to that stack via `CCMenuUrlController#fetch`: [5](#0-4) 
That legitimately-obtained, narrowly-scoped token can then be replayed against `/api/stacks/:stack_id/ccmenu.xml` for any other `stack_id` on the install, since the controller never checks the token's `stack_id` against the requested one.

### Recommendation
Remove the `stack` override in `Shipit::Api::CCMenuController`, or make it use `stacks.from_param!(params[:stack_id])` (i.e., reuse `BaseController#stack`) so stack-scoped tokens are constrained to the stack they were minted for.

### Proof of Concept
1. As a normal user, visit a stack you have read access to and fetch its CCMenu URL (`CCMenuUrlController#fetch`), obtaining a token scoped to `stack_id: A` with `permissions: ['read:stack']`.
2. Send `GET /stacks/B.xml?stack_id=B&token=<token-scoped-to-A>` (or via `Authorization: Basic`) to `Api::CCMenuController#show`, where `B` is any other stack on the installation.
3. Observe the response renders stack `B`'s CI/deploy status, even though the token was only supposed to authorize reads for stack `A`, because `check_permissions!` never validates `token.stack_id == B.id` and `CCMenuController#stack` bypasses the `stacks` scoping that would have enforced it.
