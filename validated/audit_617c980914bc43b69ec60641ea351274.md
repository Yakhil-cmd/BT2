### Title
Webhook signature verified against `repository.owner.login`, but downstream handlers act on the unauthenticated `repository.full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the `GitHubApp` (and thus the HMAC secret) to check against using `repository_owner`, taken from the payload's `repository.owner.login` (or `organization.login`). Once the signature check passes, every registered `Shipit::Webhooks::Handlers::Handler` resolves which `Repository`/`Stack` to mutate using a *different* field of the same JSON body: `repository.full_name` [1](#0-0) . Nothing ties these two fields together, so a validly-signed webhook for one GitHub organization can be crafted to target a repository/stack belonging to a completely different organization.

### Finding Description
`verify_signature` resolves the signing app from the payload itself, not from any pre-registered per-repository mapping: [2](#0-1) [3](#0-2) 

Shipit supports multiple independently-configured GitHub Apps/organizations, each with its own `webhook_secret`, as shown in the test fixture with `OrgOne`/`OrgTwo` entries [4](#0-3) . An attacker who administers their own organization's Shipit GitHub App installation therefore legitimately possesses (or can set) that organization's `webhook_secret`, and can compute a valid `X-Hub-Signature` for any payload body they construct, as long as `repository.owner.login`/`organization.login` in that payload matches their own org.

Once `verify_signature` passes, `WebhooksController#create` dispatches the full parsed payload unmodified to the handlers for the event type [5](#0-4) . Every handler (`PushHandler`, `StatusHandler`, `CheckSuiteHandler`, the `PullRequest` handlers, etc.) locates its target `Repository`/`Stack` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` [1](#0-0) , or an equivalent `params.repository.full_name` lookup in the PR handlers [6](#0-5) . `full_name` is never checked against `repository_owner`/`organization.login`, i.e. never checked against the identity that produced a valid signature.

This breaks the required binding: `organization that authenticated (repository.owner.login/organization.login, checked against a specific GitHubApp's webhook_secret) == organization that owns the repository actually written (repository.full_name, used to look up the Repository/Stack)`. An attacker in control of Organization A's webhook secret can sign a `push`/`status`/`check_suite` payload whose `repository.full_name` points at `OrganizationB/some-repo`, and every guarded action downstream of `verify_signature` will execute against Organization B's stack.

### Impact Explanation
The most severe reachable handler is `StatusHandler` (registered for the `status` event, same as `PushHandler`) [7](#0-6) , which uses the same `stacks`/`repository_name` resolution from the base `Handler` class [1](#0-0)  to create `Status` records on commits, as exercised by the ":state create a Status for the specific commit" test which merges an arbitrary `state`/`description` into a target commit [8](#0-7) . Because deploy gating (`require_ci`, `deployable?`) is driven by these `Status` records, an attacker who only controls their own org's GitHub App installation can inject a forged `success` status on an arbitrary commit belonging to a victim organization's stack, which can subsequently be used to pass CI gating for an unauthorized deploy of that commit — matching the Critical "unauthorized deploy" impact bucket. At minimum, `PushHandler` lets the attacker force `sync_github` on a victim stack it does not own [9](#0-8) .

### Likelihood Explanation
This requires the attacker to control (or self-configure) a legitimate GitHub App/organization entry already registered in Shipit's `secrets.yml` (e.g., by being an admin of one tenant organization in a multi-org Shipit deployment), which the engine explicitly supports (see the dual-org secrets fixture). No GitHub App private key, `ApiClients` token, or Shipit session is needed — only the ability to craft an arbitrary JSON body and compute an HMAC with a secret the attacker legitimately owns for their own org, then set `repository.full_name` to any other registered repository's `owner/name`.

### Recommendation
In `WebhooksController` and/or `Shipit::Webhooks::Handlers::Handler`, verify that the `repository.owner.login` (or `organization.login`) used to select the signing `GitHubApp` in `verify_signature` matches the owner encoded in `repository.full_name` used by handlers to resolve the target `Repository`. Reject the request (422) on mismatch instead of allowing handlers to independently re-derive the target repository from an unverified field.

### Proof of Concept
1. Configure Shipit with two organizations, `AttackerOrg` and `VictimOrg`, each with distinct `webhook_secret`s (as supported by `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker, who legitimately controls `AttackerOrg`'s GitHub App webhook secret, builds a `status` (or `push`) payload:
   - `repository.owner.login = "AttackerOrg"` and `organization.login = "AttackerOrg"` (used only for signature routing).
   - `repository.full_name = "VictimOrg/victim-repo"`, `sha = <victim commit sha>`, `state = "success"`.
3. Attacker signs the raw payload with `AttackerOrg`'s known `webhook_secret` and sends it to `/webhooks` with `X-Hub-Signature` set accordingly and `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: "AttackerOrg")` and successfully verifies the signature [2](#0-1) .
5. `StatusHandler` (via the shared `Handler#stacks`/`repository_name` logic) resolves the target repository from `repository.full_name = "VictimOrg/victim-repo"` [1](#0-0)  and creates a forged successful `Status` on the victim's commit, despite the signature having been produced with `AttackerOrg`'s secret rather than `VictimOrg`'s.
