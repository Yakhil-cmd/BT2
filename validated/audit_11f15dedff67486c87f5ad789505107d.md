### Title
Cross-organization commit-status forgery in `StatusHandler` allows unauthorized deploys/merges across tenants - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
Shipit officially supports a multi-tenant deployment mode where one Shipit instance serves multiple GitHub organizations, each with its own GitHub App and its own `webhook_secret` [1](#0-0) . `WebhooksController#verify_signature` selects which organization's secret to use for HMAC verification purely from the attacker-controlled payload (`repository.owner.login` / `organization.login`), and once a payload is validated against *that* organization's secret, the event is dispatched to a handler that never re-checks that the affected resource actually belongs to the authenticated organization. `StatusHandler#process` looks up commits **globally by SHA only**, with no scoping to the repository/organization whose secret produced a valid signature.

### Finding Description
`WebhooksController#verify_signature` picks the GitHub App/secret to verify against based on a field taken from the untrusted payload itself: [2](#0-1) [3](#0-2) 

The signature is a valid HMAC-SHA1 of the raw body computed with the secret belonging to `repository_owner` (org whose secret matches) [4](#0-3) . This only proves the request was signed by *some* org's key that Shipit has configured — not that the payload's other fields (in particular the target `sha`) belong to a repository owned by that org.

After signature verification passes, the handler is invoked with the raw JSON body: [5](#0-4) 

`StatusHandler#process` (and the base `Handler`) determine the target purely from the `sha` in the request body, with no cross-check against the `repository`/`owner` fields at all: [6](#0-5) 

Contrast this with the generic `Handler#stacks`, which does try to scope by `repository.full_name` for handlers that use it [7](#0-6) , but `StatusHandler` bypasses that entirely and queries `Commit.where(sha: params.sha)` across the whole database, i.e., across every stack/organization tracked by the Shipit instance.

Applying a status to a commit feeds directly into deployment/merge automation:
- `Status#schedule_continuous_delivery` → `Commit#schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` when the stack has `continuous_deployment` enabled [8](#0-7) [9](#0-8) .
- `Commit#add_status` calls `stack.schedule_merges` whenever the new state is `pending` or `success` [10](#0-9) , which enqueues `ProcessMergeRequestsJob` [11](#0-10) .
- `ProcessMergeRequestsJob` merges any pending merge request whose head commit now shows all required checks passing, via `MergeRequest#merge!`, which calls the GitHub API using the App's own installation token to actually merge the pull request [12](#0-11) [13](#0-12) .

**Binding broken:** the organization whose credential (webhook secret) authenticated the request `≠` the repository/stack whose commit status, continuous-delivery pipeline, or merge queue is actually written to. Before the attack: a status update signed by Org A's secret can only legitimately describe Org A's commits. After: `StatusHandler` accepts any `sha` value regardless of which org's secret validated the envelope, so Org A's legitimately-owned webhook secret can forge a "success" status on a commit SHA belonging to Org B's stack (git commit SHAs are public information, trivially obtainable from GitHub), triggering an unauthorized auto-deploy or an unauthorized auto-merge (a GitHub API write) on Org B's repository — a cross-tenant deployment-trust violation using only credentials the attacker legitimately possesses for their own tenant.

### Impact Explanation
This crosses the "unauthorized deploy... or merge" / "cross-repository writes" bar explicitly listed as in-scope Critical/High impact. A tenant that legitimately controls one GitHub organization's App/webhook secret (as documented in the multi-github-app setup) can, without any additional privilege, forge commit-status events that:
1. Trigger `ContinuousDeliveryJob` for another tenant's stack, causing an unauthorized deploy, or
2. Satisfy `all_status_checks_passed?` for another tenant's pending merge request, causing Shipit's GitHub App credentials to merge a pull request in a repository the attacker's org has no access to (cross-repository/cross-org write via the app's GitHub credentials).

### Likelihood Explanation
Requires the Shipit operator to run the documented multi-GitHub-App configuration (multiple orgs sharing one Shipit instance) and requires the attacker to know/guess a target SHA that is tracked by another tenant's stack — SHAs are public on GitHub, so this is easily discoverable for any public or attacker-observable repository, and moderately discoverable even for private repos the attacker doesn't have access to (e.g., via leaked CI logs, PR notification emails, etc.). No compromise of the victim org's own secret is required; only the attacker's own legitimately-held webhook secret is needed.

### Recommendation
In `WebhooksController#verify_signature` / `StatusHandler#process`, after establishing which organization's secret validated the signature, restrict all subsequent lookups (`Commit.where(sha: ...)`, `stacks`, etc.) to repositories owned by that verified `repository_owner`, and reject/ignore any payload whose `repository.owner.login` does not match the resource actually being mutated. More generally, every webhook handler should scope its side effects to `Repository.from_github_repo_name(payload.dig('repository','full_name'))` under the same organization that authenticated the request, not merely by SHA or other org-agnostic identifiers.

### Proof of Concept
1. Operator runs Shipit with two configured GitHub Apps: `OrgA` (attacker-controlled) and `OrgB` (victim), as documented in `docs/setup.md`'s "Using Multiple Github Applications" section.
2. Attacker, as an admin of `OrgA`, knows `OrgA`'s `webhook_secret` (they configured it themselves when installing their own GitHub App).
3. Attacker discovers/guesses a commit SHA tracked by a Shipit stack belonging to `OrgB` (e.g. head of a pending merge request or the tip of a continuously-deployed branch), e.g. by observing public commits or PR pages.
4. Attacker POSTs to `/webhooks` with header `X-Github-Event: status` and a JSON body:
   ```json
   { "sha": "<OrgB-commit-sha>", "state": "success", "context": "ci/required",
     "repository": { "owner": { "login": "OrgA" } } }
   ```
   signed with `sha1=` HMAC using `OrgA`'s `webhook_secret` over the raw body.
5. `verify_signature` resolves `Shipit.github(organization: "OrgA")` (from the payload's `repository.owner.login`) and successfully verifies the signature against `OrgA`'s secret.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds `OrgB`'s commit (no ownership check), and creates a `success` status on it.
7. This triggers `stack.schedule_merges` / `ContinuousDeliveryJob` for `OrgB`'s stack, causing Shipit to merge a pending PR or deploy `OrgB`'s repository using the app's `OrgB` GitHub credentials — an unauthorized cross-organization write, initiated entirely with `OrgA`'s own legitimately-held webhook secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }

      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end

    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?
      end

      return false unless stack.allows_merges?

      merge_requests.select(&:pending?).each do |merge_request|
        merge_request.refresh!
        next unless merge_request.all_status_checks_passed?

        begin
          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
      end
    end
