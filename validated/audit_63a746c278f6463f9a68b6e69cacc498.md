### Title
API clients can impersonate any Shipit `User` via the unauthenticated `X-Shipit-User` header - ([File: app/controllers/shipit/api/base_controller.rb])

### Summary
### Finding Description
`Shipit::Api::BaseController` authenticates the *caller* through an `ApiClient` token (`authenticate_api_client`), but the `current_user` that is actually attributed to state-changing actions (deploys, rollbacks, locks, task triggers/aborts) is derived from a separate, completely unauthenticated request header: [1](#0-0) 

```ruby
def current_user
  @current_user ||= identify_user || AnonymousUser.new
end

def identify_user
  user_login = request.headers['X-Shipit-User'].presence
  User.where('lower(login) = ?', user_login.downcase).first if user_login
end
```

The signature/authentication boundary that is actually verified is the `ApiClient` bearer token, checked in `authenticate_api_client`: [2](#0-1) 

That verified credential covers only the `ApiClient` identity (and its `permissions`/`stack_id` scope, enforced via `require_permission!`/`check_permissions!`). It does **not** cover the `X-Shipit-User` header value at all — the header is trusted at face value and used to look up an arbitrary `User` by login, with no cross-check that the authenticated `ApiClient`'s `creator` matches that login, or that the token was ever meant to act on behalf of that user.

This is precisely the class of bug described in the external report: a value ("the fallback"/"the field") that is *acted on* by privileged application logic is never covered by the thing that was actually verified (the "signature"/token). Here, the binding that should hold is:

`ApiClient token authenticates == User attributed as actor of the deploy/rollback/lock/task`

but the code lets an attacker who possesses *any* valid `ApiClient` token set `current_user` to an arbitrary `User` record by simply setting `X-Shipit-User` to that user's `login`.

This `current_user` value is then passed directly into privileged operations across multiple API controllers:
- `stack.trigger_deploy(commit, current_user, ...)` [3](#0-2) 
- `deploy.trigger_rollback(current_user, ...)` / `active_task.abort!(aborted_by: current_user, ...)` [4](#0-3) 
- `stack.lock(params.reason, current_user)` [5](#0-4) 
- `stack.trigger_task(params[:task_name], current_user, ...)` / `task.abort!(aborted_by: current_user)` [6](#0-5) 

### Impact Explanation
Because any holder of a valid `ApiClient` token (scoped to `deploy:stack`, `lock:stack`, etc.) can freely spoof `current_user` to be a different, more privileged `User` (e.g. an admin or a well-known reviewer/approver), they can:
- Attribute deploys/rollbacks they trigger to an arbitrary other user, defeating audit trails (`SHIPIT_USER`/committer attribution used later in `lib/shipit/task_commands.rb`'s `env` builder).
- Cause a lock to be recorded as created "by" an arbitrary user, or an abort/task action to be attributed to someone who never took it.

This does not, by itself, escalate the caller's own `ApiClient` permission scope (permission checks still run against the authenticated `ApiClient`, not the spoofed user), so it is not a full authorization bypass into `Shipit.github_teams`, but it is an identity-attribution/audit-trail integrity break that any token holder (even one restricted to a single stack via `here_come_the_walrus`-style scoped `ApiClient`s) can exploit to forge the acting user on deploy, rollback, lock, and task records.

### Likelihood Explanation
Any actor with a valid, even narrowly-scoped, `ApiClient` token can trivially exploit this by adding one HTTP header (`X-Shipit-User: <victim-login>`) — no additional secret or session is required beyond the token they already legitimately possess for other operations.

### Recommendation
Do not derive `current_user` from a bare, unauthenticated header. Either bind the acting user to the authenticated `ApiClient.creator`, or require that identity assertions carried in `X-Shipit-User` be cryptographically bound to the presented token (e.g. only trusted for clients marked as allowed to act on behalf of users, or validated against the token's own creator/permissions), and audit/restrict which callers can set that header.

### Proof of Concept
1. Obtain (or possess) any valid `ApiClient` authentication token scoped with `deploy:stack` permission for a stack (e.g. `here_come_the_walrus` fixture-style client).
2. Send `POST /api/stacks/:id/deploys` with header `X-Shipit-User: admin-login` and the token in the `Authorization: Basic` header.
3. `authenticate_api_client` verifies only the token; `current_user` resolves to the `User` whose `login == 'admin-login'` purely from the header value.
4. `stack.trigger_deploy(commit, current_user, ...)` records the deploy as triggered by `admin-login`, even though the actual token holder is a different, unrelated actor.

      def create
        commit = stack.commits.by_sha(params.sha) || param_error!(:sha, 'Unknown revision')
        param_error!(:force, "Can't rollback a locked stack") if !params.force && stack.locked?
        deploy = stack.deploys.find_by(until_commit: commit) || param_error!(:sha, 'Cant find associated deploy')
        rollback_env = stack.filter_rollback_envs(params.env)

        response = nil
        if !params.force && stack.active_task?
          param_error!(:force, "Can't rollback, deploy in progress")
        elsif stack.active_task?
          active_task = stack.active_task
          active_task.abort!(aborted_by: current_user, rollback_once_aborted_to: deploy, rollback_once_aborted: true)
          response = active_task
        else
          response = deploy.trigger_rollback(current_user, env: rollback_env, force: params.force, lock: params.lock)
        end

        render_resource(response, status: :accepted)
      end
