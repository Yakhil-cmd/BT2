### Title
`StatusHandler#process` mutates `Commit` status without verifying the commit belongs to a stack for the webhook's own repository - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` looks up commits solely by `sha` across the entire `commits` table, and never checks that the matched `Commit#stack` belongs to `self.stacks` (i.e. `Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks`), unlike `PushHandler#process` which correctly scopes to `stacks.not_archived.where(branch:)`. Because git commit SHA1s are content-addressed and identical across forks/mirrors of the same history, an attacker who owns any repository wired into Shipit can send a `status` webhook naming a SHA that also exists in a victim stack, and Shipit will write that CI status onto the victim's `Commit`.

### Finding Description
The required binding is: for every `Commit` mutated in `#process`, `commit.stack` must be a member of `self.stacks` where `self.stacks = Repository.from_github_repo_name(payload.dig('repository','full_name'))&.stacks` [1](#0-0) .

`StatusHandler#process` never references `stacks` or `repository_name`; it does:
```
Commit.where(sha: params.sha).each do |commit|
  commit.create_status_from_github!(params)
end
``` [2](#0-1) 

This is inconsistent with `PushHandler#process`, which correctly restricts its side effects to `stacks.not_archived.where(branch:)` derived from the payload's own repository [3](#0-2) . `Commit#sha` has no uniqueness scoping by `stack_id` enforced in the lookup path used here — `Commit.where(sha: ...)` is a bare, unscoped query [4](#0-3) , and `create_status_from_github!` writes a new `Status` and recomputes `status`, `deployable?`, and triggers `stack.schedule_merges` / `ContinuousDeliveryJob` [5](#0-4) [6](#0-5) .

Exploit path: the attacker owns/controls a repository (e.g. a fork of the victim's repo, sharing identical commit objects/SHAs due to git's content addressing) and that repository is wired to send webhooks to the Shipit host (the threat model explicitly grants "emit webhooks from a repository they own"). `WebhooksController#verify_signature` validates the signature using `Shipit.github(organization: repository_owner)` keyed off the *organization* named in the attacker's own payload, not the specific target repository/stack being mutated [7](#0-6) ; it authenticates that the payload came from a real GitHub webhook for that org/repo, but does nothing to ensure the `sha` referenced belongs to a commit within that same repository's stacks. The attacker sends a `status` event with `sha` equal to a shared commit and an arbitrary `state` (e.g. `success`), and `StatusHandler` writes it onto the victim `Commit` regardless of which repository it actually belongs to.

Existing guards (`verify_signature`, `drop_unhandled_event`, `ExplicitParameters` schema) only validate payload authenticity and shape — none of them check that the mutated `Commit`'s stack matches the webhook's own repository, so they do not close this gap.

### Impact Explanation
A successful exploit lets an attacker mark an arbitrary commit in a victim stack as CI `success` (or any other status/context) purely by knowing/guessing a shared SHA — which is trivial if the attacker forks the victim repository, since forked commits are byte-identical and share the exact SHA1. This can flip `Commit#deployable?` to true and trigger `schedule_continuous_delivery`/`stack.schedule_merges`, i.e. an unauthorized deploy or merge decision made on falsified CI state for a repository the attacker never authenticated against. This matches the "Critical" category: "a payload for one repository mutating another's stack, commit ... or an unauthorized deploy." The attack is repeatable against any stack/commit whose SHA the attacker can predict (any shared/forked history), with no per-repository containment.

### Likelihood Explanation
Preconditions: the attacker needs a repository that (a) is wired to send webhooks to the Shipit host with a signature that passes `verify_webhook_signature` for its declared organization, and (b) shares commit history/SHAs with the victim's stack — trivially achieved by forking the victim's public repository. Per the stated threat model, "emit webhooks from a repository they own" is an assumed attacker capability, so no additional privilege escalation is required. The attack is a single unauthenticated-from-Shipit's-perspective POST to `/webhooks` with a `status` event body, fully repeatable and scriptable against any victim stack whose repository history is forkable/public.

### Recommendation
Scope `StatusHandler#process` to only mutate commits belonging to `self.stacks`, mirroring `PushHandler`:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently: `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb` conceptually, outside `test/**` per scope note this is illustrative only):
1. Create `stack_a` (repo `owner/repoA`) and `stack_b` (repo `owner/repoB`), both containing a `Commit` with the identical `sha = "deadbeef" * 5`.
2. Build a payload with `repository.full_name = "owner/repoA"` and `sha` matching the shared commit, `state: "success"`.
3. Call `StatusHandler.call(payload)`.
4. Assert: `stack_b`'s `Commit` (which is NOT a member of `Repository.from_github_repo_name("owner/repoA").stacks`) now has a `Status` with `state == "success"` — proving mutation occurred outside `self.stacks`.
5. Additionally stub/mock `Handler#stacks` and `Handler#repository_name` on the `StatusHandler` instance and assert they are never invoked during `#process`, confirming the binding check is absent from the code path.
