### Title
Webhook Signature Is Verified Against an Organization Chosen From `repository.owner.login`, But the Affected Stack Is Selected From a Different, Uncorrelated `repository.full_name` Field - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb])

### Summary
The report's underlying bug class is "trusting an input that was never actually covered by the validity check." In `WebhooksController`, the field used to pick *which organization's secret* validates the HMAC signature (`repository.owner.login` / `organization.login`) is completely decoupled from the field used to pick *which repository/stack* the resulting webhook handler will act on (`repository.full_name`). Both fields live in the same untrusted, attacker-suppliable JSON body, and neither is cross-checked against the other after the signature check passes.

### Finding Description
`WebhooksController#verify_signature` selects the GitHub App configuration used to validate the HMAC based on the organization named in the payload itself, before the payload has been authenticated: [1](#0-0) [2](#0-1) 

`Shipit.github(organization: repository_owner)` looks up a per-organization `GitHubApp` instance (raising `Shipit::GithubOrganizationUnknown` for unrecognized orgs), confirming that a single Shipit instance can be configured to trust multiple distinct organizations, each with its own `webhook_secret`: [3](#0-2) 

Once `verify_webhook_signature` succeeds for *that* organization's secret, the raw body is parsed and dispatched to handlers: [4](#0-3) 

Every handler, however, resolves the target `Stack`/`Repository` from a *different* JSON field — `repository.full_name` — with no comparison back to the org that was actually authenticated: [5](#0-4) 

For example `PushHandler` (and by the same base-class mechanism, the status/pull_request/membership handlers) act purely on `repository_name` derived this way: [6](#0-5) 

The binding that should hold is: `organization whose secret validated the signature == organization that owns the repository the handlers act on`. Nothing enforces this. An attacker who legitimately administers **one** organization/repository onboarded to a shared Shipit instance (and therefore can set/know that org's `webhook_secret` on the GitHub side, since GitHub webhook secrets are configured by the repository/org admin who registers the webhook) can sign an HTTP request with their own org's secret while setting `repository.owner.login`/`organization.login` to their own org (so `verify_signature` passes) and `repository.full_name` to a **different, victim** organization's repository (so the handler acts on the victim's stack).

### Impact Explanation
This breaks a repository-write trust boundary explicitly called out as in-scope: "an organization that authenticated versus the repository that is written." Concretely, on a Shipit instance shared by multiple organizations:
- The `status` handler can be used to forge a CI status for an arbitrary commit on a victim's repository, which is exactly the signal `ci.require`/`ci.blocking` checks in `shipit.yml` rely on to gate deploys — enabling a bypass that leads to deploying a commit that never actually passed CI (an unauthorized deploy).
- The `push` handler can force `GithubSyncJob` to run against a victim stack.
- `membership`-style handlers can create/attach users or teams for a target Shipit-managed organization without belonging to it.

This satisfies the "unauthorized deploy" / "cross-repository writes" Critical/High impact bar because a party with no relationship to the victim's repository can cause Shipit to accept and act on falsified GitHub state for that repository.

### Likelihood Explanation
Exploitability requires the attacker to control at least one organization/repository already configured in the same multi-tenant Shipit deployment (so they know a valid `webhook_secret`) — this is a standard, supported configuration (`Shipit.github(organization:)` + `GithubOrganizationUnknown` demonstrate first-class multi-org support), not a hypothetical edge case. No GitHub App private key, `ApiClient` token, or Shipit session is needed — only the ability to send an HTTP POST with a correctly-signed body for the attacker's own org.

### Recommendation
After computing `repository_owner` and verifying the signature, re-derive the repository/organization actually used by handlers (`repository.full_name`) and reject the request unless its owner segment matches the organization whose secret validated the signature. Equivalently, have `Handler#repository_name` receive the already-authenticated organization from the controller and refuse to process payloads whose `repository.full_name` owner disagrees with it.

### Proof of Concept
1. Shipit is configured with two organizations, `attacker-org` and `victim-org`, each with distinct `webhook_secret`s (multi-org config as supported by `Shipit.github(organization:)`).
2. Attacker administers a repository under `attacker-org` and thus knows/controls `attacker-org`'s `webhook_secret`.
3. Attacker crafts a `status` (or `push`) webhook JSON body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/required-check"
}
```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known secret over this exact raw body.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')` and successfully verifies the signature. [1](#0-0) 
6. The status handler (subclass of `Handler`) resolves the target repository via `payload.dig('repository', 'full_name')` = `victim-org/victim-repo`, and records the forged `success` status against a commit in `victim-repo`, which `victim-org`'s `shipit.yml` `ci.require` may later treat as a legitimate green check when gating a deploy. [5](#0-4)

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
