### Title
Unbounded HTTP response reading in arbiter/ArbStore fetch paths allows DoS via attacker-controlled arbiter contract - (File: arbiters.js, arbiter_contract.js)

### Summary
`ocore`'s arbiter-contract feature lets a peer (an unprivileged paired-device counterparty in a private payment/contract flow) propose a contract that names an `arbiter_address`. When the receiving wallet later needs the arbiter's info or interacts with the ArbStore (fetching info, appeal fee, or filing an appeal), it asks the hub for the `arbstore_url` tied to that `arbiter_address` and then performs a raw `http(s).get`/`http.request` to that URL, buffering the entire response body in memory with no size cap, no response timeout, and no redirect/handling limits.

### Finding Description
The vulnerable pattern mirrors the Discourse Onebox issue: fetching attacker-influenced remote content without bounding the amount of data read or the time spent reading it. In `arbiters.js`, `requestInfoFromArbStore` does: [1](#0-0) 
This is reached from `getInfo`/`getArbstoreInfo`, both of which resolve the fetch URL via `device.requestFromHub("hub/get_arbstore_url", arbiter_address, ...)` — i.e., the URL is looked up using an `arbiter_address` supplied in the contract data, not a value the querying wallet fully controls: [2](#0-1) [3](#0-2) 

The same unbounded pattern exists in `arbiter_contract.js`'s `httpRequest`, used by `getArbstoreAddresses`, `appeal`, and `getAppealFee`: [4](#0-3) [5](#0-4) [6](#0-5) 

The `arbiter_address` field of a contract originates from the peer proposing the contract via a device message (`arbiter_contract_offer`) and is persisted via `store()`: [7](#0-6) 
A malicious counterparty can register an address they control as an "arbiter" on a hub they operate (or induce use of a hub entry pointing to their own server), so that `hub/get_arbstore_url` for that address resolves to a URL under attacker control. When the victim wallet subsequently calls into `getInfo`/`getArbstoreInfo`/`appeal`/`getAppealFee`, it performs an unbounded `GET`/`POST` against that attacker-controlled endpoint. The attacker's server can hold the connection open indefinitely (slow drip) or stream unbounded data, since none of `requestInfoFromArbStore`, `httpRequest`, or the shared `fetchUrl` helper in `uri.js` impose a timeout, a maximum response size, or an abort mechanism: [8](#0-7) 

### Impact Explanation
A successful exploitation causes unbounded memory growth (buffering an ever-growing `data` string) and/or an indefinitely hanging request/socket in the victim wallet process, degrading or crashing the wallet application — a denial of service triggered purely by a peer proposing/interacting in an arbiter contract, i.e., by an unprivileged paired-device counterparty. This matches the "network unable to confirm new units" / resource-exhaustion class of impact described in the Discourse advisory, translated to the wallet/device-message surface of ocore.

### Likelihood Explanation
The attacker only needs to be a pairing counterparty who proposes (or is party to) an arbiter contract, an action requiring no special privilege beyond normal peer pairing. Because the arbiter's `arbstore_url` is resolved dynamically via the hub for an address chosen by the contract proposer, controlling that resolution (by owning/registering the arbiter address on a hub) is straightforward for an attacker running their own hub/arbstore infrastructure. No user validation of the URL's safety (size caps, timeouts) is performed before the fetch, so the likelihood of successful DoS is high once an interaction occurs (e.g., victim views arbiter info or initiates/files an appeal).

### Recommendation
- Add request timeouts (`req.setTimeout`) and destroy the socket/response stream on timeout in `requestInfoFromArbStore` (`arbiters.js`), `httpRequest` (`arbiter_contract.js`), and `fetchUrl` (`uri.js`).
- Enforce a maximum response body size; abort/destroy the response stream once exceeded, mirroring the fix approach used upstream for Discourse's Onebox (bounding both time and size of fetched content).
- Validate/sanitize the `arbstore_url` returned by the hub (e.g., restrict scheme, enforce reasonable timeouts at the HTTP client/agent level) before performing any request tied to peer-supplied `arbiter_address` values.

### Proof of Concept
1. Attacker pairs with victim's wallet and sends an `arbiter_contract_offer` device message naming an `arbiter_address` that the attacker controls and has registered on a hub they operate, with `hub/get_arbstore_url` resolving to `https://attacker.example/slow`.
2. `attacker.example/slow` responds with HTTP 200 and then either streams data indefinitely at a slow rate or never ends the response.
3. Victim wallet calls `arbiters.getInfo(arbiter_address, cb)` (e.g., to display arbiter details for the offered contract) or later `arbiter_contract.getAppealFee`/`appeal`, invoking `requestInfoFromArbStore`/`httpRequest`, which buffers the response in the `data` variable with no timeout or size limit.
4. The victim's process socket remains open indefinitely and/or memory grows unbounded, degrading or crashing the wallet — denial of service achieved without any spend, signature, or elevated privilege by the attacker.

function httpRequest(host, path, data, cb) {
	var reqParams = Object.assign(url.parse(host),
		{
			path: path,
			method: "POST",
			headers: {
				"Content-Type": "application/json",
				"Content-Length": (new TextEncoder().encode(data)).length
			}
		}
	);
	var req = http.request(
		reqParams,
		function(resp){
			var data = "";
			resp.on("data", function(chunk){
				data += chunk;
			});
			resp.on("end", function(){
				try {
					data = JSON.parse(data);
					if (data.error) {
						return cb(data.error);
					}
					cb(null, data);
				} catch (e) {
					cb(e);
				}
			});
		}).on("error", cb);
	req.write(data);
	req.end();
}

function fetchUrl(url, cb) {
	var https = require('https');
	var bDone = false;
	function returnError(err) {
		console.log(err);
		if (bDone)
			return;
		bDone = true;
		cb(err);
	}
	try {
		https.get(url, function (resp) {
			if (resp.statusCode !== 200)
				return returnError("non-200 response while trying to fetch " + url);
			var data = '';

			// A chunk of data has been recieved.
			resp.on('data', function(chunk) {
				data += chunk;
			});

			// aborted before the whole response has been received
			resp.on('aborted', function () {
				returnError("connection aborted while trying to fetch " + url);
			});

			// The whole response has been received
			resp.on('end', function () {
				if (bDone)
					return;
				bDone = true;
				cb(null, data);
			});
		}).on("error", function(err) {
			returnError("non-200 response while trying to fetch " + url + ": " + err.message);
		});
	}
	catch(err) {
		returnError(err.message);
	}
}
