### Title
Cross-organization commit-status spoofing via unscoped SHA lookup in `StatusHandler` breaks the "authenticated organization = written repository" binding - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`Shipit::WebhooksController` selects the GitHub App/organization used to verify the webhook signature purely from attacker-supplied JSON fields (`repository.owner.login` / `organization.login`), and once verified it dispatches the raw JSON body to the matching event handler. For the `status` event, `Shipit::Webhooks::Handlers::StatusHandler` never re-checks that the commit being updated actually belongs to the repository/organization whose secret validated the request — it looks the commit up **only by SHA, globally, across all stacks**.

### Finding Description
The signature check is: [1](#0-0) 
and the organization used to pick the verifying `GitHubApp`/secret comes straight from the payload: [2](#0-1) 

This design implicitly assumes: *"the organization whose secret signed the payload" == "the organization/repository the payload's data is written to."* That equality is enforced for handlers such as `PushHandler`/base `Handler`, which resolve the target stack via `payload.dig('repository', 'full_name')`: [3](#0-2) 

But `StatusHandler` breaks this binding — it updates commit status by SHA only, with no repository/organization filter at all: [4](#0-3) 

`Commit.where(sha: params.sha)` matches **any** `Commit` record in the entire Shipit instance that has that SHA, regardless of which `Stack`/`Repository`/organization it belongs to. Since commit SHAs are content-addressed, the same SHA can legitimately exist in multiple tracked repositories (forks, mirrors, vendored/cherry-picked commits, shared library history, monorepo splits) — a very common occurrence, especially in orgs running many related Shipit stacks.

**Equality broken (before vs. after the attacker's webhook):**
- Before: `organization_that_authenticated(payload) == organization_repository.owner.login` (both derived from the same payload the attacker fully controls, and this is the only thing GitHub's signature guarantees).
- After: Shipit's actual side effect — the commit status write — is performed against `Commit.where(sha:)` with **no relation at all** to `organization_that_authenticated`. Any organization/app installation that can legitimately send a signed `status` webhook (e.g., any repo with the Shipit GitHub App installed, or any CI integration with `statuses:write` on any tracked repo) can, by choosing/colliding a SHA that also exists in a *different* stack/organization, write a fabricated commit status (`success`/`failure`/`pending`, custom `context`, `target_url`, `description`) onto a commit it does not own.

### Impact Explanation
Commit statuses gate deploy decisions and are surfaced in the UI/CI checks (`Commit#create_status_from_github!`, consumed by `CommitChecks`/`EphemeralCommitChecks` and the release/deploy flow). A forged "success" status injected onto another stack's commit can be used to make an unrelated, attacker-uncontrolled commit appear CI-green, which can unlock or accelerate deploy/merge decisions on a stack the attacker has no legitimate access to — an unauthorized-deploy-adjacent integrity break of the exact kind the "organization authenticated vs. repository written" binding is meant to prevent. This satisfies the High-impact bar (escalation across the app's trust boundary into another stack's state) even though it requires signature verification to pass for *some* organization (not necessarily the target one).

### Likelihood Explanation
Requires only the ability to trigger a legitimately signed `status` webhook for *any* repository tracked by the Shipit instance (e.g., any repo where the GitHub App/CI is installed) — no Shipit account, `ApiClient` token, or privileged Shipit role is needed. The practical constraint is finding/causing a SHA collision across stacks, which is realistic in organizations with forked, mirrored, or vendored repositories, or where multiple stacks track overlapping git histories. This is materially weaker than requiring compromise of a specific org's `webhook_secret`.

### Recommendation
`StatusHandler#process` should scope the `Commit` lookup to the repository identified in the payload (`payload.dig('repository', 'full_name')`, consistent with `Handler#repository_name`/`#stacks`) instead of matching by SHA alone across the whole instance, e.g. `stacks.flat_map(&:commits).where(sha: params.sha)` or joining through `Repository.from_github_repo_name(repository_name)`.

### Proof of Concept
1. Shipit tracks `OrgA/repo-a` (Stack A) and `OrgB/repo-b` (Stack B), both with the Shipit GitHub App installed.
2. Commit `abc123...` exists in both repositories' history (e.g., vendored/cherry-picked shared code, or a forked-then-diverged repo).
3. An actor with only `statuses:write` on `OrgA/repo-a` (no Shipit credentials, no access to `OrgB`) creates a commit status for SHA `abc123...` with `state: success` on `OrgA/repo-a`.
4. GitHub sends a `status` webhook signed with `OrgA`'s webhook secret; `WebhooksController#verify_signature` correctly verifies it against `OrgA`.
5. `StatusHandler#process` runs `Commit.where(sha: 'abc123...')`, which also matches the `Commit` row belonging to Stack B (`OrgB/repo-b`), and calls `create_status_from_github!` on it — writing a fabricated "success" status onto `OrgB`'s commit despite the webhook never being authenticated for `OrgB`.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
