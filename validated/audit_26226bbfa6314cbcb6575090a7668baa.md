## Finding

The commented-out authorization check in `handleMessageFromHub` allows any **indirect correspondent** — a device added automatically as a cosigner without explicit user pairing — to invoke every message subject that a fully-trusted, directly-paired device can invoke, including private-payment forwarding, multisig signing requests, and shared-address/contract operations.

### Title
Incorrect Authorization: disabled indirect-correspondent restriction lets untrusted cosigner devices invoke privileged wallet/hub message subjects - ([File: wallet.js])

### Summary
`handleMessageFromHub` in `wallet.js` receives `bIndirectCorrespondent` from `device.js` and was designed to restrict indirect correspondents to only `["cancel_new_wallet", "my_xpubkey", "new_wallet_address"]`. That enforcement is commented out [1](#0-0) , so the `switch(subject)` dispatcher processes any subject from an indirect correspondent exactly as it would from a fully-paired one [2](#0-1) .

### Finding Description
Indirect correspondents are added automatically, without the user ever confirming a pairing code, whenever a shared/multisig address proposal names other cosigners: `addIndirectCorrespondents` inserts them into `correspondent_devices` with `is_indirect=1` [3](#0-2) . When such a device later sends a hub message, `device.js` looks up `is_indirect` and passes it straight through as `bIndirectCorrespondent` without limiting which subjects are allowed [4](#0-3)  — the actual restriction was supposed to live in `wallet.js`.

Because the guard is disabled, an indirect correspondent (whose identity was never verified out-of-band by the user, only inferred from data supplied during a wallet-setup proposal that could itself be attacker-controlled) can now trigger any handler in the switch, e.g.:
- `sign` — request signature over an arbitrary attacker-supplied unit, including private payment payload validation and a `signing_request` UI prompt [5](#0-4) .
- `private_payments` — submit and force processing/forwarding of private payment chains through `handlePrivatePaymentChains`, causing the wallet to validate and forward private financial data to other members of shared/output addresses [6](#0-5) .
- `new_shared_address` / `reject_new_shared_address` / `approve_new_shared_address` — manipulate pending or active shared-address state [7](#0-6) .
- `arbiter_contract_offer` and other contract subjects that write local state and emit UI-facing events [8](#0-7) .

None of these paths currently re-check whether the sender is only an "indirect" (unverified) correspondent, which is precisely the authorization gap the removed check existed to close — mirroring the GitLab CVE-2025-0652 pattern where a class of caller that should be scoped to limited, internal functionality instead reaches functionality/data intended for verified peers only.

### Impact Explanation
An attacker who gets themselves listed as a cosigner in a shared-address proposal (which only requires being named in `device_addresses_by_relative_signing_paths`/cosigner lists, not a user-confirmed pairing) becomes an "indirect correspondent" and can then freely drive privileged wallet flows: submit private payment chains for processing/forwarding, solicit signatures over crafted units via `signing_request`, and manipulate shared-address/contract state — actions that were meant to be restricted to wallet-creation bootstrap subjects only. This can lead to leakage/forwarding of private payment data to unintended parties, and can be leveraged to push malicious signing prompts to the user in a multisig/shared-address context, ultimately assisting unauthorized spending or corruption of shared-address state.

### Likelihood Explanation
Reachable purely by device-message traffic that any peer can send to the hub/target device — the sender only needs to become an "indirect correspondent" (a low bar, achievable by naming an attacker device as a cosigner in a wallet/shared-address setup flow) and then send any message subject; there is no compensating check anywhere else in the call path once `bIndirectCorrespondent` is computed.

### Recommendation
Restore and enforce the subject whitelist for indirect correspondents in `wallet.js`'s `handleMessageFromHub` (re-enable the check removed at lines 92–93), rejecting any subject outside the wallet-bootstrap set (`cancel_new_wallet`, `my_xpubkey`, `new_wallet_address`, etc.) when `bIndirectCorrespondent` is true, and audit each sensitive subject handler (`sign`, `private_payments`, `new_shared_address`, `arbiter_contract_offer`, etc.) to ensure it independently validates that the sender is an intended, appropriately-trusted counterparty rather than relying solely on this now-broken upstream gate.

### Proof of Concept
1. Attacker proposes a shared/multisig address to a victim's device, including an attacker-controlled device address in the cosigner list; the victim's `walletDefinedByAddresses`/`walletDefinedByKeys` flow calls `addIndirectCorrespondents`, inserting the attacker device into `correspondent_devices` with `is_indirect=1` [3](#0-2) .
2. Attacker's device (still never manually paired) sends a `hub/message` with `subject: "sign"` (or `"private_payments"`, `"new_shared_address"`, etc.) to the victim through the hub.
3. `device.js` finds the correspondent known (`is_indirect=1`) and calls `handleMessage(true)`, i.e. `bIndirectCorrespondent=true` [9](#0-8) .
4. In `wallet.js`, because the whitelist check is commented out, execution proceeds into the full `switch(subject)` and processes the attacker's `sign`/`private_payments`/etc. request exactly as if from a fully verified correspondent [10](#0-9) , triggering signing prompts or private-payment forwarding that should have been blocked.
