### Title
Headers-commission split among `earned_headers_commission_recipients` uses round-to-nearest instead of floor, allowing supply inflation - (File: headers_commission.js)

### Summary
`calcHeadersCommissions()` splits a fixed headers-commission amount (`full_amount`, taken from `punits.headers_commission`) among the recipients declared in a multi-author unit's `earned_headers_commission_recipients` field. Each recipient's share is computed with `Math.round(full_amount * share / 100.0)` instead of a rounding mode that guarantees the sum of all shares never exceeds `full_amount`. Because the shares are attacker-chosen percentages (as long as they sum to 100 and are positive integers), an attacker can pick a distribution of many small shares that each round up at the `.5` boundary, so the sum of the individually-rounded amounts exceeds the original `full_amount`. This mirrors the CompoundV2/ERC4626 bug class: rounding that should always favor "the protocol" (global bytes-in-circulation invariant) instead favors "the user" (the address collecting headers commission), creating bytes from nothing.

### Finding Description
`calcHeadersCommissions()` reads, per payer unit (`punits`), the single `headers_commission` amount it paid, and distributes it to the winning child unit's authors according to `earned_headers_commission_recipients`. The per-recipient share is computed independently: [1](#0-0) 

and, in the non-`bFaster` verification path that also drives the actual DB insert used by MySQL and validated in SQLite: [2](#0-1) 

The MySQL variant of the same computation also uses `ROUND(...)`: [3](#0-2) 

These individually rounded amounts are then summed per address and inserted into `headers_commission_outputs`: [4](#0-3) 

Crucially, there is no code path anywhere in `calcHeadersCommissions()` that checks `SUM(amount) === full_amount` for a given payer unit/child unit pair — each recipient's payout is computed and summed independently, so any rounding surplus is silently created and becomes spendable.

The `earned_headers_commission_recipients` field is only constrained as follows during validation: shares must be positive integers summing to 100, addresses must be valid and sorted: [5](#0-4) 

Nothing in this validation requires the recipient addresses to actually be authors of the unit, nor does it cap the number of recipients beyond what fits in a unit (limited only by `MAX_MESSAGES_PER_UNIT`/unit size, not by author count). An attacker with control over a multi-authored unit (or a unit they know will win headers commission) can therefore declare many recipients with carefully chosen percentages designed to each round up under `Math.round`, e.g. 100 recipients each with `share=1`; whenever `full_amount * 1/100` lands above `x.5`, every one of those fractional shares rounds up, and the aggregate payout can exceed `full_amount` by close to `(recipients_count - 1) * 0.5` bytes per winning unit.

This is the direct analog of the reported bug class: a rounding operation that should be biased to protect the invariant ("total distributed must never exceed total available") is instead biased toward whichever party benefits from `round()`'s nearest behavior, exactly as `Math.Rounding.Ceil` in `_convertAssetsToShares` and `previewWithdraw`'s `Ceil` rounding favored the withdrawing user over the vault/protocol in the original report.

### Impact Explanation
Headers commission accounting directly feeds `headers_commission_outputs`, which is a spendable input type validated in `validatePaymentInputsAndOutputs` (`type: "headers_commission"`), i.e., it becomes real, transferable bytes in the base asset. If the sum of rounded recipient shares for a given payer unit systematically exceeds the `headers_commission` amount that was actually paid by that unit (which itself is deducted from a real payer's balance and is bounded, fixed money), this creates spendable bytes that were never paid in — a supply-inflation bug affecting the base asset, which every node must agree on identically as part of consensus-critical accounting. This satisfies the "supply inflation" impact criterion.

### Likelihood Explanation
Likelihood is Medium: the attacker needs to author a multi-author unit (`authors.length > 1`) that is included with an `earned_headers_commission_recipients` field, and that unit needs to be selected as the DAG "winner" child of a parent unit paying headers commission (deterministic hash-based tie-break, so this is achievable by controlling both authorship and simply waiting to be a highest-hash winning child, or by co-authoring with an accomplice). No special privileges are required — this is fully reachable by any ordinary unit author, i.e., an "unprivileged unit poster." The magnitude of the inflation per triggering unit is small (bounded by roughly half a byte times the number of distinct recipients minus one), but it is repeatable across every stabilized MC index the attacker controls, allowing systematic accumulation over time.

### Recommendation
Change the rounding strategy for headers-commission distribution so that the sum of individually rounded shares can never exceed `full_amount`:
- Use `Math.floor` for each recipient's share and assign the remainder (due to flooring) to a single fixed recipient (e.g., the last recipient in sorted order), or
- Compute all shares first, then adjust the final recipient's amount as `full_amount - sum(other rounded amounts)` to guarantee exact conservation, and
- Apply the same fix to the MySQL `ROUND(...)` query, replacing it with `FLOOR(...)` plus a remainder-correction step, or by doing the aggregation/remainder-correction in application code rather than in SQL.

### Proof of Concept
1. Attacker constructs a 2-of-2 (or more) multi-authored unit `U` that will serve as a winning child (per `getWinnerInfo`'s SHA1 hash tie-break) of a parent unit `P` whose `headers_commission` is, say, `150` bytes.
2. Unit `U` sets `earned_headers_commission_recipients` to 100 entries, each with `earned_headers_commission_share = 1` (sums to 100, satisfying `validateHeadersCommissionRecipients`), where each recipient address is fully controlled or colludes with the attacker.
3. When `calcHeadersCommissions()` runs for `P`, each recipient's payout is `Math.round(150 * 1 / 100) = Math.round(1.5) = 2` bytes.
4. Total distributed = `100 * 2 = 200` bytes, versus the `150` bytes actually paid by `P` — a `50`-byte inflation event created purely by the rounding choice.
5. These `200` bytes appear in `headers_commission_outputs` and are fully spendable as validated `headers_commission` inputs in `validatePaymentInputsAndOutputs`, meaning `50` extra base-asset bytes now circulate that were never paid by any unit's balance.

Note: I was not able to fully confirm, within this session, whether any implicit unit-size limit or an author-count restriction elsewhere in the codebase caps the number of `earned_headers_commission_recipients` entries below the ~100 used in this PoC; a smaller number of recipients still produces a smaller but nonzero inflation whenever percentages are chosen near the `.5` rounding boundary, so the vulnerability holds regardless of the exact achievable recipient count.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}
