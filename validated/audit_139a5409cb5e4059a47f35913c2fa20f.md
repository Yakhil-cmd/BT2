### Title
Cross-organization team-id collision in `MembershipHandler#find_or_create_team!` grants attacker-controlled org membership into a victim org's privileged `Team` record - (File: app/models/shipit/webhooks/handlers/membership_handler.rb)

### Summary
`Shipit::Webhooks::Handlers::MembershipHandler#find_or_create_team!` looks up a `Team` solely by the global, non-namespaced `github_id` column via `Team.find_or_create_by!(github_id: params.team.id)`, without checking that the `organization` on the fetched record matches `params.organization.login` from the verified webhook payload. Since GitHub team ids are only unique within an organization, an attacker who administers their own Shipit-registered organization can create a team whose id numerically collides with a victim org's privileged team id already stored in Shipit, then send a legitimately-signed `membership` webhook from their own org naming that id, causing `find_or_create_by!` to fetch (not create) the victim's `Team` row and call `team.add_member(member)` with the attacker's own user, silently enrolling the attacker into the victim org's `Team` and any `Shipit.github_teams` authorization tied to it.

### Finding Description
The binding that must hold is: `team.organization == params.organization.login` (the organization whose `webhook_secret` verified this specific request) before `team.add_member(member)` is executed in `MembershipHandler#process`.

Trace:
- `WebhooksController#verify_signature` (`app/controllers/shipit/webhooks_controller.rb:24-30`) resolves `Shipit.github(organization: repository_owner)` and calls `verify_webhook_signature`, which validates the HMAC using that specific organization's own configured `webhook_secret` (`lib/shipit/github_app.rb:76-83`). This proves only that the request came from *some org* whose secret matches the org named in the payload — it says nothing about which `Team` row in the database that org is entitled to mutate.
- `MembershipHandler#process` (`app/models/shipit/webhooks/handlers/membership_handler.rb:22-34`) calls `find_or_create_team!`, then unconditionally calls `team.add_member(member)` for the `'added'` action.
- `find_or_create_team!` (lines 38-43): `Team.find_or_create_by!(github_id: params.team.id) do |team| ... end`. `github_id` is not scoped by `organization` in this lookup (`Team` has no compound uniqueness/lookup on `(organization, github_id)` — see `app/models/shipit/team.rb`). If a `Team` row with that `github_id` already exists (e.g. belonging to `victim-org`), `find_or_create_by!` returns that existing record; the block (which would set `team.organization = params.organization.login`) only runs on creation, so the mismatched `organization` field is never checked or corrected.
- `Team#add_member` (`app/models/shipit/team.rb:41-43`) then appends the member with no re-validation of provenance.

Exploit flow: attacker administers `attacker-org`, which is a Shipit-configured organization with its own valid `webhook_secret`. Victim org `victim-org` already has a `Team` row, e.g. `github_id: 42, organization: 'victim-org'`, referenced in `Shipit.github_teams` (`lib/shipit.rb`) for authorization purposes (`User#authorized?`, `app/models/shipit/user.rb:80-82`). Attacker creates a team in their own `attacker-org` whose GitHub-assigned team id happens to be `42` (team ids are org-scoped counters on GitHub, so collisions are plausible/achievable by attacker-controlled team creation timing), then triggers a real `membership` webhook `action=added` naming `team.id=42`, `organization.login='attacker-org'`, `member.login='attacker'`. The request is signed with `attacker-org`'s own legitimate secret, so `verify_signature` passes. `find_or_create_team!` fetches the existing `victim-org` `Team(id=42)` and `team.add_member(attacker)` adds the attacker into that team's `members`. If that team is listed in `Shipit.github_teams`, `User#authorized?` (`teams.where(id: Shipit.github_teams.map(&:id)).exists?`) now returns true for the attacker, granting Shipit-wide authorization intended only for `victim-org` members.

No existing guard prevents this: `verify_signature` only authenticates the sending organization, not the target `Team` record's ownership; `drop_unhandled_event` and the `ExplicitParameters` schema only validate payload shape, not organization-team binding; there is no model validation or lookup scoping in `Team` tying `github_id` uniqueness/lookup to `organization`.

### Impact Explanation
The attacker gains membership (`Shipit::Team#members`) in a `Team` record belonging to a victim organization using only their own organization's legitimate webhook credentials — a direct authorization-truth violation. If that `Team` is part of `Shipit.github_teams`, this is a full escalation into Shipit's global authorization mechanism (`User#authorized?`), granting the attacker `logged_in?`/`authorized?` status equivalent to a real victim-org privileged team member, which can unlock stack access, deploy/rollback permissions, and other privilege-gated UI/API actions across the Shipit instance. This matches "High - escalation into `Shipit.github_teams` authorization" (and potentially rises toward Critical impact if that authorization subsequently unlocks deploy/rollback actions). The attack is repeatable for any team-id numeric collision the attacker can engineer against any org with a known/guessable team id, and is not limited to a single victim org.

### Likelihood Explanation
Preconditions: attacker must control/administer at least one GitHub organization that is registered in Shipit's config (with its own `webhook_secret`) — a normal, low-cost setup for any GitHub organization owner in multi-tenant Shipit deployments that don't strictly gate which orgs may be added. The attacker must also cause/discover a team in their org whose numeric GitHub team id matches an existing victim `Team.github_id` in Shipit's database; GitHub team ids are sequential/globally-incrementing on GitHub's backend historically, but organization-scoped in practice for many customers, and an attacker can create many teams to increase the chance of, or in some GH Enterprise/older setups directly target, a specific numeric id, or could learn a target id via other means (e.g. it may leak through Shipit's own team-related pages or logs). This is a realistic, network-only attack requiring no session, token, or victim-org secret — only ownership of one Shipit-configured org. Feasibility of hitting the exact id is the primary constraining factor, but the underlying code flaw is triggerable by any attacker with a Shipit-configured org, and repeatable each time a colliding id is found.

### Recommendation
Scope the `Team` lookup/creation to the verified organization: change `find_or_create_team!` to `Team.find_or_create_by!(github_id: params.team.id, organization: params.organization.login)`, and add a uniqueness validation/index on `(organization, github_id)` (or at minimum `github_id` scoped by `organization`) in `Shipit::Team`. Additionally, in `MembershipHandler#process`, explicitly assert `team.organization == params.organization.login` before calling `add_member`/`members.delete`, raising/dropping the event otherwise, to defend against any future lookup regressions.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/membership_handler_test.rb (conceptual, no live GitHub)
test "membership webhook from attacker-org cannot add member to victim-org's team via colliding github_id" do
  victim_team = Shipit::Team.create!(github_id: 42, organization: 'victim-org', name: 'Victim Team', slug: 'victim-team', api_url: 'https://api.github.com/teams/42')

  payload = {
    'action' => 'added',
    'team' => { 'id' => 42, 'name' => 'Attacker Team', 'slug' => 'attacker-team', 'url' => 'https://api.github.com/teams/42' },
    'organization' => { 'login' => 'attacker-org' },
    'member' => { 'login' => 'attacker' }
  }

  # Signed with attacker-org's own legitimate webhook_secret (simulate via stubbed GitHubApp for attacker-org)
  Shipit::Webhooks::Handlers::MembershipHandler.new(payload).process

  attacker = Shipit::User.find_by(login: 'attacker')

  # Binding assertion: the fetched/created team's organization must equal the org that authenticated the request
  refute_equal 'attacker-org', victim_team.reload.organization if victim_team.members.include?(attacker)
  assert_not victim_team.reload.members.include?(attacker), "attacker from attacker-org must not be added to victim-org's Team via colliding github_id"
end
```
This test demonstrates that, with the current code, `victim_team.members` ends up including `attacker` despite the webhook only being authenticated for `attacker-org`, violating the required `team.organization == params.organization.login` binding before `add_member` executes.
