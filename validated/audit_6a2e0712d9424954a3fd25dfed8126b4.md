### Title
Repository-unscoped commit lookup in `StatusHandler#process` allows cross-tenant status forgery - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)`, ignoring the webhook's own `repository.full_name`, unlike `PushHandler` which correctly scopes lookups through the repository-derived `stacks` helper. Any commit sharing that SHA in any stack—regardless of which repository originated the webhook—receives the forged status, which is then folded into `Status::Group.compact` via `Commit#status`, corrupting `deployable?`/`blocked?` for a repository the attacker never authenticated against.

### Finding Description
The binding assumed by the question is: *every `Status`/`CheckRun` row folded into `Status::Group.compact(commit, statuses_and_check_runs)` was authenticated for `commit.stack.repository`*, i.e. `status.provenance_repository == commit.stack.repository`. Tracing the write path shows this does not hold.

`Handler#stacks` correctly scopes lookups to the webhook's own repository: [1](#0-0) 

`PushHandler` uses that scoped helper: [2](#0-1) 

`StatusHandler` does not — it queries every `Commit` in the entire database by `sha`, with no repository filter at all: [3](#0-2) 

For each matched commit, `create_status_from_github!` writes a new `Status` scoped to that commit's own `stack_id` and reload-recomputes `Commit#status`: [4](#0-3) [5](#0-4) 

The created row's `stack_id` is correctly set to the *matched commit's* stack, so the row's DB provenance appears self-consistent — but the *data* in that row (`state`, `context`, `description`) was authenticated only against the attacker's own repository's webhook delivery, not against the victim's repository. `Status::Group.compact` (via `Commit#status`) then aggregates this attacker-authored row alongside the victim's genuine statuses, per-context, exactly as the question describes.

Exploit path:
1. Git commit SHAs are content-addressed (SHA-1 over tree/parents/author/committer/message/timestamps). Forks of a public repository, or repositories with shared history/cherry-picked commits, frequently contain commits with identical SHAs to commits also tracked by a *different* Shipit-registered stack (the victim repo).
2. Attacker owns/controls a repository (fork) that has the GitHub App/webhook installed (any repo the attacker can create where the App can be installed, or an org where the App is broadly installed) — satisfying the stated attacker model ("emit webhooks from a repository they own").
3. Attacker sets a GitHub commit status (`success`, novel `context`) via the GitHub Status API on their own repository for the SHA-colliding commit. GitHub delivers a validly-signed `status` webhook to Shipit for the attacker's own repository/installation.
4. `verify_signature`/`GitHubApp#verify_webhook_signature` correctly validates this webhook — it *is* a legitimate delivery, just legitimately about the attacker's own repo. This guard does not, and cannot, prevent the handler from acting on unrelated repositories, because `StatusHandler` never consults `repository.full_name` after signature verification.
5. `StatusHandler#process` matches the SHA against `Commit.where(sha: params.sha)`, which includes the victim's commit in a completely different stack, and calls `commit.create_status_from_github!(params)` on it, injecting the attacker's forged `success` status into the victim's commit's status set.
6. `Commit#status` recomputes `Status::Group.compact`, mixing the forged `success` context with the victim's genuine `pending`/`failure` contexts, potentially flipping `simple_state`, `deployable?`, and unblocking `schedule_continuous_delivery`/merges on the victim's stack.

Existing guards (`verify_signature`, `ExplicitParameters` schema, `force_github_authentication`) validate that a webhook *delivery* is authentic and well-formed, but none of them enforce that the *target records mutated* belong to the repository named in that same delivery — that binding is simply absent from `StatusHandler`.

### Impact Explanation
An attacker who controls any repository with the GitHub webhook/App installed can inject a forged `success`/`failure`/`pending` status context onto a same-SHA commit belonging to a stack/repository they do not control, altering `Commit#deployable?`/`blocked?` and potentially triggering `ContinuousDeliveryJob`/auto-merge on the victim's stack. This is a cross-tenant write ("a payload for one repository mutating another's stack, commit") — matching the Critical impact category (unauthorized deploy/merge triggered from forged/mismatched authorization). It is repeatable against any repository sharing commit history (forks, cherry-picks, squash-merges with identical content) with a repository registered as a Shipit stack.

### Likelihood Explanation
Exploitability requires: (a) the attacker's own repository to have the Shipit/GitHub App webhook configured (attacker-controlled, low cost — e.g. forking a public repo often auto-applies org-wide app installations, or the attacker registers their own repo if Shipit/App installation is self-service), and (b) a SHA collision with a commit in the victim stack, which is common for forks and shared-history repositories (not a cryptographic collision — an identical, unmodified commit shared via fork/cherry-pick naturally has the identical SHA). No secrets are required; the webhook is legitimately signed for the attacker's own repository. This makes the attack cheap and repeatable.

### Recommendation
In `StatusHandler#process` (and audit `CheckSuiteHandler`/other handlers for the same pattern), scope the commit lookup through the webhook's own repository, mirroring `PushHandler`:
```ruby
def process
  stacks.each do |stack|
    stack.commits.where(sha: params.sha).each do |commit|
      commit.create_status_from_github!(params)
    end
  end
end
```
This enforces `commit.stack.repository == Repository.from_github_repo_name(payload.dig('repository','full_name'))` before any status row is written, restoring the binding assumed by `Status::Group.compact`.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb (conceptual; no live GitHub)
test "status webhook from repository A must not mutate commits in repository B sharing the same sha" do
  repo_a = shipit_stacks(:shipit) # attacker-controlled repo/stack
  repo_b = shipit_stacks(:cyclimse) # victim repo/stack

  shared_sha = "a" * 40
  victim_commit = repo_b.commits.create!(sha: shared_sha, message: "shared history commit")
  victim_commit.statuses.create!(stack: repo_b, state: "pending", context: "ci/required")
  repo_b.update!(required_statuses: ["ci/required"])

  # Precondition per binding: only rows authenticated for repo_b's repository
  # should ever be folded into victim_commit.status
  before_state = victim_commit.status.simple_state
  assert_equal "pending", before_state

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "context" => "attacker/forged-context",
    "repository" => { "full_name" => repo_a.repository.full_name }, # attacker's own, validly-signed repo
  }
  Shipit::Webhooks::Handlers::StatusHandler.call(payload)

  victim_commit.reload
  after_state = victim_commit.status.simple_state

  # BINDING VIOLATION: a row authenticated only for repo_a ends up affecting repo_b's commit
  assert_includes victim_commit.statuses.pluck(:context), "attacker/forged-context"
  assert_equal before_state, after_state, "cross-repository status must not alter victim commit's aggregate state"
end
```
This test demonstrates that `StatusHandler.call` with a payload whose `repository.full_name` belongs to the attacker's repo still mutates `victim_commit`'s statuses purely because the SHA matches, violating the same-repository binding and altering the aggregate `simple_state`/`deployable?` computed by `Status::Group.compact`.
