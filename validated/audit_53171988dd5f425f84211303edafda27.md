### Title
Webhook signature verification fails open for GitHub organizations with no configured `webhook_secret`, allowing forged events to reach privileged handlers - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`)

### Summary
`WebhooksController#verify_signature` delegates trust decisions entirely to `GitHubApp#verify_webhook_signature`, which is designed to *always* return `true` whenever the target organization has no `webhook_secret` configured. [1](#0-0)  Because `docs/setup.md` explicitly documents the webhook secret as *optional*, an operator following the documented setup for an organization can end up with an endpoint that accepts **any** unsigned/unauthenticated POST as if it came from GitHub. [2](#0-1)  This mirrors the `MultiRewards` report's core defect: a guard that is assumed to always constrain a privileged action (reward distribution / signature authentication) silently degrades to a no-op under an unhandled state (no stakers / no secret), and downstream logic (reward accrual / webhook handlers) keeps acting on that unguarded state.

### Finding Description
`WebhooksController#verify_signature` resolves the GitHub App/organization to check against from the payload (`repository_owner`, falling back to `organization.login`), then calls `github_app.verify_webhook_signature`: [3](#0-2) 
The verifier itself is:
```ruby
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  ...
end
``` [1](#0-0) 

The equality this endpoint is supposed to enforce is:
`signature verified with organization's webhook_secret == request genuinely originated from GitHub for that organization`

When `webhook_secret` is blank/unset for an organization, this collapses to `true == true` unconditionally — the "verified" side of the equality is never actually evaluated against the attacker-controlled `X-Hub-Signature` header or payload at all. Any unauthenticated third party who knows (or guesses) the name of a configured GitHub organization can POST arbitrary JSON to `/webhooks` with `X-Github-Event` set to any supported event, and it will be dispatched unchanged to `Shipit::Webhooks.for_event(event)` handlers. [4](#0-3) 

This directly threatens the `membership` handler path, which creates `Team` and `User` records on the fly from webhook payload fields with no further validation against a real GitHub state: [5](#0-4) 
Because `github.oauth.teams` in `config/secrets.yml` is the authorization gate (`Shipit.github_teams`) used to decide which GitHub teams grant access to the app, forged `membership` events that add an attacker-chosen login to a permitted team escalate straight into that authorization boundary — one of the explicitly in-scope High-impact outcomes.

### Impact Explanation
This is a High-impact issue: it allows escalation into `Shipit.github_teams` authorization (via forged `membership` events creating/associating `User`/`Team` records) and unauthenticated triggering of repository sync (`push`), status, and check-suite handlers, without any GitHub session, API token, or webhook secret possessed by the attacker. It matches the report's underlying bug class — a protective check (reward gating / signature gating) that is silently bypassed under a specific, easily reachable configuration state (no stakers / no secret) while the surrounding system continues to treat the state as trusted.

### Likelihood Explanation
Low-to-Medium: it requires an organization in the deployment's `config/secrets.yml` to have `webhook_secret` left blank — which the setup docs mark as optional and even ship an example config file with `webhook_secret: # nil` for both sample organizations. [6](#0-5)  An operator who follows the documented "optional" wording literally (skipping the secret) reaches this state without doing anything wrong per the docs, so it is a plausible real-world misconfiguration rather than a hypothetical one.

### Recommendation
Do not allow `verify_webhook_signature` to return `true` when `webhook_secret` is absent. Either make `webhook_secret` mandatory for every configured organization (fail fast at boot/config-load time if missing), or make `verify_signature` reject the request (422) when no secret is configured. Consider removing "optional" language from `docs/setup.md` regarding the webhook secret.

### Proof of Concept
1. Configure an organization `victim-org` in `config/secrets.yml` with `webhook_secret` unset (as shown in the shipped example `config/secrets.development.shopify.yml`).
2. As an unauthenticated attacker, `POST /webhooks` with headers `X-Github-Event: membership` and a body such as `{"organization": {"login": "victim-org"}, "team": {"id":1,"name":"Admins","slug":"admins"}, "member": {"login":"attacker-login"}, "action":"added"}`, without any `X-Hub-Signature` header (or an arbitrary bogus one).
3. `verify_webhook_signature` returns `true` unconditionally because `webhook_secret` is blank for `victim-org`. [7](#0-6) 
4. The membership handler creates/updates `Team` and `User` records exactly as demonstrated in the existing test suite, without any verification that the request actually came from GitHub. [5](#0-4)

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
