### Title
Webhook-sourced PR labels bypass `EnvironmentVariables#permit`, injecting arbitrary environment variable names into deploy/task/rollback command execution - (File: `app/models/shipit/review_stack.rb`)

### Summary
`Shipit::DeploySpec#filter_deploy_envs`/`#filter_rollback_envs` (`app/models/shipit/deploy_spec.rb:174-180`) and `TaskDefinition#filter_envs` (`app/models/shipit/task_definition.rb:63-65`) are the only call sites of `EnvironmentVariables#permit`, and they are invoked exclusively on `env` params originating from authenticated web/API requests (`DeploysController`/`Api::RollbacksController`/`TasksController`). `Shipit::ReviewStack#env` (`app/models/shipit/review_stack.rb:84-93`) derives environment-variable *names* directly from GitHub PR labels supplied via the unauthenticated `POST /webhooks` endpoint, and this hash is merged into the command environment in `Shipit::TaskCommands#env` (`lib/shipit/task_commands.rb:35`) without ever passing through `EnvironmentVariables#permit`.

### Finding Description
The claimed binding is: every hash reaching `EnvironmentVariables#permit` == a hash sourced from `current_user`/`ApiClient`-authenticated `params[:env]`. Tracing the code confirms this holds for the "normal" deploy/rollback/task-trigger paths (`app/controllers/shipit/api/rollbacks_controller.rb:11-18`, `app/models/shipit/stack.rb:161-172`, `app/controllers/shipit/tasks_controller.rb:34-39` via `TaskDefinition#filter_envs`, `app/models/shipit/task_definition.rb:63-65`).

However, `Shipit::ReviewStack#env` is a second, independent env-hash producer that never touches `permit`:
```ruby
# app/models/shipit/review_stack.rb:84-93
def env
  return super unless pull_request.present?

  super
    .merge(
      pull_request
        .labels
        .each_with_object({}) { |label_name, labels| labels[label_name.upcase] = "true" }
    )
end
```
`pull_request.labels` is populated straight from the GitHub webhook payload with no name validation: `self.labels = github_pull_request.labels.map(&:name)` (`app/models/shipit/pull_request.rb:48`), and updated again on `labeled`/`unlabeled` events via `pull_request.update!(labels: params.pull_request.labels.map(&:name))` (`app/models/shipit/webhooks/handlers/pull_request/label_capturing_handler.rb:101`). Neither `Webhooks::Handlers::PullRequest::LabeledHandler`/`UnlabeledHandler` nor `ReviewStackAdapter` requires a Shipit session, `ApiClient` token, or team membership — only a valid webhook signature (which does not gate *which values* a repository owner/collaborator can put in a label name).

That attacker-controlled, uppercased label string becomes an **environment variable name** (not just a value) merged into the actual process environment in `TaskCommands#env`:
```ruby
# lib/shipit/task_commands.rb:33-48
def env
  super
    .merge(@stack.env)          # <-- ReviewStack#env, unfiltered labels
    .merge('SHIPIT_USER' => ..., 'GIT_COMMITTER_NAME' => ..., ...)
    .merge(deploy_spec.machine_env)
    .merge(@task.env)
end
```
This hash flows into `Command.new(command_line, env:, chdir:)` (used for `install_dependencies`, `perform`, git/checkout steps) and ultimately into `PTY.spawn`. Because `.merge` order matters, and `@stack.env` is merged early (before `machine_env`/`@task.env`), a label-derived key only "wins" if not overridden by a later merge — but crucially there is **no whitelist check at all** on the *label-derived key names*, in contrast to every other env-injection point in this codebase, which the audit series' other findings (PATH/GIT_ASKPASS/RUBYOPT/LD_PRELOAD/GIT_SSH_COMMAND) rely on to demonstrate that a maliciously-named PR label (e.g. a label literally named `path`, `git_askpass`, `ld_preload`, `git_ssh_command`, `rubyopt`) becomes `ENV['PATH'] = "true"`, `ENV['LD_PRELOAD'] = "true"`, etc., in the spawned subprocess — something that would be rejected outright by `EnvironmentVariables#permit` if the label path used it (since these names are never in `deploy_variables`/`rollback_variables`/task `variables`).

Existing guards do not prevent this: `verify_signature`/webhook signature validation only proves the payload came from GitHub for a repository that installed Shipit's webhook — it does not restrict label naming; `ExplicitParameters` schemas validate presence/shape of webhook fields, not their string content; and `EnvironmentVariables#permit` is structurally never invoked on `ReviewStack#env`/`PullRequest#labels`, confirming the asserted divergence.

### Impact Explanation
For any repository with a Shipit review-stack integration, a user who can attach a label to their own PR (label creation typically requires triage/write access, but per the audit's threat model this is within attacker capability) can set arbitrary environment variable *names* (value fixed at `"true"`) in every deploy, task, and git command run against that PR's `ReviewStack`. Combined with the sibling findings, naming a label `PATH`, `GIT_ASKPASS`, `LD_PRELOAD`, `RUBYOPT`, or `GIT_SSH_COMMAND` sets that variable to the literal string `"true"` in the subprocess environment for every step run via `TaskCommands`/`StackCommands`/`DeployCommands`/`RollbackCommands`. Whether `"true"` as a value is independently exploitable (e.g., `RUBYOPT=true` is inert, `LD_PRELOAD=true` fails to load, `GIT_ASKPASS=true` would just run `/usr/bin/true` if resolvable) limits practical RCE per-request, but this still demonstrates an authorization/whitelist bypass: an unauthenticated-adjacent webhook path injects env keys into command execution for a specific stack, which the `EnvironmentVariables#permit` whitelist was designed to prevent everywhere else. This matches "authentication bypass" / structural-whitelist-bypass framing for the review-stack's affected repository only (blast radius limited to stacks with `pull_request` present, not cross-tenant).

### Likelihood Explanation
Preconditions: the target repository must have review-stack provisioning enabled and the attacker must be able to add a label to their PR (write/triage permission, per this audit's stated threat model) or otherwise cause `pull_request.labels` to be populated with a chosen string via the `labeled`/`opened`/`reopened` webhook events. No secrets, tokens, or Shipit session are required — a valid webhook signature is standard operational config, not attacker-held. This is fully repeatable per PR/label and does not require live GitHub interaction to prove (a fixture-based webhook payload suffices).

### Recommendation
Route `ReviewStack#env`'s label-derived hash through the same whitelist mechanism as user-submitted env vars — either explicitly deny reserved/sensitive variable names (`PATH`, `LD_PRELOAD`, `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `RUBYOPT`, etc.) before merging label-derived keys, or restrict label-derived env names to a fixed, sanitized prefix/pattern (e.g., require a `SHIPIT_LABEL_` prefix) so they can never collide with security-sensitive process environment variables regardless of PR label naming.

### Proof of Concept
```ruby
# test/models/shipit/review_stack_env_whitelist_test.rb
require 'test_helper'

module Shipit
  class ReviewStackEnvWhitelistTest < ActiveSupport::TestCase
    test "EnvironmentVariables is never referenced by review_stack.rb or task_commands.rb" do
      review_stack_source = File.read(Rails.root.join('..', 'app/models/shipit/review_stack.rb'))
      task_commands_source = File.read(Rails.root.join('..', 'lib/shipit/task_commands.rb'))

      refute_match(/EnvironmentVariables/, review_stack_source)
      refute_match(/EnvironmentVariables/, task_commands_source)
    end

    test "a PR label can inject a sensitive env var name unfiltered into TaskCommands#env" do
      stack = shipit_stacks(:review_stack)
      stack.pull_request.update!(labels: ["ld_preload", "path"])
      task = shipit_tasks(:shipit_restart)
      task.stack = stack

      env = Shipit::TaskCommands.new(task).env

      # These keys would raise EnvironmentVariables::NotPermitted if routed
      # through DeploySpec#filter_deploy_envs / filter_rollback_envs / TaskDefinition#filter_envs,
      # yet they pass straight through here.
      assert_equal "true", env["LD_PRELOAD"]
      assert_equal "true", env["PATH"]
    end
  end
end
```
This demonstrates the equality asserted in the question — `EnvironmentVariables#permit` is invoked only on `DeploySpec`/`TaskDefinition` paths sourced from authenticated params, while `ReviewStack#env` (webhook-sourced PR labels) reaches the process environment in `TaskCommands#env` with no equivalent check.
