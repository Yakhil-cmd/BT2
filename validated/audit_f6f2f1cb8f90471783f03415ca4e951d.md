### Title
Unbounded, unlimited-dust asset outputs sent to an AA address can permanently freeze the AA's asset balance via `MAX_INPUTS_PER_PAYMENT_MESSAGE` bypass in `completePaymentPayload` - ([File: aa_composer.js])

### Summary
`aa_composer.js`'s `sendUnit()`/`completePaymentPayload()` builds AA outgoing payments by querying **all** unspent outputs of the target asset held by the AA address with no row limit and, for non-base assets, **no dust-amount filter** [1](#0-0) . Any unprivileged unit poster can therefore flood an AA's address with an arbitrarily large number of tiny-amount custom-asset outputs. When the AA later needs to send that asset (e.g. in response to a legitimate trigger), `iterateUnspentOutputs()` must walk through the entire unbounded result set to accumulate the target amount, potentially consuming all of it as inputs [2](#0-1) . Because `validatePaymentInputsAndOutputs()` explicitly exempts AA-authored units from the normal `MAX_INPUTS_PER_PAYMENT_MESSAGE` cap (`&& !objValidationState.bAA`), there is no protocol-level ceiling on how many inputs an AA response payment can contain [3](#0-2) .

### Finding Description
The dust-filtering comment in the code explicitly acknowledges the base-asset dust-spam risk ("byte outputs less than 60 bytes ... are ignored to prevent dust attack: spamming the AA with very small outputs so that the AA spends all its money for fees when it tries to respond") but the mitigating `amount>=FULL_TRANSFER_INPUT_SIZE` filter is applied **only when `asset` is null** (base asset); for any named asset the `WHERE` clause omits the minimum-amount condition entirely:
```
WHERE address=? AND asset"+(asset ? "="+conn.escape(asset) : " IS NULL AND amount>=" + FULL_TRANSFER_INPUT_SIZE)+" AND is_spent=0 ...
``` [4](#0-3) 

This means a low-cost unit poster can send thousands/millions of payments of amount = 1 (or any minimal amount) of a chosen custom asset to the AA's address, growing the outputs table entries for `(address, asset)` without bound — directly analogous to the `deposits` array growth described in the source report, since the attacker pays only the ordinary per-unit fee (analogous to the "msg.value = 0" cheap-growth vector) and the honest processing path (`refundDeposit`/here, the AA's asset-spend logic) must traverse the entire attacker-inflated set.

When the AA is subsequently triggered to send this asset (full amount or send-all), `readStableOutputs`/`readUnstableOutputsSentByAAs` fetch **all** matching rows (no `LIMIT`), and `iterateUnspentOutputs` loops through them, pushing every consumed output into `payload.inputs` [5](#0-4) . Because AA-authored units are exempt from `MAX_INPUTS_PER_PAYMENT_MESSAGE` [3](#0-2) , nothing stops the constructed payment message from containing an enormous number of inputs, producing a unit whose size vastly exceeds normal fee/size assumptions.

### Impact Explanation
This falls under "AA fund loss or freezing." Two concrete consequences:
1. If the resulting AA-response unit ends up being rejected downstream (oversized payload, excessive oversize/tps fees relative to the AA's byte balance, or other unit-size related failures), the AA's attempt to send the asset bounces. Since the dust outputs remain unspent and the attacker can keep re-inflating the set on every subsequent attempt, the AA can be made to permanently fail to pay out this asset — freezing legitimate user funds of that asset inside the AA, mirroring the "refund permanently DOSed" scenario in the source report.
2. Even absent an outright unit-size failure, every trigger that requires spending this asset from the AA must scan the full (attacker-inflated) output set, causing disproportionate computation/response cost paid for by ordinary trigger senders, and increasing bounce likelihood due to byte-fee exhaustion, which itself can strand the asset at the AA (fund freezing) for its rightful owner.

### Likelihood Explanation
Likelihood is high: any address (unprivileged unit poster) can post ordinary payment units containing many minimal-amount outputs of any asset the AA accepts (or even an unrelated asset it never actively manages), and the sender pays only standard commissions. The vulnerable code path is triggered automatically whenever the AA is asked to pay out that asset (a `payment` message in `messages`) as part of normal AA logic (e.g., a bounty/vault/DEX-style AA that returns a custom asset to users), which is a very common AA pattern.

### Recommendation
Apply the same dust-prevention filter used for base-asset outputs to asset outputs as well (a minimum-amount threshold, e.g. proportional to the effective per-input transfer cost/fees the AA would incur), and/or add an explicit `LIMIT` combined with pagination/looping logic in `readStableOutputs`/`readUnstableOutputsSentByAAs`, and enforce a sane input cap for AA-authored payment messages (or gracefully split multi-input payments across multiple sequential outputs) instead of exempting AAs from `MAX_INPUTS_PER_PAYMENT_MESSAGE` unconditionally in `validation.js`.

### Proof of Concept
1. Attacker identifies an AA address `A` that is designed to later pay out asset `X` to users (e.g., on a specific trigger/withdrawal condition).
2. Attacker crafts and posts a large number of low-fee units, each containing a `payment` message with a single output of asset `X`, amount = 1 (or any dust amount), addressed to `A`. Because there is no filter on minimum asset-output amount in the AA's spend-selection query [6](#0-5) , all these become eligible, unspent outputs of `A` in asset `X`.
3. Attacker repeats this over time to accumulate an arbitrarily large number of unspent `X` outputs at address `A`.
4. A legitimate user triggers the AA to withdraw/transfer asset `X` from `A`. `sendUnit()`→`completePaymentPayload()`→`readStableOutputs()` fetches all unspent `X` outputs of `A` (unbounded) and `iterateUnspentOutputs()` consumes them one by one until the target amount is reached, potentially consuming most/all of the attacker's dust plus the legitimate deposits, producing a payment message with a very large `inputs` array that is not blocked by `MAX_INPUTS_PER_PAYMENT_MESSAGE` due to the `!objValidationState.bAA` exemption [3](#0-2) .
5. The resulting AA response unit either fails oversize/fee checks (bouncing the trigger and leaving the asset stuck) or succeeds but at a disproportionate cost, and the attacker can repeat step 2 to keep the AA's asset payouts permanently degraded or blocked.

Note: I could not fully verify, within available tooling, the exact numeric thresholds (`MAX_INPUTS_PER_PAYMENT_MESSAGE` value, oversize fee formula behavior at very large input counts) that would definitively force a bounce versus merely a costly but successful response; confirming the precise breaking point would require deeper review of `constants.js` and `objectLength.js`/oversize-fee computation, which was not fully inspected in this pass.
