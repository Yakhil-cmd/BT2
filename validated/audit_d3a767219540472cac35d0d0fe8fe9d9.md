Found the binding break: the webhook signature is verified against the GitHub App configured for the organization named in `payload['repository']['owner']['login']` (or `payload['organization']['login']`), but the handler that actually mutates state (`PushHandler`, and other handlers via `Handler#stacks`) resolves the target `Repository`/`Stack` using an entirely different field: `payload['repository']['full_name']`. These two fields are never cross-checked against each other.

### Title
Webhook signature is validated against the payload's `owner.login`, but the acted-upon repository is taken from the unrelated `full_name` field - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization config (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (or `organization.login`) taken straight from the untrusted JSON body. Once the signature passes, the event is dispatched to handlers (e.g. `PushHandler`) which look up the `Stack` to mutate using a completely different payload field, `repository.full_name`, via `Handler#stacks`/`#repository_name`.

### Finding Description
`Shipit.github(organization: repository_owner)` is used purely to pick the secret for HMAC verification: [1](#0-0) . `repository_owner` is read from the same untrusted body: [2](#0-1) .

The signature computation itself only proves the raw POST body was signed by whichever organization's secret was chosen for verification: [3](#0-2) . It never binds the signature check to the specific `repository.full_name` used afterwards to decide what gets modified: [4](#0-3)  and [5](#0-4) .

In a single-organization deployment (the common case shown in `config/secrets.development.example.yml`), this is not exploitable because there is only one webhook secret and any repo name in the same signed payload is implicitly trusted. But in the documented multi-organization configuration (`config/secrets.development.shopify.yml`, `TOP_LEVEL_GH_KEYS`/`Shipit.github(organization:)`), each organization has its own independent `webhook_secret`. Because the org selection field (`owner.login`) and the repository-resolution field (`full_name`) are two independently attacker-controlled strings in the same JSON body that are never checked for consistency, an attacker who legitimately holds the webhook secret for *their own* configured GitHub organization (e.g., because they administer a repo that Shipit tracks under `some-org-they-control/*`) can craft a webhook payload where `owner.login`/`organization.login` = their own org (so the signature validates with their own secret) while `repository.full_name` = a *different* tracked repository belonging to another organization/team. `Handler#stacks` will resolve and mutate that other repository's stacks.

This is the same class of bug as the report: a security-relevant identity used for admission control (the priority-tree `startIndex`/organization used for signature verification) is decoupled from the data structure actually acted upon (the priority queue's `unprocessedIndex`/the `full_name`-resolved `Stack`), so a value that passes the "authorization" check does not correspond to the value that is subsequently operated on.

### Impact Explanation
This crosses the "organization authenticated versus repository that is written" trust boundary called out in the rules. An attacker who only controls one GitHub organization/app installation configured in Shipit can trigger `GithubSyncJob`/`sync_github` (and other handler side effects such as membership/team sync, PR/merge-queue state changes, or check-run refresh) on stacks belonging to a *different* organization's repository, without holding that organization's webhook secret. Depending on which handler is targeted this can affect merge-queue behavior and Continuous Delivery triggering for repositories the attacker does not own — a cross-repository write reachable purely through a webhook payload the attacker can legitimately sign.

### Likelihood Explanation
Requires: (1) a Shipit instance configured with multiple GitHub organizations (multi-org `github:` config, as explicitly documented/supported), and (2) the attacker legitimately controls a webhook secret for at least one of the configured organizations (e.g., they installed/administer the GitHub App for their own org, which Shipit also tracks). Given multi-tenant Shipit deployments are an explicitly supported configuration shape, this is a realistic scenario, though it does not apply to the common single-organization setup.

### Recommendation
Bind the verified organization to the resource being mutated: after computing `repository_owner` and verifying the signature, re-derive/validate that `payload['repository']['full_name']`'s owner segment matches the same `repository_owner` used for verification (or, more robustly, always look up the owning organization from `full_name` and verify the signature using that organization's secret, rather than trusting a separate `owner.login`/`organization.login` field). Reject the webhook if the two do not match.

### Proof of Concept
1. Configure Shipit with two organizations, `org-a` (attacker-controlled, webhook secret known to attacker) and `org-b` (victim, tracked repository `org-b/victim-repo` with a Shipit `Stack`).
2. Attacker crafts a `push` webhook JSON body with:
   - `repository.owner.login = "org-a"` (or `organization.login = "org-a"`)
   - `repository.full_name = "org-b/victim-repo"`
   - `ref`, `after` set to attacker-chosen values.
3. Attacker signs the raw body with `org-a`'s known `webhook_secret` and sets `X-Hub-Signature`.
4. `WebhooksController#verify_signature` calls `Shipit.github(organization: "org-a")` and the signature validates successfully (since `org-a`'s secret matches).
5. `Shipit::Webhooks.for_event('push')` dispatches to `PushHandler`, which calls `stacks` → `Repository.from_github_repo_name("org-b/victim-repo")`, resolving and acting on `org-b`'s stack (e.g., enqueuing `GithubSyncJob` with an attacker-chosen `expected_head_sha`), even though the attacker never held `org-b`'s webhook secret.

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
