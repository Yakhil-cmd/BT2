### Title
Improper Input Sanitization of Peer-Supplied Contract `title`/`text` Fields Rendered in Wallet Chat/Contract UI - (File: wallet.js)

### Summary
`prosaic_contract_offer`, `arbiter_contract_offer`, and `arbiter_dispute_request` device messages let an unprivileged **paired device (correspondent)** supply free-form `title` and `text` strings that `ocore` stores and re-emits verbatim on the `"text"` event, which is the exact channel the wallet UI uses to render chat/contract content to the user. Unlike sibling fields such as `wallet_name` and `cosigner.name` in `wallet_defined_by_keys.js`, which are explicitly stripped of `<`/`>` before being trusted for display, the contract `title`/`text` fields receive no such sanitization anywhere in `ocore`. This is the same bug class as OTF-001/CVE-2022-21690: attacker-controlled data reaches a client UI text-rendering surface without sanitization, allowing rich content/markup injection that can be used to spoof what the user believes they are agreeing to before authorizing a payment.

### Finding Description
In `wallet.js`, the `"text"` subject handler only strips four specific bracket-delimited markers and forwards everything else as-is for UI display: [1](#0-0) 

The `prosaic_contract_offer` handler accepts peer-controlled `title`/`text`, validates only non-emptiness/format of unrelated fields (address validity, hash, date format), stores the contract, and re-broadcasts the untouched `body` (containing the peer's `title`/`text`) as a `"text"` chat message intended for direct display: [2](#0-1) 

When a contract response arrives, the previously-received, unsanitized `objContract.title` is concatenated directly into a display string and emitted again via the `"text"` event: [3](#0-2) 

The arbiter dispute path similarly takes `contractContent.title` decrypted from an `arbiter_dispute_request` message body and forwards it for chat display without sanitization: [4](#0-3) 

`prosaic_contract.js` and `arbiter_contract.js` never sanitize `title`/`text` at creation, storage, or hashing time — they only compute/verify a hash over the raw strings: [5](#0-4) [6](#0-5) 

By contrast, other peer-supplied display strings elsewhere in the same file are explicitly sanitized against markup injection before being trusted, showing the developers are aware of this exact risk class but did not apply it consistently to contract `title`/`text`: [7](#0-6) 

The comment in `handleMessageFromHub` itself documents that this channel is meant to feed a UI rendering component: `// the wallet should have an event handler that displays the text to the user`, matching the QLabel rich-text rendering surface described in the OTF-001 report. [8](#0-7) 

### Impact Explanation
A paired correspondent device (reachable without any special privilege beyond an existing pairing, analogous to the "paired device"/"private-payment counterparty" actors explicitly in scope) can embed markup/rich-text payloads inside a contract `title` or `text` field. When rendered by the desktop wallet's chat/contract UI (the consumer of the `"text"` event and of stored `prosaic_contracts`/`wallet_arbiter_contracts` rows), this can be used to visually spoof the terms of a prosaic or arbiter contract offer — e.g., overlaying or hiding the true amount/asset/counterparty information that the victim relies on before deciding to fund a shared address or sign the mutually-signed contract unit. Because the actual payment amount, asset, and addresses are supplied and validated independently of the displayed `title`/`text` (`body.amount`, `body.asset`, `body.my_address`/`body.peer_address` in the `arbiter_contract_offer` handler), a victim deceived by the spoofed contract text can be induced to approve and fund a shared address, resulting in unauthorized/unintended spending of their funds to the attacker's contract terms.

### Likelihood Explanation
Exploitation requires only that the attacker be paired with the victim's device (a normal, low-barrier precondition for any correspondent interaction such as chat, textcoins, or contracts) and send a single crafted `prosaic_contract_offer`, `arbiter_contract_offer`, or a text message. All server-side validation in `handleMessageFromHub` focuses on structural/cryptographic correctness (hash, address validity, date format) and does not constrain the character content of `title`/`text`, so the injection reaches the display layer unmodified in every code path that stores or re-emits these fields.

### Recommendation
- Sanitize `title` and `text` fields the same way `wallet_name`/`cosigner.name` are handled in `wallet_defined_by_keys.js` — strip or HTML-escape `<`/`>` (and any other markup-significant characters) before storing/forwarding for display, in `wallet.js` (`prosaic_contract_offer`, `prosaic_contract_response`, `arbiter_contract_offer`, `arbiter_dispute_request` handlers) and in `prosaic_contract.js`/`arbiter_contract.js`.
- Alternatively/additionally, document and enforce that any consuming UI must treat these fields strictly as plain text (no rich-text/HTML interpretation) when rendering.

### Proof of Concept
1. Device A pairs with victim device B.
2. Device A sends a `prosaic_contract_offer` message where `title`/`text` contain a crafted markup payload (e.g. an embedded image/rich-text tag) instead of plain contract terms, while `my_address`/`peer_address`/`hash`/`creation_date` are made valid so the checks in `wallet.js` lines 455-480 pass.
3. `ocore` stores the contract via `prosaic_contract.store(body)` and emits the raw payload through `eventBus.emit("text", from_address, chat_message, ...)`.
4. The victim's wallet UI, consuming the `"text"` event / contract records as intended for direct display, renders the injected markup instead of plain text, allowing the attacker to visually spoof the contract's true terms and induce the victim to accept/fund a shared address under false pretenses.
