### Title
CCMenu API endpoint uses unscoped `Stack.from_param!` instead of the api-client-scoped `stacks` finder, allowing a stack-restricted token to read any stack's build status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
### Finding Description
`Shipit::Api::BaseController` implements per-token stack scoping: an `ApiClient` can be bound to a single `stack_id`, and every normal API controller resolves the target stack through `stacks.from_param!(params[:stack_id])`, where `stacks` is restricted to `Stack.where(id: current_api_client.stack_id)` whenever the token is stack-scoped. [1](#0-0) 

`Shipit::Api::CCMenuController` inherits from `BaseController` and correctly enforces `require_permission :read, :stack`, but it **overrides** the `stack` accessor with an unscoped lookup that ignores the API client's `stack_id` restriction entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
``` [2](#0-1) 

`check_permissions!` on `ApiClient` only checks whether the token has the `read:stack` permission string; it never verifies which stack the token is bound to — that binding is supposed to be enforced by the `stacks`/`stack` helper in the base controller. [3](#0-2) 

The engine even documents and exercises the intended per-stack scoping: creating a CCMenu client explicitly binds it to one stack via `ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, ...)`, and its companion `Shipit::CCMenuUrlController#stack` uses the same unscoped `Stack.from_param!`, generating a per-stack CCMenu URL/token pair meant to be handed out (e.g., embedded in CI dashboards) for a single stack. [4](#0-3) 

Because the API controller resolves `stack` from `params[:stack_id]` directly rather than from `current_api_client`-scoped `stacks`, any holder of a stack-scoped CCMenu token can simply change the `stack_id` in the URL to point at a different stack and successfully authenticate (the token is valid — it has `read:stack` permission), receiving that unrelated stack's build/deploy state.

**Binding broken (equality that should hold but doesn't):**
`stack the ApiClient token is authorized for` (`current_api_client.stack_id`) == `stack the request actually touches` (`params[:stack_id]` resolved via `Stack.from_param!`).

Before the attacker's request: token `T` is minted with `stack_id = A` (`ApiClient#stack` = Stack A).
After the attacker's request: `GET /api/stacks/:stack_id/ccmenu.xml?token=T` with `stack_id = B` succeeds and returns Stack B's data, even though `T.stack_id == A != B`.

### Impact Explanation
This is an authorization boundary crossing: a token that is only supposed to authorize read access to one stack's build state can be used to read `deploys_and_rollbacks`, last build status/label, and lock state for any other stack in the installation, including private/internal stacks whose existence and deploy history the token holder was never granted access to. Per the engine's own permission model (`ApiClient#stack_id`, `require_permission :read, :stack`), this is unauthenticated (relative to the target stack) read of stack state — matching the "High: escalation into `Shipit.github_teams` authorization... unauthenticated read of stack state, task streams or deploy output" impact class, since the token was never authorized for the target stack. CCMenu tokens are also commonly embedded in less-trusted contexts (CI dashboard widgets, badges) making leakage of a single such token plausible, after which the attacker can enumerate/read *all* stacks' build status, not just the one it was issued for.

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires the attacker to already hold one legitimately-issued, stack-scoped CCMenu API token (e.g. leaked from a CI dashboard/status badge configuration) and to know or guess another stack's `owner/repo/environment` param. No signature forgery, no privileged GitHub access, and no session is required beyond possessing that one token — the flaw is purely in the engine's authorization-scoping code path for this specific controller, which diverges from the pattern used by every other `Api::*Controller`.

### Recommendation
Make `CCMenuController#stack` (and `CCMenuUrlController#stack`) resolve through the token/user-scoped finder instead of the global `Stack.from_param!`:
```diff
 def stack
-  @stack ||= Stack.from_param!(params[:stack_id])
+  @stack ||= stacks.from_param!(params[:stack_id])
 end
```
using the same `stacks` helper defined in `Shipit::Api::BaseController` (`Stack.where(id: current_api_client.stack_id)` when scoped, `Stack.all` otherwise), so a stack-scoped token can never resolve a stack outside its authorized `stack_id`.

### Proof of Concept
1. As an authenticated Shipit user, create a stack-scoped CCMenu badge for stack `A` (`GET /stacks/A/ccmenu_url`), which mints an `ApiClient` with `permissions: ["read:stack"]` and returns a URL of the form `/api/stacks/A/ccmenu.xml?token=<T>`, where `T` authenticates a client bound to stack `A` only. [5](#0-4) 
2. Obtain token `T` (e.g., it was embedded in a public CI badge/dashboard for stack `A`).
3. As the attacker, issue `GET /api/stacks/B/ccmenu.xml?token=<T>` for an unrelated stack `B` that the attacker has no access to.
4. `authenticate_api_client` succeeds because `T` is a valid token (`ApiClient.authenticate(params[:token])`), and `require_permission :read, :stack` succeeds because the token does have the `read:stack` permission string. [6](#0-5) [7](#0-6) 
5. `stack` resolves via `Stack.from_param!(params[:stack_id])` — ignoring `current_api_client.stack_id == A` — and returns stack `B`'s deploy/build status in the XML response, which the attacker was never authorized to view. [8](#0-7)
