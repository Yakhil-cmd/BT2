### Title
Webhook signature is verified against the wrong organization's secret, letting an attacker forge cross-organization deploy-gating events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook against using `repository_owner`, computed from the attacker-controlled JSON body (`repository.owner.login` or `organization.login`), not from any value bound to the actual secret that produced the signature. The handlers that subsequently act on the payload (e.g. `StatusHandler`, `PushHandler`) key off a *different* attacker-controlled field, `repository.full_name` (or in `StatusHandler`'s case, a completely unscoped `sha`), to decide which `Stack`/`Repository`/`Commit` to mutate. In a multi-organization Shipit deployment, this breaks the binding "organization whose secret authenticated the request" = "repository/commit that gets written."

### Finding Description
`verify_signature` looks up the app config with: [2](#0-1) 
and [3](#0-2) 

`Shipit.github(organization:)` resolves a distinct `GitHubApp` instance per organization key, each with its **own independent `webhook_secret`**, as documented for the "Using Multiple Github Applications" setup: [4](#0-3) [5](#0-4) 

`verify_webhook_signature` just HMACs the raw body with that organization's secret: [6](#0-5) 

So the signature only proves "whoever crafted this exact raw body knows OrgA's secret" — it says nothing about which repository the body's other fields describe. The `create` action then dispatches the parsed payload to handlers based only on `event`, with no re-check that the acted-upon repository belongs to the organization whose secret validated the request: [7](#0-6) 

Handlers derive the target repository from a separate field, `repository.full_name`: [8](#0-7) 

`PushHandler` uses that repository-derived `stacks` scope to trigger a GitHub sync: [9](#0-8) 

`StatusHandler` is worse: it doesn't even use `repository_name`/`stacks` scoping — it matches **any** `Commit` row in the entire installation by raw `sha`, across all organizations/stacks, and directly mutates its GitHub-derived status: [1](#0-0) 

That status mutation can flip a commit from `pending`/`unknown` to `success`, which is exactly the trigger `Commit#add_status` uses to unblock deploys and schedule merges for a completely unrelated stack that the attacker has no relationship to: [10](#0-9) 

**Equality broken:** organization whose `webhook_secret` authenticated the request ≠ organization/repository/commit actually written by the dispatched handler.

### Impact Explanation
An attacker who legitimately controls (or has been granted webhook access/secret for) one configured GitHub organization ("OrgA") in a multi-org Shipit deployment can forge a webhook body whose `repository.owner.login`/`organization.login` says "OrgA" (so `verify_signature` selects OrgA's secret, which the attacker can sign with) while its `sha`/`repository.full_name` targets a commit/stack belonging to a completely different, victim organization ("OrgB") that the attacker has no access to. This lets the attacker:
- Force a fabricated `success` status onto an arbitrary commit sha in OrgB's stacks, unblocking `deployable?`/`schedule_merges` and enabling an unauthorized deploy or merge (`StatusHandler`).
- Trigger a `GithubSyncJob`/`sync_github` against an arbitrary OrgB stack (`PushHandler`).

This crosses an organizational trust boundary that the multi-org webhook secret feature is specifically meant to enforce, resulting in an unauthorized deploy/merge path — matching the Critical impact bar ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires only that the deployment uses (or will use) the documented multi-organization `github:` secrets configuration and that the attacker is a legitimate webhook sender for at least one configured organization (e.g. controls a repo under that org, or that org's secret has otherwise leaked/been shared) — no privileged Shipit account, GitHub App private key, or `api_clients_secret` is needed. The `sha`-only global lookup in `StatusHandler` requires no knowledge of internal IDs, just a commit sha that exists in the target stack's history (easily discoverable from the public/target repo's commit history).

### Recommendation
- After signature verification succeeds for organization `X`, re-derive the organization from `repository.full_name`/`repository.owner.login` used by the handler and reject the request (or re-verify) if it does not match the organization `X` that authenticated the request.
- Scope `StatusHandler#process` (and any other handler) to commits belonging to the verified organization's repositories/stacks instead of a global `Commit.where(sha:)` lookup.

### Proof of Concept
1. Configure Shipit with two organizations, `OrgA` and `OrgB`, each with its own `webhook_secret` (per `docs/setup.md`'s multi-app schema).
2. As an attacker who is a legitimate GitHub App/webhook sender for `OrgA` only, craft a `status` event body:
```json
{
  "sha": "<sha-of-a-commit-in-an-OrgB-stack>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgA/anything" }
}
```
3. Sign the exact raw body with OrgA's `webhook_secret` (`sha1=` HMAC) and POST it to `/github/webhooks` with header `X-Github-Event: status`.
4. `verify_signature` resolves `Shipit.github(organization: 'OrgA')` and validates successfully since the attacker knows OrgA's secret and signed this exact body.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the OrgB commit (no organization scoping), and calls `create_status_from_github!`, potentially flipping status to `success` and triggering `deployable_status`/merge scheduling for OrgB's stack — despite the attacker never having any relationship to OrgB.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
