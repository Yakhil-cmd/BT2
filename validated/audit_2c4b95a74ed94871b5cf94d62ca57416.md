### Title
Reward accrual permanently rounds to zero and is lost in `pallet-asset-rewards` due to undersized `PRECISION_SCALING_FACTOR` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes `reward_per_token` using integer division scaled by a fixed constant `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) . This is structurally the same rounding-to-zero pattern as the reported `FarmKeeper` bug (SCALE_FACTOR too small relative to the divisor), except the scaling factor here (4096 ≈ 2^12) is even smaller than the reported contract's flawed `1e12`, and any signed staker (no privileged role) can force the update path (`stake`/`unstake`/`harvest_rewards`) to run frequently, truncating the per-block reward accrual to zero and permanently losing it.

### Finding Description
`reward_per_token` accrues rewards per staked token as:

```
reward_per_token_stored += reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked
``` [2](#0-1) 

and a staker's owed reward is later derived as:

```
reward = staker.amount * (reward_per_token - reward_per_token_paid) / PRECISION_SCALING_FACTOR + staker.rewards
``` [3](#0-2) 

Every operation that touches a pool (`stake`, `unstake`, `harvest_rewards`) unconditionally calls `update_pool_and_staker_rewards`, which calls `reward_per_token` and immediately commits `last_update_block = now` and `reward_per_token_stored = reward_per_token` via `update_pool_rewards` [4](#0-3) . Any signed account can call `stake`/`unstake` on any pool [5](#0-4) , and once the pool is expired anyone can call `harvest_rewards` for any staker [6](#0-5) , each triggering an update.

Because the numerator (`reward_rate_per_block * blocks_elapsed * 4096`) is not carried over between updates — only the final `reward_per_token_stored` (already divided) is persisted — if `total_tokens_staked` is large relative to `reward_rate_per_block * blocks_elapsed * 4096`, the division truncates to `0` and that whole increment of reward is permanently discarded; it is never recovered on a later call because `last_update_block` has already advanced. This is the exact same root cause described in the report: an accumulator-per-share pattern where a too-small scaling constant causes integer-division truncation to `0`, and the loss is irreversible once the "last update" checkpoint moves forward. In the report this is exploited by anyone calling `updateFarm` frequently; here it is anyone calling `stake`/`unstake` frequently (each of which is a permissionless, fee-paying but otherwise unprivileged extrinsic) to force many small-window updates, each rounding to zero.

Unlike `pallet-nomination-pools`, which uses a `FixedU128`-based `RewardCounter` (effectively `1e18` precision) and is explicitly documented as safe against this collapse [7](#0-6) , `pallet-asset-rewards` uses a bare `u16` constant of `4096`, which offers only ~12 bits of extra precision — far less headroom than even the flawed `1e12` in the reported contract.

### Impact Explanation
When `total_tokens_staked` is large relative to `reward_rate_per_block` (e.g., a staking asset with many decimals and a modest reward rate, or simply high total value staked), per-block reward accrual rounds down to zero and is permanently lost rather than merely deferred, because the checkpoint (`last_update_block`)/(`reward_per_token_stored`) advances regardless. Stakers receive fewer rewards than the pool's configured `reward_rate_per_block` promises, and the reward pot funds effectively become unclaimable/stuck for those rounded increments. This matches a High-severity "loss of funds due to rounding" classification per the reference report, scaled to the affected pool's size and duration.

### Likelihood Explanation
Reachability requires no privileged role — pool creation is gated by `CreatePoolOrigin`, but staking, unstaking, and harvesting (the operations that trigger the vulnerable update path) are open to any signed account [8](#0-7) [9](#0-8) . Any staker (or a third party frequently unstaking/staking trivial dust amounts, or repeatedly harvesting after expiry) can force many short update windows, each of which is more likely to round to zero given the small `4096` factor. Likelihood is Medium: it depends on the specific `reward_rate_per_block` / `total_tokens_staked` ratio chosen by the (trusted) pool admin, so not every pool is affected, but for any pool with a modest reward rate and substantial staked value it is easily triggered by ordinary user activity, not just adversarial abuse.

### Recommendation
Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to `1e18`/`FixedU128`-scale precision as used in `pallet-nomination-pools`'s `RewardCounter`), and/or track the un-divided remainder across updates so that small increments accumulate instead of being discarded whenever `update_pool_rewards` commits a checkpoint.
