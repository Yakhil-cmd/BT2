### Title
CCMenuController#stack bypasses ApiClient stack_id scoping, allowing cross-stack/cross-tenant cc.xml disclosure - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`Shipit::Api::BaseController#stacks` restricts stack access to `current_api_client.stack_id` when the token is scoped to a single stack, but `Shipit::Api::CCMenuController` overrides `#stack` to bypass that scope entirely and resolve any stack via `Stack.from_param!`. A token that is restricted (via `ApiClient#stack_id`) to one stack and holds only `read:stack` can request `cc.xml` for an arbitrary, unrelated stack and receive its latest deploy/rollback commit sha, branch, and URL.

### Finding Description
The binding that should hold is: `current_api_client.stack_id == stack.id` (or `current_api_client.stack_id?` is false, i.e. unrestricted) for any stack resolved for a request authenticated by that token.

In the base controller, this binding is enforced through the `stacks` scope: [1](#0-0) 
`stacks` restricts the queryable set to `Stack.where(id: current_api_client.stack_id)` when the token is stack-scoped, and `#stack` resolves `stacks.from_param!(params[:stack_id])`.

`CCMenuController`, however, redefines `#stack` to skip the `stacks` scope entirely: [2](#0-1) 
This calls `Stack.from_param!(params[:stack_id])` directly on the unscoped `Stack` relation, so any stack in the entire installation can be resolved regardless of the token's `stack_id` restriction.

`require_permission :read, :stack` only checks that the string `"read:stack"` is present in `current_api_client.permissions`: [3](#0-2) 
It performs no comparison against `stack_id` or the resolved stack's identity — this is a scope-string check only, not a resource-ownership check. `require_permission!` in the base controller simply delegates to this same string check: [4](#0-3) 

Exploit flow: attacker holds (or is issued, e.g. as a restricted per-tenant integration token) an `ApiClient` with `permissions = ['read:stack']` and `stack_id` set to their own stack. They send `GET /api/1/stacks/:organization/:repository/:branch/cc.xml?token=<their_token>` (or via Basic auth) with `stack_id` params pointing at a stack belonging to a different, unrelated org. `authenticate_api_client` succeeds (valid token), `require_permission!(:read, :stack)` passes (permission string present), and `#stack` resolves the foreign stack unscoped, rendering its latest deploy/rollback commit sha, branch, and status in the `cc.xml` response — none of `verify_signature`, `force_github_authentication`, or any stack-ownership check intervenes because this is a token-authenticated API path, not the webhook or session path.

### Impact Explanation
An authenticated but resource-restricted API token can read cross-tenant/cross-repository deploy state (commit SHA, branch, deploy timestamp/status) for any stack in the Shipit instance, not just the one it was provisioned for. This is an authorization scope bypass that discloses deploy state belonging to a different repository/organization than the one bound to the token, matching the "unauthenticated/unauthorized read of stack state" High-severity bucket. It is repeatable against any stack ID in the installation, is not limited to a single request, and requires no additional privilege beyond possessing one (arbitrarily-restricted) `read:stack` token — the blast radius covers every stack hosted by the Shipit instance.

### Likelihood Explanation
Requires a multi-tenant/multi-org Shipit deployment where different `ApiClient` tokens are scoped to different stacks via `stack_id` — a supported and documented configuration (`ApiClient#stack_id`, `stacks` scoping in `BaseController`). The attacker needs only a valid, restricted token (their own legitimately issued low-privilege token) and knowledge/guessability of another stack's `params[:stack_id]` (organization/repo/branch slug), which is often predictable or discoverable. No secrets, sessions, or elevated roles are needed beyond the token itself; the divergence from the base controller's scoping is a straightforward, always-reachable code path (every `CCMenuController#show` request hits the overridden `#stack`).

### Recommendation
Remove the overriding `#stack` method in `CCMenuController` (or reimplement it using `stacks.from_param!` exactly as the base controller does) so that stack resolution is always scoped through `current_api_client.stack_id` when present, consistent with every other API controller.

### Proof of Concept
Minitest (integration/controller test) plan under `test/controllers/shipit/api/ccmenu_controller_test.rb`:
1. Create two `Stack` records under two different `Repository` owners, e.g. `stack_a` (owner "org-a") and `stack_b` (owner "org-b"), each with a `Deploy` having a distinct `sha`/branch.
2. Create an `ApiClient` `token_a` with `permissions: ['read:stack']` and `stack_id: stack_a.id`.
3. Assert binding before: `token_a.stack_id == stack_a.id` and `token_a.stack_id != stack_b.id`.
4. Send `GET /api/1/stacks/org-b/repo-b/master/cc.xml?token=<token_a.authentication_token>`.
5. Assert response status is `200` (not `403`/`404`) and response body contains `stack_b`'s deploy `sha`/branch, e.g. `assert_includes response.body, stack_b.deploys.last.sha`.
6. This demonstrates the binding is violated: a token scoped to `stack_a` successfully reads `stack_b`'s deploy state, proving the cross-tenant leak via `CCMenuController#stack` bypassing `BaseController#stacks`.
