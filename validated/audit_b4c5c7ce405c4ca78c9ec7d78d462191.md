### Title
Null pointer dereference in asset payment validation via unchecked `payload.inputs[0]` - (File: validation.js)

### Summary
`validatePayment()` in `validation.js` dereferences `payload.inputs[0].type` without first verifying that `payload.inputs[0]` is a non-null object, unlike the sibling per-input validation loop in `validatePaymentInputsAndOutputs()` which does perform this check. Any unprivileged unit poster can craft an asset-payment message whose first input is `null` (or another non-object JSON value) to trigger an uncaught `TypeError` deep inside the async validation callback chain, matching the CVE-2021-26948 bug class (null pointer dereference on a crafted/malformed input causing a crash).

### Finding Description
`validatePayment()` first checks that `payload.inputs` is a non-empty array with `isNonemptyArray(payload.inputs)`: [1](#0-0) 

This check only validates array-ness and length — it does not validate that each element (or even `inputs[0]`) is a non-empty object. For asset (non-base) payments, after the asynchronous asset lookup completes, the code directly accesses `.type` on the first input: [2](#0-1) 

`payload.inputs[0].type` at line 2099 will throw `TypeError: Cannot read properties of null (reading 'type')` if `payload.inputs[0]` is `null`. This is reachable because a unit's JSON payload can legally contain `null` as an array element — nothing in `isObjectWellFormed`, `isTooDeeplyNestedOrHasTooManyNodes`, or the earlier `isNonemptyArray` check filters out `null` elements.

By contrast, the later per-input validation loop in `validatePaymentInputsAndOutputs()` correctly guards against this by checking `isNonemptyObject(input)` before accessing any of its fields: [3](#0-2) 

The vulnerable code path in `validatePayment()` (lines 2078–2099) is only exercised for asset payments (i.e., payload has an `asset` field), and it runs *before* the safe per-input loop, so the crash occurs prior to reaching the code that would otherwise reject the malformed input.

### Impact Explanation
The dereference occurs inside the asynchronous callback of `storage.loadAssetWithListOfAttestedAuthors`, deep in the unit validation pipeline (`validation.js`'s `validate()` → `validateMessages()` → `validateInlinePayload()` → `validatePayment()`). There is no local `try/catch` around this callback, so a thrown `TypeError` becomes an uncaught exception in that async execution context. Because every full node (and light node validating a directly-relevant unit) must run this exact validation code against every incoming unit, a single crafted unit containing `payload.asset` set to any existing valid asset and `payload.inputs: [null, ...]` can crash or otherwise abort validation on every node that processes it. Since block/DAG progress in Obyte depends on nodes being able to validate and confirm new units, a bug that reliably crashes/aborts validation for a specific crafted (but otherwise conformant) unit can be used to disrupt a node's ability to process new units, which aligns with the "network unable to confirm new units" impact category. Whether this ultimately terminates the Node.js process versus leaving it in an inconsistent state (e.g., an unreleased DB connection/transaction from `storage.loadAssetWithListOfAttestedAuthors`) depends on whether an upstream `uncaughtException`/`unhandledRejection` handler is registered in the process running validation; I found `uncaughtException` handling only in `network.js`, and I could not fully verify at this iteration limit whether it wraps this exact code path, so the precise crash-vs-hang behavior is not fully confirmed.

### Likelihood Explanation
High. Triggering the bug requires only:
1. An existing valid asset definition (assets can be freely defined by any user via an `asset` message), and
2. Posting a unit with a `payment` message referencing that asset where `payload.inputs[0]` is `null`.

No special privileges, signatures beyond normal unit composition, or race conditions are required — this is reachable by any unprivileged unit poster.

### Recommendation
Add an explicit object-type/non-null check on `payload.inputs[0]` (and ideally all elements) in `validatePayment()` before accessing any of its properties, mirroring the `isNonemptyObject(input)` guard already present in `validatePaymentInputsAndOutputs()`. For example, insert `if (!isNonemptyObject(payload.inputs[0])) return callback("input must be a non-empty object");` immediately after the `isNonemptyArray(payload.inputs)` check (or right before line 2099), and audit other early destructive property accesses on unvalidated array elements throughout `validation.js` for the same pattern.

### Proof of Concept
1. Define (or use an existing) public asset `A` via a normal `asset` message from any address.
2. Compose and broadcast a unit containing a `payment` message such as:
```json
{
  "app": "payment",
  "payload": {
    "asset": "<A_asset_hash>",
    "inputs": [null],
    "outputs": [{"address": "SOME_VALID_ADDRESS", "amount": 1}]
  }
}
```
3. Submit this unit to a full node for validation. When `validatePayment()` reaches `var bIssue = (payload.inputs[0].type === "issue");` [4](#0-3) , it throws `TypeError: Cannot read properties of null (reading 'type')`, an uncaught exception inside the asynchronous validation callback, corrupting or terminating that node's validation of the unit.
