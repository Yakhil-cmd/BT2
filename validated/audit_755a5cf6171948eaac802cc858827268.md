### Title
Textcoin mnemonics (bearer spending secrets) are stored in plaintext and re-exposed via wallet transaction history - ([File: wallet.js])

### Summary
`sendMultiPayment()` in `wallet.js` generates a BIP39 mnemonic for each textcoin recipient and inserts it in plaintext into the `sent_mnemonics` table via the `preCommitCb` callback. [1](#0-0) 
That mnemonic is a bearer credential: anyone who knows it can derive the same private key (`m/44'/0'/0'/0/0`) and spend the textcoin, as done in `expandMnemonic()`/`receiveTextCoin()`. [2](#0-1) 
`readTransactionHistory()` subsequently joins `outputs` with `sent_mnemonics` and returns the plaintext `mnemonic` field directly on the `transaction` object for any "sent" movement, regardless of whether the caller is the original sender or just someone who can request the wallet/address history. [3](#0-2) 

### Finding Description
This mirrors the CVE-2019-1003039 bug class: a secret intended to be protected/limited-access (Jenkins job password / here, the textcoin spending mnemonic) is persisted unencrypted and then handed back out through a normal, low-privilege read path (job config view / here, wallet history read) without any authorization check tying the requester to the original credential owner.

`sent_mnemonics.mnemonic` is a full BIP39 mnemonic which is the literal private-key seed for the textcoin's temporary "sig" address; the address definition and pubkey are derived directly from it (`objectHash.getChash160(["sig", {"pubkey": pubkey}])`), so knowledge of the mnemonic is equivalent to knowledge of the spending key. [4](#0-3) 
The value is stored in cleartext in the database schema (`sent_mnemonics.mnemonic VARCHAR(107) ... NOT NULL`) with no encryption or hashing. [5](#0-4) 
The only "protection" mechanism that exists (`eraseTextcoin()`, which blanks the mnemonic column once it's presumed no longer needed) is invoked ad hoc elsewhere and is not enforced before `readTransactionHistory()` serves the row, so a caller of transaction history can retrieve the unredacted mnemonic for any not-yet-cleared row that matches the address/wallet filter used in the query. [6](#0-5) 

### Impact Explanation
If `readTransactionHistory()` (or any UI/RPC surface built on top of it, e.g. wallet apps or bots exposing history to counterparties/shared-address co-signers) returns rows for a wallet/address that isn't exclusively controlled by the caller — for instance a shared address, a multi-device wallet, or any interface that lets a less-trusted party query the history of an address they only partially control or observe — the plaintext mnemonic for a still-unclaimed textcoin is disclosed. Whoever obtains it can call `receiveTextCoin()` and steal the underlying funds before the intended recipient claims them, i.e. concrete unauthorized spending of value that the original sender still expects to be recoverable/claimable by the intended party (or by themselves via `claimBackOldTextcoins`). [7](#0-6) 

### Likelihood Explanation
The exposure is unconditional for any `sent` transaction of textcoin type as long as `sent_mnemonics.mnemonic` has not been erased: `readTransactionHistory()` performs a plain `LEFT JOIN sent_mnemonics USING(unit)` and copies `payee.mnemonic` onto the returned transaction with no permission check beyond the wallet/address filter already used for history retrieval. [8](#0-7) 
Any code path that surfaces wallet or shared-address transaction history to a party other than the funder (co-signers on a shared address, companion apps, support/monitoring tooling) reproduces the credential-leak pattern from the CVE.

### Recommendation
- Never include the raw `mnemonic` field in `readTransactionHistory()` output; instead return only a boolean `hasMnemonic`/`claimed` indicator, or require the caller to explicitly and separately request the mnemonic through a dedicated, strongly-authorized API limited to the wallet owner's own device.
- Erase or encrypt-at-rest the mnemonic in `sent_mnemonics` immediately after the payment notification is sent (rather than only via the best-effort `eraseTextcoin()` called from unrelated flows), and gate its retrieval on device-level authentication and address ownership.

### Proof of Concept
1. Send a textcoin payment (`sendMultiPayment` with an email/text recipient), which creates a `sent_mnemonics` row containing the plaintext mnemonic and a corresponding output at `assocAddresses[to]`.
2. Any process/party able to invoke `readTransactionHistory({wallet: <wallet_or_address>, ...})` for the paying wallet/address (e.g. a co-signer on a shared paying address, or any component the sender's client exposes wallet history to) receives a transaction record where `transaction.mnemonic` equals the plaintext mnemonic for the still-unclaimed textcoin. [9](#0-8) 
3. That party calls `receiveTextCoin(mnemonic, their_own_address, ...)` before the intended recipient claims it, deriving the same private key and diverting the funds to themselves. [10](#0-9)

function expandMnemonic(mnemonic) {
	var addrInfo = {};
	mnemonic = mnemonic.toLowerCase().split('-').join(' ');
	if ((mnemonic.split(' ').length % 3 !== 0) || !Mnemonic.isValid(mnemonic)) {
		throw new Error("invalid mnemonic: "+mnemonic);
	}
	mnemonic = new Mnemonic(mnemonic);
	addrInfo.xPrivKey = mnemonic.toHDPrivateKey().derive("m/44'/0'/0'/0/0");
	addrInfo.pubkey = addrInfo.xPrivKey.publicKey.toBuffer().toString("base64");
	addrInfo.definition = ["sig", {"pubkey": addrInfo.pubkey}];
	addrInfo.address = objectHash.getChash160(addrInfo.definition);
	return addrInfo;
}

function claimBackOldTextcoins(to_address, days){
	if (typeof days !== 'number')
		throw Error("bad days: " + days);
	db.query(
		"SELECT mnemonic FROM sent_mnemonics LEFT JOIN unit_authors USING(address) \n\
