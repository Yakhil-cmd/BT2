### Title
Capped-asset issuance cap can be bypassed by multiple issuer addresses, allowing unlimited supply inflation - (File: validation.js)

### Summary
The reported Nova bug is a case where a resource limit (quota) is checked with an incomplete set of state conditions, letting an authenticated user exploit an alternate state path (rescue → suspend → error → delete) to bypass the cap. In ocore, an analogous incomplete-check pattern exists in the validation of `issue` inputs for **capped assets**: the double-spend/uniqueness key used to prevent re-issuance of a capped asset optionally includes the issuer `address`, which means the "cap has already been issued" protection is only enforced *per address*, not globally for the asset. Any address can independently post a unit that issues the full `cap` amount of such an asset, so the cap can be multiplied by the number of distinct issuer addresses that choose to issue.

### Finding Description
When an asset is defined with a `cap` (fixed maximum supply) and `issued_by_definer_only` is not `true`, `validatePaymentInputsAndOutputs` in `validation.js` forces `serial_number` to `1` for any issue input of a capped asset: [1](#0-0) 

It also requires that the issued amount exactly equal `cap`: [2](#0-1) 

The uniqueness constraint that is supposed to prevent the same capped issuance from happening twice is built as a double-spend key `type='issue' AND denomination=? [AND serial_number=?] [AND address=?]`, where the `address` clause is added **only when the asset is not `issued_by_definer_only`**: [3](#0-2) 

This key is enforced through the generic double-spend/uniqueness machinery (`checkInputDoubleSpend` → `checkForDoublespends`), and ultimately through the DB `UNIQUE KEY byAssetDenominationSerialAddress(asset, denomination, serial_number, address, is_unique)`: [4](#0-3) 

Because `address` is part of the uniqueness tuple whenever `issued_by_definer_only` is false, the constraint only prevents the *same* address from issuing the capped asset twice (`serial_number` is always 1). It does **not** prevent a *different* address from independently posting its own `issue` input for the same `asset`, `denomination=1`, `serial_number=1`, with `amount === cap`. Nothing elsewhere in `validatePayment`/`validatePaymentInputsAndOutputs`/`writer.js` sums total issued amounts across addresses and rejects issuance once the aggregate reaches `cap` — the only "already issued" guard is this address-scoped uniqueness key.

`validateAssetDefinition` (both for ordinary units and for AA-defined assets in `aa_validation.js`) does not require `issued_by_definer_only=true` whenever `cap` is set: [5](#0-4) [6](#0-5) 

So a capped, non-definer-restricted asset is a fully valid, reachable configuration. Any unprivileged unit poster who is an author of a unit can supply their own `address` in the issue input (multi-authored units allow an explicit `address` field per [7](#0-6) ), letting an unlimited number of distinct addresses each mint the entire `cap` amount of the asset. This mirrors the Nova class of bug: a limit/quota ("only one issuance up to cap") is enforced through a check that is scoped too narrowly (per-VM-state in Nova; per-address here), letting the actor sidestep it by using an alternate identity/state path rather than by breaking cryptography or double-spending the *same* record.

### Impact Explanation
This is a direct supply-inflation vulnerability for any capped asset that is not restricted to `issued_by_definer_only`. The asset's advertised fixed cap is not actually enforced network-wide; it is only guaranteed per issuer address. An attacker (or several colluding addresses) can multiply the effective total supply of the asset by the number of distinct addresses they use to issue, undermining any economic assumption (e.g., scarcity-based pricing, backing ratios in AAs that trust `cap` as the total supply) built on top of that asset. This satisfies the "concrete... supply inflation" bar required by the validation rules.

### Likelihood Explanation
The action requires only composing and posting a normal `payment` message with an `issue` input referencing a capped, non-definer-restricted asset and a valid address of the attacker's choosing (multi-authored unit, or single-authored unit where `address` is implicit). No special privileges, hub/peer/network compromise, or key leakage are needed — it is directly reachable by any unprivileged unit poster who knows the `asset` id (public information once the asset is defined) and satisfies normal amount/denomination checks. The precondition (asset defined with `cap` set and `issued_by_definer_only` not `true`) depends on how the asset was defined; it is a legitimate, uncommon but valid configuration that this codebase permits without restriction.

### Recommendation
For assets where `cap` is set, either:
1. Require `issued_by_definer_only=true` whenever `cap` is set (enforced in `validateAssetDefinition` and `aa_validation.js`'s asset-message validation), so only a single, fixed issuer can ever mint the capped supply; or
2. If multi-address issuance of a capped asset must remain supported, change the uniqueness/double-spend key for capped-asset issues to be scoped by `(asset, denomination, serial_number)` only (drop `address` from the key in `validation.js`'s `doubleSpendWhere` construction around lines 2366-2373), so that only one issuance of the capped amount can ever succeed for the asset regardless of which address attempts it.

### Proof of Concept
1. Define (or have an AA define) an asset with `cap = 1_000_000`, `fixed_denominations=false`, and `issued_by_definer_only=false`.
2. Address A posts a unit with a `payment` message for this asset containing an `issue` input `{type:"issue", amount:1000000, serial_number:1, address:"ADDR_A"}` and an output to itself. This validates and is saved (no prior issue exists for `address=ADDR_A`).
3. Address B (any other address, not the definer) posts a separate unit with a `payment` message for the same asset containing an `issue` input `{type:"issue", amount:1000000, serial_number:1, address:"ADDR_B"}`. Because the double-spend/uniqueness key includes `address`, this does not collide with A's issuance key `(asset, denom=1, serial=1, ADDR_A)`; it succeeds independently, minting another 1,000,000 units.
4. Repeat with addresses C, D, … — each successfully mints another full `cap` amount, so total circulating supply becomes `cap × N` for `N` distinct issuer addresses, contradicting the asset's declared fixed cap.
