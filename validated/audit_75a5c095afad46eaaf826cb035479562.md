### Title
Asset Definer Can Front-Run and Invalidate Pending Spender-Attested Payments by Rewriting the Attestor List - (File: `validation.js`)

### Summary
For assets with `spender_attested: true`, the definer can post an `asset_attestors` message at any time to replace the list of trusted attestors [1](#0-0) . Payment validation always re-resolves attestation against the attestor list and attestations that are stable as of the payment's `last_ball_mci`, evaluated at write/validation time rather than at the time the spender composed the transaction [2](#0-1) [3](#0-2) . A malicious or compromised definer who observes a spender's in-flight payment can front-run it with an `asset_attestors` update that drops the attesting authority the spender relied on, causing the previously-valid payment to become invalid ("none of the authors is attested") once it reaches finality.

### Finding Description
`readAsset` in `storage.js` resolves `arrAttestorAddresses` by picking "the latest list of attestors" stable and sequenced-good as of `last_ball_mci` [4](#0-3) . `filterAttestedAddresses` then intersects the spender's addresses against attestations issued by whichever attestor set that resolves to [5](#0-4) . `validatePayment` rejects the payment outright if none of the authoring addresses are attested under that (possibly just-changed) attestor set [3](#0-2) .

Crucially, `validateAttestorListUpdate` places no restriction on when or how often the definer may change attestors — only that the message is single-authored by the definer and the new list passes `checkAttestorList` [1](#0-0) . Since the spender has no way to "pin" the attestor list or attestation state that applied when they built their payment (there is no analog to `expectedPaymentToken`/`maxTotal` guarding the condition actually used at inclusion time), a definer who spots a valid spender-attested payment in the network before it stabilizes can broadcast a conflicting `asset_attestors` unit that removes the attestor who vouched for the spender. If that unit gets included with an earlier position in validation ordering (definer controls timing of their own unit), the spender's pending payment fails at validation/inclusion with "none of the authors is attested" even though it was fully valid and properly signed at composition time.

### Impact Explanation
This lets a single privileged party (the asset definer) unilaterally invalidate a payment made by any other party for a `spender_attested` asset after the fact, without needing to compromise the spender's keys or double-spend inputs. This is a form of griefing/fund-freezing: the spender's inputs remain locked in a payment attempt that cannot land, they lose the network fees spent building/broadcasting the transaction, and legitimate business flows relying on stable attestation (e.g., KYC-gated tokens) can be selectively sabotaged for specific counterparties at will, entirely under control of the definer address.

### Likelihood Explanation
Likelihood is High for any asset that sets `spender_attested: true`: the `asset_attestors` message is always available to the definer with no cooldown, quorum, or timelock, and the check that gates payment validity is always re-evaluated against the attestor list current at validation time rather than at composition time [6](#0-5) . A definer monitoring the network for a specific spender's payment (or attestor's revocation) can act immediately.

### Recommendation
Give payments referencing a `spender_attested` asset a way to bind to the attestor-list state (or a specific attestation) as of the time the payment was composed, and fail validation only if that pinned state was itself invalid — mirroring the `expectedPaymentToken`/`maxTotal` pattern from the report (i.e., let the spending unit assert the expected attestor set/attestation it relied upon and revert only if that specific expectation was never true, not merely because the definer later revoked it).

### Proof of Concept
1. Definer issues asset `A` with `spender_attested: true` and attestor set `{X}` [7](#0-6) .
2. Attestor `X` attests Alice's address.
3. Alice composes and broadcasts a payment spending asset `A`, valid because she is attested by `X`.
4. Definer observes Alice's pending unit and immediately broadcasts an `asset_attestors` message removing `X` from the attestor list [1](#0-0) .
5. When Alice's payment unit is (re-)validated/written, `storage.readAsset`/`filterAttestedAddresses` resolves the now-updated attestor list, Alice is no longer attested, and `validatePayment` returns `"none of the authors is attested"` [3](#0-2) , causing Alice's otherwise-correct transaction to be rejected/frozen at the definer's discretion.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}
