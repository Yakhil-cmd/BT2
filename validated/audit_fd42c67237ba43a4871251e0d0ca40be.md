### Title
Unguarded subtraction in treasury-fee mint calculation can permanently freeze vault accrual for all depositors and borrowers - (File: mainnet/contracts/vault/v0-vault-stx.clar, v0-vault-sbtc.clar, v0-vault-ststx.clar, v0-vault-ststxbtc.clar, v0-vault-usdc.clar, v0-vault-usdh.clar)

### Summary
Every ERC4626-style vault contract computes the DAO treasury's LP-share mint amount by dividing `reserve-inc` (the reserve-factor cut of newly accrued interest) by `(total-assets-preview) - reserve-inc)` with no check that the subtrahend does not exceed the minuend, and no check that the resulting divisor is non-zero. This mirrors the M03 class of bug (`wdiv`/division helper accepting an unchecked divisor): here the divisor to `mul-div-down` can be driven to zero (direct division-by-zero abort) or the preceding subtraction can underflow (Clarity uint underflow abort), either of which aborts the enclosing transaction. Because this calculation is embedded inside `accrue`, which every `deposit`, `redeem`, `system-borrow`, and `system-repay` call must execute first, a single transaction that lands in this state permanently bricks the vault for every other depositor and borrower, not just the caller.

and the public `accrue` entrypoint performs the identical unguarded computation inline before minting treasury shares: [2](#0-1) 

`reserve-inc` is `debt-delta * fee-reserve / BPS`, where `debt-delta` is the interest accrued over the elapsed `time-delta` since `last-update`: [3](#0-2) 

`total-assets-preview` is `current-assets + max(debt-preview - borrowed, 0)`: [4](#0-3) 

If the vault is driven to near-full utilization (`current-assets` ≈ 0, which is a normal, permissionless state reachable via `system-borrow` up to `cap-debt`) and `accrue` is left uncalled for a long interval so that a large `time-delta` accumulates, `debt-delta` (the interest step computed from the index) can be comparable to or larger than the cumulative `total-assets-preview` value used in the reserve split, because the two quantities are computed via different bases (`old-debt`/`new-debt` from the interest index vs. `debt-preview - borrowed`). Once `reserve-inc >= total-assets-preview`, the subtraction `(- (total-assets-preview) reserve-inc)` underflows a `uint` (Clarity aborts) or, if exactly equal, yields `0` (division by zero in `mul-div-down`). Either way, the whole calling transaction reverts, and — critically — because the transaction aborts, `index`/`lindex`/`last-update` are never persisted, so the very same unsafe state is recomputed identically on the next call. `accrue` therefore reverts forever afterward, for every account, including any user attempting `deposit`, `redeem`, `system-borrow`, or `system-repay` since all of them call `accrue` first: [5](#0-4) 

No divisor/subtraction guard exists anywhere along this path, unlike the sibling helpers `calc-utilization`/`convert-to-shares-preview`/`convert-to-assets-preview` which explicitly special-case a zero denominator: [6](#0-5) 

### Impact Explanation
Once triggered, every other depositor's and borrower's funds in that vault become permanently locked: `deposit`, `redeem`, `system-borrow`, and `system-repay` all call `accrue` unconditionally, and `accrue` will keep reverting on the frozen `last-update`/index state. This is a permanent freezing of funds for all unprivileged users of the vault — an outcome caused by one caller's transaction (whoever happens to trigger the unsafe accrual step) harming every other depositor/borrower who shares the same vault index/state, satisfying the "shared index...primed by one caller and consumed by another" analog class.

### Likelihood Explanation
Triggering requires (a) the vault reaching high utilization (`current-assets` near zero), which is an ordinary, permissionless state reachable by any borrower maximizing `system-borrow` up to `cap-debt`, and (b) `accrue` going uncalled for a sufficiently long interval so the single-step `debt-delta` grows large relative to `total-assets-preview`. Both conditions are achievable without any privileged action or oracle manipulation, though the precise numeric window depends on interest-rate curve parameters and `fee-reserve`, so likelihood is best characterized as low-to-moderate and highly parameter-dependent; I was not able to fully verify with concrete numeric bounds whether typical `fee-reserve`/rate-curve settings make this reachable in practice, given the tools available.

### Recommendation
Guard the treasury-fee computation the same way `calc-utilization`/`convert-to-*-preview` already guard their denominators: clamp `reserve-inc` to `min(reserve-inc, total-assets-preview)` before subtracting, and short-circuit to `u0` treasury-lp mint whenever `total-assets-preview <= reserve-inc`, in both `calc-treasury-lp-preview` and the inline copy inside `accrue`, across all six vault contracts.

### Proof of Concept
1. Attacker (or any borrower) calls `system-borrow` repeatedly until `current-assets` (vault's `assets` var) is driven to (near) zero, at or under `cap-debt`.
2. No one calls any vault function (so `accrue`/`last-update` is not refreshed) for a long enough period that the interest-rate curve produces a large `time-delta`-driven `debt-delta` in `next-index`.
3. Any user then calls `deposit`, `redeem`, `system-borrow`, or `system-repay`, which invokes `accrue`; `accrue` computes `reserve-inc` and `total-assets-preview` such that `reserve-inc >= total-assets-preview`, causing the subtraction/division in the `treasury-lp` computation to abort the transaction.
4. Because `index`/`lindex`/`last-update` were never persisted (the tx reverted), the identical unsafe state is reproduced on every subsequent call — `accrue`, and therefore every user-facing vault function, permanently reverts, freezing all depositors' and borrowers' funds in that vault.
