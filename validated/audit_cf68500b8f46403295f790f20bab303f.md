### Title
`ReopenedHandler#unarchive?` operator-precedence bug bypasses `review_stacks_enabled`, allowing attacker-controlled `shipit.yml` `machine.environment` to reach `Command#unbundled_env` / `PTY.spawn` - (File: app/models/shipit/webhooks/handlers/pull_request/reopened_handler.rb)

### Summary
`ReopenedHandler#unarchive?` mixes `&&`/`||` without parentheses so that `repository.review_stacks_enabled` only gates the `allow_all` branch of the OR chain, not the `allow_with_label`/`prevent_with_label` branches. When a maintainer disables review stacks but leaves `provisioning_behavior` at `allow_with_label` or `prevent_with_label` (an independently-toggleable setting on the same form), any PR author can still trigger `stack.unarchive!` → `ReviewStackProvisioningQueue.add` → provisioning, which ultimately runs `TaskCommands#env` merging `deploy_spec.machine_env` (read from the attacker's own PR branch `shipit.yml`) into the environment passed to `PTY.spawn`.

### Finding Description
The broken binding, stated as an equality that should hold but doesn't: `respond_to_pull_request_reopened? == (review_stacks_enabled && should_provision_per_behavior?)`. Due to Ruby operator precedence, `unarchive?` in [1](#0-0)  actually evaluates as `(review_stacks_enabled && allow_all?) || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?)` — `review_stacks_enabled` is ANDed only with the first disjunct, so it does not gate the label-based branches at all.

This differs from the sibling `LabeledHandler`/`UnlabeledHandler`, where `respond_to_label_change?` correctly ANDs `repository.review_stacks_enabled` across the *entire* `(archive? || unarchive?)` expression [2](#0-1) , and `OpenedHandler#provision?` has the identical flawed pattern [3](#0-2) , confirming this is a copy-pasted defect rather than intentional design.

`review_stacks_enabled` and `provisioning_behavior` are independent form fields the maintainer can set separately [4](#0-3) , so a repository can end up in the state `review_stacks_enabled: false, provisioning_behavior: allow_with_label` (e.g. an operator temporarily disables the feature without resetting the behavior dropdown).

Exploit flow: attacker opens a PR against such a repository, applies the provisioning label they control (their own PR), then closes and reopens it (or a `reopened` webhook fires). `respond_to_pull_request_reopened?` returns true despite `review_stacks_enabled == false` [5](#0-4) . `ReviewStackAdapter#unarchive!` then enqueues `Shipit::ReviewStackProvisioningQueue.add(stack)` [6](#0-5) . Provisioning eventually calls `TaskCommands#env`, which merges `deploy_spec.machine_env` — sourced from `DeploySpec::FileSystem#machine_env` reading `config('machine','environment')` off the PR's own branch — into the hash passed to `Command#unbundled_env` and `PTY.spawn` [7](#0-6) [8](#0-7) [9](#0-8) .

However, the `machine.environment` → `PTY.spawn` merge itself is not a bug introduced by this precedence issue — it is the intended, documented design of Review Stacks: the feature's entire purpose is to run each PR branch's own `shipit.yml`-defined deploy configuration for that PR's isolated review environment [10](#0-9) . Any repository that legitimately enables review stacks (`review_stacks_enabled: true`) already grants every PR author this exact capability by design. The precedence bug's real, additive impact is narrower: it can cause review-stack provisioning to fire when an operator believed the feature was fully disabled, for repositories left in the specific stale-configuration state described above.

### Impact Explanation
Where it applies (only repositories with the specific misconfigured combination of `review_stacks_enabled: false` plus a leftover `allow_with_label`/`prevent_with_label` value), the attacker gets a review-stack task to run their own branch's `shipit.yml` `machine.environment` values on the deploy host — the same capability any legitimate review-stack PR author already has when the feature is properly enabled. This is repeatable per PR/per repository in that misconfigured state, but is not a divergence from the trust model that review stacks already establish once enabled; it is an access-control gap around the on/off toggle, not a new execution-trust violation.

### Likelihood Explanation
Requires a specific, non-default repository misconfiguration (review stacks unchecked while `provisioning_behavior` left as label-based) that must be created by a maintainer, plus the attacker needing enough access to open/label/reopen a PR against that repository (their own fork/PR, or maintainer-level label access for `allow_with_label`, which the attacker does not have if it requires a maintainer to apply the label — for `prevent_with_label` the attacker only needs to *not* apply a label, which is trivially attacker-controlled). Feasible but conditioned on an atypical, transient admin configuration state that is not the norm.

### Recommendation
Parenthesize the boolean logic so `review_stacks_enabled` gates every branch: `repository.review_stacks_enabled && (allow_all? || (allow_with_label? && has_label?) || (prevent_with_label? && !has_label?))`, matching the pattern already used correctly in `LabeledHandler#respond_to_label_change?`. Apply the same fix to `OpenedHandler#provision?`.

# Review Stacks

A Review Stack is a dynamically managed stack whose lifecycle is tied to a Github Pull Request.

# Enabling Review Stacks

Review stacks can be enabled via the shipit-engine Repository UI.

1. Visit the shipit-engine Repository UI - `https://host-application/repositories`
1. Click on the project's repository
1. Check "Dynamically provision stacks for Pull Requests?"
1. Select the "Provisioning Behavior" appropriate for your project - most likely "Allow All"
1. Click "Save"

# Configuring Review Stack behavior

shipit-engine support three distinct behaviors for determining which Pull Requests should be considered for Review Stack creation.

1. "Allow All" - shipit-engine will create a Review Stack for every new Pull Requests.
1. "Allow With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisioning_label" attribute in order for shipit-engine to dynamically create/manage a Review Stack - an opt-in strategy.
1. "Prevent With Label" - when creating or updating a Pull Request, the user must add a label matching the `Shipit::Repository`'s "provisoining_label" attribute in order to **prevent** shipit-engine from dynamically creating/managing a Review Stack - an opt-out strategy.
