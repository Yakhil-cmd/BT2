### Title
Cross-organization team-authorization forgery via `MembershipHandler#find_or_create_team!` looking up teams by `github_id` only, ignoring the delivering organization - (File: `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`force_github_authentication` gates the whole application on `User#authorized?`, which is `true` if the user belongs to any `Team` referenced by `Shipit.github_teams`. [1](#0-0) [2](#0-1)  The `membership` webhook handler resolves the target `Team` solely by GitHub's numeric `team.id`, never verifying that the org that signed the webhook actually owns that team, so a delivery signed by any other GitHub org configured in Shipit (in a multi-org GitHub App setup) can add an arbitrary member to a security-authorizing team belonging to a different org.

### Finding Description
The broken binding: `team.organization` (the org that actually registered/owns the team referenced by `Shipit.github_teams`) must equal `params.organization.login` (the org whose webhook signature was verified for this specific delivery). The code never enforces this equality.

`WebhooksController#verify_signature` verifies the HMAC signature using `Shipit.github(organization: repository_owner)` — i.e. it validates that the request was signed by *some* org's app secret, where `repository_owner` is read straight from the attacker-controlled payload (`params.dig('organization','login')` for membership events). [3](#0-2) [4](#0-3)  This proves only that *the named organization itself* signed the delivery — nothing more. It never checks whether that organization is the one that owns the specific `Team` being mutated.

`MembershipHandler#process` then dispatches purely on the verified event type, and `find_or_create_team!` looks the team up **only by `github_id`**:
```ruby
def find_or_create_team!
  Team.find_or_create_by!(github_id: params.team.id) do |team|
    team.github_team = params.team
    team.organization = params.organization.login
  end
end
``` [5](#0-4)  The `team.organization = ...` assignment only executes inside the `find_or_create_by!` block, i.e. only on first creation. If a `Team` row for that `github_id` already exists (e.g. it was created earlier from the legitimate org via `Shipit.github_teams`/`Team.find_or_create_by_handle`, see `lib/shipit.rb` `github_teams` [6](#0-5) ), the existing row — with its original `organization` — is returned unchanged, and `team.add_member(member)` runs against it regardless of which org delivered the current webhook. [7](#0-6) 

`Team#github_hooks` (`REQUIRED_HOOKS = %i[membership]`, scoped by `organization`/`GithubHook::Organization`) exists but is **never consulted** by `MembershipHandler`, `WebhooksController`, or anywhere in the dispatch path — it is dead code with respect to authorization of this event. [8](#0-7)  `GithubHook` itself is marked `# TODO: app-migration, delete class`, confirming it's legacy/unused for the current GitHub-App-based webhook flow. [9](#0-8) 

Exploit flow (requires a multi-org Shipit `secrets.yml` configuration, e.g. as documented and tested in `secrets_double_github_app.yml` [10](#0-9) , where two unrelated GitHub orgs each install the Shipit App):
1. Attacker controls `AttackerOrg`, which has the Shipit GitHub App installed (any org can do this — installing a GitHub App on your own org requires no Shipit-side approval).
2. Attacker signs and POSTs a `membership` webhook to `/webhooks` with `X-Github-Event: membership`, body `{ action: "added", team: { id: <TargetOrg's authorized team's github_id>, name, slug, url }, organization: { login: "AttackerOrg" }, member: { login: "attacker_github_login" } }`, signed with `AttackerOrg`'s own webhook secret.
3. `verify_signature` succeeds because it only checks that `AttackerOrg`'s secret matches — a check the attacker fully controls.
4. `MembershipHandler#find_or_create_team!` finds the pre-existing `Team` row for `TargetOrg`'s authorized team by `github_id` and calls `team.add_member(attacker_user)`.
5. Attacker's Shipit `User` is now a member of a `Team` present in `Shipit.github_teams`, so `User#authorized?` returns `true`, bypassing GitHub-team-based authorization entirely and granting access to deploy/rollback/merge actions gated by `force_github_authentication`.

No existing guard prevents this: `verify_signature` checks signature validity per-organization only, not per-team ownership; `drop_unhandled_event` and `check_if_ping` are irrelevant; `ExplicitParameters` schema on `MembershipHandler` only validates types/presence, not organization-team binding; `Team#github_hooks`/`GithubHook::Organization` are never queried.

### Impact Explanation
A user in any GitHub org that merely has the Shipit App installed can grant themselves (or any GitHub login they name) membership in the `Team` object(s) that gate Shipit-wide authorization via `Shipit.github_teams`, without being a member of the target org or its actual GitHub team. This is a direct authentication/authorization bypass: `User#authorized?` becomes true, unlocking `force_github_authentication`-gated resources (deploys, rollbacks, merges, task streams, stack management) that are otherwise restricted to members of the legitimate org's team. This matches "Critical - authentication bypass" / "unauthorized deploy, rollback or merge," and at minimum "High - escalation into `Shipit.github_teams` authorization." The attack is repeatable against any team github_id and works cross-tenant across every org configured under the same Shipit instance's multi-app `github:` config.

### Likelihood Explanation
Requires: (a) the Shipit instance configured with the multi-organization GitHub App layout (`github: { OrgA: {...}, OrgB: {...} }`) — a supported and documented configuration [11](#0-10) ; (b) attacker controls at least one org with the app installed and its own webhook secret (trivial — attacker installs the app on their own org); (c) knowledge of the numeric GitHub `team.id` of the target authorized team, which is discoverable via GitHub's team APIs or brute-forceable since it's a small sequential integer with no additional secret required. No Shipit session, API token, or GitHub credentials of the victim org are needed. This is fully reproducible with a signed HTTP POST and no live GitHub, using existing test fixtures (`shipit_teams(:shopify_developers)`, `Shipit.github_teams`).

### Recommendation
In `MembershipHandler#find_or_create_team!`, scope the lookup by both `github_id` AND `organization: params.organization.login`, and reject/ignore the event (or raise) if a `Team` with that `github_id` already exists under a different `organization`. Additionally, use `Team#github_hooks` (or an equivalent check against `GithubHook::Organization` rows) to confirm the delivering organization is actually registered as the membership-hook owner for that team before processing `added`/`removed` actions.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "membership event from an unrelated org cannot add members to another org's authorized team" do
  target_team = shipit_teams(:shopify_developers) # organization == 'shopify', github_id fixed
  Shipit.stubs(:github_teams).returns([target_team])

  GithubHook.any_instance.stubs(:verify_signature).returns(true)
  @request.headers['X-Github-Event'] = 'membership'

  forged_payload = {
    action: 'added',
    team: { id: target_team.github_id, name: target_team.name, slug: target_team.slug, url: target_team.api_url },
    organization: { login: 'attacker-org' }, # NOT 'shopify'
    member: { login: 'mallory' },
    repository: { owner: { login: 'attacker-org' } }
  }

  assert_no_difference -> { target_team.reload.members.count } do
    post :create, body: forged_payload.to_json, as: :json
  end
  # Currently this assertion FAILS: the member is added despite organization mismatch,
  # proving Team#organization/github_hooks is never checked against the delivering org.
end
```
Expected (secure) behavior: `assert_no_difference` passes because the mismatched organization is rejected. Actual (current) behavior: the membership is added, and a follow-up assertion `assert current_user_for(mallory).authorized?` (after logging in as `mallory`) would return `true`, demonstrating the authorization bypass.
