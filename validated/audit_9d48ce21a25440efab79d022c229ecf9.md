### Title
Blacklisted ERC20 Recipient or Reverting KLAY Recipient Permanently Locks Bridged Assets and Stalls Bridge Nonce — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`, `contracts/service_chain/bridge/BridgeTransferKLAY.sol`)

### Summary

The Kaia service-chain bridge contracts `BridgeTransferERC20` and `BridgeTransferKLAY` perform the actual asset transfer to the recipient **after** updating all bridge state (nonce records, vote closure). If the transfer to `_to` reverts — because `_to` is blacklisted by the bridged ERC20 token (e.g., USDC) or because `_to` is a contract that rejects KLAY — the entire `handleERC20Transfer` / `handleKLAYTransfer` transaction reverts. This permanently prevents that bridge nonce from ever being settled, locks the bridged assets in the bridge contract, and stalls `lowerHandleNonce` and `recoveryBlockNumber` for the affected bridge pair.

### Finding Description

In `BridgeTransferERC20.sol`, `handleERC20Transfer` executes the following sequence:

1. Nonce check (`_lowerHandleNonceCheck`)
2. Operator vote (`_voteValueTransfer`)
3. State writes: `_setHandledRequestTxHash`, `handleNoncesToBlockNums[nonce] = blockNum`, `_updateHandleNonce`
4. Emit `HandleValueTransfer`
5. **Asset transfer**: `IERC20(_tokenAddress).safeTransfer(_to, _value)` (lock mode) or `ERC20Mintable(_tokenAddress).mint(_to, _value)` (mint/burn mode) [1](#0-0) 

If `_to` is blacklisted by the ERC20 token at the time operators attempt to settle the transfer, `safeTransfer` reverts. Because Solidity reverts roll back all state changes in the same transaction, steps 3–4 are also undone. The nonce is never marked handled, `handleNoncesToBlockNums[nonce]` remains 0, and `lowerHandleNonce` cannot advance past this nonce.

The same pattern exists in `BridgeTransferKLAY.sol`: [2](#0-1) 

State is written (lines 83–84), then `_to.call.value(_value)("")` is attempted (line 98) with a hard `require(ok, ...)`. If `_to` is a contract that reverts on receiving KLAY, the entire transaction reverts.

The `_updateHandleNonce` function advances `lowerHandleNonce` only when consecutive nonces starting from `lowerHandleNonce` are all present in `handleNoncesToBlockNums`: [3](#0-2) 

Because the stuck nonce's entry is never written (always reverted), `lowerHandleNonce` is permanently frozen at that nonce, and `recoveryBlockNumber` never advances past the corresponding source block.

A secondary DOS path exists in `BridgeFee._payKLAYFeeAndRefundChange`: if `feeReceiver` is a contract that reverts on receiving KLAY, every `_requestKLAYTransfer` call on the source bridge reverts, blocking all KLAY bridge requests: [4](#0-3) 

Similarly, `_payERC20FeeAndRefundChange` calls `safeTransfer(feeReceiver, fee)` and `safeTransfer(from, feeRefund)` — if either address is blacklisted, the request-side transaction reverts: [5](#0-4) 

### Impact Explanation

- **Permanent lock of bridged assets**: ERC20 tokens (or KLAY) deposited on the source chain are locked in the destination bridge contract and can never be delivered to `_to`. There is no admin escape hatch to redirect a stuck nonce to a different address.
- **Bridge nonce stall**: `lowerHandleNonce` is frozen at the stuck nonce. The value-transfer recovery system (`vt_recovery.go`) uses `recoveryBlockNumber` (derived from `lowerHandleNonce`) to determine the scan start block; it will perpetually re-scan the same range, wasting operator gas and potentially masking new missed events.
- **Operator gas drain**: Bridge operators keep retrying the failing `handleERC20Transfer` / `handleKLAYTransfer` call (driven by the recovery loop in `node/sc/vt_recovery.go`) with no possibility of success. [6](#0-5) 

### Likelihood Explanation

- USDC and other major stablecoins with blacklisting are explicitly in scope per the README (Blocklists of ERC20 tokens are in scope, matching the judge's reasoning in the referenced audit).
- A user's address can be blacklisted by the token issuer at any time after the cross-chain request is submitted on the source chain, with no action required from the user.
- The `_to` address for KLAY transfers can be any contract; a user can intentionally specify a contract that reverts on `receive()` to permanently lock a nonce.
- No existing guard in the bridge contracts handles transfer failure gracefully — there is no try/catch, no fallback delivery address, and no admin function to skip or redirect a stuck nonce.

### Recommendation

1. **Wrap the asset transfer in a try/catch** (Solidity ≥0.6 pattern) or use a low-level call with a success check that does not revert on failure. On failure, record the unclaimed amount in a `pendingWithdrawals[_to]` mapping so the recipient can pull their funds later (pull-over-push pattern).
2. **For KLAY transfers**, replace `require(ok, ...)` with a non-reverting path: if `ok == false`, store the amount for later claim by `_to`.
3. **For ERC20 transfers**, wrap `safeTransfer` in a try/catch; on failure, store the amount in a claimable mapping.
4. **For `_payKLAYFeeAndRefundChange`**, use a non-reverting low-level call for the `feeReceiver` payment and accumulate uncollected fees rather than reverting the entire bridge request.

### Proof of Concept

**ERC20 blacklist scenario:**

1. Alice holds USDC on the parent chain and calls `requestERC20Transfer` on the parent bridge, specifying her child-chain address as `_to`. The bridge emits `RequestValueTransfer` with `requestNonce = N`.
2. Before operators process nonce N on the child bridge, USDC's issuer blacklists Alice's child-chain address.
3. Operators call `handleERC20Transfer(..., _to=Alice, ..., _requestedNonce=N, ...)` on the child bridge.
4. Steps 1–4 of `handleERC20Transfer` execute (nonce check, vote, state writes, event). Then `IERC20(usdcAddr).safeTransfer(Alice, value)` reverts because Alice is blacklisted.
5. The entire transaction reverts. `handleNoncesToBlockNums[N]` is 0. `lowerHandleNonce` stays at N.
6. Every subsequent operator retry of nonce N reverts identically. Alice's USDC is permanently locked in the child bridge contract. `lowerHandleNonce` never advances. [7](#0-6) 

**KLAY reverting-contract scenario:**

1. Attacker deploys a contract `Rejecter` with a `receive()` that always reverts.
2. Attacker calls `requestKLAYTransfer(_to=Rejecter, ...)` on the source bridge, sending KLAY.
3. Operators call `handleKLAYTransfer(..., _to=Rejecter, ..., _requestedNonce=N, ...)`.
4. `_to.call.value(_value)("")` returns `ok=false`; `require(ok, ...)` reverts the transaction.
5. Nonce N is permanently stuck. `lowerHandleNonce` is frozen. The KLAY is locked in the destination bridge. [8](#0-7)
