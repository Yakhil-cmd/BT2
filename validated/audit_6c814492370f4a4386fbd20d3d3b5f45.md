### Title
Webhook signature verification binds the wrong scope: the GitHub organization used to select the `webhook_secret` is never checked against the repository/commit the event handler actually writes, allowing cross-organization webhook forgery — ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
In multi-organization deployments, `WebhooksController#verify_signature` picks which GitHub App's `webhook_secret` to verify the incoming HMAC against using a value taken directly from the **unverified** JSON body (`repository.owner.login` / `organization.login`). Once the signature matches *that* organization's secret, the controller dispatches the *entire same, attacker-controlled* body to event handlers, which independently re-read `repository.full_name` (or, for `status` events, only a bare commit `sha`) to decide which `Stack`/`Commit` to mutate — with no check that this second value belongs to the same organization whose secret validated the signature.

### Finding Description
`repository_owner` is computed from the raw, unauthenticated payload before signature verification: [1](#0-0) [2](#0-1) 

This value is only used to pick the `GitHubApp`/`webhook_secret` to verify against (`Shipit.github(organization: repository_owner)`), which is a per-organization secret in multi-org configs: [3](#0-2) [4](#0-3) 

Once verified, the raw params are handed unchanged to every registered handler: [5](#0-4) 

Handlers then look up the target repository/stack using a *different* field of the same attacker-controlled JSON body (`repository.full_name`), with no cross-check that it matches the organization whose secret validated the request: [6](#0-5) 

The `status` handler is the most exposed: it matches purely by commit `sha` with **no repository scoping at all**, so any commit anywhere in the Shipit installation can be targeted: [7](#0-6) 

`check_suite` also resolves its target stacks purely from `Repository.from_github_repo_name(payload.dig('repository','full_name'))`, taken from the same unverified body: [8](#0-7) 

This is the same class of bug as the reported `FeeManager` issue: the field used to authenticate the caller (`repository.owner.login`/organization → which secret to trust) is never bound to the field the code actually acts on (`repository.full_name` / commit `sha` → which stack/commit is mutated). An attacker who legitimately controls or can register a webhook against one configured GitHub organization (org A, with a known `webhook_secret`) can craft a JSON body where `repository.owner.login` = `"OrgA"` (so the correct, known secret is selected and the HMAC validates) but `repository.full_name` = `"OrgB/target-repo"` or an arbitrary target commit `sha`, causing Shipit to update state (commit statuses, check-run refresh, push syncs) for stacks belonging to organization B, which the attacker never controls and for which they have no legitimate webhook secret.

### Impact Explanation
The clearest high-impact path is `status`: an attacker can inject a forged, HMAC-valid (using their own org's secret) `status` webhook that sets an arbitrary `state` (e.g. `success`), `description`, and `context` on any commit `sha` already known to Shipit across any stack/organization, via `Commit#create_status_from_github!`. Since Shipit stacks gate deployability/merge-queue behavior on commit statuses/checks, this can be used to falsify a commit's CI/status record for a repository the attacker does not own, potentially unblocking merges/deploys that should have been blocked — an escalation into deploy/merge authorization decided by unverified cross-tenant data. `check_suite` similarly lets an attacker trigger check-run refresh workflows against another organization's stacks/commits.

### Likelihood Explanation
Requires the deployment to use the multi-organization GitHub App configuration (`config/secrets.yml` keyed by org, as documented) with at least one organization's `webhook_secret` known/controlled by the attacker (e.g. an org they administer that is intentionally configured in the same Shipit instance). Given that this is Shipit's documented "Using Multiple GitHub Applications" mode, and no additional binding check exists anywhere in the handler chain, exploitation only requires crafting one HTTP POST with a correctly-computed HMAC and mismatched `repository`/`sha` fields — no privileged Shipit session, API token, or GitHub write access to the target org is needed.

### Recommendation
After `verify_signature` succeeds, thread the resolved organization through to `Shipit::Webhooks.for_event(event)` handlers and have `Handler#repository_name` / `StatusHandler#process` validate that the resolved `Repository#owner` (or the commit's stack's repository owner) matches the organization whose secret validated the signature, rejecting the event otherwise.

### Proof of Concept
Given a Shipit instance configured with two organizations, `OrgA` (attacker-controlled, secret known to attacker) and `OrgB` (victim, has a stack with commit `sha=abc123` pending a real CI check):
1. Attacker builds a JSON body:
```json
{
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "OrgA" }, "full_name": "OrgB/victim-repo" }
}
```
2. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgA_webhook_secret, body)` and sends it with `X-Github-Event: status`.
3. `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgA"` [2](#0-1) , fetches `Shipit.github(organization: "OrgA")`, and the HMAC validates successfully because it was signed with `OrgA`'s real secret.
4. `StatusHandler#process` runs `Commit.where(sha: "abc123")` [7](#0-6)  — with no organization/repo check — and marks the victim's commit status as `success`, even though the attacker only controls `OrgA`, not `OrgB`.

I was unable to fully trace, within available exploration, the exact code path that consumes `Commit`/`Status` records to gate deploy or merge-queue eligibility (e.g. required status checks logic in `Stack`/`Commit`), so the "unauthorized deploy" escalation is inferred from Shipit's documented commit-status-based deployability model rather than directly cited line-by-line; a Devin session with full repo access would be needed to confirm that exact downstream consumer.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
