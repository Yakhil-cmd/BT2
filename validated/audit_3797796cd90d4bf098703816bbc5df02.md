This confirms the vulnerability. `Handler` base class provides a `stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks` [1](#0-0) , and `PushHandler` correctly uses that scoping [2](#0-1) . `StatusHandler#process`, however, ignores the `repository` field of the payload entirely and looks up commits **only by SHA**, globally across all stacks/repositories: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .

`verify_signature` only checks that the payload is signed by the GitHub App for the `repository_owner`/`organization` present in that same payload [4](#0-3)  — it does not, and cannot, prevent the attacker from putting an arbitrary `sha` in the `status` payload that happens to collide with a `Commit` row belonging to a completely different `Stack`/repository.

### Title
Unscoped `Commit.where(sha:)` lookup in `StatusHandler#process` lets a status from one repository mutate commit status/blocking state for another repository's stack - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits purely by `sha`, with no repository/stack scoping, unlike every other webhook handler (`PushHandler`, PR handlers) which scope lookups through `Repository.from_github_repo_name(repository_name)`. If any `Commit` row with an identical `sha` exists under a different stack (e.g., two forks/mirrors of the same upstream history, submodules, or any legitimate scenario producing identical 40-hex SHAs across stacks), a validly-signed status webhook from repo A writes a `Status` for that commit under repo B's stack too, and can flip `blocked?`/`deployable?` there because `blocking_statuses` gating in `Status::Common#blocking?` and `Commit#blocked?` operate off `stack.blocking_statuses`/`stack.commits`, not off which repository sent the webhook.

### Finding Description
The broken invariant, as an equality that should hold and does not:
`commit.stack.github_repo_name == payload.dig('repository', 'full_name')` for every `commit` that `StatusHandler#process` mutates.

Path:
1. Attacker owns/controls repo A, which is registered as (or can be registered as) a Shipit stack, and can obtain a validly signed webhook for repo A (GitHub signs any webhook for a repo whose events the attacker can trigger, e.g., by using the GitHub API/UI on their own repo, or replaying a `status` event they can create by pushing a commit and having a CI system report a status).
2. `verify_signature` validates the signature against `Shipit.github(organization: repository_owner)` derived from `payload['repository']['owner']['login']`, i.e., repo A's owner [5](#0-4) . This only proves the payload came from GitHub for repo A/its owner — it says nothing about which `sha` field is inside.
3. `StatusHandler#process` never reads `payload['repository']` at all; it just does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` [3](#0-2) .
4. If a `Commit` with that same `sha` exists on victim stack B (e.g., B mirrors/forks the same upstream commit history as A, so identical git objects and SHAs exist in both `Commit` tables), the status/context/state from A's webhook is written onto B's commit via `create_status_from_github!` → `statuses.replicate_from_github!` [6](#0-5) .
5. `Status::Common#blocking?` is `!success? && commit.blocking_statuses.include?(context)` [7](#0-6) , and `Commit#blocked?` scans `stack.commits.reachable.newer_than(...).older_than(...).any?(&:blocking?)` [8](#0-7) . A `success` status for a context in stack B's `blocking_statuses` clears that commit's `blocking?` flag, which can flip `blocked?` from `true` to `false` for B, and thus flip `deployable?` (`!locked? && (stack.ignore_ci? || (success? && !blocked?))`) [9](#0-8) . `add_status` also triggers `stack.schedule_merges` on success and emits `Hook.emit(:deployable_status, ...)`, i.e., real downstream ship/merge automation for stack B [10](#0-9) .

Existing guards that fail to stop this: `verify_signature` authenticates only the sender's own repository/org, not the `sha` target [4](#0-3) ; the `ExplicitParameters` schema in `StatusHandler` validates types only, not repository ownership of the `sha` [11](#0-10) ; `Handler#stacks`/`repository_name` scoping exists in the base class but `StatusHandler#process` simply doesn't call it, unlike `PushHandler` [1](#0-0) .

### Impact Explanation
A `status` webhook validly signed for repository A can write a `Status` record onto a `Commit` belonging to an unrelated stack/repository B whenever the two share a commit SHA, altering B's `blocked?`/`deployable?` computation and triggering `stack.schedule_merges`/`Hook.emit(:deployable_status, ...)` for B without B's repository ever sending that webhook. This matches "a payload for one repository mutating another's stack/commit" (Critical). The blast radius is limited to stacks that share an identical commit SHA with the attacker-controlled repository (forks, mirrors, or repos with a common git ancestry/shared history) — it is not universally exploitable against arbitrary, unrelated repositories with no shared commit history, since SHAs are content-addressed 40-hex digests and cannot be forged to match an unrelated victim's specific commit at will.

### Likelihood Explanation
Preconditions: victim stack B must contain a `Commit` row whose `sha` collides with a commit the attacker can get GitHub to sign a `status` webhook for from repo A — realistically this requires A and B to share git history (fork/mirror relationship, monorepo submodule, or the victim stack tracking a public upstream that the attacker also has a signed status channel for), plus B configuring `blocking_statuses`/`required_statuses` for a context the attacker sends. This is not exploitable against arbitrary unrelated repositories, only against victims sharing commit history with an attacker-reachable repo, which materially reduces likelihood compared to a fully unscoped cross-tenant primitive, but is still a real and repeatable code defect once the precondition (shared SHA) is met, and requires no special privilege beyond controlling one signed repo.

### Recommendation
Scope `StatusHandler#process` by repository like `PushHandler` does: resolve `stacks` via `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` and restrict `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` (or filter by `commit.stack.github_repo_name == repository_name`) before calling `create_status_from_github!`, so a status can only affect commits belonging to the repository that authenticated the webhook.
