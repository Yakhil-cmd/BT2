### Title
CCMenuController bypasses per-stack ApiClient scoping, letting a stack-scoped token read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The reported bug is a class of "improper handling of an edge case breaks an equality invariant that authorization logic depends on." In Shipit, the analogous invariant is: *the stack a token is authorized for (`ApiClient#stack_id`) must equal the stack the request actually touches (`params[:stack_id]`)*. `Api::BaseController` enforces this equality for every other API endpoint, but `Api::CCMenuController` overrides the stack lookup and silently drops the scoping check, breaking the binding.

### Finding Description
`Api::BaseController` computes the set of stacks a request may touch by intersecting with the authenticated `ApiClient`'s scope: [1](#0-0) 

This means a stack-scoped `ApiClient` (one created with a `stack_id`, e.g. as demonstrated by the test "an api client scoped to a stack will only see that one stack") can never resolve `stack` to any stack other than the one it was created for; `stacks.from_param!` raises/`404`s for any other `stack_id`.

`Api::CCMenuController`, however, only reuses `require_permission :read, :stack` (a pure permission-string check via `ApiClient#check_permissions!`, which checks only that `"read:stack"` is in the `permissions` array) and then defines its own `stack` method that completely bypasses the `stacks` scoping helper: [2](#0-1) 

`ApiClient#check_permissions!` only inspects the `permissions` array; it never inspects `stack_id`: [3](#0-2) 

So for the `Api::CCMenuController#show` action, any authenticated `ApiClient` with the generic `read:stack` permission (which is the *only* permission ever granted to CCMenu tokens, see `CCMenuUrlController#client`) can fetch CI/deploy status for **any** `stack_id` in `params`, regardless of the `stack_id` the token was actually scoped to.

The binding broken: `current_api_client.stack_id` (the stack the token authorizes) ≠ `params[:stack_id]` (the stack the controller actually touches), because `CCMenuController#stack` uses `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`.

### Impact Explanation
This is a High-severity finding under the stated impact criteria — "escalation into ... unauthenticated read of stack state, task streams or deploy output." A token that was only ever meant to expose CI status for one stack (e.g. handed out per-project to a CI dashboard, or leaked via a query-string `ccmenu_url` as generated by `CCMenuUrlController#fetch`) can be replayed against `/api/*/ccmenu.xml` for arbitrary `stack_id` values to read the latest deploy/rollback status (id, timestamps, running state) of every stack managed by the Shipit instance, including private/internal stacks the token holder has no legitimate access to.

### Likelihood Explanation
Likelihood is straightforward once any valid `ApiClient` token with `read:stack` exists — which is the default/only permission granted for CCMenu tokens created via `CCMenuUrlController`. No repository write access, webhook secret, or GitHub App key is required; the attacker only needs one legitimately-issued CCMenu token (their own, or one leaked in a CI badge URL) and can then iterate `stack_id` values.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoped lookup as every other API controller (`stacks.from_param!(params[:stack_id])`) instead of `Stack.from_param!`, so the `current_api_client.stack_id` scoping is enforced consistently, or add an explicit check that `current_api_client.stack_id.blank? || current_api_client.stack_id == stack.id` before rendering.

### Proof of Concept
1. As a legitimate user, request a CCMenu URL for Stack A: `GET /stack-a/ccmenu_url` → `CCMenuUrlController#fetch` creates/reuses an `ApiClient` named "CCMenu Client" with permissions `["read:stack"]` (no `stack_id` set in this flow, but the same code path is reused for any per-stack token with `read:stack`), returning `.../ccmenu.xml?token=<signed-id>`. [4](#0-3) 
2. Take that `token` and call the CCMenu endpoint for a different, unrelated stack: `GET /api/other-owner/other-repo/other-env/ccmenu.xml?token=<token>`.
3. `CCMenuController#authenticate_api_client` authenticates the token successfully; `require_permission :read, :stack` passes because the token has `read:stack`; `stack` resolves via `Stack.from_param!(params[:stack_id])`, ignoring that the token was never granted access to that stack. [5](#0-4) 
4. The response renders `shipit/ccmenu/project` for the unauthorized stack, leaking its latest deploy/rollback status.
