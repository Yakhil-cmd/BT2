This confirms the vulnerability. `Handler` (the base class) provides a `stacks` helper that scopes to the requesting repository via `Repository.from_github_repo_name(repository_name)` [1](#0-0) , and `PushHandler` correctly uses it: `stacks.not_archived.where(branch:)` [2](#0-1) . `StatusHandler`, however, never calls `stacks` or checks `payload.dig('repository', 'full_name')` — it queries `Commit.where(sha: params.sha)` globally and calls `commit.create_status_from_github!(params)` on every match, regardless of which stack/repository owns that commit [3](#0-2) . `create_status_from_github!` writes into `statuses` and re-evaluates deployability/merge scheduling via `add_status`, which calls `stack.schedule_merges` when `new_status.success?` [4](#0-3) [5](#0-4) .

Signature verification is scoped only to the GitHub *organization* of the sender (`Shipit.github(organization: repository_owner)` / `verify_webhook_signature`) [6](#0-5) [7](#0-6) , not to the specific repository. It does not verify that the `sha` in the payload actually belongs to the repository that sent it. Because git commit SHAs are content-addressed, any repository sharing history with the victim's tracked repo (e.g., a fork under an attacker-controlled org, or any org sharing a Shipit-configured `webhook_secret`) can produce a real, validly-signed `status` webhook naming a SHA that also exists as a `Commit` row belonging to an unrelated victim `Stack`.

### Title
Cross-repository status forgery via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by bare SHA across the entire database instead of scoping to the repository that authenticated the webhook, unlike `PushHandler` which correctly uses the `stacks` helper scoped by `repository.full_name`. An attacker who owns/controls any repository whose webhook is signed with a `webhook_secret` valid for some GitHub organization can send a genuine, correctly-signed `status` event containing a SHA that coincidentally (or by design, e.g. via a fork sharing history) also exists as a commit in a victim's stack, flipping that victim commit's status.

### Finding Description
The broken invariant: `commit.stack.github_repo_name == payload.dig('repository', 'full_name')` is never checked, so effectively the code treats `commit.stack == status_sender_repository` as always true, which is false whenever the same SHA exists as a `Commit` record under two different stacks/repositories.

Path: `WebhooksController#create` parses the payload and dispatches to `Shipit::Webhooks.for_event(event)` handlers after `verify_signature`, which only checks the HMAC using the secret configured for `repository_owner` (the sending org) [8](#0-7) . It never validates that `params.dig('repository','full_name')` matches any specific stack. `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` with no repository filter at all [3](#0-2) , unlike `Handler#stacks`, which properly scopes via `Repository.from_github_repo_name(repository_name)` [1](#0-0) .

`create_status_from_github!` calls `add_status`, which after appending the new status re-evaluates `new_status.state`/`success?` and, if success/pending, calls `stack.schedule_merges` [9](#0-8) . `Commit#deployable?` depends on `success? && !blocked?` [10](#0-9) . When the victim stack has `bot_login` configured (i.e., `Shipit.user`/bot identity used for auto-merges/auto-deploys), a forged `success` on a required context can trigger `schedule_continuous_delivery` and merges/deploys running as that bot identity.

Attacker request: an unauthenticated `POST /webhooks` request with header `X-Github-Event: status` and body `{"sha": "<shared_sha>", "state": "success", "context": "ci/test", "repository": {"owner": {"login": "<attacker_org>"}, "full_name": "<attacker_org>/<attacker_repo>"}}`, signed with the `webhook_secret` valid for `<attacker_org>` (which the attacker legitimately controls, e.g. via a fork or a repo under an org that shares Shipit's org-level GitHub App/webhook secret configuration). If `<shared_sha>` also exists as a `Commit` row for the victim's stack (plausible for forked/mirrored repositories where commit SHAs are shared history), `verify_signature` passes (it only checks the attacker's own org secret) and `StatusHandler` mutates the victim's unrelated commit.

Existing guards fail because: `verify_signature` authenticates the *sender's organization*, not the specific *repository* named in the SHA lookup; `ExplicitParameters` only validates types/presence of `sha`/`state`/`context`, not repository ownership; and `drop_unhandled_event` only filters unregistered event types.

### Impact Explanation
A payload authenticated for one repository/organization can mutate a `Commit`/status belonging to a completely different stack, which is explicitly listed as a Critical impact ("a payload for one repository mutating another's stack, commit, task or team"). With `bot_login` configured, the forged `success` status can make an otherwise-blocked commit `deployable?`, triggering `schedule_continuous_delivery`/`schedule_merges`, resulting in unauthorized deploy or merge executed under the bot identity — an unauthorized deploy/merge as described in the Critical impact category. This is repeatable against any victim stack whose tracked repository shares commit history (identical SHAs) with any repository the attacker controls or can get a webhook signed for.

### Likelihood Explanation
Requires: (1) a victim stack configured with `bot_login`/auto-merge or continuous-deployment relying on a required `ci/test`-style context, and (2) a SHA collision between a commit in the victim's tracked repository and a repository the attacker can trigger a validly-signed `status` webhook for — most realistically via a fork of the tracked repo (shared ancestor commits have identical SHA1 by construction) where the fork's org is configured with a Shipit-recognized webhook secret, or scenarios where the org-level webhook secret is broader than a single repo. This needs no Shipit credentials, session, or API token — only the ability to legitimately push/set a commit status on a repository the attacker owns, which matches the stated "unprivileged attacker" capabilities. The forgery is repeatable per commit/context.

### Recommendation
Scope `StatusHandler#process` (and any other bare `Commit.where(sha:)`/`by_sha` lookups driven by webhook payloads) to the repository that authenticated the request, mirroring `Handler#stacks`: filter `Commit.joins(:stack).merge(stacks)` or equivalently restrict to commits whose `stack.repository` matches `payload.dig('repository','full_name')`, rather than a bare SHA match across all stacks.

### Proof of Concept
minitest plan (`test/models/webhooks/handlers/status_handler_test.rb`, conceptual — file does not currently exist per search):
1. Create `repo_a` (`Repository`) + `stack_a` with `bot_login`/continuous_deployment configured, and a `Commit` with `sha: "deadbeef" * 5` belonging to `stack_a`, with `context: "ci/test"` as a required status.
2. Create `repo_b` (unrelated) + `stack_b`, and a `Commit` with the **same** `sha` belonging to `stack_b` (simulating shared git history/fork).
3. Assert before: `stack_a.commits.find_by(sha: sha).deployable?` is `false` (no status yet / pending).
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call('sha' => sha, 'state' => 'success', 'context' => 'ci/test', 'repository' => { 'full_name' => repo_b.full_name, 'owner' => { 'login' => repo_b.owner } })` — i.e., a payload that only ever authenticated against `repo_b`.
5. Assert after: `stack_a.commits.find_by(sha: sha).reload.deployable?` is now `true` and/or `stack_a.commits.find_by(sha: sha).status.success?` is `true`, proving that a payload attributable only to `repo_b` mutated `stack_a`'s commit — violating the binding `commit.stack.repository == payload.repository.full_name`.
