### Title
Deploy `env` whitelist validated against the stack's cached HEAD `shipit.yml` while the deploy actually executes the `shipit.yml` of an arbitrary historical `until_commit` - (File: app/models/shipit/stack.rb)

### Summary
This mirrors the code4rena quorum-bypass class of bug: a security-relevant check is computed from state pinned to a *different* point (or ref) than the state that is actually acted upon at execution time, letting the two diverge and allowing the check to be bypassed. In shipit-engine, the whitelist of environment variables a caller may set on a deploy is derived from `Stack#cached_deploy_spec` — an asynchronously refreshed snapshot of `shipit.yml` at the stack's *latest reachable commit* — while the deploy that is actually built and run can target any historical, still-reachable `until_commit`, whose *own* `shipit.yml` (loaded fresh from the checked-out working directory) is what actually consumes those environment variables in the executed shell steps.

### Finding Description
`Stack#build_deploy` validates the caller-supplied `env` hash using `filter_deploy_envs`: [1](#0-0) 

`filter_deploy_envs` is delegated straight to `cached_deploy_spec`, not to any spec tied to `until_commit`: [2](#0-1) 

`cached_deploy_spec` is populated by `CacheDeploySpecJob`, which always checks out the *newest reachable commit* of the stack, independent of which commit any given deploy targets: [3](#0-2) 

The whitelist itself is enforced by `EnvironmentVariables#permit`, which simply checks variable *names* against `deploy_variables` from whatever spec it's given: [4](#0-3) [5](#0-4) 

Meanwhile, the API lets a caller pick any commit sha reachable on the stack as `until_commit`, not just HEAD: [6](#0-5) 

And when the task actually runs, the deploy steps, `machine_env`, and variable interpretation come from a *freshly loaded* `DeploySpec::FileSystem` rooted at the task's working directory — i.e., checked out to `until_commit`, not HEAD: [7](#0-6) 

The env hash that passed the whitelist check (bound to HEAD's `shipit.yml`) is what actually gets merged into the subprocess environment for the commit-specific steps: [8](#0-7) 

The equality that should hold is:
```
deploy.env permitted-by(shipit.yml @ HEAD) == deploy.env consumed-by(shipit.yml @ until_commit)
```
This does not hold, because the left side is pinned to the stack's `cached_deploy_spec` (latest reachable commit, refreshed asynchronously) while the right side is pinned to whatever historical `until_commit` the deploy actually targets.

### Impact Explanation
Any user permitted to trigger a deploy on a stack (an ordinary, expected capability — not requiring repo write access, an API token, or a privileged account) can pass an `env` variable name that is only currently permitted because HEAD's `shipit.yml` declares it under `deploy.variables`, then target an older commit whose deploy scripts were never audited against that variable being attacker-controlled. Because `env` values are merged directly into the OS-level environment of the spawned deploy subprocess (`Command.new(command_line, env:, chdir:)`), a variable name that collides with process-level environment variables interpreted by the shell/toolchain used at that historical commit (e.g. variables affecting the interpreter, bundler, or git invocation used by that revision's deploy steps) can alter subprocess behavior in ways the maintainers of that historical commit did not anticipate and could not have safety-reviewed, since they never saw the future `deploy.variables` declaration. This crosses the "unauthorized deploy behavior via environment manipulation on the deploy host" impact bar, potentially escalating to command/argument injection depending on what the historical commit's deploy steps do with unexpected env vars.

### Likelihood Explanation
Likelihood is moderate to high in any actively maintained stack: `deploy.variables` lists commonly grow over time as new deploy knobs are added, and `until_commit` is fully attacker/user-selectable via the deploy API among any commit still reachable in the stack's history. No special timing or race condition is even required — the mismatch exists any time a user deploys a non-HEAD commit while supplying a variable that only the current HEAD's `shipit.yml` declares. The `require_ci`/`force` checks in the deploys controller only gate CI status and lock state, not this whitelist/execution-config mismatch.

### Recommendation
Enforce the env whitelist using the `shipit.yml` of the commit actually being deployed (`until_commit`), not the stack's separately-cached HEAD spec. Concretely, `filter_deploy_envs` should be evaluated against a `DeploySpec` loaded (or lazily fetched) at `until_commit`, mirroring what `TaskCommands#deploy_spec` already does at execution time, rather than delegating to `cached_deploy_spec`.

### Proof of Concept
1. On the target repository's default branch (HEAD), `shipit.yml` declares a deploy variable, e.g.:
```yaml
deploy:
  variables:
    - name: BUNDLE_GEMFILE
      default: ""
```
(or any variable name colliding with a process-level environment variable meaningful to the deploy tool-chain).
2. Shipit's `CacheDeploySpecJob` syncs this into `Stack#cached_deploy_spec`.
3. An older, still-reachable commit `C` on the same stack does not declare this variable and its deploy steps were written before this variable existed / was ever considered attacker-controllable.
4. Call `POST /api/stacks/:owner/:repo/:env/deploys` with `sha: C.sha` and `env: { "BUNDLE_GEMFILE" => "/tmp/attacker/Gemfile" }` — see `app/controllers/shipit/api/deploys_controller.rb`.
5. `filter_deploy_envs` (backed by `cached_deploy_spec`, HEAD's config) accepts `BUNDLE_GEMFILE` as permitted.
6. The task runs against commit `C`'s checked-out working directory, using `C`'s deploy steps, but with the caller-supplied `BUNDLE_GEMFILE` injected into the subprocess environment via `TaskCommands#env`/`Command.new(..., env:, ...)`, altering the behavior of `C`'s deploy tooling in a way `C`'s authors never reviewed for user control.

Note: I was not able to fully trace `lib/shipit/command.rb`'s exact subprocess-spawn semantics for the `env:` kwarg within the indexed context (only usage sites were found, not the full spawn implementation), so the exact severity of downstream effects from an injected variable name (e.g., whether it can achieve full RCE versus more limited behavior alteration) could not be conclusively confirmed from the available index; a Devin session with full repository access would be needed to verify this last step precisely.
