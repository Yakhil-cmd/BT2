I found a concrete analog of the "mandatory sub-IE omitted → crash" bug class, reachable by an AA (autonomous agent) via its own generated `asset_attestors`/`asset` bounce-response messages.

### Title
AA-composed `asset_attestors`/`asset` response messages with an empty/omitted `attestors` array crash the node in `writer.js` - (File: writer.js)

### Summary
`aa_composer.js` lets an AA's oscript template emit `asset_attestors` (and `asset` with `spender_attested`) messages whose `attestors` field is computed at runtime from trigger data (e.g. `"{trigger.data.attestor1}"`). Unlike a directly-posted unit, these AA-response messages are validated in `aa_composer.js`'s pre-send filter only loosely: the attestors array is merely *sorted* if it happens to be a valid, non-empty array of addresses — it is never rejected if it is empty, missing, or contains a garbage/empty value. The message is then serialized and handed to `writer.js`, which unconditionally iterates `asset_attestors.attestors.length` when writing the DB rows, causing a crash if the array is absent or not an array.

### Finding Description
In `aa_composer.js` `handleTrigger`, after `evaluateAA` produces the response `messages`, the code does: [1](#0-0) 
Only messages that are non-empty objects with a `payload` key (and, for payments, an outputs array) are filtered out; `asset`/`asset_attestors` payloads are *only* sorted when `attestors` happens to already be a valid array — there is no rejection path if `attestors` is missing, `undefined`, an empty array, or a non-array value produced by a formula (e.g. `trigger.data.attestor1` evaluating to `false`/`''`/`0` because the trigger simply omitted that data field). The later structural filter for messages at [2](#0-1)  only validates `payment` app payloads (outputs, addresses); it does not check `asset`/`asset_attestors` payloads for a mandatory `attestors` array at all.

Once such a message passes into `sendUnit`'s completion and is saved via `writer.js` `saveJoint`, the write path unconditionally accesses `.attestors.length`: [3](#0-2) 
If `asset_attestors.attestors` is `undefined` (or not an array), `asset_attestors.attestors.length` throws a `TypeError`, which is unhandled inside the synchronous SQL-query-building loop of `saveJoint`. This is the same bug class as the PFCP report: a message declares/implies a repeated mandatory sub-structure (URRID inside a UsageReport ≈ `attestors` inside `asset_attestors`), but the omission of that mandatory sub-field is not rejected by validation before the structure is dereferenced downstream, causing a nil/undefined access crash.

Contrast this with the *directly posted unit* path, which is properly guarded: `validation.js`'s `validateAttestorListUpdate` → `checkAttestorList` rejects non-array/empty `attestors` before the unit can ever reach `writer.js` [4](#0-3) . The AA-generated-response path bypasses this hardening because `aa_composer.js` never calls the equivalent check for its own response messages; it relies purely on `evaluateAA`/formula evaluation semantics, which do not enforce a non-empty-array constraint on `attestors` when the AA template computes it dynamically from potentially-absent trigger data.

### Impact Explanation
Any address (attacker) can trigger an AA whose template contains an `asset_attestors` (or `asset` with `spender_attested`) message referencing trigger data for `attestors`, and simply omit that trigger-data field (or supply a value that evaluates to a non-array/empty result) when sending the triggering payment. This causes the full node processing the AA response — every node validating/writing that unit, i.e., the whole network attempting to build on that unit — to throw an unhandled `TypeError` inside `saveJoint`'s SQL-building loop. Because `saveJoint` runs synchronously within the write path used by full nodes to persist units and stabilize the DAG, this can crash the node process (uncaught exception) or corrupt the atomic write transaction, resulting in nodes disagreeing on validity/being unable to process further units from that AA — a "network unable to confirm new units" condition for that AA and potentially process-level DoS for any node that computes the trigger's response.

### Likelihood Explanation
High reachability: any unprivileged user can post a normal payment-triggering unit to a pre-existing (or newly defined) AA whose oscript uses `asset_attestors`/`asset` with an `attestors` expression sourced from `trigger.data`. No special privileges, hub/peer control, or race conditions are needed — just crafting a trigger unit that omits the expected data field so the formula evaluates the `attestors` expression to `undefined`/empty. AA authors may not always guard against user-omitted trigger fields, and `aa_validation.js`'s compile-time check on `asset_attestors`/`asset` payloads (`validateAttestors`) only validates the payload template shape (string-formula or well-formed array), not the case where a formula legitimately evaluates to a non-array/absent value at trigger time.

### Recommendation
In `aa_composer.js`, before calling `sendUnit`/serializing `asset`/`asset_attestors` response messages, explicitly validate that `payload.attestors` (when present or required, e.g. `spender_attested`) is a non-empty array of valid addresses, `bounce()`-ing with an error message otherwise instead of silently leaving it unvalidated. Apply the same `checkAttestorList`-style validation used in `validation.js` (`validation.js:2850-2864`) to AA-generated messages, and make `writer.js`'s `asset`/`asset_attestors` insertion code (`writer.js:229-250`) defensively check `Array.isArray(...attestors)` before iterating, converting a missing/invalid array into a hard validation failure (bounce) rather than an unhandled exception during persistence.

### Proof of Concept
1. Deploy an AA with a template message:
```
{
  app: 'asset_attestors',
  payload: {
    asset: "{trigger.output[[asset!=base]].asset}",
    attestors: "{trigger.data.attestor1}"   // single string/undefined, not wrapped in array logic guarding for undefined
  }
}
```
2. Send a trigger unit to this AA with a payment output but no `data.attestor1` field (or `data: {}`).
3. `evaluateAA` evaluates `trigger.data.attestor1` to `undefined`/false; the pre-send filter in `aa_composer.js:1878-1884` does not reject this because it only *conditionally* sorts if the array is valid — it never bounces if invalid.
4. The resulting `asset_attestors` message with a non-array/missing `attestors` field proceeds to `writer.js:saveJoint`, where `asset_attestors.attestors.length` throws `TypeError: Cannot read properties of undefined (reading 'length')`, crashing the write path for every full node processing this AA response.

**Note on confidence**: I was not able to fully trace every intermediate step in `aa_composer.js`'s `sendUnit`/`completeMessage` pipeline (some code between lines ~1300–1840 was only partially retrieved) to confirm there is no additional guard specifically rejecting malformed `attestors` before the message reaches `writer.js`. The evidence gathered strongly suggests such a guard is absent for `asset`/`asset_attestors` messages (unlike `payment` messages, which are explicitly checked), but a full Devin session with complete file access would be needed to definitively confirm no intervening check exists.

function checkAttestorList(arrAttestors){
	if (!isNonemptyArray(arrAttestors))
		return "attestors not defined";
	if (arrAttestors.length > constants.MAX_ATTESTORS_PER_ASSET)
		return "too many attestors";
	var prev="";
	for (var i=0; i<arrAttestors.length; i++){
		if (!isValidAddress(arrAttestors[i]))
			return "invalid attestor address: "+JSON.stringify(arrAttestors[i]);
		if (arrAttestors[i] <= prev)
			return "attestors not sorted";
		prev = arrAttestors[i];
	}
	return null;
}
