### Title
Cross-stack authorization bypass in CCMenu API — CCMenuController#stack resolves any stack instead of the token's authorized stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::CCMenuController#stack` overrides `BaseController#stack` to call `Stack.from_param!(params[:stack_id])` directly instead of `stacks.from_param!(params[:stack_id])`, bypassing the `current_api_client.stack_id` scoping. This lets a valid `read:stack` token minted for one stack fetch CCMenu XML (deploy/task status) for any other stack.

### Finding Description
The broken binding: stack served == `Stack.from_param!(params[:stack_id])` for arbitrary `params[:stack_id]`, whereas it should be constrained to `== current_api_client.stack_id` (i.e., stack served ∈ `stacks` = `Stack.where(id: current_api_client.stack_id)`).

`BaseController#stacks` scopes stacks by the authenticated client: [1](#0-0) . This is the mechanism that binds `params[:stack_id]` resolution to the client's authorized `stack_id`. However `CCMenuController` defines its own `#stack` that skips this scope entirely: [2](#0-1) .

The permission check only validates the `permissions` array (`read:stack`), never the `stack_id`: [3](#0-2) . `authenticate_api_client` in this controller is also overridden to only verify the token's signature via `ApiClient.authenticate`, with no stack binding check: [4](#0-3) .

CCMenu tokens are minted per-stack via `CCMenuUrlController#fetch`, creating an `ApiClient` scoped with `permissions: %w[read:stack]` (note: `stack_id` is not even set on the client, but even if it were, the check is not enforced downstream) and returning a URL containing `stack.to_param` and `token`: [5](#0-4) .

Exploit flow: an attacker who has (or obtains) any valid `read:stack` CCMenu token for stack A simply issues `GET /api/stacks/:stack_b_param/ccmenu.xml?token=<token>`. `#show` calls `stack`, which resolves stack B unconditionally, and renders stack B's deploy/task status: [6](#0-5) . None of the existing guards (`require_permission :read, :stack`, `check_permissions!`) inspect `stack_id`, so the divergence is never caught.

### Impact Explanation
The attacker obtains unauthenticated-relative-to-B read access to stack B's deploy/task state (build status, last build label/time, activity, web URL) using a token that was only ever intended to scope stack A. This is repeatable against any stack in the Shipit instance, given any single valid CCMenu token, and matches the High severity category "unauthenticated read of stack state."

### Likelihood Explanation
Preconditions are minimal: the attacker needs one valid `read:stack` token, which is fetchable by anyone with access to `CCMenuUrlController#fetch` for any stack they can view (this endpoint requires only a valid Shipit session, not elevated privilege, per the standard CCMenu integration flow). Once obtained, the exploit is a single unauthenticated GET request with an arbitrary `stack_id`, fully repeatable and low-cost.

### Recommendation
Change `CCMenuController#stack` to use the scoped lookup like the base class: `stacks.from_param!(params[:stack_id])`, and restore use of the base `authenticate_api_client`/`stacks` scoping instead of the custom override, ensuring `current_api_client.stack_id` (when present) constrains the resolvable stack set.

### Proof of Concept
```ruby
test "cannot fetch ccmenu xml for a different stack than the token authorizes" do
  stack_a = shipit_stacks(:shipit)
  stack_b = Stack.create!(repository: Repository.new(owner: "foo", name: "bar"), branch: 'main')
  client = ApiClient.create!(creator: shipit_users(:walrus), name: 'CCMenu Client',
                              permissions: %w[read:stack], stack_id: stack_a.id)

  get :show, params: { stack_id: stack_b.to_param, token: client.authentication_token }

  assert_response :ok # demonstrates bug: should be :forbidden/:not_found since token is scoped to stack_a
  assert_payload 'name', stack_b.to_param # stack B's data leaked via a token minted for stack A
end
```
