### Title
Signed packages (`is_valid_signed_package`) omit the network `alt` field from the signing hash, allowing cross-network/cross-fork signature replay - (File: signed_message.js, object_hash.js)

### Summary
`getSignedPackageHashToSign()` in `object_hash.js` computes the hash-to-sign for `signed_message`/`signed_package` objects used throughout the wallet (`signed_message.js`), AA oscript (`is_valid_signed_package` in `formula/evaluation.js`), and peer-to-peer contract flows (e.g. `arbiter_contract_response` in `wallet.js`). Unlike full unit signing (`getUnitHashToSign`, via `getNakedUnit`, which retains the unit's `alt` field), the signed-package schema explicitly allows only `["signed_message", "authors", "last_ball_unit", "timestamp", "version"]` and never includes a network/chain identifier (`alt`). This is directly analogous to the reported EIP-712/`chainId`-omission bug: a signature produced for one network/deployment context remains valid and replayable on any other network sharing the same address space.

### Finding Description
`object_hash.js`: [1](#0-0) 
shows that full-unit hashing (`getStrippedUnit`) explicitly carries the unit's `alt` (network) field forward into the value that is hashed. In contrast: [2](#0-1) 
`getSignedPackageHashToSign()` hashes the signed package as-is with no `alt` field ever present, because `signed_message.js`'s `validateSignedMessage()` restricts the object to a fixed field set that excludes any network identifier: [3](#0-2) 
and `signMessage()` builds the package the same way, again with no `alt`: [4](#0-3) 

Address derivation itself is also network-agnostic — `getChash160()` hashes only the definition content, with no chain/network binding: [5](#0-4) 

This means an identical address (and an identical AA template/definition, since AA addresses are deterministic hashes of the definition) can exist across the mainnet, the testnet, or any future fork/alternate deployment of ocore. Any signature over a `signed_message`/`signed_package` — used by:
- `is_valid_signed_package` in oscript, which any AA author can use to authorize off-chain-signed state updates (e.g., payment channels, oracle-style price feeds, delegated permissions): [6](#0-5) 
- payment-channel logic that relies on this primitive to accept a signed off-chain balance update from a channel counterparty: [7](#0-6) 
- arbiter contract acceptance flow, which likewise only checks the signer address and message content, not network scope: [8](#0-7) 

is fully reusable on any other network/deployment sharing the same address, because nothing in `unit_hash_to_sign` binds the signature to a specific `alt`/chain.

### Impact Explanation
Because AA addresses and payment addresses are derived purely from their definition (no network salt), and signed-package hashes never include `alt`, a legitimate signed authorization created by a user/counterparty for one AA instance/network context can be replayed verbatim against an identical AA template deployed on another network (mainnet vs. testnet) or after a protocol fork that produces two live chains sharing the same address space. In payment-channel-style AAs (as shown in the shipped sample) this enables replay of a stale/old off-chain balance signature to force channel closure or fund extraction in an environment other than the one the signer intended, i.e., AA fund loss for the honest counterparty, or unauthorized state transitions in any AA relying on `is_valid_signed_package` as an authorization gate. This satisfies the "AA fund loss or freezing" / "unauthorized spending" bar for Medium+ severity.

### Likelihood Explanation
Exploitability requires: (1) an AA (or wallet-level contract flow) that trusts `is_valid_signed_package`/`validateSignedMessage` as an authorization mechanism without independently embedding a network-scoping value in the signed payload, and (2) the same address/definition being live in more than one network/deployment context (testnet+mainnet coexist today for Obyte; a chain fork would create the same condition). The framework does not enforce or even provide network-scoping fields for signed packages, so any AA author who doesn't manually add such context (as `payment_channels.oscript` partially does for `channel`/`period`, but not for network) is exposed. This is a systemic gap in the primitive itself rather than a one-off usage bug, making it moderately likely to be exploited whenever contracts are cloned/tested across environments.

### Recommendation
Include a network-identifying field (e.g., `alt`, or an explicit `network`/`chain_id` value from `constants.js`) in the object hashed by `getSignedPackageHashToSign()`, and enforce its presence and correctness in `signed_message.validateSignedMessage()` (reject packages whose `alt` doesn't match the network the validating node is running on). Document that any AA relying on `is_valid_signed_package` for off-chain authorization must not assume the signature is scoped to a specific address/network purely by the signed content; the fix should make that guarantee at the framework level so individual oscript authors don't have to re-implement it.

### Proof of Concept
1. On network A (e.g. testnet, `alt` = testnet value), a user signs a `signed_message` package via `signed_message.signMessage()` authorizing, e.g., a payment-channel balance update for address `X` (an AA instance whose address is `chash160(definition)`).
2. Deploy the identical AA definition (same bytecode/params) on network B (e.g. mainnet or a forked chain); because `getChash160` has no network salt, the AA address is identical to `X` on network B.
3. Submit the same signed package (unchanged, since `getSignedPackageHashToSign` never included any network-specific data) as `trigger.data.sentByPeer` against the AA instance on network B.
4. `is_valid_signed_package` (`formula/evaluation.js` lines 1693-1699, calling `signed_message.validateSignedMessage`) succeeds because signature verification only checks `unit_hash_to_sign` derived from message content/author/last_ball_unit — none of which differ between networks — allowing the replayed authorization to be accepted on network B where it was never intended to be valid.

function getSignedPackageHashToSign(signedPackage) {
	var unsignedPackage = _.cloneDeep(signedPackage);
	for (var i=0; i<unsignedPackage.authors.length; i++)
		delete unsignedPackage.authors[i].authentifiers;
	var sourceString = (typeof signedPackage.version === 'undefined' || signedPackage.version === constants.versionWithoutTimestamp) ? getSourceString(unsignedPackage) : getJsonSourceString(unsignedPackage);
	return crypto.createHash("sha256").update(sourceString, "utf8").digest();
}
