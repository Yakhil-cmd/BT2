I found a genuine bug analog at line 2358 of `validation.js`: in the `issue` input-type branch of `validatePaymentInputsAndOutputs`, the duplicate-input-key check calls the wrong callback.

### Title
Duplicate issue-input check calls outer `callback` instead of inner `cb`, bypassing forEachOfSeries error propagation and rejecting the whole validation prematurely — ([File: validation.js])

### Summary
In `validation.js`'s `validatePaymentInputsAndOutputs`, the per-input iteration is driven by `async.forEachOfSeries(payload.inputs, function(input, input_index, cb){...}, ...)`. Inside the `"issue"` case, when a duplicate `input_key` is detected, the code invokes the outer function's `callback` parameter instead of the loop's local `cb` parameter: [1](#0-0) . This is exactly the same class of bug reported externally for `CrossCurrencyVault.sol#_redeemfCash`: a call site invoking a differently-scoped/differently-shaped function than the one actually intended by the surrounding control flow, so the call does not behave as the enclosing logic expects.

### Finding Description
`validatePaymentInputsAndOutputs(conn, payload, objAsset, message_index, objUnit, objValidationState, callback)` takes an outer `callback` used to report completion/error for the whole payload's inputs+outputs validation [2](#0-1) . Inside, `async.forEachOfSeries` is used with a per-item `cb` to signal per-input success/failure so the async loop can stop early and propagate the specific error through the `forEachOfSeries` completion handler [3](#0-2) .

Every other error path in this same `switch` block correctly calls the loop's local `cb` (e.g., lines 2312, 2314, 2316, 2318, 2320, 2323, 2326, 2332, 2337, 2339, 2346, 2350, 2352, 2404) [4](#0-3) . However, the duplicate `input_key` check for the `issue` case instead calls `callback(...)` — the function-scoped completion callback of `validatePaymentInputsAndOutputs`, not the loop iterator's `cb` [5](#0-4) .

Because `callback` is a different function from `cb`, calling it does not signal completion/error to `async.forEachOfSeries`. The iterator function that wraps this case never invokes its own `cb`, so from `forEachOfSeries`'s perspective this iteration never completes (it hangs, since no callback returns to advance the series) while at the same time the outer `callback` for the entire payload validation is invoked directly out of band, with a duplicate error message but without going through the normal completion path of `validatePaymentInputsAndOutputs` (i.e. `async.series([...], callback)` completion, and any subsequent output validations such as `total_input`/`total_output` reconciliation, `objValidationState.arrInputKeys` bookkeeping consistency, or additional side effects expected to run in sequence) [6](#0-5) .

This diverges the control flow from the single, well-defined validation pipeline that `validate()`/`validateMessage()` expects to invoke exactly once per message [7](#0-6) . Depending on how `callback` was already bound/consumed earlier in the pipeline (it is the same object passed transitively from `validateMessage` → `validatePayment` → `validatePaymentInputsAndOutputs`), invoking it a second time, or invoking it while the `async.forEachOfSeries` loop is still logically "in flight", can cause the double-invocation-of-callback pattern common in Node.js `async` pipelines: either a silently stuck validation (never calling `ifOk`/`ifUnitError`), or callback reentrancy that lets subsequent code paths (e.g. `commit_fn` in `validate()`) run more than once or in an unexpected order [8](#0-7) .

### Impact Explanation
`validatePaymentInputsAndOutputs` is the function responsible for detecting duplicate issue inputs (double-issue/double-spend protection for asset issuance) — this is precisely the mechanism guarding against supply inflation (issuing the same capped/serial-numbered coin twice) [9](#0-8) . If the duplicate-input-key branch's control flow is broken so that the async series never properly completes/aborts, a malicious unit poster could craft a payload with a duplicate issue `input_key` designed to hit this exact code path, and the ambiguous callback signaling could let validation either hang (denial of confirmation for units caught in this state) or, worse, allow the unit to be treated as accepted through a stale/incorrect completion signal at a higher level (`ifOk`), effectively bypassing the double-issue guard.

### Likelihood Explanation
The buggy branch is reached whenever an attacker posts a message containing an `issue` input whose derived `input_key` (`asset-denomination-address-serial_number`) collides with one already recorded in `objValidationState.arrInputKeys` for the same unit — an easily attacker-controlled condition requiring only crafting two issue inputs with identical asset/denomination/address/serial_number inside the same message. This makes the path directly and cheaply reachable by any unprivileged unit poster.

### Recommendation
Change line 2358 from `return callback("input "+input_key+" already used");` to `return cb("input "+input_key+" already used");`, matching every other error path in this `switch` block, so the error is correctly propagated through `async.forEachOfSeries` and the whole `validatePaymentInputsAndOutputs` pipeline terminates deterministically exactly once via the outer `callback`.

### Proof of Concept
1. Construct a unit with an asset payment message containing two `issue`-type inputs in `payload.inputs`, both with identical `payload.asset` (or base), `denomination`, `address`, and `serial_number`.
2. Submit the unit for validation via `validate()` → `validateMessage()` → `validatePayment()` → `validatePaymentInputsAndOutputs()`.
3. On processing the second colliding issue input, the `indexOf` check at line 2357 matches, and `callback(...)` is called directly instead of `cb(...)`.
4. Observe that the `async.forEachOfSeries` iteration never resolves normally (its `cb` is never called for this item), while the outer `callback` fires out-of-band — verify via instrumentation/logging that `validate()`'s `async.series` completion handler in `validation.js` lines 447-491 is invoked in an unexpected state or not at all, demonstrating the control-flow break described above.
