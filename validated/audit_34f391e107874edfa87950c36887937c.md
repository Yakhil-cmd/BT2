Confirmed: `verify_signature` in `WebhooksController` only checks that the signature is valid for the `webhook_secret` of `repository_owner` derived from the payload's own `repository.owner.login` field, using `Shipit.github(organization: repository_owner).verify_webhook_signature`.### Title
Cross-tenant status injection via unscoped `Commit.where(sha:)` in `StatusHandler` - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` only proves that the payload was signed with the `webhook_secret` belonging to the organization named in the payload's own `repository.owner.login` field, it says nothing about which stack's data the handler is allowed to mutate. `StatusHandler#process` ignores repository/stack scoping entirely and looks up commits purely by `sha` across the whole database, so a validly-signed webhook from repository B can write a `Status` onto any commit in any other stack A that happens to share the same `sha`.

### Finding Description
The broken binding, stated as an equality that the code fails to enforce: `signature_scope(webhook_secret) == B` must imply `mutated_stack == B`, but the code only guarantees `signature_scope(webhook_secret) == B` and never checks `mutated_stack == B`.

Path:
1. `Shipit::WebhooksController#verify_signature` resolves the GitHub App/secret using `repository_owner`, which is read straight from the untrusted payload (`params.dig('repository', 'owner', 'login')`), and verifies the HMAC against that org's `webhook_secret`. [1](#0-0) [2](#0-1) 
2. On success, `create` dispatches the raw parsed JSON body to every handler registered for the `status` event, with no additional binding of the payload's repository to the handler's target. [3](#0-2) 
3. `Shipit::Webhooks::Handlers::StatusHandler#process` looks up commits solely by `sha`, with no filter on `stack_id`, `repository`, or `full_name`: [4](#0-3) 
4. The base `Handler` class actually provides a `stacks` helper that scopes lookups to the repository named in the payload (`Repository.from_github_repo_name(repository_name)&.stacks`), but `StatusHandler` does not use it — it bypasses this scoping mechanism entirely and queries `Commit` globally. [5](#0-4) 
5. `Commit#create_status_from_github!` then creates a `Status` and fires hooks/continuous-delivery scheduling for whatever stack owns that commit, regardless of which repository's secret validated the request. [6](#0-5) 

Attacker's exact request: attacker owns repo B and legitimately configures a GitHub App/webhook on B per `docs/setup.md`, obtaining B's real `webhook_secret`. They compute a correct `X-Hub-Signature` over a crafted JSON body `{"repository": {"owner": {"login": "B-owner"}}, "sha": "<sha of a commit that also exists in stack A>", "state": "success", ...}` and POST it to `/webhooks` with `X-GitHub-Event: status`. Because commit SHAs are content-addressed (parent hash + tree + author/committer + message + timestamps), a commit that is shared history between a victim's stack A and an attacker-controlled fork/repo B (a very common scenario for forks or shared upstream branches) will have an identical `sha` in both `Commit` rows if Shipit has synced both repositories. `verify_signature` passes because it only validates the signature against B's secret; `StatusHandler` then matches and mutates the commit belonging to A's stack.

This defeats `WEBHOOK_PROVENANCE`: the org that signed (B) is not checked against the org whose stack is written to (A). None of the existing guards catch this — `verify_signature` checks a different equality (payload owner vs. secret owner, both attacker-controlled/self-consistent for B), `drop_unhandled_event` only filters unregistered event names, and the `ExplicitParameters` schema in `StatusHandler.params` validates the *shape* of `sha`/`state` but not repository ownership.

### Impact Explanation
An attacker who fully controls only repository B can, with a legitimately obtained webhook secret for B, inject arbitrary CI/commit statuses (`success`, `pending`, `failure`, `error`, with attacker-chosen `description`/`target_url`/`context`) onto commits belonging to a completely unrelated stack A, as long as sha collision/sharing exists (e.g., shared commit history via fork, cherry-pick, or identical patch/parent chain). Because `create_status_from_github!` drives `deployable?`/`blocked?` logic and schedules `ContinuousDeliveryJob` for A's stack, this can be leveraged to force a commit in A to appear `success` and trigger continuous deployment or unblock a merge queue — i.e., a payload for one repository (B) mutating another's (A) stack/commit state and potentially triggering an unauthorized deploy. This matches the Critical category ("payload for one repository mutating another's stack, commit, task or team, or an unauthorized deploy"). The attack is repeatable against any stack A whose commit history intersects with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the attacker needs their own GitHub App/webhook installation on a repo B they own (self-service, per `docs/setup.md`), and a commit `sha` that is present both in B and in victim stack A's `Commit` table. This is realistic when A is a public/open-source project and B is a fork or a repo that shares commit ancestry with A (git SHAs are identical across clones/forks for identical commits). No Shipit session, API token, or victim secret is required — only the attacker's own legitimately-issued secret for B. Cost is low: standard GitHub App setup plus one crafted, self-signed HTTP request.

### Recommendation
In `StatusHandler#process` (and any other handler that queries by `sha` alone), scope the lookup to the repository that signed the request, e.g. use the base `Handler#stacks` helper (`stacks.commits.where(sha: params.sha)`) instead of the global `Commit.where(sha: params.sha)`, so a status update can only touch commits belonging to stacks of the repository named (and cryptographically bound) in the verified payload.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb (illustrative addition)
test ":status from repo B's signed webhook must not mutate stack A's commit" do
  stack_a = shipit_stacks(:shipit)          # victim stack, owner "shopify"
  commit_a = shipit_commits(:first)         # belongs to stack_a
  # Simulate a commit with the SAME sha existing under attacker-owned repo B
  # (shared history / fork scenario) — for the PoC, directly reuse commit_a.sha
  # while the signed payload's repository.owner.login is a different org ("attacker-org").

  body = {
    "sha" => commit_a.sha,
    "state" => "success",
    "description" => "forged",
    "context" => "attacker/ci",
    "repository" => { "owner" => { "login" => "attacker-org" }, "full_name" => "attacker-org/repoB" }
  }.to_json

  signature = "sha1=" + OpenSSL::HMAC.hexdigest("sha1", "attacker-org-secret", body)
  GitHubApp.any_instance.stubs(:verify_webhook_signature).returns(true) # simulating a correctly-signed B request

  assert_difference -> { commit_a.statuses.count }, 1 do
    request.headers['X-Github-Event'] = 'status'
    post :create, body: body, as: :json
  end

  # Equality check per the finding: signature scope was "attacker-org" (B),
  # but the mutated stack/commit belongs to "shopify" (A) — this must not happen.
  assert_equal 'attacker-org', JSON.parse(body).dig('repository', 'owner', 'login')
  assert_not_equal 'attacker-org', commit_a.stack.repository.owner
  assert_response :ok
end
