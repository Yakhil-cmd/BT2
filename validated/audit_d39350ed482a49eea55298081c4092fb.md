### Title
Cross-repository commit-status forgery via `StatusHandler` — the organization authenticated by `verify_signature` is never bound to the stack/commit that gets written - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` picks a GitHub organization's webhook secret solely from the attacker-supplied `repository`/`organization` field of the payload and checks the HMAC against *that* organization's secret. `StatusHandler#process`, however, never re-checks that field: it looks up target `Commit` rows purely by `params.sha`, with zero scoping to the repository/organization whose signature was actually verified. Any Shipit user who legitimately owns one connected GitHub org/repo (and therefore knows its webhook secret) can forge a validly-signed `status` webhook that references a commit `sha` belonging to a completely different, unrelated stack, and have Shipit write a fabricated CI status onto that victim commit — potentially triggering an unauthorized deploy via continuous deployment.

### Finding Description
This is the same class of bug as the Cooler report: the code authenticates one identity (the loan's claimed originator / here, the payload's `repository.owner.login`) but then acts on a resource (the defaulted loan's collateral / here, the `Commit` row) without verifying the two are the same entity.

- `WebhooksController#verify_signature` derives the org used to fetch the webhook secret exclusively from the JSON payload, not from any authenticated/pinned source: [1](#0-0) [2](#0-1) 

- The base `Handler` class exposes a properly-scoped `stacks` helper that filters by `Repository.from_github_repo_name(repository_name)` (used by `PushHandler` and the PR handlers): [3](#0-2) [4](#0-3) 

- `StatusHandler`, however, ignores this scoping entirely and resolves commits purely by `sha`, globally, across every repository/stack tracked by the Shipit instance: [5](#0-4) 

Equality that should hold but doesn't: `organization_whose_secret_verified_signature == organization_owning_the_commit_being_mutated`. Before the attack: the invariant "a `status` webhook can only affect commits belonging to the repository/org whose secret validated the signature" holds only by convention, never by code. After the attack: the attacker (owner of `attacker-org`, a legitimately connected but low-privilege org) sends a `status` event whose `repository.owner.login` is `attacker-org` (so `Shipit.github(organization: 'attacker-org')` is used to verify the HMAC, which the attacker can compute because it's their own configured secret) but whose `sha` is a public commit SHA belonging to `victim-org/victim-repo`'s stack (SHAs are public, obtainable from the victim's GitHub history). `Commit.where(sha: params.sha)` finds the victim's `Commit` row regardless of which org supposedly sent the event, and `commit.create_status_from_github!(params)` writes a forged status (e.g. `state: 'success'`, `context:` matching the victim's `required_statuses`) onto it.

### Impact Explanation
If the victim stack has `continuous_deployment: true` (or is otherwise gated on required commit statuses becoming green), completing the last required status via this forged event can trigger `Commit`'s deploy-triggering flow (`schedule_continuous_delivery`/`trigger_deploy`), i.e., an **unauthorized deploy** on a stack the attacker has no access to — one of the explicitly listed Critical impacts. Even without triggering a deploy, it lets an unprivileged party pollute another organization's commit/CI status history and deployable-state gating, undermining the integrity guarantee that only the owning org's CI can report status for its commits.

### Likelihood Explanation
Requires only: (1) the attacker legitimately administers/owns any GitHub organization or repository that is connected to the same Shipit instance (a normal, unprivileged, multi-tenant scenario the engine explicitly supports via per-organization `Shipit.github(organization:)` configuration), and (2) knowledge of a public commit SHA from the victim repository (trivially obtainable from GitHub). No access to the victim's webhook secret, API token, or GitHub credentials is needed. This is directly reachable through the public, unauthenticated `WebhooksController#create` endpoint.

### Recommendation
In `StatusHandler#process` (and any other handler that doesn't already use `Handler#stacks`), scope the `Commit` lookup by the repository resolved from the same `repository.full_name`/`repository.owner.login` that was used to verify the signature, e.g. `stacks.commits.where(sha: params.sha)` instead of the unscoped `Commit.where(sha: params.sha)`. More generally, `WebhooksController` should bind the verified organization to the payload's repository consistently, and every handler should re-derive its target `Stack`/`Commit`/`Repository` scope from the *verified* organization rather than trusting the raw payload fields independently.

### Proof of Concept
1. Attacker owns/administers `attacker-org`, which has a Shipit-connected repo with its own webhook secret (`Shipit.github(organization: 'attacker-org')` config), which the attacker knows because they configured it.
2. Attacker finds a public commit SHA `S` belonging to `victim-org/victim-repo`, tracked by a Shipit stack with `continuous_deployment: true` and a `required_statuses` context of `ci/travis`.
3. Attacker builds payload:
   ```json
   {
     "sha": "S",
     "state": "success",
     "context": "ci/travis",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/decoy" }
   }
   ```
4. Attacker computes `X-Hub-Signature` using `attacker-org`'s known webhook secret and POSTs to `/github/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` calls `Shipit.github(organization: 'attacker-org')`, verification succeeds (attacker's own secret).
6. `StatusHandler#process` runs `Commit.where(sha: 'S')`, finds the victim's `Commit`, and calls `commit.create_status_from_github!(params)`, marking it `success` for `ci/travis` — potentially completing the victim stack's deploy criteria and triggering an unauthorized production deploy, entirely outside `victim-org`'s control.
