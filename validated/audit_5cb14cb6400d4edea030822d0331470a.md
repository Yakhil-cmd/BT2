### Title
Unbounded per-asset balance iteration in AA trigger processing enables balance-table bloat DoS - (File: aa_composer.js)

### Summary
`aa_composer.js`'s `updateInitialAABalances` (inside `handleTrigger`) unconditionally loads **every** asset balance row ever recorded for the triggered AA address with `SELECT asset, balance FROM aa_balances WHERE address=?` and then iterates over all returned rows on every single trigger, regardless of which asset the current trigger actually concerns. [1](#0-0) 

### Finding Description
Any unprivileged user can issue a new asset (`asset` message) and send even a dust amount of it to a target AA address. `handleTrigger`'s `updateInitialAABalances` inserts a permanent row into `aa_balances` for every new asset ever received by that address: [2](#0-1) 

These rows are never pruned — even zero-balance assets remain forever, as also seen when `updateFinalAABalances` inserts placeholder rows for new assets touched by AA responses: [3](#0-2) 

Because `updateInitialAABalances` fetches and loops through the **entire** `aa_balances` row set for the address on every subsequent trigger (not just the asset(s) present in the current trigger's outputs), an attacker can grow this row set arbitrarily by repeatedly issuing new assets and sending negligible amounts of each to the same AA. Every future trigger to that AA then pays the ever-increasing cost of reading and iterating all these balances — this is the same bug class as the reported `GetAllBalances` issue: an unbounded, attacker-inflatable enumeration of an address's balances performed inside a critical execution path, instead of looking up only the specific denom(s)/assets actually needed for that operation. [4](#0-3) 

### Impact Explanation
AA trigger processing occurs during main-chain stabilization as units are confirmed (`handlePrimaryAATrigger`), which is on the hot path of unit/DAG stability determination. [5](#0-4) 

By continually spamming a target AA with dust payments of many distinct, cheaply-issued assets, an attacker can make `aa_balances` for that address grow without bound, causing the `SELECT ... WHERE address=?` and the following `rows.forEach` loop to become slower with every trigger. Because this happens synchronously inside the AA-response computation for every future trigger sent to that AA, it degrades processing time for any user interacting with the affected AA, and in aggregate for nodes stabilizing units that invoke it — directly analogous to the reported "node unable to process/confirm" impact.

### Likelihood Explanation
No cap exists on the number of distinct assets an address can accumulate in `aa_balances`, and asset issuance combined with a payment message to an arbitrary AA is a normal, unprivileged action available to any user. The attack requires no special access — only the ability to post units, which is the baseline capability of any wallet holder.

### Recommendation
Avoid loading the full set of balances for an address inside `updateInitialAABalances`. Instead, query `aa_balances` only for the specific asset(s) referenced by `trigger.outputs` (i.e., build/compare balances denom-by-denom, similar to the recommended `GetBalance`-per-denom fix), and consider capping/pruning zero-balance or long-unused asset rows so the table cannot be grown unboundedly by dust-asset spam.

### Proof of Concept
1. Attacker issues N distinct new assets (cheap, unprivileged operation).
2. For each asset, attacker sends 1 unit of that asset to a target AA address, causing `updateInitialAABalances`/`updateFinalAABalances` to permanently insert a new row into `aa_balances` for that address. [2](#0-1) 
3. Repeating this thousands of times causes `aa_balances` rows for the AA address to grow unbounded.
4. Any subsequent legitimate trigger to that AA now must execute `SELECT asset, balance FROM aa_balances WHERE address=?` and iterate all N+ rows in `rows.forEach`, imposing growing latency on every future invocation of that AA and on unit stabilization involving it. [1](#0-0)
