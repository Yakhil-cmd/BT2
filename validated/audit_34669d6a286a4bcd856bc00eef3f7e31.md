### Title
Webhook signature verification keyed on `repository.owner.login`, but event handlers act on the unrelated `repository.full_name` field, letting any tenant org forge events for another tracked repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App (and therefore which `webhook_secret`) to verify the HMAC signature against using `repository_owner`, which is read from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature is accepted, `WebhooksController#create` hands the *entire* raw JSON body to the registered `Shipit::Webhooks::Handlers::*`, which locate the target `Repository`/`Stack` using a completely different, unauthenticated field: `payload.dig('repository', 'full_name')`. Nothing cross-checks that the organization whose secret produced a valid signature is the same organization/repository the handlers actually act on. [1](#0-0) [2](#0-1) 

### Finding Description
The engine is multi-tenant: each GitHub organization tracked by Shipit has its own `Shipit.github(organization:)` config with its own `webhook_secret` (see `config/secrets.development.shopify.yml`). `verify_signature` picks the config to check against using `repository_owner`:

```
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  head(422) unless verified
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
``` [1](#0-0) 

`verify_webhook_signature` is a standard HMAC-SHA1 comparison over the raw POST body using the secret belonging to whichever org `repository_owner` names:

```
def verify_webhook_signature(signature, message)
  return true unless webhook_secret
  algorithm, signature = signature.split("=", 2)
  return false unless algorithm == 'sha1'
  SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
end
``` [3](#0-2) 

Once verification succeeds, `create` dispatches the full payload to every handler registered for the event:

```
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
``` [4](#0-3) 

Every handler (`PushHandler`, `StatusHandler`, pull-request handlers, etc.) resolves the target `Repository`/`Stack` from `repository.full_name`, not from `repository.owner.login`:

```
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
``` [2](#0-1) 

`PushHandler`, for example, then immediately triggers a GitHub sync for every matching, non-archived stack:

```
def process
  stacks.not_archived.where(branch:).find_each { |stack| stack.sync_github(expected_head_sha: params.after) }
end
``` [5](#0-4) 

Because `owner.login` (used to pick the signing key) and `full_name` (used to pick the acted-upon repository) are two independent JSON fields inside the same signed body, an attacker who legitimately administers *any* GitHub organization already onboarded to this Shipit instance (and therefore knows that org's `webhook_secret`, exactly as a normal customer of a multi-tenant install would) can:

1. Build a JSON payload where `repository.owner.login = "attacker-org"` (so `repository_owner` resolves to their own org and thus their own known `webhook_secret`) but `repository.full_name = "victim-org/victim-repo"`.
2. Sign that exact byte sequence with their own `webhook_secret` — a computation they can perform offline, exactly as CVE-2022-27780 let an attacker construct a URL that parses one way for the security check and a different way for the actual request.
3. POST it to the shared `/webhooks` endpoint (routes.rb) with the correct `X-Hub-Signature`. `verify_signature` succeeds because the secret used really does match `repository_owner`.
4. The handler dispatch then acts on `victim-org/victim-repo`, an organization/repo the attacker never authenticated against.

This breaks exactly the binding class called out in the rules: *"an organization that authenticated versus the repository that is written."*

### Impact Explanation
This is an authentication-bypass style vulnerability: the security control (webhook HMAC verification against a specific GitHub App's secret) is checked against one field while the acted-upon resource is chosen from a different, unauthenticated field of the same payload. Concretely:
- `PushHandler` lets the forger cause `stack.sync_github` to run for an arbitrary tracked victim stack/branch on demand, using Shipit's own GitHub credentials for the victim org (`Shipit.github(organization: repository.owner)`), effectively an unauthorized trigger of the victim's sync/deploy pipeline logic.
- Other handlers keyed off the same unauthenticated `full_name`/`sha` fields (e.g. the `status` handler, confirmed by `test/controllers/webhooks_controller_test.rb`'s `":state create a Status for the specific commit"` test, which creates a `Status` for a commit purely from payload fields) allow a forged CI status on a victim's commit. Since `Commit#deployable?` is driven directly by commit status state (`success? && !blocked?`) and `Stack#trigger_continuous_delivery` fires automatically once a commit becomes deployable, this chain can escalate into unauthorized deploys/continuous delivery being triggered for a victim's stack. [6](#0-5) [7](#0-6) 

### Likelihood Explanation
Exploitation requires only that the attacker administers (or has webhook_secret access to) any one GitHub organization/app already configured in this Shipit instance's multi-tenant `Shipit.github` config — no privileged Shipit account, `ApiClient` token, or access to the victim org is needed. Computing a valid HMAC over an attacker-chosen payload with a key they legitimately possess is trivial and directly analogous to the report's premise (a value that passes a security-relevant parse/check differs from the value actually acted upon downstream).

### Recommendation
In `WebhooksController#verify_signature`/`create`, after signature verification succeeds, assert that the verified organization actually owns the repository referenced by `repository.full_name` (and any other repo-identifying fields consumed by handlers) before dispatching to handlers — e.g., require `params.dig('repository','full_name').split('/').first.casecmp?(repository_owner)`, or better, resolve `Repository.from_github_repo_name(full_name)` and reject the request if that repository's `owner` doesn't match the app/org whose secret validated the signature.

### Proof of Concept
1. Shipit is configured (per `config/secrets.*.yml`) with two GitHub Apps/orgs: `attacker-org` (secret known to the attacker, who legitimately administers that org) and `victim-org/victim-repo` (a stack tracked by Shipit).
2. Attacker crafts a `push` webhook JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen sha already present in victim's commit history>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(attacker-org's webhook_secret, <body>)`.
4. Attacker POSTs to `/webhooks` with this body/header. `verify_signature` calls `Shipit.github(organization: "attacker-org")`, whose secret matches, so verification passes.
5. `Shipit::Webhooks::Handlers::PushHandler` resolves `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: ...)` for the victim's stack, despite the attacker never having authenticated as `victim-org`.
