Based on my investigation, I found a structural analog to the reported vulnerability class (incorrect block-time assumption used to compute block-count-based time periods) in this codebase's shared constants module.

### Title
Mismatched block-time assumption between `async_backing` time constants and Asset Hub Kusama's actual Aura slot duration causes incorrect block-count-based period calculations - (File: `system-parachains/constants/src/lib.rs`)

### Summary
The reported Maia bug used an incorrect seconds-per-block assumption (15s instead of Ethereum's actual 12s) to convert human-readable durations ("2 weeks") into block counts, corrupting `MIN/MAX_VOTING_PERIOD`/`MIN/MAX_VOTING_DELAY`. The analogous pattern exists in `system-parachains/constants/src/lib.rs`, where a secondary `async_backing` constants module defines `MINUTES`/`HOURS`/`DAYS` using a `MILLISECS_PER_BLOCK` of `6_000` ms, while Asset Hub Kusama's runtime explicitly declares and documents its actual Aura slot duration as `24_000` ms and imports its `HOURS` constant from this very `async_backing` module.

### Finding Description
`system-parachains/constants/src/lib.rs` defines two separate time-unit modules: [1](#0-0) 
- the top-level module assumes `MILLISECS_PER_BLOCK = 12_000` and derives `MINUTES`/`HOURS`/`DAYS` from it;
- the `async_backing` submodule instead assumes `MILLISECS_PER_BLOCK = 6_000` (while its own `SLOT_DURATION` constant is `12_000`, already an internal inconsistency), and derives its own `MINUTES`/`HOURS`/`DAYS` from that 6-second figure: [2](#0-1) 

Asset Hub Kusama's runtime, however, explicitly documents and sets its actual Aura slot duration to 24 seconds: [3](#0-2) 

Yet it imports the `HOURS` (and other period-derived) constant from the `async_backing` module — the one computed assuming 6-second blocks — rather than from a module reflecting its own real 24-second block time: [4](#0-3) 

This is structurally the same root cause as the Maia report: a hardcoded/assumed block-formation time (6s) used to derive block-count time constants (`HOURS`, `MINUTES`, `DAYS`) that is inconsistent with the chain's actual, documented block-production interval (24s) — a 4x discrepancy, analogous to the 15s-vs-12s (1.25x) discrepancy in the original finding.

### Impact Explanation
Because `HOURS` (and any downstream `DAYS`/`MINUTES` derived from it) is computed assuming 6-second blocks but the chain actually produces one block every 24 seconds, any parameter expressed in these units (e.g., `N * HOURS` used for session lengths, staking periods, or other block-number-denominated durations) will represent 4x less real wall-clock time than intended when it elapses in terms of block count — i.e., a period nominally meant to be "N hours" will actually only take N/4 hours of real time to elapse in block count, or conversely will require 4x the wall-clock time versus what was intended if interpreted the other way, depending on which direction the mismatch is exploited. This mirrors the Maia issue's impact: state-transition/timing logic (e.g., validity windows, admin periods) is silently wrong.

### Likelihood Explanation
I was not able to fully enumerate every consumer of the `HOURS` constant imported in `asset-hub-kusama/src/lib.rs` within the remaining tool budget, so I cannot confirm with certainty which specific pallet configuration(s) (e.g., session length, staking period, vesting) consume this drifted value, nor whether this 24s slot duration is a legacy/pre-async-backing state intentionally paired with pre-async-backing constants elsewhere in the file that I did not fully trace. This is a configuration-level constant mismatch reachable by anyone observing/relying on on-chain timing (not requiring a privileged role to trigger), but the exact blast radius depends on which parameter(s) actually consume the miscalculated `HOURS` constant, which I could not fully verify given the remaining investigation budget.

### Recommendation
Verify every constant consumed from `system_parachains_constants::async_backing` in `asset-hub-kusama/src/lib.rs` (and any other runtime importing from the same module) matches that runtime's actual, current Aura `SLOT_DURATION`. Either derive `HOURS`/`MINUTES`/`DAYS` locally from the runtime's own `SLOT_DURATION` constant, or ensure the `async_backing` module's `MILLISECS_PER_BLOCK` is only imported by runtimes that have actually migrated to the corresponding block time it assumes.

### Proof of Concept
1. `system-parachains/constants/src/lib.rs:73` sets `async_backing::MILLISECS_PER_BLOCK = 6_000`, deriving `HOURS = 600` blocks/hour (`60_000/6_000*60`). [5](#0-4) 
2. `system-parachains/asset-hubs/asset-hub-kusama/src/lib.rs:167` documents/declares the runtime's actual `SLOT_DURATION = 24_000` ms (24s/block), a 4x difference from the assumption baked into `async_backing::HOURS`. [3](#0-2) 
3. The same file imports `HOURS` from `async_backing` at lines 108-110, so any parameter defined as `N * HOURS` in this runtime represents `N * 600` blocks, which at the real 24s block time equals `N * 4` real hours instead of `N` real hours. [6](#0-5) 

Note: due to the tool-call budget being exhausted, I could not trace every downstream parameter definition inside `asset-hub-kusama/src/lib.rs` that consumes this `HOURS` constant to give a concrete example of the affected pallet/parameter — a Devin session with full file access would be needed to enumerate all consumers and confirm the precise on-chain parameter(s) affected.
