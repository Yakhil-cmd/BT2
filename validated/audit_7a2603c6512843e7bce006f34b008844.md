### Title
Third-party supply can force a collateral risk refresh and liquidation - ([File: contracts/controller/src/positions/supply.rs])

### Summary
`Controller::supply` permits an arbitrary caller to deposit into an existing supply position on another account, requiring only that the market already appears in `account.supply_positions`. [1](#0-0)  The merge path refreshes the position’s full cached risk tuple, including its listed LTV/liquidation parameters, before writing the enlarged position. [2](#0-1)  Because ordinary supply does not run the post-operation solvency gate, a dust top-up can therefore move a foreign account onto newly tightened risk parameters while leaving it unhealthy. [3](#0-2) 

### Finding Description
`process_supply` authenticates the supplied `caller`, but does not require that caller to own or control a nonzero target account. [4](#0-3)  Its only third-party restriction is that every submitted `HubAssetKey` already exists in the victim’s `supply_positions` map. [1](#0-0) 

After the deposit, `merge_supply_leg` calls `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple` on the victim’s preexisting position. [2](#0-1)  Consequently, a minimal measured deposit into each existing collateral market can restamp that collateral with the current, potentially lower liquidation threshold without requiring account-owner authorization. [5](#0-4) 

The caller can then invoke the permissionless `liquidate` entrypoint once the refreshed cached parameters produce a health factor below one. [6](#0-5) 

### Impact Explanation
An attacker can force a victim’s collateral positions onto tightened risk parameters and immediately liquidate the account, receiving collateral through `SeizeMode::Transfer` or credited shares through `SeizeMode::Credit`. [7](#0-6)  This converts a nominal third-party donation into theft of liquidation bonus and forced loss of user collateral. [1](#0-0) 

### Likelihood Explanation
The attack needs a target with existing supply positions and a listed configuration change that lowers the relevant collateral LTV or liquidation threshold. [8](#0-7)  Once those conditions exist, any unprivileged address can execute it by transferring a minimal positive amount of each already-held collateral asset; no owner, delegate, or privileged role is required. [9](#0-8) 

### Recommendation
Prevent third-party top-ups from refreshing an existing position’s full risk tuple: preserve the victim’s cached parameters when `caller` is neither owner nor delegate, or restrict foreign-account `supply` entirely. [10](#0-9)  If third-party top-ups remain supported, separate the accounting update from `RiskRefreshScope::FullTuple` and add a regression test showing that a foreign dust deposit cannot reduce the target’s health factor. [11](#0-10) 

### Proof of Concept
1. Victim account `A` has existing supply positions for `C1` and `C2`, cached under older liquidation parameters.
2. Governance lists a tighter risk configuration for `C1`/`C2`, leaving `A` healthy only under its cached parameters.
3. Attacker calls `supply(caller=attacker, account_id=A, spoke_id=A.spoke_id, assets=[(C1, dust), (C2, dust)])`; both markets pass because they already exist in `A.supply_positions`. [1](#0-0) 
4. `process_deposit` pulls the dust transfers and `merge_supply_leg` restamps each victim position using `RiskRefreshScope::FullTuple`. [5](#0-4) 
5. The supply flow returns without `enforce_post_pool_solvency`, so the now-undercollateralized account remains stored. [3](#0-2) 
6. Attacker calls `liquidate(liquidator=attacker, account_id=A, debt_payments=planned_debt, seize_mode=SeizeMode::Transfer)` and seizes victim collateral once the refreshed health factor is below one. [6](#0-5)

fn require_third_party_existing_supply(
    env: &Env,
    account_id: u64,
    resolved_account_id: u64,
    caller: &Address,
    account: &Account,
    aggregated: &AggregatedPayments,
) {
    if account_id != 0
        && !account::is_owner_or_delegate(env, resolved_account_id, caller, &account.owner)
    {
        for (hub_asset, _) in aggregated.iter() {
            assert_with_error!(
                env,
                account.supply_positions.contains_key(hub_asset.clone()),
                GenericError::NotAuthorized
            );
        }
    }
}
