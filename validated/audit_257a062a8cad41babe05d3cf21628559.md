### Title
CLStakingInfo Overwrite in `consolidateNodes()` Silently Zeroes First CL Pool's KAIA Staking Reward — (`kaiax/staking/staking_info.go`)

---

### Summary

In `consolidateNodes()`, when two NodeIds that share the same `RewardAddr` both have `CLStakingInfo` entries, the second entry silently overwrites the first via a plain `=` assignment. The `Split()` function then uses the corrupted `consolidatedNode` to divide every block's staking reward, causing the first CL pool to receive zero KAIA while the second CL pool and the CN reward address receive disproportionately larger shares.

---

### Finding Description

`consolidateNodes()` merges AddressBook entries that share a `RewardAddr` into a single `consolidatedNode`, correctly **accumulating** `StakingAmount` with `+=`. However, when it attaches `CLStakingInfo` entries (Prague hardfork), it uses plain assignment:

```go
// kaiax/staking/staking_info.go  line 155-158
if r, ok := nToR[clsi.CLNodeId]; ok {
    // One CLStakingInfo per validator is guaranteed by CLRegistry.
    cmap[r].CLStakingInfo = clsi   // ← overwrites, does not accumulate
}
``` [1](#0-0) 

The CLRegistry guarantees **one CL per NodeId**, not one CL per `RewardAddr`. AddressBook explicitly supports multiple NodeIds sharing the same `RewardAddr` (the consolidation feature). If NodeIds `n1` and `n3` both map to `RewardAddr r1`, and both have `CLStakingInfo` entries in CLRegistry, the second entry (`n3`'s) silently overwrites the first (`n1`'s):

```
Before consolidation:
  n1 → r1, StakingAmount=A1, CLStakingInfo={clPool1, X}
  n3 → r1, StakingAmount=A3, CLStakingInfo={clPool2, Y}

After consolidateNodes():
  consolidatedNode{r1, StakingAmount=A1+A3, CLStakingInfo={clPool2, Y}}
  ← clPool1 and amount X are silently dropped
``` [2](#0-1) 

The test suite explicitly exercises this path and documents the silent drop:

```go
// CL1 will be ignored when being consolidated since it has duplicate CL (not feasible in real)
``` [3](#0-2) 

The corrupted `consolidatedNode` is then consumed by `assignStakingRewards` and `assignStakingRewardsFlex`, both of which call `cn.Split(reward)`:

```go
// kaiax/reward/impl/getter.go  lines 521-525
if isPrague && cn.CLStakingInfo != nil {
    cnAmount, clAmount := cn.Split(reward)
    alloc[cn.RewardAddr] = cnAmount
    alloc[cn.CLStakingInfo.CLPoolAddr] = clAmount   // only clPool2 is written
}
``` [4](#0-3) 

`Split()` computes the CL share as `CLStakingAmount / (StakingAmount + CLStakingAmount)`:

```go
// kaiax/staking/staking_info.go  lines 169-186
func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
    cnAmountBig = big.NewInt(int64(c.StakingAmount))          // A1+A3  (correct)
    clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount)) // Y only (wrong)
    totalAmount = cnAmountBig + clAmountBig                   // A1+A3+Y (wrong, missing X)
    clAmount = clAmountBig * amount / totalAmount
    cnAmount = amount - clAmount
    return cnAmount, clAmount
}
``` [5](#0-4) 

Correct vs. actual per-block distribution for the affected consolidated node:

| Recipient | Correct | Actual |
|-----------|---------|--------|
| `clPool1` | `X/(A1+A3+X+Y) × reward` | **0** |
| `clPool2` | `Y/(A1+A3+X+Y) × reward` | `Y/(A1+A3+Y) × reward` (inflated) |
| `r1` (CN) | `(A1+A3)/(A1+A3+X+Y) × reward` | `(A1+A3)/(A1+A3+Y) × reward` (inflated) |

The corrupted allocation is applied in `FinalizeState` via `state.AddBalance` at every block: [6](#0-5) 

---

### Impact Explanation

**Impact: High** — Every block that distributes staking rewards, `clPool1` receives zero KAIA instead of its proportional share. The lost KAIA is silently redistributed to `clPool2` and `r1`. This is an unauthorized redistribution of KAIA staking rewards affecting the Prague hardfork reward path (`getDeferredRewardFullKore` / `getDeferredRewardFullFlex`). [7](#0-6) 

---

### Likelihood Explanation

**Likelihood: Medium** — The trigger requires a validator to:
1. Register two or more NodeIds in AddressBook pointing to the same `RewardAddr` (explicitly supported and documented as the consolidation feature).
2. Register `CLStakingInfo` entries in CLRegistry for more than one of those NodeIds.

The developer comment "not feasible in real" relies on an informal assumption that validators will not register CL entries for multiple NodeIds sharing a `RewardAddr`. There is no on-chain enforcement preventing it. As Prague CL adoption grows, this configuration becomes increasingly likely.

---

### Recommendation

In `consolidateNodes()`, instead of overwriting `CLStakingInfo`, detect the collision and handle it explicitly. The minimal safe fix is to accumulate `CLStakingAmount` into the existing entry when both NodeIds share the same `CLPoolAddr`, or to reject/log the second entry when the pool addresses differ (since `Split()` only supports a single `CLPoolAddr`). A more complete fix extends `consolidatedNode` to hold a slice of `CLStakingInfo` and updates `Split()` accordingly. [8](#0-7) 

---

### Proof of Concept

1. Deploy AddressBook with two NodeIds `n1`, `n3` both pointing to `RewardAddr r1` (standard multi-NodeId validator setup).
2. Register `CLStakingInfo{CLNodeId: n1, CLPoolAddr: clPool1, CLStakingAmount: X}` in CLRegistry.
3. Register `CLStakingInfo{CLNodeId: n3, CLPoolAddr: clPool2, CLStakingAmount: Y}` in CLRegistry.
4. At the next staking update interval, `StakingInfo.CLStakingInfos` contains both entries.
5. `consolidateNodes()` processes n1's entry first (`cmap[r1].CLStakingInfo = {clPool1, X}`), then overwrites with n3's entry (`cmap[r1].CLStakingInfo = {clPool2, Y}`).
6. Every subsequent block: `FinalizeState` → `GetDeferredReward` → `assignStakingRewards` → `Split()` distributes `0` to `clPool1` and an inflated share to `clPool2` and `r1`.
7. `clPool1` accumulates zero KAIA staking rewards indefinitely despite having `X` KAIA staked.

func (si *StakingInfo) consolidateNodes() *[]consolidatedNode {
	// because Go map is not ordered, rList keeps track of the occurrence order of RewardAddrs.
	// to later arrange the consolidatedNodes.
	cmap := make(map[common.Address]*consolidatedNode)
	rList := make([]common.Address, 0, len(si.RewardAddrs))
	nToR := make(map[common.Address]common.Address)

	for i, n := range si.NodeIds {
		r := si.RewardAddrs[i]
		// Unique nodeId is guaranteed by AddressBook.
		nToR[n] = r
		if cn, ok := cmap[r]; ok {
			cn.NodeIds = append(cn.NodeIds, n)
			cn.StakingContracts = append(cn.StakingContracts, si.StakingContracts[i])
			cn.StakingAmount += si.StakingAmounts[i]
		} else {
			cmap[r] = &consolidatedNode{
				NodeIds:          []common.Address{n},
				StakingContracts: []common.Address{si.StakingContracts[i]},
				RewardAddr:       r,
				StakingAmount:    si.StakingAmounts[i],
			}
			rList = append(rList, r)
		}
	}

	// CLStakingInfo can only exist after Prague HF.
	if len(si.CLStakingInfos) > 0 {
		for _, clsi := range si.CLStakingInfos {
			// If the nodeId of CLStakingInfo is not found in nToR, it means the validator is not in the AddressBook.
			// So we skip it.
			if r, ok := nToR[clsi.CLNodeId]; ok {
				// One CLStakingInfo per validator is guaranteed by CLRegistry.
				cmap[r].CLStakingInfo = clsi
			}
		}
	}

	carr := make([]consolidatedNode, 0, len(cmap))
	for _, r := range rList {
		carr = append(carr, *cmap[r])
	}
	return &carr
}

func (c consolidatedNode) Split(amount *big.Int) (*big.Int, *big.Int) {
	if c.CLStakingInfo == nil {
		return amount, big.NewInt(0)
	}

	var (
		cnAmountBig = big.NewInt(int64(c.StakingAmount))
		clAmountBig = big.NewInt(int64(c.CLStakingInfo.CLStakingAmount))
		totalAmount = new(big.Int).Add(cnAmountBig, clAmountBig)
	)

	clAmount := new(big.Int).Mul(clAmountBig, amount)
	clAmount = clAmount.Div(clAmount, totalAmount)

	// The remaining amount is for the CN.
	cnAmount := big.NewInt(0).Sub(amount, clAmount)

	return cnAmount, clAmount
}

// getDeferredRewardFullKore is for non-Simple policy and after Kore.
func getDeferredRewardFullKore(config *reward.RewardConfig, execFee, burntFee, blobFee *big.Int, si *staking.StakingInfo) (*reward.RewardSpec, error) {
	var (
		spec             = reward.NewRewardSpec()
		minted           = new(big.Int).Set(config.MintingAmount)
		distributableFee = new(big.Int).Sub(execFee, burntFee)
	)

	// Distribute using RewardRatio first. Unlike Legacy, fees are not distributed here
	// because fees are exclusively allocated to proposer. By the way, remainder goes to KIF.
	validators, kif, kef := config.RewardRatio.Split(minted)
	proposer, stakers := config.Kip82Ratio.Split(validators)
	ratioRemainder := calcRemainder(minted, proposer, stakers, kif, kef)
	kif.Add(kif, ratioRemainder)

	// Further distribute using Kip82Ratio. By the way, remainder goes to proposer.
	// After Prague, if the CLStaking is not nil, the proposer and staking rewards are proportionally distributed to both CN and CL.
	// For proposer rewards, see `specWithProposerAndFunds`.
	stakersAlloc, kip82Remainder := assignStakingRewards(config, stakers, si)
	proposer.Add(proposer, kip82Remainder)
	stakers.Sub(stakers, kip82Remainder)

	// Proposer gets the fees.
	proposer.Add(proposer, distributableFee)

	spec.Minted = minted
	spec.TotalFee = new(big.Int).Add(execFee, blobFee)
	spec.BurntFee = new(big.Int).Add(burntFee, blobFee)
	spec.Stakers = stakers
	for addr, amount := range stakersAlloc {
		spec.IncRecipient(addr, amount)
	}
	spec = specWithProposerAndFunds(spec, config, proposer, kif, kef, si)
	return spec, nil
}
