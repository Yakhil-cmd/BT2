### Title
`StatusHandler` matches commits by bare SHA across all repositories, letting a webhook for repository B forge Status on unrelated Shipit-tracked repositories - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves target commits with `Commit.where(sha: params.sha)`, completely ignoring the `repository.full_name` field present in the same GitHub `status` payload. Every other handler in the engine (`PushHandler`, `CheckSuiteHandler`) scopes work through the base `Handler#stacks` helper, which resolves `Repository.from_github_repo_name(repository_name)` first, but `StatusHandler` does not. Any `Shipit::Commit` row that shares a SHA with the commit named in the webhook — regardless of which `Shipit::Repository`/`Shipit::Stack` it belongs to — receives a forged `Status`.

### Finding Description
The intended binding is: `Shipit::Commit#sha` scoped by `Shipit::Commit#stack_id` (i.e., `stack.repository == payload.repository`) uniquely identifies the commit a status event applies to. In `StatusHandler`, this is broken: [1](#0-0) 

`Commit.where(sha: params.sha)` is repository-agnostic — it returns every `Shipit::Commit` row across every stack/repository sharing that SHA. Compare with the sibling handlers that correctly scope through the repository: [2](#0-1) [3](#0-2) 

Root cause: `Handler#stacks` exists precisely to enforce this binding via `Repository.from_github_repo_name(repository_name)`, but `StatusHandler` never calls it, even though the GitHub `status` webhook payload includes a `repository.full_name` field the schema could require and filter on.

Exploit path: an attacker who owns/administers one repository B that is already onboarded into a Shipit instance (or any repo within the same GitHub organization whose webhook is routed to the same Shipit `webhook_secret`, per `Shipit.github(organization: repository_owner)` in `app/controllers/shipit/webhooks_controller.rb:24-30`) constructs a commit whose SHA collides with a commit already tracked in an unrelated stack — e.g. by reproducing a shared/templated initial commit's exact tree, parents, author/committer identities and timestamps (fully attacker-controlled fields on their own repo), or by using the canonical empty-tree object as a root commit copied verbatim across repositories. The attacker then sets a real commit status (`success`) on that commit via the GitHub Statuses API on repository B. GitHub signs and delivers a genuine, correctly-signed `status` webhook (the signature only proves "this came from GitHub for this org," not "this pertains only to repository B"). `WebhooksController#verify_signature` passes because the HMAC is valid for the org, and `StatusHandler.process` then updates **every** `Shipit::Commit` row sharing that SHA, across every stack in the Shipit instance, not just the stack for repository B.

Existing guards do not stop this: `verify_signature` authenticates the GitHub organization/app, not the specific repository the event is about; `ExplicitParameters` schema in `StatusHandler` requires only `sha`/`state`/`branches`, never validating `repository.full_name` against the target commit's stack; there is no `stacks`/`repository`-scoped filter anywhere in `StatusHandler#process`.

### Impact Explanation
A single validly-signed `status` webhook mutates `Shipit::Status`/`Shipit::Commit#status` for an unbounded number of unrelated stacks/repositories that happen to share the colliding SHA. Since `Commit#add_status` triggers `Hook.emit(:commit_status, ...)`, `Hook.emit(:deployable_status, ...)`, and `stack.schedule_merges` for a `success`/`pending` transition (`app/models/shipit/commit.rb:366-386`), this can also trigger merge-queue processing (`ProcessMergeRequestsJob`) on stacks the attacker has no relationship with. This matches the Critical category: "a payload for one repository mutating another's stack, commit, task or team."

### Likelihood Explanation
Preconditions: the attacker must have write access to at least one repository tracked by Shipit under the same GitHub organization/app configuration (to obtain a genuinely-signed webhook), and must be able to engineer or copy a commit whose full git object bytes (tree, parents, author/committer identity+timestamps, message) collide with a commit already present in a different tracked stack — feasible for shared/templated initial commits or intentionally copied root commits, not merely "any empty tree." Given those preconditions, the attack is cheap and fully repeatable: every subsequent status push against the colliding SHA re-triggers cross-tenant mutation.

### Recommendation
Scope `StatusHandler#process` through the payload's `repository.full_name`, mirroring `Handler#stacks`: require `repository.full_name` in the params schema, resolve `Repository.from_github_repo_name`, and restrict the commit lookup to `stacks.flat_map(&:commits).where(sha: params.sha)` (or `Commit.joins(:stack).merge(stacks).where(sha: params.sha)`) instead of the bare, repository-agnostic `Commit.where(sha: params.sha)`.

### Proof of Concept
```ruby
# test/models/shipit/webhooks/handlers/status_handler_test.rb
test "status webhook only updates the commit belonging to the named repository" do
  shared_sha = "4b825dc642cb6eb9a060e54bf8d69288fbee4904"

  stack1 = shipit_stacks(:shipit)
  stack2 = create_stack(repository: create_repository(owner: "victim-org", name: "repo-b"))
  stack3 = create_stack(repository: create_repository(owner: "victim-org", name: "repo-c"))

  commit1 = stack1.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "root")
  commit2 = stack2.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "root")
  commit3 = stack3.commits.create!(sha: shared_sha, author: shipit_users(:walrus), committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "root")

  payload = {
    "sha" => shared_sha,
    "state" => "success",
    "branches" => [{ "name" => stack1.branch }],
    "repository" => { "full_name" => stack1.repository.github_repo_name }
  }

  Shipit::Webhooks::Handlers::StatusHandler.new(payload).process

  # BROKEN BINDING: status leaks to stack2/stack3 despite payload naming only stack1's repository
  assert_equal "success", commit1.reload.status.state
  assert_equal "success", commit2.reload.status.state # should remain "unknown"
  assert_equal "success", commit3.reload.status.state # should remain "unknown"
end
```
