### Title
Fee-on-Transfer ERC20 Token Causes Bridge Reserve Drain and Cross-Chain Minting Inflation — (`contracts/service_chain/bridge/BridgeTransferERC20.sol`)

### Summary

The Kaia service-chain bridge's `requestERC20Transfer` and `onERC20Received` entry points record the caller-supplied `_value` in the `RequestValueTransfer` event without verifying that the bridge actually received that amount. When a fee-on-transfer ERC20 token is registered, the bridge's on-chain reserve is systematically underfunded relative to the amount relayed to the counterpart chain, leading to either unauthorized token minting (mintBurn mode) or progressive reserve drain that blocks later withdrawals (lock/unlock mode).

---

### Finding Description

**2-step deposit path** (`requestERC20Transfer`):

```solidity
// BridgeTransferERC20.sol L133-134
IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
_requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
```

The bridge pulls `_value + _feeLimit` from the sender. With a fee-on-transfer token, the bridge actually receives `(_value + _feeLimit) × (1 − fee_rate)`. The unchecked `_value` is then passed directly into `_requestERC20Transfer`, which emits `RequestValueTransfer` with the full `_value`. [1](#0-0) 

**1-step deposit path** (`onERC20Received`):

```solidity
// ERC20ServiceChain.sol L44-47
function requestValueTransfer(uint256 _amount, address _to, uint256 _feeLimit, bytes calldata _extraData) external {
    require(transfer(bridge, _amount.add(_feeLimit)), "requestValueTransfer: transfer failed");
    IERC20BridgeReceiver(bridge).onERC20Received(msg.sender, _to, _amount, _feeLimit, _extraData);
}
```

The token contract transfers `_amount + _feeLimit` to the bridge (bridge receives less due to the token's own fee), then calls `onERC20Received` with the original `_amount`. The bridge has no way to detect the shortfall. [2](#0-1) 

**`_requestERC20Transfer` emits the unverified amount:**

```solidity
// BridgeTransferERC20.sol L97-107
emit RequestValueTransfer(
    TokenType.ERC20,
    _from,
    _to,
    _tokenAddress,
    _value,          // ← caller-supplied, not verified against actual received
    requestNonce,
    fee,
    _extraData
);
``` [3](#0-2) 

The off-chain bridge operator (`BridgeInfo.handleRequestValueTransferEvent`) reads this event and relays the full `_value` to the counterpart bridge:

```go
// bridge_manager.go L339
handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, ...)
``` [4](#0-3) 

The counterpart bridge then releases or mints the full `_value`:

```solidity
// BridgeTransferERC20.sol L68-72
if (modeMintBurn) {
    require(ERC20Mintable(_tokenAddress).mint(_to, _value), "handleERC20Transfer: mint failed");
} else {
    IERC20(_tokenAddress).safeTransfer(_to, _value);
}
``` [5](#0-4) 

**Fee payment also compounds the shortfall.** `_payERC20FeeAndRefundChange` issues additional `safeTransfer` calls from the bridge's balance (fee to `feeReceiver`, refund to user), each of which also incurs the token's transfer fee, further widening the gap between the bridge's actual balance and its obligations. [6](#0-5) 

---

### Impact Explanation

**Lock/unlock mode (`modeMintBurn = false`):**
Every deposit of a fee-on-transfer token leaves the source bridge holding `_value × (1 − fee_rate)` tokens while the counterpart bridge releases `_value` tokens. The source bridge's reserve is drained at a rate proportional to the token's transfer fee. Once the reserve is exhausted, all subsequent withdrawal requests (`handleERC20Transfer → safeTransfer`) revert, permanently locking funds for later depositors.

**MintBurn mode (`modeMintBurn = true`):**
The source bridge burns `_value` tokens (it may have received less, causing a revert, or it burns the full amount if the feeLimit covers the shortfall). The counterpart bridge mints `_value` tokens. Net effect: more tokens are minted on the destination chain than were destroyed on the source chain, inflating the total supply of the bridged asset. This is an unauthorized mint of bridged assets.

---

### Likelihood Explanation

- `registerToken` is `onlyOwner`, so a fee-on-transfer token must be registered by the bridge owner. However, many real-world tokens (e.g., USDT) have a fee mechanism that is currently set to zero but can be activated by the token owner at any time. A proxy-upgradeable token registered today could become fee-on-transfer tomorrow.
- Once a token is registered, any user can call `requestERC20Transfer` or `requestValueTransfer`, making the deposit path fully unprivileged.
- There is no on-chain guard, no balance-before/after check, and no documentation warning against fee-on-transfer tokens.

---

### Recommendation

In `requestERC20Transfer`, measure the bridge's actual token balance before and after the `safeTransferFrom` call and use the delta as the effective deposit amount:

```solidity
function requestERC20Transfer(...) public {
    uint256 balanceBefore = IERC20(_tokenAddress).balanceOf(address(this));
    IERC20(_tokenAddress).safeTransferFrom(msg.sender, address(this), _value.add(_feeLimit));
    uint256 actualReceived = IERC20(_tokenAddress).balanceOf(address(this)).sub(balanceBefore);
    require(actualReceived >= _value, "fee-on-transfer: insufficient received");
    _requestERC20Transfer(_tokenAddress, msg.sender, _to, _value, _feeLimit, _extraData);
}
```

Apply the same pattern to `onERC20Received` by verifying the balance increase matches the claimed `_value + _feeLimit` before proceeding. Alternatively, document that fee-on-transfer and rebasing tokens are explicitly unsupported and enforce this at `registerToken` time.

---

### Proof of Concept

1. Deploy the bridge in lock/unlock mode (`modeMintBurn = false`).
2. Register a fee-on-transfer ERC20 token (1% fee per transfer) via `registerToken`.
3. Alice calls `requestERC20Transfer(token, Bob, 100e18, 0, "")` after approving 100e18.
   - Bridge receives 99e18 (1% fee deducted by token).
   - `RequestValueTransfer` event emits `valueOrTokenId = 100e18`.
4. Operator relays the event; counterpart bridge calls `handleERC20Transfer(..., 100e18, ...)`.
   - Counterpart bridge releases 100e18 to Bob.
5. After 100 such deposits, the source bridge holds ≈9900e18 but has promised 10000e18 in withdrawals.
6. The 100th withdrawal attempt reverts with an ERC20 insufficient-balance error, permanently locking the last depositor's funds. [1](#0-0) [5](#0-4) [6](#0-5) [2](#0-1) [4](#0-3)
