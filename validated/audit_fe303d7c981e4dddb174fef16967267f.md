### Title
CCMenu API client is never scoped to the stack it was issued for, allowing read of any stack - (File: app/controllers/shipit/ccmenu_url_controller.rb, app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
`CCMenuUrlController#client` creates/reuses an `ApiClient` with `permissions: %w[read:stack]` but never assigns `stack:`/`stack_id:`, so the token embeds an unscoped client id. `Api::CCMenuController` compounds this by overriding `stack` to call `Stack.from_param!(params[:stack_id])` directly instead of using `Api::BaseController#stacks`, so even a stack-scoped client would not be restricted. The result: any CCMenu URL generated for one stack authenticates reads for every stack on the instance.

### Finding Description
The claimed binding is `current_api_client.stack_id == Stack A.id`, required so that a CCMenu URL minted for Stack A cannot read Stack B. In practice:

- `CCMenuUrlController#client` builds the `ApiClient` with only `creator` and `name` as the `find_or_create_by!` keys and `permissions: %w[read:stack]` via `create_with`; no `stack:` is ever set: [1](#0-0) 
- `ApiClient` has `belongs_to :stack, optional: true`, so `stack_id` defaults to `nil` for this client, and `current_api_client.stack_id?` is `false`: [2](#0-1) 
- `Api::BaseController#stacks` would fall back to `Stack.all` when `stack_id?` is false: [3](#0-2) 
- Critically, `Api::CCMenuController` doesn't even use that `stacks` scoping helper — it defines its own `stack` method that resolves `Stack.from_param!(params[:stack_id])` against the full `Stack` relation, bypassing any per-client stack restriction entirely: [4](#0-3) 
- The only authorization check performed is `require_permission :read, :stack`, which merely checks that `"read:stack"` is present in `permissions` — it never compares `current_api_client.stack_id` to the requested `stack_id`: [5](#0-4) [6](#0-5) 

Since the same `ApiClient` row (keyed only by `creator` + name `'CCMenu Client'`) is reused across all `fetch` calls by the same operator for any stack, and its token (`self.class.message_verifier.generate(id)`, [7](#0-6) ) only encodes the client id, any holder of one such CCMenu URL can swap `stack_id` in the query string to target any other stack and still pass authentication and the `read:stack` permission check.

### Impact Explanation
An attacker who obtains a single CCMenu URL (e.g., pasted into a CI dashboard, forwarded email, or leaked via browser history/referrer) can substitute any other stack's identifier in the URL path and receive that stack's CCMenu XML status (`Api::CCMenuController#show`), which includes build/deploy activity, last build label/status, and web URL — i.e., unauthenticated read of stack state for arbitrary stacks on the instance. This is repeatable indefinitely (the token doesn't expire and is reused), and the blast radius is every stack hosted by the Shipit instance, not just the one the URL was generated for. This matches the "unauthenticated read of stack state" High-severity category.

### Likelihood Explanation
Preconditions are minimal: an operator only needs to have generated one CCMenu URL for any stack (a normal, documented feature) and that URL needs to leak or be forwarded — no GitHub secrets, session, or privileged role are required by the attacker. Guessing/enumerating other `stack_id` path segments is trivial since stack slugs are typically `owner/repo/branch`-derived and often public. Cost to the attacker is a single HTTP GET with a modified path; no signature or secret needs to be forged since the leaked token is valid and unscoped.

### Recommendation
Assign the target stack when creating/finding the CCMenu `ApiClient` (e.g. `ApiClient.create_with(permissions: %w[read:stack], stack: stack).find_or_create_by!(creator: current_user, stack:, name: 'CCMenu Client')`, using a per-stack name/lookup key so distinct stacks get distinct clients), and make `Api::CCMenuController#stack` use the inherited scoped `stacks.from_param!(params[:stack_id])` from `Api::BaseController` instead of querying `Stack` directly, so a client's `stack_id` is enforced.

### Proof of Concept
In a minitest under `test/controllers/`:
1. As `current_user`, call `CCMenuUrlController#fetch` for `stack_a` (`shipit_stacks(:shipit)` or similar), capturing the returned `ccmenu_url` and extracting its `token` param.
2. Assert (pre-fix expectation of the equality) that `ApiClient.find_by(...).stack_id == stack_a.id` — this fails because `stack_id` is `nil`.
3. Using that same `token`, issue `GET Api::CCMenuController#show` with `stack_id: stack_b.to_param` (a different stack).
4. Assert `response` is `:ok` and the XML payload's `name` equals `stack_b.to_param`, proving the token minted for `stack_a` authorizes reads on `stack_b`.
