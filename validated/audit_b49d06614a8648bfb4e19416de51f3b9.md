### Title
Webhook signature is verified against the organization in `repository.owner.login` while the repository actually acted upon is taken from the unauthenticated `repository.full_name` field, allowing cross-repository/cross-stack forged push events - (File: `app/controllers/shipit/webhooks_controller.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate the HMAC signature against using `repository_owner`, derived from `params.dig('repository', 'owner', 'login')` (or `organization.login`). Once the signature is accepted, the full raw payload is handed unmodified to the event handlers, which independently derive the target `Repository`/`Stack` from a *different* field: `payload.dig('repository', 'full_name')` in `Shipit::Webhooks::Handlers::Handler#repository_name`. Nothing ties these two fields together or re-validates that the authenticated organization actually owns the repository that is written to.

### Finding Description [1](#0-0) 

`verify_signature` does:
```ruby
github_app = Shipit.github(organization: repository_owner)
verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
```
where [2](#0-1) 
```ruby
def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```

In a multi-organization deployment (`Shipit.github_organizations`, see `lib/shipit.rb#github_app_config`), each organization has its own independently configured `webhook_secret`. Signature verification only proves that the request was signed with *the secret belonging to whichever organization `repository.owner.login` claims to be* — it does not prove anything about `repository.full_name`.

After verification succeeds, `Webhooks.for_event(event).each { |handler| handler.call(params) }` is invoked with the entire raw payload, and every handler resolves the target repository independently: [3](#0-2) 
```ruby
def stacks
  @stacks ||= Repository.from_github_repo_name(repository_name)&.stacks || Stack.none
end

def repository_name
  payload.dig('repository', 'full_name')
end
```

`PushHandler` then calls `stack.sync_github(expected_head_sha: params.after)` for every stack matching that `full_name`: [4](#0-3) 

Because `repository.owner.login` (used to select the verifying secret) and `repository.full_name` (used to select the acted-upon repository) are two independent JSON fields in the same attacker-controlled request body, an entity that legitimately controls an organization onboarded to this Shipit instance — and therefore knows that organization's `webhook_secret` because they can configure their own org's GitHub App webhook — can forge a payload where:
- `repository.owner.login` = their own organization (`X`), so `Shipit.github(organization: "X")` resolves to their own known secret and the HMAC check passes, and
- `repository.full_name` = a victim repository/stack hosted under a different organization on the same Shipit instance.

This breaks the intended binding: `organization authenticated by signature == organization/repository being written to`.

### Impact Explanation
This lets an attacker who only controls one onboarded GitHub organization forge webhook events (`push`, `status`, `check_suite`, `pull_request`, `membership`) that are processed against a completely different organization's repository/stack, without ever needing write access to, or a valid webhook secret for, the victim repository. For `push` specifically this can trigger `Stack#sync_github` (commit ingestion) using an attacker-chosen `after` SHA against the victim stack, and other handlers (`membership`, `pull_request`, `status`, `check_suite`) similarly act on data scoped by `full_name`/`repository` without re-checking it against the authenticated organization. This is a genuine cross-repository write/trust bypass matching the "organization authenticated vs. repository written" trust boundary called out in scope, and does not require a Shipit session, `ApiClient` token, or the victim's own webhook secret.

This is only exploitable on multi-organization Shipit deployments (`github_default_organization` non-nil, i.e., `secrets.github` keyed by multiple orgs) — in single-org mode `Shipit.github(organization:)` ignores the `organization` argument and always resolves to the single configured app/secret, so the mismatch has no effect there. I could not fully verify from static analysis whether every downstream handler additionally cross-checks the organization against the resolved repository owner; `Handler#repository_name` and `PushHandler` show no such check.

### Likelihood Explanation
Likely only in the specific configuration of a multi-tenant/multi-organization Shipit instance (several organizations sharing one Shipit deployment, each with its own GitHub App/webhook secret in `secrets.github`). In that configuration, exploitation requires no privileges beyond controlling one of the onboarded organizations' webhook configuration (which is a normal, low-privilege administrative capability for that org, not for the victim org) and the ability to send an arbitrary POST to `/webhooks`.

### Recommendation
Bind signature verification to the same repository identity used for authorization/lookup. Concretely:
1. In `WebhooksController#verify_signature`, resolve the verifying organization from a value that also gates repository lookup (e.g. derive it from `repository.full_name`'s owner segment rather than trusting `repository.owner.login`/`organization.login` independently), or
2. After verification, in `Handler#repository_name`/`Handler#stacks`, re-validate that the resolved `Repository`'s owner matches `repository_owner` (the organization whose secret verified the signature) before acting, rejecting the event otherwise.

### Proof of Concept
Assuming a multi-org Shipit deployment with organizations `attacker-org` (attacker controls, secret `S_attacker`) and `victim-org` (hosts stack `victim-org/victim-repo`):

1. Attacker computes `sig = HMAC-SHA1(S_attacker, body)` for a payload body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "full_name": "victim-org/victim-repo",
    "owner": { "login": "attacker-org" }
  }
}
```
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and `X-Hub-Signature: sha1=<sig>`.
3. `verify_signature` computes `repository_owner == "attacker-org"`, fetches `Shipit.github(organization: "attacker-org")`, and the signature validates successfully (attacker knows their own secret).
4. `PushHandler.call(params)` runs, resolving `repository_name = "victim-org/victim-repo"` via `Handler#repository_name`/`#stacks`, and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack — an event that should have required knowledge of `victim-org`'s webhook secret.

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e

        "status=#{status}"
      ].join(' '))
    end
