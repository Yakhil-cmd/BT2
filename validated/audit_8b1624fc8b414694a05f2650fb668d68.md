### Title
Webhook signature verification organization (`repository.owner.login`) not bound to the organization used by `MembershipHandler` (`organization.login`) - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/membership_handler.rb`)

### Summary
`WebhooksController#verify_signature` selects the signing organization via `repository_owner`, which prefers `params.repository.owner.login` over `params.organization.login` [1](#0-0) . `MembershipHandler` independently reads `params.organization.login` to create/label `Team` rows and never cross-checks it against the organization whose secret actually signed the request [2](#0-1) . This lets a webhook signed by org A be processed as if it originated from org B.

### Finding Description
The claimed binding, stated as an equality, is: `WebhooksController#repository_owner` (the org whose `webhook_secret` verifies `X-Hub-Signature`) `==` `params.dig('organization','login')` (the org `MembershipHandler` uses to create/tag a `Team`). The code never enforces this equality:

- `repository_owner` is `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [1](#0-0) , and `verify_signature` calls `Shipit.github(organization: repository_owner)` to select the secret used for `verify_webhook_signature` [3](#0-2) .
- `MembershipHandler#find_or_create_team!` uses `params.team.id` (`github_id`) as the sole lookup key and only assigns `team.organization = params.organization.login` inside the `find_or_create_by!` creation block, i.e. only on first creation [2](#0-1) . There is no check anywhere that `params.organization.login == repository_owner`.
- `verify_webhook_signature` returns `true` unconditionally when the resolved org has no `webhook_secret` configured [4](#0-3) .

Exploit precondition (confirmed against the code, not assumed): the attacker must control an organization that is *already configured inside this Shipit instance's own GitHub App/organization list* (i.e., they are a legitimate tenant org of this multi-org Shipit deployment — the repo ships `test/dummy/config/secrets_double_github_app.yml` demonstrating multi-org support, and `Shipit.github` raises `GithubOrganizationUnknown` for orgs it doesn't know about, per `test/controllers/webhooks_controller_test.rb` lines 109-127). Given that, the attacker:
1. Builds a `membership` payload with `repository.owner.login = "attacker-org"` (their own, Shipit-configured org) and `organization.login = "shopify"`, `team.id` equal to an existing Shopify team's `github_id`, `action: "added"`, `member.login` set to an attacker-controlled GitHub login.
2. Computes `X-Hub-Signature` with `attacker-org`'s own `webhook_secret` (which they legitimately know).
3. `verify_signature` calls `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the signature verifies successfully because it's checked against the correct, attacker-owned secret.
4. `MembershipHandler#process` then reads `params.organization.login == "shopify"` and, since `find_or_create_team!` only keys on `github_id`, it finds the *existing* Shopify `Team` row (no creation, so the mismatched `organization` string is not even written) and calls `team.add_member(member)`, adding the attacker's controlled GitHub user to that team [5](#0-4) .

No existing guard prevents this: `drop_unhandled_event` only checks the event type exists a handler for [6](#0-5) ; `verify_signature` never compares against `params.organization.login`; the `ExplicitParameters` schema in `MembershipHandler` only validates types/presence, not cross-field consistency [7](#0-6) .

### Impact Explanation
Team membership managed by `Team#add_member`/`Membership` feeds directly into `Shipit.github_teams`-style authorization (team membership is the mechanism gating privileged Shipit actions for members of authorized teams). An attacker who legitimately controls one Shipit-configured org's webhook secret can forge `membership` events that mutate a *different* org's `Team` record's membership without needing that other org's secret at all, escalating an attacker-controlled GitHub user into an authorized team. This matches the "High: escalation into `Shipit.github_teams` authorization" category. It is repeatable against any `Team` row whose `github_id` the attacker can guess/know, for any org configured on the same Shipit instance, as often as desired.

### Likelihood Explanation
This is not exploitable by an arbitrary unauthenticated internet user against a single-org Shipit deployment: it requires the Shipit instance to be configured for multiple organizations (a legitimate but repo-supported configuration — see multi-app secrets fixture), and the attacker must legitimately own/administer one of those configured orgs (which is within the "repository/org they own" attacker capability defined in scope) while targeting a different org also configured on the same instance. Given that precondition, the cost is trivial: one crafted POST with a self-computed HMAC.

### Recommendation
In `WebhooksController#verify_signature` or in each handler, enforce that `params.dig('organization','login')` (and any other embedded org identifiers used by the handler) equals the `repository_owner`/verified organization before dispatching; reject the request (422) on mismatch. Additionally, `MembershipHandler#find_or_create_team!` should scope lookups/writes by the verified organization, not trust the payload's `organization.login` for authorization-relevant records.

### Proof of Concept
Minitest plan (`test/controllers/webhooks_controller_test.rb` style, no live GitHub — reuse existing `Shipit.github(organization:).expects(:verify_webhook_signature)` stubbing pattern used at line 103):
1. Configure two orgs in `Shipit.github_teams` test config (mirroring `secrets_double_github_app.yml`): `"attacker-org"` with `webhook_secret: "attacker-secret"`, and `"shopify"` (existing fixture org).
2. Create/fetch an existing `Team` fixture with `organization: "shopify"` and a known `github_id`.
3. Build payload: `{ action: 'added', team: { id: <shopify_team.github_id>, ... }, organization: { login: 'shopify' }, member: { login: 'mallory' }, repository: { owner: { login: 'attacker-org' } } }`.
4. Compute `X-Hub-Signature` using `"attacker-secret"` (the org derived from `repository.owner.login`).
5. Assert `WebhooksController.new.send(:repository_owner)` (or equivalently `params.dig('repository','owner','login')`) resolves to `"attacker-org"` while `params.dig('organization','login')` resolves to `"shopify"` — i.e. assert the two sides of the binding differ.
6. POST to `/webhooks` with `X-Github-Event: membership`; assert `response.status == 200`.
7. Assert the `shopify` `Team` fixture's `members` now includes user `mallory`, proving a write occurred against `shopify`'s team while the signature was verified against `attacker-org`'s secret.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
