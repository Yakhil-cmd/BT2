This confirms the exploit path: `Shipit::Webhooks::Handlers::Handler#stacks` (and every handler that inherits from it, including `PushHandler` and `StatusHandler`) resolves the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`, while `WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` validates the request using a *different* field, `params.dig('repository', 'owner', 'login')` (or `organization.login` as fallback). Nothing ties these two reads of the same attacker-supplied JSON body together.

### Title
Webhook signature is verified against an attacker-chosen organization while the actual write target is read from an unrelated `repository.full_name` field, enabling cross-organization stack forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` picks the GitHub App (and thus the `webhook_secret` used to verify `X-Hub-Signature`) based on `repository.owner.login` [1](#0-0) , but the value it verifies against is decoupled from `repository.full_name`, which is what every webhook handler actually uses to look up the `Repository`/`Stack` that gets mutated [2](#0-1) . Because Shipit explicitly supports (and documents) multiple GitHub organizations sharing one Shipit instance, each with its own independently configured `webhook_secret` [3](#0-2) , and because an unset `webhook_secret` causes signature verification to be skipped entirely (`return true unless webhook_secret`) [4](#0-3) , an attacker who can trigger (or directly POST, since the endpoint accepts raw JSON) a webhook for an organization whose app has no `webhook_secret` configured can forge `repository.full_name` to point at a completely different, "protected" organization's stack.

### Finding Description
The binding that should hold is: `organization whose credential (webhook_secret) authenticated the request == organization that owns the repository being written`. The code breaks this equality:

- Verification selector: `repository_owner = params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')` [5](#0-4) , used only to pick `Shipit.github(organization: repository_owner)` and its `verify_webhook_signature` [1](#0-0) .
- Write target selector: `Repository.from_github_repo_name(payload.dig('repository', 'full_name'))` used by `Handler#stacks`, inherited by `PushHandler#process` (syncs the deploy state of matching stacks) and by any other repository-scoped handler [2](#0-1) [6](#0-5) .

`repository.owner.login` and `repository.full_name` are two independent keys inside the same attacker-suppliable JSON body — nothing in `Shipit::GitHubApp#verify_webhook_signature` or `WebhooksController` cross-checks that `full_name` actually starts with `owner.login`. Combined with the documented multi-org configuration where each org has its own (optionally absent) `webhook_secret` [3](#0-2) , and the fact that a missing secret causes `verify_webhook_signature` to short-circuit to `true` [7](#0-6) , an attacker only needs knowledge that *any one* configured organization has no `webhook_secret` to bypass authentication for the entire multi-tenant Shipit instance.

### Impact Explanation
This is an authentication-bypass / cross-repository-write bug: an unauthenticated (or single-org, low-privilege) attacker can submit a webhook payload with `repository.owner.login` set to the unsecured organization and `repository.full_name` set to any other onboarded repository (e.g., a privileged production repo in a fully-secured org). Since `PushHandler` calls `stack.sync_github(expected_head_sha:)`, this can force Shipit to sync/advance the head of an arbitrary stack belonging to a different, unrelated organization, or (via `status`/`check_suite`/`pull_request` handlers) inject fabricated CI statuses, check runs, or merge/PR state used to gate deploys — all without ever proving control of that target organization's repository or app credentials. This maps to the report's "Critical" bucket (cross-repository writes / unauthorized deploy path) since it lets an attacker manipulate deploy-gating state for repositories they do not control.

### Likelihood Explanation
The precondition (at least one onboarded organization in a multi-org deployment lacking a `webhook_secret`) is realistic: Shipit's own example/setup docs and dummy fixtures repeatedly show `webhook_secret: # nil` as an accepted, unremarkable configuration [8](#0-7) [9](#0-8) , and the multi-org feature is a first-class, documented capability [3](#0-2) . Any operator running several orgs where only some enforce a webhook secret is exposed with no further action from an attacker beyond crafting one POST to `/webhooks`.

### Recommendation
Require that `repository.owner.login` (the value used to select the verifying `webhook_secret`) match the owner segment of `repository.full_name` (and of `organization.login`, where present) before dispatching to handlers, and reject the request otherwise. Additionally, consider making `verify_webhook_signature` fail closed (require a configured secret) rather than defaulting to `true` when `webhook_secret` is blank, at least whenever more than one organization is configured.

### Proof of Concept
1. Shipit is configured with two GitHub orgs: `openorg` (no `webhook_secret` set) and `secureorg` (has stacks and a `webhook_secret`), per the documented multi-org config [3](#0-2) .
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and no valid `X-Hub-Signature`, with body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": { "owner": { "login": "openorg" }, "full_name": "secureorg/production-app" }
}
```
3. `repository_owner` resolves to `"openorg"` [5](#0-4) ; `Shipit.github(organization: "openorg").verify_webhook_signature` returns `true` because `webhook_secret` is blank for that org [7](#0-6) .
4. `PushHandler#process` resolves the target stack via `repository.full_name` = `"secureorg/production-app"` [2](#0-1)  and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the `secureorg` stack the attacker never authenticated for [6](#0-5) .
