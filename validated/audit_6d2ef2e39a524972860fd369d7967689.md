### Title
Signature verification is keyed on `repository.owner.login` while the mutation is keyed on `repository.full_name`, letting an attacker archive an arbitrary victim's `ReviewStack` - (File: `app/controllers/shipit/webhooks_controller.rb`, `lib/shipit/github_app.rb`, `app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb`)

### Summary
`Shipit::WebhooksController#verify_signature` selects which GitHub App/secret to validate the webhook against using `params.dig('repository', 'owner', 'login')`, while the downstream `pull_request` handlers resolve the `Repository`/`Stack` to mutate using the independent field `params.repository.full_name`. Since both fields are attacker-controlled JSON body values with no cross-check that they refer to the same repository, an attacker can pick an owner/org whose webhook secret they control (or that has none configured, which is treated as always-verified) to pass signature verification, while pointing `repository.full_name` at a victim's actual repository to archive that victim's active `ReviewStack`.

### Finding Description
The broken binding, stated as an equality that the code assumes but never enforces:

`params.dig('repository','owner','login') == owner_of(params.repository.full_name)`

This is false in the attacker's crafted payload, and nothing in the code path checks it.

Trace:
- `verify_signature` in `app/controllers/shipit/webhooks_controller.rb` (lines 24-49) computes `repository_owner` from `params.dig('repository','owner','login')` (line 61) and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)`.
- `GitHubApp#verify_webhook_signature` (`lib/shipit/github_app.rb` lines 76-83): `return true unless webhook_secret` — if the named org has no configured `webhook_secret`, **any** signature (or none at all, subject to header parsing) is accepted; otherwise only `sha1=` signatures are ever checked (`return false unless algorithm == 'sha1'`), the legacy algorithm.
- `Shipit::WebhooksController#create` (lines 10-15) then dispatches `params` (the raw parsed JSON, unmodified) to `Shipit::Webhooks.for_event(event)` handlers, e.g. `Handlers::PullRequest::ClosedHandler`.
- `ClosedHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/closed_handler.rb` lines 49-53) resolves the target repository via `Shipit::Repository.from_github_repo_name(params.repository.full_name)` — a completely different payload field than the one used for signature verification.
- `ClosedHandler#process` calls `review_stack.archive!`, which (`review_stack_adapter.rb` lines 23-35) looks up the `ReviewStack` by `environment` (`pr#{params.number}`) scoped to that resolved repository and calls `stack.archive!(user, ...)`, deprovisioning and archiving it.

Attacker's exact request: `POST /webhooks` with header `X-Github-Event: pull_request`, `X-Hub-Signature: sha1=<hmac>` computed with a secret the attacker knows (their own org's configured `webhook_secret`, or omitted entirely if that org has none configured), and JSON body:
```json
{
  "action": "closed",
  "number": 42,
  "repository": { "full_name": "victim-org/victim-repo", "owner": { "login": "attacker-org" } },
  "pull_request": { ... },
  "sender": { "login": "attacker" }
}
```
`repository_owner` resolves to `attacker-org`, so `verify_signature` validates against the attacker's own (or secret-less) org and passes, while the handler acts on `victim-org/victim-repo`'s active review stack for PR #42, archiving it.

Existing guards do not catch this: `drop_unhandled_event` only checks the event name is registered; the `ExplicitParameters` schema in `ClosedHandler.params` only validates types/presence of fields, not cross-field consistency between `repository.owner.login` and `repository.full_name`; there is no `force_github_authentication`, `User#authorized?`, or `require_permission!` check on this unauthenticated webhook endpoint; `Repository`/`Stack` model validations only validate format, not ownership provenance of the request that mutates them.

### Impact Explanation
An unauthenticated, unprivileged attacker can archive (deprovision) any victim repository's active `ReviewStack` for a targeted pull-request environment, a cross-tenant state mutation where one repository's/org's payload writes another repository's records — this matches the Critical impact category "a payload for one repository mutating another's stack, commit, task or team." The action is repeatable against any `victim-org/victim-repo` and any open PR number the attacker can guess or observe, requiring only that the attacker control (or exploit the absence of) a webhook secret for some org name they place in `repository.owner.login`.

### Likelihood Explanation
Preconditions: the attacker needs to know or infer some org name configured in Shipit that either has no `webhook_secret` set, or whose secret the attacker knows (e.g., their own org's Shipit-integrated GitHub App config) — signature computation itself is trivial once a valid secret/no-secret org is identified. No Shipit session, API token, or GitHub App/organization membership on the victim side is required. The attacker also needs to know the victim repository's `full_name` and the PR `number` (`environment` = `pr#{number}`), both easily discoverable via GitHub's public API/UI for public repos. This is fully reproducible with a single unauthenticated HTTP request per target PR.

### Recommendation
Enforce that the organization/owner used to select the webhook secret is the same owner as `repository.full_name` (or, better, resolve the `Repository` first via `full_name`, then verify the signature using that repository's associated organization's secret exclusively — never trust `repository.owner.login` as a separate, independently attacker-suppliable field). Additionally, support and require `X-Hub-Signature-256` (SHA-256) verification, and reject payloads when no webhook secret is configured for an organization rather than treating that as automatically verified.

### Proof of Concept
Minitest sketch (`test/controllers/webhooks_controller_test.rb` style, no live GitHub):
```ruby
test "cross-tenant pull_request payload archives a victim stack via mismatched repository.owner.login" do
  victim_repo = shipit_repositories(:shipit) # full_name "victim-org/victim-repo"
  victim_stack = create_review_stack(repository: victim_repo, number: 42, archived: false)

  payload = {
    action: 'closed',
    number: 42,
    repository: { full_name: victim_repo.full_name, owner: { login: 'attacker-org' } },
    pull_request: { id: 1, number: 42, url: '...', title: 't', state: 'closed',
                     additions: 0, deletions: 0,
                     head: { sha: 'abc', ref: 'branch' },
                     user: { login: 'attacker' }, assignees: [], labels: [] },
    sender: { login: 'attacker' }
  }.to_json

  # `attacker-org` is configured in Shipit.github_apps with no webhook_secret,
  # so GitHubApp#verify_webhook_signature returns true unconditionally.
  post webhooks_path, params: payload,
    headers: { 'X-Github-Event' => 'pull_request', 'Content-Type' => 'application/json' }

  assert_response :ok
  assert_equal 'attacker-org', JSON.parse(payload).dig('repository', 'owner', 'login')
  refute_equal 'attacker-org', victim_repo.owner # binding attacker asserted vs actual owner: mismatched
  assert victim_stack.reload.archived?, "victim stack was archived by a payload verified against a different org"
end
```
This demonstrates that `repository_owner` used in `verify_signature` (`attacker-org`) diverges from the actual owner of the mutated repository (`victim-org`), yet the mutation (`archive!`) still occurred — proving the invariant "a forged webhook cannot cause any state change attributed to a repository/org whose secret did not verify it" is violated.     def verify_webhook_signature(signature, message)
```ruby
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
