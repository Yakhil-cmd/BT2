## Finding

### Title
Wallet permanent pairing secret leaked to an attacker-controlled ArbStore URL derived from an untrusted `arbiter_address` — ([File: arbiter_contract.js])

### Summary
The Apereo CAS CVE describes a pattern where a server, in the course of validating an X.509 certificate, follows an attacker-supplied URL (from the certificate's CRL Distribution Points) and then authenticates to that URL using a shared, sensitive credential (the LDAP bind password), leaking the credential to the attacker. The same *structural* bug class — "follow an untrusted-supplied identifier to a URL, then send a durable secret to that URL" — exists in ocore's arbiter-contract dispute flow: the wallet's permanent device-pairing secret is sent, verbatim, to a URL resolved from the contract's `arbiter_address`, a field whose value originates from the counterparty (an unprivileged private-payment/AA-adjacent counterparty in an arbiter contract negotiation).

### Finding Description
When a user opens a dispute, appeals a dispute, or requests an appeal fee for an arbiter contract, ocore resolves an "ArbStore" HTTP endpoint via the hub, keyed by `objContract.arbiter_address`, and then POSTs a JSON payload that includes `my_pairing_code` — a string built from the caller's **permanent** pairing secret: [1](#0-0)

The same pattern repeats in `appeal()` and `getAppealFee()`: [2](#0-1) [3](#0-2) 

The permanent pairing secret is generated once and reused for the lifetime of the wallet install (`is_permanent=1`, expiry `2038-01-01`): [4](#0-3) 

This secret is the credential used to authenticate a *pairing* request to become a trusted correspondent device of the wallet: [5](#0-4) 

`objContract.arbiter_address` is a field of the arbiter contract that is populated at contract-creation/offer time (`createAndSend`) and can also be written by an incoming/synced contract via `store()`: [6](#0-5) [7](#0-6) 

The destination URL is *not* a hardcoded, vetted arbiter registry — it is whatever URL the hub returns for the given `arbiter_address` via `hub/get_arbstore_url`: [8](#0-7) [9](#0-8) 

Because the arbiter address embedded in the contract is attacker-influenceable (an attacker acting as a counterparty in a proposed arbiter contract chooses which address is designated as "arbiter", and can register that address with the hub as pointing to a server they control), the httpRequest ends up sending the victim's long-lived pairing secret directly to an attacker-controlled endpoint — mirroring the CVE's "attacker-controlled CRL URL receives the LDAP bind password" pattern: an attacker-influenced identifier drives resolution of an endpoint, and a durable, reusable secret is transmitted to whatever endpoint is resolved, without validating that the endpoint is one the secret was meant to be shared with.

### Impact Explanation
The permanent pairing secret (`pairing_secret`, `is_permanent=1`) is precisely the token that authorizes a third party to become a trusted "correspondent device" of the victim's wallet: [5](#0-4) 
Once an attacker obtains this secret (by operating the ArbStore endpoint that the dispute/appeal/appeal-fee flow contacts), they can pair with the victim as a device without any further victim confirmation, since the pairing_secret is the sole authenticator checked in `handlePairingMessage`. A rogue "correspondent device" can then be leveraged to socially engineer or automate further wallet actions (e.g., propose fraudulent arbiter contracts, private payments, or multisig cosigner flows) that depend on trusting device messages from paired correspondents, which can ultimately facilitate unauthorized fund movement through the wallet UI/API surface that trusts paired-device input.

### Likelihood Explanation
Exploitation requires the victim to engage in an arbiter-contract negotiation with a malicious counterparty (a normal, unprivileged interaction supported by the protocol) where the malicious party sets/influences `arbiter_address` to an address whose hub-registered ArbStore URL they control, and the victim later triggers `openDispute`, `appeal`, or `getAppealFee` for that contract — actions that are part of normal dispute-resolution UX and thus plausible in a contract dispute (which the attacker can themselves provoke by refusing to pay/cooperate).

### Recommendation
- Never include `my_pairing_code` / the permanent pairing secret in payloads sent to externally-resolved, non-pinned URLs such as the ArbStore endpoint.
- If a device introduction to the ArbStore is required, use a short-lived, single-use, ArbStore-scoped pairing secret instead of the wallet's permanent pairing secret, and/or require the ArbStore identity/certificate to be pinned or independently confirmed before sending any pairing material.
- Validate that `arbiter_address` (and the resolved ArbStore URL) corresponds to an arbiter the local user has explicitly trusted/selected, rather than trusting whatever value arrives from contract negotiation.

### Proof of Concept
1. Attacker registers an address `A` with the hub such that `hub/get_arbstore_url(A)` resolves to `https://evil.example.com`.
2. Attacker proposes (or, via a synced/incoming contract path, causes to be stored) an arbiter contract with `arbiter_address = A` to the victim, and the victim accepts and pays.
3. Attacker fails to fulfil their side, prompting the victim to call `openDispute(hash, cb)`.
4. `arbiter_contract.js` resolves the ArbStore URL for `A` (attacker's server) and POSTs `/api/dispute/new` with a JSON body containing `my_pairing_code` — the victim's permanent, reusable pairing secret — directly to the attacker's server: [10](#0-9) 
5. The attacker now has the victim's permanent pairing secret and can pair as a trusted correspondent device of the victim's wallet.
