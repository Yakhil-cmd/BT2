### Title
Membership webhook handler grants team membership by `github_id` alone with no check that the requesting organization owns that team - ([File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`MembershipHandler#find_or_create_team!` resolves the target `Team` solely by `params.team.id` (GitHub team id), never checking that the organization named in the payload (validated by signature) actually owns that team. Any organization onboarded into Shipit with its own `webhook_secret` can therefore send a signed `membership` event naming a *different* organization's already-existing team id and add an arbitrary GitHub login as a member of that team.

### Finding Description
The broken binding: the set of `github_id`s an organization's webhook may mutate should equal the set of `github_id`s of teams that organization actually owns (`team.organization == payload.organization.login`). No code enforces this.

Trace:
- `WebhooksController#verify_signature` resolves `Shipit.github(organization: repository_owner)` from `params.dig('organization', 'login')` for membership events and calls `verify_webhook_signature`, which only proves the request came from *some* org whose `webhook_secret` is known to the sender — it says nothing about which `Team` records that org may touch. [1](#0-0) [2](#0-1) 
- Dispatch is unconditional: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` → `MembershipHandler#process`. [3](#0-2) 
- `find_or_create_team!` looks the team up **only** by `github_id`: [4](#0-3) 
The `organization` attribute is only set inside the `find_or_create_by!` block, i.e. only on first creation. If a `Team` with that `github_id` already exists (belonging to org A), a signed membership event from unrelated org B's webhook secret will match the existing record and immediately call `team.add_member(member)`. [5](#0-4) 

Root cause: `Team.find_or_create_by!(github_id: ...)` performs no `where(organization: params.organization.login)` scoping, so an unrelated org's valid webhook signature is treated as sufficient authorization to mutate any team by id, not just teams whose `organization` column matches the requester.

None of the existing guards close this gap: `verify_signature` authenticates *which org* sent the payload but not *which teams* that org may reference; `drop_unhandled_event` and `ExplicitParameters` schema (`app/models/shipit/webhooks/handlers/membership_handler.rb:7-21`) only validate shape, not ownership; there is no `require_permission!`/team-ownership check anywhere in the handler.

### Impact Explanation
`Team` membership rows feed `User#authorized?`, which grants Shipit-wide authorization when a user belongs to any team in `Shipit.github_teams`: [6](#0-5) 
An attacker who legitimately administers a *separate, unrelated* GitHub organization onboarded into Shipit (with their own valid `webhook_secret`) can forge a `membership` "added" event naming their own GitHub login and the `github_id` of a privileged team belonging to a different organization (e.g. one whose handle appears in `Shipit.github_teams`). This creates a `Membership` linking the attacker's `User` to that privileged `Team`, without that org ever having added the attacker on GitHub. When the attacker subsequently logs into Shipit via OAuth with that same GitHub login, `authorized?` returns true, granting them Shipit-wide access reserved for the privileged team. This is repeatable against any team `github_id` the attacker can guess or observe, across tenants, matching the High severity category "escalation into `Shipit.github_teams` authorization."

### Likelihood Explanation
Preconditions: the attacker must control (or be an admin of) at least one GitHub organization that has been legitimately onboarded to this Shipit instance with its own `webhook_secret`/`GithubHook::Organization` record — a realistic scenario for multi-tenant Shipit deployments where multiple unrelated orgs' repos are hosted. No Shipit session, API token, or GitHub App private key is needed; the attacker only needs their own org's webhook secret (which they possess by definition of controlling that org's webhook config) and knowledge/guess of the target team's numeric GitHub team id (discoverable via GitHub's team API or UI if the attacker can view team metadata, or via existing Shipit data). The request is a single signed HTTP POST, fully repeatable.

### Recommendation
Scope the team lookup and mutation to the organization asserted by the verified webhook: reject or ignore membership events where an existing `Team.find_by(github_id: ...)` has an `organization` different from `params.organization.login`, or additionally verify `repository_owner`/`params.organization.login` matches `team.organization` before calling `find_or_create_by!`/`add_member`.

### Proof of Concept
Minitest under `test/controllers/webhooks_controller_test.rb` style (not part of the delivered fix, but illustrating the check):
1. Fixture: `GithubHook::Organization` for `attacker-org` with `secret: 'attackersecret'`, event `membership`.
2. Fixture: `Team` `privileged_team` with `organization: 'victim-org'`, `github_id: 999`.
3. POST `/webhooks` with header `X-Github-Event: membership`, signed with `attackersecret`, body:
   `{ action: 'added', team: { id: 999, name: 'Privileged', slug: 'privileged', url: '...' }, organization: { login: 'attacker-org' }, member: { login: 'attacker' } }`.
4. Assert `response.status == 200` and `Membership.exists?(team: privileged_team, user: User.find_by(login: 'attacker'))` — i.e. before: `privileged_team.organization == 'victim-org' != 'attacker-org'`; after: attacker is a member of `privileged_team` despite the mismatch, proving the binding is violated.
