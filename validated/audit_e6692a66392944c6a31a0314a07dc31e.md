### Title
`Api::CCMenuController#stack` bypasses `ApiClient#stack_id` scope, letting a stack-scoped token read any stack's CI status - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Api::BaseController` enforces that a stack-scoped `ApiClient` (one created with `stack_id` set, e.g. via `CCMenuUrlController#client`) can only see the single stack it was scoped to, by resolving the target stack through `stacks.from_param!` where `stacks` filters by `current_api_client.stack_id`. `Api::CCMenuController`, however, overrides `#stack` to resolve directly from `Stack.from_param!(params[:stack_id])`, completely bypassing that scoping filter, while still relying on the generic `require_permission :read, :stack` check which only validates the *permission name*, not *which* stack it applies to.

### Finding Description
`Api::BaseController` defines the scope binding that the rest of the API controllers rely on: [1](#0-0) 

`stacks` restricts the queryable set to the single stack referenced by `current_api_client.stack_id` when the token is scoped, and `stack` (used e.g. by `Api::StacksController#stack`, `app/controllers/shipit/api/stacks_controller.rb:87-89`) always goes through this filtered relation: [2](#0-1) 

`Api::CCMenuController`, however, defines its own `stack` method that talks to `Stack` directly, never consulting `current_api_client.stack_id`: [3](#0-2) 

The controller's only authorization gate is `require_permission :read, :stack`, which is implemented purely as a permission-name check with no notion of a specific stack: [4](#0-3) 

The binding that should hold is: `ApiClient#stack_id` (the stack the token is authorized for) == the stack the controller action actually touches. `Api::CCMenuController` breaks this equality — the token authorizes stack A (or, if unscoped and just carrying `read:stack`, was intended to be used against the caller's own stacks), but the action touches whatever `stack_id` the caller supplies in the URL/query string.

This is a close analog of the reported bug class: a security-relevant binding (here, "token’s authorized stack" vs. "stack acted upon", one of the explicitly listed analog patterns — "a stack a token authorises versus a stack it touches") that is enforced in one code path (`BaseController#stack`) but silently missing in a sibling code path (`CCMenuController#stack`), the same way `rewardsManager` was wired in one initializer path but not the other.

### Impact Explanation
`CCMenuUrlController#client` mints a stack-scoped `ApiClient` with only `read:stack` permission for a specific stack, and hands the caller a URL containing `client.authentication_token`: [5](#0-4) 

That token is meant to be usable only for the stack it was minted for (this is precisely the trust model `Api::BaseController#stacks` implements for every other API controller). Because `CCMenuController#stack` ignores `current_api_client.stack_id`, anyone holding a valid `read:stack` CCMenu token — even one legitimately scoped to a single, low-sensitivity stack — can pass an arbitrary `stack_id` and read the CI/deploy status (`name`, `activity`, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) of any other stack in the Shipit instance, including private/internal stacks the token holder was never granted access to. This is an unauthenticated-for-that-resource read of stack state (deploy/build status) via a credential that was authorized for a different, narrower scope — matching the High-impact category "unauthenticated read of stack state, task streams or deploy output."

### Likelihood Explanation
Any holder of a scoped CCMenu token (a routine, low-privilege artifact generated for CI dashboard integrations via `CCMenuUrlController`) can trivially exploit this by changing the `stack_id` query parameter/path segment of the request — no additional secrets, sessions, or elevated privileges are required beyond the token they were already legitimately issued. The existing test suite (`test/controllers/api/ccmenu_controller_test.rb`) never exercises a stack-scoped `ApiClient` against a `stack_id` outside its scope, so nothing currently catches this discrepancy.

### Recommendation
Make `Api::CCMenuController#stack` go through the same scoped lookup used elsewhere, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
reusing `Api::BaseController#stacks`, so a token scoped to one stack cannot resolve any other stack. Add a regression test asserting that a stack-scoped `ApiClient`'s CCMenu token returns 403/404 when `stack_id` does not match `current_api_client.stack_id`.

### Proof of Concept
1. Create a stack-scoped API client (as `CCMenuUrlController#client` does): `ApiClient.create!(creator: user, name: 'CCMenu Client', stack_id: stack_a.id, permissions: %w[read:stack])`, and obtain `client.authentication_token`.
2. Send `GET /api/stacks/<stack_b_owner>/<stack_b_name>/<env>/ccmenu.xml?token=<client.authentication_token>` where `stack_b` is a completely different stack than `stack_a`.
3. `authenticate_api_client` succeeds (valid token) → `require_permission :read, :stack` succeeds (client has `read:stack`) → `stack` resolves `stack_b` directly via `Stack.from_param!`, bypassing the `stack_id` scope check that `Api::BaseController#stacks` would have enforced.
4. The response renders `stack_b`'s CI/build status XML, even though the token was only ever authorized for `stack_a`.

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
