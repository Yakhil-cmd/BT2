## Finding

### Title
Cross-repository commit status forgery via unscoped `sha` lookup in `StatusHandler` triggers unauthorized merges — (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
The webhook signature check in `WebhooksController#verify_signature` only authenticates *which GitHub organization* sent the payload (by looking up `Shipit.github(organization: repository_owner)` and verifying the HMAC against that organization's `webhook_secret`) [1](#0-0) [2](#0-1) . It never binds the verified payload to a specific repository. `Shipit::Webhooks::Handlers::StatusHandler`, which processes `status` events, then updates commit state by a **global, unscoped `sha` lookup** across the entire `commits` table instead of scoping to the repository/stack the event actually concerns [3](#0-2) . This breaks the binding "organization that authenticated" versus "repository that is written": any repository under an authenticated organization can be used to write a commit-status update onto a commit belonging to a completely different stack/repository, as long as the `sha` values collide.

### Finding Description
- `Handler` base class scopes most handlers (push, pull_request, etc.) to the repository named in the payload via `Repository.from_github_repo_name(repository_name)` [4](#0-3) , and `PushHandler` correctly restricts writes to `stacks` derived from that repository [5](#0-4) .
- `StatusHandler`, however, does not use `repository_name`/`stacks` at all. It only requires `sha` and `state` and then does:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [6](#0-5) 
This matches every `Commit` record in the entire database sharing that `sha`, irrespective of which stack/repository owns it.
- `create_status_from_github!` writes a new status and, depending on the transition, calls `stack.schedule_merges` on the commit's *actual* stack (not the one implied by the payload's repository) whenever the new status is `pending` or `success` [7](#0-6) , which enqueues `ProcessMergeRequestsJob` to advance merges for that stack.
- Signature verification only confirms the payload came from an organization Shipit trusts (using that organization's own `webhook_secret`) — it says nothing about which specific repository within that org's installation is entitled to affect which stack's commits. Any repository under the trusted organization/installation can legitimately trigger real, correctly-signed `status` webhooks (e.g., via its own Checks/Commit-status API using a personal access token with only status-write scope on that one repo). If the attacker arranges (e.g., by importing/cherry-picking identical commit content, which is common when repos share history via forks/mirrors) for a commit in their own low-privilege repository to have the same `sha` as a commit tracked by a *different*, higher-privilege stack, the resulting genuine webhook lets them inject an arbitrary `state`/`success` status onto the other stack's commit and drive `stack.schedule_merges` for a stack they have no access to.

### Impact Explanation
This breaks the "organization authenticated vs. repository written" trust boundary and results in an unauthorized write into another stack's commit-status history, which can trigger `stack.schedule_merges` → `ProcessMergeRequestsJob`, i.e., an unauthorized merge/deploy-eligibility change on a stack the attacker does not control. This falls under the Critical impact bucket ("cross-repository writes, or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Requires the attacker to control at least one repository within an organization that has the Shipit GitHub App installed (unprivileged relative to the target stack) and to be able to produce a commit with an identical SHA to a commit tracked by the victim stack (achievable for public/forked history, or any commit whose content is otherwise known), then trigger a real, validly-signed `status` webhook for that SHA from their own repository.

### Recommendation
Scope `StatusHandler#process` to the repository referenced in the payload, mirroring `PushHandler`/`Handler#stacks`: require the `repository.full_name` field, resolve the repository via `Repository.from_github_repo_name`, and restrict the `Commit.where(sha: ...)` query to `commit.stack.repository == repository` (or join through `stacks`) before calling `create_status_from_github!`.

### Proof of Concept
1. Attacker has push access to `attacker-org/repo-x`, which is installed under the Shipit GitHub App for `attacker-org` (a legitimately configured organization with its own `webhook_secret`).
2. Attacker imports (or otherwise reproduces) a commit with SHA `abc123...` that is identical to a commit already tracked in a victim stack for `victim-org/repo-y` (different org/repo, different stack, attacker has no access there).
3. Attacker sets a commit status on `abc123...` in `attacker-org/repo-x` (e.g., via the GitHub Statuses API using their own repo-scoped token) with `state: success`.
4. GitHub delivers a genuinely-signed `status` webhook (signed with `attacker-org`'s webhook secret) to Shipit's `/webhooks` endpoint; `verify_signature` passes because it only checks the organization, not the repository.
5. `StatusHandler#process` executes `Commit.where(sha: 'abc123...')`, matches the commit belonging to the victim's stack, and calls `create_status_from_github!`, which can trigger `stack.schedule_merges` for the victim stack — an unauthorized effect on a stack the attacker never had permission to touch.
