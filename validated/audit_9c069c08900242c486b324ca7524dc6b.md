### Title
ERC20 collateral traded through XCM (`WithdrawAsset`) becomes permanently unclaimable when trapped, because `ERC20Transactor` never implements `mint_asset` - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` moves ERC20 tokens into a `Erc20Credit` holding by making a real, on-chain `IERC20::transfer()` call to a checking account [1](#0-0) . It never overrides `TransactAsset::mint_asset`, so it inherits the trait's default `Err(XcmError::Unimplemented)` [2](#0-1) . `mint_asset` is exactly the function `pallet_xcm::claim_assets`/`ClaimAsset` uses to recreate a previously-trapped holding [3](#0-2) . Because none of the other transactors in the `AssetTransactors` tuple match an ERC20 (`AccountKey20`) asset id either, `mint_asset` fails for every trapped ERC20 asset — meaning once ERC20 collateral is trapped (a routine, easily-triggered outcome of any XCM program that withdraws it and then fails a later instruction), it is permanently stuck in the `ERC20TransfersCheckingAccount` with **no possible recovery path**, including the canonical `claim_assets` mechanism designed for exactly this situation.

### Finding Description
This is the FRAME/XCM analog of the reported "BNB collateral locked" bug: an asset can be moved *in* via one mechanism, but the mechanism intended to move it back *out* under the failure/recovery path is missing for this specific asset type, so it locks forever.

1. **Real entry point.** Any signed account can submit `pallet_xcm::execute` (or a message routed through `pallet_xcm::send`/an XCM transport) with `WithdrawAsset` for an ERC20 asset (an `AccountKey20` location matched by `assets_common::ERC20Matcher`), followed by any instruction that fails. `WithdrawAsset` is processed inside its own `Config::TransactionalProcessor::process` block [4](#0-3) : it calls `Config::AssetTransactor::withdraw_asset_with_surplus`, which for ERC20 executes a real `pallet_revive::Pallet::<T>::bare_call` invoking `IERC20::transfer()` from the user to `ERC20TransfersCheckingAccount` [5](#0-4) . Once this instruction returns `Ok`, the tokens are physically transferred and this state change is **not** part of any subsequent instruction's transactional scope.

2. **Trap on later failure.** If any later instruction in the same program fails (e.g. `DepositAsset` failing because the ERC20 `transfer()` from the checking account reverts for an unrelated destination-side reason, or a `Trap`, or any other instruction), `vm.process` stops, and `post_process` traps whatever remains in the `holding` register via `Config::AssetTrap::drop_assets` [6](#0-5) . For `pallet_xcm`, this writes an `AssetsTrapped` entry to `AssetTraps` storage [7](#0-6) . Existing tests explicitly document that this is the intended safety net ("funds are never silently lost … trapped by post_process") [8](#0-7) , and this exact "withdraw succeeds, later instruction fails, leftover holding gets trapped" flow is unit-tested for other asset types [9](#0-8) .

3. **The recovery path is broken for ERC20.** The intended recovery is `pallet_xcm::claim_assets`, which builds `ClaimAsset` + `DepositAsset` and executes it [10](#0-9) . `ClaimAsset` calls `Config::AssetTrap::claim_assets`, whose `pallet_xcm` implementation calls `AssetTransactor::mint_asset(asset, context)` to recreate the trapped `AssetsInHolding` [3](#0-2) . `ERC20Transactor` (shown in full) implements `can_check_in/out`, `check_in/out`, `withdraw_asset_with_surplus`, and `deposit_asset_with_surplus` — but **never `mint_asset`** [11](#0-10) . It therefore falls back to the trait default, `Err(XcmError::Unimplemented)` [2](#0-1) . The other members of Asset Hub Westend's `AssetTransactors` tuple (`FungibleTransactor`, `FungiblesTransactor`, `ForeignFungiblesTransactor`, `UniquesTransactor`) match native balances, `pallet-assets` ids, foreign-asset ids, and NFTs respectively — none match an `AccountKey20` ERC20 location — so the tuple's `mint_asset` dispatch exhausts every entry and returns `Err(XcmError::AssetNotFound)` for the trapped ERC20 asset [12](#0-11) . `ClaimAssets::claim_assets` silently skips assets whose `mint_asset` errors (only logs a debug trace) while still consuming/removing the `AssetTraps` entry [13](#0-12) . So even the paper trail (the trap counter) is destroyed on a failed claim attempt, and the ERC20 tokens remain sitting in `ERC20TransfersCheckingAccount` (`assets_common::ERC20Transactor` config `ERC20TransfersCheckingAccount`), permanently unreachable by any documented on-chain mechanism [14](#0-13) .

This mirrors the report's root cause precisely: the interface required to move an asset in one direction (`transfer`/`withdraw`) is implemented and validated correctly (return-value checking is in fact done well for `withdraw`/`deposit` in this codebase, unlike the naive Cooler.sol pattern), but the interface required for the *other* direction that a real, reachable failure path depends on (`mint_asset` for trap recovery) was simply never implemented for this asset class, so funds that reach that state are locked forever.

### Impact Explanation
Any ordinary, unprivileged user who submits an XCM program that withdraws ERC20 collateral and then encounters *any* subsequent instruction failure (network congestion causing a `DepositAsset` retry-pass failure, an ERC20 contract-side condition such as a paused/blacklisted recipient, insufficient weight for a later instruction, etc.) will have their ERC20 tokens irreversibly locked in `ERC20TransfersCheckingAccount`. There is no governance action, no extrinsic, and no XCM instruction in the current codebase that can recover them, because the one designed recovery path (`claim_assets` → `mint_asset`) is unimplemented for this asset type. This is a direct, deterministic loss of user funds triggerable without any privileged actor, matching the "High" severity class of the reference report (irreversible freezing of user-owned collateral).

### Likelihood Explanation
Likelihood is high for any Asset Hub Westend deployment that enables the ERC20 asset transactor: any user-submitted XCM program combining `WithdrawAsset` (ERC20) with a subsequent instruction is enough to trigger a trap; no attacker cooperation, timing, or privileged access is required — a normal deposit-destination failure (e.g., ED not met, or the ERC20 contract itself rejecting the second `transfer` for benign reasons) suffices to enter the unrecoverable trapped state.

### Recommendation
Implement `mint_asset` on `ERC20Transactor` mirroring `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` semantics — i.e., re-issue an `Erc20Credit` for the matched asset id/amount without performing any actual token movement, exactly as `FungibleTransferAdapter`/`FungiblesTransferAdapter`/`NonFungibleAdapter` do for their respective asset classes (`fn mint_asset(what: &Asset, context: &XcmContext) -> Result<AssetsInHolding, XcmError>`) [15](#0-14) . This allows `ClaimAssets::claim_assets` to successfully rebuild the trapped `Erc20Credit` and let the follow-on `DepositAsset` in the `claim_assets` extrinsic actually return the physical tokens held in `ERC20TransfersCheckingAccount` to the claimant.

### Proof of Concept
Concrete reproduction steps (not executed in this session — flagged as unverified):
1. Deploy a standard ERC20 contract via `pallet-revive` on Asset Hub Westend; fund `ALICE` with tokens and approve/transfer enough into her account.
2. Submit `pallet_xcm::execute` with a program: `WithdrawAsset(ERC20_asset, amount)` followed by an instruction guaranteed to fail after the withdraw succeeds (e.g., a `DepositAsset` to a fresh, non-existent beneficiary account whose recipient side purposely fails, or a `Trap(0)`).
3. Confirm via events/state: (a) the ERC20 contract's `Transfer` event fired moving `amount` from `ALICE` to `ERC20TransfersCheckingAccount` (real balance change, non-reversible at this point since it's outside the failing instruction's transactional scope); (b) `pallet_xcm::Event::AssetsTrapped` emitted with the ERC20 asset.
4. Call `pallet_xcm::claim_assets(origin: ALICE, assets: [ERC20_asset, amount], beneficiary: ALICE)`.
5. Expected (per design intent): tokens are returned to ALICE. Actual (per code trace above): `AssetTransactor::mint_asset` returns `Err(XcmError::AssetNotFound)` for the ERC20 asset since no tuple member implements `mint_asset` for it; `ClaimAssets::claim_assets` silently drops it, `claimed` holding is empty, `AssetsClaimed` event still fires, and the subsequent `DepositAsset` in the `claim_assets` program has nothing to deposit. `AssetTraps` entry is deleted. Tokens remain in `ERC20TransfersCheckingAccount` permanently.

This trace was derived entirely from static code reading of `erc20_transactor.rs`, `transact_asset.rs`, `pallet-xcm/src/lib.rs`, and `xcm-executor/src/lib.rs`; no test harness was actually run to confirm the runtime-level outcome, so this should be validated with an integration test on Asset Hub Westend (or the `pallet-revive-mock-network` fixtures already present in this repo) before being treated as fully confirmed.

impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
		let versioned = VersionedAssets::from(Assets::from(assets));
		let hash = BlakeTwo256::hash_of(&(&origin, &versioned));
		AssetTraps::<T>::mutate(hash, |n| *n += 1);
		Self::deposit_event(Event::AssetsTrapped {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		// TODO #3735: Put the real weight in there.
		Weight::zero()
	}
