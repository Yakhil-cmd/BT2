Webhook Signature Verification Uses a Different Repository Field Than Event Processing, Allowing Cross-Repository/Cross-Organization Forged Webhooks - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
This is a structural analog of the reported bug class: a value used to satisfy a security check (`repository_owner`, used to pick the HMAC secret) is not the same value that is later acted upon (`repository.full_name`, used to resolve the actual `Repository`/`Stack` that gets mutated). Because these two fields live in the same attacker-controlled, unsigned-until-verified JSON body, and because per-organization `webhook_secret` is documented as optional, an attacker can forge a signature "valid" for one (weak/unsecured) organization while making the payload act on a completely different organization's repository.

### Finding Description
`WebhooksController#verify_signature` selects which GitHub App/org config (and thus which `webhook_secret`) to validate the request against using a field pulled straight from the untrusted JSON body: [1](#0-0) 

That secret lookup feeds `GitHubApp#verify_webhook_signature`, which — critically — treats a blank/unset `webhook_secret` as automatic success: [2](#0-1) 

The docs explicitly describe the webhook secret as optional per-org: [3](#0-2) 

Once the (possibly no-op) signature check passes, `WebhooksController#create` dispatches the entire raw payload to handlers: [4](#0-3) 

Every handler, however, resolves the actual `Repository`/`Stack` to write to from a *different* JSON field — `repository.full_name` — not `repository.owner.login`/`organization.login` used for the signature check: [5](#0-4) 

The same pattern repeats across the pull-request handlers, which perform genuine state-changing actions (`archive!`, `unarchive!`, `find_or_create!`) keyed off `params.repository.full_name`: [6](#0-5) [7](#0-6) [8](#0-7) 

Nothing in `WebhooksController` or `Handler` cross-checks that `repository.full_name` is prefixed by `repository.owner.login`. This breaks the intended trust binding: `organization authenticated (via webhook_secret lookup key) == repository written (via full_name)`. Before the attacker's request, both fields would naturally agree because GitHub itself sends consistent payloads; after a forged request, they can be made to disagree arbitrarily, since the attacker controls the full JSON body of an unauthenticated POST to `/webhooks`.

### Impact Explanation
In a multi-tenant Shipit deployment (multiple orgs configured under `Shipit.github`, as documented in `config/secrets.development.shopify.yml`) where at least one configured organization has no `webhook_secret` set (an explicitly supported, "optional" configuration), an unprivileged internet attacker can:
1. Set `repository.owner.login` / `organization.login` to the org with no secret (or to any org whose secret has otherwise leaked), causing `verify_webhook_signature` to short-circuit `true`.
2. Set `repository.full_name` to `victim-org/victim-repo`, a repository tracked by a stack belonging to a completely different, properly-secured organization.
3. Trigger handler side effects against the victim stack: forcing a resync (`GithubSyncJob`) with an attacker-chosen `after` SHA via `PushHandler`, or archiving/unarchiving review stacks and mutating pull request state via the `PullRequest::*Handler` classes — all without ever possessing the victim org's webhook secret, an `ApiClient` token, or repository write access.

This is a cross-repository/cross-organization write achieved purely by exploiting a confused-deputy in the signature-to-payload binding — no privileged credential is required, matching the Critical "cross-repository writes" impact bar.

### Likelihood Explanation
Exploitability only requires network access to the public `/webhooks` endpoint and knowledge (or absence) of one organization's webhook secret in a multi-org Shipit install — a configuration explicitly supported and documented as optional. No GitHub account, Shipit session, or API token is needed. This makes the likelihood high in any deployment that (a) hosts more than one organization behind a single Shipit instance, or (b) has any organization configured without a webhook secret.

### Recommendation
Bind the signature-verification identity to the same field used for repository resolution: after selecting the GitHub App config, verify that `repository.full_name` (and any other repository-identifying field consumed by handlers) is consistent with `repository.owner.login`/`organization.login` used to pick the secret — or better, always require and enforce a `webhook_secret` per organization (removing the "return true unless webhook_secret" bypass), and additionally validate, before dispatch, that the resolved `Repository`'s `owner` matches the `organization`/`repository.owner.login` that was cryptographically authenticated.

### Proof of Concept
```
POST /webhooks HTTP/1.1
X-Github-Event: pull_request
X-Hub-Signature: sha1=<any-value-or-omitted>   # accepted because org "unsecured-org" has no webhook_secret configured

{
  "action": "closed",
  "number": 1,
  "pull_request": { ... valid shape ... },
  "repository": {
    "owner": { "login": "unsecured-org" },   // used only to pick (absent) secret -> signature check auto-passes
    "full_name": "victim-org/victim-repo"    // used by ClosedHandler#repository to resolve the actual Stack
  },
  "sender": { "login": "attacker" },
  "organization": { "login": "unsecured-org" }
}
```
`WebhooksController#verify_signature` looks up `Shipit.github(organization: "unsecured-org")`, whose `webhook_secret` is blank, so `verify_webhook_signature` returns `true` unconditionally. `PullRequest::ClosedHandler#repository` then resolves `Shipit::Repository.from_github_repo_name("victim-org/victim-repo")` and calls `review_stack.archive!`, mutating a stack that belongs to a completely different, secured organization.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
