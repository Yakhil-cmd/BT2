### Title
Stack-scoped API client tokens can read the CI/deploy status of any stack via `CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` scoped to a specific stack (`stack_id` set) can only touch that one stack, by resolving requested stacks through a scoped relation. `Shipit::Api::CCMenuController` overrides the `stack` lookup and resolves the requested stack directly from `Stack.from_param!(params[:stack_id])`, completely bypassing the client's `stack_id` scope. Any client credential (even one intentionally minted for read-only access to a single stack) can therefore be replayed against the CCMenu endpoint to read the build/deploy status of every other stack in the installation.

### Finding Description
`BaseController#stacks` restricts the queryable stack set to the one the authenticated `ApiClient` is bound to: [1](#0-0) 

and the default `stack` resolver used by every other API controller (`StacksController`, `TasksController`, `DeploysController`, etc.) goes through that scoped relation: [2](#0-1) 

`ApiClient` supports being bound to a single stack via `belongs_to :stack, optional: true`, and `check_permissions!` only checks the operation/scope name, not which stack the permission applies to: [3](#0-2) [4](#0-3) 

`CCMenuController` overrides `stack` to look up the stack directly from `params[:stack_id]` against the global `Stack` relation, ignoring `current_api_client.stack_id`: [5](#0-4) 

It also overrides `authenticate_api_client` to accept the token from a URL query parameter (rather than only Basic-Auth), which is how the token is meant to be embedded in shareable CI-status-board URLs: [6](#0-5) 

The binding that should hold is: *the set of stacks a token authorizes == the set of stacks it can touch*. Before this bug, a stack-scoped `read:stack` token can only reach the one stack it was created for (via `BaseController#stack`, using `stacks.from_param!`). Through `CCMenuController#stack`, the same token can be replayed with an arbitrary `stack_id` and `Stack.from_param!` will resolve any stack in the installation, because the scoping check is never consulted on this code path.

### Impact Explanation
This is an unauthenticated-for-other-stacks read of stack state: an attacker who legitimately holds (or has been handed, e.g. embedded in a CCMenu monitoring-board URL as produced by `CCMenuUrlController#fetch`) a low-privilege, single-stack-scoped `read:stack` token can enumerate `stack_id` values and pull the CI/build/deploy status XML (`deploys_and_rollbacks`, last build status/label/time) for every stack managed by the Shipit instance, not just the one the token creator intended to expose. This matches the "unauthenticated read of stack state" High-severity category, since the token's intended authorization boundary (one stack) is silently widened to all stacks by this single controller.

### Likelihood Explanation
Likelihood is moderate-to-high wherever stack-scoped API clients exist (the `ApiClient.stack_id` column and `BaseController#stacks` scoping mechanism exist specifically to support this use case, e.g. `here_come_the_walrus` fixture demonstrates a stack-scoped client). Any holder of such a token — which by design may be distributed more broadly than a full-access token (e.g., embedded in a CI dashboard URL) — can trivially exploit this by changing the `stack_id` path segment on the `ccmenu` route; no additional secrets, signatures, or privileged access are required beyond the token itself.

### Recommendation
Make `CCMenuController#stack` reuse the scoped `stacks` relation from `BaseController` instead of querying `Stack` directly, e.g.:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```
so that a client bound to `stack_id` can never resolve a different stack, consistent with every other API controller.

### Proof of Concept
1. Create/obtain an `ApiClient` scoped to `stack_id: A` with `permissions: ['read:stack']` (as supported by the `ApiClient` model and demonstrated by the `here_come_the_walrus` fixture) — for example, one distributed via a CCMenu URL for stack A as built by `CCMenuUrlController#fetch`.
2. Request `GET /api/stacks/<owner_b>/<repo_b>/<env_b>/ccmenu?token=<token_for_stack_A>` where `owner_b/repo_b/env_b` identifies a different stack B that the client was never granted access to.
3. Because `CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` rather than `stacks.from_param!(params[:stack_id])`, the request succeeds and returns stack B's CCMenu XML (build status, last build label/time), even though the authenticated `ApiClient` is scoped to stack A only.

# frozen_string_literal: true

require 'uri'

module Shipit
  class CCMenuUrlController < ShipitController
    def fetch
      uri = URI(api_stack_ccmenu_url(stack_id: stack.to_param))
      uri.query = { 'token' => client.authentication_token }.to_query
      render(json: { ccmenu_url: uri.to_s })
    end

    private

    def client
      @client ||= ApiClient.create_with(permissions: %w[read:stack])
                           .find_or_create_by!(creator: current_user, name: 'CCMenu Client')
    end

    def stack
      @stack ||= Stack.from_param!(params[:stack_id])
    end
  end
end
