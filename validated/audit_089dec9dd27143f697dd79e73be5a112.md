## Title
`StatusHandler#process` parses `branches` but never uses it as scope, leaving `Commit.where(sha:)` completely unscoped by branch or repository - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`StatusHandler`'s `ExplicitParameters` schema accepts a `branches` array (mirroring GitHub's real `status` event payload), but `process` never reads `params.branches` — it only uses `params.sha` to look up commits globally. This confirms the branch data in the payload provides zero actual scoping, and the real (and only) selector is a bare `sha` lookup across every stack in the installation.

### Finding Description
The claimed binding — "branch list present in the payload == branch scope enforced during `Commit.where(sha:)`" — is **false**, as expected. Tracing the code: [1](#0-0) 

`params` schema declares `accepts :branches, Array do requires :name, String end` at lines 15-17, but `process` (lines 20-24) only calls `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }`. Neither `params.branches` nor any repository/stack identifier from the payload is read here. `Commit#create_status_from_github!` (`app/models/shipit/commit.rb:165-169`) forwards straight into `statuses.replicate_from_github!(stack_id, github_status)` using the commit's own `stack_id` — again, no branch filter, no cross-check against the inbound payload's `repository.full_name`.

`Commit.where(sha:)` is a bare `ActiveRecord` query with no `stack_id` or repository join [2](#0-1) , so it matches every `Commit` row across every `Stack` in the database sharing that SHA, confirmed by the schema's `sha`+`stack_id` composite unique index (not a per-repo unique index) at `db/migrate/20170524104615_index_commits_on_stack_id_and_sha.rb:1-5` and `test/dummy/db/schema.rb:79-86`.

`WebhooksController#verify_signature` only authenticates that the payload's `organization`/`repository.owner.login` matches a Shipit-configured GitHub App's `webhook_secret` [3](#0-2) ; it performs no check that the target commit's actual owning stack/repository matches the payload's `repository.full_name`. So even a correctly-signed webhook for org A can mutate a commit belonging to a stack tracked under a different repository, provided the SHA values collide (e.g., shared git history between a fork and its upstream, or any two stacks that happen to track the same commit).

### Impact Explanation
If an attacker can get a validly-signed `status` webhook accepted for any org Shipit trusts, and that SHA also exists in another tracked stack (a very plausible scenario for forks of the same upstream repository, since forks routinely share identical commit SHAs with upstream), `create_status_from_github!` will write a `Status` row against the foreign stack's commit, potentially flipping CI state (`success`/`failure`/`pending`) for a repository the attacker's webhook did not originate from. Since commit state feeds directly into `deployable?` (`app/models/shipit/commit.rb:227-229`), this can spoof green CI on a foreign stack's commit and unlock an unauthorized deploy — matching the Critical "payload for one repository mutating another's stack/commit" category.

### Likelihood Explanation
Exploitation is gated by two independent preconditions that are outside `StatusHandler` itself: (1) the attacker must obtain a webhook signed with a `webhook_secret` for an organization already configured in Shipit (`Shipit.github(organization:)`), which usually implies some legitimate write access to a repo in that org, and (2) SHA collision with a commit in a *different* tracked stack, realistic mainly for forks sharing upstream history. Given those preconditions, the vulnerability is fully repeatable and requires no further guessing (SHAs are public, deterministic, and enumerable via GitHub's API). The `branches` field itself provides no mitigating friction — it is dead code with respect to authorization, so its presence in the schema is purely cosmetic and does not narrow the attack surface at all.

### Recommendation
Scope the commit lookup in `StatusHandler#process` to the stack(s) actually associated with `payload.dig('repository', 'full_name')` (e.g., `Stack.where(repo_name: ...).commits.where(sha: params.sha)`), instead of a global `Commit.where(sha:)`. Remove or genuinely enforce the `branches` parameter if repository/branch scoping is intended to be a defense-in-depth signal.

### Proof of Concept
```ruby
# test/models/webhooks/handlers/status_handler_test.rb
test "process never reads params.branches and matches commits across stacks by sha alone" do
  foreign_stack = shipit_stacks(:shipit) # stack A
  other_stack   = shipit_stacks(:cyclimse) # stack B, different repo
  shared_sha    = "deadbeef" * 5

  commit_a = foreign_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "x")
  commit_b = other_stack.commits.create!(sha: shared_sha, author: shipit_users(:walrus),
    committer: shipit_users(:walrus), authored_at: Time.now, committed_at: Time.now, message: "y")

  params = ExplicitParameters::Parameters.new(
    sha: shared_sha, state: "success", branches: [{ name: "totally-unrelated-branch" }]
  )
  params.expects(:branches).never # branches accepted but never consulted

  Shipit::Webhooks::Handlers::StatusHandler.new.call(params.to_h)

  assert_equal 1, commit_a.reload.statuses.count
  assert_equal 1, commit_b.reload.statuses.count # foreign stack mutated despite unrelated branch
end
```
