### Title
Stack-Scoped `ApiClient` Tokens Can Read Any Stack's Build Status via `Api::CCMenuController` - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
Every other Shipit API resource controller resolves the target `Stack` through `Api::BaseController#stack`, which is scoped to the stack the authenticating `ApiClient` was authorized for. `Api::CCMenuController` overrides `stack` to bypass this scoping and resolve the stack directly from an unchecked `Stack.from_param!(params[:stack_id])` call, so any stack-scoped token can be replayed against an arbitrary `stack_id` to read another stack's build status.

### Finding Description
`Api::BaseController` enforces per-token stack scoping through two cooperating methods: [1](#0-0) 

`stacks` restricts the query to `current_api_client.stack_id` when the client is scoped to one, and `stack` resolves `params[:stack_id]` only from that restricted relation. This is the binding the rest of the API relies on: *the stack a token authorizes* must equal *the stack a request touches*.

`Api::CCMenuController` breaks this binding by defining its own `stack` method that ignores the `stacks` scoping entirely: [2](#0-1) 

```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end
```

This resolves against `Stack.from_param!`, i.e. **all** stacks, not `stacks.from_param!`. The controller's only authorization check is `require_permission :read, :stack`, which via `ApiClient#check_permissions!` only verifies the token's `permissions` array contains `read:stack` — it never checks `stack_id`: [3](#0-2) 

Tokens intended to be scoped to a single stack are minted exactly this way by `CCMenuUrlController`, which creates a `read:stack`-only `ApiClient` (no `stack` association is set, so the intent is a general "CCMenu Client" token that is embedded in a URL for one particular stack): [4](#0-3) 

The generated URL embeds `stack_id` in the query string alongside the token (`api_stack_ccmenu_url(stack_id: stack.to_param)` plus `token: client.authentication_token`). Because `authenticate_api_client` in `CCMenuController` accepts the token from the query string, and `stack` is resolved with no scoping, anyone holding one such token/URL can simply change the `stack_id` parameter to any other stack in the installation and read its build status, last build label/time, lock state, etc. — data belonging to stacks the token was never authorized to see.

Every other API resource (`Api::TasksController`, `Api::OutputsController`, `Api::DeploysController`, `Api::RollbacksController`, `Api::CommitsController`, `Api::MergeRequestsController`, `Api::ReleaseStatusesController`) relies on `BaseController#stack`/`#stacks` and is therefore correctly scoped; `CCMenuController` is the sole outlier that resolves the stack outside the scoping mechanism.

### Impact Explanation
This is a cross-stack authorization escape: a token/URL that is only meant to expose one stack's CI status (often embedded in third-party CCTray/CI-status tools, which is a query-string bearer credential with weaker handling expectations) can be used to enumerate and read build status, last build label, lock state, and web URL of **every** stack managed by the Shipit instance. This matches the "unauthenticated read of stack state" class of impact once the (weakly protected, query-string) token is available, since the token grants far broader access than its intended single-stack scope.

### Likelihood Explanation
Any holder of a single CCMenu URL — which is designed to be shared with external CI dashboard tools and transmitted as a URL query parameter rather than an Authorization header — can trivially modify the `stack_id` query parameter to pivot to other stacks. No further privilege or interaction is required; enumerating `stack_id` values (stack slugs are typically `owner/repo/environment`-derived and often guessable/discoverable) is sufficient to exercise the bug.

### Recommendation
Change `Api::CCMenuController#stack` to resolve through the scoped `stacks` relation exposed by `BaseController`, exactly as every other API controller does:

```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

This restores the invariant that a token can only ever resolve stacks it was actually scoped to, consistent with `Api::BaseController#stacks`.

### Proof of Concept
1. Visit `/ccmenu_url/*stack_id` for `stack-a` as an authorized user; Shipit creates (or reuses) a `read:stack`-only `ApiClient` named "CCMenu Client" and returns a URL such as:
   `https://shipit.example.com/api/stack-a/ccmenu.xml?token=<signed-token>`
   (see `CCMenuUrlController#fetch`).
2. Take that URL/token and request a different stack by only changing the `stack_id` segment:
   `https://shipit.example.com/api/stack-b/ccmenu.xml?token=<same-signed-token>`
3. Because `Api::CCMenuController#stack` calls `Stack.from_param!(params[:stack_id])` instead of `stacks.from_param!(params[:stack_id])`, the token — never authorized for `stack-b` — successfully returns `stack-b`'s CCTray XML (build status, last build label/time, lock state), confirmed by `require_permission :read, :stack` only checking the `read:stack` permission string, not `stack_id`.

# frozen_string_literal: true

module Shipit
  module Api
    class CCMenuController < BaseController
      require_permission :read, :stack

      class NoDeploy
        def id
          0
        end

        def ended_at
          Time.now.utc
        end

        def running?
          false
        end
      end

      def show
        latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
        render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
      end

      private

      def stack
        @stack ||= Stack.from_param!(params[:stack_id])
      end

      def authenticate_api_client
        @current_api_client = ApiClient.authenticate(params[:token])
        super unless @current_api_client
      end
    end
  end
end
