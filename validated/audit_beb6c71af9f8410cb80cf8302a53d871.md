### Title
Webhook Signature Verified Against Attacker-Controlled Organization While Payload Fields Act on Any Stack/Commit - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to validate a webhook's HMAC signature against by reading the *unauthenticated* JSON body (`repository.owner.login` / `organization.login`). Once that check passes, the handlers dispatched by `Shipit::Webhooks.for_event(event)` act on entirely different, independently attacker-controlled fields of the same payload (`repository.full_name`, `sha`, etc.) which are never cross-checked against the organization whose secret validated the signature. On a multi-tenant Shipit instance (explicitly supported via `secrets.github` keyed by organization, see `Shipit.github_app_config`), any org onboarded to the instance can forge webhooks that are "signature-valid" for their own org but that write to or read from a completely different org/repository/stack.

### Finding Description
`verify_signature` computes the signing organization from the raw, unauthenticated payload: [1](#0-0) [2](#0-1) 

`repository_owner` is taken from `params.dig('repository', 'owner', 'login')` or the fallback `params.dig('organization', 'login')` — both fully attacker-controlled JSON fields in the raw POST body, read *before* any signature check occurs. This value is used only to select which `GitHubApp`/`webhook_secret` to verify against: [3](#0-2) 

Once `verify_webhook_signature` succeeds (an HMAC-SHA1 comparison against the secret of the *selected* organization), the same raw payload is dispatched to handlers, which resolve the *target* repository/commit from separate, unrelated fields:
- `PushHandler`/`Handler#stacks` resolves the repository by `payload.dig('repository', 'full_name')`, independent of `repository_owner`: [4](#0-3) [5](#0-4) 
- `StatusHandler` is even less scoped: it updates **any** `Commit` in the entire database matching `params.sha`, with no repository/org check at all: [6](#0-5) 

The security-relevant binding the signature is supposed to enforce is "this payload was authorized by GitHub for organization X, therefore X may act on X's resources." Instead, the code creates: `signing_organization (repository.owner.login) == target_resource_organization (repository.full_name / commit.sha)` as an *assumed* equality that is never enforced. Because `repository_owner` and `repository.full_name`/`sha` are independent, unauthenticated JSON keys in the same attacker-supplied body, an attacker can set them to different values, breaking the binding.

### Impact Explanation
On a multi-organization Shipit deployment (a configuration the engine itself supports, see `github_app_config`/`github_organizations` in `lib/shipit.rb`), any organization/customer that has legitimately been onboarded (and thus knows or can obtain a valid signature for its own `webhook_secret`, e.g. by triggering real GitHub webhook events on its own repos, since GitHub signs with that org's registered secret) can forge a webhook payload where:
- `repository.owner.login` = attacker's own org (so `verify_signature` validates against the attacker's own, legitimately-known secret), while
- `repository.full_name` = a victim org/repo, or `sha` = a victim's commit SHA.

This allows the attacker to:
- Force a `push` event to trigger `GithubSyncJob`/`stack.sync_github` on a victim stack they do not own, or
- Forge a `status` (or similarly-scoped) webhook to flip a victim's commit to `success` state regardless of real CI results, which can satisfy Continuous Delivery deployability gates and lead to an **unauthorized deploy** of that commit.

This matches the required "Critical" impact bar (unauthorized deploy) because it crosses a tenant/organization trust boundary using only capabilities of an unprivileged, unrelated GitHub organization onboarded to the same Shipit instance — no Shipit session, API token, or admin credential is required.

### Likelihood Explanation
Likelihood is meaningful specifically in multi-tenant/multi-org Shipit deployments where the `secrets.github` config holds more than one organization's App credentials (a mode the code explicitly implements). In a single-organization deployment (`github_default_organization` nil-org fallback) there is only one webhook secret, so this specific cross-tenant exploitation path collapses (still, the design flaw of trusting attacker-supplied JSON to pick the verification key before verification is present, but there is no second, weaker-trust org to pivot from).

### Recommendation
- After signature verification succeeds, re-derive the organization/repository actually referenced by the payload (e.g. `repository.full_name`, `sha`'s owning repository) and assert it matches the organization whose secret was used to verify the signature, rejecting mismatches.
- Do not use attacker-supplied JSON fields to select the verification secret before the signature has been checked; instead, verify the signature against every configured organization's secret you're willing to trust for the endpoint, or bind webhooks to per-organization endpoints (`/webhooks/:organization`) so the *route*, not payload content, determines the expected secret.
- Scope `StatusHandler` (and any other handler resolving records solely by attacker-controlled identifiers like `sha`) to the repository declared in `payload.dig('repository', 'full_name')`, and ensure that repository belongs to the verified organization.

### Proof of Concept
1. Deploy Shipit configured for two organizations in `secrets.github`: `attacker-org` and `victim-org`, each with its own GitHub App/`webhook_secret` (a supported configuration per `Shipit.github_app_config`).
2. The attacker legitimately controls `attacker-org` and can obtain a validly-signed webhook for it (e.g. by pushing to a repo it owns and capturing GitHub's `X-Hub-Signature`, or since they set up the App they know the secret).
3. Attacker replays/crafts a POST to `/webhooks` with:
   - `X-Github-Event: status`
   - `X-Hub-Signature`: HMAC computed with `attacker-org`'s `webhook_secret` over the modified body
   - body: `{"sha": "<victim-commit-sha>", "state": "success", "repository": {"owner": {"login": "attacker-org"}, "full_name": "attacker-org/some-repo"}}`
4. `verify_signature` computes `repository_owner = "attacker-org"`, loads `attacker-org`'s secret, and the forged signature validates successfully.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` — matching the victim's commit regardless of organization — and creates a `success` status on it via `commit.create_status_from_github!`, potentially satisfying Continuous Delivery deployability checks for `victim-org`'s stack and enabling an unauthorized deploy. # frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

module Shipit
  module Webhooks
    module Handlers
      class StatusHandler < Handler
        params do
          requires :sha, String
          requires :state, String
          accepts :description, String
          accepts :target_url, String
          accepts :context, String
          accepts :created_at, String

          accepts :branches, Array do
            requires :name, String
          end
        end

        def process
          Commit.where(sha: params.sha).each do |commit|
            commit.create_status_from_github!(params)
          end
        end
      end
    end
  end
end
