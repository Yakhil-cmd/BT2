### Title
Webhook signature is verified against the organization derived from `repository.owner.login`/`organization.login`, but handlers act on the repository derived from the independent `repository.full_name` field, allowing cross-organization webhook forgery - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
Shipit supports multi-tenant GitHub App configuration where each onboarded GitHub organization has its own `webhook_secret` [1](#0-0) , confirmed by the multi-org fixture `test/dummy/config/secrets_double_github_app.yml` where `OrgOne` and `OrgTwo` each carry independent `webhook_secret`s. `WebhooksController#verify_signature` picks *which* organization's secret to validate the HMAC against by reading `repository.owner.login` (falling back to `organization.login`) straight out of the still-unverified JSON body, before the signature is checked [2](#0-1) [3](#0-2) . Once the HMAC matches (proving only that the sender knows *that organization's* secret), the full raw payload is handed to every registered handler unmodified: `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` [4](#0-3) .

Handlers, however, resolve which repository/stack to act on using a *different* payload field: `payload.dig('repository', 'full_name')` [5](#0-4) , used directly or via `params.repository.full_name` in `PushHandler`, and all `PullRequest::*Handler`s (`OpenedHandler`, `ClosedHandler`, `LabeledHandler`, `UnlabeledHandler`, `ReopenedHandler`, `EditedHandler`, `LabelCapturingHandler`) [6](#0-5) [7](#0-6) [8](#0-7) .

Nothing in `verify_signature` or in these handlers checks that `repository.owner.login` (the field used to pick the verifying secret) is consistent with the owner segment of `repository.full_name` (the field used to select the actual repository/stack). This breaks the intended binding: `organization that authenticated == repository that is written`.

### Finding Description
GitHub itself always produces payloads where `repository.owner.login` and the owner segment of `repository.full_name` agree, so this discrepancy can never arise from a legitimate GitHub delivery. But `WebhooksController#create` accepts POSTs from anyone on the internet who can produce a valid HMAC for *some* organization configured on the Shipit instance — it does not require the request to originate from GitHub's IP range or from GitHub's own delivery mechanism [9](#0-8) .

An attacker who is a legitimate collaborator/admin of `OrgOne` (onboarded into the same multi-tenant Shipit instance) knows or controls `OrgOne`'s `webhook_secret` (e.g., because they configured OrgOne's GitHub App integration or can trigger real webhook deliveries and observe raw payload/signature pairs). They can craft an arbitrary JSON body where:
- `repository.owner.login = "OrgOne"` and/or `organization.login = "OrgOne"` (so `verify_signature` looks up and validates against `OrgOne`'s secret, which the attacker legitimately possesses), while
- `repository.full_name = "OrgTwo/victim-repo"` (a repository belonging to a completely different, unaffiliated organization also hosted on the same Shipit instance).

`verify_signature` will succeed (`Shipit.github(organization: 'OrgOne').verify_webhook_signature(...)` validates fine against the attacker-known secret) [10](#0-9) , and the request proceeds to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` using the forged `repository.full_name` [4](#0-3) .

Downstream, `Handler#stacks` / `#repository_name` and every `PullRequest::*Handler#repository` resolve `Shipit::Repository.from_github_repo_name(params.repository.full_name)`, which now resolves to `OrgTwo/victim-repo` — a repository the attacker never authenticated for — and take real actions against it:
- `PushHandler#process` enqueues a sync of `OrgTwo`'s stacks to an attacker-chosen `expected_head_sha` [11](#0-10) .
- `PullRequest::ClosedHandler#process` archives `OrgTwo`'s review stack [12](#0-11) , and `ReviewStackAdapter#archive!` deprovisions the stack [13](#0-12) .
- `PullRequest::LabeledHandler`/`UnlabeledHandler` archive/unarchive `OrgTwo` review stacks based on attacker-supplied labels [14](#0-13) .

### Impact Explanation
This is a cross-organization/cross-repository write: an unprivileged attacker (with respect to `OrgTwo`, holding no Shipit session, API token, or GitHub write access to `OrgTwo`'s repository) can archive, unarchive, deprovision, or force a `GithubSyncJob` sync against another organization's stack purely by forging a webhook body that decouples the field used for signature-org lookup (`repository.owner.login`/`organization.login`) from the field used for repository resolution (`repository.full_name`). This matches the "Critical: cross-repository writes / unauthorized deploy or rollback" bar, since a `sync_github(expected_head_sha:)` call combined with continuous-deployment configuration can influence which commit is deployed, and stack archive/deprovision is a destructive write on a repository the attacker never proved control of.

### Likelihood Explanation
Requires the attacker to be a legitimate, low-privilege participant of at least one other organization already onboarded to the same multi-tenant Shipit instance (a realistic scenario for shared/internal deployment platforms serving multiple teams/orgs), and to know that org's `webhook_secret`. Given that, forging the payload is trivial (no protocol-level enforcement of `repository.owner.login == full_name`'s owner segment).

### Recommendation
In `WebhooksController#verify_signature`/`#create`, after resolving `repository_owner` and validating the signature, re-derive the organization from every repository-bearing field used downstream (e.g., the owner segment of `repository.full_name`, `organization.login`) and reject the request (422) if it does not exactly match the organization whose secret validated the signature. Alternatively, have `Handler#repository_name` and all handler `#repository`/`#stacks` methods take the authenticated organization as an explicit, separately-passed argument and cross-check it against the owner segment of `full_name` before resolving any `Repository`/`Stack`.

### Proof of Concept
1. Shipit is configured with two organizations, `OrgOne` and `OrgTwo`, each with a distinct `webhook_secret` (as in `test/dummy/config/secrets_double_github_app.yml`).
2. Attacker is a legitimate admin of `OrgOne`'s GitHub App integration and therefore knows `OrgOne`'s `webhook_secret`.
3. Attacker crafts a `pull_request` "closed" event JSON body:
```json
{
  "action": "closed",
  "number": 1,
  "pull_request": { "...": "valid pull_request object" },
  "repository": { "owner": { "login": "OrgOne" }, "full_name": "OrgTwo/victim-repo" },
  "sender": { "login": "attacker" }
}
```
4. Attacker computes `X-Hub-Signature: sha1=HMAC-SHA1(OrgOne_webhook_secret, raw_body)` and POSTs to `/github/webhooks` with `X-Github-Event: pull_request`.
5. `verify_signature` resolves `repository_owner` = `"OrgOne"` [3](#0-2) , fetches `Shipit.github(organization: "OrgOne")`, and successfully validates the signature against the attacker-known secret.
6. `PullRequest::ClosedHandler` resolves `repository` via `params.repository.full_name` = `"OrgTwo/victim-repo"` [15](#0-14)  and archives/deprovisions `OrgTwo`'s review stack, even though the signature only ever proved knowledge of `OrgOne`'s secret.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```
