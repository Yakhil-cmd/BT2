### Title
Unbounded oracle-address array in `in data feed` / `in merkle` spending conditions causes repeated CPU-exhaustion during every re-validation - (File: definition.js)

### Summary
The GnuTLS CVE is a CPU/memory exhaustion caused by processing an unbounded list of entries (SANs / name constraints) embedded in an attacker-supplied certificate, with no cap on the number of entries examined per validation pass. `ocore` has the same bug-class weakness in the `in data feed` and `in merkle` address-definition operators: the `arrAddresses` array is iterated and cryptographically checked (`isValidAddress`) with **no length limit**, unlike every other array accepted in the same definition/formula validators.

### Finding Description
In `definition.js`, the `evaluate()` function used by both `validateDefinition` (parses new address/asset definitions) and `validateAuthentifiers` (re-checked on **every** unit that spends from the address) handles the `in data feed` and `in merkle` operators: [1](#0-0) [2](#0-1) 

Both branches only check `isNonemptyArray(arrAddresses)` and then loop over the entire array calling `isValidAddress()` (base32 decode + checksum computation via `chash.isChashValid`) for every element, before any complexity bookkeeping happens: [3](#0-2) [4](#0-3) 

Complexity/op accounting for these ops is a flat, post-hoc addition (`complexity += arrAddresses.length-1`), and the actual `MAX_COMPLEXITY`/`MAX_OPS` guard that aborts evaluation is only checked at the top of `evaluate()`, i.e. **once per operator node**, not once per array element: [5](#0-4) 

Every other array accepted by definition/formula validation in this codebase has an explicit hard cap enforced *before* the expensive per-element work: denominations (`MAX_DENOMINATIONS_PER_ASSET_DEFINITION`), poll choices (`MAX_CHOICES_PER_POLL`), `search_param_list` pairs (5), array literals (100), `{}` statement blocks (1000), `delete`/`with_selectors` selectors (30): [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9) 

`arrAddresses` in `in data feed`/`in merkle` is the sole exception with no such cap.

Critically, the comment in `validateAuthentifiers` confirms this validation is **not a one-time cost**: the full address definition (including this loop) is re-evaluated for every single unit spent from that address, not just when the definition is first created: [11](#0-10) 

### Impact Explanation
An address (or asset spending/issue condition) owner can define spending conditions such as `['in data feed', [arrAddresses, feed_name, '=', value]]` where `arrAddresses` contains tens of thousands of syntactically valid-looking base32 strings. Because no cap exists, this passes `validateDefinition` once at definition time, and thereafter **every unit** built by that address (or referencing that asset condition) forces every full node and the hub to re-run the entire `isValidAddress` loop over the whole `arrAddresses` array in `validateAuthentifiers`, before the flat complexity penalty can trigger a bail-out. Since this happens on every validating node for every transaction from the account, an attacker can force repeated, sustained CPU exhaustion across the network by simply posting ordinary payment units from a wallet controlled by such a definition — directly matching the "network unable to confirm new units" impact class, without requiring any privileged, hub, or peer role.

### Likelihood Explanation
Likelihood is high: defining and using such an address is a completely normal, unprivileged action (any user can author an address definition and later spend from it), requires no special network position, and the missing bound is a straightforward oversight relative to the capped-array pattern used everywhere else in the same file.

### Recommendation
Add an explicit maximum length check on `arrAddresses` for both `in data feed` and `in merkle` (e.g. a new `constants.MAX_ADDRESSES_PER_ORACLE_CONDITION`, similar in spirit to `MAX_DENOMINATIONS_PER_ASSET_DEFINITION`/`MAX_CHOICES_PER_POLL`), enforced before the per-element `isValidAddress` loop in `definition.js`. Additionally, increment/check `complexity`/`count_ops` inside the loop (per address) rather than only after it, so the existing `MAX_COMPLEXITY`/`MAX_OPS` guard can abort mid-loop as it does for other operators.

### Proof of Concept
1. Craft an address definition:
```
['address', ['in data feed', [
    [ /* 20,000 valid-looking base32 addresses */ ],
    'FEED_NAME', '=', 'value'
]]]
```
2. Post a unit defining this address (passes `validateDefinition` once, cost paid once).
3. Repeatedly post ordinary payment units spending from this address; each one forces every validating node to call `chash.isChashValid` 20,000 times inside `validateAuthentifiers` → `evaluate()` in `definition.js` before returning, per [3](#0-2)  and [12](#0-11) , imposing repeated, disproportionate CPU cost on the whole validating network for each transaction.
