## Title
API client scoped to one stack can read the build status of any stack via the CCMenu endpoint - (File: `app/controllers/shipit/api/ccmenu_controller.rb`)

### Summary
`Shipit::Api::CCMenuController` overrides the stack-lookup helper inherited from `Shipit::Api::BaseController` with a version that drops the per-client stack scoping, so a stack-scoped `ApiClient` token — one created with `stack_id` set so it may only interact with a single stack — can be used to read the build status of any stack in the installation.

### Finding Description
`Shipit::Api::BaseController` defines the scope binding that every other API controller relies on to enforce "a client may only touch the stack it was scoped to": [1](#0-0) 

`stacks` restricts the queryable relation to `current_api_client.stack_id` when the client is scoped, and `stack` looks the requested `params[:stack_id]` up through that restricted relation, raising a not-found error if the requested stack isn't the one the client is bound to.

`CCMenuController`, however, redefines `stack` to bypass this scoping entirely, resolving directly against the full `Stack` relation: [2](#0-1) 

The controller still declares `require_permission :read, :stack`, which only checks that the token carries the `read:stack` *permission string* — it never checks whether the specific `stack_id` requested matches `current_api_client.stack_id`: [3](#0-2) [4](#0-3) 

This breaks the binding **"a stack a token authorises" (`ApiClient#stack_id`) vs. "a stack it touches" (`params[:stack_id]` resolved in `CCMenuController#stack`)**. Any caller holding a token for an `ApiClient` scoped to Stack A — e.g. one legitimately created for CCMenu integration via `CCMenuUrlController#client`, which always creates a narrowly scoped, `read:stack`-only client — can instead pass any other `stack_id` and read that unrelated stack's build/deploy status. [5](#0-4) 

Compare with `Api::StacksController`, which correctly relies on the inherited, scope-checked `stack`/`stacks` helpers (as covered by "an api client scoped to a stack will only see that one stack" in `test/controllers/api/stacks_controller_test.rb`), while `CCMenuController`'s own test suite never exercises this cross-stack case — every test in `test/controllers/api/ccmenu_controller_test.rb` only requests the same `@stack` the authenticated client is scoped to.

### Impact Explanation
This is an escalation into the `Shipit::ApiClient` stack-scoping authorization model: a credential intentionally minted with access limited to a single stack (the entire purpose of `ApiClient#stack_id`) can read another stack's state (name, activity, `lastBuildStatus`, `lastBuildLabel`, `lastBuildTime`, `webUrl`) it was never authorized to see. Per the rubric this is a High severity finding — "escalation into ... authorization" / unauthorized read of stack state — achieved purely by an attacker who already holds one legitimately-scoped, low-privilege API token (e.g. leaked from a CCMenu integration URL) and no other trust boundary.

### Likelihood Explanation
High. No special privileges beyond possessing any single stack-scoped `read:stack` API token are required (such tokens are routinely embedded in CCMenu URLs shared with CI dashboards, per `CCMenuUrlController#fetch`). The attacker only needs to change the `stack_id` request parameter; the vulnerable code path (`Stack.from_param!` instead of `stacks.from_param!`) is unconditionally hit for every request to this controller.

### Recommendation
Remove the `stack` override in `CCMenuController` (or reimplement it to use the inherited, scope-checked `stacks` relation), so lookups are always constrained by `current_api_client.stack_id` exactly as in `BaseController`:
```ruby
def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
```

### Proof of Concept
1. Create a stack-scoped API client for Stack A: `POST /api_clients` with `permissions: ["read:stack"]`, or via `CCMenuUrlController#fetch` for Stack A, obtaining `client.authentication_token`.
2. Issue `GET /api/stacks/:stack_id_of_A/ccmenu?token=<token>` — succeeds as expected.
3. Issue `GET /api/stacks/:stack_id_of_B/ccmenu?token=<token>` using the *same token* but a different stack's `stack_id` — the request succeeds and returns Stack B's build status, even though the token's `ApiClient#stack_id` is bound to Stack A only, demonstrating the scope bypass in `CCMenuController#stack`.
