### Title
CCMenu API endpoint bypasses per-stack `ApiClient` scoping, allowing a stack-scoped token to read the state of any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient` records can be scoped to a single `Stack` via `belongs_to :stack, optional: true` [1](#0-0) , and the generic `Api::BaseController#stack` helper enforces this binding by resolving stacks only from the set the token is authorized for [2](#0-1) . `Api::CCMenuController`, however, overrides `#stack` to resolve directly from the unrestricted `Stack` relation using the client-supplied `params[:stack_id]`, never consulting the token's `stack_id` scope [3](#0-2) . This breaks the equality "stack the token authorizes == stack the request touches", the exact class of bug called out in the analog rules (a stack a token authorises versus a stack it touches).

### Finding Description
`ApiClient#stack_id?` is meant to restrict a token's visibility to a single stack. `Api::BaseController` implements this by filtering the queryable stacks set:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [2](#0-1) 

This is the mechanism validated by `test "an api client scoped to a stack will only see that one stack"` in the stacks controller tests [4](#0-3) , and by the `here_come_the_walrus` fixture, an `ApiClient` scoped to the `shipit` stack with only `read:stack` permission [5](#0-4) .

`Api::CCMenuController` only enforces the coarse-grained `read:stack` permission via `require_permission :read, :stack` [6](#0-5) , but its `#stack` method is redefined to bypass the scoped `stacks` relation entirely:
```ruby
def stack
  @stack ||= Stack.from_param!(params[:stack_id])
end

def authenticate_api_client
  @current_api_client = ApiClient.authenticate(params[:token])
  super unless @current_api_client
end
``` [7](#0-6) 

`ApiClient.check_permissions!` only checks that the `"read:stack"` string is present in the token's permission list; it never checks `stack_id` [8](#0-7) . Consequently, a token that legitimately authorizes only `read:stack` on Stack A (e.g. `here_come_the_walrus`) can be presented at `Api::CCMenuController#show` with an arbitrary `stack_id` for Stack B and will successfully render Stack B's CI/build status, name, and last build info, none of which the token's creator ever intended to expose.

### Impact Explanation
This is an authenticated but unauthorized cross-stack read: possession of any valid `read:stack` token (including narrowly-scoped ones distributed for CCMenu integration, per `CCMenuUrlController#client`, which itself creates `read:stack`-only tokens [9](#0-8) ) is sufficient to read the state (build status, last deploy) of every other stack hosted on the Shipit instance. This matches the "unauthenticated read of stack state" / authorization-scope-escalation impact category explicitly listed as High severity.

### Likelihood Explanation
Exploitation requires no privileged access beyond possessing (or being handed, e.g. via the `ccmenu_url` link feature) a single narrowly-scoped `read:stack` token, and only requires modifying the `stack_id` request parameter — a trivial, always-reachable action for any holder of such a token.

### Recommendation
Change `Api::CCMenuController#stack` to reuse the scoped `stacks` relation from `BaseController` (i.e. `stacks.from_param!(params[:stack_id])`) instead of querying `Stack` directly, so the `stack_id` binding on the `ApiClient` is enforced consistently across all API controllers.

### Proof of Concept
1. Using the `here_come_the_walrus` fixture token (scoped to stack `shipit`, permission `read:stack` only) [5](#0-4) , authenticate against `Api::CCMenuController#show` (`GET /api/stacks/:stack_id/cc.xml?token=<token>`) and pass a different stack's `stack_id` (e.g. any other stack in the instance).
2. `authenticate_api_client` succeeds because the token is valid [10](#0-9) .
3. `require_permission :read, :stack` succeeds because the token has `read:stack` in its permission list, regardless of which stack is requested [8](#0-7) .
4. `#show` calls `stack.deploys_and_rollbacks`, where `stack` resolves via `Stack.from_param!(params[:stack_id])`, returning the attacker-chosen stack instead of the token-bound one [11](#0-10) , leaking that stack's build/deploy status in the XML response.
