### Title
Cross-organization webhook forgery triggers stack sync for repositories not owned by the authenticating organization - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/webhook secret to check based on `repository_owner`, a value read directly out of the untrusted, attacker-supplied JSON payload before any signature has been validated. Once the HMAC check passes, the entire raw payload — including a `repository.full_name` field that is never cross-checked against `repository_owner` — is handed to the event handlers, which resolve the target `Stack` purely from `repository.full_name`. This breaks the intended binding "the organization whose secret authenticated the request == the repository being acted upon."

### Finding Description
`WebhooksController#verify_signature` computes `repository_owner` from the payload itself and uses it to fetch the corresponding `GitHubApp` (and thus webhook secret) for verification: [1](#0-0) [2](#0-1) 

The signature only proves that whoever crafted the payload knows the webhook secret of the organization named in `repository.owner.login` (or `organization.login`). It does **not** prove anything about the `repository.full_name` field, which is a separate, independently-controlled JSON key in the same payload.

After signature verification succeeds, `create` passes the raw, fully attacker-controlled `params` to every registered handler for the event: [3](#0-2) 

`Handler#repository_name` (used by every handler, e.g. `PushHandler`, `CheckSuiteHandler`) reads `payload.dig('repository', 'full_name')` — a different field than the one used for signature/org selection — and resolves the `Stack`(s) to act on solely from it: [4](#0-3) 

`PushHandler#process` then triggers `stack.sync_github` for every stack matching that repository/branch: [5](#0-4) 

Nothing in this chain verifies that `repository.full_name` belongs to the same organization/owner as `repository.owner.login`/`organization.login` used to select and validate the webhook secret. An attacker who legitimately controls (or has been given) a webhook secret for **their own** organization/App installation (e.g. `attacker-org`) can send a webhook whose `X-Hub-Signature` is valid for `attacker-org`'s secret, while setting `repository.full_name` to `victim-org/victim-repo` — a repository/stack that belongs to a completely different, unrelated GitHub organization configured in the same Shipit instance. Shipit will accept the signature (it matches `attacker-org`), then process the payload against the victim's stack because the handler never re-checks organization ownership of `repository.full_name`.

### Impact Explanation
This crosses the "an organization that authenticated versus the repository that is written" boundary called out in scope. Practically, it lets an attacker who holds a webhook secret for one configured GitHub organization on a multi-org Shipit deployment forge `push`/`check_suite` events that cause Shipit to run `sync_github` (and downstream continuous-deployment/merge-queue logic) against stacks belonging to a different organization's repository, i.e., cross-repository/cross-organization writes and triggering of deploy-adjacent jobs (`GithubSyncJob`, check-run refresh) for a repository the attacker does not control. This matches the "cross-repository writes" / "unauthorized deploy" impact class.

### Likelihood Explanation
Requires the attacker to already control a valid webhook secret for at least one org configured in the Shipit instance's `github` config (i.e., not a fully anonymous attacker, but also not requiring compromise of the victim organization's secret, an `ApiClient` token, or a Shipit session/account). On any multi-tenant Shipit deployment configuring multiple GitHub organizations (as documented in `docs/setup.md`), this is directly reachable over the public `/webhooks` endpoint with a single crafted HTTP request.

### Recommendation
In `Handler#repository_name` / `WebhooksController`, cross-validate that the `repository.owner.login` (the value used to select and verify the webhook secret) matches the owner segment of `repository.full_name` before dispatching to handlers, rejecting (422) any payload where they diverge.

### Proof of Concept
1. Configure two GitHub orgs in Shipit's `github` secrets, `attacker-org` (secret known to attacker) and `victim-org` (has a stack tracking `victim-org/victim-repo`).
2. POST to `/webhooks` with header `X-Github-Event: push`, body:
```json
{
  "ref": "refs/heads/main",
  "after": "<attacker-chosen sha>",
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  }
}
```
3. Sign the body with `attacker-org`'s known webhook secret and set `X-Hub-Signature` accordingly.
4. `WebhooksController#verify_signature` looks up `Shipit.github(organization: "attacker-org")` and verifies successfully.
5. `PushHandler#process` resolves `stacks` via `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `stack.sync_github(expected_head_sha: "<attacker-chosen sha>")` on the victim's stack, even though the signature never proved anything about `victim-org`.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```
