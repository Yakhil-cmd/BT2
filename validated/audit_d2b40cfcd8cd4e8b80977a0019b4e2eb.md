### Title
Permanent market freeze via `i128` overflow in `scaled_to_original` before the borrow-index cap engages - ([File: common/src/rates/scaling.rs])

### Summary
Analog to CVE-2022-21297 (optimizer crash → complete availability loss): a market's accrual path contains an arithmetic crash that, once reached, permanently bricks every entrypoint for that market. `accrue_step` calls `scaled_to_original(env, borrowed, borrow_index)`, which multiplies the RAY-scaled total debt by the borrow index in `i128`. The product overflows `i128` before `borrow_index` ever reaches `MAX_BORROW_INDEX_RAY` (1e36 raw), so `update_borrow_index`'s clamp in `common/src/rates/index.rs:13` never gets a chance to bound growth. Every pool verb (`supply`, `withdraw`, `repay`, `borrow`, `seize`, flash paths) calls `synced_market` → `interest::global_sync` first (`contracts/pool/src/ops/mod.rs:30-33`), so the panic is unavoidable: no withdrawal, no repayment, no liquidation, no `clean_bad_debt` — permanent freezing of all supplier and collateral funds in that `(hub, token)` book.

### Finding Description
`global_sync` (`contracts/pool/src/interest.rs:20`) iterates `accrue_chunk`, which calls `accrue_step` (`common/src/rates/simulate.rs:51`). Step one is `scaled_to_original(env, borrowed, borrow_index)` (`simulate.rs:60`), implemented as `scaled.mul(env, index)` (`scaling.rs:14-16`) → `mul_div` panicking with `GenericError::MathOverflow` on `i128` overflow (`common/src/math/fp_core.rs:300-303`). Debt is stored scaled by `borrow_index`, so the unscaled value `borrowed * index` grows quadratically with time at high utilization; at a whale-scale book (e.g., ~1e9 × 10^18 native units on an 18-decimal market) it crosses `i128::MAX` (~1.7e38) at an index of roughly ~170 — far below the 1e36 cap. Once crossed, the panic reverts on every subsequent call for that market, forever.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate for the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and bad debt cannot be cleaned. All underlying tokens held by the pool for that `(hub, token)` book are locked permanently.

### Likelihood Explanation
Reachable by unprivileged addresses using only `supply`/`borrow`/`update_indexes`: the attacker (or organic usage) must build a very large book — the reference scenario needs ~1e27 raw units of an 18-decimal asset at ~98% utilization sustained for years on a steep rate curve. Not cheap and not fast, but no privileged role, upgrade, or leaked key is required; the market enters the dead zone through ordinary protocol operation and cannot be rescued (no admin unpause exists for accrual math). Medium severity.

### Recommendation
Check the multiplication in `accrue_step`/`scaled_to_original` before it overflows — e.g., clamp `borrow_index` to `MAX_BORROW_INDEX_RAY` *before* unscaling, use a saturating `mul` for the utilization computation, or cap `scaled` totals so `scaled * index` provably stays in `i128` given `MAX_BORROW_INDEX_RAY`. Listing-time cap validation (`require_cap_within_asset_domain`) should bound `cap × MAX_BORROW_INDEX_RAY < i128::MAX` so the index cap always engages before the value ceiling.

### Proof of Concept
Encoded in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`): supply `BILLION * 10^18` of an 18-decimal asset, borrow 98% of it, advance time year-by-year calling `update_indexes`. Within 40 simulated years `try_update_indexes_for(["BIG18"])` reverts with `MATH_OVERFLOW` at `borrow_index ≈ 170x` while `borrow_index < MAX_BORROW_INDEX_RAY`; afterwards `withdraw` and `repay` of even 1 unit also revert with `MATH_OVERFLOW` because every verb accrues first.
