Based on the code I found, there is a legitimate memory-leak analog in the banking-stage external scheduler's `check_worker`, reachable from ordinary transactions that use Address Lookup Tables (ALTs).

### Title
Memory leak of the shared scheduler allocator on `check_batch` allocation-failure path leads to transaction-triggered leader halt - (File: `core/src/banking_stage/transaction_scheduler/check_worker.rs`)

### Summary
`ExternalCheckWorker::check_batch` allocates a `CheckResponseRegion` from the shared `rts_alloc::Allocator` before calling `check_resolve_pubkeys`, which itself allocates one buffer per ALT-using transaction in the batch. If any of these later allocations fails and returns `None`, the `?` operator immediately returns `Err(...)` from `check_batch`, discarding the already-allocated `CheckResponseRegion` (and any earlier per-transaction pubkey buffers) without ever freeing them or handing ownership to anyone who could free them. This mirrors the highbank EDAC bug class: an allocation succeeds, a later step in the same function fails, and the function's error path forgets to release what was already allocated.

### Finding Description
`check_batch` allocates the response region first: [1](#0-0) 

That allocation ownership is only released by transferring the region to the outgoing `CheckWorkerToPackMessage`, sent at the end of the function: [2](#0-1) 

But if the `LOAD_ADDRESS_LOOKUP_TABLES` flag is set, `check_batch` calls `check_resolve_pubkeys` with `?` before that send: [3](#0-2) 

Inside `check_resolve_pubkeys`, for every transaction whose account keys exceed its static account keys (i.e. it uses an address lookup table — fully attacker-controlled), a new allocation is requested and immediately propagated via `?` on failure: [4](#0-3) [5](#0-4) 

If this `allocate` call returns `None` (allocator has no free space) for any transaction in the batch, `check_resolve_pubkeys` returns `Err(AllocationFailure)`, which propagates out of `check_batch` via the `?` at line 331. This early return means:
1. The `CheckResponseRegion` allocated at lines 285–289 is never sent to anyone and never freed — permanently lost.
2. Any `pubkeys_allocation` buffers successfully allocated for earlier transactions in the same loop (lines 404–408) are also never referenced again outside the lost response buffer — also permanently lost.

Both allocations come from the same fixed-size, per-session shared `rts_alloc::Allocator` (`allocator_size` set at session setup) that is also used by `tpu_to_pack`, `consume_worker`, and other scheduler-pipeline stages: [6](#0-5) 

The comment elsewhere in the same worker family explicitly acknowledges this leak pattern is used intentionally on unrecoverable paths ("Should de-allocate the memory, but this is a non-recoverable error and so it's not needed"): [7](#0-6) 

showing the codebase treats `AllocationFailure`/send-failure branches as "doesn't matter, leak it" — but unlike a true fatal shutdown, `check_batch`'s caller (`process_message` → `iterate` → `run`) treats `ExternalCheckWorkerError` as fatal to the *check worker thread* only, and the worker thread exits (`run` returns `Err`), while the rest of the leader (consume workers, packet ingestion, PoH) keeps running and continues submitting more batches. Each subsequent allocation-exhaustion event of this kind permanently shrinks the shared allocator's free pool.

### Impact Explanation
Because address lookup tables are a standard, permissionless transaction feature, any transaction sender can force execution of the `check_resolve_pubkeys` allocation path by including a transaction with loaded (ALT-resolved) account keys. Under sustained load or allocator fragmentation, allocation calls can transiently fail well before the pool is truly full. Each such failure permanently leaks the response-region allocation (and any partial pubkey allocations), progressively shrinking the shared scheduler allocator used by the entire banking-stage pipeline (`tpu_to_pack`, `consume_worker`, `check_worker`). Once the shared allocator's pool is exhausted, all of these pipeline stages start failing their own allocations, which — per the same code pattern — largely translates into either dropped/leaked batches or hard worker-thread termination. This can render a leader unable to process or produce transactions/blocks (a leader-side denial of service), i.e. a transaction-triggered halt of block production reachable purely from unprivileged, permissionless transaction submission.

### Likelihood Explanation
This requires no privileged access — a normal client can submit transactions that resolve accounts through address lookup tables (a common, documented feature), triggering the vulnerable allocation path on every such transaction that reaches a check worker. The leak only manifests when the shared allocator momentarily fails to satisfy an allocation request (transient fragmentation/exhaustion under load), so this is a load-dependent, cumulative issue rather than a single-shot trivial trigger — moderate likelihood that increases with sustained ALT-heavy transaction volume directed at a leader.

### Recommendation
On the error path in `check_batch`/`check_resolve_pubkeys`, ensure the previously allocated `CheckResponseRegion` and any already-completed per-transaction pubkey allocations are explicitly freed via `self.allocator.free(...)` before propagating the `AllocationFailure` error, mirroring the kernel fix pattern of calling the cleanup routine (`edac_mc_free`) on all error-return paths after a resource has been acquired.

### Proof of Concept
1. Start a validator leader session with a bounded `allocator_size` for the external scheduler (as configured via `ClientLogon`).
2. Continuously submit a high volume of valid, permissionless transactions that use address lookup tables (so `account_keys.len() > num_static_account_keys` is true for many transactions per batch), causing `check_resolve_pubkeys` to repeatedly call `self.allocator.allocate(...)` per batch — see: [8](#0-7) 
3. Under sustained throughput, some allocation calls will transiently return `None` (pool momentarily full/fragmented), causing `check_batch` to return early via `?` without freeing the `CheckResponseRegion` already allocated at lines 285–289, and without freeing any already-allocated pubkey buffers from the same request.
4. Repeat over time; observe the shared allocator's free capacity monotonically shrink until subsequent allocations across all banking-stage pipeline stages begin failing, degrading or halting the leader's transaction processing.
