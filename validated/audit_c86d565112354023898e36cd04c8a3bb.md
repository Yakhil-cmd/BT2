### Title
`$VAR` interpolation in shell steps falls back to Shipit's own process `ENV`, letting an attacker-controlled fork `shipit.yml` read host secrets - ([File: lib/shipit/environment_variables.rb])

### Summary
`EnvironmentVariables#interpolate`, used by `Command#interpolated_arguments` to build the argv passed to `PTY.spawn`, resolves any `$VAR` token that is absent from the task's whitelisted env by falling back to `ENV[VAR]` — Shipit's own process environment. [1](#0-0)  For a `ReviewStack` under `provisioning_behavior = allow_with_label`, the deploy steps (`deploy.override`) and other config are read from the `shipit.yml` on the PR's own fork branch (`stack.branch = params.pull_request.head.ref`), which is fully attacker-controlled. [2](#0-1)  This lets an unprivileged fork author reference an arbitrary variable name (e.g. `$GITHUB_TOKEN`, `$SECRET_KEY_BASE`) in a deploy step; since it's not in the task's declared/whitelisted env, `Shellwords.escape(@env.fetch(variable) { ENV[variable] })` pulls the value straight from Shipit's process environment into the executed command line / output stream.

### Finding Description
The broken binding: the codebase assumes `$VAR` references inside `deploy.override`/task `steps` can only resolve to values from the trusted, whitelisted `env` hash built by `filter_deploy_envs`/`EnvironmentVariables#permit` (`deploy_variables`, `Stack#env`, etc.), i.e. `interpolate(argument) == value_from(whitelisted_env)`. In reality, `interpolate` is `@env.fetch(variable) { ENV[variable] }` — when `variable` is not a key in `@env`, it silently returns `ENV[variable]`, so the equality actually is `interpolate(argument) == value_from(Shipit_process_ENV)` whenever the attacker picks a variable name outside the whitelist. [1](#0-0) 

Path: `deploy.override`/`deploy.pre`/`deploy.post` steps (and other config sections) come from `DeploySpec::FileSystem#load_config`, which reads `shipit.yml`/`.shipit/shipit.yml` from the checked-out working directory of `@stack.branch`. [3](#0-2)  For a `ReviewStack`, that branch is `params.pull_request.head.ref` — the PR author's own fork branch, set at stack creation time with no owner/maintainer review required, only a label the PR author (or anyone who can add the label) controls under `allow_with_label`. [4](#0-3)  Those steps are executed via `Command#start`, which calls `interpolated_arguments` → `interpolate_environment_variables` → `EnvironmentVariables.with(env).interpolate` before `PTY.spawn`. [5](#0-4) 

Exploit: a fork PR's `shipit.yml` sets `deploy: {override: ["echo $GITHUB_TOKEN"]}` (or any secret env var name Shipit's Rails process happens to hold, e.g. credentials passed via `ENV` to the host app). Because `GITHUB_TOKEN` is never in `@stack.env`/`deploy_variables`, `EnvironmentVariables#interpolate` falls to `ENV['GITHUB_TOKEN']`, `Shellwords.escape`s it, and it becomes part of the literal argv executed by `PTY.spawn` and is echoed into the task's log output, which is readable via the stack/task UI.

Existing guards and why they don't stop this:
- `EnvironmentVariables#permit` (the whitelist used to build `@env`) only restricts what values a *human submitting a deploy form* may inject into `env` via `deploy_params`; it does not restrict what variable *names* a step can reference via `$VAR` interpolation. [6](#0-5) [7](#0-6) 
- There is no whitelist/blocklist check inside `interpolate` itself — the fallback to `ENV[variable]` is unconditional. [8](#0-7) 
- This fallback-to-ENV behavior is explicitly exercised and expected by an existing unit test (`"#interpolate_environment_variables fallback to ENV"`), confirming it is intentional, generic behavior of `Command`, used across all stacks (trusted or not) — not something specific to review stacks that was newly introduced, but its risk is elevated specifically when the `shipit.yml` source is an untrusted fork branch. [9](#0-8) 

### Impact Explanation
Any secret Shipit's own Rails process holds in `ENV` (deploy credentials, API keys, potentially tokens depending on host app configuration) can be exfiltrated into task output/log or into the executed command line for a repository configured with review stacks + `allow_with_label`, by any user who can open a PR against that repository and get (or self-apply, if the label isn't restricted) the provisioning label. This is repeatable per PR/task run and is scoped to whatever secrets exist in the *Shipit process's own* `ENV` at deploy time — it does not by itself grant read access to unrelated repositories' stacks. Severity depends on what the host operator has placed into Shipit's process environment; if that includes `GITHUB_TOKEN`/app credentials it matches "Critical - exfiltration of deploy-time secrets."

### Likelihood Explanation
Preconditions: the target repository must have Review Stacks enabled with `provisioning_behavior` of `allow_with_label` (or `allow_all`), and the attacker must be able to open a PR from a fork and (for `allow_with_label`) have the provisioning label applied. The attacker needs no Shipit session, API token, or GitHub org membership — only the ability to open a PR and control its branch's `shipit.yml`. Cost is trivial (one PR); the finding is fully repeatable and deterministic once the review stack deploys.

### Recommendation
In `EnvironmentVariables#interpolate`, remove or gate the fallback to `ENV[variable]`; interpolation should only resolve names present in the explicitly permitted/whitelisted env hash, substituting an empty string (or raising) for any unknown variable instead of reading the host process environment. If some ENV fallback is required for legitimate use cases (e.g. `Stack#links` interpolation), restrict it to an explicit, operator-curated allowlist of variable names rather than the entire process environment, and ensure review-stack shipit.yml content can never reach that fallback path.

### Proof of Concept
```ruby
# test/unit/environment_variables_test.rb (minitest[allow_with_label])
test "interpolate falls back to Shipit's own ENV for unset variable names" do
  previous = ENV['SHIPIT_SECRET_TEST']
  ENV['SHIPIT_SECRET_TEST'] = 'super-secret-token'

  # Attacker-controlled step referencing a variable name absent from the task env
  argument = 'echo $SHIPIT_SECRET_TEST'
  result = EnvironmentVariables.with({}).interpolate(argument)

  # BROKEN BINDING: attacker-controlled shipit.yml step content should never
  # be able to read Shipit's own process ENV.
  assert_equal 'echo super-secret-token', result
ensure
  ENV['SHIPIT_SECRET_TEST'] = previous
end

test "Command#start builds argv containing Shipit's ENV value for a deploy.override step from an untrusted shipit.yml" do
  previous = ENV['SHIPIT_SECRET_TEST']
  ENV['SHIPIT_SECRET_TEST'] = 'super-secret-token'

  command = Shipit::Command.new('echo $SHIPIT_SECRET_TEST', env: {}, chdir: '.')
  out = command.run

  assert_includes out, 'super-secret-token'
ensure
  ENV['SHIPIT_SECRET_TEST'] = previous
end
```
This demonstrates that a `deploy.override` step sourced from an attacker-controlled fork `shipit.yml` (under `allow_with_label`), referencing any variable name not present in the whitelisted task env, resolves to and leaks the value from Shipit's own process `ENV`.

        variable.sub!('$', '')
        Shellwords.escape(@env.fetch(variable) { ENV[variable] })
      end

      return argument.map { |a| interpolate_environment_variables(a) } if argument.is_a?(Array)

    end

    def success?

    def exit_message

    def run

    end

    def run!

      end
      output.join
    end

    def interpolated_arguments

    def start(&block)
