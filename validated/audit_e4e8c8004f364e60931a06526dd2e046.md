### Title
Cross-repository commit-status forgery via `StatusHandler` missing repository binding to the verified webhook organization - ([File: app/models/shipit/webhooks/handlers/status_handler.rb])

### Summary
`WebhooksController#verify_signature` authenticates an incoming GitHub webhook by looking up the per-organization `webhook_secret` using `params.dig('repository', 'owner', 'login')` (or the `organization.login` fallback) and verifying the HMAC signature against that organization's secret. [1](#0-0)  Once the signature check passes, the JSON body is handed unchanged to the matching `Handler`. `StatusHandler` uses only the attacker-supplied `sha` field, with no repository or organization scoping at all, to locate `Commit` records and mutate their status. [2](#0-1)  This breaks the binding "organization that authenticated == repository/commit being written."

### Finding Description
Shipit supports multiple GitHub App configurations, one per organization, each with its own `webhook_secret`. [3](#0-2)  `verify_signature` resolves which secret to use purely from attacker-controlled JSON fields in the same request body (`repository.owner.login`/`organization.login`), then verifies the signature using that organization's secret: [4](#0-3) 

An attacker who legitimately controls a GitHub organization/repository that is itself configured in Shipit (i.e., has a valid, correctly-signed webhook relationship for their *own* org) can send a `status` event whose `repository.owner.login` matches their own org (so the signature check succeeds using their own real `webhook_secret`), but whose `sha` field is set to the SHA-1 of a commit that actually belongs to a completely different, victim-owned stack/repository tracked by the same Shipit instance.

`StatusHandler#process` never validates that the commit being updated belongs to the repository/organization that was authenticated — it queries `Commit.where(sha: params.sha)` globally across the entire database and applies the forged status to every matching commit, regardless of which stack/repo it belongs to: [2](#0-1) [5](#0-4) 

(Note: the base `Handler#stacks`/`repository_name` helper, which does scope by `payload.dig('repository','full_name')`, is defined but is not used by `StatusHandler` — it only uses the global `sha`.)

Applying a forged status update triggers real downstream effects: `Commit#create_status_from_github!` → `add_status` fires `commit_status`/`deployable_status` hooks and, critically, calls `stack.schedule_merges` when the new status is `pending` or `success`: [6](#0-5) 

That status directly feeds `Commit#deployable?`, which is used by the merge queue and deploy pipeline gating: [7](#0-6) 

### Impact Explanation
This qualifies as High severity: an unprivileged attacker who only controls their own GitHub organization (already onboarded to Shipit) can forge a "success" CI status for an arbitrary commit belonging to a victim's stack that they have no authorization over, causing that commit to be considered deployable/mergeable and triggering `ProcessMergeRequestsJob`/merge-queue processing. This is an authorization boundary crossing — the attacker's authenticated identity (their own org's webhook secret) is used to affect a completely different repository's deploy/merge-eligibility state, effectively enabling an unauthorized deploy/merge decision to be influenced from outside that repository's trust boundary.

### Likelihood Explanation
Requires the attacker to control (or compromise) a GitHub organization that is already configured as a Shipit `github` app entry with per-org webhook secrets (the "Using Multiple GitHub Applications" mode documented in `docs/setup.md`). [8](#0-7)  In that (supported, documented) configuration, exploitation only requires the attacker to know the victim commit's SHA (public GitHub data) and send a POST to `/webhooks` with a `status` event — no additional secrets, tokens, or session are required beyond what the attacker's own legitimately configured organization already provides. This is a realistic multi-tenant deployment scenario for Shipit.

### Recommendation
`StatusHandler` (and any other handler that doesn't already scope by `stacks`) must verify that the commit(s) being updated actually belong to a stack whose `Repository#full_name`/`owner` matches the webhook's authenticated organization, e.g. by intersecting `Commit.where(sha: params.sha)` with `stacks` (via `Handler#stacks`, which is derived from `payload.dig('repository', 'full_name')`), and additionally cross-check that the authenticated organization used in `verify_signature` matches `repository.owner.login`/`full_name` actually used for handler dispatch, rather than trusting two independently attacker-supplied JSON fields (`repository.owner.login` for auth, `repository.full_name`/`sha` for effect) to stay consistent.

### Proof of Concept
1. Shipit is configured in multi-organization mode with organizations `attacker-org` (attacker controlled, valid `webhook_secret`) and `victim-org` (has a tracked stack with commit `deadbeef...`).
2. Attacker crafts a `status` webhook payload:
```json
{
  "sha": "<victim commit sha>",
  "state": "success",
  "context": "ci/attacker-forged",
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature` using `attacker-org`'s real webhook secret (which they legitimately know, since it's their own configured GitHub App) — see `verify_webhook_signature`: [9](#0-8) 
4. POST to `/webhooks` with `X-Github-Event: status`. `WebhooksController#verify_signature` succeeds because it only checks the signature against `attacker-org`'s secret, using `repository.owner.login` from the same forged payload. [1](#0-0) 
5. `StatusHandler#process` finds the victim's `Commit` by global `sha` lookup and applies the forged `success` status, triggering `stack.schedule_merges` for the victim's stack. [2](#0-1) [10](#0-9)

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently.     def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
