### Title
AccountKeyFail Slot Bypass via Type-Mismatch in `CheckReplacable` Allows RoleFeePayer Privilege Escalation — (`blockchain/types/accountkey/account_key.go`)

---

### Summary

`CheckReplacable` only calls `oldKey.CheckUpdatable()` when `oldKey.Type() == newKey.Type()`. When types differ, it calls `newKey.CheckInstallable()` instead. Because `AccountKeyFail.CheckInstallable()` is never invoked in this branch, the invariant "AccountKeyFail cannot be updated with any key" is silently bypassed when the replacement key is a different type (e.g., `AccountKeyPublic`).

---

### Finding Description

The guard in `CheckReplacable`: [1](#0-0) 

```go
func CheckReplacable(oldKey AccountKey, newKey AccountKey, currentBlockNumber uint64) error {
    if oldKey.Type() == newKey.Type() {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    return newKey.CheckInstallable(currentBlockNumber)   // ← AccountKeyFail guard never reached
}
```

`AccountKeyFail.CheckUpdatable` unconditionally returns `ErrAccountKeyFailNotUpdatable`: [2](#0-1) 

But this is only called when `oldKey.Type() == newKey.Type()` (i.e., Fail→Fail). When the attacker supplies `AccountKeyPublic` as the new slot, the type check fails and `AccountKeyPublic.CheckInstallable()` is called instead — which returns `nil` for any valid public key.

`AccountKeyRoleBased.CheckUpdatable` calls `CheckReplacable` for each non-Nil slot: [3](#0-2) 

And `AccountKeyRoleBased.Update` only gates on `CheckUpdatable`'s return value before overwriting slots: [4](#0-3) 

**Attack path:**
1. Target account state: `RoleBasedKey = [RoleTransaction=KeyA, RoleAccountUpdate=KeyB, RoleFeePayer=AccountKeyFail]`
2. Attacker (holding `KeyB`) submits `TxTypeAccountUpdate` with new `RoleBasedKey = [AccountKeyNil, AccountKeyNil, AccountKeyPublic(attacker)]`
3. `CheckUpdatable` iterates slots:
   - Slots 0,1: `AccountKeyNil` → skipped per the `case (*newKey)[i].Type() == AccountKeyTypeNil:` branch
   - Slot 2 (RoleFeePayer): `CheckReplacable(AccountKeyFail, AccountKeyPublic, ...)` → types differ → `AccountKeyPublic.CheckInstallable()` → `nil`
4. `CheckUpdatable` returns `nil`; `Update` overwrites `(*a)[2]` with `AccountKeyPublic(attacker)`
5. Account now has `RoleFeePayer=AccountKeyPublic(attacker)` — the permanent-disable invariant is broken

---

### Impact Explanation

An account that intentionally set `RoleFeePayer=AccountKeyFail` to permanently disable fee-payer capability (e.g., a bridge operator account) can have that slot overwritten by any party controlling the `RoleAccountUpdate` key. The attacker gains fee-payer signing authority, enabling them to authorize fee-delegated transactions charged to the victim account.

---

### Likelihood Explanation

Requires control of the target account's `RoleAccountUpdate` key — a non-trivial precondition. However, in multi-party setups (e.g., bridge operators with separate update and fee-payer roles, or governance-controlled update keys), this is a realistic scenario. The transaction is submitted via the standard public RPC path (`TxTypeAccountUpdate`), requiring no special node access.

---

### Recommendation

`CheckReplacable` must enforce the `AccountKeyFail` invariant regardless of the new key's type. The fix is to check whether `oldKey` is `AccountKeyFail` before falling through to `CheckInstallable`:

```go
func CheckReplacable(oldKey AccountKey, newKey AccountKey, currentBlockNumber uint64) error {
    // AccountKeyFail can never be replaced by any key type.
    if oldKey.Type() == AccountKeyTypeFail {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    if oldKey.Type() == newKey.Type() {
        return oldKey.CheckUpdatable(newKey, currentBlockNumber)
    }
    return newKey.CheckInstallable(currentBlockNumber)
}
```
