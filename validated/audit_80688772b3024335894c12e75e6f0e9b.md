### Title
Interest accrual panics on `i128` value overflow before `MAX_BORROW_INDEX_RAY` cap, permanently freezing the market - (File: common/src/rates/simulate.rs)

### Summary
The BIND CVE is an assertion-failure crash reachable by a crafted query — a fail-open-freeze. The XOXNO Lending analog: `accrue_step` computes `scaled_to_original(borrowed, borrow_index)` = `borrowed * borrow_index / RAY` via `mul_div_half_up`, which panics with `GenericError::MathOverflow` when the product's RAY-scaled debt value exceeds `i128::MAX`. This overflow occurs *before* the `MAX_BORROW_INDEX_RAY` index cap engages, so the cap cannot save it. Every controller verb (`withdraw`, `repay`, `borrow`, `liquidate`, `update_indexes`) accrues the market first, so once the cliff is crossed the market is frozen permanently — no repay, no withdraw, no liquidation. ### Finding Description
`accrue_step` (`common/src/rates/simulate.rs:60-61`) unscales `borrowed` and `supplied` through `scaled_to_original`, which is `scaled.mul(env, index)` and ultimately `mul_div_half_up`. That helper widens the product but panics when the *result* exceeds `i128::MAX` (`common/src/math/fp_core.rs:138-143`). `update_borrow_index` clamps the *index* at `MAX_BORROW_INDEX_RAY` but never checks the *value* `borrowed * index`; a large `borrowed` scaled book crosses the value ceiling while the index is still below its cap. Because the overflow happens inside the accrual step that all entry points run first, the panic is unrecoverable and bricks the market. The checked test at `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-356` demonstrates exactly this: at 98% utilization on the XLM curve the index grows past ~170× within 40 simulated years, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all return `MATH_OVERFLOW`, and the borrow index remains below `MAX_BORROW_INDEX_RAY` ("the index cap did not engage before the value overflow"). ### Impact Explanation
Permanent freezing of user funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and no accrual can ever complete again since accrual is the first step of every verb. The state is unrecoverable absent an upgrade — an exact analog of BIND's assertion-failure termination, but persistent rather than restartable.

### Likelihood Explanation
Reachable by a single unprivileged address via `supply`/`borrow`/`update_indexes` with ordinary arguments — no privilege, upgrade, or leaked key required. However it demands whale-scale liquidity (the test uses a billion-unit, 18-decimal asset at ~98% utilization on the steep XLM curve segment) and sustained high utilization over a long accrual horizon. Partially mitigated by real-world liquidity and cap constraints, but the caps govern amounts, not the `borrowed * index` product, so a large enough book defeats them. Severity: Medium-High (permanent freeze, high economic preconditions).

### Recommendation
Inside `accrue_step`, compute `borrowed_original`/`supplied_original` with a saturating or checked path, or cap `borrowed`/`supplied` scaled totals so `scaled * index` cannot exceed `i128::MAX` (e.g., enforce `borrowed <= i128::MAX / MAX_BORROW_INDEX_RAY * RAY` at supply/borrow time, mirroring `require_cap_within_asset_domain` for caps). Alternatively, in `update_borrow_index`, clamp the index to `min(MAX_BORROW_INDEX_RAY, i128::MAX * RAY / borrowed)` so the cap engages before the value overflow.

### Proof of Concept
Existing harness test: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (lines 321-360):
1. Whale supplies `BILLION * 10^18` of an 18-decimal asset; attacker-supplied liquidity.
2. Attacker borrows to ~98% utilization, forcing the steep segment of the rate curve.
3. Advance ledger time; each `update_indexes` accrues. Within the bound the borrow index exceeds ~170× while still `< MAX_BORROW_INDEX_RAY`.
4. `scaled_to_original(borrowed, borrow_index)` overflows `i128` → `MathOverflow` panic.
5. `withdraw`, `repay`, and `update_indexes` all revert permanently — funds frozen, market bricked.

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
