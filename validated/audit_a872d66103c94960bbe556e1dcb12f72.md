### Title
Cross-tenant status write via unscoped `Commit.where(sha:)` in `StatusHandler#process` - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` resolves target commits with a bare `Commit.where(sha: params.sha)`, never restricting the query to the repository that authenticated the webhook. Every other webhook path in this engine derives its target set through `Handler#stacks`, which scopes by `Repository.from_github_repo_name(repository_name)`; `StatusHandler` bypasses that helper entirely. Any commit row sharing the same 40-character SHA across unrelated stacks/repositories will receive the attacker's status, and if the affected stack has `continuous_deployment` enabled and requires the `release/gate` context, a `success` status can flip that commit to deployable and trigger `ContinuousDeliveryJob`.

### Finding Description
The broken binding: the engine's security model assumes `commit.stack.repository.full_name == payload['repository']['full_name']` for any write performed by a webhook handler — i.e., a status can only ever attach to a commit belonging to the repository that signed the webhook. `StatusHandler` violates this: [1](#0-0) 

vs. the scoping helper every other handler is expected to use: [2](#0-1) 

`Commit#sha` is not unique per repository in the schema; it is a global lookup key here (`Commit.where(sha: params.sha)`), so if two different stacks (potentially owned by different GitHub orgs/repos) ever have a `Commit` row with the identical SHA — a realistic scenario with forks, mirrors, cherry-picks, or shared upstream history — the handler iterates over *all* of them and calls `commit.create_status_from_github!(params)` on each, regardless of which repository the request was signed for.

`create_status_from_github!` writes directly to `statuses` and re-evaluates deployability: [3](#0-2) [4](#0-3) 

Crucially, a state transition triggers `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` for the *victim* stack if that stack has `continuous_deployment?` enabled and the commit is now `deployable?`: [5](#0-4) [6](#0-5) 

Why `verify_signature` doesn't stop this: signature verification in `WebhooksController` only proves the payload was signed by the GitHub App/webhook secret belonging to `repository_owner` (`params.dig('repository','owner','login')`), i.e., it authenticates *which org sent the payload*, not which commit rows the payload is allowed to mutate: [7](#0-6) 

An attacker who owns/administers any repository wired into this Shipit instance (their own fork, or any repo with a configured GitHub App/webhook secret) can legitimately emit a signed `status` event for their own repo, but choose an arbitrary `sha` value and `context: release/gate`, `state: success`. If that SHA happens to also exist as a `Commit` row in a victim stack (shared/forked history, mirrored repos, or simply a coincidental identical SHA in a monorepo/mirror setup indexed by multiple `Stack`s), `StatusHandler` will write the status onto the victim's commit and can flip its deployability, causing the victim's `continuous_deployment`-enabled stack to autoship via `ContinuousDeliveryJob`, or conversely block deploys by making a status `blocking?`.

None of the listed guards (`ExplicitParameters` schema, `drop_unhandled_event`, `force_github_authentication`, `User#authorized?`, model validations) constrain the handler to the authenticated repository — that responsibility is delegated entirely to each handler's use (or non-use) of `Handler#stacks`, and `StatusHandler` never calls it.

### Impact Explanation
A successfully signed webhook from *any* one onboarded repository can mutate CI/gate state for commits belonging to a *different* stack/repository, satisfying the Critical category "a payload for one repository mutating another's stack, commit, task or team." When the victim stack has `continuous_deployment` enabled, this becomes an unauthorized deploy trigger (`ContinuousDeliveryJob`) or an unauthorized block of legitimate deploys — both explicitly listed Critical impacts. The blast radius spans every stack in the Shipit instance whose commits collide on SHA with a repository the attacker controls.

### Likelihood Explanation
Preconditions: the attacker must control (or be a collaborator/maintainer on) at least one repository already onboarded to the target Shipit instance so they can send an authentically-signed `status` webhook; and a SHA collision must exist between a commit in that repository and a commit in the victim's `Stack` (plausible with forks/mirrors/monorepo setups, or any workflow that imports the same commit into multiple `Stack` records). The victim stack must have `continuous_deployment` enabled and use `release/gate` as a required/blocking status context for the attack's most severe framing (ship/block), though any status write onto a foreign commit is already an integrity violation independent of that. Attacker cost is low: one HTTP status API call from an owned repo.

### Recommendation
Scope `StatusHandler#process` to the repository that authenticated the webhook, using the existing `stacks`/repository-derived commit scope (e.g., restrict `Commit.where(sha: params.sha)` to `Commit.joins(:stack).merge(stacks)` or filter by `stack_id: stacks.pluck(:id)`), mirroring the pattern used by `PushHandler`, `CheckSuiteHandler`, and the `pull_request/*` handlers via `Handler#stacks`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, new or extended):

1. Create two `Repository`/`Stack` pairs, `repo_a` (attacker's, e.g. `attacker/repo`) and `repo_b` (victim, e.g. `victim/repo`), with `repo_b`'s stack having `continuous_deployment: true` and `required_statuses: ['release/gate']`.
2. Create a `Commit` with an identical `sha` (`"a" * 40`) under both `repo_a`'s stack and `repo_b`'s stack.
3. Assert precondition equality that should hold: `commit_b.deployable? == false` (no `release/gate` success yet) and `commit_b.stack.id != commit_a.stack.id`.
4. Invoke `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` with `payload['repository']['full_name'] == 'attacker/repo'`, `sha: "a"*40`, `context: 'release/gate'`, `state: 'success'` — i.e., only `repo_a`'s webhook is "authenticated."
5. Assert the broken binding: `commit_b.reload.deployable? == true` and/or `ContinuousDeliveryJob` enqueued for `repo_b`'s stack, even though the payload's `repository.full_name` was `attacker/repo`, not `victim/repo` — proving a payload for one repository mutated another repository's commit/stack state.

      already_deployed = deployed?

      previous_status = status
      yield
      reload # to get the statuses into the right order (since sorted :desc)
      new_status = status

      unless already_deployed
        payload = { commit: self, stack:, status: new_status.state }
        Hook.emit(:commit_status, stack, payload.merge(commit_status: new_status)) if previous_status != new_status
      end

      if previous_status.simple_state != new_status.simple_state
        if !already_deployed && (!new_status.pending? || previous_status.unknown?)
          Hook.emit(:deployable_status, stack, payload.merge(deployable_status: new_status))
        end
        stack.schedule_merges if new_status.pending? || new_status.success?
      end
      new_status
    end
