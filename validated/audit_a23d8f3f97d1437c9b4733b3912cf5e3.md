Based on the code trace, this is a genuine and reproducible design flaw with no additional identity check anywhere in the pairing/execution path.

### Title
Unauthenticated `sender`/`output` binding in `PreStxOp`/`StackStxOp` allows locking an arbitrary victim's STX without their consent - (File: stackslib/src/chainstate/burn/operations/stack_stx.rs)

### Summary
`PreStxOp::parse_from_tx` sets `output` from the first Bitcoin output's decoded address with no proof that the spender of that transaction controls the corresponding Stacks private key. `Burnchain::sync_masterchecked_ops` then feeds this unauthenticated `pre_stx.output` directly as the `sender` for `StackStxOp::from_tx`, and `StacksChainState::process_stacking_ops` uses that value as the literal Clarity `tx-sender` when invoking `stack-stx` on the active PoX contract, locking that principal's STX with zero cryptographic linkage to the Bitcoin key that actually authored the operation.

### Finding Description
The broken equality: "the STX locked by a `stack-stx` burn op belongs to the principal who authored/authorized that op" is violated. In practice, `sender == pre_stx.output`, and `pre_stx.output` is set from `outputs.get(0)...address...try_into_stacks_address()` with no signature check [1](#0-0) .

`StackStxOp::get_sender_txid` only enforces that the StackStx-tagged Bitcoin transaction spends `vout == 1` of the referenced PreStxOp transaction; it performs no check that the same key/address that produced or funded `output` is doing the spending [2](#0-1) .

`Burnchain::sync_masterchecked_ops`'s pairing logic looks up the `PreStxOp` purely by `pre_stx_txid` (via `pre_stx_op_map.get` or `burnchain_db.find_burnchain_op`) and passes `&pre_stack_stx.output` straight through as `sender` to `StackStxOp::from_tx` - there is no additional identity check tying `pre_stx.output` to the Bitcoin signer of either transaction [3](#0-2) .

That `sender` field is later used verbatim as the Clarity `tx-sender` for the `stack-stx` contract call: `tx.run_contract_call(&sender.clone().into(), None, ...)` [4](#0-3) . Inside `stack-stx` (pox-4.clar), the only self-consent-adjacent checks are `is-none (get-stacker-info tx-sender)`, `is-none (get-check-delegation tx-sender)`, and a balance check `(>= (stx-get-balance tx-sender) amount-ustx)` [5](#0-4) . None of these verify that `tx-sender` (i.e., the victim) actually authorized this action - `signer-sig`/`consume-signer-key-authorization` only proves the *signer key* is authorized for the given pox-addr/params, not that the *stacker* principal consented [6](#0-5) .

Attacker's exact call sequence:
1. Attacker crafts a Bitcoin transaction tagged `PreStx`, with output[0].address = victim's Stacks address (converted to a Bitcoin address form) and output[1] funded by the attacker's own UTXO.
2. Attacker's node parses this into `PreStxOp { output: victim_address, ... }` — accepted since only the address decodability is checked, not key ownership .
3. Attacker spends output[1] of that same transaction with their own Bitcoin key, tagging the spend `StackStx` with `stacked_ustx`, `num_cycles`, etc.
4. `sync_masterchecked_ops` resolves `sender = pre_stx.output = victim_address` and builds `StackStxOp { sender: victim_address, ... }`.
5. `process_stacking_ops` invokes `stack-stx` with `tx-sender = victim_address`. If the victim has sufficient unlocked STX, is not currently stacking/delegating, the call succeeds and the victim's STX is locked for `num_cycles` reward cycles - entirely without the victim's participation.

### Impact Explanation
Any unprivileged attacker with a small amount of Bitcoin (enough for two OP_RETURN-tagged transactions and dust outputs) can permanently (for the duration of the chosen lock period, repeatable indefinitely every time the victim's account becomes unlocked and has spare balance) freeze an arbitrary victim's STX with zero consent from the victim, matching the Critical category ("permanent freezing of staked STX ... with no consent").

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: knowledge of the victim's Stacks address (public information) and the victim having unlocked STX and not already stacking/delegating. No privileged role, no signer key, no victim interaction is required. The attack costs only two ordinary Bitcoin transaction fees and is repeatable against any number of victims each cycle.

### Recommendation
Cryptographically bind `PreStxOp.output` (and thus `StackStxOp.sender`) to a value that can only be produced by someone who controls the corresponding Stacks/Bitcoin key - e.g., require the `PreStxOp`'s Bitcoin input signer's derived Stacks address to equal `output`, or require an explicit Stacks-signature (analogous to the pox-4 `signer-sig` for signer keys) authorizing the stacker principal itself before `stack-stx` is invoked with a burn-op-derived `tx-sender`.

### Proof of Concept
Rust test (in the style of `stackslib/src/burnchains/tests/db.rs`):
1. Build a `BitcoinTransaction` tagged `PreStx` whose only input is spent from a single attacker-controlled key, with `outputs[0].address` decoding to `victim_addr` (any `StacksAddress`, e.g. `StacksAddress::from_string("SP2C2...")`), distinct from any address the attacker controls, and `outputs[1]` a dust output the attacker will spend.
2. Build a second `BitcoinTransaction` tagged `StackStx` whose sole input spends `vout=1` of tx #1, signed with the SAME attacker key, carrying `stacked_ustx`/`num_cycles` payload.
3. Run both through `Burnchain::sync_masterchecked_ops` / the burnchain DB parsing pipeline used in `stackslib/src/burnchains/tests/db.rs`, and assert: `op.output == victim_addr` for the parsed `PreStxOp`, and `op.sender == victim_addr` for the parsed `StackStxOp` (equality #1: attacker's Bitcoin signer != victim's Stacks key, yet equality #2: `StackStxOp.sender == victim_addr` holds).
4. Feed the resulting `StackStxOp` into `StacksChainState::process_stacking_ops` against a chainstate where `victim_addr` holds unlocked STX; assert via `stx-account`/`get-stacker-info` that `victim_addr`'s STX becomes locked, and assert the attacker's own STX balance is untouched - demonstrating the identity equality "locked STX owner == authorizing Bitcoin key owner" is broken.
