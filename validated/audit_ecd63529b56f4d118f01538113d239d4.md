### Title
Webhook signature verification authenticates the payload's organization but handlers act on an unbound `repository.full_name` / commit `sha` - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/webhook secret to validate a delivery against based on `repository.owner.login` (or `organization.login`) taken from the JSON body, then HMAC-verifies the raw payload against that org's secret. Once verification succeeds, the same payload is handed unmodified to `Shipit::Webhooks.for_event(event)` handlers, which derive the actual target of the action from a *different* field, `repository.full_name`, that is never cross-checked against the organization used to select the verifying secret. `StatusHandler` goes even further and doesn't scope by repository at all, matching commits globally by `sha`.

### Finding Description
`repository_owner` picks the GitHub App config used for HMAC verification: [1](#0-0) [2](#0-1) 

The actual repository/stack acted on by every handler comes from a sibling field of the same JSON body, `repository.full_name`, which is not compared to `repository.owner.login`: [3](#0-2) 

`Repository.from_github_repo_name` splits this attacker-supplied string directly into an owner/name lookup with no ownership assertion beyond DB existence: [4](#0-3) 

`PushHandler` uses this lookup to force a stack sync to an attacker-chosen SHA: [5](#0-4) 

`StatusHandler` is even weaker: it matches commits by `sha` alone, with **no repository scoping whatsoever**, across the entire `commits` table, and writes an attacker-controlled `state`/`description`/`target_url`/`context`: [6](#0-5) [7](#0-6) 

Shipit explicitly supports configuring one distinct GitHub App/webhook secret per organization for exactly this multi-tenant use case: [8](#0-7) 

The binding that should hold is: **organization that authenticated (via `repository.owner.login`/`organization.login` + its webhook secret) == organization that owns the repository/commit being written to**. It does not — `verify_signature` only proves the payload bytes were HMAC-signed with *some* configured organization's secret; it never asserts that the object the handlers subsequently mutate (`repository.full_name`, or in `StatusHandler`'s case, any commit `sha` in the whole database) belongs to that same organization.

### Impact Explanation
Any entity that legitimately administers one GitHub organization/App configured in Shipit's multi-org `github:` secrets (and therefore knows that org's `webhook_secret` — a routine, non-Shipit privilege) can craft an HMAC-valid webhook body for their own org while setting `repository.full_name` (or, for `status` events, just a target `sha`) to point at a completely different tenant's repository/commit. This can:
- Force `stack.sync_github(expected_head_sha:)` on a victim stack (`PushHandler`), or
- Inject a fabricated passing (`success`) commit status for any commit `sha` known to the attacker (`StatusHandler`), which feeds directly into `Commit#deployable?` and `Commit#schedule_continuous_delivery`, potentially causing an **unauthorized deploy** of a commit that never actually passed CI in the owning organization.

This satisfies the High/Critical bar of "an unauthorized deploy" via a genuine credential/repository-boundary crossing (org A's authenticated identity writing into org B's data), not a theoretical or DoS issue.

### Likelihood Explanation
Requires only that the Shipit instance is configured for more than one GitHub organization (an explicitly documented, supported configuration) and that the attacker controls/administers one of those lower-trust orgs — a capability with zero Shipit-level privilege. No `ApiClient` token, session, or GitHub App private key is needed; only knowledge of one org's own webhook secret, which its own admins legitimately possess. On single-org deployments, this specific path is not exploitable (there is only one secret/org), so applicability depends on the multi-org deployment mode Shipit documents and supports.

### Recommendation
In `Handler#stacks`/`#repository_name`, and in `StatusHandler#process`, assert that the repository/commit's actual owning organization matches the organization whose secret verified the request (e.g., pass the verified `repository_owner` into the handler and require `repository.owner.login == verified_organization` before any lookup, and scope `StatusHandler`'s `Commit.where(sha:)` by `stack.repository` matching the verified organization).

### Proof of Concept
1. Shipit is configured with two orgs in `github:` — `attacker-org` (attacker is an org owner, knows its `webhook_secret`) and `victim-org` (hosts a tracked stack with commit `abc123` pending/unknown status).
2. Attacker computes `sha256=HMAC(attacker-org secret, body)` over a crafted JSON body:
```json
{
  "repository": { "owner": { "login": "attacker-org" }, "full_name": "victim-org/victim-repo" },
  "sha": "abc123",
  "state": "success",
  "context": "ci/required-check"
}
```
3. POST to `/webhooks` with header `X-Github-Event: status` and `X-Hub-Signature: sha256=<computed>`.
4. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` (from `repository.owner.login`) and the HMAC checks out — request passes.
5. `StatusHandler#process` runs `Commit.where(sha: "abc123")` with no org/repo filter, creating a fabricated `success` status for `victim-org`'s commit, which can trigger `schedule_continuous_delivery` and an unauthorized deploy.
