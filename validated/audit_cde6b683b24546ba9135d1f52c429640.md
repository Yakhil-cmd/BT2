### Title
Webhook signature is verified against the payload's `repository.owner.login`, but the mutated commit/repository is selected from unrelated, unverified payload fields — allowing cross-organization forged commit statuses and merge/deploy triggers - (File: `app/controllers/shipit/webhooks_controller.rb`, `app/models/shipit/webhooks/handlers/status_handler.rb`, `app/models/shipit/webhooks/handlers/handler.rb`)

### Summary
`WebhooksController#verify_signature` selects which GitHub App's `webhook_secret` to validate the HMAC signature against using `repository_owner`, taken straight from the untrusted JSON payload (`repository.owner.login` or `organization.login`). Once the signature check passes (which it will, if the attacker knows *any one* onboarded organization's `webhook_secret`, e.g. their own), the actual webhook body is handed unmodified to event handlers, which key their side effects off completely different fields of the same payload — `sha` alone for `StatusHandler`, or `repository.full_name` for `PushHandler` and PR handlers. Neither the controller nor the handlers ever verify that these acted-upon fields belong to the same organization/repository that was used to select the verification secret.

### Finding Description
The binding that should hold is: `organization whose secret verified the signature == organization/repository whose state is mutated`. This binding is broken:

- `verify_signature` picks the `GitHubApp` (and thus the `webhook_secret`) via `repository_owner`: [3](#0-2)  and [4](#0-3) .
- Once verified, the full, attacker-controlled `params` hash is dispatched unchanged to handlers: [8](#0-7) .
- `StatusHandler#process` looks up the target purely by `sha`, with no repository/organization scoping whatsoever: [1](#0-0) .
- Other handlers (push, pull_request) scope by `repository.full_name`, a separate field from `repository.owner.login` used for signature selection: [5](#0-4) , [9](#0-8) .

Because `verify_webhook_signature` HMACs the *entire raw body*, an attacker cannot simply tamper with a payload signed by a different org's secret. However, this binding failure is exploitable by anyone who legitimately controls (or is issued) the `webhook_secret` for **any one** organization configured on a multi-tenant Shipit instance (`Shipit.github_organizations`, `github_app_config`, per-organization `secrets.github[org]`). Such an actor is an unprivileged party with respect to every *other* onboarded organization's repositories/stacks, yet can craft and correctly sign a `commit_status` (or `push`/`pull_request`) payload where `repository.owner.login` names their own org (to pick their known secret) while `sha` (or `repository.full_name`) names a commit/repository belonging to a completely different, victim organization.

### Impact Explanation
Via the `commit_status` webhook, the forged payload lets the attacker inject an arbitrary GitHub commit status (e.g., `success`) onto **any commit in the entire Shipit instance**, since `StatusHandler` has no stack/repository scoping at all: [6](#0-5) . This directly affects `Commit#status`/`Commit#deployable?` and cascades: `Commit#add_status` calls `stack.schedule_merges` whenever the new status is `pending` or `success` [10](#0-9) , and `MergeRequest#any_status_checks_failed?`/`#reject_unless_mergeable!` rely on these statuses to gate the merge queue [7](#0-6) . A forged passing status can therefore make an otherwise CI-failing pull request appear mergeable, letting Shipit auto-merge it via `MergeRequest#merge!`, which calls `stack.github_api.merge_pull_request` using the **victim organization's real GitHub App credentials** [11](#0-10) . This is an unauthorized cross-repository merge/write performed with the target org's own GitHub credentials, satisfying the Critical impact bar ("cross-repository writes ... or an unauthorized deploy, rollback or merge").

### Likelihood Explanation
Exploitability requires only that the attacker possess a valid `webhook_secret` for *some* organization onboarded to a shared/multi-tenant Shipit deployment — a credential scope explicitly weaker than access to the victim organization or its GitHub token, satisfying the "unprivileged attacker" bar for this scan. No repository write access, GitHub App private key, or Shipit session/API-client token is needed for the victim side. The payload shapes required (`sha`+`state` for `commit_status`; `repository.full_name`+`ref`/`after` for `push`) are minimal and already documented by the handler `params` blocks.

### Recommendation
Cross-check, inside `WebhooksController#verify_signature` (or centrally in `Shipit::Webhooks::Handlers::Handler`), that the organization/repository actually acted upon by the handler (`repository.full_name`'s owner, or the `Stack`'s `Repository#owner` resolved from `sha`) matches the organization whose secret validated the signature (`repository_owner`). Reject the webhook if they diverge. Additionally, `StatusHandler` should be scoped to the repository identified in the payload rather than matching bare `sha` across the whole instance.

### Proof of Concept
1. Onboard/administer Org B on the shared Shipit instance and obtain its legitimate `webhook_secret` (a value scoped only to Org B, not Org A).
2. Craft a `commit_status` webhook body:
```json
{
  "sha": "<victim Org A commit sha, currently CI-failing>",
  "state": "success",
  "context": "ci/required",
  "repository": { "owner": { "login": "org-b" } }
}
```
3. Sign the raw body with Org B's `webhook_secret` and POST it to `/github/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"org-b"`, fetches Org B's app, and the HMAC check passes (attacker knows this secret).
5. `StatusHandler#process` finds `Commit.where(sha: ...)` — matching Org A's commit regardless of `repository.owner` — and calls `create_status_from_github!`, marking it `success`.
6. If this was the last blocking status for a merge-queued PR in Org A, `stack.schedule_merges` (triggered from `add_status`) proceeds to merge the PR using Org A's real GitHub App token.
