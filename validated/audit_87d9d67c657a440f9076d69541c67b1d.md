### Title
Front-runnable, attacker-controlled initial reserve ratio in the bonding-curve AA pattern allows share-price manipulation and fund extraction - (File: test/samples/uniswap_like_market_maker.oscript)

### Summary
The external report describes `SeriousMarket.createPoolAndAddLiquidity`, which adds liquidity to a Uniswap pool assuming it starts at a specific price; if the pool already exists (or is created first) with an attacker-chosen price, liquidity is misallocated and the attacker profits by swapping against the mispriced pool. The `ocore` repository ships an official AA (Autonomous Agent) template, `test/samples/uniswap_like_market_maker.oscript`, that implements the same bonding-curve/AMM pattern on top of `ocore`'s AA balance-tracking primitives, and it exhibits the identical root-cause weakness: the pool's initial reserve ratio is set by whichever *unprivileged* trigger happens to be first, with no protocol-level protection against front-running that initialization step.

### Finding Description
The AMM template's "invest in MM" branch decides between bootstrap pricing and ratio-based pricing purely from the AA's current on-chain balances, read via the `balance[...]` formula operator: [1](#0-0) 

```
$asset_balance = balance[$asset] - trigger.output[[asset=$asset]];
$bytes_balance = balance[base] - trigger.output[[asset=base]];
if ($asset_balance == 0 OR $bytes_balance == 0){ // initial deposit
    $issue_amount = balance[base];
    return;
}
$current_ratio = $asset_balance / $bytes_balance;
```

`balance[asset]` is not a value scoped to a specific "pool creation" transaction guarded by access control — it is the AA's raw aggregate confirmed balance, computed generically from every output ever sent to the AA address, as implemented in `storage.insertAADefinitions` (balance aggregation query) and read at formula-evaluation time by `readBalance`: [2](#0-1) [3](#0-2) 

Because any address can trigger the AA by simply sending it a payment (`validateAATriggerObject` only checks that outputs are positive integers and the target is a registered AA address, with no requirement about who is "first" or what ratio is being set): [4](#0-3) 

any unprivileged unit poster can be the one whose trigger first satisfies `$asset_balance == 0 OR $bytes_balance == 0`, and thereby unilaterally choose the pool's bootstrap ratio between `$asset` and `base` — exactly analogous to a user calling `IUniswapV3Pool.initialize()` with an attacker-chosen price before the "official" initializer's liquidity-add transaction lands. Every subsequent "invest", "exchange bytes to asset" and "exchange asset to bytes" branch prices trades strictly off this attacker-chosen ratio: [5](#0-4) [6](#0-5) 

There is no mechanism in `ocore`'s AA execution model (`aa_composer.js`, `formula/evaluation.js`) that lets an AA author atomically "create and correctly price" a bonding-curve pool the way a privileged, single transaction would — the balance state that determines pricing is always attacker-observable and attacker-influenceable before the AA author's own initializing/liquidity-providing trigger can execute, because trigger ordering on the DAG is controlled by whoever posts first, not by the AA definer.

### Impact Explanation
An attacker can front-run the legitimate initial liquidity provider by triggering the "invest in MM" bootstrap branch first with a heavily skewed `asset:base` ratio (e.g., depositing a large amount of `base` against a minimal amount of `$asset`, or vice versa). This sets `var['mm_asset_outstanding']` and the pool reserves to an artificial ratio. Legitimate depositors who follow are then forced to either accept the manipulated ratio (locking in an incorrect valuation and effectively transferring value to the attacker) or are bounced by the `wrong ratio of amounts` check, denying them normal use of the market maker. The attacker can subsequently use the "exchange bytes to asset" / "exchange asset to bytes" branches to arbitrage the mispriced pool against real market value, extracting funds from the pool at the expense of later depositors — a direct AA fund-loss scenario reachable purely by an unprivileged AA trigger sender.

### Likelihood Explanation
Likelihood is high: the attack requires only observing that a new AMM-style AA has been defined (its address and definition are public once the `definition` message is posted or predictable from `chash160`), and then racing to be the first trigger with a small deposit — a standard, cheap front-running operation on any DAG/mempool-like broadcast system, requiring no special privileges, keys, or protocol-level access.

### Recommendation
`ocore`'s AA template/documentation (and any bonding-curve style AA built on `balance[...]`) should not rely on "current aggregate balance equals zero" as the sole signal to determine bootstrap pricing, since this state is fully attacker-observable and attacker-mutable by unprivileged parties before the intended initializer's trigger executes. Safer patterns include: (1) fixing the initial ratio/price as an immutable parameter of the AA definition itself (so it cannot be chosen by whichever trigger arrives first), (2) restricting the bootstrap/"initial deposit" trigger to a specific address (e.g. the AA definer) via `issued_by_definer_only`-style checks, or (3) requiring an explicit, separate "finalize pool" step that reverts if the reserves were touched by anyone other than the expected initializer, mirroring the recommendation in the external report to avoid an existence/state check that silently no-ops or partially executes under attacker-controlled preconditions.

### Proof of Concept
1. AA author posts the `definition` message for `uniswap_like_market_maker.oscript`; its address becomes known/computable by anyone.
2. AA author intends to send the first "invest" trigger with `base = 10,000,000` and `$asset = 10,000` (implying a "fair" 1000:1 ratio).
3. Attacker observes the pending definition/first-trigger intent and races a trigger with `base = 100,001` (just over the `1e5` threshold) and `$asset = 1` before the AA author's transaction is included, satisfying:
   `trigger.output[[asset=base]] > 1e5 AND trigger.output[[asset=$asset]] > 0`
   Since `$asset_balance == 0` at this point, the bootstrap branch fires:
   `$issue_amount = balance[base]` (≈100,001), and reserves become `asset=1`, `base=100,001` (ratio 1:100,001).
4. When the AA author's original 10,000,000/10,000 trigger lands, `$current_ratio = 1/100001`, and `$expected_asset_amount = round(current_ratio * 10,000,000) ≈ 100`, which does not equal the AA author's supplied `10,000` — the deposit bounces with `wrong ratio of amounts`, or if resubmitted matching the skewed ratio, the AA author is forced to trade at the attacker's chosen price, after which the attacker can call the "exchange asset to bytes" / "exchange bytes to asset" branches to profit from the artificial ratio at the AA author's expense.
