## Analysis

This is a genuine analog to the reported bug class ("whitelist/governance change strands existing positions"), found in ocore's `spender_attested` asset mechanism rather than in a lending protocol. [1](#0-0) , an asset's attestor list (a whitelist of addresses trusted to vouch for spenders) can be freely rewritten by the asset **definer** at any time via an `asset_attestors` message, with no protection for addresses that already hold and rely on the *current* attestor list to move their existing balance.

`storage.js`'s `readAsset()` only loads the **single latest** attestor list unit and uses it as `objAsset.arrAttestorAddresses`: [2](#0-1) 

That current-only attestor set is what `filterAttestedAddresses()` uses to decide whether any address is "attested": [3](#0-2) 

Both the **input (spend)** side and the **output (receive)** side of a `spender_attested` asset payment are gated on this same live-computed attestor list: [4](#0-3) [5](#0-4) 

`validateAttestorListUpdate` allows the definer to swap out attestors with essentially no other constraint (only "single-authored", "definer only", and basic list format checks) [1](#0-0) .

### Title
Asset definer can rewrite an asset's attestor whitelist and permanently freeze already-issued balances of previously-attested holders - (File: storage.js, validation.js)

### Summary
`spender_attested` assets require every input owner and output address to be "attested" by one of the addresses in the asset's *current* attestor list, as computed by `storage.readAsset()`/`filterAttestedAddresses()`. Only the latest `asset_attestors` unit is ever consulted, and it can be replaced at will by the asset definer. Because attestation status is re-derived against this always-current list rather than being fixed at the time the holder actually received/was attested for their coins, a definer-initiated attestor-list update can instantly and irreversibly strip previously-valid attestation from existing coin holders. Those holders can never again build a valid `transfer`/`payment` input for that asset, since the very same live-computed attestor list is enforced on inputs, permanently freezing their balance — exactly the "whitelist change breaks existing positions" bug class from the source report, here manifesting as unauthorized freezing of already-owned coins instead of unauthorized liquidation.

### Finding Description
1. An asset is created with `spender_attested: true` and an initial `attestors` list (`validateAssetDefinition`, `validation.js:2725-2827`).
2. Address A is attested by attestor X (an `attestation` message referencing X as `attestor_address`), and subsequently receives an output of the asset. This passes the output check in `validatePaymentInputsAndOutputs` because X is in the asset's attestor list at that time (`validation.js:2630-2641`).
3. The definer later publishes an `asset_attestors` message that removes X from the attestor list (`validateAttestorListUpdate`, `validation.js:2829-2848` — no restriction preventing removal of attestors that vouch for existing balance holders).
4. `storage.readAsset()`'s `addAttestorsIfNecessary()` now returns only the new (X-less) attestor list as `objAsset.arrAttestorAddresses` for any future validation (`storage.js:1917-1946`).
5. When address A now tries to spend its existing (already-held) coin as a `transfer` input, `validatePaymentInputsAndOutputs` checks `objAsset.spender_attested && objAsset.arrAttestedAddresses.indexOf(owner_address) === -1` (`validation.js:2504-2507`), using `arrAttestedAddresses` computed via `filterAttestedAddresses()` against the *new* attestor list only (`storage.js:1959-1974`). Since A's only attestation came from the now-removed X, A is no longer considered attested and the transfer is rejected with "owner address is not attested".
6. Address A's balance is now permanently unspendable unless a currently-whitelisted attestor chooses to attest A — an action entirely outside A's control, mirroring the Isomorph-style "governance disallow prevents existing positions from being handled" bug: the whitelist change was meant to gate *new* activity but instead retroactively locks *already-owned* funds.

If the affected address A is an AA base address (an AA received the asset and is holding it as part of its balance/state), the AA itself becomes permanently unable to move that portion of its balance — a concrete AA fund freezing outcome, since AAs cannot request third-party attestation on demand and have no bypass path.

### Impact Explanation
This allows any single-authored, definer-controlled `asset_attestors` update to instantly and irreversibly freeze arbitrary existing token holders' balances (including AA-held balances) for a `spender_attested` asset, with no way for the frozen party to regain spendability except at the discretion of a currently-listed attestor. This is a direct "AA fund loss/freezing" outcome and mirrors the audited bug class: a whitelist/permission structure intended to control new activity is instead applied retroactively to strand already-existing balances, with no protection or path to recovery for the holder.

### Likelihood Explanation
Requires only the asset definer (a normal, unprivileged asset-issuance role reachable by any user who creates a `spender_attested` asset) to publish a single valid `asset_attestors` unit — an ordinary, always-available operation with no special permission beyond being the asset's own definer. No cooperation from miners, witnesses, or other privileged actors is needed, and the freezing occurs as soon as the update unit becomes stable.

### Recommendation
Do not use only the single latest attestor list when validating whether an owner/spender is attested. Either:
- Validate spend-side attestation against the attestor list that was in effect (or any historically-effective attestor list) at the time the address's underlying attestation/coin was created, similar to how `filterAttestedAddresses` already restricts by `main_chain_index > address_definition_changes` for definition changes; or
- Require any `asset_attestors` update to only add attestors, or provide a way for coin holders to "grandfather" attestation status established under a prior attestor list when spending previously-received coins, so that whitelist changes affect new payments only, not already-held balances.

### Proof of Concept
1. Definer D creates asset `ASSET` with `spender_attested: true`, `attestors: [X]`.
2. Attestor X attests address A.
3. A receives `ASSET` coins in a payment output; validation passes because X ∈ current attestor list (`validation.js:2630-2641`).
4. D publishes `asset_attestors` for `ASSET` with `attestors: [Y]` (X removed) — accepted per `validateAttestorListUpdate` (`validation.js:2829-2848`), no check for existing holders attested only by X.
5. A attempts to spend its previously-received `ASSET` coin as a `transfer` input. `readAsset`/`filterAttestedAddresses` now only recognize Y as a valid attestor (`storage.js:1917-1974`), so A is not in `arrAttestedAddresses`; `validatePaymentInputsAndOutputs` rejects with "owner address is not attested" (`validation.js:2504-2507`).
6. A's coin is now permanently frozen unless Y (a party A has no control over) chooses to attest A.

function validateAttestorListUpdate(conn, payload, objUnit, objValidationState, callback){
	if (objUnit.authors.length !== 1)
		return callback("attestor list must be single-authored");
	if (!isNonemptyObject(payload))
		return callback("attestor update must be a non-empty object");
	if (hasFieldsExcept(payload, ['asset', 'attestors']))
		return callback("foreign fields in attestor list update");
	storage.readAsset(conn, payload.asset, objValidationState.last_ball_mci, false, function(err, objAsset){
		if (err)
			return callback(err);
		if (!objAsset.spender_attested)
			return callback("this asset does not require attestors");
		if (objUnit.authors[0].address !== objAsset.definer_address)
			return callback("attestor list can be edited only by definer");
		err = checkAttestorList(payload.attestors);
		if (err)
			return callback(err);
		callback();
	});
}

function filterAttestedAddresses(conn, objAsset, last_ball_mci, arrAddresses, handleAttestedAddresses){
	conn.query(
		"SELECT DISTINCT address FROM attestations CROSS JOIN units USING(unit) \n\
		WHERE attestor_address IN(?) AND address IN(?) AND main_chain_index<=? AND is_stable=1 AND sequence='good' \n\
			AND main_chain_index>IFNULL( \n\
				(SELECT main_chain_index FROM address_definition_changes JOIN units USING(unit) \n\
				WHERE address_definition_changes.address=attestations.address AND main_chain_index<=? AND is_stable=1 AND sequence='good' ORDER BY main_chain_index DESC LIMIT 1), \n\
			0)",
		[objAsset.arrAttestorAddresses, arrAddresses, last_ball_mci, last_ball_mci],
		function(addr_rows){
			var arrAttestedAddresses = addr_rows.map(function(addr_row){ return addr_row.address; });

		}
	);
