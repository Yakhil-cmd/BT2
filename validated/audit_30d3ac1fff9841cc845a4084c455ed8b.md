### Title
Stack-scoped API token can read the CCMenu status of any stack, not just the one it authorizes - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::Api::BaseController` enforces that an `ApiClient` bound to a specific `stack_id` can only resolve stacks from its own scope via the `stacks`/`stack` helper methods. `Shipit::Api::CCMenuController` overrides the `stack` helper and resolves the stack directly from the request parameter without applying that scope, so a token that is authorized for one stack can be used to read CI/deploy status for any other stack.

### Finding Description
`BaseController#stacks` restricts the set of stacks a request can touch to the one the `ApiClient` is bound to: [1](#0-0) 

This is the binding the rest of the API relies on: `current_api_client.stack_id?` (whether the token was scoped to a specific stack) gates which `Stack` records `stack.from_param!` can resolve, and `test/controllers/api/stacks_controller_test.rb` documents this contract ("an api client scoped to a stack will only see that one stack").

`CCMenuController`, however, defines its own `stack` method that calls `Stack.from_param!(params[:stack_id])` directly, bypassing the `stacks` scoping entirely: [2](#0-1) 

The only authorization check performed before `show` is `require_permission :read, :stack`, which merely verifies the token has the `read:stack` permission string on its `permissions` array: [3](#0-2) 

`check_permissions!` never looks at `stack_id` — it only checks the coarse `permissions` list. The equality that should hold is:
`stack a token authorizes (current_api_client.stack_id) == stack the controller action touches (params[:stack_id] resolved via `stack`)`.
Everywhere else in the API this equality is enforced through `BaseController#stack` (built on `stacks`), but `CCMenuController` breaks it by resolving `params[:stack_id]` against the unscoped `Stack` model.

### Impact Explanation
Any `ApiClient` holding `read:stack` permission — including a token deliberately scoped to a single stack (`stack_id` set) via `CCMenuUrlController`/administrative provisioning — can supply an arbitrary `stack_id` to `GET /api/:stack_id/cc.xml` and retrieve that other stack's CI/build/deploy status (`lastBuildStatus`, `lastBuildLabel`, `webUrl`, lock status, etc.), even though the token was never authorized for that stack. This is an unauthorized cross-stack read of deploy/build state, matching the High-severity class "unauthenticated read of stack state, task streams or deploy output" (here, authenticated but out-of-scope).

### Likelihood Explanation
Any holder of a stack-scoped, `read:stack`-permitted token (e.g., the CCMenu token issued by `CCMenuUrlController`, or any other scoped token an operator provisions) can trigger this simply by changing the `stack_id` URL segment — no privilege escalation, signature forgery, or additional secrets are required.

### Recommendation
Remove the `CCMenuController#stack` override (or make it call `super`) so it uses the scoped `stacks.from_param!` helper from `BaseController`, ensuring the CCMenu endpoint respects the same `stack_id` scoping as every other API controller.

### Proof of Concept
1. Provision (or use an existing) `ApiClient` with `permissions: ["read:stack"]` and `stack_id` set to Stack A (e.g., via the `CCMenuUrlController#client` flow, which creates such a scoped, read-only client): [4](#0-3) 
2. Using that token's `authentication_token` for Basic Auth (or as the `token` query param), call `GET /api/<STACK_B>/cc.xml`, where `STACK_B` is a different stack the token was never scoped to.
3. `CCMenuController#stack` resolves `STACK_B` via `Stack.from_param!` (unscoped), bypassing the intended `stacks` restriction, and returns Stack B's CI/deploy status in the response, confirming the token can read data outside its authorized stack.
