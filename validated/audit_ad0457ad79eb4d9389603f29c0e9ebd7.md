### Title
Webhook organization used for signature verification is decoupled from the repository/team actually mutated by the handler, allowing a weakly-configured (or secret-less) GitHub organization to forge writes against a different organization's stacks - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization's `webhook_secret` to check the HMAC signature against using an attacker-controlled JSON field (`repository.owner.login`, falling back to `organization.login`), while the event handlers that actually perform writes (`PushHandler`, `StatusHandler`, `MembershipHandler`, etc.) derive the repository/team to act on from other, independently-controlled fields of the same unauthenticated body (`repository.full_name`) or reuse the organization/team ids without re-checking they belong to the org whose secret verified the request. This breaks the trust binding: `organization used to verify signature == organization/repository the handler mutates`.

### Finding Description
The webhook signature check picks the GitHub App configuration purely from payload content: [1](#0-0) 

`repository_owner` is read straight out of the still-unverified JSON body: [2](#0-1) 

`Shipit.github(organization: repository_owner)` returns the `GitHubApp` configured for that org and `verify_webhook_signature` is invoked against it. Critically, when no `webhook_secret` is configured for that org, verification is a no-op: [3](#0-2) 

Shipit explicitly supports multiple GitHub organizations sharing one installation, each with its own independent `webhook_secret` entry, and the webhook secret is documented/implemented as optional (`@config[:webhook_secret].presence`), which several bundled configs demonstrate by leaving it `nil`.

Once `verify_signature` passes, `WebhooksController#create` dispatches the *entire raw payload* to the handler: [4](#0-3) 

but the handlers determine the actual target of the write from a **different field** of that same payload, never re-validating it against the organization used for authentication: [5](#0-4) [6](#0-5) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used for the write) are two independent strings inside the same JSON object, nothing enforces that `full_name` actually belongs to `owner.login`. If the Shipit instance is configured with more than one GitHub organization (a documented feature) and any one of them has no `webhook_secret` set, an attacker can submit a payload where `repository.owner.login` equals that unsecured organization (so `verify_webhook_signature` trivially returns `true`), while `repository.full_name` names a repository/stack that belongs to a different, secured organization actually onboarded to Shipit. `PushHandler` will then locate stacks purely via `Repository.from_github_repo_name(repository_name)` and enqueue a `GithubSyncJob`, and `StatusHandler` will attach forged commit statuses to arbitrary commits by `sha`, all without ever revalidating that the organization which "authenticated" the request is the one whose repository is being mutated.

This is the structural analog of the report's core defect: the component performing state changes ("to_handler"/handler write target) trusts a boundary check ("settlement/from org verification") that was performed against a different, swappable/unbound identifier than the one it actually consumes.

### Impact Explanation
An attacker who knows (or exploits the absence of) the `webhook_secret` for **any one** of the organizations configured on a multi-org Shipit instance can forge `push`/`status`/`check_suite` events that are accepted as authentic for a **different** organization's repositories. This lets them: trigger `GithubSyncJob` (`sync_github`) for arbitrary stacks, forge commit `Status` records used to gate deploys/merges, and manipulate `Team`/`Membership` records tied to a `Team.organization` that governs `Shipit.github_teams` authorization. This can lead to unauthorized deploys/merges being unblocked or triggered and to cross-repository/cross-organization writes without any legitimate GitHub-signed event for the targeted repository, matching the Critical-impact bucket (cross-repository writes / unauthorized deploy).

### Likelihood Explanation
Requires: (1) the Shipit deployment to configure more than one GitHub organization (an explicitly supported, documented configuration) and (2) at least one of those configured organizations to have no `webhook_secret` set — a state the code itself treats as valid (`return true unless webhook_secret`), not a misconfiguration outside the documented feature set. No `webhook_secret`, `ApiClient` token, or session is required for the attacking organization's slot; the attacker only needs to reach the public `/webhooks` endpoint. This makes the likelihood moderate and entirely conditioned on a supported multi-org setup rather than on the host failing to mount the engine as documented.

### Recommendation
1. After selecting the `GitHubApp` for signature verification via `repository_owner`, re-derive and cross-check that `repository.full_name`'s owner segment matches the exact organization whose secret verified the payload (reject if they diverge) before dispatching to handlers.
2. Make `webhook_secret` mandatory for every configured organization (fail fast at boot if any org lacks one) rather than silently trusting unsigned payloads.
3. Have `Handler#repository_name`/`Handler#stacks` and `MembershipHandler#find_or_create_team!` accept and enforce the verified organization identity explicitly (pass it down from the controller) instead of re-reading it from the unvalidated payload.

### Proof of Concept
1. Configure Shipit with two organizations in `github:` secrets: `secure-org` (has a `webhook_secret`) and `legacy-org` (no `webhook_secret`, i.e., `nil`), both installed and with repositories/stacks tracked in Shipit.
2. POST to `/webhooks` with header `X-Github-Event: push` and a raw JSON body:
```json
{
  "ref": "refs/heads/master",
  "after": "<attacker-chosen-sha>",
  "repository": {
    "owner": { "login": "legacy-org" },
    "full_name": "secure-org/production-app"
  }
}
```
No `X-Hub-Signature` value is needed to pass, since `Shipit.github(organization: "legacy-org").verify_webhook_signature` returns `true` unconditionally (`webhook_secret` is `nil`).
3. `WebhooksController#create` dispatches the parsed body to `Shipit::Webhooks::Handlers::PushHandler`, which resolves `repository_name` as `"secure-org/production-app"` and enqueues a `GithubSyncJob` for that stack — a write against `secure-org`'s repository that was never signed by `secure-org`'s credentials.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
