## Title
Webhook signature verification keys on `repository.owner.login`/`organization.login` while handlers act on the independently-controlled `repository.full_name` field, letting one onboarded org spoof events for another org's repository - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects which `GithubApp`/`webhook_secret` to use for HMAC verification based on `repository_owner`, computed from `params.dig('repository','owner','login')` (falling back to `params.dig('organization','login')`). Once the signature validates, the handlers dispatched by `Shipit::Webhooks.for_event` (e.g. `PushHandler`, `PullRequest::OpenedHandler`) act on a *different* field of the same JSON body — `repository.full_name` — to look up the `Repository`/`Stack` to mutate. Because the raw JSON body is attacker-composed before signing (the attacker only needs a webhook secret they legitimately possess for their *own* onboarded organization), nothing enforces that `repository.owner.login` (the field used to pick the verification key) and `repository.full_name`'s owner segment (the field the handlers actually act on) refer to the same organization.

### Finding Description
`verify_signature` in `app/controllers/shipit/webhooks_controller.rb:24-49` does:
```ruby
def verify_signature
  github_app = Shipit.github(organization: repository_owner)
  verified = github_app.verify_webhook_signature(request.headers['X-Hub-Signature'], request.raw_post)
  ...
end

def repository_owner
  params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
end
```
`repository_owner` is purely a value read out of the attacker-supplied JSON body — it is not otherwise validated against anything Shipit trusts (e.g., it isn't compared against the installation that actually delivered the request; there's no GitHub App installation ID cross-check).

Once `verify_webhook_signature` succeeds (using the secret configured for whatever org string the attacker put in `repository.owner.login`), `WebhooksController#create` dispatches the parsed body to every registered handler for the event:
```ruby
def create
  params = JSON.parse(request.raw_post)
  Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }
  head(:ok)
end
```
Handlers such as `Shipit::Webhooks::Handlers::Handler#repository_name` (`app/models/shipit/webhooks/handlers/handler.rb:36-38`) and `PullRequest::OpenedHandler#repository` (`app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb:50-54`) resolve the target `Repository`/`Stack` from `payload.dig('repository', 'full_name')` via `Repository.from_github_repo_name`, i.e., a completely separate JSON field from the one used to pick the verification key.

Because `repository.owner.login` and `repository.full_name` are two independent string fields inside the same JSON object, an attacker who is a legitimate administrator of Org A (with their own GitHub App/webhook secret configured in Shipit, as shown by the multi-org `config/secrets.development.shopify.yml` layout supporting several onboarded orgs) can construct a raw POST body where:
- `repository.owner.login` = `"org-a"` (so `Shipit.github(organization: "org-a")` picks Org A's `webhook_secret`, which the attacker knows because they administer Org A's GitHub App/webhook), and
- `repository.full_name` = `"org-b/victim-repo"` (an unrelated org's onboarded repository/stack).

The attacker computes a valid `X-Hub-Signature` over this body using Org A's secret. `verify_signature` passes (the org used for verification matches what's embedded in the body). But every handler that resolves the target resource off `repository.full_name` will now act on Org B's `Repository`/`Stack`, which the attacker has no actual GitHub access to.

This is exactly the "organization that authenticated versus the repository that is written" binding break: the signature only proves the request came from *some* onboarded organization's webhook holder, not that it came from the organization owning the repository the handler is about to mutate.

### Impact Explanation
Concretely reachable outcomes for `pull_request` events (handled by `PullRequest::OpenedHandler`, `app/models/shipit/webhooks/handlers/pull_request/opened_handler.rb`):
- `repository` is resolved from the attacker-chosen `full_name` (Org B's real repo), and `ReviewStackAdapter.find_or_create!` provisions a review stack for Org B using entirely attacker-controlled `pull_request` fields (`head.sha`, `head.ref`, `user.login`, `labels`, etc.), if Org B's repository has `review_stacks_enabled` and an allow-all/label-based provisioning policy.
- The created review stack, once provisioned, is deployed by Shipit using Org B's actual GitHub App credentials and Org B's `shipit.yml` deploy scripts — i.e., a deploy is triggered for Org B's repository as a direct consequence of a forged webhook signed with Org A's secret. This satisfies the "unauthorized deploy" Critical-impact criterion.
- For `push` events (`PushHandler`), the same divergence causes `GithubSyncJob` to be enqueued against Org B's stack with an attacker-chosen `expected_head_sha`, forcing unscheduled sync/deploy-pipeline activity on an org the attacker does not control.

### Likelihood Explanation
Exploitation requires the attacker to control (administer) at least one organization that is legitimately onboarded onto the shared Shipit instance — a realistic scenario given Shipit is explicitly designed to be multi-tenant (`config/secrets.development.shopify.yml` shows multiple orgs each with their own `webhook_secret`). No compromise of Org B's credentials, GitHub App private key, or Shipit session is required; the attacker only needs their own legitimately-configured webhook secret and the ability to craft an arbitrary raw HTTP POST to Shipit's `/github/webhooks` endpoint (any HTTP client, no GitHub interaction needed). This is a straightforward, low-effort exploitation path once org boundaries are understood.

### Recommendation
After signature verification, re-derive and cross-check the organization from the field(s) the handler will actually act on (`repository.full_name`'s owner segment, or `organization.login` for org-scoped events) and require it to match `repository_owner` used to select the verifying `GithubApp`. Alternatively/additionally, verify that the resolved `Repository`'s stored `owner` matches the app/organization whose secret validated the signature before dispatching to handlers, rejecting the webhook otherwise.

### Proof of Concept
1. Shipit is configured (as in `config/secrets.development.shopify.yml`) with two onboarded orgs: `org-a` (attacker-administered, webhook secret known to attacker) and `org-b` (victim org, with a stack for `org-b/victim-repo` that has `review_stacks_enabled` and `provisioning_behavior_allow_all`).
2. Attacker crafts a `pull_request` "opened" JSON payload:
   ```json
   {
     "action": "opened",
     "number": 1,
     "pull_request": {
       "id": 1, "number": 1, "url": "...", "title": "pwn",
       "state": "open", "additions": 0, "deletions": 0,
       "head": { "sha": "deadbeef", "ref": "attacker-branch" },
       "user": { "login": "attacker" },
       "assignees": [], "labels": []
     },
     "repository": { "owner": { "login": "org-a" }, "full_name": "org-b/victim-repo" },
     "sender": { "login": "attacker" }
   }
   ```
3. Attacker computes `X-Hub-Signature: sha1=<HMAC-SHA1(org-a's webhook_secret, raw_body)>` and POSTs to `/github/webhooks` with header `X-Github-Event: pull_request`.
4. `verify_signature` calls `Shipit.github(organization: "org-a")` (from `repository.owner.login`) and successfully verifies the signature.
5. `PullRequest::OpenedHandler#repository` resolves `Shipit::Repository.from_github_repo_name("org-b/victim-repo")`, finds the real Org B repository, and — if provisioning conditions are met — creates/provisions a review stack for Org B driven entirely by attacker-supplied PR data, ultimately triggering a deploy under Org B's GitHub App credentials.
