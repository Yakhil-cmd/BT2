### Title
Weak `equals` condition in Hookify rule engine allows trivial bypass of PreToolUse blocking rules - (File: `plugins/hookify/core/rule_engine.py`)

### Summary
The `hookify` plugin's `RuleEngine._check_condition` supports an `equals` operator that performs strict string equality (`pattern == field_value`) between a rule's configured pattern and an attacker/user-controlled field such as a Bash `command` or file `new_text`/`content`. Rules using this operator to *block* dangerous operations (`action: block`) are trivially defeated by any character-level variation of the guarded value, mirroring the reported `Comparison.EQUAL` weak-condition bug class: a security-relevant check keyed on an easily-manipulated value that supports only exact equality.

### Finding Description
`RuleEngine.evaluate_rules` promotes any rule whose conditions all match to a `block` decision, which for `PreToolUse`/`PostToolUse` events becomes `"permissionDecision": "deny"` [1](#0-0) . Whether a condition matches is decided in `_check_condition`, where the `equals` operator does a strict Python `==` comparison of the rule's static `pattern` against the extracted field value: [2](#0-1) 

```python
if operator == 'regex_match':
    return self._regex_match(pattern, field_value)
elif operator == 'contains':
    return pattern in field_value
elif operator == 'equals':
    return pattern == field_value
```

The `field` fed into this comparison for Bash rules is the raw `command` string taken directly from `tool_input`, and for file-write rules is `new_text`/`content` [3](#0-2) . These values are entirely controlled by the user/agent issuing the tool call — the same actor the blocking rule is meant to restrain. Unlike `regex_match` or `contains`, `equals` requires an exact character-for-character match, so any trivial variation (extra whitespace, quoting, case change, added flag/argument, trailing `;`, alternate path form) causes the condition — and therefore the entire rule, since `_rule_matches` requires **all** conditions to match [4](#0-3)  — to silently fail, allowing the operation through with no warning at all.

This is documented as a supported, recommended configuration option in the plugin's own docs (`operator: equals` → "Exact string match") [5](#0-4)  and in the README's operator reference [6](#0-5) , so any user/team writing a hookify blocking rule for a specific dangerous command or content pattern using `equals` is inherently building a bypassable gate.

### Impact Explanation
Any Hookify rule with `action: block` that uses the `equals` operator on a `command`, `file_path`, `new_text`, `content`, or `old_text` field can be bypassed by the exact actor the rule was designed to stop — since the value being compared is fully attacker/user-controlled and only exact string matches trigger the deny decision. This defeats the intended `PreToolUse` hook-based command/content approval gate, letting a disallowed Bash command execute or disallowed file content be written despite an administrator's or team's `.local.md` rule intending to block it. This is a hook-bypass / unauthorized-shell-action class impact within the project's own trust boundary model (hooks are meant to be an enforced deny gate before tool execution) [7](#0-6) .

### Likelihood Explanation
Likelihood is high in any deployment that actually uses `equals` for a blocking rule, because bypassing it requires no special access — just typing the command slightly differently (extra space, added argument, different quoting) — something a normal user or an LLM agent could do unintentionally as well as intentionally. The plugin's own documentation presents `equals` as a normal, valid operator choice for both bash and file conditions, increasing the chance it is used in practice for blocking rules rather than reserved for benign warning use cases.

### Recommendation
Discourage or disallow `equals` as an operator for `action: block` rules on inherently variable fields like shell commands or file content; recommend `regex_match` (anchored) or `contains`/`starts_with` combined with normalization (trim whitespace, collapse repeated spaces, lowercase where appropriate) instead. At minimum, update the documentation to warn that `equals` is a literal, easily-bypassed match and unsuitable for security-blocking rules, matching the same caution the external report raises against `Comparison.EQUAL` for security-sensitive checks.

### Proof of Concept
1. Create a hookify rule blocking a dangerous command via exact match:
```markdown
---
name: block-rm-rf-tmp
enabled: true
event: bash
action: block
conditions:
  - field: command
    operator: equals
    pattern: "rm -rf /tmp/test"
---
Blocked dangerous rm command.
```
2. Running `rm -rf /tmp/test` is blocked (`_check_condition` returns `True`, rule matches, `PreToolUse` denies it) [8](#0-7) .
3. Running any trivially different but equally destructive command, e.g. `rm -rf /tmp/test ` (trailing space), `rm  -rf /tmp/test` (double space), or `rm -rf /tmp/test/`, causes `pattern == field_value` to evaluate `False`, so the condition — and the whole rule — fails to match, and `evaluate_rules` returns `{}` (allow) [9](#0-8) , letting the destructive command execute despite the intended block.
