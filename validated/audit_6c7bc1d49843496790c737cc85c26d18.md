### Title
Cross-repository commit status forgery via unscoped `Commit.where(sha:)` lookup - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `sha` alone across the entire `commits` table, without any scoping to the repository that authenticated the webhook. Any GitHub organization with a Shipit webhook configured can send a `status` event naming a sha that happens to exist on a *different* Stack (e.g. via shared fork history or coincidentally identical initial commits), causing that foreign commit's `Status` to be created/updated, potentially flipping `Commit#deployable?` to `true` and firing `schedule_continuous_delivery` on a Stack the attacker never authenticated for.

### Finding Description
The claimed binding is: `sha_targeted_by_webhook.repository == webhook_signer.repository`. In `status_handler.rb` this binding is never enforced.

`app/models/shipit/webhooks/handlers/status_handler.rb`:
```ruby
def process
  Commit.where(sha: params.sha).each do |commit|
    commit.create_status_from_github!(params)
  end
end
``` [1](#0-0) 

Unlike `CheckSuiteHandler`, which correctly scopes lookups through `Handler#stacks` — `Repository.from_github_repo_name(repository_name)&.stacks` — before filtering by sha [2](#0-1) [3](#0-2) , `StatusHandler` ignores `payload['repository']` entirely and queries `Commit` globally by `sha`.

`WebhooksController#verify_signature` only verifies that the request is validly signed for the organization named in the payload's `repository.owner.login` (or `organization.login`) — it does not restrict which shas that org's webhook is allowed to reference: `github_app = Shipit.github(organization: repository_owner)` [4](#0-3) . So a valid signature from org A's webhook secret authorizes a `status` payload naming *any* sha string, and `StatusHandler` will match it against commits belonging to any Stack in the entire Shipit instance, including Stacks owned by org B.

Exploit flow: attacker forks/owns a repository under an org for which they can generate (or already have) a valid webhook signature (this only requires that org's Shipit-configured `webhook_secret`, which the attacker's own org controls for their own repo). They send a `status` webhook body such as `{"repository": {"owner": {"login": "attacker-org"}}, "sha": "<sha_of_commit_in_victim_stack>", "state": "success", ...}`, signed with attacker-org's own secret. If that sha exists in `Commit` for a completely different, unrelated Stack (via shared git history from a fork, or a coincidental identical initial commit), `Commit#create_status_from_github!` runs for that victim commit [5](#0-4) , which can drive `Commit#deployable?` to true [6](#0-5) , and the `after_commit` hook / direct call chain leads to `schedule_continuous_delivery`, which enqueues `ContinuousDeliveryJob` if `stack.continuous_deployment? && stack.deployable?` [7](#0-6) .

None of the existing guards prevent this: `verify_signature` validates the signer's org, not the sha's owning repository; `drop_unhandled_event` only checks the event type is handled; the `ExplicitParameters` schema for `StatusHandler` only validates the shape of `sha`/`state`/etc, not repository ownership; there is no `stacks`/`Repository.from_github_repo_name` scoping in this handler at all.

### Impact Explanation
A payload signed by one organization's webhook secret can write a `Status` record for, and potentially trigger an unauthorized continuous deployment of, a Stack belonging to an entirely different organization/repository that never authenticated that request. This is a cross-tenant write and, when `continuous_deployment?` is enabled and other blocking statuses are absent, an unauthorized deploy — matching the Critical category ("a payload for one repository mutating another's stack, commit... or an unauthorized deploy"). The attack is repeatable against any Stack whose tracked commit shas the attacker can predict or share (most reliably via forked repositories sharing git history, which is common and requires no privileged access).

### Likelihood Explanation
Preconditions: the attacker must control (or own) a repository/org with a valid Shipit `webhook_secret` configured for *some* org (which they can arrange for their own tracked repo), and must know a sha that is both (a) reachable/attributable to their own org's signed payload, and (b) present as a `Commit` on a different Stack — most practically achieved by forking a victim's tracked repository (shared history commits retain identical shas) or exploiting template-generated repos with identical initial commits. This requires no Shipit session, API token, or secret belonging to the victim. Feasibility is high for the fork-sharing scenario since git commit shas are content-addressed and identical across forks for unmodified history; likelihood is therefore realistic and repeatable.

### Recommendation
Scope `StatusHandler#process` (and any other sha-keyed handler) through the repository named in the verified webhook payload, mirroring `CheckSuiteHandler`'s use of `Handler#stacks`, e.g.:
```ruby
def process
  stacks.flat_map(&:commits).select { |c| c.sha == params.sha }.each do |commit|
    commit.create_status_from_github!(params)
  end
end
```
or more efficiently `Commit.where(sha: params.sha, stack_id: stacks.select(:id))`, ensuring the sha lookup is always constrained to Stacks belonging to `Repository.from_github_repo_name(payload['repository']['full_name'])`.

### Proof of Concept
Minitest plan (`test/models/shipit/webhooks/handlers/status_handler_test.rb`, illustrative — actual file is out-of-scope per rules but describes required assertions):
1. Create `stack_a` under `repository_a` (org "org-a") and `stack_b` under `repository_b` (org "org-b").
2. Create `commit_b` on `stack_b` with a fixed `sha = "deadbeef..."` (simulating a commit shared via forked history), with `stack_b.continuous_deployment?` stubbed true and no blocking statuses.
3. Assert binding before: `commit_b.stack_id == stack_b.id` and no `Status` exists yet for `commit_b` with state `success`.
4. Build a `status` payload with `repository.full_name = repository_a.github_repo_name` (org-a) and `sha: commit_b.sha, state: "success"`.
5. Call `Shipit::Webhooks::Handlers::StatusHandler.call(payload)` (signature verification bypassed as in existing `webhooks_controller_test.rb` pattern using `GithubHook.any_instance.stubs(:verify_signature).returns(true)` or calling the handler directly, which is unit-scoped and doesn't require live GitHub).
6. Assert `commit_b.reload.statuses.last.state == "success"`, `commit_b.deployable?` is now `true`, and `ContinuousDeliveryJob` was enqueued for `stack_b` (`assert_enqueued_with(job: ContinuousDeliveryJob, args: [stack_b])`), even though the payload never named `repository_b` — proving the binding "sha belongs to the repository whose owner signed the webhook" does not hold and org-a's webhook mutated org-b's Stack.
