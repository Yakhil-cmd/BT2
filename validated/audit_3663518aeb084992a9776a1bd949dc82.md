This confirms the vulnerability. The base `Handler` class provides a `stacks` helper method that scopes to the repository from the webhook payload (`Repository.from_github_repo_name(repository_name)&.stacks`), and `PushHandler#process` correctly uses this scoped `stacks` relation. However, `StatusHandler#process` does not use `stacks` at all — it calls `Commit.where(sha: params.sha)` directly on the unscoped model class, bypassing the repository-scoping mechanism that every other handler in this codebase uses.

### Title
Unscoped `Commit.where(sha:)` lookup in StatusHandler allows a same-SHA collision across Stacks to create Status rows for unrelated repositories - (File: app/models/shipit/webhooks/handlers/status_handler.rb)

### Summary
`StatusHandler#process` looks up commits by `Commit.where(sha: params.sha)` across the entire `commits` table, unscoped by the webhook's own `repository.full_name`, unlike every other handler (e.g. `PushHandler`) which uses the `Handler#stacks` helper that scopes to `Repository.from_github_repo_name(repository_name)&.stacks`. `Commit#create_status_from_github!` is then invoked on every matching row regardless of which repository's Stack it belongs to.

### Finding Description
The broken binding: `payload.dig('repository','full_name') == stack.repository.full_name` for every `Commit` row mutated by a single verified webhook. `Handler#stacks` at [1](#0-0)  enforces exactly this binding by deriving the candidate `Stack` set from `payload.dig('repository', 'full_name')`. `PushHandler#process` uses this scoped relation, `.where(branch:).find_each`, at [2](#0-1) . `StatusHandler#process`, however, bypasses `stacks` entirely: `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github! params }` at [3](#0-2) . This is an exact (not `LIKE`-prefix) match against the `sha` column, which per the schema is a 40-char full SHA1 with a `["sha","stack_id"]` unique index (not a global unique index), meaning the same 40-char SHA can legitimately exist as separate rows across multiple unrelated Stacks — e.g. shared history from a common upstream/fork situation, or a repository being tracked by two different Stacks (same repo, different environments) is even more directly reachable without needing an actual cryptographic collision. `verify_signature` in `WebhooksController` only proves the payload came from the org owning `repository_owner`; it does not constrain which `Commit` rows the handler is permitted to touch [4](#0-3) . The `ExplicitParameters` schema for `StatusHandler` only validates `sha`/`state`/etc. types [5](#0-4) ; it does not restrict the lookup by repository. So a verified webhook for repository A, containing a SHA that also exists as a `Commit` row belonging to Stack B (tracking repository C), causes `create_status_from_github!` to run against Stack B's commit, writing a `Status` row with `stack_id` = B into `Status.replicate_from_github!` [6](#0-5) , and further triggers `enable_ci_on_stack`, `schedule_continuous_delivery`, hooks and `ProcessMergeRequestsJob` for that unrelated stack [7](#0-6) .

The realistic attacker path does not require breaking SHA1: an attacker who owns/pushes to repository A can trigger a legitimate `status` webhook (which GitHub sends automatically for CI on any commit pushed to A, no special permission needed) referencing a `sha` value. If any other Stack in the same multi-tenant Shipit instance happens to already have a `Commit` row with that identical 40-char sha (which can occur naturally, e.g., shared fork history, cherry-picked commits, or simply the same public repository tracked by two Stacks), that unrelated Stack's `Status` gets mutated by A's webhook. `check_if_ping`, `drop_unhandled_event`, `verify_signature` and the `ExplicitParameters` schema all pass normally in this flow — none of them check that resulting mutated `Commit`/`Stack` rows actually belong to the repository that signed the webhook.

### Impact Explanation
A single verified webhook for one repository can write `Status` rows (and cascade into `enable_ci_on_stack!`, `schedule_continuous_delivery`, hook emission, and `ProcessMergeRequestsJob` enqueueing) against `Commit`/`Stack` records belonging to a completely different, unrelated repository/tenant in the same Shipit instance. This matches "a payload for one repository mutating another's stack, commit, task or team" (Critical). The blast radius is every Stack in the database that has ever recorded a `Commit` with the colliding sha — repeatable on every `status` event received for that sha, and generalizable to any pair of Stacks that happen to share a commit sha (most plausibly two Stacks tracking the same or forked repository).

### Likelihood Explanation
Requires a standard multi-tenant Shipit deployment with multiple Stacks (explicitly documented as supported). No special exploitation is needed to fabricate an arbitrary cross-repo SHA1 collision; the far more practical trigger is two Stacks that track the same GitHub repository (common setup for multiple environments) or forks/shared-history repositories, where identical commit SHAs across Stacks arise naturally and are already exercised in this codebase (`Commit` has a per-stack, not global, unique index on `sha`). An attacker only needs push access to one such repository and to cause a `status` event (which GitHub emits automatically), no Shipit credentials required.

### Recommendation
Scope `StatusHandler#process` to the webhook's own repository, matching every other handler: replace `Commit.where(sha: params.sha)` with a lookup restricted to `stacks` (i.e., `Commit.where(sha: params.sha, stack_id: stacks.select(:id))` or `stacks.flat_map { |s| s.commits.where(sha: params.sha) }`), consistent with the `Handler#stacks` helper used by `PushHandler`.

### Proof of Concept
In `test/models/shipit/webhooks/handlers/status_handler_test.rb` (or the equivalent webhooks controller test):
1. Create `stack_a` for repo `org-a/repo-a` and `stack_b` for repo `org-b/repo-b` (unrelated orgs).
2. Create `Commit` fixtures with the identical `sha` value under both `stack_a` and `stack_b`.
3. POST a verified `status` webhook where `payload['repository']['full_name'] == 'org-a/repo-a'` and `payload['sha']` equals the shared sha.
4. Assert `assert_difference('Status.count', 2)` and then assert that `Status.where(stack_id: stack_b.id).exists?` is true even though the webhook's repository was `org-a/repo-a` — proving stack_b's data was mutated by a webhook that never authenticated for `org-b/repo-b`.
