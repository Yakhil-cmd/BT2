### Title
Unbounded `_extraData` in Bridge Request Functions Causes Relay Stall, Permanently Blocking Subsequent Cross-Chain Transfers — (`contracts/service_chain/bridge/BridgeTransferKLAY.sol`, `BridgeTransferERC20.sol`, `BridgeTransferERC721.sol`, `node/sc/bridge_manager.go`)

---

### Summary

The Kaia service-chain bridge accepts an unbounded `bytes _extraData` parameter in every public request function (`requestKLAYTransfer`, `requestERC20Transfer`, `requestERC721Transfer`). No size validation exists on either the source or destination side. Because the handle transaction on the destination chain encodes additional fixed-size parameters on top of `_extraData`, an attacker can craft a request whose calldata fits within the source chain's `MaxTxDataSize` (128 KB) but whose corresponding handle transaction exceeds it. The relay's `processingPendingRequestEvents` loop halts on the first failing nonce and re-queues it indefinitely, blocking every subsequent legitimate transfer.

---

### Finding Description

**Source-side request functions accept arbitrary `_extraData`:**

`requestKLAYTransfer` in `BridgeTransferKLAY.sol`: [1](#0-0) 

`requestERC20Transfer` in `BridgeTransferERC20.sol`: [2](#0-1) 

`requestERC721Transfer` in `BridgeTransferERC721.sol`: [3](#0-2) 

None of these functions validate `_extraData.length`. The value is emitted verbatim in the `RequestValueTransfer` event: [4](#0-3) 

**The relay reads the event and constructs a handle transaction with the same `_extraData`:**

`handleRequestValueTransferEvent` in `bridge_manager.go` passes `extraData` directly to `HandleKLAYTransfer` / `HandleERC20Transfer` / `HandleERC721Transfer`: [5](#0-4) 

**The handle functions also accept unbounded `_extraData` with no size check:** [6](#0-5) [7](#0-6) 

**Calldata size asymmetry:**

| Transaction | Fixed overhead (bytes) | User-controlled |
|---|---|---|
| `requestKLAYTransfer` | ~132 | `_extraData` (N bytes) |
| `handleKLAYTransfer` | ~260 | same `_extraData` (N bytes) |

The handle transaction carries 6 additional fixed ABI words (`_requestTxHash`, `_from`, `_to`, `_value`, `_requestedNonce`, `_requestedBlockNumber`) — 128 bytes more than the request transaction. Kaia's `MaxTxDataSize` is 128 KB for both chains: [8](#0-7) 

An attacker sets `_extraData` to `MaxTxDataSize − 132 − ε ≈ 130,940 bytes`. The request transaction fits (≤ 128 KB). The handle transaction is `260 + 130,940 ≈ 131,200 bytes > 128 KB` and is rejected by the destination txpool with `ErrOversizedData`.

**The relay stalls permanently on the failing nonce:**

`processingPendingRequestEvents` stops and re-queues all events from the failing nonce onward on every error: [9](#0-8) 

Because the oversized transaction is always rejected, the relay retries the same nonce every second (via the ticker) and never advances to subsequent nonces: [10](#0-9) 

The VT recovery mechanism (`vt_recovery.go`) also re-submits the same event and fails identically: [11](#0-10) 

**No existing guard:** The only `_extraData` size check in the repository is in the testing-only `ext_bridge.sol` contract, not in the production bridge: [12](#0-11) 

---

### Impact Explanation

All cross-chain value transfers submitted after the malicious request are permanently stalled at the relay layer. The corresponding KAIA/ERC-20/ERC-721 assets are locked inside the source-chain bridge contract with no automated path to release them. The `lowerHandleNonce` on the destination bridge never advances past the poisoned nonce, so the recovery system also loops indefinitely on the same stuck event. Operators must manually call handle functions out-of-band to unblock subsequent nonces, but the poisoned nonce itself can never be handled automatically.

---

### Likelihood Explanation

Any unprivileged user who can call `requestKLAYTransfer`, `requestERC20Transfer`, or `requestERC721Transfer` can trigger this. The exploit requires only a single transaction with a carefully sized `_extraData` payload (≈ 130,940 bytes). The cost is the gas for that one transaction plus the bridged value (which is returned to the attacker's `_to` address on the destination chain if the handle ever succeeds — but it never will). No special role or key is required.

---

### Recommendation

1. **Add a maximum `_extraData` size check in every request function.** A reasonable limit is 1 KB (matching typical application use-cases):

```solidity
// In BridgeTransferKLAY.sol, BridgeTransferERC20.sol, BridgeTransferERC721.sol
uint256 public constant MAX_EXTRA_DATA_LENGTH = 1024;

function requestKLAYTransfer(address _to, uint256 _value, bytes calldata _extraData) external payable {
    require(_extraData.length <= MAX_EXTRA_DATA_LENGTH, "extraData too large");
    uint256 feeLimit = msg.value.sub(_value);
    _requestKLAYTransfer(_to, feeLimit, _extraData);
}
```

2. **Apply the same guard in `_requestERC20Transfer` and `_requestERC721Transfer`** (internal functions called by both the direct and 1-step deposit paths).

3. **Add a defensive size check in the relay** (`handleRequestValueTransferEvent`) that skips and logs events whose `extraData` would produce an oversized handle transaction, rather than stalling the entire queue.

---

### Proof of Concept

1. Deploy a child-chain bridge and a parent-chain bridge with the standard Kaia service-chain setup.
2. Call `requestKLAYTransfer` on the child bridge with `_extraData` of length 130,940 bytes and any valid `_to` / `_value`. The transaction is accepted (calldata ≈ 131,072 bytes = 128 KB).
3. The relay picks up the `RequestValueTransfer` event and calls `bi.bridge.HandleKLAYTransfer(auth, ..., extraData)`.
4. The resulting handle transaction calldata is ≈ 131,200 bytes > 128 KB. The parent-chain txpool rejects it with `ErrOversizedData`.
5. `handleRequestValueTransferEvent` returns the error; `processingPendingRequestEvents` re-queues the event and returns.
6. Submit a second legitimate `requestKLAYTransfer` (nonce = 1). Observe that the relay never processes nonce 1 — it retries nonce 0 every second indefinitely.
7. The second user's KAIA is locked in the child bridge contract with no automated release path.

	ticker := time.NewTicker(time.Second)

	logger.Info("start bridge loop", "addr", bi.address.String(), "onChildChain", bi.onChildChain)

// processingPendingRequestEvents handles pending request value transfer events of the bridge.
func (bi *BridgeInfo) processingPendingRequestEvents() {
	ReadyEvent := bi.GetReadyRequestValueTransferEvents()
	if ReadyEvent == nil {
		return
	}

	logger.Trace("Get ready request value transfer event", "len(readyEvent)", len(ReadyEvent), "len(pendingEvent)", bi.pendingRequestEvent.Len())

	for idx, ev := range ReadyEvent {
		if ev.GetRequestNonce() < bi.lowerHandleNonce || bi.handledEvent.Exist(ev.GetRequestNonce()) {
			logger.Trace("handled requests can be ignored", "RequestNonce", ev.GetRequestNonce(), "lowerHandleNonce", bi.lowerHandleNonce)
			continue
		}

		if err := bi.handleRequestValueTransferEvent(ev); err != nil {
			bi.AddRequestValueTransferEvents(ReadyEvent[idx:])
			logger.Error("Failed handle request value transfer event", "err", err, "len(RePutEvent)", len(ReadyEvent[idx:]))
			return
		}
	}

// handleRequestValueTransferEvent handles the given request value transfer event.
func (bi *BridgeInfo) handleRequestValueTransferEvent(ev IRequestValueTransferEvent) error {
	var (
		tokenType                         = ev.GetTokenType()
		tokenAddr, from, to, contractAddr = ev.GetTokenAddress(), ev.GetFrom(), ev.GetTo(), ev.GetRaw().Address
		txHash                            = ev.GetRaw().TxHash
		valueOrTokenId                    = ev.GetValueOrTokenId()
		requestNonce, blkNumber           = ev.GetRequestNonce(), ev.GetRaw().BlockNumber
		extraData                         = ev.GetExtraData()
	)

	ctpartTokenAddr := bi.GetCounterPartToken(tokenAddr)
	// TODO-Kaia-Servicechain Add counterpart token address in requestValueTransferEvent
	if tokenType != KAIA && ctpartTokenAddr == (common.Address{}) {
		logger.Warn("Unregistered counter part token address.", "addr", ctpartTokenAddr.Hex())
		ctTokenAddr, err := bi.counterpartBridge.RegisteredTokens(nil, tokenAddr)
		if err != nil {
			return err
		}
		if ctTokenAddr == (common.Address{}) {
			return errors.New("can't get counterpart token from bridge")
		}
		if err := bi.RegisterToken(tokenAddr, ctTokenAddr); err != nil {
			return err
		}
		ctpartTokenAddr = ctTokenAddr
		logger.Info("Register counter part token address.", "addr", ctpartTokenAddr.Hex(), "cpAddr", ctTokenAddr.Hex())
	}

	bridgeAcc := bi.account

	bridgeAcc.Lock()
	defer bridgeAcc.UnLock()

	auth := bridgeAcc.GenerateTransactOpts()

	var handleTx *types.Transaction
	var err error

	switch tokenType {
	case KAIA:
		handleTx, err = bi.bridge.HandleKLAYTransfer(auth, txHash, from, to, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[KAIA], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC20:
		handleTx, err = bi.bridge.HandleERC20Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC20], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	case ERC721:
		uri := GetURI(ev)
		handleTx, err = bi.bridge.HandleERC721Transfer(auth, txHash, from, to, ctpartTokenAddr, valueOrTokenId, requestNonce, blkNumber, uri, extraData)
		if err != nil {
			return err
		}
		handleValueTransferLog(bi.onChildChain, handleVTmethods[ERC721], handleTx.Hash().String(), requestNonce, from, to, valueOrTokenId)
	default:
		logger.Error("Got Unknown Token Type ReceivedEvent", "bridge", contractAddr, "nonce", requestNonce, "from", from)
		return nil
	}

	bridgeAcc.IncNonce()

	bi.bridgeDB.WriteHandleTxHashFromRequestTxHash(txHash, handleTx.Hash())
	return nil
}

// recoverPendingEvents recovers all pending events by resending them.
func (vtr *valueTransferRecovery) recoverPendingEvents() error {
	defer func() {
		vtr.childEvents = []IRequestValueTransferEvent{}
		vtr.parentEvents = []IRequestValueTransferEvent{}
	}()

	if len(vtr.childEvents) > 0 {
		logger.Warn("VT Recovery : Child -> Parent Chain", "cBridge", vtr.cBridgeInfo.address.String(), "events", len(vtr.childEvents))
	}

	vtRequestEventMeter.Mark(int64(len(vtr.childEvents)))
	vtRecoveredRequestEventMeter.Mark(int64(len(vtr.childEvents)))

	events := make([]IRequestValueTransferEvent, len(vtr.childEvents))
	for i, event := range vtr.childEvents {
		events[i] = event
	}
	vtr.pBridgeInfo.AddRequestValueTransferEvents(events)

	if len(vtr.parentEvents) > 0 {
		logger.Warn("VT Recovery : Parent -> Child Chain", "pBridge", vtr.pBridgeInfo.address.String(), "events", len(vtr.parentEvents))
	}

	vtHandleEventMeter.Mark(int64(len(vtr.parentEvents)))
	events = make([]IRequestValueTransferEvent, len(vtr.parentEvents))
	for i, event := range vtr.parentEvents {
		events[i] = event
	}
	vtr.cBridgeInfo.AddRequestValueTransferEvents(events)

	return nil
}
