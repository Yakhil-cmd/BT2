### Title
Webhook signature verification org (`repository.owner.login`) is decoupled from the repository actually mutated (`repository.full_name`), letting a no-secret org's payload forge cross-repo `PullRequest` writes via `AssignedHandler` - (File: app/controllers/shipit/webhooks_controller.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects the `GitHubApp`/secret used to authenticate a webhook solely from `params.dig('repository','owner','login')`, while every `pull_request` handler (including `AssignedHandler`) resolves the actual target repository independently from `params.repository.full_name`. Because these two attacker-controlled fields are never cross-checked, a payload can be authenticated against an org with no configured `webhook_secret` while its `full_name` field targets a completely different, victim-owned repository, letting `AssignedHandler` mutate that victim's persisted `PullRequest` row.

### Finding Description
The broken invariant is: `org(repository.owner.login) == org(repository.full_name)` should always hold for the repository whose secret authenticated the request. This is never enforced.

- `verify_signature` picks the `GitHubApp` purely from `repository_owner`, itself `params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')`: [1](#0-0) [2](#0-1) 
- `GitHubApp#verify_webhook_signature` unconditionally passes when the selected org has no configured secret: `return true unless webhook_secret`: [3](#0-2) 
- After signature verification succeeds (using the no-secret org's identity), the handler is invoked with the *same raw JSON body*, and `AssignedHandler` resolves the repository it will mutate strictly from `params.repository.full_name`, ignoring `repository_owner` entirely: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker learns (via probing, since 422 vs 200 responses leak which org names are configured — `GithubOrganizationUnknown` returns 422 with a distinct log branch) that a multi-org Shipit deployment has one configured org, e.g. `no-secret-org`, whose `webhook_secret` is blank.
2. Attacker crafts a `pull_request` webhook body with `repository.owner.login = "no-secret-org"` and `repository.full_name = "victim-org/victim-repo"`, `action = "assigned"`, and a real `number` matching an existing PR on the victim stack.
3. `verify_signature` calls `Shipit.github(organization: "no-secret-org")`, whose `verify_webhook_signature` returns `true` regardless of the (even absent/garbage) `X-Hub-Signature` header.
4. `AssignedHandler#process` finds the victim's `PullRequest` by `number` + `stacks.repositories.id` matching `Repository.from_github_repo_name("victim-org/victim-repo")` and calls `pull_request.update(github_pull_request: params.pull_request)`, overwriting persisted PR attributes (title, state, additions/deletions, head sha/ref, assignees, labels) for a repository that never authenticated this request.

Existing guards do not stop this: `verify_signature` only checks that *some* configured org's secret matches (or is blank); it never asserts that org equals the owner of `repository.full_name`. The `ExplicitParameters` schema in `AssignedHandler` only validates types/presence, not owner consistency. `drop_unhandled_event` and `check_if_ping` are irrelevant to this path.

Note: the question's framing about a "shared commit SHA with attacker repo" causing a bare-SHA collision does not apply to `AssignedHandler` — it looks up the `PullRequest` purely by `number` scoped to the resolved repository's `id`, with no SHA-based lookup anywhere in this handler. That aspect of the premise is not supported by the code, but it does not affect the validity of the owner/full_name decoupling bypass.

### Impact Explanation
An attacker who has no relationship whatsoever to the victim org/repo can, with a single unauthenticated `POST /webhooks`, overwrite arbitrary fields of a real `Shipit::PullRequest` record belonging to the victim stack (title, state, additions/deletions, head SHA/ref, assignees, labels) as long as they know/guess the victim PR `number`. This is a cross-tenant state-mutation primitive: one repository's (or an unrelated no-secret org's) payload writes another repository's records, matching the "Critical — payload for one repository mutating another's stack/commit" impact category. The attack is fully repeatable against any PR number and any victim repository reachable via `full_name`, for every event type whose handler resolves its target via `full_name` rather than `repository_owner` (not limited to `AssignedHandler`).

### Likelihood Explanation
Preconditions: the Shipit deployment must run in multi-org GitHub App mode (`secrets.github` keyed by multiple orgs) with at least one configured org lacking a `webhook_secret`. This is a supported, code-sanctioned configuration (`@webhook_secret = @config[:webhook_secret].presence`, with an explicit bypass documented in `GitHubApp#verify_webhook_signature`). Attacker cost is a single crafted HTTP POST with no secrets, no session, and no GitHub credentials — only knowledge of a no-secret org name and a target PR number, both of which are guessable/enumerable via response-code differences (422 for unknown org vs 200/204 for accepted event). Feasibility and repeatability are high once the no-secret org is identified.

### Recommendation
Enforce that the org used to select the webhook secret is the same org that owns the resolved repository before any handler runs: derive the target repository (`Repository.from_github_repo_name(params.repository.full_name)`) in `verify_signature` itself, verify its `owner` matches `repository_owner`, and reject (422) on mismatch. Additionally, disallow/warn on any configured org with a blank `webhook_secret` in production, or require `webhook_secret` presence for all orgs in multi-org mode.

### Proof of Concept
```ruby
# test/controllers/webhooks_controller_test.rb
test "pull_request assigned from a no-secret org full_name-targets a victim repo's PullRequest" do
  # Setup: two orgs configured — "no-secret-org" (webhook_secret blank) and "shopify" (real secret, owns @stack's repository)
  victim_pr = shipit_pull_requests(:some_existing_pr_on_shopify_stack) # number N, stacks.repositories owner = shopify

  Shipit.stubs(:github).with(organization: 'no-secret-org').returns(
    Shipit::GitHubApp.new('no-secret-org', {}) # no webhook_secret => verify_webhook_signature always true
  )

  request.headers['X-Github-Event'] = 'pull_request'
  request.headers['X-Hub-Signature'] = 'sha1=garbage' # irrelevant, no secret configured

  body = {
    action: 'assigned',
    number: victim_pr.number,
    pull_request: {
      id: 1, number: victim_pr.number, url: 'x', title: 'ATTACKER-CONTROLLED TITLE',
      state: 'open', additions: 999, deletions: 999,
      head: { sha: 'deadbeef', ref: 'attacker-branch' },
      user: { login: 'attacker' }, assignees: [{ login: 'attacker' }], labels: []
    },
    repository: { owner: { login: 'no-secret-org' }, full_name: victim_pr.stack.repository.full_name },
    sender: { login: 'attacker' }
  }.to_json

  assert_changes -> { victim_pr.reload.title }, from: victim_pr.title, to: 'ATTACKER-CONTROLLED TITLE' do
    post :create, body: body, as: :json
  end
  assert_response :ok
end
```
Assert both sides of the equality before/after: before the request, `victim_pr.stack.repository.owner` (`"shopify"`) ≠ `"no-secret-org"` (the org that authenticated the request) — the mismatch persists after the request, and the write still succeeds, proving the invariant "a `pull_request` event only affects the repository whose secret authenticated it" is violated.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
