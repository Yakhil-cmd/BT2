### Title
Cross-repository Status webhook mutates victim Stack's `ignore_ci` flag via unscoped SHA lookup - (File: `app/models/shipit/webhooks/handlers/status_handler.rb`)

### Summary
`StatusHandler#process` resolves the Commit(s) to update purely by SHA, with no scoping to the repository/organization that the webhook's signature was verified against. Combined with `Status#after_create` unconditionally calling `commit.stack.enable_ci!`, an attacker controlling a repository whose GitHub App is registered on this Shipit instance can, given a SHA collision with a commit on any other stack, cause the `ignore_ci` flag to be mutated on a stack they do not control.

### Finding Description
The broken binding, stated explicitly: the request is authenticated as belonging to `repository.full_name` from the JSON payload (via `repository_owner` used in `verify_signature`), but the row mutated is `commit.stack` for **every** `Commit` in the database whose `sha` equals `params.sha`, i.e.:

`authenticated_repository == payload.repository.full_name` **≠** `mutated_stack == commit.stack` for all `commit in Commit.where(sha: params.sha)`

Code path:
- `WebhooksController#verify_signature` only checks that the payload is signed with the webhook secret configured for `repository_owner` (`params.dig('repository','owner','login')`), via `Shipit.github(organization: repository_owner).verify_webhook_signature` [1](#0-0) . This binds the request only to *an organization's* webhook secret, not to any specific stack/repository/commit.
- `StatusHandler#process` then does `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — no filter by repository, org, or stack at all [2](#0-1) .
- `Commit#create_status_from_github!` calls `statuses.replicate_from_github!(stack_id, github_status)`, using the pre-existing `Commit#stack_id`, not anything derived from the incoming payload [3](#0-2) .
- `Status#after_create :enable_ci_on_stack` unconditionally runs `commit.stack.enable_ci!` for every created `Status`, regardless of which repository the webhook actually came from [4](#0-3) .

Exploit flow (given the stated precondition that a Commit row in victim Stack B shares its `sha` with a commit the attacker controls in repository A): the attacker triggers (or has GitHub deliver, correctly signed with org A's real webhook secret) a `status` event for their own repository/commit. `verify_signature` passes because it is legitimately org A's secret. `StatusHandler#process` then matches not only the attacker's own commit row (if any exists for repo A) but also the unrelated Commit row belonging to Stack B, because the lookup is `Commit.where(sha:)` with no repository/org scoping. This fires `Status#after_create` on Stack B's commit, calling `commit.stack.enable_ci!` on Stack B — a stack the attacker has no relationship with.

Existing guards do not close this gap: `verify_signature` authenticates the org, not the individual stack/repository referenced by the SHA; the `StatusHandler` `ExplicitParameters` schema only validates the shape of `sha`/`state`/`branches`, not that the SHA belongs to a commit associated with the authenticated repository; there is no `repository.full_name` cross-check anywhere in this path.

### Impact Explanation
The write executed is a mutation of `Stack#ignore_ci` on a stack that never authenticated the request that changed it — this matches the rules' explicit Critical category "a payload for one repository mutating another's stack". `ignore_ci` gates `Commit#deployable?` (`stack.ignore_ci? || (success? && !blocked?)`) [5](#0-4) , so it is a safety-relevant flag controlling deploy gating. The attack is repeatable against any stack for which the attacker can arrange (per the stated precondition) a SHA that also exists in their own controlled/authenticated repository, and is not limited to a single victim — any tenant/org sharing the same Shipit instance is in the blast radius, independent of Shipit's per-organization webhook secrets, because the vulnerable lookup (`Commit.where(sha:)`) spans the whole database, not just the authenticated organization's stacks.

### Likelihood Explanation
The only precondition beyond attacker capabilities already granted by the rules is a SHA collision between a commit the attacker's repository legitimately reports status for, and a commit already tracked in a victim stack — this is stated as a given precondition in the question and is not something achievable in practice by an attacker without an actual SHA-1 collision or a shared/forked commit history (e.g., forked repos sharing early history, or a victim's Shipit tracking multiple repos with overlapping commits). No Shipit secrets, sessions, or privileged roles are needed beyond normal use of a repository the attacker owns that is already onboarded to the same Shipit instance (or any org whose GitHub App is configured). Given that precondition, exploitation costs the attacker nothing beyond a single legitimate `status` webhook delivery for their own repository/commit.

### Recommendation
Scope `StatusHandler#process` (and the analogous check-run/other SHA-keyed handlers) to commits belonging to stacks associated with the payload's `repository.full_name`/`repository.owner.login`, e.g. `Commit.joins(:stack).where(sha: params.sha, shipit_stacks: { repo_owner: ..., repo_name: ... })`, instead of an unscoped `Commit.where(sha:)`. Additionally, `Status#enable_ci_on_stack` should not be reachable through a webhook whose repository does not match `commit.stack`'s configured GitHub repository.

### Proof of Concept
Minitest plan (model/controller level, no live GitHub):
1. Fixture setup: `stack_a` (attacker-authenticated org) with `hooks`/webhook secret for org A; `stack_b` (victim) with `ignore_ci: true`, belonging to org B, containing `commit_b` with `sha: "deadbeef...”`.
2. Also create `commit_a` under `stack_a` with the same `sha: "deadbeef..."` (simulating the stated SHA-collision precondition).
3. POST to `/webhooks` with `X-Github-Event: status`, a payload whose `repository.full_name`/`owner.login` is org A's repo, signed with org A's real webhook secret, and `sha: "deadbeef..."`, `state: "success"`.
4. Assertions:
   - Before: `assert_equal true, stack_b.ignore_ci`
   - After posting: `stack_b.reload; assert_equal false, stack_b.ignore_ci` (demonstrating the victim stack, never referenced by the authenticated payload's `repository.full_name`, had its flag mutated).
   - Additionally assert `stack_b.updated_at` changed and a `Status` row was created with `stack_id: stack_b.id`, proving the write landed on the wrong stack.
