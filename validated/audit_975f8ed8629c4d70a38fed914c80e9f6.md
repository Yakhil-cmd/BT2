### Title
Unbounded multiplication in asset denomination cap validation causes floating-point precision loss / integer overflow, allowing declared asset cap to diverge from real issuable supply - (File: validation.js)

### Summary
`validateAssetDefinition()` computes the declared total capped supply of a divisible/fixed-denomination asset by summing `count_coins * denomination` for each attacker-supplied denomination entry, using ordinary JavaScript floating-point arithmetic with no bound placed on `count_coins` and, for units whose `last_ball_mci` predates `pemCurvesFixMci`, no bound placed on `denomination` either. This mirrors the CVE-2016-9084 bug class: a size/quantity value is derived from an unchecked multiplication of two attacker-influenced integers, allowing the product to silently overflow the safe range and produce an incorrect result that is nevertheless accepted as valid.

### Finding Description
In `validateAssetDefinition`, each `denominations[i]` entry is checked only with `isPositiveInteger()`: [1](#0-0) 

`denomInfo.denomination` is bounded to `constants.MAX_CAP` only conditionally — the check is skipped for units whose `last_ball_mci` is below `constants.pemCurvesFixMci` (i.e., for units that were valid under older protocol rules and are still being validated/re-validated, such as during catch-up or unstable-unit revalidation): [2](#0-1) 

`denomInfo.count_coins`, however, has **no upper bound at all** — it is only required to be `isPositiveInteger`, unlike `payload.cap`, which is explicitly capped: `isPositiveInteger(payload.cap) && payload.cap <= constants.MAX_CAP` (line 2735). This asymmetry means `count_coins` can be an arbitrarily large integer as returned by the JSON parser.

The accumulation `total_cap_from_denominations += denomInfo.count_coins * denomInfo.denomination;` is then compared against `payload.cap` for equality: [3](#0-2) 

Because JavaScript numbers are IEEE-754 doubles, once the product or the running sum exceeds `Number.MAX_SAFE_INTEGER` (2^53−1), further additions/multiplications lose precision. An attacker can craft `count_coins`/`denomination` pairs across multiple denomination entries such that the (imprecise) floating-point sum happens to equal an attacker-chosen `payload.cap`, even though the mathematically true, correctly-summed total supply representable by the denomination table is materially different (larger) than `payload.cap`. This is the direct functional analog of the CVE's misused `kzalloc(n * size)`: an allocation/quantity limit is derived from a multiplication whose overflow is never checked, so the enforced bound (`cap`) can be defeated by choosing operands that overflow to the "correct" checked value while the real quantity is different.

The `asset_denominations` table (and later issuance logic in `indivisible_asset.js`, e.g. `issue_amount = count_coins_to_issue * denomination`) trusts this validated cap/denomination relationship when issuing coins for the asset, so a mismatch introduced here propagates into real issuance accounting.

### Impact Explanation
An asset issuer (any unprivileged user who posts an `asset` definition message) can define an asset whose advertised `cap` does not match the real total quantity encoded by its `denominations` table, because the validating check silently passes due to floating-point precision loss in the size computation. This can lead to the network accepting an asset definition where the true issuable supply differs from the declared cap — a form of supply inflation/accounting inconsistency for a capped, fixed-denomination asset, which affects wallets, exchanges, and other AAs that rely on `cap` to reason about total token supply. This matches the "asset issuance and transfer conditions" / "supply inflation" categories explicitly in scope.

### Likelihood Explanation
The path is reachable by any user simply posting an `asset` definition unit with a crafted `denominations` array — no special privileges, network position, or malicious peer/node behavior are required. The check bypass for old-protocol units (`last_ball_mci < pemCurvesFixMci`) is also reachable during full-history validation/catch-up of historical-style units. Constructing operands whose floating point product/sum collides with a chosen cap requires some numeric engineering but is a well-known technique against unguarded floating-point size checks.

### Recommendation
- Bound `count_coins` explicitly (e.g., `count_coins <= constants.MAX_CAP`) in addition to `isPositiveInteger`.
- Perform the `count_coins * denomination` multiplication and the running sum using a safe-integer library (e.g. BigInt or an explicit overflow check comparing against `Number.MAX_SAFE_INTEGER`) rather than native floating-point arithmetic, rejecting the unit if any intermediate product or running total is not exactly representable.
- Remove or re-audit the `pemCurvesFixMci` exemption that allows `denomination` to exceed `MAX_CAP` for older units, or explicitly re-validate historical asset definitions against the corrected bound.

### Proof of Concept
Conceptual (not executed against a live node): post an `asset` definition unit with `fixed_denominations: true`, `cap: <chosen_value>` and a `denominations` array containing entries such as `{denomination: d1, count_coins: c1}, {denomination: d2, count_coins: c2}, ...` where each `di * ci` and their accumulated floating-point sum in `total_cap_from_denominations` numerically round to `<chosen_value>` in double-precision arithmetic, while the exact integer sum (computed with BigInt) is different (larger). Because `validation.js` line 2778/2790 compares using native `+`/`*` and `!==`, the crafted definition passes `validateAssetDefinition`, letting the asset be created with a cap that does not correspond to its real denomination table.
