### Title
Stale, block-shared `index-cache` lets a liquidator's bad-debt write-down be skipped/overridden by concurrent user transactions, letting other users under- or over-pay debt at a stale exchange rate - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The market contract caches vault liquidity/debt indexes in a map keyed only by `{timestamp: stacks-block-time, aid}` and shared by **every caller in the block**, not per-transaction. `accrue-and-cache` [1](#0-0)  treats a cache hit as authoritative and skips re-querying the vault. `socialize-debt-asset`, run during liquidation of an insolvent borrower, calls `vault-socialize-debt` (which writes down `lindex`/reduces `total-borrowed` in the vault - `socialize-debt` in `v0-vault-*.clar`) and then explicitly refreshes only that one cache entry with the post-write-down value [2](#0-1) .

### Finding Description
`index-cache` is a block-scoped, cross-user cache: `(map-get? index-cache { timestamp: stacks-block-time, aid })`. The very first caller for a given asset within a block primes it via `accrue-and-cache`, and every later caller in the same block, regardless of identity, gets a cache HIT and reuses that value verbatim instead of re-deriving it from the vault's live state [1](#0-0) .

Any borrower/repayer/health-check path in the block (`borrow`, `repay`, `get-notional-evaluation`, `scale-debt-for-liquidation`, etc.) that touches the same asset id reads whichever `index`/`lindex` happens to be sitting in that shared slot at the moment of their call [3](#0-2) [4](#0-3) . Liquidation's socialization step mutates that shared value mid-block when a borrower is wiped out: `vault-socialize-debt` write-down decreases the vault's `lindex` (see `socialize-debt` in `v0-vault-sbtc.clar` etc., which computes `new-lindex` proportional to the loss on `total-assets`) and the market then force-overwrites the same-timestamp cache entry with the new post-loss index [5](#0-4) [2](#0-1) .

Ordering inside the block therefore determines which of two unrelated, unprivileged users sees the pre- or post-writedown value for the same asset:
- Attacker (or any unrelated user), Borrower-X, primes the cache earlier in the block via `borrow`/`repay`/`collateral-add`, caching the *pre-loss* index/lindex for asset A.
- Later in the same block, a liquidator liquidates an unrelated insolvent Borrower-Y, triggering `socialize-debt-asset`, which shrinks `lindex` for asset A vault-side and rewrites the cache entry to the *post-loss* value.
- A third, unrelated User-Z who calls `repay`/`borrow`/is health-checked for asset A afterward in the same block reads the mutated cache slot that Borrower-X and the liquidator jointly (and unknowingly) produced, not a value that reflects Borrower-Z's own transaction-local state.

Because the "correct" pointer is the vault's live storage (queried by `vault-accrue`) and the cache is supposed to be a same-block memoization of that value, any path that reaches the cache HIT branch skips revalidating against the vault entirely — the cache becomes the single source of truth for the rest of the block once primed, and any of `borrow` [6](#0-5) , `repay` [7](#0-6) , or the liquidation's own health/collateral math can be the one that first sets it. Nothing ties the cached value to the transaction that reads it — it is genuinely a shared index primed by one caller and consumed by another, unprivileged caller, matching the reported bug class of an implicitly-trusted shared identifier/index that isn't revalidated per-consumer.

### Impact Explanation
Because the same-block cache is consumed for both debt-index conversions (`convert-to-scaled-debt`, `scale-debt-for-liquidation`) and collateral/zToken price resolution (`resolve-ztoken` via `get-cached-indexes`), a user whose `repay`/`borrow`/liquidation happens to land after an unrelated bad-debt socialization in the same block computes their scaled-debt conversion and/or zToken valuation from a manipulated/mutated shared slot rather than from a freshly-derived, transaction-consistent value. Depending on ordering this can make one honest, unprivileged user's debt conversion or collateral valuation diverge from their own transaction's true vault state, causing them to repay a different amount of actual debt than intended or have their zToken collateral mis-valued during health checks/liquidation — a temporary freezing/mis-accounting of funds for an unrelated party caused purely by transaction ordering within a block, not by their own action.

### Likelihood Explanation
This requires no privileged access and no oracle compromise — only (a) an insolvent position eligible for bad-debt socialization existing in the same block as (b) another unrelated borrow/repay/liquidation touching the same asset id, an ordering that a searcher/liquidator can trivially engineer by choosing when to submit the liquidation transaction relative to pending mempool transactions for that asset, since Clarity/Stacks blocks bundle multiple transactions and `stacks-block-time` is identical for all of them.

### Recommendation
Scope `index-cache` to be transaction-local (e.g., re-derive per top-level call, or include a transaction/nonce discriminator in the cache key) rather than block-shared, or force every consumer to re-validate the cached index against the vault's authoritative state before trusting it for debt/collateral math, mirroring the fix pattern in the referenced report: never let one caller's incidental cache write become implicit, unverified input to a different caller's financial calculation.

### Proof of Concept
1. Block N contains three transactions in this order: TX1 `borrow()` by User-X on asset A (primes `index-cache {timestamp: T, aid: A}` with pre-loss index via `accrue-and-cache`) [6](#0-5) ; TX2 `liquidate()` on insolvent Borrower-Y whose collateral is fully exhausted, triggering `socialize-debt-asset` for asset A, which calls `vault-socialize-debt` (shrinking `lindex`) and overwrites `index-cache {timestamp: T, aid: A}` [8](#0-7) [5](#0-4) ; TX3 `repay()` by unrelated User-Z on asset A reads `get-cached-indexes` and gets the cache HIT with TX2's post-write-down value [3](#0-2) [9](#0-8) .
2. Compare User-Z's `amount-to-repay`/scaled-debt conversion in TX3 against what it would be had TX2 not executed in the same block — the values differ purely due to ordering, demonstrating that User-Z's outcome is determined by an unrelated party's (User-X and the liquidator's) actions on the shared cache rather than by User-Z's own transaction.

**Note on confidence:** I was not able to fully trace how `get-account-scaled-debt`/`get-position` combine with this cache read in every downstream code path (e.g., whether `write-feeds`/oracle staleness checks independently bound the magnitude of the discrepancy), so the precise USD magnitude of the divergence per block is not quantified here; a Devin session with full repo access would be needed to build a concrete numeric PoC and confirm whether existing tests already cover/guard this block-shared cache behavior.

        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))

        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))

        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
