## Title
Stale `is_spent=1` flag on outputs whose spending unit is later propagated to `final-bad` causes permanent balance/fund freezing ("zombie-spent" outputs) - (File: main_chain.js)

### Summary
`CVE-2022-23033` is a Xen ARM bug where removing/invalidating a p2m mapping did not actually clear the underlying entry when a specific bit was not set, leaving a supposedly-revoked resource still accessible. The structural analog in `ocore--025` is the inverse-but-equivalent failure mode: when a unit that spent a stable output is later invalidated (`sequence` set to `'final-bad'`), the code clears the *uniqueness* state of its `inputs` row but never clears the `is_spent` flag on the `outputs` row it consumed. The "removal" (invalidation) of the spending unit is incomplete — one piece of derived state (`outputs.is_spent`) is left stale, exactly as the p2m entry was left stale in the CVE.

### Finding Description
When main-chain stabilization discovers that a unit is non-serial, `handleNonserialUnits()` in `main_chain.js` marks it `sequence='final-bad'` and nulls its own `inputs.is_unique` so future validators treat it "as a non-existent competitor": [1](#0-0) 

Any *descendant* units that spent outputs created by units which just became final-bad are propagated the same way by `propagateFinalBad()`: [2](#0-1) 

Note that in both places only `units.sequence` and `inputs.is_unique` are updated. Nowhere in this path is `outputs.is_spent` reset back to `0` for the `src_unit/src_message_index/src_output_index` that the now-invalidated unit's `transfer` input pointed to.

The *only* code path that actually clears `outputs.is_spent` for a final-bad unit's inputs is the archival/pruning path, `generateQueriesToUnspendTransferOutputsSpentInArchivedUnit`, which runs solely when a final-bad joint is later voided or removed (pruned) via `archiving.generateQueriesToVoidJoint` / `generateQueriesToRemoveJoint`: [3](#0-2) [4](#0-3) 

Pruning/voiding of a final-bad unit only happens once it is "uncovered" (`is_free=1`, no dependents) and enough time/witnessing has elapsed, via `purgeUncoveredNonserialJoints`: [5](#0-4) 

If the final-bad unit still has any DAG children (which is normal — DAG parenthood is independent of unit validity), it is never "free," so `purgeUncoveredNonserialJoints` never selects it, and `outputs.is_spent` for the legitimately stable output it "spent" remains `1` indefinitely — even though the unit that spent it is invalid and no other `good`, stable unit claims that output.

This exact defect is independently documented and reproduced by the repository's own diagnostic script, which compares two balance-computation strategies and explicitly explains the root cause: [6](#0-5) 
The script demonstrates that the "old" balance query (`is_spent=0 AND is_stable=1 AND sequence='good'`) undercounts an address's true spendable balance because of exactly this stale flag, calling the affected outputs "zombie-spent outputs": [7](#0-6) [8](#0-7) 

Any production code path that selects spendable coins using `is_spent=0` is affected by this same stale-flag class of bug, including AA output selection: [9](#0-8) 
and general wallet/light-client "outputs" queries throughout `balances.js` (9 matches for `is_spent=0` confirmed via search).

### Impact Explanation
An attacker (or even an honest but adversarial-timing participant, since this requires no special privileges) can post a unit `U2` that spends a stable output `O` owned by a victim address/AA. If `U2` later becomes non-serial and is marked `final-bad` during stabilization (e.g., because another conflicting unit `U1` spending the same input won the double-spend race and was already `good`), `O.is_spent` remains `1` forever unless `U2` happens to become fully orphaned and gets pruned. Since `U2` can easily have descendants (any downstream unit posted before finality that references it in its DAG), it commonly never becomes `is_free=1`, and the stale flag persists.

Consequences:
- The rightful owner's wallet/light client (and any AA reading its own balance via `is_spent=0`) will under-report and refuse to spend a genuinely available, stable, `good` output — a concrete, network-wide **AA fund freezing** / wallet fund-freezing condition matching the "Validate" criteria.
- For AAs specifically, `readStableOutputs()` in `aa_composer.js` uses `is_spent=0` to select the AA's own spendable outputs for building responses; a zombie-spent output permanently reduces the AA's usable balance even though the funds are still, in ledger truth, unspent and owned by the AA.
- Because different nodes could, in principle, race differently on which path (archiving vs. not) their local final-bad unit takes, this can also contribute to inconsistent local balance/coin-selection state across nodes, though the underlying consensus data (units/sequence) itself stays consistent — the divergence is in locally cached derived state (`outputs.is_spent`), which is exactly analogous to the Xen bug's "stale but locally-authoritative" TLB/mapping entry.

This satisfies the required "AA fund loss or freezing" impact bucket at High severity, since it is remotely triggerable by any unprivileged unit poster who can cause a competing spend to be built and later invalidated.

### Likelihood Explanation
Double-spends that are ultimately resolved by DAG-order (`good` vs `final-bad`) are a normal, expected, frequent occurrence in ocore's conflict-resolution protocol, not requiring any privileged position — any address holder (or an attacker targeting a victim's output) can post a competing spend. The precondition for the stale flag persisting (the losing spend having any child in the DAG, or not yet being deep/old enough for `purgeUncoveredNonserialJoints`'s witness/time thresholds) is easily met and, per the repo's own diagnostic tooling, has been observed to happen in practice ("zombie-spent outputs").

### Recommendation
When a unit's `sequence` is transitioned to `'final-bad'` in `handleNonserialUnits()` / `propagateFinalBad()` in `main_chain.js`, additionally reset `outputs.is_spent=0` for every `transfer` input of that unit whose corresponding `src_output` has no other `good` (or `good`-eligible) spender — mirroring the logic already implemented in `archiving.generateQueriesToUnspendTransferOutputsSpentInArchivedUnit` — rather than deferring this correction to the (conditional, often-delayed-or-never) archival/pruning step. Equivalently, replace all coin-selection/balance queries that trust `outputs.is_spent` as ground truth (in `balances.js`, `aa_composer.js`'s `readStableOutputs`/`readUnstableOutputsSentByAAs`, `inputs.js`, `indivisible_asset.js`) with the `NOT EXISTS`-based "new way" query demonstrated in `tools/compare_vote_balances.js`, which derives spentness live from `inputs`/`units.sequence` instead of relying on a mutable cached flag that can go stale.

### Proof of Concept
1. Address `A` owns stable, `good` output `O` (amount `X`).
2. Post unit `U1` spending `O`, get it included and stabilized as `good` (mainstream chain).
3. Simultaneously/race, have another party post unit `U2` also spending `O` (double-spend) from a different (or same) address, timed so that `U2`'s parent selection makes it lose the conflict resolution; ensure `U2` gains at least one child unit `U3` in the DAG before its branch is resolved as non-serial (e.g., a light client relays it and something references it), so `U2` never satisfies `is_free=1`.
4. When main-chain stabilization runs, `U2` becomes `sequence='final-bad'` via `handleNonserialUnits`/`propagateFinalBad` (`main_chain.js:1334-1418`); its `inputs.is_unique` is nulled, but `outputs.is_spent` for `O` — which was flipped to `1` when `U2` was first written by `writer.js` (`UPDATE outputs SET is_spent=1 WHERE unit=? ...`) — is never reset.
5. Run `node tools/compare_vote_balances.js` (or query `balances.js`'s standard balance query) for address `A`: the "old"/production-style `is_spent=0`-based balance is short by `X`, while the `NOT EXISTS`-based balance correctly shows `O` as spendable — confirming `O` is a permanently "zombie-spent" output that `A` (or an AA at that address) can never again select for spending through normal coin-selection code paths.

function generateQueriesToUnspendTransferOutputsSpentInArchivedUnit(conn, unit, arrQueries, cb){
	conn.query(
		"SELECT src_unit, src_message_index, src_output_index \n\
		FROM inputs \n\
		WHERE inputs.unit=? \n\
			AND inputs.type='transfer' \n\
			AND NOT EXISTS ( \n\
				SELECT 1 FROM inputs AS alt_inputs \n\
				WHERE inputs.src_unit=alt_inputs.src_unit \n\
					AND inputs.src_message_index=alt_inputs.src_message_index \n\
					AND inputs.src_output_index=alt_inputs.src_output_index \n\
					AND alt_inputs.type='transfer' \n\
					AND inputs.unit!=alt_inputs.unit \n\
			)",
		[unit],
		function(rows){
			rows.forEach(function(row){
				conn.addQuery(
					arrQueries, 
					"UPDATE outputs SET is_spent=0 WHERE unit=? AND message_index=? AND output_index=?", 
					[row.src_unit, row.src_message_index, row.src_output_index]
				);
			});
			cb();
		}
	);
}

function purgeUncoveredNonserialJoints(bByExistenceOfChildren, onDone){
	var cond = bByExistenceOfChildren ? "(SELECT 1 FROM parenthoods WHERE parent_unit=unit LIMIT 1) IS NULL" : "is_free=1";
	var order_column = (conf.storage === 'mysql') ? 'creation_date' : 'rowid'; // this column must be indexed!
	var byIndex = (bByExistenceOfChildren && conf.storage === 'sqlite') ? 'INDEXED BY bySequence' : '';
	// the purged units can arrive again, no problem
	db.query( // purge the bad ball if we've already received at least 7 witnesses after receiving the bad ball
		"SELECT unit FROM units "+byIndex+" \n\
		WHERE "+cond+" AND sequence IN('final-bad','temp-bad') AND content_hash IS NULL \n\
			AND NOT EXISTS (SELECT * FROM dependencies WHERE depends_on_unit=units.unit) \n\
			AND NOT EXISTS (SELECT * FROM balls WHERE balls.unit=units.unit) \n\
			AND (units.creation_date < "+db.addTime('-10 SECOND')+" OR EXISTS ( \n\
				SELECT DISTINCT address FROM units AS wunits CROSS JOIN unit_authors USING(unit) CROSS JOIN my_witnesses USING(address) \n\
				WHERE wunits."+order_column+" > units."+order_column+" \n\
				LIMIT 0,1 \n\
			)) \n\
			/* AND NOT EXISTS (SELECT * FROM unhandled_joints) */ \n\
		ORDER BY units."+order_column+" DESC", 
		// some unhandled joints may depend on the unit to be archived but it is not in dependencies because it was known when its child was received
	//	[constants.MAJORITY_OF_WITNESSES - 1],
		function(rows){
			if (rows.length === 0)
				return onDone();
			mutex.lock(["write"], function(unlock) {
				db.takeConnectionFromPool(function (conn) {
					async.eachSeries(
						rows,
						function (row, cb) {
							breadcrumbs.add("--------------- archiving uncovered unit " + row.unit);
							storage.readJoint(conn, row.unit, {
								ifNotFound: function () {
									throw Error("nonserial unit not found?");
								},
								ifFound: function (objJoint) {
									var arrQueries = [];
									conn.addQuery(arrQueries, "BEGIN");
									archiving.generateQueriesToArchiveJoint(conn, objJoint, 'uncovered', arrQueries, function(){
										conn.addQuery(arrQueries, "COMMIT");
										// sql goes first, deletion from kv is the last step
										async.series(arrQueries, function(){
											kvstore.del('j\n'+row.unit, function(){
												breadcrumbs.add("------- done archiving "+row.unit);
												var parent_units = storage.assocUnstableUnits[row.unit].parent_units;
												storage.forgetUnit(row.unit);
												storage.fixIsFreeAfterForgettingUnit(parent_units);
												cb();
											});
										});
									});
								}
							});
						},
						function () {
							conn.query(
								"UPDATE units SET is_free=1 WHERE is_free=0 AND is_stable=0 \n\
								AND (SELECT 1 FROM parenthoods WHERE parent_unit=unit LIMIT 1) IS NULL",
								function () {
									conn.release();
									unlock();
									if (rows.length > 0)
										return purgeUncoveredNonserialJoints(false, onDone); // to clean chains of bad units
									onDone();
								}
							);
						}
					);
				});
			});
		}
	);
