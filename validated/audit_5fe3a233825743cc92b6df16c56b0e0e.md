### Title
Opaque swap routes can attach unauthorized wallet-token transfers to the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` accept an opaque route payload and authenticate the account owner before passing that payload to the configured swap router. The controller constrains only the router’s authority to move the controller’s exact input amount and then checks controller-token balance deltas; it does not bound authorization effects caused by contracts reachable through the route. A malicious route can therefore invoke an attacker contract that calls `token.transfer(victim, attacker, amount)`. During simulation that transfer is recorded as a child of the victim’s strategy authorization, and if the victim signs the returned tree, the malicious hop spends unrelated wallet tokens while still producing valid swap output for the lending transaction.

### Finding Description
The strategy entrypoint accepts `swap: Bytes` without exposing the route’s invoked contracts to the controller, then calls `process_swap_collateral` with that payload. [1](#0-0) 

`swap_tokens` snapshots only the controller’s input and output balances, authorizes exactly one token transfer from the controller to the configured router, and invokes `router.execute_strategy(controller, amount_in, swap)` inside the flash guard. [2](#0-1) 

After execution, the checks reject only router overspending of the controller’s input and zero output receipt; they do not inspect the authorization tree or prevent route-selected code from requesting the caller’s authorization for unrelated operations. [3](#0-2) 

The codebase’s authorization test demonstrates the missing boundary: a route-selected pool can call `token.transfer(victim, attacker, WALLET_BALANCE)`, Soroban simulation records that transfer as a child invocation under the caller’s `swap_collateral` authorization, and signing the poisoned tree empties the victim’s unrelated wallet-token balance. [4](#0-3) 

The enforcing-auth regression confirms the two relevant cases: the same rogue transfer fails when absent from the signed tree, but succeeds when the simulated poisoned tree is signed. [5](#0-4) 

This is analogous to the reported unresolved-AST-node bypass: the security boundary validates the expected operation shape, while an indirectly reachable operation escapes the intended constraint. Here, the controller validates its own router transfer and measured balances, while arbitrary route-reachable code can introduce another caller-authorized operation outside those checks.

### Impact Explanation
A malicious route can steal arbitrary tokens from the user’s wallet, including assets that are not listed by the lending protocol and were not supplied as collateral. The strategy can still return the expected output token and pass the controller’s balance-delta and post-transaction risk checks, so the theft is not bounded by `amount_in`, protocol collateral, or the swap output. [3](#0-2) 

The demonstrated loss is direct theft of user funds: the test moves `WALLET_BALANCE` of an unlisted token from Alice to the attacker while crediting Alice with the expected swap output. [6](#0-5) 

### Likelihood Explanation
Exploitation requires the victim to submit or sign a malicious route whose simulation records the unauthorized child transfer. That is a deliberate user action, but it is within the normal opaque-route workflow: users sign the authorization tree produced by transaction simulation, and the route bytes do not by themselves reveal every nested authorization requirement. [4](#0-3) 

The controller’s own threat model states that route venues are not allowlisted and that a rogue child transfer executes when the caller signs the tree; it places the mitigation on clients decoding and refusing any unexpected child authorization. [7](#0-6) 

The issue is therefore not an unauthenticated theft path. It is a high-impact authorization-boundary bypass reachable by a malicious route supplied through an otherwise normal strategy call.

### Recommendation
Do not allow opaque, route-selected external code to execute under the same caller-authorization root as a lending strategy. Architecturally separate route execution from account authorization, or introduce an explicit authorization boundary that cannot request unrelated `caller.require_auth()` operations during router execution.

If that separation is not possible on Soroban, treat arbitrary route venues as unsafe for signed user entrypoints and restrict strategy routing to protocol-reviewed venues whose implementations cannot invoke caller-authorized token transfers. At minimum, make the contract and integration API fail closed for routes that produce any authorization children other than the exact expected input movement, and retain the existing regression proving that a poisoned tree cannot be mistaken for a normal route.

### Proof of Concept
1. Configure a router whose `execute_strategy` decodes an attacker-controlled `hop_pool` address from `swap_xdr`, invokes `hop_pool.swap()`, and returns a fair `token_out` amount. The harness’s `UnlistedPoolRouter` implements this behavior and performs the expected input/output transfers. [8](#0-7) 

2. Deploy a malicious hop contract whose `swap()` function calls `token.transfer(victim, attacker, amount)` for a token unrelated to the lending market. [9](#0-8) 

3. Call `Controller::swap_collateral` with:
   - `caller = victim`
   - `account_id = victim account`
   - `current = listed input HubAssetKey`
   - `amount = 50_000_000_000`
   - `new = listed output HubAssetKey`
   - `swap = encoded route naming the malicious hop`

   The controller authorizes only its own exact input transfer to the router and invokes the opaque route. [2](#0-1) 

4. Simulate the transaction. The recorded authorization tree contains the expected root `swap_collateral` call and an unexpected child `wallet_token.transfer(victim, attacker, WALLET_BALANCE)`. [4](#0-3) 

5. Have the victim sign the simulated tree. The lending swap succeeds and the victim receives the expected output, while `WALLET_BALANCE` moves to the attacker. Submitting an honest root-only tree instead causes the rogue transfer to fail authorization and rolls back the operation. [5](#0-4)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
