### Title
Nested `CREATE`/`CREATE2` from a delegated-EOA's code unconditionally re-increments the calling EOA's `frame_system` nonce, double-counting nonce consumption within a single `eth_transact` - ([File: substrate/frame/revive/src/exec.rs])

### Summary
`pallet-revive`'s EIP-7702 implementation lets any user delegate their EOA to a contract; the delegate's code then executes using the EOA's own address, storage and balance [1](#0-0) . The `push_frame`/`do_transaction` logic in `exec.rs` increments the *caller's* `frame_system` nonce for every nested `Constructor` frame (`CREATE`/`CREATE2`) regardless of the `ExecConfig::bump_nonce` flag that is specifically meant to prevent a double increment for Ethereum-originated transactions:

```rust
// Contracts nonce starts at 1
<System<T>>::inc_account_nonce(account_id);

if bump_nonce || !is_first_frame {
    // Needs to be incremented before calling into the code so that it is visible
    // in case of recursion.
    <System<T>>::inc_account_nonce(caller.account_id()?);
}
``` [2](#0-1) 

`ExecConfig::bump_nonce` is documented as being set to `false` for Ethereum-wallet transactions precisely because "the origin's nonce is already incremented pre-dispatch by the `CheckNonce` transaction extension," but the doc explicitly carves out an exception: "This does not apply to contract initiated instantiations. Those will always bump the instantiating contract's nonce." [3](#0-2)  The `!is_first_frame` branch of the condition means any nested `CREATE` executed while the top-level call frame is already open (i.e., a `CREATE` performed by the code that a delegated EOA is running) bumps the caller's nonce unconditionally, even on an `eth_transact`.

### Finding Description
`CheckNonce::prepare_nonce_for_account` increments the sender's `frame_system::Account::nonce` by exactly 1 during pre-dispatch preparation of every transaction extrinsic [4](#0-3) . This is the value transaction submitters/pool rely on for strictly sequential nonces.

For a normal Ethereum-style call (`eth_transact` → `eth_call`), `ExecConfig::bump_nonce = false` so the top-level frame's dispatch does not add a second increment — this is by design, matching the "Note: The origin's nonce is already incremented pre-dispatch" comment.

However, EIP-7702 delegation (`AccountInfo::set_delegation`) allows any signer to designate a target contract whose code runs in the EOA's own execution context [5](#0-4) . When a top-level `eth_transact` call targets such a delegated EOA, `exec.rs` resolves the callee's code to the delegation target and runs it with the EOA's own account/storage [6](#0-5) . If that delegated code contains a `CREATE`/`CREATE2` opcode, `contract::create` calls `ctx->host` equivalent `interpreter.ext.instantiate(...)` [7](#0-6) , which pushes a new `Constructor` frame. Because this instantiate happens *inside* the already-open top-level call frame, `is_first_frame` is `false` for it, and the `bump_nonce || !is_first_frame` guard evaluates to `true` regardless of the `bump_nonce = false` setting for the Ethereum transaction — so `<System<T>>::inc_account_nonce(caller.account_id()?)` runs a second time against the delegated EOA's own `frame_system` account, the exact account whose nonce `CheckNonce` already incremented once for this very extrinsic.

This is the direct structural analog of the reported issue: "an EOA's nonce may be incremented more than once per transaction" because the delegated-execution path was not exempted from the nonce-bump-on-`CREATE` logic that exists for ordinary contract-initiated instantiation. In the original report the check meant to gate this behavior (`create_inside_delegated_` / `EVMC_DELEGATED`) was defeated because the flag was never propagated from the opcode handler; here, the `bump_nonce` flag that is supposed to represent "already incremented pre-dispatch, don't do it again" is bypassed via the unconditional `!is_first_frame` branch specifically for the delegated-EOA-executes-its-own-code case, which was apparently not anticipated when `bump_nonce`/`is_first_frame` semantics were designed for ordinary (non-delegated) contract-initiated CREATE.

### Impact Explanation
Double-incrementing the nonce of a delegated EOA within a single `eth_transact` desynchronizes the sender's on-chain nonce from what any subsequently signed/queued transaction from the same account expects (nonce N+1 when the actual state becomes N+2). Any other transaction from that account that was prepared assuming a single increment becomes stale/invalid. Unlike ordinary contract-initiated `CREATE`, this is directly reachable by an unprivileged externally-owned account merely by authorizing an EIP-7702 delegation to a contract that performs `CREATE`/`CREATE2` and then calling into that delegated address — no privileged role or governance action is required.

### Likelihood Explanation
The path is reachable through the standard, publicly available `eth_transact`/EIP-7702 authorization flow: any user can (1) sign an EIP-7702 authorization delegating their EOA to an attacker- or self-controlled contract that performs `CREATE`/`CREATE2`, and (2) send an `eth_transact` call to their own delegated address. No governance, root, or validator/collator privilege is needed. The `bump_nonce`/`is_first_frame` logic and its documented rationale strongly suggest the double-increment for nested instantiate frames was designed around ordinary contract call chains and was not re-examined for the EIP-7702 delegated-EOA-as-callee case, where "caller" of the nested `CREATE` resolves back to the very account whose nonce `CheckNonce` already advanced for the enclosing extrinsic.

### Recommendation
Exempt nested `CREATE`/`CREATE2` frames from the extra nonce increment when the executing account is the delegated EOA itself (i.e., when the account already had its nonce incremented pre-dispatch by `CheckNonce` for the current top-level transaction), analogous to how `bump_nonce` already suppresses the increment for the top-level frame. This likely requires tracking, at the `Stack`/frame level, whether the "caller" account of a nested instantiate is the same account as the transaction's own origin under a delegated-EOA execution, and skipping the second `inc_account_nonce` call in that case.

### Proof of Concept
I was not able to execute a live reproduction in this read-only analysis session (no filesystem/terminal access), so the following describes the concrete code path that a Devin session with repo access could turn into a `pallet-revive` unit test, plus what remains unverified:

- Verified via static code review:
  - `ExecConfig::bump_nonce` is `false` for `eth_transact`, with an explicit doc caveat that nested contract-initiated instantiations "will always bump the instantiating contract's nonce" [3](#0-2) .
  - The `do_transaction` closure in `exec.rs` unconditionally re-increments `caller.account_id()`'s nonce whenever `!is_first_frame`, i.e., for any `CREATE` executed from inside an already-running call frame [2](#0-1) .
  - EIP-7702 delegated calls execute the delegate's code using the EOA's own account context [6](#0-5) , and existing tests such as `bump_nonce_once_works` / `nonce()` confirm the nonce-bump semantics for ordinary (non-delegated) constructor frames [8](#0-7) [9](#0-8) , but no existing test in `substrate/frame/revive/src/tests/eip7702.rs` specifically covers a delegated EOA whose delegate performs `CREATE`/`CREATE2` and asserts the resulting nonce delta.
- Not verified (would require execution): I could not confirm in this session (i) that `caller.account_id()` inside the nested-instantiate closure resolves precisely to the delegated EOA's own `AccountId` rather than some intermediate/mapped account in this specific delegated-call code path, and (ii) the downstream block-authoring behavior (whether `sc-block-builder`'s extrinsic inclusion logic silently drops a subsequently-stale transaction or produces a harder failure), since reading `substrate/client/block-builder/src/lib.rs`'s `push_extrinsic` implementation was not completed before the tool budget ran out. A concrete `#[test]` in `substrate/frame/revive/src/tests/eip7702.rs` that (a) delegates an EOA to a `Caller`-style contract exposing `create`/`create2` (as in `substrate/frame/revive/fixtures/contracts/Caller.sol`) [10](#0-9) , (b) drives it through `eth_transact` with `ExecConfig`'s default `bump_nonce=false`, and (c) asserts `System::account_nonce(&delegated_eoa)` before/after would give a definitive confirmation.

Given the partially-unverified reachability chain (specifically the identity of `caller` in the nested frame and the block-builder-level consequence), this should be treated as a **credible but not fully executed** finding suitable for follow-up verification with an actual test run in a Devin session with repository and execution access.

	/// In transaction extension, prepare nonce for account.
	pub fn prepare_nonce_for_account(
		who: &T::AccountId,
		mut nonce: T::Nonce,
	) -> Result<(), TransactionValidityError> {
		let account = crate::Account::<T>::get(who);
		if nonce > account.nonce {
			return Err(InvalidTransaction::Future.into());
		}
		nonce = nonce.checked_add(&T::Nonce::one()).unwrap_or(T::Nonce::zero());
		crate::Account::<T>::mutate(who, |account| account.nonce = nonce);
		Ok(())
	}

#[test]
fn bump_nonce_once_works() {
	let (code, hash) = compile_module("dummy").unwrap();

	ExtBuilder::default().existential_deposit(100).build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 1_000_000);
		frame_system::Account::<Test>::mutate(&ALICE, |account| account.nonce = 1);

		let do_not_bump = ExecConfig::new_substrate_tx_without_bump();

		let _ = <Test as Config>::Currency::set_balance(&BOB, 1_000_000);
		frame_system::Account::<Test>::mutate(&BOB, |account| account.nonce = 1);

		builder::bare_instantiate(Code::Upload(code.clone()))
			.origin(RuntimeOrigin::signed(ALICE))
			.salt(None)
			.build_and_unwrap_result();
		assert_eq!(System::account_nonce(&ALICE), 2);

		// instantiate again is ok
		let result = builder::bare_instantiate(Code::Existing(hash))
			.origin(RuntimeOrigin::signed(ALICE))
			.salt(None)
			.build()
			.result;
		assert!(result.is_ok());

		builder::bare_instantiate(Code::Upload(code.clone()))
			.origin(RuntimeOrigin::signed(BOB))
			.exec_config(ExecConfig::new_substrate_tx_without_bump())
			.salt(None)
			.build_and_unwrap_result();
		assert_eq!(System::account_nonce(&BOB), 1);

		// instantiate again should fail
		let err = builder::bare_instantiate(Code::Upload(code))
			.origin(RuntimeOrigin::signed(BOB))
			.exec_config(do_not_bump)
			.salt(None)
			.build()
			.result
			.unwrap_err();

		assert_eq!(err, <Error<Test>>::DuplicateContract.into());
	});
}
