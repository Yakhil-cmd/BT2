### Title
Unprivileged dust top-ups permanently block permissionless `clean_bad_debt`, keeping bad debt unsocialized and supplier funds short - (File: contracts/controller/src/positions/supply.rs)

### Summary
The Linea report's class — a party that can selectively prevent a pending user claim, freezing funds — maps onto XOXNO Lending's bad-debt pipeline: the permissionless `clean_bad_debt` gate requires the insolvent account's remaining collateral to be at or below the fixed `$5` dust threshold, while the equally permissionless `supply` entrypoint lets any third party top up a collateral leg the account already holds. An unprivileged attacker can therefore push the account's unweighted collateral above the dust gate at will, making every `clean_bad_debt` call revert with `CannotCleanBadDebt` and indefinitely deferring the supply-index write-down that socializes the loss.

### Finding Description
`clean_bad_debt` succeeds only when `total_debt > total_collateral` and `total_collateral <= BAD_DEBT_USD_THRESHOLD` ($5 in WAD), per `is_socializable_bad_debt`. The docs pin exactly this gate: "Permissionless cleanup requires ceil risk debt greater than half-up unweighted collateral and collateral at or below the fixed $5 dust threshold." [1](#0-0) 

Meanwhile `supply` deliberately allows any authenticated third party to add funds to a foreign account for assets it already supplies: `require_third_party_existing_supply` only rejects assets not already present in `account.supply_positions` (`contracts/controller/src/positions/supply.rs:78-97`), confirmed as intended by INV-AUTH-03 ("Supply to an existing foreign account can only top up supply assets already held"). [2](#0-1) 

There is no eligibility check on the target account's health: an insolvent, underwater account accepts third-party top-ups exactly like a healthy one (the harness exercises this path on underwater accounts, e.g. `poc_lt_cut_stays_sticky_when_hf_below_min` topping up ALICE's leg while her position is distressed). [3](#0-2) 

Combined, the censorship sequence is:

1. Alice's account goes insolvent; liquidation grinds her collateral down below $5 while debt remains. The permissionless dust gate is now open — `clean_bad_debt` should fire and socialize the debt into the supply index.
2. The attacker calls `supply(caller=attacker, account_id=alice, spoke_id, assets=[(existing_collateral_asset, >$5)])`. This credits Alice's existing leg and is fully authorized.
3. Every subsequent `clean_bad_debt(caller, alice)` reverts with `CannotCleanBadDebt` because `total_collateral > $5`. The account is still insolvent (`debt > collateral` may still hold — the attacker adds a small amount against a much larger debt).
4. Whenever liquidation or price drift brings the collateral back under $5, the attacker repeats the top-up. The debt is never written off, the supply index never falls, and the market's phantom bad debt persists.

The same gate logic is mirrored for the post-`liquidate` auto-cleanup path ("Post-liquidation cleanup applies the same gate"), so the top-up also suppresses cleanup that would otherwise fire inside a liquidation. [4](#0-3) 

### Impact Explanation
Protocol insolvency / temporary-to-permanent freezing of supplier funds. Until bad debt is socialized, the affected market's books carry borrowed shares with no backing: honest suppliers' withdrawals can fail against the actual cash/index shortfall rather than absorbing an explicit, bounded write-down (the index floor can itself leave residual unbacked claims — `docs/reference/formulas.md` "Bad debt"). The attacker converts the protocol's designed loss-recognition step into an indefinitely postponed one, exactly as the Linea prover converts a claimable L2→L1 message into an unclaimable one by omitting it from the finalized tree. The analogous "skipped message" is the skipped socialization; the frozen funds are the suppliers' claims that stay nominally whole on paper but are not payable.

### Likelihood Explanation
Reachable by any unprivileged address holding a small amount of a listed collateral asset: the attack requires only `controller::supply` on an existing leg, plus monitoring for accounts crossing the dust gate. The cost is asymmetric in the protocol's favor — each top-up must exceed the $5 threshold and is itself exposed to seizure by liquidators (the position remains HF<1-liquidatable, so added collateral is siphoned off pro-rata), so sustaining the censorship requires ongoing spend rather than a one-time lock. The owner-gated `force_socialize_bad_debt` has no collateral cap and remains a governance-mediated fallback, which bounds permanence but requires noticing the pattern and passing a timelocked op. Net effect: a griefing vector that can delay loss recognition at moderate recurring cost — Medium severity.

### Recommendation
Decouple the cleanup gate from attacker-malleable collateral value. Options: compute the dust eligibility from a stored/marked snapshot taken when the account first becomes insolvent (or from collateral excluding same-tx third-party top-ups); apply an epoch/stamp check so collateral supplied by non-owners after insolvency does not count toward the $5 gate; or have `clean_bad_debt` itself seize/socialize the topped-up leg in the same call instead of reverting. At minimum, treat "collateral rose only via third-party top-up after first insolvency" as not disqualifying.

### Proof of Concept
Built on the harness in `tests/test-harness/`:

```rust
let mut t = LendingTest::new().standard_two_asset_dust_disabled().build();

t.supply(BOB, "ETH", 100.0);
t.supply(ALICE, "USDC", 8.0);        // Alice's only collateral leg
t.borrow(ALICE, "ETH", 0.002);

t.set_price("USDC", usd_cents(5));   // collateral ~$0.40 < $5, debt > collateral
let account_id = t.resolve_account_id(ALICE);

// Precondition: permissionless cleanup is open right now.
t.clean_bad_debt_by_id(account_id);  // would succeed -- instead, attacker acts first:
```

Attack path (replace the last call):

```rust
// Attacker top-up of Alice's EXISTING USDC leg -- allowed by
// require_third_party_existing_supply (supply.rs:78-97).
t.try_supply_to_account(ATTACKER, ALICE, "USDC", 6.0)
    .expect("third-party top-up lands on the insolvent account");

// Every cleanup now reverts: collateral ~$6.40 > $5 gate.
assert_contract_error(
    t.try_clean_bad_debt_by_id(account_id),
    errors::CANNOT_CLEAN_BAD_DEBT,
);
```

The existing test `test_keeper_clean_bad_debt_decreases_supply_index` (`tests/test-harness/tests/controller/bad_debt_index.rs:196-220`) demonstrates the baseline cleanup succeeds at this exact fixture before the top-up, and `deep_underwater_account_still_liquidates_to_the_dust_gate` (`tests/test-harness/tests/controller/bad_debt_netting_and_exit_timing.rs:191-218`) shows the gate refusing above-$5 collateral. Repeating the top-up whenever liquidations re-open the gate keeps `clean_bad_debt` unreachable, leaving the ETH debt unsocialized in the market's books and supplier claims under-backed for as long as the attacker sustains the spend.

## Bad debt

`clean_bad_debt` is permissionless. It succeeds only when debt exceeds
collateral and collateral is at most `BAD_DEBT_USD_THRESHOLD`, a fixed 5 USD
in WAD. `CannotCleanBadDebt` (`controller #114`) is a legitimate result when
those conditions do not hold; it is not inherently a collision or a non-user
error. Post-liquidation cleanup applies the same gate but skips instead of
reverting. The owner-only `force_socialize_bad_debt` has no collateral cap.
Always identify the panicking contract before interpreting #114.
