### Title
Remote AA getter calls (`$aa.$getter()`) trust an attacker-suppliable address without pinning its base AA, enabling an oracle/interface-spoofing analog to the JOJO Chainlink issue - ([File: formula/evaluation.js])

### Summary
The JOJO report's root cause is that a price source address is used through a fixed interface (`latestRoundData()`) without ever verifying that the address is actually the expected/legitimate implementation. Obyte's oscript has a directly analogous pattern in inter-AA "remote getter calls": an AA can call `$remote_aa.$getter(args)` where `$remote_aa` is any address — including one supplied by the trigger sender — and the result is trusted and used in the caller's own state/response logic without any enforced check that the remote address is the AA template the developer actually intended to trust. The language does provide an optional pinning mechanism (`addr#base_aa.$getter(...)`), but its use is opt-in, not enforced by the runtime for the ordinary `.` call form.

### Finding Description
`remote_func` in the grammar allows two call forms:
- Unpinned: `remote_aa.$getter(...)` [1](#0-0) 
- Pinned: `remote_aa#base_aa.$getter(...)`, which asserts a specific base AA [2](#0-1) 

At runtime, `callGetter()` resolves `aa_address` to its *actual* base AA/getters definition via `storage.readBaseAADefinitionAndParams` and, if a getter with that name exists, blindly calls it and returns whatever value it produces — there is no requirement that this base definition matches anything the calling AA expects unless the developer explicitly used the `#` pinning syntax: [3](#0-2) 

Only when the developer chooses to pin (`#expected_base_aa`) is the actual base AA of the remote address checked against the expectation, producing the bounce error `"... is not base AA for remote AA"` demonstrated in the test suite: [4](#0-3) 

Without pinning, any address — including one taken straight from `trigger.data` (attacker-controlled input) — can be substituted for what the AA author intended to be a trusted remote AA (e.g., a price oracle, a whitelisted counterpart AA, a shared library AA), and its getter's return value is used as-is: [5](#0-4) 

This mirrors the JOJO Chainlink bug precisely: the "oracle"/counterpart address is trusted to implement a specific expected interface/semantics, but nothing enforces that at the protocol level for the unpinned call form; the responsibility is left entirely to the AA author remembering to use `#base_aa` pinning.

### Impact Explanation
If an AA author writes logic that calls a remote getter to obtain a value used for financial decisions (e.g., a price, a computed fee, or an authorization flag) and forgets — or is not aware they need — to pin the base AA with `#`, an unprivileged trigger sender can pass their own malicious AA address (deployed by themselves, as any address is postable/definable) in place of the expected oracle/counterpart AA. The malicious AA's getter can return arbitrary crafted values (fabricated "prices", fabricated "balances", fabricated boolean approvals). The caller AA then uses this data to compute payment outputs, potentially transferring more bytes/assets than warranted or approving otherwise-disallowed operations — a direct AA fund loss/drain, exactly analogous to a spoofed Chainlink price causing fund loss in the JOJO adaptor.

### Likelihood Explanation
The attack path is fully reachable by a single unprivileged AA trigger sender: they only need to (1) deploy their own AA definition with a same-named getter that returns attacker-chosen data, and (2) supply that AA's address as `trigger.data.aa` (or any other field the vulnerable AA reads for the remote call). No special privileges, witness cooperation, or network conditions are required — this is purely a data-feed/AA-trigger input problem, matching the allowed AA-trigger-sender threat class. The likelihood of any *specific* AA being vulnerable depends on whether its author uses unpinned remote calls with attacker-influenced addresses for security-critical values; the protocol itself does not prevent or warn against this pattern.

### Recommendation
- Since this is a language/runtime design choice rather than a straightforward coding bug, mitigation is primarily a documentation/tooling concern: strongly recommend (and where possible enforce via linting/`aa_validation.js`) that any remote getter call whose target address can be influenced by trigger data or other externally supplied values MUST use the pinned `#expected_base_aa` form.
- Consider adding a runtime/validation-time warning or stricter mode that flags `remote_func` calls where the `remote_aa` expression is derived from `trigger.data`/`trigger.address`/other externally controlled sources without a corresponding `#base_aa` pin.
- Documentation for `oscript`/AA development should explicitly call out that unpinned remote getter calls provide no interface/authenticity guarantee about the callee, analogous to why Chainlink-style price adaptors must validate the oracle contract's identity/interface.

### Proof of Concept
1. Deploy `attacker_aa`, an AA whose getters define `$f` (or whatever getter name the target AA calls) to return a fabricated value, e.g. a fake "price" or fake balance figure that benefits the attacker.
2. Deploy/observe `victim_aa`, an AA that performs `$remote_aa.$f(...)` where `$remote_aa` is taken from `trigger.data.aa` (or another attacker-controlled trigger field), and uses the returned value to compute a payment output (as in the test pattern at [6](#0-5) , but without the `#pin`).
3. Send a trigger unit to `victim_aa` with `data.aa = attacker_aa_address`.
4. `victim_aa` calls `attacker_aa.$f(...)`, receives the attacker-crafted value, and uses it in its payment/response logic — potentially paying out funds based on entirely fabricated data, with no error raised since the getter exists and returns a syntactically valid value.

This is presented as an analog of the reported bug class (unvalidated trusted external data source), not a confirmed exploit against a specific deployed AA — its concrete impact depends on the calling AA's own logic, which is outside `ocore`'s control, but the language/runtime provides no protection against it unless the developer opts into `#` pinning.

test.cb.serial('calling a remote function in a parameterized AA with unmatching base AA', t => {
	var trigger_address = "I2ADHGP4HL6J37NQAD73J7E5SKFIXJOT";

	var remote_base_aa = ['autonomous agent', {
		getters: `{
			$g = $x => $x*2;
		}`,
		messages: [
			{
				app: 'state',
				state: `{
				}`
			}
		]
	}];
	var remote_base_aa_address = objectHash.getChash160(remote_base_aa);
	
	var remote_base_aa2 = ['autonomous agent', {
		getters: `{
			$g = $x => $x*4;
		}`,
		messages: [
			{
				app: 'state',
				state: `{
				}`
			}
		]
	}];
	var remote_base_aa2_address = objectHash.getChash160(remote_base_aa2);
	
	var remote_aa = ['autonomous agent', {
		base_aa: remote_base_aa_address,
		params: {
			vvv: "fff",
			fee: 0.02,
		}
	}];
	var remote_aa_address = objectHash.getChash160(remote_aa);
	
	var trigger = { outputs: { base: 10000 }, data: { x: 5, aa: remote_aa_address }, address: trigger_address };

	var aa = ['autonomous agent', {
		init: `{
			$ret = trigger.data.aa#${remote_base_aa2_address}.$g(trigger.data.x);
		}`,
		messages: [
			{
				app: 'state',
				state: `{
				}`
			}
		]
	}];
	var aa_address = objectHash.getChash160(aa);

	validateAA(remote_base_aa, async err => {
		t.deepEqual(err, null);
		await asyncAddAA(remote_base_aa);
		await asyncAddAA(remote_base_aa2);

		validateAA(remote_aa, async err => {
			t.deepEqual(err, null);

					t.regex(JSON.stringify(arrResponses[0].response.error), /is not base AA for remote AA/);
					t.end();
				});
			});
		});
	});
});
