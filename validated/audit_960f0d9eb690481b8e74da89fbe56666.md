### Title
Unbounded LevelDB Range Scan in `in_data_feed`/data feed relational lookups Allows AA-Triggered Resource Exhaustion - ([File: data_feeds.js])

### Summary
The `dataFeedByAddressExists()` function used by the `in_data_feed`/`data_feed` oscript operators performs relational comparisons (`>`, `>=`, `<`, `<=`, `!=`) by opening a LevelDB key stream over a value-ordered key range without any `limit`, and only narrows to the caller's `[min_mci, max_mci]` window inside the per-record `handleData` callback. Any address that has posted many data-feed values that fall outside the requested MCI window but still within the value-ordered scan range forces the node to iterate every one of those on-disk records before it can conclude "not found." An attacker who controls an oracle address (any address can post `data_feed` messages) can pre-populate a large number of records and then trigger an AA that evaluates `in_data_feed[[oracles=...]]` against that address with a non-matching relation, forcing deterministic, unbounded synchronous DB scanning during AA execution — analogous to VannaQueryEngine's unrestricted SQL execution from user input.

### Finding Description
`dataFeedByAddressExists()` builds a key range keyed only by feed value and address/feed_name, then streams matching keys with `kvstore.createReadStream`/`createKeyStream` without an item `limit` for the `>`, `>=`, `<`, `<=` relations: [1](#0-0) 
The stream's `handleData` callback then filters by `min_mci`/`max_mci` per record and only stops the stream once a satisfying record is found: [2](#0-1) 
For the `!=` relation, `dataFeedByAddressExists` recurses into both a `>` and `<` scan, doubling the exposure: [3](#0-2) 

This function is reachable directly from oscript formula evaluation via the `in_data_feed` operator in `formula/evaluation.js`, which calls `dataFeeds.dataFeedExists()` (which in turn calls `dataFeedByAddressExists()` per oracle address) using attacker/AA-controlled `oracles`, `feed_name`, `feed_value`, and `min_mci` parameters supplied through the AA trigger or AA-defined formula: [4](#0-3) 
The `data_feed[[...]]` value-lookup operator has the analogous unbounded-scan exposure through `readDataFeedByAddress`/`readDataFeedValue`: [5](#0-4) [6](#0-5) 

Unlike other AA formula constructs, this DB-scan cost is not charged against `MAX_OPS`, `complexity`, or any other per-operation accounting enforced in `formula/validation.js` — the cost model only counts AST nodes/operations, not the number of on-disk records a relational data-feed lookup must traverse. Because any address can freely post `data_feed` messages (there is no cap on how many data feed values an address may post over time), an attacker can:
1. Post a very large number of `data_feed` messages from a self-controlled oracle address, each with values that will not satisfy the eventual relational query but sit within the value-ordered key range that will be scanned.
2. Trigger (or get others to trigger) an AA that evaluates `in_data_feed[[oracles=<attacker address>, feed_name=..., relation, value, min_mci=...]]` against that oracle, forcing every full node validating/executing that AA response to synchronously scan the entire matching value range before determining no match exists within the MCI window.

Because AA execution must be deterministic and reproducible by every full node validating the resulting response unit, this cost is paid identically by all validating nodes each time the trigger (or any similar trigger) is processed, not just by the attacker.

### Impact Explanation
This causes CPU/I-O resource exhaustion during unit/AA-response validation across all full nodes that must replay the AA logic (via `handleTrigger` → `evaluateAA` → `formula.evaluate` → `in_data_feed`/`data_feed`). Since AA execution is on the critical path for building and validating new units, sustained abuse can slow down or stall processing of new units network-wide, matching the "network unable to confirm new units" impact category. The bug class mirrors CVE-2024-58339: an operation that executes an expensive underlying data-store query driven by user-controlled parameters, with no enforced bound on the amount of work performed.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged access is required — any address can post `data_feed` messages and any address can post an AA trigger unit that evaluates `in_data_feed`/`data_feed` against a self-controlled oracle. No cooperation from a third party is needed; the attacker fully controls both the oracle data volume and the AA formula/trigger parameters (feed_name, relation, value, min_mci). The only cost to the attacker is the on-chain fee for posting the initial batch of `data_feed` units plus one trigger unit, which is cheap relative to the amortized validation cost imposed on every full node for each subsequent trigger that hits the unbounded scan.

### Recommendation
- Add an explicit `limit` to the LevelDB range scans in `dataFeedByAddressExists()` for the `>`, `>=`, `<`, `<=` cases, or otherwise bound the number of records inspected by a data feed value comparison per operation.
- Incorporate the read cost (e.g., proportional to `count_before_found`/`count`) into the AA's `MAX_OPS`/complexity accounting in `formula/validation.js` so that pathological data-feed histories cannot be exploited for free, or cap `min_mci`/`max_mci` range width and reject if a single oracle's matching record set is too large.
- Consider capping the number of `data_feed` messages an address may post within a feed_name over the range likely to be scanned, or requiring a bound/limit parameter for relational `in_data_feed` queries.

### Proof of Concept
1. From an attacker-controlled address `A`, post a large number (e.g., tens of thousands) of `data_feed` units over time with `feed_name = "x"` and values that will not match the target relation/value used in step 3 (e.g., always post `x = 1` while later querying for `x > 1000000`), spread across many different MCIs, none within the eventual `min_mci` window used by the attack trigger.
2. Deploy or reuse any AA whose formula includes:
   `in_data_feed[[oracles=A, feed_name="x", feed_value>1000000, min_mci=<large recent mci>]]`
3. Send a trigger unit to that AA. Every full node validating the resulting AA response must execute `dataFeeds.dataFeedExists` → `dataFeedByAddressExists`, opening the unbounded `createKeyStream`/`createReadStream` scan across all of `A`'s posted `x` values before concluding no match falls in the MCI window, as shown in [7](#0-6) , consuming CPU/I-O proportional to the number of records `A` posted rather than to any bounded operation count.

		key_prefix = 'dfv\n'+address+'\n'+feed_name;
	}
	else{
		var prefixed_value;
		if (typeof value === 'string'){
			var float = string_utils.toNumber(value, bLimitedPrecision);
			if (float !== null)
				prefixed_value = 'n\n'+string_utils.encodeDoubleInLexicograpicOrder(float);
			else
				prefixed_value = 's\n'+value;
		}
		else
			prefixed_value = 'n\n'+string_utils.encodeDoubleInLexicograpicOrder(value);
		key_prefix = 'df\n'+address+'\n'+feed_name+'\n'+prefixed_value;

	var options = {
		gte: key_prefix+'\n'+string_utils.encodeMci(max_mci),
		lte: key_prefix+'\n'+string_utils.encodeMci(min_mci),
		limit: bAbortIfSeveral ? 2 : 1
	};
	var handleData = function(data){
		if (bAbortIfSeveral && objResult.value !== undefined){
			objResult.bAbortedBecauseOfSeveral = true;
			return;

		var mci = string_utils.getMciFromDataFeedKey(data.key);
		if (objResult.value === undefined || ifseveral === 'last' && mci > objResult.mci){
			if (value !== null){
				objResult.value = string_utils.getValueFromDataFeedKey(data.key);

			}
			else{
				var arrParts = data.value.split('\n');
				objResult.value = string_utils.getFeedValue(arrParts[0], bLimitedPrecision); // may convert to number
				objResult.unit = arrParts[1];
			}
			objResult.mci = mci;
		}
	};
	kvstore.createReadStream(options)
	.on('data', handleData)
	.on('end', function(){
		handleResult(objResult.bAbortedBecauseOfSeveral);
	})
	.on('error', function(error){
		throw Error('error from data stream: '+error);
	});
