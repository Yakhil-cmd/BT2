### Title
Webhook signature verified against attacker-controlled organization but commit status is applied globally by SHA, enabling cross-organization CI-status forgery and unauthorized merges/deploys - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub organization's `webhook_secret` to validate the HMAC signature against using an attacker-supplied payload field (`repository.owner.login`, falling back to `organization.login`), rather than binding the verified organization to what the event handler actually mutates. `Handlers::StatusHandler`, in particular, applies the event to **any** commit matching `params.sha` in the entire database (`Commit.where(sha: params.sha)`), without ever checking that the commit belongs to a stack/repository owned by the organization whose secret validated the signature. This is the same class of bug as the Perennial-V2 liquidation check: a guard exists (`verify_signature`) but it only binds the *signature* to an org, never to the *data being written*, so anyone who legitimately controls one onboarded organization's webhook secret can forge events that affect a completely different organization's commits.

### Finding Description
The verification flow is: [1](#0-0) 

`repository_owner` is read straight out of the untrusted JSON body: [2](#0-1) 

That value is used only to pick *which* configured GitHub App/organization secret is used for HMAC comparison — it is never subsequently compared to the data the handler will write. Once `verify_signature` passes, the entire raw payload is handed to the registered handlers unmodified: [3](#0-2) 

`StatusHandler` (invoked for the `status` event) trusts `sha` from the payload and updates **every** commit in the database sharing that SHA, with no organization/repository scoping at all: [4](#0-3) 

Contrast this with `Handler#repository_name`/`#stacks`, which at least scope by `repository.full_name` for other handlers such as `PushHandler`: [5](#0-4) 

`StatusHandler` doesn't use `stacks`/`repository_name` at all — it is a global lookup keyed only by SHA. So the equality that should hold — "organization whose secret authenticated this request == organization that owns the repository/commit being mutated" — is never enforced.

If Shipit is configured (as its own docs describe) with more than one GitHub App/organization block, each with its own `webhook_secret` (`TOP_LEVEL_GH_KEYS` in `lib/shipit.rb`), then any user who is an admin of *one* of those onboarded organizations and therefore legitimately knows that organization's `webhook_secret` can craft an arbitrary JSON body, set `repository.owner.login` (or `organization.login`) to their own organization to pass signature verification, but set `sha` to a commit SHA belonging to a *different* organization's stack, and set `state: "success"` with any `context`. `verify_signature` succeeds because the HMAC matches the org they legitimately control; `StatusHandler` then blindly attaches that fabricated "success" status to the victim commit.

### Impact Explanation
A forged "success" `commit_status` on a victim stack's commit can satisfy `StatusChecker`/`Status::Group` requirements used by:
- The merge queue (`MergeRequest#all_status_checks_passed?` → `ProcessMergeRequestsJob` → `MergeRequest#merge!`), enabling an **unauthorized merge** of a pull request the attacker does not control. [6](#0-5) [7](#0-6) 
- Continuous delivery deploy gating, which relies on the same commit statuses, potentially triggering an **unauthorized deploy**.

This satisfies the Critical bar ("an unauthorized deploy, rollback or merge") using only a credential the attacker legitimately holds for an unrelated, lower-trust organization — no repository write access, `ApiClient` token, or GitHub App private key for the *victim* organization is required.

### Likelihood Explanation
Requires that Shipit is configured with multiple GitHub organizations/apps (a supported, documented configuration via `TOP_LEVEL_GH_KEYS`), and that the attacker is a legitimate admin/webhook-configurer of at least one onboarded (but otherwise unrelated) organization. Under that realistic multi-tenant deployment, the attack requires only crafting one HTTP POST to `/webhooks` with a correct HMAC computed from a secret the attacker already knows — no interaction with the victim org and no privileged Shipit account needed.

### Recommendation
After signature verification, bind the verified organization to the data being processed: handlers must resolve the target `Stack`/`Repository` from `repository.full_name` (as `PushHandler` already does) and reject/ignore updates whose target repository's owner does not match the organization whose secret validated the signature. `StatusHandler` (and any other handler that trusts a bare `sha` without repository scoping) should be limited to commits belonging to stacks whose repository owner equals the verified `repository_owner`.

### Proof of Concept
1. Shipit is configured with two organizations, e.g. `attacker-org` and `victim-org`, each with its own GitHub App and `webhook_secret` (per `lib/shipit.rb` `TOP_LEVEL_GH_KEYS` support).
2. Attacker administers `attacker-org` and therefore knows `attacker-org`'s `webhook_secret` (they configured it themselves when installing the GitHub App).
3. Attacker crafts a `status` event JSON body:
   ```json
   {
     "sha": "<victim-org commit sha pending in the merge queue>",
     "state": "success",
     "context": "ci/required-check",
     "repository": { "owner": { "login": "attacker-org" }, "full_name": "attacker-org/some-repo" }
   }
   ```
4. Attacker computes `X-Hub-Signature: sha1=HMAC(attacker-org secret, body)` and POSTs it to `/webhooks` with `X-Github-Event: status`.
5. `WebhooksController#verify_signature` resolves `repository_owner = "attacker-org"`, fetches `attacker-org`'s secret, and the HMAC matches → request is accepted.
6. `StatusHandler#process` runs `Commit.where(sha: params.sha)`, finds the victim commit (belonging to `victim-org`), and creates a fabricated `success` status on it, with no check that `attacker-org` has any relationship to that commit.
7. If that commit was the head of a pending pull request in `victim-org`'s merge queue awaiting that CI context, `ProcessMergeRequestsJob` now sees `all_status_checks_passed?` as true and calls `merge_request.merge!`, merging the PR without legitimate CI approval.

```ruby
    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end
```

```ruby
    def perform(stack)
      merge_requests = stack.merge_requests.to_be_merged.to_a
      merge_requests.each do |merge_request|
        merge_request.refresh!
        merge_request.reject_unless_mergeable!
        merge_request.cancel! if merge_request.closed?
        merge_request.revalidate! if merge_request.need_revalidation?

      return false unless stack.allows_merges?

        merge_request.refresh!

          merge_request.merge!
        rescue MergeRequest::NotReady
          ProcessMergeRequestsJob.set(wait: 10.seconds).perform_later(stack)
          return false
        end
```
