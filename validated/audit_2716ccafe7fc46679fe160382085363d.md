I have sufficient evidence to write the report now.### Title
Unbounded `in_data_feed`/`data_feed` LevelDB range scan lets an attacker-controlled oracle stall AA trigger evaluation - (File: `data_feeds.js`)

### Summary
The oscript functions `data_feed`/`in_data_feed`, evaluated whenever an AA (or a bounce-fee oscript in a normal unit) references a data feed, call into `dataFeeds.dataFeedExists()` → `dataFeedByAddressExists()`. For every relational comparison other than exact equality (`<`, `<=`, `>`, `>=`, `!=`), this function opens a `kvstore` key-range stream **without any `limit`** and iterates it record-by-record until either a match is found or the stream naturally ends. The number of records in that range is entirely controlled by how many `data_feed` messages the referenced oracle address has posted historically for that `feed_name`/value type — an attacker-controlled quantity, directly analogous to the reported `at()` issue where an unbounded backward iteration over an attacker-inflatable history caused out-of-gas.

### Finding Description
`dataFeedByAddressExists()` builds a `kvstore` range (`gte`/`gt`/`lte`/`lt`) keyed by `df\n<address>\n<feed_name>\n<type>\n<value>\n<mci>` and streams it with no `limit` option for the `<`, `<=`, `>`, `>=` relations: [1](#0-0) 

Compare this with the `=` relation path in the same function, which does set `options.limit = 1`: [2](#0-1) 

Since `data_feed` messages can be posted by **any address, with no cost limit tied to feed-name reuse**, and are persisted permanently in the `df\n...` key-space consumed by `dataFeedByAddressExists()` at stability time: [3](#0-2) 

...an attacker can post an arbitrarily large number of `data_feed` messages from a single address under one `feed_name`, all with values chosen so that a subsequent `<`/`>`/`<=`/`>=`/`!=` query against that oracle+feed_name has to scan through most or all of them before finding a match (or reaching the end of the stream without a match).

This is reachable by an ordinary unprivileged unit poster and by any AA trigger sender: many AA patterns take the oracle address as a caller-supplied trigger parameter (e.g. prediction-market / “bring your own oracle” style contracts) and then call `in_data_feed[[oracles=$oracle, ...]]`. The formula/AA op-count and complexity checks in `formula/validation.js` bound the number of *oscript operations* in a formula, but do not account for the amount of work a single `data_feed`/`in_data_feed` operation can trigger inside `dataFeedByAddressExists()` — the per-key stream iteration is invisible to that complexity budget: [4](#0-3) 

The equivalent path in `readDataFeedByAddress()` (used for `data_feed[[...]]` value retrieval with an exact `feed_value`) is properly bounded (`limit: 1` or `2`): [5](#0-4) 

but `dataFeedByAddressExists()` (used by `in_data_feed[[...]]` and by bounce-fee address-definition checks) is not.

### Impact Explanation
A node validating/executing a unit that triggers an AA (or evaluates an address-definition `in data feed` condition) referencing an attacker-poisoned oracle address will spend disproportionate, attacker-controlled CPU/I-O time scanning the LevelDB key range inside `dataFeedByAddressExists()`. Because AA execution and unit validation are synchronous/serialized per-unit in ocore (not gas-metered like an EVM), this can significantly slow down or effectively stall processing of that unit (and, since validation/execution is generally single-threaded/serialized on a node, subsequent units queued behind it), leading to delayed AA responses (funds held/locked in the AA's own balance pending a bounce/response) and delayed network progress on that node. This matches the "network unable to confirm new units" / "AA fund loss or freezing" impact classes, since AA-held funds tied to a trigger that never completes promptly are effectively frozen for the duration of the stall, and repeated exploitation can be used to degrade a node's unit-processing throughput.

### Likelihood Explanation
Likelihood is moderate-to-high in any AA ecosystem where the oracle address is caller-supplied or otherwise attacker-controllable (a documented pattern, since `in_data_feed`/`data_feed` explicitly accept any well-formed address list as `oracles`). Posting many `data_feed` messages under one's own address is unrestricted and only bounded by ordinary posting fees, making the "large number of historical data-feed messages" precondition cheap and easy for a determined attacker to construct in advance, then trigger the expensive scan on demand via an AA call.

### Recommendation
- Add a `limit` (and/or a hard scan cap with early abort + error) to the `dataFeedByAddressExists()` stream for all relations, not just `=`, mirroring the bound already applied to `readDataFeedByAddress()`.
- Alternatively/additionally, charge oscript complexity/op-cost proportional to the number of KV records actually scanned by `data_feed`/`in_data_feed`, or cap the number of `data_feed` messages with the same `feed_name` per address that participate in a single query.
- Consider indexing data feed values in a structure allowing O(log n) range existence checks (e.g., a maintained min/max per feed_name+address) instead of a linear stream scan for inequality relations.

### Proof of Concept
1. From address `A`, post a very large number of `data_feed` units over time with `feed_name = "x"` and numeric values arranged so that, e.g., all values equal `1000000` except one outlier equal to `1` placed at the very end of the LevelDB iteration order for a `<` query.
2. Deploy/trigger an AA (or any oscript definition) that anyone can call with a caller-supplied oracle parameter and that evaluates `in_data_feed[[oracles=$oracle, feed_name='x', feed_value<10]]` with `oracles` bound to attacker's address `A`.
3. Trigger the AA. `dataFeedByAddressExists()` streams through essentially all of `A`'s posted `x` records (`data_feeds.js:170-187`) before finding the single matching value, causing the node evaluating the trigger to spend time proportional to the number of records the attacker posted, with no upper bound enforced by the code.
