## Finding: Webhook signature is verified against `repository.owner.login`/`organization.login`, but events are processed against the independent `repository.full_name` field [1](#0-0) [2](#0-1) [3](#0-2) 

### Summary
`WebhooksController#verify_signature` selects which organization's GitHub App (and thus which `webhook_secret`) to use for HMAC verification based on `repository.owner.login` (falling back to `organization.login`) extracted from the attacker-supplied JSON body. Once the signature "passes," `#create` re-parses the same body and hands it to `Shipit::Webhooks` handlers, which act on the *separate* `repository.full_name` field to resolve the actual `Stack`/`Repository` to write to (as exercised in `test/controllers/webhooks_controller_test.rb` where `unknown_repo_payload["repository"]["full_name"]` alone drives repository resolution). These two fields live in the same JSON object but are never checked for consistency.

### Finding Description
The reported bug class (verifying/sizing one thing but reading/writing a different, unchecked extent) maps here to a field-confusion issue: the *organization used to select the verification secret* is decoupled from the *repository that is actually mutated*.

- Verification org selection: [4](#0-3) [5](#0-4) 

- HMAC check, which trusts whatever `GithubApp` was resolved for that org and is a no-op if that org has no configured secret (documented as optional in `docs/setup.md`): [6](#0-5) 

- The actual event processing/repository resolution key is `repository.full_name`, a sibling field the attacker fully controls independently of `repository.owner.login`: [7](#0-6) 

Because both `repository.owner.login` and `repository.full_name` are attacker-supplied plaintext inside the same HTTP body, nothing forces them to refer to the same repository. An attacker who controls (or knows the webhook secret of, or targets an org configured with no secret at all — explicitly optional per `docs/setup.md`) *any* organization mounted on the Shipit instance can craft a payload whose `owner.login`/`organization.login` names that org (satisfying signature verification) while `repository.full_name` names an entirely different, unrelated "victim" repository/stack hosted on the same Shipit instance. The signature is verified against the org, not against the resource actually acted upon.

### Impact Explanation
This breaks the equality `{organization authenticated by HMAC} == {repository actually written}`. An attacker with no credentials or write access to the victim repository can forge push/status/check_run/membership events for it, causing Shipit to record fake commits, statuses, or trigger `GithubSyncJob`/continuous-delivery logic for a repository they do not control — a cross-repository, cross-trust-boundary write consistent with the "cross-repository writes" / "unauthorized deploy" Critical impact category.

### Likelihood Explanation
Exploitability depends on the attacker being able to satisfy verification for at least one organization mounted on the Shipit instance — either because that org has no `webhook_secret` configured (explicitly optional in the documented setup) or because the attacker has legitimate webhook access to some other, lower-trust org/repo also served by the same Shipit instance. Multi-organization/multi-secret configurations are a documented, supported feature (`GithubOrganizationUnknown`, per-org `Shipit.github(organization:)` lookups), so this is not a case of the host deviating from documented deployment. I was not able to fully trace `lib/shipit.rb`'s organization-to-`GithubApp` resolution logic (e.g., whether a `nil`/unrecognized organization silently falls back to a default app) within the available iterations, so the exact conditions under which an attacker can pick a "weak" verifying organization should be confirmed against that file before treating this as certain in every deployment configuration.

### Recommendation
After verifying the signature, cross-check that the organization/owner used to select the webhook secret matches the owner embedded in `repository.full_name` (and any other repository-identifying field used downstream) before dispatching to handlers; reject the event if they diverge. Alternatively, resolve the target `Stack`/`Repository` using the same field that was used to select the verifying secret.

### Proof of Concept
1. Attacker controls (or the instance has configured without a secret) organization `attacker-org`, mounted on the same Shipit instance as victim stack `victim-org/victim-repo`.
2. Attacker POSTs to `/webhooks` with header `X-Github-Event: push` and body:
```json
{
  "repository": {
    "owner": { "login": "attacker-org" },
    "full_name": "victim-org/victim-repo"
  },
  "organization": { "login": "attacker-org" },
  "after": "<forged sha>",
  "ref": "refs/heads/master"
}
```
3. `verify_signature` resolves `Shipit.github(organization: "attacker-org")` and validates the HMAC using `attacker-org`'s secret (known/absent), which succeeds.
4. `create` re-parses the body and dispatches to the push handler, which resolves the target stack via `repository.full_name = "victim-org/victim-repo"`, causing Shipit to process a forged push event for a repository the attacker never authenticated against. [8](#0-7)

# frozen_string_literal: true

module Shipit
  class WebhooksController < ActionController::Base
    skip_before_action :verify_authenticity_token, raise: false
    before_action :check_if_ping, :drop_unhandled_event, :verify_signature

    respond_to :json

    def create
      params = JSON.parse(request.raw_post)
      Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }

      head(:ok)
    end

    private

    def drop_unhandled_event
      # Acknowledge, but do nothing
      head(204) unless Shipit::Webhooks.for_event(event).present?
    end

    def verify_signature
      github_app = Shipit.github(organization: repository_owner)
      verified = github_app.verify_webhook_signature(
        request.headers['X-Hub-Signature'],
        request.raw_post
      )
      head(422) unless verified

      Rails.logger.info([
        'WebhookController#verify_signature',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "signature=#{request.headers['X-Hub-Signature']}",
        "status=#{status}"
      ].join(' '))
    rescue Shipit::GithubOrganizationUnknown => e
      head(422)
      Rails.logger.warn([
        'WebhookController#verify_signature',
        'Webhook from unknown organization',
        "event=#{event}",
        "repository_owner=#{repository_owner}",
        "unknown_organization=#{e.message}",
        "status=#{status}"
      ].join(' '))
    end

    def check_if_ping
      head(:ok) if event == 'ping'
    end

    def event
      request.headers.fetch('X-Github-Event')
    end

    def repository_owner
      # Fallback to the organization sub-object if repository isn't included in the payload
      params.dig('repository', 'owner', 'login') || params.dig('organization', 'login')
    end
  end
end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
