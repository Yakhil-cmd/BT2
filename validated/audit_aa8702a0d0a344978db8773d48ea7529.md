### Title
Unbounded submodule recursion during `configureWorktree` causes repeated sync-timeout failures and persistent sync denial - (File: main.go)

### Summary
The Sherlock report describes `UserManager.getFrozenInfo` iterating an attacker-influenced array (`vouchees`) with no bound on the work done per call, causing out-of-gas reverts. The analogous, reachable pattern in `git-sync` is `repoSync.configureWorktree`, which runs `git submodule update --init [--recursive]` over the *entire* submodule tree of an attacker-pushed commit in a single git invocation, with no cap on submodule count or recursion depth [1](#0-0) . Because every sync attempt is bounded only by `--sync-timeout` (applied via `context.WithTimeout` to the whole `SyncRepo` call, not to submodule work specifically), an attacker who controls the synced repository's content can make the submodule checkout step exceed the timeout on every single sync cycle, causing continuous failures.

### Finding Description
`main()` wraps each sync iteration in a context with `*flSyncTimeout` and calls `git.SyncRepo(ctx, syncHooks)` [2](#0-1) . Inside the sync path, once a new remote hash is detected, `createWorktree` and then `configureWorktree` are invoked [3](#0-2) . `configureWorktree` unconditionally runs `git submodule update --init` (optionally `--recursive`) for the whole worktree whenever `git.submodules != submodulesOff` (which is the default, `recursive`) [1](#0-0) . There is no limit on:
- the number of submodules a single commit can declare,
- the recursion depth of nested submodules, or
- the amount of data/objects a submodule update must fetch and check out.

The underlying git process is started with `exec.CommandContext(ctx, ...)`, so the sync-timeout does correctly kill the git process when the deadline elapses [4](#0-3) , meaning a single sync attempt cannot hang forever. However, this only converts the vulnerability from "hang forever" into "always fail with a timeout error", which repeats indefinitely: the outer `for` loop re-enters `SyncRepo` on every period, re-attempts the same expensive submodule work, and fails again with `context.DeadlineExceeded` [5](#0-4) . The `--max-failures` mechanism only terminates the process after too many consecutive failures; it does not achieve a successful sync [6](#0-5) .

This is a direct analog to the reported bug: an attacker-controlled collection size (`vouchees` array length in the Solidity contract vs. submodule count/recursion depth in a git commit) is processed in full, in one shot, per invocation, with no cap, leading to resource-limit failure (gas exhaustion vs. wall-clock timeout) on every call.

### Impact Explanation
An attacker who can push (or otherwise get synced) a commit containing a very large number of submodules, or deeply/recursively nested submodules (including plausible submodule cycles across mirrors), can make `configureWorktree`'s submodule step consistently exceed `--sync-timeout`. This falls under the "persistent sync denial" impact category accepted by the validation rules: the sidecar can never successfully complete a sync for that ref, the published symlink is stuck on the last good (potentially stale) content, and the process either loops forever failing (if `--max-failures` is unset/negative) or exits after exhausting `--max-failures`, taking down the sidecar and, in Kubernetes, likely the pod via failed readiness/liveness checks. This is a legitimate, low-privilege-reachable denial-of-service: it requires nothing more than control over the content of the repository/ref that `git-sync` is configured to sync (the standard threat model for `git-sync`, which mirrors untrusted or semi-trusted upstream repo content).

### Likelihood Explanation
Likelihood is moderate: it requires write access to (or control of the ref pointed at) the source repository — the same "attacker-pushed commit" reachability class explicitly listed as in-scope. No special flags are required beyond the default `--submodules=recursive` behavior [7](#0-6) ; only a large or deeply-recursive submodule graph in the commit is needed. Operators using `--submodules=off` or a short/careful submodule tree are unaffected, and operators can partially mitigate by raising `--sync-timeout`, but there is no cap in the code itself, so the vulnerability is present by default configuration.

### Recommendation
- Introduce explicit caps/guardrails around submodule processing in `configureWorktree`, analogous to the "cap on vouchee size" recommendation: e.g., enumerate submodules first (`git submodule status` / `.gitmodules` parsing) and refuse or truncate/skip the sync (with a clear error) if the submodule count or recursion depth exceeds a configurable maximum, before invoking the expensive `submodule update --init --recursive`.
- Consider giving submodule operations their own sub-timeout / budget distinct from the overall `--sync-timeout`, so a single oversized submodule tree fails fast and predictably rather than always consuming the entire sync budget.
- Document and expose a `--max-submodules` / `--max-submodule-depth`-style flag so operators syncing untrusted repositories can bound worst-case work per sync cycle, matching the "put a cap on the number... do operations only up to a certain index" remediation from the original report, adapted to git-sync's per-sync submodule checkout.

### Proof of Concept
1. Create an upstream repository `REPO` that `git-sync` is configured to track with default settings (`--submodules` unset, i.e. `recursive`).
2. Commit a `.gitmodules` file referencing a very large number of submodule entries (e.g., thousands of tiny same-source submodules) or a submodule chain nested to a large depth (`sub/sub/sub/.../sub`), each adding real, checkout-required content.
3. Push this commit as the new tip of the ref `git-sync` follows.
4. Run `git-sync --repo=file://REPO --root=$ROOT --link=link --period=100ms --sync-timeout=<small value>` (or observe with the operator's existing `--sync-timeout`).
5. Observe that `configureWorktree`'s `git submodule update --init --recursive` step at [1](#0-0)  never completes within the timeout window; every `SyncRepo` call returns `context.DeadlineExceeded` from `runWithStdin` [8](#0-7) , the good-sync metric never increments, the `link` symlink is never updated to the new hash, and (depending on `--max-failures`) the process eventually exits non-zero — demonstrating persistent sync denial driven entirely by attacker-controlled repository content.

**Note on verification limits:** I was not able to inspect `.gitmodules` parsing logic (if any) or any other part of the codebase not surfaced by the indexed search, since the index only returns matching excerpts rather than full file contents; if finer-grained confirmation (e.g., whether any existing size/time guard exists elsewhere in `main.go` outside the reviewed ranges) is needed, a full-repo checkout via a Devin session would be required.
