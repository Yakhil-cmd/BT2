### Title
Cross-organization webhook signature confusion allows forging commit statuses / stack events for repositories outside the authenticating organization - (File: app/controllers/shipit/webhooks_controller.rb)

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's `webhook_secret` to validate a request against using `repository.owner.login` (or `organization.login`) from the request body, but the handlers invoked afterwards (e.g. `StatusHandler`, `PushHandler`) act on data (`sha`, `repository.full_name`) that is never checked against that same organization. In a multi-organization Shipit deployment (a documented, supported configuration), an attacker who legitimately administers *their own* onboarded GitHub organization/App (and therefore knows *their own* `webhook_secret`) can sign an arbitrary payload with that secret while setting the body's `repository`/`sha` fields to point at a target belonging to a completely different, victim organization's stack.

### Finding Description
The binding that should hold is:

`organization whose signature was verified == organization/repository whose state is mutated`

`verify_signature` picks the `GithubApp` instance purely from the attacker-controllable payload field `repository_owner`: [1](#0-0) [2](#0-1) 

Once the signature check passes (using the secret belonging to whichever org `repository_owner` names), the actual event handler is dispatched with the full raw payload and never re-validates that the organization that "owns" the credential used for verification matches the organization/repository that the handler subsequently mutates: [3](#0-2) 

`Handler#stacks` resolves the target purely from `repository.full_name` in the body, with no cross-check against `repository.owner.login`/the verified organization: [4](#0-3) 

`StatusHandler` is even less scoped: it looks up commits **globally by `sha`** with no repository or organization filter at all, then writes a GitHub-style status onto them: [5](#0-4) 

`PushHandler` similarly resolves target stacks from `stacks` (repository-name-derived) and unconditionally schedules a sync using the attacker-supplied `after` sha: [6](#0-5) 

Shipit explicitly documents and supports installing multiple independent GitHub Apps/organizations, each with its own `webhook_secret`, sharing the same `/webhooks` endpoint: [7](#0-6) 

Because the signature-selection key (`repository_owner`) and the mutation-target key (`repository.full_name` / global `sha`) are independent, unvalidated fields inside the same attacker-controlled JSON body, an operator of organization A (who legitimately knows organization A's `webhook_secret` because they configured their own GitHub App) can craft a POST to `/webhooks` where:
- `repository.owner.login` / `organization.login` = `"orgA"` → makes `verify_signature` succeed using orgA's secret (which the attacker legitimately possesses).
- `repository.full_name` = `"victim-org/victim-repo"` (for `PushHandler`, `check_suite`, PR handlers), or `sha` = a known commit sha belonging to a victim stack (for `StatusHandler`) → causes the dispatched handler to mutate state belonging to an organization the attacker never authenticated as.

This breaks exactly the class of binding called out in scope: "an organization that authenticated versus the repository that is written."

### Impact Explanation
Using `StatusHandler`, the attacker can inject arbitrary commit statuses (`state`, `context`, `description`, `target_url`) onto any commit tracked by Shipit, across any stack/organization, as long as they know the commit's 40-character sha — which is public GitHub information, and also derivable from the Shipit UI itself if stack state is readable. Forcing a commit's CI status to `success` can satisfy Shipit's CI-gating logic for deployability, which is used to unlock automatic/continuous deployment eligibility, giving the attacker a path toward an **unauthorized deploy** of a specific commit in a stack they have no legitimate access to. Using `PushHandler`/`check_suite`, the attacker can force `GithubSyncJob`/`RefreshCheckRunsJob` for a victim's stack using an attacker-chosen `after` sha, feeding falsified state into stack refresh logic. This crosses an organization/credential trust boundary without any repository write access, `ApiClient` token, or privileged Shipit session — the only thing required is administering one's own onboarded GitHub org, which is the baseline unprivileged position in a multi-tenant Shipit deployment.

### Likelihood Explanation
Requires: (1) a Shipit deployment configured with more than one GitHub organization (explicitly documented as supported), and (2) the attacker having legitimate/self-service control of one of those organizations' GitHub App + `webhook_secret` (a normal, unprivileged setup step, not "privileged account" in the sense of the victim's org). Given those, forging the request is a straightforward signed HTTP POST, requiring only knowledge of a target commit sha (public) or repo full name (public). No knowledge of the victim's secrets is required at any point.

### Recommendation
After `verify_signature` succeeds, bind the verified organization to the rest of the request: require that `repository.owner.login` (or `organization.login`) used for signature selection is the *only* organization the dispatched handler is permitted to mutate against, e.g. by having `Handler#stacks`/`StatusHandler` reject bodies whose `repository.owner.login` differs from the verified organization, and by scoping `StatusHandler`'s `Commit.where(sha:)` lookup to repositories belonging to that verified organization.

### Proof of Concept
1. Operator attacker has legitimately configured `orgA` in Shipit's multi-org `github:` config (own GitHub App, own `webhook_secret_A`, known to the attacker).
2. Attacker builds a JSON body mimicking a GitHub `status` event:
```json
{
  "sha": "<victim-stack-known-commit-sha>",
  "state": "success",
  "context": "ci/required-check",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/some-repo" }
}
```
3. Attacker computes `X-Hub-Signature: sha1=<hmac-sha1(webhook_secret_A, body)>` and POSTs it to `/webhooks` with `X-Github-Event: status`.
4. `verify_signature` resolves `repository_owner` = `"orgA"`, fetches `Shipit.github(organization: "orgA")`, and the signature validates successfully because it was computed with `webhook_secret_A`.
5. `StatusHandler#process` runs `Commit.where(sha: params.sha).each { |commit| commit.create_status_from_github!(params) }` — with no organization/repository filter, applying a forged `success` status to the victim commit regardless of which organization actually owns it.

### Using Multiple Github Applications

A Github application can only authenticate to the Github organization it's installed in. If you want to deploy code from multiple Github organizations the `github` section of your `config/secrets.yml` will need to be formatted differently. The top-level keys should be the name of each Github organization, and the following sub-keys are the Github app details for that particular organization.

```yml

  github:
    somegithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
        id:
        secret:
        teams:
    someothergithuborg:
      app_id:
      installation_id:
      webhook_secret:
      private_key:
      oauth:
