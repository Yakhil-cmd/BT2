### Title
Webhook organization used for signature verification is never bound to the repository/team actually mutated by the handler, allowing cross-organization state forgery and `Shipit.github_teams` escalation - ([File: app/controllers/shipit/webhooks_controller.rb], [File: app/models/shipit/webhooks/handlers/handler.rb], [File: app/models/shipit/webhooks/handlers/membership_handler.rb])

### Summary
`WebhooksController` selects which `GitHubApp` (and thus which `webhook_secret`) to verify a signature with using a value read directly from the untrusted, unverified JSON body (`repository.owner.login` / `organization.login`). Once that signature check passes, every downstream `Webhooks::Handlers::Handler` re-reads arbitrary fields from that *same* body (`repository.full_name`, `team.id`, `member.login`, etc.) to decide which `Stack`, `Repository`, or `Team` to mutate — with no check that those fields belong to the organization whose secret was actually verified. The binding "organization whose secret authenticated this request" == "organization/repository/team that gets written" is never enforced, exactly the same class of missing-equality-check bug as the reported `partial_close_position` vs `validate_close_position` case (a check that exists for one purpose is silently assumed to cover a different, unrelated target).

### Finding Description
`WebhooksController#verify_signature` derives the organization used to look up a webhook secret purely from the request body itself: [1](#0-0) [2](#0-1) 

Shipit explicitly supports multiple GitHub organizations, each with its own `GitHubApp` and its own `webhook_secret`, as documented and fixtured in `test/dummy/config/secrets_double_github_app.yml` and `docs/setup.md` ("Using Multiple Github Applications"). `Shipit.github(organization:)` picks the config for whatever `organization` string is supplied: [3](#0-2) 

Once `verify_webhook_signature` succeeds for the organization named in the body, `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params) }` hands the *entire raw body* to the handler. Every handler resolves its target purely from body fields, with `repository_owner`/`organization.login` discarded after the signature check and never consulted again: [4](#0-3) 

`MembershipHandler` is the most sensitive case: it resolves an arbitrary `Team` by `github_id` from the body and adds an arbitrary `User` (looked up/created purely by GitHub login string) as a member: [5](#0-4) [6](#0-5) 

Team membership is exactly what gates authenticated access to the whole engine: [7](#0-6) [8](#0-7) 

`PushHandler`/`CheckSuiteHandler` show the same pattern for stacks: they select `Stack` records purely by `payload.dig('repository', 'full_name')` and branch/sha fields from the body, and trigger `stack.sync_github`, `create_status_from_github!`, `schedule_refresh_check_runs!`, etc., with no re-check that the acted-on repository belongs to the organization whose secret was verified: [9](#0-8) [10](#0-9) 

`verify_webhook_signature` itself also short-circuits when an org has no secret configured — a documented, supported state (`webhook_secret: # nil` in `config/secrets.development.example.yml`): [11](#0-10) 

Combining these facts: in any multi-organization deployment where at least one configured organization has no `webhook_secret` set (an explicitly supported configuration shown in the shipped example secrets file), an unauthenticated caller can:
1. POST to `/webhooks` with `X-Github-Event: membership` and a body whose `repository.owner.login`/`organization.login` is set to that unsecured organization's name (so `verify_signature` trivially passes, per the `return true unless webhook_secret` branch).
2. Set `team.id` inside that same body to the `github_id` of a `Team` that is actually a member of `Shipit.github_teams` for a *different*, fully-secured organization, and set `member.login` to the attacker's own GitHub login.
3. `MembershipHandler#process` will create/add the attacker's `User` to that privileged `Team`, because no code anywhere checks that the team belongs to the organization that "authenticated" the webhook.
4. The attacker then completes GitHub OAuth login (`GithubAuthenticationController#callback` / `sign_in_github`), and `current_user.authorized?` now returns true because the attacker's `User` row is a member of a team in `Shipit.github_teams`.

This is a concrete break of the equality "organization that authenticated the webhook == organization whose Team/Repository/Stack gets written," matching the required binding classes in scope.

### Impact Explanation
Successful exploitation escalates an anonymous GitHub identity into `Shipit.github_teams` authorization — the exact "High" impact category defined for this engine ("escalation into `Shipit.github_teams` authorization"). Once authorized, the attacker gains full authenticated access to the Shipit UI/session for that installation: viewing/streaming task output, triggering deploys/rollbacks/tasks, and locking/unlocking stacks, since `Authentication#force_github_authentication` is the sole gate protecting the entire non-API surface of the engine.

### Likelihood Explanation
The precondition ("multi-org install, one org's `webhook_secret` unset") is a documented, first-class supported configuration shipped in this repo's own example (`config/secrets.development.example.yml`), not a hypothetical misconfiguration outside the engine's control — the vulnerable code path (`Handler#stacks`, `MembershipHandler#find_or_create_team!`) is exploitable purely by controlling JSON fields once *any* org's signature check is bypassable, and no additional credential, GitHub org membership, or API token is required. This makes exploitation practical wherever such a configuration exists, though it does require that specific per-organization webhook-secret gap; I could not find any code path that lets an attacker forge cross-organization payloads when *every* configured organization's `webhook_secret` is set, since GitHub's real HMAC would then bind the entire (organization-consistent) body.

### Recommendation
Bind the verified organization to every object the handler subsequently mutates:
- Pass the verified `repository_owner`/organization down to `Shipit::Webhooks.for_event(event).each { |handler| handler.call(params, verified_organization) }`.
- In `Webhooks::Handlers::Handler#stacks`, additionally assert that the resolved `Repository#owner` matches the verified organization before returning any stacks.
- In `MembershipHandler`, assert that the resolved `Team#organization` matches the verified organization before calling `team.add_member`/`team.members.delete`.
- Treat "no `webhook_secret` configured for an organization" as equivalent to "any body claiming that organization is untrusted," i.e. never allow handlers acting on behalf of an unsecured organization to write to entities scoped to other organizations.

### Proof of Concept
Preconditions: a Shipit instance configured with `github.OrgA` (no `webhook_secret`, i.e. `verify_webhook_signature` always returns `true` for it) and `github.OrgB` (secured, with a `Team` in `Shipit.github_teams`, e.g. `github_id: 999`).

```
POST /webhooks HTTP/1.1
X-Github-Event: membership
Content-Type: application/json

{
  "action": "added",
  "organization": { "login": "OrgA" },
  "team": { "id": 999, "name": "Developers", "slug": "developers", "url": "https://example.com" },
  "member": { "login": "attacker-github-login" }
}
```
`verify_signature` resolves `Shipit.github(organization: "OrgA")`, whose `webhook_secret` is unset, so `verify_webhook_signature` returns `true` regardless of any `X-Hub-Signature` header. `MembershipHandler` then finds/creates `Team` with `github_id: 999` (OrgB's privileged team) and adds `attacker-github-login` as a member, per [5](#0-4) . The attacker subsequently logs in via `/github/auth` with `attacker-github-login`, and `current_user.authorized?` (`app/models/shipit/user.rb:80-82`) returns `true`, granting full access to the deployment engine.

  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
