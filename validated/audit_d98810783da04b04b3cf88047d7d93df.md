### Title
Webhook Signature Is Verified Against the Organization Named in the Payload While Handlers Act on a Different, Unverified Repository/Commit — Cross-Organization Forgery (- [File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects which GitHub App/organization secret to check the HMAC signature against using an attacker-supplied field of the same unauthenticated JSON body it is about to verify, while the event handlers that subsequently execute act on a completely different attacker-supplied field (or no repository scoping at all). This is the shipit-engine analog of the external report's "mismatch between parameters used to authorize vs. parameters used to execute": the organization whose secret authenticates the request is not bound to the repository/commit the request actually mutates.

### Finding Description
`verify_signature` computes the org used for secret lookup purely from the payload, before/independently of verifying its own signature: [1](#0-0) [2](#0-1) 

`Shipit.github(organization:)` resolves a distinct `webhook_secret` per organization from `secrets.github` in multi-org deployments (explicitly documented and supported): [3](#0-2) 

The actual signature check (`verify_webhook_signature`) only proves that *some* holder of `organization`'s secret produced this exact raw body — it says nothing about which repository the body's other fields describe: [4](#0-3) 

Once verification passes, handlers are dispatched with the full, self-declared payload: [5](#0-4) 

Most handlers resolve the target `Repository`/`Stack` from a *different* JSON field, `repository.full_name`, than the one used for signature-secret selection (`repository.owner.login`): [6](#0-5) 

`StatusHandler` is worse still — it performs **no repository scoping whatsoever**, matching purely on `sha` across the entire instance: [7](#0-6) 

The broken equality: `organization authenticated by verify_signature (payload.repository.owner.login)` ≠ `repository/commit actually written by the handler (payload.repository.full_name / params.sha)`. Both sides of that equality are drawn from the same attacker-authored request body, so nothing forces them to refer to the same GitHub organization or repository.

### Impact Explanation
In a multi-organization Shipit installation, anyone who knows the `webhook_secret` for organization A (e.g., an admin of the GitHub App installed on their own, unrelated org A) can HMAC-sign an arbitrary crafted body with A's secret while setting `repository.owner.login` to A (to pass secret selection) and setting `repository.full_name`, or an arbitrary `sha`, to point at a stack/commit belonging to a completely unrelated organization B tracked by the same Shipit instance. This lets the attacker:
- Inject arbitrary commit statuses (`state`, `description`, `target_url`) for any commit by sha in any stack via `StatusHandler`, bypassing CI/CD gating checks that `deployable_status`/`Shipit.github_teams`-gated deploys rely on, and
- Trigger `GithubSyncJob`/other side effects for repositories the requester has no relationship to.

This crosses the "cross-repository writes" / "unauthorized deploy" impact bar because it lets a party authenticated only for org A's webhook channel affect deploy-gating state of org B's stacks.

### Likelihood Explanation
Requires the multi-org webhook configuration Shipit itself documents and ships support for (`docs/setup.md`, `lib/shipit.rb#github_app_config`), and requires the attacker to legitimately hold one organization's `webhook_secret` (e.g., as an admin of their own org's GitHub App installation) — no repository write access or GitHub token theft needed for the *target* org. Given this is a documented supported configuration and the code contains no cross-check binding the authenticated organization to the acted-upon repository, likelihood is realistic in any multi-tenant deployment.

### Recommendation
After `verify_signature` succeeds, additionally verify that `repository.full_name` (or the commit's owning stack/repository) actually belongs to the same `repository_owner`/organization whose secret validated the signature, and reject the webhook otherwise. `StatusHandler` in particular should scope `Commit.where(sha:)` lookups to repositories owned by the verified organization rather than matching globally by `sha`.

### Proof of Concept
1. Deploy Shipit with multi-org config: `secrets.github` containing `orgA` and `orgB`, each with its own `webhook_secret`, and stacks tracked for both `orgA/repo1` and `orgB/repo2` (per `docs/setup.md` multi-org schema).
2. As a party who legitimately knows `orgA`'s `webhook_secret` (e.g., an admin of the GitHub App installed on orgA), craft a JSON body:
```json
{
  "sha": "<commit-sha-belonging-to-orgB/repo2>",
  "state": "success",
  "repository": { "owner": { "login": "orgA" }, "full_name": "orgA/repo1" }
}
```
3. Compute `X-Hub-Signature: sha1=<hmac-sha1(orgA_webhook_secret, raw_body)>` and POST to `/webhooks` with `X-Github-Event: status`.
4. `WebhooksController#verify_signature` resolves `repository_owner` = `"orgA"`, fetches `orgA`'s secret via `Shipit.github(organization: "orgA")`, and the signature verifies successfully (`app/controllers/shipit/webhooks_controller.rb:24-30`).
5. `StatusHandler#process` runs `Commit.where(sha: params.sha)` (`app/models/shipit/webhooks/handlers/status_handler.rb:21`), which matches the commit under `orgB/repo2` regardless of the `repository` field, and calls `commit.create_status_from_github!(params)`, writing an attacker-chosen commit status onto a stack belonging to `orgB`, an organization the attacker was never authenticated for.

```ruby
  def github(organization: github_default_organization)
    # Backward compatibility
    # nil signifies the single github app config schema is being used
    if github_default_organization.nil?
      config = secrets.github
    else
      config = github_app_config(organization)
      raise GithubOrganizationUnknown, organization if config.nil?
    end
    @github ||= {}
    @github[organization] ||= GitHubApp.new(organization, config)
  end

  def github_default_organization
    return nil unless secrets&.github

    org = secrets.github.keys.first
    TOP_LEVEL_GH_KEYS.include?(org) ? nil : org
  end

  def github_organizations
    return [nil] unless github_default_organization

    secrets.github.keys
  end

  def github_app_config(organization)
    github_config = secrets.github.deep_transform_keys(&:downcase)
    github_organization = organization.downcase.to_sym
    github_config[github_organization]
  end
```

```ruby
    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
```
