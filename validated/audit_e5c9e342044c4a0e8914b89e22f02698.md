This confirms the exploit chain: `StatusHandler#process` at [1](#0-0)  creates a `Status` directly from unvalidated webhook payload fields (`sha`, `state`, `context`, etc.) with no cross-check against GitHub's API. A created `success` status triggers `schedule_continuous_delivery` and `stack.schedule_merges` via `Status#schedule_continuous_delivery` and `Commit#add_status` at [2](#0-1) [3](#0-2) , which can trigger an actual deploy through `Stack#trigger_continuous_delivery` at [4](#0-3) .

The critical binding break is in `WebhooksController`: signature verification is keyed on `repository_owner` (derived from `payload.dig('repository','owner','login')` or `payload.dig('organization','login')`), while every `Handler` subclass (e.g. `PushHandler`, `StatusHandler`) locates the target `Stack`/`Commit` using a *different* payload field, `repository.full_name`, via `Handler#repository_name` at [5](#0-4) . In a multi-organization deployment (`docs/setup.md` "Using Multiple Github Applications", `lib/shipit.rb` `github_app_config`), each org has its own `webhook_secret`, and critically `verify_webhook_signature` returns `true` unconditionally when that org's `webhook_secret` is blank: [6](#0-5) .

Given that setup, an attacker who knows (or picks) an org name with no configured secret can set `repository.owner.login` to that org (satisfying `verify_signature`) while setting `repository.full_name` to a *different, secured* org/repo that Shipit tracks. The signature check never inspects `full_name`, so the request "authenticates" for org verification purposes yet mutates state for an unrelated repository — exactly the equality break the report describes (`repository.owner.login` is what's checked ≠ `repository.full_name` is what's acted on).

### Title
Webhook signature verification is bound to `repository.owner.login` while state mutation is bound to `repository.full_name`, allowing unauthorized status/deploy forgery across organizations - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects the GitHub App/secret to validate a webhook against using `repository.owner.login` (falling back to `organization.login`), but every webhook `Handler` (including `StatusHandler` and `PushHandler`) resolves the target `Stack`/`Commit` using the unrelated `repository.full_name` field from the same attacker-controlled JSON body. When any configured organization in a multi-org Shipit deployment has no `webhook_secret` set, `verify_webhook_signature` returns `true` unconditionally for requests "belonging" to that org, letting an attacker forge a webhook that is accepted because of one org field but that mutates a `Stack` belonging to an entirely different, secured organization.

### Finding Description
- `WebhooksController#verify_signature` computes `repository_owner` from the payload and looks up the matching `GitHubApp`/secret via `Shipit.github(organization: repository_owner)`: [7](#0-6) .
- `repository_owner` is `params.dig('repository','owner','login') || params.dig('organization','login')`: [8](#0-7) .
- `GitHubApp#verify_webhook_signature` returns `true` without checking the signature at all when the org's `webhook_secret` is not configured: [6](#0-5) .
- After "verification", `Handler#repository_name` (used by all handlers to resolve which `Stack`/`Repository` to act on) reads a *different* field, `repository.full_name`: [5](#0-4) .
- `StatusHandler#process` creates a `Status` on any `Commit` matching the attacker-supplied `sha`, using attacker-controlled `state`/`context`/`description` fields with no independent verification against GitHub: [1](#0-0) .
- Creating a `success` status schedules continuous delivery and merges: [2](#0-1) , [9](#0-8) , [3](#0-2) , which can invoke `Stack#trigger_continuous_delivery` and produce an actual, unauthorized deploy: [4](#0-3) .

The result is the exact "binding mismatch" bug class from the report: the field the verification step checks (`repository.owner.login`) is never the field the handler acts on (`repository.full_name`), and an attacker can freely diverge the two within a single unauthenticated (no session/token required) POST to `/webhooks`.

### Impact Explanation
This crosses the High/Critical bar: it enables an unauthenticated attacker to forge a CI status on a commit belonging to a protected, unrelated stack, which can trigger an unauthorized deploy or merge (`Stack#trigger_continuous_delivery`, `stack.schedule_merges`) — matching the report's "unauthorized deploy, rollback or merge" impact category. It effectively defeats the webhook signature scheme's intended guarantee that only GitHub (holding the shared secret for a given org) can mutate that org's stacks.

### Likelihood Explanation
Exploitability is fully dependent on the deployment having at least one configured organization with no `webhook_secret` (documented as a supported, valid configuration in `docs/setup.md`/`config/secrets.development.example.yml`) alongside at least one other, secured organization/stack the attacker wants to target. This is a realistic operational configuration (e.g., a test/staging org intentionally left without a secret), and no privileged credential is required to exploit it — the webhook endpoint is unauthenticated by design (`skip_before_action :verify_authenticity_token`) and reachable directly by POST.

### Recommendation
Bind the field used to select the verifying GitHub App/secret to the same field used to resolve the target repository (`repository.full_name`'s owner segment), and require a `webhook_secret` be present for every configured organization (rejecting requests when it's absent instead of treating them as auto-verified). Additionally, `Handler#repository_name`/`repository_owner` should be reconciled — the org implied by `full_name` should be validated to equal the org used for signature verification before any handler is dispatched.

### Proof of Concept
1. Configure Shipit with two organizations: `PublicOrg` (no `webhook_secret` set) and `PrivateOrg` (secret configured, has a tracked `Stack`/`Commit` for repo `PrivateOrg/secret-repo`).
2. POST to `/webhooks` with header `X-Github-Event: status` and no valid `X-Hub-Signature`, body:
```json
{
  "repository": { "owner": { "login": "PublicOrg" }, "full_name": "PrivateOrg/secret-repo" },
  "sha": "<sha of an undeployed commit on PrivateOrg/secret-repo>",
  "state": "success",
  "context": "ci/forged"
}
```
3. `verify_signature` computes `repository_owner = "PublicOrg"`, looks up `PublicOrg`'s `GitHubApp`, and `verify_webhook_signature` returns `true` unconditionally (`webhook_secret` blank).
4. `StatusHandler` resolves the commit via `sha` (independent of `repository_owner`) and creates a `success` `Status` on it, which schedules continuous delivery / merges for the `PrivateOrg` stack — an unauthorized deploy/merge triggered without ever presenting a valid signature for `PrivateOrg`.
