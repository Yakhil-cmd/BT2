### Title
CCMenuController bypasses ApiClient stack-scoping, letting a stack-scoped token read any stack - ([File: app/controllers/shipit/api/ccmenu_controller.rb])

### Summary
`Shipit::ApiClient#authentication_token` signs only the client `id`, and `Shipit::ApiClient.authenticate` looks the client up purely by `id`, with no stack binding in the signed payload. This is normally mitigated by `Api::BaseController#stack`, which restricts lookups to `current_api_client.stack_id` when that column is set. `Api::CCMenuController` overrides `stack` with an unscoped `Stack.from_param!(params[:stack_id])`, entirely skipping this restriction, so any valid token with `read:stack` permission - even one explicitly scoped to a single stack via `ApiClient#stack` - can read the CCMenu status of any other stack.

### Finding Description
The binding that should hold is: `token.client.stack_id == requested_stack.id` (or `nil` meaning "all stacks"), enforced identically everywhere a stack-scoped client is used.

- `ApiClient#authentication_token` signs only `id`: [1](#0-0) 
- `ApiClient.authenticate` resolves the client strictly by `id`, with no stack check: [2](#0-1) 
- The generic API controller enforces the stack binding by filtering the lookup scope through `current_api_client.stack_id`: [3](#0-2) 
- `Api::CCMenuController` overrides `stack` with an unscoped lookup, bypassing that filter, and also implements its own `authenticate_api_client` that accepts `params[:token]` directly: [4](#0-3) 
- `require_permission :read, :stack` only checks the permission string, never the target stack: [5](#0-4) 

The fixture `here_come_the_walrus` demonstrates that `ApiClient` is designed to support per-stack scoping (`belongs_to :stack, optional: true`) via a `stack:` association: [6](#0-5) . That scoping is honored by `BaseController#stack`/`#stacks` for every other API endpoint, but `CCMenuController#stack` silently discards it, so a client explicitly restricted to stack A still succeeds against stack B's CCMenu endpoint.

Attacker flow: the attacker obtains any valid CCMenu-style token (e.g. via `Shipit::CCMenuUrlController#fetch`, which mints/reuses a `read:stack`-permissioned `ApiClient` without a `stack` value at all): [7](#0-6) . They then replay that same `token` query parameter against `GET /api/stacks/*other_stack_id/ccmenu` for a stack_id they were never issued the URL for. `ApiClient.authenticate` succeeds (valid signature, existing id), `check_permissions!(:read, :stack)` passes (permission is `read:stack`, scope-agnostic), and `CCMenuController#stack` resolves any stack_id unconditionally, returning 200 with real build/deploy state for the other stack.

### Impact Explanation
This yields unauthorized/unauthenticated-in-effect disclosure of stack state (latest deploy/rollback status, lock state, build labels) for a repository the token was never scoped to, matching the "High - unauthenticated read of stack state, task streams or deploy output" category. It is fully repeatable: the same token works against every `stack_id` on the instance, for as long as the `ApiClient` row exists and `Shipit.api_clients_secret` is unchanged - it does not require an active Shipit session, and does not re-check current github-team membership on each use, so it also survives revocation of the original user's org access. Blast radius is instance-wide (every stack, cross-tenant if repos have different sensitivity), though it is confined to read access via CCMenu's rendered XML view.

### Likelihood Explanation
Preconditions are default configuration: `Shipit.api_clients_secret` unchanged (default deployment), CCMenu feature enabled/used (default routes present), and the attacker only needs to have once legitimately obtained one CCMenu URL for one stack (a normal, low-privilege UI action available to any authorized Shipit user). No secrets, admin role, or elevated permission is required beyond that one-time normal token issuance. Cost is a single crafted HTTP GET with a substituted `stack_id` in the path - trivially repeatable against every stack.

### Recommendation
Make `CCMenuController#stack` honor the same client-scoping used by `BaseController`, e.g. replace the `stack` override with the inherited `stacks.from_param!(params[:stack_id])` (or explicitly check `current_api_client.stack_id.nil? || current_api_client.stack_id == resolved_stack.id`), and/or bind the signed token to the specific stack (embed and verify `stack_id` in `SimpleMessageVerifier` payload) rather than trusting the bare permission flag.

### Proof of Concept
In `test/controllers/api/ccmenu_controller_test.rb` (or a new test file):
1. Use fixture `here_come_the_walrus` (`shipit_api_clients(:here_come_the_walrus)`), which has `stack: shipit` and `read:stack` permission - assert precondition `client.stack_id == shipit_stacks(:shipit).id`.
2. Create/use a second stack, e.g. `other_stack = Stack.create!(repository: Repository.new(owner: 'foo', name: 'bar'), branch: 'main')`, and assert `client.stack_id != other_stack.id`.
3. `get :show, params: { stack_id: other_stack.to_param, token: client.authentication_token }`.
4. Assert the response is `:ok` (200) and returns `other_stack`'s CCMenu XML - demonstrating that the client scoped to `shipit` successfully read a stack it was never bound to, in contradiction to the binding `client.stack_id == requested_stack.id`, and contrast with an equivalent request through `Api::StacksController#show` (which uses the inherited `BaseController#stack` and correctly returns 403/404 for the same client/other_stack pair) to prove the divergence is specific to `CCMenuController`.
