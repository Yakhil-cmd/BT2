### Title
Webhook signature verification selects the wrong GitHub App via an attacker-controlled `repository.owner.login`/`organization.login`, allowing unauthenticated forgery of `status`/`push`/`pull_request` events - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` chooses which `GitHubApp` (and therefore which `webhook_secret`) to validate an inbound webhook's HMAC signature against by reading an unauthenticated field straight out of the still-unverified JSON body. In a multi-organization Shipit deployment, if any configured organization has no `webhook_secret` set, `GitHubApp#verify_webhook_signature` unconditionally returns `true` for it. An unprivileged attacker can therefore pick that low-security organization as `repository.owner.login` to pass signature verification, while the event handlers act on a completely independent, equally attacker-controlled field (`repository.full_name`, or nothing at all in the case of `status`) to decide which `Stack`/`Commit` gets mutated.

### Finding Description
`verify_signature` resolves the signing app from the payload before the payload has been authenticated: [1](#0-0) 

`repository_owner` is read directly from the untrusted JSON body: [2](#0-1) 

`GitHubApp#verify_webhook_signature` skips verification entirely when the resolved app has no configured secret: [3](#0-2) 

Shipit explicitly supports multiple GitHub Apps for multiple organizations sharing one instance, each with its own (optionally blank) `webhook_secret`: [4](#0-3) [5](#0-4) 

Once the (possibly unverified) request passes, `create` dispatches to per-event handlers using a *second*, independently-controlled payload field, breaking the binding between "the organization whose secret authenticated this request" and "the repository the handler actually mutates": [6](#0-5) [7](#0-6) 

The `status` handler is the most severe case: it doesn't even use `repository.full_name` — it matches purely by commit SHA across the entire instance, with no repository/org scoping at all: [8](#0-7) 

`push` and `pull_request` handlers use `repository.full_name` (a third attacker-controlled field, never cross-checked against `repository_owner`) to look up the target `Repository`/`Stack`: [9](#0-8) [10](#0-9) 

**Equality broken**: `organization authenticated (repository_owner used to pick the verifying webhook_secret)` ≠ `repository actually written (repository.full_name / bare commit sha used by the handler)`.

### Impact Explanation
An unprivileged external attacker who knows (a) that the target Shipit instance manages a multi-org config where at least one configured organization has no `webhook_secret`, and (b) a target commit SHA or repository full name tracked by Shipit, can send an unsigned/arbitrarily-signed POST to `/webhooks` claiming `repository.owner.login` = the secret-less org. This bypasses HMAC verification entirely (`return true unless webhook_secret`) and lets the attacker:
- Forge `status` events, writing fabricated CI/build states (`create_status_from_github!`) onto *any* commit in *any* stack on the instance purely by SHA, with zero repository check — this can flip a commit's status to a passing state and feed Shipit's deploy-readiness/merge-queue checks with forged data, contributing to an unauthorized deploy or merge decision.
- Forge `push` events to trigger `GithubSyncJob` against arbitrary tracked stacks.
- Forge `pull_request` events to provision/archive review stacks for arbitrary repositories via `ReviewStackAdapter`.

This crosses the authentication boundary the signature check exists to enforce and can influence stack/commit state that feeds deploy and merge decisions, matching the report's core bug class (a permissionless entry point whose "predictable"/attacker-influenced input can be leveraged for a forced, unauthorized state change) transplanted onto Shipit's webhook trust boundary.

### Likelihood Explanation
Exploitability is conditioned on the deployment using the multi-organization GitHub App configuration with at least one organization lacking a `webhook_secret` — a configuration explicitly documented and exercised in the engine's own test fixtures (`test/dummy/config/secrets_double_github_app.yml`, `config/secrets.development.example.yml`), i.e. this is a supported/blessed configuration shape, not a misuse of the engine. Given that shape, no credentials, tokens, or session are required — only knowledge of `/webhooks`, an org name with no secret, and a target commit SHA (public in git history) or repository full name (public).

### Recommendation
- Verify the webhook signature using the secret of the organization that actually owns the affected repository, not a name chosen from the same unauthenticated payload used to select handlers.
- Do not treat a missing `webhook_secret` as "verification passes"; instead require an explicit, deployment-wide opt-in for unsigned orgs, and never let an unsigned org's identity be substitutable for a signed org's.
- In every handler, cross-check that the resolved `Repository`/`Stack`'s owning organization matches the organization whose secret validated the request (bind `repository_owner` to `repository.full_name`'s owner segment) before mutating any state.
- Scope `StatusHandler#process` to the repository indicated in the payload (and validate it against the authenticated organization) instead of matching commits by bare SHA instance-wide.

### Proof of Concept
1. Configure Shipit with two organizations, e.g. `OrgSecure` (has `webhook_secret: s3cr3t`, owns tracked repo `OrgSecure/app`) and `OrgOpen` (no `webhook_secret` configured), per the supported multi-app config in `docs/setup.md`.
2. Attacker sends, with no valid `X-Hub-Signature` (or any bogus value):
```
POST /webhooks
X-Github-Event: status

{
  "sha": "<known-sha-of-a-commit-in-OrgSecure/app>",
  "state": "success",
  "context": "ci/forged",
  "repository": { "owner": { "login": "OrgOpen" }, "full_name": "OrgOpen/whatever" }
}
```
3. `verify_signature` resolves `Shipit.github(organization: "OrgOpen")`; `verify_webhook_signature` returns `true` because `OrgOpen`'s `webhook_secret` is blank — no signature check is actually performed.
4. `StatusHandler#process` runs `Commit.where(sha: params.sha)` and writes a forged `success` status onto the `OrgSecure/app` commit, with no relation to `OrgOpen` ever verified.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
