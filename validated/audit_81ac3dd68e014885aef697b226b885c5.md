### Title
Fixed benchmarked weight for `remote_proxy`/`remote_proxy_with_registered_proof` does not scale with attacker-supplied `proof: Vec<Vec<u8>>` size, allowing weight/PoV griefing - (File: pallets/remote-proxy/src/lib.rs)

### Summary
The `#[pallet::weight]` closures for `Pallet::remote_proxy` and `Pallet::remote_proxy_with_registered_proof` charge a flat `WeightInfoOf::<T, I>::remote_proxy()` (benchmarked with a minimal, single-entry trie proof) plus the inner call's `di.call_weight`, but never account for the size of the caller-supplied `proof` field. `do_remote_proxy` then runs `sp_trie::StorageProof::new(proof).into_memory_db()` and `sp_trie::read_trie_value` over that same attacker-controlled `proof`, so an arbitrarily large/malformed proof can consume far more compute and PoV than what was declared/paid for.

### Finding Description
`Pallet::remote_proxy` is dispatchable by any signed account: [1](#0-0) 

Its weight annotation is: [2](#0-1) 

`di.call_weight` only reflects the weight of the wrapped `call` (e.g. `remark`), not the cost of processing `proof`. The actual proof-processing work happens in `do_remote_proxy`: [3](#0-2) 

`proof: Vec<Vec<u8>>` is fully attacker-controlled and unbounded except by generic extrinsic-length/PoV limits (there is no pallet-level `MaxEncodedLen`/bound on the number or size of proof nodes). `sp_trie::StorageProof::new(proof).into_memory_db()` hashes and inserts every node into an in-memory trie DB, and `read_trie_value` traverses/decodes nodes — both scale with the number and size of nodes supplied, not with the single benchmarked proof used to produce `WeightInfoOf::remote_proxy()`.

The benchmark that generates the charged weight uses a trivial proof from `create_remote_proxy_proof`, confirmed by the generated weights showing a small fixed `Estimated` PoV (`1846` bytes) and short execution time (~18µs): [4](#0-3) [5](#0-4) 

Because the proof is only decoded/verified inside `do_remote_proxy` (i.e., during actual dispatch, after weight has already been reserved/charged based on the flat benchmark), the pallet's weight system has no mechanism that scales with `proof.len()` or node sizes. This is a genuine mismatch between declared weight and worst-case execution cost.

`remote_proxy_with_registered_proof` has the same flaw, since it also calls `do_remote_proxy` after a proof was registered via `register_remote_proxy_proof` (which is charged only `WeightInfoOf::register_remote_proxy_proof()`, itself a flat, tiny weight with no scaling by proof size either): [6](#0-5) [7](#0-6) 

Mitigating factors that reduce but do not eliminate the issue:
- The extrinsic's encoded length (which includes the serialized proof) is charged a length fee via `TransactionByteFee`, and is bounded by `BlockLength`/max extrinsic size, so the proof cannot be truly unbounded — it's capped by whatever the runtime's max extrinsic/PoV size is.
- Failures (`InvalidProof`, decode errors) still consume the reserved weight/fee under normal FRAME semantics, so the caller "pays" declared fee regardless of proof validity — but the point of the audit question is that *actual compute* can exceed the *declared weight*, not that the attacker gets a free ride on fees.

No check in the code path bounds or weighs `proof` proportionally before invoking `sp_trie::read_trie_value`; the origin check (`ensure_signed`) and storage-root lookup (`BlockToRoot`) do not limit proof size.

### Impact Explanation
An unprivileged signed account can submit `remote_proxy` with a `proof` containing many large, fabricated/duplicate trie nodes (up to the max extrinsic length/PoV limit), causing `into_memory_db()`/`read_trie_value` to perform hashing/decoding work proportional to that size while only being charged the small flat `WeightInfoOf::remote_proxy()` component. This is a weight/PoV-accounting asymmetry: the block's actual execution time and/or storage-proof/PoV consumption can exceed what was reserved for the extrinsic, which is a violation of the invariant that declared weight upper-bounds actual execution cost. The scoped impact is block-weight/PoV griefing at a fee cost proportional only to extrinsic length, not to the trie-processing cost incurred.

### Likelihood Explanation
Feasible and repeatable by any signed, unprivileged account with only enough balance to pay the fee for an extrinsic of the size they submit (bounded by the runtime's max extrinsic/PoV limits). No special permission or filtering blocks this — `ensure_signed` is the only origin check, and the proof is deserialized/processed unconditionally before the (already loose) UnknownProofAnchorBlock / InvalidProof checks reject it. Repeating this call across many transactions in a block increases the effect.

### Recommendation
Make the weight of `remote_proxy` / `remote_proxy_with_registered_proof` / `register_remote_proxy_proof` scale with the size of the supplied `proof` (e.g., benchmark `read_trie_value`/`into_memory_db` cost per node/byte and add a linear component based on `proof.iter().map(|n| n.len()).sum()` and node count), and/or enforce a hard cap on the number of proof nodes and per-node size (rejecting proofs larger than what a legitimate remote-proxy storage proof could plausibly require) before doing any trie processing.

### Proof of Concept
Rust benchmark/fuzz-style test in `pallets/remote-proxy/src/tests.rs`:
1. Construct a valid anchor block/storage root via `BlockToRoot::<T, I>::set(...)` as in existing tests.
2. Build `proof: Vec<Vec<u8>>` with N large fabricated byte vectors (e.g., 10_000 entries of ~1KB random/duplicate bytes) that do not need to be a valid trie (since `read_trie_value` will still traverse/hash all nodes before returning an error/`InvalidProof`).
3. Measure wall-clock (or use `frame_benchmarking`'s timing) of `Pallet::do_remote_proxy` (or the public `remote_proxy` extrinsic) with this proof vs. with the benchmark's minimal proof.
4. Assert: `actual_execution_time(large_proof) <= WeightInfoOf::<T, I>::remote_proxy().ref_time()` fails (i.e., actual time significantly exceeds the flat declared weight), demonstrating the weight/execution mismatch.
5. Optionally assert PoV/proof-size growth: compare `sp_trie::StorageProof::new(proof).encoded_size()` against the `Estimated` proof size baked into `WeightInfo::remote_proxy()` (`1846` bytes) to show the estimated proof size is exceeded by orders of magnitude for large N.
