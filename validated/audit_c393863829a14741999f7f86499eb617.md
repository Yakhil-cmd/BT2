### Title

Third-party dust supply restamps collateral risk parameters and enables forced liquidation - ([File: contracts/controller/src/positions/supply.rs])

### Summary

An unprivileged caller can supply a dust amount into an asset already held by another account. That call bypasses owner/delegate authorization and refreshes the target position’s full risk tuple with current spoke-asset parameters, even though the intended permissionless threshold-refresh path applies a post-refresh health-factor gate for gated liquidation parameters. A governance tightening can therefore make a previously healthy account liquidatable through an unauthorized dust deposit.

### Finding Description

`supply` authenticates only the paying caller and uses `AccountGuard::Supply`, which checks only that the supplied spoke matches an existing account rather than requiring ownership or delegation. [1](#0-0) [2](#0-1) 

For a third-party caller, `require_third_party_existing_supply` checks only that every submitted `HubAssetKey` already exists in the victim’s supply map. [3](#0-2) 

The deposit path then calls `merge_supply_leg`, which refreshes the existing position’s risk parameters using `RiskRefreshScope::FullTuple` before storing the updated scaled balance. [4](#0-3) [5](#0-4) 

By contrast, the documented `update_account_threshold` path refreshes gated liquidation parameters only when `has_risks` is set and requires a final health factor of at least 1.05 WAD. [6](#0-5) 

### Impact Explanation

If governance lowers an asset’s LTV or liquidation threshold after the victim’s position was last restamped, the attacker can spend only the smallest accepted amount of the already-held collateral token to restamp the entire victim position. The dust deposit can reduce the account’s health factor below 1.0 even though the nominal collateral balance increases, after which the attacker can call `liquidate` and receive collateral with the liquidation bonus. This converts an authorization bypass into theft of user collateral through forced liquidation.

### Likelihood Explanation

The attack is permissionless and requires only an existing supply position plus a transferable dust amount. It needs a stale favorable position tuple followed by a legitimate risk-parameter tightening, and the victim must be sufficiently close to liquidation for the restamp to push the health factor below 1.0. Those conditions are realistic during collateral downgrades or protocol risk tightening, but are not always present, so the practical severity is **Medium**.

### Recommendation

Do not let an unauthorized third-party supply restamp a victim’s risk tuple. Either restrict existing-account `supply` to the owner or an active delegate, or add a third-party path that credits the deposit while preserving the stored risk tuple. If the intended policy is that anyone may restamp positions, route the refresh through the same gated validation used by `update_account_threshold` and verify that the account remains safely above liquidation after the refresh.

### Proof of Concept

1. A victim owns `account_id = V` in `spoke_id = S` and has an existing supply position for `hub_asset = H`.
2. Governance legitimately tightens `H`’s collateral parameters for `S`; `V` retains its older, more favorable cached position tuple until it is restamped.
3. An attacker authorizes:
   ```text
   supply(
       caller = attacker,
       account_id = V,
       spoke_id = S,
       assets = [(H, 1)]
   )
   ```
   The call passes because `account_id != 0`, `H` is already in `V`’s supply map, and no owner/delegate check is applied to that existing-position top-up. [7](#0-6) 
4. `process_deposit` merges the leg and `merge_supply_leg` invokes `refresh_supply_risk_params` with `RiskRefreshScope::FullTuple`, applying the tightened parameters to the victim’s entire `H` position rather than only accounting for the one-unit deposit. [8](#0-7) 
5. Once the restamped position has `get_health_factor(V) < 1.0`, the attacker calls:
   ```text
   liquidate(
       liquidator = attacker,
       account_id = V,
       debt_payments = [(victim_debt_asset, repayment_amount)],
       seize_mode = SeizeMode::Transfer
   )
   ```
   and receives the seized collateral including the configured liquidation bonus.

pub(crate) fn load_or_create_account(
    env: &Env,
    caller: &Address,
    account_id: u64,
    spoke_id: u32,
    mode: PositionMode,
    guard: AccountGuard,
    cache: &mut Context,
) -> (u64, Account) {
    if account_id == 0 {
        return create_account(env, caller, spoke_id, mode, cache);
    }
    let account = storage::get_account(env, account_id);
    match guard {
        AccountGuard::Supply => require_spoke_match(env, &account, spoke_id),
        AccountGuard::Migrate => {
            require_owner_or_delegate(env, account_id, caller, &account.owner);
            require_spoke_match(env, &account, spoke_id);
        }
        AccountGuard::Multiply => {
            require_owner_or_delegate(env, account_id, caller, &account.owner);
            require_spoke_match(env, &account, spoke_id);
            assert_with_error!(env, account.mode == mode, GenericError::AccountModeMismatch);
        }
    }
