I found a genuine analog vulnerability: the API `CCMenuController` bypasses the token-to-stack scoping enforced everywhere else in the API.### Title
API CCMenu endpoint bypasses ApiClient stack scoping, allowing a stack-scoped token to read any stack's deploy status - (File: app/controllers/shipit/api/ccmenu_controller.rb)

### Summary
The `ApiClient` model supports scoping a token to a single `stack_id`, and `Shipit::Api::BaseController#stack` enforces that scope by resolving stacks through `stacks.from_param!` (which restricts to `Stack.where(id: current_api_client.stack_id)` when a scope is set). `Shipit::Api::CCMenuController` overrides `#stack` to call `Stack.from_param!(params[:stack_id])` directly, completely skipping the scoping check, so a token that is only authorized for one specific stack can be used to fetch the CCMenu status (deploy state) of any other stack in the installation.

### Finding Description
`Shipit::ApiClient` can be scoped to a single stack via its `stack_id` column, exactly as seen in the `here_come_the_walrus` fixture (`stack: shipit`, `permissions: ['read:stack']`) [1](#0-0) . This is exactly how `CCMenuUrlController` mints tokens in production: it creates (or reuses) an `ApiClient` with `read:stack` permission for the *current user* [2](#0-1) , and embeds the resulting `authentication_token` as a `token` query-string parameter in a CCMenu URL meant to be handed to third-party CI dashboard tools [3](#0-2) .

The generic API scoping mechanism lives in `Shipit::Api::BaseController`:
```ruby
def stacks
  @stacks ||= current_api_client.stack_id? ? Stack.where(id: current_api_client.stack_id) : Stack.all
end

def stack
  @stack ||= stacks.from_param!(params[:stack_id])
end
``` [4](#0-3) 

Every other API controller (`CommitsController`, `DeploysController`, `TasksController`, `StacksController`, etc.) inherits this `#stack`/`#stacks` behavior, so a token scoped to stack A cannot address stack B, confirmed by the test "an api client scoped to a stack will only see that one stack" [5](#0-4) .

However, `Shipit::Api::CCMenuController` overrides `#stack` and resolves it without going through the scoped `stacks` collection:
```ruby
class CCMenuController < BaseController
  require_permission :read, :stack

  def show
    latest_deploy = stack.deploys_and_rollbacks.last || NoDeploy.new
    render('shipit/ccmenu/project', formats: [:xml], locals: { stack:, deploy: latest_deploy })
  end

  private

  def stack
    @stack ||= Stack.from_param!(params[:stack_id])
  end

  def authenticate_api_client
    @current_api_client = ApiClient.authenticate(params[:token])
    super unless @current_api_client
  end
end
``` [6](#0-5) 

`require_permission :read, :stack` only checks that the client's permission list contains the literal string `"read:stack"` via `ApiClient#check_permissions!` [7](#0-6)  — it never checks *which* stack the permission applies to. The only place that enforces the per-token stack restriction is the overridden, bypassed `#stack` method.

**Binding broken:** *the stack a token authorizes* (`ApiClient#stack_id`, set when the CCMenu token was minted for one specific stack) **≠** *the stack the request actually touches* (`params[:stack_id]`, freely chosen by the caller and resolved via unscoped `Stack.from_param!`).

Before the flaw: for every other endpoint, `client.stack_id == A` implies only stack A is reachable.
After using CCMenu: `client.stack_id == A`, but `GET /api/ccmenu/{owner}/{repo-B}/{env}?token=<A-scoped token>` still succeeds and returns stack B's data — the equality no longer holds.

### Impact Explanation
This grants an **unauthenticated read of stack state / deploy output** for stacks the token holder was never authorized to see. CCMenu tokens are handed out per-stack (typically embedded in a URL configured in third-party CI dashboard tools such as CCMenu/CCTray clients), so anyone possessing a single stack's CCMenu URL can enumerate `owner/repo/environment` triples and pull the latest build/deploy status (name, last build status, last build label/time, activity, web URL) for every other stack hosted by the same Shipit instance, in direct violation of the stack scoping the token was supposed to enforce. This matches the "High — unauthenticated read of stack state, task streams or deploy output" impact category.

### Likelihood Explanation
Likelihood is high for any Shipit deployment that uses the CCMenu integration feature (`CCMenuUrlController`) to hand out per-stack tokens to external tooling, since:
- The token is a simple `token` query-string parameter, routinely embedded in URLs shared with third-party dashboards, and does not require any special network position.
- No additional secret or GitHub credential is needed — only a previously obtained, legitimately-scoped CCMenu token and knowledge of another stack's `repo_owner/repo_name/environment` path (stack names are often predictable or discoverable, e.g. via the same organization's other public CCMenu URLs).
- The bypass is a straightforward method override in the controller, not a race condition or timing issue, so it is 100% reproducible.

### Recommendation
Remove the private `#stack` override in `Shipit::Api::CCMenuController` (or make it delegate to the inherited scoped `#stack`/`#stacks` from `BaseController`) so CCMenu requests are resolved via `stacks.from_param!(params[:stack_id])` instead of the unscoped `Stack.from_param!(params[:stack_id])`. This ensures the `ApiClient#stack_id` restriction is uniformly enforced across all API surfaces.

### Proof of Concept
1. As an authenticated Shipit user on stack `org/repo-a/production`, visit the CCMenu settings and let `CCMenuUrlController#fetch` mint a token scoped to that stack (`ApiClient.create_with(permissions: %w[read:stack]).find_or_create_by!(creator: current_user, name: 'CCMenu Client')`, then `stack_id` set to `repo-a/production`'s id) [8](#0-7) . Obtain the resulting `ccmenu_url` containing `?token=<T>`.
2. Using that same token `T`, request a *different* stack's CCMenu endpoint:
   `GET /api/ccmenu/org/repo-b/staging?token=<T>`
3. `Api::CCMenuController#authenticate_api_client` authenticates `T` successfully (`ApiClient.authenticate(params[:token])`), and `require_permission :read, :stack` passes because `T`'s permission list contains `"read:stack"` regardless of stack. `#stack` then resolves `repo-b/staging` directly via `Stack.from_param!`, ignoring `T.stack_id` [9](#0-8) .
4. The response renders `repo-b/staging`'s latest deploy status in the CCMenu XML, even though `T` was only ever authorized for `repo-a/production` — confirming the scoping bypass.
