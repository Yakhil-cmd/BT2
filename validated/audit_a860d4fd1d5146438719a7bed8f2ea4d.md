### Title
Headers-commission split among multiple recipients can mint extra spendable balance via independent per-recipient rounding - ([File: headers_commission.js])

### Summary
Just like the Velar-Artha funding-fee bug where independently rounding `long_utilization`/`short_utilization` produces a result that no longer matches the "true" fee, ocore independently rounds each recipient's share of a payer unit's `headers_commission` with `Math.round(full_amount * share / 100.0)` in `headers_commission.js`. Because each recipient's amount is rounded separately instead of using a remainder-preserving allocation, the sum of the rounded amounts can differ from `full_amount` (the actual commission earned from the payer unit). When it rounds *up*, the protocol creates spendable `headers_commission_outputs` that exceed the commission the payer unit actually possesses, i.e. new money is minted from rounding.

### Finding Description
Multi-authored units can declare `earned_headers_commission_recipients`, an array of `{address, earned_headers_commission_share}` whose shares are validated only to sum to exactly 100: [1](#0-0) 

When a unit becomes the winner of a header commission from a parent (`payer_unit`), the full amount `full_amount = headers_commission` of the payer unit is split among the winning child unit's declared recipients using independent `Math.round()` per recipient, both in the "in-RAM" fast path and in the SQL/DB fallback path: [2](#0-1) [3](#0-2) 

These per-recipient amounts are then simply inserted into `headers_commission_contributions` and subsequently summed by `main_chain_index, address` into `headers_commission_outputs`: [4](#0-3) 

There is no step anywhere that re-normalizes the rounded amounts so that `SUM(amount over all recipients) == full_amount`. Standard "round half up" (`Math.round`) applied independently to fractional percentages that sum to exactly 100 can still cause the aggregate rounded total to exceed the original amount. A trivial example: `full_amount = 1`, two recipients with `share = [50, 50]`. Each recipient's amount is `Math.round(1 * 50 / 100.0) = Math.round(0.5) = 1`. The two entries sum to `2`, i.e., double the real `headers_commission`. This inflated total flows straight into `headers_commission_outputs`, which is later spendable as a real "headers_commission" type input in payments: [5](#0-4) [6](#0-5) 

`readNextSpendableMcIndex`/`findMcIndexIntervalToTargetAmount`/`calcEarnings` treat every row in `headers_commission_outputs` as legitimately spendable value with no cross-check against the payer unit's actual `headers_commission` field once it has been split among recipients, so the excess created by rounding becomes real, permanently spendable base-currency balance for the recipients.

This mirrors the Velar-Artha root cause exactly: individually rounding percentage-derived fee shares (there, `long_utilization`/`short_utilization`; here, `earned_headers_commission_share`-derived amounts) breaks the invariant that the parts sum to the whole, and the direction of the rounding error benefits (or, in Velar's case, harms) the counterparties instead of the protocol.

### Impact Explanation
This is a supply-inflation vector reachable by any unprivileged unit poster: an attacker composes a multi-authored unit (2+ authors, which is fully permitted for regular users) and freely chooses `earned_headers_commission_share` values that maximize the rounding-up error (e.g., an odd `full_amount` split into shares causing `.5`-boundary roundings for several recipients). Every headers-commission win by such a unit mints small amounts of extra bytes that are indistinguishable from legitimately earned commission and are fully spendable once the relevant MC index is stable. Although the excess per event is small (bounded by roughly `number_of_recipients / 2` bytes), it is unconditionally exploitable, repeatable indefinitely, and requires no special privileges, satisfying the "supply inflation" acceptance criterion.

### Likelihood Explanation
Likelihood is high for a determined attacker: composing multi-author units with custom `earned_headers_commission_share` distributions is a normal, protocol-supported operation (see `composer.js` respecting `params.earned_headers_commission_recipients`), and winning at least one headers-commission distribution per unit posted happens routinely as part of consensus (every unit contributes headers commission to its best child). An attacker only needs to consistently post multi-authored units and repeatedly harvest the rounding surplus over time; each individual step is cheap and requires only DAG parent/child participation, no privileged role.

### Recommendation
Replace independent `Math.round()` per recipient with a remainder-preserving allocation algorithm (e.g., largest-remainder method): compute each recipient's floor amount, sum the floors, and distribute the leftover (`full_amount - sum(floors)`) to the recipients with the largest fractional remainders (or deterministically to a fixed recipient, e.g. the first by address) so that `SUM(amount) == full_amount` always holds exactly. Apply the same fix consistently between the in-RAM path and the SQL/MySQL path in `headers_commission.js` so both continue to produce identical, exact results.

### Proof of Concept
1. Create a multi-authored unit `U` with two authors `A` and `B` and `earned_headers_commission_recipients = [{address: A, earned_headers_commission_share: 50}, {address: B, earned_headers_commission_share: 50}]` (validated in `validateHeadersCommissionRecipients`, requiring only that shares sum to 100).
2. Arrange (as is routine in DAG participation) for `U` to win the headers commission from some parent `payer_unit` whose `headers_commission` equals an odd number, e.g. `1` byte (any odd `full_amount` works; larger odd amounts amplify the absolute size of the exploit across many recipients).
3. In `calcHeadersCommissions`, `full_amount = 1` is split: `amount_A = Math.round(1 * 50 / 100.0) = 1`, `amount_B = Math.round(1 * 50 / 100.0) = 1`. Two rows are inserted into `headers_commission_contributions`, totalling `2`, while the payer unit only ever "earned" `1`.
4. After MCI stabilization, `headers_commission_outputs` accumulates `2` for addresses `A`/`B` combined, both of which become spendable via `type: "headers_commission"` inputs (`inputs.js:173-176`, `mc_outputs.js:116-132`), i.e. `1` extra byte of currency has been minted out of thin air relative to the actual commission generated by the network.
5. Repeating this with many multi-authored units (and optimizing share values/`full_amount` parity to always round up) allows continuous accumulation of newly minted currency.

function validateHeadersCommissionRecipients(objUnit, cb){
	if (objUnit.authors.length > 1 && typeof objUnit.earned_headers_commission_recipients !== "object")
		return cb("must specify earned_headers_commission_recipients when more than 1 author");
	if ("earned_headers_commission_recipients" in objUnit){
		if (!isNonemptyArray(objUnit.earned_headers_commission_recipients))
			return cb("empty earned_headers_commission_recipients array");
		var total_earned_headers_commission_share = 0;
		var prev_address = "";
		for (var i=0; i<objUnit.earned_headers_commission_recipients.length; i++){
			var recipient = objUnit.earned_headers_commission_recipients[i];
			if (!isPositiveInteger(recipient.earned_headers_commission_share))
				return cb("earned_headers_commission_share must be positive integer");
			if (hasFieldsExcept(recipient, ["address", "earned_headers_commission_share"]))
				return cb("unknown fields in recipient");
			if (!isValidAddress(recipient.address))
				return cb("invalid recipient address checksum");
			if (recipient.address <= prev_address)
				return cb("recipient list must be sorted by address");
			total_earned_headers_commission_share += recipient.earned_headers_commission_share;
			prev_address = recipient.address;
		}
		if (total_earned_headers_commission_share !== 100)
			return cb("sum of earned_headers_commission_share is not 100");
	}
	cb();
}

function calcEarnings(conn, type, from_main_chain_index, to_main_chain_index, address, callbacks){
	var table = type + '_outputs';
	conn.query(
		"SELECT SUM(amount) AS total \n\
		FROM "+table+" \n\
		WHERE main_chain_index>=? AND main_chain_index<=? AND +address=?",
		[from_main_chain_index, to_main_chain_index, address],
		function(rows){
			var total = rows[0].total;
			if (total === null)
				total = 0;
			if (typeof total !== 'number')
				throw Error("mc outputs total is not a number");
			callbacks.ifOk(total);
		}
	);
}
