### Title
Uncaught exceptions in async oscript formula evaluation crash all full nodes on a crafted AA trigger - ([File: formula/evaluation.js])

### Summary
CVE-2018-4118 is a WebKit memory-corruption bug in which a crafted web page causes RCE/crash while processing untrusted content. The bug-class analog in ocore is "attacker-controlled content reaching an interpreter and causing an unhandled fault that crashes the application." In ocore, untrusted content reaching an interpreter is exactly what happens with Autonomous Agent (AA) trigger data being fed into the oscript formula evaluator, `exports.evaluate` in [1](#0-0) . The evaluator contains dozens of `throw Error(...)` statements guarding "should never happen" states, several of which execute inside deeply nested asynchronous callbacks (`async.eachSeries`, `setImmediate`). Because these throws occur asynchronously, they are not caught by any surrounding `try/catch`, and propagate as Node.js `uncaughtException` events, which the process-level handler in `network.js` deliberately re-throws to crash the entire process.

### Finding Description
Any address can post a unit that pays into an Autonomous Agent, which is validated and executed deterministically by every full node via `validateAATrigger` [2](#0-1)  and `aa_composer.handleTrigger` [3](#0-2) . AA formula bodies (init/state/messages formulas, chosen by the AA's author, who may also be the attacker deploying their own malicious AA) are evaluated against attacker-controlled `trigger.data` by `formula/evaluation.js`'s recursive `evaluate()` function.

The evaluator's `evaluate()` runs asynchronously — expressions are walked via `async.eachSeries` and, to bound call-stack depth, control is explicitly handed back to the event loop every 100 evaluation steps via `setImmediate`: [4](#0-3) . Throughout the switch statement handling different oscript operators, there are numerous `case` branches that call bare `throw Error(...)` instead of the safe `setFatalError(...)` helper used everywhere else for user-triggerable bad input, e.g. the `ifelse` handler: [5](#0-4) , the `default` case for unrecognized ops [6](#0-5) , and many other type-mismatch branches throughout the file (49 occurrences of `throw Error` in this file alone). Because these throws happen inside a callback fired later on the event loop (not inside the synchronous stack of the original caller), no `try/catch` wrapping the top-level call to `evaluate()` in `aa_composer.js` or `validation.js` can catch them.

Once such an exception escapes uncaught, it reaches the global handler installed in `network.js`, which is explicit about intentionally crashing the process to avoid an inconsistent state: [7](#0-6) . This mirrors the WebKit bug class where processing of hostile content leads to an unrecoverable crash of the whole application, except here every full node that processes the same crafted unit (needed for consensus, since AA state transitions must be deterministic and universally recomputed) crashes identically and simultaneously.

### Impact Explanation
If an attacker can construct a formula/trigger-data combination that reaches one of the un-guarded `throw Error(...)` branches in `evaluate()` at runtime (bypassing the static formula validator in `formula/validation.js`, which only performs limited compile-time type checks and cannot fully enumerate all runtime type combinations produced by dynamic `trigger.data`), then every full node that executes the AA in response to the malicious unit will hit the same uncaught exception and crash via the `uncaughtException` handler in `network.js`. Because AA execution is deterministic and mandatory for maintaining consensus state, this is not a single-node crash but a synchronized crash of the entire set of full nodes processing that unit — a network unable to confirm new units, which is one of the accepted impact categories.

### Likelihood Explanation
The attacker fully controls both sides of the attack surface required to trigger this: they can author and deploy their own AA definition (choosing the formula) and immediately send the triggering unit with data of their choosing. No cooperation from any other party, elevated privileges, or waiting on external state is required — this is a self-contained, single-poster attack analogous to how CVE-2018-4118 only required luring a victim to a crafted page (here, only broadcasting one crafted unit is required for it to eventually be processed by every full node). The likelihood is limited only by the difficulty of finding one specific concrete formula/trigger-data pair that survives static `formula/validation.js` checks and reaches one of the many un-guarded `throw` sites at runtime — this was not exhaustively proven with a minimal working formula in this review, so it should be verified by fuzzing `formula/evaluation.js`'s type-narrowing branches (particularly the many locations doing `typeof x === 'object'`/`unknown type of ...` checks after partial, not exhaustive, `isValidValue`/`wrappedObject` narrowing).

### Recommendation
- Replace all remaining bare `throw Error(...)` calls inside `evaluate()`'s callback-driven code paths in `formula/evaluation.js` with the existing `setFatalError(...)` mechanism, which safely bubbles the error back to `callback(err, null)` instead of throwing synchronously.
- Wrap every `evaluate()` invocation, and the callback bodies passed into `async.eachSeries`/`setImmediate` inside it, so any thrown error is caught and converted into a formula-evaluation failure (bounced AA response) instead of propagating to `process.on('uncaughtException')`.
- Add fuzz/property-based tests that feed deeply nested, mixed-type `trigger.data` into every oscript operator to systematically discover any remaining reachable `throw Error` sites.
- Consider making the `uncaughtException` handler in `network.js` more defensive for errors that can be attributed to a specific unit/AA validation, e.g., by isolating AA execution in a way that a formula-evaluation crash results in bouncing that one trigger rather than terminating the whole process.

### Proof of Concept
Conceptual attack outline (exact minimal formula not independently verified in this review):
1. Attacker deploys an AA whose `messages`/`state` formula is designed so that, for a `trigger.data` value the attacker fully controls, a runtime code path evaluates a value whose type is not fully narrowed by the `isValidValue`/`wrappedObject` checks preceding one of the un-guarded `throw Error(...)` branches in `evaluate()` (e.g., the `ifelse` handler at [5](#0-4)  or another of the 49 `throw Error` sites in the file).
2. Attacker sends a payment + `data` message unit to that AA address, matching `validateAATriggerObject` requirements [8](#0-7) .
3. Every full node validates and executes the AA trigger via `handleTrigger` → `formulaParser.evaluate`, hitting the same `throw Error(...)` inside an asynchronous callback.
4. The exception escapes to Node's `uncaughtException` handler in `network.js`, which re-throws and crashes the process on all full nodes that processed the unit, halting confirmation of new units network-wide.
