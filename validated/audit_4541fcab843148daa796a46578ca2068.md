### Title
Webhook signature bypass for organizations with unconfigured secret allows cross-organization forged commit statuses/pushes leading to unauthorized deploy - ([File: app/controllers/shipit/webhooks_controller.rb])

### Summary
`WebhooksController#verify_signature` selects *which* GitHub App/organization's webhook secret to verify a signature with based on an attacker-controlled JSON field in the unauthenticated request body, and `GitHubApp#verify_webhook_signature` treats a missing (`nil`) `webhook_secret` as automatically valid. Combined, an unauthenticated caller can produce a "verified" webhook whose repository fields are then used, unchecked, by handlers such as `StatusHandler`/`PushHandler` to write state (commit statuses, sync) against *any* repository/stack known to Shipit — not just repositories belonging to the organization that "authenticated" the request.

### Finding Description
The equality that should hold is:

`organization whose webhook secret validated the signature == organization owning the repository the handler writes to`

`WebhooksController#verify_signature` picks the signing organization purely from the untrusted payload: [1](#0-0) [2](#0-1) 

`repository_owner` is read directly from `params.dig('repository', 'owner', 'login')` (or `organization.login`), both fully attacker-controlled since this happens before any signature check. This selects a `GitHubApp` instance via `Shipit.github(organization: repository_owner)`: [3](#0-2) 

The signature verification for that org's app is: [4](#0-3) 

`return true unless webhook_secret` means that if *any* configured organization in the multi-org `github:` config has no `webhook_secret` set (shown as the default/example state in `config/secrets.development.example.yml`, `test/dummy/config/secrets_double_github_app.yml`, and `docs/setup.md`), a request claiming `repository.owner.login` equal to that organization will pass verification unconditionally — no secret needs to be known or guessed.

Once "verified", `WebhooksController#create` dispatches the full, still fully attacker-controlled JSON payload to handlers: [5](#0-4) 

Handlers resolve the target `Repository`/`Stack` using `payload.dig('repository', 'full_name')`, which is a separate field from the one used to pick the signing org, and is not required to match it: [6](#0-5) [7](#0-6) 

Because `repository.owner.login` (used for auth) and `repository.full_name` (used to select the stack that gets written to) are independent, attacker-controlled fields, an attacker can set `repository.owner.login` to the unsecured org to pass verification, while setting `repository.full_name` to `victim-org/victim-repo` to target a stack belonging to a *different*, properly-secured organization.

### Impact Explanation
This breaks the "organization that authenticated versus the repository that is written" trust binding. Concretely, the `status` webhook handler creates `Commit::Status` records from the forged payload for the targeted commit/stack (via `Commit#create_status_from_github!`), and `Commit#deployable?` depends directly on status state: [8](#0-7) 

By forging a `success` status context that satisfies `stack.required_statuses`/`ci.require`, an unprivileged, unauthenticated internet requester can make an otherwise-failing or CI-pending commit appear `deployable?`, enabling continuous-deployment or a user-initiated deploy of unreviewed/failing code to production — an unauthorized deploy. The `push` handler similarly allows forcing `sync_github` on arbitrary stacks. This satisfies the Critical "unauthorized deploy" impact bar.

### Likelihood Explanation
Likelihood depends entirely on deployment configuration: the multi-organization `github:` schema (`Shipit.github(organization: ...)`) must be in use, and at least one configured organization must have `webhook_secret` left unset — which is exactly the state shown as the default/example in the shipped config templates (`config/secrets.development.example.yml`, `config/secrets.development.shopify.yml`, `test/dummy/config/secrets_double_github_app.yml`), suggesting this is not an unusual or purely theoretical configuration. `/webhooks` requires no session, token, or other credential — it is reachable by any unauthenticated internet client. No private key, GitHub App secret, or session is needed.

### Recommendation
- In `GitHubApp#verify_webhook_signature`, do not implicitly return `true` when `webhook_secret` is blank in a multi-organization configuration; require an explicit opt-in (e.g. only allow bypass for the legacy single-org schema) or fail closed.
- In `WebhooksController`, after verifying the signature, assert that the resolved `repository_owner` (used to select the signing org) matches the owner embedded in `repository.full_name` (and any `organization.login`) before dispatching to handlers, rejecting mismatches with `422`.
- Consider binding the resolved `GitHubApp`/organization explicitly to the `Repository` record looked up by handlers, rather than trusting payload-supplied ownership fields independently in each handler.

### Proof of Concept
Given a Shipit deployment configured with multiple GitHub organizations where `OrgTwo` has no `webhook_secret` (the shipped default), and a target stack `victim-org/critical-app` belonging to a securely-configured org:

```
POST /webhooks HTTP/1.1
X-Github-Event: status
X-Hub-Signature: sha1=0000000000000000000000000000000000000000   (arbitrary/unknown value)

{
  "sha": "<sha of a currently-failing/pending commit on victim-org/critical-app>",
  "state": "success",
  "context": "ci/required-check",
  "target_url": "https://example.com",
  "description": "forged",
  "repository": {
    "owner": { "login": "OrgTwo" },
    "full_name": "victim-org/critical-app"
  }
}
```

- `WebhooksController#verify_signature` resolves `repository_owner` = `"OrgTwo"`, fetches `Shipit.github(organization: "OrgTwo")`, whose `webhook_secret` is `nil`, so `verify_webhook_signature` returns `true` regardless of the bogus `X-Hub-Signature`.
- `StatusHandler` (via `Shipit::Webhooks::Handlers::Handler#stacks`/`#repository_name`) looks up `Repository.from_github_repo_name("victim-org/critical-app")` and creates a `success` status for the given `sha` on that stack.
- If `ci/required-check` was the missing/failing required status, `commit.deployable?` on `victim-org/critical-app` flips to `true`, allowing an unauthorized deploy of that commit (directly via continuous deployment, or by an authenticated-but-otherwise-legitimate user deploying without knowing CI was forged).

Note: I could not execute this against a live instance; verification is based on static code review of the cited files. The exact list of which orgs ship with `webhook_secret` unset in any given real-world deployment cannot be confirmed from the index alone, but the shipped example/template configs default to this state.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
