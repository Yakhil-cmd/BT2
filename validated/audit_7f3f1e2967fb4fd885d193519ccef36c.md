### Title
Cross-tenant PR handler mutation via unbound `repository_owner` used for webhook signature verification vs. `repository.full_name` used for data lookup - (File: app/controllers/shipit/webhooks_controller.rb, lib/shipit/github_app.rb, app/models/shipit/webhooks/handlers/pull_request/assigned_handler.rb)

### Summary
`Shipit::WebhooksController#verify_signature` selects which organization's `webhook_secret` to validate against using `repository_owner`, computed from `params.dig('repository','owner','login')` in the attacker-controlled JSON body [1](#0-0) . `Shipit::Webhooks::Handlers::PullRequest::AssignedHandler`, however, locates and mutates the target repository/stack/PR using a completely separate field, `params.repository.full_name` [2](#0-1) . Because nothing binds these two fields together, an attacker can pick an organization with no configured `webhook_secret` (which causes `verify_webhook_signature` to unconditionally return `true`) for the "owner" field while pointing `repository.full_name` at a victim org/repo whose PR record actually gets updated.

### Finding Description
The invariant that should hold is: `organization_that_verified_signature == organization_owning_mutated_repository`, i.e. `repository_owner` (used in `verify_signature`) must equal the owner of `Shipit::Repository.from_github_repo_name(params.repository.full_name)` (used in `AssignedHandler#repository`). These are never compared.

Path:
1. `POST /webhooks` with header `X-Github-Event: pull_request` reaches `WebhooksController#create` after `before_action :check_if_ping, :drop_unhandled_event, :verify_signature` [3](#0-2) .
2. `verify_signature` computes `repository_owner` from `params.dig('repository','owner','login') || params.dig('organization','login')` and calls `Shipit.github(organization: repository_owner).verify_webhook_signature(...)` [4](#0-3) .
3. `GitHubApp#verify_webhook_signature` short-circuits to `true` whenever that specific organization has no configured `webhook_secret` — `return true unless webhook_secret` — before the signature string is ever split [5](#0-4) . (This is why the "malformed `X-Hub-Signature` with no `=`" detail from the question is largely moot: for a secretless org the split is never reached at all, and for a secreted org a malformed header simply fails `algorithm == 'sha1'` and returns `false`. The exploitable gap is the missing binding, not the split parsing itself.)
4. Once verification passes (because the *claimed owner org* has no secret), `Shipit::Webhooks.for_event('pull_request')` fans the same JSON payload out to all PR handlers, including `AssignedHandler` [6](#0-5) .
5. `AssignedHandler#repository` and `#pull_request` resolve the target strictly from `params.repository.full_name`, independent of the field used in step 2 [2](#0-1) . If `action` is `assigned`/`unassigned` and a matching `Shipit::PullRequest` exists for that repository/number, `pull_request.update(github_pull_request: params.pull_request)` is executed, overwriting the victim's stored PR metadata (title, state, head sha/ref, assignees, labels, additions/deletions) [7](#0-6) .

No existing guard prevents this: `drop_unhandled_event` only checks the event has a handler, `verify_signature` only ever validates against the org named in the same forged payload, and none of the `ExplicitParameters` schemas for the handler assert consistency between `repository.owner.login`/`organization.login` and `repository.full_name`.

### Impact Explanation
An unauthenticated attacker can overwrite `github_pull_request` metadata (state, head sha/ref, labels, assignees, title, additions/deletions) on any existing `Shipit::PullRequest` belonging to an arbitrary repository/stack that they do not own, as long as they can name any GitHub organization configured in Shipit without a `webhook_secret` for the outer `repository.owner`/`organization` field. This is a cross-tenant write ("a payload for one repository mutating another's stack/PR record"), matching the Critical impact category. The attack is repeatable against any PR number/repository combination and requires no credentials, session, or API token.

### Likelihood Explanation
Exploitability is conditioned on the Shipit deployment having at least one configured GitHub organization/app entry with no `webhook_secret` set (an optional, documented field — see `docs/setup.md` and `config/secrets.development.example.yml`), and on `Shipit.github(organization: ...)` not raising `GithubOrganizationUnknown` for that org name (i.e., the org must be a real, configured entry, just one lacking a secret). Given that requirement is met, the attacker's cost is a single unauthenticated HTTP POST with a crafted JSON body and correct `X-Github-Event` header — trivially repeatable.

### Recommendation
Bind the organization used for signature verification to the organization that actually owns the repository being mutated: derive `repository_owner` from the same repository record resolved by the handler (e.g., verify against `Shipit::Repository.from_github_repo_name(params.dig('repository','full_name'))`'s owner), or reject events where `params.dig('repository','owner','login')` does not match the owner segment of `params.dig('repository','full_name')`. Additionally, do not allow `verify_webhook_signature` to return `true` for organizations without a configured secret if that organization can be attacker-selected independently of the repository actually mutated; consider requiring a secret for every configured organization/app.

### Proof of Concept
minitest plan (to place under `test/controllers/webhooks_controller_test.rb`, following existing test scaffolding patterns in that file — no live GitHub):
1. Configure two orgs in the test `Shipit.github_apps`/dummy secrets: `no-secret-org` (no `webhook_secret`) and `victim-org` (used only as the actual repository owner, does not need its own secret configured for the test as long as `no-secret-org` is the one validated).
2. Create `victim_repository = Shipit::Repository.create!(owner: 'victim-org', name: 'victim-repo', ...)`, a `Stack` and a `Shipit::PullRequest` under it with `number: 42` and known `github_pull_request` state (e.g. `state: 'open'`, no assignees).
3. POST to `/webhooks` with header `X-Github-Event: pull_request`, no/garbage `X-Hub-Signature`, and JSON body: `{"action":"assigned","number":42,"pull_request":{...different sha/state/assignees...},"repository":{"owner":{"login":"no-secret-org"},"full_name":"victim-org/victim-repo"},"sender":{"login":"attacker"}}`.
4. Assert response is `200 OK` (not `422`), proving `verify_signature` passed based on `no-secret-org`.
5. Reload `pull_request` and assert `pull_request.github_pull_request['state']`/`sha`/`assignees` now equals the attacker-supplied values — proving the victim's PR record (owned by `victim-org`, never in a webhook_secret relationship with `no-secret-org`) was mutated by a payload that was verified against a different organization's (non-)secret.
6. Equality check before: `repository_owner_used_for_verification ("no-secret-org") != repository_that_was_mutated.owner ("victim-org")` — both sides differ, confirming the broken binding.

    def verify_webhook_signature(signature, message)
      return true unless webhook_secret

      algorithm, signature = signature.split("=", 2)
      return false unless algorithm == 'sha1'

      SecureCompare.secure_compare(signature, OpenSSL::HMAC.hexdigest(algorithm, webhook_secret, message))
    end
